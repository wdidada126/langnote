Radix Partitioning HashJoin（基数分区哈希连接）是一种在数据库查询优化中使用的技术，特别是在处理大型数据集时。该技术结合了哈希连接（Hash Join）和分区（Partitioning）的概念，以提高连接操作的效率。以下是对Radix Partitioning HashJoin的详细解释：

1. 哈希连接（Hash Join）基础
概念：哈希连接是一种利用哈希函数来实现和加速数据库中连接（join）操作的算法。它主要适用于等值连接（equi-join）。
步骤：
构建哈希表（Build）：选择两个输入关系（relation）中基数（cardinality）较小的一个（通常称为构建关系或build relation），使用哈希函数将其中的每一条记录的主键（key）值计算为一个哈希值，并根据哈希值将该记录插入到哈希表中。
探测（Probe）：选择另一个基数较大的关系（通常称为探测关系或probe relation），针对其中的每一条记录（通常采用流式遍历的方式），使用和构建关系中相同的哈希函数，计算出相应的哈希值，并根据哈希值在哈希表中寻找到需要比较的记录。如果满足等值条件，则直接输出，得到最终结果。
2. 分区（Partitioning）
概念：当哈希表太大而无法完全存储在内存中时，可以使用分区技术将其分割成多个较小的部分（或分区），每个部分都可以独立地存储在内存中或磁盘上。
作用：通过分区，可以减少内存使用，提高I/O效率，并允许并行处理多个分区，从而进一步提高连接操作的性能。
3. Radix Partitioning HashJoin
概念：Radix Partitioning HashJoin是哈希连接的一种扩展，它使用基数分区策略来优化连接操作。基数分区基于连接键的哈希值将构建关系和探测关系分割成多个不相连的分区，然后各自相应的分区再做哈希连接。
优点：
减少内存使用：通过将哈希表分割成多个较小的分区，可以确保每个分区都能完全存储在内存中，从而避免使用磁盘存储导致的性能下降。
提高并行性：每个分区都可以独立地进行哈希连接操作，从而允许多个处理器或线程并行处理不同的分区，进一步提高整体性能。
适用于大型数据集：基数分区策略可以很好地处理大型数据集，因为它允许将数据集分割成多个较小的部分进行处理。
4. 总结
Radix Partitioning HashJoin是一种高效的数据库连接技术，它结合了哈希连接和分区策略的优点，适用于处理大型数据集和等值连接操作。通过将哈希表分割成多个较小的分区，并在每个分区上独立执行哈希连接操作，可以显著提高连接操作的性能和效率。

在数据库领域中，RBO（Rule-Based Optimization）和CBO（Cost-Based Optimization）是两种重要的查询优化技术，它们的主要目的是生成最佳的执行计划以提高查询效率。
RBO（基于规则优化）
RBO是一种根据预先定义的一套规则来选择执行计划的方法。它不考虑数据的分布和统计信息，仅根据操作符的类型和顺序来决定优先级。RBO的优点在于简单易懂，不依赖于数据的变化，适合于数据量小或者统计信息不准确的情况。然而，RBO的缺点也很明显，它不能适应复杂的查询场景，不能充分利用数据的特征，可能导致执行效率低下。
CBO（基于代价优化）
CBO则是一种根据数据的分布和统计信息来估算每个执行计划的代价，并选择代价最低的执行计划的方法。CBO的优点在于能够根据数据的实际情况来做出最优的选择，适合于数据量大或者查询复杂的情况。然而，CBO的缺点是需要维护数据的统计信息，否则可能导致代价估算不准确，影响执行效果。
在实际应用中，随着数据库技术的发展和数据的增长，CBO逐渐成为主流的优化方法。它可以根据数据的实际情况进行灵活调整，以获取更好的查询性能。同时，随着技术的进步，一些数据库系统也提供了更先进的优化策略，如动态调整执行计划、优化子查询和连接操作等，以进一步提高查询效率。
需要注意的是，无论是RBO还是CBO，都有其适用的场景和限制。在选择使用哪种优化方法时，需要根据具体的数据库环境、数据特点和查询需求进行综合考虑。

我的理解就是，WeakReference对应用的对象userInfoLocal是弱引用，不会影响到userInfoLocal的GC行为。如果是强引用的话，在线程运行过程中，我们不再使用userInfoLocal了，将userInfoLocal置为null，但userInfoLocal在线程的ThreadLocalMap里还有引用，导致其无法被GC回收（当然，可以等到线程运行结束后，整个Map都会被回收，但很多线程要运行很久，如果等到线程结束，便会一直占着内存空间）。而Entry声明为WeakReference，userInfoLocal置为null后，线程的threadLocalMap就不算强引用了，userInfoLocal就可以被GC回收了。map的后续操作中，也会逐渐把对应的"stale entry"清理出去，避免内存泄漏。
　　所以，我们在使用完ThreadLocal变量时，尽量用threadLocal.remove()来清除，避免threadLocal=null的操作。前者remove()会同时清除掉线程threadLocalMap里的entry，算是彻底清除；而后者虽然释放掉了threadLocal，但线种threadLocalMap里还有其"stale entry"，后续还需要处理。

数据库管理系统（DBMS） 管理的是符合特定数据模型的数据，最普遍的是关系数据模型（relational data model）。使用关系模型的DBMS成为RDBMS。关系数据模型中，用户的数据是一个个 ‘关系表’，每个表是数据行的集合，这些数据行具有相同的结构。这个结构主要是指一个关系表包含若干个列，每个列具备一些属性和特征，包括数据类型，完整性约束（是否允许 null 值，是否unique），用户自定义的约束等，这些特征决定了一个列的数据格式，数据使用方法，允许的操作类型和方法，以及确保数据正确的约束条件等。 

除了关系数据模型，数据库系统还出现过其他数据模型，包括层次，网状和对象数据模型，不过这些模型曾经热闹过一阵子后都沉寂下来了。唯二比较流行的是key-value 数据，和json数据模型。这两种nosql数据模型的优点是简单和灵活性，易于快速搭建业务系统，但是通常随着业务系统稳定下来之后，系统开发者又会逐步发现nosql的灵活性的另一面，就是缺乏规范性，任意加减字段等经常会把系统搞崩溃，本质原因是这种做法违背了早已被验证的系统设计理念 --- ‘程序与数据分离’。

除了具备特定的数据模型，数据库系统还需要在其数据模型之上实现方便易用的数据读写方式，对于关系数据库来说，这个读写方式就是SQL语言，对于key-value和json数据来说，通常是API 编程读写，也就是‘程序与数据绑定’了，这显然是个巨大的缺陷。另外对于json数据模型来说，也有厂家自定义的查询语言，但是并没有标准化，比如mongodb有自己的json数据查询语言。另外目前SQL标准当中已经有了json扩展，mysql和postgresql都支持json数据的存取，并且可以与关系数据同时使用，从而大大增加了便利性。

最后，关系数据库还有事务处理系统，实现ACID属性。本质上来说，就是确保并发读写数据的多个用户连接可以同时正确滴工作，互不干扰。并且用户的所有数据读写操作被划分为‘事务’的单位，每个事务要么完全成功执行并且其写入操作持久存在；要么完全不执行----无论系统经历任何故障和错误，都不会出现执行了一部分的事务的写入数据被其他事务读取到的错误情况。

最最后，现代数据库系统还有高可靠性（high availability）和高可扩展性（high scalability）机制，确保DBMS系统在部分节点故障情况下仍然可以对外提供服务，确保系统处理能力可以随着数据库节点的增加而增加。

可以看到数据库管理系统（DBMS）把用户管理其数据的任务从用户软件中独立出来，用户只需要使用简单易用的接口即可通过DBMS 管理和访问其数据。当然，其数据必须是符合特定模型的，比如关系模型，或者json数据格式。从其近50年的发展来看，关系数据模型具备非常普遍的适用性，能够满足大多数数据处理需求。

文件系统是DBMS之下的系统功能。文件系统所管理的数据是‘文件’，而文件的具体格式和内容则并不关心。在文件系统看来，一个文件中存放的就是一串子节或者字符，仅此而已。这种简单性让它具有更加广泛的适用性，但是缺点就是用户需要做的事情就多了很多很多，上述RDBMS可以做的事情，假入使用文件系统来做的话，则需要用户实现全部RDBMS的功能，这是一个难度极其巨大的任务。

## 数据库核心综合笔记：事务、SQL 实战与分布式系统

本节把本目录中 MySQL、MVCC、ARIES、TiDB/TSO、Percolator、分布式事务和 SQL 题整理成一条主线。数据库的核心目标不是“把数据放到磁盘”，而是在故障、并发和规模增长下，让应用仍能以可预测的语义读取和修改数据。

### 1. 一张总图：一次 SQL 经历了什么

```text
SQL / API
  -> Parser 与语义检查
  -> 优化器：逻辑计划 -> 物理计划
  -> 执行器：扫描、连接、排序、聚合
  -> 事务与并发控制：锁、MVCC、验证、提交
  -> 存储引擎：索引、Buffer Pool、WAL、数据页
  -> 磁盘 / 复制日志 / 备份
```

同一条慢 SQL 可能卡在完全不同的位置：没有合适索引时卡在扫描和回表；统计信息失真时卡在错误的连接顺序；被长事务阻塞时卡在锁等待；副本延迟时卡在复制链路。调优前先定位所在层次，不能把所有问题都归结为“加索引”。

### 2. 数据模型、模式设计与约束

关系模型用表、行、列和约束表达业务事实。数据库约束是最后一道数据质量防线，不能只依赖应用层校验。

| 约束或设计 | 解决的问题 | 常见实践 |
| --- | --- | --- |
| 主键 | 唯一标识一行 | 选择稳定、短、不可变的键；InnoDB 主键同时影响聚簇存储。 |
| `NOT NULL` | 区分“未知”和空字符串/零值 | 核心字段尽早定义，避免三值逻辑扩散。 |
| `UNIQUE` | 去重与幂等 | 订单号、外部请求号等业务唯一键应由数据库兜底。 |
| 外键 | 保证引用完整性 | 单库强一致场景可用；高吞吐或分库场景需评估写放大与运维成本。 |
| 检查约束 | 限制值域 | 余额非负、状态枚举等；也可与应用校验结合。 |
| 范式 | 降低更新异常和重复事实 | OLTP 核心数据通常先规范化，再为热点读场景有限反规范化。 |

反规范化不是“多存几列”这么简单。每一份冗余数据都必须回答：谁是事实来源、更新是否在同一事务中、异步同步延迟如何可见、修复与回放如何做。无法回答这些问题时，冗余最终会变成数据不一致。

### 3. ACID：分别保证什么，不保证什么

| 属性 | 含义 | 常见实现基础 | 不代表什么 |
| --- | --- | --- | --- |
| 原子性（Atomicity） | 事务的修改要么全部生效，要么全部撤销 | undo/回滚日志、提交协议 | 不保证外部 RPC、消息或邮件自动回滚。 |
| 一致性（Consistency） | 事务前后满足已定义的完整性约束与业务不变量 | 约束、事务逻辑、并发控制 | 不等于“多个副本立刻相同”。 |
| 隔离性（Isolation） | 并发事务的中间状态不互相错误可见 | 锁、MVCC、验证、串行化 | 不同隔离级别的强度不同。 |
| 持久性（Durability） | 提交成功后，故障恢复不丢失结果 | WAL/redo、刷盘、复制、恢复 | 只写入本机缓存不等于已持久。 |

一致性尤其容易被误解。数据库能保证主键、唯一索引、外键等声明式约束，也能提供某种隔离语义；“转账后两个账户总额不变”“库存绝不为负”等业务不变量仍需要正确的 SQL、事务边界和条件更新共同实现。

一个扣减库存的基本写法是把检查和修改放进同一条原子 SQL：

```sql
START TRANSACTION;

UPDATE inventory
SET available = available - 1
WHERE sku_id = :sku_id
  AND available > 0;

-- 检查受影响行数必须为 1；为 0 则无库存或记录不存在。
INSERT INTO orders(order_no, sku_id, status)
VALUES (:order_no, :sku_id, 'CREATED');

COMMIT;
```

如果 `order_no` 有唯一约束，重复请求会在数据库边界被识别。应用还应定义“唯一冲突后返回原订单还是报错”的幂等语义；ACID 不会替业务自动决定这一点。

### 4. 隔离级别、异常与事务边界

经典异常与 SQL 标准隔离级别的关系如下。具体产品会有额外实现细节，因此要以目标数据库文档和实际测试为准。

| 异常 | 含义 | 常见示例 |
| --- | --- | --- |
| 脏读 | 读到尚未提交、随后可能回滚的数据 | 事务 A 更新余额，事务 B 先读到该余额，A 随后回滚。 |
| 不可重复读 | 同一事务两次读取同一行结果不同 | A 两次读订单，B 在中间提交了更新。 |
| 幻读 | 同一谓词查询两次得到不同的行集合 | A 两次查 `amount > 100`，B 中间插入符合条件的新行。 |
| 丢失更新 | 两个事务基于旧值写回，后写覆盖先写 | 两个请求都将余额 100 改为各自计算的值。 |
| 写偏斜 | 两个事务读到同一快照，各自写不同记录但共同破坏约束 | 两位值班医生都看到另一人值班，各自把自己设为休息。 |

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 典型代价 |
| --- | --- | --- | --- |
| Read Uncommitted | 可能 | 可能 | 可能 | 语义弱，生产 OLTP 很少使用。 |
| Read Committed | 避免 | 可能 | 可能 | 并发较好；每次一致性读可能看到新快照。 |
| Repeatable Read | 避免 | 避免 | 标准定义中仍可能 | 长事务会持有旧视图，版本回收压力更大。 |
| Serializable | 避免 | 避免 | 避免 | 冲突、等待或重试增加。 |

MySQL InnoDB 的 `REPEATABLE READ` 使用 MVCC 一致性读；对加锁读、更新和删除，结合 record lock、gap lock、next-key lock 等机制处理范围并发，实际表现不能简单等同于教科书的一句“RR 一定/一定不幻读”。在 MySQL 中应明确区分普通快照读和 `SELECT ... FOR UPDATE` 这类当前读。

事务应尽量短：不要在事务中等待用户输入、调用远程服务、上传文件或做长时间计算；它们会放大锁持有时间、undo 版本链和复制延迟。事务边界应围绕一个需要共同成功或共同失败的不变量，而不是围绕一个 Java 方法名机械套 `@Transactional`。

### 5. 锁、MVCC 与乐观并发控制

并发控制的共同目标是让冲突事务遵守某种正确的执行顺序，主要路线如下：

| 机制 | 基本思路 | 适用与代价 |
| --- | --- | --- |
| 两阶段锁（2PL） | 先获取锁，提交/回滚后释放 | 冲突时阻塞，容易出现死锁；可实现强隔离。 |
| MVCC | 为同一逻辑行保留多个版本，读按快照选择可见版本 | 读写并发好，但需要版本回收和冲突检测。 |
| OCC | 先无锁执行，提交时验证读写集是否冲突 | 低冲突下吞吐高，高冲突下重试成本高。 |
| 时间戳排序 | 以事务时间戳约束读写顺序 | 实现依赖时间戳与版本管理。 |

InnoDB 中可以把 MVCC 理解为“行版本 + Read View + undo log”。更新会产生新版本；一致性读根据当前事务的可见性规则沿版本链找到应读取的版本。它提升读写并发，但不会让写写冲突消失：两个事务修改同一行仍需加锁或发生冲突。

避免丢失更新的常见策略：

```sql
-- 悲观方式：先锁定要修改的行，适合确实需要读后决策的短操作。
SELECT available FROM inventory WHERE sku_id = :sku_id FOR UPDATE;

-- 乐观方式：版本号只在与读取版本一致时更新；受影响行数为 0 则重新读取或提示冲突。
UPDATE inventory
SET available = :new_available,
    version = version + 1
WHERE sku_id = :sku_id
  AND version = :expected_version;
```

死锁并不说明数据库坏了。并发系统只要允许交叉获取资源就可能死锁；数据库通常会检测环路并回滚一个受害者。正确处理方式是：统一访问顺序、缩短事务、减少不必要范围锁，并在应用中对死锁/序列化失败做有上限且带抖动的重试。不能无限重试，也不能把所有异常都重试。

### 6. WAL、日志与崩溃恢复

写前日志（WAL）的规则是：相关数据页落盘前，描述其修改的日志必须先持久化。数据库可据此在故障后重做已提交修改、撤销未提交修改。

| 日志或结构 | 主要用途 | InnoDB 中的典型对应 |
| --- | --- | --- |
| redo/WAL | 崩溃后重做已记录的页修改 | redo log |
| undo | 回滚事务、构造旧版本 | undo log / 回滚段 |
| binlog | 复制、按时间点恢复、变更审计 | MySQL Server 层二进制日志 |
| checkpoint | 缩短恢复时需要扫描的日志范围 | 脏页推进与检查点 |
| doublewrite | 降低页部分写入损坏风险 | InnoDB doublewrite buffer |

MySQL 的 redo 和 binlog 职责不同：redo 更接近存储引擎恢复所需的物理/页级修改信息，binlog 是用于复制和逻辑变更重放的 Server 层日志。二者的协调提交用于避免“本地已提交但复制日志缺失”或反向不一致。实际备份与恢复方案必须同时考虑数据文件、日志位置、GTID/复制位点和恢复时间目标。

### 7. 索引、执行计划与 SQL 性能

索引的本质是用额外写放大和空间换取更少的读取工作。InnoDB 的聚簇索引叶子节点保存整行数据；二级索引叶子节点保存二级键和主键值，若查询列不在二级索引中，通常还要按主键回表。

设计索引时按以下顺序思考：

1. 明确最重要的查询谓词、连接键、排序和返回列，而不是为每个字段单独建索引。
2. 对联合索引遵循最左前缀；等值条件通常在前，范围条件之后的列是否还能用于排序/过滤取决于计划。
3. 尽可能让高频查询成为覆盖索引，减少回表和随机 I/O。
4. 评估选择性、写入频率和索引维护成本；低基数字段不必然无用，但通常不能单独提供好选择性。
5. 用实际执行计划验证，而不是凭口诀判断。

以下常见说法都不应绝对化：`OR` 不必然导致索引失效，优化器可能选择 index merge；`!=`、`IS NULL`、隐式类型转换、函数包装索引列也不一定“必然全表扫描”，但经常使谓词不可高效利用普通 B+ 树索引。正确做法是写出 SARGable（可搜索）谓词，并查看 `EXPLAIN ANALYZE` 的实际行数、循环次数和耗时。

```sql
-- 不利于普通索引范围扫描：对列做函数计算。
WHERE DATE(created_at) = '2026-08-12'

-- 改为半开区间，通常可以使用 created_at 索引。
WHERE created_at >= '2026-08-12 00:00:00'
  AND created_at <  '2026-08-13 00:00:00'
```

执行计划排查顺序：先确认过滤条件和结果集是否正确，再看估算行数与实际行数偏差、访问路径、连接顺序、是否出现全表扫描/临时表/文件排序、回表次数与锁等待。统计信息过旧、数据倾斜、参数值差异和复杂相关子查询都会使 CBO 选错计划。

### 8. SQL 实战与面试题方法论

面试 SQL 不应只背答案。先写清楚行粒度：结果是一人一行、一天一行，还是一次订单一行；再决定连接、分组、窗口函数和空值语义。

| 题型 | 首选工具 | 容易出错的点 |
| --- | --- | --- |
| 保留左表全部记录 | `LEFT JOIN` | 把右表过滤条件写进 `WHERE` 会把它退化为内连接。 |
| 是否存在关联记录 | `EXISTS` | 只需要存在性时不要先连接再 `DISTINCT`。 |
| 每组 Top N | `ROW_NUMBER`/`RANK`/`DENSE_RANK` | 三者对并列名次的语义不同。 |
| 聚合后过滤 | `HAVING` | `WHERE` 在聚合前过滤，`HAVING` 在聚合后过滤。 |
| 累计值、环比、留存 | 窗口函数 `SUM/LAG/LEAD` | 必须明确 `PARTITION BY` 与稳定 `ORDER BY`。 |
| 连续日期、缺失区间 | 日期序列、窗口函数、差值分组 | 先定义日期去重与时区边界。 |
| 深分页 | keyset/seek pagination | 大 offset 会扫描和丢弃大量行，且并发写入下结果不稳定。 |

每组取最新订单的通用写法：

```sql
WITH ranked_orders AS (
    SELECT
        o.*,
        ROW_NUMBER() OVER (
            PARTITION BY o.user_id
            ORDER BY o.created_at DESC, o.id DESC
        ) AS row_num
    FROM orders AS o
)
SELECT *
FROM ranked_orders
WHERE row_num = 1;
```

`ROW_NUMBER` 表示只保留一条；若并列第一都要返回，用 `RANK`。排序中增加唯一的 `id` 是为了让结果确定，避免同一时间戳的行每次顺序不同。

高性能翻页应使用最后一条记录的排序键，而不是深 offset：

```sql
SELECT id, created_at, title
FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

对应索引应匹配过滤与排序，例如 `(created_at DESC, id DESC)`。在 MySQL 等数据库中也要验证复合行比较、排序方向和索引利用是否与目标版本相符。

### 9. 常见 MySQL 面试题的回答骨架

1. 为什么 InnoDB 用 B+ 树？ 高扇出降低磁盘 I/O 高度；非叶子只存键可容纳更多分支；叶子有序链接，适合范围扫描和排序。不要说成“B+ 树永远最快”，哈希索引、LSM、列存各有场景。
2. 聚簇索引与二级索引？ 聚簇索引叶子保存整行，二级索引叶子通常保存主键；二级索引查不到所需列时会回表。主键过宽会放大所有二级索引。
3. `COUNT(*)`、`COUNT(col)`、`COUNT(1)`？ `COUNT(*)` 统计行数，`COUNT(col)` 忽略 `NULL`；现代优化器中 `COUNT(1)` 通常不比 `COUNT(*)` 更快。大表精确计数本身可能昂贵。
4. `IN` 与 `EXISTS`？ 语义优先：`IN` 比较集合成员，`EXISTS` 判断相关子查询是否至少有一行；优化器常可改写，不能仅凭“外表大用 EXISTS”背结论。注意 `NOT IN` 遇到 `NULL` 的三值逻辑陷阱，常用 `NOT EXISTS` 更稳妥。
5. 慢 SQL 怎么排查？ 收集慢日志/监控样本，拿到参数化后的真实 SQL，用 `EXPLAIN ANALYZE` 比较估算与实际，检查索引、返回列、连接和排序，改写并压测验证，再观察上线指标。
6. 长事务危害？ 长时间持锁、阻塞 DDL/写入、占用连接、阻碍 undo/purge、放大复制延迟和恢复成本。要拆分批次并监控事务年龄。
7. 死锁如何处理？ 找死锁图和事务 SQL，确定锁顺序与索引范围，统一访问顺序、缩短事务、加必要索引，并只对可安全重试的错误做有限重试。

### 10. 复制、高可用、备份与恢复

复制解决的是副本、读扩展和故障切换，不天然等于强一致。

| 模式 | 优点 | 主要风险 |
| --- | --- | --- |
| 异步复制 | 写延迟低、吞吐高 | 主库故障时最近提交可能未到副本。 |
| 半同步复制 | 降低至少一个副本未收到的窗口 | 仍需明确 ACK 语义与故障边界。 |
| 同步复制/共识复制 | 可提供更强提交确认 | 跨机房延迟与可用性成本更高。 |
| 单主读写分离 | 架构简单 | 副本延迟导致读己之写、单调读问题。 |
| 多主 | 多点写入灵活 | 冲突、顺序和运维复杂度显著提高。 |

备份不是“有一份 dump”就结束。至少要定义并演练：RPO（可接受丢失的数据量）、RTO（可接受恢复时间）、全量备份、增量/日志备份、校验、异地副本、按时间点恢复（PITR）和定期恢复演练。没有成功恢复过的备份只能算未验证的假设。

### 11. 分布式数据库的基本架构

分布式数据库将数据分片并复制到多节点，同时仍试图提供统一 SQL、事务和运维入口。常见组件为：

```text
SQL 接入层 / 计算层
  -> 分布式优化器与执行器
  -> 事务协调器、全局时间戳或锁服务
  -> 分片路由与副本调度
  -> 每个分片的复制一致性组与存储引擎
```

分片解决单机容量和吞吐上限，却引入跨分片查询、全局二级索引、重平衡、热点、全局排序分页和分布式事务。分库分表中间件把路由逻辑放在应用/代理侧；原生分布式数据库把事务、复制、调度和优化纳入系统内部。两者的复杂度位置不同，并不会凭空消失。

| 分片方式 | 适用 | 风险 |
| --- | --- | --- |
| 哈希分片 | 负载均匀、点查 | 范围扫描和按时间归档不友好，扩容可能迁移大。 |
| 范围分片 | 时间序列、范围查询 | 热点范围可能集中到单分片。 |
| 一致性哈希 | 节点动态变化 | 查询路由与热点治理仍需设计。 |
| 目录/映射分片 | 灵活路由与迁移 | 目录服务本身需要高可用与一致性。 |

全局 ID 需同时考虑唯一性、排序性、时钟回拨、索引局部性和热点。自增 ID 对单库友好；UUID 随机性可能增加 B+ 树页分裂；时间有序 ID 改善局部性但可能造成写热点；分布式 ID 方案还必须定义时钟异常和重复请求的处理方式。

### 12. CAP、一致性模型与共识

CAP 的准确表述是：在发生网络分区时，系统无法同时保证每个请求都可用（A）和每次读取都满足强一致（C）。分区容错不是平时可随意放弃的选项；真实跨节点系统必须处理网络延迟、丢包和隔离。

一致性也不是只有“强/弱”二选一：

| 语义 | 对使用者的意义 |
| --- | --- |
| 线性一致性（linearizability） | 每个操作像在一个全局实时顺序中原子完成。 |
| 顺序一致性 | 所有人看到同一顺序，但不一定满足实时先后。 |
| 因果一致性 | 因果相关操作的顺序一致，无关操作可不同。 |
| 最终一致性 | 无新写入后副本最终收敛，期间读可能陈旧。 |
| 读己之写、单调读 | 会话级保证，常用于改善用户体验。 |

Raft/Paxos 这类共识协议用于让副本组就日志顺序和 leader 达成一致；它解决单个复制组的复制顺序和故障切换，不自动解决跨分片 SQL、全局事务或业务幂等。不要把“用了 Raft”直接等同于“整个数据库所有读取和事务都是可串行化的”。

### 13. 分布式事务：先区分目标，再选择协议

跨分片或跨服务时，至少要区分三种目标：

| 目标 | 例子 | 典型手段 |
| --- | --- | --- |
| 单数据库内原子提交 | 订单与库存同库 | 本地 ACID 事务。 |
| 多资源原子提交 | 多分片余额同时扣减 | XA/2PC、原生分布式事务、共识事务。 |
| 跨服务业务一致 | 下单、支付、物流、通知 | Saga、TCC、Outbox、可靠消息、幂等消费。 |

两阶段提交（2PC）概念上分为：

```text
prepare：协调者要求所有参与者写入可恢复的预提交状态并持有必要资源
commit/rollback：全部 prepare 成功才提交，否则回滚
```

它能提供原子提交，但 prepare 到最终决定期间可能持锁；协调者或网络故障还会带来阻塞和恢复复杂度。因此 2PC/XA 适合真正需要跨资源强原子性的短事务，不适合把长业务流程、远程 HTTP 调用和人工审核放进去。

Saga 通过一系列本地事务和补偿动作实现最终业务一致，不是数据库级 ACID。补偿不一定是数学上的逆操作，例如优惠券已被使用、外部支付已清算时，往往只能定义业务补偿或人工介入。Outbox 模式把“写业务数据”和“待发送事件”放入同一本地事务，再由可靠发布器投递；消费者以幂等键去重，从而避免双写丢失与至少一次投递重复造成的问题。

### 14. 全局时间戳、Percolator 与 NewSQL

多版本分布式事务常需要全局可比较的时间戳，以定义读快照和提交顺序。中心化 TSO、混合逻辑时钟（HLC）和 TrueTime 是不同的取舍：

| 机制 | 优点 | 代价 |
| --- | --- | --- |
| 中心化 TSO | 顺序清晰、实现相对直接 | 服务热点、跨地域请求延迟，需要高可用 leader。 |
| HLC | 减少对单一授时服务的依赖，兼顾物理与逻辑时间 | 需处理时钟漂移和不确定性语义。 |
| TrueTime 类时间区间 | 可将外部一致性与时间不确定性结合 | 依赖高质量时钟基础设施和等待成本。 |

Percolator 风格事务将数据写入多版本存储，通常用 primary lock 和 secondary locks 组织提交；客户端/协调器以全局时间戳建立快照和提交顺序。它的关键不是“有 TSO 就天然强一致”，而是时间戳、锁记录、提交协议、垃圾回收和底层复制共同给出事务语义。

NewSQL 的目标是结合关系模型/SQL/ACID 与横向扩展，并不意味着所有查询都比单机 MySQL 更快。跨区域强一致、跨分片连接和全局二级索引会付出网络与协调开销；选型应从数据规模、写入热点、事务范围、查询模式、运维能力和一致性需求出发。

### 15. 生产排障清单

1. 查询变慢：确认具体 SQL、参数、执行计划、实际扫描行数、统计信息、CPU/IO/网络、缓存命中和锁等待；不要先盲目加 hint。
2. 连接耗尽：区分连接泄漏、慢查询占用、事务未提交、线程池/连接池配置不匹配和突发流量；限制并发并设置合理超时。
3. 锁等待/死锁：抓取事务、锁和 SQL；找出长事务与访问顺序；修正索引和事务范围，并验证重试是否幂等。
4. 主从延迟：看复制位点、relay/binlog、慢 SQL、大事务、DDL、网络和副本资源；读流量不能无条件导向延迟副本。
5. 磁盘增长：区分数据、索引、undo、redo/binlog、临时文件和备份；长事务会阻碍 MVCC 版本回收。
6. 数据误删/误更新：立刻停止扩大写入，保留日志和时间点，评估 PITR 或旁路恢复，再通过校验与灰度回写修复；不要直接在生产库做未经演练的大范围反向更新。
7. 在线 DDL：先评估锁级别、复制影响、磁盘与回滚窗口；大表变更采用兼容式扩展、双写/回填、校验、切换、延迟删除的演进流程。

### 16. 面试与设计题的完整回答框架

回答事务、索引或分布式数据库问题时，按“需求 -> 语义 -> 实现 -> 代价 -> 观测与降级”展开：

1. 先问清楚读写比、数据量、峰值、延迟目标、是否跨机房、能否接受陈旧读、事务涉及哪些资源。
2. 明确要保证的是本地 ACID、快照隔离、可串行化、读己之写，还是最终一致的业务流程。
3. 说明实现选择：索引/执行计划、MVCC/锁、复制模式、分片键、2PC/Saga/Outbox 等。
4. 主动给出代价和失败模式：锁竞争、热点、跨分片开销、复制延迟、协调器故障、消息重复、恢复流程。
5. 最后说明如何验证：压测数据、`EXPLAIN ANALYZE`、事务/锁监控、复制延迟、备份恢复演练、故障注入和对账。

数据库能力的分水岭不是记住多少名词，而是能把业务不变量翻译为表结构、事务边界、隔离语义、索引和可观测指标，并能在故障或扩容时解释这些保证是否仍然成立。

### 9. 阅读时的统一提问模板

每读到一个机制，都用以下问题把它落到系统设计和代码中：

1. 它保护的对象是什么：一行、一个页面、一个事务、一个副本组，还是一个跨服务业务流程？
2. 它保证的语义是什么：原子性、快照隔离、可串行化、线性一致，还是最终一致？
3. 正常路径和故障路径分别如何运行：进程崩溃、网络分区、重复投递、主从切换时会发生什么？
4. 代价由谁承担：延迟、锁等待、存储版本、网络往返、吞吐下降还是人工补偿？
5. 如何观测和验证：执行计划、锁视图、日志、复制位点、恢复演练、对账或故障注入分别看什么？

- “The Transaction Concept: Virtues and Limitations”（Jim Gray, VLDB 1981）：事务概念的经典阐述，奠定了事务处理的地位。

概率与不确定数据

排序与硬件意识

架构反思

- “Database Systems: Achievements and Opportunities”（Lagunita Report, 1990）：对数据库系统研究方向的重要反思，提出了“改革”与“综合”的研究议程。
