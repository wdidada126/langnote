当查询第100页时SQL执行慢，这通常是因为随着页码的增加，需要扫描的数据量也在增加，导致查询性能下降。为了优化这种情况，你可以考虑以下几个策略：
分页优化：
使用LIMIT和OFFSET进行分页时，随着OFFSET的增加，性能会下降。这是因为数据库需要扫描更多的行来跳过前面的记录。考虑使用“seek method”进行分页，即基于上一次查询的最后一个ID或其他唯一标识进行下一页的查询。
例如，如果你知道第99页的最后一个记录的ID是last_id，你可以查询ID大于last_id的下一个10条记录，而不是使用OFFSET。

### 一、Seek Method（Keyset Pagination）有论文吗？
没有正式学术论文，它是工业界实践驱动的高性能分页范式，核心推动者是 Markus Winand（SQL 性能专家）。

- 起源：2013 年前后，Markus Winand 在博客《Use The Index, Luke》系统化提出，后写入其同名书籍。
- 别名：Keyset Pagination、Cursor Pagination、Seek Pagination。
- 核心文献（非论文）：
  - Markus Winand. *Fetch Next Page* (2013) —— 理论源头。
  - jOOQ 博客. *Faster SQL Pagination with jOOQ Using the Seek Method* (2013) —— 工程化落地。
  - 工业界标杆：Uber、腾讯、阿里、Meta 均采用该方案解决深分页性能灾难。

### 二、Seek Method 核心原理（对比 OFFSET）
#### 传统 OFFSET 分页（致命缺陷）
```sql
SELECT * FROM t ORDER BY id LIMIT 20 OFFSET 10000;
```
- 问题：OFFSET 越大越慢，数据库需扫描并丢弃前 10000 行，复杂度 O(N)。

#### Seek Method（游标/键集分页）
核心：用“上一页最后一条的键”替代“跳过 N 行”
```sql
-- 第一页
SELECT * FROM t ORDER BY id LIMIT 20;

-- 下一页（记住上一页最后一个 id=10000）
SELECT * FROM t WHERE id > 10000 ORDER BY id LIMIT 20;
```
- 优势：索引直接定位，复杂度 O(log N + M)，与页码深度无关。


### 三、工业界最漂亮实践方案（可直接落地）
#### 1. 基础方案：单键游标（唯一有序键）
适用：自增主键、时间戳+主键
```sql
-- 排序：create_time DESC, id DESC
-- 游标：last_create_time, last_id
WHERE create_time < :last_create_time
   OR (create_time = :last_create_time AND id < :last_id)
ORDER BY create_time DESC, id DESC
LIMIT 20;
```
- 要点：排序字段必须全索引，且包含唯一键（如 id） 防止排序漂移。

#### 2. 工业级增强：复合键 + 游标编码 + 前端封装
##### （1）复合键设计（稳定排序）
- 通用模板：`(sort1, sort2, ..., id)`
- 电商：`(price DESC, sales DESC, id)`
- 社交：`(publish_time DESC, like_cnt DESC, id)`

##### （2）游标编码（前端透明）
- 后端返回：`cursor=base64("2026-04-29T23:59:59,12345")`
- 前端请求：`?cursor=xxx&limit=20`
- 优势：不暴露敏感键，前端无需解析游标结构。

##### （3）多方向翻页（上/下一页）
- 正向（下一页）：`> (last_val)` + 正序
- 反向（上一页）：`< (first_val)` + 逆序
- 实现：维护首尾双游标，支持双向无缝翻页。

#### 3. 大厂落地案例
##### （1）腾讯会议：亿级录制列表
- 方案：`user_id + create_time + id` 复合索引，游标分页
- 效果：查询耗时从秒级降至毫秒级，支持千万级用户并发。

##### （2）Uber：行程历史
- 方案：`rider_id + trip_time + id`，游标加密
- 亮点：全球分布式数据库下，分页性能稳定无衰减。

##### （3）jOOQ：框架级支持
- 语法：`seek(limit, last_val)`
- 价值：类型安全、自动生成游标条件，避免手写 SQL 出错。


### 四、终极对比：Seek vs OFFSET
| 维度 | OFFSET 分页 | Seek Method |
| :--- | :--- | :--- |
| 性能 | 随页码增加线性下降 | 稳定毫秒级，与页码无关 |
| 数据一致性 | 易丢数据/重复（增删导致偏移） | 稳定，无漂移 |
| 适用规模 | 万级以下小数据 | 千万/亿级海量数据 |
| 实现复杂度 | 简单（page+limit） | 中等（游标管理+复合索引） |
| 大厂采用 | 几乎淘汰 | 全行业标准（腾讯、阿里、Meta） |


### 五、落地避坑指南
1. 必须唯一有序：排序键必须非空、唯一、单调，否则游标失效。
2. 索引全覆盖：`WHERE + ORDER BY` 字段必须联合索引，避免回表。
3. 无总页数：不支持“跳转到第 N 页”，仅支持上一页/下一页。
4. 游标过期处理：游标对应数据被删除时，自动降级为第一页或提示“无更多数据”。


### 总结
Seek Method 是工业界解决深分页性能问题的唯一最优解，无学术论文但有成熟工业实践体系。核心是用索引键替代偏移量，实现稳定高性能分页。
