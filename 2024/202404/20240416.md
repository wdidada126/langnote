Cache Aside Pattern（旁路缓存模式）
Cache Aside Pattern 是我们平时使用比较多的一个缓存读写模式，比较适合读请求比较多的场景。

Read/Write Through Pattern（读写穿透）Read/Write Through Pattern中服务端把cache视为主要数据存储，从中读取数据并将数据写入其中。cache服务负责将此数据读取和写入db，从而减轻了应用程序的职责
Write Behind Pattern（异步缓存写入）Write Behind Pattern和Read/Write Through Pattern很相似，两者都是由cache服务来负责cache和db的读写。

# MySQL8 EXPLAIN 中 type 字段全解
从最优到最差排序：
`system > const > eq_ref > ref > range > index > all`
只讲**常用必考 5 种**：`const / eq_ref / ref / range`，每种配**可直接运行示例 + 原理 + 优劣**。

先说明：**type 代表 MySQL 表的访问类型**，越靠前性能越好。

## 前置准备（MySQL8 建测试表）
```sql
CREATE TABLE t_user (
    id INT PRIMARY KEY AUTO_INCREMENT,
    phone VARCHAR(20) UNIQUE NOT NULL,
    name VARCHAR(30),
    age INT
);

-- 普通索引
CREATE INDEX idx_name ON t_user(name);
CREATE INDEX idx_age ON t_user(age);

INSERT INTO t_user(phone,name,age) VALUES
('13800138000','zhangsan',20),
('13800138001','lisi',25),
('13800138002','wangwu',30);
```

---

# 1. type = const 常量匹配
## 介绍
- **主键 / 唯一索引** 做 **等值查询**
- 最多匹配**1 行**
- 优化器直接把值当成**常量**，执行前就定位到行，**最快级别**
- 只匹配单行、唯一键等值

## 示例
```sql
EXPLAIN SELECT * FROM t_user WHERE id = 1;

EXPLAIN SELECT * FROM t_user WHERE phone = '13800138000';
```
### 特点
- 主键、唯一索引 精准等值
- 结果最多 1 行
- 性能最优

---

# 2. type = eq_ref 等值关联（联表专用）
## 介绍
- **多表联查**时
- 驱动表每一行，去被驱动表用 **主键 / 唯一索引 等值匹配**
- 每次匹配**只能查到 1 行**
- 联表里**第二优级别**

## 再建一张关联表
```sql
CREATE TABLE t_order (
    order_id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT
);
INSERT INTO t_order(user_id) VALUES (1),(2);
```

## 示例
```sql
EXPLAIN
SELECT u.* FROM t_user u
JOIN t_order o ON u.id = o.user_id
WHERE o.order_id = 1;
```
### 解读
`u.id` 是主键，关联等值匹配，type = `eq_ref`

### 关键点
- 只出现在 **JOIN 联表**
- 关联字段是 **主键 / 唯一索引**
- 每条记录精准匹配 1 行

# 3. type = ref 普通索引等值匹配
## 介绍
- **普通非唯一索引** 做等值查询
- 可以匹配 **多行**
- 不是唯一键，索引叶子节点可能多条相同值
- 日常业务**最常用**级别

## 示例
```sql
-- name 是普通单列索引
EXPLAIN SELECT * FROM t_user WHERE name = 'zhangsan';
```

### 特点
- 普通索引 = 等值条件
- 可能查出多条
- 性能中等，业务可接受

# 4. type = range 索引范围扫描
## 介绍
- 索引上**范围查询**
- 常见场景：
  - `>` `<` `>=` `<=`
  - `BETWEEN AND`
  - `IN()` 大范围
  - `LIKE 'a%'` 前缀模糊

- 走索引，但**扫描一段索引区间**，比 ref 慢，比全表快很多

## 示例
```sql
-- 数值范围
EXPLAIN SELECT * FROM t_user WHERE age > 20;

-- between
EXPLAIN SELECT * FROM t_user WHERE age BETWEEN 20 AND 30;

-- 前缀模糊
EXPLAIN SELECT * FROM t_user WHERE name LIKE 'zhang%';
```

### 注意坑
- `LIKE '%zhang'` 后置模糊 **不走索引**，type 变成 ALL 全表
- `IN` 数据量少时可能 ref，量大直接降级 range

# 补充剩余两个 type（顺带记）
## index 索引全扫描
不走主键，**遍历整个索引树**，比全表 ALL 快，但比 range 慢
```sql
EXPLAIN SELECT id FROM t_user;
```

## ALL 全表扫描
最差，**不走任何索引**，逐行遍历数据页，大数据严禁出现
```sql
EXPLAIN SELECT * FROM t_user WHERE age = 999;
```

# 汇总排序 & 面试背诵
性能从高到低：
**const > eq_ref > ref > range > index > ALL**

| type | 场景 | 核心特征 |
|------|------|----------|
| const | 主键/唯一键 等值单行 | 最快，常量定位 |
| eq_ref | 联表 + 主键/唯一键关联 | 联表精准单行匹配 |
| ref | 普通索引 等值查询 | 可匹配多行 |
| range | 索引范围、between、like前缀 | 扫描索引区间 |


# 优化原则（直接能用）
1. 业务尽量做到 `const / eq_ref`
2. 普通查询保证 `ref`
3. 尽量少用 `range`，避免大区间范围
4. 严禁线上出现 `index / ALL`
