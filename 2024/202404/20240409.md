# 数据库高并发、一致性、各类锁全套对比精讲
按概念→作用→粒度→场景→互相区别一次性讲透：共享锁、互斥锁、意向锁、闩锁，顺带讲清锁粒度优化、提升并发的核心思路。

## 一、先打底：高并发 & 数据一致性 & 锁的关系
1. 高并发访问
大量线程同时读、改、删同一张表/同一行数据。
2. 数据一致性
并发下不出现：脏读、不可重复读、幻读、更新丢失。
3. 锁的本质
用串行化局部操作换数据一致性；
代价是并发下降，所以要做锁粒度优化：能行锁不表锁，能共享不互斥。

---

## 二、四大锁逐个详解 + 对比
### 1. 共享锁 S（读锁）
- 特性：读读共享、读写互斥、写写互斥
- 加锁后：其他事务可以加共享锁读，不能改、不能加互斥锁。
- 场景：批量查询、报表、只读事务。
- 并发友好：高，多人可同时读。

### 2. 互斥锁 X（排他锁 / 写锁）
- 特性：独占，一旦加X锁，其他人既不能读也不能写。
- 加锁后：只有当前事务能读写，其他全部阻塞。
- 场景：更新、删除、强一致性写操作。
- 并发友好：极低，独占资源。

### 3. 意向锁 IS / IX（表级意向锁）
#### 核心作用
解决 表锁 和 行锁 之间的冲突快速判定，不用遍历所有行锁。
#### 原理（你说的：父节点申请意向锁）
InnoDB 是表→行层级结构：
- 事务要加行S/X锁前，先在父表加意向锁
  - 意向共享 IS：我准备在表中某行加读锁
  - 意向排他 IX：我准备在表中某行加写锁

#### 兼容规则
1. 表已经有全表X锁 → 直接阻塞所有行锁
2. 先加意向锁，不用扫描全表所有行，提升锁检测效率
- 意向锁之间互相兼容
- 意向锁 和 全表S/X锁 互斥

#### 一句话记
意向锁是“预告”：我要改你表里某一行，先占个表级位置，防止别人直接锁整张表。

### 4. 闩锁 Latch（shuan 锁）
#### 和事务锁完全不是一回事
- 事务锁（S/X/意向）：业务层面，保护数据行、表，事务提交才释放。
- 闩锁 Latch：引擎底层内存锁，保护缓冲页、索引页、数据页内存结构。

#### 特点
1. 粒度极小：内存页级别
2. 持有时间极短：操作完立刻释放，不等到事务提交
3. 作用：防止多线程同时修改同一个内存页索引、链表、缓冲结构
4. 是 InnoDB 高并发底层基石，比事务锁更轻量、更底层

#### 场景
页拆分、页合并、索引修改、BufferPool 页面读写，全程靠闩锁保护。

---

## 三、锁粒度从粗到细（优化核心）
`数据库实例锁 → 表锁 → 行锁 → 闩锁(内存页)`

### 锁粒度优化原则（提升并发必背）
1. 能行锁绝不表锁
InnoDB 默认行级锁，MyISAM 只有表锁，并发差。
2. 能共享锁不用互斥锁
多读场景用S锁，不阻塞别人读。
3. 缩小锁持有时间
事务尽量小，晚加锁、早提交，不要长事务。
4. 避免不走索引导致行锁变表锁
无索引/索引失效 → InnoDB 行锁退化全表锁，并发直接崩。
5. 利用意向锁减少锁冲突检测开销
数据库内部自动用，不用人工管，但原理要懂。

---

## 四、四种锁横向对比表
| 锁类型 | 层级 | 作用对象 | 持有时长 | 并发影响 | 核心用途 |
|--------|------|----------|----------|----------|----------|
| 共享锁S | 事务层 | 行/表 | 事务周期 | 高 | 只读共享，允许并发读 |
| 互斥锁X | 事务层 | 行/表 | 事务周期 | 低 | 写操作独占，强一致性 |
| 意向锁IS/IX | 事务层(表级) | 表元数据 | 事务周期 | 无负面影响 | 行锁前置预告，加速锁冲突判断 |
| 闩锁Latch | 引擎底层 | 内存数据页 | 极短(毫秒级) | 极小 | 保护索引/缓冲页内存结构 |

---

## 五、高并发+一致性落地总结
1. 数据靠 S共享锁、X互斥锁 保一致性；
2. 意向锁 是表行锁的快速冲突判断机制，底层优化用；
3. 闩锁 是数据库引擎内存页底层锁，和业务事务无关；
4. 提升并发本质：锁粒度尽可能细、锁范围尽可能小、持有时间尽可能短、优先共享锁。

# 二、Java 内置锁：synchronized + wait/notify
## 1. synchronized（内置锁、监视器锁）
- JVM 原生实现
- 可重入、非公平、排他锁
- 锁升级机制：无锁 → 偏向锁 → 轻量级锁（自旋） → 重量级锁（OS互斥量）

## 2. wait() / notify() / notifyAll()
- 必须配合 synchronized 使用
- 必须在同步代码块里调用
- 作用：
  - `wait()`：释放锁 → 进入等待队列
  - `notify()`：随机唤醒一个等待线程
  - `notifyAll()`：唤醒全部等待线程

## 内部联系
synchronized 负责互斥，wait/notify 负责线程间协作通信


# 三、Java 锁的分类（高频考点）
## 1. 按是否公平
- 非公平锁：上来直接抢，不排队 → 吞吐高
- 公平锁：按顺序排队，先来先服务 → 无饥饿

## 2. 按态度
- 悲观锁：认为一定会冲突 → 先加锁再操作（synchronized、ReentrantLock）
- 乐观锁：不加锁，最后用 CAS 版本号判断（AtomicInteger）

## 3. 按等待方式
- 阻塞锁：抢不到锁就挂起（内核态）
- 自旋锁：抢不到锁循环重试（用户态）

## 4. 按共享性
- 排他锁（X）：只有一个线程能持有
- 共享锁（S）：多线程可同时读


# 四、自旋锁 VS CLH 锁（最核心对比总结）
## 1. 自旋锁（SpinLock）
- 原理：抢不到锁就while 循环空转
- 优点：避免线程切换开销
- 缺点：
  - 空转消耗CPU
  - CPU 缓存 ping-pong（大量锁状态同步）
  - 高并发下性能差

## 2. CLH 锁（Craig, Landin, Hagersten）
自旋锁的改进版，AQS 底层核心

### 改进点：
1. 基于链表队列，每个线程只自旋自己的状态
2. 不共享锁变量，避免缓存同步风暴
3. FIFO 公平，不会饥饿
4. 局部性自旋，只看前驱节点状态

### 优点：
- 自旋更轻
- 无缓存同步风暴
- 高并发性能远超普通自旋锁


# 五、最终对比总结（面试必背）
## 自旋锁
- 优点：实现简单、避免线程切换
- 缺点：CPU 消耗高、高并发缓存颠簸
- 场景：低并发、锁持有时间短

## CLH 锁
- 优点：队列公平、局部自旋、无缓存风暴、高并发性能强
- 缺点：实现复杂
- 地位：AQS 底层核心，Java 锁基石


# 六、一句话串起所有知识点（内部联系）
- synchronized 是 JVM 内置的悲观排他锁
- wait/notify 是锁的等待唤醒机制
- CLH 锁是自旋锁的优化，是 AQS 队列锁的底层实现
- ReentrantLock 基于 AQS，支持公平/非公平
- 锁的分类是对不同特性的归纳


### 最终总结
- synchronized + wait/notify = JVM 内置锁体系
- CLH = 自旋锁的高级改进版
- AQS = Java 锁的底层核心
- 所有 Java 锁最终都围绕：阻塞、自旋、队列、CAS、公平性展开
