# 系统设计面试：设计 Pastebin（粘贴分享服务）
## 一、需求澄清（面试第一步必说）
### 功能需求
1. 用户上传文本/代码片段，生成短链接
2. 通过短链接访问查看内容
3. 可选：设置过期时间、私密、密码保护、语法高亮
4. 支持匿名/登录用户提交

### 非功能需求
- 高读低写：读多写少
- 低延迟访问
- 海量文本存储、可扩容
- 短链接全局唯一、长度短
- 防恶意超大内容、防爬虫、防滥用

### 规模估算（粗略）
- 日新增粘贴：100万
- 日阅读量：1000万
- 平均单条内容：512B
- 年存储量 TB 级别，需冷热分离

## 二、整体架构分层（标准4层）
```
客户端/浏览器 → 接入层 → 业务服务层 → 存储层 + 缓存 + 异步队列
```

1. 接入层：Nginx/网关，限流、负载均衡、静态资源
2. API 服务层：提交粘贴、查询粘贴、权限校验、过期逻辑
3. 短链生成服务：全局唯一 ID → 压缩成短串
4. 存储层
   - KV存储：存短链映射、元数据
   - 对象存储：存大文本/代码原文
   - MySQL：用户信息、权限、过期配置、审计日志
5. 缓存：Redis 热点短链缓存
6. 消息队列：异步落库、异步过期清理、统计分析

## 三、核心模块设计
### 1. 短链接生成核心方案（面试必问）
#### 方案选型
- 不适用随机字符串：有碰撞、需查重
- 最优：全局自增ID + Base62 编码

流程：
1. 发号器生成 全局唯一自增 ID（雪花算法 / Redis Incr / 分布式ID）
2. 把十进制 ID 转 Base62（0-9a-zA-Z）
3. 得到 6~8 位短串，作为路由 key

优点：
- 无碰撞、全局唯一
- 短、可解析、高性能

### 2. 数据拆分设计
#### 元数据（存 MySQL/Redis）
```
short_key、content_id、user_id、expire_time、is_private、password、create_time
```

#### 文本原文（存 对象存储 / KV）
- 小文本：直接存 Redis / MySQL 文本字段
- 大代码片段：存 MinIO/OSS，只存对象路径到元数据

### 3. 读写流程
#### 写流程（提交粘贴）
1. 前端提交文本、过期时间、私密配置
2. 网关限流、校验内容大小
3. 生成分布式唯一ID → Base62 得到 short_key
4. 原文存 OSS/KV，拿到 content_path
5. 元数据入库 MySQL
6. 异步写入 Redis 缓存，提升读性能
7. 返回短链接 `domain/short_key`

#### 读流程（访问短链接）
1. 请求 `domain/abc123`
2. 网关拦截，解析 short_key
3. 先查 Redis 缓存
   - 命中：直接返回内容
   - 未命中：查 MySQL 元数据
4. 校验：是否过期、是否私密、密码校验
5. 从 OSS/KV 拉取原文
6. 渲染语法高亮、返回前端
7. 异步更新缓存、增加访问计数

## 四、关键技术点设计
### 1. 缓存策略
- Redis 缓存热点 short_key 元数据+内容
- 设置 TTL 和粘贴过期时间一致
- 缓存淘汰：LRU，冷数据自动清

### 2. 过期清理方案
1. 被动清理：访问时判断过期，直接返回已失效
2. 主动清理：定时任务扫描 MySQL 过期数据，异步删除OSS文件、清缓存

### 3. 限流 & 防滥用
- 网关层：单IP 每秒提交次数限制
- 限制单条最大文本大小
- 敏感词过滤、违规内容异步审核

### 4. 高可用 & 扩容
- 服务无状态，可水平扩容
- MySQL 主从分库分表（按 short_key 哈希分片）
- 对象存储天然分布式、支持海量扩容

### 5. 数据库表设计（核心表）
```sql
CREATE TABLE paste_info (
  id BIGINT PRIMARY KEY,
  short_key VARCHAR(16) UNIQUE NOT NULL,
  content_path VARCHAR(255),
  user_id BIGINT,
  is_private TINYINT,
  password VARCHAR(64),
  expire_time DATETIME,
  create_time DATETIME,
  visit_count BIGINT
);
```

## 五、瓶颈与优化（面试加分项）
1. 读压力大：全靠 Redis 热点缓存扛，尽量不查DB
2. 存储量大：冷热分离，冷数据归档到低成本对象存储
3. 短链冲突：不用随机，用分布式ID+Base62 彻底避免
4. 过期数据堆积：被动校验+定时异步清理双机制
5. 恶意请求：网关限流、频率控制、内容审核

## 六、极简面试口述版总结
1. 先澄清功能非功能需求、做容量估算
2. 架构分：网关、API服务、短链生成、缓存、队列、MySQL、对象存储
3. 短链用分布式自增ID + Base62，无冲突高性能
4. 元数据落MySQL，原文存对象存储，热点放Redis
5. 读多写少，优先缓存；过期用被动+主动双清理
6. 加限流、敏感审核、水平扩容、分库分表支撑海量数据
