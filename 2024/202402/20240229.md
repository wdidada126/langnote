git merge xxx和git merge origin/xxx的区别
`git merge xxx` 和 `git merge origin/xxx` 的主要区别在于 xxx 到底指的是什么类型的引用（ref），以及它们在实际使用中的行为和安全性不同。

| 命令                  | xxx 通常是什么                          | 实际合并的对象                  | 是否会意外移动你的本地分支 | 常见使用场景                     | 安全性 |
|-----------------------|-----------------------------------------|---------------------------------|------------------------|----------------------------------|--------|
| `git merge xxx`       | 本地分支（如 master、dev、feature-a）   | 本地分支的当前 commit          | 不会（只读本地分支）     | 合并本地其他分支                 | 安全   |
| `git merge origin/xxx`| 远程跟踪分支（remote-tracking branch）  | origin 远程仓库上 xxx 分支的最新 commit | 不会（远程跟踪分支受保护）| 从远程仓库同步最新代码到当前分支 | 最安全 |

### 详细解释

1. `xxx`（本地分支）
   - 存在于 `.git/refs/heads/xxx`
   - 你可以随意 push、reset、delete 它
   - 当远程的 xxx 更新后，你的本地 xxx 不会自动更新
   - 如果你直接 `git merge xxx`，合并的就是你本地 xxx 的当前状态，可能已经落后远程很久了

   ```bash
   git checkout main
   git merge dev          # 合并的是你本地的 dev，可能已经过时了
   ```

2. `origin/xxx`（远程跟踪分支）
   - 存在于 `.git/refs/remotes/origin/xxx`
   - 只有执行 `git fetch` 才会更新
   - Git 保护它不让你直接移动（不能直接 checkout 并 commit）
   - `git merge origin/xxx` 永远合并的是你最近一次 fetch 看到的远程最新状态

   ```bash
   git fetch origin          # 先更新所有 origin/* 
   git checkout main
   git merge origin/main     # 100% 合并的是远程最新的 main
   ```

### 实际工作中推荐做法（最常见也最安全）

```bash
# 情况1：你想把远程 main 合并到本地 main（最常见）
git checkout main
git fetch origin
git merge origin/main     # 推荐写法，等价于下面更简洁的
# 或者直接：
git pull                  # git pull = fetch + merge origin/<当前分支>
```

```bash
# 情况2：你想把远程 dev 分支合并到本地某个分支
git checkout feature-abc
git fetch origin
git merge origin/dev      # 明确知道合并的是远程最新 dev
```

### 什么时候两者会有明显区别？

```bash
# 假设远程 main 已经领先本地 main 5 个 commit
git fetch origin
git log --oneline --graph --all

# 你会看到：
* abc1234 (origin/main) 远程最新提交
* def5678 (HEAD -> main) 你本地的 main 已经落后了

git merge main         # 错误！只前进到 def5678，什么都没合并（fast-forward 也不动）
git merge origin/main   # 正确！会真正前进到 abc1234
```

### 总结一览表

| 写法                  | 合并的是什么                     | 需要先 fetch 吗？ | 是否推荐                  |
|-----------------------|----------------------------------|-------------------|---------------------------|
| `git merge main`      | 本地 main（可能过时）            | 不需要            | 不推荐（容易落后）         |
| `git merge origin/main`| 远程最新的 main（fetch 后的状态）| 需要先 fetch      | 强烈推荐（明确、安全）     |
| `git pull`            | 等价于 fetch + merge origin/main | 自动包含 fetch    | 最常用（最简洁）           |

结论：
- 日常开发中，几乎永远应该用 `git merge origin/xxx`（或直接 `git pull`），而不是 `git merge xxx`。
- 只有在你明确知道本地分支就是最新的，才用 `git merge xxx`（比如纯本地开发的分支）。

MySQL 5.7引入了对JSON数据类型的支持，同时也提供了一些用于处理JSON数据的函数。以下是一些常用的MySQL 5.7中的JSON处理函数：
1. JSON_OBJECT：用于创建一个JSON对象。
   ```sql
   SELECT JSON_OBJECT('name', 'John', 'age', 30);
   -- 输出：{"name": "John", "age": 30}
   ```
2. JSON_ARRAY：用于创建一个JSON数组。
   ```sql
   SELECT JSON_ARRAY('apple', 'banana', 'orange');
   -- 输出：["apple", "banana", "orange"]
   ```
3. JSON_EXTRACT：用于提取JSON对象中的特定属性或数组元素。
   ```sql
   SELECT JSON_EXTRACT('{"name": "John", "age": 30}', '$.name');
   -- 输出：John
   ```
4. JSON_SET：用于更新或添加JSON对象中的属性。
   ```sql
   SELECT JSON_SET('{"name": "John", "age": 30}', '$.age', 35);
   -- 输出：{"name": "John", "age": 35}
   ```
5. JSON_REMOVE：用于从JSON对象中删除属性。
   ```sql
   SELECT JSON_REMOVE('{"name": "John", "age": 30}', '$.age');
   -- 输出：{"name": "John"}
   ```
6. JSON_CONTAINS：用于检查JSON数组或对象是否包含指定的值。
   ```sql
   SELECT JSON_CONTAINS('["apple", "banana", "orange"]', 'orange');
   -- 输出：1
   ```
7. JSON_ARRAYAGG：用于聚合行中的JSON值，将它们组合成一个JSON数组。
   ```sql
   SELECT JSON_ARRAYAGG(name) FROM fruits;
   -- 输出：["apple", "banana", "orange"]
   ```
这些是MySQL 5.7中的一些常用的JSON处理函数。请注意，这些函数在较新的MySQL版本中可能会有所变化。建议在使用之前查阅MySQL官方文档以获取最新的函数列表和用法说明。

另一方面，IT技术的进化速度是很快的，作为技术人，我们需要迅速跟上技术更迭的速度。而这些现代语言的编译器，往往就是整合了前沿的技术。比如，Java的JIT编译器和JavaScript的V8编译器，它们都不约而同地采用了“SeaofNodes”的IR来做优化，这是为什么呢?这种IR有什么优势呢?
下面我用通俗但足够深入、偏架构/编译器设计视角一次性讲清楚：为什么 HotSpot C2（Java JIT）、V8 TurboFan（JS JIT）、Graal都不约而同选 Sea of Nodes（节点海）IR，以及它相比传统“基本块+CFG”IR 的决定性优势。

## 一、Sea of Nodes 是什么？（一句话）
Sea of Nodes（SoN）是一种基于 SSA、把控制流+数据流+副作用依赖全部揉成一张“节点依赖图”的 IR；没有基本块、没有严格顺序、只有依赖关系。

- 传统 IR：指令 → 基本块 → CFG（控制流图），强顺序、块约束多
- SoN IR：只有节点 + 依赖边（数据依赖、控制依赖、内存/副作用依赖），无块、无全局顺序、只有偏序

HotSpot C2 的 Ideal Graph、V8 TurboFan、Graal IR 都是典型 SoN。

## 二、为什么现代 JIT 都选它？（核心原因）
### 1. JIT 的核心诉求：极致优化 + 动态类型友好 + 快速迭代
Java（尤其是 Server 模式）、JS（动态类型）都需要：
- 全局、激进的优化（内联、常量传播、死代码删除、循环优化、向量化）
- 能灵活“浮动”指令、打破块边界
- 处理动态类型/多态/内联缓存时容易做特化与去优化

传统 CFG+基本块 IR 优化受块边界束缚太重、全局优化难、代码移动成本高。

### 2. SoN 的五大决定性优势（对比传统 IR）
#### 优势1：消除基本块，指令自由浮动（全局优化神器）
- 传统：指令被锁在基本块里，跨块移动难、循环外提/内联受限
- SoN：无块概念，节点只受依赖边约束；只要不破坏依赖，指令可以任意调度、跨循环/分支自由移动
→ 常量传播、死代码删除、循环优化、全局值编号（GVN）天然全局、跨块无阻力

#### 优势2：统一数据+控制+内存依赖，优化更精准
- SoN 每条边都明确：
  - 数据依赖（a = b + c → a 依赖 b、c）
  - 控制依赖（if → 分支节点控制下游节点）
  - 内存/副作用依赖（load/store、调用、异常）
- 传统 CFG：控制流和数据流分开表示，优化时容易保守、漏优化或出错
→ 内存优化（如内存 SSA、别名分析、重排 load/store）、异常处理、副作用排序更精准、更易实现

#### 优势3：天然 SSA，常量传播/死代码删除零成本
- SoN 天生是 SSA 形式：一个值只对应一个节点，无变量复用、无写后读问题
- 常量传播：常量节点直接替换所有使用，无需遍历变量、无额外分析
- 死代码删除：无使用的节点直接删掉，图遍历一次搞定
→ 这是 JIT 最常用、最有效的优化，在 SoN 上几乎免费

#### 优势4：动态类型语言（JS）特化更灵活
- JS 类型动态、函数多态、内联缓存（IC）频繁
- SoN 可以轻松插入类型检查节点、拆分控制流、生成特化路径，且不破坏整体图结构
- 去优化（deoptimization）时，只需要丢弃部分节点、回退到解释器，无需重构整个 CFG

#### 优势5：内联与组合优化极强（JIT 命脉）
- JIT 性能高度依赖深度内联（把小函数全展开）
- SoN 内联：直接把被调函数的图无缝拼入主调图，无块边界、无调用开销、优化可穿透
- 传统 CFG：内联后块爆炸、CFG 复杂、优化难以跨函数穿透

## 三、Java C2、V8 TurboFan 为什么都用它？（场景匹配）
### Java HotSpot C2（Server 编译器）
- 目标：长期运行代码的峰值性能（服务端、长生命周期）
- 需求：全局、激进、跨函数优化（内联、循环展开、向量化、逃逸分析）
- SoN 完美匹配：无块约束 → 全局优化无死角；SSA → 常量/死码优化高效；内存依赖 → 并发/volatile 优化精准

### V8 TurboFan（JS JIT）
- 目标：动态类型语言的高吞吐+低延迟（浏览器/Node.js）
- 需求：快速生成优化代码、灵活特化、易去优化、支持内联缓存
- SoN 完美匹配：无块 → 类型检查/特化路径自由插入；统一依赖 → 内联缓存/多态优化精准；SSA → 动态值传播高效

### 补充：V8 后来为什么换成 Turboshaft？
- 2022 年后 V8 放弃 SoN，回归CFG+基本块（Turboshaft）
- 原因：JS 动态性太强，SoN 图过于庞大、编译耗时高、调试难、工程维护成本高
- 本质：SoN 适合“偏静态、长运行、重优化”场景；动态性极强的语言会被图复杂度反噬

## 四、一句话总结（面试/架构必背）
Sea of Nodes 把程序表示成一张“依赖图”，去掉基本块束缚、统一数据/控制/内存依赖、天然 SSA，让全局优化（内联/常量/死码/循环）更自由、精准、高效；这正是 Java JIT（峰值性能）和 JS JIT（动态特化）最核心的诉求，所以它们不约而同选择了它。
