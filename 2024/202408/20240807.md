std::make_shared 是 C++11 引入的一个非常有用的智能指针工厂函数，它用于创建一个 std::shared_ptr 实例。std::shared_ptr 是 C++ 标准库中的一个智能指针，用于自动管理动态分配的内存，确保在不再需要时能够自动释放内存，从而避免内存泄漏。

作用
std::make_shared 的主要作用包括：

自动内存管理：通过创建一个 std::shared_ptr，它会在最后一个 std::shared_ptr 被销毁或重置时自动释放所管理的对象。
性能优化：与直接使用 new 表达式创建对象后再用 std::shared_ptr 的构造函数来管理它相比，std::make_shared 可以更高效地分配内存。因为 std::make_shared 可以在单个内存分配中同时分配控制块（用于 std::shared_ptr 的内部机制）和对象本身，这减少了内存分配的开销，并可能提高内存局部性。
异常安全：std::make_shared 保证了在构造对象时如果发生异常，则不会创建 std::shared_ptr，从而避免了潜在的内存泄漏。
示例
在你的例子中，std::make_shared<sql::connection_config>() 创建了一个 std::shared_ptr<sql::connection_config> 类型的智能指针，该指针指向一个动态分配的 sql::connection_config 对象。这里假设 sql::connection_config 是一个类，用于配置数据库连接。

```cpp
auto config = std::make_shared<sql::connection_config>();
```
这行代码执行了以下操作：

在堆上分配 sql::connection_config 类型的对象。
创建一个 std::shared_ptr<sql::connection_config> 类型的智能指针 config，该指针指向新分配的对象。
返回这个智能指针，并将其赋值给 config 变量。
兼容性
std::make_shared 是 C++11 的一部分，因此在支持 C++11 或更高版本的编译器中可用。C++14 和 C++17 保留了这一特性，并可能在此基础上进行了扩展或优化，但 std::make_shared 的基本用法和目的在所有这些版本中都是相同的。

std::make_shared 和 std::unique_ptr 是 C++ 标准库中两种不同的智能指针，它们各自服务于不同的目的和场景，主要区别在于它们对资源管理的策略上。

std::make_shared
共享所有权：std::make_shared 用于创建一个 std::shared_ptr，这是一个共享所有权的智能指针。多个 std::shared_ptr 实例可以指向同一个对象，当最后一个指向该对象的 std::shared_ptr 被销毁或重置时，对象才会被删除。
性能优化：std::make_shared 可以在单个内存分配中同时分配控制块（用于跟踪 std::shared_ptr 的数量）和对象本身，这有助于减少内存分配的开销，并可能提高内存局部性。
异常安全：如果构造函数在分配内存或初始化对象时抛出异常，则不会创建 std::shared_ptr，从而避免了潜在的内存泄漏。
std::unique_ptr
独占所有权：std::unique_ptr 是一个独占所有权的智能指针。它表示某个时刻只有一个 std::unique_ptr 可以拥有并管理某个对象。当你将 std::unique_ptr 的所有权转让给另一个 std::unique_ptr（例如，通过赋值或移动操作）时，原 std::unique_ptr 将变为空（不再拥有对象）。
性能：std::unique_ptr 通常比 std::shared_ptr 有更低的开销，因为它不需要跟踪有多少个 std::unique_ptr 指向同一个对象。但是，这种优势在大多数情况下并不显著，因为智能指针的主要开销通常来自于它们所管理的对象的内存分配和销毁。
灵活性：std::unique_ptr 提供了比 std::shared_ptr 更多的灵活性，例如自定义删除器。你可以为 std::unique_ptr 指定一个自定义的删除函数，该函数将在 std::unique_ptr 被销毁时调用。
总结
如果你需要多个智能指针共享同一个对象的所有权，那么应该使用 std::shared_ptr（通常是通过 std::make_shared 创建）。
如果你只需要一个智能指针来管理对象，或者你想要更细粒度的控制（如自定义删除器），那么应该使用 std::unique_ptr。
std::make_shared 提供了性能上的优势，特别是在需要同时分配对象和 std::shared_ptr 控制块时。但是，如果你需要单独分配它们（例如，因为对象已经存在），那么你应该直接使用 std::shared_ptr 的构造函数。

`vcvarsall.bat` 是 Visual Studio 提供的一个批处理脚本，用于设置编译环境变量。它可以为不同的目标平台（如 x86、x64、ARM 等）配置环境，使得命令行工具（如 `cl.exe`、`link.exe` 等）可以正常运行。具体来说，它会设置一些重要的环境变量，如 `PATH`、`INCLUDE`、`LIB` 等，以指向正确的编译工具和库路径。

- 设置编译器路径：将 Visual Studio 的编译器工具（如 `cl.exe`）的路径添加到 `PATH` 环境变量中，使得你可以在命令行中直接调用这些工具。
- 配置库和头文件路径：设置 `INCLUDE` 和 `LIB` 环境变量，以便编译器能够找到标准库和头文件。
- 支持不同平台：可以为不同的平台（如 x86、x64、ARM 等）配置环境。

当然，请看下面的C++代码示例，它演示了如何使用 `<stdexcept>` 头文件中的 `std::runtime_error` 异常类：

```cpp
#include <iostream>
#include <stdexcept>

void process_data(int value) {
    if (value < 0) {
        throw std::runtime_error("Negative value encountered");
    } else {
        std::cout << "Value is: " << value << std::endl;
    }
}

int main() {
    try {
        process_data(10);  // 正常调用，不会抛出异常
        process_data(-5);  // 这里会抛出 std::runtime_error 异常
    } catch (const std::runtime_error& e) {
        std::cerr << "Runtime error: " << e.what() << std::endl;
    }

    return 0;
}
```

在这个例子中，`process_data` 函数接受一个整数参数 `value`，如果 `value` 是负数，它将抛出一个 `std::runtime_error` 异常。在 `main` 函数中，我们使用 `try-catch` 块来捕获并处理 `process_data` 中可能抛出的异常。

c++ 98 线程私有变量

在 C++98 标准中，并没有直接支持 thread_local 关键字，这是 C++11 引入的一个特性，用于声明变量的线程局部存储（Thread-Local Storage，TLS）。这意味着每个线程都有自己的该变量的实例，互不影响。

然而，如果你在使用 C++98 并且需要类似 thread_local 的功能，你通常需要依赖平台特定的解决方案或第三方库。

平台特定的解决方案
Windows: 在 Windows 平台上，你可以使用 TlsAlloc、TlsSetValue 和 TlsGetValue 等 API 来实现线程局部存储。
POSIX: 在支持 POSIX 的系统（如 Linux 和 macOS）上，可以使用 pthread_key_create、pthread_setspecific 和 pthread_getspecific 等函数。
示例
Windows 示例
以下是一个简单的 Windows 示例，使用 TlsAlloc 等函数实现线程局部存储：

```cpp
#include <windows.h>  
#include <iostream>  
  
DWORD tlsIndex;  
  
void* ThreadFunction(void* lpParam) {  
    // 设置线程局部变量  
    TlsSetValue(tlsIndex, (LPVOID)12345);  
  
    // 获取并打印线程局部变量  
    DWORD value = (DWORD)TlsGetValue(tlsIndex);  
    std::cout << "Thread value: " << value << std::endl;  
  
    return NULL;  
}  
  
int main() {  
    tlsIndex = TlsAlloc();  
  
    HANDLE threadHandle = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)ThreadFunction, NULL, 0, NULL);  
    WaitForSingleObject(threadHandle, INFINITE);  
  
    CloseHandle(threadHandle);  
    TlsFree(tlsIndex);  
  
    return 0;  
}
```

这是一个 POSIX 兼容的示例，使用 pthread_key_create 等函数：

    return NULL;  
}

    // 设置线程局部变量

在C++11中，thread_local关键字被引入以支持线程局部存储（Thread-Local Storage, TLS）。使用thread_local声明的变量会在每个线程中拥有自己的实例，这意味着每个线程都可以独立地修改自己的副本，而不会影响到其他线程中的实例。

thread_local关键字的基本用法
你可以在任何全局变量、静态变量或函数内的静态变量前加上thread_local关键字来声明它们为线程局部的。

示例代码
下面是一个简单的C++11示例，展示了如何使用thread_local关键字：

```cpp
#include <iostream>  
#include <thread>  
#include <vector>  
  
// 声明一个线程局部的静态变量  
thread_local int tls_counter = 0;  
  
void increment_tls_counter() {  
    // 每个线程都会独立地增加自己的tls_counter  
    tls_counter++;  
    std::cout << "Thread " << std::this_thread::get_id() << " incremented tls_counter to " << tls_counter << std::endl;  
}  
  
int main() {  
    std::vector<std::thread> threads;  
  
    // 创建多个线程，每个线程都会调用increment_tls_counter函数  
    for (int i = 0; i < 5; ++i) {  
        threads.emplace_back(increment_tls_counter);  
    }  
  
    // 等待所有线程完成  
    for (auto& t : threads) {  
        t.join();  
    }  
  
    // 注意：这里主线程（或其他任何线程）的tls_counter仍然是初始值0，  
    // 因为tls_counter是线程局部的，每个线程都有自己的实例。  
    std::cout << "Main thread tls_counter: " << tls_counter << std::endl; // 应输出0  
  
    return 0;  
}
```
注意事项
初始化和销毁：thread_local变量的初始化在每个线程第一次访问它时发生（如果变量是基本类型或POD类型，则默认初始化或零初始化；如果是类类型，则调用其构造函数）。当线程结束时，thread_local变量的析构函数会被调用（如果有的话）。
静态持续时间和线程局部存储：静态持续时间的thread_local变量（即在全局或命名空间作用域中声明的）的生命周期与整个程序相同，但其存储是线程局部的。
性能：虽然thread_local很方便，但它可能会对性能产生影响，特别是在需要频繁创建和销毁线程的应用程序中。因为每个线程都需要分配自己的TLS空间，并且在某些平台上，访问TLS变量可能比访问普通变量更昂贵。
兼容性：虽然C++11标准引入了thread_local，但某些编译器或平台可能不完全支持或对其支持有限。在编写可移植代码时，请务必注意这一点。
替代方案：在C++11之前，通常需要依赖平台特定的API（如Windows的TLS函数或POSIX的pthread函数）来实现线程局部存储。在C++11及更高版本中，推荐使用thread_local。

std::hash 是 C++ 标准库中的一个模板类，用于生成给定类型的哈希值。这个类不是 C++17 新增的，它在 C++11 中就已经被引入了。std::hash 提供了一个统一的接口来生成哈希值，这对于需要将对象存储到基于哈希的容器中（如 std::unordered_map、std::unordered_set 等）时非常有用。

std::hash 的工作原理是，它为不同的类型提供了特化版本，每个版本都知道如何为那种类型的对象生成一个哈希值。然而，需要注意的是，标准库只为一些内置类型（如整数、浮点数、指针、字符串等）和一些常见的标准库类型（如 std::string）提供了 std::hash 的特化。如果你想要为一个自定义类型生成哈希值，你需要自己提供 std::hash 的特化版本。

对于 std::thread::id，标准库并没有直接提供 std::hash 的特化。但是，由于 std::thread::id 主要是用于线程的唯一标识，并且支持比较操作，你可以通过一些间接的方式（如上面示例中所示，使用 std::hash<std::size_t> 对 std::thread::id 的哈希值进行哈希）来生成一个哈希值。然而，需要注意的是，这种方法生成的哈希值可能不是跨程序运行或跨平台一致的，因为它依赖于 std::thread::id 的内部实现和 std::hash<std::size_t> 的具体行为。

如果你的应用场景需要跨程序运行或跨平台一致的线程ID表示，你可能需要实现自己的线程ID分配机制，而不是依赖于 std::thread::id 的直接转换或哈希。例如，你可以使用全局的原子计数器或UUID生成器来为每个线程分配一个唯一的标识符。

#include <thread>
#include <sstream>

    size_t hash = hasher(id);
    std::stringstream ss;
    ss << hash;
    return ss.str();
}
