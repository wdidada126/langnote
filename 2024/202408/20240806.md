为什么不用new


在C++中，return Article(); 和 return new Article(); 这两行代码在用途、语义和内存管理上有根本的不同，这也是为什么在大多数情况下你不会使用 new 来返回一个对象的原因。

return Article();
这行代码创建了一个Article类型的临时对象，并返回这个对象的拷贝（在C++11及以后的版本中，由于返回值优化（RVO）和移动语义的引入，这个拷贝可能会被省略）。
它返回的是一个Article类型的值，而不是指针。
这种方式非常安全，因为对象的生命周期由调用者管理（实际上是临时对象的拷贝），不需要手动释放内存。
return new Article();
这行代码在堆上动态分配了一个Article类型的对象，并返回指向这个对象的指针（Article*）。
它返回的是一个指针，这意味着调用者需要负责管理这个指针指向的内存。调用者必须确保在适当的时候使用delete来释放这块内存，否则会导致内存泄漏。
由于需要手动管理内存，这种方式更容易出错，也更难以维护。
为什么不用 new
内存管理复杂性：如上所述，使用new需要手动管理内存，这增加了代码的复杂性和出错的可能性。
异常安全性：如果在分配内存后但在返回指针之前发生异常，那么分配的内存将不会被释放，除非你有额外的异常处理逻辑来确保这一点。
现代C++标准：现代C++（特别是C++11及以后）鼓励使用智能指针（如std::unique_ptr和std::shared_ptr）来自动管理动态分配的内存。然而，即使在这种情况下，也通常推荐返回值而不是指针或智能指针，除非有明确的理由需要返回指针（例如，多态或生命周期管理需求）。
性能考虑：虽然现代编译器通常能够优化掉不必要的拷贝和移动操作，但在某些情况下，返回值可能会比返回指针引入更多的开销（尽管这种差异通常可以忽略不计）。然而，这种性能差异通常被内存安全性和代码清晰性的优势所抵消。
代码清晰度：返回值通常比返回指针更清晰、更易于理解。它直接表达了函数的输出类型，而不需要调用者去解引用指针或检查指针是否为nullptr。
综上所述，除非你有明确的理由需要返回指针（如多态或特殊的生命周期管理需求），否则在C++中通常建议返回值而不是使用new来返回指针。

libcpmtd.lib 是 Microsoft Visual C++ 运行时库的一个组成部分。这个库文件的作用和特点如下：

1. 运行时库：它是 C++ 标准库的 Debug 版本实现，提供了许多基本的 C++ 功能。
2. 多线程调试：
   - 'cpm' 代表 "C Plus Plus Multithreaded"
   - 'd' 后缀表示这是 Debug 版本
3. 动态链接：这个版本是动态链接的运行时库（/MDd 编译器选项）。
4. Debug 信息：包含额外的调试信息，便于开发过程中的错误检测和修复。
5. 内存管理：提供了调试版本的内存分配和释放函数，有助于检测内存泄漏和其他内存相关问题。
6. 检查：包含各种运行时检查，如边界检查、溢出检查等，有助于发现潜在的问题。
7. 性能影响：由于包含额外的调试信息和检查，使用这个库会降低程序的运行速度，增加内存使用。
8. 用途：主要用于开发和调试阶段，不应该用于发布的产品版本。

在你的情况下，使用 libcpmtd.lib 可能与 EASTL 的编译设置有关。确保你的项目设置和 EASTL 的编译设置匹配：

1. 如果你的项目使用 /MDd（多线程调试 DLL），EASTL 也应该用相同的设置编译。
2. 在 xmake.lua 中，你可以这样设置：

   ```lua
   if is_mode("debug") then
       add_cxflags("/MDd")
   else
       add_cxflags("/MD")
   end
   ```

3. 确保 EASTL 的编译设置与你的项目一致。如果你是从源码编译 EASTL，确保使用相同的编译器选项。
4. 如果你使用预编译的 EASTL 库，确保选择了正确的版本（Debug 多线程 DLL）。
5. 在调试完成后，记得将设置改为 Release 版本（/MD），以获得更好的性能。

总之，libcpmtd.lib 的使用表明你的项目正在使用 Debug 版本的多线程动态链接运行时库，这对于开发和调试阶段是正常的。只要确保所有依赖（包括 EASTL）都使用一致的设置即可。

使用 Git 子模块（submodule）可以将一个 Git 仓库嵌入到另一个 Git 仓库中。以下是如何下载并更新 Git 子模块的详细步骤：

### 1. 克隆包含子模块的主仓库

首先克隆包含子模块的主仓库：

```bash
git clone <repository-url>
```

### 2. 初始化并更新子模块

克隆主仓库后，需要初始化并更新子模块。你可以使用以下命令来完成：

```bash
cd <repository-directory>
git submodule update --init --recursive
```

- `git submodule update --init`：初始化并更新子模块。
- `--recursive`：递归地初始化和更新子模块（如果子模块本身还有子模块）。

### 3. 如果主仓库已经克隆，下载子模块

如果你已经克隆了主仓库，但还没有下载子模块，可以直接在仓库目录中运行上述命令：

```bash
git submodule update --init --recursive
```

### 4. 同步和更新子模块

在主仓库的 `.gitmodules` 文件更新后，可以使用以下命令来同步和更新子模块：

```bash
git submodule sync --recursive
git submodule update --init --recursive
```

### 5. 更新子模块到最新提交

如果你需要将子模块更新到它们各自仓库中的最新提交，可以使用以下命令：

```bash
git submodule update --remote --merge
```

- `--remote`：从子模块的远程仓库获取最新提交。
- `--merge`：将子模块的更新与当前分支合并。

### 示例

假设主仓库包含一个子模块，具体步骤如下：

```bash
# 克隆包含子模块的主仓库
git clone https://github.com/example/main-repo.git

# 进入主仓库目录
cd main-repo

# 初始化并更新子模块
git submodule update --init --recursive
```

通过以上步骤，你应该能够成功下载并更新 Git 子模块。
