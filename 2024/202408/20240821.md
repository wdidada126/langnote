所谓PImp是非常常见的隐藏真实数据成员的技巧，核心思路就是用另一个类包装了所要隐藏的真实成员，在接口类中保存这个类的指针。
在C++中，"PImp"（可能是一个简写或特定领域的术语，不常见于标准C++术语中）可能指的是一种用于实现接口和实现分离的技术，特别是通过指针来实现（Pointer to IMPlementation，简称PImpl）。这种技术常用于隐藏类的具体实现细节，增强编译时的独立性和减少编译依赖。下面我将介绍如何使用C++封装一个使用PImpl手法的类。

步骤 1: 定义接口类
首先，定义一个接口类（也称为抽象基类），这个类声明了将要被实现的接口（即纯虚函数）。

cpp
// IMyInterface.h  
#ifndef IMYINTERFACE_H  
#define IMYINTERFACE_H  
  
class IMyInterface {  
public:  
    virtual ~IMyInterface() {}  // 虚析构函数保证正确的析构  
    virtual void doSomething() = 0;  // 纯虚函数，表示接口  
};  
  
#endif // IMYINTERFACE_H
步骤 2: 定义实现类
然后，在另一个文件中定义具体的实现类，该类继承自接口类，并实现接口中的所有纯虚函数。

cpp
// MyInterfaceImpl.h  
#ifndef MYINTERFACEIMPL_H  
#define MYINTERFACEIMPL_H  
  
#include "IMyInterface.h"  
  
class MyInterfaceImpl : public IMyInterface {  
private:  
    // 类的私有成员  
  
public:  
    void doSomething() override;  // 实现接口  
    // 其他成员函数  
};  
  
#endif // MYINTERFACEIMPL_H  
  
// MyInterfaceImpl.cpp  
#include "MyInterfaceImpl.h"  
#include <iostream>  
  
void MyInterfaceImpl::doSomething() {  
    std::cout << "Doing something..." << std::endl;  
}
步骤 3: 使用PImpl封装
现在，我们将使用PImpl手法来封装实现类。这通常意味着在另一个类中，我们使用一个指向实现类的指针来持有具体的实现。

cpp
// MyClass.h  
#ifndef MYCLASS_H  
#define MYCLASS_H  
  
#include "IMyInterface.h"  
#include <memory>  // 对于智能指针  
  
class MyClass {  
private:  
    std::unique_ptr<IMyInterface> m_pImpl;  // 指向实现的智能指针  
  
public:  
    MyClass();  // 构造函数  
    ~MyClass();  // 析构函数  
  
    void doAction();  // 通过接口调用实现  
};  
  
#endif // MYCLASS_H  
  
// MyClass.cpp  
#include "MyClass.h"  
#include "MyInterfaceImpl.h"  
  
MyClass::MyClass() : m_pImpl(std::make_unique<MyInterfaceImpl>()) {}  
  
MyClass::~MyClass() {}  
  
void MyClass::doAction() {  
    m_pImpl->doSomething();  // 通过接口调用实现  
}
优点
隐藏实现细节：用户只需要知道接口，而不需要知道具体的实现。
减少编译依赖：因为用户代码只包含接口头文件，而不需要包含实现类头文件，这可以减少编译时间并降低编译错误的风险。
增强可扩展性和可维护性：可以在不改变接口的情况下修改实现类，或者在接口不变的情况下添加新的实现类。
通过使用PImpl手法，你可以使你的C++代码更加模块化、更加易于管理和维护。

在C++17标准中，协程（Coroutine）并没有直接被包含在标准库中，而是作为一个提议（Proposal）在后续的C++标准（特别是C++20）中被引入。然而，你可以通过一些编译器支持（如GCC的co_await、co_yield、co_return等关键字的扩展）以及第三方库（如Boost.Coroutine2）来体验协程的概念。

不过，为了给你一个接近C++20协程特性的示例，我将展示一个假设的、使用C++20协程库的简单例子。请注意，这个例子需要使用支持C++20的编译器（如GCC 10及以上版本，或者MSVC的某个支持C++20的版本）。

首先，这里是一个简单的生成器函数，它使用C++20的协程特性来生成一系列整数：

cpp
#include <coroutine>
#include <iostream>
#include <vector>
#include <memory>

// 协程的返回类型，用于生成整数
struct Generator {
    struct promise_type {
        int value;

        Generator get_return_object() {
            return Generator{std::coroutine_handle<promise_type>::from_promise(*this)};
        }
        std::suspend_never initial_suspend() { return {}; }
        std::suspend_always final_suspend() noexcept { return {}; }
        void return_void() {}
        void unhandled_exception() { std::terminate(); }
        std::suspend_always yield_value(int v) {
            value = v;
            return {};
        }
    };

    std::coroutine_handle<promise_type> coro;

    Generator(std::coroutine_handle<promise_type> h) : coro(h) {}
    ~Generator() {
        if (coro) coro.destroy();
    }

    bool moveNext() { return coro.resume(), !coro.done(); }
    int currentValue() const { return coro.promise().value; }
};

// 协程函数，生成一个整数序列
Generator generateSequence() {
    for (int i = 0; i < 5; ++i) {
        co_yield i;
    }
}

int main() {
    auto seq = generateSequence();
    while (seq.moveNext()) {
        std::cout << seq.currentValue() << std::endl;
    }
    return 0;
}

注意：这个示例代码是假设性的，因为它基于C++20的协程特性，但在C++17中并不直接可用。在C++17中，你需要依赖编译器的特定扩展或者第三方库来实现类似的协程功能。

如果你正在使用C++17并且想体验协程，你可能需要查看如Boost.Coroutine2这样的库，或者使用支持C++20特性的编译器来编译和运行上述代码。

课程简介
案例背景:
当业务不断发展和变复杂，数据不断增长，用户的数据平台架构被迫引入各种复杂的组件以解决平台的扩展性以及不同场景对数据应用的不同需求，例如批量计算的报表需求，高速高并发的数据存取，或者介于两者之间的综合需求，异或对数据的实时分析。而在引入不同组件的同时，数据在平台间流转也变得更加困难，时效性和一致性也不断降低。我们是否有可能找到一个方案，让架构尽可能简化？

解决思路:
随着 TiDB 新版发布的 TiFlash 是一套高性能的列存引擎，它补足了 TiDB 在 HTAP 场景下行存分析性能偏弱的缺点。和以往的列存设计不同，TiFlash 是专为实时分析场景设计的。它拥有匹配行存的实时更新数据能力，可以作为可随意拔插的列存镜像实时同步在线数据。配合 TiDB 优化器的智能选择功能，它不但可以让用户实时查询在线交易数据而不必担心影响业务稳定，也可以当做查询加速器为 TiDB 分析场景提速，使得整个体系同时拥有行存和列存的性能优势。这样的架构，可以很大程度满足不同场景的多种需求，简化用户的平台架构以及运维成本。

C++为什么提供move函数？
或者说，compiler为什么不能向程序员隐藏这个功能，由compiler自己选择什么情况下move？而什么情况下，需要程序员去指定move？
我大概明白问题的意思，但是编译器的优化不是万能的。左值和右值本来就是编译器自己判断的。但是当你想强制把左值当成右值时就需要调用move。也就是说移动语义大部分情况下是自动的，只有个别情况下才需要手动move。对左值move转移走以后可能把原来的值清空了。这个结果是程序可见的，不能编译器自己处理。因为编译器的优化不能改变程序逻辑。
