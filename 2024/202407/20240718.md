要在 vcpkg 中实现多个 exe 文件复用上一个 downloads 文件夹下的 zip 文件作为缓存，可以利用 vcpkg 的二进制缓存（Binary Caching）功能。
 
vcpkg 默认开启了二进制缓存特性，它会将第一次安装的依赖项文件打包并默认存储，如果将来要求 vcpkg 安装具有相同构建配置的相同库，它会从缓存中复制构建的二进制文件，从而节省构建时间。
 
默认情况下，基于 zip 的存档将缓存在以下第一个有效位置（以 Windows 系统为例）：
 
1.%localappdata%\vcpkg\archives
2.%appdata%\vcpkg\archives
 
如果你想更改缓存位置或使用其他自定义的缓存文件夹，可以通过设置环境变量vcpkg_binary_sources或在命令行中使用--binarysource选项来指定。例如，要使用D:\cache作为缓存文件夹，可以在命令行中执行以下命令：
 
plaintext
 复制
.\vcpkg.exe install <package> --binarysource="files,D:\cache,readwrite"

 
在上述命令中，--binarysource="files,D:\cache,readwrite"表示添加一个基于文件的二进制源，路径为D:\cache，并具有读写权限（readwrite）。这样，vcpkg 会首先检查并使用默认缓存设置路径中的缓存，若不存在则查找并使用D:\cache中的缓存。如果均不存在，才会将缓存放入默认路径下。
 
请注意，确保在使用自定义缓存文件夹时，你有相应的读写权限。另外，vcpkg 的二进制缓存功能可以帮助在多次安装相同库时提高效率，但对于不同构建配置的库可能仍然需要重新构建。具体的使用细节和可用选项可以通过命令vcpkg help binarycaching获取更多帮助信息。





MVCC 简介
MVCC（Multi-Version Concurrency Control，多版本并发控制）是一种在数据库系统中广泛使用的并发控制机制。它通过维护数据的多个版本来处理并发事务，从而提高数据库的并发性能和响应能力。MVCC 的主要优点包括提高并发性能、降低死锁风险等。
MVCC 的工作原理
1.当前读和快照读：
当前读：在 MySQL 中，当前读是一种读取数据的操作方式，它可以直接读取最新的数据版本，并在读取时保证其他并发事务不能修改当前记录。MySQL 提供了两种实现当前读的机制：一致性读和锁定读。
快照读：快照读是在读取数据时读取一个一致性视图中的数据。MySQL 使用 MVCC 机制来支持快照读，每个事务在开始时会创建一个一致性视图，该视图反映了事务开始时刻数据库的快照。
2.Undo 日志：
Undo 日志是 MVCC 能够得以实现的核心。它分为插入 Undo 日志和更新 Undo 日志，分别在插入和更新或删除操作中生成。Undo 日志用于事务回滚和 MVCC 实现。
3.版本链：
在 MVCC 中，每次更新操作，旧值会被保存到一条 undo 日志中，随着更新次数的增加，所有的版本会通过 roll_pointer 属性连接成一个链表，称之为版本链。
4.Read View：
一致性视图（Read View）是用来判断版本链中的哪个版本对当前事务是可见的。Read View 维护系统当前活跃事务的 ID，并根据这些 ID 来判断数据版本的可见性。
vMVCC 介绍
vMVCC 是一个基于 MVCC 的事务库，旨在减少编写并发应用程序代码的工作量。它使用 Go 语言实现，并使用 Perennial、Iris 和 Coq 进行验证。vMVCC 的主要特点包括：
提供高性能的事务处理能力。
通过机器检查证明其正确性，确保所有事务都能正确处理。
vMVCC 的设计和实现
1.数据结构：
vMVCC 使用 tuple 数据结构，包含多个版本、tslast 字段和用于同步访问的互斥锁。每个版本对应一个时间戳范围，表示其有效性。
2.事务处理：
vMVCC 通过为每个事务分配一个严格递增的时间戳来实现 MVCC。事务在提交时创建新版本，并通过互斥锁确保修改的原子性。
3.垃圾回收：
vMVCC 使用后台垃圾收集器来回收不再使用的版本，确保版本在不再被任何事务访问时被删除。
4.时间戳生成：
vMVCC 使用 CPU 时间戳计数器（如 x86 机器上的 RDTSC）生成严格递增的时间戳，避免了共享内存计数器的争用。
vMVCC 的验证
vMVCC 的验证使用了预言变量（prophecy variables），允许证明在事务的线性化点之前预测事务的行为，从而简化了对 MVCC 事务的验证。预言变量的使用使得 vMVCC 能够在事务提交时更新逻辑状态，即使事务体尚未执行。
vMVCC 的性能评估
vMVCC 在 YCSB 和 TPC-C 工作负载下的性能表现与 Silo（一种高性能事务数据库系统）进行了比较。结果显示，vMVCC 在某些工作负载下的性能接近 Silo，证明了其在并发事务处理中的有效性。
通过以上介绍，可以看出 MVCC 和 vMVCC 在数据库并发控制和事务处理中的重要性和优势。希望这些信息能帮助你更好地理解这些技术。


在 MySQL 中，Read View 是 MVCC（多版本并发控制）机制中的一个重要概念，用于处理快照读（Snapshot Read）。Read View 是在事务开始时创建的，用于确定事务可以看到哪些数据版本。以下是关于 MySQL 中 Read View 的一些关键点：
1.一致性视图（Consistent View）：
在可重复读（Repeatable Read）隔离级别下，MySQL 使用一致性视图来实现当前读。事务开始时，MySQL 会创建一个一致性视图，该视图反映了事务开始时刻数据库的快照。
2.Read View 的作用：
Read View 确保事务在执行期间看到的数据是一致的。在事务的整个生命周期内，无论其他事务如何修改数据，该事务始终使用一致性视图来读取数据。
3.Read View 的可见性规则：
Read View 会维护以下几个字段：
m_creator_trx_id：创建 Read View 的事务 ID。
m_up_limit_id：在创建 Read View 时，已提交事务的最大事务 ID。
m_low_limit_id：在创建 Read View 时，未提交事务的最小事务 ID。
m_ids：在创建 Read View 时，所有活跃事务的事务 ID 列表。
4.版本链的可见性判断：
当事务访问某个数据版本时，Read View 会根据以下规则判断该版本是否可见：
1.如果被访问版本的 DB_TRX_ID 属性值与 m_creator_trx_id 值相同，表示当前事务正在访问自己所修改的记录，因此该版本可以被当前事务访问。
2.如果被访问版本的 DB_TRX_ID 属性值小于 m_up_limit_id，说明生成该版本的事务在当前事务生成 Read View 之前已经提交，因此该版本可以被当前事务访问。
3.如果被访问版本的 DB_TRX_ID 属性值大于或等于 m_low_limit_id，说明生成该版本的事务在当前事务生成 Read View 之后才提交，因此该版本不能被当前事务访问。
4.如果被访问版本的 DB_TRX_ID 属性值位于 m_up_limit_id 和 m_low_limit_id 之间，则需要进一步检查 DB_TRX_ID 是否在 m_ids 列表中。如果在列表中，说明在创建 ReadView 时生成该版本的事务仍处于活跃状态，因此该版本不能被访问；如果不在列表中，说明在创建 Read View 时生成该版本的事务已经提交，因此该版本可以被访问。
5.Read View 的生成时机：
在可重复读（Repeatable Read）隔离级别下，每次 SELECT 数据前都生成一个 ReadView。
在读未提交（Read Uncommitted）隔离级别下，事务可以读取其他事务尚未提交的数据，因此不需要使用 Read View。
在串行化（Serializable）隔离级别下，事务具有最高的隔离性，通过锁机制保证事务之间的串行执行，因此也不需要使用 Read View。
通过以上规则，MySQL 的 MVCC 机制能够确保在高并发环境下，事务读取数据时的一致性和隔离性。

函数入参，为什么是const struct timeval tv，不是const timeval tv


在 `redisConnectWithTimeout` 函数的声明中，参数类型`const struct timeval tv`和`const timeval tv`之间的区别主要在于`struct` 关键字的使用。以下是详细解释：
1. `const struct timeval tv`:
   - 这是一个更加明确和常见的用法，尤其是在 C 语言中。
   - `struct timeval` 是一个结构体类型，表示一个时间间隔。`const` 修饰符表明在函数中不会修改这个结构体的内容。
   - `struct timeval tv` 明确表示 `tv` 是一个 `struct timeval` 类型的变量，使代码更具可读性，特别是在涉及到较复杂的代码库或跨文件使用时。
2. `const timeval tv`:
   - 这实际上是一个不完全正确的用法，除非在使用之前通过 `typedef` 将 `struct timeval` 定义为 `timeval`。
   - 如果没有typedef这种定义，编译器会无法识别 `timeval` 类型，从而导致编译错误。
总结一下，`const struct timeval tv` 的使用是为了确保类型的明确性和代码的可读性。这种习惯在编写 C 代码时非常常见，以避免歧义和潜在的编译错误。如果在代码中已经使用 `typedef` 定义了 `timeval`，那么 `const timeval tv` 也是可以的，但这种情况下 `typedef` 的定义应该是：
```c
typedef struct timeval timeval;
```
总之，使用 `const struct timeval tv` 是更安全和更普遍的做法。

#ifndef _MSC_VER  ？

#ifndef 是 C 和 C++ 语言中预处理指令的一部分，用于条件编译。这个指令的意思是“如果未定义指定的宏（macro），则执行随后的代码块”。在你的例子中，#ifndef _MSC_VER 用于检查是否未定义 _MSC_VER 宏。

_MSC_VER 是一个由 Microsoft 编译器（如 MSVC，即 Microsoft Visual C++）定义的宏，用于指示编译器的版本。这个宏的值是一个整数，不同的值代表不同的编译器版本。例如，_MSC_VER 在 Visual Studio 2019 中可能定义为 192x（具体数字取决于更新），在 Visual Studio 2022 中则更高。

因此，#ifndef _MSC_VER 的使用场景通常是为了编写跨平台的代码，特别是当你想在 Microsoft 编译器之外的环境中编译代码时。这种用法允许你为特定的编译器或环境编写特定的代码段，同时避免在不支持这些特性的其他环境中编译这些代码。

下面是一个使用 #ifndef _MSC_VER 的例子：

```c
#include <stdio.h>  
  
#ifndef _MSC_VER  
// 这段代码仅在不是 Microsoft 编译器的情况下编译  
#include <unistd.h> // 引入 UNIX/Linux 特有的头文件  
  
void myFunction() {  
    printf("This is not compiled with Microsoft's compiler.\n");  
    // 可以在这里调用 UNIX/Linux 特有的函数，如 sleep()  
    sleep(1); // UNIX/Linux 中的休眠函数  
}  
  
#else  
// 这段代码仅在是 Microsoft 编译器的情况下编译  
void myFunction() {  
    printf("This is compiled with Microsoft's compiler.\n");  
    // 可以在这里调用 Windows 特有的 API 或函数  
    // 注意：这里没有调用 Windows 特有的函数，只是为了演示  
}  
  
#endif  
  
int main() {  
    myFunction();  
    return 0;  
}
```

在这个例子中，如果代码是在 Microsoft 编译器（如 MSVC）下编译的，那么 _MSC_VER 宏会被定义，因此 #ifndef _MSC_VER 下的代码块会被忽略，而 #else 下的代码块会被编译。相反，如果代码是在其他编译器（如 GCC 或 Clang）下编译的，那么 _MSC_VER 宏不会被定义，因此 #ifndef _MSC_VER 下的代码块会被编译，而 #else 下的代码块会被忽略。

_MSC_VER、GCC 和 Clang 都有它们各自用于版本控制和条件编译的宏。这些宏允许开发者根据不同的编译器或编译器版本来编写特定的代码。

1. _MSC_VER
定义：_MSC_VER 是 Microsoft C/C++ 编译器（cl.exe）预定义的一个宏，用于表示编译器的版本。
类型：整型（int）。
用途：允许开发者根据 Microsoft 编译器的不同版本来编写条件编译的代码。
示例：
MS VC++ 9.0（Visual C++ 2008）对应 _MSC_VER = 1500。
MS VC++ 8.0（Visual C++ 2005）对应 _MSC_VER = 1400。
2. GCC
定义：__GNUC__ 和 __GNUC_MINOR__ 是 GCC 编译器预定义的宏，分别用于表示 GCC 的主版本号和次版本号。
类型：整型（int）。
用途：允许开发者根据 GCC 编译器的不同版本来编写条件编译的代码。
示例：
如果 GCC 的主版本号是 10，次版本号是 2，则 __GNUC__ 会被扩展为 10，__GNUC_MINOR__ 会被扩展为 2。
3. Clang
定义：__clang__ 是 Clang 编译器预定义的宏，用于表示代码正在被 Clang 编译器编译。
类型：通常不直接用于版本比较，但 Clang 也提供了如 __clang_major__、__clang_minor__ 和 __clang_patchlevel__ 这样的宏来表示 Clang 的版本号。
用途：允许开发者编写特定于 Clang 编译器的代码，或者通过版本号来区分不同的 Clang 编译行为。
示例：
如果 Clang 的主版本号是 12，次版本号是 0，补丁级别是 1，则 __clang_major__ 会被扩展为 12，__clang_minor__ 会被扩展为 0，__clang_patchlevel__ 会被扩展为 1。
总结
这些宏为开发者提供了在不同编译器和编译器版本之间进行条件编译的能力，从而可以编写更加灵活和可移植的代码。在编写跨平台或跨编译器的代码时，这些宏尤其有用。然而，需要注意的是，这些宏的具体值和可用性可能会随着编译器版本的更新而发生变化，因此建议查阅最新的编译器文档以获取准确的信息。

c++纯虚函数所在的类，只有.h文件，没有.cpp文件吗？
在C++中，如果一个类包含纯虚函数，那么这个类就被视为一个抽象基类（Abstract Base Class, ABC）。抽象基类的主要目的是作为其他派生类的基类，提供一个共同的接口，但是不允许直接实例化该基类本身。

关于你的问题，包含纯虚函数的类，其实现（即方法体）是否只能放在头文件（.h）中，而不能放在源文件（.cpp）中，这其实是一个有点误导性的说法。实际上，这取决于类的设计和你的具体需求。

1. 纯虚函数的定义
纯虚函数在基类中的定义通常只包含函数声明，不包含函数体。例如：

```cpp
// MyClass.h  
class MyClass {  
public:  
    virtual void myFunction() = 0; // 纯虚函数  
};
```
在这种情况下，MyClass 是一个抽象基类，因为它至少包含一个纯虚函数。这个类的定义（包括纯虚函数）通常放在头文件中，以便派生类可以包含并继承这个基类。

2. 纯虚函数的实现（可选）
虽然纯虚函数在基类中通常没有实现（即没有函数体），但在某些情况下，你可能想在基类中为纯虚函数提供一个默认实现。这可以通过在头文件中声明函数，并在源文件中定义（实现）它来完成，但需要注意的是，这种实现并不会使基类变为非抽象类。例如：

```cpp
// MyClass.h  
class MyClass {  
public:  
    virtual void myFunction() = 0; // 纯虚函数声明  
};  
```

```cpp
// 在某些情况下，你可能想在源文件中提供默认实现  
// 注意：这不会使 MyClass 成为非抽象类  
// MyClass.cpp  
#include "MyClass.h"  
void MyClass::myFunction() {  
    // 默认实现  
    // 注意：这个实现对于 MyClass 本身是不可用的，因为它是抽象的  
    // 但对于任何从 MyClass 派生的非抽象类来说，如果它们没有重写 myFunction，  
    // 它们将继承这个默认实现（尽管这在实践中很少见）  
}
```

然而，上面的做法并不常见，因为通常情况下，如果你提供了纯虚函数的实现，这意呀着你可能实际上想让它成为一个虚函数而非纯虚函数，除非你有特定的设计考虑。

结论
包含纯虚函数的类通常只在头文件中声明这些函数（无实现），但如果你有特殊需求（如为纯虚函数提供默认实现），也可以在源文件中实现它们。然而，这种实现对于基类本身是没有意义的（因为它仍然是抽象的），主要是为了给派生类提供一个可选的默认行为。在大多数情况下，纯虚函数的实现（如果有的话）会被放在源文件中，但这并不改变基类作为抽象类的性质。



head-only 库和 .h 与 .cpp 分离的库是两种不同的库实现方式，它们在组织代码、编译过程、使用便利性、以及可能的性能影响上有所不同。下面详细比较这两种方式，并讨论库开发者在选择时应考虑的因素。

1. 组织代码
head-only 库：所有的声明（包括类、函数、模板等）和定义（即实现）都放在头文件（.h 或 .hpp）中。用户只需要包含这些头文件即可使用库的功能，无需额外编译库的源代码。
.h 与 .cpp 分离的库：库的声明放在头文件中，而实现放在源文件中（.cpp）。用户需要包含头文件，并链接到库编译后生成的二进制文件（如 .dll、.so 或 .a 文件）才能使用库的功能。
2. 编译过程
head-only 库：因为实现直接包含在头文件中，所以用户在编译时，库的实现会被直接嵌入到用户的代码中。这简化了编译过程，但可能导致编译时间较长，特别是当库很大时。
.h 与 .cpp 分离的库：用户需要单独编译库的源代码，并生成库文件。用户项目在编译时需要链接到这个库文件。这种方式增加了编译的复杂性，但可以减少用户项目的编译时间，因为库的实现只会被编译一次。
3. 使用便利性
head-only 库：使用非常方便，只需包含头文件即可。不需要担心库文件的链接问题，特别适合小型库或模板库。
.h 与 .cpp 分离的库：需要确保库文件（如 .dll、.so）在编译时可用，并正确设置链接器参数。这在大型项目中或需要跨平台部署时可能更加复杂。
4. 性能影响
head-only 库：由于实现直接嵌入到用户代码中，可能会增加编译后的二进制文件大小。但是，对于模板库来说，这是必要的，因为模板的实现必须在编译时可见。
.h 与 .cpp 分离的库：由于库的实现和用户代码是分离的，因此可以更好地控制库的更新和分发，而不会影响到用户代码。此外，库的实现可以经过优化，以减少对最终程序性能的影响。
库开发者如何选择
库开发者在选择使用哪种方式时，应考虑以下因素：

库的类型和大小：模板库通常需要使用 head-only 方式，因为模板的实现必须在编译时可见。对于非模板库，如果库很小且使用频率高，head-only 方式可能更方便。但对于大型库，.h 与 .cpp 分离可能更合适。
性能考虑：如果库的性能至关重要，且可以通过优化 .cpp 文件中的代码来提高，则使用 .h 与 .cpp 分离的方式可能更好。
易用性和可维护性：head-only 库在易用性方面通常更好，因为它们不需要额外的链接步骤。但是，如果库很大或很复杂，.h 与 .cpp 分离的方式可能更有助于维护。
跨平台兼容性：如果库需要在多个平台上编译和运行，使用 .h 与 .cpp 分离的方式可能更容易处理不同平台之间的差异。
综上所述，库开发者应根据具体情况选择最适合的库实现方式。
