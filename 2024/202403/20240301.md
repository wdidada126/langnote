# Cache Aside Pattern 旁路缓存模式（面试必背，工业级标准）
## 一、是什么
Cache Aside = 旁路缓存 / 读写分离缓存模式
也叫：懒加载模式、业务代码管理缓存
最常用、最简单、互联网项目默认首选缓存方案。

核心特点：
缓存和数据库完全解耦，由业务代码自己控制 读、写、淘汰，不依赖中间件同步。

## 二、核心流程（只读、只写 标准步骤）
### 1. 读流程（Cache Aside 标准）
1. 先查 Cache
2. 缓存命中 → 直接返回
3. 缓存未命中 → 查询 数据库
4. 把数据回写缓存
5. 返回数据

口诀：先查缓存， miss 查库， 回填缓存

### 2. 写流程（标准规范：先更库，再删缓存）
1. 先 更新/写入 数据库
2. 删除缓存（不是更新缓存，是删除）
3. 下次查询自动重新加载到缓存

口诀：先改库，后删缓存


## 三、为什么写操作是「删缓存」而不是「更新缓存」
1. 更新缓存浪费：很多数据改完根本没人读，白更
2. 并发脏数据：多线程同时更新，容易缓存旧值覆盖新值
3. 删缓存更干净：下次访问懒加载重新生成，天然一致

## 四、优缺点
### 优点
1. 架构简单、易落地、无侵入
2. 缓存与数据库解耦
3. 懒加载，只缓存热点，节省内存
4. 适合读多写少绝大多数业务

### 缺点
1. 缓存击穿：热点Key过期瞬间大量请求打数据库
2. 缓存穿透：查不存在的数据，一直绕开缓存查库
3. 短暂不一致：删缓存后、新数据还没载入前，瞬间读到旧值

## 五、三大问题 + 标准解决方案
### 1. 缓存穿透
问题：请求不存在id，缓存没、库也没，一直穿透到DB
解决：
- 空值缓存（短期TTL）
- 布隆过滤器拦截非法Key

### 2. 缓存击穿
问题：热点Key过期，瞬间流量打垮DB
解决：
- 互斥锁（本地锁/分布式锁）单线程回写
- 热点Key永不过期、后台异步主动刷新

### 3. 缓存雪崩
问题：大量Key同时过期，批量打垮DB
解决：
- TTL 加随机偏移量
- 多级缓存、服务熔断降级

## 六、和另外两种缓存模式对比（面试加分）
1. Cache Aside 旁路缓存
业务自己管缓存，最灵活、用得最多

2. Read/Write Through 读写穿透
应用只操作缓存，缓存组件同步写库，业务无感知，工业极少用

3. Write Back 写回
先写缓存、异步刷库，一致性差，只适合硬件/操作系统，不适合业务数据库

## 七、面试一句话总结
Cache Aside 旁路缓存模式：
读：先缓存、miss查库、回填缓存
写：先更新数据库、再删除缓存
优势是解耦、简单、懒加载，是互联网高并发业务默认缓存架构；
配套要解决穿透、击穿、雪崩三大问题。
