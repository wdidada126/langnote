### 1. 设计一个TPS 2000+ 的购物网站（双11级别准备）

目标不是 2000 TPS，而是“峰值 100w+ TPS 还能稳”（2000 TPS 只是热身）。

核心考虑角度（按优先级排序）：

### 2. 建设一个类似阿里云的云服务平台，调度系统怎么设计？
# 自建类阿里云云平台：调度系统完整设计 + 调度对象讲透
先回答你核心疑问：
调度不只是调度CPU、内存、网络带宽；调度对象分硬件资源、虚拟化资源、业务资源、算力任务四层，远不止物理硬件。

## 一、先纠正你的概念
1. 网络带宽、网卡、公网IP、内网网段、防火墙规则
2. 调度不止是硬件：物理机只是底层，云上真正调度的是：云主机、容器、存储、负载均衡、数据库、大模型算力任务 这些抽象资源。

# 二、云平台调度系统核心定位
类比阿里云：
阿里云底层有飞天调度内核，你的自建云也要做一套资源调度+任务调度+负载调度中台。
核心目标：
- 把所有物理服务器、存储、网络池化
- 自动分配虚拟机/容器/裸金属/数据库实例
- 自动负载均衡、超分复用、故障迁移、节能减排
- 租户隔离、按需计费、弹性扩缩容

## 调度系统分为三大模块
1. 硬件资源调度（底层）
2. 虚拟化资源调度（中层）
3. 业务/任务调度（上层，容器、大模型、Job任务）

# 三、调度对象完整清单（你要设计的就是调度这些）
### 1. 物理硬件层（最底层调度对象）
- 计算：CPU 核数、超线程、内存容量、本地磁盘
- 存储：SSD/HDD 磁盘、存储节点、块存储池、对象存储节点
- 网络：网卡、交换机端口、网络带宽、公网IP、VLAN、子网、路由表、安全组
- 机架/机房：机架机位、供电、机柜负载、地域/可用区

### 2. 虚拟化资源层（云上最常用调度）
- 虚拟机 KVM/Xen：云服务器ECS
- 容器 Docker/K8s：容器服务
- 裸金属服务器 BMS
- 块磁盘、快照、镜像模板
- 负载均衡SLB、NAT网关、VPN

### 3. 高阶服务资源调度
- 中间件：Redis、MQ、MySQL 实例分库分表调度
- 大模型算力：GPU卡、显存、推理/训练任务排队调度
- 定时任务、批量计算、弹性伸缩实例

# 四、云平台调度系统整体架构设计（可直接落地照搬）
## 1. 底层资源池化层
把所有机房服务器、存储、网络统一池化，打标签：
- 地域：合肥/上海
- 可用区：AZ1/AZ2
- 机型：通用型、计算型、内存型、GPU型
- 剩余CPU、内存、带宽、磁盘余量
- 负载水位、健康状态、温度功耗

## 2. 调度核心引擎层（核心）
核心算法要做：
1. 资源匹配调度
租户申请 4核8G 云主机 → 调度引擎自动筛选满足剩余资源、同可用区、负载最低的物理机分配。

2. 负载均衡调度
物理机负载过高 → 自动把部分虚拟机热迁移到低负载节点。

3. 亲和/反亲和调度
- 亲和：主从数据库尽量放同一可用区
- 反亲和：业务主备不能放同一台物理机，防止整机宕机全挂

4. 超分与弹性调度
CPU内存超分配，闲时共享资源，忙时自动扩容加机器。

5. 故障自愈调度
物理机宕机 → 自动检测、自动把上面虚拟机迁移到正常节点。

## 3. 上层业务编排层
对接：云控制台、API、计费系统、K8s集群、数据库服务。
接收用户创建ECS、创建容器、买带宽、加磁盘请求，下发给调度引擎。

## 4. 监控&决策反馈层
实时采集每台机器 CPU/内存/带宽/磁盘负载，给调度引擎做决策依据。

# 五、调度核心策略（工业级阿里云同款）
1. 最优适配策略：优先选资源刚好够用、不浪费的节点
2. 负载最低优先：同配置下选当前负载最低物理机
3. 可用区打散：自动把租户多实例打散到不同AZ，容灾
4. GPU专属调度：卡隔离、显存拆分、大模型任务排队
5. 网络拓扑感知：尽量调度同机房同交换机，减少网络延迟

# 六、极简架构流程图（文字版）
用户控制台申请ECS
→ 业务编排层接收请求
→ 调度引擎查询资源池库存
→ 按CPU/内存/带宽/可用区/负载筛选节点
→ 下发虚拟化层创建虚拟机
→ 绑定网络、磁盘、安全组
→ 返回给用户可用

# 七、总结一句话
1. 调度不只是硬件CPU内存，还要调度网络带宽、存储、虚拟机、容器、数据库、GPU任务；
2. 类阿里云调度系统 = 资源池化 + 调度引擎 + 负载均衡 + 故障迁移 + 业务编排；
3. 设计第一步：先把所有物理机、网络、存储做标签池化，再写匹配、负载、容灾调度算法。

### 3. 设计一个高频股票量化交易系统（延迟 < 100μs 级别）

这已经不是普通互联网架构了，是真正的“军备竞赛”领域，玩家只有 Jane Street、Citadel、Two Sigma、Jump Trading、盈透等。

2025 年最硬核的高频量化架构（毫秒已经出局，微秒才是王道）：

| 模块             | 技术选型（2025 版）                                      | 延迟级别         | 关键点                                           |
|------------------|---------------------------------------------------------|------------------|--------------------------------------------------|
| 行情接收         | 交易所直连光纤 + FPGA 解析（上海 300、深圳 800）         | 1-5 μs           | 所有行情必须 FPGA 预处理，丢包率 < 0.0001%       |

| 风控&策略引擎    | FPGA（策略硬化） + CPU（复杂策略）                      | FPGA < 500ns     | 简单策略全放 FPGA（做市、套利），复杂策略 PIN CPU 核心 |
| 核心数据结构     | 平铺内存（FlatBuffer/Cap'n Proto）+ 自定义内存池         | 零拷贝           | 禁止 new/delete，全部预分配                      |
| 通信             | RDMA + Infiniband/200Gbps RoCE v2                       | < 1μs            | 跨机器共享内存一样快                             |
| 存储&回测        | ClickHouse（实时） + KDB+（历史 TiCK 数据）             | 毫秒级查询       | KDB+ 仍是王者，单机 10 亿条数据查询 < 10ms       |
| 部署方式         | 交易所同机柜托管（Colocation），光纤距离 < 50 米         | 物理极限         | 上海金桥、深圳龙华机柜租金百万级/年               |
| 容错             | 三套独立系统热备 + 自动切换（Active-Active-Active）     | 切换 < 50ms      | 一旦主系统延迟异常，自动切换                     |
| 编程范式         | C++23 + Rust（新模块） + Verilog（FPGA）                | 极致性能         | 所有热点路径禁止虚函数、STL                     |

真实延迟数据（2025 年国内一线量化私募）：
- 行情收到 → 策略决策 → 订单发出：平均 35μs（顶级团队 < 15μs）
- 订单到交易所：光纤 + 网关 < 80μs（上海 300 最快）

总结一句话：
- 购物网站：流量越大越要“读静写动 + 异步 + 削峰”
- 云平台调度：两级调度 + 预测弹性 + 干扰迁徙 + 万卡集体调度
- 高频量化：能用 FPGA 绝不用 CPU，能直连绝不走公网，能省 1μs 就值 1000 万

“两地三中心”是中国人民银行在2002年提出、2004年开始逐步实施的有关央行系统数据中心布局的战略部署，也被称为“一主两备”或“一个同城加两个异地”。它是指在北京建立两个数据中心，同时在天津和上海各建立一个数据中心。
在这个方案中，北京的两个数据中心采用双活模式，天津和上海的数据中心则采用异步方式（近同步）复制北京的数据，但不对用户开放。这样做的目的是保证当任何一个地方发生灾难时，其他的地方还可以对外提供服务。
这个方案的实施得到了花旗银行的支持。花旗银行的现金管理平台采用了Oracle真正应用集群（RAC）来整合位于纽约和伦敦的两个数据中心，并使用Oracle Data Guard作为第三点故障切换。这种多点集群技术可以提供更高的可用性，使系统在遇到故障时能够自动进行切换，从而最大限度地减少了系统的停机时间。

“两地三中心”的开源方案主要涉及确保高可用性和灾难恢复的策略。在开源领域，可以利用多个软件和工具组合来实现这一目标。以下是构建“两地三中心”的开源解决方案的一些组件和技术：
1. 分布式文件系统：
   - GlusterFS 或 Ceph：这些分布式文件系统支持数据复制和分布到多个物理位置，提供容错和灾难恢复功能。
2. 数据库复制：
   - MySQL/MariaDB：使用主从复制或组复制（Group Replication）功能来同步数据到不同数据中心。
   - PostgreSQL：通过流复制（Streaming Replication）或逻辑复制实现多地点数据同步。
   - MongoDB：提供副本集（Replica Sets）和分片（Sharding）来支持跨多个数据中心的数据复制。
3. 负载均衡和故障转移：
   - HAProxy 或 NGINX：这些负载均衡器可以在多个数据中心之间分配流量，并在一个数据中心发生故障时将流量重定向到其他中心。
   - Keepalived 或 VRRP：用于实现高可用性，通过虚拟路由冗余协议保持一个虚拟IP地址，当主服务发生故障时，可以自动切换到备份服务。
4. 消息队列系统：
   - Apache Kafka：集群可以分布在多个数据中心，Kafka的副本机制可以保证消息的持久性和高可用性。
5. 配置管理和自动化部署：
   - Ansible、Puppet、Chef 或 SaltStack：这些工具可以帮助自动化配置和管理跨多个数据中心的服务。
6. 监控和告警：
   - Prometheus 结合 Grafana 或 Zabbix：监控系统状态，一旦检测到问题，可以触发告警并采取相应措施。
7. 全局负载均衡器：
   - DNS解决方案（如Anycast DNS）：将用户请求导向最近的数据中心。
   - 硬件负载均衡器（如F5 BIG-IP）：配置在各个数据中心前端，配合DNS实现全球服务器负载均衡（GSLB）。
实施“两地三中心”的开源方案通常需要对以上技术进行综合运用，并根据实际业务需求和预算限制进行定制。重要的是要定期测试灾难恢复计划，确保在实际发生灾难时，系统能够按预期进行切换和恢复。
