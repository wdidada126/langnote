MySQL的默认隔离级别REPEATABLE READ通过多版本并发控制（MVCC）来避免不可重复读的问题
幻读（Phantom Read）是一种在事务执行过程中，由于其他事务的插入或删除操作，导致当前事务读取到的行数发生了变化的现象。幻读通常发生在范围查询（如SELECT * FROM table WHERE column BETWEEN value1 AND value2）中。

数据事务并发带来的问题：
脏读(Drity Read)：事务A更新记录但未提交，事务B查询出A未提交记录。
不可重复读(Non-repeatable read): 事务A读取一次，此时事务B对数据进行了更新或删除操作，事务A再次查询数据不一致。
幻读(Phantom Read): 事务A读取一次，此时事务B插入一条数据事务A再次查询，记录多了。
不可重复读和幻读区别：不可重复读在于记录的值，幻读在于记录的数量。
脏读，读一次，不可重复读/幻读 读两次

redo log的作用，刷盘时机 存储形式
Redo log（或称为redo log）在数据库系统中扮演着至关重要的角色。以下是关于其作用、刷盘时机以及存储形式的详细解释：
作用：
数据恢复：Redo log的主要功能是记录所有对数据库中的数据进行修改的操作，包括插入、修改和删除。在数据库发生故障或崩溃时，可以利用redo log来恢复数据库的数据，确保数据的完整性和一致性。
实时备份：Redo log还可用于实现数据库的实时备份功能。在进行数据库备份时，可以先将所有的修改操作记录在redo log中，然后再将redo log和数据库中的数据一起备份到另一台机器上，从而保证了备份的实时性和准确性。
刷盘时机：
Redo log的刷盘时机主要取决于以下几个因素：
InnoDB存储引擎的状态：当InnoDB存储引擎处于非正常关闭状态（如系统崩溃）时，需要强制刷盘以确保数据的完整性。
系统参数设置：通过设置如innodb_flush_log_at_trx_commit等参数来控制Redo Log的刷盘时机。该参数可以有以下取值：
0：表示不刷盘，由操作系统决定何时刷盘，这是默认值。
1：表示每次事务提交时都刷盘。
2：表示每秒刷一次盘。
此外，还有以下一些刷盘时机：
缓冲区日志量达到总容量的50%：当缓冲区内的日志量达到总容量的50%时，会触发刷盘操作。
事务提交时：即使不将事务对应的脏页刷入磁盘，但其对应的redo日志需要刷新到磁盘，以防止在此时发生断电等情况导致数据丢失。
后台线程每秒一次的频率：即使没有事务提交或缓冲区日志量未达到阈值，后台线程也会按照设定的频率（如每秒一次）进行刷盘操作。
正常关闭服务器时：当数据库服务器正常关闭时，会进行最后的刷盘操作，确保所有的修改都已持久化到磁盘。
存储形式：
Redo log的存储载体是log block，每个块的大小通常为512字节。在服务器启动时，会向内存申请一片连续的内存空间作为redo log buffer，这个buffer被进一步划分成若干redo log block。在事务执行过程中，一个事务中的SQL语句可能包含多个原子操作，这些原子操作对应的redo日志组可以交替写入缓存区，但一个日志组内的redo记录必须在同一块内。
总的来说，redo log通过其独特的存储形式和刷盘机制，确保了数据库在发生故障或崩溃时能够迅速恢复数据，保证了数据库的稳定性和可靠性。

### 一、为什么 MySQL 强烈不建议用字符（VARCHAR）存储时间？

主要原因有以下几点：

1. 占用空间大  
   - `'2025-04-30 14:30:45'` → VARCHAR 需要约 19~23 字节（取决于字符集）。
   - `DATETIME` 只需 5~8 字节。
   - `TIMESTAMP` 只需 4~7 字节。

2. 查询性能差  
   - 字符串比较是逐字符比较，无法使用索引的范围扫描优化。
   - 无法直接使用 `DATE()`、`YEAR()`、`DATE_ADD()`、`DATEDIFF()` 等大量日期函数，必须用 `STR_TO_DATE()` 转换，性能很差且无法走索引。

3. 功能缺失  
   - 无法方便地做时间范围查询、按月/按天统计、时区转换等操作。

4. 维护性差  
   - 数据格式容易不统一（有人存 `2025-4-30`，有人存 `2025/04/30 14:30:45` 等），导致脏数据。

结论：在 MySQL / TiDB / OceanBase 中，用 VARCHAR 存时间属于反模式（anti-pattern），除非有极特殊理由，否则不推荐。

---

### 二、在其他数据库中情况如何？（Oracle、SQL Server、DB2、TiDB、OceanBase）

下面是各数据库的推荐做法和 Trade-off：

| 数据库          | 推荐时间类型                          | 是否建议用 VARCHAR | Trade-off（用字符串的代价） | 备注 |
|-----------------|---------------------------------------|--------------------|-----------------------------|------|
| MySQL       | `DATETIME` / `TIMESTAMP` / `DATE`       | 强烈不建议    | 空间大、性能差、函数无法用 | 最严格 |
| TiDB        | `DATETIME` / `TIMESTAMP`                | 强烈不建议    | 与 MySQL 几乎一致           | 兼容 MySQL 协议 |
| OceanBase   | `DATETIME` / `TIMESTAMP`                | 强烈不建议    | 与 MySQL 一致               | 兼容 MySQL 模式 |
| Oracle      | `DATE`（推荐）或 `TIMESTAMP` / `TIMESTAMP WITH TIME ZONE` | 不建议        | 空间浪费、无法用 `TO_DATE` 等函数高效查询 | Oracle 有很强的日期函数体系 |
| SQL Server  | `DATETIME2`（推荐） / `DATETIME` / `DATE` | 不建议        | 性能较差，无法用日期函数    | `DATETIME2` 精度更高 |
| DB2         | `TIMESTAMP` / `DATE` / `TIME`           | 不建议        | 空间大、性能差              | IBM 体系对日期类型支持很好 |

总结：
- 所有主流关系型数据库（包括你提到的这些）都不推荐用纯字符类型存储时间。
- 即使在 Oracle、SQL Server、DB2 中，用 `VARCHAR2` / `VARCHAR` 存时间也会面临和 MySQL 类似的问题：空间占用更大、索引效率低、函数使用不便。

### 三、屹通系统大面积用字符存时间的 Trade-off 分析

可能他们这样做的理由（优点）：
- 前后端交互简单（直接传字符串，不用做格式转换）。
- 兼容性强（不同数据库、不同语言之间传输不容易出错）。
- 历史遗留系统，改动成本高。
- 某些特殊场景需要保留原始输入格式（比如用户手动输入的时间字符串）。

付出的代价（缺点）：
- 存储空间显著增加（尤其数据量大时）。
- 时间范围查询、统计类 SQL 性能变差（可能需要加函数索引来缓解，但仍不如原生类型）。
- 无法方便使用数据库内置的日期函数做复杂业务逻辑。
- 数据校验困难，容易出现非法时间格式。
- 后期如果要切换数据库或做数据迁移，会更麻烦。

实际建议：
- 新建表：强烈建议改用正确的日期时间类型（`DATETIME` / `DATETIME2` / `TIMESTAMP` 等）。
- 历史表：如果数据量极大，可以采用双字段策略：
  - 保留原来的 `VARCHAR` 字段（兼容老代码）。
  - 新增一个 `correct_time` 的日期类型字段，通过触发器或定时任务同步。
  - 逐步把查询迁移到新字段上。
