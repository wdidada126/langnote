在MySQL中，没有直接提供集合操作的函数来取差集，但你可以使用NOT IN或LEFT JOIN/IS NULL来模拟实现差集的操作。
假设你有两个表table1和table2，它们都有一个共同的列id，你想从table1中取出那些不在table2中的id。
使用NOT IN
```sql
SELECT id FROM table1  
WHERE id NOT IN (SELECT id FROM table2);
```
这个查询会返回table1中所有不在table2中的id。

使用LEFT JOIN/IS NULL
```sql
SELECT t1.id   
FROM table1 t1  
LEFT JOIN table2 t2 ON t1.id = t2.id  
WHERE t2.id IS NULL;
```
这个查询也会返回table1中所有不在table2中的id。它的工作原理是：首先，使用LEFT JOIN将table1和table2连接起来，基于id列。然后，通过WHERE子句筛选出那些在table2中没有匹配项（即t2.id为NULL）的table1中的id。
注意：当处理大量数据时，NOT IN和LEFT JOIN/IS NULL的性能可能会有所不同，具体取决于你的数据、索引和MySQL的版本。在实际应用中，你可能需要测试这两种方法，以确定哪种更适合你的具体情况。

分布式中通过选举出来master节点，那么master节点变动会导致服务的ip变动，这种情况怎么解决
在分布式系统中，通过**选举（Leader Election）**产生 Master（Leader）节点后，当 Master 发生故障或切换时，新 Master 的 IP/端口确实会发生变化。这是一个非常经典的问题，称为 **Master IP 漂移（IP漂移）** 或 **Leader 地址不稳定**。

下面给出生产环境中**主流且推荐的解决方案**，从简单到复杂排序：

### 1. 最推荐方案：引入服务发现 + 注册中心（主流做法）

不要让客户端或其他服务直接写死 Master 的 IP，而是通过**服务发现机制**动态获取当前 Master 的地址。

**核心思路**：
- Master 节点选举成功后，把自己的 **IP + Port + 角色（master）** 注册到注册中心。
- 其他服务/客户端通过注册中心查询 “谁是当前 Master”，而不是记住 IP。
- Master 切换时，旧 Master 下线 + 新 Master 注册，注册中心会推送变更通知。

**常用注册中心及实现方式**：

| 方案                  | 推荐场景                  | 实现方式                                      | 优点 |
|-----------------------|---------------------------|-----------------------------------------------|------|
| **etcd** (Raft)      | 云原生、Kubernetes        | 在固定路径 `/services/master` 写当前 Master 信息（带 Lease） | 强一致、轻量、高性能 |
| **ZooKeeper**        | 传统 Java 体系            | 使用临时节点 + Watcher，或 Curator 的 LeaderSelector | 成熟、功能丰富 |
| **Consul**           | 多数据中心、Service Mesh  | 使用 Service + Tag（master）或 Session        | 内置健康检查、DNS 支持好 |
| **Nacos**            | 阿里系、国内项目          | 服务注册 + 订阅 master 服务                   | 易用、支持 CP/AP 切换 |
| **Kubernetes**       | 容器化环境                | Headless Service + StatefulSet + Leader Election | 原生支持 |

**优点**：客户端无感知 Master 切换，自动更新地址；支持负载均衡、健康检查。

### 2. 使用虚拟 IP（VIP）或浮动 IP

- 通过 **Keepalived + VRRP** 或云厂商的 **弹性公网 IP / Floating IP** 实现。
- Master 节点绑定一个固定的虚拟 IP。
- Master 切换时，新 Master 接管这个 VIP（旧 Master 释放）。

**适用场景**：
- 传统虚拟机环境、数据库 HA（如 MySQL MHA、Patroni）。
- 对 IP 稳定性要求极高（部分老系统必须用固定 IP）。

**缺点**：
- 切换时有短暂中断（几秒到几十秒）。
- 在公有云上实现成本较高，且跨可用区较麻烦。

### 3. 使用域名 + DNS 动态解析

- 给 Master 分配一个固定域名（如 `master.myservice.example.com`）。
- Master 切换后，更新 DNS 记录（A 记录或 SRV 记录）。
- 客户端通过域名访问，结合短 TTL（Time To Live）实现快速生效。

**优点**：简单，对客户端透明。
**缺点**：DNS 缓存会导致切换延迟；不适合对时延敏感的场景。

### 4. 客户端缓存 + 重试 + 重新发现（组合使用）

实际生产中通常是 **“服务发现为主 + 客户端优雅降级”**：

- 客户端本地缓存当前 Master 地址（带过期时间）。
- 请求失败时，立即触发重新从注册中心拉取最新 Master 地址。
- 结合指数退避重试 + 熔断机制。

### 5. 其他高级方案

- **反向代理层**：在 Master 前加一层 Nginx / Envoy / HAProxy，由控制平面动态更新后端配置。
- **Service Mesh**（Istio、Linkerd）：Sidecar 自动处理服务发现和流量路由，几乎无感知切换。
- **Lease 机制**：Master 持有带 Lease 的锁，过期自动释放，配合服务发现使用。

### 最佳实践建议

1. **强烈推荐**采用 **服务发现（etcd / Consul / ZooKeeper）** 的方式，这是目前云原生和大规模分布式系统的主流做法。
2. Master 节点在成为 Leader 后，应立即：
   - 注册/更新自己在注册中心的状态（带 TTL/Lease）。
   - 其他节点 Watch 该路径的变化。
3. 客户端不要硬编码任何 Master IP，所有访问都走服务发现。
4. 如果你的系统是 Kubernetes 环境，优先使用 **Kubernetes 原生的 Leader Election**（基于 Lease）+ Service。
