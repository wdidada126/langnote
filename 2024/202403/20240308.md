跨数据库表join操作通常不是关系数据库管理系统（RDBMS）的标准功能，因为join操作通常是在同一个数据库内部的表之间进行的。不同的RDBMS可能有不同的扩展功能或中间件来支持跨数据库join，但这并不是它们的核心功能，也不是标准化的。

有些数据库系统或中间件可能提供了某种形式的跨数据库或跨实例的join支持，但这通常涉及到特定的配置、网络通信和性能考虑。以下是一些可能支持或可以通过特定方式实现跨数据库join操作的数据库系统：

MySQL：虽然MySQL本身并不直接支持跨数据库实例的join操作，但你可以通过其他方式实现类似的功能。例如，你可以使用中间件或微服务来组合来自不同数据库的数据，或者在应用层进行数据的组合。另外，MySQL的FEDERATED引擎允许你访问远程MySQL服务器上的表，但这更像是一个远程表的映射，而不是真正的跨数据库join。
PostgreSQL：PostgreSQL是一个功能强大的开源数据库系统，但它本身也不直接支持跨数据库实例的join。然而，你可以使用外部数据包装器（Foreign Data Wrappers, FDWs）来访问和操作外部数据源，这可能在某种程度上模拟跨数据库join的行为。
Microsoft SQL Server：SQL Server主要关注于单个数据库实例内的操作，但你可以使用链接服务器（Linked Servers）来查询其他SQL Server实例或ODBC数据源。虽然这不是真正的跨数据库join，但它允许你在一个查询中组合来自不同数据源的数据。
Oracle Database：Oracle Database提供了数据库链接（Database Links）的功能，允许你从一个数据库实例查询另一个数据库实例的数据。这可以在某种程度上模拟跨数据库join，但同样，这并不是一个真正的跨数据库join操作。
需要注意的是，跨数据库join操作通常涉及复杂的网络通信和性能问题，因此在设计数据库架构和应用程序时应该尽量避免这种需求。如果确实需要跨数据库的数据整合，通常更好的做法是在应用层进行数据的组合和处理，或者使用数据集成工具（如ETL工具）来定期同步和整合数据。

总之，虽然某些数据库系统可能提供了某种形式的跨数据库或跨实例的数据访问功能，但真正的跨数据库join操作并不是这些系统的标准或推荐用法。在设计和实施数据库解决方案时，应该优先考虑使用单个数据库实例内的join操作，并尽量避免跨数据库的数据整合需求。

准确的说，是跨schema join
在关系数据库中，跨schema join通常指的是在相同的数据库实例内，但跨越不同的schema（模式）进行join操作。与跨数据库join不同，跨schema join是在同一个数据库管理系统内部进行的，因此通常更为可行和高效。
大多数关系数据库管理系统（RDBMS）都支持在同一个数据库实例内的不同schema之间进行join操作。这是因为，从数据库的角度来看，不同的schema只是组织表、视图和其他数据库对象的一种逻辑方式，它们仍然属于同一个数据库实例，并可以通过SQL查询来访问和组合。

以下是在支持跨schema join的RDBMS中执行此类操作的一般步骤：
确保权限：首先，确保执行查询的数据库用户具有访问两个不同schema中相关表的权限。
使用完全限定名：在SQL查询中，使用完全限定名来引用不同schema中的表。完全限定名通常包括schema名、表名和列名。例如，在SQL中，你可能会这样写：SELECT a.*, b.* FROM schema1.table1 a JOIN schema2.table2 b ON a.id = b.id;
执行查询：一旦你构建了包含跨schema引用的SQL查询，就可以像执行任何其他查询一样执行它。数据库管理系统将解析查询，识别跨schema的引用，并生成执行计划来组合来自不同schema的数据。
需要注意的是，虽然跨schema join在技术上是可行的，但在设计数据库架构时仍应谨慎使用。过度使用跨schema join可能会导致性能问题、维护困难以及潜在的数据一致性问题。因此，在设计数据库时，应尽量避免不必要的跨schema引用，并尽量将数据和相关操作保持在同一schema内。
最后，不同的RDBMS可能在实现跨schema join时具有不同的语法和特性。因此，在具体实施时，建议查阅所使用数据库的官方文档以获取更详细和准确的信息。

除了MVCC（多版本并发控制）之外，还有以下两种主要的并发控制策略：
悲观并发控制（Pessimistic Concurrency Control）：这种策略通常涉及到锁的使用。在数据库的事务处理系统中，当事务需要使用某些数据时，它会尝试获取这些数据的锁。如果其他事务已经持有这些数据的锁，则当前事务必须等待直到锁被释放。这种方法可能会导致延时等待，因为它在事务开始时就假设最坏的情况，即数据冲突可能会发生。因此，悲观并发控制以牺牲性能为代价来确保数据的正确性。
乐观并发控制（Optimistic Concurrency Control）：与悲观并发控制相反，乐观并发控制假设在事务执行期间，数据冲突不太可能发生。因此，事务可以自由地读写数据，通常这些操作会在临时区域中进行。只有在事务提交时，系统才会检查是否有其他事务干扰了当前事务。如果有冲突，则当前事务可能需要回滚或采取其他措施来解决冲突。这种方法减少了等待时间，但可能增加了事务回滚的频率。
这两种策略各有优缺点，适用于不同的场景和需求。在选择使用哪种策略时，需要考虑数据的访问模式、冲突的可能性以及系统的性能要求等因素。
此外，还有一些其他的并发控制技术和方法，例如基于时间戳的并发控制、基于优先级的并发控制等。这些方法在某些特定的应用场景中可能更为有效。但需要注意的是，无论使用哪种并发控制策略，都需要确保数据的完整性和一致性不被破坏，并且系统能够及时调度和解决事务之间的冲突。

aggregate functions ignore NULL values.

"aggregate functions ignore NULL values" 的意思是，当使用聚合函数（如 SUM, AVG, MAX, MIN, COUNT 等）时，如果数据列中包含 NULL 值，这些 NULL 值通常不会被纳入聚合计算中。换句话说，聚合函数在计算时会忽略掉 NULL 值。

举个例子来说明这个概念：
假设我们有一个名为 sales 的表，其中有一个名为 amount 的列，用于记录每次销售的金额。这个列中可能包含一些 NULL 值，表示某些销售记录没有金额数据。
如果我们想要计算 amount 列的总和，可以使用 SUM 函数：
```sql
SELECT SUM(amount) AS total_sales FROM sales;
```
如果 amount 列中有 NULL 值，SUM 函数会忽略这些 NULL 值，只计算非 NULL 值的总和。因此，结果 total_sales 将不会包括任何 NULL 值。
同样地，对于 AVG 函数（计算平均值），MAX 函数（找最大值），MIN 函数（找最小值）等，它们也都会忽略 NULL 值。只有 COUNT 函数在默认情况下会计算所有行，包括包含 NULL 值的行。如果你想要 COUNT 函数只计算非 NULL 值的数量，你需要使用 COUNT(column_name) 而不是 COUNT(*)。
例如，计算非NULL值的数量：
```sql
SELECT COUNT(amount) AS non_null_count FROM sales;
```
在这个例子中，non_null_count 将只包括 amount 列中非 NULL 值的数量，而忽略NULL值。

spring aop多个，顺序
在Spring AOP（Aspect-Oriented Programming，面向切面编程）中，当存在多个切面（Aspect）时，它们的执行顺序可以通过不同的方式进行控制。默认情况下，Spring AOP会按照切面的声明顺序执行。但也可以通过一些配置来改变这个顺序。

以下是影响Spring AOP切面执行顺序的几个因素：
切面的声明顺序：在Spring配置文件中，切面的声明顺序会影响它们的执行顺序。先声明的切面通常先执行。
切点（Pointcut）的定义：如果多个切面定义了相同的切点，则它们的执行顺序由上述的切面声明顺序决定。
切面的优先级（Order）：Spring AOP允许你通过@Order注解或Ordered接口来指定切面的优先级。优先级高的切面会先执行。
例如，使用@Order注解：

java
@Aspect  
@Order(1)  
public class AspectA {  
    // ...  
}  
  
@Aspect  
@Order(2)  
public class AspectB {  
    // ...  
}
在这个例子中，AspectA的优先级高于AspectB，因此AspectA的切面逻辑会先执行。

多个通知（Advice）在同一个切面中：如果一个切面定义了多个通知（如@Before、@After、@Around等），那么这些通知的执行顺序会按照它们在代码中出现的顺序执行。
组合使用：在实际应用中，可能会组合使用上述的多种方式来控制切面的执行顺序。
请注意，上述的执行顺序主要适用于同一类型的通知（例如，都是@Before通知）。对于不同类型的通知（如@Before和@After），它们的执行顺序是由其本身的逻辑决定的：@Before通知在方法执行前执行，而@After通知在方法执行后执行。

最后，如果你使用的是基于XML的配置方式，也可以通过配置文件的顺序来控制切面的执行顺序。但现代Spring应用更推荐使用Java配置和注解方式。
