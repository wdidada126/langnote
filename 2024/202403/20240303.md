### Omega：Google 内部真正的“Kubernetes 前身”（2014-2017 时代）

Omega 是 Google 在 Borg 之后、Kubernetes 之前的那座关键桥梁，被公认为“现代云调度器的真正鼻祖”。它直接解决了 Borg 的核心痛点，并把很多设计理念原封不动地传给了 Kubernetes 和 Borg 的后继者。

#### Omega 诞生的背景（为什么 Borg 不够用了？）

| Borg（2009-2014）的问题 | Omega 要解决的核心痛点 |
|-------------------------|-------------------------|
| 完全中心化单体 Scheduler | 单点瓶颈、扩展性差（全量状态几百 GB） |
| 硬两级调度（Allocator + Scheduler） | 开发新功能极慢，所有策略都耦合在单体里 |
| 悲观锁（cell 级大锁） | 调度冲突严重，资源利用率低，任务经常排队 |
| 所有策略硬编码 | 团队间调度策略冲突（Batch vs Service vs BigData） |

#### Omega 的核心架构创新（2014 年论文直接震惊学术界）

Google 2014 年 Eurosys 论文《Large-scale cluster management at Google with Borg》后面紧接着 2015 年又发了《Omega: flexible, scalable schedulers for large compute clusters》，Omega 的设计几乎奠定了今天所有现代调度器的基础。

| 层级              | Omega 的设计                                   | 和 Borg 的根本区别                      | 对后世的影响（直接抄过去的）          |
|-------------------|------------------------------------------------|-----------------------------------------|---------------------------------------|
| 整体架构          | 完全去中心化、多 Scheduler 并行存在            | Borg 只有一个全局 Scheduler            | Kubernetes（多个调度器可插拔）        |
| 状态存储          | 引入了“共享状态”（Shared State）+ Cell State   | 所有 Scheduler 直接操作同一份全局状态   | etcd + optimistic concurrency control |
| 冲突解决          | 乐观并发控制（Optimistic Concurrency Control） | 悲观锁 → 乐观锁 + 原子 Compare-and-Swap | Kubernetes Scheduler 的两阶段调度     |
| 调度流程          | 两阶段调度（Two-level Scheduling）彻底解耦      | 1. 框架自己决定要什么资源<br>2. Scheduler 只负责最终放置 | Kubernetes 的 Predicate + Priority    |
| Scheduler 类型    | 支持多种并行 Scheduler（Batch、Service、ML 等）| 每个团队可以写自己的 Scheduler          | Kubernetes Scheduler Profiles、Volcano |
| 事务机制          | 基于 Paxos 的分布式锁 + 增量事务更新            | 状态变更都是原子事务                    | Kubernetes CRD + Operator 模式        |
| 资源争用解决      | “Yield” 机制 + Priority + Preemption           | 低优先级任务可以主动让出资源            | Kubernetes PriorityClass + Preemption  |

#### Omega 的调度流程（经典到今天还在用）

1. 所有 Scheduler 共享一份全局集群状态（放在 Paxos 存储里）
2. 每个 Scheduler 独立拉取最新状态副本（读不加锁）
3. Scheduler 本地计算调度决策（放哪台机器）
4. 把决策以“事务”的方式提交（CAS 操作）
5. 如果冲突（别人先改了状态），事务失败 → 重新拉状态重算
6. 高优先级任务可以直接抢占（preempt）低优先级任务

这套“乐观并发 + 事务回滚”的玩法，把调度吞吐量直接从 Borg 的几百 QPS 提升到几千 QPS，冲突率控制在 5% 以内。

#### Omega 的真实地位和结局

| 时间线          | 事件                                              |
|-----------------|---------------------------------------------------|
| 2013-2014      | Omega 项目立项，目标是“让不同团队的 Scheduler 能和平共存” |
| 2015           | Eurosys 论文发表，学术界炸锅                      |
| 2015-2017      | Google 内部逐渐把所有新服务（包括最早的容器服务）迁到 Omega |
| 2016           | Kubernetes 1.2+ 的 Scheduler 设计几乎完全抄 Omega 的两级 + 乐观并发 |
| 2017 以后      | Omega 逐步被新一代 Borg（支持容器）+ Kubernetes 取代，但核心思想全部保留 |
| 2025 年现状    | Google 内部真正的生产调度器仍是“Borg 的后代”（代号 Colossus），但调度核心仍是 Omega 那套乐观并发架构 |

#### 一句话总结 Omega 的历史意义

**Borg 是“帝国时代”的中央集权皇帝**  
**Omega 是“联邦制”改革的开端**  
**Kubernetes 是把 Omega 的核心思想开源后，让全世界都用上了联邦制调度**

没有 Omega，就不会有今天 Kubernetes 的 Scheduler 框架、Volcano、KubeBatch、Koordinator 等一大票现代调度器。可以说，2025 年你看到的任何云原生调度器，骨子里流的都是 Omega 的血。

真正硬核的调度论文顺序（建议按这个顺序读）：
1. Borg（2015）→ 了解 Google 第一代集群管理
2. Omega（2015）→ 真正革命性的调度架构论文
3. Kubernetes Scheduler（2017+）→ 你会发现 80% 的设计是抄 Omega 的
4. Apollo（Microsoft，2018）/ Sigma（阿里，2020）→ Omega 的现代演进版
