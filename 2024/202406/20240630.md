好的,我来为您介绍一下 C 语言中常用的Redis客户端库。
在 C 语言中,有几个比较流行的 Redis 客户端库,包括:
1. hiredis
   - 这是 Redis 官方推荐的 C 语言客户端库。
   - 支持同步和异步两种操作模式。
   - 提供了简单易用的 API,可以方便地执行 Redis 命令。
   - 项目地址: https://github.com/redis/hiredis
2. credis
   - 这是另一个流行的 C 语言 Redis 客户端库。
   - 提供了与 hiredis 类似的 API,但增加了一些额外的功能,如连接池管理等。
   - 项目地址: https://github.com/chusiang/credis
3. predis
   - 这是一个基于 phpredis 的 C 语言 Redis 客户端库。
   - 支持同步和异步两种操作模式。
   - 提供了丰富的 Redis 命令支持。
   - 项目地址: https://github.com/nrk/predis
4. libredis
   - 这是一个轻量级的 C 语言 Redis 客户端库。
   - 提供了基本的 Redis 命令执行功能。
   - 项目地址: https://github.com/gerasimou/libredis
以上是 C 语言中常用的几个 Redis 客户端库,它们各有自己的特点和优势。您可以根据项目需求和使用习惯,选择合适的库进行开发。

滥用shared_ptr会有问题，举一个最近遇到的shared_ptr导致latency增加的例子：
```c++
#include <iostream>
#include <thread>
#include <chrono>
#include <memory>

struct A {
  void foo() {}
  double a[1];
};

int main() {
  std::shared_ptr<A> a = std::make_shared<A>();
  constexpr int N = 1000000;
  auto start_time = std::chrono::high_resolution_clock::now();
  for (int i = 0; i < N; ++i) {
    std::shared_ptr<A> x = a;
    x->foo();
  }
  auto end_time1 = std::chrono::high_resolution_clock::now();
  auto diff1 = end_time1 - start_time;

  for (int i = 0; i < N; ++i) {
    A* x = a.get();
    x->foo();
  }
  auto end_time2 = std::chrono::high_resolution_clock::now();
  auto diff2 = end_time2 - end_time1;

  std::cout << "elapsed time1: "
      << std::chrono::duration_cast<std::chrono::milliseconds>(diff1).count()
      << " ms" << std::endl;
  std::cout << "elapsed time2: "
      << std::chrono::duration_cast<std::chrono::milliseconds>(diff2).count()
      << " ms" << std::endl;
  return 0;
}

```

结果：elapsed time1: 53 ms
elapsed time2: 4 ms这个例子的背景是上游模块某个函数更改了接口，返回值为 std::shared_ptr，适配新接口之后 latency 增加严重，最后定位到是某个循环中使用了上面第一种写法的代码。评论区朋友们有很多讨论，有兴趣建议看一看。回到问题本身，为什么老板不让用shared_ptr？我觉得还是怕滥用导致类似上述这种错误，很多人“知其然，不知其所以然”，特别在大型项目中，涉及的模块太多，难以保证每个开发人员都能用对，有时候为了保证项目质量不得已要做出一些约束。
