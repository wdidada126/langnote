# 医疗软件系统

## 医疗领域软件全景（截至 2026-08）

HIS 是医院核心交易系统之一，但医疗信息化覆盖“居民健康 -> 医疗服务 -> 支付结算 -> 公共卫生 -> 医药器械 -> 科研监管”的完整链条。系统边界应按谁对业务结果和数据真实性负责划分，而不是按供应商产品名划分。一个医院通常同时运行数十个业务系统，HIS 通过医院信息平台与专业系统、区域平台、医保平台和患者服务连接。

### 先区分三类范围

| 范围 | 服务对象 | 代表系统 | 与 HIS 的关系 |
| --- | --- | --- | --- |
| 院内诊疗与运营 | 患者、医护、医技、药学、财务和管理人员 | EMR/CIS、LIS、RIS/PACS、PIS、HRP、SPD | HIS 提供就诊、医嘱、收费等核心上下文；专业系统拥有本专业执行和结果数据。 |
| 区域与行业协同 | 居民、基层机构、医院集团、医保和监管部门 | 区域健康平台、电子健康档案、公共卫生、医保结算、转诊平台 | 通过标准接口、数据目录、文档/消息和授权机制交换，不应直接共享业务库。 |

## 院内临床与医技系统

### 电子病历与临床信息系统

EMR（Electronic Medical Record，电子病历）记录一次或多次诊疗过程中的临床文书、诊断、病程、知情同意等；CIS（Clinical Information System，临床信息系统）常作为覆盖医嘱、医生站、护理、手术、重症等临床应用的统称，具体边界因医院而异。二者不能简单等同于收费型 HIS。

| 系统/能力 | 常见小类 | 关键控制点 |
| --- | --- | --- |
| 医生工作站/CPOE | 门急诊与住院医嘱、处方、诊断、病历、会诊、转诊 | 医嘱版本、停止/撤销、权限、过敏/相互作用/适应证规则与审计。 |
| 护理信息系统（NIS） | 护理评估、护理计划、体征、执行单、交接班、移动护理 | 患者腕带、执行人/时间、双人核对、漏执行和补录必须可追溯。 |
| 手术麻醉系统 | 排台、术前评估、麻醉记录、术中设备数据、术后恢复 | 手术患者/部位核查、耗材植入物、麻醉用药、时间轴和归档。 |
| ICU/专科系统 | 重症、血透、产科、肿瘤、康复、口腔等专科工作站 | 专科规则、设备数据、评分量表与通用 EMR 的数据映射。 |
| 临床决策支持（CDSS） | 合理用药、抗菌药物、危急值、路径、质控提醒 | 规则/知识库版本、触发依据、告警疲劳、人工确认和效果评估。 |
| 病案与医疗质量 | 病案首页、编码、质控、院感、不良事件、指标上报 | 原始病历、修订记录、质控规则和报表口径可回溯。 |

临床系统的正确目标不是“多弹窗提醒”，而是在正确角色、正确时间使用已授权且可信的数据，帮助完成诊疗与执行闭环。自动建议必须保留医生/药师/护士的专业判断和确认记录。

### 检查、检验与影像专业系统

| 缩写/系统 | 职责 | 典型闭环 |
| --- | --- | --- |
| LIS（Laboratory Information System） | 检验申请、标本、仪器结果、审核、报告、危急值 | 申请 -> 采集/条码 -> 签收/检测 -> 复核 -> 报告 -> 危急值通知与确认。 |
| RIS（Radiology Information System） | 放射检查预约、登记、排队、报告工作流和资源管理 | 申请 -> 预约/登记 -> 检查 -> 报告书写/审核 -> 发布。 |
| PACS（Picture Archiving and Communication System） | 医学影像接收、归档、传输、调阅和后处理 | 设备产生影像 -> 可靠归档 -> 与检查/报告关联 -> 临床调阅。 |
| 病理、超声、心电、内镜 | 各专科采集、阅片/判读、审核、报告和质控 | 将专科检查号、图像/波形/切片、报告版本与患者和申请单准确关联。 |
| 输血管理 | 血液申请、配血、发血、床旁核对、回收和不良反应 | 患者、血袋、交叉配血结果和执行记录形成全程追溯链。 |

这些系统应各自维护专业状态机。HIS/EMR 发起申请并展示结果，不代表其应直接写入 LIS、PACS 或设备数据库。接口要同时处理申请撤销、患者信息更正、重复消息、离线补传、报告修订和危急值升级。

### 药学、静配与供应链

| 系统/能力 | 小类 | 关键控制点 |
| --- | --- | --- |
| 药学信息系统（PIS） | 药品目录、处方审核、调剂、发药、药品库存、处方点评 | 药品编码、批号效期、处方到收费到发药、退药和库存账实闭环。 |
| 静脉用药调配中心（PIVAS） | 医嘱审核、排药、贴签、调配、成品核对、配送 | 患者、处方、药品批次、调配人员、核对和输注执行可追溯。 |
| SPD/医用耗材管理 | 采购、入库、配送、科室二级库、领用、盘点、结算 | 高值耗材的批号/序列号、患者植入记录、退货、召回和成本归集。 |
| 设备与资产管理（CMMS/EAM） | 台账、巡检、保养、维修、计量、报废 | 设备唯一身份、校准状态、故障工单和与检查结果的关联。 |

医疗器械 UDI（Unique Device Identification）为器械产品、生产信息和数据库关联提供标准化标识基础。医院的采购、库存、使用和追溯系统应能在适用范围内保存 UDI-DI/UDI-PI 与患者、手术、批号和使用记录的关联，但不能把“扫码”误当作召回和不良事件闭环已经完成。

## 患者服务、运营与支付系统

### 患者服务与互联网医疗

患者服务系统通常包括预约挂号、排队叫号、支付、报告查询、院内导航、智能客服、随访、健康管理、远程医疗和互联网医院。它们是患者体验入口，不应成为新的患者主数据源；应以医院主索引、实名认证和授权规则统一身份。

互联网医院涉及在线复诊、处方、药事、支付、配送、随访等协同。关键不是视频/图文功能，而是医生资质与排班、患者身份、服务范围、处方审核、电子签名、线上线下病历一致性、异常升级和隐私保护。银医通/移动支付属于支付连接能力，应与挂号、计价、退费、医保结算和财务对账形成明确状态机，不能只以第三方支付回调作为最终业务事实。

### 医院运营管理

| 系统 | 典型小类 | 数据与治理重点 |
| --- | --- | --- |
| HRP/ERP | 财务、预算、总账、成本、采购、合同、资产、人力、薪酬 | 科室、项目、人员、资产和费用口径与临床业务一致，避免“多套报表各算各的”。 |
| DRG/DIP 与医保运营 | 分组、病案质控、费用分析、结算清单、异常提示 | 医保政策、编码、结算规则和版本生效日期；结果需可追溯到病案和费用明细。 |
| BI/运营驾驶舱 | 门急诊量、床位、病种、成本、质量、绩效和预测 | 指标定义、数据血缘、刷新频率、授权范围；驾驶舱不应绕过原始业务系统。 |
| OA/BPM/排班 | 公文、审批、排班、培训、任务和制度 | 与临床排班、权限、成本归属的接口；不可把行政流程审批替代医疗安全流程。 |

## 医疗数据平台与互操作系统

医院信息平台/HIE（Health Information Exchange）承担多系统互联、主数据、数据标准、服务目录、审计和交换治理。它不是简单 ESB，也不是把所有库同步到一个大表；至少要明确数据归属、事件/文档的业务语义、失败补偿和数据质量责任。

| 平台能力 | 子能力 | 设计要点 |
| --- | --- | --- |
| 主数据与患者主索引（MPI/EMPI） | 患者、人员、机构、科室、药品、项目、术语字典 | 设置权威源、唯一标识、合并/拆分、停用和人工复核规则。 |
| 集成平台 | API 网关、集成引擎、消息、服务编排、接口监控 | 每个接口有版本、幂等键、超时、重试、死信、补偿和业务负责人。 |
| 临床数据中心/数据仓库 | 文档库、主题库、指标库、科研数据集、市级/集团数据汇聚 | 区分生产交易、分析、科研与监管用途；数据延迟和质量不能被隐藏。 |
| 术语与标准服务 | 诊断、手术、药品、检验、病案、机构和项目编码映射 | 版本化、映射依据和变更影响分析；禁止各系统私自复用同一文本却语义不同。 |
| 身份、权限与审计 | SSO、MFA、RBAC/ABAC、授权、日志、堡垒机 | 最小权限、就诊关系、敏感操作二次确认、导出控制和可检索审计。 |

HL7 v2、CDA、DICOM、FHIR 等是不同场景的互操作标准或规范。FHIR 使用资源和 API 风格，不自动解决患者匹配、术语映射、授权、跨机构责任、数据质量或历史系统改造。相关说明见 [his_HL7_FHIR.md](his_HL7_FHIR.md)。

## 区域健康、公共卫生与医保系统

### 区域健康和基层公卫

区域全民健康信息平台、电子健康档案（EHR）、基层医疗卫生信息系统、家庭医生签约、双向转诊、妇幼保健、免疫规划、慢病管理、老年健康、疾病监测与突发公共卫生应急等，服务的是连续健康管理和公共卫生责任，而不是单次医院收费。

居民电子健康档案不等于把所有医院病历无差别复制到一个库。应按法律政策、诊疗目的、授权和最小必要原则归集；患者身份匹配、档案质量、来源标识、更新时间和访问审计决定共享数据是否可用。国家卫生健康委 2024 年关于居民电子健康档案首页的通知要求依托区域平台，推动电子病历及妇幼、免疫、慢病、老年健康等系统的信息动态归集和共享。

### 医保和商业健康险

医保相关系统覆盖参保人服务、定点机构、目录与编码、费用结算、清算对账、基金监管、电子凭证/移动支付、电子处方流转和个人授权查询等。医院侧必须将诊疗、收费、病案、药品耗材、医保规则和财务对账串成可复核证据链；医保结算成功、医院收费成功、银行/支付渠道成功是不同状态，必须分别记录和对账。

商业健康险系统还包括产品、投保、核保、理赔、直付网络、健康管理和反欺诈。保险公司、医院、TPA 和药店之间的数据交换必须有明确授权、用途、保留期限和责任边界，不能因“便捷理赔”而扩大无关数据访问。

## 医药、器械和生命科学软件

### 药品研发、生产、流通与药物警戒

| 环节 | 常见系统 | 关键问题 |
| --- | --- | --- |
| 研发与临床试验 | CTMS、EDC、ePRO/eCOA、IRT/IWRS、eTMF、药物随机化和供应管理 | 方案版本、受试者知情同意、稽查追踪、数据修改痕迹、盲态保护和中心管理。 |
| 药物安全 | 药物警戒（PV）、不良事件、信号检测、病例处理、定期安全报告 | 病例来源、时限、医学评估、重复合并、监管报告和可审计性。 |
| 生产与质量 | ERP、MES、LIMS、QMS/eQMS、DMS、设备管理、序列化/追溯 | 批记录、偏差、CAPA、变更控制、放行、审计追踪和计算机化系统验证。 |
| 商业与流通 | 供应链、WMS、冷链、经销、合规、药店/处方流转 | 批号效期、温湿度、召回、流向、渠道权限与合规审计。 |

药企的 LIMS 管理研发或生产实验室样本、方法和结果；医院 LIS 管理临床检验流程，二者缩写相同但业务责任、法规语境和接口对象不同。CTMS 管试验运营，EDC 管受试者研究数据，eTMF 管试验主文件；把它们合并成一个“临床试验系统”会掩盖关键合规边界。

### 医疗器械与数字医疗产品

器械企业常使用 PLM、QMS/eQMS、ERP、MES、LIMS、售后服务、投诉不良事件、注册申报和 UDI 管理系统。软件若具备医疗器械属性，还需要管理需求、风险、验证确认、版本发布、网络安全、投诉和上市后监测等全生命周期证据，不能按普通互联网 App 的“快速上线后再说”方式处理。

医疗器械 UDI 数据库由国家药监局统筹，注册人/备案人负责相关数据的上传、维护和真实性；医院、供应链和监管系统可据此支持产品识别与追溯。独立软件在适用 UDI 规则时也存在电子显示/API 提供标识等要求，具体适用性应按产品类别、注册状态和当期监管文件判断。

## 科研、教学与数据智能系统

科研数据平台、临床研究管理、专病库、队列管理、生物样本库、LIMS、影像 AI、真实世界数据（RWD）平台、医学教育与模拟培训系统，都不应直接占用生产 HIS 的事务库进行高负载分析。应通过经审批的数据抽取、去标识化/匿名化、最小数据集、访问控制、用途限制和审计提供数据服务。

AI 系统可用于影像辅助、病历质控、语音转写、科研检索、运营预测和患者服务。上线前至少评估训练/知识来源、目标人群偏差、输出适用范围、人工复核、错误反馈、模型与提示词版本、日志留存和安全边界。临床决策或诊断建议不能因模型输出而免除医疗机构与专业人员的责任。

## 一条典型数据链路

以住院手术患者为例：患者服务/登记创建患者和就诊 -> HIS/EMR 建立住院、医嘱和病历 -> LIS/RIS/PACS 等产生检查检验与报告 -> 手术麻醉、输血、耗材/UDI、药学和护理记录执行事实 -> 收费和医保系统完成结算、清单和对账 -> 病案/质控形成编码与质量记录 -> 平台将授权范围内的数据服务给集团、区域、公卫、科研或运营系统。

其中任何一步都不能只靠患者姓名匹配；需要稳定主键、来源系统、业务时间、状态、版本、操作者、授权依据和审计轨迹。跨系统最常见问题是重复患者、撤销未同步、编码版本错配、费用与执行不一致、接口重试导致重复处理、报告修订覆盖历史、数据导出越权和备份无法恢复。

## 建设与验收优先级

1. 先跑通患者身份、就诊、医嘱/执行、费用/结算、药品耗材和报告的核心闭环，再追求大屏、AI 或“数据中台”展示。
2. 每类系统明确系统 of record、业务主键、权威字段、更新责任和接口所有者；禁止以数据库直连作为常规集成方案。
3. 将数据质量、权限审计、容灾恢复、接口失败补偿和历史迁移作为上线验收项，而非上线后优化项。
4. 按真实场景做端到端演练：退费退药、患者合并/拆分、报告更正、医保撤销/冲正、设备/接口离线、同城或异地恢复。
5. 采购时要求数据可导出、接口契约、标准支持范围、实施范围、升级责任、漏洞响应、SLA、退出与交接条款；不要只比较许可证和演示功能。
