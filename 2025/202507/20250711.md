上世纪金融软件主要使用C语言而非C++或Fortran，主要有以下几个原因：

1. 历史背景与技术成熟度：
   - C语言的崛起：1970年代诞生的C语言在1980年代已成为系统编程的主流，而C++（1983年诞生）在上世纪90年代才逐渐成熟。早期金融系统需要稳定、高效的底层控制，C语言更符合需求。
   - Fortran的领域局限：Fortran虽擅长科学计算，但金融软件需要复杂的数据结构和业务逻辑处理，C的灵活性更适合。
2. 性能与硬件限制：
   - 零开销原则：C语言贴近硬件，适合编写高性能代码，而早期C++的虚函数和异常处理可能引入额外开销。
   - 内存管理：金融系统（如交易引擎）需要手动优化内存，C的`malloc/free`比C++的早期垃圾回收或Fortran的静态内存更可控。
3. 跨平台与可移植性：
   - C语言在UNIX系统上占主导地位，而早期金融系统多运行于UNIX服务器。C++编译器在不同平台差异较大，Fortran则更局限于科学计算环境。
4. 开发效率与生态：
   - 工具链支持：C的编译器（如GCC）成熟稳定，调试工具（如gdb）完善，而C++标准（如STL）在上世纪90年代才逐步统一。
   - 代码复用需求低：早期金融软件规模较小，面向对象特性（如C++的类）并非必需，过程式编程（C）已足够。
5. 行业惯性：
   - 金融领域保守，已投入的C代码库难以迁移。例如，Reuters的早期市场数据系统、Bloomberg的终端核心模块均以C为主。

例外情况：
   - 定量分析领域：部分金融数学库（如蒙特卡洛模拟）可能用Fortran编写，因其数值计算性能优异。
   - 90年代后期：随着衍生品定价模型复杂化，C++逐渐在投行前台系统中普及（如利率模型使用QuantLib库）。

总之，C语言在控制力、性能和生态上的优势使其成为上世纪金融软件的主流选择，而C++和Fortran的适用场景相对有限。这一技术选择反映了当时硬件条件和业务需求的权衡。

在中国金融机构信息化初期（20世纪70-90年代），银行业从手工记账逐步过渡到电子化处理，这一阶段的软件采购和系统建设主要围绕核心业务处理、联行清算和办公自动化展开。以下是关键时期的软件系统、功能及供应商情况，以及后续国产化替代的进程：

### 1. 早期电子化阶段（1970s-1980s）
#### 主要软件系统及功能
- 银行会计核算系统  
  - 功能：替代手工记账，实现账务自动化处理，包括存款、贷款、结算等基础业务。  
  - 供应商：国内自主研发（如中国人民银行核算工厂）及引进国外小型机（如法国60/61小型机）。  

- 电子联行系统（EIS）  
  - 功能：解决跨行资金清算问题，替代电报和邮件对账，提高联行业务效率。  
  - 供应商：中国人民银行主导，初期依赖VAST卫星通信网络，后期引入IBM等国外系统。  

#### 硬件与软件供应商
- 国外供应商：  
  - IBM（大型机、小型机）、日立（M-150中型机）、法国Bull（60/61小型机）。

### 2. 核心业务系统建设（1980s-1990s）
#### 主要软件系统及功能
- SAFE II（IBM定制化核心系统）  
  - 功能：工行、中行、建行采用，支持存贷款、结算、联行对账等核心银行业务。  
  - 供应商：IBM（提供源代码，国内银行进行本地化改造）。

### 3. 国产化替代进程（2000s至今）
#### 国外系统主导期（1990s-2000s）
- 核心系统供应商：  
  - 繁德（FIS，建行、农行、交行）、IBM（建行、宁波银行）、塔塔TCS（中行）、甲骨文（平安银行）。  
- 底层架构：IBM大型机、Oracle数据库、UNIX系统（形成“IOE”依赖）。

- 核心系统国产化：  
  - 长亮科技（替代FIS，服务多家城商行、农商行）。

### 总结
- 早期（1970s-1990s）：依赖国外硬件（IBM、日立）和定制软件（SAFE II），国内尝试自主研发但技术受限。  
- 成长期（1990s-2000s）：“两联两天”主导集成，国外核心系统（FIS、IBM）占据主流。  
- 国产替代（2010s后）：长亮、神州数码等逐步替代国外系统，信创政策加速去“IOE”进程。

你提供的宏定义是一个非常常见的 调试打印宏，用于在 C/C++ 项目中方便地开启或关闭调试信息输出。我们来一步一步讲解它，并给出一个完整可执行的 C 语言示例程序。


##  宏定义解释

```c
#define DEBUG_PRINT(fmt, ...) \
do { \
    printf(fmt, ##__VA_ARGS__); \
} while (0)
```

### 🔍 含义：

- `#define DEBUG_PRINT(fmt, ...)`：定义一个带可变参数的宏。
- `fmt`：格式化字符串（类似 `printf` 的第一个参数）。
- `__VA_ARGS__`：表示可变参数列表。
- `##__VA_ARGS__`：如果可变参数为空，`##` 会把前面的逗号去掉，避免编译错误。
- `do { ... } while (0)`：确保宏可以像语句一样使用，比如配合 `if/else` 不出错。

---

##  示例：完整的可执行 C 程序

```c
#include <stdio.h>

// 调试打印宏
#define DEBUG_PRINT(fmt, ...) \
do { \
    printf("[DEBUG] " fmt "\n", ##__VA_ARGS__); \
} while (0)

int main() {
    int a = 10;
    int b = 20;

    DEBUG_PRINT("This is a debug message.");
    DEBUG_PRINT("a = %d", a);
    DEBUG_PRINT("a = %d, b = %d", a, b);

    return 0;
}
```


##  输出结果（运行后）：

```text
[DEBUG] This is a debug message.
[DEBUG] a = 10
[DEBUG] a = 10, b = 20
```

##  可选功能：开关调试输出
你可以通过定义或取消定义 `ENABLE_DEBUG` 来控制是否启用调试输出：

```c
#include <stdio.h>

//  注释掉这一行即可关闭所有调试输出
#define ENABLE_DEBUG

#ifdef ENABLE_DEBUG
    #define DEBUG_PRINT(fmt, ...) \
    do { \
        printf("[DEBUG] " fmt "\n", ##__VA_ARGS__); \
    } while (0)
#else
    #define DEBUG_PRINT(fmt, ...)  // 空操作
#endif

int main() {
    int a = 10;
    int b = 20;

    DEBUG_PRINT("This is a debug message.");
    DEBUG_PRINT("a = %d", a);
    DEBUG_PRINT("a = %d, b = %d", a, b);

    return 0;
}
```

> - 当你注释掉 `#define ENABLE_DEBUG`，所有的 `DEBUG_PRINT(...)` 都不会输出任何内容。
> - 这种方式非常适合用于项目构建时区分 Debug / Release 模式。


##  编译与运行（Linux/macOS）
保存为 `debug_print.c`，然后执行：

```bash
gcc debug_print.c -o debug_print
./debug_print
```

##  编译与运行（Windows 命令行）
使用MinGW或Visual Studio开发环境编译：

```bash
gcc debug_print.c -o debug_print.exe
debug_print.exe
```

### 1. 技术演进的滞后性
   - JSON的普及时间较晚：虽然JSON在2000年代初已被提出，但其成为主流数据交换格式是在2010年左右（随着 Web 2.0和RESTful API 的兴起）。而Java标准库的更新周期较长，新功能的引入需要经过 Java 社区进程（JCP）和 JSR（Java 规范请求）的漫长流程。
   - Java EE 的分离：JSON 处理最初被纳入 Java EE 规范（如 JSR 353: JSON-P 在 Java EE 7 中引入），而非 Java SE。Java EE 由独立组织（如 JCP）管理，与 Java SE 标准库分开发布，导致 Java SE 用户需额外引入依赖。

### 2. 第三方库的成熟与生态竞争
   - 早期已有成熟解决方案：在 JSON 流行前，XML 是主要的数据交换格式（Java 标准库内置了 JAXB 和 DOM 等 XML 工具）。而 JSON 处理库（如 Jackson、Gson、Fastjson）在社区中迅速成熟，满足了大部分需求，削弱了标准库集成的紧迫性。
   - 性能与灵活性权衡：第三方库（如 Jackson）通过优化（如流式解析、字节码生成）实现了高性能，而标准库需兼顾通用性，可能无法在特定场景下竞争。

### 3. 标准化进程的复杂性
   - JSR 353 的局限性：Java EE 7 引入的 JSON-P（JSR 353）仅提供基础的解析和生成 API，缺乏对象绑定功能（如 Java 对象与 JSON 的自动转换）。更高级的 JSON-B（JSR 367）直到 Java EE 8 才加入，进一步延迟了标准化进程。
   - 模块化与兼容性挑战：Java 9 引入模块化系统（JPMS）后，标准库的扩展需考虑模块隔离和向后兼容性，增加了集成新功能的复杂度。

### 4. 社区与厂商的分歧
   - 厂商主导的生态：Oracle 和 OpenJDK 社区更关注语言核心特性（如 Lambda、模块化），而 JSON 处理被视为“应用层需求”，由第三方库（如阿里 Fastjson、Google Gson）或 Java EE 供应商（如 Red Hat）主导。
   - 信创与国产化影响：国内开发者更倾向使用 Fastjson，而国际社区偏好 Jackson，标准库难以统一各方需求。

### 5. 后续进展
   - Java EE 到 Jakarta EE：随着 Java EE 移交 Eclipse 基金会（更名为 Jakarta EE），JSON-P 和 JSON-B 成为 Jakarta EE 的一部分，但仍需用户显式引入依赖（如 `jakarta.json` 包）。
   - Java SE 的补充：直到 Java 15 之后，标准库仍未直接集成 JSON，但通过 Project Panama 等计划探索更高效的数据交换支持。

### 总结
Java 标准库未内置 JSON 支持，本质上是由于 技术演进节奏、第三方库生态竞争 和 标准化复杂性 共同作用的结果。开发者仍需依赖第三方库（如 Jackson）或 Jakarta EE 的扩展包（如 JSON-P/JSON-B）处理 JSON。

在 Conan、vcpkg等现代 C/C++包管理工具出现之前，开发者管理第三方库的方式确实较为原始，主要依赖以下几种方式：

### 1. 手动下载源码 + 编译安装
- 常见方式：
  - 从官网（如 `SourceForge`、`GitHub`、`项目主页`）下载源码包（`.tar.gz`、`.zip`）。
  - 解压后运行 `./configure`（Autotools 项目）或 `cmake`（CMake 项目），再执行 `make && make install`。
  - 可能需手动解决依赖（如先安装 `zlib`、`openssl` 等）。
- 问题：
  - 依赖地狱：库 A 依赖库 B 的特定版本，而库 C 依赖库 B 的另一个版本，导致冲突。
  - 系统污染：`make install` 默认安装到 `/usr/local`，可能覆盖系统包管理器（如 `apt`）安装的版本。
  - 跨平台困难：Windows 开发者需手动配置 Visual Studio 项目包含路径和库路径。
举例：make 4.3

### 2. 系统包管理器（apt/yum/homebrew）
- 适用场景：
  - Linux 发行版（如 Ubuntu/Debian/CentOS）通过 `apt`、`yum` 提供预编译的库（如 `libcurl-dev`）。
  - macOS 通过 `Homebrew` 或 `MacPorts` 安装库（如 `brew install openssl`）。
- 局限性：
  - 版本滞后：系统仓库的库版本通常较旧（如 Ubuntu LTS 的库可能落后上游数年）。
  - 平台限制：Windows 无统一包管理器（直到 `vcpkg` 出现）。

### 3. 手动管理二进制包
- Windows 开发者常见做法：
  - 下载预编译的 `.lib`/`.dll` 文件（如 Boost 官方提供的 Windows 二进制包）。
  - 手动配置 IDE（如 Visual Studio）的包含路径（`Include Directories`）和库路径（`Library Directories`）。
- 问题：
  - ABI 兼容性问题：不同编译器（如 MSVC 和 MinGW）或运行时版本（如 MT vs MD）编译的库无法混用。
  - 调试版/发布版混淆：需区分 `Debug` 和 `Release` 版本的库。

### 4. 嵌入式源码（Vendor）
- 常见于小型项目：
  - 直接将第三方库源码（如 `stb_image.h`、`nlohmann/json`）复制到项目目录中。
  - 通过 `git submodule` 引入依赖（如 `git submodule add https://github.com/xxx/yyy.git`）。
- 优点：
  - 避免外部依赖，适合跨平台分发。
- 缺点：
  - 更新困难，可能引入安全风险（如未及时同步上游修复）。

### 5. 自研工具链或脚本
- 大公司的解决方案：
  - Google 使用 `Bazel`（原 `Blaze`）管理依赖和构建。
  - Meta（Facebook）开发 `Buck` 或内部工具链。
  - 游戏公司（如育碧）可能用 `Python` 脚本自动化下载和编译依赖。
- 特点：
  - 高度定制化，但维护成本高。

### 6. 无依赖或重复造轮子
- 极端情况：
  - 开发者因管理依赖太麻烦，直接手写功能（如自己实现 JSON 解析、哈希表等）。
  - 典型案例：早期游戏引擎（如 Quake）几乎零第三方依赖。

### 为什么需要 Conan/vcpkg？
- 解决痛点：
  - 依赖管理：自动下载、编译、链接依赖库。
  - 版本控制：支持多版本共存（如 OpenSSL 1.1 和 3.0）。
  - 跨平台一致性：统一 Windows/Linux/macOS 的库获取方式。
  - 构建系统集成：与 CMake、Visual Studio 等工具链无缝协作。

### 总结
在现代化工具（如 Conan、vcpkg）之前，C/C++ 开发者主要依赖手动编译、系统包管理器或源码嵌入，导致：
1. 依赖管理混乱（“DLL Hell” 的 C++ 版）。
2. 项目配置复杂（尤其是 Windows 开发）。
3. 跨团队协作困难（需文档记录依赖安装步骤）。

这些痛点直接推动了现代 C++ 包管理工具的诞生。

在Windows平台的C/C++开发中，/MT和/MD是Microsoft Visual Studio（MSVC）编译器提供的两种运行时库（CRT, C Runtime Library）链接选项，它们决定了程序如何链接和使用C标准库（如内存管理、文件操作等基础功能）。以下是关键区别和注意事项：

### 1. 核心区别
| 编译选项 | 含义                          | 链接方式               | 适用场景                  | 堆管理问题                  |
|----------|-------------------------------|------------------------|---------------------------|-----------------------------|
| /MT  | 多线程静态链接（Static Link） | 将运行时库（如`LIBCMT.lib`）直接嵌入到程序中 | 程序独立运行，不依赖系统DLL | 每个模块有自己的堆，跨模块释放内存会导致崩溃 |
| /MD  | 多线程动态链接（Dynamic Link）| 依赖系统提供的DLL（如`MSVCRT.dll`） | 减少程序体积，共享系统库   | 所有模块共享同一堆，避免跨堆释放问题 |

- /MT：运行时库代码直接编译进程序，生成的文件较大，但无需外部DLL支持。
- /MD：程序运行时动态加载系统目录下的`MSVCRT.dll`，文件较小，但需确保目标系统有对应版本的运行时库。

### 2. 为什么不能混用？
1. 堆内存管理冲突  
   - /MT：每个模块（EXE/DLL）有独立的堆，若在模块A中申请内存，在模块B中释放，会因堆不匹配导致崩溃。
   - /MD：所有模块共享系统DLL的堆，无此问题。

2. 运行时库版本不一致  
   - 若DLL1使用`/MD`链接`MSVCRT120.dll`，而DLL2使用`/MT`嵌入静态库，可能导致全局状态（如文件句柄、locale设置）无法共享。

3. 调试与非调试版本混用  
   - 混合`/MTd`（Debug）和`/MT`（Release）会引发符号冲突（如`LIBCMTD.lib`与`LIBCMT.lib`）。

### 3. 如何选择？
- 优先使用/MD：  
  - 减少程序体积，便于更新运行时库（通过Windows Update）。
  - 适用于多模块项目（如主程序+多个DLL），确保堆统一。

- 使用/MT的场景：  
  - 目标系统可能缺少所需CRT DLL（如老旧Windows）。
  - 需完全独立分发的工具（如绿色软件）。

### 4. 常见问题解决
- 错误示例：  
  ```plaintext
  LIBCMT.lib(chsize.obj) : error LNK2005: __chsize already defined in MSVCRT.lib
  ```
  原因：项目混合了`/MT`和`/MD`编译的库。  
  解决：统一所有模块的编译选项。

- 第三方库不可控时：  
  - 若第三方库仅提供`/MT`版本，主程序也需改用`/MT`。
  - 或联系供应商获取`/MD`版本。

### 5. 扩展：Debug与Release版本
- /MTd、/MDd：调试版本（带`_DEBUG`宏），链接调试版CRT（如`MSVCRTD.dll`），不可与Release版本混用。

### 总结
- /MT：自包含，无DLL依赖，但需避免跨模块内存操作。  
- /MD：依赖系统DLL，模块间兼容性好，但需确保目标环境有匹配的CRT。  
- 强制规则：同一进程内所有模块（EXE/DLL）必须使用相同的运行时库选项。
