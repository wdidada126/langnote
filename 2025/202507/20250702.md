今天跟大家聊聊面试里超级常见的“虚函数表”（vtable），很多人回答只说“支持多态”，其实那只是皮毛！
想要面试官眼前一亮，你得懂这几个细节
1.  vptr和vtable的关系
每个对象都有个隐藏指针vptr，指向类的虚函数表vtable。调用虚函数其实是先通过vptr找到vtable，再跳到具体函数地址。
2.  多继承时的vtable
知道多继承会导致一个对象里有多个vptr吗？这就是为了指向各自基类的vtable，面试中说出来，分分钟加分。
3.  纯虚函数在vtable里长啥样？
其实纯虚函数对应的vtable函数指针通常指向“纯虚调用处理函数”，说这个能显得你理解到底层实现。
4.  为什么虚析构必须设为虚？
这是为了保证用基类指针delete子类对象时，析构函数能正确调用，避免内存泄漏。
记住，不要只说“多态”两个字，带上这些细节和原理，面试官立马觉得你不简单。

一、基础架构：分层设计与接口标准化
1. 核心系统为枢纽
核心银行系统：负责账户管理、记账、清算等底层功能，是所有业务的数据中心（如存款、贷款的本金利息计算）。
外围系统对接：通过标准化接口（如API、消息队列）与核心系统交互，例：
柜面系统（前端操作）→ 核心系统（账务处理）；
电子银行系统（APP/网银）→ 核心系统（查询/转账）。
2. 接口协议统一
采用ISO 20022（国际支付标准）、SWIFT（跨境结算）等协议，确保不同系统间数据格式一致（如交易指令、账户信息）。
二、业务串联：以转账为例的流程逻辑
1. 发起端系统处理
客户通过手机银行（渠道系统）提交转账请求，系统校验身份后，将指令发送至支付清算系统（如国内的大小额支付系统）。
2. 中间环节数据流转
支付清算系统按规则路由指令：
同行转账：直接调用核心系统完成扣款与入账（如工行转工行，实时到账）；
跨行转账：通过央行清算系统（如网联、银联）与接收行核心系统交互，完成资金划拨。
3. 接收端系统响应
接收行核心系统校验指令合法性（如账户存在、余额充足），执行入账并返回结果至支付清算系统，最终反馈给发起端系统（显示转账成功）。
三、数据一致性保障：分布式事务与对账机制
1. 事务一致性控制
采用“两阶段提交（2PC）”或分布式事务框架（如Seata），确保跨系统交易要么全部成功，要么全部回滚（例：转账时扣款与入账必须同时完成，避免单边账）。
2. 每日对账机制
系统间对账：核心系统与清算系统、第三方支付等每日日终核对交易明细，通过“流水比对+余额试算”发现差异（如某笔转账未记账），自动触发补账或人工核查。
内外账核对：银行核心系统与客户账户（如信用卡、理财账户）余额定期校验，防止数据不一致（例：理财赎回金额未及时到账）。

你在 Windows 11 上将文件名从 b.java 改成了 B.java（即更改了大小写），但在使用 Git 提交并推送到远程仓库后，远程仓库的文件名没有变化。这是 Git 在 Windows 系统上的一个常见问题。

问题原因
Git 默认在 Windows 上忽略文件名大小写（ignorecase = true）
Git 会根据操作系统决定是否区分文件名大小写：

Windows 和 macOS（默认文件系统不区分大小写）：Git 默认设置为：
Ini
[core]
    ignorecase = true
这意味着 Git 认为 b.java 和 B.java 是同一个文件！

所以当你执行：

git mv b.java B.java
Git 并不会认为这是一个“重命名”，而只是一个“大小写变更”，但底层文件系统（Windows）并不真正支持区分大小写的文件名，导致 Git 没有正确提交这个变更。

解决方案
强制 Git 区分大小写（推荐）
步骤 1：启用 core.ignorecase = false
git config core.ignorecase false
git config --global core.ignorecase false

Windows 默认文件系统（NTFS）是不区分大小写的，所以 Git 默认行为是为了兼容。
如果你在开发 Java、C++ 等语言项目，类名和文件名通常严格匹配（如 B.java），建议在 Windows 上设置 core.ignorecase = false 避免重命名问题。
如果你使用 WSL2（Windows Subsystem for Linux），它支持真正的大小写区分，也可以在那里做更准确的 Git 操作。

你遇到的错误：

```
error: The following untracked files would be overwritten by checkout:
    some_file

```

但执行 `git status` 后却发现 **没有任何未跟踪文件（Untracked Files）**，这是一个看似矛盾的情况。以下是可能原因和解决办法。

---

## 为什么会出现这个现象？

Git 的 `checkout` 命令会检查目标分支中某些路径是否已经在当前工作目录中存在未被 Git 跟踪的文件（即“untracked”），这些文件可能会在切换分支时被覆盖。

但是，有些文件虽然没有出现在 `git status` 中，却仍然属于“untracked”，因为它们匹配了 `.gitignore` 规则，所以不会显示在 `git status` 的 “Untracked files” 列表中。

---

## ✅ 解决方法

### 方法一：查看被忽略但存在的文件（推荐）

运行以下命令来查找所有被 `.gitignore` 忽略但实际存在于工作目录中的文件：

```bash
git ls-files --others --ignored --directory --no-empty-directory
```

输出类似：

```
logs/
build/
*.tmp
```

这些文件就是 Git 认为是“untracked”的，但在 `git status` 中不显示的原因是因为它们被 `.gitignore` 忽略了。

---

### 方法二：强制 checkout（慎用）

如果你确定这些文件不会影响你要切换的分支内容，可以使用 `-f` 强制切换分支：

```bash
git checkout -f <branch-name>
```

⚠️ 注意：这会 **丢弃所有未跟踪或修改的文件**，包括被 `.gitignore` 忽略的文件。

---

### 方法三：手动删除/移动冲突文件

你可以根据提示信息中的文件名，手动删除或移动这些文件，例如：

```bash
rm -rf some_file
```

然后再尝试切换分支。

---

## 进阶排查技巧

如果你想确认 Git 是不是真的检测到这些“untracked”文件，可以使用：

```bash
git check-attr all -- some_file
```

或者：

```bash
git hash-object -t blob -w --path=some_file some_file
```

看看 Git 是否能处理该文件。

---

## ✅ 总结

| 现象 | 原因 | 解决方案 |
|------|------|-----------|
| `Untracked files prevent checkout` 但 `git status` 没有输出 | 文件被 `.gitignore` 忽略了，不在状态中显示 | 使用 `git ls-files --ignored` 查看 |
| 想快速解决问题 | 可以强制 checkout | 使用 `git checkout -f` |
| 想保留文件 | 手动备份后删除再切换分支 | 移动文件到其他位置 |
