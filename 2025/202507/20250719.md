new_local_repository(name, build_file, build_file_content, path, repo_mapping)
将不包含 Bazel 文件的本地目录作为代码库提供。此目录无需包含 Bazel BUILD 文件或代码库边界文件；这些文件将由此代码库规则创建。如果目录中已包含 Bazel 文件，请考虑改用 <a href="#local_repository"><code>local_repository</code></a>。

属性
name  名称；必需
此代码库的唯一名称。

build_file  标签；可选
要用作此代码库的 BUILD 文件的文件。

必须指定 build_file 和 build_file_content 中的一个（且只能指定其中一个）。

此标签所引用的文件不必命名为 BUILD，但可以这样命名。BUILD.new-repo-name 之类的名称可能很适合用来将其与实际的 BUILD 文件区分开来。

build_file_content  字符串；可选
要为此代码库创建的 BUILD 文件的内容。

必须指定 build_file 和 build_file_content 中的一个（且只能指定其中一个）。

path  字符串；必需
要作为代码库提供的目录的路径。

该路径可以是绝对路径，也可以是相对于工作区根目录的相对路径。

repo_mapping  字典：String -> String；必需
一个字典，用于将本地代码库名称转换为全局代码库名称。这样，您就可以控制此代码库的依赖项的工作区依赖项解析。

例如，条目“@foo”:“@bar”声明，每当此仓库依赖于“@foo”（例如依赖于“@foo//some:target”）时，它实际上应在全局声明的“@bar”中解析该依赖项（“@bar//some:target”）。

在 Java 的并发编程中，`Condition` 和 `ConditionObject` 都是与条件变量相关的类，它们主要用于实现线程间的协调和通信。理解它们之间的联系、区别以及作用对于编写高效且正确的并发程序非常重要。

### 1. `Condition` 接口

定义：
- `Condition` 是一个接口，位于 `java.util.concurrent.locks` 包中。
- 它提供了类似 `Object` 类中的 `wait()`、`notify()` 和 `notifyAll()` 方法的功能，但这些方法必须与显式的锁（如 `Lock`）一起使用，而不是隐式的监视器锁（即同步块或同步方法使用的锁）。

核心方法：
- `await()`：使当前线程等待直到被其他线程唤醒。
- `signal()`：唤醒一个等待的线程。
- `signalAll()`：唤醒所有等待的线程。

使用场景：
- 当你需要更灵活地控制锁的行为时，比如读写锁、公平锁等，`Condition` 提供了比传统的 `synchronized` 更强大的功能。

### 2. `ConditionObject` 类

定义：
- `ConditionObject` 是 `AbstractQueuedSynchronizer` (AQS) 的内部静态类，实现了 `Condition` 接口。
- 它是 AQS 框架的一部分，用于支持基于 AQS 实现的锁（如 `ReentrantLock`）上的条件队列管理。

核心特点：
- `ConditionObject` 使用了两个队列：
  - 同步队列（Sync Queue）：用于管理获取锁的线程。
  - 条件队列（Condition Queue）：用于管理等待某个条件的线程。
- 当调用 `await()` 方法时，当前线程会被加入到条件队列，并释放锁；当调用 `signal()` 或 `signalAll()` 方法时，会从条件队列中移除一个或多个线程，并将它们重新插入同步队列以尝试重新获取锁。

### 3. 联系与区别

#### 联系：
- `ConditionObject` 是 `Condition` 接口的具体实现。
- `ConditionObject` 主要用于与基于 AQS 的锁（如 `ReentrantLock`）配合使用，而 `Condition` 则是一个通用接口，任何符合该接口规范的实现都可以使用。

#### 区别：
- 实现基础：`ConditionObject` 基于 AQS 实现，而 `Condition` 只是一个接口。
- 使用方式：`ConditionObject` 必须与 AQS 锁（如 `ReentrantLock`）一起使用，而 `Condition` 可以由任何实现了该接口的对象使用。
- 灵活性：`ConditionObject` 提供了更多高级特性，如公平性控制、可中断等待等，这些都是通过 AQS 框架提供的。

### 4. `Condition` 和 `ConditionObject` 的作用

#### `Condition` 的作用：
- 提供了一种机制，允许线程在某些条件不满足时进入等待状态，直到其他线程通知它条件已经满足。
- 支持更细粒度的锁控制，允许不同的线程等待不同的条件变量。

#### `ConditionObject` 的作用：
- 作为 `Condition` 接口的一个具体实现，为基于 AQS 的锁提供条件变量的支持。
- 通过维护独立的条件队列，使得不同的条件变量可以独立地管理各自的等待线程，增强了并发控制的灵活性和效率。

### 示例代码

以下是一个简单的示例，展示了如何使用 `ReentrantLock` 和 `Condition` 来实现生产者-消费者模式：

```java
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

public class ProducerConsumerExample {
    private final Lock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    private final int[] buffer;
    private int count = 0;

    public ProducerConsumerExample(int capacity) {
        this.buffer = new int[capacity];
    }

    public void produce(int value) throws InterruptedException {
        lock.lock();
        try {
            while (count == buffer.length) {
                notFull.await(); // 等待缓冲区不满
            }
            buffer[count] = value;
            count++;
            notEmpty.signal(); // 通知消费者缓冲区非空
        } finally {
            lock.unlock();
        }
    }

    public int consume() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) {
                notEmpty.await(); // 等待缓冲区非空
            }
            count--;
            int value = buffer[count];
            notFull.signal(); // 通知生产者缓冲区未满
            return value;
        } finally {
            lock.unlock();
        }
    }
}
```

在这个例子中，`notFull` 和 `notEmpty` 都是 `Condition` 对象，它们分别用于控制生产者和消费者的等待行为。这些 `Condition` 对象实际上是由 `ReentrantLock` 的 `newCondition()` 方法返回的 `ConditionObject` 实例。

	}

int main(int argc, char argv) {
	netp::app _app;
	NRP<netp::thread> th1 = netp::make_ref<netp::thread>();
