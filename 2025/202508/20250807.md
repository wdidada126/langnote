```cpp
// cpu_100.cpp
#include <thread>
#include <vector>
#include <chrono>

int main() {
    // 获取 CPU 核心数
    unsigned int num_threads = std::thread::hardware_concurrency();

    // 创建与核心数相同的线程，每个线程空转
    std::vector<std::thread> threads;
    for (unsigned int i = 0; i < num_threads; ++i) {
        threads.emplace_back([]() {
            while (true) {
                // 空循环，尽可能占用 CPU
                // 注意：不要加 sleep 或 IO 输出
            }
        });
    }

    // 主线程等待所有工作线程（它们永远不会结束）
    for (auto& t : threads) {
        t.join();
    }

    return 0;
}
```

这和“运行 ClickHouse 查询导致 CPU 100%”是完全不同的两个场景。我们来深入分析这个编译阶段的 CPU 高占用问题，并对比你写的“空循环占满 CPU”的代码。


##  场景澄清：`cmake ../` 时 CPU 占用 100%？

先说结论：

>  `cmake` 命令本身不会导致 CPU 长时间 100%，它主要是配置生成，不是编译。
>
>  但你在执行 `cmake ../` 后紧接着执行 `make` 或 `ninja`，那才是真正的编译过程，会导致 CPU 长时间 100%。

###  很可能你混淆了两个命令：

| 命令 | 作用 | CPU 占用 |
|------|------|----------|
| `cmake ../` | 生成 Makefile 或 Ninja 构建文件 | ⚠️ 短时中等占用（几秒） |
| `make -j` 或 `ninja` | 真正编译源码 → 多进程编译 → CPU 100% | ✅ 长时间 100% |

> 所以：你看到的“编译 ClickHouse 时 CPU 100%”，其实是 `make` 或 `ninja` 在并行编译数千个 C++ 文件。

##  正确理解：为什么编译 ClickHouse 会占满 CPU？

ClickHouse 是一个用 C++ 编写的、极其复杂的 OLAP 数据库，代码量巨大（数十万行 C++ 代码），使用现代 C++（C++17/20）、模板、SIMD 指令等高级特性。

当你执行：

```bash
cmake ../
make -j$(nproc)
```

会发生什么？

### 1. `make -jN` 启动 N 个并行编译任务
- `-j$(nproc)` 表示使用所有 CPU 核心并行编译
- 每个 `.cpp` 文件由一个 `g++` 或 `clang++` 进程独立编译
- 每个编译器进程都会占用一个 CPU 核心 → 整体 CPU 100%

### 2. C++ 编译本身是 CPU 密集型操作
- 解析模板（尤其是 ClickHouse 大量使用模板）
- 优化代码（`-O2`/`-O3`）
- 生成目标文件（`.o`）
- 这些都极度依赖 CPU 计算能力

### 3. ClickHouse 代码特点加剧 CPU 占用
- 大量头文件包含（`#include`）
- 模板元编程（编译期计算）
- 内联函数、SIMD 向量化
- 所有这些都让编译器“很忙”

##  对比：你写的“CPU 100%”代码 vs 编译 ClickHouse

| 维度 | 你写的空循环代码 | 编译 ClickHouse（`make -j`） |
|------|------------------|-------------------------------|
| 是否做有效工作 | ❌ 没有，纯空转 | ✅ 有，生成可执行文件 |
| 是否多线程/多进程 | ✅ 多线程 | ✅ 多进程（`make -j` 并行） |
| CPU 占用原因 | 主动空循环 | 编译器解析、优化、生成代码 |
| 资源消耗 | CPU 高，内存低 | CPU 高，内存也高（GB 级） |
| 可持续时间 | 永久 | 几分钟到几十分钟（完成后自动结束） |
| 是否可接受 | ❌ 不合理（浪费电） | ✅ 合理（构建必要过程） |

##  如何降低编译时 CPU 占用？

如果你不想让机器“卡死”，可以：

```bash
# 减少并行任务数
make -j4        # 只用 4 个核心，而不是全部

# 或者限制 CPU 使用率（使用 nice + cpulimit）
nice -n 10 make -j$(nproc)
```

但这会延长编译时间。

这是一个非常好的问题！`nice` 和 `cpulimit` 是 Linux 系统中用于控制进程优先级和 CPU 使用率的两个重要工具。它们在编译大型项目（如 ClickHouse）时非常有用，可以避免编译过程“霸占”整个系统资源，导致机器卡顿。

我们来分别解释：


## 一、`nice` 命令：调整进程的调度优先级

###  作用
- `nice` 用来设置一个进程的 “谦让值”（niceness），影响它在 CPU 调度中的优先级。
- 值越高，优先级越低，越“谦让”其他进程。
- 取值范围：`-20`（最高优先级）到 `+19`（最低优先级）。
- 普通用户只能设置 `0 ~ 19`，`root` 可以设负值。

###  示例：
```bash
nice -n 10 make -j$(nproc)
```

- 表示以 `nice=10` 的优先级运行 `make` 编译。
- 意思是：“我这个编译任务不着急，如果系统有其他更重要的任务（比如你正在写文档、看视频），请优先让它们用 CPU。”

###  实际效果：
- 编译仍然会使用尽可能多的 CPU，但当其他高优先级任务需要 CPU 时，`make` 会更快地让出 CPU。
- 你的系统不会“卡死”，响应依然流畅。

---

## 二、`cpulimit` 工具：直接限制进程的CPU 使用率百分比

###  作用
- `cpulimit` 可以硬性限制一个进程的 CPU 使用率，比如限制为 50%。
- 它通过周期性地 暂停（stop）和恢复（continue） 目标进程来实现限制。

###  示例：
```bash
# 先安装 cpulimit（Ubuntu/Debian）
sudo apt install cpulimit

# 限制 make 最多使用 60% 的 CPU
cpulimit -l 60 -- make -j$(nproc)
```

- `-l 60` 表示限制 CPU 使用率不超过 60%
- 即使系统空闲，`make` 也不会超过这个上限

###  实际效果：
- 编译速度变慢，但系统始终有足够 CPU 资源留给其他程序。
- 非常适合在开发机上后台编译，不影响日常操作。

##  对比：`nice` vs `cpulimit`

| 特性 | `nice` | `cpulimit` |
|------|--------|-----------|
| 是否限制 CPU 百分比 | ❌ 否，只影响优先级 | ✅ 是，可设 50%、80% 等 |
| 何时生效 | 当系统忙碌时，低优先级进程让出 CPU | 无论系统是否空闲，都强制限制 |
| 性能影响 | 小，只在竞争时让出 | 大，直接限制最大使用率 |
| 适用场景 | 希望“不打扰”其他任务 | 希望“绝对不超”某个 CPU 上限 |
| 是否需要安装 | ✅ 系统自带 | ❌ 通常需手动安装 |


##  使用建议（编译 ClickHouse 时）

### 场景 1：你想编译快，但又不想卡顿
```bash
nice -n 10 make -j$(nproc)
```
>  推荐！既快又不影响系统响应。


### 场景 2：你只想用一半 CPU，后台慢慢编译
```bash
cpulimit -l 50 -- make -j$(nproc)
```
>  适合在笔记本上编译，避免风扇狂转、电池快速耗尽。


### 场景 3：结合使用（更精细控制）
```bash
nice -n 10 cpulimit -l 70 -- make -j$(nproc)
```
> 既降低优先级，又限制最大 CPU 使用率。
