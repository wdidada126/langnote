Redis Bitmap（位图）是一种基于String数据类型实现的特殊数据结构，它利用字符串底层的二进制位（bit）来存储和操作海量的二值状态数据。

简单来说，它不是一种独立的数据类型，而是将String当作一个由二进制位组成的数组来使用。

### 核心概念

- 二值状态：每一位（bit）只能存储 `0` 或 `1`，非常适合表示“是/否”、“开/关”、“已打卡/未打卡”这类状态。
- 高效存储：一个字节（byte）包含8个位（bit）。存储一个用户一年365天的签到状态，理论上只需要365个位，即约46字节，极其节省空间。
- 高效操作：Redis提供了直接对位进行操作的命令，时间复杂度通常是 O(1)，性能非常高，适合高并发场景。

### 在考勤打卡中的应用

在考勤系统中，Bitmap 的典型用法如下：
1.  Key设计：
    *   通常以用户ID为核心，结合年月来设计Key，例如：`attendance:uid:202508` 表示用户 `uid` 在2025年8月的打卡记录。

2.  Offset（偏移量）：
    *   代表日期。例如，8月1日对应 offset `0`，8月2日对应 offset `1`，以此类推，8月31日对应 offset `30`。

3.  核心操作命令：
    *   `SETBIT key offset 1`：当用户在某一天打卡时，执行此命令，将对应日期的位设置为 `1`。
        *   例如：`SETBIT attendance:uid:202508 15 1` 表示用户在8月16日（offset=15）打卡。
    *   `GETBIT key offset`：查询用户在某一天是否打卡。返回 `1` 表示已打卡，`0` 表示未打卡。
        *   例如：`GETBIT attendance:uid:202508 15` 查询8月16日的打卡状态。
    *   `BITCOUNT key`：统计用户在该Key所代表时间段内的总打卡天数。例如，统计整个8月份的打卡次数。

### 优势

- 空间效率极高：相比在数据库中为每次打卡都存储一条记录，Bitmap的存储空间可以节省几个数量级。
- 读写性能极快：位操作是计算机最底层的操作之一，`SETBIT` 和 `GETBIT` 的时间复杂度都是 O(1)。
- 支持批量统计：`BITCOUNT` 可以快速统计总天数，`BITOP` 命令可以进行复杂的位运算（如计算多个人的共同出勤日）。

总结：Redis Bitmap 就像一个超级紧凑的打卡日历，每个用户每月用一个非常小的“日历”（String），每一天用一个“格子”（bit）标记是否打卡，从而实现高效、低成本的考勤数据管理。

在 TiDB 中，可以通过监控指标来观察事务的开启与结束次数，这主要通过 `Transaction OPS` 指标来实现。

###  核心监控指标：`Transaction OPS`

| 指标名称 | 含义 | 单位 | 来源组件 |
|--------|------|------|--------|
| `Transaction OPS` | 每秒事务操作数（Operations Per Second） | 次/秒 | TiDB-Server |

该指标通常分为：
- 成功事务数
- 失败事务数

它反映了单位时间内事务的开启与提交/回滚（即结束） 的总次数。虽然没有单独的“事务开启次数”和“事务结束次数”计数器，但 `Transaction OPS` 实际上就是对事务生命周期的统计。

###  监控方式（基于 Prometheus + Grafana）

TiDB 默认通过 Prometheus 收集指标，并使用 Grafana 展示。你可以在以下面板中查看：

#### 1. Grafana 面板路径
> `TiDB` → `Transactions` → `Transaction OPS`

#### 2. 关键图表
- `Transaction OPS`：显示每秒事务总数（成功 + 失败）
- `Transaction Rollback OPS`：每秒回滚事务数
- `Transaction Retry Num`：事务重试次数（可间接反映冲突或失败）

###  指标详细说明

| 指标 | 说明 |
|------|------|
| `tidb_server_statement_total{type="Begin"}` | 事务开启（`BEGIN`）的总次数（可通过 Prometheus 查询） |
| `tidb_server_statement_total{type="Commit"}` | 提交事务次数 |
| `tidb_server_statement_total{type="Rollback"}` | 回滚事务次数 |
| `tidb_tikvclient_txn_cmd_total{type="commit"}` | TiKV 客户端提交事务的总次数 |
| `tidb_tikvclient_txn_cmd_total{type="rollback"}` | TiKV 客户端回滚事务的总次数 |

>  你可以通过 PromQL 查询这些指标来精确统计事务的开启和结束行为。

#### 示例 PromQL 查询：
```promql
# 每秒事务开启（BEGIN）次数
rate(ttidb_server_statement_total{type="Begin"}[1m])

# 每秒事务提交次数
rate(ttidb_server_statement_total{type="Commit"}[1m])

# 每秒事务回滚次数
rate(ttidb_server_statement_total{type="Rollback"}[1m])
```

###  事务生命周期监控建议

| 阶段 | 监控指标 | 说明 |
|------|--------|------|
| 开启 | `Begin OPS` | `BEGIN` 语句的执行频率 |
| 提交 | `Commit OPS` | 成功提交的事务数 |
| 回滚 | `Rollback OPS` | 显式或隐式回滚的事务数 |
| 重试 | `Transaction Retry Num` | 高重试可能表示锁冲突或网络问题 |
| 耗时 | `Transaction Duration` | 事务执行时间（99线等） |


###  总结

| 问题 | 解决方案 |
|------|----------|
| 如何监控事务开启次数？ | 查看 `tidb_server_statement_total{type="Begin"}` 的速率 |
| 如何监控事务结束次数？ | 查看 `Commit` 和 `Rollback` 的总和 |
| 使用什么工具？ | Prometheus + Grafana（TiDB Dashboard 内置） |
| Grafana 面板位置？ | `Transactions` 面板下的 `Transaction OPS` 图表 |


 建议：在生产环境中，持续监控 `Transaction OPS` 和 `Retry Num`，若发现事务数突增或重试频繁，可能预示着性能瓶颈或应用逻辑问题。

## ✅ 一、什么是 Transaction OPS？

- **Transaction OPS** = Transactions Per Second（每秒事务数）
- 表示 TiDB 集群每秒成功提交的事务数量。
- 是衡量数据库写入负载和吞吐能力的重要指标。

---

## ✅ 二、TiDB 中监控 Transaction OPS 的 4 种方式

### 方法 1️⃣：通过 **Grafana 监控面板**（推荐）

TiDB 集群通常部署时会集成 **Prometheus + Grafana** 监控系统。这是最直观、最常用的方式。

#### 🔍 操作步骤：

1. 打开 Grafana 监控页面（默认端口 `3000`）：
   ```
   http://<your-monitor-ip>:3000
   ```

2. 登录后选择 TiDB 的 Dashboard，推荐查看以下面板：
   - **"TiDB"** → **"Performance Overview"**
   - **"TiDB"** → **"Transaction"**

3. 查找关键图表：
   - ✅ **"Transactions Per Second"**（Transaction OPS）
   - ✅ "Statement OPS"（QPS）
   - ✅ "Aborted Transactions"（事务回滚数）

4. 可按 `instance`、`type`（如 pessimistic / optimistic）筛选。

#### 📌 示例图中指标含义：
- `tidb_executor_statement_total`（带 `type="Commit"`）可用于计算 TPS
- 实际图表已自动聚合为每秒事务数（OPS）

---

### 方法 2️⃣：通过 **Prometheus + PromQL 查询**

如果你熟悉 PromQL，可以直接查询 Prometheus。

#### 🔍 查询 Transaction OPS 的 PromQL：

```promql
rate(tidb_executor_statement_total{type="Commit"}[1m])
```

- `type="Commit"`：表示成功提交的事务
- `rate(...[1m])`：计算过去 1 分钟内的每秒事务数
- 单位：**transactions per second (TPS)**

#### 🔍 查看回滚事务数：
```promql
rate(tidb_executor_statement_total{type="Rollback"}[1m])
```

> 💡 提示：可在 Prometheus Web UI（默认 `9090` 端口）中测试该查询。

---

### 方法 3️⃣：通过 **TiDB 内部系统表**（SQL 查询）

TiDB 提供了 `METRICS_SCHEMA` 虚拟库，可以直接用 SQL 查询监控指标。

#### 🔍 查询 Transaction OPS 示例：

```sql
SELECT 
  time,
  value as tps
FROM METRICS_SCHEMA.tidb_executor_statement_total
WHERE 
  type = 'Commit'
  AND job = 'tidb'
  AND instance = 'your-tidb-instance:4000'
  AND time >= DATE_SUB(NOW(), INTERVAL 1 HOUR)
ORDER BY time DESC;
```

> ⚠️ 注意：
> - `METRICS_SCHEMA` 是 Prometheus 的 SQL 封装，数据是采样值。
> - `instance` 需替换为你的 TiDB 节点地址。
> - 实际使用中建议配合 `rate()` 函数或 Grafana 使用。

---

### 方法 4️⃣：通过 **tidb-dashboard**（TiDB v8.5.0 推荐）

TiDB v8.0+ 内置了 **TiDB Dashboard**，无需额外部署 Grafana 也能查看核心指标。

#### 🔍 操作步骤：

1. 访问 TiDB Dashboard：
   ```
   http://<any-pd-ip>:2379/dashboard
   ```
   （默认端口 `2379`，使用 PD 节点 IP）

2. 登录后进入：
   - **"Monitoring"** → **"Overview"** 或 **"Transaction"**

3. 查看：
   - ✅ **TPS（Transactions Per Second）**
   - ✅ 事务延迟（Transaction Duration）
   - ✅ 事务冲突数（Conflict Count）

> ✅ 优势：开箱即用，适合快速排查。

## ✅ 三、常见 Transaction OPS 异常分析

| 现象 | 可能原因 | 建议 |
|------|---------|------|
| TPS 突降为 0 | 应用中断、网络问题、OOM | 检查应用日志、TiDB 日志 |
| TPS 波动大 | 自动调度、大事务、锁冲突 | 查看 `Lock Panel`、慢查询 |
| TPS 高但 QPS 低 | 大事务批量写入 | 优化事务粒度 |
| 回滚率高（Rollback OPS 高） | 事务冲突、死锁 | 检查 `pessimistic_lock_wait_seconds`、`deadlock` 指标 |

## ✅ 四、自动化告警（可选）

你可以通过 Prometheus 配置告警规则，例如：

```yaml
- alert: HighTransactionRollbackRate
  expr: rate(tidb_executor_statement_total{type="Rollback"}[5m]) > 10
  for: 10m
  labels:
    severity: warning
  annotations:
    summary: "TiDB 事务回滚率过高"
```

## 🔍 为什么会报错？

### ❌ 错误理解：
你可能以为 `METRICS_SCHEMA.tidb_executor_statement_total` 是一个可以直接用客户端（如 Navicat、DBeaver、MySQL CLI）查询的“真实表”。

### ✅ 实际机制：
- `METRICS_SCHEMA` 是 TiDB 提供的一个**伪数据库**，它本身不存储数据。
- 它的作用是：**将 Prometheus 的监控数据通过 SQL 接口暴露出来**，但前提是：
  - 你连接的是 **TiDB Dashboard 的内部 SQL 接口**
  - 或使用了 **配套的监控组件（如 `tidb-lightning`, `tidb-dashboard`）**

> 🚫 **普通客户端直接连 TiDB Server 是无法查询 `METRICS_SCHEMA` 的！**

###  方法 4：通过 **TiDB 日志或 `SHOW STATS`**（临时排查）

虽然不能直接看 TPS，但可以间接判断：

```sql
-- 查看当前连接和状态
SHOW STATUS LIKE 'Com_commit';
SHOW STATUS LIKE 'Com_rollback';

-- 过一段时间再查一次，计算差值
```

然后手动计算：
```
TPS = (Com_commit_new - Com_commit_old) / 时间间隔（秒）
```

>  缺点：不精确，无法区分乐观/悲观事务，仅用于临时排查。
