Oracle分页查询，查询的结果有重复的，北京生产环境，

在Oracle分页查询中出现数据重复的问题，是一个常见但容易被忽视的技术细节。你提到“加上某字段排序就解决了”，这正是问题的关键所在。下面我将结合Oracle的机制，详细解释为什么会出现重复数据，以及为何加上排序字段（特别是唯一性字段）可以解决。

###  问题现象

在生产环境（如北京环境）执行分页查询时，例如：

```sql
SELECT * FROM (
    SELECT a.*, ROWNUM rn FROM (
        SELECT * FROM your_table -- 没有 ORDER BY
    ) a WHERE ROWNUM <= 20
) WHERE rn > 10;
```

可能会发现：
- 第一页显示记录 A、B、C……
- 第二页又出现了 A、B……（重复数据）
- 或者某些数据“跳过”未显示


###  原因分析：Oracle 的排序不稳定 + ROWNUM 机制

#### 1. 没有排序时，Oracle 不保证返回顺序
- Oracle 是按“数据块”读取数据的。 如果 SQL 中没有 `ORDER BY`，Oracle 会按数据物理存储顺序返回结果。 但这个顺序不是固定的，可能因数据插入、更新、索引重建、执行计划变化而改变。

#### 2. ROWNUM 是在排序前分配的
- `ROWNUM` 是在 `ORDER BY` 之前生成的（除非在子查询中显式排序）。
- 所以如果排序字段值不唯一（如 `create_time` 有很多相同时间），Oracle 的排序算法是不稳定的，即：
  > 对于相同排序键的多条记录，每次执行时它们的相对顺序可能不同。

#### 3. 分页依赖 ROWNUM，顺序一变，分页就乱
- 第一次查询：相同 `create_time` 的记录顺序是 A → B → C
- 第二次查询：顺序变成 B → A → C
- 那么 A 可能在第一页，也可能在第二页，造成重复或丢失

---

###  解决方案：使用唯一性排序字段

你提到“加上某字段排序就解决了”，真正起作用的是：

> 在 `ORDER BY` 中加入一个唯一性字段（如主键 `id`），确保排序结果完全确定。

####  正确写法示例：

```sql
SELECT * FROM (
    SELECT a.*, ROWNUM rn FROM (
        SELECT * FROM your_table
        ORDER BY create_time DESC, id DESC  -- 关键：create_time 不唯一，加上唯一主键 id
    ) a WHERE ROWNUM <= 20
) WHERE rn > 10;
```

####  为什么这样能解决？
- `create_time` 相同的记录，再按 `id` 排序，顺序就完全确定了。
- 每次查询结果顺序一致，ROWNUM 分配也一致。
- 分页结果稳定，不再出现重复或跳过。

---

###  其他可选的唯一性字段

如果主键不方便，也可以使用：
- `ROWID`（每行物理地址，唯一）：
  ```sql
  ORDER BY create_time, ROWID
  ```
- 唯一索引字段
- 业务上能保证唯一的组合字段

---

### ✅ 总结：Oracle 分页防重复的两个必要条件

| 条件 | 说明 |
|------|------|
| ✅ 必须有 `ORDER BY` | 否则顺序不固定，ROWNUM 分配混乱 |
| ✅ 排序字段必须能保证全局唯一顺序 | 如果排序字段不唯一，必须追加一个唯一字段（如主键） |

---

### 📌 生产建议（北京环境适用）

1. 所有分页查询必须带排序，即使是“默认顺序”也要显式指定。
2. 避免仅按时间、状态等非唯一字段排序。
3. 推荐格式：
   ```sql
   ORDER BY biz_date DESC, id DESC
   ```
4. 前端分页传参时，后端必须校验排序字段合法性，防止注入。

---

### 🧪 验证方法

你可以用以下方式验证是否解决：
- 多次执行同一页查询，看是否返回相同数据。
- 使用 `ORDER BY` 前后对比 `ROWNUM` 分配是否一致。

---

✅ 结论：你在北京生产环境“加上某字段排序就解决”，本质是通过引入唯一性排序字段，解决了 Oracle 排序不稳定性导致的分页重复问题。这是最佳实践，建议在所有分页场景中强制遵循。

### 一句话总结

> 安装 `ccache` 后，只要你的构建系统（如 CMake, Ninja, Make）调用了 `gcc`/`g++`/`clang`/`clang++`，ccache 通常会自动拦截并缓存编译结果。  
> 对于 ClickHouse 和 AOSP，这是开箱即用的。

## 🛠 一、ccache 是如何工作的？

`ccache` 的原理是 “拦截编译器调用”：

1.  当构建系统（如 `make`）要运行 `g++` 编译一个 `.cpp` 文件时。
2.  `ccache` 会“假装”自己是 `g++`（通过符号链接或 PATH 优先级）。
3.  `ccache` 计算本次编译的 缓存键（Cache Key），包括：
    - 源文件内容
    - 编译器命令行参数（`-I`, `-D`, `-O2` 等）
    - 编译器版本
    - 目标文件名
4.  如果缓存命中，`ccache` 直接输出之前编译好的 `.o` 文件，跳过实际编译。
5.  如果未命中，`ccache` 调用真正的 `g++` 编译，并将结果存入缓存。

---

## 🐼 二、编译 ClickHouse：ccache 开箱即用

ClickHouse 使用 CMake + Ninja 构建。

### ✅ 如何启用 ccache？

1.  安装 ccache（Ubuntu/Debian）：
    ```bash
    sudo apt-get install ccache
    ```

2.  确保 `ccache` 在 `PATH` 中且优先级高（通常安装后自动完成）：
    ```bash
    which ccache  # 应该输出 /usr/bin/ccache
    ```

3.  正常编译即可：
    ```bash
    mkdir build && cd build
    cmake .. -DCMAKE_C_COMPILER=clang-14 -DCMAKE_CXX_COMPILER=clang-14
    ninja
    ```

### ✅ 为什么能自动工作？

- CMake 在生成 `build.ninja` 时，会查找 `CC` 和 `CXX` 环境变量或命令行参数指定的编译器。
- 如果你的系统中 `gcc`/`g++`/`clang`/`clang++` 是 `ccache` 的符号链接（或 `ccache` 在 `PATH` 前面），CMake 找到的就是 `ccache`。
- Ninja 执行时调用 `clang++`，实际上执行的是 `ccache clang++`，缓存自动生效。

### 🔍 验证是否启用：

```bash
# 查看 ccache 统计
ccache -s

# 输出示例：
#  cache hit (direct)               150
#  cache hit (preprocessed)          20
#  cache miss                       300
#  ...
```

如果 `cache hit` 数字在增长，说明缓存工作正常。

## 📱 三、编译 AOSP：ccache 也是默认支持

AOSP（Android Open Source Project）构建系统也原生支持并推荐使用 ccache。

### ✅ 如何启用 ccache？

1.  安装 ccache：
    ```bash
    sudo apt-get install ccache
    ```

2.  （可选）设置 ccache 大小：
    ```bash
    ccache -M 50G  # 设置缓存最大 50GB
    ```

3.  在编译前设置环境变量（推荐）：
    ```bash
    export USE_CCACHE=1
    export CCACHE_EXEC=/usr/bin/ccache  # 指定路径
    ```

4.  初始化环境并编译：
    ```bash
    source build/envsetup.sh
    lunch aosp_arm64-userdebug
    make -j32
    ```

### ✅ 为什么能自动工作？

- AOSP 的构建脚本（`build/envsetup.sh`）会检查 `USE_CCACHE` 环境变量。
- 如果启用，它会自动将 `ccache` 注入到编译命令中，确保所有 `gcc`/`g++` 调用都经过 `ccache`。

### 🔍 验证是否启用：

```bash
# 查看 ccache 统计
prebuilts/misc/linux-x86/ccache/ccache -s
# 或者
ccache -s
```

AOSP 构建过程中也会打印类似 `ccache: enabled` 的信息。

---

## ⚠ 四、注意事项（重要！）

虽然“安装即用”，但以下几点能确保最佳效果：

| 问题 | 说明 |
|------|------|
| 1. 编译器路径 | 确保 `ccache` 在 `PATH` 中优先于 `gcc`/`clang`。可以用 `which gcc` 看是否指向 `ccache`。 |
| 2. 缓存大小 | 默认缓存可能较小（如 5GB）。建议设置更大：`ccache -M 20G` 或 `50G`。 |
| 3. 编译器一致性 | 如果你切换了编译器（如 `gcc-9` → `gcc-11`），缓存会失效（因为编译器版本是缓存键的一部分）。 |
| 4. 构建目录 | 不同的构建目录（如 `build-debug`, `build-release`）会有独立的缓存键（因为 `-O2` vs `-O0` 不同）。 |
| 5. 清理缓存 | 定期清理：`ccache -C`（清空），`ccache -s`（查看状态）。 |
| 6. 分布式编译 | `ccache` 支持 `ccache-sloccache` 实现多台机器共享缓存，极大加速团队编译。 |

## 📊 五、ccache 对编译速度的提升

| 场景 | 速度提升 |
|------|----------|
| 首次编译 | 无提升（甚至略慢，因计算哈希） |
| 修改少量文件后重新编译 | ⚡ 5-10 倍加速（90%+ 文件缓存命中） |
| 切换分支后编译 | ⚡ 显著加速（公共文件无需重编） |
| CI/CD 流水线 | ⚡ 大幅提升构建速度（配合缓存卷） |

| 项目 | ccache 是否自动启用？ | 关键步骤 |
|------|----------------------|----------|
| ClickHouse | ✅ 是 | 安装 `ccache`，正常 `cmake + ninja` |
| AOSP | ✅ 是 | 安装 `ccache`，设置 `USE_CCACHE=1`，然后 `make` |

Redis Bitmap（位图）是一种基于 String 数据类型实现的特殊数据结构，它利用字符串底层的二进制位（bit）来存储和操作海量的二值状态数据。

简单来说，它不是一种独立的数据类型，而是将String当作一个由二进制位组成的数组来使用。

### 核心概念

- 二值状态：每一位（bit）只能存储 `0` 或 `1`，非常适合表示“是/否”、“开/关”、“已打卡/未打卡”这类状态。
- 高效存储：一个字节（byte）包含8个位（bit）。存储一个用户一年365天的签到状态，理论上只需要365个位，即约46字节，极其节省空间。
- 高效操作：Redis提供了直接对位进行操作的命令，时间复杂度通常是 O(1)，性能非常高，适合高并发场景。

### 在考勤打卡中的应用

在考勤系统中，Bitmap 的典型用法如下：

1.  Key设计：
    *   通常以用户ID为核心，结合年月来设计Key，例如：`attendance:uid:202508` 表示用户 `uid` 在2025年8月的打卡记录。

2.  Offset（偏移量）：
    *   代表日期。例如，8月1日对应 offset `0`，8月2日对应 offset `1`，以此类推，8月31日对应 offset `30`。

3.  核心操作命令：
    *   `SETBIT key offset 1`：当用户在某一天打卡时，执行此命令，将对应日期的位设置为 `1`。
        *   例如：`SETBIT attendance:uid:202508 15 1` 表示用户在8月16日（offset=15）打卡。
    *   `GETBIT key offset`：查询用户在某一天是否打卡。返回 `1` 表示已打卡，`0` 表示未打卡。
        *   例如：`GETBIT attendance:uid:202508 15` 查询8月16日的打卡状态。
    *   `BITCOUNT key`：统计用户在该Key所代表时间段内的总打卡天数。例如，统计整个8月份的打卡次数。

### 优势

- 空间效率极高：相比在数据库中为每次打卡都存储一条记录，Bitmap的存储空间可以节省几个数量级。
- 读写性能极快：位操作是计算机最底层的操作之一，`SETBIT` 和 `GETBIT` 的时间复杂度都是 O(1)。
- 支持批量统计：`BITCOUNT` 可以快速统计总天数，`BITOP` 命令可以进行复杂的位运算（如计算多个人的共同出勤日）。

总结：Redis Bitmap 就像一个超级紧凑的打卡日历，每个用户每月用一个非常小的“日历”（String），每一天用一个“格子”（bit）标记是否打卡，从而实现高效、低成本的考勤数据管理。

在 TiDB 中，可以通过监控指标来观察事务的开启与结束次数，这主要通过 `Transaction OPS` 指标来实现。

###  核心监控指标：`Transaction OPS`

| 指标名称 | 含义 | 单位 | 来源组件 |
|--------|------|------|--------|
| `Transaction OPS` | 每秒事务操作数（Operations Per Second） | 次/秒 | TiDB-Server |

该指标通常分为：
- 成功事务数
- 失败事务数

它反映了单位时间内事务的开启与提交/回滚（即结束） 的总次数。虽然没有单独的“事务开启次数”和“事务结束次数”计数器，但 `Transaction OPS` 实际上就是对事务生命周期的统计。

###  监控方式（基于 Prometheus + Grafana）

TiDB 默认通过 Prometheus 收集指标，并使用 Grafana 展示。你可以在以下面板中查看：

#### 1. Grafana 面板路径
> `TiDB` → `Transactions` → `Transaction OPS`

#### 2. 关键图表
- `Transaction OPS`：显示每秒事务总数（成功 + 失败）
- `Transaction Rollback OPS`：每秒回滚事务数
- `Transaction Retry Num`：事务重试次数（可间接反映冲突或失败）

###  指标详细说明

| 指标 | 说明 |
|------|------|
| `tidb_server_statement_total{type="Begin"}` | 事务开启（`BEGIN`）的总次数（可通过 Prometheus 查询） |
| `tidb_server_statement_total{type="Commit"}` | 提交事务次数 |
| `tidb_server_statement_total{type="Rollback"}` | 回滚事务次数 |
| `tidb_tikvclient_txn_cmd_total{type="commit"}` | TiKV 客户端提交事务的总次数 |
| `tidb_tikvclient_txn_cmd_total{type="rollback"}` | TiKV 客户端回滚事务的总次数 |

>  你可以通过 PromQL 查询这些指标来精确统计事务的开启和结束行为。

#### 示例 PromQL 查询：
```promql
# 每秒事务开启（BEGIN）次数
rate(ttidb_server_statement_total{type="Begin"}[1m])

# 每秒事务提交次数
rate(ttidb_server_statement_total{type="Commit"}[1m])

# 每秒事务回滚次数
rate(ttidb_server_statement_total{type="Rollback"}[1m])
```

###  事务生命周期监控建议

| 阶段 | 监控指标 | 说明 |
|------|--------|------|
| 开启 | `Begin OPS` | `BEGIN` 语句的执行频率 |
| 提交 | `Commit OPS` | 成功提交的事务数 |
| 回滚 | `Rollback OPS` | 显式或隐式回滚的事务数 |
| 重试 | `Transaction Retry Num` | 高重试可能表示锁冲突或网络问题 |
| 耗时 | `Transaction Duration` | 事务执行时间（99线等） |


###  总结

| 问题 | 解决方案 |
|------|----------|
| 如何监控事务开启次数？ | 查看 `tidb_server_statement_total{type="Begin"}` 的速率 |
| 如何监控事务结束次数？ | 查看 `Commit` 和 `Rollback` 的总和 |
| 使用什么工具？ | Prometheus + Grafana（TiDB Dashboard 内置） |
| Grafana 面板位置？ | `Transactions` 面板下的 `Transaction OPS` 图表 |

### 方法 2️⃣：通过 Prometheus + PromQL 查询

如果你熟悉 PromQL，可以直接查询 Prometheus。

#### 🔍 查询 Transaction OPS 的 PromQL：

```promql
rate(tidb_executor_statement_total{type="Commit"}[1m])
```

- `type="Commit"`：表示成功提交的事务
- `rate(...[1m])`：计算过去 1 分钟内的每秒事务数
- 单位：transactions per second (TPS)

#### 🔍 查看回滚事务数：
```promql
rate(tidb_executor_statement_total{type="Rollback"}[1m])
```

> 💡 提示：可在 Prometheus Web UI（默认 `9090` 端口）中测试该查询。

---

### 方法 3️⃣：通过 TiDB 内部系统表（SQL 查询）

TiDB 提供了 `METRICS_SCHEMA` 虚拟库，可以直接用 SQL 查询监控指标。

#### 🔍 查询 Transaction OPS 示例：

```sql
SELECT 
  time,
  value as tps
FROM METRICS_SCHEMA.tidb_executor_statement_total
WHERE 
  type = 'Commit'
  AND job = 'tidb'
  AND instance = 'your-tidb-instance:4000'
  AND time >= DATE_SUB(NOW(), INTERVAL 1 HOUR)
ORDER BY time DESC;
```

> ⚠️ 注意：
> - `METRICS_SCHEMA` 是 Prometheus 的 SQL 封装，数据是采样值。
> - `instance` 需替换为你的 TiDB 节点地址。
> - 实际使用中建议配合 `rate()` 函数或 Grafana 使用。

## ✅ 三、常见 Transaction OPS 异常分析

| 现象 | 可能原因 | 建议 |
|------|---------|------|
| TPS 突降为 0 | 应用中断、网络问题、OOM | 检查应用日志、TiDB 日志 |
| TPS 波动大 | 自动调度、大事务、锁冲突 | 查看 `Lock Panel`、慢查询 |
| TPS 高但 QPS 低 | 大事务批量写入 | 优化事务粒度 |
| 回滚率高（Rollback OPS 高） | 事务冲突、死锁 | 检查 `pessimistic_lock_wait_seconds`、`deadlock` 指标 |
