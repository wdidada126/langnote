## 编译原理核心概念解析  
Parser → 语法树 (AST) → 逻辑算子树 (Logical Plan) → 物理算子树 (Physical Plan)  

### 一、整体流程（以 SQL 为例）

```
SQL 文本
   ↓  (Lexer)
Token 流
   ↓  (Parser)
抽象语法树 (AST)                     ← 语法层
   ↓  (Semantic Analysis / Name Resolution)
逻辑算子树 (Logical Plan)            ← 代数层（关系代数）
   ↓  (Optimizer)
物理算子树 (Physical Plan)           ← 执行层（具体算法+访问路径）
   ↓  (Code Generator / Interpreter)
执行引擎 (Iterator / Volcano Model)
```

## 二、每层结构详解

| 层级 | 名称 | 作用 | 典型节点（C++ 类名示例） | 关键属性 |
||||--|-|
| 1 | AST | 保留原始 SQL 结构，不关心语义 | `SelectStmt`, `Expr`, `TableRef` | `std::vector<Expr*> proj`, `TableRef* from` |
| 2 | Logical Plan | 关系代数表达，与实现无关 | `LogicalProject`, `LogicalFilter`, `LogicalJoin` | `Schema output_schema`, `std::vector<Expr*> exprs` |
| 3 | Physical Plan | 具体执行算法 + 访问路径 | `PhysicalProject`, `NestedLoopJoin`, `HashJoin`, `IndexScan` | `Operator* child`, `IndexMeta* index`, `Chunk* buffer` |



## 三、节点结构示例（MiniOB / OceanBase 风格）

### 1. 抽象基类（所有节点共用）

```cpp
class PlanNode {
public:
  virtual ~PlanNode() = default;
  virtual RC prepare() = 0;                     // 推导 schema、打开资源
  virtual RC next(Chunk &chunk) = 0;            // Volcano 模型拉取
  virtual Schema *schema() const = 0;
};
```



### 2. 逻辑算子（Logical Plan）

```cpp
class LogicalProject : public PlanNode {
  std::vector<Expression*> projections_;   // 投影表达式
  std::unique_ptr<PlanNode> child_;
public:
  Schema *schema() const override { /* 依据 projections_ 构造 */ }
};
```

```cpp
class LogicalFilter : public PlanNode {
  Expression *predicate_;                  // WHERE 条件
  std::unique_ptr<PlanNode> child_;
};
```

```cpp
class LogicalJoin : public PlanNode {
  JoinType type_;                          // INNER / LEFT / ...
  Expression *on_condition_;
  std::unique_ptr<PlanNode> left_, right_;
};
```



### 3. 物理算子（Physical Plan）

| 物理算子 | 对应逻辑算子 | 关键实现点 |
|-|--||
| `TableScan` | `LogicalScan` | 顺序扫描 / 索引扫描 |
| `IndexScan` | `LogicalScan` | `BplusTree::scan(key_range)` |
| `NestedLoopJoin` | `LogicalJoin` | 双层循环 + 条件过滤 |
| `HashJoin` | `LogicalJoin` | `build_hash_table → probe` |
| `Sort` | `LogicalSort` | 外部归并（大内存时内部） |
| `Projection` | `LogicalProject` | 评估表达式、填充 Chunk |

```cpp
class IndexScanOperator : public PlanNode {
  Table       *table_;
  Index       *index_;
  const TupleCell *key_low_, *key_high_;   // 范围
  bool         inclusive_low_, inclusive_high_;
public:
  RC next(Chunk &chunk) override {
    return index_->scan(key_low_, key_high_, inclusive_low_, inclusive_high_, chunk);
  }
};
```



## 四、从 AST → Logical → Physical 的转换（伪代码）

```cpp
// 1. AST → Logical
LogicalPlan *SqlParser::build_logical_plan(SelectStmt *stmt) {
  auto scan   = new LogicalScan(stmt->from_table);
  auto filter = new LogicalFilter(stmt->where_expr, scan);
  auto proj   = new LogicalProject(stmt->select_exprs, filter);
  return proj;
}

// 2. Logical → Physical (Optimizer)
PhysicalPlan *Optimizer::optimize(LogicalPlan *log) {
  if (auto *join = dynamic_cast<LogicalJoin*>(log)) {
    if (can_use_hash_join(join)) {
      return new HashJoinOperator(join->left_, join->right_, join->on_);
    } else {
      return new NestedLoopJoinOperator(join->left_, join->right_, join->on_);
    }
  }
  // 递归处理子节点...
}
```



## 五、关键概念对比表

| 维度 | AST | Logical Plan | Physical Plan |
||--|--||
| 语义 | 语法结构 | 关系代数 | 具体算法 |
| 是否含索引 | No | No | Yes |
| 是否含表达式求值 | 原始字符串 | 抽象 Expression | 实际 EvalContext |
| 优化阶段 | 语义检查 | 规则/代价优化 | 物理实现选择 |
| 执行模型 | 不可执行 | 可代数等价变换 | Volcano pull-based |



## 六、MiniOB 实际目录结构（2024 复赛）

```
src/observer/
├── sql/parser/          → yacc + lexer → AST (SelectStmt, Expr)
├── sql/plan/            → LogicalPlan, LogicalProject, LogicalFilter
├── sql/executor/        → PhysicalPlan, TableScanOperator, IndexScanOperator
└── sql/optimizer/       → rewrite + cost-based → PhysicalPlan
```



## 七、一句话总结

> Parser 产出 AST（语法树） → 语义分析后转为 Logical Plan（关系代数树） → Optimizer 依据统计信息选择 Physical Plan（物理算子树），最终由 Volcano 模型拉取 Chunk 执行。



实战建议（MiniOB 调优）  
1. 先打印 Logical Plan（`PlanNode::to_string()`）看 `JOIN` 顺序。  
2. 再打印 Physical Plan 确认是否走 IndexScan 而不是 TableScan。  
3. 用 `EXPLAIN`（MiniOB 已实现）直观看到三层结构。

### 图数据库在风控领域应用场景

图数据库（Graph Database）是一种专为处理高度关联数据设计的数据库系统，通过节点（Node）、边（Edge）和属性（Property）表示实体及其关系，特别适合风控（Risk Control）场景中揭示隐藏模式和网络行为。传统关系型数据库（RDBMS）依赖多表JOIN查询，处理复杂关系时效率低下，而图数据库可实现毫秒级遍历（如Cypher或Gremlin查询语言），显著提升实时检测能力。根据2025年市场报告，图数据库已占金融风控系统的50%以上，减少虚假阳性率达92%，并支持GNN（Graph Neural Networks）集成AI分析。

以下基于金融风控核心场景整理应用，按场景分类。数据来源于Neo4j、TigerGraph、AWS Neptune等主流图数据库案例，以及PubMed和ScienceDirect研究。

#### 1. 欺诈检测（Fraud Detection）
图数据库通过多跳关系分析（如账户→交易→设备），发现异常网络模式，适用于信用卡欺诈、贷款欺诈和在线游戏欺诈。相比规则引擎，图技术可降低虚假阳性30%-50%。

| 应用子场景 | 具体实现 | 典型工具/案例 | 益处 |
|------------|----------|--------------|------|
| 信用卡/支付欺诈 | 检测循环交易（circular money movement）或共享设备网络，标记合成身份（synthetic identities）。 | Neo4j：实时遍历账户-交易图，识别 mule networks。 TigerGraph：多跳路径评分，处理42M/日交易。 | 响应时间<1s，减少损失$2.67/美元欺诈。 |
| 贷款/申请欺诈 | 分析申请人-担保人-设备关系，检测ghost brokers（假网站）。 | AWS Neptune：加载RDBMS数据，查询多层连接。 | 识别隐藏连接，提高准确率92%。 |
| 游戏/电商欺诈 | 追踪刷单环或假账户群。 | Aerospike Graph：时间图（temporal graph）分析注册-登录-购买行为。 | 减少$57.8B电商损失。 |

#### 2. 反洗钱（Anti-Money Laundering, AML）
图数据库擅长追踪资金路径（如多层转账网络），支持实时监控25+风险指标，处理$2万亿可疑交易。

| 应用子场景 | 具体实现 | 典型工具/案例 | 益处 |
|------------|----------|--------------|------|
| 资金清洗路径 | 构建交易图，检测结构化存款（structured deposits）和不一致文档。 | Neo4j：Cypher查询循环路径，集成ML模型。 NebulaGraph：知识图（knowledge graph）可视化异常。 | 处理速度提升100倍，监控$514B JPMorgan交易。 |
| 合规报告 | 社区检测（community detection）识别洗钱环。 | TigerGraph：GNN集成，减少调查时间。 | 合规效率提升，减少手动审查。 |

#### 3. 信用风险评估（Credit Risk Assessment）
通过关系网络评估借款人风险，如关联账户或共享担保。

| 应用子场景 | 具体实现 | 典型工具/案例 | 益处 |
|------------|----------|--------------|------|
| 信用评分 | 链接分析（link analysis）评估多账户风险。 | Graphable：账户-交易图，检测高风险实体。 NVIDIA GNN：节点嵌入（node embedding）预测。 | 准确率提升，减少默认率。 |
| 网络风险 | 检测共谋环（collusive rings）。 | Dataversity：实时图查询。 | 覆盖百万账户，实时警报。 |

#### 4. 网络安全风险（Cybersecurity Risk）
在风控中扩展到检测内部威胁或钓鱼网络。

| 应用子场景 | 具体实现 | 典型工具/案例 | 益处 |
|------------|----------|--------------|------|
| 内部威胁 | 行为图分析用户-设备-访问路径。 | ResearchGate：GNN-based检测。 | 实时风险评估，减少入侵。 |
| 钓鱼/APT | 关系网络追踪异常访问。 | ScienceDirect：Neo4j集成ML。 | 检测复杂攻击，提升安全。 |

#### 实施建议
- 主流图数据库：Neo4j（易用，Cypher语言）、TigerGraph（高性能，GSQL）、AWS Neptune（云托管）。
- 集成ML：结合GNN（如NVIDIA RAPIDS）提升预测准确率。
- 挑战与益处：初始建模复杂，但ROI高（减少$2T损失），2025年预计占风控50%。
