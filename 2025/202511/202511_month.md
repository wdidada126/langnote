您说得非常对！LLVM 的强大之处不仅在于其命令行工具，更在于其模块化的库设计，允许开发者将这些库集成到自己的工具中，实现静态分析、JIT编译、代码转换等高级功能。

您列出的包已经包含了核心的开发库。以下是更全面的 LLVM 20 相关开发库和工具包列表，可以根据您的具体需求进行选择安装。

1. 核心编译器与工具链库（您已列出大部分）

这些是进行底层编译器开发、静态分析或构建基于 Clang/LLVM 的工具所必需的。

•   llvm-20-dev: LLVM 核心库的头文件和静态库。

•   clang-20: Clang 编译器前端（可执行文件）。

•   libclang-20-dev: 官方 C 接口库。提供稳定的 C API，是与 Clang 交互最常用的库（例如用于语法高亮、代码补全等IDE功能）。

•   libclang-cpp20-dev: Clang C++ 接口库。提供更完整、更原生的 C++ API，功能比 libclang 更强大，但 API 稳定性可能稍差。

•   liblld-20-dev: LLD 链接器的开发库。

2. 其他重要的工具和库

•   lldb-20-dev: LLDB 调试器的开发库。如果你想将 LLDB 集成到自己的调试器或 IDE 中，需要这个包。

•   libc++-20-dev: LLVM 自己的 C++ 标准库实现（libc++）的开发文件。

•   libc++abi-20-dev: LLVM 的 C++ 标准库 ABI 库的开发文件。

•   libunwind-20-dev: 提供栈展开功能的库，通常与 libc++abi 配合使用。

•   libomp-20-dev: LLVM 的 OpenMP 运行时库。如果你要使用 Clang 编译 OpenMP 程序，需要这个。

•   polly-20-dev: 多面体优化框架。用于高级循环优化。

•   mlir-20-dev: 多级中间表示 框架的开发库。用于编译器领域特定优化和代码生成，是当前LLVM生态的重点方向。

•   clang-tools-20: 包含一系列基于 Clang 的工具，如 clangd（语言服务器）、clang-format（代码格式化）、clang-tidy（静态分析）等。这些工具本身是可执行文件，但它们也展示了如何使用 LLVM 库。

3. 相关工具包（非库，但极其有用）

•   llvm-20-tools: 包含 LLVM 的各种工具，如 opt（优化器）、llc（静态编译器）、lli（LLVM 解释器/JIT）等。

•   clang-format-20: 独立的代码格式化工具。

•   clang-tidy-20: 独立的静态分析工具。

•   clangd-20: 独立的语言服务器，为编辑器提供强大的代码补全、跳转等功能。

vcpkg install库，除了编译，还有各种patch，我现在在linux平台手动编译，如何寻找是否存在patch，如何应用patch？

这是一个非常专业且关键的问题。当您使用 vcpkg 时，它会自动处理补丁（patches）。但是，当您在 Linux 平台手动编译同一个库时，您需要自己查找并应用这些补丁，否则您可能会遇到 vcpkg 已经解决的环境、兼容性或编译错误。

这些补丁通常是为了解决跨平台兼容性或上游项目（upstream）的 Bug。

## 如何寻找 vcpkg 为特定库使用的 Patch

要确定 vcpkg 在 Linux 平台为某个库使用了哪些补丁，您需要查看 vcpkg 仓库中的端口文件 (Portfile)。

### 1、 找到目标库的 Portfile

假设您要手动编译的库是 `ffmpeg`。
1.  访问 vcpkg 官方 GitHub 仓库：
    `https://github.com/microsoft/vcpkg`
2.  导航到 Ports 目录：
    `ports/`
3.  找到目标库的目录：
    `ports/ffmpeg/` (假设库是 ffmpeg)
4.  定位核心文件：
      * `portfile.cmake`: 这是 vcpkg 告诉 CMake 如何构建库的主脚本。
      * `vcpkg.json`: 库的元数据和依赖信息。

### 2、 分析 Portfile 和 Patches 目录
在 `ports/ffmpeg/` 目录下，您会看到以下结构：

```
ffmpeg/
├── portfile.cmake  # 核心脚本
├── vcpkg.json
└── patches/        # 包含所有补丁文件的目录
    ├── 0001-fix-something-on-linux.patch
    ├── 0002-add-arm-support.patch
    └── ...
```

#### A. 查看 `portfile.cmake`

在 `portfile.cmake` 文件中，查找任何调用 `vcpkg_patchfile()` 或类似函数的代码段。这会明确列出 vcpkg 应用的所有补丁文件。

示例代码片段 (虚拟)：

```cmake
# ... 其他配置 ...

# vcpkg 负责应用补丁的命令
vcpkg_patchfile(
    SOURCE_PATH "${SOURCE_PATH}"
    PATCHES
        "${CMAKE_CURRENT_LIST_DIR}/patches/0001-fix-dependency-path.patch"
        "${CMAKE_CURRENT_LIST_DIR}/patches/0002-enable-neon-for-arm.patch"
)
```

#### B. 浏览 `patches/` 目录
直接进入 `patches/` 目录，阅读 `.patch` 文件的内容。文件的命名通常会提示该补丁解决的问题（例如：`0001-fix-linux-abi.patch`）。
## 如何在 Linux 手动编译时应用 Patch
找到所需的补丁文件（例如 `0001-fix-dependency-path.patch`）后，您需要在库的源码目录下使用 `patch` 工具来应用它。
### 1、 步骤：应用补丁
假设您已经将库的原始源码下载并解压到 `/path/to/source/`，并将补丁文件放在您的工作目录下。
① 切换到源码根目录：
这是至关重要的一步。您必须在 `patch` 命令期望的目录结构下运行它。

```bash
cd /path/to/source/
```

② 执行 `patch` 命令：
使用 `-p` 参数指定补丁文件中的路径剥离级别。对于 vcpkg 的补丁，通常是从源码根目录开始应用的，所以 `-p1` 是最常见的选项，表示剥离一个路径组件（通常是源码目录本身）。

```bash
# 假设补丁文件位于上一级目录
patch -p1 < /path/to/patches/0001-fix-dependency-path.patch
```

  * `-p1` (Strip Count): 告诉 `patch` 工具忽略补丁文件中路径的第一个目录名。
      * *示例：* 如果补丁文件中的路径是 `a/b/c.c`，`-p1` 会尝试将补丁应用到当前目录下的 `b/c.c`。
  * `<`: 通过标准输入将补丁文件内容传递给 `patch` 程序。

### 2、 验证和常见问题
#### A. 验证
如果应用成功，`patch` 命令不会有太多输出，通常会显示类似 `patching file <filename>` 的信息。
#### B. 撤销（可选）
如果您应用错了或想还原，可以使用 `-R` 选项：

```bash
patch -R -p1 < /path/to/patches/0001-fix-dependency-path.patch
```

#### C. 常见错误

1.  `can't find file to patch`：
      * 原因： `patch` 命令没有在当前目录下找到补丁文件引用的文件。
      * 解决： 检查您是否在正确的源码根目录运行命令，并调整 `-p` 的级别（尝试 `-p0`、`-p2` 等）。
2.  `patch failed` / `Fuzz`：
      * 原因： 补丁文件是针对特定版本的源码创建的，而您的源码版本不匹配，导致行号或代码内容不一致。
      * 解决： 确保您手动编译的源码版本与 vcpkg `portfile.cmake` 中指定的版本完全一致。
通过这种方式，您可以精确地复制 vcpkg 的构建环境，解决上游源码在 Linux 下可能存在的兼容性或构建问题。

OceanBase的MiniOB竞赛和TiDB社区都有面向高校学生的类似开源实践和学习项目。
这些项目都是为了让学生通过实践接触真实的数据库内核代码、学习分布式系统设计，并最终成为社区贡献者。
这里是对OceanBase MiniOB和TiDB类似项目的总结和对比：
## OceanBase MiniOB (微型数据库项目)
MiniOB 是一个竞赛驱动的数据库内核实践项目。
| 特点 | 描述 |
| :--- | :--- |
| 形式 | 竞赛 (Competition)。提供一个简化的MiniOB框架（通常是单机版），要求参赛者在限定时间内实现或优化核心功能（如SQL解析、事务、存储引擎）。 |
| 目标 | 数据库内核实现。通过动手实现MiniOB的关键模块，深入理解数据库的内部原理和工程细节。 |
| 侧重 | 工程实践、功能实现和性能调优。 |
| 产出 | 最终提交一个完整的、可运行的MiniOB数据库实例，并与他人进行性能评测。 |

## TiDB 社区的类似项目和参与方式
TiDB 社区提供的是一个持续性、社区驱动的贡献者培养体系，而非单一的竞赛。最类似 MiniOB 这种动手实践精神的项目是Talent Plan和Hackathon。

### 1. Talent Plan (贡献者培养计划)
| 特点 | 描述 |
| :--- | :--- |
| 形式 | 系统化的学习路径 (Training Path)。Talent Plan 提供了从 TiDB 基础知识到具体组件源码阅读、再到完成第一个贡献的详细教程和任务清单。 |
| 目标 | 社区贡献入门。帮助新手（包括学生）降低参与门槛，找到第一个 `good first issue`，成为社区 Contributor。 |
| 侧重 | 社区协作、源码理解和基础 Bug 修复。 |
| 产出 | 完成第一个 Pull Request (PR) 并成功合并，成为 TiDB 社区的正式贡献者。 |

### 2. Hackathon (黑客马拉松)
| 特点 | 描述 |
| :--- | :--- |
| 形式 | 短期、高强度的创新活动。参赛者在 24-48 小时内基于 TiDB 源码或生态工具，完成一个具有创新性、可原型化的项目。 |
| 目标 | 原型创新和快速实现。鼓励参与者将新想法快速转化为 TiDB/TiKV/TiFlash 的原型功能。 |
| 侧重 | 创新、原型实现和团队合作。 |
| 产出 | 一个具备新功能或新工具的功能原型，优秀的成果会被社区考虑纳入主线开发。 |

### 3. Google Summer of Code (GSoC)
虽然 GSoC 是 Google 组织的项目，但 PingCAP/TiDB 社区通常作为参与组织。

| 特点 | 描述 |
| :--- | :--- |
| 形式 | 导师制暑期实习项目。学生在整个暑假期间，在 TiDB 社区导师的指导下，完成一个大型、预先定义的开源项目。 |
| 侧重 | 深入研究和复杂功能开发。 |
| 产出 | 完成一个具有高影响力的功能实现，并获得 Google 提供的奖金。 |

## 总结对比

| 特性 | OceanBase MiniOB | TiDB/PingCAP Talent Plan/Hackathon |
| :--- | :--- | :--- |
| 性质 | 竞赛（定时、淘汰制） | 持续性社区贡献与活动（非淘汰制） |
| 门槛 | 较高（需从零开始或基于框架实现） | 较低（从 `good first issue` 入门） |
