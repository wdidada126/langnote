实际上，AI Infra就是一个特定的计算机系统结构。
从计算机系统结构来看，AI Infra包括硬件层、操作系统层、系统支撑软件层。
顺便说一下，现在中文博客污染太严重了，把计算机系统结构和计算机体系结构搞混了。百度百科、CSDN、华为云社区等等。还有的把计算机体系结构和计算机系统结构拼凑在一起。
对于计算机系统结构来说：
在硬件层，一般不考虑处理器的内部细节，比如，处理器的缓存、流水线等等。同样地，对于GPU，也是不考虑GPU的内部细节。
在硬件层，计算机系统结构更多地考处理器、存储器的互连拓扑，这个互连拓扑，要考虑一些约束，同时在具体的场景中，还要考虑到一致性问题。
一般来说，计算机系统结构是不需要关心CPU内部的具体细节，也不关心GPU内部细节。特别是对于NVidia GPU来说，应该专门有一个岗位，GPU性能工程师或算子开发工程师。当然，如果是自研硬件，那么，需要从零构建算子库，或者极致性能优化，或者调试与Profiling，或者构建新抽象。但是，仍然是“一次性封装，长期免维护”。
AI Infra中的系统结构拓扑，是一个多层次的拓扑结构。包括GPU互连拓扑、内存层次拓扑、计算-存储耦合。互连方式（总线、Mesh、NVLink）、内存访问模型（UMA/NUMA/NORMA）、一致性协议、通信延迟与带宽特性等等，其实还是计算机系统结构的内容。AI Infra作为现代并行计算机的一种，其设计必须深刻理解并利用底层系统结构的拓扑特性。
对于这几个问题，在理论上来说，并不新鲜，在上个世纪80、90年代，被研究了许多遍，已经建立多个理论框架和数学模型。事实上，工业上的纯GPU集群的理论框架高度收敛于BSP+α-β 通信模型+拓扑感知路由，通信模型是α-β模型，互连拓扑，多机是胖树，单机内是全连接或部分连接。
就目前工业界的情况来看，纯GPU集群是主流。GPU+CPU的异构，几乎不用考虑。
那么，优化空间就是网络（有限，可调参数，如拥塞控制，但拓扑和带宽固定），存储I/O（有限，可优化文件系统、缓存，但磁盘/SSD 性能上限固定），操作系统（调度、内存管理、中断处理等可调），运行时系统（流调度、内存分配、通信后端等），通信库（拓扑感知通信，通信/计算重叠，融合通信，量化通信，自适应算法选择），框架层（算子融合、图优化、分布式策略），应用层（Batch size、流水线设计、混合精度等）等。

严格说，体系结构和微架构不是一个东西。
体系结构可以看作是程序员视角下的功能设计，而微架构可以看作是硬件工程师视角下的底层实现。
体系结构是对计算机系统的抽象描述，定义了程序员可见的部分，比如指令集、寄存器、内存模型、I/O机制等，主要面向编译器设计者、操作系统开发者、应用程序员：支持哪些指令（如加法、乘法、跳转等）？有多少寄存器、它们的用途？如何寻址内存？数据类型和格式（如整数、浮点数）？
微架构是对体系结构的具体实现方式，决定了如何在硬件中执行这些指令。主要面向芯片设计师、硬件工程师：是否使用流水线？几级？是否支持乱序执行、超标量执行？缓存的层级、大小、替换策略？分支预测、指令调度、功耗管理？
不过，现代处理器的性能瓶颈往往不在指令集，而在微架构层面，如乱序执行、分支预测、缓存一致性等。例如，ARM 架构下的 Cortex-A 系列与 Apple 的 M 系列芯片。随着制程工艺的进步，微架构设计成为提升性能和能效的主要手段。
它们之间的关系：体系结构仍然是设计的基础，微架构是在其之上的实现。因此，体系结构决定了“能做什么”，微架构决定了“怎么做得更好”。
所以，GPU、NPU、TPU的设计，既包括体系结构，也包括微架构。
体系结构是从程序员或系统设计者的视角出发，定义这些处理器的功能接口和编程模型：指令集设计（是否支持张量运算、矩阵乘法等）、数据类型支持（如 FP16、INT8、BF16）、内存访问模型（共享内存、统一内存、片上缓存）、并行计算模型（SIMD、SIMT、MIMD 等）、编程接口（如 CUDA、OpenCL、TensorFlow XLA）。GPU 的体系结构强调大规模并行计算和图形渲染管线、NPU 的体系结构强调神经网络层的加速（如卷积、激活、池化）、TPU 的体系结构专为张量处理优化，支持高吞吐量矩阵乘法。
微架构是从硬件工程师的视角出发，决定如何实现体系结构定义的功能：计算单元布局（如 ALU、MAC 单元、张量核心）、缓存层级和大小（L1/L2 cache、SRAM、eDRAM）、数据通路设计（总线宽度、带宽、DMA）、调度与控制逻辑（指令调度、流水线深度）、功耗与热设计（低功耗设计、动态电压频率调整）。NVIDIA Ampere GPU 微架构引入了更高效的张量核心和统一内存访问，Apple 的 NPU（Neural Engine）在 A 系列芯片中采用专用卷积加速器，Google TPU v4 微架构优化了片间互联和能效比。

很好的问题！基于图的 SSA IR 和 三地址码（TAC） 代表了编译器中间表示的两种不同设计哲学。让我来对比一下它们的关系和区别：

## 核心差异

### 1. 数据流表示方式
| 特性 | 三地址码 (TAC) | 基于图的 SSA (如 libfirm) |
|------|---------------|-------------------------|
| 结构 | 线性指令序列（像汇编） | 有向图（DAG/数据流图） |
| 数据依赖 | 通过变量名显式传递 | 通过图边直接连接操作 |
| 示例 | `t1 = a + b`<br>`t2 = t1 * c` | 节点`+`的输出直接连到节点`*`的输入 |

### 2. 静态单赋值 (SSA) 实现
```c
// TAC + 传统 SSA（需要 φ 函数）
x1 = a + b
if (...) goto L1
x2 = x1 * 2
goto L2
L1: x3 = x1 + 1
L2: y = x2 + x3  // 需要φ: x4 = φ(x2, x3)

// 图的 SSA（libfirm 风格，无需 φ 函数）
+节点(a,b) ──┐
              ├─ *节点 ──┐
常数2         │           ├─ +节点 ── y
控制流分歧    │           │
              └─ +节点 ──┘
常数1         │
              └───────────┘
```

## 关系与演进路径

### 从 TAC 到图 SSA 的演进
1. TAC：最简单的线性 IR，易于从语法树生成
2. TAC + SSA：在 TAC 上加 φ 函数，解决变量重定义问题
3. 图 SSA：根本上用数据流图替代变量名，用控制等价性消除 φ 函数需求

### libfirm 的创新
```c
// 传统 SSA 需要：
x1 = φ(x0, x2)  // 合并不同分支的值

// libfirm 用控制流分析：
if (cond) {
    block1: x2 = f(x0)
} else {
    block2: x1 = g(x0)
}
result = h(merge(x1, x2))  // 自动推断控制等价点
```

## 实际影响

### 优势对比
| 方面 | TAC | 图 SSA |
|------|-----|--------|
| 分析复杂度 | 简单，数据流分析较慢 | 复杂，但分析天然高效 |
| 优化效果 | 一般，需要多次传递 | 优秀，单次传递发现更多机会 |
| 内存使用 | 低 | 高（图结构开销） |
| 调试友好性 | 高（像汇编） | 低（抽象层次高） |

### 典型使用场景
- TAC：教学编译器、简单优化器、JIT（如 LuaJIT）
- 图 SSA：工业级编译器（如 LLVM 的早期版本灵感来源）、研究性编译器

## 总结
图 SSA 不是 TAC 的替代，而是更高层次的抽象。你可以把 TAC 看作"汇编语言"，图 SSA 看作"数据流图语言"。libfirm 选择图表示是为了让优化算法天然高效，而非手动分析线性指令序列。

一句话：TAC 让你写指令，图 SSA 让你画数据流图。
