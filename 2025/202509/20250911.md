你被问到的 偏向锁、轻量级锁 是 Java 中 `synchronized` 锁升级过程中的核心概念。下面我们来系统地梳理一下：
##  一、Java 中常见的锁类型分类（按用途/实现）

| 类型 | 说明 |
|------|------|
| 共享锁（Shared Lock） | 又叫读锁，多个线程可同时持有，用于读操作 |
| 排它锁（Exclusive Lock） | 又叫写锁，只能一个线程持有，用于写操作 |
| 读写锁（ReadWriteLock） | 包含读锁和写锁，如 `ReentrantReadWriteLock` |
| 乐观锁（Optimistic Lock） | 假设没有冲突，用 CAS + 版本号实现（如数据库 version 字段） |
| 悲观锁（Pessimistic Lock） | 假设有冲突，直接加锁（如 synchronized、ReentrantLock） |
| 表锁 / 行锁 | 数据库层面的概念，InnoDB 支持行锁 |
| 间隙锁（Gap Lock） | 锁住记录之间的“间隙”，防止幻读 |
| 临键锁（Next-Key Lock） | 行锁 + 间隙锁，InnoDB 默认使用的锁 |
| 意向锁（Intention Lock） | 表级锁，表示事务打算在某行上加锁 |

上面这些大多是 数据库或并发控制层面的锁。

而下面这些是 JVM 层面对 synchronized 的优化机制：

| 类型 | 所属机制 |
|------|---------|
| 偏向锁 | synchronized 锁升级 |
| 轻量级锁 | synchronized 锁升级 |
| 自旋锁 | 轻量级锁的辅助策略 |
| 重量级锁 | synchronized 最终形态（OS Mutex） |

##  二、`synchronized` 锁升级原理（重点！）
Java 的 `synchronized` 在 JVM 层面经历了从无锁 → 偏向 → 轻量级 → 重量级 的 锁升级过程，目的是为了 减少开销。

###  锁升级流程图

```
无锁状态
   ↓
偏向锁（只有一个线程使用）
   ↓
轻量级锁（短时间竞争，2个线程以内）
   ↓
重量级锁（长时间竞争，多线程激烈竞争）
```

>  锁只能升级，不能降级

### 1. 偏向锁（Biased Locking）

####  目的：
避免无竞争情况下的同步开销。如果 只有一个线程访问同步块，连 CAS 都不想做。

####  原理：
- 当一个线程第一次进入 `synchronized` 块时，JVM 会把对象头 Mark Word 中的 线程 ID 记录为当前线程。
- 下次同一个线程再进入时，只需检查线程 ID 是否是自己，是就直接执行 —— 无需任何同步操作。
- 大幅提升单线程重复进入同步块的性能。
####  触发条件：
- 只有一个线程访问同步代码块
- JDK 15+ 默认禁用偏向锁（可通过 `-XX:+UseBiasedLocking` 启用）
####  缺点：
- 一旦有第二个线程尝试获取锁，就要 撤销（revoke）偏向锁，开销较大。
### 2. 轻量级锁（Lightweight Locking）
####  目的：
在 低竞争场景 下，避免立即升级为操作系统级别的互斥锁（重量级锁），减少开销。
####  原理：
- 线程尝试通过 CAS 操作 将对象头的 Mark Word 复制到自己的栈帧中，并替换为指向锁记录的指针。
- 如果 CAS 成功，说明获取锁成功（轻量级锁状态）。
- 如果失败（说明有竞争），则膨胀为 重量级锁。
####  特点：
- 使用 CAS + 自旋尝试获取锁
- 不阻塞线程（忙等）
- 适用于 同步块执行很快 的场景
### 3. 自旋锁（Spinning Lock）
####  是轻量级锁的补充策略：
- 当线程竞争轻量级锁失败时，JVM 不马上挂起线程，而是让线程 空循环等待（自旋） 几次，看持有锁的线程是否很快释放。
- 避免线程频繁地 用户态 ↔ 内核态切换（上下文切换代价高）。
####  注意：
- 自旋次数有限（默认 10 次左右，JDK 6 可自适应）
- 多核 CPU 才有意义
### 4. 重量级锁（Heavyweight Locking）
####  最终形态：
- 当竞争激烈、自旋一定次数仍未获取锁时，JVM 将锁升级为 重量级锁。
- 此时依赖操作系统的 互斥量（Mutex） 实现，线程会进入阻塞状态。
- 性能耗费大，但适合长时间持有锁的场景。
####  特点：
- 依赖 OS 的 Mutex
- 线程阻塞/唤醒开销大
- 保证公平性
##  三、锁升级全过程详解（以对象锁为例）

假设有一个对象 `obj`，多个线程访问其 `synchronized(obj)` 块。

| 阶段 | 对象头状态 | 动作 |
|------|------------|------|
| 1. 初始状态 | 无锁（可偏向） | Mark Word 标记为“可偏向” |
| 2. 线程 A 第一次进入 | 偏向锁 | Mark Word 写入线程 A 的 ID |
| 3. 线程 A 再次进入 | 偏向锁 | 检查线程 ID 一致，直接进入 |
| 4. 线程 B 尝试进入 | 发生竞争 | 撤销偏向锁，升级为轻量级锁（CAS） |
| 5. 线程 A 持有，线程 B 自旋 | 轻量级锁 + 自旋 | B 循环等待 A 释放 |
| 6. 自旋失败或竞争加剧 | 升级为重量级锁 | 所有等待线程进入阻塞队列，由 OS 调度 |


##  四、Mark Word 结构（关键）

Java 对象头中的 Mark Word 存储了锁状态信息（32位或64位）：

| 锁状态 | Mark Word 内容 |
|--------|----------------|
| 无锁 | 哈希码、分代年龄、可偏向标志 |
| 偏向锁 | 线程 ID、Epoch、偏向时间戳 |
| 轻量级锁 | 指向栈中锁记录的指针 |
| 重量级锁 | 指向互斥量（Monitor）的指针 |

> Monitor 是 C++ 实现的对象监视器，每个 Java 对象都有一个关联的 Monitor。

##  五、如何回答面试题：“说说 synchronized 锁升级过程”

###  标准回答模板：

> `synchronized` 在 JVM 层面采用了锁升级机制来优化性能，分为四个阶段：
>
> 1. 偏向锁：当只有一个线程访问同步块时，JVM 会将锁偏向该线程，记录线程 ID，下次进入无需 CAS，直接执行。
> 2. 轻量级锁：当出现短暂竞争时，JVM 使用 CAS 将对象头替换为指向线程栈中锁记录的指针，避免阻塞。
> 3. 自旋锁：作为轻量级锁的辅助，线程空循环等待，避免上下文切换。
> 4. 重量级锁：当竞争激烈或自旋失败，锁膨胀为基于操作系统 Mutex 的重量级锁，线程阻塞。
>
> 锁只能升级不能降级。整个过程通过对象头的 Mark Word 来维护状态，目的是在无竞争或低竞争时减少开销。

##  六、总结表格

| 锁类型 | 适用场景 | 是否阻塞 | 实现方式 | 是否推荐 |
|--------|----------|-----------|------------|----------|
| 偏向锁 | 单线程重复进入 | 否 | 记录线程 ID | JDK 15+ 默认关闭 |
| 轻量级锁 | 低竞争、短临界区 | 否 | CAS + 栈帧锁记录 |  推荐 |
| 自旋锁 | 短暂等待 | 否（忙等） | 空循环 | 辅助策略 |
| 重量级锁 | 高竞争、长临界区 | 是 | OS Mutex | 开销大 |
