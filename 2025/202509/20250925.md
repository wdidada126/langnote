谓词下推（Predicate Pushdown）是数据库查询优化中的一个核心概念，其核心思想是：将查询中的过滤条件（谓词）尽可能地“下推”到数据访问的早期阶段，以减少中间数据量，从而提升查询性能。

## 一、什么是谓词下推？

### 1. 基本定义
- 谓词（Predicate）：SQL 中的 `WHERE` 子句或 `JOIN` 条件中的过滤表达式，如 `age > 30`, `status = 'active'`。
- 下推（Pushdown）：将这些过滤条件尽可能早地应用在数据读取或处理流程中，而不是等到所有数据都加载到内存后再过滤。

### 2. 核心目的
- 减少数据传输量：避免将大量无用数据从存储层或子查询中传递到上层处理。
- 减少内存和CPU开销：越早过滤，参与后续操作的数据越少。
- 利用索引和分区裁剪：下推后可能触发索引查找或分区剪枝。

---

## 二、谓词下推的典型场景

### 场景1：视图或子查询
```sql
SELECT * FROM (
    SELECT id, name, dept FROM employees
) v WHERE dept = 'IT';
```
- 如果 不支持下推：先全表扫描 `employees`，生成临时结果集，再过滤 `dept='IT'`。
- 如果 支持下推：优化器会将 `dept='IT'` 条件“下推”到子查询中，等价于：
  ```sql
  SELECT id, name, dept FROM employees WHERE dept = 'IT';
  ```
  → 显著减少中间结果集。

### 场景2：连接（JOIN）操作
```sql
SELECT * FROM A JOIN B ON A.id = B.id WHERE A.status = 'active';
```
- 理想情况下，`A.status = 'active'` 应该在扫描表 A 时就应用，而不是等到 JOIN 后再过滤。

### 场景3：分区表
```sql
SELECT * FROM sales WHERE sale_date = '2023-01-01';
```
- 如果 `sales` 是按 `sale_date` 分区的表，谓词下推可以实现 分区裁剪（Partition Pruning），只扫描相关分区。

## 三、主流数据库对谓词下推的支持情况

| 数据库 | 谓词下推支持程度 | 特点与限制 |
|--------|------------------|-----------|
| Oracle | 强大支持 | - CBO（Cost-Based Optimizer）自动进行谓词下推<br>- 支持视图合并（View Merging）、子查询展开<br>- 分区裁剪非常成熟<br>- 可通过 `/*+ PUSH_PRED */` 等 Hint 强制控制 |
| PostgreSQL | 支持良好 | - 8.4+ 版本开始支持子查询/视图的谓词下推<br>- 对简单视图自动下推<br>- 复杂视图（含聚合、DISTINCT）可能无法下推<br>- 扩展如 `postgres_fdw` 也支持远程谓词下推 |
| MySQL | 基础支持 | - 5.7+ 对派生表（Derived Table）有基本下推能力<br>- 8.0 增强了物化与下推优化<br>- 视图下推能力有限，尤其含 `UNION` 或聚合时 |
| SQL Server (MS SQL) | 强大支持 | - 查询优化器高度智能，自动进行谓词下推、视图展开<br>- 支持 Indexed Views<br>- 可通过执行计划查看是否下推 |
| DB2 | ✅ 成熟支持 | - 早期就支持复杂的查询重写<br>- 谓词下推、子查询转连接等优化成熟<br>- 支持 MDC（Multi-Dimensional Clustering）下的谓词优化 |
| TiDB | ✅ 高度支持 | - 基于 TiKV 分布式存储，谓词下推是性能关键<br>- 谓词尽可能下推到 TiKV 层（存储层）<br>- 支持表达式下推到 Coprocessor<br>- 大幅减少网络传输 |
| OceanBase | ✅ 高度支持 | - 分布式架构下，强调“计算下推”<br>- 谓词下推至分区层级（Partition Level）<br>- 支持在存储层（如 Macro Block）进行过滤<br>- 优化器可重写查询以实现下推 |

## 四、谓词下推的技术实现层次

谓词下推可以在多个层级发生：

| 层级 | 说明 |
|------|------|
| 1. 存储引擎层 | 如 TiDB 将谓词下推到 TiKV，OceanBase 下推到存储层，直接在 SSTable 或 Block 中过滤。 |
| 2. 分区层 | 利用分区键谓词进行分区裁剪（Partition Pruning），只扫描相关分区。 |
| 3. 表扫描层 | 在全表扫描或索引扫描时，尽早应用过滤条件。 |
| 4. 子查询/视图层 | 重写查询计划，将外层谓词合并到内层查询中。 |
| 5. JOIN 层 | 将过滤条件提前应用于 JOIN 的输入表。 |

> 最佳实践：越靠近数据源下推，效果越好。

---

## 五、如何判断谓词下推是否生效？

### 方法：查看执行计划（Execution Plan）

#### 示例（Oracle / PostgreSQL / MySQL）：
```sql
EXPLAIN SELECT * FROM (SELECT * FROM employees) v WHERE dept = 'IT';
```

- 如果执行计划中 `employees` 表的访问路径包含 `dept = 'IT'` 的过滤（如 `FILTER` 或 `ACCESS` 条件），说明下推成功。
- 如果子查询先物化（Materialize），再过滤，则未下推。

#### TiDB 示例：
```sql
EXPLAIN SELECT * FROM t1 WHERE a > 10;
```
- 查看 `cop[tikv]` 算子是否包含 `a > 10`，如果是，则谓词已下推到 TiKV。

## 六、限制与不能下推的情况

尽管大多数现代数据库都支持谓词下推，但以下情况可能无法下推：

| 情况 | 说明 |
|------|------|
| 含聚合的视图 | 如 `CREATE VIEW v AS SELECT dept, COUNT(*) FROM emp GROUP BY dept`，外层加 `WHERE COUNT > 10` 无法下推。 |
| 含 DISTINCT / GROUP BY | 可能阻止谓词下推，除非优化器能证明等价性。 |
| 含窗口函数 | 如 `ROW_NUMBER()`，通常不能将外层谓词下推到窗口函数内部。 |
| UNION / EXCEPT | 复杂集合操作可能限制下推。 |
| 复杂表达式或函数 | 如 `WHERE UPPER(name) = 'JOHN'`，若索引未建函数索引，可能无法有效下推。 |

## 七、总结

| 要点 | 说明 |
|------|------|
| ✅ 核心价值 | 减少数据流动、提升查询性能 |
| ✅ 实现方式 | 查询重写、优化器规则、执行计划调整 |
| ✅ 主流数据库 | Oracle、PostgreSQL、SQL Server、DB2、TiDB、OceanBase 均支持 |
| ✅ 分布式数据库更依赖 | TiDB、OceanBase 等靠谓词下推减少网络开销 |
| ⚠️ 注意限制 | 聚合、DISTINCT、复杂视图可能阻止下推 |
| 🔍 验证方法 | 使用 `EXPLAIN` 查看执行计划 |

## 八、建议

1. 编写 SQL 时尽量将过滤条件靠近数据源。
2. 避免不必要的嵌套视图或子查询包装。
3. 使用执行计划工具验证谓词是否下推。
4. 在分布式数据库中，关注谓词是否下推到存储层（如 TiKV、OceanBase 存储节点）。

谓词下推虽是透明的优化技术，但理解其原理有助于写出更高效的 SQL，并更好地解读执行计划。
