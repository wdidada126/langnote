一、密码验证：为何只能单向加密

密码的核心需求是 验证，而非解密。因此必须使用不可逆的加密，即哈希（Hash）。

1. 正确做法：使用强哈希算法
// 示例：使用 BCrypt 算法（目前公认最安全的密码哈希算法之一）
public class PasswordService {
    
    // 注册或修改密码时：对明文密码进行哈希处理
    public String hashPassword(String plainTextPassword) {
        // BCrypt.gensalt() 会自动生成随机的盐值，并包含在最终的哈希字符串中
        return BCrypt.hashpw(plainTextPassword, BCrypt.gensalt(12)); // 12是成本因子，越高越安全但越慢
    }
    
    // 登录验证时：比较用户输入的密码和数据库存储的哈希值
    public boolean verifyPassword(String plainTextPassword, String storedHash) {
        try {
            return BCrypt.checkpw(plainTextPassword, storedHash);
        } catch (Exception e) {
            return false; // 比较失败，密码错误
        }
    }
}


2. 验证流程
•   存储阶段： 用户注册时，对密码明文进行哈希，将哈希值存入数据库。绝对不存储明文密码。

•   验证阶段： 用户登录时，系统对用户输入的密码再次进行相同的哈希运算，然后将得到的哈希值与数据库存储的哈希值进行比对。如果一致，则密码正确。

关键点：
•   加盐： 现代哈希算法（如 BCrypt）会自动加入随机“盐值”，即使两个用户密码相同，其哈希值也不同，有效防止彩虹表攻击。

•   不可逆： 从哈希值无法反推出原始密码。即使数据库泄露，攻击者也无法直接获得用户密码。

二、手机号/身份证号搜索：如何实现加密字段的查询

手机号和身份证号的核心需求是 精确匹配查询。但直接加密后，相同的明文每次加密都会得到不同的密文（由于IV的存在），导致无法直接使用 SQL 的 WHERE 语句进行查询。

这里有几种主流的解决方案：

方案一：可搜索加密 - 确定性加密（最常用）

对需要查询的字段，使用确定性加密。即相同的明文和密钥，总是产生相同的密文。
// 使用 AES-SIV 模式或简单的 AES-ECB（仅用于特定字段搜索，不推荐用于大量数据加密）
// 更常见的做法是使用固定的IV
public class SearchableEncryptor {
    
    public String encryptForSearch(String plainText, SecretKey key) throws Exception {
        Cipher cipher = Cipher.getInstance("AES/CBC/PKCS5Padding");
        // 使用固定的IV，或者从某个固定规则生成（例如，从密钥和固定字符串派生）
        IvParameterSpec iv = new IvParameterSpec(getFixedIVForKey(key));
        cipher.init(Cipher.ENCRYPT_MODE, key, iv);
        byte[] cipherText = cipher.doFinal(plainText.getBytes(StandardCharsets.UTF_8));
        return Base64.getEncoder().encodeToString(cipherText);
    }
    
    private byte[] getFixedIVForKey(SecretKey key) {
        // 例如，对密钥进行SHA-256哈希，取前16字节作为固定IV
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        byte[] hash = digest.digest(key.getEncoded());
        return Arrays.copyOf(hash, 16); // AES Block Size is 16 bytes
    }
}


搜索流程：
1.  当需要搜索手机号 13812345678 时，在应用程序层使用相同的密钥和固定IV对其进行加密，得到密文 C1。
2.  执行 SQL 查询：SELECT * FROM users WHERE phone_encrypted = 'C1'。

优缺点：
•   优点： 实现相对简单，查询效率高。

•   缺点： 安全性略低于随机IV的加密模式。如果攻击者知道加密方式是确定性的，他们可以通过“频率分析”或“已知明文攻击”来推测信息。必须严格保护密钥。

方案二：盲索引

存储明文数据的哈希值（或HMAC）作为“索引”，用于搜索，但实际数据用更强的加密方式存储。
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    -- 强加密存储，使用随机IV，安全性高
    phone_encrypted VARBINARY(256),
    phone_iv VARBINARY(16),
    -- 盲索引：用于快速搜索的哈希值
    phone_index CHAR(64), -- 存储 SHA-256 或 HMAC 的Hex值
    ...
);


操作流程：
1.  存储： 
    ◦   用强加密算法（如AES-GCM）加密手机号，存入 phone_encrypted。

    ◦   计算手机号的哈希值（如 SHA-256("13812345678")）或HMAC值，存入 phone_index。

2.  搜索：
    ◦   计算待搜索手机号的哈希值 H1。

    ◦   执行 SQL：SELECT * FROM users WHERE phone_index = 'H1'。

优缺点：
•   优点： 将搜索功能与数据加密解耦，加密数据部分可以使用最高安全级别的随机IV加密。哈希是单向的，索引本身不泄露明文。

•   缺点： 哈希冲突理论上存在（虽然概率极低）。无法支持模糊查询（如 LIKE '%138%'）。

方案三：应用层过滤（适用于数据量小的情况）

1.  将所有数据解密到应用层，在内存中进行筛选。
2.  缺点： 性能极差，完全不可用于生产环境的大量数据搜索。

方案四：使用专业数据库加密功能

一些现代数据库或安全产品提供了原生的可搜索加密功能。
•   MySQL Enterprise Edition： 透明数据加密（TDE）并结合应用程序管理密钥。

•   CipherTrust、Vault 等专业产品： 提供字段级加密和令牌化功能。

三、综合实践建议

对于金融级应用，推荐以下组合策略：

数据字段 存储方案 搜索方案 理由

密码 强哈希（BCrypt/Argon2） 不搜索 绝对安全，验证通过比对哈希值实现。

手机号/身份证号 强加密（AES-GCM等）+ 盲索引 通过盲索引搜索 在保证数据存储安全的前提下，提供高效的精确查询能力。盲索引比确定性加密更安全。

用户姓名 强加密 通常不提供搜索 或 应用层过滤 搜索需求不频繁，或数据量小可容忍性能。

示例表结构：
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    -- 认证信息（哈希）
    password_hash VARCHAR(255) NOT NULL,
    
    -- 敏感信息（强加密）
    id_card_encrypted VARBINARY(512) NOT NULL,
    id_card_iv VARBINARY(16) NOT NULL,
    phone_encrypted VARBINARY(256) NOT NULL,
    phone_iv VARBINARY(16) NOT NULL,
    
    -- 盲索引（用于搜索）
    phone_index CHAR(64) NOT NULL UNIQUE, -- SHA-256(phone)
    id_card_index CHAR(64) NOT NULL UNIQUE, -- SHA-256(id_card)
    
    -- 其他非敏感信息
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    INDEX `idx_phone_index` (phone_index),
    INDEX `idx_id_card_index` (id_card_index)
);


总结： 永远用哈希处理密码，用“盲索引”或“确定性加密”来解决加密后的精确查询问题，并根据安全等级要求优先选择“盲索引”。整个系统的核心是安全且隔离的密钥管理。
