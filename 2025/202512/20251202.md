Rust 编译器（rustc）深度依赖 LLVM 作为其后端代码生成器，几乎所有目标平台的机器码都是通过 LLVM 生成的。下面是 Rust 源代码（rust-lang/rust.git）实际使用到的 LLVM API 的最全、最准确清单（截至 2025 年 12 月，适用于 rustc 1.83+ 和 master 分支）：

| 模块/文件位置 | 使用的 LLVM C++ API（核心类/函数） | 用途说明 |
|---------------|-----------------------------------|--------|
| `compiler/rustc_codegen_llvm/` | `llvm::Module`, `llvm::Function`, `llvm::BasicBlock`, `llvm::Value`, `llvm::Type`, `llvm::IRBuilder<>`, `llvm::DIBuilder` | 构建 LLVM IR（Rust 的 MIR → LLVM IR） |
| | `llvm::TargetMachine`, `llvm::Target`, `llvm::TargetOptions` | 目标三元组解析、代码生成选项（relaxed SIMD、指令集等） |
| | `llvm::PassManagerBuilder`, `llvm::legacy::PassManager`, `llvm::legacy::FunctionPassManager` | 运行 LLVM 的优化 Pass（O0/O1/O2/O3/s/z） |
| | `llvm::orc::LLJIT`, `llvm::orc::ThreadSafeModule` | 新的 ORC JIT（rustc 自带的解释器、playground、incremental compilation） |
| `compiler/rustc_llvm/` | 所有 `llvm::*` C++ 类在 Rust 侧的薄 thin wrapper（通过 bindgen 生成） | 把 LLVM C++ API 暴露给 Rust 代码 |
| `src/llvm-project/llvm/include/llvm-c/` | 几乎不使用（只有极少数地方） | Rust 已经完全抛弃 LLVM C API，100% 用 C++ API |
| LTO（Link Time Optimization） | `llvm::lto::LTO`, `llvm::lto::Config` | `cargo build -Z thin-lto` / `full-lto` 时使用 |
| Codegen Backend | `llvm::MCStreamer`, `llvm::MCObjectWriter` | 生成 .o 文件（ELF/MachO/COFF/PE/Wasm） |
| Linker 集成 | 不直接调用 `lld::elf::link` 等 | rustc 自己调用系统链接器或 lld 可执行文件，不像 Zig 那样直接调用 LLD C++ API |
| WebAssembly 后端 | `llvm::wasm::link`（旧后端曾短暂使用，现已移除） | wasm32-unknown-unknown 现在 100% 用 Cranelift 或自研后端，LLVM 后端已废弃 |
| Debug Info | `llvm::DIBuilder`, `llvm::DICompileUnit`, `llvm::DIScope` | 生成 DWARF/GDB/CodeView 调试信息 |
| Profile-Guided Optimization | `llvm::SampleProfileLoader` | `-C profile-generate/use` |
| Sanitizers | `llvm::SanitizerOptions` | AddressSanitizer、LeakSanitizer、ThreadSanitizer |
| Exception Handling | `llvm::LandingPadInst` | Rust 的 panic 展开（DWARF EH 或 Win64 SEH） |
| Inline Assembly | `llvm::InlineAsm` | `asm!` 宏 |
| Atomic 指令 | `llvm::AtomicOrdering`, `llvm::AtomicRMWInst` | `std::sync::atomic` 的代码生成 |
| SIMD / Vector | `llvm::VectorType`, `llvm::Intrinsic::getDeclaration` | `std::arch`、portable-simd、target_feature |

### 关键结论（2025 年现状）

1. Rust 100% 使用 LLVM C++ API，通过 `rustc_llvm` 子模块里的 bindgen + 手写 wrapper。
2. 完全不使用 LLD 的 C++ API（`lld::elf::link`、`lld::coff::link` 等）  
   → Rust 调用的是 `ld.lld` 可执行文件（或系统默认链接器），不像 Zig 那样静态链接 liblld*.so。  
   所以你用 Ubuntu 的 `llvm-20-dev` 包（只有 .a，没有 .so）完全可以编译 Rust，不会出现 Zig 那种 undefined reference。
3. 最核心依赖的动态库只有两个：
   - `libLLVM-*.so`（大一统动态库，或一堆小的 .so）
   - `libclang-cpp.so`（极少数地方用到 clang 的 API，如 C 语言 FFI 解析）
4. Rust 自研后端正在快速取代 LLVM：
   - `wasm32-unknown-unknown`：默认已切换到 Cranelift（更快冷启动）
   - `aarch64-unknown-linux-gnu`：Cranelift 已成为 tier-2
   - `x86_64-unknown-linux-gnu`：Cranelift 正在测试中
   - 未来 3–5 年内，LLVM 可能只在需要最高优化（-O3/-Oz）和某些特殊目标时使用。

### 总结：Rust 到底依赖 LLVM 的哪些“共享库”？

| 动态库 | 是否必须 | 备注 |
|-------|---------|------|
| `libLLVM.so`（或 libLLVM-*.so） | 必须 | 99% 的 LLVM API 都在这里 |
| `liblld*.so`（COFF/ELF/Wasm） | 不需要 | Rust 不调用 LLD C++ API |
| `libclang-cpp.so` | 很少需要 | 只有解析 C 头文件时用到 |

所以你用 Ubuntu 的 `llvm-20-dev` 包（只有 .a）编译 Rust 完全没问题；只有 Zig、rust-analyzer、clangd 等少数项目才强制要求 `liblld*.so` 动态库。

一句话：Rust 是 LLVM 的“轻度用户”，Zig 才是“重度用户”。

这是一个 ANTLR4 的语法文件（.g4），定义了名为 Pred 的语法。让我详细解释这段代码的含义：
语法结构分析
assign
    : ID '=' v=INT {$v.int>0}? ';'
      {System.out.println("assign "+$ID.text+" to ");}
    ;

组成部分解析：
1. 规则定义：assign 是一个语法规则
2. 模式匹配：ID '=' v=INT ';'
   • ID：匹配一个标识符（如变量名）
   • '='：匹配等号字符
   • v=INT：匹配整数，并将匹配到的 INT 标记命名为 v
   • ';'：匹配分号

3. 语义谓词（Semantic Predicate）：{$v.int>0}?
   • 作用：运行时条件检查
   • 含义：只有当 v 对应的整数值大于 0 时，这个语法分支才有效
   • 位置：? 前面的布尔表达式为真时才继续解析

4. 动作代码（Action）：{System.out.println("assign "+$ID.text+" to ");}
   • 作用：在解析时执行的 Java 代码
   • 含义：打印赋值语句信息

实际匹配示例
有效输入：
x = 5;    // 通过，因为 5 > 0
y = 100;  // 通过，因为 100 > 0

无效输入：
x = 0;    // 失败，语义谓词 0>0 为 false
z = -3;   // 词法分析阶段就会失败，因为 INT 规则只匹配数字

完整的语法文件上下文
grammar Pred;
// 语法规则
assign
    : ID '=' v=INT {$v.int>0}? ';'  // 语义谓词：值必须>0
      {System.out.println("assign "+$ID.text+" to ");}  // 动作代码
    ;
// 词法规则
INT :   [0-9]+ ;     // 匹配一个或多个数字
ID  :   [a-zA-Z]+ ;  // 匹配一个或多个字母
WS  :   [ \t\r\n]+ -> skip ;  // 跳过空白字符

语义谓词的重要作用
语义谓词让语法分析不仅考虑语法结构，还考虑语义值。这在以下场景很有用：
1. 范围检查：如本例中的正数检查
2. 上下文相关语法：如变量必须先声明后使用
3. 类型检查：在语法分析阶段进行基本类型验证

这种机制大大增强了 ANTLR4 的表达能力，使得语法规则可以包含复杂的运行时条件。
这是一个 ANTLR4 语法文件，定义了一个名为 Vec 的语法，专门用于解析包含特定数量元素的向量。让我详细解释：

语法结构分析

1. 主规则 vec4
vec4:   '[' ints[4] ']' ;
• 匹配格式：[元素1, 元素2, 元素3, 元素4]
• ints[4]：调用 ints 规则，并传入参数 max=4

2. 参数化规则 ints[int max]
ints[int max]           // 接受一个max参数
locals [int i=1]        // 定义局部变量i，初始值为1
    :   INT ( ',' {$i++;} {$i<=$max}? INT )* ;

规则详解
ints[int max] 规则分解：
1. INT - 匹配第一个整数
2. ( ',' {$i++;} {$i<=$max}? INT )* - 匹配0个或多个后续整数
   • ',' - 匹配逗号
   • {$i++;} - 动作：局部变量i自增1
   • {$i<=$max}? - 语义谓词：只有i≤max时才继续解析
   • INT - 匹配整数

执行流程示例

对于输入：[10, 20, 30, 40]

1. vec4 匹配 [ 和 ]
2. 调用 ints[4]（max=4）：
   • 匹配 10（i=1）
   • 匹配 , → i++ → i=2 → 2≤4? ✓ → 匹配 20
   • 匹配 , → i++ → i=3 → 3≤4? ✓ → 匹配 30  
   • 匹配 , → i++ → i=4 → 4≤4? ✓ → 匹配 40
   • 匹配 , → i++ → i=5 → 5≤4? ✗ → 停止匹配

匹配示例
有效输入：

[1]                    # 调用 ints[1]

从 .g4 到 Java 代码的转换

原始语法规则：

ints[int max]
locals [int i=1]
    :   INT ( ',' {$i++;} {$i<=$max}?<fail={"exceeded max "+$max}> INT )* ;


生成的 Java 代码逻辑：

public class VecMsgParser extends Parser {
    public static class IntsContext extends ParserRuleContext {
        public int max;  // 参数
        public int i = 1; // locals 变量
    }
    
    public IntsContext ints(int max) {
        IntsContext _localctx = new IntsContext(max);
        enterRule(_localctx);
        
        try {
            // 匹配第一个 INT
            match(INT);
            
            // 循环匹配后续的 ,INT
            while (hasNextToken()) {
                match(COMMA);
                _localctx.i++;  // $i++ 动作
                
                // 语义谓词检查 - 核心逻辑！
                if (!(_localctx.i <= _localctx.max)) {
                    throw new FailedPredicateException(
                        this, 
                        "$i<=$max", 
                        "exceeded max " + _localctx.max
                    );
                }
                
                match(INT);
            }
        } finally {
            exitRule();
        }
        return _localctx;
    }
}


错误处理流程

1. 条件检查：if (!(_localctx.i <= _localctx.max))
2. 异常抛出：throw new FailedPredicateException(...)
3. 错误恢复：ANTLR4 的错误恢复机制会捕获此异常，尝试重新同步
4. 错误报告：最终显示友好的错误消息给用户

完整的错误消息生成

对于输入 [1,2,3,4,5] 和规则 ints[4]：

### 语法谓词（Predicates）

在 ANTLR 4 中，语法谓词（predicates）是一种在解析过程中动态影响解析决策的机制。主要用于解决以下两种经典难题：

1. 解决上下文无关文法无法表达的语言特性（例如 C++ 中 `T* p;` 可能是乘法也可能是指针声明）
2. 在无限前瞻的情况下安全地消除左递归

ANTLR 4 支持两种谓词：

- 语义谓词（semantic predicates）  
  用 `{ ... }?` 表示，里面可以写任意 Java 代码（或目标语言代码），返回 `true` 或 `false`，决定当前规则是否匹配成功。

- 验证谓词（validating predicates）  
  又叫 disambiguating semantic predicates，写在规则最前面，用 `{ ... }?=>` 形式，主要用于在多个候选规则之间进行选择。

#### 1. 基本的语义谓词

```antlr
stat:   {isDeclaredLocal()}? ID      -> localVariable
    |   {isField()}?         ID      -> fieldReference
    |   expr ';'                     -> expressionStatement
    ;
```

上面这个例子中：
- 如果当前 ID 已经在局部变量表里，就走 `localVariable`
- 如果它是类的字段，就走 `fieldReference`
- 否则当作普通表达式

只要大括号里的 Java 表达式返回 `true`，该候选规则（alternative）才能继续匹配，否则直接失败并尝试下一个候选。

#### 2. 验证谓词（解决二义性最常用）

当多个候选规则都可能匹配输入时，ANTLR 4 按顺序尝试。但如果你希望在某些特定条件下“跳过”前面的候选，就要用验证谓词 `{...}?=>`

经典例子：C 语言中区分 typedef 名和普通标识符

```antlr
declaration
    :   {isTypeDefName()}?=> ID ID ';'   -> typedefUse
    |   type ID ';'                      -> variableDeclaration
    ;
```

加上 `?=>` 后，只有当 `{isTypeDefName()}?` 为 true 时，这个候选才会被真正考虑。  
这能大幅提升性能，避免不必要的回溯（backtracking）。

#### 3. 在 lexer 中使用谓词（超级实用）

lexer 规则也可以带谓词，常用于解决“关键字 vs 标识符”问题。

```antlr
TYPE_NAME   :   {isType()}? ID ;
ID          :   [a-zA-Z_] [a-zA-Z0-9_]* ;
```

这样，当输入是已知类型名时，会优先匹配 `TYPE_NAME`，否则走普通 `ID`。

#### 4. 常见实际案例

##### 案例 1：C++ 中 `*` 是乘法还是指针声明？

```antlr
expr:   expr '*' expr       -> multiply
    |   type '*' ID         -> pointerDeclaration
    ;
    
type:   {nextIsPointerType()}?=> '*' type
    |   ID
    ;
```

##### 案例 2：Python 中 `>>` 是右移还是嵌套泛型？

```antlr
shiftExpr   :   expr '>>' expr ;
closeExpr   :   expr '>'  {closeGeneric()}? ;
```

#### 5. 失败谓词（failing predicate）—— 强制报错

```antlr
stat:   {!allowLegacyCode()}?=> 'goto' ID ';'   // 禁止使用 goto
    |   ...
    ;
```

如果 `allowLegacyCode()` 返回 false，就会直接抛出 `FailedPredicateException`，你可以自定义错误信息。

#### 6. 注意事项与最佳实践

1. 语义谓词必须是纯函数（pure），不能有副作用（ANTLR 可能会多次求值）。
2. 不要在谓词里写太复杂的逻辑，会严重拖慢解析速度。
3. 优先使用验证谓词 `{...}?=>` 来消除二义性，比普通谓词性能高很多。
4. 在 lexer 中使用谓词是完全安全的，性能开销极小。
5. 如果你开启了 SLL 模式（默认的快速解析模式），普通语义谓词可能会导致自动回退到 LL(*)，降低性能，所以能用验证谓词就尽量用。

#### 7. 错误处理示例

```antlr
@parser::members {
    boolean isTypeDefName() { ... }
    
    @Override
    public void reportError(RecognitionException e) {
        if (e instanceof FailedPredicateException fpe) {
            String msg = "这不是合法用法：" + fpe.getMessage();
            throw new RuntimeException(msg, e);
        }
        super.reportError(e);
    }
}
```

总结：
- 需要动态决策 → 用普通语义谓词 `{...}?`
- 需要消除二义性、提升性能 → 用验证谓词 `{...}?=>`
- 在 lexer 中区分关键字/类型名 → 强烈推荐用谓词

掌握了谓词，你就真正掌握了 ANTLR 4 处理真实世界复杂语言的终极武器。

### 问题分析

你遇到的链接错误（`undefined reference to lld::coff::link`、`lld::elf::link`、`lld::wasm::link` 等）是因为 Zig 的构建过程（具体在 `zig_llvm.cpp` 文件中）需要链接到 LLVM 20 的 动态共享库（`.so` 文件），这些函数是 LLD（LLVM 的链接器）模块的 C++ API 入口点。

- 为什么系统包不行？ Ubuntu/Debian 的 `llvm-20` 包只提供了 静态库（`liblldCOFF.a`、`liblldELF.a` 等），没有动态版本的 `liblld*.so`。Zig 的 `libzigcpp.a` 是静态库，它期望动态链接 LLD 的符号，但静态库中这些符号的可见性/ABI 不匹配，导致链接失败。
- 这些函数实现在哪里？ 这些是 LLD 项目的核心函数：
  - `lld::coff::link(...)` 在 `lld/COFF/Driver.cpp`（或相关源文件）。
  - `lld::elf::link(...)` 在 `lld/ELF/Driver.cpp`。
  - `lld::wasm::link(...)` 在 `lld/Wasm/Driver.cpp`。
  但在 预编译二进制包 中，它们编译成：
    - `liblldCOFF.so`（COFF 模块）
    - `liblldELF.so`（ELF 模块）
    - `liblldWasm.so`（WebAssembly 模块）
  这些 `.so` 文件位于 LLVM 完整二进制发布包的 `lib` 目录下。

### 解决方案：使用 LLVM 20 的完整预编译库

Ubuntu 的系统包不全，你需要下载 官方预编译的 LLVM 20 二进制包（LLVM-20.1.x-Linux-x86_64.tar.xz），它包含所有动态 LLD 库（包括 `liblld*.so`）。这个包是针对 Ubuntu 22.04 构建的，但兼容 24.04+（glibc 版本匹配）。

```bash

```

- 解压后目录结构（确认这些文件存在）：
  ```
  llvm-20-full/
  ├── bin/          # clang-20, ld.lld 等可执行文件
  ├── include/      # 头文件
  ├── lib/          # 关键：这里有动态库！

  │   ├── liblldELF.so           # ← 解决 elf::link
  │   ├── liblldWasm.so          # ← 解决 wasm::link
  │   ├── liblldCommon.so        # 通用模块

  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_PREFIX_PATH=~/dev/llvm-20-full \  # 替换成你的实际路径

```

- 为什么这些参数？
  - `-DCMAKE_PREFIX_PATH=...`：告诉 CMake 从这个目录找库/头文件，包括所有 `liblld*.so`。
  - `-DZIG_PREFER_CLANG_CPP_DYLIB=ON`：优先用动态 `libclang-cpp.so`。
  - `-DZIG_STATIC_LLVM=OFF`：避免静态链接，强制用动态库。
- 构建过程会自动链接到 `llvm-20-full/lib/` 中的动态 LLD 库，解决 undefined reference。
