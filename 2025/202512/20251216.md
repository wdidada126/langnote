Selinger算法
Selinger算法（也称为System R优化器或Selinger-style动态规划查询优化器）是1979年IBM System R项目中由Pat Selinger等人提出的经典基于代价的查询优化算法，主要使用动态规划（Dynamic Programming）来枚举连接顺序（Join Order），结合统计信息和代价模型选择最优执行计划。它是现代关系型数据库查询优化器的基础框架（如PostgreSQL、Oracle等都受其影响）。

### 开源实现或库推荐
Selinger算法本身是学术/工程框架，没有官方独立的开源库，但有以下开源项目实现了其核心思想（动态规划 + 代价估计）：

1. Berkeley CS186课程项目（最经典的教育实现）  
   - GitHub搜索“CS186 Query Optimizer”或直接参考Berkeley大学数据库课程项目。  
   - 实现包括：代价估计（IO Cost）、Selinger动态规划枚举左深树（left-deep joins）。  
   - 示例仓库：https://cs186.gitbook.io/project/（课程文档，有完整代码骨架）。

2. sameerkhanna786/Cost-Estimation-and-Selinger-Query-Optimization  
   - GitHub：https://github.com/sameerkhanna786/Cost-Estimation-and-Selinger-Query-Optimization  
   - 完整实现了查询优化器的两部分：代价估计器 + Selinger风格的最优计划选择器（动态规划）。

3. Apache Calcite（工业级开源优化器框架）  
   - GitHub：https://calcite.apache.org/  
   - 广泛用于Flink、Hive、Drill、Kylin等大数据系统，支持基于规则（RBO）和基于代价（CBO）的优化，可扩展实现Selinger-style动态规划。许多项目基于Calcite自定义Join Order枚举。

4. PostgreSQL源码（生产级实现）  
   - PostgreSQL优化器（planner.c等）部分继承Selinger思路：对于小表连接用动态规划，大表用遗传算法（GEQO）。  
   - 开源地址：https://github.com/postgres/postgres（查看src/backend/optimizer/）。

5. ORCA（Pivotal/Greenplum开源优化器）  
   - GitHub：https://github.com/greenplum-db/gpdb/tree/main/src/backend/orca  
   - 使用自顶向下的动态规划变体，支持更复杂的查询。

如果你想学习或实验Selinger算法，推荐从CS186课程项目或上述GitHub仓库入手（Java实现，易懂）。实际数据库如CockroachDB、TiDB等也使用了类似动态规划的Join Order优化。如果你需要具体代码示例或某个仓库的深入解释，再告诉我！

Edward Sciore 的《Database Design and Implementation》（第二版）附带的实验代码是作者自己开发的 SimpleDB 系统（Java 实现），这是一个完整的教学用小型数据库系统，包括文件管理、缓冲区、日志、恢复、事务、查询解析、优化器、JDBC 接口等模块。代码原本托管在作者的 Boston College 个人网站（http://cs.bc.edu/~sciore/simpledb/），现在可以在 GitHub 上找到多个镜像或增强版（如 borgoat/simpledb、chaoyangnz/simpledb 等）。

而你之前提到的 MIT 的代码（https://github.com/MIT-DB-Class/simple-db-hw-2021）是 MIT 数据库课程（6.830/6.814）的 学生作业框架，也是叫 SimpleDB，但这是完全不同的实现：

- MIT 的 SimpleDB 是学生逐步实现的（从 heap file、buffer pool 到 B+ tree、join、transaction、recovery 等 lab），框架提供测试和部分骨架代码，学生填空完成。
- Sciore 的 SimpleDB 是作者已完整实现的系统，读者通过阅读和修改现有代码来学习（书中每章对应代码模块，并有练习建议扩展）。

主要区别：
- 设计目的：MIT 版重在“动手实现”数据库内部组件；Sciore 版重在“阅读和理解”一个完整系统的实现细节。
- 功能范围：两者都覆盖数据库核心，但模块划分、API、实现细节（如页面格式、锁机制、索引结构）不同。
- 复杂度：有读者反馈（Reddit 等）MIT 版内部工具类较多，较复杂；Sciore 版更简洁直观，适合自学。

简单说，虽然都叫 SimpleDB、都用 Java、都用于教学数据库实现，但它们是两个独立的系统，代码结构和内容不相同，不能直接互换使用。

如果你想尝试 Sciore 的代码，推荐从 GitHub 搜索 “sciore simpledb” 或 “borgoat/simpledb” 下载，结合书第二版阅读效果最好。

在Notepad++中显示不可打印字符（换行符、制表符、空格等）非常方便。以下是几种方法：
方法一：通过工具栏按钮（最快捷）
找到工具栏上的 "显示所有字符" 按钮
图标是：¶（类似一个反向的P）
或者通过菜单：视图 → 显示符号 → 显示所有字符
点击后，文档中将显示：
制表符 → 显示为右箭头：→
空格 → 显示为中间点：·
换行符 → 显示为：
CRLF (Windows)：↵或显示为CRLF
LF (Unix/Linux)：↵
CR (Mac)：↵

这是一个非常好的问题，涉及到文本文件的物理存储和不同软件的显示逻辑之间的区别。
简单回答：你的理解是正确的，Java词法解析器在源代码中确实将换行符识别为\n，但Notepad++显示的是文件在磁盘上实际存储的字节格式。两者是不同层面的概念。
让我详细解释：
1. 物理存储层面（Notepad++ 显示的内容）
在磁盘上，不同操作系统使用不同的字符表示换行：

操作系统 换行符表示 字节序列 Notepad++ 显示
Windows CRLF \r\n (0x0D 0x0A) CR LF
Unix/Linux/Mac LF \n (0x0A) LF
旧版 Mac CR \r (0x0D) CR

当Notepad++显示"CRLF" 时，它告诉你：
• 这个文件在磁盘上实际存储的是 \r\n 两个字节
• 文件很可能是在 Windows 系统上创建的，或者用 Windows 风格的换行保存的

2.Java词法解析层面（JLS 规定）
Java 语言规范（JLS）规定：

1. 在源代码中，无论实际存储的是什么，换行符都被规范化为：
   • 单个 \n (LF, U+000A)
   • 单个 \r (CR, U+000D)
   • 或 \r\n 序列

2. 词法分析时，Java 编译器会统一处理：
   // 无论文件实际是 CRLF 还是 LF
   // Java 词法解析器都会将换行识别为 "\n"
   // 例如，源码中的字符串：
   String s = "第一行\n第二行";  // 这里的 \n 是转义字符
   // 或者在正则表达式中：
   String[] lines = text.split("\n");

3. Java 编译器会自动转换：
   • 读取源代码时，编译器会识别 \r\n、\r 或 \n 作为行终止符
   • 但在词法层面，统一视为行终止符，而不是特定的转义序列

3. 示例说明
假设你有一个Test.java文件，在Windows上创建：
public class Test {
    public static void main(String[] args) {
        System.out.println("Hello");
        System.out.println("World");
    }
}

在磁盘上（十六进制查看）：

70 75 62 6C 69 63 20 63 6C 61 73 73 20 54 65 73 74 20 7B 0D 0A
public class Test {..  // 注意这里的 0D 0A (\r\n)

在 Notepad++ 中：
• 状态栏显示：Windows (CR LF)
• 如果开启"显示所有字符"，会看到每个行尾都有 ↵ 符号
但 Java 编译器看到的是：

1. 读取字节流
2. 遇到 0D 0A 时，识别为一个行终止符
3. 在词法分析中，这个行终止符用于分隔 token
4. 在字符串字面量中，\n 转义字符被识别为行终止符

4. 验证实验

你可以用以下代码验证：

```
import java.io.*;
import java.nio.file.*;

public class LineEndingTest {
    public static void main(String[] args) throws IOException {
        // 读取文件原始字节
        byte[] bytes = Files.readAllBytes(Paths.get("LineEndingTest.java"));
        
        // 查找换行符
        for (int i = 0; i < bytes.length; i++) {
            if (bytes[i] == 0x0D) {
                System.out.println("位置 " + i + ": CR (\\r)");
            }
            if (bytes[i] == 0x0A) {
                System.out.println("位置 " + i + ": LF (\\n)");
            }
        }
        
        // 用Java读取行
        System.out.println("\n--- 按行读取 ---");
        try (BufferedReader br = new BufferedReader(
            new FileReader("LineEndingTest.java"))) {
            int lineNum = 1;
            while (br.readLine() != null) {
                System.out.println("第 " + lineNum + " 行");
                lineNum++;
            }
        }
    }
}
```

总结
层面 表示 说明
磁盘物理存储 CRLF / LF / CR Notepad++ 显示的实际字节
Java 词法解析 \n (标准化) Java 编译器统一处理后的逻辑表示
Java 字符串字面量 \n 转义 源代码中的转义字符，编译时转换为行终止符
关键点：Java 语言处理的是逻辑上的换行，而不关心底层是 \r\n 还是 \n。Notepad++ 显示的是物理存储格式。这种抽象使得 Java 代码可以跨平台移植，只要编译器能识别出各种格式的行终止符即可。

建议在团队开发中统一使用 LF 格式，以避免跨平台问题。在 Notepad++ 中可以通过 编辑 → 文档格式转换 → 转换为 Unix (LF) 来转换。

### MIT Database Lab（或相关课程/项目）中的 MVCC 和 WAL 实现情况

MIT 有多个与数据库相关的课程和研究组，主要包括：
- Database Systems 课程（当前编号 6.5830/6.5831，以前是 6.830/6.814，由 MIT CSAIL 的 Database Group 维护）。
- Distributed Systems 课程（6.824/6.5840，由 PDOS Group 维护）。

#### 1. Database Systems Lab (6.5830 等) 中的 SimpleDB 项目
- 这个课程的核心教学项目是实现一个简化版 DBMS 叫 SimpleDB（基于 Java 或近年转为 Go）。
- 学生通过多个 Labs 逐步实现：
  - Lab 1：基本存储、查询执行。
  - Lab 2：查询优化、缓冲管理。
  - Lab 3：Transactions – 实现 locking-based concurrency control（两阶段锁 2PL），支持隔离性和恢复。
  - 包括 ARIES-style recovery：实现 Write-Ahead Logging (WAL)、Undo/Redo Log、Checkpoint 等，用于原子性和持久性。
- MVCC：没有实现。SimpleDB 的并发控制是基于锁的（lock manager + deadlock detection），不是多版本并发控制（MVCC）。它使用单版本数据 + 锁来实现隔离。
- 许多学生实现公开在 GitHub 上（如 dstibrany/SimpleDB 等），你可以查看 Lab 3 代码确认 WAL 有，但无 MVCC。

#### 2. Distributed Systems Lab (6.824)
- Labs 包括 Raft 共识、sharded KV store。
- Lab 3/4 是 fault-tolerant/sharded KV database，使用 Raft 复制日志（类似 WAL 的作用，用于持久性和恢复）。
- MVCC：没有典型的数据库 MVCC。KV store 是单版本的，依赖 Raft 日志实现线性一致性。

#### 3. MIT 研究项目中的实现
- MIT PDOS Group（Parallel and Distributed Operating Systems）有一个研究项目叫 vMVCC（verified Multi-Version Concurrency Control）。
  - 这是一个高性能、可形式化验证的 MVCC 事务库，使用 Coq/Perennial 框架证明正确性。
  - 结合 MVCC 用于并发，目标是构建可靠的事务数据库。
  - 项目页面：https://pdos.csail.mit.edu/projects/vmvcc.html
  - WAL：作为事务恢复的一部分，通常会涉及日志（ARIES-like），但重点在 MVCC 的验证上。
  - 这不是教学 Lab，而是研究原型，有代码（可能在 PDOS repo 中）。

总结：
- WAL：有，在 Database Systems 的 SimpleDB Lab 3 中实现（ARIES 恢复）。
- MVCC：教学 Lab 中没有（用锁代替）；但研究层面有 vMVCC 项目实现了可验证的 MVCC。
如果你指的是教学项目（如 SimpleDB），答案是 WAL 有，MVCC 没有。如果你想实验 vMVCC 或查看 SimpleDB 代码，可以去对应 GitHub repo 下载。需要具体链接或指导吗？

Coq/Perennial框架 是由 MIT CSAIL 的 Parallel and Distributed Operating Systems (PDOS) 组开发的一个形式化验证框架，用于在 Coq 证明助手（现更名为 Rocq）中验证并发且崩溃安全（crash-safe）的系统，特别是存储系统（如文件系统、数据库等）。

### 核心特点
- 基于 Iris：Perennial 是对 Iris（一个高级并发分离逻辑框架）的扩展。Iris 提供并发验证支持，Perennial 在此基础上添加了崩溃安全（crash safety） 的证明机制，包括恢复过程（recovery）、日志（logging）、内存版本化等。
- 支持崩溃后正确性：能证明系统在突发崩溃（如电源故障）后，通过恢复代码能回到一致状态，而不会丢失数据或违反不变量。
- 结合 Goose：Perennial 通常与 Goose 工具配合使用。Goose 是一个 Go 语言子集的翻译器，能将 Go 代码自动转换为 Coq 模型，便于在 Perennial 中进行证明。这样可以验证实际可运行的 Go 代码，而非纯抽象模型。

### 应用示例
- 使用 Perennial 和 Goose 验证了一个并发崩溃安全的邮件服务器（mail server），证明已投递的消息永不丢失，并支持多核加速。
- 其他项目如 DaisyNFS（验证的文件系统）、GoJournal（事务日志系统）等也基于 Perennial。

### 开源信息
- 主仓库：https://github.com/mit-pdos/perennial
- Goose 翻译器：https://github.com/goose-lang/goose
- 项目页面：https://pdos.csail.mit.edu/projects/perennial.html
- 相关论文：SOSP 2019 “Verifying concurrent, crash-safe systems with Perennial”。

这个框架特别适合研究数据库、文件系统等需要同时处理并发和持久性/崩溃恢复的系统（如 MVCC、WAL 等机制的形式化验证）。如果你在研究 vMVCC 或类似项目，它就是那个提到的 Perennial 框架！需要更多细节或代码示例吗？

### 大学数据库实验室/课程项目中实现 MVCC、Redo Log、Undo Log 和 WAL 的代表性例子

许多大学的数据库系统课程（Database Systems Implementation）会通过教学项目让学生实现 DBMS 的核心组件，包括 MVCC（多版本并发控制）、Redo Log（重做日志）、Undo Log（回滚日志） 和 WAL（Write-Ahead Logging，先写日志）。这些通常基于 ARIES 恢复算法（包括分析、重做、回滚三阶段，支持 WAL、Redo/Undo）。

#### 1. Carnegie Mellon University (CMU) - 15-445/645 Introduction to Database Systems
   - 项目：BusTub（一个完整的教学 DBMS，用 C++ 实现）。
   - 实现内容：
     - MVCC：Project #4 中实现 Optimistic Multi-Version Concurrency Control (MVOCC)，包括版本链、读视图（Read View）、时间戳分配，支持快照隔离。
     - WAL / Redo Log / Undo Log：早期项目涉及缓冲管理、日志记录；恢复部分支持 ARIES-style WAL，包括 Redo（重做已提交变更）和 Undo（回滚未提交）。
   - 开源：https://github.com/cmu-db/bustub（学生 forks 众多）。
   - 特点：最全面的教学实现之一，覆盖从存储到并发控制的全栈，常被视为“金标准”。

#### 2. MIT - 6.5830 / 6.830 Database Systems
   - 项目：SimpleDB（Java 或 Go 实现）。
   - 实现内容：
     - WAL：Lab 3 中实现 ARIES-style recovery，包括 Write-Ahead Logging、Checkpoint、Redo/Undo Log。
     - MVCC：教学版本主要用锁-based 并发（2PL），没有标准 MVCC；但研究分支（如 vMVCC 项目）有形式化验证的 MVCC。
   - 特点：重点在 WAL 和恢复上，MVCC 不是核心。

#### 3. 其他大学
   - UC Berkeley (CS186)：课程涉及恢复和日志讲解，实现简单 Undo/Redo Logging 和 WAL，但项目更侧重查询执行而非完整 MVCC。
   - Stanford (CS346 Database System Implementation)：RedBase 项目，实现日志、恢复（包括 WAL），但无明确 MVCC。
   - Caltech (CS122)：有明确 WAL 作业，包括 Undo/Redo 生成和恢复。

最推荐：如果你想找同时实现 MVCC + WAL/Redo/Undo 的完整开源教学项目，CMU 的 BusTub 是最佳选择。它直接支持这些机制，并有详细文档和测试用例，便于学习和扩展。许多其他大学的课程也会参考或 fork BusTub。
