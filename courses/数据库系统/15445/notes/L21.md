# L21 分布式数据库导论（Introduction to Distributed Databases）

> 15-445/645 Fall 2023 · Lecture 21 · 阅读：课程讲义；6.824 相关材料
> 单机扛不住时把数据/计算摊到多机：分片解决"容量与并行"，复制解决"可用与就近"，共识解决"多机就一份真相"。

## 1. 核心概念

### 1.1 为什么分布式
- **规模**：数据 > 单机磁盘、查询 > 单机 CPU；
- **可用性**：容忍节点故障（无单点）；
- **地理**：就近读、容灾。
代价：网络不可靠（部分失败）、时钟不可信、延迟高、一致性难。

### 1.2 复制（Replication）
把同一份数据存多副本：
- **主-备（Primary/Backup）**：主处理写并转发；
- **主动复制（active/primary-replica 都执行同一 SQL）** vs **被动复制（passive，只主执行、传日志/页）**——本课重点：传"逻辑 redo 日志"给备库重放；
- **同步 vs 异步 vs 半同步**：同步（等副本落盘才返回，RPO=0 但延迟高）、异步（快但可能丢，RPO>0）、半同步折中。
- **复制引发的问题**：副本滞后（读旧）、主库故障后新主可能缺日志（数据丢失/分叉）。

### 1.3 一致性与共识（Consensus）
- **CAP**：分区容忍(P)必选，于是 C（一致）与 A（可用）二选一——"网络分区时，是拒绝服务保一致，还是各写各保可用（之后调和）"。
- **线性一致性（linearizability）**：外部看像"单一副本、原子操作"——分布式正确性的金标准（对应单机可串行化）。
- **共识算法**：**Paxos / Raft / Viewstamped Replication**——多副本就"下一条日志"达成一致，容 f 个故障需 2f+1（多数派 quorum）。Raft 分解为 leader 选举 + 日志复制 + 安全性，是工程首选。
- 复制状态机（RSM）：只要所有副本以相同顺序应用相同日志，从相同初始状态出发→最终状态一致（确定性）。

### 1.4 分片 / 分区（Sharding / Partitioning）
把不同数据放不同机器：
- **按键哈希分片**：`shard = h(key) % N`，均匀、点查直接定位，但范围查需广播、再均衡（一致性哈希/虚拟桶）麻烦；
- **范围分片（range）**：按 key 区间切，范围查友好，易热点；
- **列表/轮询/数据库内自治分片**；
- **再均衡（rebalance）**：加减节点时迁移 shard，用双写/影子读/一致性哈希最小化搬运。
分片 + 复制组合：每 shard 是一个 Raft/Paxos 复制组（TiDB/CockroachDB/FoundationDB 架构）。

### 1.5 跨分片/分布式事务预告
数据一分片，一条事务就可能碰多个 shard → 需要 **两阶段提交 2PC**（L22 细讲，协调者 + prepare/commit，慢、协调者单点）或 **Percolator/Spanner** 式方案。异构复制：分布式查询 = 计划切段 + 分布式 shuffle/exchange。

## 4. 开源项目应用
- **PostgreSQL 复制**：流复制（streaming replication）传 WAL，同步/异步；`pg` 逻辑复制；分片靠 Citus 扩展。
- **MySQL**：binlog 主从复制（异步/半同步/group replication 用 Paxos）。
- **etcd / Consul**：Raft 实现，配置存储——学共识的最佳代码。
- **MongoDB**：副本集（Raft 系）+ 分片集群（chunk + config server）。
- **CockroachDB / TiDB**：Raft 复制组 + 范围分片（region/tablet）+ 分布式 MVCC，本讲的工业完整体（L22 深入）。

## 速记自检
- Q：分片解决什么、复制解决什么？——A：容量与并行 / 可用与就近（§1.1）。
- Q：CAP 为何必选 P？——A：网络分区不可避免（§1.3）。
- Q：容 f 故障需几副本？——A：2f+1（quorum，§1.3）。
- Q：哈希分片 vs 范围分片？——A：均匀但范围查广播 vs 范围友好但易热点（§1.4）。
