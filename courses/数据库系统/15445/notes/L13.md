# L13 查询执行 II（向量化与并行执行）

> 15-445/645 Fall 2023 · Lecture 13 · 阅读：MonetDB/X100、Vectorwise、Morsel-Driven 论文；Project #3
> 火山模型逐元组跑，CPU 大部分周期花在"函数调用和分支"上；向量化说：别再逐条了，一次给一批，让 SIMD 和缓存动起来。

## 1. 核心概念

### 1.1 为什么逐元组慢（SIMD 动机）
现代 CPU：**单指令吞吐高、有 SIMD（一条指令同时算 4/8/16 个数）**、深流水线、乱序执行、分支预测。逐元组火山模型的三个原罪：
1. **虚函数调用开销**：每元组每算子一次 `Next()`，无法内联，吃掉指令带宽；
2. **无 ILP/SIMD**：一次只处理一个值，`a+b` 只加一次，浪费 SIMD 向量单元（一次本可加 8 个）；
3. **分支误预测**：`WHERE` 里逐行 if，数据无序→预测失败→流水线冲刷（mispredict 成本几十周期）。
=> CPU 利用率可能只有 10%。目标：**把每元组的"控制开销"摊到一批上，让算术/访存占主导。**

### 1.2 向量化执行（Vectorized / Block-at-a-Time）
代表：**MonetDB/X100**（Idreos & Kersten 2002）、**Vectorwise**（Abadi 等）、被 DuckDB/ClickHouse/Velox/Photon 采纳。
- 接口仍是火山式，但 `Next()` 每次返回**一批（batch/data chunk，典型 1024–4096 行）**的**列式数组**，而非一行。
- 每个算子对整批做循环 → 编译器/CPU 能：内联、自动向量化（SIMD）、指令流水填满。
- **列式批次 + SIMD**：同类型连续，一条 AVX `_mm256_add_ps` 处理 8 个 float。
- **Selection Vector（选择向量）**：Filter 不物化拷贝元组，而是维护一个"哪些行存活"的整数向量（或直接 bitmask），下游算子据此跳过死行——避免逐行搬数据，缓存友好。这是 X100 的关键设计。

### 1.3 向量化 vs 编译执行（两条提速路线）
| | 向量化 | 全阶段代码生成 (JIT) |
|---|---|---|
| 思路 | 解释器 + 批量 + SIMD | 把算子树编译成机器码 |
| 消除虚调用 | 部分（批内循环内联） | 完全 |
| SIMD | 天然 | 需手工 intrinsic |
| 短查询 | 好（无编译延迟） | 差（编译开销） |
| 长查询/复杂表达式 | 好 | 略优 |
| 代表 | DuckDB/ClickHouse | HyPer/Spark Tungsten/Photon |
现代常**混合**：向量化为骨架，热点表达式 JIT。

### 1.4 并行执行
- ** intra-query 并行**：一个查询多核同时跑。
  - **按分区/pipeline 静态划分**：数据切 N 份给 N 线程——负载可能不均（倾斜）。
  - **Morsel-Driven Parallelism**（Leis 2014）：数据切成小 morsel（~10 万行），线程用**原子 fetch-add 动态认领**下一个 morsel → **自适应负载均衡**，抗数据倾斜，无需手工分区。扫描、聚合、hash join build 都能 morsel 化。
  - **Phase-Parallel / Exchange**：pipeline breaker 处分相，相内并行、相间用 exchange 算子（+本地调度，无 shuffle）通信。
- **并行度**：与缓冲池/预读配合，多线程各持帧句柄。

## 4. 开源项目应用
- **DuckDB**：DataChunk(2048) + selection vector + 自动并行（morsel-driven，`TaskScheduler`）；本仓库 projects 向其看齐。
- **ClickHouse**：向量化 + SIMD（`Block` 列批），单核吞吐极高。
- **Velox（Meta）/Photon（Databricks）**：库级向量化执行引擎，供上层复用。
- **Postgres 17**：实验性向量化增量聚合（SUM 用 SIMD）——火山老系统也开始吸收向量红利。
- **HyPer**：走 JIT（Whole-Query Codegen）路线的另一极。
