# L17 时间戳排序（Concurrency Control Based on Timestamp Ordering）

> 15-445/645 Fall 2023 · Lecture 17 · 阅读：课程讲义
> 2PL 用"锁"阻止非法交错；TO 换思路：给每个事务发一个"出生时间戳"，凡会破坏"按时间戳串行序"的操作直接拒绝/回滚——从不等待，从不限流。

## 1. 核心概念

### 1.1 时间戳与目标
- 每个事务 T 在进入系统时获得唯一、单调递增的 **TS(T)**（可用逻辑计数器 / Lamport clock / 混合逻辑时钟 HLC）。
- 目标：调度等价于**按 TS 升序的串行执行**。为每个数据项 Q 维护两个时间戳：
  - **W-ts(Q)**：最后成功写 Q 的事务 TS；
  - **R-ts(Q)**：最后成功读 Q 的事务 TS。

### 1.2 基本 TO 协议
事务 T（时间戳 t）：
- **Read(Q)**：
  - 若 t < W-ts(Q)：Q 的值是"未来事务"写的，T 读到的是"不该看到的更新后版本"→ **回滚 T**（用旧值重放）。
  - 否则：接受，令 R-ts(Q)=max(R-ts(Q), t)。
- **Write(Q)**：
  - 若 t < R-ts(Q)：有"未来事务"已读过 Q 的旧值，本次写会使其读到不同结果 → **回滚 T**。
  - 若 t < W-ts(Q)：写已被未来事务覆盖 → **回滚 T**（写丢失）。
  - 否则：接受，W-ts(Q)=t。
- 回滚后事务**换新时间戳**重试（保持串行序=新 TS）。

### 1.3 Thomas's Write Rule（放宽）
在 Write 时，若 t < R-ts(Q) 但 t ≥ W-ts(Q)：**不丢弃写**——因为那个"未来的读"之后肯定又被同样未来的写覆盖了，忽略即可。Thomas 规则允许更多调度（不再严格可串行化到 TS 序，但冲突可串行化），提升并发。这是本课常考的"规则变体"点。

### 1.4 多版本 TO（MVTO）
基本 TO 回滚率高。给每个数据项存**多版本** (value, R-ts, W-ts)：
- Read(Q,t)：返回 W-ts ≤ t 的**最新版本**（不必回滚去读旧值）；
- Write(Q,t)：若 t < 某版本 R-ts → 该读依赖旧值，回滚；否则新建版本。
→ 这正是 L18 MVCC 的思想源头之一：多版本把"读阻塞/回滚"消除。

## 2. TO vs 2PL 对比
| 维度 | 2PL | Timestamp Ordering |
|---|---|---|
| 等待 | 会阻塞（拿不到锁等） | 从不等待（要么过要么滚） |
| 死锁 | 有，需检测/预防 | **无死锁**（无循环等待） |
|  starvation | 可用 wait-die 防 | 老事务不断回滚新事务可能饿死新者 |
| 恢复 | 便于结合日志 | 回滚频繁，undo 多 |
| 实际使用 | 广泛 | 纯 TO 很少，多版本 TO 思想活 |

## 3. 前后讲联系
承 L15（目标可串行化）、L16（同为解法但更乐观）。MVTO 直接引出 L18 MVCC。时间戳的分配与回滚的 undo 依赖 L19 日志。HLC/Lamport 时间戳是 L21-22 分布式一致性的基础设施。

## 5. 开源项目应用
- **纯 TO 罕见**，但思想无处不在：
- **Spanner（L22）**：commit wait + TrueTime 给事务一个"有效时间戳"，读按时间戳取快照——本质是**分布式 MVTO**。
- **CockroachDB**：HLC 时间戳 + 事务，读时间戳/写时间戳冲突时 push（"timestamp push"），是 TO 的分布式演化。
- **PostgreSQL/InnoDB（L18）**：用事务 ID/LSN 当"版本时间戳"做 MVCC 可见性判断——R-ts/W-ts 的血统。
- **Google Percolator**：timestamp + optimistic 事务，是分布式 TO 的代表。
