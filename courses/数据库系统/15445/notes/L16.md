# L16 两阶段锁（Concurrency Control Based on Two-Phase Locking）

> 15-445/645 Fall 2023 · Lecture 16 · 阅读：课程讲义；Project #5(锁管理器)
> 2PL 用"先拿锁、后释放，且释放后不许再拿"这一条纪律，把并发调度钉成可串行化——代价是死锁，必须配套处理。

## 1. 核心概念

### 1.1 锁模式与冲突矩阵
基本锁模式：**Shared(S)** 读锁、**Exclusive(X)** 写锁。冲突矩阵：
| 持有\请求 | S | X |
|---|---|---|
| **S** | 兼容 | 冲突 |
| **X** | 冲突 | 冲突 |
升级（strengthening）：S→X；降级（weakening）：X→S（一般禁止，会破坏正确性）。
多粒度锁（intent locks）见 1.5。

### 1.2 两阶段协议
- **Growing phase**：事务只能加锁、不能释放锁（可升级）。
- **Shrinking phase**：一旦释放任一把锁，就进入缩减期，**不得再申请新锁**。
- **定理**：所有 2PL 调度都冲突可串行化（锁的获取/释放顺序定义了串行序）。
- **Strict 2PL（S2PL）**：所有 **X 锁持有到事务提交/回滚** 才释放 → 避免级联回滚 + 便于恢复（多数工业 DB 用其变体）。Rigorous 2PL：S 也持到底。
- 基本 2PL 能保可串行化，但**不防死锁、不防级联回滚**（非 strict 时）。

### 1.3 死锁（Deadlock）——2PL 的头号麻烦
两个（或以上）事务互相持有对方需要的锁 → 循环等待 → 永久阻塞。
处理策略：
- **预防（Prevention）**：破坏四个必要条件之一。
  - **Wait-Die（older 等 younger 者，young 请求被 older 持有→young 回滚重来）**：基于**时间戳**的无饿死方案；older 可等，younger 被"杀"。
  - **Wound-Wait（older 请求被 younger 持有→older "wound"即强制 younger 回滚；younger 请求被 older 持有→younger 等待）**：抢占式，younger 让路。
  - 两者都用"老事务优先"保证不死锁、无饥饿；代价：不必要回滚（尤其数据分区多时 older 可能真该等）。
  - 简单预防：让所有事务按同一全局顺序申请锁（破坏循环等待），实现难、并发度低。
- **检测（Detection）**：允许死锁，靠**等待图（wait-for graph）** 周期性/触发式找环：事务=节点，T1 等 T2 的锁→边 T1→T2；**有环=死锁**。选**牺牲者（victim）** 回滚（选"回滚代价最小"或最年轻事务）。检测开销 = 图的维护 + 找环（O(V+E)）。这是 **MySQL InnoDB** 的做法。
- **超时（Timeout）**：最简单，等锁超过 `lock_wait_timeout` 就放弃回滚（Postgres `deadlock_timeout` + 之后才建 wait-for graph 检测）。

### 1.4 锁管理器（Lock Manager）数据结构
- **锁表（lock table）**：`(对象 ID, 事务 ID) → 锁模式` 哈希；读多写少 → 分片锁/原子操作降热点。
- 每个对象维护"持有者列表 + 等待队列"；释放锁时唤醒等待者（FCFS 或按优先级）。
- BusTub Project #5：实现 `LockManager`（两阶段锁 + 升级 + 死锁检测），对应本仓库 projects 锁管理项目。

### 1.5 多粒度与索引锁
- **Intent Locks（IS/IX/SIX）**：表→页→行三级层次，父节点打意向锁，使"锁整张表"无需遍历下层行锁（快速冲突判断）。
- **Index Locks / Gap Locks（InnoDB）**：锁加在索引记录上；**Next-Key Lock = record lock + gap lock**，锁住"记录及其前间隙"，防止他人插入到范围内 → 在 REPEATABLE READ 下消灭幻读。这是"谓词锁"的工程近似。
- 谓词锁（predicated lock，lock on "age<30"）理论最优但实现重；索引锁是其近似。

## 4. 开源项目应用
- **MySQL/InnoDB**：行级 2PL + Next-Key/Gap Lock（RR 隔离下）；死锁用 **wait-for graph 实时检测**（`SHOW ENGINE INNODB STATUS` 打 LATEST DETECTED DEADLOCK）；`innodb_deadlock_detect`。
- **PostgreSQL**：行级锁 + advisory lock；死锁用**超时(1s)后建 wait-for graph 检测**；表级/页级用 tuple 锁位（ xmax ）辅助；SERIALIZABLE 用 SSI 补充谓词冲突。
- **SQL Server**：lock escalation（行锁过多时升级为表锁，减少锁表内存）；优先用锁而非 MVCC（默认 READ COMMITTED 用锁）。
- **Spanner**：严格 2PL +  Paxos 复制（L22）——分布式下 2PL 需要协调。
