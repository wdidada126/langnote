# 第 4 讲 · 应用层原理：协议、进程寻址与运输服务需求

> 章节：Chapter 2 §2.1
> 中文对照：topdown_ustc 第 2 章（应用层概述）

## 1. 核心概念

- **网络应用 = 分布在不同端系统上的进程协同**。协议定义报文字段与收发规则——写协议就是写"两个状态机之间的对话"（本笔记反复使用的视角）。
- **进程寻址**：`IP + 端口`（socket 地址）。端口是传输层的解复用钥匙（第 9 讲），知名端口只是"约定"（HTTP 80、HTTPS 443）。
- **传输服务需求四象限**：可靠数据传输、时序（低延迟）、带宽（固定/弹性）、不丢序。典型矩阵：
  - 文件传输/邮件：可靠、弹性带宽、不敏感延迟。
  - 实时音频/视频：可容忍丢、要求延迟 <100~200ms、要求稳定速率（自适应码率 DASH 的动机，第 8 讲）。
  - 交互游戏：延迟敏感+可靠（部分状态）。
- **套接字 API 抽象**：TCP socket 是"字节流管道"（无消息边界，需自定框架/长度前缀）；UDP socket 是"信封投递"（保留消息边界、不保证到达）。这个区别是第 1 个项目（HTTP 服务器）与第 3/4 个项目（ARQ/聊天）的共同地基。
- **C/S 与 P2P 在应用层的实现差异**：服务器需要有固定地址+常开；P2P 要处理 NAT 后打洞（联系第 15 讲 NAT、第 8 讲 BitTorrent tracker 与 DHT）。

## 2. 关键设计要点

- 设计一个应用层协议清单：报文格式（文本如 HTTP / 二进制如 DNS）、握手语义、超时与重试、错误码、版本协商（TLS ALPN 等）。
- 消息边界问题示例：TCP 粘包/拆包——HTTP 用 `Content-Length`/分块解决；自定义协议要用 TLV 或分隔符+转义。

## 3. 层次间与前后讲联系

- "需求矩阵"直接决定运输层选择：TCP（可靠流）/UDP（轻+可控）/QUIC（用户态可靠流，第 12、14 讲）。
- 本讲是全章总纲：HTTP(5)、DNS(6)、socket(7)、流媒体/P2P(8) 都是"应用层协议实例"。
- 封装栈位置：所有应用报文最终装入 TCP/UDP 段（第 9-12 讲），再到 IP、链路。

## 4. 跨课程联系

- **CSAPP**：`socket/bind/listen/accept/connect` 即本讲 API 的 C 语言实现；tiny 服务器是 HTTP 迷你实例（对应 projects/ch2_http_server）。

## 5. 开源项目应用

- **Nginx/Envoy**：Envoy 的路由/filter 链就是"应用协议到服务语义"的产品化；HTTP/2、gRPC 代理展示协议分层在工业侧的复杂度。
- **Wireshark**：dissector 体系——每种应用协议一个插件，印证"协议即状态机+字段表"。
- **Python 标准库**：本讲所有项目共用 `socket`、`threading`；`selectors` 模块可对比 C/S 并发模型。

## 7. 自查问题

1. 为什么"UDP 更简单所以一定更快"是错误表述？（应用层重传逻辑往往重造 TCP，还常更差）
2. TCP 粘包到底是谁的问题？应用还是传输？举 HTTP 与自定义协议各一种解法。
3. 一个 P2P 应用如何获得"可被连接"的地址？（UPnP/NAT-Punching/中继——对应第 15 讲 NAT 类型）
4. 实时语音为什么不直接用带 TLS 的 TCP？（队头阻塞——引出第 12 讲 QUIC/媒体传输）

## 8. 本讲一句话

应用层的全部自由度 = 协议设计 + 并发模型 + 运输服务选择；先想清需求矩阵，再选 TCP/UDP/QUIC，不要反过来。
（补）设计练习：给"多人在线白板"写一页协议草案——报文类型（join/update/sync）、心跳周期、冲突合并策略；用它检验本讲四象限是否真能指导选型（结论通常是 TCP/QUIC+增量同步，与第 12 讲队头阻塞议题相连）。

## 9. 记忆卡

- socket 地址 = IP + 端口；字节流无边界 → 应用必须自定界（长度前缀/分隔符）。
- 需求矩阵四轴：可靠 / 时序 / 带宽 / 有序；TCP=流、UDP=信封、QUIC=用户态流。
- 架构三选：C/S（固定地址+常开）、P2P（自扩展+NAT 难题）、混合（tracker/relay）。
