# L18 数据并行系统谱系：Millipipe / GraphX / Lightning / Piccolo / Pregel

> 阅读：Isard et al., *Dryad*（背景，可选）；Yuan et al., *Millipipe: Elastic Pipeline Computation for Data-Parallel Graph Analytics*, OSDI 2020；
> 节选：PowerGraph (OSDI 2012, GraphX 基础)、Lightning (ATC 2015)、Piccolo (HotCloud 2012)
> 主线：从"通用两层"到"流水线 + 专用抽象"——数据并行的分化时代。

## 1. 核心问题

- L02 MapReduce 通用但慢（两层 + 落盘）；L17 Spark 通用且快（内存 + DAG）但仍有痛点：
  1. **Stage 间全量物化**：宽依赖必须等上游全部算完（栅栏同步），
     长流水线里延迟 = 各阶段之和；
  2. **迭代图/ML 算法**要"沿图传播"，用通用 DAG 表达 = 反复全量 shuffle；
  3. 调度是 **data-driven**（数据就绪触发）→ 内存与并行度难以预测。
- 本讲命题：**为特定负载定制数据流抽象，在通用性与性能间继续细化取舍**。

## 2. 各系统的解法（按问题拆解）

### 2.1 Piccolo（2012）：为 ML 定制"表 + 分区 + 同步"
- 数据 = 分区表（range-partitioned table）；计算 = 表上的并行函数；
  **子区间锁（sub-range locking）+ 表屏障（table barrier）**取代全局栅栏 →
  迭代 ML（Gibbs/逻辑回归）避免全局同步。
- 定位：**参数服务器（PS）思想的学术原型**；对比 Spark 通用 RDD，
  Piccolo 押注"迭代式 ML + 结构化共享状态"（→ 对接 15-442/MLC 的 PS 架构）。

### 2.2 GraphX/PowerGraph（2012）：图专用 = 顶点为中心
- **Pregel 模型**：超步（BSP）里顶点收消息 → compute → 发消息给邻居。
- **顶点中心化通信（vertex-centered, FGP）**：一条边拆成"出发半消息 + 到达半消息"，
  通信从 O(边) 降到 O(顶点+边) 的聚合，天然支持幂等合并（reduce）。
- **mirror + edge-cut 分区**（PowerGraph）：图切边难（重平衡），
  镜像顶点解决度数倾斜；一致性用"异步但有 barrier 收敛"的弱一致。
- GraphX = Spark 上的 RDD 化实现（EdgeTriplet），"通用引擎 + 图 DSL"。

### 2.3 Lightning（ATC 2015）：把迭代变成"流水线"
- 观察：迭代算法（SGD/PageRank）每轮 = 相同的 DAGE 执行；
  **把计算图编译成 data-pipeline：数据在算子间流动，多轮"重叠"执行（pipeline parallelism）**，
  消除轮间同步 → 论文对 Spark/GraphX 有数倍～一个数量级优势（特定负载）。
- 代价：放弃通用性（静态图、固定更新顺序语义）——**专用系统的典型取舍**。

### 2.4 Millipipe（OSDI 2020, MIT PDOS——本课自家作品）
- 关键思想：**control-driven 调度**——不是"数据就绪触发计算"，
  而是"调度器主动决定：哪些数据、何时、在哪台机、并行度多少"。
- 实现：把计算图编译成"任务组（group）+ 流水线阶段（stage）"，
  组间用队列衔接 → 内存有界、长尾可控、可弹性扩缩容；
  对 Spark GraphX/Bipolar（同类控制驱动）继续优化 6.6×–35×（官方数据）。
- 与本课程的联系：PDOS 出品，**读它就是读"你对 Spark 不满的完整答案"**。

## 3. 谱系总结（记忆锚点）

| 系统 | 抽象 | 同步方式 | 押注 |
|---|---|---|---|
| MapReduce | 两层函数 | 作业级全量物化 | 容错与通用 |
| Dryad | 任意 DAG | 边即流/文件 | 表达力 |
| Spark | RDD+DAG | Stage 栅栏 | 内存通用 |
| Piccolo | 分区表 | 子区间锁+表屏障 | 迭代 ML |
| GraphX/PowerGraph | 顶点程序 | 超步 | 图 |
| Lightning | 固定计算图流水线 | 无全局同步 | 迭代流水线 |
| Millipipe | 控制驱动流水线 | 调度器主导 | 内存/长尾/弹性 |

## 4. 论文间脉络

- 收束本课数据并行主线（L02→L17→L18）：每一代都在修正上一代的"同步代价"与"表达-性能矛盾"。
- 与 L16 Kafka 对偶：Spark/Millipipe 是"批/迭代"的极限，Kafka Streams/Flink 是"流"的另一极，
  两者在"流水线执行"上概念汇合（算子流水线、反压）。
- 与 L14 事务/ML 交叉：Piccolo 的表 + 锁是"把数据库搬进数据并行框架"；
  对接 15-442/MLC：PS 与 AllReduce 之争（参数服务器 vs 集合通信）可追溯到 Piccolo。

## 6. 开源项目中的应用

- **GraphFrames/Neo4j（Pregel 变体 Giraph、GraphX on Spark）**：图处理工业线。
- **PS-Learning / Parameter Server /angel / 早期 XGBoost 分布式**：Piccolo 直系后代。
- **TensorFlow（图编译 + 流水线）、PyTorch FSDP / DeepSpeed（AllReduce 路线）**：
  PS vs AllReduce 的现代战场（对照 MLC/15-442）。
- **Spark 自身**：Adaptive Query Execution（AQE）= 把"控制驱动"回补进通用引擎。
