# L14 分布式事务与两阶段提交（2PC）

> 阅读：6.033 Chapter 9（Gray, *The Transaction Concept: Virtues and Limitations*）；
> 辅读：Helland, *Life beyond Distributed Transactions: an Apostate's Opinion* (CIDR 2007)；Percolator (OSDI 2010)
> 主线：单机事务 ACID 如何跨机重建——以及 2PC 那个致命缺陷。

## 1. 核心问题

- 事务 = 把"一串操作"变成"仿佛原子、隔离、持久"的整体（ACID）。
  单机靠 WAL + 锁 + MVCC（15-445 全课）。**跨机后**：
  各分片只能保证**本地**原子提交，需要一个协议把 N 个本地提交
  变成"要么全成要么全弃"——**原子提交（atomic commit）**问题。
- 注意与共识（L05/L08）区分：共识 = 对"值/顺序"达成一致（可在少数派故障下继续）；
  2PC = 对"提交与否"达成一致（**任何一台不投票都可能卡死**）。
  **共识比 2PC 强**，这也是"为什么用 3PC 也救不了 2PC 的阻塞"的根源。

## 2. 两阶段提交

- 角色：协调者（coordinator）+ 参与者（ cohorts，各分片的事务管理器）。
- **Prepare 阶段**：协调者广播"能提交吗？"→ 参与者**写 prepare 记录到 WAL 并锁住资源**，
  回 yes/no。
- **Commit 阶段**：全 yes → 广播 commit，参与者落 commit 记录、释放锁、ack；
  有 no → 广播 abort。
- 关键不变式：参与者一旦 voted yes，**必须无限期等待**最终裁决 → 阻塞点。

### 2.1 阻塞灾难（必考）
协调者在"已发出 commit 决定但部分参与者未收到"时崩溃 →
参与者握着锁既不敢提交也不敢回滚 → **整个数据库其他事务被拖死**。
- 3PC 引入 CanCommit/PreCommit + 超时猜测 → 仍需**故障检测 + 超时**，
  在异步模型下**无法同时保证安全与终止**（FLP 推论，L08）。
- 工程解：**阻塞时让新协调者从参与者处收集投票**重建决定
  （把"协调者状态"也持久化/共识化——这正是 Spanner 与 Percolator 的做法）。

## 3. 优化与现实变体

- **Presumed Abort/Commit**：少写一条日志的优化（未记录 = 隐含决定），
  减日志放大。
- **2PC on Raft**：把协调者状态放进一个 Raft 组 → 协调者崩溃由组内新 leader 续推
  → "阻塞问题"降级为"多数派存活问题"（etcd/TiDB 的 TSO + 事务层）。
- **Percolator**（2010，Bigtable 上做事务）：**无中心协调者**的 2PC 变体——
  每个数据自带 lock/write 列，提交 = 在"主列"上原子写 committed；
  事务自带恢复信息（谁在提交就能替它清锁）→ **去中心化 + 可恢复**。
- **Saga**（Helland 倡导）：长事务拆成一串本地事务 + 补偿动作，
  放弃隔离换可用性——Microservices 时代的默认选择。
- **柔性事务/TCC/最终一致消息（outbox + inbox）**：工程界对"跨服务 2PC 太脆"的回答。

## 4. 论文间脉络

- 上承 L10（隔离级别与线性一致正交）、L05（共识 vs 原子提交的强度差）。
- 下启 L15 Spanner = 2PC + Paxos + TrueTime 的全家桶；
  TiDB/CockroachDB 的事务层就是"Raft 之上重建 2PC + Percolator 式乐观锁"。
- 主线：可靠性（单机持久化）→ 复制到多机（共识）→ 事务跨机（原子提交）——
  本课三大支柱在此汇合。

## 5. 跨课程联系

- **15-445/15-721**：2PL（悲观）与 OCC（乐观）+ 死锁检测/超时/回滚，
  在跨机后全部要重新设计（网络 RTT 让"持锁等待"代价爆炸 → 倾向短锁 + 乐观）；
  MVCC 快照读 ↔ Percolator 的 start_ts 读旧版本。
- **6.S081**：WAL 的 prepare/commit 两阶段 fsync ↔ 文件系统的 crash atomicity；
  2PC 是"把单机 WAL 纪律推广到多机"。
- **自顶向下网络**：RPC 超时/重试（L01）决定参与者"yes 之后失联"的不确定性。
- **CS242/PL**：exactly-once 消息 = "事务 + 幂等"的另一种表述（对接 L16 Kafka）。

## 6. 开源项目中的应用

- **PostgreSQL/MySQL(InnoDB) XA**：经典 2PC，协调者在连接断开时阻塞（著名运维坑）。
- **TiDB**：Percolator 模型——TSO（单点授时）+ 乐观/悲观两模式 + 
  "事务自带恢复信息"清残留锁。
- **CockroachDB**：Hybrid Logical Clock + 异步 2PC（Raft 组各自即参与者，
  协调者状态可被任何 observer 恢复）。
- **Kafka 事务**（producer 原子写多分区，L16）、**Flink 两阶段提交 sink**
  checkpoint↔checkpoint 对齐（分布式快照驱动）。
- **Seata / Axon（Saga）/ Debezium outbox**：微服务柔性事务生态。
