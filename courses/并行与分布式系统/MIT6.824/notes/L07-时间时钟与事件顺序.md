# L07 时间、时钟与事件顺序

> 阅读：Lamport, *Time, Clocks, and the Ordering of Events in a Distributed System*, CACM 1978；
> Kulkarni et al., *Logical Physical Clocks and Consistent Snapshots in Globally Distributed Databases*（HLC, 2014）
> 主线：物理时间不可信 → 因果才是分布式里"时间"的本质 → 工程上把两者缝合。

## 1. 核心问题

- 分布式系统没有全局时钟。石英晶振漂移 ~10⁻⁶（每天数十秒），
  NTP 同步到几十毫秒，**"两点事件谁先发生"在物理时间上根本无法可靠回答**。
- Lamport 的洞见：**"之前"不是物理概念而是逻辑概念**——我们真正需要的
  只是事件的全序/偏序，以便系统对"历史"达成一致。

## 2. Lamport 逻辑时钟（1978）

- 时钟公理：若 a → b（a 因果先于 b），则 C(a) < C(b)。
- 实现规则：IR1 进程内事件递增计数器；IR2 消息携带时间戳，
  接收方取 `max(本地, 消息)+1` 后投递。
- **只能保证"因果序 ⇒ 时间戳序"，反过来不成立**：
  并发事件也会拿到大小（两个时钟 1/2 的进程互发消息被强行定序）。
- 意义：给出第一个不依赖物理时间的"全局快照"工具，
  为互斥算法（中央批准式）、分布式快照（Chandy-Lamport，对接 CS149/大数据 checkpoint）奠基。
- 遗留问题：向量时钟（VVC）能精确刻画因果偏序，但 O(N) 大小 →
  大规模系统用不起，于是有了"因果 ≈ 物理"的工程折中。

## 3. HLC：逻辑 + 物理的缝合（CockroachDB 的引擎）

- 目标：时间戳既**与墙钟近似同步**（人可读、可做 TTL/GC），
  又**尊重因果序**（不骗系统）。
- 结构：`<pt（物理毫秒）, l（逻辑反推值）, n（同毫秒计数）>`。
  规则：发送方若本地物理超前对端，对端把自己的物理"推着走"
  （pt' = max(pt, 对端 pt)，相等时 l 递增）。
- 结果：**因果一致 + 误差 ≤ 时钟漂移上界 ε**。这正是 L15 Spanner 用
  TrueTime 买到的性质（用原子钟硬件），也是 CockroachDB 用 HLC + 
  "不确定性窗口"以纯软件达到的路线。
- 对照：NTP 只保证"接近"，不保证因果；TrueTime 只保证"区间"，不用逻辑位；
  HLC 是"没有硬件预算时的第三种答案"。

## 4. 时间谱系总结（本讲记忆锚点）

| 方案 | 给出什么 | 代价 | 代表 |
|---|---|---|---|
| 物理墙钟 | 近似真实时间 | 无因果保证 | 单机应用 |
| Lamport | 因果相容的全序 | 并发被任意定序 | 互斥/检测算法 |
| 向量时钟 | 精确因果偏序 | O(N) 开销 | Dynamo 的 siblings |
| HLC | 因果 + 近似物理 | ε 内模糊 | CockroachDB |
| TrueTime | 物理时间 + 已知误差区间 | GPS/原子钟硬件 | Spanner |

## 5. 论文间脉络

- 上游：L05/L06 的 term 就是一个"粗糙的 Lamport 时钟"（单调、可比较、防旧主）。
- 下游：L09 Dynamo 的向量时钟处理并发写；L15 Spanner 用 TrueTime + 2PC
  给出外部一致性（external consistency = 事实上的因果序）；
  L10 线性一致性讨论里"读到的值是否过期"本质是时间问题。
- 主线位置：**可靠性（复制）之后，一致性需要"顺序"来定义，顺序需要"时间"**。

## 6. 跨课程联系

- **6.S081**：内核用序列号/版本化解决并发对象可见性（如 RCU 的 grace period
  本质是"判定所有旧读者已退出"——与快照/因果同一族问题）。
- **CS149**：批量同步并行（BSP）的超步编号 = 进程全局的 Lamport 时钟。
- **15-445**：事务提交顺序 = 可串行化调度问题；MVCC 的 read timestamp
  与 HLC 一样需要"既有序又近似物理"。15-445/15-721 里 Spanner 的
  "commit wait = 2ε"会直接用到本讲。
- **自顶向下网络**：TCP 时间戳选项（RTTM/PAWS）用物理时间防旧包/绕回，
  是工程界对"时钟不可信"的另一类回应（用单调性而非绝对值）。

## 7. 开源项目中的应用

- **CockroachDB**：HLC + 500ms 最大时钟偏移假设；读穿越"不确定性窗口"需重试
  （文档里的 Uncertainty Restart 即本讲内容）。
- **MongoDB（HLC 用于因果一致性会话）**、**TiKV（PDO 中心化分配物理时间戳，
  第三条路线：用单点预取换全局单调，5.0 起 Hybrid Logical Clock 混合）**。
- **Kafka**：log 的 offset 是"流内 Lamport 时钟"；Kafka Streams 的
  event-time/watermark 处理乱序事件流（Flink 同）。
- **Spanner 的 TrueTime API、AWS Time Sync（Chronext/PTP 给云 VM 亚毫秒同步）**。
