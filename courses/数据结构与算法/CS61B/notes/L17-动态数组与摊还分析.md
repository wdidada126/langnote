# L17 动态数组与摊还分析（ResizingArraySLList / AList）

> 对应 spring2024 L17：几何扩容、摊还 O(1)。阅读：Hug 笔记 "Resizing Arrays"、CLRS 17.1（摊还分析）。

## 1. 核心概念

- **问题**：数组定长，`addLast` 满了怎么办？copy 全部到更大数组——单次 Θ(n)，但**总账**是摊还 Θ(1)。
- **关键实现（AList 模式）**：
  ```java
  public class ArraySeq61B<Item> {
      private Item[] items;
      private int size;
      @SuppressWarnings("unchecked")
      public ArraySeq61B() { items = (Item[]) new Object[8]; }
      public void addLast(Item x) {
          if (size == items.length) resize(items.length * 2); // 几何扩容！
          items[size++] = x;
      }
      private void resize(int cap) {
          Item[] n = (Item[]) new Object[cap];
          System.arraycopy(items, 0, n, 0, size);
          items = n;
      }
      public Item get(int i) { return items[i]; } // Θ(1) 随机访问
  }
  ```
- **泛型数组限制**：不能 `new Item[8]`（擦除后无法知运行时类型），惯用 `(Item[]) new Object[cap]` + `@SuppressWarnings`。
- **为什么必须乘常数而非 +1**：+k 扩容的 n 次 add 总成本 Θ(n²/k)；几何扩容总成本 n + n/2 + n/4 + … < 2n。

## 2. 摊还分析三法（CLRS 17.1 对应）

| 方法 | 思路 | 用于动态数组 |
| --- | --- | --- |
| 聚合法 | n 次操作总成本 / n | Σ2ⁱ < 2n ⇒ 摊还 < 2 |
| 记账法 | 给 add 收 3 元"信用"：1 存自己、2 付将来两次复制 | 每次复制费用已被信用覆盖 |
| 势能法 | Φ = 2·extra(未满槽数)；cᵢ = 实际 + ΔΦ | 扩容 c=2·2ᵏ-(2ᵏ-2·2ᵏ⁻¹)…≤3 |

- **缩容陷阱**：`removeLast` 若在 n/2 阈值直接减半会"抖动"（thrashing）：反复 add/remove 每次 Θ(n)。解法：阈值与扩容点错开（如 size < cap/4 才缩到 cap/2）。JDK `ArrayList` 干脆不缩容（只 grow），`ArrayDeque` 也只在增长时 resize。

## 3. 复杂度视角

| 操作 | 最坏单次 | 摊还 | 说明 |
| --- | --- | --- | --- |
| addLast | Θ(n)（扩容那一次） | **Θ(1)** | 几何倍增 |
| removeLast | Θ(1) | Θ(1)（有滞后缩容时） | |
| get/set | Θ(1) | Θ(1) | 保持数组核心优势 |
| addFirst | Θ(n) | Θ(n) | 动态数组救不了头插——那是 DLList/ArrayDeque 的活 |
| n 次 add 总计 | — | Θ(n) | 复制总字节 < 2× 最终大小 |

## 5. 跨课程联系

- **CS61A**：61A 从不"原地 resize"——函数式数据结构以共享结构换取不可变性，代价模型不同（持久化列表 cons 永远 O(1)，因为根本不复制）。
- **6.006/CS170**：6.006 不教摊还（放在 6.046/CS170 的 splay/并查集）；势能法是 61B 里最接近"算法设计与分析正式课"的一讲。
- **CSAPP**：`realloc` 与 glibc malloc 对大块内存的 mremap 让倍增扩容可能零拷贝（改页表不改数据）——理论摊还 O(1) 在系统层的进一步优化。
- **DDCA/OS**：文件系统块分配按 extent 几何增长（ext4），内存分配器 arena 倍增——"倍增 + 偶发复制"是全系统模式。

## 6. 开源项目应用

- **JDK**：`ArrayList.grow`：`newCapacity = oldCapacity + (oldCapacity >> 1)`（×1.5，比 ×2 更利于 GC 复用与 memcpy 总量 3n）；`StringBuilder` 同款倍增，这就是循环 `+=` 字符串 O(n²) 的解药。
- **RocksDB/LevelDB**：memtable 容量阈值触发 flush 成不可变 SST——"写满就整体搬迁"的动态数组哲学放大到磁盘层。
- **Git**：`nth_bloom`、pack-index 内存缓冲按倍增增长；git 对象写入前的 index 条目数组即典型 AList。
- **Lucene**：`PagedBytes`、文档缓冲按页倍增，页大小对齐缓存。
