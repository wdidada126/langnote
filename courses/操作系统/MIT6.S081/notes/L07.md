# L07 日志与崩溃一致性（Log）

> 6.1810 Lecture 7 · 阅读：xv6 book "Crash consistency" 节；kernel/log.c、fs.c 日志路径
> 断电不是异常，是常态。文件系统必须假设：任何一次磁盘写入都可能"只完成一半"。

## 1. 核心概念

### 1.1 问题模型：撕裂写（torn write）
磁盘一次写一个 512B 扇区，扇区内容要么全对要么全错；但**扇区之间没有原子性**。
`mkdir` 要改 5 块：位图 ×2、父目录、inode 块、新目录数据块。断电在中间 ⇒
"半完成操作"：要么 inode 有但数据块没分配，要么目录项指向已回收的 inode。
一致性 = 崩溃后磁盘状态等价于"操作要么没发生、要么完整发生"。

### 1.2 fsck 为什么死了
ext2/FFS 时代靠重启后全盘扫描（fsck）重建一致性：正确但慢（TB 盘分钟级），
且 fsck 自己崩溃会造成二次损坏。现代文件系统全部转向**写前日志（WAL/write-ahead logging）**：
先把"意图"以可恢复形式落盘，崩溃后重放（redo）即可，无需全扫描。

### 1.3 WAL 协议（xv6 版）
1. 修改前：把原块内容复制进内存 log 缓冲；
2. `commit`：① log 块 + ② log header（记录数量与块号）③ 写屏障 ④ 原位置写回 ⑤ 更新磁盘 head——
   顺序即正确性：barrier 保证任何"数据已改"的状态下 log 一定先落盘，重放可安全 redo。
关键不变式：**只有 log 完整落盘的修改才会触碰原块；原块写完才移动 head**。

### 1.4 redo vs undo，checkpoint 在哪
xv6 只有 redo（重放已提交事务）。数据库（15445/ARIES）还有 undo 未提交事务与
checkpoint 缩短恢复时间——思想同源：日志是"事实"，主存是"缓存"。
写屏障（`wbarrier`/cache flush）是日志协议的命门：磁盘内部缓存重排序会摧毁顺序假设。

### 1.5 fsync 语义与"撒谎的驱动"
POSIX `fsync` 承诺数据+元数据持久；历史上磁盘/RAID 缓存不刷导致"假 fsync"（Huang et al., USENIX ATC 2015 对 Linux 主流文件系统持久性保证的测量研究，具体标题待核实）。
日志设计的下游问题是**接口诚实性**，L11 journal 讲会再展开。

## 2. xv6 代码走读要点
- `kernel/log.c: log_write()`：块进 log（每块最多记一次）；`begin_op/end_op`：用 `log.out` 引用计数支持事务嵌套（open→write→close 一个事务）。
- `commit() → write_log() → log.sync` 三连：`log.buf[]` 数据 → `log_header`（magic+count+block[]）→ `wbarrier` → 原块 → `read_head/write_head` 移动 head。
- `install()/replay`：开机 `log.recover` 比较 `log->head` 与 `log->size`，把未提交完的 log 重放到磁盘——lab-fs 的 kv 日志正是它的简化复刻。
- `kernel/fs.c` 里所有 `bwrite` 之前都有 `log_write(bp)`（`iupdate/ writei/balloc` 路径），漏一处就是一个崩溃 bug——lab 里 `bit.c` 练习会让你体会。

## 4. 开源项目应用
- **Linux**：jbd2（ext4 日志层）是 xv6 log.c 的工业版——有事务、checkpoint 队列、异步提交；XFS 自研 log；Btrfs/ZFS 走 cow+checkpoint 树路线（无传统日志）。
- **RocksDB/LevelDB**：MANIFEST + WAL 完全是本课模型；15445 的 LogStructured 项目同理。
- **验证系统**：经证明的一致性实现见 FSCQ（L09）；工业侧 Android F2FS 的日志模式直接对应 flash 顺序写特性。
