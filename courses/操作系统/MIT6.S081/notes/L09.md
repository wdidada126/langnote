# L09 日志式文件系统的深化（Journal）

> 6.1810 Lecture 9 · 阅读：journaling 讲义；Shapiro & Bernstein《Designing a File System for the Non-Volatile Era》(ACM TOCS 2023)
> L07 给了最小 WAL；本讲把"journal"放到整个设计空间里比较：shadow paging、redo、undo、ordering。

## 1. 核心概念

### 1.1 两种古老方案：journaling vs shadow paging
- **Shadow paging**（旧 FFS/VAX）：复制要改的块到新位置，最后原子切换一个指针。
  优点无重放；缺点：写放大 + 碎 + 难并发（一棵影子树怎么多人一起改？）。
- **Journaling/redo log**（xv6、ext3/4、NTFS）：先记"将改成什么"，崩溃后重放。
  需要屏障与双写（先写 log 再写原块 ⇒ 元数据一度存在两份）。
现代主流是 journaling 或它的 COW 变体（ZFS checkpoint 树可视为"shadow paging 的可扩展复活"）。

### 1.2 日志里放什么：元数据日志 vs 全数据日志
ext4 默认只 journal 元数据（fast commit 又进一步）：数据块不进日志，快但崩溃后文件内容
可能与"已提交的 rename"不一致。三种模式 `data=journal/logged/writeback` 就是一根性能-一致性滑杆。
数据库默认"数据进 WAL"，文件系统默认"数据不进"——两代工程师对同一取舍的不同答案。

### 1.3 ordering 才是崩溃一致性的全部
单块写原子 ⇒ 一切 bug 都来自"顺序"：
rename 必须晚于新 inode；数据必须早于"指向它的元数据"。
journal 用"日志整体先于目标块"强制一批顺序；journal 之外的数据块仍要显式 barrier（ext4 的 `fsync` 语义演化即是一部 barrier 血泪史）。
Mohan 的 ARIES 论文与 L07 的 wbarrier 在此汇合成统一语言：**happens-before 的持久化**。

### 1.4 崩溃语义的再定义：crash-only
"crash-only 软件"（Marsh & Scott, HotOS 2007）：测试的崩溃路径与恢复路径合一才可信。
FSCQ/Jeitner 一条线（见 papers.md）把崩溃一致性变成**可验证/可委托**的问题：
Jeitner《Delegating Consistency to Hardware》(HotOS'23) 主张让存储硬件保证块间顺序，
文件系统一致性协议随之大幅简化——协议复杂度从软件搬到设备接口。

### 1.5 验证文件系统：FSCQ 与下游
FSCQ（OSDI'13）证明"崩溃后行为 ≡ 某个抽象规范"；FizzBee/Laminar 等后续把可验证性
带进真实代码。读 xv6 log.c 后再读 FSCQ 规范，会明白"重放不变式"原来可以写成定理。

## 2. xv6 代码走读要点
- `kernel/log.c: write_log()` 与磁盘 `superblock` 的 `logstart/logsize`：log 是保留块区，容量即最大事务——"日志大小 = 崩溃重放停顿预算"，ext4 journal 大小的取值逻辑相同。
- `log->head` 只在原块全部写完后更新（`commit()` 末行）：这一行的前后顺序就是 redo 协议全部；试着把两行对调并解释 lab-fs 测试为何失败。
- `kernel/bio.c` 的 dirty 标志与 log 的关系：`bwrite` 在事务内只入 log、事务外才直写——`log_write` 判断 `int log.out` 的分支。
- 思考题：`trunc()` 释放数百块时事务有多大？（xv6 直接吃下，ext4 有事务大小上限与"大事务拆分"。）

## 4. 开源项目应用
- **Linux**：jbd2 的 handle/commit 两阶段；XFS log 的 item 粒度（只日志改动字段而非整块）；btrfs 的 tree-log（按目录分事务）。
- **RocksDB**：WAL + MANIFEST + 版本 set，三件套与"journal + superblock"逐字对应。
- **F2FS 与崩溃测试**：闪存档 log-structured 实现；工业界用差分测试框架（如 bftrace、fsck 对比法）检验崩溃一致性——"测试即规格"的延伸。
