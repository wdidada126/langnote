# L15 RCU 与无锁读（Read-Copy-Update）

> 6.1810 Lecture 15 · 阅读：McKenney《What is RCU, Fundamentally?》(ACM Queue 2012)；lab-thread
> Linux 内核最常被误用的同步原语：读端零指令开销，代价全在写端与回收时机。

## 1. 核心概念

### 1.1 问题：读者不能等，写者不能删
内核数据结构（路由表、模块链表、tasklist）读远多于写。rwlock 的读者计数本身是
争用点：每核cacheline ping-pong。理想：**读端不加锁不计数**，写端复制-更新-发布。

### 1.2 回收是唯一的真问题
RCU = Read-Copy-Update + **grace period（宽限期）**：
写者更新指针后，旧对象不能立即 free——必须等"所有可能在引用它的读者都离开"。
判定"都离开"的方式决定流派：
- **epoch-based**：每 CPU 记录进入/离开临界区的 epoch，写者推进全局 epoch 等一轮静默状态（xv6 lab-thread 方案）；
- **hazard pointer**（Michael, ASPLOS'04）：读者声明"我正在看这个指针"到私有槽，写者回收前扫描所有槽；
- **reference counting**：正确但读者要写共享计数——争用回来了。

### 1.3 内存序是暗线
`rcu_assign_pointer` 需要**发布语义**（写对象先于写指针）；`rcu_dereference` 需要
获取语义 + 抑制编译器投机（历史上 DEC Alpha 的弱序咬过 RCU）。
读端临界区 = `rcu_read_lock()`（关抢占）… `rcu_read_unlock()`；宽限期 = 每 CPU 至少一次静默。

### 1.4 seqlock：RCU 的近亲
读者重试式序列号锁：读时记 seq，读后再校验，变了就重来。
适合"读者可重试"的小数据（xv6/内核的时间戳、jiffies）。与 RCU 共享"读者零争用"哲学，
但 RCU 管对象生命周期，seqlock 不管——"发布易，回收难"。

### 1.5 lab-thread：用户级 RCU
xv6 lab-thread 让你在用户态多线程里实现带 RCU 保护的 reader-writer 数据集：
读者只读写 per-thread 状态，写者换版本 + 等 grace。通过 `racecheck`（模拟调度器）
穷举交错找 bug——**模型检验式测试**，与 6.824 的 test harness 一脉。

## 2. xv6/lab-thread 代码走读要点
- `kernel/proc.c` 遍历进程表的锁 vs 讨论：为何 RCU 化 `tasklist` 是 Linux 真实做法（`rcu_read_lock` + `list_for_each_entry_rcu`）。
- lab-thread 骨架 `main.c`：`begin_valid(tid)`/`advance_epoch()` 式的 per-CPU epoch 写回全局 + `synchronize()` 轮询——回收安全性的全部代码。
- hazard pointer 练习：`hp_store()/hp_clear()` 与 `reclaim()` 的扫描；思考为何 HP 读端比 RCU 多一次写（store 到私有槽）。
- `racecheck`：可控调度器 + 原子操作模拟——写并发代码时"测试穷举 > 祈祷"。

## 4. 开源项目应用
- **Linux**：`kernel/rcu/tree.c`（Tree RCU 分层收敛宽限期）、`synchronize_rcu()`  everywhere；`call_rcu()` 异步回收；用户态 liburcu。
- **DPDK/Seastar**：per-core 单写者 + epoch 回收，把 RCU 思想推入网络数据面（接 L21）。
- **Go runtime**：GC 的写屏障 + 三色标记处理指针集合的"宽限期"问题——RCU 的垃圾回收放大版。
