# L06 文件系统（File System）

> 6.1810 Lecture 6 · 阅读：xv6 book Ch.9；kernel/fs.c、bio.c、log.c 初览；Lab: fs
> 磁盘只有"读块/写块"，"文件"是软件凭空造出来的概念——本讲拆解这层魔术。

## 1. 核心概念

### 1.1 三级抽象：fd → open 文件 → inode
- 每进程 fd 表：`struct file` 指针数组（dup/fork 的共享语义由此实现）；
- 全局打开文件表：引用计数 + 读写偏移（父子进程 fork 后共享偏移，dup 亦然）；
- inode 表：每 inode 一份，引用计数保护，采用双锁协议（`struct spinlock ilock` 保护磁盘字段 + `struct sleeplock lock` 保护内存字段，详见走读）。
三层各司其职：fd 是"我的把手"，open 文件是"我这次打开的状态"，inode 是"磁盘上那个东西"。

### 1.2 磁盘上的三件套
superblock（魔数/大小/free 起始位）、位图块（块与 inode 的空闲标记）、inode 块 + 数据块。
inode：类型 + 引用计数 + 大小 + 12 直接块 + 1 一级间接块（xv6 最大约 288KB+32 间接 ≈ 268KB；
再高要二级间接——Linux ext2 有三级，正是"间接块链"的推广）。
目录 = 特殊文件：`(name, inum)` 数组，`.` 与 `..` 靠硬链接自指——"树"其实是图，靠约定不成环。

### 1.3 硬链接与引用计数
`link()` 只增 `ref`；`unlink()` 减一，为 0 才释放块。fd 关完但链接还在 ⇒ 文件还在；
链接删了但 fd 还开着 ⇒ 数据保留到最后一个引用消失。Linux 的 `unlinkat` 与匿名 tmpfile 即此语义。

### 1.4 namei：路径解析
`namei("a/b/c")` 从根 inode 出发，逐段在当前目录里 `namecmp` 找 inum，`iput` 旧的、`ialloc` 新的。
所有路径相关系统调用（open/mkdir/unlink/chdir）都要过 namei；`chmod/chown` 只操作文件不解析路径。

### 1.5 块缓存与写策略
`bio.c`：512 项 hash(table[blockno]) + LRU 空闲列表的块缓存——同一块多次读不重复下盘。
写回（write-back）vs 写透：`bwrite` 只写缓存标记 dirty，commit 时才下盘——崩溃一致性问题（L07）就此埋下。

## 2. xv6 代码走读要点
- `kernel/fs.c` 中 `fdalloc/fdiput/filedup/fileclose/close` 三层表的全部操作；`sysfile.c` 对应有 `sys_dup`。
- `kernel/fs.c: namei()` + `iput()`：注意 `nameiparent` 处理最后一段（mkdir/create 要拆开父目录）。
- `kernel/bio.c: bread/bwrite/brelse`：`buf->locked` 自旋等待——sleep lock 包住临界区的典型；`bget` 回收 LRU。
- `kernel/log.c: log_write/begin_op/end_op/commit`：本讲先当黑盒，L07 打开——所有元数据修改都走 `bwrite` 进 log。
- `kernel/sysfile.c: sys_open → namei → openi/createi`；`sys_write → filewrite → (管道|磁盘|控制台)` 的三大分支。

## 3. 跨课程联系
- **CSAPP（Ch.10）**：CSAPP 的 `open/read/write` 与 short count 处理在这里获得内核解释——短读不是 bug，是 Unix 接口契约。
- **DDCA/CS61C**：磁盘几何、块设备顺序访问模型是"为什么用间接块与位图"的物理原因。
- **MIT 6.824 / 15445**：6.824 的 Raft 快照 + log ≈ 文件系统的 journal + checkpoint；15445 BufferPool 的 disk manager/page guard 与 xv6 `bread` 的双缓冲是同一问题（缓存 + 并发 + 回写）。
- **NJUOS/CS162/HITOS**：NJUOS 的 tmpfs 练习对照 inode 表实现；CS162 用 LFS 讲"把随机写变顺序写"的另一路线（本课 L14 继续）；HITOS 对照 Linux VFS——xv6 `struct file` ≈ `struct file`，xv6 inode ≈ `struct inode`，中间还隔着一层 `dentry`。

## 4. 开源项目应用
- **Linux**：VFS → ext4 → block layer → SCSI/NVMe 的完整链条就是 xv6 fs.c 的放大版；`struct address_space` 页缓存替代了 xv6 的 `buf[]` 数组。
- **FreeRTOS/Zephyr**：Zephyr FS 层（NVS/LittleFS）面向 flash 的磨损约束，inode 简化为键值对，对照理解"介质决定文件系统形态"。
- **seL4/CAmkES**：文件系统作为独立 server 进程通过 IPC 提供 `read/write`——回到 L20 IPC 话题的活教材。

## 6. 自检测验
- fd→file→inode 三层抽象：哪种共享（dup/fork/两进程同文件）各加 ref 在哪一层？
- namei 每步走一个路径分量：它 bread 哪些块、如何维护"当前目录"？
- stat 能从缓存 inode 直接回答 size，读内容为什么必须再过一次 bread/brelse？
- 硬链接下 rm 为什么不销毁已打开文件的数据？引用计数在哪一步减？
- O_TRUNC / O_APPEND 的语义差异在哪一层实现：file 还是 inode？
- 用 projects/minifs 画出 open("a/b") 失败与成功各bread哪几个块的时序图。
