在Spring中,DefaultListableBeanFactory的beanDefinitionNames变量中保存了所有已注册的Bean定义的名称。
其中的Bean名称值主要来源于以下几个方面:
1. 配置类上的@Bean方法名
例如:
```java
@Bean
public UserService userService() {
  // ...
}
```
userService会作为一个Bean名称。
2. <bean>元素的id或name属性
例如:
```xml
<bean id="userService" class="...">
</bean> 
```
id或name会成为Bean名称。
3. @Component等注解的value值
例如:
```java
@Component("userService")
public class UserService {

}
```
4. 其他生成Bean名称的命名策略
例如@Bean方法名生成或全限定类名生成等。
5. BeanDefinitionRegistryPostProcessor自定义注册的Bean定义
以上都是Bean名称的来源。最终都会存入DefaultListableBeanFactory的beanDefinitionNames变量中。
我们可以通过这些名称访问所对应的Bean定义信息。

问题：
DefaultListableBeanFactory的beanDefinitionNames是List， requestMappingHandlerMapping是如何添加到里面的


在Spring MVC中,RequestMappingHandlerMapping这个Bean的名称是如何被添加到DefaultListableBeanFactory的beanDefinitionNames中的呢?

主要过程是:

1. 在Spring MVC默认配置类WebMvcConfigurationSupport中,通过@Bean注解定义了RequestMappingHandlerMapping:

   ```java
   @Bean
   public RequestMappingHandlerMapping requestMappingHandlerMapping() {
     //...
   }
   ```

2. 在Spring容器启动时,ConfigurationClassPostProcessor会解析该配置类。

3. 它会以方法名"requestMappingHandlerMapping"作为Bean名称,注册该Bean定义。

4. 然后会调用BeanDefinitionRegistryPostProcessor接口的postProcessBeanDefinitionRegistry方法。

5. 这个方法在DefaultListableBeanFactory中实现,会把注册的Bean定义名称添加到beanDefinitionNames集合中。

6. 这样RequestMappingHandlerMapping的名称就被添加到了beanDefinitionNames中。

总结一下:

1. 通过@Bean方法定义,名称为方法名
2. ConfigurationClassPostProcessor解析注册
3. DefaultListableBeanFactory的postProcessor接口实现将名称存入beanDefinitionNames
4. 这样名称就被记录下来了



问：PathMatchConfigurer类作用
在Spring MVC中,PathMatchConfigurer用于配置路径匹配参数,主要功能包括:
1. 设置路径匹配是否区分文件扩展名。
2. 设置路径分割符,默认是'/'。
3. 设置是否自动后缀路径的点号,如"account." 自动补全为 "account.*"。
4. 设置路径匹配参数的缓存大小。
示例代码:
```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

  @Override
  public void configurePathMatch(PathMatchConfigurer configurer) {
    configurer
      .setUseRegisteredSuffixPatternMatch(true)
      .setUseTrailingSlashMatch(false)
      .setPathSeparator(".");
  }

}
```
这允许自定义路径匹配的各种细节,比如:
- 是否区分文件扩展名
- 使用自定义分隔符
- 是否自动补全点号
等等。
这样可以更灵活地调整路径匹配策略,实现RESTful API定制。

这些类都是Spring MVC中用来注册各种组件的注册类,它们的联系与区别总结如下:

联系:

- 都实现了一种组件的注册,比如视图解析器、视图控制器等
- 都将组件注册到相应的注册中心,如ViewResolverRegistry
- 提供了REGISTRATION常量标记注册的组件类型

区别:

- 注册的组件类型不同
  - ResourceHandlerRegistry:资源处理器
  - ViewResolverRegistry:视图解析器
  - ViewControllerRegistry:视图控制器
- 注册方式也不完全相同
  - 某些通过继承,某些通过组合注册中心

作用:

- ResourceHandlerRegistration:注册静态资源处理器
- ViewControllerRegistration:注册视图控制器 
- UrlBasedViewResolverRegistration: 注册基于URL的视图解析器
- 等等

综上,它们在注册流程上有共性,但针对不同组件类型,职责明确,组合起来服务于Spring MVC。

@CompontScan spring源码分析

@Controller修饰的类是如何被注册到Spring IOC容器中的,主要通过@ComponentScan注解驱动的过程:

1. @ComponentScan会被解析为一个Bean定义扫描器ComponentScanAnnotationParser
2. 这个扫描器包含了类解析器ClassPathBeanDefinitionScanner
3. 在扫描指定基础包时,解析器会找到被@Controller修饰的类
4. 然后利用委托的ScopeMetadataResolver解析注解元数据
5. 得到一个Controller作用域的Bean定义,并生成默认的Bean名称
6. 最后注册这个Bean定义到容器中,默认的BeanNameGenerator会将类名作为Bean名  

主要的类:
- ComponentScanAnnotationParser:扫描器
- ClassPathBeanDefinitionScanner:类解析器 
- AnnotationScopeMetadataResolver:注解解析器
流程:
- 扫描类->找到Controller类->解析注解->生成Bean定义->注册Bean
所以@ComponentScan通过类解析机制,自动识别并注册被@Controller标注的Bean。

org.springframework.web.servlet.handler.AbstractHandlerMethodMapping.MappingRegistry#validateMethodMapping()

在 Spring 框架中，请求 URL 到具体处理方法的映射是通过 `HandlerMapping` 接口的实现类完成的。其中，`AbstractHandlerMethodMapping` 是一个抽象类，它提供了默认的映射方法实现，并定义了一个名为 `validateMethodMapping` 的方法，用于检测处理方法的映射是否存在冲突。
具体来说，当你在一个 `@Controller` 中定义了两个相同的 URL 映射时，`AbstractHandlerMethodMapping` 的子类会在应用程序启动时调用 `validateMethodMapping` 方法，并抛出 `IllegalStateException` 异常，表示存在 URL 映射冲突。该异常会被 Spring MVC 框架捕获，并在应用程序启动失败时输出错误日志。
在 `AbstractHandlerMethodMapping` 的实现类中，`validateMethodMapping` 方法会遍历所有的处理方法，检查它们的 URL 映射是否存在冲突。如果存在冲突，则会抛出异常。具体的实现代码如下所示：
```
@Override
protected void validateMethodMapping(Method method, HandlerMethod handlerMethod, Map<RequestMappingInfo, HandlerMethod> mappingRegistry) {
    RequestMappingInfo requestMappingInfo = createRequestMappingInfo(method);
    HandlerMethod existingHandlerMethod = mappingRegistry.get(requestMappingInfo);
    if (existingHandlerMethod != null && !handlerMethod.equals(existingHandlerMethod)) {
        throw new IllegalStateException("Ambiguous mapping. Cannot map '" + handlerMethod.getBeanType().getName() + "' method \n" +
                handlerMethod + "\nto " + requestMappingInfo + ": There is already '" +
                existingHandlerMethod.getBeanType().getName() + "' bean method\n" + existingHandlerMethod +
                " mapped.");
    }
}
```
在这个例子中，我们看到 `validateMethodMapping` 方法的实现代码。该方法会根据处理方法创建一个 `RequestMappingInfo` 实例，并从映射注册表中获取已经存在的处理方法。如果已经存在的处理方法与当前处理方法不同，且它们的 URL 映射相同，则会抛出异常，表示存在 URL 映射冲突。
总之，Spring MVC 框架在应用程序启动时会检查 URL 映射是否存在冲突，并在发现冲突时抛出异常。这样做可以确保应用程序能够正常处理请求，并避免 URL 映射冲突带来的问题。

问题：
spring mvc 404，或者调用@Controller修饰的某个类的流程

404对应的handler
org.springframework.boot.autoconfigure.web.servlet.error.BasicErrorController#error(HttpServletRequest)

当一个请求到达 Spring MVC 应用程序时，Spring MVC 框架会根据请求的 URL 和处理方法的映射关系，将请求分发给对应的处理方法进行处理。如果找不到对应的处理方法，就会返回 404 错误。

以下是 Spring MVC 框架处理请求的流程，从 Spring 5.2.9 源码的角度来解释：

1. 首先，当一个请求到达 Spring MVC 应用程序时，它会被 `DispatcherServlet` 类捕获。`DispatcherServlet` 是 Spring MVC 框架的核心组件之一，它是一个 Servlet，负责接收 HTTP 请求并将它们分发给对应的处理方法进行处理。
2. `DispatcherServlet` 会将请求分发给 `HandlerMapping` 接口的实现类，以获取请求对应的处理方法。在 Spring MVC 框架中，`HandlerMapping` 负责将请求 URL 映射到具体的处理方法。在 Spring 5.2.9 中，`HandlerMapping` 的实现类有 `RequestMappingHandlerMapping`、`SimpleUrlHandlerMapping` 等。
3. `HandlerMapping` 实现类会根据请求 URL 查找对应的处理方法，并返回一个 `HandlerExecutionChain` 对象。`HandlerExecutionChain` 包含了处理方法及其所需的拦截器列表。
4. `DispatcherServlet` 会将 `HandlerExecutionChain` 对象传递给 `HandlerAdapter` 接口的实现类，以执行处理方法。在 Spring MVC 框架中，`HandlerAdapter` 负责执行处理方法，并将处理结果返回给客户端。在 Spring 5.2.9 中，`HandlerAdapter` 的实现类有 `RequestMappingHandlerAdapter`、`SimpleControllerHandlerAdapter` 等。
5. `HandlerAdapter` 实现类会执行处理方法，并返回一个 `ModelAndView` 对象。`ModelAndView` 包含了处理结果及其所需的视图名称和模型数据。
6. `DispatcherServlet` 会将 `ModelAndView` 对象传递给 `ViewResolver` 接口的实现类，以获取视图。在 Spring MVC 框架中，`ViewResolver` 负责将视图名称解析为具体的视图对象。在 Spring 5.2.9 中，`ViewResolver` 的实现类有 `InternalResourceViewResolver`、`FreeMarkerViewResolver` 等。
7. `ViewResolver` 实现类会根据视图名称查找对应的视图，并返回一个 `View` 对象。
8. `DispatcherServlet` 会将 `ModelAndView` 和 `View` 对象传递给 `View` 接口的实现类，以渲染视图。在 Spring MVC 框架中，`View` 负责将模型数据渲染到视图中。在 Spring 5.2.9 中，`View` 的实现类有 `InternalResourceView`、`FreeMarkerView` 等。
9. `View` 实现类会将模型数据渲染到视图中，并将渲染结果返回给 `DispatcherServlet`。
10. `DispatcherServlet` 会将渲染结果返回给客户端，完成请求处理。
需要注意的是，在上述流程中，如果 `DispatcherServlet` 找不到对应的处理方法，就会返回 404 错误。这通常是由于请求 URL 与处理方法的映射关系不匹配或处理方法不存在导致的。在这种情况下，你可以检查 `HandlerMapping` 的实现类是否正确配置，并确保处理方法的 URL 映射与请求 URL 相匹配。

`RequestMappingHandlerMapping` 类是 Spring MVC 框架中 `HandlerMapping` 接口的实现类之一，它负责将请求 URL 映射到具体的处理方法。`RequestMappingHandlerMapping` 类中的 `getHandler` 方法会根据请求 URL 查找对应的处理方法，并返回一个 `HandlerExecutionChain` 对象。

以下是 `RequestMappingHandlerMapping` 类中 `getHandler` 方法的代码：

```
@Override
protected Object getHandlerInternal(HttpServletRequest request) throws Exception {
    RequestMappingInfo mappingInfo = getMappingForRequest(request);
    if (mappingInfo != null) {
        HandlerMethod handlerMethod = getHandlerInternal(mappingInfo, request);
        if (handlerMethod != null) {
            return createHandlerExecutionChain(handlerMethod, mappingInfo, request);
        }
    }
    return null;
}
```

在这个方法中，`getMappingForRequest` 方法用于查找请求 URL 对应的 `RequestMappingInfo` 对象，它包含了请求 URL 和处理方法之间的映射关系。如果找到了 `RequestMappingInfo` 对象，则调用 `getHandlerInternal` 方法继续处理请求。
`getHandlerInternal` 方法会根据 `RequestMappingInfo` 对象和请求对象查找具体的处理方法，并返回一个 `HandlerMethod` 对象。如果找到了 `HandlerMethod` 对象，则调用 `createHandlerExecutionChain` 方法创建一个 `HandlerExecutionChain` 对象，并将 `HandlerMethod` 对象、`RequestMappingInfo` 对象和请求对象传递给它。
`createHandlerExecutionChain` 方法会创建一个 `HandlerExecutionChain` 对象，并将 `HandlerMethod` 对象、`RequestMappingInfo` 对象和请求对象设置为它的属性。然后，它会遍历所有的拦截器，将它们添加到 `HandlerExecutionChain` 对象的拦截器列表中。
最后，`getHandlerInternal` 方法会返回创建的 `HandlerExecutionChain` 对象，以供 `DispatcherServlet` 调用处理方法并执行请求处理。

`org.springframework.context.annotation.ClassPathScanningCandidateComponentProvider#isConditionMatch` 是 Spring 框架中的一个方法，用于判断指定的 Bean 候选组件是否满足指定的条件。
在 Spring 框架中，可以使用条件注解（Conditional）来定义某个 Bean 是否应该被创建。这些条件注解可以应用于注解在类或方法上的任何 Spring 注解，例如 `@Bean`、`@Component`、`@Configuration` 等。当应用程序上下文启动时，Spring 框架会根据这些条件注解来确定是否应该创建某个 Bean。
`org.springframework.context.annotation.ClassPathScanningCandidateComponentProvider` 是一个用于扫描类路径中的 Bean 候选组件的工具类。它可以扫描指定的包或类路径，并查找符合指定条件的 Bean 候选组件。
`isConditionMatch` 方法是 `ClassPathScanningCandidateComponentProvider` 类中的一个方法，用于判断是否应该创建某个 Bean。它接收一个 `AnnotatedTypeMetadata` 对象作为参数，该对象包含有关要创建的 Bean 类型的元数据信息。`isConditionMatch` 方法会检查这些元数据信息，以确定是否满足与之关联的条件注解。
例如，如果你有一个带有 `@Conditional` 注解的 Bean，它的值为 `MyCondition.class`，那么 `isConditionMatch` 方法将会检查是否存在一个名为 `MyCondition` 的 Spring `Condition` 实例，并调用它的 `matches` 方法来确定是否满足条件。
如果 `isConditionMatch` 方法返回 `true`，则说明 Bean 候选组件满足条件，可以被创建。否则，该 Bean 候选组件将被忽略，不会被创建。
需要注意的是，`isConditionMatch` 方法通常是在 Spring 应用程序上下文启动时调用的，用于确定哪些 Bean 应该被创建。如果你想要自定义 Bean 的创建过程，可以考虑实现自己的 `Condition` 类，并在需要的 Bean 上使用 `@Conditional` 注解来指定该条件。


org.springframework.beans.BeanMetadataElement接口作用？


BeanDefinitionHolder实现了BeanMetadataElement接口


在Spring框架中,org.springframework.beans.BeanMetadataElement接口表示一个Bean元信息元素。其主要作用是:

1. 该接口为Bean元信息提供基础模型,用于描述Bean的配置。
2. Spring中许多Bean元信息类都实现了该接口,例如Bean属性、构造器参数等。
3. 通过该接口,可以获取元信息元素的一些通用属性,如源注解、角色等。
4. 也可以判断一个元信息元素是否等效。
5. Bean定义配置中存储了许多实现该接口的Bean元信息类的实例。
6. 通过接口统一访问元信息,而不依赖具体实现。

示例:

```java
// 获取属性的名称 
BeanMetadataElement property = beanDefinition.getPropertyValues().getPropertyElement("name");
String propertyName = property.getSource();

// 判断是否等效
if (property.isEquivalent(otherProperty)) {
  // ...
}
```

总结:

BeanMetadataElement提供元信息元素的通用模型抽象,方便在Bean定义中统一访问和处理元信息,而不依赖具体的实现类。

FlashMapManager
说到FlashMapManager，就得先提一下FlashMap。
FlashMap 用于重定向Redirect 时的参数数据传递，比如，在处理用户订单提交时，为了避免重复提交，可以处理完post 请求后redirect 到一个get 请求，这个get 请求可以用来显示订单详情之类的信息。这样做虽然可以规避用户刷新重新提交表单的问题，但是在这个页面上要显示订单的信息，那这些数据从哪里去获取呢，因为redirect 重定向是没有传递参数这一功能的，如果不想把参数写进url(其实也不推荐这么做，url 有长度限制不说，把参数都直接暴露，感觉也不安全)， 那么就可以通过flashMap 来传递。只需要在redirect 之前， 将要传递的数据写入request （ 可以通过ServletRequestAttributes.getRequest() 获得） 的属性OUTPUT_FLASH_MAP_ATTRIBUTE 中，这样在redirect 之后的handler 中Spring 就会自动将其设置到Model 中，在显示订单信息的页面上，就可以直接从Model 中取得数据了。而FlashMapManager 就是用来管理FlashMap 的。

在Spring Boot中,org.springframework.boot.web.servlet.MultipartConfigFactory这个类的作用是用来创建MultipartConfigElement实例,以配置multipart文件上传所需的设置。

`org.springframework.web.method.support.ModelAndViewContainer` 类是 Spring MVC 框架中的一个重要组件，用于持有处理器方法的返回值和模型数据，同时提供一系列方法来处理视图解析和模型数据的处理。让我们对该类的源码进行详解：

1. 定义 `ModelAndViewContainer` 类：

        return this.view;
    }

    public boolean isRequestHandled() {

    }

    public void setRequestHandled(boolean requestHandled) {

    }

    // 省略其他方法...

2. ModelAndViewContainer 类的作用：

- `ModelAndViewContainer` 类用于持有处理器方法的返回值和模型数据，它在处理器方法返回时，会将返回值和模型数据保存在容器中，以便后续的视图解析和渲染过程使用。

- 该类提供了 `getModel()` 方法来获取 `ModelMap` 对象，`ModelMap` 是一个用于保存模型数据的容器，可以将数据以键值对的形式存储在其中。

- `setView()` 方法用于设置处理器方法返回的视图，视图可以是一个字符串（视图名称），也可以是一个 `View` 对象。

- `isRequestHandled()` 方法用于判断请求是否已处理。当设置为 `true` 时，表示请求已经处理完毕，后续不再需要进行视图渲染；当设置为 `false` 时，表示请求还需要进行视图渲染。

3. 源码解析：

在 Spring MVC 的请求处理过程中，当处理器方法返回时，返回值会被包装成一个 `ModelAndView` 对象，并交给 `ModelAndViewContainer` 类进行处理。

在 `DispatcherServlet` 中，有一个方法 `processDispatchResult`，其中会调用 `ModelAndViewContainer` 的相关方法来处理返回值和模型数据：

在Spring MVC中,LongTaskTimingHandlerInterceptor是一个拦截器,它的主要作用是:
1. 统计处理器方法的执行时间,计算长时间运行任务。
2. 如果请求处理超过指定时间,会记录warn级别的日志。
3. 可以设置长任务的超时时间阈值,默认为1秒。
4. 可用于检测 Controller 中执行时间过长的任务。

使用方式:

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

  @Override
  public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(new LongTaskTimingInterceptor());
  }

} 
```

这样就允许LongTaskTimingInterceptor统计所有处理器的执行时间。

如果出现超时任务,可以及时发现问题所在。

相比拦截器链自身的时间统计,它提供了更灵活的阈值设置等功能。
