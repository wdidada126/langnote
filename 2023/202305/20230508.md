Java 线程池提供了多种拒绝策略，如 AbortPolicy、CallerRunsPolicy、DiscardPolicy 和 DiscardOldestPolicy。如果这些预定义的拒绝策略不能满足需求，可以通过自定义 RejectedExecutionHandler 接口来实现自定义的拒绝策略。

下面是一个简单的自定义拒绝策略的示例代码：

```java
public class MyRejectedExecutionHandler implements RejectedExecutionHandler {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        // 自定义拒绝策略的实现逻辑
        System.out.println("Task " + r.toString() + " rejected from " + executor.toString());
    }
}
```

在上面的代码中，我们实现了 RejectedExecutionHandler 接口，并实现了 rejectedExecution() 方法。在这个方法中，我们可以自定义拒绝策略的实现逻辑，例如打印日志、将任务添加到队列中等。

下面是使用自定义拒绝策略的示例代码：

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2, // 核心线程数
    5, // 最大线程数
    1, TimeUnit.MINUTES, // 空闲线程的存活时间
    new ArrayBlockingQueue<>(10), // 任务队列
    new MyThreadFactory(), // 线程工厂
    new MyRejectedExecutionHandler() // 自定义拒绝策略
);
```

在上面的代码中，我们创建了一个 ThreadPoolExecutor 对象，并指定了自定义的拒绝策略 MyRejectedExecutionHandler。在线程池中提交任务时，如果线程池已满或者任务队列已满，则会触发 MyRejectedExecutionHandler 中的 rejectedExecution() 方法，执行自定义的拒绝策略。

需要注意的是，在实现自定义拒绝策略时，需要考虑线程安全和并发性等问题，以确保线程池的正确性和性能。同时，也需要根据实际需求选择合适的拒绝策略，以保证系统的稳定性和可靠性。

在 Java 的 Validation API 中，1.x 版本和 2.x 版本的 Maven 坐标不一样，主要是因为包名和类名发生了变化。

下面是 Java Validation API 1.x 和 2.x 版本的 Maven 坐标：

- Java Validation API 1.x 版本的 Maven 坐标：

```xml
<dependency>
    <groupId>javax.validation</groupId>
    <artifactId>validation-api</artifactId>
    <version>1.0.0.GA</version>
</dependency>
```

在上面的代码中，我们使用了 javax.validation 包下的 validation-api 模块，版本号为 1.0.0.GA。

- Java Validation API 2.x 版本的 Maven 坐标：

```xml
<dependency>
    <groupId>javax.validation</groupId>
    <artifactId>validation-api</artifactId>
    <version>2.0.1.Final</version>
</dependency>
```

在上面的代码中，我们同样使用了 javax.validation 包下的 validation-api 模块，版本号为 2.0.1.Final。

需要注意的是，Java Validation API 2.x 版本中，包名和类名发生了变化，例如：

- javax.validation.constraints 包下的注解名称从 @NotNull 变为了 @NotBlank，@NotEmpty 和 @NotNull。

- javax.validation.Valid 注解的导入路径从 javax.validation.Valid 变为了 jakarta.validation.Valid。

因此，在升级 Java Validation API 版本时，需要注意相应的包名和类名的变化，以免出现编译错误或运行时错误。同时，也需要注意应用程序的其他依赖库是否与升级后的 Java Validation API 版本兼容。

Java Validation API 1.x 版本是在 Java EE 6 中引入的，而 Java Validation API 2.x 版本是在 Java EE 8 中引入的。在 Java EE 8 中，Java EE 规范已经迁移到了 Eclipse Foundation，并更名为 Jakarta EE。因此，Java Validation API 2.x 版本的包名和类名已经从 javax.validation 变为 jakarta.validation。

如果你的项目使用的是 Jakarta EE 8 或者更高版本，那么应该使用 jakarta.validation 包下的 API，而不是 javax.validation 包下的 API。下面是 Jakarta Validation API 2.x 版本的 Maven 坐标：

```xml
<dependency>
    <groupId>jakarta.validation</groupId>
    <artifactId>jakarta.validation-api</artifactId>
    <version>2.0.2</version>
</dependency>
```

需要注意的是，Jakarta Validation API 2.x 版本与 Java Validation API 1.x 版本之间存在一些差异和兼容性问题，例如注解名称的变化、校验器的变化等。因此，在升级到 Jakarta Validation API 2.x 版本时，可能需要修改一些代码并重新测试以确保应用程序的正确性和兼容性。

如果你的项目使用的是 Java EE 6 或者 Java EE 7，那么应该使用 javax.validation 包下的 API，不需要升级到 Jakarta Validation API 2.x 版本。
这两个依赖都是用于在 Java 应用程序中使用 Bean Validation API 进行数据校验的，不同之处在于包名和类名的变化。
`javax.validation:validation-api:2.0.1.Final` 是适用于 Java EE 8 及以下版本的 Bean Validation API，包名为 `javax.validation`，类名也是以 `javax.validation` 开头。
而 `jakarta.validation:jakarta.validation-api:2.0.2` 则是适用于 Jakarta EE 9 及以上版本的 Bean Validation API，包名变为了 `jakarta.validation`，类名也相应地变为了 `jakarta.validation` 开头。
由于 Java EE 规范已经迁移到了 Eclipse Foundation 并更名为 Jakarta EE，所以对应的 API 包名和类名也随之发生了变化，为了保持兼容性，需要使用对应版本的 API。
如果你的应用程序运行在 Java EE 8 及以下版本，那么应该使用 `javax.validation:validation-api`；如果你的应用程序运行在 Jakarta EE 9 及以上版本，那么应该使用 `jakarta.validation:jakarta.validation-api`。
