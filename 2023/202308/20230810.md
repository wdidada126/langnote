2. `prepareBeanFactory(beanFactory)`: 准备 BeanFactory 的设置。在这一步中，会调用一些后处理器，以及注册一些必要的 BeanFactory 后处理器。

   - `postProcessBeanFactory(beanFactory)`: 对 BeanFactory 进行一些后处理。这是一个钩子方法，可以在子类中实现以自定义 BeanFactory 的处理。

总之，`refresh` 方法是 Spring 应用上下文的核心刷新流程，负责初始化和准备应用上下文，以及完成各种后处理和清理工作。这个过程确保了应用上下文的正确初始化，从而让应用能够正常运行。

ConfigurationClassPostProcessor

在Spring框架中,ConfigurationClassPostProcessor是一个很重要的后置处理器,它的主要作用是:
1. 处理被@Configuration注解的配置类,并构建出IODC(Inversion of Control)容器内部的bean定义。
2. 寻找@ComponentScan等注解,并将扫描到的组件注册为Spring Bean。
3. 处理@Import注解,导入额外的配置类。
4. 处理@Bean注解方法,注册为Bean定义。
5. 负责处理配置类之间的依赖关系,确保顺序初始化。
简单来说,它是启用注解驱动注册Bean定义的关键类,不光处理配置类,还会解析组件扫描等注解。
在Spring应用启动阶段,这个后置处理器会非常早被调用到,用来构建Spring的IOC容器,是非常重要的一个步骤。
没了它,只靠@Configuration注解的配置类是不会生效的,它起到了承上启下的作用。
所以 ConfigurationClassPostProcessor是一个关键的后置处理器,它使注解驱动的配置类可以生效,是Spring注解配置模式的基石。

`org.springframework.beans.factory.support.AbstractAutowireCapableBeanFactory#applyPropertyValues` 方法是 Spring IoC 容器中的一个核心方法，用于在创建和初始化 Bean 时，将属性值应用到 Bean 实例中。这个方法在完成属性的自动注入、属性的依赖解析以及属性值的设置等过程中起着关键作用。

下面是对 `applyPropertyValues` 方法的处理流程的简要说明：

1. 获取 BeanDefinition 中的属性信息，这些属性信息包括需要自动注入的属性、属性值等。

2. 遍历属性列表，检查每个属性是否需要自动注入。这可能涉及 `@Autowired` 注解、`@Value` 注解、`@Resource` 注解等。

3. 如果属性需要自动注入，首先尝试从容器中获取对应的依赖 Bean。如果依赖 Bean 已经在容器中存在，则将它设置到当前 Bean 实例的属性中。

4. 如果找不到依赖 Bean，可能会根据属性的类型和注解信息，创建一个适当的代理对象或者特定实例，然后将这个对象设置到当前 Bean 实例的属性中。例如，如果属性类型是接口，并且有多个实现类，Spring 可能会创建一个代理对象，根据代理的逻辑决定具体注入哪个实现类。

5. 重复以上步骤，直到所有需要自动注入的属性都完成注入。

需要注意的是，`applyPropertyValues` 方法是 Spring IoC 容器在创建和初始化 Bean 时的一部分流程。这个方法与整个 Bean 生命周期密切相关，在 `populateBean`、`initializeBean` 等阶段被调用，确保 Bean 的属性被正确注入，依赖被解析，并且属性值得到正确设置。

总之，`applyPropertyValues` 方法是 Spring IoC 容器实现属性自动注入的核心部分，它通过解析 BeanDefinition 中的属性信息，根据注解和依赖关系完成属性注入，从而构建和初始化完整的 Bean 实例。

org.springframework.context.support.AbstractApplicationContext#parent 作用

`parent` 是 Spring Framework 中 `AbstractApplicationContext` 类的一个属性，用于表示当前应用上下文的父上下文。它的作用是支持应用上下文的层级结构，允许在子上下文中访问和继承父上下文中定义的 Bean 和其他配置信息。
具体来说，`parent` 的作用如下：
1. **层级结构：** 通过使用父子上下文的层级结构，可以将配置信息和 Bean 的定义进行组织，使得不同层次的上下文具有不同的配置。这对于大型应用程序中的模块化和组织性很有帮助。每个子上下文可以关注自己特定的配置和 Bean，而共享父上下文的一些公共配置。
2. **Bean 继承：** 子上下文可以继承父上下文中的 Bean 定义。这意味着子上下文可以访问和使用父上下文中定义的 Bean，而不需要重新定义。这在一些场景下很有用，比如将通用的配置和 Bean 放在父上下文中，子上下文继承这些通用配置，并可以定义自己特定的 Bean。
3. **作用域限制：** 父上下文中的 Bean 对子上下文是不可见的，但子上下文中的 Bean 对父上下文是可见的。这种作用域的限制可以确保子上下文中的 Bean 不会影响到父上下文，但可以利用继承机制访问父上下文中的 Bean。
4. **资源共享：** 父子上下文可以共享一些资源，如消息源、事件多播器等。这使得在应用中统一配置这些共享资源变得容易。
总之，`parent` 属性允许在 Spring 应用上下文中创建父子层级关系，以达到更好的模块化、组织和配置共享等目的。在需要将应用划分为不同的逻辑部分、模块或者需要共享一些配置时，使用父子上下文关系可以提高应用的可维护性和灵活性。

Javax.inject包包含了JSR-330标准定义的依赖注入注解,如@Inject、@Named等。

在Maven中的坐标为:

```xml
<dependency>
    <groupId>javax.inject</groupId>
    <artifactId>javax.inject</artifactId>
    <version>1</version>
</dependency>
```

具体坐标为:

- groupId: javax.inject
- artifactId: javax.inject
- version: 1

这个依赖包含了javax.inject中的所有类和注解。

要使用@Inject、@Named等注解,需要引入这个依赖。

注意从Java EE 6开始,它已经包含在Java EE API中,不再需要显式依赖。

另外,在Jakarta EE中,包名变更为jakarta.inject, coordinates也发生改变:

```xml
<dependency>
  <groupId>jakarta.inject</groupId>
  <artifactId>jakarta.inject-api</artifactId>
  <version>2.0.0</version>
</dependency>
```

groupId为jakarta.inject,需要注意区分。


Spring框架通过注解的方式支持JSR-330标准(javax.inject包)中的依赖注入功能。

主要的实现方式有:

1. Spring对@Inject和@Named注解提供了支持,可以用于注入Bean:

```java
@Inject 
private MessageService messageService;
```

2. Spring自己的@Autowired注解也提供了相似的功能。

3. Spring实现了CommonAnnotationBeanPostProcessor后置处理器,来处理这些注解。

4. 该后置处理器会识别@Inject/@Named注解,并注入所需的Bean。

5. 同时它也支持JSR-250的@Resource注解,提供注入功能。


6. 这些后置处理器默认会自动注册到ApplicationContext中。

7. 通过@Qualifier可以细粒度控制依赖注入。

所以Spring并没有显式依赖javax.inject,而是通过后置处理器内部实现了对相关注解的支持,使得这些注解可以用于注入Bean。

这样既提供了JSR-330标准的兼容,也保持了Spring自身的灵活性,无需外部依赖。

假设我们有两个实现类:

```java
@Component
public class MessageSenderImpl implements MessageSender {

}

@Component 
public class EmailSenderImpl implements MessageSender {

}
```
都实现了同一个MessageSender接口。
在服务类中,我们可以通过@Qualifier来区分这两个实现:

```java
public class MyService {

  @Autowired
  @Qualifier("messageSenderImpl")
  private MessageSender messageSender; 

  @Autowired
  @Qualifier("emailSenderImpl")
  private MessageSender emailSender;

}
```

虽然类名默认就可以区分,但我们还可以指定@Qualifier:

```java
@Component("messageSenderImpl")
public class MessageSenderImpl implements MessageSender {

}

@Component("emailSenderImpl") 
public class EmailSenderImpl implements MessageSender {

}
```
现在通过@Qualifier我们可以选择注入指定的实现类,这样就达到了细粒度的控制依赖注入的效果。
我们也可以自定义@Qualifier:
```java
@Qualifier
@Retention(RetentionPolicy.RUNTIME)
public @interface SmsSender {

}
```

然后在字段上指定即可。

所以@Qualifier提供了非常灵活的注入控制能力,是Spring依赖注入很重要的一个方面。


spring 读取配置文件的值

在 Spring 项目中，可以使用不同的配置文件加载器和属性源配置来确保 Spring 可以正确加载配置文件中的属性值。下面是一些常见的操作：

1. **配置文件加载器**：
   Spring 支持多种配置文件加载器，包括 `PropertySourcesPlaceholderConfigurer`、`PropertySourcesPlaceholderConfigurer`、`PropertyOverrideConfigurer` 等。你可以根据需要选择适合的加载器。

   例如，在 XML 配置文件中，可以添加以下配置来加载属性文件：

   ```xml
   <context:property-placeholder location="classpath:application.properties"/>
   ```

   这将告诉 Spring 加载类路径下的 `application.properties` 文件，并将其属性值注入到相应的 `@Value` 注解中。

1. **属性源配置**：
   在 Spring 项目中，你可以通过多种方式配置属性源，包括使用属性文件、环境变量、系统属性等。

   - 使用属性文件：
     在属性文件（如 `application.properties` 或 `application.yml`）中定义属性值，并确保配置文件位于类路径下。

   - 使用环境变量：
     你可以通过在操作系统或容器中设置环境变量，并在 Spring 配置文件中使用 `${ENV_VARIABLE_NAME}` 的方式引用环境变量的值。

   - 使用系统属性：
     你可以在启动应用程序时通过命令行参数或 JVM 参数设置系统属性，并在 Spring 配置文件中使用 `${systemProperty}` 的方式引用系统属性的值。

   例如，在属性文件中定义属性值：

   ```properties
   my.property=Hello, World!
   ```

   然后在 Spring 组件中使用 `@Value` 注解引用该属性：

   ```java
   @Value("${my.property}")
   private String myProperty;
   ```

   在上述示例中，Spring 将自动加载属性文件，并将 `my.property` 属性的值注入到 `myProperty` 变量中。

通过适当的配置文件加载器和属性源配置，你可以确保 Spring 可以正确加载配置文件中的属性值，并将其注入到相应的组件中。这样，你就可以在项目中使用 `@Value` 注解引用这些属性值了。


    @Bean
    public PropertySourcesPlaceholderConfigurer propertySourcesPlaceholderConfigurer() {
        PropertySourcesPlaceholderConfigurer configurer = new PropertySourcesPlaceholderConfigurer();
        Resource[] resources = new ClassPathResource[]{new ClassPathResource("application.properties")};
        configurer.setLocations(resources);
        return configurer;
    }
