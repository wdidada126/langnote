一、 VARCHAR 长度设计与索引的注意事项

VARCHAR 的长度定义不仅关乎存储，更直接影响索引的性能。

1. 索引长度限制

• MySQL 的 InnoDB 引擎对单列索引有 3072 字节的长度限制。

• UTF8MB4 字符集（推荐使用，支持emoji等所有字符）下，一个字符最多占用 4 字节。

• 计算：3072 字节 / 4 字节/字符 = 768 字符。

• 结论：如果你定义了一个 VARCHAR(1000) 并使用 UTF8MB4 字符集，你无法为这个列创建完整长度的索引。创建索引时会报错。

2. 前缀索引

为了解决长字段的索引问题，MySQL 允许使用前缀索引，即为字段值的前 N 个字符创建索引。
-- 为 name 字段的前 10 个字符创建索引
CREATE INDEX idx_name ON your_table (name(10));


• 优点：节省索引空间，加快索引速度。

• 缺点：可能会降低选择性，导致查询效率下降。

    ◦ 选择性指不重复的索引值数量与表记录总数的比例。比例越高，索引过滤效果越好。

    ◦ 如果 name 字段前10个字符重复度很高（如都以“北京市朝阳区...”开头），那么 WHERE name = '北京市朝阳区xxx' 用前缀索引效率依然很低。

如何确定最佳前缀长度？
通过计算不同前缀长度的选择性来选择。
-- 计算完整列的选择性
SELECT 
  COUNT(DISTINCT name) / COUNT(*) AS full_selectivity
FROM your_table;

-- 计算前 N 个字符的选择性，不断调整 N 直到接近完整列的选择性
SELECT 
  COUNT(DISTINCT LEFT(name, 5)) / COUNT(*) AS sel5,
  COUNT(DISTINCT LEFT(name, 10)) / COUNT(*) AS sel10,
  COUNT(DISTINCT LEFT(name, 15)) / COUNT(*) AS sel15
FROM your_table;


最佳实践：在满足业务需求的前提下，VARCHAR 的长度不宜过长。对于需要索引的字段，应确保其长度在限制内，并考虑使用前缀索引优化长字段。

二、 LIKE '%xx%' 查询为何不走索引？（核心原因）

这是一个“最左前缀匹配”原则的问题。

1. 索引的数据结构（B+Tree）简介

可以想象索引像一本电话簿，它是按姓氏（索引列）有序排列的。如果你知道姓氏是“张”，你可以快速定位到“张”所在的那几页。但如果你只知道名字里有个“三”字，你就只能一页一页地翻整本电话簿。

2. 为什么 LIKE '%xx%' 是“全表扫描”？

• LIKE '张%'：对应 WHERE surname = '张'。索引是有序的，所以可以快速找到所有以“张”开头的记录。索引有效。

• LIKE '%三' 或 LIKE '%三%'：对应 WHERE given_name LIKE '%三'。索引的有序性在这里毫无用处，因为字符串的开头是未知的（通配符 % 开头）。优化器知道，使用索引（先读索引树，再回表查数据）的代价可能比直接顺序扫描整个数据表（全表扫描）更高。因此，它选择放弃使用索引。

3. CHAR 和 VARCHAR 在索引行为上一致

您提到的 CHAR 索引，在这个问题上和 VARCHAR 没有区别。LIKE 查询能否用上索引，只取决于查询模式是否满足最左前缀匹配，与字段是 CHAR 还是 VARCHAR 无关。

三、 解决方案：如何优化 LIKE '%xx%' 查询？

既然传统的 B-Tree 索引无效，我们需要另辟蹊径。

方案一：使用反转函数索引（逆向思维）

思路：如果查询 LIKE '%abc'，我们可以创建一个反转字符串的索引，然后将查询条件也反转，变成 LIKE 'cba%'。
-- 1. 新增一个用于存储反转值的列
ALTER TABLE your_table ADD COLUMN name_reverse VARCHAR(100);
UPDATE your_table SET name_reverse = REVERSE(name);

-- 2. 为该列创建索引
CREATE INDEX idx_name_reverse ON your_table (name_reverse);

-- 3. 查询时也使用 REVERSE 函数
SELECT * FROM your_table WHERE name_reverse LIKE REVERSE('%三')； -- 反转后变成 '三%'
-- 等价于原查询：SELECT * FROM your_table WHERE name LIKE '%三';

缺点：需要维护冗余列，查询语句需要修改。

方案二：使用全文索引（最佳方案）

全文索引是专门为这种“文本内容搜索”场景设计的。
-- 1. 创建全文索引 (MySQL 5.6+ 的 InnoDB 表支持)
ALTER TABLE your_table ADD FULLTEXT INDEX ft_idx_name (name);

-- 2. 使用 MATCH ... AGAINST 语法进行搜索
SELECT * FROM your_table 
WHERE MATCH (name) AGAINST ('+三' IN BOOLEAN MODE); 
-- 这会查找所有包含“三”的记录，效率远高于 LIKE '%三%'


优点：
• 专为文本搜索优化，性能极高。

• 支持自然语言模式和布尔模式，功能强大（如匹配多个词、排除某些词等）。

• 支持相关性排序。

限制：
• 有默认的最小词长度（ft_min_word_len，通常为4），搜索“三”可能无效。需要修改配置或使用 ngram 解析器（适用于中文）。

方案三：使用专业的搜索引擎

如果查询量巨大，对搜索性能和要求极高（如电商网站、内容平台），MySQL 的全文索引可能仍不够用。应考虑集成外部搜索引擎：
• Elasticsearch

• Solr

这些系统专为海量数据的实时搜索而设计，通过将数据从 MySQL 同步到搜索引擎中来提供极致性能。

总结与执行计划验证

最后，一定要用 EXPLAIN 查看执行计划，这是判断索引是否生效的金科玉律。
-- 查看你的 LIKE 查询是否使用了索引
EXPLAIN SELECT * FROM your_table WHERE name LIKE '%三%';

-- 查看全文索引查询的计划
EXPLAIN SELECT * FROM your_table WHERE MATCH (name) AGAINST ('三');


在 EXPLAIN 的结果中，关注 type 和 key 列：
• type = index 或 range：表示使用了索引扫描。

• type = ALL：表示全表扫描，索引未生效。

• key 列会显示使用的索引名称。

最终建议：
对于 LIKE '%xx%' 这种需求，在现代 MySQL 版本中，首选方案是使用全文索引（FULLTEXT）。它是最规范、性能最好且维护成本最低的解决方案。
