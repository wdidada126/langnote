为啥不用new

s用完之后，不用释放内存吗？
在C++中，当你创建一个字符串对象时，你不需要使用关键字"new"来分配内存。相反，编译器会自动为你分配内存。

当你使用以下代码创建一个字符串对象`s`：
```cpp
string s("s");
```
编译器会在栈上为字符串对象分配足够的内存空间来存储字符序列"s"。这意味着你不需要手动释放该对象的内存，因为它是由编译器自动管理的。

当字符串对象`s`超出作用域或被显式销毁时，其析构函数会被调用，内存将自动释放。例如，如果你在某个函数内部创建了一个字符串对象`s`，当函数返回或执行了离开作用域的操作时，`s`的析构函数将被调用，内存将被释放。

总结起来，C++中的字符串对象会在栈上分配内存，并且由编译器自动管理内存的释放，因此你不需要手动释放内存。
这里你没有动态申请内存, 因此, 系统会自动释放.

好的，您提到了一个非常前沿和重要的信息。TiKV 作为 TiDB 的分布式存储引擎，其默认的底层单机存储引擎一直是 RocksDB（一个由 Facebook 基于 LevelDB 开发的高性能、持久化的键值存储库）。

然而，您提到的 Titan 并不是一个全新的、独立的存储引擎，而是 RocksDB 的一个关键插件或高级功能，专门为优化 Value 值非常大 的场景而设计。

下面我将为您详细解释 Titan 是什么、它解决了什么问题，以及它与 RocksDB 的关系。

一、 核心概念：RocksDB 的痛点

要理解 Titan，首先要明白经典 RocksDB 在处理大 Value 时的问题。

RocksDB 的 LSM-Tree 写放大问题：
1.  写入：数据首先写入内存的 MemTable，满后刷到磁盘成为 SST 文件（Level 0）。
2.  压缩：当每层的 SST 文件过多时，会进行压缩合并，将多个文件合并成一个新文件，并推到下一层。
3.  问题：一个巨大的 Value 会被反复读写和压缩。即使只更新了一个小 Key，整个巨大的 Value 也需要被重写一次。这导致了严重的写放大，消耗大量 CPU 和 I/O，缩短 SSD 寿命。

简单比喻：
• 就像你有一个装满了大文件的文件夹，每次想修改其中一个文件的文件名，却不得不把整个文件夹复制、压缩、再重命名一遍。效率极低。

二、 Titan：为大 Value 而生的解决方案

Titan 是 PingCAP 团队为 RocksDB 开发的一个插件式存储引擎，其核心思想是 “键值分离”。

1. 设计理念

• Key 和 Small Value：仍然保存在经典的 RocksDB LSM-Tree 中。

• Large Value：被提取出来，存储在一个单独的Blob文件中。在 LSM-Tree 中只保留一个指向该 Blob 文件的句柄。

2. 工作流程

• 写入：RocksDB 接收到一个 (Key, LargeValue) 对。Titan 会判断 Value 的大小是否超过阈值（可配置）。

    ◦ 如果超过，则将 Value 写入专门的 Blob 文件，并在原来的 LSM-Tree 中只存储 (Key, BlobHandle)。

    ◦ 如果未超过，则像普通 RocksDB 一样处理。

• 读取：根据 Key 找到记录。如果发现它是一个 BlobHandle，则根据其中的指针去对应的 Blob 文件中读取真正的 Value。

• 垃圾回收：由于 Blob 文件中的 Value 可能因为 key 的删除或更新而变成垃圾，Titan 有独立的Blob文件压缩进程来回收空间，避免存储泄漏。

三、 Titan 的核心优势与适用场景

特性 经典 RocksDB 启用 Titan 的 RocksDB 优势

写放大 高 显著降低 大幅减少磁盘 I/O，提升写入吞吐，延长 SSD 寿命

写入吞吐 低（大Value时） 高 特别适合写入密集型且 Value 较大的场景

读取性能 好 略有损耗 多了一次间接寻址，但对大Value场景整体收益远大于损耗

空间放大 低 相对较高 垃圾回收前，Blob文件中有可能存在更多过期数据

最佳适用场景：
• TiKV： 这正是 Titan 被开发出来的首要原因。TiKV 中可能存储着较大的 Value（如文本内容、图片链接、长文档序列化值等）。

• 监控数据存储： 存储大量的日志或监控指标数据。

• 对象存储元数据管理： 其中 Value 可能是较大的元信息。

• 社交网络： 存储用户发的长帖子、评论等。

四、 在 TiKV 中启用 Titan

Titan 在 TiKV 中是作为一个可配置的选项存在的。你可以在 TiKV 的配置文件中轻松启用和配置它。

示例配置 (tikv.toml):
[rocksdb.titan]
# 启用 Titan
enabled = true
# 触发键值分离的 Value 大小阈值（默认 1KB）
min-blob-size = "1KB"
# Blob 文件的最大大小
blob-file-size = "256MB"
# Blob 垃圾回收的比率阈值
discardable-ratio = 0.5
# Blob 垃圾回收的运行模式
gc-sample-cycles = 10


运维命令：
你可以通过 TiKV 的 API 动态开启或关闭 Titan（注意：这是一个重大操作，需要谨慎！）：
# 开启 Titan
tikv-ctl --host <tikv-ip:port> modify-tikv-config -n rocksdb.titan.enabled -v true

# 关闭 Titan
tikv-ctl --host <tikv-ip:port> modify-tikv-config -n rocksdb.titan.enabled -v false


五、 总结：Tian vs. RocksDB

维度 RocksDB Titan
定位 通用的、高性能的嵌入式 KV 存储引擎 RocksDB 的 插件/扩展，用于优化大 Value 场景
关系 基础 增强补丁
核心创新 LSM-Tree 键值分离
优势 综合性能均衡，成熟稳定 极大改善写放大，提升大 Value 写入吞吐
代价 大 Value 时写放大严重 读性能有轻微损耗，配置更复杂
适用场景 通用场景，Value 大小均匀 Value 明显偏大 的场景
结论：
Tian 不是要取代 RocksDB，而是赋能 RocksDB。它是为了解决 RocksDB 在特定场景下的核心痛点而诞生的卓越解决方案。对于像 TiKV 这样底层依赖 RocksDB 且可能处理海量大小不一的 Value 的分布式系统来说，Titan 是一个至关重要的性能优化利器，能够显著降低写放大，提升集群的稳定性和吞吐能力。

如果你的 TiDB 集群 workload 中包含大量大于 1KB 的 Value，强烈建议考虑启用 Titan 以获得更好的性能。
