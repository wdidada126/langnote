# geaflow

GeaFlow 是一个由 蚂蚁集团 自主研发的 一体化流批图（Streaming-Batch-Graph）计算引擎，旨在统一处理 流计算、批处理和图计算 三种典型的大数据计算模式，实现“一套引擎、一种编程模型、一份代码”处理多种计算任务的目标。

它被设计用于应对金融、风控、社交网络、知识图谱等场景中日益复杂的实时关联分析需求。

### GeaFlow 的核心定位
> “流 + 批 + 图”一体化计算引擎

传统大数据架构中：
- 流计算用 Flink
- 批处理用 Spark
- 图计算用 GraphX 或独立图数据库

导致系统复杂、数据冗余、开发成本高。

GeaFlow 的目标是：用一个引擎，解决三类问题。

### 主要特性
| 特性 | 说明 |
|------|------|
| 统一计算模型 | 提供统一的编程 API（Java/Scala），支持流、批、图的混合计算，开发者无需切换引擎。 |
| 动态图计算（Dynamic Graph） | 支持图结构随时间演进的计算（如实时更新的交易网络），而非静态图。 |
| 事件驱动的图处理 | 图的更新和计算基于事件流驱动，适合实时风控、反欺诈等场景。 |
| 低延迟高吞吐 | 基于分布式流处理架构，支持毫秒级实时响应。 |
| 与 Flink 深度集成 | GeaFlow 构建在 Apache Flink 之上（或兼容其运行时），复用其强大的流处理能力。 |
| 图视图抽象 | 提供 `GraphView`、`StreamGraph` 等抽象，允许用户以“图”的视角分析流数据。 |
| SQL + SDK 支持 | 支持通过 SQL 或 Java/Scala SDK 编写图计算逻辑。 |

### 典型应用场景
1. 实时反欺诈
   - 实时构建用户交易关系图，检测异常转账链、团伙作案。
2. 金融风控
   - 实时分析信贷申请人的社交、资金往来图谱，识别共债风险。
3. 社交网络分析
   - 实时计算影响力传播、社区发现。
4. 知识图谱推理
   - 增量更新图谱并实时推理新关系。
5. 供应链/物流网络优化
   - 实时路径分析、瓶颈检测。

### 架构简述（简化版）

```
+---------------------+
|  用户代码 (Java/SQL)  |
+----------+----------+
           |
           v
+---------------------+
|  GeaFlow Runtime     |  ← 基于 Flink 运行时
|  - 流处理引擎         |
|  - 图计算引擎         |
|  - 统一调度与状态管理   |
+----------+----------+
           |
           v
+---------------------+
|  存储层 (HDFS, Kafka,  |
|   RDS, 图数据库等)     |
+---------------------+
```

- 数据源：Kafka（流）、HDFS（批）、数据库（图）
- 计算：在 Flink 集群上运行 GeaFlow 任务
- 结果：输出到数据库、消息队列或实时大屏

###  与其他图计算引擎对比
| 引擎 | 类型 | 实时性 | 特点 |
|------|------|--------|------|
| GeaFlow | 流批图一体 | ⚡ 高（毫秒级） | 蚂蚁自研，实时动态图，与业务深度集成 |
| GraphX (Spark) | 批处理图 | ❌ 低 | 基于 Spark RDD，适合离线分析 |
| Gelly (Flink) | 批/迭代图 | 中 | Flink 原生图库，但非事件驱动 |
| NebulaGraph / JanusGraph | 图数据库 | 高 | 存储+查询，适合 OLTP，计算能力有限 |
| Pregel / PowerGraph | 离线图计算 | 低 | 经典图计算模型 |

GeaFlow 的独特优势在于：将图计算嵌入流处理管道中，支持持续、增量的图分析。

### 发展现状
- 开源状态：截至 2025 年，GeaFlow 尚未完全开源，主要在蚂蚁集团内部及部分合作方使用。
- 生态集成：与蚂蚁的 SOFAStack、OceanBase、Kafka 等技术栈深度集成。
- 性能表现：在蚂蚁的双11等大促场景中，支撑了万亿级边的实时图计算任务。

### 总结
GeaFlow 是什么？

> GeaFlow 是蚂蚁集团推出的一体化 流批图计算引擎，基于 Flink 构建，支持 实时动态图计算，用于解决金融风控、反欺诈、社交网络等场景中的 复杂关联实时分析 问题。

它的出现代表了大数据计算向 “融合计算” 演进的趋势：不再孤立看待流、批、图，而是用统一模型处理日益复杂的现实业务逻辑。
