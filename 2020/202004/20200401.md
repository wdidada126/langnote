## 高级数据库系统：分布式数据库课程导读与笔记

这门课的核心不是“把 MySQL 拆到多台机器上”，而是在网络延迟、节点故障、数据多副本和水平扩展存在时，仍然为应用提供明确的数据模型、查询语义和事务保证。分布式数据库系统试图在数据局部性、性能、可用性、一致性、运维复杂度之间做可解释的取舍。

本地保存的《清华大学计算机研究生课程表 - feipeng8848 - 博客园.mht》与原链接列出的课程范围包括：分布式数据库设计、查询分解与数据定位、分布式查询处理优化、事务语义与可串行化理论、分布式并发控制、可靠性和实验系统实现。该页面是课程资料转载，适合用于回顾课程主题；具体培养方案、教师和开课安排应以学校当期官方信息为准。

### 1. 从单机数据库到分布式数据库

单机数据库的基础问题是：如何在一台机器的存储、CPU 和内存约束下，实现 SQL、索引、事务、恢复和并发控制。分布式数据库增加了新的事实：一次操作可能跨越多台机器，机器之间通过可能丢包、延迟、乱序或分区的网络通信，任何节点都可能在任意时刻崩溃或重启。

```text
应用/SQL 客户端
    -> SQL 网关/协调者：解析、优化、路由、事务协调
    -> 分片 1：leader + follower replicas
    -> 分片 2：leader + follower replicas
    -> 分片 N：leader + follower replicas

控制面：成员管理、调度、元数据、schema 变更、备份恢复、监控告警
```

一个系统是否是“原生分布式数据库”，关键不在于有多少机器，而在于分片路由、复制一致性、跨分片事务、分布式查询执行、故障恢复和运维是否由数据库本身统一实现。仅由应用或中间件把 SQL 路由到多个独立 MySQL 实例，通常称为分库分表或分片中间件；它也能扩展，但跨库语义和运维责任更多暴露给应用。

### 2. 数据分布：分片、复制与目录

| 概念 | 要解决的问题 | 主要代价/风险 |
| --- | --- | --- |
| 水平分片（sharding） | 按行或 key 分散容量、写入与热点 | 跨分片 join、聚合、事务、全局唯一性和热点 key。 |
| 垂直分片 | 将不同列族/业务表放到不同节点 | 跨表访问、业务边界演化和事务范围扩大。 |
| 副本（replication） | 提高可用性、读扩展和容灾能力 | 副本延迟、写入协调、读陈旧和故障切换。 |
| 分区键/路由键 | 决定数据在哪个分片，尽量让常用事务单分片完成 | 选择错误会形成热点、广播查询或频繁重分片。 |
| 全局目录/元数据 | 记录 table、range、shard、replica 与 leader 映射 | 元数据本身必须高可用、强一致且可演进。 |

常见分片方式：

- 哈希分片：均衡性较好，范围查询与顺序扫描代价高；扩容往往需要一致性哈希、虚拟分片或在线重平衡。
- 范围分片：范围扫描、按时间归档自然，但递增 key、最新时间段和大客户容易变成热点。
- 目录/查找表分片：灵活地将租户、地域或业务实体映射到分片，但目录服务成为关键依赖。
- 地域/租户分片：有利于数据主权和本地访问；跨地域、跨租户分析和统一事务会更复杂。

设计时先写出事务访问的主键集合，再反推分片键。以订单为例，若“下单、支付、扣库存”总跨订单、账户和库存三个分片，那么即使每张表本身分得均匀，事务仍会频繁跨节点；应该评估共置（colocation）、业务拆分、异步补偿或更强分布式事务的代价。

### 3. 复制与一致性：副本不是备份

备份用于在误删、逻辑错误或灾难后恢复到历史点；复制用于让多个在线副本共同提供读写与故障切换。二者都需要，不能互相替代。

| 模式 | 写确认条件 | 读语义 | 典型场景 |
| --- | --- | --- |
| 单主异步复制 | 主库先提交，副本稍后追赶 | 读副本可能陈旧；主故障切换可能丢最近已确认写 | 可容忍短暂读旧、追求低写延迟。 |
| 同步/半同步复制 | 等待一个或多个副本确认 | 降低数据丢失窗口，写延迟受网络影响 | 同城高可用、关键数据。 |
| 共识复制（Raft/Paxos） | 多数副本复制日志后提交 | 在故障模型和 leader 规则下提供一致复制状态机 | 分片元数据、强一致 KV、NewSQL 存储层。 |
| 多主/最终一致复制 | 多个节点均可接收写入，之后合并 | 需要冲突检测/解决，通常不是线性一致 | 离线协作、跨地域低延迟且可接受冲突的业务。 |

一致性术语必须精确：**线性一致（linearizability）** 要求每个操作看起来在实时顺序中的某个瞬间完成；**可串行化（serializability）** 要求事务结果等价于某个串行顺序，但不必保持客户端观察到的实时先后；**快照隔离（SI）** 提供一致快照但仍可能发生写偏斜；**最终一致** 只承诺在没有新更新后副本最终收敛。CAP 是网络分区存在时的一组约束，不是产品宣传中的三选一标签；真正设计还要说明读写超时、quorum、故障转移和冲突策略。

### 4. 分布式事务：原子提交不等于业务完成

跨分片事务需要同时解决两件事：

1. **并发控制**：哪些读写能同时提交，是否保证可串行化，冲突时谁中止。
2. **原子提交**：多个参与分片在故障下要么都提交，要么都回滚，不能只完成一半。

```text
协调者                      分片 A                 分片 B
  |--- prepare(T) ----------->|                       |
  |-------------------------->|--- prepare(T) ------->|
  |<-- prepared / vote -------|<-- prepared / vote ---|
  |--- commit(T) ------------>|--- commit(T) -------->|
```

两阶段提交（2PC）通过 prepare/commit 协调原子提交：参与者在 prepare 后持有必要锁和日志，协调者收齐成功投票后发出 commit；任一参与者失败则 abort。它解决“多参与者原子决定”，但不天然解决高可用、长时间阻塞、死锁、热点和业务补偿。协调者或网络故障时，prepared 事务可能占住资源；生产系统需要持久化决议、超时、恢复协议、事务状态监控与限流。

常见组合包括：

- Percolator/TSO 类：以全局时间戳和 MVCC 提供读写版本控制，再用 primary lock 和 2PC 协调跨分片提交。
- Spanner 类：以共识复制每个分片，并借助有界时钟不确定性/提交等待提供外部一致事务语义。
- 分库分表 + XA：由应用或中间件驱动多个传统数据库的 XA/2PC，接入成本较低但要面对跨库锁、故障恢复和吞吐限制。
- Saga、Outbox、TCC：适用于业务允许最终一致或显式补偿的场景；它们不是 ACID 分布式事务的同义替代，而是把失败处理纳入业务状态机。

### 5. 分布式并发控制与 MVCC

分布式 MVCC 通常为每个版本分配提交时间戳，逻辑上可写为 `(user_key, commit_ts) -> value`。事务以 `start_ts` 读取“不晚于该快照的最新已提交版本”，写入先放入锁/意向记录或私有缓冲，提交时验证冲突并赋予 `commit_ts`。时间戳服务可以是集中式 TSO、混合逻辑时钟（HLC）或基于时钟不确定性的方法；关键不是“时间戳看起来像时间”，而是它能否建立系统需要的全局顺序并支持故障恢复。

```text
key = account:42

(account:42, ts=100) -> balance=100
(account:42, ts=120) -> balance= 90

事务 start_ts=110 读取 ts=100
事务 start_ts=130 读取 ts=120
```

MVCC 减少普通读写阻塞，但不会自动消除写写冲突、写偏斜、唯一约束、范围谓词冲突、死锁或长事务阻塞版本回收。要保证可串行化，系统还可能采用严格两阶段锁、SSI、OCC 验证、范围锁/谓词锁或确定性调度。相关细节见 [MVCC 笔记](../../db/mvcc.md) 与 [TSO 笔记](../../db/tidb/中心化TSO.md)。

### 6. 分布式查询处理与优化

查询优化的目标从“选择单机索引与 join 算法”扩展为“尽量减少跨网络搬运的数据量与同步轮次”。典型过程为：

```text
SQL
  -> 关系代数/逻辑计划：选择、投影、join、聚合下推
  -> 数据定位：每个表/分区/副本实际在哪些节点
  -> 物理分布式计划：scan、exchange/shuffle、broadcast、local join、final aggregate
  -> 协调节点合并、排序、返回结果
```

核心优化原则：

- 先做选择和投影下推，避免传输不需要的列和行。
- 尽量让同一分片键的数据本地 join；必要时重分布（shuffle）或小表广播（broadcast）。
- 分组、聚合、TopN 尽可能部分聚合后再跨网络汇总。
- 统计信息不仅要有行数，还要考虑分区分布、数据倾斜、热点、网络带宽和副本位置。
- `LIMIT/OFFSET`、全局排序、跨分片 `COUNT(DISTINCT)`、大范围 `JOIN` 常是网络和协调节点瓶颈；需改写查询、预聚合、索引或异步分析架构。

### 7. 可靠性、恢复与运维

分布式数据库的可靠性不是“节点挂了会自动恢复”的一句话，而是要分别验证：数据副本是否足够、leader 选举是否安全、日志/快照是否可恢复、事务决议是否可追踪、网络分区是否有明确超时与降级、备份能否恢复到目标时间点，以及 schema/版本升级是否可回滚。

运行时至少观测：每分片 leader 与副本健康、复制 lag、Raft/Paxos 提交延迟、事务提交/中止率、2PC prepared 数与最老 prepared 时长、锁等待/死锁、MVCC 版本数与 GC safe point、跨分片查询比例、网络 shuffle 流量、热点 key/range、重平衡进度、备份校验和恢复演练结果。只有看到这些指标，才能判断“慢”是 SQL 计划、热点、复制、锁冲突、网络还是恢复任务导致。

### 8. 课程实验建议

1. 实现或使用一个带 range/hash 分片的 KV 服务：完成路由表、单分片 `Get/Put`、副本读写与节点故障注入。
2. 在两个或三个分片上实现简化 2PC：记录 prepare/commit/abort 日志，模拟协调者在不同阶段崩溃并恢复决议。
3. 为 KV 加入 MVCC：实现 `start_ts`、版本可见性、冲突检测和 GC safe point；复现实验性写偏斜并比较 SI 与可串行化策略。
4. 为简单 SQL/关系代数计划实现选择投影下推、分片本地 join、shuffle join 和部分聚合，测量网络传输与数据倾斜的影响。
5. 写一份故障报告：一次分片 leader 故障、一次网络分区、一次长事务阻塞 GC、一次热点 key，分别说明观测指标、用户可见语义和修复措施。

### 10. 本节要回答的问题

- 数据为什么按这个键分片？热点、扩容和跨分片事务比例如何评估？
- 读到的是线性一致、可串行化快照、可重复读快照还是可能陈旧的副本读？
- 事务跨分片时，commit 决议保存在哪里；协调者和参与者崩溃后如何恢复？
- 写冲突、死锁、时间戳服务异常、网络分区和副本 lag 时，客户端收到什么错误或延迟？
- 一条跨分片查询的数据移动路径是什么；能否通过下推、共置、预计算或异步化降低成本？
- RPO、RTO、备份恢复、在线 schema 变更和容量扩缩容是否有验证过的运行手册？

推特rpc框架 kotli写的 finagle
Finagle是Twitter基于Netty开发的支持容错的、协议无关的RPC（远程过程调用）框架，该框架支撑了Twitter的核心服务。

Finagle框架的核心概念是一个简单的函数，即从Request生成包含Response的Future。这个Future是一个容器，用来保存异步操作的结果，这样的操作包括网络RPC、超时或磁盘的I/O操作。
在面向服务的架构之中，服务会将大多数的时间花费在等待上游服务的响应上，因此使用异步的库能够让服务并发地处理请求，从而充分发挥硬件的潜能。Finagle构建在Netty之上，并不是直接在原生NIO之上构建的，这是因为Netty已经解决了许多Twitter所遇到的问题并提供了干净整洁的API。网络栈需要足够灵活，以保证能与这些协议进行交流并且还要具有足够的可扩展性以支持添加新的协议。
