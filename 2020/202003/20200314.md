红黑树的五点规定再贴一遍：
1、每个节点都只能是红色或者黑色
2、根节点是黑色
3、每个叶节点（NIL节点，空节点）是黑色的。
4、如果一个结点是红的，则它两个子节点都是黑的。也就是说在一条路径上不能出现相邻的两个红色结点。
5、从任一节点到其每个叶子的所有路径都包含相同数目的黑色节点。

并行复制原理
MySQL 5.7的并行复制是基于组提交（group commit）的思想实现的。当多个事务同时提交时，它们可以在单个操作中写入到二进制日志中。通过在主机上的二进制日志中添加组提交信息，这些Slave可以并行地安全地运行事务。
在MySQL 5.7之前，并行复制受到许多复杂的分发算法、等待策略等效率低下的工作的限制。而现在，并行复制的思想完全摆脱了这些限制，所有组提交的事务都可以并行回放，因为这些事务都已进入事务的prepare阶段，说明事务之间没有任何冲突。
因此，MySQL 5.7并行复制的核心原理就是基于事务的组提交，通过在二进制日志中记录特殊的信息，实现主从之间的一致性复制。这一改进大大提高了并行复制的效率和性能。

## 补充整理

### 1. TreeMap 和红黑树

你这里的主线没有问题。`TreeMap` 底层就是红黑树，核心价值是同时满足“有序”和“插入/删除/查找复杂度稳定”。

- `HashMap` 更偏快速定位
- `TreeMap` 更偏有序访问和范围查询

面试里更稳的说法是：

1. `TreeMap` 基于红黑树
2. 红黑树是一种自平衡二叉搜索树
3. 所以它能保证 key 有序
4. 插入、删除、查找通常是 `O(log n)`

### 2. MySQL 5.7 MTS 的表述修正

你这里方向是对的，但“所有组提交事务都能并行回放，因为进入 prepare 阶段说明没有冲突”这个说法太绝对。

更准确的理解应该是：

- MTS 是 `Multi-Threaded Slave`
- 它解决的是从库 SQL 回放单线程瓶颈
- MySQL 5.7 会利用主库事务提交顺序和依赖关系信息，提高从库并行回放能力
- 不能简单理解成“同组提交事务天然都无冲突”

### 3. 复制延迟

这一块你只记了标题，建议补成这条主线：

- 主库写入快
- 从库回放慢
- relay log 堆积
- 最终形成主从延迟

典型原因：

- 从库 SQL 回放能力不足
- 大事务
- 锁冲突
- 从库读压力过大
- 网络抖动

### 4. 主从复制、读写分离、分库分表的关系

这几个点最好串起来记：

1. 主从复制：解决高可用和只读扩展基础
2. 读写分离：利用主从缓解读压力
3. 分库分表：单库或单表本身到瓶颈后继续拆

### 5. 分库分表概念修正

你原文里“把表分到不通的库”，应为“不同的库”。

另外要区分：

- 垂直分库：按业务模块拆库
- 垂直分表：按字段拆表
- 水平分表：按数据行拆表
- 水平分库：按分片规则把数据分散到多个库

### 6. Amoeba / MySQL Proxy 的定位

不要只记产品名，重点记它们在做什么：

- SQL 路由
- 读写分离
- 隐藏后端数据库拓扑

这类东西本质上是数据库访问中间层。
