## 一、这次面试涉及的核心知识点

### 1. Java 基础与 JVM

- 类加载器
- 类加载过程
- 双亲委派模型
- Tomcat 自定义类加载器
- `final` 修饰类、方法、变量的语义

这里真正要掌握的不是名词，而是逻辑关系：

1. Java 类从 `.class` 文件进入 JVM，要经历加载、链接、初始化。
2. 类加载器决定“谁来加载类”。
3. 双亲委派决定“加载顺序和查找顺序”。
4. 容器如 Tomcat 因为要隔离不同应用，所以会扩展默认类加载体系。

#### 类加载过程整理

当程序首次主动使用某个类时，如果该类还没有被 JVM 加载，就会经历下面几个阶段：

1. **加载（Loading）**
   JVM 读取类的字节码，并在内存中生成对应的 `Class` 对象。

2. **链接（Linking）**
   链接又分为三部分：
   - 验证：校验字节码是否合法
   - 准备：为类变量分配内存并设置初始值
   - 解析：把符号引用替换为直接引用

3. **初始化（Initialization）**
   执行类变量赋值和静态代码块。

需要纠正的一点：  
原笔记里写“系统会通过加载，连接，初始化三步来实现这个类进行初始化”，表述不准确。更准确地说，是 JVM 对类完成**加载、链接、初始化**，其中初始化只是最后一个阶段，不是这三步的总称。

#### 类加载器要点

常见类加载器：

- Bootstrap ClassLoader
- Extension / Platform ClassLoader
- Application ClassLoader

双亲委派的核心价值：

- 避免类重复加载
- 保证 Java 核心类库不被应用随意篡改

Tomcat 自定义类加载器的意义：

- 不同 Web 应用之间类隔离
- 支持同一容器下部署多个依赖版本不同的应用
- 打破纯双亲委派，以满足容器场景的灵活加载需求

### 2. 并发基础

原笔记里提到了：

- `wait`
- `notify`
- `notifyAll`
- `finalize`
- `await`

这里要理顺，否则很容易混。

#### `wait/notify/notifyAll`

它们属于 `Object`，用于线程间通信，必须在同步块中使用。

- `wait()`：当前线程释放锁并进入等待
- `notify()`：随机唤醒一个等待线程
- `notifyAll()`：唤醒所有等待线程

关键点：

- `wait` 会释放当前对象监视器锁
- `sleep` 不会释放锁
- `wait/notify` 依赖 `synchronized`

#### `await`

`await()` 通常来自 `CountDownLatch`、`CyclicBarrier`、`Condition` 等并发工具，不属于 `Object`。  
它是 JUC 并发包体系的一部分，和 `wait/notify` 不是一套机制。

#### `finalize`

`finalize()` 是对象回收前可能被 JVM 调用的方法，但它不可靠，也不应该再作为资源释放机制使用。现代 Java 开发里，不应该把它作为重点实践方案，知道它的历史意义即可。

### 3. 集合与线程安全

原笔记写了：

- `hashtable map current`

应该整理成：

- `HashMap`：非线程安全
- `Hashtable`：线程安全，但整体同步，性能一般
- `ConcurrentHashMap`：高并发下更常用

面试时应该能说清楚：

1. `HashMap` 为什么线程不安全
2. `Hashtable` 为什么性能差
3. `ConcurrentHashMap` 在 JDK 1.7 和 1.8 的实现差异

## 二、Web 请求链路要理顺

原笔记里这些点其实是连在一起的：

- SpringMVC -- Servlet
- filter
- listener
- HTTP 请求流程
- SpringMVC 源码
- session
- cookie
- 怎么标记是同一个会话

### 1. Servlet、Filter、Listener、SpringMVC 的关系

应该从容器视角理解：

1. 浏览器发起 HTTP 请求
2. 请求先进入 Servlet 容器（Tomcat）
3. 经过 Filter 链
4. 到达目标 Servlet
5. 如果是 SpringMVC 项目，核心 Servlet 一般是 `DispatcherServlet`
6. `DispatcherServlet` 再分发给对应的 Controller
7. Controller 执行业务逻辑后返回视图或 JSON

### 2. Filter 和 Listener 的区别

#### Filter

用于拦截请求与响应，常见用途：

- 登录校验
- 编码处理
- 日志记录
- XSS/跨域处理

#### Listener

用于监听容器事件，常见用途：

- 容器启动初始化
- Session 创建与销毁监听
- ServletContext 生命周期监听

原笔记里的 `filter listerer` 有拼写问题，应为 `listener`。

### 3. Session 和 Cookie 的关系

这个点面试非常高频。

- `Cookie` 保存在浏览器端
- `Session` 保存在服务端
- 浏览器通过 Cookie 中的 Session ID 来标识“这是同一个会话”

更准确地说：

1. 服务端第一次创建 Session 时，会生成一个 Session ID
2. 这个 ID 一般通过 Cookie（如 `JSESSIONID`）返回给浏览器
3. 浏览器后续请求带上这个 Cookie
4. 服务端通过这个 ID 找回对应 Session

所以“怎么标记是同一个会话”的答案通常是：

- 默认靠 Cookie 中保存的 Session ID
- 如果禁用 Cookie，也可能通过 URL 重写等方式传递

### 4. SpringMVC 源码最少要知道什么

不要一上来就死抠所有源码细节，先建立主流程：

1. 请求进入 `DispatcherServlet`
2. 找到对应的 `HandlerMapping`
3. 找到对应的 `HandlerAdapter`
4. 调用 Controller
5. 返回 `ModelAndView` 或响应体
6. 视图解析或消息转换后输出给客户端

## 三、MySQL 这部分要修正结论

原笔记中最需要改正的是这段：

> 如果一个表有3个字段，姓名，年龄，地址，我想 select from table where 地址=上海 order by 年龄  
> 我也是回答的地址+年龄，然而只需要地址就可以了  
> 原因是因为mysql索引下推，只用建立地址一个索引就够了

这个结论不严谨，甚至在大多数情况下是错误的。

### 1. 这个 SQL 到底该怎么分析

假设 SQL 是：

```sql
select *
from table
where 地址 = '上海'
order by 年龄;
```

#### 如果只有 `地址` 单列索引

那么 MySQL 可以利用索引先过滤出“地址=上海”的记录，但**排序字段是 `年龄`**，通常仍然需要额外排序，常见表现就是 `Using filesort`。

也就是说：

- `地址` 索引可以帮助过滤
- 但不一定能直接避免排序

#### 如果有联合索引 `(地址, 年龄)`

那么在 `where 地址 = ? order by 年龄` 这种场景下，联合索引更有机会同时完成：

- 按地址过滤
- 按年龄有序输出

这才是更典型、更稳定的优化思路。

### 2. 索引下推不是这个意思

原笔记把“索引下推”和“避免排序”混在了一起，需要分开：

#### 索引下推（ICP）

Index Condition Pushdown 的意思是：  
MySQL 在存储引擎层就尽量利用索引条件过滤数据，减少回表次数。

它解决的是：

- 能否在更早阶段过滤掉不满足条件的记录

它**不等于**：

- 只要有 where 的单列索引，就一定不需要排序

#### 覆盖索引

如果查询的字段全部包含在索引中，就不需要回表，这叫覆盖索引。

它解决的是：

- 是否需要再回主键索引/聚簇索引取整行数据

它也**不等于**：

- 自动满足 `order by`

### 3. 这类题更稳妥的回答方式

可以这样答：

1. 先看 `where` 条件能否命中索引
2. 再看 `order by` 能否利用索引顺序避免额外排序
3. 如果查询列很多，还要考虑是否能形成覆盖索引
4. 最终索引设计要结合真实数据分布、选择性、更新成本和查询模式

这样回答比“只建地址索引就够了”严谨得多。

### 4. 大表加字段和重建索引

原笔记这两块其实很有价值，可以补得更完整。

#### 给百万/千万/亿级表加字段

常见策略：

- 小表、低峰期直接 `ALTER TABLE`
- 大表优先评估 Online DDL 能力
- 超大表考虑影子表、双写、分批迁移
- 变更前必须评估锁表风险、回滚方案、主从延迟

#### 实际业务中可以删索引再重建吗

可以，但不能只从“耗时长不长”判断，而要考虑：

- 删除期间查询是否退化
- 是否影响其他 SQL
- 是否造成锁等待或业务抖动
- 重建过程是否可在线

也就是说，生产环境里索引变更属于正式变更，不是临场试错。

### 2. Redis 跳表表述修正

原笔记写：

> Redis 跳表 get耗时是线性的

这个不准确。  
跳表的查找、插入、删除平均时间复杂度通常是 **O(log n)**，不是线性 O(n)。

更准确的表述应该是：

- Redis 有序集合底层使用跳表与哈希表配合
- 跳表适合范围查询和有序遍历
- 平均查找复杂度是 O(log n)
