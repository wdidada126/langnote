### Oracle：存储层智能卸载（Exadata Smart Scan）

Oracle 提高时间利用率最典型的底层机制是 Smart Scan（智能扫描），核心思想是把过滤计算下沉到存储服务器，而不是把原始数据全搬到数据库服务器再过滤。

底层过程：
1. 谓词下推：查询 `SELECT customer_name FROM calls WHERE amount > 200` 时，`WHERE amount > 200` 的过滤直接在存储服务器的单元格（Cell）内执行。
2. 列过滤：只把 `customer_name` 这一列从存储层传回数据库层，而不是整行数据。
3. 效果：如果表有 1TB 数据，但查询结果只有 2MB，那么只有 2MB 的数据会在存储服务器和数据库服务器之间传输。这大幅减少了 I/O 通信和数据库服务器的 CPU 消耗。

### StarRocks：向量化执行 + 排序键跳读

StarRocks 的时间利用率优势来自两个层面的配合：存储层让数据“可跳读”，执行层让 CPU“批处理”。

存储层：排序键与前缀索引
StarRocks 在写入时按排序键（Sort Key）对数据物理排序，并构建前缀索引（每 1024 行取第一个排序键值作为索引项，索引大小仅为数据的约 1/1024）。
*   底层效果：当查询条件包含排序键前缀（如 `WHERE site_id = 123 AND city_code = 2`）时，可以通过二分查找直接跳过绝大多数无关数据块。如果查询只涉及排序键的第二列（如只查 `city_code`），则排序效果失效，退化为全表扫描。

执行层：向量化 + SIMD
传统数据库逐行处理，每行都伴随函数调用开销。StarRocks 以向量（通常 1024~4096 行） 为单位批量处理，充分利用 CPU 的 SIMD（单指令多数据） 指令集。
*   底层效果：一条 CPU 指令可以并行完成一批数据的过滤或计算，CPU 流水线利用率大幅提升。实测在聚合查询中，内存访问效率比行存数据库高 70% 以上。

总结：Oracle 靠硬件协同的存储卸载加速，StarRocks 靠软件层面的列式批处理与索引跳读加速。

### `EPOLLOUT` 事件的触发条件

`EPOLLOUT` 表示关联的文件描述符当前可写，而不是“上一次写操作完成了”。它的触发条件在 LT 和 ET 模式下有不同的表现：

水平触发 (LT) 模式
- 核心逻辑：只要 socket 的发送缓冲区未满，`EPOLLOUT` 事件就会持续触发。这意味着，如果你在 `epoll_wait` 返回后没有向 socket 写入数据，下一次 `epoll_wait` 还会立刻返回 `EPOLLOUT`。
- 初始状态：当一个 TCP 连接建立成功时，内核会首先触发一次 `EPOLLOUT`，通知应用程序“这个连接现在可以写数据了”。

边缘触发 (ET) 模式
- 核心逻辑：`EPOLLOUT` 仅在状态从“不可写”变为“可写” 时触发一次。
- 状态转换：这种“不可写 → 可写”的转换，通常发生在你尝试 `write` 并因为发送缓冲区满而返回 `EAGAIN` 之后。当对端读取数据，发送缓冲区有空间时，`EPOLLOUT` 才会被再次触发。

### 事件通知的本质：状态更新，而非单一事件

有一个容易混淆的点：当 `epoll_wait` 返回时，它返回的是文件描述符当前所有满足条件的状态集合。

在内核的 `tcp_poll` 方法中，会检查 socket 的多种状态（可读、可写、错误等）。例如，当有新数据到达触发 `EPOLLIN` 时，内核会重新检查所有条件。如果此时发送缓冲区也是可写的，那么返回的事件掩码就会包含 `EPOLLIN | EPOLLOUT`。

因此，即使处于 ET 模式，`EPOLLOUT` 也可能“附赠”在 `EPOLLIN` 事件中一起返回。这不意味着 `EPOLLOUT` 作为一个独立的“边沿事件”被触发了，它只是通知你“当前 socket 的状态是可读且可写的”。

### 编程实践中的常见陷阱

1. 死循环与 CPU 飙高
在 LT 模式下，如果注册了 `EPOLLOUT` 并且程序逻辑是“收到 `EPOLLOUT` 就 write，write 成功后又立刻 `epoll_wait`”，由于发送缓冲区通常不为满，`EPOLLOUT` 会再次立刻触发，导致程序陷入无限循环，占满 CPU。
- 正确做法：在 LT 模式下，不要一直监听 `EPOLLOUT`。仅当需要发送数据但 write 遇到 EAGAIN 时，才通过 `epoll_ctl` 添加 `EPOLLOUT` 监听；数据发送完毕后，立即移除 `EPOLLOUT` 监听。

2. Netty 的实战教训
Netty 在修复其 epoll 传输的 Bug 时也遇到过类似问题。当 Channel 仅被注册但尚未激活时，`epoll_wait` 可能会因为持续的 `EPOLLHUP` 事件而立即返回，造成高 CPU 占用的空转。修复方案是延迟到 Channel 激活后再进行注册。另一个漏洞则涉及半关闭连接收到 RST 后未正确关闭，导致 `epoll_wait` 在事件循环中100% CPU 忙循环。

### 与 `write` 行为的关联

理解 `EPOLLOUT` 需要结合 `write` 的语义：
- 当 socket 发送缓冲区有足够空间时，`write` 将数据拷贝到内核缓冲区后立即成功返回（非阻塞模式）。
- 当发送缓冲区已满时，`write` 会返回 `EAGAIN` 错误（非阻塞模式）。
- `EPOLLOUT` 的再次触发（ET 模式），正是依赖于对端读取数据后，本地发送缓冲区从满变为不满这一状态变化。

### 总结建议

| 模式 | EPOLLOUT 行为 | 编程要点 |
| :--- | :--- | :--- |
| 水平触发 (LT) | 发送缓冲区未满则持续触发。 | 按需注册/注销，避免死循环。数据未发完且 write 返回 EAGAIN 时再监听。 |
| 边缘触发 (ET) | 仅在“不可写”变为“可写”时触发一次。 | 必须在 write 返回 EAGAIN 后，才依赖下一次 EPOLLOUT 来继续发送。 |

核心原则是：将 `EPOLLOUT` 视为一个“可以尝试写入”的信号，而不是一个“必须写入”的命令。在 LT 模式下尤其要注意控制监听的开启与关闭。

### 子查询改写的核心：去关联（Decorrelate）

相关子查询的性能问题在于，外层每有一行数据，子查询就要执行一次。如果外层有 1000 万行，子查询就重复 1000 万次。去关联的目标，就是把它等价改写成一次性的 `JOIN` 或聚合，让优化器能对整体做统一的代价评估。

以你熟悉的模式为例：
```sql
select * from t1 where t1.a < (select sum(t2.a) from t2 where t2.b = t1.b)
```
改写的关键判断是关联条件 `t2.b = t1.b` 是等值连接。利用这个等值关系，可以把子查询变成按 `t2.b` 分组的聚合，再与外层 `t1` 做 `JOIN`。

改写后：
```sql
select t1.* from t1, (select b, sum(a) sum_a from t2 group by b) t2 
where t1.b = t2.b and t1.a < t2.sum_a
```
这样，子查询从“外层驱动、逐行执行”变成了“一次聚合 + 一次 Join”。

### 改写不是永远划算，存在权衡

去关联不是无条件更优。改写前后的执行特性有本质差异：

未去关联时，子查询虽然重复执行，但每次都可以利用关联列上的索引进行精准过滤。例如 `t2.b` 上有索引，每次传入一个 `t1.b` 的值，都能用 `IndexRangeScan` 快速定位少量数据。

去关联后，子查询只执行一次，但如果改写后的 Join 方式选择了 `HashJoin`，可能需要对 `t2` 做全表扫描来构建哈希表，单次执行的开销反而增大。

因此，去关联的收益取决于一个核心判断：“重复多次但每次很快”和“执行一次但可能较慢”哪个总代价更低。TiDB 的做法是同时评估“去关联”和“不去关联”两类候选计划，选代价更低的。你也可以通过 `NO_DECORRELATE` Hint 强制禁止改写。

### 与你提到的几个概念的联系

CTE 在子查询改写中常作为中间步骤。将去关联后的聚合结果放进一个 CTE，既提升了可读性，也方便优化器决策是内联（merge）还是物化（materialize）。对于递归查询（如组织架构树），递归 CTE 是标准且高效的写法。

Group Join 可以理解为去关联的一种产物：当子查询是 `GROUP BY` 聚合且关联列恰好是分组键时，改写后的形态天然就是一个“分组后 Join 原表”的模式。

Join Reorder 是你之前投入较多的方向，和子查询改写的关联在于：一旦子查询被改写成 `JOIN`，优化器的 join reorder 模块就获得了更大的搜索空间，可以决定这个新加入的表放在 Join 树的哪个位置代价最低。反过来，如果不去关联，Join 树里就没有它的位置，reorder 也帮不上忙。所以去关联为 join reorder 创造了施展条件，但最终是否采纳去关联后的计划，要由包含 reorder 结果的整体代价来决定。

SPM 在你的语境里是计划管理的收口工具。当一个 SQL 的去关联/不去关联决策在统计信息变化后发生摇摆，导致计划突变、性能回退时，SPM 提供了一种“稳定当前可接受计划”的机制。

### 关于你提到的三层视角

优化器是你最想做的方向。它的核心任务是在计划空间里搜索，用统计信息和代价模型选一个“足够好”的计划。子查询改写、join reorder 都是优化器对计划空间做变换的手段。

执行层把优化器选出的物理计划落实为算子调度。火山模型是最经典的执行框架，向量化和编译执行是当前提升执行效率的主流优化路径。去关联改写后的计划是否真的更快，最终要在执行层兑现。

存储层决定了数据的物理布局和访问成本。同样的去关联改写，在存储层有合适索引时，可能 `IndexJoin` 就很划算；没有索引时，可能 `HashJoin` 的全扫描代价更低。存储层的索引结构、聚簇方式（如 InnoDB 的聚簇索引）直接影响优化器的选择空间。

你写子查询改写的文章时，可以把这个“改写产生候选计划 → 优化器代价决策 → 执行层兑现收益”的链条串起来讲，这样比单纯罗列改写规则更有深度。

## CTE（Common Table Expression，公共表表达式）

CTE 是 SQL 中的一种命名临时结果集，用 `WITH` 子句定义，作用域限定在紧随其后的那条查询里。

```sql
WITH t2_agg AS (
    SELECT b, SUM(a) AS sum_a FROM t2 GROUP BY b
)
SELECT t1.* FROM t1, t2_agg WHERE t1.b = t2_agg.b AND t1.a < t2_agg.sum_a;
```

核心机制在于物化与内联的选择。 CTE 定义之后，优化器有两种处理方式：

- 物化（Materialize）：先把 CTE 的结果算出来存到临时表，后续每次引用都读这个临时表。适合 CTE 被多次引用、且每次重新计算代价高的场景。
- 内联（Inline/Merge）：把 CTE 定义直接展开到引用位置，不单独物化。适合 CTE 只被引用一次的场景，避免物化的额外开销。

递归 CTE 是特殊形态，用 `WITH RECURSIVE` 定义，包含一个锚点成员（基础情况）和一个递归成员，反复迭代直到不再产生新行。典型场景是组织架构树、图遍历、BOM 展开。递归 CTE 通常无法内联，必须物化并迭代执行。

与子查询改写的关系：去关联后的聚合结果常放进 CTE，既提升可读性，也让优化器在“物化还是内联”上有明确的决策点。有些数据库（如 PostgreSQL 12 之前）默认物化 CTE，12 之后改为默认内联、除非显式 `MATERIALIZED` 或多次引用，这个变化本身就是为了避免 CTE 被误当成优化屏障。

## Group Join

Group Join 不是 SQL 标准语法，而是优化器内部的一种计划形态或改写规则，描述的是“先对一侧分组聚合，再与另一侧做 Join”的模式。

考虑这个查询：

```sql
SELECT t1.* FROM t1 
WHERE t1.a < (SELECT SUM(t2.a) FROM t2 WHERE t2.b = t1.b);
```

去关联后：

```sql
SELECT t1.* FROM t1, 
    (SELECT b, SUM(a) AS sum_a FROM t2 GROUP BY b) t2_agg
WHERE t1.b = t2_agg.b AND t1.a < t2_agg.sum_a;
```

这里的 `t2_agg` 就是“按 `t2.b` 分组后的聚合结果”，再与 `t1` 做 Join。分组键恰好是关联列，这是 Group Join 能成立的关键条件——因为关联是等值的，才能把逐行的关联聚合转化为按关联列的一次性分组聚合。

为什么它重要：它把相关子查询从“外层驱动、逐行执行”改写成“一次分组聚合 + 一次 Join”，是去关联最常用的产出形态之一。改写后，优化器获得了完整的 Join 树，可以进一步做 join reorder，决定 `t1` 和 `t2_agg` 谁做驱动表、用哪种 Join 算法。

代价权衡：Group Join 不是无条件更优。如果 `t2.b` 上有索引，不去关联时每次传入一个 `t1.b` 都能走索引精准定位；去关联后如果选择 HashJoin，可能要对 `t2` 全表扫描一次来建哈希表。所以优化器要同时评估改写前后两类计划，选代价低的。TiDB 中可用 `NO_DECORRELATE` Hint 禁止这类改写。

## SPM（SQL Plan Management，SQL 计划管理）

SPM 解决的是一个运维层面的问题：同一条 SQL，因为统计信息变化、参数变化或优化器版本升级，执行计划突然变了，性能大幅回退。

它的核心思路是：不直接信任优化器每次现算的计划，而是维护一组“已认可的计划”（Plan Baseline），让优化器只能在这些基线计划里选，或者只有当新计划被验证确实更优时才允许替换。

工作流程大致是：

1. 捕获（Capture）：一条 SQL 首次执行时，优化器生成的计划被记录为基线。
2. 演进（Evolve）：后续执行时，优化器可能生成新计划。新计划不会立即生效，而是先被验证——如果它的代价明显低于现有基线，才被接纳为新的基线。
3. 固定（Fix）：一旦某条 SQL 被标记为“计划已固定”，优化器就只能从基线计划里选，禁止自由探索，从而保证计划稳定。

Oracle 的 SPM 是最经典的实现，通过 `DBMS_SPM` 包管理，计划基线存在数据字典里。TiDB 的 SPM 形态略有不同，主要围绕 `CREATE PLAN BASELINE`、`BINDING` 等机制，用于固定执行计划、避免计划抖动。

与去关联/join reorder 的关系：去关联和 join reorder 都是优化器自由探索计划空间的手段，收益是可能找到更优计划，风险是计划可能抖动。SPM 是收口工具——当某个改写决策在统计信息变化后反复摇摆、导致性能回退时，SPM 提供一种“稳定在当前可接受计划”的机制。两者是一放一收的关系。

## 三者放在一起看

- CTE 是 SQL 层的语法结构，优化器要决定物化还是内联。
- Group Join 是优化器改写相关子查询时产生的一种计划形态，把逐行关联聚合变成一次分组聚合加 Join。
- SPM 是运维层的计划稳定机制，在优化器自由探索和计划稳定性之间做平衡。

它们共同指向一个主题：优化器的自由度和可控性之间的权衡。CTE 的物化/内联、Group Join 的改写/不改写、SPM 的固定/演进，都是这个权衡在不同层面的体现。

你提到的这几个方向，核心论文脉络确实存在明显的重叠——尤其是子查询去关联、join reorder 和 CTE 优化，很多工作都绕不开微软、Oracle 和学术界那条从 APPLY 算子到代价决策的路线。以下按主题整理一份可追溯的论文列表，方便你对照自己看过的内容。

### 简要的脉络总结

你提到的“overlap”感，来源于这条线其实高度集中：
1. Dayal (1987) 最早统一了嵌套查询的框架；
2. Galindo-Legaria & Joshi (2001) 和微软系列把 APPLY 算子形式化，明确了“去关联只是一个中间正常形式，最终仍要代价决策”这个关键认知；
3. Bruno et al. (2025) 的 Fabric DW 工作是对这条线最新的工业总结，Class 1/2/3 的划分基本成了讨论去关联边界时的通用语言；
4. Outerjoin Simplification (1997) 和 join reorder 的工作，则是在去关联产出 Join 树之后，决定“怎么排”的那一步。

如果你要写子查询改写的文章，建议以 APPLY 移除 + 代价决策 作为主线，而不是单纯罗列改写规则——这样能把你提到的 join reorder、CTE 物化、SPM 收口都自然地串进来。

“APPLY 移除 + 代价决策”这条主线可以拆成三层来看：归一化（把子查询变成 Apply）、去关联（尝试消除 Apply）、代价决策（决定是否真的消除）。前两步是逻辑等价变换，第三步才是优化器真正体现“智能”的地方。

### 归一化：为什么需要 Apply

子查询之所以难优化，根本原因在于它藏在表达式中（比如 `WHERE t1.a < (SELECT ...)`），而不是以一个独立关系算子的形式存在。优化器擅长处理的是 Projection、Join、Aggregation 这些关系算子之间的等价变换，但一个嵌在 Filter 条件里的子查询，让规则匹配变得很别扭。

Apply 算子的引入就是为了解决这个问题。它的语义是：对于外层关系 R 的每一行 r，把 r 作为参数传入内层参数化表达式 E，计算 E(r)，再与外层做某种连接（⊗）。根据 ⊗ 的不同，Apply 有四种形态：Cross Apply、Left Outer Apply、Semi Apply、Anti-Semi Apply，分别对应子查询在 SELECT 列表、FROM 子句、EXISTS、NOT EXISTS 中的使用。

关键点：Apply 保留了子查询的“相关”语义，但它已经是一个逻辑算子了。优化器可以像处理 Join 一样对它应用规则。

### 去关联：Apply 移除的规则体系

有了 Apply，接下来的事情就是尝试消除它——把参数化执行变成集合执行。核心思路可以用一句话概括：把 Apply 下面的算子往上提，把 Apply 上面的算子往下推，直到右侧不再引用左侧的参数。

一套完整的去关联规则通常包括：

基本消除规则：如果 Apply 的右侧不包含来自左侧的参数（即不相关），那么 Apply 直接退化为普通 Join。这是最平凡的情况。

把选择下推/上提：如果 Apply 右侧是一个 Selection，且其条件中包含了关联变量，这个 Selection 可以被“拉”到 Apply 之上，条件是变成 Apply 的附加谓词。一旦关联条件被挪走，右侧就不再相关了。

把聚合上提：这是最需要小心的一类。如果 Apply 右侧是一个 Aggregation（比如 `SUM`），且分组键就是关联列，那么可以把聚合拉到 Apply 之上。这在语义上要求分组键与关联列匹配，典型场景就是 `t2.b = t1.b` 这种等值关联——把子查询改写为 `t2` 按 `b` 分组聚合，再与 `t1` 做 Join。

Max1Row 处理：标量子查询语义要求右侧最多返回一行。在 Apply 中通常插入一个 `MaxOneRow` 算子来保证这一点，去关联时也要相应处理。

这套规则在理论上可以处理所有确定性的 SQL 子查询。TiDB 沿袭了这套思路，在逻辑优化阶段由 `decorrelateSolver` 尝试将 Apply 转换为 Join。

### 代价决策：为什么不能无脑去关联

这是整条主线里最值得强调的一步。去关联是一个逻辑等价变换，但执行效率上不一定更优。

原因在于执行特性的根本差异：

不去关联时（保留 Apply），外层每行驱动一次子查询执行。如果关联列上有索引，每次传入一个 `t1.b` 的值，都能走索引精准定位少量数据。虽然执行次数多，但每次极快。TiDB 文档中明确指出，当外层值很少时，不做去关联可能反而更好。

去关联后（变成 Join），子查询只执行一次。但如果改写后的 Join 选择了 HashJoin，可能需要对 `t2` 做全表扫描来构建哈希表。单次执行的开销远大于多次索引查找的总和。TiDB 的实际测试显示，去关联后计划变成 `HashJoin + HashAgg`，而保留 Apply 时内层走的是 `IndexRangeScan`。

所以，去关联的收益取决于“重复多次但每次很快”和“执行一次但可能很慢”哪个总代价更低。这必须由代价模型来裁决。

### 优化器框架的支撑：为什么需要 Volcano/Cascade

这个决策对优化器框架有硬性要求：必须能同时考虑逻辑等价规则和代价选择。TiDB 的文档说得很直白：“只有 Volcano 或 Cascade Style 的优化器，可以同时考虑逻辑等价规则和代价选择”。

为什么？因为优化器需要同时生成并评估两类候选计划：
1. 去关联后的计划（Join 形态）
2. 保留 Apply 的计划（参数化执行形态）

在 Volcano/Cascade 框架下，这两类计划是同一逻辑表达式（原始 Apply 表达式）的不同物理实现候选。优化器在探索阶段同时考虑 `ApplyToJoin` 和 `ApplyToNL` 等规则，生成多个候选，再由代价模型统一比较。

SQL Server 的实现很好地说明了这一点。即使查询写法是 `JOIN`，优化器也可能在代价优化阶段探索 `JoinToIndexOnTheFly` 规则，把 Join 转换成带 Eager Index Spool 的 Apply 形态；反过来，用 `APPLY` 写的查询，`ApplyHandler` 规则也会先把它转成 Join 形态，再在后续阶段考虑是否重新引入 Apply。写法不决定最终计划形态，代价才决定。

### 可控性：当代价决策“失败”时

代价模型可能因为统计信息不准而做出错误选择。TiDB 提供了 `NO_DECORRELATE` Hint，允许手动禁止对特定子查询做去关联，强制保留 Apply 执行。文档建议在“外层值很少、子查询可利用索引”的场景下使用这个 Hint，并配合 SQL Plan Management 来稳定计划。

这回到了你之前提到的 SPM：去关联和 join reorder 是优化器自由探索的手段，SPM 是当这种自由度导致计划抖动时的收口工具。

### 小结

“APPLY 移除 + 代价决策”这条主线的完整逻辑是：

1. 归一化：把任意位置的子查询统一提取为 Apply 算子，使其进入关系算子的世界。
2. 去关联规则：通过上提/下推变换，在逻辑上消除 Apply 的相关性，为 Join 化创造条件。
3. 代价裁决：生成去关联和不去关联两类候选计划，用代价模型选择更优者。
4. 人工兜底：当代价选择不理想时，用 Hint 和 SPM 干预。

你写子查询改写文章时，可以把“去关联是变换，不是优化；优化发生在变换之后”作为核心论点，这样就能自然地把 join reorder（去关联后 Join 树的排序空间）、CTE 物化（去关联后聚合结果的中间表示）、SPM（计划稳定性保障）都串进来。
