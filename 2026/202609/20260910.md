你列的这 9 条都是 C/C++（以及系统/数据库）里非常典型、也确实容易踩的坑。逐条展开一点，并补上一些“为什么”和“怎么防”：

1. `volatile` 不是线程锁，也不是原子类型。

`volatile` 只告诉编译器“这个对象可能被外部因素改变，别把它优化进寄存器/别删掉访问”，它不提供：

- 原子性
- 内存序（memory ordering）
- 互斥

多线程下应该用 `_Atomic` / `stdatomic.h`、`pthread_mutex`、C++ 的 `std::atomic`、`std::mutex` 等。`volatile` 适合的场景基本只有：内存映射 I/O 寄存器、信号处理里与 `sig_atomic_t` 配合的极少数情况。


2. `memcpy` 的源和目标重叠时是 UB，使用 `memmove`。

标准规定 `memcpy` 要求源和目标不重叠。重叠时用 `memmove`，它保证像先复制到临时缓冲区一样正确。

实践里还有个坑：有些实现里 `memcpy` 在重叠时“看起来能工作”，于是代码带着 UB 上线，换编译器/优化级别后炸掉。

3. 负数传给 `memcpy` 的长度参数会变成巨大的无符号数。

`memcpy` 的第三个参数是 `size_t`，是有符号 `int` 负数时会隐式转换成很大的无符号值，直接越界写/读。

防法：

- 长度用 `size_t` 计算和传递；
- 从 `int`/`ssize_t` 转 `size_t` 前先检查 `< 0`；
- 打开 `-Wsign-conversion`、`-Wconversion` 之类警告。

4. 非 void 函数必须在所有路径返回值。

C 里“走到函数末尾却没 return”再使用返回值是 UB（C99 起 `main` 是例外，隐式 `return 0`）。C++ 里同样是 UB（除 `main` 等少数）。

常见坑：

```c
int f(int x) {
    if (x > 0) return 1;
    // 忘了 else / return
}
```

开 `-Wreturn-type`，并且让函数尽量单出口或显式 `return`。

5. `snprintf` 只在“指针仍在数组内且容量计算正确”时安全。

`snprintf(buf, size, ...)` 的 `size` 是缓冲区总大小，不是“可写字符数”。返回值是“假如空间足够会写多少字符”（不含 `\0`），可能大于 `size`，所以：

- 不能拿返回值当“实际写入长度”去索引；
- 拼接时要用 `size_t` 做剩余容量计算，别用 `int`；
- 指针要始终指向数组内，别 `buf + len` 越界后再传给下一次 `snprintf`。

安全拼接模式：

```c
size_t off = 0;
int n = snprintf(buf + off, sizeof buf - off, "...");
if (n < 0) { /* 错误 */ }
if ((size_t)n >= sizeof buf - off) { /* 截断 */ }
else off += (size_t)n;
```


6. `int f();` 在 C 中不是严格的无参数声明，应写 `int f(void);`。

C 里 `int f();` 是“旧式声明”，表示参数未指定（K&R），不是“无参数”。调用时可能传入任意参数而不报错，和定义 `int f(void)` 也不一定兼容。

C++ 里 `int f();` 才表示无参数。所以跨语言头文件、严格 C 代码里应写 `int f(void);`。


7. `malloc` 失败策略必须全项目一致，不能底层退出、上层又假装能够返回错误。

这是架构一致性问题。要么：

- 全项目“分配失败即致命”，底层直接 abort/exit，上层不需要检查；
- 要么全项目“分配失败可恢复”，每层都检查并向上返回错误。

最糟的是混合：底层 `xmalloc` 失败就 `exit(1)`，上层却写 `if (!p) return -ENOMEM;`，这段错误处理永远走不到，测试也测不出，真出问题时进程直接死，上层清理逻辑全废。

8. 数据库不能忽略 `fsync` 失败；“写入成功”和“持久化成功”不是一回事。

`write()` 成功只说明数据到了内核页缓存，没到稳定存储。`fsync`/`fdatasync` 失败可能意味着：

- 设备写缓存丢失；
- 文件系统错误；
- 磁盘即将故障。

数据库/存储系统必须把 `fsync` 失败当成严重错误处理：重试、报错、进入只读/崩溃恢复，不能当没发生。否则会违反持久性（Durability），出现“事务提交了但掉电后数据没了”。

另外还要注意：`fsync` 只刷文件数据，目录项持久化要 `fsync` 目录；某些文件系统上还需要 `fdatasync` 与 `fsync` 的取舍。


9. 编译通过不等于没有 UB，单个测试通过也不等于线程和错误路径安全。

- 编译通过只说明语法/类型大致合法，UB 往往在运行时才表现，甚至“现在看起来正常”。
- 单个测试通过只覆盖一条路径；线程竞争、错误路径、边界条件、资源耗尽、信号中断等都没被覆盖。
- 工具：`-fsanitize=address,undefined,thread`、Valgrind、静态分析器、模糊测试、压力测试、故障注入。
- 并发代码要专门做 race 检测和模型检查（如 ThreadSanitizer、CDSChecker 等）。

一句话总结：

这 9 条的共同主题是：C/C++ 里“看起来对”和“实际定义良好”之间差距很大；底层系统编程里“调用成功”和“语义成功”之间差距也很大。 要靠类型、约定、工具和测试一起兜底，而不是靠“编译过了、跑过一次没问题”。
