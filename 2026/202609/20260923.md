### JUC 中的实现类：ConcurrentLinkedQueue

`java.util.concurrent.ConcurrentLinkedQueue` 是 MS 算法在 Java 并发包中的直接落地。它基于 Michael-Scott 非阻塞算法的一种变体实现，依赖 CAS 而非锁来保证线程安全。

### 核心设计对应

1. 哨兵节点（dummy/sentinel node）

MS 算法使用 dummy 节点作为初始的 head 和 tail，避免空队列的边界判断。`ConcurrentLinkedQueue` 同样在初始化时将 head 和 tail 都指向一个空节点。

2. 两阶段入队与 “help” 机制

MS 算法的入队分两步：先 CAS 链接新节点到 `tail.next`，再 CAS 移动 `tail`。若中间状态被观察到，其他线程会通过检查 `tail.next != null` 来帮助推进 tail 指针。`ConcurrentLinkedQueue` 的 `offer` 方法实现了完全相同的逻辑：定位尾节点、CAS 设置 `next`、CAS 更新 `tail`，并在循环中“帮助”推进滞后的 tail。

3. 出队时推进 tail

MS 算法在出队时，若发现 `head == tail` 但 `head.next != null`，说明 tail 滞后，需要先 CAS 推进 tail，再移动 head。`ConcurrentLinkedQueue` 的 `poll` 方法同样包含了这一处理。

### 与标准 MS 算法的差异

`ConcurrentLinkedQueue` 并非逐行复刻，而是做了工程化优化。最典型的是引入了 `hops` 变量：Doug Lea 没有每次入队后都立即 CAS 更新 `tail`，而是等到 tail 与真正尾节点的距离超过阈值（默认 `HOPS = 1`）时才更新。这是为了减少 volatile 写操作的频率，用少量的定位开销换取更高的入队吞吐量。

### 一个容易混淆的点

JUC 中还有 `ConcurrentLinkedDeque`，它支持双端操作，但其内部实现并非标准 MS 算法——MS 算法本身是单端队列（FIFO）的算法。`ConcurrentLinkedDeque` 的双端支持需要更复杂的并发控制，与 MS 算法的设计目标不同。

在 libcds（Concurrent Data Structures）C++ 库中，MS 算法的对应实现类是 `MSQueue`，具体分为侵入式（intrusive）和非侵入式（non-intrusive）两个版本。

### 核心实现类

`cds::intrusive::MSQueue` 是 Michael & Scott 侵入式无锁队列。它要求存入的 `value_type` 类型必须派生自 `msqueue::node`，或者包含一个该类型的成员，或者能够转换为该节点类型。这种设计把队列节点直接嵌入用户数据结构，减少了内存分配开销。

`cds::container::MSQueue` 则是非侵入式版本，它基于侵入式实现构建，用户无需修改自己的数据结构定义，由队列内部负责节点的分配与管理。

### 头文件与垃圾回收

两个版本分别位于 `<cds/intrusive/msqueue.h>` 和 `<cds/container/msqueue.h>`。

关键约束在于模板参数 `GC`（Garbage Collector）：它只支持 Hazard Pointer 回收机制，即 `gc::HP` 和 `gc::DHP`，这是 MS 算法安全回收内存的必要条件。算法需要 2 个 hazard pointer。

### 基本接口

MSQueue 提供 `enqueue` / `dequeue` 作为主要操作，同时 `push` / `pop` 是同义函数。非侵入式版本还额外提供了带移动语义的 `enqueue(value_type&&)` 以及 `emplace` 原地构造方法。

### 在库中的定位

libcds 的 README 明确列出了 MSQueue 对应 Michael & Scott 1998 年论文《Simple, fast, and practical non-blocking and blocking concurrent queue algorithms》。同一库中还包含该算法的变体（如 flat combining queue、segmented queue）以及基于 Hunt 等人算法的 RWQueue。

使用 libcds 时有一个前置要求：线程在操作数据结构前必须绑定到库的线程管理器，这也是第三方评测中确认的约束。
