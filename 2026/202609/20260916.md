# 20260916
在数据库（DB）领域，丢失更新（Lost Update） 是并发控制中最经典的数据一致性问题之一。它描述的是：两个或多个事务并发修改同一数据时，后提交的事务覆盖了先提交事务的修改，导致先前的更新“丢失”。

下面从定义、发生条件、两种典型形态、与隔离级别的关系以及解决方案几个方面来解析。

## 一、定义

丢失更新指：事务 T1 和 T2 都读取同一数据并基于读取值进行修改，T2 的提交晚于 T1，但 T2 在写入时并未感知 T1 已经修改过该数据，结果 T1 的更新被 T2 覆盖，从最终结果看 T1 的修改好像从未发生过。

关键点：“读—改—写”序列在并发下交错，且写入时没有对已修改的数据做冲突检测。

## 二、发生条件

丢失更新通常需要满足：

1. 两个事务访问同一数据项；
2. 至少有一个事务对该数据项执行“读取后写入”（read-modify-write）；
3. 事务的读与写之间没有足够的隔离/锁保护；
4. 后写的事务在写之前没有检测到该数据已被其他事务修改。

## 三、两种典型形态

### 1. 第一类丢失更新（回滚丢失更新）

- T1 修改了数据但尚未提交；
- T2 也修改同一数据并提交；
- 随后 T1 因故回滚。
- 如果系统在回滚时直接把数据恢复为 T1 开始前的旧值，就会把 T2 已提交的修改一并抹掉。

这种问题在允许“脏写”或使用基于旧值回滚的系统中出现。现代数据库通过写锁/严格两阶段锁基本避免了第一类丢失更新。

### 2. 第二类丢失更新（提交覆盖丢失更新）

- T1 读取值 A=100；
- T2 读取值 A=100；
- T1 计算 A=100+10，写入 110 并提交；
- T2 计算 A=100+20，写入 120 并提交；
- 最终 A=120，T1 的 +10 丢失。

这是最常见、也是通常所说的“丢失更新”。它发生在读已提交（Read Committed） 隔离级别下，因为该级别只保证不读未提交数据，但不保证“读到的数据在写回前未被别人改过”。

## 四、与隔离级别的关系

| 隔离级别 | 是否可能发生第二类丢失更新 | 说明 |
|---|---|---|
| 读未提交 | 可能 | 并发控制最弱 |
| 读已提交 | 可能 | 只防脏读，不防丢失更新 |
| 可重复读 | 视实现而定 | 基于锁的实现通常可防；基于快照的实现（如 MVCC）可能出现“写偏差”或需额外检测 |
| 可串行化 | 不可能 | 保证等价于串行执行 |

注意：在基于 MVCC 的“快照隔离”下，第二类丢失更新可能以“写—写冲突”形式被检测到并回滚其中一个事务，也可能在“读—改—写”跨多个数据项时表现为更复杂的写偏差。因此不能简单说“可重复读一定没有丢失更新”。

## 五、示例（SQL）

假设账户余额 `balance = 100`：

```sql
-- T1
BEGIN;
SELECT balance FROM account WHERE id = 1;  -- 读到 100
-- 应用层计算 100 + 10 = 110
UPDATE account SET balance = 110 WHERE id = 1;
COMMIT;

-- T2 几乎同时
BEGIN;
SELECT balance FROM account WHERE id = 1;  -- 也读到 100
-- 应用层计算 100 + 20 = 120
UPDATE account SET balance = 120 WHERE id = 1;
COMMIT;
```

若 T1 先提交、T2 后提交，最终余额为 120，T1 的 +10 丢失。

## 六、解决方案

### 1. 悲观锁（Pessimistic Locking）

在读取时就加锁，阻止其他事务读写：

```sql
SELECT balance FROM account WHERE id = 1 FOR UPDATE;
```

这样 T2 必须等 T1 提交后才能读取，读到的就是 110，再计算为 130，不会丢失。

- 优点：简单可靠；
- 缺点：降低并发，可能死锁。

### 2. 乐观锁（Optimistic Locking）

在更新时检查版本号或时间戳：

```sql
UPDATE account
SET balance = 110, version = version + 1
WHERE id = 1 AND version = 5;
```

若影响行数为 0，说明数据已被他人修改，应用层重试或报错。

- 优点：读不加锁，并发好；
- 缺点：冲突多时重试成本高。

### 3. 提高隔离级别到可串行化

数据库自动检测冲突并回滚其中一个事务。应用需处理重试。

### 4. 原子更新

把“读—改—写”合并为一条原子语句：

```sql
UPDATE account SET balance = balance + 10 WHERE id = 1;
```

这样数据库在行锁保护下完成读和写，天然避免丢失更新。

### 5. 应用层串行化

对同一数据的修改走单线程/队列/分布式锁，从源头避免并发交错。

## 七、小结

- 丢失更新的本质：并发事务的“读—改—写”交错，后写覆盖先写。
- 第一类由回滚引起，现代数据库基本已解决；
- 第二类是读已提交下的典型问题，需通过锁、乐观锁、原子更新或更高隔离级别解决。
- 判断是否会发生，关键看：写回时是否检测到数据已被其他事务修改。

并发控制中最经典的数据一致性问题，通常围绕多个事务并发读写同一数据时，因交错执行而破坏一致性展开。业界常归纳为以下几类（不同教材分类略有差异，但核心就是这些）：

## 一、四大经典问题（按隔离级别递进）

### 1. 脏读（Dirty Read）

- 定义：事务 T1 修改了数据但尚未提交，T2 读取到了这个未提交的值。随后 T1 回滚，T2 读到的就是一个从未真实存在过的“脏”数据。
- 本质：读到了未提交的、可能被回滚的中间状态。
- 示例：
  - T1：`UPDATE account SET balance = 200 WHERE id = 1;`（未提交）
  - T2：`SELECT balance FROM account WHERE id = 1;` → 读到 200
  - T1：`ROLLBACK;` → 余额回到 100，T2 读到的 200 是脏数据
- 由谁防：读已提交（Read Committed）及以上。

### 2. 不可重复读（Non-Repeatable Read）

- 定义：同一事务内两次读取同一数据，期间另一事务修改并提交了该数据，导致两次读取结果不一致。
- 本质：读到了别人已提交的修改，同一事务内读值不稳定。
- 示例：
  - T1：`SELECT balance ...` → 100
  - T2：`UPDATE ... SET balance = 200; COMMIT;`
  - T1：`SELECT balance ...` → 200（同一事务内前后不一致）
- 由谁防：可重复读（Repeatable Read）及以上。

### 3. 幻读（Phantom Read）

- 定义：同一事务内两次执行同一范围查询，期间另一事务插入/删除了满足条件的行并提交，导致第二次查询“多出”或“少了”一些行。
- 本质：读到了别人已提交的新增/删除行，是“范围级”的不可重复读。
- 示例：
  - T1：`SELECT * FROM orders WHERE amount > 100;` → 5 行
  - T2：`INSERT INTO orders ... amount = 150; COMMIT;`
  - T1：再次 `SELECT ... WHERE amount > 100;` → 6 行
- 由谁防：可串行化（Serializable），部分数据库在可重复读下用间隙锁也能防。

### 4. 丢失更新（Lost Update）

- 定义：两个事务同时读取同一数据并基于读值修改，后提交者覆盖先提交者，导致先前的更新丢失。
- 本质：写覆盖，且写回时未检测数据已被他人修改。
- 示例：
  - T1、T2 都读到 balance=100
  - T1 写 110 提交；T2 写 120 提交 → 最终 120，T1 的 +10 丢失
- 由谁防：可串行化、悲观锁、乐观锁、原子更新。

## 二、丢失更新的两种细分

### 5. 第一类丢失更新（回滚丢失更新）

- T1 修改未提交，T2 修改并提交，T1 回滚时把 T2 的提交一并抹掉。
- 现代数据库通过写锁/严格两阶段锁基本已避免。

### 6. 第二类丢失更新（提交覆盖丢失更新）

- 即上面第 4 条最常见的丢失更新，发生在读已提交下。
- 需靠锁、乐观锁、原子更新或可串行化解决。

## 三、比丢失更新更隐蔽的问题

### 7. 写偏差（Write Skew）

- 定义：两个事务读取同一组数据的不同部分，各自基于读取结果修改不同的数据项，单独看都合法，但合在一起违反业务约束。
- 本质：快照隔离下，写的是不同行，写—写冲突检测不到，但语义上互相依赖。
- 经典示例（值班约束：至少一人在岗）：
  - 初始：Alice 和 Bob 都在岗
  - T1：查“在岗人数=2”，判断可以离开，把 Alice 设为离岗
  - T2：查“在岗人数=2”，判断可以离开，把 Bob 设为离岗
  - 两者写不同行，都提交 → 最终无人值班，约束被破坏
- 由谁防：可串行化；快照隔离下需显式 `SELECT ... FOR UPDATE` 或物化冲突。

### 8. 读偏差（Read Skew）

- 定义：事务内先读 A，另一事务修改 A 和 B 并提交，事务再读 B，导致读到 A 的旧值和 B 的新值，二者不一致。
- 本质：跨数据项的读不一致，破坏事务内的快照一致性。
- 示例：
  - 初始 A=100，B=100（约束 A=B）
  - T1 读 A=100
  - T2：A=50，B=50，提交
  - T1 读 B=50 → 看到 A=100、B=50 的不一致组合
- 由谁防：可重复读/快照隔离（保证整个事务读同一快照）。

### 9. 脏写（Dirty Write）

- 定义：一个事务覆盖了另一个未提交事务的修改。
- 本质：写—写冲突，且不等待对方提交/回滚。
- 危害：回滚时无法确定恢复到什么状态，是比脏读更严重的问题。
- 由谁防：几乎所有主流数据库默认都禁止脏写（即使读未提交也常加写锁）。

## 四、按“读—写”维度归纳

| 问题 | 读到了什么 | 典型隔离级别下是否可能 |
|---|---|---|
| 脏读 | 未提交的写 | 读未提交可能 |
| 不可重复读 | 已提交的修改 | 读已提交可能 |
| 幻读 | 已提交的新增/删除 | 读已提交、可重复读可能 |
| 丢失更新 | —（写覆盖） | 读已提交可能 |
| 脏写 | —（写覆盖未提交） | 基本被禁止 |
| 写偏差 | 同一快照，写不同项 | 快照隔离可能 |
| 读偏差 | 跨项不一致快照 | 读已提交可能 |

## 五、更完整的“全部”清单

如果按学术上较完整的并发异常分类，通常包括：

1. 脏读（Dirty Read）
2. 脏写（Dirty Write）
3. 不可重复读（Non-Repeatable Read / Fuzzy Read）
4. 幻读（Phantom Read）
5. 丢失更新（Lost Update）
   - 第一类丢失更新（回滚丢失）
   - 第二类丢失更新（提交覆盖丢失）
6. 读偏差（Read Skew）
7. 写偏差（Write Skew）
8. 幻写/谓词写偏差（Phantom Write / Predicate-Based Write Skew）
   - 写偏差的范围版本，涉及插入/删除满足谓词的行
9. 级联回滚（Cascading Rollback）
   - 一个事务回滚导致依赖它未提交数据的事务被迫回滚
10. 不可恢复调度（Unrecoverable Schedule）
    - 事务读了未提交数据，且该数据的事务后回滚，读方已提交无法回滚
11. 脏写导致的中间态丢失（Intermediate Lost Update）
    - 与脏写相关的一种细分

其中 1–7 是面试和教材最常考的“经典问题”，8–11 属于更深入的调度/恢复理论范畴。

## 六、一句话总结

经典数据一致性问题可概括为：

> 脏读、脏写、不可重复读、幻读、丢失更新（两类）、读偏差、写偏差，再加上恢复理论中的级联回滚、不可恢复调度。

它们的共同根源都是：并发事务的读—写交错，缺乏足够的隔离或冲突检测。解决手段无非是锁、时间戳/版本、快照、可串行化验证这几大类。
