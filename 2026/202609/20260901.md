toctou
竟态问题，如何解决

针对HTTP Web服务中数据库读写的TOCTOU（先检查后使用）竞态问题，核心解决思路是将“检查”和“更新”操作合并为一个不可分割的原子操作。下面是几种主流的解决策略，你可以根据业务场景选择。

### 最佳方案：在数据库层使用原子操作

这是最可靠、性能也较好的方式。核心思想是让数据库来完成条件判断和更新的组合动作，避免将数据读到应用层再判断。

1.  使用原子性的 `UPDATE` 或 `UPSERT` 语句
    这是最常见的实践。例如，在实现“任务认领”功能时，直接执行一条 `UPDATE`，在 `WHERE` 条件中同时包含状态检查和资格校验。如果 `UPDATE` 影响的行数为0，说明资源已被他人占用或条件不满足，直接返回失败。这种方式将检查和更新合并为一次数据库交互，从根本上消除了TOCTOU的时间窗口。

    ```sql
    -- 原子性地认领一个状态为 'todo' 或 'backlog' 且未被认领的任务
    UPDATE issues 
    SET status = 'doing', session = ? 
    WHERE id = ? 
      AND status IN ('todo', 'backlog') 
      AND owner_type = 'agent';
    -- 然后通过 affected rows (rowcount) 判断是否认领成功
    ```

2.  利用数据库的唯一约束或排他约束
    利用数据库自身的约束来保证数据的唯一性和不重叠性。例如，在预订系统中，可以使用PostgreSQL的 `EXCLUDE USING GIST` 约束，在数据库层面物理上防止时间段冲突或资源被重复预订，实现绝对的“数据完整性保证”。但这在高并发下可能带来性能开销。

3.  使用乐观锁
    为数据表增加一个版本号（`version`）或时间戳字段。更新时，在 `WHERE` 条件中带上当前版本号，并在 `SET` 中更新版本号。如果更新影响行数为0，说明数据已被其他请求修改，应用层可以重试或报错。HTTP API设计中的 ETag 机制就是乐观锁的体现。

### 备选方案：应用层引入锁机制

当业务逻辑复杂，无法完全用数据库语句表达时，可以考虑在应用层引入锁，但需注意其复杂性和性能损耗。

1.  悲观锁：使用 `SELECT ... FOR UPDATE`
    在事务中先查询数据并对查询到的行加锁，阻止其他事务修改，然后再执行更新逻辑，最后提交事务释放锁。这能有效防止并发修改，但会降低并发性能，并可能导致死锁。

2.  分布式锁
    对于分布式服务（多个实例），可以使用Redis或ZooKeeper实现分布式锁，确保同一时间只有一个服务实例能处理特定资源的请求。但这会增加系统复杂度和网络开销。

### 高级架构方案：混合架构 (Hybrid Architecture)

对于超大规模、超高并发的系统（如秒杀），可以采用一种混合架构：应用层作为第一道“过滤器”（例如异步队列）来缓冲流量、削峰填谷，快速拒绝明显无效的请求。真正的数据完整性校验，则交给后端的数据库原子操作来完成。这种方式可以同时兼顾高吞吐量和绝对的数据一致性。

### 总结与建议

*   优先推荐：使用数据库的原子UPDATE或乐观锁。它们实现简单，性能较好，能解决绝大多数HTTP Web服务的TOCTOU问题。
*   不要使用“先查后改”模式：`SELECT` -> 应用层判断 -> `UPDATE` 这种模式在并发下是危险的，应严格避免。
*   将逻辑尽可能推向数据库：让数据库利用其ACID特性来保证一致性，远比在应用层通过复杂逻辑和锁来控制要可靠和高效。

你的理解非常准确！在Oracle中，`MERGE`（也称为"UPSERT"）正是解决"先`SELECT`查不到再`INSERT`"这类TOCTOU竞态问题的终极武器。

它把"检查存在性"和"插入/更新"合并为一个原子SQL语句，数据库内部加锁，应用层完全感知不到中间状态。


### 核心写法：Oracle MERGE 标准语法

假设你有一个用户积分表 `user_points`，需要实现"如果用户不存在则插入初始积分，如果存在则累加积分"：

```sql
MERGE INTO user_points t
USING (SELECT 1001 AS user_id, 10 AS points FROM DUAL) s
ON (t.user_id = s.user_id)
WHEN MATCHED THEN
    UPDATE SET t.points = t.points + s.points
WHEN NOT MATCHED THEN
    INSERT (user_id, points) VALUES (s.user_id, s.points);
```

关键点：
- `USING` 子句可以来自 `DUAL`（单条）或子查询（批量）。
- `ON` 条件中的字段（如 `user_id`）最好有唯一索引/主键，否则可能出现 `ORA-30926` 错误（无法确定更新哪一行）。
- 整个操作是原子性的，不会出现两个会话同时`SELECT`不到然后重复`INSERT`的情况。


### 更保险的写法：处理并发冲突

在高并发下，即使 `MERGE` 也可能遇到唯一约束冲突（尤其当 `ON` 条件不是唯一键时）。更健壮的做法是结合 错误捕获 或 使用`INSERT` + 异常处理：

#### 方式1：MERGE + 唯一约束（推荐）
确保 `ON` 条件中的列有唯一约束，这样数据库会在 `MERGE` 执行期间对该行加锁，其他会话的 `MERGE` 会等待锁释放，从而保证串行化执行。

#### 方式2：INSERT 捕获 DUP_VAL_ON_INDEX 异常（PL/SQL 块）
如果业务逻辑复杂，无法用 `MERGE` 表达，可以用 PL/SQL 包裹：

```plsql
BEGIN
    INSERT INTO user_points (user_id, points) VALUES (1001, 10);
EXCEPTION
    WHEN DUP_VAL_ON_INDEX THEN
        UPDATE user_points SET points = points + 10 WHERE user_id = 1001;
END;
/
```

这种方式同样是原子性的（整个PL/SQL块作为一个事务），并且利用了唯一索引来防止重复插入。


### 对比：MERGE vs. SELECT + INSERT

| 维度 | SELECT + INSERT（危险） | MERGE / INSERT+异常（安全） |
|------|------------------------|----------------------------|
| 原子性 | ❌ 分两步，存在TOCTOU窗口 | ✅ 一步完成，数据库内部加锁 |
| 并发安全 | ❌ 可能重复插入或丢失更新 | ✅ 安全，利用行锁或唯一约束 |
| 网络往返 | 至少2次（查+改） | 1次（合并操作） |
| 适用场景 | 低并发、容忍错误 | 所有生产环境 |


### 实战示例：HTTP API 中的使用

假设你有一个 "用户首次访问赠送积分" 的接口：

```sql
-- Controller 层只需调用这个存储过程或直接执行 MERGE
MERGE INTO user_activities t
USING (SELECT 
          #{userId} AS user_id,
          'FIRST_VISIT' AS activity_type,
          SYSDATE AS created_at
       FROM DUAL) s
ON (t.user_id = s.user_id AND t.activity_type = s.activity_type)
WHEN NOT MATCHED THEN
    INSERT (user_id, activity_type, created_at, points_awarded)
    VALUES (s.user_id, s.activity_type, s.created_at, 100);
```

这个 `MERGE` 保证了即使同一用户并发请求两次，也只会插入一条记录，不会重复赠送积分。


### 注意事项

1. 索引必备：`ON` 条件涉及的列必须有唯一索引/主键，否则 `MERGE` 在并发下可能报错或产生非预期结果。
2. 性能考量：`MERGE` 是全表扫描或索引扫描，确保 `ON` 条件有索引支持。
3. 批量操作：`MERGE` 支持 `USING` 子查询，可以一次性处理几千条数据，性能远优于循环单条处理。


### 总结

永远不要用 `SELECT` 判断存在性再 `INSERT`，而是直接使用：

- Oracle MERGE（最推荐）
- INSERT + DUP_VAL_ON_INDEX 捕获（PL/SQL场景）

这两种方式从数据库层面彻底解决了TOCTOU竞态问题，让你的HTTP Web服务在高并发下也能保证数据一致性。

你的这个"先唯一键SELECT，查到就UPDATE，查不到就INSERT"场景，正是Oracle MERGE语句的标准应用场景。


### 直接使用 MERGE（最简方案）

假设你的表结构是：
```sql
CREATE TABLE user_profile (
    user_id    NUMBER PRIMARY KEY,   -- 唯一键
    user_name  VARCHAR2(100),
    points     NUMBER,
    update_time DATE
);
```

对应你的需求，MERGE写法如下：

```sql
MERGE INTO user_profile t
USING (SELECT 
          1001 AS user_id, 
          '张三' AS user_name, 
          100 AS points, 
          SYSDATE AS update_time 
       FROM DUAL) s
ON (t.user_id = s.user_id)   -- 这就是你的"唯一键SELECT"条件
WHEN MATCHED THEN            -- 查询到了 → UPDATE
    UPDATE SET 
        t.user_name = s.user_name,
        t.points = t.points + s.points,  -- 可以基于原值累加
        t.update_time = s.update_time
WHEN NOT MATCHED THEN        -- 没查询到 → INSERT
    INSERT (user_id, user_name, points, update_time) 
    VALUES (s.user_id, s.user_name, s.points, s.update_time);
```


### 拆解 MERGE 的执行逻辑

| 你的步骤 | MERGE 对应部分 | 说明 |
|---------|---------------|------|
| 1. 根据唯一键SELECT | `ON (t.user_id = s.user_id)` | 数据库内部执行存在性检查 |
| 2. 如果查询到 → UPDATE | `WHEN MATCHED THEN UPDATE ...` | 原子性更新 |
| 3. 如果没查询到 → INSERT | `WHEN NOT MATCHED THEN INSERT ...` | 原子性插入 |

关键优势：这三个步骤在数据库内部是一个原子操作，不会有两个会话同时"查不到"然后重复插入。


### 验证并发安全性

假设两个会话同时执行上面的MERGE，user_id=1001的记录不存在：

| 时间 | 会话A | 会话B | 结果 |
|------|-------|-------|------|
| T1 | 执行MERGE，发现不存在，准备插入 | 执行MERGE，发现不存在，准备插入 | - |
| T2 | 插入成功，持有行锁 | 等待行锁释放 | 会话A插入成功 |
| T3 | 提交事务，释放锁 | 获得锁，发现记录已存在，执行UPDATE | 会话B更新成功 |

结论：绝对不会出现重复插入，也不会出现"查不到但插入失败"的问题。


### 重要：务必有唯一索引/主键

你的"唯一键"字段（这里是`user_id`）必须有主键约束或唯一索引，否则：
- MERGE依然能执行，但在高并发下可能报 `ORA-30926: 无法在源表中获取一组稳定的行`
- 即使不报错，也可能出现数据不一致

```sql
-- 确保有唯一约束
ALTER TABLE user_profile ADD CONSTRAINT pk_user_id PRIMARY KEY (user_id);
-- 或者
CREATE UNIQUE INDEX idx_user_id ON user_profile(user_id);
```


### 批量处理场景（一次性处理多条）

如果HTTP接口需要批量更新（比如传入多条用户数据），MERGE同样支持：

```sql
MERGE INTO user_profile t
USING (
    SELECT 1001 AS user_id, '张三' AS user_name, 100 AS points FROM DUAL UNION ALL
    SELECT 1002, '李四', 200 FROM DUAL UNION ALL
    SELECT 1003, '王五', 300 FROM DUAL
) s
ON (t.user_id = s.user_id)
WHEN MATCHED THEN
    UPDATE SET t.user_name = s.user_name, t.points = s.points
WHEN NOT MATCHED THEN
    INSERT (user_id, user_name, points) VALUES (s.user_id, s.user_name, s.points);
```

这样一次SQL处理所有数据，性能远优于循环单条操作。

|------|-----------|---------|---------|--------|
| SELECT + UPDATE/INSERT（你的原始方案） | 中等 | 至少2次 | ❌ 存在TOCTOU | 不推荐 |
| MERGE | 简单 | 1次 | ✅ 原子操作 | ⭐⭐⭐⭐⭐ |
| INSERT + DUP_VAL_ON_INDEX捕获 | 稍复杂（PL/SQL） | 1次 | ✅ 原子操作 | ⭐⭐⭐⭐ |


### 总结

你的需求 = MERGE的标准用法，直接这样写即可：

```sql
MERGE INTO 你的表 t
USING (SELECT 你的唯一键值, 其他字段 FROM DUAL) s
ON (t.唯一键字段 = s.唯一键字段)
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;
```

这完美实现了"先SELECT判断，存在就UPDATE，不存在就INSERT"的逻辑，且是原子操作，完全杜绝了并发竞态问题。
