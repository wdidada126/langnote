# 1. 一句话区别
- mysqld：真正的数据库服务器程序（干活的）
- mysqld_safe：守护脚本（保姆），用来安全启动 mysqld、异常崩溃自动重启、记录日志

---

# 2. 详细解释（一看就懂）
## ① mysqld
- 是 MySQL 的核心程序
- 负责接收 SQL、处理数据、读写文件
- 不能直接后台运行，直接启动会卡住当前终端
- 崩溃了就直接挂掉，不会自动重启

## ② mysqld_safe
- 是一个启动脚本，不是数据库本身
- 它会调用 mysqld 来启动数据库
- 自带守护功能：mysqld 意外挂了，它会自动重启
- 自动把日志输出到错误日志，方便排查问题
- 可以后台运行，不卡住终端

---

# 3. 为什么我们启动用 mysqld_safe？
因为：
1. 安全
2. 稳定
3. 崩溃自动重启
4. 日志自动记录
5. 适合生产环境

这是 MySQL 官方推荐的启动方式。

### 一、FSM（有限状态机）核心概念
有限状态机（Finite State Machine, FSM），又称有限状态自动机（FSA），是描述有限状态、事件驱动、状态迁移行为的数学模型，核心是：状态有限 + 输入驱动 + 确定迁移。
- 核心四要素
    - 状态（State）：系统当前模式（如 AQS: 0/SIGNAL/CANCELLED；TCP: LISTEN/ESTABLISHED）
    - 事件（Event/输入）：触发迁移的信号（如 lock/unlock、SYN/ACK、消息消费）
    - 迁移（Transition）：当前状态+事件→下一状态的规则
    - 动作（Action）：迁移时执行的逻辑（如 CAS、阻塞、ACK应答）
- 经典分类
    - Moore机：输出仅依赖当前状态（如 TCP 连接状态、AQS 同步状态）
    - Mealy机：输出依赖当前状态+输入（如数字电路、词法分析）
    - DFA（确定型）：一个状态+一个输入→唯一迁移（AQS、TCP 均属此类）
    - NFA（非确定型）：一个状态+一个输入→多可能迁移（正则表达式底层）

### 二、FSM 同类/相关概念（一脉相承，能力递增）
1. 自动机谱系（计算能力从弱到强）
    - 有限状态机（FSM/FA）：记忆有限，识别正则语言（编译器词法、TCP、AQS、MQ）
    - 下推自动机（PDA）：FSM+栈，识别上下文无关语言（编译器语法、JSON/XML解析）
    - 图灵机（TM）：FSM+无限纸带，通用计算模型（所有可计算问题、算法本质）
    - 线性有界自动机（LBA）：图灵机变种，识别上下文有关语言
2. 工程/系统层面同源概念
    - 状态模式（State Pattern）：面向对象实现 FSM，封装状态行为（如 Java 状态机框架）
    - 状态图（Statechart）：UML 扩展 FSM，支持并发、子状态、历史状态（复杂系统建模）
    - Petri网：并发系统建模，比 FSM 更适合描述同步、异步、资源竞争（分布式、工作流）
    - 事件驱动架构（EDA）：FSM 工程化，事件触发状态/行为（MQ、微服务、Reactor）

### 五、三者（AQS/TCP/MQ）与 FSM 的统一本质
- AQS 状态机：内存线程同步 FSM，解决多线程互斥、排队、唤醒，状态：0/SIGNAL/CONDITION
- TCP 状态机：网络传输 FSM，解决不可靠网络的可靠连接，状态：LISTEN/ESTABLISHED/TIME_WAIT
- MQ 状态机：分布式消息 FSM，解决异步解耦、可靠投递，状态：待发送/已消费/死信
- 共性：均为 DFA（确定型 FSM），用有限状态+事件迁移保证并发/异步/不可靠场景下的一致性。

# AQS 核心内部属性一览
```java
// 同步状态：0=无锁，>0=持有锁，重入时累加
private volatile int state;

// 同步队列的头结点（等待队列的队首）
private transient volatile Node head;

// 同步队列的尾结点（等待队列的队尾）
private transient volatile Node tail;

// 独占模式下，当前持有锁的线程（来自父类 AbstractOwnableSynchronizer）
private transient Thread exclusiveOwnerThread;
```

下面逐个讲作用。

---

# 1. `private volatile int state`
作用：表示同步资源的状态
- 0：当前没有线程持有锁/资源
- 1：有一个线程持有锁
- >1：重入次数（ReentrantLock 用）
- 共享模式下表示剩余许可数（Semaphore、CountDownLatch）

本质：一把原子状态开关
所有加锁、解锁都是通过 CAS 修改这个 state。

---

# 2. `private transient volatile Node head`
作用：同步队列（CLH 队列）的头结点
- head 是已经获取到锁、正在执行的线程节点
- 线程释放锁后，会唤醒 head 的下一个节点
- head 节点不阻塞，只作为“哨兵”控制队列唤醒顺序

队列是：head → node1 → node2 → node3 → tail

---

# 3. `private transient volatile Node tail`
作用：同步队列的尾结点
- 新线程抢锁失败时，尾插法加入队列
- 用 CAS 保证多线程并发入队安全

---

# 4. `private transient Thread exclusiveOwnerThread`
来自父类 AOS，不是 AQS 直接定义，但 AQS 大量使用
作用：记录当前独占锁的持有者线程
- 实现可重入：判断当前线程是不是持有者
- 实现解锁权限检查：只有持有者才能解锁

---

# 5. Node 内部节点核心属性（必须一起理解）
每个等待线程封装成 Node：
```java
// 节点等待状态：
// 0=初始
// SIGNAL=-1=后继需要被唤醒
// CANCELLED=1=取消
// CONDITION=-2=条件队列等待
// PROPAGATE=-3=共享模式传播唤醒
volatile int waitStatus;

// 前驱节点
volatile Node prev;

// 后继节点
volatile Node next;

// 节点所属线程
volatile Thread thread;

// 条件队列的下一个节点
Node nextWaiter;
```

## Node 字段作用
- waitStatus：控制线程是否需要阻塞、唤醒、取消
- prev / next：构成双向链表，安全入队、出队
- thread：要阻塞/唤醒的线程
- nextWaiter：用于 Condition 条件队列

---

# 极简总结（记忆版）
- state：资源状态，锁的计数器
- head：队列头，控制唤醒顺序
- tail：队列尾，用于线程安全入队
- exclusiveOwnerThread：谁持有锁（可重入靠它）
- Node 链表：抢不到锁的线程排队、阻塞、等待唤醒

一句话：
AQS 用 state 做资源控制，用 head/tail 做线程排队，用 Node 管理阻塞与唤醒。

# 前提规则（必须先懂）
- `state` 是一个 int(32位)
- 高 16 位：读锁计数（shared count）
- 低 16 位：写锁计数（exclusive count）
- 写锁是独占：只要低16位≠0，就不能加读、不能加写
- 读锁是共享：只要没写锁，就能一起加读

---

# 初始状态
state = 0
二进制：
```
00000000 00000000   00000000 00000000
```
高16位读计数=0
低16位写计数=0

---

# 1）第一次读：read lock
读锁 +1
高16位 = 1
低16位 = 0

state = 1 << 16 = 65536

---

# 2）第二次读：read lock
读锁再 +1
高16位 = 2
低16位 = 0

state = 2 << 16 = 131072

---

# 3）第一次写：write lock
必须等读锁全部释放才能加写！
假设现在两个读锁都释放：
高16位回到 0

然后加写锁：
低16位 = 1

state = 1

---

# 4）再次读：read lock
此时写锁持有（低16位=1），读锁不能获取！会阻塞
必须等写锁释放，才能读。

写锁释放 → 低16位=0
读锁获取 → 高16位=1

state = 65536

---

# 5）写锁：write lock
必须等读锁释放
读释放 → 高16=0
加写 → 低16=1

state = 1

---

# 6）再次写：write lock（可重入）
写锁是可重入的，不需要释放，直接 +1
低16位 = 2

state = 2

---

state 变化：

4. 读 → 65536（前提：写释放）

# 最关键结论（面试必问）
1. 写锁独占：只要写锁持有，读写都阻塞
2. 读锁共享：可以多人读，但不能有写
3. 写锁可重入，读锁不重入（计数累加）
4. state 高低16位严格分离，互不干扰
5. 要写必须等读全部释放；要读必须等写释放

# 那你说的“写写互斥”体现在哪里？
体现在：
如果是 线程B 来加写锁
此时 state 低16位 = 1（线程A持有）
线程B 会阻塞，无法获取锁

这就是 写写互斥。

---

# 总结一句话
- 不同线程写写 → 互斥、阻塞
- 同一线程写写 → 重入、state 低16位 +1

所以：
- 线程A 第一次写 → state = 1
- 线程A 第二次写 → state = 2
- 线程B 想写 → 阻塞，state 不变

---

# 回到你最开始的序列：读 读 写 读 写 写
我给你完全正确、严格版本：

1. 读 → 高16=1，低16=0 → state = 65536
2. 读 → 高16=2，低16=0 → state = 131072
3. 读全部释放 → state = 0
4. 写 → 低16=1 → state = 1
5. 写释放 → state = 0
6. 读 → 高16=1 → state = 65536
7. 读释放 → state = 0
8. 写 → 低16=1 → state = 1
9. 写（同一线程重入）→ 低16=2 → state = 2

---

# 最终回答你这句疑问：
> 写写不应该是1 1吗？因为写写互斥？

- 如果是两个不同线程写写：
  第二个写会阻塞，永远到不了 2，state 保持 1
- 如果是同一个线程写写：
  允许重入，state 从 1 → 2，这不是违反互斥，而是可重入特性

不区分！读读完全不区分是不是同一个线程。

这是 ReentrantReadWriteLock 最关键的设计点之一，我给你说透：

---

# 核心结论
读锁是“纯共享模式”：
不管是不是同一个线程，只要加读锁，高16位读计数一律 +1。

- 同一个线程连续加两次读锁 → 读计数 = 2
- 线程A加一次、线程B加一次 → 读计数 = 2

读锁没有“重入”概念，只有“计数”概念。

---

# 为什么读锁不区分线程？
因为读锁只做一件事：
保护数据不被同时修改，允许多线程同时读。

它不关心是谁在读，只关心有多少路并发在读。

所以：
- 写锁：需要区分线程 → 实现可重入、排他
- 读锁：不区分线程 → 只计数，大家一起读

---

# 举个最直观的例子

## 情况1：同一个线程连续加读锁
```
thread1: readLock  → 读计数 +1 = 1
thread1: readLock  → 读计数 +1 = 2
```
state 高16位 = 2

## 情况2：两个不同线程各加一次读锁
```
thread1: readLock  → 读计数 = 1
thread2: readLock  → 读计数 = 2
```
state 高16位 = 2

## 结果完全一样！
读锁根本不看线程 ID，只看计数。

---

# 再对比写锁（帮助你彻底区分）
- 写锁：同一线程可重入，不同线程互斥
- 读锁：同一线程/不同线程都共享，一律计数+1

---

# 最终一句话记忆
- 写锁看线程（重入、排他）
- 读锁只看人头数（共享、不看线程）
