结论先说：Java 标准库（JDK）几乎不用 KMP。

## 一、JDK 字符串匹配：到底用什么算法？
### 1. String.indexOf（最常用）
- Java 8 及更早：纯暴力（双层循环）
- Java 9+：改进版暴力 + 快速失败（先找首字符，再整体匹配）
- 为什么不用 KMP？
  - KMP 要预处理 `next/LPS` 数组（O(m) 时间+空间）
  - 短串场景下，暴力 + JIT 优化 + CPU 缓存 比 KMP 更快
  - JDK 设计：常见短串优先，极端长串交给库外实现

### 2. 标准库哪里真正用了 KMP？
几乎没有公开的标准类用 KMP。
- `java.util.regex`（正则）：用 自定义 NFA/DFA，不是 KMP
- `Pattern`/`Matcher`：基于状态机，不依赖 KMP
- `String`/`StringBuilder`/`StringBuffer`：全是暴力/优化暴力
- 第三方/扩展库（不算标准库）：
  - Apache Commons Lang `StringUtils`
  - Guava `Strings`：也不用 KMP



## 二、KMP 面试题（Java 版）+ 标准答案
### 1. KMP 核心原理（必背）
- 核心：利用 最长公共前后缀（LPS/next 数组），主串 i 不回退，模式串 j 跳回 LPS[j-1]
- 时间：O(n + m)
- 空间：O(m)（存 LPS）
- 优势：无回溯、适合流式、重复模式多的时候极快

### 2. next/LPS 数组是什么？
- LPS[j]：模式串 `[0..j]` 子串中，最长相等真前缀 & 真后缀 的长度
- 例：`ABABC`
  ```
  j: 0 1 2 3 4
  p: A B A B C
  LPS:0 0 1 2 0
  ```

### 3. Java 手写 KMP（面试高频代码）
```java
public class KMP {
    // 找 pattern 在 text 中第一次出现的位置
    public static int strStr(String text, String pattern) {
        if (pattern == null || pattern.isEmpty()) return 0;
        int[] lps = buildLPS(pattern);
        int n = text.length(), m = pattern.length();
        int i = 0; // text指针
        int j = 0; // pattern指针
        while (i < n) {
            if (text.charAt(i) == pattern.charAt(j)) {
                i++; j++;
            }
            if (j == m) {
                return i - j; // 找到
            } else if (i < n && text.charAt(i) != pattern.charAt(j)) {
                if (j != 0) j = lps[j-1]; // 不匹配，跳LPS
                else i++;
            }
        }
        return -1;
    }

    // 构建最长公共前后缀数组 LPS
    private static int[] buildLPS(String pat) {
        int m = pat.length();
        int[] lps = new int[m];
        int len = 0; // 最长公共前后缀长度
        int i = 1;
        while (i < m) {
            if (pat.charAt(i) == pat.charAt(len)) {
                len++;
                lps[i] = len;
                i++;
            } else {
                if (len != 0) len = lps[len-1];
                else {
                    lps[i] = 0;
                    i++;
                }
            }
        }
        return lps;
    }
}
```

### 4. 面试高频问答（直接背）
Q1：Java String.indexOf 用 KMP 吗？为什么？
A：不用。用优化版暴力。因为 KMP 有预处理开销，短串下暴力更快；JDK 面向通用场景，极端长串由开发者自己用 KMP/Rabin-Karp/Boyer-Moore 实现。

Q2：KMP 与暴力（BF）区别？
A：
- BF：主串 i 频繁回退，O(nm)
- KMP：i 永不回退，O(n+m)
- KMP 适合：重复模式多、长文本、流式数据

Q3：KMP 与 Boyer-Moore（BM）区别？
A：
- KMP：从左到右匹配，用前缀
- BM：从右到左匹配，用好后缀坏字符规则
- 实际：BM 平均比 KMP 更快（文本编辑器常用）

Q4：KMP 适用场景？
A：
1. 长文本 + 固定模式（日志分析、DNA匹配）
2. 流式数据（网络流、文件流，不能回溯）
3. 多次复用同一模式（预处理一次 LPS，多次搜索）

Q5：JDK 有没有内置 KMP？
A：没有。标准库无 KMP 实现，需手写或引第三方库。

# java.util.regex 底层：NFA/DFA 到底怎么工作？（超详细+代码+示例）
先说结论：
Java 正则底层是 NFA（非确定有限自动机），不是 DFA，更不是 KMP。
- 采用 回溯式 NFA 引擎（传统 POSIX 风格）
- 支持捕获组、环视、非贪婪、反向引用，这些 DFA 做不到
- 代价是最坏情况指数复杂度（回溯爆炸）

# 0. 极简区分 NFA / DFA
## NFA（Non-deterministic）
- 同一个状态、同一个字符，可能有多条出路
- 需要试探 + 回溯
- 支持捕获组、分组、反向引用、零宽断言
- Java / Python / PHP / JS 都是 NFA

## DFA（Deterministic）
- 每个状态只有唯一确定的转移
- 不回溯，速度稳定 O(n)
- 不支持捕获组/反向引用
- Awk / Grep / Ag 常用 DFA

# 1. Java 正则 NFA 执行流程（核心四步）
以正则 `a(b|c)d` 匹配文本 `abd` 为例：

1. 编译 Pattern
   把正则表达式解析成一棵 语法树 + NFA 状态机
2. 创建 Matcher
   绑定待匹配字符串
3. 逐个字符尝试匹配
   状态机一步步走，遇到分支就试探
4. 不匹配则回溯
   回到上一个分支点，走另一条路

Java NFA 特点：
- 从左到右，贪婪匹配
- 遇到 `|`、`*`、`+`、`?` 会产生分支
- 分支失败 → 回溯 → 重选路径

# 2. JDK 内部类结构（简化版）
你不需要自己写 NFA，但要知道类对应关系：

```
Pattern          # 编译后的正则（NFA 结构）
  ↑
Matcher          # 匹配器，持有状态、位置、回溯栈
  ↓
Pattern$Node     # 各种 NFA 节点：
  - Start
  - CharNode        单个字符
  - BranchNode      分支 |
  - LoopNode        * + ?
  - GroupNode       捕获组 ()
  - EndNode
```

`java.util.regex` 完全自己实现 NFA，不依赖任何第三方自动机库。



# 3. 最直观例子：`a(b|c)d` 匹配 `abd`
## NFA 状态转移示意
```
Start → a → [分支: b 或 c] → d → End
```

## 实际执行步骤
1. 读 `a` → 匹配，进入分支
2. 试探走 `b` 分支
3. 读 `b` → 匹配
4. 读 `d` → 匹配
5. 到达结束状态 → 匹配成功

如果是 `acd`，就走 `c` 分支。
如果是 `abx`，走到 `x` 不匹配，回溯到分支点，尝试另一条（但没有了）→ 匹配失败。

# 4. 带回溯的经典例子：`.*b` 匹配 `aab`
`.*` 是贪婪的，会先吞掉所有字符：

1. `.*` 吞掉 `a a b`
2. 剩下空，无法匹配 `b`
3. 回溯吐出一个字符 `b`
4. 现在 `.*` 是 `aa`，后面是 `b` → 匹配成功

这就是 NFA 典型行为。

# 5. 完整可运行 main 函数示例（带注释）
下面代码演示：
- 正则编译（生成 NFA）
- Matcher 执行
- 分组捕获（NFA 必须记录位置，DFA 做不到）

```java
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class JavaRegexNFAExample {
    public static void main(String[] args) {
        // 1. 编译正则 → 内部构建 NFA 状态机
        Pattern pattern = Pattern.compile("a(b|c)d(\\d+)");

        // 2. 待匹配字符串
        String input = "abd123 acd456 abx789";

        // 3. 创建 matcher，绑定输入
        Matcher matcher = pattern.matcher(input);

        // 4. NFA 开始逐个字符匹配、试探、回溯
        while (matcher.find()) {
            System.out.println("完整匹配: " + matcher.group(0));
            System.out.println("分组1 (b/c): " + matcher.group(1));
            System.out.println("分组2 (数字): " + matcher.group(2));
            System.out.println("");
        }
    }
}
```

## 输出
```
完整匹配: abd123
分组1 (b/c): b
分组2 (数字): 123

完整匹配: acd456
分组1 (b/c): c
分组2 (数字): 456

```

`abx789` 不匹配，因为 NFA 走到 `x` 无法匹配 `d`，回溯后无分支可走，丢弃。



# 6. 为什么 Java 必须用 NFA，不能用 DFA？
因为 Java 正则支持大量 DFA 无法实现 的功能：

- 捕获组 `()`
- 反向引用 `\1`
- 非贪婪 `*? +??`
- 零宽断言 `(?=...)` `(?!...)` `(?<=...)`
- 占有量词 `*+`
- 复杂分支优先级控制

DFA 不记录路径，只记录“当前状态”，所以无法回溯、无法存分组。



# 7. 面试必问：Java 正则引擎是什么？
标准答案（直接背）：
> Java `java.util.regex` 采用 传统回溯式 NFA 引擎，不是 DFA，也不是 KMP。
> 它通过构建状态机、试探分支、回溯重试实现匹配，支持捕获组、环视、非贪婪、反向引用等高级特性。
> 优点是功能极强；缺点是极端场景下可能出现回溯爆炸，性能退化严重。



# 8. 一句话总结（最核心）
- Java 正则 = 手写 NFA 状态机 + 回溯
- `Pattern` 是编译后的 NFA
- `Matcher` 是 NFA 运行时
- 支持所有高级正则语法，但可能回溯
- 和 DFA/KMP 完全无关

MQ 混合模式（Push+Pull，主流为长轮询 Long Polling），核心是：以 Pull 为底座、用长连接/挂起模拟 Push 实时性，同时保留消费者自主流控能力，解决纯 Push 易压垮消费者、纯 Pull 延迟/空轮询浪费的痛点。

---

## 一、核心机制：长轮询（最主流混合实现）
### 流程（RocketMQ PushConsumer / Kafka poll 优化）
1. Consumer 主动发 Pull 请求（底层是 Pull）
2. Broker 检查消息：
   - 有消息：立即返回（接近 Push 实时）
   - 无消息：挂起连接（不返回空），等待一段时间（如 15s/30s）
3. 挂起期间新消息到达：Broker 立刻通过原连接返回（准实时）
4. 超时无消息：返回空，Consumer 立即重发 Pull（避免频繁短轮询）



### 关键特点
- 表面 Push、底层 Pull：API 像 Push（回调/监听器），实际是客户端驱动的拉取
- Broker 不主动建连接、不维护大量推送状态：比纯 Push 轻量
- Consumer 天然可控速率：处理不过来就不发下一轮 Pull（自带背压）

---

## 二、两种典型混合形态
### 1）长轮询型（RocketMQ、Kafka、Pulsar 主流）
- 结构：Pull 基础 + 服务端挂起 + 超时重连
- 优点：
  - 实时性接近 Push（ms 级）
  - 无空轮询、网络开销低
  - 消费者可控、不易过载
- 缺点：
  - Broker 需挂起连接，占用少量 FD/线程资源
  - 超时/重连仍有轻微延迟

### 2）Push+流控型（RabbitMQ、ActiveMQ 为主）
- 结构：Broker 主动 Push，但严格限流（QoS/preFetch）
  - 限制消费者未 ACK 消息上限（如 basic.qos=10）
  - 消费者处理完一批再推下一批
- 优点：
  - 极致实时
  - 开发简单（回调）
- 缺点：
  - Broker 状态重、连接多则压力大
  - 流控相对被动

---

## 三、纯 Push / 纯 Pull / 混合模式对比
| 维度 | 纯 Push | 纯 Pull | 混合（长轮询） |
| :--- | :--- | :--- | :--- |
| 实时性 | 极高 | 低（短轮询）/中（长轮询） | 高（准实时） |
| 消费者负载 | 易过载、难控 | 完全可控 | 可控（自带背压） |
| Broker 压力 | 高（维护连接/状态） | 低 | 中 |
| 空轮询 | 无 | 严重（短轮询） | 几乎无 |
| 适用场景 | 低延迟、消费者稳定 | 大数据、弹性、批量 | 通用主流（90%场景） |

---

## 四、主流 MQ 混合实现
### RocketMQ
- PushConsumer = 长轮询 Pull 封装
- 客户端 PullRequestService 循环发 Pull，Broker 挂起 15–30s
- 内置流控：堆积多时加快拉取、空闲时放缓

### Kafka
- 原生 Pull，但 `poll(Duration)` 自带长轮询超时
- 无消息时阻塞等待（不立即返回），接近混合效果

### RabbitMQ
- 以 Push 为主，用 `basic.qos` 做推拉结合限流

---

## 五、混合模式解决的核心问题
1. 实时性与稳定性平衡：既快又不压垮 Consumer
2. 消除空轮询浪费：无消息时不频繁请求
3. 天然背压：消费能力决定拉取节奏，Broker 不强行推送
4. 易扩展：Consumer 水平扩缩不影响 Broker 推送逻辑

---

## 六、一句话总结
混合模式 = 长轮询 = 用 Pull 的控制权 + Push 的实时性，是现代 MQ 的标准消费模型。

# 一、四种 MQ 消费模式到底是什么？
## 1. Kafka
- 表面：纯 Pull API
- 实际：Pull + 内置长轮询（混合模式）
- 你调用 `poll(Duration.ofMillis(1000))`
  - 有消息 → 立刻返回
  - 没消息 → 阻塞等待，不疯狂循环
- 优点：消费者完全控速、无过载、批量强
- 定位：流式 Pull，伪 Push 体验

## 2. RocketMQ
- PushConsumer：最标准的「混合模式」
  - 底层：客户端主动 Pull
  - Broker：无消息就挂起请求 30s
  - 来消息立即返回 → 你感觉是 Push
- PullConsumer：纯手动拉取
- 一句话：披着 Push 外衣的长轮询 Pull

## 3. RabbitMQ
- 默认模式：Push（推模式）
  - Broker 主动推给消费者
  - 靠 `basic.qos(prefetchCount)` 做限流，防止打崩消费者
- 也支持 Pull（basic.get），但极少用
- 一句话：Push 为主 + QoS 限流 = 简易混合流控

## 4. Pulsar
- 共享订阅 / 灾备订阅：Push 模式
- 独占/重试队列：类长轮询 Pull
- 底层也是 broker hold 连接 + 有消息立即推
- 一句话：灵活混合，对外更像 Push

| Kafka | Pull | poll + 阻塞长轮询 | Pull 为主，伪 Push | 消费者完全控速，高吞吐 |

# 三、混合模式到底解决了什么？（结合 MQ 讲）
## 1. 纯 Push 的问题（RabbitMQ 早期痛点）
- Broker 疯狂推
- 消费者处理不过来 → 堆内存 OOM、雪崩
→ 所以 RabbitMQ 必须加 `prefetch` 变成半推拉混合。

## 2. 纯 Pull 短轮询的问题（老式 MQ）
- 消费者每秒发 100 次请求
- 99% 是空轮询 → 浪费 CPU、网络、Broker 资源

## 3. 混合模式（现代 MQ 标准答案）
- 消费者自己决定要不要拉、什么时候拉（Pull 的安全）
- 没消息不返回，来消息秒回（Push 的实时）
- 这就是 Kafka/RocketMQ/Pulsar 都在用这套的原因。


# 四、面试标准答案（可直接背诵）
## 问：MQ Push/Pull/混合模式是什么？主流产品怎么实现？
答：
1. 纯 Push：Broker 主动推，实时但容易压垮消费者，如 RabbitMQ 默认模式。
2. 纯 Pull：消费者主动拉，安全但空轮询浪费资源。
3. 混合模式（主流） = Pull 底座 + 长轮询/阻塞等待，兼具实时性与流控能力。
   - Kafka：poll 长轮询，Pull 为主
   - RocketMQ PushConsumer：长轮询 Pull，最典型混合
   - RabbitMQ：Push + QoS 限流，简易混合
   - Pulsar：长连接准 Push 模式

混合模式是现代消息队列的标准消费模型，解决了 Push 易过载、Pull 空轮询的痛点。

- 同一个字符可能有多条路径
- 需要回溯 / 需要维护状态集合
- 速度慢、不适合流式扫描

- 每个状态、每个字符 只有一条路

- 能直接生成高效代码（flex/ragel 都是干这个）

### 所以编译器前端的标准流程是：
```

NFA 只是构造 DFA 的梯子，用完就扔。

## 一、正则历史沿革（一句话脉络）

### 1. 理论起源（1950s）
- 1951：数学家 Stephen Kleene 提出 正则集合/正则语言（Regular Sets），用符号描述“可被有限自动机识别的模式”。
- 用途：形式语言、自动机理论，不是给文本处理用的。

### 2. Unix 工具时代（1960s–1980s）：最早的实用分裂
- 1968：Ken Thompson 在 QED/ed 编辑器实现正则 → 诞生 `grep`（g/re/p）
- 工具分裂：
  - `grep`、`sed`、`ed`、`vi`：BRE（Basic RE）
    - `()+?{}|` 必须 转义 才是元字符：`\( \) \+ \? \|`
  - `egrep`、`awk`：ERE（Extended RE）
    - `()+?{}|` 默认是元字符，不用转义
- 根源：Unix 工具各自独立实现，语法不统一。

### 3. POSIX 标准化（1986）：第一次官方标准
IEEE 发布 POSIX.2，定义两大流派：
- BRE（Basic Regular Expressions）
  - 元字符：`. * ^ $ []`
  - `()+?{}|` 需转义：`\( \) \+ \? \{ \} \|`
- ERE（Extended Regular Expressions）
  - 直接支持：`()+?{}|`
  - 增加：锚点、分组、范围、选择
- 影响：C 语言 `regex.h`、grep/sed/awk、MySQL、Oracle 等沿用至今。

### 4. Perl 革命（1987–1990s）：现代正则的诞生
Larry Wall 发布 Perl，把正则 内置到语言语法，并加入大量新特性：
- 捕获分组 `()`、反向引用 `\1`
- 非贪婪 `*? +? ??`
- 零宽断言 `(?=...) (?<=...) (?!...)`
- 单词边界 `\b`、简写 `\d \w \s`
- 修饰符 `/i /g /m /s /x`
- 模式修饰符、内嵌代码、条件匹配
- 引擎：回溯 NFA（支持路径记录，牺牲速度换表达力）

关键影响：
Perl 5 成为 Web 早期文本处理标配（CGI 时代），其正则语法成为 事实工业标准。

### 5. PCRE 大一统（1997）：跨语言兼容层
Philip Hazel 发布 PCRE（Perl Compatible Regular Expressions）：
- 目标：完全兼容 Perl 正则语法与语义
- C 库，可嵌入几乎所有语言
- 使用者：PHP、Apache、Nmap、Postfix、Exim、很多脚本语言

### 6. 主流语言内置（2000s）：第二次大分裂
各语言不再满足于简单套 PCRE，开始 自研引擎 + 语法魔改：
- Java：`java.util.regex`（类 PCRE，但细节不同）
- Python：`re`（早期 PCRE，后来自研）
- JavaScript：`RegExp`（类 PCRE，但阉割/扩展）
- C#/.NET：自研引擎（命名分组、平衡组、超级断言）
- Go：`regexp`（RE2 引擎，DFA 安全无回溯，语法阉割）
- Ruby：早期 PCRE，后来自研 Onigmo

### 7. 现代（2010s+）：性能与安全分流
- 安全/无回溯派（DFA/混合）：Go、Rust regex、Google RE2、Java 部分优化
- 表达力派（回溯 NFA）：PCRE2、.NET、JavaScript、Python、Ruby
- 学术/专用：Raku（原 Perl6）正则、ANTLR、Lex/Flex

## 二、为什么不同语言支持的 RE 不同（核心原因）

### 1. 历史源头不同：POSIX vs Perl
- Unix/POSIX 系（C、grep、sed、awk、MySQL）
  - 起源：文本工具，简洁、最小化、强调性能
  - 语法：`\( \) \+ \? \|` 转义分裂
- Perl 系（PHP、Python、Java、JS、.NET）
  - 起源：脚本语言，强表达力、内置语法、捕获/断言
  - 语法：`() + ? |` 默认元字符，`\d \w \s` 简写

### 2. 引擎底层分裂：回溯 NFA vs DFA
这是 最根本差异，决定功能上限：

#### A. 回溯 NFA（主流语言：Perl/PCRE/Python/Java/JS/.NET）
- 优点：支持捕获组、反向引用、环视、非贪婪、条件、递归
- 缺点：可能灾难性回溯（恶意正则卡死）
- 设计哲学：表达力 > 绝对安全

#### B. DFA/混合（Go、Rust regex、RE2、grep -F）
- 优点：O(n) 稳定、无回溯、超大规则安全
- 缺点：不支持捕获组、反向引用、环视、非贪婪
- 设计哲学：安全/性能 > 表达力

### 3. 语法设计：各语言“魔改”PCRE
即使都叫“Perl 兼容”，细节全不一样：

#### （1）命名分组语法（最典型）
- .NET：`(?<name>...)` 引用 `${name}` / `\k<name>`
- Python：`(?P<name>...)` 引用 `\g<name>` / `(?P=name)`
- PCRE/PHP：`(?<name>...)` / `(?'name'...)` 引用 `\k<name>`
- JS（ES2018+）：`(?<name>...)` 引用 `$<name>` / `\k<name>`
- Go：`(?P<name>...)`（但不支持反向引用）

#### （2）反向引用
- 多数：`\1 \2`
- JS：仅支持 `\1` 风格，不支持 `\g<1>`
- RE2/Go：不支持

#### （3）零宽断言
- 支持：`(?=...)`（正向前瞻）、`(?!...)`（负向前瞻）
- 差异：后发断言 `(?<=...) (?<!...)`
  - JS（ES2018+）、Python、Java、.NET、PCRE：支持
  - Go、RE2、JavaScript 旧版：不支持

#### （4）修饰符
- Perl/PCRE：`/i /g /m /s /x /U`
- JS：`i g m s y u`
- Java：`Pattern.CASE_INSENSITIVE` 等常量
- Python：`re.I re.M re.S`

#### （5）转义规则
- POSIX：`()+?{}|` 必须 `\`
- Perl/PCRE：`\` 仅转义元字符
- JS：`/` 必须转义（字面量 `/pattern/`）
- C#：`\` 在字符串中需 `\\`

### 4. 语言设计哲学不同
- Go：拒绝回溯，安全优先 → 阉割功能
- Python：中庸 → 兼容 PCRE，逐步加特性
- .NET：最强大 → 平衡组、递归、条件、超级断言
- JS：浏览器安全 → 早期阉割，ES6+逐步补全
- Java：保守稳定 → 慢迭代，少语法糖
- Perl/Raku：正则即语言 → 无限扩展

### 5. 标准缺失：没有真正的“国际正则标准”
- POSIX 是 OS 标准，不是编程语言标准
- PCRE 是“事实标准”，但不是官方标准
- ECMA（JS）、JCP（Java）、ECMA（C#）各自定义

# 0. 总路线（必背）
```

# 一、RE → NFA：构造算法（自己造自动机的第一步）
## 1. Thompson 构造法（最经典、教学必学）
- 对每个 RE 子结构，机械拼接小 NFA
- 支持：单字符、连接、选择 a|b、闭包 a\*
- 大量使用 ε 转移
- 优点：简单、机械、好实现
- 缺点：状态多、ε 多

## 2. Glushkov 构造法（无 ε NFA）
- 直接构造 不带 ε 转移 的 NFA
- 状态数 = 正则字符数 + 1
- 工业常用：Lucene、搜索引擎、DFA 前置
- 优点：无 ε、更快、状态少

## 3. McNaughton-Yamada 构造法
- 从正则表达式的 位置抽象 构建 NFA
- 理论性强，和 Glushkov 高度相似

## 4. Brzozowski 导数法（超级优雅）
- 用正则导数一步步拆表达式
- 可直接跳到 DFA，跳过 NFA
- 函数式语言最爱（Rust/Scala）

---

# 二、NFA → DFA：确定化算法
## 1. 子集构造法（Subset Construction）最标准
- 对每个 NFA 状态集合，构造一个 DFA 状态
- 步骤：
  1. ε-闭包
  2. 对每个字符移动
  3. 新集合 = 新 DFA 状态
- 几乎所有教学/工业都用它

## 2. Brzozowski 算法（反向+确定化+最小化一步到位）
- 反转 NFA → 确定化 → 再反转 → 确定化
- 得到直接最小化 DFA
- 极优雅，代码短

## 3. Glushkov 直接 DFA 构造
- 无 ε NFA 直接变 DFA
- 状态少、效率高

---

# 三、DFA → 最小 DFA：最小化算法
## 1. Hopcroft 算法（工业最强、最快 O(n log n)）
- 现代 DFA 最小化标准
- Lucene、RE2、ragel、flex 都用

## 2. Moore 算法（简单 O(n²)）
- 教学常用
- 不断划分类，直到不能分

## 3. Brzozowski（再次出现）
- 反转 → 确定化 → 反转 → 确定化
- 自动最小化，非常神奇

## 4. Valmari 算法
- 更快的 Hopcroft 改进
- 学术常用

---

# 四、DFA 执行/匹配算法
## 1. 标准单步转移 DFA
- 读一个字符走一步
- 最快、无回溯

## 2. Bit-parallel DFA（位并行 DFA）
- 用机器整数 bit 并行表示状态
- 极快：ripgrep、Hyperscan

## 3. Lazy DFA（懒 DFA）
- 运行时才生成需要的状态
- 解决状态爆炸
- RE2、Go/Rust regex 库核心

## 4. Byte-based DFA（字节级 DFA）
- 按字节而非 char 匹配
- 现代引擎标配

---

# 五、NFA 执行算法（不转 DFA，直接跑 NFA）
## 1. Thompson 模拟法（回溯 NFA）
- Java/Python/JS/PCRE 正则引擎底层
- 支持捕获组、反向引用、环视
- 缺点：可能回溯爆炸

## 2. Breadth-First NFA 模拟（非回溯）
- 同时跑所有可能路径
- 稳定 O(n*m)，不爆炸
- RE2 用这种思路

## 3. Bit-parallel NFA（Shift-Or / Shift-And）
- 用 bit 并行跑 NFA
- 极快，多模式匹配常用

# 六、多模式匹配（一堆 RE → 一个自动机）
## 1. Aho-Corasick（AC 自动机）
- KMP 的多模式版
- 本质是 DFA
- 敏感词、WAF、日志检索

## 2. Commentz-Walter
- AC + BM 坏字符
- 更快

## 3. Hyperscan（Intel）
- 混合 NFA/DFA
- 世界最强正则匹配引擎

- 理论性强，和 Glushkov 高度相似

## 4. Brzozowski 导数法（超级优雅）
- 用正则导数一步步拆表达式
- 可直接跳到 DFA，跳过 NFA
- 函数式语言最爱（Rust/Scala）

---

# 二、NFA → DFA：确定化算法
## 1. 子集构造法（Subset Construction）最标准
- 对每个 NFA 状态集合，构造一个 DFA 状态
- 步骤：
  1. ε-闭包
  2. 对每个字符移动
  3. 新集合 = 新 DFA 状态
- 几乎所有教学/工业都用它

## 2. Brzozowski 算法（反向+确定化+最小化一步到位）
- 反转 NFA → 确定化 → 再反转 → 确定化
- 得到直接最小化 DFA
- 极优雅，代码短

## 3. Glushkov 直接 DFA 构造
- 无 ε NFA 直接变 DFA
- 状态少、效率高

# 三、DFA → 最小 DFA：最小化算法
## 1. Hopcroft 算法（工业最强、最快 O(n log n)）
- 现代 DFA 最小化标准
- Lucene、RE2、ragel、flex 都用

## 2. Moore 算法（简单 O(n²)）
- 教学常用
- 不断划分类，直到不能分

## 3. Brzozowski（再次出现）
- 反转 → 确定化 → 反转 → 确定化
- 自动最小化，非常神奇

## 4. Valmari 算法
- 更快的 Hopcroft 改进
- 学术常用

---

# 四、DFA 执行/匹配算法
## 1. 标准单步转移 DFA
- 读一个字符走一步
- 最快、无回溯

## 2. Bit-parallel DFA（位并行 DFA）
- 用机器整数 bit 并行表示状态
- 极快：ripgrep、Hyperscan

## 3. Lazy DFA（懒 DFA）
- 运行时才生成需要的状态
- 解决状态爆炸
- RE2、Go/Rust regex 库核心

## 4. Byte-based DFA（字节级 DFA）
- 按字节而非 char 匹配
- 现代引擎标配

---

# 五、NFA 执行算法（不转 DFA，直接跑 NFA）
## 1. Thompson 模拟法（回溯 NFA）
- Java/Python/JS/PCRE 正则引擎底层
- 支持捕获组、反向引用、环视
- 缺点：可能回溯爆炸

## 2. Breadth-First NFA 模拟（非回溯）
- 同时跑所有可能路径
- 稳定 O(n*m)，不爆炸
- RE2 用这种思路

## 3. Bit-parallel NFA（Shift-Or / Shift-And）
- 用 bit 并行跑 NFA
- 极快，多模式匹配常用

# 六、多模式匹配（一堆 RE → 一个自动机）
## 1. Aho-Corasick（AC 自动机）
- KMP 的多模式版
- 本质是 DFA
- 敏感词、WAF、日志检索

## 2. Commentz-Walter
- AC + BM 坏字符
- 更快

## 3. Hyperscan（Intel）
- 混合 NFA/DFA
- 世界最强正则匹配引擎

# 七、你要“自己构造算法”，可以怎么玩？
你可以任意混搭，造出你的专属 RE 引擎：

例 1：
```
Glushkov → 子集构造 → Hopcroft → DFA执行
```

例 2：
```
Thompson → Brzozowski → 最小DFA
```

例 3：
```
正则导数 → 直接 DFA（跳过 NFA）
```

例 4：
```
Bit-parallel NFA 模拟（不生成 DFA）
```

例 5：
```
Thompson NFA → 广度模拟（不回溯、安全正则）
```


# 八、一句话总结（面试/论文万能句）
- RE→NFA：Thompson、Glushkov、McNaughton-Yamada、Brzozowski
- NFA→DFA：子集构造、Brzozowski
- DFA→最小DFA：Hopcroft、Moore、Brzozowski
- NFA执行：回溯、广度优先、bit-parallel
- DFA执行：直接转移、懒生成、字节级、位并行
