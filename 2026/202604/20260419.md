# 一、报文每个字段含义（超级清晰）

# 二、JS / TS 如何赋值（直接复制用）
## 1）工具函数（生成日期、时间、流水号、设备号）
```js
// 获取当前日期 YYYY-MM-DD
function getDate() {
  return new Date().toISOString().slice(0, 10)
}

// 获取当前时间 HH:mm:ss
function getTime() {
  return new Date().toTimeString().slice(0, 8)
}

// 生成流水号 XSQD + 日期 + 时间 + 随机数
function getTrackSeq() {
  const now = new Date();
  const Ymd = now.toISOString().slice(0, 10).replace(/-/g, "");
  const His = now.toTimeString().slice(0, 8).replace(/:/g, "");
  const rand = Math.random().toString().slice(2, 12);
  return `XSQD${Ymd}${His}${rand}`;
}

// 生成随机设备号（模拟）
function getDeviceNo() {
  return "74B8D45258769D1A"; // 或用 uuid
}

// 获取客户端IP（前端一般后端取，前端可传空）
function getClientIp() {
  return "";
}
```

## 2）构建请求头（最关键！）
```js
// 构建 head
const buildHead = (tranCode, url) => {
  return {
    APP_ID: "202",

    H_APP_VERSION: "1.0",
    H_OS_TYPE: "W",
    H_OS_VERSION: "Windows 10",
    H_DEVICE_MODEL: navigator.userAgent, // 浏览器真实信息
    H_BLACK_BOX: "",
    H_DEVICE_NO: getDeviceNo(),
    H_TRACK_SEQ: getTrackSeq(),
    H_SEND_DATE: getDate(),
    H_SEND_TIME: getTime(),
    CLIENT_IP: getClientIp(),
    TRANS_URL: url
  };
};
```

## 3）登出请求完整代码
```js
// 登出接口
export async function loginLogout() {
  const req = {
    head: buildHead("login/logOut", "/api/login/logOut"),
    body: {}
  };

  // 发送请求
  return await axios.post("/api/login/logOut", req);
}
```

```swift
struct HeadModel: Codable {
    let APP_ID: String
    let H_TRAN_CODE: String
    let H_CHNL_NO: String
    let H_INCORP_NO: String
    let H_APP_VERSION: String
    let H_OS_TYPE: String
    let H_OS_VERSION: String
    let H_DEVICE_MODEL: String
    let H_BLACK_BOX: String
    let H_DEVICE_NO: String
    let H_TRACK_SEQ: String
    let H_SEND_DATE: String
    let H_SEND_TIME: String
    let CLIENT_IP: String
    let TRANS_URL: String
}

struct BaseRequest<T: Codable>: Codable {
    let head: HeadModel
    let body: T
}

// 构建 Head
func buildHead(tranCode: String, url: String) -> HeadModel {
    let date = Date()
    let df = DateFormatter()
    df.dateFormat = "yyyy-MM-dd"
    let sendDate = df.string(from: date)
    
    df.dateFormat = "HH:mm:ss"
    let sendTime = df.string(from: date)
    
    df.dateFormat = "yyyyMMddHHmmssSSS"
    let seq = "XSQD\(df.string(from: date))\(Int.random(in: 1...100000))"
    
    return HeadModel(
        APP_ID: "202",
        H_TRAN_CODE: tranCode,
        H_CHNL_NO: "202",
        H_INCORP_NO: "001",
        H_APP_VERSION: "1.0",
        H_OS_TYPE: "I",
        H_OS_VERSION: UIDevice.current.systemVersion,
        H_DEVICE_MODEL: "iPhone",
        H_BLACK_BOX: "",
        H_DEVICE_NO: UIDevice.current.identifierForVendor?.uuidString ?? "",
        H_TRACK_SEQ: seq,
        H_SEND_DATE: sendDate,
        H_SEND_TIME: sendTime,
        CLIENT_IP: "",
        TRANS_URL: url
    )
}
```

# 三、哪些变量 必须放 head？（固定规范）
head = 公共请求头，所有接口都一样

放这些：
1. 应用编号 APP_ID
2. 交易码 TRAN_CODE
3. 渠道编号 CHNL_NO（PC/安卓/iOS/H5）
4. 机构号 INCORP_NO
5. 版本号 APP_VERSION
6. 设备信息（型号、系统、设备号）
7. 唯一流水号 TRACK_SEQ（必传，用于日志追踪）
8. 请求时间 SEND_DATE + SEND_TIME
9. 客户端IP
10. 接口地址 TRANS_URL

head 里不放业务数据！

# 四、哪些变量 必须放 body？
body = 业务数据，每个接口不同

例如：
- 登录：userNo、password、custNo、phone
- 转账：payAccount、recvAccount、amount、fee
- 查询：idNo、name、custNo
- 登出：空（{}）

业务数据永远放 body！

# 五、鉴权 token 放哪里？（非常重要）
token 不放 head，也不放 body！
放在 HTTP 请求头 header 里！

```
Header:
token: xxxxxxxxxxxxx
Authorization: Bearer xxxxx
```

原因：
- 安全
- 全局拦截器统一处理
- 不参与业务序列化

# Web客户端「忘记密码」+「修改密码」完整安全方案
核心解决：防止盗号、越权、暴力破解、短信/邮箱劫持、账号被盗重置密码，覆盖两个场景全流程安全设计，直接可写进需求&开发文档。

## 一、先明确两个场景区别（安全边界不一样）
1. 忘记密码（找回重置）：用户未登录，验证身份后直接重置新密码
2. 修改密码（改密）：用户已登录，输入旧密码→设置新密码

两个场景安全风险完全不同，防护策略分开设计。

---

## 二、忘记密码（未登录）安全防护（最高危场景）
风险：短信验证码劫持、邮箱劫持、接口遍历撞验证码、恶意遍历手机号、直接调用接口重置密码

### 1. 前端安全限制
1. 手机号/邮箱脱敏显示，不完整暴露
2. 发送验证码按钮：倒计时、图形验证码前置（防机器刷接口）
3. 禁止URL拼接参数传手机号、验证码、token
4. 禁止浏览器缓存页面、禁止后退重复提交

### 2. 接口后端核心安全（必做）
1. 发送验证码接口限流
   - 同一IP：1分钟≤5次
   - 同一手机号：1分钟≤1次，1小时≤5次
   防止恶意轰炸短信/邮箱、暴力猜验证码

2. 验证码有效期短
   短信/邮箱验证码：5~10分钟过期，一次性有效，用完立即销毁

3. 生成一次性重置令牌（resetToken），绝不直接用验证码改密
流程：
手机号验证通过 → 后端生成临时加密重置token（带过期时间、绑定手机号、随机盐、不可预测）
前端携带resetToken请求重置密码，不携带手机号
防止抓包篡改手机号重置别人账号密码

4. resetToken安全规则
- AES/RSA加密签名，不可伪造
- 绑定用户ID+过期时间，跨用户不可复用
- 重置成功立刻作废，只能使用1次

5. 密码强度校验
新密码长度、大小写、数字、特殊字符，禁止简单密码123456

6. 重置成功安全通知
短信/邮箱通知：您的账号密码已重置，非本人操作立即冻结账号

## 三、已登录修改密码场景安全防护
风险：会话劫持、CSRF、越权修改他人密码、弱密码、接口未鉴权

1. 必须校验旧密码
不能跳过旧密码直接改新密码，防止账号被盗后别人随便改密

2. 接口必须携带登录会话token（session/accessToken）
后端校验：token归属当前用户ID，禁止越权

3. 防止CSRF攻击
请求头携带CSRF Token，后端校验同源

4. 改密后强制注销当前所有登录设备
踢下线其他端登录（手机、网页、小程序），防止盗号者继续登录

5. 改密成功通知提醒
站内信+短信/邮箱：密码已修改

6. 禁止新旧密码一致
禁止短时间频繁修改密码

## 四、两个场景通用高危漏洞&修复清单（面试/评审直接用）

# 先通俗说：防跨步攻击 = 防越权重置密码（密码跨步漏洞）
你之前问的【忘记密码】里最严重、最常见的安全漏洞，面试、安全评审必考。

## 一、什么是「密码跨步漏洞（跨步攻击）」？
简单一句话：
攻击者A，用自己手机号收验证码，但是抓包篡改接口参数，把别人B的账号重置密码。

也就是：
验证了我自己 → 却拿去改了别人账号 → 这就叫跨步（越权跨步重置密码）

### 正常应该是：
手机号138xxxx → 验证通过 → 只能重置138xxxx这个账号

### 跨步漏洞攻击过程：
1. 攻击者自己输入自己手机号 `138A`
2. 获取短信验证码，输入正确验证码
3. 抓包接口，把请求里的 `userId/手机号` 改成别人 `138B`
4. 直接重置别人密码，登录别人账号

后端只校验了验证码对不对，没校验验证码属于哪个用户，就形成跨步漏洞。

# 二、完整：忘记密码防跨步 标准流程（安全正确版）
## 步骤1：前端输入手机号，先图形验证码防刷
输入手机号 → 滑动/图形验证码 → 才能发送短信验证码

## 步骤2：后端发送短信验证码时
后端生成验证码，把验证码和【当前手机号/用户ID】绑定存储
验证码 = 手机号 + 过期时间 + 随机串
≠ 全局通用验证码

## 步骤3：用户输入短信验证码提交校验
后端校验：
1. 验证码是否正确
2. 验证码归属的手机号，和前端提交手机号完全一致
不一致直接拒绝 → 这一步就是防跨步核心

## 步骤4：校验通过，生成【一次性重置令牌resetToken】
重点：
resetToken内部加密绑定用户ID，返回给前端
前端重置密码时，只传resetToken，不再传手机号/用户ID

后端解密resetToken拿到用户ID，重置对应账号密码。

## 步骤5：重置密码成功
resetToken立即作废、验证码作废、踢掉所有登录、发送异常通知。

# 三、防跨步 vs 不防跨步 对比一眼看懂
|情况|是否防跨步|漏洞原因|
|----|----|----|
|后端只校验验证码对错，不绑定手机号|不防跨步|可篡改手机号重置他人账号（跨步漏洞）|
|验证码绑定手机号，提交必须一致|防跨步|篡改手机号则验证码不匹配|
|重置用绑定用户ID的resetToken，不传手机号|彻底防跨步|无法篡改用户|

# 四、再区分：修改密码场景有没有跨步？
已登录修改密码：
接口必须校验当前登录token对应的用户ID
后端直接用token里的用户ID改密，前端不能传userId
所以修改密码天然很难跨步，跨步漏洞99%都出在【忘记密码找回】。

## 二、接口拆分（一共2个接口，不是1个）
1. 发送短信验证码接口：`/api/pwd/sendCode`
2. 验证验证码+获取重置令牌：`/api/pwd/verifyCode`
3. 用令牌重置密码：`/api/pwd/resetPassword`

> 为什么分3步？不分步 = 100%跨步漏洞

# 三、每个接口：参数是谁提供？前端传啥？后端存啥？校验啥？
## 1）接口1：发送验证码 sendCode
### 前端请求参数（前端提供）
```json
{
  "mobile": "138xxxxxxxx",   // 用户输入手机号
  "captcha": "xxxx"         // 图形验证码（防刷）
}
```

### 后端做什么（关键防跨步第一步）
1. 校验图形验证码正确
2. 根据mobile查询数据库，拿到userId
3. 生成6位短信验证码 `smsCode`
4. 后端Redis存储：
```
key: sms:reset:138xxxxxxxx
value: {userId, smsCode, expireTime}
过期：5分钟
```
> 重点：验证码和userId、手机号三者绑定，不是单独存验证码

后端发送短信给手机，前端不拿到userId。

## 2）接口2：校验短信验证码 verifyCode（防跨步核心接口）
### 前端请求参数（前端只传这2个）
```json
{
  "mobile": "138xxxxxxxx",
  "smsCode": "123456"
}
```
前端不传userId！！！

### 后端校验逻辑（完整防跨步代码逻辑）
1. 后端从Redis根据前端传的mobile，取出缓存对象：`{userId, smsCode, expire}`
2. 判断是否过期
3. 判断前端传入smsCode 是否 == 缓存smsCode
4. 重点跨步校验：前端传的mobile，必须等于缓存里绑定的mobile
   不一致 → 直接报错：验证码不匹配（防跨步）

> 攻击者抓包把mobile改成别人的 → Redis查不到对应验证码/绑定不一致 → 直接拦截

5. 校验全部通过 → 后端生成一次性重置令牌 resetToken
resetToken加密签名，内部包含：userId、过期时间、随机盐
返回给前端：
```json
{
  "resetToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

### 关键规则：
resetToken 后端生成、后端加密、绑定userId
前端只负责携带，前端无法篡改、无法伪造、无法改成别人userId

---

## 3）接口3：最终重置密码 resetPassword（彻底杜绝跨步）
### 前端请求参数（前端只传2个）
```json
{
  "resetToken": "xxx",
  "newPassword": "xxx"
}
```
重点：
前端不再传mobile、不再传userId！！！

### 后端校验逻辑（最终防跨步）
1. 后端解密resetToken
2. 校验token是否过期、是否签名合法、是否已经使用过
3. 从token里后端自己取出userId
4. 后端根据自己取出的userId修改密码
5. 修改成功：立即删除Redis验证码、作废resetToken（一次性）

> 攻击者抓包想改userId？不可能
> token是后端加密签好的，篡改就失效

# 四、完整后端伪代码（Java版，直接看懂逻辑）
## 1.发送验证码
```java
public void sendResetCode(String mobile, String imgCode) {
    // 校验图形验证码
    checkImgCode(imgCode);
    // 查询用户
    User user = userMapper.selectByMobile(mobile);
    Long userId = user.getId();
    // 生成短信验证码
    String smsCode = RandomUtil.randomNumbers(6);
    // 【防跨步】验证码绑定手机号+userId
    RedisUtil.set("sms:reset:"+mobile, 
            JSON.toJSONString(new CodeDTO(userId, mobile, smsCode)), 
            5, TimeUnit.MINUTES);
    // 发送短信
    smsService.send(mobile, smsCode);
}
```

## 2.校验验证码（跨步校验核心）
```java
public String verifyResetCode(String mobile, String smsCode) {
    String key = "sms:reset:"+mobile;
    String cache = RedisUtil.get(key);
    if(cache == null) return "验证码过期或错误";

    CodeDTO dto = JSON.parseObject(cache, CodeDTO.class);

    // ========== 防跨步关键校验 ==========
    // 前端传的手机号 必须 == 缓存绑定手机号
    if(!dto.getMobile().equals(mobile)){
        return "非法请求，禁止跨步越权"; //跨步攻击直接拦截
    }
    if(!dto.getSmsCode().equals(smsCode)){
        return "验证码错误";
    }

    // 校验通过，生成重置token，绑定userId
    String resetToken = tokenUtil.createResetToken(dto.getUserId());
    return resetToken;
}
```

## 3.重置密码（彻底防跨步）
```java
public void resetPassword(String resetToken, String newPwd) {
    // 解密token，后端自己拿userId，不信任前端
    ResetTokenDTO dto = tokenUtil.verifyResetToken(resetToken);
    Long userId = dto.getUserId();

    // 判断token是否已使用、过期
    if(tokenUtil.isUsed(resetToken)){
        throw new RuntimeException("令牌无效");
    }

    // 后端用自己取出的userId改密
    userMapper.updatePassword(userId, newPwd);

    // 令牌作废、验证码清空
    tokenUtil.markUsed(resetToken);
    RedisUtil.del("sms:reset:*");
}
```

# 五、总结：谁提供参数？前端/后端分工？
|参数|前端提供？|后端提供？|作用|防跨步关键|
|---|---|---|---|---|
|mobile手机号|前端输入上传|后端绑定缓存|收验证码|提交mobile必须和缓存一致|
|smsCode短信码|前端输入上传|后端生成存储|验证身份|必须匹配缓存userId+mobile|
|userId|前端绝对不传|后端DB查询+存入缓存+加密进token|唯一账号标识|重置密码完全由后端token取userId|
|resetToken重置令牌|前端只携带|后端加密生成|安全重置凭证|不可篡改、绑定用户、一次性|

# 六、其他端（APP/小程序/H5）如何统一校验？
规则完全一样，不分端：
1. 所有端发送验证码都必须绑定手机号+userId
2. 所有端校验验证码都必须校验手机号归属一致
3. 所有端重置密码都只能传resetToken，禁止传userId/mobile
4. token加密算法、过期时间、一次性规则全端统一
5. 网关层统一拦截：重置密码接口检测到前端传userId/mobile → 直接拒绝
