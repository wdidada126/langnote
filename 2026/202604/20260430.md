- 头衔：中国现代目录学奠基人、武大图书情报学院首任院长、人文社科资深教授、荆楚社科名家 。

3. 全国首创图书发行学本科专业，完善图情学科体系布局。
4. 主持多项国家级课题，成果获教育部、全国人文社科优秀成果奖多项 。
 
2. 严怡民
 
- 头衔：中国科技情报学奠基人，武大首个情报学博士点创始人 。
- 研究方向：科技情报理论、情报教育、情报管理。

分库分表中间件全清单（开源+闭源｜客户端/代理/云原生全覆盖）
 
一、开源中间件（主流必用）
 
1. 客户端分片（SDK嵌入、无代理、性能高）
 
- Apache ShardingSphere-JDBC（Apache顶级）：Java内嵌Jar，分库分表、读写分离、分布式事务、数据脱敏，国内企业首选 
- TSharding（蘑菇街）：轻量客户端分片，适配电商场景，规则简单
- Hibernate Shards：老牌ORM层分片，老旧项目遗留技术
 
2. 服务端代理分片（独立服务、多语言透明接入）
 
- MyCat（国产最流行）：基于阿里Cobar，MySQL协议代理，分片+读写分离+多租户，社区庞大

- Dble：MyCat团队升级版，稳定性、SQL兼容性更强
- 360 Atlas：轻量MySQL代理，分片+读写分离，适合中小集群
- Vitess（Google）：K8s云原生，大规模MySQL分片，适合容器化架构
- ProxySQL：通用数据库代理，支持分片、路由、熔断，生态通用
 
3. 海外开源
 
- MaxScale（MariaDB）：官方企业级代理，分片+读写分离+故障转移
- pgBouncer Sharding：PostgreSQL生态分片代理

2. 大厂自研
 
- OceanBase 分片路由：蚂蚁金服分布式数据库，内置自动分片，闭源
- 京东Sharding-JDBC商业版：定制化分片+多活方案
- 腾讯云 TDSQL：商业分布式MySQL，自动分库分表，托管化
- 百度DBProxy：内部分片代理，未开源
 
3. 传统商业
 
- OneProxy：商业数据库中间件，分片+负载均衡，闭源
- IBM DB2 Sharding Gateway：传统商用库分片网关

先直接给结论：
sendfile 不是 CPU 指令集，而是 Linux 系统调用（syscall），MQ（消息队列）里用到它，是为了零拷贝提升网络发送性能。
 
 
 
1. 它到底是什么？
 
- 属于 Linux 系统调用： sendfile(int out_fd, int in_fd, ...) 
- 作用：在内核态直接把文件数据拷贝到 socket
- 不用经过：用户态缓冲区 → 内核态 socket 缓冲区 的拷贝
 
所以它是操作系统提供的功能，不是 CPU 指令（不是 mov、cmp 这种）。


2. 为什么 MQ 会用到 sendfile？
很多 MQ/存储层做持久化 + 网络发送时会用：
- Kafka 最典型：日志文件直接通过 sendfile 发给消费者
- RocketMQ 也类似，CommitLog 转发消费时用零拷贝
目的：减少数据拷贝、减少系统调用、降低 CPU 占用。
 

3. 和 CPU 指令集的关系
 
- sendfile 底层会用到 CPU 指令（比如内存复制、DMA）
- 但 sendfile 本身不是指令集，是操作系统封装好的接口
- 类似： read / write  也是系统调用，不是指令
 
 
 
一句话总结：
sendfile 是 Linux 零拷贝系统调用，MQ 用它做高效网络传输，它不属于 CPU 指令集。

以 Kafka、RocketMQ 这类高性能 MQ 为例，除了  sendfile ，还大量依赖下面这些系统调用，按用途给你分好类了：
 
一、文件 / 磁盘相关（持久化核心）
 
1.  open  /  openat 
打开 CommitLog、索引文件、日志分段文件。
2.  pwrite  /  pread 
带偏移量的原子读写，MQ 写日志常用，不需要 lseek，效率更高。
3.  fsync  /  fdatasync 
强制刷盘，保证消息不丢。-  fdatasync  只同步数据，更快
-  fsync  连元数据一起同步，更安全
4.  mmap  /  munmap 
内存映射文件，MQ 最核心系统调用之一。
把磁盘文件映射到虚拟内存，直接读写内存 = 写磁盘，减少拷贝。
5.  fallocate 
预先分配磁盘空间，避免运行时动态扩容导致卡顿。
6.  ftruncate 
扩展或截断文件，用于日志滚动、分段。
 
二、网络 IO 相关（高性能通信）
 
1.  socket  /  bind  /  listen  /  accept 
基础 TCP 网络系统调用。
2.  epoll_create  /  epoll_ctl  /  epoll_wait 
Linux 多路复用，支撑百万连接，MQ 网络层必用。
3.  recv  /  send  /  recvfrom  /  sendto 
普通网络读写（非零拷贝路径）。
4.  splice 
类似 sendfile，在内核管道/文件/socket 之间零拷贝搬运数据。
5.  setsockopt 
设置 TCP 参数：- SO_REUSEPORT
- TCP_NODELAY
- SO_RCVBUF / SO_SNDBUF
 
三、进程 / 线程 / 同步
 
1.  clone  /  fork 
创建子进程/线程。
2.  pthread  系列底层调用
线程创建、互斥锁、条件变量。
3.  eventfd  /  timerfd 
用于线程间唤醒、定时任务，无锁、高效。
4.  futex 
Linux 底层轻量级锁，几乎所有高并发 MQ 的锁都基于它。
 
四、内存管理
 
1.  brk  /  mmap 
堆内存分配、大内存申请。
2.  mlock  /  munlock 
锁住内存不被 swap 换出，保证低延迟。
 
五、其他工具类
 
1.  stat  /  fstat 
获取文件大小、修改时间，用于日志清理、滚动。
2.  unlink 
删除过期日志分段。
3.  gettimeofday  /  clock_gettime 
高精度时间戳，消息存储、超时判断。
 
 
 
一句话总结 MQ 最核心的几个系统调用
 
- mmap：内存映射文件，写消息极快
- sendfile：零拷贝发数据
- epoll：高并发网络
- pread/pwrite：高效随机读写
- fsync/fdatasync：保证可靠性
- futex：高并发锁

Nginx 高并发&高稳定核心技术 + 带年份时间线 + 异步高并发技术演进
 
一、支撑高并发+高稳定 核心底层技术
 
1. 依托 Linux C10K 内核能力（2003 年背景）
 
2003 年前后互联网爆发，C10K 万级并发瓶颈凸显，Linux 2.6 内核正式推出  epoll ，彻底淘汰 select/poll 低效轮询：
 
- 采用 epoll 边缘触发ET + 水平触发LT 双模式，时间复杂度 O(1)，仅返回就绪文件描述符，单机支撑 10w+ 长连接。
- 全链路 Socket 非阻塞设计，读写循环捕获  EAGAIN/EWOULDBLOCK  重试，无同步阻塞、无线程闲置浪费，完美适配异步模型。
 
2. Master-Worker 多进程隔离架构（Nginx 1.0 定型，2004）
 
- Master 主进程：专属负责信号监听、配置热重载、版本平滑升级、Worker 故障监护，不处理业务IO。
- Worker 工作进程：数量与 CPU 核心绑定，单进程单 epoll 实例，纯无锁事件循环，规避多线程竞争、锁冲突与上下文切换开销。
- 强进程隔离：单个 Worker 内存溢出、异常崩溃不会牵连整体，Master 自动重启恢复，筑牢工业级稳定性底座。
 
3. 深度复用 Linux 高性能系统API
 
- 零拷贝体系： sendfile() 、 splice() 、 mmap() ，跳过用户态内存拷贝，静态资源转发大幅降低CPU与IO损耗。
- 多核负载： SO_REUSEPORT  端口复用，内核层面将连接均分到多，Worker，解决多核争抢瓶颈。
- 网络栈优化： TCP_NODELAY  关闭粘包延迟、自定义读写缓冲区、快速回收 TIME_WAIT 连接，适配高吞吐短连接与长连接场景。
 
4. 自研工程化稳定设计
- 轻量化内存池：统一管理内存分配/释放，减少频繁  malloc/free  系统调用，杜绝内存碎片与长期运行泄漏。
- 事件+定时器双调度：精准管控连接超时、空闲回收、心跳淘汰，避免僵死连接堆积耗尽文件句柄。
- 微内核模块化：核心代码极简，功能以插件化扩展，缩小故障攻击面，降低复杂迭代带来的稳定性风险。
 

二、同期竞品差距（印证 Nginx 稳定性优势）
1. Apache：同步阻塞+每连接进程/线程模型，并发上限极低，无法突破 C10K。
2. lighttpd：早于 Nginx 实现异步事件模型，但长期存在内存泄漏、边界异常崩溃问题，生产稳定性不足。
3. 时代背景：2000–2005 年异步高并发编程理论、调试工具、工程实践完全空白，Nginx 手写复杂异步状态机，实现高性能+高可用，工程设计极具前瞻性。

一、Bazel 分布式缓存 命中核心原理
Bazel 是纯基于哈希 + 可复现构建的缓存体系，和 Make/CMake/Conan 逻辑完全不同。
 
1. 缓存判断核心：Action Key（动作指纹）
每一个编译步骤（编译、汇编、链接、打包）叫一个  Action 
Bazel 为每个 Action 计算唯一指纹 = Action Key
只有 Action Key 完全一致，才会命中远程/本地缓存，直接下载产物、跳过编译。
 
 
 
2. Action Key 由哪些信息组成（你关心的「主机/环境信息」）
① 所有输入文件的 SHA256 哈希（最核心）
- 源码  .c/.cpp/.dart/.java 
- BUILD 文件、bazelrc 配置
- 依赖头文件、静态库、资源文件
- 脚本、工具链依赖文件
 
文件内容不变 → 哈希不变；改一行代码，哈希直接变，缓存失效。
 
② 完整的编译命令行参数
 
-  -O2 / -g  优化等级
- 宏定义  -DXXX 
- 目标架构  x86_64/arm64 
- 编译标准、静态/动态链接参数
 
③ 工具链哈希（关键，跨机器缓存核心）
 
- 编译器本身哈希（gcc/clang/ld/ar 二进制）
- 系统库、基础依赖的哈希
- SDK/NDK/系统头文件指纹
 
④ 固定环境白名单变量
 
Bazel 默认屏蔽绝大部分本地环境变量，只纳入白名单：
 
-  PATH （裁剪标准化）
- 系统时区、目标操作系统/CPU 架构
不会收集：主机名、IP、用户名、本地路径、系统无关环境变量。
 
⑤ 目标平台 / 执行平台 / 主机平台 三元组
 
plaintext
  
exec_platform（执行编译的机器）
target_platform（最终运行的机器）
host_platform（工具链运行环境）
 
 
跨架构编译、跨机器分布式，靠这组标识隔离缓存。
 
 
 
3. 重点：Bazel 会不会收集隐私/主机信息？
 
- 不上传：IP、Mac、用户名、硬盘路径、系统版本、进程信息
- 不识别：硬件差异、CPU 型号
- 只上传：文件哈希、Action 指令、工具链指纹、平台标识
完全无隐私泄露，只做构建一致性校验。
 
 
 
二、Conan 不同版本 → 是否一定不同编译产物？
结论
1. Conan 大版本跨版本：1.x vs 2.x
编译产物 100% 不通用，缓存完全隔离- 依赖解析逻辑变了
- 环境变量、依赖传递规则变更
- 编译器封装、构建上下文不同
2. 同大版本、小版本升级（如 2.0.5 → 2.0.10）
大概率产物不同，部分场景兼容- 修复编译补丁、cmake 生成逻辑微调
- 依赖版本锁、哈希计算规则微调
→ 建议视为「不兼容缓存」
3. 即使 Conan 版本相同
以下改动也会导致产物不一样：- conan profile 差异（os/arch/compiler/build_type）
- compiler major/minor 版本
- cppstd、libc++ 标准库
- 依赖包版本升级/降级
 
 
 
三、Bazel vs Conan 缓存逻辑 关键区别
维度 Bazel 分布式缓存 Conan 缓存 
判定依据 全量文件哈希+Action 指令+工具链 包名+版本+编译器+profile 摘要 
环境敏感度 极高（强可复现） 中等 
跨机器复用 天然支持（远程 CAS） 需要统一 profile/工具链 
产物隔离 细粒度 Action 级别 包级别 
版本影响 工具链变一点，缓存全失效 依赖包版本变即失效 
 
 
 
四、实操关键（分布式编译避坑）
1. 想跨机器 100% 命中缓存- 统一：编译器版本、工具链、系统依赖、bazelrc 编译参数
- 禁用本地动态环境变量、绝对路径硬编码
2. Conan + Bazel 混合架构- Conan 产出的依赖库，要打入 Bazel 输入哈希
- Conan 版本升级 → 强制清空远端缓存，避免诡异符号冲突
3. 远程执行（分布式调度）
Worker 集群必须工具链一致，否则 Action Key 不一致，永远miss
 
 
 
精简总结
1. Bazel 缓存键 = 输入文件哈希 + 编译参数 + 工具链指纹 + 平台信息，无隐私主机数据。
2. 不采集 IP、用户名、硬件信息，只做构建一致性校验。
3. Conan 1.x / 2.x 跨版本编译产物完全不兼容；同大版本小版本也建议隔离缓存。
4. 分布式编译缓存复用的核心：全环境标准化 + 工具链统一。

二、Jar 包 为什么「像 Bazel 命中缓存」？
 
1. 表层效果完全一样
 
- 你引入  implementation("xxx:xxx:1.0.0") 
- 本地已经下载过这个版本 Jar/AAR
- 不会重新网络下载、不会重新编译源码
👉 和 Bazel action 命中缓存、跳过重新编译 肉眼效果一模一样。
 
2. 但：Jar 是「二进制缓存」，不是「编译动作缓存」
 
- Android/Gradle：
缓存的是别人提前编译好的成品 Jar/AAR
只校验「版本号字符串」，不关心：编译器、系统、编译参数
- Bazel：
缓存的是你本机每一步编译动作的产物
校验全环境指纹，差一个编译参数、工具链版本就缓存失效

1. Conan2 和 Jar 更像
 
Conan2 也是预编译二进制包缓存：
 
- 只要：Conan 版本、编译器、OS、arch、build_type、依赖版本不变
- 直接复用本地缓存的  .a/.so/.dll 
和 Gradle 拉取本地缓存 Jar 逻辑高度统一：
按「环境+版本」复用二进制，规避重复构建/下载
 
2. Bazel 是另一套更强的模型
 
Bazel 不依赖「外部预编译包」：
 
- 大多是源码构建
- 缓存到「单步 Action 级别」
- 连一条编译参数、头文件改动都能精准识别
 
 
 
四、关键差异（面试/架构核心区别）
 
1. 缓存粒度
 
- Jar/Gradle/Conan2：包级粗粒度缓存
整个库不管改没改，版本号不变就复用
- Bazel：文件+编译动作细粒度缓存
只重新编译改动的单个文件/单个 Action
 
2. 缓存失效条件
 
- Jar：版本号改了才失效（极宽松）
- Conan2：编译器/架构/配置变了才失效（中等）
- Bazel：任意输入变更→哈希变更→缓存失效（极严格）
 
3. 可移植性
 
- Jar：跨机器、跨编译器强行通用，容易崩溃
- Conan2：按编译环境隔离缓存，兼容性可控
- Bazel：强一致哈希，分布式跨机器缓存最稳
 
 
 
五、一句话极简对标
 
1. Android Jar 本地缓存
= 只看版本号的「粗放二进制复用」
2. Conan2 本地包缓存
= 带编译环境隔离的「标准二进制依赖复用」
3. Bazel 分布式缓存
= 源码构建下「极致严格、细粒度、可跨集群」的编译产物复用
