# 二、方案逐条解析（面试背诵版）

## 1）同步调用 + 重试 + 熔断
**做法**：告警直接调用接口，失败重试 3～5 次，超时熔断。
**优点**：简单、实时、无中间件。
**缺点**：
- 下游挂了就丢报警
- 重试风暴
- 无法保证 100%
**结论**：**不能保证 100% 送达**，只能做基础保障。

---

## 2）本地重试队列 + 定时任务
**做法**：告警先落本地内存队列，失败放入重试池，定时任务重试。
**优点**：轻量、无依赖。
**缺点**：
- 应用重启丢失
- 无法分布式
- 高并发容易 OOM
**结论**：适合**非核心告警**，绝对不能保证 100%。

---

## 3）数据库 + 轮询补偿（**最稳、最通用、面试最爱**）
**做法**：
1. 告警先**入库**（status=待发送）
2. 定时任务（XXL-Job/Quartz）拉取未发送成功的
3. 发送成功 → 更新状态为成功
4. 失败继续重试，超过次数进入人工兜底

**优点**：
- 数据持久化，**机器宕机不丢**
- 分布式可扩展
- 成本低、通用、任何系统都能做
- 可审计、可回溯、可重放

**缺点**：
- 有延迟（秒级～分钟级）
- 数据库有轮询压力
- 不适合超高并发

**适用**：**核心告警、监控报警、工单、风控提醒**
**结论**：**不依赖 MQ 也能 100% 送达的首选方案**。

---

## 4）分布式事务（Seata/TCC/XA）
**做法**：告警生成与发送放在一个分布式事务里，要么都成功，要么都回滚。
**优点**：强一致、不丢、不错乱。
**缺点**：
- 复杂度极高
- 性能差
- 不适合高并发告警
**结论**：**太重，一般不用在告警**，适合交易、支付。

---

## 5）WebSocket / 长连接推送
**做法**：服务端与接收端保持长连接，告警实时推送。
**优点**：实时性极高。
**缺点**：
- 断网重连复杂
- 客户端掉线会丢消息
- 需要**确认 ACK + 离线重发**才能保证 100%
**结论**：必须配合**离线库 + 重发 + 持久化**才能 100%。

---

## 6）gRPC 双向流 + 可靠确认
**做法**：双向流推送，每条消息带 ID，接收方回复 ACK。
**优点**：低延迟、高效、可靠。
**缺点**：
- 需自己实现 ACK、重试、去重、离线消息
- 架构复杂
**结论**：能做到 100%，但开发成本高。


## 7）多通道兜底（短信 + 电话 + 机器人）
**做法**：
- 主通道：MQ/WebSocket
- 降级通道：短信/语音/钉钉机器人
**优点**：真正**业务层面 100% 触达**。
**缺点**：成本高。
**适用**：**核心金融告警、运维 P0 告警**。

数据库隔离级别，是事物隔离级别
MySQL 脏读、不可重复读、幻读
 
一、先搞懂三个问题
 
1. 脏读
读到别的事务还没提交的修改数据，对方回滚，你读到的就是脏数据。
2. 不可重复读
一个事务内，同一行数据两次查询结果不一样（被别的事务update提交了）。
3. 幻读
一个事务内，两次查询结果行数不一样（被别的事务insert/delete提交了）。
 
 
 
二、MySQL 怎么解决？
 
靠两个东西：事务隔离级别 + InnoDB 锁机制（行锁 + 间隙锁）
 
1. 脏读怎么解决？
 
- 原因：读了未提交数据
- 解决：把隔离级别设为 READ COMMITTED（RC）及以上
- 原理：只能读到已提交的数据
 
2. 不可重复读怎么解决？
 
- 原因：同一行被别的事务update 并提交
- 解决：使用 REPEATABLE READ（RR）（MySQL 默认）
- 原理：MVCC 多版本控制，事务内读快照，不受别的事务 update 影响
 
3. 幻读怎么解决？
 
- 原因：别的事务insert/delete导致行数变化
- 解决：
1）隔离级别 RR
2）配合 InnoDB Next-Key Lock（行锁 + 间隙锁）
- 原理：锁住范围，不让别的事务插入数据
 
 
 
三、标准背诵版（面试直接用）
 
1. 脏读：设置为 读已提交（RC） 及以上，禁止读取未提交数据。
2. 不可重复读：使用 可重复读（RR），通过 MVCC 快照读 保证同一事务内数据一致。
3. 幻读：在 RR 级别下，通过 Next-Key Lock（临键锁） 锁定索引区间，防止其他事务插入或删除，解决幻读。
 
 
 
四、一句话总结
 
- 脏读：RC 解决
- 不可重复读：RR + MVCC 解决
- 幻读：RR + Next-Key Lock 解决
- MySQL 默认隔离级别 RR，已经同时解决这三个问题。


今天聊个很多人忽略的冷知识，C++里std::string有个叫SSO的优化，全称Small String Optimization，小字符串优化。

啥意思呢？就是当你string里存的字符串比较短的时候，通常15个字节以内，数据直接存在string对象本身的栈内存里，不会去堆上分配。你可能觉得这有啥大不了的？但你想想，短字符串在实际业务里出现频率超高，函数参数、配置项、状态名，基本都是短的。如果没有SSO，每次构造一个string都要malloc一次堆内存，那开销可就大了去了，尤其是循环里反复创建临时string的场景，性能差距能差好几倍。

有个容易踩的坑，有些人觉得既然string内部有SSO，那sizeof(std::string)应该很小吧？其实在主流实现里sizeof(std::string)是32字节，因为它要同时容纳SSO缓冲区和一个指向堆内存的指针，所以string对象本身并不小。另外SSO的阈值各平台不一样，libstdc++是15，libc++是22，MSVC是15，跨平台代码要注意这个差异。

下次写代码创建大量短字符串的时候，心里可以想着SSO在默默帮你省掉无数次的堆分配，是不是感觉string又香了一分？

// 按字典序排序
const char *keywords[] = {
    "auto", "break", "case", ..., "while"
};

// 二分查找
int lookup(const char *s) {
    int left=0, right=sizeof(keywords)/sizeof(*)-1;
    while (left <= right) {
        int mid = (left+right)/2;
        int cmp = strcmp(s, keywords[mid]);
        if (cmp == 0) return mid; // 关键字
        if (cmp < 0) right = mid-1;
        else left = mid+1;
    }
    return -1; // 普通标识符
}

四、极简关键字表（哈希表）C语言示例
c
运行
#include <stdio.h>
#include <string.h>
#include <stdlib.h>

#define TABLE_SIZE 128

typedef struct {
    char *key;
    int token;
} Entry;

Entry table[TABLE_SIZE] = {0};

// 简单哈希
unsigned int hash(const char *s) {
    unsigned int h = 0;
    while (*s) h = h * 31 + *s++;
    return h % TABLE_SIZE;
}

// 插入关键字
void add_keyword(const char *key, int token) {
    unsigned int idx = hash(key);
    table[idx].key = strdup(key);
    table[idx].token = token;
}

// 查找
int lookup(const char *key) {
    unsigned int idx = hash(key);
    if (table[idx].key && strcmp(table[idx].key, key) == 0)
        return table[idx].token;
    return -1; // 不是关键字
}

int main() {
    add_keyword("if", 1);
    add_keyword("else", 2);
    add_keyword("int", 3);

    printf("if -> %d\n", lookup("if"));    // 1
    printf("abc -> %d\n", lookup("abc"));  // -1
    return 0;
}

编译原理。中间表示 vs 汇编（目标代码） 哪个先生成？
结论先说：先生成中间表示（IR），再生成汇编 / 目标代码。
标准编译流程顺序
源代码 → 2. 词法 / 语法分析 → 3. 生成中间表示 IR
对 IR 做各种优化（核心步骤）
从 IR 生成汇编代码
汇编器 → 目标文件（.o/.obj）
链接器 → 可执行文件
为什么必须先 IR、后汇编？
汇编是平台相关的（x86、ARM、RISC-V 各不相同）
IR 是平台无关的，适合做统一优化
优化算法在 IR 上实现最简单、高效
同一个前端 + 优化器，可以适配多个架构，只需要重写「IR→汇编」这一层
一句话记忆
IR 是编译器内部的 “通用汇编”，汇编是给具体 CPU 看的最终指令。顺序永远是：源码 → IR → 汇编 → 机器码

先给你一句**最核心结论**：
**InnoDB 里的 Next-Key Lock = 行锁（Record Lock） + 间隙锁（Gap Lock）**
默认 RR（可重复读）级别下，**普通的行锁查询，实际加的都是 Next-Key Lock**。

---

# 1. 三个锁的定义
## 1）Record Lock（行锁）
- 只锁**某一行记录本身**
- 锁住：`id = 10` 这一行
- 作用：防止别的事务修改/删除这一行

## 2）Gap Lock（间隙锁）
- 锁**两个索引之间的空隙**，不锁记录
- 锁住：`(5,10)` 这个区间
- 作用：**防止别的事务往这个间隙里 insert**，从而解决幻读

## 3）Next-Key Lock（临键锁）
- **行锁 + 间隙锁 合在一起**
- 锁住：`(5,10]` 左开右闭区间
- 作用：既防修改，又防插入，**彻底解决幻读**

---

# 2. 联系与区别（一句话版）
- **行锁**：锁单行，防 update/delete
- **间隙锁**：锁区间，防 insert
- **Next-Key Lock**：
  = 行锁 + 间隙锁
  = 既锁行，又锁前后间隙
  = InnoDB RR 级别下默认的锁机制

索引上的区间：
`(-∞,1], (1,5], (5,10], (10,15], (15,+∞)`

## 例1：行锁 Record Lock
```sql
select * from t where id = 10 for update;
```
- 只锁：`id=10` 这一行
- 允许：往 `(5,10)` 插入新行
- 不允许：修改/删除 `id=10`

---

## 例2：间隙锁 Gap Lock
```sql
select * from t where id = 10 for update;
-- 在某些条件下会退化成只锁间隙
```
更典型的是**范围查询命中不到数据**：
```sql

```
- 锁住区间 `(5,10)`
- 禁止 insert 任何 id 在 5~10 之间的数据
- 不锁任何已存在行

## 例3：Next-Key Lock（最常用）
```sql
select * from t where id = 10 for update;
```
在 RR 级别下，InnoDB 加的是：
- 行锁：锁 `id=10`
- 间隙锁：锁 `(5,10)`
合起来就是 **Next-Key Lock：(5,10]**

结果：
1. 不能修改/删除 id=10
2. 不能 insert id=6/7/8/9
3. 彻底避免幻读

|--------|--------|----------|
| 行锁 Record | 单行 | 不可重复读 |
| 间隙锁 Gap | 索引间隙 | 防止insert |
| 临键锁 Next-Key | 行+间隙 | 完全解决幻读 |

- 行锁：锁行
- 间隙锁：锁空
- Next-Key：锁行+锁空

## 一、源码层面：三个锁的定义与标识
### 1. 核心源码常量（lock0lock.h）
```c
// 锁类型（type_mode 低4位）
#define LOCK_REC_NOT_GAP  1 << 0    /* 行锁（仅锁记录） */
#define LOCK_GAP          1 << 1    /* 间隙锁（仅锁间隙） */
#define LOCK_ORDINARY     1 << 2    /* 临键锁（行锁+间隙锁，默认） */
#define LOCK_AUTO_INC     1 << 3    /* 自增锁 */
```

### 2. 锁结构（lock_t）
```c
struct lock_t {
    trx_t*            trx;        // 所属事务
    dict_index_t*     index;      // 锁在哪个索引
    uint32_t         type_mode;   // 锁模式+类型（含上述常量）
    union {
        lock_rec_t   rec;         // 行锁：space+page+heap_no
        lock_table_t tab;         // 表锁
    };
};
```
- **行锁（LOCK_REC_NOT_GAP）**：`type_mode` 标记为 **仅记录**，锁单个索引记录（heap_no）。
- **间隙锁（LOCK_GAP）**：`type_mode` 标记为 **仅间隙**，锁索引区间、不锁记录。
- **临键锁（LOCK_ORDINARY）**：`type_mode` 标记为 **记录+间隙**，左开右闭区间（a, b]。

### 3. 加锁决策函数（lock_rec_lock_get_type，核心）
```c
ulint lock_rec_lock_get_type(
    dict_index_t* index,
    ulint search_mode,
    bool unique_search
) {
    // 1. 唯一索引 + 精确匹配（=）
    if (unique_search && (search_mode == PAGE_CUR_GE)) {
        if (记录存在) return LOCK_REC_NOT_GAP;  // → 行锁
        else          return LOCK_GAP;           // → 间隙锁
    }
    // 2. 非唯一索引 / 范围查询（BETWEEN、>、<）
    return LOCK_ORDINARY;                        // → 临键锁（默认）
}
```
**源码结论**：
- **唯一索引等值命中** → **行锁**
- **唯一索引等值未命中 / 范围查询** → **间隙锁 / 临键锁**
- **非唯一索引任何查询** → **临键锁**

---

## 二、三大锁：联系、区别、应用场景（含源码触发条件）
### 1. Record Lock（行锁 / LOCK_REC_NOT_GAP）
#### （1）核心特性
- **锁对象**：**单个索引记录**（主键/唯一索引）
- **锁范围**：仅 `id=10` 这一行，不锁前后间隙
- **源码触发**：唯一索引 + 精确匹配 + 记录存在
- **作用**：防止该行被 **update/delete**，解决**不可重复读**

#### （2）应用场景（唯一索引等值）
- 主键/唯一键查询：
  ```sql
  SELECT * FROM user WHERE id=10 FOR UPDATE;  -- X行锁
  UPDATE user SET name='xx' WHERE id=10;       -- 自动X行锁
  ```
- 场景：**单行修改、扣减库存、用户信息更新**（高并发单行操作）
- 优势：**粒度最小、并发最高、无间隙阻塞**

#### （3）源码行为
- 调用 `lock_rec_add_to_queue`，`type_mode=LOCK_REC_NOT_GAP`
- 仅锁对应 `heap_no` 记录，位图标记单行

---

### 2. Gap Lock（间隙锁 / LOCK_GAP）
#### （1）核心特性
- **锁对象**：**索引间隙（开区间）**，不锁任何记录
- **锁范围**：`(5,10)`，禁止插入此区间
- **源码触发**：唯一索引等值未命中、外键/唯一键检查
- **作用**：防止 **insert**，解决**幻读**（插入导致条数变化）

#### （2）应用场景
- 唯一索引查询不存在记录：
  ```sql
  SELECT * FROM user WHERE id=8 FOR UPDATE;  -- id=8不存在 → 锁(5,10)间隙
  ```
- 外键约束、唯一键重复检查（防止并发插入重复）
- 场景：**防并发插入、唯一键冲突、订单号防重**

#### （3）源码行为
- `type_mode=LOCK_GAP`，仅锁区间、不锁记录
- 插入意向锁（Insert Intention）与 Gap Lock 互斥 → 插入阻塞

---

### 3. Next-Key Lock（临键锁 / LOCK_ORDINARY）
#### （1）核心特性
- **锁对象**：**行锁 + 间隙锁（组合）**
- **锁范围**：左开右闭 `(5,10]`（锁间隙+锁记录）
- **源码触发**：非唯一索引、范围查询（RR默认）
- **作用**：**同时防 update/delete/insert**，**彻底解决幻读**

#### （2）应用场景（最广泛）
- 非唯一索引查询（普通索引）：
  ```sql
  SELECT * FROM user WHERE age=20 FOR UPDATE;  -- 非唯一 → 临键锁(10,20]
  ```
- 范围查询（BETWEEN、>、<）：
  ```sql
  SELECT * FROM user WHERE age BETWEEN 15 AND 25 FOR UPDATE;
  -- 锁(10,20]、(20,30]...所有命中区间
  ```
- 场景：**列表查询、范围更新、统计计数、防幻读**（RR核心）

#### （3）源码行为
- `type_mode=LOCK_ORDINARY`，同时标记记录+间隙
- 扫描到的每个索引项都加 **(前间隙, 当前记录]**

---

## 三、联系与区别（表格+源码视角）
| 维度 | 行锁 Record Lock | 间隙锁 Gap Lock | 临键锁 Next-Key Lock |
|:--- |:--- |:--- |:--- |
| **源码常量** | LOCK_REC_NOT_GAP | LOCK_GAP | LOCK_ORDINARY（默认） |
| **锁范围** | 单行记录（=10） | 开区间 (5,10) | 左开右闭 (5,10] |
| **触发条件** | 唯一索引+等值+命中 | 唯一索引+等值未命中 | 非唯一索引/范围查询 |
| **隔离级别** | RC/RR | RR（RC基本无） | RR（RC关闭） |
| **解决问题** | 不可重复读 | 防insert、幻读 | 不可重复读+幻读（全解决） |
| **并发度** | 最高 | 中 | 较低（范围锁） |
| **源码函数** | lock_rec_lock(NOT_GAP) | lock_rec_lock(GAP) | lock_rec_lock(ORDINARY) |

**联系**：
- 临键锁 = 行锁 + 间隙锁（InnoDB 组合实现）
- 三者都**基于索引**（无索引→全表锁）
- 锁结构共用 `lock_t`，仅 `type_mode` 区分

## 四、实战场景：源码级案例（可复现）
表结构（RR隔离级别）：
```sql
CREATE TABLE t (id INT PRIMARY KEY, age INT, KEY idx_age(age));
INSERT INTO t VALUES (1,10),(5,20),(10,30),(15,40);
```

### 场景1：主键等值（唯一索引命中）→ 行锁
```sql
-- T1

SELECT * FROM t WHERE id=10 FOR UPDATE;  -- 源码：LOCK_REC_NOT_GAP
-- 仅锁 id=10，允许插入 id=6/7/8/9
```
- 源码：`unique_search=true` + 记录存在 → **行锁**

### 场景2：主键等值（唯一索引未命中）→ 间隙锁
```sql
-- T1
BEGIN;
SELECT * FROM t WHERE id=8 FOR UPDATE;  -- 不存在
-- 锁 (5,10) 间隙，禁止插入 id=6-9
```
- 源码：`unique_search=true` + 记录不存在 → **间隙锁**

### 场景3：非唯一索引（age）→ 临键锁
```sql

SELECT * FROM t WHERE age=30 FOR UPDATE;
-- 锁 (20,30] 区间：禁止修改age=30、禁止插入age=21-29
```
- 源码：非唯一索引 → **LOCK_ORDINARY**（临键锁）

### 场景4：范围查询 → 临键锁链
```sql
-- T1

-- 锁 (10,20]、(20,30] → 两个临键锁
```
- 源码：范围查询 → 逐个加 **临键锁**

## 五、源码关键结论（面试/开发必背）
1. **RR 级别默认 Next-Key Lock**，RC 级别**关闭间隙/临键锁**（仅行锁）
2. **唯一索引等值**是唯一能**降级为行锁**的条件（源码特殊分支）
3. 无索引 → 全表加临键锁（性能灾难）
4. 间隙锁**不互斥读**，仅**互斥插入**（Insert Intention Lock）
5. 三者**都锁索引**，不锁数据行（二级索引→回表再锁聚簇索引）
