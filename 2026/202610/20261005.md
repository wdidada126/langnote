静态存储期（static storage duration）是 C++ 对象生命周期模型里的一个核心概念，但它的定义、边界和常见误解，值得单独拆开讲。下面从标准语义、初始化顺序、与 linkage 的关系、以及落到实现层的表现几个角度展开。

---

## 1. 标准定义

C++ 标准 [basic.stc] 把存储期分为四类：

- static storage duration：整个程序运行期间存在
- thread storage duration：线程运行期间存在（`thread_local`）
- automatic storage duration：块作用域内存在
- dynamic storage duration：`new`/`delete` 管理

static storage duration 的对象：

> 在程序启动时分配存储，在程序结束时释放，其生命周期覆盖整个程序的执行。

关键点：static storage duration 是一个生命周期概念，不是“用 static 关键字声明的对象”。两者经常重合，但不完全等价。

---

## 2. 哪些对象有 static storage duration

容易漏掉的几类：

| 声明形式 | 是否有 static storage duration |
|---|---|
| 命名空间作用域的变量（`int g;`） | 是 |
| `static` 全局变量 | 是 |
| `static` 局部变量 | 是 |
| 匿名 namespace 里的变量 | 是 |
| 类静态数据成员 | 是 |
| 函数返回的引用/指针指向的静态对象 | 是（对象本身） |
| 字符串字面量 | 是（数组对象有 static storage duration） |
| `constexpr` / `constinit` 全局 | 是 |
| 临时对象 | 否（除非绑定到引用并延长生命周期到 static） |
| 块作用域的非 static 局部变量 | 否 |

两个常见混淆点：

1. `static` 关键字在类成员函数上不产生 static storage duration。`static void f();` 里的 `static` 是“没有 `this`”，跟存储期无关。
2. 块作用域的 `static` 局部变量确实有 static storage duration，但它的名字是块作用域，linkage 是 no linkage，生命周期是整个程序。

所以“static”这个词在 C++ 里至少承担了三种不同角色：

- storage duration（`static` 局部变量、`static` 全局变量）
- linkage（`static` 全局变量、`static` 函数）
- 成员属性（`static` 数据成员、`static` 成员函数）

这三者不总是同时出现。

---

## 3. 初始化：static storage duration 的核心难点

static storage duration 对象的初始化分两类：

### 3.1 静态初始化（static initialization）

包括：

- constant initialization：编译期完成，直接写进 `.data` / `.rodata`
- zero initialization：`.bss`，加载时清零

对非局部的 static storage duration 对象，zero initialization 在 constant initialization 之前，dynamic initialization 之前。

对函数局部的 static 变量，zero initialization 发生在第一次进入函数之前（实际上在程序启动时，但标准只保证在首次使用前）。

### 3.2 动态初始化（dynamic initialization）

包括：

- 有序初始化：同一 TU 内按定义顺序
- 无序初始化：不同 TU 之间顺序不确定

标准 [basic.start.dynamic] 的规则：

- 非局部 static storage duration 对象的 dynamic initialization，如果是有序的，按 TU 内定义顺序执行。
- 跨 TU 的顺序是未指定的，这是 static initialization order fiasco 的根源。
- C++17 起，对部分情况引入了 sequenced-before 保证（比如 `inline` 变量的初始化），但跨 TU 的非 inline 变量仍然未指定。

### 3.3 延迟动态初始化

对函数局部 static 变量：

- C++11 起要求线程安全
- 实现为 guard variable + `__cxa_guard_acquire/release`
- 第一次控制流到达声明时初始化
- 构造抛异常时 guard 回滚，下次重新尝试

这是 static storage duration 里唯一有“懒初始化”语义的类别。

---

## 4. 与 linkage 的关系

static storage duration 和 linkage 是两个正交维度，但经常被 `static` 关键字同时影响：

| 声明 | storage duration | linkage |
|---|---|---|
| `int g;`（命名空间作用域） | static | external |
| `static int g;`（命名空间作用域） | static | internal |
| `static int x;`（块作用域） | static | no linkage |
| `thread_local int t;` | thread | external |
| `static thread_local int t;` | thread | internal |
| 类静态数据成员 | static | 取决于类 |

注意：

- 块作用域的 `static` 变量没有 linkage。它不能被其他 TU 或甚至同一 TU 的其他函数按名字引用。
- 命名空间作用域的 `static` 变量有 internal linkage，名字只在本 TU 可见，但存储期仍然是 static。
- `const` 命名空间作用域变量在 C++ 里默认 internal linkage，这一点和 C 不同。

## 5. 落到实现层

### 5.1 section 选择

| 对象 | 典型 section |
|---|---|
| 非零初始化的可写 static | `.data` |
| 零初始化的可写 static | `.bss` |
| 只读 static（字符串、vtable、typeinfo） | `.rodata` |
| TLS static | `.tdata` / `.tbss` |
| 函数局部 static（非平凡构造） | `.bss` 原始存储 + guard |

### 5.2 初始化函数

- 非局部 dynamic init → `_GLOBAL__sub_I_*`，放进 `.init_array`
- 析构 → `_GLOBAL__sub_D_*`，放进 `.fini_array`
- 函数局部 dynamic init → guard + `__cxa_guard_*`
- 非局部析构注册 → `__cxa_atexit`

### 5.3 汇编层面

```cpp
struct X { X(); ~X(); };
X g;                    // 非局部 dynamic init
void f() { static X x; } // 函数局部 dynamic init
```

```asm
# g 的初始化
_GLOBAL__sub_I_g:
    call X::X()
    # 注册析构 __cxa_atexit

# f 里的 static
f():
    movb guard(%rip), %al
    testb %al, %al
    jne .Ldone
    lea guard(%rip), %rdi
    call __cxa_guard_acquire
    testl %eax, %eax
    je .Ldone
    call X::X()
    lea guard(%rip), %rdi
    call __cxa_guard_release
.Ldone:
    ...
```

## 6. 几个容易被忽略的细节

1. 字符串字面量的数组对象有 static storage duration，但它是 `const char[N]`，通常放 `.rodata`。多个相同字面量是否合并是未指定的。

2. `constexpr` 变量不一定是 static storage duration。如果它被 ODR-use，就有存储；否则可以完全被常量折叠掉，没有存储。

3. `constinit` 保证的是 constant initialization，不是 storage duration。`constinit int x = f();` 里的 `f()` 必须是 constexpr，否则编译错误。它不改变 storage duration。

4. 函数局部 static 的析构顺序：按构造完成顺序的逆序，在 `main` 返回后或 `exit` 时执行，通过 `__cxa_atexit` 注册。如果 `exit` 被调用，栈上的 automatic 对象不会析构，但 static 对象会。

5. `static` 局部变量的线程安全初始化只保证一次，但如果构造函数递归调用同一个 static 变量，行为是未定义或死锁，不是“再初始化一次”。

6. 非局部 static 的析构顺序：按构造顺序的逆序，但跨 TU 顺序同样未指定。如果析构函数访问另一个已析构的 static 对象，是 UB。

7. `thread_local` 的 static storage duration 是 thread storage duration，两者互斥。`static thread_local` 的 `static` 只影响 linkage，不影响 storage duration。

---

## 7. 常见误解

- 误解 1：`static` 关键字声明的对象都有 static storage duration。
  - 错。`static` 成员函数、`static` 类成员声明不产生对象；`static thread_local` 是 thread storage duration。

- 误解 2：static storage duration 对象的初始化顺序是确定的。
  - 错。同一 TU 内有序，跨 TU 未指定。C++17 只对部分情况有改进。

- 误解 3：函数局部 static 变量在程序启动时构造。
  - 错。它在第一次控制流到达声明时构造（C++11 起线程安全）。

- 误解 4：`const` 全局变量有 external linkage。
  - 错。C++ 里命名空间作用域的 `const` 变量默认 internal linkage。

- 误解 5：static storage duration 对象一定在 `.data` 或 `.bss`。
  - 不完整。也可能在 `.rodata`、`.tdata`、`.tbss`，或者根本没有存储（被常量折叠）。

---

## 8. 一句话总结

> static storage duration 是“对象生命周期覆盖整个程序运行”的语义；它和 linkage、`static` 关键字、初始化时机是三组独立但经常交织的概念。语言层保证生命周期和初始化规则，实现层通过 section 选择、`.init_array`、`_GLOBAL__sub_I_*`、`__cxa_guard_*`、`__cxa_atexit` 来落地。

如果要继续深挖，最自然的下一站是 thread storage duration（`thread_local` 的 TLS 模型、`__tls_get_addr`、动态 TLS 与静态 TLS）和 dynamic initialization 的跨 TU 顺序问题（`constinit`、`inline` 变量、module 的影响）。

可以。这两个主题正好是前面 `static storage duration` 往 C++ 对象模型 → ABI → ELF → loader/runtime 深挖的两条主线。

先建立一个总框架：

```text
C++ storage duration
│
├── automatic
├── static
├── thread        ← thread_local
└── dynamic       ← new / allocator 等

初始化 initialization
│
├── static initialization
│   ├── constant initialization
│   └── zero initialization
│
└── dynamic initialization
    ├── ordered
    ├── partially-ordered
    └── unordered
```

注意：thread storage duration 和 dynamic initialization 是两个不同维度。 `thread_local` 对象本身也可能需要动态初始化。

# 一、thread storage duration

## 1. `thread_local` 到底是什么意思

最简单：

```cpp
thread_local int counter = 0;
```

如果程序有三个线程：

```text
                 counter
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
Thread A         Thread B     Thread C
counter = 3      counter = 7  counter = 1
```

不是所有线程共享一个 `counter`。

而是：

> 每个线程都有自己独立的对象实例。

例如：

```cpp
thread_local int counter = 0;

void foo() {
    ++counter;
}
```

线程 A 调三次：

```text
A.counter = 3
```

线程 B 调五次：

```text
B.counter = 5
```

互不影响。

---

# 二、thread_local 与 static 的本质区别

比较：

```cpp
static int x;
thread_local int y;
```

`static` 对象：

```text
整个进程
   │
   └── x
        ↑
   所有线程共享
```

`thread_local`：

```text
Process
│
├── Thread A
│      └── y
│
├── Thread B
│      └── y
│
└── Thread C
       └── y
```

因此：

```text
static storage duration
→ 通常整个程序生命周期一个对象

thread storage duration
→ 每个线程生命周期各有一个对象
```

线程退出时，该线程对应的 `thread_local` 对象也会被销毁。

---

# 三、TLS：Thread Local Storage

从语言层继续往 ABI 下走：

```cpp
thread_local int x = 42;
```

编译器不能简单把所有访问都编译成：

```asm
mov eax, [x]
```

因为问题是：

> `[x]` 到底是哪个线程的 `x`？

所以操作系统、ABI、编译器、链接器、动态加载器共同提供：

TLS — Thread Local Storage

概念上：

```text
              TLS template
                   │
          创建线程时建立
                   ↓
Thread A TLS     Thread B TLS      Thread C TLS
┌──────────┐     ┌──────────┐      ┌──────────┐
│ x = 42   │     │ x = 42   │      │ x = 42   │
│ y        │     │ y        │      │ y        │
└──────────┘     └──────────┘      └──────────┘
```

所以 `thread_local` 不是简单的：

> “把变量放到另一个全局区。”

而是：

> 变量对应一个 TLS slot/offset，而每个线程都有自己的 TLS 实例。

---

# 四、x86-64 Linux 上怎么找到当前线程 TLS？

这里开始进入 ABI。

Linux x86-64 常见实现会利用：

```text
FS segment register
```

准确地说，现代 x86-64 下重点是：

```text
FS.base
```

它可以指向当前线程相关的数据结构。

于是访问 TLS 可以抽象成：

```text
current thread
     │
     ↓
  FS.base
     │
     ↓
TLS / TCB
     │
     └── x
```

因此编译器有机会把：

```cpp
thread_local int x;
```

编译成类似：

```asm
mov eax, DWORD PTR fs:[offset]
```

而不是进行哈希表：

```text
thread_id → TLS
```

查找。

这也是 TLS 能非常快的重要原因。

---

# 五、为什么会有多种 TLS model？

关键问题来自动态链接。

如果：

```cpp
thread_local int x;
```

编译器在编译时就知道：

```text
x 相对于当前线程 TLS base 的 offset
```

那么访问极其简单：

```text
TLS_base + constant_offset
```

但考虑：

```text
main executable
     │
     ├── libA.so
     │
     ├── libB.so
     │
     └── dlopen("plugin.so")
```

`plugin.so` 甚至可能在程序运行很久之后才加载。

编译 `plugin.so` 时：

> 怎么提前知道它的 TLS 数据最终放在哪？

不知道。

所以 ELF TLS ABI 设计出了多种 TLS model。

---

# 六、四种经典 ELF TLS Model

通常会遇到：

```text
Global Dynamic
Local Dynamic
Initial Exec
Local Exec
```

可以粗略理解成：

| TLS model | 灵活性 | 性能 | 常见场景 |
|---|---:|---:|---|
| Global Dynamic | 最高 | 较慢 | 通用 shared library |
| Local Dynamic | 高 | 较慢 | DSO 内部 TLS |
| Initial Exec | 较低 | 快 | 启动时已加载的 DSO |
| Local Exec | 最低 | 最快 | executable 自己的 TLS |

核心规律：

```text
越动态
    ↓
运行时查找越多
    ↓
访问成本越高

越确定
    ↓
链接阶段能计算更多
    ↓
最终代码越接近普通 offset 访问
```

---

# 七、Local Exec：最好理解

例如主程序：

```cpp
thread_local int x = 42;

int get() {
    return x;
}
```

链接器已经知道：

```text
x 在 TLS 中的位置
```

最终可以接近：

```asm
mov eax, DWORD PTR fs:[constant_offset]
```

逻辑：

```text
FS.base
   +
固定 offset
   ↓
当前线程 x
```

没有函数调用。

没有运行时符号查找。

所以：

> Local Exec 是最便宜的 TLS 访问方式之一。

---

# 八、Initial Exec

Initial Exec 允许共享库使用 TLS，但有一个重要假设：

> 这个 TLS 模块在程序启动阶段已经存在，可以使用静态 TLS 区域。

大致：

```text
FS.base
   +
链接器/loader 提供的 offset
   ↓
TLS variable
```

相比 Local Exec，多了一些间接性，但仍然非常快。

问题在于：

> 它不适合任意晚期 `dlopen()` 的 TLS 模块。

这就引出了：

static TLS vs dynamic TLS

---

# 九、static TLS 是什么？

这里的 `static TLS` 千万别和 C++ `static` 关键字混淆。

这是 ELF/runtime 层面的概念。

程序启动：

```text
Executable
libA.so
libB.so
libc.so
...
```

loader 已经知道这些模块需要多少 TLS。

于是可以为每个线程准备类似：

```text
Thread TLS block
┌───────────────────┐
│ executable TLS    │
├───────────────────┤
│ libA TLS          │
├───────────────────┤
│ libB TLS          │
├───────────────────┤
│ libc TLS          │
└───────────────────┘
```

这些可以提前规划。

因此：

> static TLS = loader 能够提前纳入线程 TLS 布局的 TLS。

# 十、动态 TLS 为什么存在？

运行中：

```cpp
dlopen("plugin.so", ...);
```

结果发现：

```text
plugin.so
└── thread_local Foo foo;
```

问题来了。

程序已经有：

```text
Thread A
Thread B
Thread C
```

它们的 TLS 都已经建立。

现在突然来了：

```text
plugin TLS
```

不能简单重新移动所有线程的 TLS。

因此 runtime 需要支持：

dynamic TLS allocation

概念上：

```text
Thread A
│
├── static TLS
│
└── dynamic TLS
       └── plugin.so TLS

Thread B
│
├── static TLS
│
└── dynamic TLS
       └── plugin.so TLS
```

这里通常需要更复杂的运行时寻址。

# 十一、`__tls_get_addr`

这就是你点名的核心。

对于不能直接用固定 offset 定位的 TLS，编译器可能生成调用：

```cpp
__tls_get_addr(...)
```

它的目标可以粗略理解为：

> 给我“当前线程中，某个 TLS 模块里的某个 TLS 变量”的地址。

概念输入：

```text
module ID
+
offset
```

然后：

```text
              __tls_get_addr
                     │
                     ↓
              当前线程 DTV
                     │
              ┌──────┴──────┐
              ↓             ↓
           module 3       module 7
              │
              ↓
         TLS block
              │
           + offset
              ↓
             &x
```

---

# 十二、DTV：Dynamic Thread Vector

这是理解动态 TLS 的另一个关键词。

可以把每个线程想象成维护：

```text
DTV
│
├── module 1 → TLS block
├── module 2 → TLS block
├── module 3 → TLS block
│
...
└── module N → TLS block
```

动态加载：

```text
dlopen(plugin.so)
        ↓
获得新的 TLS module ID
        ↓
必要时扩展/更新 DTV
        ↓
当前线程第一次访问
        ↓
__tls_get_addr
        ↓
找到/分配对应 TLS block
```

真实实现和 ABI 细节比这个复杂，但这个心智模型非常好用。

于是可以把：

```cpp
thread_local Foo x;
```

一路映射成：

```text
C++
thread_local
   ↓
Compiler
TLS relocation
   ↓
Linker
TLS model relaxation
   ↓
ELF loader / libc runtime
   ↓
TCB / DTV
   ↓
__tls_get_addr
   ↓
当前线程自己的 x
```

这就是第一条完整链路。

# 十三、第二大主题：dynamic initialization

现在回到 C++ 语言。

考虑：

```cpp
int foo();

int x = foo();
```

这不是简单的编译期常量初始化。

它可能需要：

```text
程序启动
   ↓
调用 foo()
   ↓
得到返回值
   ↓
初始化 x
   ↓
main()
```

这就是 dynamic initialization 的典型场景。

---

# 十四、static initialization vs dynamic initialization

例如：

```cpp
int a;
const int b = 10;
int c = 20;
int d = foo();
```

概念上可以分：

```text
Initialization
│
├── static initialization
│
│   ├── zero initialization
│   └── constant initialization
│
└── dynamic initialization
```

其中：

```cpp
int d = foo();
```

如果 `foo()` 不能在编译期完成初始化，那么就涉及 dynamic initialization。

---

# 十五、为什么跨 TU 会出大问题？

这是经典：

Static Initialization Order Fiasco

假设：

```cpp
// a.cpp

extern int b;

int getA() {
    return b + 1;
}

int a = getA();
```

另外：

```cpp
// b.cpp

int getB() {
    return 100;
}

int b = getB();
```

我们希望：

```text
b 初始化
↓
a 初始化
```

但是：

```text
a.cpp
b.cpp
```

属于不同 Translation Unit。

传统 C++ 中跨 TU 的动态初始化顺序存在非常重要的不确定性。

可能：

```text
b = getB()
↓
a = getA()
```

也可能在相关规则允许的情况下：

```text
a = getA()
↓
b = getB()
```

那么 `a` 初始化期间访问 `b` 就可能观察到：

```text
b 尚未完成 dynamic initialization
```

这就是著名的：

> Static Initialization Order Fiasco

简称：

SIOF

---

# 十六、为什么同一个 TU 相对好处理？

例如：

```cpp
int a = foo();
int b = bar();
int c = baz();
```

传统的 ordered dynamic initialization 对同一 TU 中按定义出现顺序提供了强得多的顺序关系：

```text
a
↓
b
↓
c
```

所以：

```text
同 TU
通常容易推理

跨 TU
危险显著增加
```

工程里真正让人头疼的是：

```text
A.cpp global object
      ↓ depends on
B.cpp global object
      ↓ depends on
C.cpp global object
```

最后形成：

```text
global constructor dependency graph
```

---

# 十七、Construct on First Use

经典解决方法：

不要：

```cpp
Foo globalFoo;
```

而：

```cpp
Foo& getFoo() {
    static Foo foo;
    return foo;
}
```

于是：

```text
程序启动
   │
   │ 不初始化 Foo
   ↓
main
   ↓
第一次 getFoo()
   ↓
初始化 foo
```

这把：

> 不确定的跨 TU 初始化

转换成：

> 第一次实际使用时初始化。

也就是我们前面讲的 function-local static。

所以你现在能看到两部分知识连接起来了：

```text
static local initialization
             ↑
             │
解决部分
             │
cross-TU dynamic initialization
```

# 十八、`constinit` 是干什么的？

C++20：

```cpp
constinit int x = 42;
```

`constinit` 的核心目标不是：

> x 永远不能修改。

那是 `const`。

而是要求：

> 这个具有 static/thread storage duration 的对象必须进行静态初始化（特别是保证不落入需要运行期动态初始化的情况）。

例如：

```cpp
constinit int x = 42;

int main() {
    x = 100;  // 可以
}
```

所以：

```text
const
    ↓
能不能修改？

constinit
    ↓
初始化阶段是否保证静态初始化？
```

完全不同。

---

# 十九、constinit 为什么能降低 SIOF 风险？

假设：

```cpp
int foo();

int x = foo();
```

可能需要：

```text
runtime dynamic initialization
```

改成：

```cpp
constinit int x = foo();
```

如果 `foo()` 不能提供满足常量初始化要求的结果：

```text
编译错误
```

而不是：

```text
悄悄生成 global constructor
```

因此 `constinit` 的价值之一就是：

> 把一部分“启动时才发现的初始化顺序问题”，提前变成编译期约束。

可以把它理解成一个非常有用的声明：

```text
“这个全局/静态/TLS 对象不能依赖运行期动态初始化。”
```

---

# 二十、`inline` variable 又改变了什么？

C++17：

```cpp
// config.h

inline Foo foo;
```

可以被：

```text
a.cpp
b.cpp
c.cpp
```

共同 include。

而程序中仍然表示满足 ODR 规则的同一个 inline variable 实体。

这解决的是过去：

```cpp
// header
Foo foo;   // ❌ 多重定义问题
```

这类问题。

但是：

> inline variable 并不等于“没有 dynamic initialization”。

例如：

```cpp
inline Foo foo = makeFoo();
```

`makeFoo()` 仍然可能要求动态初始化。

所以：

```text
inline
    ↓
ODR / 多 TU 定义模型

constinit
    ↓
初始化时机约束
```

也是两个完全不同的维度。

---

# 二十一、inline variable 还引出了“部分有序”

现代 C++ 对动态初始化不能只记：

```text
按顺序
vs
无顺序
```

还需要知道：

```text
ordered
partially-ordered
unordered
```

普通非模板、非 inline 变量通常属于 ordered initialization 的讨论范围。

而：

```cpp
inline Foo x;
```

引入了 partially-ordered initialization 的规则。

直觉上原因也很好理解：

普通变量：

```cpp
// a.cpp

A a;
B b;
```

源码顺序非常明确：

```text
a before b
```

但 inline variable 通常放 header：

```cpp
// common.h

inline A a;
inline B b;
```

然后：

```text
TU1 include common.h
TU2 include common.h
TU3 include common.h
```

标准需要定义：

> 当这些定义分布在多个 TU 中时，到底什么时候还能建立顺序关系？

因此才出现 partially ordered 这一层。

工程上不要把：

```cpp
inline
```

理解成：

> “初始化顺序问题彻底解决。”

它主要解决的是定义/ODR模型，并提供相应的初始化排序规则。

---

# 二十二、template static 又更复杂

例如：

```cpp
template<typename T>
struct X {
    static Foo value;
};
```

或者 inline/template 组合。

模板实例化可能发生在不同 TU。

因此初始化顺序更加难以建立传统：

```text
源码第一行
↓
第二行
↓
第三行
```

这样的全局顺序。

这也是 C++ 标准为什么必须区分：

```text
ordered
partially ordered
unordered
```

而不是简单说：

> “全局变量按照声明顺序初始化。”

这句话只在非常有限的上下文里成立。

---

# 二十三、Modules 能不能解决这个问题？

C++20 Modules 改变了非常多传统：

```text
header
↓
#include
↓
复制文本
```

的模型。

传统：

```text
a.cpp ─┐
       ├── #include config.h
b.cpp ─┤
       │
c.cpp ─┘
```

Modules 更接近：

```text
module A
   ↓ import
module B
   ↓ import
program
```

Import dependency 本身能够提供更多结构化信息。

因此 Modules 对初始化排序提供了比传统完全独立 TU 更明确的关系，特别是涉及模块依赖时。

但是千万不要总结成：

> Modules 消灭了 static initialization order fiasco。

不准确。

更好的理解：

> Modules 给编译系统增加了显式依赖关系，因此部分跨单元初始化顺序能够获得更强的约束，但动态初始化依赖本身仍然是需要谨慎设计的问题。

---

# 二十四、把 Modules 看成 dependency graph

传统 header：

```text
TU A          TU B
 │             │
 │ global A    │ global B
 │             │
 └──── ??? ────┘

链接器最后组合
```

很多语义关系并不直接表达成模块依赖。

Modules：

```text
Module A
   │
   ↓ import
Module B
   │
   ↓
Module C
```

现在编译器看到一个更明确的：

```text
dependency DAG
```

所以初始化顺序也有机会利用：

```text
module dependency
```

建立 happens-before / sequencing 类关系。

# 二十五、TLS 和 dynamic initialization 会在这里汇合

最有意思的是：

```cpp
thread_local Foo foo = createFoo();
```

它同时涉及：

```text
thread storage duration
+
dynamic initialization
```

因此：

```text
Thread A
第一次 odr-use foo
        ↓
createFoo()
        ↓
构造 A.foo

Thread B
第一次 odr-use foo
        ↓
createFoo()
        ↓
构造 B.foo
```

每个线程都有：

```text
自己的 Foo
+
自己的初始化状态
+
自己的析构
```

所以 TLS 绝不是：

> 每线程复制一块 `.data`

那么简单。

对于：

```cpp
thread_local std::string buffer;
```

runtime 需要处理：

```text
TLS 地址定位
        +
constructor
        +
初始化 guard/state
        +
thread exit destructor
```

# 二十六、从源码一路追到汇编

现在可以建立你真正需要的软件工程师视角。

源码：

```cpp
thread_local Foo foo;
```

### 编译阶段

编译器分析：

```text
thread storage duration
        ↓
TLS symbol
        ↓
选择/假设 TLS model
        ↓
生成 TLS relocation
```

### 链接阶段

linker：

```text
symbol visibility
PIC / PIE
executable / shared object
preemption
        ↓
决定是否可以 relaxation
        ↓
GD → IE？
GD → LE？
```

TLS relaxation 很重要：

> 编译器可能生成保守方案，链接器发现信息足够后，把昂贵访问优化成便宜访问。

### ELF

你可能看到：

```text
.tdata
.tbss
```

可以粗略类比：

```text
.data → initialized global/static data
.bss  → zero-initialized global/static data

.tdata → initialized TLS data
.tbss  → zero-initialized TLS data
```

### Loader

```text
ld.so
 ↓
读取 PT_TLS
 ↓
计算 TLS layout
 ↓
建立 initial thread TLS
 ↓
后续线程建立自己的 TLS
```

### Runtime access

最终可能变成：

```text
FS.base + offset
```

或者：

```text
__tls_get_addr(...)
```

# 二十七、另一个方向：普通全局对象怎么变成启动代码？

例如：

```cpp
Foo foo = makeFoo();
```

编译器需要生成类似概念上的：

```cpp
void __initialize_foo() {
    new (&foo) Foo(makeFoo());
}
```

然后安排：

```text
ELF initialization mechanism
        ↓
runtime startup
        ↓
__initialize_foo()
        ↓
main()
```

在 GCC/Clang/Linux 环境继续反汇编时，你经常会碰到：

```text
.init_array
_GLOBAL__sub_I_*
__static_initialization_and_destruction_0
```

具体名字属于实现细节，但它们非常适合用来理解：

> C++ 的“main 前构造全局对象”到底是怎么实现的。

# 二十八、`constinit` 在二进制层面为什么漂亮？

比较：

```cpp
Foo foo = makeFoo();
```

可能产生：

```text
storage
+
startup constructor code
+
.init_array entry
```

而如果一个对象能够完成 constant initialization：

```cpp
constinit int foo = 42;
```

最终可能基本就是：

```text
.data

foo:
    .long 42
```

程序启动时：

```text
loader 把数据映射进内存
```

就够了。

不需要：

```text
call initialize_foo
```

所以 `constinit` 不只是语言洁癖。

它可能直接影响：

```text
startup cost
binary initialization machinery
initialization dependency
global constructor complexity
```

# 二十九、工程上我建议的优先级

如果你以后写大型 C++ 系统，可以形成这样一个偏好：

```text
最好
│
├── constexpr / constant initialization
│
├── constinit
│
├── trivially initialized global state
│
├── function-local static
│
├── carefully designed dynamic initialization
│
└── cross-TU dynamically initialized globals
                         ↑
                       尽量少
```

尤其避免：

```cpp
// A.cpp
Foo a = makeFoo(b);

// B.cpp
Bar b = makeBar(c);

// C.cpp
Baz c = makeBaz(a);
```

这种：

```text
global dependency graph
```

程序规模一大，非常难维护。

# 三十、把你现在的知识串成一条“编译器/ABI路线”

你前面问过 `static`、ABI、汇编，这几个主题其实已经可以合并成一条非常漂亮的学习链：

```text
C++ source
│
├── static
├── thread_local
├── inline
├── constexpr
└── constinit
        ↓
C++ object model
        ↓
storage duration
│
├── automatic
├── static
├── thread
└── dynamic
        ↓
initialization model
│
├── zero initialization
├── constant initialization
└── dynamic initialization
        ↓
Translation Unit / ODR
        ↓
linkage
│
├── no linkage
├── internal linkage
└── external linkage
        ↓
ABI
        ↓
ELF
│
├── .text
├── .rodata
├── .data
├── .bss
├── .tdata
├── .tbss
├── .init_array
├── symbol table
└── relocations
        ↓
linker
│
├── symbol resolution
├── relocation
└── TLS relaxation
        ↓
dynamic loader
│
├── PT_TLS
├── TLS layout
├── module ID
└── DTV
        ↓
runtime
│
├── FS.base / TCB
├── __tls_get_addr
├── TLS constructors/destructors
└── global constructors
        ↓
assembly
```

到这里，`static` 就已经不再是“C++ 关键字知识点”了。

它实际上把 C++ 语言标准 → 编译器 → ABI → ELF → linker → dynamic loader → libc runtime → CPU 寻址 全部连接起来了。

你下一步尤其值得实际做一个小实验：分别写 `static int`、`thread_local int`、`thread_local std::string`、`constinit int`、跨 TU 动态初始化五个最小程序，然后用 `g++ -S`、`readelf -S/-s/-r`、`objdump -drC` 对照观察 `.data/.bss/.tdata/.tbss/.init_array`、TLS relocation、`__tls_get_addr` 和 `_GLOBAL__sub_I_*`。这样这套知识会从“概念”直接落到真实 ELF 二进制上。
