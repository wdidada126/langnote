# 哪些老书需要警惕？

可以用三个等级，而不是简单删除旧书：

继续读：核心思想和现代 Python 基本一致。

选择性读：思想仍然重要，但不要照抄环境、框架版本和 API。

不建议作为主教材：Python 2、旧 Django/Flask、旧 TensorFlow、旧 packaging 等内容占主体。

例如 Python Cookbook 3e 虽然出版时间已经很早，但仍然非常适合研究 Python idiom；相反，一本 2018 年的 Django/数据科学框架操作书可能已经严重过时。判断技术书寿命，不能只看出版年份。

你看到的这两种风格，本质上是 Python 打包生态标准化进程的产物。简单来说，`[project]` 是官方标准，而 `[tool.poetry]` 是 Poetry 工具早期自己定义的一套格式。

### 历史渊源：为什么会有两种？

`[tool.poetry]` 的出现早于官方标准。Poetry 在 2018 年诞生时，Python 还没有一个统一的 `pyproject.toml` 元数据标准，所以它自己定义了一套配置格式（`[tool.poetry]`），并一直沿用至今。

后来，社区制定了 PEP 621 标准，规定了项目元数据应该存放在 `[project]` 表中。从 Poetry 2.0（2025 年 1 月发布） 开始，Poetry 终于支持读取官方的 `[project]` 表了。

### 核心区别对比

| 特性 | `[project]` (PEP 621 标准) | `[tool.poetry]` (Poetry 专有) |
| :--- | :--- | :--- |
| 本质 | Python 官方打包标准 | Poetry 工具的私有配置 |
| 兼容性 | 极佳：`setuptools`、`hatchling`、`uv`、`flit`、`PDM` 等所有现代后端都支持 | 受限：主要被 Poetry 自身识别，其他工具可能忽略 |
| 依赖声明语法 | 使用 PEP 508 标准字符串，如 `"ortools>=9.0"` | 使用 Poetry 特有的 Caret (`^`) 或 Tilde 语法，如 `ortools = "^9.0"` |
| Python 版本约束 | 单独的 `requires-python` 字段 | 作为 `python` 依赖声明，如 `python = "^3.11"` |
| 开发依赖 | 放在 `[dependency-groups]` (PEP 735) 或自定义 `[project.optional-dependencies]` 中 | 放在 `[tool.poetry.group.dev.dependencies]` 中 |
| 构建后端 | 可自由选择（`setuptools`、`hatchling` 等） | 必须使用 `poetry-core` |

### 你现在应该选哪种？

推荐做法：混合使用，以 `[project]` 为主。

既然你正在用 Poetry（或者未来可能换用其他工具），最佳实践是把能标准化的都放进 `[project]`，只把 Poetry 独有的功能（比如复杂的依赖分组、`packages` 包含配置）留在 `[tool.poetry]` 里。

这样做的好处是：
1. 兼容性更好：任何支持 PEP 621 的工具都能读取你的项目信息。
2. 未来不折腾：如果以后想从 Poetry 迁移到 `uv` 或 `hatch`，几乎不需要改动 `pyproject.toml`。
3. 社区趋势：Poetry 2.x 已经开始弃用 `[tool.poetry]` 中有标准替代品的字段（如 `name`、`version`、`authors`、`dependencies` 等），并建议迁移到 `[project]`。

你之前写的 `pulp = "^2.8"` 那种风格，就是典型的 `[tool.poetry]` 写法。 如果迁移到 `[project]`，同一行依赖会写成 `"pulp>=2.8,<3.0"`（PEP 508 格式）。


规划与排程问题的数学基础，核心可以归纳为运筹学与组合优化。以下按知识层次和推荐书籍来整理。

### 数学知识列表

1. 基础层：线性代数与微积分
这是理解后续所有优化模型的前提。你需要熟悉向量、矩阵运算，以及函数的极值、梯度等概念。线性规划本质上就是线性代数在约束下的延伸。

2. 核心层：运筹学（OR）的经典分支
这是直接支撑规划与排程的数学主体：
*   线性规划：处理连续变量的资源分配问题，是理解约束与目标函数关系的起点。
*   整数规划：排班、排座这类问题中，变量（如“某学生是否坐某座位”）通常是 0/1 整数，必须掌握整数规划建模。
*   动态规划：适用于多阶段决策问题，如项目调度、资源分期分配。
*   图论与网络分析：用于建模任务依赖关系、最短路径、最大流等（如项目中的关键路径）。
*   排队论：分析服务系统中的等待与资源利用率，常用于评估排班或服务窗口设置的效果。

3. 应用层：调度理论（Scheduling Theory）
这是排程问题的“专业数学”：
*   确定性调度模型：研究在加工时间已知的情况下，如何排列任务以优化完工时间、延迟等目标。涉及单机、并行机、流水车间等经典模型及其算法复杂度分析。
*   随机调度模型：处理加工时间或到达时间不确定的情况，需要概率与随机过程知识。
*   启发式与元启发式：当问题规模大到无法求精确最优解时（NP-hard），需要遗传算法、模拟退火、禁忌搜索等方法。

4. 计算层：约束编程（Constraint Programming）
这是现代排程求解器（如 OptaPlanner）背后的核心数学与算法。它研究如何通过约束传播和搜索来高效地缩减解空间，专门处理组合问题。

### 参考书籍

入门与基础（运筹学通识）
*   《运筹学基础及应用》（胡运权）：国内经典教材，覆盖线性规划、整数规划、图论等基础，适合建立全貌。
*   《Introduction to Operations Research》（Hillier & Lieberman）：国际公认的运筹学入门标准教材，案例丰富，数学推导清晰。

调度理论专项（深入排程）
*   《Scheduling: Theory, Algorithms, and Systems》（Michael Pinedo）：调度领域的“圣经”。系统讲解确定性/随机调度模型、算法复杂度，以及约束编程在调度中的应用，附有大量工业案例。
*   《Introduction to the Mathematics of Planning and Scheduling》（Geza Bottlik）：直接针对“规划与排程”的数学入门，从变量、约束讲起，适合理解建模全貌。

约束编程与求解器底层（理解工具原理）
*   《Principles of Constraint Programming》（Krzysztof Apt）：约束编程领域的权威教材，系统讲解约束传播算法与搜索策略。读它你会更清楚 OptaPlanner 这类工具内部在做什么。

组合优化（进阶）
*   《Integer and Combinatorial Optimization》（Nemhauser & Wolsey）：整数规划与组合优化的经典著作，深入讲解调度、资源分配等问题的数学基础与算法。

### 学习路径建议

如果你是为了用好 OptaPlanner 或 OR-Tools，不必从头啃完所有运筹学。建议的路径是：先补整数规划的建模思想（理解如何把“不能相邻”写成约束），再读约束编程原理（理解求解器的工作方式），最后按需翻阅调度理论中的启发式部分，应对大规模问题。
