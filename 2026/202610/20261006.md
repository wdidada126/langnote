C++ 内存模型 / ABI / 汇编，static 最值得继续往下挖的其实是 .data/.bss/.rodata → ELF 符号表 → local/global symbol → internal/external linkage → static initialization → GLOBAL__sub_I→_cxa_guard`。这一条链能把“C++ 语言层的 static”一直打通到编译器、链接器和汇编层。

你这条链梳理得很准，基本就是从语言语义一路打到 ELF/链接器/运行时的完整路径。沿着它往下挖，可以把“static 到底是什么”拆成几个彼此独立、但经常被混在一起的问题。下面按你的链条逐段展开，顺带标出每段真正值得抠的细节和容易踩的坑。

## 1. `.data` / `.bss` / `.rodata`：存储期与可写性的落点

C++ 语言层说的是 storage duration（static / thread / automatic / dynamic）和 linkage，到了目标文件里就变成 section 的选择问题。

| 语言层 | 典型落点 | 条件 |
|---|---|---|
| `static int x = 42;` | `.data` | 有非零初值，可写 |
| `static int x;` / `static int x = 0;` | `.bss` | 零初始化，不占文件空间 |
| `static const int x = 42;` | 常被优化进 `.rodata`，也可能直接常量折叠 | 取决于是否 ODR-use |
| `const char* s = "abc";` | 指针在 `.data`，字面量在 `.rodata` | |
| `static constexpr` / `consteval` 结果 | 通常无存储，或 `.rodata` | 看是否取地址/ODR-use |

关键点：

- `.bss` 不是“没有初始化”，而是零初始化。C++ 里 `static int x;` 是 zero-initialization，然后才是 default-initialization（对 int 无操作）。`.bss` 的语义是“文件里不存，加载时清零”。
- `.rodata` 不等于 `const`。`const` 对象如果没被 ODR-use，可以完全不存在；反过来，字符串字面量、vtable、typeinfo 这些即使你没写 `const` 也在 `.rodata`。
- `static` 局部变量：如果带非平凡构造/析构，它不在 `.data`/`.bss` 里直接放对象本身，而是放一块对齐的原始存储（通常在 `.bss` 或 `.data`），再加一个 guard variable。这就是后面 `__cxa_guard` 的由来。

汇编层可以直接验证：

```cpp
int g = 1;            // .data
int z;                // .bss
const int c = 42;     // 可能 .rodata，也可能没有符号
void f(){ static int s = 7; }  // s 在 .data，guard 在 .bss
```

```asm
# gcc -S -O0
    .data
g:  .long 1
    .bss
z:  .zero 4
```

## 2. ELF 符号表：binding / type / visibility 是三个正交维度

ELF 符号表里跟 static 最相关的是 `st_info` 里的 binding 和 type，以及 `st_other` 里的 visibility。

- binding：`STB_LOCAL` / `STB_GLOBAL` / `STB_WEAK`
- type：`STT_OBJECT` / `STT_FUNC` / `STT_SECTION` / `STT_FILE` / `STT_TLS` / `STT_GNU_IFUNC`
- visibility：`STV_DEFAULT` / `STV_HIDDEN` / `STV_PROTECTED` / `STV_INTERNAL`

C++ 的 linkage 映射到 ELF 时：

| C++ linkage | ELF binding | 说明 |
|---|---|---|
| external linkage | `STB_GLOBAL` | 默认 |
| internal linkage（`static` 全局、匿名 namespace） | `STB_LOCAL` | 不参与动态链接 |
| `inline` / 模板 / 类内定义 | `STB_WEAK`（或 COMDAT） | 允许多个定义合并 |
| `__attribute__((visibility("hidden")))` | `STV_HIDDEN` | 仍是 GLOBAL，但不导出到动态符号表 |

这里最容易混的是：

- `static` 全局变量 = internal linkage，符号是 `LOCAL`，链接器不会拿它去满足其他编译单元的未定义引用。
- `static` 成员函数 没有 `this`，但它的 linkage 取决于类本身，不是 `static` 关键字决定的。类内定义的成员函数默认是 external，且常是 weak/COMDAT。
- 匿名 namespace 里的东西是 internal linkage，效果类似 `static`，但作用域规则更干净。

`readelf -s` 能直接看到：

```bash
readelf -s a.o | grep -E 'g|z|f'
# LOCAL  OBJECT  g?  -> 如果是 static int g;
# GLOBAL OBJECT  g?  -> 如果是 int g;
```

## 3. local / global symbol → internal / external linkage

这一段要区分两个层面：

1. C++ 语言层的 linkage（[basic.link]）：external / internal / no linkage。
2. ELF 符号层的 binding：LOCAL / GLOBAL / WEAK。

它们大体对应，但不是一一对应：

- `static` 全局 → internal linkage → `STB_LOCAL`
- 匿名 namespace → internal linkage → `STB_LOCAL`（名字还会被 mangling 成带 `_GLOBAL__N_1` 的形式）
- `const` 全局在 C++ 里默认 internal linkage（这点和 C 不同！）→ `STB_LOCAL`
- `inline` 函数 / 模板实例 → external linkage，但 `STB_WEAK` + COMDAT，靠链接器去重

一个常被忽略的点：`const` 全局变量在 C++ 里是 internal linkage，所以：

```cpp
// a.cpp
const int N = 10;   // internal linkage
// b.cpp
extern const int N; // 引用的是另一个 N？不一定，看定义
```

这也是为什么头文件里写 `const int N = 10;` 不会 multiple definition，但每个 TU 各有一份。

## 4. static initialization：从常量初始化到动态初始化

C++ 的静态存储期对象初始化分几档：

1. constant initialization：编译期完成，直接写进 `.data`/`.rodata`，无运行时开销。
2. zero initialization：`.bss`，加载时清零。
3. dynamic initialization：
   - 有序初始化（同一个 TU 内按定义顺序）
   - 无序初始化（不同 TU 之间顺序不确定）
   - C++17 起对部分情况有 sequenced-before 保证，但跨 TU 仍是老大难。

关键机制：

- 对于非局部的 dynamic initialization，编译器通常生成一个初始化函数，放进 `.init_array`，由 `__libc_csu_init` / `_init` 调用。
- 对于函数局部 static，C++11 起要求线程安全的懒初始化，于是有了 guard variable + `__cxa_guard_acquire/release/abort`。
- 对于非局部的 dynamic init，如果涉及跨 TU 依赖，标准只保证同一 TU 内有序，跨 TU 基本靠链接顺序，这是 static initialization order fiasco 的根源。

汇编层面：

```cpp
struct A { A(); ~A(); };
A g;   // 非局部，dynamic init
```

会看到：

```asm
_GLOBAL__sub_I_g:      # 初始化函数
    call A::A()
    ...
    .init_array:
    .quad _GLOBAL__sub_I_g
```

## 5. `GLOBAL__sub_I_*`：非局部 static 的初始化入口

`_GLOBAL__sub_I_<mangled>` 是 GCC/Clang 为某个 TU 的非局部静态对象初始化生成的函数，名字里的 `sub_I` 是 “sub-initializer” 的意思（历史上还有 `_GLOBAL__I_`、`_GLOBAL__D_` 等）。

要点：

- 每个 TU 里所有需要动态初始化的非局部对象，会被合并到少数几个 `_GLOBAL__sub_I_*` 函数里。
- 这些函数指针被放进 `.init_array`（ELF）或 `.ctors`（老式）。
- 析构对应 `_GLOBAL__sub_D_*`，放进 `.fini_array`。
- 调用顺序：`.init_array` 按链接顺序执行，所以跨 TU 的初始化顺序取决于链接顺序，标准不保证。

`objdump -d` 看：

```asm
0000000000000000 <_GLOBAL__sub_I_g>:
    push %rbp
    ...
    call A::A()
    ...
```

`readelf -x .init_array` 能看到函数指针。

## 6. `__cxa_guard_*`：函数局部 static 的线程安全懒初始化

函数局部 static 的初始化，C++11 起要求：

- 第一次控制流到达声明时初始化。
- 多线程并发到达时，只有一个线程执行初始化，其他线程等待。
- 初始化抛异常时，guard 要回滚，下次重新尝试。

实现机制（Itanium C++ ABI）：

```cpp
void f() {
    static X x;
}
```

大致生成：

```asm
f():
    movb guard(%rip), %al
    testb %al, %al
    jne .Ldone
    lea guard(%rip), %rdi
    call __cxa_guard_acquire
    testl %eax, %eax
    je .Ldone
    call X::X()
    lea guard(%rip), %rdi
    call __cxa_guard_release
.Ldone:
    ...
```

guard variable 是一个 8 字节（或更大）的对齐对象：

- 第一个字节：`已初始化` 标志。
- 后面：`正在初始化` 标志 / 线程 ID 等，用于处理递归和并发。

`__cxa_guard_acquire` 返回非零表示“我拿到了初始化权”，返回 0 表示“别人已经初始化完了”。如果构造抛异常，会调用 `__cxa_guard_abort` 释放 guard。

几个值得抠的点：

- `-fno-threadsafe-statics` 可以去掉这套机制，回到非线程安全版本。
- guard 的存储：通常在 `.bss`（零初始化），所以不占文件空间。
- 递归初始化：如果在 `X::X()` 里又进入同一个 static 的初始化，`__cxa_guard_acquire` 会死锁或抛异常，标准里是 UB / 未指定。
- 常量初始化优化：如果 `static X x;` 的构造是 constexpr 且满足条件，编译器可以把它变成 constant initialization，直接放 `.data`，完全省掉 guard。

汇编里能直接看到 `__cxa_guard_acquire` / `__cxa_guard_release` 的调用，以及那个 guard 符号（通常叫 `_ZGVZ1fvE1x` 之类，`GV` = guard variable）。


## 7. 把整条链串起来

用一个例子贯穿：

```cpp
// a.cpp
struct X { X(); ~X(); };
X g;                       // 非局部 dynamic init
void f() {
    static X x;            // 函数局部 dynamic init
}
static int s = 42;         // internal linkage, .data
static int z;              // internal linkage, .bss
const int c = 7;           // internal linkage, 可能 .rodata / 常量折叠
```

对应：

| 语言层 | 目标文件 | 运行时 |
|---|---|---|
| `g` | `.bss` 原始存储 + `_GLOBAL__sub_I_g` 在 `.init_array` | 启动时构造 |
| `f::x` | `.bss` 原始存储 + guard 变量 | 首次到达时 `__cxa_guard_acquire` |
| `s` | `.data`，`STB_LOCAL` | 无 |
| `z` | `.bss`，`STB_LOCAL` | 无 |
| `c` | 可能 `.rodata` 或无常量存储 | 无 |

链接器视角：

- `s`、`z`、`c` 是 LOCAL，不参与符号解析。
- `g` 如果是 `X g;`（非 static），是 GLOBAL，可能被其他 TU 引用。
- `_GLOBAL__sub_I_g` 通常是 LOCAL，但被 `.init_array` 引用。
- `f::x` 的 guard 是 LOCAL，名字经过 mangling。


## 8. 值得继续往下挖的方向

如果这条链还要再深：

1. COMDAT / weak symbol：inline 函数、模板、vtable 怎么去重，`.group` section 和 `SHF_GROUP` 的作用。
2. `-fno-common` / tentative definition：C 的 common symbol 和 C++ 的区别，`.bss` vs `COMMON`。
3. `__cxa_atexit`：非局部 static 析构怎么注册，和 `atexit` 的区别，`__dso_handle` 的作用。
4. `init_array` vs `ctors`：老式 `.ctors` 和新式 `.init_array` 的差别，链接器脚本怎么排布。
5. TLS：`thread_local` static 的 `STT_TLS`、`.tdata`/`.tbss`、`__tls_get_addr`。
6. visibility 与动态链接：`-fvisibility=hidden` 怎么影响 `STB_LOCAL`/`STV_HIDDEN`，以及 PLT/GOT。
7. 模块化 / C++20 modules：模块里的 static 和 linkage 有什么新规则。
8. 静态初始化顺序 fiasco：`constinit`、`std::call_once`、Meyers singleton 的取舍。


一句话总结你这条链：

> C++ 的 `static` 在语言层是 storage duration + linkage 的组合；落到 ELF 是 section + binding + visibility；再落到运行时是 `.init_array` / `_GLOBAL__sub_I_*` / `__cxa_guard_*` 三套机制分别处理非局部 dynamic init、函数局部 lazy init 和线程安全。

这条链打通之后，看 `readelf`、`objdump`、`nm` 的输出基本就能反推回源码里的 static 语义了。
