## 2. Kotlin 又提供了 Coroutine

现代 Kotlin 更重要的是：

```text
kotlinx.coroutines
```

[Kotlin Coroutines 官方文档](https://kotlinlang.org/docs/coroutines-overview.html?utm_source=chatgpt.com)

Coroutine 和 Thread 不是同一个层次。

```text
                  OS / CPU
                     │
                  Thread
                     │
        ┌────────────┴────────────┐
        │                         │
    JVM Thread Pool          JVM Thread Pool
        │                         │
   Coroutine                  Coroutine
   Coroutine                  Coroutine
   Coroutine                  Coroutine
   Coroutine                  ...
```

Coroutine 最终仍然需要在线程上执行。在 JVM 上，协程的并发代码底层运行在线程上；区别在于协程可以**挂起而不阻塞线程**，之后甚至可以在另一个线程恢复。[Kotlin](https://kotlinlang.org/docs/coroutines-basics.html?utm_source=chatgpt.com)

例如：

```kotlin
coroutineScope {
    launch {
        delay(1000)
        println("A")
    }

    launch {
        delay(1000)
        println("B")
    }
}
```

这里 `delay()` 不等价于：

```java
Thread.sleep()
```

前者挂起 coroutine，线程可以去执行其他 coroutine；后者直接把线程阻塞住。

# 3. Coroutine 能不能利用多个 CPU Core？

**能。**

例如：

```kotlin
withContext(Dispatchers.Default) {
    launch { cpuTask1() }
    launch { cpuTask2() }
    launch { cpuTask3() }
}
```

`Dispatchers.Default` 是多线程 dispatcher，因此多个 coroutine 可以真正并行执行，也就可以利用多个 CPU Core。官方也明确指出，多线程 dispatcher 下的 coroutine 会面对普通多线程一样的共享可变状态问题。[Kotlin](https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html?utm_source=chatgpt.com)

这点非常重要：

```text
Concurrency ≠ Parallelism

Coroutine
   │
   ├── 可以只是并发
   │
   └── 配合多线程 Dispatcher
           ↓
        可以并行
           ↓
        多 CPU Core
```

所以 **Coroutine 并不会神奇地消除 data race**。

# 4. Kotlin 如何解决 Data Race？

假设：

```kotlin
var counter = 0

repeat(1000) {
    launch(Dispatchers.Default) {
        counter++
    }
}
```

这是有问题的。

因为：

```text
counter++

≈

load counter
add  1
store counter
```

两个 CPU Core 可以发生：

```text
Core 0                  Core 1

load counter = 10
                        load counter = 10

add → 11
                        add → 11

store 11
                        store 11
```

最终应该 `12`，结果却是 `11`。

这和 Java/C++ 的 data race 本质完全一样。

# 6. 第二种：synchronized / ReentrantLock

Kotlin/JVM 同样可以：

```kotlin
val lock = ReentrantLock()

lock.lock()
try {
    counter++
} finally {
    lock.unlock()
}
```

或者 JVM monitor：

```kotlin
synchronized(lock) {
    counter++
}
```

所以：

```text
Kotlin/JVM
    ↓
JVM Memory Model
    ↓
happens-before
    ↓
monitor
volatile
CAS
Lock
Atomic
```

Java 并发理论依然非常重要。

# 7. Coroutine 自己还有 Mutex

Coroutine 世界更推荐：

```kotlin
val mutex = Mutex()

mutex.withLock {
    counter++
}
```

区别很关键：

```text
ReentrantLock.lock()
        ↓
线程等待
        ↓
Thread blocked


Mutex.lock()
        ↓
Coroutine suspend
        ↓
Thread 可以执行其他 coroutine
```

`kotlinx.coroutines.sync.Mutex` 是**非重入锁**；在 JVM 上，它的 unlock→后续成功 lock 也具有类似 `synchronized` 的 happens-before 内存语义。[Kotlin](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.sync/-mutex/?utm_source=chatgpt.com)

因此不要简单理解成：

> Mutex = Kotlin 版 ReentrantLock

它是面向 coroutine 的同步原语。

# 9. Kotlin 怎么避免死锁？

它**不能保证你不会写出死锁**。

例如：

```text
Coroutine A

lock A
   ↓
wait B


Coroutine B

lock B
   ↓
wait A
```

照样死锁。

Coroutine 解决的是很多传统“线程阻塞成本”的问题，**不是从理论上消灭 deadlock**。

仍然需要遵守：

```text
减少 shared mutable state
        ↓
尽量 immutable

必须共享
        ↓
Atomic / Mutex

多个锁
        ↓
固定 lock ordering

复杂协作
        ↓
Channel / message passing

任务生命周期
        ↓
Structured Concurrency

无限等待
        ↓
timeout / cancellation
```

这也是 Kotlin coroutine 比简单 `Thread + Lock` 更有意思的地方。

# 10. Channel：从“共享内存”转向“消息传递”

例如：

```kotlin
val channel = Channel<Int>()

launch {
    channel.send(100)
}

launch {
    val value = channel.receive()
}
```

思维从：

```text
Thread A ──┐
           ├── shared mutable state
Thread B ──┘
```

转变成：

```text
Coroutine A
     │
   message
     ↓
  Channel
     ↓
   message
     │
Coroutine B
```

这样能减少很多共享状态竞争。

这和 Go：

```go
channel
goroutine
```

在理念上有相似之处，不过实现和语言模型不要简单画等号。

# 11. 多核效率问题怎么解决？

Kotlin 给了 Dispatcher：

```text
Dispatchers.Default
        ↓
CPU-intensive
        ↓
多核并行


Dispatchers.IO
        ↓
blocking IO
        ↓
DB / File / legacy blocking API
```

官方把 `Dispatchers.IO` 定义为处理阻塞 IO 的共享线程池；还支持：

```kotlin
Dispatchers.IO.limitedParallelism(32)
```

来限制某类工作的并行度。[Kotlin](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-dispatchers/-i-o.html?utm_source=chatgpt.com)

例如：

```kotlin
val dbDispatcher =
    Dispatchers.IO.limitedParallelism(32)

withContext(dbDispatcher) {
    queryDatabase()
}
```

这就涉及非常重要的性能工程问题：

```text
CPU Core 数量
    ↓
Thread Pool size
    ↓
Coroutine parallelism
    ↓
Context Switching
    ↓
Cache Miss
    ↓
Lock Contention
    ↓
Throughput / Latency
```

所以 coroutine **不是越多越快**。

## 1. 最大区别：类型到底是不是“真的”

这是理解 Rust vs TS 最重要的一点。

Rust：

```rust
struct User {
    id: u64,
    active: bool,
}
```

这个类型会实际影响：

```text
源代码
   ↓
Rust type checking
   ↓
内存布局
   ↓
LLVM IR
   ↓
机器码
```

编译器必须考虑 `u64`、`bool`、alignment、ownership、drop 等问题。

TypeScript：

```typescript
interface User {
    id: number;
    active: boolean;
}
```

编译后大体只剩：

```javascript
const user = {
    id: 1,
    active: true
};
```

`User` 消失了。

所以：

```text
TypeScript type system
        │
        ├── 编译期：非常强
        │
        └── runtime：基本不存在
```

这是 TS 很多“奇怪特性”的根源。

# 2. Nominal vs Structural Typing

这是两门语言非常值得比较的地方。

TypeScript：

```typescript
interface A {
    x: number;
}

interface B {
    x: number;
}

let a: A = { x: 1 };
let b: B = a;
```

没问题。

因为 TS 主要看：

> 你长什么样。

也就是 structural typing。

Rust：

```rust
struct A {
    x: i32,
}

struct B {
    x: i32,
}
```

即使字段完全相同：

```rust
let a = A { x: 1 };

let b: B = a; // error
```

`A` 和 `B` 仍然是不同类型。

Rust 更接近：

> 你到底是什么类型。

这也是为什么 TS 特别适合描述 JavaScript 世界已有的各种对象结构。

# 3. Rust `enum` vs TS Union

两者其实有很有意思的对应关系。

Rust：

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

TS 可以写：

```typescript
type Result<T, E> =
    | { type: "ok"; value: T }
    | { type: "error"; error: E };
```

然后：

```typescript
function handle(result: Result<number, string>) {
    if (result.type === "ok") {
        console.log(result.value);
    } else {
        console.log(result.error);
    }
}
```

这里 TS 的：

```text
Union Type
+
Literal Type
+
Discriminated Union
+
Control Flow Narrowing
```

组合起来，能实现类似 Rust enum 的很多建模效果。

但 Rust `enum` 是真正的运行时数据类型；TS union 是编译期类型描述。

# 4. Rust match vs TS Narrowing

Rust：

```rust
match value {
    Some(x) => println!("{x}"),
    None => println!("none"),
}
```

这是语言级 pattern matching。

TS：


```text
  ↓

```

# 6. TS 有一套 Rust 很少直接对应的“类型变换语言”

# 1. CompletableFuture：我要等“一个未来结果”

先从 Java 最容易理解的开始。

传统同步：

```java
User user = loadUser();
Order order = loadOrder(user);
Result result = calculate(order);
```

问题是：

```text
Thread
 │
 ├─ loadUser()
 │     │
 │     └──── 等网络/DB ─────┐
 │                          │
 │       Thread blocked     │
 │                          │
 │◀─────────────────────────┘
 │
 └─ continue
```

于是 Java 8 有：

```java
CompletableFuture<User> future =
    CompletableFuture.supplyAsync(() -> loadUser());
```

然后：

```java
future
    .thenApply(this::loadOrder)
    .thenApply(this::calculate)
    .thenAccept(System.out::println);
```

它表达：

```text
现在
 │
 └──── Future ─────────────────→ 将来
                                  │
                                  ▼
                                User
```

所以：

```text
CompletableFuture<T>

本质：
Future value

数量：
0..1
```

它特别适合：

```text
HTTP 请求 → 一个 Response
DB 查询   → 一个结果
RPC       → 一个 Response
两个异步任务并行 → 合并结果
```

例如：

```java
var user = loadUserAsync();
var orders = loadOrdersAsync();

user.thenCombine(orders, UserOrders::new);
```

### 它不擅长什么？

假设服务器不断产生：

```text
event1
event2
event3
...
event1000000
...
```

你总不能优雅地表达：

```text
CompletableFuture<T>
CompletableFuture<T>
CompletableFuture<T>
CompletableFuture<T>
...
```

所以：

> `CompletableFuture<T>` 更像异步世界里的一个 `T`，而不是 `List<T>` / Stream。

# 2. Reactive Streams：我要解决“无限异步数据流”

现在需求变成：

```text
Kafka
 │
 ├─ message
 ├─ message
 ├─ message
 ├─ message
 ├─ ...
 │
 ▼
Consumer
```

它不是：

```text
未来产生一个 T
```

而是：

```text
未来不断产生 T

T T T T T T T T ...
```

于是需要：

```text
Publisher<T>
```

但是马上产生一个严重问题：

```text
Producer
100,000/s
     │
     ▼
Consumer
10,000/s
```

怎么办？

这就是 **Backpressure**。

Reactive Streams 的关键协议：

```text
Publisher
    ▲
    │ request(10)
    │
Subscriber
```

Subscriber 告诉上游：

> 我现在能接收 10 个。

Publisher：

```text
request(10)

    ↓

onNext(1)
onNext(2)
...
onNext(10)

    ↓

暂停等待更多 demand
```

所以 Reactive Streams 最重要的不是：

> “Reactive 写起来比较酷。”

而是：

> **定义异步 Stream 的标准 Publisher/Subscriber/Subscription + Demand/Backpressure 协议。**

# 3. Reactor Flux/Mono：把 Reactive Streams 变成真正可编程的库

Reactive Streams 本身更接近**规范/协议**。

如果直接操作：

```java
Publisher
Subscriber
Subscription
```

太底层。

于是 Project Reactor 给你：

```java
Mono<T>
Flux<T>
```

可以粗略记：

```text
Mono<T>
   ↓
0..1 个 T


Flux<T>
   ↓
0..N 个 T
```

例如：

```java
Mono<User> user =
    userRepository.findById(id);
```

然后：

```java
user
    .map(this::convert)
    .flatMap(this::save)
    .subscribe();
```

Flux：

```java
Flux<Order> orders =
    repository.findAll();
```

然后：

```java
orders
    .filter(Order::isValid)
    .map(this::calculate)
    .flatMap(this::save)
    .subscribe();
```

因此关系是：

```text
Reactive Streams
       │
       │ specification
       ↓
Publisher / Subscriber
Subscription / Backpressure
       │
       │ implementation / programming model
       ↓
Project Reactor
       │
    ┌──┴──┐
    │     │
  Mono   Flux
  0..1   0..N
```

因此不要说：

> Reactive Streams = Flux。

应该说：

> Reactor 的 `Flux`/`Mono` 建立在 Reactive Streams 模型之上。

# 4. Kotlin suspend：它根本不是 Stream

这是最容易混淆的地方。

```kotlin
suspend fun loadUser(): User
```

不要理解成：

```text
suspend = Reactive
```

它解决的问题是：

> **一个函数需要等待异步操作时，能不能挂起 coroutine，而不是阻塞 Thread？**

例如：

```kotlin
suspend fun getUser(): User {
    delay(1000)
    return User()
}
```

逻辑上你写的是：

```text
A
↓
delay
↓
B
```

但运行过程可能是：

```text
Thread-1

A
│
▼
suspend
│
└──────── coroutine 挂起
             │
Thread-1     │
去干其他事   │
             │
      一秒之后完成
             │
             ▼
          resume
             │
             ▼
          Thread-2
             │
             B
```

所以：

> **suspend 的核心价值是把异步程序重新写成类似同步的顺序代码。**

这和 Reactive 的思维区别非常明显。

### Reactor

```java
loadUser()
    .flatMap(this::loadOrders)
    .flatMap(this::calculate)
    .flatMap(this::save)
    .subscribe();
```

### Coroutine

```kotlin
val user = loadUser()
val orders = loadOrders(user)
val result = calculate(orders)
save(result)
```

函数都是：

```kotlin
suspend fun
```

代码看起来同步：

```text
A
↓
B
↓
C
↓
D
```

执行却可以是非阻塞异步的。

这就是 coroutine 很大的价值。

# 5. `suspend fun(): T` 和 CompletableFuture 很像，但不完全一样

建立一个非常有用的对应关系：

```text
Java                         Kotlin

CompletableFuture<T>         suspend fun(): T
```

两者经常解决类似需求：

> **异步计算，最终得到一个 T。**

Java：

```java
CompletableFuture<User> loadUser()
```

Kotlin：

```kotlin
suspend fun loadUser(): User
```

调用体验差异很明显。

Java：

```java
loadUser()
    .thenCompose(this::loadOrders)
    .thenCompose(this::save);
```

Kotlin：

```kotlin
val user = loadUser()
val orders = loadOrders(user)
save(orders)
```

因此可以粗略理解：

```text
CompletableFuture<T>
       ≈
异步世界里的 T 容器


suspend fun(): T
       ≈
可以挂起的函数，
恢复后直接得到 T
```

注意：`suspend` **不是自动切线程，也不等于异步启动任务**。

# 7. Flow 和 Flux 最值得比较

现在终于来到两套体系真正对应的位置：

```text

                               （粗略对应）

Flux<T>                         Flow<T>
```

例如 Reactor：

```java
Flux.range(1, 100)
    .filter(x -> x % 2 == 0)
    .map(x -> x * 10)
```

Kotlin：

```kotlin
(1..100)
    .asFlow()
    .filter { it % 2 == 0 }
    .map { it * 10 }
    .collect { println(it) }
```

表面非常相似：

```text

  ↓
filter
  ↓
map
  ↓
flatMap
  ↓
consumer
```

但内部模型不完全一样。

Reactor 的核心世界观：

```text

Subscriber
Subscription
request(n)
Backpressure
```

Kotlin Flow 的核心世界观：

```text
Coroutine
suspend
emit()
collect()
structured concurrency
```

# 8. Flow 的背压非常有意思

考虑：

```kotlin
flow {
    for (i in 1..1000) {
        emit(i)
    }
}.collect {
    slowProcess(it)
}
```

可以粗略理解：

```text
Producer

emit(1)
   │
   ▼
Consumer
slowProcess(1)
   │
   ▼
完成
   │
   ▼
emit(2)
```

如果 downstream 很慢，`emit()` 可以挂起。

于是：

```text
Producer
   │
 emit()
   │
   ▼
Consumer 太慢
   │
   ▼
Coroutine suspend

而不是：
Thread blocked
```

所以 Flow 可以天然利用 coroutine suspension 实现流量协调。

这和 Reactive Streams 显式：

```java
subscription.request(n)
```

的模型不同。

# 9. Channel 又是什么？

很多人会把：

```text
Channel
Flow
```

混在一起。

最简单的区别：

> **Flow 主要是“数据流抽象”；Channel 主要是“协程之间通信”。**

Channel 很像：

```text
BlockingQueue
```

但面向 coroutine。

传统 Java：

```java
BlockingQueue<Task> queue =
    new ArrayBlockingQueue<>(100);
```

Producer：

```java
queue.put(task);
```

Consumer：

```java
Task task = queue.take();
```

问题：

```text
put / take

可能阻塞 Thread
```

Kotlin：

```kotlin
val channel = Channel<Task>(100)
```

Producer：

```kotlin
channel.send(task)
```

Consumer：

```kotlin
val task = channel.receive()
```

如果 Channel 满：

```text
send()
  ↓
suspend coroutine

不是

block thread
```

所以可以粗略记：

```text
Java BlockingQueue
       │
       │ coroutine version
       ▼
Kotlin Channel
```

虽然两者语义不能完全画等号。

# 10. Channel 与 Flow 的根本区别

假设：

```kotlin
val flow = flow {
    println("start")
    emit(1)
    emit(2)
}
```

没有：

```kotlin
collect()
```

通常不会执行。

因为普通 Flow 默认是 **cold stream**：

```text
Flow
 │
 │ collect()
 ▼
开始生产
```

第二个 collector：

```text
Collector A
    │
    ▼
重新执行 Flow


Collector B
    │
    ▼
重新执行 Flow
```

而 Channel 更像：

```text
Producer
    │
    │ send()
    ▼
┌────────────┐
│  Channel   │
└────────────┘
    │
    │ receive()
    ▼
Consumer
```

它是一个通信机制。

所以：

```text
Flow
≈ stream abstraction

Channel
≈ coroutine communication primitive
```

# 12. 六者放进同一张表

| 技术 | 主要解决什么 | 数据数量 | 背压/流控 | 核心抽象 |
|---|---|---:|---|---|
| `CompletableFuture<T>` | 一个未来异步结果 | 0..1 | 不是核心 | Future |
| Reactive Streams | 异步数据流标准协议 | 0..N | **核心** | Publisher/Subscriber |
| `Mono<T>` | Reactor 单值流 | 0..1 | 支持 | Publisher |
| `Flux<T>` | Reactor 多值流 | 0..N | **支持** | Publisher |
| `suspend fun(): T` | 挂起式异步函数 | 通常一个返回值 | 不属于 Stream 背压模型 | Continuation |
| `Flow<T>` | 协程异步数据流 | 0..N | suspension-based | Flow |
| `Channel<T>` | 协程通信 | 0..N | capacity + suspension | Channel |

这里其实是 **六类概念，但 `Flux/Mono` 包含两个类型**。

# 14. 最后把它和你之前学的 JUC 串起来

从软件工程师知识体系看，我建议你建立成下面这棵树：

```text
                     JVM Concurrency
                           │
         ┌─────────────────┼─────────────────┐
         │                 │                 │
      Thread            Async             Stream
         │                 │                 │
        JUC        CompletableFuture   Reactive Streams
         │                                   │
 ┌───────┼────────┐                    Reactor
 │       │        │                   ┌───┴───┐
Lock   Atomic   Executor             Mono    Flux
 │
 │
 └──────────────── JVM Memory Model
                  happens-before
                  volatile
                  CAS


                    Kotlin
                       │
                  Coroutine
                       │
        ┌──────────────┼──────────────┐
        │              │              │
     suspend         Channel         Flow
        │              │              │
   async function   communication   async stream
        │
    Continuation
        │
   state machine
        │
   Dispatcher
        │
     JVM Thread
        │
       CPU
```

**最值得注意的一条分界线是：**

```text
CompletableFuture / suspend
            ↓
      “一个异步计算”


Reactive Streams / Flux / Flow
            ↓
      “一串异步数据”


BlockingQueue / Channel
            ↓
      “并发执行单元之间通信”
```

而 **Reactive Streams 又比 `Flux` 高一个抽象层级**：前者首先是一套协议，后者是这套响应式思想在 Reactor 中真正给程序员使用的类型和 operator 体系。

如果继续往底层学，下一层最有价值的是把 **`suspend` 编译后的 JVM 字节码/Continuation 状态机、Reactor 的 `request(n)` 调用链，以及 Flow 的 `emit()` 为什么能够 suspend** 放在一起拆。这样就会从“会用异步 API”进入“理解 JVM 异步运行时实现”的层次。
