# 经典并发问题全景清单（Concurrency Problem Catalog）

从软件工程、操作系统、JVM、Linux 内核、数据库、网络编程和分布式系统的角度，可以把\*\*惊群效应（Thundering Herd）、上下文切换（Context Switch）\*\*等经典问题整理成以下 18 大类。

这里不仅包括并发正确性问题，还包括并发性能、资源竞争、调度、异步、网络和分布式系统问题。

## 一、经典并发问题分类总览

| 分类            | 典型问题                                           | 主要关注    |
| ------------- | ---------------------------------------------- | ------- |
| 01. 竞态与原子性    | Race Condition、Data Race、TOCTOU                | 正确性     |
| 02. 可见性与内存模型  | Visibility、Reordering、Publication              | 正确性     |
| 03. 锁与死锁      | Deadlock、Livelock、Lock Convoy                  | 正确性、性能  |
| 04. 线程调度      | Context Switch、Starvation、Priority Inversion   | 调度      |
| 05. 唤醒与等待     | Thundering Herd、Lost Wakeup、Spurious Wakeup    | 调度、同步   |
| 06. CPU 缓存与硬件 | False Sharing、Cache Line Ping-Pong             | 性能      |
| 07. 原子操作与无锁算法 | ABA、CAS Contention、Reclamation                 | 正确性、性能  |
| 08. 线程池与任务调度  | Thread Pool Exhaustion、Queue Saturation        | 吞吐、延迟   |
| 09. 异步与事件循环   | Event Loop Blocking、Callback Hell              | 响应性     |

## 二、详细问题列表

### 01. 竞态条件与原子性（Race & Atomicity）

| 问题       | 英文名称                                | 典型表现                |
| -------- | ----------------------------------- | ------------------- |
| 竞态条件     | Race Condition                      | 执行结果依赖线程执行顺序        |
| 数据竞争     | Data Race                           | 无适当同步的冲突内存访问        |
| 丢失更新     | Lost Update                         | 多线程更新覆盖彼此结果         |
| 检查与使用竞争  | TOCTOU                              | 检查条件后状态发生变化         |
| 复合操作非原子  | Check-Then-Act                      | `if` 判断和后续操作被其他线程插入 |
| 读改写竞争    | Read-Modify-Write Race              | `count++` 丢失更新      |
| 双重检查锁定错误 | Broken Double-Checked Locking       | 对象未安全发布             |
| 不安全发布    | Unsafe Publication                  | 其他线程观察到未正确初始化的状态    |
| 部分初始化暴露  | Partially Constructed Object Escape | 构造期间 `this` 逸出      |
| 多对象一致性破坏 | Inconsistent Snapshot               | 读取到不属于同一时刻的数据       |

### 02. 内存可见性与重排序（Memory Model）

- Visibility Problem：内存可见性问题
- Instruction Reordering：指令重排序
- Store Buffering：存储缓冲导致的可见性差异
- Load Buffering：加载缓冲相关的内存序现象
- Memory Ordering Violation：内存顺序约束违反
- Missing Happens-Before：缺失先行发生关系
- Stale Read：读取陈旧数据
- Unsafe Publication：不安全发布
- Out-of-Thin-Air Read：凭空值问题（内存模型理论）
- Incorrect Memory Fence：内存屏障使用错误
- Relaxed Atomic Misuse：宽松原子内存序误用

重点研究 Java Memory Model、C++ Memory Model、CPU TSO/弱内存模型。

### 03. 锁竞争与死锁（Locking）

- Deadlock：死锁
- Livelock：活锁
- Starvation：饥饿
- Lock Contention：锁竞争
- Lock Convoy：锁护送效应
- Lock Granularity Problem：锁粒度不合理
- Lock Ordering Violation：锁顺序不一致
- Recursive Locking Deadlock：递归加锁导致死锁
- Reader-Writer Starvation：读写锁饥饿
- Writer Preference Starvation：写优先策略下的读者饥饿
- Lock Upgrade Deadlock：读锁升级死锁
- Nested Lock Deadlock：嵌套锁死锁
- Oversynchronization：过度同步
- Under-Synchronization：同步不足
- Long Critical Section：临界区过长
- Blocking While Holding Lock：持锁执行阻塞操作

### 04. 线程调度与上下文切换（Scheduling）

| 问题        | 英文                      | 原因              |
| --------- | ----------------------- | --------------- |
| 上下文切换开销   | Context Switch Overhead | 线程频繁切换          |
| 线程过度订阅    | CPU Oversubscription    | 可运行线程远超 CPU 核数  |
| 优先级反转     | Priority Inversion      | 高优先级线程等待低优先级线程  |
| 优先级饥饿     | Priority Starvation     | 低优先级任务长期无法运行    |
| 调度器抖动     | Scheduler Jitter        | 执行时间不稳定         |
| 线程迁移      | CPU Migration           | 线程在不同 CPU 间迁移   |
| CPU 亲和性问题 | CPU Affinity Issue      | 绑定策略不合理         |
| NUMA 远程访问 | Remote NUMA Access      | 访问远端节点内存        |
| 过度抢占      | Excessive Preemption    | 频繁被抢占           |
| 自旋浪费      | Busy-Wait Overhead      | 空转消耗 CPU        |

### 05. 惊群与线程唤醒（Wakeup & Waiting）

这是 Linux、Java 并发和高性能网络编程中非常值得重点研究的一类。

| 问题     | 英文                        | 典型场景             |
| ------ | ------------------------- | ---------------- |
| 惊群效应   | Thundering Herd           | 大量线程被同一事件唤醒      |
| 丢失唤醒   | Lost Wakeup               | 通知发生但等待方错过       |
| 虚假唤醒   | Spurious Wakeup           | 条件未满足却从等待中返回     |
| 过度唤醒   | Excessive Wakeup          | `notifyAll` 使用不当 |
| 无效唤醒   | Futile Wakeup             | 被唤醒后发现无工作可做      |
| 唤醒竞争   | Wakeup Contention         | 大量线程竞争同一资源       |
| 等待队列竞争 | Wait Queue Contention     | 多线程竞争等待队列        |
| 信号量竞争  | Semaphore Contention      | 大量线程争夺 permit    |
| 条件变量误用 | Condition Variable Misuse | 未使用条件循环检查        |
| 唤醒延迟   | Wakeup Latency            | 通知到真正执行间隔过长      |

值得比较：

`select` / `poll` / `epoll`、`EPOLLEXCLUSIVE`、`SO_REUSEPORT`、Java `wait/notify`、`Condition.signal/signalAll`。

## 四、进一步建立知识体系

建议不要仅按照问题名称学习，而是建立下面这条因果链：

硬件层

CPU Cache · MESI · NUMA · Memory Ordering

操作系统层

线程调度 · Futex · Epoll · Context Switch

语言与运行时层

JMM · CAS · Locks · Thread Pool · Coroutine

框架与中间件层

Netty · Reactor · Kafka · Redis · Database

分布式系统层

Retry Storm · Cache Stampede · Cascading Failure

每个问题统一采用六个研究维度：

1. 定义与触发条件：什么情况下发生？
2. 底层机制：CPU、内核、语言运行时如何导致它？
3. 最小复现：编写可以直接运行的演示代码。
4. 可观测指标：如何用 JFR、`perf`、JMH、eBPF、线程转储证明？
5. 解决方案：同步策略、算法、架构如何改进？
6. 工程案例：JDK、Linux、Netty、Redis、MySQL、ShardingSphere 等源码如何处理？

尤其建议把 惊群效应、上下文切换、锁护送、伪共享、CAS 重试风暴、线程池饥饿、背压失效、重试风暴 放在同一条性能问题研究主线上：它们分别发生在不同层次，却可能通过资源竞争、唤醒放大和排队形成相似的吞吐下降与尾延迟恶化现象。

这份清单适合作为 `并发与异步知识体系` 的问题索引，后续可以扩展成 200+ 经典并发问题 → 原理 → Java/C++/Go 复现代码 → 观测工具 → 源码案例 → 解决方案 的系统化学习项目。

# 经典并发问题研究体系：论文、书籍与工业界中间件实现（截至 2026 年 10 月）

这份资料按照软件工程师 → 并发运行时 → 操作系统 → 中间件内核 → 分布式系统的研究路线组织。

重点不只是掌握 `synchronized`、CAS、线程池等 API，而是回答三个更深入的问题：

1. 学术界如何定义和解决经典并发问题？ 例如惊群、锁护送、ABA、伪共享、优先级反转、无锁内存回收。
2. 工业界如何实现这些解决方案？ 例如 Linux、JDK、Netty、Redis、Kafka、MySQL、PostgreSQL、RocksDB、Flink。
3. 如何通过源码、实验和性能分析验证？ 例如使用 JMH、JCStress、JFR、perf、eBPF、Jepsen。

需要特别区分：并发正确性、并发性能和分布式一致性。三者相互关联，但论文的证明方法、系统的实现机制和测试手段并不相同。

### 1. Linux：惊群、上下文切换与锁竞争

核心机制

- EPOLLEXCLUSIVE：减少多个 epoll 实例对同一 fd 的无效唤醒。
- Futex：用户态快速路径与内核等待队列结合，避免无竞争锁操作每次都进入内核。
- Priority Inheritance：缓解特定锁场景的优先级反转。
- RCU：通过延迟回收等机制改善读多写少场景的扩展性。
- Per-CPU Data：减少共享计数器和全局锁竞争。

源码入口

- fs/eventpoll.c
- kernel/futex/
- kernel/rcu/
- kernel/sched/

源码阅读应从具体的内核 tag 开始，因为 `master` 会不断变化。EPOLLEXCLUSIVE 的适用范围与限制应以 `epoll_ctl(2)` 文档为准。

Flink 的经典问题是：下游慢算子使上游网络缓冲积压，进而导致 Checkpoint Barrier 传播缓慢。

Flink 提供 Buffer Debloating、Unaligned Checkpoint 等机制。Unaligned Checkpoint 允许 Barrier 越过缓冲中的数据，但需要把在途数据纳入检查点，带来额外状态 I/O。

## 六、推荐优先研究的方向

如果以理解软件底层机制、提高故障诊断能力和中间件源码研发能力为目标，我建议采用以下顺序：

1. 内存与并发：解释大量难复现、低层次正确性问题。
2. CPU、操作系统与 I/O：解释性能抖动、上下文切换、资源竞争。
3. 网络与数据库：解释大部分服务端性能和正确性问题。
4. 缓存、消息队列、分布式系统：解释高并发业务与多节点故障。
5. 编译器、ABI、语言运行时：解释跨平台、跨语言和运行时问题。
6. 测试、可观测性、构建与安全：建立系统化的故障发现、复现和修复能力。

最终可以形成一个覆盖 24 个一级领域、100+ 二级专题、500+ 经典软件问题的研究体系。这里的 500+ 是建议的建设规模，并非本次已经完整列举的数量。

最重要的是区分三类内容：经典故障现象（如死锁、OOM）、根本机制（如内存模型、队列论）和工程设计权衡（如吞吐与延迟、强一致性与可用性）。这样建立的问题索引才不会变成单纯的术语堆积，而能真正用于源码分析和排障。
