### 论文阅读 + 代码复现推荐流程（分布式存储偏工程向）

1. 选论文优先级  
   - 有官方/完整代码 > 有社区实现 > 只有伪代码/算法描述  
   - 优先：Erasure Code 修复优化、元数据扩展性、读写分离/链式复制、跨数据中心一致性  
   - 参考来源：PapersWithCode、USENIX FAST/OSDI、EuroSys、SOSP、ATC、arXiv trending

2. 阅读节奏建议（1篇 5–10 天）  
   - Day 1–2：Abstract + Intro + Conclusion + 图表（了解痛点 & 贡献）  
   - Day 3–5：System Design / Architecture（画出组件图、数据流、元数据布局、故障模型）  
   - Day 6–8：算法细节（Erasure Code构造、repair bandwidth、placement、consistency）  
   - Day 9+：Experiments & Appendix（看真实trace、瓶颈分析、trade-off）
3. 复现准备（最难的部分）  
   - 环境：多机（至少 3–9 台，推荐 5+），Ubuntu 20.04/22.04，ceph/rocksdb/leveldb 等依赖  
   - 工具：Docker / Minikube / kind（小规模测试），真实多机用 Ansible / Terraform  
   - 硬件：SSD/NVMe 优先，网络 10G+（修复带宽敏感）  
   - 常见依赖：Go/Rust/C++/Python，gflags/glog/protobuf/rocksdb/libfuse 等
4. 复现路径（从小到大）  
   - 先跑 paper 中的 micro-benchmark（put/get/repair latency/throughput）  
   - 再跑 YCSB / fio / cosbench / mdtest 等标准负载  
   - 最后注入故障（kill node、网络分区、慢盘）测修复时间 & 带宽  
   - 记录：修复带宽、重建时间、尾延迟、元数据规模 vs. 节点数
5. 高频坑 & 解法  
   - Erasure Code 矩阵计算慢 → 用 GF-complete / isa-l / jerasure 库  
   - 修复流量爆炸 → 检查 placement 是否 rack-aware / node-aware  
   - 元数据瓶颈 → 验证是否有分布式元数据（如 etcd/CRDB）  
   - 一致性问题 → 用 Jepsen 测试线性一致性

最推荐复现顺序（2025–2026 性价比）：
1. CubeFS → 完整云原生分布式文件系统，最接近工业级
2. JuiceFS / SeaweedFS → POSIX 接口 + Redis/数据库元数据，易上手
3. CRAQ (Go 版) → 理解链式复制 + apportioned read 经典机制
4. Ceph EC 插件 + 自适应 repair 思路 → 基于现有系统加论文优化
5. 如果有兴趣做 Erasure Code，从 jerasure / isa-l 开始写 toy EC 修复模拟器

如果你硬件有限（< 5 台机器），优先从 CRAQ、SeaweedFS 单机多进程、JuiceFS 本地模式 开始。

### 论文阅读 + 代码复现的推荐完整流程（2025–2026适用）

1. 选论文（优先级排序）  
   - 看Papers with Code trending / leaderboard  
   - 看dair-ai/ML-Papers-of-the-Week 每周精选  
   - 看HuggingFace Papers Trending  
   - 看Reddit r/MachineLearning 年度/月度讨论  
   - 优先选择：有官方代码 + star数高 + 最近1年内更新活跃 的论文

2. 阅读阶段（建议3–7天/篇）  
   - 先读 Abstract + Introduction + Conclusion（10分钟）  
   - 再读 Method 部分，画出架构图（核心！）  
   - 看 Experiments 表格，记住关键指标和数据集  
   - 最后看 Related Work 和 Appendix（很多trick藏在附录）

3. 环境准备（最耗时的一步）  
   - 用 conda 或 uv/uvic 创建干净环境（python 3.10/3.11/3.12）  
   - 优先安装官方 requirements.txt  
   - 常见依赖冲突解决：torch 版本、flash-attn、apex、deepspeed、vllm、triton 等  
   - GPU：至少 1张 24GB（A100/4090/5090），多卡建议用 deepspeed/FSdp

4. 代码复现路径（从小到大）  
   - 先跑官方提供的 demo / example / notebook  
   - 复现 Table 1 / Figure 3 最核心的结果（通常是最容易的）  
   - 逐步增加 scale：bs → 模型尺寸 → 数据量  
   - 记录每一次的 超参、seed、硬件、时间、指标（非常重要！）

5. 常见卡点 & 解决  
   - 数值不match → 检查 fp16/bf16/TF32、random seed、数据预处理  
   - OOM → 减小 batch / 用 gradient checkpointing / zero-3 / QLoRA  
   - 速度慢 → flash-attn 2、torch.compile、vllm、triton kernel  
   - loss爆炸 → 学习率太高、warmup太短、梯度裁剪、weight decay

6. 记录与输出  
   - 用 Notion / markdown 写复现报告（架构图 + 超参表 + 曲线对比）  
   - 上传到自己的 GitHub（别人会 star & fork）  
   - 写成博客 / X 推文 / B站视频，收获反馈

根据 Rust 的官方设计，edition 和 rustc/cargo 版本 是两个独立但相关的概念。以下是它们关系的详细说明：

1. 核心关系概述

维度 Edition Rustc/Cargo 版本

本质 语言特性集合 工具链版本

作用 定义可用的语法和特性 提供编译器和包管理功能

更新频率 每3年一个大版本 每6周一个小版本

兼容性 向前兼容，不破坏现有代码 通常向前兼容

2. 具体关系说明

2.1 Edition 是 Rustc 版本的子集

# 查看 Rust 版本
rustc --version
# 输出示例: rustc 1.78.0 (9b00956e5 2024-05-27)
#                     ^^^^^^
#                     工具链版本

# 查看项目使用的 Edition
cat Cargo.toml
# 输出示例: edition = "2021"


关键点：一个 Rust 工具链版本（如 1.78.0）可以支持多个 Edition（2015、2018、2021，可能还有 2024 预览版）。

2.2 版本对应关系

通常，新版 Rust 工具链向后兼容所有已发布的 Edition：

Rust 版本范围 支持的 Edition

1.0-1.30 (2015-2018) 仅 2015

1.31-1.55 (2018-2021) 2015, 2018

1.56.0+ (2021至今) 2015, 2018, 2021

Nightly 版本 2015, 2018, 2021, 2024(预览)

2.3 实际示例

# 使用 Rust 1.78.0 (稳定版)
$ rustc --version
rustc 1.78.0 (9b00956e5 2024-05-27)

# 可以编译以下任何 Edition 的项目
# Cargo.toml 中可以设置:
# edition = "2015"  ✓ 支持
# edition = "2018"  ✓ 支持  
# edition = "2021"  ✓ 支持
# edition = "2024"  ✗ 不支持（需要 Nightly）


3. 工作原理

3.1 编译时的 Edition 处理

当使用 cargo build 时：
# 假设 Cargo.toml 中: edition = "2021"

cargo build
# 编译器 (rustc 1.78.0) 会:
# 1. 识别 edition = "2021"
# 2. 启用 2021 Edition 的所有特性
# 3. 应用 2021 Edition 的语法规则
# 4. 生成二进制文件


3.2 多 Edition 的依赖兼容

不同 Edition 的 crate 可以互相依赖：
# 项目 A: 使用 edition = "2021"
[package]
name = "project_a"
edition = "2021"

[dependencies]
# 可以依赖使用 edition = "2015" 的库
old_lib = "1.0"  # edition = "2015"

# 也可以依赖使用 edition = "2018" 的库  
newer_lib = "2.0"  # edition = "2018"


4. 迁移与升级

4.1 独立升级

你可以单独升级 Edition 或 Rust 版本：
# 情况1: 只升级 Rust 版本
rustup update stable  # 1.77 → 1.78
# edition 保持不变: "2021"

# 情况2: 只升级 Edition
# 修改 Cargo.toml: edition = "2018" → "2021"
# Rust 版本保持不变: 1.78.0


4.3 升级路径建议


时间线:    2021        2023        2025
Edition:  "2021" ────→ "2021" ────→ "2024"(预计)
Rust版本:  1.56 ────→ 1.68 ────→ 最新稳定版
           │          │          │
           ├──────────┼──────────┼──── 可以一直使用 2021 Edition
           │          │          │
           └──────────┴──────────┴──── 需要时再升级到 2024 Edition


6. 总结

1. edition 是语言特性的集合，定义了可用的语法
2. rustc/cargo 版本是工具链版本，提供编译和执行能力
3. 新版 Rust 工具链支持所有旧 Edition
4. 可以单独升级 Edition 或 Rust 版本
5. 不同 Edition 的 crate 可以相互依赖
6. 生产项目建议：最新稳定 Rust + 2021 Edition

简单比喻：
• Rust 版本像是汽车的发动机版本（性能、功能）

• Edition 像是汽车的驾驶模式（运动模式、经济模式）

你可以用新款发动机（Rust 1.78）开老驾驶模式（edition 2015），也可以用老发动机（Rust 1.56）开新驾驶模式（edition 2021，但有限制）。最佳搭配是新发动机配新驾驶模式（最新 Rust + 2021 Edition）。
