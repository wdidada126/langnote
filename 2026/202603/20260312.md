WebRTC简介
WebRTC是一种开放标准，允许网络应用或站点在不借助中间媒介的情况下，建立浏览器之间的点对点连接，实现视频流和（或）音频流的传输。WebRTC的关键特性包括：
点对点通信：WebRTC允许浏览器之间直接进行通信，无需服务器中转。
支持多种数据类型：除了音视频流，WebRTC还可以传输任意类型的数据。
跨平台：WebRTC支持多种平台和操作系统。

2. 了解WebRTC API
WebRTC提供了丰富的API，用于处理音视频流、信令、NAT穿透等。了解以下API对于开发WebRTC应用至关重要：
RTCPeerConnection：用于建立点对点连接。
MediaStream：用于处理音视频流。
RTCRtpReceiver和RTCRtpSender：用于处理RTP流。

根据你的技术栈需求（C/C++、Python、Rust），以下是各语言领域主流的开源 OCR 库推荐，涵盖了从传统算法到深度学习模型的完整生态。

1. C/C++ 核心库（底层引擎）
C/C++ 库通常作为高性能的底层引擎，被其他语言（如 Python、Rust）封装调用。

项目名称 简介 特点
Tesseract 行业标准，由 Google 维护的开源 OCR 引擎。 支持 100+ 种语言，识别精度高，支持版面分析。通常作为后端引擎使用。
Leptonica Tesseract 的依赖库，图像处理库。 提供图像预处理（二值化、降噪、旋转）等基础功能，是 OCR 的“前置处理器”。
GOCR 基于 C 的轻量级 OCR 程序。 体积小，适合命令行快速识别，但识别精度和语言支持不如 Tesseract。
Ocrad GNU 项目下的 OCR 程序。 基于特征提取，适合识别打印体数字和英文，对图像质量要求较高。

2. Python 库（应用层/深度学习）

Python 生态拥有最丰富的 OCR 库，主要基于深度学习模型，识别精度最高。

项目名称 简介 特点
EasyOCR 基于 PyTorch 的深度学习 OCR 库。 支持 80+ 种语言，开箱即用，对中文支持极佳，是目前最流行的选择之一。
PaddleOCR 百度飞桨团队开源的 OCR 工具库。 中文识别精度极高，支持多语言、表格识别、版面分析，部署灵活。
RapidOCR 基于 PaddleOCR 和 ONNX 的跨平台库。 轻量级，推理速度快，支持 Python/C++/Java/C#，适合移动端和嵌入式部署。
Tesseract (Python Wrapper) pytesseract 或 tesserocr。 对 Tesseract 引擎的 Python 封装，适合需要精细控制识别参数的专业场景。

3. Rust 库（高性能/系统级）

Rust 生态的 OCR 库通常追求高性能和内存安全，部分项目是 Python 库的 Rust 重写或封装。

项目名称 简介 特点
tesseract-rs Tesseract 的 Rust 绑定。 允许在 Rust 中调用 Tesseract 引擎，结合 Rust 的并发特性实现高性能处理。
rust-ocr 基于 Rust 的 OCR 库（部分项目）。 社区项目，部分实现了 OCR 功能，但成熟度不如 Python 生态。
DeepSeek-OCR.rs DeepSeek 模型的 Rust 实现。 纯 Rust 实现，无需 Python 环境，提供 CLI 和 HTTP 服务，适合私有化部署。

4. 综合推荐

•   追求最高精度和中文支持：首选 PaddleOCR 或 EasyOCR（Python）。
•   需要系统级集成或极致性能：使用 Tesseract（C++）或 tesseract-rs（Rust）。
•   轻量级或移动端部署：选择 RapidOCR（Python/C++）。

Win64调用约定 指的是在64位 Windows 系统中，由 Microsoft 官方定义的一套函数调用标准，也称为 Microsoft x64 Calling Convention。它规定了函数调用时，参数如何传递、寄存器如何分配、栈由谁清理等核心规则，以确保不同代码模块（如你的汇编函数和C++主程序）之间能够正确、无缝地协作。

核心规则（与 32 位的 __stdcall 等截然不同）
1.  前 4 个参数用寄存器传递：
    ◦   整数/指针参数：依次使用 RCX、RDX、R8、R9 传递。
    ◦   浮点参数：依次使用 XMM0、XMM1、XMM2、XMM3 传递。
2.  更多的参数用栈传递：
    ◦   第 5 个及之后的参数，从右向左压入栈中。调用方必须在栈上为前 4 个参数预留“影子空间”（Shadow Space/Home Space），即使它们实际是通过寄存器传递的。
3.  返回值：
    ◦   整数返回值通过 RAX 返回。
    ◦   浮点返回值通过 XMM0 返回。
4.  栈的清理：
    ◦   由调用方（Caller）负责清理栈。这是与 32 位 __stdcall（被调用方清理）的关键区别。
5.  需保留的寄存器：
    ◦   RBX、RBP、RDI、RSI、R12、R13、R14、R15 必须被调用方保存（如果你在汇编函数中使用了它们，必须先压栈保存，返回前恢复）。其余寄存器可自由使用。

汇编代码示例对比

假设一个函数：int64_t add(int64_t a, int64_t b, int64_t c, int64_t d, int64_t e);
; --- 32位 __stdcall 约定 (旧) ---
; 参数全部通过栈传递，从右向左压栈
push dword 5  ; e
push dword 4  ; d
push dword 3  ; c
push dword 2  ; b
push dword 1  ; a
call _add@20  ; 函数名修饰，20表示参数总字节数
; 栈由被调用方清理

; --- 64位 Win64 约定 (新) ---
; 前4个参数通过寄存器传递
mov rcx, 1    ; a -> RCX
mov rdx, 2    ; b -> RDX
mov r8, 3     ; c -> R8
mov r9, 4     ; d -> R9
; 第5个参数通过栈传递
push 5        ; e
; 必须预留 32 字节的影子空间（4个寄存器*8字节）
sub rsp, 32
call add
add rsp, 32+8 ; 调用方清理栈：影子空间(32) + 第5个参数(8)
; 返回值在 RAX


为什么需要“更新到 Win64 调用约定”？
1.  64位迁移：你正在将 32 位汇编代码升级到 64 位。
2.  与 C/C++ 互操作：你的汇编函数需要被 64 位 C/C++ 代码调用，必须遵循同一套规则。
3.  系统 API 调用：调用 Windows 64 位 API（如 MessageBox）时，必须使用 Win64 约定。

简单来说：在 64 位 Windows 上写汇编函数给别人调用，就必须遵守这套“游戏规则”，否则程序会崩溃。你需要将旧的 push 传参方式改为用 RCX/RDX/R8/R9 传参，并正确管理栈帧。

根据你提供的 libmoq crate 描述（Media over QUIC, C bindings），它绑定的核心 C 库是 libhang（已重命名为 libmoq）。

核心库：libhang / libmoq

libmoq Rust crate 实际上是一个 FFI (Foreign Function Interface) 包装层，它的底层实现依赖于一个名为 libhang 的 C/C++ 库。该库专门用于实现 Media over QUIC (MoQ) 协议。

•   GitHub 仓库：moq-dev/moq 

•   核心功能：提供低延迟的实时媒体传输（视频/音频）能力，基于 QUIC 协议构建。

关于“C bindings”的含义

这里提到的 C bindings 指的是该 Rust crate 提供了与 C 语言交互的接口。通常有两种实现方式：

1.  libhang 的 Rust 封装：Rust 代码通过 FFI 调用 libhang 库中的 C 函数。
2.  生成 C 头文件：Rust 代码会暴露出一套 C 风格的 API（通常使用 extern "C" 关键字），以便 C/C++ 程序（如 OBS Studio、GStreamer）能够直接调用该 Rust 库的功能。

总结

如果你在开发 OBS 插件或其他 C/C++ 项目，你可以直接使用 libmoq crate 生成的 C 头文件来接入 MoQ 功能。如果你需要查看底层的 C/C++ 实现细节，可以参考 libhang 库的源码。
