汇编语言（Assembly）的 IDE 市场比较特殊，绝大多数专业级工具都是商业付费软件，且主要集中在嵌入式开发和逆向工程领域。以下是按“通用学习”和“专业/商业”分类的详细列表：

1. 通用学习与开源 IDE（免费/开源）

这类工具适合初学者、教学或简单的 x86/x64 开发，通常跨平台且免费。

名称 平台 价格 特点

SASM (SimpleASM) Win/Linux/Mac 免费 你提到的工具。跨平台，支持 NASM/MASM/GAS，内置调试器，适合初学者入门。

Visual Studio Code 跨平台 免费 配合汇编插件（如 MASM/TASM、x86/x64 Assembly）和调试器，是目前最流行的轻量级方案。

RadASM Windows 免费 老牌 MASM 专用 IDE，界面经典，支持资源编辑，适合 Windows 汇编开发。

Easy Code Windows 免费 可视化界面生成器，类似 Visual Basic，可以快速生成 Windows GUI 汇编程序。

Fresh IDE Windows 免费 支持 FASM，内置宏处理器，适合编写复杂的汇编程序。

2. 专业/商业 IDE（收费）

这类工具通常用于嵌入式系统开发（ARM、MIPS、RISC-V）或逆向工程，功能强大，价格较高。

名称 平台 价格/授权 特点

Keil MDK (Microcontroller Development Kit) Windows 商业 ARM 开发领域的行业标准。包含 µVision IDE，支持汇编和 C，主要用于 Cortex-M 微控制器。

IAR Embedded Workbench Windows 商业 与 Keil 齐名的商业 IDE，支持多种 MCU 架构，编译效率高，调试功能强大。

ARM Development Studio Windows/Linux 商业 ARM 官方工具，功能最全，支持 Cortex-A/R/M 全系列，包含性能分析器，价格昂贵。

IDA Pro Windows/Linux/Mac 商业 顶级的交互式反汇编器（逆向工程工具）。严格来说不是“编程 IDE”，但支持编辑汇编代码，是安全分析师的必备工具。

Visual Studio (Professional/Enterprise) Windows 商业/订阅 虽然社区版免费，但其专业版和企业版提供更高级的调试和分析工具，在处理大型混合语言项目（C++内嵌汇编）时更有优势。

3. 总结与建议

•   如果你是初学者或学习 x86 汇编：继续使用 SASM 或 VS Code 完全足够，没必要购买商业软件。

•   如果你从事嵌入式开发（如单片机、ARM）：Keil MDK 和 IAR EW 是行业标配，通常公司会购买授权。

•   如果你从事逆向工程或恶意代码分析：IDA Pro 是无可替代的专业工具。


SASM（SimpleASM）本身的设计主要是针对单个 .asm 文件的快速编写、汇编、链接和运行/调试，官方默认界面和“Run”/“Build”功能不支持直接添加多个源文件到同一个项目（不像VS、CLion那样有工程多文件管理）。

目前（到2025-2026年版本）SASM 原生不支持多文件项目，GitHub issue 中也有人提过“Multiple file programs debugging”未实现。

但是你仍然有几种实用方法可以处理“多个 .asm 文件一起编译链接”的需求：

### 方法1：最推荐（用 `%include` 把多个文件“伪装”成一个文件）
这是 NASM / FASM 最常用、最简单的做法，SASM 默认也支持。

假设你有这些文件：

- main.asm（主文件）
- func.asm（放子程序）
- data.asm（放数据定义）

在 main.asm 里写：

```nasm
; main.asm

%include "func.asm"      ; 或者写相对路径 ./func.asm
%include "data.asm"

section .text
global _start

_start:
    ; 调用 func.asm 里的过程
    call some_function

    ; 退出
    mov eax, 60
    xor edi, edi
    syscall
```

然后在 SASM 里只打开 main.asm，直接 Run / Build / Debug 就可以了。

- 优点：最简单，不改 SASM 设置
- 缺点：所有文件看起来像“一个大文件”，不利于大型项目

### 方法2：改 SASM 的 Build 命令行，自己实现多文件编译+链接
SASM 允许你自定义汇编和链接命令（Settings → Build 标签）。

示例（以 NASM + ld 为例，Linux/macOS）：

1. 把所有 .asm 文件放在同一个文件夹
2. Settings → Build → 选 NASM
3. 把 Assembler options 改成：

   ```
   -f elf64 -F dwarf
   ```

4. 把 Linker 路径保持默认（通常是 gcc 或 ld）
5. 把 Linker options 改成类似这样（最关键的一步）：

   ```
   main.o func.o data.o -o program
   ```

   或者更灵活一点用 gcc 链接：

   ```
   main.o func.o data.o -o program
   ```

但问题在于：SASM 每次 Run/Build 只会对当前打开的那个 .asm 文件自动执行 `nasm` 编译成 .o

所以你还需要：

- 先手动在终端里把其他文件编译成 .o

  ```bash
  nasm -f elf64 func.asm -o func.o
  nasm -f elf64 data.asm -o data.o
  ```

- 然后在 SASM 里只编译 main.asm → main.o
- 最后手动链接：`gcc main.o func.o data.o -o myprogram`（或者 ld）

或者你写一个批处理/ shell 脚本，把所有步骤写进去，然后把 SASM 的 linker 命令指向你的脚本。

### 方法3：干脆离开 SASM，用 VS Code + 插件 或 CLion + CMake
当项目文件变多后，SASM 确实不太方便。推荐：

- VS Code + “NASM” 插件 + “C/C++” 插件 + tasks.json / makefile
- CLion + 自定义 External Tools 或 CMakeLists.txt（最优雅）

示例 tasks.json（VS Code）：

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "Build ASM project",
      "type": "shell",
      "command": "nasm -f elf64 *.asm -o program.o && ld -s -o program program.o",
      "group": {
        "kind": "build",
        "isDefault": true
      }
    }
  ]
}
```

### 总结建议（按优先级）

| 场景               | 推荐做法                  | 难度 |
|---------------------|-----------------------------|------|
| 2–5 个文件，简单项目 | 用 `%include` 全写进 main.asm | ★☆☆☆☆ |
| 必须分开维护文件     | 手动终端编译所有 .o → SASM 只管 main → 手动链接 | ★★☆☆☆ |
| 项目会继续变大       | 换 VS Code + NASM 插件 或 CLion | ★★★☆☆ |

好的，这是一个非常核心且正确的观点。想写出高效、可靠的汇编代码，绝不能仅仅满足于指令集的翻译。你提到的“程序之间传递参数”就是一个完美的切入点，它串联起了硬件结构、操作系统约定和编程实践。

我们可以从以下几个层面来深入展开：

1. 硬件基础：寄存器与内存层级

这是所有约定的物理基础。
•   寄存器：CPU内部的超高速存储单元，是数据操作的“主战场”。参数传递会优先使用寄存器，因为速度极快。你需要熟悉通用寄存器（如x86的RAX, RBX, RCX, RDX, RSI, RDI；ARM的R0-R7）和它们的传统用途。

•   内存：当寄存器不够用或需要保存状态时，数据被存入内存（栈、堆）。访问内存比访问寄存器慢几个数量级，因此调用约定的核心目标之一就是尽量减少不必要的内存访问。

•   栈：一种“后进先出”的内存结构，由栈指针寄存器（x86的RSP, ARM的SP）管理。它是实现函数调用、保存返回地址、传递额外参数、存放局部变量的关键。

2. 核心机制：调用约定

调用约定是一套编译器、操作系统和程序员之间心照不宣的“协议”，规定了函数调用前后如何维护状态。它主要解决四个问题：
1.  参数如何传递：哪些参数放寄存器？按什么顺序放？剩下的放哪？（在栈上，按什么顺序？）
2.  返回值放哪里：通常放在特定的寄存器中（如x86用RAX/EAX/AX/AL，ARM用R0）。
3.  哪些寄存器由调用者保存，哪些由被调用者保存：
    ◦   易失性寄存器：函数可以随意使用，其值在调用后可能被破坏。如果调用者需要其中的值，调用者必须在调用前保存它们。

    ◦   非易失性寄存器：函数如果要用，必须在开头保存原值，并在返回前恢复。这样调用者可以放心地认为这些值在调用后不变。

4.  栈如何清理：函数调用后，由谁（调用者还是被调用者）来调整栈指针，清理栈上的参数。

3. 具体实例：x86-64在Linux/Unix下的System V ABI

这是最经典的64位调用约定之一，很好地体现了上述思想。

•   整数/指针参数传递：优先使用寄存器。顺序为：RDI, RSI, RDX, RCX, R8, R9。只有参数超过6个时，第7个及以后的才从右向左压入栈中。

•   返回值：整数和指针通过RAX返回，更大的数据可能通过RDX:RAX或内存返回。

•   寄存器保存责任：

    ◦   被调用者保存：RBX, RBP, R12-R15。如果你想在函数中使用它们，必须先push保存，返回前pop恢复。

    ◦   调用者保存：RAX, RCX, RDX, RSI, RDI, R8-R11等。你可以随意使用，但若调用者（父函数）还需要其中的值，它得自己负责保存。

•   栈对齐：在函数调用前，栈指针必须16字节对齐（这对SSE/AVX指令的性能至关重要）。

一个简单的汇编函数调用C代码的思维过程：
你想调用C函数 int func(int a, int b, int c, int d, int e, int f, int g);
1.  将第一个参数a放入EDI（RDI的低32位）。
2.  将第二个参数b放入ESI。
3.  ... 第六个参数f放入R9D。
4.  第七个参数g需要压栈。注意，在call指令之前，先将g压栈。并且要确保此时RSP是16字节对齐的。
5.  执行 call func。CPU会自动将返回地址（下一条指令地址）压栈。
6.  函数内部可能会使用一些“调用者保存”的寄存器，并把自己的局部变量放在栈上。
7.  函数执行完毕，返回值在EAX中。
8.  ret指令从栈顶弹出返回地址，并跳转回去。
9.  调用者清理栈：因为第七个参数是我们压的，所以返回后，我们要调整栈指针 add rsp, 8 来清理它。

4. 高级视角：与系统交互和性能

理解了这些，你就能看懂并写出更复杂的代码：
•   系统调用：本质是一种特殊的、从用户态进入内核态的函数调用。在x86-64 Linux上，系统调用号放在RAX，参数依次放入RDI, RSI, RDX, R10, R8, R9，然后执行syscall指令。这与C库的函数调用约定不同！你必须查阅操作系统的文档。
•   性能优化：为什么频繁调用的、参数少的小函数（inline函数或宏）很快？因为它们完全通过寄存器通信，避免了访问内存和操作栈的开销。在汇编层面，你会主动规划数据和寄存器使用，让热点路径尽可能保持在寄存器层面。
•   调试与逆向：当你在调试器或反汇编中看到一个函数入口时，你能立刻识别出：哪些指令在保存非易失寄存器（push rbp; mov rbp, rsp），哪里在为局部变量分配栈空间（sub rsp, 0x20），参数在哪里被访问（从rdi读取，或从[rbp+0x10]这样的栈地址读取）。

总结
所以，你问“如何传递参数”，其答案远不止一个顺序列表。它引出了对整个计算机工作方式的深刻理解：

1.  硬件驱动设计：寄存器的速度远高于内存，因此约定优先使用寄存器。
2.  状态管理协议：调用约定是管理复杂性的社会契约，明确了调用双方的责任，保证了程序状态在函数跳转中的可靠性。
3.  连接高级与低级：它是高级语言函数调用在机器层面的直接体现，是编译器后端工作的核心部分。

当你用汇编语言编程时，你就是在扮演“编译器+程序员”的双重角色，直接操控硬件，同时严格遵守这些软硬件协同的契约。这就是汇编编程的挑战与魅力所在。
