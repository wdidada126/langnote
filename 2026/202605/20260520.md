Apache Cassandra，Zoom 也在用的中间件/存储层。
 
一、它是什么
- 开源分布式 NoSQL 数据库（宽列存储） 
- 由 Facebook 开发，后捐给 Apache 基金会，现为顶级项目 
- 特点：无主节点、线性扩展、高可用、多数据中心、写入极强
 
三、Zoom 为什么用它
Zoom 后端大量用 Cassandra 存：
- 用户会话/状态
- 会议元数据
- 实时日志/事件流
- 高可用、全球多活、百万级 QPS 场景

四、核心定位
- 不是消息队列，也不是缓存，是分布式存储数据库
- 在 Zoom 架构里属于：存储层/中间件（和 Kafka、Redis、MySQL 并列）
 
五、一句话总结
Cassandra = 分布式 NoSQL 数据库，Zoom 用它做高可用、高并发的海量数据存储。

一、大厂使用场景清单（Cassandra 核心：高可用、写强、线性扩展、全球多活）

二、技术选型演进历史（从起源到现在，含关键节点与架构取舍）
 
1）起源：2007–2008（Facebook 自研）
 
- 背景：Facebook Inbox 遇到高并发写+随机读+超大存储痛点，MySQL 分片扛不住
- 设计融合：- Dynamo（Amazon）：去中心化、Gossip、多副本、最终一致、高可用
- BigTable（Google）：LSM 树、列族、SSTable、排序存储
- 2008.7：开源到 Google Code，命名 Cassandra（希腊神话，与 Dynamo 同源） 
 
2）孵化到成熟：2009–2015（Apache 化，版本关键节点）
 
- 2009.3：进入 Apache 孵化器（社区化）
- 2010.2：毕业成为 Apache 顶级项目（里程碑）
- 2011：1.0 发布 → Leveled Compaction、稳定生产可用
- 2013：2.0 → 轻量级事务（Paxos）、CQL 成熟（类 SQL，降低门槛）
- 2015：3.0 → 物化视图、性能大提升；“Tick-Tock”发布模式（后放弃）
- 选型趋势：替代 HBase / 自研分片 MySQL，成为社交/时间序列首选 
 
3）规模化与分化：2016–2020（大厂大规模上，Scylla 出现）
- 2016–2018：Apple/Netflix/Zoom 等大规模部署，节点数破万
- 痛点：Java 堆大、GC 卡顿、运维复杂
- 2017：ScyllaDB出现（C++ 重写 Cassandra 协议，兼容 Cassandra，性能提升 5–10倍）
- 大厂演进：- 纯 Cassandra：Apple、Facebook、Zoom（稳定性优先）
- Scylla：部分互联网公司（性能优先）
- 混合：核心用 Cassandra，热点用 Redis，离线用 Hive
 
4）现代演进：2021–2026（4.0+、云原生、AI 集成）
- 2021：4.0 → 零拷贝流、增量修复、Java 11、性能大幅提升
- 2023：4.1 → 审计日志、SAI 二级索引、向量搜索（AI 场景）
- 2024：5.0 → Java 17、内存优化、向量执行、安全增强
- 新场景：AI 向量数据库（替代部分 Pinecone/FAISS）、Serverless 部署、K8s 原生支持
 
5）选型决策树（大厂怎么选 Cassandra）
- ✅ 选 Cassandra：写密集、高可用、全球多活、时间序列、PB 级、无单点
- ❌ 不选 Cassandra：强一致事务（银行核心）、复杂查询（多表 Join）、小数据量（<1TB）
- 替代对比：- vs HBase：C* 无主节点、跨 DC 更稳、写入更强；HBase 强一致、生态更 Hadoop
- vs MongoDB：Cassandra 写吞吐更高、多活更好；MongoDB 查询更灵活
- vs Redis：Cassandra持久化、存储更大；Redis 内存、读写更低延
 
三、一句话总结
Cassandra 是 2007 年 Facebook 为解决高并发写入而生，融合 Dynamo 与 BigTable，经 Apache 孵化成熟，现被 Apple/Netflix/Zoom 等大厂用于全球多活、时间序列、社交/推荐场景；近年演进到 5.0，支持向量搜索与云原生，仍是写密集高可用场景的首选 NoSQL。

一、Cassandra 开发语言
 
主体核心：Java
 
- 原生 Apache Cassandra 完全基于 Java 开发
- 依赖 JVM 运行，底层网络、Gossip、LSM 树、副本策略全是 Java
- 衍生版 ScyllaDB：C++ 重写，协议完全兼容 Cassandra，不依赖 JVM
 
二、Cassandra 磁盘存储格式（对标 MySQL .frm / .ibd）
 
核心概念
Cassandra 是 LSM-Tree 架构，没有 MySQL 那种单表 .frm 表结构文件、 .ibd 索引数据文件，而是一套多组件文件组，一张表对应一组文件。
1、关键文件类型（对标 MySQL 对应关系）
Cassandra 文件 作用 对标 MySQL 
Schema 元数据 集群表结构、键空间、字段、索引定义  .frm  表结构文件 
SSTable (.db 等) 落地磁盘的有序持久化数据/主键/索引  .ibd  数据+索引文件 
CommitLog 预写日志，崩溃恢复用 MySQL redo log 
MemTable 内存写入缓冲区 内存缓冲池 
 
2、SSTable 实际文件组成（表真正的存储文件）
Cassandra 刷盘后一张表的 SSTable 包含多个后缀文件：

-  Data.db ：主数据文件，行数据主体
-  Index.db ：主键索引、偏移索引
-  Filter.db ：布隆过滤器，快速判断数据是否不在此 SSTable
-  Summary.db ：索引摘要，加速索引查找
-  Statistics.db ：表统计元信息、压缩、版本
-  Digest.crc32 ：校验文件

3、存储目录结构 
plaintext
  
data/键空间名/表名-UUID/
  若干 SSTable 组(Data.db/Index.db/Filter.db...)
commitlog/  # 预写日志目录
saved_caches/ # 缓存落地文件

4、和 MySQL 格式核心区别
1. MySQL：B+树 单文件表空间（.ibd），表结构独立 .frm
2. Cassandra：LSM-Tree 批量有序 SSTable，多文件组合，分层压缩合并，不原地更新，只追加写、后台 Compaction 合并
 
5、补充 
- 表结构不存单独静态文件，存在集群 system_schema 系统表里，元数据集群同步
- 支持多种压缩格式：LZ4、Snappy、Deflate，SSTable 天然压缩落地
- 无日志 binlog 概念，靠 CommitLog + 副本同步做高可用



原生多模态大模型 通俗详解（结合你关心的：不是OCR、能直接读图片）
一、先分清核心区别
1. 传统OCR
只做图片→提取文字，是单独的文字识别工具，看不懂画面、看不懂图表、看不懂布局、不懂逻辑，只是把图里的字扒出来，丢给文字模型去读。
本质：先拆图成文字，再只处理文字。
2. 原生多模态
不走OCR中间步骤，不先抠文字，而是直接把整张图片的像素、画面结构、文字、图形、表格、空间位置，全部当成统一输入。
本质：图像、文字是同等模态，一起进模型融合理解。
二、原生多模态底层原理
1. 用视觉编码器ViT 把整张图片转换成视觉Token（图像特征向量）
2. 文字prompt转换成文本Token
3. 图像Token + 文本Token 拼接融合，一起送入大模型主干网络
4. 模型端到端同时理解：字、图、表、布局、逻辑、关系
全程没有单独OCR环节，不是先识别字再分析，是看着整张图直接懂含义。
三、能力和OCR拉开的差距
- OCR：只能出零散文字、数字，看不懂表格行列、折线趋势、流程图逻辑、试卷题干配图
- 原生多模态：1. 识别图片里的文字（比普通OCR更准，模糊、手写、倾斜都能认）
2. 理解图形结构：流程图、架构图、拓扑图一眼看懂逻辑
3. 读懂图表：柱状图、折线图自动分析涨跌、极值、对比
4. 理解空间布局：页面排版、试卷题号位置、表单填写区域
5. 图文联动问答：你发一张截图/试卷/架构图，直接问结论、找错误、解读含义
四、一句话概括
原生多模态 = 模型自带视觉大脑，直接看整张图片整体语义，不是靠OCR扒文字再读，是真正能“看图懂意思”，而不是只会“看图抄字”。
五、常见原生多模态模型
Qwen-VL、GLM-4V、GPT-4V、Claude 3 全系、Gemini 全系，都是原生多模态架构，不是套了OCR的文字模型。
