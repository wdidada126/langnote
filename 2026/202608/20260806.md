SQL建表语句，有哪些考虑的点



这个问题问到根子上了。SQL执行计划的生成，不是凭空变出来的，在MySQL中它要经历“一条龙”的彻查流程。作为开发，你不需要背源码，但必须理解这4个核心阶段，因为它直接告诉你“为什么我的索引没生效”。

从你输入SQL到出结果，流程是这样走的：



第一阶段：词法 & 语法解析（Parser）

目的：检查你的SQL“写对了没”。
MySQL会把你的SQL字符串拆解成一个个“单词”（词法分析），然后根据SQL语法规则，检查关键字顺序、括号匹配、表名是否存在。如果写错（比如SELEC *），这里就直接报错 You have an error in your SQL syntax，流程终止。

输出：一颗解析树（Parse Tree），就是SQL的“语法结构骨架”。



第二阶段：预处理（Preprocessor）

目的：检查“语义”对不对，把“*”展开。
这一步会做几件关键事：

· 检查表和列是否存在。
· 把 SELECT * 展开成实际的列名列表。
· 验证 JOIN 条件里的列是否歧义（比如两个表都有id）。
· 权限检查（你有没有查这个表的权限）。

输出：一颗“合法化”的解析树。



第三阶段：查询优化器（Optimizer）—— 最核心的“大脑”

目的：找出“最快”的执行路径。这是执行计划生成的灵魂阶段。
优化器会做大量计算，核心是代价估算（Cost-based Optimization）：

· 收集统计信息：从information_schema和mysql.innodb_table_stats读取表的行数、索引区分度、页数等。
· 计算各种访问路径的代价：比如走索引idx_age要读取多少行（rows）？全表扫描要读多少页？把这些折算成数值代价（比如cost=125.3）。
· 选择代价最低的方案：不是你觉得走索引快，而是优化器算出来哪个IO成本+CPU成本最小。

关键输出：多种执行计划候选，最终选定一个“最优”的。


第四阶段：执行计划生成 & 执行（Executor）

目的：把优化器的“决策”变成可执行的指令。
这一步会把优化器选定的路径，转换成执行器引擎能理解的迭代器模型（火山模型）。它决定了：

· 先查哪张表？(驱动表)
· 用哪个索引？(key)
· 怎么JOIN？(Nested Loop / Hash Join)
· 怎么排序？

最终，你通过 EXPLAIN 看到的 type、key、rows、Extra，就是优化器决策过程的“快照”。

一张图总结流程

```text
SQL字符串 → 解析器(语法树) → 预处理器(语义校验) → 优化器(代价估算) → 执行器(生成计划并执行)
                                                      ↑
                                          统计信息(行数/区分度)
```


开发必知的3个“计划突变”陷阱

· 统计信息过时：表数据激增但没更新统计信息，优化器用了“老数据”评估，导致选错索引。执行 ANALYZE TABLE 可刷新。
· 参数嗅探：第一次执行的SQL传入特定值（如WHERE age=18），优化器据此生成计划并缓存；后续传age=50（结果集差异巨大），计划可能不再最优，导致性能突降。
· OR条件拆分：WHERE a=1 OR b=2 优化器可能拆成两个独立查询再合并，索引策略会变，建议用 UNION 或改写。


一句话总结：执行计划是“语法-语义-代价估算-执行指令”四步后的产物，EXPLAIN 是你窥探优化器“内心独白”的唯一窗口。

这个问题问到Java内存管理的核心了！先给你纠正一个关键误区：Java“没有指针”是语法层面的说法，实际上Java处处是“引用”（Reference），而强/软/弱/虚引用是指引用的“强度”和“生命周期”策略。


一、先厘清概念：指针 vs 引用

· 指针（C/C++）：存的是内存地址，可以玩指针运算（p++），极其灵活但容易野指针。
· 引用（Java）：也是存地址，但禁止运算，由JVM托管。你写的 User user = new User()，这个 user 就是个引用变量。

结论：Java没有指针运算，但有引用机制。你说的“没有引用”是误解，实际是“没有像C++那样的引用传递语法糖”，但对象访问全靠引用。

---

二、四大引用强度排行（从强到弱）

从java.lang.ref包说起，强度依次递减：

· 强引用（Strong Reference）：Object obj = new Object()。只要强引用存在，GC永不回收。内存不足时宁可OOM也不回收它。这是99%业务代码用的。
· 软引用（Soft Reference）：SoftReference<Object> ref = new SoftReference<>(obj);。内存不足时才会回收，适合做缓存（如图片缓存、大对象缓存）。JVM在抛出OOM前会尽力清理软引用。
· 弱引用（Weak Reference）：WeakReference<Object> ref = new WeakReference<>(obj);。不管内存够不够，下次GC就回收。适合做非强制关联，如ThreadLocal的ThreadLocalMap就是用弱引用存Key，防止线程池复用导致内存泄漏。
· 虚引用（Phantom Reference）：PhantomReference。拿不到对象实例（get()永远返回null），只用于追踪对象被回收的时机，常配合ReferenceQueue做资源清理或堆外内存释放（如NIO的DirectByteBuffer）。

---

三、实战场景（帮你落地）

引用类型 回收时机 经典场景 代码示例
强引用 永不（OOM也不回收） 普通业务对象、Spring Bean User user = new User();
软引用 内存不足时 本地缓存（如Caffeine底层）、图片加载缓存 SoftReference<Bitmap> cache = new SoftReference<>(bitmap);
弱引用 下次GC即回收 ThreadLocal（防止内存泄漏）、WeakHashMap（自动清除过期Key） ThreadLocal.set()底层就是弱引用Key
虚引用 任何时候（无法获取对象） 堆外内存清理（DirectByteBuffer）、对象回收监听 PhantomReference + ReferenceQueue


四、开发高频踩坑点（必看）

· ThreadLocal的内存泄漏：Key是弱引用，但Value是强引用。线程池复用线程时，Key被GC回收，Value却残留，必须手动remove()。
· 缓存选型：软引用做缓存时，GC回收不可控，可能造成性能抖动。生产推荐用Caffeine（它结合了时间/大小/引用策略）而非裸用SoftReference。
· WeakHashMap陷阱：只对Key弱引用，Value是强引用。如果Value引用了Key，会形成循环引用导致无法回收。

五、一句话总结

· 强引用：我活着，对象就不能死（业务核心）。
· 软引用：你要死了（OOM），我才死（缓存）。
· 弱引用：我不管，GC一来你就死（临时关联）。
· 虚引用：你死了告诉我一声（资源清理）。
