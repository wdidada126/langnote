## 说明与补充
- SQLite：最成熟、零配置、单文件，WAL 模式下并发读很好，但写仍单线程。
- H2：Java 生态友好，支持内存/文件/混合模式，常用于测试/原型。
- Apache Derby：完整企业级特性，但较重，已于2025年后维护减弱。
- DuckDB：列式 + 向量化执行，分析性能碾压其他，MVCC 实现优雅，读写不阻塞。

如需添加更多数据库（LMDB、RocksDB、SurrealDB embedded、libSQL 等）或调整维度，欢迎补充要求。

Hekaton、MemSQL、SAP HANA 和 NuoDB 都是在2010年代兴起的高性能/内存优化/分布式数据库技术或产品，主要针对实时事务处理（OLTP）、分析或大规模并发场景。下面按顺序简单说明它们是什么（基于2026年最新现状）：

- Hekaton（也叫 SQL Server In-Memory OLTP）  
  这是 Microsoft SQL Server 的一个内置内存优化 OLTP 引擎（代码名 Hekaton），从 SQL Server 2014 开始引入。  
  核心特点：完全内存驻留表（memory-optimized tables）、乐观 MVCC（无锁并发）、编译为本地代码（native compilation）来加速事务。  
  它不是独立的数据库，而是 SQL Server 的一个可选引擎：你可以把某些表声明为 memory-optimized，混合使用传统表和 Hekaton 表。  
  2026年现状：仍在 SQL Server 中活跃使用（最新版本如 SQL Server 2022/2025 继续支持和优化），常用于高吞吐 OLTP 场景（如金融、电商实时订单）。  
  简单说：Microsoft SQL Server 的“内存加速插件”。

- MemSQL
  MemSQL 是 SingleStore 的旧名字（2020年正式改名为 SingleStore）。

### MVTO 是什么？
MVTO 全称 Multiversion Timestamp Ordering（多版本时间戳排序协议）。

- 核心机制：每个事务在开始时分配一个唯一的时间戳（或事务ID作为时间戳）。
- 读操作：读取时间戳 < 当前事务时间戳 的最新版本。
- 写操作：写时创建新版本，带上当前事务的时间戳；在 commit 时检查冲突（如果有更高时间戳的读已发生，可能 abort）。
- 特点：纯乐观或时间戳驱动，读不加锁，写时可能需要验证顺序。读写不阻塞，但 abort 率可能较高。
- 典型实现：MemSQL（旧名，现在 SingleStore）、Hekaton（SQL Server 内存 OLTP）、HyPer 等内存优化数据库常用 MVTO。
- PostgreSQL 不使用 MVTO（而是更接近 MV2PL + SSI 的混合）。

### MV2PL 是什么？
MV2PL 全称 Multiversion Two-Phase Locking（多版本两阶段锁协议）。

- 核心机制：在传统严格两阶段锁（Strict 2PL）基础上加多版本。
  - 写者加排它锁（X锁），持到 commit。
  - 读者不阻塞写者，而是读取旧版本（已提交的最新版本）。
- 特点：结合锁（写加锁）和版本（读用旧版），写-写冲突仍阻塞，但读-写不阻塞。比纯 2PL 并发度高。
- 典型实现：Oracle、MySQL InnoDB、PostgreSQL（最接近）、SAP HANA、NuoDB 等都属于或接近 MV2PL 风格。

- PostgreSQL 的 MVCC 是MV2PL 的变体 + SSI（用于 Serializable 级别防写倾斜）。
- 它不是 MVTO（没有纯时间戳排序 + 乐观验证 abort 机制）。
- 表格中 MV2PL / MVTO 写法常见于中文资料或简化对比，但严格说 PostgreSQL 是 MV2PL（写加锁 + 读用旧版）。

### xmin / xmax 在 PostgreSQL 中是否存在？（答案：存在，而且是核心）

是的，PostgreSQL 的 MVCC 高度依赖 xmin 和 xmax。

- xmin：创建这个 tuple 版本的事务 ID（Transaction ID, XID）。
- xmax：删除/更新（使这个版本失效）的事务 ID（如果为 0 或无效，则版本还活着）。
- 每个 heap tuple（行版本）的头部（HeapTupleHeader）都包含：
  - xmin（4 或 8 字节，取决于 xid8）
  - xmax
  - cmin / cmax（事务内命令 ID，处理 intra-transaction 可见性）
  - t_ctid（指向下一个版本的指针）

可见性判断完全基于 xmin / xmax + 当前事务的 Snapshot（快照）：
- 如果 xmin 已提交且在 snapshot “可见”范围内 → 可读。
- 如果 xmax 已提交且在 snapshot “之前” → 不可见（被删/更新了）。

PostgreSQL 的“纯逻辑可见性判断”就是靠这些字段 + Snapshot 的 xmin/xmax/xip_list 比较实现的，无需回溯长链（不像一些 undo-based 系统）。
