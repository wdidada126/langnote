重要规则：READ COMMITTED (RC) → 几乎不产生 Gap Lock / Next-key Lock（只 Record Lock，且非匹配记录的锁会很快释放）

2. 释放（Releasing）时机InnoDB 严格遵守 两阶段锁协议（2PL）：加锁阶段（Growing phase）：事务执行过程中可以不断获取锁
释放阶段（Shrinking phase）：只有在事务 COMMIT 或 ROLLBACK 时，才会一次性释放该事务持有的所有锁（包括 Record、Gap、Next-key、意向锁等）

例外情况（锁提前释放）：READ COMMITTED 隔离级别下：扫描过程中遇到不匹配的记录，记录锁会提前释放（但在 RR 下不会）。
隐式锁（insert 产生的）→ 在某些冲突时会转为显式锁，但释放仍随事务结束。

4. 快速记忆口诀想防幻读 → 用 RR + 加锁读（FOR UPDATE / LOCK IN SHARE MODE） → 自动 Next-key Lock
只更新/删除已存在的行，不关心未来插入 → RC 就够（少锁，插入不阻塞）
只要事务没提交 → 它加的 Next-key / Gap 锁就不会放
范围操作 + RR = 容易锁大片间隙 → 并发插入容易卡住

总结一句话：严格来说：Gap lock和Next-key lock是MySQL（InnoDB）特有的命名和实现。
功能上：其他数据库也需要解决幻读问题，但几乎都不采用 MySQL 这种“在 RR 级别就对范围加 gap lock”的激进方式，而是更多依赖 MVCC + 冲突检测（PostgreSQL、Oracle、SQL Server Serializable 的常见做法）。
只有高度兼容 MySQL 协议的数据库（MariaDB、TiDB、OceanBase 等）才会保留几乎一样的 gap lock / next-key lock 机制。

所以当面试官或同事问“gap lock 是 MySQL 独有的吗？”时，最准确的回答是：是的，gap lock和next-key lock是MySQL InnoDB 特有的锁类型和命名，其他主流数据库基本没有直接等价物，它们用不同的方式解决同样的问题。
