.gitignore的匹配规则-知乎.mhtml
以下是 .gitignore 文件的核心匹配规则总结：

基本规则
• 作用范围：对所在目录及所有子目录生效。
• 格式：每行一条规则，空行无意义，# 开头为注释。
• 路径基准：匹配相对路径（相对于 .gitignore 文件所在目录）。

路径匹配规则
1. 不带 / 的规则（如 log）  
   • 匹配任意层级下同名文件或目录（如 log、src/log）。
2. 以 / 开头的规则（如 /log）  
   • 仅匹配当前目录下的文件或目录（如 ./log，不匹配 src/log）。
3. 以 / 结尾的规则（如 cache/）  
   • 忽略整个目录及其内容（如 cache/、cache/file.txt）。

通配符
• *：匹配任意字符（不含 /），如 *.log 匹配所有 .log 文件。
• ?：匹配单个字符（如 config?.json 匹配 configA.json）。
• []：匹配字符集合（如 file[0-9].txt 匹配 file0.txt~file9.txt）。
• ：跨目录匹配（如 logs//debug.log 匹配任意层级的 debug.log）。

取反规则（例外）

• 以 ! 开头表示不忽略指定文件（如 !important.log）。  

• 注意：  
  • 仅对已被忽略的文件生效。  
  • 若父目录被忽略，无法通过 ! 恢复其内部文件（需直接忽略父目录内容，如 cache/* 配合 !cache/.gitkeep）。

优先级与匹配顺序

• 规则从上到下解析，后定义的规则覆盖前者。  
• 示例：  
  *.log          # 忽略所有 .log
  !main.log      # 保留 main.log
  /debug/main.log # 忽略特定路径的 main.log
  

多文件配合
Git 按以下顺序合并忽略规则（路径均相对当前 .gitignore）：
1. 仓库根目录的 .gitignore  
2. 子目录中的 .gitignore  
3. 全局忽略文件（如 ~/.config/git/ignore）  
4. 仓库本地配置（如 .git/info/exclude）

常见示例

• Node.js 项目：  
  node_modules/
  dist/
  *.log
  .env

• Python 项目：  
  __pycache__/
  *.pyc
  venv/

是的，Apache Derby（也叫 Java DB）完全支持事务，并且在并发控制方面实现了三级封锁协议（Degree 3 Consistency / Strict 2PL 风格的 Repeatable Read + Serializable 级别）。

下面基于官方文档（Derby 10.x 系列，包括最新维护版）和实现细节的总结：

### 1. Derby 是否支持事务？
支持，而且支持得非常完整（从诞生起就是 ACID 数据库）：

- 支持 JDBC 标准事务控制：Connection.setAutoCommit(false)、commit()、rollback()、savepoints（部分回滚）。
- 支持 日志恢复：基于 ARIES 算法的 WAL（Write-Ahead Logging），崩溃恢复可靠。
- 支持 多用户并发：嵌入式（embedded）和客户端/服务器模式（network server）都支持多连接事务。
- 支持 JTA/XA（分布式事务协调器）。

官方文档反复强调：Derby 提供完整的事务支持，确保数据完整性，并用于在线事务处理（OLTP）。

### 2. Derby 是否支持三级封锁协议？
是的，支持 Degree 3（三级一致性），而且在最高隔离级别下接近或等价于严格两阶段锁（Strict 2PL）。

Derby 支持 JDBC 标准的 4 个隔离级别（ANSI SQL 定义）：

| JDBC 常量                              | ANSI 级别 | 俗称 / 别名              | Derby 中文常见称呼 | 是否实现 Degree 3 / Strict 2PL 风格？ |
|----------------------------------------|-----------|--------------------------|---------------------|---------------------------------------|
| TRANSACTION_READ_UNCOMMITTED           | 0         | Dirty Read / Read Uncommitted | 读未提交           | 否（允许脏读）                        |
| TRANSACTION_READ_COMMITTED（默认）     | 1         | Read Committed / Cursor Stability | 读已提交           | 否（Degree 1 或 2 级别）              |
| TRANSACTION_REPEATABLE_READ            | 2         | Repeatable Read          | 可重复读           | 是（Degree 3 核心）               |
| TRANSACTION_SERIALIZABLE               | 3         | Serializable             | 可串行化           | 是（Degree 3 + 防幻读）           |

- Degree 3 Consistency（三级一致性 / Degree 3）：
  - 来自经典论文《Granularity of Locks and Degrees of Consistency》（Gray et al.）。
  - 要求：长写锁（写锁持到事务结束）、长读锁（读锁持到事务结束或至少到下一次读相同数据时），防止脏读、不可重复读。
  - Derby 的 TRANSACTION_REPEATABLE_READ（RS）和 TRANSACTION_SERIALIZABLE（RR）级别实现了 Degree 3：
    - 写锁（Exclusive/X 锁）严格持到 commit/abort（Strict 2PL 特性）。
    - 读锁（Shared/S 锁）在 Repeatable Read 级别下也持足够长时间，避免不可重复读。
    - Serializable 级别额外锁范围（range lock 或 next-key lock 类似机制）防幻读（phantom read）。

- 锁粒度：
  - 默认行级锁（row-level locking）。
  - 可配置表级锁（table-level locking，通过 derby.locks.escalation.threshold 等参数）。
  - 支持意向锁（IS/IX/SIX）和更新锁（Update/U 锁，防止死锁升级）。

- 实际行为（官方文档关键点）：
  - 在 Serializable 级别：对 SELECT 会锁住结果集 + 范围，防止插入/更新导致幻读。
  - 写操作的 X 锁始终持到事务结束（无脏写、无级联回滚）。
  - 符合严格两阶段锁（Strict 2PL）：growing phase 加锁，shrinking phase 只在 commit/abort 后释放（尤其是 X 锁）。

### 总结
- Apache Derby 支持完整事务（ACID、日志、恢复、savepoint）。
- 支持三级封锁协议（Degree 3 Consistency）：在 REPEATABLE_READ 和 SERIALIZABLE 隔离级别下实现，写锁严格持到事务结束，读锁行为满足可重复读 + 防幻读（Serializable）。
- 默认隔离级别是 READ_COMMITTED（CS），但你可以轻松切换到更高隔离级别：
  ```java
  connection.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ);
  // 或 TRANSACTION_SERIALIZABLE
  ```

Derby 虽然项目在 2025 年宣布退休（维护停止），但代码和文档仍然可用，很多嵌入式 Java 应用还在用它。如果你用在生产，建议迁移到 H2、HSQLDB 或嵌入式 PostgreSQL 等活跃替代品。

以下是针对你的问题——Derby 的隔离级别配置代码示例，以及与 MySQL/InnoDB 的 Strict 2PL 对比的完整说明（基于 Apache Derby 官方文档和实现细节）。

### 1. Derby 隔离级别配置代码示例（JDBC）

Derby 支持标准的 JDBC 4 个隔离级别，使用 `Connection.setTransactionIsolation()` 设置。默认是 READ_COMMITTED（相当于 Cursor Stability / CS）。

推荐方式：在开启事务前设置隔离级别（推荐在 `setAutoCommit(false)` 之后）。

```java
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;

public class DerbyIsolationExample {
    public static void main(String[] args) {
        String url = "jdbc:derby:memory:myDB;create=true";  // 内存模式示例，或用文件路径 jdbc:derby:/path/to/db

        try (Connection conn = DriverManager.getConnection(url)) {
            // 关闭自动提交，进入手动事务模式（必须先关闭 auto-commit）
            conn.setAutoCommit(false);

            // 示例1: 设置为 READ_COMMITTED（默认，读已提交）
            conn.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);
            System.out.println("隔离级别: READ_COMMITTED");

            // 示例2: 设置为 REPEATABLE_READ（可重复读，接近 Degree 3）
            conn.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ);
            System.out.println("隔离级别: REPEATABLE_READ (Degree 3 风格)");

            // 示例3: 设置为 SERIALIZABLE（最高隔离，可串行化，防幻读 + Strict 2PL 严格行为）
            conn.setTransactionIsolation(Connection.TRANSACTION_SERIALIZABLE);
            System.out.println("隔离级别: SERIALIZABLE (最严格的 Strict 2PL)");

            // ... 执行你的 SQL 操作 ...

            // 提交事务
            conn.commit();

        } catch (SQLException e) {
            e.printStackTrace();
            // 出错时回滚
            try (Connection conn = DriverManager.getConnection(url)) {
                if (conn != null) conn.rollback();
            } catch (SQLException rollbackEx) {
                rollbackEx.printStackTrace();
            }
        }
    }
}
```

等价的 SQL 方式（在连接后执行语句）：
```sql
SET ISOLATION RS;          -- REPEATABLE READ
SET ISOLATION RR;          -- SERIALIZABLE (Derby 用 RR 表示 Serializable)
SET ISOLATION CS;          -- READ COMMITTED (默认)
SET ISOLATION UR;          -- READ UNCOMMITTED
```

注意事项：
- 隔离级别只能在事务开始前设置（即 auto-commit=false 后、commit/rollback 前）。
- SERIALIZABLE 级别下，Derby 会使用范围锁（range locking）防幻读，性能开销较大。
- Derby 嵌入式模式下多线程并发时，SERIALIZABLE 可能导致更多阻塞或死锁。

### 2. Derby 与 MySQL/InnoDB 的 Strict 2PL 对比

两者都支持 Strict 2PL（严格两阶段锁），但实现细节、默认行为和锁机制有明显差异。

| 方面                     | Apache Derby (Java DB)                                                                 | MySQL InnoDB                                                                                  | 主要差异 / 备注                                                                 |
|--------------------------|----------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| 默认隔离级别         | READ_COMMITTED (CS)                                                                    | REPEATABLE_READ                                                                               | Derby 默认更“松”，InnoDB 默认更“严格”                                           |
| Strict 2PL 支持级别  | REPEATABLE_READ (RS) 和 SERIALIZABLE (RR) 实现 Strict 2PL                              | REPEATABLE_READ 和 SERIALIZABLE 都严格使用 Strict 2PL（所有锁持到 commit）                   | 两者在最高级别下行为类似，但 InnoDB REPEATABLE_READ 也接近 Strict 2PL           |
| 写锁（X 锁）持有时机 | Strict 2PL：X 锁持到 commit/abort 后释放（避免脏读、无级联中止）                       | Strict 2PL：X 锁持到 commit/abort 后释放（标准）                                              | 几乎相同                                                                        |
| 读锁（S 锁）行为     | REPEATABLE_READ：读锁持足够长（避免不可重复读）<br>SERIALIZABLE：持到事务结束 + 范围锁 | REPEATABLE_READ：MVCC + 记录锁（gap lock/next-key lock 防幻读）<br>SERIALIZABLE：类似但更强 | Derby 更依赖锁；InnoDB REPEATABLE_READ 主要靠 MVCC（少锁）                      |
| 防幻读机制           | SERIALIZABLE：范围锁（lock entire range）                                              | REPEATABLE_READ & SERIALIZABLE：gap lock / next-key lock（防插入/删除导致幻读）               | InnoDB gap lock 更精细，Derby 范围锁更粗粒度（阻塞更多）                        |
| 锁粒度               | 行级锁为主，可配置表级锁（derby.locks.escalation.threshold）                           | 行级锁 + 意向锁 + 自适应哈希 + gap lock                                                   | 两者都支持行级，但 InnoDB 锁机制更复杂/优化更好                                 |
| MVCC 支持            | 有限（主要靠锁实现隔离，版本控制不强）                                                 | 强大 MVCC（undo log + read view），REPEATABLE_READ 下读不加锁                                | 最大区别：InnoDB 并发度更高（读不阻塞写）                                       |
| 死锁检测             | 有（等待图 + 超时或周期检测）                                                          | 有（等待图 + 死锁检测线程，innodb_deadlock_detect）                                           | 类似，但 InnoDB 更成熟                                                          |
| 性能 & 并发度        | 适合嵌入式、小型应用；高隔离下阻塞多                                                   | 高并发、大型 OLTP；MVCC 让 REPEATABLE_READ 并发极高                                          | InnoDB 整体并发更好，Derby 更轻量                                               |
| 实际使用场景         | 嵌入式 Java 应用、测试、教学、小型工具                                                 | Web/企业级生产数据库                                                                          | Derby 已退休（2025年后无维护），InnoDB 活跃                                     |

一句话总结：
- Derby 的 Strict 2PL 主要在 SERIALIZABLE 级别最严格（纯锁实现，范围锁防幻读），但整体更依赖锁，MVCC 弱 → 并发度不如 InnoDB。
- MySQL InnoDB 的 Strict 2PL 结合 MVCC，即使在 REPEATABLE_READ（默认）下也能实现类似 Strict 2PL 的效果（无脏读、无级联中止），且读性能远高于 Derby。

如果你在 Java 项目中用 Derby 做嵌入式数据库，想追求最高隔离，直接设 SERIALIZABLE 即可；但生产环境推荐迁移到 MySQL/PostgreSQL/H2 等，以获得更好的 MVCC + Strict 2PL 平衡。

下面我们进行详细分析：
1. MySQL (InnoDB) MVCC 机制
核心：Read View + Undo Log

优点：
• 空间效率高：当前数据只有一份（在聚集索引中），历史版本在分离的Undo Log中。对于频繁更新的行，不会在堆中留下大量过期版本。
• “写时复制”成本明确：只在需要时（发生更新/删除）创建Undo记录，且Undo Log本身可被Purge线程清理。这避免了表数据的过度膨胀。
• 与锁结合紧密：默认的RR级别通过“Next-Key Lock”有效防止幻读，适合高并发OLTP写场景。
• 读取性能稳定：通过Read View在事务开始时（RR级别）或语句开始时（RC级别）确定可见性，判断逻辑在内存中完成，回溯Undo链通常很短。

缺点/挑战：
• 长事务问题严重：一个很老的Read View（如长事务）会阻止其能看到的所有旧Undo Log被Purge，导致Undo表空间暴涨，可能影响写性能甚至写阻塞。
• Undo链回溯开销：当需要读取很旧的版本时，可能需要遍历很长的Undo链，影响读性能。
• 实现复杂：需要维护Undo Log的链接、回滚段、Read View的状态等，逻辑复杂度高。

2. PostgreSQL MVCC 机制

核心：Heap Tuple Header + CID (Command ID) 与 Snapshot
优点：
• 实现优雅、逻辑清晰：可见性判断是纯逻辑的，通过比较事务ID和快照中的xmin, xmax即可决定，无需回溯链。这是其“先进”感的来源。
• 没有“长事务导致的全局清理阻塞”问题：一个长事务只会阻止其能看到的那些特定行版本被清理，而不会像MySQL那样阻止一个范围内的所有Undo Log清理。VACUUM可以更精细、安全地进行。
• 非常适合只读查询和复杂分析：稳定的快照、无锁读取，对OLAP和长时间运行的报表查询非常友好。
• 时间旅行和闪回查询：基于多版本数据，可以相对容易地实现“查询过去某个时间点的数据”功能。

缺点/挑战：

• 表膨胀问题：更新/删除会在堆中产生新的行版本，必须由VACUUM（尤其是AUTO VACUUM）来回收空间。如果更新非常频繁，会带来显著的写放大和存储开销。
• 事务ID回卷（XID Wraparound）风险：这是一个著名的运维挑战。如果数据库在很长一段时间内（约20亿个事务）没有完成VACUUM冻结过程，事务ID会用尽，数据库会进入紧急只读模式以强制进行VACUUM FREEZE。需要精心监控和配置。
• 高并发更新热点行：虽然写不阻塞读，但多个事务更新同一行时，仍会产生多个版本，加剧膨胀。虽然引入了HOT（Heap-Only Tuples）优化，但并非所有情况都适用。

对比总结与“先进性”评判
评判维度 MySQL (Read View + Undo Log) PostgreSQL (Heap Multi-version) 解读
哲学与目标 空间效率优先， OLTP写优化。分离当前数据与历史版本。 时间效率与逻辑简洁性优先， OLAP/混合负载友好。拥抱多版本数据。 PG的设计在学术和工程上被认为更“纯粹”和“优雅”。
可见性判断 动态回溯，可能复杂。 静态逻辑比较，非常直接。 PG的判断逻辑更“先进”和高效，尤其是在读取历史版本时。
存储与清理 集中式清理，但受长事务全局阻塞。 分散式渐进清理，更精细，但有膨胀风险。 PG的清理机制更健壮，不易因单一长事务导致系统级问题。MySQL的机制在云原生时代（如TiDB）已被改进。
对运维的要求 需监控长事务和Undo表空间。 需精心配置AUTO VACUUM，监控表膨胀和事务年龄。 两者都有运维痛点，PG的痛点（膨胀、冻结）更为经典和知名。
扩展与生态 与InnoDB的锁、索引深度绑定。 MVCC是存储引擎的核心，更容易支持ZHeap等减少膨胀的新引擎。 PG的MVCC与存储层解耦更好，为未来优化（如ZEDSTORE）留下了更多可能。

结论：哪个更“先进”？
1.  从“理论优雅性和逻辑清晰度”来看，PostgreSQL的策略更先进。它的多版本模型是数据库教科书的经典实现，可见性判断是确定性的逻辑运算，没有回溯链的复杂性和不确定性，对只读查询和复杂分析的支持是天生的优势。
2.  从“工程权衡和对现代硬件/云环境的适应性”来看，两者各有千秋，但趋势是融合。
    ◦ MySQL的分离式Undo在云数据库（如 PolarDB、Aurora）中可以被优化（如将Undo放入独立、可扩展的存储层）。
    ◦ PostgreSQL也在积极解决膨胀问题（如引入ZHeap原型存储引擎，实现“in-place update”以复用旧版本空间）。
    ◦ 现代NewSQL数据库（如TiDB、CockroachDB）的MVCC实现，更多借鉴了PG的基于时间戳/事务ID的快照判断逻辑，但采用了类似MySQL的分离式历史数据存储（将多版本数据放在独立的存储或通过垃圾回收周期清理），可以说是吸取了两家之长。

最终建议：
• 如果你的场景是传统的、高并发、短事务的OLTP，对存储成本敏感，MySQL的模型可能“更合适”。
• 如果你的场景是混合负载、有复杂分析、需要稳定快照，或者你欣赏更清晰一致的数据库行为，PostgreSQL的模型可能“更先进、更省心”。
• 对于全新的分布式数据库选型，基于混合时钟（Hybrid Logical Clock）的MVCC 和 分离历史数据的存储架构 代表了当前更“先进”的方向。

### 1. Derby 隔离级别配置代码示例（JDBC）

Derby 支持标准的 JDBC 4 个隔离级别，使用 `Connection.setTransactionIsolation()` 设置。默认是 READ_COMMITTED（相当于 Cursor Stability / CS）。

推荐方式：在开启事务前设置隔离级别（推荐在 `setAutoCommit(false)` 之后）。

```java
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;

public class DerbyIsolationExample {
    public static void main(String[] args) {
        String url = "jdbc:derby:memory:myDB;create=true";  // 内存模式示例，或用文件路径 jdbc:derby:/path/to/db

        try (Connection conn = DriverManager.getConnection(url)) {
            // 关闭自动提交，进入手动事务模式（必须先关闭 auto-commit）
            conn.setAutoCommit(false);

            // 示例1: 设置为 READ_COMMITTED（默认，读已提交）
            conn.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);
            System.out.println("隔离级别: READ_COMMITTED");

            // 示例2: 设置为 REPEATABLE_READ（可重复读，接近 Degree 3）
            conn.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ);
            System.out.println("隔离级别: REPEATABLE_READ (Degree 3 风格)");

            // 示例3: 设置为 SERIALIZABLE（最高隔离，可串行化，防幻读 + Strict 2PL 严格行为）
            conn.setTransactionIsolation(Connection.TRANSACTION_SERIALIZABLE);
            System.out.println("隔离级别: SERIALIZABLE (最严格的 Strict 2PL)");

            // ... 执行你的 SQL 操作 ...

            // 提交事务
            conn.commit();

        } catch (SQLException e) {
            e.printStackTrace();
            // 出错时回滚
            try (Connection conn = DriverManager.getConnection(url)) {
                if (conn != null) conn.rollback();
            } catch (SQLException rollbackEx) {
                rollbackEx.printStackTrace();
            }
        }
    }
}
```

等价的 SQL 方式（在连接后执行语句）：
```sql
SET ISOLATION RS;          -- REPEATABLE READ
SET ISOLATION RR;          -- SERIALIZABLE (Derby 用 RR 表示 Serializable)
SET ISOLATION CS;          -- READ COMMITTED (默认)
SET ISOLATION UR;          -- READ UNCOMMITTED
```

注意事项：
- 隔离级别只能在事务开始前设置（即 auto-commit=false 后、commit/rollback 前）。
- SERIALIZABLE 级别下，Derby 会使用范围锁（range locking）防幻读，性能开销较大。
- Derby 嵌入式模式下多线程并发时，SERIALIZABLE 可能导致更多阻塞或死锁。

### 2. Derby 与 MySQL/InnoDB 的 Strict 2PL 对比

两者都支持 Strict 2PL（严格两阶段锁），但实现细节、默认行为和锁机制有明显差异。

| 方面                     | Apache Derby (Java DB)                                                                 | MySQL InnoDB                                                                                  | 主要差异 / 备注                                                                 |
|--------------------------|----------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| 默认隔离级别         | READ_COMMITTED (CS)                                                                    | REPEATABLE_READ                                                                               | Derby 默认更“松”，InnoDB 默认更“严格”                                           |
| Strict 2PL 支持级别  | REPEATABLE_READ (RS) 和 SERIALIZABLE (RR) 实现 Strict 2PL                              | REPEATABLE_READ 和 SERIALIZABLE 都严格使用 Strict 2PL（所有锁持到 commit）                   | 两者在最高级别下行为类似，但 InnoDB REPEATABLE_READ 也接近 Strict 2PL           |
| 写锁（X 锁）持有时机 | Strict 2PL：X 锁持到 commit/abort 后释放（避免脏读、无级联中止）                       | Strict 2PL：X 锁持到 commit/abort 后释放（标准）                                              | 几乎相同                                                                        |
| 读锁（S 锁）行为     | REPEATABLE_READ：读锁持足够长（避免不可重复读）<br>SERIALIZABLE：持到事务结束 + 范围锁 | REPEATABLE_READ：MVCC + 记录锁（gap lock/next-key lock 防幻读）<br>SERIALIZABLE：类似但更强 | Derby 更依赖锁；InnoDB REPEATABLE_READ 主要靠 MVCC（少锁）                      |
| 防幻读机制           | SERIALIZABLE：范围锁（lock entire range）                                              | REPEATABLE_READ & SERIALIZABLE：gap lock / next-key lock（防插入/删除导致幻读）               | InnoDB gap lock 更精细，Derby 范围锁更粗粒度（阻塞更多）                        |
| 锁粒度               | 行级锁为主，可配置表级锁（derby.locks.escalation.threshold）                           | 行级锁 + 意向锁 + 自适应哈希 + gap lock                                                   | 两者都支持行级，但 InnoDB 锁机制更复杂/优化更好                                 |
| MVCC 支持            | 有限（主要靠锁实现隔离，版本控制不强）                                                 | 强大 MVCC（undo log + read view），REPEATABLE_READ 下读不加锁                                | 最大区别：InnoDB 并发度更高（读不阻塞写）                                       |
| 死锁检测             | 有（等待图 + 超时或周期检测）                                                          | 有（等待图 + 死锁检测线程，innodb_deadlock_detect）                                           | 类似，但 InnoDB 更成熟                                                          |
| 性能 & 并发度        | 适合嵌入式、小型应用；高隔离下阻塞多                                                   | 高并发、大型 OLTP；MVCC 让 REPEATABLE_READ 并发极高                                          | InnoDB 整体并发更好，Derby 更轻量                                               |
| 实际使用场景         | 嵌入式 Java 应用、测试、教学、小型工具                                                 | Web/企业级生产数据库                                                                          | Derby 已退休（2025年后无维护），InnoDB 活跃                                     |

一句话总结：
- Derby 的 Strict 2PL 主要在 SERIALIZABLE 级别最严格（纯锁实现，范围锁防幻读），但整体更依赖锁，MVCC 弱 → 并发度不如 InnoDB。
- MySQL InnoDB 的 Strict 2PL 结合 MVCC，即使在 REPEATABLE_READ（默认）下也能实现类似 Strict 2PL 的效果（无脏读、无级联中止），且读性能远高于 Derby。

如果你在 Java 项目中用 Derby 做嵌入式数据库，想追求最高隔离，直接设 SERIALIZABLE 即可；但生产环境推荐迁移到 MySQL/PostgreSQL/H2 等，以获得更好的 MVCC + Strict 2PL 平衡。

PostgreSQL 的 MVCC（Multi-Version Concurrency Control，多版本并发控制） 是其并发控制的核心机制，与很多数据库（如 MySQL InnoDB 的 MVCC + 锁混合）不同，PostgreSQL 的 MVCC 实现非常“纯净”和逻辑化，这正是它被很多人称为“优雅”“先进”的原因。

### 核心组件：Heap Tuple Header + xmin / xmax / cid + Snapshot

1. Heap Tuple Header（堆元组头部）
   - 每一条记录（tuple/行版本）在物理页面上都有一个头部（HeapTupleHeader），其中关键字段包括：
     - xmin：创建这条记录版本的事务 ID（Transaction ID，简称 XID）。
     - xmax：删除/更新这条记录版本的事务 ID（如果未被删除/更新，则为 0 或无效值）。
     - cid（Command ID，cmin / cmax）：事务内部的命令序号（一个事务内多条语句的顺序）。
       - 用于处理同一个事务内的可见性（例如事务内先 insert 再 update 同一行）。
       - 大多数情况下不需要回溯链（chain），因为 cid 就能解决 intra-transaction 可见性。
     - 其他：t_ctid（指向下一个版本的指针，用于 HOT 更新链）、hint bits（提交状态缓存）等。

2. Snapshot（快照）
   - 每个事务（或 READ COMMITTED 隔离级别的每个语句）都会获取一个 Snapshot。
   - Snapshot 是一个轻量结构，主要包含：
     - xmin：当前活跃事务中最小的 XID（所有 < xmin 的 XID 都已经提交或回滚）。
     - xmax：下一个将要分配的 XID（所有 ≥ xmax 的 XID 都还没开始或未完成）。
     - xip_list（活跃事务列表）：xmin ≤ XID < xmax 且仍在运行的事务 ID 列表。
     - curcid：当前命令 ID（用于 intra-transaction 判断）。

   Snapshot 不是数据的物理拷贝，而是几个数字 + 列表，用于纯逻辑判断可见性。

### 可见性判断规则（Visibility Rules）——纯逻辑、无需回溯链

核心函数：`HeapTupleSatisfiesMVCC()`（位于 src/backend/access/heap/heapam_visibility.c）

一个 tuple 是否对当前 Snapshot 可见，主要看下面几条规则（简化版，忽略 hint bits 和 aborted 细节）：

1. 创建规则（xmin 可见性）：
   - xmin 已提交（committed）且
   - xmin < snapshot.xmin（太旧，已完成）或 xmin 在 snapshot 的活跃列表中但属于当前事务（自己可见）且 cmin < curcid（事务内顺序早于当前命令）。

   简单说：创建者必须在 Snapshot “看到”的时间点之前已提交。

2. 删除/更新规则（xmax 可见性）：
   - xmax 为 0（未被删除）或
   - xmax 未提交（还在运行）或
   - xmax 已提交但 xmax ≥ snapshot.xmax（删除发生在 Snapshot 之后）。

   简单说：如果有删除/更新，它必须发生在 Snapshot 之后才“还没发生”。

一句话总结可见性：
> Tuple 可见 ⇔ “xmin 已经提交且在 Snapshot 生效之前” 且 “xmax 要么不存在，要么还没提交或发生在 Snapshot 之后”。

- 所有判断都基于 xmin、xmax 与 Snapshot 的 xmin/xmax/xip_list 的比较，加上少量 CLOG（提交日志）查询和 cid 比较。
- 没有物理链回溯（不像 Oracle/MySQL 那样必须沿着 undo/redo 链跳），这大大降低了读放大。

### 为什么说“实现优雅、逻辑清晰”？（PostgreSQL MVCC 的“先进”感来源）

| 方面                   | PostgreSQL MVCC（纯逻辑）                          | 传统锁机制 / 其他 MVCC（如早期 Oracle 部分） | 优势说明                                                                 |
|------------------------|----------------------------------------------------|-----------------------------------------------|--------------------------------------------------------------------------|
| 读者阻塞写者           | 从不阻塞（readers never block writers）            | 读者常阻塞写者（共享锁 vs 排他锁）             | 高并发读写场景下读性能极高                                               |
| 写者阻塞读者           | 从不阻塞（writers never block readers）            | 写者阻塞读者                                   | 写操作不影响正在读的查询                                                 |
| 可见性判断方式         | 纯逻辑比较（xmin/xmax vs Snapshot 数字）           | 常需回溯 undo/版本链重建旧版本                 | 无需 I/O 回溯链 → 读延迟低、CPU 友好                                     |
| 链长度与读放大         | 通常 1（HOT 更新优化下甚至无链）                   | 可能很长（频繁更新导致长 undo 链）             | 读性能稳定，索引扫描快                                                   |
| 隔离级别实现           | Snapshot + 少量谓词锁（Serializable）              | 常需更多锁或复杂 MVCC                          | Repeatable Read / Serializable 几乎免费（靠 Snapshot）                   |
| 死锁风险               | 极低（写-写才锁，读不锁）                          | 高（读-写锁冲突易死锁）                        | 生产环境更稳定                                                           |
| 代价                   | 产生 dead tuples，需要 VACUUM/AUTOVACUUM 清理      | 锁开销、阻塞、死锁检测                         | 代价后置（后台清理），不影响前台读写                                     |

核心优雅点：
- 可见性是纯逻辑运算（几个整数比较 + 列表查找），不需要物理重建旧版本。
- Snapshot 只是几个字段 + 小列表（活跃事务通常很少），创建极轻量。
- cid 巧妙解决了事务内可见性，无需为每个命令创建新版本或复杂链。
- 结合 HOT（Heap-Only Tuple） 更新（同一页面内更新不改 ctid）和 visibility map，极大减少了 vacuum 压力。

这就是 PostgreSQL MVCC 被誉为“最优雅”的原因：它把并发控制从“锁竞争”转向“版本 + 快照逻辑判断”，读写高度解耦，读性能接近单版本数据库。
