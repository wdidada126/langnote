经典多粒度锁协议（Multiple Granularity Locking）

意向锁（Intention Lock）不是 MySQL 独有的机制，它是一种经典的数据库并发控制技术，正式名称叫 Multiple Granularity Locking (MGL，多粒度锁) 中的一部分，早在 20 世纪 70-80 年代的数据库理论论文中就已经被提出和广泛讨论。1. 意向锁的本质和通用目的（所有数据库都类似）在支持多粒度锁（database → table → page → row）的 DBMS 中，当事务想对细粒度资源（如某一行）加锁时，需要一种方式快速告诉别人：“我已经在表/页的更细粒度上加了锁/打算加锁”。没有意向锁 → 想加表级 X 锁时，必须扫描检查表里每一行/每一页有没有锁 → 效率极低
有意向锁 → 只需看表级有没有 IX/IS → 就能快速判断冲突 → 大幅提升性能

3. 总结一句话回答你的问题意向锁（Intention Lock）不是 MySQL 独有的，它是经典多粒度锁协议（Multiple Granularity Locking） 中的标准组成部分，SQL Server、DB2 等商业数据库早就实现了几乎一模一样的 IS/IX/SIX 机制。MySQL InnoDB 把这个机制做得最透明、最常被面试/博客讨论，所以很多人误以为它是 MySQL 专有的。
Oracle 和 PostgreSQL 走的是不同的并发路径（更依赖 MVCC + 其他锁类型），所以没有叫 Intention Lock 的东西，但它们也解决了同样的问题（粗细粒度锁冲突检测）。

最准确的说法是：意向锁是支持多粒度锁的 DBMS 中的常见优化机制，MySQL、SQL Server、DB2 等都明确有，Oracle 和 PostgreSQL 则用其他方式实现类似效果。

经典的多粒度锁协议（Multiple Granularity Locking，简称 MGL） 是数据库并发控制中处理层次化资源（如数据库 → 表 → 页面/分区 → 行/记录）的标准方案，最早由 Gray 等人在 1970 年代的论文中提出（System R 时代）。它的核心思想是通过顶层意向声明来避免每次都要扫描整个子树检查冲突，从而大幅提高粗细粒度混用时的效率。MGL 中的主要锁模式（Lock Modes）经典 MGL 定义了以下几种锁模式（几乎所有实现都遵循这个集合）：锁模式

除了意向锁（IS/IX/SIX），MGL 协议里还有哪些重要组成部分/概念？层次结构（Hierarchy）
数据库资源必须组织成树形（Database → Table → Page → Tuple），锁必须从根向下获取（top-down），从叶向上释放（bottom-up）。
加锁规则（Locking Protocol Rules）  要对某个节点加 S/IS → 祖先必须已有 IS/IX/SIX 中的一种。  
要对某个节点加 X/IX/SIX → 祖先必须已有 IX/SIX。  
不能跳层：必须显式锁住所有祖先（即使只是意向锁）。

锁升级 / 锁粒度提升（Lock Escalation）
当一个事务持有了太多细粒度锁（例如锁了表里 5000 行），系统可以自动把它们升级为表级 IX 或 X，释放所有行锁，减少锁内存占用和遍历开销。这是 MGL 的实用优化（MySQL、SQL Server、DB2 都支持）。
锁收缩 / 降级（Lock Shrinking / Downgrade）
在某些实现中，事务可以把表级 IX 降级为 IS（如果不再需要写子节点了），但经典 MGL 较少强调。
Null Lock (NL)
虽然不常提，但它是兼容矩阵的起点，代表“没锁”。

一句话总结经典 MGL 协议的核心锁模式就是 NL / IS / IX / S / SIX / X 这六种，其中 IS、IX、SIX 是“意向锁家族”，它们本身不真正阻塞数据访问，而是声明意图以支持高效的多粒度并发。除了意向锁，协议还依赖层次加锁顺序、兼容性矩阵、锁升级（escalation） 等机制共同工作。MySQL InnoDB、SQL Server、DB2 基本都忠实实现了这个经典模型（可能名字稍有差异，如 SQL Server 也叫 Intent Shared / Intent Exclusive / SharedWithIntentExclusive）。
