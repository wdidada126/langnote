MySQL的最初版本（第一个公开版本）主要由以下几位核心开发人员在1994–1995年期间开发完成：
- Michael "Monty" Widenius（最核心人物，常被称为“MySQL 之父”）：  
  他是MySQL代码的主要作者，几乎独自完成了服务器端95%以上的早期代码。开发从1994年正式开始，第一个版本于1995年5月23日发布。他用自己大女儿的名字“My” + SQL给数据库命名。
- David Axmark：  
  与Monty一起从 1994 年开始共同开发MySQL的核心部分，是联合创始人之一，负责很多早期设计和实现工作。
- Allan Larsson：  
  也是三位创始人之一，早年与 Monty 合作（从 TcX 公司时期开始），参与 MySQL AB 公司的创立和早期项目，但代码贡献相对 Monty 和 David 少一些，主要在商业和公司运营方面。
简单时间线总结：
- 1979 年 → Monty 开始写早期数据库工具 UNIREG（MySQL 的远祖）。
- 1994 年 → Monty + David 开始正式开发 MySQL（为了替换当时不满意的 mSQL）。
- 1995 年 5 月 → 第一个版本（内部/早期版本常称为 3.11.x 系列）发布。
- 1995 年 → 三人正式成立 MySQL AB 公司。
所以严格来说，MySQL 最初版本的核心开发人员主要是 Monty Widenius 和 David Axmark，Allan Larsson 更多是联合创始人角色。

PostgreSQL（最初名为 POSTGRES）的最初版本是高度学术化的项目，由大学机构主导开发，非常偏向学术研究。
### 核心开发背景
- 开发机构：University of California, Berkeley（加州大学伯克利分校，简称UC Berkeley），计算机科学系。
- 项目启动时间：1986年开始正式实现（概念更早从 1980 年代初）。
- 领导者：Professor Michael Stonebraker（迈克尔·斯通布雷克教授，常被称为“Postgres 之父”），他是整个项目的负责人和主要设计者。他之前领导了 Ingres 项目（世界上最早的 RDBMS 之一），Postgres 是 Ingres 的“后继者”（Post-Ingres），目标是解决当时关系型数据库的局限性，引入对象-关系特性（Object-Relational）、用户自定义类型、规则系统（rules）、复杂数据支持等前沿想法。
- 资助来源：主要来自学术和政府科研基金，包括 DARPA（美国国防高级研究计划局）、ARO（陆军研究办公室）、NSF（国家科学基金会）和 ESL, Inc. 等，完全是学术研究性质的资助。

### 最初版本的时间线与关键人物
- 1986–1987：POSTGRES 项目启动，第一个“demoware”（演示版）系统在 1987 年运行，并在 1988 年 ACM-SIGMOD 会议上展示。这是学术会议上的典型展示。
- 1989年6月：Version 1 发布给少量外部用户（论文：[The implementation of POSTGRES](https://www.postgresql.org/docs/current/history.html)）。
- 1990年6月：Version 2，重新设计了规则系统。
- 1991年：Version 3，改进查询执行器、多存储管理器支持等。
- 早期版本使用 PostQUEL 查询语言（非 SQL），核心代码主要由 Stonebraker 领导的Berkeley研究团队开发，包括他的学生和研究人员（如 Lawrence A. Rowe 等合作者参与早期论文）。
- 1994 年：两位 Berkeley 学生 Andrew Yu 和 Jolly Chen 为 Postgres 添加了 SQL 解析器支持，发布了 Postgres95（这是第一个支持 SQL 的版本）。
- 1996 年：项目从 Berkeley 移出学术界，成立 PostgreSQL Global Development Group，改名为 PostgreSQL（反映支持 SQL），版本号重置为 6.0，进入全球开源社区维护。

### 与 MySQL 的对比（你之前问过 MySQL）
- MySQL：1995 年由Monty Widenius等少数工程师在商业公司TcX/MySQL AB开发，目标是实用、高性能，非学术。
- PostgreSQL：从大学实验室起步，目标是探索数据库理论前沿（如规则系统、类型扩展、对象支持），论文发表在顶级会议（如 SIGMOD），非常典型的学术项目，早期几乎没有商业驱动。
总结：是的，PostgreSQL 最初版本（POSTGRES 1–3 以及 Postgres95）完全是大学机构（UC Berkeley）开发的，高度偏向学术，由 Michael Stonebraker 教授领导的研究团队主导，目的是推动数据库理论创新，而不是直接做产品。后来才转为社区开源项目，成为今天的企业级数据库。Stonebraker 因此项目也获得了图灵奖（数据库领域的重大贡献）。

### 1. 核心概念总览

| 中文术语         | 英文术语                     | 含义简述                                                                 | 是否在第17章重点出现 |
|------------------|------------------------------|--------------------------------------------------------------------------|----------------------|

### 2. 什么是“优先图”（Precedence Graph / 串行化图）

定义（书中典型表述）：
在一个事务调度（Schedule）S 中，我们构造一个有向图 G = (V, E)，其中：
- 顶点 V：所有参与该调度的事务，即 T1, T2, ..., Tn
- 有向边 E：如果事务 Ti 中的一个操作 op_i 与事务 Tj 中的一个操作 op_j 冲突，并且 op_i 在 op_j 之前出现，那么画一条从 Ti 到 Tj 的有向边，记作 Ti → Tj。
关键一句话（几乎所有教材都会强调）：
> Ti → Tj 意味着：在任何等价的串行调度中，Ti必须排在Tj前面。

### 3. 冲突操作（Conflicting Operations）的严格定义
两个操作冲突，当且仅当同时满足下面三条件：
1. 属于不同的事务
2. 操作同一个数据项（同一个数据库对象，如 X、Y）
3. 其中至少一个是写操作（Write）

常见的冲突组合（最重要三种）：

| 操作1   | 操作2   | 是否冲突 | 说明                             |
|---------|---------|----------|----------------------------------|
| read(X) | read(X) | 否   | 读-读不冲突                      |
| read(X) | write(X)| 是   | 读-写冲突                        |
| write(X)| read(X) | 是   | 写-读冲突                        |
| write(X)| write(X)| 是   | 写-写冲突                        |

### 4. 如何判断一个调度是否冲突可串行化（书中核心判定定理）
定理（Silberschatz / Raghu Ramakrishnan / 数据库管理系统原理与设计 等经典教材一致）：
> 一个调度 S 是冲突可串行化的 ⇔ 它的优先图（串行化图）中不存在环（即为有向无环图 DAG）。
- 无环 → 可冲突串行化 → 存在某个串行顺序与之等价
- 有环 → 不可冲突串行化 → 一定存在冲突，无法通过交换非冲突操作得到任何串行调度

### 5. 画优先图的步骤（强烈建议按此步骤做题）
1. 列出调度中所有事务：T1, T2, T3, ...
2. 按时间顺序扫描调度中的每一条操作
3. 只要发现两个冲突操作，且前一个属于 Ti，后一个属于 Tj，就画一条 Ti → Tj
4. 注意：同一个冲突对只需要画一次边（不要重复画）
5. 最后检查整个图是否有环（可以用 DFS、拓扑排序等方式判断）

### 6. 典型例子（最常见的教材例题类型）
调度 S：

```
T1: r1(A)  w1(A)  r1(B)  w1(B)
T2:       r2(A)           w2(A)  r2(B)  w2(B)
```

按时间顺序写成标准形式：

```
r1(A), w1(A), r2(A), r1(B), w1(B), w2(A), r2(B), w2(B)
```

画优先图步骤：

1. r1(A) → w1(A)：T1内部，不画
2. w1(A) → r2(A)：写-读冲突，T1 → T2
3. r1(B) → w1(B)：T1内部
4. w1(B) → w2(A)：不同数据项，不冲突
5. w2(A) → r2(B)：T2内部
6. r2(B) → w2(B)：T2内部

最终优先图：只有一条边 T1 → T2  
结论：无环 → 冲突可串行化，等价串行顺序为 T1 → T2

再看一个有环的例子：

```
r1(A) w1(A) r2(A) w2(A) r1(B) w1(B) r2(B) w2(B) r3(A) w3(A)
```

常见情况会产生：

T1 → T2 → T3 → T1（环）

结论：有环 → 不可冲突串行化

### 7. 优先图 vs 视图可串行化（书里常对比）

| 特性               | 冲突可串行化（优先图）         | 视图可串行化                       |
|--------------------|--------------------------------|------------------------------------|
| 判断依据           | 冲突操作顺序（优先图无环）     | 读写依赖（读了谁写的、最终写了谁） |
| 严格程度           | 更严格                         | 更宽松                             |
| 是否一定包含       | 冲突可串行化 ⇒ 视图可串行化    | 视图可串行化 ⇏ 冲突可串行化        |
| 计算复杂度         | 画图 + 判环（多项式时间）      | NP-完全（很难判定）                |
| 实际系统中常用     | 绝大多数（2PL、SERIALIZABLE） | 理论研究较多                       |

### 8. 总结口诀（快速记忆）
- 优先图 = 串行化图 = 冲突图
- Ti → Tj：Ti 必须排在 Tj 前面
- 无环 = 可冲突串行化
- 有环 = 一定不可冲突串行化
- 冲突操作 = 不同事务 + 同数据项 + 至少一个写

### 1. 两阶段锁协议（Two-Phase Locking Protocol，简称2PL）
核心目标：保证调度是冲突可串行化的（即等价于某个串行调度）。

定义（书中严格表述）：
一个事务的锁操作必须分为两个阶段：

- 扩展阶段（Growing Phase）：事务可以获取锁（申请S锁或X锁），但不能释放任何锁。
- 收缩阶段（Shrinking Phase）：事务可以释放锁，但不能再获取任何新的锁。

关键性质：
- 只要所有事务都遵守2PL → 整个调度一定是冲突可串行化的（反之不一定）。
- 证明：2PL 强制事务的锁获取顺序决定了优先图的拓扑顺序，无环。

优缺点（书中常对比）：
| 方面     | 优点                               | 缺点                               |
|----------|------------------------------------|------------------------------------|
| 隔离性   | 保证冲突可串行化（Serializable）   | —                                  |
| 并发度   | 比基本锁好（可部分重叠）           | 仍可能阻塞较多                     |
| 死锁     | —                                  | 容易产生死锁（最主要缺点）     |
| 级联回滚 | —                                  | 可能导致级联回滚（Cascading Abort） |

基本2PL vs 增强变体（第17章会逐步引入）：
- 基本2PL：可能在收缩阶段释放锁 → 可能级联回滚
- 严格2PL（Strict 2PL）：下面重点讲

### 2. 严格两阶段锁协议（Strict Two-Phase Locking，Strict 2PL）
最常用的实际工业协议（MySQL InnoDB、PostgreSQL、SQL Server 等默认或强烈推荐）。

定义：
在基本2PL的基础上增加一条规则：
- 所有排他锁（X锁）必须持有到事务提交（commit）或回滚（abort）之后才能释放。
- 共享锁（S锁）可以较早释放（但多数系统也持到commit以简化）。

进一步变体（有时书中或文献叫 Strong Strict 2PL / Rigorous 2PL）：
所有锁（S锁 + X锁）都持到事务结束才释放。

为什么需要 Strict 2PL？
- 避免脏读（Dirty Read）：写操作的X锁持到commit → 其他事务读不到未提交的数据。
- 避免级联回滚（No Cascading Abort）：如果事务T2读了T1写的数据，但T1 abort，则T2也必须abort（级联）。Strict 2PL下T2根本读不到未提交数据 → 无级联。
- 可恢复性（Recoverable）和避免级联（Cascadeless）几乎自动满足。

总结对比表（第17章典型总结）：
| 协议          | 是否保证冲突可串行化 | 是否避免脏读 | 是否避免级联回滚 | 是否避免死锁 | 实际使用度 |
|---------------|----------------------|--------------|------------------|--------------|------------|
| 基本锁（无协议）| 否                   | 否           | 否               | —            | 极低       |
| 基本2PL       | 是                   | 否           | 否               | 否           | 中等       |
| Strict 2PL    | 是                   | 是           | 是               | 否           | 极高   |
| Rigorous 2PL  | 是                   | 是           | 是               | 否           | 高         |

### 3. 死锁（Deadlock）
定义：一组事务互相等待对方持有的锁，形成循环等待，谁都无法继续。
必要条件（Coffman条件，四条同时满足才死锁）：
1. 互斥（Mutual Exclusion）：锁是互斥的。
2. 占有并等待（Hold and Wait）：事务持有至少一个锁，还在等待另一个。
3. 不可抢占（No Preemption）：锁不能被强行剥夺。
4. 循环等待（Circular Wait）：存在等待环。

数据库中最常见的是第4条：循环等待。
### 4. 等待图（Wait-for Graph） / 死锁检测图
定义（书中标准工具）：
构造一个有向图：

- 节点：当前活跃的事务（T1, T2, ...）
- 有向边 Ti → Tj：事务 Ti 正在等待 Tj 持有的锁（Ti 在请求某个数据项的锁，但该锁被 Tj 持有）。

死锁判定定理：
> 系统存在死锁 ⇔ 等待图中存在环。
这与优先图类似，但：

| 项目       | 优先图（Precedence Graph）          | 等待图（Wait-for Graph）            |
|------------|-------------------------------------|-------------------------------------|
| 目的       | 判断是否冲突可串行化                | 检测当前是否发生死锁                |
| 节点       | 所有参与调度的事务                  | 当前活跃且被阻塞的事务              |
| 边 Ti → Tj | Ti 的操作先于 Tj 的冲突操作         | Ti 等待 Tj 释放的锁                 |
| 检查时机   | 调度结束后或理论分析                | 系统周期性运行死锁检测算法          |
| 有环含义   | 不可冲突串行化                      | 存在死锁                        |

### 5. 死锁处理方式（第17章重点对比）
| 方法         | 原理                               | 优点                         | 缺点                         | 常见系统实现 |
|--------------|------------------------------------|------------------------------|------------------------------|--------------|
| 死锁预防 | 破坏四个条件之一（如排序加锁）     | 根本不发生死锁               | 并发度低、实现复杂           | 少用         |
| 死锁避免 | 银行家算法等，检查安全序列         | 避免死锁                     | 开销大、需要预知未来请求     | 很少         |
| 死锁检测 + 恢复 | 周期性建等待图，找环 → 选犠牲者 abort | 并发度高、实现简单           | 可能频繁 abort、浪费资源     | 最常见（MySQL、PG等） |

死锁恢复常用策略（书中习题常考）：

- 选择牺牲事务（Victim Selection）：选 abort 代价最小的事务（回滚工作量小、已运行时间短、优先级低等）。
- 可能需要多次 abort（连锁反应）。

### 快速记忆口诀（第17章核心）

- 死锁检测最常用，周期跑等待图 → abort 受害者

- 锁协议就是基于 Two-Phase Locking (2PL)，并进一步要求实现 Strict 2PL（或接近 Strong Strict 2PL/Rigorous 2PL）的行为：
  - 事务必须在 growing phase 获取锁（包括表锁、行锁、意向锁等：IS/IX/SIX/S/X）。

- 学生作业中需要：
  - 实现 deadlock detection（等待图 + 周期检测）。
  - 在 executor（如 seq scan、insert、update、delete）中正确加/解锁。
  - 保证冲突可串行化 + strictness（无脏读、无级联中止）。

### 在 huadb 中 Strict 2PL 的实现情况
是的，huadb 的 Lab 3（Concurrency Control / 事务与并发控制实验）中明确要求实现严格两阶段锁协议（Strict 2PL），这是该实验的核心任务之一。

- 协议要求：
  - 实现 Lock Manager（锁管理器），支持行级锁 + 表级意向锁（IS/IX/S/X 等）。
  - 强制遵守 Two-Phase Locking (2PL)：growing phase 只加锁，shrinking phase 只解锁。
  - 进一步实现 Strict 2PL：所有锁（尤其是 X 锁/写锁）必须持有到事务 commit 或 abort 后才能释放（避免脏读、避免级联中止）。
  - 同时需要实现 死锁检测（通常用等待图 Wait-for Graph + 周期性检测环，或超时机制）。
- 代码位置（基于 huadb 框架）：
  - 事务相关模块：src/transaction/（Transaction、TransactionManager 等）
  - 锁管理：src/lock/ 或 transaction/lock_manager.h 等（学生需要在 // LAB 3 BEGIN 标记处补充 Lock/Unlock 逻辑）。
  - 执行器中加锁：在 executors（如 seq_scan_executor、insert_executor 等）调用锁接口。
- 测试方式：
  - make lab3：运行并发控制相关的测试用例（包括隔离级别测试，如 Serializable）。
  - 框架会检查是否满足 Strict 2PL（无脏读、无级联中止、冲突可串行化）。

huadb 的设计灵感部分来自 CMU 的 Bustub（尤其是早期版本的 Lock Manager 项目），但针对清华课程做了本地化调整和重构（比如更模块化、C++ 风格更规范）。

如果你正在做清华的数据库课程实验（比如 Lab 3），Strict 2PL 是必须正确实现的部分，否则并发测试（如多事务读写冲突、死锁场景）会 fail。常见坑包括：
- 忘记在 abort 时释放锁 → 导致锁泄漏。
- 解锁时机不对 → 违反 Strict 规则（比如提前释放 X 锁）。
- 死锁检测不准 → 等待图没正确建边或没检测环。
