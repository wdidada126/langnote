MVCC额度核心是快照读
好的，我们来详细、系统地解释一下 MVCC 快照读，这是现代数据库实现高并发、非阻塞读操作的核心技术。

1. 核心概念：什么是 MVCC 快照读？

MVCC (Multi-Version Concurrency Control)，即多版本并发控制。它的核心思想是：数据库中的每一行数据在更新时，并不直接覆盖旧数据，而是创建一个新版本。这样，系统中就同时存在数据的多个版本。

快照读 是 MVCC 的实现体现，指的是：在一个事务中，无论数据被其他事务如何修改，该事务看到的始终是它启动时（或某个时间点）的数据“快照”。

简单来说，它解决了经典的“读-写”冲突：

· 传统锁机制：读会阻塞写，写会阻塞读。
· MVCC 快照读：读不阻塞写，写也不阻塞读。读写可以并行进行，极大地提升了并发性能。

2. 核心原理：如何实现快照读？
要实现“一个事务看到稳定的数据快照”，需要三个关键技术的配合：
a) 数据行的多版本存储

每一行数据除了用户定义的列，还有几个系统隐藏字段（以 InnoDB 为例）：

· DB_TRX_ID (6字节)：最近修改/插入该行数据的事务ID。
· DB_ROLL_PTR (7字节)：回滚指针，指向该行数据的上一个版本（存储在 Undo Log 中），形成一条版本链。
· DB_ROW_ID (6字节)：隐含的自增行ID（如果表没有主键）。
· DELETED_BIT：标记该行记录是否被删除。

更新/删除操作流程：
1. 当更新一行数据时，InnoDB 不会立即删除旧数据，而是将旧数据复制到 Undo Log 中。
2. 用新数据覆盖当前行的数据，并更新 DB_TRX_ID 为当前事务ID，将 DB_ROLL_PTR 指向刚刚存入 Undo Log 的旧版本。
3. 删除操作也类似，它被标记为删除，并在 Undo Log 中保留删除前的版本。

这样，一行数据就通过 DB_ROLL_PTR 串联起一条由新到旧的“版本链”。

b) 事务ID与系统版本号
· 每个事务在开始时，都会被分配一个全局递增的、唯一的 事务ID (Transaction ID)。
· 系统维护着一些关键的全局视图信息：
  · up_limit_id：当前活跃事务中，ID最小的事务。
  · low_limit_id：下一个即将被分配的事务ID（即当前最大事务ID+1）。

c) Read View（读视图）—— 快照的定义

Read View 是决定一个事务能看到哪个数据版本的关键数据结构。 它定义了一个事务的“可见性规则”。

一个 Read View 主要包含：
1. trx_ids：生成 Read View 时，系统中活跃（即未提交的）事务ID列表。
2. low_limit_id：生成 Read View 时，系统应该分配给下一个事务的ID。
3. up_limit_id：trx_ids 列表中最小的事务ID。
4. creator_trx_id：创建该 Read View 的事务自己的ID。

3. 可见性判断算法
当一个事务执行快照读（如普通的 SELECT）时，对于查询到的每一行数据，会根据其 DB_TRX_ID 和当前事务的 Read View，按照以下规则判断应该读取哪个版本的数据：

1. 如果 DB_TRX_ID < up_limit_id，说明该版本在 Read View 创建时已经提交，可见。
2. 如果 DB_TRX_ID >= low_limit_id，说明该版本在 Read View 创建之后才被创建/修改，不可见。需要沿着版本链找到更早的版本。
3. 如果 up_limit_id <= DB_TRX_ID < low_limit_id，则检查 DB_TRX_ID 是否在活跃事务列表 trx_ids 中：
   · 如果在，说明该版本是由当前仍活跃（未提交）的事务修改的，不可见。
   · 如果不在，说明该版本在 Read View 创建时已经提交，可见。
4. 如果某个版本对当前事务不可见，则沿着 DB_ROLL_PTR 指向的 Undo Log 中的旧版本，重复上述判断，直到找到第一个可见的版本或到达链尾。

简单记忆：事务只能看到那些在它开始之前（或快照建立时）已经提交的事务所做的修改。

4. 不同隔离级别下的快照读行为
· READ COMMITTED (RC - 提交读)：
  · 每次执行普通 SELECT 语句时，都会生成一个新的 Read View（新的快照）。
  · 效果：在一个事务内，你总能读到其他事务最新提交的数据。这解决了“不可重复读”问题吗？没有，因为两次读可能看到不同的快照。
· REPEATABLE READ (RR - 可重复读)：
  · 只在第一次执行普通 SELECT 语句时生成一个 Read View，整个事务期间都复用这个相同的 Read View。
  · 效果：在一个事务内，无论读多少次，看到的数据都是一致的。它解决了“不可重复读”问题。
  · InnoDB 的扩展：通过 Next-Key Lock 机制，在 RR 级别下还能防止幻读。

5. 示例
假设有数据行 balance = 100。

时间点 事务A (TRX_ID=100) 事务B (TRX_ID=200)
T1 开始事务 开始事务
T2 UPDATE SET balance=90 
T3  SELECT balance (快照读)
T4 COMMIT 
T5  SELECT balance (快照读)

假设隔离级别为 RR：
· 在T3，事务B的Read View生成。up_limit_id=100 (活跃事务最小ID)，low_limit_id=201，活跃列表 trx_ids=[100]。
· 事务B 读到数据行 DB_TRX_ID=100，它在 trx_ids 中（事务A未提交），因此不可见。沿着版本链找到上一个版本 DB_TRX_ID 可能更小（比如是已提交的50），符合可见规则，读到 balance=100。
· 在 T5，事务A已提交。但事务B复用 T3 时的 Read View，判断规则不变。DB_TRX_ID=100 的版本（balance=90）依然在旧的活跃列表中吗？不，Read View 是静态的，它记录的是生成时的活跃事务（当时事务A活跃）。所以该版本依然“不可见”。事务B仍然只能读到 balance=100。这就是可重复读。

如果隔离级别是RC：

· 在 T5，事务B会重新生成一个 Read View。此时事务A已提交，不在新的活跃列表中。所以 DB_TRX_ID=100 的版本（balance=90）可见。事务B会读到 balance=90。

6. 快照读的触发与例外
· 触发快照读的操作：
  · 普通的 SELECT ... 语句（在 READ COMMITTED 和 REPEATABLE READ 级别下，且未加锁）。
· 非快照读（当前读）的操作：
  · SELECT ... FOR UPDATE
  · SELECT ... LOCK IN SHARE MODE (或 FOR SHARE)
  · UPDATE, DELETE, INSERT
  · 这些操作总是读取数据的最新版本，并会对数据加锁，以保证数据一致性。

7. 优点与缺点

优点：
· 高并发：读写互不阻塞，是OLTP系统的基石。
· 避免锁等待：读操作无需等待写锁释放。
· 一致的视图：为事务提供一致的数据视图。

缺点：
· 空间开销：需要存储多个数据版本和 Undo Log。
· 时间开销：需要遍历版本链，在链很长时性能下降。
· 清理工作：需要后台的 Purge 线程来清理不再需要的旧版本数据。如果长事务存在，会导致旧版本无法清理，可能引发表空间膨胀。

总结

MVCC 快照读 是一种通过维护数据的历史版本，结合 Read View 可见性规则，为每个事务提供数据一致性视图的并发控制机制。它完美地平衡了并发性能和事务隔离性，是 MySQL InnoDB、PostgreSQL、Oracle 等主流数据库实现高并发的核心技术。理解快照读的关键在于理解 Read View 的生成时机和可见性判断规则。
