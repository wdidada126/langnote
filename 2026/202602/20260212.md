你提到的WAL和LSM是现代数据库（尤其是 NoSQL 和 NewSQL 数据库）中两个至关重要的核心技术。它们分别解决了数据持久化和数据写入性能的问题。

下面为你详细解析这两个概念。
1. WAL (Write-Ahead Logging) - 预写式日志
核心思想：先写日志，后写数据。在数据真正写入磁盘的数据文件之前，必须先将修改操作记录到日志文件中。

为什么需要 WAL？
•   保证持久性 (Durability)：如果数据库在写入数据时突然崩溃（如断电），数据可能只写入了一半，导致数据文件损坏。WAL 机制确保在崩溃恢复时，可以根据日志重做（Redo）未完成的操作，保证数据不丢失。
•   提升性能：写入日志是顺序写（Append-Only），而写入数据文件通常是随机写。顺序写的速度远快于随机写。通过WAL，数据库可以先将修改缓存在内存中，然后批量写入磁盘，从而大幅提升吞吐量。

工作流程
1.  写日志：事务开始时，将修改操作（如 "SET key=A value=1"）记录到WAL文件。
2.  刷日志：强制将WAL日志刷到磁盘（fsync），确保日志持久化。
3.  写内存：将修改应用到内存中的数据结构（如 MemTable）。
4.  返回成功：告诉客户端写入完成。
5.  刷数据：在后台合适的时机，将内存中的数据刷到磁盘的数据文件。

代表数据库：PostgreSQL、SQLite、MySQL (InnoDB redo log)、Redis (AOF)、LevelDB/RocksDB。

2. LSM (Log-Structured Merge-Tree) - 日志结构合并树
核心思想：将随机写转换为顺序写。它通过先在内存中缓冲写入操作，然后批量写入磁盘，来解决传统 B+ 树在写密集场景下的磁盘 I/O 瓶颈。
为什么需要 LSM？

传统 B+ 树在更新数据时，可能需要多次随机写磁盘来维护树结构（如分裂、旋转）。在高并发写入场景下，磁盘寻道时间成为瓶颈。LSM 通过牺牲一定的读性能（需要合并查找多个文件），换取了极高的写吞吐量。

工作流程（以 LevelDB/RocksDB 为例）
1.  MemTable：数据首先写入内存中的数据结构（通常是有序的跳表 SkipList）。
2.  WAL：同时写入 WAL 日志，防止内存数据丢失。
3.  Immutable MemTable：当 MemTable 写满后，变为只读状态（Immutable），并准备刷盘。
4.  SSTable (Sorted String Table)：将 Immutable MemTable 顺序写入磁盘，生成一个有序的数据文件（SSTable）。这是顺序写，速度极快。
5.  Compaction (合并)：随着 SSTable 文件增多，后台线程会将这些文件合并、去重、排序，生成新的、更大的 SSTable 文件，并删除旧文件，以控制读放大和空间放大。

LSM 的优缺点
•   优点：
    ◦   高写入吞吐量：大量写入被缓冲在内存，并批量顺序写入磁盘。
    ◦   高压缩率：SSTable 文件有序，便于压缩。
•   缺点：
    ◦   读放大 (Read Amplification)：读取一个 Key 可能需要查找 MemTable 和多个层级的 SSTable。
    ◦   写放大 (Write Amplification)：Compaction 过程会反复重写数据。
代表数据库：LevelDB、RocksDB、Cassandra、HBase、ClickHouse。

3. 两者的关系
WAL和LSM通常协同工作：
•   在LSM结构的数据库中（如 RocksDB），WAL是LSM架构的一部分。
•   WAL负责保证数据安全（防止内存数据丢失）。
•   LSM负责组织数据存储（将内存数据转化为磁盘上的有序文件）。

简单来说：WAL是LSM的“保镖”，确保数据在写入内存（MemTable）后不会因为宕机而丢失。

### Oracle 数据库存储结构详解
Oracle 数据库的物理存储结构是一个分层设计，用于高效管理数据、索引和事务信息。它从逻辑到物理的层次结构是：表空间 (Tablespace) → 段 (Segment) → 区 (Extent) → 块 (Block/Page)。这是一种经典的细粒度管理方式，支持动态分配和扩展。下面我按用户查询的关键术语逐一详解（基于 Oracle 官方文档和标准实现，默认块大小为 8KB，但可配置）。

- 表 (Table)：逻辑结构，不是物理存储的最小单位。表数据存储在数据段中。表属于某个模式 (Schema)，并分配到表空间中。创建表时，Oracle 会自动创建一个数据段来存储其行数据。
- 数据段 (Data Segment)：用于存储表数据的段类型。每个非分区表对应一个数据段（分区表每个分区一个段）。它包含表的行数据、LOB 数据等。数据段是段的一种，负责实际的数据存储。
- 索引段 (Index Segment)：用于存储索引的段类型。每个索引（B-tree、位图等）对应一个索引段，存储索引键值和行指针。索引段优化查询，但不存储实际表数据。
- 回滚段 (Rollback/Undo Segment)：用于存储事务的“回滚”信息（undo data），如旧值版本，用于 MVCC（多版本并发控制）、读一致性和回滚操作。Oracle 11g 后更常用“Undo Tablespace”中的自动管理回滚段（系统回滚段 + 用户回滚段）。它确保事务的原子性和一致性。

- 段 (Segment)：Oracle 存储的基本单元，由一个或多个区组成。段是逻辑容器，分配给特定对象（如表、索引、LOB）。  
  - 用户提到“段（256区）”：这可能是个误解或特定配置。Oracle 中一个段没有固定“256区”的限制；段由动态分配的 extents 组成，最小一个 extent。extent 数量取决于数据增长（autoextend on 时自动扩展）。例如，一个表段可能从 1 个 extent 开始，增长到数百个，但没有默认 256 的硬性规定（或许指某些 DBA 配置的 initial/next extent size）。

- 区 (Extent)：段的子单元，由连续的块 (blocks) 组成。Extent 是 Oracle 分配存储的最小连续单元，用于避免碎片。  
  - 用户提到“区（128页）”：同样可能是个配置示例。Oracle 中 extent 大小可变，默认取决于表空间类型（如 dictionary-managed vs locally-managed）。在 locally-managed tablespace（推荐）中，uniform extent size 可设为固定值（如 1MB = 128 个 8KB blocks/pages）。但不是固定 128 页；可自定义（如 64KB = 8 pages）。Extent 确保连续 I/O 高效。

整体流程示例：
- 创建表时：Oracle 在指定表空间中分配一个数据段 → 初始 extent（e.g., 8 blocks） → 每个 block 存储实际数据页。
- 数据增长：当extent满时，分配新 extent（可能连续或非连续，但逻辑上属于同一段）。
- 块 (Block/Page)：最小 I/O 单位，默认 8KB，包含 header + 数据行 + 空闲空间。

这些结构支持 Oracle 的高可用性、并发和恢复（如通过 redo/undo logs）。

### 其他主流数据库是否类似？

不完全相同。Oracle 的存储结构是最复杂和细粒度的（企业级设计），强调分层管理和动态扩展。但其他主流 RDBMS（如 PostgreSQL、MySQL InnoDB、SQL Server）有类似概念（如页/块管理），但 terminology 和实现细节不同，通常更简单或优化特定场景。下面是比较表（基于 2025–2026 年版本）：

| 概念 / 数据库       | Oracle                                   | PostgreSQL                               | MySQL InnoDB                             | SQL Server                               |
|----------------------|------------------------------------------|------------------------------------------|------------------------------------------|------------------------------------------|
| 整体层次        | Tablespace → Segment → Extent → Block   | Database → Schema → Table/Index → Heap File → Block/Page | Tablespace → Page (内部管理 extents-like) | Filegroup → Extent → Page               |
| 表 (Table)      | 逻辑，数据存数据段                       | 逻辑，每个表有独立 heap file（数据 + TOAST for 大对象） | 逻辑，数据存 .ibd 文件（per-table tablespace） | 逻辑，数据存 .mdf 文件                  |
| 数据段          | 是（Table Segment）                      | 无，等价于 heap file                     | 无，等价于 InnoDB 数据页集合             | 无，等价于 heap 或 clustered index      |
| 索引段          | 是（Index Segment）                      | 无，索引有独立文件（e.g., _idx）         | 无，二级索引存页中                       | 无，索引页嵌入文件组                    |
| 回滚段          | 是（Undo Segment）                       | 无，使用 WAL + MVCC（xmin/xmax in tuple header） | 是（Undo Space in ib_undo 文件）         | 是（Transaction Log + Version Store）    |
| 段 (Segment)    | 是，由 extents 组成                     | 无（类似表/索引文件集合）                | 无（内部页管理）                         | 无（但有 allocation units 类似）        |
| 区 (Extent)     | 是，连续 blocks（e.g., 8–128+ pages，可变） | 无（但内部有 free space map 管理块）     | 是（内部 extents = 64 pages = 1MB）      | 是（8 pages = 64KB）                    |
| 块/页 (Block/Page) | 是，默认 8KB                           | 是，默认 8KB                            | 是，默认 16KB                           | 是，默认 8KB                            |
| 相似度          | —                                       | 简化版，无 segment/extent 层            | 类似但更扁平（InnoDB 引擎主导）          | 类似 extents，但无 segment 层           |

解释：
- PostgreSQL：更简单，数据存文件目录（base/目录下每个表/索引一个文件）。没有 explicit segments/extents，使用 vacuum/autovacuum 管理碎片。WAL (pg_wal) 处理恢复/回滚。
- MySQL InnoDB：扁平化，数据/索引/undo 存 .ibd 或系统 tablespace。内部有 extents (1MB) 和 pages，但不暴露给用户。回滚用 undo log。
- SQL Server：类似 Oracle，有 extents (64KB) 和 pages (8KB)，但无 segments。数据存文件组 (filegroups)，回滚用 transaction log + tempdb version store。

总体上，其他数据库借鉴了 Oracle 的分层思想（如块/页管理），但简化了（如无显式 segments），更注重性能/开源友好。Oracle 适合大型企业复杂场景，其他更通用/轻量。

二、各区域详解
1. BSS段（Block Started by Symbol）
作用：存放未初始化或显式初始化为0的全局变量和静态变量。

特点：
• 程序加载时，操作系统将整个 BSS 段全部清零
• 不占用可执行文件空间，只有大小信息
• 节省磁盘空间

示例：
// BSS 段变量示例
#include <stdio.h>

int global_uninit;          // → BSS（未初始化全局变量）
int global_zero = 0;        // → BSS（显式初始化为0）
static int static_uninit;   // → BSS（未初始化静态变量）
const int global_const = 1; // → 数据段（只读数据段）

int main() {
    static int local_static_uninit;  // → BSS（函数内的未初始化静态变量）
    return 0;
}

查看 BSS 大小：
# 编译程序
gcc -o test test.c

# 查看段信息
size test
# 输出示例：
# text    data     bss     dec     hex filename
# 1415     544       8    1967     7af test
#                     ↑ BSS 大小：8字节

# 详细段信息
readelf -S test | grep -E "\.bss|\.data"
objdump -h test  # 显示各段头部信息


2. 数据段（Data Segment）
作用：存放 已初始化且非零 的全局变量和静态变量。

特点：
• 占用可执行文件空间（初始值保存在文件中）
• 程序加载时从文件读入内存

示例：
// 数据段变量
int global_init = 42;                // → 数据段
static int static_init = 100;        // → 数据段
const char* str = "hello";           // 指针在数据段，字符串在只读数据段
char arr[] = "world";                // 数组在数据段

3. 堆（Heap）
作用：动态内存分配的区域。

特点：
• 由程序员手动管理（malloc/free, new/delete）
• 向上增长（向高地址）
• 分配的系统调用：brk() 和 mmap()

示例：
#include <stdlib.h>

int main() {
    // 在堆上分配内存
    int* heap_array = (int*)malloc(100 * sizeof(int));  // → 堆
    int* heap_int = new int(42);                        // C++ → 堆
    
    // 必须手动释放！
    free(heap_array);
    delete heap_int;
    
    return 0;
}


堆的管理：
#include <unistd.h>
#include <sys/types.h>

void heap_operations() {
    // 1. brk/sbrk - 调整program break位置
    void* original_brk = sbrk(0);  // 获取当前program break
    sbrk(4096);                    // 扩展堆4096字节
    
    // 2. malloc/free - 标准库内存管理
    void* ptr1 = malloc(100);
    void* ptr2 = calloc(10, sizeof(int));  // 分配并清零
    void* ptr3 = realloc(ptr1, 200);       // 重新分配
    
    free(ptr2);
    free(ptr3);
    
    // 3. mmap - 大内存分配（通常>128KB）
    void* large_mem = mmap(NULL, 1024*1024, 
                          PROT_READ|PROT_WRITE,
                          MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
    munmap(large_mem, 1024*1024);
}


4. 栈（Stack）
作用：存放局部变量、函数参数、返回地址等。

特点：
• 自动管理（编译器生成代码）
• 向下增长（向低地址）
• 每个线程有自己的栈
• 大小有限（通常8MB，可调整）

示例：
void stack_example(int param) {  // 参数 param 在栈上
    int local_var = 10;          // 局部变量在栈上
    char buffer[100];            // 数组在栈上
    int* ptr = &local_var;       // 指针在栈上，指向栈地址
    
    // 函数调用时，返回地址和寄存器保存在栈上
    recursive_call(param - 1);
}

void recursive_call(int n) {
    int local = n;               // 每次递归调用都有独立的栈帧
    if (n > 0) {
        recursive_call(n - 1);    // 深度递归可能导致栈溢出
    }
}

栈的查看和调整：

四、实际编程中的注意事项

1. BSS vs 数据段的选择

// 不好的做法：大数据放在数据段
int big_array[1000000] = {0};  // 使可执行文件增大4MB！

// 好的做法：大数据放在BSS段
int big_array[1000000];        // 可执行文件很小，运行时分配并清零

// 需要非零初始值时才用数据段
int config_values[10] = {1, 2, 3};  // 必须用数据段


2. 堆内存管理最佳实践

// C++ RAII (Resource Acquisition Is Initialization)
class SmartBuffer {
private:
    int* data;
    size_t size;
public:
    SmartBuffer(size_t n) : data(new int[n]), size(n) {}
    ~SmartBuffer() { delete[] data; }
    // 禁用拷贝（或实现深拷贝）
    SmartBuffer(const SmartBuffer&) = delete;
    SmartBuffer& operator=(const SmartBuffer&) = delete;
};

// 使用现代C++智能指针
#include <memory>
void modern_cpp() {
    auto ptr = std::make_unique<int[]>(100);  // 自动管理内存
    auto shared = std::make_shared<MyClass>(); // 共享所有权
}


3. 栈溢出的预防

// 危险：大数组在栈上
void dangerous() {
    char buffer[10*1024*1024];  // 10MB在栈上 → 可能栈溢出！
}

// 安全：大对象在堆上
void safe() {
    char* buffer = (char*)malloc(10*1024*1024);  // 10MB在堆上
    // 使用buffer...
    free(buffer);
}

// 安全：使用动态栈大小
#include <alloca.h>  // 谨慎使用！
void with_alloca(size_t size) {
    void* temp = alloca(size);  // 在栈上分配，函数返回自动释放
    // 但alloca可能使栈溢出检查失效
}

五、高级话题：内存映射段
除了上面四个主要区域，还有 内存映射段（Memory Mapping Segment）：
#include <sys/mman.h>
#include <fcntl.h>

void memory_mapping() {
    // 1. 文件映射
    int fd = open("data.bin", O_RDONLY);
    void* file_mem = mmap(NULL, 4096, PROT_READ, 
                         MAP_PRIVATE, fd, 0);
    
    // 2. 匿名映射（类似堆但更灵活）
    void* anon_mem = mmap(NULL, 1024*1024,
                         PROT_READ|PROT_WRITE,
                         MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
    
    // 3. 共享内存（进程间通信）
    void* shared_mem = mmap(NULL, 4096,
                           PROT_READ|PROT_WRITE,
                           MAP_SHARED|MAP_ANONYMOUS, -1, 0);
    
    munmap(file_mem, 4096);
    munmap(anon_mem, 1024*1024);
    munmap(shared_mem, 4096);
    close(fd);
}

六、总结与建议
1. BSS段：用于未初始化/零初始化的全局/静态变量，节省磁盘空间
2. 数据段：用于已初始化的全局/静态变量，占用文件空间
3. 堆：动态分配内存，手动管理，小心内存泄漏
4. 栈：自动管理的局部存储，速度快但大小有限

编程建议：
• 小数据、短生命周期 → 用栈
• 大数据、动态大小 → 用堆（配合智能指针）
• 全局配置、常量 → 用数据段
• 大型零初始化数组 → 用BSS段
• 文件I/O、共享内存 → 用内存映射

理解这些内存区域对于编写高效、安全的 C/C++ 程序至关重要，尤其是在资源受限的嵌入式系统或高性能服务器开发中。

在 MySQL 5.7 中，InnoDB 存储引擎支持四种事务隔离级别（Transaction Isolation Level），默认是REPEATABLE READ（可重复读）。
### MySQL 5.7 支持的隔离级别（从低到高）
- READ UNCOMMITTED（读未提交） — 可能出现脏读
- READ COMMITTED（读已提交） — 可能出现不可重复读和幻读
- REPEATABLE READ（可重复读） — MySQL 的默认级别，InnoDB 通过 MVCC + 间隙锁防幻读（接近 Serializable 但性能更好）
- SERIALIZABLE（可串行化） — 最严格，读写都加锁，并发最低

### 如何查看当前隔离级别
```sql
-- 当前会话（session）级别
SELECT @@tx_isolation;                  -- MySQL 5.7.19 及更早版本常用
-- 或
SELECT @@transaction_isolation;         -- MySQL 5.7.20+ 推荐（tx_isolation 已弃用）

-- 全局（global）级别
SELECT @@global.tx_isolation;
-- 或
SELECT @@global.transaction_isolation;
```

### 如何更改隔离级别（三种方式）
#### 1. 仅当前会话（Session）级别生效（最常用，推荐）
```sql
-- 方式一：标准写法（推荐）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 方式二：简写（MySQL 5.7 支持）
SET SESSION tx_isolation = 'READ-COMMITTED';   -- 5.7.19 及更早
SET SESSION transaction_isolation = 'READ-COMMITTED';  -- 5.7.20+

-- 生效后只对本连接有效，新开连接仍用默认
```

#### 2. 全局级别（影响所有新连接，不影响当前连接）
```sql
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 或
SET GLOBAL tx_isolation = 'READ-COMMITTED';   -- 旧写法
SET GLOBAL transaction_isolation = 'READ-COMMITTED';  -- 新写法

-- 注意：已连接的会话不受影响，新连接才会使用新全局值
-- 重启 MySQL 后会丢失，除非写入配置文件
```

#### 3. 永久生效（修改配置文件，重启 MySQL）
在 `my.cnf` 或 `my.ini` 文件中添加（推荐）：

```ini
[mysqld]
transaction-isolation = READ-COMMITTED
# 或旧写法（5.7.19 及更早）
# tx_isolation = READ-COMMITTED
```

- 保存后重启 MySQL 服务（或 `systemctl restart mysqld`）
- 所有连接默认使用该级别

### 常见场景示例

想改成 READ COMMITTED（减少死锁，提高并发）：

```sql
-- 当前会话
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 全局 + 永久（配置文件）
[mysqld]
transaction-isolation = READ-COMMITTED
```

改回默认 REPEATABLE READ：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

最高级别 SERIALIZABLE（严格一致性，但性能差）：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

### 注意事项（MySQL 5.7 特有）
- `tx_isolation` 在 5.7.20 后被 `transaction_isolation` 取代为推荐写法，但两者都支持（向后兼容）。
- InnoDB 只支持这四种级别，其他存储引擎（如 MyISAM）不支持事务隔离。
- 隔离级别越高，并发越低，死锁/锁等待风险越高。
- 生产环境改隔离级别前测试（尤其是从 REPEATABLE READ 改 READ COMMITTED，可能出现幻读）。
- 连接池（如 HikariCP、Druid）建议在连接初始化时执行 SET SESSION ...，避免每个事务都设。

如果你是 MySQL 5.7 的 RDS/Aurora 等云服务，可能需要在控制台参数组修改 `transaction_isolation` 参数。

在 PostgreSQL 中，事务隔离级别（Transaction Isolation Level）的默认值是 read committed（读已提交），这是全局配置参数 `default_transaction_isolation` 决定的。

你可以通过修改配置文件 `postgresql.conf` 来永久更改默认隔离级别（影响所有新事务/新连接）。PostgreSQL 支持的标准隔离级别有：

- read uncommitted（读未提交，实际行为等同 read committed）
- read committed（默认）
- repeatable read（可重复读）
- serializable（可串行化，最严格）

### 修改配置文件 postgresql.conf 的步骤

1. 找到配置文件位置  
   通常在数据目录下（运行以下命令查看确切路径）：
   ```sql
   SHOW config_file;
   ```
   常见路径示例：
   - Linux/Debian/Ubuntu：`/etc/postgresql/<version>/main/postgresql.conf` 或 `/var/lib/postgresql/<version>/main/postgresql.conf`
   - macOS (Homebrew)：`/usr/local/var/postgres/postgresql.conf`
   - Windows：`C:\Program Files\PostgreSQL\<version>\data\postgresql.conf`

2. 编辑 postgresql.conf  
   找到或添加以下行（建议放在文件末尾或 [Client Connection Defaults] 部分附近）：
   ```ini
   # 设置默认隔离级别为 repeatable read（示例）
   default_transaction_isolation = 'repeatable read'
   
   # 或者其他选项：
   # default_transaction_isolation = 'serializable'
   # default_transaction_isolation = 'read committed'   # 恢复默认
   # default_transaction_isolation = 'read uncommitted' # 实际等同 read committed
   ```

   - 值必须用单引号包围。
   - 支持的枚举值：`serializable`、`repeatable read`、`read committed`、`read uncommitted`（大小写不敏感，但建议小写）。

3. 重载配置（不需重启数据库）  
   修改后执行以下任一命令使配置生效（推荐）：
   ```sql
   -- 在 psql 或任何客户端执行
   SELECT pg_reload_conf();
   ```
   或在服务器终端：
   ```bash
   pg_ctl reload -D /path/to/data/dir
   # 或 systemd
   sudo systemctl reload postgresql
   ```

   注意：`default_transaction_isolation` 是 user 上下文参数，重载（reload）后立即对新连接生效，已有连接不受影响（需断开重连）。

4. 验证修改是否生效  
   新开一个连接（或断开重连），运行：
   ```sql
   SHOW default_transaction_isolation;
   SHOW transaction_isolation;  -- 当前事务的隔离级别（新事务开始时会继承 default）
   ```

### 其他方式设置隔离级别（对比参考）

- 会话级别（只影响当前连接，不改配置文件）：
  ```sql
  SET default_transaction_isolation = 'serializable';
  -- 或
  SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  ```

- 数据库级别（影响特定数据库的所有用户）：
  ```sql
  ALTER DATABASE your_db_name SET default_transaction_isolation = 'repeatable read';
  ```

- 用户/角色级别（影响特定用户的所有连接）：
  ```sql
  ALTER ROLE your_user SET default_transaction_isolation = 'serializable';
  ```

- 单个事务级别（最灵活，只影响当前事务）：
  ```sql
  BEGIN;
  SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  -- ... 你的查询 ...
  COMMIT;
  ```

### 注意事项（PostgreSQL特性）
- PostgreSQL的read uncommitted实际行为与read committed相同（文档明确说明）。
- serializable级别使用Serializable Snapshot Isolation (SSI)，性能开销较大，适合对一致性要求极高的场景。
- 改成 repeatable read 或 serializable 后，并发可能下降，死锁/事务失败率上升，生产环境要先测试。
- 如果你是云托管（如 AWS RDS、Google Cloud SQL、Azure Database for PostgreSQL），通常通过参数组修改 `default_transaction_isolation`（控制台操作），而不是直接编辑文件。

在 PostgreSQL 的源代码中，配置文件 `postgresql.conf` 中的参数 `default_transaction_isolation` 是通过 GUC（Grand Unified Configuration）系统 读取并解析的。

这个参数最终会影响全局变量 `DefaultXactIsoLevel`，它是一个 `int` 类型的值，对应内部枚举（`XACT_READ_COMMITTED`、`XACT_REPEATABLE_READ` 等）。

下面一步步详解 PostgreSQL（以主分支 / 最新稳定版为例，17/18 类似，5.x–16.x 核心逻辑几乎相同）中读取和应用这个配置的 C 代码路径。

### 1. GUC 定义位置（参数注册）
`default_transaction_isolation` 是一个 enum 类型 的 GUC 变量，在源代码中通过 `DefineEnumGUC` 或类似宏注册。

核心文件：
- `src/backend/utils/misc/guc.c`（GUC 系统核心实现）
- `src/include/utils/guc.h`（GUC 宏和结构体定义）
- `src/backend/utils/misc/guc_tables.c`（所有内置 GUC 的静态表定义）

在 `guc_tables.c` 中找到类似下面的定义（简化摘录，实际代码更复杂）：

```c
/* src/backend/utils/misc/guc_tables.c */

static struct config_enum ConfigureNamesEnum[] = {
    ...
    {
        {"default_transaction_isolation", PGC_USER, GUC_ENUM},
        &DefaultXactIsoLevel,
        "default_transaction_isolation", gettext_noop("Sets the transaction isolation level of each new transaction."),
        gettext_noop("The default is \"read committed\"."),
        NULL, NULL, NULL,
        assign_default_xact_iso_level, show_xact_iso_level, NULL,
        {
            {"serializable", XACT_SERIALIZABLE},
            {"repeatable read", XACT_REPEATABLE_READ},
            {"read committed", XACT_READ_COMMITTED},
            {"read uncommitted", XACT_READ_COMMITTED},  /* 映射为 read committed */
            {NULL, 0}
        }
    },
    ...
};
```

- `DefaultXactIsoLevel` 是全局变量（`int` 类型），定义在 `src/backend/access/transam/xact.c`
- 它的初始值（编译时默认）是 `XACT_READ_COMMITTED`（即 "read committed"）

```c
/* src/backend/access/transam/xact.c */

int DefaultXactIsoLevel = XACT_READ_COMMITTED;
int XactIsoLevel = XACT_READ_COMMITTED;  /* 当前事务的隔离级别，会在事务开始时继承 Default */
```

### 2. 配置文件读取流程（postgresql.conf → GUC 系统）

PostgreSQL 启动时（或 `pg_reload_conf()` 时）会读取配置文件，核心调用链如下：

1. Postmaster 启动阶段 → `PostmasterMain()` → `ResetAllOptions()` → `SelectConfigFiles()`
2. 读取配置文件 → `ProcessConfigFile(PGC_POSTMASTER)` 或 `PGC_SIGHUP`（reload 时）
   - 文件：`src/backend/utils/misc/guc.c` 中的 `ProcessConfigFile()`
3. 逐行解析 → 调用 `ParseConfigFile()` → `ParseConfigFp()` → `lex_one_token()`（词法分析）
4. 参数赋值 → `set_config_option()`（核心函数）

关键函数：`set_config_option()`（`guc.c`）

```c
/* src/backend/utils/misc/guc.c */

bool
set_config_option(const char *name, const char *value,
                  GucContext context, GucSource source,
                  GucAction action, bool changeVal,
                  int elevel, bool isStartup)
{
    ...
    conf = find_option(name, true, elevel);
    if (conf == NULL)
        return false;

    /* 枚举类型会调用 assign hook */
    if (conf->assign_hook)
        newval = conf->assign_hook(value, context, conf->extra);

    ...
    if (changeVal)
        assign_variable(conf, newval, isStartup);
}
```

对于 `default_transaction_isolation`，它的 `assign_hook` 是：

```c
/* 在 guc_tables.c 或相关文件中注册的 assign 函数 */
static bool
assign_default_xact_iso_level(const char *value, void *extra)
{
    int level = *((int *) extra);

    DefaultXactIsoLevel = level;

    return true;
}
```

（实际代码中通常用 `show_xact_iso_level` 做显示 hook，用 `assign_default_xact_iso_level` 或直接用内置枚举转换）

### 3. 关键全局变量赋值时机

- 启动时：`ResetAllOptions()` → `InitializeGUCOptions()` → 读取配置文件 → `set_config_option()` → 最终 `DefaultXactIsoLevel = XACT_REPEATABLE_READ`（如果配置文件中写了 `'repeatable read'`）
- 重载时（`pg_reload_conf()` 或 SIGHUP）：只重新读取 user 级别的参数（`PGC_USER`），`default_transaction_isolation` 属于 `PGC_USER`，所以 reload 后新连接立即生效（旧连接不受影响）。

### 4. 事务开始时继承

当一个新事务启动时（`StartTransaction()`），会从 `DefaultXactIsoLevel` 继承：

```c
/* src/backend/access/transam/xact.c */

void
StartTransaction(void)
{
    ...
    XactIsoLevel = DefaultXactIsoLevel;
    ...
}
```

- `XactIsoLevel` 是当前事务的隔离级别。
- 后续的 `SET TRANSACTION ISOLATION LEVEL ...` 会修改 `XactIsoLevel`，但不改 `DefaultXactIsoLevel`。

### 5. 总结：读取 → 赋值 → 生效的完整链路（简要）

```
postgresql.conf
   ↓ (解析)
ProcessConfigFile() → ParseConfigFile() → set_config_option("default_transaction_isolation", "repeatable read")
   ↓
find_option() → 找到 GUC 条目（name = "default_transaction_isolation"）
   ↓
assign hook 或直接赋值 → DefaultXactIsoLevel = XACT_REPEATABLE_READ
   ↓ (新事务开始时)
StartTransaction() → XactIsoLevel = DefaultXactIsoLevel
   ↓
事务执行中使用 XactIsoLevel 判断可见性（Snapshot 构建、谓词锁等）
```

调度为事务的并发过程中，决定事务中每个操作的执行顺序。

串行调度(serial schedule): 事务串行执行
调度定义下的并发控制:
给定一个并发调度S ，存在一个串行调度S’， 在任何数据库状态下，按照调度S和调度S’执行后所产生的结果都是相同的 。
此时调度S 被称之为可串行化调度（serializable schedule）。
可串行化调度的数量十分巨大，且难以校验，数据库中一般通过找到可串行化调度的子集（充分条件），即找到能够提前确认是可串行调度的并发调度，进而提升调度效率。
