封锁协议
三种

数据库封锁协议主要分为三级封锁协议，用于保证并发事务的正确性：
一、一级封锁协议
定义：事务在修改数据前必须先加X锁（排他锁），直到事务结束才释放。

特点：
• 防止丢失修改（Lost Update）
• 不能保证可重复读和读"脏"数据

示例：
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- 加X锁
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;  -- 释放锁

二、二级封锁协议
定义：在一级封锁基础上，事务在读取数据前必须先加S锁（共享锁），读完后立即释放。

特点：
• 防止丢失修改和读"脏"数据
• 不能保证可重复读

示例：
BEGIN;
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;  -- 加S锁，读完后释放
UPDATE accounts SET balance = balance - 100 WHERE id = 1 FOR UPDATE;  -- 加X锁
COMMIT;

三、三级封锁协议
定义：在一级封锁基础上，事务在读取数据前必须先加S锁，直到事务结束才释放。
特点：
• 防止丢失修改、读"脏"数据和不可重复读
• 保证可串行化调度

示例：
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR SHARE;  -- 加S锁，事务结束释放
-- 其他操作...
SELECT * FROM accounts WHERE id = 1;  -- 可重复读
COMMIT;  -- 释放所有锁


四、对比总结
协议 丢失修改 读脏数据 不可重复读 锁释放时机
一级 ✅ 防止 ❌ 不防止 ❌ 不防止 X锁事务结束
二级 ✅ 防止 ✅ 防止 ❌ 不防止 S锁读完释放
三级 ✅ 防止 ✅ 防止 ✅ 防止 S锁事务结束

五、实际应用建议
PostgreSQL 中的实现：
• 使用 FOR UPDATE 加X锁
• 使用 FOR SHARE 加S锁
• 使用 LOCK TABLE 表级锁

推荐场景：
• 财务系统：使用三级封锁
• 报表查询：使用二级封锁
• 高并发更新：使用一级封锁

三级封锁协议通过不同的锁释放时机，在并发性和一致性之间提供不同的权衡选择。
数据库中的封锁协议（Locking Protocol）是并发控制的核心机制之一，用于防止多个事务并发操作同一数据时产生不一致性问题（如丢失修改、读“脏”数据、不可重复读等）。
在中文数据库教材（尤其是国内经典教材如《数据库系统概论》王珊版）中，最常提到的三种封锁协议是：

1. 一级封锁协议  
   - 规则：事务T在修改数据R之前，必须先对其加X锁（排他锁/写锁），直到事务结束（commit或rollback）才释放。  
   - 解决的问题：丢失修改（防止两个事务同时修改同一数据导致覆盖）。  
   - 不能解决：读“脏”数据、不可重复读。  
   - 这是所有数据库都至少要满足的最低要求。
2. 二级封锁协议  
   - 规则：在一级封锁协议基础上，事务T在读取数据R之前，必须先加S锁（共享锁/读锁），读完后立即释放S锁。  
   - 解决的问题：丢失修改 + 读“脏”数据（因为读时要等写事务结束）。  
   - 仍不能完全防止：不可重复读（因为读完就释放S锁，之后别人可以改）。
3. 三级封锁协议  
   - 规则：在一级封锁协议基础上，事务T在读取数据R之前，必须先加S锁，直到事务结束才释放。  
   - 解决的问题：丢失修改 + 读“脏”数据 + 不可重复读（同一事务多次读同一数据结果相同）。  
   - 这是最强的封锁协议，能提供较高的隔离性，但并发度较低。

三种封锁协议的对比总结（最常用的一张表）：
| 封锁协议   | 加X锁时机          | 加S锁时机              | S锁释放时机       | 防止丢失修改 | 防止脏读 | 防止不可重复读 | 对应常见隔离级别（参考） |
|------------|---------------------|-------------------------|-------------------|--------------|----------|----------------|--------------------------|
| 一级       | 修改前             | 不加                   | —                 | 是          | 否      | 否            | Read Uncommitted        |
| 二级       | 修改前             | 读取前                 | 读完立即释放     | 是          | 是      | 否            | Read Committed          |
| 三级       | 修改前             | 读取前                 | 事务结束才释放   | 是          | 是      | 是            | Repeatable Read         |

注意：  
- 以上三种是国内教材最经典的说法，主要来自《数据库系统概论》（王珊/萨师煊版）。  
- 国际教材（如《Database System Concepts》Abraham Silberschatz版）更常讨论两段锁协议（2PL）及其变种（Strict 2PL、Rigorous 2PL、Conservative 2PL），它们是实现可串行化调度的核心。  
  - Strict 2PL（严格两阶段锁）：写锁到事务结束才释放（最常用，MySQL InnoDB默认）。  
  - Conservative 2PL（保守两阶段锁）：提前一次性锁住所有需要的数据（防死锁，但实际很少用）。

### 推荐的相关经典书籍
1. 《数据库系统概论》（第5版/第6版） —— 王珊 / 萨师煊  
   - 国内数据库考研/本科生最权威教材，第11章「并发控制」详细讲解三级封锁协议、两段锁协议、死锁、多粒度封锁等。强烈推荐！
2. 《数据库系统概念》（Database System Concepts, 7th Edition） —— Abraham Silberschatz, Henry F. Korth, S. Sudarshan  
   - 国际公认经典教材，英文名“龙书”。第16-17章深入讲解Lock-based Protocols（包括2PL及其变种）、Timestamp Ordering、MVCC等。中文译本质量很高。
3. 《数据库系统实现》（Database Systems: The Complete Book） —— Hector Garcia-Molina 等  
   - 对实现层面讲解更详细，包括锁管理器、死锁检测算法等，适合想深入理解的人。

### 推荐的相关经典论文

1. "Granular Concurrency Control in Database Systems" —— Jim Gray (1978)  
   - 多粒度封锁的奠基论文，引入了意向锁（Intention Lock），几乎所有现代数据库都在用。
2. "On Optimistic Methods for Concurrency Control" —— H. T. Kung & John T. Robinson (1981)  
   - 乐观并发控制的开山之作，与封锁（悲观）形成对比。

3. "The Notions of Consistency and Predicate Locks in a Database System" —— K.P. Eswaran et al. (1976)  
   - 最早系统性讨论谓词锁和两阶段锁协议的论文。

小结：  
如果你是国内学生/考研党，王珊《数据库系统概论》 + 三级封锁协议是必背内容。  
如果你想深入研究并发控制底层原理，Silberschatz龙书 + Gray的意向锁论文 是绕不过去的经典。
