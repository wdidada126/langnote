我来详细讲解 MVCC可见性判断 的核心逻辑，这是数据库实现隔离级别的关键机制。

一、MVCC可见性基本模型

1. 版本数据结构回顾


版本 Entry:
+-------+-------+-------+
| XMIN  | XMAX  | DATA  |
+-------+-------+-------+
创建者  删除者   实际数据


• XMIN：创建此版本的事务ID

• XMAX：删除/更新此版本的事务ID（0表示未删除）

• DATA：实际数据内容

2. 版本链示例


时间线: T1(100) → T2(200) → T3(300) → 当前事务T4(400)

数据版本链:
v1: [XMIN=100, XMAX=200, DATA="v1"]  ← T1创建，T2删除
v2: [XMIN=200, XMAX=300, DATA="v2"]  ← T2创建，T3删除  
v3: [XMIN=300, XMAX=0,   DATA="v3"]  ← T3创建，未删除


二、可见性判断算法详解

核心算法伪代码

public static boolean isVisible(TransactionManager tm, 
                                Transaction t, 
                                Entry entry) {
    long xmin = entry.getXmin();
    long xmax = entry.getXmax();
    
    // 情况1：版本由本事务创建
    if (xmin == t.xid) {
        return xmax == 0 || xmax != t.xid;  // 自己创建且未删除
    }
    
    // 情况2：版本由未提交事务创建 → 不可见
    if (!tm.isCommitted(xmin)) {
        return false;
    }
    
    // 情况3：版本创建事务在本事务开始后提交 → 不可见
    if (xmin > t.xid) {
        return false;
    }
    
    // 情况4：版本已被删除
    if (xmax != 0) {
        // 删除事务未提交 → 版本仍可见
        if (!tm.isCommitted(xmax)) {
            return true;
        }
        // 删除事务在本事务开始前提交 → 不可见
        if (xmax < t.xid) {
            return false;
        }
        // 删除事务在本事务开始后提交 → 版本可见
        return true;
    }
    
    // 情况5：版本未删除，创建事务已提交且在本事务开始前提交 → 可见
    return true;
}


三、各种场景分析

场景1：读已提交（Read Committed）

事务时间线：

T1(100): 开始 → 创建版本v1 → 提交
T2(200): 开始 → 读取数据


判断过程：
// T2(200) 查询 v1[XMIN=100, XMAX=0]
1. xmin=100 != 200
2. tm.isCommitted(100) = true
3. xmin(100) < t.xid(200) ✓
4. xmax=0 → 可见 ✅
// 结果：T2能看到T1已提交的数据


场景2：不可重复读（Read Committed问题）

// 时间点1：T2(200) 第一次查询
// v1[XMIN=100, XMAX=0] → 可见

// 时间点2：T3(300) 更新数据
// v1.setXmax(300) → v1[XMIN=100, XMAX=300]
// 创建 v2[XMIN=300, XMAX=0]
// T3提交

// 时间点3：T2(200) 第二次查询
// 检查v1: xmax=300, tm.isCommitted(300)=true, xmax(300) > t.xid(200) → 可见 ✗
// 检查v2: xmin=300, tm.isCommitted(300)=true, xmin(300) > t.xid(200) → 不可见 ✓
// 结果：T2看到v1被删除，但看不到v2 → 返回null
// 这就是"不可重复读"：同事务内两次查询结果不一致


场景3：可重复读（Repeatable Read）

实现关键：记录ReadView（事务快照）
class Transaction {
    long xid;                    // 事务ID
    long startTs;                // 事务开始时间戳
    Set<Long> activeTransactions; // 活动事务列表（快照）
}

// 可重复读的可见性判断
public static boolean isVisibleRR(Transaction t, Entry entry) {
    long xmin = entry.getXmin();
    long xmax = entry.getXmax();
    
    // 版本由本事务创建
    if (xmin == t.xid) {
        return xmax == 0 || xmax != t.xid;
    }
    
    // 版本创建时，创建事务已提交且在快照中不可见
    if (t.activeTransactions.contains(xmin) || 
        (!tm.isCommitted(xmin) && xmin != t.xid)) {
        return false;
    }
    
    // 版本删除时，删除事务在快照中或未提交
    if (xmax != 0) {
        if (xmax == t.xid) return false;
        if (!tm.isCommitted(xmax) || 
            t.activeTransactions.contains(xmax)) {
            return true;  // 删除未生效，版本仍可见
        }
        return false;  // 已删除
    }
    
    return true;
}


四、隔离级别实现差异

// 最简单：总是读取最新版本
public static boolean isVisibleRU(Entry entry) {
    return entry.getXmax() == 0;  // 只要没被删除就可见
}


2. 读已提交（Read Committed）

// 每次查询重新获取ReadView
public static boolean isVisibleRC(TransactionManager tm, 
                                  long currentXid, 
                                  Entry entry) {
    // 每次查询时获取新的活动事务列表
    Set<Long> snapshot = tm.getActiveTransactions();
    return isVisibleWithSnapshot(tm, currentXid, entry, snapshot);
}


3. 可重复读（Repeatable Read）

// 事务开始时获取ReadView，整个事务保持不变
public static boolean isVisibleRR(Transaction t, Entry entry) {
    // 使用事务开始时获取的快照

/* PostgreSQL的HeapTupleSatisfiesMVCC函数简化版 */
bool HeapTupleSatisfiesMVCC(HeapTupleHeader tuple, 
                           Snapshot snapshot) {
    // 获取版本信息
    xmin = HeapTupleHeaderGetXmin(tuple);
    xmax = HeapTupleHeaderGetXmax(tuple);
    
    // 情况A：本事务插入
    if (TransactionIdIsCurrentTransactionId(xmin)) {
        if (tuple->t_infomask & HEAP_XMAX_INVALID)
            return true;  // 未删除
        if (TransactionIdIsCurrentTransactionId(xmax))
            return false; // 本事务删除
        return true;
    }
    
    // 情况B：在快照中可见
    if (XidInMVCCSnapshot(xmin, snapshot))
        return false;  // 创建事务在快照中活跃
    
    // 情况C：已提交且在快照前
    if (TransactionIdDidCommit(xmin) && 
        TransactionIdPrecedes(xmin, snapshot->xmin))
        return true;
        
    // ... 其他情况
}


MySQL InnoDB可见性判断

// InnoDB的read_view_sees_trx_id函数
bool read_view_sees_trx_id(const read_view_t* view, 
                          trx_id_t trx_id) {
    // 1. 事务ID小于视图最小ID → 已提交且可见
    if (trx_id < view->up_limit_id) {
        return(true);
    }
    
    // 2. 检查是否在活动事务列表中
    const trx_id_t* ids = view->descriptors;
    for (size_t i = 0; i < view->n_descriptors; i++) {
        trx_id_t id = ids[i];
        if (id == trx_id) {
            return(false);  // 在活动事务中，不可见
        }
        if (id > trx_id) {
            break;  // 列表有序，提前结束
        }
    }
    
    // 3. 事务ID大于等于视图最大ID → 在视图后开始，不可见
    if (trx_id >= view->low_limit_id) {
        return(false);
    }
    
    return(true);  // 在间隙中，可见
}


六、版本跳跃（Version Skip）检测

问题：防止丢失更新（Lost Update）
public static boolean isVersionSkip(TransactionManager tm, 
                                   Transaction t, 
                                   Entry entry) {
    long xmax = entry.getXmax();
    if (xmax == 0) return false;  // 未删除
    
    // 检查是否有其他事务在本事务执行期间修改了数据
    if (tm.isCommitted(xmax) && xmax > t.xid) {
        // 有其他事务在本事务开始后提交了删除/更新
        return true;
    }
    
    // 检查是否有未提交事务正在修改
    if (!tm.isCommitted(xmax) && xmax != t.xid) {
        return true;
    }
    
    return false;
}

九、总结

MVCC可见性判断的核心原则：

1. 创建时间规则：
   • 版本由已提交事务创建

   • 在当前事务开始前提交

   • → 可能可见

2. 删除时间规则：
   • 版本未被删除（XMAX=0）

   • 或删除事务未提交

   • 或删除在当前事务开始后提交

   • → 仍然可见

3. 隔离级别影响：
   • RC：每次查询新快照

   • RR：事务级快照

   • 通过控制ReadView的获取时机实现

4. 性能关键：
   • 快速判断事务状态

   • 减少版本遍历

   • 缓存优化

本质：MVCC通过多版本+时间戳实现了无锁读取和快照隔离，是现代数据库高并发的基石。
