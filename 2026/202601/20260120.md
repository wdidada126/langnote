数据库并发控制：封锁协议与三级封锁协议详解

一、并发控制概述
为什么需要并发控制？
当多个事务同时访问数据库时，可能出现以下问题：
• 丢失更新（Lost Update）：两个事务同时更新同一数据，后提交的覆盖先提交的
• 脏读（Dirty Read）：读到未提交事务的中间数据
• 不可重复读（Non-repeatable Read）：同一事务两次读取同一数据结果不同
• 幻读（Phantom Read）：同一查询条件返回不同的行集

解决方案
数据库通过封锁机制实现并发控制，确保事务的ACID特性。
二、封锁（Locking）基本概念
1. 封锁类型
锁类型 作用 兼容性
共享锁（S Lock） 用于读取，阻止其他事务写 与S锁兼容，与X锁不兼容
排他锁（X Lock） 用于写入，阻止其他事务读写 与其他所有锁都不兼容

2. 锁粒度
• 行级锁：锁定单行，并发度高
• 页级锁：锁定数据页
• 表级锁：锁定整个表，并发度低
• 数据库级锁：锁定整个数据库

三、三级封锁协议（Two-Phase Locking, 2PL）
三级封锁协议是封锁机制中的核心协议，它确保事务可串行化执行。
graph LR
    A[事务开始] --> B[获得锁阶段 Growing Phase]
    B --> C[释放锁阶段 Shrinking Phase]
    C --> D[事务结束]

协议规则
1. 增长阶段（Growing Phase）：事务只能获得锁，不能释放锁
2. 缩减阶段（Shrinking Phase）：事务只能释放锁，不能获得锁
3. 封锁点：获得最后一个锁的时刻称为封锁点

示例
-- 事务T1执行过程
BEGIN TRANSACTION;
-- 增长阶段开始
LOCK-S(A);  -- 获取A的共享锁
READ(A);
LOCK-X(B);  -- 获取B的排他锁
READ(B);
-- 封锁点：已获得所有需要的锁
-- 缩减阶段开始
UNLOCK(A);  -- 释放A的锁
WRITE(B);
UNLOCK(B);  -- 释放B的锁
COMMIT;

三级封锁协议变种
1. 基本2PL（Basic 2PL）
• 严格遵循增长和缩减阶段
• 可能导致级联回滚问题

2. 严格2PL（Strict 2PL）
• 规则：事务持有的所有排他锁必须在事务结束后才能释放
• 优点：避免级联回滚，保证可恢复性

• 示例：
  BEGIN;
  LOCK-X(A);
  UPDATE A SET value = 100;
  -- 持有锁直到提交
  COMMIT;  -- 提交时自动释放所有锁

3. 强严格2PL（Rigorous 2PL）
• 规则：事务持有的所有锁（包括共享锁和排他锁）必须在事务结束后才能释放
• 优点：最简单的实现，避免所有并发问题
• 缺点：并发度最低

四、三级封锁协议对比
特性 基本2PL 严格2PL 强严格2PL
锁释放时机 缩减阶段 X锁事务结束释放 所有锁事务结束释放
避免脏读 ❌ ✅ ✅
避免不可重复读 ✅ ✅ ✅
避免幻读 ❌ ❌ 需要其他机制
避免级联回滚 ❌ ✅ ✅

并发度 高 中 低
实现复杂度 中 高 低

五、实际数据库中的实现
MySQL InnoDB
-- 默认使用严格2PL + MVCC（多版本并发控制）
BEGIN;
SELECT * FROM t WHERE id=1 FOR UPDATE;  -- 获取排他锁
UPDATE t SET value=100 WHERE id=1;
-- 锁在事务提交后释放
COMMIT;

Oracle
• 使用行级排他锁 + MVCC
• 读操作不阻塞写操作
• 写操作使用行级锁

SQL Server
• 支持多种隔离级别
• 默认使用严格2PL

六、封锁协议的问题与解决方案

问题1：死锁（Deadlock）
场景：事务T1锁A等B，事务T2锁B等A
解决方案：
1. 死锁预防
   • 一次封锁法：事务开始前获得所有需要的锁
   • 顺序封锁法：按固定顺序获取锁

2. 死锁检测与解除
   -- MySQL查看死锁信息
   SHOW ENGINE INNODB STATUS;

问题2：活锁（Livelock）
场景：事务总是等待，但无法获得锁
解决方案：
• 先来先服务调度
• 超时重试机制

问题3：饥饿（Starvation）

场景：小事务总是被大事务阻塞
解决方案：
• 公平调度算法
• 锁升级机制

七、多粒度封锁与意向锁

锁类型 符号 作用

九、现代并发控制发展
乐观并发控制（OCC）
• 假设冲突少，先执行后验证
• 适合读多写少场景
• 典型实现：MVCC（多版本并发控制）
多版本并发控制（MVCC）
• 每个数据项维护多个版本
• 读操作不阻塞写操作
• MySQL InnoDB、PostgreSQL等使用

总结
三级封锁协议（2PL）是数据库并发控制的理论基础，它通过：
1. 增长阶段获取所有需要的锁
2. 缩减阶段释放锁
3. 严格变种避免级联回滚

实际数据库实现中，通常结合：
• 严格2PL保证一致性
• MVCC提高并发度
• 意向锁支持多粒度封锁
理解这些机制对于：
• 设计高性能应用：避免锁竞争
• 诊断性能问题：分析锁等待
• 优化SQL：减少锁持有时间

数据库等待图算法（Wait-for Graph Algorithm）
一、作用概述
等待图算法的主要作用是检测数据库系统中的死锁。它是一种图论算法，用于识别并发事务执行过程中出现的循环等待情况，这是死锁发生的必要条件之一。
二、算法核心原理
基本思想
将事务间的等待关系建模为有向图，通过检测图中是否存在环来判断死锁。

图的构成
等待图 G = (V, E)
其中：
V: 顶点集合，每个顶点表示一个事务（T₁, T₂, ..., Tₙ）
E: 边集合，有向边 Tᵢ → Tⱼ 表示：
   "事务Tᵢ正在等待事务Tⱼ释放某个资源"

三、算法详细过程
步骤1：构建等待图
等待关系的产生场景：
1. 锁等待：T₁持有资源R的锁，T₂请求R的锁被阻塞
2. 数据依赖：T₁修改了数据，T₂需要读取最新版本
3. 通信等待：分布式系统中消息传递

示例：

事务 T1: 持有资源A的锁，请求资源B的锁
事务 T2: 持有资源B的锁，请求资源A的锁

构建的等待图：
T1 → T2  (因为T1等待T2释放B)
T2 → T1  (因为T2等待T1释放A)


步骤2：检测环路

算法伪代码：
def detect_deadlock(wait_for_graph):
    # 步骤1：复制图副本
    graph = copy(wait_for_graph)
    
    # 步骤2：重复移除没有出边的节点
    while exists node in graph with no outgoing edges:
        remove node and all incoming edges to it
    
    # 步骤3：判断剩余图
    if graph is empty:
        return false  # 无死锁
    else:
        return true   # 存在死锁
        # 剩余节点构成死锁环


步骤3：死锁环分析

如果图非空，剩余的节点和边构成了死锁环。

示例分析：
初始图：
T1 → T2 → T3 → T1
第一次迭代：所有节点都有出边，不移除
最终图非空 → 存在死锁环：T1→T2→T3→T1

四、算法特性
时间复杂度
• 最坏情况：O(V + E )，其中 V 是顶点数， E
是边数
• 实际应用：通常检测间隔为几秒到几十秒
空间复杂度
• O(V + E
)，需要存储图结构
算法优势
1. 准确率高：能精确检测所有死锁
2. 可追溯性：能识别参与死锁的所有事务
3. 实现简单：基于图论，算法清晰

2. 数据结构设计

// 典型的等待图数据结构
struct WaitForGraph {
    HashMap<TransactionId, Vertex> vertices;  // 顶点映射
    List<Edge> edges;                         // 边列表
};

struct Vertex {
    TransactionId tid;        // 事务ID
    List<Edge> outgoing;      // 出边
    List<Edge> incoming;      // 入边
    int outDegree;            // 出度（优化）
};

struct Edge {
    Vertex* from;             // 起始事务
    Vertex* to;               // 等待的事务
    ResourceId resource;      // 等待的资源
    LockType lockType;        // 锁类型
};

六、死锁处理流程

完整死锁管理流程

graph TD
    A[事务请求资源] --> B{资源可用?}
    B -->|是| C[分配资源]
    B -->|否| D[加入等待队列]
    D --> E[定期检测死锁]
    E --> F{发现死锁?}
    F -->|是| G[选择牺牲者victim]
    F -->|否| H[继续等待]
    G --> I[回滚牺牲者事务]
    I --> J[释放资源]
    J --> K[通知其他事务继续]


牺牲者选择策略

数据库系统需要选择一个事务回滚来打破死锁：

选择标准 优点 缺点

最近启动的事务 回滚代价最小 可能不公平

执行时间最短 重做成本低 需要记录时间

修改数据最少 回滚影响小 统计开销大

优先级最低 符合业务需求 需要维护优先级

随机选择 实现简单 可能选择代价大的

MySQL InnoDB的选择策略：
-- InnoDB选择回滚代价最小的事务
-- 通常选择修改数据量最小的事务作为牺牲者

九、等待图算法的局限性

1. 无法预防死锁

• 只能检测已发生的死锁

• 检测有延迟，事务可能已等待较长时间

2. 性能开销

• 频繁检测增加CPU负担

• 大并发下图规模增长快

3. 分布式环境复杂

• 全局等待图构建困难

• 网络延迟影响检测准确性

4. 资源类型限制

• 主要针对锁资源

• 对其他资源（如内存、CPU）的死锁检测有限

总结
等待图算法是数据库死锁检测的核心机制，它的作用可以概括为：
方面 说明
核心作用 检测并发事务中的循环等待，识别死锁
工作原理 构建事务等待关系的有向图，检测环路
触发方式 定期检测（秒级间隔）或请求超时触发
输出结果 识别死锁环，选择牺牲者事务回滚
系统支持 所有主流数据库都实现了此算法或其变种

关键要点：
1. 死锁的四个必要条件：互斥、持有等待、不可剥夺、循环等待
2. 等待图算法主要检测"循环等待"条件
3. 算法是被动检测，不是主动预防
4. 实际应用中需配合超时机制、锁超时等策略
5. 分布式环境下算法更复杂，需要全局协调

理解等待图算法对于诊断和解决数据库并发问题至关重要，特别是当应用出现性能瓶颈或事务失败时，死锁检测日志是重要的调试信息来源。
