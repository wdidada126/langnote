数据库 并发管理，只加锁会有一系列问题
脏读，不可重复读 幻读

您的问题很准确！是的，单纯使用基本的封锁协议确实无法完全解决所有并发问题。让我详细解释：

一、基本封锁协议的问题

基本封锁协议规则：

• 读前加共享锁（S锁）

• 写前加排他锁（X锁）

• 事务结束释放所有锁

这个简单的协议只能解决丢失更新问题，但无法解决其他三种问题。

二、具体问题分析

1. 脏读（Dirty Read）问题

场景：事务T1修改数据但未提交，事务T2读取该数据。

T1: lock-X(A)         T2: lock-S(A)等待
    write(A)              ...等待...
    unlock(A) ←--- 提前释放锁！
                    read(A) ← 读到未提交数据
    (之后T1可能回滚)
    rollback


根本原因：T1提前释放了X锁，让T2在T1提交前就读到了数据。

2. 不可重复读（Non-repeatable Read）问题

场景：同一事务两次读取同一数据，结果不同。

T1: lock-S(A)         T2: lock-X(A)等待
    read(A)=100           ...等待...
    unlock(A) ←--- 中间释放锁！
                    write(A=200)
                    commit
                    unlock(A)
    lock-S(A)
    read(A)=200 ← 与第一次读取结果不同！


根本原因：在两次读取之间释放并重新获取锁，其他事务有机会修改数据。

3. 幻读（Phantom Read）问题

场景：同一查询条件返回不同数量的行。

T1: SELECT * FROM users WHERE age > 30
    -- 返回3行
    
    T2: INSERT INTO users VALUES (..., age=35)
        COMMIT
    
T1: SELECT * FROM users WHERE age > 30
    -- 返回4行，多了"幻影"行！


根本原因：范围查询无法用行锁保护，新插入的行不在原有锁定范围内。

三、解决方案：隔离级别 + 锁协议

数据库通过隔离级别配合不同的锁协议变种来解决这些问题：

四种隔离级别对比

隔离级别 脏读 不可重复读 幻读 实现机制

READ UNCOMMITTED ❌ 可能发生 ❌ 可能发生 ❌ 可能发生 不加锁或最小锁

READ COMMITTED ✅ 防止 ❌ 可能发生 ❌ 可能发生 语句级锁，读后立即释放

REPEATABLE READ ✅ 防止 ✅ 防止 ❌ 可能发生 事务级锁，事务结束释放

SERIALIZABLE ✅ 防止 ✅ 防止 ✅ 防止 范围锁/表锁，严格2PL

四、详细解决方案

1. 防止脏读：严格2PL（Strict 2PL）

规则：排他锁（X锁）必须在事务提交后才释放。
-- MySQL示例：使用REPEATABLE READ或更高级别
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
-- T1持有X锁直到提交
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- 此时其他事务无法读取此行
COMMIT; -- 提交后才释放锁


2. 防止不可重复读：保持读锁

方案1：使用REPEATABLE READ隔离级别，共享锁在事务结束前不释放。

方案2：使用SELECT ... FOR UPDATE（悲观锁）
BEGIN;
-- 第一次读取并加锁
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- ...执行其他操作...
-- 第二次读取，数据不会变
SELECT * FROM accounts WHERE id = 1;
COMMIT;


3. 防止幻读：范围锁/间隙锁

MySQL InnoDB的解决方案：在REPEATABLE READ级别下自动加间隙锁。
-- 假设表中有age=20,30,40的记录
BEGIN;
-- 不仅锁住age>30的现有行(40)
-- 还锁住(30,40)和(40,+∞)的间隙
SELECT * FROM users WHERE age > 30 FOR UPDATE;

-- 其他事务无法在间隙插入数据
-- INSERT INTO users (age=35)会被阻塞


五、实际数据库的实现差异

MySQL InnoDB

-- 查看当前隔离级别
SELECT @@transaction_isolation;

-- 设置隔离级别
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- InnoDB在REPEATABLE READ下就防止了幻读（通过间隙锁）
-- 但SQL标准中幻读要到SERIALIZABLE才防止


PostgreSQL

-- PostgreSQL的MVCC实现有所不同
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- 使用快照隔离，不会看到其他事务的修改
SELECT * FROM table WHERE condition;


SQL Server

-- SQL Server需要明确指定锁提示
BEGIN TRANSACTION;
SELECT * FROM table WITH (HOLDLOCK, ROWLOCK) WHERE condition;
-- HOLDLOCK相当于保持共享锁直到事务结束
COMMIT;


六、锁的权衡与选择

锁粒度与性能权衡

-- 行级锁：并发度高，但锁开销大
SELECT * FROM table WHERE id = 1 FOR UPDATE;

-- 表级锁：并发度低，但管理简单
LOCK TABLE table IN EXCLUSIVE MODE;


死锁风险

-- 事务1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- 事务2（反向顺序，可能导致死锁）
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 2;
UPDATE accounts SET balance = balance + 100 WHERE id = 1;


解决方案：按固定顺序访问资源。

七、现代解决方案：MVCC

许多现代数据库使用多版本并发控制（MVCC） 而不是纯锁机制：

MVCC工作原理

1. 写不阻塞读：读操作读取旧版本
2. 读不阻塞写：写操作创建新版本
3. 版本链管理：每个数据项维护多个版本

MVCC vs 锁机制

方面 基于锁 MVCC

读性能 读-写冲突 读不阻塞写，性能好

写性能 写-写冲突 写冲突检测代价

隔离级别 4种标准级别 通常提供快照隔离

实现复杂度 相对简单 版本管理复杂

总结

1. 基本封锁协议不够：只能解决丢失更新
2. 需要严格2PL：防止脏读
3. 需要保持锁：防止不可重复读  
4. 需要范围锁：防止幻读
5. 隔离级别是平衡：在并发度和一致性间权衡
6. 现代数据库多用MVCC：提供更好的并发性能

最佳实践：
• 默认使用REPEATABLE READ（MySQL）或READ COMMITTED（PostgreSQL）

• 明确需要时使用SELECT ... FOR UPDATE

• 事务尽量简短，减少锁持有时间

• 按固定顺序访问资源，避免死锁
