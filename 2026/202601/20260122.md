ARIES 恢复算法全面解析
IBM数据库恢复的原型算法
ARIES（Algorithms for Recovery and Isolation Exploiting Semantics）是IBM数据库采用的恢复算法原型，属于数据库恢复技术领域的算法。该算法基于ACID原则设计，提供事务失效与系统失效后的恢复机制，依赖预写日志（WAL）的日志序列号（LSN）机制保障数据一致性。
ARIES恢复流程包含三个阶段：分析阶段 通过扫描检查点后的日志识别未完成事务与脏页，Redo阶段 从检查点开始重做所有操作至崩溃前状态，Undo阶段逆向回滚未提交事务修改。算法采用steal/no-force恢复策略，支持事务提交前刷新脏页且提交后不强制刷盘。核心数据结构包含flushed-LSN、page-LSN和rec-LSN，并利用模糊检查点机制降低恢复开销。在撤销操作中生成补偿日志记录（CLR）以避免重复回滚。

一、历史背景与发展
1.1 诞生背景
ARIES (Algorithm for Recovery and Isolation Exploiting Semantics) 算法由IBM研究院的C. Mohan等人于1992年提出，是为了解决传统恢复算法的局限性：
• 传统方法问题：Shadow Paging性能差，Write-Ahead Logging(WAL)恢复效率低
• 市场需求：90年代数据库系统需要支持高并发、高可用性
• 技术驱动：OLTP系统对故障恢复时间和数据一致性要求越来越高

1.2 发展历程
1992: ARIES首次发表（VLDB会议）
1993: ARIES/IM（索引管理扩展）
1995: ARIES/KVL（键值锁扩展）
2000+: 成为工业标准，被DB2、SQL Server等主流数据库采用

enum class LogType {
    UPDATE = 1,     // 数据更新
    COMPENSATE = 2, // 补偿日志记录(CLR)
    COMMIT = 3,     // 事务提交
    ABORT = 4,      // 事务中止
    CHECKPOINT = 5  // 检查点

struct LogRecord {
    lsn_t lsn_;              // 日志序列号
    lsn_t prev_lsn_;         // 同一事务前一条日志LSN
    xid_t xid_;             // 事务ID
    LogType type_;          // 日志类型
    page_id_t page_id_;     // 影响的页面
    // 物理日志：页面偏移、旧值、新值
    // 逻辑日志：操作类型、参数
};

3.2 三个核心阶段

阶段1：分析阶段 (Analysis Phase)

class AnalysisPhase {
public:
    RecoveryInfo Analyze() {
        // 1. 从最新检查点开始
        CheckpointRecord checkpoint = ReadMasterRecord();
        
        // 2. 初始化事务表和脏页表
        att_ = checkpoint.att_;
        dpt_ = checkpoint.dpt_;
        
        // 3. 扫描日志到末尾
        for (lsn_t lsn = checkpoint.checkpoint_lsn_ + 1; lsn <= end_lsn_; lsn++) {
            LogRecord log = ReadLog(lsn);
            ProcessLogRecord(log);
        }
        
        return {att_, dpt_, redo_start_lsn_};
    }
    
private:
    void ProcessLogRecord(const LogRecord& log) {
        switch (log.type_) {
            case LogType::UPDATE:
                UpdateATT(log.xid_, log.lsn_);
                UpdateDPT(log.page_id_, log.lsn_);
                break;
            case LogType::COMMIT:
                RemoveFromATT(log.xid_);
                break;
            case LogType::ABORT:
                MarkForUndo(log.xid_);
                break;
            case LogType::COMPENSATE:
                // CLR特殊处理
                ProcessCLR(log);
                break;
        }
    }
};


阶段2：重做阶段 (Redo Phase)

class RedoPhase {
public:
    void Redo(lsn_t redo_start_lsn) {
        // 从脏页表最小LSN开始重做
        lsn_t start_lsn = CalculateRedoStartLSN();
        
        for (lsn_t lsn = start_lsn; lsn <= end_lsn_; lsn++) {
            LogRecord log = ReadLog(lsn);
            
            if (NeedRedo(log)) {
                ApplyRedo(log);
            }
        }
    }
    
private:
    bool NeedRedo(const LogRecord& log) {
        // 条件1：是更新日志
        if (log.type_ != LogType::UPDATE) return false;
        
        // 条件2：页面在脏页表中
        if (dpt_.find(log.page_id_) == dpt_.end()) return false;
        
        // 条件3：日志LSN ≥ 页面第一次脏的LSN
        // 条件4：页面当前LSN < 日志LSN（避免重复重做）
        Page* page = buffer_pool_->GetPage(log.page_id_);
        return page->GetLSN() < log.lsn_;
    }
};


阶段3：回滚阶段 (Undo Phase)

class UndoPhase {
public:
    void Undo() {
        // 1. 收集需要回滚的事务（分析阶段确定的）
        std::vector<xid_t> losers = CollectLoserTransactions();
        
        // 2. 按LSN倒序回滚
        std::priority_queue<lsn_t> undo_queue;
        for (xid_t xid : losers) {
            undo_queue.push(att_[xid].last_lsn_);
        }
        
        while (!undo_queue.empty()) {
            lsn_t lsn = undo_queue.top();
            undo_queue.pop();
            
            LogRecord log = ReadLog(lsn);
            UndoLogRecord(log);
            
            // 记录CLR并继续前一条日志
            if (log.prev_lsn_ != INVALID_LSN) {
                undo_queue.push(log.prev_lsn_);
            }
        }
    }
    
private:
    void UndoLogRecord(const LogRecord& log) {
        // 1. 执行实际回滚操作
        ApplyUndo(log);
        
        // 2. 记录补偿日志(CLR)
        lsn_t clr_lsn = WriteCompensationLog(log);
        
        // 3. 更新事务最后LSN
        att_[log.xid_].last_lsn_ = clr_lsn;
    }
};

一、优先图（串行化图）的完整定义
优先图（Precedence Graph）也叫串行化图（Serialization Graph），是一种用于判断调度是否冲突可串行化（Conflict Serializable）的有向图。

1. 图的结构定义
给定调度S，其优先图G(S) = (V, E)：
• 顶点V：调度S中每个提交的事务（通常忽略中止的事务）
• 边E：对于任意两个事务Tᵢ和Tⱼ，如果满足：
  1. Tᵢ在Tⱼ之前执行了某个操作
  2. 这个操作与Tⱼ的某个操作冲突
  则存在有向边 Tᵢ → Tⱼ

2. 冲突操作的条件
两个操作冲突（conflict）需要同时满足：
1. 操作涉及同一数据项
2. 至少有一个是写操作
3. 来自不同的事务

具体冲突类型：
• 读-写冲突：Rᵢ(X) 和 Wⱼ(X)
• 写-读冲突：Wᵢ(X) 和 Rⱼ(X)  
• 写-写冲突：Wᵢ(X) 和 Wⱼ(X)

注意：读-读操作不冲突。
二、优先图构建算法
1. 构建步骤
def build_precedence_graph(schedule_S):
    # 步骤1：识别所有事务
    transactions = extract_transactions(schedule_S)
    
    # 步骤2：创建图节点
    graph = {T: set() for T in transactions}
    
    # 步骤3：遍历调度，检测冲突边
    for i in range(len(schedule_S)):
        for j in range(i+1, len(schedule_S)):
            op_i = schedule_S[i]  # 操作i: T₁的操作
            op_j = schedule_S[j]  # 操作j: Tⱼ的操作
            
            # 检查是否冲突
            if are_conflicting(op_i, op_j):
                # Tᵢ在Tⱼ之前，添加边 Tᵢ → Tⱼ
                graph[op_i.transaction].add(op_j.transaction)
    
    return graph

def are_conflicting(op1, op2):
    # 相同事务内的操作不冲突
    if op1.transaction == op2.transaction:
        return False
    
    # 不同数据项不冲突
    if op1.data_item != op2.data_item:
        return False
    
    # 检查操作类型组合
    return (op1.type == 'W' or op2.type == 'W')


2. 示例分析

调度S₁：

R₁(A) → W₁(A) → R₂(A) → W₂(A) → R₁(B) → W₁(B) → R₂(B) → W₂(B)


构建优先图：
1. 冲突1：W₁(A) 和 R₂(A) 冲突 → 边：T₁ → T₂
2. 冲突2：W₂(A) 和 R₁(B) 不冲突（不同数据项）
3. 冲突3：W₁(B) 和 R₂(B) 冲突 → 边：T₁ → T₂（已存在）
4. 冲突4：W₂(B) 和 后面无操作

优先图：

T₁ ───→ T₂


三、冲突可串行化判断定理
核心定理：
调度S是冲突可串行化的 ⇔ 其优先图G(S)是无环的
证明思路：
• 如果G(S)无环，可以拓扑排序得到等价的串行调度
• 如果G(S)有环，说明存在循环依赖，无法找到等价串行调度

示例：判断调度是否冲突可串行化
调度S₂：
R₁(X) → R₂(X) → W₁(X) → W₂(X)

构建优先图：
1. R₁(X) 和 W₂(X) 冲突 → T₁ → T₂
2. R₂(X) 和 W₁(X) 冲突 → T₂ → T₁

优先图：
T₁ ←──→ T₂  （形成环）
结论：S₂不是冲突可串行化的，因为存在环。

四、优先图与两阶段封锁（2PL）的关系
重要定理：
如果一个调度遵守严格两阶段封锁协议，那么它的优先图一定是无环的。
证明：
• 在2PL下，事务必须按顺序获取和释放锁
• 如果有Tᵢ → Tⱼ的边，意味着Tᵢ先获取了锁
• Tⱼ必须等待Tᵢ释放锁，不可能出现反向边
• 因此不会形成环

五、优先图在死锁检测中的应用
优先图也可用于死锁检测（作为等待图的变种）：
等待图（Wait-for Graph）
• 顶点：事务
• 边：Tᵢ → Tⱼ 表示 Tᵢ正在等待Tⱼ释放锁
• 环检测：存在环表示死锁

示例：
事务T₁：持有锁A，等待锁B
事务T₂：持有锁B，等待锁A
等待图：T₁ → T₂ → T₁ （环！）

1. 增量检测：只检查新加入的操作
2. 启发式剪枝：忽略不可能形成环的操作

八、扩展：视图可串行化
优先图主要用于冲突可串行化。对于更一般的视图可串行化，判断更复杂：
视图可串行化条件
调度S是视图可串行化的，如果存在串行调度S'使得：
1. 初始读一致：每个读操作读取相同事务的写
2. 最终写一致：每个数据项的最终写操作相同
视图可串行化 ⊃ 冲突可串行化

九、代码实现示例
from collections import defaultdict, deque

class PrecedenceGraph:
    def __init__(self):
        self.graph = defaultdict(set)  # 邻接表
        self.transactions = set()
    
    def add_conflict(self, Ti, Tj):
        """添加冲突边 Ti → Tj"""
        if Ti != Tj:
            self.graph[Ti].add(Tj)
            self.transactions.add(Ti)
            self.transactions.add(Tj)
    
    def is_serializable(self):
        """检查是否冲突可串行化（是否有环）"""
        return not self.has_cycle()
    
    def has_cycle(self):
        """检测图中是否有环（DFS）"""
        visited = set()
        recursion_stack = set()
        
        def dfs(node):
            visited.add(node)
            recursion_stack.add(node)
            
            for neighbor in self.graph.get(node, []):
                if neighbor not in visited:
                    if dfs(neighbor):
                        return True
                elif neighbor in recursion_stack:
                    return True
            
            recursion_stack.remove(node)
            return False
        
        for node in self.transactions:
            if node not in visited:
                if dfs(node):
                    return True
        return False
    
    def topological_order(self):
        """获取拓扑排序（如果无环）"""
        if self.has_cycle():
            return None
        
        in_degree = defaultdict(int)
        for u in self.graph:
            for v in self.graph[u]:
                in_degree[v] += 1
        
        # 入度为0的节点入队
        queue = deque([v for v in self.transactions if in_degree[v] == 0])
        result = []
        
        while queue:
            u = queue.popleft()
            result.append(u)
            
            for v in self.graph.get(u, []):
                in_degree[v] -= 1
                if in_degree[v] == 0:
                    queue.append(v)
        
        return result if len(result) == len(self.transactions) else None
    
    def analyze_schedule(self, schedule):
        """分析调度并构建优先图"""
        # 简化的分析：假设schedule是操作列表
        # 格式: [(T_id, op_type, data_item), ...]
        # op_type: 'R' 或 'W'
        
        last_write = {}  # 数据项的最后写入事务
        
        for i, (Ti, op_i, data_i) in enumerate(schedule):
            if op_i == 'W':
                # 写操作：与后续的所有读写冲突
                for j in range(i+1, len(schedule)):
                    Tj, op_j, data_j = schedule[j]
                    if data_i == data_j and Ti != Tj:
                        self.add_conflict(Ti, Tj)
                last_write[data_i] = Ti
                
            elif op_i == 'R':
                # 读操作：只与后续的写冲突
                for j in range(i+1, len(schedule)):
                    Tj, op_j, data_j = schedule[j]
                    if data_i == data_j and op_j == 'W' and Ti != Tj:
                        self.add_conflict(Ti, Tj)


十、总结
1. 优先图（串行化图）是判断调度冲突可串行化的核心工具
2. 核心定理：调度冲突可串行化 ⇔ 优先图无环
3. 构建规则：基于操作之间的冲突关系
4. 应用场景：
   • 并发控制理论分析
   • 数据库优化器调度选择
   • 死锁检测和预防

优先图为理解数据库事务的并发执行提供了清晰的数学模型，是现代数据库并发控制理论的基石之一。
