IBM System R 是一个作为研究项目而创建的数据库系统，该项目始于1974年的IBM圣何塞研究实验室。
System R 是一个具有开创性的项目，该项目是SQL 语言的第一次实现，从此SQL便成为标准关系型数据库查询语言。System R 也是第一个论证了关系型数据库管理系统能够提供良好的事务处理性能。System R 中的设计决策以及一些基本的选择算法（例如查询优化中的动态规划算法）对后来的关系型系统有巨大的影响。

Redo日志和Undo日志是数据库事务恢复的核心机制，两者协同工作确保ACID特性。以下是主流数据库（以MySQL InnoDB为例）的日志格式详解。

一、Redo日志格式

物理Redo日志格式（InnoDB）
| Log Type (1B) | Space ID (4B) | Page Number (4B) | Data (变长) | LSN (8B) |

具体字段说明：
• Log Type：操作类型（MLOG_1BYTE、MLOG_2BYTE、MLOG_4BYTE、MLOG_8BYTE、MLOG_WRITE_STRING）
• Space ID：表空间ID
• Page Number：页号
• Data：修改数据（物理字节）
• LSN：日志序列号，用于恢复顺序

示例：更新一行数据
MLOG_4BYTE | 0x0001 | 0x00000001 | 0x12345678 | 0x0000000000001000
表示在表空间1的页1上，将某个4字节字段更新为0x12345678。
逻辑Redo日志格式（部分数据库）

| Transaction ID | Operation | Table | Row ID | Old Value | New Value |

二、Undo日志格式
InnoDB Undo日志格式

| Undo Log Header (56B) | Undo Record (变长) |

Undo Log Header字段：
• TRX_ID：事务ID（8B）
• TRX_UNDO_ID：Undo日志ID（8B）
• TRX_UNDO_NEXT：下一个Undo记录指针（8B）
• TRX_UNDO_PREV：前一个Undo记录指针（8B）
• TRX_UNDO_LAST_LOG：最后一个Undo记录（8B）
• TRX_UNDO_STATE：Undo日志状态（2B）
• TRX_UNDO_XID：XID事务标识符（140B）
Undo Record格式：
| Type (1B) | Next Offset (2B) | Data (变长) |

操作类型：
• TRX_UNDO_INSERT_REC：插入操作
• TRX_UNDO_DELETE_MARK_REC：删除操作
• TRX_UNDO_UPDATE_REC：更新操作

Undo日志示例
插入操作Undo记录：
TRX_UNDO_INSERT_REC | 0x0010 | 主键值 | 各列旧值
表示需要删除该行数据。
更新操作Undo记录：
TRX_UNDO_UPDATE_REC | 0x0020 | 主键值 | 被修改列的旧值
表示需要将数据恢复为旧值。
三、Redo与Undo的协同工作

事务执行流程
1. 开始事务：分配事务ID，记录开始LSN
2. 数据修改：
   • 记录Undo Log（修改前的值）
   • 修改数据页（内存中）
   • 记录Redo Log（修改后的值）
3. 提交事务：
   • 将Redo Log强制刷盘（fsync）
   • 标记Undo Log为可清理
4. 回滚事务：根据Undo Log逆向恢复数据

系统恢复流程
1. 分析阶段：确定需要重做和回滚的事务
2. 重做阶段：从检查点开始，重做所有已提交事务的Redo Log
3. 回滚阶段：回滚所有未提交事务的Undo Log

数据库 Redo日志类型 Undo日志存储 特点

五、性能优化建议
1. Redo日志大小：合理设置日志文件大小，避免频繁切换
2. Undo表空间：监控Undo空间使用，避免空间不足
3. 事务长度：控制事务大小，减少日志量
4. 批量操作：使用批量提交减少日志开销

总结：Redo日志记录"重做"信息，确保持久性；Undo日志记录"撤销"信息，确保原子性。两者共同保障数据库在故障后能够恢复到一致状态。

redo日志须用物理日志
Undo日志须用逻辑日志

每次执行undo日志记录后，数据库需要向日志中写入一条补偿日志记录（compensation log record，CLR），记录撤销的动作
CLR实现了undo日志的redo，记录已经undo的日志，保证undo不被重复执行

ARIES是一种state-of-the-art的恢复算法
IBM的，DB2上的
ARIES算法基于undo/redo日志的恢复算法缺陷

ARIES（Algorithms for Recovery and Isolation Exploiting Semantics）是IBM数据库采用的恢复算法原型，属于数据库恢复技术领域的算法。该算法基于ACID原则设计，提供事务失效与系统失效后的恢复机制，依赖预写日志（WAL）的日志序列号（LSN）机制保障数据一致性。

ARIES恢复流程包含三个阶段：分析阶段通过扫描检查点后的日志识别未完成事务与脏页，Redo阶段从检查点开始重做所有操作至崩溃前状态，Undo阶段逆向回滚未提交事务修改。算法采用steal/no-force恢复策略，支持事务提交前刷新脏页且提交后不强制刷盘。核心数据结构包含flushed-LSN、page-LSN和rec-LSN，并利用模糊检查点机制降低恢复开销。在撤销操作中生成补偿日志记录（CLR）以避免重复回滚。
