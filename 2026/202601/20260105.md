Serializable Snapshot Isolation (SSI) 是由 Michael Cahill 等人在 2008–2009 年提出的理论（论文：Serializable Isolation for Snapshot Databases），PostgreSQL 是第一个（也是目前最著名和最成熟的）将其实际应用到生产级数据库中的系统。

PostgreSQL从9.1版本（2011 年）开始正式引入SSI，作为其 SERIALIZABLE 隔离级别的实现方式，至今（2025 年底，PostgreSQL 18 仍在使用）没有重大改变，性能和稳定性都经过了十多年的大规模生产验证。

### PostgreSQL中的SSI实现特点
- 基于 MVCC（多版本并发控制） + 快照隔离（Snapshot Isolation） 基础
- 在提交时通过检测 rw-冲突（读-写冲突） 和 危险结构（dangerous structure） 来判断是否存在序列化异常（主要是 write-skew）
- 一旦检测到异常，就回滚其中一个事务（抛出 serialization_failure 错误），应用层需重试
- 优点：读不阻塞写，写不阻塞读，性能接近普通 Snapshot Isolation（Repeatable Read），远优于传统严格两阶段锁（S2PL）在读密集场景
- 缺点：可能有较多序列化失败回滚（需要应用配合重试逻辑），对长事务/热点数据敏感
- 当前状态（2025 年）：依然是官方推荐的 SERIALIZABLE 实现，没有计划替换为 S2PL 或其他方式

### 其他主流数据库的 SSI 实现情况对比（2025 年现状）

| 数据库              | 是否实现 SSI                          | SERIALIZABLE 实现方式                          | 默认隔离级别          | 备注 / 特点                                                                 |
|---------------------|---------------------------------------|------------------------------------------------|-----------------------|-----------------------------------------------------------------------------|
| PostgreSQL      | 是（首个生产级实现）              | SSI（Serializable Snapshot Isolation）     | Read Committed        | 最成熟、最广泛使用的 SSI 实现，性能优秀，社区活跃                           |
| Oracle          | 否                                    | 传统 Snapshot Isolation（但 Oracle 称其为 SERIALIZABLE） | Snapshot Isolation    | 历史上最早大规模用 SI 的数据库，但不防 write-skew，实际不是真可串行化      |
| Microsoft SQL Server | 否                                | Snapshot Isolation + 读写锁（可选 READ COMMITTED SNAPSHOT） | Read Committed        | 有单独的 SNAPSHOT 级别；SERIALIZABLE 用传统锁实现                           |
| MySQL (InnoDB)  | 否                                    | Repeatable Read（带 gap lock/next-key lock 防幻读）接近可串行化 | Repeatable Read       | 不提供真正的 SERIALIZABLE（官方文档称 Repeatable Read 接近，但有差异）      |
| CockroachDB     | 否                                    | 严格 SERIALIZABLE（基于分布式共识 + 锁/时间戳） | SERIALIZABLE          | 只支持 SERIALIZABLE（默认且唯一），不提供更弱级别，性能依赖分布式特性       |
| YugabyteDB      | 否（讨论过，但未实现）                | Snapshot（Repeatable Read） + Serializable（基于锁/意图锁） | Snapshot              | YSQL 兼容 PostgreSQL 语法，但 SERIALIZABLE 用锁实现，非 SSI；曾有 issue 讨论引入 SSI 但未落地 |
| TiDB            | 否                                    | Serializable（基于 Percolator + 悲观/乐观混合锁） | Repeatable Read       | 类似 Google Spanner 的实现，非纯 SSI                                        |
| Spanner / Cloud Spanner | 否                            | TrueTime + 两阶段提交 + 锁                 | SERIALIZABLE          | Google 内部最早实现分布式真可串行化，非 SSI                                 |

### 总结与关键点
- PostgreSQL 是目前唯一主流关系型数据库真正把 SSI 作为 SERIALIZABLE 官方实现 的系统，并且保持了 14 年以上（从 9.1 到 18），证明了其可靠性和实用性。
- 其他数据库大多选择：
  - 传统 S2PL（严格两阶段锁）来实现真 SERIALIZABLE（并发度较低）
  - 或干脆用 Snapshot Isolation 并称其为“足够好”（Oracle 的历史做法）
  - 分布式数据库（如 CockroachDB、YugabyteDB、TiDB）倾向于用时间戳/共识协议 + 锁来实现真可串行化，而非依赖 SSI 的冲突检测回滚机制（因为分布式环境重试成本更高）。
- SSI 的最大优势是高并发 + MVCC 友好，但需要应用层有重试机制（PostgreSQL 社区推荐在 SERIALIZABLE 事务外包一层 retry loop）。

如果你在实际项目中考虑用 SERIALIZABLE 隔离级别，PostgreSQL + SSI 仍然是目前最平衡、最成熟的选择，尤其适合读多写少或中等并发场景。

Undo Log 版本链（也叫回滚段/版本链/row history chain）是主流数据库实现 MVCC（多版本并发控制） 时最常见的两种方式之一，主要用于支持一致性读（非阻塞读）和事务回滚。

主流数据库对这个机制的实现方式有两大派系，区别非常明显：

| 数据库              | 是否使用 Undo Log + 版本链                  | 实现方式核心描述                                                                 | 存储方式                              | 读旧版本方式                          | 优点                                      | 缺点/代价                                 | 垃圾回收机制                  |
|---------------------|---------------------------------------------|----------------------------------------------------------------------------------|---------------------------------------|---------------------------------------|-------------------------------------------|-------------------------------------------|-------------------------------|
| MySQL (InnoDB)  | 是（经典 Undo Log + 版本链）            | 当前最新版本存在数据页中，通过 roll_pointer 指向 undo log 中的上一个版本，形成链 | 最新版本在表空间，旧版本在 undo tablespace | 读时顺着 roll_pointer 链逐层回滚重建旧版本 | 空间效率高（只存变更列差值），写放大小   | 读旧版本需 IO 回滚重建，链长时性能下降    | purge 线程后台清理            |
| Oracle          | 是（Rollback Segment / Undo Segment）   | 类似 InnoDB，使用 undo segment 存旧版本，当前版本在表中，链式指向               | 最新版本在表，旧版本在 undo tablespace | 顺链动态重建旧版本                | 非常适合长事务 + 一致性读，优化好时性能高 | undo 表空间可能爆掉，长事务风险大         | Undo retention + 自动回收     |
| PostgreSQL      | 否（不使用 Undo Log）                   | 全行版本化：更新时直接生成新行（tuple），旧行保留在原表页中，xmax 标记删除 | 所有版本（新旧）都物理存在在表 heap 中 | 通过 xmin/xmax + 事务快照直接判断可见性，无需重建 | 读性能极高（无回滚开销），实现简单       | 空间膨胀严重（bloat），更新多时表巨大 | VACUUM / autovacuum 清理      |
| SQL Server      | 部分（Snapshot Isolation 用 row versioning） | 启用 snapshot 时类似 PostgreSQL，旧版本存 tempdb；默认用锁                     | 旧版本在 tempdb（临时表空间）         | 读 tempdb 中的版本                    | 灵活（可开关），tempdb 独立管理           | tempdb 压力大，高并发下 IO 瓶颈           | 版本清理后台线程              |
| TiDB / CockroachDB | 否（类似 PostgreSQL，但分布式）       | 分布式 MVCC，通常基于时间戳 + 全版本存储或混合方式                              | 版本分散在 RocksDB 等 KV 存储中       | 通过时间戳判断可见版本                | 分布式扩展性好                            | 版本管理复杂，GC 压力大                   | 分布式 GC                     |

### 两大主流实现思路对比（2025 年现状）

1. Undo Log + 版本链派（MySQL InnoDB / Oracle）
   - 存储逻辑：表中只存最新提交版本，所有历史版本存在独立的 undo/rollback 段中，通过 roll_pointer（7 字节指针）串成链表。
   - 读过程：一致性读时，如果当前行版本不可见，就顺着 roll_pointer 往回走，逐层应用 undo 记录重建旧版本。
   - 优点：更新时写放大小（只写变更 + undo），索引维护简单（索引指向最新版本）。
   - 缺点：读旧版本需要 IO + CPU 重建，undo 链过长时性能急剧下降；长事务会导致 undo 爆表空间。
   - 典型场景：OLTP + 长一致性读（如报表）。

2. 全行版本化派（PostgreSQL 代表）
   - 存储逻辑：更新/删除时直接插入新 tuple，旧 tuple 保留在原页中，通过 xmin（创建事务ID） 和 xmax（删除/更新事务ID） 控制可见性。
   - 读过程：直接读取表页，根据事务快照（活跃事务列表）判断该 tuple 是否可见，完全不需要重建。
   - 优点：读性能最高（无额外 IO），适合读多写少的场景。
   - 缺点：空间膨胀（bloat）严重，每更新一次就多一行；需要频繁 VACUUM 回收。
   - 典型场景：复杂查询 + OLAP 混合负载。

### 快速记忆口诀

- MySQL/Oracle → “Undo 链回滚”：最新在表，旧的在 undo，读要“倒带”
- PostgreSQL → “全版本躺平”：新旧都在表里，读时“挑着看”，扫地阿姨（VACUUM）辛苦

### 2025 年最新趋势
- MySQL 8.0+：undo tablespace 独立管理，可多表空间，purge 优化更好，但本质仍是 Undo Log 链。
- PostgreSQL 17/18：autovacuum 更智能，toast 压缩更好，但膨胀问题依然存在（社区仍在优化）。
- 分布式数据库（TiDB、CockroachDB、Yugabyte）大多借鉴 PostgreSQL 风格的全版本 + 时间戳，避免 undo 链在分布式环境下的复杂 GC。

总结一句话：  
如果你在意读性能和简单性 → 选 PostgreSQL 风格  
如果你在意空间效率和长事务 → 选 InnoDB/Oracle 风格的 Undo Log 版本链

### JDK 动态代理概述
JDK 动态代理（Dynamic Proxy）是 Java 反射机制的一部分，用于在运行时动态生成代理类，实现接口的方法拦截和增强。主要通过 `java.lang.reflect.Proxy` 类实现。

- 工作原理：
  - 使用 `Proxy.newProxyInstance(ClassLoader loader, Class<?>[] interfaces, InvocationHandler h)` 创建代理实例。
  - 内部生成代理类的字节码（通过 `sun.misc.ProxyGenerator`），然后由指定类加载器加载。
  - 生成的代理类名称通常如 `com.sun.proxy.$Proxy0`，实现指定接口的所有方法。
  - 调用代理方法时，会委托到 `InvocationHandler.invoke(Object proxy, Method method, Object[] args)` 方法中执行自定义逻辑。
  - 如果相同接口集的代理类已存在于类加载器中，则复用；否则新建并定义。

- 与序列化/反序列化的关系：
  - 动态代理类支持序列化（实现 `Serializable` 接口），但在反序列化时，可能触发 `InvocationHandler` 的方法调用。
  - 在漏洞利用中，常用于 gadget chain 的起点：反序列化代理对象时，某些方法（如 `hashCode()`、`equals()`）被自动调用，导致链式触发恶意代码。

- 类加载方面：
  - 代理类是动态生成的字节码，直接由类加载器（如系统类加载器）加载，无需额外文件。
  - 在漏洞场景中，如果涉及自定义类加载器（如 `URLClassLoader`），可用于加载远程恶意类，但标准动态代理不直接涉及。

### Java 反序列化漏洞概述

Java 反序列化漏洞（CWE-502: Deserialization of Untrusted Data）指应用从不可信源读取序列化数据时，未验证对象类型，导致远程代码执行（RCE）、拒绝服务（DoS）等。 核心问题是 `ObjectInputStream.readObject()` 会调用对象的 `readObject()` 方法，可能执行恶意逻辑。

- 常见攻击方式：使用 "gadget chains"（小工具链），即一组可序列化类的嵌套组合，反序列化时链式调用方法，最终执行命令。
- 工具：ysoserial 是经典工具，生成各种 payload，包括 CC 链。
- 防御：JDK 9+ 引入 JEP 290（序列化过滤器），允许白名单/黑名单类；子类化 `ObjectInputStream` 重写 `resolveClass()` 检查类名。 Java 17+ 加强反射限制，禁止访问内部 JDK 类。

### CC 链（Commons Collections Gadget Chains）

CC 链利用 Apache Commons Collections 库中的 Transformer 和 Map 类，实现方法动态调用和代码执行。需要库在 classpath 中（如 commons-collections 3.1）。这些链在 ysoserial 中实现，用于反序列化攻击。 常与动态代理结合，触发 `InvocationHandler.invoke()`。

#### CC1 链
- 机制：使用 `InvokerTransformer`（动态方法调用）、`ChainedTransformer`（链式变换器）和 `ConstantTransformer`（常量返回）。结合 `LazyMap`（懒加载 Map）和动态代理，反序列化时触发 `LazyMap.get()`，执行链式反射调用，最终到 `Runtime.exec()`。
- 详细流程（以 ysoserial CommonsCollections1 为例）：
  1. 反序列化 `AnnotationInvocationHandler` 对象，其 `readObject()` 调用 `memberValues.entrySet()`。
  2. `memberValues` 是动态代理（`$Proxy0`，实现 `Map` 接口），调用方法委托到 `InvocationHandler.invoke()`。
  3. `invoke()` 中调用 `memberValues.get(key)`（`memberValues` 是嵌套的 `LazyMap`）。
  4. `LazyMap.get(key)` 未找到值，调用 `ChainedTransformer.transform(key)`。
  5. 链式 Transformer：
     - `ConstantTransformer` 返回 `Runtime.class`。
     - `InvokerTransformer` 调用 `getMethod("getRuntime", ...)`。
     - `InvokerTransformer` 调用 `invoke(null, ...)` 获取 `Runtime` 实例。
     - `InvokerTransformer` 调用 `exec(command)` 执行命令。
- 与动态代理关系：代理用于拦截方法调用，触发 `invoke()` 和后续链。
- 类加载方面：不直接加载新类，但依赖反射调用现有类（如 `Runtime`）。如果链涉及 `TemplatesImpl`，可加载字节码。
- 前提：commons-collections 3.1；JDK ≤ 8u72（之后 `memberValues` 类型固定为 `LinkedHashMap`）。  

#### CC3 链
- 机制：类似 CC1，使用 `InvokerTransformer` 和 `LazyMap` 或 `TiedMapEntry`（绑定 Map 条目）。通过属性访问或方法调用触发执行，常涉及 Map/List 操作。
- 与动态代理关系：集成代理来处理反序列化时的方法调用。
- 类加载方面：可能通过反射动态加载类在链中。
- 前提：commons-collections 3.1；适用于无反序列化保护的 Java 环境。

#### CC6 链
- 机制：使用 `InvokerTransformer`、`ChainedTransformer` 和 `LazyRef`（懒引用）或 Map 装饰器。延迟方法调用直到属性访问，反序列化时执行命令。
- 与动态代理关系：代理机制用于在反序列化中调用方法，启动 gadget 执行。
- 类加载方面：支持通过反射的动态类加载。
- 前提：commons-collections 3.1；目标 JDK < 8u121/7u131。

### 类加载相关补充

- Java 类加载机制：由类加载器（Bootstrap、Extension、Application）负责加载 .class 文件。双亲委派模型确保核心类优先加载。
- 在反序列化漏洞中的作用：
  - Gadget 如 `TemplatesImpl`（Xalan 库）使用 `defineClass` 加载恶意字节码，反序列化时调用 `getOutputProperties()` 执行静态初始化块。 
  - CC 链中较少直接用类加载，但反射（如 `InvokerTransformer`）可间接调用 `Class.forName()` 或加载器方法。
  - Java 17+ 限制反射访问内部类，影响链如 TemplatesImpl。

- 防御建议：
  - 使用 `ObjectInputFilter` 白名单类。
  - 避免 commons-collections 旧版。
  - 升级 JDK 并启用 `--illegal-access=deny`。

| 链类型 | 关键组件 | JDK 版本限制 | 库要求 |
|--------|----------|--------------|--------|
| CC1   | LazyMap + ChainedTransformer + InvokerTransformer | ≤ 8u72 | commons-collections 3.1 |
| CC3   | LazyMap/TiedMapEntry + InvokerTransformer | 无保护环境 | commons-collections 3.1 |
| CC6   | LazyRef/Map Decorator + InvokerTransformer | < 8u121 | commons-collections 3.1 |

MySQL 的 MDL 锁（Metadata Lock / 元数据锁） 是 MySQL Server 层实现的一种非常重要的保护机制，从 MySQL 5.5 开始引入，主要目的是保证 DDL 操作与 DML 操作之间的一致性，防止在事务执行过程中表结构被偷偷改掉导致各种诡异问题。

### MDL 锁最核心的作用（为什么要发明它？）

经典的两个场景（5.5 之前会出问题的场景）：

1. 主从复制不一致（经典 bug#989）
   ```sql
   Session1: BEGIN; INSERT INTO t ...; COMMIT;
   Session2: DROP TABLE t;
   ```
   → binlog 里可能是先 DROP 再 INSERT → 从库直接报错 1032

2. 可重复读（RR）隔离级别下同一条语句前后读不一致
   ```sql
   BEGIN;
   SELECT * FROM t WHERE id=1;  -- 看到有 name 字段
   -- 此时别人 ALTER TABLE t DROP COLUMN name;
   SELECT * FROM t WHERE id=1;  -- 报错或字段没了
   ```

为了彻底解决这类问题，MySQL 在语句开始执行时就给相关表加上了 MDL 读锁，只要事务没结束，这个读锁就不释放，DDL 需要的独占写锁就拿不到，从而实现保护。

### MySQL 中常见的 MDL 锁类型（2025年主流版本）

| 锁类型               | 简称     | 典型场景                              | 与其他锁的兼容性                                 | 持有周期         |
|----------------------|----------|---------------------------------------|--------------------------------------------------|------------------|
| MDL_SHARED_READ      | S(R)     | 普通 SELECT、DML（部分）              | 与其他读锁兼容，与写锁互斥                       | 语句结束或事务结束 |
| MDL_SHARED_WRITE     | S(W)     | DML（INSERT/UPDATE/DELETE）           | 与其他读锁兼容，与写锁互斥                       | 语句结束或事务结束 |
| MDL_SHARED_READ_ONLY | S(RO)    | 部分只读操作（较新版本优化用）         | —                                                | —                |
| MDL_SHARED_NO_WRITE  | S(NW)    | 某些 SHOW / I_S 查询                  | 允许读但不允许写                                 | —                |
| MDL_INTENTION_EXCLUSIVE | IX    | 很多 DDL 操作的第一阶段               | 几乎跟所有锁都兼容（只是表达意图）               | 语句周期         |
| MDL_EXCLUSIVE        | X        | 真正的 DDL（ALTER/DROP/TRUNCATE等）   | 和几乎所有锁都互斥，最霸道                   | 整个DDL执行期间  |

最容易引起事故的组合：  
大量长事务/未提交事务 → 持有大量 S(R)/S(W) 读锁 → 运维想执行 ALTER TABLE 加不上 X 锁 → 所有新进来访问该表的请求全部 Waiting for table metadata lock → 雪崩

| MySQL 8.4/9.0 | 有（MDL）          | 表级                | 仍然很大        | 很高          | 很低     | data_locks/data_lock_waits 表重构（去全局锁）、更多瞬态锁优化                  |
| TiDB 6.5~8.x | 有（Metadata Lock）   | 表级（早期）→ 分区级（部分支持） | 中～小          | 高            | 中等     | v6.3 引入，v6.5 默认开启；DDL 等待旧版本 DML 提交，兼容性更好；未来分区级更细 |
| PostgreSQL | 无独立MDL             | 表级 + 更细粒度依赖 | 小～中          | 非常高        | 低       | 靠 AccessExclusiveLock / ShareUpdateExclusiveLock 等实现，绝大多数DDL在线     |
| Oracle   | 有（TM锁 + 更复杂的体系） | 表级 + 行级         | 很小            | 极高          | 中～高   | 支持 Online DDL 程度最高，元数据操作非常精细，基本不阻塞DML                   |
| PolarDB/MySQL分支 | 有（增强版MDL）     | 分区级MDL（重要改进） | 小              | 很高          | 中等     | 阿里自研分区级元数据锁，DML和分区DDL基本不互堵，目前最激进的优化方向之一   |

### 目前（2025～2026）主流趋势小结
- MySQL 官方：仍然是严格的表级 MDL，优化方向是减少锁等待时间、增加读锁细分、降低诊断成本（8.4/9.0 版本进步明显），但本质上长事务仍然是大杀器
- TiDB → 越来越友好：从无 MDL → 有表级 MDL → 向分区级演进，目标是让业务DML尽量少被 DDL 卡住
- PolarDB/MySQL分支 → 目前走得最激进，分区级MDL 已经商用落地，基本解决了传统 MySQL 最痛苦的「改分区字段卡全表」问题
- PostgreSQL/Oracle → 靠语言本身的在线DDL能力 + 更精细的锁类型体系，天生对长事务更友好，基本不需要像 MySQL 这样搞一个全局大锁

一句话总结目前状态（2025-2026）：

MySQL 仍然是「MDL 表级锁最严格、使用最广泛、也最容易出事故」的代表；  
而各个分支/新一代分布式数据库（TiDB、PolarDB、OceanBase等）都在疯狂往「让DDL少堵DML」这个方向优化，分区级/对象级元数据锁 正在逐渐成为主流趋势。

生产上遇到 Waiting for table metadata lock 的时候，第一反应永远是：先找长事务，然后才是考虑升级版本/换分支/拆表/优化DDL策略
