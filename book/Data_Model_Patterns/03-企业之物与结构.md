# 03 企业之物：产品、库存与结构（原书 Ch4 Things of the Enterprise，页 46–67）

## 章定位

Ch4 处理企业的"物"：可拥有的、可移动的、可计划的东西。核心是 Hay 招牌二分——**Thing（个体）vs ThingType（类型）**，及其三大下游模式：Inventory（批次/序列号）、Structure（递归部件结构/BOM）、Heterogeneous Entities（异构实体）。Ch9/Ch10 的制造两章全建在本章骨架上。

## 模式逐条转述

### 4.1 Products and Product Types（产品与产品类型）

- **问题**：`Product` 一词在不同团队指"型号"（一款自行车）或"个体"（仓库里那台带序列号的）。混用导致同一张表既想约束型号又想记录个体。
- **约定解法**：
  - `Product Type`：型号的规格与描述所在（一行=一个 SKU 级概念）；
  - `Product`：个体（一行=一台可追踪的东西，序列号挂这里）；
  - `Product → Product Type` 恰一外键；个体不必都有序列号——序列号是可选身份，不是主键替代品。
- 语义读法示范（Ch2 纪律落地）："每一个个体**是**一个类型的一个实例；每一个类型**被例示于**零或多个个体。
- "Type of a Type"：类别的类别（分类树）另立递归 Structure，**不许**与例示关系混在同一自关联里——这是 Hay 反复强调的"两种父子"。

### 4.2 Inventory（库存）

- 库存三态：`On Hand`（在库）、`On Order`（在途承诺，回指 Ch6 合同）、`Reserved/Allocated`（分配给某计划/订单的事实行）。
- 关键区分：**Lot（批次）与 Serial Number（序列）是两种个体聚合**——批次共享属性（生产日期/供应商批号），序列号才是完全个体；`Product Type → Lot → Individual` 三层链，缺层建模（Lot 直挂类型而漏个体）是常见事故。
- 库存位置=Address/Location（Ch3）+时间，移动用事实表记录而非在库存行上 UPDATE 数量列。

### 4.3 Structure（结构）

- **递归结构模式**：`Component(Parent, Child, Quantity)` 一张事实表表达任意深度部件树；BOM、组织树、分类树同骨架（Ch3 组织递归、Ch11 文档结构递归全部回指本节）。
- 约定：结构表里挂的是**类型级**部件清单（BOM 是型号的配方，不是个体的清单）；个体级"换件历史"是另一事实（维修记录）。
- 时间维度：工程变更（ECN）=结构带生效区间，新旧两行并存。

### 4.4 Heterogeneous Entities（异构实体）

- **问题**：一类东西的属性集天生不齐（实验室仪器 vs 办公桌椅都是"资产"）。
- **约定解法**：共同属性上提父表（Asset），按"属性簇"分子类型表（不是每列一表，也不是 JSON 大列一把梭）；子类型可继续分层；**类别（Category）≠ 子类型**：类别是描述性分组（可移动可不移动），子类型改变属性的合法性——这是"类型三分法"（父类/子类/类别）的 Hay 版本，Ch12 再收口。

### 4.5 A Variation（一个变体）

- 变体讨论（转述）：当"个体不需要全追踪"时，允许 `Product Type` 直接参与业务事实（跳过个体层），但必须显式声明该省略是团队约定——对应 Ch1 "有记录的偏离"。

## 🔧 T2b 实测：Structure 递归展开与双引擎同构（SQLite 3.45.3；对偶 🔧T2 见 06 文件 DuckDB 1.5.5）

方法（脚本 `D:\develops\tmp\dbwave_w5_dmpatt\sqlite_bom_out.txt` 来源）：`part(parent, child, qty)` 四行部件（1→2×1, 1→4×2, 2→3×1, 4→5×1），`WITH RECURSIVE` 从"100 台型号 1"展开，**无深度守卫**（SQLite 递归 CTE 自然收敛）。

实测输出（逐字）：
```
(1, '1', 100.0, 0)
(2, '1>2', 100.0, 1)
(3, '1>2>3', 100.0, 2)
(4, '1>4', 200.0, 1)
(5, '1>4>5', 200.0, 2)
```
- 路径串 `1>4>5` 即"结构路径"物证；数量沿路径连乘（200=100×2×1）；
- 同一数据在 DuckDB 1.5.5（06 文件 T2）聚合结果 `[(2,100.0),(3,100.0),(4,200.0),(5,200.0)]` 完全一致——**递归 Structure 模式不依赖引擎方言**（仅 CTE 语法细节差异，如 DuckDB 演示版加了 depth<5 守卫）。
- 非本书引擎行为：原书只画结构图，SQL 化为本目录演示。

## 常见误读

1. 用 `category` 表兼任子类型与分类——两类关系基数合法性不同，必然混染。
2. 序列号当主键——序列是"可选身份"，回收/复用序列号时外键链全错。
3. 库存数量列 UPDATE 当盘点——丢了移动事实，审计断链。

## 三分法速查（个体/类型/批次/类别）

| 症状 | 判定 | 处置 |
|---|---|---|
| 新增"类别"需要改表加列 | 类型被当类别 | 移入子类型/属性簇（4.4） |
| 同型号个体属性值逐行不同 | 个体被当类型 | 规格上收 Product Type，个体挂外键（4.1） |
| 贴/摘"类别"会改变合法字段校验 | 类别被当类型 | 解除其校验独占，还原为描述性分组 |
| BOM 固定三列 parent1..3 | 结构被拍平 | 回归 Component 递归单表（4.3） |
| 序列号回收复用后外键错乱 | 序列当主键 | 代理身份与业务身份分列（4.1） |
| 批次生产日/供应商批号散落个体行 | 缺 Lot 层 | Type→Lot→Individual 三层链（4.2） |

## 建模练习

1. **练习 1**：电商手机业务含"型号 / 个体(IMSI/IMEI) / 运营商批次 / 颜色分类"——逐一落位 Thing/Type/Lot/Category。参考要点：型号=Type；IMEI=个体身份；运营商批次=Lot；颜色=Category——除非颜色决定规格参数合法性（则升格子类型，4.4）。
2. **练习 2**：纺织厂"一筒纱线"（一筒含多只管纱）：筒是个体还是批次？参考要点：筒=物理个体、管=其下个体或 Lot 成员，批次号描述生产同源；一筒承载多批用料时用事实行记录构成，不硬统一粒度（4.2/4.3 分界）。
3. **练习 3**：售后记录"个体 P 把部件 A 换成 B"。参考要点：类型层 BOM 不动（配方没改）；个体级维修/替换是另一事实（4.3 尾注）——这正是"类型级结构 vs 个体级历史"的试金石。
4. **练习 4**：给"商品分类树（食品→乳品→酸奶）"与"物料装配树"各判一条外键语义。参考要点：前者 category-of（多对多可移贴），后者 instance-of 结构（数量/工序语义）；两棵树禁止共享一个 `parent_id` 列。

## 三分法四问判定（拿到任意"XX 分类"先问）

| 问 | 答"是"的含义 | 落位 |
|---|---|---|
| 换掉它，合法字段集合会变吗 | 身份性分类 | 子类型（4.4 属性簇） |
| 同一个东西可以同时属于两个吗 | 描述性分组 | 类别（多对多桥） |
| 它带生产/供货属性吗 | 同源聚合 | Lot（4.2） |
| 它有独立生命周期吗 | 独立个体 | Thing 个体行（4.1） |

四问全"否"的对象多半只是报表口径——放视图层，别进逻辑模型。

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
|---|---|---|
| 个体 | Thing / Product | 一个可追踪的东西本身 |
| 类型 | Thing Type / Product Type | 个体共享规格的型号层 |
| 例示 | Instance-of | 个体恰属一个类型的关系（区别于分类） |
| 批次 | Lot | 共享生产属性的个体聚合层 |
| 序列号 | Serial Number | 个体级可选身份，非主键替代品 |
| 部件结构 | Structure / BOM | Component(父,子,数量) 递归事实表 |
| 工程变更 | Engineering Change | 结构行带生效区间，新旧并存 |
| 异构实体 | Heterogeneous Entity | 共同列上提+按属性簇分子类型 |
| 类别 | Category | 描述性分组，不改变属性合法性 |
| 三态库存 | On Hand/On Order/Reserved | 在手、在途、已分配的三种库存事实 |

## 最新演进与工业实践

- **STEP / ISO 10303**：制造业 BOM/配置交换标准的产品结构模型（product_definition 与 formation 关系）与 Hay 的类型/个体+Structure 同构（⚠️ wikipedia 本机不可达未能验链，标准名与概念为通识转述）。
- **PLM/ERP 2024–2026**：SAP/Oracle 物料主数据仍分 Material（类型层）与 Serial/Batch（个体/批次层），印证 Ch4 二分长期稳定（⚠️ 转述）。
- **半结构化回潮**：文档数据库把异构实体推回"宽 JSON+可选字段"，Hay 式折中（父表+属性簇子表）在关系型数仓与 schema-on-read 间仍是治理锚点；dlt/Iceberg 等管道对可选列族的处理可对照（⚠️ 方向性）。
- **图库对照**：Structure 在图库里退化为一条边类型+路径查询，无需递归 CTE，见 [../Graph_Databases_2e/03-使用图进行数据建模.md](../Graph_Databases_2e/03-使用图进行数据建模.md)。
