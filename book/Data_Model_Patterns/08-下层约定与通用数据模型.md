# 08 下层约定与通用数据模型（原书 Ch12 Lower-Level Conventions + References/Bibliography/Index，页 235–263）

## 章定位

Ch12 是全书收口：把 Ch3–Ch11 里反复出现的微观构件（Thing/类型/类别、地址、角色、资源、关系、变长记录、"通常一对一、偶尔一对多"、数学表达式）**抽出来当作"下层约定"**——相当于给 Ch2 的三层约定补上构件级词汇表；最后以 The Universal Data Model 一节点出全书终极主张：这些约定趋同到足够普适时，存在一个跨行业通用的数据模型骨架。

## 模式/约定逐条转述

### 12.1 Things, Thing Types, and Categories（物、物类型与类别）

- 三分法定型：**个体（Thing）/ 类型（Thing Type）/ 类别（Category）**——03 文件的"两种父子"在此升格为全书公理：
  - 类型:个体=恰一（身份性，改变属性的合法性）；
  - 类别:个体=多对多（描述性，可移动可不贴）；
  - 混用（把类别当子类型外键）是"客户分为 A/B/C 级"这类需求把模型带偏的根因。

### 12.2 Addresses / 12.3 Roles / 12.4 Resources / 12.5 Relationships

- 地址、角色作为"下层约定"复盘：地址=点+历史（02），角色=当事人×上下文×时间（02/04/07 三章已三次落地）；
- **Resources（资源）**：把 Labor Usage/Asset Usage/测点/文档载体统一为"可被活动消费或占用的东西"父约定——04 文件两节模式在理论上合并；
- Relationships：鼓励**命名关系家族**（is associated with / is recorded for / is a kind of）三件套，禁止每图新造动词——这是 Hay 给"模型可读性"的最后一道约定。

### 12.6 Variable Length Records（变长记录）

- 对 EAV/纵表的正式态度：**能用列不用行，必须用行时锁定三元组（宿主×定义×值）并给定义表以版本管理**（07 文件 11.9 的普适化）；明确其查询代价与约束失守风险。

### 12.7 Usually One, Sometimes Many（通常一，偶尔多）

- 招牌微模式：基数在业务上"通常 1:1，偶发 1:N"（一次手术通常一个主刀、偶发双人术）——**按多数情况外键化会丢数据，按少数情况建桥表会天天 JOIN 空转**；
- Hay 的裁定（转述）：建模按**语义真实基数**（多），用视图/约定满足"取唯一主责人"的常用读法；此节是全书"语义约定高于存取便利"的最强示例。

### 12.8 Mathematical Expressions in the Data Model（模型中的数学表达式）

- 派生值纪律：公式（派生规则）作为**一等建模对象**登记（表达式版本×输入观测集×输出），而非藏在报表工具里——05 文件派生观测、06 文件 MRP 净需求的通则化；
- 与 Ch7 分录规则同族："规则即数据"在此完成理论化。

### 12.9 The Universal Data Model / 12.10 A Final Example

- 通用数据模型主张：跨行业反复验证的模式集合收敛后，其并集构成"世界描述的通用骨架"——组织/当事人/物/活动/合同/账/文档/观测八大族（恰好=Ch3–Ch11 的章序）；
- Final Example 把前述约定串成一张端到端示例图（转述其功能定位）；
- 尾层：References（258）/Bibliography（259）/Index（263）——模式集体裁的"引用即谱系"：Hay 的谱系可上溯 Codd 的关系语义与 1970s 关系实现史（DOI 均已过 Crossref 校验）：Codd, *A relational model of data for large shared data banks*, CACM 1970, [10.1145/362384.362685](https://api.crossref.org/works/10.1145/362384.362685)；关系实现史锚点 Stonebraker 等的 INGRES 论文 *The Design and Implementation of INGRES*, ACM TODS 1976, [10.1145/320473.320476](https://api.crossref.org/works/10.1145/320473.320476)（✅ 200 校验；用于"类型/域约束可实现性"的历史锚，⚠️ 与本书正文的直接引用关系未逐页核对，登记为线索）。

## 常见误读

1. "通用模型=拿来即用的行业标准表"——Hay 的 UDM 是**约定收敛的结果**，不是 COTS 数据字典；落地仍需组织级裁剪与"有记录的偏离"（01 文件）。
2. "Usually one, sometimes many"按一建模——偶发多即数据丢失（12.7 裁定相反）。
3. 把 12.8"规则即数据"理解成全部外置到脚本——公式不入模型=派生值不可重演（05 文件原则的违例）。

## 建模练习（综合）

1. **练习 1**：某 MES 把工单同时当"生产命令（承诺）"与"批次记录（事实）"，改期即覆写。给出重构方案。参考要点：拆 Work Order（承诺侧，04）+ Activity/Usage（事实侧，04）+ 批次版本化载体（07 章 11.8）；三向时间戳（计划/开始/结束）归位。
2. **练习 2**：集团"统一代码表"治理——用三分法判定每个代码族归属。参考要点：改变合法字段者=子类型；可贴可摘者=类别；跨主体身份者=角色；三类分别落库（外键列/桥表/事实表），一张"大字典表"包打天下必乱。
3. **练习 3**：判断"客户等级 A/B/C"入哪族。参考要点：等级=类别（可变动、不改变属性合法性，12.1）；若等级决定授信字段集合才生效，则升级为子类型并显式记录该约定（Ch1 偏离纪律）。
4. **练习 4**：UDM 与 DDD 限界上下文是竞争关系吗？参考要点：本目录观点（⚠️ 非原书）——不竞争：上下文内词汇归 DDD 战略设计，跨上下文共享骨架可用 Hay 八族对齐；UDM 提供的是"通用语言"的下游公共档。

## 最新演进与工业实践

- **本体/知识图谱化**：UDM 主张在 2020s 的对应物是企业本体（FIBO、schema.org、Palantir Ontology 一类"业务对象骨架"产品化，⚠️ 仅 FIBO/OMG 概念对应可转述，URL 本机未验）；"类型/个体/角色"与 OWL 的类-个体-属性区分可互译（⚠️ 转述）。
- **向量时代的位置**：LLM 应用把"统一语义层"推为热点（text-to-SQL 语义层、指标层 dbt Semantic Layer 等，⚠️ 转述），Hay 一书提供的是其逻辑地基——先有约定，再谈映射。
- **SQL 标准与引擎能力表更新**（截至 2026-09，本机可测口径 🔧）：SQLite 3.45.3 支持偏索引/递归 CTE、不支持区间排他约束；DuckDB 1.5.5 支持 PIVOT/窗口、不支持偏索引——"模式不变式落哪层"的决策表应随版本每季重跑（本目录脚本即模板）。
- **社区现状**：Hay 的 Community Data Model 讲义仍在数据管理从业者会议流通；本书与其 Morgan Kaufmann 姊妹册（A Metadata Map）构成"模式集"体裁的双壁，选读次序建议：本书（约定叙事）→ MK 册（元数据索引）（⚠️ 流通渠道未逐一验链）。
