# 04 程序、活动与合同（原书 Ch5 Procedures and Activities + Ch6 Contracts，页 68–116）

## 章定位

Ch5 定义"做事怎么记"（Procedure=规程，Activity/Work Order=干了什么），Ch6 定义"承诺怎么记"（合同/订单=对未来活动的承诺）。两章成对出现：**合同的履行生成活动，活动的签收回溯合同**——这是采购-销售-生产全链路的地基，也是本书篇幅最重的模式带（68–116 近 50 页）。

## Ch5 转述要点

### 5.1 Some Definitions（定义）

- **Procedure（规程）**：类型层。"这类工作怎么做"的步骤清单（工序模板），一行=一个步骤（含顺序号），挂在工作类型下；
- **Activity（活动）**：事实层。"某时某人/某物干了某事"的一次发生；
- **Work Order（工单）**：Activity 的受控形态——有发起方承诺（常由 Ch6 合同/订单驱动）、有对象、有排程。
- 读法纪律：规程:活动 = 类型:个体，与 Ch4 Thing/ThingType（见 03 文件）同一二分在"动词侧"的投影。

### 5.2 Dividing Activities（活动的切分）

- 切分粒度=**责任交接点**：谁在何时把什么交给谁。按管理需要（成本归集、工时统计）切太碎或太粗都破坏模型；
- 活动可分解：`Activity → Sub-Activity` 递归（又一次 Structure，03 文件），父活动=汇总视图。

### 5.3 Work Orders / 5.5 Kinds of Work Orders

- 工单核心五元组：对象（对什么干活）+ 执行者（谁干）+ 时间窗（计划 vs 实际两对时间）+ 数量（做多少）+ 发起承诺（哪份合同/订单，可空）；
- "Kinds of Work Orders"：维修单/生产单/检验单共享同一父模式，用子类型+各自扩展事实，**禁止**每种工单一套表（异构实体原则在动词侧的复用）。

### 5.4 Labor Usage（人力使用）

- 人时不是员工表的字段，而是事实：`Work Order × Person × 时间段 × 角色`——角色直接回指 02 文件 Party Role；
- 同人工时重叠（同一小时报两个工单）=数据质量事故，模型层用时间窗互斥表达（见 🔧T3 同构问题）。

### 5.6 Actual Asset Usage（资产使用）

- 设备/工具占用=资产 × 活动 × 时间窗的事实；与 Labor Usage 完全同构，合并为"资源使用"母模式（Ch12 Resources 节预告）。

## Ch6 转述要点

### 6.1 Purchase / Sales Orders（采购/销售订单）

- 订单=**双方或多方对未来的承诺**：`Contract`（合同）父实体 + `Contract Item/Line`（条款行，承诺的具体物/服务+数量+价）；
- PO 与 SO 是同一合同模式的**视角对称**：本方的采购合同=对方的销售合同，一个合同实体、两条 Party Role（买方/卖方），不是两张系统表拼起来；
- 履行链：合同行 → 交付事实（6.5）→ 开票/付款事实（05 文件会计）——**承诺与事实永不混列**。

### 6.2 User Specifications（用户规格）

- 合同可附带"按买方规格生产"的规格书实体：版本化的条款附件，回指 Ch11 文档模式（07 文件）；规格变更=新行，旧行留在历史里。

### 6.3 Contract Roles（合同角色）

- 缔约方通过 `Contract Role`（角色 × 当事人 × 合同）挂上：买方、卖方、担保方、见证方可同场多角色——Party Role 在合同语境的实例化（02 文件）。

### 6.4 Employment Contracts（雇佣合同）

- 雇佣=合同子类型：员工 Party × 组织 Party × 期限 × 职位/工资条款行；与 Ch3 Employee/Assignment 咬合：**合同是承诺，派任是事实**，两表时间窗允许不完全重合（先签合同后到岗）。

### 6.5 Marketing Regions and Districts / 6.6 Deliveries / 6.7 Summary of Material Movements

- 营销区域：组织单元 × 地理（Ch3 地理链）× 任期的责任地图；
- 交付：`Delivery` 事实=合同行 × 个体/批次（Ch4 Inventory）× 时间 × 承运活动（Ch5）；所有权转移点是语义关键（风险何时换方）；
- 物料移动汇总：所有"物换位置/换所属"的事实统一进 Movement 母表（收/发/调拨都是其子型），与库存三态（03 文件）闭环。

## 🔧 T3 实测：合同角色时间窗互斥（SQLite 3.45.3，非本书引擎行为）

方法（脚本 `D:\develops\tmp\dbwave_w5_dmpatt\sqlite_tests.py`，输出 `sqlite_out.txt`）：`employment(person, org, start_d, end_d)` 三行，其中 emp1(2020-01-01~2023-12-31) 与 emp2(2023-03-01~2025-01-01) 故意重叠；用自连接 `a.start < b.end AND b.start < a.end AND a.emp_id < b.emp_id` 检测。

实测结果（逐字）：`overlap pairs detected: [(1, 2)] count= 1` —— 重叠窗口被成对揪出，emp3 无违规。
工程注记（实测发现）：SQLite **没有** `EXCLUDE ... &&` 区间排他约束，窗口互斥只能靠应用层/触发器/自连接审计（本演示取最后者）；PostgreSQL 的 GiST EXCLUDE 约束可声明式实现（⚠️ 本机无 PG，转述）。Hay 的"合同期互斥"语义约定在最小引擎上要额外搭脚手架——这正是"模式 ≠ DDL"的实例。

## 常见误读

1. 订单表存"已发货量"列——把履行事实汇总写回承诺实体，改期/退货时两头失真；汇总应是视图。
2. 工序模板与工单同表——规程（类型）与活动（事实）基数不同，混表后无法表达"未派工的模板步骤"。
3. 员工调岗 UPDATE 原雇佣行——丢历史；合同行保持、新增派任行（02 文件时间切片）。

## 承诺-事实链对照表（本章总干）

| 环节 | 核心实体 | 层 | 直接下游 |
|---|---|---|---|
| 承诺 | Contract / Contract Item | 未来事实 | Delivery、Planned Order |
| 排程 | Planned Order（06 章四段式） | 未来事实 | Work Order |
| 执行 | Work Order / Activity | 过去事实 | Labor/Asset Usage |
| 交付 | Delivery（6.6） | 过去事实 | Movement、库存三态（03） |
| 结算 | Invoice/Payment（05 章会计） | 过去事实 | Journal Entry |
| 凭证 | Document、Receipt（07 章） | 过去事实 | 审计链 |

读法：任何一环节的行都只向前引用，不向后覆盖——"链"的单向性=承诺/事实分离的全局形态。

## 建模练习

1. **练习 1**：建筑工程"业主-总包-分包-监理"四方合同，业主要求追加"出资银行"角色。参考要点：全部走 Contract Role（6.3）——角色行+条款行，禁止一角色一表；监理的验收权是条款行不是新实体。
2. **练习 2**：客户一张销售合同分三批提货，第二批延期后改量。参考要点：三条 Delivery 事实链同一合同行（6.5）；变更=新行留痕；"已发货量"回写合同行列属违例（常见误读 1）。
3. **练习 3**：工厂维修工单与生产工单共表还是分表？参考要点：父模式共享+子类型扩展（5.5 Kinds of Work Orders）；分表=异构实体反模式，混列全字段=稀疏空列反模式。
4. **练习 4**：医生 20 分钟连续接诊 3 位患者，工时如何入账？参考要点：3 条活动行各挂 Labor Usage 事实；切分点=责任交接（5.2），按时间硬切成"20 分钟一行"是伪精细。

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
|---|---|---|
| 规程 | Procedure | 工作步骤的类型层模板 |
| 活动 | Activity | 一次"干了某事"的事实 |
| 工单 | Work Order | 受承诺驱动、带计划/实际两对时间的活动 |
| 人力使用 | Labor Usage | 人×活动×时段×角色的事实行 |
| 资产使用 | Actual Asset Usage | 资产×活动×时段的占用事实 |
| 合同 | Contract | 对未来活动的正式承诺实体 |
| 合同行 | Contract Item | 承诺的最小条款粒度（物/服务+量+价） |
| 合同角色 | Contract Role | 当事人以何身份缔约（买/卖/担保…） |
| 交付 | Delivery | 所有权/风险转移点的事实 |
| 物料移动 | Material Movement | 收發调拨统一的移动母表 |
| 承诺-事实分离 | Promise/Fact Separation | 订单与履行永不混列 |

## 最新演进与工业实践

- **SQL 标准时间区间**：SQL:2011/2016 的 `PERIOD`/`SYSTEM_TIME` 与 PostgreSQL `daterange + EXCLUDE`（⚠️ 转述）正把 Hay 手工的"区间互斥"变成声明式约束；SQLite 3.45.3 实测仍无此能力（🔧T3）。
- **采购网络协同**：订单-交付-开票链路在 e-invoicing（欧洲 Peppol、中国数电发票）下事实粒度更细，合同/履行分离模式反而更必要（⚠️ 方向性转述）。
- **工作流引擎对照**：BPMN/Camunda 类引擎的流程实例≈Work Order 的运行时投影，"规程=流程定义、活动=任务实例"的对应提示两栖建模时以数据模型为主档（⚠️ 转述）。
- **合同结构化**：智能合同/CLM（合同生命周期管理）厂商把 Contract Role/Item 做成机器可读对象，与 Ch6 实体一一对应（⚠️ 商业实现不作实证）。
