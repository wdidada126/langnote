## 核心概念速览（中英对照）

- **两阶段名称查找** — two-phase name lookup：定义期解析非依赖名，实例化期解析依赖名（第二段常借 ADL）。
- **依赖名** — dependent name：含义随模板实参而定的名字；类型要 `typename`、成员模板要 `template` 前缀。
- **当前实例化** — current instantiation：模板体内引用自身特化被视为已知，`Node* next;` 不用写全。
- **模板实参推导** — template argument deduction：从调用实参反推形参的算法，含衰减与引用折叠两条子规则。
- **类模板实参推导** — CTAD（C++17）：由隐式/显式**推导指南**驱动；`iterator_range b(v.begin(), v.end())` 免写尖括号。
- **推导指南** — deduction guide：告诉编译器"构造函数签名 → 类模板实参"的映射；聚合/隐式指南之外的补丁。
- **转发引用** — forwarding reference：`T&&` 且 `T` 正在被推导的局部语法位置；引用折叠规则 `& + && → &`。
- **decltype 说明符** — decltype specifier：从表达式取类型；`decltype(x)` 看实体，`decltype((x))` 看值类别（左值 ⇒ 带引用）。
- **std::declval** — declval：只有声明没有定义的"类型→引用"伪装函数，unevaluated 上下文的探针。
- **模板友元** — friendship in templates：友元声明进模板特化体系的三种姿势（全特化互指/友元模板/模板参数即友元）。

## 动机

前三章的语法一旦跨进"操作未知类型"的领域，立刻撞上三堵墙：
**名字什么时候解析**（4.1）、**实参怎么反推**（4.3/4.4）、**表达式不真跑怎么谈类型**
（4.6/4.7）。这三堵墙就是模板编译模型与运行期语言的根本差异所在；
05/06 章的所有探测器（traits、requires）都建立在这套机制上——不会 `declval`，
`requires` 表达式里 `std::declval<T>().foo()` 就是天书。

## 机制

**两阶段查找与两个消歧关键字**。定义模板时，非依赖名立刻解析（写错立刻报错）；
含未定形参的名字推迟到实例化。漏写 `typename` 的代价——🔧（已实测 g++ 15.2 诊断原文）：

```cpp
template <typename T>
void f(T& c) { T::value_type x{}; }
// error: need 'typename' before 'T::value_type' because 'T' is a dependent scope
```

`template` 关键字同理：`this->template as<int>()`——依赖基类里的成员模板，
第二段查找前编译器默认把 `as` 当变量，`<` 当小于号。"当前实例化"是豁免条款：
`struct Node { Node* next; }` 的 `Node` 自动指当前特化，无需 `Node<T>*`。

**函数模板推导的三条主干规则**（以 `void g(T&&)` 为例）：
实参是左值 ⇒ `T = X&` ⇒ 折叠成 `X&`（转发引用吃左值）；实参是右值 ⇒ `T = X` ⇒ `X&&`。
数组/函数实参先衰减为指针再进上述规则；`T` 同时从两个实参推出矛盾 ⇒ 推导失败而非"择优"
（01 章 `maxv(3.5, 2)` 的死因）。

**CTAD 与推导指南**。没有指南时，编译器从构造函数隐式生成；🔧（已实测 g++ 15.2）：

```cpp
template <typename It, typename Sent = It>
struct iterator_range { It b; Sent e; iterator_range(It, Sent); };
template <typename It, typename Sent> iterator_range(It, Sent) -> iterator_range<It, Sent>;
std::vector<int> v{1,2,3};
auto rng = iterator_range(v.begin(), v.end());   // 指南推成 iterator_range<int*, int*>
```

坑位预告：指南可以推出与构造函数**不同**的类模板实参（`iterator_range(It, Sent) ->
iterator_range<It, It>` 之类），这是 09 章视图工厂的常用手法。

**模板递归（4.2）= TMP 的循环**。🔧（已实测）：

```cpp
template <unsigned N> struct Fact { static constexpr unsigned v = N * Fact<N-1>::v; };
template <> struct Fact<0> { static constexpr unsigned v = 1; };
static_assert(Fact<6>::v == 720);
```

递归基**必须是特化**（部分特化 `Fact<1>` 也行），否则推导无出口 ⇒ 实例化深度爆栈。
这一小节是全书"类型即状态、特化即分支"世界观的最小展示，05 章 traits、07 章类型列表全是它的变奏。

**declval 的存在理由**：探测 `T` 是否可比较需要写 `a < b`，但 `T` 可能不可默认构造、
甚至抽象。`std::declval<T>()` 只有声明（`add_rvalue_reference_t<T> declval() noexcept;`），
永远只在 unevaluated 上下文出现，让"假装有个 T 的表达式"合法化。requires 表达式的
语法糖底下铺的就是这条路——05 章实测探测器与 06 章 `requires` 的等价性由此而来。

**模板友元三态**（4.8）：① 友元模板：类模板内 `template<class U> friend U peek(const Secret<U>&);`
——每个特化把所有 peek<U> 当朋友（过宽）；② 模板参数即友元：`friend T;`（02 章 CRTP 里
`friend Counter<Derived>` 的同族手法）；③ 只授某特化：需再垫一层实现细节类。
🔧 实测①可行（`peek(s)` 读到私有 `v_`）。

## 权衡

- **`typename` 噪声 vs 解析歧义**：C++98 时代两阶段查找未强制时，MSVC 一度宽松接受漏写
  （模板在 MSVC 编译不过、GCC 能过的经典错位），"dependent qualifier" 开关即为此。
- **转发引用 vs 两个重载（const& / &&）**：转发引用一份通吃但**吞掉一切**（连 `int` 都能接），
  约束场景要配 concept 收窄（06 章 6.9-6.10 专门讲约束 `T&&`/`auto`）；两重载版语义诚实
  但成本 2ⁿ。
- **CTAD vs 显式实参**：指南让"看起来在做什么"更清楚（`std::pair p{a, b}` 比
  `std::pair<A&, B&>` 衰减更友好）；但推导结果可能与直觉不符（值类别、引用成员），
  库设计者要显式写指南来掌控接口。

## 相邻概念对比

- **`decltype` 三兄弟**：`decltype(x)` 实体规则（无转换）、`decltype((x))` 值类别规则、
  `auto` 推导规则（= 模板推导 + 花括号特例）——三者互不等价，对照
  [../Effective_Modern_C++/00-总览与阅读地图.md](../Effective_Modern_C++/00-总览与阅读地图.md) 的 01/02 篇口径。
- **两阶段查找 vs SFINAE**：都发生在"替换"时间线；两阶段管**名字找得到**，
  SFINAE 管**替换错不算错**（05 章）。`typename` 漏了是查找阶段错误，SFINAE 救不了它。
- **模板递归 vs constexpr 循环**：C++14 起 constexpr 函数可以用真 for/if，
  "编译期算值"的很多递归（如 Fact）被 `constexpr` 循环平替；但**类型层递归**
  （包展开、列表操作）仍只有模板能做——这是 05/07 章保留地。

## 最新演进与工业实践

- **依赖名治理的后续**：C++20 的 `typename auto:3 = ...` 等约束语法没有取消任何消歧
  关键字；社区曾有"简化 typename 规则"的讨论（P1928 语境 ⚠️ 未核实到对应裁决），
  本书规则今天仍然全量有效。
- **CTAD 的 C++23 增量**：聚合初始化指南、函数模板当指南（"用 make 函数名推导"，
  `std::complex z = std::sqrt(1.0)` 风格）落地 ⚠️ 提案号未实测，特性名属实。
- **range-v3 大规模实践**：Niebler 的 range-v3 仓库（ericniebler/range-v3）里
  `declval`+依赖名是探测器密度最高的区域——其 `concept` 宏体系就是为绕开
  前 concepts 时代 4.7 的书写成本而生；读它的 `detail::declval` 别名即懂本节存在意义。
- **编译器诊断工业级改善**：GCC 的 `-fconcepts-diagnostics-depth`、clang 的约束回溯链，
  都是对"4.1 的错到实例化才爆"的运维补偿；本项目实测中 GCC 15 对模板体错误已加
  `-Wtemplate-body` 提示（见 00 诊断记录）。
