## 核心概念速览（中英对照）

- **类型特征** — type trait：以类型为输入、以 bool/类型为输出的编译期函数；`<type_traits>` 是标准库给的"类型的反射"。
- **SFINAE** — Substitution Failure Is Not An Error：实参替换进函数签名（含默认实参/返回类型）阶段出错 ⇒ 该候选静默出局，**不是**硬错误。
- **替换上下文** — immediate context：只有签名"当场"的替换失败才 SFINAE；替换成功后在模板体内引发的错误是硬错误。
- **enable_if** — std::enable_if：`enable_if_t<B, T>` 当 B 为假时无成员 type ⇒ 把布尔门禁翻译成"签名不可替换"。
- **探测惯用法** — detection idiom：主模板 `false_type` + `void_t<探测表达式>` 偏特化 `true_type`。
- **void_t** — `template<class...> using void_t = void`：把所有合法类型折叠成 `void`，从而让"表达式合法"成为可偏特化的模式。
- **constexpr if** — `if constexpr`（C++17）：编译期选分支，未选中分支**不实例化**；依赖表达式的分叉利器。
- **条件萃取** — `conditional_t` / `common_type_t`：类型层的三元运算与最小公共类型。
- **调用结果特征** — `invoke_result_t`：函数/可调用对象 × 实参类型 ⇒ 返回类型（`decltype(declval...)` 的标准化）。
- **修饰符流水线** — `remove_reference_t`/`add_pointer_t`/`decay_t`…：5.5.5/5.5.6 的"类型字符串改写"家族，组合即变换。

## 动机

泛型代码的两类根本问题：**"T 能不能做 X"**（决定实现策略/开关重载）与
**"从 T 造出 U"**（决定成员类型）。前 concepts 时代，两件事分别由 SFINAE 与 traits 承担，
本章就是这两件兵器的完整锻造流程。学完要能做到：不用 concepts 也能写出任意能力探测器，
**并且知道它的诊断学极限**——否则无法理解 06 章"concepts 到底改了什么"。

## 机制

**SFINAE 的准确作用域**。重载决议收集候选 → 用实参**替换**模板形参进签名
（类型、默认实参、返回类型、noexcept 表达式等 immediate context）→ 替换失败则**剔除候选**；
若所有候选出局才报"no matching function"。两个推论：① 藏在函数体里的错误不是 SFINAE
（所以门禁必须写在签名上）；② 默认模板实参是惯用的"藏身处"（`typename = enable_if_t<...>`
形式），因为它在替换阶段被求值又不出现在调用界面里。

**探测器的实现原理**（本目录实测核心，也是 5.1/5.5 的"自研标准库"练习）🔧（已实测 g++ 15.2）：

```cpp
template <typename...> using VoidT = void;
template <typename T, typename = VoidT<>>
struct is_cc : std::false_type {};                       // 主模板：默认"不可拷贝构造"
template <typename T>
struct is_cc<T, VoidT<decltype(T(std::declval<const T&>()))>> : std::true_type {};
static_assert(is_cc<std::string>::value);
static_assert(!is_cc<std::unique_ptr<int>>::value);      // unique_ptr 拷贝构造被 delete：
                                                          // 声明存在但不可用 ⇒ decltype 失败 ⇒ 回落主模板
```

三层递进：`declval` 造探针表达式（04 章）→ `decltype` 要表达式的类型 →
`void_t` 把"任何合法类型"归一为 `void`，使"表达式合法"变成**部分特化可匹配的模式**。
被 delete 的函数参与重载但不可调用 ⇒ `decltype` 里替换失败 ⇒ 探测为假——这正是
`is_copy_constructible_v<std::unique_ptr<int>> == false` 的实现逻辑
（标准库真身还要处理"union 成员不可拷贝"等边角，方向一致 ⚠️ 未逐行比对 libstdc++）。

**enable_if 的最小可用门禁**🔧（已实测）：

```cpp
template <typename T>
typename std::enable_if<std::is_arithmetic_v<T>, T>::type
only_numbers(T a, T b) { return a + b; }   // T=std::string ⇒ enable_if 无 type ⇒ 候选出局
```

**constexpr if：分叉不实例化**。5.4 的定位要看清：它不是 SFINAE 的替身，而是
**实现体内部**的分叉器——SFINAE 决定"谁有资格当候选"，`if constexpr` 决定"选中的候选
内部走哪条路"。标签派发（07 章 7.5）的三段式（helper + 两重载 + 转发）被一段替换：
🔧（已实测）：

```cpp
template <typename It>
auto distance_n(It a, It b) {
    using cat = typename std::iterator_traits<It>::iterator_category;
    if constexpr (std::is_base_of_v<std::random_access_iterator_tag, cat>) return b - a;
    else { long n = 0; for (; a != b; ++a) ++n; return n; }
}
```

未选中分支不实例化 ⇒ `b - a` 对输入迭代器**合法地不存在**也不报错——旧时代要为它写
`distance_impl` 重载对。

**5.6.1"实现拷贝算法"的意图**：按 `is_trivially_copyable_v<T>` 决定 memcpy 路线还是
逐元素构造路线——traits 驱动**实现策略**的样板（本目录 🔧 最小化复现于
`copy_trivial_or_loop`，已实测）。5.6.2"同质变参"：`common_type_t<Ts...>` +
折叠 `(s += double(xs), ...)`，见 [03 章](03-变参模板.md) `homogeneousSum2`（已实测）。

**诊断学实测：SFINAE 失败长什么样**。同一意图、两代写法、两种失败文本
（g++ 15.2 `-std=gnu++20`，仓库外实测捕获，本目录保留逐字首行）：

```text
// enable_if 版调用 incr(2.5)：
error: no matching function for call to 'incr(double)'
note: candidate: 'template<class T, class> int incr(T)'      ← 门禁身份藏在匿名默认实参里，不可见

// requires 版同调用：
error: no matching function for call to 'incr(double)'
note: candidate: 'template<class T>  requires  integral<T> int incr(T)'   ← 约束随签名现身
（缩写版 incr(std::integral auto) 还会追加：note: constraints not satisfied + 约束回溯链）
```

诚实结论：GCC 15 已把两者收拢到同一主诊断；**差异在候选签名是否自带失败原因**
（`requires integral<T>` 直接印在候选上，且约束版可再展开回溯链）。clang 的差异更戏剧化
⚠️ 本机无 clang 未实测。这就是 06 章"诊断即文档"主张的实底。

## 权衡

- **`typename = void_t<...>` vs `enable_if_t`**：前者可把多个探测叠进一个偏特化、
  还能区分不同失败形态（不同 void_t<表达式> = 不同偏特化），是探测器的首选载体；
  `enable_if` 胜在布尔即门禁、读起来像注释。C++20 后两者共同退居"仍要会读"。
- **`if constexpr` 的滥用风险**：分支条件是 traits 组合时，函数体迅速变成"类型 switch"；
  超过两三叉就该拆回重载/特化，否则单函数承担多职责（与"别写 800 行模板"的编译时间账对赌）。
- **trait 粒度**：`is_pod`（已弃用）教训——名字与语义漂移的标准库特性；优先用
  `is_(trivially|standard)_layout`、`is_(copy|move)_constructible` 等语义明确的组合件。

## 相邻概念对比

- **SFINAE vs concepts（本卷最大对比）**：同一替换机器，前者"失败即沉默出局"，
  后者"失败即具名诊断"；06 章展开。
- **`if constexpr` vs `requires`**：一个管体内分叉（不改变候选集），一个管候选资格
  （改变重载集）；功能交集靠"约束在签名、分支在体内"的纪律划清。
- **traits vs `typeid`**：`typeid` 运行期（需 RTTI、多态类型查动态类型），
  traits 纯编译期；"编译期已知类型就不要付运行期的钱"。

## 最新演进与工业实践

- **concepts 接管后 traits 的新分工**：写约束表达式（06 章）与实现分叉（本章）两套用法
  都活得很好；死掉的只是"手写 SFINAE 做门禁"。Google/Chromium 代码库至今仍大量使用
  traits + `if constexpr`（abseil 的 `type_traits.h` 是其自研基地），本书 5.5 的六类清单
  正是读它们的词典。
- **P0323R12 "std::expected"**（2022 文件索引实测确认编号标题）与 **P2505R5
  "Monadic Functions for std::expected"**（Jeff Garland，实测 wg21.link 解析）：C++23 的
  expected 内部正是"trait 决定可存放性 + constexpr 分叉"的集成展示，也是本书 5.3 门禁
  思想的接口化后代。
- **fmt 编译期格式串检查**：fmtlib 把 `is_formattable` 用探测惯用法实现（其
  `formattable` 概念版在 C++20 模式启用）——**探测 → 概念**的迁移路径与本章→06 章完全同构，
  是最值得读 200 行的工业样本（fmt/core.h 的 `FMT_ENABLE` 时代 → `concepts` 命名空间）。
- **heterogeneous 查找的 traits 根**：`std::less<>` 的 `is_transparent` 标志位（C++14）
  是 trait 影响**标准库自身行为**的著名案例；unordered 系列的更多异构重载提案号
  （P2363 语境）待核 ⚠️，机制本身 05/08 章都会复用。
