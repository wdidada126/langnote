## 核心概念速览（中英对照）

- **概念** — concept：以 `constexpr bool` 谓词命名的**类型约束接口**；`template<概念 T>` 或 `T 概念` 皆可用。
- **requires 表达式** — requires expression：`requires { 要求; }` 返回 bool 的编译期谓词，概念的主体原料。
- **简单要求** — simple requirement：一个表达式，只检查"能编译"（不检查返回类型）。
- **类型要求** — type requirement：`typename T::value_type;` 检查嵌套类型存在。
- **复合要求** — compound requirement：`{ expr } -> concept; noexcept`——存在性 + 返回类型 + 异常性三合一。
- **嵌套要求** — nested requirement：`requires std::copyable<T>;` 把另一个谓词并入。
- **约束** — constraint：出现在 requires 子句/概念体内的布尔表达式，参与重载排序的实体。
- **约束蕴含** — subsumption：约束 A 蕴含 B 当 B 是 A 的（合取）子句；决定"谁更受约束"。
- **约束偏序** — partial ordering of constrained overloads：更受约束者胜；不可比则二义或按旧规则（签名偏序）。
- **缩写函数模板** — abbreviated function template：`void f(std::integral auto)`；auto 形参按位置展开成模板参数+约束。
- **约束返回类型** — constrained auto return：`std::integral auto f()` 把约束钉在结果上。
- **标准概念** — standard library concepts：`<concepts>`（same_as/convertible_to/predicate…）+ 迭代器/范围概念族。

## 动机

05 章末尾的实测诊断已经给出答案：**门禁写不进界面、失败说不出原因**。
concepts 的设计目标不是新能力（一切 requires 都能翻成 traits+SFINAE），而是三件旧能力
的界面学升级：① 约束成为**签名的一部分**（文档即接口即检查）；② 失败产生**具名诊断**；
③ 重载之间引入**可判定的偏序**，替代"更多候选碰运气"。一句话：SFINAE 是编译器的
内部机制被挪用成用户策略，concepts 是终于给了正身。

## 机制

**requires 表达式 = 05 章探测器的语法化**。四要素逐一（🔧 已实测 g++ 15.2）：

```cpp
template <typename T>
concept ContainerLike = requires(T c, const T cc) {
    typename T::value_type;                            // 类型要求
    { cc.size() } -> std::convertible_to<std::size_t>; // 复合要求
    c.begin(); c.end();                                // 简单要求
    requires std::copyable<T>;                         // 嵌套要求
};
static_assert(ContainerLike<std::vector<int>>);
static_assert(!ContainerLike<int>);
```

与 `void_t<decltype(...)偏特化` 的机器级等价：编译器把要求逐条替换、任何一条在该
上下文不合法 ⇒ 整个表达式 false——**且失败原因保留到诊断层**。复合要求的箭头后面
跟的是**概念**（`same_as`/`convertible_to`），不是类型：`-> std::same_as<int>` 检查
"返回类型与 int 同一"，把 05 章 `is_convertible` 的推理嵌进语法。

**约束的三放置位 + 偏序**。同一模板参数可写：`template<std::integral T>`（形参约束）、
`template<T> requires std::integral<T>`（子句约束）、`template<T> ... requires` 尾置，
以及 C++20 内概念即可当占位符。重载决胜看**约束子句的合取范式蕴含**：🔧（已实测）：

```cpp
template <typename T> concept Base1 = std::destructible<T>;
template <typename T> concept Derived1 = Base1<T> && std::movable<T>;
template <Base1 T>    const char* who(T&&) { return "Base1"; };
template <Derived1 T> const char* who(T&&) { return "Derived1"; };
// who(42) 实测输出 Derived1 —— Derived1 蕴含 Base1，更受约束者胜
```

注意偏序判定是**句法级**的（子句包含关系），不是语义等价判定：两个逻辑等价但写法不同
的概念比不出胜负，会退化到签名偏序或二义——6.5 的深坑，工程对策是"概念树保持单继承
式细化"。

**约束一切可约束物**（6.6–6.8 清单）：普通成员函数用缩写 auto 即成员模板
（`void assign(std::integral auto)`，🔧 实测）；类模板形参（`template<std::semiregular T>
class Box`，🔧 实测特化匹配照常）；变量模板（`template<std::regular T> constexpr T
defaulted = T{};`，🔧 实测）；**模板别名也可以带约束**——但注意约束别名不改变
重载/特化匹配能力，它只是使用点检查。自由运算符、协程返回类型同样可约束。

**缩写形式与 `auto`（6.9/6.10）**：`void f(auto)` ≡ `template<auto:1> void f(T)`（无约束）；
`void f(std::integral auto)` ≡ 带约束版本。返回值位 `std::integral auto g()` 约束的是
推导出的返回类型。**`T&&` 与概念的配合**是接口设计关键决策点：`std::integral auto&&`
几乎从不想要——概念会阻断引用折叠的推导直觉，转发界面用 `T&& + requires`，
值语义界面才用缩写（本目录立场，与原书 6.10 的示例方向一致 ⚠️ 未比对原文措辞）。

**标准概念库（6.11）分层**：`<concepts>` 基元（same_as/derived_from/convertible_to/
integral/invocable/predicate…）→ `<iterator>` 设施（weakly_incrementable/
input_or_output_iterator/sentinel_for/indirectly_readable…）→ `<ranges>` 层
（range/view/range_of…）。自测等价性 🔧（已实测）：
`std::invocable<F, Args...>` ≈ 05 章 `invoke_result_t` 探测器；
`std::same_as<std::remove_cvref_t<T>, U>` ≈ `decay` 风格比较。

## 权衡

- **concepts vs SFINAE**：诊断与界面全面胜；**没有赢的**是"从失败候选集中回落"的体验——
  概念不满足也是"no matching function"+回溯链（05 章实测），只是链条可读。
  另一处残余优势：SFINAE 可以**探测失败后再造替代方案**（fallback 重载天然多），
  concepts 写 fallback 要显式 `not C<T>` 补一个重载，包约束组合易出二义。
- **约束的验证成本**：概念体不要求是模型（model）——`requires` 通过不代表类型真有语义
  律（`regular` 的半群公理、`range` 的迭代可重复性都不检查）；概念是**必要非充分**，
  文档与测试仍要背语义合同（Niebler《Concepts & Hints》博文口径 ⚠️ 未直连）。
- **库概念缺位的现实**：C++20 只标准化了语言机制+一部分迭代器/范围概念；
  `printable`、`numeric` 类要自定——标准委员会自评"首批概念不全"是公开立场（见演进节）。

## 相邻概念对比

- **概念 vs traits 布尔**：`is_integral_v<T>` 是值，概念是**带检查规则的谓词**
  （概念本身隐含 `requires bool` 检查）；`enable_if` 桥接两个世界。
- **概念 vs 虚接口/静态断言**：虚接口是运行期合同的类型化，static_assert 是体内心证；
  概念把合同放进**重载决议**——只有它能影响"哪个函数被选中"。
- **缩写模板 vs 显式 template<>**：语法糖与展开严格对应，无语义差异；选哪个看约束密度。

## 最新演进与工业实践

- **"缺概念"的标准化补课**：C++23/C++26 持续向标准库补概念约束（ranges 的 v2 修订、
  `std::movable` 系算法签名收紧 ⚠️ 具体提案未逐一实测）；委员会承认 C++20 首版
  库中大量模板**未加**概念（如 `std::function` 至今约束宽松）——"库缺概念"是当前
  标准化长尾，不是误解。
- **ranges 概念争议（工业史实）**：Niebler 对 std::ranges 的仓促合并公开表达失望并淡出
  （range-v3 仓库 README 与 cppcon  talk 口径 ⚠️ 未直连原文）；range-v3 至今保留比
  标准更全的概念层（`indirect_callable` 等），是概念设计的活实验室——09 章再见。
- **fmtlib**：fmt 在 C++20 下用 `fmt::detail` 概念层实现"不可格式化类型"的**一句话诊断**
  （`formattable` 检查），是"concepts 改善诊断"主张的工业实证（对应 05 章对照实验的生产版）。
- **Boost.Hana 的退位启示**：Hana（仓库 boostorg/hana，Louis Dionne 主笔）用概念前技术
  实现全套"运行时-编译期统一接口"；concepts 出现后其接口层价值大幅贬值 ⚠️ 项目归档状态
  未实测确认——但作为"约束与类型的依赖计算"设计美学教材仍是上品。
- **P2996 反射与概念的关系**：静态反射落地后多数"结构探测"概念（有某成员吗）可泛型生成；
  概念作为**接口合同**层则不会消失（实测提案号见 00/01 章：P2996R13，2025）。
