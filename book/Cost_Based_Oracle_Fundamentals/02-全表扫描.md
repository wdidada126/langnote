# 02 · Tablescans（全表扫描）

> 原书第 2 章 ⚠️ 精读重构：章题 ✅ 实抓（Springer/Crossref），小节自拟；全部 Oracle 成本行为为文档/社区转述，标 ⚠️。

## 本章定位

把 01 章的成本模型套到最简单也最被低估的路径——全表扫描（FTS）上。Lewis 此章的颠覆点（社区共识转述 ⚠️）：**FTS 的代价几乎只取决于"段有多少块要读"，而与你查出多少行、查什么列基本无关**；而优化器对"块数"的认知来自统计信息，统计信息对块数的刻画恰恰最粗糙。

## 2.1 FTS 成本的骨架 ⚠️ 文档转述

- 成本 ≈ **要读的多块数 + 少量单块数**：扫描需先单块读段头块，然后沿 extent 图（fsm/位图块，视版本 ASSM 与否 ⚠️）顺序"碰"所有使用中的块，每次多块读至多 MBRC 块。
- 关键统计输入：`blocks`（高水位 HWM 下的块数）、`pct_free$`、`avg_row_len`、`num_rows`。
- 由 avg_row_len 折算"块均有效行数"，再得扫描块数估计；**rows 本身不增加扫描 I/O 成本**——返回 1 行和返回 100 万行的 FTS 一样贵 ⚠️。
- 与 01 章呼应：`db_file_multiblock_read_count` 越大，FTS 越便宜，索引越吃亏；操作层的 MBRC/参数视角见 [../Oracle12c数据库应用与开发/06-SQL执行计划与CBO.md](../Oracle12c数据库应用与开发/06-SQL执行计划与CBO.md)。

## 2.2 块数从哪来：统计如何"数块" ⚠️ 文档转述

- `DBMS_STATS.GATHER_TABLE_STATS` 收集 `blocks`/`empty_blocks`（老版本），新版本统一 `num_blks` 口径 ⚠️；采样率不足或表正在 ETL 波动时块数失真。
- 经典坑（本书时代广为流传 ⚠️）：
  1. **DELETE 不降 HWM**——清空一半数据的表 FTS 成本不变，直到 MOVE/SHRINK 或 direct path 语义介入；
  2. **行迁移（chained/migrated rows）只加"回表读"不加"扫描读"**，但按比例记成本，导致实际耗时 > 模型；
  3. **pct_free 的两种世界**：手工设定与 ASSM 自动管理下，优化器对空间利用的假设完全不同。
- 物理结构背景（表空间/段/块、HWM、PCTFREE 的运维定义）在系列里由 [../Oracle12c数据库应用与开发/03-存储结构-表空间与段区块.md](../Oracle12c数据库应用与开发/03-存储结构-表空间与段区块.md) 承担，本章只管"它们在成本公式里的角色"。

## 2.3 min/max cache hit：缓冲世界的两种记账 ⚠️ 文档转述

- 10g 优化器为表访问记两笔账：**min cache hit / max cache hit**（缓存命中率下限/上限假设），据此把"物理块需求"折算成"逻辑需求"。
- 后果：同一 SQL 在"全冷缓存"与"全热缓存"两端的成本可能差一个 MBRC 因子；这也是"成本对但耗时离谱"的常见解释入口 ⚠️。
- 概念谱系：这套"缓存假设折算"与 PostgreSQL 用 `effective_cache_size` 调整随机成本的思路同族 ⚠️，对照 [../PostgreSQL技术内幕_查询优化深度探索.md](../PostgreSQL技术内幕_查询优化深度探索.md)。

## 2.4 缓存选项与直接路径 ⚠️ 文档转述

- 对象的 `CACHE / NOCACHE / CACHE READS` 存储属性进入模型：大表 NOCACHE + 全扫倾向 direct path read（绕过 LRU 主链、批读进 PGA/SGA 私有区，9i 并行默认如此 ⚠️）。
- 直接路径的记账差异：串行 FTS 走缓冲多块读，并行/超阈值扫描可能走直接路径——**两条路径的成本参数不同源**，这是"加并行度成本骤降"的机制 ⚠️。
- 演进注：11g 起 `_serial_direct_read`、12c 自适应直接读（ADBKM 类阈值机制，官方文档转述 ⚠️）让串行扫描也大量走直接路径，本书的纯缓冲假设需按版本修正。

## 2.5 "扫描总是便宜"的判断链 ⚠️ 文档转述

Lewis 给出一条实践判断（重构转述 ⚠️）：决定走 FTS 还是索引，比"选择性 5%"这类经验值更可靠的是——
1. 表块数 ÷ 有效 MBRC ≈ 扫描成本量级；
2. 索引侧成本 = 索引块 + 回表单块（受聚簇因子支配，见 [05-聚簇因子.md](05-聚簇因子.md)）；
3. 两者之差与"缓存中已有什么"比较；
4. 用 10053 验证（[14-10053跟踪文件.md](14-10053跟踪文件.md)）。
- 改写案例库的对应物：当模型算对了而 SQL 仍慢，问题多在谓词写法与驱动方向，案例见 [../Oracle查询优化改写技巧与案例.md](../Oracle查询优化改写技巧与案例.md)。

## 2.6 常见误区 ⚠️ 文档转述

- "SELECT 列表瘦身能降 FTS 成本"——错（I/O 按块不按列；仅宽行溢出块数变化时才间接影响）。
- "FTS 一定比索引慢"——错，块少/MBRC 大/聚簇差时 FTS 常胜；这正是 CBO"看起来偷懒"的根源。
- "统计信息新 = 块数准"——错，ETL 清空-重灌型表在收集窗口外 HWM 变化即失真。
- 治理层对策（规范、预聚合、分区裁剪思路）另见 [../数据库高效优化.md](../数据库高效优化.md)。

## 2.7 一次 FTS 成本核算走查（示意数字，非实测 ⚠️）

目标：把 2.1 的骨架跑通一遍，建立"数字感"。

1. 输入：表 T，`blocks=16000`，`avg_row_len=120`，`num_rows=1500000`，8K 块，MBRC=8。
2. 折算块均行数：块净空间 (8192−块头/行目录开销) ÷ 120 ≈ 60 余行——与 1500000/16000≈94 的字典口径差 ⇒ pct_free 与行目录在两头拉扯（2.2 坑 1 的量化入口）。
3. 扫描 I/O ≈ 16000/8 = 2000 个多块单位；启用 workload 统计后按"多块相对单块的实测比"再修正（1.3 呼应）。
4. CPU 项 ≈ 扫描块数×块扫描单价 + 150 万行×行处理单价——块均行少时 CPU 占比升高（宽行表的另一面）。
5. 结论形态：Cost≈2000+CPU 折算。此后任何"谓词再毒辣也不减 2000"的直觉都应成立；若不成立，回查 2.4 直接路径改写。

## 2.8 分区与并行对 FTS 账本的改写 ⚠️ 转述

- 分区裁剪命中 k/n 分区：成本表观为"k 个分区各自 blocks/MBRC 之和"——裁剪失败则全分区累加，比不分区更贵（分区键选择是 02+05+11 三章的复合决策）。
- 并行度 d：扫描量分摊，成本 ≈ 全量/d 级别（启停开销另计）；"并行降扫描成本、升资源风险"的双面性在 [../Oracle12c数据库应用与开发/13-高并发系统的架构与设计.md](../Oracle12c数据库应用与开发/13-高并发系统的架构与设计.md) 有系统级讨论 ⚠️。
- 与兄弟对照：PG 侧同题（分区序扫描/并行启动成本）见 [../PostgreSQL技术内幕_查询优化深度探索.md](../PostgreSQL技术内幕_查询优化深度探索.md) ⚠️ 文档级。

## 2.10 三个经典案型（社区转述 ⚠️）

**案型一：清库后的幽灵成本**
- 现象：夜间 ETL 清空重灌的小表，白天仍按"亿级块数"被定价，优化器坚决走索引，实际 FTS 明明更便宜。
- 解剖：HWM 不随 DELETE 下降（2.2 坑 1），统计里 blocks 未重收集 ⇒ 模型输入虚胖。
- 处方：灌数后立即 `GATHER_TABLE_STATS`；结构性方案是 TRUNCATE 重排或分区交换装载（操作层 [../Oracle12c数据库应用与开发/07-SQL性能诊断与调优实践.md](../Oracle12c数据库应用与开发/07-SQL性能诊断与调优实践.md)）。

**案型二：MBRC 调大后的索引坟场**
- 现象：DBA 照"最佳实践"把 `db_file_multiblock_read_count` 从 8 调到 32（存储升级），大量 SQL 改走全表扫描，系统吞吐反降。
- 解剖：1.2/2.1 的杠杆——扫描单价除以 4，索引相对变贵 4 倍当量；模型没错，环境假设变了。
- 教训：本书"改一个参数=改一类计划"的活案例；参数实验必须配 SPM 灰度（各章演进节反复出现的现代答案）。

**案型三：宽行表的"每块三行"**
- 现象：含大 VARCHAR2/CLOB 定位器的表，优化器按 avg_row_len 折算"块均行数"极低，任何谓词下索引/扫描竞价都失真。
- 解剖：行链/溢出块（2.2）让块数统计与真实读取量脱钩；行目录开销未计。
- 处方方向：垂直拆分宽列、LOB 改 SECUREFILE 外置（按版本 ⚠️），属"修模型输入"的 01 章哲学应用。

## 核心概念速览（中英对照）

- **全表扫描** — full table scan（FTS）：按 extent 顺序多块读遍历段内块的路径。
- **高水位线** — high water mark（HWM）：段曾使用过的块边界，FTS 读到此为止。
- **段头块** — segment header block：存放 extent 图/位图指针的块，扫描的单块成本来源。
- **块数统计** — blocks statistic：优化器对表体积的唯一直接刻度，`GATHER_TABLE_STATS` 采集。
- **行迁移** — migrated row：行移块保留原行目录，扫描漏读、回表补读的失真源。
- **行链** — chained row：行长超块被拆分，扫描按多行计。
- **min/max cache hit** — 缓存命中率上下限假设，10g 表成本的双账本。
- **直接路径读** — direct path read：绕缓冲池的大块读，与缓冲扫描成本参数不同。
- **NOCACHE** — nocache 存储选项：影响扫描走缓冲还是直接路径的对象属性。
- **pct_free** — 空闲百分比：决定块均有效行数与扫描块数折算。
- **ASSM** — 自动段空间管理：以位图块代 freelists，改变空间语义的段管理模式。
- **自适应直接读** — adaptive direct reads（12c）：按阈值自动切直接路径，本书模型的现代修正。

## 最新演进与工业实践

- **12c–23ai 扫描路径**：官方文档转述 ⚠️，自适应直接读（12c）、In-Memory Column Store（12c+，列存扫描以向量化+SIMD 重定义"扫描成本"，19c/23ai 持续增强）；均不改 FTS 在字典层的统计口径，但改变实际耗时分布——19c 性能管理指南（✅ 可达：https://docs.oracle.com/en/database/oracle/oracle-database/19/tgdba/ ）的 IO 校准章节承接此话题。
- **Exadata/云底座**：Storage Index 与智能扫描（官方产品文档转述 ⚠️）让"块数≈成本"再次失真——谓词在存储层过滤，扫描物理量由列热度决定；这是 Lewis 模型在 2024–2026 的最大环境变化。
- **统计自动化**：`ESTIMATE_PERCENT=>DBMS_STATS.AUTO_SAMPLE_SIZE` 默认近全表精确抽样（11g+，文档转述 ⚠️），块数与 num_rows 失真率下降，但 HWM 语义坑依旧存在。
- **观测替代**：旧版靠 tkprof/timing 猜扫描行为；现靠 ASH（`db file scattered read` / `direct path read` 事件占比）与 SQL Monitoring 直接看每计划行的实际行数与耗时——操作路径见 [../Oracle12c数据库应用与开发/07-SQL性能诊断与调优实践.md](../Oracle12c数据库应用与开发/07-SQL性能诊断与调优实践.md)（文档转述 ⚠️）。
- **论文线**：扫描 vs 索引的代价权衡源头是 Selinger 1988（✅ DOI：https://doi.org/10.1145/50202.50214 ）的 access path 代价框架；系列谱系见 [../../db/db.md](../../db/db.md)。
