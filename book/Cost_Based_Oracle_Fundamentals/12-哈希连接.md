# 12 · Hash Joins（哈希连接）

> 原书第 12 章 ⚠️ 精读重构：章题 ✅ 实抓（Springer/Crossref），小节自拟；成本与内存行为为文档/社区转述，一律 ⚠️。

## 本章定位

9i 起 CBO 的默认大件连接方法。Lewis 此章的锋芒在于指出：**HJ 的成本公式简单到"可疑地便宜"**——两个输入各扫一遍、与行数近似线性，于是只要统计稍有偏差，优化器就有系统性偏向 HJ 的引力；而它要求的"两侧都全量物化/不可提前终止"恰是模型最不敏感的部分 ⚠️。

## 12.1 成本骨架 ⚠️ 转述

- 两阶段：build（小侧入哈希表）+ probe（大侧逐行探测）。
- 模型式：`cost ≈ 扫描A + 扫描B + (内存不足时：临时段写出+重读 × passes)`。
  - **理想单趟（one-pass）**：I/O 成本 = 两输入扫描成本之和——与 02 章 FTS 定价复用同一套"块数/MBRC"；
  - **多趟（multipass）**：溢出按桶分区写盘再读，每多一趟乘近 2 倍临时段 I/O ⚠️。
- 内存输入：workarea 受 `pga_aggregate_target`/`workarea_size_policy` 与 `_hash_area_size`（旧式显式）支配；本书时代"设了 hash_area_size 成本就翻转"是常见演示 ⚠️。
- 无序输出：无法利用已有排序、不能喂 stopkey——与 [13-排序与归并连接.md](13-排序与归并连接.md) 的排序项联合定价时才完整 ⚠️。

## 12.2 对输入的要求与路径绑定 ⚠️ 转述

- 两侧都要求**全量行源**（无索引式提前停止），因此谓词选择度只影响"扫多少块"，不影响 HJ 自身乘数——这与 NL 的"探查次数"结构形成对照（→ [11-嵌套循环连接.md](11-嵌套循环连接.md)）⚠️。
- 后果（社区转述 ⚠️）：小结果集一侧被错误放大（10 章基数高估）时，HJ 成本随扫描线性上升但仍可能"赢"竞价；真实执行却因一侧其实很小而 NL 本可完胜——"HJ 抢走 NL 的活然后慢十倍"的病理解剖。
- 分区 wise join：两侧按连接键同构分区时只配对着分区扫描（local/对偶分区），成本表观为"每分区小 HJ 之和"；不对齐分区则退全量 ⚠️。

## 12.3 分布与倾斜 ⚠️ 转述

- 并行 HJ 的分布方法（broadcast / partition hash / hybrid，9i 引入 ⚠️ 名转述）进入成本：广播小表免重分布，适合 build 侧小；不对称时成本差一个倍数。
- 值倾斜（NULL 巨量、单值热点）：哈希桶不均 → 某进程多趟/长尾，模型对此**无感知** ⚠️；NULL 不参与连接的语义与"NULL 巨多仍进扫描成本"的账目错位是经典陷阱。
- 与位图/Bloom 预过滤的组合（10g 起 Bloom，12c 命名强化 ⚠️）：HJ 的 build 侧键集编为 Bloom filter 提前下推到 probe 侧扫描，**执行层改扫描量、不改成本模型**——又是"实际快于 cost"的一侧 ⚠️。

## 12.4 为什么 CBO"爱"HJ（精读重构）⚠️ 转述

1. 公式无乘数悬崖（不像 NL 的探查次数项），统计误差的下行风险被平滑；
2. 9i 时代 HJ 是"新默认"，成本参数与特性开关倾向它（`_optim_..._hash_...` 家族，名 ⚠️ 转述）；
3. DSS 负载（星型、大事实表互连）恰是 HJ 的物理主场；
4. OLTP 混合负载里它对基数错误的"钝感"反过来成隐患 ⚠️。
- Lewis 的处方仍是：修统计、必要时 `USE_NL/USE_HASH` 显式，并把翻转事件登记进基线管理（12 章时代靠 profile，现代靠 SPM ⚠️）。

## 12.6 HJ 成本核算走查（示意 ⚠️ 非实测）

沿用 11.6 的 A(1 万行/200 cost) 与 B(1000 万行)。

1. B 侧扫描：10 万块 ÷ MBRC(8) = 12500 I/O 片 + 行处理 CPU 片。
2. build 选小侧 A（优化器自动 swap 输入角色）：哈希区可容纳 1 万×行宽 ⇒ 单趟。
3. HJ 总账 ≈ 200 + 12500 + probe 比较 CPU ⇒ 对 NL 的 14 万乘积项大胜——12 章"大行源对大行源"主场成立 ⚠️。
4. 内存反例：若误把 B 当 build 侧（统计未反映实际膨胀/倾斜），workarea 溢出 multipass：临时段读写两轮，账目 12500→近 2×(B 块数)——成本式里 passes 系数从 trace 的 `#jso`/workarea 估行可见（段名 ⚠️ 转述）。
5. 与 11.6 合并看：外层 100 行 ⇒ NL 1600 胜 HJ 1.27 万；外层 10 万行 ⇒ HJ 胜。交叉点在"探查成本×次数 = 扫描成本"处解出——**方法选择本质是 10 章基数的一句话函数**。
6. 速记：本走查中 HJ 账对基数误差的敏感度≈0（只随扫描量线性走），NL 账≈1（随外层基数线性放大）——两章交叉图（11.10）的斜率来源。

- [ ] 倾斜体检：连接键 GROUP BY 计数 top 值 vs NULL 占比（12.3 两病同治前先确诊）。

## 12.8 本章自测

1. 为什么"谓词选择度不影响 HJ 自身乘数"？那它影响什么？（两侧扫描块数/行数）
2. broadcast 与 partition-hash 分布各在 build 侧多大时占优？给一句直觉。
3. Bloom 过滤器为什么"改执行量不改成本"？对 12.2 的误判有缓解吗？
4. 说出 HJ 抢 NL 生意的完整因果链（基数高估→乘积项显贵→线性式显便宜）。
5. NULL 占连接键 80% 时，HJ 的真实耗时与模型账各错在哪端？

## 12.9 HJ 模型的三条限界（重构总结 ⚠️）

1. **规模下限失效**：一侧极小时 HJ 的固定成本（建表/哈希函数）摊不平，模型仍按线性给价——对小侧"过于慷慨"，需靠 11.10 交叉图找边界。
2. **内存记账静态化**：passes 由"优化器自估的可用 workarea"决定，而真实可用量受并发争抢（12.7 第一条）——同一 SQL 高峰期计划翻转的隐藏第三变量。
3. **值分布盲区**：桶深不均/NULL 洪水都只改执行不改成本（12.3）；观测上"one-pass 计数>0"即是模型已被现实打脸的物证。
- 与 01 章呼应收口：HJ 是"成本平滑"哲学的极致，也因此是"平滑即盲目"的极致；本章与 11 章对读才完整。

- 在 `[../Oracle12c数据库应用与开发/02-实例内存与后台进程.md](../Oracle12c数据库应用与开发/02-实例内存与后台进程.md)` 复核 PGA 结构，为 12.7 治理清单补"参数落在哪个内存组件"一列。
- 设计一个自适应连接观察实验（纸面 ⚠️）：制造外层基数高估 100 倍的统计，预测 12c 下"初选 NL→切换 HJ"或反向的触发条件。
- HJ 记账速默（贴墙版 ⚠️ 自拟）：
  - 单趟：`cost ≈ 扫A + 扫B + CPU(哈希/探测)`；
  - 溢出：`+ (passes−1) × 临时段读写`；
  - 并行：`÷ DOP ± 重分布/广播项`；
  - 三句话：乘数不随基数涨、内存决定趟数、倾斜不入账。
- 与其他方法的对账单（收口 11–13 三章）：同一对输入，NL 账在"次数×单价"、HJ 账在"两扫+内存"、SMJ 账在"两排+两扫"；把 11.6/12.6/13.6 三组示意数字并到一张表上，你会亲眼看到交叉点如何随外层规模移动——这就是 CBO 连接方法竞价的全部直觉底盘。

## 核心概念速览（中英对照）

- **哈希连接** — hash join（HJ）：build 小侧入表、probe 大侧逐行探测。
- **build/probe 侧** — build input / probe input：两侧角色，影响内存占用与分布策略。
- **单趟/多趟** — one-pass / multipass：workarea 充足与否引发的临时段 I/O 倍增。
- **工作区** — workarea（PGA 管理）：受 pga_aggregate_target 约束的执行内存配额。
- **_hash_area_size** — 旧式手工哈希区上限（隐藏参数 ⚠️ 名转述）。
- **分区 wise** — partition-wise join：双端按连接键同构分区时的配对局部化。
- **广播** — broadcast distribution：小表全量分发各并行进程免重分布。
- **Bloom 过滤** — Bloom filter pruning：build 键集位图下推 probe 扫描的预过滤。
- **无序性** — hash 无序：不能利用有序性/提前终止的结构性短板。
- **倾斜盲区** — skew blindness：模型对哈希桶不均无感知。
- **成本引力** — cost gravity to HJ：公式平滑导致的系统性偏选倾向。
- **输入交换** — input swap：优化器自选 build/probe 角色的动作。
- **哈希分区** — hybrid/partition hash 分布：并行下两侧按键重分布对齐。
- **workarea 争抢** — workarea contention：并发执行件挤占 PGA 造成的假性 multipass。
- **自适应半径** — graceful/adaptive hashing（研究线）：把"单趟/多趟"二值改连续谱的现代算法族；含"DOP 切分/并发争抢导致的假性溢出"这一工程近亲 ⚠️。

## 最新演进与工业实践

- **12c 自适应连接**（文档转述 ⚠️）：执行期在 NL↔HJ 间切换，12.2 的"基数错→HJ 抢活"事故面显著收窄；12c 起 Bloom 增强（多表 Bloom、Bloom 进存储层）。
- **In-Memory/Exadata**：HJ 的 probe 侧扫描由列存向量化或智能扫描承担（产品文档转述 ⚠️），multipass 概率随 PGA 管理改善下降；`V$SQL_WORKAREA_ACTIVE` 类监控仍是首选（名 ⚠️ 转述）。
- **19c/23ai**：workarea 自动调优与 parallel 语句服务器配额（`PGA_AGGREGATE_LIMIT` 语义，转述 ⚠️）；官方 23ai 性能管理指南目录 ✅ 可达：https://docs.oracle.com/en/database/oracle/oracle-database/23/tgdba/index.html 。
- **跨引擎对照**：PG 哈希连接（扩容/批式执行、OOM 降级策略）见 [../PostgreSQL技术内幕_查询优化深度探索.md](../PostgreSQL技术内幕_查询优化深度探索.md)；现代"perfectly hash join"（Blanas 等，未核 DOI ⚠️ 不给链接）把本书"内存不足即 multipass"的粗粒度记账细化为自适应半径——HJ 内核算法研究的当代线。
