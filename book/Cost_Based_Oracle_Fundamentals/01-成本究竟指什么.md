# 01 · What Do You Mean by Cost?（成本究竟指什么）

> 原书第 1 章 ⚠️ 精读重构：章题与主旨 ✅ 实抓（Springer/Crossref），小节划分为本目录自拟，Oracle 行为一律文档转述标 ⚠️。

## 本章定位

全书的地基章：回答"执行计划里那个 Cost 列到底是什么单位"。Lewis 的核心答案（社区转述广泛一致 ✅ 主旨）：**cost 不是时间、不是资源百分比，而是"按优化器模型折算后的块访问次数"**——一个无量纲的相对刻度。理解这一点，才能理解后面 13 章所有公式为什么长那样。

## 1.1 成本的历史包袱：从 RBO 到 CBO ⚠️ 文档转述

- RBO（规则优化）按固定优先级选路径，与数据量无关；Oracle 自 8i/9i 起转向"唯一受支持"的 CBO（12c 后 RBO 路径彻底退役，官方文档转述 ⚠️）。
- 本书前言明示写作动机之一：大量从 RBO 迁移的人把"cost 越小越好"当成绝对真理，或反过来认为 CBO 的 cost 毫无意义——两种误解都源于不懂成本单位 ⚠️。
- 使用层对照：[../Oracle12c数据库应用与开发/06-SQL执行计划与CBO.md](../Oracle12c数据库应用与开发/06-SQL执行计划与CBO.md) 讲"怎么让 CBO 工作起来"，本章讲"CBO 的尺子是怎么造的"。

## 1.2 I/O 成本：两种读与一块 MBRC ⚠️ 文档转述

优化器把 I/O 分为两类，代价折算规则不同：

| 读类型 | 触发者 | 折算 |
|---|---|---|
| 单块随机读（db file sequential read） | 索引探块、回表 | 每块记 1 个成本单位 |
| 多块顺序读（db file scattered read） | 全表扫描、快速全扫描 | 每"次读"记 1 个单位，一次最多读 `db_file_multiblock_read_count`（MBRC）个块，即每块成本 ≈ 1/MBRC |

- 推论（Lewis 反复强调的模型特性 ⚠️）：**一次多块读的第 2 到第 MBRC 块近乎白送**。这是 CBO 在统计缺省时偏爱全表扫描的结构性原因。
- 经典后果：表 8000 块、MBRC=8 时，全表扫描的 I/O 成本 ≈ 8000/8 = 1000；而通过聚簇差的索引取 5000 行，成本可能是 5000 次单块读 + 索引自身——扫描反而便宜 ⚠️。展开见 [02-全表扫描.md](02-全表扫描.md) 与 [04-B树索引基础访问.md](04-B树索引基础访问.md)。

## 1.3 CPU 成本的加入（9i/10g 时代语境）⚠️ 文档转述

- 10i 之前 cost 纯 I/O；9i 起在启用系统统计（system statistics）后，cost 掺入 CPU 时间片，10g 公式化 ⚠️。
- 两类统计：**noworkload**（用伪基准测单块/多块/CPU 的相对比）与 **workload**（从真实负载采样）。CPU 快、I/O 慢的盘阵上，收集 workload 统计会系统性地"把成本往 I/O 上压"，计划随之漂移——本书时代的著名坑 ⚠️。
- 时间模型：cost 换算成耗时时用 `cost × 单块读耗时 + CPU 周期数 × 周期耗时`，这也是"Cost 值相同的两个计划耗时可差几倍"的解释 ⚠️。

## 1.4 成本 ≠ 时间：三个不等式 ⚠️ 文档转述

1. **单位不等**：cost 是折算块数，无时间纲。
2. **非线性不等**：等待（锁、latch、IO 队列）不进模型；模型假设系统空闲。
3. **半连接/提前终止不等**：stopkey（`ROWNUM<=10` 类）使真实读取远小于估算，cost 对"提前退出"的折算长期粗糙 ⚠️（12c 的 stopkey 成本细化见 13 章演进节）。
- 系列互参：调优层次观（先定位卡在扫描/连接/锁/复制哪层）见 [../../db/db.md](../../db/db.md)；执行计划排查顺序（估算行数 vs 实际行数偏差优先）同文与 [../Oracle12c数据库应用与开发/07-SQL性能诊断与调优实践.md](../Oracle12c数据库应用与开发/07-SQL性能诊断与调优实践.md)。

## 1.5 本章方法论：把模型当"可调节对象" ⚠️ 文档转述

- Lewis 的招牌主张：与其 hint 一条 SQL，不如修正模型的输入（统计）或参数（MBRC、系统统计、伪列统计），**修一类问题** ✅ 此句为 Springer 简介原话方向。
- 可动旋钮清单（本书时代）：`gather_table_stats/gather_index_stats`（采样率、手工 SET_xxx_STATS）、`db_file_multiblock_read_count`、系统统计收集模式、10053 trace 验证 ⚠️。操作细节对应 [14-10053跟踪文件.md](14-10053跟踪文件.md)。
- 跨引擎映射：PostgreSQL 的 cost 同样是"折算 I/O 页数"（`seq_page_cost/random_page_cost`），其 `cpu_operator_cost` 对应 Oracle 的 CPU 成本项 ⚠️ 文档级对照，详见 [../PostgreSQL技术内幕_查询优化深度探索.md](../PostgreSQL技术内幕_查询优化深度探索.md)。

## 1.6 常见误读辨析 ⚠️ 文档转述

- "Cost 27 比 Cost 53 快一倍"——错，二者仅可比同实例同统计态下的相对优劣。
- "优化器选错是因为它笨"——多数场景是统计撒谎（采样、直方图缺失、聚簇因子被行迁移破坏），见 [05-聚簇因子.md](05-聚簇因子.md)、[07-直方图.md](07-直方图.md)。
- "显示行数和真实行数差不多就行"——错，基数误差在连接里级联放大，见 [10-连接基数估算.md](10-连接基数估算.md)。

## 1.7 模型参数速查（重构 ⚠️ 转述）

| 参数/对象 | 层级 | 对成本的作用 |
|---|---|---|
| db_file_multiblock_read_count | 会话/实例 | 多块读的折算分母，扫描↔索引天平主砝码 |
| 系统统计（noworkload/workload） | 实例 | I/O 与 CPU 的相对定价基准 |
| cpu_cost / io_cost 列 | 计划行 | 分项记账：CPU 片与折算 I/O 片 |
| PCTFREE / 段块数 | 对象 | 决定扫描侧"块数"输入 |
| 统计采样率 | 对象 | 决定 num_rows/blocks 的保真度 |
| optimizer_mode（FIRST_ROWS_ALL/CHOOSE 等，名按 ⚠️） | 会话 | 不改变单位，只改变竞价目标的加权 |

## 1.8 一次完整的"成本读表"示范（精读重构示例，数字示意非实测 ⚠️）

给定计划行 `TABLE ACCESS FULL, Cost=520`，反推链条：

1. 查段块数（示意 4000 块）与有效 MBRC（示意 8）→ 扫描 I/O ≈ 500。
2. 加段头/位图块等单块项 → 520 与打印值吻合 ⇒ 模型没被统计坑，剩下看行数估算。
3. 若同 SQL 的索引方案 Cost 更高但实测更快 → 查 05 章 CF 是否被高估、或 01.4 的缓存不等式是否在起作用。
4. 每一步都可在 10053 找到打印（→ [14-10053跟踪文件.md](14-10053跟踪文件.md)）。

## 核心概念速览（中英对照）

- **成本单位** — cost unit：优化器模型中折算后的块访问计数，非时间非百分比。
- **单块读** — single-block read / db file sequential read：索引式随机读，每块成本记 1。
- **多块读** — multiblock read / db file scattered read：顺序批量读，每块成本 ≈ 1/MBRC。
- **MBRC** — db_file_multiblock_read_count：一次多块读的最大块数，扫描/索引天平上的关键砝码。
- **系统统计** — system statistics：noworkload/workload 两模式，决定 I/O 与 CPU 的折算比。
- **CPU 成本** — CPU cost：9i/10g 起计入成本公式的 CPU 周期分量。
- **缓冲读** — buffered access：经 buffer cache 的常规访问路径，模型默认假设。
- **直接路径读** — direct path read：绕过/旁路缓存的大块读，折算规则不同。
- **成本模型** — cost-based model：把统计信息映射为计划代价的沙盘，模型错则计划错。
- **提前终止** — stopkey / early termination：TOP-N 类查询实际只读部分数据，cost 折算粗糙点。
- **统计操纵** — SET_xxx_STATS：绕过重新收集、直接改字典统计值以修模型的手段。
- **10053 事件** — event 10053：打印优化器决策全过程的 trace，模型的可观测接口。
- **RBO 遗产** — rule-based optimizer：按固定优先级选路径的旧优化器，本书的对照背景。

## 最新演进与工业实践

- **时间统计模型（2024–2026）**：Oracle 官方仍维持"cost=折算块数+CPU"的框架；19c/23ai 的性能管理文档（Database Performance Management Guide，✅ 链接可达：https://docs.oracle.com/en/database/oracle/oracle-database/19/tgdba/ ）转述 ⚠️：workload 系统统计的采集与 `DBMS_STATS.GATHER_SYSTEM_STATISTICS` 流程不变，但默认基线更倾向 workload 模式。
- **MBRC 的黄昏**：现代存储（ASM/闪存/SAN 预读）下"多块近乎免费"假设失真；官方文档转述 ⚠️：11g 后多块读行为受 `_db_file_direct_io_count` 等隐藏参数与异步 I/O 影响，公开建议是"用系统统计而不是手改 MBRC"。
- **自适应与计划稳定**：12c 的 Adaptive Query Optimization 与 SQL Plan Management（SPM）没有改成本公式，而是在"cost 选出的计划"之外加了执行期纠偏与计划锁定层 ⚠️（23ai 目录：https://docs.oracle.com/en/database/oracle/oracle-database/23/tgdba/index.html ）。
- **实证研究呼应本章主旨**：成本模型与现实的鸿沟是学术公认问题——Selinger 等的 System R 成本优化器开山文（Access Path Selection in a RDBMS, SIGMOD 1988，✅ DOI 校验：https://doi.org/10.1145/50202.50214 ）确立"统计→选择度→代价"范式；Leis 等《How Good Are Query Optimizers, Really?》（PVLDB 9(3), 2015，✅ DOI 校验：https://doi.org/10.14778/2850583.2850594 ）用基数误差证明"cost≈时间的代理"在真实负载上常不可靠；2025 年续作《Still Asking: How Good Are Query Optimizers, Really?》（PVLDB，✅ DOI 校验：https://doi.org/10.14778/3750601.3760521 ）确认十年后该问题仍未解决——Lewis 二十年前"模型不是现实"的告诫仍是主线。
- **工业实践**：作者 Jonathan Lewis 持续在其博客（✅ 可达：https://jonathanlewis.wordpress.com/ ）输出 CBO 行为分析，可作本书之外的更新源 ⚠️ 转述；国内实践中"统计信息基线+SPM 指纹"的固计划组合（参见 [../Oracle12c数据库应用与开发/07-SQL性能诊断与调优实践.md](../Oracle12c数据库应用与开发/07-SQL性能诊断与调优实践.md) ）是本章思想的操作化形态。
