# 05 · The Clustering Factor（聚簇因子）

> 原书第 5 章 ⚠️ 精读重构：章题 ✅ 实抓（Springer/Crossref），小节自拟；全部行为为文档/社区转述标 ⚠️，未实测。

## 本章定位

聚簇因子（CF）是本书"改变读者认知"密度最高的一章：它解释了 04 章定价公式里最重的乘数从哪来、为什么会撒谎、以及**为什么大量 OLTP 系统的索引其实是摆设**。Lewis 的贡献在于把 CF 从"一个统计项"升格为"数据组织与负载顺序的函数"。

## 5.1 定义与几何直觉 ⚠️ 文档转述

- 定义：按索引键序做一次全索引扫描（遍历叶子链）时，**相邻键值所属表块发生切换的次数**。
- 两个端点：
  - 最好 CF ≈ 表块数（键序=存储序，每次切换前把一块读穿）；
  - 最坏 CF ≈ 索引行数（键序与存储序无关，每行一个新块）。
- CF 不是"比率"而是"次数"，其量纲与 04 章回表项 `rows × CF/rows` 直接相乘——所以 CF 翻倍，回表成本翻倍 ⚠️。
- 与 02 章呼应：CF 恶化时 FTS 的"块数/MBRC"显得便宜，CBO"弃索引投扫描"多半是模型正确而数据组织失败 ⚠️。

## 5.2 CF 的生产方式与失真源 ⚠️ 文档转述

- `GATHER_INDEX_STATS` 时代：9i 起可全扫/估算采样，采样在聚簇良好但分布不均的索引上产生系统性偏差（本书时代坑 ⚠️）。
- **行迁移（migrated rows）**：行因 UPDATE 变长迁走后，索引键仍指旧块目录项，扫描时多一次单块读却不一定按新块计切换——CF 与真实成本脱钩 ⚠️。
- 序列主键+并发提交（commit SCN 有序）→ CF 近乎完美；**批量乱序导入/按时间倒序归档/多应用共用不同插入序** → CF 崩坏 ⚠️。
- Lewis 的社会学观察（重构转述 ⚠️）：一张表往往有多个索引，各自期望不同的插入序；**任何"对所有索引友好"的聚簇都不存在**——这是"为最重要的查询选聚簇"论断的由来。

## 5.3 手工校正：向模型说实话 ⚠️ 文档转述

- `DBMS_STATS.SET_INDEX_STATS` 直接改 CF 字典值（不改数据），本书招牌操作：
  - 场景：知道 CF 被采样/迁移失真 → 用脚本全扫测算真值 → SET 回去 → 计划翻正。
  - 约束：下次自动收集作业会覆盖——需锁统计 `LOCK_INDEX` 或调整作业（运维细节操作层见 [../Oracle12c数据库应用与开发/05-索引与约束.md](../Oracle12c数据库应用与开发/05-索引与约束.md)）⚠️。
- 验证通道：10053 trace 里打印优化器实际使用的 CF，与字典值逐字对照（→ [14-10053跟踪文件.md](14-10053跟踪文件.md)）⚠️。

## 5.4 改数据组织的选项与代价 ⚠️ 文档转述

| 手段 | 效果 | 代价 |
|---|---|---|
| 重建表（按目标键序 INSERT） | 目标索引 CF 趋最优 | 其他索引 CF 受损；停机/空间 |
| 反向键索引 reverse key | 消除热块争用 | 键序被反转，范围谓词 CF 灾难 |
| IOT（索引组织表） | 数据即主键序，主键路径 CF≈块数 | 二级索引 ROWID 间接层，谓词列非主键时又回到 CF 问题 |
| 哈希聚簇/簇表 | 指定键共置 | 维护复杂，现代版本鲜用 ⚠️ |
| 分区 + 本地索引 | 每分区小 CF | 裁剪失效时逐分区累加 |

- 12c 的 `clustering_factor` 增强与 AUTO 统计下的稳定化属版本差异（文档转述 ⚠️，本书未覆盖）。

## 5.5 决策心法（精读重构）⚠️ 文档转述

1. 看到"该用索引却全表扫"：先 `SELECT clustering_factor FROM user_indexes`（视图名 ⚠️ 转述）对照 `blocks` 与 `num_rows` 两端点。
2. CF 靠近坏端点 → 问题在数据组织/插入历史，hint 只是止痛。
3. CF 可疑（远离两端点的中值、或与数据常识不符）→ 全扫测真值 + SET_INDEX_STATS。
4. 改聚簇前跑"索引家族影响清单"：本表每个索引的谓词模式各自要什么序。
5. 与位图索引的替代判断 → [08-位图索引.md](08-位图索引.md)（DSS 环境 CF 痛点常被位图绕开）。

## 5.6 测 CF 真值的通道（精读重构 ⚠️ 转述，未实测）

三种由轻到重的手段：

1. **全扫对账**：按索引键序遍历（`SELECT rowid FROM t ORDER BY key` 的计划形态会暴露顺序访问），对照逻辑读计数与字典 CF——差一个数量级即失真嫌疑 ⚠️。
2. **10053 直读**：定价段打印优化器所用 CF，与 `USER_INDEXES.CLUSTERING_FACTOR`（名 ⚠️ 转述）对表，排除"字典对、模型旧"的解析期缓存问题。
3. **脚本重算**：Lewis 社区流传的经典游标脚本——按键序读相邻 rowid 的块号（DBMS_ROWID 解 file/block），统计变化次数即 CF 定义的可执行化 ⚠️（本目录不背书其逐字正确性，仅记录方法论）。

回填：`DBMS_STATS.SET_INDEX_STATS(ownname, indname, indpart=>NULL, num_lblk?, clustering_factor=>真值)` 形态（参数名以 ⚠️ 转述为准），随后 `LOCK_INDEX` 防自动收集覆盖。

## 5.7 CF 的生命周期管理（工程清单）

- **建表期**：为最高频路径选定聚簇键（序列/时间戳入表顺序）——一次决策长期吃红利（11.3 的"内层热块"也源于此）。
- **装载期**：批量乱序导入后必重算目标索引统计；增量归档会单调恶化 CF（尾部新块+键值旧 → 切换数暴涨）。
- **变更期**：行迁移高发（变长列频繁 UPDATE）时把 `INITRANS/pctfree`（按版本 ⚠️）纳入体检，迁移率有专用统计视图（名 ⚠️ 转述）。
- **校正期**：锁统计+手工 SET 是"止疼"，重建聚簇才是"手术"；两者都进 SPM 灰度（文末演进）。
- **多索引权衡表**：列出本表所有索引→各自期望插入序→按业务权重投票→唯一聚簇方案（Lewis 式会议纸笔工作 ⚠️）。

- 数据实验设计（纸面即可 ⚠️）：同一张表分别按键升序/随机/逆序装载，预测三种 CF 量级与 4.6 第二组成本的移动方向，误差归因写清。
- 反向键索引辩论题：给"高并发序列写入一律用反向键"的观点列三条反例场景（范围谓词/归档区间/位图替代）。
- 回看 01 章不等式：CF 失真同时污染成本与真实耗时两端，各举一条机制。
- CF 判读速查（重构 ⚠️）：`CF ≈ blocks` ⇒ 索引天堂；`blocks ≪ CF ≪ rows` ⇒ 先查迁移/乱序混合；`CF ≈ rows` ⇒ 该键路径按"每行一块"记成本，索引基本出局；`CF > rows` ⇒ 统计/迁移异常，直接进 5.6 重算流程。
- 与 11 章接口一句：NL 的内层探查每次都是"索引三项式"，所以**聚簇决定 NL 的生死**比决定 HJ 更直接——热小维表若 CF 崩坏，整个 OLTP 计划骨架会改向。

## 5.10 一段史料（社区转述 ⚠️）

本书出版前，CF 在英文/中文社区资料里基本只有"越大越差"一句话；Lewis 的贡献链是：定义可视化（块切换计数）→ 采样失真机制 → SET_INDEX_STATS 操作通道 → "插入序是产品决策"的工程文化。此后各引擎文档普遍把 clustering 提为一级统计概念——读 04/11 章时把这四步当背景音：你会在别的书里不断重逢它们。

补充三行版（贴评审墙用 ⚠️ 自拟）：

- CF 是历史，不是属性：改装载方式=改 CF=改一类计划。
- 修 CF 先问"真值还是假值"：真值坏→动数据；假值坏→动统计。
- 任何"索引失效"报告，CF 一栏不许空白。

## 核心概念速览（中英对照）

- **聚簇因子** — clustering factor（CF）：键序全索引扫描时的表块切换次数。
- **块切换** — block switch：相邻键值落在不同表块造成的额外单块读源。
- **行迁移** — migrated row：行迁块留目录指针，CF 与真实 IO 脱钩的主因。
- **统计锁定** — lock statistics：阻止自动收集覆盖手工 SET 值的开关。
- **SET_INDEX_STATS** — 手工写字典统计（含 CF）的 DBMS_STATS 过程。
- **反向键索引** — reverse key index：键字节反转分散热块，牺牲范围扫描聚簇。
- **索引组织表** — IOT：数据按主键 B 树组织，主键路径天然聚簇。
- **二级索引** — IOT secondary index：经 OVERFLOW/逻辑 ROWID 间接，含猜针机制 ⚠️。
- **哈希聚簇** — hash cluster：按键哈希共置行，特定等值负载的最优组织。
- **本地索引** — local index：分区级统计使 CF 作用域缩小到分区。
- **插入序依赖** — insert-order dependency：CF 是负载历史的函数而非表的固有属性。
- **块切换率** — block-switch ratio：CF/rows 的归一化读数，>0.5 基本宣告回表死亡。
- **热块争用** — hot block contention：序列尾部单块高并发的 latch 问题，反向键的另一半动机。
- **逻辑 ROWID** — logical ROWID（IOT）：主键+物理猜测构成的间接行地址，含猜失代价 ⚠️。
- **统计缓存** — dictionary/object stats cache：SGA 中统计副本，改字典未生效的常见原因（名 ⚠️ 转述）。

## 最新演进与工业实践

- **11g+ 统计自动化下的 CF**：默认全表扫式精确统计让 CF 计算更稳（文档转述 ⚠️），但行迁移失真机制未变；23ai 统计话题见官方指南（✅ 可达：https://docs.oracle.com/en/database/oracle/oracle-database/23/tgdba/index.html ）。
- **SQL Plan Management（11g+ ⚠️）**：当 CF 修复需要窗口期时，用 baseline 把"已被证伪的坏计划"钉住、灰度验证新统计——本书时代只能靠 outline/hint 的两难，SPM 给了工程化解；操作视角参见 [../Oracle12c数据库应用与开发/07-SQL性能诊断与调优实践.md](../Oracle12c数据库应用与开发/07-SQL性能诊断与调优实践.md)（12c 目录版对应其 SPM 转述节）。
- **In-Memory 与 Exadata**（产品文档转述 ⚠️）：列存/智能扫描路径下 CF 不参与定价（没有回表概念），"CF 决定命运"的适用范围收窄到行存 OLTP——但行存仍是 Oracle 负载主体。
- **观测现代化**：CF 失真的后果（索引被弃用/回表风暴）今天用 ASH 历史直接看 `db file sequential read` 的对象热点与 SQL 计划漂移，替代本书时代翻 trace+Statspack 的手工作业 ⚠️（ADDM→ASH/AWR 工具链演进，转述）。
- **对照与谱系**：CF 的通用对应物是"表的物理序与索引键序相关性"，PostgreSQL 以 `pg_stats.correlation` + CLUSTER 处理（对照 [../PostgreSQL技术内幕_查询优化深度探索.md](../PostgreSQL技术内幕_查询优化深度探索.md) ⚠️）；理论源头仍是 Selinger 1988 的 index 代价中"页引用数"项（✅ DOI：https://doi.org/10.1145/50202.50214 ），系列论文线见 [../../db/db.md](../../db/db.md)。
