# 09 · Query Transformation（查询变换）

> 原书第 9 章 ⚠️ 精读重构：章题 ✅ 实抓（Springer/Crossref），小节自拟；变换清单与行为按 9i/10g 语境转述，一律 ⚠️。

## 本章定位

CBO 不是"给原 SQL 选路径"，而是**先把 SQL 改写成一批等价形态，再在变换×路径×顺序的爆炸空间里挑最便宜的**。本章列出主要变换及其"为什么会改变成本"的机制——它也是全书与"改写技巧类书"（[../Oracle查询优化改写技巧与案例.md](../Oracle查询优化改写技巧与案例.md)）分界最清晰的章：**你手工做的每一条改写，优化器理论上都能自己做——只要它算得对** ⚠️。

## 9.1 启发式 vs 成本驱动 ⚠️ 转述

- 启发式（heuristic）：条件满足即变，不看成本（如早期简单合并视图）；成本驱动（CBO-driven）：变换后进入竞价，赢者用（如复杂视图合并、OR 展开）⚠️。
- 后果：同一 SQL 加一个谓词/索引可能让"是否变换"翻转，计划呈**不连续跳变**；Lewis 的忠告：不理解变换层的人会把"成本模型正确但行为诡异"归咎于优化器随机性 ⚠️。
- 控制阀：`QUERY_REWRITE`、`REWRITE`、`MERGE`、`UNNEST`、`EXPAND_OR` 一类 hint 及隐含参数按版本增删（名字 ⚠️ 转述）；`_optimizer_cost_based_transformation` 之类控搜索宽度 ⚠️。

## 9.2 变换主力清单（重构 ⚠️ 转述）

| 变换 | 英文 | 成本学动机 |
|---|---|---|
| 视图合并 | view merging（simple/complex） | 打通内外谓词，让基索引的过滤下推进入定价 |
| 谓词下推/上推 | predicate pushdown / pullup | 提早过滤减行；或让连接侧选择度可见 |
| 子查询展平 | subquery unnesting | IN/EXISTS 变连接，进入 10–13 章连接定价体系 |
| OR 展开 | OR-expansion | 每支各走最优索引，UNION ALL 合并去重代价换索引命中 |
| IN 列表展开 | in-list iteration | IN 当驱动行源嵌套循环，防全表扫 |
| 连接消除 | join elimination（11g+ 成型） | 外键/非空保证下整个表退出计划 |
| 星型变换 | star transformation | 维度位图/B 树合并出连接键，事实表走位图（接 [08-位图索引.md](08-位图索引.md)） |
| 物化视图重写 | query rewrite | 用 MV 竞价替代基表聚合/连接（统计与新鲜度决定敢不敢用 ⚠️） |
| GROUP BY 位置调整 | place group by / rollup 类 | 先聚后连缩小行源 |

- 传递闭包在 06 章讲过估算侧，其"生成新谓词"动作本身也是一种（恒为启发式的）变换 ⚠️。

## 9.3 变换与统计的纠缠 ⚠️ 转述

- 变换竞价用的仍是同一套统计输入：列选择度错 → 该变的不变、不该变的乱变。典型：**绑定变量隐藏了谓词值**，OR 展开/视图合并的竞价失去信息（→ [06-选择度组合难题.md](06-选择度组合难题.md) 6.4）⚠️。
- MV 重写额外要 `rewrite enabled` 的刷新保证与可信度判定（enable no validate 的信任缺口 ⚠️）。
- 10053 的 `TRANSFORMATION/` 段落打印每次尝试与弃用原因（段落名 ⚠️ 转述）→ [14-10053跟踪文件.md](14-10053跟踪文件.md)。

## 9.4 与手工改写的分工（精读重构）⚠️ 转述

1. 先看 10053/SQL Profile 报告里优化器**是否已尝试**该变换。
2. 尝试而弃用 → 查成本输入（统计）而不是改 SQL；未尝试 → 才考虑 hint 或改写触发。
3. 改写案例库对应：`../Oracle查询优化改写技巧与案例.md` 中"把 OR 改成 UNION ALL""手工展平 IN 子查询"等条目，正是替优化器完成它当时不敢做的 9.2 项 ⚠️。
4. 治理视角：变换依赖统计，统计依赖规范（命名收集作业、变更窗口）——规范层见 [../数据库高效优化.md](../数据库高效优化.md)。

## 9.5 搜索空间与编译时间 ⚠️ 转述

- 变换×连接顺序×路径三乘的搜索靠剪枝与"时间预算"类参数控制；超过复杂度阈值时优化器可能**放弃变换甚至退化为简化搜索**（`_optimizer_max_...` 家族，名 ⚠️ 转述），表现为"巨型 SQL 解析慢且计划次优" ⚠️。
- Lewis 的数仓告诫：百表级 ETL SQL 的解析期本身是生产问题，控制手段包括绑定变量分段、拆步骤、物化中间结果——工程层在 [../Oracle12c数据库应用与开发/08-常见SQL误区与最佳实践.md](../Oracle12c数据库应用与开发/08-常见SQL误区与最佳实践.md) 有使用级讨论 ⚠️。

## 9.6 OR 展开竞价走查（示意 ⚠️ 非实测）

表 T：`c1`、`c2` 各有 B 树索引；谓词 `c1=5 OR c2=9`，真实返回两列各 100 行、重叠 10 行。

1. 不展开：无复合索引可用 ⇒ 全表扫描（02 章定价）或 10053 里干脆无候选。
2. 展开：`SELECT ... WHERE c1=5 UNION ALL SELECT ... WHERE c2=9 AND c1<>5`（第二支带排重修正，Lewis 式展开细节 ⚠️）——两支各走索引+回表，成本 ≈ 2×(04 章三项式) ≈ 数百；对比扫描的数千 ⇒ 展开胜出，计划出现 `CONCAT` 行源（名 ⚠️ 转述）。
3. 翻转实验：把 c1 谓词改成返回 40% 行——第一支索引账崩溃，展开版成本>扫描版，优化器回退 ⇒ **同一变换的取舍随统计连续漂移**，正是 9.1"不连续跳变"的温和版；若两版成本相近而实测差大，回到 10 章查基数。
4. 手工改写判据（9.4 流程）：若 10053 显示"已试 OR_EXPANSION 且弃用"，你手写 UNION ALL 只是把弃用的计划强行钉上——先修统计再谈改写，案例对照 [../Oracle查询优化改写技巧与案例.md](../Oracle查询优化改写技巧与案例.md)。

## 9.7 控制旋钮速查（名以 ⚠️ 转述）

| 旋钮 | 职能 |
|---|---|

| MERGE / NO_MERGE / MERGE_LEADING | 视图合并方向（QB_NAME 定位块） |

## 9.9 变换与行源形态对照（重构 ⚠️）

| 变换 | 计划中可见的形态标记（名 ⚠️ 转述） | 常见弃用原因 |
|---|---|---|
| 视图合并 | 视图名从行源消失，基表上提 | 合并后连接宽度/基数恶化 |
| 谓词下推 | 视图/UNION 分支内出现新 FILTER | 分支含 ROWNUM/聚合等阻断器 |
| 子查询展平 | EXISTS 变 SEMI（LEFT）JOIN 行源 | 展平后 NDV 估算使竞价失败 |
| OR 展开 | CONCAT + 各支路独立访问 | 分支重叠修正成本>全扫 |
| 连接消除 | 表整体从计划消失 | 约束未启用/可空性不满足 |
| 星型变换 | 事实表前挂 BITMAP AND/子查询串 | 位图缺失或连接键 NDV 估算不利 |
| MV 重写 | 基表被 MV 行源替换 | 重写信任度/成本竞价败 |

- 判读法：改一条谓词后对比两版 10053 的行源树，"哪一层出现/消失"直接对应上表；9.1 的不连续跳变在此表上找相邻两格。
- 9.4 流程的表格化补充：先查格（变换名）再查价（成本输入）。

## 核心概念速览（中英对照）

- **查询变换** — query transformation（QT）：优化器对等价改写空间的成本驱动探索。
- **启发式变换** — heuristic transformation：免竞价、命中即用的改写。
- **视图合并** — view merging：把内联/派生视图并入外层块。
- **谓词下推** — predicate pushdown：过滤条件移入视图/ UNION 分支内。
- **子查询展平** — subquery unnesting：IN/EXISTS 标量/半连接化。
- **OR 展开** — OR-expansion：析取式改 UNION ALL 多分支各取最优路径。
- **IN 列表迭代** — in-list iteration：字面值列表作驱动行源。
- **连接消除** — join elimination：约束证明下冗余表退出计划。
- **星型变换** — star transformation：维度子查询合并过滤事实表。
- **物化视图重写** — materialized view query rewrite：以 MV 竞价替换基表运算。
- **改写控制** — hint 类 REWRITE/NO_REWRITE、QB_NAME 查询块命名（现代可用 `@QBNAME` 引用 ⚠️）。
- **解析期** — compilation/optimization time：搜索空间过大时的隐藏成本。

## 最新演进与工业实践

- **11g–23ai 新增变换**（文档转述 ⚠️）：join elimination 默认启用、复杂视图文档化增强、group by 放置类、`WITH` 子句合并、自动 MV 调优顾问（`DBMS_MLS`/tuning set 类工具，名以 ⚠️ 转述）；12c 的 top-n/聚合变换与 19c 持续增强使本书清单成"子集"。
- **SQL 优化器演进观**：官方 SQL Tuning Guide 23ai（转述 ⚠️，经 19c 性能管理指南入口 ✅ 可达：https://docs.oracle.com/en/database/oracle/oracle-database/19/tgdba/ ）承接变换开关与默认策略的版本差异表。
- **SPM 的护栏角色**：变换引起的计划翻转风险由 SQL Plan Baseline 兜底（11g+，文档转述 ⚠️）；这与 05 章演进同源，构成"变换自由+计划稳定"的现代组合。
- **跨引擎对照**：PG 的 pullup/pushdown 体系（子查询上拉、JOIN 树合并）、Calcite 的规则集 Volcano/Cascades 框架，通用叙述见 [../数据库查询优化器的艺术.md](../数据库查询优化器的艺术.md) 与 [../PostgreSQL技术内幕_查询优化深度探索.md](../PostgreSQL技术内幕_查询优化深度探索.md) ⚠️；CBO 变换竞价思想源自 Selinger 系的搜索函数 + 后续 Cascades 谱系（Goft 1989/Graefe 1993，本目录未核其 DOI ⚠️ 不给链接），论文线在 [../../db/db.md](../../db/db.md)。
- **工业实践**：2024–2026 厂商趋势是"更多变换自动化+基线保稳定"（Oracle 自动索引/自适应、各云数仓 rewriter 规则内置）；手写改写降格为"教学与兜底"，本书 9 章的判读框架恰是判断"改写是否已被覆盖"的唯一可靠知识 ⚠️。
