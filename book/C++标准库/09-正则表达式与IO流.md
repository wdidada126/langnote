# 第 9 站 · 正则表达式与 Stream I/O（原书第 14–15 章）

> 覆盖原书第 14 章「正则表达式」（14.1 匹配接口 → 14.10 签名细究）与
> 第 15 章「以 Stream 完成 I/O」（15.1 共通基础 → 15.14 效能）。
> 一站两章的理由：regex 在本书时代是全新章（C++11 收编 boost.regex），
> 体量与 iostream 的十分之九篇幅相比不匹配，且两者在「文本处理管线」上会师。

## 核心概念速览（中英对照）

- **匹配四大接口** — match / regex_search / regex_match / regex_replace：整串全匹配 vs 局部搜索 vs 替换。
- **匹配结果** — match_results（smatch）：次表达式（捕获组）的随机访问袋 + 前后缀。
- **正则迭代器** — sregex_iterator / sregex_token_iterator：把「所有匹配 / 指定子表达式」枚举成区间。
- **语法旗标** — syntax_option_type：ECMAScript 默认，可选 basic/extended/awk/grep/egrep 与 icase。
- **流类层次** — Stream Class Hierarchy：basic_ios → basic_istream/basic_ostream → iostream / fstream / sstream 菱形。
- **串流状态** — Stream State：goodbit/eofbit/failbit/badbit 四标志 + rdstate/clear，异常模式可选开。
- **操控器** — Manipulator：endl/setw/setfill/hex/boolalpha…——改「流状态」或「一次性参数」两类。
- **格式标志** — Format Flags：fmtflags 位袋（showpoint/showbase/uppercase/scientific/fixed…），**粘滞**。
- **sentry** — sentry：每个高层 I/O 成员函数体的 RAII 前置（flush .tie、缓冲准备）与后置。
- **缓冲区** — streambuf：get/put 两区 + seek 的底层存储抽象；`rdbuf()` 是重定向的抓手。
- **tie** — tie()：读前自动 flush 另一流的松耦合；cin 默认 tie 到 cout。
- **文件模式** — ios::in/out/app/ate/trunc/binary：打开语义组合拳。

## 动机：两套「文本进出」机制的互补

regex 管「结构化文本的识别与改写」，iostream 管「字符的流式搬运与格式化」。
两者共同的底层协议是**迭代器与区间**（第 5 站）：`sregex_iterator` 让「找出所有匹配」成为可迭代对象；
`istream_iterator<string>` 让整份文件成为区间；`ostream_iterator` 让算法直接往流里倒。

## 机制

### 1. regex 三件套（14.1–14.5）

```cpp
std::regex e(R"((\w+)\s+(\d+))");
if (std::regex_match(line, m, e)) {        // 整行必须全匹配
  auto name = m[1].str(); auto n = std::stoi(m[2]);
}
if (std::regex_search(text, m, e)) { ... } // 找第一处子串匹配
auto out = std::regex_replace(text, e, "$2-$1");   // 格式替换
for (sregex_iterator it(text.begin(), text.end(), e), e{}; it != e; ++it) { /* 每次匹配 */ }
sregex_token_iterator it(text.begin(), text.end(), e, {1});   // 枚举第 1 子表达式
```

- 14.2 的关键区分：`regex_match` 要**整段**，`regex_search` 允许局部——「验证用 match、提取用 search」。
- 次表达式编号 = 捕获组开括号序；`m.prefix()/m.suffix()` 给搜索型匹配的剩余上下文。
- 14.8/14.9：默认 ECMAScript（JS 语法）；POSIX 系（basic/extended）存在但工业界几乎不碰；
  `std::regex_traits` 可整体替换文法层（冷门扩展点）。
- 14.7 异常：坏模式抛 `regex_error`，`code()` 细分（`error_syntax/error_complexity/error_space`）。
- **性能红线**：`std::regex` 是出了名的慢（回溯引擎 + 构造开销），RE2（DFA、无回溯、不支持反向引用）
  常快 1–2 个数量级——生产高吞吐路径几乎不用 std::regex ⚠️ 结论性质，基准依文法而定。

### 2. iostream 分层解剖（15.1–15.2、15.13）

```text
basic_ios<CharT,Traits>            状态位/填充/宽度/facet 挂点
   ├─ basic_istream / basic_ostream   << >> getline read 等「高层格式化」成员
   └─ basic_iostream（菱形合流）
        ├─ ifstream/ofstream/fstream     文件：open/mode/文件描述器（15.9.5）
        └─ istringstream/.../stringstream 内存串
底层: basic_streambuf  get/put 区 + uflow/xsputn 虚函数族（自定义设备写这里）
特征: 一切类模板 double 在 CharT+Traits ⇒ char/wchar_t 两套全局对象（cout / wcout）
```

### 3. 状态机与「读失败一次全盘皆输」（15.4）

- `>>` 遇类型不符：设 failbit、**把输入推回缓冲**（不消费），之后所有 `>>` 都会立刻失败——
  经典死循环：`while (cin >> x)` 配 `if (fail) cin.clear()` 忘 `ignore()` 会无限重试同一坏值。
- eofbit 与 failbit 常同置（读到尾且读不到东西）；`badbit` 才是设备级灾难。
- 异常模式 `cin.exceptions(ios::failbit|ios::badbit)` 把状态检查换成 try/catch（15.4.4），
  书中示例偏爱它，工业代码罕见 ⚠️（性能与心智）。

### 4. 操控器的两类（15.6–15.7，高频事故点）

| 类别 | 例 | 生命周期 |
| --- | --- | --- |
| 粘滞标志 | hex/showbase/boolalpha/fixed/setprecision/setfill | 一旦设置**持续到流关闭**或再改 |
| 一次性 | setw | 只对**下一个**输出项生效 |
| 带副作用 | endl（写换行+flush）/ flush / ends | flush 成本被 15.14 点名：循环里用 '\n' 而非 endl |

「宽度包含进制前缀」实测：`std::setw(8) << std::setfill('0') << std::hex << 42` → `00000x2a`
（🔧 已实测 g++ 15.2，见 [../C++标准库](08-特殊容器与字符串.md) 同款样本）。

### 5. 自定义类型的 I/O（15.11）与紧耦合（15.12）

- `operator<<` 返回 `ostream&` 支持链式；`operator>>` 必须**自己检查失败并设 failbit**（15.11.2 约定）。
- 用户自定义格式标志（15.11.4）：`ios_base::xalloc/indexword/register_callback` 三元组——
  iostream 的「开放扩展、封闭修改」孔，冷门但面试杀手。
- `rdbuf()` 重定向（15.12.3）：`cout.rdbuf(&capture)` 把 cout 接到 stringstream——测试利器。
- streambuf 迭代器（15.13.2 + 9.4.3）：二进制文件↔容器的零格式化搬运。

## 权衡

- **iostream vs printf vs format**：类型安全/可扩展 vs 熟速 vs（C++20）三者最优格式化（见演进）。
- **ifstream 逐行 getline vs 读进 string 再 split**：前者内存友好；后者缓存/分割逻辑友好。
- **regex vs 手写 FSM**：14 章示例的分词场景，若热路径，RE2/手工 split 胜。
- **文本 vs 二进制模式**：`ios::binary` 在 Windows 只影响换行翻译（15.9 讲过 CRLF），不改变 seek 语义的
  「按字节」本质——跨平台坑在行尾不在模式。

## 相邻概念对比

- `stringstream` vs 字符串手工拼接：格式化输出（精度/对齐）前者胜；单纯 append 后者快（SSO + 预留）。
- `tie()`（松耦合，读前 flush）vs 共享 `rdbuf`（紧耦合，两流同一缓冲）——15.12 两个小节的对位题。
- `cin >>`（分词、跳空白）vs `getline(cin, s)`（整行、不跳）vs `istreambuf_iterator`（含空白的全量）。

## 最新演进与工业实践

- **C++11（本书自身）**：文件/串流对象的 move 语义与 `fstream f(path, mode)` 构造（15.9.2/15.10.2）；
  `long long` I/O；`sstream` 头拆分细化。
- **C++14/17**：`std::osd18n`（C++11 引入的弃用件）C++17 移除；`codecvt_utf8` 族 C++17 **弃用**——
  标准至今没有给出 UTF 转换的正统替身，工业实践走第三方（icu、tinyutf8、utfcpp 等 ⚠️ 选型依项目）。
- **C++20**：`std::format`（P2286R8，已核；🔧 实测 `format("{:x}|{:>6.2f}", 255, 3.14159)` → `ff|  3.14`）——
  编译期检查格式串（FMT 语法）、位置参数、`{:L}` locale 感知；iostream 的「格式化」职责被大面积接管。
- **C++23**：`std::print/println`（P2093 ⚠️ 编号未核实，仅记版次）——格式化 + 输出一步，默认不 flush。
- **工业实践**：
  - 高性能日志与序列化绕开 iostream：`fmt::format_to(output_iterator)`（FMT 库即 std::format 的胚胎，
    [fmtlib/fmt](https://github.com/fmtlib/fmt)）、abseil `StrFormat`（[abseil](https://github.com/abseil/abseil-cpp)）。
  - `std::ios_base::sync_with_stdio(false)` + .tie(nullptr) 是竞赛/吞吐场景标配（15.14.1 的 C 同步税）。
  - 正则性能问题至今无标准级解法：没有 RE2 型引擎进入 C++ 标准的日程落地 ⚠️，高吞吐场景一律引第三方。
  - 行为查证：[cppreference IO 库](https://en.cppreference.com/w/cpp/io)、libstdc++/libc++ 的 `testsuite`（链接见 00 站）。
