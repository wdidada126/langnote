> 与第 13 章「字符串」（13.1 目的与实例、13.2 细节描述、13.3 细究成员）。
> string 与 STL 的关系在 7.10.1 已埋线（「String 作为一种 STL 容器」），本章正式展开。

## 核心概念速览（中英对照）

- **容器适配器** — Container Adapter：stack/queue/priority_queue——在既有容器上换一副接口的模板套壳。
- **底层容器可换** — Underlying Container：stack/queue 默认 deque，priority_queue 默认 vector，可作第二模板参数替换。
- **优先队列** — priority_queue：最大堆封装（默认 `less<>` 准则 = 堆顶最大），只出不进语义。
- **位集** — bitset：编译期定长位向量（`<bitset>`），非容器（无迭代器协议），位运算/计数/测试全套。
- **字符串类** — basic_string<charT, traits, Alloc>：字符容器 + 数值转换 + 查找协议；三种 typedef（string/u16/u32/wstring）。
- **npos** — string::npos：`static const size_type = -1`，「找不到」的哨兵值——比较时注意无符号陷阱。
- **字符萃取** — char_traits：字符串对「字符是什么」的抽象层（C++20 收紧其合法范围 ⚠️）。
- **查找族** — find/rfind/find_first_(not_)of：三种查找策略（子串/反向/字符集），全部返回 npos 表失败。
- **数值转换** — sto* / to_string：`<string>` 的字符串↔数双向门（异常版），非异常版在 `<charconv>`（C++17）。
- **SSO** — Small String Optimization：短串存对象本体的实现技巧——**非标准规定**，但解释了「string 比 vector 便宜」。

## 动机：第 12 章是「借还接口」，第 13 章是「最重要的值类型」

适配器三件套的存在理由：算法/协议世界之外，还有「语义要窄」的需求——栈就该只会 push/pop/top。
12.1.3/12.2.3 甚至示范「不用适配器自己写一个 stack class」，然后指出标准版赢在**换底层容器只改一个参数**。
string 则相反：它是标准库里接口最宽的类（13.2 列了 14 组操作），
因为「文本」同时是容器、值、I/O 公民和 locale 消费者。

## 机制

### 1. 适配器内部（12.1–12.4）

```text
stack<T, Deque>      :  push/pop 都走 c.push_back / c.pop_back
queue<T, Deque>      :  push→back, pop→front（deque 两端 O(1) 是默认选择的理由）
priority_queue<T, Vector, less<T>>:
    push→push_back+push_heap;  pop→pop_heap+pop_back;  top→front
    默认 less ⇒ 最大堆。要最小堆: priority_queue<T, vector<T>, greater<T>>
    * 没有 lower_bound/迭代器：堆不是有序容器，「已序区间算法」禁止喂它。
```

细究节（12.4）给出 `protected c`（底层容器公开给派生类）这一冷门后门——历史上不少「想访问 stack 内部 vector」
的需求靠派生解决。

### 2. bitset（12.5）

- `bitset<10>` 长度是**模板参数**：不可 resize（要动态位集 → `vector<bool>`/boost::dynamic_bitset ⚠️/手写 uint64 数组）。
- 全家族：`test/set/reset/flip/any/none/all/count` + `to_string/to_ullong` + 位运算符重载。
- 与 `vector<bool>` 的分工：定长 vs 变长；bitset 无迭代器协议（所以不是容器，也喂不进算法）。

### 3. string 的骨架（13.2）

- **构造/赋值重载密度全库第一**：C 串、`(ptr,n)` 对、`(n,c)` 对、子串 `(str,pos,len)`、初值列、迭代器对——
  13.3.2 按源类型分组罗列，值得当菜单读。
- **访问**：`[]` 无检查、`at` 抛 `out_of_range`；C++11 起 `&s[0]` 与 `s.data()` 保证连续 + 尾部隐含 `'\0'`
  （写 `s[s.size()]` 位置以外的 C 串行为是 UB——这条「可写性」是 C++11 对 C-API 生态的重大让步）。
- **修改**：append/insert/replace/erase/push_back/resize/clear——与 vector 同构但多了**位置裁剪语义**
  （`replace(pos,n,str)` 之类）。
- **查找**：`find` 族 + 比较 `compare`（三态 -1/0/1；它按 char_traits 码位序，**不走 locale**——校勘排序属第 16 章 facet）。
  `npos` 参与算术（`s.substr(p+1)` 当 p==npos → 极大下标 → 抛 out_of_range）——13.2.12 专节警示。
- **数值转换**（13.2.13）：`stoi/stol/stod...` 抛异常、`to_string` 系格式化简陋（永远定点/默认精度）——
  性能与格式两个维度都被 C++17 `charconv` 与 C++20 `format` 接管（见演进节）。
- **string vs vector\<char\>**（13.2.17）：接口重叠 95%，剩余 5% 是「查找族 + C 串互转 + 数值转换」——
  文本语义选 string，字节缓冲选 vector\<byte\>（C++17）或 string（二进制安全，string 可含 '\0'！）。

### 4. 效率注脚（13.2.16、15.14 呼应）

- SSO 让短串零堆分配（主流实现的 15/22 字节阈值，实现定义 ⚠️）；
- `c_str()` 不拷贝（返回内部缓冲，前提是你不碰容器）；`data()` C++17 起 const 版优先。
- 传参永远 `const std::string&` 或 `std::string_view`（后者见演进节）；返回值靠 RVO/move。

🔧 已实测 g++ 15.2（`-std=gnu++23`）的格式化/转换行为（与第 9 站共用的样本）：

```cpp
std::string s = "a,b,,c";
s.substr(s.find_first_of("bd")+1);          // ",,c"——跳过找到的字符
s.starts_with("a,");                        // true（C++20）
// ostringstream: hex+showbase 得 "0xff"；setw(8)+setfill('0') 得 "00000x2a"（宽度含进制前缀）
// from_chars("  123") → errc::invalid_argument：不跳空白、不收 '+'，与 stoi 行为不同
```

## 权衡

| 需求 | 选 | 理由 |
| --- | --- | --- |
| LIFO/ FIFO 语义要窄 | stack/queue 适配器 | 接口防呆；性能与直接用 vector/deque 相同 |
| Top-K 流式维护 | priority_queue | 每次 push/pop O(log n)，内存 O(K) |
| 定长标志位 | bitset | 编译期尺寸、无分配、可 `to_ullong` |
| 变长标志位 | vector\<bool\>（知 proxy 坑）或手写 uint64 数组 | vector\<bool\> 无 `data()`、不能取元素地址（04 站） |
| 文本处理 | string（拥有）+ string_view（观察） | 后者见演进节 |
| 与 C API 互操作 | string::data/c_str | C++11 起连续 + NUL 终止有保证 |

## 相邻概念对比

- **`stack` vs `vector` 当栈用**：后者 `pop_back` 少一层壳、可迭代；前者语义窄、防「中间掏元素」。
- **`queue` vs `deque`**：同前；12.2.4 明示适配器只暴露 push_back/pop_front/双向访问的裁剪。
- **bitset vs 整数位运算**：`uint64_t` 手工位 hacks 在 n≤64 时常更快（无 test/flip 边界检查）；
  bitset 赢在可读与 n 为编译期常量。
- **string 的 `operator<` vs `locale` 校勘**：前者逐 char_traits::lt（码位序），后者走 collate facet（第 10 站）；
  「排序结果不符合用户预期」的 bug 九成在这。

## 最新演进与工业实践

- **C++11（本书）**：`(n,'c')` 构造歧义修复、move 语义进 string、`u16string/u32string`、`to_string/stoi` 家族、
  写路径连续 + NUL 保证。
- **C++14/17**：`operator""s` 字面量后缀；`std::byte`；`charconv::to_chars/from_chars`（C++17，
  浮点 shortest-round-trip 在 GCC 8+/libc++ 可用；实测见上）。
- **C++17 · string_view**（P0254R2，提案存在已核）：`std::string_view`——「（可能非 NUL 结尾的）字符数组借用」，
  子串切分零分配；代价是**悬垂**（不拥有！返回 string_view 指向已析构临时串是新增头号 UB 类别）。
- **C++20**：`starts_with/ends_with/contains`；`operator<=>` 三路比较（P1614R2，已核）让 string 比较族统一；
  `constexpr std::string`（P0980R1，已核）——编译期字符串处理从幻想变为日常。
- **C++23**：`std::format` 全面接管「数值→文本」（P2286R8，已核，🔧 实测 `std::format("{:x}|{:>6.2f}", 255, 3.14159)`
  → `ff|  3.14`）；`string::push_back` 之外的容器化补齐与 `from_range` 构造。
- **工业实践**：
  - 解析器/分词器风格迁移：`string_view` 切片 + `std::from_chars` 数值 + `std::format` 输出，
    三者合计常比 regex/stringstream 快一个量级（std::regex 的性能在 09 站另述）。
  - abseil 的 `string_view/string_format` 早已内建同样路线（[abseil/strings](https://github.com/abseil/abseil-cpp)）；
    行为差异（不保证 NUL 结尾的 view 转 C 串）是其文档重点。
  - 二进制缓冲：`std::vector<std::byte>`/`std::span<std::byte>` 取代 `vector<char>` 的意图表达。
  - 查证入口：[cppreference basic_string](https://en.cppreference.com/w/cpp/string/byte)、
    [libc++](https://github.com/llvm/llvm-project/tree/main/libcxx) 的 string/string_view 测试。
