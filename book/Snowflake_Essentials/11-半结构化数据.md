# 11 半结构化数据（Semi-structured Data in Snowflake）

> 原书章：Ch.11 "Semi-structured Data in Snowflake"（pp.239–251），DOI `10.1007/978-1-4842-7316-6_11` ✅（Crossref 章级寄存实证）。
> 口径：页码区间一手实证；机制「官方文档转述 ⚠️ + ✅ URL」；含 🔧 类比实验 G4（本机 DuckDB/SQLite 实跑，**非 Snowflake 行为**）。

## 阅读目标

1. 理解 VARIANT 的"免 ETL 落地"价值：JSON 原样进表、子字段自动列式化进微分区统计。
2. 会写路径表达式与 FLATTEN 的"关系↔半关系"桥。
3. 掌握 INFER_SCHEMA 把"猜列"工程化的装载前奏。

## 1. 三类型与存储红利（⚠️ 转述，✅ https://docs.snowflake.com/en/sql-reference/data-types-semistructured）

- `VARIANT`（万能容器，≤16MB/值）、`OBJECT`（键值）、`ARRAY`（有序）——同表可与关系列混住（✅ semistructured-considerations）。
- 存储红利：微分区对 VARIANT **自动抽子字段成列式**、带统计——`WHERE obj:city='SH'` 也能吃分区裁剪（⚠️ 成书卖点，✅ semistructured-considerations）。
- 教学立场反转：传统数仓"JSON 必须先拍平"→ Snowflake"先住下、后塑形"——这是本章在全书中最具方法论冲击的一章（⚠️ 评述）。

## 2. 查询桥：路径、类型判断与 FLATTEN（自拟示意 SQL）

```sql
-- 路径提取 + 类型转换（:: 强转）
SELECT id, f:amount::FLOAT AS amt, f:tags AS tags FROM DEMODB.SALES.RAW_JSON;
-- FLATTEN 把数组炸成行；LATERAL 让外层列可被引用
SELECT r.id, fl.value::STRING AS tag
FROM DEMODB.SALES.RAW_JSON r, LATERAL FLATTEN(INPUT => r.f:tags) fl;
-- 对象键值也炸：fl.key / fl.value / fl.path / fl.seq
```

- `TYPEOF`/`TRY_CAST` 做防御性读取；`OBJECT_CONSTRUCT`/`ARRAY_CONSTRUCT` 反向拼装（⚠️，✅ https://docs.snowflake.com/en/sql-reference/functions/flatten）。
- 心智模型：FLATTEN=把 VARIANT 视图化为临时表的表值函数；嵌套循环用 LATERAL 缝合（⚠️）。

## 3. INFER_SCHEMA：装载侧的列发现

- `INFER_SCHEMA(LOCATION=>@stage FILE_FORMAT=>JSON)` 返回列名+建议类型，喂给 `CREATE TABLE ... USING TEMPLATE`；装载时配 `MATCH_BY_COLUMN_NAME`（⚠️ 转述，✅ https://docs.snowflake.com/en/user-guide/data-load-schema-evolution）。
- 与"VARIANT 整包入表"互补：前者通向**宽表化**、后者通向**延迟塑形**——入门者按下游消费方式二选一（⚠️ 教学建议）。

## 4. 🔧 类比实验：JSON 桥的本机原型（非 Snowflake 行为）

本机 DuckDB 1.5.5 + SQLite 3.45.3 实跑（2026-10-02，输出摘录）：

```
== G4 VARIANT/FLATTEN analog (DuckDB JSON + SQLite json_each) ==
extract: [('SH', 3)]
unnest: [('a',), ('b',), ('c',)]
json_each: [(10,), (20,), (30,)]
```

- DuckDB 侧：`'{"city":"SH","tags":["a","b","c"]}'::JSON` 列，`json_extract_string` 取标量、`unnest(CAST(... AS VARCHAR[]))` 把数组炸行——对应 Snowflake 的 `f:city` 与 `FLATTEN(f:tags)`。
- SQLite 侧：`json_each(d,'$.tags')` 表值函数炸数组——LATERAL 语义的近亲。
- **非 Snowflake 行为声明**：本机 JSON 扩展是**运行时解析**，无 VARIANT 微分区子列化、无路径剪枝统计、无 16MB 契约；实验只移植"路径提取+数组炸行"两张概念卡片，存储红利（本章第 1 节）在单机侧不存在——恰证 Snowflake 半结构化的护城河在存储层而非函数层。

## 5. 章内易错与疑问

- **易错 1**：`f:tags` 直接当数组比较——需 `::ARRAY`/`TRY_CAST`，同键多类型时取数随机踩坑（⚠️ 脏 JSON 防御）。
- **易错 2**：忘 `LATERAL` 引外层列报"invalid identifier"（⚠️）。
- **易错 3**：把 VARIANT 当万能——超大数组/深度嵌套触 16MB 上限装载失败；先拆再存（⚠️，✅ semistructured-considerations）。
- **疑问**：为什么本章排在装载章（Ch.12）之前？答：先懂"数据能以什么形态住下"，再学"怎么运进来"——教材编排的存储优先逻辑（⚠️ 评述）。

## 扩展深读点：VARIANT 建模三方案对比与炸行排障

### 同一份 JSON 的三种住法（决策对照，⚠️ 综合口径）

| 方案 | 建表 | 查询 | 适用 |
| --- | --- | --- | --- |
| 整包 VARIANT | `payload VARIANT` | 路径+FLATTEN | schema 未定/多态事件流 |
| 宽表化 | INFER_SCHEMA→显式列 | 纯关系 SQL | 稳定 BI 消费、聚合密集 |
| 混合 | 高频列+VARIANT 兜底 | 双轨 | 主流折中（raw→curated 分层入口） |

- 判据两问：**字段还会变吗**（变化→VARIANT）；**下游是聚合还是取原文**（聚合→宽表）。Ch.12 的模式演化让"先包后拆"的迁移成本逐年下降。

### FLATTEN 排障四规则（⚠️ 教学综合）

1. 键不存在返回 NULL 不报错——先 `TRY_CAST`+`TYPEOF` 探脏。
2. 同键多类型（"amount" 既有数又有串）→ 显式分支 `CASE TYPEOF(...)`。
3. 大数组炸行×多分区=行爆炸：先过滤再 FLATTEN（谓词上推）。
4. 嵌套数组要"双层炸"：两层 LATERAL，第二层引用第一层 `value`。

### 模式演化三种姿势速查（本章与装载章的接缝）

| 姿势 | 时机 | 载体 | 代价 |
| --- | --- | --- | --- |
| INFER_SCHEMA 一次性 | 首建表/回填 | 文件采样 | 采样外新键漏识 |
| MATCH_BY_COLUMN_NAME | COPY/Snowpipe 装载中 | 列名对齐 | 隐式列序依赖解除 |
| EVOLVE COLUMNS（后代 ⚠️） | 管道持续运行 | 自动加列 | 演化审计需接 Ch.8 元数据 |

- 三种姿势合看即一条光谱：**从"拍平一次"到"永远在拍平"**——VARIANT 兜底位随光谱右移而缩小，但 2026 仍未消灭它（raw 层信仰，⚠️ 社区共识）。

## 最新演进与工业实践

- **开放格式合流（2022→2026）**：Parquet/Iceberg 侧半结构化支持加深（✅ https://docs.snowflake.com/en/user-guide/data-unload-overview 与 https://docs.snowflake.com/en/sql-reference/sql/copy-into-location 均 200 实证），VARIANT 与列式开放格式的双向通道变宽（⚠️ 转述）。
- **AI 负载抬升本章权重**：非结构化文本/JSONL 进表喂 Cortex 批推理（embedding、COMPLETE 函数族，✅ https://docs.snowflake.com/en/guides-overview-ai-features 200 实证）——"先住下后塑形"教义在 2026 比 2022 更主流（⚠️ 评述）。
- **装载侧 schema 演化产品化**：Snowpipe 自动摄取+模式演化列（✅ data-load-schema-evolution）把 INFER_SCHEMA 从一次性脚本变成持续能力（⚠️ 转述）。
- **工业实践**：主流分层=raw VARIANT 落地 → curated 拍平宽表（dbt snapshots）；FLATTEN 的性能陷阱（大数组炸行×分区爆炸）在剖析器中已成经典课例（→ Tuning 03 章，⚠️ 社区共识转述）。
