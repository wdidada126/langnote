# 12 数据装载（Loading Data）

> 原书章：Ch.12 "Loading Data"（pp.253–281），DOI `10.1007/978-1-4842-7316-6_12` ✅（Crossref 章级寄存实证）。
> 口径：页码区间一手实证；机制「官方文档转述 ⚠️ + ✅ URL」；含 🔧 类比实验 G6 装载半（本机 DuckDB 实跑，**非 Snowflake 行为**）；示意 SQL 自拟。

## 阅读目标

1. 默写装载四件套路线：文件→Stage→（File Format）→COPY INTO / Snowpipe→表。
2. 分清批量（COPY）与连续（Snowpipe）两种节奏的选型判据。
3. 会用增量语义（不去重、靠"已载清单"+模式演化）搭最小 ELT。

## 1. 装载模型与 Stage 两端（⚠️ 转述，✅ https://docs.snowflake.com/en/user-guide/intro-summary-loading）

- Stage=文件集结区：**内部 Stage**（托管存储，含用户/表级隐式 Stage，`@%mytable` 语法）与**外部 Stage**（S3/Azure Blob/GCS 直连，IAM/凭据挂 URL）（⚠️，✅ https://docs.snowflake.com/en/sql-reference/sql/create-stage）。
- 本地文件入内部 Stage：SnowSQL `PUT file://... @stage`（其余客户端无 PUT，成书期事实 ⚠️）；浏览器路径=Snowsight Load Data 向导（Ch.4/5 的装载侧收口）。
- File Format 对象：CSV（分隔/引号/转义/换行）、JSON（多行/单行、`INFER_SCHEMA` 前哨 Ch.11）、Parquet/AVRO/ORC（列式直读）（⚠️，✅ https://docs.snowflake.com/en/user-guide/data-load-considerations-stage）。

## 2. COPY INTO：批量装载主引擎（⚠️，✅ https://docs.snowflake.com/en/sql-reference/sql/copy-into-table）

```sql
COPY INTO DEMODB.SALES.ORDERS
FROM @DEMODB.SALES.MY_STAGE/data/
FILE_FORMAT = (TYPE = CSV FIELD_DELIMITER=',' SKIP_HEADER=1)
PATTERN = '.*orders_.*\.csv.gz'
ON_ERROR = 'CONTINUE'
PURGE = FALSE;
```

- 关键语义四条（⚠️ 全部是入门误区高发地）：
  1. **不去重**：重复执行同 COPY 会重复入表——增量靠平台"已载文件清单"（同文件同元组指纹自动跳过）+ `VALIDATE`/`LOAD_HISTORY` 对账（✅ https://docs.snowflake.com/en/user-guide/data-load-transform）。
  2. `ON_ERROR` 决定脏行策略（CONTINUE/ABORT/SKIP_FILE），配合 `TRUNCATECOLUMNS` 兜超长。
  3. `PURGE=TRUE` 载后即焚源文件——默认 FALSE 保重跑余地。
  4. 装载吃仓库：COPY 消耗计算、走缓存（大仓热表快）——Ch.10 的账单在此发生（⚠️）。
- 变换位：`TRANSFORM`/列映射做轻量清洗（位置参数 `$1..$n` 元组寻址），复杂整形留给下游 SQL（⚠️ EL 取舍）。

## 3. Snowpipe：连续自动摄取（⚠️，✅ https://docs.snowflake.com/en/user-guide/data-load-snowpipe-intro）

- 形态：`CREATE PIPE` 绑 stage 自动触发；文件到达→**无仓库常驻**的服务化微批摄取；触发通道=云消息通知（SQS/Event Grid/PubSub）或 REST API 显式调用（✅ https://docs.snowflake.com/en/user-guide/data-load-snowpipe-auto-s3 同族经索引）。
- 计费独立于用户仓库（按文件/时长微计费 ⚠️ 成书口径），延迟"秒到分钟"级（⚠️）。
- 选型判据（成书口径 ⚠️）：人时批→COPY；到达即载、文件小而密→Snowpipe；巨型历史回填→COPY 并行切分。
- 排障入口：`COPY_HISTORY`/`PIPE` 状态 + Snowsight Loads 页（⚠️，✅ https://docs.snowflake.com/en/user-guide/ui-snowsight-data 经索引）。

## 4. 🔧 类比实验：COPY 的两端在本机长什么样（非 Snowflake 行为）

本机 DuckDB 1.5.5 实跑（2026-10-02，输出摘录；卸载半见 13 章）：

```
== G6 COPY INTO/unload analog (DuckDB csv/parquet) ==
loaded: [(1, 'ann'), (2, 'bob')]
```

- `CREATE TABLE stg AS SELECT * FROM read_csv('rows.csv')` ≈ `COPY INTO t FROM @stage`——"文件→表"的一步式心智；`read_csv` 的自动列推断 ≈ File Format+INFER_SCHEMA 合体。
- **非 Snowflake 行为声明**：DuckDB 无 Stage 概念（文件系统即 stage）、无"已载清单"增量语义（重复执行即重复插）、无服务端微批管道、无 ON_ERROR/PURGE 契约。第 2 节四条关键语义**一条都没被本机验证**——装载的工程难度恰全在平台侧。

## 5. 章内易错与疑问

- **易错 1**：`SKIP_HEADER` 与多文件表头错位——每文件首行都跳，合并文件需改策略（⚠️）。
- **易错 2**：CSV 内嵌换行未配 `FIELD_OPTIONALLY_ENCLOSED_BY`——列错位雪崩（⚠️ 经典事故）。
- **易错 3**：重跑 COPY"怎么又双叒载了"——误解增量边界：文件**新增/改名/重传**才会重载（⚠️）。
- **疑问**：为什么不讲流式 CDC 工具？答：成书期生态止于 Kafka Connector 萌芽（⚠️），本册覆盖"文件装载"即完成入门使命；CDC 深潜留给后续册。

## 扩展深读点：文件准备清单与节奏选型树

### 进 Stage 前的文件七检（⚠️ 综合本章事故高发点）

| 检项 | 通过标准 | 失配症状（对应易错） |
| --- | --- | --- |
| 编码 | UTF-8（含 BOM 声明处理） | 乱码/首列名带 \ufeff |
| 换行/内嵌换行 | 引号包裹+`FIELD_OPTIONALLY_ENCLOSED_BY` | 列错位雪崩（易错 2） |
| 表头行 | 统一有/无，`SKIP_HEADER` 与文件数匹配 | 多文件时表头混入（易错 1） |
| 分隔符/转义 | File Format 显式声明，不靠默认 | 隐式逗号事故 |
| 压缩 | gzip 等与 `COMPRESSION` 匹配 | 魔数报错 |
| 尺寸 | 单文件≤上限、大表切多文件并行 | 装载拖尾 |
| 命名 | PATTERN 可判别 + 与增量边界一致 | "怎么又载了"（易错 3） |

### 批量 vs Snowpipe 选型树（成书期口径）

```
到达节奏？─ 人时一批/日清 → COPY（仓库计费，重跑可控）
           ├─ 小而密连续  → Snowpipe（通知/REST 触发，微计费）
           └─ 巨型历史回填 → COPY 并行切分 + 事后对账 LOAD HISTORY
延迟要求 <1min？→ Snowpipe；成本敏感且可批→ COPY。
```

## 最新演进与工业实践

- **Snowpipe 家族化（2022→2026）**：Snowpipe **Streaming**（Kafka 连接器直写、行级延迟、绕开文件——2022 后 GA ⚠️）+ Snowpipe Automation/目录集成（✅ 现行页 https://docs.snowflake.com/en/user-guide/data-load-snowpipe-intro 与 https://docs.snowflake.com/en/user-guide/data-load-snowpipe-auto 均 200 实证）；"文件=装载唯一入口"的成书前提已被打破。
- **声明式装载**：目录集成/Auto Table Discovery/Refresh 自动发现新文件建管道（主题经官方索引 https://docs.snowflake.com/en/user-guide/llms.txt 登记，锚点 ✅ https://docs.snowflake.com/en/user-guide/data-load-snowpipe-auto 200）——本章手工 PIPE+通知的托管化后代（⚠️ 转述）。
- **模式演化转正**：`MATCH_BY_COLUMN_NAME + EVOLVE COLUMNS` 让加列免改管道（✅ https://docs.snowflake.com/en/user-guide/data-load-schema-evolution）——Ch.11 INFER_SCHEMA 的动态版。
- **工业实践**：ELT 主流=原始落地（COPY/Snowpipe）→ dbt 整形；装载对账（行数/校验和/唯一键）进 CI 门禁；Kafka/EventHub 直写蚕食小文件场景，大历史回填仍是 COPY 天下（⚠️ 社区共识转述）。
