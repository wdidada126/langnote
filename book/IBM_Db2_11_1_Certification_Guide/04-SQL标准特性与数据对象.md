# 04 · SQL 标准特性与数据对象（对齐考试域：Working with Data / Objects ⚠️ 推定）

> 章名 ⚠️ 推定（主题重构，见 00 降级声明）。DB2 语法/行为一律 ⚠️ 转述自 IBM 11.1 公开文档；本章 🔧 组为 SQLite 3.45.3 / DuckDB 1.5.5 实测，**全部是非 DB2 行为**，仅作 Db2 语法谱的概念锚点（登记于 00 第七节）。

## 一、章定位

Db2 认证里的 SQL 域偏"标准语法的 Db2 方言落点"：分页、MERGE、CTE、分组集、数据类型选型、以及 11.1 新对象（时段表/列组织表/JSON）。题型以"哪个语句合法/等价改写"为主。本章把 🔧 对照密度放在这里：拿可跑的引擎反衬 Db2 语法在标准谱系中的位置。

## 二、分页与行限制：FETCH FIRST 家族 🔧A

- Db2 立场（⚠️ 转述）：`SELECT ... ORDER BY ... FETCH FIRST n ROWS ONLY`，可配 `OFFSET m ROWS`；`OPTIMIZE FOR n ROWS` 是提示性取回优化（不同于 LIMIT 语义，考试爱混）。
- 🔧A 实测（非 DB2）：DuckDB 1.5.5 `OFFSET 2 ROWS FETCH FIRST 2 ROWS ONLY` 通过、`FETCH FIRST 2 ROWS ONLY` 通过；SQLite 3.45.3 同句报 `near "OFFSET"/"FETCH": syntax error`，仅认 `LIMIT 2 OFFSET 2`（返回 (3,)(4,)）。
- 结论锚点：Db2 属"标准语法阵营"（与 PG/DuckDB 同侧），MySQL/SQLite 方言阵营另一侧；移植审查先查这两族。
- 延伸考点：`FETCH FIRST ... ROWS ONLY` vs `WITH TIES`（SQL:2003 选项，Db2 支持情况 ⚠️ 未逐版核实，答题前回文档）。

## 三、MERGE 与变更语句 🔧B

- Db2 立场（⚠️ 转述）：`MERGE INTO t USING s ON cond WHEN MATCHED THEN UPDATE/DELETE WHEN NOT MATCHED THEN INSERT`，SQL:2003 血统；Db2 早年即支持，且 MERGE 可作触发器宿主。
- 🔧B 实测（非 DB2）：DuckDB MERGE 通过（dst 变 (1,10),(2,20)）；SQLite 报 `near "MERGE"`，其替代 `INSERT ... ON CONFLICT(k) DO UPDATE` VALUES 形式可用；带 FROM 的 `INSERT..SELECT..ON CONFLICT` 在 3.45.3 实测报语法错（VALUES 形式则可）——方言细节差异的活例。
- 考点提醒：Db2 的 UPDATE/DELETE 支持 `FROM`? 写法与子查询相关更新；"哪些方言里 MERGE=幂等 upsert"是跨引擎面试常客。

## 四、生成列、序列与标识列 🔧C 🔧D

- Db2 立场（⚠️ 转述）：生成列 `GENERATED ALWAYS AS (expr) VIRTUAL|STORED`，VIRTUAL 读时算 STORED 存时算；标识列 `GENERATED BY DEFAULT|ALWAYS AS IDENTITY`（序列家族之上）；独立序列对象 `CREATE SEQUENCE`。
- 🔧C 实测（非 DB2）：SQLite `GENERATED ALWAYS AS (a+b) STORED` 通过（2+3→5）；DuckDB 报 "Can not create a STORED generated column"——同一标准特性两引擎走向相反，Db2 的 VIRTUAL/STORED 双态恰是调和形态 ⚠️。
- 🔧D 实测（非 DB2）：DuckDB `CREATE SEQUENCE sq START 100 INCREMENT 5`+`nextval` 通过（100→105）；SQLite 报 `near "SEQUENCE"`，只能以计数表手工模拟。
- 考点：ALWAYS 标识列覆盖需 OVERRIDING USER VALUE?/BY DEFAULT 才能插显式值（配对题）；序列与标识列共用参数谱（CYCLE/CACHE? ⚠️）。

## 五、递归 CTE 与环保护 🔧E

- Db2 立场（⚠️ 转述）：`WITH RECURSIVE`（SQL:1999 正统在 Db2 的实现名即 WITH RECURSIVE），支持标准 `CYCLE ... SET flag USING path` 环检测与 `SEARCH BREADTH/DEPTH FIRST`?（特性年代归属 ⚠️ 存疑不展开）。
- 🔧E 实测（非 DB2）：两引擎 `WITH RECURSIVE c(i) AS (SELECT 1 UNION ALL SELECT i+1 FROM c WHERE i<5)` 均通过；`CYCLE n SET cyc USING path` 两家均语法错——标准特性普及度的现实刻度。
- 应用锚：树形遍历/层次查询是 Db2 考卷"老题新考"区；与 SQL Server 线 CTE 章对照读。

## 六、11.1 时段表（SYSTEM VERSIONING）🔧F

- Db2 立场（⚠️ 转述）：`ALTER TABLE ... ADD PERIOD SYSTEM_TIME(start,end) ... WITH SYSTEM VERSIONING`（双时态另有 VALID_TIME）；查询 `FOR SYSTEM_TIME AS OF / FROM..TO`；版本数据归档分区或同表。
- 🔧F 实测（非 DB2）：`CREATE TABLE tv(i INT) WITH SYSTEM VERSIONING` 在 SQLite/DuckDB 均语法错——2024–2026 年这仍是 Db2/PG(触发器路线)/SQL Server(系统版本表) 各家分道区，Db2 是标准 SQL:2011 原生路线代表 ⚠️ 转述。
- 考试角度：时段表的维护选项（KEEP VERSIONS? RETENTION）、历史查询谓词形态、与审计需求的对应关系。

## 七、数据类型与多模存储选型（⚠️ 转述）

- 定长/变长：CHAR/VARCHAR（上限约 32672 ⚠️ 页尺寸相关）、CLOB/BLOB、DECFLOAT 财务小数；LONG VARCHAR 类大字段进入弃用叙事 ⚠️。
- XML：原生类型 + 索引谱（path? 摘要索引）；JSON：11.1 以 BSON 存于 VARCHAR/CLOB? 路线并提供函数族（⚠️ 细节；后续版本转向原生 JSON 的演进见"最新演进"）。
- 空间/时序扩展与列组织表（ORGANIZE BY COLUMN ⚠️，BLU 引擎：列压缩字典、实时统计倾向）——"行表 vs 列表选型"是 11.1 时代新增考点。

## 八、表组织与分区（放置策略考点）

- 范围分区：`PARTITION BY RANGE (col) (START..END..EVERY..)`+ 分区索引；哈希分区表（10.5/11 谱系 ⚠️）打散热点。
- 聚簇：旧 MDC（多维聚簇）在 11.1 后进入淘汰叙事 ⚠️，替代路线=组织键（ORGANIZE ON KEY，列组织表）+ range clustering（11.1 新 ⚠️ 细节存疑）——代差注记务必配 #77 第 5/11 章主题读。
- 视图/MQT：逻辑视图、物化查询表（REFRESH DEFERRED? 与查询重写开关）、昵称/别名（联邦/远程对象命名 ⚠️ 联邦不在本册域内）。

## 九、常见陷阱（例题库向）

1. 把 Oracle 的 `ROWNUM` 直接搬进 Db2——分页考点用 FETCH FIRST；或忘 ORDER BY 使"前 N 行"语义不定。
2. MERGE 的 WHEN NOT MATCHED 分支漏插 NOT MATCHED BY SOURCE 语义差异（跨引擎混背高发）。
3. ALWAYS 标识列上硬塞显式值报 SQL0802N? 类（错误号示意）——换 BY DEFAULT 或 OVERRIDING 子句。
4. 时段表上加不兼容 ALTER/约束限制；版本膨胀需保留策略（⚠️）。
5. 生成列 VIRTUAL 上不能直接建某些索引形态?（转述口径，答题前回 11.1 文档核对，✅ https://www.ibm.com/docs/zh/db2/11.1.0 ）。

## 十·五、自测题（本目录自编，非原书题 ⚠️；🔧 组结论均指 SQLite/DuckDB 实测，非 DB2）

**Q1** 🔧 复述：写出标准阵营分页句，并说出本机哪个引擎拒绝它、报什么。
**答**：`ORDER BY c OFFSET 2 ROWS FETCH FIRST 2 ROWS ONLY`；DuckDB 1.5.5 通过，SQLite 3.45.3 报 `near "OFFSET"/"FETCH"` 语法错（🔧A 组，脚本 results.txt 可复查）。

**Q2** 移植题：一段 Oracle `(+)` 外连接 + ROWNUM 分页 + MERGE 的脚本迁到 Db2，三处各查什么？
**答**：外连接改标准 JOIN 写法（Db2 兼容向量可开 Oracle 方言位 ⚠️）、ROWNUM 改 FETCH FIRST、MERGE 语法核对 WHEN 分支覆盖面（04 章二/三节；跨引擎坑位口径）。

**Q3** 判断：`GENERATED ALWAYS AS IDENTITY` 列上直接插显式值一定报错。
**答**：不绝对——语句级 `OVERRIDING USER VALUE` 类子句可覆盖（⚠️ 转述语法位），或建列时用 BY DEFAULT；这是 D/四节考点"ALWAYS 不是绝对"。

**Q4** 场景：合规要求保留订单表全部历史行且主查询不减速，11.1 首选对象是什么？代价？
**答**：系统时段表（WITH SYSTEM VERSIONING，第六节 🔧F 锚：SQLite/DuckDB 均无此语法）；代价=版本数据膨胀、归档/保留策略与部分 ALTER 限制（⚠️）。

**Q5** 读题：`WITH RECURSIVE` 图上遍历疑似成环，标准解法是什么？两对照引擎支持吗？
**答**：标准 `CYCLE ... SET ... USING path` 环保护；🔧E 实测 SQLite/DuckDB 均语法错，只能手工 `WHERE NOT EXISTS/深度上限` 土办法——Db2 在标准支持面领先是常见考点（⚠️ 转述口径）。

**Q6** 选型：报表库大宽表聚合为主，行表还是 ORGANIZE BY COLUMN？依据两句话。
**答**：列组织表（BLU）——列压缩省 IO+聚合扫描只读所需列；OLTP 点查/更新为主才留行表（第七节；数据分布与并发画像两依据 ⚠️）。

## 十·七、本域场景表达两句话

1. 方言句："分页与 upsert 分两阵营：标准 OFFSET..FETCH/MERGE 一派（Db2/PG/DuckDB 实测通过侧），LIMIT/UPSERT 方言一派（SQLite 实测侧）——审查移植先切阵营再谈优化。"
2. 对象句："11.1 的三张新名片各答一类需求：时段表答审计、列组织答分析、RCAC 答行级权限——选型先答需求再背语法。"

## 十·九、本域语法速查表（阵营一列即考点）

| 特性 | 标准/Db2 写法（⚠️ 转述） | 🔧 实测阵营备注 |
|---|---|---|
| 分页 | OFFSET n ROWS FETCH FIRST m ROWS ONLY | DuckDB 过 / SQLite 拒（🔧A） |
| upsert | MERGE INTO ... WHEN MATCHED/NOT MATCHED | DuckDB 过 / SQLite 拒，ON CONFLICT 代（🔧B） |
| 生成列 | GENERATED ALWAYS AS (expr) VIRTUAL\|STORED | SQLite 有 STORED / DuckDB 拒（🔧C，Db2 双态居中 ⚠️） |
| 序列 | CREATE SEQUENCE / NEXTVAL | DuckDB 过 / SQLite 拒（🔧D） |
| 递归保护 | WITH RECURSIVE + CYCLE ... USING path | 两家均拒 CYCLE（🔧E） |
| 时段表 | WITH SYSTEM VERSIONING + FOR SYSTEM_TIME | 两家均拒（🔧F，Db2 原生领先 ⚠️） |

## 核心概念速览（中英对照）

- **FETCH FIRST** — Row Limiting：标准分页子句（Db2/PG/DuckDB 阵营）🔧A
- **OFFSET n ROWS** — 标准偏移子句，与 FETCH FIRST 连用 🔧A
- **OPTIMIZE FOR n ROWS** — Db2 取回优化提示（非行数限制 ⚠️）
- **MERGE INTO** — SQL:2003 upsert 语句 🔧B
- **UPSERT/ON CONFLICT** — SQLite 路线的等价物 🔧B（非 DB2）
- **生成列** — Generated Column（VIRTUAL/STORED）🔧C
- **标识列** — Identity Column（BY DEFAULT/ALWAYS）
- **序列** — Sequence：独立号段对象 🔧D
- **递归 CTE** — WITH RECURSIVE + CYCLE 环保护 🔧E
- **时段表** — System-Versioned Table（SQL:2011 双时态族）🔧F
- **FOR SYSTEM_TIME** — 历史时点查询谓词
- **列组织表** — Column-Organized Table（BLU）：分析型列存表形态
- **MQT** — Materialized Query Table：物化查询表+查询重写
- **组织键** — ORGANIZE KEY：列存表的排序加速键（替代 MDC 叙事 ⚠️）

## 最新演进与工业实践

- 分页谱系现状（🔧 复测口径）：DuckDB 1.5.5 与现行 PostgreSQL 全系支持标准 OFFSET..FETCH；SQLite 到 3.45 仍仅 LIMIT/OFFSET——"SQL:2008 子集 vs 全曲"的落差在 2024–2026 依旧存在，Db2 语法书考点不过时。
- MERGE 扩散史：DuckDB（1.x 已支持，🔧B 实跑通过）、Oracle/SQL Server/Db2 多年标配，SQLite 至 3.45 仍拒绝——跨引擎 ETL 模板里 MERGE 仍是"可移植性雷区"（对照 [../DuckDB_in_Action/00-总览与阅读地图.md](../DuckDB_in_Action/00-总览与阅读地图.md) 的数据管道章）。
- JSON 路线分叉：Db2 11.1 BSON 存储 → 11.5.x/12 文档谱出现原生 JSON 类型与 JSON 函数族叙事 ⚠️ 转述（✅ 版本对比入口 https://www.ibm.com/docs/en/db2 ）；PG jsonb、DuckDB JSON/ARRAY 原生列已成默认心智，备考时区分"Db2 的 JSON 史"与"行业现状"。
- 时段表商业化：SQL:2011 时态在 Db2 保持原生实现，PG 以扩展/触发器、SQL Server 以 SYSTEM_VERSIONED 表跟进（⚠️ 各家细节不展开）；审计/SCD 场景的"用引擎特性替代手工拉链"是近年建模讨论主线，可回链 [../../db/db.md](../../db/db.md) 论文索引的时序存储条目。
- 规范核对纪律：凡本章 ⚠️ 存疑语法点（WITH TIES、组织键、生成列索引限制），以 11.1 官方文档为准逐条回验，不背笔记不背本目录。
