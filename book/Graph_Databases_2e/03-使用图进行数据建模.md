## 3.1–3.2 带标签的属性图模型（Labeled Property Graph）

构成元（本书固定术语，后续章沿用）：

- **节点（node）**：实体/事件，带 **0..n 个标签（label）** 与键值属性。
- **关系（relationship）**：有**类型（type）**、有**方向**、可带属性；连接两个节点；同一对节点间可并存多种类型的关系。
- **属性（property）**：挂在点与关系上的键值对，值类型基本（字符串/数值/布尔/时间）。

对比 RDF 三元组（书在附录/2 章语境有对照）：属性图把“边”提升为带类型、可带属性的结构，天然支持属性图式“实体-联系-属性”三元扩展；RDF 的谓词只能指向字面量或另一节点，边上再挂属性要 reify。

关键立场：**标签是索引入口，不是表**。节点“同时是 Person 又是 Employee”毫无成本——这是与关系建模（多对多拆分）的根区别。

## 3.3 Cypher 简介：声明式“模式匹配”语言

本章引入 Cypher（作者之一即 Cypher 发起者），理念：**在屏幕上画出你想查的东西**——ASCII-Art 模式：

- `(a)-[:KNOWS]->(b)` 节点圆括号、关系方括号带类型和方向；
- `MATCH` 声明模式，`WHERE` 加约束，`RETURN` 投影（3.3.2/3.3.3 即这两个子句）；
- 变长路径 `*1..3`、`CREATE/MERGE` 写操作（3.3.4 “其他子句”）。

重构者按：Cypher 之于图，相当于 SQL 之于关系——但**抽象层级不同**：SQL 声明“什么结果”，Cypher 声明“结果的形状”。第 6 章会回到“声明式查询 vs 命令式/遍历 API”的取舍。

## 3.4 关系建模 vs 图建模：同一领域两次建模

书中用系统管理领域（IT 资产、机架、服务依赖）做 A/B：
- 关系模型：实体表 + 外键 + 桥接表；查询“某服务故障影响哪些业务”需要跨 4+ 表 JOIN。
- 图模型：`(Server)-[:HOSTS]->(Service)-[:SUPPORTS]->(BusinessApplication)`；同一查询是三段模式。
- 3.4.3 “测试模型”给出方法论：用领域问题清单当“验收查询”，**模型好坏 = 这些查询写得顺不顺**——图建模的 TDD 思想，直接通到第 4 章 4.3（测试驱动的数据模型开发）。

## 3.5 跨域模型：莎士比亚图

经典演示：把《莎士比亚全集》的词/场景/说话者建成图，跨域查询“某词出现在哪些场景、由谁说出”成为模式匹配练习场。要点不是莎士比亚本身，而是**同一批原始关系数据（CSV 导出）同时可被关系模型与图模型消费**——跨域模型 = 把不同领域的“行”翻译成“点边”，为第 5 章案例与第 4 章导入（4.5）埋线。

## 3.6 常见陷阱：以“电子邮件起源”问题域为例

书中用迭代开发里两次建模失败复盘（3.6.2 “敏感的第一次迭代”/3.6.3 “第二次的魅力”）：
- 陷阱 1：**把 schema 当 DDL 思维**——一上来穷举所有属性，错过关系语义；正确姿势是白板圈箭头、从“问题”出发。
- 陷阱 2：**过度具体化的关系类型**（KNOWS_SINCE_2010 之类把属性焊进类型名）——类型应表达语义范畴，细节交给属性。
- 陷阱 3：把**可复用实体做成属性**：同一值大量重复（城市名）→ 该升格为节点 + 关系，天然去冗余并打开“同城市”类查询。

### Cypher 速查小抄（重构示例，语法以官方手册为准）

| 意图 | 写法 | 备注 |
|---|---|---|
| 一跳好友 | `MATCH (p:Person {name:'Aya'})-[:KNOWS]-(f) RETURN f` | 无向用 `-[]-` |
| 共同邻居计数 | `MATCH (a)-[:KNOWS]-(m)-[:KNOWS]-(b) WHERE a<>b RETURN count(m)` | 三元闭包特征 |
| 限跳可达 | `MATCH (a)-[:KNOWS*1..3]-(x) RETURN x` | 变长路径 `*1..3` |
| 方向+属性约束 | `MATCH (u)-[r:WORKED_AT {role:'dev'}]->(c) RETURN u,c` | 关系属性过滤 |
| 幂等建点 | `MERGE (p:Person {id:$id})` | 参数化防注入 |
| 批量建行 | `UNWIND $rows AS r CREATE (:Skill {name:r.name})` | 配 4.5 导入 |
| 删子图 | `MATCH (p:Person {id:$id}) DETACH DELETE p` | DETACH 连边一起删 |

### 5 分钟莎士比亚图演练（3.5 的重构走查）

1. 数据源：speeches.csv（`scene,speaker_id,text` 之类）——跨域模型入口（同批数据关系模型是平表）。
2. 翻译：一行 CSV = 一条事实 → `(:Scene)-[:HAS_SPEECH]->(:Speech {text})<-[:SPOKE]-(:Speaker)`；词表另建 `(:Word)` 由 Speech 指向。
3. 声明查找模式（3.5.3）：先写下三个领域问题（“某词在哪些场景出现”“谁与谁同场说过同一词”“某说话者的场景谱”），每个问题对应一条 MATCH——**问题即验收查询**。
4. 约束匹配（3.5.4）与查询链（3.5.6）：把上一条结果当下一条起点（管道思维），体会 Cypher 组合性。
5. 复盘：若某问题需要“先 JOIN 再 GROUP 再 JOIN”三段，多半是建模错位（该成节点的做了属性）。

### 本章自测问答

1. 标签和关系类型的本质区别？——标签=入口/分类（多归属），类型=查询语言的语义词汇（模式里必须写）。
2. RDF 与属性图对“边上的属性”的处理差异？——RDF 需 reify；属性图原生支持。
3. “KNOWS_SINCE_2010”错在哪？——把属性焊进类型名，类型空间爆炸、查询不可泛化。
4. 何时把关系升为节点？——该联系需要携带第三方信息或被多方引用（4.1.4 事实节点同理）。
5. 上帝节点为何破坏“代价∝邻域”公式？——其邻域≈全图，任何经过它的遍历都退化。
6. 验收查询法与 TDD 的对应关系？——fixture=代表性小图，断言=模式匹配结果，重构=改模型不删问题。

## 3.7–3.8 节点还是关系？反模式清单

- **辨别准则（3.7）**：某东西若“被别人指向还不够，还要携带别人的元信息/参与多方”——升格为节点（reification）；反之保持关系。
- **反模式（3.8）**：
  - **上帝节点（god node）**：超级枢纽（如一个 `ALL_USERS` 节点连所有人）让“遍历”瞬间退化为全图——用分层/分桶类型拆；
  - **通用关系（generic relationship）**：`RELATED_TO` 无类型语义——查询无法约束模式，遍历效率与可解释性双输；
  - **把查询需求硬编码成关系**：为某查询专门造“预连接”边，等于在图里手工预计算 JOIN，违背建模中立性。

## 核心概念速览（中英对照）

- **带标签属性图** — labeled property graph：点带标签、边带类型/方向/属性的图数据模型。
- **标签** — label：节点的分类入口（多归属），常兼作索引前缀。
- **关系类型** — relationship type：边的语义范畴，查询模式的核心约束。
- **模式匹配** — pattern matching：以图同态/子图匹配表达查询意图。
- **ASCII-Art 模式** — ASCII-art pattern：`(n)-[r:TYPE]->(m)` 的 Cypher 书写字法。
- **变长路径** — variable-length path：`*1..n` 跳数区间匹配。
- **MERGE** — MERGE：幂等的“不存在则创建”写入子句。
- **实体化** — reification：把带属性/多参与方的关系升格为节点。
- **上帝节点** — god node：连接爆炸的超级枢纽节点，遍历性能杀手反模式。
- **泛型关系** — generic relationship：语义空泛的关系类型（RELATED_TO 等）。
- **验收查询** — acceptance queries：以领域问题清单验证模型的方法。
- **跨域模型** — cross-domain model：同一数据源向多领域模型（关系行/图点边）的互译。

## 最新演进与工业实践

- **Cypher → GQL 标准血统**：Cypher（Neo4j 2011）与 openCypher 是 **ISO/IEC 39075:2024 GQL** 的主要输入之一，标准正文由 GqlStandard.org 工作组（含 Neo4j 代表）维护：https://www.gqlstandards.org/ （curl 200 ✅，含 ISO/IEC 39075 文本条目）。学 Cypher ≈ 学 GQL 的图模式子集。
- **Cypher 手册现行版**：语法权威以 Neo4j Cypher Manual 为准（MATCH/WHERE/RETURN、`*1..n`、MERGE 皆对应）：https://neo4j.com/docs/cypher-manual/current/ （curl 200 ✅）。2025.x 版本手册新增/调整（如 `+` 语法糖、异步索引、组合标签——细节以手册为准 ⚠️ 本目录未逐项抓）。
- **建模工具的代际更替**：书中白板方法如今有专员工具——Neo4j **GraphAcademy**（建模课程）https://graphacademy.neo4j.com/ （curl 200 ✅）；官方建模器（Data Modeler/Bloom 等）形态与定价变动频繁，此处不逐一给链接（⚠️）。
- **属性图 + 向量的混合建模**（2024–2026 热点）：节点除属性外可挂**向量索引**（embedding），Cypher 提供 `db.index.vector.queryNodes` 类过程，实现“语义相似召回 + 图关系扩圈”的混合检索：https://neo4j.com/docs/cypher-manual/current/indexes/semantic-indexes/vector-indexes/ （curl 200 ✅；GA 于 Neo4j 5.11+，版本口径同页可查）。建模陷阱清单也因此新增一条：**把 embedding 当属性乱堆**——向量应入专门索引，不占普通属性遍历路径。
- **GraphRAG 时代的 schema 观**：微软 GraphRAG（https://github.com/microsoft/graphrag ，curl 200 ✅；论文见 `./05-现实世界中的图.md` 最新演进）用 LLM 从文本**自动抽实体/关系构图**——3.6 的“从问题出发定义模型”演化为“从检索问题出发定义抽取 schema（实体类型/关系类型清单）”，方法论未变、执行者变了。
- **反模式的工业验证渠道**：LDBC SNB 的负载设计（朋友的朋友、推荐分数等）本质是“验收查询标准化”，建模好坏可直接跑基准回归：https://ldbcouncil.org/ （curl 200 ✅）。
