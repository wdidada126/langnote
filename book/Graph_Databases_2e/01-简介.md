## 1.1 图是什么 —— 本章要纠正的直觉

本书开篇的动作不是讲软件，而是讲数据结构：图（graph）= 顶点（vertex/node）+ 边（edge/relationship）的集合。作者刻意强调两层区别：

1. **图论的图**是数学对象（属性可忽略）；**属性图**给点与边都挂上键值属性，才成为可存储的数据库模型。
2. **图作为“数据”而非“数据结构的图片”**：关系数据模型里，关联要通过外键 + JOIN 在查询时“重建”；属性图模型里，关联本身就是存储的一等公民。这一点在第 2 章展开，本章先埋钩子。

阅读提示（重构者按）：这一节信息量不大，但决定了全书叙事策略——先说服你“连通性（connectedness）是数据的第一性质”，后面的建模规范、遍历性能、案例才有落点。

## 1.2 图领域概览：两个物种别混淆

### 1.2.1 图数据库

定义关键词：**原生图存储 + 原生图处理 + 面向 OLTP 的数据库**。
- 原生图存储：邻接关系直接落盘（免索引邻接，index-free adjacency），点/边/属性都有持久标识。
- 原生图处理：查询执行 = 沿邻接的遍历，而非对表的扫描与重联。
- 数据库属性：事务（ACID）、约束、恢复、并发——这是它与“图计算引擎”的分水岭。

### 1.2.2 图计算引擎

面向**全局批处理/分析**（PageRank、连通分量、社区发现之类），常把图加载进内存或分布式计算框架（本书语境下的 Hadoop/Hama/Pregel 系谱），通常**不保证 OLTP 事务语义**，更新模型也不友好。

重构者按：这一小节是全书最有“选型价值”的区分之一。今天仍然成立：**图数据库管“在线读写 + 局部邻域查询”，图计算引擎管“全图批分析”**，中间地带被后文的 GDS（图数据科学库）类产品吃掉。

两类系统的对照（按书意重构）：

| 维度 | 图数据库 | 图计算引擎 |
|---|---|---|
| 负载 | OLTP：小范围读写、在线查询 | OLAP/批：全图算法、迭代计算 |
| 数据访问 | 从入口点出发的局部遍历 | 全图加载/分区并行 |
| 一致性 | ACID 事务 | 通常快照/尽力而为 |
| 更新 | 持续增量写 | 批量重算为主 |
| 代表（2015） | Neo4j、Titan | Hama、Pregel 系、Giraph |
| 代表（今天） | Neo4j/Memgraph/Neptune | GraphX/GraphFrames/GDS 库内算法 |

## 1.3 图数据库的威力：三个卖点

本章的论证体裁是“主张 + 机理”各一句，这里把三条主张的论证链拆开（重构表述）：

**性能主张的论证链**
1. 深度关联查询的瓶颈在“找邻居”；
2. 关系/文档/宽列都必须借索引或预计算“重建”邻接，代价与表规模相关（第 2 章展开并给出反例边界）；
3. 免索引邻接把“找邻居”降为 O(1) 指针访问，代价只与访问邻域相关；
4. 结论：查询越深、越选择性，图的相对优势越大——同时书也预埋了反面（全图聚合无优势，见 4.3.2 负载画像）。

**灵活性主张的论证链**
1. 领域语言里“联系”的语义变化最快（新关系类型、新属性）；
2. schema 变更在关系模型是 DDL 工程，在属性图只是增类型/标签；
3. 标签多归属 + 关系带属性，使“同一事实的多种建模口径”可共存演化。

**敏捷性主张的论证链**
1. 白板圈箭头与图模型同构，业务方能读能改；
2. 验收查询（3.4.3/4.3.1）把“模型好不好”变成可执行断言，迭代有反馈闭环；
3. 结论：图建模与领域驱动设计（DDD 聚合边界之外的“跨聚合关系”）互补——这也是本书长盛的部分。

| 卖点 | 书中论证 | 需要警惕的简化 |
|---|---|---|
| 性能 | 深度关联查询（3–4 跳）在图中是局部遍历，代价 ~ 路径上各点度数之和；关系模型中是多次 JOIN/自 JOIN，代价随扇出爆炸 | 单跳点查、聚合扫描类负载，列存/OLAP 更快——本书第 4 章容量规划部分自己也承认要分区负载 |
| 灵活性 | 属性图 schema-on-write 约束弱，加类型/属性不破坏既有查询；关联语义（边类型）可以随领域语言演化 | 灵活性≠无模型：3.6/3.8 章“建模陷阱与反模式”就是给灵活性立规矩 |
| 敏捷性 | 建模与领域白板讨论同构（白板上的圈和箭头≈图中的节点和关系），迭代成本低 | 对强约束、强汇总报表需求（数仓建模）并非如此，与维度建模对照见互链 |

### 本章自测问答

1. 图数据库与图计算引擎的分水岭是什么？——事务语义与增量写（OLTP 属性），不是“谁算法多”。
2. “性能优势”成立的负载前提？——查询沿关系多跳扩散且选择性高；全表聚合不在其列。
3. 为什么说灵活性≠没有模型？——类型/标签仍是语义约束，滥用会产生 3.8 反模式。
4. 敏捷性的可执行载体？——验收查询（后续 3.4.3、4.3.1 落地）。
5. “connected data”的判据两问？——关系是否携带业务语义；查询是否以邻域为中心。
6. 本章没有回答但第 2 章必须回答的？——“外键+索引为什么不算原生邻接”。

## 精读札记

- 本书作者身份（Neo4j 创始团队成员/高管）决定了叙事偏向：第 1 章的“威力三卖点对比对象其实是 RDBMS 而非其他 NoSQL”。读时应有意识：图数据库的代价（全局聚合慢、学习成本、生态工具少）要到自己动手时才暴露。
- “connected data”这个短语是 O'Reilly 副标题的核心：本书把社交/推荐/网络管理这类“关系密集型”负载归为一类，与《NoSQL 精粹》按数据形态（键值/文档/列/图）分类互补——一个从负载出发，一个从模型出发。
- 1.2.1 的“持久标识”一词常被忽略：节点/关系 ID 是**稳定的**（ID 即位置），这带来“引用可缓存、遍历可续算”的工程性质，也埋下“ID 不能跨集群迁移”的隐患（本书第 4 章集群节未展开，后续产品用 element id/uid 修补 ⚠️ 口径以版本手册为准）。

## 核心概念速览（中英对照）

- **图** — graph：顶点与边的集合；本书语境下默认“属性图”而非纯图论对象。
- **顶点/节点** — vertex/node：领域实体，携带属性与标签。
- **边/关系** — edge/relationship：带类型与方向的关联，可携带属性，是一等公民。
- **属性图模型** — property graph model：点/边均可挂键值属性的图模型。
- **连通数据** — connected data：以关系密度为特征的负载（社交/推荐/网络/权限）。
- **原生图存储** — native graph storage：邻接直接持久化，典型实现为免索引邻接。
- **原生图处理** — native graph processing：以邻接遍历为执行模型。
- **图数据库** — graph database：OLTP 型、带事务的图存储引擎。
- **图计算引擎** — graph computation/analysis engine：面向全图批分析的引擎，无 OLTP 事务。
- **免索引邻接** — index-free adjacency：点直接指向邻居记录，沿边前进无需索引查找（第 2 章正式引入）。
- **扇出** — fan-out：一个节点在某类型上的出度，决定遍历局部成本。
- **模式契合** — pattern fit：模型与领域语言同构带来的敏捷性论证。
