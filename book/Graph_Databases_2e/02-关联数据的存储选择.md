# 02 关联数据的存储选择（Storage Options for Connected Data）

> 对应原书第 2 章（中译本页码 9–20）。二级目录（✅ 实抓自中译本目录）：2.1 关系型数据库缺少联系｜2.2 NoSQL 数据库也缺少联系｜2.3 图数据库拥抱联系｜2.4 小结。
> 本章文件为**精读重构**，非原书文本。本章是全书的“立论章”：论证三类现有存储在关联数据上的结构性缺陷。

## 2.1 关系型数据库缺少联系

书的论证链（重构表述）：

1. 关系模型把联系“编码”成外键值。外键是**值**，不是**指针**：要从 A 找到相关的 B，必须执行 JOIN——本质是“在查询时重算邻接关系”。
2. 于是出现三宗罪：
   - **查询复杂度**：多跳关联变成多次自 JOIN，SQL 里用 JOIN 堆叠表达“朋友的的朋友”，语句本身与意图越来越远；
   - **性能**：JOIN 依赖外键列上的索引，但代价模型是“按表规模/中间结果规模”计，而不是“按真正关心的子图规模”计；深度遍历尤其灾难；
   - **schema 刚性**：新增关联语义（关系类型）要动表结构，影响面大，且“关系上的属性”要么塞进关联表列，要么另立表——关系是一等公民这件事在 DDL 里没有表达位。
3. 作者承认关系型能表达图（用桥接表），争的是**效率与表达力的“原生性”**：需要索引来维护的邻接，就是非原生邻接。

⚠️ 阅读提醒：本节批评对象是 2015 年语境下的通用 RDBMS。今天图查询能力已进入关系阵营（SQL/PGQ 与 GQL 见“最新演进”），但“JOIN 重算邻接 vs 直接沿邻接”这一执行模型的差异仍在，批评的内核没有过期。

## 2.2 NoSQL 数据库也缺少联系

按《NoSQL 精粹》式分类学逐类检视（书中顺序：键值 → 文档 → 列族 → 聚合/事件溯源）：

- **键值存储**：值不透明，找“关联”只能靠把关系再编码进键名（复合键约定）——脆弱、不可查询。
- **文档存储**：内嵌子文档 + 引用 ID。引用仍是“值”，跨文档关联要在应用层做多次取回（或反范式化冗余）——“聚合”边界与“关系”边界冲突。
- **列族（宽列）**：行键即查询主路径；跨行关系需要为每种查询形态预建“索引表/物化视图”（cassandra 的 table-per-query 习惯），本质是手工预计算 JOIN。
- **聚合/事件溯源**：时间维度强，空间（实体-实体）维度仍靠把关系塞进聚合内。

共同结论：**这些范式优化了“对象”，没有优化“对象之间的联系”**；关系在它们那里要么不存在、要么被拆成键或文档片段。

## 2.3 图数据库拥抱联系

本章的正面陈述，也是全书反复回味的概念基座：

- 关系是**存储结构本身**：节点直接持有指向邻居的指针——**免索引邻接（index-free adjacency）**。从一个节点走到相邻节点不经过任何索引查找、不扫描任何表。
- 由此得到遍历成本公式（书中大意）：一跳的代价 ≈ 当前节点在该类型上的**出度（fan-out）**；k 跳的代价 ≈ 沿途各点度数之和——**只与访问到的邻域成正比，与图总规模无关**。
- 关系带类型、带方向、带属性：建模语言与领域语言直接同构（对照第 3 章建模实践）。
- 索引不是没有，而是“**只用在入口点定位**”（标签/属性索引找到起点，之后全靠邻接遍历）——这句是第 6 章原生处理的伏笔。

## 2.4 小结

立论完成式：需要“关系一等公民 + 原生遍历 + OLTP 事务”三合一 → 图数据库。第 3 章转入“怎么建模”，第 6 章兑现“为什么快”。

## 🔧 实测（本机 DuckDB 1.5.5 + Python，方法可复现）

**问题**：书的“关系模型按表规模计代价、图模型按访问邻域计代价”是否可演示？

**方法**（临时脚本在 `D:\develops\tmp\dbwave_graphdatabases\`，repo 零产物）：
- 关系侧：DuckDB 表 `knows(p1,p2)`，2–3 跳可达集用递归 CTE（每跳 ≈ 对 knows 的一次哈希 JOIN 迭代）。
- 图侧：同一边集装入 Python 邻接字典（等价“免索引邻接：邻居直接在手”），同样跳数做 BFS 遍历；邻接表一次性构建不计入查询时间。
- 场景 A：10 万节点均匀随机图（~400 万条边，低选择性扩散查询）；场景 B：按 1000 人社区生成边（查询被限制在一个社区内，高选择性）；场景 C：B 的图规模翻倍（20 万节点），查询仍是那一个社区。

**解读（诚实版，含反转）**：
- 场景 A→B 对照证明：DuckDB 每跳一次“全表级”JOIN 迭代，耗时几乎不随查询选择性下降；邻接遍历耗时随访问邻域缩小而缩小——**书的中断点代价模型差异是真实的**。
- 场景 B→C 对照证明：**关系侧代价 ∝ 边表规模（×2 即近 ×2），图侧代价 ∝ 访问到的子图（不变则近似不变）**——这就是 2.3 那两句“与图总规模无关”的实测形态。
- 但要标注边界：均匀随机图、深度 2 的低选择性场景下两者差距并不悬殊；且 DuckDB 是**内存向量化的 OLAP 引擎**，已是关系阵营里对“扫描重算邻接”最友好的实现；书批评的是磁盘行存 + B+ 树二级索引的 OLTP 关系库，那里每跳还要叠加随机 I/O。本实测不能外推为“图数据库对一切 SQL 场景快 24 倍”——那类跨引擎数字游戏恰恰是书 1.3 警告过的。
- 另注：4 跳以上随机图 BFS 的“遍历”退化为全图扫描（小世界效应，可达集爆炸），此时任何引擎都不该用遍历做——见 `./07-图论与预测分析.md` 对遍历适用边界（选择性、局部性）的讨论。

## 核心概念速览（中英对照）

- **外键** — foreign key：关系模型中表示联系的值约束，查询时需 JOIN 激活。
- **自连接** — self-join：同一表对自身 JOIN，表达一跳“同类关系”的标准 SQL 手段，多跳即递归/叠套。
- **重算邻接** — adjacency recomputation：用 JOIN/索引查找在查询期临时重建邻居，本书对关系模型的核心批判点。
- **不透明值** — opaque value：键值存储中不可查询的值体，关联只能编码进键约定。
- **聚合** — aggregate：DDD/文档模型的一致性边界单元，跨聚合关系退化为 ID 引用。
- **反范式化** — denormalization：文档/宽列存储为免 JOIN 而冗余数据，写放大换读性能。
- **按查询建表** — table per query：宽列生态惯例，为每种关联查询预建物化结构。
- **免索引邻接** — index-free adjacency：节点物理持有邻居指针，遍历不经索引。
- **出度/扇出** — out-degree/fan-out：某节点某类型关系条数，单跳遍历代价的主变量。
- **入口索引** — entry-point index：仅用于按标签/属性定位遍历起点的高选择性索引。
- **选择性** — selectivity：查询触达子图占全图的比例，决定“遍历型 vs 扫描型”谁占优。
- **原生图** — native graph：存储与处理均以图为第一结构，区别于“在别的模型里模拟图”。

## 最新演进与工业实践

- **GQL 成为 ISO 标准，关系阵营“原生补图”**：2024-04 发布 **ISO/IEC 39075:2024《Information technology — Database languages — GQL》**——SQL 之后 ISO 新语言标准。官方目录页 https://www.iso.org/standard/76120.html （curl 校验：403 反爬，仅作官方入口；标准号与标题经 https://www.gqlstandards.org/ 与 https://learn.microsoft.com/en-us/fabric/graph/gql-conformance 双源核证 ✅）。同族还有嵌入 SQL 的 **SQL/PGQ** 图模式匹配。本章“JOIN 重算邻接”的批判对象，正在被关系厂商用“内核里加原生图执行器”的方式回应。
- **LDBC 把“谁快”变成标准问题**：LDBC（Linked Data Benchmark Council，2013 年起）的 SNB 基准给出可复现的图负载定义。核证论文（DOI 均过 `api.crossref.org` 200 ✅）：
  - Erling et al., *The LDBC Social Network Benchmark*, SIGMOD 2015 — DOI [10.1145/2723372.2742786](https://doi.org/10.1145/2723372.2742786)
  - Szárnyas et al., *The LDBC Social Network Benchmark*, PVLDB Vol.16（2022/2023，含 BI 负载） — DOI [10.14778/3574245.3574270](https://doi.org/10.14778/3574245.3574270)

  - 官网 https://ldbcouncil.org/ （curl 200 ✅）。
- **列存/OLAP 引擎也内置了图遍历**（本实测的提示）：DuckDB/PostgreSQL 的递归 CTE、SQL:2023 属性图扩展说明“重算邻接”的工程成本在内存向量化后急剧下降——2.2 的批判要按负载（选择性、深度、更新频率）重新校准。
- 多模数据库吸收图引擎：AWS Neptune（图库原生，见 `./05-现实世界中的图.md` 最新演进）、Microsoft Fabric Graph（GQL 一致 ✅ 页）、Oracle/SQL Server 的 property graph 路线（2025 年后 SQL Server 亦有图预览；各家状态以厂商页为准 ⚠️ 未逐一核证）。
- 2.3 的“遍历只与邻域成正比”在现代 NVMe 磁盘 + 页缓存环境仍成立，但“随机 I/O 便宜了”削弱的是第 6 章存储布局论证，不动摇本章代价模型结论。
