## 4.1 从检测到行动：告警是桥梁

检测算法的产出是「异常信号」；告警系统的工作是把异常信号翻译成**对的人**在**对的时刻**能采取的**行动**。

三要素（⚠️ 按 #226 五支柱 Alerting 推定）：
1. **路由**（Routing）：告警发给谁？——依赖 Documentation 支柱的负责人登记。
2. **冷却**（Cooldown）：多久发一次？——防止告警风暴。
3. **升级**（Escalation）：没人认领怎么办？——依赖组织合同。

## 4.2 告警路由的工程实施

**路由表设计**（⚠️ 推定）：

```sql
CREATE TABLE alert_routing (
    table_name TEXT, severity TEXT,
    channel TEXT, owner_team TEXT, cooldown_minutes INTEGER
);
```

路由的核心依据是**血缘 + 负责人登记**——这正是 02 章 G3 血缘分析的下游产品。没有血缘，告警只能发给「数据团队全体」，等于没人负责。

与数据目录的接榫：负责人字段来自目录——见 [../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md](../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md)。

## 4.3 冷却与去重：防止告警风暴

**冷却机制**（⚠️ 推定）：同一表同一规则在 `cooldown_minutes` 内不重复告警。

**去重策略**：
1. **时间窗去重**：N 分钟内同表同规则 → 合并为一条。
2. **因果去重**：上游表的告警抑制下游表的派生告警（需血缘支持）。
3. **严重级别升级**：冷却期内若异常持续恶化，自动升级严重级别。

与 #226 G4（z-score + 24h 冷却去重）的错位：本组聚焦**路由表设计**与**因果去重**的工程实施，而非检测算法本身。

## 4.4 事件响应工作流

事件响应的标准流程（⚠️ 推定，参考 SRE 事件管理 + 数据域适配）：

1. **检测**（Detection）：监控规则触发 → 告警生成。
2. **分诊**（Triage）：值班工程师判定严重级别与影响面。
3. **定位**（Localization）：血缘分析（02 章 G3）定位根因节点。
4. **修复**（Remediation）：修复管道/数据——下游闭环见 [../数据清洗.md](../数据清洗.md)。
5. **复盘**（Post-mortem）：记录根因、影响面、修复动作，更新监控规则。

## 4.5 数据事故台账

**事故台账**是组织学习的载体（⚠️ 推定）：

```sql
CREATE TABLE data_incidents (
    incident_id TEXT, detected_at TEXT,
    table_name TEXT, severity TEXT,
    tt_detect_minutes REAL, tt_resolve_minutes REAL,
    root_cause TEXT, affected_downstream INTEGER
);
```

台账的聚合分析可以回答：
- 哪张表的事故率最高？（指导监控资源分配）
- 平均 TTD/TTR 是多少？（度量观测体系效能）
- 根因分布？（指导预防性投资）

## 4.6 告警质量的度量

告警系统本身也需要被观测（⚠️ 推定）：

| 指标 | 定义 | 健康范围 |
|---|---|---|
| 精确率 | 真告警 / 总告警 | > 70% |
| 召回率 | 真告警 / 总故障 | > 90% |
| MTTD | 故障发生到告警的平均时长 | < SLA 的 50% |
| 告警疲劳指数 | 每人每天收到的告警数 | < 10 |

## 4.7 与治理制度的接口

告警路由的「owner_team」字段需要治理制度来维护——见 [../Understanding_Data_Governance/00-总览与阅读地图.md](../Understanding_Data_Governance/00-总览与阅读地图.md) 的数据所有权章。没有治理制度支撑的告警路由，等于把信交给路人。

## 4.8 告警成熟度阶梯（⚠️ 编者归纳）

组织在告警能力建设上通常经历四个阶段（⚠️ 推定）：

| 阶段 | 特征 | 典型工具 |
|---|---|---|
| L1 手工对账 | 靠人发现、靠群沟通 | Excel + 即时通讯 |
| L2 规则告警 | SQL 规则 + cron + 通知 | dbt tests + Slack |
| L3 统计检测 | 自动基线 + z-score/MAD | Elementary + Monte Carlo |
| L4 因果闭环 | 血缘驱动根因推断 + 自动升级 | 商业平台全栈 |

渐进式路径建议：先做到 L2（规则告警 + 路由表 + 冷却），再追求 L3（统计检测），最后按需进入 L4。跳级建设往往导致「工具到位、组织没跟上」的空转。

与 05 章选型的关系：L1–L2 用开源/自建即可；L3 开始考虑商业平台的推断引擎；L4 需要自动血缘作为基础设施。

## 核心概念速览（中英对照）

- **告警路由** — Alert Routing：把告警送到对的团队/个人。
- **冷却** — Cooldown：同一规则在时间窗内不重复告警。
- **去重** — Deduplication：合并同源/因果相关的告警。
- **因果去重** — Causal Dedup：利用血缘抑制上游引起的下游派生告警。
- **升级** — Escalation：告警无人认领时的组织级上升机制。
- **事件响应** — Incident Response：检测→分诊→定位→修复→复盘的标准流程。
- **数据事故台账** — Data Incident Log：记录事故根因/影响/TTD/TTR 的结构化日志。
- **TTD** — Time to Detect：故障发生到被发现。
- **TTR** — Time to Resolve：发现到恢复。
- **告警疲劳** — Alert Fatigue：告警过多导致接收者麻木的现象。

## 最新演进与工业实践

- **AIOps 告警降噪**：商业平台开始用 ML 做告警聚合与根因推断，减少人工分诊成本（⚠️ 厂商口径）。
- **PagerDuty/OpsGenie 集成**：告警路由与 IT 事件管理平台的集成已成标准配置（⚠️ 品类通识）。
- **数据事故复盘文化**：Monte Carlo 等厂商推动「Data Incident Post-mortem」文化，类比 SRE 的事后复盘（⚠️）。
- **工业实践口径**：先建路由表 + 冷却机制，再追求因果去重和自动升级——渐进式路径（⚠️）。
- **与治理的关系**：告警路由的 owner 字段是治理制度（[../Data_Governance_Elsevier/00-总览与阅读地图.md](../Data_Governance_Elsevier/00-总览与阅读地图.md)）的运行态兑现。
