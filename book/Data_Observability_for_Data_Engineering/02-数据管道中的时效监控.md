# 02 · 数据管道中的时效监控

> 时效（Freshness）是数据可观测性的第一支柱。本章从工程角度实现多层 SLA 级联检测。
> 🔧 原型 H1：4 层 × 5 表 × 30 天，23 条违规（9 根因 / 14 级联）。

## 2.1 时效的工程定义

时效不是一个单一数字，而是三个时间点的关系：

```
数据时效 = 实际可用时间 - 承诺可用时间

其中：
  承诺可用时间 = SLA 约定的 deadline（如每日 08:00）
  实际可用时间 = 数据到达 + 质量检查通过 + 血缘链完整
```

关键区分：
- **到达时间** ≠ **可用时间**：数据到了但质量检查未过，不算可用
- **管道成功** ≠ **数据按时**：管道 07:59 成功但 SLA 是 07:00，已违约
- **根因违规** ≠ **级联违规**：上游延迟导致下游全部延迟，只有上游是根因

## 2.2 多层 SLA 架构

现代数据仓库通常有 4 层，每层的 SLA 不同：

| 层级 | 典型 SLA | 说明 |
|------|---------|------|
| raw | 无 SLA（源系统决定） | 原始数据落地层 |
| stg | raw + 1h | 清洗转换后 |
| dwd | stg + 2h | 明细建模层 |
| ads | dwd + 1h | 应用层，直接服务 BI/ML |

> 级联逻辑：如果 raw 延迟 3h，stg 的 SLA 是 raw+1h，那么 stg 的"预期完成时间"也会后移。
> 关键问题：ads 的 SLA 是固定时间（如 08:00），不随上游滑动。

## 2.3 🔧 H1 原型：多层 SLA 级联违规检测

> ⚠️ 非本书引擎行为。学习用原型，SQLite 3.45.3+。

### 2.3.1 数据模型

```sql
-- 表注册：每层的 SLA 定义
CREATE TABLE obs_table_sla (
    table_id    TEXT PRIMARY KEY,
    layer       TEXT NOT NULL,  -- raw / stg / dwd / ads
    sla_minutes INTEGER NOT NULL, -- 相对于上游的 SLA（分钟）
    fixed_deadline TEXT,         -- 固定截止时间（ads 层用）
    owner       TEXT
);

-- 运行记录：每次管道运行的元数据
CREATE TABLE obs_run_log (
    run_id      INTEGER PRIMARY KEY,
    table_id    TEXT NOT NULL,
    run_date    TEXT NOT NULL,    -- YYYY-MM-DD
    start_time  TEXT NOT NULL,    -- ISO8601
    end_time    TEXT NOT NULL,
    row_count   INTEGER,
    status      TEXT NOT NULL     -- success / failed / partial
);

-- 依赖关系
CREATE TABLE obs_dependency (
    upstream    TEXT NOT NULL,
    downstream  TEXT NOT NULL,
    PRIMARY KEY (upstream, downstream)
);
```

### 2.3.3 级联违规检测逻辑

```sql
-- 计算每张表的实际完成时间 vs SLA
WITH table_completion AS (
    SELECT
        r.table_id,
        r.run_date,
        r.end_time,
        s.layer,
        s.sla_minutes,
        s.fixed_deadline,
        -- 上游完成时间
        MAX(up.end_time) AS upstream_end
    FROM obs_run_log r
    JOIN obs_table_sla s ON r.table_id = s.table_id
    LEFT JOIN obs_dependency d ON d.downstream = r.table_id
    LEFT JOIN obs_run_log up ON up.table_id = d.upstream
        AND up.run_date = r.run_date
    WHERE r.status = 'success'
    GROUP BY r.table_id, r.run_date
),
violation_check AS (
    SELECT
        *,
        CASE
            WHEN fixed_deadline IS NOT NULL THEN
                CASE WHEN time(end_time) > fixed_deadline THEN 1 ELSE 0 END
            WHEN upstream_end IS NOT NULL THEN
                CASE WHEN (julianday(end_time) - julianday(upstream_end)) * 1440 > sla_minutes
                     THEN 1 ELSE 0 END
            ELSE 0
        END AS is_violated
    FROM table_completion
)
SELECT run_date, table_id, layer, end_time, upstream_end,
       sla_minutes, is_violated
FROM violation_check
WHERE is_violated = 1
ORDER BY run_date, layer;
```

### 2.3.4 根因 vs 级联分类

```sql
-- 区分根因违规和级联违规
WITH violations AS (
    -- 上一步的违规结果
    SELECT run_date, table_id, layer, is_violated FROM violation_check WHERE is_violated = 1
),
root_cause AS (
    SELECT v.*,
        CASE
            WHEN NOT EXISTS (
                SELECT 1 FROM violations v2
                JOIN obs_dependency d ON d.downstream = v.table_id
                WHERE v2.run_date = v.run_date AND v2.table_id = d.upstream
            ) THEN 'root_cause'
            ELSE 'cascade'
        END AS violation_type
    FROM violations v
)
SELECT
    violation_type,
    COUNT(*) AS cnt,
    GROUP_CONCAT(DISTINCT table_id) AS tables_affected
FROM root_cause
GROUP BY violation_type;

-- 预期结果：
-- root_cause: 9 条（raw/stg 层直接延迟）
-- cascade:   14 条（dwd/ads 层被上游拖累）
```

## 2.4 时效监控的工程模式

### 模式一：嵌入式检查

```python
# Airflow DAG 中的时效检查（伪代码）
def check_freshness(context):
    table_id = context['task'].table_id
    run_date = context['ds']
    deadline = get_sla(table_id, run_date)
    actual = get_completion_time(table_id, run_date)
    if actual > deadline:
        alert(f"FRESHNESS VIOLATION: {table_id} "
              f"expected={deadline} actual={actual}")
```

### 模式二：独立监控查询

```sql
-- 每小时运行的监控查询
SELECT table_id,
    MAX(end_time) AS last_success,
    (julianday('now') - julianday(MAX(end_time))) * 24 AS hours_ago
FROM obs_run_log
WHERE status = 'success'
GROUP BY table_id
HAVING hours_ago > 2;  -- 超过 2 小时未更新
```

## 2.5 实战注意事项

1. **时钟同步**：所有节点必须 NTP 同步，否则时间差计算无意义
2. **重试处理**：重试成功时，用首次 start_time 还是末次 end_time？建议用末次
3. **分区感知**：按分区检查时效，而非全表
4. **SLA 继承**：ads 层的 fixed_deadline 不随上游滑动，这是设计意图

## 核心概念速览（中英对照）

| 中文 | English | 一句话 |
|------|---------|--------|
| 时效 | Freshness | 数据是否在约定时间内可用 |
| SLA 级联 | SLA Cascade | 上游延迟导致下游连续违约 |
| 根因违规 | Root-cause Violation | 本层自身问题导致的违约 |
| 级联违规 | Cascade Violation | 被上游违约拖累导致的违约 |
| 固定截止时间 | Fixed Deadline | 不随上游滑动的绝对时间 |

## 最新演进与工业实践

- **Monte Carlo**：自动从管道元数据推断 SLA，无需手动配置
- **dbt tests**：`dbt expect_row_values_to_have_recent_data` 插件
- **Airflow SLA Miss**：原生 SLA 机制，但缺乏级联感知
- **Dagster Sensors**：基于传感器的时效监控，支持自定义逻辑
- **趋势**：从静态 SLA 向动态 SLA 演进——根据历史分布自动调整阈值
