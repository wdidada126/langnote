## 2.2 时效维度（Freshness）工程化 🔧 G1

**核心问题**：一张表是否在承诺时间内被更新到足够新的数据？

**工程实施三件套**（⚠️ 推定）：
1. **SLA 登记**：每张关键表声明 `sla_max_minutes`（最大允许滞后）。
2. **快照采集**：调度系统在每次 ETL 完成后记录 `actual_lag_minutes`。
3. **违约判定**：`actual_lag_minutes > sla_max_minutes` 即违约，进入告警队列。

🔧 **G1 实验**（SQLite，非本书引擎行为）：

```sql
-- 建表：时效 SLA 台账
CREATE TABLE freshness_sla (
    table_name TEXT, snap_date TEXT,
    actual_lag_minutes REAL, sla_max_minutes REAL
);
-- 违约判定
SELECT table_name, COUNT(*) AS checks,
    SUM(CASE WHEN actual_lag_minutes > sla_max_minutes THEN 1 ELSE 0 END) AS violations,
    ROUND(100.0*(1.0-1.0*violations/checks),2) AS sla_pct
FROM freshness_sla GROUP BY table_name;
```

**真实输出**（种子 224，详见 `D:\develops\tmp\dbwave_w6_dode\exp_out.txt`）：

| Table | Checks | Violations | SLA% | WorstOver(min) |
|---|---|---|---|---|
| raw.events | 30 | 10 | 66.67 | 62.0 |
| stg.orders | 30 | 6 | 80.0 | 73.2 |
| mart.kpi_daily | 30 | 10 | 66.67 | 210.0 |
| ads.revenue | 30 | 5 | 83.33 | 106.5 |
| dwd.clicks | 30 | 8 | 73.33 | 68.5 |

**整体 SLA 达成率 ≈74.0%**——说明即使「作业全绿」，时效面仍可能大面积违约。这正是「作业成功 ≠ 数据正确」的量化版。

## 2.3 血缘维度（Lineage）工程化 🔧 G3

**核心问题**：一张表坏了，谁遭殃？

**工程实施**（⚠️ 推定）：
1. **边登记表**：`lineage_edges(src_table, dst_table, pipeline_job)`。
2. **递归遍历**：`WITH RECURSIVE` 从故障节点向下游 BFS。
3. **影响面报告**：输出深度、路径、受影响节点数——直接喂给告警通知。

🔧 **G3 实验**（SQLite，非本书引擎行为）：

```sql
WITH RECURSIVE downstream(tbl, depth, path) AS (
    SELECT dst_table, 1, src_table || ' -> ' || dst_table
    FROM lineage_edges WHERE src_table = 'raw.orders'
    UNION ALL
    SELECT e.dst_table, d.depth+1, d.path || ' -> ' || e.dst_table
    FROM downstream d JOIN lineage_edges e ON d.tbl = e.src_table
    WHERE d.depth < 6
)
SELECT DISTINCT tbl, depth, path FROM downstream ORDER BY depth;
```

**真实输出**（10 边图，从 `raw.orders` 出发）：

| Node | Depth | Path |
|---|---|---|
| stg.orders | 1 | raw.orders -> stg.orders |
| dwd.order_items | 2 | raw.orders -> stg.orders -> dwd.order_items |
| mart.sales_daily | 3 | ... -> dwd.order_items -> mart.sales_daily |
| mart.customer_ltv | 3 | ... -> dwd.order_items -> mart.customer_ltv |
| ads.revenue_dashboard | 4 | ... -> mart.sales_daily -> ads.revenue_dashboard |

**5 个下游节点受影响**，深度 1–3。此结果直接决定告警的影响面字段。

与 #226 G3（9 边 → 6 下游）和 #223 E5（22 节点覆盖率审计）全部错位——本组聚焦「单源递归路径枚举」的工程实施视角。

## 2.4 分布维度的工程实施（⚠️ 推定，无 🔧 组）

分布偏移检测的工程实施通常包含：
1. **分桶策略**：数值列十分位分桶、类别列频率 top-K。
2. **基线窗口**：取历史 N 天作为参考分布。
3. **距离度量**：PSI（Population Stability Index）或 KS 检验。
4. **阈值判定**：PSI < 0.1 稳定、0.1–0.25 预警、> 0.25 显著偏移。

本目录不在本组设 🔧 实验（#223 E1 已做 PSI 原型，零重合原则）。

## 2.6 维度间的耦合与优先级

五个维度不是独立的——时效违约可能由血缘断裂引起，模式漂移可能导致分布偏移。工程实施的优先级建议（⚠️ 推定）：

1. **先血缘**：没有血缘，其他维度的告警无法路由到 owner。
2. **再时效**：时效是最直观、最低成本的检测维度。
3. **然后体量**：行数/字节数异常是最简单的统计检测。
4. **再模式**：schema 漂移检测需要元数据快照基础设施。
5. **最后分布**：分布偏移检测的误报率最高，需要最成熟的基线体系。

## 核心概念速览（中英对照）

- **时效** — Freshness：数据是否在承诺时间内更新到足够新。
- **体量** — Volume：行数/字节数的日序列，异常检测的基础信号。
- **模式/Schema** — Schema：列元数据的结构快照，漂移即违约。
- **分布** — Distribution：列值的统计分布，偏移用 PSI/KS 度量。
- **血缘** — Lineage：从源到消费点的链路登记，影响分析的图基础。
- **SLA 达成率** — SLA Attainment：时效承诺被满足的比例。
- **递归影响分析** — Recursive Impact Analysis：WITH RECURSIVE 遍历下游。
- **元数据覆盖率** — Metadata Coverage：负责人/SLA/口径的挂接比例。
- **维度耦合** — Dimension Coupling：五个维度非独立，故障可跨维传播。
- **工程优先级** — Engineering Priority：血缘→时效→体量→模式→分布。

## 最新演进与工业实践

- **自动化血缘采集**：OpenLineage 等开放标准使血缘事件可从 Spark/dbt 自动提取，降低人工登记成本（⚠️ 工具细节见 05 章）。
- **时效监控内建化**：云仓（Snowflake/BigQuery）开始内建 freshness 指标采集，减少自建快照表的需求（⚠️ 厂商口径）。
- **分布检测的统计严谨化**：从简单阈值向假设检验（Bootstrap/KS）演进，降低误报率（⚠️ 学术口径转述）。
- **工业实践口径**：先建血缘登记、再铺时效/体量监控、最后做分布检测——渐进式部署是品类共识（⚠️）。
- **与治理的接榫**：元数据覆盖率审计是治理制度（[../Data_Governance_Elsevier/00-总览与阅读地图.md](../Data_Governance_Elsevier/00-总览与阅读地图.md)）的运行态验证器。
