# 03 过期策略与内存管理

> ⚠️ 结构声明：精读重构主题单元，非原书实抓章节（缺口申报见 [00-总览与阅读地图.md](00-总览与阅读地图.md)）。
> 全单元前提：**Redis 本机不装不跑 ⚠️**——过期/逐出的服务器行为一律「转述+官方文档 URL」；🔧 部分是用 sqlite3 3.45.3 **复现回收算法的概念实验，非 Redis 行为**。

## 3.1 TTL 语义层（⚠️ 转述，命令族见 https://redis.io/docs/latest/commands/ ✅）

- 设定面：`EXPIRE/PEXPIRE/EXPIREAT`（秒/毫秒/绝对时刻）、`TTL/PTTL`（-1=永不过期，-2=键不存在——两个负值语义要背清 ⚠️）；`PERSIST` 撤销。
- 继承规则（⚠️ 易错）：对整值覆盖写（SET/GETSET）会**清除** TTL；而像 LREM、HDEL 这类「改结构内部」的命令**保留** TTL——过期是**键级属性**，不是值级。
- 与 SQL 世界的对照：没有「行级自动删除」这种内建机制；最接近的是 MySQL 事件调度器/分区 TRUNCATE 的运维土办法——Redis 把这件事做进了内核调度循环，这是它作为缓存服务器的身份特征。

## 3.2 惰性删除 + 周期抽样：双轨回收模型

Redis 的过期键回收是两条轨道（⚠️ 以下服务器行为全部为文档/源码书转述口径，本机未实测）：

1. **惰性删除（lazy deletion）**：任何命令访问键时先检查是否过期，过期则删除并返回 nil。**不访问就永远占内存**。
2. **主动过期（active expiration）**：后台周期性从带 TTL 的键空间里**随机抽样**（官方文档口径：默认每 100ms 若干轮、每轮抽 20 个、过期比例>25% 则续轮 ⚠️ 具体节拍数字以 redis.io 文档树现文为准，本册仅交易页路径实测可达（https://redis.io/docs/latest/develop/using-commands/transactions/ ✅ 200），过期专页未逐一验证，按缺口处理）；本书按「抽样-概率」骨架记忆）。

**关键性质**：抽样是概率算法 → **过期≠即时释放**，内存回收与键数、TTL 分布、CPU 余量耦合。这解释了经典事故形态：写入风暴产生海量过期键 → 回收跟不上 → 触发 maxmemory 逐出（3.3）。

### 🔧 概念复现：抽样回收到底多「不即时」

sqlite3 3.45.3 建 10000 键、其中 1000 个 50ms 短 TTL；等其逻辑过期后（无人访问）：

- 惰性轨道模拟：未被访问的过期行**物理仍在表中**（实测 COUNT 存活=1，行未删——只保证「读时不可见」）。
- 主动轨道模拟：每轮随机抽 10 个键删除其中已过期者，循环直到清完 1000 个过期键：**5653 轮、总耗时 8173ms**（本机实测数字 🔧）。
- 读数：末期每轮期望命中趋近 0——**剩余过期键越稀疏，抽样回收越慢**（几何衰减尾部拖长）。这正是 Redis 要配合「按 TTL 小顶堆/桶」做近似定序、并在 CPU 余量不足时放弃回收的原因（⚠️ 机制转述）。
- 方法脚本：`D:\develops\tmp\dbwave_w3_lredis\demo.py`。**被测的是回收算法的普遍形态，不是 Redis 的 20ms/100ms 节拍** ⚠️。

## 3.3 maxmemory 与逐出策略族（⚠️ 转述）

- `maxmemory` 不设=纯放任（32 位/容器场景经典 OOM 来源）；设定后按 `maxmemory-policy` 逐出。策略族（8 种，2015 书基线即有主体）：
  - `noeviction`（默认）：写命令报错，读仍可——「当数据库用」的正确姿势。
  - LRU 近亲：`allkeys-lru` / `volatile-lru`（后者无带 TTL 键可逐时退化为报错 ⚠️）。
  - TTL 近亲：`volatile-ttl`（优先逐出最早过期者；八策略族中 TTL 向只有它，无 allkeys 对应物 ⚠️）。
  - 随机：`allkeys-random` / `volatile-random`。
  - LFU：`allkeys-lfu` / `volatile-lfu`（**4.0 才加入** ⚠️——2015 书里不可能讲，读它时的时代断层）。
- 实现注记（⚠️ 转述）：Redis 的 LRU 是**近似**的——每键存 24bit 逻辑时钟+随机采样池（文档口径：`maxmemory-samples` 默认 5），不是精确链表；LFU 同理用衰减计数。背「O(1) 精确 LRU」去面试会答错 Redis。
- volatile vs allkeys 的选型实质是**数据分类学问题**：哪些键「丢了也不能错」（缓存→allkeys），哪些键「丢=事故」（业务态→必须带 TTL 进 volatile 池并保证全覆盖 ⚠️ 或干脆 noeviction）。

## 3.4 内存从哪里省：键值之外的账

- 键名本身是内存：`user:10086:profile` 式长键×百万级 → 前缀压缩/短名/编号化的空间（⚠️ 经验口径；官方整理见 https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/ ✅ 实测 200）。
- 结构选择即容量：同是「一组 id」，set vs zset vs bitmap（连续整数值域）的位图编码差着数量级（02 的类型账在内存维度的重算）。
- 共享对象池：0-9999 整数缓存、小 SDS 的编码复用（⚠️ 转述，源码层展开让位 [../Redis设计与实现.md](../Redis设计与实现.md)——其「对象」章正讲此机制）。
- hash field 级 TTL（7.4+ ✅ https://redis.io/commands/hexpire/ ）把「大 hash 整体过期浪费窗口」变成精细回收——本单元 3.1「过期是键级属性」的教科书表述在 2026 年需要打补丁。

## 3.5 面向 SQL 开发者的类比收束 🔧

把 Redis 缓存池想成 Buffer Pool：MySQL 用 LRU 变体在**页**粒度换入换出、数据源头在盘；Redis 在**键**粒度逐出、逐出即**数据蒸发**（无回源换入的对称机制——回源是应用层 cache-aside 的职责，见 [07](07-Web与业务解决方案模式.md)）。这一字之差（页会回来、键不会）是两套内存管理哲学的分界：**缓存层级 vs 存储层级**。TTL/逐出参数永远回答不了「丢了谁负责」——那是架构题（⚠️ 判断句）。

## 3.7 事故推演：三种典型死法（⚠️ 机制推演，非实测）

1. **TTL 风暴**：整点批量写入同 TTL 键 → 同刻集体过期 → 主动回收占满 CPU + 逐出潮 → 延迟毛刺成分钟级周期。药方：TTL 加抖动（07 呼应）、错峰写入。
2. **volatile 错觉**：以为「设了 TTL 就等于管住了内存」——海量键挤在同一长 TTL 档里，未到期前 maxmemory 先到 → 逐出候选池已空 → 写报错。TTL 是**寿命**策略，逐出是**水位**策略，两条线独立记账。
3. **近似 LRU 的头部盲区**：采样 5 的近似实现下，一个被高频访问但采样恰好漏掉的键可能被逐出；工作集略超内存时命中率悬崖式抖动——**缓存容量的账要按尖峰而非均值算**（⚠️ 工程通识句）。

## 3.9 一页纸决策流（写进配置模板前的四问 ⚠️）

①这份数据丢了谁负责？（答不上→别放 Redis）→ ②是缓存还是业务态？（缓存→allkeys-*，业务态→全键带 TTL 进 volatile-*，混合→拆实例）→ ③内存水位按尖峰工作集×安全系数留了几成？→ ④TTL 有抖动吗？四问全过再谈 `maxmemory-samples` 调参——本册不给调参数字（无实测资格 ⚠️）。

## 3.10 与教科书口径的三处对照（防止概念串线 ⚠️）

- vs 操作系统页面置换：近似 LRU 采样 ↔ 时钟/二次机会算法——都在「精确账本太贵」下用**统计代理**；但页能换出再换回（03 3.5），键逐出即蒸发。
- vs GC 理论：惰性+周期双轨 = 「handle 时检查 + 后台 mark-sweep」的KV件变体；🔧 演示 5653 轮的几何尾部就是无根集扫描代价的缩影。
- vs 关系库 buffer pool：见 3.5 收束段——同词（LRU/逐出）不同实（可回/不可回），本系列老规矩：**两代机制同名必分两句写**。

## 核心概念速览（中英对照）

- **过期** — expiration：键级 TTL 属性，EXPIRE 族命令设定。
- **惰性删除** — lazy expiration：访问时检查并删，不访问不释放。
- **主动过期** — active expiration：周期随机抽样回收的后台轨道。
- **抽样概率性** — sampling probabilistic：回收完成时间不可保证上界。
- **最大内存** — maxmemory：逐出机制的触发水位线。
- **逐出策略** — eviction policy：noeviction/LRU/LFU/TTL/random×allkeys/volatile 族。
- **近似 LRU** — approximate LRU：随机采样候选+24bit 逻辑时钟的实现折中（⚠️）。
- **LFU** — least frequently used：4.0 加入的频次衰减策略，书基线不存在 ⚠️。
- **volatile/allkeys 域** — 逐出候选集是否限定带 TTL 键的分类轴。
- **逻辑过期** — logically expired：已超时未回收的中间态（🔧 演示中的存活行）。
- **内存放大** — memory amplification：键名/编码/结构选择造成的隐性占用。
- **键级过期** — key-level TTL：过期粒度是键不是 field（7.4 前）⚠️。
- **逐出即蒸发** — eviction as data loss：与 Buffer Pool 换页的本质区别。

- **TTL 粒度革命（7.4+）**：hash 字段级 TTL（HEXPIRE/HTTL ✅ 命令页实测 200）——3.1 的「键级属性」在 2026 年已是弱命题；00 对位表登记。
