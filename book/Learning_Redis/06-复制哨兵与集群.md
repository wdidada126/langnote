# 06 复制、哨兵与集群

> ⚠️ 结构声明：精读重构主题单元，非原书实抓章节（缺口申报见 [00-总览与阅读地图.md](00-总览与阅读地图.md)）。
> **本单元零实测**：Redis 本机不装不跑 ⚠️（波次红线：不尝试任何引擎/Docker）；全部内容「转述+已验证 URL 文档页」，Sentinel 官方页 ✅ 本轮实测 200（https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/ ）。

## 6.1 主从复制：一切高可用的地基（⚠️ 转述）

- 机制骨架：从库 `REPLICAOF`（新名；旧名 SLAVEOF——2015 书用的是旧词汇 ⚠️ 历史语境）→ 全量同步（以主库 RDB 为种子，正是 [05](05-持久化RDB与AOF.md) 5.2 的「复制首传」用途）→ 增量续传（复制偏移量+复制积压缓冲区 repl-backlog）。
- **异步默认**：主库写完即答客户端，不等从库落账 → 主库崩溃在途写可能丢；半同步方向的文件描述符级确认（`WAIT` 命令，7.2 前后引入 ⚠️ 不咬死版本）只把「等待确认」变成应用可选项，不改变默认语义。
- 与教科书的坐标：这是 [../数据库系统概念6/19-分布式数据库.md](../数据库系统概念6/19-分布式数据库.md) 里「更新传播+多副本读」的最简档；[../设计数据密集型应用.md](../设计数据密集型应用.md) 的复制三态（单主/多主/无主）框架在 Redis 上的落点是「单主+星型读副本」。
- 只读副本的读扩展示实是缓存层的第二杠杆：报表/热点读分流到从库，写与强一致读钉主库（⚠️ 架构口径；「从库读到旧数据」的会话不一致问题不因复制而消失）。

## 6.2 Sentinel：故障检测与自动接管（⚠️ 转述）

- 职责三件：监控（quorum 个哨兵异议通过才判主观/客观下线，SDOWN/ODOWN 两级判定）、通知、**自动主从切换+配置提供**（客户端问哨兵「现在主是谁」）。
- 关键清醒剂（⚠️）：哨兵解决「谁当主」，**不解决脑裂期间的数据归属**——旧主在分区里继续接受写，恢复后被降级、其 in-flight 写可能被丢弃（与 6.1 异步默认同源）。要「已知安全」的切换必须上 quorum 化方案，社区标准是 Redlock 争议域（[04](04-事务MULTI与服务器端脚本.md) 已登记不站队）。
- 书基线语境：Sentinel 在 2015 已被认真讨论但生产化比例低；今天哨兵+托管 Redis 的组合大量被「云原生多副本」替代（⚠️ 观察转述）。

## 6.3 Cluster：分片 + 内建故障转移（⚠️ 转述）

- 数据切分：**16384 个哈希槽**，`CRC16(key) mod 16384` 定槽（⚠️ 算法与槽数为文档/源码书口径）；槽指派给节点对（每主可挂从），节点间走二进制集群总线协议（ gossip + 故障判定 + failover，与 RESP 客户端协议不同层 ⚠️）。
- 客户端代价（架构题，SQL 开发者最易低估）：
  1. 跨槽多键命令（MSET 两键、涉及多键的 Lua/事务）**不可用**，除非用 **hash tag**（`{user1000}.following` 式花括号强制同槽）——分片把「查询的形状」变成数据模型约束 ⚠️。
  2. `ASK`/`MOVED` 重定向：路由缓存与迁移期重试是客户端库的核心竞争力。
  3. SCAN 变成「按节点并行游标」的聚合遍历。
- Cluster vs Sentinel 的分工表（本单元背诵版）：

| 维度 | 主从+Sentinel | Cluster |
| --- | --- | --- |
| 写扩展 | 无（单主） | 有（按槽分片） |
| 容量 | 单实例内存上限 | 内存水平扩容 |
| 多键语义 | 完整 | 受同槽限制 ⚠️ |
| 运维心智 | 类关系库主备 | 自带分片中间件语义 |

## 6.4 高可用谱系上的 Redis 位置（收束判断 ⚠️）

- 「复制=耐久化补充」「哨兵=可用性自动机」「集群=容量+可用性合体」——三层各治一病，2015 书把它们并列讲是当时社区用法的写照；今天的选型现实是：多数团队**用云的托管多副本而自建无**，这三层机制退化为「理解托管产品行为的原理层」（⚠️ 判断句）。
- 数据正确性的最后防线不在这三层中的任何一层，而在应用对「异步+可能丢」的显式补偿（对账/幂等）——这是 [../设计数据密集型应用.md](../设计数据密集型应用.md) 容错主题在 Redis 语境的回声。

### 🔧 无类比演示的说明

分片/故障转移的「形状」理论上可用 sqlite3 主键哈希路由模拟（本册方法域内），但本单元核心命题是**时序与共识行为**，SQL 单机件无法诚实地复现其语义——按纪律**不做伪实测**，全节维持 ⚠️ 转述。此判断本身即是本系列「🔧 只测能测的」纪律的执行样例。

## 6.5 本单元的三条易错点清单

1. 「有从库=有备份」——错：异步复制不救逻辑写坏（DEL 也照复制），救硬件；备份仍走 05 的 RDB 外送 ⚠️。
2. 「Cluster 会自动 rebalance」——错：槽迁移需人发起（reshard），自动只管故障转移 ⚠️。
3. 「哨兵数随便 3 个」——不够：quorum 是**判定**参数不是法定人数，部署拓扑（跨 AZ、故障域分离）另题 ⚠️。

## 6.6 副本侧的两块补板（⚠️ 转述）

- **副本优先级**（`replica-priority` ⚠️ 参数名以现文为准）：故障转移时哨兵/集群按优先级+偏移量+runid 三级排序选新主——「数据最全者优先」的体现，运维上意味着**别让低内存机器当候选主**。
- **无盘复制**（diskless sync，4.0+ ⚠️）：全量首传不落中间文件、子进程直接流式发送——专治「磁盘慢到 fork/写 RDB 成为复制瓶颈」的云盘环境；书基线读者会惊讶于「复制居然可以不碰 RDB」，这正是 05 快照用途的旁支化。
- 两块板共同的教科书意义：**复制通道的耐久化耦合点**（RDB 种子/缓冲区/磁盘）全是 RTO-带宽-CPU 三角的投影，对照 [../数据库系统概念6/19-分布式数据库.md](../数据库系统概念6/19-分布式数据库.md) 更新传播成本一节来读最省解。

## 6.7 分片感知的客户端旅程（文字版时序 ⚠️）

以「对 `order:{u1000}:detail` 与 `order:{u1000}:items` 做 MGET」为例：

1. 客户端持槽表缓存（16384 槽 → 节点映射，CLUSTER SLOTS/SHARDS 口径 ⚠️ 命令名以现文为准）。
2. hash tag `{u1000}` 使两键 CRC16 同槽 → 路由单节点 → MGET 合法执行（**同槽是多键命令的通行证**）。
3. 若其中一键算错槽：首命令即 `MOVED` 回包 → 客户端刷新该槽路由重试；迁移进行中则 `ASK` + `ASKING` 的一次性转发（⚠️）。
4. 迁移完成的信号也只是槽表版本号变化——**客户端库的集群成熟度 = 对 2/3 步的处理质量**，选型时这条比功能表重要（⚠️ 判断句）。

对照关系库心智：这一步「把 JOIN 拆成路由问题」的过程，正是 [../设计数据密集型应用.md](../设计数据密集型应用.md) 分区篇在 Redis 上的特化版。

## 6.8 三步迁移决策：单机 → 主从+哨兵 → Cluster（⚠️ 架构推演）

| 触发信号 | 升级动作 | 会新增的代价 |
| --- | --- | --- |
| 读 QPS 把主库 CPU 吃满 | +只读副本分流（6.1） | 副本会话不一致窗口 |
| 主库故障需要人夜间接管 | +Sentinel 自动切换（6.2） | 脑裂窗口暴露给业务（6.2 清醒剂） |
| 容量/写 QPS 触顶，且能接受键设计约束 | Cluster 分片（6.3） | hash tag 设计税、跨槽命令禁、SCAN 聚合 |
| 全都要且不想自建 | 托管多副本服务 | 供应商锁定、参数黑盒 |

- 纪律句：**每一档升级都是拿一种新故障换旧故障**，不是「更多保险」——与 03/05 的「逐出/丢窗」账本同构，架构层的账也要三态标注 ⚠️。
- 本表不背书任何容量数字（不装不跑 ⚠️），阈值判断全部以你的监控基线为准。

## 6.9 一句话词汇映射（读 2015 书前贴好）

slave→replica（命令与配置全族更名 ⚠️）、master→primary/主、集群「节点」在现代文档里区分 cluster nodes 与哨兵 monitoring nodes 两词（6.2/6.3 各用各的）——本书原文两种旧词混用处，按此表翻译后语义即通。

再补两个高频旧配置：`slaveof`→`replicaof`、`slave-read-only`→`replica-read-only`（⚠️ 更名随 4.0+ 术语治理，旧名在现版多作别名仍可解析，以 redis.conf 现文为准）；哨兵的 `sentinel monitor <name> <ip> <port> <quorum>` 配置句式自引入以来骨架未变（⚠️），是 6.2 少数「书里写的今天还认」的条目。

## 6.10 快问快答（面试级 ⚠️ 全转述）

- Q：主库挂了，从库会不会自动补上？A：主从模式不会（人上），哨兵/集群才会（6.2/6.3）。
- Q：切主后旧主在分区里写的数去哪了？A：降级为从后按复制协议对齐新主，**分区期写入按机制可丢**（6.2 清醒剂）。
- Q：Cluster 能线性扩容到任意大吗？A：受限于单键体量（大键不可切）与热点槽（6.3 hash tag 副作用），横向扩「键数」不扩「单键」。
- Q：读从库安全吗？A：数据层安全、逻辑层可能旧——对旧值敏感的读钉主库（6.1 末段）。
- Q：三套机制能叠加吗？A：Cluster 内建每槽主从+故障转移，通常**不再**另挂哨兵（6.3 分工表）。

## 核心概念速览（中英对照）

- **主从复制** — replication：全量（RDB 首传）+增量（偏移量/积压缓冲）的单主传播。
- **异步复制默认** — async by default：主库应答不等从库确认的丢窗根源。
- **复制偏移量** — replication offset：续传与裂化判定的游标。
- **REPLICAOF** — 新命名口径；旧名 SLAVEOF 属 2015 书词汇（历史语境 ⚠️）。
- **Sentinel 哨兵** — 监控/判定/自动切换/配置提供的独立进程族。
- **主观/客观下线** — SDOWN/ODOWN：单哨兵疑心 vs quorum 共识定罪。
- **故障转移** — failover：从库升主+其他从库改父的接管流程。
- **脑裂窗口** — split-brain window：分区中旧主继续写的危险期（⚠️ 不承诺安全）。
- **哈希槽** — hash slot：16384 格，CRC16 取模的元分片映射 ⚠️。
- **hash tag** — 花括号键片段：强制同槽以恢复多键命令能力 ⚠️。
- **MOVED/ASK** — 路由重定向：客户端迁移感知协议。
- **集群总线** — cluster bus：节点间 gossip/故障判定的二进制通道 ⚠️。
- **WAIT** — 副本确认等待命令：把异步往同步方向拉一档的应用级选项 ⚠️。
