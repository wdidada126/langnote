# 02 五大数据类型的语义

> ⚠️ 结构声明：精读重构主题单元，非原书实抓章节（缺口申报见 [00-总览与阅读地图.md](00-总览与阅读地图.md)）。
> 类型语义面证据：redis.io 数据类型文档 ✅ 本轮实测 200（https://redis.io/docs/latest/develop/data-types/ ）；命令族语义标 ⚠️ 转述；🔧 演示为 sqlite3 3.45.3 / DuckDB 1.5.5 上的概念复现，**非 Redis 行为**。

## 2.0 类型总表（2015 书基线 → 今天）

| 类型 | 语义一句话 | 典型复杂度 | 书时代(≈2.8/3.0)后的重要增补 |
| --- | --- | --- | --- |
| string | 二进制安全字节串，可当整数用（INCR）| O(1) | —（GETRANGE/SET 选项演变 ⚠️） |
| hash | field→value 二级小哈希，对象属性存储 | 字段操作 O(1) | 7.4+ 字段级 TTL（HEXPIRE ✅ https://redis.io/commands/hexpire/ ） |
| list | 双向链表/快表，两端 O(1) | LPOS 等后来者 ⚠️ | 6.0.6+ LPOP/RPOP count 参数 ⚠️ |
| set | 无序唯一集 | SADD/SISMEMBER O(1) | SDS 编码的 listpack 化 ⚠️（内部实现让位 [../Redis设计与实现.md](../Redis设计与实现.md)） |
| zset | 按 score 排序+成员唯一，排行榜原语 | 核心操作 O(logN) | 7.4+ ZMPOP ⚠️ |
| （书中或有）bitmap/hyperloglog/geo | string/set/zset 之上的编码应用 | — | Stream(5.0) 才是最大的后补类型 ⚠️ |

## 2.1 string：最被低估的类型

- 语义要点（⚠️ 转述）：值是二进制安全的 blob（可放图片字节/序列化对象）；`INCR/DECR` 把字符串当 64 位整数**原子**修改——计数器、限流器、分布式锁的令牌都是这一条语义的衍生物。
- SQL 心智对照：`UPDATE t SET n=n+1` 的行锁原子性，在 Redis 里由「单命令天然串行」免费提供（见 [01](01-Redis定位与SQL开发者的视角.md) 1.3）。
- 反模式：把整张「宽表」序列化成 JSON 塞进一个 string——退化为远程字典缓存，放弃了 02/07 全部结构能力（⚠️ 经验口径）。

## 2.2 hash：对象与其二级索引的抉择

- 语义：`HSET user:1 name x score 10` —— 外层仍是键空间的扁平 key，内层 field→value。适合「整体读写少数域」的对象；不适合「按域聚合查询」（hash 不可按 field 检索 ⚠️）。
- 与关系库对照：hash ≈ 一行记录的 KV 化投影；**但无类型、无约束、无 NULL 语义**（HGET 未命中即 nil）。
- 选型题：对象要么整存 string(JSON)，要么拆 field 存 hash——前者省 RTT、后者可局部改与 TTL 于整体（field 级 TTL 是 2024+ 才补的课 ⚠️）。

## 2.3 list：队列与窗口

- 语义：LPUSH/RPOP 两端操作；`BRPOP` 阻塞出队=最早的轻量任务队列（⚠️ 转述；可靠性远逊专职 MQ，见 [07](07-Web与业务解决方案模式.md)）。
- LRANGE 是 O(N)——大 list 全读与 KEYS 同属阻塞反模式族。
- 历史语境：2015 书时代「列表做队列」尚无消费者组语义；5.0 Stream（XADD/XACK/组）才把「Redis 当 MQ」认真化（⚠️，08 对位表登记）。

## 2.4 set：唯一性与集合代数

- 语义：SADD/SREM/SISMEMBER + 交并差（SINTER/SUNION/SDIFF）——共同好友、标签圈选这类「关系运算」在 SQL 里是 JOIN，在 Redis 里是服务端一条命令 ⚠️。
- 🔧 类比演示（DuckDB 1.5.5，概念复现非 Redis）：以 100 万成员主键表模拟 SISMEMBER 判定：

```
命中: SELECT count(*) FROM s WHERE member='m999999'  → 1，用时 2.1ms
未命中: 同型查询 'nope'                              → 0，用时 1.1ms
```

  哈希主键的 O(1) 判定路径与 Redis set 的「哈希+唯一性」同一复杂度族；注意 DuckDB 是列存扫描/索引优化器行为，**不是** Redis 内存哈希表 🔧。

## 2.5 zset：本书副题「business solutions」的第一原语

- 语义：`ZADD board 1234 user42`；成员唯一、按 (score, member 字典序) 全序；核心读路径 `ZRANGE/ZREVRANGE`（排名分页）、`ZRANK`、`ZCOUNT/ZRANGEBYSCORE`（分数区间）、`ZINCRBY`（榜单更新）。
- 为什么它是「数据结构设计课」：排行榜=前 N、热点榜=score 用时间戳（时间窗口滑动的技巧 ⚠️）、延迟任务=score 存执行时刻（07 复用）。
- 🔧 类比演示（sqlite3 3.45.3 真跑，20 万成员，方法同 `D:\develops\tmp\dbwave_w3_lredis\demo.py`）：

```
ZREVRANGE 0 4 类比   ORDER BY score DESC, member ASC LIMIT 5      11.4ms（无索引全排序）
ZRANK 类比           COUNT(*) WHERE score > 目标                  11.1ms（rank=72057）
ZCOUNT 5000~5100 类比 BETWEEN 区间计数                             10.2ms（count=2054）
建 (score,member) 复合索引后重跑 ZCOUNT 类比                        0.09ms
```

  解读：Redis zset 用「跳表+字典」把后两类查询常备化成 O(logN)——相当于**永远自带**那条复合索引；🔧 演示里「裸表 vs 加索引」的百倍差就是这一设计价值的镜像复现。再次强调：测的是 SQL 引擎，不是 Redis ⚠️。

## 2.6 「编码类型」层：为什么本册不讲 ziplist/listpack

- 2015 书的常见卖点是「底层编码切换」（ziplist、intset、skiplist…）。本目录**主动让位**：该主题是 [../Redis设计与实现.md](../Redis设计与实现.md)（黄健宏，SDS/字典/跳表逐结构源码级）与 [../Redis5设计与源码分析.md](../Redis5设计与源码分析.md)（陈雷等，5.x 口径）的既有领地，重复建档违反系列分工（见 00 对位表）。
- 需要记住的接口事实只有两条（⚠️ 转述）：小集合用紧凑编码省内存、超阈值自动升级且**不降级**；`OBJECT ENCODING` 可观测（✅ 命令索引页在 https://redis.io/docs/latest/commands/ ）。

## 2.7 类型选型速查（面向 SQL 开发者的三问）

1. 访问路径是否只有「按 id 取整体 / 改一个域 / 原子加减」？→ string/hash。
2. 是否需要服务端排序、排名、分数窗口？→ zset（并自问：这是不是把 ORDER BY 挪进了内存）。
3. 是否需要集合代数或多值去重？→ set（基数巨大且只要计数？→ HyperLogLog，误差 ~0.81% ⚠️）。

## 2.8 同一张榜单的三种搭法（类型组合演练 ⚠️ 模式口径）

需求「商品近 7 天销量榜」，用 2.1–2.5 的件组装出三个档：

| 档位 | 结构 | 写路径 | 读路径 | 死穴 |
| --- | --- | --- | --- | --- |
| 粗 | hash `sales:{sku}` + 定时全量算 | HINCRBY | 应用拉 HGETALL 排序 | 键数=SKU 数，聚合在应用侧 |
| 中 | 单 zset `board:7d` | `ZINCRBY board:7d 1 sku` | `ZREVRANGE 0 9` | 无法按时间切片 |
| 精 | 日桶 zset `board:{date}` + 读时 ZUNIONSTORE 合并 | 当日桶 ZINCRBY | 合并进临时键再取 TOP | 合并代价与桶数成正比（O(N) 命令！） |

- 三档全部只用到 2.1 的 INCR 原子性 + 2.5 的排序读；「类型即 API」的含义=**组合空间在设计期枚举，运行期零规划**。
- 精档的 ZUNIONSTORE 是 LRANGE 同款惰性复杂度（2.6 告诫的复用点）：桶数一多必须预计算物化榜——物化思想即关系库的 MV 前奏（⚠️ 对照 [../数据库系统概念6/14-事务.md](../数据库系统概念6/14-事务.md) 所在教材的物化视图章节口径）。

## 2.9 键命名：约定而非机制

- 通行惯例（⚠️ 社区口径，非官方规范）：`业务:实体:id[:字段]` 冒号分层——**键空间是扁平的，分层只为 SCAN MATCH 前缀遍历与人类可读**；`{}` 才是有语义的字符（hash tag，06/Cluster）。
- SQL 对照：命名前缀≈ schema 表名前缀，但无任何约束力；键写错前缀=制造孤儿数据，无外键无审计（01 1.3 的一致性责任全在应用的又一体现）。
- 体量卫生：键名按 8 字节级设计（`u:10086` 优于 `user:profile:10086` 的极端例），百万键规模下前缀每省 1 字节都是真金白银（03 内存账的入口）。

## 2.10 类型×命令×复杂度的速查矩阵

| 你想做 | 类型 | 命令（⚠️ 转述，索引见 ✅ https://redis.io/docs/latest/commands/ ） | 复杂度档 |
| --- | --- | --- | --- |
| 判成员 | set / zset | SISMEMBER / ZSCORE | O(1) / O(logN) |
| 取前 N | zset | ZRANGE | O(logN+N) |
| 按分数切片 | zset | ZRANGEBYSCORE | O(logN+M) |
| 交集圈选 | set | SINTERSTORE | O(最小集×N) |
| 队列弹出 | list | LPOP/BRPOP | O(1) |
| 计数 | string | INCR | O(1) |
| 对象局部改 | hash | HSET/HINCRBY | O(1) |
| 全量遍历 | 任意 | SCAN（渐进，非原子） | 摊销 O(N) |

最后一行的 SCAN 单独记：**它是唯一「合法的全键访问」**，游标式渐进、允许遍历期增删（⚠️ 语义转述）；02 全矩阵里没有任何一行写着「条件查询」——这就是 01 那张表的下半句。

## 核心概念速览（中英对照）

- **字符串** — string：二进制安全 blob + 原子计数语义（INCR）。
- **哈希** — hash：field→value 二级映射，对象局部读写的默认载体。
- **列表** — list：两端 O(1) 的有序可重复序列，BRPOP 提供阻塞出队。
- **集合** — set：无序唯一集，SINTER 系命令把集合代数下推服务端。
- **有序集合** — sorted set (zset)：score 全序+成员唯一，排行榜/延迟队列原语。
- **排名** — rank：ZRANK 的名次语义，与 score 区分（同分按字典序 ⚠️）。
- **字典序破平** — lexicographical order：score 相同时以 member 定序，zset 全序的来源。
- **编码升级** — encoding upgrade：ziplist/listpack→大型结构的单向切换（细节让位源码书）。
- **HyperLogLog** — HLL：概率基数估计，换精度省内存（⚠️ 转述口径）。
- **位图** — bitmap：string 上的 SETBIT 编码，签到/活跃标记类应用。
- **惰性复杂度** — hidden O(N)：LRANGE/SMEMBERS 等「看似一条命令实则全量」的阻塞风险。
- **反向索引** — inverted index emulation：set/zset 组合模拟二级索引的通用手法。
- **Stream** — 5.0 起的追加日志类型：书基线之后最重要的类型增补（⚠️）。

## 最新演进与工业实践

- **字段级 TTL**：hash 域可过期（HEXPIRE，7.4 引入，⚠️ 转述）；官方命令页 https://redis.io/commands/hexpire/ ✅ 实测 200——直接改变 2.2 的「整键过期」局限。
- **类型增补节奏**：Stream(5.0)、zset 的 ZADD GT/LT 选项、list 的 LMOVE 家族、ExHash/ExSet 等企业版类型（⚠️ 口径混合，不逐条断言版本）。
- **listpack 全面替换 ziplist**（7.0 代际，⚠️ 转述）：2.6 的编码名词表若照 2015 书背会过时。
- **客户端生态**：redis-py（PyPI `redis`）与 node-redis 官方客户端仓库均挂在 https://github.com/redis 名下（组织主页 ✅ 可回链 redis.io 文档）；「用什么类型的第四问：客户端支不支持」是 2026 年新现实。
- **概念复现方法本身**：本单元 🔧 的「SQL 件模拟 NoSQL 语义」路线与 [../DuckDB_Up_and_Running/00-总览与阅读地图.md](../DuckDB_Up_and_Running/00-总览与阅读地图.md) 的「不装重型引擎拿一手数字」纪律同源，可互为方法引证。
