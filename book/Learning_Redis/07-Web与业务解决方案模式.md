> ⚠️ 结构声明：精读重构主题单元，非原书实抓章节（缺口申报见 [00-总览与阅读地图.md](00-总览与阅读地图.md)）。
> 本单元是对副题「Design efficient web and business solutions with Redis」✅（isbnsearch/Amazon 实抓）的正面回应：把 02 的类型学 + 03/04/05 的机制约束组装成应用模式。模式描述属通用工程知识（⚠️ 转述/判断句），Redis 行为面沿用前几单元的标注纪律。

## 7.1 缓存旁路（cache-aside）：默认集成形态

- 流程：读→GET 命中返回；未命中→回源关系库→SET（带 TTL）→返回。写→**先更新库，再删缓存**（delayed double-delete 变体 ⚠️ 社区口径）。
- 竞态账本（SQL 开发者必须会画）：读回源与写失效交错时会出现「旧值回填」——TTL 是最终一致的下界保险，不是正确性机制；「删缓存失败」则需要 TTL 或消息补偿兜底 ⚠️。
- 三个经典击穿形态与解法档位 ⚠️：热点键过期瞬间（互斥重建/singleflight）、大量键同刻过期（TTL 加抖动——03 的抽样回收在应用侧的礼貌配合）、穿透不存在的键（空值短 TTL 或布隆过滤器）。
- 与 [../设计数据密集型应用.md](../设计数据密集型应用.md) 缓存章的分工：那边讲「为何/何时缓存会撒谎」的原理；本节给 Redis 命令级的组装。

## 7.2 计数器与排行榜：INCR/ZINCRBY 的业务直线

- 计数族：PV/限流/额度——`INCR key + TTL 桶`（如 `rate:{user}:{minute}`）是最小方案；04 已示「INCR 与 EXPIRE 两条命令」的原子缺口 → Lua/管道化建键时带 TTL ⚠️。
- 排行族（副题里 business solutions 的招牌）：`ZINCRBY board 1 uid` 更新、`ZREVRANGE board 0 9 WITHSCORES` 取 TOP10、`ZREVRANK` 查自己名次——三命令覆盖 90% 产品需求。
- 🔧 语义底座（承 02 演示 🔧）：20 万成员榜上 TOP5=11.4ms、区间计数加复合索引后 0.09ms（sqlite3 3.45.3）——「榜的三操作全部对数级」的形状已在 SQL 件上镜像过；Redis 侧为跳表+字典的常备化（⚠️ 结构口径让位 [../Redis设计与实现.md](../Redis设计与实现.md) 跳表章）。
- 时间窗口榜（「近 1 小时热榜」）：score=时间戳滑窗 + 定期清理旧段，或用多桶 zset 合并 ⚠️ 模式口径。

## 7.3 分布式锁：一个必须泼冷水的模式

- 正确姿势的下界（⚠️ 全部为文档/社区共识转述）：`SET lock tok NX PX 30000`（单命令原子获取+超时，04 4.3），值放随机 token，释放用 **Lua 比较 token 再删**（防误删他人锁）。
- 单实例 Redis 锁的固有洞：主崩溃→从升主时锁丢失（异步复制，6.1）；客户端 GC 停顿越过 TTL 后继续持「已失效锁」作业。Redlock（多实例 quorum）试图补前洞、争议仍在（[04](04-事务MULTI与服务器端脚本.md) 登记过不站队 ⚠️）。
- 工程判断句（⚠️）：锁用于**效率**（少做重复工）安全；用于**正确性**（资金互斥）要另加数据库唯一约束/条件更新做最终闸——把不变量押在 Redis 上违反 01 的「一致性归应用」原则。

## 7.4 队列与轻量消息

- 任务队列最小形：`LPUSH`/`BRPOP`（03 类型账+阻塞读）；至少一次语义要靠**可靠出队**模式：`LMOVE`（6.2+ ⚠️；书基线时代用 LPOP+备份队列的组合拳）把「取出即丢」改成「取出+在制队列」，处理完成再删——ACK 语义的手工拼装。
- 延迟任务：zset score=执行时刻 + 轮询 `ZRANGEBYSCORE ... LIMIT`（本单元第二个「时间当分数」手法 ⚠️）。
- 发布订阅（PUB/SUB）：即发即弃、离线丢消息——**通知**可以，**账本**不行（⚠️）；5.0 Stream 才补上持久日志+消费者组的 MQ 正经形（02 已登记为书基线后的最大增补 ⚠️）。
- 边界判断：需要顺序/事务性/回放保障的消息系统职责，不归 Redis 兼任（与 [../Stream_Processing_with_Apache_Flink/00-总览与阅读地图.md](../Stream_Processing_with_Apache_Flink/00-总览与阅读地图.md) 的领域分工一瞥）。

## 7.5 会话与用户态存储

- session 哈希/串（带 TTL = 会话自然过期，03 机制的产品化）；横向扩容 Web 层无需粘滞会话的经典解，2015 书时代即主打 ✅ 副题语境。
- 购物车/最近浏览：hash 与 list 的小数据高频形态；「用户画像类宽表」则应回到列存/OLAP 件（本系列立场句 ⚠️：Redis 不承担分析查询，01 已述无 ad-hoc）。
- 前端加速位：接口响应缓存 + 客户端缓存（RESP3 client-side caching，6.0 ⚠️ 见 08）——同一个 cache-aside 从服务端一路铺到浏览器侧。

## 7.6 模式组装的三条纪律（单元收束）

1. **每个模式先过「丢窗审计」**：该数据蒸发后谁重建、多久重建、重建前错给谁看——03/05/06 的三本账在此合拢（⚠️ 判断句）。
2. **不变量最终闸留在关系库**：Redis 做快、不做保——与 01 1.3 的表对位，约束/唯一性在回源库里兜底。
3. **可观测先行**：命中率的唯一真指标是「回源 QPS 曲线」；`INFO` 族计数器与慢日志（SLOWLOG ⚠️）是模式跑偏的第一报警器。

## 7.7 限流专型：从固定窗到滑动账（⚠️ 模式推演）

| 方案 | 键设计 | 原子性来源 | 缺陷 |
| --- | --- | --- | --- |
| 固定窗 | `rate:{uid}:{分钟片}` INCR+首建 EXPIRE | INCR 单命令（04 层1）；EXPIRE 竞态用「建键即 TTL」堵 | 窗边双峰：两窗交界可放行 2× 配额 |
| 双窗近似 | 当前片+前片按分钟占比加权 | 同上+两次读 | 权重计算在读侧 |
| 滑动日志 | zset：member=请求 id，score=时间戳 | ZREMRANGEBYSCORE+ZCARD+ZADD 入 MULTI/Lua（04 层2/3） | 键体积=窗内请求数，须设上限 |
| 令牌桶 | 两键（token 数+last_ts）Lua 结算 | Lua 原子（04 层3） | 脚本即规格，升级成本最高 |

- 读法示范：同一个「业务解决方案」在四个档上走的恰是 04 原子性金字塔的 1→2→3 层——**限流器是 Redis 模式学的标本盒**：类型（02 string/zset）、过期（03）、事务（04）、逐出（限流键必须 allkeys 域外或永不逐出）四单元在此合流。

## 7.8 设计演练：热门商品详情页（端到端 ⚠️）

场景：读 9000 QPS / 写 2 QPS，MySQL 读侧告急（副题「efficient web solutions」的教科书病例）。

1. 分层：静态素材出 CDN；动态数据走 cache-aside（7.1），TTL 90s+抖动（03 事故 1 的预防）。
2. 键形状：详情对象整存 string(JSON)（02 2.1 反模式的**正当使用位**：读写同粒度、无局部改需求）；库存单独 hash（高频局部改，HINCRBY 原子扣减意向 ⚠️ 最终账在库）。
3. 击穿防御：热点键重建用「互斥锁标记键」（30s 短 TTL，7.3 锁的效率侧用法——**别上 Redlock**，此处 7.3 判据：丢了只会多回源，不损正确性）。
4. 失效链：商品编辑→更新 MySQL→**删**缓存键（非改）；编辑后台再发一道延迟双删（补偿删缓存失败）。
5. 容量：峰值详情对象 50KB×热集 2 万 → 内存预算含 03 3.4 放大项；逐出域设 allkeys-lru（纯缓存，丢了可重建）。
6. 验收：回源 QPS 曲线从 9000 压到 <300 即达标（7.6 指标句的落地）。

- 演练的每个决策都能回指一个前序单元的编号——这就是本目录按「语义→机制→模式」排序的理由（00 阅读地图）。

## 7.9 反模式清单（副题的另一面 ⚠️）

1. 用 Redis 存「唯一的真相」：无约束+丢窗（01 1.3）+逐出三杀——它是加速层不是记录系统。
2. `KEYS *`、无上限 SMEMBERS、大 JSON GET 塞回 SET：单线程的三种自杀方式（01 1.4）。
3. 把 pub/sub 当订单消息总线：离线即丢（7.4），正确件在专职 MQ/Stream。
4. 一把全局锁保护所有写：04 4.8 活性平方塌方 + 06 主从切换丢锁双杀。
5. 会话里塞大对象：session 膨胀成「不可分析的宽表」——03 内存账与 7.5 定位的双重违规。

## 核心概念速览（中英对照）

- **缓存旁路** — cache-aside：应用自管读写两道的默认缓存拓扑。
- **回源** — origin fetch：未命中时对关系库的代读。
- **缓存击穿/穿透/雪崩** — hotkey stampede / penetration / mass expiry：三大失效形态族。
- **TTL 抖动** — expiry jitter：同批键过期时间加随机量错峰。
- **原子获取带超时** — SET NX PX：分布式锁的最小安全原语 ⚠️。
- **锁令牌** — lock token：防误删的持有者凭证。
- **Redlock** — 多实例仲裁锁算法：争议中的 quorum 方案 ⚠️。
- **可靠出队** — reliable dequeue：LMOVE/备份队列式 ACK 拼装。
- **延迟队列** — delayed queue：zset 时间戳分数模式的通称。
- **发布订阅** — pub/sub：fire-and-forget 通道，非队列 ⚠️。
- **会话外置** — session offload：Web 层无状态化的 Redis 经典用途。
- **命中率** — hit ratio：缓存健康度第一指标（结合回源 QPS 读）。
- **慢日志** — SLOWLOG：大 key/重命令的现场报警器 ⚠️。

- **命令面补齐**：LMOVE/BZPOPMIN 族（6.x）、SET 参数继续扩展（⚠️ 转述）——7.4 的可靠队列拼装比 2015 顺手得多；Stream 消费者组成为「轻量 MQ」的正式档（✅ 命令存在性见 https://redis.io/docs/latest/commands/ ）。
