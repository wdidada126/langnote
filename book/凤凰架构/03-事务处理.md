# 第 3 章　事务处理

> 原书第 3 章是「架构师的视角」里技术密度最高的一章：它从单机本地事务出发，一直推到跨服务的分布式事务，
> 并给出 CAP 与 ACID 的关系、可靠事件队列、TCC、SAGA 四条落地路线。
> 这一章是把第 2 章「远程调用」必然带来的「数据一致性」问题摊开来讲。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 3.1 本地事务 | 原子性+持久性（日志/写前日志）、隔离性（锁/多版本） | 单机下靠 ACID 与 WAL 即可保证，是后面一切的参照系 |
| 3.1.1 原子性/持久性 | Undo/Redo 日志、Checkpoint | 提交前先写日志，崩溃后可恢复 |
| 3.1.2 隔离性 | 四级隔离、MVCC、锁 | 隔离级别是「正确性 vs 并发」的权衡旋钮 |
| 3.2 全局事务 | DTP/XA、两阶段提交（2PC） | 跨多资源的事务靠协调者统一提交；但 2PC 是阻塞协议 |
| 3.3 共享事务 | 共享连接/数据源（同一库） | 规避分布式事务的「同库」取巧方案，适用范围窄 |
| 3.4 分布式事务 | CAP 与 ACID、可靠事件队列、TCC、SAGA | 跨服务的终极解法：放弃强一致，改用最终一致 + 补偿 |
| 3.4.1 CAP 与 ACID | 分区下 C/A 取舍，ACID 的 C 与 CAP 的 C 不同义 | 不要把「数据库一致性」与「分布式一致性」混为一谈 |
| 3.4.2 可靠事件队列 | 本地事务 + 发消息（本地消息表/事务消息） | 用「消息」桥接两个本地事务，追求最终一致 |
| 3.4.3 TCC 事务 | Try/Confirm/Cancel 三阶段补偿 | 业务层两阶段，适合强约束金融场景 |
| 3.4.4 SAGA 事务 | 长事务拆成一系列本地事务 + 补偿 | 适合跨多服务、长流程的业务编排 |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 3.1 本地事务：靠日志把「原子」和「持久」焊死

```text
# 教学示意，不参与构建：提交时先写日志（WAL）
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = ?;   -- 改内存页
WRITE REDO LOG (balance' = x-100)                          -- 先落盘日志
COMMIT;                                                    -- 提交标记入日志
-- 崩溃恢复：重放 redo 把已提交但未刷盘的改动补齐；回滚未提交事务
```

- **隔离性**：读未提交 → 读已提交 → 可重复读 → 串行化，是「并发度 vs 正确性」的旋钮；
  现代引擎多用 **MVCC**（多版本）实现「读不阻塞写、写不阻塞读」。

### 3.2 全局事务：XA / 2PC 把多个资源绑成一个原子操作

```text
# 教学示意，不参与构建：两阶段提交
Coordinator                         Participant A / B
    |-------- PREPARE ------------>|  写 undo/redo，回执「就绪/拒绝」
    |<------- READY/NO -----------|
    |-------- COMMIT ------------->|  真正提交（或 ABORT 回滚）
```

- **致命缺陷**：协调者在「参与者已就绪、自己还没发 COMMIT」时宕机 → 参与者**无限期阻塞**等待。
  所以全局事务的可用性差，通常只用于「同一机房、同构数据库」的窄场景。

### 3.4 分布式事务：接受「最终一致」

- **CAP 与 ACID 的 C 不是一回事**：ACID 的 C 是「约束不被破坏」（如账户总额不变），
  CAP 的 C 是「所有副本同时看到同一值」。分区发生时，CAP 逼你在 C 与 A 间取舍。
- **三条落地路线对比**：

| 方案 | 一致性 | 适用 | 代价 |
| --- | --- | --- | --- |
| 可靠事件队列 | 最终一致 | 可异步的业务（通知、积分） | 需处理消息重复/丢失 |
| TCC | 最终一致（业务补偿） | 强约束、短流程（支付） | 业务侵入大，需写 Confirm/Cancel |
| SAGA | 最终一致（长流程） | 跨多服务长事务（下单→减库存→发货） | 补偿链复杂、隔离弱 |

## 版本演进

- **本书无第二版**；本节写 2021 年口径 → 2026 年视角的变化。
- **共识算法的普及改变「全局事务」底座**：本书 3.2 的 2PC 协调者单点问题，今天由 Raft/Paxos 选主+日志复制解决（见 [06-分布式共识.md](06-分布式共识.md) 与 [../深入理解分布式共识算法/00-总览与阅读地图.md](../深入理解分布式共识算法/00-总览与阅读地图.md)）。
- **事务消息成为标准能力**：RocketMQ/Kafka 的事务消息让「可靠事件队列」落地更稳，本书 3.4.2 的本地消息表可被事务消息部分取代。
- **NewSQL/分布式 SQL 把分布式事务做到「可串行化」**：TiDB、CockroachDB、OceanBase 等用 Percolator/TSO 或 HLC 提供跨分片 ACID，读本书时应补这条现代路线（见 [../分布式数据库入门进阶与实战/00-总览与阅读地图.md](../分布式数据库入门进阶与实战/00-总览与阅读地图.md)）。
- **SAGA 编排 vs 协同**：本书 3.4.4 偏命令式，2026 年更强调「编排器（Orchestrator）」与「事件协同（Choreography）」两种模式取舍。
- **Jepsen 测试**把「声称的一致性」变成可证伪项（本书 2021 年未强调）。

## 近年研究与工业界开源实践（2015–2026）

- **分布式事务框架**：`seata/Seata`（26012★，2026-09-27 实测）是阿里巴巴开源的分布式事务框架，同时支持 AT/TCC/SAGA/事务消息四种模式，是本书 3.4 各方案的直接工程落地；
- **消息中间件（本书 3.4.2 可靠事件队列的载体）**：`apache/kafka`（33850★）提供事务消息；`rabbitmq/rabbitmq-server`（13879★）是经典 AMQP 实现；
- **缓存（事务边界外的加速，常参与最终一致方案）**：`redis/redis`（76487★）；
- **NewSQL（把分布式事务做成可串行化）**：`tikv/tikv`（16878★，Multi-Raft + Percolator）、`cockroachdb/cockroach`（32508★，HLC，未单独实测）、`vitessio/vitess`（21356★，MySQL 分片 + 事务）；
- **共识底座（2PC 协调者高可用）**：`etcd-io/etcd`（52310★）、`hashicorp/consul`（30087★）；
- **Jepsen 测试**把一致性声明变为可证伪工程实践（本书 3.4.1 应补）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「XA/2PC 能解决一切分布式事务」 | 2PC 阻塞、协调者单点、跨机房性能差；只适合窄场景 |
| 2 | 「ACID 的 C 与 CAP 的 C 是一回事」 | 前者是约束不被破坏，后者是副本同时可见同一值，不可混用 |
| 3 | 「分布式事务一定要强一致」 | 绝大多数业务用最终一致即可，强一致代价过高 |
| 4 | 「SAGA/TCC 能直接替代本地事务」 | 它们是业务层补偿，隔离性弱，仍需本地事务打底 |
| 5 | 🔧 3.2 缺 Raft/Paxos 支撑的协调者 | 现代全局事务用共识保证协调者高可用，本书未展开 |
| 6 | 🔧 3.4 缺 NewSQL 可串行化路线 | TiDB/CockroachDB/OB 已把跨分片 ACID 做成默认能力 |
| 7 | 🔧 3.4.2 缺事务消息标准化 | Kafka/RocketMQ 事务消息让可靠事件队列更稳 |
| 8 | 🔧 缺 Jepsen 一致性验证视角 | 「声明一致」需可证伪测试，是选型硬指标 |
