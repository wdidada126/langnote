# 第 1 章　服务架构演进史

> 原书第 1 章是全书的「史观」：它沿着软件架构的演进，把原始分布式、单体、SOA、微服务、后微服务（云原生）、无服务
> 六种风格串成一条线，每一种都先讲它**解决了什么**，再讲它**带来了什么新缺陷**。
> 这一章不直接给技术细节，而是为后面所有章节（尤其是第 16 章方法论）铺垫「为什么是这样」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 原始分布式时代 | UNIX 出现后的「计算机联网」探索，DCE/RPC、CORBA 等分布式对象努力 | 分布式不是新概念，但早期受限于网络与硬件，愿景大于现实 |
| 1.2 单体系统时代 | 单进程、分层架构（表现/领域/数据），以 J2EE/.NET 为代表 | 简单、易部署、易调试；但耦合随规模增长而恶化 |
| 1.3 SOA 时代 | 以服务为单元、ESB 总线集成，理论成功、工程实践失败居多 | 方向对（解耦），但中心化 ESB 成了新瓶颈与单点 |
| 1.4 微服务时代 | 小服务、独立部署、轻量通信、去中心化治理 | 解耦彻底、独立伸缩；代价是分布式固有的复杂度被推到运维与一致性 |
| 1.5 后微服务时代 | 容器 + 编排（K8s）把服务治理下沉到基础设施 | 从「应用自己解决」转向「基础设施屏蔽」，云原生起点 |
| 1.6 无服务时代 | FaaS/Serverless，算力按请求计费、无常住进程 | 运维负担最低；但冷启动、有状态、长任务受限 |

## 核心精讲

（以下为教学性梳理，伪代码/示意均**教学示意，不参与构建**。）

### 1.2 单体：被误解的「反面教材」

- 单体（Monolith）**不等于**「错误架构」。在团队小、业务简单时，单体在开发、测试、部署、排障上的综合成本最低。
- 单体的真正天花板是**组织与代码规模的耦合**：当模块间依赖图变成「改一处动全身」，才需要拆分。
- 现代看法（2026）：「模块化单体（Modular Monolith）」重新被提倡——先用清晰模块边界，再按需拆分。

### 1.3 SOA 的成败

```text
# 教学示意，不参与构建：SOA 与微服务的核心差异
SOA:
    集成方式 = 企业服务总线 ESB（中心化、重量级、常带消息转换/编排）
    治理     = 统一标准（WS-*、UDDI、BPEL）
    结果     = 总线成为单点 + 改造成本高 -> 多数项目沦为「换个包装的单体」

Microservices:
    集成方式 = 轻量协议（HTTP/REST、gRPC、消息队列），去中心化
    治理     = 各服务自选技术栈、独立数据库（Database per Service）
    结果     = 拆解彻底，但一致性/运维复杂度上移
```

### 1.4 微服务：把复杂度「搬」而不是「消」

- 微服务没有消灭分布式问题，只是把它从「进程内方法调用」变成「跨网络服务调用」，
  于是第 2 章（远程调用）、第 3 章（分布式事务）、第 7–10 章（治理/可观测）全部被逼出来。
- 关键反直觉：**微服务首要收益是组织层面的（康威定律），而非技术性能**。

### 1.5 后微服务：基础设施吞掉治理

- 「后微服务」指以 Kubernetes 为代表的、把服务发现/负载均衡/伸缩/容错下沉到平台的做法。
- 书里用「跨越软件与硬件之间的界限」概括：以前应用层做的，现在由 Sidecar / 控制平面代劳。

### 1.6 无服务：不是「没有服务器」

- Serverless = 没有**常住**服务器、按调用计费、弹性到零。
- 本质是「算力服务化」，代价是受限运行时（时长、内存、无本地状态）、冷启动、调试困难。

## 版本演进

- **本书无第二版**；本节写 2021 年口径 → 2026 年视角的变化。
- **模块化单体回归**：2021 年业界已开始反思「微服务至上」，2023–2026 年「先单体后微服务」成为主流建议（如 Prime Video 把微服务回退为单体处理视频流），本书第 16 章的「粒度」讨论需补这一现实案例。
- **平台工程（Platform Engineering）**：后微服务之后，「内部开发者平台（IDP）」成为把 K8s 复杂度封装起来的新一层，本书第 15/16 章未及。
- **Serverless 容器化**：Fargate、Cloud Run、Knative 把「无服务」与「容器」缝合，本书 1.6 写于 Knative 早期，需补 2026 形态。
- **AI-Native 架构**：2023 年后推理/训练负载带来新架构范式（如分离式推理、向量检索），超出本书视野。

## 近年研究与工业界开源实践（2015–2026）

- **微服务框架（本章 1.4 的工程落地）**：
  - `apache/dubbo`（41579★，2026-09-27 实测）是国内最主流的 Java 微服务 RPC 框架；
  - `spring-cloud/spring-cloud-netflix`（4967★）与 `netflix/eureka`（12746★）是 Spring Cloud 微服务治理体系（注册/发现/熔断）的代表，Eureka 已进入维护态；
  - `grpc/grpc`（45341★）是跨语言高性能 RPC，是「后微服务」通信层的事实选项之一。
- **云原生底座（本章 1.5）**：`kubernetes/kubernetes`（128015★）把单体/微服务的部署运维标准化，是后微服务时代的核心平台；`dapr/dapr`（26117★）代表「多运行时」思路（见第 7 章补丁）。
- **无服务（本章 1.6）**：Knative（knative/serving，未单独实测，star 未核验）是 K8s 上的 Serverless 层；AWS Lambda 为商业代表。
- **反思性实践**：Prime Video 2023 年公开将部分微服务回退为单体以降成本，是「微服务不是银弹」的工业界佐证，本书 2021 年尚未有此案例。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「单体是坏架构」 | 单体在多数早期阶段综合成本最低；「先单体、后微服务」是更稳妥路径 |
| 2 | 「SOA 就是失败」 | SOA 的「服务化解耦」方向正确，失败多在中心化 ESB 工程实现，而非思想 |
| 3 | 「微服务让系统更简单」 | 微服务把复杂度从「代码内」搬到「网络与运维」，总量不减反增 |
| 4 | 「Serverless 没有服务器」 | 只是没有常住/用户自管的服务器，底层仍是服务器，且有运行时约束 |
| 5 | 🔧 1.4 缺少「模块化单体」回潮视角 | 2023–2026 年业界反思过度拆分，模块化单体与「合理粒度」被重新强调，第 16 章亦需补 |
| 6 | 🔧 1.5 缺平台工程/IDP 一层 | 后微服务之后，内部开发者平台成为封装 K8s 复杂度的新层，本书未及 |
| 7 | 🔧 1.6 无服务形态已演进 | Serverless 容器（Fargate/Cloud Run/Knative）与 AI 推理负载是新现实 |
| 8 | 🔧 缺 AI-Native 架构视角 | 2023 后推理/训练负载带来新范式，超出 2021 视野，第 16 章方法论应补 |
