# 第 6 章　分布式共识

> 原书第 6 章是「分布式的基石」第一块，也是最重要的那块：当多个节点对「某件事该听谁的」达不成一致时，
> 系统就不可能可靠。本章讲 Paxos、Multi Paxos、Gossip 三类协议——前两者追求**强一致决策**，
> 后者追求**最终一致传播**。它们是第 7–10 章服务治理与第 3 章分布式事务的底层保证。

## 核心精讲

（以下为教学性梳理，伪代码均**教学示意，不参与构建**。）

### 6.1.2 Paxos 基本流程（单值决议）

```text
# 教学示意，不参与构建
角色: Proposer(提议者) / Acceptor(接受者) / Learner(学习者)
阶段一 Prepare:
    Proposer 发 Prepare(n)        n 为递增提案号
    Acceptor 若 n > 已见最大号, 回 Promise(承诺不再接受 <n 的提案, 并附已接受的最高号值)
阶段二 Accept:
    Proposer 收多数派 Promise 后, 发 Accept(n, value)   (value 取 Promise 中号最大的已接受值, 无则自己定)
    Acceptor 若 n 仍≥已承诺号, 接受并回 Ack
学习者: 某值被多数派接受 -> 该值定案, 广播给 Learner
```

- **关键不变量**：一旦某值被选定，后续更高号的提案都必须携带该值——这保证了安全性。

### 6.2 Multi Paxos：从「选值」到「选主 + 追日志」

- 单轮 Paxos 只定一个值；连续决议时，先通过一轮选出**稳定 Leader**，此后 Leader 直接连续发 Accept，
  把两阶段压成一阶段，性能大增。**这就是 Raft/etcd/ZooKeeper 类系统的内在结构**。
- 注意：本书称 Multi Paxos，工业界同构实现常叫 Raft（更易理解），详见 🔧 补丁。

### 6.3 Gossip：另一种「共识」

- Gossip 不追求所有节点瞬时一致，而是让消息像传染病一样周期扩散，最终全网一致。
- 优点：无中心、天然容错、可扩展；缺点：有传播延迟、不保证强一致——适合**成员管理、状态传播**（如 Consul 的 Serf）。

## 版本演进

- **本书无第二版**；本节写 2021 年口径 → 2026 年视角的变化。
- **Raft 事实标准的确立**：本书 6.1–6.2 只讲 Paxos/Multi Paxos，而 Raft（Ongaro & Ousterhout, ATC 2014）因其「可理解性」已成为
  工业界默认（etcd、Consul、TiKV、CockroachDB 皆用）。读本章务必配 [../深入理解分布式共识算法/00-总览与阅读地图.md](../深入理解分布式共识算法/00-总览与阅读地图.md) 的 Raft 推导。
- **共识即服务（Consensus-as-a-Service）**：etcd/Consul/ZooKeeper 把共识封装成「一致 KV + 锁 + 选举」，是本书 6.2 思路的产品化。
- **EPaxos / Flexible Paxos**：对 Multi Paxos 领导瓶颈的改进（乱序提交、无主冲突处理），2026 仍在研究与部分落地。
- **共识与硬件**：RDMA、NVMe 降低共识延迟；RAFT 在异构网络下的优化（如 TiKV 的 PreVote）是持续工程议题。
- **区块链共识**：PoW/PoS 是另类「拜占庭容错共识」，超出本书非拜占庭假设，可对比阅读。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Paxos 就是选主算法」 | Paxos 本质是「对单值达成共识」；选主/日志复制是上层构造（常被叫 Multi Paxos/Raft） |
| 2 | 「共识=强一致」 | Gossip 这类是最终一致传播，不算强一致共识；二者要解决不同问题 |
| 3 | 「多数派接受就绝对安全」 | 需 quorum 交叠 + 提案号单调才能保安全，单看「过半」会误用 |
| 4 | 「FLP 说共识不可能」 | 是说**纯异步无随机/超时**下不可能；加超时/部分同步即可（现实系统都这么做） |
| 5 | 🔧 6.1–6.2 完全没有 Raft | Raft(2014) 已是工业事实标准，本书只给 Paxos 轮廓，必须配 Raft 材料 |
| 6 | 🔧 缺 EPaxos/Flexible Paxos 等改进 | 无主/乱序共识在降低领导瓶颈上已有进展，2026 视角应提及 |
| 7 | 🔧 缺共识与硬件加速(RDMA/NVMe) | 低延迟共识的工程现实已变化 |
| 8 | 🔧 缺区块链类拜占庭共识对照 | PoW/PoS 是 BFT 路线，可对比本书的非拜占庭假设 |
