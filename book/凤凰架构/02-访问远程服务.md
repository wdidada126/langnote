# 第 2 章　访问远程服务

> 原书第 2 章进入「架构师的视角」第一部分：分布式系统之所以是分布式，第一道坎就是**让程序像调本地方法一样调远程方法**，
> 而这件事比想象中难——网络会失败、会变慢、会乱序。本章拆成「远程服务调用」与「REST 设计风格」两节，
> 本质是在回答：我们究竟该用**方法（RPC）**还是**资源（REST）**来组织远程交互。

| 节 | 内容 | 结论 |
| --- | --- | --- |

| 2.1.1 进程间通信 | 管道/消息队列/套接字/信号等；RPC 多基于套接字 + 序列化 | 选择取决于性能与解耦需求 |
| 2.1.2 通信的成本 | 网络延迟、序列化/反序列化开销、异常语义 | 一次远程调用比本地方法慢几个数量级，必须量化 |
| 2.1.3 三个基本问题 | ① 如何找到远端（寻址）② 用什么传输/编码 ③ 以方法还是资源表达 | 后世所有 RPC/REST 框架都在答这三问 |

## 核心精讲

（以下为教学性梳理，代码/伪代码均**教学示意，不参与构建**。）

### 2.1.3 三个基本问题（本章枢纽）

```text
# 教学示意，不参与构建
Q1 位置(寻址):  服务名 -> IP:Port  (静态配置 / 注册中心 / DNS)
Q2 通信(传输):  传输协议(TCP/gRPC/HTTP) + 编码(二进制 protobuf / 文本 JSON)
Q3 表达(语义):  方法导向(RPC: doSomething(req))  vs  资源导向(REST: POST /orders)
```

- **Q3 是 RPC 与 REST 的根本分野**：RPC 暴露「动作/动词」，REST 暴露「资源/名词 + 标准动词（GET/POST…）」。

### 2.1.2 通信的成本（为什么不能无脑远程调用）

- 本地方法调用：纳秒级、不会失败（除 OOM）、返回即完成。
- 远程调用：毫秒级、可能超时/丢包/重复、需序列化。一处「for 循环里调 RPC」就可能把延迟放大千倍。
- 推论：**尽量把计算推到数据附近**，或批量调用，避免「聊天式（chatty）」交互。

### 2.1.4 / 2.1.5 统一 RPC 与它的分裂

- 统一 RPC 一脉（CORBA→RMI→Web Service→gRPC）的梦想是「位置透明」，但 Waldo 等人在 1994 年已警告：
  **本地与远程调用的失败模型根本不同**，强行统一只会掩盖失败、酿成 bug。
- 分裂点：当调用跨越组织边界、需要长期演化、要被浏览器/CDN 缓存时，REST 的资源模型更稳；
  当调用在同构内部服务间、追求性能与强类型契约时，RPC/gRPC 更高效。

### 2.2 REST 的约束（RMM 之外的真正要点）

- 六大架构约束：客户端-服务器、无状态、可缓存、统一接口、分层系统、按需代码（可选）。
- RMM（Richardson 成熟度模型）只是「接口像不像 REST」的粗略量尺，**真正重要的是无状态 + 统一接口**，而非 HATOAS 做到第几级。

## 版本演进

- **本书无第二版**；本节写 2021 年口径 → 2026 年视角的变化。
- **gRPC 已成内部 RPC 主流**：本书 2.1.4 列举的 CORBA/Remoting 基本退出历史舞台，`grpc/grpc`（45341★）与 Protocol Buffers 成为跨语言 RPC 事实标准。
- **GraphQL / gRPC-Web 补了 REST 的空白**：前端聚合查询（GraphQL）、浏览器直连（gRPC-Web）是 2021 后常见新选择，本书未见。
- **Service Mesh 接管 RPC 横切关注点**：重试/超时/熔断/追踪从 SDK 下沉到 Sidecar（见第 15 章），RPC 框架职责变窄。
- **WASM 插件化网关（Proxy-Wasm）**让网关在 RPC/REST 边界做扩展更轻量（🔧 见第 15 章）。

## 近年研究与工业界开源实践（2015–2026）

- **RPC 框架**：`grpc/grpc`（45341★，2026-09-27 实测）是跨语言高性能 RPC 事实标准；`apache/dubbo`（41579★）是国内主流 Java RPC/微服务框架；
  `apache/dubbo-go`（4965★）是其 Go 实现。
- **服务交互抽象**：`spring-cloud/spring-cloud-netflix`（4967★）与 `netflix/eureka`（12746★）是 Java 生态远程调用 + 注册发现的经典组合（Eureka 已转维护态）。
- **边缘/传输**：`nginx/nginx`（31736★）作为反向代理承载 REST/gRPC 网关；`envoyproxy/envoy`（28995★）是云原生数据平面（见第 15 章）。
- **协议演进**：gRPC-Web、gRPC-HTTP/2、Connect（RPC over HTTP/JSON）等让浏览器/异构系统接入 RPC 更容易，本书 2.1 未展开。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「RPC 让远程调用和本地一样简单」 | 失败模型本质不同（见 Waldo 1994）；必须显式处理超时/重试/幂等 |
| 2 | 「REST 就是 HTTP + JSON」 | REST 是架构风格（无状态/统一接口/可缓存），HTTP 只是常用载体，JSON 非必须 |
| 3 | 「RMM 三级才算 RESTful」 | 成熟度模型是参考，HATOAS 在实践中很少做到，无状态与统一接口才是核心 |
| 4 | 「选 RPC 还是 REST 二选一」 | 内部高性能用 RPC，开放 API 用 REST，二者长期共存而非互斥 |
| 5 | 🔧 2.1.4 的 CORBA/Remoting 已淘汰 | 应更新为 gRPC/Protobuf 为主流，并提及其与 Service Mesh 的关系 |
| 6 | 🔧 缺 GraphQL / gRPC-Web 选项 | 前端聚合与浏览器直连是 2021 后重要交互形态 |
| 7 | 🔧 缺 WASM 网关扩展（Proxy-Wasm） | 网关在 RPC/REST 边界的轻量扩展能力已成熟（见第 15 章补丁） |
