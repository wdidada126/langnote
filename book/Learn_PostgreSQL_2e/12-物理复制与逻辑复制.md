## 1. 物理复制：WAL 流的搬运工（Ch17 ⚠️+✅）

- 原理：主库流式发送 WAL，备库**持续回放** ⇒ 字节级镜像+只读服务（warm/hot standby ✅ https://www.postgresql.org/docs/current/warm-standby.html ）；备库恢复中可查=HOT STANDBY 默认形态 ⚠️。
- 建立五步（书流程 ⚠️+✅ 同页）：wal_level=replica → 复制用户+REPLICATION 权限 → pg_hba `replication` 行 → `pg_basebackup -R` 克隆基线 → 备库 `standby.signal` 起服务。
- 三种送达语义（✅ 三镜像逐一对位）：
  - **async**：默认，`synchronous_commit=on` 也可能丢已确认事务（故障切换 RPO>0）；
  - **synchronous**（synchoronous 容器 ✅）：`synchronous_commit = on/local/remote_write/remote_apply` 四档耐久-延迟旋钮 ⚠️+✅ warm-standby 同步复制节；
  - **delayed**（delayed 容器 ✅）：`recovery_min_apply_delay`——人为时差防误删/勒索，"后悔药备库"。
- 复制槽：`CREATE PHYSICAL REPLICATION SLOT` 给 WAL 保留兜底；**失活槽=磁盘炸弹**，盯 `pg_replication_slots.retention` ⚠️+✅（wal-internals/monitoring 族 ✅）。
- 观测双侧账本：主库 `pg_stat_replication`（sent/write/flush/replay 位点）+ 备库 `pg_stat_wal_receiver` ✅ https://www.postgresql.org/docs/current/monitoring-stats.html 。
- 拓扑与仲裁（⚠️+✅ https://www.postgresql.org/docs/current/high-availability.html ）：级联/同步候选/quorum（PG 10+）；工具脑：Patroni ✅（https://api.github.com/repos/patroni/patroni 200 实抓）、repmgr ⚠️。

## 2. 逻辑复制：发布与订阅（Ch18 ⚠️+✅）

- 与物理的本质差：WAL **行解码**后按 PUBLICATION→SUBSCRIPTION 路由——目标可写、可选表、跨版本、双向可做（✅ https://www.postgresql.org/docs/current/logical-replication.html ）。
- 建立骨架 ✅ https://www.postgresql.org/docs/current/sql-createpublication.html ：

```sql
-- 发布端
CREATE PUBLICATION pub_posts FOR TABLE posts;
-- 订阅端（wal_level=logical 先决）
CREATE SUBSCRIPTION sub1 CONNECTION 'host=... dbname=forumdb'
    PUBLICATION pub_posts;
```

- 限制清单（书与文档同调 ⚠️+✅ logical-replication 各节）：
  - **序列/DDL/大对象不同步**——迁移收尾要手工对齐 ⚠️；
  - 初始快照 `copy_data=true`：搬运但**跨多表非全局一致快照**（分表时点差 ⚠️）；
  - 冲突不自动解决（改两边同键→报错停摆），`origin` 防环、双向需纪律 ⚠️；
  - 标识键要求：UPDATE/DELETE 需全键唯一约束（`REPLICA IDENTITY FULL` 代价大 ⚠️+✅）。
- docker 三场景读法（✅ 目录名）：`logical_clear`=冷建全流程；`logical_ready`=已同步+增量观测（`pg_stat_subscription` ✅ monitoring 族）；`physical_logical`=**物理备库上开逻辑解码**给下游供流——作者用容器组合教混合拓扑。
- 升级神器定位 ⚠️：逻辑复制做跨大版本"零停机迁移+回滚通道"是 2020s 社区标准打法（对位 [../PostgreSQL_16_Administration_Cookbook/07-复制高可用与升级.md](../PostgreSQL_16_Administration_Cookbook/07-复制高可用与升级.md)）。

## 3. 🔧 类比实测：无服务器引擎如何"想象复制"（duck6.out / sq1.out 🔧，非 PostgreSQL 行为）

- 两引擎都**没有**服务端复制协议：
  - SQLite 的读扩展=文件复制/rsync（⚠️ 通例）；本机可验证的是单写者约束——WAL 下双连接读并发、写互斥（🔧 `wal_checkpoint` busy 位实验，sq1.out：返回 `0|0|0`）；
  - DuckDB 同文件多写连接冲突 ⚠️ 通例（本次未做双进程实验，诚实登记）。
- "反向直连"玩具 ✅ 实测一半：DuckDB `postgres_scanner` 扩展本机 `installed=True, loaded=False`（duck6.out 🔧）——`ATTACH ... (TYPE postgres)` 可把**活 PG 当外表读**（省去复制）；因本机无 PG 服务端，端到端未通 ⚠️，登记为缺口。
- 概念对照 ⚠️：PG 物理复制=重放日志到副本；逻辑复制=发布变更事件流；嵌入式=没有第三态，只能"文件级快照搬运"。DuckDB 生态把该职责外包给对象存储上的 Parquet（对位 [../DuckDB_in_Action/00-总览与阅读地图.md](../DuckDB_in_Action/00-总览与阅读地图.md) 湖仓章 ⚠️）。

## 5. 本章自测（重构版；题目自拟 ⚠️）

1. **问**：备库为何不能写？**答**：物理复制是日志重放，回放流与本地写流无法合并——只读（hot standby）。
2. **问**：remote_write 与 remote_apply 的语义差？**答**：到达对方 OS 缓存 vs 已应用到可见——RPO/读己所写两档。
3. **问**：逻辑订阅的表为什么删不掉 PK？**答**：UPDATE/DELETE 定位依赖标识键 ⚠️+✅。
4. **问**：延迟备库能防什么？**答**：误 DELETE/UPDATE 与部分勒索（时间窗内回放可停）。
5. **问**：pg_basebackup -R 干了什么？**答**：克隆基线+自动写好连接配置（primary_conninfo/信号文件）⚠️。

## 核心概念速览（中英对照）

1. **流复制** — streaming replication：WAL 实时搬运。
2. **热备** — hot standby：边回放边供读。
3. **synchronous_commit 四档** — 耐久-延迟旋钮 ⚠️+✅。
4. **延迟备库** — recovery_min_apply_delay ✅（容器实证）。
5. **复制槽** — replication slot：WAL 保留承诺+失活风险。
6. **quorum 同步** — 仲裁提交：任意 N 备确认 ⚠️+✅。
7. **发布/订阅** — publication/subscription：逻辑复制双端。
8. **REPLICA IDENTITY** — 逻辑解码的行定位键。
9. **copy_data** — 订阅初始化快照搬运。
10. **origin** — 复制原点：防环标记。
11. **pg_stat_replication / pg_stat_subscription** — 两本观测账 ✅。
12. **Patroni** — HA 编排事实标准 ✅（API 200）。
13. **混合拓扑** — 物理备库供逻辑流 ✅（physical_logical 容器）。
