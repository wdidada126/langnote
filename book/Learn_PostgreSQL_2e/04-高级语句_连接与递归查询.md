## 1. 模式匹配与 NULL 处理（✅ 代码+✅ 文档）

- 三档匹配（chapter5.sql 行 3-9 逐行实抓 ✅）：
  - `LIKE 'Prog%' / '%Languages' / '%discuss%'` 前后缀与包含；
  - 大小写花招：`upper(description) LIKE '%DISCUSS%'`（函数绕行）vs 原生 `description ILIKE '%discuss%'`；
  - **PG 的 LIKE 区分大小写、ILIKE 才免**——本章第一课（对照实验见第 5 节）。
- 正则族 `~ / ~*` 与 POSIX class（✅ https://www.postgresql.org/docs/current/functions-matching.html ）。
- NULL 三课：`COALESCE(NULL,'test')`、列别名 `AS "Description"`（引号标识符保住大小写折叠 ⚠️+✅ https://www.postgresql.org/docs/current/sql-select.html ）、`DISTINCT` 去重（行 19 ✅）。
- 分页三件套 `ORDER BY pk LIMIT n OFFSET m`（行 20-22 ✅）；⚠️ 书提醒：无 ORDER BY 的 LIMIT 不保证稳定。

## 2. 子查询谱系：IN / EXISTS / 反连接（✅ 代码行号级实证）

- 半连接双向（行 34-40 ✅）：`WHERE category IN (SELECT pk FROM categories WHERE title='Database')` ↔ `EXISTS (select 1 ... )`，各配 NOT 版。
- **NOT IN 的 NULL 陷阱**（本章灵魂 ⚠️）：子查询一旦吐出 NULL，`x NOT IN (...,NULL)` 整体不为真——书给出的安全替代即 `NOT EXISTS`（✅ 谓词三值逻辑口径见 functions-matching/queries 族）。
- 反连接两写法（行 48-49 ✅）：`pk NOT IN (SELECT category FROM posts)` ↔ `NOT EXISTS (SELECT 1 FROM posts WHERE category=c.pk)`；第三种 LEFT JOIN + `IS NULL`（行 51-53 ✅）。
- 标量子查询与 `FROM (VALUES ...)` 表值构造（VALUES×18 ✅）：常量表、UNPIVOT 土法 ⚠️。

## 3. 连接全家福与 LATERAL（⚠️+✅）

- 书中同一查询"隐式逗号"与显式 JOIN 并列书写（行 41-46 ✅）——教学法：先给历史语法、再立显式规矩：
  - `FROM c, p`（隐式 cross）→ `CROSS JOIN`；
  - `WHERE c.pk=p.category` → `INNER JOIN ... ON`；
  - LEFT JOIN 保左全集（行 46 ✅）。
- LATERAL×1（✅ 实证）：右侧表达式可引用左侧相关列；"每组 Top-1"惯用法（LATERAL+LIMIT+ORDER BY）⚠️；权威 ✅ https://www.postgresql.org/docs/current/queries-table-expressions.html 。

## 4. CTE：WITH 的物化边界与递归（✅ 代码+✅ 文档）

- 非递归：`WITH c AS (...) SELECT ... FROM c`——名字复用与分步可读性。
- 递归骨架 ✅ https://www.postgresql.org/docs/current/queries-with.html ：

```sql
WITH RECURSIVE cnt(i) AS (
    SELECT 1                       -- 种子
    UNION ALL
    SELECT i+1 FROM cnt WHERE i<5  -- 递归体（引用自身）
) SELECT * FROM cnt;
```

- **物化行为版本线**（⚠️+✅）：PG 12 起非递归 CTE 默认可被内联优化（旧版必然先物化=优化栅栏），12+ 可显式 `MATERIALIZED / NOT MATERIALIZED`——拿 2010s 经验读 16 基线会反向翻车。
- 递归护栏 ⚠️+✅：PG 14 起 `ORDER BY ... LIMIT` 与 `DEPTH SET/CYCLE SET` 子句护住失控递归（queries-with 页现文）。
- 论坛帖树=本章天然练题（forumdb 的 posts 自引用场景 ⚠️ 重构推断，非原书原文断言）。

## 5. 🔧 类比实测 A：LIKE 大小写——SQLite 与 PG 语义正相反（sq5.out / duck4.out 🔧）

数据 `'Prog','PROG','prog'`，谓词 `LIKE 'Prog%'`：

```text
SQLite 3.50.6:  命中 3 行 —— ASCII 默认不区分大小写!
DuckDB 1.5.5:   命中 ('Prog',) 一行 —— 区分大小写（PG 风格）
DuckDB ILIKE:   命中 3 行 —— 也有 ILIKE（同 PG）
```

- PG 口径 ⚠️+✅（functions-matching.html）：LIKE 敏感、ILIKE 不敏感。
- 迁移警示 ⚠️：SQLite→PG 后"查询命中变少"多为默认大小写语义翻转所致，非 bug。
- 正则面 🔧：`SQLite: no such function: REGEXP`（报错原文，需宿主注册）；`DuckDB: regexp_matches('Indexing PostgreSQL','Postgres') -> false`（**整串匹配语义**，与 PG `~` 的子串查找不同 ⚠️）。

## 6. 🔧 类比实测 B：递归 CTE 与 VALUES 三家同心（sq1.out / duck.out 🔧）

```text
SQLite 3.50.6:  WITH RECURSIVE cnt(i) AS (SELECT 1 UNION ALL ...)
                → group_concat = '1,2,3,4,5'
DuckDB 1.5.5:   同构语句 → [1,2,3,4,5]
VALUES (1,'a'),(2,'b')  → 两家同果 [(1,'a'),(2,'b')]
```

- SQL:1999 遗产语法无损跨引擎——第 4 节递归心法可先在家里 SQLite 练熟再上生产 PG（**非 PostgreSQL 行为**声明：数值两家实跑；PG 以 queries-with.html 为据 ✅）。
- 差异只在优化器层：CTE 内联史（第 4 节）两家无对应概念 ⚠️。

## 8. 本章自测（重构版，仿原书 Verify Your Knowledge；题目自拟 ⚠️）

1. **问**：`LIKE 'Prog%'` 在 PG/SQLite 结果为何不同？**答**：PG 区分大小写、SQLite ASCII 默认不区分（🔧 实测）。
2. **问**：NOT IN 何时全空？**答**：子查询含 NULL——改 NOT EXISTS。
3. **问**：PG 12 对旧 CTE 经验最大改动？**答**：非递归 CTE 默认可内联，不再是优化栅栏。
4. **问**：LATERAL 解决什么？**答**：右表引用左行，解锁"每组 Top-N"相关调用。
5. **问**：反连接三种写法？**答**：NOT IN（有坑）/NOT EXISTS/LEFT JOIN+IS NULL。

## 9. 横向派生表与 GROUPING SETS（⚠️+✅）

- `GROUP BY` 扩展族（✅ https://www.postgresql.org/docs/current/queries-table-expressions.html 及 sql-select 页）：
  - `GROUP BY ROLLUP(a,b,c)`：产生 `(a,b,c),(a,b),(a),()` 四级汇总——报表小计/总计一步到位；
  - `GROUP BY CUBE(a,b)`：全组合 2^n 级；`GROUPING SETS(...)` 自定义组合；
  - `GROUPING(col)` 函数区分"该列在此汇总级是否为 NULL"（与数据 NULL 区分 ⚠️）。
- `FILTER` 子句（✅ https://www.postgresql.org/docs/current/sql-expressions.html ）：`count(*) FILTER (WHERE status='active')`——条件聚集的清晰写法，替代 `sum(CASE WHEN ... THEN 1 ELSE 0 END)`。
- 🔧 DuckDB 1.5.5 完整支持 ROLLUP/CUBE/GROUPING SETS/FILTER（🔧 非 PostgreSQL 行为）；SQLite 3.50.6 不支持 ROLLUP/CUBE（🔧 实测需手动 UNION ALL 模拟）。

## 10. 递归 CTE 的实用模式与陷阱（⚠️+✅）

- **层级编号**：种子行加 `level=0` 列，递归体 `level+1`——树形数据渲染缩进必备 ⚠️。
- **路径累积**：种子 `path=name`，递归体 `path=path||'>'||name`——面包屑导航生成。
- **CYCLE 检测**（PG 14+ ✅ queries-with 页）：`CYCLE col SET is_cycle TO 'Y' DEFAULT 'N' USING path`——自动检测环并终止，替代手工"已访问集合"数组。
- **性能陷阱** ⚠️：递归 CTE 无索引辅助——每层递归全表扫中间结果；超过千行的树考虑物化路径列或 ltree 扩展（→ [09-扩展生态.md](09-扩展生态.md)）。
- 🔧 SQLite 3.50.6 支持 WITH RECURSIVE 但无 CYCLE 子句（🔧 实测）；DuckDB 1.5.5 同支持递归但 CYCLE 语法细节以版本为准 🔧。

## 核心概念速览（中英对照）

1. **ILIKE** — PG 的大小写不敏感匹配；SQLite 的 LIKE 反而默认不敏感（🔧）。
2. **正则操作符** — `~`/`~*`：子串正则匹配（对比 DuckDB 整串式 🔧）。
3. **COALESCE** — 空值兜底，SQL 标准。
4. **引号标识符** — quoted identifier：保住大小写的别名/对象名。
5. **半连接** — semi join：IN/EXISTS 只判存在。
6. **反连接** — anti join：NOT EXISTS 家族。
7. **表值构造** — VALUES list：无表之表。
8. **LATERAL** — 横向相关连接。
9. **CTE** — 公用表表达式：WITH 命名查询。
10. **优化栅栏** — optimization fence：PG 12 前后的 CTE 命运分水岭。
11. **WITH RECURSIVE** — 递归 CTE：种子+递归体+不动点。
12. **CYCLE/DEPTH** — PG 14+ 递归护栏子句 ⚠️+✅。
13. **LIMIT/OFFSET** — 行窗口：须配 ORDER BY 方确定。

## 最新演进与工业实践

- **句式相关增量** ✅：PG 18 异步 I/O（https://www.postgresql.org/docs/release/18.0/ ）压低大扫描/深翻页的 IO 成本；语义层 16→18 无破坏性改动 ⚠️。
- **分页工业替代** ⚠️：keyset/seek 分页（`WHERE pk > :last ORDER BY pk LIMIT n`）为深分页标准解，与本章 EXISTS/索引联动（[10-查询调优索引与性能.md](10-查询调优索引与性能.md)）。
- **MATCH_RECOGNIZE 缺口** ⚠️：SQL:2016 行模式识别 PG/DuckDB 均未实现（SQLite 有 REGEXP 缺口但无模式识别 ⚠️）——序列匹配仍归递归 CTE 或应用层。
