# 02 · 用户与连接管理（原书第 3 章）

> 对应原书 Ch3 *Managing Users and Connections*（✅ 官方 README 章题）。
> 勘误义务（✅ README Errata）：p58 多处 `IF EXIST` 正字为 `IF EXISTS`——本文全按勘误后口径。
> 三态：✅ 取证 / ⚠️ 转述 / 🔧 本机 SQLite(3.45.3/3.50.6)、DuckDB 1.5.5 类比（**非 PostgreSQL 行为**）。

## 1. 角色即一切：users、roles 与继承

- PG 把"登录者"与"权限组"统一为 **role**：`CREATE ROLE ... LOGIN` 才是用户；`CREATE USER` 等价于带 LOGIN 的 ROLE（✅ https://www.postgresql.org/docs/current/sql-createrole.html 可达 200 已验）。
- `INHERIT / NOINHERIT` 决定成员是否自动继承被授角色的权限——本书强调这是排障高频坑 ⚠️。
- 组角色（group role）模式 ⚠️：建不可登录 role 当"权限袋"，`GRANT bag TO user` 挂接，应用侧只授袋。
- 本书的角色阵容（✅ 代码仓实证）：`setup/001-create-database-users.sh` 建 **luca/enrico**，`002-forum-database.sql` 建 **forum** 用户与 forumdb——后续属主/权限演示全部围绕这四人转。
- 删除防呆 ✅（README Errata 原例）：

```sql
forumdb=# DROP ROLE IF EXISTS this_role_does_not_exist;
```

- 角色级参数（⚠️+✅ https://www.postgresql.org/docs/current/config-setting.html ）：

```sql
forumdb=# ALTER ROLE luca SET statement_timeout = '30s';
```

## 2. 连接链路：客户端 → pg_hba → 服务器进程

一次连接的四步（⚠️ 书中心智模型 + ✅ 文档族）：

1. TCP/Unix socket 抵达 postmaster（`listen_addresses`/`port`，改后**需重启** ⚠️）；
2. 查 **pg_hba.conf**：按"地址+库+用户"逐行匹配，决定认证方法（trust / password / **scram-sha-256** / md5 / peer / ldap…）；
3. 认证通过（服务端或 PAM/LDAP/RADIUS 外置 ⚠️，✅ https://www.postgresql.org/docs/current/auth-ldap.html 族）；
4. fork 专用 backend 进程，进入库/角色会话。

客户端侧配套：

- 免密凭据文件 `~/.pgpass`（✅ https://www.postgresql.org/docs/current/libpq-pgpass.html ）；
- 连接串 URI/关键词两式、`sslmode` 传输加密 ⚠️+✅ libpq 族。

## 3. 会话治理三件套（本章实操高光）

- **看**：`SELECT pid, usename, application_name, state, query FROM pg_stat_activity;`（⚠️+✅ https://www.postgresql.org/docs/current/monitoring-stats.html ）。
- **缓**：`SELECT pg_cancel_backend(pid);`——取消当前语句不断连接 ⚠️。
- **踢**：`SELECT pg_terminate_backend(pid);`——README 提示符示例原文即为 `forumdb=# SELECT pg_terminate_backend( 987 );` ✅。
- 连接天花板 `max_connections` 与复制/备份会话抢配额——为 Ch15/17 埋线 ⚠️（对位 [12-物理复制与逻辑复制.md](12-物理复制与逻辑复制.md)）。
- 参数可在四粒度挂接（⚠️+✅ config-setting 页）：集群 / `ALTER DATABASE SET` / `ALTER ROLE SET` / 会话 `SET`；`ALTER ROLE ... IN DATABASE` 二维组合。

## 4. 🔧 类比实测 A：嵌入式引擎根本没有"认证"这层（对照组）

- **SQLite**：能打开 .db 文件者即全权——权限模型=**文件系统权限**；无 role、无 hba、无监听端口、无可查询的活动会话视图（其语法总面无认证语句族 ⚠️，官方语法索引 https://www.sqlite.org/lang.html 可对照；本机两构建亦无相关 PRAGMA）。
- **DuckDB 1.5.5（duck.out 系 🔧）**：

```text
> con.sql("SELECT current_user").fetchall()   -> [('duckdb',)]
```

有 SQL 兼容层外壳（current_user 存在），但无口令、无 hba、无 kill-backend 原语。

结论 ⚠️：Ch3 整章的存在理由是 **服务器进程模型**；嵌入式引擎把这些关切外包给了 OS/宿主程序。SQLite/DuckDB 用户转 PG 的第一道认知坎就是"连接是被治理的资源"（**非 PostgreSQL 行为**声明：前二为对照面）。

## 5. 🔧 类比实测 B：会话级参数的"最小模型"（Python sqlite3 3.45.3，py_fts.out 同批 🔧）

```python
>>> c1 = sqlite3.connect('sq1.db')
>>> c1.execute("PRAGMA busy_timeout=5000").fetchone()
(5000,)                       # 会话级参数生效
>>> c2 = sqlite3.connect('sq1.db')
>>> c2.execute("PRAGMA busy_timeout").fetchone()
(0,)                          # 新连接不继承 → 回到默认
```

DuckDB 🔧：`SET memory_limit='256MB'` 同样只影响本实例。
差异表 ⚠️：PG 参数可**持久挂到对象上**（角色/库维度，会话建立时自动应用），嵌入式只有进程/连接两层——这正是 Ch16 配置章（[11-日志备份与监控.md](11-日志备份与监控.md)）要收口的主题。

## 7. 本章自测（重构版，仿原书 Verify Your Knowledge；题目自拟 ⚠️）

1. **问**：`CREATE USER x;` 与 `CREATE ROLE x LOGIN;` 差别？**答**：等价（✅ sql-createrole）。
2. **问**：pg_hba 匹配规则？**答**：自上而下第一命中行决定方法，行序即策略 ⚠️。

## 8. 连接池与进程模型的工业推论（⚠️ 书外延伸+✅ 文档口径）

- PG 的 **process-per-connection** 模型（⚠️+✅ https://www.postgresql.org/docs/current/processes.html ）意味着每个活跃连接=一个 OS 进程（典型 5-20MB RSS）；`max_connections` 默认 100 不是性能上限而是内存闸 ⚠️。
- 连接池三件 ⚠️ 通例：
  - **PgBouncer**（✅ https://www.pgbouncer.org/ ）：transaction mode 最常用，多路复用千级并发到百级后端；
  - **pgcat**（Rust 实现，⚠️ 社区项目）：分片+读写分离附加层；
  - **Odyssey**（Postgres Professional，⚠️）：多线程池化。
- 池化与本章概念的交互 ⚠️：
  - `ALTER ROLE SET` 参数在**每次新建后端时**应用——池化复用连接时 SET 只生效一次，换池模式=换会话参数；
  - `pg_terminate_backend` 踢的是后端进程，池中间件需感知重连；
  - `LISTEN/NOTIFY` 跨事务通知在 transaction mode 下不可靠（连接归还后通知丢失）⚠️。
- 🔧 DuckDB 1.5.5 对照：单进程多线程，无连接池概念——`con1 = duckdb.connect(); con2 = duckdb.connect()` 各自独立但共享进程资源（🔧 非 PostgreSQL 行为）。
- 纪律 ⚠️：应用侧连接池（HikariCP 类）+ 数据库侧 PgBouncer 双层池化是 2020s 标配；`max_connections` 调到 1000+ 而不加池化是新手最常见的性能自杀。

## 9. pg_hba.conf 常见配置模式速查（⚠️ 书外整理+✅ 文档锚点）

典型行格式（✅ https://www.postgresql.org/docs/current/auth-pg-hba-conf.html ）：

```text
# TYPE  DATABASE  USER  ADDRESS       METHOD
hostssl all       all   10.0.0.0/8    scram-sha-256    # 内网 TLS+口令
host    all       all   0.0.0.0/0     scram-sha-256    # 全网（配合防火墙）
local   all       postgres              peer            # 本机超管免密
host    all       all   ::1/128       scram-sha-256    # IPv6 回环
```

- 匹配原则：**自上而下第一命中**——把宽泛拒绝行放窄放行行之后会静默吞掉连接 ⚠️。
- `hostssl` vs `host`：前者**强制** TLS，后者接受明文与加密——生产一律 `hostssl` ⚠️。
- `include` / `include_if_exists` / `include_dir` 指令（PG 16 ✅ auth-pg-hba-conf 页）：大集群把规则拆文件管理。
- 变更生效：`SELECT pg_reload_conf();`（sighup 级 ⚠️+✅ config-setting）——**不需重启**，但 `listen_addresses`/`port` 改仍需重启 ⚠️。

## 核心概念速览（中英对照）

1. **角色** — role：登录者与权限组的统一抽象。
2. **继承** — INHERIT/NOINHERIT：成员权限传导开关，排障第一检查点。
3. **组角色** — group role：不可登录的"权限袋"。
4. **pg_hba.conf** — 主机认证表：连接准入+方法路由，行序优先 ⚠️。
5. **SCRAM-SHA-256** — 现行默认口令法：md5 已弃用方向 ⚠️+✅。
6. **peer 认证** — Unix socket 同名放行。
7. **pg_stat_activity** — 活动会话视图：一切连接治理的起点。
8. **pg_terminate_backend** — 踢连接：README 示例原函数 ✅。
9. **listen_addresses** — 监听面：默认 localhost，改必重启 ⚠️。
10. **pg_reload_conf** — 热加载：hba 类变更免重启。
11. **.pgpass** — 客户端凭据文件（✅ libpq-pgpass）。
12. **ALTER ROLE SET** — 角色级参数固化。
13. **max_connections** — 会话配额：与复制/备份共享的天花板 ⚠️。

## 最新演进与工业实践

- **认证演进** ✅：md5 弃用、SCRAM 默认；**PG 18 引入 OAuth 认证**（✅ https://www.postgresql.org/docs/release/18.0/ ）——本书 16 基线无此选项，云身份联邦（AWS IAM auth、Supabase/Neon token 化 ⚠️ 通例）已是托管 PG 主流。
- **传输安全** ⚠️：托管平台默认强制 TLS；自建以 `hostssl` hba 行+证书轮转达标合规。
- **连接池是必选项不是可选项** ⚠️：process-per-connection ⇒ PgBouncer（transaction mode）/pgcat/Odyssey 分层；池化与 `ALTER ROLE SET`、advisory lock、`pg_terminate_backend` 的相互作用是面试与事故复盘常客。
- **口令治理**：核心至今无复杂度引擎 ⚠️，靠扩展或 pgbouncer+外部 vault；LDAP 文档 ✅ https://www.postgresql.org/docs/current/auth-ldap.html 。
