# 10 · 查询调优、索引与性能优化（原书第 13 章）

> 对应原书 Ch13 *Query Tuning, Indexes and Performance Optimization*（✅ 章题）。
> 实证 ✅：docker `chapter_13/init/090-configuration-autoexplain.sh`——本章配了 **auto_explain** 现场捕获环境（✅ https://www.postgresql.org/docs/current/auto-explain.html ）。
> 勘误义务（✅ README Errata）：p499 自测题 "EXPLAIN and EXPLAIN EXPLAIN" 应为 **EXPLAIN 与 EXPLAIN ANALYZE 之别**。

## 1. EXPLAIN：优化器的口供（⚠️+✅）

- 两分法：`EXPLAIN` 只出计划；`EXPLAIN ANALYZE` 真跑并给**估算 vs 实际**双列（勘误后口径 ✅）；`EXPLAIN (ANALYZE, BUFFERS)` 逐节点报 shared hit/read、temp read（✅ https://www.postgresql.org/docs/current/using-explain.html ）。
- 读数三部曲 ⚠️（书式方法论重构）：
  1. 扫描方式：Seq / Index / **Bitmap**（多索引位图合并+排序回表，PG 特色）/ Index Only；
  2. 连接策略：Nested Loop（小外表+索引内表）/ Hash Join（等值大集合）/ Merge Join（双有序）；
  3. 估算失真：`rows=1` 而 `actual rows=10k` ⇒ 统计过期或多列相关性（→ CREATE STATISTICS）。
- 告警灯清单 ⚠️+✅（using-explain 页要素）：`Sort Method: external merge  Disk: xxxkB`（work_mem 不足）、JIT 块、Parallel (Gather) 未生效、`Loop=` 乘积爆炸。
- 成本模型参数：`random_page_cost`（SSD 时代从 4.0 下调是社区惯例 ⚠️）、`effective_cache_size`（只影响选择率信心不吃内存 ⚠️）；连接数爆炸走 geqo ✅ https://www.postgresql.org/docs/current/geqo.html 。

## 2. 索引全家桶（⚠️+✅）

- 方法谱（✅ https://www.postgresql.org/docs/current/indexes-types.html ）：
  - **B-tree**：默认，等值+范围+排序通吃；
  - **Hash**：等值专才（PG 10 起 WAL 安全 ⚠️）；
  - **GiST**：平衡搜索树框架——几何/全文 tsvector/最近邻；
  - **SP-GiST**：非平衡空间（kd/ip4r 族）；
  - **GIN**：倒排多值（数组/JSONB/全文）——写放大换读加速 ⚠️；
  - **BRIN**：块级摘要，十亿行时序表的最便宜索引。
- 形态进阶：
  - 表达式索引 ✅ https://www.postgresql.org/docs/current/indexes-expressional.html （谓词函数列建键——IMMUTABLE 契约在 [06 号文件](06-服务端编程_PLPGSQL.md)）；
  - 部分索引（`WHERE` 圈热点 ⚠️+✅）；
  - 多列索引列序纪律：等值列在前、范围列在后 ✅ https://www.postgresql.org/docs/current/indexes-multicolumn.html ；
  - 覆盖索引 `INCLUDE`（PG 11+，index-only scan 免回表 ⚠️+✅）。
- 在线运维 ✅ https://www.postgresql.org/docs/current/sql-createindex.html ：`CONCURRENTLY` 两遍扫描+等旧事务，失败留 `INVALID` 索引须 `REINDEX`/drop 重来 ⚠️；B-tree 去重（PG 14+ ⚠️）。
- 统计补药：`CREATE STATISTICS (ndistinct, dependencies)` 多列相关性建模（PG 10+ ⚠️+✅ https://www.postgresql.org/docs/current/sql-createstatistics.html ）；`ALTER COLUMN SET STATISTICS 1000` 提采样 ⚠️。

## 3. 慢查询工作流（本章实操骨架 ⚠️+✅）

1. 广度：`pg_stat_statements` 聚合指纹定 Top-N（✅ https://www.postgresql.org/docs/current/pgstatstatements.html ）；
2. 现场：auto_explain 记录超阈语句真实计划（✅ 本章 docker 脚本实证）；
3. 供料：`log_min_duration_statement` 落 csvlog → pgBadger 出报表（→ [11-日志备份与监控.md](11-日志备份与监控.md) ✅ runtime-config-logging ）；
4. 取证：`enable_seqscan=off` 等开关只作探针，**禁入生产配置** ⚠️；
5. 反向：`pg_stat_user_indexes.idx_scan≈0` 揪闲置索引再删（✅ https://www.postgresql.org/docs/current/monitoring-stats.html ）。

## 4. 🔧 类比实测：计划输出的三种方言（sq1.out / duck2.out 🔧，非 PostgreSQL 行为）

```text
SQLite 3.50.6:
  EXPLAIN QUERY PLAN SELECT * FROM j WHERE json_extract(doc,'$.stars')>2;
  -> `--SCAN j            # 指令级一句话；表达式谓词无索引可用（除非建表达式索引）
DuckDB 1.5.5:
  EXPLAIN SELECT g,sum(v) FROM t GROUP BY g
  -> PROJECTION / ~1 row ... PERFECT_HASH_GROUP_BY (sum_no_overflow) ...
     # 向量化物理算子树+基数波浪估算（~1 row）
PostgreSQL:
  EXPLAIN (ANALYZE, BUFFERS) ...
  -> 逐节点 est/actual rows、loops、buffers、时间三件套 ⚠️+✅（using-explain.html）
```

- 同构：三家都"先看计划再动手"；PG 独有价值在**估算/实际并排+BUFFERS 细分**——排障信息量最高的一族 🔧 对照结论 ⚠️；
- 表达式索引思想跨引擎通用：SQLite 需 `CREATE INDEX ... ON j(json_extract(...))` 方可摆脱 SCAN（⚠️ 通例+同款于 PG ✅ indexes-expressional）；
- DuckDB 无代价模型细节可移植性警告：其估算风格与 PG 成本常量完全两制，勿互抄参数（对位 [../DuckDB_in_Action/00-总览与阅读地图.md](../DuckDB_in_Action/00-总览与阅读地图.md)）。

## 6. 本章自测（重构版，对勘误后口径；题目自拟 ⚠️）

1. **问**：EXPLAIN 与 EXPLAIN ANALYZE 差别（✅ 勘误原题）？**答**：前者不出实际行不进真执行；后者实测 est vs act。
2. **问**：external merge Disk 出现说明什么？**答**：work_mem 不够，排序落盘。
3. **问**：GIN 为何写放大？**答**：每键多 posting，更新需清理 pending（fastupdate 缓解 ⚠️）。
4. **问**：CONCURRENTLY 失败留什么？**答**：INVALID 索引——REINDEX 或 drop。
5. **问**：BRIN 适合什么表？**答**：物理有序大表（时间/自增），摘要块级 min/max。

## 7. 物化视图与缓存策略（⚠️+✅）

- **物化视图**（✅ https://www.postgresql.org/docs/current/rules-materializedviews.html ）：`CREATE MATERIALIZED VIEW mv AS SELECT ...`——查询结果落盘为物理表。
- **刷新模式** ⚠️+✅：
  - `REFRESH MATERIALIZED VIEW mv`：全量重灌，期间不可读（阻塞查询 ⚠️）；
  - `REFRESH MATERIALIZED VIEW CONCURRENTLY mv`：增量差量刷新（需唯一索引 ✅ sql-creatematerializedview）；
  - 无自动增量刷新——需 pg_cron 定时触发或触发器联动 ⚠️。
- **与分区联动** ⚠️：大表物化视图可建成分区表——刷新时 ATTACH 新分区+DETACH 旧分区实现"零停机切换"。
- 🔧 SQLite/DuckDB 均无物化视图（🔧 第 6 节 08 号文件已实测否证）——替代方案=手工汇总表+触发器增量（SQLite）或 CTAS+调度（DuckDB）。

## 8. 执行计划中的并行查询（⚠️+✅）

- **并行扫描**（✅ https://www.postgresql.org/docs/current/parallel-query.html ）：`Gather`/`Gather Merge` 节点=主进程收集 worker 结果——EXPLAIN 中可见 `Workers Planned: N` / `Workers Launched: M`。
- **启用条件** ⚠️+✅：
  - `max_parallel_workers_per_gather`（默认 2 ⚠️）> 0；
  - 表足够大（`min_parallel_table_scan_size` 默认 8MB ⚠️）；
  - 查询无写入/游标/某些函数（标记 PARALLEL UNSAFE 者阻断 ⚠️）。
- **并行度调优** ⚠️：`parallel_tuple_cost`/`parallel_setup_cost` 控制优化器对并行的偏好——SSD 时代降低 `parallel_setup_cost` 常能激活更多并行计划。
- 🔧 DuckDB 1.5.5 默认全查询并行（多线程向量化 🔧 非 PostgreSQL 行为）；SQLite 单线程执行（🔧）。

## 9. 统计信息与优化器认知（⚠️+✅）

- **ANALYZE**（✅ https://www.postgresql.org/docs/current/sql-analyze.html ）：采集列统计（直方图/MCV/最公共值）→ 写入 `pg_statistic`——`autovacuum` 自动触发但高频写入表需手工补 ANALYZE ⚠️。
- **CREATE STATISTICS 扩展统计**（✅ https://www.postgresql.org/docs/current/sql-createstatistics.html ）：
  - `ndistinct`：多列组合基数建模——解决 `WHERE a=1 AND b=2` 的独立假设过估；
  - `dependencies`：函数依赖建模——`WHERE a=1` 蕴含 `b=常值` 场景；
  - `mcv`：多列 Most Common Values 列表（PG 12+ ⚠️）。
- **诊断统计不足** ⚠️：EXPLAIN 中 `rows=1` 实际 `rows=10000` → 统计过期或多列相关性——先 `ANALYZE`，不改善则 `CREATE STATISTICS`。
- 🔧 DuckDB 1.5.5 自动统计采集（首次查询后自动 ANALYZE 🔧 非 PostgreSQL 行为）；SQLite 依赖 `ANALYZE` 命令但无扩展统计。

## 核心概念速览（中英对照）

1. **执行计划** — query plan：算子树；EXPLAIN 是口供。
2. **EXPLAIN ANALYZE** — 实测对照（勘误正题 ✅）。
3. **BUFFERS** — 缓冲命中细账。
4. **位图扫描** — Bitmap Scan：多索引合并策略 ⚠️+✅。
5. **Index Only Scan** — 覆盖读：visibility map 决定回表与否 ⚠️。
6. **GIN/BRIN/GiST** — 特化索引三杰 ✅ indexes-types。
7. **表达式索引** — expression index：函数键。
8. **部分索引** — partial index：WHERE 圈热点。
9. **INCLUDE 覆盖列** — 免回表（PG 11+ ⚠️）。
10. **CONCURRENTLY** — 在线建删索引：两遍扫描+INVALID 风险。
11. **pg_stat_statements** — 指纹聚合：Top SQL 正解 ✅。
12. **auto_explain** — 现场计划捕获 ✅（本章实证）。
13. **扩展统计** — CREATE STATISTICS：多列相关性建模。
14. **random_page_cost** — 成本常量：SSD 语境重校准 ⚠️。
