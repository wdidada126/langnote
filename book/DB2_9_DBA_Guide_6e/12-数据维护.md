# 12 · Maintaining Data（Ch12 · RUNSTATS/REORG/自动维护三驾马车）

> 章名 ✅ InformIT 出版社页实抓；正文 ⚠️ 转述重构。**🔧 实验 C、E 两组**在第七节，SQLite 本机类比、非 DB2 行为。

## 一、章定位

数据维护章给 DBA 的"日常工单"建模：统计（RUNSTATS）、重组（REORG/REORGCHK）、完整性与可用性维护（LOAD 后续、约束激活）、以及 9.1 起的**自动维护调度器**。本章是"计划劣化"与"性能慢性病"的处方学，与 07/14 章构成 SQL 性能三角。

## 二、RUNSTATS 深读（⚠️ 转述）

1. 采集物：表的 CARD/NPAGES、列频率/分布（`DISTRIBUTIONS ALL`）、索引 LEAF/NLLEVELS/CLUSTERRATIO 与 KEY 分布（`COUNT n`）——优化器成本模型的燃料。
2. 触发时机：装载后、大 DELETE/UPDATE 后、REORG 后（原书 SOP：LOAD/REORG→RUNSTATS 成对出现）。
3. 命令面：`db2 runstats on table demo.emp with distribution and detailed indexes all`；`ALLOW ACCESS` 并发档位。
4. XML 列统计（08 章接口）：路径分布 `distribution on path`（⚠️ 语法保守）。
5. 成本面：RUNSTATS 自身吃 I/O 与 CPU；采样率/表函数式增量属后话（⚠️ 本版保守）。

## 三、REORG 与 REORGCHK（⚠️ 转述）

- 病因：聚簇退化（FREQ/CLUSTER 参数）、行迁移/溢出、页碎片导致"同表扫描越来越慢"。
- 处方：`db2 reorg table demo.emp`（离线：表不可写）；Inplace REORG 与 `online reorg` 是 9.7/10.5 演进面（⚠️ 本册成书离线为主，诚实标注）。
- 索引：`REORG INDEXES ALL FOR TABLE ... ALLOW WRITE ACCESS` 重建叶序。
- REORGCHK：按阈值表（FP/FSE 等列）给出"建议 REORG"判决——`db2 reorgchk current statistics on table` 输出即工单源。
- 流程铁律：REORG→RUNSTATS→（必要时）REBIND 静态包（09 章接口）。

## 四、自动维护调度器（9.1 卖点，⚠️ 转述）

- 三开关：`AUTO_RUNSTATS / AUTO_REORG / AUTO_BACKUP`（DB CFG）+ 实例调度器进程（`db2sched` ⚠️ 名保守）。
- 输入：利用率统计（表对象利用度）驱动"该不该做"，维护窗口参数控节奏。
- 运维观：自动≠免检——调度器日志（`db2schedlog` 系 ⚠️）与作业窗冲突是常见事故；考试面记开关名与依赖（→13 章 AUTO_BACKUP）。

## 五、其他维护件（清单）

1. `db2dart`：库离线诊断转储（页级体检）。
2. 约束/完整性：`SET INTEGRITY`（06 章）、分区 attach/detach 后的校验（11 章）。
3. 包治理：`REBIND`、清理 `SYSCAT.PACKAGES` 僵尸（09 章）。
4. 目录卫生：大对象 DROP 后的表空间回收（自动存储库内碎片需 REORG 表空间面 ⚠️）。
5. `db2ckwkup`：备份可恢复性预检（→13 章）。

## 七、🔧 类比实测（SQLite，**非 DB2 行为**）

本机 Python 3 + 内置 sqlite3，Windows，2026-10-01，临时件 `D:\develops\tmp\dbwave_w7_db2dba\`。

**C 组（VACUUM ↔ REORG 碎片回收）**
- 方法：10 万行表 DELETE 90%（留 id%10=0），测 `PRAGMA page_count`/`freelist_count` 与文件大小；再 `VACUUM`。
- 结果：VACUUM 前 412 页/空闲链 359 页/1,687,552 B；VACUUM 后 44 页/空闲 0/180,224 B（约省 89%）。
- 锚定：SQLite VACUUM 只回收空间；DB2 REORG 还**按聚簇顺序重排行**并联动统计——"回收+重排"二合一才是 REORG，单靠 VACUUM 类比会低估其计划影响面。

**E 组（ANALYZE ↔ RUNSTATS 基数控量）**
- 方法：建索引 `idx_v` 后执行 `ANALYZE`，读 `sqlite_stat1`。
- 结果：生成一行 `(t, idx_v, "10000 1")`——表基数 10000、索引平均重复度 1。
- 锚定：DB2 RUNSTATS 采集面远大于此（列频率/分布/索引层级/聚簇比），但优化器"靠统计估行数→选路径"的链条同构；E 组是 07/14 章 EXPLAIN 读法的实验化入门。

## 八、易错雷点（例题库精华）

1. 只 RUNSTATS 不 REORG：统计好看但物理碎片照旧，扫描成本真高。
2. REORG 后忘 RUNSTATS：CLUSTER RATIO 新值没进目录，计划仍按旧估。
3. 自动维护开着但 `AUTO_BACKUP` 指向满盘路径 → 备份连环败（→13 章）。
4. 维护作业撞业务高峰：调度窗口/`db2 "quiesce"` 时序规划缺失。
5. 大表 REORG 期间依赖该表的活动包未重绑 → 旧统计计划劣化（09 章）。
6. REORGCHK 阈值误读：把"建议"当"必须"，小表过度重组反伤 I/O。

## 核心概念速览（中英对照）

- **RUNSTATS** — 统计采集：CARD/频率/分布/索引指标入库
- **cluster ratio** — 聚簇比：逻辑序与物理序贴合度
- **REORG** — 重组：行/索引物理重排回收碎片
- **REORGCHK** — 重组体检：阈值判决工单源
- **inplace reorg** — 在线重组（书后演进 ⚠️）
- **auto maintenance** — 自动维护：runstats/reorg/backup 自治
- **scheduler** — 调度器：自动维护执行体
- **db2dart** — 库诊断转储：离线页级体检
- **SET INTEGRITY** — 完整性激活（06 章呼应）
- **REBIND** — 重绑：统计刷新后的静态包跟进（09 章）
- **VACUUM** — SQLite 回收（🔧 类比词，非 DB2）
- **freelist** — 空闲页链（🔧 类比词，非 DB2）

## 最新演进与工业实践

- 延续与增援：Db2 11.x 的自动维护扩为 **Auto Maintenance + Advisory 框架**（advisor 建议索引/MQT，`db2advis` 工作负载顾问 14 章呼应）；REORG 在线化（inplace/online）+ `ADMIN_CMD` 作业化成标配（⚠️ 转述；入口 ✅ https://www.ibm.com/docs/en/db2 ）。
- 统计新面：列统计扩展（直方图类型丰富）、`REOPT`/自适应编译（ACCF）缓解统计陈旧——"统计-计划耦合"议题在 2024–2026 由"重优化/计划固化"（Oracle SQL Plan 系、PG 扩展）多解并存。
- 工业实践：K8s/云托管下"维护窗口"让位于在线滚动维护；本册 C 组类比（VACUUM/ANALYZE）成为 PG/MySQL 双修读者的通用词汇桥（PG VACUUM/ANALYZE 与 SQLite 近亲——对照 [../Understanding_MySQL_Internals/00-总览与阅读地图.md](../Understanding_MySQL_Internals/00-总览与阅读地图.md)）。
- 学术锚点：碎片与聚簇属物理设计经典议题，教材面 [../数据库系列·总索引.md](../数据库系列·总索引.md) 原理层可回读；本目录 E 组把"统计影响计划"做成 10 分钟可复演实验。
