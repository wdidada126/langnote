# 13 · Database Recovery（Ch13 · 日志、备份与前滚恢复的完整链）

> 章名 ✅ InformIT 出版社页实抓；正文 ⚠️ 转述重构。**🔧 实验 A、B 两组**在第七节，SQLite 本机类比、非 DB2 行为。本章为全册 DBA 含金量最高章之一。

## 一、章定位

恢复章回答三个问题：崩溃后怎么自愈（崩溃恢复）、介质坏了怎么回（备份+前滚）、误操作怎么追（时点恢复/逻辑修复）。DB2 的答案全部建筑在**日志形态**上：循环日志 vs 归档日志是第一分水岭。

## 二、日志形态与参数（⚠️ 转述）

1. 循环日志（默认）：`LOGRETAIN` 未设/NOTHING，日志文件复用 → **只保崩溃恢复，备库介质即死**。
2. 归档日志：`LOGRETAIN(RECOVERY)` 或 `USEREXIT`（+`LOGARCHMETH1 DISK:/path | TSM | vendor`，9.x 参数面 ⚠️ 保守）→ 日志归档留存，支撑前滚与在线备份。
3. 参数族：`LOGFILESIZE × LOGFILSIZ`（主日志体积）、`LOGPRIMARY/LOGSECOND`、`LOGBUFSZ`；日志满=挂起事故（DB CFG 巡检项，02 章双轨）。
4. 写序纪律：WAL（先写日志后写页）+ 检查点（⚠️ DB2 术语 "log checkpoint" 参数 `CHKLOGRET`? 保守不展开）——理论底座见 [../事务处理概念与技术.md](../事务处理概念与技术.md)。
5. 断链事件：`NONRECOVERABLE` LOAD（06 章）、`NOT LOGGED INITIALLY` 激活（05 章）→ 备份必须重做，前滚链作废。

## 三、备份体系（⚠️ 转述）

- 全量：`BACKUP DATABASE demo ONLINE TO /mnt/bk1 COMPRESS? INCLUDE LOGS?`（选项面 ⚠️ 保守；ONLINE 前提=归档模式）。
- 增量谱系：`INCREMENTAL`（累积式，Δ 备份自最近全量）与 **DELTA**（差异式，自上次任意备份）——9.1 引入；恢复时按链重放。
- 备份元数据：`db2 list history backup all for demo` 是"备份目录即事实源"；`db2ckwkup` 预检可用性。
- 表空间级备份与恢复（ESE/分区场景）；离线备份=实例停+非归档亦可（应急面）。
- 存储面：本地/远程（NFS/SAN）+ TSM 供应商 API 流式（企业级标配，⚠️ 本书点到）。

## 四、恢复剧本三段（本章骨架，⚠️ 转述）

1. **崩溃恢复**：实例重启自动完成——redo 已提交+undo 在途；无参数，但恢复时长与 LOGBUFSZ/checkpoint 距离相关（14 章 RTO 关联）。
2. **版本恢复（rollback）**：`RESTORE DATABASE demo FROM /mnt/bk1` → 回到备份点，归档日志无用武地（除非再前滚）。
3. **前滚（rollforward）**：`ROLLFORWARD DATABASE demo TO END OF LOGS AND COMPLETE [USING LOCAL PATH]`；三种停点：`TO timestamp`（PITR）/`TO logseq`/`END OF LOGS`；`QUERY ONLY` 模式查可前滚范围。
4. 表空间级前滚与 `ROLLFORWARD ... RENAME` 容器重组（⚠️ 冷门保守）。
5. HADR（9 时代高可用主打）：主库日志流→备库前滚读； takeover 语义（⚠️ 版次归属存疑，本册按"原书有专节"转述）。

## 五、误操作与逻辑损坏（原书"repair"面）

- 误 DROP/TRUNCATE：版本恢复+前滚到误操作**前一时点**→导出受影响表→再恢复到当前（两步恢复法）——本章压轴例题模式。
- 坏页：`db2dart` 定位 + 表空间级备份恢复（11/12 章接口）。
- 挂起态处置：`LOAD IN DOUBT`/`RESTORE PENDING`/`BACKUP PENDING` 三态的解锁动作各自不同（06/12/13 联动）。
- 备份即保险：恢复演练（恢复测试环境全链跑通）是原书反复强调的 DBA 纪律。

## 七、🔧 类比实测（SQLite，**非 DB2 行为**）

本机 Python 3 + 内置 sqlite3，Windows，2026-10-01，临时件 `D:\develops\tmp\dbwave_w7_db2dba\`。

**A 组（在线备份 ↔ BACKUP DATABASE ONLINE）**
- 方法：`src.db` 灌 10 万行（1,687,552 B），Backup API（`src.backup(dst)`）边读边写复制出新库，行数校验。
- 结果：目标库 1,687,552 B、`COUNT(*)=100000` 与源一致。
- 锚定：等价 DB2"ONLINE 备份+INCLUDE LOGS"拿到的**一致性镜像**；但 SQLite 无"备份后前滚"能力——缺归档日志面，恢复只能回到拷贝点，正对应 DB2 循环日志+离线拷文件的天花板。

**B 组（WAL 检查点 ↔ 日志/检查点）**
- 方法：`journal_mode` 默认读出 `delete`；切 `wal` 后观察 `-wal/-shm` 伴生文件；执行 `wal_checkpoint(TRUNCATE)`。
- 结果：返回 `(0,0,0)`（busy=0，日志已截空）；WAL 文件即"归档前日志段"的最小标本。
- 锚定：WAL 中的已提交帧=前滚重放的原料；`checkpoint`=把 WAL 页应用到主库的"检查点"动作。SQLite 无 PITR/无增量备份谱系，故 B 组仅锚定**机制**，不可推及 DB2 的恢复语义（LOGRETAIN/ROLLFORWARD 全靠 ⚠️ 转述）。

## 八、易错雷点（例题库精华）

1. 循环日志库做 ONLINE 备份直接报错——先开归档（考纲必考）。
2. 改 `LOGARCHMETH1` 后不备份 → "新策略生效前旧链作废"（需一次全量）。
3. 归档盘写满 → 库挂起；`ARCHIVE LOG` 主动搬运+独立盘是容量纪律（11 章）。
4. `RESTORE` 后忘前滚/未 `COMPLETE` 即连 → 挂起态迷惑。
5. 增量链断裂：一次全量缺失，Δ/累积链全体作废——history 核对。
6. TSM 保留策略与本地备份目录双轨不同步——恢复时"清单有、文件无"。

## 核心概念速览（中英对照）

- **circular logging** — 循环日志：覆写式日志，仅崩溃恢复
- **archive logging** — 归档日志：LOGRETAIN/LOGARCHMETH 体系
- **WAL** — 先写日志：恢复理论基石（Gray/Reuter）
- **online backup** — 在线备份：运行中一致性镜像（需归档）
- **incremental/delta** — 累积/差异备份：9.1 起的增量谱系
- **ROLLFORWARD** — 前滚：备份+归档日志重放到停点
- **PITR** — 时点恢复：TO timestamp 停点
- **RESTORE PENDING** — 恢复挂起：待前滚表态态
- **BACKUP PENDING** — 备份挂起：断链后的强制补备份态
- **db2ckwkup** — 备份预检：可恢复性验证
- **list history** — 备份履历：目录即事实源
- **HADR** — 高可用灾备：日志流实时前滚（⚠️ 版次存疑）
- **INCLUDE LOGS** — 备内含日志：备份集自足化

## 最新演进与工业实践

- 2024–2026：Db2 11.5/12 恢复主干未变（备份+归档+前滚），新增 **DB2 级"备份加密"、云对象存储直写、`ADMIN_CMD` 作业化、HADR 自动故障转移（automatic failover with arbitration）**（⚠️ 转述；入口 ✅ https://www.ibm.com/docs/en/db2 ）。
