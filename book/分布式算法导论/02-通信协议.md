# 第 3 章 通信协议（Communication Protocols，原书 pp.74–102）

> 一句话定位：在不可靠信道上，用**滑动窗口 + 计时器 + 序号**造出可靠 FIFO 连接——这是 TCP 的算法内核，
> 也是全书唯一一处「协议工程」味道最浓的章。
> 延伸对照：[../TCPIP详解.md](../TCPIP详解.md)（TCP 滑动窗口的工程细节）。

## 核心精讲

（以下伪代码均为**教学示意，不参与构建**。）

### 1. 问题定义

- 两个进程 U（发起方）与 V（应答方）经**单向不可靠信道**相连：消息可能丢失、可能**重复、可能乱序**
  （原书模型里信道是先入先出或非 FIFO 两种假设下分别讨论）。
- 目标：在 U/V 之间模拟一个**可靠 FIFO 连接**，并支持**双向**流量（balanced = 双方地位对称，都可发数据）。

### 2. 平衡滑动窗口协议（3.1）

- 核心三件套：**序号**、**窗口**（未确认帧的额度）、**确认（ack）**。
- 发送方维护 `[L, H)` 窗口内可发送；收到 ack 后左边界右移；接收方按序上交、用「期望序号」去重。
- 原书讨论的关键参数是**序号空间与窗口大小的关系**：窗口必须严格小于序号空间，否则新旧帧会混淆。
  （TCP 的窗口受此约束是同一道理。）
- ** piggybacking（捎带确认）**：balanced 协议里 ack 搭在反向数据帧上，没有数据也要发「空帧」——
  这解释了为什么纯 ack-only 帧在真实协议里是常态。

```
发送方循环（教学示意，不参与构建）:
  while 窗口非空:
    if 收到 ack(k): L = k+1
    if 计时器超时:   重发窗口内全部未确认帧   ← Go-Back-N 风格
    else: 发送下一帧
```

### 3. 基于计时器的协议（3.2）：交替位与超时重传

- **交替位协议（alternating bit）**：序号只有 1 bit；发送方反复重发直到收到带正确 bit 的 ack；
  接收方只在序号翻转时上交、重复帧丢弃并重 ack。
- 原文出处是 Bartlett–Scantlebury–Wilkinson（CACM 1969）的「reliable full-duplex transmission over half-duplex links」，
  最初是为半双工链路设计的。
- Tel 的讲法把它推广成**基于计时器的协议**：每个未确认帧绑定一个计时器，超时即重发；
  并讨论了**定时精度假设**——计时器误差与消息往返时间的比值决定协议活性能否成立。
- 🔧 复杂度结论（原书口径）：交替位协议在无丢失时每数据帧约 2 条消息（含 ack）；
  窗口为 w 的滑动窗口在往返延迟 d、带宽 b 的信道上要把管道填满需 w ≥ 2bd——这就是 TCP 窗口缩放定理的教材版。

### 4. 不变量证明视角

- 原书用 Ch2 的不变量法证明「上交的消息序列 = 发送的消息序列」：关键不变量是
  「接收方已上交的帧 ⇔ 发送方已收到对应 ack 的帧」（借助序号唯一性 + 超时下界假设）。
- 🔧 修正：交替位协议的活性证明**依赖计时器下界假设**（超时必须大于一个往返），原书对此反复强调——
  工程上「RTO 设小了导致雪崩重传」就是这个假设被破坏的后果。

### 4. 停等 / Go-Back-N / 选择重传：一张对比表

| 维度 | 停等（=窗口 1） | Go-Back-N | 选择重传（SR） |
| --- | --- | --- | --- |
| 接收方缓冲 | 1 帧 | 1 帧（乱序即丢） | 窗口内乱序缓存 |
| 确认方式 | 逐帧 ack | 累积 ack | 逐帧（或 SACK） |
| 超时行为 | 重发 1 帧 | 重发窗口内**全部**未确认帧 | 只重发丢失帧 |
| 带宽利用率（RTT 大时） | 极差 | 好 | 好 |
| 接收方复杂度 | 最低 | 低 | 高（需重排序缓冲） |

- 原书 3.1 的「平衡滑动窗口」是 Go-Back-N 风格的理论化；**选择重传 = TCP 的 SACK（RFC 2018）路线**，
  原书未覆盖，但理论结构相同（序号空间 vs 窗口大小的不等式约束对三者一致）。

### 5. 交替位协议的逐帧推演（自查用）

链路 A→B，两条数据 d0、d1（**教学示意，不参与构建**）：

```
A: send d0(bit0)          B: 收到 bit0 → 上交 d0, ack(0)
A: 丢 ack, 超时重发 d0(0)  B: 重复帧(bit0 已交) → 丢弃, 重 ack(0)   ← 去重生效
A: 收 ack(0), send d1(1)  B: 翻转 → 上交 d1, ack(1)
```

- 关键不变量：「B 已上交的帧 ⇔ A 已收到对应 ack 的帧」；重复帧靠 bit 翻转区分「新帧」与「上一帧的重发」。
- 该推演可直接推广到窗口 w、序号空间 S 的一般协议：**约束是 w ≤ S−1（停等推广版）/ w ≤ ⌊S/2⌋（SR 版）**，
  否则「最老未确认帧」与「最新重发帧」的序号可能撞车。

### 6. 计时器的定量：RTO 从哪儿来

- 原书只要求「超时 > 一个往返时间」的下界；工程量化由 Jacobson/Karels 算法（RFC 6298）给出：
  - `SRTT = (1−α)·SRTT + α·R`（采样 R 的指数加权平均，α=1/8）
  - `RTTVAR = (1−β)·RTTVAR + β·|SRTT−R|`（β=1/4）
  - `RTO = SRTT + max(G, 4·RTTVAR)`，超时后指数退避（每次 ×2）。
- 🔧 这是「3.2 计时器精度假设」的现代数学化：RTO 公式本质是在**自适应地满足原书活性下界**。
  超时爆炸（重传风暴）= 下界被破坏的工业案例。

### 7. 与可靠性的边界：本书的「可靠」到哪一层

- 本章协议保证「不丢、不重、有序」，**不保证**：完整性（需校验和）、机密性（需加密）、
  长期可用（对方宕机则活性失效）。TLS/QUIC 在其上叠加 AEAD；QUIC 把序号空间扩到 2^62
  并每包单调递增，从协议层面消除了「重发包混淆」一类攻击面——这是对序号空间理论的密码学再利用。

### 8. RTO 计算的数值演练（自查用）

- 采样往返 R 依次为 100、120、80 ms（**教学示意，不参与构建**），初值 SRTT=R₀=100、RTTVAR=0：
  - 第 1 采样 R=100：SRTT=100，RTTVAR=0，RTO=100（+G 上限保护）
  - 第 2 采样 R=120：RTTVAR=0.75·0+0.25·|100−120|=5；SRTT=0.875·100+0.125·120=102.5；RTO≈102.5+20=122.5
  - 第 3 采样 R=80：RTTVAR=0.75·5+0.25·|102.5−80|≈9.4；SRTT=0.875·102.5+0.125·80≈99.7；RTO≈99.7+37.6≈137.3
- 观察：一次「快但波动大」的样本同时抬高方差项 → RTO 变得保守——公式的本意是**宁可晚发不可早发**，
  即自适应逼近原书的活性下界。

### 9. 有损信道上「窗口」与「拥塞」的分离（原书缺位的架构提醒）

- 本章窗口回答「**对方能收多少**」（流控）；1988 年后的拥塞窗口回答「**网络能扛多少**」（cwnd）；
  发送窗 = min(rwnd, cwnd)。原书只有前者——因为它假设「信道损坏但永不拥塞」。
- 工程后果：只看本章学 TCP 会漏掉「慢启动、AIMD、BBR 测带宽」这整条线；但反过来，
  拥塞控制的**状态机骨架**（超时/重复确认驱动重传）仍是本章协议的重传逻辑，两者不可互相替代。

### 10. 本章协议 ↔ TCP 特性对照（自查 / 面试两用）

| 本章概念 | TCP 对应物 | 差异点 |
| --- | --- | --- |
| 滑动窗口 | 发送/接收窗口（rwnd 通告） | TCP 双窗口（叠加拥塞窗口） |
| 交替位 | 窗口=1 的退化 | TCP 序号按字节计，非按帧 |
| 捎带 ack | delayed ack + 捎带 | TCP 有延迟确认计时器 |
| 超时重发 | RTO 状态机 + 快速重传 | TCP 加了 3 个重复 ack 触发的重传路径 |
| 序号空间约束 | 32 位序号 + PAWS 防回绕 | 高带宽长肥管道下序号回绕是真实问题 |

- 阅读建议：先吃透本章的「理论最小集」，再去看 [../TCPIP详解.md](../TCPIP详解.md) 的工程扩展，
  每一处扩展都能问一句「它补的是原书哪条假设」。

## 版本演进

| 阶段 | 变化 | 影响 |
| --- | --- | --- |
| 1969 | 交替位协议（CACM） | 3.2 的原始形态 |
| 1981 | TCP（RFC 793）：滑动窗口 + 累积确认 + 自计时 | 本章思想的工业标准实现 |
| 1988 | Jacobson 拥塞控制（慢启动/拥塞避免，SIGCOMM '88） | 在「可靠」之上加「公平」维度，原书不涉及 |
| 1996–2014 | SACK（RFC 2018）→ CUBIC → BBR（Google，ACM Queue 2016，非同行评审期刊文章） | 丢包不再是拥塞唯一信号，计时器协议从「超时重传」进化到「带宽测度」 |
| 2015–今 | QUIC（RFC 9000, 2021）：把滑动窗口搬到用户态 UDP 上，流级独立 | 滑动窗口抽象依旧，实现位置变了 |

## 近年研究与工业界开源实践（2015–2026）

- **QUIC 与 HTTP/3**（RFC 9000，2021）：滑动窗口 + 序号 + 计时器三件套全部保留，只是把重传逻辑放进用户态。
- 开源实践（star 数 2026-09-26 `gh api` 实测）：
  - `torvalds/linux`（250.2k★）：TCP 实现见 `net/ipv4/tcp_input.c` / `tcp_output.c`，滑动窗口与 RTO 状态机即本章协议的工业级放大版。
  - `nginx/nginx`（star 未核验，主仓库镜像未单独查询）：对上游连接的缓冲/背压可视作应用层「窗口」。
- 🔧 数据库场景：分布式数据库 RPC 层（如 TiKV 的 grpc 流控）也在做「应用层滑动窗口」，思路同源
  （见 [../分布式数据库入门进阶与实战/00-总览与阅读地图.md](../分布式数据库入门进阶与实战/00-总览与阅读地图.md)）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「滑动窗口保证不丢消息」 | 滑动窗口只保证**可靠+有序的抽象**，底层依赖超时重传与最大重试；无限期丢包时活性仍不成立 |
| 2 | 「交替位协议不需要窗口」 | 它是窗口大小为 1 的特例；管道化后必须扩大窗口与序号空间 |
| 3 | 「超时越短越好」 | 原书证明：超时下界必须覆盖一个完整往返；超时过短破坏协议活性并引发重传风暴 |
| 4 | 🔧 本书假设「信道可能重复但不会恶意篡改」 | 现代协议必须叠加校验和/加密（TLS、QUIC 的 AEAD），防的是篡改与注入，不只是丢包 |
| 5 | 🔧 原书没有拥塞控制维度 | 1988 年后的 TCP/QUIC 都把「网络也是共享资源」纳入协议目标——可靠 ≠ 公平，两者要分别设计 |
