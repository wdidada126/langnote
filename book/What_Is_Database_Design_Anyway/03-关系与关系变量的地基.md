## 讲解精要

### 3.1 值 vs 变量：设计作用于哪个

- **关系是值**（某时刻的集合），**关系变量（relvar）是变量**（可以取不同关系的占位符）。
  ⚠️ 出处：#12 第 2 章（盘上 02 文件，其 00 摘要句"SQL 表是 relvar 的近似，且近似得很脏" ✅ 盘上原文）。
- 设计者定义的是 **relvar + 约束**，不是"某张表"；对 relvar 的赋值（赋值必须整体进行）才是状态转移。
  把设计交付物说成"建表脚本"（DDL）是术语事故的源头——DDL 描述的是 SQL 基本表，不是 relvar（偏离清单见 [09 章](09-从理论到实践的断层.md)）。

### 3.2 标题（heading）与内容（body）：设计的双层制品

- 关系值 = 属性名→类型的映射（标题）+ 元组集合（内容）。
- **设计的产物一半在标题里**：属性名承载谓词参量的名字，类型承载域（domain）语义；内容层只是当前外延。
  ⚠️（重构自 #12 02 章与 #8 02 章的"预备知识"两层口径。）
- 🔧 类比实测（EX6 片段，SQLite 3.45.3，**非本书引擎**）：`CREATE TABLE T(c2 INTEGER, c1 TEXT)`——
  `PRAGMA table_info(T)` 返回 `['c2','c1']`：**从左到右的列序是真实存储属性**。理论上的标题是**集合**（无左无右），
  产品把有序列表塞进了本应无序的层。设计者若依赖列序（`SELECT *` 拼接、按位置装载），等于把语义焊在事故上。

### 3.3 元组是命题，行是载体

- 一个元组 = 谓词的一个真实例（[02 章](02-设计就是谓词的决定.md)）；行（SQL tuple）只是近似载体。
- 🔧 类比实测（EX6 片段，SQLite，非本书引擎）：同值两行连插两次，`COUNT(*)=2`——**产品允许同一命题被断言两遍**。
  关系语义里这是同一个元组（幂等），包语义里这是"两条供应记录"——设计者必须知道自己在哪个宇宙（对位：
  [../SQL_and_Relational_Theory/09-重复行DISTINCT与集合语义.md](../SQL_and_Relational_Theory/09-重复行DISTINCT与集合语义.md)）。
- 物理层对照（为什么"行"≠"元组"有硬件理由）：[../mysql/04-记录在页中如何存储.md](../mysql/04-记录在页中如何存储.md)——
  行有地址、顺序、版本指针；元组没有。

### 3.4 dum 与 dee：把布尔装进关系层次

- `TABLE_DEE`（0 度 1 元组）= 真；`TABLE_DUM`（0 度 0 元组）= 假。
- 设计用途：约束断言、`IS TRUE` 语义、`NOT MATCHING` 的全集判据都在 0 度关系上说话；
  没有这一层，"数据库断言"无法在关系代数内部表达。⚠️ 细节全在 #12 附录 B（[../Relational_Theory_for_Computer_Professionals/15-附录TutorialD dum与dee集合论与关系演算.md](../Relational_Theory_for_Computer_Professionals/15-附录TutorialD dum与dee集合论与关系演算.md)）。
- 🔧 类比（SQLite，非本书引擎）：sqlite 无 0 度关系原语；最接近的写法是 `SELECT EXISTS(SELECT 1 FROM 空表)` 返回 0——
  **布尔活在标量层而不是关系层**，这正是 dum/dee 缺席的体检报告。

### 3.5 封闭性：设计语言必须能表达"关系的图灵等价"

- 算子输入输出皆关系 ⇒ 可任意嵌套（出处：[../SQL_and_Relational_Theory/02-关系代数与封闭性.md](../SQL_and_Relational_Theory/02-关系代数与封闭性.md)）。
- 设计推论：**视图/派生 relvar 必须是关系**，否则"同一谓词的两种写法"不可证等——SQL 的 CTE/派生表满足，物化视图部分满足（⚠️，展开在 [08 章](08-反规范化的正确位置.md)）。

### 3.6 一条元组的旅程（从谓词到断言的串联图 ⚠️ 编辑自拟）

`谓词 P(x,y)`（02 章）→ 声明 relvar `R{x:TX, y:TY}` 带标题（3.2）与码约束（04/06 章）
→ 某业务时刻真值实例化 `P(a,b)` → 赋值语义下 `R := R ∪ {tuple(a,b)}`（3.1；SQL 里写成 INSERT 是行宇宙方言）
→ CWA 断言其余实例皆假（2.1）→ 分解/物化时该元组必须无损迁移（05/08 章）
→ 任何一处 NULL/重复/列序耦合都会在这条旅程上造假（3.2/3.3/3.4 🔧 各点名一次）。
**设计质量=旅程完整性**；地基章的全部作用是把这条链的名词钉死，后面各章才有共同语言。

## 常见误区

1. **表=关系**：🔧 3.2/3.3 两处实测（列序、重复行）就是反例本身。
2. **relvar=变量=可任意 UPDATE 一行**：赋值语义是整体替换（关系值语义）；逐行更新是 SQL 的行对象遗风 ⚠️。
3. **把标题当纯语法**：改属性名=改谓词参量名=改设计，不是"美化"；重命名算子 ρ 的严肃性在此。
4. **认为集合论地基"工程上无所谓"**：[../BuildYourOwnDatabaseFromScratch.md](../BuildYourOwnDatabaseFromScratch.md) 的亲手实现线显示，
   凡是把元组当带地址对象的存储设计，都会在删除异常/更新异常上交税（数字见 [05 章](05-规范化是为真理而分解.md) 🔧 EX1）。
5. **0 度关系是玩具**：断言引擎、参照完整性检查、无损性测试的最一般陈述都要经过它（#12 附录 B 的练习题生态 ⚠️）。

## 核心概念速览（中英对照）

1. **关系** — relation：标题+元组集合的值；设计语义在标题、外延在集合。
2. **关系变量** — relation variable (relvar)：取关系值为状态的变量；DDL 的真正所指。
3. **标题** — heading：属性名与类型的有限映射（无序集合）。
4. **内容** — body：当前成立的元组集合。
5. **度** — degree：标题中属性个数；0 度关系承载真/假。
6. **基数** — cardinality：元组数；与"行数"在包语义下不可互换。
7. **TABLE_DEE / dum 之对** — dee：0 度 1 元组 = 真；**TABLE_DUM** — dum：0 度 0 元组 = 假。
8. **赋值** — assignment：relvar 整体换值；不是逐行 UPDATE。
9. **封闭性** — closure：算子输入输出皆关系，嵌套自由。
10. **包** — bag/list：允许重复的集合近似；SQL 表的默认宇宙。
11. **列序** — column order：理论无、产品有（🔧 3.2 实测）。
12. **域** — domain/type：属性的取值原子的类型层；设计的词汇表。

## 最新演进与工业实践

- **DuckDB 的嵌套值不是 RVA**（🔧 EX6v2 实测，duckdb python 1.5.5）：`CREATE TABLE rva(id INTEGER, r INTEGER[]); INSERT ... VALUES(1,[2,3])` 成功，
  返回 `[(1, [2, 3])]`——LIST/STRUCT 是**值类型的复合**，不是 Date 期望的**关系值属性**（带标题、封闭于关系算子）；
  半结构化阵营（JSON 列，PostgreSQL jsonb / SQLite JSON1）同构地绕开了 1NF 争论（⚠️ 定位转述；官方文档：
  https://www.postgresql.org/docs/current/ddl.html ✅ 200、https://www.sqlite.org/limits.html ✅ 200、https://duckdb.org/docs/stable/ ✅ 200）。
