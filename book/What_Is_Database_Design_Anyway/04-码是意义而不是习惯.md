## 本章定位与取证依据

"设计=谓词的决定"（[02 章](02-设计就是谓词的决定.md)）落到属性层，第一件产物就是**码**：谓词里哪些参量单值决定其余参量，
码就把这件事**声明出来**。Date 的一贯立场（⚠️ 重构，出处盘上可查）：码是**被发现的**（业务真值决定），不是被选美的；
而"主键"只是众多候选码里被**特别指定用于外键指向**的那一个——"特别"仅指引用便利，不指本体优越。

## 讲解精要

### 4.1 定义层三件套

- **超码（superkey）**：能唯一决定全元组的属性集。⚠️
- **候选码（candidate key）**：极小超码——去掉任何一列就不再唯一。一个 relvar 可以有**多个**候选码，这不是缺陷。
- **主码/主键（primary key）**：被设计者**指定**为"外键默认指向对象"的那个候选码。
  Date 命题（盘上出处即 DDRT 附录 A 文件名所示）：主键是好的（nice）但非必需（not essential）✅ 文件名实证，论述 ⚠️。
- **外码（foreign key）**：跨 relvar 的包含依赖声明——"我的这个码值集合必须包含于它的那个"。

### 4.2 码从谓词来：两条判据

1. **唯一性判据**：谓词 `存在供应商 s 名为 n 位于城市 c` 中，`s` 单值决定 `n`、`c`（对同一 s 不能有两个不同名），⇒ `{s}` 是候选码。
   判据来源是**业务世界的规律**，不是"数据看起来唯一"（采样唯一≠必然唯一）。
2. **不可约判据**：`{s, n}` 也唯一，但去掉 n 仍唯一 ⇒ 非候选码。把非候选码声明成主键是冗余声明的温床（🔧 关联 EX1 冗余计数）。

### 4.3 "任意主键"之争（surrogate 问题）

- 立场重构 ⚠️：`id INTEGER AUTOINCREMENT` 类代理键**本身合法**（任何超码都行得通，Date 不禁止），
  非法的是**用代理键掩盖谓词没想清楚**——当业务存在自然候选码（身份证号、ISBN）却从不声明，
  重复事实（`(123456, '张三')` vs `(987654, '张三')` 同谓词两元组）就只能靠应用层"自觉"。
- 🔧 类比实测（EX3 片段，SQLite 3.45.3，**非本书引擎**）：`CREATE TABLE K(c TEXT UNIQUE)` 后连插两个 NULL **全部成功**——
  `UNIQUE 列上 NULL 计 2 行`。SQL 的 UNIQUE 语义是"非 NULL 值互异"，与"码值唯一"差一个 3VL 鸿沟；
  以码自居的约束产品实现得先问 NULL（对照 #12 第 3 章与 #12 第 13 章的"会话开关"批判）。

### 4.4 引用完整性是码的第二半

- 外码不是"表间连线"，是**两个集合的包含断言**——它让"删父留子"成为可检查的谎言（🔧 机制在 [06 章](06-约束是设计的一部分.md) EX3 FK 实测：
  孤儿插入在 `PRAGMA foreign_keys` 开时 `FOREIGN KEY constraint failed`，关时静默成功）。
- Date 对"ON DELETE CASCADE 之类"的态度 ⚠️：动作子句（SQL:2003 起产品普及）把约束变成触发器方言，
  声明式纯度下降；约束应当只说"不许发生"，不说"发生时怎么办"。

### 4.5 与 #8 规范化的接口

- 码声明是 BCNF 的正面表述：**每个非平凡 FD 的决定因素都是超码**（[../Database_Design_and_Relational_Theory/04-函数依赖与BCNF非正式.md](../Database_Design_and_Relational_Theory/04-函数依赖与BCNF非正式.md)）。
- 设计顺序上码先于范式（声明=文档化谓词，范式=修复声明不了的分解），此即题面文章"目的一致论"的又一体。

### 4.6 声明写法对照（Tutorial D 示意 vs SQL 现实；⚠️ 示意非原文）

```tutorial-d        -- ⚠️ 依 #12 附录 A 的语言形态示意，本机不可运行
VAR S RELATION {SNO SNO, STATUS INTEGER, CITY CITY, ...}
  KEY {SNO} ;              // 候选码声明：一个事实，一处声明
CONSTRAINT CITY_OVERLOAD NOT (EXISTS (S GROUP ...)) ;  // 断言层：本机产品均无（06 章 EX3）
```

```sql
-- SQL 现实（可跑，SQLite 3.45.3/DuckDB 1.5.5 语法子集，🔧 非本书引擎）
CREATE TABLE S (
  SNO TEXT PRIMARY KEY,          -- 主码：唯一性+非空（但见 EX3 的 UNIQUE-NULL 侧漏）
  STATUS INTEGER CHECK (STATUS >= 0),
  CITY TEXT
);
-- 'SNO, CITY 组合也唯一' 的第二候选码：只能再挂 UNIQUE——两声明间无"候选码平等"的语义层
```

**读法**：Tutorial D 侧的 `KEY{...}` 是**语义声明**（业务规律），SQL 侧的 PRIMARY KEY/UNIQUE 是**机制开关**（引擎承诺）。
4.1–4.5 的所有立场都可浓缩为一句：**设计文档写前者，DDL 只是后者的投影**；把投影当原物，就是[09 章](09-从理论到实践的断层.md)断层的日常形态。

## 常见误区

1. **"每表必须一个主键，没有就加 id"**：必须的是**至少一个候选码**（关系值语义下天然成立——集合无重复元组）；
   "必须声明"是 SQL 产品需求，不是模型需求（附录 A 的主论点 ⚠️）。
2. **"主键=行的身份证"**：主键标识的是**命题**不是行（同一命题两行=包语义事故，🔧 [03 章](03-关系与关系变量的地基.md) 3.3）。
3. **"UNIQUE 和主键只差一个 NULL"**：差的是整个 3VL 宇宙（🔧 EX3 实测）与外码可指向性。
4. **"复合码不好，尽量单列"**：业务复合唯一性（`(订单, 商品)`）拆成代理键反而**隐藏**谓词；码形状=谓词形状 ⚠️。
5. **"FK 性能差所以不用"**：代价讨论属于物理层（[08 章](08-反规范化的正确位置.md)）；不用 FK 等于把包含断言外包给每个应用——设计层弃权。

## 核心概念速览（中英对照）

1. **超码** — superkey：唯一决定全元的属性集（不必极小）。
2. **候选码** — candidate key：极小超码；业务规律的直接投影。
3. **主码/主键** — primary key：被指定供外码引用的候选码；"良好而非必需"。
4. **外码** — foreign key：跨 relvar 包含依赖的声明形式。
5. **包含依赖** — inclusion dependency (IND)：Π_X(R) ⊆ Π_Y(S) 的全称断言。
6. **代理键** — surrogate key：无业务语义的人造唯一值；合法但可被滥用于遮丑。
7. **自然键** — natural key：携带业务语义的候选码。
8. **极小性** — irreducibility：候选码的"不可约"判据。
9. **码值 NULL 问题** — UNIQUE-with-NULL：SQL UNIQUE 放过多 NULL（🔧 EX3 实测 2 行）。
10. **级联动作** — referential actions (CASCADE/SET NULL)：把约束改写成事件策略的 SQL 装置。
11. **决定因素** — determinant：FD 左端；BCNF 判定的主语。
12. **闭包** — closure (X+)：由 X 推出的全属性集；码验证的机械法（#8 06/11 章机器）。
