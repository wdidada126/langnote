## 核心精讲

### 1. 四性定义：Subject-Oriented / Integrated / Non-Volatile / Time-Variant

- **面向主题**：按分析实体（客户/产品/交易）而非业务功能（开票/发货）组织数据 ⚠️ 通行定义。后果：同一业务对象在多个源系统的数据必须"并成一个说法人"。
- **集成**：进入仓库前必须完成命名、编码、单位、口径的归一（例：A 系统性别 F/M/1/2/Y/N 混战 → 单一域）⚠️。这是 ETL（04 章）存在的第一理由。
- **非易失**：只读不写（除装载窗口外）——数据进入后以追加/版本化代替 UPDATE/DELETE ⚠️。工程后果：SCD 策略（04 章 E2 🔧 演示）。
- **时变**：每一事实在时间轴上有位臵，仓库本质是"带时间的历史账本" ⚠️。后果：粒度设计（05 章）与保留/归档策略（06 章）。
- 盘上口径互校：[../Building_the_Data_Warehouse/01-决策支持系统的演化.md](../Building_the_Data_Warehouse/01-决策支持系统的演化.md)（Inmon 母册 01/02 章同源定义）✅ 实链。

### 2. OLTP 与 DSS 的分野：为什么"再加个从库"不够

- 负载形态对立：OLTP=短事务高并发写、按主键点查；DSS=长查询大范围扫、聚合与多维切片 ⚠️。
- 混用三害：大查询拖垮生产事务；生产规范化结构对分析极不友好（十几张表关联）；取数口径与生产变更互相绑架 ⚠️。
- 2002 年前后主流解法：独立仓库库 + 夜间批量装载 + 集市分层（02 章架构谱）。
- 🔧 最小直觉实验（非本书引擎）：在 10 万行事实表（E1 库）上，主键点查（`SELECT ... WHERE sale_id=?`）SQLite 亚毫秒完成，而跨三维表聚合需 107.3ms（00 第七节 E1）——点查与聚合的代价结构完全不同，这就是"两套系统"的微观证据 ✅ 本机实测。

### 3. 架构金字塔：概念 → 逻辑 → 物理的秩序

- **概念层**：业务实体与其关系的极简图（客户-订单-产品），业务人员可复核 ⚠️。
- **逻辑层**：主题域划分、总线矩阵（业务过程 × 维度）雏形（05 章）⚠️。
- **物理层**：表/分区/索引/聚合/装载窗口落地（06 章）⚠️。
- 金字塔隐喻的要点：**上层未定，下层先建=返工之源**；实施顺序常与建模顺序相反（自底向上实施、自顶向下设计）⚠️ 2002 教材共识口径。

### 5. 常见谬误（2002 视角 + 今日回看）

- "生产库加宽表/物化视图 = 数仓"——没有集成与时变积累，只是查询加速 ⚠️。
- "先上 BI 工具再谈数据"——工具放大口径混乱而非解决之 ⚠️。
- "仓库=一次性工程"——仓库是持续的数据产品线，2026 年以"数据平台/分析工程"重生（10 章）✅ URL。

## 工程问答卡（⚠️ 重构口径，逐问一行）

- **问**：四性各买到了什么 **答**：面向主题买重组，集成买口径，非易失买信任，时变买回溯——四个词对应四种下游能力。
- **问**：为什么 OLTP 读复制不能代替仓库 **答**：复制只解决可用性，不解决口径；它既不沉淀历史也不做版本化，schema 还跟着生产系统走。
- **问**：面向主题的最小证据 **答**：同一主题域内所有表能用一句'一行=业务实体的一次什么'讲清，且业务方认账。
- **问**：时变与审计列差在哪 **答**：审计列记'装载时刻'，时变记'事实发生/变化时刻'——混用即历史不可回放。
- **问**：两学派分歧在哪层最硬 **答**：在企业中心 vs 集市先行的来源与节奏；物理层（06 章）上两者约束同构。
- **问**：DataVault 为何常不算进 2002 战场 **答**：其推广稍晚于两派交锋主期；当年同类诉求多由源合同+人规审计承接。
- **问**：视图化伪仓库算不算仓库 **答**：不算——无集成沉淀与时变积累，视图不存数据、口径漂移无处仲裁。
- **问**：粒度不声明的后果链 **答**：聚合重复计数、报表不可比、容量估错（06 章输入失效）三连。
- **问**：同名中文书为何是取证课 **答**：题域同名不等于同书；书目定性必须锚 ISBN+出版社链，题名只做线索。
- **问**：金字塔隐喻何时失效 **答**：下层被旧引擎锁死而上层随意改动时——此时需要适配层设计，不是重排金字塔。
- **问**：四性在湖仓年代还成立吗 **答**：成立，载体从'库'改为'表格式+分层承诺'（10 章线 1），矛盾未变。
- **问**：把大数据库当仓库的头号受害者 **答**：口径消费者——报表与指标随生产变更漂移且无法回滚。
- **问**：E1 的点查/聚合倍数如何指导投资 **答**：两个数量级的代价结构差，是'分析要独立资源预算'的最短论证。
- **问**：BI 工具先行有仓库后行错吗 **答**：工具可提前暴露口径矛盾，未必需禁止；风险在'用工具补丁代替集成'。
- **问**：四性里哪条定义寿命最长 **答**：集成——源越多口径越难，2026 的语义层运动恰是其当代回声。
- **问**：30 秒读本章的三个必答 **答**：为什么要独立存储、为什么口径单点、为什么要留历史。
- **问**：本章重构最大风险 **答**：无法对照原书详略取舍，只能以 2002 通行共识呈现并声明（00 第三节）。

## 核心概念速览（中英对照）

- **数据仓库** — Data Warehouse：面向主题、集成、非易失、时变的分析数据存储 ⚠️ 经典四性。
- **操作型系统** — OLTP：短事务、点访问、强一致的生产系统，与仓库负载形态对立。
- **决策支持系统** — DSS：以分析数据支撑非结构化决策的应用族，仓库的服务对象。
- **概念/逻辑/物理模型** — Conceptual/Logical/Physical Model：金字塔三态，设计自上而下、实施自下而上。
- **架构学派** — Inmon-style Enterprise DW：先企业级规范化仓库，集市下游派生。
- **维度学派** — Kimball-style Dimensional Modeling：总线架构与一致性维度直接交付集市。
- **信息工厂** — CIF（Corporate Information Factory）：Inmon 的仓库+ODS+集市流水线全景 ⚠️。
- **集成（归一）** — Integration：多源同名异义/异名同义数据在入库前统一口径。
- **非易失** — Non-Volatile：入库后不覆写历史，以追加与版本化保留时间旅行能力。
- **时变** — Time-Variant：一切事实带时间戳，粒度与保留期成为一级设计变量。

## 最新演进与工业实践

- **定义依然成立，载体全面换代**：四性描述的核心矛盾（生产 vs 分析）在 2026 年仍由独立分析层解决，只是"仓库"从一体机变为云托管服务/湖仓表——微软对"数据平台"的分层定义 ✅ https://learn.microsoft.com/en-us/azure/architecture/data-guide/lake/lakehouse 。
- **湖仓对"仓库=表"的重述**：Databricks 官方以 open table format+ACID 统一 lake 与 warehouse 语义 ✅ https://www.databricks.com/product/data-lakehouse （2026-10-02 curl 200）。
- **表格式的时变工程化**：Apache Iceberg 把"时变+非易失"下沉为表规范（快照、时间旅行、模式演进）✅ https://iceberg.apache.org/docs/latest/ ——2002 年在仓库里手工做的事，2026 年由开放表格式出厂自带。
- **学派之争的新形态**：维度建模与 DataVault 在云仓/湖仓中共存，选型问题从"学派信仰"变为"审计、演化速度、分析易用性"三角权衡 ⚠️ 转述（盘上 [../Data_Vault_2_0/00-总览与阅读地图.md](../Data_Vault_2_0/00-总览与阅读地图.md) 附册有分工辨析）。
- **分析工程接棒"仓库实施"**：dbt 把转换层 SQL 软件化（版本/测试/文档）✅ https://docs.getdbt.com/docs/build/incremental-models ——本目录 04/07/09 章议题的 2026 工程形态。
- **口径治理成为产品**：语义层与数据目录（DataHub/OpenMetadata 类）把"集成"从 ETL 一次性动作变成持续元数据服务 ✅ https://docs.datahub.com/docs/introduction 。
