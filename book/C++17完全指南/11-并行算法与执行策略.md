# 11 并行算法与执行策略——`par` 是承诺，后端才是兑现

> 覆盖原书 **Part V 第 21 章（并行算法部分）**。
> 一句话：给现成的 STL 算法加一个「授权等级」参数（`seq`/`par`/`par_unseq`），让库替你切分任务——
> 但**授权不等于执行**：没有并行后端，`par` 只是一句悄悄落空的愿望（本章核心实测）。
> 互链：[../C++17完全指南.md](../C++17完全指南.md)｜[../C++系列·总索引.md](../C++系列·总索引.md)｜[12-库扩充小件与移除特性.md](12-库扩充小件与移除特性.md)

## 核心概念速览（中英对照）

- **执行策略** — execution policy（`std::execution::seq` / `par` / `par_unseq`）：调用方对算法做出的**语义授权**，不是并行的开关。
- **并行后端** — parallel backend：PSTL 底下真正干活的实现。libstdc++ 依赖 **Intel TBB**；缺失时**静默退化为串行**（实测，零警告零报错）。
- **可并行的累加** — `std::reduce` / `std::transform_reduce`：`accumulate`/`inner_product` 的替身，**要求运算可结合**，求值顺序不定。
- **前缀和** — `std::inclusive_scan` / `exclusive_scan`：并行世界的「分工原语」，也是串行下照样好用的新算法。
- **交错执行** — vectorized interleaving（`par_unseq` 的额外授权）：同一线程内访存操作可被打散重排，谓词必须彻底无状态。
- **数据竞争前提** — race-free precondition：`par` 要求元素间访问不重叠；违反不是「可能出bug」而是 **UB**。
- **`is_execution_policy_v`** — 策略类型的 traits（实测 `parallel_unsequenced_policy` 通过），写泛型转发层时用。

## 动机：不想手写线程池的并行化

老路：分块 → 建 N 个线程 → 各算一段 → 合并 → 处理异常与负载均衡，每个算法重来一遍。
C++17 的路线是把决策交给库：

```cpp
#include <execution>
std::sort(std::execution::par, v.begin(), v.end());          // 一行：授权并行排序
auto sum = std::reduce(std::execution::par_unseq, v.begin(), v.end(), 0.0);
std::for_each(std::execution::par, v.begin(), v.end(), f);
```

三档授权从轻到重：`seq`（保持串行语义）⊂ `par`（可多线程，元素各管各的）⊂ `par_unseq`（还可向量化交错）。
**算法可选实现你的授权**——这是本章所有实测故事的伏笔。

## 机制与实测证据（g++ 15.2 MinGW，全部 `-std=gnu++17 -O2 -static`）

### 1. 编译期：API 齐全，语义严格

```cpp
static_assert(std::is_execution_policy_v<std::execution::parallel_unsequenced_policy>); // 实测通过
std::reduce(std::execution::par, v, 0LL);   // 误把容器整个传入：
// 实测报错原文：no matching function for call to 'reduce(const __pstl::execution::v1::parallel_policy&,
//   std::vector<int>&, long long int)' … candidate expects 4 arguments, 3 provided
```

报错里的 `__pstl::execution::v1` 就是 libstdc++ PSTL 的 inline namespace——名字本身就交代了实现出身。
策略参数**永远排第一**，且必须有迭代器对；没有「range 重载」（那是 C++20 ranges 的地盘）。

### 2. 运行期：`par` 一个线程都没开（本章最重的实测）

探针：`for_each` 的 lambda 里把 `std::this_thread::get_id()` 插入 `set`，10 万元素——

| 构建方式 | seq 线程数 | par 线程数 |
| --- | --- | --- |
| 普通 `-O2` | 1 | **1** |
| `-fopenmp` | 1 | **1** |

计时佐证（2M 元素 × 300 轮 `sin` 链的重计算 `transform`）：
`seq=12528ms  par=12372ms  par_unseq=11084ms`；换 `-fopenmp` 构建再跑：`12103/12883/11393ms`。
**par 与 seq 打平**（差距在噪声内；同机不同轮次绝对值可从 7.9s 漂到 12.5s ⚠️ 计时受负载影响）。
`par_unseq` 小幅领先约 10%——来自向量化而非多线程。内存带宽受限的 20M `sqrt` transform 则三档全平（39/39/41ms）。

结论：**本机 libstdc++ 把 `par` 静默降级成了串行**。没有警告、没有 `#error`，benchmark 是唯一能揭穿它的手段。

### 3. 根因：libstdc++ 的 PSTL 要 TBB，而 `-fopenmp` 救不了它

- 在 `D:\develops\tools\mingw64` 全树 `find -iname "*tbb*"` **无结果**（实测）：本机工具链没带 Intel TBB。
- libstdc++ 的并行算法是薄封装，任务切分/工作线程全部委托 TBB；缺 TBB 时头文件走「serial 后端」路径——即 §2 的实测行为。
- 网传「GCC 的 PSTL 需要 `-fopenmp`」**在本机被证伪**：`-fopenmp` 构建下 par 仍是单线程（§2 表格第二行）。
  合理的解释是 GCC 12 移除了 PSTL 的 OpenMP 后端、只留 TBB ⚠️（GCC changelog 原文今日无法联网核验，标注待核）。
- **本目录 `00` 工具链表写「并行算法需 `-fopenmp`」，以本章实测为准：需要的是 TBB（`-ltbb`），装不上就串行**。
  （00 已定稿不改，此处作为勘误记录。）

要在 GCC 上真正兑现 `par`：安装 oneTBB 后 `-fuse-ld=... -ltbb` 重测（本机未装，无法实测 ⚠️）。
MSVC 自带并默认启用并行后端（`/std:c++17` 即真并行）⚠️ 本机无 MSVC 未实测；Linux 发行版一般 `libtbb-dev` + `-ltbb` 即可。

### 4. 语义契约：`reduce` 为什么不是 `accumulate`

`reduce` 允许库**任意结合顺序、任意切分**地求值，所以要求二元运算**可结合**；还按值拷贝初值、可多次调用 op。
经典反例（推演，未实测 ⚠️）：`std::reduce(par, {1,2,3,4}, 0, std::minus{})`——减法不可结合，
串行给 `-2`，并行切分后可得 `((1-2)-(3-4))=0` 之类的任意结果，且**不报错**。
浮点加法「可结合」只是数学幻觉：`reduce` 打乱顺序后结果与 `accumulate` 在最后一位不同是常态——要确定性就别用 `par` 版，
要并行归约就别抱怨低位差异。`transform_reduce` 的两段式（先变换后归约）同理，还额外允许「减 1 再求和」这类
每个元素独立变换的组合（其并行合法性来自逐元素，不来自减法）。

## 权衡

| 方案 | 得到什么 | 付出什么 |
| --- | --- | --- |
| `seq`（或不开后端） | 确定性顺序、异常语义清晰、可单步 | 无并行 |
| PSTL `par` + 装好的 TBB | 一行并行、work-stealing 免费拿 | 依赖后端；谓词契约；结果顺序不定 |
| 直接用 oneTBB（`parallel_for`/`parallel_reduce`） | 粒度/分配器可控，无后端失踪问题 | 非标准库依赖、API 学习 |
| 手写线程分块 | 完全控制 | 每个算法重写一遍 §动机 里那套样板 |

## 相邻概念对比

- **vs `06` 折叠表达式**：折叠是**编译期**对参数包的「reduce」，`std::reduce` 是**运行期**对元素序列的折叠——两者都对「结合律」有隐含契约（折叠的逗号/加号顺序是规定死的，reduce 的不是）。
- **vs OpenMP `#pragma omp parallel for`**：OpenMP 是语句级注解+自己的运行时；PSTL 是库调用级。§2 的实测顺便说明它们互不相干：`-fopenmp` 不喂给 PSTL 任何线程。
- **vs C++26 `std::execution`（senders/receivers）**：**同名不同物**——那是异步执行框架（P2300R10，wg21 可达已核 ✅，标题即 `std::execution`），PSTL 的策略参数不会因它改变；未来 PSTL 可能改用其原语实现（⚠️ 走向未核）。

## 最新演进与工业实践

**标准之后**
- C++20/23 没有给执行策略添新成员；PSTL 作为一个整体热度下降，社区的并行化叙事转向 **ranges + 执行器**。
- **C++26 `std::execution`**（P2300R10 ✅）定义 senders/receivers 异步组合层——读并行代码时务必分清
  `std::execution::par`（17 的策略）与 `std::execution::sender`（26 的抽象）。
- 「为并行而设计的数值算法」继续以普通函数形式入库（如 `std::midpoint` 无分支中点，见 `12`）。

**工业实践与开源口径**
- **oneAPI Threading Building Blocks**（[oneapi-src/oneTBB](https://github.com/oneapi-src/oneTBB)）：libstdc++ PSTL 的官方后端；
  星数当日未能核验 ⚠️（GitHub API 限流，见 `00` 约定）。
- 游戏/金融等「计时敏感」团队普遍**禁用 PSTL 静默退化**的可能：CI 里跑一个 par 加速比冒烟测试，
  低于阈值直接 fail——§2 证明了这比任何文档承诺都可靠（做法推演，无单一出处 ⚠️）。
- 大数据并行归约的常青模式仍是 map-reduce 化的 `transform_reduce`：先在库内切分、后合并，TBB 的 work-stealing 在背后买单。

## 常见误区（实测/标注）

1. **「写了 `par` 就并行了」——实测没有**：单线程集合 {1}、计时打平（§2）；**先测加速比再谈并行**。
2. **「没装后端会编译失败或抛异常」——都不会**：静默串行是 libstdc++ 的选择（实测），错误报告为零。
3. **「`-fopenmp` 是给并行算法用的」——本机证伪**（§2/§3）：它喂的是 OpenMP pragma；PSTL 要的是 TBB ⚠️（changelog 待核）。
4. **「`reduce` 就是能并行的 `accumulate`」——语义前提不同**：`accumulate` 定序、可减可除；`reduce` 不定序、**必须结合**，`std::minus` 传进去就是定时炸弹（§4）。
5. **「`par_unseq` 比 `par` 多个参数而已」——契约重了一截**：谓词在 `par_unseq` 下连「同线程内被交错打断」都要能活：不能有共享可变态、不能依赖访存顺序、不能自己再开线程。
6. **「并行版对迭代器的要求一样」——注意**：多数并行算法要**随机访问迭代器**（`list::sort` 式容器无从受益），`par` 排序对 `deque` 也不如 vector 友好 ⚠️ 细节未逐条实测。
