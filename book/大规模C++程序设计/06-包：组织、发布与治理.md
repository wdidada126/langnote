# 06 包：组织、发布与治理

> 对应原书：第 7 章「包」（7.1 从组件到包 / 7.2 注册包前缀 / 7.3 包层次化 / 7.4 包隔离 /
> 7.5 包群 / 7.6 发布过程 / 7.7 main 程序 / 7.8 启动）。至此第二部分（物理设计概念）收官。
> 一句话：**组件管"一个抽象怎么立"，包管"一百个抽象怎么治"——从工程学进入管理学。**

## 核心概念速览（中英对照）

- **包** — package：共享一个全局名字前缀、处于同一物理层、按同一日程发布的一组组件；重用与治理的中间单位。
- **包前缀** — package prefix：包内一切外部可见名字的统一冠（组件文件名、类名、链接符号），注册后全局唯一。
- **包层级化** — package levelization：包间依赖也必须是 DAG；包 L 只依赖编号更小的包。
- **包隔离** — package isolation：用低层"协议层/公用设施包"承接两个包互相需要的共享物，破**包级**环。
- **包群** — package group：若干强协作包的联盟，共享设计文档与发布版本，但保持各自前缀。
- **发布过程** — release process：包从"开发中"到"入库冻结"的仪式：冻结→全量回归→版本递增→公告。
- **main 程序** — main program：物理设计中的特殊公民——可执行文件的根，独立成包、不供链接复用。
- **启动/静态初始化顺序灾祸** — startup / static initialization order fiasco：多翻译单元静态对象初始化次序未定义，须用引导机制驯服。
- **引导注册** — bootstrap registration：函数局部静态＋注册表（Meyers 单例式）保证跨包初始化次序无关性 ⚠️（本书解法细节以第 7.8 节原文为准）。
- **自底向上装配** — bottom-up assembly：包的层级天然支持"先发布地基、再盖楼"的里程碑排布。

## 动机：组件规则救不了"组件海洋"

7.1 的转折：假设全库 5000 个组件都守了第 3–5 章的规矩，仍有三件事无人管——

1. **命名生态**：每个组件都往全局名字空间投放符号，冲突与"谁允许你叫 util"变成政治问题；
2. **演化节奏**：组件级冻结发布不现实，需要一档"批量晋升"的容器；
3. **跨组件环**：A 包⇄B 包的环由十根组件级 include 箭头合成，逐根做第 5 章手术不如换**包级**术式。

包＝给物理设计装上"行政区"：有边界（前缀）、有宪法（层级）、有民政（发布）、有史书（版本）。

## 机制：包的五件套

**（1）前缀注册（7.2）**：新包立项先领前缀——组件文件、类、宏、链接符号一律冠之前缀
（BDE 式 `bdl`/`bsl` ⚠️ 例名凭开源仓库常识）。注册表杜绝"两个包抢一个名字空间"，
同时让 `objdump`/栈回溯里一眼看出符号出身——**名字空间即物理指纹**。

**（2）包层级化（7.3）**：把每个包的组件层号投影成包层号（取包内最大层号＋1），
再对包图做第 3 章同款 DAG 检查。工程含义：依赖朝下＝**只准依赖已发布的包**，
新包必须插进现有序列的某个空位，杜绝"平行宇宙"。

**（3）包隔离与协议层包（7.4）**：两包互用 → 把共享需求下沉为一个低层包
（数据下沉＝哑数据的包级版；行为上收＝管理者/回调的包级版）。附录 A 协议层模式在此复用，
见 [08](08-协议层、C兼容与依赖分析工具.md)。

**（4）发布过程（7.6）**：转述其要（⚠️ 细节以原文为准）——
候选包全组件过隔离测试＋累积回归；冻结后进入"只准修 bug 不准改接口"的发布通道；
版本号让上层包能精确声明依赖下界。**库不是目录树，是有版本合同的包集合。**

**（5）main 与启动（7.7–7.8）**：每个可执行文件一个专属 `main` 组件/包（不链接复用、不污染层图）；
跨包静态初始化用引导技术（构造时登记、显式 `initialize()` 阶段、或函数局部静态延迟）保证顺序安全。
🔧 最小示意：

```cpp
// 🔧 依赖注册式引导，规避静态顺序未定义（机制自写示意）
// 低层包 bsx：只认"注册者列表"
bsx::Registry& registry() { static bsx::Registry r; return r; }   // 首次使用时才构造
// 高层包 hix 的组件：把自己挂上去（在显式 bootstrap 阶段调用，而非静态构造期）
void hix_install() { registry().add({"hix", &hix_init}); }
```

## 算例：包图治理一轮（🔧 自写示意）

```text
治理前（含包级环）：            治理后（协议层包下沉）：
  app ⇄ net 互相 include          app(4) → net(3) → proto(1) ← io(2)
   └──────┘                        proto 装着从双方抽出的哑数据与共享契约
（1）前缀：app/net/proto 各领各的注册名，组件文件一律 `前缀_词.h`；
（2）层号：proto=1（依赖 bsx=0）、io=2、net=3、app=4——每根箭头朝下；
（3）发布：bsx → proto → io/net 并行 → app，周历即层历；
（4）评审：新需求"想 include 上层"＝一次**降级手术申请**，进变更队列而不是进代码。
```

## 发布检查单（7.6 的清单化改写，条目组织为笔者归纳 ⚠️）

- [ ] 包内全部组件：层级合法、无环、驱动绿（`09` 门禁口径）
- [ ] 对外只暴露注册前缀下的符号；私有片段头不在安装 include 路径
- [ ] 接口冻结公告：本期允许改什么、下期预计动什么
- [ ] 版本递增策略记录（修 bug 不动 ABI？接口演进走新符号？）
- [ ] 上层包的依赖下界随公告更新

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "目录结构就是包结构" | 包是**依赖图上的缩合点＋发布单位**；把目录重命名当成建包，前缀与层图不改＝没建 |
| "C++ 没有包关键字，所以无所谓" | 语言缺位恰恰要流程补位（前缀注册/层级 lint），这正是 BDE/CMake/Bazel 各自补法不同但都存在的根因 |
| "main 随便塞进哪个应用包" | main 不可复用、会污染包层图；7.7 判其独立成包 |
| "静态初始化顺序靠运气/靠链接序" | 平台/链接器变了就翻车；7.8 要求注册式引导（本目录 🔧 示例） |

## 权衡

- **包粒度**：太碎→发布接力赛累死协调人；太大→冻结半径伤及无辜。经验判据"一次变更评审一个包"（经验值 ⚠️）。
- **前缀税**：所有名字变长、样板变多；换来的是零冲突与可审计的出身——在 2014 年后被
  `namespace` 与模块部分抵消了语法成本，但**注册制**的政治功能无可替代。
- **冻结 vs 并行开发**：上层想改底层接口时，"包级合同"逼双方排队；这是特性不是缺陷（第 3 章的测试日程依赖它）。
- **包群**给了协作便利，但也最容易滑回"包群=一个巨型包"的违规互用——群内仍须 DAG。

## 相邻概念对比

- **vs 组件（章 02）**：组件对编译器可见（include/链接），包对**流程**可见（评审/版本/CI）。
- **vs 包隔离 vs 组件隔离（章 05）**：手法同源（下沉共享、中介管理），手术对象从"类布局"放大到"两组类的边界"。
- **vs 语言"包/命名空间"**：C++17 嵌套命名空间、2019 卷一的 "package" 都继承本节语义；
  Java package / Rust crate 是**语言内建**的同类物——C++ 把这份治理留给了流程与工具。
- **vs [../C++API设计.md](../C++API设计.md)**：API 书谈"库对外承诺什么"，本章谈"库对内如何组织兑现承诺的供应链"。

## 最新演进与工业实践

- **abseil 的"live at head"反例**：abseil 明确不做版本化发布，要求用户整库同日期快照（其官方指南观点，定性）——
  恰好证明 Lakos 的发布过程条款针对的是**不能 live-at-head 的多数组织**；两种模式各自成立的前提值得对比阅读。
- **Bazel/monorepo 的 package 概念**：BUILD 目录即包、visibility 即前缀注册＋层级化、target 依赖即包 DAG——
  Google 系用构建系统把 7.2/7.3 直接**机器化**；CMake 生态则以 `add_subdirectory`＋alias namespace＋
  `INTERFACE` 依赖图近似（约束力弱一档，需 lint 补）。
- **BDE 开源仓库**：包前缀（bsl/bdl/bde… ⚠️ 具体层表未逐项核对）、每包 `package.yml`＋层级配置、
  自研 ucm/mldb 构建链（名称凭仓库资料 ⚠️）是本章每节对应实物。
- **Conan/vcpkg 时代**：把"发布过程"外包给包管理器与 registry，但**包层级图仍在**——
  只是从"一个库内"变成"依赖树里"，循环依赖问题以"包版本互斥"的更凶形式回归（经验观察 ⚠️）。
