# 09 测试与构建的物理设计（横切重排 ⚠️）

> **口径声明**：本篇不是 1996 原书某一章，而是把散落各章的测试/构建线索横切重排成一篇
> （主要素材：4.1–4.10 隔离测试与增量测试、3.2 测试驱动条款、8.2/9.1 契约与 usage-based、
> 7.6 发布过程、附录 C 工具），主题在 2019 卷一才获得正式章号（第 5 章 Designing Components for Test ⚠️ 章名未逐字核实）。
> 一句话：**本书真正的杀手锏——测试不是物理设计的受益者，而是它的定义者。**

## 核心概念速览（中英对照）

- **测试驱动主程序** — test driver（`.t`）：每个组件自带的独立可执行回归程序，与 `.h/.cc` 并列的第三文件。
- **隔离测试** — isolated testing：链接闭包＝被测 `.cc`＋其直接依赖的**已测下层**；绝不为测试链接"兄弟"。
- **基于使用的测试** — usage-based testing：按操作类别（创建者/访问器/变更器/原语）×契约边界（最小/最大合法用法）系统化枚举用例。
- **增量测试日程** — incremental test schedule：0 层清零→1 层开工的层间准入条件，把 bug 平均存活期压到最短。
- **自文档化设计** — self-documenting design：契约写成规范注释，测试用例从注释机械导出——文档、代码、测试三位一体。
- **组件级覆盖率** — component-level coverage：语句/分支之外更严的"使用级"完备性：每个操作在其契约全域被测过。
- **物理可测性门禁** — physical testability gate：CI 强制"任何组件可单独构建并运行其驱动"，违例即红灯。
- **发布回归** — release regression：包冻结前跑全包组件驱动＋跨版本兼容检查（7.6 的自动化形态）。
- **构建描述** — build description：组件→目标→包的装配清单（BDE 的 package/component 文件系 ⚠️ 例名未核实）。

## 动机：4.1 比喻的工程化展开

第 3 章已给出理论：测不动＝设计坏了。但多数团队把这话当口号，因为看不到"怎么测"与
"文件怎么摆"的因果链。本篇把链条焊死：**测试金字塔的底部在这里被重定义为"组件驱动"**——
不是"多写单元测试"，而是"单元测试想写得动，依赖图必须先层级化"。
因果方向常被人搞反：不是有了好习惯才顺手测试，而是**物理设计不合格 ⇒ 测试在工程上不可行**。

## 机制：一套可照抄的操作手册

**（1）组件驱动的骨架（3.2/8.2 汇流）**：🔧（自写示意，风格仿 BDE 惯例）

```cpp
// baf_gadget.t.cpp —— 三段式：用法示例 + 缺省构造测试 + 逐操作测试
// USAGE 注释先写"最小/最大合法用法"——它同时是文档与用例清单（8.2/9.1）
int main() {
    ASSERTV(testDefaultConstructor());   // L0：创建者全集
    ASSERTV(testAccessors());            // L1：访问器 × 契约边界
    ASSERTV(testPrimaryManipulators());  // L2：变更器 × 回滚性质
    ASSERTV(testLevel3Usage());          // L3：跨操作序列不变式
    return 0;                            // 非零 = 该组件不可发布（门禁语义）
}
```

**（2）usage-based 用例推导（9.1 契约 → 表格）**：每个操作按
`前置条件违例 / 最小合法 / 典型 / 最大合法 / 后置条件断言` 五列展开；
不回滚型变更器额外测"异常后状态"。测试不是灵感活，是**填表活**——这是本书最反直觉也最可复制的主张。

**（3）层级排产（4.8）**：第 k 层组件的驱动里允许链接 0..k-1 层真实组件；
同层与上层只允许以声明形式出现（mock 以"接口＋低层实现"正规化，回扣 05 章）。

**（4）发布线（7.6）**：包内全部驱动绿 → 冻结接口 → 上层全量回归 → 版本递增。
CI 时代映射：每组件一个测试 target ＋ 每包一个聚合 job ＋ 主干层级 lint。

**（5）度量（4.13/附录 C）**：报表四件套——环数（必须为 0）、孤立组件数、累积依赖 Top-N、
驱动覆盖率（有驱动的组件/全部组件）。前三项机器可算，第四项最常被偷工减料。

## 从契约到用例：一行表怎么填（🔧 自写示意，接 `07` 的 interval 例）

被测操作：`Interval::setBounds(int lo, int hi)`，前置 `lo<=hi`，可回滚变更器。

| # | 用例族 | 输入 | 断言 |
| --- | --- | --- | --- |
| 1 | 前置违例 | lo>hi | 对象状态与调用前**逐字节一致**（可回滚承诺） |
| 2 | 最小合法 | lo==hi | 不变式成立；length()==0 |
| 3 | 典型 | (-5, 7) | 访问器全对 |
| 4 | 最大合法 | 区间端点全集边界 | 无溢出/无 UB |
| 5 | 后置条件 | 任意合法 | `lowerBound()<=upperBound()` 恒真 |

同一模板套到每个操作、再乘操作间的**序列不变式**（L3 组），就是 usage-based 的全部机械工作量。
经验线（数值为笔者归纳 ⚠️）：组件驱动的用例数常与"操作数×5＋序列组"同阶，估得出来才排得进日程。

## CI 门禁的最小拼法（🔧 自写示意，概念级）

```yaml
# 概念示意（不可直接跑；语法随 CI 产品而异）
jobs:
  per-component:            # 每组件：只链自己 + 下层已发布库（4.5 隔离测试）
    matrix: { component: [baf_gadget, biv_interval, ...] }
    steps: [ build $c.cc $c.t, run $c.t ]
  level-lint:               # 全库：-M 提依赖 → 查环/查层单调（03/08 工具）
  package-release:          # 仅包冻结分支：聚合回归 + 版本递增
```

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "覆盖率 100% 就是测完了" | 语句覆盖 ≠ 使用覆盖：契约边界（表第 1/4 行）可能一行没打 |
| "先赶进度，层级化以后补" | 依赖环是复利债（`01` 算例）；"以后补"= 在全库震的构建上再加测试代码 |
| "驱动=集成测试的缩小版" | 驱动的链接闭包经过刻意设计（只链朝下）；集成测试链接一切——两者失败含义完全不同 |
| "为测试把私有方法设成 public" | 直接摧毁封装评估（2.2）；用可测性设计（依赖注入/协议层）正道解决（4.4） |

## 权衡

- **驱动数量 vs 意义**：5000 组件 = 5000 个可执行文件；聚合跑与抽样跑的策略是团队政治问题。
- **usage-based vs 属性测试**：填表覆盖"契约内宇宙"，property-based 随机打"契约边界"——
  现代组合是 表驱动骨架＋快速检查器打边界（见"演进"）。
- **禁 mock 的教条风险**：本书对"链接兄弟来测试"近乎零容忍；对交互密集组件（网络栈）
  完全照搬会付出巨大 fake 成本——卷一在"为测试设计"章放宽了口径 ⚠️（未逐字核实）。
- **构建时间 vs 门禁密度**：每组件单独链接很贵；用静态库切片/测试对象复用降本，但别让复用破坏"隔离"定义。

## 最新演进与工业实践

- **gtest/Catch2/doctest/bdd 系**：驱动的组织形式从 main＋ASSERTV 换成分层 fixture，语义不变；
  "每组件一可执行"在多数团队软化为"每组件一 test target"。
- **Sanitizers 与覆盖率**：ASan/UBSan/TSan 把 10.3 时代的内存纪律变成每次 CI 的运行时审计；
  llvm 的 source-based coverage（`-fprofile-instr-generate`）让"驱动覆盖率"可精确到行（定性）。
- **property-based/fuzz**：libFuzzer＋OSS-Fuzz、rapidcheck 补 usage-based 的边界盲区；
  BDE 上游与 protobuf 等库均有 fuzz target 样本（定性）。
- **BDE 测试文化开源化**：bde 仓库每组件 `.t.cpp` 带完整 USAGE 块与层级化测试注释，
  是本书方法唯一的大规模公开活体（规模数字 ⚠️ 未逐项统计）。
- **构建侧**：Bazel 原生"每目标单测"语义、ctest＋标签分层、Ninja＋LTO 的时长折中——
  门禁的机器化程度远超 1996，但**规则本身**仍是 Lakos 那套（对照见章 10）。
