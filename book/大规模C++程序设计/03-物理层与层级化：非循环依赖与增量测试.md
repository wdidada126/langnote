# 03 物理层与层级化：非循环依赖与增量测试

> 4.9 测试一个复杂子系统 / 4.10 可测性与测试 / 4.11 循环物理依赖 / 4.12 累积组件依赖 / 4.13 物理设计质量）。
> 一句话：**把"依赖图无环"从美德升级为可执行的测试日程表。**

## 核心概念速览（中英对照）

- **物理层** — physical level：赋予每个组件的非负整数编号 L，满足"其全部物理依赖者编号 < L"。
- **层级化** — levelization：为整个组件森林求出一组合法层级编号的过程；无环是它可解的充要条件。
- **第 0 层** — level 0：不依赖任何组件的叶子层（如基本断言、哑数据类型），必须最先建成。
- **隔离测试** — isolated testing：测试某组件时，链接闭包里只有它自己（被测者 `.cc` 在列、其 `.h` 不在列）——证明其自足。
- **增量测试** — incremental testing：按 0,1,2,… 层推进的测试日程：做第 k 层时，0..k-1 层已全部测好入库。
- **可测性设计** — design for testability：设计期就把"能不能先测我"当作排产约束，而非事后补测试。
- **循环物理依赖** — cyclic physical dependency：A⇒B⇒A；在 C++ 里轻则同归于一次全量重编，重则根本无法编译。
- **累积组件依赖** — accumulated component dependencies：自底向上数"有多少组件最终依赖我"，即变更爆炸半径。
- **物理设计质量** — physical design quality：以层级数、累积依赖和、依赖扇出等指标刻画的图论打分。
- **聚合循环（慢性病）** — accumulation cycle：逻辑上无环，但 include 层面互相"顺手一拔"沉淀出的依赖环。

## 动机：4.1 的装配线比喻

Lakos 用制造业类比（转述 ⚠️ 非逐字）：没有工厂会等整机组装完成才第一次点火测试零件——
**先在零件台上单测，再上线位、再整机组**。软件却普遍反着来：单元测试晚于集成、
"好接口"因为必须攒齐一圈依赖才能跑起来而退化成"最后一起联调"。
第 4 章前半（4.2–4.3）借一个复杂子系统案例说明：**即使逻辑接口设计得干净，
只要物理上互相牵制，可测性照样归零**——这就是"接口好≠测得动"。

## 机制：从判环到编号到排产

**（1）非循环物理依赖（4.6）**：物理依赖图必须是 DAG。判据朴素——对每个组件跑一次
"只链接它自己"的可执行构建，失败即隐藏依赖；全库跑即拓扑排序的存在性证明。

**（2）层次编号（4.7）**：在 DAG 上自底向上取 `L(X) = 1 + max(L(所有 X 依赖的组件))`。
编号不唯一、不必最紧，但必须**单调**：依赖只许朝下。编号的工程含义：

```text
日程即层级：团队按层排产，第 k 层的开发启动条件 = 第 k-1 层全部发布；
门禁即编号 ：CI 规则"include 目标组件的层级必须 < 我"，机器可查；
沟通即坐标 ：架构评审时说"这在 7 层压到 3 层了"，不再争论"感觉不对"。
```

**（3）分层和增量测试（4.8–4.10）**：隔离测试在第 0 层是纯自下而上的地基工程；
往上每层测试时可**放心复用**下层的已测组件（它们不会反过来牵制你），
于是测试金字塔在此有了**物理**结构而非比喻结构。4.10 点题：可测性（testability）
是设计属性，测试（testing）是执行活动——前者不达标，后者只是昂贵的碰运气。

**（4）累积组件依赖与质量度量（4.12–4.13）**：对第 0/1 层组件特别记账——
被累积依赖数越高，一次误改的爆炸半径越大，所以**底层组件要比顶层更苛刻地冻结接口**。
4.13 给出的质量观感：层数太多→协调成本；太少（层内巨胖）→变更传染；
指标是"在合理层数下让累积依赖和最小"。🔧 直觉实验：50 个组件若呈 50 级细链 vs
压成 5 级×10 宽的层级，底层一个 ABI 变更的传染面完全不同（本章为定性推演 ⚠️）。

**（5）循环的成因预告（4.11）**：本章只判环、称其为重罪；**破环手术**整章留给第 5 章。
成因清单（双向 peer 使用、is-a、缺省实参、模板体、友元误用等）在 [04](04-破环惯用法：升级降级与九种技术.md) 展开。

## 算例：一张小图的判环、编号与记账（🔧 自写示意）

```text
组件图（箭头=物理依赖，X→Y 读作"编译 X 需要 Y"）：
        util ←─ ipc          widget → gadget ← hub
         ↑      │               ↑
         └──────┘ ←─ 边 ipc→util 正常；若再有人写 util→ipc 即成环

(1) 判环：对全图 DFS，发现回边 util→ipc ⇒ 报环清单 [(util, ipc)]，退回 `04` 章手术。
(2) 编号：手术去掉回边后拓扑递推
      L(util)=0, L(ipc)=1, L(gadget)=1, L(widget)=2, L(hub)=3
    单调性自检：每条箭头必须从高编号指向低编号。
(3) 累积依赖：自底向上累加"谁最终依赖我"
      util: 被 ipc/widget/gadget/hub 全依赖 → A=4   ← 冻结其接口，评审最严
      hub : 叶子 → A=1，接口可以激进演进
    同样的改动，落在 util 是核弹、落在 hub 是鞭炮——4.12 的账就是这么记的。
```

## 排产视图：层级如何变成日历

```text
第 1 周   ▓▓▓▓  第 0 层：util            （隔离测试：只链自己）✅ 门禁：0 环
第 2 周   ░░▓▓  第 1 层：ipc、gadget     （可链第 0 层真实件）
第 3 周   ··░░▓ 第 2 层：widget          （同层互不知晓——widget 不许 include gadget）
第 4 周   ···░▓ 第 3 层：hub ＋ 集成冒烟
关键路径性质：任何一层的"已完成"都是下一层的**免费**测试夹具——错误平均存活期 ≈ 一层工期。
```

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "有 mock 就不需要层级化" | mock 只能糊住接口，糊不住 include 闭包与链接闭包；隔离测试的本体是"只链我自己"（4.5） |
| "层级越深越优雅" | 深链=每次晋升都要等；4.13 的口径是"合理层数下累积依赖和最小" |
| "底层组件反正稳定，测试可省" | 被依赖最多=爆炸半径最大，0 层恰恰要**最重**的 usage-based 测试（`09`） |
| "逻辑依赖图无环即可" | 内联体/缺省实参造的隐含边不画在类图上（3.4）；以构建闭包为准 |
| "层号定终身" | 允许换层（先降级后升级），但要走变更流程——编号是合同（`04`） |

## 权衡

- **严格隔离测试 vs 集成信心**：每层都单测并不等于不需要集成测试——本书把"好测试"重排为
  "组件级用量覆盖 ＋ 系统级薄集成"，省下的成本必须**投回去**做 usage-based 覆盖，否则是裸奔。
- **层级数优化 vs 团队节奏**：层多利于并行排产、伤于发布接力赛；实践上以"每周能稳定晋升 2–3 层"为节律（经验值 ⚠️）。
- **累积依赖度量 vs 早期数据缺失**：项目初期图小指标虚高，需配合代码评审人工兜底。
- **编号固化 vs 演化**：允许组件换层（先降级破环再升级），但必须走变更流程——编号是合同不是注释。

## 相邻概念对比

- **vs 逻辑分层架构（N 层应用）**：那说的是运行期职责划分；此处是编译期依赖方向。二者正交且互不保证——逻辑上干净的三层照样可以物理成环。
- **vs 《软件架构设计》/整洁架构的依赖规则**：Uncle Bob 的依赖倒置与"层级化"同向，但 Lakos 给出的是**可机检**的 DAG 编号与构建门禁，粒度到文件。
- **vs [../C++API设计.md](../C++API设计.md)**：API 书谈"接口该长什么样"；本章谈"接口好也救不了错误的依赖物理性"。

## 最新演进与工业实践

- **Bazel 的 strict deps / visibility**：Google 系构建系统把"只能依赖显式声明的下层目标"做成机器强制，即 4.6/4.7 的商品化；CMake 侧可用 `target_link_libraries` 的 PRIVATE/PUBLIC 语义与 include 目录纪律近似，或用 include-what-you-use＋脚本查环。
- **clang-tidy / lint 工具**：llvm 仓库有头文件包含顺序与层间依赖的评审规则；社区有 lint 规则库可查"头是否用了未包含的类型（IWYU 违例）"（定性）。
- **CI 上的"只链我自己"作业**：把 4.5 的隔离构建做成每组件一个 CI target，是本书流程最可直接移植的现代实践——成本是 target 数量爆炸，收益是回归定位从"半天"到"一次构建"。
- **依赖图度量产品化**：NDepend 类工具（.NET 起家）、cpp-depend-analysis、madge 等对 C++ 生态相对薄弱，但"层图＋爆炸半径"指标已是通识（具体工具现状 ⚠️ 未逐一核实）。
