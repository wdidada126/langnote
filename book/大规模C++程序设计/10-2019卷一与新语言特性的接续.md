# 10 2019 卷一与新语言特性的接续（书外补编 ⚠️）

> **口径声明**：本篇不在 1996 原书中（原书止于第 10 章＋附录）。接续材料：
> ① Large-Scale C++ Volume I: Process and Architecture（Addison-Wesley，2019/2020，三部曲第一卷 ✅，
> 中译《大规模C++软件开发 卷1：过程与架构》魏文崟译，人民邮电出版社 2023-08，ISBN 9787115609779 ✅ 豆瓣 36600646）；
> ② 作者《Upgrading C++》（O'Reilly，2021 ⚠️ 未逐字核实）；③ C++11→C++23 语言演进对本书技术的替代/存续。

## 核心概念速览（中英对照）

- **卷一（Volume I）** — Large-Scale C++ Volume I: Process and Architecture：1996 书的现代化重写＋扩展，把"过程"提为第一分部。
- **模块** — C++20 modules：以编译后接口（BMI）替代文本 include；`import` 一次可见、不可重复污染。
- **头文件单元** — header units（C++23）：`import <vector>;`——不重写生态，先把文本复制换成二进制解析。
- **全局模块片段** — global module fragment：模块文件顶部 `module;` 之后的#include 区，与遗留头共存的桥。
- **编译防火墙（新解）** — compilation firewall：卷一把 pimpl 系技术正名，并分"实现分离/编译分离"两职。
- **破除物理循环** — breaking physical cycles：卷一专章（第 9 章 ⚠️ 章号凭通行记载），系统化 04 章九式。
- **为测试而设计组件** — designing components for test：卷一架构分部专章，对应本书 4.x＋本目录 09。
- **P0678 业务需求** — Modules business requirements（Bloomberg 提交）：模块须可加性/非侵入、支持更高层接口、不许脆弱传递包（2017 多伦多会议 ✅ 经微软出差报告核实）。
- **concepts 替代裸降级** — concepts replacing downgrading：以 `requires` 给模板参数化破环装上编译期契约。
- **std::expected** — P0323：值或错误的一等类型，改善跨防火墙的错误传播（wg21.link 实测重定向至 2022 年 r12 ✅）。

## 动机：30 年后重读，哪些变成了公理、哪些等着被替换

Lakos 在 2019 年亲自回答过这个问题（卷一即答案）：物理设计的**定理层**（DAG、层级、隔离测试、
包治理）一字不改地存续；**机制层**（include、前置声明、显式实例化）被语言逐项置换。
读法建议：把本目录 01–09 当作"不变量"，本篇当作"置换表"。

## 机制：五组"旧技术 → 新语言"映射

**（1）include 图 → module 图**
C++20 modules 把文本复制换成 BMI 依赖，`import` 天然做到"只暴露接口面、不传递内部 include"
——本书靠纪律＋工具维持的东西，编译器接管了一半（环检测变成模块循环的硬错误）。
🔧 本机实测（g++ 15.2.0 `-std=c++20 -fmodules`，仓库外临时目录，2026-09）：

```cpp
// mathx.cppm
export module mathx;
export int twice(int x) { return 2 * x; }
// main.cpp —— import 后可直接调用，无需任何声明
import mathx;
int main() { return twice(21) == 42 ? 0 : 1; }
```

编译链接运行通过（已实测）。附赠一个生动的"脆败"样本：在 main.cpp 里再手写一遍
`int twice(int);` 会被判 `redeclaring ... in global module conflicts with import`——
**重复声明这类物理事故从此不可表达**。但注意：模块图仍须人来层级化，
Bloomberg 当年（P0678 ✅）提的三条业务需求（可加、不脆弱传递、高一层接口）正是为了
让模块能承载本书式的包治理，而 GCC 实验性实现在 Windows/MinGW 上离生产仍有距离 ⚠️。

**（2）前置声明/IWYU → header units**
`import <vector>;`（C++23）让标准库只解析一次，编译器把文本复制换成可复用的二进制接口（BMI），
第 2 章"依赖提取"的收益被白送了一半。但**布局依赖不会消失**：pimpl 若不改成模块内部切片，
接口变更照样打穿 BMI——隔离仍是设计问题，不是语言问题（卷一"进阶编译防火墙"章主题 ⚠️ 章名未核实）。

**（3）降级（模板参数化）→ concepts**
04 章"降级"术的最大痛点是无约束模板的错误深渊与隐式依赖泄漏；
C++20 `requires` 把"参数化破环"升格为"带契约的参数化破环"，概念检查在定义点报错。
08 章协议层的静态多态化（CRTP/concept 约束）同获其益。

**（4）契约书写 → 类型系统**
9.1 的契约表格时代靠注释；`std::optional/expected`、`[[nodiscard]]`、
（演进中的）contract 设施把一部分契约写进签名——usage-based 测试的推导表因此更机械。

**（5）依赖提取器/自建工具 → 生态基建**
附录 C 的手工活已由 IWYU、clang 模块映射、构建系统级依赖声明（Bazel）分摊；
"层级 lint＋发布门禁"则商品化为 CI 常规件（见下节工业对照）。

## 置换总表：1996 机制 → 2020s 归宿（笔者归纳 ⚠️ 非原书内容）

| 1996 机制 | 现代归宿 | 残值 |
| --- | --- | --- |
| include 纪律/前置声明 | modules import／header units | 混用期与 C 头边界仍需原纪律 |
| pimpl/值句柄 | 存续（ABI＋变更半径）＋模块内部切片 | 布局传染依旧只有它能挡 |
| 模板降级破环 | concepts 约束的降级 | 显式实例化在 BMI 时代部分退休 |
| 依赖提取器（附录 C） | IWYU／构建系统声明图 | 跨构建系统的"层图审计"仍是自建居多 |
| 冗余包含卫哨 | **已死**（当年即被弃用 ⚠️） | 反面教材价值 |
| 层级编号/包发布/驱动测试 | **原样存续**，工具化为 CI 门禁 | 本书不朽部 |

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "modules = 官方包系统，本书可扔" | 模块只治**文本复制**；前缀治理、发布冻结、爆炸半径、隔离测试语言一概不管（P0678 ✅ 正是逼标准补这些的诉求） |
| "import 消灭 include 就消灭依赖" | BMI 依赖图与 include 图同构，环以模块循环形式**硬报错**——层级化从建议变法定 |
| "卷一只是再版" | 分部重排（过程提为第一分部）、专章新增（破环/性能/开源）；两本读序：1996 学手术，卷一学规程 ⚠️ 分部细节未逐字核实 |
| "头文件单位化后不需要接口设计了" | 导出的每个名字仍在 BMI 图上刻边——2.2/3.2 规则换皮重演 |

## 权衡

- **modules 的迁移税**：GMF 里旧头照旧传染；混用期"半模块"状态比纯 include 时代更难评审——
  这正是 P0678 反对"侵入式模块化"的现实注脚（✅ 需求出处已核实，评价为笔者立场 ⚠️）。
- **编译防火墙存续论**：modules 消灭"编译期文本传染"，消灭不了"实现期变更传染"
  （接口面过宽＝BMI 图过密），pimpl/句柄在 ABI 敏感处仍是唯一解——05 章结论原样平移，
  但动机权重从"省重编"移向"限爆炸半径＋稳 ABI"。
- **卷一 vs 1996 原书**：卷一更严整、例子更新，但 1996 版九式破环与"测试比喻"章的
  推导过程更手把手；两读不冲突（中译：1996 版见本目录两份单文件所指；卷一有中译 ✅）。

## 最新演进与工业实践

- **提案账本（逐项核实）**：P0323（std::expected，wg21.link→r12/2022 ✅，C++23 入库）；
  P0678（Bloomberg 三业务需求，2017 多伦多 ✅）；Modules TS 2017 进 PDTS、2020 入 C++20 ✅。
  **勘误**：有资料把 P1102/P1774/P2523 记作"modules 相关提案"——实测 wg21.link：P1102R2 是
  "Down with ()!"（Christensen/Bastien，2020），**与模块无关**；P1774 重定向至 2022 文档但未能
  核实标题，P2523 未核实——引用模块史料请以 P0581/P1102 系外的专文逐一另证 ⚠️。
- **BDE 开源（github.com/bloomberg/bde ✅ 存在）**：书-库互证 30 年；卷一的例子库即其公开化。
- **LLVM / abseil**：LLVM 主体仍以严格 include 治理＋header hygiene 为主，对全面转向 modules 持谨慎观望（截至笔者资料时间，定性 ⚠️）；abseil 亦曾公开表态暂不采用 modules（⚠️ 文档现状未逐字核实）。
- **CMake 生态**：CMake 3.28 起提供 C++20 modules 的实验性支持（FILE_SET/CXX_MODULES 相关语义），后续版本持续修补工具链缺口（本机 cmake 3.30.8；各版本行为细节 ⚠️ 建议对照官方文档核实后再用于生产）。
- **include-what-you-use**：与 clang 同步演进，仍是非模块代码库的主力清理器（定性）。
- **展望口径**：三部曲卷二/卷三（发布与过程 ⚠️ 内容传闻）与 1996→卷一的自我重写史，
  是"物理设计是常青学科、机制层是折旧资产"的最佳注脚。
