# 01 大规模开发的成本与全局思维

> 对应原书：前言 ＋ 第 0 章「概述」（0.1 从 C 到 C++ / 0.2 使用 C++ 开发大型项目 / 0.3 重用 /
> 0.4 质量 / 0.5 软件开发工具）。本章是全书问题域的总纲：**为什么 C++ 大项目的头号敌人不是算法，
> 而是"文件之间的物理关系"。**

## 核心概念速览（中英对照）

- **物理设计** — physical design：源文件/头文件如何切分、谁包含谁、如何链接成系统的布局学问；与类图层面的逻辑设计正交。
- **逻辑设计** — logical design：抽象、契约、继承、成员组织"是什么"的设计。
- **大 M 设计** — big-M design：以成百上千文件、数十人年、多年演进为前提做取舍的视角；"小 m"则是单文件、demo 视角。
- **可重用性** — reusability：代码被再次使用的难易，本书以**组件**为重用原子而非类。
- **可维护性** — maintainability：改一处需要理解/重建/重测多少地方的倒数度量。
- **可测试性** — testability：能否在隔离、增量、不依赖产品代码的前提下测试单元；本书主张它是物理设计质量的**操作性定义**。
- **编译依赖** — compilation dependency：改一个头文件迫使多少翻译单元重编译，是"物理债"的利息。
- **链接依赖** — linkage dependency：符号在多翻译单元间的一致性约束（ODR 前身语境、静态初始化顺序）。
- **全局名字空间污染** — global namespace pollution：宏/typedef/全局函数的物理级耦合源，第 2 章规则的动机。
- **自底向上/自顶向下** — bottom-up / top-down：重用靠自底向上攒层，分解靠自顶向下切任务，二者在包层级上会合。

## 动机：成本不在写代码，而在"改代码的人多、时间长"

Lakos 的开篇论断（转述其大意，非逐字 ⚠️）：小程序的设计问题在于算法与数据结构；
一旦系统进入**多年、多人、持续变更**的状态，主要成本转移为：

1. **理解成本**：新人要能局部地理解系统——"读一个组件不需要读一百万行"。
2. **变更成本**：改一个头文件，构建系统知道有多少 TU 要重编——这个数就是物理设计质量的第一信号。
3. **测试成本**：如果测试 X 必须先把 X 之外的半个系统链接进来，测试日程和错误定位同时崩溃。

这三项成本都由**物理布局**放大或抑制，而 1996 年前后的主流 C++ 教材（包括当时的"面向对象设计"）
几乎完全不谈物理侧。本书填的就是这块空白。

🔧 一个可以亲手感受数量级的实验（本机 g++ 15.2.0 已实测，Windows/MinGW）：
40 个客户端 TU 共享一条三层实现头链（`det3.h→det2.h→det1.h`），当 `det3.h` 变更——

```text
naive   （接口头直接 include 实现头）: 需重编 40 个 TU，串行 4.17 s
firewall（接口头只见 pimpl 前向声明 ）: 需重编  1 个 TU，串行 0.31 s
```

同一行代码改动，构建闭包相差两个数量级。把 40 换成 4000，就是 Lakos 说的"大 M"。

## 机制：全书的三层抽象阶梯

第 0 章给出贯穿全书的物理对象阶梯（后续各章逐一展开）：

```text
文件(file) ⊂ 组件(component) ⊂ 包(package) ⊂ [包群/子系统 ⚠️ 术语为本书后语
   .h/.cc/测试驱动     同前缀同层组件     治理与发布单位     口径]
```

- **组件**回答"重用的最小合法单位是什么"——不是类，是闭包（含测试）。→ 章 02
- **物理层**回答"依赖必须朝哪个方向"——只能朝下，图必须无环。→ 章 03/04
- **包**回答"很多组件如何被组织、冻结、发布"。→ 章 06
- **隔离**回答"值使用产生的编译期耦合如何剪断"。→ 章 05
- **逻辑设计**（第 8–10 章）在物理骨架就位后才展开——这个编排本身就是主张：
  没有物理设计的逻辑设计是空中楼阁。

与之配套的还有第 1 章预备知识（多文件编译模型、typedef、断言、迭代器、逻辑设计表示法）
与第 2 章基本规则（成员数据私有、卫哨、命名），它们是"地基上的水泥标号"，归入章 02 讲。

## 权衡：物理设计的每个决定都是三选多的折中

| 想优化 | 常见手段 | 反噬 |
| --- | --- | --- |
| 编译时间 | 前置声明、pimpl、拆分头 | 运行时间接层、内存分配、代码啰嗦 |
| 重用 | 细粒度组件 | 组件数暴涨、包治理成本、find-the-right-component 难 |
| 可测试性 | 强制层级化 | 为破环引入的中间抽象（哑数据/管理者类）看似"不优雅" |
| 一致性 | 包级冻结发布 | 上层开发被底层发布日程卡住 |

本书的独特立场：这些折中**必须显式记录在设计文档里**（附录 D 快速参考的用途），
因为"物理债"不像内存泄漏有症状，它的症状是三年后没人敢动那个目录。

## 最新演进与工业实践

- **C++20 modules 并未推翻本章问题域**：import 替代了文本复制，但"谁可依赖谁、发布单元、
  隔离测试"依旧要人来定；BMI 依赖图与 include 依赖图同构。详见 [10-2019卷一与新语言特性的接续.md](10-2019卷一与新语言特性的接续.md)。
- **构建并行化掩盖但不消灭物理债**：分布式编译/缓存（ccache、Bazel remote cache）能把 4.17s 摊薄，
  但依赖边的**语义半径**（改哪要测哪）无法被硬件买断——这正是 Lakos 强调可测性而非编译时间的原因。
- **Bloomberg bde**（github.com/bloomberg/bde）：开源的基础库群，包前缀 bsl/bdl/bbl ⚠️（例名凭公开仓库常识，未逐字核对版本布局）
  即第 0 章阶梯的实物标本；其文档明确沿用本书的 levelization 术语。
- **abseil / LLVM / Google C++ Style**：三家公开规范里都能看到"依赖必须朝下、禁止环、
  头文件自检"的家谱痕迹（分别见各章"最新演进"，此处不展开）。
- **Upgrading C++**（O'Reilly，2021 ⚠️）：同作者短文式作品，处理"老代码库现代化"，与本章"成本视角"一脉相承。


物理债的复利算例（🔧 自写示意推演，非原书数字）：某 1000-TU 项目把"接口含实现细节"的
naive 布局留给底层工具头，一次底层字段调整的构建闭包≈全部 TU；
每次迭代多花 20 分钟、每天 3 次，一年≈250 人时——**这还只是编译，不含重测与排错传染**。
Lakos 说的"大 M"，就是让这类账从"感觉不对"变成可填的表格。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "物理设计=编译优化问题，机器快了就无所谓" | 依赖边承载的是**语义半径**（改哪测哪），并行构建改变不了它（见 `09`） |
| "我们逻辑分层很清楚，物理不会差" | 逻辑 DAG 与物理 DAG 相互独立；原书 4.11 的案例口径专讲"逻辑干净、物理成环"（展开见 `03`/`04`） |
| "重用靠把函数写成通用工具" | 无测试驱动、无层级位置的工具函数会被依赖者反向绑架，重用变负债（`02` 组件判据） |
| "书太老，例子都是 90 年代编译器" | 技术层折旧（冗余卫哨/显式实例化），**度量层零折旧**（重编半径/环/层数今天照测，见 `10` 实测） |
