# 05 编译防火墙：隔离技术

> 对应原书：第 6 章「隔离」（6.1 从封装到隔离 / 6.2 C++结构和编译时耦合 / 6.3 局部隔离技术 /
> 6.4 整体的隔离技术 / 6.5 过程接口 / 6.6 隔离或不隔离）。
> 一句话：**封装管"别人看不见我的成员"，隔离管"别人编译时不需要复制我的布局"——两回事。**

## 核心概念速览（中英对照）

- **封装** — encapsulation：语言级的访问控制（private/protected），逻辑属性，不改变 include 闭包。
- **隔离** — isolation：物理属性——使用方编译时不必展开被用方的实现细节头文件。
- **编译期耦合** — compile-time coupling：值使用把对方的完整布局文本复制进自己每个翻译单元。
- **虚表耦合** — vtable coupling：带虚函数的具体类会把**整条基类链**所有基类的成员数据类型拖进自己的编译闭包——C++ 最阴的隐性依赖。
- **抽象接口类** — abstract (interface) class：纯虚基类，无数据成员；把 is-a 的编译耦合剪到只剩一张 vtable 指针。
- **抽象工厂** — abstract factory：以接口形态提供"造具体对象"的能力，把创建依赖隔离在工厂实现侧。
- **智能指针** — smart pointer：`shared_ptr<Impl>` 型句柄，值语义外壳＋指针语义内核，隔离且可拷贝。
- **值句柄** — value handle：手工版的智能指针隔离（Body 句柄模式），本书时代的叫法。
- **不透明指针** — opaque pointer / pimpl：成员收敛为一个前向声明指针，`.h` 零实现依赖——最常用防火墙。
- **过程接口** — procedural interface：一组自由函数代替成员方法暴露协作，切断方法体内联带来的双向 include。
- **局部/整体隔离** — local vs global isolation：只隔离某成员/某操作 vs 整个类改句柄化，代价与收益的量级差。

## 动机：封装得很好，为什么编译还是全库震？

6.1 用"从封装到隔离"的递进点破误区：把成员全设 private 只是**逻辑**封装；
只要 `.h` 里 `#include` 了实现所需的头，每个使用方仍在编译期持有你的全部布局——
改一个私有成员的数组大小，全库重编。6.2 进而解剖"C++ 结构与编译时耦合"：

- **值成员的传染**：`X m_` ⇒ 复制 X 布局（及其成员闭包）；
- **内联函数的传染**：成员函数定义在类内＝隐式 inline＝其体内值使用的全部类型都在你头文件里；
- **虚表耦合**：`struct Derived : Base` 即便空扩展，也继承 Base 的全部数据依赖，
  且**传递**——链条越长，一个叶子基类改动越像核弹。机器层的布局解释在
  [../深度探索C++对象模型.md](../深度探索C++对象模型.md)。

## 机制：两类隔离，五种墙

**（1）局部隔离（6.3）**：不动类的整体形态，只给泄漏点装墙——

- **抽象基类化**：把"互相知道"的具体继承改成"都指向接口"，配合工厂创建；
  is-a 的编译方向从"子认父"变成"双方各认接口＋第三方工厂认具体"。
- **成员指针化＋前置声明**：`X m_` → `X* m_`（手工管理）→ 智能指针（现代默认，见"演进"）。
- **抽象工厂**：当"造哪种具体类"本身是高层知识时，接口留低层、映射表放高层注册——
  创建依赖也被层级化。

**（2）整体隔离（6.4）**：整个类句柄化——

```cpp
// 🔧 baf_gadget.h —— pimpl 骨架（示意；已实测的构建收益见下节）
#pragma once
#include <memory>
class GadgetImpl;                       // 仅名字
class Gadget {
    std::unique_ptr<GadgetImpl> d_;     // 布局恒定：一个指针
public:
    Gadget();  ~Gadget();               // 析构必须出 .cc：unique_ptr 需要完整类型 deleter
    void spin();
};
```

值句柄（shared 语义）则解决"要能廉价拷贝"的场景；两者对比：unique 句柄防拷贝、shared 句柄
天然支持值语义但引入引用计数与一次堆分配。

**（3）过程接口（6.5）**：A 与 B 只需"协作"不需要"互为成员"时，把操作写成
低层可见的自由函数、实现放高层——两个类的头文件互不相见（回调思想的静态版）。
这同时是**模板友好**的：ADL 找到的过程函数让泛型代码只依赖表达式合法性，不依赖成员存在性
（与 [../C++模板元编程.md](../C++模板元编程.md) 的 generic programming 观衔接）。

**（4）隔离或不隔离（6.6）**：不是所有类都配一面墙。判据（转述 ⚠️）：
被隔离者是否**频繁变更且被广泛值使用**；隔离收益≈重编半径×变更频率，墙本身有
间接层、堆分配、ABI 简化三类恒定成本。

## 布局算例：虚表耦合到底复制了什么（🔧 自写示意）

```cpp
struct Base1 { std::array<double, 8> a_; };      // 布局 64B
struct Base2 : Base1 { Widget w_; };             // Widget 又含 3 个值成员…
struct Derived : Base2 { };                       // 空扩展！
```

`Derived` 虽然"什么也没写"，其每个使用方的翻译单元里都要**依次展开**
`Base1→Base2→Widget→…` 的完整布局（6.2 的主弹头）；
改 `Widget` 一个私有成员，`Derived` 的全部使用者重编——而代码评审里你只看到一个空 struct。
处方对照：把"继承链"换成"接口链（纯虚＋指针）"后，`Derived.h` 只剩一个 vtable 指针，
闭包长度从 O(链长×成员闭包) 降到 O(接口声明)。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "pimpl 到处无脑上" | 6.6 的判据是"被广泛值使用×频繁变更"；叶子小类上墙只添堆分配与间接 |
| "unique_ptr 成员＝自动隔离" | 析构必须落在 `.cc`（否则前向声明类型不完整直接编译失败）；墙是三件套不是成员声明 |
| "抽象类＝隔离" | 只有**纯虚＋零数据**的接口类才隔离；带成员的抽象基类照样传染（8.3 封装程度谱系） |
| "modules 来了，墙可以拆了" | BMI 消灭文本复制，不消灭实现期变更传染与 ABI 债——见 `10` 存续论 |

## 权衡

- **运行时间接与分配**：每次调用穿指针、构造多一次 malloc——小对象高频场景慎用整体隔离。
- **可见性下降**：编译器看不见跨墙代码，内联与 SRO 失效；LTO 部分回血但改变不了依赖语义。
- **写起来啰嗦**：pimpl 的构造/析构/拷贝五件套（C++11 后 move-only 缓解）；错误处理路径翻倍。
- **与"逻辑上是一体"的张力**：拆墙设计本质是承认"我的实现细节是公共契约的一部分"——
  6.6 的清单就是帮你拒绝这种投降的地方。

## 相邻概念对比

- **vs [04](04-破环惯用法：升级降级与九种技术.md) 破环**：不透明指针在两边都出现，但使命不同——
  破环术解决**方向**（箭头掉头），隔离术解决**重量**（布局复制）。先判环再谈墙。
- **vs [../C++API设计.md](../C++API设计.md) 的 pimpl**：Reddy 的第一动机是**二进制兼容**
  （.so 不换 ABI），Lakos 的第一动机是**编译闭包与可测性**；同一堵墙，两种房产证。
- **vs 封装（private）**：private 防"用错"，防火墙防"编不动"；逻辑/物理再次对照。
- **vs 虚表/多态**：抽象接口类用一次 vtable 间接换掉整条继承链的编译耦合——虚函数在此是**物理**工具而非仅逻辑工具。

## 最新演进与工业实践

- **本机已实测（g++ 15.2.0，MinGW，2026-09，仓库外临时目录）**：40 客户端共享三层实现头链，
  改最底层实现头后，naive 接口需重编 40 个 TU（串行 4.17s），pimpl 接口只需重编 1 个 TU（0.31s）——
  6.4"整体隔离"的收益在 30 年后的工具链上仍是**两个数量级**。
- **std::unique_ptr/std::make_shared 标准化**：本书时代的裸指针句柄全部现代化为智能指针；
  Item 系建议（[../Effective_Modern_C++.md](../Effective_Modern_C++.md)）与 6.3 智能指针节直接互认。
- **C++23 header units（`import <vector>;`）**：以 BMI 替代文本复制，隔离的是"解析成本"而非"布局依赖"——
  接口稳定性仍要 pimpl，两者不互斥。见 [10](10-2019卷一与新语言特性的接续.md)。
- **std::expected（P0323，wg21.link 实测重定向至 2022 年 r12；随 C++23 入库）**：跨墙的错误传播
  不再被迫用异常或出参，值句柄类 API 的"错误路径啰嗦"权衡被显著改善。
- **工业样本**：Qt（d-pointer 即值句柄化的产业化）、Chromium/LLVM 对公共头暴露 STL 布局的限制性规范、
  abseil 的 `absl::` 不透明类型（如 `Cord` 的自管句柄）——墙的名字变了， anatomy 没变（定性描述）。
