# 02 组件：物理设计的原子单位

> 对应原书：第一部分「基础知识」第 1 章 预备知识、第 2 章 基本规则 ＋ 第二部分第 3 章 组件
> （3.1 组件与类 / 3.2 物理设计规则 / 3.3 依赖关系 / 3.4 隐含依赖 / 3.5 提取实际的依赖 / 3.6 友元关系）。
> 一句话：**类是逻辑设计的原子，组件是物理设计的原子；本章规定"什么才配叫一个组件"。**

## 核心概念速览（中英对照）

- **翻译单元** — translation unit：预处理后交给编译器的单一文本＋其内部声明；C++ 独立编译的物理边界。
- **组件** — component：一个对外 `.h` ＋ 一个实现 `.cc` ＋ 一个测试驱动 `.t` 的闭包；可重用、可独立编译、可隔离测试的最小单位。
- **组件测试驱动** — component test driver：随组件自带的回归程序；"没有测试驱动的组件不合法"。
- **包含卫哨** — include guard：`#ifndef` 三件套防重复展开；卫哨名须全库唯一，防止不同头互相"吃掉"。
- **冗余包含卫哨** — redundant include guard：在每个使用处再包一层宏以跳过整个文件——90 年代预处理提速 hack，现代反模式。
- **前置声明** — forward declaration：只给名字不给布局；把"值使用"降级为"指针/引用使用"从而削依赖。
- **物理依赖** — physical dependency：编译/链接 A 前必须纳入构建的 B 集合；**传递**（A⊃B⊃C ⇒ A⇒C），且沿 include 与链接两条通道。
- **逻辑依赖** — logical dependency：接口文本上的概念引用；可以物理上零包含（如只以 `void*`/模板参数出现）。
- **隐含依赖** — implicit/hidden dependency：内联函数体、默认实参、宏、模板体展开带来的"看不见"的 include 需求。
- **依赖提取** — dependency extraction：逐条删 include、换前置声明、挪声明位置，把物理依赖压到逻辑必需的下界。
- **友元关系** — friendship：授予实现访问而非类型可见性；Lakos 辨析其**不引入额外物理依赖方向**但影响封装评估。
- **基本规则** — basic rules：成员数据一律 private、不污染全局名字空间（宏/typedef 慎用）、自文档化、命名规范等。

## 动机：C++ 的"文件"不是设计单位

第 1 章先用多文件程序解剖（0.x/1.1）摆出事实：C++ 以翻译单元为单位编译，
`.h` 是**被文本复制**进每个使用者的契约（这与 [../C++语言的设计与演化.md](../C++语言的设计与演化.md) 里
Stroustrup 对 include 模型的解释互为表里）。于是：

- 逻辑上"我用一下你的类"，物理上可能变成"我编译时复制了你整个 include 闭包"；
- 按类组织文件（一个类一个对）会把**一个概念的实现劈散到多个编译单元**，制造链接级隐忧；
- 按功能大杂烩组织文件（"util.h 包治百病"）则制造百万级复制的依赖黑洞。

所以需要一个新的物理原子——组件——并同时给出它的宪法（基本规则）。

## 机制：组件的构成判据与依赖演算

**（1）物理设计规则（3.2）**，本书核心条款的转述（⚠️ 措辞为笔者归纳，非逐字）：

- 每个组件有唯一的对外 `.h`（入口契约）与至多一个 `.cc`；其余 `.h` 一律视为私有实现片段。
- 每个组件配一个测试驱动（`.t`），**独立编译链接**即可运行——这是"自足性"的可执行定义。
- 一个组件（除个别受限情形外）只呈现**一个**主要抽象；相关自由函数并入同一组件而非拆散。
- 组件之间只能**单向**依赖：同层禁止互用（互用即环的前兆，处理办法见 [04](04-破环惯用法：升级降级与九种技术.md)）。

**（2）依赖关系（3.3–3.5）**：先定义 `X 物理依赖 Y ⇔ 编译或链接 X 需要 Y 在构建闭包内`，
再区分**使用**的三种强度——

```text
值使用   （要布局/要调用） → 必须 include，构成物理依赖
指针使用（仅存/仅传指针）   → 前置声明即可，不构成物理依赖（链接期除外）
创建/销毁（new/delete）     → 需要完整类型，哪怕接口里只出现指针
```

依赖提取即按此表逐 include 审问"你真 needed 吗"。🔧 示意：

```cpp
// baf_persongrep.h —— 提取后的最小时刻
#include <string>          // 值使用：返回 std::string ✅ 必需
class bam_employer;        // 仅持有指针：前置声明 ✅ 不 include bam_employer.h
class Baf_PersonGrep {
    bam_employer* d_emp;
public:
    std::string fullName() const;   // 若改成 inline 调 d_emp->...，立刻漏依赖 ⚠️
};
```

**（3）隐含依赖（3.4）**：内联成员函数体、缺省实参、默认拷贝语义、模板体内引用——
都会把"接口上看不见的类型"拖进 include 闭包。Lakos 的解药：少 inline、缺省实参降级为重载、
模板体外置或显式实例化（后者在 2019 卷一里被重新讨论 ⚠️）。

**（4）基本规则（第 2 章）**：public 数据成员=物理级泄漏（任何人改布局都重编你）；
全局 `#define`/`typedef` 是跨组件的时间炸弹；卫哨名要"路径化唯一"；
冗余包含卫哨当年为省几秒预处理，今天换来的是"卫哨漂移"类假编译错误——**弃用**。

## 权衡

- **组件粒度**：越细越可重用、可测，但组件数×发布成本上升；经验线"一次评审能看完一个组件"。
- **前置声明 vs include**：前者省构建闭包，后者省"改前置声明波及所有使用者"的维护风险；
  接口只出现指针/引用时选前者（这就是后来 pimpl 的最小形态，见 [05](05-编译防火墙：隔离技术.md)）。
- **唯一 .h 的纪律成本**：把私有片段藏进 `.cc` 会让文件变长、IDE 跳转变笨——用构建工具补偿，不用破例补偿。
- **友元的开放**：给足实现可见性但不给 include 方向；代价是封装评估（哪些函数能碰我的布局）失去语法强制。

## 组件解剖图与卫哨模板（🔧 自写示意）

```text
组件 baf_gadget 的合法形态（3.2 条款的空间表达）
├── baf_gadget.h        对外契约：仅此一个头可被包外 include
│     #ifndef INCLUDED_BAF_GADGET   ← 卫哨名=路径化唯一（2.4），全库不许撞名
│     #define INCLUDED_BAF_GADGET
│     ...
│     #endif
├── baf_gadget.cc       实现：可 include 一切"朝下"的头（含自己的 .h 以防自足性缺失）
└── baf_gadget.t        测试驱动：独立编译链接即可运行 = 组件自足性的证明
```

依赖提取的一轮完整审问（3.5 流程的压缩复述）：

1. 对头文件里每个 `#include "…"` 提问：删掉还能编译吗？（试删→编译器回答）
2. 不能编译时再问：用到的类型出现在**值/基类/模板实参**位置，还是仅**指针/引用/形参**位置？
3. 仅指针/引用 → 换前置声明，include 移入 `.cc`；值 → 承认物理依赖，登记进层级图；
4. 顺手检查宏与缺省实参——它们是最常见的"漏网值使用"。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "一个类一对文件天然正确" | 互相值使用的两个类拆两组件＝自造环；同组件多类或升级处理（`04`） |
| "卫哨名随手 BIG_HEADER_H 即可" | 撞名会让第二个头被"吃掉"——症状诡异（缺符号），病因在 2.4/2.5 条款 |
| "include 越少越先进" | 目标是**恰如其分**：该 include 的不 include 是脆弱依赖，迟早以"传递 include 突然断裂"的形式爆炸 |
| "友元破坏物理设计" | 友元给可见性不给 include 方向（3.6）；它破坏的是**封装评估**，别混罪名下狱 |
| "测试驱动是测试部门的事" | 驱动缺失＝组件自足性无法证明，3.2 判它不合法——这是**设计**问题 |

## 最新演进与工业实践

- **include-what-you-use（IWYU）**：clang 工具，把 3.5"依赖提取"自动化（输出该删/该加/该改前置声明的清单），可视为 Lakos 手工流程的现代执行器；LLVM/Chromium 均在其 CI 中使用过（定性说法）。
- **Google C++ Style Guide**：要求"include 自己的头文件放最前、头文件必须自足（self-contained）、用 `<sys/types.h>` 式绝对路径"——即 2.4 卫哨与自足原则的规范后代。
- **abseil 依赖政策**：公开声明公共头文件只暴露必要依赖、鼓励前向声明与瘦接口（docs/abseil 依赖 FAQ，定性），与 3.5 同一血统。
- **BDE 实物**：每个组件 `.h/.cpp/.td.cpp` 三件套＋`bsc` 构建描述 ⚠️（工具名凭开源仓库印象），测试驱动条款 3.2 的忠实执行。
- **C++20 modules 下的等价物**：一个 module 接口单元 ≈ 一个对外 `.h`，但"实现切片不自动隔离测试"——组件纪律仍然要人守，见 [10](10-2019卷一与新语言特性的接续.md)。
