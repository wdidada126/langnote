# 04 破环惯用法：升级、降级与九种技术

> 对应原书：第 5 章「层次化」（5.1 循环物理依赖的一些来源 / 5.2 升级 / 5.3 降级 / 5.4 不透明指针 /
> 5.5 哑数据 / 5.6 冗余 / 5.7 回调方法 / 5.8 管理者类 / 5.9 分解 / 5.10 升级封装）。
> 一句话：**第 3 章判环是诊断学，本章是外科学——九种术式，各治一种成因。**

## 核心概念速览（中英对照）

- **循环物理依赖** — cyclic physical dependency：组件 A、B 互相处于对方构建闭包；层级编号无解，隔离测试失效。
- **对等互用** — peer usage：两个同层类互相做值使用，最常见的环源。
- **升级** — upgrading：把互为依赖的两个抽象合并进同一组件（或提升到共享组件），环内化。
- **降级** — downgrading：把被依赖者的"名字"参数化（模板/类型形参），令头文件不再含其定义。
- **不透明指针** — opaque pointer：类里只存 `X*`＋前置声明，`X` 的完整定义推迟到 `.cc`——破环与隔离的双重利器（pimpl 的前身形态）。
- **哑数据** — dumb data：砍掉行为、只剩公共数据的低层类型；把"共享的概念"降格为"共享的字节"。
- **冗余** — redundancy：在低层重新声明一个更小的等价契约，容忍信息重复换依赖单向。
- **回调方法** — callback method：低层留钩子、高层注入操作，把"低层需要知道高层"反转为参数。
- **管理者类** — manager class：新建中间类同时持有 A、B，A⊄B、B⊄A，双向箭头变两根单向。
- **分解** — decomposition：把一个类劈成"低层核心半"＋"高层扩展半"，让不同依赖各归其层。
- **升级封装** — upgrading encapsulation：多个纠缠组件整体打包升为一包/一组件，环降为内部组织。
- **类级数据** — class-level data：静态成员/全局单例带来的隐形向上引用，常靠提升为调用者数据破环。

## 动机：环为什么必然长出来

5.1 列举的成因（按已核实节名整理 ⚠️ 细节以原文为准）：

1. **对等互用**：`Car` 存 `Engine`、`Engine` 报告回 `Car`——写的时候各是一行 include。
2. **is-a 滥用**：派生要 include 基类，天经地义；一旦基类接口出现派生类型（工厂自产、
   协变返回**值**、默认实参），箭头立刻掉头成环。
3. **缺省实参**：`void f(Color c = Color())` 把 `Color` 的定义拖进本组件头文件。
4. **类级数据/单例**：静态成员的初始化引用高层符号，物理引用藏在 `.cc` 里，评审看不见。
5. **模板体**：模板头文件里值使用谁，就把谁拖进所有实例化者的闭包。

环的代价在第 3 章已量化：同生共死的重编半径、测 A 必先建 B 的死锁式日程。
**破环不是洁癖，是把排期表和 CI 从对方手里赎回来。**

## 机制：九种术式速查

🔧 以下代码均为自写示意。以"对等互用 `Gui` ⇄ `Doc`"为主诉样本：

| 术式 | 节 | 刀法 | 适用判断 |
| --- | --- | --- | --- |
| 升级 | 5.2 | `Gui`、`Doc` 合成一个组件，环成内部事 | 两者其实是一个概念的两半；体量合得拢 |
| 降级 | 5.3 | `template<class DocT> class Gui { DocT* d; }` 头文件不含 `Doc` | 被用者可以晚绑定为类型形参 |
| 不透明指针 | 5.4 | `Gui { class Doc* d_; }` 仅前置声明 | 值使用其实只发生在 `.cc` 内部 |
| 哑数据 | 5.5 | 抽出 `struct DocState {…}` 放 0 层，双方依赖它 | 互相分享的只是**数据**不是行为 |
| 冗余 | 5.6 | 低层复制一份自己需要的最小子契约 | 上层契约稳定、低层不能等它 |
| 回调 | 5.7 | `Gui::setRefresh(fn)`，`Doc` 不认 `Gui` | 低层需要"做某事"，不需要"是某人" |
| 管理者类 | 5.8 | `App` 持 `Gui`＋`Doc` 并转接二者消息 | 环是"第三者撮合"出来的 |
| 分解 | 5.9 | `Gui`→`GuiModel`(低)＋`GuiView`(高)，各自单向 | 一个类身上压着两层的职责 |
| 升级封装 | 5.10 | 三包整编为一个包群/高层包 | 环长在**包**边界上而非类 |

三个高频样本的机制展开：

**（a）class-level data 上提**：单例 `Session::current()` 被 0 层工具引用 → 把"会话"降级为
调用者传入的参数（或回调上下文），依赖箭头从"底层仰望全局"变回"高层注入低层"。

**（b）is-a 环的标准拆法**：基类 `Shape` 想 `clone()` 返回**值** → 必然 include 派生。
术式：返回抽象指针（配合 [05](05-编译防火墙：隔离技术.md) 的抽象工厂），或用"降级"把派生类型
作模板参数——这正是 2019 卷一把 **concepts＋模板参数化**列为破环首选的原因（⚠️ 口径见卷一第 9 章说法，本次未逐字核实）。

**（c）回调的最小形**：`struct Observer { virtual void notify() = 0; }` 放低层，
高层实现它、构造时注册——依赖方向与调用方向解耦（C++11 后可用 `std::function` 免掉虚表，见"演进"）。

**（d）管理者类的最小形**🔧（自写示意）：`Gui`⇄`Doc` 的环其实是"窗口刷新要读文档、
文档变更要通知窗口"——谁都不该拥有谁：

```cpp
// 低层两组件：互不知晓
class Doc  { public: void onChange(std::function<void()>); /* 只认回调 */ };
class Gui  { public: void show(const std::string&);        /* 只认字符串/接口 */ };
// 高层管理者：环的两条边在这里被拆成两根朝下的箭头
class App  { Doc d_; Gui g_;
  public: App() { d_.onChange([this]{ g_.show(d_.summary()); }); } };
```

**（e）分解的两刀法**🔧：`GuiModel`（数据与不变式，低层）＋`GuiView`（渲染，高层，持有 Model）。
判据：类里总有一批成员函数只碰"数据半"、另一批只碰"呈现半"——缝线已经写在你脸上了。

## 术式选择决策树（口述版）

1. 环里的两坨是不是**同一概念的两半**？→ 是：升级/升级封装（5.2/5.10）；
2. 互相需要的只是**数据**？→ 哑数据下沉（5.5），不够再加冗余（5.6）；
3. 低层需要高层**做事**而非**知道名字**？→ 回调/过程接口（5.7，跨到 6.5）；
4. 低层只是引用高层**类型**？→ 不透明指针（5.4）或降级参数化（5.3）；
5. 是第三者把双方**撮合**成环？→ 管理者类（5.8）或分解（5.9）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "模板化＝万能破环" | 模板体内值使用照样拖依赖（3.4/10.4）；参数化只是把箭头推迟到实例化点 |
| "pimpl 是隔离专用，与破环无关" | 5.4 明确把不透明指针列为破环术：指针位置不需要完整类型 |
| "环必须当场根治" | 允许"临时冗余"止血（低层先复制小契约），但要在图上挂账，择期手术 |
| "升级后没有环就赢了" | 巨型组件的**内部**依赖仍需层级注释，否则半年后再裂出环（4.12 累积记账） |

## 权衡

- **升级**最干脆但反重用：合并后的巨型组件未来更难拆——"环内化"要求你真的想清楚了它们是一个概念。
- **降级（模板化）**把编译期依赖换成**实例化点**依赖：头文件瘦了，但错误信息胖了、编译更慢、
  且模板体内值使用会**照样**拖入依赖（5.1 的教训）；泛型不是万能防火墙。
- **哑数据/冗余**主动放弃"单一事实来源"，用一致性纪律（或生成代码）补账。
- **回调**引入生命周期与悬垂风险（注册方与被注册方谁先死），需要配对注销或弱引用语义。
- 术式选择的第一问永远是："**这个环的逻辑依赖是真的吗？**"——很多环源于把"协作"写成了"拥有"。

- **vs DIP（依赖倒置原则）**：回调/降级即 DIP 的物理化执行；Lakos 多给的是"倒置后箭头仍必须朝下"的层级记账法。
- **vs [../C++20设计模式.md](../C++20设计模式.md)**：观察者/中介者等模式章谈运行期协作结构，本章谈**include 图**手术；同一张 UML 图可对应两种物理结局。
- **vs [../C++模板元编程.md](../C++模板元编程.md)**：Abrahams 讲参数化的机制极限（哪里会漏依赖），本章讲何时该用它破环。
- **vs 第 6 章隔离**：破环解决"方向"，隔离解决"重量"（值使用带来的编译期复制）；不透明指针同时是两边的药。

## 最新演进与工业实践

- **concepts 取代"裸模板降级"**（C++20）：`template<class T> requires DocLike<T>` 让降级术的参数化
  有了编译期契约检查，错误在实例化点而非深渊模板体里报出——把本章最重的权衡（泛型错误可读性）显著削薄。
- **std::function / lambda 注入**：回调术式在 C++11 后少建一层抽象基类，`std::function<void()>`
  即可携带上下文；代价是堆分配与类型擦除开销（见 [../Effective_Modern_C++.md](../Effective_Modern_C++.md) Item 34 系讨论）。
- **2019 卷一"Breaking Physical Cycles"专章**：把本节九式重排为升级（upgrading）/降级（downgrading）/
  数据隐去（redaction，即把惹祸数据成员移出接口）等正式分类，并加入基于**协议层**的破环（见 [08](08-协议层、C兼容与依赖分析工具.md)）⚠️（分节名未逐字核实）。
- **工业对照**：abseil 的"用 `std::function`/接口注入打破 cc 层环"实践、LLVM 的 `llvm/Support`
  低层哑数据下放（`StringRef` 类 `struct` 群）都是降级/哑数据术的量产形态（定性）。
