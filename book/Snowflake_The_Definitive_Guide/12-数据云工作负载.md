## 核心精讲

### 1. 基准实验的正确姿势（书中 SQL 实抓 ✅，p.372/p.392–403 逐句）
```sql
-- p.372 上下文与"关缓存"（实抓 ✅）
USE ROLE SYSADMIN;
USE WAREHOUSE COMPUTE_WH;
CREATE OR REPLACE DATABASE DEMO12_DB;
CREATE OR REPLACE SCHEMA CYBERSECURITY;
ALTER SESSION SET USE_CACHED_RESULT = FALSE;

-- p.392 基表 + 零复制克隆对照（实抓 ✅）
CREATE OR REPLACE TABLE BASETABLE AS
    SELECT * FROM SNOWFLAKE_SAMPLE_DATA.TPCH_SF100.LINEITEM;
CREATE OR REPLACE TABLE CLUSTEREXAMPLE CLONE BASETABLE;
ALTER TABLE CLUSTEREXAMPLE CLUSTER BY (L_SHIPDATE);
SELECT SYSTEM$CLUSTERING_INFORMATION('CLUSTEREXAMPLE','(L_SHIPDATE)');  -- p.392
SELECT SYSTEM$CLUSTERING_INFORMATION('BASETABLE','(L_SHIPDATE)');       -- p.393 未聚簇对照

-- p.394 搜索优化对照面（实抓 ✅）
CREATE OR REPLACE TABLE OPTIMIZEEXAMPLE CLONE BASETABLE;
ALTER TABLE OPTIMIZEEXAMPLE ADD SEARCH OPTIMIZATION;

-- p.396–399 三表同查询：点查 L_ORDERKEY；p.397 再叠聚簇键前缀范围
SELECT * FROM CLUSTEREXAMPLE
    WHERE L_SHIPDATE >= '1992-12-05' AND L_SHIPDATE <= '1993-02-20'
      AND L_ORDERKEY = '363617027';
```
三条方法论（本章真正的可迁移知识）：
1. **关掉结果缓存再比性能**，否则第二次起跑的是缓存不是引擎（会话级参数，
   https://docs.snowflake.com/en/sql-reference/sql/alter-session ✅200）。
2. **用零复制克隆造对照表**：`CLONE` 秒级、不占存储（第 7 章机制），是"同一份数据、不同物理布局"的
   天然 A/B 架。
3. **量具内置**：`SYSTEM$CLUSTERING_INFORMATION` 给微分区重叠度（第 9 章主场），点查收益看查询 Profile。
   本章把第 9 章的结论用实验复述了一遍：聚簇帮**范围过滤**（L_SHIPDATE），搜索优化帮**点查/低基数**
   （L_ORDERKEY），互不越界 ⚠️（转述，官方：https://docs.snowflake.com/en/user-guide/tables-clustering-keys ✅、
   https://docs.snowflake.com/en/user-guide/search-optimization-service ✅）。

| 负载 | 典型形态 | 依赖的前章机制 |
| --- | --- | --- |

### 3. 多负载共存的治理三件套
- **仓库隔离**：每类负载独立虚拟仓库（ETL/BI/DS/共享各一），互不抢算力、账单可归因（第 2/8 章）。
- **对象分层**：raw→curated→consumption 的 schema 布局；湖仓界同款叙事是 medallion →
  [../Delta_Lake_Definitive_Guide/08-湖仓架构-Medallion.md](../Delta_Lake_Definitive_Guide/08-湖仓架构-Medallion.md)。
- **权限与共享**：负载间用角色切开，对外用安全数据共享而非搬数（第 5/10 章）。

### 4. Unistore 与其身后事（⚠️ 转述）
书稿时代（2022）Unistore（把行存分析表与键值事务表统一）尚在承诺/早期形态，作者以展望口径处理 ⚠️。
其思想的后继是 **Hybrid Tables**（官方 SQL 已实点可查：
https://docs.snowflake.com/en/sql-reference/sql/create-hybrid-table ✅200）：面向应用的低延迟
CRUD 表，与列式分析表同库共存——"数据云服务运营负载"的官方现行答案 ⚠️。
Unistore 品牌本身在官网已淡出（未见官方"更名公告"URL 可核 → 仅 ⚠️ 转述，不引链接）。

### 5. 复制与故障转移：跨区负载的落地件（任务书 ★）
账户级 **Replication & Failover**（官方总览：
https://docs.snowflake.com/en/user-guide/database-replication-failover ✅200）：
- **对象**：数据库/schema/warehouse/角色/用户等元数据 + 数据库数据，可打包成 **failover group** 统一复制。
- **拓扑**：主账户 → 一个/多个次要（secondary）账户，跨区域乃至跨云（AWS→Azure 等）⚠️。
- **提升**：次要侧 `ALTER ... FAILOVER` 提升为主——灾难恢复切换；切换回原区用 failback（`SWITCH`）⚠️ 以官方文档为准。
- **典型负载动机**：区域配额不足时的算力第二落点、就近服务海外消费者、合规驻留要求、DR 演练。
- 成本口径：复制耗源侧/目的侧算力与双倍存储（第 8 章账）；**复制不是共享**——消费者读共享不需要副本，
  容灾才需要（对照第 10 章）。
理论对照：复制拓扑/主备提升语义的通识底图在 [../设计数据密集型应用/05-复制.md](../设计数据密集型应用/05-复制.md)
（单主/多主/故障转移章节），架构论文语境见 [`../../db/db.md`](../../db/db.md) 的 CIDR 2016 精读条目。

## 常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "默认缓存下比性能" | 第二次跑的是结果缓存，必须 `USE_CACHED_RESULT=FALSE`（本章实抓范式） |
| "聚簇对所有查询都有益" | 点查不吃聚簇，该用搜索优化；两者机制不同（第 9 章） |
| "一个仓库服务所有负载" | 并发画像不同的负载互相踩踏；隔离仓库 + 成本标签是标准解 |
| "Snowflake 不能做应用/事务" | 2022 书稿弱项，Hybrid Tables + SPCS 已改写边界（见演进） |
| "开了复制就自动切换" | 提升为主是显式操作；RPO/RTO 取决于复制频率与手动切换 |
| "跨区域复制=跨区域共享" | 前者搬副本为容灾，后者零拷贝为协作（第 10 章） |

## 核心概念速览（中英对照）

1. **工作负载** — workload：按用途（DW/湖/安全分析/DS/应用）切分的平台使用形态。
2. **负载隔离** — workload isolation：每类负载独立虚拟仓库，算力与账单互不干扰。
3. **结果缓存开关** — USE_CACHED_RESULT：性能对照实验的公平性前提。
4. **克隆对照实验** — benchmarking via CLONE：零复制克隆造 A/B 表的实验方法。
5. **聚簇信息函数** — SYSTEM$CLUSTERING_INFORMATION：微分区重叠度的量具。
6. **搜索优化** — search optimization：面向点查/连接键的表级加速结构。
7. **混合表** — hybrid tables：Unistore 思想后继，面向应用事务的表形态 ⚠️。
8. **账户复制** — account replication：跨区域/跨云复制数据库与元数据。
9. **故障转移组** — failover group：打包复制与提升的故障转移单元。
10. **主/次账户** — primary/secondary account：复制拓扑两端；次要可提升为主。
11. **回切** — failback（switch）：切换后把原主纳为次的动作 ⚠️。
12. **数据驻留** — data residency：合规驱动的就近存储/就近计算要求。
