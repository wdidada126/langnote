# 第 19 章 趣味编程（原书 pp.306–314）

> 一句话定位：本章不教具体技术，而教**做事的方法**——用兴趣驱动、用原型试错、把会变的东西外置为配置、用日志代替 `print`。它是全书唯一一章「元方法」内容，也是第 20–29 章项目部分的总纲。基线：原书 Python 3.5；本目录按 3.12+ 校验。

## 核心精讲

> 以下均为**教学示意，不参与构建**：本目录不搭建真实项目，示例可直接运行。

### 1. 编程柔术（原书 19.2）：四条可操作原则

| 原则 | 含义 | 例子 |
| --- | --- | --- |
| 借力 | 先找现成库，别自己实现 | 解析 HTML 用解析器，不要正则硬啃 |
| 自动化 | 让机器替你做重复的事 | 重复三次以上的操作就写成脚本 |
| 保持灵活 | 把会变的东西外置 | 常量 → 配置 → 环境变量，见 19.4 |
| 缩短路径 | 减少「想法 → 可运行」的步数 | REPL、热重载、小脚本起步 |

「柔术」的隐喻核心是**不与问题硬碰**：能绕开的复杂度就绕开，能交给工具的就交出去。

### 2. 原型设计（原书 19.3）

```
想法 → 最小可运行原型（1 小时～1 天）→ 使用它 → 发现真实需求 → 重写（或丢弃）
```

关键心态：原型是**用来扔的**。原书强调「先做出来再看」，因为需求往往在使用中才浮现。
工程上的纪律是——原型阶段允许不写测试、允许硬编码，但一旦决定保留，就要补测试与配置外置
（分别见 [16-测试基础.md](16-测试基础.md) 与下节）。

### 3. 配置三部曲：常量 → 配置模块 → 配置文件

**第一步，提取常量**（原书 19.4 上半）：

```python
# 坏：魔法数字散落各处
def connect(timeout=3): ...
def fetch(retries=5): ...

# 好：集中到一个模块
# settings.py —— 教学示意，不参与构建
TIMEOUT = 3
RETRIES = 5
USER_AGENT = "hetland-demo/0.1"
```

**第二步，外置到配置文件**（`configparser`，标准库）：

```python
# configparser_demo.py —— 教学示意，不参与构建（仅用标准库）
import configparser
import io

text = """
[network]
timeout = 3
retries = 5

[ui]
theme = dark
"""

cfg = configparser.ConfigParser()
cfg.read_file(io.StringIO(text))          # 真实项目里用 cfg.read("settings.ini")
print(cfg.getint("network", "timeout"))   # 3
print(cfg.getint("network", "retries"))   # 5
print(cfg.get("ui", "theme"))             # dark
```

**第三步，2026 年的常用形态：TOML**（Python 3.11 起标准库自带 `tomllib`，PEP 680）：

```python
# toml_demo.py —— 教学示意，不参与构建（需要 Python 3.11+）
import tomllib

data = tomllib.loads("""
[network]
timeout = 3
retries = 5
""")
print(data["network"]["timeout"])    # 3
```

> 「读」用 `tomllib`；「写」标准库没有对应模块，第三方用 `tomli-w` 或 `tomlkit`（后者保留注释与格式）。

**第四步（可选）：带校验的配置对象**：

```bash
pip install pydantic-settings         # 环境变量 + .env + 校验一体
```

```python
# pydantic_settings_demo.py —— 教学示意，不参与构建
from pydantic import Field
from pydantic_settings import BaseSettings


class Settings(BaseSettings):
    timeout: float = Field(default=3.0, ge=0.1)
    retries: int = Field(default=5, ge=0, le=10)


print(Settings())                 # 默认值；环境变量 TIMEOUT=... 会自动覆盖
```

选型顺序（越靠右越强、也越重）：常量模块 → `configparser`/`tomllib` → 环境变量 → `pydantic-settings`。

### 4. 日志（原书 19.5，`logging` 模块）

`print` 与 `logging` 的本质差别：**`print` 只有「有/无」两态，`logging` 有级别、目的地与格式三层可配置**。

```python
# logging_demo.py —— 教学示意，不参与构建（仅用标准库）
import logging
import logging.config
import sys

CONFIG = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "plain": {"format": "%(asctime)s %(levelname)-8s %(name)s: %(message)s"},
    },
    "handlers": {
        "console": {
            "class": "logging.StreamHandler",
            "stream": "ext://sys.stderr",     # 日志走 stderr，数据走 stdout
            "formatter": "plain",
            "level": "DEBUG",
        },
    },
    "root": {"level": "INFO", "handlers": ["console"]},
}

logging.config.dictConfig(CONFIG)
log = logging.getLogger("demo")

log.debug("不会输出（root 级别是 INFO）")
log.info("处理完成，共 %d 条", 3)          # 延迟格式化，别写 f-string
try:
    1 / 0
except ZeroDivisionError:
    log.exception("计算失败")              # 自动带上 traceback
```

三条纪律：

1. **库只 `getLogger(__name__)`，不加 handler、不设级别**；配置权交给应用程序（入口脚本）。
2. 用 `log.info("...%s", x)` 的**延迟格式化**，别用 f-string——级别被关闭时能省掉格式化开销。
3. 记录**事件**（「连接重试第 2 次」），不是记录「进度条」；调试信息用 `DEBUG`，能随时关掉。

结构化日志（可机读、便于检索）在 2026 年是服务端默认：`pip install structlog`，
或让 `logging` 输出 JSON 后交给采集端。**两者不冲突**：`structlog` 可以渲染到标准 `logging`。

### 5. 卡住时怎么办（原书 19.6）

| 症状 | 做法 |
| --- | --- |
| 死盯着一段代码改不动 | 离开屏幕走一圈；把问题写下来（「橡皮鸭调试法」） |
| 怀疑是库的问题 | 写一个 10 行最小复现，往往复现不出来就找到原因了 |
| 概念不清 | 回读文档/源码，而不是继续试参数组合 |
| 长期厌倦 | 换个项目；原书的观点是**保持有趣优先于完成度** |

### 6. 原书 19.7 的「深入学习方向」在 2026 年的重排

| 原书方向 | 2026 年状态 |
| --- | --- |
| 图形用户界面（Tkinter） | 🔧 桌面 GUI 需求收缩，优先 Web 前端或 TUI（`textual`/`rich`） |
| 网络编程（Twisted） | 🔧 `asyncio` 是标准答案，Twisted 仅作历史对照；见 [14-网络编程.md](14-网络编程.md) |
| Web（CGI） | 🔧 CGI 已被移出标准库；走 FastAPI / Django / Flask + ASGI |
| 科学计算（NumPy/SciPy） | **依然是最值得投入的方向之一**，且生态扩展到 polars / JAX |
| 游戏（pygame） | 仍活跃，适合入门；商业级看 Godot（GDScript）/ Unity |
| 测试、打包、类型、可观测性 | 🔧 原书未列，2026 年属于「必须补的工程底座」 |

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| 3.5（原书基线） | `logging` 已稳定；`configparser` 无变化；配置格式以 `.ini` 为主 |
| 3.6 | f-string（PEP 498）让日志/消息写法更简洁（但仍建议用延迟格式化） |
| 3.7 | `dataclasses`（PEP 557）出现，配置对象表达更轻 |
| 3.8 | `functools.cached_property`、f-string `=` 调试语法（`print(f"{x=}")`） |
| 3.10 | `match`（PEP 634）可替代一长串 `if/elif` 的配置分支 |
| 3.11 | 🔴 **`tomllib`（PEP 680）进入标准库**：读 TOML 不再需要第三方库；`ExceptionGroup`（PEP 654）让「批量配置校验」可一次报完所有错 |
| 3.12 | 类型参数语法（PEP 695）让配置 dataclass 的泛型写法更干净 |
| 3.13 / 3.14 | 死电池清理（PEP 594）让原书提到的一些老工具彻底不可用 🔧；`logging` 本身稳定 |

## 近年研究与工业界开源实践（2015–2026）

- **结构化日志**：`structlog`（`hynek/structlog`）与 JSON 输出是服务端的默认形态；
  分布式追踪（OpenTelemetry）把「一条日志」升级为「一次请求链路」。
  相关文档均为**非同行评审**的工业界资料。
- **配置管理**：`pydantic-settings`、`dynaconf`、`hydra`（研究/实验配置组合）；
  云原生场景把配置进一步推向环境变量与 Secret 管理服务。
- **TUI 与终端体验**：`rich`、`textual`、`typer`（CLI 参数）让「命令行工具」重新成为高频形态，
  这与原书「GUI 是下一个方向」的判断正好相反。
- **可观测性三件套**（指标 / 日志 / 追踪）：OpenTelemetry 成为跨语言的统一事实标准，
  Python 侧通过 `opentelemetry-python` 自动埋点。
- **CLI 分发**：配合 [18-程序打包.md](18-程序打包.md) 的 `[project.scripts]` 与 `pipx`，
  一个脚本可以变成团队共用的命令。
- **研究侧**：关于「开发者动机与乐趣」的研究属于软件工程中的人因方向（如内在动机、
  心流与开发者生产力的实证研究）；关于「配置错误」的研究显示**配置是运维故障的主要来源之一**，
  这正支持原书「把配置外置并集中管理」的主张。🔧 具体文献本目录不列，以免误引。

## 常见误区与本书需修正之处

| # | 原书说法 / 常见想法 | 问题 | 2026 正确写法（🔧 = 需修正） |
| --- | --- | --- | --- |
| 1 | 用 `print` 调试并保留在成品里 | 无法分级、无法关掉、污染 stdout | 🔧 `logging` + `getLogger(__name__)`；调试用 `breakpoint()` |
| 2 | 日志写 `log.info(f"结果是 {x}")` | 级别关闭时仍会格式化；且丢失结构化 | 🔧 延迟格式化 `log.info("结果是 %s", x)`；或 `structlog` 输出键值 |
| 3 | 在库里配 handler 与级别 | 会与使用方的配置打架 | 🔧 库只取 logger 并打日志，配置只在应用入口做一次 |
| 4 | 配置文件只讲 `.ini` | 🔧 2026 年 TOML 是 Python 项目的事实标准（`pyproject.toml` 就是 TOML） | 🔧 首选 TOML（`tomllib` 读），兼容旧项目保留 `configparser` |
| 5 | 常量硬编码在函数签名里 | 每次调整都要动代码 | 🔧 常量集中 → 配置文件 → 环境变量（按变化频率分层） |
| 6 | 配置不校验 | 错误配置在运行时才炸 | 🔧 `pydantic-settings` / dataclass + 显式校验；PEP 654 可一次报全部错误 |
| 7 | 原型直接变成产品 | 原书也反对这点，但没说清边界 | 原型保留前必须补：测试、配置外置、日志、错误处理 |
| 8 | 「有趣」= 一直做简单的东西 | 乐趣来自**难度与能力匹配**（心流），不是简单 | 刻意加一点难度：换个不熟的库、加个约束 |
| 9 | 🔧 原书未涉及 | 原书没讲环境变量与密钥管理 | 补：密钥走环境变量/Secret 管理，**绝不进配置文件进仓库** |
| 10 | 🔧 原书未涉及 | 原书没讲可观测性与追踪 | 补：OpenTelemetry；一次请求一个 trace id，日志带上它 |
| 11 | 🔧 原书方向清单过时 | GUI/Twisted/CGI 已非主流 | 🔧 重排见上文第 6 小节 |
| 12 | 日志越多越好 | 高量级 DEBUG 日志在生产会拖垮 I/O 与账单 | 生产默认 INFO；DEBUG 按需临时开启；对高频路径采样 |
