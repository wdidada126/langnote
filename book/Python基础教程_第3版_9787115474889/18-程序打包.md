# 第 18 章 程序打包（原书 pp.300–305）

> 一句话定位：本章教你把「自己能跑的脚本」变成「别人能装的包 / 能双击的程序」。**原书这一章在 2026 年已整体过时**：`distutils` 被移除、`py2exe` 边缘化、`setup.py` 不再是入口，取而代之的是 `pyproject.toml` + 构建后端 + 冻结工具。基线：原书 Python 3.5；本目录按 3.12+ 校验。
> 对应英文章名：**Packaging Your Programs**。

## 本章地图

| 节 | 原书内容 | 2026 年等价结论 |
| --- | --- | --- |
| 18.1 Setuptools基础 | `setup.py` 里写 `setup(name=..., version=..., py_modules=[...])` | 🔧 元数据搬进 `pyproject.toml` 的 `[project]`（PEP 621）；构建后端显式声明（PEP 517/518） |
| 18.2 打包 | `python setup.py sdist` / `bdist` | 🔧 `python -m build` 产出 **sdist + wheel**；上传用 `twine`，先传到 TestPyPI |
| 18.3 编译扩展 | `setup(ext_modules=[Extension(...)])` + `distutils` | 🔧 `setuptools` 的 `ext-modules`，或 `meson-python` / `scikit-build-core`；跨版本分发用 **abi3 wheel + cibuildwheel** |
| 18.4 使用py2exe创建可执行程序 | Windows-only 冻结 | 🔧 用 **PyInstaller / Nuitka / cx_Freeze**；单文件脚本可用标准库 `zipapp` |
| 18.5 小结 | 「打包不难」 | 结论仍成立，但**难点从「写 setup.py」变成了「依赖与环境的确定性」**（PEP 668、锁文件） |

## 核心精讲

> 以下均为**教学示意，不参与构建**：本目录不发布真实包，示例用于对齐命令与文件结构。

### 1. 现代最小包：`pyproject.toml` 取代 `setup.py`

目录结构：

```
hello_hetland/
├── pyproject.toml
└── src/hello_hetland/__init__.py      # def main(): print("Hello, Hetland!")
```

`pyproject.toml`（教学示意，不参与构建）：

```toml
# pyproject.toml —— 教学示意，不参与构建
[build-system]
requires = ["hatchling>=1.25"]
build-backend = "hatchling.build"

[project]
name = "hello-hetland"
version = "0.1.0"
description = "A tiny demo package for Beginning Python ch.18"
readme = "README.md"
requires-python = ">=3.12"
license = "MIT"
authors = [{ name = "You" }]
dependencies = []                      # 运行期依赖写这里，不要写版本号上限除非有理由

[project.optional-dependencies]
dev = ["pytest>=8", "ruff>=0.6", "mypy>=1.11"]

[project.scripts]
hello-hetland = "hello_hetland:main"   # 安装后生成命令行入口

[tool.hatch.build.targets.wheel]
packages = ["src/hello_hetland"]
```

三个后端任选其一，语法差异很小：

| 后端 | `requires` / `build-backend` | 特点 |
| --- | --- | --- |
| hatchling | `hatchling` / `hatchling.build` | 默认零配置、快，新项目友好 |
| setuptools | `setuptools>=68` / `setuptools.build_meta` | 生态最全，**编译扩展时最稳** |
| flit-core | `flit_core>=3` / `flit_core.buildapi` | 极简，只做纯 Python 包 |

### 2. 构建与发布：`python -m build` + `twine`

```bash
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install --upgrade pip build twine
python -m build            # 产出 dist/*.tar.gz（sdist）与 dist/*.whl（wheel）
twine check dist/*         # 先自检元数据能否在 PyPI 页面正常渲染
twine upload --repository testpypi dist/*   # 先传测试索引
twine upload dist/*        # 确认无误再传正式索引
```

**sdist 与 wheel 的分工**（原书没有讲清这一点）：

| 产物 | 内容 | 谁在用 |
| --- | --- | --- |
| sdist | 源码 + 元数据，安装时**在本机构建** | 需要编译、需要改源码的场合；也是发行版打包的输入 |
| wheel | 已构建好的 `.whl`，安装时**只解压** | 绝大多数用户的默认路径；纯 Python 的 wheel 一次构建处处可用 |

命名里的 `py3-none-any`（纯 Python）与 `cp312-cp312-win_amd64`（含 C 扩展）正是这个区别的体现。

### 3. 环境管理：PEP 668 之后不要往系统 Python 里装

| 场景 | 命令 | 说明 |
| --- | --- | --- |
| 项目环境 | `python -m venv .venv` | 永远优先；PEP 668 让系统 Python 被标记为「外部管理」 |
| 装命令行工具 | `pipx install ruff` | 工具各自隔离，不污染任何项目环境 |
| 快速依赖解析 | `uv pip install -r requirements.txt` | `uv` 用 Rust 实现，解析与安装都快于 pip |
| 锁文件 | `uv pip compile pyproject.toml -o requirements.lock` | 保证 CI 与本地装到同一组版本 |
| 误装系统 Python | `error: externally-managed-environment` | 这是 **PEP 668** 的保护，不是 bug；`--break-system-packages` 只在容器里用 |

### 4. 编译扩展（原书 18.3 的现代版）

```toml
# 用 setuptools 后端编译 C 扩展 —— 教学示意，不参与构建
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[tool.setuptools]
ext-modules = [{ name = "spam", sources = ["src/spam.c"] }]
```

- 想要「一次编译、多版本可用」：定义 `Py_LIMITED_API` 产出 **abi3 wheel**（🔧 稳定 ABI 相关 PEP 编号以官方文档为准）。
- 想要「多平台多版本都自动编」：在 CI 里用 `cibuildwheel`，它按矩阵调用各平台容器/虚拟机产出全套 wheel。
- 构建系统更复杂的 C/C++ 项目：`meson-python` 或 `scikit-build-core` 常比手写 `setup.py` 更好维护。
- 详细代码见 [17-扩展Python.md](17-扩展Python.md)。

### 5. 冻结成可执行程序（原书 18.4 的替代）

标准库方案，零第三方依赖（教学示意，不参与构建）：

```bash
mkdir -p demo_app && printf 'def main():\n    print("Hello from zipapp")\n' > demo_app/__main__.py
python -m zipapp demo_app -m "demo_app.__main__:main" -o demo.pyz
python demo.pyz                 # Hello from zipapp
```

第三方方案对比：

| 工具 | 特点 | 适用 |
| --- | --- | --- |
| PyInstaller | 打包解释器 + 依赖，支持 `--onefile`；体积大、启动慢 | 通用默认选择，Windows 上最成熟 |
| Nuitka | 把 Python **编译成 C** 再链接，体积与启动更好，兼容面略窄 | 追求性能与分发体积 |
| cx_Freeze | 老牌、跨平台、配置直观 | 需要细粒度控制打包内容 |
| `zipapp` | 标准库，产出 `.pyz`，**需要目标机已装 Python** | 内部工具、CI 脚本分发 |
| py2exe | 🔧 原书推荐，Windows-only，今日已边缘化 | 仅维护老项目时使用 |

> 冻结工具的共同坑：**动态导入与数据文件不会被自动发现**，需要显式
> `--hidden-import` / `--collect-data`（PyInstaller）或 `include_files`（cx_Freeze）；
> 杀毒软件对 `--onefile` 的误报也是常态。

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| 3.5（原书基线） | `distutils` + `setup.py` 是官方路径；wheel 已普及但 pyproject 尚未出现 |
| 3.6–3.10 | `pip` 逐步默认使用 PEP 517 构建；`setup.py install` 被标记为不推荐 |
| 3.10 | PEP 517 构建已成 pip 默认；`python setup.py ...` 陆续弃用 |
| 3.11 | 🔴 **PEP 668 外部管理环境**：系统 Python 默认禁止 `pip install`（Debian/Ubuntu 首先落地）；`tomllib`（PEP 680）让读取 pyproject 不必装第三方库 |
| 3.12 | 🔴 **`distutils` 被移除（PEP 632）**——原书 18.1/18.3 的示例**直接跑不起来**；`setuptools` 成为唯一标准路径之一 |
| 3.13 | 打包链进一步清理；`pip` 对遗留 `setup.py` 直接调用的支持继续收紧 🔧 |
| 3.14 | 注解延迟求值等语言变化间接影响需读注解的打包插件 🔧；`uv`/`hatch` 等工具生态成为主流选择 |

## 近年研究与工业界开源实践（2015–2026）

- **PyPA 工具链**：`pip`、`setuptools`、`wheel`、`twine`、`build` 是官方推荐组合；
  `python -m build` 的价值在于「在干净隔离环境里按 PEP 517 构建」，避免本机残留污染产物。
- **`uv`（astral-sh/uv）**：Rust 实现的 pip/venv 替代品，把「解析 + 安装 + 锁文件 + Python 版本管理」
  合成一个二进制；它是 2024–2026 年打包领域变化最大的变量。以下工具文档均为**非同行评审**资料。
- **hatch / PDM / Poetry**：项目与依赖管理一体化工坊；Poetry 自带锁与发布，
  PDM 支持 PEP 582 风格，hatch 以环境矩阵见长。三者与 `pyproject.toml` 兼容，退出成本低。
- **cibuildwheel**（PyPA）：CI 里一次性产出全平台 wheel，是「含扩展模块的库」能否被顺利安装的关键设施。
- **pipx**：命令行工具安装器，直接解决「全局装工具会污染环境」的老问题。
- **可复现构建与供应链安全**：近年重点从「能不能装上」转向「装的是不是我以为的那个」
  —— 锁文件、哈希固定（`--require-hashes`）、索引镜像审计、PyPI 的 Trusted Publishing（OIDC）取代长期 API token。
- **研究侧**：打包/依赖领域的研究集中在**依赖冲突求解与生态系统健康度度量**
  （如「依赖树膨胀」「弃包风险」），多为软件工程会议论文；🔧 本目录不列具体文献以免误引。

## 常见误区与本书需修正之处

| # | 原书说法 / 常见想法 | 问题 | 2026 正确写法（🔧 = 需修正） |
| --- | --- | --- | --- |
| 1 | 写 `setup.py` 调用 `setup(...)` | 元数据分散、命令式、已被 PEP 621 取代 | 🔧 `[project]` 写进 `pyproject.toml`；纯声明式 |
| 2 | `python setup.py install` | 该调用方式已弃用，且绕过依赖解析 | 🔧 `pip install .` 或 `python -m build` + `pip install dist/*.whl` |
| 3 | 用 `distutils` | **3.12 已移除（PEP 632）**，原书代码直接 `ModuleNotFoundError` | 🔧 `setuptools` / `hatchling` / `flit-core` |
| 4 | `python setup.py sdist` | 同上 | 🔧 `python -m build`（同时产出 sdist 与 wheel） |
| 5 | 直接 `python setup.py upload` 上传 | 该命令早已从 PyPI 下线，且不走 TLS 校验实践 | 🔧 `twine upload`，推荐 PyPI 的 Trusted Publishing |
| 6 | 用 `py2exe` 打包成 exe | Windows-only、维护趋缓 | 🔧 PyInstaller（通用）/ Nuitka（追求体积与性能）/ cx_Freeze |
| 7 | 直接 `pip install X` 装进系统 Python | 3.11 起多数发行版报 `externally-managed-environment`（PEP 668） | 🔧 用 `venv`；装工具用 `pipx`；容器里才考虑 `--break-system-packages` |
| 8 | 依赖写成 `requests==2.31.0` | 对库而言过紧的钉死会制造冲突 | 🔧 库用宽松下界 `requests>=2.32`；**应用**才用锁文件钉全部版本 |
| 9 | `requirements.txt` 就是依赖声明 | 它既不能直接表达 `extras`，也不区分构建期依赖 | 🔧 库用 `pyproject.toml`；部署用锁文件；`pip-compile`/`uv pip compile` 生成 |
| 10 | 只要有 sdist 就够了 | 用户安装慢、可能编译失败 | 🔧 同时发布 wheel；纯 Python 包发布 `py3-none-any` |
| 11 | 版本号随手改 | 下游靠版本约束解析依赖 | 遵循语义化版本；`__version__` 由 `importlib.metadata.version()` 读取，不手写 |
| 12 | 🔧 原书未涉及 | 原书完全没有 pyproject / PEP 517-518-621 / PEP 668 | 本章**整体重写**：以上述 PEP 为骨架 |
| 13 | 🔧 原书未涉及 | 原书没讲数据文件与入口点 | 补：`[project.scripts]` 声明命令行；包内数据用 `importlib.resources`（非 `__file__` 拼路径） |
| 14 | 🔧 原书未涉及 | 冻结后运行报 `ModuleNotFoundError` | 补：显式声明隐藏导入与数据文件；`--onefile` 注意解压到临时目录导致的路径问题 |
