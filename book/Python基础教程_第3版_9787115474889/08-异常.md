# 第 8 章 异常（原书 pp.132-143）

> 一句话定位：把「出错」从特殊情况变成语言的正常控制流——`raise` 主动抛、`try/except/else/finally` 结构化捕获、异常链保留上下文，以及「异常之禅」（EAFP）。基线：原书 Python 3.5；本目录按 3.12+ 校验，并补 3.11 的 `ExceptionGroup` 与 `except*`。
> 对应英文章名：Exceptions

## 本章地图

| 小节 | 内容 | 结论 |
| --- | --- | --- |
| 8.1 异常是什么 | 异常是对象，未捕获则沿调用栈向上传播并终止程序 | 异常携带**类型 + 消息 + 回溯**三件套 |
| 8.2.1 `raise` 语句 | `raise Exc("msg")`；裸 `raise` 重抛当前异常 | 抛异常要带**足够定位的信息** |
| 8.2.2 自定义的异常类 | 继承 `Exception`（或其子类） | 一个模块定义自己的异常基类是好习惯 |
| 8.3.1 不用提供参数 | `except ValueError:` 只关心类型 | 需要消息时才写 `as e` |
| 8.3.2 多个 `except` 子句 | 按顺序匹配，**先具体后宽泛** | 写反了宽泛的会「吃掉」具体的 |
| 8.3.3 一箭双雕 | `except (A, B):` 元组捕获 | 处理逻辑相同时合并 |
| 8.3.4 捕获对象 | `except OSError as e:` 访问 `e.args`、`e.errno` | 对象里才有 errno/filename 等细节 |
| 8.3.5 一网打尽 | `except Exception:` / 裸 `except:` | 🔴 裸 `except` 会连 `KeyboardInterrupt` 一起吞 |
| 8.3.6 万事大吉时 | `else` 无异常才跑；`finally` 一定跑 | `finally` 用于清理，`else` 用于「成功路径」 |
| 8.4 异常和函数 | 异常穿过函数栈；未捕获则程序崩溃并打印 traceback | 在函数边界决定「处理还是向上抛」 |
| 8.5 异常之禅 | EAFP（请求宽恕） vs LBYL（三思而后行） | Python 偏爱 EAFP；但 EAFP 不能掩盖逻辑错误 |
| 8.6 不那么异常的情况 | 用 `warnings` / `logging` 表达「警告」 | 可预期的失败不该用异常做流程控制 |
| 8.7 小结 | 新函数表 | 第 9 章之后到处用到异常 |

## 核心精讲

> 以下均为**教学示意，不参与构建**：片段自足，可直接 `python x.py` 运行。

### 1. 异常对象与 `raise`

```python
# demo_ch8_raise.py —— 教学示意，不参与构建
try:
    1 / 0
except ZeroDivisionError as e:
    print(type(e).__name__, e.args, str(e))     # ZeroDivisionError ('division by zero',) division by zero

class AppError(Exception):
    """本应用的异常基类：便于调用方统一捕获。"""

class ValidationError(AppError, ValueError):    # 多继承：既是 AppError 又是 ValueError
    def __init__(self, field, message):
        super().__init__(f"{field}: {message}")
        self.field = field

try:
    raise ValidationError("age", "must be >= 0")
except ValidationError as e:
    print(e.field, e)                            # age age: must be >= 0

def rethrow():
    try:
        raise ValidationError("age", "must be >= 0")
    except ValidationError:
        raise                                    # 裸 raise：原样重抛（保留回溯）

try:
    rethrow()
except ValidationError as e:
    print("rethrown:", e)                        # rethrown: age: must be >= 0

# 显式异常链：raise X from Y 保留「起因」
def load(path):
    try:
        with open(path, encoding="utf-8") as f:
            return f.read()
    except OSError as exc:
        raise AppError(f"cannot load {path}") from exc   # __cause__ = exc
```

说明：`raise ... from ...` 的显式异常链自 Python 3.0 引入；🔧 对应 PEP 编号未在已核对清单内，以官方文档为准。

### 2. `try/except/else/finally` 的完整形态

```python
# demo_ch8_try.py —— 教学示意，不参与构建
def divide(a, b):
    try:
        result = a / b
    except ZeroDivisionError:
        print("除数为 0")
    except (TypeError, ValueError) as e:        # 一箭双雕
        print("类型不对：", e)
    else:
        print("成功：", result)                  # 仅当没有异常时执行
        return result
    finally:
        print("finally 一定执行")                 # 即使 return/break/异常也会跑
    return None

print(divide(6, 3))     # 成功：2.0 / finally 一定执行 / 2.0
print(divide(1, 0))     # 除数为 0 / finally 一定执行 / None

# 一网打尽的正确姿势
import logging
try:
    risky = int("not a number")
except ValueError as e:
    logging.getLogger(__name__).exception("bad input: %s", e)
except Exception:                                # 兜底：至少不吞 BaseException
    logging.getLogger(__name__).exception("unexpected")
    raise
```

`finally` 的两个陷阱：
1. **`finally` 里的 `return` 会吞掉异常**（应绝对避免）。
2. `finally` 用于释放资源；**现代写法用 `with` 上下文管理器**（PEP 343），见第 11 章。

### 3. 异常之禅：EAFP vs LBYL

```python
# demo_ch8_eafp.py —— 教学示意，不参与构建
d = {"a": 1}

# LBYL（Look Before You Leap）：先检查
if "b" in d:
    print(d["b"])
else:
    print("missing")

# EAFP（Easier to Ask Forgiveness than Permission）：直接试
try:
    print(d["b"])
except KeyError:
    print("missing")

# 更地道：用 API 自带的缺省值能力
print(d.get("b", "missing"))
```

选择原则：
- 竞争条件场景（文件是否存在、锁能否拿到）**必须 EAFP**——检查与操作之间存在时间窗。
- 逻辑错误（参数类型不对）应**直接抛异常**，不要用 `try` 掩盖。
- 能用返回值表达缺省（`get`、`next(it, default)`）时，比 `try` 更清晰。

### 4. 3.11+ `ExceptionGroup` 与 `except*`（本书未覆盖）

```python
# demo_ch8_group.py —— 教学示意，不参与构建（需 Python 3.11+）
def collect(errors):
    raise ExceptionGroup("multiple failures", errors)   # PEP 654

try:
    collect([ValueError("a"), TypeError("b"), ValueError("c")])
except* ValueError as eg:            # 只捕获组内的 ValueError
    print("values:", [str(e) for e in eg.exceptions])   # ['a', 'c']
except* TypeError as eg:
    print("types:", [str(e) for e in eg.exceptions])    # ['b']

# add_note：给异常追加上下文（3.11+）🔧 对应 PEP 未在已核对清单内，以官方文档为准
def boom():
    raise ValueError("bad config")

try:
    try:
        boom()
    except ValueError as e:
        e.add_note("hint: check config.toml")    # 追加上下文
        raise                                    # 重抛，notes 随之带上
except ValueError as outer:
    print(outer, "|", outer.__notes__)           # bad config | ['hint: check config.toml']
```

### 5. 不那么异常的情况：`warnings` 与 `logging`

```python
# demo_ch8_warn.py —— 教学示意，不参与构建
import warnings, logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
log = logging.getLogger(__name__)

def deprecated():
    warnings.warn("deprecated() 将于下个版本移除", DeprecationWarning, stacklevel=2)
    log.info("called deprecated()")

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    deprecated()
    print([str(w.message) for w in caught])
```

## 近年研究与工业界开源实践（2015–2026）

- **结构化并发驱动异常组**：`asyncio.TaskGroup`（3.11）与 `anyio`/`trio` 的 nursery 都面临「多个子任务同时失败怎么办」——`ExceptionGroup`（PEP 654）正是为此设计，是 2020 年代并发错误处理的范式转变。
- **错误可观测性**：`Sentry`、`OpenTelemetry` 等把 traceback、`__notes__`、`__cause__` 链一并上报；实践上「给异常加上下文」比「换个异常类型」更有价值。
- **异常 vs Result 类型**：Rust/Go 风格的 `Result[T, E]` 在 Python 有 `returns` 等第三方实现，但**主流仍是异常**（社区共识，非同行评审）；类型检查器可配合 `NoReturn` 标注「此函数必抛」。
- **失败快速与重试**：`tenacity`/`backoff` 等重试库把「可重试异常」与「致命异常」分开声明，是对 8.5「异常之禅」的工程化落地。
- **研究侧**：异常处理的研究集中在「异常安全（exception safety）」与「错误传播的可验证性」，主要在函数式语言与形式方法社区；CPython 属于 unchecked exceptions 阵营，本章结论不受影响。🔧 具体论文本目录不引用，避免编造。

## 常见误区与本书需修正之处

| # | 原书说法 / 常见误解 | 问题 | 2026 正确写法 |
| --- | --- | --- | --- |
| 1 | 「`except:` 裸捕获最方便」 | 会吞掉 `KeyboardInterrupt`、`SystemExit` | `except Exception:`；真要全捕获用 `BaseException` 并立刻 `raise` |
| 2 | 「`except` 顺序无所谓」 | 从上到下匹配，宽泛的在前会遮蔽具体的 | 先具体（`FileNotFoundError`）后宽泛（`OSError`） |
| 3 | 「`except` 里 `pass` 掉就行」 | 静默失败是最难排查的 bug | 至少 `logging.exception(...)`；或加注释说明为何忽略 |
| 4 | 「`finally` 里可以 `return`」 | 会吞掉正在传播的异常 | `finally` 只做清理，不放控制流 |
| 5 | 「`raise` 之后代码还会继续」 | 控制流立即转移 | `raise` 写在该分支最后一句 |
| 6 | 「自定义异常继承 `BaseException`」 | 会逃过 `except Exception` | 一律继承 `Exception`（或其子类） |
| 7 | 🔧「自定义异常不需要基类层级」 | 调用方无法统一捕获 | 每个包定义一个基类（如 `AppError`），对外公开 |
| 8 | 「异常消息里拼变量就够了」 | 缺少上下文难以定位 | 用 `raise X(...) from e` 保留链；或用 `e.add_note()`（3.11+） |
| 9 | 「用异常做正常流程控制」 | 慢且难读 | 用返回值/哨兵值；真的「异常」才抛 |
| 10 | 「`try` 块越大越好」 | 会把无关异常也吞进来 | `try` 只包住**可能失败的那一行** |
| 11 | 🔧 原书未覆盖 `ExceptionGroup` | 3.11 起批量错误有专门机制 | 并发/批量校验用 `except*`（PEP 654） |
| 12 | 「`assert` 可以做用户输入校验」 | `-O` 会剔除断言 | 公开接口用 `if ...: raise ValueError(...)`（呼应第 5 章） |
| 13 | 「`warnings` 和 `logging` 一样」 | warnings 面向**开发者**（可被过滤/转错误） | 弃用提示用 `warnings.warn(...)`，运行事件用 `logging` |
| 14 | 「资源关闭写 `finally: f.close()`」 | 易漏、易被 `return` 干扰 | `with open(...) as f:`（PEP 343） |
