> 对应原书第 8 章「转储文件调试分析」（✅ 章名双源核实）。节级目录（⚠️ 据豆瓣阅读电子书页 TOC）：

> 原书覆盖死锁/崩溃两类转储的实操（第 2 版摘要 ✅）；本章以「转储是怎么来的→里面有什么→怎么复原现场」重写。

## 核心概念速览（中英对照）

- **转储** — dump file：进程/内核在某时刻状态的可离线分析快照；Windows 叫 dump，Linux 用户态叫 core dump。
- **core dump（核心转储）** — 崩溃信号致死时内核把进程内存镜像写出；文件名默认 `core` 或 `core.PID`。
- **ulimit -c** — core 尺寸上限（默认 0=关闭）：core 不生成的头号原因。
- **core_pattern** — `/proc/sys/kernel/core_pattern`：命名模板（`%e.%p`）或 `|` 开头交给管道收集器（abrt/systemd-coredump/apport）。
- **小程序转储** — minidump：只含线程栈/模块表/异常记录的 Windows 摘要转储；全转储含整堆。
- **堆转储** — heap/full dump：含全部私有提交内存——大但能查第 6 章的「谁持有这块内存」。
- **WER** — Windows Error Reporting：崩溃拦截→按策略产 dmp→上传符号化服务的 OS 基建；LocalDumps 注册表可白嫖落盘。
- **事后调试** — postmortem debugging：`gdb exe core` / WinDbg 开 dmp——第 3 章技能在静态现场上的重放。
- **符号化** — symbolization：转储里只有地址+模块基址，行号/变量全靠「同一次构建」的 PDB/DWARF——转储分析 90% 的失败是符号没对上。
- **栈回收线** — stack canon：x64 转储回溯不依赖帧指针，靠 UNWIND_INFO 表（Windows）/`.eh_frame` CFI（Linux）重建。
- **kd/netdump** — 内核侧转储：Windows 内核 memory.dmp、Linux kdump/vmcore（第 11 章接口，本章提区别）。
- **address@module** — 无符号最后手段：只有 `0x7ff6`+`x/3i` 时，用偏移+反汇编比对二进制仍能定位（第 9/10 章技能）。

## 动机：崩溃不等你在场

生产环境的崩溃有三重不可重现性：现场（用户机器）、数据（真实分布）、时序（负载交错）。
转储的意义是把「不可重现」翻译成「可无限次调试」——代价是**一次性现场**：
没有 watchpoint、没有单步，只有一个坐标原语（内存读）+ 栈重建 + 符号。
本章因此是第 3 章的反面教材：所有命令不再改变任何东西，纯粹考古。

## 机制：两条生成-分析链路

### Linux：core 的生成与打开（8.2）

生成侧四道开关（缺一不生成，运维排查顺序）🔧：

```bash
🔧 ulimit -c unlimited                      # ① 尺寸
🔧 cat /proc/sys/kernel/core_pattern        # ② 名字/管道归属
🔧 cat /proc/PID/dumpable                   # ③ setuid/ptrace 过的进程不可 dump
🔧 df -h $(dirname core)                    # ④ 磁盘够不够(全镜像可能数 GB)
```

分析侧（本机已实测同族命令的在线版；core 版为标准用法，跨行为一致 ⚠️ Linux 侧未在本机复验）：

```text
🔧 $ gdb ./so core.12345
Program terminated with signal SIGSEGV, Segmentation fault.
#0  deep (n=43340) at so.c:2               ← 与第 3 章在线命中同一坐标
(gdb) bt                                    ← 沿 CFI/rbp 重建的调用链
(gdb) info threads → thread N → bt          ← 多线程崩溃：先看肇事线程
(gdb) p arr@4 / x/16gx $rsp                 ← 变量与栈原始区
(gdb) info files                            ← 模块基址：符号化对表
```

关键机制：core 的 ELF 头只有 **PT_NOTE 段**（`NT_PRSTATUS`＝每个线程的寄存器组、`NT_FILE`＝映射表），
数据段是稀疏的 `PT_LOAD`（只存映射过的页）。`readelf -n core` 一眼看出「几个线程、崩在哪条指令」——
**寄存器组+栈+映射表，就是一次事后调试的全部原料**。
发行版现状：Ubuntu 的 core 常被 `apport`、Fedora 被 `systemd-coredump` 接管（core_pattern 以 `|` 开头），
`coredumpctl list / dump PID` 是新的标准取件口。

### Windows：dump 的生成与 WinDbg 分析（8.1）

生成路径谱系（从被动到主动）：

1. **WER 自动**：崩溃 → `LocalDumps` 注册表键（`DumpType`=0 小/1 大/2 全）落 `%LOCALAPPDATA%\CrashDumps`；
2. **任务管理器/Process Explorer** 右键「创建转储文件」——对活进程抓 minidump/完整转储（hang 诊断主路）；
3. **procdump**（Sysinternals）：`procdump -ma -w 10 -e PID out.dmp`（异常触发+等待稳定）、`-t` 定时；
4. 代码内 `MiniDumpWriteDump`（自家崩溃处理器的标配）。

分析侧骨架（WinDbg 预览版同款命令，详见第 11 章）🔧：

```text
🔧 0: kd> .sympath srv*C:\sym*https://msdl.microsoft.com/download/symbols
🔧 0: kd> .reload /f
🔧 0: kd> !analyze -v        ← 崩溃分类器：栈+异常码+疑似归因一键输出
🔧 0: kd> kP / ~*k           ← 带参数打印的全线程栈
🔧 0: kd> !heap -p -a ADDR   ← 堆块归属：第 6 章「越界写坏元数据」的取证终点
```

死锁转储（第 4 章 hang 的离线形态）：`!analyze -hang` 或 `!locks` 找持有环——与 4 章同一张图的
静态版。**x64 栈回溯不靠 rbp**：Windows x64 要求所有代码附 UNWIND_INFO 表（模块内函数边界表），
转储只需表+栈即可展开任意帧——这是「Release 也能回溯」的制度性保证（第 9 章呼应）。

## 权衡：转储类型与隐私/体积的三角

| 类型 | 内容 | 体积 | 适用 |
| --- | --- | --- | --- |
| minidump/小 | 栈+模块+线程+异常记录 | KB~MB | 崩溃分诊、符号化栈顶 |
| 完整/heap | 全部私有内存 | ~RSS | 第 6 章泄漏取证、数据现场 |
| Linux core(ulimit 全) | 全部映射可读写页 | ~RSS | 通用；稀疏文件实占小 |
| coredump 截断 | 写一半被杀(磁盘/超时) | — | **栈可能残缺，先查 `Truncated message`** |

隐私线：转储含**全堆**＝用户数据/密钥都在里面——外发前必须过脱敏（微软 `!for_each_module` 清洗/
自家 sanitizer 流程），这是转储进 CI 的最大阻力（2026 实践：崩溃→自动符号化→**只上传栈**，原始 dmp 留在受控域）。

## 相邻概念对比

- 转储 vs 远程调试：同一现场的两条运输线——「过去送现场」（core/dmp）对「现场送命令」（RSP 每次内存读）；
  网络差/目标脆弱选前者，需要交互下断选后者（第 7 章）。
- 转储 vs TTD/rr：录像带（时间可逆、可 watch 任意时刻）对照片；TTD trace 文件本质是「增量转储+调度流」，第 11 章。
- core 的「谁没生成」排查链 vs Windows 的「WER 策略」——OS 层等价物对照表：
  ulimit↔DumpType、core_pattern↔LocalDumps、gdb↔WinDbg。

  另册讲 ELF 格式细节，本笔记讲操作路径与判读。

## 最新演进与工业实践

- **systemd-coredump/coredumpctl** 已是主流发行版默认取件口；容器里 `ulimit` 由运行时控制，
  Kubernetes 侧出现 `deadsnmp`/`coredump-agent`（如 datadog/agent 的 coredump check、
  以及专门的 github: datadog/security 之类——⚠️ 具体仓库归属凭记忆）统一收集。
- **Breakpad/Crashpad**（google/breakpad、google/crashpad）：跨平台「客户端产 minidump + 服务端符号化」栈，
  Chrome/Firefox 同款——把 8.1 的 WER 模型搬到了非 Windows；`minidump_stackwalk` + 自建 symbol 服务是
  开源产品的默认崩溃平台骨架。
- **debuginfod 与 core**：gdb 读 core 时按 build-id 自动向服务器拉可执行/库的 DWARF（sourceware.org/elfutils）——
  符号化失败的解药进入发行版默认路径（第 9 章对表）。
- **WinDbg 现代默认**：新蓝 WinDbg（microsoft/windebug 仓库）预置符号路径模板、`!analyze -v` 结果卡片化；
  Time Travel Debugging 的 `tt -t` 录制的 trace 可直接当转储打开，**照片与录像开始共用同一文件入口**。
- **minidump 格式开放**：Microsoft 公开了 minidump 文件格式规范（「Windows Mini Dump File」文档），
  Rust `minidumper`/`dumpsyndrome` 等实现涌现——第 8.1 节的私有格式正被社区解析器补全。
