## 核心概念速览（中英对照）

- **死锁** — deadlock：线程集合互相等待对方持有的资源，全体永久阻塞；调试器视角=「所有线程都在等」。
- **死锁四条件** — four necessary conditions：互斥、持有并等待、不可剥夺、循环等待；破坏任一即无死锁（操作系统经典四条件，语言无关）。
- **锁顺序/偏序** — lock ordering：给锁编号、只允许递增获取——工程上最主流的破除「循环等待」手段。
- **数据竞争** — data race：无同步的并发读写；与死锁同属并发 bug 两极（一「闹死」一「僵住」）。
- **线程转储** — thread dump / `thread apply all bt`：把所有线程的当前栈一次打印——死锁分析的第一现场。
- **锁持有图** — lock/holder graph：从「线程在等哪把锁」+「哪把锁被谁持」构建的有向图；死锁=图中有环。
- **all-stop 模式** — all-stop：命中断点冻结全部线程（gdb/VS 默认）；调试并发 bug 时本身就是扰动源。
- **non-stop 模式** — non-stop：只冻结命中线程，其余继续跑（`set non-stop on` + 异步模式；gdb 对 remote 支持最实）。
- **调度断点** — scheduling breakpoint：断点命中时选择性地冻结/放行特定线程（第 2 章 VS UI 的对应功能）。
- **优先级反转** — priority inversion：高优先级线程被低优先级线程间接阻塞——「不是死锁的死锁」，需时序工具而非栈快照。

## 动机：为什么死锁是「栈快照型」问题

死锁的症状极稳定：界面卡死/服务 hang，但 CPU 为 0、日志沉默。它的取证不需要「回到过去」，
只需要**在 hang 的当下把所有线程的栈拍一张全家福**——每个卡死线程的栈顶几乎总是
「等待原语」（`WaitForSingleObject`/`pthread_cond_wait`/`futex`），于是问题化为：

> 从「谁在等谁」的边集合里找环。

这正是本章所有工具（gdb 线程命令、WinDbg `!locks`、VS 并行栈窗口、Java 的 jstack+死锁检测）共同的问题骨架。

## 机制：gdb 死锁现场实操流程

🔧 经典死锁样本骨架（两线程反序拿两锁；本目录示意，未在本机跑死锁样本——hang 样本在 batch gdb 下需手动介入，验证从简 ⚠️）：

```c
pthread_mutex_t A, B;
void* t1(void*) { lock(A); sleep(1); lock(B); ... }   // t1 持 A 等 B
void* t2(void*) { lock(B); sleep(1); lock(A); ... }   // t2 持 B 等 A → 环
```

排查命令序列（gdb，attach 到 hang 的进程）：

```text
🔧 (gdb) attach 12345
🔧 (gdb) thread apply all bt        ← 全家福
Thread 3 (LWP 12348): #0 futex_wait ... #2 pthread_mutex_lock_full ... #3 t2() at dead.c:12
Thread 2 (LWP 12347): #0 futex_wait ... #2 pthread_mutex_lock_full ... #3 t1() at dead.c:7
```

两条栈：t1 卡在 `lock(B)`、t2 卡在 `lock(A)`。但「等 A/B」只是栈里的参数，**gdb 裸看栈并不能直接给出
持有者**——需要 `p B.__data.__owner`（Linux glibc pthread_mutex 的 owner TID 字段，glibc 内部布局 ⚠️ 随版本变）
把「等待边」补成「持有边」。这一步在 Windows 上是现成的：

- WinDbg：`!locks` 直接打印锁-持有者表；死锁时输出 `Deadlock found ... Attempt to enter lock already owned`。
- VS：调试→窗口→**并行堆栈**（Parallel Stacks）以图形展示「全部线程都停在等待里」的斑马线。

**已实测**（本机 gdb 17.1/Windows，thr.cpp——竞争样本而非死锁，命令同款）：

```text
  Id   Target Id           Frame
  1    Thread 18416.0xa470  ntdll!ZwWaitForSingleObject () from C:\Windows\SYSTEM32\ntdll.dll
  2    Thread 18416.0xa3a0  ntdll!ZwWaitForWorkViaWorkerFactory () ...
* 5    Thread 18416.0x62a4 worker (n=100000) at thr.cpp:8
  6    Thread 18416.0x9ce0 worker (n=100000) at thr.cpp:8
(gdb) thread apply all bt 2
Thread 6 (...): #0 worker (...) at thr.cpp:8
                  #1 std::__invoke_impl<...> at .../bits/invoke.h:63
```

读法即 4.4 的操作化：`*` 是当前线程；`Switching to Thread ...` 自动跟随命中；
`thread N` 切上下文后 `info locals` 就是那个线程的局部。
**已实测坑**（Windows/CP65001）：`p name`（char* 参数）报
`Converting character sets: Invalid argument`——`set charset UTF-8`/`set coding UTF-8` 可绕（gdb 主机编码转换缺陷，Linux 罕见 ⚠️）。

## 权衡与延伸：数据竞争侧的同型操作

并发 bug 的另一半（闹死的）在 4.1–4.3 的锁语义之外，用调试器抓几乎全靠「复现+watchpoint」，性价比极差。
**已实测**其危害的直观量化——无锁共享计数器（thr.cpp，2×100000 次 `counter += 1`）：

```text
$ for i in 1 2 3; do ./thr.exe | tail -1; done
final counter = 197752 (expected 200000)
final counter = 178178 (expected 200000)
final counter = 170643 (expected 200000)
```

丢计数每次不同——这就是「调试器一停就复现不了」的根源：断点冻结改变了交错（all-stop 扰动）。
工程顺序应是：**先 TSan（第 6 章演进节），复现不了再 `watch counter` 硬件观察点守株待兔，
最后才考虑 non-stop/调度断点**（VS 的「仅挂起命中线程」或 gdb `set schedule-multiple on` + 线程专属断点）。

## 相邻概念对比

| 症状 | 死锁 | 活锁 | 优先级反转 | 数据竞争 |
| --- | --- | --- | --- | --- |
| CPU | ~0 | 100% | 高优任务延迟 | 正常 |
| 栈快照 | 全在等待原语 | 总在推进 | 单点看不出 | 单点看不出 |
| 正解工具 | thread dump/`!locks` | 采样+时序 | 调度器/追踪 | TSan |
| 调试器能力 | 强（本章） | 弱 | 弱 | 弱（扰动） |

与 OS 教材的分工：死锁四条件/银行家算法是 OS 课内容；本笔记只取「**调试器里怎么看见那个环**」这一段。
锁的正确使用（RAII 的 `lock_guard`/`scoped_lock` 多锁死锁避免重载、`std::mutex` 语义）以

## 最新演进与工业实践

- **TSan 工业化**（google/sanitizers 仓库 → 已并入 llvm/gcc 分发）：`-fsanitize=thread` 以 happens-before
  向量时钟检测竞争，2~15 倍减速+4~8GB 影子内存；C++ 标准库锁被 TSan 原生识别（`std::mutex` 无需标注）。
  ⚠️ TSan 需要 OS 侧支持，Windows/MSVC 与 MinGW **均不可用**（本机 g++ 15.2 无 libtsan，实测 `-lasan` 同型失败记录见第 6 章）——Windows 侧替代：Visual Studio 并发运行时诊断 / 转 WSL/Linux 跑 TSan。
- **rr (mozilla/rr)**：死锁排查新工作流=`rr record` 到 hang、`rr replay` 后**反向执行**从「等待点」退回
  「拿锁序列」，持有边自动补全（配合 `rr` 的调度记录）；Linux-only。
- **WinDbg 线**：`!analyze -hang`（2024 后新蓝 WinDbg 的 hang 分析扩展）、TTD 录制直接回放拿锁顺序——
  第 11 章展开；「锁持有者字段读法」（`__owner`）被 `!locks`/VS 完全封装。
- **锁卫生前移**：clang-tidy 无通用死锁检查，但 `SCOPED_LOCKABLE` 注解族（Clang thread-safety-analysis）
  在编译期强制锁顺序——大量用于 Chromium 代码库（核实状态：Clang 文档公开特性；Chromium 使用 ⚠️ 凭记忆）。
  语言层依据亦见 [../cppprime.md](../cppprime.md) 的 RAII 讨论。
- **标准库动态**：C++20 `std::atomic_ref`/`std::jthread`、C++26 执行器定型中——与本调试主题正交，
  但 `std::jthread`+`stop_token` 让「取消而非杀线程」成为 hang 的运维级解药（见 08 章演进）。
