## 核心概念速览（中英对照）

- **断点** — breakpoint：F9 切换；命中即挂起整个调试会话（all-stop），VS 默认如此。
- **条件断点/命中次数** — condition / hit count：断点右键属性；「当 i==42 时」「命中 100 次后」。
- **数据断点** — data breakpoint：对「变量被写坏」类 bug 的 UI 化 watchpoint；只能用于静态/栈内存（底层 DR 寄存器，见第 10 章）。
- **监视窗口** — Watch：把表达式钉在屏幕上当探针；**快速监视** QuickWatch 是一次性版本（Shift+F9）。
- **局部变量/自动窗口** — Locals / Autos：当前帧全部局部变量；Autos 只挑「本行及其上下游看起来相关的」。
- **即时窗口** — Immediate Window：断点处的 REPL，可求值、可改值（`a = 5`）、可调小函数。
- **调用堆栈窗口** — Call Stack：帧列表；双击切帧，切帧改变「当前上下文」从而改变 Locals/Watch 的解释域。
- **设置下一条语句** — Set Next Statement：把 EIP 拽回/跳过源码行；危险（跳过构造/资源获取即泄漏或半构造态）。
- **编辑并继续** — Edit and Continue (EnC)：调试中改函数体热生效；MSVC 私有黑科技，依赖可重定位的函数边界与元数据。
- **内存窗口** — Memory Window：按地址看原始字节；**十六进制/文本可视化工具** 与「字符串可视化工具」补齐 STL/字符集视图。
- **错误码窗口** — command `err`：把 `GetLastError()`/HRESULT 的裸数字翻译成符号名——Windows 程序员的手术刀。
- **ASSERT 宏** — assert()：Debug 版弹窗+可「重试→进入调试器」，`NDEBUG` 定义后整条语句消失（第 9 章 Release 陷阱）。
- **PDB** — Program Database：`/Zi` 产出的符号库；调试会话按「exe 旁 .pdb 或符号服务器」加载。

## 动机：微软世界为什么单独成章

Windows C/C++ 调试生态与 Linux 是**两套平行宇宙**，硬差异四条：

1. 符号格式：PDB（私有格式，微软工具独占良好支持）对 DWARF（公开规范）。
2. 调试原语：Win32 调试 API 的**事件循环模型**（`WaitForDebugEvent`，异常/线程创建/模块加载都是事件）
   对 Linux 的 `ptrace` + signal/waitpid 模型——这决定了 VS 断点本质是「调试器线程收到
   `EXCEPTION_BREAKPOINT` 后不 Resume」，见第 10 章。
3. 崩溃基建：Windows 有 SEH/SIDEs/WER 全套（第 8 章转储即 WER 产物），Linux 靠 signal + core。
4. 交付形态：大量商业软件只发 EXE/DLL + 选择性发 PDB，「事后拿 PDB 调无源码发行版」是 Windows 常态需求（第 9 章）。

因此本章的学习目标不是记菜单，而是建立「**每个 UI 功能背后是哪条 OS/编译器设施**」的映射。

## 机制：一条断点生命周期在 VS 里的链路

以「在函数第 12 行按 F9 → 命中 → 看变量 → F10 单步」为例，各环节的设施归属：

| UI 动作 | 背后机制 | 归属层 |
| --- | --- | --- |
| F9 设断点 | 行号经 `.debug_line` 等价物（PDB 序列点表）→ 地址 → 进程内写 `INT 3` | 符号引擎 + OS |
| 程序跑到该行 | CPU 触发 `EXCEPTION_BREAKPOINT`，OS 把异常投递给调试器事件队列 | OS（第 10 章） |
| VS 停住并高亮 | 调试器监视线程 `WaitForDebugEvent` 收到事件，不 `ContinueDebugEvent`，全部线程保持挂起（all-stop） | 调试器 |
| 悬停/局部窗口显值 | 用 PDB 里该变量的位置（栈偏移/寄存器/DWARF 表达式式的 location）读被调试进程内存 | 符号引擎 |
| F10 逐语句 | 临时软件断点打在「下一序列点」；遇调用不进入——所谓 step over 就是「下一行断点 + 命中后删除」 | 调试器 |
| 数据断点 | 占用 CPU DR0–DR3 之一，命中体现为 `EXCEPTION_SINGLE_STEP`(写监视地址) | CPU + OS |
| 编辑并继续 | 重编译函数 → 把新代码写进被调试进程可执行内存并 patch 调用者/EIP——只能在 Debug 生成、函数边界独立时成立 | 编译器+调试器一体化 |

VS 相对 gdb 的**独家便利**与其代价：

- **调度断点/线程冻结 UI**（2.9）：断点属性里「仅中断线程 X / 挂起其他线程」，是 non-stop 思想的 UI 化（机制对照见第 4 章）。
- **IntelliTrace（历史调试）**：企业版 VS 的「录制执行」，是 TTD 的浅形态（.NET 支持完整，native 有限）；2026 视角下它的精神继承者是 WinDbg TTD（见下节与第 11 章）。
- 代价：UI 遮蔽了「你现在看到的值是活的还是被优化掉的」——Release 下 Locals 满屏 `{optimized out}` 时，本章所有便利瞬间清零（第 9 章正面处理）。

### 「当前上下文」：一个容易被忽略的中心概念

VS 的调用堆栈窗口双击切帧，改变的不只是高亮——它改变**所有求值类窗口的坐标系**：
Watch/Locals/Immediate 里的名字一律按当前帧的作用域与地址解释，条件断点表达式的可引用符号集也由命中帧决定。
这与 gdb 的 `frame N` 语义完全同构（第 3 章 3.12），也是内存窗口里「栈上变量地址随帧变化、全局变量地址随模块基址变化（ASLR）」
两条读法的前提。调试会话陷入「为什么这个名字解析不出来」时，第一反应应是**检查当前帧**而非怀疑符号——
大量此类求助的根因是停在了优化帧/第三方帧上。

## 权衡：断点用量的分寸

- **断点是手术刀不是探照灯**：条件断点/命中次数能把「循环第 4000 次」变成可复现现场，但**每个断点都扰动时序**——
  多线程 heisenbug（一挂 debugger 就不复现）多半是断点冻结掩盖了竞争窗口（第 4 章实验）。
- **改值（即时窗口 `x = 42`）是双刃剑**：跳过赋值语句维持不变式的能力存在，但对象半构造/引用计数被绕开的假现场也源于它。
  2026 年的同型判断适用于 gdb 的 `set var`/`call`。
- **Assert 的正确姿势**：`assert` 表达「此处必须为真，否则我的模型错了」，弹窗「重试」即原地入调试器（2.11 的工程价值）；
  但它是**会被 Release 删掉的检查**——凡「即使发布版也必须成立」的不变式，应使用带返回值的检查或 static_assert 前移
  （语言层依据见 [../cppprime.md](../cppprime.md)）。

### 常见「UI 不显示我预期的东西」排障表（本章知识的运维面）

| 症状 | 大概率原因 | 处置 |
| --- | --- | --- |
| 断点是空心圆「当前不会命中」 | 模块未载/源码与二进制不同版/PDB 未加载 | 模块窗口查 PDB 签名；重新构建或修符号路径（第 9 章） |
| 悬停显示 `{无法读取}`/乱值 | 变量在寄存器且被复用、作用域已出 | 换 `disassemble` 窗口对照；别信 UI 信汇编（第 10 章） |
| 数据断点菜单是灰的 | 目标是堆地址（DR 只能监视静态/栈）或槽位已满 | 改用 ASan（第 6 章）；`watch` 思路在 gdb 同限制 |
| 调用堆栈只有地址 | 缺系统/第三方模块符号 | 配符号服务器路径（本章演进节） |
| 「编辑并继续」不可用 | Release/x64 部分配置、函数含内联汇编 | 接受重启会话；EnC 从来不是可靠性设施 |

## 相邻概念对比

| 维度 | VS 调试器 | WinDbg | gdb（+CLion） |
| --- | --- | --- | --- |
| 主战场 | 开发期交互调试 | 转储/内核/生产现场 | 跨平台 CLI/服务器 |
| 符号 | PDB 原生 | PDB+DWARF（新蓝 WinDbg） | DWARF；MinGW 也读 PE 的 DWARF（本机实证：第 1 章 objdump 见 .debug_* 节在 PE 中） |
| 断点 UI | 功能全（条件/命中/数据/线程过滤） | 命令行 `bp module!func /c` | `break/if/commands`，脚本化最强 |
| 时间机器 | IntelliTrace（弱） | **TTD（强，第 11 章）** | rr 外挂（第 6 章演进） |
| 事后调试 | 也能开 .dmp，但生态在 WinDbg | 正统（`!analyze -v`） | `gdb exe core` |

与「另册」的分工：VS/Windows 侧的**调试符号与对象布局原理**，本仓库 [../高效CC++调试.md](../高效CC++调试.md)

## 最新演进与工业实践

- **VS2022 调试增量**（原书第 2 版第 11 章亦提及 ⚠️ 未逐字核对）：临时断点（命中自动删除）、依赖断点
  （A 命中过才允许 B 命中——路径敏感断点）、地址断点 UI、异常设置里按模块过滤「中断时的模块」；
  这些把 gdb 早年靠 `commands`/条件表达式手搓的流程 UI 化了。
- **MSVC 的 Sanitizer 路线**：VS2019 16.9+ `/fsanitize=address`（clang-cl 亦有）——第 2 章「内存窗口看堆破坏」
  的传统教学在 2026 年应升级为「直接跑 ASan」；**本机已用 MSVC 14.43 实测通过**，详见第 6 章。
- **WinDbg 双轨**：经典 WinDbg（工具化 exe）与新「WinDbg on GitHub」（microsoft/windebug 仓库，UI 重写、
  支持 DWARF、可与 VS 共享扩展模型）——Windows 侧「IDE 调试 + WinDbg 事后」的分工在 2026 年反而更清晰。
- **符号基础设施**：`srv*C:\Symbols*https://msdl.microsoft.com/download/symbols` 符号服务器路径写进
  `_NT_SYMBOL_PATH` 的习惯延续二十年至今；微软符号服务器对 Windows 系统模块全量开放，
  这解释了「WinDbg 调系统 DLL 也能看到栈」——Linux 对应物是 debuginfod（见第 9 章）。
- **CLion 用户注意**：CLion 在 Windows 上后端可以是 gdb 或 LLDB，UI 断点语义向 VS 看齐，但**数据断点在
  MinGW/gdb 后端只读静态/栈内存的 hw watch**，与 VS 行为同源（DR 寄存器只有 4 个且不可换页），非 CLion 缺陷（第 10 章）。
