# 05 调试动态库（对应原书第 5 章）

> 对应原书第 5 章「调试动态库」（✅ 章名双源核实）。节级目录（⚠️ 据豆瓣阅读电子书页 TOC）：
> 5.1 Windows系统动态库开发与调试、5.2 Linux系统动态库开发与调试。
> 原书含工程创建与导出方式实操 ⚠️ 未逐字核对；本章以「装载机制决定调试体验」为主线重写。

## 核心概念速览（中英对照）

- **动态链接库** — DLL (Windows) / shared object `.so` (Linux)：运行期/装载期映射进进程地址空间的复用代码单元。
- **装载期断点问题** — module-load breakpoint：库还没被装载时，设在其内的断点无处落脚 → 调试器的「pending 断点」机制。
- **延迟装载** — lazy loading：符号按首次调用才解析（Windows delay-load、Linux PLT/GOT）；单步会「跳进解析桩」。
- **导入库** — import library（.lib）：链接期给主 EXE 的「存根」，真实代码在 DLL——断点设错侧的后果之一。
- **符号解析顺序** — symbol resolution：同名符号的查找次序（Windows 按模块装载序；Linux 全局符号插入 interposition）决定你断到哪个实现。
- **预加载** — LD_PRELOAD：Linux 在一切库之前注入自己的 .so，拦截/观察调用的第一工具；Windows 对应物是 API hooking（第 10 章）。
- **位置无关代码** — PIC/PIE：.so 编译前提；ASLR 下基址每轮变化，断点地址要加模块基址重定位。
- **模块事件** — DLL_THREAD_ATTACH / `ld.so` 调试钩子 `_r_debug`：调试器与装载器协作的接口点。
- **stdc++ 混用陷阱** — CRT/标准库多副本：EXE 与 DLL 链了不同运行库（/MDd vs /MT）时，跨模块 new/delete 崩溃——Windows 侧动态库 bug 的头号来源 ⚠️ 原书是否如此强调未核对，本笔记立场。
- **core 里的库现场**：转储只有地址，符号化需要「同一次构建」的 .so/PDB——第 8/9 章的伏笔。

## 动机：为什么动态库调试「感觉比主程序难一层」

主程序的地址、符号、装载时机全部确定；动态库把三件事都推迟了：

1. **地址不确定**：装载基址由 ASLR/装载顺序决定，`break libfoo.so:f` 在装载前只是挂在 pending 表里的愿望；
2. **实现不确定**：同名函数可能有多份（EXE 静态链了一份、另一个 DLL 又导出一份；Linux 符号插入还会选中
   预加载者），你以为断的是 A 实现，命中的是 B；
3. **现场不确定**：崩溃发生在第三方 .so 里时，你连它的符号都没有（strip 过），
   第 9 章「无源码调试」的常态正是从本章的困境长出来的。

## 机制：装载-断点-符号三条链

### Windows 线（5.1）

- 装载器在进程启动后按 import 表逐个映射 DLL，并向调试器投递 `DLL_PROCESS_ATTACH` 调试事件——
  VS/gdb 收到事件那一刻把 pending 断点补打在真实地址上。**已实测**可见面（gdb 17.1/MinGW，第 3 章线程样本）：
  `[New Thread 18416.0xa3a0]` 类事件 gdb 会打印，DLL 装载事件同族（gdb 默认静默，
  `set verbose on`/`info sharedlibrary` 显式查看，🔧 后者在 Windows 列已装载模块）。
- 断点写法：`break mydll!func`（VS）/ `b func`（gdb，装载后自动解析到所有同名）。VS 断点属性可勾
  「仅在模块 X 中」解决多实现歧义——pending+模块过滤是本章 UI 层的两大件。
- **调试库内 vs 库调用方**：库的 .pdb 缺失时 VS 停在 `mydll!unknown_function`；MinGW 的 DWARF 直接嵌在
  .dll/.so 内（第 1 章 objdump 实测的 `.debug_*` 节在 PE 中——Windows 的 gcc 系不走 PDB，两套符号宇宙并存）。

### Linux 线（5.2）

- 装载器是 `ld-linux.so`；gdb 用 `_r_debug`/`LM_BASE` 链接表维护 `info sharedlibrary` 视图。
- 🔧 断点时序全谱：

```text
(gdb) break libfoo.so:helper        # pending：库未装载 → "Make breakpoint pending? y"
(gdb) sharedlibrary libfoo          # 强制装载（若代码里是 dlopen）
(gdb) info sharedlibrary            # 已装载/符号已读 列表
(gdb) break *0x7f4c1234 + 0x1230     # 无符号逃生门：模块基址+文件偏移
```

- **dlopen 场景**：插件式程序里库是运行期才来的——`catch load`/`catch unload`（gdb 命令，对应
  `dlopen` 事件）是标准答案；Windows 对位 `sxe ld:modulename`（WinDbg）。
- **LD_PRELOAD 拦截示范** 🔧：写一个同名 `malloc` 的 .so 预加载，在里面下断点/打计数——
  「不重建目标就能在库边界看一切」，这是第 10 章 hooking 的良性使用。

### 两界共同的坑（各给一个已实测/可复现锚点）

- **重定位与断点地址漂移**：`info proc mappings`（Linux）/`info files`（Windows gdb）拿基址，
  `add-symbol-file` 手工挂 strip 过的符号（第 9 章）。
- **CRT 多副本（Windows）**：Debug CRT 的堆与 Release CRT 的堆是两套元数据，
  跨 DLL new/delete 直接把第 6 章的「堆破坏」演成必死bug；统一 `/MD` 或统一运行库是构建层纪律。
- **STL 边界（两界）**：跨模块传递 `std::string`/容器要求**同一 CRT 同一迭代器调试等级**——
  接口退化为 POD/抽象接口的动机详见 [../C++API设计.md](../C++API设计.md) 的 ABI 讨论。

### 导出与符号可见性：断点「断不到」的构建层根因 🔧

| 手段 | Windows | Linux | 调试后果 |
| --- | --- | --- | --- |
| 显式导出 | `__declspec(dllexport)` / .def | `__attribute__((visibility("default")))` + `-fvisibility=hidden` | 未导出符号仍可从 DWARF/PDB 断（内部函数可断，**调用约定/栈布局未知时单步很野**） |
| C 名字改编 | `?func@@YAHXZ` | `_Z4funci` | 断点写**源码名**让调试器去 demangle；直接写修饰名是脚本自动化正路（`nm -C`/`dumpbin /exports` 先查） |
| strip | PDB 外置后 DLL 无符号 | `-s` 后只剩 `.dynsym` | `bt` 出现 `[Inferior stack]`/地址帧——转入第 9 章工艺 |
| 版本脚本 | — | `-Wl,--version-script` | 隐藏导出把「误用内部函数」变成链接错误——也是**缩小调试面**的手段 |

插件式程序（`dlopen` 加载）里最常见的求助是「我的内部函数 `static` 过、也 strip 过，怎么断」——
答案链：`nm` 找符号是否还在 → `info sharedlibrary`+`add-symbol-file` 手工挂符号 →
只剩地址时 `break *base+offset`（`info proc mappings` 取基址）。三层全部是本章与第 9 章的合流点。

## 权衡：静态化、内联化还是模块边界调清楚

| 方案 | 调试体验 | 代价 |
| --- | --- | --- |
| 全静态链接调试 | 地址/符号全确定，断点无 pending 问题 | 丢失部署灵活性；Windows 启动变慢 |
| 大 DLL 少边界 | 跨模块坑少 | 加载尖峰、增量编译差 |
| 保持边界但补工具 | 模块过滤断点、`-rdynamic`/导出表纪律 | 学习成本（本章内容） |

经验判断：**能调主程序就不调库**——先在调用方边界（导入函数）下断验证语义，再进库内；
反向做会在 pending/歧义实现里耗掉半天。

## 最新演进与工业实践

- **Linux 包管理的符号现状**：发行版 .so 默认 strip，符号进 `*-dbgsym`/`*-debuginfo` 包并按 build-id 索引——
  debuginfod（dnf/debuginfod、elfutils 仓库）把「gdb 停在第三方库栈帧自动拉符号」变成默认体验；
  Windows 对应机制是符号服务器 + PDB 签名匹配（第 2/9 章）。
- **C++23/26 无新语言设施改变本章**，但模块（modules）在工具链的成熟让「共享库导出接口」多一条
  named-modules 路径；gdb 对 C++20 modules 的符号解析仍在改进（sourceware/gdb issue 追踪 ⚠️ 凭记忆，未逐单核实）。
- **LLDB 的 `target modules` 命令族**比 gdb 的 `info sharedlibrary` 更成体系（list/lookup/add-address）；
  macOS/iOS 上 dlopen 调试是日常，lldb 的 pending 断点处理最成熟。
- **Windows delay-load 调试体验**：VS 输出窗口的模块装载日志 + `/DELAYLOAD` 的 `__HrDelayLoadFailureHook`
  失败钩子，是把「延迟解析失败」从崩溃变成可控断点的工程手段（⚠️ 细节凭记忆，MSVC 文档级事实）。
- **容器里的动态库**：镜像内 `/usr/lib` 与 volume 挂载的自研 .so 版本错位导致「栈符号对不上」——
  用 build-id（`file *.so`、`readelf -n`）三方核对（exe/.so/符号包）是 2026 年容器调试的标准动作。
