> 本章按主题重写）。

## 核心概念速览（中英对照）

- **缺陷/故障** — bug / defect：程序实际行为与预期行为之差；debug 的「虫」，历史上有真蛾子（1947 Grace Hopper  relay 事故掌故，与本技术主题无关但常被引用 ⚠️）。
- **调试** — debugging：以观察、假设、验证的循环缩小「差异发生在哪」的搜索空间。
- **调试器** — debugger：能暂停目标、读改其内存与寄存器、并把这些状态翻译回源码层的程序。
- **调试符号** — debug symbols：编译器产出的「地址↔源码」元数据（函数名、行号表、类型、变量位置）。
- **DWARF** — DWARF debugging format：Linux/ELF 世界的主流调试信息格式，存于 `.debug_info`/`.debug_line` 等节。
- **PDB** — Program Database：MSVC 的调试信息载体（.pdb），Windows 生态对应物。
- **目标程序/被调试进程** — inferior / debuggee：被调试器控制的进程；GDB 语境称 inferior。
- **主机/目标** — host / target：运行调试器的机器与实际跑被调试程序的机器（可分离，见第 7 章）。
- **断点** — breakpoint：让目标在指定处停下的机制（第 2/3 章操作、第 10 章原理）。
- **单步** — stepping：`next`（逐语句）、`step`（入函数）、`finish`（跳出）三种粒度。
- **事后调试** — postmortem debugging：拿崩溃现场（core/转储）离线复原，而非在线暂停。
- **未定义行为** — undefined behavior (UB)：C/C++ 标准不施以要求的程序行为；本书后半部所有内存类 bug 的总根因。

## 动机：为什么「会写代码」不等于「会调试」

调试与开发的反馈回路不同：开发是「意图 → 代码」的正向展开，调试是「症状 → 原因」的逆向搜索。
C/C++ 把逆向搜索的难度拉到最高的那档，原因恰是原书 1.2「为什么选择 C/C++」要回答的（⚠️ 原书论述未持有，
以下为本笔记立场）：

1. **没有安全网**：Java/C# 的越界访问立刻抛异常；C/C++ 的越界写会静默破坏相邻内存，
   症状在几百万条指令之后才出现——「bug 的位置」与「症状的位置」可以相距任意远。
2. **抽象会漏**：指针、对象布局、调用约定、链接与装载全都暴露给程序员，任何一层理解错位都是一类 bug
   （对象布局的理论与 [../深度探索C++对象模型.md](../深度探索C++对象模型.md) 共享）。
3. **优化重写了你的代码**：Release 下 as-if 规则允许编译器删循环、换算法（高斯公式顶替累加循环），
   「我明明没执行这行」的困惑由此而来（第 9 章实测）。
4. **工具链是双人格的**：同一份代码要在 MSVC/PDB 世界与 gcc/DWARF 世界各调一遍——本书第 2/3 章成对出现就是为此。

## 机制：调试器到底是一个什么东西

剥掉 UI，任何调试器（VS、gdb、lldb、WinDbg）都是四个模块的组合：

| 模块 | 职责 | Windows 实现 | Linux 实现 |
| --- | --- | --- | --- |
| 目标控制 | 创建/附加/暂停/恢复/单步/杀 | Win32 调试 API：`CreateProcess(DEBUG_ONLY_THIS_PROCESS)` + `WaitForDebugEvent` 循环（第 10 章） | `fork/exec` + `ptrace(PTRACE_ATTACH/CONT/SINGLESTEP)`（第 10 章） |
| 符号引擎 | 地址↔名字/行号/类型 | 解析 PDB（微软私有格式） | 解析 DWARF（公开规范；GDB 自带解析器，lldb 用 LLVM 的） |
| 展开引擎 | 从任意栈深度重建调用链 | 走 x64 统一表式 UNWIND_INFO/SEH（Windows x64 栈回溯不需要帧指针） | rbp 链 + `.eh_frame` CFI；崩溃现场读 core |
| 表达求值 | 在目标进程里算表达式 `p vec.size()` | 编译表达式为目标机指令注入执行（或解释 DWARF 位置） | 同（GDB 有内置 C 编译器 JIT） |

关键洞察：**「暂停」是 OS 给调试器的特权，「看懂」是符号引擎给的恩惠**。
没有后者，你停在 `0x7ff6cc521548`，有的只是一堆寄存器；有了前者，
`bt` 能走通全靠编译器留的展开信息。这两点分别是第 10 章（机制）与第 1/9 章（符号）的主题。

一台调试器如何把「机器状态」映射回「源码状态」——以本机实测为证（已实测，objdump/GDB 17.1）：

```text
🔧 objdump -h wp.exe | grep debug
  9 .debug_aranges  ... DEBUGGING
 10 .debug_info     ... DEBUGGING     ← 类型/变量/函数的 DIE 树
 11 .debug_abbrev   ... DEBUGGING
 12 .debug_line     ... DEBUGGING     ← 行号状态机：地址→(文件,行)
```

`b wp.c:7` 做的事就是查 `.debug_line` 把「wp.c 第 7 行」反查成地址 `0x140001485`，再写断点；
`p sum` 查 `.debug_info` 里变量 `sum` 的 DWARF 表达式（本例是 `fbreg` 栈帧偏移）再读目标内存。

🔧 已实测（MinGW 工具链，Windows）：

```text
$ nm -C wp.exe | grep ' main'
0000000140001440 T main
$ addr2line -e wp.exe 0x140001440
main
D:/develops/tmp/cppsnippets_debug/wp.c:2
```

`addr2line` 单独可用说明：**符号化本质是离线可做的纯查表**——这正是第 8 章转储分析、
第 7 章远程调试「目标机不需要有源码/符号」的架构基础。

## 权衡：没有调试器的调试与全有调试器的调试

- **printf 派**：对时序敏感、跨进程、内核态场景（第 11 章驱动调试里 gdb 会改变时序），日志是唯一不扰序的探针；
  缺点是没有「现场」——症状出现时值早已变化。
- **调试器派**：断点给你「值正在被写坏的那一条指令」这种决定性现场（watchpoint，第 3 章实测）；
  代价是扰动（all-stop 模式冻结全线程，第 4 章）、以及与 Release 优化的对抗（第 9 章）。
- **回放派**（2026 工业主流增量）：rr/TTD 把「进程当录像带」，扰动为零且可倒退；见各章演进节。
- 调试方法论的通识骨架（任何流派共享的循环）：
  **复现 → 缩小（二分/隔离）→ 假设 → 取证（观察）→ 修复 → 回归防复发**；
  工具只决定「取证」一环的成本，而「复现」是 C/C++ 内存/并发 bug 的真正瓶颈——
  这就是为什么本书后半部（第 6/8 章）的现场保全技术比断点操作更值钱。
- 三者的选择不是立场问题，而是**问题对时序扰动的敏感度**决定的：
  heisenbug（怕观察）→ 回放/日志；确定但难缩小 → watchpoint 二分；语义错位 → 直接断点对照。

## 机制小结：一张「谁在骗我」的责任链

调试中最贵的问题是「眼前信息可不可信」。按本章的四模块模型给出一条判据链：

| 你看到的 | 可能骗你的环节 | 交叉验证手段（后续章节） |
| --- | --- | --- |
| 停在了某行 | `.debug_line` 非单调、内联 | `disassemble /m`（第 9 章实测） |
| 变量的值 | 位置过期、寄存器复用 | `info location`/裸内存 `x`（第 3 章） |
| 栈回溯的完整性 | 帧链断裂、优化删除 | CFI 平台知识（第 8 章）、`bt` 与汇编互证 |
| 崩溃点 | 症状≠作案 | ASan 双栈报告（第 6 章实测）、watchpoint |

这张表是整个目录版的浓缩索引：**每一行骗局的解药都在指定的那一章里被实测过**。

## 相邻概念对比

| 维度 | 调试器 (debugger) | 追踪器 (tracing/profiler) | 静态分析 (cppcheck/clang-tidy) | Sanitizer |
| --- | --- | --- | --- | --- |
| 介入时机 | 运行期，可暂停 | 运行期，不暂停 | 编译前/中 | 运行期，不暂停但即时报告 |
| 获得现场 | 完整内存/寄存器 | 事件流/采样 | 无（纯代码） | 崩溃点+分配点 |
| 时序扰动 | 大 | 小~中 | 无 | 2~10 倍减速 |
| 典型问题 | 「为什么错了」 | 「为什么慢/没来」 | 「哪里可能错」 | 「谁写坏了内存」 |

「BUG 与 Debug」的一层原书目录级事实（✅ 1.1 节名）之外，本笔记强调：**debug 的对象从来不是代码，
而是你的心智模型与机器实际行为之差**——第 10 章拆断点底层时这种「模型差」会被反复利用。

## 最新演进与工业实践

- **DWARF 5**（2017 定稿，dwarfstd.org）：行号表/分包（split DWARF）大幅瘦身，配合 `-gsplit-dwarf` 已是发行版构建默认；GDB 16/17、lldb 均已完整支持（核实状态：规范版本 ✅ 公开事实，本目录未逐条核对原书是否提及 DWARF5 ⚠️）。
- **PDB 开源化**：microsoft/mimalloc 无关，但微软已开源 `Microsoft.PDB` 解析器生态（LLDB 可直读 PDB）；WinDbg 全新 UI（microsoft/windebug 仓库）2024 年起成为默认调试器入口。
- **debuginfod**（elfutils 项目，源码仓库源分立于 sourceware.org/elfutils 与 dnf/debuginfod）：HTTP 服务集中托管发行版的分离 DWARF，gdb/lldb/binutils 原生按 build-id 拉符号——「Linux 侧符号服务器」落地，与 Windows 符号服务器（_NT_SYMBOL_PATH）对位。本目录 `09` 章实测对比。
- **libdebuginfo** 等统一解析层：跨 DWARF/PDB 的单一 API 尝试，工业渗透仍低（⚠️ 成熟度为本笔记判断）。
- **cppcheck / clang-tidy 前移**：`-Wall -Wextra` 已能在编译期抓住本章 dang.cpp 的悬垂返回（见 `06` 章实测：`[-Wreturn-local-addr]`），clang-tidy 的 `bugprone-*` 检查族是这条线的工业化——「最好的调试器是压根不需要调试」。
- **IDE vs CLI 分工现状**：VS/CLion 吃掉日常「断点+看变量」，CLI（gdb/WinDbg/lldb）守住转储分析、内核、远程三块 IDE 够不着的高地。本仓库用户（Windows+MinGW）双轨都要会，这正是本书 2/3 章成对结构在 2026 年的价值。
