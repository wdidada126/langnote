## 核心概念速览（中英对照）

- **内存泄漏** — memory leak：动态分配的内存失去全部引用，无法归还；慢性（耗尽）或急性（fork 放大）。
- **越界读写** — buffer overflow：访问分配区之外；栈越界即第 1 章 so.c 的邻居，堆越界则「作案与爆雷分离」。
- **释放后使用** — use-after-free (UAF)：访问归还给分配器的内存；堆调试器的「毒化填充」就是为把它当场化。
- **未初始化读** — uninitialized read：读从未写入的内存；MSan 的目标，第 3 章 watch 的 Old value 垃圾值是其温和展示。
- **堆元数据** — heap metadata：分配器记账区（空闲链/块头）；越界写先砸元数据 → 「free 时崩在 nt.dll/libc」的经典假现场。
- **调试堆** — debug heap：CRT 的带护栏分配器版本（`_CLIENT_BLOCK`、填充字节 0xCD/0xDD/0xFEEEFEEE、越界哨兵）。
- **红区** — redzone：ASan 在分配区两侧插的毒化字节；任何触碰立刻报告——「作案当场化」的通用配方。
- **影子内存** — shadow memory：ASan/MSan 以 1/8 比例映射记录每字节的可访问性；报告里 `fa fa fd fd` 行即其输出。
- **分配栈回溯** — allocation stack trace：Sanitizer 同时记录「这块内存是谁分配的」——双栈报告是定位泄漏/UAF 的决定性信息。
- **AddressSanitizer (ASan)** — 编译期插桩的地址错误检测器；`-fsanitize=address` / MSVC `/fsanitize=address`。
- **UBSan** — UndefinedBehaviorSanitizer：整数溢出/空解引用/坏 cast 的 UB 检查，`-fsanitize=undefined`。
- **LeakSanitizer (LSan)** — 退出时的可达性泄漏扫描，Linux 默认随 ASan 开启（Windows 不支持 ⚠️ 平台差异）。
- **Valgrind/memcheck** — 动态二进制插桩（无需重编译）的内存检查旗舰；慢 20~50 倍但能查未初始化传播。
- **毒化 (poison) / 去毒化 (unpoison)** — Sanitizer 标记区不可用的机制；自定义分配器需调用其注解 API。

## 动机：为什么内存 bug 必须换工具而不是换姿势

第 3 章的断点世界对内存 bug 有根本缺陷：**症状点≠作案点**。堆上越界写坏的可能是三个月后被 free 的邻居块，
栈上溢出踩的是另一函数的返回地址。人肉 gdb 走到尽头就是「在 case 里反复 `watch`」——槽位只有 4 个，
且要求你**已经知道**该盯哪个地址。Sanitizer/调试堆的共性是：**让分配器替你记录不变式，在触碰越界的指令上当场断**。

## 机制：四条诊断路径与本机实测

### 路径 A：编译器警告（前移的第一道）🔧 已实测

悬垂返回在 MinGW g++ 15.2 下 `-Wall` 即被抓住：

```text
dang.cpp:3:62: warning: address of local variable 'local' returned [-Wreturn-local-addr]
    3 | X* make_bad() { X local{42,...}; return &local; }
```

运行期后果同轮实测：`p->v` 读取处 gdb 收到 SIGSEGV（dang.cpp:7）——本例栈帧被后续调用覆盖后
指针域不可映射，「悬垂不必然出错」的反面教材 ⚠️（行为未定义，崩不崩都合法）。
**纪律：`-Wall -Wextra` 常开；把 Sanitizer 查不到的交给它。**

### 路径 B：Windows CRT 调试堆（6.1 的主内容 ⚠️ 原书细节未逐字核对）

- Debug 配置自动用 Debug CRT：分配带 0xFD 前后哨兵、释放填 0xDD、未初始化填 0xCD——
  内存窗口（第 2 章 2.5）里这些魔术字节一眼可读：`0xFEEEFEEE`=已 free 的堆块、`0xCDCDCDCD`=堆未初始化、
  `0xCCCCCCCC`=栈未初始化、`0xDDDDDDDD`=已删除（微软调试器填充谱系，公开事实）。
- `_CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF)` 退出时向调试输出打泄漏清单；
  `_CrtDumpMemoryLeaks()` 手动时点；`_CrtSetBreakAlloc(N)` 在**第 N 次分配的当场**下断——
  这是「把泄漏从结果化变成过程化」的经典杀招，思想与 ASan 的分配栈同构。

### 路径 C：ASan 双侧（Linux gcc/clang + Windows MSVC）🔧 已实测

**MSVC 14.43 实测**（VS2022，vcvars64 环境）：`cl /nologo /Zi /fsanitize=address heap.c` 后运行，
heap.c 里 `a[4]=99`（分配 4 个 int 后越界写）当场被抓：

```text
==21448==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x113d6fca01e0
WRITE of size 4 at ... thread T0
    #0 in main D:\develops\tmp\cppsnippets_debug\heap.c:5
0x113d6fca01e0 is located 0 bytes to the right of 16-byte region [...]
allocated by thread T0 here:
    #0 in malloc ...
    #1 in main D:\develops\tmp\cppsnippets_debug\heap.c:4
SUMMARY: AddressSanitizer: heap-buffer-overflow heap.c:5 in main
Shadow bytes around the buggy address:
   ... fa fa 00 00 [fa] fa fd fd ...
```

读法（每处都是教学点）：**双栈报告**（作案栈 + 分配栈）；`fa` = 红区影子码，`[fa]` 指出越界落点；
「0 bytes to the right」= 差一个字节出界。**同轮实测**：MinGW g++ 15.2 **无 ASan 运行时**
（`-fsanitize=address` 链接期 `cannot find -lasan` 失败）——Windows 的 gcc 系至今没有可用的
libasan 分发（⚠️ MSYS2 部分构建带实验支持，本机 MinGW-Builds 没有）。
→ Windows 用户路线：**MSVC/clang-cl + /fsanitize=address**，或 WSL 内 gcc/clang。

**Linux 侧**（标准用法，非本机）：`-fsanitize=address -g -fno-omit-frame-pointer`；
`ASAN_OPTIONS=detect_leaks=1 halt_on_error=0` 控制行为；报告同款双栈。

### 路径 D：Valgrind（6.2 Linux 段 ⚠️ 原书讲解未核对）

`valgrind --leak-check=full --track-origins=yes ./prog`：零重编译、查未初始化值**来源**
（track-origins 是其独门），代价 20~50 倍减速与不支持 ASLR 密集环境。2026 定位：
有源码可重编译 → ASan 优先；不能重编译/怀疑第三方发行版 → Valgrind。

## 权衡：各工具的捕获面矩阵

| bug | -Wall | CRT调试堆 | ASan | UBSan | Valgrind | MSan | 裸 gdb watch |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 栈上悬垂返回 | ✅(常见) | ➖ | ✅(stack-use-after-scope 需选项) | ➖ | ⚠️部分 | ➖ | ✅ |
| 堆越界 | ➖ | ✅(哨兵) | ✅ 当场 | ➖ | ✅ | ➖ | ❌ |
| UAF | ➖ | ⚠️(0xDD 需人看) | ✅ | ➖ | ✅ | ➖ | ❌ |
| 泄漏 | ➖ | ✅(清单) | ✅(LSan,Linux) | ➖ | ✅ | ➖ | ❌ |
| 未初始化读 | ⚠️ | ⚠️ | ➖ | ➖ | ✅ | ✅ 唯一强项 | ❌ |
| 数据竞争 | ❌ | ❌ | ❌ | ❌ | ✅(DRD/Helgrind 弱) | ❌ | ❌ |

（✅=可靠捕获 ⚠️=部分/需姿势 ➖=非其目标 ❌=无能为力；各列细节以官方文档为准。）

## 相邻概念对比

- 调试堆 vs ASan：前者运行时记账（无需重编译为特殊版，但要 Debug CRT），后者编译期插桩+影子内存
  （Release 可跑、双栈报告、还能查栈越界）；思想同为「护栏+当场断」。
- ASan vs UBSan：ASan 管「地址可不可触」，UBSan 管「运算合不合法」（有符号溢出、坏枚举 cast）——可同开。
- Sanitizer vs rr/TTD：前者「作案当场」，后者「任意回看」；互补，见 11 章与第 10 章演进。
- 本仓库另一册 [../高效CC++调试.md](../高效CC++调试.md) 第 2/3 章从堆元数据结构（ptmalloc/tcmalloc）
  讲「为什么越界会毁元数据、如何手读被毁现场」——调试器派最后的浪漫，建议与本章工具派对读。

## 最新演进与工业实践

- **经典论文核实记录**：AddressSanitizer 论文 Serebryany & Iskhakov, *"AddressSanitizer: An A Practical Memory Error
  Detector"*, ASPLOS 2012。**网传 DOI `10.1145/2150976.2151003` 经本机 Crossref API 实测解析到的是 CRUISE 论文
  （Jaleel 等，pages 249–260），并非 ASan** ⚠️；在 Crossref 检索中亦未能定位其准确 DOI，故本目录仅按标题+会场+年份引用。
  （这正是本书第 9 章精神的注脚：**一切引用先核实**。）
- **google/sanitizers 仓库**：文档/基准/兼容性的家；ASan/UBSan/LSan/HWASan 均已并入 clang/gcc 发行，
  仓库本身转为「知识库」形态——引用时以 llvm 官方 sanitizer 文档为准。
- **HWASan / MTE**：硬件标记内存（AArch64 top-byte-ignore）的 ASan 替身，Android 全线采用
  （google/sanitizers/hwasan 文档）；x86 侧对应方向是 **MTE/Intel PT 的 ASan 化**（第 10 章 Intel PT 条目）。
- **编译器支持现状**：clang 20/ GCC 15 的 ASan 支持 `-fsanitize-address-use-after-scope`、
  `container-annotations`；MSVC `/fsanitize=address` 自 16.9 起持续补漏（第 3 方库无插桩时的调用拦截等）。
- **CI 前移（工业默认）**：OSS-Fuzz/ClusterFuzzLite 把 ASan+UBSan+MSan fuzz 变成开源库准入线；
  对内部 C++ 工程即「一条 ASan 构建的流水线路」——把本章从「救火手册」变成「防火规范」。
  clang-tidy 的 `bugprone-*`、cppcheck 承接静态侧（第 1 章演进呼应）。
