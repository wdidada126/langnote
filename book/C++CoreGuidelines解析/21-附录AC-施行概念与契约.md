# 附录合读 A 施行 · B 概念 · C 契约 — In.force / Glossary / Contracts

> 本章目录版：[← 00-总览与阅读地图](00-总览与阅读地图.md) ｜ 单文件笔记：[../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md) ｜ 系列导航：[../C++系列·总索引.md](../C++系列·总索引.md)

**本章对象**：本书三个附录——附录 A"施行 C++ Core Guidelines"、附录 B"概念"、附录 C"契约"
——在指南侧没有一一对应的章（指南的附录是 A:Libraries / B:Modernizing code / C:Discussion /
D:Supporting tools 四件，实测标题）。本笔记按**主题**重挂资源：施行 ↔ In.force 节 + 指南
附录 B/D；概念 ↔ Glossary（实测 129 条术语，源自 Stroustrup《P:PPiC》词汇表）；契约 ↔
GSL.assert + 合约提案链。⚠️ 三个映射全部是推断，非本书原意逐字核对。

## 核心概念速览（中英对照）

- **施行** — enforcement：规则从文本变成事实的全部手段；"无执法的规则在大库不可管理"
  （In.force 首句）
- **四种执法** — code review / static analysis / compiler / run-time checks：机械优先，
  运行期检查"仅当无路可走"（In.force 原文排序）
- **抑制语法** — `[[gsl::suppress("tag")]]`：In.force 钦定的显式豁免（可带 message，
  C++11 属性语法）；Pro 章示例写作 `[[suppress("bounds")]]`——两处拼写不一致（实测原文）
- **渐变现代化** — gradual modernization（指南附录 B）：四条施工路线 + "自动化 modernizer
  工具是大规模升级的前提"判断
- **支持工具** — Appendix D：点名 clang-tidy（cppcoreguidelines-* 前缀）与 MSVC
  CppCoreCheck 两家"直属执法者"
- **概念表** — Glossary：129 条术语（ABI 到 undefined behavior），指南的"共同语言层"
- **具体类型** — concrete type（Glossary 词条）：5 章 C.11 抽象/具体二分在词汇表的根定义
- **契约** — contracts：前置/后置条件的语言化；"分布式膨胀"（distributed bloat）的反义词是
  把校验集中到接口
- **`Expects`/`Ensures`** — 契约的 GSL 占位宏（FAQ.59/60：不是 assert，是语法 placeholders）
- **`[[pre]]`/`[[post]]`** — 合约提案的目标语法（P2900R14 系，302 已验）

## 动机：三附录是正文的"地基三件套"

正文 20 章讲**写什么**；三附录补三个元问题——**怎么强制（施行）、词义边界在哪（概念）、
接口怎么承诺（契约）**。指南把它们散落在 In.force/Glossary/GSL.assert/附录 B-D 五处，
本书收拢成三个附录——这个"收纳动作"本身就是笔记价值所在：**施行是 19 章 profile 的目的，
概念是全部规则的语义前提，契约是 2 章 P.4"I&ES 之外第三支柱"的未竟之业**。

## 机制与深解析（主题 → 原文锚点 → 现代承接）

### 施行 1：In.force 的 dilemma 文体——先列愿望再认账

- 原文用五个 "But" 自我抬杠（要多规则 / 但没人读得多 / 但要子集 / 但乱选子集生乱……），
  结论是 profile（19 章）作为消解装置。**这段是全书方法论最短摘要**：规则众怒难犯 →
  子集 → 子集必须成建制 → profile。
- 执法偏好链条值得背下：code review（最弱）< 运行期检查（"仅当无路可走，且我们不想引入
  分布式膨胀"）< 编译器/静态分析（最强）。对照 🔧 实测证据链：18 章 const 成员两阶段
  初始化被编译器直接拒绝（最强档）；19 章 `_GLIBCXX_ASSERTIONS` 把静默 UB 降为运行期
  可定位崩溃（次强档）；`misc-header-include-cycle` 类 lint 居中（静态档）。

### 施行 2：`[[gsl::suppress("tag")]]` 与被遗忘的注解史

- In.force 规定工具**必须尊重**该抑制语法；Pro 章（19 章引）示例却是 `[[suppress("bounds")]]`
  ——同一文档两拼法（实测）。这段公案的真实结局：属性路线（P0380R1，wg21.link 302 已验，
  GSL.assert 节直链引用）败给了函数式合约语法（P2900R14 阵营批评属性"不是表达契约的正确
  语法"），suppress 亦随 GCC/Clang 对 `[[gsl::suppress]]` 无实现而停留在指南文本。
  ⚠️ "无实现"判断依据本机 g++ 15.2 与常识面，未逐一跑验证用例。
- 现代承接是**工具层配置**而非语言层：clang-tidy 行内 `// NOLINT`、`.clang-tidy` 的
  Checks 排除与 HeaderFilter 边界——豁免从代码注解迁到构建配置，可清点性反而更好。

### 施行 3：指南附录 B 的四条现代化路线

- "理想是全部升级→多数场景不可能"；逐模块（但改 ABI 的规则如 span 化**跨模块联动**，
  此路对接口规则不通）；自底向上（挑收益最大/噪声最小规则先做）；**接口先行**（先把
  资源不漏/指针不误用固化在边界，后面的藏其后慢慢改）。
- 与 17 章 A.1 稳定分层互证：接口先行路线其实就是"A.1 + profile 分批"的施工版；
  P.12（抽象要稳定）在此获得经济学理由。
- 工具支持判断（"没有自动 modernizer 就没有大升级"）已兑现为 clang-tidy 的
  `modernize-*` 家族（01–13 章各节多处引用，如 modernize-use-nullptr/use-override/
  make-unique——官方列表实测存在）：指南自己没等编译器厂商，先给规则配了改写器。

### 施行 4：附录 D 点名簿与其后的工具版图

- master 附录 D 仅两行点名（实测）：clang-tidy `cppcoreguidelines-*`（本机核对官方页
  43 项，19 章）与 Microsoft CppCoreCheck（⚠️ VS 侧现状未验证，本机 MinGW 无从运行）。
- 批评性补注：附录 D 的"只列直属工具"标准使它错过了真正的执法主力——编译器警告
  （-Wall -Wextra 家族，8/14/15 章 🔧 大量实测）与 sanitizers（10 章记录本机 MinGW
  无 libtsan/libasan，⚠️ 平台缺口）。今日实践排序：编译器诊断 > sanitizers（测试期）>
  clang-tidy（评审期）> 人工 review，附录 D 恰好倒过来。

### 概念：Glossary 129 条的正确用法——查"指南说的 object 是哪个 object"

- 高频歧义词条（均实测原文）：*object*（指南语境常含"资源句柄"远大于 std 定义）、
  *resource*（词条明列 memory/object/文件句柄/锁/套接字/线程——7 章 R 组作用域的定义源）、
  *concrete type*（"大小已知、可随处分配、不以基类方式用"——5 章 C.11 决策树的叶子定义）、
  *concept*（双义：想法 & 模板要求集——20 章 GSL.concept 标题的双关是故意的）。
- ABI/词条互指（"Contrast with API"）是 3 章 I.1"智能指针不入 ABI"论断的词汇支点：
  ABI 是"平台+OS 的规格"，而 unique_ptr 的移动语义让对象布局跨越编译单元可变——
  概念层读懂了，接口层规则就不再是教条。
- 术语表血统声明（"based off the glossary in Programming: Principles and Practice"）：
  指南刻意用**教学版**定义而非标准措辞——执法文本要能被工程师背下来。

### 契约：从 Expects/Ensures 到 P2900——三附录里唯一"未完成"的那件

- 现状栈（全部实测于 master 文本）：GSL.assert 宏（"yuck!"自供，FAQ.59/60 否认 assert
  同物）→ 指南直链 P0380R1 属性语法设想（302 已验）→ 当代共识转向普通函数调用式
  `contract{pre: ...}`（P2900R14 主流提案，302 已验；P2388R4 最小合约子集为其保守派
  同盟，302 已验）。
- 语义要点（正文已埋线）：违约默认 terminate（"contract_violation 不进异常体系"是
  P2900 系立场，11 章 🔧 std::expected 实测讨论过其互补性）；三档执法模式
  （observe/build 检查/disable 擦除）对应 19 章"运行期检查是次强档"的分层——合约把
  断言的**开关权**从 NDEBUG 的野蛮二分收归调用方策略。
- 本书附录 C 若含格林的手写合约例子，⚠️ 未与原文核对；本笔记以
  `Expects(size > 0)`（18 章 Picture 正解）+ P2900 语法映射为替身讲解：
  `int check_size(int size) [[expects r: size > 0]] { return size; }`（示意语法，
  非任何已 ship 编译器支持的拼写）。

## 权衡与边界

- **概念附录的不可执行性**：Glossary 无 Enforcement 节（逐条实测无此段落）——129 条里
  真正影响裁决的只有十余条（object/resource/ownership/bounds…），读法是从"会被争论的词"
  查起而非通读。
- **契约的成本面**：Expects 检查在热点内循环里可能就是那"分布式膨胀"（In.force 用词）；
  P.4 说"库不变量入类型"，契约处理剩余"每次调用都要重验"的部分——两者边界（构造期 vs
  调用期）至今无指南条款，属附录 C 地带的空白。
- **施行 vs 信仰**：附录 B 明言"改代码不是为了好看"——现代化必须能用新功能/维护/性能
  三种收益之一偿付风险；这条判据同时裁决了"要不要全开 43 个 cppcoreguidelines 检查"
  （答案：按 profile 分批，收益自证）。

## 相邻概念对比

- **本书附录 A vs 指南附录 B**：主题重合（施行/现代化策略），编号无关——引用时务必写明
  是哪个"附录 A"（本笔记三处歧义源：两书各一 + GSL 语境 FAQ）。
- **Glossary vs cppreference**：前者定义"指南如何用语"（意图导向，如 base class 词条
  含设计师意图），后者定义"标准如何规定"（规范导向）；同词不同义时以 Glossary 理解
  规则条文（⚠️ 对比为笔记立场）。
- **契约 vs 19 章 profile**：profile 禁**语言模式**（局部、静态、确定性），契约断言
  **值语义**（调用点、可运行期）——互补而非替代：Lifetime profile 治不了"值错但地址合法"。
- **`contract` vs 20 章 `not_null`**：类型能表达的不用断言（P.4 优先级），not_null 是
  "非空"的零成本类型化，Expects 留给类型吃不下的部分（如 `0 < size` 的数值域）。

## 最新演进与工业实践

- C++26 合约线：P2900R14/P2388R4 均 302 在案（本笔记实测清单），2024–2025 会议风向为
  最小化子集先行；若落地，本附录 C、GSL.assert、20 章 Expects 词条将三处同步改写。
- 工具承接现状：clang-tidy 已有 `cppcoreguidelines-pro-bounds-avoid-unchecked-container-access`
  （官方列表实测）把 19 章 Bounds.4 伸向标准库访问；C++26 hardening（libc++
  `_LIBCPP_HARDENING_MODE` 与 libstdc++ assert 线，16/19 章记录）实质是"库自带契约层"。
- 工业样本：abseil 以 `CHECK/DCHECK` 家族运营着事实上的 Expects 语义（多档执法模式），
  与 P2900 的 observe/build/disable 三档几乎同构——合约语言化前，工业界已用宏把语义
  跑通了十年（⚠️ CHECK 各档细节以 abseil 官方文档为准，未在本机验证）。
- 施行侧的静默革命：编译期求值（2 章 constexpr 🔧 实测）让一部分运行时契约升格为
  **编译错误**——In.force"机械优先"原则的最大红利其实来自泛型线而非 lint 线。
