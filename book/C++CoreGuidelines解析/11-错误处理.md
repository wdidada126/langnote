# 第11章 错误处理 — E: Error handling（E.1–E.31）

> 本章目录版：[← 00-总览与阅读地图](00-总览与阅读地图.md) ｜ 单文件笔记：[../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md) ｜ 系列导航：[../C++系列·总索引.md](../C++系列·总索引.md)

**本章对象**：current master 实测 E 组 21 条。结构是"一套正史 + 一条旁支"：E.1–E.19 默认异常路线，
E.25–E.28 专给"不能抛异常的环境"（no-exceptions 项目）留的错误码工程指南。
⚠️ 旧版 D 组（Function technique/设计侧）与 E 组部分条款交叉，重构后已并入 F/E/Con；
本书按新版行文。格林把本章称"体系结构章"——错误策略不是函数级决定，是**项目级宪法**（E.1）。

## 核心概念速览（中英对照）

- **错误处理策略** — error-handling strategy (E.1)：项目开局就定：异常/错误码/混合的适用边界
- **不变式中心** — design around invariants (E.4)：错误处理的对象是"被破坏的不变式"，不是"返回值不为 0"
- **异常=办不成差事** — exception for "can't perform task" (E.2/E.3)：异常专用于非常规失败，不当控制流用
- **构造即抛** — constructor throws (E.5/C.42)：造不出合法对象时的唯一体面出路
- **noexcept** — E.12：抛出即 terminate 的显式接受；析构/释放/swap 永不失败（E.16/C.36–C.37）
- **抛值捕引用** — throw by value, catch by reference (E.15)：对象切片决定捕获姿势
- **专用异常类型** — purpose-designed user-defined exceptions (E.14)：`throw int` 是接口自杀
- **final_action** — E.19：`gsl::finally`/`std::experimental::scope_exit` 的"稍后执行"原语
- **错误码** — error code (E.27)：不可抛环境里让 `std::error_code`/typed error category 系统性接管
- **errno 之罪** — E.28：全局状态式错误报告在并发世界失效
- **catch 顺序** — E.31：派生先于基类、具体先于 `...`，顺序错=静默吞异常
- **不每层都 catch** — E.17/E.18：捕获点放在"有能力处理"的层，不是"出事的那层"
- **可期望类型** — `std::expected<T,E>`（C++23）：错误码的类型系统化，异常/错误码两线的新汇流点

## 动机：为什么"异常 vs 错误码"在指南里不是站队题

E 章的写法很工程：默认推荐异常（构造失败、跨层传播、类型化错误对象），
但用五条规则（E.25–E.28）正面承认 no-exceptions 环境的合理性（嵌入式/硬实时/遗留 RTTI 禁用）。
格林的解析强调两句话：**混用不设边界才是灾难**（有的模块抛、有的返回码、有的静默——三套语义互不翻译）；
**错误处理的选择本质是生命周期问题**（资源章的异常安全=这里的展开安全）。

## 机制：失败传播的三条通道

```text
通道1 异常     构造期失败/跨层罕见失败        成本：零成本展开表+抛出路径慢
通道2 返回值   常规失败、预期内二态            std::optional / std::expected(C++23)
通道3 全局态   errno/setjmp/lastError         E.28 判死刑，仅 C 边界翻译时容忍
（旁路） terminate/abort：不可恢复+不可期望 —— 只在 E.26 fail-fast 语义下使用
```

## 代表性规则深解析（规则 → 理由 → 现代工具承接）

### E.1/E.4: 设计期定策略；围绕不变式设计
- 理由：错误路径数量常超成功路径；无策略=每个函数各发明一套，组合后无人能推理全项目失败语义。
- 承接：无单一检查器可查"策略缺失"——靠项目级 lint 配置、评审 checklist 与
  `bugprone-empty-catch`（已核对官方表）兜底；文档侧 C++23 `std::expected` 让"策略"能在类型签名中被读出。

### E.2/E.3/E.5: 异常的三个适用判据
- 理由："无法完成分配的任务"、不用于常规控制流、构造失败唯一出路（与 NR.3"别回避异常"呼应）。
- 承接：`-fno-exceptions` 项目（E.25–E.28 分轨）；MSVC `/EHsc`；静态分析对"构造函数返回错误码"零支持。

### E.6/E.13/E.16: 展开期的资源纪律
- 理由：栈展开只析构已构造的局部对象——裸 new 夹在两个构造之间就是泄漏缝；
  持有者析构中再抛=双重失败=terminate。
- 承接：🔧 07 章泄漏实测即 E.6 的反面证据；资源一律入句柄（unique_ptr/容器）杜绝展开缝隙；
  clang-tidy `bugprone-exception-copy-constructor-throws`（已核对官方表，
  专治异常对象拷贝构造抛出的连环雷）。

### E.12/E.16/F.6: noexcept 三兄弟
- 理由：`noexcept` 把"永不抛"写进类型：析构/swap/移动必须（E.16/C.36/C.66），
  硬实时关键函数应该（F.6）；违约即 terminate——承诺越硬越要显式。
- 承接：🔧 04 章 vector 扩容实测；clang-tidy `cppcoreguidelines-noexcept-destructor`、
  `cppcoreguidelines-noexcept-swap`（均已核对官方表）。

### E.14/E.15: 类型化异常与捕获姿势
- 理由：`throw 42;` 让捕获方无法用类型区分语义；按值捕获再抛会切片派生信息，按引用捕获零成本。
- 承接：clang-tidy `misc-throw-by-value-catch-by-reference`（已核对官方表，规则同名）；
  `catch (const std::exception&)` 成为标准"通配符"。

### E.17/E.18: 少 catch；在能处理的层 catch
- 理由：层层 catch 制造"吞异常"漏斗；"处理"的定义=恢复不变式/转换用户语义/记录并上抛——
  做不到就别 catch。
- 承接：clang-tidy `bugprone-empty-catch`（已核对官方表）专抓空 catch 黑洞。

### E.27/E.28: 不可抛环境的错误码工程学
- 理由：不用异常≠可以随手 return -1；错误码要有类型（enum+category）、有传播协议、有唯一出口点。
- 承接：`std::error_code`/`std::system_category`（C++11）；`std::expected<T,E>`（C++23）把错误码
  与返回值合并成可组合类型（`and_then/or_else` 单子链）——🔧 本章实测。

### E.31: catch 子句排序
- 理由：C++ 按声明顺序匹配第一个可行 handler，基类在前会把派生异常"吃掉"；
  `catch(...)` 永远最后。
- 承接：编译器 `-Wexceptions`（Clang 专报"catch 顺序遮蔽"，GCC 无此检——⚠️ 平台差异按文档表述）；
  clang-tidy 侧 `misc-*` 无专职，评审 checklist 兜底。

## 🔧 实测一：`std::expected`——错误码线的现代汇流（已实测 g++ 15.2）

```cpp
#include <expected>
#include <cstdio>
std::expected<int, int> divide(int a, int b) {
    if (b == 0) return std::unexpected(b);
    return a / b;
}
int main() {
    if (auto r = divide(10, 2)) std::printf("ok: %d\n", *r);
    if (auto r = divide(10, 0)) std::printf("?!%d\n", *r);
    else std::printf("error code: %d\n", r.error());
}
```

`-std=gnu++23 -O2 -Wall -Wextra` 真实输出：

```text
ok: 5
error code: 0
```

（`error code: 0` 是样本故意用 0 作除数错误码的结果——真实项目应换非零语义码，
格林式提醒：**expected 的正确性不在类型在编码约定**，E.27 原文。）

## 🔧 实测二：E.16 反面——`string::at` 的越界现场报告（已实测 g++ 15.2）

```cpp
#include <string>
#include <stdexcept>
#include <cstdio>
int main() {
    std::string s = "abc";
    try { char c = s.at(7); (void)c; }
    catch (const std::out_of_range& e) { std::printf("at(): caught: %s\n", e.what()); }
}
```

真实输出（libstdc++ 措辞）：

```text
at(): caught: basic_string::at: __n (which is 7) >= this->size() (which is 3)
```

同一越界在 `s[7]` 路径上什么都不说——"尽早捕获"（P.7）与"检查有名字"（ES.55）的对照。

## 权衡与边界

- **异常性能税的正确姿势**：零成本展开意味着"不抛时免费"，抛出路径的查表/unwind 才慢——
  热循环里用异常做控制流违反 E.3，与"异常慢"的玄学是两回事（对象模型笔记与调试艺术笔记有同类实测口径）。
- **`expected` 与异常的选型线**：预期内失败（用户输入、IO）→expected；真异常（内存耗尽、不变式崩塌）→异常。
  指南文本成书早于 C++23，此线由本目录版补位。
- **RTTI 被禁环境**：`-frtti` 关闭时 E.15 的"按引用捕层次"退化为按具体类型捕获——E 章在极端嵌入式
  的裁剪版。

## 最新演进与工业实践

- C++23：`std::expected`（P2505R5，wg21.link 实测 302）成为 E.27 线官方答案；
  契约路线：P2388R4（最小契约支持，实测 302）与 P2900R14（contract-based programming，实测 302）
  会把 E.2/I.5–I.8 的"前条件违反"从异常语义分离出来（断言 vs 可恢复失败的制度化）。
- C++26 方向：std.print 等 I/O 卫生降低 E.28 类全局态依赖（提案号未实测不引）。
- 工业界：LLVM `llvm::Error`/`Expected`（早于标准十年）、abseil `StatusOr`、protobuf 错误层次——
  均为"类型化错误值+禁止全局态"路线的规模化运营证据。
