# 第10章 并发 — CP: Concurrency and parallelism（CP.1–CP.201）

> 本章目录版：[← 00-总览与阅读地图](00-总览与阅读地图.md) ｜ 单文件笔记：[../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md) ｜ 系列导航：[../C++系列·总索引.md](../C++系列·总索引.md)

**本章对象**：current master 实测 CP 组 31 条，分节：CP.con（锁与线程管理）、CP.coro（协程三条）、
CP.par/CP.vec/CP.mess/CP.free/CP.etc。⚠️ 旧版编号体系里并发规则曾挂 `R.`（Concurrency）前缀
（R.1–R.45，如旧 R.1"不要假设单线程"），重构后整体迁到 CP——老评论区的"R.1"与新体系"R.1(RAII)"
同号不同文，引用务必看年份。格林在本章的基调：**并发正确性买的是"默认姿势"，不是"事后调试"**。

## 核心概念速览（中英对照）

- **数据竞争** — data race (CP.2)：同一内存位置的并发访问至少一写且无同步=UB（与"竞态条件"不同：后者是逻辑错）
- **任务优先于线程** — think in tasks, not threads (CP.4)：以工作单元建模，线程只是执行体
- **volatile 不是同步** — CP.8：volatile 只保证"每次真访存"（与设备内存对话），不保证原子性与顺序
- **RAII 锁** — CP.20：`lock_guard/scoped_lock/unique_lock`，禁裸 `lock()/unlock()` 配对
- **多锁一次到位** — `std::scoped_lock`（C++17，CP.21）：死锁预防的免死金牌（内部 deadlock avoidance）
- **持锁不跑外来代码** — CP.22：回调/虚调用在锁内=把死锁风险外包给全代码库
- **线程是容器** — CP.23/CP.24：joinable thread 是 RAII 资源；detach=失控的孤儿进程化
- **joining_thread** — CP.25：GSL 的"析构必 join"线程（`std::jthread` 入标前身的过渡物）
- **协程不挂锁** — CP.52：悬挂点（suspension point）跨持锁=协程调度器的死锁温床
- **协程参数按值** — CP.53：协程参数拷贝进帧，引用参数悬垂风险随挂起放大
- **future/async** — CP.60/CP.61：跨任务传值的标准通道；`std::async` 的 launch 策略语义要读透
- **无锁编程门槛** — CP.100–CP.111：除非证明必要+研究过文献+用成熟模式（含双检锁的正规姿势）
- **锁伴数据** — CP.50：mutex 与被保护数据同生共死（同类封装/`synchronized_value`）
- **锁对象要命名** — CP.44：`lock_guard{...}` 匿名临时量=当场解锁的空操作

## 动机：为什么并发规则"少而贵"

CP 组数量不及 ES 一半，但格林给它的篇幅最重——每条背后都是不可逆的事故类别
（死锁、竞态、UB 级数据竞争）。与 03/04/07 章"写错能编译失败"不同，并发错误**能编译、能测试通过、
能在生产环境以万亿分之一概率发作**。所以本章规则全部服务于一个目标：把并发写法的
"默认形态"调成可静态/动态检查的形态。

## 机制：四个同心圆

```text
第1圆  模型层   任务/消息传递（CP.4/CP.60–61）→ senders（C++26 方向）
第2圆  卫生层   数据竞争与 volatile 语义（CP.1–CP.3/CP.8）
第3圆  资源层   线程与锁的 RAII（CP.20–CP.26/CP.44/CP.50）
第4圆  精英层   协程（CP.51–53）与无锁（CP.100–111）——默认禁用，持证上岗
```

## 代表性规则深解析（规则 → 理由 → 现代工具承接）

### CP.1/CP.2: 假设你的代码将运行在多线程程序里；避免数据竞争
- 理由："我的函数没写并发"不构成安全论证——调用方决定线程模型；
  竞争是 UB 不是"偶尔错值"，编译器有权按"无竞争"优化出更离奇的行为。
- 承接：ThreadSanitizer（`-fsanitize=thread`）；🔧 本章实测其在本机 MinGW 缺 `libtsan`；
  工业平台侧 MSVC `/fsanitize=thread` 同样缺席，Windows 现实路径=WSL/Linux 跑 TSan
  （对照 [../C++代码调试的艺术/04-多线程死锁调试.md](../C++代码调试的艺术/04-多线程死锁调试.md) 与
  [../C++并发编程实战2/11-多线程应用的测试和除错.md](../C++并发编程实战2/11-多线程应用的测试和除错.md)）。

### CP.4: Think in terms of tasks, rather than threads
- 理由：线程是稀缺执行体不是业务单元；以任务建模自然得到队列、取消、背压与线程数治理。
- 承接：`std::async`（CP.61 配套）；C++26 senders/receivers（P2300R10，wg21.link 实测 302）
  把"任务"升格为标准库对象；folly::coro/task 是工业现成品。

### CP.8/CP.200: Don't try to use `volatile` for synchronization
- 理由：volatile≠atomic——无顺序保证、无原子性保证；把它当同步用是 C++ 并发第一大民间迷信
  （Windows 头文件曾逼出这种用法）。
- 承接：`std::atomic`（C++11）与 `std::atomic_ref`（P0019R8，实测 302，C++20：给已有对象临时附加原子操作）；
  `-Wvolatile` 类告警不拦误用，靠 code review 清单。

### CP.20/CP.21: RAII 锁；`std::lock()`/`std::scoped_lock` 拿多把锁
- 理由：裸 lock/unlock 在异常/早退路径必然漏解锁；多锁顺序错开=教科书死锁。
- 承接：C++17 `std::scoped_lock`（CTAD 免命名，顺带治好 CP.44 的匿名锁病）；
  clang-tidy `bugprone-unused-raii`（已核对官方表）专抓"构造即析构"的匿名锁/条件变量；
  死锁本体仍靠 TSan 与锁序评审。

### CP.22: Never call unknown code while holding a lock
- 理由：回调/容器元素操作/虚函数在锁内触发不可知重入——锁图出现环只是时间问题。
- 承接：结构手段=把"值拷贝出锁再调用"固化为模式（CP.3 精神）；静态侧无通用检查器
  （过程间分析在 clang-tidy 缺位），属"纪律层"规则。

### CP.24/CP.25/CP.26: 线程是全局容器；prefer joining_thread；禁 detach
- 理由：detach 的线程活着时所有它引用的栈对象都可能已经下葬；joinable 即资源（R 章延伸）。
  `gsl::joining_thread` 在 C++17 时代给"永不裸 join"一个句柄。
- 承接：🔧 本章实测 `std::jthread`（C++20）+ stop_token——标准库已吸收 CP.25 全部动机，
  joining_thread 退位为兼容概念（[../Effective_Modern_C++/07-并发API.md](../Effective_Modern_C++/07-并发API.md) item 39 对偶）。

### CP.50: Define a mutex together with the data it guards
- 理由：锁与数据分家=每个访问点都要回答"现在持的是哪把锁"；同封装后答案由类型给出。
- 承接：GSL `synchronized_value<T>`（20 章）；absl::Mutex 注解（`ABSL_GUARDED_BY`，clang 线程安全分析
  `-Wthread-safety` 可检——这是本章少数进编译器的检查）。

### CP.51–CP.53: 协程三禁（捕获式协程 lambda/跨悬挂点持锁/引用传参）
- 理由：协程帧的生命周期由 promise/awaiter 体系搬运，lambda 捕获与引用参数的"对象寿命假设"
  全线失效；持锁挂起=在调度器手里攥着别人要的钥匙睡着。
- 承接：C++20 协程由 P0912R5（wg21.link 实测 302）并入；folly::coro、cppcoro 的规范姿势与三禁一致；
  语言侧"修复"路线：P2742R2（"Avoid capturing 'this' implicitly by copy"，实测 302）等捕获语义改进
  间接缓解 CP.51。

### CP.100/CP.110: 无锁门槛；不要手写双检锁
- 理由：内存序是"硬件+编译器"的联合协议，个人智力不是适格主体（CP.101/102 同文）；
  初始化双检锁有现成免费替身。
- 承接：CP.110 的标准答案是两把现成锁-free 设施——静态局部变量初始化的线程安全（C++11
  "Magic Statics"）与 `std::call_once`；无锁容器一律用 folly 等成熟库。

## 🔧 实测：CP.25 的现代承接 `std::jthread`（已实测 g++ 15.2，静态链接运行）

```cpp
#include <thread>
#include <atomic>
#include <cstdio>
int main() {
    std::atomic<int> n{0};
    std::jthread worker([&n](std::stop_token st) {     // CP.23/25：自动 join，永不 detach
        while (!st.stop_requested()) { ++n; std::this_thread::sleep_for(std::chrono::microseconds(200)); }
    });
    std::this_thread::sleep_for(std::chrono::milliseconds(20));
    worker.request_stop();
    std::this_thread::sleep_for(std::chrono::milliseconds(5));
    std::printf("worker iterations=%d, joined automatically\n", n.load());
}
```

`-std=gnu++20 -O0 -Wall -Wextra -static` 真实运行输出：

```text
start
worker iterations=168, joined automatically
```

（注一：`start` 行来自样本内前置打印；注二：本机动态链接的同名二进制在 Git Bash 下运行异常
（exit=127），改 `-static` 后稳定——MinGW 线程运行时的平台小坑，如实记录。注三：
`-fsanitize=thread` 在本机链接失败：`cannot find -ltsan`，TSan 缺席实证——CP.2 的运行期检查
需转 WSL/Linux/MSVC 平台。）

## 权衡与边界

- **CP.31 传值 vs 共享**：小数据跨线程传值最安全，大数据共享又回到锁/无锁——指南给的判据是
  "先共享不可变（值拷贝/只读快照），再考虑同步可变"。
- **jthread 不是银弹**：线程池/任务图仍需要手工调度；CP.4 的任务模型在标准库（至今）只是半成品。
- **协程规则的地基薄**：CP.51–53 的多数结论来自实现经验而非形式验证——格林提醒该组更新最快。

## 最新演进与工业实践

- C++20 承接了本章三条：`jthread/stop_token`（CP.25 正解化）、`std::scoped_lock` CTAD（CP.21）、
  `atomic_ref`（P0019R8，实测 302）。
- C++26 方向：senders（P2300R10，实测 302）为 CP.4 提供标准任务对象；协程内存治理
  （P2573R2 生命周期分析，实测 302）与 CP.53 同题。
- 工业界：folly（` folly::coro`、`Baton`）、seastar（share-nothing 消息传递=CP.par/CP.mess 的
  极端工业答案）、tokio（Rust）证明"任务+消息"模型可运营十亿级设备——指南的方向性得到市场背书。
