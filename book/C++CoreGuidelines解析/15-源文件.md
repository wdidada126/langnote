# 第15章 源文件 — SF: Source files（SF.1–SF.22）

> 本章目录版：[← 00-总览与阅读地图](00-总览与阅读地图.md) ｜ 单文件笔记：[../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md) ｜ 系列导航：[../C++系列·总索引.md](../C++系列·总索引.md)

**本章对象**：current master 实测 SF 组 16 条，管三件事：**文件与头的物理纪律**（SF.1–SF.13）、
**namespace 逻辑结构**（SF.20–SF.22）、以及它们背后的 ODR/链接语义。⚠️ 旧版 S 组（S.1–S.21）
与 NL 命名节内容有重叠搬迁，本书按新版行文。格林给本章的定位是"构建系统视角的 C++"——
头文件不是"复制粘贴池"，是**接口单元+编译期依赖图上的边**。

## 核心概念速览（中英对照）

- **翻译单元** — translation unit (TU)：一个 .cpp 加其全部 include 闭包=独立编译宇宙；ODR 的舞台
- **头文件=接口** — header as interface (SF.3/SF.5)：跨 TU 的声明进头，每个 .cpp 带上自己的"出生证"头
- **包含守卫** — #include guard (SF.8)：`#ifndef X_H` 三件套；`#pragma once` 为流行非标准替身
- **自足头** — self-contained header (SF.11)：头单独编译通过=不依赖包含顺序=依赖图可信
- **隐式包含之罪** — avoid implicit includes (SF.10)：用 `std::vector` 却没包 `<vector>`，靠别人先包含=沙上堡
- **引号 vs 尖括号** — SF.12：项目内相对路径用 `""`，外部/标准用 `<>`——给工具留寻址线索
- **ODR（单一定义规则）** — one definition rule：非 inline 函数在头里定义=双 TU 各一份符号=链接期爆炸
- **using namespace 三许可** — SF.6：过渡期/基础库（std）/局部作用域，其余皆禁区
- **头文件全局 using 之禁** — SF.7：头里 `using namespace std;` 把污染广播给所有用户
- **匿名命名空间** — unnamed namespace (SF.21/SF.22)：TU 内部实体的正确封装（旧 `static` 的现代语）
- **循环依赖** — cyclic dependency (SF.9)：a.h→b.h→a.h 靠守卫"看似工作"，实为接口不可分拆的病体
- **模块** — modules（C++20）：`.ixx`/header-unit 路线，终极终结 include 纪律全族问题

## 动机：头文件是 C++ 最古老的"分布式系统"

每个 .cpp 独立编译、链接器最后对账——这模型三十多年没变，SF 章的全部条文都是这套
分布式协议的操作手册。格林举的例很有工业味：一次 `<vector>` 移除引发的跨仓库连环编译失败
（SF.10 反例：某个头一直替全公司"捎带"标准库）；以及 include guard 缺失时"第二次包含报重定义"
的无辜事故（🔧 本章实测）。

## 机制：物理设计的三条边

1. **内容边**：声明进头（SF.2/SF.3）、定义进 .cpp（SF.2 反面=🔧 实测链接爆炸）、
   inline/模板是合法越境者（ODR 白名单）；
2. **包含边**：守卫（SF.8）、自足（SF.11）、无环（SF.9）、顺序（SF.4，配套 include-what-you-use）；
3. **名字边**：namespace 表逻辑组件（SF.20）、内部实体匿名化（SF.22）、using 的方向纪律（SF.6/7）。

## 代表性规则深解析（规则 → 理由 → 现代工具承接）

### SF.2: A header file must not contain object definitions or non-inline function definitions
- 理由：头被 N 个 TU 包含=定义复制 N 份；非 inline 函数违反 ODR，轻则链接器报 multiple definition，
  重则"每 TU 状态独立"的全局对象静默精神分裂。
- 承接：🔧 实测二（双 TU 链接现场）；`inline`（C++17 对 static data member 的隐式豁免）；
  链接器 `--detect-multiple-definition` 族兜底；模块后该问题结构性消解。

### SF.8: Use #include guards for all header files
- 理由：守卫让头可被多次包含（分布式包含图的必然）；`#pragma once` 依赖文件系统身份，
  在网络盘/符号链接/头合并工具下有边界案例。
- 承接：🔧 实测一；现代工具：`#include_next` 冲突检查、include-guard 检查器（clang-tidy
  `llvm-header-guard` 属 LLVM 专用模块，⚠️ 通用 CI 多用脚本+IWYU 的 @file guard 检查）。

### SF.10/SF.11: 隐式包含之禁、自足头
- 理由：依赖别人头文件的"捎带包含"=把编译成功寄存在他人的实现细节上；标准库升级/重排即爆。
- 承接：include-what-you-use（IWYU，clang 系工具）自动生成"该 include 的/该删的"清单；
  libc++/libstdc++ 头瘦身工程（每次版本升级重划传递包含）持续教育社区——**不要依赖传递闭包**。

### SF.6/SF.7: using namespace 的三条许可与一条红线
- 理由：名字查找从" TU 内可读性"变成"全局冲突风险"；头里的 using 把成本转嫁给全部下游。
- 承接：clang-tidy `misc-unused-using-decls`（已核对官方表）清理冗余 using；
  `-Wshadow` 抓 using 后的遮蔽事故；模块化后 `using namespace std;` 局部化（函数体内）成为指南认可的写法。

### SF.20–SF.22: namespace 即架构
- 理由：namespace 是免费的逻辑组件边界（项目名→组件→版本层级）；内部符号匿名化=不导出+防符号撞车。
- 承接：clang-tidy `misc-use-anonymous-namespace`（已核对官方表，`static` 全局→匿名 ns 迁移）；
  符号表可见性治理（`-fvisibility=hidden`+导出宏）见 [../C++API设计/07-C++用法与符号导出.md](../C++API设计/07-C++用法与符号导出.md)。

### SF.9: 避免循环依赖
- 理由：环=两个头不可独立复用/测试/替换；守卫"止错"但不治本，重构方向是按 A 章（架构）分层。
- 承接：依赖分析工具（deps/cyclo 图、`nm`+`objdump` 实测路线见 API 设计笔记）；Pimpl 常是断环手术刀（I.27）。

## 🔧 实测一：SF.8 缺失——重复包含的重定义现场（已实测 g++ 15.2）

```cpp
// point.h（无守卫）:  struct Point { int x, y; };
// main.cpp          :  #include "point.h"
                      #include "point.h"   // 第二次包含
```

`-std=gnu++17 -Wall -Wextra -c` 真实报错：

```text
error: redefinition of 'struct Point'
note: previous definition of 'struct Point' is here
```

（同一 TU 两次 textual include，守卫缺失时编译器不给你"第二次免罪"——
include guard 一行成本对冲的就是这种链接期前的当场击毙。）

## 🔧 实测二：SF.2 违规——头里放非 inline 函数定义的链接爆炸（已实测 g++ 15.2）

```cpp
// evil.h:  inline int ok(){return 1;}  int bad(){return 2;}   // bad 违规
// a.cpp 与 b.cpp 各自 #include "evil.h" 并调用
```

`g++ -std=gnu++17 a.cpp b.cpp` 链接阶段真实报错（节选）：

```text
ld.exe: b.cpp:(.text+0x0): multiple definition of `bad()'; a.cpp:(.text+0x0): first defined here
```

`ok()`（inline）安然无恙、`bad()` 当场对账——ODR 的执行部门其实是链接器，
这条边界正是 SF.2 的存在理由。

## 权衡与边界

- **守卫 vs pragma once**：MSVC 生态 pragma once 主流、GCC 生态守卫主流——混用时以"能被复制的
  文件系统语义"为安全底线；指南站在标准侧。
- **头文件拆分的粒度政治**：`std::bit_cast` 这类小函数进哪个头都有争论；SF 章的原则只有一条——
  **接口成族、实现下沉**。
- **`.inc`/模板显式实例化的灰色区**：模板定义进 .ipp 被包含是合法越境；指南认可但工具链支持参差。

## 最新演进与工业实践

- C++20/23：modules（header unit/import std）直接改写 SF.2/SF.10/SF.11 的问题域——
  BMI（编译模块接口）取代 textual 闭包；`import <vector>;` 兼容层让迁移渐进
  （⚠️ modules 相关提案号未逐一实测，不引 P 号）。
- C++26 方向：模块与 include 的共存治理持续（⚠️ 同上不引 P 号）。
- 工业界：Google/Azure 大型 monorepo 的 IWYU+include-what-you-clean CI 门禁是 SF 组的工业化执行；
  CMake 的 `target_include_directories` 现代用法（PRIVATE/PUBLIC 传播控制）把 SF.10 的成本模型
  搬进构建系统（对照 [../深度探索C++对象模型/](../深度探索C++对象模型/00-总览与阅读地图.md) 的 ABI 侧账本）。
