# 第3章 接口 — I: Interfaces（I.1–I.30）

> 本章目录版：[← 00-总览与阅读地图](00-总览与阅读地图.md) ｜ 单文件笔记：[../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md) ｜ 系列导航：[../C++系列·总索引.md](../C++系列·总索引.md)

**本章对象**：接口=调用方与实现方之间的契约边界。current master 实测 I 组 20 条规则
（I.1–I.8、I.9–I.13、I.22–I.30，中间 I.14–I.21 等空洞是历史合并/移组的痕迹）。
格林的解析主线：**接口 bug 的成本 = 波及的调用点数**，所以接口章是全书"投资回报率最高"的一章。

## 核心概念速览（中英对照）

- **显式接口** — explicit interface (I.1)：参与计算的数据必须经参数显式进入，或声明为（可见的）全局状态
- **隐式接口** — hidden/invisible interface：可变全局、`this` 捕获、文件级状态——编译通过但行为不可推
- **强类型参数** — precisely and strongly typed (I.4)：用类型区分单位/语义（`Meter` vs `Yard`），拒收错型调用
- **前置/后置条件** — pre-/postcondition (I.5/I.7)：`Expects()`/`Ensures()` 写在接口而非口头
- **概念文档化** — document template parameters using concepts (I.9)：模板参数要求用概念表达（C++20 已入标）
- **裸指针不传递所有权** — never transfer ownership by raw pointer (I.11)：`T*`/`T&` 恒为非拥有视图
- **非空指针** — `not_null<T>` (I.12)：把"永不为 nullptr"升级为类型承诺（GSL）
- **数组+长度** — don't pass an array as a single pointer (I.13)：长度必须随行（`span` 的前身要求）
- **单例禁忌** — avoid singletons (I.3)：隐藏依赖+初始化顺序+测试不可替换三重罪
- **Pimpl** — pointer to implementation (I.27)：以间接层换编译防火墙与 ABI 稳定
- **交叉编译器 ABI** — C-style subset (I.26)：跨编译器边界退化到 C 子集是现实妥协
- **封装违规点** — encapsulate rule violations (I.30)：非可避免的脏代码集中到一个函数里

## 动机：接口是缺陷的震中

C++ 缺陷统计的老经验（Google/MSVC 团队均报告过类似分布）：绝大多数现场事故源于
"参数错了没人拦"（缺 I.4/I.12/I.13）与"全局状态被动过"（缺 I.1/I.2）。接口章的规则全部是
**把口头承诺升级为类型系统或工具可检查的承诺**。这也是本章与第 4 章（函数内部设计）的分界线：
I 章管"边界上必须说什么"，F 章管"边界之内怎么实现"。

## 机制：三类手段把接口收紧

1. **类型手段**：强类型参数（I.4）、`not_null`（I.12）、`span`（I.13→R.14）、枚举（Enum 章）——
   让非法调用不编译；
2. **契约手段**：`Expects/Ensures`（I.5–I.8）——非法调用运行期出局（P.6/P.7 的落地）；
3. **结构手段**：抽象基类作接口（I.25）、Pimpl（I.27）、减少参数（I.23–I.24 参数包 struct 化）——
   让接口形状本身难以误用。

## 代表性规则深解析（规则 → 理由 → 现代工具承接）

### I.1: Make interfaces explicit
- 理由：函数行为依赖未声明的状态（可变全局、TLS、`[&]` 捕获的外围变量）时，调用点无法审计影响面。
- 承接：clang-tidy `cppcoreguidelines-interfaces-global-init`（名称已核对官方表）；
  `cppcoreguidelines-avoid-non-const-global-variables` 承接 I.2；静态分析器把隐式依赖列为专项。

### I.4: Make interfaces precisely and strongly typed
- 理由：`double` 传米还是码、`int` 传索引还是计数——弱类型签名让"合法但错误"的调用畅通无阻。
- 承接：🔧 本章实测强类型别名直接编译失败；C++20 `std::concepts` 让"接受任何 Number 但拒 Unit"可读化；
  units 库（如 nholthaus/units）提供量纲模板。

### I.11: Never transfer ownership by a raw pointer or reference
- 理由：所有权是资源章的第一变量；裸指针语义在指南新体系里被钉死为"非拥有视图"（R.3 互为表里）。
- 承接：clang-tidy `cppcoreguidelines-owning-memory`；`std::unique_ptr`（C++11）+ `std::move` 语义
  （[../Effective_Modern_C++/04-智能指针.md](../Effective_Modern_C++/04-智能指针.md)）。

### I.12: Declare a pointer that must not be null as not_null
- 理由：`T*` 可空的默认语义让每个解引用点都要自证非空；`not_null<T>` 把证明责任移到构造点一次完成。
- 承接：GSL `not_null`（见 [20-Guidelines支持库](20-Guidelines支持库.md)）；C++26 契约提案
  （P2900R14，wg21.link 实测 302）试图把这类"参数永真承诺"语言化。

### I.13: Do not pass an array as a single pointer
- 理由：指针不带长度，边界检查无从谈起——本书"边界检查"主题的第一块多米诺（详见 07/08/16 章）。
- 承接：C++20 `std::span`（P0896R4，实测 302，随 ranges 合入）；GSL `span` 是 C++17 前的替身；
  clang-tidy `cppcoreguidelines-pro-bounds-pointer-arithmetic`。

### I.23/I.24: 参数数量与相邻参数对调
- 理由：>4 参数的调用点易错位；相邻同型参数交换（`draw(x, y)` 调成 `draw(y, x)`）编译器看不见。
- 承接：clang-tidy `bugprone-easily-swappable-parameters`（名称已核对官方表）；聚合参数 struct 化
  （与 F.21 "返回 struct" 同族手法）。

### I.25: Prefer empty abstract classes as interfaces
- 理由：带状态的基类强迫派生类接受布局与构造协议；纯接口（全纯虚）才支持多继承合成（C.135 呼应）。
- 承接：Java `interface` 式用法在 C++ 的等价物；`std::function`/concepts 在"单方法接口"场景的竞争替代（05/13 章）。

### I.27: For stable library ABI, consider the Pimpl idiom
- 理由：成员变量布局改动即 ABI 断裂；pimpl 把私有成员移出头文件，换来重编译防火墙。
- 承接：本仓库实测过 sizeof 对照与析构坑——[../C++API设计/02-不透明指针与Pimpl.md](../C++API设计/02-不透明指针与Pimpl.md)；
  代价（堆分配+间接访问）在 09 章 Per.13 有账。

### I.30: Encapsulate rule violations
- 理由：工业代码总有躲不开的违规（遗留 C API、平台怪癖）；把违规压进一个函数=审查面积最小化。
- 承接：clang-tidy 文件级/函数级 `NOLINT` 粒度收敛（全文件禁言是反模式）。

## 🔧 实测：I.4 强类型拦截单位混用（已实测 g++ 15.2）

```cpp
struct Meter { double v; };
struct Yard  { double v; };
int main() {
    Yard y{1.0};
    Meter m = y;   // I.4 合规写法期待：不编译
    return (int)m.v;
}
```

`-std=gnu++17 -Wall -Wextra` 真实报错：

```text
t03_strongtype.cpp:5:15: error: conversion from 'Yard' to non-scalar type 'Meter' requested
```

若两侧都退化成 `double`（指南批评的弱接口），同样的笔误直接通过编译——这就是 I.4 的性价比论证：
**一次类型定义，换来所有调用点的永久卫兵**。

## 权衡与边界

- **强类型的膨胀税**：每个语义概念一个新类型，模板匹配与转换成本上升；常用折中=using 别名+概念约束。
- **not_null/span 不在标准（至今）**：GSL 依赖带来跨编译器协调成本；纯标准库替代
  （`std::span` 有、`not_null` 无）让承诺降级为文档。
- **契约的可执行性**：`Expects` 只在开了检查的构建里生效——release 关掉时接口承诺变纸面（附录 A 主题）。

## 最新演进与工业实践

- C++20：`span`、`starts_with/ends_with`（字符串接口卫生）、concepts 承接 I.9；
  P2674R1（"out" 参数性能方案，实测 302）与 F.20/I 章出参主题持续发酵。
- C++26 在途：contracts（P2900/P2388，均实测 302）目标就是把 I.5–I.8 变成语言设施；
  若通过，`Expects/Ensures` 将退位为兼容层。
- 工业界：Google StyleGuide 明确"不用裸指针表所有权"与 I.11 同文；abseil `absl::string_view/Status`
  即"强类型返回值"接口的大规模实证；Chromium 的 `raw_ptr` 项目是 I.12/生命周期主题的工业化极端样本。
