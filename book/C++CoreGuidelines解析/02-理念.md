# 第2章 理念 — P: Philosophy（P.1–P.13）

> 本章目录版：[← 00-总览与阅读地图](00-总览与阅读地图.md) ｜ 单文件笔记：[../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md) ｜ 系列导航：[../C++系列·总索引.md](../C++系列·总索引.md)

**本章对象**：指南的"宪法"。13 条理念规则（current master 实测 P.1–P.13 无空洞）不规定具体写法，
规定**评判具体写法的标准**——后面 18 章的每条规则都要能回溯到这里的某一条。格林的处理是逐条
配"违反成本"的故事：类型不安全=运行期爆炸、资源泄漏=慢性中毒、意图不明=维护税。

## 核心概念速览（中英对照）

- **表达意图** — express intent (P.3)：让代码直陈"要做什么"，而非让读者从机制反推
- **静态类型安全** — statically type safe (P.4)：不存在运行期类型错误的可能性，理想态而非全可达
- **编译期检查优先** — prefer compile-time checking (P.5)：错误发现点每前移一阶段，成本降一个量级
- **可运行期检查** — checkable at run time (P.6)：编译期检不了的至少要能配置运行期检查（profiles/assert）
- **尽早捕获** — catch run-time errors early (P.7)：错误发生点与检测点越近，定位成本越低
- **不泄漏任何资源** — don't leak any resources (P.8)：内存之外还有句柄/锁/文件描述符
- **不浪费时间和空间** — don't waste time or space (P.9)：以性能档案（performance profile）划定量化的"零成本"边界
- **偏好不可变数据** — prefer immutable data (P.10)：能 const/constexpr 就不用可变全局
- **封装丑陋构造** — encapsulate messy constructs (P.11)：脏活进一个库函数，别散落全代码库
- **支持工具** — supporting tools (P.12)：sanitizer/静态分析/concurrency check 是规范的义肢
- **支持库** — support libraries (P.13)：GSL 及标准库补足语言未覆盖的抽象（not_null、span）
- **领域适配** — write code appropriate to the domain (旧 Ph.r.1，⚠️ current master 已并入理念前言)
- **直接表达** — express ideas directly in code (P.1)：能用语言设施说的，别用注释/约定说

## 动机：为什么理念章值得整章精读

规则式知识（"F.16 该怎么传参"）会随标准版本腐烂，理念（"错误发现点越早越好"）不会。
P.1–P.13 实际上是 Stroustrup 对"什么让 C++ 程序配得上叫现代"的一次公理化：
后面每一章的规则都是这些公理在具体语言设施上的**定理解**。读法建议倒过来用——
遇到一条看不懂理由的规则（例如"为什么禁止 va_arg"），回理念章找它的引理（P.4 类型安全 + P.6 可检查性）。

## 机制：13 条如何压成一棵判据树

1. **表达轴**：P.1 直接表达 / P.2 用 ISO 标准 C++ / P.3 表达意图——解决"代码说了什么"；
2. **安全轴**：P.4 静态类型安全 → P.5 编译期优先 → P.6 运行期兜底 → P.7 尽早捕获——
   一条从理想态到工程退路的完整梯度；
3. **资源轴**：P.8 不泄漏 + P.9 不浪费——安全与效率不是交换关系，指南坚持"两者都要"；
4. **数据轴**：P.10 不可变优先——把并发正确性的成本前移到设计期；
5. **工程轴**：P.11 封装丑陋 + P.12 工具 + P.13 支持库——承认语言不完备，用库和工具缝合。

## 代表性规则深解析（规则 → 理由 → 现代工具承接）

### P.1: Express ideas directly in code
- 理由：注释与命名约定不进入类型系统，重构时不会跟着改；能直接说的（bool、枚举、模板参数）写进注释=双重维护。
- 工具承接：clang-tidy `modernize-use-bool-literals`、`readability-implicit-bool-conversion`；
  C++20 concepts 把"对模板参数的文字要求"直接变成代码（详见 [13-模板和泛型编程](13-模板和泛型编程.md)）。

### P.4: Ideally, a program should be statically type safe
- 理由：动态类型的事故（越界强转、vararg 格式串）都在生产环境才暴露；C++ 的 cast/vararg/union 是类型安全三洞。
- 工具承接：`-Wcast-align`/`-Wformat` 系列告警（🔧 本章下方实测）；type profile 把 union/强转列为可检查违规；
  `std::variant`（C++17）承接 tagged union 场景。

### P.5: Prefer compile-time checking to run-time checking
- 理由：编译期失败的修复成本约为运行期事故的 1/10（错误定位、测试覆盖、灰度风险全免）。
- 工具承接：`static_assert`（C++11）、`constexpr` 扩张（C++20 循环/容器雏形、C++23 `constexpr<algorithm>` 子集）、
  `consteval`（C++20）；clang-tidy `misc-static-assert`、`modernize-unary-static-assert`（名称已核对官方检查表）。

### P.7: Catch run-time errors early
- 理由：晚发现的错误代价指数级；`Expects()`/边界检查/`_GLIBCXX_ASSERTIONS` 把检测点拖回现场。
- 工具承接：`-D_GLIBCXX_ASSERTIONS`（libstdc++ 现成开关）、AddressSanitizer、GSL `Expects/Ensures`；
  ⚠️ Windows MinGW 无 libasan，运行期检查线让位于 MSVC/WSL（本仓库 `../C++代码调试的艺术/06-内存检查.md` 实测过平台分野）。

### P.9: Don't waste time or space
- 理由：指南罕见地给出量化口径——按性能档案（memory/allocation/lock 四类操作计数）设预算，
  无预算不优化（与 Per.1–Per.6 呼应，见 [09-性能](09-性能.md)）。
- 工具承接：perf counters/`__rdtsc` 计时（🔧 第 9 章 reserve 实测即此类"先计数后动手"）。

### P.10: Prefer immutable data to mutable data
- 理由：不可变数据天然线程安全、可推理、可共享（值语义）；可变状态是并发 bug 的头号来源。
- 工具承接：`const`/`constexpr` 与 clang-tidy `misc-const-correctness`；`std::expected`+无副作用函数便于纯函数化（C++23）。

### P.11: Encapsulate messy constructs
- 理由：`void*`、`realloc`、系统调用散落=审查面爆炸；封进一个 RAII 类型后全代码库只剩一个可疑点。
- 工具承接：unique_ptr 自定义删除器、`std::filesystem::path` 接管平台差异——指南思路即"库吸收复杂度"。

### P.12 / P.13: Use supporting tools / support libraries as appropriate
- 理由：语言、工具、库三角互补；规范假设你会用 clang-tidy/GSL，而不是要求语言本身长出一切。
- 工具承接：clang-tidy（`clang-analyzer-*`）、GSL；abseil 提供了指南部分概念的非标准实现
  （`absl::StatusOr` ↔ `std::expected`、`absl::Span` ↔ `gsl::span`）。

## 🔧 实测：编译期检查前移的两种形态（已实测 g++ 15.2）

```cpp
constexpr unsigned fact(unsigned n) { return n <= 1 ? 1 : n * fact(n - 1); }
static_assert(fact(5) == 120, "5! must be 120");   // 错误在编译期出局（P.5）
#include <cstdio>
int main() { std::printf("fact(5)=%u computed at compile time\n", fact(5)); }
```

`-std=gnu++23 -O2 -Wall -Wextra` 编译运行：

```text
fact(5)=120 computed at compile time
```

同一表达式当 `fact(5)` 换成 `fact(20)`（32 位溢出）时，clang-tidy 的 `bugprone-*`/UBSan 都要运行期才抓到，
而 `static_assert(fact(20) == 2432902008176640000ULL)` 在编译期即红——P.5 的"发现点前移"就是这一屏之差。

## 权衡与边界

- **理想态 vs 可实现**：P.4 用 "Ideally" 开头，指南自己承认 C++ 全静态类型安全做不到（C 接口、外部输入）；
  退路是 P.6 的运行期 profile——两条款互为泄压阀，教条式只执行其一都会受伤。
- **编译期不是免费的**：`constexpr`/模板前移检查的代价是编译时间与诊断可读性（13 章实测 concepts 报错
  行数并不短，收益在"错误落点"）。
- **P.9 的量化门槛**：性能档案在工业界基本没落地——指南里完成度最低的条款之一。

## 最新演进与工业实践

- C++20/23 大幅兑现 P.5/P.10：`consteval`、`std::is_constant_evaluated`、constexpr 容器化持续推进
  （constexpr `std::vector` 经 P2552R3 进入 C++26 方向，wg21.link 实测 302）；
  `[[assume]]`（P1774R8，wg21.link 实测 302，C++23）把"编译器可信赖的事实"写进代码，是 P.1/P.3 的设施化。
- 工业界：Google 内部大规模 clang-tidy + sanitizer 矩阵即 P.12/P.7 的落地模板；
  LLVM 项目自研 clang 工具链承担同类职能（P.12 的"自建工具"路线）。
- 提案化维护：P2188R1（实测 302）主张理念章条目也应随标准演化"可演化地"修订——本章正是
  2022 重构中从 Ph.r 记号退回 P.n 记号的区域（⚠️ 重构细节以 git 史为准）。
