# 第17章 架构观念 — A: Architectural ideas（A.1–A.4）

> 本章目录版：[← 00-总览与阅读地图](00-总览与阅读地图.md) ｜ 单文件笔记：[../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md) ｜ 系列导航：[../C++系列·总索引.md](../C++系列·总索引.md)

**本章对象**：current master 实测 A 节仅 3 条正式规则——A.1（稳定/不稳定代码分离）、
A.2（可复用部分库化）、A.4（库之间无环）；编号 A.3 缺位，且 master 的规则汇总表里 A.4
之后是一排 `???` 占位——**A 节是整部指南草稿感最重的部分**，⚠️ 本书第 17 章的"架构观念"
主题远比这 3 条规则丰满，格林在此借题发挥了大量自己的工程经验（章节↔规则对应为推断映射，
见 00 总览的勘误说明）。

## 核心概念速览（中英对照）

- **架构观念** — architectural ideas：指南里唯一"看山外"的一节，规则作用域从函数/类放大到库
- **稳定核** — separate stable code from less stable code (A.1)：变化率分层，隔离不稳定代码
- **库化** — express reusable parts as a library (A.2)：维护/文档/交付三位一体的复用单位
- **头文件库** — header-only library (A.2 注)：纯头交付，编译期耦合换链接期自由
- **依赖无环** — no cycles among libraries (A.4)：库依赖图必须是 DAG
- **库内自环许可** — cyclic references inside one library (A.4 注)：环的禁令划在库边界，不入库门
- **渐变采纳** — gradual adoption (Pro 章首)：架构视角下改造存量代码的总策略（19 章主讲）
- **链接期现实** — static/dynamic linking (A.2 注)：同一段规则文本覆盖三种交付形态
- **未定义行为之网** — unspecified behavior via cycles (A.4 理由)：环不只是构建麻烦，可致语义不确定
- **模块** — C++20 modules：指南成书时只能呼吁"库"，模块给了机器可执行的库边界

## 动机：为什么规则书要有一章"反规则"的话

前 16 章的规则都在**编译单元内部**执法：类型、资源、命名、链接。A 节突然把镜头拉远：
一段合规的 C++ 代码嵌在一个循环依赖、稳定与易变互相污染的工程里，照样是灾难。Stroustrup
在指南开篇就承认规则"不完整、可能有洞"（P.3 邻文），A 节就是自认的洞——它记录的是方向：
**代码质量是全栈属性，不是单文件属性**。格林把这一小節放大成一整章，实际是在讲他自己的
老本行（他写过架构与微服务题材的书），⚠️ 具体论述未能与原书逐字核对，本章以 A.1/A.2/A.4
三条规则为锚重建其论证骨架。

## 机制：三条规则构成一条"内聚→封装→拓扑"链

1. **A.1 定内聚策略**：按变化率切分代码。不稳定代码被隔离后可以单独做单元测试、改接口、
   重构、直至废弃（deprecate）而不牵动全身。
2. **A.2 定交付形态**：切出来的可复用部分要"维护、文档、一起交付"才算库——散落的工具函数
   不是库，是负债。库可以静态链、动态链或 header-only。
3. **A.4 定拓扑约束**：库是图的节点，节点间的边不允许成环。环让构建顺序失去良定义、
   可能引入未指定行为（初始化顺序类问题，呼应 SF.22/静态初始化章）。

三条合读：**先分层（A.1），再装箱（A.2），最后画无环图（A.4）**——这是指南里唯一的
"自顶向下"段落，其余全部自底向上。

## 代表性规则深解析（规则 → 理由 → 现代工具承接）

### A.1 稳定/不稳定分离 → 理由：隔离使测试/改进/重构/废弃成为可能 → 承接：无直接 check，工程承接是 CI 分层

- master 原文只有一句话的理由（"Isolating less stable code facilitates its unit testing,
  interface improvement, refactoring, and eventual deprecation"），是全文最"占位"的规则。
- 现代承接靠流程工具：按目录/库粒度配置不同的 clang-tidy 严格度是常态做法——新代码上全量
  `cppcoreguidelines-*`，遗留层只开 P2 级子集（clang-tidy 的 `.clang-tidy` 支持按目录树
  继承配置，正是 A.1 的工具化表达）。
- 与 ES/Per 章的暗合：不稳定代码往往是"手工内存/原始指针"聚集区，R/A 两章是同一病灶的
  微观与宏观视图。

### A.2 库化 → 理由：复用只有伴随维护契约才是复用 → 承接：C++20 modules + 包管理生态

- A.2 的 Note 给了库的操作定义："collection of declarations and definitions maintained,
  documented, and shipped together"——三个 -ed 缺一不可。
- C++20 `import`/`module` 把"库"从目录约定升格为语言实体：编译一次、接口显式、不再靠
  `#include` 复制粘贴语义（呼应 15 章 SF 节）。⚠️ 指南正文对 modules 着墨极少（成书早于
  MSVC/gcc 模块实用化），这是快照落后的典型点。
- 工业承接：conan/vcpkg 把 A.2 变成 `manifest` 文件；abseil 文档明确"每个 target 是
  一个库，支持 live-at-head 或 pin 版本"——同一思想。

### A.4 库无环 → 理由：环 complicates build + might introduce indeterminism → 承接：`misc-header-include-cycle`（环的微观形态）

- 官方 clang-tidy 检查列表实测存在 `misc-header-include-cycle`（已核对本机抓取的官方页），
  它抓的是头文件层面的环——A.4 的最小可用执法：头环是库环的前兆与主要载体。
- A.4 的 Note 划界精确：**库内**组件互相引用合法（如双向链表的节点与容器），禁的是
  "A 依赖 B 且 B 依赖 A"。这条界线在拆分遗留库时是核心操作问题：要么合并成一个节点
  （承认强内聚），要么抽公共下沉（消除环）。
- 链接器不报库环（静态库循环引用靠重复列库/`--start-group` 苟活）——**语言层面对环无感，
  所以 A.4 只能靠构建系统执法**（CMake 的 `DEPENDS` 图、Bazel 的加载期环检测会直接报错）。

### 配套深读：SF.9/SF.10（命名空间↔库层次映射）是 A 节在源文件尺度的孪生

- 15 章已实测过其违反形态（重定义/多重定义错误）。A 节 + SF 节合起来是"指南的空间拓扑学"：
  SF 管一个库内文件怎么摆，A 管库和库怎么连。

### 配套深读：A 节 × Pro 章的"渐变采纳"是架构级施工法

- Pro 章首（19 章主讲）明说：规则不能整库一把梭，要按 profile 成组落地——这本身就是
  A.1 的稳定/不稳定分层思想的执法版：先让最不稳定层达到 type profile，再逐层推进。

## 权衡与边界

- **A 节规则不可判真伪**：A.1 的"稳定"没有阈值，A.2 的"可复用"需要预言未来——它们处于
  P.3"好规则难以完全执法"光谱的最模糊端。批评者说这不是规则是格言；辩护者说没有这节，
  指南会诱导"每个 .cpp 都完美、整个系统没人负责"的局部最优陷阱。
- **header-only 的双刃**：A.2 把 header-only 列为合法库形态，但 14 章 CPL 与 SF 节都记录了
  头文件泛滥的代价（编译时间、ODR 风险窗口）。指南不替你做这个权衡，P.5（基于语义分析）
  在这里失灵，因为语义是"交付策略"不是"程序行为"。
- **无环 vs 分层架构**：DAG 比严格分层（layered architecture）弱——同层库之间允许横向边，
  只禁环。指南选了更弱的约束，因为更强的约束（层序）在真实代码里几乎总是被违反而沦为摆设。

## 相邻概念对比

- **A 节 vs P 章（2 章）**：P 章讲"为什么这样写代码"（语言哲学），A 章讲"为什么这样摆代码"
  （工程哲学）；两者都是不可完全执法层，但 A 更弱——P 至少有 P.2 静态检查支撑的论断。
- **A 节 vs SF 节（15 章）**：单库内 vs 库间；SF.8 include 守卫防的是文件级重复包含，
  A.4 防的是目标级循环依赖，尺度差一整层。
- **`misc-header-include-cycle` vs 构建系统环检测**：前者语法级即时反馈（IDE 内），后者
  目标级权威裁决（CI 内）；指南快照时代两者都不存在，属于"事后追授"的承接工具。
- **A.2"库" vs 设计模式"库"**：[../C++20设计模式/](../C++20设计模式/00-总览与阅读地图.md)
  意义上的模式是库内词汇表，A.2 是交付单元——别把"我们用了工厂模式"当成"我们有库"。

## 最新演进与工业实践

- **C++20 modules 是 A 节的最大变量**：编译防火墙 + 显式接口使 A.4 的环第一次变得
  机器可查（`import` 关系是编译器已知信息，无需启发式）；⚠️ 未引用具体提案号（modules
  本体为 P1103R3 合入 C++20，本次未对其做 wg21 302 验证，故不落编号）。
- **Bazel/Gradle 式构建图**把 A.1–A.4 变成声明：target 即库（A.2）、deps 即边（A.4 由构建器
  强制无环）、visibility 控制谁能动不稳定层（A.1 的权限面表达）。
- **抽象-稳定原则（P.3 邻域）**：依赖应指向更稳定、更抽象的一侧——与 5 章 C.129（面向
  稳定接口）、3 章 I.1（库优先于智能指针 ABI）同构。
- C++26 方向：合约（21 章）与 profile 工具链成熟后，"库的契约面"会成为 A.2"文档"要素的
  机器化替身；本节自身在 master 上仍停在 `???` 占位状态（实测），演进压力可见。
