## 核心概念速览（中英对照）

- **资源** — resource：需要获取且必须释放的东西——内存、句柄、锁、套接字、线程
- **RAII** — Resource Acquisition Is Initialization (R.1)：资源寿命绑到对象寿命，构造获取、析构释放
- **资源句柄** — resource handle (R.1)：承载 RAII 的类型（vector/unique_ptr/jthread/lock_guard）
- **裸指针非拥有** — a raw pointer is non-owning (R.3/R.4)：`T*`/`T&` 默认语义钉死为"视图"
- **owner\<T\>** — GSL 所有权标注类型：在无所有权语义的语言里保留"我拥有"的文字声明
- **显式 new/delete 之禁** — avoid calling new/delete explicitly (R.11)：裸分配只允许出现在管理器内部
- **立即托管** — immediately give allocation to a manager (R.12)：`new` 的结果当场进智能指针
- **单语句单分配** — at most one explicit resource allocation per expression (R.13)：多个裸 new 同语句=异常半泄漏
- **span 取代 [] 参数** — R.14：数组形参带长度随行
- **unique_ptr** — 独占所有权（R.20/R.21）：默认选择，零额外开销
- **shared_ptr** — 共享所有权（R.20）：仅在"所有权期限不可静态判定且需共享"时使用
- **make_shared/make_unique** — R.22/R.23：异常安全+分配合并+代码缩短
- **weak_ptr 断环** — R.24：shared 环=永不归零的引用计数
- **所有权参数四态** — R.32–R.36：按值收 `unique_ptr`=接管；`unique_ptr&`=重定位；
  `shared_ptr` 系=共享/重定位/持有计数
- **别名指针禁逃逸** — R.37：从智能指针取的裸指针/引用不得活过其拥有期
- **生命周期安全** — lifetime safety (Pro.lifetime/profile)：越出语言能力交给静态分析

## 动机：为什么"所有权"是 C++ 内存安全的主轴

C++ 没有 GC，资源泄漏与悬垂访问只能靠**结构性纪律**消灭。R 组的答案是一套单向车道：
`new` 只在工厂出现一次（R.11/R.12）→ 所有权永远在 `unique_ptr` 手里移动（R.20/R.21）→
边界上传视图（`T*`，R.2/R.3）→ 共享是例外且要写明（R.34–R.36）→ 工具在每一环可检查（clang-tidy/profile）。
格林特别强调 R 章与 07 之外的章互为因果：锁是资源（CP.20）、目录句柄是资源、线程也是资源（CP.23/24）。

## 机制：四层所有权表达

```text
第1层 语言值语义        vector/string/值成员 —— 隐式所有权（首选）
第2层 标准智能指针      unique_ptr（默认） / shared_ptr（共享例外） / weak_ptr（观测）
第3层 GSL 标注          owner<T*>（"裸但拥有"的过渡语）/ not_null（非空视图）
第4层 外部检查          bounds/type/lifetime profile + clang-tidy/StaticAnalyzer/CppCoreCheck
```

## 代表性规则深解析（规则 → 理由 → 现代工具承接）

### R.1: Manage resources automatically using resource handles and RAII
- 理由：手工配对释放的路径数随分支组合爆炸（异常/提前 return/循环 break 都是新路径）；
  对象寿命由作用域自动管理，把"每条路径都记得"变成"编译器保证"。
- 承接：C++11 起全套标准句柄（vector/unique_ptr/lock_guard/jthread）；专项检查器按资源类型见下方各条。

### R.3/R.4: A raw pointer (T*) / reference (T&) is non-owning
- 理由：所有权语义从约定升格为**定义**——"看到裸指针就假定不拥有"成为全体系公理，
  I.11（不裸传所有权）与 F.7（参数用裸指针）都由它支撑。
- 承接：clang-tidy `cppcoreguidelines-owning-memory`（已核对官方表，识别 owner/裸指针错配）；
  C++26 方向的生命周期所有权分析 P2547R1（实测 302）试图把"谁拥有"变成可静态推导的属性。

### R.11: Avoid calling `new` and `delete` explicitly
- 理由：裸 `new` 的手写时代结束于 C++11——"异常路径泄漏"这一整类 bug 的正确修法是让裸分配
  只存在于 `make_unique/make_shared` 内部这一处。
- 承接：`std::make_unique`（C++14）；clang-tidy `cppcoreguidelines-owning-memory`、
  `modernize-make-unique`（已核对官方表）；MSVC CppCoreCheck 有专属规则类。

### R.13: Perform at most one explicit resource allocation in a single expression statement
- 理由：`f(new A, new B)` 中 B 分配失败时 A 已泄漏——求值顺序未定 + 无托管点=经典半泄漏。
- 承接：`make_unique` 化（`f(make_unique<A>(), make_unique<B>())`）后异常安全由构造保证；
  编译期 `-Wall` 帮不了，靠结构纪律。

### R.14: Avoid `[]` parameters, prefer `span`
- 理由：`void f(int a[])` 里 `sizeof(a)` 是指针大小这个世纪陷阱；不带长度的数组参数让
  被调函数无法自检边界。
- 承接：C++20 `std::span`（P0896R4，实测 302）；clang-tidy
  `cppcoreguidelines-pro-bounds-array-to-pointer-decay`（已核对官方表）。

### R.21: Prefer `unique_ptr` over `shared_ptr` unless you need to share ownership
- 理由："所有权单一"作为默认设计原则——shared 的计数原子操作、控制块、循环引用、线程语义
  全是税；先证明确实要共享，再买单。
- 承接：🔧 本章实测即 unique 路径零泄漏；`std::make_unique` 一行托管；
  "ownership 单则 unique_ptr"运动（Sutter 路线，P2547 实测 302）正把该默认推向语言级检查。

### R.30–R.36: 智能指针作参数的精确语义
- 理由：`f(unique_ptr<T>)`（按值）=宣告"我接管"；`f(unique_ptr<T>&)`=宣告"我可能换你指的东西"；
  只想看对象就回到 `T*`/`T&`（F.7）。参数类型即函数对资源的"意向书"。
- 承接：clang-tidy `modernize-pass-by-value`（构造场景，已核对官方表）+ `performance-unnecessary-value-param`
  反向拦截无谓的智能指针拷贝。

### R.37: Do not pass a pointer or reference obtained from an aliased smart pointer
- 理由：从 `shared_ptr` 取 `T*` 存下来，智能指针死亡后视图悬垂——所有权与视图的寿命解耦是
  悬垂引用的头号生产事故。
- 承接：静态生命周期检查 P2573R2（实测 302）瞄准该类问题；运行时侧 AddressSanitizer 的
  heap-use-after-free 报告（平台分野见 [../C++代码调试的艺术/06-内存检查.md](../C++代码调试的艺术/06-内存检查.md)）。

## 🔧 实测：R.11/R.12 违规 vs R.1 合规——异常路径下的泄漏计数（已实测 g++ 15.2）

```cpp
#include <memory>
#include <cstdio>
#include <stdexcept>
int live = 0;
struct Res { Res(){ ++live; } ~Res(){ --live; } };
void good() { auto r = std::make_unique<Res>(); throw std::runtime_error("early exit"); } // R.1 合规
void bad()  { Res* r = new Res; throw std::runtime_error("early exit"); delete r; }        // R.11/R.12 违规
int main() {
    try { good(); } catch (...) {}
    std::printf("after good() (unique_ptr): live=%d\n", live);
    try { bad(); }  catch (...) {}
    std::printf("after bad()  (raw new):    live=%d  <- leaked\n", live);
}
```

`-std=gnu++23 -O0 -Wall -Wextra` 编译运行，真实输出：

```text
after good() (unique_ptr): live=0
after bad()  (raw new):    live=1  <- leaked
```

同一异常、同一函数形状，`delete r` 永远执行不到 vs 栈展开自动析构——R 组一切条文的存在理由
被这两行输出讲完。泄漏在本机无 ASan 可抓（MinGW 无 libasan，见调试艺术笔记实测节），
计数法是跨平台的教学替身。

## 权衡与边界

- **shared_ptr 的合法生态位**：缓存+多读者+失效时刻不可静态判定——指南不禁共享，要求共享"证明存在"
  （R.20/R.34）；图/观察者/异步任务回调是三大正当用户。
- **owner\<T*\> 的过渡性**：C++ 没有所有权语言设施（至今），GSL `owner` 只是文档+检查器可懂的标记——
  R 章对它的着墨（FAQ.56）反映指南"先标注后立法"的路线。
- **RAII 不检查逻辑泄漏**：句柄计数正常但缓存无界增长——指南承认这类"非资源型泄漏"超出 R 组射程。

## 最新演进与工业实践

- **标准侧**：C++20 `std::span` 落地 R.14；C++23 无所有权新设施；C++26 的生命周期/所有权安全
  （P2547R1、P2573R2，均实测 302）是 Guidelines→语言回流的主战场；`std::expected`+工厂函数
  为"不抛环境的资源返回"补了第三条腿。
- **工具侧**：clang-tidy `cppcoreguidelines-owning-memory`/`-no-malloc`（R.10）/
  `modernize-make-unique`；VS CppCoreCheck 的 lifetime profile 是 R.37 的运行最成熟检查器。
- **工业界**：Windows/Chromium 等团队以"R.3 非拥有约定+注解+静态分析"重构内存安全预算；
  abseil 内部 `raw_ptr`+`scoped_refptr` 分工即 R.3/R.34 的工业方言；folly `Singleton`/`IOBuf` 
  展示共享所有权的受控用法。
