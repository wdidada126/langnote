# 第19章 规格配置 — Pro: Profiles（Type.1–8 / Bounds.1–4 / Lifetime.1）

> 本章目录版：[← 00-总览与阅读地图](00-总览与阅读地图.md) ｜ 单文件笔记：[../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md) ｜ 系列导航：[../C++系列·总索引.md](../C++系列·总索引.md)

**本章对象**：current master 实测 Pro 节共 **13 条 profile 规则**：Type.1–Type.8（类型安全，
Type.1 内含 4 个子项）、Bounds.1–Bounds.4（边界安全）、Lifetime.1（生命周期安全）。
"Profile（规格/画像）"是指南的**执法操作系统**：把 448 条规则切成可整组开关、可跨工具
一致裁决的子集。⚠️ 本书第 19 章书名"规格配置"与 Pro 节的对应系推断映射（附录 A"施行"
与本章一体两面，见 [21-附录AC](21-附录AC-施行概念与契约.md)）。

## 核心概念速览（中英对照）

- **规格/画像** — profile：一组**确定性、可移植执法**的规则子集，瞄准单一错误类别
- **确定性** — deterministic：只需局部分析，理论上编译器可实现（不依赖全程序数据流）
- **可移植执法** — portably enforceable：不同工具对同一代码给同一裁决——"像语言规则一样"
- **成组执法** — coherent enforcement：随机挑规则单独执法"比解决问题更具破坏性"（章首原话）
- **类型安全规格** — Pro.type：封杀 cast/union/varargs 等一切"绕开类型系统"的通道
- **边界安全规格** — Pro.bounds：指针只指单对象；数组索引/算术/衰减全禁，`span` 上位
- **生命周期安全规格** — Pro.lifetime：不解引用可能失效的指针（Lifetime.1 独苗，配套 Lifetime.pdf）
- **抑制标注** — `[[suppress("bounds")]]`：在语言契约上显式豁免，"应当极罕见"（章首原话）
- **按构造安全** — safe by construction：合规代码**不是该属性错误的根因**（定义精确到绕口）
- **执法节** — Enforcement section (In.force)：每条规则自带的执法设想清单，含"愿望清单"
- **未检查访问** — unchecked access：`operator[]`/迭代器裸用；`_GLIBCXX_ASSERTIONS` 是运行期兜底

## 动机：规则会众包，执法要成建制

In.force（指南"执法"节）开宗明义：**无执法的规则对大型代码库不可管理**。但一次让全公司
遵守 448 条同样不可管理——正确姿势是：先消灭"越界写"这一个类别（Bounds profile），验收
效果，再推下一个。Profile 思想 ≈ 安全领域的"威胁建模驱动的加固"，也 ≈ SLS 火灾逃生演练：
不承诺绝对安全，承诺**消除一类事故**。Type/Bounds/Lifetime 三个规格合起来正好覆盖
"访问了错误的内存"的全部三种方式（错误的解释/错误的位置/错误的时间）。

## 机制：profile 的三层结构

1. **定义层**：每个 profile 给出被禁语言模式的**穷举清单**（Type.1–8 等），只允许局部判断
   ——这是"确定性"的工程含义：工具不需要指针分析就能裁决。
2. **库层**：profile "可能引入额外库类型以便利合规"（章首原话）——Bounds 带 `span`、
   Type 带 `variant`/`not_null`，这正是 GSL（20 章）存在论上的另一半理由。
3. **豁免层**：`[[suppress("profile")]]` 标注 + 逐工具配置。豁免集中出现在"ABI 强制的
   原始指针"处（呼应 I.1 对智能指针入 ABI 的反对）——**profile 不消灭例外，只让例外可清点**。

## 代表性规则深解析（规则 → 理由 → 现代工具承接）

### Type.1 避免 cast（严格版四连） → 承接：`cppcoreguidelines-pro-type-reinterpret-cast` 等四检查一一对应

- 四个子项：禁 `reinterpret_cast`；禁对算术类型用 `static_cast`；禁同型指针转换；
  禁可隐式完成的指针转换——粒度递进，从"明禁"到"暗禁冗余"。全部已核对官方 clang-tidy
  检查列表：`cppcoreguidelines-pro-type-reinterpret-cast`、`-static-cast-downcast`、
  `-cstyle-cast`、`-const-cast` 等 pro-type 家族实测在列（本机抓取核对）。
- Type.2 禁 `static_cast` 向下转型（用 `dynamic_cast`）：注意与 C.146 的微妙分工——
  热点路径可用 `polymorphic_downcast`（static + debug 断言）折中，profile 层面一刀切、
  规则层面留门，这个矛盾是指南"执法粗糙于规则精细"的自供状。
- Type.7 禁裸 union（用 `variant`）、Type.8 禁 varargs（F.55）：14 章 🔧 实测的
  `printf("%d", 3.5)` 只报 -Wformat 而 C++ 类型系统全程失明，就是 Type.8 存在的理由。

### Type.5/Type.6 一切皆初始化 → 承接：`cppcoreguidelines-init-variables` + `cppcoreguidelines-pro-type-member-init`

- profile 特意把"别用未初始化变量"（语言契约）与"成员永远初始化"（C.41/C.49）列为两条
  check——前者局部可判（声明点），后者需要类级别扫描。两条均在官方列表实测存在。
- 组合 12 章 Con 线：初始化 + const 默认 = 让"值从何来"和"值会变吗"都在声明点回答。

### Bounds.1–3 指针/索引/衰减三连 → 承接：`cppcoreguidelines-pro-bounds-*` 三检查实测在列

- 核心设计：**把指针的合法身份压缩到"单对象"**——一旦指针不表示序列，越界在类型上无处
  藏身；序列一律 `span`（携带长度）。Bounds.3"禁数组到指针衰减"是三者中最狠也最易误报的
  （C 边界文件常需豁免，呼应 CPL 章的渐进策略）。
- 8 章 ES.107 的 `gsl::index` 是 Bounds 家族的索引配套：`index`（现 `ptrdiff_t` 别名）
  带"可为负=已越界可检测"语义，与无符号 `size_type` 对拍。
- 权衡：Bounds.4"不用未检查的标准库设施"在现实 libstdc++ 里不可完全执法（标准库自己
  就用裸迭代器），profile 的执法对象事实上限于**用户代码**。

### Bounds 线的运行期兜底：`_GLIBCXX_ASSERTIONS` 🔧（已实测 g++ 15.2）

- 静态执法之外，libstdc++ 提供可打开的运行期断言层（16 章预告过）。🔧 实测：

  ```cpp
  #include <vector>
  #include <cstdio>
  int main() {
      std::vector<int> v(3, 1);
      std::printf("v[100]=%d\n", v[100]); // ES.55/SL.con.3: out of bounds via operator[]
  }
  ```

  `g++ -std=gnu++23 -O0 -D_GLIBCXX_ASSERTIONS` 编译运行，**真实输出**（Git Bash，
  断言消息来自 libstdc++ 头文件内联展开处）：

  ```text
  D:/develops/tools/mingw64/lib/gcc/x86_64-w64-mingw32/15.2.0/include/c++/bits/stl_vector.h:1263:
  constexpr std::vector<...>::reference std::vector<...>::operator[](size_type) [...]:
  Assertion '__n < this->size()' failed.
  exit=3
  ```

  （原文为单行长消息，此处为排版折行；exit=3 为 Windows 下 abort 的退出码观测值。）
- 判读：不开宏时 `v[100]` 是静默 UB（本机 -O0 实测打印了某个垃圾值后正常返回——这正是
  "insidious" 的定义）；开宏后变成**可定位的**终止。性能代价约等于每次访问一个分支，
  Debug/测试构建全开、发布构建按风险关闭——这就是 Bounds profile 的"部署形态"。
  同族还有 `-D_GLIBCXX_DEBUG`（迭代器/失效检查，更慢）与 libc++ 的
  `_LIBCPP_HARDENING_MODE`（C++25 hardening 方向，16 章已注）。

### Lifetime.1 不解引用可疑指针 → 承接：无编译器级 check，工具生态最年轻的一条

- 13 条 profile 规则里唯一"名存实亡"的执法面：clang-tidy 的 cppcoreguidelines 家族
  **没有** pro-lifetime 检查（官方列表实测无）。它的实质承载是指南仓库 docs 下的
  **Lifetime safety profile 规范 PDF**（master 原文直链，2021 年定稿）——按函数签名
  推断指针参数流向调用者的静态分析规范，clang 侧实验性 `-Wdangling-gsl` 等告警是其雏形。
- C++26 视角：悬垂治理的主流路线反而走了库+告警组合（`string_view` 系
  `bugprone-*` 三件套，10/15 章实测引用）。这条 profile 的未来形态最可能是"编译器内建"
  而非"外挂 lint"——章首"理论上编译器可实现"的自指。

### 执法配置现实：clang-tidy / CppCoreCheck 双工具对照（In.force + 附录 D）

- clang-tidy：`cppcoreguidelines-*` 前缀 43 项（本机对官方检查列表 grep -c 实测），
  与 profile 规则**近似同义反复**（pro-type/pro-bounds 直接按 profile 命名）；
  `.clang-tidy` 的 Checks/HeaderFilterExtensions 就是"规格配置"的配置文件实体。
- CppCoreCheck（MSVC `/analyze` 的 cpp-core-guidelines-rules 规则集）：微软当年按 profile
  粒度发布的商用执法，⚠️ 规则集现状以 VS 版本文档为准，本机 MinGW 环境无法验证。
- 本机环境诚实记录：clang-tidy/cppcheck 均未安装（10 章已记），上述检查名全部核对自
  官方在线列表抓取件，非本地运行输出。

## 权衡与边界

- **"确定性"砍掉了什么**：只许局部分析 = 放弃跨函数指针流——Lifetime profile 因此只剩
  1 条规则却最难执法。profile 的抱负（消灭错误**类别**）与其手段（局部判据）之间存在
  结构性张力，这是理解第 19 章全部配置的钥匙。
- **成组开关 vs 逐条精调**：profile 鼓励整组启用（否则"随机执法更破坏"），但大型存量库
  往往先开 `pro-type-cstyle-cast` 这类低噪声项、缓开 `pro-bounds-array-to-pointer-decay`
  这类高噪声项——实践中"半 profile"状态是常态，指南对此沉默。
- **豁免的考古学价值**：`[[suppress]]` 清单 = 架构债务清单。审计一个库的 suppress 标注
  分布，比任何静态报告都直接地暴露其 ABI 伤口（I.1/CPL 章的交汇）。

## 相邻概念对比

- **Pro 章 vs In.force 节**：In.force 是**逐规则**的执法设想（含大量"(Not enforceable)"
  标注与"愿望"），Pro 是**跨规则**的成建制规格——先有逐条设想，后攒成组规格。
- **profile vs 编译警告等级**：-Wall -Wextra 是"严重性"梯度开关，profile 是"错误类别"
  正交开关；8 章实测的 -Wsign-compare 不属于任何 profile（它服务的是可读性线），两套
  坐标互不涵盖。
- **Bounds profile vs sanitizers**：ASan 运行期抓**已执行**的越界（概率证据），profile
  静态禁**可能越界**的写法（构造性证明）；[../C++代码调试的艺术/](../C++代码调试的艺术/06-内存检查.md)
  的 ASan/Valgrind 线是本节工具缺位（本机无 libasan，10 章已记）时的替身。
- **`_GLIBCXX_ASSERTIONS` vs `Expects`/`gsl::Expects`**：前者是库**内部**预置断言（供应商
  决定断什么），后者是**你的**契约（你决定断什么，21 章）——层级不同，可叠加。

## 最新演进与工业实践

- Lifetime profile（PDF 规范）是三条中唯一未 lint 化的，clang `-Wdangerous`（D.960 系列
  悬垂告警工作）是其在 LLVM 侧的推进形态；⚠️ 该工作未以 wg21 提案号呈现，不落编号。
- C++26 合约提案（P2900R14，wg21.link 已 302 验证）被广泛视为"第四条 profile 的种子"：
  契约违规的检测语义若语言化，profile 的"可移植执法"将获得比 lint 强得多的载体。
- 工业配置样板：LLVM 自身 `.clang-tidy` 精选子集、Fuchsia/Chromium 的 clang-tidy 集成、
  微软 GSL + CppCoreCheck 组合（FAQ.51 语境）都印证"profile = 工具配置的语义单元"。
  abseil 的"不鼓励 reinterpret_cast/union 裸用"文档线可视为 Type profile 的无声采纳。
- 演进压力实测注记：current master（2026-09 抓取件）的 Pro 节仍只有原有三个 profile，
  "未来候选清单"（narrowing/UB/const 违约等）原封未动地挂着——profile 机制的火种已移交
  合约与 hardening 两条线。
