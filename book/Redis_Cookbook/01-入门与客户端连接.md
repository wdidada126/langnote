## 核心配方精讲

### 配方：编译与最小可用实例 ⚠️

文档转述（Redis 2.x 时代即可用、至今流程未变）：解压源码后 `make` 即可（无强制外部依赖，Linux/macOS 主流发行版
直接可编）；`make test` 跑 Tcl 集成测试套件——这是当年 Cookbook 式书籍反复推荐「先跑测试再上线」的底气。
开发实例最小启动：`redis-server --port 6380 --daemonize no`，客户端 `redis-cli -p 6380 PING` 得 `PONG`。
生产三件事起步就要定：`daemonize yes` + `pidfile` + `logfile`（默认日志到 stdout 会把 syslog 刷爆 ⚠️），
以及**先设 `requirepass`/ACL 再暴露端口**（见 06 章安全段）。

### 配方：redis-cli 的四种工作姿态 ⚠️

- 交互：`redis-cli`（提示符显示 db 号与库名）；`-r 100 SET k v` 重复发命令做简易压测（非真压测，勿得出性能结论）。
- 远程：`redis-cli -h host -p 6379`；2011 年书基线用 `-a 密码`，现文档已提示 `-a` 会告警（进程列表泄露密码），
  改用 `REDISCLI_AUTH` 环境变量或 `--user name`。
- 观测：`--latency` 每 100ms 一次 PING 打点（能抓出毛刺与超时）；`--bigkeys`/`--memkeys` 用 SCAN 安全扫库找大键——
  这直接对应 02 章的「禁止在生产跑 KEYS」配方。
- 装载：`redis-cli --pipe` 吃 RESP 协议文本批量灌入，是 Cookbook 传统「迁移数据集」通道；与 05 章 MULTI 不同，
  pipe 无原子性只有吞吐。

### 配方：连接治理——timeout、tcp-keepalive、池大小 ⚠️

- 服务端 `timeout 0` 默认不断空闲连接；设非零会踢空闲超 N 秒的客户端——与 pub/sub 订阅者（05 章）组合时**必须为 0**
  或加大心跳，否则订阅连接被回收，这是 2011 版书里就已点名的经典坑。
- `tcp-keepalive` 现代默认 300s；中间层（云 LB/NAT）空闲超时更短，**客户端池的 idle 回收必须小于链路回收**，
  否则会拿到「半开连接」，第一条命令才炸。
- 池：redis-py 的 `ConnectionPool` 上限要按「请求并发 × 平均命令耗时」估，不是一味调大——连接本身每条约
  数十 KB 服务端开销（`CLIENT LIST` 里看 `tot-net-in/mem` ⚠️）。`maxclients` 默认 10000，实际先受 ulimit 约束。

### 配方：客户端库选型（2011 基线 → 2026 现状）⚠️

书年代：Python 用 redis-py（`StrictRedis` 尚未与 `Redis` 合并）、Java 用 Jedis（同步单连接模型）。
现状（转述官方与各库 README）：redis-py 已合并、原生 pipeline/Lua/集群支持；Java 侧 Lettuce（基于 Netty、
线程安全共享连接、支持 RESP3）成为 Spring Boot 默认，Jedis 仍是简单同步选择；Go 用 go-redis，Node 用 ioredis。
选型三问没有变：**要不要共享连接（线程安全）？要不要 RESP3/推模式？要不要集群拓扑自动发现？**

### 配方：管道（pipeline）——省往返的原子幻觉 ⚠️

`MGET k1..kN` 之外的一切批量：把 N 条命令一次写进 socket、一次读回 N 个回复，省 N-1 个 RTT。
三个不变的事实（至今成立）：① 管道**不保证原子执行**，中间可被其他客户端命令穿插（要原子用 MULTI 或脚本，05 章）；
② 回复顺序与请求顺序一致，客户端必须按序读；③ 管道太长会让服务端单命令排队执行期间阻塞其他客户——
每批 100–1000 条量级，别无脑全量。

## 配方：redis.conf 的最小可用集 ⚠️

新实例上线只需先动六个参数（其余全部继承 06 章的持久化/安全决策）：
`bind`（网络面）、`protected-mode yes`（无密码时的公网护栏）、`daemonize`+`pidfile`+`logfile`（进程形态）、
`databases`（逻辑库数，默认 16）、`maxmemory`+`maxmemory-policy`（04 章容量合同）、`timeout`（本章上文的
连接回收）。改完 `CONFIG REWRITE` 固化或直接改文件重启——2011 年 Cookbook 的「先配置后加压」顺序至今正确。
注意 `SELECT` 的弱隔离代价：**所有逻辑库共享同一份 maxmemory 与淘汰压力**，缓存实例与任务实例混库=互相拖累 ⚠️。

## 常见坑与判读

| 坑 | 症状 | 判读/规避 |
| --- | --- | --- |
| 生产用 KEYS | 全库扫描阻塞秒级 | 一律 SCAN/`--bigkeys`（🔧 语义见 02 章） |
| timeout 与 pub/sub 打架 | 订阅者莫名掉线 | timeout 0 + 心跳/重连逻辑 |
| 池大于链路空闲超时 | 偶现连接重置 | 客户端 idle < LB/NAT 超时 |
| `-a` 明文密码 | ps 里可见 | `REDISCLI_AUTH`/`--user` |
| 把管道当事务 | 穿插写导致读出不一致 | 原子需求升级 MULTI/EVAL |
| SELECT 分库当租户隔离 | 全量权限互相可见 | 逻辑库共享同一淘汰/内存压力，隔离用 ACL 或实例 |

## 核心概念速览（中英对照）

- **管道** — Pipelining — 批量写命令一次往返、按序读回，省 RTT 但不保原子。
- **逻辑库** — Database/SELECT — 单实例内 0–15 编号的弱隔离键空间，共享内存与淘汰。
- **连接池** — Connection Pool — 复用 TCP+认证开销的客户端侧池，大小受并发×耗时约束。
- **客户端身份** — Client Identity — `CLIENT LIST` 中的 addr/lag/mem/flags 四元组，排障第一现场。
- **RESP** — REdis Serialization Protocol — 客户端与服务端间的文本/二进制协议，2011 年为 RESP2。
- **空闲超时** — `timeout` — 服务端踢掉空闲 N 秒的客户端；pub/sub 场景须设 0。
- **TCP 保活** — `tcp-keepalive` — 探测半开连接的内核级心跳，须与中间层超时对齐。
- **半开连接** — Half-open Connection — LB 静默断链后客户端仍持有 fd，下一条命令才报错。
- **bigkeys 扫描** — `redis-cli --bigkeys` — 基于 SCAN 分类型找大键的安全巡检。
- **maxclients** — Max Client Limit — 服务端连接硬上限，实际常先被 ulimit(fd) 卡住。
- **ACL 用户** — ACL User — 7.0 起的多用户授权模型，取代单一 `requirepass`。
- **Lettuce/Jedis** — Java 客户端双雄 — 前者异步共享连接+RESP3，后者简单同步；选型看线程安全与推模式。
