| 配方 | 你能做到 | 关键命令 |

## 核心配方精讲

### 配方：限流两代目 ⚠️

固定窗口：`INCR rate:uid:1m`，首击（值=1）时 `EXPIRE 60`——窗口边界处最坏可放行 2N。
滑动窗口用有序集（03 章能力的直接应用）：`ZREMRANGEBYSCORE k 0 now-60s` 清陈旧、
`ZADD k now event-id` 记本次、`ZCARD k` 数当前窗口——每条命令 O(log N)，突发被真实滑动削平。
两个坑从 2011 年到网关产品从未消失：EXPIRE 与 INCR 非原子（崩溃留下永久键）→ 一律改
`SET k 1 EX 60 NX` 起手或脚本化（05 章）；计数的「读后判」与「记」之间可穿插 → 高精确场景把三步包一个脚本 ⚠️。

### 配方：会话与幂等 ⚠️

会话=哈希+TTL 的经典体：登录 `HSET session:sid ...`+`EXPIRE sid TTL`，每次读滑窗续期
（`GETEX` 6.2 把这些合成一条）。幂等写=SETNX 占位的直接推论：处理前先
`SET idem:<request-id> processing NX EX 3600`，抢到位才干活，完成后改写结果摘要——
重复请求第二次 SETNX 得 0 即短路返回。这即 02 章计数语义的第二应用，也是 DDIA 语系里「幂等消费者」的 Redis 落点。

### 配方：去重与「要不要精确」的分水岭 ⚠️

精确去重：集合 `SADD seen:campaign:7 uid` 返回 1/0 兼职「首次判定+登记」双职（命令本身原子）。
只要「数一数大概多少不重复的人」：HyperLogLog 用 12KB 级固定内存换 PFCOUNT 误差 ~0.81% ⚠️
（文档：https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/ ✅ curl 200）。
判读线：**会拿这个数做「是否放行」决策的→集合；做报表的→HLL**。

### 配方：分布式锁语义逐条拆解（本章主菜）⚠️+🔧

Redis 锁的最小正确协议四条（命令面全部文档转述 ⚠️）：
1. **原子获取**：`SET lock:job1 <token> NX PX 30000`——NX=不存在才写、PX=自带租期（旧 SETNX+EXPIRE 两命令配方已废：
   崩溃夹缝会造出无 TTL 死锁）；文档：https://redis.io/docs/latest/commands/set/ ✅ curl 200。
2. **持有者可辨**：value 必须是本次尝试独有的 token（随机 UUID/连接+请求号），否则「谁删的锁」无从判定。
3. **原子释放**：`EVAL` 两步「GET==token 才 DEL」——裸 `DEL` 会删掉**别人**在租期翻转后拿到的锁
   （05 章 EVAL 的头号教材；https://redis.io/docs/latest/commands/eval/ ✅ curl 200）。
4. **租期兜底**：PX 是崩溃安全网；业务超过租期需要「续租/看门狗」（Redisson 类库的自动续约），
   而**续约救不了 GC 停顿/网络分割后的僵尸持有者**——这正是锁只是尽力而为的根源。

🔧 **协议逻辑真跑**（sqlite3 3.45.3 内存库；脚本 `D:\develops\tmp\dbwave_w3_rcook\demo.py`，输出 `demo.out`；
表 `lockt(name PRIMARY KEY, owner, expires_at)` ⇔ 四件事的 SQL 等价物：主键=NX、单语句 CAS UPDATE=接管仅当过期、
带 owner 条件的 DELETE=Lua 比较删除、expires_at 列=PX 租期）。实跑序列与结果：
```
A acquire -> True                      （INSERT OR IGNORE 成功=拿到）
B acquire(同键未过期) -> False          （NX 冲突=拿不到）
C release(非持有者) -> False            （DELETE WHERE owner 不中=不误删他人锁）
A release -> True
B acquire(锁已释放) -> True
（强制把 expires_at 拨到过去后）
A acquire(抢占过期锁) -> True 持有者=A  （CAS 接管过期锁）
```
**边界声明**：该演示只证锁协议的**状态机语义**（互斥、持有者校验、过期接管、不误删），不含真实并发争用、
进程时钟漂移、GC 停顿与 fencing token 校验——那些是 06 章异步复制丢写与下方论战的主题，SQL 演示给不出结论 ⚠️。

### 配方：锁的失效模型与 Redlock 论战（判读立场）⚠️

失效链三条：① 主确认 SET 成功后崩、AOF everysec 也可能带上这把锁（06 章 RDB 快照同理复活旧锁）——
异步复制+粗耐久让「唯一持有者」破防；② 时钟跳变让租期提前归零（Redlock 对时钟依赖的软肋）；
③ 持有者长停顿（GC/换页）后醒来继续「自认为持有」。**结论谱系**：Kleppmann 的 2016 判词——
「锁+租期只能当**尽力而为的优化**，正确性要靠 fencing token/幂等/可线性化存储兜底」
（✅ 2026-09-27 curl 200：https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html）；
antirez 的回应强调 Redlock 的概率安全与工程务实（✅ curl 200：https://antirez.com/news/101）。
本册立场：**单实例 RedLock 化（含看门狗）用于降低竞争成本的场景；正确性关键（exactly-once 副作用）场景
一律叠加幂等或 fencing token**——与 DDCA 08/09 章的「锁≠共识」论证完全同向。

## 常见坑与判读

| 坑 | 症状 | 判读/规避 |
| --- | --- | --- |
| 裸 DEL 释放 | 删了别人的锁双写 | GET==token 比较删除（EVAL） |
| 无 token 锁 | 无法判定持有者 | value=本次独有 token |
| SETNX+EXPIRE 分两步 | 崩溃后永久死锁 | SET NX PX 单命令 |
| 租期=业务最短时间 | GC 停顿即双持有 | 租期>最坏耗时+看门狗+fencing |
| 限流首击不带 EXPIRE 分原子 | 永久键堆积 | SET EX NX 起手或脚本 |
| HLL 当精确去重 | 0.81% 误差进决策 | 精确上集合 |

## 核心概念速览（中英对照）

- **固定窗口限流** — Fixed Window — INCR+TTL 的每分钟计数；边界双倍突发。
- **滑动窗口限流** — Sliding Window — ZSET 记事件流，按分清理+计数。
- **分布式锁** — Distributed Lock — SET NX PX + token + 比较删除的租期制尽力协议。
- **NX/EXISTS 语义** — Set-if-absent — 原子占位，锁与幂等的地基。
- **PX 租期** — Lease/TTL — 崩溃安全网；到期锁可被接管。
- **fencing token** — 栅栏令牌 — 单调递增号让存储拒绝旧持有者的写入，锁正确性的最后防线。
- **看门狗续租** — Watchdog Renewal — 库侧自动续约把租期拉长到「业务结束为止」。
- **Redlock** — 多实例锁算法 — antirez 提出的 N 实例过半加锁方案，论战焦点。
- **幂等键** — Idempotency Key — SETNX 占位 request-id，重试不重复副作用。
- **滑动会话** — Sliding Session — 读即续期的服务端会话 TTL 策略。
- **HyperLogLog** — HLL — 固定小内存的近似基数，误差约 0.81% ⚠️。
- **尽力而为锁** — Best-Effort Lock — 只降竞争成本、不担正确性的定位声明。
