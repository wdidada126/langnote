### 23.1 需求分析：把前 22 章变成问题清单

自建系统的第一份文档不是架构图，而是**有数字的取舍表**（每行都在为某章还债）：

| 需求条目 | 追问到的数字 | 对应章 |
| --- | --- | --- |
| 负载画像 | 读写比、事务大小分布、热点形态（租户/时间）？ | 3 |
| 一致性 | 接受跨副本多旧？分区期写策略 C 还是 A？ | 7/8/13 |
| 事务 | 跨片事务率上限？隔离级别对外承诺什么？ | 9/14 |
| SLA | RPO/RTO？切主风暴预算？误判容忍度？ | 5/15 |
| 弹性 | 扩容停顿预算？搬迁限流红线？ | 6/12 |
| 兼容 | 「兼容」到协议级还是语义级？不支持清单敢不敢公开？ | 2/20/21 |
| 成本 | 副本数×压缩率×故障域布局的钱算过吗？ | 10/11/22 |

**判别法**：答不出对应数字的需求，说明你还没决定要不要自研——多数团队在第 7 行（兼容）和第 1 行（热点形态）就出局，这是健康的。

### 23.2 方案设计：五层各一道不可回避的难题

按可核实的「自学/造轮子」路线（simpledb/BusTub 教学系 → Raft 库拼装 → mini NewSQL 的社区公开路径；
仓库有 [../自己动手设计数据库.md](../自己动手设计数据库.md)、[../BuildYourOwnDatabaseFromScratch.md](../BuildYourOwnDatabaseFromScratch.md)、
[../../db/simpledb.md](../../db/simpledb.md) 等对照）：

```text
① 单机内核层：事务管理器+索引+WAL
   难题：崩溃恢复的正确性——ARIES 四步（19 章笔记）里任何一个「我以为原子」的假设都要用测试砸实。
② 共识层：给日志装多数派
   难题：快照与日志追赶（16.4）——线性一致的引擎状态与截断的日志要能对接；这里第一次遇到「实现正确性>实现性能」。
③ 分区与调度层：分裂/合并/搬迁
   难题：搬迁瞬间的在途请求（6.4）——两种停顿策略选边站，并写进对外 SLA。
④ 分布式事务层：2PC + 时间戳
   难题：时间戳从哪来（14.5 谱系：TSO 单点吞吐 vs HLC 因果弱）；以及悬挂事务的清理（14.1 的阻塞具象化）。
⑤ SQL 层：优化器与执行器
   难题：分区裁剪与统计（17 章）——从这里开始，「能跑」与「敢用」分道：客户负载会把第 17 章的每个坑重踩一遍。
```

方案设计的正确顺序是**按难题排序排期，不是按层排序**：先攻②④（正确性风险最大），再①③，最后⑤的功能清单。
原书若给出具体样例系统，*未能核实*；上面路线与公开教学项目（MIT 6.824、stanford 等，
仓库对应 [../MIT 6.824 Distributed Systems.md](../MIT%206.824%20Distributed%20Systems.md)）完全可互证。

### 24.1 传统 Text-to-SQL：三代路线的得与失

1. **规则/文法期**：模板+槽填充；准确率可控但覆盖率感人，每加一种问法要人工扩规则。
2. **语义解析/seq2seq 期**：Spider 基准（公开）定义了「跨库泛化」考题；编码器-解码器+注意力能把问句映射到 SQL 骨架，
   死穴在 schema 术语鸿沟（"客户" ↔ `tbl_customer`）与多表 join 路径猜测——**schema linking 是这道题的传统主瓶颈**。
3. **预训练微调期**：PLG/代码模型微调（公开研究线），语法正确率跃升，语义仍靠数据堆。

这三代在 LLM 时代并未作废：**schema linking 演化成了 prompt 里的 schema 裁剪与示例选择**，问题换了包装，没换本质。

### 24.2 优势与场景 + 24.3 核心技术

LLM 路线的增量（公开可核的现象）：少样本甚至零样本跨库泛化、对话式修正（「把金额换算成万元」）、
对不规范口语问法的鲁棒性。落地技术栈的五个组件：

```text
① Schema 供给：只放相关表/列（裁剪：检索库→按问句召回表；注释与样例值进 prompt）
② 语义接地：业务黑话词典（"GMV" → 口径公式）；口径错=全错
③ 生成与自检：先生成再让模型自查/多采样投票；SQL 静态校验（只读、行数上限、必带分区条件）
④ 执行反馈回路：执行报错/空结果 → 带错误信息回炉；「跑通且行数合理」才交付
⑤ 评测：Spider/BIRD 公开基准 + 业务私有评测集（金标准问-答对），上线后按周回归
```

护栏是这一节真正的工程含量：**只读账号、行列级权限继承、复杂查询熔断（成本估算先行）、
敏感列脱敏、以及「LLM 的 SQL 也当作不可信输入做审计」**。本仓库 [../白帽子讲Web安全.md](../白帽子讲Web安全.md)
的注入思维可平移——SQL 注入的对象从字符串升级成了模型。

### 24.4 前沿研究（以公开文献为准的安全表述）

可核实的公开脉络：DIN-SQL/分解提示、MAC-SQL/多智能体（planner-executor-critic）、
执行反馈强化、面向 schema 巨大化的检索（RAG over catalog）、以及「语义层/指标层」与 Text-to-SQL 合流
（LLM 面向指标 API 而非裸表）。*原书 24.4 具体引了哪些工作未能核实*，此处不作代拟。

### 24.5 与第 2 章的对位：接口史押韵

第 2 章说 SQL 接口长寿；第 24 章给出它的演化方向——**自然语言成为 SQL 的「编译器前端」**。
一个值得记住的对称：SQL 赢在「声明式+可校验」；LLM 路线若不保留**执行与校验回路（④⑤）**，
就丢掉了 SQL 抽象最值钱的性质。这也是全书首尾合拢的一句：
**接口的未来不是消灭 SQL，而是让更多人说得出 SQL 的等价物，再由系统把它编译回可校验的 SQL。**

## 例子：一个最小可行的 NL→SQL 查询助手（教学示意，不参与构建）

```text
链路：用户问「华东区上季度退货率最高的 5 个 SKU」
→ 检索召回 tbl_returns / tbl_sku / dim_region（带注释与 3 行样例）
→ 黑话词典：退货率=退货量/销量，上季度=日期范围计算
→ 生成 SQL → 静态校验（只读 ✓ 分区条件 ✓ 行数上限 ✓）→ EXPLAIN 估成本（超阈值则拒绝并提示改问法）
→ 执行 → 结果异常自检（比率为 0 或 100% 时标记「口径可疑」）→ 返回 SQL+结果+口径说明
审计日志记录：原文/生成SQL/执行计划/行数 —— 每周抽 50 条人工评口径正确性，进评测集。
```

三条教训藏在链路里：口径说明必须随结果返回（可信度的展示层）；成本熔断放在执行前（LLM 不会心疼资源）；
人工抽检回流评测集（24.3-⑤ 的闭环）。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「需求分析写完就开工」 | 23.1 的价值在逼你发现「说不出数字的取舍」——每个空白都是一次线上事故预订 |
| 2 | 「自研=从零写所有层」 | 共识用成熟库、执行借力生态是公开社区常态；自研的护城河应聚焦「哪一层」讲得清 |
| 3 | 「LLM 会 SQL 语法所以安全」 | 语法正确≠口径正确≠可执行成本可接受；三层校验一个都不能少（④⑤ 是护栏不是可选项） |
| 4 | 「Text-to-SQL 取代 BI/报表」 | 高频稳定口径该固化成指标层/物化视图；LLM 的增量价值在长尾问法与探索式分析 |
