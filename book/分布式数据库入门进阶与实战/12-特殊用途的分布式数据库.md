# 第 22 章 特殊用途的分布式数据库

> 覆盖原书扩展篇第 22 章（22.1 云原生数据库、22.2 HTAP融合数据库、22.3 内存数据库、22.4 图数据库、22.5 时序数据库、22.6 总结）。
> 本章是「按负载形态分物种」的图鉴：通用 NewSQL 之外，五类专用/半专用系统各自如何解决
> 「访问模式决定物理形态」这道题。读法建议：每节抓两个问题——它优化了什么、为此放弃了什么。

## 本章地图

> 一句话：**云原生卖「弹性」，HTAP 融合卖「新鲜度」，内存库卖「延迟下限」，图库卖「遍历局部性」，时序库卖「高基数写入与压缩」；没有免费物种。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 22.1 云原生 | 存算分离、池化、秒级弹性、按量计费 | 弹性=把「容量」从采购问题变成调度问题 |
| 22.2 HTAP 融合 | 行/列双形态与路由（承接第 4 章） | 融合的是「入口与数据」，不融合「资源隔离」 |
| 22.3 内存数据库 | 全内存、跳过序列化、持久化选项谱系 | 延迟下限由「内核穿透层数」而非磁盘决定 |
| 22.4 图数据库 | 邻接遍历、Pregel/Gremlin、分布式切图 | 多跳 join 的「索引嵌套循环地狱」在此变成一级操作 |
| 22.5 时序数据库 | 高基数标签、列存+压缩、TTL 降冷 | 写吞吐与压缩率来自「数据本身的时间结构」 |

## 核心精讲

> **教学示意，不参与构建。** 各产品能力以官方文档为准；原书对各物种的独特论断*未能核实原文*。

### 22.1 云原生数据库：三件事做到位才算「云原生」

对照第 12 章存算分离谱系，云原生化的判据可压缩为三件事：

1. **计算无状态化**：节点崩溃/秒级拉起 = 重挂日志位点 + 预热缓存（冷启动抖动是真实账单，Aurora 公开论文
   的「log is the database」即为此提供机制基础）。
2. **存储池化与按需复制**：数据不进「本机盘」，日志段/页副本由共享存储层保证（7 章复制协议下沉，16 章共识上移）。
3. **计费与容量解耦**：读写容量、存储容量独立伸缩；「买一年机器」变成「买一小时配额」。

反直觉提醒：**云原生≠更快**。同 AZ 内单行更新常慢于本地 NVMe 直写（多了一跳存储 RPC）；
它买的是「弹性与单位成本」，热路径延迟要靠本地缓存层买回来。仓库既有视角可对照
[../凤凰架构.md](../凤凰架构.md) 的「弹性设计」与 [../SRE.md](../SRE.md) 的容量管理。

### 22.2 HTAP 融合数据库：第 4 章的物种化落地

第 4 章给概念与架构模式，本节把它收成产品形态（公开可核的样本）：

- 双引擎同集群（行存分片 + 列存副本）：TiDB+TiFlash、OceanBase 的行列混存路线、SQL Server 列存储索引
  是「单机版前驱」（公开文档）；
- 内存列存一体（SAP HANA 一脉）：单副本双视图，新鲜度=提交即可见，隔离靠资源组；
- 旁路联邦（库 + ClickHouse/ES 加速）：严格说是「异构索引副本」，新鲜度与一致性窗口自担。

读这一节要带走**路由三问**：AP 查询被送到哪份副本？副本 lag 多少算「读旧违约」？
TP 与 AP 的资源隔离阈值谁说了算？——三问全有书面答案的才配叫 HTAP，否则只是「支持列存」。

### 22.3 内存数据库：延迟下限与持久化谱系

- 快的来源不是「内存」二字，而是：跳过页表/Buffer Pool 管理层、对象即结构（免反序列化）、
  单线程分片避免锁（Redis 模型）。对照 [../Redis设计与实现.md](../Redis设计与实现.md)、
  [../深入分布式缓存.md](../深入分布式缓存.md)。
- 分布式化的两难：数据大 → 分片（Redis Cluster 的 slots/Cassandra 式 ring），
  跨分片操作能力骤降（Lua/多键事务受限）——**「内存库 + 多键强一致」是天然紧张组合**。
- 持久化是谱系不是开关：RDB 快照 / AOF 追加 / 混合（Redis 公开机制）；
  全内存 + 无持久化 = 把 durability 外包给上层（14.6 消息框架常做这个交换）。
- 内存数据库的当代位置：缓存、会话、排行榜、限流计数等**明确可丢/可重建**或**语义自洽**的场景；
  把它当「便宜的 NewSQL」用的团队，最终都在补数据校验与事务边界。

### 22.4 图数据库：把「多跳关系」变成一级公民

问题原型：`朋友的朋友的朋友` 在关系库=三次自 join，索引嵌套循环的代价随深度指数膨胀；
图库的解法是**邻接遍历**——存储层直接存「出边指针/邻接表」，一跳=常数级邻取（对照
[../数据库系统概念6/11-索引与散列.md](../数据库系统概念6/11-索引与散列.md) 的 join 代价讨论，反衬才深刻）。

- 计算模型两派：OL 遍历查询（Gremlin/Cypher，点边随机访问）与 BSP/图计算（Pregel 一脉，全图迭代，
  公开论文可核）——同一存储上的两种引擎，选型先分「在线查关系」还是「跑算法」。
- 分布式切图是本章最硬的一节：顶点切 vs 边切（random/hash/power-law 切分），
  跨切边=每次遍历的远程跳（网络放大），**超级节点**（幂律分布）制造无法回避的热切点；
  工程手段：邻居列表拆分、replicated vertex、按社区结构预聚合。
- 事务与一致性：图库多数走「弱全局事务+局部强」路线；需要 ACID 的多跳写要评估其事务 API 的真实语义
  （各图库公开文档差异大，*原书案例未能核实*）。

### 22.5 时序数据库：时间结构的红利

写侧：设备/指标每秒百万点的追加（与 OLTP 的低量高价值写完全反命题）；
读侧：按时间窗聚合、降采样、极少点查整行。物理设计的三件套：

1. **按 series 组织 + 列存**：tag 做标识维度、field 做测量值，列存+delta-of-delta/RLE 压缩（公开机制，如
   Facebook Gorilla 论文一脉）——压缩率来自「时间序列自身的相邻相似性」。
2. **高基数 tag 索引**：倒排/ roaring bitmap；「tag 值组合爆炸」是时序库最大的运维雷（基数失控=索引内存炸）。
3. **生命周期即架构**：热 SSD→温→对象存储的 TTL 降冷（22.1 计费解耦的垂直样本）、连续聚合/物化视图替代重复扫。

关系库能不能扛时序？能，但要在分区表+列存副本+专门写入路径上重做上述三件套——
这恰是「为什么不直接用 TSDB」的答案，也是第 22.6 总结的题眼：**专用系统=把负载的统计规律写进物理结构**。

## 例子：同一份「风控特征查询」在五物种下的账单（教学示意）

```text
需求：支付事件写入 + 3 秒内可查「该卡 10 分钟内关联设备数」。
云原生库：写入与弹性好；3 跳关联查询=三次 join，P99 难压。
NewSQL：单片事务好；关联查询仍吃多表 join 与索引维护。
HTAP：明细进列存副本，窗口聚合快；关联数=图遍历语义，列存不擅长。
图库：卡→设备→卡的邻接遍历是原生强项；高吞吐写入的切图放大是成本。
时序库：事件流 ingestion 完美；「关联」查询根本不是它的谓词形态。
结论：真实风控=时序(事件流)+图(关系)+NewSQL(账户状态)+缓存(热特征) 的组合；
「特殊用途」的选型答案常常是「各就各位」，而不是「一库通吃」。
```

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「云原生=把库搬上 K8s」 | 没有存算分离与无状态计算的容器化只是搬家，弹性红利为零，还新增调度故障域 |
| 2 | 「HTAP 什么都能干」 | 融合的是入口不是物理规律；超大规模 AP 与极低延迟 TP 的极限场景仍互相倾轧（4 章冲突账） |
| 3 | 「内存数据库不怕丢数据」 | 要看业务语义：会话可重建、库存不可；对不可丢数据必须配持久化+副本+对账三选二以上 |
| 4 | 「图库=加速版 join」 | 它改变的是遍历的复杂度量级（邻接 vs 索引查找×深度）；拿图库做全表聚合是反向误用 |
| 5 | 「时序库随便塞」 | tag 基数=内存预算的硬约束；把 user_id 当 tag 的高基数滥用是 TSDB 事故榜首 |

## 思考题

1. 为你们的三个核心负载各选一个「最省」物种并写出账单：写入量、查询形态、新鲜度要求、允许丢什么。
2. 云原生库的冷启动抖动如何量化？写出你的缓存预热与按租户绑核（亲和性）方案。
3. 图库切图：power-law 切分 vs 顶点 hash 切分在「查超级节点的邻居」上的远程跳数对比，推一个 5 节点小例子。
4. TSDB 高基数治理：给出「发现阶段（指标统计）—拦截阶段（写入校验）—兜底阶段（降冷/重索引）」三段方案，各配一个可观测指标。
