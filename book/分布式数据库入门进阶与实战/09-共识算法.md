## 本章地图

> 一句话：**共识=在不可靠消息网络上对「一个序列」达成一致（而非对「一个值」）；
> 原子广播（可靠广播）与共识互为可归约的孪生问题；Paxos 给出优雅下界，Raft 给出工程可读性。**

### 16.1 原子广播：数据库真正需要的东西

共识（consensus）与原子广播（atomic broadcast / total order broadcast）的差别常被抹平，但对数据库读者要抠回来：

```text
共识：对「单个值」（如：谁是主）达成一致。
原子广播：对「无限消息流」达成一致全序：
  性质 = 有效性(广播的消息最终都交付) + 完整性(至多交付一次)
       + 协议安全( agreed 一致) + 全序(所有正确节点看到同一顺序)。
二者互相归约：Multi-Paxos = 逐槽位共识拼成有序日志；
            原子广播亦可解共识（广播「我提议谁当主」）。
数据库的日志（redo/WAL/raft log）正是原子广播的载体：
  「所有副本按同一顺序应用同一批写」= 状态机复制（SMR, Schneider 1990）。
```

于是 7.4 的「多数派复制」、14.1 的「协调者容错」、15.2 的「副本追日志」在本章会师：
**它们都是 SMR 的一个投影**。db.md 那句「raft log 即 redo，崩溃恢复与共识重启合二为一」
（[../../db/db.md](../../db/db.md)）描述的正是这种合体（对照 TiKV/CockroachDB 公开论文，两者均把
复制日志直接作为恢复来源，单机 redo 的前滚语义升级为「日志已获多数派即 durable」）。

### 16.2 Paxos：两阶段各自在防什么

Basic Paxos 的最小可复述版本（教学示意，不参与构建）：

```text
Proposer:
  阶段一 prepare(n)：向多数派请求「n 比你们承诺过的都大」
  阶段二 accept(n, v)：若多数派回 NO_REPLY，v 取已承诺值中编号最大者（或自己的 v）
Acceptor 的两条纪律（灵魂所在）:
  ① 不再承诺(ack)任何编号 ≤ n 的 prepare；
  ② 一旦为 (n, v) 承诺，之后只 accept v（或编号更大且被说服的新值）。
```

两条纪律各防一类事故：①防「旧轮次幽灵决议」（fencing 的时间戳原型，15 章旧主复活的解药）；
②防「多数派交叠处出现两个值」——两个多数派必有公共成员，它就是「历史的证人」。
**读 Paxos 若只背流程不背这两条纪律，等于没读。**

Multi-Paxos 的优化：稳定 leader + 跳过 prepare（租约化，与 5.2/15.1 的租约呼应），
每槽位（slot/instance）独立决议拼出全序日志。Chubby 的实用细节（租约、视图切换、状态转移）以
Lamport *Paxos Made Live* 等公开论文为准。

### 16.3 Paxos 与原子广播的对比：换个镜头看同一座山

16.3 的比较（按标题展开，*原文角度未能核实*）最有价值的读法是「问题属性对照表」：

| 维度 | 共识 | 原子广播 |
| --- | --- | --- |
| 决议对象 | 单值 | 消息序列 |
| 终止性要求 | 部分同步下才能终止（FLP，5.2） | 同 |
| 数据库用途 | 选主、元数据决议 | 事务日志/复制日志 |
| 归约方向 | 广播可解共识（广播“提议”） | 共识逐槽拼广播（Multi-Paxos） |

工程提醒：**「共识慢」的锅常不在共识**。一次提交的两轮 RPC（prepare/accept 或 append/ack）里，
第二轮可与 fsync 并行、可与后续批次流水线化（Raft 的 pipeline、CockroachDB 的
*Consensus: Reduce the Disk Syncs in Multi-Raft*, VLDB 2019 即砍掉一轮同步）。
把「共识=高延迟」当物理定律是选型期最大的误判。

### 16.4 Raft：为可理解性设计的共识

Raft（Ongaro & Ousterhout 2014）三支柱与安全性定理的工程读法：

- **选举**：随机化超时防分票；**投票规则=只投给日志不比自己旧的候选**（up-to-date 定义：先比 term 再比 index），
  这条规则就是「已提交不被覆盖」定理的全部家底。
- **日志复制**：leader 定序、appendentries 携带 prevLog 校验、follower 一致性检查失败则回退重试；
  提交=**多数派持久化后，leader 推进 commitIndex，且仅提交当前 term 的条目**（Figure 2 规则，防旧 term 连锁提交陷阱）。
- **成员变更**：单步（joint consensus / 等面积变体如 Learner 转移），防「两拨多数派」。

数据库场景里 Raft 的三个高频工程问题：

```text
① 副本数：5 副本多数派写延迟高于 3 副本——不是越多越安全，跨 AZ 部署下先看延迟预算（7.1 放置）；
② Learner/快照：新副本追日志用「快照+增量」（15.2 三段式），Raft 的 snapshot 传输语义要自定义；
③ 单组粒度：一个 Raft 组吞吐有上限（心跳/流水线窗口），所以 BigTable/TiKV/Spanner 都走
   「一片一共识组（Multi-Raft）」——随之而来的跨组事务即 14 章 2PC，跨组负载均衡即 6.4 再平衡。
```

### 16.5 工程选用清单（本章「总结」的实操化）

1. 能不自研就不自研：选用成熟实现（etcd/Raft libraries 等），自定义的是日志语义与快照格式；
2. 想清楚「决议什么」：选主、成员、日志顺序、时间戳（14.5）是四件事，别用一套决议硬扛；
3. 测「部分同步」路径：延迟尖峰注入、时钟跳变、旧主复活——5 章失败模型就是测试用例大纲；
4. 量化关键路径：一轮多数派往返 + 一次 fsync 是提交延迟的地板，优化都在地板之上做文章。

## 例子：用 3 副本 Raft 算一笔提交延迟账（教学示意）

```text
拓扑：同 AZ 三机。网络 RTT 0.2ms，fsync ~0.1ms（NVMe）。
一次写提交关键路径：
  leader 本地追加+fsync(0.1) ∥ 发 append 给 f1/f2
  f1 fsync(0.1) 后回 ACK（0.1 + 0.1 单程0.1）
  leader 收到任一 ACK → 多数派达成 → 应答客户端
≈ max(0.1+0.1, 0.1) + 应答 ≈ 0.3–0.4ms 级。
跨 AZ（RTT 1ms）：立刻变成 ~1.2ms+，×  事务若再跨片 2PC（14.1）则 3 个往返起步。
结论：「共识延迟」问题的正确问法是「我的多数派跨越了哪些故障域」——
      安全（跨故障域）与快（同机房）的张力在此第一次量化出现。
```

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「共识=一致性算法所以能保证数据一致」 | 共识保证**日志顺序一致**；数据一致还要求状态机确定性执行（14.3）+ 正确的上层事务语义 |
| 2 | 「Raft 比 Paxos 强/更安全」 | 二者可证等价（同容错下界）；Raft 赢在可读与工程收敛，不是更强的保证 |
| 3 | 「多数派写丢不了数据，切主也没风险」 | 成员变更期的「双多数派」、旧 term 提交陷阱、fencing 缺失的裸奔实现都是真实事故源 |
| 4 |「用 ZK/etcd 就万无一失」 | 外部依赖引入新故障域；会话过期误杀、依赖抖动放大成集群误切主等风险仍在（本仓库 [../ZooKeeper-分布式过程协同技术详解.md](../ZooKeeper-分布式过程协同技术详解.md)）——依赖共识不等于你理解了自己的共识 |
| 5 | 「5 副本比 3 副本容忍更多所以默认 5」 | 5 副本容忍 2 故障但写要 3 ACK：延迟与成本上升；按可用性目标反推副本与放置 |
