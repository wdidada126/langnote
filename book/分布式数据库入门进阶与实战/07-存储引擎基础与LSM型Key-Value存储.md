### 10.2–10.4 物理层三件套：页、记录布局、空间管理

- **页（page）是原子 IO/锁/恢复单位**：4–16KB 的取舍=随机 IO 延迟 vs 内存浪费（对照
  [../mysql/02-Buffer-Pool.md](../mysql/02-Buffer-Pool.md)）。
- **记录布局**：定长记录朴素；变长记录=偏移表/TLV；NULL 位图省空间（InnoDB 的行格式是活教材）。
  列式与 PAX（partitioning across）是「同一页内按列聚集」的折中——HTAP 列存副本的物理基础（第 4 章）。
- **空间管理**：空闲空间图/链、行溢出区、追加写 vs 原地更新——**追加写（append-only）家族
  （LSM/WAL 风格）天然亲和 SSD 与对象存储，原地更新家族（B 树）天然亲和随机读**。
  这句对立是理解 10.6 路线分歧的钥匙。

### 10.5 分布式索引：局部与全局的经济学

```text
局部二级索引：每个分片只索引自己的数据
  优点：写入零跨片、索引随分片迁移整体搬迁
  缺点：非分片键查询 = 扫描全部分片的索引（scatter-gather），分页与排序昂贵
全局二级索引：索引项跨片集中（或按索引键独立分片）
  优点：任意键查询单点路由
  缺点：主表写伴随跨片索引写 → 每个写事务多一跳甚至多一次 2PC；索引与主表分片不同 → 搬迁要解耦
```

工程折中（各系统公开文档可核）：索引表「物理上按索引键分片、逻辑上由数据库维护」（TiDB/CockroachDB 的全局索引即此路线）、
用覆盖索引把回表变成范围扫、用「异构索引副本」（列存副本）替代部分二级索引需求。
**第 17 章的数据定位、第 14 章的跨片事务代价，都会在这里埋单。**

### 10.6 面向分布式数据库的存储引擎：三条新约束

1. **搬迁友好**：引擎的数据单位（tablet/region/region 级 SST）必须能被「快照+日志追赶」原子迁移（6.4/15.2），
   单文件巨型结构（如整库一个数据文件）是反模式。
2. **日志即共识**：单机 WAL 只服务恢复；分布式引擎把 WAL 交给 Raft/Paxos 多数派持久化，
   「刷盘」变成「法定人数 ACK」——db.md 的判断「raft log 即 redo」即此
   （[../../db/db.md](../../db/db.md)；机制详见本目录 `09`）。
3. **引擎与 SQL 层解耦**：KV 基座路线（TiDB 的 TiKV、CockroachDB 的 Pebble）把关系算子压到「有序 KV + 事务接口」之上；
   关系基座路线（PolarDB/OceanBase 一脉）保留页式引擎，把共识做进日志流。两条路线的对比在本仓库
   DDIA 笔记与 [../分布式数据库原理、架构与实践.md](../分布式数据库原理、架构与实践.md) 有更深处理。

### 11.1–11.3 LSM 机制：一次写/读/合并的完整生命周期

```text
写路径：WAL(顺序追加) → memtable(有序内存表，常跳表) → 满后冻结 flush 成 L0 SSTable
读路径：memtable → immutable → L0(可能全扫) → L1..Ln 逐层二分 → 布隆过滤器挡「不存在」
合并(compaction)：
  Size-tiered：同尺寸文件归并 —— 写放大低、空间放大高、读放大波动
  Leveled：每层容量 ×10、跨层归并 —— 读/空间友好、写放大高（典型 10–30×）
删除 = 写墓碑(tombstone)；范围删除需区间墓碑或重写补齐。
```

读这一节要带走三个「为什么」：
① 为什么 LSM 写便宜——**把随机写变成顺序写 + 批量整理**，代价延后到 compaction 与读路径；
② 为什么 LSM 读贵——同一 key 的版本散布多层，需 bloom filter/块索引/缓存救场；
③ 为什么删除/更新多是关键——墓碑与旧版本要靠 compaction 回收，**空间放大是延迟账单**。

### 11.4 RUM 假说：三角坐标系（Diffusion 会议论文，公开可核）

RUM = **R**ead amplification / **U**pdate amplification / **M**emory amplification 三角，
任意两者降低必抬高第三者。LSM 的经典坐标是「低读放大 ⟺ 高写放大/高空间」之间滑动：

| 优化手段 | 动了哪个角 | 账单 |
| --- | --- | --- |
| 布隆过滤器 | 降读放大（挡 miss） | 内存（M 角） |
| 分层数与每层比例调大 | 降写放大 | 读放大、空间放大 |
| compaction 并发限流 | 稳延迟 | 读放大临时上升（L0 堆积） |
| 键压缩前缀编码 | 降空间/IO | CPU |
| 分离 KV（值存 blob 文件，如 WiscKey/Titan） | 大幅降写放大（大 value 不随 compaction 搬家） | GC 复杂度、读多一跳 |

**RUM 是本书第 11 章对工程最有用的交付物**：评审任何「引擎优化提案」时先问三角里谁在挨刀。
B 树一侧的对应坐标是「更新原地、读单路径、空间紧凑」，但写路径的页随机 IO 与页分裂是它的 U 角出血点
（对照 [../mysql/06-B树索引.md](../mysql/06-B树索引.md) 的页分裂讨论）。

## 例子：一次「compaction 风暴拖垮 P99」的复盘（教学示意）

```text
现象：批量导入 2 小时，同集群无关表点查 P99 从 3ms 劣化到 80ms。
链路：大量新 SST 进 L0 → 触发 leveled compaction → 磁盘带宽+CPU 被归并吃满 → 前台读排队。
处置阶梯：
  ① 限流：compaction 带宽/线程数上限，换取前台延迟红线（空间放大短期上升，事后补做）；
  ② 调度：导入走低优先级令牌桶（TiDB/RocksDB 均有 rate limiter 类机制，公开文档可查）；
  ③ 结构：热点层拆为「小层级多文件」减少单次归并体量；
  ④ 路线：大 value 列改用分离存储，不让它陪跑 compaction。
RUM 视角一句话：你把 U 角的成本转嫁给了 I/O 竞争，而 I/O 是读写的公共通道——
「写便宜」从来不是免费的，只是换了个付款日。
```

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「LSM 写性能碾压 B 树」 | 只在「写密集+可容忍读放大/后台整理」区间成立；点读 P99 与空间放大常反超 B 树 |
| 2 | 「布隆过滤器解决 LSM 读慢」 | 它只挡「不存在的 key」；存在但散布多层的 key 仍要逐层查块 |
| 3 | 「全局二级索引和单机索引一样便宜」 | 它把单分片写变跨分片写（10.5+14 章的税）；建前必须算跨片率 |
| 4 | 「删除行=空间释放」 | LSM 里删除是写墓碑，真回收等 compaction；大删除后先观测空间放大再决定 manual compact |
| 5 | 「分布式数据库随便挑个引擎接上就行」 | 引擎的搬迁/事务/日志接口与上层协议强耦合（10.6 三约束）；「换引擎」≈换架构（db.md 中 TiDB 从 HBase 迁到 RocksDB 的先例） |

## 思考题

1. 用 RUM 三角给你现用最引擎定位：它把主要成本藏在读、写还是内存/磁盘？你们最近的「优化」让哪个角变差了？
2. 为「订单表按用户查 + 按商家查」的双维访问设计：局部索引 scatter-gather、全局二级索引、列存副本三方案，各自给出写放大与跨片事务率的估算式。
3. LSM 的墓碑为什么必须配「范围墓碑或定期全量重写」？构造一个墓碑堆积导致读放大的具体数据分布。
4. 「redo 即共识日志」这句话在崩溃恢复语义上带来什么新命题：单机 checkpoint 对应分布式的什么水位？（提示：应用日志的进度与多数派持久化进度的差）
