### 19.1 生成唯一 ID：为什么这是中间件的第一题

分库分表后自增主键失效（各库各自增会撞车），候选方案与账：

| 方案 | 机制 | 优点 | 坑 |
| --- | --- | --- | --- |
| 号段模式 | 中心服务批量领号（如 `update ... set max_id=max_id+N` 双 buffer 预取） | 趋势递增、对 DB 压力小 | 中心服务可用性；号段浪费；实例重启跳号（可接受） |
| UUID | 本地随机/有序 v7 | 无中心 | 128bit 无序 → B 树随机插页分裂灾难（对照 [../mysql/06-B树索引.md](../mysql/06-B树索引.md)）；存储与索引膨胀 |
| Snowflake | 毫秒时间戳+机器位+序列位 | 趋势递增、位宽紧凑、离线可解（时间可逆推） | **时钟回拨拒号**（NTP 校时/虚拟机冻结，5.1 时钟不可靠的正面病例）；机器位管理=运维工作 |
| 数据库分组自增 | 步长+偏移（A 库奇数 B 库偶数） | 零组件 | 扩分片数=改步长，几乎不可行；只配过渡 |

一个常被漏掉的下游约束：**ID 会进 binlog、消息队列、搜索引擎与对账文件**——
换 ID 方案=全链路数据格式变更，19.1 的分量比看上去重。

### 19.2–19.4 中间件能力清单：路由、补偿与辅助

分片查询的补偿机制（都是「优化器本该免费的东西」的手工重做）：

- **路由**：分片键出现在谓词才能定向；否则全片扫描（scatter-gather）——中间件里最贵的默认行为。
- **跨片 join**：一般禁止或退化「广播 join」；根治靠字段冗余（反范式，回到 DDIA 的取舍）。
- **跨片聚合/排序分页**：归并各片结果；`LIMIT 100000,10` 变成每片取 100010 行——**深分页在分片下是乘法灾难**，
  游标/书签分页是必修改造。
- **全局二级索引的替代**：异构索引表（双写+回查）或引入搜索/列存旁路——一致性窗口由此诞生（第 13 章会话保证的业务版）。

19.3 客户端事务：XA（强一致但协调者复杂、性能差）与柔性事务（14.6 的中间件形态：TCC/消息表/最大努力通知）。
19.4 辅助功能：读写分离、压测影子库、热点规则限流、全局表/广播表——**中间件是「数据访问治理」的集装柜**，
可对照仓库既有笔记 [../分布式中间件技术实战.md](../分布式中间件技术实战.md) 与 [../分布式Java应用.md](../分布式Java应用.md)。

### 20.1–20.2 传统阵营的进化：Oracle Sharding 与开源并行 SQL

- **Oracle Sharding**（公开文档可核）：分片是一级数据库特性——chunk 为再平衡单位、
  全局查询走跨 PDB 联合视图/查询路由、抗单片故障；与中间件派的区别是**布局真相在内核**（呼应 1.3），
  但事务模型仍是「分片本地为主、跨片受控」。
- **开源并行类 SQL**（20.2，按公开产品谱系）：PostgreSQL 生态的外向扩展（Citus 把表分布到 worker、
  分布式执行+本地事务）、Greenplum 类 MPP（分析向）、以及各「计算层分布式 + 存储层单库」的混合体。
  共同取向：**用「并行数据库」的旧骨架解决「分片+聚合」问题**，与 NewSQL 的「共识+分布式事务」骨架分野清晰。
- **20.3 比较**的公认可落点：

| 维度 | 传统进化派 | NewSQL |
| --- | --- | --- |
| 扩容模型 | 片/实例为粒度，迁移多人工参与 | region/tablet 自动调度（6.4/12.1） |
| 一致性来源 | 单实例内 ACID；跨片弱化或受控 | 共识+全局时钟做原生分布式 ACID |
| 生态兼容 | 原生生态成熟（工具/DBA 技能） | 协议兼容 MySQL/PG 是普遍策略，但语义兼容有缝（隔离级别、DDL 行为） |
| 典型心态 | 「我已有大库，切一切」 | 「我从零组一个分片世界」 |

### 21 章选型：四象限与两张负面清单

原书按互联网/传统行业分列实践（*具体条目未能核实*），这里给可核实的决策骨架：

```text
象限一 负载：TP/AP/混合？事务跨片率上限要求？热点形态（租户型/时间型）？
象限二 团队：养得起内核级排障吗？DBA 技能栈迁移成本？（21.2 的核心矛盾常在此）
象限三 生态：协议兼容≠语义兼容；DDL/权限/备份/监控工具链逐项过（db.md 运维清单同源）
象限四 监管与容灾：金融核心看 RPO=0/两地三中心/国产化名录；这常是硬约束，先过这关再谈性能（21.3）
```

两张负面清单（比正面理由更能防止事故选型）：

1. **不建议上原生分布式的信号**：数据量与 TPS 距单机上限尚有一个数量级、团队无 On-call 内核能力、
   业务大量依赖存储过程/触发器且不可改造、迁移窗口只有一次——先做「大规格单机+严谨读写分离+归档」路线。
2. **不建议继续中间件硬扛的信号**：跨片事务/深分页/全局索引补丁堆到第三层、扩容 SOP 需要全公司排期、
   多活需求出现、中间件与内核版本互等升级——此时迁移成本以「月」为单位还在涨，再拖就变成以「年」。

NewSQL 自身的诚实边界（21.1 的「特点」按公认事实给负面部分）：
单分片快路径依赖分片键设计、跨片事务延迟税、DDL/统计信息成熟度参差、小版本升级仍是高危动作、
「兼容 MySQL」不等于可以无脑把 MySQL 的 SQL 搬过来（隐式类型、事务超时、隔离级别默认值等语义缝）。

## 例子：一次「分库分表 → NewSQL」迁移的评估底稿（教学示意）

```text
现状：订单库 MyCat 64 分片；痛点=热点租户、扩容排期 3 个月一次、跨片报表跑 40 分钟。
评估（四象限过一遍）：
  负载：事务 92% 单片（迁移后按业务键→自增改哈希对齐，目标 >95%）；报表迁列存副本（4 章）；
  团队：2 名 DBA 有内核排障经验？无 → 培训计划与厂商支持列为成交条款；
  生态：灰度用「双写+回放对账」（19.2/23 章方法），SQL 语义扫描 400 条高危语句；
  监管：金融云名录内产品，RPO=0 模式（7.4 多数派）压测通过。
决策：分两步——先报表出逃到 HTAP 列存（收益快、风险低），订单核心迁 NewSQL（一年期）。
对照组（不做的方案）：继续加中间件补丁 = 把第四层补丁打进第三层，回归成本无上限。
```

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「中间件低端、NewSQL 高端」 | 两者是复杂度位置之争（1.2/1.3）；规模、团队、监管合拍的中间件方案是好方案 |
| 2 | 「兼容 MySQL 协议=可以直接搬」 | 隔离级别默认值、DDL 原子性、隐式类型、事务超时语义都有缝；迁移前做语义 diff 清单 |
| 3 | 「POC 跑分高=选型赢」 | POC 测不出热点、扩容、升级、故障演练这些生产主战场；21 章的实践清单全在 POC 之外 |
| 4 | 「上分布式顺便上多活」 | 多活是一致性模型+路由+仲裁的系统工程（13/15/16 章），选型期把它当附赠功能=事故预订 |
