## 本章地图

> 一句话：**第 1 章解决“名词到底指什么”，第 2 章解决“它是怎么来的”。**
> 广义=任何把数据放在多台机器上的数据库系统（含中间件拼装的分库分表）；狭义=数据库内核原生具备分片、复制与分布式事务能力的系统。

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 发展脉络 | 集中式→客户端/服务器→集群→云；关系数据库理论与分布式实践的错位 | 分布式数据库是「网络与磁盘同样昂贵」时代的产物，且时代一直在变 |
| 1.2 广义 | 把所有「数据分布在多节点」的方案都纳入：共享存储、无共享、中间件拼装 | 广义口径便于分类，不便于工程承诺 |
| 1.3 狭义 | 原生分布式：数据自动分片、多副本、分布式事务、统一 SQL 入口 | 狭义口径才是本书后续讨论的主体 |
| 2.1 SQL 系统 | 关系模型 + SQL 的工程胜利：schema、优化器、事务 | SQL 的护城河是「声明式 + 可组合的事务」 |
| 2.2 NoSQL 挑战 | 互联网规模、灵活 schema、高可用诉求催生 KV/文档/列族/图 | NoSQL 放弃的是 joins 与全局事务，不是容量 |
| 2.3 NewSQL | 在保持 SQL/ACID 的同时获得水平扩展 | NewSQL = 关系语义 + 分布式内核 |
| 2.4 未来的 SQL 系统 | 云原生、存算分离、HTAP、多模等方向 | SQL 是接口层最长寿的抽象 |

### 1.1 分布式数据库发展脉络：为什么每个年代都有「新答案」

把发展史压缩成一条因果链，每一环都是上一环的瓶颈：

1. **集中式主机时代**：一台机器承担全部计算与存储。瓶颈是垂直扩展的成本与可用性上限。
2. **客户端/服务器时代**：把查询解析/执行下沉到服务器，终端只发 SQL。省了客户端部署，但数据仍在单机。
3. **集群与并行数据库时代（1980s–1990s）**：Shared-Nothing / Shared-Disk / Shared-Memory 三种拓扑出现
   （术语与分类在教科书口径里可查，见 [数据库系统概念6/17-数据库系统体系结构.md](../数据库系统概念6/17-数据库系统体系结构.md)）。
   这一代产品（如 Oracle RAC、Tandem/NonStop SQL）证明了「多机也能做事务」，但目标主要是**高可用与并行加速**，不是透明水平扩展。
4. **Web 规模时代（2000s）**：Google 三篇论文（GFS 2003、BigTable 2006、MapReduce 2004）给出「用廉价机器堆规模」的样板，
   催生 HBase/Cassandra/Dynamo 一脉——即 NoSQL。代价是放弃关系语义与全局 ACID。
5. **云与 NewSQL 时代（2012– ）**：Spanner（2012）、后来者 Aurora/CockroachDB/TiDB/OceanBase 等
   把「水平扩展 + SQL + ACID」重新拼在一起；再往后是云原生存算分离（见本书第 12、22 章）。

这条脉络里有一个反复出现的教训：**每次「放弃 SQL/事务换规模」，几年后都会「把 SQL/事务加回来」**
（例：各家 NoSQL 陆续补查询语言与二级索引；分库分表中间件用户最终想要透明扩展）。
声明式关系接口的生产力红利太厚，没有任何系统能长期承受「不支持 SQL」的代价。

### 1.2 / 1.3 广义与狭义：一字之差，工程含义天差地别

书用「广义/狭义」两个口径划界（这个二分是本书的组织方式，*具体措辞未能核实原文*，但其区分在业界有据可依）：

| 维度 | 广义的分布式数据库 | 狭义的（原生）分布式数据库 |
| --- | --- | --- |
| 定义 | 数据物理上分布在多台机器，对外可能由多个系统拼成 | 数据库内核自己管理分片、副本、事务与故障转移 |
| 典型形态 | 分库分表中间件（MyCat/ShardingSphere）、联邦查询、共享存储集群 | Spanner、TiDB、CockroachDB、OceanBase、TDSQL |
| 分片感知 | 应用/中间件感知，DB 不感知 | DB 内部元数据感知，应用不感知 |
| 事务 | 跨分片要么靠柔性事务，要么靠 TCC/消息最终一致 | 内核提供分布式 ACID（2PC + 共识日志，见第 14、16 章） |
| 扩容 | 数据迁移与路由规则由人/中间件运维 | 调度器自动搬 region/tablet，业务基本无感 |
| 复杂度位置 | 暴露在应用侧（每个业务团队都有一份坑） | 收敛进内核（由数据库团队集中扛） |

**为什么这个区分重要**：db.md 里有一条被反复验证的判断——
「简单在接入层处理一下然后透传，这是数据库中间件干的活，不是一个分布式数据库的事儿」
（[../../db/db.md](../../db/db.md)）。广义/狭义之分就是这条判断的学术表述：
**「复杂度不会消失，只会转移」**。选型时真正要回答的是：你愿意把复杂度放在应用层还是数据库层。

一个帮助记忆的判别法（教学示意）：

```text
问：把表 t 的 1/3 数据搬到新机器上，需要改应用代码吗？
需要      → 广义/中间件方案（路由规则、ID 生成、扩容预案都在应用可见范围）
不需要    → 狭义/原生方案（搬数据是数据库内部的事务）
```

### 2.1 SQL 系统：声明式接口 + 优化器是真正的护城河

SQL 系统赢在两点（对照 [../数据库系统概念6/12-查询处理.md](../数据库系统概念6/12-查询处理.md)）：

- **声明式**：你描述「要什么」而非「怎么拿」，把执行路径的选择权交给优化器。于是同一份 SQL，
  在数据量、索引、硬件变化时可由优化器自行改写计划——应用的正确性不依赖物理布局。
- **一套语言覆盖增删改查 + 事务 + 模式演化**：join、约束、视图、权限在同一个语义层里可组合。

单机关系数据库的工程巅峰（InnoDB 的 B+ 树 + redo/WAL + MVCC）在本仓库已有完整笔记：
[../mysql/06-B树索引.md](../mysql/06-B树索引.md)、[../mysql/19-redo日志.md](../mysql/19-redo日志.md)、
[../mysql/21-事务隔离级别与MVCC.md](../mysql/21-事务隔离级别与MVCC.md)。
第 1 章的视角是：这些机制**全部假设「一个进程持有一个一致的页世界」**，分布式化打破的正是这个假设——
redo 变成共识日志、read view 变成全局时间戳、Buffer Pool 之外多了数据搬迁。这条「假设破裂线」是全书后半部分的引线。

### 2.2 NoSQL 的挑战：它放弃了什么，换到了什么

NoSQL 四象限与各自的「放弃项」：

| 家族 | 代表 | 换到的 | 放弃的 |
| --- | --- | --- | --- |
| KV/文档 | Redis、DynamoDB、MongoDB | 极高并发点查、灵活 schema | joins、跨行事务（早期） |
| 列族 | BigTable/HBase、Cassandra | 稀疏列、范围扫描局部性 | 全局二级索引、跨行 ACID |
| 图 | Neo4j、JanusGraph | 遍历的局部性 | 通用聚合分析 |
| OLAP/分析 | Druid、ClickHouse | 扫描吞吐 | 点更新与短事务 |

关键洞察（与 DDIA 一致，见 [../设计数据密集型应用.md](../设计数据密集型应用.md) 的「数据模型与查询语言」章）：
**NoSQL 真正放弃的不是容量，而是「join + 全局事务」这个关系代数闭环**。
容量问题单机也能凑合（更大磁盘、读写分离），join 与事务一旦在接口层被砍掉，应用就得用「反范式 + 补偿逻辑」重造它们——
这部分成本往往被「上线快」的表象掩盖，三五年后集中爆发（对账、修数、数据漂移）。

### 2.3 NewSQL：把 SQL/ACID 和水平扩展重新拼起来

NewSQL 一词 2011 年由 David Foster 提出（社区共识的说法，具体书内表述*未能核实原文*）。它的技术配方：

```text
NewSQL = SQL 接口 + 关系语义
       + 自动分片（第 6 章）
       + 多数派复制/共识（第 7、16 章）
       + 分布式事务（第 14 章：2PC + 全局时钟）
       + LSM 或页式存储引擎（第 10、11 章）
```

对照仓库既有笔记：db.md 记录过分布式数据库底层存储的两条路线——
「KV 存储为基座（CockroachDB、TiDB 用 RocksDB）」与「关系库为基座（Aurora、PolarDB，OceanBase 亦类似）」
（[../../db/db.md](../../db/db.md)）。**NewSQL 内部的路线分歧正在于此**：
前者把关系模型翻译到有序 KV 之上（一个 Raft 组管一段 key 空间），
后者把共识日志塞进传统复制路径（redo 即日志、日志即共识）。两条路线在第 12 章（架构）与第 9 章（共识）会反复出现。

NewSQL 的诚实账单（书将其归入 2.3 的「新希望」，以下按公认知识展开）：
- 跨分片事务延迟高于单分片；热点分片仍是瓶颈；
- 分布式优化器的计划质量长期弱于成熟单机优化器（这是第 17 章的主题）；
- 运维模型变复杂：观测、扩缩容、版本升级都要重做一遍。

### 2.4 未来的 SQL 系统：接口长寿，内核常新

「SQL 会不会被替代」的争论三十年未休，工程事实是：**SQL 作为接口持续长寿，实现层反复翻新**。
本书把「未来」押在几个方向（与第 4、12、22、24 章呼应）：云原生存算分离、HTAP 一体、多模查询、LLM 自然语言接口（第 24 章）。
可核实的外部信号：ISO/IEC 9075 仍在修订；各家 NewSQL 纷纷补 JSON/地理/向量等多模能力。
至于书中对「未来 SQL 系统」的具体预言列表，*未能核实原文*，此处不代拟。

## 例子：同一份订单数据在三种口径下的形态

用一个 30 行的思想实验把 1.2/1.3/2.x 串起来（教学示意，不参与构建）：

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  user_id BIGINT,
  amount DECIMAL(10,2),
  status VARCHAR(16),
  created_at DATETIME,
  INDEX idx_user_time (user_id, created_at)
);
-- 典型查询：
-- Q1: 按 id 点查（KV 式）
-- Q2: 查某用户最近 30 天订单并按金额排序（索引范围 + 排序）
-- Q3: JOIN orders 与 users 输出「大额未支付用户名单」（关系代数）
-- Q4: SELECT sum(amount) GROUP BY status 的全表统计（扫描型）
```

- **NoSQL（KV+文档）**：Q1/Q2 靠反范式内嵌文档可做好；Q3 要靠应用层双写两张表 + 补偿任务；Q4 靠不上。
- **分库分表中间件（广义）**：按 user_id 分片后 Q1/Q2 局部性好；Q3 变成跨库 join（被禁用或走广播）；
  Q4 需要单独的数据仓库链路。扩容时要人工规划分片数与迁移。
- **原生 NewSQL（狭义）**：四条查询共用一套 SQL 与事务语义；Q1/Q2 靠局部索引，Q4 可走列存副本（HTAP，第 4 章）；
  扩容由调度器搬 region，应用无感。代价：内核复杂度、跨分片 Q3 的延迟比单库时高。

这个对照不是书中原例（*未能核实原文*），但三种形态的能力差异属于公认知识，可作为第 2 章结论的最小实验。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「用了微服务 + 多个 MySQL 实例就是分布式数据库」 | 那是分布式**应用** + 多个集中式数据库；每个数据事实没有统一的查询/事务入口，属广义口径 |
| 2 | 「NoSQL 比 SQL 先进」 | NoSQL 是特定取舍（写扩展、灵活 schema）的产物；NewSQL 证明 SQL 语义与水平扩展并不矛盾 |
| 3 | 「分布式数据库能无限扩展」 | 单 key/单分片的热点无法靠加机器解决；扩展有粒度与上限（第 6 章分片键、第 17 章数据定位） |
| 4 | 「支持 SQL 语法 = 兼容关系语义」 | 兼容 MySQL 协议不等于给出一致的隔离级别/可串行化；协议兼容与语义保证是两件事（第 9、14 章） |
| 5 | 「发展脉络=越来越先进」 | 每个时代的技术都是当时硬件成本与负载形状的函数；2010 年代重回「大内存 + 高速网络」恰是集群数据库复活的前提 |

## 思考题

1. 用 1.2/1.3 的判别法检查你所在系统的数据库：扩容一次需要改几处应用代码/配置？据此判断它属于广义还是狭义，差的那部分能力（自动重平衡？全局事务？）值不值得为它迁移？
2. NoSQL「放弃 join 与全局事务」后，你的业务用哪些机制重造了它们（双写？消息？对账任务？）？把这条隐式数据流水线画出来，评估其一致性级别落在第 8 章 BASE 谱系的哪一档。
3. 如果让你给一个只支持点查与范围查的 KV 存储加上 Q3（跨表 join）能力而不动接口，你会把它做成广义还是狭义的分布式数据库？两条路线各自的失败模式是什么？
4. 「SQL 接口长寿、实现层常新」——找出一个你熟悉的反例（从未支持 SQL 却活得很好的系统），解释它为什么没有落入 2.2 所说的「反范式成本爆发」陷阱。
