### 12.1 广义的数据库架构：六类「真相持有者」

把任何一个云原生分布式数据库剥到组件层（TiDB/PolarDB/OceanBase/Aurora 公开架构均可对号）：

```text
SQL 接入与优化层    ——持有「查询计划」的真相
分布式执行器        ——持有「算子并行」的调度
事务层（TSO/锁/2PC 协调）——持有「顺序」的真相（第 14 章）
副本调度与再平衡    ——持有「布局」的真相（第 6/15 章）
存储引擎（tablet 级共识组）——持有「数据+日志」的真相（第 7/10/16 章）
元数据/路由服务     ——持有「谁在哪」的真相（第 17 章数据定位）
```

**架构评审的第一问永远是：某组件的真相丢了/分裂了，恢复路径是什么。**
本仓库 [../软件架构设计/11-多副本一致性.md](../软件架构设计/11-多副本一致性.md) 与
[../凤凰架构.md](../凤凰架构.md) 的「真相与状态」视角可以迁移过来使用。

### 12.2 当代架构设计目标：一张冲突矩阵

| 目标 | 与谁会冲突 | 典型妥协 |
| --- | --- | --- |
| 水平弹性（秒级加节点） | 与「本地性」冲突：搬迁即跨网流量 | 只在新分片/热点迁移时扩容；预分区预留 |
| 强一致（RPO=0） | 与「跨区延迟」冲突：共识多数派+2PC 关键路径 | 同 AZ 多数派 + 异步灾备；或 Spanner 式等待（14.2） |
| 多租户隔离 | 与「装箱率（成本）」冲突 | 资源组、优先级限流、专用节点 |
| 存算分离（对象存储做底） | 与「热路径延迟」冲突 | 本地 SSD/NVMe 缓存层 + 预取（18.3 因此更关键） |
| 可观测 | 与「性能」冲突：追踪/审计开销 | 采样+慢日志+内核指标分级 |

12.2 若按书里「设计目标」清单读，最容易犯的错是把目标当愿望：**每个目标都是另一目标签发的账单**，
架构文档里必须写清付账方式。

### 12.3 数据库存储架构谱系：日志在谁手里

| 谱系 | 机制 | 代表 | 特征 |
| --- | --- | --- | --- |
| 共享磁盘（shared-disk） | 多计算节点挂同一块存储，锁/缓存一致性走网络（如缓存融合） | Oracle RAC、（PolarDB 的计算侧） | 弹性受存储单点上限约束；故障域大 |
| 无共享分片（shared-nothing） | 每节点自带盘，数据按分片+共识副本分布 | TiDB、CockroachDB、OceanBase、TDSQL | 水平弹性最好；跨片代价内建（14 章） |
| 存算分离/日志为中枢 | 计算节点无状态；「日志=真相」下沉到共享日志服务/对象存储 | Aurora、S3 路线 | 「redo 即数据库」——存储层按日志段自愈式复制，计算挂了秒拉起 |
| 混合 | 共识日志+对象存储冷数据分层 | 各云厂商近年的湖仓化产品 | 新鲜度/成本双轨 |

Aurora 的设计（公开论文 *Amazon Aurora: Design Considerations*）是理解 12.3 的钥匙：
它把「六份日志副本、多数派写、按段补齐（gossip 收敛）」做成存储层职责，
数据库节点只发日志段——**复制协议（第 7 章）被搬进了存储基础设施**。
这与「把 raft log 当 redo」（KV 路线）殊途同归：**都在让日志承担跨节点一致性的第一职责**。

### 18.1–18.3 SSD：从「顺序 IO 崇拜」到「写放大焦虑」

数据库为 HDD 建立的三大假设（大顺序 IO、覆盖写贵、磁头调度）在 SSD 上逐一变形（对照
[../每个程序员都应该知道的内存知识.md](../每个程序员都应该知道的内存知识.md) 与存储工程共识）：

- 随机读不再贵 → 页式 B 树的随机点读代价被高估了，LSM 的「顺序化红利」相对缩小；
- 覆盖写不再是寻道问题，而是 **FTL 垃圾回收与写放大**问题 → 大页原地更新（B 树）与 LSM compaction
  都在向闪存「多写一份」，账要合并算；
- 擦除块语义 → 追加写/日志结构（WAL、SSTable、段式日志）天然亲和；
- NVMe 多队列 → 单机 IO 并发度暴涨，传统「IO 调度瓶颈」转移到 CPU 与软件栈（这正是 18.4/18.5 的舞台）。

工程结论：**「LSM vs B 树」的胜负手随介质移动**——HDD 时代 LSM 赢写，高端 NVMe + 多队列下 B 树写路径的
随机 IO 不再致命，于是出现「页式引擎+共识日志」的关系基座路线回勇（PolarDB/OceanBase 公开架构可佐证；
*原书是否给出此论断未能核实*，此处为公认工程观察）。

### 18.4–18.5 FPGA/RDMA：卸载改变的是「关键路径的形状」

- **RDMA**：旁路内核协议栈的零拷贝远端内存读，μs 级延迟 + CPU 几乎不参与。
  后果：「同步复制」第一次便宜到可以在生产启用（微软 *Smokescreen*/Hercules、
  ClockWork 等公开研究；CockroachDB/多家国产库的 RDMA 加速复制路径亦有论文或演讲可查）；
  共识协议的两轮 RPC（16 章）在 RDMA 下可压成一轮类操作，**跨机一致性从「网络贵」降级为「协调贵」**。
- **FPGA/智能网卡**：卸载压缩（如公开案例：SQL Server 的 FPGA 备份压缩、AWS Nitro 的加解密/网络）、
  日志复制的 ACK 硬件时间戳、索引探查（B 树/LSM 点查的硬件加速，如 *PDA/ZOWA* 等 OSDI/FAST 公开研究）。
- 代价：可编程性差、迭代慢、云上可采购性弱——所以 18.6 式的总结必然落在「按热点场景选择性使用」。

### 18.1/18.2 硬件对数据库的支持与新型存储

可核实的公开方向：持久内存（PMem/DCPMM——Intel 已退出该产品线，2026 视角要写清其退场事实）、
CXL 内存池化（解耦容量与带宽）、ZNS SSD（主机控制布局，直接治写放大）、
计算存储（在盘内做过滤下推）。*原书成稿时对哪些方向下注未能核实*，本文按「方向存在但成熟度不一」处理，
不替书做预言。

## 例子：三种架构下「加一台只读节点」的动作序列对比（教学示意）

```text
共享磁盘（RAC/PolarDB 型）：新节点挂载同一存储 → 恢复缓存一致性协议 → 拉日志追平 → 加入读流量。
  瓶颈面：存储带宽仍是全集群单点。
无共享分片（TiDB/Cockroach 型）：新节点本身不持分片 → 调度器把部分 region 的副本/或 Learner 摆上去 →
  快照+日志追赶（15.2）→ 追平后接读。
  瓶颈面：搬迁流量与快照风暴，必须限流。
存算分离（Aurora 型）：计算节点无状态 → 直接拉新节点读共享日志/页 → 无需搬数据。
  瓶颈面：存储层吞吐上限与本地缓存冷启动（刚拉起时全走远端读，P99 先抖后稳）。
```

同一个小需求在三族架构里是三种完全不同的工程动作——这就是 12.3 谱系学的意义。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「存算分离=先进」 | 它是「弹性优先」目标的解，不是普适升级；热数据本地性被牺牲，缓存层的工程质量决定成败 |
| 2 | 「上 SSD 就不用管写放大」 | 应用层写放大（LSM compaction）+ FTL 写放大叠加；批量更新大字段仍要重算 |
| 3 | 「RDMA 让一致性免费」 | 它消灭了网络延迟的大头，消灭不了共识的两轮结构与故障推理（5.2 的部分同步依旧成立） |
| 4 | 「多租户=容器隔离」 | 数据库内的资源组/内存池/IO 令牌才是隔离本体，容器只隔离 CPU/内存上限的粗粒度 |
