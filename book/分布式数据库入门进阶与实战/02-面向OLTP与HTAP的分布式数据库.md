## 核心精讲

### 3.1 从 TPS 看 OLTP：一个指标的三面的

OLTP（On-Line Transaction Processing）的负载画像：短事务、点读写为主、高并发、强一致要求、数据不能丢。
衡量它的三元组是 **吞吐（TPS）、延迟（P99）、单事务大小**，三者互相拉扯：

```text
TPS ↑   往往靠：批量化（组提交）、并行度（多核/多分片）、弱化持久性（调低刷盘档位）
延迟 ↓  往往靠：缓存命中、本地化（数据与计算同机）、短关键路径（少一次 RPC）
事务大 ↑ 往往使：TPS ↓（锁持有久）、延迟 ↑（关键路径长）、且热点集中
```

教科书级的对照实验是 TPC-C：它同时考核 throughput（tpmC）与 price/tpmC，
各家国产分布式数据库（OceanBase、TiDB、TDSQL、GaussDB 等）都刷过榜——
**榜单数字只能横向比硬件与审计口径，纵向比「我们的业务」毫无意义**，这是读 3.1 应有的免疫力。
（TPC-C 模型本身在 [../数据库系统概念6/26-高级事务处理.md](../数据库系统概念6/26-高级事务处理.md) 有标准描述。）

工程视角的推论：**OLTP 分布式化的原动力排序**是
①单机写吞吐上限（一台机器 redo/锁的极限）→ ②容量（磁盘与内存装不下热数据）→ ③可用域（一个 AZ 挂了业务不能停）。
多数团队实际是被 ②③ 逼上分布式，而不是被 ①——看监控时先看磁盘水位与单表行数，而不是 TPS。

### 3.2 从传统数据库到分布式数据库：四代方案的得与失

这条演进线在本仓库 DDIA 笔记与 db.md 都有对应表述，这里按本书第 3 章的叙事合并复述（公认知识）：

| 代际 | 方案 | 解决了什么 | 留下了什么坑 |
| --- | --- | --- | --- |
| 第一代 | 垂直扩展（加 CPU/内存/磁盘） | 一切问题都能用「更大的机器」拖延 | 成本非线性、单点故障域不缩小 |
| 第二代 | 主从复制 + 读写分离 | 读扩展、热备份 | 写仍单点；复制延迟带来「读不到自己刚写的」（见 [../设计数据密集型应用.md](../设计数据密集型应用.md) 复制章） |
| 第三代 | 分库分表中间件 | 写扩展、容量扩展 | 路由/ID/扩容/跨片事务全部上移到应用与中间件（本书第 19 章主题；广义/狭义之分见第 1 章） |
| 第四代 | 原生分布式（NewSQL） | 透明分片、分布式事务、自动故障转移 | 内核复杂度；跨分片延迟；团队要重新学习运维模型（第 12、21 章） |

一个容易被忽略的机制细节：**第三代与第四代的本质分界在「谁持有数据布局的真相」**。
分库分表时代，布局真相散落在中间件配置 + 应用代码 + DBA 手册里；
原生分布式时代，布局真相收敛为内核元数据（region/tablet → 节点的映射，如 TiKV 的 Region 路由表、
OceanBase 的分区到 OBServer 映射）。真相收敛之后，才谈得上「自动重平衡」「线性一致性读」这些能力——
这条线在第 17 章「数据定位」里会落成算法。

与单机世界的衔接：第 3.2 节讨论的每个新坑，都能在 InnoDB 笔记里找到「旧版对应物」——

- 组提交提升 TPS → [../mysql/19-redo日志.md](../mysql/19-redo日志.md) 19.7；
- 主从复制延迟 → [../mysql/X2-日志系统专题.md](../mysql/X2-日志系统专题.md)（binlog 三日志协作）；
- 锁等待与热点 → [../mysql/22-锁.md](../mysql/22-锁.md)，分布式化后升级为跨分片锁与长事务（第 14 章）。

### 4.1 HTAP：为什么 TP 与 AP 天生互相打架

行存与列存对同一张表的物理组织相反（机制在 [../mysql/04-记录在页中如何存储.md](../mysql/04-记录在页中如何存储.md) 与
[../数据库系统概念6/10-存储和文件结构.md](../数据库系统概念6/10-存储和文件结构.md) 都有基础）：

| 负载 | 访问模式 | 最优组织 | 反例代价 |
| --- | --- | --- | --- |
| OLTP | 按主键取整行、更新个别列 | 行式（一次 IO 拿到整元组） | 列存更新=拆散重写多个列段，写放大大 |
| OLAP | 扫少数列、聚合大部分行 | 列式（只读需要的列，压缩率高） | 行存全表扫=把不需要的列也读进内存，带宽浪费 |
| 两者共恨 | —— | —— | 为一种负载组织的存储， servicing 另一种负载时必然损耗 |

传统解法是 TP 库 + ETL/数仓 + AP 库，代价是三样：**新鲜度（T+1）、管道运维（DDL 变更要同步改链路）、口径漂移（两边数据不一致时先信谁）**。
HTAP（Hybrid Transactional/Analytical Processing）的定义就是把这三样压掉：
**同一系统、同一份逻辑数据，TP 查询走行存路径、AP 查询走列存路径，分析读到的事务新鲜度是秒级而非天级**。

一个常见的夸大宣传要提防：「HTAP 之后不需要数仓」。事实是——
HTAP 适合**运营分析**（近实时报表、风控规则、内部看板），
不天然适合**历史全量 + 多源加工 + 极低成本归档**的数据仓库场景；列存副本的压缩与对象存储归档是另一套成本曲线（见第 22 章云原生一节）。

### 4.2 HTAP 的架构模式：两条路线，一个分野

业界 HTAP 按「列存数据从哪来」分两大模式（与 SAP HANA/TiFlash/ClickHouse 联邦等公开实现对照）：

**(1) 行/列双副本（物理复制）**——代表思路：TiDB（行存 TiKV + 列存 TiFlash，Raft Learner 复制）；
OceanBase 早期亦走「同一日志、行/列多副本」方向（各产品当前形态以其官方文档为准，*书中案例版本未能核实原文*）。

```text
写入 → 分片日志（共识多数派确认） ─┬→ 行存副本（TP 读）
                                  └→ 列存副本（异步/半同步，AP 读）
关键取舍：列存副本的新鲜度 = 复制 lag；优化器按代价在两种副本间路由查询
```

**(2) 单副本内存/统一引擎（逻辑列存）**——代表思路：SAP HANA 与一些内存库：
同一份数据在内存里用「PAX/混合组织」或双索引兼顾两种访问。

两条路线的分野其实只有一个变量：**列存是独立副本，还是同一副本的另一种视图**。
独立副本 → 新鲜度受复制协议约束、故障域分离、成本多一份；
同副本视图 → 新鲜度=提交即可见、但 TP/AP 资源隔离更弱（一个大查询打满 CPU 就会伤交易）。

资源隔离的工程手段（公认做法，书中具体条目*未能核实原文*）：
AP 查询限流/独立资源组、列存副本放专用节点、只读租约路由，避免「分析把交易拖死」这类事故。

## 例子：一个「当日 GMV 大屏」需求的三代方案对比（教学示意）

```text
需求：交易库 orders 表 500GB、写入 3 万 TPS；大屏每 10 秒刷新当日按类目聚合 GMV；
      同时不允许聚合查询拖慢下单链路。

第一代 单库硬扛：一条 GROUP BY 扫当日分区 → P99 下单延迟从 8ms 恶化到 200ms，事故。
第二代 ETL+数仓：binlog→Kafka→ClickHouse → 新鲜度分钟级尚可，但类目字段加列时
                 链路三处要同步改，一次 DDL 漂移导致大屏少算 7% 金额，一周才发现。
第三代 HTAP 双副本：orders 加列存 Learner 副本，大屏 SQL 由优化器路由到列存节点，
                 交易节点零干扰；新鲜度=复制 lag（秒级）；成本=多 1 份存储 + 1 组专用节点。
```

第三代里最该盯的指标：**列存副本 lag 的 P99**。它决定了「大屏数字与收银台差多少」，
也是第 7 章复制协议、第 13 章一致性模型在业务侧的直接投影。

## 常见误区

| # 误区 | 修正 |
| --- | --- |
| 「TPS 高 = 分布式数据库好」 | 必须同报硬件与事务模型；TPC-C 榜单间不可直接比，业务混合负载更不可外推 |
| 「HTAP = 在线跑 OLAP」 | HTAP 的核心是**存储/路由/隔离设计**，不是把 BI 查询塞回交易库；没有列存路径与资源隔离的「HTAP」就是事故发生器 |
| 「有了 HTAP 就淘汰数仓」 | 历史归档、多源加工、极低成本列存仍属数仓/湖仓场景（第 22 章；与仓库 `book/数据仓库工具箱.md` 一类笔记分工） |
| 「读写分离就是 HTAP」 | 读写分离只分流读请求、不改变存储组织，副本仍是行存、仍服务 TP 型查询 |
