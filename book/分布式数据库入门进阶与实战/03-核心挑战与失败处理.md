## 本章地图

> 一句话：**单机数据库假设「世界是一个进程」；分布式数据库的第一课是放弃这个假设——
> 网络会分区、时钟会漂移、进程会暂停，而你能观测到的只有消息的迟到与缺席。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 挑战的来源 | 不可靠网络、不可靠时钟、不可靠节点；部分失败 | 新故障模式：从「全对/全错」变成「一半对一半错」 |
| 5.2 失败模型 | 崩溃型/遗漏型/拜占庭型；同步/异步/部分同步系统 | 模型选择决定算法下界与工程成本 |
| 15.1 失败检测 | 心跳、租约、故障探测器（failure detector） | 异步系统里失败检测只能「最终可信」，不能「即时可信」 |
| 15.2 失败修复 | 副本重建、日志回放、自动/手动切主、数据修复任务 | 检测只是开始；修复要有资源、限流与误判保护 |

### 5.1 挑战的来源：三个「不可靠」与一个「部分失败」

单机数据库的可靠性叙事（redo/checksum/RAID）默认：**组件要么全好要么全坏，且进程内对状态的读取没有延迟**。
分布式化打破的是：

1. **网络不可靠**：消息会丢、会重、会乱序、会迟到很久再突然到达。
   最阴险的不是「不通」而是「时通时不通」——**延迟尖峰是分布式系统的一等公民**。
2. **时钟不可靠**：机器时钟会漂移、会被 NTP 回拨；跨机器的「先后」不可直接观测。
   这直接催生 Lamport 时间、向量时钟、TrueTime/TSO/HLC 一整套「人造时间」技术（第 13、14 章展开；
   仓库已有 [../../db/tidb/中心化TSO.md](../../db/tidb/中心化TSO.md) 专文）。
3. **节点不可靠**：进程崩溃之外还有**长时间 GC 暂停/虚拟机冻结**——节点自己都可能搞不清「我是不是已经死了」。
4. **部分失败（partial failure）**：以上三者的合流——系统第一次出现
   「A 看 B 死了、B 看 A 死了、双方都在服务」的世界。单机的全有全无优雅退场，分布式的敌人是**分歧**。

工程后果（公认知识）：所有「在单机里免费」的性质——顺序、原子可见性、超时判断——
在分布式里要么花钱（共识/租约/全局时钟）要么降级（最终一致/柔性事务）。
第 8/13 章的 CAP 与一致性谱系就是这份「花钱或降级」的价目表。

### 5.2 失败模型：把敌人画清楚再谈判

**(1) 进程/节点失效行为分类**

| 模型 | 行为 | 数据库工程的对应 |
| --- | --- | --- |
| 崩溃型 crash | 停止运行，之前行为忠实、之后不再动作 | 主流假设；Raft/Paxos 的容错对象 |
| 遗漏型 omission | 继续运行但漏收/漏发消息 | 网络分区可归并建模 |
| 恢复型 recovery | 崩溃后可能重启并恢复部分状态 | WAL/副本重建必须假设它会回来「捣乱」（旧主复活问题） |
| 拜占庭 Byzantine | 任意行为，包括说谎串谋 | 通用数据库不防（成本高）；联盟链/容错安全场景才考虑 |

**(2) 时序假设分类**

| 模型 | 假设 | 关键结论 |
| --- | --- | --- |
| 同步系统 | 消息延迟、处理时间、时钟漂移有已知上界 | 超时可以当作失败证据 |
| 异步系统 | 无任何时间上界 | **FLP 定理**：异步系统中确定性共识不能在「哪怕一个崩溃」时保证终止；无法实现完美故障探测器 |
| 部分同步系统 | 大部分时间近似同步，最坏时候未知 | DLS 结论：共识算法的现实落点；Raft 心跳超时的理论辩护 |

数据库产品几乎全部运行在**部分同步 + 崩溃型**假设下，
这决定了第 15 章故障检测只能「怀疑→确认→隔离」分步走，也决定了旧主复活必须靠**租约/fencing token** 兜底。

**(3) 一个必须会讲的思想实验**（教学示意，不参与构建）：

```text
主节点 M 因 GC 暂停 30s。期间从节点 S 心跳超时 → 选新主 M'。
GC 结束后 M 苏醒，仍自认主，继续接收旧会话写入。
若没有保护机制 → 双主 → 已提交写被覆盖。
保护机制三件套：
  ① 租约：M 的「我是主」有到期时间，暂停即失效；
  ② fencing token：每次切主发新令牌，存储/下游拒绝旧令牌写入；
  ③ 多数派写：单点写不构成提交，旧主无法独立提交（第 7、16 章）。
```

### 15.1 失败检测：你检测不到失败，只能检测「可疑」

异步系统里没有完美故障探测器（公认结论，Chandra & Toueg 1996），能实现的只有带性质弱化的探测器：
**强完备（最终会怀疑所有真失败者）+ 强精确（真健康者最终不被永久怀疑）**，即 Eventually Strong。
工程实现层：

| 手段 | 机制 | 坑 |
| --- | --- | --- |
| 心跳 + 超时 | 周期 ping，连续 N 次超时判死 | 阈值两难：太小误判风暴、太大 RTO 恶化；尖峰网络下必误判 |
| 租约 lease | 授权带 TTL，续约失败即失效；**被检测方自己参与判定** | TTL 到期与续约消息竞态；时钟跳变；主 I/O 卡顿但租约未过期→「活着但不可用」的灰色区 |
|  gossip/phi-accrual | 怀疑值随间隔分布自适应，而非硬超时 | 需要调 φ 与历史窗口；Cassandra 等采用（公开文档可查） |
| 仲裁 probing | 由多数派共同判死，而非单方 | 慢但抗误判；共识系统切主的标配路径 |

真实系统把多种叠加：TCP 层快速失败 + 心跳滑动窗口 + 仲裁确认 + 人工升级闸门。
读这一节要建立的直觉是：**故障检测的输出是「概率信号」，处置动作必须带防抖与可观测证据链**。

### 15.2 失败修复：检测之后的四件事

**(1) 角色修复（高可用主线）**：切主/重选。要点是**先隔离旧主，再接纳新主**
（fencing 先行，否则出现上文双主事故）；以及**级联故障保护**——同一机柜/同一交换机故障域内的副本等于没有副本。

**(2) 副本补齐（数据冗余主线）**：节点回来后重建副本：全量快照 + 日志回放（如 TiKV 的快照+raft log 追赶、
PG 的 basebackup+wal replay、MySQL 的 clone plugin+binlog 追平——机制各异，骨架相同：
**「快照定基线、日志追增量、校验防漂移」**，对照 [../mysql/19-redo日志.md](../mysql/19-redo日志.md) 19.9 恢复目标表）。
要点：重平衡流量必须限流，否则「修复风暴」压垮剩余节点，把一次单点故障放大成集群雪崩。

**(3) 数据损坏修复（静默损坏主线）**：磁盘位翻转、半途写页、固件 bug 造成 checksum 失败。
手段：副本间一致性校验（repair/scrub 任务）、跨介质备份。DDIA 把 silent data corruption 列为独立敌人
（[../设计数据密集型应用.md](../设计数据密集型应用.md)），第 10 章物理结构里的 checksum 是它的第一道防线。

**(4) 误判与人工回路**：自动切主要有熔断（短时间多次切主→停止自动化转人工）；
修复任务要可暂停、可回滚。**自动化不是消灭人值守，而是把人的介入推迟到正确的时间点**。

## 例子：一次「机房断网」事故的时间线复盘（教学示意）

```text
T+0s   机房 A 与 B 间专线中断（分区，5.1 的「时通时不通」极限版）。
T+5s   B 区检测器开始累积怀疑（15.1）；A 区多数派仍在，B 区少数派无法选主 → B 区写入拒绝。
T+30s  业务侧：读走 A 区副本；写全部路由 A；跨区事务报 -ECONNREFUSED（而不是超时）。
T+2m   专线半通：心跳间歇恢复 → 怀疑信号抖动，切主风暴风险出现（15.2 第4点的熔断生效，保持 A 主）。
T+40m  专线恢复：B 区落后副本走「快照+日志追赶」，限速回放（15.2 第2点），lag 从 38min 收敛到秒级。
T+2h   复盘：确认期间无双主（fencing 生效）、无丢已提交写（多数派在 A）；
       行动项：把「少数派可读旧数据」做成显式的产品开关，而不是事故里的临时决策。
```

这张时间线把 5.1/5.2/15.1/15.2 全部走了一遍：**分区是失败模型问题，切主是检测问题，追数据是修复问题，
而「业务看到什么」是一致性模型问题（第 13 章）**。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「心跳超时 = 对方已死」 | 只能得出「对方失联」；进程暂停/网络抖动都会超时。处置要防抖、要隔离而非杀死 |
| 2 | 「我们三副本所以任何单点故障无感」 | 副本若在同一个故障域（同机柜/同可用区网络）等于一副本；多数派写也可能因「追不上」而降级 |
| 3 | 「自动修复越快越好」 | 修复流量不限流 → 修复风暴；误判切主不熔断 → 脑暴。自动化需要刹车 |
| 4 | 「拜占庭防护加上更安全」 | 通用数据库不采用（成本、吞吐）；崩溃型假设 + 权限边界 + 审计已覆盖绝大多数威胁模型（*书中是否展开此论断未能核实*，此处为公认工程观点） |
| 5 | 「时钟可以信任到毫秒」 | NTP 校时是「长期平均」；跨机时序必须走逻辑时钟/TSO/HLC（见 [../../db/tidb/中心化TSO.md](../../db/tidb/中心化TSO.md)） |

## 思考题

1. 画出你们系统的故障域树（进程/机器/机架/AZ/region），标出每个副本落在哪个叶子；是否存在「一个叶子故障击穿法定多数派」的组合？
2. 你们的故障检测阈值若调小一半，误切主概率与 RTO 各怎么变？有没有「切主风暴熔断」？写出你的判据。
3. 旧主复活时，你的存储层靠什么拒绝它的写？如果没有 fencing token，能提出一个不依赖时钟的正确方案吗（提示：单调序号）？
4. 修复风暴演练：模拟 1/3 节点同时掉线回归，检查限流参数与剩余节点的延迟曲线；据 15.2 的「快照+日志+校验」三段说明你们各缺哪段。
