# 03 列表与元组

## 本章地图

| 节 | 内容 | 结论 |

| 更高效的搜索 | 线性 vs 哈希 | list 查找 O(n)，set/dict 查找 O(1) |

## 核心精讲

**1. 列表 = 动态数组。** CPython 的 `list` 内部是「指针数组」，有预留容量（over-allocation）。`append` 摊销 O(1)，但偶尔触发整体搬迁（resize）。可以用 `list.append` 而非 `+=` 拼接大序列避免多次分配。

**2. 元组 = 静态数组。** `tuple` 不可变、长度固定、对象更紧凑（无 over-allocation 字段），且可作为 dict 键。纯数据、不修改的异构集合优先用 tuple。

**3. 不可变带来的优化。** 因为 tuple 不可变，CPython 在某些情况下能缓存/共享（如空元组单例、字符串驻留思路），并减少 GC 跟踪开销。

```python
# 教学示意，不参与构建
import sys
lst = [1, 2, 3]
tup = (1, 2, 3)
print(sys.getsizeof(lst), sys.getsizeof(tup))   # tuple 更小
```

## 版本演进

- 3.9 起 `list` 增加 `copy()`（更早也有 `list[:]`，但显式 API 更清晰）；3.10 起 `list`/`tuple` 支持 `|` 联合类型标注 `list[int]`（PEP 585 泛型内置，3.9 起可用，3.9 之前需 `typing.List`）。
- 3.11 起空元组与单元素元组的小对象缓存进一步稳定。
- 列表推导与 `*` 解包在 3.11+「Faster CPython」下更快。

## 近年研究与工业界开源实践（2015–2026）

- `array` 模块（同类型定长数组）在纯数值场景比 list 省内存；`collections.deque` 双端 O(1)。
- 工业界在高频路径用 tuple / namedtuple / dataclass(frozen=True) 表达不可变记录，配合类型检查。
- 3.11+ 解释器提速让「list 比 tuple 慢多少」差距缩小，但内存差仍在。

## 常见误区与本书需修正之处

- 误：以为「tuple 一定更快」——访问单元素两者几乎一样快，tuple 的优势在内存与不可变语义，不在访问速度。
- 误：把 list 当队列用（`pop(0)` 是 O(n)）；需要 FIFO 用 `collections.deque`。
- 🔧 原书未提 PEP 585 泛型标注普及，现代代码应直接写 `list[int]` 而非 `typing.List[int]`。
