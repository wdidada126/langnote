## 一、动机：为什么一个 GUI 框架要自带容器家族

三个历史原因（5.1/5.2 的字里行间）：① 90 年代编译器 STL 残缺，跨 MSVC/Borland/GCC 的容器抽象必须自建；② GUI 容器有特种需求——`wxArrayString` 要同时喂 Win32 的 `TCHAR*` 数组和 GTK 的 `gchar**`，**元素布局本身平台相关**，std::vector 帮不上；③ wxString 要在一套 API 下同时兼容 MBCS 与 Unicode 构建——这是 2.8 时代最重的包袱。STL 源码剖析讲的是"SGI 在 C++03 前造标准容器"，本章讲的是"每个大框架都得自己来一遍"——同一段历史的两份独立证词。

## 二、机制逐个看

- **基本/抽象数据类型（5.1）**：`wxInt32/wxChar/wxUniChar` typedef 层 + `wxSize/wxPoint/wxRect` 几何值类型 + `wxLongLong`（C++03 无 `long long` 保证时的兜底——今天已被标准吸收）。
- **wxVector（5.2.1）**：2.9.1 加入，`#include <vector>` 后 `typedef` 别名（机制转述 ⚠️），存在的意义只剩命名一致。**结论：它就是 std::vector**。
- **wxString（5.2.2）**：全书最高频类。值语义 + COW（写时复制）实现在 2.8 省拷贝；3.0 把内部编码统一为 **UTF-8**（Unicode build），`wchar_t`/`wxChar` 语义随平台（Windows 2 字节、POSIX 4 字节）——跨平台比较/切片按码点还是按字节的坑从此有了官方答案：用 `wxConvertToCharset`/`std::u8string` 界面对话（细节转述 ⚠️）。
- **wxArray（5.2.3）**：`wxArrayString/wxArrayInt`——前者因平台互操作仍活，后者已被 wxVector 别名取代。**void\* 数组的类型不安全**见下方实测 D。
- **wxList（5.2.4）**：双向链表 + `wxNode` 侵入式节点、`GetNext/GetData` 手写游标——对应 std::list 的前 C++ 时代 API 形状；书中"delete 时要不要 free 节点内容"的 `wxNode` 所有权讨论，就是侵入式容器（intrusive）的老故事。
- **wxHashMap（5.2.5）**：2.8 遗留哈希表，3.x 已删（转述 ⚠️）——std::unordered_map 的纯粹替代。

### 🔧 实测 D：void\* 数组容器的类型不安全（已实测 g++ 15.2，`-std=gnu++98`）

复刻 wxArray 老实现（存 `void*`、取时靠自觉转型）与模板容器（类型锁死）：

```text
legacy: 取回 0000016330871940，类型信息已丢失，误用直到崩溃才暴露
modern: 容器知道自己是 WxVector<int>，元素=42
```

混装 `int*` 与 `double*` 后按下标取回，编译器全程沉默——这正是 5.2.3 里"把 wxArray 当什么用全靠注释"的机制根源；std::vector\<T\> 把事故从运行期提到编译期，wx 在 2.9/3.0 就此缴械。样例：`d_wxarray.cpp`。

## 三、权衡与相邻概念对比

| 容器 | 2026 定位 | 替代 |
|---|---|---|
| wxString | **不可替代**（与全部 wx API 的边界货币） | std::string(string_view)/std::u8string 只在边界转换一次 |
| wxArrayString | 与 OS 交互处仍用（如 `wxGetTextFromUser` 的多选结果） | 其余场景 wxVector\<wxString\> |
| wxVector | wx 世界的 std::vector | 直接用 std::vector 也无妨 |
| wxList | 仅维护旧代码 | std::list（本身也罕用）/std::vector |
| wxHashMap | 已移除 | std::unordered_map |

与 STL源码剖析的对读点：SGI 版 allocator/特性讨论（[02-空间配置器](../STL源码剖析/02-空间配置器.md)、[04-序列式容器](../STL源码剖析/04-序列式容器.md)）针对"没有 std 怎么办"；wx 的 wxArray/wxList 针对"有 std 但跨不了平台边界怎么办"。**框架容器层的存在理由=平台边界适配，一旦 std 覆盖该职责（C++11 后基本覆盖），除 wxString 外全线退役**——这是本章可迁移的判断框架。

### 🔧 实测 D 核心段（已实测 g++ 15.2 编译运行，`-std=gnu++98`）

```cpp
struct WxArrayLegacy {            // 复刻 5.2.3 老 wxArray 的存储形态
    void** data; size_t n;
    void Add(void* p) { data[n++] = p; }
    void* operator[](size_t i) const { return data[i]; }   // 类型已丢失
};
// 混装 int* 与 double* 后按 int* 取回 double* —— 编译器全程沉默
WxArrayLegacy mix; mix.Add(pi); mix.Add(pd);
void* wrong = mix[1];             // 真解引用即 UB，故只打印指针值
// 现代: WxVector<int> 把"取错类型"变成编译期事件
```

### wxString 2026 用法卡（阅读性示例，GUI 未实测 ⚠️）

```cpp
wxString s = wxString::FromUTF8(std::string_view);  // 边界: 一次性转换
std::string out = s.ToStdString();                   // 出口: 交给 std 世界
// 2.8 遗产禁复踩:
//  wxString t = someCharPtr;      // 隐式转换在 3.x 收紧/歧义(编码按 locale 猜)
//  s.Printf(...)  → 优先 std::format 生成后 FromUTF8 入界
//  按字节 find/截断会把 UTF-8 汉字腰斩 —— 按码点用 s.GetCharLength()/索引迭代
```

容器退役时间线（把 5.2 五小节钉在版本轴上，节点年份为公开文档口径 ⚠️ 转述）：

```text
2.8(本书) ── wxVector 已预告(2.9.1) ── 3.0: wxHashMap 除名 / wxString 转内部 UTF-8
        ── 3.1/3.2: 文档明示新代码 std 容器 ── 3.3: 仅 wxArrayString 因 OS 数组协议留存
```

### 与 std 的边界协议（2026 工程口径，5.2 各节的统一出口）

- 参数/返回：public API 收放 `std::string_view`/`std::string`，**进入 wx 调用面才转 wxString**；转换点=编码策略决策点（默认 UTF-8 显式化）。
- 容器：`wxVector<T>` 只在需要与 wx API 签名对齐时用；其余一律 `std::vector`（两者本可互为别名，无转换成本）。
- 字符串比较：跨平台大小写折叠用 `wxString::Cmp` 系（ICU 级语义交给 `std::locale`/ICU 显式做），别拿 `operator==` 当折叠比较——2.8 时代就错，今天更错。
- 日志：书中 wxLog 家族不占本章小节但同属"数据类型周边"，3.x 起 `wxLog` 与 `std::format` 风格格式化并用（转述 ⚠️）。

## 核心概念速览（中英对照）

- **写时复制** — copy-on-write (COW)：2.8 wxString 的共享缓冲+写时分家策略
- **Unicode/MBCS 双构建** — 2.8 时代二选一的编译模式，3.0 终结
- **内部 UTF-8** — UTF-8 internal representation：3.0+ wxString 的统一编码
- **C 风格数组互操作** — interop array：wxArrayString 与 OS API 的数组协议
- **侵入式链表节点** — intrusive list node（wxNode）：容器拥有链接域的旧式设计
- **类型擦除容器** — void*-backed container：wxArray 老实现，见实测 D
- **伪模板时代** — pre-STL era：框架自建容器的历史动因
- **char traits** — 字符特质：std::char_traits 与 wxCharBuffer 各自的适配层
- **wxScopedArray / wxScopeGuard** — RAII 前身工具：3.0 引入的极简作用域守卫
- **string_view（对照）** — std::string_view：现代只读字符串参数，替代 wx 时代按值传串

## 最新演进与工业实践

- **C++11 后 wxString 的处境**：隐式 `const char*`/`std::string` 互转在 3.x 被刻意收紧（默认构造函数不再接受裸 char* 的隐式转换，需 `wxString::FromUTF8`/字面量 `wxT`→`wxS` 宏淡出——细节转述 ⚠️）。2026 评审口径：接口收 `std::string_view`，边界处一次性转 wxString。
- **std::u8string/char8_t（C++20）**：给"UTF-8 字节串"以语言级类型，wx 内部编码选择与之同向；`std::format`（C++20）吃掉 wxString::Format 的最后优势：跨平台格式化。
- **容器选型 2026 共识**： absl/Boost 生态早已全 std 化（abseil 的 many 组件与 C++11/14 兼容层同源），框架容器层的"过渡政府"使命结束——与 [STL源码剖析 07 专题](../STL源码剖析/07-专题-SGI_STL到现代标准库.md) 的"SGI→现代标准库"结论完全同构：当年自造轮子的每一件，先被 std 覆盖，再被框架重新导出为别名（wxVector）保留名义兼容。
- **性能补注**：COW 字符串在多线程下引用计数是全局热点，且 C++11 标准**明令禁止 std::string 的 COW**（`noexcept` 拷贝要求所致，转述口径）；wxString 因 ABI 包袱仍留部分 COW 行为——跨线程大量共享 wxString 的老代码在 2026 要做并发评审（机制判断，未实测 ⚠️）。

## 本章小结

1. wx 容器家族 = 前 STL 时代 + 平台边界适配的复合产物；2026 只有 wxString（边界货币）与 wxArrayString（OS 数组互操作）有留存理由。
2. 实测 D 把"void\* 容器类型不安全"从书中概念变成可运行证据。
3. 对读 STL源码剖析：一份"没有轮子造轮子"，一份"轮子被 std 回收"，合成完整的容器考古学。
