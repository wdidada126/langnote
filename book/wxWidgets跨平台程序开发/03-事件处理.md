# 第3章 wxWidgets 事件处理 —— 宏、事件表与 2026 年的 std::function

## 一、动机：GUI 框架的命门是"消息怎么找到函数"

操作系统递给你的只有 `(hwnd, UINT msg, WPARAM, LPARAM)` 或 GTK 信号。框架必须回答：一个点击事件如何路由到"你写的那个成员函数"？C++03 没有 lambda、没有 `std::function`、没有反射，wxWidgets 的答案是**宏生成静态表 + 成员函数指针线性查找**。Qt 的答案是 **moc 预处理生成元代码**。这一分歧是两框架 20 年恩怨的技术根源。

## 二、机制（3.1）：静态表、动态表、处理器

- **事件（3.1.1）**：`wxEvent` 携带 `EventType`（int 常量）、`id`、`Skip()` 标志。事件对象**在分派栈上构造**、处理器返回即销毁——所以绝不能保存事件引用（2.8 经典崩溃点，3.x 仍成立）。
- **静态事件表（3.1.2）**：`BEGIN_EVENT_TABLE(MyFrame, wxFrame)` 宏展开为该类的 `static const wxEventTable`，条目形如 `{类型, id, 处理函数指针}`。类定义处理函数的**函数名字符串**（宏里）而非签名——写错到运行期才暴雷。
- **动态事件表（3.1.3）**：`PushEventHandler` 挂接 `wxEvtHandler` 链，查找顺序：动态表→静态表→`Skip()` 后向父窗口冒泡。**父先于子收到命令事件**（菜单/按钮命令向上传播）与**子先于父收到鼠标事件**（捕获阶段）方向相反，这是书中一笔带过但极易晕的知识点。
- **事件处理器（3.1.4）**：`wxEventHandler` 宏系（`EVT_BUTTON`/`EVT_PAINT`/…）+ 3.x 的 `Bind(wxEVT_BUTTON, &MyFrame::OnClick, this)`——Bind 的本质是把同一张表在运行期用 `std::function`（内部实现为仿函数包成员指针）填条目，且对 `this` 持**弱引用语义**：窗口销毁后自动失效。

### 🔧 实测 A：静态事件表的 C++03 语言机制（已实测 g++ 15.2，`-std=gnu++98`）

本机无 wx 库（诚实声明），但事件表宏依赖的**纯语言机制**可 1:1 复刻：编译期数组 + 静态对象 main 前自注册 + 成员函数指针跨类转存 + 手写伪 RTTI 链。核心输出：

```text
[main 之前] 注册类 WxWindow
[main 之前] 注册类 MyFrame 派生自 -> 父类 WxWindow
[main 之前] 事件表条目 type=1001 id=-1 已登记
[main 之前] 事件表条目 type=1002 id=-1 已登记
---- main 开始：事件表已有 2 条（全部在静态初始化期登记）----
伪RTTI: f.info->IsKindOf(WxWindow)=1
分派 EVT_PAINT:
  MyFrame::OnPaint 重绘 id=7
```

三个取证点：① 表条目登记确实发生在 `main` 之前（静态初始化期）——真实 `wxEventTable` 同理；② `IsKindOf` 是沿手写 `WxClassInfo` 父链遍历，**不依赖语言 RTTI**——这正是 `wxDynamicCast` 的实现原理（当年各编译器 RTTI 支持残缺）；③ 成员函数指针用 `reinterpret_cast` 跨类转存，单继承零偏移下可运行——2.8 头文件里就是这么写的（现代标准下属 unspecified，这段代码的价值是暴露宏方案对语言特性的历史依赖）。样例全文在 `D:\develops\tmp\cppsnippets_wx\a_evtable.cpp`（仓库外）。

### 🔧 实测 B：C++17 动态绑定与生命周期（已实测 g++ 15.2，`-std=gnu++17`）

复刻 `Bind()` 的语义骨架（Signal + `std::function` 槽 + `weak_ptr` 上下文）：

```text
emit EVT_CLICKED:
  lambda槽(值捕获 by-value): type=1001
  弱引用槽存活, 处理 id=5
  成员函数槽: id=5 payload=hello
owner 析构后再 emit（裸 this 槽此时是悬空的——这就是 wxWidgets 3.x 用 Bind+weak_ptr 的原因）：
  owner 已亡, 跳过 (wxEVT 自动断连等价行为)
```

关键对照：捕获**裸 `this`** 的槽在 owner 析构后即悬空（wx 2.8 事件表把 this 转成基类成员指针调用，同样是"窗口先亡事件后到"=崩溃）；`Bind(..., this)` 的弱引用语义、boost.signals2 的连接管理、Qt 的 `QObject::destroyed` 自动断连，是同一问题的三种 2026 答案。样例：`b_bind.cpp`。

## 三、3.2 输入事件与 3.3 自定义事件

鼠标（3.2.1）/键盘（3.2.2）/其他设备（3.2.3，joystick 等）：2026 年新增的是**指针设备抽象**（笔、触控、高 DPI 坐标一律设备坐标→逻辑坐标缩放，机制转述 ⚠️）。自定义事件（3.3）两条路书中都给了：`wxDEFINE_EVENT`（3.1+，类型安全的 `wxEventType`）替代 2.8 的 `DECLARE_EVENT_TYPE` 宏；事件类派生 `wxEvent` 需实现 `Clone()`——**值语义多态**（原型模式），和 std::function 内部类型擦除同构。worker 线程向 UI 线程发自定义事件在 2012 要靠 `wxMutexGuiEnter` 或事件法，3.x 的正规解是 `wxObject::CallAfter`（2.9.3+，把调用编组回目标对象所在线程的事件循环执行）（见 [08-并发编程](08-并发编程.md)）。

## 四、权衡与相邻概念对比：宏表 vs moc vs 模板反射

| 方案 | 代表 | 元信息来源 | 错签名暴露时机 | 代价 |
|---|---|---|---|---|
| 宏+静态表 | wx 2.8 | 头文件宏展开 | 运行期（查不到即无人处理） | 表查找线性扫描 |
| Bind/`std::function` | wx 3.x | 编译器类型系统 | **编译期** | 每连接一次堆分配 |
| moc 代码生成 | Qt | 预处理额外一遍 | 编译期 | 构建系统多一步 |
| 注册式信号槽 | sigslot/Boost.Signals2 | 模板 | 编译期 | 头文件膨胀（C++03 尤甚） |
| 语言反射（未来） | C++26 P2996 | 编译期内省 | — | 尚未普及 ⚠️ |

与 Qt 之争的终局判词：**moc 赢了 DX（签名安全、IDE 可见），wx 赢了部署（无预处理步骤、纯 C++ 头文件可被任意构建系统吃掉）**；而 C++11 之后 wx 用 `Bind`+`override` 把 DX 差距基本抹平——这是"语言标准进步消解框架路线之争"的干净案例。机制类比可参 [C++API设计·插件扩展](../C++API设计/11-脚本绑定与插件扩展.md)（自注册表是同一族技术）。

### 同一件事的四代写法（迁移卡；GUI 代码阅读性示例，未实测 ⚠️）

```cpp
// ① 2.8 静态事件表（书主线）——签名错到运行期才发现
BEGIN_EVENT_TABLE(MyFrame, wxFrame)
    EVT_BUTTON(ID_OK, MyFrame::OnClick)     // 处理函数以"名字"登记
    EVT_PAINT(MyFrame::OnPaint)
END_EVENT_TABLE()

// ② 2.8 动态挂接：PushEventHandler(new MySubHandler()) —— 子处理器栈
// ③ 3.x Bind（2.9.3+）：类型进编译器，this 弱引用
btn->Bind(wxEVT_BUTTON, &MyFrame::OnClick, this);
GetEventHandler()->Bind(wxEVT_IDLE, [this](wxIdleEvent& e){ /* lambda */ });
// ④ 语言层等价（实测 B 的骨架）：std::function 槽 + weak_ptr 上下文
//    ——与 wx 3.x Bind 内部思想同构，亦即 Boost.Signals2/sigslot 的公共分母
```

## 核心概念速览（中英对照）

- **事件表** — event table：宏生成的静态 (类型,id,处理函数) 三元组数组
- **动态事件表** — dynamic event table：运行期 Push 的处理器链
- **事件冒泡** — event propagation：Skip 后沿窗口树向父传播
- **命令事件 vs 输入事件** — command vs input events：传播方向相反的默认路由
- **处理器函数指针** — event handler function pointer：宏里以名字登记、成员指针存储
- **wxDynamicCast / 伪 RTTI** — hand-rolled class info chain：wxClassInfo 父链判型
- **Bind()** — dynamic binding：3.x 推荐写法，成员指针+this 弱引用
- **弱引用上下文** — weak ref context：对象亡则连接自动断，防悬空 this
- **自定义事件** — custom event：`wxDEFINE_EVENT` + 需 `Clone()` 的事件类
- **Skip()** — propagation pass flag：交还给默认/父级处理
- **CallAfter** — queued callback：跨线程安全投递回 UI 线程的编组机制
- **事件克隆** — `wxEvent::Clone`：值语义多态/原型模式

## 最新演进与工业实践

- **官方口径**：wiki 与 3.x 文档明确 `BEGIN_EVENT_TABLE` 已过时、教程示例全部改用 `Bind`（转述 ⚠️，未逐页抓）。3.3.3 仍在修事件层 bug——机制没死，只是宏外壳退休。
- **std::function 谱系**：Bind 的类型擦除底座在语言层的出处是 N1720（Dimov 的 `std::function` 包装器生成器，wg21.link 实测 302）；今天 `std::bind` 已退位、lambda 直接捕获成员指针即可。
- **生命周期管理是 2026 的显学**：Qt6 用 `QPointer`/`deleteLater`，wx 用 `wxWeakRef`/`wxEvent` 自动断连，Rust GUI（Slint）干脆用借用检查器静态化整个问题——当年"事件打到死窗口"的崩溃学，现代以"可观测的生命周期模型"重做。
- **性能视角**：静态表线性查找在万级控件应用（老 KiCad 场景）可测出热点；解法与 2026 通用方案一致——按类型哈希分桶或连接期即编译为函数表。无基准不引数据：本处仅给机制判断。
- **论文/文献纪律**：GUI 事件系统经典论文（如 1990s 的 model-view-controller 系）多无可靠 DOI 映射，本章按规范**不注 DOI**；GoF 复合模式对 Qt/wx 事件-中介者结构的描述以书为源（无 DOI，⚠️ 只列书名）。

## 本章小结

1. 事件表宏 = C++03 无 lambda/无 `std::function` 时代的消息路由装置，其语言机制（静态初始化自注册、伪 RTTI、成员指针转存）已实测还原（A）。
2. `Bind` + 弱引用把签名错误和悬空 `this` 两类事故分别从运行期、析构期提前/消除（B）。
3. wx vs Qt 的宏 vs moc 之争，被 C++11 类型系统仲裁为"两边都对一半"。
