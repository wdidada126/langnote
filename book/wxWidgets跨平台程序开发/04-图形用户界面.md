## 一、动机：GUI 对象树是一棵"有析构协议的树"

窗口/控件在 wx 里是一棵树：每个子挂在父的 `wxWindowList` 上。4.1 按用途切窗口：基本窗口（wxWindow 裸用极少）、框架窗口（wxFrame）、对话框窗口（wxDialog，模态/非模态）、容器窗口（wxPanel/wxScrolledWindow/wxSplitterWindow）、其他（顶层 popup、MDI  Parent）。分类不新，**新的是它没告诉你的两件事**：谁 delete 谁、以什么顺序。

## 二、机制：菜单、控件谱系、布局（4.2–4.5）

- **菜单（4.2）**：`wxMenuBar` 挂到 Frame、上下文菜单绑窗口；命令 id 走第 3 章事件冒泡。`wxWidgets 3.x` 引入 `wxUICommandList` 统一"菜单项+快捷键"使能态，属书后增量（转述 ⚠️）。
- **控件（4.3）**：静态（StaticText/Line/BMP）、非静态（Button/TextCtrl/CheckBox/RadioBox/Choice/ComboBox/ListBox/Slider/Gauge/SpinCtrl）、容器（Notebook/ListBox 家族/ListCtrl/TreeCtrl/GridCtrl）、高级（DatePickerCtrl/RichTextCtrl/wxAUI 系）、自定义（自绘或组合）。2.8 到 3.x 的名单级变化：`wxGrid` 大版本重写（`wxGenericGrid` 退居兼容层）、`wxListCtrl` 报告模式成为主力、`wxRibbonBar/wxWebView` 为 3.0+ 新增。
- **布局（4.5）**：`wxBoxSizer/wxStaticBoxSizer/wxGridBagSizer` + `AddGrowableItem`；XRC（4.5.2）用 XML 描述界面实现"资源与代码分离"。书末的"为什么不用绝对坐标"在 DPI 时代有了更强理由（见演进节）。
- **4.4 高级用户界面**：AUI/DockingManager/GenericDirCtrl 一代组件——3.x 中 **wxAUI 存活且常用**，老 `wxDockingManager`（CodeProject 血统）已弃用删除（转述 ⚠️）。

### 🔧 实测 C：所有权/析构顺序陷阱（已实测 g++ 15.2，`-std=gnu++17`，无 wx 环境，复刻机制）

wx 协议：父析构遍历子表逐个 `delete`；子的析构**先把自己从父表摘除**。复刻输出：

```text
== 1) wx 风格 C++03 所有权：父亡子随，子亡自摘 ==
  top 直接子数=3
  析构 Button-1 (tag 注销)
  析构 Canvas (tag 注销)
  delete Canvas 后 top 子数=2
  析构 Panel-B   析构 Panel-A   析构 Frame
== 2) 错误遍历方式的可观察后果（索引错位 -> 部分子没被父删除=泄漏） ==
  top 子数=3，用 for i=0..size 正序 delete
  析构 A   析构 C   析构 Frame          <-- B 从未被析构：泄漏实证
```

三点结论：① "子亡自摘"少了这步就是 double free——解释 wx 为何在 `wxWindowBase::~wxWindowBase` 里做 Unregister；② 父销毁子时**从尾部 pop 或先拷贝列表**，正序索引 + 子自摘 = 上例 B 泄漏（wx 源码注释里真写了这个原因，机制转述 ⚠️）；③ `Delete()` 只是把销毁推迟到安全点（事件循环里），不改变所有权协议。样例：`c_ownership.cpp`。

## 三、权衡与 2026 讲法：智能指针能接管 wxWindow 吗？

实测 C 第 3 段给出答案：`std::vector<std::unique_ptr<Win>>` 拥有子 + 裸指针观察——**单一所有权成立时完全可用且更优**。但 wxWindow 树是"框架拥有 + 用户可提前销毁 + 销毁顺序被事件循环干预"三方协议，`unique_ptr` 自定义删除器接不进"父析构遍历子表"。2026 实务口径：

- 顶层 Frame：仍 `new`，`CallAfter`/`Close` 触发框架销毁；观察用 `wxWeakRef<wxFrame>`（3.0+ 提供，转述 ⚠️）或 `wxWindowPtr`。
- 非窗口资源（缓存、控制器）：一律 `unique_ptr`，与 [C++API设计·Pimpl](../C++API设计/02-不透明指针与Pimpl.md) 同谱。
- 禁忌组合：栈上窗口 + 父子关系（栈析构与父表 delete 双杀）——书未明说，属于当年论坛高频崩溃。

### 布局两代写法 + 所有权现代卡（阅读性示例，GUI 未实测 ⚠️）

```cpp
// 2012 书式：wxBoxSizer 手工三件套
wxBoxSizer* s = new wxBoxSizer(wxVERTICAL);
s->Add(new wxStaticText(panel, wxID_ANY, "name:"), 0, wxALL, 5);
s->Add(textCtrl, 0, wxEXPAND | wxLEFT | wxRIGHT, 5);
s->Add(btnPanel, 1, wxEXPAND);            // proportion=1 吃掉剩余空间
frame->SetSizer(s);                        // 尺寸此后由 sizer 说了算

// 2026 增量口径：
//  - wxGridBagSizer/加 wxFlexGridSizer 行列可伸缩替代"嵌套 Box 深坑"
//  - Add 的比例/标志语义没变；变的是尺寸一律逻辑像素(DPI 纪律, 本章演进节)
// 所有权速查（实测 C 的落地结论）：
//   子窗口:  new 时传 parent 即移交, 永不自己 delete（要单杀用 Destroy()）
//   观察引用: wxWeakRef<wxWindow> / wxWindowPtr<T>（3.x）
//   非窗口资源: std::unique_ptr 照常，与框架树无关
```

## 核心概念速览（中英对照）

- **框架窗口** — frame（wxFrame）：带标题栏菜单的顶层窗口
- **模态对话框** — modal dialog：`ShowModal` 阻塞自有循环
- **容器窗口** — container window（panel/splitter）：管子窗口布局与背景
- **客户区** — client area：去掉边框/菜单后可绘制的区域
- **菜单条/上下文菜单** — menu bar / popup menu：命令事件的两大入口
- **Sizer 布局** — sizer layout：以约束（比例/标志）代替绝对坐标
- **XRC** — XML resources：运行时解释 XML 构建界面的资源机制
- **AUI** — Advanced User Interface：可浮动面板/停靠框架（3.x 仍活跃）
- **两段式 Create** — two-phase construction：构造+Create+IsOk
- **子窗口自摘除** — child unregistration in dtor：析构协议的一方
- **Delete() vs destroy** — deferred destruction：请求安全点销毁
- **wxWeakRef** — weak reference template：3.x 的窗口弱观察指针

## 最新演进与工业实践

- **DPI/高分屏是本章 2026 最大的重写点**：2.8 无 DPI 抽象，书中所有 `wxSize(300,200)` 字面量在 4K/Retina 上直接失真；3.0.4+/3.1 起 wxMSW 全面 DPI-aware（per-monitor v2），坐标分**设备坐标/逻辑坐标**两套，`FromDIP/ToDIP` 转换 API（3.1+，转述 ⚠️）。今天所有布局建议从"记住 2012 的像素值"改为"以逻辑像素 + sizer 自适应"。
- **控件后端更新**：wxWebView 3.0 引入、3.3 新增 **Chromium/Edge WebView2 后端**（3.3.0 changes.txt 实测含 "Add Chromium-based wxWebView backend (#706)"）——WebView 已成 wx 应对"现代 UI 需求"的正解之一：图表、富文本、登录页用嵌入式浏览器，原生窗体壳保留。
- **wxGrid → wxDataViewCtrl 系**：数据网格推荐用 `wxDataViewModel` 观察者模型（MVC 化），2.8 式 `wxGrid` 手填单元格在 2026 被视为遗留写法。
- **XRC 的 2026 处境**：仍在维护但社区工具链（wxFormBuilder 等）活跃度远不及 Qt Designer；`std::format`/Figma 时代"XML 描述界面"没有迎来复兴，反而被 Web 前端吃掉——wx 应用内嵌 WebView 即是承认这一点。
- **工业案例**：KiCad 5→8 全程用 wxWidgets 承载其复杂停靠/网格界面（业界公认，具体组件替换细节未逐一核 ⚠️）；其踩坑路径（自绘网格转原生、AUI 大改版）与本章演进方向一致。

## 本章小结

1. 窗口家族分类学 14 年未变，变的是**每类的生命周期建议写法**（自摘协议→观察智能指针/弱引用）。
2. 所有权三条铁律：new 交父、栈上不建父子、销毁走 Close/Delete。实测 C 给出协议失效时的可观察后果。
3. 布局永远用 sizer；4.4/4.5 的组件名单要用 3.x 现状覆盖：AUI/WebView 活，DockingManager/绝对坐标死。
4. 自查三题：对话框该 `ShowModal` 还是 `Create`+非模态（自有循环的代价是什么）？为什么裸 wxWindow 不做面板？splitter 两侧窗口的父子与 sizer 归属谁？——三问答案全在"析构协议+焦点协议"两条线上。
5. 关联件：事件路由在 [03](03-事件处理.md)；自绘控件的绘图纪律在 [06](06-图像与绘图.md)；DPI 与位图倍率联动同章。
6. 一句话版本：控件名单会过时，"树+析构协议+焦点协议"三件套不会——把它当 GUI 对象模型入门读。
