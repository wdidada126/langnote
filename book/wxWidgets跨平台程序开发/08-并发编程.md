## 一、动机：单线程事件循环为什么需要并发

第 2 章的 `while(GetMessage)` 意味着**任何长任务都会冻住界面**。2.8 给的三条逃生路（9.2/9.3/9.4）：开进程、开线程、或者干脆别开（定时器/空闲事件让出控制权）。GUI 并发的全部难点在于：多控制流与单 UI 线程消息泵之间必须有一道"只许单向投递"的闸——2012 年这道闸是"从工作线程发自定义事件"，2026 年叫 **UI 线程 marshalling**（wx 的 `CallAfter` 队列就是它的官方形态）。

## 二、机制（9.2 进程路）

`wxProcess::Execute/Wait` 起外部程序 + 管道（`wxStream` 系 I/O 封装）、`End`/`Kill` 终止、进程间通信（9.2.3）走管道/套接字/共享内存（`wxTempFile`、`wxFileConfig` 等）。进程隔离的强项：崩溃不连坐、可用别的语言工具链——2026 依旧如此（浏览器、编译服务、插件沙箱全走进程）；弱项：开销与 IPC 序列化。本节内容几乎全部可平移进 std::filesystem + 平台 API 时代（`popen`→std::format 拼命令的注入风险属 2026 新增提醒）。

## 三、机制（9.3 线程路）

- **创建/启动（9.3.1/9.3.2）**：`wxThread` 派生类 + `Create()`/`Run()`，**分离式（detached）是默认气质**——joinable 语义要 2.9.3+ 的 `Wait()`（转述 ⚠️）。对照 std::thread：C++11 起 joinable/detached 显式二选一、忘 join 直接 terminate——语言层修掉了 wx 时代的"幽灵线程"类事故。
- **暂停（9.3.3）**：`Pause()` 只在**工作线程自己调用**才安全（在别的线程调它=经典死锁样本）；std::thread 干脆没有 pause——"可暂停线程"被证明是坏接口（重估结论）。
- **同步（9.3.4）**：`wxMutex/wxCriticalSection/wxSemaphore/wxCondition`；2026 一律 `std::mutex + std::scoped_lock`（C++17；scoped_lock 与 wxMutexLocker 的差别=异常安全+多锁死锁避免算法）。`wxCriticalSection`（递归？非递归语义平台有别）这类"名字含糊的锁"已被标准语言层消灭。
- **通信（9.3.5）**：书中正解"线程发自定义事件给 UI"——2.8 时代要手工 new 事件 + `wxPostEvent`；3.x 一行 `window->CallAfter(&W::Handle, args...)`（值捕获参数自动编组，2.9.3+，转述 ⚠️）。
- **终止（9.3.6）**：`Delete()`/TestDestroy 轮询协作退出；硬杀线程在 wx/std 都不可移植（`pthread_cancel` 禁区）。C++20 的答案：**std::jthread + stop_token**——协作取消进了语言，与 TestDestroy 同思想但编译器记账（jthread 自动 join 消灭"忘了 join"泄漏）。

## 四、机制（9.4 替代方案）——"不开线程"的正经军

- **9.4.1 多控制流切换**：书中口径已接近"状态机/协程"——把任务切碎进事件循环。2026 的完全体是 **C++20 协程 + 事件循环调度器**（把 wxEventLoop 当 executor：wxEVT_IDLE/timer 恢复协程句柄），以及 P2300 `std::execution`（senders/receivers，2024 年 P2300R10 已并入 C++26——wg21.link/p2300 实测 302）给"异步任务组合"的标准化语言。
- **9.4.2 定时器**：`wxTimer`（每窗口一个、绑事件或回调）——`std::chrono` 时代它仍是 GUI 定时器的正确形状（触发在 UI 线程）。
- **9.4.3 空闲事件**：`OnIdle` 切片处理（进度条、批量导入分批）——2026 定位=轻量版协程；缺陷（空闲饥饿、优先级反转）与当年相同。

### worker→UI 回报两代写法（阅读性示例，GUI 未实测 ⚠️；语言层机制同实测 B）

```cpp
// 2012（2.8）：工作线程手发事件 —— 手工 new 事件 + 手工 delete 数据
class WorkThread : public wxThread {
    wxWindow* ui;
public:
    ExitCode Entry() override {                // 书式: 协作退出轮询
        while (!TestDestroy()) {
            size_t done = Tick();
            wxThreadEvent* e = new wxThreadEvent(wxEVT_THREAD, ID_PROGRESS);
            e->SetInt((int)done);              // 事件是跨线程搬运值数据的载体
            wxQueueEvent(ui, e);               // 2.9.1+ 的队列安全投递
        }
        return (ExitCode)0;
    }
};
// 2026（3.x）: 一行编组，参数值捕获、目标亡则静默丢弃
long done = Tick();
wxGetApp().GetMainFrame()->CallAfter(&MainFrame::SetProgress, done);
// 锁具对照（9.3.4 的 2026 等价物）:
//  wxCriticalSection  → std::mutex + std::scoped_lock（多锁防死锁算法内置）
//  wxMutex+wxCondition→ std::mutex + condition_variable(谓词版防丢唤醒)
//  wxSemaphore        → std::counting_semaphore(C++20)
//  线程所有权         → std::jthread + stop_token 取代 TestDestroy 手轮询
```

### 进程路 vs 线程路速查（9.2 与 9.3 的对做决策表）

| 维度 | wxProcess 路（9.2） | wxThread 路（9.3） |
|---|---|---|
| 隔离 | 崩溃/内存全隔离 | 共享地址空间，一损俱损 |
| 通信成本 | 管道/序列化（IPC） | 共享内存+锁（便宜但危险） |
| 取消/超时 | 杀进程干净 | 只能协作退出（9.3.6） |
| 适用 | 转换器/编解码器/第三方 exe | 计算密集、需喂大量共享数据 |
| 2026 对应 | std::process(未入标)→平台 API/boost.process | std::jthread/TBB/OneAPI |

### 9.4 的 2026 完成态一行样板（协程↔事件循环缝合示意，机制示例 ⚠️）

```cpp
// 把 OnIdle/定时器当恢复点: 任务切进事件循环而不开线程 —— 9.4.1 的正统进化
wxGetApp().Schedule([this]{                 // 自制 executor: 往 UI 循环排队
    co_await ui_resume{};                    // 每个 await 点交还控制权给消息泵
    progress->SetValue(done);                // 永远在 UI 线程, 免锁免 CallAfter
});
// 与 std::execution(P2300) 对接后: schedule_on(ui_executor) 即其标准化形态
```

## 核心概念速览（中英对照）

- **UI 线程规矩** — UI-thread affinity：窗口对象只归事件循环线程碰
- **跨线程投递** — event marshalling：`wxPostEvent`/`CallAfter` 单向闸
- **分离线程** — detached thread：wxThread 的默认气质，std::thread 需显式选
- **协作终止** — cooperative cancellation（TestDestroy ↔ std::stop_token）
- **递归锁陷阱** — recursive mutex pitfall：wxCriticalSection 平台语义差异
- **条件等待** — wxCondition ↔ std::condition_variable（配 unique_lock 谓词防丢唤醒）
- **进程隔离** — process isolation：崩溃不连坐的重武器
- **管道 IPC** — pipe：wxProcess+wxStreams 的父子通信
- **定时器** — wxTimer：UI 线程节拍源
- **空闲事件** — idle processing：无工作时的分时切片
- **scoped_lock（对照）** — C++17 RAII 锁组，替代 wxMutexLocker
- **jthread（对照）** — C++20 自动 join+stop_token 的线程所有者

## 最新演进与工业实践

- **官方倾向**：3.x 文档/社区长期口径"能用 std::thread 就别用 wxThread"（转述 ⚠️）；wxThread 保留是为 ABI 与老码。
- **CallAfter 是本章的 2026 主 API**：它同时解决三件 2012 要手工做的事——线程编组、悬空 this（弱引用）、参数拷贝（值语义事件）；与 [03-事件处理](03-事件处理.md) 实测 B 的 weak_ptr 槽是同一机制学。
- **数据竞争的法律地位变化**：2012 年"看起来没事的裸共享变量"在 C++11 内存模型后正式 UB（[C++并发编程实战2·内存模型](../C++并发编程实战2/05-Cpp内存模型与原子操作.md)）；当年 wx 示例里 worker 直接读 UI 成员变量的代码，2026 评审一票否决——哪怕它"跑得挺久没崩"。
- **重负载并发的现代形态**：计算侧 `std::execution`(P2300)/TBB/OneAPI 把任务图跑在原生线程池，UI 侧只收 `CallAfter` 进度——"9.4 多控制流切换"的教学精神在 2026 的完全体。
- **工具链**：TSan 在 MSVC 无原生版、MinGW/Windows GCC 支持残缺（本库多书实测过此平台分野）——GUI 程序的线程审计常被迫回到"锁注解+评审"土法，跨平台桌面项目要预留这笔成本（机制判断）。

## 本章小结

1. wxThread 家族≈C++11 之前的语言设施化石：形状可辨（joinable/锁/条件/协作取消），细节全被 std 更优取代。
2. GUI 并发不可现代代化的部分是定律：窗口=UI 线程私有财产；跨线通信=CallAfter 投递。
3. 9.4"不开线程"一节最有未来感——协程与 std::execution 正是它的 2026 完成态。
4. 自查三题：为什么 `Pause()` 只许线程自调？worker 里直接 `label->SetLabel()` 在 2026 评审里判什么罪（数据竞争+跨线程 UI 双罪）？空闲事件做进度与定时器做进度，各自饿死条件是什么？
