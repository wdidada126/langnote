## 一、动机：为什么 1992 年会产生 wxWidgets

原书 1.1 从"跨平台开发"切入：同一份 C++ 源码要在 Windows、macOS、Linux 上都有原生外观。当时只有三条路（1.1.2 的口径）：

1. **各平台原生 API 各写一遍**（Win32 SDK / Carbon / X11 Motif）——代码三份、人力三份；
2. **自建工具包重绘一切**（TK、FLTK、早期 Java Swing）——一致但"不像本机程序"；
3. **薄抽象层 + 各平台原生后端**——这正是 wxWidgets 的路线：**编到哪个平台就调用哪个平台的原生控件**（Windows 调 ComCtl32，Linux 调 GTK，macOS 调 Cocoa），API 层统一。

wxWidgets 历史（1.2.1）：源自 Robert Roebling 的 Motif 封装与 Julian Smart 的 wxWindows，1992 年前后合流；2004 年因与微软 Windows 商标冲突**改名 wxWidgets**（改名波及全部 `wx` 前缀但保留类名）。这段历史解释了它两个"原罪"式的设计：类名一律 `wx` 前缀的命名法诞生于没有 namespace 的 C++98 前夜；API 中大量"两个平台都能懂的最小公分母"取舍来自 90 年代移植 Motif/Win32 的经验。

## 二、机制：框架结构（1.2.3）与"三层一本"

书中把 wxWidgets 拆为：

- **base 库**：字符串、容器、线程、IPC、日志、事件核心——无 GUI 也能用（`wxBase`）；
- **core 库**：窗口、控件、绘图、事件分派；
- **adv 库**：文档视图、AUI、媒体、网格等"增值组件"；
- 各平台 port：wxMSW / wxGTK / wxOSX（书中还有 wxMotif、wxPocketPC 等 2026 已消失的 port）。

链接时还依赖平台库（gdi32、comctl32 等）与可选第三方库（libjpeg/libpng/OpenGL）。**权衡**：薄抽象换来原生外观与较小体积，代价是"最小公分母"——macOS 上很多 Windows 习惯（如逐像素自绘）会碰壁，且三平台行为差异要靠 `__WXMSW__` 条件编译兜底，抽象层漏底是常态而非例外。

## 三、1.2.2"wxWidgets 评述"：当年的诚实账

书中评述与今天复盘一致的要点：

- 优点：LGPL-like 许可（wxWindows Library Licence，实质 LGPL + 静态链接豁免）——比当时 GPL 化的 Qt 对闭源友好得多，这是它在 2000 年代企业与开源工具圈扎根的头号原因；原生外观；纯 C++ 无预处理扩展（对比 Qt 的 moc）。
- 缺点：文档碎片化；Visual Designer 生态弱（wxGlade/wxFormBuilder 远不如 Qt Designer）；API 更新慢、历史包袱重；2.8 无官方 x64 二进制（当年装机成本明显高于 Qt）。

## 四、1.3 开发环境搭建：2012 vs 2026

2012 口径：Windows 上装 MinGW + 源码编译或跑 `wxMSW-2.8.x-Setup.exe`；配 Dev-C++/Code::Blocks；书中大量手工 makefile 细节。2026 口径：Windows 首选 **vcpkg `x64-windows` 一行装** 或官方 Releases 的预编译包（实测 GitHub Releases 提供 vc14x/gcc14/gcc16 的 x64 DLL 包，见 [00 核实记录](00-总览与阅读地图.md)）；Linux 发行版自带 `wx3.0-headers`/`libwxgtk3.2-dev`；macOS 走 Homebrew `wxwidgets`。CMake 时代用 `find_package(wxWidgets COMPONENTS core base)`，官方 `wx-config` 机制不变。本机未装 wx 库，所有 GUI 装填细节均为文档转述 ⚠️。

## 五、相邻概念对比：薄封装（wx）/厚抽象（Qt、FLTK）/系统库（Win32、GTK）

| 维度 | wxWidgets | Qt | 裸平台 API |
|---|---|---|---|
| 外观 | 原生 | 风格化统一 | 原生 |
| 语言扩展 | 无（纯宏） | moc（2.9 后 cmake_autogen） | 无 |
| 许可 | wxLL（类 LGPL 宽松） | 商业/LGPLv3 双轨 | — |
| 信号槽 vs 事件表 | 宏事件表 + Bind | 真语法级信号槽 | 消息泵 switch |

Qt 与 wx 的"要不要预处理元对象"之争，第 3 章用实测样例给结论；本节先立坐标。

## 核心概念速览（中英对照）

- **跨平台开发** — cross-platform development：一份源码多平台构建并保原生行为
- **薄抽象层** — thin abstraction layer：把各平台原生控件包住的最小公共 API
- **原生控件封装** — native widget wrapper：wxButton 在 Win 上是真 BUTTON 控件
- **移植后端（port）** — backend port：wxMSW/wxGTK/wxOSX 等平台实现层
- **base/core/adv 库分层** — library layering：无 GUI 基础设施与 GUI 组件分离
- **wxWindows Library Licence** — wxLL：允许静态链接闭源发布的宽松许可
- **最小公分母问题** — least common denominator：抽象层对平台特性覆盖不全
- **条件编译兜底** — `__WXMSW__` guarded code：抽象漏底时的平台补丁写法
- **wx-config** — build helper script：Unix 下向编译器注入头/库路径的官方脚本
- **Setup.h 裁剪** — build-time feature toggles：以宏关闭未用模块换体积

## 最新演进与工业实践

### 版本与活跃度（全部实测）

- GitHub Releases：`v3.3.3`（2026-07-07）、`v3.2.11`（2026-07-07）——3.2 是稳定线、3.3 是开发线，**14 年间版本推进从未中断**；仓库 `pushed_at=2026-09-24`、stars≈7.3k、open issues≈2.3k（api.github.com 实测）。
- 官方站首页口径（实测）："free, open-source C++ … Windows, macOS, Linux"，发布页列 3.2.11 stable / 3.3.3 dev。
- 3.3.0 changes.txt（raw.githubusercontent 实测摘录）：`wxMSW doesn't support versions of Windows before Windows 7`（XP/Vista 用户留在 3.2）；**wxMotif、wxGTK1 后端整体移除**——本书 1.2.3 提到的多条 port 已只余历史意义。

### C++11–23 对"wx 式抽象"的影响

书中 `wx` 前缀防冲突、`wxLongLong` 补平台字长、手写智能指针替代品这些动机，今天被语言接管：`override/final`（N2928，wg21.link 实测 302）让虚表实现可被编译器校验；`std::shared_ptr/weak_ptr` 接管了 wx 对象生命周期学（第 3、4 章实测展开）；`<type_traits>` 与 RTTI 统一让 wx 伪 RTTI 退出新建项目。

### 2012 竞争格局 vs 2026 产业重估（诚实账）

2012：桌面 GUI 选型 ≈ wx / Qt / GTK / 自绘，移动尚未吃掉桌面注意力。2026：
- **Qt6** 成为商业桌面默认答案之一；The Qt Company 2022 年收购老牌 Qt 咨询商 KDAB（业界周知事件；本次核查 qt.io 相关公告页均 404，链接未核实 ⚠️）；LGPL 路线 + Qt Design Studio 形成完整商业生态。
- **GTK4 + libadwaita** 随 GNOME 定型，Windows 支持仍非一等。
- 新势力改写"跨平台桌面"定义：**Electron/Tauri**（Web 皮）、**Flutter desktop**、**Compose Multiplatform Desktop**（JetBrains）、**Slint**（官网 https://www.slint.dev 实测 200，Rust/C++ 双 API 的嵌入式+桌面 UI）、自绘派 **Dear ImGui** 在游戏工具圈。
- wxWidgets 为何边缘化：无商业公司押注（Qt 有 The Qt Company，wx 靠社区）、设计器生态弱、API 演进保守导致 2.8→3.x 书和例子的"新鲜度半衰期"极短。为何仍活着：**Audacity、KiCad** 等重量级开源项目深度绑定（项目归属为业界公认事实，具体版本线未逐一核 ⚠️），加上"必须原生外观 + 必须宽松许可 + 必须纯 C++"三必须交集里它仍是少数解。
- 结论：本章的"选型坐标"在 2026 依然值得读，但要带着"它是细分方案而非主流方案"的前提读。

### 读本章的三个正确姿势

1. 把 1.2.1 历史线当"兼容性债务的来源学"读：每个怪 API 背后都有一个 90 年代移植事故。
2. 把 1.2.3 框架结构当"库分层教科书"读：base/core/adv 与 [大规模C++程序设计](../大规模C++程序设计/00-总览与阅读地图.md) 的物理设计话题同构。
3. 把 1.3 环境搭建**跳过**，直接读本文件的 2026 口径段——这是全书唯一"照着敲会浪费一天"的小节。

### 与同目录 C++API设计 的互文

wxWidgets 是**大型 C API/类库设计**的反面+正面教材：`wxWindow::Create` 两段构造、`wxString` 隐式转换、事件表宏——在第 2/3/5 章各对应 [C++API设计](../C++API设计/00-总览与阅读地图.md) 的构造成品、扩展性、类型设计条目。

### 2026 选型决策树（把本章坐标用起来）

```text
必须纯 C++？ ──否──> Web 系(Electron/Tauri)/Flutter/Rust(Slint) 世界，wx 出局
   │是
必须进程内极小体积 + 原生外观？ ──否──> Qt6（要预算）/ GTK4（GNOME 域）
   │是
必须静态链接宽松许可交付（不能吃 LGPL 传染/商业费）？ ──否──> Qt 商业或 LGPL 动态链接亦可
   │是
==> wxWidgets 3.2/3.3：仍在候选集，且往往是唯一解
（附加税：接受无内置排版/多媒体/高级文本引擎，一切外包）
```

三棵树问下来还留在 wx 的，典型是：音频工作站与 EDA 这类"专业工具+老代码引力"、工控上位机这类"长寿+审计"、以及"给既有 wx 项目续命"场景——恰好对应它的存量用户构成。

## 本章小结

1. wxWidgets = "薄抽象 + 原生后端"，许可宽松是历史胜负手。
2. 2026 项目活跃（3.2/3.3 双线）但定位已从"通用选型"变为"三必须交集选型"。
3. 读本章的 2012 细节（Setup.exe、2.8）时，凡 port 名单、环境搭建一律以 3.x 现状覆盖。
