## 核心精讲

### 7.7.1 MapReduce：容错靠「再算一遍」

```text
Input splits → Map → （分区 + 排序）shuffle → Reduce → Output
                        ↑ combiner 可在 map 端预聚合以减少网络传输
```

几个必须理解的设计点：

1. **输入分片与副本**：split 大小通常与底层块大小对齐（HDFS 默认 64/128 MB），让计算**尽量靠近数据**（locality）；
2. **straggler（落后者）的处理**：任务接近尾声时启动**备份任务**（speculative execution），谁先完成用谁的结果；
3. **失败即重算**：worker 死掉后，它已完成的 map 输出消失 ⇒ 必须重跑（因为中间结果存在本地盘）；
   而 reduce 输出到 HDFS（多副本）则不必重跑；
4. **确定性的重要性**：重算要求 map 函数**确定性**（对同一输入产生同一输出），否则重算会给出不同结果。

**由此得到的关键结论**：MapReduce 的「正确性」建立在「**纯函数 + 不可变输入 + 重算**」三条之上，
这也是为什么它不适合迭代算法（每次迭代都要重新读写 shuffle 结果）。

### 7.7.2 Spark：RDD 的关键思想

RDD（Resilient Distributed Dataset，弹性分布式数据集）用三个东西把自己描述清楚：
**血统（lineage）、依赖关系、分区与位置偏好**。

| 依赖 | 含义 | 失败恢复代价 |
| --- | --- | --- |
| 窄依赖（narrow） | 每个父分区最多被子分区中的一个使用（map/filter/union） | 只重算丢失分区，**可流水线执行** |
| 宽依赖（wide/shuffle） | 一个父分区被多个子分区使用（reduceByKey/join） | 需要重算整个 stage，它也是 stage 的切分边界 |

```text
为什么它能提速迭代：
  中间结果可以放在内存（cache/persist），且 lineage 允许「丢哪算哪」；
为什么它也会慢：
  长 lineage 会导致恢复代价上升（因此要 checkpoint 切断血统），
  并且 shuffle 依然是昂贵操作 —— 「内存计算一定快」是错觉。
```

### 7.8 Flink：把「流」当第一公民

#### 三段时间-semantics

| 时间语义 | 定义 | 适用 |
| --- | --- | --- |
| Processing time | 处理这条数据时机器上的时钟 | 简单，结果不可复现 |
| Ingestion time | 数据进入系统的时间 | 折中，介于两者之间 |
| Event time | 数据**自身携带的**产生时间 | 结果可复现，必须用 watermark 判断「时间是否推进」 |

**watermark 的本质是一条 heuristically 推进的水位线**（常表述为「不再会有小于 T 的数据到来」）：
它是**启发式**的（迟到的 late data 仍然可能出现），因此 Flink 提供了
allowed lateness 与**侧输出（side output）**来接收迟到的数据。
把 watermark 当成严格保证是常见的误解。

#### 异步屏障快照（7.8.4）

Chandy-Lamport 在 Flink 的实现形态：JobManager 的 checkpoint coordinator 向 source 注入**屏障（barrier）**，
屏障随数据流向下游；算子在收到第 n 个屏障之前处理属于第 n-1 个 checkpoint 的数据，越过屏障则属于第 n+1 个。

```go
// 教学示意，不参与构建
// 算子收到某路输入的屏障后：当前路停止处理后续数据，等其余各路的屏障都到齐
func (op *Operator) OnBarrier(input int, ckptID int64) {
    op.blocked[input] = true
    if allBlocked(op.blocked) {
        op.snapshotState(ckptID)   // 写下状态快照
        op.forwardBarrier(ckptID)  // 屏障继续向下游流
        op.unblockAll()            // 恢复被阻塞的输入
    }
}
```

特点：**不停机、不全局暂停**（只在对齐阶段拦住一部分输入）；对于要求更低延迟的场景可以选择
unaligned checkpoint（把在途数据也写入快照，代价是快照更大）。

#### 端到端 exactly-once（7.8.5）

三个参与方，缺一不可：

1. **source 可重放**（如 Kafka 的 offset 那一套），才能在回滚后重播同一段数据；
2. **状态 + checkpoint 一致**（由上面的 barrier 快照保证原子性）；
3. **sink 必须幂等或支持两阶段提交**（如 Kafka 的事务性生产者，或外部系统支持幂等写入/预提交）。

```go
// 教学示意，不参与构建
// 两阶段提交 sink 的骨架：preCommit 阶段的数据对外不可见
func (s *TxnSink) NotifyCheckpointComplete(ckptID int64) error {
    // 只有 checkpoint 完成时才真正「提交」外部事务
    return s.pending[ckptID].Commit()
}
```

## 版本演进

- 本书 2022 年第一版。**2015 → 2026 在这一章的变化最为显著**：
  - **流批一体 + Lakehouse**：Iceberg/Delta Lake/Paimon 一类表格式把「批处理的表」和「流处理的日志」合在一起，
    湖仓一体取代了「批/流两条独立管线」的形态；本书的 MapReduce→Spark→Flink 叙述线没有这一层。
  - **Spark 与 Flink 的 Engine 侧逃逸速度放缓**：两者在 SQL/批/流能力上互相靠拢，差别更多在状态管理与延迟模型。
  - **Kafka 的元数据面从外部协调服务转向 KRaft**，这也改变了流处理系统依赖的底座。
  - **实时数仓与 OLAP 化**：Flink SQL + 湖格式 + OLAP 引擎成为「准实时」的标准组合。
- **不变的部分**：MapReduce 的「重算 + 纯函数」思想、RDD 的 lineage、Chandy-Lamport 在流处理里的落地，
  这三者在 2026 年依然成立。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「MapReduce 适合迭代式机器学习」 | 每次迭代都要落盘并重新 shuffle ⇒ 慢；Spark 的 lineage + 内存缓存正是为了修正这一点 |
| 2 | 「Spark 是内存计算，所以一定比 MapReduce 快」 | 快的前提是数据能放进内存且 lineage 短；shuffle 与 spill 依旧存在，长 lineage 恢复代价大 |
| 3 | 「宽依赖只是跑得慢一点」 | 宽依赖是 stage 边界，也是容错重算的放大源：一个分区丢失意味着整段上游要重算 |
| 4 | 「watermark 保证不会有迟到数据」 | watermark 是启发式推进的；迟到要靠 allowed lateness / 侧输出处理 |
| 5 | 「Flink checkpoint 会暂停整个作业」 | 对齐模式下只阻塞部分输入；unaligned 模式连阻塞都省了（代价是快照变大） |
| 6 | 「Flink 提供了端到端 exactly-once」 | 它提供的是**框架内的**一致性保证；端到端还要 source 可重放 + sink 幂等/两阶段提交 |
| 7 | 「exactly-once 等于每条消息只处理一次」 | 语义上等价，物理上仍会重算；「恰好一次」指的是**结果不受重算影响** |
| 8 | 「重试 + checkpoint 就够了」 | 若 map/用户函数不确定（随机数、`now()`、外部查询），重算会得到不同结果 ⇒ 要保证可复现 |
| 9 | 🔧 本书的批处理/流处理二分没有涵盖 **Lakehouse / 湖表格式** | 2026 的现实：Iceberg/Delta/Paimon 让「同一套表」同时服务批作业与流写入；批处理与流处理已经不再是两条独立管线，本书的叙述在此处以 2015 年前后为界 |
| 10 | 🔧 本书没有讨论**Kubernetes Operator 作为控制循环**这一现实形态 | 2026 的现实：声明式期望状态 + reconcile 循环 + 资源版本号（resourceVersion）就是分布式控制循环的日常形态；它把本书第 4、7 章的「元数据/协调」概念变成了每个 Operator 都在用的东西 |
| 11 | 🔧 本书对流处理「状态成本」的讨论偏轻 | 2026 的现实：状态大小与 checkpoint 时长是流作业的头号运维问题（状态后端、增量 checkpoint、远端状态、TTL）。选型时往往比「延迟多少毫秒」更关键 |
| 12 | 🔧 本书的 Flink 叙述未涉及 **SQL/Table API 层与 OLAP 化** | 2026 的现实：绝大多数 Flink 作业通过 SQL 表达，并与 OLAP 引擎/湖格式相连；纯 DataStream 编程的比例在下降 |
