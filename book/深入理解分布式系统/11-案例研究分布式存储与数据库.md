| 7.3.4 其他优化 | 局部性群、压缩、缓存两级、commit log 重放 | LSM 的一整套调优清单，今天仍在 RocksDB 里被继续使用 |

| 7.5.1 Cassandra 数据模型 | ColumnFamily / SuperColumn/宽行；后来有 CQL 表模型 | 把 Bigtable 的宽列模型带上 Dynamo 的 quorum 复制 |

| 7.5.3 协调请求 | coordinator 按一致性级别把请求转发到副本；读修复/摘要读参与 | coordinator 不是 leader，任何节点都可以当 coordinator |
| 7.5.4 一致性级别 | ONE/TWO/QUORUM/LOCAL_QUORUM/EACH_QUORUM/ALL | 一致性级别等于「per-request 的 CAP 开关」 |
| 7.5.5 轻量级事务 | Paxos-based LWT（serializable IF NOT EXISTS / CAS） | 用 Paxos 换取单行线性一致，代价是 4 轮往返 |
| 7.5.6 二级索引 | 本地索引 vs 物化视图 | 「写多份」与「读多节点」的取舍 |
| 7.5.7 批处理 | logged/unlogged batch；跨分区 batch 需要 batchlog 保障 | batch 不是事务，除非显式用 logged batch |
| 7.6.1 Spanner 数据模型 | 半关系模型 + schema + `INTERLEAVE IN PARENT` | 把「父子表的 locality」写进 schema |
| 7.6.2 架构 | zone / spanserver / placement driver / Paxos group | 每个 tablet 一个 Paxos 组 ⇒ Paxos 不再是「一个集群一个组」 |
| 7.6.3 TrueTime | GPS + 原子钟；返回的是**区间** `[earliest, latest]` | 「等不确定性过去」 ⇒ 不需要互相沟通也能得到外部一致性 |
| 7.6.4 读写事务 | 两阶段锁 + 2PC + commit-wait | 强一致仍有代价；min commit delay ≈ 2ε |
| 7.6.5 只读事务 | 取一个时间戳做快照读；follower 可服务（若够新） | 只读事务不用锁 ⇒ 这是 Spanner 性能的关键 |
| 7.6.6 快照读和模式变更事务 | 多版本 GC + 模式变更的特殊处理 | 「多版本 + 在线演进」让 DDL 成为在线操作 |

## 核心精讲

### 7.3 Bigtable：一个「披着 NoSQL 外衣的有序映射」

四维键的实际含义：

```text
(row:string, column family:qualifier, version:int64) → string(byte[])
```

理解要点：

- **row key 有序且按 range 切分成 tablet** ⇒ 相邻的 row 通常在同一 tablet，利于 scan，但也带来「顺序 key 热点」；
- **column family 是「locality / ACL / 压缩」的单位**，qualifier 在 family 内可自由新增 ⇒ 半结构化；
- **多版本由 timestamp 决定**，可按时间读取历史；GC 规则可以「只留最近 N 版」或「只留最近 T 时间」；
- ** tablet 的原子单位是一次 row-level mutation**：单行读写原子，**跨行没有事务**。

#### SSTable 与 LSM

```text
写：commit log(WAL) → memtable(sorted) → flush → SSTable(immutable) → compaction(merged)
读：memtable → (block cache) → SSTable 索引块 → 布隆过滤器判断 → 可能的多次 SSTable 探查
```

由此推出三对取舍：**写友好 vs 读放大 / 空间友好 vs 写放大(compaction) / 顺序写 vs 随机读**。
这也是为什么今天的 RocksDB/LevelDB 生态仍然在本节的技术空间里做微优化。

### 7.4 Dynamo：永远可写，代价是「冲突交给你」

```text
N=3, W=2, R=2 之外，Dynamo 真正特别的是：
  sloppy quorum + hinted handoff    → 分区期间也接受写（临时接管）
  向量时钟                          → 保留并发版本
  读侧协调 + 读修复 + Merkle 反熵    → 收敛的责任在读侧与后台
```

**这套设计像一次明确的业务决策**：购物车写入必须 100% 成功，
因此「多版本购物车 + 读时合并」要比「写失败」划算。

### 7.5 Cassandra：把两个时代的想法合在一起

| 维度 | 继承 Dynamo | 继承 Bigtable |
| --- | --- | --- |
| 分布 | 一致性哈希 ring + gossip + hinted handoff | — |
| 复制 | 可调 quorum / 多 DC aware snitch | — |
| 存储 | — | commit log + memtable + SSTable + compaction |
| 数据模型 | — | ColumnFamily / 宽行 / 后续 CQL |

一致性级别的「换算表」回答了这里最重要的问题：

| 一致性级别 | 语义 | R+W 是否满足 quorum |
| --- | --- | --- |
| `ONE` | 任意一个副本响应 | 视 W 而定（W=ONE 不满足） |
| `QUORUM` | 多数副本响应（RF/2+1） | `QUORUM + QUORUM` ⇒ 满足 R+W>N |
| `LOCAL_QUORUM` | 本 DC 内多数 | 单 DC 语义，跨 DC 一致性要配 `EACH_QUORUM` |
| `ALL` | 全部副本 | 最强，可用性最弱 |

```go
// 教学示意，不参与构建
// 把「一致性级别」换算成 quorum 是否成立：这是判断一次读写能否线性化的第一步
func readWriteStronglyConsistent(rf int, wCL int, rCL int) bool {
    // wCL / rCL 已经换算成实际需要的副本数（如 QUORUM = rf/2 + 1）
    return wCL+rCL > rf
}

// LWT 的语义：给单行操作加一层 Paxos，代价是多轮往返，不能放在高 QPS 路径上
func (t *Txn) CompareAndSet(key string, expect, update []byte) (applied bool, err error) {
    proposal := Proposal{Key: key, Expected: expect, Update: update}
    return t.paxosGroup.Propose(proposal) // 被多数派接受 ⇒ applied 为真
}
```

### 7.6 Spanner：用 TrueTime 把强一致拿回来

TrueTime 的关键不是「时间更准」，而是**把不确定性显式化**：

```text
now() 返回区间 [earliest, latest]，区间宽度 ε 通常维持在毫秒甚至亚毫秒量级
```

Spanner 的两条关键结论：

1. **外部一致性（external consistency = strict serializability）**：若 T2 在 T1 提交之后才开始，则 T2 的时间戳大于 T1；
2. **Commit Wait**：取得提交时间戳后，必须**再等 ε 时间**才允许把 T 的结果暴露出去 ⇒ 保证任何在其后发起的事务都能看到它。

```text
读写事务：2PL + Paxos leader lease + 2PC + commit-wait → apply
只读事务：取 TT.now().latest 作为快照读时间戳 → 无需锁，甚至可由足够新的副本处理
```

**由此得到 Spanner 的真教训**：强一致不是靠「更快的网络」，而是靠「把时间不确定性做成一等公民」。

## 版本演进

- 本书 2022 年第一版。四个案例中，两个来自 2006/2007，一个来自 2010，Spanner 来自 2012；
  **2022 → 2026 的变化**：
  - **Bigtable 模型的扩散比模型本身更重要**：今天的 SSTable/LSM stack（RocksDB 与其各语言 port）
    是HBase/TiKV/Cockroach/Pebble 的共同底座；
  - **Dynamo 论文里的假设被产品在逐步矫正**：应用层处理合并的成本常常高于预期，
    新一代系统越来越倾向于提供「可调一致 + 服务端合并（CRDT/LWW with harder checks）」；
  - **Cassandra 的 CQL 化**：现在的「Cassandra 数据模型」几乎 CQL 表 + partition/clustering key，
    SuperColumn/Thrift 时代已经过去；
  - **Spanner 一族成为商用基准**：多个商业化 NewSQL（含国内云 RDS 的分布式版）宣称「外部一致性」语义，
    但大多数没有 GPS/原子钟，而是用 TSO/HLC + 一定假设来逼近 —— 本书 7.6 的读法是理想样例。
- **2026 视角的两条补丁**：① Jepsen 一类的第三方评测让「宣称强一致」必须可复核；
  ② 「Spanner 路线」与「TSO 路线（TiDB/国产库）」的对照，是今天选型的常见分歧点。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Bigtable 是一个关系数据库」 | 不是。它提供单行的原子 mutation，无跨行事务、无二级索引之外的查询能力 |
| 2 | 「LSM 读慢，所以不适合读场景」 | 用块缓存 + 布隆过滤器 + compaction 策略可把随机读逼近 B+tree；代价是 compaction 带来的写放大 |
| 3 | 「Dynamo 的冲突都会自动解决」 | 它把并发版本保留起来，很多情况需要**应用层合并**（购物车合并是最典型的例子） |
| 4 | 「sloppy quorum 是 quorum」 | 不是：它在分区期间临时更换了副本集合，因此不满足「读写集合相交」的前提 |
| 5 | 「Cassandra 的一致性级别是全局配置」 | 是 per-request 的：不同请求可以用不同 CL；真正的一致性取决于读写 CL 的组合是否满足 quorum |
| 6 | 「LWT 是便宜的 CAS」 | 轻量级事务走 Paxos，通常需多轮往返；它不是给高 QPS 路径设计的 |
| 7 | 「batch 就是事务」 | 只有 logged batch 提供有限的原子性；普通 batch 只是省网络往返 |
| 8 | 「Spanner 强一致靠的是时钟特别准」 | 靠的是**把不确定性做成区间并 wait**；没有 wait 就没有外部一致性 |
| 9 | 「只要用了 Spanner 就没有时钟问题了」 | 单区域到跨区域的 Read/write 正确性仍然依赖 Paxos leader lease 的有效性，这是另一层假设 |
| 10 | 🔧 本书对「宣称强一致」缺乏第三方评测视角 | 2026 的现实：Jepsen 一类公开评测反复证明「文档宣称」与「默认配置下的实际保证」存在落差。读本节四个案例时应同步养成习惯：**先确定默认配置，再看声称的模型** |
| 11 | 🔧 本书没有对比**TrueTime 路线 vs TSO/HLC 路线** | 2026 的现实：绝大多数商用分布式数据库没有 GPS/原子钟，用 TSO 或 HLC 逼近强一致，并在一定假设（单点时钟、漂移上界）下成立。本书以 Spanner 为理想样例，缺少这条对照，容易让读者高估强一致的普适成本 |
| 12 | 🔧 本书对 Cassandra 的数据模型停留在 Thrift/SuperColumn 时代语义 | 2026 的现实：Cassandra 的主用模型是 **CQL**（partition key + clustering key），SuperColumn 已被弃用；读本节时应按 CQL 重新理解「宽行」 |
| 13 | 🔧 本书未涉及 HTAP 这一 2015 后兴起的形态 | 2026 的现实：TiDB（VLDB 2020）等把行存主副本与列存只读副本放进同一套共识体系；这是本书四个案例都没有覆盖、但今天极常见的差分形态 |
