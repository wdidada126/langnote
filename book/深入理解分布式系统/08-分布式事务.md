# 第 5 章 分布式事务

> **本章地图**：定义「跨多个节点/多个资源的事务」→ 求 **原子提交**（2PC / 3PC / Paxos Commit / 基于 Quorum 的提交 / Saga）
> → 求 **并发控制**（2PL / OCC / MVCC）→ 以一个完整工业案例（Percolator）收尾。
> 一句话主线：**分布式事务 = 原子提交 + 并发控制**，前者保证「要么都成、要么都不成」，后者保证「互相不干扰」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 什么是分布式事务 | 多个参与者 + 一个协调者；跨资源、跨机房 | 一旦涉及多节点，提交决定就不再由单机 RM（资源管理器）单独完成，需要一个跨节点的「决定机制」 |
| 5.2.1 两阶段提交（2PC） | prepare 投票 + commit 执行；协调者日志是核心 | 简单且正确，但**协调者崩溃会阻塞**（永久握着锁），这是第 2 章两将军问题的现实版本 |
| 5.2.2 三阶段提交（3PC） | canCommit / preCommit / doCommit | 解决了「协调者崩溃 + 参与者超时」的一种情形，但**在网络分区下仍不成立** ⇒ 实践中不用 |
| 5.2.3 Paxos 提交算法 | 复制协调者，每一票局都是一次 Paxos 实例 | 用「复制状态机化的协调者」消除阻塞，代价是消息数与延迟 |
| 5.2.4 基于 Quorum 的提交协议 | 参与者也能充当「协调者」；用 quorum 冗余决定 | 把「单点」变成「服务中可用的 quorum」，是 recent lineage 的解法 |
| 5.2.5 Saga 事务 | 长事务拆成可逆的小事务；失败走补偿 | 牺牲隔离性换取长事务可行性；是微服务时代的默认选择 |
| 5.3.1 两阶段锁（2PL） | 加锁/解锁两阶段；严格 2PL | 强一致的经典解；分布式下要处理跨节点死锁 |
| 5.3.2 乐观并发控制（OCC） | 读 + 校验 + 写三个阶段 | 低冲突下吞吐高；高冲突下有重启风暴（FoundationDB 是其代表实践） |
| 5.3.3 MVCC | MVTO / MV2PL / 快照隔离 SI | 读写互不阻塞的现代默认；注意 SI ≠ 可串行化（写偏斜） |
| 5.4 Percolator | Google 增量处理系统的事务层，确认 SI + 客户端驱动的 2PC | 工业参考实现；TiDB 直接继承了这个模型 |

## 核心精讲

### 5.2.1 2PC：正确、简单、会阻塞

```text
协调者                          参与者
  |—— prepare(vote request) ——>|
  |<—— vote yes/no ————————————|
  |   （协调者写 commit 日志并持久化）
  |—— global commit/abort ——>|
  |<—— ack ————————————————————|
```

四个必须记住的点：

1. **协调者的 `commit` 日志是单点判优依据**：在写这个日志之前崩溃 ⇒ 可以安全 abort；之后崩溃 ⇒ 必须重驱完成 commit。
2. **参与者在 prepare 后即进入不确定状态（in-doubt）**：必须自己保留 undo/redo 日志，不能替协调者做决定。
3. **协调者崩溃 = 阻塞**：参与者不知道最终决定，只能握着锁等待 ⇒ 这就是 2PC 的痛点。
4. **两个重要的工程优化**：presumed abort / presumed commit 可以减少日志量与交互次数。

### 教学示意：2PC 协调者状态机

```go
// 教学示意，不参与构建
type Coordinator struct {
    votes   map[string]bool
    decided bool
}

func (c *Coordinator) Run(parts []Participant) Decision {
    // 阶段一：收集投票
    for _, p := range parts {
        if !p.Prepare() {
            return c.Abort(parts) // 任一 no ⇒ 决定 abort
        }
    }
    // 关键的持久化点：一旦写入就不能反悔
    c.log.Write("commit")
    c.decided = true
    // 阶段二：驱投递（可重试，必须幂等）
    for _, p := range parts {
        p.Commit()
    }
    return Commit
}

func (c *Coordinator) Recover(parts []Participant) Decision {
    if c.log.Last() == "commit" {
        for _, p := range parts {
            p.Commit() // 崩溃后重做：只允许是幂等可被幂等驱动的
        }
    } else {
        for _, p := range parts {
            p.Abort()
        }
    }
}
```

### 5.2.2 3PC：为什么工业不用

3PC 在 commit 前插入 pre-commit，使参与者在「协调者已崩溃但大家已 pre-commit」时可以安全提交。
这解决了一部分「阻塞」问题，但它依赖于**超时可靠地区分崩溃与慢**；
在网络分区或时钟不准的现实里，这个假设不成立 ⇒ **3PC 更多是理论上的中间站，工业不用它**。

### 5.2.3 Paxos Commit（Gray & Lamport, TOCS 2006）

思路：把协调者变成一个复制状态机。每个参与者的|vote 都是一次 Paxos 实例的一个 ballot：
- 每个参与者先把自己灌入一个 acceptors group；
- 协调者（及其副本）对每个参与者的 votes 做一次 Paxos，达成「这个参与者投了 yes」的一致；
- 收集到所有参与者都 yes 的一致性 Paxos 实例后，提交。

代价是每个参与者的决定要一次 Paxos（消息数与延迟按参与者数线性增长），所以实际部署常常改动为
「用 Paxos/Raft 复制协调者 + 普通 2PC」的混合：协调者不再单点，参与者照旧。

### 5.2.5 Saga：微服务时代的默认形态

Garcia-Molina & Salem（SIGMOD 1987）的原始定义：**一个长事务 T 分解成 T1..Tn，每个 Ti 配一个补偿 Ci**。
若 Tj 失败，则以逆序执行 C(j-1)..C1。

| 问题 | 解释 |
| --- | --- |
| 缺乏隔离性 | 其他事务可以看到中间状态（脏脏/丢失更新可能）；对策：语义锁、交换式更新、版本号 |
| 补偿必须幂等且可能失败 | 补偿本身可能要重试；最终往往需要人工介入 |
| 两条组织方式 | **编排（orchestration，中心协调者）** vs **编排（choreography，事件驱动）** |

### 5.3 并发控制三法对照

| 方法 | 核心 | 适用场景 | 主要缺点 |
| --- | --- | --- | --- |
| 2PL（严格版） | 冲突即阻塞，提交后释放 | 冲突高、写多 | 跨分布式死锁检测代价高 |
| OCC | 乐观执行，提交前校验 | 冲突低、短事务 | 高冲突下重启风暴 |
| MVCC / SI | 多版本 + 快照读 | 读多写少、OLTP | SI 允许写偏斜，需要 SSI 才真正可串行化 |

### 5.4 Percolator：把 SI 做成分布式

Google 的增量索引处理系统（OSDI 2010）的事务层设计：

- **依赖 TSO 分配时间戳**（start_ts, commit_ts），因此获得的是**快照隔离（SI）**而非可串行化；
- **客户端驱动 2PC**：没有中心协调者，`prewrite` 阶段在**一个 primary key** 上放置锁，
  其余 secondary keys 记录指向 primary 的指针 ⇒ **primary 锁就是整个事务的原子开关**；
- 遇到另一个事务的锁时，处置依据是 primary 是否已提交（通过查询 primary 的元数据写记录判定）；
- 崩溃事务由后续读操作（自带的 `checkTxnStatus` + `cleanup`）来清理 ⇒ 叫「惰性恢复」。

## 版本演进

- 本书 2022 年第一版。2015 → 2026 的变化集中在两点：
  - **确定性事务的复兴**：Calvin（SIGMOD 2012）之后，Aria（VLDB 2020）等把「先定序再执行」
    推成了可选的主流路线之一，绕过分布式 2PC 中的不确定性。
  - **Saga 从「模式」变成「基础设施」**：编排引擎（Temporal 等）把补偿、重试、幂等变成框架能力，
    本书 5.2.5 讲的还是「手写补偿」，2026 年更多是「写工作流 + 幂等的活动」。
- **不变的部分**：2PC 与 Percolator 模型依然是 NewSQL 的底座；
  2022 年以来没有新的原子提交模型替代它们，只有更好的实现风格（批量提交、流水线、异步化）。

## 近年研究与工业界开源实践（2015–2026）

- **研究**：确定性事务之外，近两条活跃主线是**跨地域事务**与 **OCC 的复兴**：
  Sundial（CIDR 2021）用逻辑租约降低重启率，代表了「OCC 在现代硬件/网络上重新可用」这一方向。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「2PC 保证了原子性，所以很安全」 | 它保证原子，但**不保证可用**：协调者崩溃会一直阻塞，这是为什么要把它复制出来（Paxos Commit / Raft 协调者） |
| 2 | 「3PC 解决了 2PC 的问题」 | 3PC 只在「能可靠区分崩溃与慢」时成立；网络分区下它会误判，故工业不用 |
| 3 | 「Saga 提供隔离性」 | Saga **没有隔离性**（中间状态可见）；需要业务侧补救（语义锁、版本号、拼凑式更新） |
| 4 | 「Percolator 提供可串行化」 | 它提供的是**快照隔离**；写偏斜仍可能发生 |
| 5 | 「 MVCC 就不需要锁了」 | 写仍要加锁/写意图；且 SI 允许写偏斜，需要 SSI 或显式加锁 |
| 6 | 「分布式事务慢主要是因为 2PC 多了一轮网络」 | 主要成本是**锁的持有时间**（跨越 prepare→commit 全过程）+ 时间戳获取 + 协调者持久化，而不是那一轮 RPC |
| 7 | 「协调者只是个进程，崩了重启即可」 | 协调者崩溃期间参与者是 in-doubt 状态，握着锁；恢复期间业务受影响 |
| 8 | 「重试一定安全」 | 只有幂等操作可以随意重试；非幂等写入必须有幂等键/去重表，且去重状态要与业务在同一事务里 |
| 9 | 🔧 本书 5.2.5 的 Saga 仍停留在「手写补偿」层面 | 2026 的现实：**编排引擎**（Temporal 一类）把补偿、重试、超时、幂等与可观测变成框架能力。读本节时应把它理解为「手写一个工作流引擎的最小相當」，而不是生产形态 |
| 10 | 🔧 本书的并发控制讨论没有涉及确定性事务 | 2026 的现实：**Calvin/Aria 路线**用「先定序后执行」消除执行期不确定性，从而避免分布式 2PC 中的 abort 与锁等待；这是 2015 年后最有影响的事务研究方向之一 |
| 11 | 🔧 本书对「高并发下的隔离级别选择」没有给出工程度量方法 | 2026 的现实：选 SI 还是 SSI、乐观还是悲观，本质上是在度量**冲突率与重试成本**；本书偏概念，工程侧可参照 [../数据库系统概念6/15-并发控制.md](../数据库系统概念6/15-并发控制.md) 的测量视角 |
| 12 | 🔧 本书未涉及**跨服务（跨消息队列）的原子性**这一常见现实需求 | 2026 的现实：「写本地表 + 写消息」的原子性通常由 **outbox 模式**或工作流引擎提供，而不是使用 XA 分布式事务；这是微服务里最常见的「分布式事务」，本书的原子提交章节没有等价物 |
