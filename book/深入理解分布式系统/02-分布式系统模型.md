# 第 2 章 分布式系统模型

> **本章地图**：两个「不可能」的经典寓言（两将军 / 拜占庭将军）→ 把寓言翻译成**可推理的系统模型**
> （网络链路模型、节点故障类型、按时间划分的模型）→ 最后给出两节点之间最基本的**传递语义**。
> 本章的作用只有一个：**给后面五章提供一个可以证明对错的地基**。第 4 章的 FLP、Paxos、Raft，
> 全部是建立在第 2 章所做的假设之上的。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 2.1 两将军问题 | 两支军队只能靠可能丢失的信使协同进攻 | 在**信道可能丢包**的前提下，不存在能保证双方同时进攻的协议；这就是「共识」的第一个不可能轮廓 |
| 2.2 拜占庭将军问题 | 将军中可能有叛徒，消息可能被伪造或选择性隐瞒 | 口头消息下容忍 f 个叛徒需要 **3f+1** 个节点；这是第 4 章 PBFT 的门槛来源 |
| 2.3.1 网络链路模型 | 可靠链路 / 公平丢失链路 / 任意链路 | 假设越强，能实现的算法越多；但真实网络最弱假设才安全 |
| 2.3.2 节点故障类型 | crash-stop / crash-recovery / 遗漏 / 拜占庭 | 「故障能恶劣到什么程度」决定所需冗余度：多数派 vs 2f+1 vs 3f+1 |
| 2.3.3 按时间划分系统模型 | 同步 / 异步 / 部分同步 | **部分同步**是真实系统的常态，也是 Paxos/Raft 的假设；纯异步下 FLP 掐死确定性共识 |
| 2.4 消息传递语义 | at-most-once / at-least-once / exactly-once | exactly-once 需要「重传 + 去重」或事务性输出，网络层给不了免费午餐 |
| 2.5 本章小结 | 归纳 | 系统模型 = 网络 + 故障 + 时间三元组；写算法前必须先说清这三项 |

## 核心精讲

### 2.1 两将军问题：信道不可靠 → 不可能

两支友军隔着山谷夹击敌军，任一方单独出击必败，因此必须**同时**进攻。
通信只能派信使穿越山谷，而信使可能被俘（消息丢失）。

结论：**不存在**能保证两支军队在同一时刻进攻的确定性协议。

为什么？用「最短反例」的话来体会（这是标准证明的直觉版）：
任何能达成一致的协议都有一条「最后一条决定性的消息」——如果在某次执行里，
这条最后一条消息被丢掉了，那么未收到的一方必须保持保守（不进攻），
于是已发出消息的一方无法判断对方是否收到，也就无法「知道对方知道」。
这个推理可以无限递归下去，因此没有「最短协议」存在 —— 严格证明见 Gray 的整理。

**工程含义**（比证明本身更重要）：

- 现实里的「两将军」由 **重试 + 幂等 + 超时/租约** 变成「够用的概率」：TCP 三次握手解决不了两将军，
  但它把「两端都确认」的概率提高到可接受；
- 分布式提交协议（本书第 5 章的 2PC）正是被困在这一不可能里：**协调者崩溃即阻塞**。

### 2.2 拜占庭将军问题：节点可能说谎

与两将军不同，拜占庭模型假设**消息本身是可靠的**，但**节点可能任意作恶**（篡改、重放、串通、选择性沉默）。

经典的口头消息（oral message）结论（Lamport, Shostak & Pease, TOPLAS 1982）：

- 总节点数 **n ≥ 3f + 1** 时，可以容忍 f 个拜占庭节点，且该界是最优的（f ≥ n/3 时不可解）；
- 若使用**签名消息**（unforgeable signatures），能突破 n ≥ 3f+1 的限制。

由此得到整个分布式世界最有用的一张表：

| 目标 | 故障模型 | 最少节点数 | 典型算法 |
| --- | --- | --- | --- |
| 只要大多数还在就行（非拜占庭） | crash-stop / crash-recovery | 2f + 1 | Paxos、Raft、Zab |
| 容忍说谎 | 拜占庭（口头消息） | 3f + 1 | PBFT |
| 容忍说谎 + 开放成员 | 拜占庭 + 女巫/身份不确定 | — | PoW（比特币）、PoS 家族 |

### 2.3 系统模型：把「假设」写成三元组

作者这里整理的模型口径与教科书一致。任何分布式算法的正确性陈述，都只对一组特定假设成立。
务必养成习惯：**读论文先读它的 System Model 小节。**

#### 2.3.1 网络链路模型（弱→强）

| 模型 | 定义 | 备注 |
| --- | --- | --- |
| 任意链路（arbitrary / lossy） | 消息可能丢、重复、乱序、被篡改 | 最弱；配合密码学可升为可靠 |
| 公平丢失链路（fair-loss） | 无限次重传中至少一次成功 | TCP / 重传近似的现实模型 |
| 可靠链路（reliable link） | 只要两端都不崩，消息最终到达且不重复 | 由重传 + 去重实现；**不要白拿这个假设**——它是被构造出来的，不是网络给的 |

#### 2.3.2 节点故障类型（弱→强）

| 类型 | 行为 | 冗余需求 |
| --- | --- | --- |
| crash-stop（失败-停止，最常见假设） | 一旦停止就永远停止，不会「做完半件事再继续」 | 多数派 2f+1 |
| crash-recovery（失败-恢复） | 崩溃后重启，内存状态丢失，磁盘状态保留 | 需要**持久化日志**再参与投票（Raft 的关键要求） |
| 遗漏（omission） | 该发的消息不发/该收的收不到 | 介于 crash 与 Byzantine 之间 |
| 拜占庭（arbitrary） | 任意行为，包括说谎、串通、伪造 | 3f+1（口头） |

#### 2.3.3 时间模型——决定了「能不能等到答案」

| 时间模型 | 定义 | 后果 |
| --- | --- | --- |
| 同步（synchronous） | 存在已知上界 Δ：消息延迟、进程步进速度都有上限 | 可以靠**超时**判断节点已死；故障检测器完美；共识可解 |
| 异步（asynchronous） | 没有任何时间上界 | 无法区分「慢」与「死」；FLP 告诉我们确定性共识不可解 |
| 部分同步（partially synchronous） | 存在一个 GST（global stabilization time），在其之前网络可能混乱，之后进入同步 | **现实工业系统的实际假设**；Paxos/Raft 在此模型下安全 + 最终活性 |

> 关键理解：算法要保证的是 **安全性（safety）在任何时候都不被破坏**，
> 而 **活性（liveness）通常只能承诺「在网络/时间假设稳定后成立」**。这句话是理解第 4 章所有算法的钥匙。

### 2.4 消息传递语义

| 语义 | 实现手段 | 风险 |
| --- | --- | --- |
| at-most-once（至多一次） | 发一次不重试 | 丢，接受请求损失 |
| at-least-once（至少一次） | 超时重传直到收到 ACK | 重复，要求幂等 |
| exactly-once（恰好一次） | 重传 + 接收端去重（序号/幂等键）或事务性写入 | 「恰好」只是在**语义层**成立 |

```go
// 教学示意，不参与构建
// at-least-once 发送：应用层的「至少一次」，靠序号去重升级为「有效恰好一次」
type Sender struct {
    seq     uint64
    pending map[uint64]*Packet // 未 ACK 的包
}

func (s *Sender) Send(ctx context.Context, body []byte, ch chan<- *Packet) error {
    p := &Packet{Seq: s.seq, Body: body}
    s.seq++
    for {
        select {
        case ch <- p:
        case <-ctx.Done():
            return ctx.Err()
        }
        select {
        case <-acked(p.Seq): // 收到 ACK：离开
            return nil
        case <-time.After(backoff(p.Seq)): // 超时：退避后重发「同一序号」
            continue
        }
    }
}

// 接收侧去重：同一 Seq 只处理一次 → 语义层的 exactly-once
func (r *Receiver) Handle(p *Packet) bool {
    if r.seen[p.Seq] {
        return false // 重复包，丢弃但仍回 ACK
    }
    r.seen[p.Seq] = true
    return true
}
```

注意上面的「去重表」必须在**崩溃恢复后仍然存在**，否则 restart 之后会重复处理——
这就是为什么生产系统要把去重状态写进数据库并与业务处理放**同一个事务**里。

### 2.5 本章小结

- 两将军：信道不可靠 ⇒ 「同时确认」不可能（第 5 章 2PC 的阻塞性根源）；
- 拜占庭：节点作恶 ⇒ 3f+1（第 4.10 节 PBFT 的门槛）；
- 系统模型 = **网络 + 故障 + 时间** 三元组，读任何算法先看这三个假设；
- 现实系统跑在 **部分同步 + crash-recovery + TCP** 上：牺牲理论上的强假设，换取可实现性。

## 版本演进

- 本书 2022 年第一版。截至 2026-09 未见第 2 版；本章内容的「版本演进」主要表现为
  **建模语言本身没有变，但被建模的对象变了**。
- **2022 → 2026 的三点变化**：
  - **故障检测的现实实现标准化**：Kubernetes 的 liveness/readiness/startup 探针 + Lease 资源，
    把本章的「failure detector」从论文概念变成每天在跑的基础设施；etcd 的租约（lease）
    相当于教科书里「带超时的失效检测」的工程版本。
  - **网络的 IO 模型变了**：QUIC/HTTP3 的多路复用把「队头阻塞」从应用层挪到传输层，
    「链路公平丢失」的假设因此更难成立（一条连接的丢包不再等价于另一条的丢包）。
  - **故障面从「机器」扩展到「策略」**：限流（429）、抢占（spot reclaim）、网格 sidecar 重启
    都表现为 omission failure，而这些在本书的模型分类里没有显式条目（见 🔧 补丁）。
- **不变的部分**：Lamport/FLP/DLS 的结论一个字没变。**模型这一层是分布式的「牛顿定律」**，近四年没有新写法。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「两将军问题 = 拜占庭将军问题」 | 前者是**信道**不可靠且节点诚实；后者是**节点**可能作恶而信道可靠；两者的解门槛完全不同 |
| 2 | 「TCP 解决了两将军问题」 | TCP 只把丢包概率降低，握手双方仍然无法同时确认，TCP FIN/BSD socket close 语义依旧是当今 bug 的来源 |
| 3 | 「多数派 quorum 能容忍任意故障」 | 2f+1 只覆盖 crash 类；拜占庭需要 3f+1，且需要视图更替与认证链路 |
| 4 | 「crash-recovery 和 crash-stop 一样简单」 | recovery 后节点可能带着**过期状态**重新加入投票，因此必须靠持久化日志 + 投票限制（Raft 的 votedFor/日志新度比较） |
| 5 | 「超时能检测出节点故障」 | 超时只是猜测；完美失效检测器只在同步系统存在，现实是 ◊P（最终完美）级检测器 |
| 6 | 「exactly-once 是传输层的属性」 | 传输层只能保证 at-least/at-most；exactly-once 只有在应用层去重或事务性输出后才成立 |
| 7 | 「异步模型是保守假设，所以不重要」 | 恰恰相反：异步下 FLP 成立，工业系统的安全性证明通常要求在异步假设下也成立 |
| 8 | 🔧 本书的模型分类未包含**「策略性失效」**（限流/抢占/降级/配额） | 2026 的现实：一条「429 Too Many Requests」或 spot 实例被回收，其行为是 **omission failure**，但不来自故障。设计 2026 年的系统时需要把这类失效纳入模型，且它们通常**不随 GSR 收敛而消失** |
| 9 | 🔧 本书把失效检测器放在第 4 章，本章没有给出现实形态 | 2026 的现实：**Kubernetes 探针 + Lease + etcd 租约**才是今天大多数工程师唯一接触到的失效检测器实现。它们是不完美检测器（可能误判），因此业务层不能假定「被驱逐 = 已停止工作」，必须配租约/令牌围栏（fencing token） |
| 10 | 🔧 本章未提到**形式化验证与建模**已是共识/事务系统的标准工艺 | 2026 的现实：TLA+、P、Jepsen 已进入了常态化使用；仅「把算法讲清楚」不足以确认实现正确。**写不出来/跑不了 TLA+ 描述的算法，不要轻易声称自己实现了它** |
| 11 | 🔧 本书对**服务网格 / sidecar**引入的新失效面没有涉及 | 2026 的现实：envoy sidecar 重启、配置推送、mTLS 证书轮换都会造成 omission 或部分失效；本书的「节点」概念需要扩展为「节点 + 它脚下的代理」 |
