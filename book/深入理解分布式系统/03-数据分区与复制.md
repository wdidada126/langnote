# 第 3 章（上） 数据分区与复制

> 本章笔记覆盖原书 **第 3 章 3.1 分区、3.2 复制** 两节；CAP、一致性模型与隔离级别在
> [04-CAP定理与一致性模型与隔离级别.md](04-CAP定理与一致性模型与隔离级别.md)。
> **本章地图**：先把数据切成能放得下、能分布的片（分区），再把每一片复制出多个副本来抗故障与提读性能（复制）。
> 一句话主线：**分区决定数据怎么「摊」，复制决定数据怎么「保」，两者共同决定了后面所有一致性讨论的对象形态。**

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 3.1.1 水平分区算法 | 按范围分区、按哈希分区、一致性哈希（含虚拟节点）、固定数目分区 | 分区算法的核心指标只有两个：**分布是否均匀**、**扩缩容时要搬多少数据** |
| 3.1.2 分区的挑战 | 热点（数据歪斜）、二级索引（本地 vs 全局）、跨分区查询/事务、再平衡 | 分区不是「分完就完」：再平衡策略与热点处理才是长期运维成本所在 |
| 3.2.1 单主复制 | 同步/异步/半同步复制；日志传输形式（语句、WAL、逻辑行） | 单主简单且有确定性顺序，代价是**主是单点**（靠共识算法选主，第 4 章） |
| 3.2.2 多主复制 | 多活写、异地就近写；冲突检测与解决 | 多主提高了写可用性与地理延迟，但必须显式处理**写冲突**（因果一致性与合并策略见下一个文件） |
| 3.2.3 无主复制 | Quorum（N/R/W）、读修复、反熵、sloppy quorum + hinted handoff | Dynamo 一系的基石：**用「不要求单一权威」换取可用性**，代价是弱一致性与应用层负担 |

## 核心精讲

### 3.1.1 水平分区的四种算法

| 算法 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 按范围（range） | key 排好序，按范围切分 | 范围查询高效、天然支持前缀 | 热点集中在最新范围（如按时间戳） |
| 按哈希（hash mod N） | 取哈希后整除 | 分布均匀 | **扩缩容时几乎全部数据都要搬迁** |
| 一致性哈希（ring） | 哈希到环上顺时针找后继；加虚拟节点改善均匀 | 扩缩容只搬相邻数据 | 仍有偏斜；需虚拟节点/边界布局 |
| 固定数目分区 + 映射表 | 逻辑分区数远大于节点数，节点负责若干分区 | 搬迁粒度 = 分区；支持热点迁移 | 需要目录/元数据服务维护映射 |

#### 三种主流迭代的执行-搬迁成本

```text
hash mod N        : N=3 → N=4，约 75% 的 key 搬迁
一致性哈希        : 平均约 (K/N) 个 token 搬迁，即 1/N 的数据
固定分区 + 再映射 : 只搬「被迁移的分区」，粒度由人控制，可限速/可灰度
```

#### 一致性哈希的教学示意（含虚拟节点）

```go
// 教学示意，不参与构建
type Ring struct {
    tokens   []uint32          // 有序的虚拟节点 token
    owners   map[uint32]string // token -> nodeID
    vnodeCnt int               // 每个物理节点的虚拟节点数
}

func (r *Ring) Lookup(key string) string {
    h := fnv32(key)
    i := sort.Search(len(r.tokens), func(i int) bool { return r.tokens[i] >= h })
    if i == len(r.tokens) {
        i = 0 // 环回
    }
    return r.owners[r.tokens[i]]
}

func (r *Ring) AddNode(node string) {
    for i := 0; i < r.vnodeCnt; i++ {
        r.tokens = append(r.tokens, fnv32(fmt.Sprintf("%s#%d", node, i)))
        r.owners[r.tokens[len(r.tokens)-1]] = node
    }
    sort.Slice(r.tokens, func(i, j int) bool { return r.tokens[i] < r.tokens[j] })
}
```

要点：

- **虚拟节点**（vnode）解决「随机放置导致负载不均」，常见取 100–300，TiKV/Cassandra 一系也采用类似的 token 布局；
- 即便有虚拟节点，**节点的加入/离开仍然会导致相邻区间的数据搬迁**，需要用 CDC/异步搬迁，并在搬迁期间保证读写正确
  （流程通常为：预分配 → 追增量 → 短暂禁写切主 → 提交路由）；
- 另一种思路是不用环：**跳跃一致性哈希**（Jump Consistent Hash，Google 2014）只需一个 32 位 state 即可算出目标节点，
  无需存储整个环。

### 3.1.2 分区带来的四个长期挑战

1. **热点 / 数据歪斜**：同一个 key 分区内的大 V、明星记录。对策：加盐、加随机后缀拆分 key、或按「热点单独一片」手动拆分。
2. **二级索引**：
   - *本地二级索引*（document-partitioned）：每片各建各的，写快读需搜全部片（scatter-gather）；
   - *全局二级索引*：索引本身也是一张表，也要分区——写要跨片（通常需要分布式事务）。
3. **跨分区查询与事务**：join/聚合需要协调者；原子提交交给第 5 章。
4. **再平衡（rebalancing）**：自动 vs 手动。工业界的共识是**支持自动拆分但半自动迁移**
   （CockroachDB/TiKV 的 Range split 自动，但跨节点搬迁由调度器按负载/容量限速执行）。

### 3.2.1 单主复制（primary / leader-based）

单主复制是今天绝大多数系统的默认形态（MySQL 主从、PostgreSQL 流复制、Kafka 分区 leader、Raft/Zab 副本组）。

| 模式 | 写延迟 | 持久性 | 适用 |
| --- | --- | --- | --- |
| 异步 | 低 | 主崩可能丢数据 | 一般业务的默认档 |
| 半同步（sync to ≥1 follower） | 中 | 至少有 1 份 | MySQL semi-sync、Kafka `acks=1` 近似 |
| 全同步（多数派/全部） | 高 | 强 | 金融类；也等价于「共识驱动的复制」（第 4 章） |

三种日志传输形式，本书提到的套路与业界一致：**语句级（binlog statement）→ WAL 物理 → 逻辑行（row-based / logical decoding）**。
三者的取舍：**物理 WAL 体积小但耦合存储格式**（不能跨版本、不能异构），
**逻辑行便于跨版本兼容和 CDC**，语句级最省空间但依赖「语句确定性」（`NOW()`、`UUID()`、触发器都会踩坑）。

**由复制延迟引出的四种「读保证」**（Terry 等人 1994 年的会话保证）：

1. **读写保证（read-your-writes / read my writes）**：自己写了必须能看到；由「会话粘连到同一副本 + 版本号（或本地缓存）」实现；
2. **单调读（monotonic reads）**：同一客户端不会读到「时光倒流」；通过绑定同一副本实现；
3. **一致性前缀读（consistent prefix reads）**：因果关系不能被打乱；需要按因果序复制；
4. **单调写（monotonic writes）**：同一客户端的写按发出顺序被应用。

### 3.2.2 多主复制（multi-leader）

适用场景：多数据中心就近写、离线客户端（协作文档、手机 App 本地先写）。

核心难点不是「如何把更新发给多个主」，而是**冲突**：

| 冲突处理套路 | 说明 |
| --- | --- |
| 冲突避免（让同一记录只在一个中心写） | 最干净，但通常需要「用户归属 + 迁移期禁写」的业务设计 |
| LWW（last-write-wins，通常按时间戳或时钟） | 实现简单，**会丢写**，且依赖时钟（第 6 章重点批判） |
| 版本向量 / 因果元信息 | 保留并发版本，交给上层合并 |
| 自动合并（CRDT） | 见 [04-CAP定理与一致性模型与隔离级别.md](04-CAP定理与一致性模型与隔离级别.md) 的 2026 补丁 |

### 3.2.3 无主复制（leaderless / Dynamo-style）

| 机制 | 含意 |
| --- | --- |
| N / W / R | 副本总数 / 写需要几个 ACK / 读需要几个应答 |
| 读修复（read repair） | 发现陈旧副本时顺手修复 |
| 反熵（anti-entropy） | 后台定期对比修复（Merkle tree 加速比对） |
| sloppy quorum | 网络分区时先写给"临时接管"的节点，恢复后交回（回交：hinted handoff） |
| 版本向量 | 判定两个写是并发还是有因果先后 |

**Quorum 不等式**（N=3, W=2, R=2 ⇒ W+R>N）：直观上「写成功的集合与读应答的集合一定相交，
因此读到的一定包含最新值」。但这个直觉要挂上很多限定条件才成立——
这是本章最值得记住的一条教训，见下文误区表。

## 版本演进

- 本书 2022 年第一版；截至 2026-09 未见第 2 版。本章涉及的算法本身很老（1997 年的一致性哈希），
  但**工业实现在这四年发生了形态变化**：
  - **分区从「静态哈希」转向「动态 Range + 自动 split/merge」**：TiKV/CockroachDB 一系以 Range 为单位，
    用共识组（Multi-Raft）为单位复制；这是 2015 年后才普及的形态（见第 7 章案例文件）。
  - **元数据管理从「中心/文档」走向「共识组 + 调度器」**：PD（Placement Driver）这类角色把迁移、
    均衡、热点打散变成在线决策，而不是人工脚本。
  - **异步复制生态的全面 Raft 化**：MySQL/PostgreSQL 生态普遍引入 raft-based 的一致性方案与 CDC 链路，
    「选主」从外部脚本变成了共识组内部的正常工作。
  - **2022 年之后**：存算分离（Aurora/PolarDB 一类形态）让「分区」从计算层的概念
    回到了存储层的概念，范围切割与修复组（repair group）的组织方式和本书描述的不完全一致。

## 近年研究与工业界开源实践（2015–2026）

- **研究与工程动向**：
  - **Multi-Raft / Range-based replication**：把一个 key-空间切成成百上千个 Range，每个 Range 一个 Raft 组，
    既是分区单位也是复制单位；调度器做在线迁移与热点打散。这是 2015 年后最重要的形态变化。
  - **确定性模拟 + 故障注入** 成为复制层验证的标配（`apple/foundationdb`、TiKV 的 failpoint）。
  - **存算分离**：Aurora（SIGMOD 2017）、PolarDB、Socrates 等把复制做在存储层（一个专门的日志服务 + quorum），
    计算层就可以「无状态」地扩缩——这是本书出版时已成熟但未被本书展开的形态。
- **工业界开源**（star 数均为 2026-09-26 用 `gh api repos/OWNER/REPO --jq '.stargazers_count'` 实测）：

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「一致性哈希能让负载完全均匀」 | 虚拟节点只是降低方差；key 访问频率不均（热点 key）才是真正的歪斜来源 |
| 2 | 「加了虚拟节点就不用管数据搬迁」 | 节点增减仍会搬迁相邻区间，必须限流、必须在迁移过程中保证读写路由一致 |
| 3 | 「W + R > N 就是强一致读」 | 这是最著名的误解。它只在实现到位时才近似成立：**并发写**（需版本号/冲突解决）、**写入失败后的回滚**（可能读到半成品值）、**sloppy quorum**（退化了 quorum 语义）、**读修复的时机**都会让这个不等式失效 |
| 4 | 「多主复制 = 写可用性的免费升级」 | 多主把冲突推迟到读侧或业务侧，LWW 会静默丢写，是"最贵的"一种胜利 |
| 5 | 「异步复制的主从切换不会丢数据」 | 会。主崩时未同步到从库的写会丢；要「不丢写」就得引入共识（第 4 章），或半同步 + 崩溃后从原主回收未同步的日志 |
| 6 | 「二级索引和主表一样 shard 就好」 | 本地索引要 scatter-gather 查询；全局索引本身需要事务维护，成本远超预期 |
| 7 | 「分区键先选一个，以后能改」 | 分区决定了数据存放位置，改键通常要做全量双写 + 切流级别的迁移，成本远高于早期选型 |
| 8 | 「读修复会保证最终一致」 | 只有被读到的 key 才被修复；长期不访问的陈旧副本依赖反熵（而且可能永远没有被访问，如 tombstones/墓碑结构） |
| 9 | 🔧 本书对 **Range/动态分区 + Multi-Raft** 的时代形态着墨不多 | 2026 的现实：TiKV/CockroachDB 一系已经把「分区」与「共识组」合一（Range = Raft group），再用中心调度器（PD）在线迁移；这是「继承一致哈希之后的事实标准」 |
| 10 | 🔧 本书缺少「客户端责任被 infrastructure 接管」的视角 | 2026 的现实：服务网格/云代理接管了路由、重试与熔断；当客户端不再自己路由，「如何保证 read-your-writes / 不读到陈旧值」的责任随之移到网关层，需要显式设计
  （例如读写会话路由绑定、会话令牌，或由数据库提供会话/快照读 API） |
| 11 | 🔧 本书对「分区 + 复制的数值累积效应」讨论不够 | 2026 的现实：当一个集群有上万 Range、每个 Range 三副本，单点/单机抖动会被 Raft 心跳、gossip/leader 选举与后台反熵放大；本书以算法讲解为主，少见"SRE 视角的数目放大"分析 |
| 12 | 🔧 本书未涉及 **LSM/存储引擎形态对分区迁移的影响** | 2026 的现实：Range 迁移/均衡的成本受底层引擎（LSM compaction、文件级 ingest/fast-path）影响巨大；单纯算法层面的讨论不足以评估迁移代价 |
