# 第 4 章（上） 共识的地基与不可能定理

> 本章笔记覆盖原书 **第 4 章 4.1 分布式共识简介、4.2 异步系统中的共识、4.3 同步系统中的共识**。
> Paxos 家族见 [06-Paxos与Multi-Paxos及其变体.md](06-Paxos与Multi-Paxos及其变体.md)，
> Raft 与拜占庭容错见 [07-Raft与拜占庭容错.md](07-Raft与拜占庭容错.md)。
> **本章地图**：先定义「共识」到底是什么（agreement/validity/termination），解释我们为什么需要它（状态机复制的地基），
> 再证明**在纯异步模型下确定性共识不可解（FLP）**，最后给出三条绕开不可能的路：**故障屏蔽、故障检测器、随机性**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 4.1.1 什么是分布式共识 | 多个节点就一个值达成一致：一致性（agreement）、合法性（validity）、终止性（termination） | 共识 = 就**一个不可撤销的决定**达成一致；这套定义决定了后续所有算法的正确性陈述方式 |
| 4.1.2 为什么要达成共识 | 选主、分布式锁/租约、成员/配置管理、状态机复制（SMR） | 绝大多数分布式系统的「看起来在正常工作」都建立在一次成功的共识之上 |
| 4.2.1 FLP 不可能定理 | 异步 + 一个节点可能崩溃 ⇒ 不存在同时保证安全与终止的**确定性**共识 | 它不是「共识无解」的判决书，而是给这一地图划出了地雷位置 |
| 4.2.2 故障屏蔽 | 用冗余隐藏故障（如三模冗余、多数表决） | 屏蔽能挡住 crash 类故障，但**不能凭它达成一致**（未提供默认缺省值的统一视图） |
| 4.2.3 使用故障检测器 | Chandra-Toueg 检测器分类，◊P（最终完美） | 加入检测器等于是**修改了模型**，绕开 FLP：这是 Paxos/Raft 的实际路线 |
| 4.2.4 使用随机性算法 | Ben-Or 式随机提议，概率 1 终止 | 另一条绕路：牺牲「确定性终止」，换取「几乎必定终止」 |
| 4.3 同步系统中的共识 | 有已知延迟上界 Δ，可以靠超时判断死亡 | 同步下共识可解，但需要 **f + 1** 轮的轮数下界；这也是「为什么容错容忍 f 个故障需要至少 f+1 轮试图/ n≥2f+1」的来源 |

## 核心精讲

### 4.1.1 共识的三个性质

一个「共识（consensus）」问题的最简定义：n 个进程各提出一个值 v_i，最终要决定（decide）同一个值 v，满足：

| 性质 | 表述 |
| --- | --- |
| 一致性（Agreement / Safety） | 任意两个正确进程决定的值相同（不会有两个不同的值被决定） |
| 合法性（Validity / Non-triviality） | 被决定的值必须是某个进程提出的值（不能凭空诞生） |
| 终止性（Termination / Liveness） | 若系统最终稳定（或所有正确进程都参与），每个正确进程最终都能决定 |

**完整性（Integrity）**还有一种更严格的写法：「每个进程最多决定一次」（防止同一进程先后决定不同值），加上 Agreement 就等价于上面的安全表述。

### 4.1.2 为什么要有共识？

| 场景 | 共识在其中扮演的角色 |
| --- | --- |
| 选主（leader election） | 就「谁是 leader」达成一致；实际上是一次关于成员 id 的共识实例 |
| 分布式锁/租约 | 「这把锁归谁」达成一致；etcd/ZooKeeper 的实现依赖共识组 |
| 成员/配置变更 | 「新一代成员名单是什么」——必须走**一致性变更**（Raft 的 joint consensus，见下一个文件） |
| 状态机复制（SMR） | 就「日志的第 i 项是什么」逐项达成共识，于是相同输入序列 ⇒ 相同状态 |
| 原子提交 | 「这批 txn 是提交还是中止」——见 [08-分布式事务.md](08-分布式事务.md) 的 Paxos Commit |

**状态机复制（State Machine Replication）**是本章最值得记住的应用模式：

```text
相同的初始状态 + 相同的输入序列（每条日志都由共识决定） = 相同的最终状态
```

Schneider 的教程（ACM Computing Surveys 1990）是这一模式的标准出处。

### 4.2.1 FLP：到底「不可能」什么

> Fischer, Lynch, Paterson（JACM 1985）：**在异步系统模型中，即使只有一个进程可能 crash-stop，
> 也不存在既保证 Agreement/Validity 又保证 Termination 的确定性共识算法。**

三条限定词缺一不可：

1. **异步**：不存在任何延迟上界，因此无法区分「慢」与「死」；
2. **确定性**：算法的所有转移不能抛骰子；
3. **同时保证安全与终止**：可以只保证安全而不保证终止（很多系统确实是这样做的，等网络恢复再恢复活性）。

证明骨架（valency argument，值得记一轮直觉）：

- 定义「二价（bivalent）配置」：从它出发，最终被决定的值**仍有可能**是 0，也有可能是 1；
- 证明存在一个初始的二价配置（否则算法是平凡的）；
- 证明任何二价配置总存在一个「既不 0 定也不 1 定」的**后续二价配置**（关键的一步：那个「决定性」的步骤可以被延迟到容忍选定的 step 之后）；
- 于是可构造一条永不定案的无限执行 ⇒ 违背终止性。

```go
// 教学示意，不参与构建
// FLP 的「诱导无限执行」直觉：一个 step 若能让配置从二价走向确定，
// 就先延迟它，转而先执行别的、仍保持二价的 step。
func scheduleBivalentForever(cfg Config, steps []Step) {
    for {
        var next Step
        for _, s := range enabledSteps(cfg) {
            if isBivalent(apply(cfg, s)) {
                next = s
                break // 永远存在一个能保持「二价」的 step
            }
        }
        cfg = apply(cfg, next) // 配置永远停留在「二价」，算法无法终止
    }
}
```

**工程含义**：不要试图「消灭」FLP，要在**模型上做交换**：

- 引入**超时**（把模型升级到部分同步，并承担「猜错」的风险由 safety 设计来兜底）；
- 引入**随机化**（打散同时并发提议导致的活锁）；
- 引入**故障检测器**以绕开纯粹的「不可判定」（见 4.2.3）。

### 4.2.2 故障屏蔽（Masking Redundancy）

用「多套加起来盖住一套的故障」的思路（三模冗余、多数表决、纠删码）来提高可靠性。
但单纯的屏蔽**不能让你达成一致**：三路输出 0/1/⊥ 时，你仍然需要一个「谁是多数」的一致性判定规则，
而这个规则面对恶意/不一致输入时又回到了共识问题。

### 4.2.3 故障检测器：修改模型，而不是攻破 FLP

Chandra & Toueg（JACM 1996）给出了检测器的强度分类，最常用的是：

| 类别 | 含义 | 能做什么 |
| --- | --- | --- |
| P（perfect） | 不误判，最终能发现所有崩溃 | 同步系统常见 |
| ◊P（eventually perfect） | 允许一段时间误判，最终不再误判且能发现崩溃 | **这正是 Paxos/Raft 的实际假设** |

有了 ◊P，就绕开了 FLP 的前提（模型不再是「纯异步」）。现实的实现形式是：
心跳 / lease / Kubernetes 探针 + 随机化退避。

### 4.2.4 随机化：放弃「确定性」换取概率 1 终止

Ben-Or（PODC 1983）的路线：每轮随机选择提议值，让「大家想法一致」的概率以 1 收敛。
随机化在今天的工业实现里最常见的变体其实是：** leader 选举的随机化退避**（避免同时发起选举活锁），
以及加密货币里的工作量证明（PoW = 随机化 + 经济代价）。

### 4.3 同步模型下：可解，但代价是轮数

在同步模型中（存在已知上界 Δ），可以用超时准确判断进程已崩溃，于是共识可解：

- 每轮中「死掉」的至少补发一个，因此 **f + 1 轮**足以保证留下至少一个正确进程收集到全部信息；
- 崩溃失败下需要 **n ≥ 2f+1**（多数派）才能保证单一保管者的决定不会和旧 leader 冲突；
- 拜占庭下需要 **n ≥ 3f+1**（第 2 章结论），且需要 **f + 1 轮**。

代价提示：同步算法的延迟上界是「f+1 轮 RTT」，这在 f 很大时不实用，所以工业系统用 leader 大幅摊薄了每轮成本
（由 leader 提出，follower 只在 leader 故障时才让另一个 leader 接任 ⇒ 稳态下没有不必要的「轮」）。

## 版本演进

- 本书 2022 年第一版。本章是全书「最耐时间」的一章：FLP、Chandra-Toueg、Ben-Or、DLS 都是 1980–90 年代的结果，
  2026 年一个字都无需修改。
- **真正发生变化的是工程侧的动词**：
  - 「**超时**」从配置项变成了**一次次都要重算的自适应值**（Raft 的 randomized election timeout + CheckQuorum + PreVote，
    三者组合才真正缓解了 FLP 在实践中的表现）；
  - 「**部分同步**」从论文术语变成了**集群调优项**：今天的工程师调的是 `heartbeat-interval` 与
    `election-timeout` 的比例，而这正是 FLP 所说的「假设是否成立」的实际值；
  - 2015 年之后，**Multi-Raft** 让共识从「一个组」变成「成千上万个组」，引入的新工程问题
    （成员均匀、lease 连贯性、跨组事务）与 FLP 本身无关，但决定了可用性的实际分布；
  - Kubernetes 把「领导者选举」做成日常 API（Lease-based leader election），使得很多应用
    不需要自己实现共识，只需要「用共识」。
- **本书未涉及的会在下一个文件补**：Raft 的工程细节与 etcd/HashiCorp 实现差异，见 07 号文件的 🔧 补丁。

## 近年研究与工业界开源实践（2015–2026）

- **理论层**：近四年没有改写式成果；有价值的发展集中在**可从模型推出的复杂度下界**（如 N Out of N vs Flexible Quorum）、
  以及** leaderless / wide-area 变体**（EPaxos、designing leaderless protocols）的工程评测。
- **工程层**：2022 → 2026 的主流变化是把共识「做进」三个地方：① 元数据与控制面（etcd、ZooKeeper 的替代/升级）、
  ② 存储层的一批一批 Range（Multi-Raft）、③ 消息队列的元数据面（Kafka 的 KRaft 替代 ZooKeeper）。
- **随机化的现实形态**：从论文里的「随机提议」变成了**退避 + PreVote + Lease** 三件套；
  这是理论活力与实践可靠性交接得最好的地方。
- **工业界开源**（star 数均为 2026-09-26 用 `gh api repos/OWNER/REPO --jq '.stargazers_count'` 实测）：

| 项目 | star | 与本章的对应 |

| `etcd-io/raft` | 1128 | Raft 参考实现，可直接看到 CheckQuorum/PreVote/租约的处理 |

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「FLP 说明分布式共识做不了」 | FLP 只对**异步 + 确定性 + 同时要求安全与终止**成立；引入部分同步/随机化/故障检测器即可解，今天的系统就是这么做的 |
| 2 | 「安全性可以在性能不好时牺牲」 | 恰恰相反：工程上**安全必须在任何情况下成立**（哪怕整个集群看起来「停机」），能被放弃的只有活性 |
| 3 | 「Paxos 不终止，所以它违反完备性」 | Paxos 保证安全但在请求不断冲突时可能活锁；这与 FLP 的方向一致，不是它的缺陷 |
| 4 | 「故障检测器能告诉我们节点已死」 | 它只能「怀疑」；绝大多数现实检测器是 ◊P（最终完美），误判必须由上层设计兜住（租约/围栏令牌） |
| 5 | 「leader 选举不需要共识」 | 「谁是 leader」必须被一致承认，否则出现双主；现代实现用 lease + 自增任期号（term / ballot）防止旧主复活导致的双主 |
| 6 | 「状态机复制 = 共识」 | SMR 是**应用模式**：它靠逐项共识实现一个全序日志；算法负责「一项怎么定」，SMR 负责「怎么用它」 |
| 7 | 「同步模型没用，反正真实网络是异步的」 | 同步/部分同步是**用来书写正确性承诺的坐标系**：没有模型，就无法陈述「系统在什么条件下可用」 |
| 8 | 🔧 本书未把「随机化」与现代选举实践连起来 | 2026 的现实：**随机化退避 + PreVote + CheckQuorum + lease** 四件套才是 FLP 在生产里的答案；只看「随机提议」的论文版容易误解为什么今天的 Raft 实现都要加 PreVote |
| 9 | 🔧 本书对「共识组的规模」缺少工程讨论 | 2026 的现实：共识组从「一个集群一个组」变成「成千上万个组」（Multi-Raft）；此时真正的难点变成成员均匀、lease 连贯、热点与跨组事务，而这些不在 FLP 的叙事里 |
| 10 | 🔧 本书没有提及「应用不必自己写共识」的现状 | 2026 的现实：Kubernetes 的 Lease leader election、云厂商的托管协调服务让绝大多数应用只需要**调用**共识；把本章读成「必须自己实现」是不必要的负担 |
