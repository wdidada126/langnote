# 第 1 章 认识分布式系统

> **本章地图**：给出分布式系统的定义 → 回答「为什么非要分布式」→ 用搜索引擎与加密货币两个完整示例把抽象概念落地
> → 列出三大挑战（网络延迟 / 部分失效 / 时钟）→ 用一组数量级数字建立工程直觉。
> 本章没有算法，但它决定了后面六章的**问题意识**：分布式的一切复杂度，都来自「多个自主部件 + 不可靠的通信」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 什么是分布式系统 | 一组通过网络通信、为完成共同任务而协作的自治节点 | 分布式系统的本质是**多个自治部件 + 消息传递**，没有共享内存、没有全局时钟 |
| 1.2 为什么需要分布式系统 | 性能（超越单机上限）、可用性（容错）、地理就近、可扩展性 | 分布式的动机不是「炫技」，而是**单机在数据/流量/可用性三个维度上都不够用了** |
| 1.3.1 示例：搜索引擎 | 抓取 → 建索引 → 检索（倒排索引、PageRank 类排序） | 一个搜索引擎天然就是分布式流水线：顺序可以异步、可以重试，但对外的「结果完整性」难以证明 |
| 1.3.2 示例：加密货币 | 比特币式账本：交易广播 + 挖矿 + 最长链 | 加密货币是**开放网络上的拜占庭容错 + 随机性共识**的现实样本（详见第 4 章） |
| 1.4.1 挑战：网络延迟 | 延迟不可预测、尾部延迟被放大（fan-out） | 「慢」和「挂」在观测上无法区分，一切设计必须默认超时不可信 |
| 1.4.2 挑战：部分失效 | 一部分组件失效而另一部分正常工作 | 这是分布式**最难**的问题：返回值只有三种——成功、明确失败、**无响应** |
| 1.4.3 挑战：时钟问题 | 墙上时钟会跳变、单调时钟不可跨机比较 | 不要用时间戳给事件定序（第 6 章给替代方案：逻辑时钟 / 向量时钟） |
| 1.5 每个程序员都应该知道的数字 | 各级存储的延迟数量级 | 数量级比具体数字重要；延迟差 6 个数量级决定了架构形态 |
| 1.6 本章小结 | 归纳 | 后续章节都是对本章三个挑战的逐个应答 |

## 核心精讲

### 1.1 什么才算「分布式」

本书在这里沿用的是教科书口径：一组**自治的**计算节点，通过网络通信协作，对外表现为一个系统。
van Steen & Tanenbaum 的表述是「分布式系统是若干独立计算机的集合，对这个系统的用户来说，
它就像**一台**计算机在工作」——注意「像一台」是目标，**透明性**（transparency）才是真正的难点。

Leslie Lamport 那句被广泛引用的吐槽，最能说明分布式系统的心理落差：

> A distributed system is one in which the failure of a computer you didn't even know existed
> can render your own computer unusable.

这句话里的关键词是 **didn't even know existed**：在分布式里，你连自己依赖了谁都不完全清楚。

**三个不可回避的事实**（后续所有算法的出发点）：

1. **没有共享内存**：节点间只能发消息，而且消息可能丢、可能重复、可能乱序、可能延迟任意久；
2. **没有全局时钟**：读到的时间戳不能直接比较先后顺序；
3. **存在部分失效**：调用方只能观察到「超时」，无法判断对端是挂了、慢了还是根本没收到请求。

### 1.2 为什么非要分布式

| 动机 | 单机为何不够 | 分布式带来的新成本 |
| --- | --- | --- |
| 数据规模 | 单机磁盘/内存有上限，而数据持续膨胀 | 分区、再平衡、跨片查询 |
| 性能/吞吐 | 摩尔定律放缓，单机 CPU 主频不再快速增长 | 副本、异步、批处理、放大延迟之和 |
| 可用性 | 单机断电即全站不可用 | 故障检测、主备切换、脑裂处理 |
| 地理分布 | 光速有限，跨洲访问延迟 100ms 量级 | 多区域复制、跨区域一致性取舍 |
| 隔离/合规 | 数据必须留在本区域 | 多活、单元化架构 |

一句话：**分布式不是把单机问题变小，而是把「确定性问题」变成「概率性问题」再靠系统设计把概率压低。**

### 1.4 三大挑战（本章的重心）

#### 1.4.1 网络延迟：不可预测，且会被扇出放大

一次用户请求可能扇出到 N 个后端（`fan-out`）。即使单个后端 p99 只有 100ms，
当 N = 100 时，「所有分片都很快」的概率远低于直觉——这就是 **尾部延迟放大（tail latency amplification）**。
Dean & Barroso 在 *The Tail at Scale*（CACM 2013）里给的对策至今仍是标准答案：
`hedged request`（对冲请求）、`tied request`（请求绑定取消）、自适应超时、把慢节点降级。

#### 1.4.2 部分失效：三种返回值，第三世界才可怕

```go
// 教学示意，不参与构建
func Call(ctx context.Context, req Request) (Result, error) {
    select {
    case res := <-doRPC(req):
        return res.Val, nil      // ① 成功：请求一定被执行了吗？不一定（响应丢失也可能重试）
    case err := <-rpcError():
        return Result{}, err     // ② 明确失败：语义清晰，可安全重试（对幂等接口）
    case <-ctx.Done():
        return Result{}, ErrTimeout // ③ 无响应：请求「可能」已经执行、「可能」从未到达
    }
}
```

上面这段代码想说明的是：**第三种返回值无法收敛**。因此：

- 写接口必须**幂等**（用幂等键去重），否则重试会破坏正确性；
- 必须区分 **at-most-once / at-least-once / exactly-once**（本书 2.4 节展开）；
- 「exactly-once」在真实系统里通常是「at-least-once + 应用侧幂等」的组合，而不是网络层免费提供的东西
  （Flink 的 end-to-end exactly-once 也是这个思路，见第 12 章）。

#### 1.4.3 时钟：三种时钟各有各的坑

| 时钟 | 含义 | 坑 |
| --- | --- | --- |
| 墙上时钟（time-of-day） | 日历时间 | 会被 NTP 校时**回拨**，两次读数之差可能为负；不能用 `time.Now()` 算耗时 |
| 单调时钟（monotonic） | 本机递增计时 | 只能在本机比较，跨机器无意义 |
| 进程时钟（process CPU time） | CPU 消耗时间 | 忽略 I/O 等待，不能用于分布式推理 |

第 6 章会用逻辑时钟与向量时钟彻底解决「在没有可信全局时钟时如何给事件定序」。

### 1.5 一组必须记住的数量级

下表是 Jeff Dean 于 2010 年前后给出的经典延迟数量级（他以 Google 内部演讲/幻灯片的形式传播），
后来被 Colin Scott 整理成常被引用的交互式页面「Latency Numbers Every Programmer Should Know」。

| 操作 | 经典参考值 | 注 |
| --- | --- | --- |
| L1 cache 引用 | ~1 ns | — |
| 分支预测失败 | ~5 ns | — |
| L2 cache 引用 | ~4 ns | — |
| 互斥锁加锁/解锁 | ~25 ns | — |
| 主存引用 | ~100 ns | 比 L1 慢 100 倍 |
| 用 Zippy 压缩 1 KB | ~10 μs | — |
| 通过 1 Gbps 网络发 1 KB | ~10 μs | 现在是 10/25/100 Gbps，量级下降但数量级关系不变 |
| 从内存顺序读 1 MB | ~250 μs | — |
| SSD 随机读 4 KB | ~150 μs（2010 代 SSD） | 2026 年的 NVMe 已低至数十 μs，**具体数字已过时** |
| 磁盘寻道（HDD） | ~10 ms | 机械结构决定，20 年未变 |
| 同机房 RTT | ~0.5 ms | — |
| 跨区域 RTT（如 北京↔美西） | ~100–200 ms | 光速下限决定 |

> ⚠️ 不要把上表的绝对数值当 2026 年的事实：它是 **2010 年前后** 的量级表。
> 真正有价值的是**数量级关系**（缓存:内存:SSD:网络:磁盘 ≈ 1:10²:10⁵:10⁵:10⁷ 纳秒级跨度），
> 以及由此推出的架构结论：能用顺序 I/O 就别随机 I/O，能同机房就别跨区域，能批处理就别逐条请求。

### 1.6 本章小结

本章给了整本书的坐标系：

- **什么是分布式**：自治节点 + 消息传递，目标是透明性；
- **为什么分布**：数据、吞吐、可用性、地理、合规五个维度单机不够；
- **难在哪里**：网络延迟分布的长尾、部分失效的不可观测、时钟的不可信；
- **后面六章怎么应答**：第 2 章建模 → 第 3 章数据 → 第 4 章共识 → 第 5 章事务 → 第 6 章时间 → 第 7 章看别人怎么做。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「分布式一定能提高性能」 | 分布式首先引入开销；只在单机成为瓶颈、或需要可用性与地理分布时才划算 |
| 2 | 「超时 = 对方没执行」 | 超时只代表「不知道」；请求可能已执行、正在执行或从未到达，必须靠幂等键兜底 |
| 3 | 「重试次数越多越可靠」 | 无退避、无抖动的密集重试会造成**重试风暴**，把小故障放大成雪崩 |
| 4 | 「网络一定比磁盘快」 | 2010 年代成立；但跨 region RTT 仍远高于本地 SSD；要看的单位永远是**当前拓扑下的实际量级** |
| 5 | 「墙上时钟可以用来排序事件」 | NTP 校时会导致回拨；同机用单调时钟计时，分布式定序要用逻辑时钟/向量时钟 |
| 6 | 「exactly-once 是消息队列提供的能力」 | 消息层的「恰好一次」只在自己边界内成立；端到端 exactly-once = at-least-once + 幂等/事务性输出 |
| 7 | 「数字应该背下来」 | 记住数量级；具体值每 5 年翻新一次，本章表格的绝对值已经过时 |
| 8 | 🔧 本书写于 2022，本书没有覆盖**服务网格**这个重要形态 | 2026 的现实：超时/重试/幂等/熔断原本是**客户端库**的职责，现在越来越多由 `Envoy` + `Istio`/网格层统一接管。这意味着本书 1.4.2「重试要幂等」的建议，在现代部署里可能由基础设施层执行，**应用层仍然必须提供幂等语义**，否则网格帮不了你 |
| 9 | 🔧 本书的延迟表未考虑 **Serverless/抢占式实例**带来的新型失效 | 2026 的现实：节点的消失方式从「宕机」变成「被调度/被抢占/冷启动/被限流」，这三种都表现为部分失效；本书讲的忍跳对本类失效依然适用，但需要把续租、租约与「被限流（429）」纳入同一套失效模型 |
| 10 | 🔧 本书对**可观测性**着墨很少 | 2026 的现实：OpenTelemetry trace/metric/log 三位一体已是默认要求；「部分失效」今天不再是黑盒——但前提是请求带了 trace context，这是本书未提及的现代硬要求 |
