# 第 6 章 时间和事件顺序

> **本章地图**：为什么物理时钟不能用于定序 → 怎么同步时钟（仍然不够）→ 用**逻辑时钟**定义 happens-before
> → 用**向量时钟**真正识别并发 → 在没有全局时钟的前提下，如何给系统拍一张**一致快照**。
> 一句话主线：**分布式系统里没有「现在」，只有「先后」；本章就是在教我们如何在没有全局时钟时推理「先后」。**

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 6.1 物理时钟 | TAI / UTC / 闰秒、墙上时钟与单调时钟 | 物理时钟有跳变与漂移，**读一次的时钟不能当作事实的排序依据** |
| 6.2 时钟同步 | Cristian 算法、NTP/Berkeley 算法、NTP 精度分层、故障时间源（falseticker） | 同步只能把误差收敛到「毫秒～微秒」，永远到不了零；而且读到的值仍可能被回拨 |
| 6.3 逻辑时钟 | Lamport happens-before、Lamport 时间戳规则 | 逻辑时钟给出「一个人hew 的序」，代价是它不能识别并发 |
| 6.4 向量时钟 | 每个进程维护一个向量；比较规则判定「并发/先后」 | 真正的因果追踪工具；代价是随节点数线性增长 |
| 6.5 分布式快照 | Chandy-Lamport 算法：marker + 通道状态记录 | 快照不是「某一瞬间的真实全球状态」，而是一个 **consistent cut** |
| 6.6 本章小结 | 归纳 | 所有"定序"手段都是在租约/时间戳/因果关系之间做交换 |

## 核心精讲

### 6.1 物理时钟：两种时间和三个陷阱

| 概念 | 说明 |
| --- | --- |
| TAI（国际原子时） | 以原子振荡定义，均匀连续 |
| UTC（协调世界时） | 基于 TAI，用**闰秒**修正以贴近地球自转（UT1） |
| 墙上时钟（time-of-day） | 日历时间，**可回拨**（NTP 校时、管理员改表、闰秒） |
| 单调时钟（monotonic） | 本机单调，适合测量耗时，**跨机不可比较** |

三个陷阱：

1. **跳变**：NTP 发现本机快了 5 秒可能直接跳回 ⇒ 同一个时钟两次读数之差可能为负；
2. **漂移（skew / drift）**：晶振受温度与老化影响，常见漂移约 **10⁻⁶ ~ 10⁻⁵**（每天几十毫秒到几秒不等）；
3. **精度 vs 真实值**：即使读数稳定，也没有人告诉你「真实时间」——时钟给出的是**一个区间**（这正是 TrueTime 的设计哲学）。

> 闰秒相关：国际计量大会 2022 年的决议要求到 2035 年前放宽 UTC 与 UT1 的允许偏差上限，
> 业界因此在先行部署「闰秒平滑（leap smear）」等做法。
> 对本目录结论的影响：闰秒不会消失，但处理方式正在变化；工程上仍要对「一分钟 61 秒 / 59 秒」具备容错。

### 6.2 时钟同步：能做到多好，以及为什么还不够

| 机制 | 思路 | 特点 |
| --- | --- | --- |
| Cristian 算法 | 客户端向时间服务器 RTT 校正，取中间值 | 假设上行/下行延迟对称 |
| Berkeley 算法 | 时间守护轮询客户端并做内部平均，**没有 UTC** | 适合内部一致即可的场景 |
| NTP | 分层（stratum）时间服务器 + 时钟选择算法 + 调整曲线 | 广域网通常毫秒级；同数据中心可达亚毫秒～百微秒级 |
| GPS / 原子钟接收机 | 直连卫星时间 | 每个机房都要布设；Spanner 即此路线 |
| 混合逻辑时钟 HLC | 物理时钟提供直观的原始值，逻辑部分保证因果 | CockroachDB/Yugabyte 一系采用 |

**NTP 的坑**（本书提到的编程陷阱大多落在这些点上）：

- 时间源可能失效（falseticker）；NTP 的选择算法会试图排除它们，但结果可能差很大；
- `time-of-day` 会被**回拨**，因此不能用「两次读数相减」计算时间间隔；
- 单调时钟只能本机用；
- 代码里的"超时/租约"如果依赖跨机时钟，就假设了一个不存在的东西。

### 6.3 逻辑时钟：Happens-before 与一条规则

**Happens-before（→）的定义**（Lamport, CACM 1978）：

1. 同一进程内 a 在 b 之前 ⇒ a → b；
2. 若 a 是「发送消息」、b 是「接收同一条消息」 ⇒ a → b；
3. 传递闭合：a → b 且 b → c ⇒ a → c。

两个事件如果互相都不能到达，则它们是**并发（concurrent）**：

```text
a → b  ⇒  C(a) < C(b)       （逻辑时钟保证这条）
C(a) = C(b) ⇏ a 与 b 并发    （反过来不成立！）
```

**Lamport 时钟的三条规则**（教学示意）：

```go
// 教学示意，不参与构建
type LamportClock struct {
    counter int
}

// 本地事件发生
func (c *LamportClock) Local() int {
    c.counter++
    return c.counter
}

// 发送消息：带上自己的时间戳
func (c *LamportClock) Send() int {
    return c.Local()
}

// 接收消息：合并对方的时钟
func (c *LamportClock) Receive(remoteTs int) int {
    if remoteTs > c.counter {
        c.counter = remoteTs
    }
    c.counter++
    return c.counter
}
```

规则总结：**每次事件发生 `++`；发送消息带上 c；接收消息时 `c = max(c, remote) + 1`。**
用 `(c, pid)` 元组可以构造一个全序，但它与因果关系脱钩——这也是为什么需要向量时钟。

### 6.4 向量时钟：真正能判定并发

每个节点维护长度 n 的向量 V：

```go
// 教学示意，不参与构建
type VectorClock struct {
    v   []int
    idx int
}

func (vc *VectorClock) Local() []int {
    vc.v[vc.idx]++
    return clone(vc.v)
}

// 接收时逐分量取 max，再把自己的分量 +1
func (vc *VectorClock) Receive(remote []int) []int {
    for i := range vc.v {
        if remote[i] > vc.v[i] {
            vc.v[i] = remote[i]
        }
    }
    vc.v[vc.idx]++
    return clone(vc.v)
}

// 判定：Va < Vb（Va happened-before Vb）⇔ Va 各分量 ≤ Vb 且至少一处严格小于
func HappensBefore(a, b []int) bool {
    le, lt := true, false
    for i := range a {
        if a[i] > b[i] {
            return false
        }
        if a[i] < b[i] {
            lt = true
        } else {
            le = le && true
        }
    }
    return le && lt
}
```

三条重要结论：

1. `Va ≤ Vb` 且不可比 ⇒ a、b 是**并发**（这是 Lamport 时钟做不到的）；
2. 向量长度随参与者数量线性增长 ⇒ 大规模开放系统中不适用（因此有了版本向量、近似因果编码等变体）；
3. **版本向量**（version vector）是向量时钟在「每个副本」而非「每个进程」粒度上的同构版本，
   是 Dynamo/Cassandra/Riak 判定写冲突的实际工具。

### 6.5 分布式快照：Chandy-Lamport

要解决的问题：**「给系统拍一张照片」，但没有全局时钟、也没有一个时刻可以喊「现在」。**

算法要点：

1. 任意一个进程可以发起快照：先记下自己的状态，然后向所有出边通道发送 **marker**；
2. 进程第一次收到 marker（从某条入边通道 c）时：记录自己的状态 + 记录该通道状态为「空」，向所有出边发 marker；
3. 此后从通道 c' 收到的普通消息：记录到「通道 c' 的状态」里（这就是「在途消息」）；
4. 当所有通道的 marker 都被收齐，快照完成。

```text
关键性质：快照是一致切割（consistent cut）——
若快照包含事件 b，则所有 happened-before b 的事件也都被包含。
它不必是「真实发生过的某个瞬间」，但它是「一个逻辑上成立的状态」。
```

**为什么这有用**：

- 检测稳定属性（stable property，如「死锁」「终止」）时，一致快照足够推出结论；
- Flink 的**异步屏障快照（asynchronous barrier snapshotting）**就是把 Chandy-Lamport 中的 marker
  换成常驻数据流里的 **barrier**，从而实现「不停机也能 checkpoint」（详见第 12 章案例文件）。

## 版本演进

- 本书 2022 年第一版。本章理论全部出自 1978–1985 年，2026 年依然成立。
- **2022 → 2026 的变化**：
  - **HLC（混合逻辑时钟）成为工程默认**：CockroachDB/Yugabyte/HBase 一系用它作为读写时间戳，
    兼具物理时钟的直观性与因果性。本书讲了物理时钟与逻辑时钟，但没讲这个「融合降级方案」。
  - **云厂商的时钟服务**：主流云都提供带发行商持 GPS/原子钟的时间服务与闰秒 smear，
    「本机 NTP 直连公网上游」逐渐不再是最佳实践。
  - **闰秒的处理方式在变化**：如前所述，放宽 UTC-UT1 上限的讨论使「2035 年后怎么办」成了实时话题，
    工程上 continue 支持 smear 与容忍 61 秒/59 秒分钟的代码。
  - **TrueTime 一族扩散**：除 Spanner 外，多个商业化 NewSQL 也宣称使用 GPS/原子钟 + 收窄不确定性窗口。
- **不变的部分**：happens-before 与 Chandy-Lamport 的定义一个字没改。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「同步好 NTP 就能用时间戳排序」 | NTP 只能把误差收敛，不能消除；跨节点比较时间戳需要「误差bound + commit-wait」（TrueTime 正是这么做的） |
| 2 | 「用墙上时钟算耗时没问题」 | 会被回拨；测耗时请用单调时钟，跨机比较请用逻辑时钟/HLC |
| 3 | 「Lamport 时钟相同 ⇒ 事件并发」 | 不成立。Lamport 时钟只保证「a→b 则 C(a)<C(b)」；判定并发必须用向量时钟 |
| 4 | 「向量时钟可以无限扩展」 | 随参与者数量线性增长；在大规模系统中要改用版本向量、近似结构或 TSO/HLC |
| 5 | 「分布式快照是某一瞬间的真实状态」 | 它是一个 **consistent cut**：逻辑一致，但不必对应真实的某个时刻 |
| 6 | 「快照算法需要暂停业务」 | Chandy-Lamport 不需要停机；现代流处理是在数据流里嵌 barrier 实现在线 checkpoint |
| 7 | 「tombstone 可以随便删」 | 删除墓碑需要节点 recover 时钟对齐；时钟或副本长时间离线会导致「删除的数据复活」 |
| 8 | 「 TrueTime 让时间变准了」 | TrueTime 不让时间变准，它把「不确定区间」显式化，让算法可以等区间过去再提交 |
| 9 | 🔧 本书未涉及 **HLC（混合逻辑时钟）** | 2026 的现实：HLC 已经是多款分布式数据库的默认时间戳方案；它比纯逻辑时钟直观，比纯物理时钟安全。读本章时应把 6.3 的结尾接上 HLC |
| 10 | 🔧 本书的时间源讨论停留在「自建 NTP」 | 2026 的现实：主流云提供托管时间服务（含 GPS/原子钟与闰秒 smear）；工程上更重要的是**监控偏移并在超阈值时主动隔离节点**，而不是单纯「把 NTP 配好」 |
| 11 | 🔧 本书未讨论闰秒的处理策略变化 | 2026 的现实：UTC 与 UT1 偏差上限的放宽已提上日程，闰秒 smear 与「61 秒分钟」的兼容性成为系统的常设要求 |
| 12 | 🔧 本书的快照一节没有接上流处理这条线 | 2026 的现实：Chandy-Lamport 今天最广泛的实际使用地是**流处理框架的容错机制**（Flink 检查点）。补上 barrier 版本，学生才明白「这个 1985 年的算法为什么今天还在被每天使用」 |
