## 核心精讲

### 7.1 GFS：把「元数据与数据」分开

```text
                 ┌─────────┐ 控制流（chunk 位置 / lease / 心跳）
                 │  Master │
                 └────┬────┘
        ┌─────────────┼─────────────┐
   ┌────▼───┐    ┌────▼───┐    ┌────▼───┐
   │ChunkSrv│    │ChunkSrv│    │ChunkSrv│   数据流：client → nearest → next → ...（流水线）
   └────────┘    └────────┘    └────────┘
```

三条设计关键点：

1. **单 master + 元数据全在内存**：master 保存 namespace、文件到 chunk 的映射、chunk 副本位置。
   内存 + 操作日志 + 检查点让 master 重启极快；也因此单机的内存限制了元数据规模。
2. **64 MB 的大 chunk**：减少元数据条目、减少与 master 的交互；代价是小文件会浪费空间与产生热点。
3. **控制流与数据流解耦**：client 只从 master 拿 leases 与位置（可缓存），数据则直接推送给 chunkserver，
   并在 chunkserver 之间按「就近优先」链式转发。

#### record append（7.1.4 的重头戏）

- **普通写**（指定 offset）：多个 client 并发写同一区域会产生**互相覆盖/交错**的数据（不保证原子）；
- **record append**：client 只 semantically append，由 primary（持有 lease 的副本）决定 offset，
  并保证数据在多副本上「至少一次」被写入。异常情况（部分副本失败）客户端需要重试，
  因此同一条记录**可能在不同副本不同位置出现多次**，甚至副本间出现 padding。

由此引出的「定义状态 vs 已定义」差别非常重要：

| 状态 | 含义 |
| --- | --- |
| defined（已定义） | 客户端读到的数据与自己写入的内容完全一致（含并发 intact 的 append） |
| consistent but undefined | 各副本最终数据一致，但中间可能有由并发 append 产生的交错/重复片段 |
| inconsistent（不一致） | 写入失败且没有重试成功，副本之间不同 |

**application 侧的责任**（GFS 论文的真正教训）：应用层要用 **checksum + 记录里有唯一 id + apex 重复**来自己处理碎片。

### 7.2 ZooKeeper：用「主序广播」实现元数据的线性一致

- **Zab 与 Paxos/Raft 的关系**：三者都是「返回一个全序 + 只在主 failures 时重选」的主序协议。
  Zab 特别强调 **主序（primary order）**：一个 leader 在任期内的所有提案按严格顺序提交，
  而崩溃恢复阶段要保证「已经被上位者 ALLOWED 的提案不能被丢」。
- **写路径**：所有写请求转发到 leader → 分配 zxid（64 位 = 高 32 位 epoch + 低 32 位 counter） → Proposal → 多数派 ACK → Commit；
- **读路径**：follower 可以直接读本地 ⇒ 快速但可能陈旧；需要强一致时用 **`sync` + 读**，
  这也是本书「协调服务的 responsibility 在客户端」这一节想强调的。
- **会话与临时节点**：客户端与某个 server 保持心跳会话；会话过期会让该会话创建的 ephemeral node 消失，
  因此「临时节点 = 存活证明」。

```go
// 教学示意，不参与构建
// 一个最小的分布式锁（教科书版）：临时顺序节点 + 监听前驱
func acquireLock(zk ZKClient, lockPath string) (release func(), err error) {
    node := zk.CreateEphemeralSequential(lockPath+"/lock-", nil)
    for {
        children := zk.GetChildren(lockPath)
        sort.Strings(children)
        idx := indexOf(children, base(node))
        if idx == 0 {
            return func() { zk.Delete(node) }, nil // 序号最小 ⇒ 拿到锁
        }
        prev := children[idx-1]
        exists := zk.ExistsWithWatch(lockPath + "/" + prev) // 一次性 watch
        ev := <-exists.Events
        switch ev.Type {
        case Deleted:
            continue // 前驱释放了，重新检查
        case SessionExpired:
            return nil, ErrSessionLost // 会话过期：必须假设锁已被他人拿走
        }
    }
}
```

这段代码有三个「千万别写错」的地方：① watch 是**一次性**的，触发后必须重注册；
② `create` 之后必须**重新一次 getChildren** 再判断（因为创建和列举之间可能有其他人插队）；
③ 会话过期后本地状态全部失效，**不能假设锁还在自己手里**。

## 版本演进

- 本书 2022 年第一版。这两个案例比本书早 20 年，但**它们在 2022 → 2026 的地位发生了明显变化**：
  - **GFS 早已被内部后继系统取代**（Google 公开称其后继为 Colossus），HDFS 是今天我们还能直接接触到的最接近形态；
  - **ZooKeeper 的使用面在缩窄**：Kafka 用 KRaft 移除 ZooKeeper、新一代组件直接嵌入 etcd/raft；
    本书 7.2 讲的「协调服务是独立部署的一组进程」在 2026 年不再是唯一形态；
  - **etcd 成为云原生控制面的事实标准**：Kubernetes 的所有对象都写在 etcd 里，
    这把「协调服务」从「业务用的小组件」变成了「整个基础设施的根」。
- **新增的 2026 视角**：**Kubernetes Operator = 现实世界最大的分布式控制循环**（详见 🔧 补丁）。
  展开一点说，它的形态是：

| 组成 | 对应本章的概念 |
| --- | --- |
| 声明式的期望状态（spec） | 「想要的状态」写在 etcd 里，而不是靠命令推动 |
| `reconcile()` 循环 | **幂等的收敛过程**：每次被调用都把现状推向期望状态，可以失败重跑 |
| `resourceVersion` / watch | 用**单调递增编号而非时钟**来判断「这条数据是不是新的」（见第 6 章） |
| 乐观并发 + 冲突重试 | 多个控制器写同一对象时用版本号做 CAS，冲突就重算一遍 |
| leader election（Lease） | Operator 多副本时用租约选主，正是第 4 章 consensus 的「使用者视角」 |

- **为什么值得与 ZooKeeper 一块读**：两者都在解决「多个参与者围绕一份元数据收敛」，
  差别在于 ZooKeeper 把原语暴露给用户（锁/选举/watch），而 Kubernetes 把这些原语**封装成了 reconcile 框架**。

## 近年研究与工业界开源实践（2015–2026）

- **研究**：文件系统方向的重心已转向「高性能存储 + 一致性」而不是单一 master 元数据：
  对象存储、共享 nothing 的元数据分割、以及内核外（SPDK/io_uring）IO 栈；
  协调服务方向的重心是「把协调服务变成嵌入式共享库」（Multi-Raft 组 → 不必单独部署 ensemble）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「GFS/HDFS 支持并发随机写」 | 不支持；它面向追加写与流式读，GFS 时代甚至没有通用的 POSIX 随机写语义 |
| 2 | 「record append 恰好一次」 | 是**原子的至少一次**：副本可能有重复、padding、不同位置；去重是应用层的责任 |
| 3 | 「master 在数据路径上，是带宽瓶颈」 | 不在。client 与 chunkserver 直接传数据；master 只给位置与 lease |
| 4 | 「64 MB chunk 永远更好」 | 大 chunk 让小文件的元数据放大、热点难以打散；「多大合适」取决于负载 |
| 5 | 「ZooKeeper 读就是线性一致」 | 默认 follower 读可能陈旧；需要强一致时必须 `sync` 后读，或走 leader |
| 6 | 「watch 是持续订阅」 | 一次性 Watch：触发即失效，必须重新注册，事件可能在这之间丢失 |
| 7 | 「临时节点在客户端进程挂掉后立刻消失」 | 消失的触发条件是**会话过期**（超时），不是进程关闭；短暂 GC 停顿可能造成「假失效」 |
| 8 | 「协调服务可以当数据库用」 | znode 有 1 MB 级限制、适合元数据；把业务数据放进去会拖垮 ensemble |
| 9 | 🔧 本书 7.2 把「协调服务 = 独立部署的 ensemble」当作默认形态 | 2026 的现实：新一代系统倾向于**把一组 Raft 组嵌进自己的进程**（etcd-io/raft、hashicorp/raft），或用 KRaft 去掉外部协调服务。读本节时应把「独立 ZooKeeper 集群」视为 2010 年代的主流形态 |
| 10 | 🔧 本书未提 **Kubernetes Operator** 这一现实形态 | 2026 的现实：Operator = 「把运维语义写成 reconcile 控制循环」，它依赖 etcd 提供的 watch + Raft 线性一致写 + revision 号。这几乎是本书 7.2 概念在今天的**最大面积落地**：读本节时把它当成「协调服务的客户端范例」 |
| 11 | 🔧 本书未提 **etcd 相对 ZooKeeper 的差异** | 2026 的现实：两者语义不同（租约 TTL vs 临时会话、mvcc revision vs zxid、持续 watch vs 一次性 watch）。本书以 ZooKeeper 为主角，读者需要自己补上 etcd 一侧的对照 |
| 12 | 🔧 本书 7.1 未讨论「业务使用 GFS 形态系统时的责任清单」 | 2026 的现实：用 GFS/HDFS 形态系统时，应用层必须处理 checksum、记录去重、幂等写入与副本修复；论文把这些留给了应用，本书清单口子太轻 |
