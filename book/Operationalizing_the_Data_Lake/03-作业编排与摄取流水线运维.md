# 03 · 作业编排与摄取流水线运维

> 🔻 降级册主题重建章（⚠️ 非原书目录）。本章是"运营化"的心脏：管线的日常生命周期工程。
> 三态：✅=文档实链预检 200；⚠️=平台不可实测；🔧=SQLite/DuckDB 类比，**非本书平台行为**。

## 3.1 编排的运营语义：从 DAG 到"账本"

调度器视角的编排是"依赖图+定时器"；运营视角的编排是**一本可审计的产出账本**：
每个 `(job, partition)` 单元有唯一状态（pending/running/retry/dead）、产出计数与生效时刻。
账本思维带来三个直接推论：

1. 回填是一等公民操作（账本允许旧单元改状态，但必须留痕）；
2. "跳过"（skip）与"空跑"（produce 0 rows）是两种不同记账，混用会污染新鲜度；
3. 重试不是策略而是**经济学**：指数退避把重试成本显式化，超过预算即降级为人工事件。

平台文档面：Airflow（任务/数据集/SLA 语义）✅ https://airflow.apache.org/docs/ ；
托管摄取作业面参考 Glue ✅ https://docs.aws.amazon.com/glue/latest/dg/welcome.html 。

## 3.2 摄取流水线的四种节拍

| 节拍 | 典型形态 | 运营要点 | 失败签名 |
|---|---|---|---|
| 微批 | 5–15min 增量 | 水位线管理（§3.4 组3） | 迟到洪水、小文件 |
| 批 | T+1 全量/增量 | 窗口与 SLO 对齐 | 窗口塌陷（上游晚到） |
| CDC | 变更日志摄取 | 序一致性、schema 变更风暴 | 结构漂移炸表 |
| 手工回填 | 事故重放 | 幂等+限流+审批三件套 | 二次事故 |

⚠️ 具体平台上四种节拍的实现组件差异极大（托管服务/自建调度），本册只统一记账口径。

## 3.3 状态机：把"卡住的作业"变成可枚举集合

合法状态迁移是运营化的低级乐趣，但不可枚举的状态是高级事故源：
`pending→running→{success|retry}`，`retry→{running|dead}`，`dead→人工`，别无他路。
凡出现 `zombie`（无心跳无终态）即告警——状态枚举+心跳两件套，成本极低，收益极大。

## 3.4 🔧 本机类比（5 组，全部**非本书平台行为**）

**🔧组1 拓扑分层=调度序**。SQLite 递归 CTE 对依赖表
（bronze→silver→{gold_a,gold_b}→report）求最大深度分层，实测：
`bronze:0, silver:1, gold_a:2, gold_b:2, report:3`。→ 一个 SQL 就能校验"是否存在环/孤儿节点"，
这是任何调度器 UI 背后的最小内核。

**🔧组2 退避经济学**。纯函数序列 `min(5·2^i, 300)`：`[5,10,20,40,80,160,300,300]`，
8 次重试总等待 915s≈15 分钟。→ "重试预算"可以精确到秒：超过预算的失败**必须**惊动人，
否则 SLO 是假的（对照 [01 章](01-从建设到运营·数据湖运营化的问题域.md) §1.4 错误预算）。

**🔧组3 水位线与迟到**。表 `wm(silver='2026-10-01 12:00')`，对三条事件
（09-30 05:00 / 10-01 18:00 / 10-02 01:00）按 `event_time<=watermark` 判收，
实测放行 2、拒收 1。→ 迟到策略的全部复杂度就在"水位线由谁推进、可否人工回拨"一句——
回拨=一次受审批的回填（§3.2 第四行）。

**🔧组4 并发写互斥**。两会话同库：会话1 `BEGIN EXCLUSIVE` 持锁改账，会话2 busy_timeout=200ms
内 `BEGIN IMMEDIATE` 实测 `locked`。→ 湖的多写者冲突在表格式层以乐观并发协议解决（⚠️ 平台差异大），
但"冲突要能被观测到"的运营要求在单机模型上完全同构。

**🔧组5 非法状态拒收**。`run_state.status` 加 CHECK 枚举
（pending/running/retry/dead），插 `zombie` 实测被拒（IntegrityError）。
→ §3.3 的状态机不靠自觉靠约束；台账查询 `[('ingest_s3','retry'),('ingest_kafka','running')]`
即值班交接班单的形状。

## 3.5 回填手册（运营化成熟度的试金石）

一次合格回填 = 组1 的序 + 组3 的水位线回拨 + 组2 的重试预算 + [01 章](01-从建设到运营·数据湖运营化的问题域.md) 组1 的幂等写入 + 全程留痕。
缺任何一件，回填就是"用新事故覆盖旧事故"。经验规则：回填窗口>3 天必须限流，
因为摄取洪峰会把 [04 章](04-数据质量·新鲜度与湖上可观测性.md) 的新鲜度曲线全线打穿。

## 3.6 反模式清单

- **调度器当目录**：依赖关系只存在于 cron 表达式注释里（解法在 05 章）；
- **成功=退出码 0**：不看产出行数/字节（0 行也是"成功"）；
- **人人可改 DAG**：无评审的节拍变更是破线首因（对照 §1.4 预算联动，01 章）；
- **重试配置复制粘贴**：不同摄取节拍的退避预算应不同（组2 的 915s 只是示范常数）；
- **告警直连个人**：破线通知绕过值班表直达作者邮箱，等于没有运营只有牺牲品；
- **回填不登记**：账本外的补算让新鲜度统计系统性说谎（比破线更恶性）。

六条反模式的共同结构是：**省掉一次记账，换取未来一次不可归因的事故**。
运营化改造的次序，就是按事故频率给这张清单排序。

## 3.7 值班一分钟速查（本章概念的班表化）

| 看到什么 | 第一动作 | 依据小节 |
|---|---|---|
| gold 层 3 个分区未就绪 | 查 silver 是否在 retry（勿先重启 report） | §3.1 账本 / §3.3 状态机 |
| 作业"成功"但行数=0 | 判空跑，查水位线是否未推进 | §3.4 组3 / 04 章三信号 |
| retry 单元滞留 >915s 预算 | 转 dead，人工接管，冻结相关 DAG 变更 | §3.4 组2 / 01 章 §1.4 |
| 上游宣布补发历史数据 | 走回填手册四件套，先限流后开窗 | §3.5 |
| 会话间锁等待告警 | 核对写并发是否绕过了表格式收口 | §3.4 组4 / 02 章 §2.4 |

这张表的运营学含义：每一条都**只查表不查人**——交接班质量取决于可查表的完备度，
而不是口口相传的部落知识。

## 核心概念速览（中英对照）

| 中文 | 英文 | 一句话 |
|---|---|---|
| 产出账本 | materialization ledger | (job,partition) 单元的权威状态记录 |

| 僵尸作业 | zombie job | 无心跳无终态的违例状态 |

## 最新演进与工业实践

- 编排层 2021→2026 的公开演进主线：数据资产（dataset）成为调度一等对象——
  Airflow 的"数据感知调度"特性线（✅ §3.1 链接的当期文档）标志"以数据就绪触发"取代"以时钟触发"的普及。
- 数据工程界对"pipeline as product"的采纳使 CI/CD 语义（评审、回滚、金丝雀）进入 DAG 变更流程，
  §3.6 第三条反模式在成熟团队已是红线级制度（通识表述 ⚠️）。
- 流式摄取（CDC/Paimon 类）把 §3.2 的"微批/流"边界模糊化，但 §3.4 组3 的水位线语义
  反而更核心：流的运营化=迟到与乱序的账本化（盘上链 3.7 可读其深）。
- 托管编排 SaaS（DAG 即代码+托管执行）在 2024–2026 增多 ⚠️；运营判据不变：
  **能否导出全部 run 历史**——不能导出账本的编排面不可运营。
