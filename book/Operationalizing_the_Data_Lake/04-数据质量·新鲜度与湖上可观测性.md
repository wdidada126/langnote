# 04 · 数据质量、新鲜度与湖上可观测性

> 🔻 降级册主题重建章（⚠️ 非原书目录）。本章把 [01 章](01-从建设到运营·数据湖运营化的问题域.md) 的三条曲线
> 中的两条（质量/新鲜度）做成可运行的制度，并补第三支柱：湖上可观测性。
> 三态：✅=文档实链预检 200；⚠️=平台不可实测；🔧=SQLite/DuckDB 类比，**非本书平台行为**。

## 4.1 质量制度的最小闭环：规则→闸门→台账→修正→复检

```
 上游变更 ──▶ [规则库] ──▶ [写侧闸门] ──pass──▶ silver
                 │              │reject
                 │              ▼
                 │          [隔离台账 dq_reject]──▶ 工单/告警
                 │              │
                 └──[修正+审计]──┴──▶ 复检通过才回补（回补走 03 章回填手册）
```

要点：规则必须**即代码**（存在表里可执行，不是 wiki 里），隔离必须**有台账**（拒绝是数据
不是异常栈），修正必须**留审计**（湖上改一行=一次小型事故）。
文档面：规则即代码的代表实现 Great Expectations ✅ https://docs.greatexpectations.io/docs/ 。

## 4.2 新鲜度的三种口径与一个共同敌人

| 口径 | 定义 | 适用 |
|---|---|---|
| 就绪新鲜度 | 分区承诺时刻 vs 生效时刻 | 批/T+1 管线 |
| 事件新鲜度 | 事件时刻 vs 可见时刻（lag） | 流/微批 |
| 陈旧度 staleness | 距最后一次实质变更的时间 | 维表/静态资产 |

共同敌人是**"看起来正常"的空跑**：作业成功、行数 0、水位线未推进——三信号
（成功/量/时）缺一即假象。度量式统一为：`now - max(materialized_at) where rows>0`。
⚠️ Dataplex 的 freshness 规范与 Glue DataBrew 的质量规则集是平台化样本（前者本机不可达，
后者归在 Glue ✅ 文档树 https://docs.aws.amazon.com/glue/latest/dg/welcome.html 下）。

## 4.3 湖上可观测性三支柱（对位应用可观测性）

1. **管线指标**：run 时长分位数、重试率、退避预算耗尽次数（03 章账本的聚合视图）；
2. **数据指标**：行数/字节数/空值率/重复率的时序带（volume & distribution 漂移检测）；
3. **平台指标**：文件数、平均文件尺寸、元数据快照龄、孤儿文件占比（02 章四手术的仪表盘）。

三支柱的告警预算共享 [01 章](01-从建设到运营·数据湖运营化的问题域.md) §1.4 的 SLO 框架；
工业界的"数据可观测性"品类即三支柱的产品化 ⚠️（演进性表述，不点名厂商）。

## 4.4 🔧 本机类比（5 组，全部**非本书平台行为**）

**🔧组1 规则即代码**。SQLite 表 `dq_rule(rule_id, tbl, sql_chk)` 存三条规则
（amount>0 / order_id NOT NULL / currency∈{CNY,USD}），对 4 行脏样本逐条执行
`WHERE NOT (chk)`：实测每条规则各逮到 1 行违规（如 `rule1 [amount>0] 违规行=1`）。
→ 规则库驱动的画像循环，正是 GX 类框架的 5 行内核。

**🔧组2 新鲜度巡检 SQL**。复用 [01 章](01-从建设到运营·数据湖运营化的问题域.md) 组3 数据，
julianday 差值实测：gold_kpi 滞后 53.0h 超 SLA 24h → BREACH；silver_orders 11.8/12 临界。
→ 临界带（>80% SLA）就该出告警——破线才响的监控器只是验尸官。

**🔧组3 数据画像**。DuckDB 对 2000 行样本实测：`n=2000, nulls=0, min(k)=0, max(k)=999,
stddev(v)=0.2907, 重复键组=0`。→ 画像四件套（量/空/域/重）全部一条 SQL 可得；
漂移检测=把这条 SQL 变成时序表再比对。

**🔧组4 修正审计**。`UPDATE fact_orders SET amount=11` 后同事务写
`audit(t1, order1.amount, 10, 11)`，实测台账 `[('t1','order1.amount','10','11')]`。
→ "改数必留痕"在单机是一个触发器的距离；湖上没有事务包裹时，这个习惯更值钱。

**🔧组5 孤儿文件检出**。清单表 manifest 登记 parts/f0–f2，实际目录有 f0–f3，
差集实测孤儿=`['parts/f3.parquet']`。→ 对位 02 章第三手术：孤儿清点的本质是
**清单 vs 有效快照指针表的差集运算**——dry-run 输出即此差集，先核对再删除。

## 4.5 质量经济学：闸门阈值怎么定

- 拒收率>1% 常态 → 是上游契约问题，修管线不修阈值（03 章 CDC schema 风暴对位）；
- 修正回补时长>回填预算 → 宁可发布"标记陈旧"分区也不阻塞下游（新鲜度与质量的汇率）；
- 规则数量与告警疲劳正相关 → 规则分诊：BLOCK 级（进台账拦写）与 WARN 级（只进画像）。
经验通则 ⚠️：闸门的价值不在严格，在**可预期**——下游按台账大小规划兜底逻辑。

## 4.6 三信号巡检表参考实现（可直接抄行的最小件）

把 §4.2 的"成功/量/时"三信号落为一张每表每分区的巡检行（列即 SQL 结果列）：

| 列 | 信号 | 判读 | 异常示例 |
|---|---|---|---|
| run_ok | 成功 | 账本终态=success？ | retry 滞留 |
| rows_delta | 量 | 行数环比带内？（±k·σ） | 成功但 0 行 |
| bytes_delta | 量 | 字节与行数同向？ | 行平字节暴涨=列污染 |
| lag_h / sla_h | 时 | 比值 >0.8 即临界告警 | 11.8/12（§4.4 组2 实录） |
| dq_reject_n | 质 | 隔离增量突增=上游变脸 | 单规则命中跳档 |
| files / avg_size | 平台 | 小文件趋势（02 章三支柱之3） | avg_size 周环比 -30% |
| snapshot_age | 平台 | 过期手术是否失守 | 只增不减 |

巡检 SQL 全部是本机组1/2/3/5 的列组合，平台无关；**先有这张表，再谈可观测性选型**。

## 最新演进与工业实践

- 2021 年"质量工具"叙事在 2023–2026 分化为两支：CI 内测试框架（GX 类，✅ 链接文档树持续演进）
  与平台内建约束（表格式/目录侧挂规则，如 Unity Catalog 线 ✅ 见 05 章链接）——
  本册 §4.1 闭环对两支同样成立。
- 数据可观测性品类自 2022 年前后爆发后并入主流平台特性 ⚠️（演进性表述），
  三支柱中"平台指标"（§4.3-3）最常被产品化遗漏，恰是湖运营事故大户。
- 新鲜度承诺进入合同语境（DaaS/内部服务目录的 SLA 条款）→ staleness 可作赔付依据，
  §4.2 的度量式因此要求第三方可复核（台账+时钟源留痕）。
- 核对纪律同 02 章：⚠️ 句在决策前一律以当期 ✅ 文档重验。
