# 第 4 章 处理器（一）：数据通路与控制

> **一句话**：处理器就是一个**「按时钟节拍把数据从一个寄存器搬到另一个寄存器」的状态机**——先画出数据通路，再把它每一步该做什么压缩成一组**控制信号**，单周期实现只是这份状态机的第一版。

## 核心精讲

> 以下均为**教学示意，不参与构建、不编译、不运行**。

### 五个步骤：一切流水线的骨架

```text
IF  取指   instruction fetch        ：从存储器取指令，PC ← PC + 4
ID  译码   instruction decode       ：读寄存器堆（rs1、rs2），译出操作与立即数
EX  执行   execute                  ：ALU 计算（或计算地址）
MEM 访存   memory access            ：lw/sw 才碰数据 cache，其余段空转
WB  写回   write back               ：结果写回目的寄存器
```

> 单周期实现的本质：**把这五步在一个时钟周期内全部走完**。CPI = 1 是它的优点，但每个时钟周期必须等最慢的那条指令（load 或 long-latency ALU 运算），所以时钟频率被压得很低；
> 多周期/流水线正是为了「让每个时钟只做一段」而出现——代价是**流水寄存器与控制信号复杂度**。

### 数据通路与控制信号

```asm
# 教学示意，不参与构建、不编译不运行
# 三种最典型的指令，看它们分别用到哪些阶段与控制信号：
lw   t0, 8(a0)      # 需要全部五段，且 MEM 段真读内存        -> 最慢
sw   t0, 8(a0)      # 五段，MEM 段真写内存                  -> 需要 Write/Read memory 信号
addi t1, t0, 4      # IF/ID/EX/WB（MEM 段空转写给 0）       -> 只有 EX 段干活
beq  t0, t1, L      # IF/ID/EX（WB 空转），分支结果在 EX 末尾出现
```

```c
/* 教学示意，不参与构建、不编译不运行 */
/* 单周期 CPU 的控制信号可以看成一张「指令操作码 × 状态」的真值表 */
typedef struct {
    int reg_dst;    /* 写回寄存器选择：rt 还是 rd */
    int alu_src;    /* ALU 第二 operand 来自寄存器还是立即数 */
    int mem_to_reg; /* 写回值来自内存还是 ALU */
    int mem_read;   /* 读内存 */
    int mem_write;  /* 写内存 */
    int branch;     /* 分支 */
    int alu_op;     /* 决定 ALU 做什么 */
} ctrl_signals;

/* 关键设计：为了让五段都对齐，其他指令在 MEM/WB 段的控制信号全部置 0（即「空转」） */
static const ctrl_signals CTRL_RTYPE  = {1, 0, 0, 0, 0, 0, 2};  /* add/sub/and/or */
static const ctrl_signals CTRL_LW     = {1, 0, 1, 1, 0, 0, 0};  /* load word      */
static const ctrl_signals CTRL_SW     = {0, 1, 0, 0, 1, 0, 0};  /* store word     */
static const ctrl_signals CTRL_BEQ    = {0, 0, 0, 0, 0, 1, 1};  /* branch equal   */
```

> 控制信号的设计原则（本书反复强调）：**「每条指令都走完全相同的路径，用 0 表示不干活」**。
> 这让数据通路只有一份，代价是那些用不到的段必须被「填 0」——这也是流水线冒险的来源之一。

### 寄存器堆与「读两个、写一个」的冲突

```verilog
/* 教学示意，不参与构建、不编译、不运行 */
/* 32×32 寄存器堆：单写口 + 双读口 */
module regfile (
    input  wire        clk,
    input  wire [4:0]  waddr,   /* 写地址 */
    input  wire [31:0] wdata,   /* 写数据 */
    input  wire        we,      /* 写使能 */
    input  wire [4:0]  raddr1, raddr2,   /* 读地址 */
    output wire [31:0] rdata1, rdata2
);
    reg [31:0] regs [0:31];
    always @(posedge clk) if (we) regs[waddr] <= wdata;
    assign rdata1 = regs[raddr1];   /* 读口是组合的 */
    assign rdata2 = regs[raddr2];
endmodule
```

> 注意「同一周期既读又写同一寄存器」的情形：`x0` 恒为 0、以及 `lw` 的目的寄存器恰好是下一条指令的源寄存器——
> 若寄存器堆不做「写口与读口同时命中就直连」的旁路，就需要停顿一个周期；这正是 4.7 数据冒险的物理根源。

### 异常：让「正常路径」与「例外路径」分叉

```text
异常（exception）：CPU 内部事件触发（非法指令、除零、算术溢出）
中断（interrupt） ：CPU 外部事件触发（I/O 完成、定时器）
两者的共同处理流程：
  ① 把 PC 与状态压栈（或写入特定寄存器）
  ② 关中断、设置特权级
  ③ 跳到异常处理程序（向量表）
  ④ 恢复现场后返回
在单周期实现里，异常只需要「把多路选择器的目标从下一条指令改成异常向量」；
在流水线里，异常处理就变成「抹掉已写入结果、回退 PC」——这是 05 章最难的部分。
```

### 单周期 vs 多周期 vs 流水线

| 实现 | CPI | 时钟周期长度 | 面积/功耗 | 适合 |
| --- | --- | --- | --- | --- |
| 单周期 | 1 | **最长**（等于最慢指令的时延） | 小 | 教学；真实核不用 |
| 多周期 | 3–5（平均） | 中等 | 小 + 需状态机控制 | 教学、低功耗微控制器 |
| 五段流水线 | ≈1 | ≈ 最大段时延 + 流水寄存器开销 | 大（寄存器与转发逻辑指数上升） | 几乎所有现代通用核 |

> 一句话记忆：**单周期用「慢时钟」换简单；流水线用「复杂控制」换快时钟**。

## 版本演进

| 阶段 | 与本章相关的关键变化 |
| --- | --- |
| **1970s** | 微处理器普遍用微码（microcode）实现复杂指令；CISC 时代 |
| **1980 RISC 宣言之后** | 单周期/多周期的教学模型定型；RISC-I 的指令在单周期内完成 |
| **1985–1990** | Intel i960、MIPS R2000 把流水线搬进商品芯片；**CPI 概念让位给 IPC** |
| **1993 Pentium** | 双流水线（U/V）超标量；1995 Pentium Pro 转向乱序执行 |
| **1996 Alpha 21264** | 猜测执行 + 大窗口，微体系结构复杂度登顶 |
| **2011 ARM Cortex-A8 / 2015 Core i7（本书 4.11 Real stuff）** | 处理器被描述成「几条固定流水线 + 组合逻辑 + 缓存」；本书用它们当 Real stuff 实例 |
| **2019/2020 本书 RISC-V 版** | 数据通路例子全部换成 RV32I；附录 D「控制通路的硬件实现」用 Verilog 描述流水线控制，体现教学重心向 **RISC-V + 硬件描述语言**迁移 |
| **2020s** | 开源核（Rocket/BOOM/CVA6）让本书的数据通路图可以被**直接综合与实测**；CHIPS 框架把「生成器」引入教学 |
| **对照 x86 的微码化** | x86 的外部 ISA 仍是 CISC，但内部早在 Pentium Pro 就被拆成微操作（micro-op），用 RISC 式流水线执行——**CISC 只在 microcode 里活着**，这是 03/08 章都会回来讨论的一点 |

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **只讲单周期 + 五段流水线** | 真实核是多发射、乱序、猜测执行；把 4.4 的「CPI=1」当成真实处理器的性能模型会严重误导（真实 IPC 在 1.5–5 之间靠多发射） |
| 🔧 **流水线深度停留在 5 段** | 2020 年代的高级 ARM/x86 核有效流水深度是十几个到几十段（含译码/重命名/重排序缓冲），将「五段」直接套到其时钟周期上会算错 |
| **把流水寄存器当成免费** | 每加一级流水就多一次寄存；本书 4.6 提到「控制开销」但未量化流水寄存器的面积/功耗成本 |
| **转发（forwarding）只在 04 章讲了一半** | 4.7 的转发规则表在 05 章才补齐；只看 04 章会以为 load 只需要一个 stall |
| 🔧 **异常只讲「跳向量表」** | 5 章之后才说明流水线里的异常要「冲刷流水线并回退」；本书对精确异常（precise exception）的代价几乎不提 |
| 🔧 **附录 D 的微码讨论偏旧** | 附录 D 讨论微程序控制；现代实现用硬布线有限状态机，微码只在 x86 这类 CISC 兼容层里还有残骸 |
| **忽略乘法/浮点对 EX 段时延的支配** | 单周期实现里一次 `fadd` 可能比整条整数指令链还慢；本书 3.3/3.5 讲完之后，4.4 的「最长路径」结论才能被真正理解 |
| 🔧 **未覆盖 2017 年后的能效视角** | 本章没有讨论「流水到多深才划算」的功耗约束，也没有提 CHIPS Alliance 项目之后「按面积预算做微结构」的做法 |
