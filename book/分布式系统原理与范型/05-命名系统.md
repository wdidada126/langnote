## 本章地图

- 命名回答「**给一个名字，如何找到实体**」。按名字结构分三类：
  - **平坦命名**：不透明的唯一 ID（GUID、内容哈希），定位靠广播/指针/DHT；
  - **结构化命名**：人类可读、层级组织（DNS、路径名），解析靠树与闭包；
  - **属性命名**：按「描述」找实体（LDAP、属性匹配）。
- 本章是「位置透明」的实现章：迁移、复制、负载均衡都要先改写名字解析过程。

## 核心精讲（教学示意，不参与构建）

### 5.1 名称、标识符和地址
- **名称（name）**：可读、可变绑定；**标识符（identifier）**：唯一、终身不变、不可复用；
  **地址（address）**：指向当前位置（访问点）的名称。
- 关键张力：**把地址当标识符是万恶之源**——实体迁移/换网卡后地址失效；
  正确结构是「标识符 → 解析系统 → 当前地址」。
- 原书建议：标识符最好**位置无关且自验证**（如内容哈希/公钥哈希），DHT 与内容寻址存储都吃这个红利。

### 5.2 平坦命名
- **简单方案**：
  - 广播/多播解析（ARP 即此类）：简单，规模与跨网受限；
  - **转发指针（forwarding pointers）**：迁移时旧位置留指针，链式跟随；痛点：链长延迟、断链（需要回home修补）、失效重连。
- **基于归属的（home-based）方案**：每个实体有固定 home 代理记录当前位置（Mobile IP、Skype 登录、
  微信路由都是此结构）；痛点：home 固定形成单点与**地理次优路径**（亚洲用户绕美国 home）。
- **DHT（分布式哈希表）**：把 key 空间哈希到 P2P 节点环上，路由 O(log N)：
  - Chord：一致哈希环 + 后继表（finger table），查找沿环折半；
  - 数据复制 = 同一 key 复制到环上 s 个后继（succeeding replicas）；
  - 优点：完全去中心、负载均衡；缺点：一次查找跳数多、维护 churn 下的拓扑代价。
- **分层定位服务**：定位树（根/域/叶），查找自底向上；把「稳定层」与「易变层」分离，兼顾延迟与可扩展性——
  DNS/Globe 定位服务的共同结构。

### 5.3 结构化命名
- **命名空间**：有向图（根节点、叶节点、中间节点）；**闭包机制（closure）**：确定「从哪个名字开始解析」
  （如 URL 的 scheme 决定解析器）。
- **挂载（mounting）**：把一个命名空间的子图挂到另一空间（NFS 挂载点、容器 volume 同理）；
  跨空间挂载形成联合命名空间。
- **解析实现**：
  - 递归解析（服务器代劳，缓存友好）vs 迭代解析（客户端自跑，服务器压力小）；
  - 缓存与 TTL：就近缓存答案，用时效换扩展性。
- **DNS（域名系统）**：分层命名空间（root → TLD → 域）、资源记录（A/NS/CNAME/SOA/MX/PTR）、
  区域（zone）与权威服务器、递归/迭代查询结合、缓存 TTL——**分布式的命名=分区的树+缓存**，
  是本书最成功的实际系统案例。
- 🔧 2026 视角：DNS 之外又长出了**服务发现**层（Consul/etcd/K8s Service DNS），把「解析结果」从静态 IP
  换成动态端点列表；也长出了 DoH/DoT（DNS over HTTPS/TLS）回应隐私与劫持。

### 5.4 基于属性的命名
- 目标：按属性组合检索实体（「找一台在杭州、内存 32G、空闲的机器」）。
- **目录服务（directory service）**：LDAP——分层条目（dn/rdn）+ 属性集 + 过滤器；同步复制的目录树。
- 集中式目录易成瓶颈；分布式属性查找用 DHT+倒排索引，但复杂查询（连词）性能难保证——
  这是属性命名至今不如结构化命名普及的原因。

### 三类命名的「解析 vs 放置」总对照（补充）

| | 平坦命名 | 结构化命名 | 属性命名 |
| --- | --- | --- | --- |
| 名字形态 | 不透明 ID | 层级路径 | 属性谓词 |
| 解析方式 | 定位服务/DHT | 树解析 + 缓存 | 匹配/索引 |
| 扩展手段 | 一致哈希、分层域 | 区域委派、缓存 TTL | 倒排、分区 |
| 典型失效模式 | 热点键、churn | 缓存投毒、委派失效 | 查询组合爆炸 |
| 2026 代表 | 内容哈希、服务 ID | DNS、文件路径 | 资源标签、LDAP/云 IAM |

### 一次 DNS 查询的完整旅程（教学示意，对应原书 5.3 的解析叙述）

1. 应用问 stub resolver → 本地缓存（OS/浏览器）；
2. 未命中 → 问递归解析器（运营商或 8.8.8.8/1.1.1.1）；
3. 递归解析器自根 → TLD → 权威服务器**迭代**查询（每级缓存 TTL）；
4. 权威返回 A/CNAME 记录 → 逐级缓存回客户端；
5. 客户端拿到 IP 建连——若 CDN，则同一域名对不同地域返回**不同答案**（GeoDNS，命名的负载均衡化身）。
- 观察点：这条链把「递归 vs 迭代」「缓存与 TTL」「分层委派」三个概念全部具象化，
  也解释了为什么 DNS 变更生效慢（TTL 逐级缓存）与 DNS 劫持为什么危险（任何一级都可被污染）。
- **一次 DHT（Chord）查找的旅程**（与 DNS 旅程对照记忆）：
  1. 节点把 key 哈希到环上（SHA-1 空间）；
  2. 查本地 finger table 找到**不超过**目标的最远节点；
  3. 逐跳转发，每跳距离至少减半 → O(log N) 跳到达目标的后继；
  4. 后继节点持有数据（及 s 个后继副本）；
  5. 节点加入/退出只影响相邻区间（一致哈希的平滑性）， stabilize 协议修复指针。
- 对照结论：DNS 用**人类可读的树**换管理权清晰；Chord 用**不透明的环**换完全去中心——
  两者是「结构化命名 vs 平坦命名」的工程化身。
- **转发指针 vs home vs DHT 三方案速判**（选型口诀）：
  | 方案 | 迁移频繁 | 查找频繁 | 跨管理域 | 适用 |
  | --- | --- | --- | --- | --- |
  | 转发指针 | 代价低 | 链长变慢 | 可用 | 短期/局部迁移 |
  | home | 代价中 | 三角路由 | 天然支持 | 移动设备（Mobile IP） |
  | DHT | 代价高（重哈希） | O(log N) 稳定 | 去中心 | 内容寻址、海量对象 |

### 一页速记

- ID（唯一终身）/ 名称（可读可变）/ 地址（当前位置）三分；「地址当 ID」是根源性设计错误。
- 平坦命名四方案：广播（最简单）、转发指针（链）、home（三角路由）、DHT（O(log N)）。
- 结构化命名的三板斧：闭包（从哪开始解析）、挂载（联合命名空间）、缓存 TTL（一致性换扩展）。
- DNS 是全书最成功的分布式系统案例：分区树 + 委派 + 缓存 + 权威应答。
- 属性命名的天花板：复杂查询性能——所以它活成了「目录服务/标签系统」而不是通用解析层。


## 版本演进

- **第 1 版（2002）**：DHT 已入正文（Chord/CAN/Pastry/Kademlia 四件套并列介绍）。
- **第 2 版（2007，本书）**：DHT 收敛为「定位技术」之一，增加分层定位服务；LDAP 与 DNS 作为案例保留。
- **第 3 版（2017）**：结构基本保留，DHT 叙述进一步简化（实践中 churn 维护成本高，落地多在内容寻址）。
- **2026 口径**：命名 = **DNS（全局）+ 服务发现（集群内）+ 内容寻址（DHT/哈希，IPFS、git、Docker 镜像层）**；
  转发指针的工程形态是「注册中心 + 心跳租约」（etcd TTL key、Consul session）。

## 近年研究与工业界开源实践（2015–2026）

- **服务发现即命名**：
  - `etcd-io/etcd`（≈52.3k★，2026-09 实测）：Raft 复制的 KV + TTL 租约 + watch，K8s 的注册中心底座
    （呼应 [10-Web与协调范型.md](10-Web与协调范型.md)）；
  - `hashicorp/consul`（star 未核验）：健康检查 + DNS 接口——把服务发现直接挂回 DNS 语义；
  - K8s Service/EndpointSlice：集群内的「平坦名 → 虚 IP → 端点集」两级解析。
- **内容寻址（标识符自验证的胜利）**：Git 对象哈希、Docker 镜像摘要、`protocol/ipfs`（IPFS，DHT+内容寻址，star 未核验）——
  「哈希即名字」让完整性校验与去重免费获得。
- **DNS 的现代化**：DoH/DoT 加密查询、anycast 根服务器、EDNS 扩展；权威 DNS 仍是全球最大的分布式命名系统。
- **一致哈希工业化**：Dynamo 系（Cassandra、Riak、TiKV 的 Placement Driver 分组）把
  「一致哈希 + 虚拟节点」变成分片路由默认（对照 [07-一致性与复制.md](07-一致性与复制.md) 的 Multi-Raft 分组）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「IP 地址 = 标识符」 | 地址绑定位置与网卡，实体迁移即失效；需要 ID/位置分离（Mobile IP、服务 ID、内容哈希） |
| 2 | 「DHT 是命名系统的通用答案」 | DHT 擅长精确键查找，不擅长复杂查询与低延迟单跳解析；生产系统多为「注册中心+目录树」，DHT 用于内容寻址 |
| 3 | 「DNS 缓存可以随便设 TTL」 | TTL 是**一致性与负载的调节阀**：太长迁移慢（ DNS 迁移 48h 之痛），太短权威服务器被打爆 |
| 4 | 「转发指针与 home 方案二选一」 | 实际系统组合使用：先问 home 拿当前位置，之后链式跟踪多次迁移（Mobile IP 三角路由即此折中） |
| 5 | 🔧 原书未覆盖 | **服务网格/注册中心的租约语义**：心跳 TTL + 过期摘除，本质是「带失效检测的平坦命名」（见 [08-容错与安全.md](08-容错与安全.md)） |
| 6 | 🔧 原书未覆盖 | **DNS 安全**：DNSSEC 签名链、域名劫持/缓存投毒、DoH 隐私；原书 DNS 案例完全没有安全层 |
| 7 | 🔧 原书未覆盖 | **多集群/多云命名**：跨管理域的服务名冲突与全局负载均衡（GeoDNS、Global Endpoint） |

### 本章自测六问（读完自查）

1. 名称、标识符、地址三者中，哪个必须「唯一且终身不变」？（标识符；地址是「当前访问点」的名称。）
2. 转发指针方案的两个死穴？（链长累积延迟与断链；解决靠 home 回链或周期性全量重定位。）
3. home-based 方案为什么有「地理次优」问题？（所有实体都先绕 home——亚洲实体经美国 home 转接三角路由。）
4. Chord 后继副本（succeeding replicas）复制到哪几个节点？（键在环上的 s 个直接后继——不是随机挑选。）
5. 闭包机制解决什么问题？（确定「从哪开始、用哪个解析器」解释一个名字——URL 的 scheme 即最简闭包。）
6. 递归解析与迭代解析各自的代价落在谁头上？
   （递归：服务器承担链式查询，客户端省事、服务器重；迭代：客户端自己跑完全程，服务器只答下一跳。）
