## 本章地图

- 两章合并的理由：**容错与安全是同一枚硬币**——都是「在不可信/会出错的部件之上构造可信服务」，
  都靠冗余与协议，都有「故障模型 → 检测 → 屏蔽 → 恢复」的因果链。原书作者也把两章并列为原理部分收尾。
- 容错章的核心成果：状态机复制 + 2PC——这是 2026 年所有共识系统（Raft/Paxos）的理论前身。
- 安全章的核心成果：认证（你是谁）+ 授权（你能干什么）+ 分发信任（PKI）——mTLS 与零信任的原型。

## 核心精讲（教学示意，不参与构建）

### 上：容错（原书第 8 章）

#### 8.1 引论：故障模型与冗余
- **故障分层**：故障（fault）→ 错误（error）→ 失效（failure）；容错的目标是阻断「故障升级为用户可见失效」。
- **故障模型谱系**：崩溃故障（halt，最温和）→ 遗漏（丢消息/丢步）→ 时序（响应超时）→
  **任意（拜占庭）**（乱发消息、说谎）——容忍后者的代价是 O(3f+1) 副本级别的开销。
- **屏蔽手段 = 冗余**：信息冗余（校验码）、时间冗余（重试）、**物理冗余**（多副本）。
- **失效检测器**：完美 vs 不完美（不可靠网络上只能近似：及时性 + 完整性两个维度的弱化组合）；
  Chandra-Toueg 证明何种最弱检测器足以解共识——这是「检测器也是协议的一部分」的经典论证。

#### 8.2 进程恢复力
- **故障检测器**：心跳 + 超时是工程默认；检测不是判断而是「怀疑」，要可撤销。
- **主备份（primary-backup）**：主处理请求并同步状态到备份；主挂后备份接管。
  状态同步的三个拷贝点（请求处理前 / 请求排序后 / 执行完成后）决定丢失多少已确认操作。
- **状态机复制（state machine replication）**：副本从相同初始状态出发，**以相同顺序执行相同确定性请求序列**，
  则状态始终一致。关键需求 = **全序广播**——而全序广播的最强实现就是共识算法（Paxos/Raft，见下）。
  - 非确定性来源（本地时间、随机数、多线程调度）必须消除或改从日志取值。

#### 8.3 可靠通信与可靠多播
- 可靠 RPC：超时重传 + 至多一次语义（去重表）——呼应 [04-通信.md](04-通信.md) 的四象限。
- **可靠多播**：简单方案（每副本反馈 + 发送者重发）不可扩展；**分层反馈**（树状组织接收者，
  局部聚合 NACK/ACK）把反馈复杂度从 O(N) 降到 O(log N)。

#### 8.4 分布式提交
- **2PC（两阶段提交）**：
  1. 投票阶段：协调者发 VOTE-REQUEST，参与者回 VOTE-COMMIT / VOTE-ABORT；
  2. 决策阶段：协调者发 GLOBAL-COMMIT / GLOBAL-ABORT，参与者按决策落定。
  - 两种致命阻塞：协调者在「决策阶段前」挂 → 参与者悬置（已投 commit 票后既不能单方面提交也不能放弃）；
    参与者挂 → 协调者等待。**2PC 是阻塞协议**。
- **3PC（三阶段提交）**：增加 pre-commit 阶段，使「协调者挂 + 网络分区」下参与者可依据
  pre-commit 状态自行决策——消除阻塞，但**分区下可能两个协调者并存**（split brain），
  且消息轮数更多——原书结论：3PC 不值得，实践中仍用 2PC + 超时 + 人工干预。
- 🔧 2026 的答案：把「提交」交给**共识**——协调者本身就是 Raft/Paxos 复制的日志（协调者故障后
  新主从日志恢复未决事务），或干脆采用 Percolator/Spanner 式的容错协调者。

#### 8.5 恢复
- **向后恢复**：回滚到检查点 + 日志重放：
  - **undo/redo 日志**：undo（撤销未提交）、redo（重做已提交）——对应数据库 WAL（对照
    [数据库系统概念6/26-高级事务处理.md](../数据库系统概念6/26-高级事务处理.md)）；
  - **消息日志**：确定性重放需要记下「入站消息的顺序」（乐观/悲观消息日志的取舍）；
  - 检查点协调：独立检查点可能产生「孤儿检查点」（永远无法与全局一致状态对齐），需分布式快照
    （Chandy-Lamport 算法，见 [06-同步.md](06-同步.md) 的向量时钟基础）。

### 下：安全（原书第 9 章）

#### 9.1 引论
- **策略 vs 机制**：策略说「不允许 A 读 B 的文件」，机制是 ACL/加密/审计——机制应可配置以实现不同策略。
- 分布式特有难度：消息可被窃听/篡改/重放，身份声明可伪造——**安全 = 认证 + 完整性 + 机密性 + 可用性**。
- 设计原则：聚焦控制点（focus of control）、分层防御、简单性（复杂机制自己就是漏洞）。

#### 9.2 安全通道
- 机密性（加密）+ 完整性（MAC/哈希）+ 认证（身份验证）+ 新鲜性（防重放：nonce/时间戳）。
- **共享密钥认证**：挑战-应答（challenge-response）；**Needham-Schroeder**：KDC 介质的会话密钥分发
  （含 nonce 防重放）——Kerberos 的直系祖先。
- **公钥认证**：私钥签名 / Diffie-Hellman 会话协商；**相互认证**需双方各验一遍。
- 🔧 2026 的对应物：TLS 1.3 简化了握手（1-RTT、0-RTT）、移除了老旧原语；mTLS = 双向证书认证，
  是服务网格的默认通道（见「近年实践」）。

#### 9.3 访问控制
- **ACL（访问控制表）**：按资源列出谁能做什么——「资源 → 主体」索引；
- **能力（capability）**：按主体持有不可伪造票据——「主体 → 资源」索引；
  能力难吊销是工程痛点（Amoeba 系统的能力加密自验证是经典设计）。
- 保护域与域切换（进程/用户/角色）；RBAC（基于角色）把主体组织成组以简化策略。

#### 9.4 安全管理
- **密钥管理**：KDC（集中分发会话密钥，单点风险）vs CA（证书链）；
- **PKI**：X.509 证书、信任锚、层级 CA；**证书吊销**（CRL / OCSP）——吊销不及时是经典漏洞窗口；
- 🔧 2026 补充：短生命周期证书（Let's Encrypt 90 天 → 2026 推动更短）、自动化续期（ACME）、
  SPIFFE/SPIRE 工作负载身份（把「证书」发给容器/服务而非人）。

#### 9.5 可信系统
- **TCB（可信计算基）**：安全策略所依赖的最小硬件/软件集合；TCB 越小越可信。
- **多级安全（MLS）**：Bell-LaPadula 模型——**不上读（no read up）、不下写（no write down）**；
  军事分级背景，但思想渗透到现代隔离设计。
- 橙皮书（TCSEC）分级：D/C1/C2/B1/B2/B3/A1——历史价值大于工程价值，但其「最小 TCB」思想不灭。

### 容错与安全共用一张「信任/失效」地图（合并章的统摄视图）

| | 容错（Ch8） | 安全（Ch9） |
| --- | --- | --- |
| 假设 | 部件会**随机**出错 | 对手会**故意**作恶 |
| 故障模型 | 崩溃/遗漏/时序/拜占庭 | 窃听/篡改/重放/伪造 |
| 检测 | 心跳超时、失败检测器 | 完整性校验、审计、异常检测 |
| 屏蔽 | 冗余（副本/重试/校验码） | 加密 + 认证 + 授权 |
| 恢复 | 检查点 + 日志回滚 | 密钥轮换、吊销、灾备 |
| 验证 | 故障注入（混沌工程） | 渗透测试、红蓝对抗 |
- 拜占庭模型是两栏的交点：**对手即故障**——区块链正是把安全章的对手假设接进容错章的协议世界。
- 主备份 vs 状态机复制的取舍表（上-8.2 的展开）：
  | | 主备份 | 状态机复制 |
  | --- | --- | --- |
  | 复制对象 | 服务（一台主干活） | 确定性状态机（全副本干活） |
  | 关键要求 | 快速故障转移 + 状态同步 | 全序广播 + 确定性 |
  | 失效切换延迟 | 主挂后可能丢已确认请求 | 无请求丢失（多数派已确认） |
  | 2026 实现 | 云盘主备、数据库主从 | Raft/Paxos 全家桶 |

## 版本演进

- **第 1 版（2002）**：容错与安全两章已有主体结构；拜占庭容错、可靠多播叙述较简。
- **第 2 版（2007，本书）**：容错章强化 2PC/3PC 与恢复；安全章加入 DRM（数字版权管理）小节（时代特色，已淡出）。
- **第 3 版（2017）**：容错章正式引入 **Paxos/Raft**（共识成为容错的中心）；安全章移除 DRM，
  补充访问控制矩阵与密钥分发。
- **2026 口径**：容错 = **共识即容错**（Raft 取代手写主备份）+ **混沌工程验证**；
  安全 = **零信任架构**（不再有「可信内网」）+ mTLS + 短期凭证 + 工作负载身份。

## 近年研究与工业界开源实践（2015–2026）

- **共识的工程化（容错主线）**：
  - `etcd-io/etcd`（≈52.3k★，2026-09 实测）：Raft 库 + MVCC KV + lease，K8s 大脑；「2PC 协调者故障」
    类问题在 etcd 里的答案是——把决策记进 Raft 日志，新主续决；
  - `apache/zookeeper`（≈12.8k★）：ZAB 协议（类 Paxos 的原子广播），原书 Ch13 协调范型的工业化身；
  - `tikv/tikv`、`cockroachdb/cockroach`：数千个小共识分组替代「一个巨大 2PC 域」，
    跨分组才用 2PC 且配容错协调者（Percolator 式锁表或 Spanner 式时间）。
- **混沌工程（容错的验证）**：
  - `chaosblade-io/chaosblade`（≈6.5k★）、`litmuschaos/litmus`（≈5.6k★，2026-09 实测）：
    故障注入（杀进程、断网、时钟漂移、磁盘满）+ 稳态断言——原书「设计容错」升级为「验证容错」；
    Netflix Chaos Monkey 是思想源头（2010 年代公开）。
- **零信任与 mTLS（安全主线）**：
  - `istio/istio`（≈38.4k★）：sidecar 间自动 mTLS、SPIFFE 风格工作负载身份、细粒度授权策略；
  - BeyondCorp（Google 公开的零信任实践）：访问决策按设备+身份+上下文，而非网段；
  - 🔧 原书 ACL vs 能力之争的现代综合：**短期签名凭证（JWT/OIDC）+ 策略引擎（OPA）**——
    能力（票据）的可吊销性问题用「短有效期 + 自动刷新」缓解。
- **2PC 的三种现代化出路**（原书 8.5 的 2026 续篇）：
  1. **共识化协调者**：决策记入 Raft 日志，协调者可换人续决（TiDB/TiKV、CockroachDB 路线）；
  2. **Percolator 模型**：客户端协调 + 主锁行 + 时间戳排序（Google OSDI 2010，TiDB 乐观事务采用）；
  3. **避免跨资源事务**：Saga（补偿事务）/ 事件驱动最终一致——微服务时代把 2PC「设计掉」。
- **TLS/证书运维的现实清单**（原书 9.2 的工程续篇）：
  - 证书轮换自动化（ACME/ cert-manager），生命周期 ≤90 天；
  - 内部流量 mTLS 全覆盖（服务网格），人肉配置证书视为事故源；
  - 秘密不落盘：Vault/KMS 动态发凭证，短期化一切长期密码。
- **拜占庭容错的民用化**：区块链（PoW/PoS/BFT 族）把拜占庭模型从军方课题变成万亿级产业，
  但吞吐/成本仍印证原书「拜占庭容错很贵」的判断。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「3PC 比 2PC 好」 | 3PC 消除阻塞但引入分区双主风险且更慢；生产用 2PC + 容错协调者（共识化），或直接避免跨资源事务 |
| 2 | 「心跳超时 = 对方宕机」 | 超时只证明「暂时失联」；检测器必然不完美，决策要按「怀疑可撤销」设计（FLP 与检测器理论的共同结论） |
| 3 | 「加密 = 安全」 | 原书框架：认证、完整性、机密性、可用性各自独立；加密只覆盖机密性，重放/授权/审计另需机制 |
| 4 | 「内网流量可信」 | 零信任原则：东西向流量同样要 mTLS 与授权；服务网格让它成为默认而非锦上添花 |
| 5 | 「状态机复制只要求顺序相同」 | 还要求**确定性**：随机数、系统时间、线程调度等非确定源必须消除或日志化 |
| 6 | 🔧 原书未覆盖 | **Raft 工程实现**：日志压缩快照、成员变更（joint consensus/单步变更）、pre-vote 防扰动、读索引/租约读 |
| 7 | 🔧 原书未覆盖 | **混沌工程**与「故障注入即测试」的工程化（原书只有设计论证，没有验证方法论） |
| 8 | 🔧 原书未覆盖 | **零信任/mTLS/工作负载身份（SPIFFE）**、证书自动化（ACME）、秘密管理（Vault 类）替代静态配置密钥 |
