# 10-Web与协调范型（覆盖原书第 12 章「基于Web的分布式系统」+ 第 13 章「基于协作的分布式系统」）

> **本章地图（上：Web 范型，第 12 章）**：传统 Web 体系（HTML/HTTP 分离关注点、胖 vs 瘦客户端）→
> **Web 服务**（WSDL 服务描述、SOAP 消息、WS-* 栈）→ 进程：客户端（瘦客户、富互联网应用、
> widget）、**Apache Web Server**、**Web 服务器集群**（传输层交换机、内容感知分发）→
> 通信：HTTP 方法/头部/状态码、SOAP 细节 → 命名（URL）→ **一致性与复制**（Web 代理缓存、
> Web 托管系统复制——含 **GoogleFS/MapReduce** 案例、Web 应用复制：边缘服务器、一致性哈希）→
> 容错与安全（CDN 冗余、SSL/TLS、认证）。
> **本章地图（下：协作范型，第 13 章）**：协调模型引论（**时间耦合/引用耦合**二维分类：
> 直接通信、邮箱、共享数据空间、发布-订阅）→ 架构（总体方法：数据空间与 pub/sub、
> 传统架构：Linda/Lime、P2P 架构）→ 进程 → 通信（**基于内容的路由**、复合订阅）→
> 命名（复合事件描述、事件与订阅匹配）→ 同步 → 一致性与复制（静态注册表/事件覆盖网、动态复制）→
> 容错（可靠发布-订阅、共享数据空间的容错）→ 安全（机密性、安全数据空间）。

## 本章地图

- 两个范型代表 2007 年的两个方向：**Web 范型 = 以文档/服务为中心的请求-响应世界**；
  **协作范型 = 以事件/共享空间为中心的解耦世界**。
- 协作范型的灵魂是二维解耦矩阵：**时间耦合**（双方必须同时在线？）× **引用耦合**（双方必须互相知道？）
  ——发布-订阅与共享数据空间在两轴上都解耦，是 2026 年事件驱动架构（EDA）的理论底图。
- Web 范型章是全书距离「今天的互联网」最近的一章，也是被时代改写最快的一章（SOAP → REST）。

## 核心精讲（教学示意，不参与构建）

### 上：基于 Web 的分布式系统（第 12 章）

#### 12.1 架构
- **传统 Web**：三层——浏览器（表示）+ Web 服务器（逻辑 + 内容）+ 数据库服务器（数据）；
  DHTML/CGI 到服务器端脚本的演进；瘦客户端把状态推回服务器（对照 [03-进程与虚拟化.md](03-进程与虚拟化.md) 的有/无状态之争）。
- **Web 服务**：把「跨组织的 RPC」标准化——WSDL 描述接口（操作/消息/绑定）、SOAP 作为消息信封
  （XML + envelope/header/body）、UDDI 注册发现；WS-Security 等扩展合称 WS-* 栈。
  - 🔧 原书 2007 年的判断（SOAP/WSDL 是企业集成正解）在十年内被 **REST** 掀翻：
    资源 + 统一接口 + 无状态 + 可缓存，把 HTTP 本身当应用协议。

#### 12.2 进程
- 客户端：瘦客户（浏览器渲染）→ 富互联网应用（RIA：AJAX）→ **widget**（可嵌入的小型应用组件，
  2007 年的 iGoogle/桌面挂件——今天的前端组件化与微前端是其直系后代）。
- **Apache Web Server**：进程/线程池模型、模块化管道（对照 Nginx 的事件驱动，见 [03-进程与虚拟化.md](03-进程与虚拟化.md)）。
- **Web 服务器集群**：传输层交换机（L4：按 TCP 会话分发，粘性会话问题）vs 内容感知分发（L7：按 URL/负载）；
  本地分发节点（LVS 类）+ 广域分发（GeoDNS，见 [05-命名系统.md](05-命名系统.md)）。

#### 12.3–12.4 通信与命名
- HTTP：方法（GET/POST/HEAD…）、头部（缓存控制/条件请求 If-Modified-Since）、状态码；
  简单性 + 无状态 + 文本协议是 Web 扩散的技术理由。
- SOAP：RPC-over-HTTP 与消息式两种用法；URL 作为全局命名（引用透明）。

#### 12.6 一致性与复制（本章最重的一节）
- **Web 代理缓存**：命中/未命中/一致性检查；TTL + 条件 GET（If-Modified-Since/ETag）——
  「客户为中心一致性」的 Internet 尺度实现（对照 [07-一致性与复制.md](07-一致性与复制.md)）。
- **Web 托管系统复制**：原书以 **GoogleFS + MapReduce** 为例说明「Web 规模下，
  把计算搬到数据旁」——GFS 用大块（64MB）+ 单主多块服务器 + 追加写优化吞吐；
  MapReduce 把计算调度到块所在节点，故障重试内建。
- **Web 应用复制**：边缘服务器复制（动态内容缓存 + 应用逻辑下沉，Akamai 模式）、
  **一致哈希**做前端分配（对照 Ch5 DHT）、读复制与写主库的常规组合。

#### 12.7–12.8 容错与安全
- 容错：CDN 天然多副本 + 集群健康检查；Web 应用的 graceful degradation。
- 安全：SSL/TLS 安全通道（对照 [08-容错与安全.md](08-容错与安全.md)）、Web 认证（表单/证书）、
  跨站脚本/注入类应用层攻击与输入过滤。

### 下：基于协作的分布式系统（第 13 章）

#### 13.1 协调模型
- 二维耦合分类：
  | 模型 | 时间耦合 | 引用耦合 |
  | --- | --- | --- |
  | 直接通信（RPC/消息） | 强（需同时在线） | 强（互知地址） |
  | 邮箱（消息队列） | **弱**（可离线投递） | 强 |
  | 发布-订阅 | 弱 | **弱**（发布者不知订阅者） |
  | 共享数据空间（tuple space） | 弱 | 弱（通过数据模式匹配） |
- **Linda**：tuple space 的始祖——in/out/rd 原语，按模板匹配元组；**Lime** 把 tuple space 与移动设备结合
  （按物理位置拆分聚合）。
- **TripleSpace**：以「语义 Web 三元组」为数据单元的共享空间（W3C 语义 Web 语境的实验系统，
  van Steen 团队参与），数据单元从元组升级为 RDF 三元组。

#### 13.2–13.4 架构、进程与通信
- pub/sub 的三种路由形态：基于主题（topic）、基于**内容**（按消息属性匹配订阅）、基于类型。
- **基于内容的路由（content-based routing）**：订阅以谓词树表达，路由器做**订阅合并与分割**
  （覆盖网节点按订阅树转发，消息沿匹配路径扩散）；复合订阅（composite subscriptions）支持
  「事件 A 之后事件 B」的组合模式。
- 匹配算法：事件与订阅的**多级匹配**（类/属性/值），覆盖网一致性要求各路由器看到一致的订阅集
  ——这就是 13.7 一致性节的主题。

#### 13.5–13.9 命名、同步、复制、容错、安全
- 命名：事件的「身份」不是地址而是**内容本身**——复合事件（事件序列模式）的描述与匹配即「协调系统的命名层」。
- 一致性与复制：**静态方法**（订阅注册表集中复制 + 事件覆盖网固定拓扑）vs **动态方法**
  （按负载复制热门订阅、自组织覆盖网）——对照 [07-一致性与复制.md](07-一致性与复制.md) 的放置三段论。
- 容错：**可靠发布-订阅**（发布者代理的事务性 + 端到端确认；订阅端持久化）；
  共享数据空间的容错 = 元组的复制与访问串行化。
- 安全：发布-订阅的机密性难题（路由器必须看内容才能路由 → 加密与可路由性冲突，
  研究方向为加密匹配/安全多播组密钥管理）。

### SOAP vs REST vs gRPC vs GraphQL 四代接口风格（2026 补充）

| | SOAP | REST | gRPC | GraphQL |
| --- | --- | --- | --- | --- |
| 契约 | WSDL | OpenAPI（可选） | proto | SDL schema |
| 语义 | 操作 | 资源+统一方法 | 方法 | 查询树 |
| 传输 | HTTP/SMTP | HTTP | HTTP/2 | HTTP |
| 缓存 | 难 | 原生友好 | 难 | 难 |
| 适合 | 遗留企业集成 | 公开 API | 内部微服务 | 聚合前端数据 |
- 原书只写了前一代（SOAP），这一张表是它被 2026 补完的样子；REST 胜在「把 HTTP 当协议而不是隧道」，
  正是对原书 WS-* 复杂性的直接反驳（Fielding 博士论文 2000）。

### 协调范型 → 2026 事件生态映射（下章的收束表）

| 原书概念 | 2026 工业对应物 |
| --- | --- |
| tuple space（Linda） | Redis 之外的内存数据网格（Hazelcast/Infinispan，star 未核验） |
| 发布-订阅（主题/内容） | Kafka（主题+分区）、NATS（主题通配）、Pulsar（属性过滤） |
| 内容路由 | Kafka Streams / Flink 的流处理路由 |
| 复合订阅（事件模式） | CEP（复杂事件处理，Flink CEP）、Kafka Streams DSL |
| 共享数据空间容错 | 事件日志的副本与重放（offset 语义） |
| TripleSpace（RDF 三元组空间） | 知识图谱存储 + LLM 结构化检索（2026 语境的远亲） |
| 协调服务（本书末章的落点） | ZooKeeper/etcd——强一致小 KV + watch |

## 版本演进

- **第 1 版（2002）**：Web 章为「基于文档的（web-based）」叙述；协作章案例是 pub/sub 与 Linda。
- **第 2 版（2007，本书）**：Web 章改名「基于 Web 的」，加入 Web 服务/SOAP 与 Web 托管复制（GFS/MapReduce 案例）；
  协作章加入 TripleSpace 与内容路由。
- **第 3 版（2017）**：**两章合并为一章「Distributed Web-based systems」**，协作范型独立成章被删
  （pub/sub 融入通信章）；Web 章补 REST 与云。
- **2026 口径**：SOAP→REST/gRPC/GraphQL；Web 服务器 → 边缘计算与 CDN-as-a-platform（边缘函数）；
  widget → 微前端与 PWA；Tuple space/pub-sub → Kafka/Pulsar 事件流与事件网格（EventMesh）；
  语义 Web（TripleSpace 的语境）演进为知识图谱与 LLM 时代的结构化数据层。

## 近年研究与工业界开源实践（2015–2026）

- **Web 侧**：
  - **HTTP/2（2015）与 HTTP/3（QUIC, RFC 9000）**：多路复用消灭队头阻塞、0-RTT 建连——
    原书 HTTP 1.x 的「每请求一连接」假设全面过时（对照 [04-通信.md](04-通信.md)）；
  - **边缘计算**：Cloudflare Workers、Lambda@Edge——原书「Web 应用复制/边缘服务器」一节的完全体；
    **WebAssembly** 作为边缘运行时：`wasmerio/wasmer`（≈21.1k★，2026-09 实测）；
  - **微前端与组件化**：widget 思想的 2026 形态（module federation、PWA）。
- **事件与协调侧**：
  - `apache/kafka`（≈33.8k★）：日志即事件总线；Kafka Streams 把「复合订阅」变成流处理拓扑；
  - `apache/pulsar`（star 未核验）：存算分离的 pub/sub，分层分片与订阅模式丰富；
  - **协调服务**：`apache/zookeeper`（≈12.8k★）、`etcd-io/etcd`（≈52.3k★，2026-09 实测）——
    「协调范型」最成功的工业化后代不是 tuple space，而是**强一致的小型 KV + watch**；
  - **Google Spanner**（Corbett et al., OSDI 2012）：全球范围的外部一致事务——把「协调」做成数据库服务
    （TrueTime 见 [06-同步.md](06-同步.md)）。
- **ZooKeeper/etcd 的 2026 现状**：ZooKeeper 在 Kafka 3.x 起被 KRaft（内置 Raft）逐步替代——
  「外部协调服务」与「内置共识」之争天平向后者倾斜；etcd 反而因 K8s 而无处不在。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「SOAP/WSDL 是企业集成的标准答案」 | 2007 年的教科书结论；REST 以简单性、可缓存性、HTTP 原生语义胜出，gRPC 补高性能场景——SOAP 现存于遗留系统 |
| 2 | 「发布-订阅消息中间件 = 协调范型的全部」 | 原书分类学（时间/引用耦合四象限）提醒：MQ 只解决时间解耦，内容路由与共享空间另有语义 |
| 3 | 「Web 代理缓存的 TTL 是可靠性问题」 | TTL 是**一致性-新鲜度-负载**的联合调节阀；CDN/浏览器/代理三层缓存各有策略层 |
| 4 | 「事件系统天然可靠」 | pub/sub 的可靠投递需要持久化 + 确认 + 重放（offset/log），「发出去」不等于「处理成功」——原书 13.8 专门讲了这点 |
| 5 | 🔧 原书未覆盖 | **GFS→Colossus 与对象存储生态**：存储从「文件系统范型」滑向「对象 API + 元数据服务」（见 [09-对象与文件系统范型.md](09-对象与文件系统范型.md)） |
| 6 | 🔧 原书未覆盖 | **MapReduce 的演进**：Spark（内存计算）→ 流批一体（Flink）→ Lakehouse（Iceberg/Delta/Hudi）；MR 编程模型已退居历史层 |
| 7 | 🔧 原书未覆盖 | **边缘计算与 WebAssembly**、服务端推送（WebSocket/SSE）替代轮询、WebRTC 实时通道 |
| 8 | 🔧 原书未覆盖 | **Zero-trust Web 安全**：OAuth2/OIDC、JWT、CSP——原书 Web 安全只覆盖 TLS 与输入过滤 |
