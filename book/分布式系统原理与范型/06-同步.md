# 06-同步（覆盖原书第 6 章「同步化」）

> **本章地图**：物理时钟同步（Cristian 算法、Berkeley 算法、**NTP**）→ **逻辑时钟**
> （Lamport 时钟与 happens-before、向量时钟）→ **选举算法**（欺凌算法、环算法）→

## 本章地图

- 分布式系统没有共享时钟与共享内存，「同步化」= 在异步网络上人为制造**顺序**（逻辑时钟）、
  **唯一性**（互斥/选举）与**时间感**（物理同步）。
- 本章是 Ch8（提交需要协调者=选举）与 Ch7（一致性需要顺序=时钟）的前置章。
- 2007 年还没有 Spanner——「物理时钟上做外部一致性」在当年是异端，2026 已是 Spanner 的工业现实。

## 核心精讲（教学示意，不参与构建）

### 6.1 物理时钟同步
- 目标：让不同机器的时钟**偏差（skew）**足够小。晶体振荡器漂移 ~10⁻⁵ 量级，一天可差数秒。
- **Cristian 算法**（外部同步）：向时间服务器发请求，用往返时延估计偏差——
  `T = T_server + (T_return - T_send - 处理时间)/2`；精度受 RTT 下限约束。
- **Berkeley 算法**（内部同步）：master 轮询各机时钟，取平均（剔除离群）后**通知各机调整**——
  不依赖权威时间源，适合无外部时钟的内网。
- **NTP（网络时间协议）**：分层 stratum 结构、多次采样取最小 RTT、逐步调频（slew 不跳变），
  全球主干同步到毫秒级——Internet 物理同步的事实标准。
- 🔧 2026 视角：数据中心内 **PTP（IEEE 1588）** 配合支持硬件时间戳的网卡可达亚微秒；
  **Google TrueTime（Spanner）** 反其道而行——不给点值给**区间** [earliest, latest]，
  把「时钟不确定度」变成一等公民，事务提交等待区间收敛换取外部一致性。

### 6.2 逻辑时钟
- **happens-before 关系（→）**：同进程程序序 + 消息收发序的传递闭包；并发事件互不可比。
- **Lamport 时钟**：每个事件计数 +1；消息携带时间戳，接收方 `C = max(C, ts)+1`。
  - 性质：a → b ⟹ C(a) < C(b)；**逆命题不成立**（时间戳小不代表因果在前）——只能给全序，不能判因果。
- **向量时钟**：每个进程维护 N 维向量，消息携带全向量合并；C(a) < C(b) ⟺ a → b（**充要条件**）。
  - 代价：消息体积与进程数成正比；用于因果广播、冲突检测（Dynamo 的版本向量即其工业后代）。
- 🔧 2026 视角：**混合逻辑时钟 HLC**（Kulkarni et al., OPODIS 2014）= 物理时间戳 + 逻辑计数器，
  兼得「接近物理时间的可读时戳」与「因果正确」；CockroachDB、MongoDB、YugabyteDB 均采用。

### 三种「顺序工具」对照表（补充）

| 工具 | 保证 | 消息开销 | 判因果 | 2026 用途 |
| --- | --- | --- | --- | --- |
| Lamport 时钟 | 全序（自建打破平局规则） | O(1) | 否 | 事件排序、教学 |
| 向量时钟 | 因果充要 | O(N) | 是 | Dynamo 版本向量、冲突检测 |
| HLC | 因果 + 贴近物理时间 | O(1)（固定两元组） | 是 | 分布式数据库快照时间戳 |
| TrueTime | 物理时间区间 | 专用硬件 | 靠等待区间 | Spanner 外部一致性 |
- 记忆法：**开销与表达能力成正比，HLC 用 O(1) 开销买到因果判别，是工程最优折中**；
  TrueTime 不走逻辑路线，用硬件把物理时间误差变成「可等待掉」的区间。

### 6.3 选举算法
- 目标：故障/重启后选出一个唯一协调者（供互斥、提交、复制主节点使用）。
- **欺凌算法（bully）**：编号最大的存活者胜出——新加入或恢复的高编号节点「欺压」现主，触发再选举；
  代价：最坏 O(n²) 消息。
- **环算法**：进程构成逻辑环，检测到失效的节点沿环通告自己的编号，绕一圈后选出最大者，再绕一圈宣布结果。
- 🔧 2026 视角：生产系统的选举几乎都换成了**基于多数派的租约/共识选举**（Raft leader election、
  etcd lease、Redis Sentinel 投票）——bully/ring 只剩教学价值，因为它们无法在消息重复/乱序下保证安全。

### 三个互斥算法的量化对照（补充）

| 算法 | 进入临界区消息数 | 容错 | 2026 评价 |
| --- | --- | --- | --- |
| 集中式 | 3（请求/授权/释放） | 协调者单点 | 消息最少，本质是「单点锁服务」——etcd 锁即其共识化版本 |
| 令牌环 | 1–n（令牌轮转） | 丢令牌难检测 | 平均等待长，工程罕见 |
| Ricart-Agrawala | 2(n-1) | 一节点故障即停 | 教学价值；n 大完全不可用 |
- 把表读反了也有收获：**集中式不是错，而是「把共识外包给单点」**——原书真正想说的是
  消息复杂度与容错性的互斥；2026 的共识算法在「3 条消息 + 容错」两点上同时达标，代价是复杂度。

### Lamport 时钟 vs 向量时钟：一个判因果小例（教学示意）

- 三个进程 P1/P2/P3，事件：
  - P1: a₁（本地）→ 发消息 m 给 P2（a₂）
  - P2: 收 m（b₁）→ b₂（本地）
  - P3: c₁（本地，与 P1/P2 无通信）
- Lamport 时钟：C(a₁)=1, C(a₂)=2, C(b₁)=3, C(b₂)=4, C(c₁)=1——C(c₁)=C(a₁)=1 无法与 a₁ 分先后；
  用打破平局规则（按进程号）能排全序，但**该序不是因果序**。
- 向量时钟：V(a₁)=[1,0,0], V(a₂)=[2,0,0], V(b₁)=[2,1,0], V(b₂)=[2,2,0], V(c₁)=[0,0,1]——
  V(c₁) 与 V(a₁) 互不小于 ⟹ **并发**，可被算法直接判定。
- 结论记忆：**要「排个队」用 Lamport，要「问关系」用向量时钟；要「贴着钟走」用 HLC。**

### 位置系统的设计维度（原书 6.5 的参数化展开）

| 设计维度 | 选项 | 取舍 |
| --- | --- | --- |
| 谁维护位置记录 | home / 分层定位服务 / 对等 | 单点风险 ↔ 扩展性 ↔ 复杂度 |
| 更新时机 | 强更新（每移必更）/ 弱更新（按域聚合） | 查找精度 ↔ 更新开销 |
| 查找方式 | 精确 / 就近代理 | 精确性 ↔ 延迟 |
| 规模策略 | 逐层上溯（Globe）/ 全局根（DNS 式） | 本地命中率高 ↔ 根负载 |

### 6.4 互斥
- **集中式**：单协调者授权令牌——消息少（3 条/次）但单点；协调者故障即全局停摆。
- **令牌环**：令牌沿环轮转，持令牌者可进临界区——无饥饿，但令牌丢失检测难、平均等待 O(n)。
- **分布式 Ricart-Agrawala**：基于 Lamport 时间戳的全序请求 + 打包应答（deferred reply）；
  每次进入需 n-1 条请求 + n-1 条应答；故障一个进程即卡死，且全序带来的消息量随 n 线性膨胀。
- 共同结论：**分布式互斥是「用消息换协调」**，n 大时都不划算——工程答案是把临界区数据做成
  共识复制的日志（把互斥降维成「谁写日志谁持有」）。

### 6.5 位置系统
- 任务：回答「实体 X 现在在哪」。设计空间：谁维护位置记录（home / 位置服务器分层 / 对等）；
  更新频率与查找延迟的权衡（强更新 vs 弱更新 + 就近查找）。
- **GPS**：作为「位置的时间参照」——每个实体用 GPS 报告自身位置（含精确时钟！），
  原书已注意到 GPS 提供的其实是**全球统一的物理时钟源**。
- **Globe 定位服务**（本书作者 van Steen 的研究项目）：分层定位域，自底向上汇聚位置指针，
  与 05 章的 home-based 方案对照（详见 [05-命名系统.md](05-命名系统.md)）。
- 🔧 2026 视角：位置系统工业化成 LBS 栈（基站/WiFi 定位 + 地图服务）；
  「实体位置 → 最近副本/节点」的抽象活在 CDN GeoDNS、边缘调度与 Cell-based 数据库路由中。

## 近年研究与工业界开源实践（2015–2026）

- **TrueTime 路线**：`google/spanner`（闭源；论文 Corbett et al., OSDI 2012）用 GPS+原子钟数组
  把不确定度压到毫秒内，提交等待 ε 实现**外部一致性**（对照 [07-一致性与复制.md](07-一致性与复制.md)）；
  开源跟随者走 HLC 路线：
  - `cockroachdb/cockroach`（≈32.5k★，2026-09 实测）：HLC 时戳 + Range 级 Raft，串行化快照隔离；
  - `tikv/tikv`（≈16.9k★）：中心化 TSO（单点时钟服务）+ 分组 Raft，与 HLC/TrueTime 三条路线并存的活样本。
- **共识化选举/互斥**：`etcd-io/etcd`（≈52.3k★）的 lease + Raft 选举取代 bully/ring；
  分布式锁（Redlock 争论、etcd 锁服务）是互斥的工业形态。
- **时钟漂移的现实教训**：Leap Second 与 NTP 阶跃导致的元凶故障（2012 年 LinkedIn、2017 年 Cloudflare）
  促使 smearing（时间抹平）成为云厂商默认——原书「调整方式 slew 不跳变」在 NTP 层有了工业级实践。
- **开源实现锚点**：Raft 的时钟/选举代码可读 `etcd-io/raft`（star 未核验，随 etcd 仓库分发）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「时钟同步了，事件就有序了」 | 物理同步有误差；**依赖物理时戳排序必须考虑不确定区间**（TrueTime 之所以给区间） |
| 2 | 「Lamport 时钟能判断因果」 | 只保证 a→b ⟹ C(a)<C(b)；判因果要用**向量时钟**或 HLC |
| 3 | 「分布式互斥算法（Ricart-Agrawala）可以用于生产」 | n 个节点每次进入 O(n) 消息且单点故障卡死；生产用租约+共识日志，或干脆用单点协调服务 |
| 4 | 「选举算法选出的主是安全的」 | bully/ring 在消息重复、网络分区下可能选出两个主（split brain）；只有**多数派共识**保证唯一性（Ch8 详述） |
| 5 | 🔧 原书未覆盖 | **HLC/TrueTime 的外部一致性**：2007 年主流观点「物理时戳做不了严格顺序」被 Spanner 推翻 |
| 6 | 🔧 原书未覆盖 | **共识选举的任期（term）与租约租期设计**：避免旧主复活（fencing token、epoch） |
| 7 | 🔧 原书未覆盖 | **云环境时钟的运维性**：NTP smearing、闰秒处理、VM 暂停恢复后的时钟跳变 |

### 本章自测六问（读完自查）

1. Cristian 算法的时间估计误差下界由什么决定？（消息单向传输延迟；只能估 RTT 的一半作乐观近似。）
2. NTP 为什么「slew 而不跳变」？（跳变会让单调递增的时间倒流，破坏程序对时间序的假设——
   云厂商的 leap second smearing 同理。）
3. Lamport 时钟的逆命题（C(a)<C(b) ⟹ a→b）为什么不成立？（并发事件在各自计数器上无序，靠任意打破平局规则排出的序与因果无关。）
4. 欺凌算法最坏消息复杂度多少？什么场景触发？（O(n²)；低编号进程超时反复发起选举、高编号逐级压制时。）
5. 令牌环算法怎么检测「令牌丢失」？（超时——环上一圈轮转的预期时间内未再见令牌，则重生成；风险是双令牌。）
6. 位置系统中「强更新」与「弱更新」的取舍各偏向什么？（强更新偏向**查找精度**（位置记录常新），
   弱更新偏向**更新开销与就近查找**（读本地副本，容忍短暂陈旧）。）
