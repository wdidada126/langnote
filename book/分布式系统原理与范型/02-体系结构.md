# 02-体系结构（覆盖原书第 2 章「体系结构」）

> **本章地图**：软件体系结构 = 组件 + 连接器 → 四种架构样式（分层、基于对象、以数据为中心、基于事件）→
> 系统体系结构：集中式（C/S、两层/三层、垂直分布）→ 非集中式（P2P：结构化 DHT、非结构化 super-peer、混合 BitTorrent）→
> 混合式（边缘服务器、云）→ 体系结构与中间件：中断器（interceptor）、可修改中间件 →
> 自我管理：反馈控制模型 + 三个案例（Astrolabe 监视、Globule 差分复制、Jade 自动组件修复）。

## 本章地图

- 第 2 版新增章。核心区分：**软件体系结构**（组件如何组织、如何交互）与**系统体系结构**（组件在物理机器上如何放置）。
- 逻辑组织 ≠ 物理组织：同一套逻辑（如三层应用）可以部署成集中式，也可以部署成 P2P。
- 本章是全书的「目录页」：后面每章讲的一种机制（命名、通信、复制……）都能在本章找到它在架构中的位置。

## 核心精讲（教学示意，不参与构建）

### 2.1 体系结构的样式（architectural styles）
- 组件（component）：封装良好的功能单元（如存根、服务器）；连接器（connector）：组件间的交互机制（RPC、消息、事件总线）。
- 四种样式：
  | 样式 | 组件 | 连接器 | 典型 |
  | --- | --- | --- | --- |
  | 分层 | 逐层调用 | 过程调用 | 网络协议栈、三层应用 |
  | 基于对象 | 对象（接口+实现） | RPC/RMI | CORBA、Java RMI |
  | 以数据为中心 | 数据仓库 + 存取组件 | 数据读写 | 分布式文件系统、Web 仓库 |
  | 基于事件（协调） | 订阅者/发布者 | 事件发布 | pub/sub、Tuple space |
- 样式可以组合：现代消息中间件 = 以数据为中心的存储 + 基于事件的发布。

### 2.2 系统体系结构
- **集中式**：客户-服务器。服务器按功能分层（两层：表示+数据层；三层：表示+逻辑+数据），
  即**垂直分布**（vertical distribution）——按层切分。
  - 三层的现代映射：浏览器 / 应用服务器 / 数据库；逻辑上分层、物理上可任意放置。
- **非集中式**：**水平分布**（按机器/数据切分）。P2P 谱系：
  1. **结构化**：数据与节点按确定性拓扑（DHT：Chord 环、CAN 网格）组织，键→节点可路由，查找 O(log N)；
  2. **非结构化**：图随意（Gnutella 泛洪、super-peer 骨干），查找靠随机游走/泛洪，简单但无保证；
  - **混合**：Tracker 集中协调 + 数据传输 P2P（BitTorrent 是原书钦点的混合范例）。
- **P2P 三族对照表**（原书 2.2.2 的展开）：
  | 族 | 代表系统 | 查找方式 | 数据放置 | 复制 |
  | --- | --- | --- | --- | --- |
  | 结构化 | Chord / CAN | DHT 路由 O(log N) | 按键哈希确定 | 后继 s 副本 |
  | 非结构化 | Gnutella / super-peer | 泛洪 / 随机游走 | 随意 | 按流行度缓存 |
  | 混合 | BitTorrent | Tracker + DHT | 用户自主 | 分片互换（tit-for-tat） |
- **混合式（hybrid）**：边缘服务器体系——边缘侧缓存/计算 + 中心协调；CDN、云边协同的 2007 年版本。
- 🔧 原书 2.2.2 特别强调 P2P 的**自治系统**（自治协作、非集中控制）本质，是「可扩展性」的一剂猛药，
  但代价是激励与治理问题（搭便车）——原书已点到，2026 的区块链把这一点推到极致。

### 2.3 体系结构与中间件
- 中间件的三种「改写」方式：
  1. **中断器（interceptor）**：在调用链上插入逻辑——把面向对象的调用改写为面向消息的（RMI→消息），
     处理跨平台/安全/日志。gRPC 拦截器、K8s admission webhook、Envoy filter 都是它的直系后代。
  2. **可修改中间件（adaptive middleware）**：运行时改变组件绑定（动态重配置）。
  3. **上下文感知**：根据环境（位置、负载）调整行为。
- 原书论断：**中间件不该包办一切**——它解决的是「互操作」共性，应用特有的适应性必须留给应用层。

### 2.4 分布式系统的自我管理
- **反馈控制模型**：监视（monitor）→ 分析（analyze）→ 规划（plan）→ 执行（execute）四件套绕目标闭环，
  与今天 Kubernetes 的「observe-diff-act」控制循环同构。
- 三个案例：
  - **Astrolabe**：gossip 式聚合信息树，监视大规模系统状态（作者 van Renesse 等，ACM TOCS 2003）；
  - **Globule**：CDN 节点上的**差分复制策略**（differentiated replication）——对每个页面自动选择
    一致性协议（失效/租约/短复制），按页面流量特征权衡一致性开销；
  - **Jade**：组件失效自动检测与替换（自动修复管理）。
- 🔧 这三个案例今天都有工业化后代：Astrolabe → gossip 健康检查（Serf/Consul）；Globule → 自适应副本策略；
  Jade → K8s 控制器的自愈（self-healing）。

## 版本演进

- **第 1 版（2002）**：无独立架构章；C/S 与 P2P 内容散落在进程章与应用章。
- **第 2 版（2007，本书）**：新增本章；P2P（DHT、super-peer、BitTorrent）与自适应中间件成为正文重点。
- **第 3 版（2017）**：架构章保留但重心转向**云与边缘**、组织式架构（organizational architectures），
  P2P 部分收缩（DHT 在实践中退居后台）；开始讨论容器与微服务。
- **2026 口径**：架构光谱从「集中式 ↔ P2P」扩展为「单体 → 微服务 → service mesh → serverless → 边缘」；
  中断器思想在 sidecar proxy（Envoy/Istio）中复兴；反馈控制模型就是 K8s 的声明式控制循环。

## 近年研究与工业界开源实践（2015–2026）

- **集中式的回归与再分布**：P2P 在文件共享领域衰落，但其技术（DHT、gossip、BitTorrent 协议）被
  内容分发与区块链继承；微服务把「垂直分布」做成默认，代价是分布式事务/可观测性。
- **服务网格 = 中间件下沉**：原书的「体系结构 vs 中间件」之争，2017–2026 的答案是 sidecar：
  把中断器从应用进程挪到独立代理进程。
  - `istio/istio`（≈38.4k★，2026-09 实测）：控制面下发策略、数据面 Envoy 执行——教科书式「可修改中间件」；
  - `linkerd/linkerd2`：更轻的网格实现（star 未核验）。
- **自我管理 → 声明式控制循环**：`kubernetes/kubernetes`（star 未核验，量级 100k+）的
  reconcile loop 与原书反馈控制模型逐要素对应；失败自愈对应 Jade，gossip 成员管理对应 Astrolabe（etcd/Serf）。
- **反馈控制模型 × K8s 要素对照**（原书 2.4.1 的 2026 版）：
| 反馈控制要素（原书） | K8s 对应物 |
| --- | --- |
| 监视（monitor） | 控制器 list/watch + 指标（metrics-server） |
| 分析（analyze） | reconcile diff（期望状态 vs 实际状态） |
| 规划（plan） | 控制器策略（Deployment 的副本策略、HPA） |
| 执行（execute） | API Server 写回（patch/update） |
| 知识库（受管状态） | etcd（声明式期望状态存储） |- **P2P 遗产**：`webtorrent`（浏览器内 BitTorrent）、IPFS（DHT 寻址内容，star 未核验）延续结构化命名思想。
- **架构光谱 2026 速览**（本章「集中式 ↔ 非集中式」光谱的当代展开）：
  单体 → 模块化单体 → 微服务 → service mesh → serverless → 边缘函数 → Web3/去中心化网络；
  判据不再是「机器多少」，而是**控制面集中度**与**信任边界数量**——原书的光谱仍够用，只是两端被拉长。
- **中断器的三个现代落点**（原书 2.3.1 的 2026 对照，帮助定位概念）：
  | 中断层次 | 典型实现 | 拦截内容 |
  | --- | --- | --- |
  | 语言级 | 装饰器/中间件函数（Express、Spring AOP） | 请求处理管线 |
  | 进程级 | SDK 拦截器（gRPC interceptor） | RPC 编解码前后 |
  | 进程外 | sidecar proxy（Envoy/Istio） | 全部进出流量（含 mTLS） |
  - 拦截点越往下移，应用越「零侵入」，但调试链路越长——这是 2026 架构争论「SDK vs sidecar」的根源。
- **服务器放置算法的直觉**（原书 2.2.3 混合架构的支撑技术）：K-希望树按层级聚合「每个节点能服务的请求量」，
  自底向上选 K 个候选副本位置——它解决的是「客户发起副本/边缘节点放在哪」；
  与 Ch7 的「放置三段论」是同一问题的两种粒度（机器级 vs 数据级）。

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「三层架构就是分布式系统」 | 三层只是垂直分布；判据仍是组件是否跨机协作与隐藏连贯性（见 [01-引论.md](01-引论.md)） |

### 本章自测六问（读完自查）

1. 四种架构样式里，「以数据为中心」与「基于事件」的差异是什么？
   （数据仓库是**被动的存储**，组件主动读写；事件系统是**主动的推送**，订阅者被动收。）
2. 垂直分布与水平分布分别按什么切分？（按**层**切 vs 按**机器/数据**切。）
3. 结构化 P2P 为什么能保证 O(log N) 查找？（键与节点落在同一确定性拓扑上，路由表逐级折半。）
4. 中断器拦截的是哪两件事？（平台差异的改写——把对象调用翻译成消息；以及横切关注点——安全/日志/重试。）
5. 反馈控制四件套中，K8s 的「期望状态」存在哪里？（etcd——知识库与执行分离是声明式架构的关键。）
6. Globule 的「差分复制」差分在哪？（**按页面**选一致性协议：热点页用强协议，冷页用弱协议——
   粒度细到资源级而非系统级。）

### 一页速记

- 四样式：分层、对象、数据、事件——组件与连接器的四种组合姿势。
- 两类分布：垂直（按层切）、水平（按机器切）；集中/非集中/混合是物理放置的三档。
- 中间件三改法：中断器（拦）、可修改（换）、上下文感知（适）。
- 自管理四件套：监视 → 分析 → 规划 → 执行；Astrolabe（看）、Globule（放）、Jade（修）。
- 一句总纲：**逻辑组织管「怎么协作」，物理放置管「跑在哪」，中间件管「差异藏多少」**——
  架构设计的全部动作都在这三句话里。
