## 核心精讲（教学示意，不参与构建）

### 3.1 线程
- 线程 = 进程内的执行上下文，共享地址空间但各有栈。原书强调：**分布式系统中多线程的本质是「隐藏延迟」**——
  一个线程阻塞在 RPC 时，其他线程继续跑，把广域网延迟与计算重叠。
- 多线程客户端：浏览器并发拉取页面元素；多线程服务器：每个连接/请求一个线程（或线程池），
  与单进程事件驱动（select/poll）对照：前者编程简单、上下文切换开销大；后者高效但状态机化编程复杂。
- 🔧 原书的取舍表在 2026 的新解：事件驱动路线赢了——Nginx、Redis、Node.js、io_uring 都是
  「少量线程 + 事件循环」，而线程-per-request 被 async/await 语法弥补了编程复杂度。

### 3.2 虚拟化
- 虚拟机监控器（VMM/hypervisor）：在硬件（类型 1：Xen、ESXi）或宿主 OS（类型 2：VMware Workstation）上
  提供多个完整机器接口。
- 四个接口层次：硬件、OS（系统调用）、库（API）、应用（语言运行时）——在哪一层虚拟化决定了虚拟机形态：
  - 在硬件层：系统 VM；在 OS 层：Solaris Zones 类容器；在库层：WINE 类兼容层；
    在应用层：**进程虚拟机**（JVM、CLR）。
- **虚拟化层次对照表**（原书 3.2.2 的展开，2026 口径补全）：
  | 虚拟化层 | 形态 | 典型实现 | 隔离强度 | 启动速度 |
  | --- | --- | --- | --- | --- |
  | 硬件层 | 系统 VM | Xen/ESXi/Firecracker | 强 | 秒级 |
  | OS 层 | 容器 | Docker/containerd | 中（共享内核） | 亚秒 |
  | 库层 | 兼容层 | WINE | 弱 | — |
  | 应用层 | 语言 VM | JVM / Wasm | 弱-中 | 毫秒 |
- **服务器集群分发方案对照**（原书 3.4.2 的展开）：
  | 方案 | 机制 | 优点 | 缺点 |
  | --- | --- | --- | --- |
  | 传输层交换（L4） | 按 TCP 连接分发 | 高性能 | 无法感知内容、粘性会话难 |
  | 内容感知（L7） | 按 URL/Cookie 分发 | 可按业务路由 | 分发节点成瓶颈 |
  | 基于归属（home-based） | home 节点转发 | 会话粘性天然 | home 迁移复杂、单点风险 |
- **虚拟化在分布式系统中的角色**：迁移（把整个机器状态搬走）、隔离（多租户）、
  服务器整合（多虚机一物理机）——原书已预见云计算的三要素。
- 🔧 2026 的对应物：**容器**（OS 层虚拟化的胜利，Docker/K8s）、**microVM**（Firecracker：VM 隔离 + 容器启动速度）、
  **WebAssembly**（应用层虚拟机从 JVM 走到浏览器与服务端，见 [10-Web与协调范型.md](10-Web与协调范型.md)）。
- **虚拟化给分布式系统带来什么**（原书 3.2.1 的要点，2026 复述）：
  1. **隔离**：多租户安全边界（故障隔离 > 安全隔离，后者需 microVM/sandbox 补强）；
  2. **可迁移**：整机状态可搬运（VM 热迁移、快照恢复），故障域可调度；
  3. **可复制**：镜像即模板——「创建 100 个相同节点」从安装问题变成复制问题；
  4. **可定制**：每台「机器」可装不同 OS/内核版本，异构集群的同构化手段。

### 3.3 客户
- 网络用户接口：X-11 是「瘦客户」的代表（显示与计算分离）；Web 浏览器继承并胜出。
- 客户端的分布透明性软件：stub/RPC 运行时放在客户端，负责编组、重传、位置查找——
  「透明性是客户端的成本」这一视角贯穿全书。

### 3.4 服务器
- **设计问题**：
  - 接触方式：客户端如何找到服务器（端点固定 vs 目录服务 vs 转发）；
  - 无连接 vs 有连接：UDP 简单高效 vs TCP 可靠有序；
  - **有状态 vs 无状态**：无状态服务器崩溃后客户端重试即可（简化容错），有状态可做缓存与会话（提高效率）——
    这是全书容错章（Ch8）的伏笔；REST 把无状态推向 Web 标准。
- **superserver**：inetd/xinetd，单一守护进程按端口孵化服务，省内存。
- **服务器集群**：
  - 逻辑组织：**传输层交换机**（L4 switch）按内容/负载分发；**基于归属的（home-based）**方案——
    客户端先找归属节点（home node）再转发，兼顾负载与会话粘性；
  - 物理组织：传统数据中心、自主（多管理域）、分层（分层集群，如全球 DNS 根）；Web 服务器集群多配反向代理；
  - 管理：**分布式服务器**把服务镜像到多节点，客户端只感知单一端点；**服务器内迁移**把热负载搬离拥塞节点。
- 🔧 2026 的对应物：L4/L7 负载均衡（Envoy、HAProxy、云 LB）、**会话粘性与一致性哈希**、
  K8s Service/ipvs 的虚拟 IP 与端点转发——home-based 方案的工程形态就是「服务注册 + 控制器转发」。

### 3.5 代码迁移
- 迁移模型两维度：**移动性**（弱：仅代码+数据，目标环境重执行；强：连同执行状态一起搬）×
  **发起方**（发送方发起：client pull，如 applet/JS；接收方发起：server push，如按需加载的代理）。
- **迁移与本地资源**：绑定策略——按引用类型（资源 URL/能力/路径）与绑定时机（未绑定/已绑定/固定）
  组合成四象限，决定迁移成本；
- 异构性：跨平台迁移的答案是**可移植代码**（Java 字节码 / JS / Wasm），不是真实机状态搬迁。
- 🔧 2026 的对应物：代码迁移思想散落在「容器镜像迁移（弱移动）」、FaaS 的代码即部署、
  以及 checkpointer（CRIU）对强移动性的极少数工程化。

## 版本演进

- **第 1 版（2002）**：虚拟化一节薄，线程与代码迁移为主。
- **第 2 版（2007，本书）**：虚拟化扩成独立大节（正是 VMware/Xen 商业化高峰），新增服务器集群管理；
  代码迁移因安全顾虑与 Web 崛起而收缩为「思想史」地位。
- **第 3 版（2017）**：本章改名「进程」，虚拟化重点转向**容器与云**；代码迁移几乎删除。
- **2026 口径**：进程的组织单位从「线程/VM」变成「容器 + 编排器」；客户端-服务器演化成
  「前端-网关-服务网格-存储」多级链路；代码迁移被镜像分发与冷启动优化（快照恢复）替代。

## 近年研究与工业界开源实践（2015–2026）

- **容器与编排**：`kubernetes/kubernetes`（star 未核验，量级 100k+）、`containerd/containerd`（star 未核验）——
  OS 层虚拟化 + 控制循环，使「服务器集群管理」从论文变成基础设施默认。
- **microVM 与 FaaS**：`firecracker-microvm/firecracker`（AWS Lambda/Fargate 底座，star 未核验）——
  类型 1 hypervisor 与容器的折中；冷启动问题让「弱移动性」研究复活（快照/预取）。
- **WebAssembly 服务端化**：`wasmerio/wasmer`（≈21.1k★，2026-09 实测）、`wasmtime`（star 未核验）——
  应用层虚拟机走出浏览器，成为插件/边缘计算载体（呼应原书「在哪一层虚拟化」的分类）。
- **无状态化实践**：REST/HTTP 缓存 + 会话外置（Redis）+ JWT，把原书「无状态服务器利容错」变成行业纪律；
  `redis/redis`（star 未核验）承担有状态会话的独立层。
- **代码迁移四象限的 2026 复现**（原书 3.5.1 的「移动性 × 发起方」）：
  | | 接收方发起（server pull） | 发送方发起（client push） |
  | --- | --- | --- |
  | 弱移动 | 插件按需下载（浏览器扩展、Wasm 插件） | applet/JS 注入（历史形态） |
  | 强移动 | 进程检查点迁移（CRIU、VM live migration） | 移动 agent（已基本退场） |
  - 结论：活下来的是「弱移动 + 接收方发起」（Wasm 插件、FaaS 镜像）与「强移动 + 基础设施级」
    （VM 热迁移——云厂商透明维护，用户无感），其余象限被安全模型淘汰。
- **线程 vs 事件 vs 协程的选型表**（2026 补充，替代原书的二分讨论）：
  | 模型 | 适用 | 代价 |
  | --- | --- | --- |
  | 线程池 | CPU 密集、阻塞依赖多 | 上下文切换、栈内存 |
  | 事件循环（Nginx/Redis） | 海量连接、IO 密集 | 回调地狱/状态机化 |
  | 协程 async/await | IO 密集 + 想要顺序代码 | 运行时复杂度、传染性（函数染色） |


## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「虚拟机 = 更重的容器」 | 二者虚拟化层次不同（硬件层 vs OS 层），隔离/性能/迁移语义完全不同，按租户与信任边界选型 |
| 2 | 「无状态服务器是唯一正解」 | 无状态利容错但难做写一致性；数据库/有状态中间件必须管理状态——正确结论是「把状态收拢到专门层」 |
| 3 | 「多线程 = 并发 = 高性能」 | 上下文切换与锁开销真实存在；事件驱动 + 异步 I/O 在高并发连接场景常胜（Nginx/Redis 路线） |
| 4 | 「代码迁移已无价值」 | 强移动性确实退场，但「把计算搬到数据旁」（FaaS 边缘计算、Server-Side Include）是其弱移动形态的延续 |
| 5 | 🔧 原书未覆盖 | **容器镜像分层与镜像分发**（P2P 镜像分发、lazy pulling）、**K8s 调度**对「放置问题」的系统化 |
| 6 | 🔧 原书未覆盖 | **cgroup/namespace 安全边界**的局限与 sandbox（gVisor、microVM）补充；供应链安全对「可移植代码」的新挑战 |
| 7 | 🔧 原书未覆盖 | async 运行时（tokio、io_uring）对「线程 vs 事件」之争的新平衡 |

### 一页速记

- 线程的价值 = 把远端等待与本地计算重叠。
- 虚拟化选层：硬件层（强隔离）/ OS 层（容器）/ 库层（兼容）/ 应用层（语言 VM）。
- 服务器第一问：有状态还是无状态？答案决定容错、缓存与扩展的全部后续。
- 集群分发三招：L4 交换（快）、L7 内容感知（准）、home 转发（粘）。
- 代码迁移四象限：活下来的是「弱移动 × 接收方发起」（Wasm/FaaS）与「基础设施级强移动」（VM 热迁移）。
