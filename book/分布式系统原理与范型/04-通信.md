# 04-通信（覆盖原书第 4 章「通信」）

> **本章地图**：基础知识（分层协议 OSI/Internet 栈；通信类型四象限：瞬时/持久 × 同步/异步）→
> **远程过程调用 RPC**（stub、编组、参数传递、异步 RPC、DCE RPC）→ **面向消息的通信**

## 本章地图

- 本章是全书的「粘合剂」：任何机制（复制、提交、选举）最终都落在这几类通信原语上。
- 组织逻辑 = 三个抽象层次递进：**过程级（RPC）→ 消息级（MQ）→ 流/群组级（流媒体与多播）**。
- 四象限是理解一切通信系统的钥匙：持久性解决「接收方暂时不可达」，同步性解决「调用方等不等」。

## 核心精讲（教学示意，不参与构建）

### 4.1 基础知识
- 分层协议：OSI 七层参考 vs Internet 实际栈（IP/UDP/TCP）；原书强调「中间件位于传输层之上」。
- **通信类型四象限**：
  | | 瞬时通信 | 持久通信 |
  | --- | --- | --- |
  | 异步 | 发完即忘，不等；消息不落存储（UDP） | 中间件存储消息直到送达（MQ） |
  | 同步 | 发送方阻塞到对方收到（RPC 类） | 发送方阻塞到消息入库 |
  - 关键概念：**持久性**针对中间件是否暂存；**同步性**针对发送方是否阻塞——两个正交维度。

### 4.2 远程过程调用（RPC）
- 目标：让跨机调用**看起来像本地过程调用**（访问/位置透明的通信实现）。
- 机制：客户端 stub 打包参数（marshalling）→ 网络传输 → 服务端 stub 解包 → 调用本地过程 → 结果逆向返回。
- **参数传递**：值传递简单；引用（指针）传递需**拷贝-恢复**或不可用；复杂对象（树/图）需序列化协议处理别名。
- **异步 RPC**：立即返回（one-way / deferred synchronous：后续轮询或回调取结果）；
  原书指出：**永远不该有阻塞超过可感知时长的同步 RPC**。
- **DCE RPC**（OSF 分布式计算环境）：接口定义语言 IDL → 生成 stub；端点映射服务（epmapper）动态定位端口；
  跨机全局标识符 UUID——服务定位与版本管理的完整工程范本。
- 🔧 2026 的对应物：gRPC（IDL=proto，HTTP/2 流式）、Thrift——IDL 生成 stub 的思想 40 年未变，
  变的只是传输（HTTP/2、QUIC）与序列化（protobuf）。

### 4.3 面向消息的通信
- **瞬时**：socket（TCP/UDP 编程原语）、MPI（科学计算的高层接口，持久进程组语义）。
- **持久（消息队列系统 MQ）**：
  - 队列模型：发送方→发送队列→中间件存储→接收队列→接收方；支持**离线投递**（收发双方不必同时在线）；
  - 语义要点：至少一次（需幂等）/至多一次/恰好一次（代价最高）；事务消息与确认；
  - 案例：**IBM WebSphere MQ**（原书钦点）：队列管理器、通道、命名队列、多播域。
- 🔧 2026 的对应物：Kafka（日志抽象取代「队列」）、RocketMQ、RabbitMQ、NATS、云上 SQS/PubSub；
  「恰好一次」仍是工程圣杯——通常靠幂等 + 事务性读写组合逼近（Kafka 事务 + 幂等生产者）。

### 4.4 面向流的通信
- 连续媒体（音视频）的关键不是带宽而是**时延抖动与同步**：流间同步（唇音同步）、流内连续性。
- QoS：令牌桶整形、RSVP 预留；传输协议 RTP/RTCP 在 UDP 上做序号/时间戳/丢包反馈。
- 🔧 2026 的视角：WebRTC 实时通信、HLS/DASH 自适应码率把「QoS 预留」替换为「客户端自适应」——
  网络不再承诺，应用自己降级。

### 4.5 多播通信
- **应用层多播（overlay multicast）**：IP 多播部署难 → 在应用层自组覆盖网转发树；节点即路由器。
- **gossip（流行病）数据扩散**：
  - **反熵（anti-entropy）**：周期随机选同伴，交换差量（pull/push/push-pull），最终收敛，O(log N) 轮传播；
  - **谣言散布（rumor spreading）**：热消息推给同伴， gossip s 次后转冷——传播快但可能漏。
  - 特点：无需全局视图、容错极好、代价是冗余消息——适合状态聚合（Astrolabe）、成员管理（SWIM）。

### 通信系统选型的 2026 决策表（补充）

| 需求 | 优先形态 | 代表 |
| --- | --- | --- |
| 低延迟请求-应答 | RPC（二进制、连接复用） | gRPC、Thrift |
| 跨组织松耦合集成 | HTTP/REST + JSON | OpenAPI 生态 |
| 削峰填谷、离线处理 | 持久消息队列 | RocketMQ、RabbitMQ |
| 高吞吐事件流/回放 | 提交日志 | Kafka、Pulsar |
| 海量设备上行 | 轻量 pub/sub | MQTT、NATS |
| 实时音视频 | 专用流协议 | WebRTC/RTP |
- 决策的第一问永远是「要不要应答」与「双方可否离线」——正是原书四象限的两个轴；
  第二问是「消息要不要可回放」——把「队列」升级为「日志」的关键判据。
- **编组（marshalling）的演进脉络**：XDR（DCE RPC）→ Java 序列化（对象图）→ XML/SOAP →
  JSON（人可读）→ protobuf/Avro（schema 化、跨语言）→ Cap'n Proto/FlatBuffers（零拷贝）。
  原书强调的「引用对象不能直接传、别名图要展开」的难点从未消失，只是被 schema 规范化吸收。
- **gossip 的两个变体参数**（补充到 4.5 的记忆点）：
  - 反熵 push / pull / push-pull：push-pull 收敛最快（双方互补差量）；
  - 谣言散布的「转冷」阈值（gossip 概率衰减）：控制冗余消息量与遗漏率的权衡——
    原书未给参数化分析，这是读 SWIM/Prophet 类论文时的前置直觉。
- **RPC 的失败语义清单**（原书散落在 4.2 各处的要点汇总）：
  | 失败点 | 客户端看到什么 | 处理 |
  | --- | --- | --- |
  | 请求未达服务器 | 超时 | 安全重试（幂等前提下） |
  | 服务器执行中崩溃 | 超时/连接断 | 无法区分「没执行」与「执行了」——需要幂等或去重 |
  | 应答丢失 | 超时 | 重试会重复执行 → 至少一次 + 幂等 |
  | 服务器执行后崩溃（应答前） | 超时 | 同上；状态机复制可屏蔽 |
- 这张表解释了为什么「幂等性」是分布式通信的第一纪律，也是 [08-容错与安全.md](08-容错与安全.md)
  可靠 RPC 与去重表的前置知识。

### 一页速记

- 四象限：瞬时/持久 × 同步/异步——所有通信系统的坐标系。
- RPC = 想要本地调用的手感；MQ = 想要时空解耦；gossip = 想要无中心的鲁棒扩散。
- DCE RPC 的遗产：IDL 生成 stub + 端点映射 + UUID——gRPC 的 proto + 服务发现 + request ID 一一对应。
- 流媒体的教训：网络不承诺 QoS 时，应用层自适应（降码率/降清晰度）是唯一可靠的兜底。
- 应用层多播的现实：IP 多播不出内网，于是「人人即路由器」的覆盖网思想演变成今天的 CDN 与消息总线。


## 版本演进

- **第 1 版（2002）**：RPC/MQ 为主，gossip 已有，流媒体章节更重（当时音视频网络是新前沿）。
- **第 2 版（2007，本书）**：强化 gossip 与应用层多播（P2P 热潮），WebSphere MQ 为 MQ 案例；
  流媒体 QoS 仍是完整一节。
- **第 3 版（2017）**：删去面向流的通信与 MPI 细节；新增 RPC 的现代形态与发布-订阅强化。
- **2026 口径**：通信版图 = RPC（gRPC/Thrift）+ 消息流（Kafka/Pulsar）+ 推送（WebSocket/SSE）+
  服务网格 mTLS；RTP/RSVP 内容退到音视频专项；QUIC 重写了「传输层」这一节的全部假设。

## 近年研究与工业界开源实践（2015–2026）

- **QUIC（RFC 9000, 2021）**：UDP 之上的可靠传输，0-RTT 建连、**流级多路复用**（消除 TCP 队头阻塞）、
  内建 TLS 1.3——原书「有连接 vs 无连接」的争论被「连接内多流」终结；HTTP/3 全面铺开。
  - `grpc/grpc`（≈45.3k★，2026-09 实测）：gRPC 核心库，proto IDL + HTTP/2/QUIC，异步 RPC 的当代标准实现；
  - `confluentinc/librdkafka`（≈1.1k★）：C 客户端，Kafka 生态的低延迟实现样本。
- **消息中间件现状**：
  - `apache/kafka`（≈33.8k★）：分布式提交日志；分区=并行单位，消费者组=弹性伸缩单位；
  - `apache/rocketmq`（≈22.6k★）：事务消息与延迟消息的国产代表，与原书 WebSphere MQ 案例直接对照；
  - `rabbitmq/rabbitmq-server`（≈13.9k★）：AMQP 经典，保留「队列 + 路由」的教科书语义；
  - `nats-io/nats-server`（≈20.8k★）：轻量 pub/sub + JetStream 持久化——「瞬时 ↔ 持久」四象限的可调实现。
- **多播与群组**：IP 多播仍限于内网/金融行情；应用层多播的落地形态是 **pub/sub 覆盖网与消息总线**；
  gossip 存活在成员检测（SWIM、Serf）与数据库反熵（Dynamo 风格）中。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「RPC 比消息队列先进/低级」 | 两者解决不同问题：RPC 要**即时应答**，MQ 要**时空解耦**；混合使用是常态（命令走 RPC，事件走 MQ） |
| 2 | 「持久消息 = 可靠消息」 | 持久只保证「不丢在中间件里」；端到端可靠还需确认、重试、幂等（见 [08-容错与安全.md](08-容错与安全.md)） |
| 3 | 「恰好一次投递可以由中间件单独保证」 | 需要接收方幂等或事务性处理配合，否则至少一次 + 重复是常态 |
| 4 | 「应用层多播已无用」 | IP 多播未普及，CDN/push 长连接/SSE 都是其单播化实现；gossip 在成员管理与反熵同步中是主力 |
| 5 | 🔧 原书未覆盖 | **QUIC/HTTP-3**：多流复用、0-RTT、连接迁移（换网络不断连），传输层假设全面更新 |
| 6 | 🔧 原书未覆盖 | **服务网格 mTLS**：加密与身份下沉到 sidecar，应用层 RPC「免代码」获得安全通道（见 [08-容错与安全.md](08-容错与安全.md)） |
| 7 | 🔧 原书未覆盖 | **背压（backpressure）与流控语义**：异步系统的第一公民；原书 QoS 视角重网络预留、轻应用背压 |
| 8 | 🔧 原书未覆盖 | 序列化生态的碎片化（protobuf/avro/json）与 **schema 演进兼容性**管理（消息总线上的版本问题） |

### 本章自测六问（读完自查）

1. 「持久」与「同步」分别约束谁？
   （持久约束**中间件是否暂存消息**；同步约束**发送方是否阻塞**——两轴正交，可组合出四类系统。）
2. RPC 的参数「按引用传递」在跨机时为什么难？
   （指针只在本地地址空间有意义；要么拷贝-恢复（两次全量传输），要么放弃引用语义。）
3. 异步 RPC 的两种取结果方式？（轮询（deferred synchronous）与回调（one-way 通知）。）
4. 消息队列「恰好一次」为什么不可能由中间件单独实现？
   （投递确认与业务处理无法原子：先确认后处理会丢，先处理后确认会重——必须接收方幂等兜底。）
5. gossip 反熵的收敛速度量级？（O(log N) 轮；每轮消息量 O(N·fanout)，靠冗余换鲁棒。）
6. 应用层多播相比 IP 多播的优势与代价？
   （优势：无需网络设备支持、可部署在应用层覆盖网；代价：同一链路可能重复传输、端节点承担转发职责。）
