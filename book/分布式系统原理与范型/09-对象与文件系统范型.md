> **本章地图（上：对象范型，第 10 章）**：从对象到分布式对象 → **Globe**（本书作者 van Steen 团队的
> 代表性案例：分布式动态对象、用户代理/系统代理、定位服务、复制与一致性、容错与安全各一节）→
> 通信：**远程方法调用 RMI**（Java RMI 的对象编组与引用传递）、**CORBA**（IDL、对象引用、DII/DSI）。

> v2 安全缺陷与 v4 修正）→ **Coda**（AFS 后裔：断连操作、AVSG、服务器复制与客户端缓存、
> 事务式会话语义）→ **SMB**（CIFS 会话语义与锁）；文件共享语义谱系（UNIX/会话/事务/不可变文件）。

- 范型部分（Ch10–13）的共同写法：每个范型选**一个代表性系统**贯穿「架构/进程/通信/命名/同步/

- 两者的共同母题：**位置透明 + 缓存一致性**——正好把 Ch1（透明性）与 Ch7（一致性）的原理落到实例上。

## 核心精讲（教学示意，不参与构建）

### 上：基于对象的分布式系统（第 10 章）

#### 10.1 架构与进程
- 对象 = 封装状态 + 接口（方法集）；分布式对象把「远程方法调用」包装成普通方法调用（stub/proxy）。
- **Globe** 的三层对象模型：**用户代理**（应用看到的 stub）+ **系统代理**（实现透明性策略：
  绑定、复制、安全）+ **服务对象**（真正的远程对象）；多个本地对象可与一个远程对象绑定。
- 系统代理是本书「中间件做共性、应用留个性」主张（[02-体系结构.md](02-体系结构.md)）的代码化。

#### 10.2 通信：RMI 与 CORBA
- **Java RMI**：远程接口 extends Remote；对象编组（可序列化对象按值、远程对象按引用传）；
  分布式垃圾回收（引用计数 + 租约）——与 [04-通信.md](04-通信.md) 的 RPC 同源，差异在**引用传递语义**。
- **CORBA**：OMG 的接口定义语言 IDL → 多语言 stub/skeleton；对象引用（IOR）、静态调用、
  动态调用接口 DII 与动态骨架 DSI（网关/适配器场景）；POA（可移植对象适配器）管理对象生命周期。
- 🔧 2026 视角：CORBA 的复杂度（命名服务/交易服务/事务服务的一堆 OMG 规范）正是它衰落的理由；
  gRPC 用「简单 + protobuf + HTTP/2」赢下同样的领地；对象范型的遗产在 gRPC stub 与 actor 框架中。

#### 10.3–10.7 Globe 的命名/同步/复制/容错/安全
- 命名：**Globe 定位服务**——分层定位域树（对照 [05-命名系统.md](05-命名系统.md) 的 home-based 方案），
  叶域内目录节点存「句柄 → 地址」链，迁移/复制时更新路径。
- 复制：系统代理内实现多策略（读-写副本、失效协议、租约），**复制策略可按对象逐个配置**——
  Globule（Ch2 案例）即其 Web 页面版。
- 容错：对象级冗余与失效检测；安全：绑定时的相互认证与安全通道（Ch9 机制的对象化应用）。

### 下：分布式文件系统（第 11 章）

#### 11.1–11.2 架构与进程
- 客户-服务器架构（Sun NFS 的模型：客户端文件系统 + 服务器文件系统，中间 RPC）；
  集群化与 P2P 文件系统（BitTorrent）作对照。
- NFS 组件：**VFS（虚拟文件系统）** 在内核统一本地/远程文件操作；文件句柄（file handle）=
  「文件系统标识 + inode」的不透明引用——把「地址当标识符」的典型（对照 [05-命名系统.md](05-命名系统.md)）。

#### 11.3 通信
- NFS v2/v3 基于 RPC（ONC RPC）：无状态服务器（v3）——读写幂等可重试，服务器崩溃客户端重发即可；
  代价：锁与租约要靠辅助协议（NLM）。
- 🔧 v4 起改为**有状态**（状态 ID + 租约 + compound RPC 合并调用）——为的是一致性语义与防火墙友好，
  是「无状态利容错」原则的著名例外（对照 [03-进程与虚拟化.md](03-进程与虚拟化.md) 的取舍表）。

#### 11.4 命名
- NFS 的**挂载协议**与自动挂载（automounting）：把远程目录挂进本地命名空间，联合命名空间（对照 Ch5 的挂载）；
  v4 用 pseudo file system 统一导出视图。

#### 11.5 文件共享语义
- **UNIX 语义**：写立即对后续读可见（单机不变量）；
- **会话语义**：写对自己的会话可见，关闭文件时传播（AFS/Coda 路线）；
- **不可变文件**：文件一旦创建不可修改（更新 = 新版本）——乐观并发、无锁语义；
- NFS v3 的缓存一致性介于两者之间（AC 属性：actimeo 缓存时效）。

#### 11.6 一致性与复制
- **NFS 客户端缓存**：属性缓存 + 数据缓存，用 actimeo 时效折中（对照 [07-一致性与复制.md](07-一致性与复制.md) 的客户为中心一致性）；
- **Coda**：AVSG（可访问卷存储组）+ 服务器复制（RWV/RW 分组，乐观复制）+ 客户端缓存整卷（venus/vice）；
  断连时用本地缓存继续工作，重连后做**冲突检测与协商**（目录级 CML 重放日志）。

#### 11.7–11.8 容错与安全
- Coda 可用性优先：副本 + 缓存双重冗余，断连即「可用的降级」；NFS 依赖无状态重试（v3）或租约恢复（v4）；
- 安全：NFS v2/v3 的 AUTH_SYS（UID 明文信任）是教科书级反面案例；v4 用 RPCSEC_GSS（Kerberos）修复；
  Coda 用安全通道与能力（对照 [08-容错与安全.md](08-容错与安全.md) 的访问控制）。

### NFS vs Coda vs SMB 三系统对照（原书第 11 章的收束表）

| | NFS（v3/v4） | Coda | SMB/CIFS |
| --- | --- | --- | --- |
| 出身 | Sun，1985 | CMU（AFS 后继） | 微软 |
| 服务器状态 | v3 无状态 / v4 有状态+租约 | 有状态（回调+卷复制） | 有状态（oplock） |
| 缓存单位 | 块/属性 + actimeo 时效 | 整卷（venus 缓存） | 文件 + oplock 委托 |
| 断连支持 | 弱（v4 委派改善） | **强**（设计目标） | 弱（离线文件补丁式） |
| 复制 | v4 pNFS/镜像 | 服务器复制 AVSG | DFS 副本 |
| 一致性折中 | 时效 + 条件请求 | 乐观 + 冲突协商 | oplock 回收 |
- 读法：三列就是「无状态简单 vs 冗余可用 vs 厂商生态」三种取舍，没有全胜者——
  2026 年它们分别在容器 PV、离线优先研究、Windows 生态里各安其位。

### RMI/CORBA/gRPC 三代远程调用对照（原书第 10 章的 2026 续篇）

| | Java RMI | CORBA | gRPC |
| --- | --- | --- | --- |
| 接口描述 | Java 接口 | IDL（多语言） | proto（多语言） |
| 传输 | JRMP | IIOP（ORB 总线） | HTTP/2（+QUIC 趋势） |
| 序列化 | Java 序列化 | CDR | protobuf |
| 对象引用 | 远程引用 | IOR | 无对象引用（服务+方法） |
| 生态教训 | 绑死 JVM | 规范过全、互操作碎片 | 简单、云原生默认 |
- 教训一句话：**「远程引用 + 分布式 GC」这条路被放弃**——gRPC 刻意退回「无状态方法调用」，
  因为对象生命周期跨进程管理（引用计数/租约回收）的复杂度远超其收益。

## 版本演进

- **第 1 版（2002）**：CORBA 全套案例 + NFS/Coda 并重；Globe 已是 van Steen 团队主打。
- **第 2 版（2007，本书）**：对象章**聚焦 Globe**（CORBA 压缩为通信一节）；文件章保留 NFS/Coda/SMB 三案例。
- **第 3 版（2017）**：**整章删除对象范型**（CORBA 死亡、RMI 并入 RPC 叙述）；文件系统章改为
  「Distributed file systems」聚焦 NFS 与 Google File System 两端。
- **2026 口径**：对象范型 → RPC/服务框架（gRPC、Thrift）与 actor 模型（Orleans/Akka）；
  文件范型 → **分布式块/对象存储**（GFS→Colossus、HDFS、Ceph、S3 生态）与云原生并行文件系统，
  「POSIX 语义的远程挂载」退守 NAS 场景。

## 近年研究与工业界开源实践（2015–2026）

- **GFS→Colossus 与对象存储的统治**：GFS（SOSP 2003）之后 Google 内部演进为 Colossus
  （分布式元数据 + 更弹性分片，公开资料确认其存在与「取代 GFS」的事实，细节未完整公开）；
  开源生态的对应物：
  - `apache/hadoop`（HDFS，star 未核验）：GFS 的开源直译，批处理时代主力；
  - `ceph/ceph`（star 未核验，量级 10k+）：CRUSH 无中心元数据 + 统一块/对象/文件三种接口；
  - **对象存储（S3 语义）** 成为 2026 年事实存储 API：`minio/minio`（star 未核验）、
    云厂商对象存储——「文件系统范型」的重心从 NFS 挂载转向 HTTP 对象接口。
- **NFS 的现状**：NFS v4.2 仍在企业 NAS/容器持久卷（PV）里服役；性能敏感场景让位给
  分布式块存储 + 本地文件系统组合。
- **对象范型的遗产**：
  - gRPC/Thrift（见 [04-通信.md](04-通信.md)）承接远程方法调用；
  - **actor 模型**：`microsoft/orleans`（虚拟 actor，star 未核验）、`akka/akka`（star 未核验）——
    「分布式对象」以 actor 身份复活（透明引用被有意放弃，改为显式地址，正是原书透明性争论的裁决）；
- **客户端缓存的现代形态**：Alluxio/JuiceFS 类「缓存层 + 对象存储」组合把 Coda 的
  「本地缓存 + 远程副本」搬到云上（`alluxio/alluxio`、`juicedata/juicefs`，star 未核验）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「NFS v3 的无状态设计过时了」 | 无状态换来崩溃简单恢复；v4 改有状态是为语义（锁/委派），代价是状态恢复协议复杂——这是取舍不是优劣 |
| 2 | 「CORBA 失败是因为技术不够强」 | 恰恰相反：规范过全（事务/事件/交易服务全都要），接口膨胀 + 互操作碎片化；gRPC 的胜利是「少即是多」 |
| 3 | 「分布式对象的远程引用应该完全透明」 | 网络分区下透明引用的调用语义无法定义；actor/微服务用显式寻址 + 显式失败，是工程对透明性的修正 |
| 4 | 「Coda 的断连操作只是学术玩具」 | 它是离线优先（offline-first）应用、边缘设备同步与「本地缓存 + 云端协调」的直接思想源头 |
| 5 | 🔧 原书未覆盖 | **GFS→Colossus、HDFS 之后的存储栈**：元数据服务（Master/NameNode/Placement Driver）成为分布式文件系统的真核心 |
| 6 | 🔧 原书未覆盖 | **对象存储 S3 语义**与 POSIX 兼容层的折中（JuiceFS/Alluxio/GooseFS）：目录语义、强一致元数据、缓存回收 |
| 7 | 🔧 原书未覆盖 | **云原生挂载**：CSI 驱动、NFS-as-PV、卷快照与备份——文件系统范型的容器时代交付形态 |
