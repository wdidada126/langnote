## 本章地图

- 原书本章是 2007 年最完整的一致性教科书叙述，其谱系表至今仍是理解 CRDT/Raft/Spanner 的地图。
- 核心张力：**一致性越强，副本间通信越多，可用性与延迟越差**——CAP 的具体化。

## 核心精讲（教学示意，不参与构建）

### 7.1 引言：一致性的三种来源
- 数据项在 R 个副本上，「读操作必须读到最近写的值」这句话在分布式下**本身就不良定义**（哪个「最近」？），
  于是发展出一系列可实现的模型。
- 决定一致性强度的两要素：**操作的排序要求** + **读写可见性要求**。

### 7.2 以数据为中心的一致性模型
| 模型 | 约束 | 直觉 |
| --- | --- | --- |
| 严格一致 | 写即刻全局可见 | 需要绝对全局时间，不可实现 |
| **线性一致（atomic）** | 结果等价于某次「实时顺序」的串行执行 | 单机错觉的极限，成本最高 |
| **顺序一致** | 等价于某个全局顺序，但不必与实时时间吻合 | 进程各自视角的顺序保持即可 |
| 因果一致 | 有因果关系的写全序，无关写可乱序 | 只对「有故事关系」的操作排序 |
| FIFO（PRAM）一致 | 同一进程的写按序可见，跨进程可乱序 | 因果一致的放宽版 |
| 最终一致 | 停止更新后最终收敛 | 没有中间不变量，最弱 |
- 判别工具：**同一进程的操作序 + 消息因果**——向量时钟（[06-同步.md](06-同步.md)）是验证这些模型的实现基础。
- **两个易混点辨析**（读谱系表时最容易错的）：
  - 「顺序一致 ≠ FIFO 一致」：顺序一致要求存在**跨所有进程**的一个全局序；
    FIFO 只管单进程自己的写按序可见，不同进程的写可任意交错——FIFO 弱得多。
  - 「因果一致 ⊃ FIFO」：FIFO 是因果一致的特例（只保留「同进程写」的因果链），
    因果一致还要保住「读后写」「写后读」等跨进程因果链。
- 原书用「并发程序设计中的内存一致性」类比多处理机顺序一致（Lamport 1979 的概念移植到分布式副本）。

### 7.3 以客户为中心的一致性
- 目标：保证**同一客户**在多副本间切换时看到连贯历史：
  1. **单调读**：客户读到的值不会「回退」；
  2. **单调写**：客户自己的写按序生效；
  3. **读己之写**：自己写的值自己总能读到；
  4. **写后读（writes-follow-reads）**：读过某值后，后续写必须基于不早于该值的状态。
- 实现思路：客户端绑定「会话」并携带版本信息（如读到的时戳），把请求路由到满足条件的副本。
- 工业映射：**Dynamo（SOSP 2007）** 的会话保证、MySQL 读写分离的「读己之写」（粘性路由/延迟阈值）、
  Cassandra 的 R+W>N quorum 调参。

### 7.4 副本管理
- **放置问题三段**：
  1. **永久副本**（permanent replicas）：初始分发点（CDN 源站、数据库主库）；
  2. **服务器发起副本**（server-initiated）：按负载/请求密度动态加节点（CDN 边缘节点、动态缓存）；
  3. **客户发起副本**（client-initiated）：客户端缓存（浏览器缓存、client-side cache）。
- 服务器放置算法：拓扑感知选举（K-希望树：聚合节点度量、按层级选 K 个候选）——CDN 扩容的教科书算法。

### 7.5 一致性协议
- **主备份（primary-based）**：
  - **远程写协议**：所有读写走 primary，primary 顺序转发给备份——简单、易线性/顺序一致，主是瓶颈；
  - **本地写协议**：副本可以是主（迁移式所有权，写完再传播），支持移动/断连场景（Coda 用它）。
- **复制写（replicated-write）**：
  - **主动复制**：每个副本执行同样的操作序列（需要全序广播）——Ch8 状态机复制的入口；
  - **法定数（quorum）**：读 N_R 个 + 写 N_W 个副本，约束 N_R + N_W > N（读写相交保证读到新值）、
    N_W > N/2（写相交保证写序）——ROWA（读一写全部）是 N_W=N、N_R=1 的特例；加权投票支持非对称放置。
  - 🔧 quorum 交集保证的是「读到最新**已写完**的版本」，不等于线性一致——还取决于读写与提交时序。
- **quorum 参数的现实调节**（原书投票协议的工程展开）：
  | 配置 | 读性能 | 写性能 | 语义 |
  | --- | --- | --- | --- |
  | ROWA（R=1, W=N） | 极高 | 极低（写全副本） | 读新值易、写慢且被慢副本拖死 |
  | R=W=N/2+1（对称） | 中 | 中 | 强一致偏好 |
  | R=1, W=1（无交集） | 极高 | 极高 | 只剩最终一致（Dynamo 默认可调） |
  - Cassandra 的可调一致性（ONE/QUORUM/ALL）就是这张表的产品化；
    W+R>N 的「相交」只是必要条件——**读到最新已提交值还要求写提交的顺序性**，
    这正是 Jepsen 屡次验证「quorum ≠ 线性一致」的原因。
- **高速缓存一致性**：客户端缓存的失效/租约/回调协议（GMS 总结、写直达 vs 写回）——
  连到 [09-对象与文件系统范型.md](09-对象与文件系统范型.md) 的 NFS/Coda 缓存。

### 一致性模型谱系的判定练习（补充）

- 给定四个读操作序列，判断各模型是否允许（教学示意）：
  - P1: W(x)a → P2: R(x)a → P3: R(x)0（P2 读到 a 之后 P3 读到旧值 0，且无因果链连接 P2/P3）；
  - 判定：违反**单调读**（若 P2、P3 同一客户）、违反**FIFO**？——不是（不同进程写）；
    满足**因果一致**（读到的顺序无因果要求）、不满足**顺序一致**（全局序中 R(x)a 必须在 W(x)a 后，
    P3 的读在其后仍读到旧值即矛盾）。
- 这种「用反例卡模型」的练习是掌握谱系表最快的方法；原书 7.2 的图例（六张时序图）就是为此设计，
  建议每张都自己推一遍。
- **一致性谱系 × 实现协议对照**（本章两大节的合流点）：
  | 目标模型 | 实现协议（7.5） | 典型系统 |
  | --- | --- | --- |
  | 线性一致 | 主备份（远程写）+ 共识定序 | Spanner、etcd、ZooKeeper |
  | 顺序一致 | 主备份（顺序由 primary 定） | NFS v4（文件级近似） |
  | 因果/最终 | gossip 反熵 + 版本向量 | Dynamo、Cassandra |
  | 客户为中心 | 会话粘性 + 版本令牌 | Dynamo 会话、读写分离代理 |
  | 复制写收敛 | quorum / CRDT 合并 | Riak、协同编辑 |

## 版本演进

- **第 1 版（2002）**：一致性模型谱系已成型；副本管理与协议分节同本版。
- **第 2 版（2007，本书）**：与 Dynamo 论文同年，最终一致 + 客户中心一致性被系统化；quorum 与主动复制并存叙述。
- **第 3 版（2017）**：章名对调为「Replication and Consistency」，新增 **CRDT** 与乐观复制（OPODIS/SSS 2011 论文）；
  事务级一致性（串行化、快照隔离）仍不在本章（属于数据库教材的领地）。
- **2026 口径**：一致性实现的主流是**共识分组**（Multi-Raft/Multi-Paxos）承载线性一致 + 事务；
  弱一致场景用 CRDT/事件溯源；验证工具是 Jepsen 黑盒测试——原书的「模型谱系」仍是理解它们的地图。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「最终一致 = 随便读写」 | 最终一致只承诺收敛；读己之写等会话保证需要显式设计（粘性路由/版本令牌），否则用户看到「自己提交的评论消失」 |
| 2 | 「quorum（N_R+N_W>N）= 线性一致」 | quorum 只保证读写集相交；要线性一致还需读写与提交的实时约束（Jepsen 曾验证 Cassandra 调成 quorum 仍非线性一致） |
| 3 | 「主动复制只要全序广播就行」 | 还需确定性执行（所有副本对同一序的副作用一致）——非确定性（随机、系统时间）必须屏蔽或日志化 |
| 4 | 「因果一致比顺序一致『慢一点但差不多』」 | 二者是不同的可实现的模型档位，因果一致允许无关写乱序，实现代价远低；混淆会导致语义判断错误 |
| 5 | 🔧 原书未覆盖 | **CRDT 家族**（计数器/寄存器/集合/序列）与合并函数设计；协同编辑的并发控制完全绕开了原书协议分类 |
| 6 | 🔧 原书未覆盖 | **Multi-Raft/Multi-Paxos 分组**：把「单组主备份」扩展为「上千个小分组」+ 调度器平衡，是 2026 强一致存储的主流形态 |
| 7 | 🔧 原书未覆盖 | **一致性级别的黑盒验证**（Jepsen/Elle）、以及「无迹可寻（stale read）」类异常的判定框架 |
| 8 | 🔧 原书未覆盖 | **事务与一致性的交叉**：快照隔离、串行化与副本一致性的关系原书未涉（见 [08-容错与安全.md](08-容错与安全.md) 的 2PC 与数据库教材） |

### 本章自测六问（读完自查）

1. 严格一致为什么被公认为「不可实现」？（需要绝对全局时间且写操作零延迟可见——任何实现都有传播延迟。）
2. 顺序一致与线性一致的唯一差别？（是否要求等价顺序与**实时时间**吻合；顺序一致只要求存在某个全局序。）
3. 「读己之写」在读副本架构里怎么实现？
   （会话粘到主库/带版本的副本路由；例如写后短期内强制读主，或携带写入时戳过滤陈旧副本。）
4. 本地写协议（主可迁移）适合什么场景？（移动/断连设备：在哪写就把所有权带到哪——Coda 的复制即此。）
5. 主动复制与主备份在「故障切换时丢不丢已确认请求」上的差别？
   （主动复制多数派已确认不丢；主备份取决于备份同步点，可能在切换时回退。）
6. 客户发起副本（缓存）与服务器发起副本（CDN 节点）的一致性责任方有何不同？
   （缓存由客户端负责失效/时效；服务器副本由服务方主动推送与回收——责任与信任模型不同。）
