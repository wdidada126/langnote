## 章定位与中心论题

"平面（plane）"在基础设施语汇里指**横切所有数据路径的公共层**（控制平面/数据平面之分）。
⚠️ 据此推定本章主张：流应当升格为数据栈的**一等平面**——介于存储层与应用层之间的
"在途数据公共层"：同一份 changelog 同时供给（a）持续查询/物化视图（第 4/5 章）、
（b）push 服务（第 3 章）、（c）湖仓落地（第 8 章）、（d）他系统触发（第 7 章混合体们），
替代今天各链路各自拉取的"影子复制"。

## 逐节精读重构（⚠️ 章级）

### 9.1 问题：流今天藏在缝隙里

- 现状：流数据被拆在 Kafka 主题、CDC 工具、ETL 调度、各消费组 offset 之间；
  **没有统一的"流目录"**（谁发布什么 schema、谁消费到哪个位点、哪份物化视图依赖哪条流）；
- 于是血缘断裂、重放无门、schema 演化各自为战——这是第 1 章三跳架构的运维侧账单。

### 9.2 流式平面的构成件（⚠️ 本目录按通用架构语汇整理）

| 构件 | 职责 | 既有对应物 |
| --- | --- | --- |
| 统一日志/目录 | 流的命名、schema、留存、位点 | Kafka + Schema Registry（⚠️ 未装） |
| 流上的表 | changelog⇄表无损转换 | #228 06 对偶；Paimon/Iceberg 表格式 |
| 持续查询层 | 注册式增量维护 | 本册第 4/5 章 |
| 服务分发 | push 订阅 + pull 索引 | 本册第 3 章 |
| 治理钩子 | 血缘/质量/权限随流走 | Data Catalog 语境（姊妹波书目） |

### 9.3 与"数据平面/控制平面"的家族相似

- 网络史的教训挪用 ⚠️（推定本书有此类比）：平面化=把散落各设备的策略上提为可编程公共层；
  流式平面的对手是"每个业务管道自己焊策略"（过滤、重试、对账全在作业代码里）；
- 与 Data Mesh 的关系（本目录平衡观点）：Mesh 管**所有权**，平面管**通路**；
  两者正交，可互为落地件（见衔接节）。

### 9.4 流式数据库=平面的计算心脏（⚠️ 本书推定论点）

若流是一等平面，则"消费流并持续产出可服务视图"的引擎就是平面的 CPU：
第 5 章定义在 9 章升维为架构纲领——**从"一个产品"改写成"一层公共基础设施"**。
这也解释了本书把 Materialize/RisingWave/ksqlDB 混称"streaming databases"的分类学动机。

### 9.5 风险清单（本目录补充，非原文）

平面化的经典风险：单点心智（全体依赖一个日志的运维等级）、
schema 政治（谁有权改公共流）、以及"平面漂移"（plane creep——什么都能塞进流的诱惑）。

## 🔧 概念演示：一条 changelog 喂四个消费者（sqlite3 3.45.3 触发器，非流引擎）

单表 journal 追加一次，四个"平面出口"（聚合视图/明细快照表/通知表/物化文件表）
由触发器同事务各自派生：

```sql
CREATE TRIGGER fanout AFTER INSERT ON journal BEGIN
  INSERT INTO agg(k,s,c) VALUES (NEW.k,NEW.v,1)
    ON CONFLICT(k) DO UPDATE SET s=s+NEW.v, c=c+1;                -- 持续查询
  INSERT INTO audit VALUES (NEW.off, NEW.k, NEW.v);                -- 湖仓落地类比
  INSERT INTO notify(reason,snapshot) VALUES ('j'||NEW.off, NEW.k); -- push 服务
END;
```

🔧 实测输出（原样，`ch9_demo.py`，SQLite 3.45.3）：

```text
agg: [('a', 4, 2), ('b', 2, 1)]
audit rows: 3 notify rows: 3
after rollback agg: [('a', 4, 2), ('b', 2, 1)] | audit: 3 | notify: 3
```

解读：插 3 行，聚合出口/审计出口/通知出口三路同时各得其所；再演回滚——第四条插入被撤销时
**三路派生一并撤销**——"一次事实、多路派生、原子一致"即 9.2 表格的最小可用样片；
真实平面还要把 AUTOINCREMENT offset 换成可重放的持久日志与**各消费者独立的位点**
（上例三路共享同一事务，消费端不存在"慢半拍"问题——那正是 9.5 与第 3 章订阅游标的分界）（🔧 演示结论）。

## 核心概念速览（中英对照）

- **流式平面** — streaming plane：把流升格为横切数据栈的公共一等层（章题 ✅，外延 ⚠️ 重构）
- **平面** — plane：控制/数据/计算横切层的基建语汇（9.3）
- **影子复制** — shadow copies：各链路私拉自蒸造成的隐形多份数据（9.1）
- **流目录** — stream catalog：流的命名/schema/留存/位点的统一注册表（9.2）
- **一次事实多路派生** — fact once, fan-out many：平面化的收益原型（🔧 演示）
- **消费位点** — consumer offset/cursor：重放与断线续读的锚（9.2/第 3 章）
- **在途数据** — data in flight：介于"已落地"与"已消费"之间的状态（9.1）
- **通路 vs 所有权** — plumbing vs ownership：平面与 Mesh 的正交分工（9.3）
- **平面心脏** — compute heart of the plane：流式数据库在纲领中的定位（9.4 ⚠️）
- **分类学动机** — taxonomy motive："streaming databases" 一词的圈地行为（9.4）
- **平面漂移** — plane creep：公共流过载一切的熵增风险（9.5）
- **schema 政治** — schema governance：公共流的变更权力结构（9.5）
