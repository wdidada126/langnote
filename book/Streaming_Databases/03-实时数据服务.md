## 章定位与中心论题

算得快不等于用得上：实时分析的最后一公里是**把结果以合适 latency/吞吐/新鲜度交付给消费者**。
本章把"服务"拆成两个正交问题：**谁发起**（服务端 pull：消费者现问现查；客户端 push：结果变了主动到）
与**多快到账**（同步：请求路径内出结果；异步：事件/回调/订阅）。⚠️ 推定本书以 ksqlDB 的
pull/push 双模式为原生样本，以"流式数据库 + 应用订阅"为终局形态。

## 逐节精读重构（⚠️ 章级）

### 3.1 pull 与 push 的根本不对称

- **pull**（`SELECT ... FROM mv WHERE key=?`）：实现简单（就是查表）、消费者主导速率、
  但**新鲜度受轮询频率限制**、空闲时也耗成本、规模化要索引/缓存伺候；
- **push**（`SELECT ... EMIT CHANGES` / subscribe）：变化即刻送达、天然事件驱动、
  但消费者要有订阅管理（连接、背压、断线重放、乱序）、服务端要维护每个订阅的增量游标；
- 语义根源（接 #228 06/08 章）：pull 读的是**表的某个快照**，push 订阅的是**该表的 changelog**——
  push 查询其实是"把流表对偶的反方向开放给终端消费者"。

### 3.2 服务层架构菜单（⚠️ 重构目录）

| 方案 | 新鲜度 | 延迟 | 运维税 | 典型 |
| --- | --- | --- | --- | --- |
| 计算写回 KV/关系库 | 一个作业周期 | 毫秒 | 双系统一致性 | Kafka Streams→MySQL/Redis/Cassandra |
| 结果主题（push 事件化） | 逐条 | 毫秒 | 消费者端组装状态 | Flink→Kafka topic→WS/SSE |
| 原生 pull（引擎内表） | 实时 | 毫秒~ | 局部性/索引受限 | ksqlDB pull + locality |
| 原生 subscribe | 实时 | 毫秒 | 订阅生命周期 | Materialize/RisingWave subscribe |
| 交互式重查 | 实时 | 百毫秒~ | 全算成本 | Trino/Presto 直查湖表（对照组） |

### 3.3 同步 vs 异步服务

- **同步**：请求路径内完成"读现成结果"（不能等计算！）→ 一切预计算/物化都是为同步服务买的时间；
- **异步**：Webhook/推送/批量文件→对新鲜度更宽容但要求幂等消费与重试语义（→ 第 6 章）；
- ⚠️ 推定本书提出"同一份物化视图两种消费法"：能忍轮询用 pull，不能忍变化用 push，
  **别为了 5% 的场景把 95% 的接口 push 化**（本目录认同的平衡观点）。

### 3.4 服务质量的三件套

新鲜度（staleness bound）、尾延迟（p99）、可用性降级（读旧快照还是读错值）：
⚠️ 本书大概率强调"物化视图天然带来可声明的 staleness 契约"，比"现查算到超时"更可运维。

## 🔧 演示：一次写入同时喂 pull 与 push（sqlite3 3.45.3 触发器，非流引擎）

mv_total 是"物化结果"；pull=直接 SELECT；push=触发器把每次变化**快照追加**进 notify 主题表：

```sql
CREATE TABLE notify(seq INTEGER PRIMARY KEY AUTOINCREMENT, reason TEXT, snapshot TEXT);
CREATE TRIGGER push_ai AFTER INSERT ON orders BEGIN
  UPDATE mv_total SET s = s + NEW.amount;
  INSERT INTO notify(reason,snapshot)
    SELECT 'order-'||NEW.oid, (SELECT json_object('total', s) FROM mv_total);
END;
```

🔧 实测输出（原样）：

```text
pull 现值: 65
push 订阅流: (1, 'order-1', '{"total":10}')
push 订阅流: (2, 'order-2', '{"total":30}')
push 订阅流: (3, 'order-3', '{"total":65}')
```

解读：pull 一次拿终值（消费者主导）；push 流含**全部中间态**（服务端主导，seq 即订阅游标≈Kafka
offset）；两者共享同一维护逻辑，无二次同步——这就是"流式数据库同时服务两类消费者"的最小骨架（🔧 演示结论）。

## 核心概念速览（中英对照）

- **pull 查询** — pull query：消费者发起的即席读，读表快照
- **push 查询** — push query / subscribe：消费者订阅视图 changelog，变化主动送达
- **EMIT CHANGES** — ksqlDB 的 push 子句：流式结果的语法标志
- **新鲜度契约** — staleness bound：可声明的"最多旧多久"SLA
- **同步服务** — synchronous serving：请求路径内出结果，依赖预计算
- **异步服务** — asynchronous serving：事件/回调交付，要求幂等与重试
- **订阅游标** — subscription cursor：notify.seq/offset，断线重放之锚
- **背压** — backpressure：push 侧消费者慢时反压生产端的机制
- **局部性** — locality：把 pull 路由到持有分区状态的节点（ksqlDB 专属权衡）
- **结果主题化** — results as topics：把物化视图变更再发布成 Kafka 主题的解耦法
- **降级语义** — degrade-to-stale：故障时读旧快照优于读错值
- **最后一公里** — serving tail：计算到用户体验的链路尾段，本书三段论第三段
