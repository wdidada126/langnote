## 章定位与中心论题

流式数据库不是孤岛：实时化压力让**每个数据系统都长出对方的器官**。⚠️ 推定本章按
"从哪跨界到哪"盘点四类混合体——OLTP+流、实时 OLAP+流、湖仓+流、批引擎+流——
并论证第 5 章边界辨析（vs 实时 OLAP）在混合现实中需要的修正系数。

## 逐类精读重构（⚠️ 章级）

### 7.1 数据库长出流器官（OLTP → changelog-first）

- PostgreSQL `REFRESH MATERIALIZED VIEW CONCURRENTLY`、pg_ivm 扩展（✅ GitHub API 活跃至 2026-09）、

### 7.5 混合的代价

每个跨界器官都自带**双重人格税**：两套一致性心智、两套伸缩曲线、两套值班手册。

## 🔧 演示：递归不动点的"全量 vs 增量"（DuckDB 1.5.5，批式，非流引擎）

7.2/7.3 的共同数学：物化闭包=递推不动点。给关系图维护传递闭包 `closure`，
新增边 `w→v` 时只沿**新边的可达祖先**传播 delta，与全量重算对账（脚本 `demos2.py`）：

🔧 实测输出（原样）：

```text
D1 closure before: 6 pairs
D2 delta(new pairs via w->v): [('x', 'v'), ('y', 'v'), ('z', 'v')]
D3 merged==full recompute: True | sizes: 10 10
```

解读：递归查询也能"增量维护"（只补 3 对而非重算 10 对）——实时 OLAP 的连续聚合、
湖仓物化视图刷新、流式数据库的递归算子共享同一数学；但收敛式增量的**终止条件检测**
在引擎里远比 demo 昂贵（多轮 delta 直到空集），这是递归类持续查询少被产品化的原因（🔧 演示结论）。

## 核心概念速览（中英对照）

- **混合数据系统** — hybrid data system：为实时目标长出他类系统器官的数据引擎
- **边界带** — boundary band：品类之间无法画线的渐变竞争区（7.2 结论）
- **CDC 升格** — CDC as public API：redo/WAL 对外暴露为订阅接口（7.1）
- **连续聚合** — continuous aggregation：OLAP 阵营的增量物化近亲（7.2）
- **流式表格式** — streaming table format：Paimon/Iceberg/Delta 的 changelog 化（7.3）
- **节奏带** — cadence band：分钟级（湖仓微批）vs 毫秒级（逐条维护）的保鲜分工
- **日志层两端吸收** — log absorbs semantics：表化+湖化的 Kafka 系路线（7.4）
- **双重人格税** — hybridity tax：两套心智/伸缩/运维的隐性成本（7.5）
- **枢纽定位** — hub claim：流式数据库作实时中枢、他系统为源汇（⚠️ 本书推定立场）
- **不动点** — fixpoint：递归查询的语义核心（🔧 演示 D）
- **delta 传播** — delta propagation：只沿新变化推进的增量范式（演示 D）
- **物化闭包** — materialized transitive closure：图/层级数据的持续维护样例
