# 04 · 契约生命周期与执行——版本、兼容与 CI 守门

> 主题重构册声明：本章章题为笔记作者编排，非原书目录（见 `00` §4）。内容基底=契约工件通用工程实践 ✅（可实证部分）+ 本书主题线 ⚠️。

## 4.1 契约的生命周期状态机

契约不是静态文件，其头段 `status` 字段（ODCS ✅）承载状态机：**draft → active → deprecated → retired**，配一条不可逆规则：只有 active 可被新产品引用，deprecated 仍可消费但目录页挂黄牌，retired 后引用即 CI 红灯。状态迁移的工程含义：

- **draft→active**：首次发布，消费者从此可信。
- **active 内变更**：走 4.2 兼容矩阵；破坏性变更=新 major 契约并存（4.3）。
- **active→deprecated**：给出迁移窗口（以新鲜度/SLA 字段公告）。
- **→retired**：接口下线，目录条目保留墓碑（血缘查询仍可达）。

## 4.2 兼容性矩阵：谁改字段谁付钱

| 变更 | 对读方（消费者） | 对写方（生产者） | 判定 |
|---|---|---|---|
| 加可选列 | 无感（忽略未知列） | 需回填策略 | 向后兼容 ✅ |
| 加必填列 | 旧消费者违约 | 新行才有值 | 破坏 ⚠️ |
| 删列/改名 | 查询列消失即炸 | — | 破坏 ✗ |
| 收紧值域/类型 | 旧合法数据变违约 | 历史数据需豁免 | 破坏（对存量）⚠️ |
| 放宽值域 | 无感 | 校验成本 | 兼容 ✅ |

规则：**结构兼容看读写方向，语义兼容看存量数据**——改名+别名视图可把"破坏"降级为"两段式兼容"（先加新列双写，再删旧列）。

## 4.3 版本化策略：契约 URN 里的 major.minor

ODCS 的 `id` URN 含版本槽（3.2 表 ✅，实例 `urn:dp:climate:obs:1`）。策略要点：

1. **major 变更=新契约对象**，旧契约进 deprecated，两接口并行供数（双写窗口）；目录同时展示两版并标注迁移建议。
2. **minor 变更=原地更新**，指纹（🔧-J）变化触发订阅者通知，但兼容性由 CI 判定器背书（4.4）。
3. **消费者钉版本**：消费方锁 `major`，自动升 `minor`——与包管理 semver 心智一致。

## 4.4 CI 守门：违约在合并前死亡

流水线三道门（⚠️ 主题级，工件通用）：

- **门1 契约 lint**：schema-of-schema 校验（ODCS 官方 JSON Schema 可机检 ✅），无主/缺质量段直接拒。
- **门2 兼容判定**：契约 diff 过 4.2 矩阵，破坏性变更未升 major 即红。
- **门3 数据实测**：对候选发布数据跑契约质量表达式（🔧-K 形态），违约率超阈值即红——**契约测的是数据不是文件**。

运行时第四道（发布后）：数据面持续巡检 + 违约事件回灌目录页（06 章观测线）。

## 4.5 🔧 类比实验组（SQLite/DuckDB 本机实测，**非本书平台行为**）

**🔧-M 加列兼容（读方无感）**：`ALTER TABLE readings ADD COLUMN quality TEXT DEFAULT 'A'` 后，旧视图 `v_readings`（只选 ts,value）实测仍返回 `[('2026-10-01', 21.5)]`（E4）——**加列不破坏既有接口**的直接证据。

**🔧-N 删列破坏（引擎替你拉闸）**：`ALTER TABLE readings DROP COLUMN ts` 实测被拒：`error in view v_readings after drop column: no such column`（E4）——SQLite 因视图依赖拒绝破坏性演化；真实平台里没这么幸运，需要 4.4 的兼容判定器代劳。

**🔧-O 双版本并存**：`obs_v1(ts,value)` 与 `obs_v2(ts,value,quality)` 两视图同表并行，实测各自返回 `[('2026-10-01',21.5)]` 与 `[('2026-10-01',21.5,'A')]`（E10）——major 并行=同一底座两个接口投影。

**🔧-P 只读发布面防"消费者回写污染"**：消费者以 READ_ONLY 挂 DuckDB 域库，INSERT 实测报 `Cannot execute statement of type "INSERT"`（E5）——生命周期纪律的物理兜底：违约只可能来自生产侧。

## 4.6 违约处置手册（运行期）

1. **定性**：数据违约（存量脏）vs 契约违约（演化失配）vs 消费者违约（越权用法）——三者回写目标不同（域 backlog / 版本流程 / 接入策略）。
2. **止损排序**：隔离违约分区 > 回滚发布 > 降级读旧版本（4.3 钉版本让降级有路）。
3. **信用记账**：违约事件累计进产品页 SLA 达成率（07 章度量输入）；**连续违约的契约应被目录降权**，否则市场劣币驱逐良币。

## 4.7 本章要点回写

1. 状态机+URN 版本+双写窗口=契约可演化的三支柱。
2. 兼容判定必须区分读写方向与存量数据；改名可用别名视图两段式消化。
3. 三道 CI 门+运行巡检：契约的价值在执行，不在文件。
4. 🔧 实证：引擎约束能拦结构破坏（🔧-N），拦不了语义漂移——语义层要人守。
5. 华氏/摄氏教训（4.8 T8）：值域内的语义违约是契约三层分工存在的理由，结构门全绿≠数据可信。
6. 判定器自身要版本化：它是治理代码不是无状态工具，否则历史 diff 结论随判定器漂移（4.9）。

## 4.8 演化实录：obs 产品两年时间线（⚠️ 重构示例）

| 时点 | 事件 | 走的通道 | 工件变化 |
|---|---|---|---|
| T0 | v1 发布：station/temp_c/obs_date | active | URN `...:obs:1`，指纹 F1 |
| T3月 | 新增 `quality` 可选列 | minor | 兼容判定=绿（🔧-M 形态）；指纹 F2，订阅者收 diff 通知 |
| T8月 | 发现 `temp_c` 混入华氏存量 | 数据违约 | 隔离 2 月分区重刷；契约加语义行"单位摄氏，T5–T7 存量豁免至 T14" |
| T12月 | 机构 B 要求按小时粒度 | major 评估 | 判定：新模型非破坏（独立产品更优）→ 立 `obs-hourly:1` 新产品而非 v2 |
| T18月 | 日粒度产品并入 hourly 视图 | deprecated | 迁移窗口 6 个月，目录页黄牌+账单提醒 |
| T24月 | v1 下线 | retired | 接口关、墓碑留（血缘可查）；双写窗口成本在 T12 已预算 |

三条教训：**语义违约比结构违约更晚暴露**（T8 的华氏混入在 CHECK 值域内！[-100,100] 拦不住 21℃ 写成 70℉）——防线只能是语义层+交叉验证；**"要不要开 v2"先问"是不是新产品"**；**deprecated 的账单提醒比邮件通知有效**（消费者自己的成本可见）。

## 4.9 兼容判定器的最小逻辑（伪码）

```
diff(old, new):
  for 字段变更 c:
     if c in {删列, 改类型收紧, 必填化, 值域收紧}: → BREAKING
     if c in {加可选列, 值域放宽, 描述修订}:      → MINOR
     if c == 改名:                               → 两段式(先 MINOR 加别名, 后 BREAKING 删旧)
  if any BREAKING and new.major == old.major:    → CI 红灯
```

判定器本身要版本化（它变了会让历史 diff 结论漂移）；边界案例集中营：日期格式收紧、枚举增值（对读方 MINOR、对写方 BREAKING——**方向敏感**是 4.2 矩阵的实现核心）。
