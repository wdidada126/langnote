# 04 表存储（原书 ch5 Table Storage）

> 状态标注：⚠️ = SQL Server 引擎二手转述（本机不可实测）；✅ = Microsoft Learn 现行文档（写前 curl -sL 200）；🔧 = 本机 SQLite/DuckDB 类比，**非本书 SQL Server 引擎行为**。

## 一、本章地图

一行数据在 8KB 页里到底长什么样？堆与聚集索引表的空间行为有何不同？本章解剖行格式、页内布局、三种分配单元（行溢出/LOB），并量化"页分裂税"。

- 2A 行格式：状态位/长度/固定列/列偏移数组/NULL 位图
- 2B 变长列、定长列与行大小上限
- 2C 堆（Heap）：无聚集索引的表及其查找代价
- 2D 三种分配单元：IN_ROW / ROW_OVERFLOW / LOB_DATA
- 2E FORWARDING 指针与堆上的更新

## 二、核心精讲（⚠️ 转述）

### 2.1 行的物理布局（⚠️）

一行在页内由若干段构成：状态位 A/B（记录是否变长、是否被前移）、**固定长度部分**（int/datetime 等）、**变长列偏移数组**（每变长列 2 字节，列数超阈值再加一个短整型计数）、**NULL 位图**（哪些列是 NULL）、然后是列数据本身。变长列（varchar/nvarchar/varbinary 实际只占用到的长度 + 2 字节偏移）。行首还挂一个 2 字节长度，页尾 slot 数组用 2 字节指向行首（⚠️）。

- 单行上限：固定+变长列合计不能超过约 8060 字节（页内不能塞下就触发溢出，见 2.4）。
- 行最小开销：即使全 NULL 也有状态/长度/偏移等元字节。

### 2.2 堆（Heap）（⚠️）

**没有聚集索引**的表即堆。堆不保证物理或逻辑顺序，`SELECT *` 顺序未定义；定位某行靠 **RID（File:Page:Slot）** 或扫描。堆的优势是高并发纯插入无聚集键竞争；劣势是任何"按内容找行"都是全表扫描，且更新可能把行"前移"到新页留 FORWARDING 桩（⚠️，2008 用 `sys.dm_db_database_page_allocations` 观察；无聚集索引时非聚集索引行存 RID 指向堆）。

### 2.3 聚集索引表 = "表即索引"（⚠️）

一旦建聚集索引，表数据就按聚集键组织成 B+ 树叶子（详见 [05-索引内部结构与管理.md](05-索引内部结构与管理.md)）。此时"行"存在索引页里，堆与聚集表是同一空间账本的两种形态。

### 2.4 行溢出与 LOB（⚠️）

超过页内可容纳的变长数据：

- **ROW_OVERFLOW 单元**：`varchar(max)/nvarchar(max)/varbinary(max)` 及超阈值列，部分留在 IN_ROW 页、尾部溢出到 ROW_OVERFLOW 页，用 16 字节指针（TIMESTAMP+长度+文件/页/偏移链）串联。
- **LOB_DATA 单元**：`text/image/varchar(max)` 大对象可整块放 LOB 分配单元（⚠️；2008 新 `max` 类型逐步取代旧 text/image）。

> 与 [02-数据库与数据库文件.md](02-数据库与数据库文件.md) 的三级分配单元呼应：IN_ROW/ROW_OVERFLOW/LOB_DATA 就是"HOBO 分配单元"三兄弟（⚠️）。

## 三、🔧 类比实验 E3：顺序 vs 随机聚集键插入的页分裂税（非本书 SQL Server 引擎行为）

行/页布局本机不可测 SQL Server，但"聚集键顺序决定插入局部性"这一通识，用 SQLite INTEGER PRIMARY KEY（即 rowid 聚集）可量化：

```text
# 本机 python sqlite3 3.45.3，20000 行，page_size=4096
顺序主键插入：0.01s / 141 页 / 577536 B
随机主键插入：0.02s / 156 页 / 638976 B   （多 15 页、约 60KB 碎片）
```

观察：随机聚集键把新行散插到各处，逼出大量**页分裂**，页更松散、总页数上升；顺序键则页填得满。这正是 SQL Server 反复告诫"聚集键宜递增/窄、避免 GUID 随机聚集"背后的通用机制（⚠️ SQL Server 结论为转述，数字来自 SQLite 类比）。

## 五、要点与检查清单（⚠️）

- 选聚集键：窄、稳定、递增（identity/序列）优于随机 GUID（2008 无 `NEWSEQUENTIALID` 聚集最佳实践时尤其）。
- 堆并非"不能管理"：定期重建堆可回收 FORWARDING/碎片（但重建期不可用）。
- `varchar(max)` 未必总溢出：短值仍留在 IN_ROW，超 8000 字节才走 ROW_OVERFLOW/LOB。
- 列数极多的表：NULL 位图与偏移数组开销上升；宽表谨慎（⚠️）。

## 六、行大小与"8060"边界推演（⚠️）

一页 8KB=8192 字节，减去页头 96 与 slot 数组，实际可放约 8060 字节的行内容。若一条 UPDATE 让行超出所在页剩余空间：

1. 整行迁到新页，原位置留 **FORWARDING STATS 桩**（堆上），RID 不变以免破坏非聚集索引（⚠️）。
2. 变长部分超阈值 → 溢出到 ROW_OVERFLOW 页，IN_ROW 留 16 字节指针。
3. LOB → LOB_DATA 分配单元整块存放。

这就是"行格式 + 三分配单元"协同的落点，也是 SQL Server 能把"超过一页的大对象"塞进单个逻辑行的原因。

## 七、🔧 补充：用 SQLite 看"行大小→页占用"（非本书引擎行为）

```sql
-- 定长窄行 vs 变长宽行，同样 5000 行占多少页（page_size=4096）
CREATE TABLE narrow(k INTEGER PRIMARY KEY, n INT);
CREATE TABLE wide  (k INTEGER PRIMARY KEY, blob BLOB);  -- blob 每行 ~2000B
-- 观察 page_count：wide 因行大、每页装得少，页数显著更多
```

对照 SQL Server：行越宽/越大，每页行数越少、页链越长，扫描 IO 越多；这与"页是 IO 原子"一脉相承（⚠️ 类比，SQL Server 数字须以实测库为准）。

## 八、堆 vs 聚集表：选型推演（⚠️）

- **纯高速插入、按扫描/批量消费、几乎不点查**：堆有优势——无聚集键维护成本、无插入热点页竞争（⚠️，如日志落地区、ETL 暂存）。
- **按主键点查、范围扫、需要稳定物理序**：聚集表——一次定位沿 B+ 树直达叶子行。
- **代价对比**：堆每次点查是全扫或依赖非聚集索引回 RID；聚集表插入要为键顺序付出页分裂税（见 E3 🔧）。
- **混合现实**：2008 常见反模式是给堆加一堆非聚集索引却仍用 RID 定位，堆上一旦发生 FORWARDING，非聚集索引跳转成本上升（⚠️）。

## 九、常见问答（FAQ）

1. **问：一个表能有几个聚集索引？** 答：0 或 1——聚集索引就是表本身，只能有一种物理序（⚠️）。
2. **问：堆能"转"成聚集表吗？** 答：在其上建唯一/聚集索引即把堆重塑为 B+ 树表（重建，锁与日志代价大，⚠️）。
3. **问：`varchar(max)` 一定在 LOB 页吗？** 答：不一定；短值仍留在 IN_ROW 行内，仅超阈值才外溢（⚠️）。
4. **问：FORWARDING 桩能消除吗？** 答：重建堆（或加聚集索引）可消除；否则每次前移都可能留桩（⚠️）。
5. **问：SQLite 数字能当 SQL Server 行大小结论吗？** 答：不能；E3/E7 仅演示"顺序局部性/行大→页多"的通用机制。

## 核心概念速览（中英对照）

- 行格式 — Record Format：状态位/固定列/变长偏移数组/NULL 位图/数据的组合。
- NULL 位图 — Null Bitmap：标记哪些列为 NULL 的位压缩结构。
- 变长列偏移 — Variable-length Column Offset：定位每变长列边界的 2 字节项。
- 堆 — Heap：无聚集索引的表，行无序、靠 RID 定位。
- RID — Row Identifier：File:Page:Slot 三元组，堆行的物理坐标。
- FORWARDING 桩 — Forwarding Stub：堆行前移后原地留下的跳板，保持 RID 稳定。
- 分配单元 — Allocation Unit (LOB/ROW_OVERFLOW/IN_ROW)：按数据大小分层的空间账本。
- 行溢出 — Row Overflow：变长数据超页容纳时外溢到专用页。
- LOB — Large Object：text/image/(max) 大对象，独立 LOB_DATA 单元。
- 聚集索引表 — Clustered Table：表数据按聚集键组成 B+ 树叶子。
- 8060 上限 — 8060-byte row limit：单行 IN_ROW 可用的字节上界（⚠️）。
- FILLFACTOR — Fillfactor：索引页预留空闲以缓解放置期分裂的比例。

## 最新演进与工业实践

- 行存储骨架稳定：SQL Server 2022 仍用同一页/行格式；但 **vardecimal 存储**、宽表列压缩等优化在数仓向场景（列存）中替代行存热点，见 [06-特殊存储与特殊索引.md](06-特殊存储与特殊索引.md)。
- 2016+ 默认 `varchar(max)`/JSON 承载半结构化，替代旧 `text/image`；2008 时 `max` 类型刚落地（⚠️ 版本边界）。
- 聚集键 GUID 之害已成工业共识：改用 `NEWSEQUENTIALID`/BIGINT 自增；此建议在 #36/#68 排错册反复出现。
