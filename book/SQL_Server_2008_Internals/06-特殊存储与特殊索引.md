# 06 特殊存储与特殊索引（原书 ch7 Special Storage + ch8 Special Indexes）

> 状态标注：⚠️ = SQL Server 引擎二手转述（本机不可实测）；✅ = Microsoft Learn 现行文档（写前 curl -sL 200）；🔧 = 本机 SQLite/DuckDB 类比，**非本书 SQL Server 引擎行为**。

## 一、本章地图

"行式 B+ 树"不是万能。本章是 2008 给行式世界观打的补丁集：稀疏列、FILESTREAM 大对象、分区；以及特殊索引：筛选索引、XML、全文。**注意版本边界：2008 尚无列存储索引、无内存优化表**（Hekaton 是 2014，CCI 是 2012 预览/2014 GA），故本章对列存/内存表一律 ⚠️ 前向引用 #56/#71，不在 2008 语境臆造。

## 二、核心精讲：特殊存储（⚠️）

### 2.1 稀疏列 Sparse Columns（⚠️）

`SPARSE` 属性：把"绝大多数为 NULL"的列从每行的 NULL 位图里抽出，改存到行尾"稀疏集合"，仅对**非 NULL** 值记录（列名+值）。列越多 NULL 越省空间，代价是每个非空值要多存一个列 ID。2008 用它支撑大型宽表（如 EAV 场景）与后来的表类型基础（⚠️；具体 SPARSE 官方页本机不可达，仅以 Learn [Execution plans](https://learn.microsoft.com/en-us/sql/relational-databases/performance/execution-plans) 等 200 通页为查询侧准绳）。

### 2.2 FILESTREAM / FILETABLE（⚠️ 版本提醒）

FILESTREAM（2008 引入）让 `varbinary(max)` 大对象**直接落 NTFS 文件**、由 SQL Server 事务与句柄统一管，绕过 T-SQL 分块读大 BLOB 的低效——把"最大 2GB 的 BLOB"交给文件系统流式访问（⚠️）。FILETABLE 是 2012 才在 FILESTREAM 上加的"以 Windows 文件语义看表"层（⚠️ 前向引用 #56，2008 无）。

### 2.3 表分区 Partitioning（⚠️）

按分区函数（边界值）+ 分区方案（映射到多文件组）把一张表/索引**水平切分**成多个分区，每分区各自 B+ 树叶子、可放不同文件组/盘。收益：`$PARTITION` 定位、分区交换（`SWITCH` 秒级搬数据）、维护可按分区做（⚠️）；成本：所有索引必须"对齐"到同一分区边界否则退化。承接 [02-数据库与数据库文件.md](02-数据库与数据库文件.md) 的文件组放置。

## 三、核心精讲：特殊索引（⚠️）

- **筛选索引 Filtered Index（2008 新增）**：带 `WHERE` 谓词的"子集索引"，只索引满足条件的行（如 `WHERE IsActive=1`），比全表非聚集索引更小、统计更准（⚠️）。
- **XML 索引**：主 XML 索引把 XML 实例拆成路径/值/节点的 B+ 树（primary + secondary PATH/PROPERTY/VALUE），让 `query()`/`exist()` 免于每次解析整段 XML（⚠️）。
- **全文索引 Full-Text**：由独立的**全文引擎**建倒排目录（词→文档），`CONTAINS`/`FREETEXT` 走词项匹配而非 LIKE 扫（⚠️，与列存/倒排概念同源，见下方 DuckDB 🔧）。

✅ 官方口径：[Clustered and Nonclustered Indexes Described](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described)（含筛选索引讨论）。

## 四、🔧 类比实验 E6：列存扫描/段消元（呼应 2012+ 列存；非本书 SQL Server 2008 引擎行为）

2008 **没有**列存储索引，但为了理解"为什么后来要加列存"，用 DuckDB（纯列存）量化列式对分析型扫描的优势（⚠️ 明确：SQL Server 2008 行存无此能力）：

```text
# 本机 duckdb 1.5.5，2M 行表 t(id, cat, v)
谓词扫描  WHERE cat=42            -> 0.002s（仅读 cat 列 + zone-map）
分组聚合  GROUP BY cat            -> 0.009s
连接+聚合 JOIN 2M×3M 后 avg        -> 0.055s
尾部段消元 WHERE id>1999000        -> 0.0006s（min/max 元组跳过整段）
```

对照：列存只读所需列 + 按段（row group）的 min/max 做**段消元**，扫描/聚合比行存"整页整行搬运"少几个数量级 IO——这正是 2012 之后 SQL Server 引入 CCI 的动机。本实验数字来自 DuckDB，**非 SQL Server 2008**；SQL Server 2008 上这些查询都走行存 B+ 树（⚠️）。

## 六、要点与检查清单（⚠️）

- 稀疏列只对"高 NULL 密度"划算；非空多反而更占空间。
- 分区不是万能：查询若跨全部分区反而更慢；须看裁剪（partition elimination）能否生效。
- 筛选索引谓词要与查询谓词匹配才命中；隐式类型转换会让筛选索引失效。
- FILESTREAM 受 Win32 句柄/事务上下文约束，T-SQL 内更新大 BLOB 仍受 TransactSQL-only 访问模式限制。
- 版本纪律：2008 无列存/内存表/FILETABLE，写任何"2008 有 CCI"都是错的（⚠️ 硬边界）。

## 七、🔧 补充：用 SQLite 看"NULL 多→省空间"（非本书引擎行为）

```sql
-- 稀疏化直觉：大量 NULL 列是否比大量非空值更省页？（page_size=4096）
CREATE TABLE dense  (a INT, b INT, c INT);           -- 全填非空
CREATE TABLE mostly (a INT, b INT, c INT);           -- 仅 a 非空、b/c 恒 NULL
-- 灌等行数后比 page_count：mostly 每行更短、页数更少
```

对照 SQL Server：普通列的 NULL 仍占 NULL 位图 + 偏移；`SPARSE` 才把 NULL 彻底移出。SQLite 无 SPARSE，但演示"NULL 不写值→行更短→页更省"的底层直觉（⚠️ 类比，非 SPARSE 实现）。

## 八、常见问答（FAQ）

1. **问：2008 能建列存储索引吗？** 答：不能。CCI 是 2012 预览 / 2014 GA，本册一律 ⚠️ 前向引用。
2. **问：分区表一定是"性能魔法"吗？** 答：否；需查询能分区裁剪，且索引对齐；否则维护与扫描可能更重（⚠️）。
3. **问：筛选索引能替代 WHERE 过滤吗？** 答：它只索引子集；对不满足谓词的行仍须扫描/其他索引（⚠️）。
4. **问：FILESTREAM 和 IMAGE 列的区别？** 答：FILESTREAM 把 BLOB 交 NTFS 流式、受事务管；旧 IMAGE 塞在 LOB 页里（⚠️）。
5. **问：DuckDB 数字能当 SQL Server 列存结论吗？** 答：不能；2008 无列存，仅用 DuckDB 演示列式为何快。
6. **问：SPARSE 列有上限吗？** 答：一张表稀疏列数量有上限（数百级，依行大小），超了建表失败（⚠️）。
7. **问：XML 主索引能省掉解析吗？** 答：省一半——路径/值/节点已建 B+ 树，但 XML 实例本身仍在 LOB/ROW_OVERFLOW；次级索引在主索引之上（⚠️）。
8. **问：全文索引和 LIKE %...% 谁快？** 答：LIKE 是暴力扫，全文走倒排词表；但全文受独立引擎异步更新（⚠️）。

## 九、分区滑动窗口实战（⚠️）

以"按天/月分区 + 归档"为例（工业最常见）：

1. 左端 `SPLIT RANGE` 加新分区（承接最新日期）；右端 `MERGE RANGE` 与 `SWITCH OUT` 联手最老分区。
2. 分区表与"结构同构的普通表"通过 `SWITCH PARTITION n TO TABLE staging` **元数据搬迁**——秒级、不搬数据，前提是分布对齐、约束一致（⚠️）。
3. 归档：staging 表再 `BACKUP` 或直接迁冷存；主表始终只留热窗（⚠️）。
4. 索引必须**对齐**（aligned）分区边界，否则 `SWITCH` 报"索引不对齐"错误，且每分区索引各自维护（⚠️）。

> 关键：分区的价值不是"让 SELECT 变快"，而是**把维护/归档/滑动窗口从"数据搬运"降级成"元数据操作"**。

## 十、要点：特殊存储/索引选型表（⚠️）

| 场景 | 选什么 | 为什么 |
| --- | --- | --- |
| 大量 NULL 的宽表 | SPARSE 列 | NULL 移出位图，行更瘦 |
| >1MB 大对象频繁读写 | FILESTREAM | NTFS 流式访问、事务管 |
| 时间冷热明显、按月归档 | 分区表 + 文件组 | SWITCH 元数据搬迁 |
| 只查活跃行 | 筛选索引 WHERE IsActive=1 | 索引更小、统计更准 |
| 半结构化文档 | XML 列 + 主/次 XML 索引 | 免每次解析整段 |
| 自然语言词项检索 | 全文索引（倒排） | 词→文档 O(log) |
| 分析型扫描/聚合 | 2008 无解 → 迁 #56 CCI（2012/2014） | 列式+段消元 |

## 核心概念速览（中英对照）

- 稀疏列 — Sparse Column：把高 NULL 密度列移出 NULL 位图、只存非空值。
- FILESTREAM：把 varbinary(max) 交给 NTFS 文件流、纳入 SQL 事务管理。
- FILETABLE（2012）：以 Windows 共享文件夹语义呈现的 FILESTREAM 表 ⚠️ 前向引用。
- 表分区 — Table Partitioning：按边界把表/索引水平切成多个分区。
- 分区消除 — Partition Elimination：查询仅触达相关分区，跳过其余。
- 分区交换 — SWITCH：把整块表/分区以元数据操作秒级并入/拆出。
- 筛选索引 — Filtered Index：带谓词、只索引行子集的非聚集索引。
- XML 主/次索引 — Primary/Secondary XML Index：把 XML 拆成路径/值/节点树加速 XQuery。
- 全文索引 — Full-Text Index：外置倒排目录，词项级 CONTAINS/FREETEXT。
- 列存储索引 — Columnstore Index（2012/2014）：按列分段存储 + 段消元 ⚠️ 非 2008。
- zone-map — Zone Map：按段 min/max 元数据在扫描时跳过整段（列存类比）。
- 内存优化表 — Memory-Optimized Table（2014 Hekaton）：常驻内存、无闩锁结构 ⚠️ 非 2008。
