# 03 日志与恢复（原书 ch4 Logging and Recovery）

> 状态标注：⚠️ = SQL Server 引擎二手转述（本机不可实测）；✅ = Microsoft Learn 现行文档（写前 curl -sL 200）；🔧 = 本机 SQLite/DuckDB 类比，**非本书 SQL Server 引擎行为**。

## 一、本章地图

"先写日志、后改数据"（WAL）是数据库可靠性的第一性原理。本章讲 SQL Server 事务日志的结构（LSN/VLF）、检查点、以及重启/单页/完整库三种恢复剧本，并区分三种恢复模型。

- 2A WAL 与最小日志直觉
- 2B 日志文件、VLF（Virtual Log File）环
- 2C LSN、日志序列与"页最小 LSN"
- 2D 检查点（Checkpoint）与 dirty page 刷盘
- 2E 恢复三阶段：分析 / 重做(redo) / 撤销(undo)
- 2F 完整 / 大容量日志 / 简单三种恢复模型

## 二、核心精讲（⚠️ 转述）

### 2.1 WAL 与日志结构（⚠️）

任何修改在脏页落盘前，**描述该修改的日志记录必须先持久化**（write-ahead logging）。日志物理上存在 `.ldf` 文件里，逻辑上被切成若干 **VLF（Virtual Log File）**，按环形复用：日志空间写满后，只有"已提交且其脏页已被检查点刷盘"的 VLF 才能被截断（log truncate）回收（⚠️）。VLF 过多/过大都会拖慢日志管理，是 2008 运维经典调优点。

✅ 官方口径：[The Transaction Log](https://learn.microsoft.com/en-us/sql/relational-databases/logs/the-transaction-log-sql-server)。

### 2.2 LSN 与页最小 LSN（⚠️）

每条日志记录有全局递增的 **LSN（Log Sequence Number）**。每个数据页头存"该页当前内容对应的最小 LSN"。恢复时据此判断：磁盘上的页比日志旧到什么程度，需不需要重放。**日志是真相之源**——只要日志完整，页可以落后。

### 2.3 检查点（⚠️）

检查点把"脏页清单"里被改过的页写回磁盘，并在日志记一条 checkpoint 记录，从而划定"这之前的修改都已安全落盘"的界限。重启时无需重放检查点之前的日志，大幅缩短恢复时间。恢复间隔（recovery interval）目标由实例配置驱动（⚠️）。

### 2.4 恢复三阶段（⚠️）

启动或联机还原时，SQL Server 对日志做（依 ARIES 式思想，见 [../../db/ARIES.md](../../db/ARIES.md)）：

1. **分析（Analysis）**：从最近检查点扫日志，建 dirty page 表与活跃事务表。
2. **重做（Redo）**：正向重放，把所有页（含已提交与未提交的）恢复到崩溃那一刻的最新状态（forward restore）。
3. **撤销（Undo）**：反向回滚崩溃时仍未提交的事务，写补偿日志记录（CLR）。

### 2.5 三种恢复模型（⚠️）

- **完整（FULL）**：日志直到备份才截断，支持时点恢复（PITR）。
- **大容量日志（BULK_LOGGED）**：最小化大容量操作日志，省空间但牺牲部分 PITR 粒度。
- **简单（SIMPLE）**：检查点后自动截断可复用日志，不能做日志备份/时点恢复。

✅ 官方口径：[View or Change Recovery Model](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/view-or-change-the-recovery-model-of-a-database-sql-server)。

## 三、🔧 类比实验 E4：journal vs WAL 文件形态（非本书 SQL Server 引擎行为）

SQLite 的两种持久化模式，正好演示"WAL 语义、检查点、脏页刷盘"的通识（SQL Server 只有一种统一事务日志，⚠️，无 SQLite 式双模式）：

```text
# 本机 python sqlite3 3.45.3，200 行插入后观察落盘文件
journal_mode=DELETE  -> 主库 8192 B + 临时 -journal 文件 4616 B（回滚式）
journal_mode=WAL     -> 主库 4096 B + -wal 8272 B + -shm 32768 B（追加式）
```

观察：WAL 模式把改动**追加**到 `-wal`，主库保持较小、由 checkpoint 把 WAL 内容合并回主库——与 SQL Server"日志追加 + 检查点刷脏页 + 截断可复用 VLF"在思想上同构（⚠️ 类比，非同一实现）。数字来自本机，不代表 SQL Server。

## 五、要点与检查清单（⚠️）

- 简单模型下"日志满"多因长事务/未提交阻止截断，非真没空间。
- FULL 模型必须配定期日志备份，否则 `.ldf` 无限增长。
- 大量 VLF（数千）会拉长启动恢复；应预配日志初值、固定增长步长。
- 崩溃恢复期间数据库不可用：recovery 时间预算要纳入高可用设计。
- `DBCC CHECKDB` 是结构一致性审计（非"恢复到某时点"），见 [09-备份与还原.md](09-备份与还原.md)。

## 六、恢复剧本推演（⚠️）

- **重启恢复**：实例崩溃或正常停机后启动，对每个带活动的库走 分析→重做→撤销，直到检查点线；用户看到"Recovery is writing a checkpoint"即此段（⚠️）。
- **单页/页修复（Page Restore）**：只坏了几页时，还原对应文件的一部分并从日志重放该页所属 LSN 区间，库其余保持联机（⚠️，需 FULL）。
- **完整库时点恢复**：还原全库备份 → 顺次还原差异 → 顺次还原所有日志备份到某个标记/时间点，最后 `RESTORE ... WITH RECOVERY` 触发 undo（⚠️，与 [09-备份与还原.md](09-备份与还原.md) 协作）。

## 七、日志为何"只增不减"直到截断（⚠️）

日志不能像数据文件那样"就地擦除"，因为 VLF 是环形：头部未截断的 VLF 仍可能被恢复/副本依赖。只有当某 VLF 内所有事务（a）已提交、且（b）其脏页已被检查点刷盘、且（c）在 FULL 下已被日志备份覆盖——该 VLF 才进入"可复用"状态。任一条件不满足（常见：长事务未提交、日志备份停摆、复制/AG 未读完），日志就会持续增长（⚠️）。

## 八、🔧 补充实验：检查点与 WAL 合并（非本书 SQL Server 引擎行为）

```text
# SQLite WAL：观察 checkpoint 把 -wal 合并回主库、wal 尺寸回落
PRAGMA journal_mode=WAL;
-- 灌若干写事务后：-wal 明显增长
PRAGMA wal_checkpoint(FULL);     -- 强制把 WAL 内容合并回主库（类比"检查点刷脏页"）
PRAGMA integrity_check;          -- 合并后仍 ok，体现 WAL→主库一致性
```

对照：SQL Server 的检查点是周期/自动的、把 dirty page 刷盘并划恢复线；SQLite `wal_checkpoint` 是把 -wal 页并回主文件——两者都是"把追加式日志的改动固化到数据载体"的同类动作（⚠️ 类比）。数字来自本机，不代表 SQL Server。

## 九、常见问答（FAQ）

1. **问：删数据文件能靠日志救回吗？** 答：不能凭日志"重建"文件；日志只保证已写事务不丢，文件缺失须靠备份还原（⚠️）。
2. **问：为什么简单模型不能时点恢复？** 答：检查点后日志即截断复用，缺少连续日志链可重放到任意时刻（⚠️）。
3. **问：崩溃恢复卡在 Undo 怎么办？** 答：多为超长未提交事务；2019+ ADR 缓解，旧版只能等回滚完成（⚠️）。
4. **问：SQLite 能替代理解 SQL Server 日志吗？** 答：只能类比 WAL/checkpoint 通识；VLF 环、页最小 LSN、三阶段恢复是 SQL Server 特有，一律 ⚠️ 转述。

## 核心概念速览（中英对照）

- 前滚日志 — Write-Ahead Logging (WAL)：日志先于脏页落盘的持久化法则。
- 日志序列号 — LSN：日志记录的全局递增坐标。
- 虚拟日志文件 — VLF：日志文件内的逻辑分段，环形复用单位。
- 日志截断 — Log Truncate：回收已备份/已落盘日志空间（非删除文件）。
- 检查点 — Checkpoint：把脏页刷盘并划恢复界限的动作。
- 脏页 — Dirty Page：被改但尚未写回磁盘的缓存页。
- 分析阶段 — Analysis Phase：崩溃恢复第一步，建脏页/活动事务表。
- 重做 — Redo：正向重放日志到最新状态。
- 撤销 — Undo：回滚未提交事务，写补偿记录。
- 补偿日志记录 — CLR (Compensation Log Record)：标记回滚动作的日志。
- 完整恢复模型 — Full Recovery Model：可日志备份、可时点恢复。
- 大容量日志模型 — Bulk-Logged：最小化大容量日志，牺牲 PITR 粒度。
- 简单恢复模型 — Simple Recovery Model：检查点自动截断，无日志备份。
- 时点恢复 — Point-in-Time Recovery (PITR)：恢复到备份链中任一时刻。

## 最新演进与工业实践

- WAL/检查点/三阶段恢复骨架至今不变；SQL Server 2019+ 引入 **加速数据库恢复（Accelerated Database Recovery, ADR）**，把长事务回滚从"重启阻塞"改为持续清理，显著改善本章"撤销阶段拖慢启动"的痛点（✅ [ADR](https://learn.microsoft.com/en-us/sql/relational-databases/accelerated-database-recovery-concepts)）。
- 2016+ **始终加密/日志相关**运维工具化，VLF 诊断脚本（如 Paul S. Randal 团队与社区的 `fn_dblog`/`DBCC LOGINFO` 用法）成工业标配（⚠️ 转述）。
- 恢复模型与高可用绑定：Always On 可用性组要求 FULL + 日志备份；✅ [Always On AGs](https://learn.microsoft.com/en-us/sql/database-engine/availability-groups/windows/always-on-availability-groups-sql-server)。
