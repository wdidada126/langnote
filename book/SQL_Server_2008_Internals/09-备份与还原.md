# 09 备份与还原（原书 ch14 Backup and Restore）

> 状态标注：⚠️ = SQL Server 引擎二手转述（本机不可实测）；✅ = Microsoft Learn 现行文档（写前 curl -sL 200）；🔧 = 本机 SQLite/DuckDB 类比，**非本书 SQL Server 引擎行为**。
> 版本提醒：本章是 **2008 内幕卷独有的"Inside Backup and Restore"**；2012 内幕卷把备份章移出、换成 DBCC Internals——故此章在四册谱系里是 2008→2012 的"消失的章"，见 [00-总览与阅读地图.md](00-总览与阅读地图.md) 第五节。

## 一、本章地图

备份=可重放的副本，还原=把副本+日志链重放到目标状态。本章讲三支柱（完整/差异/日志）、备份链与尾日志、恢复模式如何约束这一切，并接 [03-日志与恢复.md](03-日志与恢复.md) 的恢复三阶段。

## 二、核心精讲（⚠️）

### 2.1 三种备份（⚠️）

- **完整备份（Full）**：整库（数据+部分日志）的基线，链的起点。
- **差异备份（Differential）**：自**上次完整备份以来**所有被改的"扩展盘区（EA, Differential Bitmap）"——注意是相对最近 FULL，而非相对上次差异，故差异只增不减（⚠️）。
- **日志备份（Transaction Log）**：截获自上次日志备份以来的活动日志段并**顺带截断**已提交日志（这是 FULL 模型下回收 `.ldf` 空间的唯一途径，⚠️）。

✅ 官方口径：[Recovery Model](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/view-or-change-the-recovery-model-of-a-database-sql-server)；[The Transaction Log](https://learn.microsoft.com/en-us/sql/relational-databases/logs/the-transaction-log-sql-server)。

### 2.2 备份链与时点恢复（⚠️）

还原序列 = Full → (Diff 取最新一个) → 顺次所有 Log 备份 → 尾日志（Tail-Log Backup）→ `RESTORE WITH RECOVERY`。`STOPAT '时间'` / `STOPATMARK`/`STOPBEFOREMARK` 实现**时点恢复（PITR）**。任一环节断链（缺一个日志备份）整条只能退到最近完整点（⚠️）。

### 2.3 恢复模式与备份能力矩阵（⚠️）

- **FULL / BULK_LOGGED**：可日志备份、可 PITR；BULK_LOGGED 最小记录大容量操作、PITR 粒度受限。
- **SIMPLE**：检查点自动截断，只能整库/文件级还原，无 PITR。
矩阵决定了运维节奏：FULL + 定期日志备份 + 定期完整 + 差异。

### 2.4 备份的完整性与校验（⚠️）

`BACKUP ... WITH CHECKSUM` 让备份自带页校验和，还原时 `RESTORE ... WITH CHECKSUM` 检出损坏；`BACKUP ... TO MIRROR TO` 多目标镜像抗介质故障；`VERIFYONLY`/`RESTORE HEADERONLY` 只读元数据快速验（⚠️）。备份**不等于**"库没坏"——它防介质/误删，不防逻辑损坏复制到备份，故须配 `DBCC CHECKDB` 一致性审计（见下方 🔧）。

## 三、🔧 类比实验 E5：一致性审计（呼应 DBCC CHECKDB；非本书 SQL Server 引擎行为）

2008 的 `DBCC CHECKDB` 会遍历全库页、重建索引结构校验分配/完整性/一致性——重且长。SQLite 提供同类"全库一致性审计"的轻量对照：

```text
# 本机 python sqlite3 3.45.3，5000 行库
PRAGMA integrity_check;  -> ok    （逐页/逐索引结构一致性遍历，类比 CHECKDB）
PRAGMA quick_check;      -> ok    （不建索引重扫，类比 CHECKDB PHYSICAL_ONLY 思路）
```

对照：`integrity_check` 会检查 B 树结构、页链接、外键，返回 `ok` 或列出损坏——目标与 `DBCC CHECKDB`"发现物理/逻辑不一致"同构；但 SQL Server CHECKDB 还交叉校验 IAM/GAM 分配一致、且会隐式对 tempdb 建快照旁路加锁（⚠️ 转述）。数字来自本机，不代表 SQL Server。

## 四、还原选项与可用性（⚠️）

- `WITH RECOVERY`：完成还原并回滚未提交（对外可访问）。
- `WITH NORECOVERY`：保持"还原中/正在还原"状态，以便继续接日志备份——链式还原关键（⚠️）。
- `WITH STANDBY`：只读备用（log shipping 目标、镜像见证），让还原库可读又不结束链（⚠️）。
- 文件/页级还原：坏页用 `RESTORE DATABASE ... PAGE` 局部修复，库其余联机（承接 [03-日志与恢复.md](03-日志与恢复.md) 单页恢复）。

> 高可用衔接：2008 的 **数据库镜像（Database Mirroring）** 用日志流把主体实时同步到镜像（`SAFETY FULL` 同步可自动故障转移，⚠️）；2012 起被 **Always On 可用性组** 取代（✅ [Always On AGs](https://learn.microsoft.com/en-us/sql/database-engine/availability-groups/windows/always-on-availability-groups-sql-server)，前向引用 #56/#71）。

## 六、要点与检查清单（⚠️）

- 备份三件套 + 定期日志备份是 FULL 模型的铁律；缺日志备份 → `.ldf` 暴涨。
- 差异是"相对 FULL"：一次差异还原会跳过更早差异，别按"链"理解错。
- 尾日志备份：还原前先备当前活日志，才能 PITR 到崩溃点。
- 备份放对地方 + CHECKSUM + 异质介质；没验证过的备份不算备份（`RESTORE VERIFYONLY`）。
- 版本纪律：2008 无 Always On AG（2012），只有镜像/日志传送（⚠️ 硬边界）。

## 七、日志传送与镜像的角色（⚠️）

- **Log Shipping**：`BACKUP LOG → COPY → RESTORE WITH STANDBY` 循环，主库故障时把备库 `RESTORE WITH RECOVERY` 上线；RPO 分钟级、无需共享存储、无自动故障转移（⚠️）。
- **Database Mirroring**：主体把日志流实时推给镜像；`SAFETY FULL` 同步模式（见证服务器在场则自动故障转移），`SAFETY NONE` 异步高吞吐但 RPO>0；镜像**只读不可查**（2008 无"读取意图副本"），要读只能靠日志传送的 STANDBY 备（⚠️）。
- 与可用性组的定位差：**镜像=库级、日志传送=库级批、AG=实例级、多库共享事务日志流 + 只读副本**（⚠️；AG 属 2012，前向引用 #56/#71）。

## 八、备份策略：RPO/RTO 权衡（⚠️）

| 目标 | 手段 | 权衡 |
| --- | --- | --- |
| RPO≈0（少丢数据） | FULL 模型 + 高频日志备份 + 同步镜像 | 备份/网络成本上升 |
| RTO 短（快速上线） | 差异备份 + 副本常驻 | 备机硬件成本 |
| 归档 PITR 长期 | 完整+日志链 + 归档存储 | 存储成本、链维护复杂 |
| 大容量批量 | BULK_LOGGED + 大批 BACKUP+RESTORE | PITR 粒度受损 |

工业实践：常见"日完整 + 每 6h 差异 + 每 10–15min 日志"三件套，配合 `CHECKSUM`、异质介质、每季度 `RESTORE VERIFYONLY` 演练（⚠️，具体阈值随 SLA）。

## 九、常见问答（FAQ）

1. **问：只做过完整备份，能 PITR 吗？** 答：不能，缺日志链，只能退到最近完整点（⚠️）。
2. **问：差异备份能替代日志备份吗？** 答：不能——差异记录"自 FULL 以来改了哪些区"，粒度到区，无法重放到时刻（⚠️）。
3. **问：SIMPLE 模型下截断日志、日志文件为何仍不缩？** 答：截断≠收缩；未 VLF 复用需 `DBCC SHRINKFILE` 或预配（⚠️，收缩制造碎片）。
4. **问：CHECKSUM 能防介质坏吗？** 答：能检不能修；检出损坏仍靠还原链（⚠️）。
5. **问：备份文件本身丢了怎么办？** 答：这就是"3-2-1"多副本异地策略存在的理由（⚠️）。
6. **问：单页恢复要满足什么条件？** 答：FULL/BULK_LOGGED 模型 + 该页之后日志链完整 + 文件组联机（⚠️）。

## 核心概念速览（中英对照）

- 完整备份 — Full Backup：整库基线，还原链起点。
- 差异备份 — Differential Backup：自最近 FULL 起改动的扩展盘区集。
- 扩展盘区图 — Differential Bitmap (EA)：标记"自上次 FULL 以来"变过的区。
- 日志备份 — Log Backup：截取活动日志段并截断已提交日志。
- 尾日志备份 — Tail-Log Backup：还原前对当前活日志的最后一段截取。
- 恢复链 — Restore Chain：Full→Diff→Logs 依序衔接才能到目标点。
- 时点恢复 — Point-in-Time Recovery：STOPAT 恢复到链内任意时刻。
- NORECOVERY — NORECOVERY：还原不终止，留待接后续日志。
- STANDBY — STANDBY：只读备用还原态，可读且不结束链。
- 恢复模型 — Recovery Model：FULL/BULK_LOGGED/SIMPLE，决定备份能力。
- CHECKSUM — CHECKSUM：备份/还原级页校验和，检出损坏。
- 数据库镜像 — Database Mirroring（2008 HA）：主体日志流式同步到镜像 ⚠️。
- DBCC CHECKDB — CHECKDB：全库分配/完整性/一致性审计。
