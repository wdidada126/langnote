# 07 查询处理、优化器与计划缓存（原书 ch9 Query Execution + ch10 The Query Optimizer + ch11 Plan Caching and Recompilation）

> 状态标注：⚠️ = SQL Server 引擎二手转述（本机不可实测）；✅ = Microsoft Learn 现行文档（写前 curl -sL 200）；🔧 = 本机 SQLite/DuckDB 类比，**非本书 SQL Server 引擎行为**。

## 一、本章地图

一条 SQL 的一生：解析→绑定→**优化**（估成本选计划）→**执行**（火山模型逐行拉取）→**计划缓存**（下次复用）。三章合一，因为它们是同一条流水线。它运行在 [01-体系结构与SQLOS.md](01-体系结构与SQLOS.md) 的 SQLOS 之上，物理取数靠 [05-索引内部结构与管理.md](05-索引内部结构与管理.md)。

## 二、核心精讲：优化器（⚠️）

### 2.1 基数估算与统计（⚠️）

优化器是**成本基（cost-based）**的：它先用**统计信息**（直方图 + 密度向量 + 头部频率）估算每个算子输出行数（基数），再据此选连接顺序/算法/索引。统计的"新鲜度"与"覆盖列"决定估算质量——过期/缺失统计会让优化器"瞎猜"，选出灾难计划。✅ [Statistics](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics)；对照 #36 [../Pro_SQL_Server_Internals/03-统计信息.md](../Pro_SQL_Server_Internals/03-统计信息.md)。

### 2.2 连接算法与顺序（⚠️）

三大利器：**Nested Loops**（外层驱动、内层参数查找，适合小外层+可 seek 内层）、**Merge Join**（两输入有序，边扫边配）、**Hash Join**（建哈希表再探测，适合大无序）。优化器在搜索空间中枚举连接顺序，用 cost 模型剪枝；2008 用"代价 + 启发式超时"约束搜索广度，避免优化本身过久（⚠️）。

### 2.3 查询执行：火山模型（⚠️）

执行算子是**迭代器（row-at-a-time, Volcano/打开-取行-关闭）**：根算子反复调用子算子 `GetNextRow()`，行"流"上去。并行计划在 Exchange（Repartition/Broadcast/Gather）处切段（⚠️）。这就是**行式**执行——与列存"一次一批向量"的根本分野，用下方 DuckDB 🔧 对照。

## 三、核心精讲：计划缓存与重编译（⚠️）

- **编译一次、复用多次**：计划按参数化后的签名进**计划缓存（plan cache）**，同签名直接复用，省编译成本。
- **参数嗅探（Parameter Sniffing）**：编译时用首批参数值估基数，后续不同值复用同一计划可能次优（⚠️，2008 经典顽疾）。
- **重编译触发**：统计更新、`sp_recompile`、基架构改变、SET 选项变化、缓存压力驱逐等会让计划失效重编（⚠️）。
- 缓解：`OPTION (RECOMPILE)`、`OPTIMIZE FOR`、`OPTION(EMBEDDED)`；2016+ 才有**参数化查询提示**与 2017+ **自动计划修正**（⚠️ 前向引用 #56/#71）。

✅ 官方口径：[Execution Plans](https://learn.microsoft.com/en-us/sql/relational-databases/performance/execution-plans)。

## 四、🔧 类比实验 E6：行式火山 vs 列式向量化（非本书 SQL Server 引擎行为）

SQL Server 2008 查询执行是**行式火山模型**（⚠️，无向量化）。为理解"为什么现代引擎改用批处理/向量化"，用 DuckDB 对照同一分析查询的执行范式：

```text
# 本机 duckdb 1.5.5（列存+向量化，一次处理一批/向量，而非逐行 GetNextRow）
GROUP BY cat over 2M 行          -> 0.009s
JOIN 2M×3M + 聚合                -> 0.055s
谓词扫描 仅读所需列              -> 0.002s
```

对照：火山模型逐行虚函数调用开销大、CPU 分支预测差；向量化按列批量处理、SIMD/缓存友好。SQL Server 也在 2012+ 用**批处理模式（Batch Mode，900 行一批）** 逼近这一思想（尤其配合 CCI），但 2008 主体是行式（⚠️）。数字来自 DuckDB，**非 SQL Server 实测**。

## 六、优化流程推演（⚠️）

1. **解析/绑定**：T-SQL → 语法树 → 绑定到对象，产出逻辑树（relational algebra）。
2. **简单规范化**：去冗余、可交换律/结合律改写、消除 subquery→join 等。
3. **代价搜索**：自底向上物化候选，用统计估基数、cost 公式估 I/O+CPU+内存，保留每节点最优子计划（有限时间预算内）。
4. **物理算子选择**：Join→NL/Merge/Hash、聚合→Hash/Stream、Spool 等。
5. **加交叉验证/行目标**，出计划，进缓存。

> 关键点：优化器不是"遍历所有计划"，而是**在超时约束下的启发式搜索**；这解释了为什么"看起来明显更好"的计划偶尔没被选中（⚠️）。

## 七、要点与检查清单（⚠️）

- 先看统计：过期的 `UPDATE STATISTICS`/自动统计是否触发；大表采样率与直方图步数（200 步上限）决定精度。
- 参数嗅探三查：计划缓存里对比"编译时估算行数 vs 实际执行行数"（`sys.dm_exec_query_stats` 类，⚠️）。
- 行式热点：百万级行虚调用密集的分析查询在 2008 上先天吃亏；2012+ 批处理模式/列存才是解（⚠️ 前向引用）。
- 并行过度：小查询被并行化反增 Exchange 开销（⚠️，Cost Threshold for Parallelism）。
- 强制提示是最后手段：`INDEX=`/`FORCE ORDER` 会锁死搜索空间，妨碍将来数据变化时的自适应。

## 八、编译-缓存-复用 全生命周期推演（⚠️）

1. **语句到达** → 解析器产语法树、绑定器解析对象名。
2. **查询规范化 → 优化器搜索** → 用统计估基数、代价模型比较 NL/Merge/Hash、Spool 等，出候选计划。
3. **加交叉验证/行目标 → 生成执行计划**，序列化后进 plan cache（按对象 ID + 参数化签名 + SET 选项哈希）。
4. **下次同签名到来** → 命中缓存直接复用，跳过编译；若缓存被内存压力驱逐，则再编译。
5. **失效场景** → 基架构改变 / `sp_recompile` / 统计更新 / SET 变化 / 参数嗅探出坏计划 → 强制重编或 `OPTION(RECOMPILE)` 每次现编现用。

## 九、并行度与内存授予（⚠️）

- **最大并行度（MAXDOP）** 与 **Cost Threshold for Parallelism** 共同决定"什么查询值得并行"；2008 默认阈值 5，工业经验常调高（⚠️）。
- **内存授予（Memory Grant）**：Sort/Hash 大算子启动前向 SQLOS 申请一块内存；授予过大或过小都会引发 spill 到 tempdb、并饿死后继查询（⚠️；2012+ 有内存授予反馈、2019+ 有 SQL 操作符级内存授予监视）。
- **Exchange 迭代器** 三段：Repartition / Broadcast / Gather——选错分布会引入数据倾斜或网络放大（⚠️）。

## 十、常见问答（FAQ）

1. **问：为什么明明有索引，优化器仍走全表扫？** 答：基数估算觉得"要回表太多、不如顺序扫全表"；选择性差、统计过期都触发（⚠️）。
2. **问：参数嗅探能彻底避免吗？** 答：2008 只能靠 RECOMPILE/OPTIMIZE FOR/分散语句；2016+ 参数化查询提示 + 2017 自动计划修正才有工程级解（⚠️ 前向）。
3. **问：并行一定更快吗？** 答：小查询 Exchange 开销 > 收益；DOP 过高反致内存授予排队（⚠️）。
4. **问：批处理模式与列存必须绑定吗？** 答：2016+ 有 Batch Mode on Row（行存也可批处理），但列存才是最佳伴侣（⚠️ 前向引用 #56/#71）。
5. **问：DuckDB 数字能当 SQL Server 结论吗？** 答：不能；仅演示向量化范式，SQL Server 2008 无向量化。
6. **问：为什么同一 SQL 有时快有时慢？** 答：多为参数嗅探——计划复用但最佳计划依参数不同；诊断对比估计/实际行数（⚠️）。
7. **问：Adaptive Join 是什么？** 答：2017+ 特性，运行中按首批行数在 NL↔Hash 动态切换；2008 无（⚠️ 前向）。
8. **问：并行度设置的经验值？** 答：OLTP 低 DOP（≤4）、分析适度高；随核数/NUMA 而变，无一刀切（⚠️）。
9. **问：为什么加 INCLUDE 列比把它做成键列便宜？** 答：INCLUDE 只落叶子、不参与排序/去重维护（⚠️）。

## 核心概念速览（中英对照）

- 成本基优化器 — Cost-Based Optimizer：用统计估基数、按代价选计划。
- 统计信息 — Statistics：直方图+密度+范围键，供基数估算。
- 基数估算 — Cardinality Estimation：预测算子输出行数。
- Nested Loops — 嵌套循环连接：外层驱动、内层 seek，小外层高效。
- Merge Join — 归并连接：两输入有序时线性配对。
- Hash Join — 哈希连接：建探测哈希表，适合大无序。
- 火山模型 — Volcano/Iterator Model：算子 GetNextRow 逐行拉取的执行范式。
- 批处理模式 — Batch Mode：一次约 900 行的列式批执行 ⚠️ 2008 后逐步引入。
- 计划缓存 — Plan Cache：按签名复用已编译计划的内存区。
- 参数嗅探 — Parameter Sniffing：编译时参数值固化进复用计划致次优。
- 重编译 — Recompilation：计划失效重新编译触发。
- Exchange 迭代器 — Exchange Operator：并行计划段间 Repartition/Broadcast/Gather。
- 最优子计划 — Best Subplan：自底向上保留每节点最优候选。
- 基数估算框架 — CE Version（compat）：不同兼容级别用不同估算器，升级致计划漂移 ⚠️。

- 优化器演进为主线：2008→2012→2014/2016/2019/2022 的**基数估算框架（CE 70/120 legacy/new）**、**自适应连接**、**内存授予反馈**、**自动计划修正**（✅ [Intelligent Query Processing](https://learn.microsoft.com/en-us/sql/relational-databases/performance/intelligent-query-processing)），逐项缓解本章参数嗅探/次优计划顽疾；细节见 #56/#71。
