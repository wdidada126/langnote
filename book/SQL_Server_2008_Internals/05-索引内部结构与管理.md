# 05 索引内部结构与管理（原书 ch6 Indexes: Internals and Management）

> 状态标注：⚠️ = SQL Server 引擎二手转述（本机不可实测）；✅ = Microsoft Learn 现行文档（写前 curl -sL 200）；🔧 = 本机 SQLite/DuckDB 类比，**非本书 SQL Server 引擎行为**。

## 一、本章地图

索引就是 B+ 树。本章讲两棵树（聚集 vs 非聚集）的物理差别、叶子双向链表、覆盖/回表、以及碎片三本账（内部/外部/页级）。它承接 [04-表存储.md](04-表存储.md) 的行/页，是查询性能的物理地基。

- 2A B+ 树结构：根/中间层/叶子，页分裂与合并
- 2B 聚集索引 = 数据本身；非聚集索引 = 定位器
- 2C 覆盖索引与键查找（Key Lookup）/回表
- 2D 索引维护：填充因子、重建 vs 重新组织
- 2E 碎片：extent 顺序 vs 页内顺序，两种"乱"

## 二、核心精讲（⚠️ 转述）

### 2.1 B+ 树的物理形态（⚠️）

SQL Server 索引是平衡的 **B+ 树**：所有键在内部节点作分隔（separator），真实行/指针只在**叶子层**，叶子之间用**双向链表**相连，故范围扫描 `ORDER BY`/`BETWEEN` 沿链表走而非重树下潜。插入触发**页分裂**（一页满→拆两页、父层加分隔键），删除触发**页合并**回收空页（⚠️）。

✅ 官方口径：[Clustered and Nonclustered Indexes Described](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described)。

### 2.2 聚集 vs 非聚集：叶子装什么（⚠️）

- **聚集索引**叶子页 = 数据行本身（表即索引）。
- **非聚集索引**叶子 = 索引键列 + **定位器（locator）**：聚集表上是聚集键，堆上是 RID。据此再回聚集树取其余列。

这就是"回表"的物理原因：非聚集索引命中后，若查询还需未索引的列，就得拿定位器回聚集索引**键查找（Key Lookup）**。

### 2.3 覆盖索引与 INCLUDE 列（⚠️）

把查询需要的列全塞进索引（键列 + `INCLUDE` 非键列），使叶子自带答案，消除回表 = **覆盖（Covering）**。INCLUDE 列只进叶子、不作排序键，成本低于放进键列。设计索引的核心权衡就落在"多一个索引=多一棵树要维护"。

### 2.4 索引维护（⚠️）

- `FILLFACTOR`：建/重建时预留多少空闲以缓冲将来插入的分裂。
- **ALTER INDEX REBUILD**：整树重建（等价删除+创建，释放/重分配区，消碎片彻底）；**REORGANIZE**：原地整理叶子级碎片，轻量在线。
- `ONLINE`（2008 Enterprise）：重建期间保持可查询（⚠️，Edition 依赖）。

## 三、🔧 类比实验 E2：聚集(PK)树 vs 二级索引足迹（非本书 SQL Server 引擎行为）

```text
# 本机 python sqlite3 3.45.3，page_size=4096，20000 行
仅主键（聚集，数据即 B+ 树）： base 208 页
再建二级索引 ix_a：           262 页（+54 页）
```

观察：二级索引**另立一棵 B+ 树**，只存 `a + rowid(定位器)`，故其体积远小于主树（54 页 vs 208 页）——正对应 SQL Server"非聚集索引=键+定位器"的瘦叶子；而建/用二级索引都要付出额外树的维护与回表代价（⚠️ 类比）。数字来自本机，不代表 SQL Server。

## 五、要点与检查清单（⚠️）

- 覆盖优先：能 INCLUDE 就别逼出 Key Lookup。
- 索引不是越多越好：每个写操作要更新所有受影响索引（写放大，⚠️）。
- 碎片阈值：<10% 忽略、10–30% REORGANIZE、>30% REBUILD（社区通行经验，⚠️）。
- 聚集键宜窄且稳定：宽/常变的聚集键会让**所有**非聚集索引跟着胖且抖。
- 前向/顺序扫描：双向链表让 range scan 廉价，但大范围仍回表，须看选择率。

## 六、碎片两本账（⚠️）

- **逻辑碎片（extent 连续性）**：叶子页在磁盘上的 extent 是否顺序分配——扫描时是否频繁"跳跃"到不同物理位置。
- **页内碎片（密度/可用空间）**：单页内空闲字节、平均页密度——同样数据摊到更多页，扫描读更多页。
- 外部碎片（extent 乱序）靠 REBUILD 重分配区来根治；REORGANIZE 主要整理叶子级密度。SQL Server 2008 无 2016+ 的"延迟持久化/列存段消元"式碎片治理（⚠️ 版本边界）。

## 七、🔧 补充：用 SQLite 看覆盖 vs 回表（非本书引擎行为）

```sql
CREATE TABLE t(k INTEGER PRIMARY KEY, a INT, b TEXT);
CREATE INDEX ix_a ON t(a);              -- 二级索引：a -> rowid
-- 🔧 覆盖：只 SELECT a，命中 ix_a 即可，无需回主树
SELECT a FROM t WHERE a BETWEEN 10 AND 20;
-- 🔧 回表：SELECT * 需 b，命中 ix_a 后用 rowid 回主 B+ 树取整行（Key Lookup 类比）
SELECT * FROM t WHERE a BETWEEN 10 AND 20;
```

对照 SQL Server：第二条计划会出现"Index Seek + Key Lookup"，第一条纯 Seek——与 SQLite 的"index-only vs 回 rowid 取行"完全同构（⚠️ 类比，代价模型不同）。

## 八、常见问答（FAQ）

1. **问：非聚集索引能定位表吗？** 答：靠定位器——聚集表用聚集键、堆用 RID（⚠️）。
2. **问：INCLUDE 列参与排序吗？** 答：不参与键排序，只存于叶子供覆盖读取（⚠️）。
3. **问：REBUILD 一定比 REORGANIZE 好吗？** 答：碎片高才值得重（成本/日志大）；轻量碎片用 REORGANIZE（⚠️）。
4. **问：为什么加索引反而查询变慢？** 答：写放大 + 优化器可能选错；索引是"读加速/写减速"的权衡（⚠️）。
5. **问：唯一索引和非唯一在物理上有何不同？** 答：唯一索引叶子键不重复，可省部分去重/定位开销，但仍是 B+ 树（⚠️）。
6. **问：主键一定聚集吗？** 答：默认常是，但可显式把 PK 建成非聚集、另选聚集键（⚠️）。

## 九、补充：索引视图与物化（⚠️）

2008 支持 **Indexed View（物化视图）**：视图上可建唯一聚集索引，把 JOIN/聚合结果**物化**到实际页里，查询优化器可在基表匹配时**自动视图匹配**用之。代价：基表每次改动都要维护视图索引（写放大巨大），且限制多（需 SCHEMABINDING、ANSI_NULLS 严格 SET 选项等），工业界常仅用于 OLAP 聚合热点（⚠️，与后来列存聚合互补）。

## 十、补充：主键与唯一约束的索引化（⚠️）

- 主键（PK）：2008 默认建 **唯一聚集索引**（可显式改非聚集），并强制 NOT NULL。
- 唯一约束（UNIQUE）：默认建 **唯一非聚集索引**（可显式改聚集，但同一表只能一个聚集）。
- 二者本质是"约束层"，落到物理层就是一棵 B+ 树；约束失效（如禁用聚集索引）会连带主键不可用（⚠️）。

## 核心概念速览（中英对照）

- B+ 树 — B+ Tree：键在内部分隔、数据在叶子、叶子双向链表相连的平衡树。
- 叶子双向链表 — Leaf Linked List：使范围扫描顺序化、无需重下潜。
- 定位器 — Locator：非聚集叶子指向行的凭据（聚集键或 RID）。
- 回表/键查找 — Key Lookup：非聚集命中后回聚集树取未索引列。
- 覆盖索引 — Covering Index：索引自带查询全部所需列，免回表。
- INCLUDE 列 — Included Column：只进叶子、不作排序键的非键列。
- 页分裂 — Page Split：满页一分为二、父层加分隔键的插入放大动作。
- 页合并 — Page Merge：删除致近空页时回收。
- FILLFACTOR — Fillfactor：建/重建时预留页内空闲比例。
- REBUILD — Rebuild：整树重建，彻底消外部碎片。
- REORGANIZE — Reorganize：原地整理叶子级碎片，轻量在线。
- 逻辑碎片 — Logical Fragmentation：叶子 extent 物理顺序的错乱。
- 页内碎片 — Page Fragmentation：页内平均密度低、可用空间碎散。
- 写放大 — Write Amplification：一个写需同步更新多棵索引树的代价。
