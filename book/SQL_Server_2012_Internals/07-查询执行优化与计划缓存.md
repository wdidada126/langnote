## 核心精讲（转述 + ⚠️）

### 1. 优化器的经济学教材结构
第 11 章的叙事骨架：优化器是"在有限时间预算内给不出最优解的 NP 问题承包商"——它用统计+假设+成本常量换搜索时间。书中演示的"好索引喂坏统计仍出坏计划"案例链，本质都在讲：**基数估算是唯一全局杠杆**。现代对照读物 #36 专章：[../Pro_SQL_Server_Internals/03-统计信息.md](../Pro_SQL_Server_Internals/03-统计信息.md) ✅在盘；理论通识 [../数据库系统概念6.md](../数据库系统概念6.md) 查询处理章 ⚠️。✅ https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics 。

### 2. 火山模型与它的朋友们
2012 的执行引擎=逐行 Pull 火山 + 表达式逐行求值；批处理模式(列存储)在 06 章 NCCI 侧以"每批 1024 行向量"露脸 ⚠️——这正是本章 E6 对照的时代现场：**同一引擎里两套执行范式并存**。对位阅读：DuckDB 的向量化(✅ [../DuckDB_in_Action/00-总览与阅读地图.md](../DuckDB_in_Action/00-总览与阅读地图.md))与 MonetDBX 列范式 [../Database_Internals/00-总览与阅读地图.md](../Database_Internals/00-总览与阅读地图.md) ⚠️。

### 3. 计划缓存：复用是性能的第一来源
每条语句先过"是否可参数化→算指纹→查缓存→miss 才编译"。简单参数化(等值/整型 literals)vs 强制参数化(全字面量抠参，伤统计)的取舍 ⚠️；ad-hoc 洪水的三件药方：optimize for ad hoc workloads(先存 44 字节存根)、存储过程化、强制参数化+查询 Store 观察。参数嗅探的机制解释(编译期用首参+当前统计)在 2012 时代只能靠提示/指南对抗，Query Store 时代改为"观察→钉回"——演进节续讲。✅ 准绳：query store 文档 https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store 。

### 4. 编译与执行之间的并发账（转述 ⚠️）
编译计划要 schema 稳定(Sch-S)、缓存查找要走内存闩、执行期对象锁按隔离级别发放——第 12 章把"重编译风暴"(计划被频繁 invalidate)列为并发热点之一，与 08 章锁/版本叙事打通 ⚠️。

## 🔧 类比实验 E6 · 向量化批执行 vs 逐行拉取：同负载的两种身体（DuckDB 1.5.5）

**非本书引擎行为，仅通用机制演示**：2M 行列存表 JOIN 1.8M 行表 + 聚合：

```
建 2M 行表 line(id,cat,part,val)：0.57s；库体积 17.5 MiB(列存+字典)
EXPLAIN 计划算子集：{SEQ_SCAN, HASH_JOIN, PERFECT_HASH_GROUP_BY, PROJECTION}
JOIN+GROUP BY 实测：0.018s
谓词 cat=42：0.002s（zone-map 段消元）
DELETE 200k 行：0.01s（删除向量标记不搬数据）
```
实测 ✅。对照本章叙事：SQL Server 行式引擎同规模 JOIN 靠"索引嵌套循环+并行哈希"也能快，但**成本模型里为逐行模型准备的三算法菜单，在批式引擎里塌缩成 HASH+消元两板斧** ⚠️ 观察性结论；这正是 2012→2025 列存占比一路走高的机制注脚。SQLite(3.45.3，逐行火山)同查询作参照更慢且计划形态贴近视 2012 SQL Server ⚠️。

## 本章结论速记

- 计划质量=统计质量×搜索预算；提示只是止痛药。
- 火山逐行是 2012 的主流；列存批处理已在同版本内偷换范式。
- 缓存与嗅探是一对矛盾：复用省编译、错配毁运行；钉计划是人工仲裁。
- 内存授予与估算绑定：spill 与 resource_semaphore 是同一枚硬币两面。
- 并行不是加速开关，是 Exchange 重分布的预算表。

## 常见误区（转述 ⚠️）

| 误区 | 事实 |
| --- | --- |
| "NOLOCK 提速无害" | 脏读之外还有重读/漏行的正确性债(08 章) ⚠️ |
| "TOP 1 一定找一行就停" | 有序需求/并行 exchange 下 top 不短路边(书含案例 ⚠️) |
| "标量函数进 WHERE 不伤索引" | 每行调用+不可内联→谓词变成全表扫描 ⚠️ |
| "计划缓存命中=快" | 命中可能命中"为别的参数形状"的坏计划(嗅探) ⚠️ |
| "重建存储过程修坏计划" | 重编译不改统计与参数分布，旧病复发 ⚠️ |
| "并行度调高就好" | 交换开销+调度预算；短查询并行是负资产 ⚠️ |
| "RECOMPILE 提示治嗅探" | 是药也是病：编译成本上升，适合参数倾斜极端场景 ⚠️ |

## 转述扩写：一条坏计划的验尸报告（案例转述 ⚠️）

1. 症状：报表查询偶发 40 分钟，常态 2 秒；等待集中在 RESOURCE_SEMAPHORE + SOS_VIRTUALMEMORY ⚠️；
2. 取证：缓存里同一指纹两张计划——一张并行哈希、一张串行嵌套循环；参数形状决定首编译 ⚠️；
3. 病根：日期范围统计陈旧+列相关(状态×日期)密度向量失真→行数估低两个数量级→grant 过小→排序 spill+NL 误选 ⚠️；
4. 处置(2012 工具箱)：过滤统计/手动 UPDATE STATISTICS、OPTIMIZE FOR UNKNOWN 或本地变量截断嗅探、必要时 plan guide 钉好计划 ⚠️；
5. 复盘教训：估算错先查统计再怪 CE；"偶发"多为参数分布的函数 ⚠️。
（案例为书叙事骨架的重组转述 ⚠️，数字非原书逐字。）

## 参数化与缓存复用的判定流（⚠️ 转述 + ✅ Learn plan caching）

- 简单参数化只吃"安全字面量位"(等值比较/INSERT VALUES 的整型串)——IN 列表长串常原样入库成"每个字面量一条计划"的洪水 ⚠️；
- 洪水解药三件套：optimize for ad hoc workloads(存根先行)、应用侧真参数化(驱动参数化开关)、强制参数化+风险审计(统计污染) ⚠️；
- 复用匹配=指纹+设选项+DB 上下文+SQL 补正(ANSI_NULLS 等)多维同键——"同 SQL 不同连接设置=两个计划"的经典惊愕 ⚠️；
- 驱逐路径：内存压力→缓存时钟扫描→零使用计划先出血(01 章 broker 呼应) ⚠️。
✅ https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics 、✅ query store 页(见演进节)。

## JOIN 算法的成本直觉（⚠️ 转述）

| 算法 | 吃得下的前提 | 内存行为 | 失配时的惨状 |
| --- | --- | --- | --- |
| 嵌套循环 | 外表小或可短路；内表有树 | 几乎零授予 | 外表行数估低→N×树高灾难 |
| 归并 | 双有序(或愿付排序) | 排序授予+spill | 统计错→选无索引排序 |
| 哈希 | 无序大集；build 侧要小 | 授予+tempdb 落盘 | grant 不足→多级分区回炉 |

估算→授予→算法三连环是本章全部案例的公共骨架 ⚠️。

## 核心概念速览（中英对照）

1. **基数估算** — Cardinality Estimation：统计+假设换算行数，一切成本之源 ⚠️。
2. **火山模型** — Volcano Model：Pull 逐行算子树 ⚠️。
3. **批处理模式** — Batch Mode：列存向量批执行范式 ⚠️✅(columnstore/Learn)。
4. **嵌套循环连接** — Nested Loops：小外表×有序内查找 ⚠️。
5. **归并连接** — Merge Join：双有序线扫 ⚠️。
6. **哈希连接** — Hash Match：build/probe 两阶段+内存授予 ⚠️。
7. **Exchange 算子** — Exchange：并行计划的重分布闸口(BROADCAST/HASH PARTITION) ⚠️。
8. **内存授予** — Memory Grant：执行前按估算预领的配额 ⚠️。
9. **溢出** — Spill：配额不够时排序/哈希落 tempdb ⚠️。
10. **参数嗅探** — Parameter Sniffing：首参与统计绑定编译的副作用 ⚠️。
11. **计划缓存** — Plan Cache：指纹→计划复用的共享库 ⚠️✅(plan caching/Learn)。
12. **简单/强制参数化** — Simple/Forced Parameterization：字面量抠参的两档策略 ⚠️。
13. **计划指南** — Plan Guide：不改 SQL 钉计划的旧机制(Query Store 的前任) ⚠️✅(query store/Learn)。
14. **重编译** — Recompilation：对象/统计/环境变更引发的计划失效重建 ⚠️。
15. **RESOURCE_SEMAPHORE** — 编译内存等待：授予排队等待类型 ⚠️✅(wait stats/Learn)。

## 最新演进与工业实践

- **2012→2017**：**Query Store(2016)**把"计划回归"从捉现行变成回放厅(✅ https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store )；**自适应 JOIN 反馈(2017)**给行式引擎装上"运行时改道"的耳朵 ⚠️ 转述。
- **2019→2022**：智能查询处理家族扩容(表变量延迟编译、内存授予反馈、并行计划升级、CSA ⚠️ 转述)；**2022 的可选新 CE + TF 9453"原生编译 only"**等细节本册未逐条验 ⚠️ 不展开；Intelligence/数据湖接入让"查询"边界外扩 ⚠️。
- **2025**：向量检索(VECTORS + 邻近索引)与 AI 服务线把"特殊存储→特殊执行"续写成第六代谱系；Kubernetes 部署下的 CPU 配额/并行度治理成为新的"调度预算"课题 ✅(入口：what's new https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025 、✅ https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-overview ，细节 ⚠️ 转述)。
- **工业实践**：参数嗅探对策的代际更替——2012 时代 OPTIMIZE FOR/提示 → 2016+ 参数化程度+Query Store 钉回 → 云托管自动调优 ⚠️；排障路径仍是"估算错→看统计→看授予→看并行"四步，等待统计为总入口 ✅( https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-os-wait-stats-transact-sql )。
