## 核心精讲（转述 + ⚠️）

### 1. 日志的三重身份
同一份事务日志同时服务：(a) 原子性(回滚未提交)、(b) 持久性/崩溃恢复(前滚)、(c) 复制/HA/时间点恢复(重放给别的实例或过去)。书中反复强调三者共享同一个"边界推进"机制：任何钉住日志的环节(长事务、失效的备份、镜像挂断)都会同时伤害三者——LDF 暴涨事故的根因分析就是"LOG_REUSE_WAIT_DESC 逐项排除" ⚠️。✅ https://learn.microsoft.com/en-us/sql/relational-databases/logs/the-transaction-log-sql-server 。

### 2. LSN：全库统一的逻辑时钟
每页页头存"最后一次改它的日志 LSN"(页 LSN)，日志记录里存"上一条同类型记录 LSN"——构成页粒度的重放校验网。检查点记录标定"脏页表分界"，恢复时按它划"无需重放"的世界。这与 ARIES 的页 LSN/日志序列号设计同构 ⚠️，理论对位直接读 [../../db/ARIES.md](../../db/ARIES.md)；InnoDB 的 redo LSN/checkpoint no 概念可在 [../Understanding_MySQL_Internals/00-总览与阅读地图.md](../Understanding_MySQL_Internals/00-总览与阅读地图.md) 找镜像 ⚠️。

### 3. 间接检查点：2012 的"恢复时间预算制"（转述 ⚠️）
旧行为：固定 60–90 秒节奏写 CHECKPOINT，脏页攒多则崩溃恢复长。2012 新机制：实例级设定目标恢复秒数，引擎按写脏速率动态反推检查点间隔——"RPO≈0、RTO 可承诺"从运维玄学变成旋钮。演进节续讲到 2016+ 的可用性组提交时间与云 SLA。

### 4. 恢复=重放的三种时间线
崩溃恢复(本机重启)、还原恢复(备份链重放到现在)、时间点恢复(重放到指定标记/LSN 后停)。log backup 的可链性由"首次日志备份截断旧头"规则决定 ⚠️。备份策略设计的实操版在 #36 的 [../Pro_SQL_Server_Internals/16-事务日志备份与高可用.md](../Pro_SQL_Server_Internals/16-事务日志备份与高可用.md)，两家互证 ⚠️。

### 5. 最小日志不是"不写日志"
BULK_LOGGED 下批量操作只记区间分配而非行内容——快且省，但**打断时间点恢复链**；书中立场：把它当"可接受的窗口性降级"，默认常态用 FULL ⚠️ 转述。此坑在 2025 云时代换成"恢复点目标"话术，本质未变(演进节)。

## 🔧 类比实验 E4 · rollback-journal vs WAL 的文件形态（SQLite 3.45.3）

**非本书引擎行为，仅通用机制演示**：同一张表在两种日志模式下，观察"日志文件何时存在、何时长大、何时被截断"。

```
mode=delete(回滚日志)：事务中途目录含 e4_delete.db + e4_delete.db-journal；提交/回滚后 -journal 消失
mode=wal：常驻 -wal + -shm；1 个单行事务后 -wal=8272 字节；PRAGMA wal_checkpoint(TRUNCATE) → (0,0,0)，-wal 回收
```
实测数字如上 ✅。概念迁移(SQL Server 对照，⚠️ 转述)：(a) delete 模式=undo-first，与 SIMPLE 恢复模型"提交前把改动想清楚丢掉"神似；(b) WAL=redo-first，正是 SQL Server 的立场；(c) checkpoint 截断 wal = "复用边界前移"的迷你化身，而 SQL Server 里钉住这个边界的名单长得多(备份/镜像/复制/查询)。SQLite 把脏页刷盘和日志截断压进同一文件对儿，SQL Server 则用 8KB 页 + 环形 VLF 撑起多并发服务器场景——规模差一个数量级，机制同谱 ⚠️。恢复语义进一步对照 [../../db/ARIES.md](../../db/ARIES.md) 的三阶段与日志分析过程。

## 本章结论速记

- WAL：提交=日志落盘；数据页可以滞后，靠页 LSN 链条兜底。
- 日志是环，截断点由最"钉"的环节决定：LDF 暴涨先查 LOG_REUSE_WAIT。
- 恢复模型决定时间点能力：SIMPLE 断链、FULL 成链、BULK_LOGGED 断链窗口 ⚠️。
- 间接检查点(2012)=把 RTO 变成可配置预算。
- 崩溃恢复/备份还原/日志传送是同一重放机制的三种剧本。

## 常见误区（转述 ⚠️）

| 误区 | 事实 |
| --- | --- |
| "事务日志记录行数据" | 主要是页级逻辑操作(含分裂时的整页镜像)，为 redo/undo 服务 ⚠️ |
| "FULL 模式备份才能收缩文件" | shrink 能缩文件但伤碎片；收缩≠截断，两件事 ⚠️ |
| "检查点=提交" | 提交刷日志；检查点刷脏页——两套时钟 ⚠️ |
| "崩溃后数据库自动就一致" | 一致靠 redo+undo 跑完；长回滚期间实例不可用度被低估 ⚠️ |
| "镜像/AG 能替代备份" | 副本挡故障不挡逻辑错误/误删；时间点恢复仍靠备份链 ⚠️ |
| "自动增长关掉就稳了" | 日志写满≠自动增长可兜底：FULL 下不截断的增长只是把事故延后 ⚠️ |
| "99999 页日志备份损坏就没救" | 有尾日志/继续恢复等手册路径(书含修复叙事 ⚠️ 细节从略) |

## 转述扩写：三种剧本的逐帧分解（⚠️ 转述 + ✅ ARIES 对位）

### 剧本 A：崩溃恢复（实例重启）
1. 读 checkpoint 记录定"重放起点"；2. 前滚：按 LSN 顺序重放所有记录（redo）；3. 回滚：反向扫描撤销未提交事务（undo）；4. 回滚量=剩余脏页+未提交写——"简单重启"背后的分钟级账单 ⚠️。
- 间接检查点的存在让第 1 步起点更新、第 2 步更短；但第 3 步不可压缩——长事务回滚窗口是 RTO 承诺的暗礁 ⚠️。

### 剧本 B：链式还原（时间点）
full → diff(可选) → log ×N → tail log(若还能抢救) → 停在标记/LSN；每步=一段重放，RECOVERY 时才跑 undo ⚠️。
- 陷阱登记：BULK_LOGGED 窗口打断可停点(最小日志区间)；日志备份截断旧头后链才有"可续性" ⚠️。

### 剧本 C：页级手术（824/825 之后）
单页还原(企业版)=在线补一页，链上前后日志照吃；CHECKDB 报告(08 章)决定"修还是换" ⚠️。

### VLF 卫生清单（⚠️ 转述）
- DBCC LOGINFO 看 VLF 数与状态；过多 VLF=碎片化日志，过少巨大 VLF=截断粒度粗 ⚠️；
- 急救：把 LDF 撑爆的"假收缩"循环(shrink→满→增长)会制造畸形 VLF——正规路径见本章误区表 ⚠️。

### 恢复等待诊断决策树（文字版 ⚠️）
1. `log_reuse_wait_desc` 为何值？NOTHING=可截断；LOG_BACKUP=缺日志备份；ACTIVE_TRANSACTION=长事务；AVAILABILITY_REPLICA/MIRROR=同步伙伴滞后 ⚠️；
2. 值指向谁，就去治谁(备份计划/事务生命周期/副本健康)——而不是先 shrink ⚠️；
3. 事后复盘用默认跟踪与 msdb 史(02 章系统库呼应) ⚠️。

## 核心概念速览（中英对照）

1. **预写日志** — Write-Ahead Logging (WAL)：日志记录先于数据页持久化 ⚠️✅(Learn)。
2. **日志序列号** — LSN：全库单调时钟，页头与记录互锁成重放网 ⚠️。
3. **虚拟日志文件** — VLF：日志的环内切分单位，增长与截断的操作对象 ⚠️。
4. **复用边界** — Reuse/Truncation Point：环上"之前可覆盖"的水位线 ⚠️。
5. **检查点** — Checkpoint：推进脏页刷盘 + 写检查点记录缩短恢复 ⚠️✅(Learn)。
6. **间接检查点** — Indirect Checkpoint：2012 新，按恢复时间目标反推节奏 ⚠️。
7. **恢复模型** — Recovery Model：SIMPLE/FULL/BULK_LOGGED，决定时间点能力 ⚠️✅(Learn)。
8. **前滚** — Roll Forward (REDo)：重放日志到故障点 ⚠️。
9. **回滚** — Rollback (UNDO)：撤销未提交事务的改动 ⚠️。
10. **尾部日志** — Log Tail：故障后最后一次抢救日志以续链 ⚠️。
11. **最小日志** — Minimal Logging：批量路径只记区间不记行 ⚠️。
12. **写撕裂** — Torn Page：8KB 页对 512B 扇区的部分失败，torn-page detection/校验和的靶子 ⚠️。
13. **日志传送** — Log Shipping：备份链的自动化异地重放 ⚠️。
14. **时间点恢复** — Point-in-Time Recovery：按标记/LSN 停链的剧本 ⚠️✅(Learn)。

## 最新演进与工业实践

- **2012→2017**：AlwaysOn AG 提交/回滚时间与 secondary 可读性持续进化 ⚠️；日志相关的"间接检查点"成为默认争议话题(很多团队显式回 0 ⚠️ 转述)。
- **2019→2022**：RESTORE WITH SNAPSHOT 等还原语义进云；**BACKUP TO URL 直写 S3/Azure Blob**(✅ https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/sql-server-backup-to-url )把"备份链=文件链"落到对象存储，链式恢复的时间点能力保留、运维形态云化 ⚠️。
- **2025 现状**：SQL Server 2025 的 Kubernetes 部署中，PVC + 日志文件布局 + 副本重放构成"有状态容器"三件套(✅ https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-overview 、✅ what's new https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025 )；Azure SQL 托管实例的自动备份/保留策略事实上把本章运维层"产品化没收"，但机制叙事仍是考试与故障复盘的底层语言 ⚠️。
