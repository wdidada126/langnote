## 核心精讲（转述 + ⚠️）

### 1. 文件组：逻辑与物理的解耦点
数据文件不直接归表，表→分区→分配单元→页→**文件组**→文件。工程含义：把"热表放哪块盘"变成"把文件组放哪"，为后来的分层存储/tiering 与分区对齐(本册 [06-特殊存储与特殊索引.md](06-特殊存储与特殊索引.md))埋线；物理设计通论可对照 [../Physical_Database_Design/00-总览与阅读地图.md](../Physical_Database_Design/00-总览与阅读地图.md) 的 placement 章节 ⚠️。✅ 现代准绳：https://learn.microsoft.com/en-us/sql/relational-databases/pages-and-extents-architecture-guide 。

### 2. 页的账本四件套
PFS(每 8088 页一页：谁在用/是否脏/类型)、GAM/SGAM(扩展区统一/混合分配位图)、IAM(对象→区的反向索引，决定扫描顺序)。"IAM 有序而 extent 内页物理无序"是外部碎片的定义源(05 章呼应)。InnoDB 的 extent=1MB、页 16KB，账本思路同构——对照 [../MySQL技术内幕_InnoDB存储引擎2.md](../MySQL技术内幕_InnoDB存储引擎2.md) ⚠️。

### 3. 日志文件的物理结构先睹
LDF 内是 VLF 的环形序列：活动/非活动边界随检查点与复制进度推进(03 章主场)。文件"无限增长"事故的通解不是"删日志"而是"截断点为何不能前移"(LOG_REUSE_WAIT 诊断线) ⚠️。✅ 现代准绳：https://learn.microsoft.com/en-us/sql/relational-databases/logs/the-transaction-log-sql-server 。

### 4. tempdb：公共厕所效应（转述 ⚠️）
内部对象(排序/哈希工作区)、版本存储(RCSI/SI 行版本)、用户对象(#临时表)三类负载共用它；2012 时代分配争用(PFS/GAM latch)的经典药方是"每 CPU 一文件、8 的倍数起步、等大小"——此建议在后续版本随 GAM 缓存与 eager writer 演化而弱化 ⚠️，见演进节。工作区溢出与 07 章内存授予相连。

### 5. 快照与 resource 库
数据库快照=源库只读视图 + 首写前把被改页复制进稀疏文件；源库每页最多保留一份副本，所以"任意时刻回滚"只对分钟级审计友好，不是备份替代品 ⚠️。resource 库(只读、隐藏、升级即替换文件)解释了"系统视图物理在哪"的历史悬案 ⚠️。

## 🔧 类比实验 E1 · 文件头里的"页大小宪法"（SQLite 3.45.3，python 内置）

**非本书引擎行为，仅通用机制演示**：SQL Server 页固定 8KB 写进架构；SQLite 页大小建库时可定(512–65536)。对照实验看"页作为 IO/分配原子单位"的普适性。

```
con=sqlite3.connect('e1.db'); PRAGMA page_size=4096;
CREATE TABLE t(id INTEGER PRIMARY KEY, name TEXT); 插入 200 行 'rowNNN'
读文件第 16–17 字节(大端) → page_size=4096
file size=8192 → 恰好 2 页；表+模式+数据全在页格子里
```
实测：头 2 字节解析出 4096 ✅；200 行文本行占 2 页 ✅。要点迁移：任何页式引擎(SQL Server/InnoDB/SQLite)的"行装箱、碎片、膨胀"都从页字节预算推导——SQL Server 还要额外扣 96 字节页头 + 行尾偏移数组 ⚠️(数字未本机验证，属转述)。

## 本章结论速记

- 数据库=文件组⊃文件⊃扩展区⊃页；表不直接认识文件。
- 四本账(PFS/GAM/SGAM/IAM)决定分配与扫描顺序，是碎片与热点的总开关。
- 日志文件是环：截断=前移复用边界，边界被检查点/复制/镜像钉死(03 章)。
- tempdb 无记忆、有热闹：三类负载共享，启动即重建。
- 快照=页级 copy-on-write，resource=系统对象可替换挂载，contained=用户随库走(2012)。

## 常见误区（转述 ⚠️）

| 误区 | 事实 |
| --- | --- |
| "删掉 LDF 就能救磁盘" | 日志不可缺文件；应备份日志后让截断点前移 ⚠️ |
| "自动增长关掉就稳了" | 不增长=写满即报错；正确姿势是预配+监控 ⚠️ |
| "tempdb 重启才好" | 争用是结构性的，加文件/拆负载才是根治 ⚠️ |
| "快照是热备" | 稀疏文件只留改动前页，源盘故障即全丢，不作备份 ⚠️ |
| "文件越多扫描越快" | 只在并行扫描/分配争用场景成立；过度切分伤管理性 ⚠️ |
| "系统库和用户库一个脾气" | master/msdb 有自己的日志与备份语义(03 章呼应) ⚠️ |

## 转述扩写：库级生命周期与文件运维细目（⚠️ 转述）

### 一页文件的"身份证"
- 数据文件页 0/1/2/3/8/9 存库级元数据(/boot/header/安全页/bitmap/allocation 根)——修复叙事里"前 10 页决定生死"的出处 ⚠️；
- 每文件页头 9 字节：页 ID、对象 ID、索引 ID、**页偏移**、状态位——快照差分页、备份链、DBCC 定位全靠它(04/08 章回扣) ⚠️。

### 创建/附加/分离/还原的状态机
- CREATE：model 库当模板逐页复制(所以改 model 影响所有未来库) ⚠️；
- ATTACH：日志缺失时可重建(LDF 事故的"最后救生圈"，书中含警告与副作用 ⚠️)；
- 还原序列：NORECOVERY 链式接续→RECOVERY 开放——与 03 章"重放剧本"同一台机器 ⚠️；
- 单用户/紧急模式：master 挂了怎么进"最小可修状态"的运维史 ⚠️。

### 增长策略算术（⚠️ 转述示例）
- 10GB 库、1MB 增长=1 万次增长事件；每次增长=元数据写+清零；VLF 碎片化连带拖累日志备份(03 章) ⚠️；
- 书给容量规划的手法："先量峰值日增，再定月度预配，增长只兜底"——Azure 时代的 StorageClass 预配同理 ⚠️。

### tempdb 三负载的分离观察法
- 内部对象(排序/哈希，07 章 spill)、版本(08 章 RCSI/SI)、用户对象(#表/表变量)各自可观测视图不同 ⚠️；
- 容量告急定位顺序：版本存储水位→最大用户对象→内部对象——三步法在 2025 云托管版仍需(平台替你兜了大半) ⚠️。

### 系统库的"脾气差异"表

| 库 | 恢复模型默认 | 备份要点 | 挂了会怎样 ⚠️ |
| --- | --- | --- | --- |
| master | SIMPLE | 配置即数据，改动后立备 | 实例不认识自己的库 |
| model | SIMPLE | 小且低频 | 新库模板丢失 |
| msdb | FULL(默认) | 备份史/作业都在它里面 | 备份系统失忆 |
| tempdb | 不适用 | 不可备份 | 重启重建即愈 |
| 用户库 | 业务定 | 链式+时间点 | 单库事故 |

## 核心概念速览（中英对照）

1. **主数据文件** — Primary Data File (.mdf)：含启动信息与系统表，每库恰一个 ⚠️。
2. **次要数据文件** — Secondary (.ndf)：扩展容量的可选文件 ⚠️。
3. **日志文件** — Log File (.ldf)：VLF 环形序列，WAL 的物理载体 ⚠️。
4. **文件组** — Filegroup：文件的逻辑分组，表落盘的间接层 ⚠️。
5. **扩展区** — Extent：连续 8 页(64KB)的分配单位 ⚠️✅(Learn)。
6. **混合区** — Mixed Extent：最多 8 对象共享，小对象省空间 ⚠️。
7. **PFS/GAM/SGAM/IAM** — 分配账本四件套：页状态/区分配/混合可用/对象→区映射 ⚠️✅(Learn)。
8. **VLF** — Virtual Log File：日志的内部切分单位，增长时切、截断时回收 ⚠️。
9. **页偏移** — Page Offset：文件在备份链中的坐标，增量/还原的锚 ⚠️。
10. **tempdb** — 系统工作区：启动重建，排序/版本/临时对象的公共池 ⚠️。
11. **数据库快照** — Database Snapshot：页级 copy-on-write 只读视图 ⚠️。
12. **包含数据库** — Contained Database：2012 新特性，用户/策略随库走 ⚠️。
13. **resource 库** — Resource Database：只读系统对象载体，替换文件即升级 ⚠️。
14. **写前复制** — Copy-on-Write：快照与日志共同依赖的页保护原语 ⚠️。

## 最新演进与工业实践

- **2014–2019**：内存优化表(OLTP 引擎)走"无文件页"路线，与本章文件世界观并立(✅ https://learn.microsoft.com/en-us/sql/relational-databases/in-memory-oltp/overview-and-usage-scenarios ，[../../db/Hekaton.md](../../db/Hekaton.md) )；2016+ PolyBase/大数池把"文件组分层"升级为异构数据源路由 ⚠️。
- **2022–2025**：**备份直写 URL(S3/Azure Blob)**让"文件=磁盘物件"的旧边界外移 ✅( https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/sql-server-backup-to-url )；SQL Server 2025 的容器化/Kubernetes 部署使 .mdf/.ldf 落到持久卷与存储类调度上——本章"文件放哪"的问题升维为"块存储 + 拓扑感知"云问题 ⚠️( ✅ https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-overview 、what's new 2025 ✅ https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025 )。
- **tempdb 药方演变**：现代版本(2019+)默认多文件 + 内存中优化，"一 CPU 一文件"教条淡化 ⚠️ 转述；Azure SQL DB 彻底托管掉文件组决策。
- **工业实践**：容量规划三件套仍为——文件预配、增长事件监控、日志复用等待告警；页大小教条(8KB)未变，变的是"对象可以不落页"(列存/内存表/向量索引 ⚠️)。
