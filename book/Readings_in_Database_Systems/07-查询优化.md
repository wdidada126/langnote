# 07 查询优化：Volcano、Eddies 与渐进优化——Selinger 之外的第二条血脉（书第 7 章 Query Optimization）

> 对应书章：Chapter 7，评论作者 Joseph M. Hellerstein，小节：Volcano/Cascades / Adaptive Query Processing / Eddies / Progressive Optimization / Discussion。
> 收录：① Graefe & McKenna, *The Volcano Optimizer Generator: Extensibility and Efficient Search*（ICDE 1993）；
> ② Avnur & Hellerstein, *Eddies: Continuously Adaptive Query Processing*（SIGMOD 2000）；
> ③ Markl, Raman, Simmen, Lohman, Pirahesh & Cilimdzic, *Robust Query Processing Through Progressive Optimization*（SIGMOD 2004）。
> 定位：第 3 章讲了"查询优化问题的第一次定义"（Selinger），本章讲**它的两大流派之争与三场手术**——
> 这是全书对"优化器"这一 DBMS 皇冠部件最系统的一次编排。

## 核心概念速览（中英对照）

- **两大参考架构** — Two reference architectures：Selinger 的 System R 式（自底向上动态规划）与 Graefe 的 Exodus/Volcano/Cascades 式（自顶向下目标驱动），覆盖当今绝大多数商用优化器
- **优化器生成器** — Optimizer generator (Volcano)：把"规则库+搜索框架"做成可配置引擎，新物理算子/新语言/新执行目标只加规则不改内核
- **自顶向下目标驱动搜索** — Goal-driven / top-down search：以 promise 机制向子计划"许需求"（需要的序、需要的属性），与自底向上枚举对偶
- **扩展性动机** — Extensibility rationale：Volcano 的设计假设是"数据流可用于广泛数据密集应用"——比 MapReduce 早十年的预言（评论点明）
- **自适应查询处理** — Adaptive query processing：计划在执行期可变；动因=流数据/交互探索/外部源无统计/弹性多租户环境/UDF 黑盒
- **Eddies 路由算子** — Eddies / tuple routing：把优化器压进一个数据流算子，每个元组独立选择下一个执行算子；算子顺序/物理实现/调度全部动态化
- **算子内 vs 算子间再优化** — Intra-operator vs inter-operator re-optimization：Eddies 在"数据运动中"重排，IPO 在"阻塞点"上重算
- **渐进优化 (IPO)** — Progressive optimization：阻塞算子（排序/多数哈希连接）消耗完输入处，实测统计 vs 预测对账，随后半程重新优化
- **计划可信度** — Plan bonafides：IPO 把"估计的置信度"带进优化目标——不确定性本身成为成本项
- **基数误差的指数放大** — Cardinality error amplification：多表连接里估计误差沿计划树相乘放大（评论引理论事实），鲁棒性问题的总根源
- **鲁棒性** — Plan robustness：坏统计/新环境下"至少别太离谱"的性质；与"平均最优"相对的目标函数
- **大数据栈的十年倒退** — MapReduce 把阻塞算子当容错机制，令"运动中数据自适应"议题停摆十年（评论原话方向）

## 核心精讲

### 7.1 先摆谱系：为什么红书要两章分讲优化器

Hellerstein 开场（评论大意）：从数据库研究早期起，查询优化就有两个参考架构，覆盖了今天大多数重要实现——

| 谱系 | 出身 | 搜索方向 | 工业代表 |
| --- | --- | --- | --- |
| Selinger/System R | IBM（书第 3 章收录） | 自底向上、动态规划、左深树 | Postgres、MySQL、Oracle（血统上） |
| Exodus→Volcano→Cascades | GRAIL/Exodus（Wisconsin）→Bell Labs→Microsoft | 自顶向下、目标驱动、规则库 | SQL Server（据称 plus 多家闭源）、Greenplum ORCA、Apache Calcite |

"每个数据库研究者都该懂 Selinger；但 Volcano 血脉研究文献里露脸少、实践中渗透狠"——
这句是本章选文的合法性来源。自上而下 vs 自下而上的争论**未分胜负**（评论明说），
且同样的争论在递归查询处理里还有一遍（评论注：Evita Raced 优化器用递归查询语言把两种搜索方向统一实现）。

### 7.2 Volcano 1993：优化器作为"框架"而非"算法"

**解决什么问题**：Selinger 式优化器把"枚举逻辑等价→物理实现→成本"焊死在代码里，
每加一种新算子/新语法/新执行模型要动内核。Volcano 的回答是**软件工程化**：

- **三接口分离**（本目录归纳）：领域语言（XLANG，把"查询"和"数据流程序"统一成图表达）、
  规则引擎（变换以属性文法式的规则注册）、搜索框架（promise 驱动的枚举，
  按需物化搜索空间避免爆炸）；
- **扩展性红利**：新算子=新规则+新属性需求传播；优化器第一次可以被"配置"进不同执行目标。
  评论强调它"比 MapReduce 和大数据栈早十年"就探索了"数据流作为通用执行 substrate"——
  Volcano 的遗产之一是**把查询优化问题一般化为'任何生产-消费图'的优化**；
- **Cascades 才是完成体**：评论诚实补充——选了 Volcano 只因它"最平易近人"，
  爱好者该读 Cascades（解决 Volcano 的多个细节缺陷，如搜索开销的 memo/规则调度），
  它是该方法的现行标准参考。

**为什么被收录 + 落地**：SQL Server 优化器公开继承 Cascades 血统；开源侧 ORCA（Greenplum）
与 Calcite（多后端逻辑优化框架，服务 Hive/Flink/Dataflow 系）是"可扩展优化器"理念的当代放大——
**今天每家有自研 SQL 层的大数据公司，招聘 JD 里那句"参考 Cascades 架构"即本章的回声。**

**取舍**：框架化的税=性能与调试复杂度的隐性成本（规则多→搜索空间爆炸→剪枝启发式越加越多）；
Graefe 论文自带"内行味"（评论原话：写给关心实现的人），红书用它筛读者。

### 7.3 自适应的五个动因（1990s 末清单 → 2026 现状）

Hellerstein 列出的重新思考优化的理由，逐条到今天仍有效：

| 动因（书中清单） | 2026 对应物 |
| --- | --- |
| 流数据上的连续查询 | Flink/Kafka Streams 常驻查询 |
| 交互式数据探索/在线聚合 | Notebook 文化 + 第 8 章近似查询线 |
| 查询 DBMS 之外的数据源（无可靠统计） | 湖仓直读外部表、联邦查询、API/模型端点 |
| 不可预测的动态执行环境 | 云上弹性与多租户干扰（评论点名 elastic/multi-tenant） |
| 不透明数据与 UDF | 向量化 UDF/模型推理函数的黑盒选择率 |

外加一条理论背景：多算子计划的成本估计误差会**组合放大**——纸面上"平均最优"的计划
在统计偏差下可以灾难性劣化。**自适应不是锦上添花，是对"计划编译期一次性决定"的根本不信任。**

### 7.4 Eddies：把优化器变成一个算子

**解决什么问题**：如果计划必须在执行中改，为什么不干脆**取消 planning 与 execution 的边界**？
Eddies（Berkeley）的做法（评论的完整表述很精彩）：

- 优化器被"封装为一个数据流算子"（eddy），穿插在算子网络前：每来一个元组，按当前各算子
  的实测吞吐/选择性动态选下一个——**元组顺序=逻辑计划顺序**；
- 一个机制吃三件事：换序（路由顺序）、物理算子选择（把 join 的多种实现并联、元组投票）、
  调度（缓冲与背压）；多查询可在 eddy 上穿插共享算子；
- 它擅长**长流水与流式**场景：选错算子可以在它"跑完之前"放弃——阻塞式重优化做不到这点。
- 评论还补了历史彩蛋：**最早的 INGRES 优化器本来就有逐元组做优化决策的能力**——
  自适应不是新发明，是被"编译期决定一切"的潮流忘了的老主意。

**为什么被收录**：它代表自适应设计空间的**一极**（激进：粒度=每元组、时刻=随时）；
下一节 IPO 是另一极。读红书要练的就是这种"在空间里标定论文坐标"的本事。

**取舍**：路由本身有每元组开销（Deshpande 等人的实现改进被评论点名）；它放弃
"一个可解释的静态计划"，对 DBA 文化与查询日志分析是双刃剑——这也是它商业渗透远不如
渐进派彻底的原因（本目录判断，标注为推论）。

### 7.5 IPO（Markl et al. 2004）：给 System R 式优化器装反馈回路

**解决什么问题**：IBM 的 DB2 路线：不推翻 Selinger，**在它的关键弱点上打补丁**——
基数估计错导致连接顺序灾难。机制：

1. 利用**阻塞算子**天然存在的"输入消耗完毕"时刻（排序、多数哈希连接）：
   实测统计 vs 优化器预测对账；
2. 用"计划可信度（bonafides）"重定义优化目标：不只是估计成本，还要估计"这个成本的把握有多大"，
   把握低就重优化后半程；
3. 结果：对多连接查询在坏统计下保住 2–10 倍级的劣化不再发生（论文实验口径，大意）。

**与 Eddies 的正交性**（评论明说，两派共存的设计图）：eddy 管**算子内/运动中**（数据"在动"时），
IPO 管**算子间/静止点**（数据"停下"时）；原则上可以把 eddy 塞进带阻塞点的计划里同时用。

**为什么被收录**：它是"鲁棒性"从形容词变成可优化目标的标志论文；且它直接教读者
**如何评估一篇优化器论文的立场坐标**（改多少 Selinger / 改多少执行模型 / 优化粒度多细）。

### 7.6 Discussion：Hellerstein 对大数据十年的开炮（本章最锋利的段落）

评论的批评链（按原文方向整理）：

- MapReduce **"在执行模型里引入阻塞算子作为容错机制，使运动中数据自适应的讨论倒退了十年"**——
  2000s 中后期几乎无法就流水线内优化进行合理讨论，因为它与 Hadoop 容错模型不相容；
- 社区花了太长时间才接受"SQL/LINQ 式声明接口是好的通用接口"；即便接了 Hive，
  **查询优化仍被少讨论、差实施**——"也许优化器比执行器难得多，也许是商业与开源的历史质量鸿沟"；
- 判词：无论开源大数据界还是研究界，**关注查询优化都太慢了，这对两边都不利**。
  到评论写作时，Tenzing/F1/Dremel/DryadLINQ/Naiad/Spark/Impala/Tez/Drill/Flink
  已经"相似多于差异"，而本章列的自适应动因问题**在大世界讨论中依旧热门、依旧没被处理好**。

**2026 验收（书外补充）**：现代引擎各认领了一格——AQE（Spark Adaptive Query Execution 的运行时
重排序，IPO 的直系还魂）、CTE/计划缓存鲁棒性（各云数仓）、向量化与编译执行（第 4 章线）、
湖仓统计自动采集（Auto Stats）。Hellerstein 点名的"动因清单"一条没少，只是处理它们的
公司从商业 DBMS 换成了"云+开源"双轨。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "Volcano 和 Cascades 是一篇论文的两个名字" | 两代系统；Cascades 修了 Volcano 的若干缺陷并被作者阵营视为标准参考（红书选 Volcano 只为可读性，评论自注） |
| 2 | "自适应=运行时重优化（re-optimization）的同义词" | 本章给了坐标系：重优化的**粒度**（元组/算子间）、**时刻**（运动中/阻塞点）、**代价**（保留/取消计划边界）三轴不同组合才是完整分类 |
| 3 | "Eddies 失败证明静态计划就够了" | Eddies 的每元组路由开销是真问题，但它的思想（把选择率反馈进路由）在 AQE/云数仓里活着；红书选它因为**空间位置**，不是因为推荐照抄 |
| 4 | "大数据栈不关心优化器是因为不需要" | 评论给的是反向因果：容错模型先定（MR 阻塞点），优化议题被制度性压制了十年 |
| 5 | "Selinger vs Volcano 已分胜负" | 评论原话：没分胜负；两边都有活的用户；争论同构地再现于递归查询优化（Evita Raced 统一两种搜索） |
