# 06 弱隔离与分布式：从广义隔离定义到 CAP 的落地（书第 6 章 Weak Isolation and Distribution）

> 对应书章：Chapter 6，评论作者 Peter Bailis，小节：Overview and Prevalence / Reasoning about Anomalies /
> Weak Isolation, Distribution, and "NoSQL" / Trade-offs and the CAP Theorem / Programmability and Practice。

> ② DeCandia, Hastorun, Jampani, Kakulapati, Lakshman, Pilchin, Sivasubramanian, Vosshall & Vogels,
> *Dynamo: Amazon's Highly Available Key-Value Store*（SOSP 2007）；
> ③ Brewer, *CAP Twelve Years Later: How the "Rules" Have Changed*（IEEE Computer 45(2), 2012）。
> 本章与第 3 章互为镜像：第 3 章建"事务巴别塔"（Gray 度数、ARIES、2PC），
> 本章拆它——**"可串行化在现实中几乎没人真用"是本章给出的、有调查证据的第一句话。**

## 核心概念速览（中英对照）

- **弱隔离** — Weak isolation：不保证可串行化的并发控制模式的统称；事务可能观察到串行执行中不可能出现的异常
- **异常现象** — Anomaly：脏读、不可重复读、幻读、丢失更新等"在可串行化下不该出现"的可观察行为
- **多版本串行化理论** — Multi-version serialization theory：Adya 用带版本号的读写事件图刻画并发历史，隔离级别=对图形态的约束
- **广义隔离级别定义** — Generalized isolation levels：以 G0(冲突可串行)/G1(不允许读废弃/中间/回滚写)/G2(反依赖环禁止) 系谱替代 ANSI 含糊表
- **法定数协议** — Quorum (R+W>N)：读写副本数之和过多数则"逻辑上"无间隙；Dynamo 的实际保证远弱于此直觉
- **斜法定数** — Sloppy quorum：R+W>N 不保证交集含最新写入（可能落在暂存副本上），"读己之写"要靠别的机制
- **提示移交与读修复** — Hinted handoff & read repair：不可达节点的写先由邻居代管后移交；读时发现版本不一致顺手修复——用最终一致换始终可用
- **版本向量** — Version vector / causality tracking：记录副本间因果历史的向量，冲突由客户端 resolve——"并发写都合法"的代价
- **CAP 定理** — CAP：一致性、可用性、分区容错三者 partition 发生时只能保两个
- **PACELC** — PACELC（Brewer 2012 重述）：无分区时也存在延迟-一致性权衡（latency vs consistency otherwise），"C vs A"只是特例
- **最终一致性光谱** — Eventual consistency as a spectrum：评论点名它不是单一性质而是一束（收敛性/会话保证/单调性……）
- **协调的账单** — Coordination cost：2PC/锁/法定数共识的延迟与吞吐代价，驱动厂商滑向弱隔离（第 3 章 R\* 的续集）

## 核心精讲

### 6.1 现实普查：可串行化是少数派

评论的第一组事实（Bailis 团队 2015 年前后调查，18 个 SQL/NewSQL 系统）：

- 仅 3 个默认提供可串行化；8 个**根本不提供**（评论点名含 Oracle 与 SAP）；
- 术语欺诈常态化：Oracle "SERIALIZABLE" 实际是快照隔离——这个标签官司从 Berenson 等 1995
  《A Critique of ANSI SQL Isolation Levels》一路打到本章；
- **商业逆淘汰**：厂商 A 把默认档从可串行化降到读已提交后，仍默认串行化的厂商 B 在销售中落败
  （"你的系统更慢"），B 随后跟进——**隔离级别是竞争品，不是安全品**。

性能账（评论引 Bernstein 观点）：单机上串行化相对读已提交常有多倍损失；分布式的网络往返让
"持锁关键段"更长，劣化条件可达**多个数量级**（Bailis 自己的协调避免研究即此句的出处）。

### 6.2 Adya 2000：给异常立法

**解决什么问题**：弱隔离的规范史是一部"含糊史"——ANSI SQL 的英文描述多种读法、形式化又
覆盖不了锁实现的全部行为、快照隔离被发明时 ANSI 表里根本没有它。Adya 的贡献（评论口径）：

1. 把 Bernstein 多版本串行化图论改造成**异常的定义语言**：以读写冲突边（ww/wr/rw）与
   版本号构建历史图，每种隔离=禁止某类环/边形态——G0 冲突可串行、G1 三条禁止项（不读未提交、
   不读已回滚、不读"反写"）、G2 禁止抗依-读写环。
2. **实现无关**：锁/时间戳/乐观/MVCC 都被同一张图刻画——ANSI 做不到的正是这条。
3. 遗留问题评论也不回避：G0 在"不涉及读"时仍有含糊；不同引擎对同一级别的实装范围不一致——
   所以"看文档不如看图定义"成为本章给读者的实操建议。

**为什么被收录**：它是第 3 章 Gray"度数"的正规化续集——度数给词，Adya 给语义。
红书把两篇隔了 4 个章节互为回链：**隔离级别的词汇表，前一半在 03 文件，后一半在这里。**
（而词汇表的"产品名与实装漂移"，仓库在 Gray 1981 精读里另有一层"概念发明者自己都没料到"的历史纵深：
[../../paper/doi_1981_gray_transaction_concept/00-精读笔记.md](../../paper/doi_1981_gray_transaction_concept/00-精读笔记.md)。）

**推理之难的本质**（评论反复强调）：要判断弱隔离是否安全，程序员必须把**应用层不变量**
翻译成**低层读写行为**再逐异常排查——连并发专家都常翻车。最有说服力的"为什么居然没事"答案是
**多数应用并发度本来就低**：无并发时弱隔离自动给出串行结果；Facebook 最终一致存储读到过旧结果
的概率实测约 0.0004%。评论的警示同样明确：Flexcoin 攻击者用程序化并发读-改-写掏空交易所——
**"没并发"是运气，不是设计。**

### 6.3 Dynamo：为"永远在线"写一份架构自首书

**解决什么问题**：亚马逊购物车——写路径要**恒定低延迟高可用**，业务能容忍偶尔的旧读与冲突
（同 SKU 数量最终调对就行）。Dynamo 的每个决策都是对第 3 章正统的定向放弃：

| 正统（第 3 章） | Dynamo 的替代 | 换到什么 |
| --- | --- | --- |
| 单写主+锁/法定数读 | 全副本可写（sloppy quorum, R+W>N 仅概率性） | 写路径不依赖"谁在线" |
| ARIES：数据永不丢 | 副本数减一仍可服务，接受修复窗口 | 可用性优先 |
| 2PC 原子跨节点 | 冲突暴露给客户端：版本向量+last-writer-wins 可配 | 一致性变成应用层函数 |
| 隔离级别（引擎保证） | 无事务语义（接口层） | 正确性整体外移 |

评论的框架：Dynamo 是**"弱隔离+分布式的 NoSQL 化身"**——它把 Adya 式规范缺失直接演成产品现实：
文档里的"最终一致"对工程师的实际含义是"你拿到几份版本、自己合并"。**hinted handoff 与 read repair
是本章最该背下来的两个机制**：用后台修复替代前台协调，用带宽换尾延迟。

**为什么被收录**：不是因为它对（Bailis 明说其保证"比法定数直觉弱得多"），而是因为它**让一整个
设计象限可触摸**，此后十年的"共识 KV/多模型/CRDT 文档库"都在与它对照定义自己。

### 6.4 Brewer 2012：亲手拆掉自己的口号

CAP（2000 猜想、2002 Gilbert-Lynch 证明）到 2010s 成了"2/3 必丢一"的营销万能贴。Brewer 亲自撰文修宪，
评论摘其要：

1. **分区不是二选一的开关，是概率事件**；C 与 A 的取舍实际发生在**每个操作、每个数据项粒度**，
   不是系统级站队。
2. **无分区时仍有取舍**：一致 vs **延迟**（进而吞吐）——这就是 PACELC 记法的由来（Else/ Latency）。
   把"选 AP/CP"当架构决策的终点、而不是起点，是十年间最昂贵的误读。
3. **最终一致性是一个光谱束**：收敛只是最弱承诺；会话保证（读己之写、单调读、前缀一致、单调写）
   才是工程可消费的单元。"用最终一致性"这句话信息量为零。
4. **银行案例**（评论引用）：分区两侧各自放款=业务灾难，但解法不是"选 C"，而是
   **把不变量设计进数据分布**（分区内自治/单点写主/跨区走异步对账）——"CAP 不豁免建模责任"。

**红书编排的用心**：Adya（语义）→ Dynamo（放弃语义）→ CAP（放弃的宪法），三篇构成
"弱隔离"的**定义、标本与法理**。第 9 章 Bloom/CALM 将给出第四条路（逻辑上免协调），第 3 章
R\* 的 2PC 则是被绕开的对象——建议按 03→06→09 顺序读这条暗线。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "R+W>N 保证读到最新写" | sloppy quorum+提示移交下不成立；最新性要靠向量/会话保证/读主 |
| 2 | "CAP=三选二，系统要定阵营" | Brewer 2012 已作废该口号：取舍按操作在 C-A 与 L-C 两轴上取点 |
| 3 | "最终一致性= eventual= 会自己好" | 光谱束总称；不加会话保证时连"读自己刚写的"都不成立 |
| 4 | "我们并发低，RC 够安全" | 评论同意"多数时候没事"，但 Flexcoin 说明攻击/事故恰好制造那部分并发；要按"设计"而非"运气"过审 |
| 5 | "快照隔离=可串行化的一种实现" | 它是独立弱级别（GSI）；写偏斜异常是它的经典死法——Adya 的 G2 就是为抓它 |
| 6 | "NoSQL 都是弱一致" | 第 4 章的内存 OLTP 与新共识库都在强一致侧；红书自己就把 NoSQL 定性为"过渡形态" |
