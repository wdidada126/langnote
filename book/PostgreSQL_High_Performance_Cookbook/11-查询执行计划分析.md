## 11.3 代表配方精读

### 配方：Timing overhead 与冷热缓存（实验方法学组）

- 主张：任何"这条 SQL 快慢"结论前先回答三问——**计时本身多少开销？缓存热否？跑了几次？**
  `\timing on`+3 次取中位数；冷缓存用可重现手段（重启服务或大表扫描挤出缓冲，⚠️ 细节转述）。
- 与第 1 章 X-B 实验同构：并行/缓存形态不控制，数字全是噪声（DuckDB 实测 threads=1 无差异即教训）。

### 配方：Query plan node structure / Computing basic cost

- EXPLAIN 树的读法：缩进=执行顺序（最内先执行）；每节点 `(cost=startup..total rows=width=)` 语义；
  ANALYZE 版加 actual time/rows/loops——**loops 列是嵌套循环陷阱的照妖镜**（当日强调，至今金规）。
- cost 模型最小直觉：`random_page_cost=4`（HDD 遗产默认）在 SSD 上系统性歧视索引扫→坏计划来源；
  调参前先测真机（第 1 章 seek/IOPS 在此兑现）。`effective_cache_size` 影响选择率外推。⚠️ 转述，✅ 手册
  https://www.postgresql.org/docs/current/using-explain.html、/runtime-config-query.html（curl 200）。
- **bitmap scan 专讲**（配方 9）：位图收集多索引命中页→按物理序回表，解决"多个中等选择率索引
  交叉条件"；`BitmapAnd/BitmapHeapScan` 节点的 lossy/recheck 计数是 2026 排障常客（EXPLAIN
  ANALYZE 的 `Lossy Pages` 行 ✅ 手册域）。

### 配方：CTE scan 与优化围栏（时代分水岭）

- 9.6/10 基线：CTE 是**优化围栏**（先物化再参与外层计划），作者演示其代价；PG12 起非危险/单引用
  CTE 自动内联 + `MATERIALIZED/[NOT] MATERIALIZED` 手动闸——当年"CTE 慢"配方 today 需按版本分叉。⚠️
- 嵌套循环配方：小外表+索引内表=最优解，行数误估 1 行 vs 百万行=NL 灾难——统计（08 章）与
  计划（本章）在此闭环。

## 11.6 🔧 类比实测（非 PostgreSQL 行为；PG 不可装 ✅ where psql 无输出）

- **X-E（sqlite3 3.45.3 + DuckDB 1.5.5）**：
  - sqlite `EXPLAIN QUERY PLAN`：无索引 `SCAN t` → 建 `ix_t_b` 后同查询变
    `SEARCH t USING COVERING INDEX ix_t_b (b=?)`——"节点结构换形"的最小标本；
  - **部分索引 px_t_b 在场时规划器仍选全量索引 ix_t_b**（SELECT s 需回表场景实测）：
    "候选索引≠被选索引"，成本/覆盖判断先行——与 PG 的索引选择教训同构；
  - DuckDB 计划算子链实测：`TOP_N → PROJECTION → PERFECT_HASH_GROUP_BY → PROJECTION×2 →
    HASH_JOIN → SEQ_SCAN(300,000) + SEQ_SCAN(1,000)`，含基数估算 `~97/~1,000 rows`——列式引擎
    也有"树+cost"抽象，读 PG 计划的技能可迁移；⚠️ 算子语义严禁互推（无回表/位图等概念）。

## 高频坑与实操清单

- `work_mem` 的正确心智=**每排序/哈希节点**而非每查询，再乘并行 worker 数：单条复杂 SQL 吃爆
  内存的经典算法是 plan 节点数 × 声明值。
- `enable_seqscan=off` 一类开关只用于取证，写进生产配置=给优化器戴眼罩做手术。
- EXPLAIN ANALYZE 会**真执行** DML：测大写查询用 `ROLLBACK` 包裹或 GENERIC_PLAN/只读副本（PG15+
  选项 ⚠️），别在生产主库裸跑。
- loops 列陷阱：`(never executed)` 与 `rows=1 loops=99999` 比单看 time 更能定位"外表巨大"。
- 冷/热缓存差异大于多数参数调优：对照组永远声明缓存态（本章配方 3/4 的存在理由，X-B 数字为鉴）。
- 函数/表达式无统计→行数拍脑袋（默认 1000）：外层 JOIN 策略全歪，拆临时表或扩展统计对象对症。
- CTE 读写两用：PG12+ 含 DML 的 CTE 仍物化、普通 CTE 默认内联——"CTE 强制物化优化"的老 trick
  按版本反转，跨版本脚本要分支。⚠️
- 计时纪律（配方 2）先于一切结论：`\timing` 分辨率、客户端往返、popen 开销都算进"查询时间"。

## 核心概念速览（中英对照）

- **执行计划** — Query plan：优化器选定的算子树，SQL→物理操作的施工图。
- **解释分析** — EXPLAIN ANALYZE：真跑并回报每节点 actual time/rows/loops。
- **代价模型** — Cost model：启动/总代价双数，单位≈磁盘页读取当量。
- **随机页代价** — random_page_cost：成本模型对随机读的惩罚系数，SSD 上首调参数。
- **有效缓存尺寸** — effective_cache_size：优化器眼中的 OS+PG 缓存合计，影响索引选择。
- **顺序扫描** — Sequential scan：全表页扫，大表低选择率下反而最优。
- **位图扫描** — Bitmap heap/index scan：多索引命中合取为位图、按页序回表。
- **哈希聚合** — Hash aggregate：内存哈希表聚合，超 work_mem 转外部排序。
- **公用表表达式** — CTE：9.6=物化围栏，PG12+ 默认可内联。
- **嵌套循环** — Nested loop：外表行驱动内表查找，行数误估即灾难。
- **循环计数** — loops：ANALYZE 输出中该节点被执行次数，识破"单次便宜总巨贵"。
- **并行计划** — Gather/Workers：9.6 起的并行节点呈现，读计划需带视角。

## 最新演进与工业实践

- **并行查询十年**：9.6 并行扫描（本书基线）→10 并行 JOIN/聚合部分→11 并行 VACUUM→12 并行
  INSERT/CREATE TABLE AS→14 分区表并行裁剪→16 并行 FULL/RIGHT JOIN 与增量排序并行→17/18 继续
  扩面（⚠️ 逐版细节转述）。✅ https://www.postgresql.org/docs/current/parallel-query.html（curl 200）。
- **JIT 编译**：PG11 起 LLVM 表达式/黑盒内联编译（`jit`/`llvm_above_cost` 族，默认只对高 CPU 查询
  生效），2017 章内"解释执行"前提已部分改写。⚠️ 转述，✅ runtime-config-query 同页。
- **EXPLAIN 选项族**：BUFFERS(WAL/GENERIC_PLAN/MEMORY(PG18 ⚠️))、`EXPLAIN (ANALYZE, SETTINGS)`
  （PG15 提示非默认参数）成排障标配；auto_explain 采样自动化。⚠️
- **优化器新件**：增量排序（PG13）、lead/lag IGNORE NULLS（PG14）、MERGE（PG15）、并行+向量化式的
  表达式求值改进与 IO 统一栈（PG18，⚠️）——当日"坏计划"清单半数已被内核消化。
- **工业实践**：计划治理平台化——外部工具承接本章手工课：pg_hintman（计划钉选/规范 SQL，pgEdge 线 ⚠️）、
  HypoPG（假设索引试算 EXPLAIN，✅ 扩展名属常识、细节 ⚠️）、`pg_stat_statements` 慢查询榜+auto_explain
  采样自动化。学习式优化器（Lero/Neo 等论文系）⚠️ 本次未做 DOI 校验，只留名不入引用；真产主流仍是
  统计（扩展统计对象）+计划钉选+SQL 重写三板斧。
