## 1.1 本章定位

全书第一块基石：**先测机器，再调数据库**。作者在本章把"性能问题的硬件边界"量化成一套可复制的
基准流程——CPU（himeno 浮点分）、内存、磁盘顺序/随机、fsync 提交率、IOPS，最后落到存储容量估算
与 pgbench 压测。这是 cookbook 体裁的典型写法：每道配方给命令、给判读标准，不讲操作系统原理
（原理留给第 4 章与 repo 里的 [../Database_Tuning/00-总览与阅读地图.md](../Database_Tuning/00-总览与阅读地图.md)）。

## 1.3 代表配方精读

### 配方：CPU benchmarking（pts/himeno）

- **做法**：`phoronix-test-suite benchmark pts/himeno`，装套件→跑 3 轮→看标准差与均值
  （官方 README 实录样例：1503.6/1512.2/1550.9，均值 1522.27 MFLOPS，Std. Dev 1.66%）。
- **判读要点**：作者强调**多次运行取离散度**——单次数值没有意义，这与其 README 样例中
  `[Std. Dev: 1.66%]` 的呈现方式一致。基准的目的是给"数据库慢是否怪 CPU"画一条可复核的线。
- **2026 评注**：PTS 仍在维护（phoronix-test-suite 开源 ✅），但更常见的做法已换成 `stress-ng`、
  UnixBench 或直接 `pgbench` 端到端；himeno 解泊松方程对现代多核的标度也一般——选型需重测。⚠️

### 配方：Working with the fsync commit rate / Checking IOPS

- **做法**：用 `pgbench -S`（只读点查）与读写混合分别压 `synchronous_commit` 开/关两档，
  比较 TPS 与 `iostat -x` 的 `await/%util`；seek rate 测试则回答"这台盘的随机 4K 能力上限"。
- **原理**：OLTP 提交延迟被 WAL fsync 钉死，盘的 fsync 延迟≈每事务成本下界；这为第 3 章
  WAL/检查点配方埋下"写放大"预算。⚠️（原理为通用共识转述，本册 PG 行为不实测）
- **坑**：RAID 卡写缓存带 BBU 时 fsync 语义被硬件改写，裸盘数字与生产数字会差一个量级——
  作者本章要求先记录硬件拓扑再谈数字。✅（该要求可从 recipe 行文结构核对，细节 ⚠️）

### 配方：Storage sizing 与 pgbench 读/写用例

- sizing 三要素：表+索引+**WAL 与膨胀余量**（第 9 章会回收这个坑：膨胀可让实际占用远超逻辑量）+
  备份副本空间。pgbench 配方给出 init/TPC-B 只读/TPC-B 读写三种跑法，作为"交付前验收数字"。
- **方法学**：任何调参结论必须能表述为"同一 pgbench 脚本，改 X 前 TPS=A±s，改后 TPS=B±s"。

## 1.7 适用性判断（2026 视角）

硬件基准配方思路**依旧成立且必要**（NVMe/NVMe-of/CXL 内存让"边界"变了但方法没变）；具体工具面
（PTS+himeno、seek rate 的写法）已老，fio 的现代用法与 `io_method` 新档（PG18）应替换之——见文末。

## 高频坑与实操清单

- 基准数字未附硬件拓扑（RAID 缓存/盘型/NUMA）=无效数字——先拍拓扑再跑分。
- 备份/归档窗口内跑基准：await 被后台 IO 污染，测出的"盘能力"是幻觉（与 07 章互斥排程）。
- RAID 卡 BBU 写缓存改写 fsync 语义：裸盘 fsync 测试与生产路径不同构，需按真实卷重测。⚠️
- pgbench 客户端数要与连接池档位对齐（05 章）：`-c 200` 直连生产配置可能先压垮连接层而非数据库。
- 只跑一种负载形态：himeno 高分不代表嵌套循环快，X-B 已示范"DuckDB 小聚合并行无增益"——负载形状决定并行收益。
- 交付验收留档：基准三件套（CPU/盘/端到端 pgbench）数值+命令+日期入工单，后续所有调优引用同一基线。
- 云盘双桶配额（IOPS 与吞吐各限其一）：fio 曲线要在两个桶边界各测一次。⚠️

## 核心概念速览（中英对照）

- **基准测试** — Benchmarking：用可重复的标准负载给硬件/系统定"能力基线"，一切调优以此为锚。
- **浮点基准** — CPU benchmark (himeno)：解 3D 泊松方程的浮点吞吐测试，单位 MFLOPS。
- **寻道率** — Seek rate：磁盘每秒随机 4K 定位次数，OLTP 点查的硬件上界。
- **每秒输入输出** — IOPS：单位时间完成的 IO 请求数，需与块大小/读写比一起报。
- **同步提交率** — fsync commit rate：每事务 WAL fsync 的耗时分布，决定 OLTP 延迟下界。
- **容量规划** — Storage sizing：表+索引+WAL+膨胀+副本的空间总账，预留余量。
- **压测工具** — pgbench：PG 官方基准工具，TPC-B 简化版读写/只读脚本。
- **离散度** — Standard deviation：多次基准结果的标准差，作者用它判定基准是否可信。
- **写放大** — Write amplification：一次逻辑写触发数倍物理写（WAL+检查点+脏页）。
- **等待时间** — await（iostat）：IO 请求平均排队+服务时间，%util 之外的核心判读指标。
- **硬件拓扑** — Hardware topology：RAID 卡/缓存/盘型/NUMA 记录，基准数字的解释上下文。

## 最新演进与工业实践

- **PG 基线迁移（本章 2017 视角=9.6/10）**：现代 PG 单机并行体系已彻底改变"CPU 基准"的含义——
  并行查询自 9.6 引入、11/12/13/16 逐代扩面（并行聚合/并行索引扫描/并行 FULL/RIGHT JOIN 等），
  官方文档 ✅ https://www.postgresql.org/docs/current/parallel-query.html（curl 200，2026-09-27）。
- **IO 栈最大变量——异步 IO**：PG18 引入 `io_method` GUC（worker/io_uring 可选）与组合读写
  （io_combine_limit），预读路径重写；硬件基准必须新增"io_method 档位×fio 曲线"维度。
  依据：官方资源文档 ✅ https://www.postgresql.org/docs/current/runtime-config-resource.html 与
  PG18 发行注记入口 ✅ https://www.postgresql.org/docs/release/18.0/（细节 ⚠️ 转述）。
- **pgbench 现状**：仍是官方交付验收标准件，新增 `--persistent`、脚本变量、预处理语句支持（PG12+，⚠️）；
  工业界云环境更多用 HammerDB（TPC-C/TPC-H 全量）与 Sysbench 交叉验证。⚠️
- **工具换代**：Phoronix Test Suite 仍开源维护 ✅（github.com/phoronix-test-suite 存在性）；fio 为事实标准，
  himeno 一类合成分数让位于"直接 pgbench/TPC-C 端到端 + perf 火焰图定位"的实践。⚠️
- **服务器硬件面**：NVMe 多队列、Optane 退市后的 QLC 取舍、持久内存式样变化——2017 章内"seek rate 测试"
  对 NVMe 需换成队列深度 QD32/64 的随机 4K 读写混合曲线。⚠️
- **版本现状锚点**：截至 2026 年 PG 稳定大版本为 17（2024-09-26 发布）与 18（2025-09 发布），
  支持策略见 ✅ https://www.postgresql.org/support/versioning/（curl 200）。
