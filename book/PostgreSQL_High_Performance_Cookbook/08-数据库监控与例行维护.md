## 8.3 代表配方精读

### 配方：blocked sessions 与长事务（监控组的枢纽）

- 2017 做法：pg_locks 自连接查 `granted=false`（txt 风格 ✅）；PG9.6+ 起 `pg_stat_activity` 的
  `wait_event_type='Lock'` + `pg_blocking_pids()` 成为标准答案——**同一问题两代 SQL**，本章正好
  留下断层切片。⚠️/✅混合（函数引入版本为社区常识转述）。
- 长事务三重罪：膨胀（第 9 章）、vacuum 无法推进、复制槽堆积——本章教会"先看见"，第 9 章教"怎么治"。

### 配方：Preventing page corruption

- 关键动作：initdb `--data-checksums`（建库后不可加，只能重做/逻辑迁移——当日即警告 ✅ 语义，⚠️ 细节）、
  `data_checksums`/`wal_log_hints` 与 amcheck 缺席的 2017 年代主要靠"防+备"两手。
- 现代对应：pg_amcheck（PG10+）把"巡检"变一等公民，见
  [../PostgreSQL_10_High_Performance_3e/16-过渡表触发器与amcheck等.md](../PostgreSQL_10_High_Performance_3e/16-过渡表触发器与amcheck等.md)。

### 配方：Routine reindexing 与 REINDEX 的锁经济学

- 立场还原：当年"索引膨胀→定期 REINDEX"是流行护养；作者给出按表/按库 REINDEX 与停机窗口权衡。
- **今天的反驳**（B-tree 膨胀假设被多路证据修正）：根页分裂才是主因、REINDEX 持 ACCESS EXCLUSIVE
  阻塞一切；替代=`REINDEX CONCURRENTLY`（PG12+）或干脆不重建（14+ 改进）。本章这条配方是
  "保质期最短"的典型——读时必须带演进节。⚠️

### 配方：ANALYZE / 统计与 bgwriter 调优

- `ALTER TABLE ... SET (autovacuum_analyze_scale_factor=0.02)` 对大表热点提密（✅ txt 有 autovacuum
  按表参数域实录，见 09 章互指）；`default_statistics_target` 的均匀加税警告。
- bgwriter：`bgwriter_delay` + `checkpoint_completion_target` 联合判读 `pg_stat_bgwriter.buffers_backend` 占比——
  "bgwriter 没干活，backend 在自刷脏"的诊断句式（⚠️ 转述）。PG14+ 默认策略转向"让 checkpointer 多干、
  bgwriter 少干甚至关闭"（bgwriter 参数新默认，⚠️），当日配方方向已反转。

## 高频坑与实操清单

- 忘了 `track_counts=off` 会连 autovacuum 决策一起瞎（统计断供）——测试环境参数严禁漂移到生产。
- 会话观测要看 `backend_type`/`state` 组合：`idle in transaction` 才是阻塞链上游的常客，active 只是表象。
- REINDEX 全库在高峰期=集体停摆（ACCESS EXCLUSIVE 排队雪崩）；升级后第一件事：把本章 reindex 脚本
  换成 CONCURRENTLY 版或删除循环。⚠️
- checksums 建库后不可加：需要时走"新簇+逻辑迁移"（10 章路径），别信"在线打补丁"传言。⚠️
- `log_min_duration_statement` 抓不到"排队慢"：等锁时间不记入语句时长，锁观测走 `log_lock_waits` 专线。
- ANALYZE 时机：大批量写入后、pg_upgrade 后、恢复演练后——三个"统计真空期"列进 runbook 检查单。
- 磁盘占用报表要把 `pg_wal`、临时文件、膨胀三源分列（04/03/09 章各管一段，混在一起就都说不清）。
- 例行维护窗口与备份窗口错峰：reindex/vacuum full 撞上 base backup=两边都慢（07 章排程约束）。
- `default_statistics_target` 全局翻倍=每表 ANALYZE 变慢+计划缓存重估风暴，按列定点加密度。

## 核心概念速览（中英对照）

- **活动跟踪** — track_activities：pg_stat_activity 有 query/state 列的开关。
- **统计收集** — track_counts：计数视图（含 autovacuum 决策输入）的总开关。
- **阻塞链** — Blocking chain：`pg_blocking_pids()` 还原的等锁序列。
- **慢语句日志** — log_min_duration_statement：语句级延迟取证入口。
- **关系尺寸族** — pg_relation_size/pg_total_relation_size：表/索引/FSM/VM 分层占用度量。
- **数据页校验和** — data checksums：initdb 时定的块级 CRC，防静默损坏。
- **重索引** — REINDEX（CONCURRENTLY）：重建索引消膨胀；并发版为 PG12+ 标配。
- **规划器统计** — planner statistics：ANALYZE 产出的直方图/MCV，坏统计=坏计划。
- **背景写者** — bgwriter：后台预刷脏以削 backend 同步刷概率的进程。
- **WAL IO 计时** — track_wal_io_timing：9.6 新观测开关，默认关闭因计时有税。

## 最新演进与工业实践

- **等待事件体系**：PG9.6 wait_event（本章基线）→PG13 IO 类等待事件细分→PG14 backend_type 扩展→
  pg_stat_io（PG16）进程级 IO 统计——"被什么卡住"四问在 2026 已全部有视图。✅
  https://www.postgresql.org/docs/18/monitoring-stats.html（curl 200）。
- **pg_stat_statements 标准化**：2017 尚属"建议安装"，今为托管服务默认+Grafana dashboard 素材核心；
  与 auto_explain 构成语句级+计划级双证据链。⚠️
- **REINDEX CONCURRENTLY（PG12）** 终结"维护窗口 reindex"文化；社区共识转为"膨胀监测+必要时重建"，
  监控项=pgstat 索引尺寸趋势。⚠️
- **巡检工具化**：PGAdmin 4/GetFC 的仪表化、`amcheck` 进发行、`postgres_exporter` 把本章每条 SQL
  变成指标与告警——"看板式例行维护"替代"人肉例行维护"。⚠️
- **统计演进**：扩展统计对象（多列依赖/表达式，PG10+）、ANALYZE 采样质量持续改进（⚠️），
  坏计划归因中"统计不足"占比下降、"结构错位"占比上升——与 12 章结论合流。
