## 2.3 代表配方精读

### 配方：Stopping the server quickly——三档关机的工程含义

- **语义**（⚠️ 通用共识转述 + ✅ 官方手册核对，见文末）：smart 等所有客户端退出；fast 回滚活跃事务、
  断开连接后正常关机（默认推荐）；immediate 崩溃式关机，重启走恢复流程。
- **性能视角**：immediate 把关机成本转嫁为下次启动的 WAL 恢复时间；对高写入服务器，fast 也可能因
  检查点过远而启动慢——这与第 3 章检查点配方共享同一个"WAL 前沿"预算。
- **坑**：把 `-m fast` 当 `-m immediate` 用在事务挂死场景会等待；反之用 immediate 处理例行发布重启，
  等于给可用性埋雷。

### 配方：Reloading server configuration——参数生效语境（context）

- 2017 原书口径：SIGHUP 类参数 reload 即生效；postmaster 类需重启；backend/superuser 类可会话级 SET。
- ✅ 该分类体系至今有效，官方资源文档：https://www.postgresql.org/docs/current/runtime-config-resource.html
  （curl 200；`context` 列于 `pg_settings` 视图，PGHP3e 第 6 章曾以官方脚本实测全集——两册同一知识点的
  食谱版与专书版，见 [../PostgreSQL_10_High_Performance_3e/06-配置参数语境与生效方式.md](../PostgreSQL_10_High_Performance_3e/06-配置参数语境与生效方式.md)）。
- **工程做法**：变更单里必须标注每个参数的 context；"reload 成功但没生效"九成是把 postmaster 级参数
  当成了 SIGHUP 级。

### 配方：Tuning logging-related parameters

- 关键族：`logging_collector`（服务端收集）、`log_directory/log_filename/log_rotationage`、
  `log_min_duration_statement`（慢 SQL 阈值）、`log_checkpoints`、`log_lock_waits`、`log_temp_files`、
  `auto_explain` 扩展。
- 作者立场：**日志是性能诊断的第一数据源**——第 4/8/11 章的分析全部回料于这里开的开关。
  `log_checkpoints=on` 是第 3 章检查点判读的前置条件（✅ 章间引用结构可从官方 txt 与 README 目录顺序核对）。
- **性能税**：`log_min_duration_statement=0` 在高压 OLTP 下放大 IO 与 CPU；原书给的折中是分阶段
  开阈值+按 `application_name` 采样。⚠️（具体数值配方为转述）

## 高频坑与实操清单

- 把 postmaster 级参数（shared_buffers/max_connections）当 SIGHUP 级：reload"成功"但纹丝未动——
  变更单必须带 `pg_settings.context` 抄录。
- `log_min_duration_statement=0` 全量记录：高 QPS 下日志本身成为第 4 章 iostat 里的主角。
- `log_filename` 宏配错（不含时间戳）→轮转互相覆盖，事故当天恰好无日志——开日志前先做一次轮转演练。
- `ALTER SYSTEM` 后忘记 reload/restart：postgresql.auto.conf 的生效时机同样看 context。
- systemd `TimeoutStopSec` < fast 关机实际耗时 → SIGKILL 介入，正常关机变崩溃恢复（03 章 WAL 预算遭殃）。
- 容器镜像里 pg_ctl 被 entrypoint 接管：`pg_ctl stop -m fast` 手动演练要在宿主机/调试容器做，勿在 pid 1 视角误判。⚠️
- `auto_explain` 与 `log_temp_files` 是"事后取证"，别等事故再开——开着的税远小于盲着的夜。
- 日志目录与数据目录同卷：日志风暴挤占 WAL 空间，04 章 disk space 配方要覆盖 log 目录。
- reload 失败的静默：conf 语法错误时 reload 拒绝但旧值继续跑，`pg_file_settings` 校验要进变更流程。
- 检查点/慢语句日志字段随版本增删，解析器（pgBadger 版本）要先于日志参数升级。⚠️

## 核心概念速览（中英对照）

- **服务器控制** — pg_ctl：PG 生命周期 CLI（start/stop/restart/reload/promotion）。
- **快速关机** — fast shutdown：回滚事务、断连接后干净关闭的默认模式。
- **立即关机** — immediate shutdown：跳过正常关闭，下次启动走 WAL 恢复。
- **配置重载** — reload (SIGHUP)：不重启使 SIGHUP 语境参数生效。
- **生效语境** — context：`pg_settings` 中标注参数属 internal/postmaster/sighup/backend/user 哪级。
- **日志收集器** — logging_collector：服务端进程接管 stderr 日志并做轮转。
- **慢语句阈值** — log_min_duration_statement：超过毫秒数的语句记日志，0=全记。
- **检查点日志** — log_checkpoints：记录检查点耗时/距离，第 3 章判读的数据源。
- **自动解释** — auto_explain：对超阈值语句自动输出 EXPLAIN 的扩展。
- **覆盖配置** — ALTER SYSTEM：写 postgresql.auto.conf 的实例级参数变更入口。
- **临时文件日志** — log_temp_files：暴露排序/哈希溢盘，与第 11 章内存参数联动。

## 最新演进与工业实践

- **参数面演进**：`log_checkpoints` 默认值后随版本转为 on（PG15 线，⚠️ 转述待核），检查点可见性成为
  开箱默认；`log_lock_waits`/`deadlock_timeout` 组合至今是锁诊断第一通道。
- **进程类型监控**：PG14 起 `pg_stat_activity.backend_type` 更细（checkpointer/autovacuum worker 等），
  与日志族构成 2026 诊断双通道。✅ https://www.postgresql.org/docs/18/monitoring-stats.html（curl 200）。
- **systemd 托管**：主流发行版 unit 文件 + `pg_ctl promote`/`pg_rewind` 流程化；`TimeoutStopSec` 小于
  fast 关机耗时会触发 SIGKILL——当日"smart/fast/immediate"三档问题升级为"unit 与 OS 信号双层级"。⚠️
- **配置即代码**：K8s CloudNativePG/Stolon 等把 postgresql.conf 模板化+滚动 reload，context 分级决定了
  哪些变更能热滚动、哪些要走重启窗口——本章知识以新形态存活。⚠️
- **日志分析栈**：pgBadger 仍是日志侧报表事实标准；新趋势是把慢 SQL 直接进 `pg_stat_statements` +
  Grafana（与 [../Mastering_PostgreSQL_Administration/07-监控_pgAdmin与Grafana.md](../Mastering_PostgreSQL_Administration/07-监控_pgAdmin与Grafana.md) 同路线）。⚠️
