## 7.1 本章定位

"性能预算的最后一道"：备份恢复与持续归档的四套工具横评——**Barman、OmniPITR、repmgr、walctl**。
2017 年它们各有拥趸；十年后的存活名单（Barman/repmgr/pgBackRest，OmniPITR/walctl 退役）让本章
成为工具选型史的又一对账样本。txt 首行 `yum install barman` + ssh 免密准备（✅ 实抓）即当日典型开场。

## 7.3 代表配方精读

### 配方：Barman——"备份服务器"范式

- **架构**：独立主机上跑 barman，经 SSH（rsync/pipe）拉 base backup 与 WAL，元数据目录管理
  保留策略（`retention_policy`）、`backup`/`recover`/`list-files` 命令族（✅ txt 骨架）。
- **PITR 语义**：base backup + 连续归档 WAL → `recovery_target_time` 任意点恢复——与第 3 章检查点
  截断逻辑互为镜像（不归档就无 PITR，`archive_mode` 是前提）。⚠️ 转述。
- **坑**：复制槽保 WAL（`slot_name` 选项）与 `max_wal_size` 的角力：归档滞后会让 pg_wal 涨爆磁盘，
  呼应 04 章 disk space 配方。

### 配方：OmniPITR / walctl——已退役两兄弟（史料价值）

- OmniPITR：`omniarch` 推 WAL 到远端+`omnirestore` 拉回，配 crontab 管保留——纯脚本哲学，无中心目录。
- walctl（Percona）：JSON 配置+多线程上传 S3，当年卖点=云对象存储原生。
- 两者约 2019-2021 间停止实质维护（⚠️ 仓库现状观察）；其思想（对象存储+并行上传+保留策略）
  被 pgBackRest 完整继承并成为新事实标准之一。

### 配方：repmgr——备份与 HA 的交叠地带

- repmgr 本质是**复制管理**（注册/提升/切换），备份靠其 `standby clone` 派生副本——本章把它列进
  备份工具，反映当年"用备库当热备份"的普遍做法。
- **对偶提醒**：备库不是备份（误删照样复制过去）；独立归档+还原演练不可省——当日社区就在反复强调，
  2026 仍是铁律。⚠️

## 7.4 机制小深潜：备份的三原语

任何工具都=①一致基线（`pg_start_backup`/块级复制/`pg_basebackup`）+②WAL 流归档+③恢复目标指定。
读懂三原语，四套工具的配置语法的差异只是工程包装——这也是 [../Mastering_PostgreSQL_Administration/05-备份与恢复.md](../Mastering_PostgreSQL_Administration/05-备份与恢复.md)
（现代单工具深讲）与本册（多工具横评）互补的读法。

## 高频坑与实操清单

- "有备库"≠"有备份"：误删/逻辑损坏会忠实复制，恢复深度取决于归档+快照，本章四工具都只管搬运。
- archive_command 失败默认只是重试+攒 pg_wal：必须对"最老未归档段年龄"单独告警（与 03 章合并口径）。
- PITR 恢复目标点选在"扩展/配置变更"附近会二次翻车：恢复后先跑一致性检查再放流量。⚠️
- `--link`/硬链式基线备份与文件系统行为强相关：跨卷/快照文件系统下静默退化为拷贝或失败，演练定生死。
- Barman `keep`/retention 配错：唯一的全量被滚动删除是教科书事故——保留策略评审要双人签核。⚠️
- 恢复演练要"裸环境"演练：在自己顺手的那台机上还原=没演练（RRE 谱系制度化主张 ⚠️）。
- 备份链加密与密钥分离：桶权限事故=全库泄露；KMS/Vault 化是 2017 配方缺失的一课。⚠️
- WAL 归档卷与数据卷同盘共存亡：爆炸半径隔离（03 章同款结论在备份侧复述）。
- repmgr `standby clone` 期间对主库是全量读冲击：窗口与限速选项（rate limit）先行设定。⚠️

## 核心概念速览（中英对照）

- **基础备份** — Base backup：某一致性时刻的全量数据拷贝。
- **连续归档** — Continuous archiving：把 WAL 段持续外送，PITR 的前提。
- **时间点恢复** — PITR：恢复到 `recovery_target_time/xid/name` 的任意时刻。
- **备份保留策略** — Retention policy：按窗口/代数决定可恢复深度。
- **备份目录** — Barman catalog：barman 的中心元数据库（`barman list-backup`）。
- **复制槽归档** — slot_name 选项：让归档进度决定 WAL 保留，防 pg_wal 爆炸。
- **备库克隆** — standby clone（repmgr/walctl）：从现有实例直接派生副本。
- **归档命令** — archive_command/archive_mode：WAL 外送通道开关。
- **还原演练** — Recovery drill：定期真实恢复验证备份有效性，可靠性铁律。
- **对象存储归档** — S3-style archiving：walctl/pgBackRest 把备份推云桶的路线。

## 最新演进与工业实践

- **工具存活榜（2026）**：pgBackRest（Citus 系，并行/增量/加密/S3 原生）与 Barman（EnterpriseDB 系，
  持续发版）双雄；repmgr 转攻 HA（1.x→5.x 线）；**OmniPITR、walctl 已停更退役**——本章四选二的
  当代答案。⚠️（结论性现状，仓库存在性 ✅ 实查：github.com/pgbackrest/pgbackrest、
  github.com/2ndquadrant-it/barman→EnterpriseDB/barman 迁移线）
- **PG17 服务端增量备份**：`pg_basebackup`/系统级 API 支持增量（清单式块差量），"全量+归档"模型
  开始松动。✅ 入口 https://www.postgresql.org/docs/release/17.0/（curl 200；机制细节 ⚠️ 转述）。
- **逻辑备份面**：pg_dump 并行（-j）自 PG16 支持目录格式全库并行（⚠️），与第 10 章升级路径衔接。
- **云与不可变备份**：快照+对象存储+Vault 化密钥、"备份即代码"（Terraform 管理 barman 节点）成
  工业常态；勒索场景推动 immutable bucket/S3 Object Lock 进入 PG 备份设计。⚠️
- **RPO 连续体**：同步复制/归档异步间"备份不是恢复方案"的边界教育（7.3 坑位）已由
  [../Database_Reliability_Engineering](../Database_Reliability_Engineering/00-总览与阅读地图.md) 谱系承接为制度化演练。⚠️
