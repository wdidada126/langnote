# Ch1 Performance Problems（性能问题）— 原书 p.3–18 · Part I Foundations

> ⚠️ 文档转述（基于官方目录 PDF 的二级标题逐节精读重构，非原书文本）。Oracle 不可本机实测。

## 本章定位

- 全书第一篇不讲"怎么调"，讲"什么时候、以什么姿势进入性能这件事"。
- 作者立场：性能是贯穿软件生命周期的属性，不是上线后的补救。
- 进入排障阶段前先回答两个问题：问题是否真实存在？以谁的口径定义存在？
- 本章为 Part II（识别方法论）铺设组织与流程前提；Ch2 铺设概念前提。

## 1.1 Do You Need to Plan Performance?（需要为性能做规划吗，p.3）

- 答案：需要。规划点散布在生命周期四阶段，每阶段各有性能交付物。
- **Requirements Analysis（需求分析，p.4）**
  - 把业务语言翻译为可度量指标：响应时间目标、吞吐、并发档位、时段特征。
  - 性能需求常被遗漏，因为业务方默认"快"是天性；作者建议逐项签字确认阈值。
- **Analysis and Design（分析与设计，p.5）**
  - 逻辑/物理设计期消除结构性慢模式：过度规范化却按宽表访问、泛型 EAV 表。
  - 设计债的利息在运行时以等待事件的形式偿还（为 1.2 清单埋线）。
- **Coding and Unit Testing（编码与单元测试，p.6）**
  - 开发期就用真实量级数据测基本操作。
  - 绑定变量、数组接口等习惯在此阶段定型，决定后期命运。
- **Integration and Acceptance Testing（集成与验收测试，p.7）**
  - 负载/容量测试结果必须回扣需求分析阶段的数字，形成闭环。
  - 验收阈值不是"演示能跑"，而是与业务时段模型对齐。

## 1.2 Designing for Performance（为性能而设计，p.8）——十类反模式

官方目录即完整清单（✅），每条都是"设计债→运行时症状"的因果对：

1. Lack of Logical Database Design（缺逻辑设计，p.8）
2. Implementing Generic Tables（泛型表/EAV 滥用，p.8）——灵活换取查询结构性低效
3. Not Using Constraints to Enforce Data Integrity（不用约束，p.9）——约束同时是给优化器的信息（Ch6 join 消除、Ch13 谓词可达性）
4. Lack of Physical Database Design（缺物理设计，p.9）——直接引出 Ch16
5. Not Choosing the Right Data Type（类型选错，p.9）——引出 Ch16.2
6. Not Using Bind Variables Correctly（绑定变量误用，p.10）——引出 Ch2/Ch12 硬解析风暴
7. Not Using Advanced Database Features（弃用高级特性，p.10）——MV/并行/压缩（Ch15/Ch16）
8. Not Using PL/SQL for Data-Centric Processing（数据中心处理不用 PL/SQL，p.11）——上下文切换税
9. Performing Unnecessary Commits（不必要提交，p.11）——log file sync 与块 cleanout 行为
10. Steadily Opening and Closing Database Connections（频繁开关连接，p.11）——会话建立成本与连接池

- 使用方式：评审 checklist。每条反模式都对应后文某一章的"症状"，形成全书索引。

## 1.3 Do You Have Performance Problems?（你真有性能问题吗，p.11）

- **System Monitoring（系统监控，p.12）**
  - 资源视角（CPU/IO/内存利用率）；利用率低 ≠ 没问题，利用率高 ≠ 有问题。
- **Response-Time Monitoring（响应时间监控，p.12）**
  - 用户视角；**本书判据：只有响应时间能定义性能问题**。
  - 这条为 Ch3–Ch5 一切"以响应时间为轴"的剖析法奠基（Cary Millsap 作序并非巧合）。
- **Compulsive Tuning Disorder（强迫性调优失调，p.12）**
  - 术语借自 Millsap：不断微调参数/内存池，从不回到"用户响应时间是否改善"。
  - 组织病而非技术病；解药是 1.4 的台账与判据。

## 1.4 How Do You Approach Performance Problems?（如何切入，p.13）

- **Business Perspective vs. System Perspective（p.13）**
  - 先按业务影响排序（哪个事务、哪个时段、影响多少人），再落到系统。
  - 两个视角的响应时间口径可能不同（端到端含网络与应用层）。
- **Cataloging the Problems（问题台账，p.14）**
  - 登记：症状、复现性、影响、负责人、状态。
  - **可复现性是台账核心字段**——直接决定走 Ch3 还是 Ch4/Ch5（全书三分法入口）。
- **Working the Problems（处理问题，p.14）**
  - 一次一个，商业优先级驱动；产出必须是"已证实根因 + 可回归的改善"。

## 核心概念速览（中英对照）

- **性能规划** — Performance Planning：把性能需求嵌入生命周期四阶段而非事后补救
- **性能需求** — Performance Requirements：业务语言转可度量阈值（RT/吞吐/并发）
- **泛型表** — Generic Tables：EAV 式通用表，逻辑灵活换查询结构性低效
- **约束即信息** — Constraints as Optimizer Input：约束缺失既坏数据也坏计划
- **绑定变量** — Bind Variables：以文本一致换游标共享
- **不必要提交** — Unnecessary Commits：放大 log file sync 并破坏原子性
- **系统监控** — System Monitoring：资源利用率视角，不能单独定义性能问题
- **响应时间监控** — Response-Time Monitoring：用户视角，判定性能问题的唯一准绳
- **强迫性调优失调** — Compulsive Tuning Disorder (CTD)：无根因的连环参数微调
- **商业视角** — Business Perspective：按业务影响定优先级
- **系统视角** — System Perspective：按技术症状定位层级
- **问题台账** — Cataloging the Problems：以复现性与影响登记排障队列
- **可复现性** — Reproducibility：决定排障路径的核心字段

## 最新演进与工业实践

- **SRE 化同构**：Google SRE 的 error budget 与四大黄金信号（延迟/流量/错误/饱和）与本章"响应时间定义问题、资源视角仅参考"完全同构；2020 年代 Millsap 的 Method-R 培训体系（method-r.com，⚠️ 转述）仍是本章的组织学版本。
- **平台化左移**：Oracle 云（Autonomous DB）用自动索引/ADI 把 1.2 清单里"物理设计缺失"类债自动化偿还；但逻辑设计/EAV 类债仍归人 ⚠️ 转述。
- **AIOps 台账**：商用可观测平台（Datadog Watchdog、Oracle Cloud APM Health Dashboard）把问题台账自动化为异常事件流，"复现性决定路径"的洞察仍需人工执行 ⚠️ 转述。
- 论文线：性能故障归因的学术综述可沿 ../../db/db.md 检索（如 "Towards a Simple and Principled Method for Database Performance Diagnosis"，SIGMOD 2015，⚠️ 仅标题+会议+年份，DOI 未校验）。
