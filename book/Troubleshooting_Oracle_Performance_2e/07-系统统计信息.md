# Ch7 System Statistics（系统统计信息）— 原书 p.191–206 · Part III Query Optimizer

> ⚠️ 文档转述。系统统计（I/O 时序模型）为 Oracle 专有，不实测。#23 已落盘（互链见文末与 00）。

## 本章定位

- 成本以**秒**为单位（10g 起）的前提，是优化器手里有"本机各种操作各要多久"的标定表——系统统计。
- 短而关键：不采集它，CPU 成本记 0、单块/多块读同价，计划自然错得离奇。
- 2e 把它从 1e 的统计合章中拆出独立成章（作者 Introduction 自述"splitting the chapter about system and object statistics in two" ✅），分量可见。

## 7.1 The dbms_stats Package（p.191）

- 入口统一：`DBMS_STATS` 同时管理系统统计与对象统计——SET/GET/EXPORT/IMPORT、备份恢复、日志共用一套设施。
- 本章涉及过程：`GATHER_SYSTEM_STATISTICS`、`DELETE_SYSTEM_STATISTICS`、`RESTORE_SYSTEM_STATISTICS`、`EXPORT/IMPORT_SYSTEM_STATISTICS`。
- 存储位：`SYS.OPTSTAT_HIST_CONTROL$`（⚠️ 转述）。

## 7.2 What System Statistics Are Available?（p.192）

- 两代模型并存：
  - **单块/多块读时序**：`SREADTIM`（= ioseektim + iotfrspeed 折算）、`MREADTIM(n)`（随块数 n 的折线公式）——传统"以 I/O 为中心"模型；标定值源自 iostat 类工具。
  - **CPU + 工作负载模型（11g 起）**：负载拆为 nio/nseq/nrnd（块操作计数）与 ncyc（每执行 CPU 周期），配 `CPUSPEED(NW)`、`PMREADSRATIO` 等系数合成时间——**成本 = I/O 时间 + CPU 时间**的完整表达；`PDMARKER$` 记录负载样本。

## 7.3 Gathering System Statistics（p.194）

- **Noworkload Statistics（p.194）**
  - `GATHER_SYSTEM_STATISTICS` 默认路：合成 I/O 标定（对临时段读写测速）得 sreadtim/mreadtim/cpuspeednw。
  - 优点：快、无业务依赖；缺点：与真实负载的块大小/缓存命中脱节。
- **Workload Statistics（p.195）**
  - 在代表性负载上采样（`statistics_level=ALL` 口径 + 跑一段业务 + `GATHER_SYSTEM_STATISTICS('WORKLOAD')`）。
  - 优点：贴近现实；代价：要维护窗口或常开采样。
- **Choosing（p.198）**
  - 作者判据：缓存充足、负载多样时 workload 明显更优；拿不准时 **noworkload 也比没有强**；升级站点注意 10g 时代遗留 noworkload 值在 11g CPU 模型下失真，应重采。

## 7.4–7.6 管理三面（p.199–200）

- **Restoring（p.199）**：`RESTORE_SYSTEM_STATISTICS` 带时间戳回滚——统计是可回退的变更。
- **Working with a Backup Table（p.200）**：备份表（srestab 语义）——升级/迁移前手动快照统计的标准件。
- **Logging of Management Operations（p.200）**：优化器操作日志记录一切统计动作——排查"计划昨天还好好的"必查。

## 7.7 Impact on the Query Optimizer（p.202）

- 无系统统计：默认口径下 I/O 主导一切，FULL vs INDEX 平衡点被系统性地推向错误一侧。
- 有 workload 统计：多块读相对成本上升、CPU 成本登场——**同一语句的计划可能整体翻转**（书内以同组表演示）。
- 与 Ch9 接口：`_optimizer_sysstats_mode` 等控制 CPU costing 参与度（⚠️ 隐参数转述）。

## 关键动作速查（⚠️ 转述）

- 采：`EXEC DBMS_STATS.GATHER_SYSTEM_STATISTICS`（noworkload）/ `...'WORKLOAD'`（需先跑代表性负载）

## 易混点与补记

- 系统统计只有一份全局标定（OPTSTAT_HIST_CONTROL$），不是每表每索引——别拿它当对象统计用（⚠️ 转述）。
- CPUSPEED 与 CPUSPEEDNW 分属 workload 与 noworkload 两代标定，aux_stats$ 里同时出现时要认清哪条在生效。
- sreadtim 是"单块读时间"不是"随机读时间"：概念相近但口径由标定方法决定，混用会推错成本。
- noworkload 的合成标定走临时段：临时 I/O 子系统异常慢时，标定值会系统性偏大，全库计划一起变形。
- workload 采集要求代表性负载"正在跑"：只采到半夜批处理，白天 OLTP 的计划自然不对味。
- 11g 引入 CPU costing 默认开启，升级站点若沿袭 10g 习惯不采系统统计，等于用 10g 的假设跑 11g 的模型。
- 删系统统计（DELETE_SYSTEM_STATISTICS）会退回内置默认值——"删了总比错着强"在这里不成立。
- 备份/恢复统计是跨环境搬运的正规通道（EXPORT/IMPORT），直接 exp 字典表是危险捷径。
- 系统统计变更通常不立即让游标失效：老计划可能继续服役，观察窗口要足够长。
- 它回答"这台机器各操作多快"，对象统计回答"这些数据长什么样"——两章配套，缺一不可。
- 隐参数只能关参与度、不能替代采集：`_optimizer_sysstats_mode` 是旋钮不是地基。

## 核心概念速览（中英对照）

- **系统统计** — System Statistics：主机 I/O/CPU 时序标定集
- **无负载统计** — Noworkload Statistics：合成标定，免业务窗口
- **工作负载统计** — Workload Statistics：真实负载采样含 CPU 周期
- **SREADTIM / MREADTIM** — 单块/多块读时间（毫秒）
- **CPUSPEED / CPUSPEEDNW** — CPU 速度（MHz）
- **PDMARKER$** — 负载采样的设备标记表
- **GATHER_SYSTEM_STATISTICS** — DBMS_STATS 系统统计入口
- **统计回滚** — Restore System Statistics：时间机器
- **统计备份表** — Backup (Restore) Table：迁移前快照
- **操作日志** — Optimizer Operation Log：统计变更审计
- **CPU Costing** — _optimizer_sysstats_mode：成本含 CPU 的开关族

## 最新演进与工业实践

- **19c/23ai 现状**：自动维护任务只管对象统计，**系统统计仍须人工首采**；Oracle 自家托管环境（Exadata Service、ADW）交付时预置 workload 统计——印证本章"noworkload 及格线、workload 标准线" ⚠️ 转述。
- **文档对位**：官方统计章节持续可达：docs.oracle.com/en/database/oracle/oracle-database/26/tgdba/gathering-database-statistics.html（curl -sIL 校验 200，2026-09）。
- **方法论外溢**：基准定标思想同构于 PostgreSQL `pgbench` 实测 random/seq 比再设 `random_page_cost` 的最佳实践、SQL Server 缺少系统统计而被社区反复诟病的成本模型——"给成本模型喂真实时序"仍是行业欠账 ⚠️ 转述。
