# Ch5 Postmortem Analysis of Irreproducible Problems（不可复现问题的事后分析）— 原书 p.151–166 · Part II Identification

> ⚠️ 文档转述。AWR/Statspack 为 Oracle 专有机制，不实测。

## 本章定位

- 三分法第三类：**问题已过去、现场已消失**——凌晨批慢过一次、昨天 14:02 卡了 40 秒。
- 唯一可依赖的是**仓储（repository）**：按时间轴持续采样的历史仓库。
- 分析框架与 Ch4 完全同构（4.1 路线图原样复用），只是数据源从"实时视图"换成"历史视图"。
- 本章是 1e→2e 增量最大的块之一（作者 Introduction 自述 2e 补 AWR/Statspack/HPROF/ASH 内容 ✅）。

## 5.1 Repositories（仓储，p.151）

- 实时视图 = 环形缓冲 + 会遗忘；仓储 = 带保留策略的时间序列。
- 设计四要素：采样频率、粒度（系统/会话/语句）、保留期、查询许可。
- Oracle 站内两个候选：**AWR**（内核自动、受 Diagnostics Pack 约束）与 **Statspack**（手工部署、免费）。

## 5.2 Automatic Workload Repository（AWR，p.152）

- **Performing Configuration（p.152）**
  - 快照间隔（默认 60 分钟）、保留期（默认 8 天）；`DBA_HIST_WR_CONTROL` 与 `DBMS_WORKLOAD_REPOSITORY.MODIFY_SNAPSHOT_SETTINGS`。
  - 采集开关到 SQL/OS/段统计粒度；12c 多租户下 AWR 归 CDB 级（12.1 口径提示）。
  - 作者提醒：**加深采集=加系统开销**，给保守默认。
- **Taking Snapshots（p.154）**
  - `CREATE_SNAPSHOT` 手工打点。
  - 排障铁律：**问题复现窗口两端各打一快照**，把事后分析变成"区间 A/B"。
- **Managing Baselines（p.154）**
  - 固定基线（capture baseline：把"好时期"整段封存防清理）；
  - 移动基线（moving window：默认 7 天均值±2σ 的异常检测带）；
  - `LOAD_BASELINE`/`ADD_TIME_INTERVAL`：任意区间转正。
  - 概念定位：**基线是"正常"的机器定义**——回答"今天到底异不异常"。
- 报告出口：`awrrpt.sql/awrgrpt.sql`（RAC 全局）与 EM 页双轨。

## 5.3 Statspack（p.156）

- **Performing Installation（p.157）**：`spcreate.sql` 建 PERFSTAT schema；授权与表空间。
- **Configuring the Repository（p.157)**：收集级别 0/6/7/8（越高越贵：快照/SQL/段级闩）；STATS$ 表族与 AWR 的映射关系。
- **Taking and Purging Snapshots（p.158）**：`snap snapshot|fast|flush`；`purgestat.sql`/`sp purge` 保留策略。
- **Managing Baselines（p.160）**：无原生基线，用命名快照区间+差分模拟 AWR 基线工作流。
- 定位声明：**Statspack 是无 Diagnostics Pack 授权时的 AWR 平替**，粒度较粗（无 ASH 细节、SQL 按级别采集）。

## 5.4 / 5.5 报告解读：有包与无包（p.160 / p.161）

- 有包：EM AWR 页与文本报告分段——Load Profile、Top 等待、SQL 区、缓存、段统计，每段回扣 4.1 层级。
- 无包：`spreport.sql` 同构解读；作者以 TVD$XTAT 思路把多区间 SQL 统计入库对比。
- 本章警句（转述大意 ⚠️）：**"AWR 报告是系统级平均的合集——平均值越漂亮，越要怀疑双峰"**；事后分析的正确产物是"一个值得用 Ch4 实时法或 Ch3 trace 法进攻的时间窗"。

## 易混点与补记

- AWR 默认 1 小时快照：闪断型问题可能整段被平均掉——先确认采样窗口是否覆盖病灶（⚠️ 转述）。
- Statspack 与 AWR 不是一回事的两种写法：Statspack 依赖手工作业与版本口径，AWR 是内置且属 Diagnostic Pack 许可（2014 书内地图）。
- AWR baseline 与 guaranteed restore point：前者保统计口径，后者保数据可回退，用途别混。
- SQL Tuning Set 是"SQL+执行统计"的容器，不是执行计划缓存的副本——演进后与 plan 的关系要分开看。
- `DBA_HIST_*` 视图是事后取证主矿：ASH 历史、segment 统计、sysmetric_history 各有归属，查前先想问的是哪层。
- 事后分析的弱点是"证据已过期"：指标保留策略（retention）应在事故前就设计好。
- AWR 报告读法：先 load profile 定规模，再 top 段定对象，最后 SQL 段定语句——顺序反了就会迷路。
- Statspack `snap`/`stats.sql` 的差别在快照与报告两步，误把 snap 当报告会拿到空文件。
- 本章与 Ch4 的分工：实时是"正在发生的 ASH"，事后是"已经沉淀的 AWR/Statspack"，同一方法论两副面孔。

## 核心概念速览（中英对照）

- **仓储** — Repository：带保留策略的时间序列历史库
- **AWR** — Automatic Workload Repository：内核级自动快照仓库
- **快照** — Snapshot：两次采样的时间点记录
- **快照间隔/保留期** — Snap Interval / Retention：粒度与遗忘周期
- **固定基线** — Baseline：被显式保护的好时期区间
- **移动基线** — Moving Window Baseline：7 天滚动均值±2σ
- **DBA_HIST_\*** — AWR 历史视图族
- **Statspack** — PERFSTAT schema 手工仓库（免费）
- **收集级别** — Collection Level (0/6/7/8)：深度-开销旋钮
- **awrrpt.sql** — AWR 报告脚本
- **区间 A/B** — Snapshot Pair Comparison：两快照差分
- **事后分析** — Postmortem Analysis：问题缺席时的历史取证
