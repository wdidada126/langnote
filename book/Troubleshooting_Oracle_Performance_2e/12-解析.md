# Ch12 Parsing（解析）— 原书 p.419–447 · Part IV Optimization

> ⚠️ 文档转述。解析诊断与 API 建议以书内骨架重构，不实测。

## 本章定位

- "解析"是响应时间里最常被忽视的暗物质——用户说"查询慢"，实际可能根本没执行。
- 两类病理：**快解析太多**（版本爆炸/latch 争用）与**慢解析太长**（优化阶段 CPU 失控）。
- 本章四段式：识别→解决→绕行→API 预防，是全书"症状到根因"范式在解析域的全量应用；Ch2 的游标生命周期在这里收割。

## 12.1 Identifying Parsing Problems（识别，p.419）

- **Quick Parses（p.420）**
  - 单次解析很快但次数天文级：症状是 `library cache: mutex X`、`cursor: mutex X/S` 等待、共享池闩风暴、`V$SYSSTAT` 的 parse count (hard/total) 暴涨。
  - 诊断路：ASH 按 top_level_sql_id+事件切片；`V$SQL_SHARED_CURSOR` 数同一 parent 的 child 数（版本数逼近上限即高危，⚠️ 转述）。
  - 根因画像：**字面量 SQL（无绑定）+ 环境漂移**（NLS/统计版本/优化器参数不一致）。
- **Long Parses（p.425）**
  - 单次解析秒级：时间模型 `parse time elapsed/hard parse elapsed time` 定位；10053 trace 是解剖刀（优化器决策日志）。
  - 根因画像：**搜索空间爆炸**（连接表数超 `_optimizer_max_permutations`）、统计缺失引发的深度动态采样、自适应组件叠加。

## 12.2 Solving Parsing Problems（解决，p.427）

- **Quick Parses 的解（427）**：绑定变量（唯一治本）；消除 child 版本增殖（统一会话环境、修 V$SQL_SHARED_CURSOR 指出的具体不共享位）；共享池 sizing 与 `session_cached_cursors`（软解析也吃的"免闩路径"）；应用层语句缓存（12.3 续）。
- **Long Parses 的解（433）**：补统计让动态采样降级；SQL Profile/SPM 固化计划以短化演化；拆分语句压缩连接数；优化器策略类隐参数削减搜索（须 SR 背书）。

## 12.3 Working Around Parsing Problems（绕行，p.433）

- **Cursor Sharing（p.434）**：`cursor_sharing=FORCE/SIMILAR` 把字面量归一为系统绑定——**急救阀**。
  - SIMILAR 在倾斜列上生成多子游标（≈没救）；FORCE 一把梭的风险在计划错配。
  - 作者立场：用它争取修复时间，不用于常态。
- **Server-Side Statement Caching（p.436）**：`session_cached_cursors` 的 LRU——命中时跳过库缓存闩直达游标，把软解析再降级；sizing 依据 V$SYSSTAT 的 session cursor cache hits 比例（⚠️ 转述）。

## 易混点与补记

- 硬解析、软解析、软软解析（session cached cursor）是三级成本，不是两级（⚠️ 转述）。
- `V$SYSSTAT` 的 parse count (hard) 与 SQL area 数量对不上是常态：游标会被老化，历史计数不会说谎但会混入噪声。
- 版本计数爆炸（version count）的元凶常在对象失效与统计变更连锁：DDL 风暴后的凌晨计划漂移多源于此。
- `CURSOR_SHARING_FORCE` 能救共享池但可能毁计划：先用直方图与窥视评估谓词敏感性。
- 绑定与否的判据是"执行计划是否随值变化"：不是所有 SQL 都该绑（书内明言）。
- 共享池闩（library cache latch/pin）等待是解析问题的最终症状，不是病因。
- `SESSION_CACHED_CURSORS` 过小会让高频小 SQL 反复走软解析，调它先测游标命中率。
- 12c 的 adaptive sharing 会依据绑定值特征自动拆子游标，与手工 bind 敏感/ACS 机制叠用时看 V$SQLCS_FEEDBACK。
- IN 列表长度不定是版本爆炸的经典来源：拆成临时表 join 或固定桶宽是两味解药。
- 统计变更后的 no_invalidate 窗口决定老游标存活时长——解析风暴常在改统计后半小时内出现。
- PL/SQL 里的 SQL 同样吃解析账：包体重编译会级联失效游标。
- 快速定位解析热点：按 `V$SQL` 的 PARSE_CALLS/EXECUTIONS 比值排序，远胜盲猜。
- 硬解析的 CPU 时间在小 SQL 上能盖过执行本身——"语句很快但库很卡"的经典答案。
- DDL 与统计操作是解析稳定性的两大外敌，变更窗口要配套游标保活预案。
- 序列/时间戳类函数在语句级只求值一次的语义，被很多"意外一致"的更新依赖，改写前先确认。
- 客户端预编译（statement cache）与应用层 ORM 缓存是同一问题的两层，别双开双花。
- 本章与 Ch13 的接口：解析省的是 CPU，数据访问省的是 IO，账要分开算再合并看。

## 核心概念速览（中英对照）

- **硬解析/软解析** — Hard/Soft Parse：有无完整优化阶段之分
- **版本爆炸** — Cursor Version Explosion：child cursor 失控
- **V$SQL_SHARED_CURSOR** — 子游标不共享原因位图
- **library cache: mutex X** — 共享池并发争用标志等待
- **cursor: mutex S/X** — 游标级闩等待
- **10053 trace** — 优化器决策日志（慢解析解剖刀）
- **parse time cpu/elapsed** — 时间模型解析项
- **动态采样** — Dynamic Sampling：统计缺位运行时补数（解析贵之源）
- **_optimizer_max_permutations** — 连接序搜索上限
- **cursor_sharing** — EXACT/FORCE/SIMILAR 急救语义
- **session_cached_cursors** — 会话游标缓存（软解析免闩通道）
- **隐式语句缓存** — Implicit Statement Cache（JDBC/ODP.NET）

## 最新演进与工业实践

- **19c/23ai 对位**：解析等待事件族继续细化，`cursor: mutex X` 仍是常客；共享池自管理与解析路径优化使闩风暴频率下降，但字面量灾难依旧 ⚠️ 转述。
- **PL/SQL 侧减负**：11g 起 SYS_MANAGED 对象在 PL/SQL 调用序列里维持会话游标缓存命中（`session_cached_cursors` 在 PL/SQL 环境近乎免费），19c 的 PL/SQL function result cache 与本章解析成本互补 ⚠️ 转述。
- **ORM 时代新变种**："IN 列表枚举爆炸"制造海量 parent cursor；标准解（临时表 join、`SYS.ODCIVARCHAR2LIST` 集合绑定、12c 的 IN 表达式上限参数）都是 12.4 思路的延伸 ⚠️ 转述。
- **跨引擎同题**：PostgreSQL 的 prepared statement 计划缓存反复调优（12/13/17 的 generic/custom 策略、`plan_cache_mode` 三值）——与"绑定后如何保计划质量"完全同构 ⚠️ 转述。
