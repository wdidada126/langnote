# 第 1 章　分布式微服务架构设计原理

> 原书第 1 章是**定调章**：用约 50 页把「单体 → 服务化（SOA）→ 微服务」的演进讲清楚，
> 并给出微服务的核心要点（团队划分、去中心化治理、交互模式、分解组合、容错、粒度）与
> Java 平台下的项目组织形式、技术选型。内容偏入门、偏 Java 生态，但骨架是对的。
> 它也是**最需要 2026 年补丁**的一章：2017 年书里几乎只有「微服务 + Docker」的雏形，
> 而 **Service Mesh / 云原生** 已彻底改写了「去中心化治理」和「服务间通信」的实现方式。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 1.1–1.2 演进主线：单体 → 服务化 → 微服务

- **单体（JEE/SSH）**：一个 WAR 包打天下。优点：开发部署简单、事务本地、调试直接；
  缺点：随着代码膨胀，**编译慢、启动慢、牵一发动全身、无法按模块独立扩容**。
- **服务化（SOA）**：按业务域拆成服务，通过 ESB/中心化总线通信，强调「企业级治理」
  （统一注册、统一协议、统一安全）。缺点：ESB 成了**中心化瓶颈与单点**。
- **微服务**：在 SOA 思想上「去中心化」——去掉 ESB，服务自己选通信协议、自己治理，
  粒度更细、独立数据、独立部署、自动化运维。本书明确：**微服务是 SOA 的延续与升华**，
  后续不再刻意区分 SOA 与微服务。

### 1.3.3 微服务的交互模式（本章重点表之一）

| 模式 | 做法 | 适用 |
| --- | --- | --- |
| 同步请求/响应 | 调用方阻塞等结果（REST/gRPC） | 强实时、需即时返回 |
| 异步消息 | 发到消息队列，不阻塞（Kafka/Pulsar） | 解耦、削峰、最终一致 |
| 同步 + 异步回调 | 先同步拿到受理号，完成后再回调 | 长耗时任务 |

### 1.3.4 微服务的分解和组合模式（本章重点表之二）

| 模式 | 说明 | 例子 |
| --- | --- | --- |
| 代理模式 | 服务做简单编排/路由 | API 网关前置 |
| 聚合模式 | 一个服务聚合多个下游结果 | 商品详情页聚合库存/价格/评价 |
| 链式模式 | A→B→C 串行调用 | 下单链路 |
| 分支模式 | 并行调用多个下游再汇总 | 并行查多个风控规则 |
| 数据共享模式 | 多个服务共享同一数据源（谨慎） | 遗留系统过渡 |
| 异步消息模式 | 事件驱动，服务间通过事件解耦 | 订单创建后发「订单已下」事件 |

### 1.3.5 微服务的容错模式（高频面试/实战点）

```text
# 教学示意，不参与构建：六种常用容错手段
舱壁隔离(bulkhead):   把线程池/连接池按依赖隔离，A 依赖挂了不会拖垮 B 的线程
熔断(circuit breaker): 失败率超阈值则直接拒流一段时间，给下游喘息（Closed→Open→Half-Open）
限流(rate limit):     令牌桶/漏桶， protect 自身不被打垮（Sentinel 23461? 实测 23146）
降级(fallback):       非核心功能返回默认值/走缓存，保核心链路
超时(timeout):        任何远程调用必须带超时，否则线程堆积（见第 2 章超时模式）
重试(retry):          幂等前提下有限次重试，配退避；非幂等接口严禁重试
```

> 这六种容错手段今天几乎被 Sentinel（alibaba/Sentinel 23146★）、Istio（istio/istio
> 38408★）等框架产品化。读这节时应同时对照 [05-基于调用链的服务治理系统的设计与实现.md](05-基于调用链的服务治理系统的设计与实现.md)
> ——熔断/限流决策正是靠调用链数据驱动的。

### 1.3.6 微服务粒度

- 太粗：又回到单体；太细：**分布式单体**——网络调用爆炸、事务难做、运维成本飙升。
- 经验尺度：一个微服务能由「**两个披萨团队**」（6–10 人）独立负责，且对应一个清晰的
  业务域/限界上下文（DDD 概念）。

### 1.4 Java 平台项目组织形式

- **一个服务一个代码库、独立版本号、独立 CI/CD**；共享逻辑抽成独立二方库发布到 Maven
  私服，而非在源码里软链接——避免「改一处全公司重编译」。
- 层级：接口层（API 二方包）→ 服务实现层 → 基础设施层。

### 1.5 技术选型（RPC / 服务化 / 微服务）

- **RPC 框架**：关心序列化、传输协议、服务发现。代表：gRPC（grpc/grpc 45341★）、
  Dubbo（apache/dubbo 41579★）、SOFA-RPC（sofastack/sofa-rpc 3921★）。
- **服务化/微服务框架**：在 RPC 之上补齐注册中心、配置、限流、链路。代表：
  Spring Cloud Alibaba（alibaba/spring-cloud-alibaba 29179★，含 Nacos/Sentinel）、
  Dubbo 全家桶。
- **注册配置中心**：Nacos（alibaba/nacos 33419★）、北极星 polaris（polarismesh/polaris 2564★）。

## 版本演进

- **本书无第二版**（未见公开第二版书目）；本节写 2017 年口径 → 2026 年视角的变化。
- **🔧 去中心化治理被 Service Mesh 重写**：2017 年书里的「去中心化」主要靠
  各语言 SDK（如 Dubbo client、Spring Cloud 各组件）把治理逻辑**塞进业务进程**；
  2026 年的主流是 **sidecar 代理**（Envoy）把服务发现、负载均衡、熔断、限流、mTLS、
  重试/超时**下沉到数据面**，业务代码零侵入。Istio（istio/istio 38408★）、
  Linkerd（linkerd/linkerd2 11499★）即此范式。
- **🔧 多语言成为硬需求**：书里默认 Java。Mesh 的最大价值正是**语言无关**的治理。
- **🔧 粒度反思**：2020 年后业界出现「微服务过细反模式」的反思，**模块化单体
  （modulith）/ 宏服务** 重新被提倡；DDD 限界上下文成为拆分的真正依据而非「越细越好」。
- **🔧 通信协议**：书里以 REST 为主；今天 **gRPC/Protobuf**（grpc/grpc 45341★）在内部
  服务间成为默认，REST 退居对外网关。
- **🔧 服务网格与 Kubernetes 融合**：今天服务部署即 Pod，治理由 Mesh + K8s
  （kubernetes/kubernetes 128015★）共同完成，书里「自己搭注册中心」的图景已淡出。

## 近年研究与工业界开源实践（2015–2026）

- **服务框架（本书 1.5 的现实答案）**：
  - `grpc/grpc`（45341★，2026-09 实测）是内部 RPC 的事实标准（Protobuf + HTTP/2）；
  - `apache/dubbo`（41579★）仍是国内最主流的 Java 微服务框架，Dubbo 3 已支持
    Triple 协议（兼容 gRPC）与应用级服务发现；
  - `alibaba/spring-cloud-alibaba`（29179★）把 Nacos/Sentinel/Seata 打包成
    Spring Cloud 一站式方案；
  - `sofastack/sofa-rpc`（3921★）是蚂蚁的 RPC 框架，配套 SOFA 体系。
- **🔧 服务网格（本书没有的一课）**：
  - `istio/istio`（38408★）是 Mesh 控制面事实标准（基于 Envoy sidecar）；
  - `linkerd/linkerd2`（11499★）以轻量、Rust 数据面著称；
  - 它们把本书 1.3.5 的容错、1.5 的治理**下沉到 sidecar**，与书里 SDK 模式形成对照。
- **注册配置中心**：`alibaba/nacos`（33419★）一栈解决注册+配置；
  `polarismesh/polaris`（2564★，腾讯北极星）主打服务网格化的治理与鉴权。
- **🔧 粒度反思的工业声音**：众多团队公开复盘「微服务过细导致分布式单体」，
  「modulith/宏服务」被重新提倡；这与本书 1.3.6 的粒度讨论形成 2026 年修正。
- **容器编排底座**：服务要跑在 `kubernetes/kubernetes`（128015★）上，
  与本书第 7 章容器化直接衔接。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「微服务 = 把单体拆成很多小服务」 | 拆分依据是**业务能力/限界上下文**，不是代码行数；拆错会变分布式单体 |
| 2 | 「去中心化 = 不需要治理」 | 去中心化是「无 ESB 中心」，治理（发现/限流/熔断/配置）仍在，只是**下沉到 SDK 或 sidecar** |
| 3 | 「微服务必须上 Docker/K8s」 | 容器化是推荐项不是前提；但 2026 年事实标准是 K8s，裸机部署微服务已罕见 |
| 4 | 「REST 永远够用」 | 内部高频调用应首选 gRPC/Protobuf，REST 退居对外网关 |
| 5 | 「熔断限流只在网关做」 | 应**多层**防御：sidecar + 框架 SDK + 网关，单点防护会被绕过 |
| 6 | 「服务越多越弹性」 | 数量与弹性非单调关系；过细反而增加网络与运维开销 |
| 7 | 🔧 本书 1.3.5/1.5 的治理靠业务进程内 SDK | 2026 年主流是 **Service Mesh sidecar** 下沉治理，业务零侵入、语言无关 |
| 8 | 🔧 本书几乎没有 Service Mesh / 云原生 | Istio 2017 年才发布，书里仅萌芽；今天治理形态已被 Mesh 改写 |
| 9 | 🔧 本书默认 Java 单体技术栈 | 多语言（Go/Rust/Node）已是常态，Mesh 正是为此而生 |
| 10 | 🔧 本书 1.3.6 粒度偏「越细越好」倾向 | 2026 年反思微服务过细，「模块化单体/宏服务」回归，拆分以 DDD 限界上下文为准 |
