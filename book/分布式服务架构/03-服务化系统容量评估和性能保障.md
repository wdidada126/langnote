> 一个真实的性能/容量评估案例、性能评估参考标准。评价「表面」主要指案例偏模板化、

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 3.2 非功能质量需求（评审的「尺子」）

| 维度 | 典型指标 |
| --- | --- |
| 性能 | 响应时间（P99/P95）、吞吐（QPS/TPS）、并发数 |
| 容量 | 可支撑的数据量、可支撑的峰值流量、存储增长速率 |
| 可用性 | SLA（如 99.95%）、年停机时长、容灾 RPO/RTO |
| 安全性 | 认证/授权/审计、防注入、敏感数据加密 |
| 伸缩性 | 水平扩容倍数、扩容耗时 |
| 扩展性 | 新增业务是否要改核心代码 |
| 可监控性 | 是否有指标/日志/链路、是否可告警 |

### 3.4 容量评估的算术（本章最有用的公式）

```text
# 教学示意，不参与构建
单实例容量 ≈ 1 / 单次请求平均耗时(秒) * 并发线程数
集群容量   ≈ 单实例容量 * 实例数 * 安全系数(通常 1.2~2)
所需实例数 ≈ 目标峰值QPS / (单实例容量 / 安全系数)

例: 目标 10000 QPS, 单请求 20ms, 单实例 50 线程
    单实例容量 = 1/0.02 * 50 = 2500 QPS
    安全系数 1.5 -> 有效容量 2500/1.5 ≈ 1667
    实例数 = 10000 / 1667 ≈ 6 台 (再留 buffer)
```

> 关键点：**峰值不是均值**，要按大促/秒杀的瞬时峰值算；还要算**存储/带宽/连接数**而非只算 QPS。

### 3.3 技术评审提纲（照书里的六段）

1. **现状**：现有系统瓶颈、历史故障；
2. **需求**：功能 + 非功能（性能/容量目标）；
3. **方案描述**：架构图、数据流、关键设计；
4. **方案对比**：备选方案与取舍理由；
5. **风险评估**：单点、容量、依赖、回滚；
6. **工作量评估**：排期与人力。

### 3.5 性能评估参考标准

- 用经验基线（如一次 DB 查询 1–10ms、一次跨机房 RPC 5–50ms、一次缓存命中 <1ms）快速判断
  方案是否离谱；远低于基线要怀疑测量错误，远高于基线要查慢查询/锁/GC。

## 版本演进

- **本书无第二版**；本节写 2017 年口径 → 2026 年视角的变化。
- **🔧 全链路压测平台化**：书里 3.4 是「手算 + 单接口压测」。2026 年主流是**全链路压测**
  （影子库/影子表、流量染色、生产环境按比例回放），阿里 PTS、京东、字节等都有成熟平台；
  双十一容量评估已高度自动化。
- **🔧 SLO/SLI/Error Budget（SRE）**：书里谈「可用性」但无量化工程。2026 年用
  SLI 定义「什么算正常」、SLO 设目标、Error Budget 决定能否发版，是容量与稳定性的统一语言
  （见 [../SRE.md](../SRE.md)）。
- **🔧 混沌工程**：书里谈应急（见第 6 章）但属被动。2026 年用**主动故障注入**验证容量与容错
  是否真的有效——`netflix/chaosmonkey`（17151★）、`pingcap/chaos-mesh`（7916★）。
- **🔧 性能剖析工具化**：书里靠经验。2026 年用 `perf`、async-profiler 出**火焰图**定位瓶颈，
  结合 `prometheus/prometheus`（66251★）+ `grafana/grafana`（76928★）做持续性能观测。
- **🔧 容量评估自动化/弹性**：结合 K8s HPA（基于 CPU/自定义指标自动扩缩），容量从「一次性算」
  变成「持续自适应」（见 [07-服务的容器化过程.md](07-服务的容器化过程.md)）。

## 近年研究与工业界开源实践（2015–2026）

- **压测工具**：JMeter、Gatling、`grafana/k6`（star 未在本目录逐一核实）用于脚本化压测；
  企业级全链路压测多为内部平台（阿里 PTS 等），开源自建以流量回放 + 影子存储为主。
- **监控/可观测底座（容量与性能持续观测）**：
  - `prometheus/prometheus`（66251★）、`grafana/grafana`（76928★）、
    `prometheus/alertmanager`（8628★）；
  - 长期存储：`thanos-io/thanos`（14220★）、`VictoriaMetrics/VictoriaMetrics`（17771★）、
    `cortexproject/cortex`（5867★）。
- **🔧 混沌工程（主动验证容量/容错）**：
  - `netflix/chaosmonkey`（17151★）是混沌工程鼻祖；
  - `pingcap/chaos-mesh`（7916★）是 K8s 原生混沌平台，与本章 3.4 容量验证互补。
- **火焰图剖析**：async-profiler、perf、`brendangregg/FlameGraph`（star 未逐一核实）是定位
  CPU/锁/GC 瓶颈的标准手段，对应本书 3.5「性能评估参考标准」的工程化落地。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「压测只压单接口」 | 单接口达标 ≠ 全链路达标；必须**全链路压测**算真实容量 |
| 2 | 「容量 = 历史峰值 × 2」 | 应按**业务目标**反推，考虑大促/秒杀瞬时峰值与存储增速 |
| 3 | 「QPS 可线性叠加扩容」 | 存在数据库/锁/网络瓶颈，扩展受 **Amdahl/USL** 限制，非无限线性 |
| 4 | 「评审是走过场」 | 评审提纲（3.3）是逼出盲点的结构化工具，必须写清风险与回滚 |
| 5 | 「性能不达标就加机器」 | 先剖析定位瓶颈（火焰图），加机器可能只是掩盖锁竞争 |
| 6 | 🔧 本书 3.4 偏手算/单接口压测 | 2026 年全链路压测 + 影子库表 + 流量染色才是标准 |
| 7 | 🔧 本书 3.2 的「可用性」无量化方法 | 应补 SLO/SLI/Error Budget（SRE），把可用性变可操作目标 |
| 8 | 🔧 本书缺混沌工程 | 容错设计要靠主动故障注入验证，而非等线上出事 |
| 9 | 🔧 本书缺持续性能观测 | 容量评估应结合 Prometheus/Grafana 持续做，而非一次性 |
