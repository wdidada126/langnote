# 09 数据完整性（Chapter 13: Data Integrity，pp.409–448）

> 对应原书第 13 章 ✅（章题与全部小节名实抓自 InformIT 官方 TOC）。数据保护主题域（13–17 章）的第一章。正文为主题级精读重构；
> 各 DBMS 约束能力差异均为 ⚠️ 文档转述，本目录零实测。

## 1. 完整性的类型（Types of Integrity，p.409）

- ✅ 章即分类开篇。本书的三分法直接写在 TOC 上：**结构完整性（Database Structure Integrity，p.410）、
  语义完整性（Semantic Data Integrity，p.414）、时态（Temporal Database Systems，p.444）**——三节即三类，罕见地把分类学做成了目录 ⚠️ 结构为实抓、细节为重构。
- 定义口径（⚠️ 转述）：完整性 = 数据在任何时刻都符合**业务规则与结构规则**；它与安全（第 14 章：谁能看）正交——合法路径下的脏数据仍是完整性事故 ⚠️ 推定。

## 2. 结构完整性（Database Structure Integrity，p.410）

✅ 页 410–414，短而硬。内容重构：
- 声明式约束层：主键/唯一/外键/CHECK/NOT NULL 的引擎支持与执行位置 ⚠️ 转述——外键的支持度是各引擎分歧最大项，
  本书持「结构完整性必须由数据库执行，应用校验只是第一道礼貌性防线」的强立场 ⚠️ 转述。
- 数据类型的严格性、域完整性 ⚠️ 重构条目。

## 3. 语义完整性（Semantic Data Integrity，p.414）

本章主体（✅ 页 414–444，独占 30 页——全书最重的单节之一，作者用墨量即立场）⚠️ 篇幅实抓/内容为重构：
1. **定义**：超越结构规则的业务规则（列间关系、跨行跨表约束、状态迁移合法性）；多数超出声明式约束表达力 ⚠️ 转述。
2. **实施位点选择**（⚠️ 重构为通行框架）：数据库触发器 / 存储过程 / 应用层 / 独立规则引擎四选一或分层，
   书中倾向**靠近数据一侧**实施——触发器与约束是「最后一道且在所有人路径上」的防线 ⚠️ 转述。
3. 断言（assertion）、列默认值规则、参照动作（CASCADE/SET NULL 等）的语义面 ⚠️ 重构。
4. 与第 6 章评审、第 22 章元数据的联动：业务规则要**写下来并登记**，否则不可审计 ⚠️ 推定（依据节题与全书流程线）。
- 中文纵深对照：[../SQL反模式.md](../SQL反模式.md)（存在已验证）的「元数据污染/键基溢出」等章节正是语义完整性失守案例集。

## 4. 时态数据库系统（Temporal Database Systems，p.444）

- ✅ 独立小节（页 444–446）。概念（⚠️ 转述）：有效时间（数据在现实中成立的时间）vs 事务时间（数据入库的时间），
  双时态（bitemporal）支持；时态约束与时态查询的特殊性。
- 回收点：第 4 章 p.177 Temporal Data Support（见 [04-数据库设计与应用设计.md](04-数据库设计与应用设计.md)）在设计层首次布点，本节在机制层收口 ⚠️ 结构实抓。
- 2012 年时态支持以 DB2 最完备、Oracle 靠闪回/审计列近似、SQL Server 2011 语法刚标准化 ⚠️ 文档转述，未实测任何引擎。

## 6. 精读要点备忘（重构）

1. 语义完整性独占 30 页 ✅，是全书的**重心偏移证据**：Mullins 认为 DBA 价值最高的战场不是让库跑得快，而是让数据「一直是对的」——
   这直接铺垫第 15 章合规（数据质量即合规）与第 22 章元数据（规则要可查）⚠️ 推定。
2. 结构/语义的分界线=「声明式可表达 vs 需要程序逻辑」；工程上按分界选实施位点，可以省掉一半关于「触发器该不该用」的无谓争论 ⚠️ 重构。
3. 时态数据是完整性被低估的第三维：历史正确性（valid time）与记录正确性（transaction time）会各自漂移，备份恢复（第 16 章）只解决后者 ⚠️ 推定。

## 7. 约束实施位点决策表（⚠️ 重构，对应 p.414–444 语义完整性核心议题；表中「书中倾向」为 ⚠️ 转述）

| 位点 | 能表达 | 强项 | 软肋 | 适用判定 |
| --- | --- | --- | --- | --- |
| 声明式约束（PK/FK/CHECK） | 结构与简单域规则 | 引擎保证、无法绕过、可目录化 | 跨行/跨表表达力弱 | **默认首选**（p.410 ✅ 立场） |
| 触发器 | 跨行跨表规则、审计列 | 贴着数据、覆盖所有写入路径 | 隐蔽、性能税、调试难 | 声明式写不出的**写路径规则** |
| 存储过程/包 | 流程性复合规则 | 事务内闭环 | 管不住旁路写入（ETL/运维直连） | 应用受控环境的业务动作 |
| 应用层 | 复杂业务语义 | 迭代快、可测试 | 多入口即多漏洞 | 作第一道礼貌防线，**不作唯一防线** ⚠️ |
| 独立校验作业（批量） | 全局一致性（对账/总量） | 可跑重型规则 | 事后发现 | T+ 兜底层（与第 20 章装载联动 ✅） |

- 组合原则（⚠️ 重构）：同一规则**至少两站设防**（就近+兜底），且在哪站违例要能区分报告——「谁破坏的」比「被破坏了」更重要 ⚠️ 转述。

## 9. 完整性失效模式清单（⚠️ 重构；评审与巡检两用）

1. 外键缺失下的孤儿行（报表口径漂移的常见根因）；
2. 检查约束缺位、脏值靠应用「自觉」；
3. 触发器被批量作业绕过（禁用触发器提效后忘记恢复）⚠️ 转述；
4. ETL 窗口内的一致性空窗未声明 SLA（第 20 章装载 ✅）；
5. 时态数据只留事务时间、丢失有效时间（历史「事实」被静默改写）⚠️ 推定；
6. 规则只存在于代码注释，无登记卡——人走规则亡 ⚠️ 对应 p.735 法则 ✅。

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
| --- | --- | --- |
| 数据完整性 | Data Integrity | 数据恒符合结构规则与业务规则的状态 |
| 结构完整性 | Database Structure Integrity | 键/约束/类型层面的正确性（本书三分法之一） |
| 语义完整性 | Semantic Data Integrity | 业务规则层面的正确性，超出声明式约束表达力 |
| 时态完整性 | Temporal Integrity | 时间维度上的正确性（本书三分法之三） |
| 声明式约束 | Declarative Constraint | PK/UNIQUE/FK/CHECK/NOT NULL 等 DDL 级规则 |
| 参照动作 | Referential Action | 外键联动的 CASCADE/SET NULL 等策略 |
| 断言 | Assertion | 跨对象的全局约束表达 ⚠️ 多数引擎支持有限，转述 |
| 触发器 | Trigger | 数据变更时执行的服务端规则程序 |
| 有效时间 | Valid Time | 事实在现实世界成立的时间区间 |
| 事务时间 | Transaction Time | 事实被数据库记录的时间区间 |
| 双时态 | Bitemporal | 两时间轴同时建模 |
| 域完整性 | Domain Integrity | 列取值范围/格式的正确性 ⚠️ 重构条目 |

## 最新演进与工业实践

1. **声明式约束的「引擎方差」仍在扩大而非收敛**：MySQL/InnoDB 的外键语义、PG 的约束与行级触发完整性体系、
   云数仓普遍**弱化或不支持**外键（一致性交给 ETL/治理层）——本书「约束必须在库端执行」的立场在 OLAP 侧基本失守，在 OLTP 侧仍是金标准 ⚠️ 转述；
   PG 权威描述 https://www.postgresql.org/docs/current/ddl-constraints.html （✅curl 200）。
2. **语义完整性外移至数据网格/契约**：2024–2026 的新形态是「数据契约（data contract）+ schema 注册表 + 质量规则即代码」，
   规则表达离引擎更远、离流水线更近；波内 [#201《Data Mesh》](../Data_Mesh/00-总览与阅读地图.md)（已落盘）是该转向的正面文本，义务波尾闭环。
3. **时态支持标准化**：SQL:2011 时态表进入商用实现（DB2、SQL Server 2016+ 系统版本表、MariaDB 系统版本等）⚠️ 一律文档转述、未实测；
   审计/合规（第 15 章主题）成为时态建模的第一买单场景 ⚠️ 转述。
4. **完整性×安全的合流**：现代数据质量平台（Great Expectations 类工具 ⚠️ 名称提及、URL 未经本环境校验故不附）
   把「语义规则」做成了可执行测试——恰是 p.414 三十年之久的 30 页主张的 CI 化，与 [11-法规遵从与数据治理.md](11-法规遵从与数据治理.md) 的数据质量节互为镜像。
