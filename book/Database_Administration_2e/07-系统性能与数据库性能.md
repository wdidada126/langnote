# 07 系统性能与数据库性能（Chapter 10: System Performance，pp.319–348；Chapter 11: Database Performance，pp.349–372）

## 一、第 10 章：系统性能

## 1. 更大的环境（The Larger Environment，p.320）

- ✅ 开篇即把 DBMS 放回整机：CPU、内存、磁盘 I/O、网络四大资源与 OS 调度/文件系统的中介层 ⚠️ 重构。
- 方法论（⚠️ 转述）：**先证明瓶颈在 DBMS 之外还是之内**，再决定动作——避免「DBA 背整机锅」或「调 SQL 治 I/O 病」的错位。
- 磁盘章节分量最重（2012 年 HDD 仍主流）：顺序 vs 随机 I/O、条带化与镜像布局、预读与写回缓存的取舍 ⚠️ 重构；
  SSD 已在第 1 章「newer technology」出现，此处仅局部考虑 ⚠️ 待核验。

## 2. DBMS 安装与配置议题（DBMS Installation and Configuration Issues，p.327）

本章主体（✅ 页 327–345，18 页）。参数族（⚠️ 重构，通用关系引擎公约数）：
1. **内存分配**：缓冲池/排序区/连接内存的配比与总账，防止 OS 换页；
2. **I/O 并行**：容器/表空间到物理盘的条带映射、异步 I/O 启用；
3. **日志与临时空间**：写顺序性对 fsync 策略的要求、temp 表空间独立布局；
4. **进程/线程模型**与连接上限、并发度参数；
5. **安装布局本身即性能决策**——回指第 2 章 Installing the DBMS（p.75 ✅）：安装期错误要到负载期才暴露 ⚠️ 转述。

## 3. 系统监视（System Monitoring，p.345）

- ✅ 小节存在但短（页 345–346）：OS 计数器（CPU/分页/磁盘队列）与 DBMS 内部计数器的双轨采集、基线与趋势比对 ⚠️ 重构。
- 定位说明：本节是「最小可行为」，完整的工具与采购评估在 ch23（本目录 [16-元数据管理与DBA工具.md](16-元数据管理与DBA工具.md)）✅。

## 二、第 11 章：数据库性能

## 4. 优化数据库的技术（Techniques for Optimizing Databases，p.349）

本章主体（✅ 页 349–365，16 页）。在数据**结构**层面动手术的技术族（⚠️ 重构）：
1. **索引优化**：补建/合并/删除冗余索引，匹配访问路径（设计期版本在第 4 章 p.150 ✅）；
2. **统计信息维护**：让优化器看见真实数据分布 ⚠️ 转述；
3. **反规范与物化**：把第 4 章 p.160 的承诺在运行期兑现/修正 ⚠️ 推定；
4. **集群/分区与数据布局**：把热数据放近、把扫描变裁剪；
5. **对象级参数**：填充度、初始/增量分配（与第 18 章空间管理 p.587 ✅ 分界：那里管容量，这里管速度）。
- 分层调优的判别式（⚠️ 转述）：结构层技术优先于参数层，参数层优先于 SQL 层——与第 9 章「静态优先」一致。
- 深入对照：索引/结构的引擎机制在 [../mysql/00-总览与阅读地图.md](../mysql/00-总览与阅读地图.md) 与 [../数据库索引设计与优化.md](../数据库索引设计与优化.md)（存在已验证）；
  方法论史（实验证明每条技术收益）在 [../Database_Tuning/00-总览与阅读地图.md](../Database_Tuning/00-总览与阅读地图.md)。

## 5. 数据库重组织（Database Reorganization，p.365）

- ✅ 独立小节（页 365–371）。问题机理（⚠️ 转述）：行迁移/链、碎片化（第 18 章 p.595 Fragmentation and Storage ✅ 为其存储面）、
  索引深度劣化，使「逻辑未变、物理已胖」。
- 手段：REORG/重建索引/收缩，及「在线重组织 vs 停机窗口」的可用性权衡——直接吃第 8 章 Ensuring Availability（p.287 ✅）的红利 ⚠️ 推定。
- 现代化名：VACUUM/自治回收在 PG 文档有权威描述（https://www.postgresql.org/docs/current/routine-vacuuming.html curl 200 验证 ⚠️ 转述）；
  MySQL 的 OPTIMIZE TABLE/在线 DDL 复制表方案见 [../高性能mysql.md](../高性能mysql.md) ⚠️ 转述。

## 7. 精读要点备忘（重构）

1. 第 10+11 章合计 54 页 ✅，覆盖三层法的前两层；本书的隐含漏斗是「系统层排除 → 结构层消化 → 才轮到 SQL 层」，
   与市面单引擎调优书「上来就 EXPLAIN」的路径相反——这是它作为管理书的气质注脚 ⚠️ 推定。
2. p.327 配置节以「安装即性能」破题，提醒读者：**调优的第一现场往往在安装决策时已落幕**（回指 [02-创建数据库环境.md](02-创建数据库环境.md)）⚠️ 转述。
3. 重组织（p.365）在 2012 是 DBA 的周期体力活；2026 已半自动化（自治回收、托管服务后台整理），但「整理窗口 vs 可用性预算」的决策结构原样保留 ⚠️ 转述。

## 8. 配置参数族盘点表（⚠️ 重构，对应 p.327–345 的 18 页；参数名一律通用化，不指名各引擎私有项）

| 参数族 | 决策问题 | 主要牵连层 | 失控症状 |
| --- | --- | --- | --- |
| 内存总账 | 引擎与 OS 的边界在哪 | 缓冲池/排序 | 换页风暴、全库卡顿 |
| 缓冲池 | 热数据装得下吗 | 读路径 I/O | 物理读率爬升 |
| 日志/检查点 | fsync 频率与恢复时长的互换 | 写路径 | 提交延迟尖刺或恢复超窗 |
| I/O 并行/条带 | 容器与盘的映射 | 存储层（p.579 ✅） | 单盘热点 |
| 连接/并发上限 | 会话内存×并发=总账 | 应用链路（p.661 ✅） | 内存溢出或排队雪崩 |
| 并行度/优化器档位 | 单查询吃多少资源 | CPU | 批任务挤死 OLTP |
| 临时空间布局 | 排序/散列的落点 | 装载/报表窗口 | 大查询互相踩踏 |

- 使用说明（⚠️ 推定）：每族留「当前值/理由/复核日期」三列——第 24 章 Write Down Everything 在参数域的落地 ⚠️ 联动结构实抓。

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
| --- | --- | --- |
| 瓶颈定位 | Bottleneck Analysis | 判定受限资源（CPU/内存/I/O/锁）的动作 |
| 条带化 | Striping | 数据跨盘并行分布的布局法 |
| 缓冲池配比 | Buffer Pool Sizing | 内存总账中的引擎侧份额决策 |
| 异步 I/O | Asynchronous I/O | 不阻塞线程的读写提交方式 ⚠️ 通用转述 |
| 统计信息 | Statistics | 优化器赖以估行的数据分布摘要 |
| 索引调优 | Index Tuning | 增删合并索引以匹配访问路径 |
| 物化/反规范 | Materialization/Denormalization | 以存储换读取路径的结构手段 |
| 行迁移/链 | Row Migration/Chaining | 行长大或跨页导致的读取罚单 ⚠️ 术语通用化 |
| 碎片化 | Fragmentation | 逻辑连续数据物理离散化 |
| 重组织 | Reorganization (Reorg) | 在线/停机重建物理布局恢复紧凑 |
| 系统监视 | System Monitoring | OS+DBMS 双轨计数器采集与基线比对 |
| 三层调优 | System/Database/Application Tuning | 本书第 10–12 章的分层执行序 |

## 最新演进与工业实践

1. **硬件前提整体换代的再解读**：2024–2026 主流是 NVMe+RDMA+超大内存，第 10 章的磁盘布局学问大多沉入云存储层
   （EBS 类卷性能等级/本地 NVMe 缓存），DBA 的对应决策从「条带几块盘」变成「选哪档存储类型」⚠️ 转述（以 AWS RDS
   https://aws.amazon.com/rds/ 与 Oracle 文档库 https://docs.oracle.com/en/database/oracle/oracle-database/ 的现行形态为准，curl 均 200）。
2. **自动调参与索引自动化**：查询驱动的自动调优系统已发论文——BlackMagic（PVLDB 2019，DOI `10.14778/3352063.3352072` ✅ Crossref 200），
   工业侧 Oracle Autonomous DB（https://www.oracle.com/database/autonomous-database/ ✅200）把第 11 章「索引优化+重组织」变成了后台守护进程；
   「结构层优先」的分层判断仍是人机分工的划线依据 ⚠️ 转述。
3. **重组织的现代形态**：PG 的 autovacuum/膨胀治理（文档页 ✅ 见上）与 MySQL 8.x 的在线 DDL/表重建流水线是两大主流答案；
   列存与向量化引擎则从根上减少「物理布局劣化」问题——湖仓侧压缩与布局优化进入论文期：BtrBlocks（SIGMOD 2023，DOI `10.1145/3589263` ✅ Crossref 200）⚠️ 结论转述。
