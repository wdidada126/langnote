## 精读笔记

### 1. 备份谱系（第 22 章）

书中给出从"糙到精"的三级火箭：

1. **冷拷贝数据文件**：停写或从延迟节点拉文件——一致性依赖"不再写"或引擎静默。
2. **文件系统快照**（LVM/企业 SAN）：书中假设 MMapv1，需"先 fsync+ 锁集合（`fsyncLock`）再拍"的仪式——这是 22 章最技术也最速朽的一段。
3. **mongodump/mongorestore**：逻辑备份，BSON 转储；对副本集从 secondary 读；**分片集群要"同一时间戳"对齐 mongos 转储 + mongoseed 重建分片**——细节繁琐到书里用"痛苦但可行"描述。
- **mongooplog 增量**：转储 + oplog 重放 = 手工 PITR；`oplogLimit/tsFromSecondary` 选项——概念即现代连续备份的雏形。

### 2. 部署工程（第 23 章：本书最"耐久"的一章）

作者的金属层建议清单（2013）：**SSD 优先、RAID10（拒绝 RAID5 写惩罚）、XFS/ext4、noatime、关闭 swap（或 `vm.swappiness=0`）、THP 关闭、NUMA 交叉访问控制、readahead 调小、ulimit -n 拉高、ntp 时钟同步（副本集对时钟敏感！）、OOM killer 豁免 mongod、停掉 cron 风暴**。多数条目至今原样出现在官方安装文档（XFS/ext4 推荐、THP、ulimit 三件套）。

### 3. 备份策略对比表（把 22.1–22.4 摆进同一坐标系）

| 策略 | 一致性机制 | 粒度 | 恢复速度 | 对服务器的侵入 | 2026 存活性 |
|---|---|---|---|---|---|
| 停写冷拷贝数据文件 | 全局静默 | 整库 | 最快（复制回去即起） | 停服 | 仅归档/灾备极端场景 ⚠️ |
| 延迟节点拷贝 | 时间机器静默（滞后窗口内无写） | 整库 | 快 | 需专用成员 | 思路存活（slaveDelay→secondaryDelaySecs）⚠️ |
| 文件系统快照（LVM/SAN） | `fsync+fsyncLock` 仪式（MMapv1 专属） | 整卷 | 快（回卷） | 短暂锁集合 | 仪式已随引擎退役；WT 走 checkpoint 一致快照 ⚠️ |
| mongodump 逻辑转储 | 逐集合游标读（**非全局一致**，靠 oplog 补齐） | 库/集合/查询级 | 慢（重放 BSON+重建索引） | 最低（普通读） | **永生**——跨版本/跨云/切片主力 ✅ |
| mongodump + mongooplog 增量 | 全量转储+oplog 连续捕获重放 | 任意时间点 | 中 | 低 | 手工 PITR 前身，被平台吸收 ⚠️ |
| 块级/连续备份（Ops Manager/Atlas） | checkpoint + oplog 流水线 | 任意时间点（PITR） | 快（块级还原） | agent 部署 | 企业默认 ✅（产品名实抓域内）|

推演要点：**逻辑备份买"灵活"、付"恢复时间"**——mongodump 不含全局快照一致性，书中用 `oplogLimit` 对齐时间戳来补洞（22.1.3），这正是 PITR 的机制胚胎；分片集群的"mongos 同刻转储+按 shard 并行"复杂度（22.3）是逻辑路线的天花板，也是平台块级备份存在的理由。

### 4. 为什么 mongodump 单独不够：捕获-重放配对纪律（22.4 机制推演）

1. 全量阶段：mongodump 边读边记下起始 oplog 时间戳 `ts0`（副本集上加 `--oplog` 才做此捕获）。
2. 转储期间发生的写**不会**进 BSON 文件（游标读到哪算哪）——一致性缺口=转储时长。
3. 恢复阶段：mongorestore 灌完 BSON 后 `--oplogReplay` 重放 `ts0→终点` 的 oplog 增量，把库追到捕获终点。
4. 缺口条件：**两次备份间 oplog 必须连续**（窗口内未被覆盖）——窗口估算与扩容纪律直接进备份 SLA（07 文件 12.4.6 的公式在此兑现）。
5. 危险动作：单独 mongodump 不带 oplog 却当"完整备份"用——书里没写、事故里常见；RPO=备份周期，且无任意点恢复能力。⚠️（机制为文档转述）

这条"全量+增量重放"结构 2026 原样活在 Atlas PITR 与 Ops Manager 连续备份里——只是 agent 替你捕获、平台替你校验窗口连续性。

### 5. 恢复演练 runbook（书中隐含、本目录显式化，⚠️ 全部为文档通识）

1. **频率**：季度起步；业务变更（大迁移/新分片键上线）前加做一次——演练对象是"最新备份+最新 oplog"，不是祖传样本。
2. **环境**：孤岛实例（断网/独立账号/随机端口），从备份介质直接拉起——验证的是介质可读性，不是本地缓存。
3. **还原**：`mongorestore --oplogReplay`（或平台 PITR 选一个目标时间点）——把"恢复到任意时刻"当成产品能力来验收。
4. **校验三件套**：dbStats/collStats 数量级对账 → 关键集合抽样哈希（业务不变式，如余额和） → 应用冒烟（读写各一遍真实查询形状）。
5. **计时**：记录全量重放与索引重建耗时——这就是 RTO 的真实数字；书中"mongorestore 慢"的告诫在此量化成 SLA 谈判筹码。
6. **回滚预案**：演练失败项逐条进整改清单（密钥不可达/介质损坏/oplog 断链各写处置路径）。

未过演练的备份在事故复盘里的正式名称是"希望"——22 章三级火箭的全部价值要用这条 runbook 来兑现。

## 2013 基线 → 2026 现状对位勘误

| 本书说法（2013） | 2026 现状 | 依据 |
|---|---|---|
| `fsync + fsyncLock` 快照仪式 | MMapv1 专属仪式消失；WT 时代文件级备份需 **checkpoint 一致性**：官方 **filesystem-independent backup（`createBackup` 命令）** + 块级备份工具 | ✅ https://www.mongodb.com/docs/manual/core/wiredtiger/（引擎页）；createBackup ⚠️ |
| mongodump 是主力 | 仍是**逻辑备份标准件**（版本兼容纪律：用新版工具备份旧服务），但企业主力转向块级/连续备份 | ⚠️（工具包纪律为官方文档通识）|
| mongooplog 手工 PITR | **Ops Manager/Cloud Manager 块备份 + oplog 重放 = PITR 产品化；Atlas 连续备份（默认 1 天可扩，任意时间点恢复）** | ⚠️（Atlas 能力为官方文档描述）|
| 分片备份的"同时间戳 mongos 转储" | 流程保留但被平台吸收；mongodump 对 sharded 集群加 `--query`/按分片并行等现代旗标 | ⚠️ |
| RAID10 + 本地 SSD | 云盘/ESSD + 副本集三副本替代 RAID 信仰；RAID 建议淡出（Atlas 存储层不可见） | ⚠️ |
| 物理机/虚拟化 | **容器化/K8s 成自建主流**（官方 Community Operator；CPU/内存限制策略有官方文档背书，书中"虚拟化有害"论被条件化推翻） | ⚠️（Operator 为公开项目）|
| THP/NUMA/ulimit/ntp 清单 | **几乎原样保留在现行安装文档**——本目录唯一"零勘误"大块；WT 对 NUMA 敏感度低于 MMapv1 但建议仍在 | ✅ https://www.mongodb.com/docs/manual/administration/install-community/（实抓）|

## 常见误区（本目录归纳）

1. "副本集就是备份"——同步的是错误传播（误删秒到全体）；延迟节点只是缓期，真备份另做（06 文件误区 3 在此兑现账期）。
2. "mongodump 不带 oplog 也算完整备份"——转储窗口内的写全丢，RPO=备份周期；捕获-重放必须成对（上文推演第 4 节）。
3. "备份成功=恢复可行"——未演练的备份只是文件；恢复演练（restore 到孤岛+校验）才是验收动作，书中 22 章隐含、社区事故反复补写。⚠️
4. "fsyncLock 仪式现在还要学"——MMapv1 专属；WT 文件级备份的正确入口是 checkpoint 一致快照/`createBackup` 路线（对位表）。
5. "关 swap 万能"——OOM killer 与内存配额才是真裁判（12 文件），容器里"关 swap"表现为 limit 设置+驱逐策略。
6. "ntp 是玄学合规项"——选举计时/oplog 时序/证书校验全对时钟敏感；漂移的代价以复制拓扑为单位爆发（12 文件坑 4）。
7. "备份加密=安全"——书中没有的威胁模型（勒索/供应链）要求不可变存储+隔离账号+密钥分置三件套（下文演进）。

## 核心概念速览（中英对照）

- **mongodump/mongorestore** — BSON 逻辑备份/还原双工具：书中主力、今日仍在。
- **fsyncLock** — 文件级备份冻结（MMapv1）：随引擎退役。⚠️
- **createBackup** — WT 文件系统无关备份命令：快照仪式的官方继任者。⚠️
- **mongooplog** — oplog 抓取重放：手工 PITR 前身（工具已被平台取代 ⚠️）。
- **PITR** — Point-in-Time Recovery：连续备份 + oplog 重放的产品化。
- **RAID10** — 书中磁盘答案：写密集 + 镜像条带；云时代淡出。
- **THP** — 透明大页：安装文档至今要求关闭/限制。✅
- **noatime** — 不记访问时间挂载项：建议存活 13 年。
- **ntp 同步** — 时钟一致性：副本集/选举/Oplog 时序的地基纪律。
- **OOM killer** — Linux 内存杀手豁免配置：`--maxMem`?（书中用 OS 侧手段，现代用 systemd `OOMScoreAdjust`）。
- **Community Operator** — K8s 官方运维控制器：部署叙事的换代标志。⚠️
- **RPO/RTO** — 恢复点/恢复时间目标：备份谱系六档的验收坐标系（书中未命名，本目录补纲）。
- **oplogLimit** — mongodump/mongorestore 的时间戳对齐旗标：逻辑路线做"准 PITR"的机关（22.1.3）。
- **捕获-重放配对** — dump 记 ts0 + restore 重放：mongodump 一致性的成立条件（本节推演核心）。
- **不可变备份（immutability）** — Object Lock/版本化/离线副本：勒索时代对 22 章的追加要求。⚠️

## 最新演进与工业实践

- **备份三级形态（2026）**：逻辑（mongodump，跨云/迁移/切片场景仍不可替代）→ 块级（Ops Manager，自建企业）→ 连续 PITR（Atlas，默认能力）。书中"选哪级"的问题变成"预算与合规选哪家"。
- **Ransomware 时代的不可变性**：对象存储 Object Lock/版本化 + 离线副本进入 MongoDB 备份规范——书中 22 章没有对手威胁模型；官方 2023+ 安全公告持续强调最小权限 + 备份隔离。⚠️（叙事性判断）
- **部署默认值变化**：官方容器镜像 + Helm/Operator 的资源限制模板（cpu/mem/liveness）接管书中 23 章手工调优；但**上 OS 裸金属仍要回来抄这章**——THP/ulimit/ntp/swap 清单在 8.x 安装文档原文可见（✅ 已核验安装页）。
- **工具形状**：`mongodump` 属于独立的 MongoDB Database Tools 发行（与服务器版本解耦，支持向后兼容转储）——升级服务 ≠ 换旧转储。⚠️ 细节以工具兼容矩阵为准
- **备份预算的语言变了**：书中"要不要买快照设备"的选型题，2026 化为三参数谈判——保留期天数、PITR 窗口深度、副本地理分布（Atlas 各层与各云市场定价差异大，尽调时逐项核对官方矩阵）。⚠️
- **部署清单的容器化改写**：THP/ulimit/swap/ntp 四件套在 K8s 里分别对应 host 级 init 脚本/SecurityContext+资源 limit/`swapBehavior`/宿主机 chrony——清单没变，执行层换世；照抄 2013 命令进 Pod spec 是新型事故源。⚠️
