## 精读笔记

### 1. 反范式化的判据：基数

作者把关系代数的"1:1 / 1:N / N:M"翻成文档决策表：

- **1:1 或 1:few** → 内嵌（one-to-few 的"few"以数百条为界，16MB 与"数组不能无限膨胀"是硬约束——内嵌数组的每个元素都要搬移整个文档，这是 MMapv1 时代的真实痛点，书里用 padding 机制解释）。
- **1:many / N:M** → 引用 + 手工 join（"应用层 join"），必要时维护双向引用。
- **无限增长的对端**（粉丝、评论、日志）→ 单独集合 + 冗余计数；书中给出"用户存 userids 数组 vs 关系存两端"的经典分析：**有界数组内嵌、无界数组外引**。
- 反范式带来的写放大与"一致性由谁负责"问题，留给 8.4：应用层多步写要么放弃强一致、要么用"findAndModify 单文档原子性 + 状态标记/补偿"。

### 2. 文档增长与 padding（时代烙印）

MMapv1 的"文档原位增长、预留 padding、空间碎片化、`compact` 整理"整节是本书最具体的运维建议之一。⚠️ 该机制随 WiredTiger（文档级压缩、记录搬移）整体作废——但"设计时就限制数组大小"的结论保留。

### 3. 迁移与"不要用 Mongo 的场景"

- 模式迁移：文档"天然可缺字段"，渐进重写（`$set` 补版本号字段）即可无锁演进——作者对比 SQL 的 ALTER TABLE 之痛。
- 8.6 罕见地**劝退自家数据库**：多步复杂事务重度依赖者、重度 ad-hoc 报表（当时缺 join/管道弱）、数据高度关系化且查询模式不可预知——2026 年看这份清单需要按事务/`$lookup`/Atlas Search 重新校准（见对位表）。

## 2013 基线 → 2026 现状对位勘误

|---|---|---|

## 核心概念速览（中英对照）

- **反范式化** — Denormalization：冗余换读性能，文档库的默认姿势。
- **内嵌模式** — Embedding：1:1/1:few 关系直接进同一文档。
- **引用模式** — Referencing：无界/共享关系存独立集合 + 外键字段。
- **基数决策表** — Cardinality（1:1/1:N/N:M）：内嵌 vs 引用的判据框架（本章核心贡献）。
- **填充因子** — Padding Factor（MMapv1）：文档原位增长的预留空间，已随引擎换代作废。
- **模式迁移** — Schema Migration（文档式）：版本字段 + `$set` 渐进重写，无需停服 DDL。
- **补偿事务** — Compensating Transaction：无跨文档原子性时的人工回滚逻辑。
- **物化视图** — Materialized View：`$out/$merge` 定时重算聚合结果（书后时代工具化）。
- **热文档问题** — Hot Document：单文档承载超高频写（计数器）时的锁瓶颈。
- **工作流字段** — Status Flag/两阶段写：书中"转账式"多步一致性手法。
- **schema 校验器** — JSON Schema Validator（3.6+）：给"无模式"补上强制闸门。

## 最新演进与工业实践

- **2026 设计共识与本章高度一致**：MongoDB 官方数据建模指南（✅ 实抓 https://www.mongodb.com/docs/manual/data-modeling/ ）的"访问模式优先、嵌入减少读、引用限制增长、多值字段慎重"四原则就是 8.1–8.3 的现行版。
- **事务没有改变设计重心**：官方文档仍建议 schema 按"无事务"设计，因为分片集群事务有延迟/资源成本；"transactions are possible, not free"是社区高频警句。✅ 事务页实抓
- **模式治理工具化**：Atlas Schema Analysis、schema suggestions、以及向量时代新增的**embedding 字段版本管理**（模型换代导致向量列重建）是 8.5"模式迁移"的 AI 续题。⚠️ 产品能力描述，未实测。
- **时间序列/日志类数据的归宿变了**：6.0 原生 **clustered/time-series collections** 取代"手工按天分集合"；本书 8.2"删除旧数据"章节的手艺被 TTL + 时序集合压缩成配置项。✅ https://www.mongodb.com/docs/manual/core/clustered-collections/（实抓）
