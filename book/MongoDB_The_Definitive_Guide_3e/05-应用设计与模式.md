## 精读笔记

### 1. 反范式化的判据：基数（8.1）

作者把关系代数的基数翻成文档决策表，全章围绕它展开：

- **1:1 / 1:few → 内嵌**：一次读全取、随父文档原子更新；边界是 16MB 与"数组增长要搬移文档"（MMapv1 语境下尤其昂贵）。
- **1:many / N:M → 引用**：独立集合 + 外键字段 + 应用层 join；必要时双向引用（两侧都冗余维护，写放大换读路径）。
- **无界端（粉丝、评论、日志、关注列表）→ 一律外引**："有界数组内嵌、无界数组外引"是本章被引用最多的一句话；书中用"好友/粉丝"经典案例演示失败的内嵌（数组无限膨胀 + 每次关注搬移整个用户文档）。
- 数据表示例子：博客（文章 + 少量评论内嵌、评论无限则外引）、产品目录（属性动态 → 文档天然优势）、社交网络（双向关系的读模式决定存法）。

### 2. 写路径优化与治理（8.2–8.3）

- 优化文档增长：预留形状（先写定字段再填充）、避免频繁"加一个字段"式更新（padding 机制时代的技艺，见对位表）。
- 删除旧数据：按时间分集合 + `drop` 整集合 vs TTL vs 逐条删的成本梯度。
- 库/集合划分原则：一个库一个应用域？书中务实——"备份粒度、权限粒度、内存驻留"三者决定切分，别被关系库"库=系统"惯性绑架。

### 3. 一致性、迁移与劝退清单（8.4–8.6）

- 无跨文档原子 → 手艺四件套：单文档 `findAndModify` 原子改、多步写带**状态标记 + 补偿**、冗余计数的"慢同步"（定时对账）、"接受最终一致并显式声明"。
- 模式迁移：版本字段 + 渐进 `$set` 重写、读写两侧兼容新旧版——对比 SQL 的 ALTER TABLE 停服之痛，文档库的"在线演进"是真优势。
- 8.6 劝退清单（罕见地劝退自家）：重多步事务、重度 ad-hoc 报表、高度关系化且查询模式不可预知——2026 年需重新校准（对位表）。

### 4. 基数决策表（把 8.1 论证压缩成一页）

| 关系 | 形态例 | 首选 | 理由 | 翻脸条件 |
|---|---|---|---|---|
| 1:1 | 用户↔档案 | 内嵌 | 一读全得、原子更新 | 一侧巨大 → 拆（近似 1:1 的 1:few） |
| 1:few（有界） | 文章↔≤百条评论 | 内嵌数组 | 随父原子、免 join | 增长无界 → 变 1:many，必须外引 |
| 1:many（无界） | 用户↔粉丝、订单↔明细流水 | 引用（独立集合） | 防 16MB/搬移雪崩 | 读永远带父键聚合 → 考虑分桶（子文档组） |
| N:M | 课程↔学生 | 双向引用或关系集合 | 两侧都可独立扩 | 高频"两侧都要全量" → 预计算视图（$merge） |

判据一句话：**内嵌优化读、引用限制增长**——与 2026 官方建模指南口径一字不差（✅ data-modeling 页实抓）。

### 5. 模式词典（本章 → Applied Design Patterns 的展开位）

- **计数桶 Counter**：热门计数（点赞/库存）拆成 N 个文档桶轮写、读时求和——书中"计算字段"的极限版；WiredTiger 文档级并发大幅缓解后，桶数可小于书中建议 ⚠️。
- **文档拆分 Document Splitting**：横向（少字段文档+扩展文档）与纵向（按访问热度分表）——大对象治理，2026 由 16MB 上限背书仍在。
- **属性快照 Attribute Snapshot**：订单里冻结商品价格/税率——"反范式 = 记录事实而非引用现值"的经典表述。
- **树结构**：materialized path/嵌套集/祖先数组的文档化表达——`$graphLookup`（3.4+）出现后新增"引用 + 递归查询"选项 ⚠️。
- 以上命名体系归属姊妹书《Applied Design Patterns》（00 谱系 ⚠️ O'Reilly 页 403 未能直验），本章是其论文版。

### 6. 时间分桶：8.2"删除旧数据"的 2026 终局

- 书中方案是"按天/月分集合 + drop 整集合"；现代官方建模指南给出**bucket collection pattern**：把 N 个时间事件折叠进一个"分钟/小时桶文档"（数组内仍是内嵌、桶间按时间引用）——1:few 与 1:many 之间的人工阶梯，读写局部性与"删旧=删桶"同时达成。⚠️（data-modeling 页通识，模式细节未逐页核验）
- 原生**时序集合**（5.0+）则是该模式的引擎内置版：自动分桶 + 元数据分离 + TTL，8.2 的手艺被压缩成两个配置项（13/08 文件对位）。
- 设计课要点不变：**先画访问模式，再定内嵌边界**——分桶只是把"无界数组"改写成"有界数组的链表"，基数决策表（第 4 节）仍是判据。

## 常见误区（书中显式纠正的）

1. "文档库 = 把 JSON 扔进去"——设计失误的代价与关系库同量级，只是罚单形式不同。
2. "内嵌一定快"——更新放大与 16MB 逼近时的雪崩。
3. "计数冗余无所谓"——不一致会永久累积，对账任务必须成文。
4. "无模式所以不需要迁移计划"——恰恰相反，**没有 DDL 强制你迁移 = 全靠自觉**。
5. "事务来了就不用设计了"——4.x 事务改变兜底手段，不改变"单文档原子最优"的成本结构；跨片事务更贵（05 对位表）。
6. "schema 校验器 = 建模"——validator 只拦畸形，拦不住坏设计（无界数组照样合法）。
7. "文档越小越好"——过度范式化把一次读拆成十次往返；基数表左右都是账，别只盯 16MB。
8. "内嵌了就不用建索引"——内嵌数组/子文档字段照样要（点号路径）索引，且多键索引每元素一条目；写放大账在 03 文件。

## 2013 基线 → 2026 现状对位勘误

| 本书说法（2013） | 2026 现状 | 依据 |
|---|---|---|
| 无多文档事务，一致性全靠手艺 | 4.0/4.2 有 ACID 事务：**"仍按无事务设计，事务兜底关键路径"**成官方共识——本章方法论不作废，只多了安全网 | ✅ https://www.mongodb.com/docs/manual/core/transactions/（实抓） |
| 应用层 join 痛苦（引用模式代价） | `$lookup` 缓解读侧；写侧反范式仍首选——决策树原样可教 | ⚠️ |
| 无界数组危险（16MB + 搬移成本） | 16MB 不变；"无界数组反模式"被 Atlas **schema suggestions** 产品化为自动告警 | ⚠️（同域文档体系） |
| padding/文档增长调参 | WiredTiger 时代 padding 概念整体退役；"限制数组大小"结论保留 | ✅ WT 页实抓 |
| 模式迁移全靠自觉 | **JSON Schema validator（3.6+）** 给写入设闸门；Atlas 模式分析 + 迁移工具链 | ✅ https://www.mongodb.com/docs/manual/data-modeling/（实抓） |
| 不适合：重度报表 | 报表仍弱项：BI Connector/Atlas SQL 只能轻量；重分析 → 湖仓/Flink 阵营 | ⚠️ |
| 不适合：多步事务 | 部分解禁（事务性能有成本、分片事务更重） | ⚠️ |
| （无对应） | 新增红线：**热文档高频写**（单文档锁竞争）、图遍历（`$graphLookup` 勉强）、纯 OLAP | ⚠️ |

## 核心概念速览（中英对照）

- **反范式化** — Denormalization：冗余换读性能，文档库默认姿势。
- **内嵌模式** — Embedding：1:1/1:few 关系入同一文档。
- **引用模式** — Referencing：无界/共享关系独立集合 + 外键。
- **基数决策表** — Cardinality（1:1/1:N/N:M）：内嵌 vs 引用的判据框架（本章核心贡献）。
- **有界/无界数组** — Bounded/Unbounded Array：能否内嵌的分水岭。
- **填充因子** — Padding Factor（MMapv1）：文档原位增长预留——已随引擎退役。
- **补偿事务** — Compensating Transaction：无跨文档原子时的人工回滚。
- **状态标记写** — Status Flag / 两阶段写：书中转账场景手艺。
- **对账任务** — Reconciliation：冗余计数慢同步的兜底。
- **模式迁移** — Schema Migration：版本字段 + 渐进重写的无锁演进。
- **schema 校验器** — JSON Schema Validator（3.6+）："无模式"的强制闸门。
- **热文档** — Hot Document：单文档承载超高频写时的锁瓶颈。
- **物化视图** — Materialized View：`$out/$merge` 定时重算（书后工具化）。

## 最新演进与工业实践

- **官方建模指南与本章同构**（✅ data-modeling 页实抓）："访问模式优先、嵌入减少读、引用限制增长、多值字段慎重"——2026 年教材语言与 2013 年一字不差地兼容，这是本章含金量的证明。
- **事务改变兜底而非重心**：分片事务延迟/资源成本使官方持续建议"事务是例外"；面试语境的标准答案：先问能否改 schema（内嵌/原子单文档），事务做最后手段。✅ 事务页
- **模式治理工具化**：Atlas Schema Analysis、schema suggestions（无界数组告警等）；**embedding 字段的版本管理**（换嵌入模型 → 双写灰度 → 重建向量索引）是 8.5"模式迁移"的 AI 续题。⚠️ 产品描述未实测
- **日志/时序数据的归宿变了**：原生时序集合 + clustered collections 取代"手工按天分集合"——8.2"删除旧数据"被压缩成 TTL + bucket 配置。✅ https://www.mongodb.com/docs/manual/core/clustered-collections/（实抓）
- **模式词典的分工**：本章给判据，Applied Design Patterns 给命名目录，DDIA 给通用理论——三书连读是本文件推荐的"设计三件套"（另两书链接见上）。
