## 精读笔记

### 1. 索引的物理与语法（第 5 章）

- MMapv1 下索引是磁盘 B-tree、内存中靠页缓存加速——**索引常比数据先驻留内存**，这是全书"工作集"叙事（21 章）的物理基础。
- 复合索引 = 有序键元组 B-tree：**前缀可用、等值在前范围在后、排序方向须匹配**（书里用手推 `{a,b,c}` 树解释 8 种可加速形态）。
- `$in/$or/$ne/$nin` 的索引利用各有一节：`$ne` 永远全扫；`$in` 多值可能退化为多段扫。
- 数组 → **多键索引（multikey）**：一元素一键；含数组键的查询**不能覆盖（covered）**，必须回表。内嵌文档按点号路径索引；"数组里内嵌文档"存在跨元素误配陷阱，解药是 `$elemMatch`。
- **基数（cardinality）**决定选择性；`explain` 字段（`indexOnly/cursor/multiKey/nscanned/nreturned`）是调优仪表盘；`hint()` 强制索引做对照实验。
- 何时不建索引：小集合、写多读少、索引比查询更密、大数组多键爆炸——作者列了反例量化。
- 索引管理：`ensureIndex`（幂等，后并入 `createIndex`）、命名、`dropIndex(s)`、修改 = 重建（当时无原地改）。

### 2. 特殊集合与索引类型（第 6 章）

- **固定集合（capped）**：定容环形文件 + 插入序自然排序 + 循环游标；**oplog 的实现**；书中用例：日志表、最新 N 条、廉价事件流。
- **TTL 索引**：单键日期、清理线程约每 60s 一轮、删除不即时；书时代尚不支持分片集合（后补全）。
- **全文索引（2.4 新特性）**：`$text/$meta textScore`、权重、停用词、多语言——功能孱弱但意义深远（Atlas Search 的前世）。
- **地理**：2d 平面索引 + `$near/$within/$geoWithin/$geoIntersect` 过渡期语法；书中同时演示了刚露面的球面思路。
- **GridFS**：驱动规范，文件切 chunk（默认数百 KB）存 `fs.chunks` + 元数据 `fs.files`；"用两集合模拟流式对象存储"，跨驱动互通是其精髓。

### 3. explain 读法（5.2 的仪表盘，两代刻度对照）

| 书世代字段（2013） | 含义 | 现代 explain（4.x+，⚠️ 未实测） |
|---|---|---|
| `cursor: BtreeCursor x_1` | 用了哪个索引 | `winningPlan.inputStage.indexName` |
| `indexOnly: true` | 覆盖查询不回表 | `stage: PROJECTION_COVERED` / FETCH 缺席 |
| `nscanned` vs `nreturned` | 扫了多少/返回多少（比值≈选择性） | `executionStats.keysExamined/docsExamined/returned` |
| `nscannedObjects` | 回表摸过的文档数 | `docsExamined` |
| `multiKey: true` | 数组索引警告位 | `MULTIPLIER`/IXSCAN notes |
| `isMultiKey` + 无索引时全扫 | COLLSCAN 定性 | `stage: COLLSCAN` |

读法纪律未变：**keysExamined≈returned 是好计划；docsExamined≫returned 说明回表浪费；COLLSCAN+SORT 是最贵的组合**。

### 4. 索引选型决策流（把 5.3 的判断写成流程）

1. 有没有查询能变成"等值前缀 + 范围后缀"？有 → 复合索引，字段序按**等值优先、选择性次之、排序键收尾**（ESR 规则是书内容的现代命名 ⚠️）。
2. 查询命中比例 > 20–30%？→ 索引可能不如全扫（书中量化告诫）；写多读少的集合索引每加一个都是复利税。
3. 只要索引里的字段？→ 争取覆盖（避开数组/多键即可）。
4. 字段是 ad-hoc 动态的？→ 书答"稀疏索引救急"，2026 答 **wildcard 索引**（6.0+/6.2 GA ⚠️）。
5. 都不满足还慢？→ 改查询或改 schema（回到 05 文件），别硬 hint。

### 5. 特殊集合的"物种存续表"

| 2013 物种 | 2026 存续状态 |
|---|---|
| capped 集合 | **活得好**：仍是 oplog 实现，也是轻量事件缓冲的正当选择 |
| TTL 索引 | 活 + 扩展：分片可用、时序集合内建生命周期 |
| `$text` 全文 | 苟延：服务器保留，心智份额尽失于 Atlas Search ✅ |
| 2d 平面索引 | 标本：2dsphere + GeoJSON 全胜 |
| GridFS | 规范长青、场景退位：大文件默认走对象存储 |
| `group` 命令（7.4）| 灭绝（见 04 文件） |

## 常见误区（书中显式纠正的）

1. "索引越多查询越快"——写放大 + 规划器选择摇摆；"未用索引的查询比慢查询更该优化"。
2. "TTL 保证精确过期时刻"——只保证"尽力尽快"。
3. "唯一索引自动稀疏"——反了，唯一 + 稀疏的组合语义要显式设计。
4. "dropDups 放心用"——建唯一索引遇冲突会**删旧数据**的选项（后被移除），书中已警告。
5. "复合索引能救任意排序"——排序键必须是索引前缀且方向匹配（或整体反向），否则照样内存排序。
6. "给数组建索引就能覆盖查询"——多键索引禁止覆盖（必须回表确认元素归属），5.1.3 的硬规则。

## 2013 基线 → 2026 现状对位勘误

| 本书说法（2013） | 2026 现状 | 依据 |
|---|---|---|
| 建索引阻塞写/`background:true` 慢 | 4.2+ **混合（hybrid）构建默认化**，副本集自动级联构建 | ⚠️（机制为官方长期事实） |
| 全文索引 `$text` 是文本方案 | 服务器 `$text` 保留但被 **Atlas Search（Lucene 内核）/ `$search`** 实质取代 | ✅ https://www.mongodb.com/docs/manual/core/indexes/ |
| 2d 平面索引为主 | **2dsphere + GeoJSON** 为地理标准，2d 属遗留 | ⚠️ |
| TTL 不支持分片 | 已支持；配合 **clustered collections（6.0 GA）** 与原生时序集合做日志生命周期 | ✅ https://www.mongodb.com/docs/manual/core/clustered-collections/ |
| 索引类型止于 B-tree 家族 | 新增：**wildcard 通配符索引**、**隐藏索引**、**向量索引（Atlas：HNSW/IVF）**、时序自动索引 | ✅ https://www.mongodb.com/docs/atlas/atlas-vector-search/vector-search-overview/ |
| GridFS 是大文件标准答案 | 规范仍在、驱动互通；工业实践多用对象存储 + Mongo 存元数据 | ⚠️ |
| `hint()` 是调试偏方 | `hint` 保留；新增查询级索引提示治理与 Atlas 自动索引建议 | ⚠️ |
| dropDups 可用 | 选项早已移除 | ⚠️ |
| 规划器简单（首选最特定索引） | 多计划竞争 + `$hint/planCache` 治理；explain 输出三层结构 | ⚠️ |

## 核心概念速览（中英对照）

- **复合索引** — Compound Index：多键 B-tree；前缀匹配 + 排序方向敏感。
- **多键索引** — Multikey Index：数组逐元素入树；禁覆盖回表代价。
- **索引基数** — Cardinality：键值密度决定选择性。
- **覆盖查询** — Covered Query：只扫索引不回表（`indexOnly`）。
- **explain** — 计划输出：现代为 `winningPlan/executionStats` 三层。
- **hint** — 强制索引：计划对照实验工具。
- **稀疏索引** — Sparse Index：跳过缺键文档；与唯一性组合有坑。
- **TTL 索引** — Time-To-Live：日期键后台过期删除（尽力而为）。
- **固定集合** — Capped Collection：定容环形、插入序自然排，oplog 之基。
- **全文索引** — Text Index（2.4）：分词 + 权重；2026 由 Atlas Search 接管。
- **2dsphere 索引** — 球面地理索引（GeoJSON）：取代 2d 平面。
- **GridFS** — 文件分块存储驱动规范：`fs.files + fs.chunks`。
- **通配符索引** — Wildcard Index（6.2+）：`field.$**` 动态子键自动入索引。⚠️
- **向量索引** — Vector Search Index（HNSW/IVF）：embedding 近邻检索的存储层。✅
- **混合索引构建** — Hybrid Index Build（4.2+）：不阻塞写的默认建索引方式。

## 最新演进与工业实践

- **API 形状（🔧 import 级）**：pymongo 4.18.2 的 `pymongo.TEXT/GEOSPHERE/HASHED` 常量、`Collection.create_index/list_indexes`、以及 Atlas Search 索引管理入口 `create_search_index` 均可导入——"索引"物种从 B-tree 家族扩张到文本/地理/向量全族的证据就写在客户端签名上；服务端行为 ⚠️ 未实测。
- **Atlas 自动索引建议/Performance Advisor** 把书 5.3 的手工判断产品化；自建集群仍靠 `db.currentOp()` + profiler（10 文件）+ `planCacheList` 组合拳。⚠️
- **2026 索引设计共识**（与本章逐条可直译）：查询模式先行、低基数前缀警惕、wildcard 兜 ad-hoc 动态 schema、TTL × 时序集合管日志生命周期、向量字段与元数据 `filter` 合建。
- **工具链换代**：Compass 索引可视化、`mongosh` 的 `getIndexes()` 输出结构化；书中 `vme/vmes`（MMapv1 内存映射指标）在 `mongostat` 输出里已成历史——WT 时代看 `wiredTiger.cache.*`（12 文件）。
- **通配符与模式漂移**：面对 embedding 时代"字段频繁增删"的文档，wildcard 索引 + 显式热键复合索引的"双层策略"是社区主流；对应书中"稀疏索引救 ad-hoc"的旧招。⚠️
