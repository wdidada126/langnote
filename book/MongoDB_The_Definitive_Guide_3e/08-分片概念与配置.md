## 精读笔记

### 1. 架构三角（第 13 章）

- **范围分片**：按片键值域切 chunk、散布到 shard；`config.chunks/ns` 是"真理账本"；书中时代配置服务器 = **三台独立 mongod 手工保持一致**（著名的 2.4 前之痛：靠一致读 + 运维纪律兜底）。
- **mongos**：无状态路由器——查询拆分/路由/聚合散收（scatter-gather vs targeted）、chunk 拆分与迁移协调都经它但状态在 config。
- 快速建集群实验：`sh.enable("db")` + `sh.shardCollection("db.coll", {_id: 1})`——作者立刻声明"用 `_id` 是玩具演示，片键是第 15 章的事"。

### 2. 何时分片（14.1 的清醒）

动机排序（2013）：① **工作集超出单机内存**（MMapv1 页缓存世界观下的硬墙）② 写吞吐超过单主能力 ③ 数据规模超过单机磁盘——高可用**不是**分片的理由（那是副本集的活）。结论："先副本集、先纵向扩、先 schema 瘦身，最后才分片"，并直言运维复杂度陡增。

### 3. 块与均衡器（14.3–14.4）

- chunk 大小上限（书时代默认数十 MB；4.4 起 128MB）；**split 触发时机**（迁移前后按需）与"块太小→迁移风暴、块太大→均衡迟钝"的两难。
- 迁移协议：目标复制块 → 增量追写 → **config 原子改 owner** → 源端清理；期间双读保护。
- balancer：按"各 shard 块数差"轮巡搬砖——范围分片按块不按字节，故倾斜片键会让均衡器失灵（15 章的因果）。
- 运维旋钮：均衡窗口（业务低谷）、`balancerStop/Start`、维护模式；"jumbo 块"（超阈值无法迁移）的雏形警告。
- 增加容量：加 shard、改副本集为分片（书时代常见"先单机后补票"，2026 路径不同——对位表）。

### 4. chunk 迁移全程解剖（14.3–14.4 的机制推演，⚠️ 官方文档转述、未实测）

以一次 `[user_id: 300)` 块的搬家为例，协议分幕回放：

1. **选块**：balancer 在过载 shard 上挑 chunk；目标 shard 按"该范围块数最少"选取。
2. **拷贝写**：目标端对源端发起 clone 查询，把范围内文档全量写上目标；目标必须已有同序片键索引，缺则迁移直接失败——书世代常见事故。
3. **追增量**：拷贝期间的新写被记录在迁移缓冲里，目标端逐笔追平（书时代为 config 侧 staging 集合）。
4. **原子换主**：计数校验一致后，mongos 取 `config.collections` 上的集合级锁，把 `config.chunks` 该 range 的 owner 一笔翻向目标——**config 的这一次更新是全迁移唯一的路由权交接时刻**。
5. **双读保护**：提交前后，该 range 的请求按 config 版本被两端拒绝或转发到新 owner；仍落在源端的迟到写交给孤儿文档清理兜底。
6. **清理**：源端删除已搬走范围；孤儿收集器（orphan collector）此后周期运行于各 shard。

   推论：迁移本质是"元数据交易"，数据只是货物——所以"片键选错=全书重做"（09 文件），也是 jumbo 块与热 range 对集群杀伤力如此大的根源。

### 5. balancer 一轮的决策机制（14.4）

- balancer 是**单实例守护**：任意 mongos 都可起轮，但 `config.locks` 中 `{"_id": "balancer"}` 文档的 CAS 锁保证全局只有一轮在跑——2.4 时代配置服务器"原子更新"能力的第二种妙用。
- 每轮：统计各 shard 块数 → 最大最小差超阈值（书时代默认为个位数块，⚠️ 现代阈值动态化）→ 挑一块（必要时先 split）搬走。
- **搬家速率自适应**：书中已讲"业务高峰搬得少"；现代版是自动迁移节流 + 均衡窗口（⚠️ 转述）。
- 按块不按字节均衡：大块小块同权——"shard 磁盘倾斜但 sh.status 太平"与"块数均衡但数据倾斜"两种假信号的机制根源。

### 6. 2.4 的三台配置服务器：为什么叫"手工保持一致"

- 三台 config mongod 各自独立运行，mongos 把同一笔元数据更新**逐一写满三台**（等全部确认）——没有多数派提交流程，任一节点悄悄掉写即成"两本账"。
- 不一致没有自动修复：书时代靠人工比对/纠正，运维手册是"起第四台临时实例、dump config 库、逐行 diff"（转述 ⚠️）。
- 这正是 3.4 推荐、4.4 强制 CSRS 的直接动因：账本变成副本集 + 多数派提交，"两本账"被机制性根除（对位表）。
- 阅读收获：第 13–14 章里"三台机器"的表象不是分布式，而是**裸复制+纪律**；对照 06 文件选举机制，能体会共识协议难在哪。

### 7. mongos 的元数据缓存与路由"撞墙"

- mongos 本地缓存 chunk 范围，用 config 中的 `version` 号对账；撞到"文档不在预期 shard"即触发缓存刷新——迁移期查询变慢变散的一个机制注脚（转述 ⚠️）。
- minKey/maxKey 哨兵（01 文件类型表）在此兑现：range chunk 的上下界就是 ±maxKey；单调递增片键的最右"无界块"就是那堵墙——09 文件热点问题的几何表达。

### 8. 分片/副本集/纵向扩容分工表（14.1 论证压缩）

| 需求 | 正解工具 | 错误用法 |
|---|---|---|
| 工作集装不进单机内存 | 分片（水平切） | 加副本——内存不会变大 |
| 主节点故障自动切换 | 副本集 | 加分片——每个 shard 仍单点 |
| 读扩展 | 副本集读分散 | 分片——scatter 更慢 |
| 写吞吐 | 对高写集合分片（以好片键为前提） | 加副本——写仍只走主 |
| 运维复杂度预算 | 先纵向扩+schema 瘦身，最后分片 | 过早分片=复杂度×3 起步 |

## 常见误区

1. "分片 = 免费高可用"——错；分片解决容量/吞吐，HA 靠副本集。
2. "mongos 有状态"——挂了重启即可；路由智能全在 config 账本。
3. "配置服务器只是缓存"——**它是元数据唯一真相**，丢了 = 集群地图焚毁（书时代尤甚，2.4 三件套手工同步的惊险由此而来）。
4. "均衡器会救烂片键"——不会，只会救分布、救不了热块。
5. "迁移是原子的所以读写无感"——提交瞬间该 range 经 config 锁短暂拒写；大块迁移+高峰叠加就是书时代"分片维护窗口"概念的来源（机制推演 ⚠️）。
6. "出故障时 balancer 会自动停"——计划内运维要主动设均衡窗口/`balancerStop`；官方均衡器文档同样强调迁移纪律（转述 ⚠️）。

## 2013 基线 → 2026 现状对位勘误

| 本书说法（2013） | 2026 现状 | 依据 |
|---|---|---|
| 三台独立配置服务器 + 手工一致 | **CSRS 强制**（4.4 起；3.4 已推荐）：配置服务器自身是副本集，自动容错 | ⚠️（官方迁移文档通识） |
| chunk 默认 64MB 级 | 默认 **128MB**（4.4+）；6.0.3+/7.x 分裂阈值动态化、8.x 自动裂合并（ranged 集合） | ⚠️ |
| 只有 range 一种分片策略 | 三种并存：**range / hashed（2.4 末年出现于书附录级新特性，本书尚未展开）/ ranged sharded collections（7.0 GA，按负载自适应）**；zone sharding 管数据亲和 | ⚠️ |
| 单机 shard 起步、后转副本集 | 4.4 后 standalone shard 无从升级——**分片必须从副本集开始** | ⚠️ |
| 无跨片事务 | **4.2 起分布式 ACID 事务**（有延迟成本） | ✅ https://www.mongodb.com/docs/manual/core/transactions/（实抓） |
| 按库启用分片 | 6.0 起 **per-collection enableSharding**（per-db 移除） | ✅ https://www.mongodb.com/docs/manual/release-notes/6.0/（实抓） |
| 时间序列日志手工按天分集合 | 原生**时序集合**（bucketed + 自动时间分片）内置"时间片键最佳实践" | ✅ https://www.mongodb.com/docs/manual/core/clustered-collections/（实抓） |
| mongos 连接数大坑 | 驱动统一池化 + mongos 侧治理改进，但"连接放大"账要照算 | ⚠️ |

## 核心概念速览（中英对照）

- **分片（集群）** — Sharding / Cluster：按片键水平切集合到多存储节点。
- **片键** — Shard Key：文档落点依据（详见 09 文件）。
- **chunk** — 块：范围分片最小迁移单位。
- **配置服务器** — Config Servers（CSRS）：集群元数据唯一真相的副本集。
- **mongos** — 查询路由器：无状态路由/散收/迁移协调进程。
- **scatter-gather / targeted** — 全扇出 vs 定向路由：片键谓词决定形态。
- **均衡器** — Balancer：按块数轮巡搬砖的后台守护。
- **均衡窗口** — Balancer Window：只在低谷期迁移的配置。
- **块迁移** — Chunk Migration：复制→追增量→原子换主→清理。
- **jumbo chunk** — 特大块：超阈值拒迁的死角（16 章详）。
- **zone sharding** — 区域分片：书后时代"数据亲和"官方化。
- **ranged sharded collections** — 负载自适应分片（7.0）：range/hash 之外的第三形态。⚠️
- **orphan documents** — 孤儿文档：迁移/删除遗留的错位副本，orphan collector 的清理对象。
- **config.chunks 账本** — 集群路由唯一真相表：owner 字段翻转即路由权交接。
- **预分片（pre-splitting）** — 建集合时先切好边界块：避免开局"最后一块独大"的迁移风暴。

## 最新演进与工业实践

- **最小可信部署（2026）**：`mongod --configsvr --replSet`（CSRS）+ 副本集 shard + mongos——书中"三台 config 手工对齐"的章节整体替换为一次 `rs.initiate`。⚠️
- **Atlas 把"分片"变成选项**：M10+ 层自动均衡/推荐预分片/托管 mongos——本章手工知识转为"理解平台在做什么"。
- **按负载分片的新范式**：ranged collections 弱化预分片手艺（splitAt 时代渐远），但"片键决定路由"第一性原理不变（09 文件）。⚠️
- **可观测面**：`config.changelog/chunks` 直查、`sh.iostat`? 保守——现代入口 = `db.coll.getShardDistribution()` + sh.status + 平台面板；书里 `printShardingStatus` 的字段含义大多原样可读。
- **替代生态的"无分片假象"**：DocumentDB 以分片集群兼容 API 自居、FerretDB 用 PG 分区表承接——本书架构三角仍是读懂它们设计取舍的母语。✅ https://aws.amazon.com/documentdb/ 、https://docs.ferretdb.io/（实抓）
- **官方分片入口三页可直查**（2026-09 curl 200 复核）：片键概念 https://www.mongodb.com/docs/manual/core/sharding-shard-key/ 、决策教程 https://www.mongodb.com/docs/manual/tutorial/choose-a-shard-key/ 、均衡器与管理 https://www.mongodb.com/docs/manual/core/sharding-balancer-administration/ ——读 13–14 章时逐段对读，书中 chunk 尺寸/窗口话题在第三页有现代数值。
- **迁移协议仍可调试**：现代集群的 chunk 迁移仍分 clone/追增量/commit/清理四幕，`config.changelog` 逐事件留痕——本书模型至今有解释力（机制转述 ⚠️ 未实测）。
