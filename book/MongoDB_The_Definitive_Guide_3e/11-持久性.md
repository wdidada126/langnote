- 明确本章哪些内容只剩原理史价值（--nojournal、换文件、commitIntervalMs），哪些概念至今是面试与事故复盘主语（组提交、撕裂写、复制≠落盘）。

## 精读笔记

### 1. MMapv1 的持久性模型（本章的前提，已被整体替换）

书中机制：数据文件 = **内存映射文件**，写 = 改内存视图，靠 **journal（日记）** 提供 durability：

- 默认**每 100ms** 批量把日记写盘（组提交），`commitIntervalMs` 可调；`fsync` 命令控制数据文件刷盘节奏（默认 60s）。
- 崩溃恢复 = 重放 journal 到数据文件；`mongod.lock` 判定脏关闭；`--journal / --nojournal` 开关。
- 19.3 的诚实清单："**单文档写不保证原子性跨越日记组**"——断电瞬间可能撕裂文档，恢复靠 journal 重放；副本集读 SECONDARY 时"已复制 ≠ 已持久化"（这直接引出 11/12 章 writeConcern 与 `j:true`）。
- 19.4 数据损坏检验：`db.runCommand({validate: ...})`、`--repair`（会丢"修不回来"的文档，书中语气相当后怕）。

### 2. 为什么这一章值得单独精读

它是本书与 2026 现实**落差最大**的一章：整套"关日记提速、控制 fsync、手工换文件"的技艺，建立在"MMapv1 + 全局写锁 + 裸金属/RAID 运维"之上。作者自己也在章末预告了 WiredTiger（压缩、文档级并发、checkpoint + journal 的新模型）——2013 年它是展望，2015 年后它是唯一现实。

### 3. 一次断电的完整剧本（书中 19.1–19.2 的机制推演）

设默认配置（日记 100ms 组提交、数据 60s fsync）：

1. t0：客户端写经确认返回——**`w:1` 只保证进了内存视图 + 日记缓冲**，不等于任何文件落盘。
2. t0+50ms 断电：日记里最后不足 100ms 的组丢失；数据文件落后日记最多 60s。
3. 重启：`mongod.lock` 标记脏关闭 → 重放 journal 把数据文件追到最后一个完整日记组 → 未落日记的写**无声蒸发**。
4. 若 `j:true`（书中 `getLastError {j:true}`）：第 1 步就要等日记 fsync——断电剧本第 3 幕消失，代价是每次写一跳磁盘。
5. 若关了日记（`--nojournal`，书中"提速戏法"）：第 3 幕升级为**数据文件撕裂**，只能 validate+repair 或从备份重来。

这幅剧本的每个名词都退役了，但**结构一字不差地适用于 WT**：checkpoint（60s 级）↔ 数据落盘、WT journal（约 100ms 组提交）↔ 日记、`j:true` 语义原样保留——只有 `--nojournal` 这个选项本身死了。读 19 章的正确方式就是做这种"名词替换后 still-valid?"的练习。

### 4. 持久性风险预算表（书中隐含、2026 显式化）

| 档位 | 表达 | 断电丢失窗口 | 场景 |
|---|---|---|---|
| 裸奔 | `w:1`（旧 safe=False） | 日记组间隔级（~100ms） | 日志/埋点，可再生数据 |
| 单点持久 | `w:1, j:true` | 单机磁盘故障仍丢全部 | 低配单实例（不该存在于生产） |
| 多数派 | `w:majority`（无 j） | 副本内存态被同时断电则丢 | 多数在线业务实际档位 |
| 多数派+持久 | `w:majority, j:true` | 理论最小 | 账务/凭证 |
| 快照读加持 | + readConcern majority / snapshot | —（读侧防脏） | 与事务配套（02/07 文件） |

书中只能给到前三行的方言（getLastError 世界），后两行是 4.x 时代的完整拼图为本书补课重点 ⚠️（各档位实测延迟未做）。

### 5. journal、oplog、checkpoint：三本账的辨析（书中未命名、事故复盘天天用）

- **journal（WT 日志）**：本机持久化账——记录"哪些页改动还没进 checkpoint"；崩溃恢复只重放它（第 3 节剧本的 WT 版）。范围：单个 mongod 磁盘。
- **checkpoint**：数据文件的推进水位——"到哪一刻的状态是自洽的"；60s 级周期（书时代 fsync 的现代化身）。范围：单个实例的文件。
- **oplog**：跨机器复制账——"其他成员要应用什么"（06 文件解剖）；它不保证任何一台已落盘，落盘与否归 journal/checkpoint 管。范围：副本集。
- 三账对齐才有 durable：`j:true` 管第一本、`w:majority` 管第三本的多数派、第二本决定还原起点。**"复制了≠落盘了、落盘了≠多数派认了"**——两句话是 19.5 的全部现代意义。
- 备份侧呼应：mongorestore `--oplogReplay` 用第三本账把"checkpoint 时刻"追到"备份时刻"（13 文件捕获-重放推演）——三本账在备份链上各司其职的图景一到位，本章与 22 章就连成一门课。⚠️（机制为文档转述）

## 2013 基线 → 2026 现状对位勘误

| 本书说法（2013，MMapv1） | 2026 现状（WiredTiger 独存） | 依据 |
|---|---|---|
| 每 100ms 日记组提交 + 60s fsync | WT 默认 **60s checkpoint + 约 100ms journal 组提交**（数值同源但机制不同：B-tree 页快照 + 日志）；`--nojournal` 已无从谈起 | ⚠️ |
| `--journal/--nojournal`、`commitIntervalMs` 可调 | journal 常开不可关；书中那批日记调参选项整体退役 | ✅ https://www.mongodb.com/docs/manual/core/wiredtiger/（实抓）|
| 撕裂文档风险 + journal 重放恢复 | WT 以**快照隔离 + 记录级校验和**防御；崩溃恢复 = log 重放到 checkpoint | ⚠️ |
| 关闭日记提速（写吞吐翻倍戏法） | 无对应开关；提速改走 `w:1`/批量写/延迟 checkpoint 的**受控风险预算**讨论 | ⚠️ |
| `validate`/`--repair` 日常化 | `validate` 仍在（语法有演进，含 `full` 深度校验）；`--repair` 对 WT 能力受限，官方更推荐**重初始同步/备份还原** | ⚠️ |
| 数据文件/命名空间手工替换 | WT 单目录文件族（`WiredTiger.turtle` 等），"换文件"手艺作废 | ⚠️ |
| 副本集持久性 = 复制 ≠ 落盘 | 语义未变但表达升级：`w:majority + j:true` + readConcern majority；**change streams/事务快照读**建立在其上 | ✅ 事务页实抓 |
| MMapv1 是默认且几乎唯一 | **MMapv1 已于 6.0 移除**（4.2 起弃用）；引擎话题重心转向 WT 调参（cache 50%规则）与 In-memory 引擎（企业版） | ✅ https://www.mongodb.com/docs/manual/release-notes/6.0/（实抓）|

## 常见误区（书中语境 + 本目录补注）

1. "写返回成功 = 已落盘"——默认连日记都不等（19.3 的头号诚实清单）。
2. "journal 开着就零丢失"——只保证恢复到上一个日记组，**组间隔内的写在单机视角仍可丢**。
3. "fsync 越勤越安全"——每写一 fsync 的代价是把随机 IOPS 瓶颈放大到所有写路径（书时代实测话术 ⚠️ 未复现）；现代等价讨论是 checkpoint 周期与 WT journal 的 IOPS 预算。
4. "副本集开了就持久"——复制 ≠ 落盘 ≠ 多数派确认，三者独立（19.5 → 07 文件 writeConcern 谱系）。
5. "--repair 能救回损坏数据"——书中语气已后怕：repair 会**丢弃修不回来的文档**；2026 正解是备份还原/重初始同步。
6. "关闭日记提速是免费午餐"——风险从"丢一个日记组"升级为"文件撕裂整库伤"。
7. "checkpoint 周期越长越省磁盘"——省的是写放大，欠的是恢复重放时长与 WT journal 空间占用；11 文件与 12 文件的脏页水位是同一枚硬币两面（权衡转述 ⚠️）。

## 核心概念速览（中英对照）

- **日记系统** — Journaling：先写顺序日志再刷数据的 durability 基座。
- **组提交** — Group Commit：多写合并一次 fsync（书中 100ms 批量）。
- **checkpoint** — WT 周期把脏页快照落盘的水位推进（书后时代核心词）。
- **fsync** — 刷盘命令/选项：书中控制数据文件持久化节奏。
- **mongod.lock** — 脏关闭标记文件：恢复流程的裁判。
- **撕裂写** — Torn Write：断电瞬间文档半更新态，journal 重放修复。
- **validate** — 一致性校验命令：发现损坏的第一现场。
- **--repair** — 修复模式：MMapv1 时代常用，WT 时代降级为应急。
- **快照隔离** — Snapshot Isolation：WT 读侧隔离级别（书基线无此层）。
- **cacheSizeGB** — WT 缓存配额：保守记"约一半可用 RAM"（社区广泛流传 (RAM−1GB)×50% 公式 ⚠️ 未核官方原页）：现代持久性调优主旋钮。⚠️
- **多数派写 + j:true** — 跨副本持久化的现代正解：替代书中 `getLastError {j:true}` 方言。
- **恢复水位** — Recovery Point：checkpoint + 日志重放终点=崩溃后数据库的"现在"；RPO 的引擎侧对应物。⚠️

## 最新演进与工业实践

- **阅读策略**：本章按"数据库恢复原理史"读，不按操作手册读——概念（WAL、组提交、脏关闭）仍考试/面试高频，命令全数退役。
- **WT 运维共识**：缓存（`storage.wiredTiger.engineConfig.cacheSizeGB`）≈ 物理内存一半；磁盘 IOPS 预算给 journal；`compact` 仍用于空间回收但语义变轻。⚠️ 未实测
- **持久性产品化**：Atlas PITR、Ops Manager 块级备份（22 章/13 文件）把"备份 = 复制文件 + 重放 oplog"的书中手工方案整体吸收。
- **引擎谱系收尾**：本书预告的 WiredTiger 于 3.0 落地、3.2 定默认、4.2 弃 MMapv1、6.0 删；Labs 的 RocksDB/内存引擎亦已淡出——"存储引擎可插拔"叙事让位于"WT 深耕"。✅（3.0/6.0 里程碑见已核验 release notes/WT 文档页）
- **本书时代的"关日记提速"在 2026 的合法后裔**：`w:1` 批写 + `ordered:false` + 更大 checkpoint 预算——风险表述从"关日志"改为"显式声明可容忍丢失窗口"，事故复盘语言已统一（13 文件 PITR 是另一半答案）。⚠️
- **校验的现代化**：`validate` 之外，WT 块级校验和 + `--repair` 能力收缩，使"损坏 = 还原备份/重新初始同步"成为标准 runbook 首选项——书中 19.4 的抢救文学整体让位于 13 文件的备份工程。⚠️
