> 书目：《MongoDB: The Definitive Guide, 3rd Edition》（Kristina Chodorow, O'Reilly, 2013）。精读重构笔记，非原书文本；取证见 [00-总览与阅读地图.md](00-总览与阅读地图.md)。

## 精读笔记

### 1. 架构与建立（9.1–9.4）

- 副本集 = **自动故障转移的多副本组**：写落主、异步复制到成员、oplog（特殊 capped 集合）承载"幂等操作"而非数据页——成员可任意顺序应用、可断连重追。
- 书中明确**禁用链式复制**（所有成员从 primary 拉取）——2026 年这一定律被 5.0 部分推翻（见对位表）。
- `rs.initiate()` 流程与 `local.me` 时代hack；改配置 = 取 config → 改 → `rs.reconfig()`（版本号 + 多数派落盘的仪式，`force` 是"失去多数派时的赌注"）。
- 网络注意事项：内部心跳端口 + 数据端口（书中时代 27017/27019 双端口，后统一为单端口增量协议——对位表）。

### 2. 成员角色工具箱（9.5–9.6）

- 设计副本集：奇数票、跨机架/机房感知、**"多数派 = 能在你预期的最坏故障下活下来"**。
- 仲裁者（arbiter）：只投票不存数据——作者警告"它会让你的票池变小却不一定更安全"。
- 优先级（priority）：指定"谁是钦定主"；隐藏成员（hidden）：对默认读路由不可见，专用于差异化索引/后台任务（9.6.5 节：给隐藏节点建不同索引喂分析）。
- 延迟节点（slaveDelay，现 secondaryDelaySecs）：故意滞后 30 分钟起步的"时间机器"，防误删/勒索软件的第一道自留地。

### 3. 机制四件套（第 10 章）

- **初始同步**：clone 全量 + 追 oplog；书中警告大集合初始同步打爆网络/磁盘（MMapv1 还要在同步末端重建索引）。"处理陈旧数据"= 同步期间数据变化的追赶逻辑。
- **心跳**：每 2s ping、10s 判死（书时代数字）；拖慢检测与"心跳失败≠死亡"的灰区。
- **选举**：自研多数派协议（Raft 论文同年才发布，⚠️ 按公开史料）：任期 term、投票资格、`rs.stepDown()/rs.freeze()` 人工干预；2.0 后"网络恢复自动降级"专节治双主恐惧。
- **回滚**：旧主复活发现部分写未被多数派接受 → 移入 `rollback/` 目录；作者定性：回滚是容量/网络问题的症状，应当避免其发生。

### 4. oplog 记录解剖（10 章机制的最小标本）

一条 oplog entry ≈ `{ts: Timestamp(秒.序号), t: 操作类型, ns: "库.集合", o: 操作对象, o2: {_id:...}(更新定位), wall, v}`。三个设计后果书中反复利用：

1. **幂等**：更新记"设置成什么"而非"加了什么"（`{$set:{x:5}}` 重放百遍同果）→ 任意成员可按序自回放、可断点续传（change streams 的 resume token 就是 `ts` 的包装 ✅ changeStreams 页）。
2. **createOnly 型操作例外**：insert 重放撞 `_id` 会被忽略——语义上"存在即已应用"。
3. **capped + 时间序**：oplog 是固定容量环形文件，写满覆盖最老历史 → "窗口外只能全量初始同步"的容量因果链（12.4.6 与 07 文件）。

### 5. 选举走一遍（10.3 的剧本化复述，⚠️ 时序数值按书世代）

1. 心跳超时（约 10s 未收到主心跳）→ 自视 SECONDARY 转 `try for primary?` 状态：先查自己**是否有资格**（非仲裁、数据不太旧、未 freeze）。
2. 自增 term（任期），向所有投票成员拉票：候选者只有 `oplog 尾 ts` **不早于投票者**才能拿到票（安全性：不丢已确认写）。
3. 拿到多数票立即升主，旧主收到更高 term 的任一信号即自降——"双主窗口"被 term 单调性封死（2.0 后自动降级一节的世界观）。
4. 未过半数（如 3 票池断网成 1+2）→ 少数侧无主可读，**可用性让位于一致性**：这正是书中"多数派=最坏故障假设"设计公式的用武之地。

### 6. 成员状态机速览（书中术语 → 今名，多原样存活 ⚠️）

STARTUP / STARTUP2（初始同步中）/ RECOVERING（追分、追 oplog）/ **SECONDARY** / **PRIMARY** / ARBITER / DOWN / FAILED / UNKNOWN / ROLLBACK——`rs.conf()/rs.status()` 输出至今是这套词；12.1"单机模式启动"= 借 RECOVERING 之外的后门直连抢救。

### 7. 成员配置字段速查（rs.conf() 视角，9.6 工具箱的字段化；⚠️ 默认值以官方 rs.conf 文档为准）

| 字段 | 语义 | 默认 | 组合禁忌/注记 |
|---|---|---|---|
| `priority` | 选举权重（0=永不选主） | 1 | 全员 0 = 无主集群（维护误操作经典款） |
| `votes` | 投票权（0/1） | 1 | 投票成员上限 7——票池要设计不要默认 |
| `arbiterOnly` | 只投票不存数据 | false | 与 priority:0 的隐藏从库比，多数场景后者更值（书中算过账） |
| `hidden` | 默认读路由不可见 | false | 官方要求搭配 priority:0 / votes:0 / 延迟之一（⚠️ 细则以 rs.conf 文档为准）；差异化索引的载体 |
| `slaveDelay`→`secondaryDelaySecs` | 故意滞后 | 无 | 延迟成员天然 hidden，显式 hidden:false 会被拒（⚠️ 转述）；恢复粒度=整成员（07 文件） |
| `buildIndexes` | 是否建索引 | true | 0=全禁但永远"落后"；书中建议配合 hidden 用 |
| `tags` | 机房/角色坐标 | 无 | 11.3 自定义写规则与 zone 读的公共底座（07 文件） |
| `_id/host` | 成员身份 | — | 改 host 要走 reconfig 仪式（版本号+多数派落盘） |

字段之外的两个"元字段"同样长青：`settings.getLastErrorModes`（本书特性，已移除——对位表）与 `protocolVersion`（v1 自 4.0：更规整的多数派提交，书基线无此概念 ⚠️）。

## 常见误区

1. "加机器就更安全"——票数是设计问题不是硬件问题（延迟/仲裁节点不算数据冗余）。
2. "仲裁者省成本"——作者算过：多数派所需成员数可能不降反升。
3. "副本集 = 备份方案"——同步的是错误传播；备份另说（13 文件）。
4. "回滚的数据能自动找回来"——要人工从 rollback 目录捞。
5. "oplog 越大越稳"——过大浪费磁盘与同步传输；正确姿势：**按峰值写入速率 × 可容忍离线时长**反推（07 文件给算法）。
6. "PRIMARY 挂了必然秒切"——选举 + 驱动重连叠加是十秒级；对延迟敏感业务要做重试预算（02/07 文件）。
7. "隐藏成员=安全"——hidden 只管读路由可见性，不管认证授权；把敏感数据寄托在"路由不到"上是 2013 式幻觉（现代答案见 12 文件安全六层）。
8. "初始同步可以赶在业务高峰前赌一把"——clone 阶段打爆带宽、index build 阶段打爆磁盘（书中两条警告）；500GB 级起步要么错峰要么预置数据文件（07 文件 12.1 的抢救通道）。⚠️

| 本书说法（2013） | 2026 现状 | 依据 |
|---|---|---|

## 核心概念速览（中英对照）

- **副本集** — Replica Set：自动故障转移的多副本组，多数派定生死。
- **oplog** — Operations Log：幂等操作日志（capped 集合），复制载体。
- **初始同步** — Initial Sync：全量拷贝 + oplog 追赶的入伙流程。
- **心跳** — Heartbeat：成员存活探测（书中 2s/10s，现代可调）。
- **任期** — Term：选举世代号，防旧主复活干扰。
- **仲裁者** — Arbiter：只投票不存数据的凑票成员。
- **延迟节点** — Delayed Member：故意滞后的时间机器备份。
- **隐藏成员** — Hidden Member：读路由不可见，做差异化索引/任务。
- **回滚** — Rollback：未被多数派接受的写移出 oplog 入 `rollback/`。
- **stepDown/freeze** — 让位/选举冻结：计划内切换工具。
- **脑裂防护** — Split-Brain Defense：多数派 + 自动降级（书中"2.0 自动恢复"叙事）。
- **链式复制** — Chaining：书时代禁用、5.0 复活——本目录最戏剧性的往返。
- **Change Streams** — 变更流（3.6+）：官方 oplog 消费接口。✅

## 最新演进与工业实践

- **概念没变，包装变了**：`rs.initiate/confReconfig`、成员选项、投票权重——今天的官方教程与本章几乎同构；变的是"配置服务器必须副本集"（4.4 强制 CSRS，见 08 文件）与多数派读成为默认（4.0+）。⚠️
- **运维自动化**：Atlas/Ops Manager 把 9.4"改配置的 reconfig 陷阱"变成按钮与校验；自建集群这些手艺仍是硬要求。
- **可观测**：`replSetGetStatus` 的 `optimeDate` 差 = 复制滞后；Prometheus/Cloud Monitoring 取代书里"肉眼算 oplog 窗口"。⚠️ 未实测
- **选举的现代语义补充**：驱动/服务端引入 **read concern majority + 因果一致性** 后，"读到旧主数据"类问题（本章 11.4 的前置知识）被系统性缓解（07 文件）。
- **替代生态**：DocumentDB 把"复制/选举"藏进不可见基础设施；FerretDB 用 PostgreSQL 流复制承接——本章模型仍是理解两者的钥匙。✅ https://aws.amazon.com/documentdb/ 、https://docs.ferretdb.io/（实抓）
- **容量算例（书 9.5 方法论示范）**：500GB 数据、峰值写入 5MB/s、希望故障成员能"追分"而非"全量重同步"（后者按 100MB/s 内网也要 83 分钟 + 索引重建）→ oplog 至少要 5MB/s × 数小时 ≈ 数十 GB 级；书中"宁可偏大"的结论在 SSD 时代成本已低，但"窗口 < 修复时长 = 必然全量同步"的算术永不朽。⚠️ 数值为方法演示非实测
- **选举的现代可观测**：`rs.stepDown(60)` 仍是发布窗口标准动作；新增点是 Atlas/Ops Manager 把"谁在何时为何让位"记成事件流——自建集群则靠 `replSetElect` 日志行与 heartbeat 状态迁移表，本章 10.3 的剧本仍是读懂这些日志的唯一钥匙。⚠️
- **成员上限的宽进严出**：书中"50 成员/7 投票"数量级的限制延续（投票池上限至今 7 ⚠️ 未核现行文档原句）——"多副本少投票 + tags 定权重"成为跨机房标准拓扑，恰是 9.6 角色工具箱的组合拳用法。
