# 第 04 讲 Primary-Backup Replication：VMware FT 与「输出规则」

> 官方标题：**Primary-Backup Replication**（LEC 4，主讲 rtm）
> 指定必读：**Fault-Tolerant Virtual Machines (2010)**

## 本章地图

本讲从 GFS 的「弱一致、应用级」跳到另一个极端：**强一致、机器级**的主从复制。
VMware FT 的做法是：把**整台虚拟机**当成一个确定性状态机来复制，
主备逐条事件同步，主挂了备立刻接上，且接上后**对外表现得像什么都没发生**。

主线：复制的两种范式（状态转移 vs 复制状态机）→ 复制的**层次**选择（应用级 vs 机器级）→
FT 的机制（日志通道 + 确定性重放）→ **输出规则（output rule）** →
失效检测与脑裂（共享磁盘 test-and-set）→ 代价与适用边界。

## 核心精讲

### 4.1 两种复制范式

| 范式 | 主做什么 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **状态转移（state transfer）** | 把主的全部状态（内存、磁盘）拷给备 | 概念简单 | 状态通常极大，传输成本高 |
| **复制状态机（replicated state machine, RSM）** | 只把「输入/操作」发给备，备从同一初态按同序执行 | 传输量小（通常） | 要求**确定性**：同输入同序必得同结果 |

FT 属于后者，且把「状态机」定义在了**机器指令/中断**这一层。

### 4.2 复制的层次：应用级 vs 机器级

| 层次 | 例子 | 传什么 | 代价 | 透明性 |
| --- | --- | --- | --- | --- |
| 应用级 | GFS 的主副本（L3）、Raft KV（Lab 3） | 高层操作（「在偏移 X 写 Y」） | 低——只传语义 | 应用必须自己设计 |
| 机器级 | **VMware FT** | 中断、DMA、磁盘读结果、时钟、随机数等所有非确定性输入 | 高——粒度极细 | 应用完全无感 |

机器级的好处是「不用改应用」，坏处是**所有非确定性都必须在机器层面被捕获并记录**。

### 4.3 FT 的机制

- 主 VM 与备 VM 运行在不同物理机上，共享存储（shared disk）；
- 主 VM 的所有**输入**经**日志通道（logging channel）**发给备，备在自己的 VM 上重放；
- 日志项包含：指令序号（instruction index）+ 事件类型 + 重放所需的数据；
- 备执行到「某个日志项已收到但下一步会发生非确定性事件」时必须**等待**（不能猜）；
- 主若日志通道写满则会**减速**（这是 FT 的性能代价来源）。

**必须被记录的非确定性事件**（这是本讲最容易考的点）：

1. 定时器/设备中断——必须在**同一条指令边界**上投递给备；
2. 读取真实时间（`RDTSC`、时钟）；
3. 随机数；
4. 多核共享内存的并发交错——**这也是论文当年把 FT 限制在单处理器 VM 的原因**：
   多核下的内存访问交错无法廉价记录与重放。

### 4.4 输出规则（output rule）——正确性的核心

> **规则：主 VM 不得把任何输出发到外部世界，直到备 VM 已经确认收到了「产生该输出」所对应的那条日志项。**

为什么必须有它？把两种做法对比一下：

```
情况 A（无输出规则）：
  主执行到某点 → 立刻回包给 client → 主崩溃
  备可能还没收到那条日志项 → 备接管后不会发出这个回包
  结果：client 曾看到回包，但接管后的系统认为没发过 → 外部可见的不一致

情况 B（有输出规则）：
  主执行到某点 → 先等备确认日志项 → 再回包 → 主崩溃
  备一定已经持有该日志项 → 备接管后要么已经发过、要么会发（重发）
  结果：client 至多看到「重复的输出」，不会出现「主说有、备说没有」
```

重复输出是可接受的：**输出不是状态**，TCP/网络层天然容忍重复包，应用也能靠幂等处理。
而「不一致的输出」是不可接受的。这就是「宁可重复、不可矛盾」的经典取舍。

代价是：**每次输出都要等一个日志往返**，所以 FT 会增加输出延迟。

### 4.5 失效检测与脑裂

- 主备之间 **UDP 心跳** + 监控日志通道流量；
- 但「心跳没了」不等于「对方死了」——可能是网络分区。若两边都认为对方死了并同时接管，就是**脑裂（split brain）**，
  两台机器同时写共享磁盘会损坏数据；
- FT 的解法：主从切换前，先在**共享存储上执行一次原子 test-and-set**；
  谁拿到谁 go live，拿不到就停止（自己 halt）。**共享磁盘成了仲裁者**。

> 这是一个重要模式：**用外部可仲裁的原子操作打破对称**。后面 Raft 用「多数派」做同样的事，
> 但不需要共享磁盘——这也是共识算法相对 FT 的关键优势（不依赖单点共享存储）。

### 4.6 教学示意：输出规则的状态机

> **教学示意，不参与构建**——只表达「输出必须延迟到备确认」的控制流。

```go
// 教学示意，不参与构建
type FTPair struct {
    // 已发出的最大指令序号
    primaryIndex int
    // 备已确认收到的最大指令序号（ACK 水位）
    backupAckedIndex int
}

// 主 VM 想产生输出前必须调用；返回 false 表示「还不能输出，再等等」
func (p *FTPair) outputAllowed(atIndex int) bool {
    return atIndex <= p.backupAckedIndex
}

// 备上重放：只有当下一条非确定性事件的日志项已到达才能继续
func (p *FTPair) backupCanAdvance(toIndex int) bool {
    return toIndex <= p.primaryIndex // 日志项已收到
}
```

> 注意这里的顺序：**先推进日志 → 备 ACK → 才允许输出**。
> 反过来（先输出再补日志）就会掉进 4.4 的情况 A。这句话是本讲唯一必须背下来的东西。

## 版本演进

- **1980s–1990s**：主从复制是数据库高可用（HA）的标准形态（主备日志传送 / log shipping），
  但通常是「异步 + 可能丢数据」或「同步两阶段提交」。
- **2010（论文当年）**：VMware FT 首次在**商用虚拟机层**做到「应用无感、零数据丢失、秒级接管」，
  代价是单处理器限制与日志带宽。
- **2010s 后期**：虚拟化平台的 FT 支持逐步扩展到多 vCPU（具体版本与 vCPU 上限以各厂商官方发布说明为准，本目录不写未经核实的型号/数字）。
- **2020（本讲）**：课程把 FT 作为「**RSM 的极端形式**」与「**输出规则**」的范本；
  紧接着的 L6–L7 会用 Raft 做同样的正确性，但**不依赖共享存储、也不要求机器级确定性**。
- **2026**：机器级 FT 在生产里是**小众方案**（成本高、限制多）。
  主流做法是：
  - 应用级 RSM（Raft/Paxos）+ 无状态服务，把状态放到外部复制存储；
  - 云原生「实例可随时被替换」——用**快速重启 + 幂等**替代「零中断接管」；
  - **确定性重放**思想转移到**测试**领域（确定性仿真测试，见 [13-Labs总结与2026视角.md](13-Labs总结与2026视角.md)），
    而不是生产容错。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：
  - **确定性多线程（DMT）**：Dthreads（OSDI 2011）、DMP、Calvin 等，研究如何在多核下廉价地记录/约束并发交错——
    正是 FT 当年放弃的那条路；
  - **记录-重放用于调试与测试**：把 FT 的日志通道思想用于「复现线上偶发 bug」；
  - **确定性仿真测试**（FoundationDB 的模拟器、`madsim`、Antithesis 一类）：
    把整个系统（含时钟、网络、磁盘）变成确定性状态机，在仿真里暴力搜索调度——
    这是 FT 思想在 2020s 最有生命力的继承者。
- **工业界开源（star 数 2026-09-26 `gh api` 实测）**：
  - `rr-debugger/rr`（**10679★**）：用户态记录-重放调试器，把「确定性重放」做成日常工具。
  - `firecracker-microvm/firecracker`（**36964★**）：microVM；把虚拟化做成「轻量、快照友好」的沙箱，
    2026 的 Serverless/FaaS 常用它做快速启动与隔离（与 FT 的「快速接管」目标不同但技术同源）。
  - `checkpoint-restore/criu`（**4004★**）：进程级检查点/恢复——「状态转移」范式的现代工程实现。
  - `cloud-hypervisor/cloud-hypervisor`（**6262★**）：VMM 的现代开源实现，可对照阅读「机器级复制需要捕获哪些东西」。
  - `madsim-rs/madsim`（**1161★**）：Rust 的确定性仿真器（含模拟网络/时钟/磁盘），用于把分布式系统跑成可复现的测试。

> 说明：VMware FT 本身是闭源商业产品，没有对应开源仓库；本目录不给 star 臆测。

## 常见误区与本课程需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「备和主完全同步执行」 | 备**只在需要非确定性输入时才必须等**；它按自己的节奏消费日志，通常落后一点 |
| 2 | 「输出延迟是优化项，可以先输出再补日志」 | 违反输出规则会产生「client 见过、接管后不认」的外部不一致，是正确性 bug 不是性能问题 |
| 3 | 「重复输出也不行」 | 重复可接受（输出非状态，且网络层/应用可去重）；**矛盾**不可接受 |
| 4 | 「心跳没了就能接管」 | 必须先用共享存储的 **原子 test-and-set** 仲裁，否则脑裂 |
| 5 | 「FT 能容忍任意故障」 | 只处理 **fail-stop**（机器停机）；应用逻辑 bug、数据损坏会被忠实地复制到备机上 |
| 6 | 🔧 2020 课程未覆盖 | **多核限制的工程解法**：论文只支持单处理器；2026 的确定性多核（Dthreads/Calvin/确定性数据库）已给出若干路线，但仍是研究级取舍 |
| 7 | 🔧 2020 课程未覆盖 | **共享存储是单点**：FT 的仲裁者依赖共享磁盘；现代方案（Raft/Paxos）用多数派消除这个依赖，这是共识算法取代机器级 FT 的主要原因 |
| 8 | 🔧 2020 课程未覆盖 | **云原生不做 FT**：主流是「无状态 + 外部复制状态 + 快速重启」，用可用性指标（RTO/RPO）而非「零中断」来定义目标 |
| 9 | 🔧 2020 课程未覆盖 | **FT 的性能模型**：日志带宽在 I/O 密集负载下极高，且主会因日志通道满而减速；2026 应补充讨论「哪些负载适合 FT」（低 I/O、低变更率的控制面服务） |
