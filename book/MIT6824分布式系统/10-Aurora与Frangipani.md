# 第 10 讲 Aurora + 第 11 讲 Frangipani：共享存储上的「日志」与「缓存一致性」

> **L10 官方标题**：Cloud Replicated DB, Aurora（rtm）　必读：**Aurora (2017)**
> **L11 官方标题**：Cache Consistency: Frangipani（rtm）　必读：**Frangipani**
> 本目录把相邻的两讲合并在一个文件里，因为它们讲的是**同一枚硬币的两面**：
> 「计算层带着缓存，下面挂一层共享持久存储」时，怎么保证**崩溃后可恢复**、**缓存间一致**。

## 本章地图

```
L10 Aurora（2017，云数据库）
   核心断言：在云里，瓶颈已经从 CPU/磁盘 转移到了「网络」
   → 于是只跨网络传 redo log，把「由日志构造页面」下沉到存储层
   → 「the log is the database」

L11 Frangipani（1997，分布式文件系统）
   多个工作站共享一块虚拟磁盘（Petal），各自带 write-back 缓存
   → 缓存一致性：用「锁 + 租约」保证同一时刻只有一个写者
   → 崩溃恢复：用「每台机器自己的预写日志 + 锁接管」实现「别人替死掉的机器恢复」
```

两讲的共同结构：**共享持久层（Petal / Aurora 存储服务） + 带状态的计算层（缓存 / 页面缓存） + 日志**。

## 核心精讲（一）：Aurora

### 10.1 前提变了：云里瓶颈是网络

Aurora 论文的第一个论断很关键：传统数据库是为「CPU 与磁盘是瓶颈」设计的，
而在云环境中，**网络（含存储网络）成为瓶颈**。因此云数据库的优化目标变成：
**最大限度地减少跨网络传输的字节数**。

### 10.2 只传 redo log

传统主备复制要传：redo log + 数据页 + 双写（double-write）+ 检查点 + 后台写脏页……
Aurora 的做法是：

- 数据库引擎生成的还是正常的 redo log；
- **存储层负责把 redo log 异步地应用到页上**（materialization）；
- 于是网络上只跑 redo log 记录（以及必要的元数据与 gossip）；
- **不需要两阶段提交、不需要分布式文件系统、不需要存储层做检查点协调**。

论文的名言：**"the log is the database"**——日志是唯一需要被持久化和复制的东西，
页面只是日志的一个可以随时重算的物化视图。

直接收益（论文给出的方向性收益，具体数字以论文为准）：

- 网络 I/O 大幅下降（只传日志）；
- 崩溃恢复变快：恢复不需要「重放大量日志才能服务」，
  存储层可以在读页时按需应用日志（**恢复是持续的、懒的**）；
- 备份/快照变成连续行为。

### 10.3 复制与法定数：6 副本 / 3 AZ

| 参数 | 值 | 含义 |
| --- | --- | --- |
| 副本数 V | 6 | 数据库卷被切成 **10 GB 的段（segment）**，每个段组成一个 6 副本的保护组（protection group） |
| AZ 分布 | 3 AZ × 2 副本 | 跨可用区，抗 AZ 级故障 |
| **写法定数 Vw** | **4/6** | 满足 `Vw > V/2`（两写不冲突） |
| **读法定数 Vr** | **3/6** | 满足 `Vw + Vr > V`（读写必相交） |

由此得到的容错边界（这是本讲最容易算错的地方，务必按公式推）：

- **写可用性**：要凑够 4 个副本 → 允许 `6 - 4 = 2` 个缺失 → 可容忍**整个一个 AZ（2 副本）**失效仍能写；
- **读可用性**：要凑够 3 个副本 → 允许 `6 - 3 = 3` 个缺失 → 可容忍**整个 AZ + 1 个节点**失效仍能读。

> 这就是为什么论文说 Aurora 能容忍「AZ + 1」：
> 它指的是**读可用性**（以及 6 副本下的持久性），而不是「还能写」。
> 把「AZ+1」理解成「还能写」是常见误读。

**为什么是 10 GB 的段**：修复（re-replication）的粒度决定了恢复时间——
一个 10 GB 的段在 10 Gbps 网络上的修复时间在**十秒量级**，
比「整卷修复」或「整盘修复」要可控得多。段也自然成为负载均衡与故障隔离的单位。

### 10.4 教学示意：法定数是否满足安全性

> **教学示意，不参与构建**——把两条不等式写成可执行判断。

```go
// 教学示意，不参与构建
func quorumSafe(V, Vw, Vr int) (writeExclusive bool, readSeesLatest bool) {
    writeExclusive = Vw > V/2                    // 任意两个写集合必有交集 → 不会并发提交冲突写
    readSeesLatest = Vw+Vr > V                   // 任意读集合与写集合必有交集 → 读必能看到已提交写
    return
}

// Aurora: V=6, Vw=4, Vr=3
//   4 > 3     ✅
//   4+3 > 6   ✅
// 传统 3 副本: V=3, Vw=2, Vr=2 → 同样成立，但容错能力不同：
//   3 副本容忍 1 个节点失效；6 副本容忍 2（写）/ 3（读）
```

### 10.5 单写者假设与它的后果

2017 年的 Aurora 论文描述的是**单写者（single writer）**架构：一个主实例产生日志，
多个只读副本消费。这让很多问题（并发写冲突、分布式事务）被绕开了。
多写（multi-master）是后来的产品形态，且引入了额外的冲突处理机制
（**具体形态与支持范围以厂商官方发布说明为准，本目录不臆断**）。

## 核心精讲（二）：Frangipani

### 10.6 结构：Petal + Frangipani

- **Petal**：提供一块「大、稀疏、复制的虚拟磁盘」（块接口），对上层隐藏分布与故障；
- **Frangipani**：文件系统层，跑在每台工作站上，所有工作站看到同一个文件系统；
- Frangipani 本身**不是**分布式算法密集的系统——它把难题交给两个组件：**锁服务**和**预写日志**。

### 10.7 缓存一致性：锁 + 写回缓存

- 每台工作站**缓存**元数据与数据，并采用**写回（write-back）**策略；
- 缓存一致性由**锁**保证：要修改一个对象得先拿到写锁，拿到写锁意味着「别人不会同时改它」；
- 锁带**租约（lease）**：持锁者必须定期续租；若续租停止（崩溃或网络中断），
  锁服务等租约过期后才能把锁给别人（**租约是「崩溃检测」的手段**）；
- 锁冲突时：当前持锁者必须先把脏数据写回共享存储、再释放锁（类似 [02-RPC与线程.md](02-RPC与线程.md) 的「写回 + 失效」协议）；
- 锁采用**惰性释放**（一直持有直到别人要），减少锁流量；
- 死锁：通过**全局加锁顺序**（层次化加锁）避免，因此不需要死锁检测。

### 10.8 崩溃恢复：让别人替你恢复

这是 Frangipani 最漂亮的地方：

1. 每台工作站有自己的**预写日志（redo log）**，写在 Petal 上；
2. 日志在真正修改共享结构**之前**落盘；
3. 某台工作站崩溃 → 锁服务发现它的租约过期 → 把它的锁交给另一台工作站（恢复者）；
4. 恢复者**重放它的日志** → 文件系统结构恢复一致；
5. 关键点：**恢复不依赖死掉的那台机器做任何事**——它的状态（锁 + 日志）都在共享存储上。

> 这个设计的前提是「**持锁 + 有日志**」这两件事的耦合：
> 没有锁，别人不知道该重放谁的日志；没有日志，锁过期后脏缓存就丢了。
> 二者缺一不可——这也是它与 [11-分布式事务与两阶段提交.md](11-分布式事务与两阶段提交.md) 中「日志 + 锁」思路的呼应。

（论文细节：Frangipani 的日志记录的是**文件系统结构/元数据的更新**；
用户数据是否入日志及其崩溃语义，以论文原文表述为准，本目录不臆断。）

### 10.9 教学示意：租约与恢复的时序

> **教学示意，不参与构建**——只表达「租约过期后才能接管」这条硬规则。

```go
// 教学示意，不参与构建
type Lock struct {
    Owner    string
    Expiry   time.Time // 租约到期时刻
}

// 锁服务：只有租约过期（或主动释放）才能把锁交给别人
func grant(l Lock, now time.Time, requester string) bool {
    if l.Owner != "" && now.Before(l.Expiry) {
        return false // 原持有者的租约还有效 —— 绝不能给别人，否则两个写者
    }
    return true
}

// 恢复者拿到锁之后的动作顺序（顺序不能反）：
//   1. 读该工作站的日志（在共享存储上）
//   2. 重放日志，修复 FS 结构
//   3. 释放锁 / 清除日志
// —— 若在步骤 1 之前就开始提供文件服务，客户端会看到中间态
```

## 版本演进

- **1997**：Frangipani（SOSP 1997）+ Petal 提出「共享虚拟磁盘 + 缓存一致性 + 日志恢复」的完整方案。
- **2000s**：集群文件系统（GPFS、Lustre、OCFS2、GFS2）用**分布式锁管理器（DLM）**实现同样的目标；
  NFSv4 delegation / SMB oplock 是「租约」思想在标准协议里的落地。
- **2010s**：云数据库的存算分离成为主流。Aurora（SIGMOD 2017）把「日志下沉到存储」做到商用规模；
  同期还有 Microsoft Socrates（VLDB 2019）等「日志即数据库」路线的系统。
- **2020（本讲）**：课程把 Aurora 与 Frangipani 放在相邻两讲，
  意图是让学生看到「**共享存储 + 本地缓存 + 日志**」这个模式跨越 20 年仍然成立。
- **2026**：
  - Aurora 家族继续演化（Serverless、Global Database、以及面向扩展的分片形态等，
    **具体形态与支持范围以 AWS 官方发布说明为准**）；
  - 开源界出现同构系统：**Neon**（Postgres 的存算分离：Safekeeper 管 WAL 法定数，Pageserver 管物化页面），
    与 Aurora 的「日志即数据库 + 存储层物化」几乎同构；
  - 国产云数据库的共享存储路线（PolarDB 等）也是同一范式。
- **课程侧**：2026（6.5840）的 schedule 中**未见 Aurora 与 Frangipani 两讲**（以官方页为准，可能年度轮换），
  但存算分离已成为背景常识。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：
  - **日志即数据库**的推广：把 WAL 作为复制与恢复的唯一真相源，存储层按需物化；
  - **内存/非易失存储下的日志瓶颈**：FaRM（L14 必读，见 [13-Labs总结与2026视角.md](13-Labs总结与2026视角.md)）用 RDMA 把日志提交做到微秒级；
  - **可分支（branching）的存储**：把「日志 + 物化」的分层暴露给用户，实现数据库的时间旅行与分支（Neon 的 branch）；
  - **租约的正确性边界**：租约把「崩溃检测」变成**时间假设**，与 [12-Spanner与TrueTime.md](12-Spanner与TrueTime.md) 的时钟问题同源。
- **工业界开源（star 数 2026-09-26 `gh api` 实测）**：
  - `neondatabase/neon`（**23132★**）：Postgres 的存算分离实现——
    **Safekeeper（WAL 法定数）+ Pageserver（物化页面）**，与 Aurora 的架构几乎同构，且开源可读。
  - `polardb/PolarDB-for-PostgreSQL`（**3204★**）：共享存储路线的开源版本（产品线细节以厂商文档为准）。
  - `juicedata/juicefs`（**14471★**）：把「元数据引擎 + 对象存储」组合成 POSIX 文件系统的现代实现，
    可与 Frangipani 的「Petal + FS 层」结构对照。
  - `pingcap/tidb`（**40590★**）、`cockroachdb/cockroach`（**32508★**）：**共享无（shared-nothing）**路线的代表，
    与 Aurora 的**共享存储**路线形成两种范式对比。

## 常见误区与本课程需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Aurora 的 AZ+1 是写容错」 | 按公式推：写要 4 副本 → 只容忍 2 个缺失（**一个 AZ**）；读要 3 副本 → 容忍 3 个缺失（**AZ+1**） |
| 2 | 「Aurora 复制了数据页」 | 只复制 redo log；页面由存储层异步物化 |
| 3 | 「法定数只要多数派就行」 | 必须同时满足 `Vw > V/2` 且 `Vw + Vr > V`；Aurora 的 4/3 正是这样选出来的 |
| 4 | 「Frangipani 的缓存一致性靠广播失效」 | 靠**锁 + 租约**：只有锁的持有者能写，冲突时写回并释放 |
| 5 | 「Frangipani 恢复要等那台机器重启」 | 不需要——**任何拿到它的锁的机器**都能替它重放日志 |
| 6 | 🔧 2020 课程未覆盖 | **Serverless 与弹性**：2026 的计算层可以瞬间扩缩，缓存与租约的生命周期管理成为新难点（连接与会话迁移） |
| 7 | 🔧 2020 课程未覆盖 | **Neon 的 branch / 时间旅行**：把「日志 + 物化」分层暴露成产品能力，是 Aurora 模式在 2020s 的新形态 |
| 8 | 🔧 2020 课程未覆盖 | **共享存储 vs 共享无的选型**：Aurora/PolarDB 是共享存储，TiDB/Cockroach 是共享无；2026 的选型要在「写扩展性」与「运维简单」之间权衡 |
| 9 | 🔧 2020 课程未覆盖 | **租约 = 时钟假设**：Frangipani 的租约把正确性绑定到「时钟不会跳太多」；现代系统普遍改用「leases + 单调时钟 + 保守余量」，并明确记录这一假设 |
| 10 | 🔧 课程本身演进 | 6.5840 2026 schedule 中**未见** Aurora/Frangipani 两讲（以官方页为准）；但「日志下沉 + 存算分离」已是默认背景知识 |
