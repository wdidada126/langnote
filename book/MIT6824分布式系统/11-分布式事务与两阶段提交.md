# 第 12 讲 Distributed Transactions：两阶段提交与「协调者必须被复制」

> 官方标题：**Distributed Transactions**（LEC 12，主讲 fk）
> 指定必读：**6.033 Chapter 9**（Saltzer & Kaashoek《Principles of Computer System Design》），
> 仅 **9.1.5、9.1.6、9.5.2、9.5.3、9.6.3**（小节主题以教材原文为准）
> 布置：**Lab 4: Sharded KV**；同时收 Final Project 提案

## 本章地图

前面所有讲次都在解决「**一份数据在多个副本上怎么一致**」；
本讲解决另一个维度：**一笔操作要改多个（分片的）服务器上的数据，怎么做到全有或全无**。

主线：为什么需要分布式原子性 → 单机原子性靠日志（undo/redo + commit 记录）→
把日志思想推广到多机 = **两阶段提交（2PC）** → 逐个崩溃点的分析 →
**2PC 会阻塞**这一根本缺陷 → 修法（复制协调者 / 客户端驱动 2PC / 预先定序）。

## 核心精讲

### 11.1 目标：all-or-nothing 跨越多台机器

典型场景：银行转账（A 在 shard1，B 在 shard2）；或者 Lab 4 里一个请求要动多个分片的数据。
要求：**要么两个 shard 都改，要么都没改**，且并发执行时结果等价于某种串行顺序。

难点在于：每个参与者都可能单独崩溃，而崩溃的时机可能在「我已经做了本地修改」之后。

### 11.2 单机原子性：日志与提交记录

无论 undo 还是 redo 日志，核心机制都是同一个：**日志里有一条「提交记录（commit record）」，
它是不可逆的分界点**。

| 方案 | 写日志的时机 | 恢复规则 |
| --- | --- | --- |
| **undo 日志** | 先记旧值，再改数据，**改完（刷盘）才写 commit** | 有 commit → 已提交；无 commit → 用日志回滚 |
| **redo 日志（WAL）** | 先记新值 + commit（**必须先于改数据刷盘**），再改数据 | 有 commit → 重做；无 commit → 当作没发生过 |

两条纪律（值得背下来）：

1. **write-ahead**：描述「要做什么」的日志必须先于「真的去做」落盘；
2. **commit 记录是唯一的判定依据**：日志里有没有它，决定了一切。

### 11.3 两阶段提交（2PC）

角色：**协调者（coordinator / TC）+ 参与者（participants / workers）**。

```
阶段一（Prepare / Voting）
  TC  →  所有参与者：PREPARE（把要做的事做完，写 undo/redo 日志，加锁）
  参与者 →  TC：YES（已准备好、可以提交）或 NO（做不了，要中止）

阶段二（Commit / Abort）
  若全部 YES：
      TC 在自己的日志里写 COMMIT（← 不可逆的分界点）
      TC → 参与者：COMMIT
      参与者：写 commit 记录、真正提交、释放锁、回 ACK
      TC 收到全部 ACK 后可以清理该事务的状态
  若有任一 NO 或超时：
      TC 写 ABORT，广播 ABORT；参与者按 undo 日志回滚并释放锁
```

### 11.4 逐个崩溃点分析（本讲的核心训练）

| 崩溃方 | 时机 | 正确行为 | 为什么 |
| --- | --- | --- | --- |
| 参与者 | 投票前 | 恢复后**自行中止** | 它还没承诺过任何事 |
| 参与者 | 投票 YES 之后 | 恢复后必须**问协调者**（或等协调者重发） | 它可能已经处于「准备提交」状态，不能自行决定 |
| 参与者 | 收到 COMMIT 之后 | 恢复后**redo** | 提交记录已存在 |
| 协调者 | 写 COMMIT **之前** | 恢复后**中止**该事务 | 参与者只投过 YES，没人承诺过提交 |
| 协调者 | 写 COMMIT **之后** | 恢复后**继续把 COMMIT 发完** | 已经有参与者可能提交了，绝不能反悔 |
| 任意一方 | 网络分区 | 参与者**阻塞等待** | 见下节 |

结论：**2PC 的正确性完全建立在「参与者把票写进持久日志、协调者把决定写进持久日志」这两件事上。**

### 11.5 2PC 的根本缺陷：会阻塞

若一个参与者投了 YES 之后，协调者崩溃且迟迟不回来：

- 它**不能**提交——协调者可能已经决定中止（或还没决定）；
- 它**不能**中止——协调者可能已经决定提交，别的参与者可能已经提交了；
- 它**也不能**问别的参与者——参与者之间不交流决定，只有协调者知道结果。

于是它只能**阻塞并持有锁**，直到协调者恢复。
这就是 2PC 的名声来源：**它在协调者单点故障时会卡住资源**。

这也是「3PC 为什么没被采用」的原因：三阶段提交多加一轮 pre-commit 来减少阻塞窗口，
但**在网络分区下它仍然可能做出不一致的决定**，因此实践中几乎不用
（严格地说，异步网络下不存在既非阻塞又安全的原子提交协议）。

### 11.6 修法一：把协调者复制掉（本讲最重要的结论）

> **如果协调者本身是一个 Raft/Paxos 复制组，它就不是一个单点。**

- 协调者的每一步（收票结果、COMMIT 决定）都写进**复制日志**；
- 协调者挂了 → 组内选新 leader → 新 leader 从日志里知道「这个事务决定过什么」→ 继续推进；
- 参与者因此**不再无限阻塞**，只需等协调者组恢复（通常秒级）；
- 这正是 [12-Spanner与TrueTime.md](12-Spanner与TrueTime.md) 里 Spanner 的做法：
  每个分片是一个 Paxos 组，跨分片的提交用 2PC，**协调者本身是被复制的**。

一句话：**2PC 的安全性没问题，问题在可用性；用共识来补可用性。**

### 11.7 修法二：客户端驱动的 2PC（Percolator 思路）

Google Percolator（OSDI 2010）把协调者从服务端挪到客户端：

- 客户端选一个参与者作为 **primary**，其余为 secondary；
- 先给 primary 加一把锁并写入数据（锁记录里指向 primary）；
- 提交时只需**在 primary 上写一条提交记录**——这条记录的存在与否就是全局决定；
- secondary 上的锁指向 primary，任何后来者（包括崩溃后的恢复者）都去问 primary 的状态来「补完」；
- 客户端崩溃后，系统仍能自愈，因为**真相源（primary 的提交记录）在服务端**。

代价：读操作可能撞到未决的锁，需要等待或清理（这也是 Percolator 延迟模型的一部分）。

### 11.8 教学示意：2PC 的状态机

> **教学示意，不参与构建**——只表达状态与不可逆的分界点。

```go
// 教学示意，不参与构建
type TxnState int

const (
    Init TxnState = iota
    Prepared // 参与者已投票 YES（已落盘）
    Decided  // 协调者已写 COMMIT/ABORT（已落盘，不可逆）
    Done
)

// 参与者的超时处理：这里最能看出阻塞问题的根源
func (p *Participant) onTimeout(coordinatorReachable bool, s TxnState) string {
    switch s {
    case Init:
        return "abort" // 还没承诺 → 可以自行中止
    case Prepared:
        if coordinatorReachable {
            return "ask coordinator" // 问到结果就继续
        }
        return "BLOCK (holding locks)" // ← 2PC 的死穴
    case Decided:
        return "redo/undo per decision"
    }
    return "unknown"
}
```

> 把 `BLOCK` 这一支改掉，只有两条路：
> **(a) 让协调者高可用（复制它）**；**(b) 让真相源不在协调者身上（Percolator 的 primary 记录）**。

### 11.9 Lab 4 的连接点

Lab 4（Sharded KV）的难点不是 2PC 本身，而是**分片迁移**：

- 配置变更时，一个分片从 group A 迁到 group B；
- 迁移过程中，任何时刻都必须**只有一个 group 服务该分片**（否则出现双写）；
- 迁移必须**幂等**（重复收到同一批数据不能出错），且不能在「已迁移完成」后又重复拉取；
- 客户端与服务端都要能识别「我已经不服务这个分片了」并触发重试/重定向。

这些要求与 2PC 同构：**有一个不可逆的决定点（新配置生效），所有参与者必须按同一个决定行动**。

## 版本演进

- **1970s–1980s**：Gray 等人确立事务与 2PC（"Notes on Data Base Operating Systems"，1978；
  Gray & Lamport 之后的共识化演进）。
- **1990s**：XA 规范（分布式事务的工业接口）、CORBA OTS；2PC 进入企业中间件。
- **2000s**：互联网公司发现 2PC 的阻塞与锁代价太高，转向「最终一致 + 补偿（Saga/TCC）」。
- **2010**：Google **Percolator**（OSDI 2010）证明「客户端驱动 2PC + 快照隔离」能在大规模下工作。
- **2012**：**Spanner**（OSDI 2012）证明「复制协调者 + 2PC + TrueTime」能给出外部一致性。
- **2020（本讲）**：课程把 2PC 讲成「**正确但会阻塞，靠共识补可用性**」，
  并紧接着在 L13 用 Spanner 展示完整形态。
- **2026**：NewSQL 普遍提供分布式事务（TiDB 的 Percolator 模型、CockroachDB 的并行提交等），
  微服务端则仍以「Saga / 幂等 + 补偿」为主；确定性数据库（Calvin 一系）用「先定序再执行」绕开提交期协调。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：
  - **确定性数据库**（Calvin, SIGMOD 2012；Aria/Bohm, VLDB 2020）：提交前先就「顺序」达成一致，
    执行阶段无需再协调 → **从根本上减少 2PC 的提交延迟**；
  - **并行提交（parallel commits）**：把「准备」与「提交」的往返重叠，把分布式提交延迟从 2 轮降到约 1 轮；
  - **确定性 + 无协调**：研究热点是让跨分片事务在常见场景下走「一阶段提交」（所有参与者在同一复制组内时）。
- **工业界开源（star 数 2026-09-26 `gh api` 实测）**：
  - `pingcap/tidb`（**40590★**）：Percolator 模型的开源实现（乐观事务 + 后来的悲观事务），
    是「客户端驱动 2PC」最常被研究的样本。
  - `cockroachdb/cockroach`（**32508★**）：以复制的 range + 事务记录实现分布式提交，
    并做了并行提交类优化（细节以官方发布说明与论文为准）。
  - `apple/foundationdb`（**16731★**）：用确定性模拟测试把分布式事务的正确性测试做到极致，
    是「如何验证事务实现」的标杆。
  - `jepsen-io/jepsen`（**7504★**）：分布式系统的**一致性测试框架**，
    专门用来验证「你声称的一致性级别是不是真的」（见 [13-Labs总结与2026视角.md](13-Labs总结与2026视角.md)）。
  - `vitessio/vitess`（**21355★**）：MySQL 分片中间件，提供尽力而为的分布式事务（2PC）与单分片事务优化。

## 常见误区与本课程需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「2PC 能保证原子性，所以很安全」 | 原子性有保证，但**协调者单点故障会导致参与者无限阻塞**（可用性问题） |
| 2 | 「3PC 解决了 2PC 的阻塞」 | 3PC 只在「无网络分区」的假设下减少阻塞；分区下仍可能不一致，实践中不用 |
| 3 | 「参与者超时可以自行决定」 | 投票前可自行中止，**投票 YES 之后不行**——必须知道协调者的决定 |
| 4 | 「2PC 不需要日志」 | 参与者的投票、协调者的决定**都必须落盘**，否则崩溃后无法判定 |
| 5 | 「提交点是在收到 COMMIT 消息那一刻」 | 真正的分界点是**协调者把 COMMIT 写进自己的日志**那一刻 |
| 6 | 🔧 2020 课程未覆盖 | **复制协调者是标配**：现代 NewSQL 把 TC 放进 Raft/Paxos 组，2PC 的阻塞窗口被压缩到「组内选主时间」 |
| 7 | 🔧 2020 课程未覆盖 | **Percolator 与客户端驱动 2PC**：课程只提到概念，2026 的 TiDB 等已把它做成主流方案，值得单独读论文 |
| 8 | 🔧 2020 课程未覆盖 | **一阶段提交优化**：若事务只涉及一个复制组/一个分片，可完全跳过 2PC——这是真实系统里最大的性能优化来源 |
| 9 | 🔧 2020 课程未覆盖 | **微服务场景不用 2PC**：跨服务用 Saga/TCC + 幂等补偿；把 2PC 用在跨服务调用上是常见反模式 |
| 10 | 🔧 2020 课程未覆盖 | **可验证性**：Jepsen / 确定性仿真已成为「声称支持事务」系统的入场券；只跑单元测试远远不够 |
