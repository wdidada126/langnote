# 第 03 讲 GFS：为特定负载放宽一致性

> 官方标题：**GFS**（LEC 3，主讲 fk）
> 指定必读：**GFS (2003)**
> 布置：**Lab 2: Raft**（本讲后开始做 Raft）

## 本章地图

GFS 是课程里第一个「完整的真实系统」案例，也是**一致性取舍**的第一次示范：
它主动放弃 POSIX 语义，换来在当时硬件条件下可行的高吞吐。

主线：设计前提（工作负载长什么样）→ 架构（单 master + chunkserver）→ 写路径（租约 + 流水线）→
**一致性模型（consistent / defined）** → 原子记录追加（record append）→ 应用怎么在不一致上活下来 →
master 的元数据与恢复 → 弱点与 2026 视角。

## 核心精讲

### 3.1 设计前提：先说清楚「给谁用」

GFS 假设的负载是：

- 文件**很大**（多 GB 的单个文件很常见），小文件不是重点；
- 写以**追加（append）**为主，几乎不改写已写内容；
- 读以**大块顺序读**为主，随机小读很少；
- 高**吞吐**比低**延迟**重要得多；
- 客户端成百上千并发地往同一个文件追加。

这些前提决定了后面所有取舍：大 chunk、单 master、租约、放宽一致性、原子追加。
**脱离这些前提评价 GFS 的设计是常见误读**。

### 3.2 架构：把 master 从数据路径上摘掉

```
client ──(只问元数据)──> master（namespace + chunk 映射 + 租约）
  │
  └──(真正搬数据)──────> chunkserver（Linux 本地文件，chunk 作为普通文件存）
```

- 文件切成固定大小的 **chunk（64 MB）**，每个 chunk 有 64 位句柄，默认 3 副本；
- **master 只管元数据**：命名空间、文件→chunk 映射、chunk 当前位置。
  它**不参与数据读写**——这是单 master 还能撑住的根本原因；
- master 的元数据**全在内存**（约每 64 MB chunk 几十字节级元数据，具体规模取决于文件名长度与压缩），
  靠**操作日志（operation log，持久化并复制）+ 检查点（checkpoint）**恢复；
- **chunk 位置不入日志**：master 启动时问 chunkserver，之后靠心跳维护——
  因为位置是「chunkserver 说了算」的事实，写进日志反而会与真实状态不一致。

### 3.3 写路径：租约 + 流水线

1. client 向 master 询问「我要写的 chunk 的副本在哪、**主副本（primary）**是谁」；
2. master 给某个副本发**租约（lease，论文中为初始 60 秒，可经心跳续期）**，该副本成为 primary；
3. client 把数据**沿一条链流水线推送**（按网络拓扑选下一跳，而不是星型分发），充分利用各节点带宽；
4. 数据都到位后，client 向 primary 发**写请求**；
5. **primary 给并发的多个写请求编号定序**，按序应用到本地并转发给其余副本；
6. 所有副本成功后 primary 回复 client；失败则由 client 重试。

这个设计的要点：**控制流（定序）集中到 primary，数据流（搬运）去中心化**。
定序集中是为了所有副本顺序一致；数据流水线是为了不让 primary 的出口带宽成为瓶颈。

### 3.4 一致性模型：consistent 与 defined

这是本课最需要精确的区分：

| 状态 | 含义 |
| --- | --- |
| **consistent（一致的）** | 所有客户端无论从哪个副本读，该区域内容**相同** |
| **defined（已定义的）** | consistent **且**客户端能完整看到自己刚写入的内容 |

由此得到的状态表（论文原表）：

| 操作 | 结果 |
| --- | --- |
| 串行成功的写 | **defined** |
| 并发成功的写（有重叠） | **consistent 但未定义**（多个写的片段混在一起，顺序不确定） |
| 成功的记录追加（含重试造成的重复） | 追加的数据是 **defined**，中间可能夹着 **inconsistent** 的填充/重复片段 |
| 失败的操作 | **inconsistent**（即不同副本可能不同） |

### 3.5 原子记录追加（atomic record append）

client 只给「数据」，不给偏移量——**偏移量由 GFS 选**，并保证「至少成功追加一次（at least once）」。
若某副本在追加中失败，client 重试，于是：

- 同一条记录可能在某些副本上**出现多次**；
- 失败的副本可能留下**填充（padding）**或半条记录。

GFS 明确**不保证字节级完全一致**，把「识别并跳过重复/残缺记录」的责任交给应用。
应用侧的常规做法：

- **自校验记录**：记录里带校验和，读到坏的跳过；
- **自标识记录**：记录里带唯一 ID，消费者按 ID 去重；
- **追加而非覆盖**：覆盖写一旦失败会留下「新旧混合」的不可判定状态，追加最多留下可识别的垃圾。

### 3.6 master：命名空间锁、快照与副本管理

- **命名空间锁**：对路径前缀加读/写锁，允许同目录下的并发写、跨目录可并行（`/d1/...` 与 `/d2/...` 不冲突）；
- **快照（snapshot）**：用写时复制（COW），先撤销相关 chunk 的租约，之后首次写才真正复制；
- **副本放置**：跨机架分布（兼顾可靠与带宽），**再复制（re-replication）**按优先级恢复副本数，**再均衡**迁移；
- **陈旧副本（stale replica）**：靠 **chunk 版本号**识别，版本号在租约续期时推进；落后的副本在垃圾回收中清理；
- **master 高可用**：操作日志复制到多台；**shadow master** 提供只读服务（可接受轻微滞后，读的是日志副本）。

### 3.7 教学示意：一致性状态的判定

> **教学示意，不参与构建**——只用来把 consistent/defined 的区别说清楚。

```go
// 教学示意：三副本下同一个 chunk 区域的三种典型状态
type Region struct {
    ReplicaA, ReplicaB, ReplicaC string
}

func classify(r Region) string {
    if r.ReplicaA == r.ReplicaB && r.ReplicaB == r.ReplicaC {
        // 三副本一致：可能是 defined（串行写成功），
        // 也可能是 consistent-but-undefined（并发写碎片混合，但每个副本都一样）
        // —— 二者无法仅从副本内容区分，必须看「写是怎么发出的」
        return "consistent"
    }
    // 副本不同：必然经历过失败（如追加时某副本宕机）
    return "inconsistent (padding / duplicate / partial)"
}
```

> 这个示意刻意说明一件事：**「一致」不等于「是我想要的」**。
> 并发覆盖写可以把两个写混成「三副本都一样但谁都不想要」的内容，它仍是 consistent。
> GFS 把这个判断完全交给应用，这正是它「放宽一致性」的实质。

## 版本演进

- **2003（论文当年）**：GFS 解决的是「用廉价机器存几百 TB、支持上千并发追加」；
  单 master 与放宽的一致性在当时是合理的工程取舍。
- **2004**：MapReduce 建立在 GFS 之上（原子 rename 与顺序读就是为它准备的）。
- **2010 前后**：Google 内部以 **Colossus**（GFS 的后继）取代 GFS——
  公开资料有限，可确认的方向是：**元数据不再由单 master 承担、编码冗余（如 Reed-Solomon）降低存储成本、客户端驱动的复制**。
  细节以 Google 自己的公开表述为准，本目录不展开未经核实的实现细节。
- **2006–2020**：开源侧 **HDFS** 沿 GFS 架构实现（NameNode + DataNode），
  后续陆续补上 GFS 论文里没解决或没强调的东西：NameNode HA（JournalNode 法定组 + ZKFC）、
  Federation（多命名空间）、Erasure Coding（HDFS 3.x）、Router-based Federation。
- **2020（本讲）**：课程把 GFS 作为「**放宽一致性以换取简单与吞吐**」的范例来读，
  并在后面用 Spanner（L13）展示相反的选择。
- **2026**：新建的大数据栈越来越多直接落在**对象存储**上（存算分离），
  「HDFS 独占集群」在云上退化为一种可选形态；但 HDFS 仍有大量存量部署，
  而 GFS 提出的三个问题（元数据可扩展性、追加语义、副本一致性判定）依然是存储系统的核心议题。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：
  - **元数据可扩展性**：把目录树与块映射拆到分布式 KV/BigTable 上（即 Colossus 路线），
    以及 CephFS（`ceph`）的动态子树分区、BeeGFS、Lustre 的 metadata 分层；
  - **纠删码（EC）vs 三副本**：冷数据用 EC 大幅降成本，代价是修复带宽与尾延迟；
    研究热点是 **局部可修复码（LRC）** 与「修复时只动少量节点」；
  - **追加语义的复兴**：以日志为中心的分布式存储（Aurora 的「日志即数据库」，见 [10-Aurora与Frangipani.md](10-Aurora与Frangipani.md)）
    与对象存储的 WAL 化，本质上都继承了 GFS 的「追加优先」思想。
- **工业界开源（star 数 2026-09-26 `gh api` 实测）**：
  - `apache/hadoop`（**15669★**）：HDFS 仍是最大的开源 GFS 实现；生产上常见 NameNode HA + Federation + EC 组合。
  - `apache/hbase`（**5560★**）：Bigtable 的开源实现，跑在 HDFS 上——可观察「在放宽一致性的 FS 上如何做出结构化语义」。
  - `minio/minio`（**61350★**）：对象存储；2026 年新栈的事实底座，取代了 GFS/HDFS 的「唯一存储层」地位。
  - `seaweedfs/seaweedfs`（**34986★**）：小文件友好的分布式 FS，直接针对 GFS 的「小文件不友好」弱点设计
    （元数据与数据分离、filer 层）。

## 常见误区与本课程需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「GFS 一致性很弱，所以设计失败」 | 它为之服务的负载（大文件、追加、高吞吐）下这个取舍是对的；评价要回到前提 |
| 2 | 「consistent = 数据正确」 | consistent 只保证副本相同；并发覆盖写可以一致但「不是任何人想要的结果」（undefined） |
| 3 | 「record append 保证 exactly-once」 | 只保证 **at-least-once**：重复、填充、半条记录都会出现，应用必须自校验/自标识 |
| 4 | 「master 持久化了 chunk 位置」 | 位置不入日志，靠启动时询问 + 心跳维护；入日志反而会产生与事实不符的权威状态 |
| 5 | 「单 master 是数据瓶颈」 | master 不在数据路径上；它的瓶颈是**元数据规模与每秒元数据操作**，不是带宽 |
| 6 | 🔧 2020 课程未覆盖 | **单 master 的可扩展性在 2026 已彻底被解决**（元数据分片 / 分布式 KV 承载），Colossus 路线成为默认；读 GFS 时应把它当作「历史取舍」而非「可行方案」 |
| 7 | 🔧 2020 课程未覆盖 | **纠删码**：GFS 只讲三副本，2026 的冷数据几乎必谈 EC（HDFS 3.x、对象存储默认），代价是修复带宽 |
| 8 | 🔧 2020 课程未覆盖 | **存算分离**：GFS 的核心优化「让计算靠近数据（本地性）」在云上对象存储场景失效，调度目标已改变（见 [01-引言与MapReduce.md](01-引言与MapReduce.md)） |
| 9 | 🔧 2020 课程未覆盖 | **小文件与热 chunk**：GFS 只简略提及；2026 的实践中这是最痛的点之一（可执行包/索引文件热 chunk），需要副本扩量、客户端缓存与打散 |
