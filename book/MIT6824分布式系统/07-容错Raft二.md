## 核心精讲

### 7.1 持久化：哪些状态必须在回复前落盘

| 状态 | 是否必须持久化 | 理由 |
| --- | --- | --- |
| `currentTerm` | ✅ | 崩后重启不能「忘记自己已经进入更高任期」 |
| `votedFor` | ✅ | **同一任期投给两个人 = 安全性崩溃**（会出现两个 leader） |
| `log[]` | ✅ | 已提交的条目必须能找回 |
| `commitIndex` / `lastApplied` | ❌（可重算） | 重启后跟随 leader 的 `leaderCommit` 推进 |
| 状态机内容 | 视实现 | 若有快照则恢复；否则靠重放日志 |

> Lab 2C 的判定标准就是一句话：**在回复 RPC 之前，凡是要持久化的字段必须先落盘**。
> 「先回复再落盘」在崩溃时会直接破坏安全性，而且这种 bug 只在特定崩溃时序下出现。

### 7.2 日志压缩（§7）：快照

- 每个服务器**独立**地对自己的已提交日志做快照（不需要 leader 协调，因为已提交部分必然一致）；
- 快照内容：状态机的完整状态 + **lastIncludedIndex / lastIncludedTerm**（最后一个被快照包含的日志条目）；
- 快照之后，索引 ≤ lastIncludedIndex 的日志条目可以丢弃；
- 对**落后太多**或**新加入**的 follower，leader 用 **`InstallSnapshot`** RPC 直接发快照，
  因为要补的日志已经被丢弃了。

工程要点：

| 问题 | 常见做法 |
| --- | --- |
| 快照太慢/太大 | 写时复制（COW）、增量快照、只持久化「相对上次快照的变化」 |
| 快照与日志的边界 | 快照必须原子地记录 lastIncludedIndex/Term；两者不一致 = 数据错位 |
| 什么时候做 | 日志超过阈值；也要避免「不停做快照」拖垮正常路径 |
| 状态机要不要参与 | 需要状态机提供「把当前状态序列化」的接口（这是状态机与共识层解耦的关键约定） |

### 7.3 客户端交互（§8）

**写请求**：client → leader → 追加日志 → 等提交 → 应用状态机 → 回复 client。
若 leader 崩溃，client 会超时并重连到别的节点；新 leader 会告诉它「我不是 leader」（或重定向）。

**重复请求（at-most-once）**：

- 每个 client 有一个 **session id**，每条命令带**单调递增序号**；
- 服务端按 session 记录「已处理的最大序号 + 该命令的结果」；
- 重复的请求直接返回记录的结果，不再执行；
- 这是 [02-RPC与线程.md](02-RPC与线程.md) 中 `kv.go` 去重表在复制状态机上的升级版：
  区别在于**去重表也被复制了**（它在状态机里，随日志同步），所以 leader 切换后仍然有效。

**只读请求为什么不能「直接读状态机」**：

若一个 leader 被网络隔离（它自己不知道），它可能仍在用旧数据回答读请求 → **违反线性一致**。
论文给出两种安全做法：

| 方案 | 做法 | 代价 | 依赖 |
| --- | --- | --- | --- |
| **(a) 把读也写进日志** | 读请求走一遍日志提交 | 一次日志复制的开销（慢） | 无 |
| **(b) ReadIndex**（论文 §8 的方案） | leader 记下当前 `commitIndex` 为 ReadIndex；向集群发一轮心跳确认自己「仍是 leader」（要拿到多数派回应）；等状态机应用到 ReadIndex；然后在本地读 | 一轮心跳（比写日志便宜很多） | 无 |
| **(c) Leader lease（租约）** | leader 在租约期内**假设**自己仍是 leader，直接本地读，不发心跳 | 几乎零开销 | **依赖时钟漂移有界** |

三种方案的取舍一句话：**(b) 是默认选择；(c) 快但要把时钟误差做成安全性假设**（这也是它与 [12-Spanner与TrueTime.md](12-Spanner与TrueTime.md) 的内在联系）。

> 配套工程技巧：新 leader 上任后**立刻追加一条 no-op 空条目**。
> 原因：ReadIndex 要求「leader 任期内的多数派确认」，若本任期还没有任何条目被提交，
> `commitIndex` 可能落后于上任期的数据，读会不安全/阻塞。no-op 条目让 commitIndex 尽快推进到本任期。

### 7.4 教学示意：ReadIndex 的控制流

> **教学示意，不参与构建**——只表达顺序，不构成实现。

```go
// 教学示意，不参与构建
func (rf *Raft) readIndex() (int, bool) {
    rf.mu.Lock()
    if rf.role != Leader {
        rf.mu.Unlock()
        return 0, false // 不是 leader：让客户端换节点
    }
    readIdx := rf.commitIndex // 1) 记下当前提交水位
    term := rf.currentTerm
    rf.mu.Unlock()

    // 2) 向多数派发心跳，确认「此刻我仍是 leader」
    if !rf.confirmLeadershipWithMajority(term) {
        return 0, false
    }

    // 3) 等状态机追到 readIdx，之后才能读本地状态
    rf.waitApplied(readIdx)
    return readIdx, true
}
```

> 注意步骤 2 与 3 的**顺序不能颠倒**：先确认领导权（防止读到被罢黜 leader 的陈旧数据），
> 再等待应用到位（防止读到「本节点还没应用」的数据）。
> 这个顺序就是「线性一致读」的全部要害。

### 7.5 §6 成员变更（**非本讲指定阅读，工程必补**）

> 2020 课表明确要求「§7 到末尾，**但不含 §6**」。本节是补注，读的时候要区分。

为什么需要它：集群要加机器、换机器、缩容，而「多数派」的定义随成员集合变化。

| 方案 | 机制 | 评价 |
| --- | --- | --- |
| **联合共识（joint consensus，`C_old,new`）** | 两阶段：先切到「新旧配置都生效」（选举与提交都需两个配置各自的多数派），再切到新配置 | 安全、可任意变更；实现复杂 |
| **单节点变更（single-server changes）** | 一次只加/删**一个**节点 | 简单；**新旧多数派必有交集**，故安全；但一次只能动一个 |

单节点变更的工程注意点（论文与后续实践强调的）：

- **新加入的节点先当 learner（非投票成员）**：否则它在追上日志前参与投票会拖慢/破坏多数派；
- **要移除的节点若是 leader**：leader 必须在新配置提交后**主动退位**（step down），然后重新选举；
- **leader 不在新配置中**时的处理要格外小心（它仍需负责把新配置复制出去，之后才能退位）；
- 社区后来讨论过单节点变更在特定交错下的边界情况，实践上很多实现（如 etcd）选择**联合共识**或混合方案。

### 7.6 论文没写但生产实现几乎必加的两项

- **PreVote（预投票）**：一个被网络隔离的节点会不断超时、自增 term、发起选举——
  它选不上，但每次都会把 term 推高；等它回到集群时会强制触发一次不必要的重新选举，
  造成可用性抖动。PreVote 让候选人在**真正自增 term 之前**先问一圈「我有可能赢吗」，
  拿不到多数派的预投票就不自增 term。
- **CheckQuorum**：leader 若在一段时间内无法与多数派通信（例如自己被隔离），
  应**主动退位**为 follower，避免它继续以「leader」身份回应客户端。

> 这两项出自 Ongaro 的博士论文中关于「disruptive servers（捣乱节点）」的讨论，
> **不在 ATC 2014 论文正文的 §1–§5 里**。工程实现几乎都有，读论文时不要以为它是协议的一部分。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：
  - **租约读的时钟依赖**：把 leader lease 的安全性绑定到「时钟漂移有界」，
    与 Spanner 的 TrueTime、CockroachDB 的 HLC 属同一族问题（见 [12-Spanner与TrueTime.md](12-Spanner与TrueTime.md)）；
  - **跟随者读（follower read / replica read）**：让 follower 也能服务线性一致读，
    代价是向 leader 要 ReadIndex 或等租约；
  - **快照与状态机解耦**：增量快照、LSM 引擎快照（直接快照 SSTable 文件）在工程上替代「序列化整个状态机」；
  - **形式化验证与仿真测试**：IronFleet（SOSP 2015）；确定性仿真（FoundationDB、`madsim`）。
- **工业界开源（star 数 2026-09-26 `gh api` 实测）**：
  - `etcd-io/etcd`（**52310★**）：实现了 ReadIndex、learner、快照、PreVote（可用作「论文之外有哪些工程补丁」的样本）。
  - `tikv/tikv`（**16878★**）、`tikv/raft-rs`（**3401★**）、`tikv/pd`（**1159★**）：**Multi-Raft** 的教科书级实践——
    TiKV 把数据切成 region，每个 region 一个 Raft group，PD 负责调度与迁移。
  - `pingcap/tidb`（**40590★**）：建立在 TiKV 之上的 NewSQL，事务层见 [11-分布式事务与两阶段提交.md](11-分布式事务与两阶段提交.md)。
  - `baidu/braft`（**4227★**）：C++ 实现，文档里明确列出论文未覆盖的工程点。
  - `madsim-rs/madsim`（**1161★**）：确定性仿真测试框架（把时钟/网络/磁盘都变成可控输入）。

## 常见误区与本课程需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「commitIndex 也要持久化」 | 不必；`votedFor` 与 `currentTerm` 才是安全性的关键（同任期重复投票会选出两个 leader） |
| 2 | 「leader 直接读自己的状态机就是线性一致」 | 被隔离的旧 leader 会读到陈旧数据；必须 ReadIndex（或 lease + 有界时钟） |
| 3 | 「快照由 leader 统一做再分发」 | 各节点**独立**做自己的快照；`InstallSnapshot` 只用于追不上的 follower / 新节点 |
| 4 | 「成员变更可以一次换多个」 | 单节点变更的安全论证依赖「一次只动一个」；任意变更要走联合共识 |
| 5 | 「读走日志最安全，那就都走日志」 | 正确但慢；ReadIndex 是标准折中（一轮心跳而非一次日志复制） |
| 6 | 🔧 2020 课程未覆盖 | **§6 成员变更**：课表跳过，但 Lab 4（Sharded KV 的配置变更）本质上就是它的应用形式；必须自学补齐 |
| 7 | 🔧 2020 课程未覆盖 | **PreVote / CheckQuorum**：论文正文没有，生产实现几乎必加，否则隔离节点会造成 term 爆炸与抖动 |
| 8 | 🔧 2020 课程未覆盖 | **Multi-Raft 与分片调度**：真实系统不是「一个 Raft group 管全部数据」，而是上千个 group + 调度器（rebalance / 迁移 / 分裂） |
| 9 | 🔧 2020 课程未覆盖 | **快照的工程形态**：现代引擎多用 LSM 的文件级快照/增量快照，而不是「序列化整个状态机」；课程只讲概念形态 |
| 10 | 🔧 课程本身演进 | 6.5840（2026）把 Raft 移到 **Lab 3**，并在 Lab 2 前插入 **Key/Value server**；且 Lab 含快照部分。按 2020 资料做时需注意实验编号错位 |
