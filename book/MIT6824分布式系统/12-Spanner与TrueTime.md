# 第 13 讲 Spanner：用「时间的不确定区间」换外部一致性

> 官方标题：**Spanner**（LEC 13，主讲 rtm）
> 指定必读：**Spanner (2012)**

## 本章地图

Spanner 是这门课里「**把前面所有技术拼成一个完整系统**」的收尾案例：

```
副本一致性  → 每个 tablet 一个 Paxos 组（L6/L7 的共识）
跨分片原子性 → 2PC，且协调者被复制（L12 的结论）
分布式时间  → TrueTime：时钟不再是「一个值」，而是「一个区间」
外部一致性  → commit wait：等这个区间完全过去才提交
只读性能    → 快照读：在指定时间戳读，不加锁、可就近副本
```

主线：Spanner 的结构 → **TrueTime 的语义** → 读写事务与 **commit wait** →
只读事务与 safe time → 外部一致性的论证形状 → 没有 TrueTime 怎么办（HLC / TSO）。

## 核心精讲

### 12.1 结构：Paxos 组 + 目录

- 数据按 key range 切分，每个分片（tablet / directory 组）由**一个 Paxos 组**复制；
- Paxos 组的 leader 持有**租约**（论文中为十秒量级），负责本地读写与 2PC 的参与者角色；
- 跨分片的事务用 **2PC**，参与者是各组的 leader；**协调者本身也在 Paxos 组里**（呼应 [11-分布式事务与两阶段提交.md](11-分布式事务与两阶段提交.md) 的「协调者必须被复制」）；
- 数据放置由 **directory（目录）** 决定，可跨数据中心迁移（movedir）。

### 12.2 TrueTime：把时钟建模成区间

TrueTime 提供的 API 只有三个，但语义与「读一下系统时间」完全不同：

| API | 返回值 | 含义 |
| --- | --- | --- |
| `TT.now()` | 区间 `[earliest, latest]` | **保证**真实时间落在这个区间内 |
| `TT.after(t)` | bool | 「真实时间是否已确定地超过了 t」 |
| `TT.before(t)` | bool | 「真实时间是否已确定地早于 t」 |

- 实现：每个数据中心配备 **GPS 接收机与原子钟**（两类时钟失效模式不同，互为兜底），
  并通过时钟同步协议把偏差限制在一个可测量的界限内；
- **ε（epsilon）** 是时间不确定性的半宽；论文给出的典型值在毫秒到十毫秒量级，
  且随时钟漂移波动（**具体数值以论文原文为准，本目录不臆造数字**）。

> 关键思维转变：**分布式系统里不能问「现在几点」，只能问「现在几点 ± 多少」**。
> Spanner 的整套正确性建立在把这个「±」明确化、可测量化之上。

### 12.3 读写事务与 commit wait

只读会另说，这里先说读写事务（read-write txn）：

1. 事务读取时加锁（论文采用两阶段封锁，并提到用 **wound-wait** 处理死锁风险——细节以论文为准）；
2. 在提交阶段，协调者收集所有参与者的 prepare 结果，然后**选一个提交时间戳 s**：
   `s` 必须大于事务读过的所有数据的时间戳，且大于所有已分配的时间戳；
3. **commit wait**：协调者在真正提交前，
   **必须等到 `TT.after(s)` 为真**（即「真实时间已经确定地走过了 s」）才提交并回复客户端；
4. 等待时长约等于 `2 × ε`（因为要保证区间完全越过 s）。

**为什么要等这一下？** 论证的外部一致性（external consistency，等价于线性一致性）：

> 若事务 T2 在真实时间上「开始于 T1 提交完成之后」，
> 那么 T2 的提交时间戳一定大于 T1 的提交时间戳。

直觉：T1 提交时它已经等到了「真实时间确定越过 s1」；
T2 在 T1 对外可见之后才开始，它取到的时间戳 s2 必然晚于那个时刻，于是 s2 > s1。
**如果不做 commit wait，两台机器的时钟偏差足以让 s2 < s1，于是一个「后发生的」事务被分配了更早的时间戳**——
这就是外部一致性被破坏的方式。

### 12.4 只读事务：无锁、就近、快照

这是 Spanner 性能好用的另一半：

- 只读事务**不参与 2PC、不加锁**；
- 它先**选一个时间戳**（可以是 `TT.now().latest`，也可以是用户指定的过去时间戳或带 staleness 约束的时间）；
- 然后向**任意足够新的副本**发起读：该副本必须已经应用了截止到该时间戳的所有事务；
- 副本怎么知道「我够不够新」？靠 **safe time（t_safe）**：
  副本维护一个「我已经完整应用到的时间点」，只有 `t_safe >= 读时间戳` 才能服务这次读。

于是：

| 读的类型 | 代价 | 新鲜度 |
| --- | --- | --- |
| 强读（`TT.now().latest`） | 通常仍需走 leader 或等 safe time 追上 | 最新 |
| **有界陈旧读**（如「读 10 秒前的快照」） | 可以完全本地服务（**极快、延迟低**） | 最多落后 10 秒 |

**这是本讲最重要的工程结论**：把「一致性」和「新鲜度」拆成两个可调旋钮，
让应用按需求选择——而不是像 [08-ZooKeeper.md](08-ZooKeeper.md) 那样默认陈旧、或像 Raft ReadIndex 那样默认最强。

### 12.5 教学示意：commit wait 的判定

> **教学示意，不参与构建**——只表达「提交前必须等区间越过」。

```go
// 教学示意，不参与构建
type Interval struct{ Earliest, Latest time.Time }

// 真实时间（绝对真值）保证落在 [Earliest, Latest] 内
func TTAfter(s time.Time, now Interval) bool {
    return now.Earliest.After(s) // 连最保守的下界都越过了 s → 确定地超过了
}

func TTBefore(s time.Time, now Interval) bool {
    return now.Latest.Before(s)
}

// 读写事务的提交路径（顺序不可颠倒）
func commitRW(s time.Time, now func() Interval) {
    // 1) 收集 prepare 票
    // 2) 选定提交时间戳 s
    // 3) 【关键的等待】——不等待就会破坏外部一致性
    for !TTAfter(s, now()) {
        waitABit()
    }
    // 4) 写入提交记录并回复客户端
}
```

### 12.6 三种「分布式时间」方案对比（2026 视角的骨架）

| 方案 | 代表 | 时间从哪来 | 外部一致性 | 代价 |
| --- | --- | --- | --- | --- |
| **TrueTime（GPS + 原子钟）** | Spanner | 每台机器本地读，返回**区间** | ✅ 可做到 | 专用硬件 + commit wait 延迟 |
| **HLC（混合逻辑时钟）** | CockroachDB、YugabyteDB | 物理时钟 + 逻辑计数器，单调推进 | 通常**不承诺**跨节点外部一致 | 无需专用硬件；靠「不确定性区间重启/重试」补救 |
| **TSO（中心时间戳分配器）** | TiDB（PD）、Percolator | 单点/复制组发号 | ✅（因为权威唯一） | 每次取号一次 RTT；TSO 必须高可用 |

> 这三种方案回答的是同一个问题：**「谁有权说一件事发生在另一件事之后」**。
> TrueTime 说「硬件保证的区间说」；HLC 说「物理+逻辑的因果序说」；TSO 说「一个权威说」。

## 版本演进

- **2012（论文当年）**：Spanner（OSDI 2012）首次把 Paxos 复制、2PC、TrueTime 组合成全球规模的强一致数据库。
- **2012–2017**：Google F1 建立在 Spanner 之上（F1: A Distributed SQL Database That Scales，VLDB 2012）；
  同期 Aurora（2017）走的是「共享存储 + 单写者」的另一条路（见 [10-Aurora与Frangipani.md](10-Aurora与Frangipani.md)）。
- **2010s 后期**：CockroachDB 与 TiDB 等开源 NewSQL 在没有 GPS/原子钟的前提下，
  分别用 **HLC** 与 **TSO** 提供了各自的一致性保证——Spanner 的思想被「去硬件化」。
- **2020（本讲）**：课程把 Spanner 放在分布式事务之后（L12 → L13），
  意图很明确：**Spanner = 复制 + 2PC + 时间的完整组装**。
- **2026**：
  - Spanner 已发展为托管服务（接口/形态以官方产品文档为准）；
  - 云厂商开始提供**带误差界的时钟服务**（如 AWS 的 ClockBound 一类），
    使「TrueTime 式区间」在没有 GPS/原子钟的环境里也能近似获得；
  - 研究侧继续探索「无专用硬件的外部一致性」与「跨区域延迟优化」（确定性、预先定序、并行提交）。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：
  - **HLC 与混合时钟**：把物理时钟与逻辑时钟合并，保留因果序且贴近物理时间；
  - **带误差界的时钟服务**：ClockBound 一类的思路——让普通服务器也能拿到「误差区间」，
    从而复用 commit wait 的推理方式；
  - **确定性事务与预先定序**（Calvin 一系）：用「先定序、后执行」消除提交期的时钟依赖；
  - **并行提交**：把提交延迟从两轮往返压缩到约一轮，降低 commit wait 在总延迟中的占比。
- **工业界开源（star 数 2026-09-26 `gh api` 实测）**：
  - `cockroachdb/cockroach`（**32508★**）：**HLC** 的代表实现，是「没有 TrueTime 怎么做」的最佳对照样本。
  - `pingcap/tidb`（**40590★**）+ `tikv/pd`（**1159★**）：**TSO** 路线——PD 担任中心时间戳分配器。
  - `yugabyte/yugabyte-db`（**10557★**）：同样采用 **HLC**，按 tablet 做 Raft 复制 + 分布式事务。
  - `aws/clock-bound`（**350★**）：提供**时钟误差区间**的开源实现（TrueTime 思路的去硬件化版本）。
  - `jepsen-io/jepsen`（**7504★**）：用于检验「声称的外部一致性/可串行化」是否成立。

## 常见误区与本课程需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Spanner 的时钟很准，所以不需要等待」 | 恰恰相反：**因为它承认有误差，才必须 commit wait** |
| 2 | 「commit wait 是性能优化」 | 它是**正确性的必要条件**：去掉它就失去外部一致性 |
| 3 | 「只读事务也要加锁」 | 不加锁；靠快照时间戳 + safe time 服务 |
| 4 | 「有界陈旧读就是弱一致」 | 它仍是**一致的快照**（事务看到自洽的历史），只是不最新——「一致性」与「新鲜度」是两个旋钮 |
| 5 | 「Spanner 完全靠 TrueTime，Paxos 只是备份」 | 两者分工：Paxos 保证**副本一致与容错**，TrueTime 保证**跨事务的时间序** |
| 6 | 🔧 2020 课程未覆盖 | **HLC / TSO 两条替代路线**：没有 GPS/原子钟也能做全球数据库，但保证强度不同（读论文时必须问清楚「它承诺什么」） |
| 7 | 🔧 2020 课程未覆盖 | **ClockBound 一类的误差界时钟**：2020s 后才出现，让「区间时钟」在普通云主机上可用 |
| 8 | 🔧 2020 课程未覆盖 | **并行提交/一阶段提交**：现代 NewSQL 大幅优化提交延迟，commit wait 在总延迟中的占比已不是论文时代的样子 |
| 9 | 🔧 2020 课程未覆盖 | **跨区域延迟与放置策略**：论文讲了 directory/movedir，2026 的实践更强调「把数据放到靠近写入方」并配合 follower read / 本地读 |
| 10 | 🔧 课程本身演进 | 6.5840 2026 schedule **保留** Spanner 一讲（LEC 12），可见其地位未变；但周围讲次（如新增 Chain Replication）有轮换 |
