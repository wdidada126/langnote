## 5.1 题纲

1. 建模公理：一切从查询出发（query-first），实体关系图只是原材料
2. 反范式是默认，不是妥协：一行一查询 vs 一行多查询的成本差
3. 分区设计三问：基数有界？大小有界（~10 万行/MB 级 ⚠️ 经验值）？热点可控？
4. 聚簇设计二问：分区内按什么排序才让 WHERE/ORDER BY 免费？范围谓词前缀连续吗？
5. 一张表一个访问模式：N 个查询 → 最多 N 张表（+ 双写一致性策略选型）
6. 二级索引的使用判据：低基数、稀疏、结果集小；否则回到反范式
7. 时间序列模式：日桶/月桶、`PRIMARY KEY ((bucket), ts)`、TWCS 的建模搭档
8. 宽分区与游标分页：大分区不是错，无分页的读是错
9. 计数器/多 DC/物化视图在建模期的连带决策

## 5.2 反范式三姿势与它们的账

书中给出的核心循环（⚠️ 转述）：**列出查询 → 为每个查询设计"一次分区命中"的表 → 用写入
路径的一致性策略把多表串起来**。三姿势：

```sql
-- 姿势 A：同一事实、两种分区（按城市查 & 按日期查）
CREATE TABLE trips_by_city (city text, id uuid, ts timestamp, ...,
  PRIMARY KEY ((city), ts, id)) WITH CLUSTERING ORDER BY (ts DESC, id DESC);
CREATE TABLE trips_by_day  (day date, id uuid, city text, ts timestamp, ...,
  PRIMARY KEY ((day), ts, id));
-- 姿势 B：聚合预计算（"Top-K by rating" 用计数列+桶拆分区防热 ⚠️）
CREATE TABLE ratings_bucket (bucket int, rating int, id uuid, cnt bigint,
  PRIMARY KEY ((bucket), rating, id)) CLUSTERING ORDER ...;
-- 姿势 C：查找表（外键式 JOIN 的替身：查询时两次单行读代替运行时 JOIN）
```

账本：A 的双写要么同分区 UNLOGGED BATCH/要么接受"两表短暂不一致"+对账修复 ⚠️；
B 的计数器列在高并发下有 LWW 丢更新风险（要 counter 语义则回 03 章的代价表）；
C 的延迟=多次往返但都 O(1) 分区命中。**建模的产物不是 ER 图，而是"每查询延迟预算表"**。

见 [../设计数据密集型应用/02-数据模型与查询语言.md](../设计数据密集型应用/02-数据模型与查询语言.md)（✅ 盘上存在）；

## 5.3 分区键的四宗罪（书中反例集 ⚠️ 重构）

1. **低基数分区键**：`PRIMARY KEY (status, ...)`——status 只有三种值 → 三个巨型分区，
   等于把数据钉死在 3 个节点上（扩不动+热分区）。
2. **无界增长分区**：按租户建模但租户内无限追加（消息表只按 `user_id` 分区）→ 破 2GB 软限、
   修复与流式搬迁变成灾难。解法：时间桶进分区键。
3. **把"属性"当分区键**：`WHERE age>?` 的 age 进分区键不解决任何事——范围属性应进聚簇列
   或 2i/MV/反范式。
4. **随机 UUID 主键当查询入口**：分布均匀但没有访问模式——写入分散、读"该用户最近 10 条"
   仍需全分区扫；应 `(user_id, ts DESC, id)`。

每条罪名的修复都在环上改变数据摆放，因此**建模期改键=运维期重建表**（`nodetool`/快照/
SSTable 导出重灌的迁移工法在 #89 册 08 章）。

## 5.4 二级索引：能用的窄门（2.x 判词 ⚠️）

2.x 的 2i 本质：每节点在自己持有的行上建本地索引，查询时协调节点广播"索引探测"再合并。
适用判据（书中三条 ⚠️）：基数低（性别/国家）、使用稀疏（只有少数行有此值）、结果集小。
书中反对清单：高基数列（timeuuid）、需要"索引列+非索引列"混合谓词的查询、对写延迟敏感
的表。2026 的当代判词（SAI）见文末演进节——**判据本身不变，变的是实现代价曲线**。

与 ES 的分工叙事（系列读者向）：全文/多维探索查询是搜索引擎的地盘——本系列
[Elasticsearch TDG](../Elasticsearch_The_Definitive_Guide/00-总览与阅读地图.md) 13–15 章的
"倒排+分片广播"与 Cassandra 2i 的"本地索引+环上广播"是同一类操作在不同结构上的两次
昂贵尝试；双写同步的当代答案叫 CDC（12 章与下文演进节）。

## 5.5 时间序列模式与 TWCS

书中时序场景（IoT/事件流）的标准解（⚠️）：

```sql
CREATE TABLE events (
  device_id text, yyyymm int,          -- 分区键=设备+月桶
  ts timestamp, event blob,
  PRIMARY KEY ((device_id, yyyymm), ts)
) WITH compaction = {'class':'TimeWindowCompactionStrategy',
                     'compaction_window_unit':'DAYS','compaction_window_size':1};
```

TWCS（2.1 出现 ⚠️）把"同时间窗的 SSTable 互相压实、过期窗整体 TTL 删除"变成结构保证，
解决 STCS 在时序数据上的"新旧混压写放大"。桶粒度选择=查询窗口 vs 分区大小的直接交易。
时序域的本系列对照端：`Time_Series_Databases`（#20，本波兄弟，登记于 [00 §7](00-总览与阅读地图.md)）。

## 核心概念速览（中英对照）

- **查询优先建模** — Query-first modeling：以访问模式而非实体关系为建模起点。
- **反范式** — Denormalization：同一事实多分区键重复存储，买读换写与双写一致性。
- **访问模式** — Access pattern：一组 WHERE 形态，一个表的建模单位。
- **分区键基数** — Partition key cardinality：分区键取值数量，决定集群利用率下限。
- **热分区** — Hot/large partition：基数低或无界增长的分区键造成的容量与流量黑洞。
- **时间桶** — Time bucketing：把时间高位（年月）并入分区键的限界手法。
- **TWCS** — TimeWindowCompactionStrategy：按时间窗分组压实，时序 TTL 的最佳搭档。
- **查找表** — Lookup/denormalized index table：用预生成的键序替代运行时 JOIN。
- **2i 判据** — Secondary index criteria：低基数+稀疏+小结果集的三门槛。
- **MV** — Materialized view：服务端维护的反范式副本，2.x 实验性 ⚠️。
- **双写对账** — Dual-write reconciliation：多表写不一致的批修复预案 ⚠️。
- **宽分区** — Wide partition：行数多的分区（相对字节超限），分页可驯。
- **分区内聚簇序** — Clustering order：DESC/ASC 选择决定"最近 N 条"是否免费。
