## 3.1 题纲

1. 三层模型：Cluster → Keyspace → Table（列族 ColumnFamily 的 CQL 化身位）
2. 分区（partition）是一切：partition key → 一片"排序表"；clustering columns 定分区内序
3. 列的真相：静态列、普通列、集合列、(frozen) UDT；不存在"列族的动态列"在 CQL 表的暴露面
4. 类型系统：基础标量（int/bigint/text/ascii/boolean/double/float/varint/decimal/timestamp/
   date/time/blob/inet/uuid/timeuuid/duration⚠️2.1+）；集合 set/list/map；元组与 UDT
5. 时间语义：timestamp/timeuuid 的选择、`now()`/`currentTimestamp`、TTL 与过期清理
6. 计数器 counter：类型即承诺（`COUNTER` 列独立表），CRDT 前夜的合并语义 ⚠️
7. keyspace 与副本策略：SimpleStrategy/NetworkTopologyStrategy 的建模后果
8. "表不是表"：CQL 表=按分区键分片的排序记录集，跨分区操作皆昂贵

## 3.2 分区的物理意义

`PRIMARY KEY ((a,b), c, d)` 里第一个元组是分区键：`hash(a,b)` 决定这行落在环上哪个节点、
其全部副本（07 章放置策略）；`(c,d)` 是分区内聚簇序——**同分区内**按 c,d 有序存储，
因此 `WHERE a=? AND b=? AND c>?` 才是"一次磁盘顺序读"，而 `WHERE c=?`（不带分区键）是
全环扫描。2.x 的默认分区上限告警（约 2GB 软限 ⚠️ 阈值随版本变）意味着：**分区键取值基数
必须是"无界事实"的对立面**——用 `userid` 而非 `status='active'` 当分区键。这条建模公理
在 [05-数据建模](05-数据建模.md) 全面展开，本章先把词汇立起来。

概念对照端：分区与哈希路由的通论在
[../设计数据密集型应用/06-分区.md](../设计数据密集型应用/06-分区.md)（其"按键分区 vs 按范围分区"
一节里 Cassandra 归按键分区+二级范围）；本册给出的是 CQL 语法化的同一件事。

## 3.3 类型系统速查（2.x 口径 ⚠️）

| 类别 | 类型 | 建模注记 |
|---|---|---|
| 标量-数 | int/bigint/smallint/tinyint/varint/decimal/double/float | varint/decimal 有编码代价，计数用 bigint |
| 标量-文 | text/ascii/varchar(同义)/blob | text 是 UTF-8 变长；blob 存原始字节 |
| 标量-时间 | timestamp/date/time/duration(2.1+ ⚠️) | timestamp=epoch 毫秒；date 允许"任意公元" |
| 标量-ID | uuid/timeuuid/inet | timeuuid 自带可排序时间性，审计列首选 |
| 布尔 | boolean | 三值逻辑仅 LWT 语境出现（08 章 IF 条件） |
| 集合 | set/list/map | 2.1 起可作分区/聚簇键者受限（frozen 整存）⚠️ |
| 复合 | tuple / UDT（2.1 引入 ⚠️） | `frozen<tuple<...>>`、`frozen<udt>` 非 frozen 自 3.x 才可用（跨代注意） |
| 特殊 | counter | 只许出现在 dedicated counter 表，不能与 mix |

**frozen 的语义坑（书中时代半新不旧）**：`frozen<list<text>>` 整值序列化为一列，
读改写代价=全列重写、不支持元素级更新；非冻结集合允许 `UPDATE ... SET tags[3]='x'` 的
元素级操作但有大集合膨胀风险。2.x 的默认建议仍是小集合+能拆表就拆表 ⚠️。

## 3.4 TTL、Writetime 与删除的形而上学

Cassandra 2.x 中每一列都是带时间戳的 KV（LSM 语义泄漏到数据模型层，06 章机制端）：

- `INSERT ... USING TTL 3600`：列级过期；过期由 compaction 清理，读侧不见。
- `WRITETIME col` / `TTL col`：时间戳可见性调试的双探针——排"谁最后写了这列"必备。
- `DELETE` 产生**墓碑（tombstone）**：删除不即时清盘，读放大与 GC 删除（gc_grace_seconds）
  的账本在 06/11 章；"DELETE 是写"是本章给新手的头号心智转换。
- timeuuid 与 `now()` 的混用陷阱：client-time vs server-time（2.2 起 `totimestamp/toTimeUUID`
  族函数）⚠️ 细节版本点。

## 3.5 Counter 与其他"反模式友好"特性

计数器表：`CREATE TABLE counts (id text, day int, c counter, PRIMARY KEY (id, day))`，
写只能 `UPDATE counts ADD c = c + 3 WHERE ...`。书中定位诚实 ⚠️：counter 是 AP 写入的
合并型特殊列（跨副本 partial replica 合并），读一致性低于普通列、性能开销大，
"能用普通列累加建模就别用 counter"。与之相邻的"特性但慎用"清单：二级索引 2i（低基数+
小分区场景，05 章的判词）、物化视图（2.1 实验 ⚠️，修复制约多）、批量 UNLOGGED/BATCHED
（08 章代价账）。

## 3.6 keyspace 的放置决策提前到建模期

副本策略写在表创建之前，是"数据模型的一部分"：

```sql
CREATE KEYSPACE prod WITH replication = {
  'class':'NetworkTopologyStrategy',
  'dc-west':3, 'dc-east':2, 'dc-east-spare':1   -- 跨 DC 副本数即写预算
};
```

DC 内 RF、跨 DC 冗余、CL 可选集（LOCAL_QUORUM 等）三者的耦合在 08 章算总账；建模期
就要问"这张表允许丢哪个 DC"——这是 CQL 与 Dynamo 家族"放置即模型"的传承（理论端：
[../设计数据密集型应用/05-复制.md](../设计数据密集型应用/05-复制.md) 的多数据中心节）。

## 核心概念速览（中英对照）

- **Keyspace** — Keyspace：表容器与副本策略挂载点，类比"database+放置策略"合一。
- **Partition key** — Partition key：定行物理归属的哈希输入，一切查询性能的总开关。
- **Clustering columns** — Clustering columns：分区内排序键，决定范围查询可用性。
- **Wide partition** — Wide partition：单分区多行大分区，合法但需行缓存/分页管理。
- **Frozen 类型** — Frozen type：集合/UDT 整体序列化为单列的存法，写放大换原子性。
- **UDT** — User-Defined Type：2.1 引入的命名字段组（record），`TYPE` 对象独立于表。
- **timeuuid** — Time UUID：版本 1 UUID，时间可排序，`now()` 的返回体。
- **TTL** — Time To Live：列级过期秒数，`USING TTL` 语法与过期 compaction。
- **Writetime** — Writetime：列的最后写入逻辑时钟，LWW 冲突裁决的显式探针。
- **Tombstone** — Tombstone：删除生成的遮蔽标记，读放大元凶之一（06 章机制）。
- **gc_grace_seconds** — GC grace：墓碑物理清理的宽限期，跨节点修复窗口保险。
- **Counter** — Counter：合并型计数列，专用表、代价高、语义 AP。
- **NetworkTopologyStrategy** — NTS：按 DC/机架计副本的放置策略，生产默认。
- **SimpleStrategy** — SimpleStrategy：全局 RF 计数策略，仅限单 DC/测试。
- **Secondary index (2i)** — Secondary index：分区内本地索引+全节点广播查询的低效形态。
