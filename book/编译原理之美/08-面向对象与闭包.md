# 第 8 章 面向对象与闭包：实现数据和方法的封装（讲 09、10）

> **一句话**：面向对象是「**数据 + 行为打包 + 名字查找按接收者分派**」；闭包是「**函数 + 定义处的环境**」。这两件事看起来是两章，其实是同一件事的两个侧面。

## 核心精讲

### 8.1 封装：把数据和操作打包

```java
// 这门小语言的类语法（示意）
class Counter {
    int count;
    void inc()  { count = count + 1; }      // this 指向接收者
    int get()   { return count; }
}
```

实现上只有三件事：

1. **类型定义**：类名 →（字段名列表 + 方法列表）的元数据。
2. **实例对象**：一个「字段值表 + 指向类型元数据的指针」。
3. **方法查找**：调用 `obj.get()` 时，先按 `obj` 的类型找到方法，再把 `obj` 当作隐含的第一个参数传进去。

### 8.2 `this` 只是语法糖

```java
// 教学示意：方法调用的等价展开（不参与构建）
obj.inc();
// 展开成：
invoke(TYPE_OF(obj), "inc", obj);      // 方法名 + 接收者 + 实参

// 方法体里的 this 其实只是「接收者形参」：
void inc(Counter this, ...) { this.count = this.count + 1; }
```

**这就是全部秘密**：面向对象 = 给函数加了一个隐含的第一个参数。一旦接受这个观点，「为什么 Ruby/Java 的方法不能脱离对象存在」这类纠结就消失了。

### 8.3 实例的内存布局

```
对象（Object）：
   +---------------------+
   | 类型指针 vtable/klass |----> class Counter { fields:[count]; methods:[inc,get] }
   +---------------------+
   | 字段 slot 0: count  |      实例数据
   +---------------------+
```

课程里「实现数据和方法的封装」这句话，落点就是上面这个结构：**数据在一边，行为在另一边，中间用类型指针连起来**。

### 8.4 静态作用域：环境的保存与恢复

这是本章真正的转折点。回想第 7 章的 `Environment`：

```java
// 教学示意：函数值需要连环境一起存（不参与构建）
class FunctionValue {
    AstNode body;
    Environment definingEnv;      // 关键：记住「定义时」的环境
    List<String> params;
}
```

调用时：

```java
Environment newEnv = new Environment(fn.definingEnv);   // 父 = 定义处
bind params;
eval body in newEnv;
```

### 8.5 闭包的正式定义

**闭包（Closure）= 函数体 + 定义它时的环境。**

```java
// 教学示意：闭包就是这两样东西打包（不参与构建）
Callable makeCounter() {
    int n = 0;                     // n 是 makeCounter 的局部变量
    return () -> { n = n + 1; return n; };   // 这个函数「捕获」了 n
}
// makeCounter() 返回后，栈已经展开，n 本该消失
// 但因为返回值带着 definingEnv，n 活了下来 —— 这就是闭包
```

课程的原话是这个意思（用户原摘录）：

> 我认为，**闭包是为了让函数能够在这种情况下继续运行所提供的一个方案。**

这句话是准确的补白：**闭包解决的是「函数需要活下去，但它依赖的变量按栈规则已经该死了」这个问题。**

### 8.6 「理解了原理，它就不反直觉了」

课程讲 10 的标题就是这个。闭包之所以反直觉，是因为我们把「函数」和「函数运行所需的环境」当成了两件独立的东西。**一旦承认「环境是函数的一部分」，闭包就只是普通的函数值**——就像 C++ 里带捕获的 lambda、Python 里保存自由变量的 `closure` 对象。

| 直觉版理解 | 机制版理解 |
| --- | --- |
| 「闭包会记住外面的变量」 | 「函数值里存了指向定义环境的指针」 |
| 「闭包里的变量会被共享」 | 「多个闭包共享**同一个** `Environment` 对象」 |
| 「闭包很重」 | 多一个指针，代价常常可忽略 |
| 「闭包导致内存泄漏」 | 确实：被闭包捕获的对象无法回收；这是真实的代价 |

### 8.7 动态作用域下的闭包

在动态作用域语言里，「环境」在函数调用时被重建，而不是沿用定义时的环境。于是：

```text
静态作用域：闭包看到的是「定义处的变量」  -> 可预测
动态作用域：闭包看到的是「调用时的变量」  -> 难预测
```

这就是为什么今天的工业语言几乎全选静态作用域——**可预测性是工程价值的来源**。

### 8.8 方法就是闭包

统一视角下的三种「带状态的函数」：

| 形式 | 本质 |
| --- | --- |
| 函数（第 7 章） | 代码 + 定义环境 |
| 闭包（本讲） | 同上，但捕获了可变的状态 |
| 方法（本讲） | 同上，外加一个隐含的接收者参数 |

**三者在机制上完全同构**，区别只在语法糖与查找规则。课程把它们分到两讲讲，是为了降低入门难度，但理解了之后应该把它们合并成一条思路。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「闭包 = 匿名函数」 | 匿名函数只是语法；闭包强调「捕获了环境」，C 的函数指针不是闭包 |
| 2 | 「闭包里的变量被每个闭包复制一份」 | 多个闭包**共享同一个 Environment 对象**；这才有了「计数器累加」这类用法 |
| 3 | 「闭包一定导致内存泄漏」 | 捕获不是引用计数外的泄漏；泄漏发生在**被捕获的东西长期存活且不再可达**时 |
| 4 | 「对象是数据 + 方法放在一起」 | 实际实现里数据与方法**分离**（数据 slot + 类型指针），方法是共享的 |
| 5 | 「`this` 是语言里的一个特殊关键字」 | `this` 只是被调用时绑定的**隐含第一个参数** |
| 6 | 🔧 本课程把封装与闭包分成两讲，容易割裂 | 建议合并理解：**方法就是带接收者的闭包**（本章 8.8） |
| 7 | 🔧 未提 **Rust 的闭包捕获语义（move / copy / ref）** | 2026 年讲闭包最值得对照的现代设计，比 Java 的 effectively final 更能说明问题 |
| 8 | 🔧 未提 **闭包与垃圾回收的关系** | 闭包捕获的对象进入可达性分析；讲 33 讲 GC 时要回看这一章 |
| 9 | 🔧 未提 **JS 引擎里的闭包优化** | V8 的 context 分配、context escape analysis 是「闭包」在真实引擎里的样子 |
| 10 | 🔧 未提 **LLM 生成闭包代码的高频错误** | 捕获修改过的局部变量、忘记 `nonlocal`/`global`、循环里的捕获陷阱 |
