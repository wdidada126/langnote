## 核心精讲

### 11.1 业务侧为什么需要编译器

课程在开篇词里给的清单就已经列好了：

- 编写界面模板引擎
- 为项目编写各种各样的 DSL
- 深度理解甚至编写 Spring、Hibernate、阿里巴巴 Druid 这样的工具

这三件事的共同结构是完全一样的：**读一段文本 → 建成树 → 按你的意图改写这棵树 → 输出新的文本或执行计划**。

### 11.2 案例一：透明地支持数据库分库分表（讲 14 原题）

目标：应用写 `SELECT * FROM t_order WHERE user_id = 1 AND status = 0`，框架自动把它改写成 `t_order_0` / `t_order_1` 上的两条查询，再合并结果。

```java
// 教学示意：分库分表改写的骨架（不参与构建）
class SqlRewriter {
    // 1. 解析
    SqlNode ast = sqlParser.parse("SELECT * FROM t_order WHERE user_id = 1 AND status = 0");
    // 2. 分析：哪些列是分片键、改写规则命中了吗
    ShardingContext ctx = analyze(ast);          // user_id 是分片键 -> 可定位到单库
    // 3. 改写
    if (!ctx.canRouteToSingleShard()) {
        ast = ctx.pushDown(ast);                  // 把分片条件下推
    }
    // 4. 生成
    List<String> rewritten = sqlGen.toSql(ast, ctx.shards());   // t_order_0 / t_order_1
    // 5. 执行与合并（课程里的「透明」就是指这一步对应用无感）
    Rows merged = executor.executeAll(rewritten).merge();
}
```

**三个真正的难点**（这才是课程的价值）：

| 难点 | 说明 |
| --- | --- |
| **解析的完备性** | 要支持 MySQL / Oracle / PostgreSQL 的方言差异，任何一种 `WHERE` 写法解析不了，用户就会踩坑 |
| **改写的正确性** | 不能只改表名；`SELECT COUNT(*)`、`ORDER BY`、`LIMIT`、`GROUP BY` 都要跟着改 |
| **改写的幂等与可回滚** | 改写本身也是一段程序，出错了要能回退 |

### 11.3 改写 AST 的三种手法

```java
// 教学示意：Visitor 改写 AST（不参与构建）
class ShardingRewriter extends SqlBaseVisitor<SqlNode> {
    @Override public SqlNode visitTableName(TableName ctx) {
        String logic = ctx.getText();                     // "t_order"
        if (shardingRule.contains(logic))
            return new ShardedTableName(logic, ctx.row);  // 换成带路由的表名节点
        return visitChildren(ctx);
    }
    @Override public SqlNode visitSelectItem(SelectItem ctx) {
        if (isStar(ctx)) return expandToColumns(logicColumns(logic));  // * 展开成具体列
        return visitChildren(ctx);
    }
}
```

| 手法 | 适用 |
| --- | --- |
| **替换节点** | 表名、函数名等「一对一换掉」 |
| **插桩（inject）** | 在 `WHERE` 前插入分片条件、在 `SELECT` 列表里插入去重列 |
| **局部重写** | 把 `IN (1,2,3)` 拆成 `OR` 链、把 `NOT IN` 改写成 `NOT EXISTS` |

### 11.4 能解析 ≠ 能改写

这是本章最该记住的一条经验：

```text
语法正确  ->  语义合法  ->  改写可执行  ->  结果正确
   ^            ^             ^
   |            |             +-- 课程讲 14 关注的正是这一层
   +------------+---------------+
              语法分析          语义分析
```

很多失败的中间件项目，都倒在第 1 步（解析不全）和第 3 步（改写出错），而不是第 0 步。

### 11.5 案例二：设计一个报表工具（讲 15 原题）

需求：业务人员写一段「报表公式」，系统据此算出结果。

```text
// 报表 DSL 的示意（不是某个真实产品的语法）
报表 本月销售汇总 {
    数据源: orders;
    维度: 区域, 品类;
    度量: 销售额 = SUM(price * count);
    筛选: date >= '2026-01-01' AND status = 'paid';
    排序: 销售额 DESC;
}
```

### 11.6 报表 DSL 的语法取舍

| 取舍 | 选轻 | 选重 |
| --- | --- | --- |
| 语法形式 | 仿 SQL 的表达式 | 独立的 XML/JSON 结构 |
| 类型检查 | 只查列名存在 | 推类型、查聚合与分组一致 |
| 执行方式 | 解释执行 | 编译成执行计划（见 11.7） |
| 扩展方式 | 加函数库 | 加优化规则 |

课程给出的判断是：**先定义一个能被类型检查的最小 DSL，再谈性能**。这与课程第一部分（词法/语法/语义）的顺序完全一致——**语法分析之后必须有语义分析，否则 DSL 只是字符串处理**。

### 11.7 从 AST 到执行计划

```java
// 教学示意：DSL -> 计划 -> 执行（不参与构建）
List<PlanNode> plan = optimize(buildPlan(ast));   // 优化 pass，见讲 27
// 常见 pass：
//   1. 谓词下推（push down filter）
//   2. 列裁剪（column pruning）：只取真正用到的列
//   3. 聚合上移 / 下移（join reorder 的简化版）
//   4. 常量折叠（见讲 27）
```

**这里出现了一个关键转折**：从这一章开始，「编译」不再只是「编译」——它变成了**查询优化 / 执行计划 / 规则引擎**这一整族技术的共同底座。

### 11.8 规则引擎：同一套技术的另一种外壳

规则引擎（Drools、Easy Rules、各类国产规则引擎）在技术上就是：

```text
规则文件（DSL）  ->  词法/语法分析  ->  AST  ->  规则集（带优先级）  ->  匹配 + 执行
```

它与报表工具、SQL 改写共享**同一个技术栈**，区别只在「改写目标是什么」：

| 外壳 | 改写目标 |
| --- | --- |
| SQL 分库分表 | SQL 语句 |
| 报表工具 | 计算表达式与聚合 |
| 规则引擎 | 动作与副作用 |
| 模板引擎 | 文本输出 |
| **AI 编译器（2020s）** | **计算图（graph）** |

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1970s | 报表生成器（RPG、SAS）用「公式语言」描述计算 |
| 1990s | 规则引擎兴起（CLIPS、Jess） |
| 2000s | Hibernate 的 HQL 解析器、Spring 的表达式语言（SpEL） |
| 2006 | 国内互联网进入分库分表大规模实践阶段，SQL 解析器的完备性开始成为真实成本 |
| 2011 | ShardingSphere 的前身（当当网的分库分表框架） |

| 2016 | ShardingSphere 进入 Apache；规则引擎国产化浪潮 |

| `triton-lang/triton` | **20,239★** | 把「改写」的目标从 SQL 换成 GPU kernel |

**2026 年的一条重要观察**：**LLM 大量生成 SQL 之后，「SQL 解析」从性能工具变成了安全刚需**。因为模型生成的 SQL 里会混入不可信的输入，任何一条执行前都必须经过**解析 + 白名单校验 + 改写**，而不是字符串拼接。这正是课程讲 14 的技术在 2026 年最刚性的应用场景。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「分库分表就是改个表名」 | 分片键分析、`COUNT(*)` 改写、`ORDER BY`/`LIMIT` 处理、结果合并，全都要 |
| 2 | 「解析器支持多少种方言不重要」 | **支持多少方言就是中间件的可用性上限**；这是讲 14 最真实的成本 |
| 3 | 「能解析就等于能改写」 | 见本章 11.4；改写本身是第二次编译，也要被测试 |
| 4 | 「报表 DSL 越像 SQL 越好」 | 业务人员要的是「够用且不会写错」，工程侧要的是「能被类型检查」 |
| 5 | 「规则引擎是另一套技术」 | 它就是 DSL + 解析 + 优先级调度，与本章两个案例同栈 |
| 6 | 🔧 本课程 2019 年上线，未提 **AI 编译器**这一最大的延伸 | 2026 年「改写计算图」是编译技术应用的最大战场：`apache/tvm`、`llvm/mlir`、`triton-lang/triton`，见 `14` |
| 7 | 🔧 未提 **Flink SQL / Calcite 的流批一体** | 讲 14 的 SQL 解析在流式计算里的现代形态 |
| 8 | 🔧 未提 **LLM 生成 SQL 后的注入与改写需求** | 这是 2022 年之后 SQL 解析器最大的需求增量 |
| 9 | 🔧 未提 **数据脱敏 / 数据防火墙**场景 | 基于 SQL 解析的脱敏规则，是国产中间件的重要卖点 |
| 10 | 🔧 未提 **WASM 沙箱**作为「改写目标」的新形态 | 2026 年很多「DSL 的执行」最终落到 WASM（见 13/14 章） |
