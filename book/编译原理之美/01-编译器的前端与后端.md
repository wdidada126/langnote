# 第 1 章 编译器的前端与后端（开篇词 + 讲 01）

> **一句话**：编译器的本质是一个**翻译管道**——把一种符号串翻译成另一种符号串；管道被「语义边界」切成**前端**（读得懂）和**后端**（跑得快）。理解这条分界线，你就知道该在哪里下手。

## 核心精讲

### 1.1 编译器就是一个翻译管道

> 教学示意，不参与构建、不编译、不运行。

```java
// 教学示意：编译器的经典阶段划分（不参与构建）
class CompilerPipeline {
    // 前端：与机器无关，只关心「源码有没有意义」
    TokenStream   lex(XxxLangSource src);        // 词法分析
    AstNode       parse(TokenStream toks);       // 语法分析 -> 抽象语法树
    AstNode       analyze(AstNode ast);          // 语义分析 -> 注解过的语法树
    // 中端：与机器无关、与语言也无关的那一层
    IrModule      emit(AstNode ast);             // 中间表示
    IrModule      optimize(IrModule m);          // 优化
    // 后端：与具体硬件相关
    AsmFile       codegen(IrModule m);           // 目标代码生成
    Binary        assemble(AsmFile f);           // 汇编 / 链接
}
```

五个阶段对应到本课程：

| 阶段 | 课程讲次 | 产出 |
| --- | --- | --- |
| 词法分析 | 讲 02 | Token 流 |
| 语法分析 | 讲 03、04、05 | AST（抽象语法树） |
| 语义分析 | 讲 11、12 | 带类型注解的 AST |
| 中间表示 / 优化 | 讲 24、26、27、28 | IR |
| 目标代码生成 | 讲 22、23、29、30 | 汇编 / 可执行文件 |

### 1.2 前端与后端：一条叫 IR 的缝

**前端**（Front End）回答「这串字符有没有意义」：词法、语法、语义、符号表、类型检查。
**后端**（Back End）回答「怎么让它跑得快」：IR 优化、指令选择、寄存器分配、指令调度。

课程把 01–19 讲给了前端，20–35 讲给了后端。这条分界线不是为了考试，而是因为：

- **前端可以被多语言复用**：你只要能生成 LLVM IR，就能白拿 GCC/Clang 的全部后端优化。这就是讲 25「后端技术的重用：LLVM 不仅仅让你高效」的底气。
- **后端可以被多目标复用**：同一份 IR，编译到 x86、ARM、RISC-V 只是换一个 `TargetMachine`。
- **前端的技术栈复用价值更高**：大多数工程师一辈子不写后端，但天天写前端（解析 SQL、解析配置、解析模板）。

### 1.3 GPL 与 DSL：本课最值钱的一句话

课程开篇就点出了这一对概念，这也是全书真正的落点：

| | GPL（General Purpose Language，通用用途语言） | DSL（Domain Specific Language，特定领域语言） |
| --- | --- | --- |
| 例子 | C、Java、Python、Rust | JSON（描述数据）、SQL（描述查询）、XML/HTML（描述标记）、Antlr 的 `.g4`、报表公式、规则引擎表达式 |
| 设计目标 | 图「表达一切」 | 图「表达这一件事」得心应手 |
| 代价 | 表达查询、模板、公式都很啰嗦 | 语言越多，维护成本越高，生态越弱 |
| 典型用户 | 程序员 | 程序员 + 业务人员 |

**DSL 的现实价值**：课程讲 14（分库分表 SQL 解析）与讲 15（报表工具）就是把编译技术直接当成「业务工具制造机」来用。宫文学本人的创业史（BPM、BI、电子表单、快速开发平台）本质上就是反复在「做一个 DSL，再让业务人员用 DSL 表达意图」。

### 1.4 解释型 vs 编译型：一个被讲错三十年的区分

严格来说，区分二者的不是「解释」和「编译」，而是**中间表示的存在形式与优化程度**：

```text
源码 -> 前端 -> IR -> [ 直接解释执行（脚本语言）  |  优化 + 生成目标码（编译型语言） ]
```

- 讲 05 的脚本语言 = 生成 AST 后**直接解释执行**（本章后面会给 REPL）。
- 讲 23、26 的脚本语言 = 生成 IR 后**编译成可执行文件**。
- Java 是两条路都走：先生成 `.class` 字节码（IR 的一种），启动后由 JIT（讲 34）再编译成本地码。

### 1.5 REPL 与自举：两个里程碑

**REPL（Read-Eval-Print Loop，输入—执行—打印的循环）** 是交互式语言的最小形态：

```java
// 教学示意：REPL 骨架（不参与构建）
while (true) {
    String line = console.readLine("> ");     // Read
    Object v = interpreter.eval(line);        // Eval
    console.printLine(format(v));             // Print
}
```

> **自举（bootstraping）**：先用一门已有的语言（比如 C 或 Java）写出编译器 v1，再用 v1 编译编译器的源码，得到编译器 v2；v2 能编译更复杂的语言特性，于是又能编译出更强的 v3……最终语言可以自己编译自己。Rust 的 `rustc`、Zig 的 `zig build zig`、V 语言编译 V，都是这一路数。

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1950s | 汇编器出现；编译技术以「机器相关的手写重写」形态存在 |
| 1960 | ALGOL 60 报告（Naur 主持）采用 BNF，**语言的语法有了机器可读的形式** |
| 1970s | 编译器构造工具（lex / yacc）出现，「写编译器」从手工作业变成半自动化 |
| 1990s | GCC 成为事实标准；开源编译器第一次拥有大规模协作可能 |
| 2000s | **中间表示的价值被重新发现**：GCC 的 GIMPLE、LLVM 的 LLVM IR 都在这十年定型 |
| 2013 | ANTLR 4 的 ALL(\*) 让「写前端」的成本再降一档 |
| 2016 | LLVM Foundation 成立，LLVM 从 Apache 项目独立（2016-03） |
| 2019 | 本专栏上线，把「前端技术可复用」这件事用 19 讲讲透 |
| 2020 | MLIR 白皮书，多层 IR 成为新范式 |
| 2022+ | Rust/Zig 的自举编译器成为「现代小型编译器的工程范本」 |
| 2023+ | PyTorch 2 的 TorchInductor 让「AI 编译器」进入主流框架 |
| 2025–2026 | LLM 让「做一个 DSL」的论证成本骤降，但**歧义与诊断质量**仍是硬骨头 |

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「编译原理 = 考试科目」 | 编译技术的 80% 价值在**前端**：解析配置、解析 SQL、写 DSL、写报表公式 |
| 2 | 「解释型和编译型的区别是解释 vs 编译」 | 真正区别是**中间表示是否被优化、是否被落到目标码**；Java 两条路都走 |
| 3 | 「DSL 就是造一门新语言，很重」 | 轻量 DSL 只需一个 `.g4` 语法文件 + 一个解释器，一天能做完 |
| 4 | 「前端做完就结束了」 | 前端产出的 AST 是后面所有优化与静态分析的**唯一入口**，AST 设计不好，后面全返工 |
| 5 | 🔧 本课程 2019 年上线，未涉及 **AI 编译器** | 2026 年必须补：`apache/tvm`、`llvm/mlir`、`triton-lang/triton`、`pytorch/pytorch` 里的 TorchInductor |
| 6 | 🔧 未区分「编译器的组件化」趋势 | 讲 25 已提 LLVM 重用，但应更明确：**2026 年你更少写编译器，更多是「组合编译器组件」** |
| 7 | 🔧 未提 **Rust/Zig 的自举编译器**作为工程范本 | 建议补：rustc 用 Rust 自举、zig 用 Zig 自举，是「小型现代编译器」最好的照抄对象 |
| 8 | 🔧 未提 **LLM 与编译技术**的关系 | 2026 年的现实：大模型能自动生成 `.g4`，但**歧义消解与错误诊断质量**仍是人类专家的活 |
