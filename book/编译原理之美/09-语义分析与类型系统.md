## 核心精讲

### 9.1 语义分析的三个任务

| 任务 | 例子 |
| --- | --- |
| **名字解析** | `x = 1; x = x + 1;` 中的 `x` 指向同一个声明；`y` 未声明 → 报错 |
| **类型检查** | `1 + "a"` 类型不匹配；`if` 的条件必须是布尔 |
| **上下文相关约束** | 必须先声明后使用、`return` 只能在函数里、标签必须唯一 |

### 9.2 属性文法：语义规则的骨架

课程原摘录里记了这四个术语，它们是理解语义分析的关键：

> **类型推导（Type Inference）**
> **类型检查（Type Checking）**
> **类型转换（Type Conversion）**
> **属性文法（Attribute Grammar）**

属性文法把语义动作挂到产生式上：

```text
产生式： F -> id ( E )
语义规则： F.type = lookupType(id.name)
           F.code = gen("param " + E.type)
```

两种属性：

| 属性类型 | 计算方向 | 例子 |
| --- | --- | --- |
| **综合属性（synthesized）** | 自底向上，子节点 → 父节点 | 表达式的类型 |
| **继承属性（inherited）** | 自顶向下，父/左兄弟 → 右子节点 | 作用域链、期望类型 |

```java
// 教学示意：综合属性 = 返回值（不参与构建）
Type typeOf(Binary b) {
    Type l = typeOf(b.left), r = typeOf(b.right);
    if (l == ERROR || r == ERROR) return ERROR;        // 容错：不因为一处错就停
    if (l.isNumeric() && r.isNumeric()) return l.widestOf(r);
    throw new TypeMismatch(b.op, l, r, b.line);
}
```

### 9.3 类型系统三件套

| | 定义 | 典型语言 |
| --- | --- | --- |
| **类型推导** | 从表达式的结构算出它的类型 | ML、Haskell、Rust 的部分场景、Swift |
| **类型检查** | 判断一个程序是否类型正确 | C、Java、Go（ Soundness 各异） |
| **类型转换** | 两个类型不匹配时自动/强制转换 | C 的隐式转换、Java 的装箱 |

### 9.4 类型表达式

```text
类型构造子：
  int        基本类型
  string     基本类型
  boolean    基本类型
  array[T, n]   数组
  record { name: T, ... }
  function(T1, T2) -> T3
  union(T1, T2)      （C 的 union / 可选类型）
```

### 9.5 简单类型检查算法

```java
// 教学示意：一个玩具级类型检查器（不参与构建）
class TypeChecker {
    SymbolTable syms;

    Type check(AstNode n) {
        if (n instanceof IdRef) {
            Symbol s = syms.lookup(((IdRef) n).name);
            if (s == null) throw new SemanticError("未定义的符号", n);
            return s.type;
        }
        if (n instanceof NumLit)     return Type.INT;
        if (n instanceof StrLit)     return Type.STRING;
        if (n instanceof Binary)     return checkBinary((Binary) n);
        if (n instanceof Assign)     return checkAssign((Assign) n);
        // ...
        return Type.ERROR;                  // 关键：返回 ERROR 而不是抛异常
    }

    Type checkBinary(Binary b) {
        Type l = check(b.left), r = check(b.right);
        if (l == Type.ERROR || r == Type.ERROR) return Type.ERROR;
        if (!l.isNumeric() || !r.isNumeric())   // 本课只支持数值二元运算
            throw new SemanticError("运算符 " + b.op + " 不能用于 " + l + " 和 " + r, b);
        return l.isWiderThan(r) ? l : r;
    }
}
```

> **一张小表很重要**：玩具类型系统的能力边界，决定了你能不能写出有用的程序。
> 课程的类型系统属于**「够用的玩具级」**——它支持数值运算与基本类型，不支持子类型、泛型推断、多态，这是本章「常见误区」里要修正的重点。

### 9.6 隐式类型转换（Coercion）

```java
// 教学示意：算术提升（不参与构建）
Type widen(Type t) {
    if (t == Type.INT)  return Type.LONG;
    if (t == Type.LONG) return Type.DOUBLE;
    return t;
}
```

规则的三条经验：

1. **窄 → 宽自动升**，且自动升的链条不要太长（C 的整型提升是历史包袱）。
2. **宽 → 窄需要显式**（`as` / `(int)` / `static_cast`），否则丢精度太隐蔽。
3. **字符串与数值之间不要隐式转**——这是 Java 里最著名的坑（`+` 重载）。

### 9.7 重载与多态初探

| 形式 | 何时决定 | 例子 |
| --- | --- | --- |
| **静态重载（Ad-hoc）** | 编译期按签名 | C++ / Java 的方法重载 |
| **参数多态（Parametric）** | 泛型参数化 | 模板 / 泛型 |
| **子类型多态** | 运行期按实际类型 | 虚函数（讲 10） |

### 9.8 上下文相关处理（讲 12）

「上下文相关」指的是：**同一个语法形式，在不同上下文里含义不同，或者需要额外信息才能理解**。

```java
// 教学示意：先声明后使用（不参与构建）
void declare(IdRef id) {
    if (syms.lookup(id.name) != null)
        throw new SemanticError("重复声明：" + id.name, id);     // 上下文 1：声明处
}
void use(IdRef id) {
    if (syms.lookup(id.name) == null)
        throw new SemanticError("未定义的符号：" + id.name, id); // 上下文 2：使用处
}
```

课程讲 12 的典型议题：

| 议题 | 例子 |
| --- | --- |
| 先声明后使用 | C 的隐式声明 vs Java 的强制先声明 |
| 定义与使用顺序 | 函数是否可以在定义前递归调用（前向声明） |
| 声明位置约束 | `static` 只能在模块顶层 |
| 名字的唯一性 | 局部变量不得遮蔽外层（或允许，但要有提示） |

### 9.9 语义错误与容错

好的编译器**不会因为一处错就停**：

```java
// 教学示意：错误累积（不参与构建）
class Diagnostics {
    List<String> errors = new ArrayList<>();
    void error(String msg, AstNode at) { errors.add(at.line + ":" + at.column + " " + msg); }
    boolean hasErrors() { return !errors.isEmpty(); }
    void reportAndExitIfAny() {
        if (hasErrors()) { errors.forEach(System.err::println); System.exit(1); }
    }
}
```

ANTLR 4 的语义谓词（`{...}?`）也是同一思路：**在语法分析阶段就用代码做条件判断**。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「语义分析就是检查类型」 | 还有**名字解析**和**上下文相关约束**，类型检查只是其中一部分 |
| 2 | 「语义分析发生在语法分析之后」 | 真实编译器里两者**交织**：ANTLR 的语义谓词、yacc 的语义动作都在分析过程中跑 |
| 3 | 「类型错误应该一报就停」 | 工业级编译器**累积错误**；玩具检查器应在出错处返回 `ERROR` 类型继续 |
| 4 | 「隐式转换很方便」 | C 的隐式转换是历史包袱；现代语言（Rust、Swift）大量取消隐式数值转换 |
| 5 | 🔧 本课程的类型系统是**玩具级**的 | 缺子类型（subtyping）、缺泛型推断（Hindley-Milner 只提一嘴）、缺泛型擦除/替换细节 |
| 6 | 🔧 未推荐 **TAPL（Types and Programming Languages）** 作为进阶读物 | 这是类型系统唯一公认的现代教材，本课程止步于够用 |
| 7 | 🔧 未提 **Rust 的借用检查器** = 作用域 + 类型系统的合流 | 2026 年讲类型系统最值得对照的现代设计 |
| 8 | 🔧 未提 **Python 类型提示 / mypy** 的规模 | 一门动态语言的主流工业界选择了「加静态类型」，这是类型系统最大的一次现实胜利 |
| 9 | 🔧 未提 **LLM 修编译错误**这一 2022 年后的新场景 | 诊断文本 + 可验证修复，是 AI × 编译技术最易落地的方向 |
| 10 | 🔧 未提 **语义谓词与属性文法的现代形态** | ANTLR 的 `{...}?` 谓词、yacc 的语义动作，就是属性文法在真实工具里的样子 |
