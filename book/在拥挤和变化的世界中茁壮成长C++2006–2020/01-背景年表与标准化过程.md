## 核心概念速览（中英对照）

- **零开销原则** — zero-overhead principle：What you don't use, you don't pay for；What you do use, you couldn't hand-code any better（论文开篇引 D&E 1994）
- **直接映射硬件** — direct map to hardware：语言构造到机器设施的直接对应，与零开销抽象并列为 C++ 双重焦点
- **三种矛盾诉求** — three contradictory demands：把语言变简单！立刻加这两个 essential 特性！别破坏我的代码！
- **年表** — Chronology：1979 C with Classes → 1985 首个商用版 → 1989–91 标准化启动 → 1998 C++98 → 2011/2014/2017/2020
- **列车模型** — train model：C++11 后采纳的发布制——"列车准点发车，没赶上的等下一班"，3 年一班＋Intel tick-tock 大小年交替
- **委员会的委员会** — design by a confederation of committees：WG（CWG/LWG/EWG/LEWG）＋SG（SG1 并发…SG21 契约）＋全国代表机构的多层共识体
- **方向组** — Direction Group (DG)：2017 年应各国 NB 负责人呼吁设立，5 人、只在一致同意时发声的咨询组
- **提案检查清单** — Proposal Checklists：几乎每个提案都会被问的 18 问（问题是谁的？库方案够吗？破坏 ABI 吗？可教吗？进 top-20 吗？）
- **规范而非实现** — a specification, not an implementation：标准的作用是约束多家实现（至少 4 前端：Clang/EDG/GCC/MSVC）彼此一致

## 一、论文的定位：为什么"如何活下来"本身就是结论（§1）

动机：2006 年的 C++ 已工业使用 20 年，内含 1970 年代初的 C 遗骸与 2000 年代初的新特性；
同期新编程模型涌现、硬件架构转向、多语言围剿。论文的问题意识是摘要那一句——
**"一种没有真正商业支持的、老得多的语言，是如何茁壮成长的？"**

精读要点（史实）：
1. C++ 之于用户的完整形态不是一个 ISO 文档，而是一个工具集七件套：语言、标准库、其他库、海量（常是陈年）代码、工具（含其他语言）、教学、社区——论文声明将考察这些"零件"的相互作用。
2. Bjarne 反复强调的一个反直觉论点：**"程序员想要简单语言"是流行的神话**。学习与教学场景确实要简单；一旦转向交付与维护大型应用，诉求就变成完备支持、稳定性（兼容性）与熟悉感——"人们总是把熟悉误认为简单，有得选时宁选熟悉"。
3. 三条情绪化诉求的三角张力是全书骨架：简单化／加特性／别破坏代码。后面每一章的"裁决视角"都落在这三角上。

## 二、1979–2006 背景与 2006 年的至暗时刻（§2）

§2.1–2.2 是对 HOPL-II/III（→ [../C++语言的设计与演化/03-年表、标准化与关注使用.md](../C++语言的设计与演化/03-年表、标准化与关注使用.md)）的压缩复述：第一个十年（classes、虚函数、重载、引用、const）；第二个十年（抽象类、多重继承、异常、模板；标准库 iostreams）。§2.2.2 点出关键史实：**早期年代"标准库的贫乏"**——库很多但少有人共用、多为私有，开源尚未普及，社区缺共享底座。

§2.3 "C++ in 2006" 是本章最重的史实段：
- Bjarne 在 2006 HOPL-III 论文里列 39 项提案、预测前 21 项进 C++0x；结果前 25 项中 **24 项**进了 C++11（他列为"2007 年待投票"的 22–25 也全部通过），26–39 则**连 C++17 都没进**；唯一"预测外"的是第 10 项 concepts——"一段漫长悲伤、在 C++20 迎来幸福结局的故事"（→ 本目录 04 章）。
- 2006 年 C++ 使用量**有史以来首次下降**（Bjarne 最佳估计 −7%，在误差内，但足以恐慌）；Java 仍在涨、C# 重金营销。"托管语言教条"四连击：底层交给 C/汇编、上层交给 GC 语言、托管语言让普通人多产/专家贬值、深度平台绑定才是大厂正道。
- 转折（论文归因）：约 2005 年单核性能停止提升，"每瓦性能"成为关键度量——软件经济性重新青睐高效语言，熟练开发者凭"利器"可再获数量级优势。另有平台锁定反弹：Android-Java/iOS-ObjC/Windows-C# 逼得 Adobe、Google、Microsoft 把苛刻应用主体写回 C++＋薄接口层。
- 生态面坏消息：专业纸媒死亡（DDJ 撑到 2009）、会议被"面向对象"综合会议吞并、教育塌陷（美国高中 CS 考纲从 C++ 突改 Java；大学 C-first＋重继承的教法拉低质量）——Bjarne survey 二十本教材后放出那句名言："**If that's C++, I don't like it either!**"，催生 2008《Programming: Principles and Practice Using C++》。
- Boost 的定位被专门一节讲：1998 年 Beman Dawes 建"C++ 库仓库网站"，后来 regex/thread/shared_ptr/variant/filesystem 等由 Boost"少年级标准库"转正。
- 2018 年估计开发者约 450 万（较 2006 +50%），⚠️ 口径为 JetBrains/Kazakova 2015 调查转述。

§2.4 Other Languages 是"影响论"解毒剂：**C++ 很少直接抄别的语言**——影响经由共同祖先与共享观念冒泡上来；auto"老如群山"（1983 年就实现过）、tuple 来自 boost::tuple、regex 抄 Unix/JS（经由 Boost 并致谢）、future 来自 Multilisp、`<=>` 灵感含 strcmp/Perl/Python/Ruby、无栈协程主要学 F#。反方向输出：Java/C# 的泛型语法、dispose 惯用法（析构的 GC 近似品）、D 的 constexpr（Walter Bright 听 Bjarne 亲讲早期设计）、Rust 的所有权灵感之一、C11 的内存模型与多处语法。名场面一句："有趣的是，如今 C++ 常被指控把这些想法抄自 Rust。"

## 三、标准委员会：过程即设计（§3）

§3.1：标准是规范不是实现；1990 年代咨询过世界级专家后**放弃形式化规范与参考实现**——语言复杂度＋硬件利用优化使两者"要么太贵太杂，要么简化到帮不上最难的忙"。选择"多实现＋大型委员会的半有序混沌"而非"单一组织的 monoculture"风险。

§3.2 组织史实：ISO/IEC JTC1/SC22/WG21（1991 成立；之前是 1989 的 ANSI 组）。C++17/20 时代每次全会到会最多 250 人（会员约为两倍）、代表 100+ 机构（Apple、Bloomberg、CERN、EDG、Google、IBM、Microsoft、Morgan Stanley、Nvidia、Red Hat…）；全部志愿者、无带薪秘书处，"代表我自己"是合法身份。官方职位只有三个：Convener（Herb Sutter，2002 起，中间 2008–09 由 PJ. Plauger 短暂接任）、Project Editor（C++11 Pete Becker／C++14 Stephanus du Toit／C++17/20 Richard Smith）、Secretary（Nina Ranns）。会议节奏：一年 3 次全会，08:30–22:00 连轴五天（论文原话："通常成员从早餐聊到午夜……会议在夏威夷 Kona 这类好地方时，委员会外似乎没人相信一场会议居然不是休假"）；WG 与 SG 主席多半在饭点加会。共识不是多数——WG 处理后全会所求 9:1/8:2，且会议召集人可裁定 8:2 **不算共识**。1998 后曾缩为一年两会。修订周期史：ISO 惯例十年一修 → "这个特性等不起"逻辑 → C++0x 变 C++11（距 C++98 十三年）→ 此后列车模型 3 年＋大小年（train model 与 Intel tick-tock 两个比喻的出处与适用边界都在 §3.2）。

§3.3 是论文最有独立价值的一节：Bjarne 列出 **17 种委员会病症**（"这不只是 design by committee，这是 design by a **confederation of committees**"）并逐个给案例：

1. **拖延**——nullptr 也走了三年；concepts 现行方案 6 年、契约从起步到失败 6 年、networking 15 年未完；
2. **孤立特性偏好**——成员评个案不评体系（C++17 无统一主题的病根，→ 05 册）；
3. **迟到的替代方案**（late alternatives）——老提案临近表决，新想法以"近乎同等权重"入场，提案者被迫转入防御：concepts、结构化绑定、digit separators、operator dot、modules、协程、契约全上过名单；
4. **热情偏向新事物**——"新而未经检验的总显得更好"；Bjarne 怕**星期四下午的 EWG**：人人疲惫，小提案溜过（显式条件测试、inline variables）；
5. **过度自信**——"许多人太确信自己的观点"；
6. **实现时机两难**——先实现被细节绑死，先投票靠盲飞；
7. **特性交互被忽视**——"一次只看一项新增是危险的"（结构化绑定加位域的膨胀案，→ 05 册）；
8. **体量与干扰**——2018 秋会前邮件量"**三倍于莎士比亚全集**"；
9. **精确规范之累**——再小的特性也要条文化，时间不可挪用；
10. **经院哲学**——细枝末节的形式争论吞噬议程；
11. **方向缺失**——"C++ 长大后想成为什么"无人能答（→ 06 册 DG）；
12. **专注一隅**——成员只代表自己公司的用例；
13. **原则误用**——D&E 原则被贬为"rules of thumb"后任意引用或任意忽略；
14. **亲专家偏见**——enable_if/traits 通行无阻 vs concepts 寸步难行（"Joe Coder 之问"，→ 04 册）；
15. **聪明病**——偏爱精巧方案胜过朴素可用方案；
16. **不愿妥协＋优先级缺失**——"**整个会议花在 digit separators 上的时间比 range-for 还多**"；
17. **完美主义／少数否决／抱团小团体**——operator dot、networking、异常规约死于 mission creep；constexpr/operator dot/modules/协程死于少数否决；Conway 定律式后果：any/optional/variant 接口互异（→ 05 册）。

解药叙事：DG 的设立、大量无薪琐事承担者（点名 Jens Maurer 数十年记笔记）。替代制度评估：小核心组最理想但无钱无权无制度惯性；公司控制不可取（ROI、朝秦暮楚、偏好差异化优势）；千人开放投票不可行；BDLF（终身仁慈独裁者）"从未与 C++ 相关"。收尾引丘吉尔论民主。
- 与 D&E 方法论对照 → [../C++语言的设计与演化/02-语言设计规则与演化方法论.md](../C++语言的设计与演化/02-语言设计规则与演化方法论.md)：D&E 的"决策记录"在委员会时代变成"检查清单＋reflectors 档案"，方法论从个人档案学升格为组织流程。

§3.4 提案检查清单：18 问全文值得背几问——"问题是什么、服务哪种用户（新手/专家）？库方案够不够？为什么必须在标准里？迁移要多久？实现了吗、有用户反馈吗？编译期/运行期开销？破坏现有代码/ABI 吗？与现有和其他新特性的交互？可教吗？影响标准库哪部分？会不会引发后续扩展需求？……**这是全体社区 top-20 的改进吗？top-10？某个子社群的 top-3？**"Bjarne 注脚：实际提案 rationale 普遍很弱，而"坏提案偶尔溜过——原因是提案人的热情＋反对者的分心、礼貌与疲惫"。

## 四、g++ 实测：三条诉求中"别破坏我的代码"的实证

选论文 §1.1 年表起点特性（类、虚函数、流）构造一段纯 C++98 代码，验证六档标准输出逐字节一致——这正是"稳定性是几十年系统的本质属性"的可执行证词：

```cpp
// s01.cpp 摘要：Shape 基类+Circle 派生（虚函数/构造析构）、内建数组与隐式 int→double 窄化
// （即论文 11.3 所说"数千亿行依赖的 C-ism"）混排
Shape* ps = new Circle(2.0);
cout << ps->name() << " area=" << ps->area() << '\n';  // Circle area=12.5664
```

已实测 g++ 15.2：`-std=gnu++98 / c++11 / c++14 / c++17 / c++20 / c++23` 六次编译运行，输出全部为

```
Circle area=12.5664
sum=6
```

## 五、2020–2026 裁决视角

- 列车模型兑现：C++23 于 2024-02 批准（准点，未因任何"等不起"停摆）；C++26 按 2028 档期推进——Bjarne 当年"可预测发布周期比任何单一改进重要"的坚持赢了两次。
- 2006 年的托管语言教条被后续现实逐条否定：GC 语言在服务器能耗与端侧性能上撞墙，Rust 的兴起反而验证"零成本抽象＋确定性析构"路线（论文 §2.4 的"反向输出"段落有了续集）。
- §3.3 病症学在 2024–2025 的新验证：反射（P2996，→ [wg21.link/p2996](https://wg21.link/p2996) ✅302）以"函数式+单类型"新方案**整体替换**旧方案进 C++26；契约（→ [wg21.link/p2900](https://wg21.link/p2900) ✅302）仍在 SG21 多路线缠斗——late alternatives 与少数否决两种病同框复发。

## 最新演进与工业实践

- **C++23/26 补位**：发布纪律延续（C++23＝P2361 等小步快跑＋library fundamentals V2/V3）；2017 年的 DG 持续产出方向文件，本目录 07 章"权利法案"是其制度遗产。WG21 到会人数 2024–2025 维持 200–300 人量级，SG 序列新增 SG22（Safety，2022，硬化的工业出口——见 07 章）。
- **经典论文对读**：HOPL-II（10.1145/155360.155375）→ HOPL-III（10.1145/1238844.1238848）→ 本文（10.1145/3386320）三篇的 2.x 节构成互文的"自引纠偏链"：每篇都修订上一篇的预测（本文 §2.3 修正 HOPL-III 的 39 提案清单即是范例）。
- **工业界对应**：提案流程的活教材可在 <https://www.open-std.org/jtc1/sc22/wg21/docs/papers/>（WG21 1989–2020 全档，论文 §3.2 点名"年增 500+ 篇"）与 isocpp.org/std 复核；abseil/folly 等大厂库如今以"LEWG 提案孵化器"身份运作，正是 §3.3"委员会里应用_builder 太少"诊断的五年后回应。
- **现代重估**：本目录全系列的"否决理由"素材库都在 §3.3/§3.4——读任何一章前先记住 18 问，特性存亡几乎都能在其中找到判词。
