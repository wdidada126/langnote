## 核心概念速览（中英对照）

- **大海迷航** — Lost at Sea：Bjarne 给 C++17 的判词——"约 21 个语言特性＋13 个库组件，但没有一个称得上 major；找不到统一主题，只是一堆被投票机器抛进语言的'好点子'"
- **major 的定义** — "majorness"：Bjarne 自定标尺——"改变我们思考编程与组织代码的方式"；他直言 C++11 有此 web，C++17 没有，"这让我非常不安"
- **动态异常规约** — Dynamic exception specifications（`throw(T1,T2)`）：1989 年为让异常过关的"首付"；2010 年废弃（Gregor），2017 年**全票**移除——C++ 史上删除旧特性最干净的一次
- **noexcept 规约** — noexcept Specifications：0/1 版异常规约（详见 03 册 §4.5.3）；廉价、可判定、可优化；但"在 throw 与 handler 之间加一个 noexcept，就能让原本正确的程序在运行时 terminate"
- **异常的类型系统支持** — Type System Support for Exceptions：异常进类型系统=函数类型的一部分——被否决的真实理由是**重编译脆弱性**与 C 回调；Bjarne 数出"四种异常方案＋指针函数组合=16 种alternatives"的恐怖图景
- **两轨理想** — Two mechanisms：异常管"稀有或调用方处理不了"，错误码管"就地可处理"；Bjarne 的著名天真问句："**一个错误要多罕见才算 exceptional？**"——答案是 it depends
- **N+1 问题** — the N+1 problem：新错误处理方案进来，旧方案不会消失（异常把流行方案从 7 种变 8 种；(value,error) 对已有"十几二十种变体"）
- **构造函数模板参数推导** — Constructor Template Argument Deduction (CTAD)：Spertus/Smith 攻克——`pair p("Hi!"s,129)` 不再需要 make_pair  workaround；与 scoped_lock 组成 C++17 罕见的"互相支撑"范例
- **结构化绑定** — Structured Bindings：Kona 2015 **午餐前 45 分钟**起死回生；位域需求进场后设计复杂度翻倍——"孤立评估一项新增是危险的"标本
- **variant / optional / any**：三兄弟"案例教科书式的设计失败"——Bjarne 原话："委员会决定标准化这三个类型。不幸的是，三者被当作**用例互不相交**分开讨论……它们是经典的 design by committee"
- **网络库 / asio** — Networking：Kohlhoff 2003 动手、2005 入 Boost、2006 提案 TR2、2018 才成 TS——"生产使用 15 年后我们仍要至少等到 2023"；executors 是它的连环扣（"the best is the enemy of the good"再引用）
- **点运算符** — Operator Dot（`operator.()`）：1990 Adcock 首提案→1991 Koenig/Stroustrup→2004 Powell/Gregor/Järvi→2014/2016 Stroustrup/Dos Reis——"三十年、六份提案、许多讨论与实现工作，**我们一无所有**（we have nothing）"
- **统一调用语法** — Uniform Call Syntax (UCS)：2014 Sutter 与 Bjarne 各自提案随即合并；"接口稳定性"论战（Google 系 vs "该担忧被**极度夸大**"）；2016 战死，遗言：modules 落地后或可借"模块名可见性"复活
- **缺省比较 / 三路比较** — Default Comparisons / `<=>`：Smolsky 2014 递刀；本册只讲到"进入 C++20 成 spaceship"，完整"意外后果" saga 在 06 册 §9.3.4

## 一、§7 错误处理：一篇"四十年辩护词"

§7 开场先立总纲："错误处理过去是、我看将来也是激烈争议之地。许多人持有强烈意见——部分建立在多种应用领域的坚实经验之上——过去约五十年发展出许多不同技术。这是性能、通用性、可靠性三方的诉求极易互相冲突的领域。"紧接着是那句可贴在所有架构评审墙上的判词："**与 C++ 的常态一样，问题不在于我们没有解决方案，而在于我们有很多个**（the problem is not that we don't have a solution, but that we have many）。用单一机制满足 C++ 社区的多样需求从根本上很难；但只看问题的一个子集，人们就常以为自己已经拿到了解药〔Stroustrup 2019a〕。"——本节全部四小节都是这句话的展开。

7.1 从 C 的遗产讲起，论文给出三个原型："sqrt(d) 负数时设 errno==33、getchar() 到文件尾返回 -1、malloc 失败返回 0"——返回码、特殊值、全局态、局部态、回调五类手段。1980 年代早期用户发现这些**令人困惑且不够用**，于是 (value,error-code) pair 流行："加剧了多样与混乱"（论文原话 adding to the variety and confusion）。Bjarne 举 make_window 返回 Result 的典型片段，然后列三重代价：主流业务逻辑与大量罕见怪异错误纠缠（"有些系统里错误处理占代码多数也是最复杂部分"）；ABI 税——"许多 ABI 连小结构体都不用寄存器传，不但信息翻倍，还慢一个数量级**，且此问题 2020 年仍在，尤其为 C 代码设计的嵌入式 ABI"；**构造函数没有返回值可放错误码**，加上当年流行的大型复杂类层次，子对象构造错误的处理复杂易错。还有贯穿一切的一条：人忘记检查——"这在 2020 年仍是错误的主要来源"。异常（1988–89 设计、ARM〔Ellis & Stroustrup 1990〕记载、进 ANSI C++ 基线文档）的设计还被供应商语言额外捆住："C++ 函数 f() 调 C 函数 g()、g() 又调 C++ 函数 h()、h() 抛给 f() 接"——此场景直接排除了"给所有函数签名加异常传播参数"或"隐式往返回类型里塞返回码"两派实现方案。异常＋RAII 解决了最难的问题（构造失败、错误远在千里之外），代价"到 1990 年代中期通常低于 3%，有时甚至比替代方案更便宜"。但 Bjarne 罕见自我检讨："异常从来不是没有争议的，**我低估了它的争议潜力**（I underestimated their potential for controversy）。"

7.2 的坦白程度是全文最高的一节。不适合异常的真实场景三条：内存小到运行时支持挤掉应用功能的系统；工具链无法保证 throw 后及时响应的硬实时（引 Lockheed Martin 2005 手册）；靠多台不可靠计算机、就地崩溃重启反而是正解的系统——"所以几乎所有实现都有 no-exception 开关"。error-code 无解的场景六条：构造失败（没有返回值，纯 RAII 得换成显式对象状态检查）；运算符（`++`、`*`、`->` 无处塞错误指示，否则只能写 multiply(add(a,b),c) 这种残废记法）；回调（调用方要能承接被调方五花八门的错误，且回调常是 lambda——§4.3.1）；非 C++ 代码（不经 C++ 的函数没法传播）；**调用链深处新增错误种类**（每个中间函数都得准备处理或传播，如"为网络而生的程序之外"冒出网络错误）；人忘记检查返回码——"精巧的保证检查方案要么不完整，要么在漏检发生时依赖异常或 terminate（引 Botet & Bastien 2018）"。再列"实践中的污点"：烂指针代码的人把矛头指向异常而非旧代码；不懂 RAII 的人把 try-catch 当 if-then 用（"更丑、更大、更慢"）；实现低效（MS 结构化异常泛化、GCC 为保 backtrace 抛后走两遍栈、一套机制服务多语言"一样糟"）；异常相对越来越慢——因为非异常路径被拼命优化，而 Bjarne 认为异常本身还有巨大优化空间（引 Gor Nishanov 2019：协程相关的简单优化在 Windows/Linux 上报告过**高达 1000 倍**提速；空间问题更难；Renwick 等 2019 的实验有希望）。**最狠的一条**："为了异常过关我们加了异常规约……宣称的可维护性从未兑现，啰嗦与开销一字不差兑现——而当年喊得最响要规约的人，后来参与了 Java 的设计（Ironically）。（→02 册 §2.2 的史前对应）"另有一条技术账：catch 按类型匹配使 throw/catch 与 RTTI 实现互相纠缠——不用 RTTI 也得为它付内存、动态链接下类型匹配难优化、"实现总是为最罕见的复杂情形调校"；而静态可分析类层次的嵌入式场景本可做常数时间匹配〔Gibbs & Stroustrup 2006〕；异常类层次进标准库后"鼓励人连最简单的场景也用层次"，雪上加霜；且异常已进平台 ABI，早期过度设计再也改不动。还有人坚持"单一错误手段"、把错误码的问题贬为"小不便"；还有人相信最坏场景与不公平对比喂出来的低效谣言——"关于异常代价的严肃研究太少。**我怀疑关于异常的神话比任何事实影响都大**（myths...more influence than any fact）"。净效应：社区分裂成 exception 与 non-exception 阵营——"no-exceptions 事实上是一门方言，而方言正是标准要避免的东西（§3.1）；方言对个别组织是优势，对整个 C++ 社区则伤害代码与能力的共享"。零开销原则是否被违反（Sutter 2018 质疑）一节，Bjarne 先复述"对任何错误都终止的程序，一切错误处理都是开销"的抬杠、再引 1989 年 Koenig 的论证（异常表可驻虚拟内存、不抛就无运行时代价）后承认：无虚拟内存且内存稀缺的场景确是认真的问题；当年零开销的口径是"**与同等检查严谨度的错误码方案相比**无额外开销"。

7.3/7.4 是本册实测样例的正面战场。noexcept 是废弃动态规约后的"简化廉价替代"（详见 03 册 §4.5.3）：它让担忧性能者安心、能通过削减控制流改善优化——"除非程序员又用返回码检查把分支加回来"；大量天然 noexcept 的底层函数（多数 C 函数）。但正反手都成立：函数不会抛则免 catch（简化），不会抛却可能失败则必须另找报错通道（复杂化）。最关键警告："在 throw 与其 handler 之间的路径上加一个 noexcept，就能让原本正确的程序在运行时 terminate。维护期为函数加 noexcept 可以使 previously-correct 程序失败。"Bjarne 顺势提醒一段被遗忘的初史：把错误**永远不导致无条件 abort**正是当年加异常的重大理由之一——"main() 到抛出点之间的任何代码都可接管；尤其支持 terminate 前做本地清理（刷输出缓冲、往日志里追加一条错误报告）这一重要用例"。（→03 册 §4.5.3 noexcept 的 0/1 压缩史）7.4 讲"把异常搬进静态类型系统"为何三十年不通过：直觉收益明确（更强类型检查、函数自文档、更易优化），否决理由是**重编译脆弱性**——异常集进函数类型后，任何一次"可能抛出的集合"变更会强制重编译所有调用方，"在大多数程序由许多独立开发的库拼装的世界里，这等于灾难性的脆弱与不可管理的依赖〔Stroustrup 1994〕"。函数指针是第二道锁：C 风格泛型代码（qsort 的比较器）与 GUI 回调都靠函数指针——"你要么总要求被指函数有异常、要么永不接受、要么两者兼顾——后者除非加类型探询或按异常重载，几乎不可行；就算 C++ 内部能办，与 C 的交互怎么办？C++ 函数指针怎么递给 C？C 回调进依赖异常的 C++ 程序长什么样？"而且老异常不会消失，于是场上并存四种方案：错误码、编译期检查异常〔Sutter 2018 又提〕、现行异常、noexcept——"只有现行异常与非局部错误码两样不动类型系统与 ABI 调用约定。**幸运的是，需要两个函数指针作参数的函数不多——否则要面对 16 种组合**；若再像现行异常那样接受不同异常类型，混沌才完整。"Bjarne 补一句：同样的问题在现代 C++ 会换皮重现于"带成员函数待调用的对象、函数对象、lambda"这些回调机制上。结论（WG21 背书）："把异常加入静态类型系统会带来脆弱性、代码复杂度显著上升、严重不兼容与 C 交互问题。**这一判断在 1989 年就已获得认同（appreciated）**。"

**7.5 "回归基础"**：理想世界只有两轨——异常管"稀有或调用方处理不了"，错误码管"就地可处理"（常伪装在易用的测试操作里，或以 (value,error) pair 返回）。Bjarne 的现场样本 user()：五行代码（vector 初始化、cin 循环 push_back、make_unique<Shape>(read_shape(cin))、Smiley_face{Point{0,0},20} 构造）全是小概率错误的温床——内存耗尽、读错误、构造失败（Smiley_face 类层次深处）、unique_ptr 防泄漏。"若改用错误码，这个函数里至少要插**五次显式检查，源码量翻倍**，各构造函数内部还有几处；没有 RAII（及与异常的整合）会更糟。**平均而言更多代码意味着更多错误**，尤其当新增代码搅乱控制流时。拿小例子论证的人常无视这点——小例子里'就多一个测试'无关痛痒且不易忘。"反例也给足：`ifstream f{"Myfile"}; if (!f)` ——错误码就该藏在流状态里，方便就地检查。所以两轨理想成立，但 Bjarne 自认不知如何到达："**(value,error) 变体广泛使用的有十几二十种**（std::map::insert() 就是一种伪装），2018 年 WG21 还在新增〔Botet & Bastien 2018；Sutter 2018b〕。就算委员会选定一版，外面仍有至少一打各拥大批忠实信徒、动辄数百万行难改代码的方案。"性能论战部分他开出处方："跑个简单实验：递归进调用链 N 层再报错。错误罕见（1:1000 或 1:10000）且链够深（100、1000 层）——异常快得多；深度 1、错误率 50%——显式测试完胜。**这里的大差距（big）是整数倍，不是百分之几**——据我所知没有半点严肃的研究做不到同时在两类现实场景里各让一方大胜。"决定胜负的是调用深度×错误概率。那句"天真的、但可能有用的问句"："**一个错误要多罕见才算 exceptional？**"——答案 it depends（代码复杂度、硬件、优化器、异常实现都掺和）。史实一针："C++ 异常的设计假设至少在 **1:100 这一档**——即'传播错误指示'远比'就地显式处理'常见。"空间问题比时间问题更难；对"凡本地处理不了就立即终止"的系统，可以想象实现直接在 throw 时 terminate——但只要错误需要传播并处理，取舍难题就不会消失。任何收拾残局的方案都会撞上 **N+1 问题**（§4.2.5）："给定 N 种错误处理法，有人想出第 N+1 种，旧的一种都不消失——异常的引入可视作把流行方案从 7 种加到 8 种"；组织级还有 N*M 恶化版："M 个独立开发的程序各用 N 个库，就是 N*M 问题"〔Crowl 2015a 分析〕。基础库作者受伤最深——"他们不可能知道用户偏好，而用户偏好可能很多样"。制度化落地的唯一样本是 filesystem 双接口（§8.6）：每个操作两个函数，一抛一不抛——"bool create_directory(const path&); / bool create_directory(const path&, error_code&) noexcept;——啰嗦，只讨好二选一的人；注意 bool 返回值是特意给的，免得人总 try 或总查 ec"。而"文件系统对罕见错误用异常（Bjarne 按语：以我的看法完全正当）"也说服不了认为异常本质有原罪的人——因为它要求异常支持必须在场。结尾彩蛋：当年反对者竟嫌异常**不够**通用——相当数量的人认为 resumption 语义必不可少〔Stroustrup 1993〕，Bjarne 赌当年若允许恢复语义，异常处理至少慢**一倍**——"看，问题从来不是特性不够，而是方向没有共识。"

## 二、g++ 实测：动态异常规约之死与 noexcept 的 terminate（s05/s05b）

```cpp
// s05b.cpp —— 1993 年的"首付"
void old_style(int n) throw(std::runtime_error) {   // 动态异常规约
    if (n < 0) throw std::runtime_error("neg");
}
```

已实测 g++ 15.2：`-std=gnu++98` 编译**通过**（rc=0，"它真的活了二十多年"）；`-std=c++17` 报错：

```
error: ISO C++17 does not allow dynamic exception specifications
  note: 'throw()' replaces 'throw(...)' ...
```

——2010 废弃、2017 全票移除，在本机上能"亲眼看到行刑记录"。

```cpp
// s05.cpp —— noexcept 的双刃
void risky(int n) noexcept {
    std::vector<int> v{1,2,3};
    std::cout << "size=" << v.size() << '\n';
    if (n) { std::cout << "即将违约...\n"; v.resize(static_cast<size_t>(n) - 100); } // length_error
}
int main() { risky(0); }        // 无异常路径：正常退出
```

已实测 g++ 15.2（`-std=c++20`）：编译期即警告 `-Wterminate: 'throw' will always call 'terminate'`——§7.3 "noexcept 把 throw 变 terminate" 被编译器静态抓到；运行输出 `size=3`。把 `risky(0)` 改为 `risky(50)` 后：

```
size=3
即将违约...
terminate called after throwing an instance of 'std::length_error'
  what():  vector::_M_default_append        // exit code = 3
```

——异常在 noexcept 边界被"处决"，本地清理（flush 日志等 §7.3 场景）全部跳过。这正是 §7.2 所列"两阵营"各自论据的机器可复现版本。

```cpp
// s05c.cpp —— C++17 四件"互相支撑"：CTAD(8.1) / 结构化绑定(8.2) / scoped_lock(8.4) / 折叠表达式(§8 清单)
using namespace std::string_literals;
std::tuple<int, double, std::string> unpack() { return {7, 2.5, "ok"}; }
template <class... Ts> auto sum(Ts... xs) { return (xs + ...); }      // 折叠表达式
int main() {
    std::pair p{"Hi!"s, 129};               // 8.1 CTAD：p2 在 C++14 里是 error
    auto [n, d, s] = unpack();              // 8.2 免先声明再 tie() 赋值
    std::mutex m1, m2;
    { std::scoped_lock lck{m1, m2};         // 8.4 CTAD+scoped_lock：一次锁俩、无死锁
      std::printf("locked together\n"); }
    std::printf("%s %d %.1f sum=%.1f\n", s.c_str(), p.second, n + d, sum(1, 2, 3.5));
}
```

已实测 g++ 15.2：`-std=c++14` 编译**失败**——恰 3 个 error（`missing template arguments before 'p'`＝CTAD 缺席、`'scoped_lock' is not a member of 'std'`、连带 `p` 未声明）＋2 个 warning（结构化绑定与折叠表达式作为 `-Wc++17-extensions` 被 GCC 当扩展**预先放行**——"GCC 提前塞私有扩展"的老毛病，对照 03 册 §4.5 注）；`-std=c++17` 零诊断通过并运行，输出：

```
locked together
ok 129 9.5 sum=6.5
```

`-std=c++20` 亦通过。这个样例把 Bjarne 在 8.1 说的"C++17 罕见的**互相支撑**特性"（CTAD×scoped_lock 组成 `lock_guard lg{m};` 式简化）与 8.2 的"tie() 之痛"一次跑齐：把 CTAD 行还原成 C++98 口径就得写 `pair<string,int> p(string("Hi!"),129)` 或 `make_pair` workaround——正是论文 8.1 开头三连例（p0/p1/p2）的原文剧情。

四案对照小结（本册三组实测各打中论文哪条论点）：

- s05b（动态异常规约）→ §7.2 "为异常过关付的首付"：gnu++98 可编译、C++17 直接 error——废弃（2010）与移除（2017）的分界在同一台 g++ 15.2 上可见。
- s05（noexcept 违约）→ §7.3 "noexcept 把 throw 变 terminate、跳过本地清理"：编译期 -Wterminate 警告＋运行期 exit code 3 双重印证。
- s05c（CTAD/结构化绑定/scoped_lock/折叠）→ §8.1/8.2/8.4 "互撑范例"与"tie() 之痛"：C++14 与 C++17 之间的 3 error 就是 make_pair 时代的墙。
- 未实测者照旧挂账：N*M 问题、resumption 双倍减速猜想、"异常表驻虚拟内存"（无 Windows 页面锁实验环境，⚠️ 均维持论文口径转述）。

## 三、§8 C++17 八小节：21 个"好点子"的成色检验

开篇设定：C++14 是 minor 修订，C++17〔Smith 2017〕**本应**是 major。Bjarne 的核心问句是"Why did all of that hard work not lead to more significant improvements?"——流程还在、社区更老练更大更热情，产出却没升级。数字：**约 21 个语言特性**（看怎么数）＋**约 13 个库组件**，且"远不是全部——有些小到难以一句话描述"。论文点名带出处的语言特性：CTAD＋推导指南（8.1）、结构化绑定（8.2）、inline variables〔Finkel & Smith 2016，救 header-only 库的静态成员〕、折叠表达式〔Sutton & Smith 2014，简化变参模板〕、条件内显式测试（8.7）、保证拷贝消除〔Smith 2015〕、更严的表达式求值顺序〔Dos Reis 等 2016b，防顺序坑〕、auto 作模板实参类型〔Touton & Spertus 2016，值模板参数的推导〕、三个防错属性 [[maybe_unused]]/[[nodiscard]]/[[fallthrough]]〔Tomazos 2015〕、十六进制浮点字面量〔Köppe 2016a〕、constexpr 里的 if〔Voutilainen & Vandevoorde 2016〕；库侧：optional/variant/any（8.3）、shared_mutex/shared_lock/scoped_lock（8.4）、parallel STL（8.5）、filesystem（8.6）、string_view〔Yasskin 2014，不可变字符序列的非拥有引用〕、数学特殊函数〔Reverdy 2012：Laguerre/Legendre 多项式、beta、Riemann zeta〕。总判词（速览已引）："找不到任何统一主题……只是一堆在能凑出投票多数时被抛进语言和标准库的'好点子'。**这让我非常不安**——哪怕我喜欢其中单个特性也一样不安。**没有总体计划**——这对未来是不祥之兆〔Stroustrup 2018d〕，Direction Group 的成立（§3.2、§9.1）正是 WG21 的应对之一。"major 标尺的定义也在这一节："让编程方式与代码组织方式为之改变"；对照 C++11"致密互撑之网"，C++17 只"Minor ways 帮到多数人"。Bjarne 还点名五张"如果进了就是 major"的遗珠票：concepts（§6.3.8）、networking、operator dot、UCS、缺省比较、coroutines（§9.3.2）——"我怀疑它们若获通过，每一个都会是 C++17 最重要的特性之一；它们契合'C++ 该成为什么'的连贯愿景（§9.2）"。末段为火车模型辩护："也可以辩称 C++17 只是通往 C++20 的踏脚石——但委员会的讨论几乎没流露过这个意图，注意力始终钉在单个特性上。**我甚至听过'火车模型排除了长期规划'的说法——它没有排除**（it does not）。"逐册点评其"互相支撑"程度：

- **8.1 CTAD**（Spertus/Smith 2015）：三十年之问——"为什么函数模板能推参数而构造函数不能"。论文开场三连例：`pair<string,int> p0(string("Hi!"),129)` 无推导；`auto p1 = make_pair("Hi!"s,129)` workaround；`pair p2("Hi!"s,129)` 在 C++98/11/14 全是 error"模板参数缺失"。Bjarne 自白：初设模板时就考虑过构造推导，**被"怕歧义"吓退**；技术障碍最终被 Spertus/Smith 翻越，p2 从此合法，make_pair 退化为惯用法而非必需品。推导指南（deduction guides）是歧义逃生门（8.3 有实例）。Bjarne 定调："这是 C++17 里罕见的**互相支撑**范例——类型（pair/tuple）与并发（锁）代码同时显著变简。"可惜各简化是按案批准而非整体设计，"补类型推导规则之洞"的工作持续到 Spertus 等 2018〔见后续册〕。
- **8.2 结构化绑定**：Sutter/Stroustrup/Dos Reis 2015 提案，两大动机——简化记法＋**消灭 uninitialized 变量**的残余源头（Bjarne："消除 Core Guidelines 里倒数第二个未初始化变量来源才是我进场的主因，记法只是次爱的"，→07 册 §10.6）。对手戏是 C++14 的"生得方便拆得丑"：`tuple<T1,T2,T3> f()` 配 `{a,b,c}` 返回很漂亮，拆解却要么 `get<0>(res)` 起别名（间接、还有一份 copy），要么走 `tie(x,y,z) = f()`——"要先分别声明并写出类型；留下用前未赋值窗口和先初始化后赋值的开销；**而且多数程序员不知道 tie() 存在、或嫌它太怪不敢在生产代码用**。"Sutter 的解法镜像返回语法：`auto {x,y,z} = f()`，对任何三成员 struct 有效。生死时刻：提案**迟到**，Kona 2015 正是冻结 C++17 特性集的会议，"EWG 散会前剩约 45 分钟到午饭，我判断大家想看它——来不及把 Herb 从另一个组拎来，我代讲。Minutes 记为 *Encouragement by acclamation*（全场欢呼通过）。Then, the real work started."之后三场拉锯：①Chandler Carruth 等人指出要服务非 tuple/plain-struct 类型（如 complex 不暴露表示），解法是让用户自定义 `get<N>()`" effectively pretending a tuple——有效但要点不雅的样板，到 C++20 也没有实质简化；②位域/数组返回值的支持需求进场（"late alternatives"病理学 §3.3 现场发作），"最终设计**至少比原提案复杂一倍**"；③要不要允许 `auto {int x, const double* y, string& z}` 显式写类型——Voutilainen 表述最力（不写伤可读性/可维护性/易错），Bjarne 逐条拆：与反 auto 的论点同源、类型不匹配算 error 还是允许转换（char[20]→string？）众说纷纭、且结构化绑定本该是**零开销别名**、任何改变表示的转换都引入显著开销、写类型会让它比现有替代方案更啰嗦——推导派胜出。记法之战：原提案用 `{}`，Carruth 与 Vandevoorde 坚持"**{} 意味着作用域**、会混淆"，改成 `[]`；Bjarne 判"小改动但**我认为是个错误**"——临时改出与属性记法（[[fallthrough]]，§4.2.10）的语法小摩擦，且他 2014 年就展示过用 `{...}` 承载函数式模式匹配的通盘设计〔8.3〕，"结构化绑定本是为嵌入那个通盘方案而设计的"。结语标本："单独评估一项新增是危险的；孤立的最后一刻改动除非嵌进更大的图景否则危险，且会以'求完整'之名催生 bloat。**我至今不确信'结构化绑定该支持位域'值回它的复杂度**。"
- **8.3 variant/optional/any**：前史从 C 的 union 讲起——"最早年代起就有类型'时分复用'同一内存，编译期运行期**零检查**，程序员自己保证用法一致、**错得令人作呕地规律**（with sickening regularity）"；熟手用类包住 union 自救，Boost 给出三件套 optional/variant/any，效用已被多语言反复证明。判词（速览已引）：委员会决定标准化三者，"不幸，三者的设计被**当作用例互不相交而分开讨论**；语言直接支持（而非库支持）的可能性似乎压根没被认真考虑——结果是三个形态迥异的库类型，**经典的 design by committee**"。取值的三套互异记法摆进论文：`*var1`（解引用 optional）/`get<int>(var2)`（当 tuple 拆 variant）/`any_cast<int>(var3)`（转换 any）——"资深程序员会习惯，**但本不该有东西要人习惯**"。访问机制要 std::visit，前置是那段 overloaded 样板（`template<class...Ts> struct overloaded : Ts... { using Ts::operator()...; };` ＋推导指南一行）——Bjarne 批注："**这段样板真该进标准**。它对吃透变参模板（§4.3.2）与推导指南（§8.1）的人才算简单"；给了 overloaded 才能对 variant 做"按类型的 switch"（论文附 vector<variant<int,long,double,string>> 遍历示例）。判词收尾："variant 们确实在解决重要问题，**只是不优雅**。"更优解是函数式模式匹配——2014 年 11 月 UIUC 会议上 Bjarne 讲 pattern matching 设计〔Solodkyy 等 2014，底子是 Texas A&M 与 Solodkyy/Dos Reis 的研究 2013〕，纯库实现已达可比拟函数式语言的性能、同时覆盖封闭集（代数数据类型）与开放集（类层次），目标之一就是**消灭 visitor 模式**〔Gamma 等 1994〕；"欠缺的是可接受的语法。我那次报告的目的就是勾起兴趣、立长期目标"——兴趣勾到了，C++17 完工后开工〔Murzin 等 2019/2020〕，"也许能赶 C++23"（→07 册 §11.5）。
- **8.4/8.5/8.6/8.7**：scoped_lock 一次锁任意多个互斥量且无死锁、shared_mutex/shared_lock 补上读写锁（"读者们共享、写者独占"；论文点名 C++11/14 **竟然没有**读写锁——"明显的严重遗漏，成因是提案压力与处理时长"；Bjarne 盖章"这是'make simple things simple'哲学的好例子，我和许多程序员都好奇过 **what took them so long?**"，并点题"记法靠 8.1 的构造推导才简化到 `shared_lock lck{mx};`"）；parallel STL 只给每算法加一执行策略参数 `sort(par_unseq,begin(v),end(v))`——"从用户视角没有比'请把此算法并行做掉'更简单的接口；从实现者视角，有具体接口而无串行约束就是机会"。Bjarne 记下阻力："委员会里有些反对，大多来自**想要更复杂专家接口的人**；有人 seriously 怀疑这么简单的方案可行、主张推迟。"缺陷也直书：只覆盖 STL 算法（find_any/find_all 还缺）、**没有标准取消手段**（POSIX 当年对一切 cancellation 的绞杀后坐力，§4.1.2；C++20 协作式取消补，§9.4）、向量化的长线价值——"SIMD 是 2017 年后硬件仍在**单线程**性能上给出戏剧性增长的少数领域之一"；range 版并行算法没赶上 C++20（`sort(par_unseq, v)` 要等 C++23）， interim 可自写 adapter（论文示例直接用 C++20 concepts：`template<class T> concept execution_policy = is_execution_policy_v<T>;`——"毕竟标准库是可扩展的"）；filesystem（Dawes 2002 Boost→最热门 Boost 库之一→2014 改头换面成 TS→再改进入 C++17；难点清单——并发、多自然语言、多操作系统；关键抽象 path 屏蔽字符集与文件名法——"名字可以是俄语或阿拉伯语、Linux 或 Windows 记法"；论文示例 do_something() 用 exists/is_regular_file/directory_iterator 走目录，**try 包起来防的是 TOCTOU**："exists(p) 检查后、细看前文件被人删掉"这类罕见错误；双错误接口见第一节，正是 §7.2 两轨理想的制度化）；条件内显式测试〔Köppe 2016b〕`if (auto p = f(y); p->m>0)`——Bjarne 立场罕见："**很多小提案**是危险，哪怕每个都能帮到某人。这是对 C++98'声明即测试'（if (auto pd = dynamic_cast<Derived*>(pb))，§2.2.1）的泛化，问题在泛化是否**显然到值得**——**我的答案是不**。结果是我被投票否决了（我被投票否决的一个不算罕见的例子）。"他认为显式测试放 if 体内更难被忽视、对不天天写 C++ 的人惯例有价；反过来此特性受欢迎于"每个函数返回都得测错"的编码风格——"我强烈不喜欢那种风格（§7.5）"。附送事故标本："有人激进翻新代码：见 `if (auto p = f(y)) { if (p->m>2) ... }` 立刻改写成 `if (auto p = f(y); p->m>2)`，宣称更短更优雅——**然后崩在 p==nullptr 上，原代码不崩**。不论得到什么好处，我们确实造出了新的犯错机会。"该测试也进了 switch/while；C++20 又扩到 range-for 初始化〔Köppe 2017c〕。
- **8.8 四大遗珠**（Bjarne 判断："我怀疑它们若进 C++17，每一个都会是最重要特性级"；static reflection 在 SG 里推进不算遗珠但同源）：networking/asio 时间线（2003 动工→2005 Boost→2006 提案→2018 才 TS，"13 年重度生产使用仍没赶上 C++17，更糟是进 C++20 的努力也**停摆**——生产使用 15 年后还要至少等到 2023"；病根是 executors 连环扣——"如何泛化 asio 内外处理并发的方式仍在认真讨论，Hoberock 等的 executors 提案有广泛支持、有人盼进 C++20"；判词："C++20 没有 executors 和 networking，是我反复引用的'**the best is the enemy of the good**'的又一例"）；operator dot 三十年史——1984 起 -> 可重载养出智能指针，众人想要 . 可重载养出**智能引用**：让 `x.f()` 变 `x.operator.().f()`，从 handle 与 value 分界（Ref 类示例：构造/析构/operator.()/rebind() 归 handle，其余落到 *p——`x = X{9}` 意思是 `(*x.p) = X{9}`）。死结在**隐式 dot 要不要走重载**："用户定义类型上 ++x 本解读为 x.operator++()；若该类型还有 operator.()，++x 该不该变成 x.operator.().operator++()？"1991 Koenig/Stroustrup 试解，**被原始提案人 Adcock 本人激烈反对**；2004 Powell/Gregor/Järvi 再试，再度僵死；2014 Stroustrup/Dos Reis〔N4173，✅ 已实测 wg21.link 可达〕"我认为更完备更讲理的一版"进场，Bjarne 记录死因很有层次：措辞问题与暗角是老毛病，**真正原因是委员会对'智能引用'过于兴奋诱发 mission creep**——Gaunard/Kühl 2015（要求所有定义者写重度模板元编程，其核心是 operator.() 应**依被访问成员而定**的二元观——S/D 其实考虑过二元并判定"复杂度爆表、且必须与 -> 对齐成一元"）与 Tong/Vali 2016（基本对象化：新继承形式＋隐式转换）分头抢滩；2016〔P0416R1，✅ 已实测 wg21.link 可达〕后原提案**其实没被否决**——EWG 通过、**从未送上全委员会投票**，缺乏新输入在竞争案之间凝聚共识，提案人又被 concepts 与 modules 及"正职"抽身。判词："operator dot 是'委员们对 C++ 是什么、该成为什么没有共享愿景'的头号标本（§9.1）。**三十年、六份提案、许多讨论与实现工作——我们一无所有（we have nothing）**。"（→06 册 DG 的由来）UCS——2003 concepts 首篇就顺手点名"统一调用语法"需求〔Stroustrup & Dos Reis 2003b〕：写泛型库必须二选一 x.f(y)/f(x,y)，用户被迫服从库设计者的选择，各家标准库为此供养"成对函数"之疫（begin(x) 与 x.begin() 都要能用）；"运算符从来看得见成员与自由函数两种解析（x+y）——**我本该在 1985 年前后、委员会还没被细节缠死前，从运算符案例推广定调，但我没能推广**"。2014 Sutter 与 Bjarne 各自提案（动机分裂——Herb 一半为 IDE 自动补全、偏向对象记法；Bjarne 为泛型编程、偏向数学记法 f(x,y)），随即合体〔Stroustrup & Sutter 2015〕。第一关"兼容性"（可破坏现有代码：择优匹配或歧义化）被说服接受**只查一侧**的降级版：x.f(y) 先看类内、找不到才试 f(x,y)——不破任何存量。第二关却爆出"**稳定接口末日论**"：Google 系主张"凡依赖重载解析的接口都不稳定——新增函数可改变现有代码含义"。论文摆出 print 重载实例：`void print(int); void print(double); print('a');` 打整数值；中途 `void print(char);` 一出，`print('a')` 改打字符。Bjarne 拆台："任何程序都可能被各种新增声明改变含义；重载的日常正名恰是**补语义更对的候选（常为修 bug）**；我们从来强烈反对在程序中途加 print(char) 这种改语义的重载——**这个'稳定'定义不现实**。而且类成员早有同款问题——答复是'类的成员集是封闭的所以可控'；我指出用命名空间同样能把绑定于类的自由函数集圈出来〔Stroustrup 2015b〕。"混战中 C# 式扩展方法（UK 代表团 Coe & Orr 2015）、John Spicer 领衔的"该发明第三种记法"相继冒头——Bjarne 至今不服："我仍然看不出**再加一种记法（如有人提议的 .f(x,y)）统一了什么**——那只会是 N+1 问题的新成员（§4.2.5）。"提案战死后被请回炉："等 modules 落地后再审视——把自由函数的名字查找范围限制到其首参类的模块"或可复活，但"我看那也治不好（依我判断）**被极度夸大的**接口稳定性担忧"。结尾放出全论文最自我批判的一句（速览已收）："回头看，我根本不该引入面向对象记法。f(x,y) 足够，还白送多重方法、省掉 visitor 模式这坨 workaround〔Solodkyy 等 2012〕。"**再次**归因"共享愿景缺失"（§9.1）；default comparisons——C/C++ 双双没有缺省比较的考古层：`struct S{char a; int b;}` 能初始化能赋值、`s1==s2` 却 compile error，根源是内存布局的 **padding "unused bits"**——逐位比可能 false；"若有那圈填充位，C 本会有缺省相等。1980 年代初我和 **Dennis Ritchie** 讨论过，俩人都忙、作罢。复制不受影响（照抄所有位既朴素又传统）。允许赋值却不允许比较——为 1970 年代的实现效率辩护合理，**对 2010 年代就古怪了**：优化器早已能处理，而我和很多人一样厌倦了解释'为什么不给你比较'；尤其 STL 算法动辄要 == 或 <，简单数据结构不手写 operator==/operator< 就进不了算法。"2014 Smolsky 递刀：`= default` 逐个声明六行——"对症，但**为了说'我要缺省比较'写六行长定义**实在次优"；且"侵入式（不能改的类就加不了）"等技术问题尚在，竞赛开场。Bjarne 自己写分析＋提案〔Stroustrup 2014c/2014b：简单类**自动**获得比较〕，败在两个细节鬼：给"简单"下定义很难；**Jens Maurer** 揪出用户自定义比较与缺省比较跨作用域共存的 nasty scope 问题（"先用了缺省 ==、之后另一个作用域又定义 operator==()，什么意思？"）。需求越堆越高（"缺省比较的性能要等于朴素写的三路比较"）、Crowl 2015b 把总序/弱序/偏序全景分析了一遍——EWG 公认分析精妙，"但他需要一台时光机才能把机制装进 C++"。2017 终局 Sutter〔部分基于 Crowl〕端出三路比较 `<=>`（多语言皆有之物）生成全家桶：`friend std::strong_order operator<=>(S,S) = default;` 一行拿到 ==/!=/</<=/>/>=（`s1<=>s2` 得 0）——非侵入版也可写成自由函数；提案里本带"简单类**隐式**获得 <=> "选项，"不出所料，那些认为事事显式更安全的人把它投死了"。Bjarne 的 bitter takeaway："我们没得到让平凡例子对新手自然工作的设施，得到的是让专家精心雕琢微妙比较的** elaborate 设施**。"奇观级细节："`<=>` 是我能想起的**近年来过关最容易**的提案——尽管当时**没有可用实现**、且对标准库影响巨大。我猜是多年比较论战让人觉得'总得做点什么'，加上 <=> 覆盖面宽、和其他语言熟面孔合拍。代价是可预测的——它制造了大量意外（§9.3.4），包括当初坑掉 == 提案的那类查找难题。"预告："将来我多半还会再提为简单类缺省定义 == 与 <=>。**新手与偶尔写 C++ 的人配得上那份简单**（The novice and casual users of C++ deserve that simplicity）。"2017 年提出的 <=> 错过 C++17、苦修后进 C++20（§9.3.4，本册只讲到"递刀"，"意外后果" saga 在 06 册）。

## 最新演进与工业实践

以"出版后又过了 6 年"（2020→2026）的裁决视角清点：

- **§7 的最大变量：std::expected 落地 C++23**。P2505R5（wg21.link/p2505 ✅302，"Monadic Functions for std::expected"）——Bjarne 数出的"十几二十种 (value,error) 变体"第一次有了**标准版**：`std::expected<int, std::string>` 携 then/and_then/map 单子接口，正是"就地可处理错误"的官方答案；本目录 07 册附第二个实测样例（s07：C++20 编译失败→C++23 通过）。异常阵营未再扩张：动态规约尸体无人喊冤；GCC/Clang 的 -fno-exceptions 阵营与异常阵营在 2023 后出现缓和信号——Google 公开风格指南修订允许在满足 ABI 约束的项目中使用异常（工业实践转向，⚠️ 本笔记未直接核对指南原文措辞）。
- **§8.8 遗珠的六年后账**：networking 仍未全量进标准——Bjarne 那句"至少还要等到 2023"的预言落空为"更久"：其前置条件 executors 执行模型已随 std::execution（P2300R10 ✅302）定于 C++26， asio 系网络库本身截至 2026 仍是 SG4 在途工作（⚠️ 单一"终结提案号"本笔记未逐一实测，不列）；operator dot 的**精神续作** deducing this 成功进 C++23：P0847R7（wg21.link/p0847 ✅302，"Deducing this"）——智能引用喊了三十年没等来 operator.()，等来的是 `this Self&&` 参数，代理类终于可写；UCS 借 modules 名字可见性复活尝试仍未果（⚠️ 未列提案号，未实测）；default comparisons 的 spaceship"意外后果"（== 不再自动合成）已成定局，详见 06 册。
- **工业实践**：`std::optional`/`variant` 三件套记法不互容的代价由生态自补——fmt/abseil 各自提供 expected 前身（absl::StatusOr、tl::expected），"overloaded 样板"已成为 C++17 访客代码的事实惯用法并被广泛抄写（Bjarne"该进标准"六年未进，C++26 亦无共识提案 ⚠️）；filesystem 双接口在 2026 年新代码评审中仍是-no-exceptions 项目的标准依赖。
