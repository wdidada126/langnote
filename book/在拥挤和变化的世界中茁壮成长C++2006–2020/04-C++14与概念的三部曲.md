## 核心概念速览（中英对照）

- **概念** — Concepts："模板参数对实参的要求"的编译期可表达规范——论文题眼："设计一个既灵活精确又不施加运行时代价的机制，结果被证明很难"
- **概念的早期历史** — The Prehistory of Concepts：1980s 扎根——"type of type"、Järvi/Gregor 谱系、2003 年首份提案就把 UCS 与 concept 捆在一起
- **概念映射** — Concept Maps：C++0x 的显式建模机制（让 int 满足 Incrementable 需作者手写映射）——"哪里出错了"的第一病灶
- **定义检查** — Definition Checking：模板定义处即对照 concept 检查用法——承诺"早报错"，实际把编译时间推高十倍
- **Joe Coder 之问** — "Are concepts required of Joe Coder?"：2009 reflector 论战代号；答案："多数程序员（包括我自己多数时候）就是 Joe Coder，我要'使用的教条'远简于专家技艺"
- **Concepts TS** — The Concepts TS：Sutton/Gregorian 分阶段路线（先实现后冻结）的技术规范书；Bjarne 复盘："我当时投了赞成票，现在认为那是错误"
- **概念名称引导器** — Concept Name Introducers：`typename T : Sortable` 式记号，TS 阶段有过，C++20 未获共识而亡
- **缩写语法** — Abbreviated Syntax：`void sort(Sortable auto&)`——2018 年 Voutilainen 三方死锁的破局记号；Bjarne 判词：auto 是"冗余、分心"的妥协
- **概念的命名** — Naming of Concepts：CamelCase 曾一度与标准库蛇形命名决裂，2019 Sutter 提案把全部标准概念改名 sortable/forward_iterator
- **变量模板** — Variable Templates：`template<class T> constexpr int rank_v = rank<T>::value;`（5.2，C++14）——概念语法的"constexpr 变量"底座
- **泛型 lambda** — Generic Lambdas：`[](auto a, auto b){...}`（5.4，N3649 实测 ✅302），C++14 最重要补件

## 一、C++14：小步五件套（§5）

tick-tock 模型的第一个"补票年"——把 C++11 漏的、晚到的、修错的收拢：数字分隔符（`1'000'000`）、变量模板（Bjarne 亲历命名插曲：Gregor 提案里写作 `Pi`，被改名 `pi` 进了标准）、函数返回类型推导（`auto f() { return ...; }`）、泛型 lambda（auto 形参）、constexpr 函数局部变量（把编译期计算从"表达式杂技"还原为"写普通函数"——N3652 实测 ✅302 "Relaxing constraints on constexpr functions"）。五件都是"孤立特性"标本（§3.3），但第 5.5 件是给 §9.3.3 编译期计算大爆炸埋的地线。

**定位与政治意义（论文 §5 开篇）**：C++14 的两大任务——收编"2009 特性冻结之后被认可的好点子"＋修复"C++11 大规模初用暴露的问题"——"以这个有限目标衡量，它成功了"。更重要的是**过程信用**：本届证明 WG21 真能按时发货，从而实现方也敢按时发货——2014 年底前 Clang/GCC/MSVC 三家都到达"多数人认可的功能完备"（一致性不完美，但几乎所有特性及组合都可试验；"用全部高级特性的库"到 2018 年才等到 MSVC 就绪）——"**标准化工作与实现工作从此紧紧绑在一起，这对社区意义重大**"。升级体验：C++11→14 无 ABI 破坏，熬过 98→11 大迁移的人"意外发现能更快更省力地再升级"。论文记录的委员会温差：多数特性一半人是"Good, what took you so long?"，一半人是"Huh? who needs that?"——Bjarne 判词：每件都有真实（哪怕非普适）的重要需求，尤其 constexpr 局部变量与泛型 lambda"显著改进了许多人的代码"。完整清单不止五件：还有**二进制字面量**（`0b1001000011110011`）、**移动捕获**（`[p = move(ptr)] {...}`）、**按类型访问 tuple**（`get<int>(t)`——03 册埋的债在此偿还）、**标准库用户定义字面量**（`10i`、`"Hello!"s`、`3ms`、`55us`、`17ns`）。

- **数字分隔符（5.1）**：论文称奇——**全场吵得最凶的正是这件小事**。Crowl 反复提交备选方案对比分析；Bjarne 等多数人主张下划线（多门语言的先例），致命伤：下划线同时是用户定义字面量后缀的开头——`1_234_567_s` 最后一个下划线是"冗余分隔符"还是 `_s` 后缀的起点？歧义不可接受；另一半原因：LWG 为保护程序员，把**非下划线开头的后缀预留给了标准库**。经历含全会（约百人）在内的无数次长会后定为单引号：`1'234'567`、`1'234'567s` 各归其位——**单引号系 Vandevoorde 建议，论据是瑞士金融记法中惯用的分组符号**；"单引号会打破无数工具"的危言最终没有应验。Bjarne 自己的替代案"空白分隔符"（`int a = 1 234 567;`）从未获得认真讨论——"很多人以为那是拿我 1998 年愚人节文章开玩笑"，其实它镜像的是 C 的相邻字符串字面量自动拼接老规则（`"abc" "def"` 即 `"abcdef"`）。§3.3 记账："这件花的委员会时间比 range-for 还多。"
- **变量模板（5.2）**：论文档案：2012 年 **Dos Reis** 提案把模板机制扩展到"模板变量"（与模板类/函数/别名并列）。Bjarne 自白"起初在我看来这是个明显的语言技术泛化、没什么特别重要性"——随后改口：为不同精度定义常数的历史"漫长、塞满不舒服的 workaround 与妥协"，一个简单泛化之后大量代码被简化。最重要的连锁：**变量模板很快成为定义 concept 的主要机制（6.3.6）**——本章两件由此直连概念三部曲；C++20 的数学常量（Minkovsky/McFarlane 2019）即 `pi_v` 变量模板＋最常见类型的 plain constexpr 双层定义。
- **函数返回类型推导（5.3）**：`template<typename T> auto size(const T& a) { return a.size(); }`——C++11 只许 lambda 从 return 语句推导，C++14 给普通函数开同等待遇；对泛型代码里的小函数记法收益可观。论文的警告却不关记法而关**接口稳定性**：函数类型从此依赖其实现，且实现必须在调用点编译时可见——"这样提供的不是稳定接口"。与 8.8.3 UCS 之殇（05 册）、9.6.2 monotype 之争（06 册）同一条"类型泄漏自实现"的担忧在不同章节三次出现，是 Bjarne"特性交互"病理学的暗线。
- **泛型 lambda（5.4）**：2012 年 Faisal Vali/Herb Sutter/Dave Abrahams 提案；**最初记法直接省掉参数类型**，委员会多人（包括 Bjarne 本人）强烈反对：该记法"独此一家"、无法推广到**带约束的**泛型 lambda → 改用 `[](auto& m){ return m.size(); }`，**与 concept 提案及上溯 2002 年的"泛型函数"设想拉平**；另一派人想要 C# `x => x*x`、Java `x -> x*x`、D `(x){...}` 式的超简洁专属语法，未得逞。Bjarne 的双重判词照录：用 auto、"不给 lambda 引入专属记法"是对的；**但不同步引入 concept 就把泛型 lambda 塞进 C++14 是错的**——约束/非约束的形参规则没能一起考虑，留下的语言不规则性要到 C++20（6.4）才修复；"我们现在有整整一代程序员习惯了不带约束的泛型 lambda 并以此为豪，这需要很长时间才能扭转"。本节还藏着全论文最可引用的一段方法论（为语法之争正名）："**语法是程序员的 user interface，语法之争往往反映语义之争或对该特性用法之争**。记法应映射底层语义；完全通用而冗长的记法偏向要表达细微差别的专家，为简单情形优化的记法偏向新手与偶发用户——我通常站后者，并常主张两种都给（4.2）。"
- **constexpr 函数局部变量（5.5）**：到 2012 年人们不再怕 constexpr，转而要求放宽实现限制，甚至有人想"什么都许"——用户与编译器实现者都未准备好；Richard Smith（Google）2013 年提出**相对温和**的一揽放宽：局部变量与 for 循环。论文原例 `constexpr int min(initializer_list<int>)` 在常量实参下编译期求值——"局部变量 low 和 x 就**住在编译器里**"，对调用方环境不可能有副作用；2010 Dos Reis & Stroustrup 论文早已指向这个可能。收益：不用把循环写成递归，大量 constexpr 函数简化，"让不满足于'只有纯函数式表达式可编译期求值'的多数 C++ 程序员满意"；长期效应是"释放了 C++17/20 更多放宽的需求"（9.3.3）。Bjarne 收尾留档一句："constexpr 线程是可能的，**但我不着急提这个提案**"——与 9.3.3"这可能是过多的好东西"互文。

## 二、第一部曲：C++0x Concepts——"深坑"解剖（§6.1–6.2）

论文 §6 开篇先立题（find 案例），这是全书最短的一次"概念＋库"分工演示：C++98 标准库算法的需求全靠散文规范——"第一个模板参数必须是 forward iterator；第二个参数类型必须可与该迭代器 value_type 用 == 比较；前两个实参必须表示一个序列"——而这些要求**隐含在代码里**，编译器唯一能依据的就是函数体对模板参数的用法。后果三联："**巨大的灵活性、正确调用时华丽的生成码、错误调用时 spectacularly bad 的错误信息**"。自明的解法是把前两条需求写成模板接口的一部分：`template<forward_iterator Iter, typename Value> requires equality_comparable<Value, Iter::value_type> ...`——"**这大体就是 C++20 给出的**"；注意 equality_comparable 这个多参数概念——"多参数概念极其常见"；第三条需求（[first,last) 是序列）语言管不了、要库扩展——那就是 ranges（9.3.5）。

**6.1 前史（论文档案展开）**：Bjarne 自我纠错——1980 年他 conjecture"C 风格宏足以支撑 GP"（Stroustrup 1982），"**flat wrong**"；前标准 C++ 的 `<generic.h>` 宏套件能表达少数简单泛型抽象，但大项目不可管理。约 1987 年他试图设计"带 Proper 接口的模板"（D&E 记载了失败），留下三条根本要求：**完全一般性/表达力**（"我明确不想要只能表达我想象得到之物的设施"）、**与手写代码零开销**（vector 要和 C 数组拼时间空间）、**良定义接口**（类型检查与重载不低于非泛型代码的水平）——"当时无人能三者兼得"，C++ 最终拿到的是：图灵完备（Veldhuizen 2003）、优于手写的性能、"**Lousy 接口（本质是编译期 duck typing），但仍是 statically type safe**"。前两条让模板 runaway success，第三条留下"我们多年来见到、C++17 里依旧可见的可怕错误信息"。学术考古要点：concept 源自 Stepanov 1970 年代末的 GP 工作、1981 年以"algebraic structures"留档（Kapur et al. 1981）——**比 Haskell type classes（Wadler & Blott 1989）早近十年、比 Bjarne 的尝试早约五年**；Stepanov 在 1990 年代末讲学启用"concept"一词（Dehnert & Stepanov 2000 定文），命名立意是"代表应用域的基本概念（如代数）"——论文专门回驳"concepts 是 type classes 移植加误名"论：当代"编译期谓词＋用模式"用法源自 Stroustrup & Dos Reis 2000 年代初（2003/2005/2006 文，D&E 1994 已提一角），选"用模式"是为简单一般地处理**隐式转换与重载**——"我们知道 type classes，但嫌其僵化，对当今设计影响甚小"。2003 三份论文的目标清单可当概念史目录：编译期谓词概念、用模式原语约束、多参数概念（`Mergeable<In1,In2,Out>`）、**值概念**（`Buffer<unsigned char,128>`）、type-of-type 简写（`template<Iterator Iter>`）、"模板定义简化记法"（`void f(Comparable&)`）、auto 作最弱约束、UCS（8.8.3）——自嘲补刀："奇怪的是我们当年**没提一般 requires 子句**，而它此后出现在所有概念变体里"。Boost 的 concept_check 库（Siek/Lumsdaine）"从未如我期望流行：不够一般、不够优雅（被迫用宏藏细节）、无标准支持——很多人视之为 hack"。

**2004 两派分立与妥协的代价**：委员会代号极其传神——"**Indiana**"（Lumsdaine 教授＋Gregor 博士后兼编译器作者；近 Haskell type classes、以操作表定义概念、强调程序员**显式声明**类型 models 概念）与"**Texas**"（Stroustrup＋Dos Reis；编译期类型谓词＋谓词逻辑、主张匹配**由编译器算出**、坚称隐式转换/重载/混型表达式必须优雅高效处理）。纸上两派不可调和，"但局中人当时不这么看"——Bjarne 还论证过**理论等价**，复盘："论证或许为真，**可它到 C++ 语境下的细节语言设计与使用层面，实际蕴含并不等价**。"程序压力：WG21 共识文化鼓励联合提案——对抗到底会"大 shootout"，败方不会弃实现与用户而去，是"**造方言的配方**"；第一版折中设计的 OOPSLA 论文由两边全员＋Siek（Indiana 生、曾在 AT&T  Labs 给 Bjarne 当暑期实习生）＋Järvi（Indiana 博士后→后来也去了 Texas A&M）共同署名——"我们真的想让折中方案成"。最后是实现现实定路：Indiana 领先实现与人力，记法"更正统、学术上更体面"，于是主要照其推进，剩下的"只是"三件事——**编译器够快、生成码够高效、摆平重载与隐式转换**。"这个决定花掉我们三年苦工与大量争议。"

6.2 的叙事价值在于它是**完整的设计失败尸检**（6.2.6 "What Went Wrong?" 逐条清单，抄录要点）：
1. 隐式 vs 显式建模（concept maps 用不用）始终未达成共识；
2. concept 间 refinement 层级（类继承式显式声明）未决；
3. 约束后的生成码**劣于**未约束模板——"模板的晚期组合机会不断展示惊人力量"；
4. 写 concept 难以捕获惯见的转换/重载组合；
5. 非平凡 concept_maps＋late_checks 导致**类型系统的一致性被打破**（"几乎不可见的违规"）；
6. 草案文字膨胀到 91 页（尚不含库用法），"某些人认为基本不可读"；库侧约 125 个 concept（STL 独占 103）；
7. 编译速度：带 concept 的编译器慢十倍以上——多家大厂商私下划红线"慢 20% 就反对，不管多好"。

**病理解剖的机制档案（6.2.1–6.2.5 原文展开）**：
- **概念＝"操作集合"的病灶（6.2.1）**：`concept EqualityComparable<typename T> { bool operator==(const T&, const T&); ... }` 与类的相像被 Indiana 派视为优点，但概念内函数不是类成员（无 this）。真正潜伏的是**传参方式的组合爆炸**：`f(X)`、`f(X&)`、`f(const X&)`、`f(X&&)` 四种（volatile 先不算）——概念里代表一种让用户适配？全部重载？让用户写 concept_map 映射？还是语言隐式适配？**两参数就 16 种组合、三参数 4³、变参 4^N**。各值类语义不等价，设计只好漂移向"按原样接受实参类型，把匹配重担推给类型作者与 concept_map 写手"。同期裂缝：概念规范 `x.f(y)`（OO 记法）还是 `f(x,y)`（函数记法）还是两者？二元运算符 + 一出场就撞上——判词："我们当年对'用具体类型/伪签名表示操作'的框架内解决这些问题**过于乐观**。"概念间关系用显式 refinement（`concept BidirectionalIterator : ForwardIterator`），"almost, but not quite"类继承——而"概念（英语常义）往往**不是严格层级**的"，僵化由此注入。
- **使用记法与 requires 的偶然出生（6.2.2）**：谓词用法最初关键词是 **where**——"where 在既有代码里作为标识符太流行了"，遂改名 **requires**。今天满屏的 requires 子句源自这次撞名。type-of-type 简写（`template<GreaterThanComparable T>`）迅速大受欢迎。
- **concept_map（6.2.3）**：`concept_map EqualityComparable<int> {};`——"int 明明已经可比，**为什么还要告诉编译器？**编译器本来就知道！"这是恒久争论点；student_record 案例则展示威力：类型没有 ==，可以在 map 里补写——**非侵入式给他人类型加能力的强机制**。Indiana"显式永远好"vs Texas"不加功能的 concept_map 负价值"：显式声明究竟能救"句法巧合而语义无意义的 accidental match"，还是错误罕见、声明本身才是 nuisance 与出错源？折中：概念作者可加 `auto` 宣布映射可省——EqualityComparable 即 auto 化。
- **定义检查（6.2.4）**：模板**定义处**即对照参数概念检查函数体——find 误用 `<`（EqualityComparable 只保证 ==）当场报错。"抓住未被概念保证的用法"是核心卖点，也是 6.3.1 大取舍的伏笔。
- **批准之后的修补史（6.2.5）**：Gregor 英雄式保生成码质量，但 concepts 编译器仍比无约束版**慢十倍**；Bjarne 的根因诊断——**编译器内部用"类式结构"表示概念**："概念不是类"；把概念表示为一组函数（像虚成员函数）令隐式转换与混型操作难处理，GP/TMP codegen 的"秘密武器"（不同上下文的代码灵活组合）变得无法规范表达；同时概念内函数绝不能落成调用（更忌间接调用），否则追不上无约束模板的性能。神似史前案：早期 C++ 编译器作者想拿 C 编译器代码库塞进 C++，最后几乎都重写前端（Cfront 当年用专门 scope 类直谕设计概念避开了这个坑）——"**语言设计与实现技术互相强烈影响**"。第二深坑：约束↔非约束模板互调——约束的不能叫非约束的（ callee 用法集合未知，定义检查无从做起），反之检查推迟到实例化；补丁 `late_check` 引出"有趣后果"：非约束 callee 里看不到 Semigroup 的 concept_map——"**同一对象在程序两处被完全同样地使用，语义却不同**"，类型系统被以难追踪的方式击穿。第三深坑是语义本身：Stepanov 口头禅"concepts are all about semantics"；2009 Dos Reis 的 **axioms** 记法（Bjarne 强力背书）过审——TotalOrdering 内写 Antisymmetry/Transitivity/Totality 三公理。**反对主因竟是提案人明确拒绝让编译器检验公理抓错**——"数学上公理＝一般无法检验才允许做的假设"这个观念"对某些委员闻所未闻"，另有人不信公理能帮到编译器之外的工具。

压垮事件：2009 reflector "Joe Coder" 论战（起因：Hinnant 问一个工具用方案 A 要用户写 concept maps、方案 B 不用 concept——"平均用户该懂多少 concept？"）。Bjarne 的立场文献《Simplifying the use of concepts》：concept_maps 应稀有、应全部隐式/自动、begin(x) 与 x.begin() 必须互相接受（即 UCS 回环）、标准库 concept 全自动。他还搬出 Stepanov《Elements of Programming》**一个 concept map 都没用**作重锤。委员会的回应是：修不好＋按时发货二者不可得兼 → 投票移除（Bjarne 本人投了移除票）。6.2.6 的三段个人教训（过度依赖早期实现；根本分歧不可妥协、要早识别早摊牌；大专家委员会的"服务所有人"必膨胀）被 Bjarne 声明**与 concepts 无关，是普遍设计规律**——这是全论文最可迁移的一页。

论战细部（论文原文补全）："Who is Joe Coder? 是 Peter Gottschling 问出的"——Bjarne 接："**绝好的问题。我想多数 C++ 程序员就是 Joe Coder（我同时登记对该词的反对）。我多数时候、对多数库也是 Joe Coder，只要我还在学新技术和新库就会一直是。可我**想**用 concepts（必要时也想用 concept maps）。我想要'使用的教条'远简于现在这套仅供少数专家精控的微妙技艺。**"——问题的本征形式："把 concepts 设计成少数语言专家手里精细调控的**名贵仪器**，还是多数程序员的**耐用工具**？"这个问句在语言与库设计里反复出现：当年围绕 class 就听了多年——在某些人看来"平均程序员"（有时讽刺地就叫 Joe Coder）显然不够聪明、不该被鼓励定义类。Bjarne 立场一以贯之："多数程序员**学得会**用好 class 与 concepts；学会之后编程更轻、代码更好。社区消化一课可能要多年——**若总是消化不了，失败的是我们（语言与库设计者），不是用户**。"为何坚持"全部隐式/自动"：Bjarne 观察到"给了选择，最死板、最不信人的程序员就能把 explicit 的活法强加给所有人"——库作者们正表现出把连最显然的选择都推给用户裁决的强倾向（用非自动概念）。移除投票的吊诡收尾：大会以绝大多数票移除 concepts，**而每一个发言的人都重申"我还要 concepts"**——票面意思只是"这个设计没准备好"。Bjarne 的更深诊断：问题比这糟——委员会想要 concepts，但成员**不认同要的是哪一种 concepts**；没有共享的设计目标，这道"哲学裂缝"至今仍在，且不限于 concepts。两条主裂缝：**显式 vs 隐式**（为安全与不意外，是否应要求程序员写明备选如何裁决——重载决议、作用域解析、类型-概念匹配、概念间关系处处复发）；**专家 vs 平均**（关键语言与库设施是否按专家设计？是否应鼓励"平均程序员"只用受限子集、另设专用库？class、类层级、异常、模板全部复发过）。两边的"yes"都会把设计推向需要高段位的复杂功能与"频繁手写才对的记法"——Bjarne 系统站在对面：信平均程序员、信正则语言规则与编译器/工具检查，"程序员把难题显式裁错的概率，不低于（隐式）语言规则出错"。

## 三、第二部曲：Concepts TS——"分阶段实现"路线（§6.3）

**重启叙事（论文 §6.3 开篇）**：2009 年 concepts 被移除**几乎当场**，Dos Reis、Andrew Sutton 与 Bjarne 就着手按原始思想＋C++0x 经验＋委员会反馈重新设计，先立三条结论：概念必须有**语义**；概念应当**少**；概念应当**基本（fundamental）而非极小（minimal）**——他们判定 C++ 标准库那份概念清单多数脱离上下文就没有意义："**STL 按任何合理的'概念'定义都不该有 103 个概念！**我在与 Sutton 的争论里喊出来过——**连初等代数都没有超过一打**！"（语言设计讨论可以相当火爆。）2011 年，在 Lumsdaine 撮合下 **Stepanov 召集 Palo Alto 一周会议**——原班人马加 Sean Parent，从用户视角反攻问题："一个**被正确约束的 STL 算法集**理想上长什么样？"然后各自回家把用户导向的设计文档化、再发明语言机制去逼近它（Stroustrup & Sutton 2012 技术备忘录）——**2016 年 Concepts TS 与 C++20 concepts 都是这次会议的直接产物**；Sutton 的 GCC 实现自 2012 供实验、**随 GCC 6.0 出厂**。曾被称为 "Concepts Lite"，"许多人认为它不完整、甚至无用"——但放弃定义检查的好处很快显形（下文）。

**TS 设计七条（论文清单照录）**：概念＝编译期谓词（允许多参数与**值参数**）；原语需求用 **requires-expression 的"用模式"**表达；概念可用于一般 requires 子句、可替代 typename 引入模板参数、可替代函数形参的类型名；**类型-概念匹配全隐式（无 concept_maps）**；概念间关系**由编译器计算**（无显式 refinement）；**暂不做定义检查**（因而无 late_check）；**无 axioms**——"只是不想让潜在争议拖慢设计，C++0x 的 axioms 会是个好起点"。总基调：消除"要求程序员写明、依赖人裁决"的一切，改为编译器按良定义的简单算法解析。支持显式派警惕"accidental match/意外惊喜"——最常见例证：Forward_iterator 与 Input_iterator **只差语义**（可多次遍历）。论文回应堪称设计律："没人否认这类例子存在，但为它们该怎么解决吵了十年——**让少数罕见复杂个案支配整个设计，是严重错误**。"实际解朴素得可爱：给最约束的那个概念加一条 `can_multipass()` 操作——**它甚至可以什么都不做**，只是让概念解析机制有个可检查的存在性——"不需要为消除可能的意外歧义而新增任何语言设施"。还有本体宣言，值得抄进所有"concept 是不是类"的讨论：**"概念是谓词。它们不是类，也不是类层级。我们本质上只是在编译期对类型问简单问题——'你是 Iterator 吗？'——以及对一组类型问互操作问题——'你们能用 == 互比吗？'"**潜在歧义靠**比较谓词**消解，不靠用户手写裁决规则；只问编译期能答的问题，无运行期求值。性能自证：Sutton 编译器**早期版本用 concepts 编模板就比用 enable_if workaround（03 册）的版本快**——"概念会拖编译"从第一天就是反事实。

**6.3.1 定义检查的大取舍**：三人决定**分阶段**做语言特性与实现——先实现、从使用中学习、拿到反馈**之后**才"冻结设计"；首刀砍的就是定义检查。教材案例：`template<Forward_iterator Iter> void advance(Iter p, int n) { p += n; }`——Forward_iterator 只有 ++ 没有 +=，有定义检查就在定义处报错；没有它，只在误用处得到糟糕的实例化期信息——但**实例化生成的码始终经过类型检查，不会漏出运行期错误**。量化理由："**约 90% 的收益来自使用处（point-of-use）检查**"——Bjarne 承认这是 ad hoc 估计，但"十年概念工作回看，我认为是个好的猜测"；约束模板的实现者多为老手，可以暂时没有它。不做检查换到的三项实利：①**开发期可用部分检查**——大程序初建时没人知道需求全集，部分检查让许多错误早抓、设计随早期反馈渐进收紧；②**接口得以稳定**——想给类/函数加调试语句、统计、tracing、telemetry，不必把那些设施的接口需求改进签名（它们几乎从不基本、且随时而变）；③**存量模板可渐进转约束**——反之若有定义检查，约束模板不能调用非约束模板（callee 用什么设施不可知）。EWG 主席（2014 起）Voutilainen 的重话原文："**我无法支持任何包含定义检查的 concepts 提案**。我们最终或许会得到某种定义检查，但前提是能设计出**逃离它的机制**来照顾迁移与数据采集需求——那需要仔细思考与实验，C++0x 的 late_check 不够格。**定义检查的问题是使用的问题，不是实现的问题**——Gabriel Dos Reis 用实验语言 **Liz** 把含定义检查的全套 TS 设施都实现验证过；若我们找到可接受的定义检查形式，随时可以实现。"（顺带：当年"先实现后冻结"的激进，对照物是历届论文里定义检查总被列为"提供 concepts 的主要理由"。）

**6.3.2–6.3.3 使用与定义（机制骨架）**：重载决议规则="**取需求最严者**"——advance 的 forward 版（循环 ++）与 random-access 版（p+=n）并存，编译器把概念拆成"原子"需求：forward 的需求集是 random-access 的**真子集**，`vector::iterator` 走快版、`list::iterator` 走慢版；需求重叠但互非子集则**歧义编译错**（`Copyable&&Integral` 与 `Copyable&&Swappable` 两版 fct：`fct(2)` 歧义——int 三个都是；`fct(complex{1,2})` OK——complex 非 integral）。程序员唯一的调控手段＝定义概念时加操作——"对真实世界的例子这就够了"。requires-expression 是 **Sutton 在实现 TS 时的发明**，"好用得让用户坚持把它送进标准"；用模式的记法则是 **Bjarne 在 Palo Alto 会议现场实时发明**（根子仍在 2003 文）——关键性质：**不涉及函数签名、不搞函数表实现**（对 C++0x 病灶的定点清除）。`concept Equality_comparable = requires(T a, U b) { { a==b } -> bool; { a!=b } -> bool; };`——`=T` 给第二参数默认、单类型可用；关联类型（`typename Value_type<S>`）照支持；Sequence 例子里 begin(a)/a.begin()、end(a)/a.end() **各写两遍**——"缺了 uniform function call 真疼（6.1/8.8.3 伏笔）"。无专用"匹配声明"机制，但通用 `static_assert(Equality_comparable<int>)` 随手可用（struct S 无自动 == → 断言失败，教科书式反馈）。

**6.3.4 概念名引导器——"试了才知道"的标本**：实践中发现原语用法太重复——requires-expression 直写满屏、"小概念"用滥，需求清单长得像新手代码（函数太少、抽象太少、符号名太少）。merge 族函数三序列＝三个类型需求＋三条元素关系，第一版 requires 一大串（STL 至少四个 merge）；教训是先学会用**多参数概念**打包常见需求图案（`requires Mergeable<In1,In2,Out>`）；这仍让"**2012 年大概写过最多 concepts 使用代码的人**"Sutton 嫌乱，遂提出"为一组必须满足某概念的类型引入名字"的**概念名引导器**：`Mergeable{In1,In2,Out} Out merge(In1,In1,In2,In2,Out);`——归约到逻辑最小。Bjarne 两句抄录："**光是试一试，你就能学到惊人多的东西**！同样惊人的是：新记法与新方案会遭遇多少**来自尚未体验过问题之人**的抵制。"（此机制在 C++20 未获共识而死——见第四节。）

**6.3.5 概念与类型之辨**：许多人（至今）把 concepts 看成 type-of-type 变体——单参数概念勉强算，但**多数泛型函数有多个模板参数，参数间必须相关**，于是必须多参数概念；多参数概念恰好直接接管隐式转换与混型操作——这正是 2003 年起与 Dos Reis 死磕的课题。曾被认真评估的替代路线（逐参数孤立约束）需要：参数化（Iterator 带值类型参数）、某种继承（Random_access 是 Forward 一种）、一参数叠多概念、三者组合——"结果是**复杂得没必要的**模板参数约束"。x+y 与 y+x（X、Y 不同类型）按孤立路线要 X 参数化于 Y、Y 参数化于 X——纯 OO 语言里或许自然（两边各一个 + 方法），"**可我在 1982 年就把这个方案给 C++ 否了**"；再加隐式转换（x+2、2+x）才是完整图景——"多参数概念**精确匹配 C++ 解析这些例子的方式**，绕开绝大部分复杂度"。此后多年反复重估、结论维持；"把 Haskell type classes / Java 约束等标准学术系统直接套用，未能给出规模使用所需的实现与使用的简单"。定义层对照记（论文原文三分法）：类型规定对象可受哪些操作、依赖函数声明与语言规则、**并规定内存布局**；概念同样规定可受操作集、同样依赖"反映声明与规则的用模式"、**对布局只字未提**——"因此概念是一种 interface"。Bjarne 的理想："我想在**所有用类型之处同样使用概念**"——除布局外二者极像，概念甚至可以约束由初始化式定类型的变量（constrained auto：`Integer x1 = 7;` 与 `void f(int&)`/`void f(Integer&)` 一个普通函数一个函数模板互相重载）。"C++20 接近实现这个理想——只是每处要加一个**逻辑上冗余的 auto**（6.4）；另一方面 C++20 里可以用标准 integral 替换这个明显不完备的 Integer。"

**6.3.6 改良性收敛**：TS 起步时概念是**返回 bool 的 constexpr 函数**（谓词观的自然写法）；Dos Reis 把变量模板送进 C++14（5.2）后出现**两派并立**——函数式 `concept bool Sequence() {...}` 与表达式式 `concept bool Sequence = ...`；"两派都能愉快共存，但概念**用户**得先知道定义用的哪派才好写括号——很快就不可行了"。函数式独有红利是概念重载，但真实例子寥寥 → **简化为概念只用变量模板**（Sutton 首倡一贯的表达式风格）。`concept bool` 里那个 bool 早知冗余（"概念定义上就是谓词"），当时决定"不动语法、专注语义话题"——后来**人们把冗余 bool 当靶子攻击概念设计**，"于是我们修掉了它，从此不必提 bool"；该修订属 Smith & Sutton 2017 一组改进（更精确的"原子谓词"定义、简化匹配规则）。一段机制史浓缩在 5.2↔6.3.6 的互文里：**C++14 的小特征是 C++20 大特征的载具**。

**6.3.7 语法等价之争——两种"简单"的世界观**：TS 支持三种使用记法并**定义为等价**：显式 requires 子句（全一般性）、type-of-type 简写（`template<Sortable S>`）、自然记法（`void sort(Sortable&)`——论文列出它的全部绰号：terse/conventional…）；设计意图：让程序员按当下声明的需要挑记法、不被复杂案例的记法淹没，且开发/维护中可自由改换。用户满意，多偏好自然与简写；但**部分委员"horror"于自然记法**（"看不出是模板！"）而挺最显式 requires（"为什么还要更多？"）。Bjarne 的诊断是两种"简单"观的冲撞：**"我能用最短最直接的方式写代码"** vs **"我只需要学一种记法"**——他持前者，并点名这是洋葱原则（4.2）的实例。辩护连段带出历史自白：自然记法让 GP "只是普通编程"——不同语法、不同的源码组织（header-only 苦役）、不同的编码风格（TMP 黑魔法）都曾是 GP 的"不同"；modules 治源码组织（9.3.1），自然语法回应的是"template 语法冗长笨拙"的**常年抱怨**——而"**`template<...>` 前缀就不是我设计模板时的首选**，是怕模板被能力不足的程序员滥用导致困惑的人们强加给我的；异常处理的厚重记法 try/catch 是同一故事。似乎每个新特性都有人要求 **LOUD 的记法**去防真问题和假问题，过些年他们再抱怨冗长。"反对派坚持的"危险样品"是 `void f(C&&);`——C 是概念还是类型，决定 C&& 在"函数模板"与"普通函数"下的含义差异；Bjarne 针锋相对："C&& 语义的这种不同**是 C++11 的一个最不幸的设计错误，我们本该去修正它**，而不是让它来绑架 concepts 的定义。误会的可能性真实存在、千万用户里总会发生——可我多年教学与使用**没有观察到位**，而且真会写这种代码的资深程序员也不会被它绊倒。换句话说，我认为这是**狗尾巴摇狗（tail wagging the dog）**：以生僻个案挡掉惠及大众的功能。"他几乎肯定"让 GP 尽可能接近普通编程"的目标并非人人共有——"今天仍有人认为 GP 在 vast mass 程序员的能力线之外。**我依然看不到支持这一判断的证据**。"

**6.3.8 为什么 C++17 没有 concepts**：Bjarne 的复盘罕见地先把责任揽到**路线选择**："我曾期望 concepts 进 C++17；在我认为 2017 周期可行的扩展（9.2）里，concepts 是对 C++ 程序员基础词汇改进最大的一个——消除大量丑陋易错的 TMP、精确化库规范、改善库设计。**我担心这恰恰是问题的一部分：concepts 会直接影响几乎所有投票委员**。有人更安于旧技艺，许多人对它没有经验，还有一些人视之为未试用的'学术/理论'想法。" 正是这类忧虑（＋C++0x 概念时代的大败（6.2）供血）当初催生了 TS 路线：2013 Bristol 会议上 **Sutter 力主 TS**，J.-Daniel Garcia 与 Bjarne 警告**迟到的风险**，Bjarne 还警告"把 concepts 与泛型 lambda 分开考虑"的危险（5.4 判词的预告）——"但'谨慎'与'我们还需要更多经验'在标准委员会里是强势论据。**最终我投了 TS 赞成票。现在我认为那是个错误。**"（对分阶段路线的价值评估：2013 年就有实现和相当好的规范（头功 Sutton），TS 完成却再花三年——"我分辨不出 TS 进标准与直接进标准在严谨度上有何差别。"）2016 Jacksonville 表决日（原 25:31:8 记录）：所有旧反对理由原样复读、反对者三年没看 concepts、"对 TS 设计从未成立的 C++0x 时代理由也被拿来反对"；到场者中**没用过 concepts 的人比 2013 布里斯托尔还多——委员会膨胀的直接后果**；"除了我过去十年听过的全部反对意见，还有全新反对被提出、**未经试用的设计在全会现场被当真**"。动议原文（Voutilainen）与"别为假想的设计问题扣着不发"已见前引；Bjarne 对票面的自我解读："**用户投了赞成，语言技术派投了反对——不过这可以被视为酸葡萄。**"同一会议 UCS 被否决（→ 05 册）、协程被送去 TS——三票定下"C++17 只能是小版本"（→ 05 册开篇）。Bjarne 的毒舌复盘："反对者三年没看 concepts，把 C++0x 概念时代的旧反对理由原样复读，还混进从未在 TS 里存在过的'问题'。"

## 四、第三部曲：C++20 Concepts 与命名战争（§6.4–6.5）

2017 年 C++20 第一批投票只收了"无争议底座"（requires 子句＋`template<Sortable S>` 简写），把"自然语法"（`void sort(Sortable&)` 不写 template 头）当争议砍掉——反对理由清单（6.4 抄录）："看不出是模板""`f(C&&)` 里 C 是 concept 还是类型有歧义""`Iterator foo(Iterator,Iterator)` 三处 Iterator 同不同型？""难教""`template<auto N>` 怎么约束"。随后 Sutter/Stroustrup 两案并行（两版互斥且各获 EWG 大票支持=死锁），Voutilainen 三方变体胜出：**概念名后加 auto**——"abbreviated syntax"。Bjarne 接受但不满："也许将来大家会同意 auto 冗余（Sutter 当时就这么说）。我不抱希望——有一大群人认为'为模板记法加句法标记'很重要。" 6.3.4 的概念名引导器则没能复活（"缺乏足够常规的语法"＋部分人不信其必要）。

**论战升级期的弹药库（论文 6.4 档案补全）**：那些"反对理由并不新"，新的是**伴随而来的一批 novel syntax 提案**（Hönermann、Keane 等、Küppe、Riedle、Sutter 2018a）——"它们互不相同、全部与 Concepts TS 不兼容、在会上被带着相当情绪地呈现、**没有一个有真实使用经验背书**。"对照组是 Bjarne 自己的底气："约四年教学、大量实验性使用、若干工业使用、多个标准库提案组件已经采用（iterator facade（Dawes et al. 2016）、tuple 实现（Voutilainen）、ranges（Niebler et al.））"——**经验派 vs 白板设计派**，委员会病理学（01 册 §3.3"热情偏向新事物"）的标本。2018 Jacksonville 上 Honermann 动议移除自然语法并交替代方案，Bjarne 以两文应战（Stroustrup 2017a,b），基本防御五条原文：自然记法**五年多教学与实用未出问题**；**用户喜欢它**；**无技术歧义**；**简化常见情形**；它是"让 GP 更像普通编程"纲领的一部分。判词冷酷："**这些没能说服任何本来就反对的人**"——自然语法未进工作稿。最后堡垒是 `template<auto N>`（源自 C++17 小特性"auto 非类型模板参数"，Touton & Spertus 2015）：有人要在语法上区分值参数与类型参数——**通常意味着 2002 年以来所有提案与使用都以之为主力的简写记法作废**，连 `template<typename T> void f(T&);` 都在"拟议禁用"之列。破局三步（时间线精确到半年）：2018 年中 Bjarne 交**最小折中**——保住 `template<Concept T>` 的含义＋自然记法加 template 前缀（`template void f(Concept&);`）——**该案过了，可 Sutter 的另一个截然不同的案也过了**：两份大不相同、互不兼容的提案各握着 EWG 的多数支持，**死锁**；门因此向 EWG 主席 Voutilainen 的三方变体打开——保住 `template<Concept T>`＋**用 auto 标识自然记法的模板参数**（`void f(Concept auto&)`），2018-11 以压倒支持通过。"natural notation" 就此改名 **"abbreviated syntax"（缩写语法）**——Bjarne 咬文嚼字记下："尽管它**并不只是缩写**。"样例三连（论文原码）：`void sort(Sortable auto& x);`、`Integral auto ch = f(val);`、`Integral auto add(Integral auto x, Integral auto y); // 可用更宽类型防溢出`。Bjarne 的和解词全文要义："我支持这个妥协，尽管我认为 auto 的使用**冗余、分心**、损害我'让 GP 就是普通编程'的目标。也许将来人们会同意的（Sutter 当时就说）——让概念名后的 auto 变冗余。**我不抱希望**：有一大群人认为'为实现技术加句法标记'很重要。也许 IDE 的自动补全会把用户从冗余 auto 里救出来。" 同节还有一条未遂复活：概念名引导器"可惜没有共识"——双重死因照录："**缺乏足够常规的语法**是主要障碍；另外不少人**至今不信其效用**"（6.3.4 那句"尚未体验过问题之人的抵制"在此收口）。延迟的代价总账（判词已见原引）之后还有一句安慰性观察："IDE 时代记法税由工具代付"——与 6.3.5"理想待 auto 冗余被消解"同为悬账。

**6.5 命名战争（全档案）**：C++20 发车前关于 concepts 的最后一轮大讨论是命名——"命名从来都是棘手的题目"。两条家谱：Bjarne 沿用他为非标准库类型的个人惯例——首字母大写如专有名词＋词间下划线（`Sortable`、`Forward_iterator`）；Indiana 队用 CamelCase（`ForwardIterator`）。"不幸的是，这一（CamelCase）惯例**爬进了标准文本**（Carter 2018），与标准库其余一切名字（全小写下划线；MACRO 和'三个生僻难寻的例外'除外）决裂，造成混乱。"随后出现一个 Bjarne 事后强烈厌恶的**合理化叙事**："命名不同是为把'新奇而困难的'concepts 与普通函数、类型区分开"——"在 C++ 里我们一般**不在名字里编码类型**"。他本已认命（改风格太晚了），2019 年 **Sutter 回应他的牢骚（grumbles）提案全数改名**、循标准库惯例——**所有主要概念设计者与 ranges 库设计者联署**。另一个务实理由：CamelCase 的标准概念名**开始与用户库的 CamelCase 名撞车**——而当初选 CamelCase 的理由之一恰恰是"与标准库名字避开冲突"！命名惯例的因果在十年里翻了个面。终局账本：C++20 标准库约 **70 个概念**，覆盖调用操作、基本类型使用、ranges 与标准算法之需——constructible_from、convertible_to、derived_from、equality_comparable、invocable、mergeable、range、regular、same_as、signed_integral、semiregular、sortable、swappable、totally_ordered……"它们将指导此后很久的 C++ 库设计"——并附一句去魅声明："**这 70 个里许多并不基本**，只是记法便利或作为积木存在。"
6.4 收尾判词要抄在每一本模板书的封底：**"概念引入被推迟的这些年造成了持久伤害：基于 traits 与 enable_if 的临时设计泛滥成灾；一代程序员在低层的、无类型的元编程里长大。"**

## 五、g++ 实测：概念的错误信息质量——当年"最响亮的抱怨"如今兑现

```cpp
// s04.cpp 摘要：requires-expression 定义 Addable；用概念约束 sum_all
template <typename T>
concept Addable = requires(T a, T b) { { a + b } -> same_as<T>; };
template <Addable T> T sum_all(const vector<T>& v) { ... }
```

已实测 g++ 15.2：`-std=c++17` 失败（`error: 'concept' does not name a type; did you mean 'const'?`）；`-std=c++20` 通过，运行输出：

```
10
abcd
```

取消注释 `sum_all(vector<vector<int>>...)`（vector 无 `a+b` 返回同类，不满足 Addable）后，报错为：

```
error: no matching function for call to 'sum_all(std::vector<std::vector<int> >)'
note: constraints not satisfied
note: the required expression '(a + b)' is invalid
```

——两行因果式诊断对比 C++14 时代动辄数百行的模板回溯，正是 §6.1 承诺"改善最响亮的抱怨（错误信息）"的十六年兑现。

**补测：C++14 五件套基线（s04b，本目录续写轮新增实测）**——把 5.1–5.5 五件写进同一小程序（`1'000'000`、`template<typename T> constexpr T pi`、`template<typename T> auto size_of(const T& a)`、`[](const auto& m)`、constexpr 函数内局部变量＋range-for＋`static_assert(imin({5,3,2,4})==2)`）：

已实测 g++ 15.2：`-std=c++11` **失败（8 处 error）**——`use of 'auto' in lambda parameter declaration only available with '-std=c++14'`、`'size_of' function uses 'auto' type specifier without trailing return type`、`body of 'constexpr' function ... not a return-statement`（及 static_assert 连锁）；`-std=c++11 -pedantic-errors` 再升一格（**9 处 error**，`variable templates` 从警告转正）；`-std=c++14` 通过，运行输出：

```
pi=3.14159 big=1000000 vsize=3 min=7
```

两处与"编译器扩展"博弈的实况（本续写轮逐条单独复测）：①同一台 GCC 在 `-std=c++11` 下把**变量模板当 -Wc++14-extensions 警告放行**（单测 rc=0）——"标准先行、方言随行"，也是 -pedantic-errors 存在的理由；②`1'000'000` 在 C++11 下被词法器拆成 `1`＋多字符常量 `'000'`（先 `-Wmultichar` 警告、再 syntax error）——数字分隔符连"被误吞"的资格都没有，歧义要等语法层解决。对照 03 册"逼特性设计者直面真实用例"：工具方言与标准列车各有节奏，严肃构建两个开关都得拧。

## 最新演进与工业实践

- **落地率盘点**：论文中 C++20 已 ship 的概念即 §6.4 语法（requires/abbreviated function templates 全支持：GCC 10+/Clang 10+）；夭折项：概念名引导器、`Concept x` 裸缩写（无 auto）至今无共识；2024–2026 议题"概念与模板之间的语法统一"（concept auto/参数概念再简化，⚠️ 本笔记未实测其提案号，故不列）。
- **库生态**：std::execution（P2300R10 ✅302）通篇以 concept 书写 Sender/Receiver 契约——concepts 首次成为标准库的"规格语言"而非"报错美化工具"；range-v3→std::ranges 的 concept 层（input_or_output_iterator、borrowed_range…）是 6.5 命名的最大用户。工业侧 fmt 11、absl 文档普遍改用 C++20 概念表达要求。
