## 核心概念速览（中英对照）

- **lambda 表达式** — Lambda：就地匿名函数对象；根脉可追到 BCPL 代码块＋C 反复被拒的本地函数＋函数对象
- **变参模板** — Variadic Templates：`template<typename... Args>`，Gregor/Järvi/Powell（Indiana，2004）贡献，终结"宏＋N 份重载"时代
- **别名模板** — Aliases：`template<class T> using Vec = std::vector<T, My_alloc<T>>`，补齐 typedef 不能带模板参数的缺角
- **tuple** — tuples：函数"多返回值"的标准化句柄，源自 boost::tuple，泛函数式传统的移植
- **静态类型安全** — Static Type Safety：C++11 的立论两理由——把意图写清楚（帮人也帮编译器抓错）＋帮编译器生成更好的码
- **SFINAE** — Substitution Failure Is Not An Error："当且仅当谓词成立才提供操作"的暗黑艺术，概念缺席年代的基础库支柱
- **类型特征** — Type Traits：`is_copy_assignable` 等编译期内省工具，C++11 一次性提供数十个
- **noexcept 规约** — noexcept Specifications：动态异常规约的死与再生——0/1 语义、可判定、近零开销
- **标准库组件** — Standard-Library Components：C++11 新增 hash 容器、chrono、regex、随机数、array、tuple 等的集体亮相

## 一、泛型编程四补件（§4.3）

论文按"改进对泛型编程的支持"统摄这四个子节——泛型编程（GP）是 C++ 标准库的骨架（§10.5.1），C++98 给了容器算法却缺"就地组合"的胶水，C++11 补齐：

论文 §4.3 开篇的诊断句与四红利值得原文照录："GP 及其子嗣模板元编程（10.5.2）成为 runaway success……**它的使用严重压垮了语言，不足的语言支持导致 baroque（巴洛克式）编程技巧与可怕（horrendous）的错误信息**"——而"那么多神志正常的程序员（so many sane programmers）愿意忍受这些代价"，正是 GP 效用的证词。他们换来的四项红利：①超出 C 风格与 OO 风格所能给的**灵活性**；②**更干净的代码**；③**更细粒度的静态类型检查**；④**效率**（主要来自内联、编译器一次看到多来源的代码、以及更好的类型检查）。另有一句定场白贯穿全章：**concepts 本应是 C++11 泛型支持升级的"中心件"（centerpiece），"但那没有发生"（6.2.6），要等到 C++20（6.4）**——本节四个"补件"多少带 workaround 色彩，病根都在这句。

- **lambda（4.3.1）**：史实链很讲究——BCPL 允许代码块作表达式，Ritchie 为省编译器空间没进 C；Bjarne 跟 C 走，但用 inline 函数换回"无调用开销的码"，仍缺两样：**在需要处就地写码**＋**代码访问上下文**。C++98 期间"本地函数"提案被**以"潜在 bug 源"投票否决**；替代方案=函数对象（带 operator() 的类），而"命名对象比匿名操作更清晰"论仅在"起得出好名字且复用多次"时成立。
  - 2002 Järvi/Powell Boost.lambda（`find_if(v.begin(), v.end(), _1 < i)`）是"早期模板元编程的杰作"，便利而流行——**但不快**：Bjarne 多年实测对比手写等价物"**稳定慢 2.5 倍**"："我不能推荐一个便利但慢的东西，那会伤害 C++ 作为高效语言的名声。"
  - 于是 Järvi 团队（Willcock et al. 2006）提**语言级 lambda**：引导符用 `<>`（"我们不敢提新关键字"）。2006–09 讨论清单（论文照录）：记法要表达力还是简洁？捕获哪些名字（Crowl 2009）？生成的函数对象默认可变否（否）？能多态否（**直到 C++14**）？lambda 的类型（唯一匿名类型）？能有名字否（"需要名字就赋给变量"）？按值还是按引用捕获（随你选）？能移动捕获否（**直到 C++14**）？会与各种非标准扩展冲突否（严重地不会）。
  - 2009 年定稿时记法已"变异得更常规"：**`<>` 改 `[]` 系 Sutter 建议、Jonathan Caves 实施**——Sutter 回忆原文："EWG 采纳的那版 lambda 用起来**丑得没边（butt-ugly）**、语法一致性设计糟糕（捕获出现在两处、'构造件'该在前、'调用件'该在后、顺序全反……）我是被平行算法项目逼着非用 lambda 不可。"
  - 捕获语义：默认不能引用局部名（即普通函数）；`[&s]` 按引用——同线程回调高效，**跨线程回调则 s 可能先亡，"灾难"**；`[=s]` 按值=为回调场景准备的解；`[&]`/`[=]` 全捕获。捕获机制正是对"1990s 本地函数易错"之忧的正面回答。
  - 实现模型＝编译器造匿名函数对象（捕获变量成成员、由构造函数初始化、lambda 体成 operator()），返回类型可从 return 语句推导；无 return 语句则不返回任何东西。论文给出的脱糖标本：`bar_callback([=s](double d){ return do_bar(d,s); })` 等价于编译器手搓 `struct __XYZ { string s; __XYZ(const string& ss):s{ss}{} int operator()(double d){ return do_bar(d,s); } };`——"函数对象方案"与"语言方案"在实现层是同一个东西，省掉的只是人的打字与名字的臃肿。Bjarne 自白分类立场："我把 lambda 归入**泛型编程支持**——它最常见用途与主要动机就是 STL 算法实参。"机制教例见 → [../c++之旅3/04-模板与概念和泛型编程.md](../c++之旅3/04-模板与概念和泛型编程.md)。
- **变参模板（4.3.2）**：2004 年 Indiana 三人组（Gregor/Järvi/Powell）提案（N2242 为措辞稿，[wg21.link/n2242](https://wg21.link/n2242) ✅302，标题实测 "Proposed Wording for Variadic Templates (Revision 2)"），目标两条："以任意长参数表实例化模板"＋"**以类型安全方式向函数传任意多实参**"。Bjarne 的自白很值钱：初看"方案过度复杂、记法晦涩、编程风格过于递归，**不合我口味**"——**2004 年 Doug Gregor 一场精彩报告后他倒戈并"全力背书"**，让变参"相对平滑地过关"；真正说服他的是**编译时长实测**：对比当时各种 workaround，变参是"有时 20 倍"的改善。反讽伏笔："变参后来太流行、成了标准库essential零件，**编译时长问题因此卷土重来**——不过那时还远在将来。"实现模型：递归搭参数包再递归用（包中每元素自有类型与大小，必须如此）；Gregor 的类型安全 printf 例子（head T＋tail Args，`%s` 处直接用 `<<` 打印、天然支持用户自定义类型、免疫 `%g`/`%c` 与实参错配——"这个 technique 是 C++20 format（9.3.7）的基础"）；弱点："N 个参数=N 份实例化，极易 code bloat"（→ C++17 折叠只治记法不治本）。此前"可变参数模板"靠手工 0..9 元重载＋宏生成（boost.function  famously ugly 的实现）；`Args&&... args`＋`forward<Args>(args)...` 之后一个模板通吃。与 tuple（4.3.4）同构互撑：tuple 是"编译期可变长记录"，是变参的原生载体。
  - 论文留档的验收测试（Gregor 本人、时任印第安纳大学）：`printf("The value of %s is about %g (unless you live in %s).\n", std::string("pi"), 3.14159, "Indiana ")` 打印 `The value of pi is about 3.14159 (unless you live in Indiana).`——`%s` 之后**不再需要类型指示**（类型编译期已知），用户自定义类型与内建类型同等待遇，且 `printf("%g %c","Hello",7.2)` 这类格式/实参错配从机制上根除；论文点名"这个 technique 是 C++20 format（9.3.7）的基础"。头-尾递归结构（`<typename T, typename... Args>`＝传统表头 T＋表尾 Args，每次处理头、拿尾递归自身）是"参数包中每元素自有类型与大小，必须如此"的直接后果。
  - 机制拆解——完全转发靠两条派生规则协作：①**引用 collapsing**：`T& &`、`T& &&`、`T&& &` 均塌回 `T&`，唯有 `T&& &&` 保持 `T&&`；②**推导约定**：传左值时模板实参 `Args` 推成 `int&`（塌缩后 `Args&&` 变 `int&`），传右值时 `Args` 推成 `int`（`Args&&` 即 `int&&`）——同一拼写 `T&&` 因实参值类获得两副面孔，这正是 02 册"有标识/可搬空"二元矩阵的推论，也是 Scott Meyers 坚称"万能引用（universal reference）"而非"右值引用"的原因。`forward<Args>` 的作用就是把这副面孔原样焊回实参上。
- **别名（4.3.3）**：typedef 不能带模板参数，于是 C++03 时代"给 traits 起小名"必须套 struct；连 `typedef double (*pf)(int);` 这种 C 别名都"绕但无处不在"。
  - 史前：从模板诞生首日就有人琢磨"typedef 模板"；**2002 年 Sutter 给出第一版方案**（`template<typename T> typedef X<T,int> Xi;` 式），2007 年 Dos Reis 以 N2258（[wg21.link/n2258](https://wg21.link/n2258) ✅302，"Templates Aliases"）定稿 `using` 语法：`template<class T> using Vec = std::vector<T, My_alloc<T>>;`。论文补全的分工细节：Dos Reis（时在职法国 INRIA）与 Matt Marcus（Adobe）在漫长的 reflector 论战后解决了**与特化相关的几桩棘手问题**，"alias templates"这个名字出自 **Vandevoorde**；"被定义的名字永远在前"的 `using` 记法系 **Bjarne 本人建议**，随后他与 Dos Reis 一起把它推广为"（几乎）完整的别名机制"——即使不涉及模板也可选择 `using analysis_fp = double(*)(const vector<Student_info>&);` 顶替绕人的 C typedef。
  - 论文的真实组合拳案例（一个通信库 InputChannel，Bjarne 自评"**C++11 诸特性组合为难题给出优雅零开销解的绝佳标本**"）：类界面主要由三条别名承担——`using InputMessage = ...`、`using MessageCallback = function<void(InputMessage&&)>`、`using ErrorCallback = function<void(const error_code&)>`，从模板实参初始化；别名让用户"以一组标准名字说话"而各家实现可用自己的名字与技巧——**零开销抽象与模块化就住在这里**。而 InputChannel 必须持有并初始化 Transport 成员却**不该知道传输实现细节**（拿不到其构造方式）——变参模板在此救场：`template<typename... TransportArgs> InputChannel(TransportArgs&&... args) : _transport{forward<TransportArgs>(args)...} {}`。权衡档案：没有变参，就只有两条烂路——给所有 transport 定义公共初始化接口（为不存在的一致性付费）或把 transport 暴露给用户（封装破了）。
  - 后续战场：Concepts TS 时代"concept 是否就是变量模板"的语法辩论（6.3.6，→ 04 册）就站在这块舞台板上——别名模板与变量模板共同构成"constexpr 化元编程"的地基（9.3.3）。
- **tuple（4.3.4）**：函数返回多值的老问题（出参、struct 手搓）终于有通用件；论文提醒 tuple 被**过度使用**——"若多个值彼此不独立，我更愿意具名类"。§3.3 的"特性交互"病例也点名 tuple：为孤立可用而膨胀。补件史实：按类型访问 `get<int>(t)` 要到 C++14 才进（§5 特性清单点名）——"下标访问的 tuple 是句法糖的温床，命名访问才是设计意图的栖身处"（笔记概括）；结构化绑定（C++17，05 册 8.2）与 `std::apply/invoke`（C++17）才是 tuple 记法之耻的迟到救赎。
  - 论文原档（Järvi 2002，明确 referencing Haskell/ML/Python/Eiffel）："tuple 是**定长异质容器**"，三条通用用途：需要多于一个返回值者的函数返回类型；把相关类型/对象（如参数表诸项）打包成单一实体；多值同时赋值。C++98 已有 `pair<T,U>`（主要用来返回迭代器对或"指针＋成功位"），tuple 即其推广；配套件 `make_tuple()`（从实参推导元素类型）与 `tie()`（把 tuple 各成员赋给一组具名变量）。
  - 论文教学例（矩阵分解三连返回）：`auto SVD(const Matrix& A) -> tuple<Matrix,Vector,Matrix> { ... return make_tuple(U,S,V); }` ＋ `tie(U,S,V) = SVD(A);`；论文顺手展示 C++17 结构化绑定后同例缩为 `return {U,S,V};` ＋ `auto [U,S,V] = SVD(A);`，并补记 Spertus 2018 的进一步简化——`tuple SVD(const Matrix&)` 直接从 return 语句推导 tuple 模板实参——"**没能赶上班车（didn't make it on time）**"。N+1 问题在此再露脸：记法每改一代，旧写法一行不删。
  - 相邻概念对比（论文自问"tuple 为什么不是语言特性？"）：1979 年以来的老规矩——**能用库合理解决就不加语言特性；不能，就改进抽象机制让它能用库解决**。三条红利照录：库比语言特性容易实验得多，反馈来得早且好；库能在所有编译器升级之前就获得认真使用；改进抽象机制（类、模板等）的收益超出眼前问题。tuple 恰好有 boost::tuple 可依托、且看不出偏要语言实现有什么运行期效率理由——Bjarne 怪一声"That's somewhat impressive"。对照面：**参数包（parameter packs）就是 tuple 的编译器直撑版**（4.3.2 与 tuple 互撑的另一半）；tuple 还是 C++ 与 Python 等语言间接口胶水的重武器。

## 二、静态类型安全的清单政治（§4.4）

论文的 4.4 不是特性列表而是**立论**：

- 理由一（为人也为机器）："确保程序按**你的意思**做事的最简单方式，是让你把意思**写出来**"——好的类型接口精确描述想支持的操作与运算数，既帮人抓错、更帮编译器抓错；
- 理由二："**类型安全的程序往往更快**"——编译期信息越多，可生成的优化越多；
- 警告："只依赖内建类型谈不上类型安全"——int/string 能表达任何东西；真安全要靠**细粒度自定义类型**（物理单位检查等 constexpr 帮得上）。
- Simula 底色（论文补全立论来处）："受 Simula 启发，我为 C++ 设定的目标是提供**灵活且可扩展的静态类型系统**——目标不只是 type safety，而是**直接表达细微差别（fine-grained distinctions）的能力**"（物理单位检查即 4.2.7 constexpr 的用武之地）；"纯用内建类型写的程序可以类型安全却拿不到实质好处——那样的代码不直接表达应用域的概念"，尤其"一个 int 或 string 几乎可以代表任何东西，**传出去时对方看不出这值的语义**"。

清单：线程锁的类型安全接口（对 `void**`）、range-for（对裸 first/last）、移动语义（对深拷贝）、资源管理指针（对裸拥有权）、统一初始化（对窄化）、constexpr（对宏）、用户字面量（对"内建型特权"）、**enum class**（消弱类型整数常量）、std::array（消数组到指针的意外 decay）。

末两件的机制展开（论文清单只点名，此处补足"为什么"）：C++98 的 enum 是"披着类型的整数常量集"——枚举量泄漏进外围作用域、可隐式提升为 int 参与任意算术，两个不同 enum 能比较大小；`enum class` 三刀切断：枚举量限定在作用域内、默认不隐式转换（可指定底层类型）、同类型内比较有意义。`std::array` 针对的是 C 数组一进函数签名就 decay 成指针、`sizeof`/长度信息当场蒸发的老毛病——把"大小是类型的一部分"写成零开销包装（继承自 §4.2.5 统一初始化的花括号语义，与 §11.3"清理旧账"里的隐式窄化同属 C 遗产）。这两件加上 4.4 的"细粒度自定义类型"论，构成 C++11 静态安全观的完整三角：**约束隐式转换、保住尺寸信息、让语义住进类型**。

关键裁决史实：*"委员会该禁掉不安全特性（内建数组、强转）吗？"*——Bjarne 答"**deprecate 屡试屡败**：用户无视警告并逼实现方保留"。可行路径＝**指南＋可执行检查＋标准保持兼容**（→ §10.6 Core Guidelines/静态分析，本目录 07 册）。这段是理解"C++ 为何不学 Rust 强制安全"的钥匙。

## 三、库构建支持：SFINAE 的辉煌与耻（§4.5）

**§4.5 开篇立论**：C++ 的基础库常被设计成**与语言内建设施及其他语言的内建设施拼性能、拼易用**——这正"是查找规则、重载决议、访问控制、模板实例化规则等种种微妙之处交汇的地方：它们合起来给出巨大的表达力，也同时暴露出可怕（fearsome）的复杂度"。本节三个子节就是这个交汇区的三份档案。

**§4.5.1 实现技术**。开篇是论文自嘲浓度最高的一段：基础库的"暗黑艺术"（dark arts）——多数程序员一生无需知晓，但新手最爱围观最吓人的模板码并（常错地）布道，博主讲者靠炫技赢声誉，"这是 C++ 名声复杂的**主要来源**；别的语言里这种技巧藏在优化器里或不提供"。随后点名 SFINAE（"代入失败**不**是错误"——候选被剔除而非编译失败）：pair 的赋值"当且仅当两成员都可拷贝赋值"——enable_if＋traits 的实现"极丑但极有用"。C++11 的 type traits 家族（`is_copy_assignable`、`is_nothrow_constructible`……数十个）＋enable_if 全入标准库。机制拆解（论文原文级）：`enable_if<is_copy_assignable<T>::value && is_copy_assignable<U>::value, pair&>::type` 在条件成立时**就是**普通的 `pair&`，条件不成立时特化不提供成员 `type` → 代入失败 → 按 SFINAE 规则**整个声明如同从未写下**，重载集里安静消失（而非报错）；enable_if 的"像模像样"实现只要两个 specialization（false 分支空 struct、true 分支 `typedef T type;`），Boost 首创并入 C++11。论文同时留了一个时间坐标：concepts "为 C++20 提供该能力（**而 GCC 自 2015 年就有**）"——TS 时代"先在 GCC 落地再谈冻结"的路线（6.3/04 册）在这半句话里自证。两条系统级注脚：

- SFINAE 规则"微妙难产"但在用户压力下越改越简——**副作用是编译器内部被迫改进**：失败代入必须无副作用回退，"严重抑制了编译器对非局部状态的滥用"（标准化反哺实现的隐秘案例）；
- 这些设施存在的根因是 concepts 之缺位——"当且仅当"表达只能靠 traits 迂回（→ 04 章三部曲）。

**§4.5.2 元编程支持**。2000s 十年被比作**狂野西部**：技巧无人传授、报错惨烈、编译巨慢、资源耗尽（内存/递归深度/标识符长度）、"人人重新发现问题、重新发明基础技术"。救济双线（论文原分栏）：语言线=concepts（**失败**，→ 04 章）＋constexpr＋lambda＋别名模板＋更精确的实例化规范；库线=tuple＋type traits＋enable_if。结论句："concepts 在 C++11 的失败把场地留给了**通常丑陋易错的 workaround**——典型即 traits＋enable_if 组合。"这段是 04 章三部曲的报幕。

**§4.5.3 noexcept**。完整的"特性生死样本"，论文四段论：

1. 原教旨立场："**最初的异常设计压根没有标示'函数可能抛出'的机制——我今天仍认为那才是正确设计**。"为了让异常进 C++98 才搭售了动态异常规约（运行时检查、解压路径逐层重复检查、源码膨胀）——"如我所料"全数兑现；2010 废弃（Gregor），**C++17 一致投票移除**。
2. 编译期异常检查的持久否决："总有一批人想要编译期检查谁能抛——它在**类型论、小程序、快编译器、源码全控**的场景里工作得很好。委员会反复否决，理由一句话：**它无法扩展到由几十个组织开发维护的百万行程序**（另见 §7.4——05 册主题）。"
3. noexcept 的**出生即务实**：规约退场后库作者面临性能问题——"很多关键场景需要知道**拷贝操作会不会抛**：会抛就必须先取副本以保住异常保证，不会抛就能直接写目标，**性能差距可以非常显著**"。于是 Abrahams/Gregor 提案（[Abrahams et al. 2010; Gregor 2010; Gregor and Abrahams 2009]）带来 noexcept：违约即 terminate，"动态检查仍在，只是把标准异常传播机制**短路**了——开销近乎为零"。
4. **条件 noexcept 才是原始动机**：pair 的移动构造"当且仅当两成员都可移动且移动不抛"才 `noexcept(is_nothrow_constructible<...>::value && ...)`——"在底层与极通用的位置上写出最优码并非易事；在基础层，'该按位拷贝、移动、还是逐成员拷贝'的知识**值整数倍的性能**"。

05 册 s05 实测样例（动态规约之死＋noexcept 违约 terminate）与本节构成"文本-机器"对读。

## 四、C++11 标准库全家福（§4.6）

论文先自贬再自傲："C++ 的标准库历来**小得可怜**，且组件多为地基件而非应用级任务。C++11 补上四大件：threads、regex、chrono、random——'与那些大企业支持库相比显然寒酸，但**质量高**，且相比 C++ 历史上任何一次标准库扩容都是巨量的'。治理教训随附："这些组件的背景差异直接显形为接口风格不一——**除了灵活与高性能，没有连贯的总设计哲学**；C++98 时代尚有入库标准（出自 D&E），C++11 **没有成文的组件准入准则**，来路是'社区里已被验证成功的'——多数来自 Boost（§2.3 的 junior standard 论）。"逐个点名：

- **regex**：主功 John Maddock（2002 起）；谱系是"抄 Unix/JS 经 Boost 并公开致谢"（§2.4 影响论的标本）；
- **unordered_* 哈希容器**：Matt Austern 2001 提案（[wg21.link/n1326](https://wg21.link/n1326) ✅302，"A Proposal to Add Hashtables to the Standard Library"——C++0x 最早批提案之一，差一点赶进 C++98）；命名弃 `hash_map`（早被各家库占光）取 `unordered_map`——Bjarne 反转好评："**指陈它提供什么而非如何实现， arguably 是个更好的名字**"；
- **random**：Jens Maurer 2002 首提、Fermilab 团队修订 2006 定稿；"引擎＋分布"正交设计的成熟度赢得那句美誉——"**每个随机数库长大后都想成为的样子**"，但新手/偶尔用户嫌难用；
- **chrono**：Hinnant 2008 提案；"复杂但**极易用**"的对位样板（`duration_cast<milliseconds>(t1-t0)`），与 thread 库共享时间概念；"用它能让**一年级学生**体会算法数据结构的成本差异"；C++20 的 date/时区（9.3.6）与 `cout << t1-t0` 都长在它身上。

怎么用 → [../c++之旅3/05-标准库概览与字符串正则.md](../c++之旅3/05-标准库概览与字符串正则.md)。

论文对本节的自限也要记下：regex 与 unordered 容器虽"替许多程序员省了大量乏味工作、产出更好的程序"，但"**这些库组件没有实质改变人们组织代码的方式，所以我不详细讨论**"——取舍尺仍是 05 册给 Bjarne 定的 "majorness"（改变人们思考与组织代码的方式）。用这把尺，C++11 真正改变代码组织的是 §4.2–4.5 的语言件；库四大件是"补齐地基"，这个自评同时解释了为什么"没有成文准入准则"的账要到 C++17/C++20 才显形（05 册 8.3、06 册 9.3 收编案）。

## 五、g++ 实测：变参模板＋完全转发，C++98 无路可走

```cpp
// s03.cpp 摘要：一个模板顶替 C++03 的 9 份重载；lambda 替代函数对象
template <class T, class... Args>
unique_ptr<T> factory(Args&&... args) {      // 转发引用：&& 此处是"万能引用"
    return unique_ptr<T>(new T(forward<Args>(args)...));
}
sort(begin(xs), end(xs), [](int a, int b) { return a > b; }); // 4.3.1：不写类也能定制比较
```

已实测 g++ 15.2：`-std=c++98` 失败（**10 个 error**：`'unique_ptr' does not name a type`、`'move' was not declared`…）；`-std=c++11` 通过：

```
hello 42 2.71828 ctors=1
desc: 5 4 3 1 1
```

`ctors=1` 直接验证完全转发链只构造一次目标对象——C++03 时代同样的工厂需要为 0/1/2/3 参数写 4 份模板（真实库写 9–15 份）。

## 最新演进与工业实践

- **C++17/20/23 演化补位**：折叠表达式（论文 §8 特性清单点名 [Sutton and Smith 2014] 一系）终结递归模板尾巴；`std::invoke`/`std::apply`（C++17）补 tuple 工具面；**concepts 接管 enable_if**（C++20，→ [04 章](./04-C++14与概念的三部曲.md)）后，新库（std::execution P2300R10 ✅302）一律用 concept 写约束——Bjarne "狂野西部"时代正式落幕。
- **工业界对应**：fmt（Zverovich，后经 §9.3.7 入标）与 range-v3（Niebler，§9.3.5 前身）是 traits+SFINAE 巅峰与 concepts 后时代的分水岭标本；abseil 至今保留大量 SFINAE（须兼容 C++14 库版本），folly 在 F14 容器等热点处仍 SFINAE/concept 混用——读大厂库源码＝读这一节的活化石。
- **史学钩子（供 05/06 册引用）**：C++11 无成文库准入准则→组件接口风格分裂；这正是 §8.3"variant/optional/any 三件套记法互异"与 §9.3"四件外部库收编案"的远因——**库治理缺位在十年后连本带利偿还**。
- **现代重估**：noexcept 已成为 ABI 级设计语言（vector 增长、移动构造、swap 三件套），Core Guideline F.6/GS.6 一脉源自本节；"deprecate 必败"论在 2024–2026 硬化路线中得到再验证——治理不安全代码靠工具告警（-fsanitize=undefined、GS 检查）而非删语法。
