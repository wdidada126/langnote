## 核心精讲

### 1. 服务器侧开门（⚠️ 转述）
实例启动后经 SVCENAME（dbm cfg）或 services 文件里的 DB2c_实例名 监听 TCP 端口（默认 50000 系惯例）；DPF 环境每分区节点端口顺延——"一个实例一个门，多分区一排门"。

### 2. 编目三件套之一：CATALOG TCPIP NODE（⚠️ 转述）
`CATALOG TCPIP NODE rnode REMOTE host SERVER port`：把"远端服务器的门"登记为本地节点对象；LOCAL_IP/STALE_TIME 等修饰项 ⚠️ 略。节点是"机器+端口"的本地别名。

### 3. 编目三件套之二/三：CATALOG DATABASE 与 DIRECT（⚠️ 转述）
- `CATALOG DATABASE demo AS demoAlias AT NODE rnode`：远端库挂到节点之下进数据库清单；
- 本地实例内库可 `CATALOG LOCAL DATABASE ...`；
- 不编目也能连的"直接连接串"（hostname:port/dbname 形式，JDBC URL 风格）自 9.x 渐成主流，但 CLI/ODBC 老通路仍认清单——两套心智并存是本章最大信息量。【注】UNCATALOG 是逆操作；清单残留清理见 [05](05-环境与实例数据库.md) 误区 1。

### 4. 驱动栈（⚠️ 转述）
- **CLI/ODBC**：C API 与 ODBC 映射，走本地 DB2 客户端安装（Runtime Client 即可）；
- **JDBC Type 2**：JNI 桥到本地库，需客户端安装；
- **JDBC Type 4（JCC）**：纯 Java 直连 TCP，薄部署首选（9.5 语境双 jar，现行换代为单一驱动 jar ⚠️）；
- .NET Provider 等同层配角。
选型三问：客户端能否装 DB2 代码？要不要认证/加密插件？连接池中间件是否只吃 JDBC？

### 5. 认证接口（⚠️ 转述）
CONNECTION AUTHENTICATION 模式：SERVER/CLIENT/DDCS/LDAP 插件谱系；SERVER 模式下"服务器 OS 认账号"是 50000 端口裸奔时代事故重灾区——与 [11](11-安全实现.md) 的认证层直接衔接。

### 6. DPF 连接视角（⚠️ 转述）
连"分区数据库"时节点对象指向协调分区门户，客户端无须感知分区数；跨分区透明性是 DB2 卖点和黑盒之一（全景见 [02](02-DB2全景大图.md)）。

### 7. 排障分层听诊（⚠️ 转述+方法论 ✅）
ping→telnet 端口→`db2 ping`/`db2pd`→编目正确性→认证/权限→`db2diag.log` 时间戳对齐。本章的"分层剥洋葱"是全目录 [15](15-性能与问题诊断.md) 诊断框架的前身。

## 常见误区

1. "编了节点就能连库"——还差 CATALOG DATABASE 一步（或用直连串）。
2. "Type 4 也要装客户端"——恰恰相反，纯 Java 免本地 DB2 代码（jar 名换代 ⚠️）。
3. "别名随便起"——应用配置引用别名，改别名=全量改串。
4. "端口开了=认证过了"——监听与鉴权两层（第 5 讲）。
5. "清单里没有就是网络坏了"——先分清单问题还是网络问题，听诊顺序不可乱。

【微讲堂】经典 TCP 编目两连（示意，⚠️ 非实测）：

```text
db2 CATALOG TCPIP NODE srv1 REMOTE 192.168.1.20 SERVER 60000
db2 CATALOG DATABASE demo AT NODE srv1 AS demoAlias
db2 CONNECT demoAlias USER appuser USING ******
```

## 🔧 类比实验（本章无独立实验）
连接编目是"服务器引擎+OS 网络栈"的合体行为，SQLite/DuckDB 无进程服务器对位面（嵌入式直开文件）；唯一可迁移的直觉是"多文件多库的登记/引用"——E6（[05](05-环境与实例数据库.md)）已演示 ATTACH 会话级引用，注意**非 DB2 行为**且不涉及网络与认证。

## 编目 vs 直连两心智对照

| 维度 | 编目心智（CLI/ODBC 传统） | 直连心智（现代 URL） |
| --- | --- | --- |
| 登记位置 | 本地节点/库清单 | 连接串自带 |
| 换端点 | 改清单重编目 | 改应用配置 |
| 排障入口 | LIST ... DIRECTORY | URL 参数拆解 |
| 存量倾向 | 强（老脚本满地） | 弱（新项目默认） |

【注】编目三件套顺序不可颠倒：先节点、再库、后连接（⚠️ 转述）。
【注】选型一问：驱动与实例是否同机——同机议 Type 2，跨机议 Type 4（⚠️）。

## 核心概念速览（中英对照）

1. **SVCENAME** — 服务名参数: 实例监听端口/服务映射。
2. **编目节点** — Catalog TCPIP Node: 远端门牌的本地登记。
3. **编目数据库** — Catalog Database: 远端库进本地清单。
4. **数据库清单** — Database Directory: 客户端可连库账本（05 联动）。
5. **直连串** — Direct Connection: host:port/db 免编目连接式。
6. **CLI/ODBC** — Call Level Interface: C 层驱动 API。
7. **JDBC Type 2/4** — 两型 Java 驱动: JNI 桥 vs 纯 Java 直连。
8. **JCC** — Java Common Client: IBM 的 Type 4 驱动族。
9. **认证模式** — Authentication: SERVER/CLIENT/LDAP 等插件谱系。
10. **DAS** — 管理服务: GUI 远程管理的辅助服务（03 联动）。
11. **db2 ping/db2pd** — 通路体检: 网络与实例层听诊器。
12. **UNCATALOG** — 撤编目: 清单逆操作。
13. **连接池** — Connection Pooling: 中间件复用物理连接（CLI 语境）。

## 最新演进与工业实践

- **编目淡出**：Db2 11.5 + 现代应用栈里直连 URL（含 TLS 参数）成默认姿势；"清单两件套"退守存量系统运维与 CLI 习惯（⚠️；官方文档入口 https://www.ibm.com/docs/en/db2 curl 200 ✅）。
- **驱动换代**：JCC 双 jar→单构件演进、OSGi 形态等 ⚠️ 细节不写死；Type 2 类本地桥接驱动在多数新栈中绝迹。
- **安全加码**：TLS 1.2/1.3、IAM/令牌式认证（云形态）与加密默认化——本章"SERVER 裸奔"反例在 2024–2026 已属事故级配置（联动 [11](11-安全实现.md) 演进节）。
- **无服务器语境**：Db2 on Cloud/数据库即服务里"编目"被 URL 吞并，但排障分层听诊法完整存续——本章真正不过时的部分是第 7 讲。
- **对照阅读**：驱动/协议世界观可与 MySQL 通信章并读（链接见"联系"节）；连接管理通论以 [../数据库系统概念6.md](../数据库系统概念6.md) 的体系结构章为基线。
