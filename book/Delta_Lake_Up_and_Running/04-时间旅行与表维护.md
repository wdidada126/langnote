## 1. 双坐标时间旅行（⚠️ 文档转述）

```sql
SELECT * FROM t VERSION AS OF 3;
SELECT * FROM t TIMESTAMP AS OF '2023-05-01 09:00:00';
-- DataFrame: spark.read.format("delta").option("versionAsOf", 3)
```

版本号 = 日志序号（02 章），时间戳→版本的映射由 commitInfo 反查；
**旅行能力 = 旧 add 文件还在 + 日志还在**，两个前提都会被维护打断（§4）。
🔧 迷你同构：02 章 §5 的 `snap(V)` 谓词即旅行内核，换 V 即换坐标——
版本/时间双轴在真实系统里只是"日志 ts→version 索引"一层薄糖。

## 2. DESCRIBE HISTORY：把日志读成审计报表

列：version / timestamp / userId / operation / operationParameters / job / reads /
isolationLevel / isBlindAppend / retention 参数快照（⚠️ 转述）。排障三问：
"谁在几点删了分区"（operation+userId）、"这次 overwrite 是不是覆盖了两个分区"
（operationParameters.partitions）、"这版还留着多少可旅行窗口"（retention 列，§4）。
平台侧同名视图 `table_history` 属 DBR 专有 ⚠️。

## 3. RESTORE：回滚不是删日志，是再提交

`RESTORE TABLE t TO VERSION AS OF v`（Delta 2.2+ OSS）：读旧版本的**文件列表**，
差量算出新 add/remove，以一次新提交生效——历史不丢（回滚本身是 v' 之后的新版本），
audit 链完整。对照"误删自救"的另一路：从 VACUUM 前备份目录重新 ADD 文件（重型手段 ⚠️）。
同名姊妹：Iceberg 的 `rollback_to_snapshot`
（[../Use_Iceberg_with_Spark/04-时间旅行与元数据表.md](../Use_Iceberg_with_Spark/04-时间旅行与元数据表.md)）。

## 4. VACUUM 与保留窗口（🔧 本章实测核心）

- 语法：`VACUUM t RETAIN n HOURS`（默认 `delta.deletedFileRetentionDuration`=7 天）；
  删的是"remove 出日志且超窗"的物理文件；孤儿文件另需 `LIST_FAILED_FILES` 类工具补扫（⚠️ 转述）。
- **🔧 毁史实测**（02 章 sqlite 迷你版续集）：VACUUM 清掉 `removed_v<5` 的 3 行死版本后，
  同一条快照读谓词回看 v2 得到 `[(2,b2)]`（真值应为 `[(1,a),(2,b2),(3,c)]`）——
  **旧版本静默给错数据，不报错**。Delta 的保留窗口参数就是给这个坑立的护栏：
  旅行深度 ≤ 保留窗口，VACUUM 前未超窗的文件不动。
- 增量/并行 VACUUM（3.3+/4.x 线）缓解"全目录 LIST 代价"（✅ https://delta.io/blog/delta-lake-3-3/；
  DG 00 缺口表同款话题）。

## 5. 小文件与聚类的三时代（⚠️ 转述）

| 时代 | 工具 | 机制 | 遗留问题 |
| --- | --- | --- | --- |
| 一 | `OPTIMIZE t` | bin-packing 合并小文件（文件级重写、提交原子） | 高并发下与流写者互踩（02 章冲突检查的主角之一） |
| 二 | `ZORDER (a,b)` | 按列簇重排数据布局，强化 min/max 裁剪 | 手工选列、重写全分区 |
| 三 | **Liquid Clustering**（CLUSTER BY，DBR 先熟、OSS 3.x+ 跟进 ⚠️） | 增量聚簇、免分区爆炸、可演化 | 书基线（2023）时多为预览口径，读旧教程当小心 |
| 附 | Predictive IO/自动 OPTIMIZE | 平台层缓存与调度 | 商业专有 ⚠️ |

分区正在退位：新表建议"少分区 + 聚类/跳过"（与 Iceberg 隐藏分区、Paimon bucket 演进的
收敛方向一致，[../Apache_Paimon_Streaming_Lakehouse/03-追加表与数据布局.md](../Apache_Paimon_Streaming_Lakehouse/03-追加表与数据布局.md)）。

## 6. 快照治理的跨格式对表

- **ducklake（🔧 引姊妹实测，注明来源）**：`ducklake_expire_snapshots` 在函数目录在册
  但语义未测；`AT (VERSION => n)` 是唯一正解语法（四连败后实测）；"内联数据未 flush
  则外部引擎不可见"——它的旅行深度受"元数据库 + 已落文件"两端约束（来源：
  [../DuckDB_Up_and_Running/09-云端DuckDB与MotherDuck.md](../DuckDB_Up_and_Running/09-云端DuckDB与MotherDuck.md) 实测二/三）。
- **Iceberg**：`expire_snapshots` + `remove_orphan_files`，且"保留窗口 vs 流消费者
  位点"要协同（[../Apache_Iceberg活用入門/08-表维护操作.md](../Apache_Iceberg活用入門/08-表维护操作.md)）。
- **Paimon**：snapshot 过期 + Tag 钉版 + consumer-id 防追尾（
  [../Apache_Paimon_Streaming_Lakehouse/10-Tag分支与时间旅行.md](../Apache_Paimon_Streaming_Lakehouse/10-Tag分支与时间旅行.md)）；
  Delta 的对应解是浅克隆/深克隆（CLONE，2.1+ ⚠️）与 CDF 消费位点（05 章）。
- 四家共同教训：**时间旅行是收费特性**，价格 = 存储 + 元数据扫描，维护窗口就是账单日。

## 7. 常见误区

| 误区 | 修正 |
| --- | --- |
| "VACUUM 后还能 TRUNCATE 前旅行" | 超窗即毁（🔧 §4 实测）；`RETAIN 0` 是自断后路（仅测试用） |
| "RESTORE 会抹掉之后的历史" | 它只是新版本；历史是只增账本 |
| "OPTIMIZE 保证无重复" | 它合并文件不改行集；防重是 MERGE/幂等写的职责（03 章） |
| "DESCRIBE HISTORY 全量可靠" | 日志被清理/表被 DROP 重建后历史断链 |
| "旅行随便查" | 深度旅行触发旧 checkpoint 链重放 + 可能踩冷存储（对象层取回费 ⚠️） |

## 核心概念速览（中英对照）

- **时间旅行** — Time Travel：按 VERSION/TIMESTAMP 读历史快照。
- **快照读谓词** — Snapshot Predicate：`added_v≤V<removed_v` 的日志解释（🔧）。
- **审计历史** — DESCRIBE HISTORY：提交级操作报表。
- **保留窗口** — deletedFileRetentionDuration：VACUUM 前的法定旅行深度。
- **VACUUM** — 清理：物理删除超窗死亡文件；毁史风险源。
- **孤儿文件** — Orphan Files：不在任何版本文件集里的残留；需专项清理。
- **RESTORE** — 回滚：以历史文件集为内容做一次新提交。
- **OPTIMIZE** — 压缩：bin-packing 重写小文件。
- **Z-ORDER** — 空间填充曲线聚类：多列联合裁剪布局。
- **Liquid Clustering** — 液聚：可演化的增量聚簇，替代手工分区+ZORDER。
- **克隆** — CLONE（shallow/deep）：零拷贝引用/物化两种版本快照导出。
- **快照过期** — Snapshot Expiration：跨格式同题的旅行预算管理。

- **增量/并行 VACUUM** 与 checkpoint v2 族在 3.3→4.x 持续落地（✅

  4.x 线把"维护即产品"推进到 catalog 侧（✅ https://delta.io/blog/2026-02-02-delta-catalog-managed-tables/）。

- **工业实践**：生产湖仓通行"旅行窗口 7 天 + Tag/克隆固化月度口径 + 维护作业错峰"三件套（定性转述）；
