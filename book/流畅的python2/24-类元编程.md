## 核心精讲

### 24.3 三参数 `type()` 造类

```python
# 教学示意，不参与构建
def hello(self):
    return "hi"

# type(类名, 基类元组, 命名空间)
Dynamic = type("Dynamic", (object,), {"greet": hello, "x": 1})
print(Dynamic().greet())        # hi
print(Dynamic.x)                # 1
```

### 24.5 `__init_subclass__`：子类化钩子（现代首选）

```python
# 教学示意，不参与构建 —— Python 3.6+
class PluginBase:
    plugins = []
    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        cls.plugins.append(cls)        # 每有子类自动登记

class A(PluginBase): ...
class B(PluginBase): ...
print(PluginBase.plugins)             # [A, B]
```

### 24.6 类装饰器

```python
# 教学示意，不参与构建
def verbose_init(cls):
    orig = cls.__init__
    def __init__(self, *a, **k):
        print(f"实例化 {cls.__name__}")
        orig(self, *a, **k)
    cls.__init__ = __init__
    return cls

@verbose_init
class Service: ...
```

## 版本演进

- 🔴 **PEP 487 — `__init_subclass__`（3.6）**：本章最重要的「现代结论」——原书把很多能力归到元类，今天应优先用 `__init_subclass__`：它在子类定义时被调用，能完成「登记子类/注入方法」等多数元类任务，且代码更直白、可读。
- **PEP 3115 — Python 3000 Metaclasses（🔧 以官方为准）**：`class X(metaclass=M)` 关键字语法（取代旧 `class X(object): __metaclass__ = M`），3.12+ 一致。
- **PEP 526 — 变量注解（3.6）**：类体内的变量注解（`x: int = 1`）进入命名空间的方式与 `__prepare__`/`__annotations__` 协作，影响元类读取类体注解。
- **PEP 563 / 649 — 注解延迟求值**：3.14 起类体注解默认延迟求值，元类在 `class` 语句执行后读 `__annotations__` 的行为有变化（🔧 以官方为准，呼应 [15-类型提示进阶.md](15-类型提示进阶.md)）。
- **PEP 695 — 类型参数语法（3.12）**：`class C[T]` 的泛型参数在类创建流程中如何与元类交互（🔧 以官方为准）。
- 3.12 `immortal objects`（PEP 683，🔧 以官方为准）：对元类创建的类的内部单例无语义影响。
- 🔧 关于「一个类只能有一个元类」的冲突解决（24.10.3）——若两个元类无共同祖先会 `TypeError`，以官方/社区文档为准给出「用混入+单元类或类装饰器」的规避。

## 近年研究与工业界开源实践（2015–2026）

- **`pydantic` 用元类 + `__init_subclass__` 实现模型**：`BaseModel` 在子类定义时收集字段注解、生成校验器（非同行评审，框架源码）。
- **`dataclasses` 用类装饰器思路**：`@dataclass` 本质是「类装饰器」，印证「装饰器 > 元类」的优先级（见 [05-数据类构建器.md](05-数据类构建器.md)）。
- **Django 的 `Model`/`Form` 元类**：ORM 模型仍用元类收集字段，但新代码倾向把「注册/校验」下沉到 `__init_subclass__`（非同行评审）。
- **SQLAlchemy 2.0 的声明式：`__init_subclass__` + 描述符**：减少元类黑魔法，提升可读性（非同行评审）。

## 常见误区与本书需修正之处

| 原书说法 / 习惯 | 问题 | 2026 正确写法 |
| --- | --- | --- |
| 一上来就写元类 | 元类难读、难调试、易冲突 | 🔴 优先 `__init_subclass__`（3.6）/类装饰器 |
| 忽略「导入时创建类」 | 类体顶层代码 import 时执行一次，副作用难控 | 把重逻辑放 `__init__`/方法，类体只做声明 |
| 认为元类能「任意定制」 | 元类解决「类如何被创建」，不是「运行期行为」 | 运行期逻辑用实例方法/描述符，别塞元类 |
| 「一个类只能有一个元类」冲突 | 两个无共同祖先的元类无法合并 | 用「单元类 + 混入」或「类装饰器」规避 |
| 元类作为公开 API | 元类应是实现细节 | 对使用者隐藏元类，只暴露基类/装饰器 |
| 🔧 元类与 PEP 695 泛型参数交互 | `class C[T]` 的 `T` 在元类命名空间里如何可见 | 以官方文档为准，不要凭旧经验下笔 |
