## 核心精讲

### 14.2 `super()` 的真实含义

```python
# 教学示意，不参与构建
class A:
    def ping(self): print("A.ping")
class B(A):
    def ping(self):
        super().ping()        # 不是「调父类」，而是「按 MRO 调下一个类」
        print("B.ping")

b = B()
b.ping()                     # A.ping / B.ping
print(B.__mro__)             # 显示 C3 线性化顺序
```

### 14.3 子类化内置类型会漏掉覆盖

```python
# 教学示意，不参与构建 —— 展示「内置类型跳过覆盖方法」的坑
class DoppelDict(dict):
    def __setitem__(self, key, value):
        super().__setitem__(key, [value] * 2)   # 想做点魔法

dd = DoppelDict(one=1)
dd["two"] = 2
dd.update(three=3)          # update 是 C 实现，不走 __setitem__！
print(dd)                   # {'two': [2, 2], 'three': 3} —— 不一致

# ✅ 用 UserDict 就不会有此问题
from collections import UserDict
class GoodDict(UserDict):
    def __setitem__(self, key, value):
        self.data[key] = [value] * 2
```

## 版本演进

- **PEP 3135 — `super()` 无参形式（3.0）**：`super()` 不再需要 `super(Cls, self)`，本章用的正是无参形式；3.12+ 不变。
- **PEP 487 — `__init_subclass__`（3.6）**：在类定义时自动收到子类钩子，是「元类轻量替代」，本章 14.7 的「避免元类」建议应补这条（详见 [24-类元编程.md](24-类元编程.md)）。
- **PEP 698 — `@override`（3.12）**：标注「我确实覆盖了父类方法」，静态检查器能发现「以为覆盖了其实没覆盖」的拼写错误，是继承安全性的重要补充。
- 内置类型子类化的坑（14.3）自 Python 3.x 一直存在，涉及 C 实现绕开 Python 层方法；标准库 `collections.UserDict`/`UserList`/`UserString` 仍是官方推荐解法，3.12+ 不变。

## 近年研究与工业界开源实践（2015–2026）

- **Django / DRF 的视图混入体系**：`APIView` + `ListModelMixin`/`CreateModelMixin` 等是 14.6 混入类模式的工业标杆（非同行评审，框架文档）。
- **SQLAlchemy 2.0 的 `DeclarativeBase` 与混入**：用 `Mixin` 组合时间戳/`soft delete` 等横向能力，避免深继承（非同行评审）。
- **`@override`（PEP 698）+ ruff/mypy 进 CI**：在大型继承树里把「漏覆盖」类 bug 前移到静态检查（非同行评审，工具文档）。
- **组合优于继承的再强调**：现代 Python 项目（如 FastAPI 的 `Depends`、依赖注入容器）更倾向组合/注入而非继承（非同行评审）。

## 常见误区与本书需修正之处

| 原书说法 / 习惯 | 问题 | 2026 正确写法 |
| --- | --- | --- |
| 把 `super()` 当成「调父类方法」 | 多重继承下 `super()` 按 MRO 找下一个类，未必是父类 | 理解 `super()` = MRO 中的下一个类 |
| 直接 `class MyDict(dict)` 扩展内置类型 | 内置方法（如 `update`）的 C 实现会绕过覆盖方法 | 继承 `collections.UserDict`/`UserList`/`UserString` |
| 用深继承树组织能力 | 紧耦合、脆弱、难以测试 | 用「混入类 + 组合」拼装横向能力 |
| 多重继承凭直觉猜调用顺序 | 菱形继承顺序不直观 | 查 `Cls.__mro__` 验证，或用 `@override` 显式标注 |
| 忘记「避免子类化具体类」 | 具体类的方法可能改，破坏子类 | 只子类化为「明确为继承设计」的基类 |
| 🔧 元类是「高级继承」 | 元类解决的是「类如何被创建」，不是「复用」 | 多数场景用 `__init_subclass__`/类装饰器即可，见 24 章 |
