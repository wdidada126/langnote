## 二、10.1 CountDownLatch：AQS 共享模式的最小范例

```java
public class CountDownLatch {
    private static final class Sync extends AbstractQueuedSynchronizer {
        Sync(int count) { setState(count); }
        int getCount() { return getState(); }
        // 共享获取：state == 0 才算成功（返回 1），否则入队阻塞（返回 -1）
        protected int tryAcquireShared(int acquires) {
            return (getState() == 0) ? 1 : -1;
        }
        // 共享释放：CAS 递减，减到 0 返回 true（唤醒所有等待者）
        protected boolean tryReleaseShared(int releases) {
            for (;;) {
                int c = getState();
                if (c == 0) return false;                       // 已经归零，不再传播
                int nextc = c - 1;
                if (compareAndSetState(c, nextc))
                    return nextc == 0;
            }
        }
    }
    public void await()        { sync.acquireSharedInterruptibly(1); }
    public void countDown()    { sync.releaseShared(1); }
}
```

三个要点：

1. **共享模式 vs 独占模式**：`CountDownLatch` 用 `acquireShared`/`releaseShared` 而非 `acquire`/`release`——区别是**释放时可以唤醒多个等待者**（`doReleaseShared` 会传播，propagation）。`ReentrantLock` 是独占模式，一次只唤醒一个后继。这是"AQS 两种模式"的教科书对照。
2. **`countDown()` 不阻塞**：它是 CAS 自旋递减，永远不会睡；只有 `await()` 会阻塞。
3. **不可重置**：没有 `reset()`，`state` 归零后 `tryReleaseShared` 直接返回 false。需要可复用就用 `CyclicBarrier` 或 `Phaser`。

> ⚠️ 本书未强调：**`await()` 被中断会抛 `InterruptedException` 且不恢复中断标志**（`acquireSharedInterruptibly` 抛异常出去）。在 catch 里应 `Thread.currentThread().interrupt()` 恢复。
EOF

### 10.1 的现代替代：JDK 8 `CompletableFuture` 与 JDK 21 结构化并发

`CountDownLatch` 的典型用法（等 N 个并行任务完成）在今天有更清晰的写法：

```java
// JDK 8 风格
List<CompletableFuture<Result>> fs = tasks.stream()
    .map(t -> CompletableFuture.supplyAsync(t::call, pool))
    .toList();
CompletableFuture.allOf(fs.toArray(new CompletableFuture[0])).join();

// JDK 21+ 结构化并发（预览于 21/22/23，JEP 453/480；JDK 25 仍有预览 API）
try (var scope = StructuredTaskScope.open(Joiner.awaitAllSuccessfulOrThrow())) {
    var a = scope.fork(() -> queryA());
    var b = scope.fork(() -> queryB());
    scope.join();
    return combine(a.get(), b.get());
}
```

结构化并发的优势是：**作用域结束时所有子任务必然已结束**（不会有"泄漏的线程"），且父任务的取消/超时能自动传播到子任务——这正是 `CountDownLatch` 做不到的事情（用 latch 时，一个子任务卡死会导致主线程永久等待，除非你写 `await(timeout)`）。

## 三、10.2 CyclicBarrier：用 `ReentrantLock + Condition` 而非 AQS 子类

```java
public class CyclicBarrier {
    private static class Generation { boolean broken; }        // "代"，用于复用与破损标记
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition trip = lock.newCondition();        // 所有到达者在此等待
    private final int parties;                                 // 参与方数量
    private final Runnable barrierAction;                      // 屏障动作（可选）
    private Generation generation = new Generation();
    private int count;                                         // 剩余未到达数

    private int dowait(boolean timed, long nanos) throws ... {
        final ReentrantLock lock = this.lock;
        lock.lock();
        try {
            final Generation g = generation;
            if (g.broken) throw new BrokenBarrierException();
            if (Thread.interrupted()) { breakBarrier(); throw new InterruptedException(); }
            int index = --count;
            if (index == 0) {                                   // 最后一个到达者
                boolean ranAction = false;
                try {
                    final Runnable command = barrierAction;
                    if (command != null) command.run();         // ① 先跑 barrierAction
                    ranAction = true;
                    nextGeneration();                           // ② 唤醒所有人 + 重置 count = parties
                    return 0;
                } finally {
                    if (!ranAction) breakBarrier();             // 动作失败 -> 屏障破损
                }
            }
            for (;;) {                                          // 非最后到达者：等
                try {
                    if (!timed) trip.await();
                    else if (nanos > 0L) nanos = trip.awaitNanos(nanos);
                } catch (InterruptedException ie) {
                    if (g == generation && !g.broken) { breakBarrier(); throw ie; }
                    else Thread.currentThread().interrupt();
                }
                if (g.broken) throw new BrokenBarrierException();
                if (g != generation) return index;              // 换代了 -> 放行
                if (timed && nanos <= 0L) { breakBarrier(); throw new TimeoutException(); }
            }
        } finally { lock.unlock(); }
    }
}
```

本书讲得清晰、但值得再强调的四点：

1. **为什么不用 AQS 而要组合 `ReentrantLock`？** 因为屏障需要"**唤醒所有等待者并同时重置计数**"这一复合操作，用 `Condition.signalAll()` + 自管 `count` 更直接；AQS 的共享模式虽然能传播唤醒，但"换代"语义（`generation`）需要额外的对象，组合反而更简洁。这也说明一个设计原则：**AQS 不是万能的，能用组合就别硬套**。
2. **`Generation` 是"可复用"的实现核心**：每次 `nextGeneration()` 就 `trip.signalAll()` + `count = parties` + `generation = new Generation()`。等待者通过 `g != generation` 判断是否被放行，从而天然支持多轮（比如多轮迭代计算的 barrier）。
3. **`barrierAction` 由最后一个到达的线程执行**，且**在所有等待者被唤醒之前**——这是 Javadoc 明确说明的语义，适合做"汇总上一轮结果"这类操作。若 barrierAction 抛异常，屏障**broken**，所有人抛 `BrokenBarrierException`。
4. **`await()` 的返回值 `index`**（最后一个到达返回 0）可用于**选主**：`if (barrier.await() == 0) doLeaderWork();`。

**破损（broken）语义**：任何一个参与者被中断、超时、或 barrierAction 抛异常，屏障进入 broken 状态，**所有**当前及后续 `await()` 都抛 `BrokenBarrierException`，直到调用 `reset()`。这与 `CountDownLatch`（某线程中断不影响别人）不同，是因为屏障要求"全员到齐"，缺一个就没意义。

### 书中的 Solver 例子（并行矩阵分解）

```java
class Solver {
    final int N;
    final float[][] data;
    final CyclicBarrier barrier;
    class Worker implements Runnable {
        int myRow;
        Worker(int row) { myRow = row; }
        public void run() {
            while (!done()) {
                processRow(myRow);
                try { barrier.await(); }                 // 所有行处理完才能进入下一轮
                catch (InterruptedException ex) { return; }
                catch (BrokenBarrierException ex) { return; }
            }
        }
    }
    public Solver(float[][] matrix) {
        data = matrix; N = matrix.length;
        barrier = new CyclicBarrier(N, () -> mergeRows(...));   // 屏障动作：合并本轮结果
        for (int i = 0; i < N; ++i) new Thread(new Worker(i)).start();
    }
}
```

这正是 `CyclicBarrier` 的**设计动机场景**：N 个线程**互相等待**而非"等一个外部事件"，且需要多轮。注意 `await()` 必须处理 `BrokenBarrierException`——**新手常只 catch `InterruptedException` 而编译不过**。

## 四、10.3 Semaphore：AQS 共享模式 + 公平/非公平两版

```java
abstract static class Sync extends AbstractQueuedSynchronizer {
    Sync(int permits) { setState(permits); }
    final int getPermits() { return getState(); }
    // 非公平：不管队列里有没有人在等，直接抢
    final int nonfairTryAcquireShared(int acquires) {
        for (;;) {
            int available = getState();
            int remaining = available - acquires;
            if (remaining < 0 || compareAndSetState(available, remaining))
                return remaining;
        }
    }
    protected final boolean tryReleaseShared(int releases) {
        for (;;) {
            int current = getState();
            int next = current + releases;
            if (next < current) throw new Error("Maximum permit count exceeded");
            if (compareAndSetState(current, next)) return true;
        }
    }
}
static final class FairSync extends Sync {
    protected int tryAcquireShared(int acquires) {
        for (;;) {
            if (hasQueuedPredecessors()) return -1;      // 关键：前面有人排队就老实排队
            ... 同 nonfair ...
        }
    }
}
public void acquire()          { sync.acquireSharedInterruptibly(1); }   // 获取 1 个许可
public void acquire(int p)     { sync.acquireSharedInterruptibly(p); }
public void release()          { sync.releaseShared(1); }                // 归还 1 个许可
public void release(int p)     { sync.releaseShared(p); }
```

四个必须记住的点：

1. **`release()` 不需要持有过 `acquire()`**——任何线程都可以凭空 `release()` 增加许可。这既是灵活之处（可由初始化线程"发放"许可），也是**误用之源**（多 release 会导致限流失效）。
2. **公平版靠 `hasQueuedPredecessors()`** 实现，代价是吞吐量下降（不能 barging）。默认 `new Semaphore(n)` 是**非公平**。
3. **许可数是 `int`**，上限 `Integer.MAX_VALUE`；`next < current` 的溢出检查是必需的。
4. `acquire()` 可被中断；`acquireUninterruptibly()` 不可；`tryAcquire(timeout)` 带超时。

> ⚠️ 本书未展开：JDK 的 `Semaphore` **不支持动态改上限**（没有 `setPermits`）。想做动态限流，应使用 Guava `RateLimiter`、Resilience4j `RateLimiter`、Sentinel，或自己组合 `Semaphore` + 原子调整（缩小需多 acquire，扩大需 release）。

### 现代替代：JDK 21 虚拟线程下的限流

虚拟线程时代，"限制并发数"的正确做法**不是**用信号量阻塞虚拟线程（会钉住 carrier，JDK 24 之前），而是：

```java
// JDK 21+：Semaphore 本身在 JDK 24 后不再 pinning（改用独立锁实现）
// 但对虚拟线程更自然的做法是用有界队列或 StructuredTaskScope 的并发上限
try (var sem = new Semaphore(100)) { ... }
```

JDK 24（JEP 491）之后，`synchronized` 内的阻塞不再钉住 carrier；`Semaphore.acquire` 走 `AbstractQueuedSynchronizer`（内部用 `LockSupport.park`，本身就是"unpark 友好"的），在虚拟线程中是安全的。

## 五、补充：本书没写但生产常用 —— `Phaser` 与 `Exchanger`

| 工具 | JDK | 用途 | 机制 |
| --- | --- | --- | --- |
| `Phaser` | 7 | 多阶段屏障，**参与方可动态注册/注销**（`register`/`bulkRegister`/`arriveAndDeregister`），支持**分层（tiering）**降低大规模争用 | CAS + 一个 long 编码 phase/parties/unarrived |
| `Exchanger` | 5 | 两个线程在**屏障点交换数据**（如生产者/消费者缓冲区双缓冲切换） | 单槽 `Node` + CAS + `LockSupport.park`（`jdk.internal.misc` 的竞技场化避免伪共享） |
| `CountDownLatch` / `CyclicBarrier` / `Semaphore` | 5 | 见上 | AQS |

`Phaser` 用**一个 long 拆成四段**（`phase` 高 32 位、`parties` 中 16 位、`unarrived` 低 16 位），与 `ThreadPoolExecutor` 的 `ctl` 是同一套思路的升级版；它也是分代（phase 递增到 `Integer.MAX_VALUE` 后归零）。**大规模参与方（> 几十）时 `Phaser` 明显优于 `CyclicBarrier`**。

## 六、JDK 版本演进

| 版本 | 变更 | 影响 |
| --- | --- | --- |
| JDK 5 | JSR 166：`CountDownLatch`、`CyclicBarrier`、`Semaphore`、`Exchanger` 全部引入 | 三种范式定型 |
| JDK 7 | `Phaser`（JSR 166y） | 可动态注册的多阶段屏障；`ForkJoinPool` 也在此版本 |
| JDK 8 | `CompletableFuture`、`StampedLock`、LongAdder | `CountDownLatch` 的很多用法被 `CompletableFuture.allOf` 取代 |
| JDK 9 | `Flow` API（响应式） | 异步编排进一步替代显式同步器 |
| JDK 21 | JEP 444 虚拟线程 + JEP 453 结构化并发（预览） | `StructuredTaskScope` 是 `CountDownLatch` 场景下**更安全**的替代品（自动取消/不泄漏线程） |

> 迁移建议：**新代码不要再用裸 `CountDownLatch` 做"等一堆任务"**，优先 `CompletableFuture.allOf`（JDK 8+）或 `StructuredTaskScope`（JDK 21+）。保留 `CountDownLatch` 用于"等外部事件"（如等某个服务启动完成），`CyclicBarrier`/`Phaser` 用于真正的多轮协作，`Semaphore` 用于限流。

**近年研究（2020 后）**：

- **屏障的形式化验证**：2020-2025 年间有多篇用分离逻辑 / Iris（Coq）验证屏障与 latch 的工作（如 *Verifying a Concurrent Barrier with Iris* 类工作），结论是 `Generation`/sense-reversing 这类"分代"设计是能被机器证明正确的最简形式。
- **大规模众核屏障**：ISCA/MICRO 2020-2024 关于 RISC-V / GPU 上硬件加速屏障（`bar.sync`、cluster barrier）的研究，思路与 `Phaser` 的 tiering（分层）完全一致——软件分层，硬件分簇。

- **结构化并发的语义研究**：围绕 JEP 453 的类型系统与作用域语义（如 *Structured Asynchrony with Algebraic Effects*，ICFP 2022 系列工作），把 `StructuredTaskScope` 的取消传播形式化。

## 九、跨语言对比

| 语言 | CountDownLatch 等价物 | CyclicBarrier 等价物 | Semaphore 等价物 | 差异要点 |
| --- | --- | --- | --- | --- |
| **Java** | `CountDownLatch`（一次性） | `CyclicBarrier`（可复用、可选 barrierAction）／`Phaser`（多阶段、动态注册） | `Semaphore`（公平/非公平，许可可凭空增加） | 全部基于 AQS 或 Lock+Condition |
| **Go** | `sync.WaitGroup`（`Add`/`Done`/`Wait`） | 无内置；常用 `errgroup` + channel 或第三方 barrier | 带缓冲 channel（容量即许可数）或 `golang.org/x/sync/semaphore` | **首选 channel**；`WaitGroup` 复用了 `runtime` 的信号量原语，语义比 Java 更严格（`Add` 不能与 `Wait` 并发） |
| **Rust** | 无标准 latch；用 `Arc<(Mutex<usize>, Condvar)>` 或 `tokio::sync::watch` | `std::sync::Barrier`（基于 `Mutex`+`Condvar`，语义等同 `CyclicBarrier`） | `tokio::sync::Semaphore`（async 版）/ `std::sync::Semaphore`（1.85 起稳定） | `Barrier::wait()` 返回 `BarrierWaitResult::is_leader()`，等价于 `CyclicBarrier.await() == 0` 的选主用法 |
| **C++20** | **`std::latch`**（一次性，且不可增加） | **`std::barrier`**（可复用，支持 `arrive_and_wait`、arrival token、completion function ≈ barrierAction） | **`std::counting_semaphore<N>`** | C++20 把这三件套标准化了，**几乎与 Java 一一对应**；`std::barrier` 的 completion function 与 `CyclicBarrier(parties, action)` 完全同构 |
| **Python** | `threading.Event` 组合 | `threading.Barrier`（含 `broken` 语义，与 Java 一致） | `threading.Semaphore` / `asyncio.Semaphore` | 受 GIL 限制；`asyncio` 版本用于协程限流 |
| **Erlang/BEAM** | 无（用消息传递等待 N 条回复） | 无 | 无 | **根本不需要**：进程间无共享内存，靠 mailbox + 超时即可 |
| **C#/.NET** | `CountdownEvent`、`ManualResetEventSlim` | `Barrier`（含 `ParticipantsRemaining`、`SignalAndWait`） | `SemaphoreSlim`（async 友好） | `SemaphoreSlim.WaitAsync` 是 async 时代的标配，Java 直到 21 才有类似体验 |

**横向观察**：
1. C++20 的 `std::latch` / `std::barrier` / `std::counting_semaphore` 几乎是 Java 5 (2004) 设计的**延迟 16 年的标准化复刻**，说明 Java 并发库当初的设计是对的。
2. Go 的取舍最激进：**只提供 `WaitGroup` 和 channel**，屏障/信号量都鼓励用 channel 组合。代价是复杂屏障要手写，收益是"只有一种并发原语"带来的心智统一。
3. Rust 的 async 生态（`tokio::sync`）把每个同步器都做了 async 版本，避免了"阻塞线程"——这与 Java 虚拟线程想解决的问题相同，但 Rust 选择**显式 async/await**（函数染色），Java 选择**隐式挂起**（不改签名）。这是两条路线最本质的分歧。

## 十、误区与纠错

1. ❌ "`CountDownLatch` 可以 reset 后复用" → 不能。要复用用 `CyclicBarrier` 或 `Phaser`；也可以重建一个新 latch（但要注意已 await 的线程）。
2. ❌ "`CyclicBarrier.await()` 只需 catch `InterruptedException`" → 还必须 catch **`BrokenBarrierException`**（受检异常），否则编译不过。
3. ❌ "`Semaphore.release()` 必须先 `acquire()`" → 不必；凭空 release 会增加许可，**容易把限流打穿**。务必配对使用。
4. ❌ "`Semaphore` 能动态改限流值" → 不支持，见第四节。
5. ❌ "`CountDownLatch.await()` 能可靠地等所有任务" → 若某个子任务抛异常而未 `countDown()`，主线程**永久等待**。务必 `try/finally { latch.countDown(); }`，或用带超时的 `await(timeout, unit)`，或改 `CompletableFuture.allOf`（异常会传播）。
6. ❌ "屏障参与方数量可以设很大" → `CyclicBarrier` 是单锁 + `signalAll`，参与方几十以上会严重争用，改用 `Phaser`（支持分层）。
7. ❌ "`Exchanger` 可用于三个线程交换" → 只支持**成对**交换；多余的线程会阻塞等待配对。

## 十一、本章一页纸总结

- 三个同步器是 **AQS 三种范式**的样本：`CountDownLatch`/`Semaphore` = AQS 共享模式；`CyclicBarrier` = `ReentrantLock` + `Condition` 组合。
- **共享模式 vs 独占模式**的关键区别是释放时的**传播唤醒**（`doReleaseShared`）。
- `CyclicBarrier` 的 `Generation` 实现"可复用"，`broken` 状态保证"缺一不可"语义。
- `Semaphore` 的公平性由 `hasQueuedPredecessors()` 决定，默认非公平（吞吐更好）。
- 现代替代：`CompletableFuture.allOf`（JDK 8+）、`StructuredTaskScope`（JDK 21+）、`Phaser`（多阶段）、`std::latch/barrier/semaphore`（C++20 对照）。
