## 二、7.1 ConcurrentLinkedQueue：Michael-Scott 无锁队列的 JDK 版本

结构非常简单：**单向链表 + `volatile Node head/tail` + CAS**。

```java
private static class Node<E> {
    volatile E item;
    volatile Node<E> next;
}

public boolean offer(E e) {
    Node<E> newNode = new Node<>(Objects.requireNonNull(e));
    for (Node<E> t = tail, p = t;;) {
        Node<E> q = p.next;
        if (q == null) {                                   // p 是最后一个节点
            if (casNext(p, null, newNode)) {               // ① CAS 接上（线性化点）
                if (p != t) casTail(t, newNode);           // ② tail 惰性更新
                return true;
            }
        }
        else if (p == q)                                   // ③ 哨兵/自环，跳到 head 重来
            p = (t != (t = tail)) ? t : head;
        else
            p = (p != t && t != (t = tail)) ? t : q;       // ④ 往前走
    }
}
```

三个必须理解的设计点：

1. **tail 不是最后一个节点（惰性更新）**：每 **` hops=2`** 次入队才更新一次 tail —— 均摊掉 CAS tail 的成本。同理 head 也不是第一个有效节点。这是 Doug Lea 对原始 M-S 算法的工程优化。
2. **哨兵节点（self-link）**：出队时把节点的 `next` 指向自己（形成自环），帮助 GC 并让正在遍历的其他线程跳出。
3. **`size()` 是 O(n)**：需要遍历整个链表，且高并发下结果不准 —— **文档明确建议用 `isEmpty()` 替代 `size() == 0`**。这是本书强调的重点，也是生产事故常见来源（在监控/限流里调 size）。

> ⚠️ **本书没强调的点**：`ConcurrentLinkedQueue` **不允许 null 元素**（会用哨兵节点表达），且 **迭代器弱一致**。

## 三、7.2 LinkedBlockingQueue：经典的“两把锁”阻塞队列

```java
final ReentrantLock takeLock = new ReentrantLock();
final ReentrantLock putLock  = new ReentrantLock();
private final Condition notEmpty = takeLock.newCondition();
private final Condition notFull  = putLock.newCondition();
private final AtomicInteger count = new AtomicInteger();   // 跨两把锁的计数，必须是原子的
```

**为什么要两把锁**（这是 Michael & Scott PODC 1996 论文的第二个算法）：
多数场景下队列既不空也不满，入队和出队操作的是**链表的不同端**（tail / head），完全可以并行 —— 用 `putLock` 保护 tail、`takeLock` 保护 head，吞吐显著高于单锁的 `ArrayBlockingQueue`。

入队/出队要点：
- `put`：拿 `putLock` → 入队 → `count.incrementAndGet()` → 若未满则 `notFull.signal()`（**唤醒下一个生产者**）→ 释放锁 → 若入队前 count 为 0 则 `signalNotEmpty()`（**跨锁唤醒消费者**，需先获取 `takeLock`）。
- `take`：对称。这一步“信号级联（cascading notifies）”正是维持高吞吐的关键。
- **容量为 `Integer.MAX_VALUE` 时被称为无界队列** —— 这也是 `Executors.newFixedThreadPool()` 用它的原因（也正因如此，任务堆积会 OOM，见第 8 章）。

```java
// 经典生产者-消费者写法（本书 11.1 会再讲一遍 ArrayBlockingQueue 版本）
BlockingQueue<Task> q = new LinkedBlockingQueue<>(10_000);
while (true) q.take().run();              // take / poll(timeout) / offer(timeout) 全部响应中断
```

## 四、7.3 ArrayBlockingQueue：单锁 + 环形数组

```java
final Object[] items;
int takeIndex, putIndex, count;
final ReentrantLock lock;                // ★ 只有一把锁
private final Condition notEmpty, notFull;
```
- 数组定长 → **构造时必须指定容量**，putIndex/takeIndex 取模形成环形缓冲；
- **一把锁**保护读写两端 ⇒ 吞吐不如 LinkedBlockingQueue，但**内存连续、GC 更友好、可预测性好**；
- 可通过 `new ArrayBlockingQueue<>(cap, true)` 开启**公平模式**（等候最久的线程优先），代价是吞吐下降；
- 不产生 Node 对象 —— 对 GC 敏感场景反而是优势。

**四种阻塞方法的行为差异（务必记牢）**

| 行为 | 插入 | 移除 | 检查 |
| --- | --- | --- | --- |
| 抛异常 | `add(e)` | `remove()` | `element()` |
| 返回特殊值 | `offer(e)` | `poll()` | `peek()` |
| 一直阻塞 | `put(e)` | `take()` | 不适用 |
| 超时退出 | `offer(e, t, u)` | `poll(t, u)` | 不适用 |

## 五、7.4 PriorityBlockingQueue：无界 + 二叉堆 + 自旋扩容

```java
private transient Object[] queue;              // 二叉小顶堆（数组表示）
private transient volatile int allocationSpinLock;  // ★ 扩容时的 CAS 自旋锁
private final ReentrantLock lock;              // 单锁
private final Condition notEmpty;              // 只有一个：因为无界，插入永不阻塞，不需要 notFull
```
- **不是 FIFO**：按比较器排序出队（`Comparator` 或 `Comparable`）；**迭代器无序**（数组顺序不等于优先级顺序）。
- **无界**：这是最容易误用的点 —— 生产者快于消费者时会 OOM（健康检查/告警 P0 常客）。
- **扩容丝滑**：`tryGrow` 用 CAS 抢 `allocationSpinLock`（0→1），抢到才 `Arrays.copyOf`，其余线程在此期间让出 CPU（`Thread.yield()`），避免扩容期间阻塞所有入队线程。
- 不支持 null 元素。

## 六、7.5 DelayQueue：延时出队（Leader-Follower）

```java
private final PriorityQueue<E> q = new PriorityQueue<>();   // 内部还是按到期时间排序的堆
private final ReentrantLock lock;
private final Condition available;
private Thread leader;                                       // ★ Leader-Follower 模式的核心
```
- 元素必须实现 `Delayed`（`getDelay(TimeUnit)` 决定剩余延迟）；
- `take()` 的精髓：只有 **leader** 线程按"最早到期元素的剩余时间"做**定时等待**（`available.awaitNanos`），其余 follower **无限期等待**；leader 到点出队后 `signal()` 下一个；
  → 这避免了"所有消费者都在同一时刻醒来争抢"的惊群，是延时队列的经典实现（也见于 Redis/定时任务框架）。
- 同样无界；典型用途：缓存过期清理、`ScheduledThreadPoolExecutor` 的底层（第 9 章）、重试队列、订单超时取消。

```java
class DelayTask implements Delayed {
    private final long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(3);
    public long getDelay(TimeUnit u) { return u.convert(deadline - System.nanoTime(), TimeUnit.NANOSECONDS); }
    public int compareTo(Delayed o) { return Long.compare(this.deadline, ((DelayTask) o).deadline); }
}
```

## 七、JDK 版本演进

| 版本 | 变化 |
| --- | --- |
| JDK 5 | `ConcurrentLinkedQueue`、`LinkedBlockingQueue`、`ArrayBlockingQueue`、`PriorityBlockingQueue`、`DelayQueue`、`SynchronousQueue` 引入 |
| JDK 7 | `LinkedTransferQueue`、`TransferQueue`（`transfer()` 让生产者等待被消费者取走） |
| JDK 8 | `ConcurrentLinkedQueue` 支持 `spliterator()` / 并行流；迭代器实现改进 |

| **JDK 21** | 🔴 虚拟线程 GA —— 所有 `BlockingQueue.take/put` 的阻塞都不再占用 OS 线程 |
| JDK 21+ | `SequencedCollection`（JEP 431）让双端队列获得更统一的 API |

## 九、近年研究与工业界前沿（2020-2026）

**同行评审论文**

- **安全内存回收（SMR）仍是活跃方向**：hazard pointers 与 epoch-based reclamation 的各种改良（含自动回收）在 2020-2025 年持续出现在 PPoPP / PLDI / SPAA。有趣的是 Java 因为有 GC，从业者几乎不需要显式处理 ABA 与节点回收 —— **GC 本身扮演了 SMR 的角色**，这是托管语言相对 C++/Rust 的显著优势。
- **批处理 / 向量化的队列**：近年工作倾向于批量 enqueue/dequeue 以摊薄 CAS 成本，以及在 GPU/NIC 上做 offload —— 这类研究与 JDK 的通用队列距离较远，但对极致吞吐场景有意义。

**工业界资料（非同行评审）**

- **JCTools**：当前高性能队列的事实参照物，`MpscArrayQueue`、`MpmcArrayQueue` 在特定拓扑下远高于 `ConcurrentLinkedQueue`：https://github.com/JCTools/JCTools
- **LMAX Disruptor**：用 RingBuffer + 缓存填充 + busy-spin 彻底取代队列语义：https://github.com/LMAX-Exchange/disruptor
- **Chronicle Queue / Agrona**（OpenHFT）：堆外内存映射队列，跨越 JVM 生命周期：https://github.com/OpenHFT/Chronicle-Queue
- **Netty**：内部用 JCTools 的 `MpscUnboundedArrayQueue` 承载写入任务，是 "MPSC 拓扑下 SPSC/MPSC 队列远胜通用队列" 的最好工业证据。
