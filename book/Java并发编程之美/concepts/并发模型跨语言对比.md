# 专篇：并发模型的六条路线 —— 从线程锁到虚拟线程，一次看全

> 本书通篇是**"共享内存 + 锁/CAS"**这一条路线（这也是 Java 的主线）。
> 但并发编程至少有**六条**成熟路线：线程锁、Actor、CSP 通道、事件驱动 async/await、
> 软件事务内存（STM）、结构化并发。**不知道其他路线，就不知道自己这条路的边界**。
> 本篇做横向对照，并给出"什么时候该离开 Java 这套模型"的判断依据。

## 一、本章地图

```
六条路线各自的"世界观"与代表作
        ↓
Lauer-Needham 对偶性：消息传递 ≡ 共享内存（1979 就证明了）
        ↓
史上最著名的一场论战：Ousterhout「线程有害」vs von Behren「事件有害」
        ↓
async/await 的"函数染色"问题（为什么它传染）
        ↓
Dijkstra 的 goto 批判 → 结构化并发（从 Kotlin/Swift/Trio 到 JEP 453）
        ↓
Java 的位置：JUC（共享内存）+ Loom（结构化并发/虚拟线程）
        ↓
一张选型决策表
```

## 二、六条路线对照表

| 路线 | 世界观 | 代表作 | 共享状态 | 错误处理 | 背压 |
| --- | --- | --- | --- | --- | --- |
| **① 线程 + 锁/CAS** | 共享内存，用互斥保证正确 | Java JUC、C++ `std::thread`、pthread | 直接共享 | 异常栈，但跨线程断掉 | 需自己用信号量/队列 |
| **② Actor** | 万物皆 actor，只通过**消息**通信，actor 内单线程 | Erlang/OTP、akka/akka-core | **禁止共享** | **监督树（supervision tree）**：父 actor 决定子 actor 崩溃后重启 | 邮箱天然有界/无界可选 |
| **③ CSP 通道** | 进程通过**通道**通信，"通过通信共享内存" | Go（`goroutine` + `channel`）、Rust `std::sync::mpsc`、Occam | 通过通道传递 | 显式传 error（Go）或 panic 传播 | **通道容量即背压** |
| **④ 事件驱动 + async/await** | 单/少线程事件循环，I/O 不阻塞线程 | Node.js、Tokio（Rust）、Python asyncio、C++ Boost.Asio/C++20 协程 | 通常不共享 | 依赖 Promise 链/`.await` 栈 | Reactive Streams / Flow |
| **⑤ STM（软件事务内存）** | 把共享内存的更新包成"事务"，乐观执行 + 冲突回滚 | Haskell STM、Clojure `ref`/`dosync`、Scala ZIO STM | 事务化共享 | 事务回滚，自动重试 | 不适用 |
| **⑥ 结构化并发** | 并发任务有**词法作用域**与父子关系，作用域结束前必须全部完成 | Kotlin 协程、Swift `async let`/`TaskGroup`、Python Trio、**Java `StructuredTaskScope`（JEP 453+）** | 视底座而定 | **父作用域传播子异常**并取消兄弟任务 | 视底座而定 |

## 三、Lauer-Needham 对偶性：这场路线之争其实是个伪命题

> **Lauer, H. C. & Needham, R. M. 1979. "On the Duality of Operating System Structures."**

两位作者证明：**"消息传递系统"与"共享内存（过程调用）系统"是对偶的**——
任何一个都能用另一个实现，且**性能特征相同**。差别只在**编程体验与容错**：

- 消息传递更容易做**故障隔离**（进程间没有共享状态）；
- 共享内存更容易做**细粒度、低延迟**的数据交换。

> 这解释了为什么 Erlang（Actor）在电信交换机上做到 99.9999999% 可用性，
> 而 Java（共享内存）在单机高吞吐上更顺手——**不是谁更"先进"，是取舍不同**。

## 四、史上最著名的一场论战：线程 vs 事件

| 时间 | 论战方 | 主张 |
| --- | --- | --- |
| **1996** | **Ousterhout, "Why Threads Are A Bad Idea (for most purposes)" (USENIX ATC'96)** | 线程太难：锁、死锁、竞态、条件变量难用；**用事件驱动 + 非阻塞 I/O** |
| **2002** | **Adya 等, "Cooperative Task Management Without Manual Stack Management" (USENIX ATC'02)** | 提出"**协程/协作式任务**"作为折中：既保留栈，又避免抢占 |
| **2003** | **von Behren, Condit, Brewer, "Why Events Are A Bad Idea (for high-concurrency servers)" (HotOS'03)** | 事件驱动把控制流**打碎成回调**，调试与错误处理灾难；**用线程 + 改进的调度器** |
| **2007** | **Krohn, Kohler, Kaashoek, "Events Can Make Sense" (USENIX ATC'07)** | 折中：用 **libasync** 之类的库给事件加上"线程式抽象"（Tame） |

**2000 年代的结论**：事件驱动赢了**高并发服务器**（C10K 问题，OS 线程太重）。
**2020 年代的反转**：虚拟线程/协程让"线程"重新变轻，**线程的写法 + 事件的性能**同时拿到
——这就是 Loom、Go、Tokio、Kotlin 协程共同的方向。

> **Java 的时间线**：1996 线程 → 2004 JUC（Doug Lea）→ 2011 NIO/Netty（事件驱动成为事实标准）
> → **2023 JDK 21 虚拟线程（JEP 444）让同步写法回归**。

## 五、async/await 的"函数染色"问题

Bob Nystrom 2015 年的著名文章 **"What Color is Your Function?"** 指出：

```javascript
// 一旦某个函数是 async（蓝色），所有调用它的函数也必须是 async（蓝色）
async function fetchUser() { ... }        // 蓝
function main() { fetchUser(); }          // 红 → 无法 await，只能 .then()
```

| 后果 | 说明 |
| --- | --- |
| **API 传染** | 一个 async 库会强迫整条调用链变成 async |
| **两套库生态** | 同步版与异步版 API 各写一遍 |
| **阻塞调用变"隐形炸弹"** | 在 async 函数里调一个阻塞的同步函数，整个事件循环卡住 |
| **调试栈断裂** | 异步栈被切成片段（除非运行时专门维护 async stack trace） |

**虚拟线程正是对"染色"的回答**：阻塞调用在虚拟线程里是**安全的**，
不需要把函数标成 `async`，因此**不需要染色**。

> 这也解释了为什么 Java 选择了虚拟线程而不是 async/await 语法：
> **Java 有大量存量同步代码（JDBC、servlet、各种 SDK），染色会让它们全部作废。**

## 六、从 `goto` 到结构化并发

**Dijkstra 1968, "Go To Statement Considered Harmful" (CACM 11(3))**
→ 催生了"结构化编程"（`if/while/函数`）→ 控制流有了**词法结构**。

50 年后，同样的论证被应用到并发：

> **Nathaniel J. Smith, "Notes on structured concurrency, or: Go statement considered harmful" (2018)**
> —— `go func() { ... }()` / `executor.submit(...)` 就是并发里的 `goto`：
> **它启动了一个没有边界、没有父节点、无法等待也无法取消的控制流。**

结构化并发的三条规则：

1. **生命周期有作用域**：子任务必须在父作用域结束前结束（类似 `try-with-resources`）；
2. **错误向上传播**：子任务失败 → 自动取消兄弟任务 → 把异常交给父作用域；
3. **取消向下传播**：父作用域取消 → 所有子任务收到中断。

| 语言 | 结构化并发的形式 | 出处 |
| --- | --- | --- |
| Kotlin | `coroutineScope { launch { } }` | kotlinx.coroutines（2017） |
| Swift | `async let` / `withTaskGroup` | Swift Evolution **SE-0304 Structured Concurrency**、SE-0317 `async let` |
| Python | `async with trio.open_nursery()` | Trio（2017，"nursery" 一词即来源） |
| **Java** | `StructuredTaskScope`（含 `ShutdownOnFailure` / `ShutdownOnSuccess`） | **JEP 428（预览）→ JEP 453 → JEP 480 → JEP 505（JDK 25 五度预览）** |
| C++ | `std::execution` sender/receiver（P2300） | C++26 方向 |

> Java 的 `StructuredTaskScope` 详见本目录《结构化并发与ScopedValue》。

## 七、Java 的位置：两条腿走路

```
         Java 并发
          /     \
   共享内存     结构化并发
  （JUC, 2004）  （Loom, 2023）
      |              |
  锁/AQS/CAS     虚拟线程 + StructuredTaskScope
  适合：CPU密集   适合：阻塞 I/O、扇出聚合
  与核数对齐      与并发请求数对齐
```

**决策规则**：

| 你要做的事 | 选哪条腿 |
| --- | --- |
| CPU 密集、可递归分治 | `ForkJoinPool` / `parallelStream`（见《ForkJoin与工作窃取》） |
| 高频共享计数器 | `LongAdder` |
| 阻塞 I/O（HTTP、JDBC、Redis） | **虚拟线程**（JEP 444） |
| 扇出多个 I/O 再聚合 | 虚拟线程 + `StructuredTaskScope` |
| 需要超时/取消的长期链路 | `CompletableFuture`（显式指定 Executor） |
| 事件流、背压、多值 | `java.util.concurrent.Flow` / Reactive Streams |
| 极致延迟、无 GC 抖动 | 专用队列（JCTools / Disruptor）+ 预分配 |

## 八、跨语言速查：同一个需求，六门语言怎么写

**需求：并发拉 3 个 URL，全部成功后合并；任一失败立即取消其余。**

| 语言 | 写法 |
| --- | --- |
| **Java 21+** | `try (var s = new StructuredTaskScope.ShutdownOnFailure()) { var a = s.fork(...); var b = s.fork(...); s.join().throwIfFailed(); }` |
| **Go** | `errgroup.WithContext(ctx)` + `g.Go(func() error {...})` + `g.Wait()` |
| **Kotlin** | `coroutineScope { val a = async { }; val b = async { }; a.await() + b.await() }` |
| **Swift** | `async let a = f(); async let b = g(); return await a + b`（`async let` 自带结构化） |
| **Rust (Tokio)** | `tokio::try_join!(a, b)` 或 `JoinSet`（取消需 `abort()`） |
| **Erlang** | `{ok, A} = ..., {ok, B} = ...` + `pmap` 或 `rpc:pmap`；失败由监督树兜底 |

> 有意思的是：**除了 Java，其他语言很早就有"结构化"版本**。
> Java 到 JDK 21（2023）才补上课，这就是本书（2018, JDK 8）读者最需要补的课。

## 十、近年研究与工业界前沿

### 近年研究

- **结构化并发的形式化**：近年开始有工作把 `StructuredTaskScope` / `TaskGroup` 的语义做成类型系统或效果系统的一部分（Swift、Kotlin、Rust 都有相关探索）。
- **取消语义（cancellation）**：近年共识是"取消是**协作式**的且必须**可组合**"——Go 的 `context`、Rust 的 `CancellationToken`、Java 的中断，三者都在收敛到"取消向下传播、错误向上传播"。
- **并发错误的静态检测**：从 `jcstress`（JMM 验证）到 Go race detector、Rust 类型系统（Send/Sync）、到近年基于 LLM 的竞态检测，检测手段是近年最活跃的工程研究方向。
- **"async 是否还有必要"的再评估**：虚拟线程/协程成熟后，社区正在重估 async/await 的必要性（Rust 因无 GC + 无栈协程的特殊约束，仍坚定选择 async）。

## 十一、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "并发编程就是加锁" | 六条路线，锁只是其中一条；Java 主线是它，但边界要看清 |
| 2 | "Actor 比线程高级" | Lauer-Needham 对偶性：二者**表达能力等价**，差别在容错与工程体验 |
| 3 | "事件驱动一定比线程快" | 那是 OS 线程重的年代；虚拟线程/协程下，同步写法的吞吐已相当 |
| 4 | "async/await 就是最佳实践" | 有**函数染色**代价；Java 明确选择了不染色的虚拟线程路线 |
| 5 | "`go func(){}()` / `executor.submit()` 很方便" | 这是并发里的 `goto`——**无边界、无法等待、无法取消**；用结构化并发替代 |
| 6 | "Java 落后了" | Java 在 2023 才补齐结构化并发，但**一次性补到了与 Swift/Kotlin 同一水平**，且保留了百万存量同步代码的兼容 |
| 7 | "STM 是未来" | STM 在 Haskell/Clojure 很成功，但**I/O 副作用无法回滚**是硬伤；工业界主流仍是锁/通道 |
| 8 | "选一个模型用到老" | 现实是**混合**：CPU 密集用 ForkJoin，I/O 用虚拟线程，事件流用 Flow，延迟敏感用 Disruptor |
| 9 | "Erlang 那套只适合电信" | "让它崩溃 + 监督树"的思想已进入 Kubernetes（重启失败的 Pod）、Actor 已进入 Akka/Pekko |
| 10 | "结构化并发只管生命周期，不管错误" | 恰恰相反：**错误处理是它的一半**（`ShutdownOnFailure` 自动取消兄弟任务） |

> **本书补充定位**：本书（2018, JDK 8）通篇只有"共享内存 + 锁/CAS"一条路线。
> 本篇给出全局地图，让读者知道自己学的东西在什么位置、边界在哪、
> 以及**JDK 21 之后的 Java 已经补齐了哪些拼图**。
> 建议与《结构化并发与ScopedValue》《虚拟线程Loom》《CompletableFuture与异步编排》三篇连读。
