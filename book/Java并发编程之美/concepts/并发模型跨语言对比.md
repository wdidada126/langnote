# 并发模型跨语言对比

> 定位：《Java并发编程之美》第 1—2 章的主线是「Java 平台线程 + 共享内存 + synchronized/volatile」；本篇把这条路线放回坐标系，横向对比 Go、Rust、C++、Erlang/BEAM、Python、C# 的选择，解释为什么 JDK 21 还要再发明虚拟线程。

## 一、是什么（最小示例）

并发模型只回答一个问题：**一段需要等待的工作，由谁调度、在哪让出、让出后状态存在哪**。据此主流分三条路线。

```java
// 路线 A：平台线程（thread）——本书基线 JDK 8
ExecutorService pool = Executors.newFixedThreadPool(4);
Future<Integer> f = pool.submit(() -> http.get("/api/user/42").length()); // 阻塞即挂起
int n = f.get();                                  // 阻塞等待，栈约 1MB，OS 线程 1:1

// 路线 B：虚拟线程（coroutine）——JDK 21，写法与 A 完全一致
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<Integer> g = exec.submit(() -> http.get("/api/user/42").length());
    int m = g.get();                              // 挂起的是虚拟线程，载体线程立刻去干别的
}

// 路线 C：async/await（Future + 回调状态机）——JDK 8 CompletableFuture
CompletableFuture<Integer> c = CompletableFuture
        .supplyAsync(() -> http.get("/api/user/42"), pool)
        .thenApply(String::length);               // 显式编排，拿到的是"未来的值"而不是值
```

三条路线的差异不在语法，而在**阻塞的代价**：

| 路线 | 阻塞一个任务的代价 | 单机并发上限 | 代码形状 |
| --- | --- | --- | --- |
| 平台线程 | 占住一个 OS 线程 + MB 级栈 | 千级 | 同步代码 |
| 协程 / 虚拟线程 | 只占堆上一段续延（continuation） | 百万级 | 同步代码 |
| async / await | 只占一个状态机对象 | 百万级 | 显式 async+await，**函数染色** |

- **函数染色（function coloring）**：`async` 函数只能被 `async` 函数调用，同步函数调不动它，于是「异步」像颜料一样沿调用链向上蔓延（Bob Nystrom, *What Color Is Your Function?*, 2015）。协程路线（Go、虚拟线程、Erlang）在阻塞点自动保存并恢复续延，从语言层面**抹掉了这滴颜色**——这正是虚拟线程相对 `CompletableFuture` 最大的工程价值。
- **代价反转**：协程并非免费。调度权交给了运行时；一旦在协程里跑 CPU 密集循环，或在 `synchronized` 里阻塞，虚拟线程会被**钉住（pinned）**在载体线程上，直接退化成普通线程池。

## 二、实现原理（源码级）

### 调度层：1:1、M:N 与协作式

| 语言 | 调度单位 | 映射 | 让出方式 |
| --- | --- | --- | --- |
| Java 8 平台线程 | `Thread` | 1:1 OS 线程 | 抢占式，内核调度 |
| Java 21 虚拟线程 | `VirtualThread` | M:N，载体是 `ForkJoinPool` | 协作式，库层阻塞点 `Continuation.yield()` |
| Go | goroutine | M:N，G-M-P 模型 | 协作式，函数调用/网络/`channel` 处让出 |
| Rust tokio | task | M:N，多线程 work-stealing 运行时 | 协作式，`await` |
| Erlang/BEAM | process | M:N，每核一个 scheduler | 抢占式，按 reduction 计数强制切换 |
| Python asyncio | coroutine | N:1，单线程事件循环 | 协作式，`await` |
| .NET | Task | M:N，`ThreadPool` | 协作式，`await` |

### 内存模型：x86-TSO 与 ARM 的分歧

```cpp
// HotSpot：JMM 的可见性最终落到 CPU 屏障上（orderAccess_linux_x86.inline.hpp）
inline void OrderAccess::storeload() { fence(); }
inline void OrderAccess::fence() {
  if (os::is_MP()) __asm__ volatile ("lock; addl $0,0(%%rsp)" : : : "cc", "memory");
}
// AArch64 上对应的是 dmb ish / ldar / stlr，没有 x86 那种"免费的 TSO"
```

- **x86-TSO**：硬件只允许 Store→Load 一种重排（源于 store buffer），故 `volatile` 写只需在写后插一条 StoreLoad 屏障（`lock addl` 或 `mfence`），LoadLoad/StoreStore 零成本。
- **ARM/POWER**：弱内存模型，四类重排都可能，每次 `volatile` 访问都要 `dmb ish`，成本显著更高。这是「x86 上跑通的无锁代码搬到 ARM 就崩」的根因。
- **Rust 把这个问题编译期封死**：`Send`（所有权可跨线程转移）与 `Sync`（引用可跨线程共享）是 auto trait，`Arc<T>` 仅在 `T: Send + Sync` 时才 `Send`，因此数据竞争在 safe Rust 中不可表达；代价是 `Rc<RefCell<T>>` 这类共享可变状态无法跨线程使用。
- **BEAM 直接绕开**：进程间不共享内存，只发送不可变消息（大二进制走引用计数共享堆），既没有内存模型问题也几乎不会死锁，但吞吐受消息拷贝成本约束。

## 三、JDK 版本演进

| 版本 | 与并发模型相关的变化 |
| --- | --- |
| JDK 8 | 本书基线：`ForkJoinPool`（第 4 章）、`CompletableFuture`、`StampedLock`、`LongAdder`；并发模型仍是"平台线程池 + 显式异步编排" |
| JDK 9 | `Flow`（Reactive Streams 四接口）进入 JDK；`VarHandle`（JEP 193）；`CompletableFuture.orTimeout` |
| JDK 15-18 | 🔴 **JEP 428 之前**：Loom 以预览形式孵化 `java.lang.Continuation`（内部 API，未导出） |
| JDK 19 | 🔴 **JEP 425 虚拟线程（预览）**：`Thread.ofVirtual()`，M:N 协程首次进入 `java.lang` |
| JDK 21 | 🔴 **JEP 444 虚拟线程正式转正**；**JEP 453 `StructuredTaskScope`（预览）**——结构化并发，把线程生命周期绑定到代码块作用域 |
| JDK 22-24 | JEP 464/480 `StructuredTaskScope` 继续预览并调整 API；JEP 471 计划弃用 `sun.misc.Unsafe` 的内存访问方法 |
| JDK 21+ | 虚拟线程 + `StructuredTaskScope` 合起来，等于给 Java 补上了 Go 的 `goroutine`+`errgroup` 体验 |

## 五、近年研究与工业界实践（2020-2026）

| 项目 | GitHub 地址 | 看点 |
| --- | --- | --- |
| OpenJDK Project Loom | https://github.com/openjdk/loom | `VirtualThread` + `Continuation` 的完整实现，虚拟线程从孵化到 JEP 444 的全部代码演进 |
| Go runtime | https://github.com/golang/go | `src/runtime/proc.go` 中的 G-M-P 调度器、`netpoll` 与 `async preemption`（Go 1.14 起的异步抢占） |
| tokio | https://github.com/tokio-rs/tokio | Rust 异步运行时的工业标准：多线程 work-stealing、`task` 状态机、`io_uring` 支持 |
| rayon | https://github.com/rayon-rs/rayon | Rust 的 fork/join 数据并行库，用 `Send`/`Sync` 编译期保证并行安全，是 `parallelStream` 的类型安全版本 |
| Erlang/OTP | https://github.com/erlang/otp | BEAM 的 reduction 抢占式调度与 per-scheduler 运行队列，OTP 24+ 的 `erpc`/多队列迁移 |
| CPython（free-threading） | https://github.com/python/cpython | PEP 703 移除 GIL 的 3.13 实验分支：偏向引用计数 +  immortalization + 临界区锁 |
| stdexec（P2300 参考实现） | https://github.com/NVIDIA/stdexec | C++26 `std::execution` 的 sender/receiver 模型实现，把异步执行与调度器解耦 |
| kotlinx.coroutines | https://github.com/Kotlin/kotlinx.coroutines | 结构化并发（`CoroutineScope` 取消传播）的成熟范式，Java `StructuredTaskScope` 的对照物 |
| .NET runtime | https://github.com/dotnet/runtime | `ThreadPool` 的 hill-climbing 注入算法 + `async/await` 状态机下沉到运行时 |

实践结论（2020 年后的行业共识）：**IO 密集用协程/async，CPU 密集用线程池**。虚拟线程让 Java 的 IO 密集服务可以用同步代码写出接近 Netty 的吞吐，但 `parallelStream`、ForkJoin 这类 CPU 并行不受益于虚拟线程——它们受核数限制，不是受栈限制。

## 六、常见误区 + 跨语言对照

| 误区 | 真相 |
| --- | --- |
| "虚拟线程更快" | 虚拟线程不提高单请求速度，它提高的是**并发密度**（同样的 RAM 能挂更多请求）。CPU 密集任务用它会更慢 |
| "async/await 一定比线程省" | 省的是内存不是 CPU；状态机分配与调度本身有开销，且带来函数染色与栈信息丢失 |
| "Rust 没有数据竞争所以没有并发 bug" | `Send`/`Sync` 只保证无数据竞争，**逻辑死锁、活锁、消息顺序错误**一样会发生 |
| "Go 的 channel 就是 CSP 全部" | CSP 要求通信是同步会合；Go channel 有缓冲，语义上已偏离 Hoare 原始 CSP |
| "x86 正确即 ARM 正确" | 见第二节：弱内存模型下需要 `dmb`，无锁代码必须按 acquire/release 语义重写 |
| "GIL 让 Python 多线程无用" | IO 密集与 C 扩展（numpy 等）会释放 GIL；3.13 的 free-threading 构建正在拆除这一限制 |

**跨语言速查表**：Java 平台线程 ≈ C++ `std::thread`（1:1）；Java 虚拟线程 ≈ Go goroutine ≈ Erlang process ≈ Kotlin 协程；`CompletableFuture` ≈ Rust `tokio::spawn` + `JoinHandle` ≈ C# `Task` ≈ Python `asyncio.Task`；`StructuredTaskScope` ≈ Go `errgroup.Group` ≈ Kotlin `coroutineScope` ≈ Swift `withTaskGroup`。
