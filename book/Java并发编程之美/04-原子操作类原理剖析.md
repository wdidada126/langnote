## 二、核心精讲

### 4.1 AtomicLong：单点 CAS + 自旋

```java
// JDK 8 实现（本书基于它）
public final long incrementAndGet() {
    for (;;) {
        long current = get();
        long next = current + 1;
        if (compareAndSet(current, next))     // 失败就重试（自旋）
            return next;
    }
}
```

本质问题：N 个线程竞争**同一个热点变量** → N-1 次 CAS 失败/每轮 → 总线事务 + cache line 乒乓 → **吞吐随线程数增长反而下降**。

原子类家族一览（JDK 8）：

| 类别 | 类 |
| --- | --- |
| 基本类型原子类 | `AtomicBoolean`、`AtomicInteger`、`AtomicLong` |
| 数组 | `AtomicIntegerArray`、`AtomicLongArray`、`AtomicReferenceArray` |
| 引用类型 | `AtomicReference`、`AtomicStampedReference`（带版本 → 解 ABA）、`AtomicMarkableReference` |
| 字段更新器 | `AtomicIntegerFieldUpdater`、`AtomicLongFieldUpdater`、`AtomicReferenceFieldUpdater` |
| **累加器（JDK 8 新增）** | `LongAdder`、`DoubleAdder`、`LongAccumulator`、`DoubleAccumulator` |

### 4.2 LongAdder：把热点"拆散"（本书最重要的一节）

核心思想 —— **空间和时间的交换**：一个变量撑不住，就拆成一堆变量，最后求和。

```
              ┌─ base (无竞争时直接用这里 CAS，快路径)
LongAdder ────┤
              └─ Cell[] (竞争发生时按线程哈希映射到不同 Cell)
                 每个 Cell 用 @Contended 填充 → 互不干扰（第 2.11 节的落地！）
                 sum() = base + Σ cells[i].value      // 弱一致：不加锁，期间可能有并发更新
```

```java
// Striped64.longAccumulate 的简化语义（JDK 8）
public void add(long x) {
    Cell[] cs; long b, v; int m; Cell c;
    if ((cs = cells) != null || !casBase(b = base, b + x)) {   // ① 先试 base
        boolean uncontended = true;
        if (cs == null || (m = cs.length - 1) < 0 ||           // ② cells 未初始化
            (c = cs[getProbe() & m]) == null ||                // ③ 映射到的槽位为空
            !(uncontended = c.cas(v = c.value, v + x)))        // ④ 槽位 CAS 失败
            longAccumulate(x, null, uncontended);              // ⑤ 走慢路径：初始化/扩容/换槽
    }
}
```

慢路径 `longAccumulate` 做了三件事（本书 4.2.2 的精华）：
1. **初始化**：用 `cellsBusy`（一个简单的 CAS 自旋锁）保护 `cells` 数组的创建，首次只建 **2 个** Cell；
2. **扩容**：单个 Cell 持续 CAS 失败 → 认为是冲突 → **翻倍扩容**（上限受 CPU 核数约束：`NCPU`）；
3. **rehash**：如果槽位为空，分配新 Cell；分配失败/仍冲突则用 `ThreadLocalRandom` 的 probe 重新哈希换槽。

```java
@sun.misc.Contended static final class Cell {   // ★ 每个 Cell 独占一个 cache line
    volatile long value;
    Cell(long x) { value = x; }
    final boolean cas(long cmp, long val) { return UNSAFE.compareAndSwapLong(this, valueOffset, cmp, val); }
}
```

**为什么 LongAdder 在高并发计数上碾压 AtomicLong**：
| 场景 | AtomicLong | LongAdder |
| --- | --- | --- |
| 无竞争 | 更快（一次 CAS 就完） | 略慢（多一次判断） |
| 高竞争累加 | 惨不忍睹（CAS 成功率 ~1/N） | 近似线性扩展（落到不同 Cell） |
| 读取即时精确值 | ✅ `get()` 精确 | ❌ `sum()` 是**弱一致**快照 |

> **实践口诀**：`LongAdder` 适合 **统计/计数** 这类"写多读少、读的时候不强求精确"的场景（QPS、监控指标、错误计数）；需要"读改写"复合逻辑或精确读取时用 `AtomicLong`。

### 4.3 LongAccumulator：带自定义运算的可扩容累加器

```java
// identity 是「幺元」：必须满足 accumulator.apply(identity, x) == x
LongAccumulator max = new LongAccumulator(Long::max, Long.MIN_VALUE);   // 求最大值
max.accumulate(7); max.accumulate(3);
System.out.println(max.get());   // 7
```
与 `LongAdder` 的差别：
- `LongAdder` 是 `x + y` 的特例版，只做加法；
- `LongAccumulator` 提供任意 `LongBinaryOperator`，但要求运算**满足结合律**（`(a op b) op c == a op (b op c)`）且 `identity` 为幺元，否则结果无定义。
- `DoubleAdder/DoubleAccumulator` 内部用 `doubleToRawLongBits` / `longBitsToDouble` 做位运算下的 CAS。

## 三、JDK 版本演进

| 版本 | 变化 |
| --- | --- |
| JDK 8 | `LongAdder`/`LongAccumulator`/`Striped64` 引入（本书基线）；`AtomicInteger` 内部仍是 `Unsafe.compareAndSwapInt` |
| **JDK 9** | 🔴 **JEP 193 引入 `VarHandle`**，`java.util.concurrent.atomic` 全部改写为 VarHandle 实现；`compareAndSet` 内部不再是 Unsafe；JDK 8 已有的 `getAndUpdate`/`updateAndGet`/`accumulateAndGet` 等 lambda 风格方法在 JDK 9 起改用 VarHandle 实现 |
| JDK 9 | `AtomicInteger` 等方法变为 `@HotSpotIntrinsicCandidate`（JIT 内建，`LOCK XADD` 直接生成） |
| **JDK 17/23/24** | `sun.misc.Unsafe` 逐渐退役（JEP 403/471/498），但由于 **JDK 9 起 atomic 已改用 VarHandle**，你自己的代码几乎不受影响 —— 这是 OpenJDK 最成功的一次解耦 |
| JDK 21+ | 虚拟线程本身不影响 atomic 语义，但**百万虚拟线程同时打同一个 AtomicLong 会更糟**；与之相对，`LongAdder` 在虚拟线程数量远超 CPU 时会因为 `cells` 上限=NCPU 而失去分散优势（这是本书没讲的新现象） |

```java
// JDK 17+ 推荐的写法（无需 Unsafe，同样的性能）
private volatile long n;
private static final VarHandle N;
static { /* lookup().findVarHandle(...) */ }
void bump() { N.getAndAdd(this, 1); }        // 与 AtomicLong.incrementAndGet 等价
```

## 五、近年研究与工业界前沿（2020-2026）

**同行评审论文**

- 近年围绕 CAS 原语最有代表性的理论工作之一是**可放宽一致性的计数器**：
  - Alistarh, Brown, Kopinsky 等关于 **relaxed/non-linearizable counters** 的研究（如 *Relaxed Linearizability* 系列、Alistarh 等的 *The Semantics of Relaxed Data Types* 方向）在理论上解释了为什么像 `LongAdder.sum()` 这种"不精确但很快"的结构是合法的。（这批工作集中在 2015-2019 前后，之后持续被引用与工程化。）
  - 2020 年以后的活跃方向是**持久化内存上的失败原子计数**与**近数据处理**（Pnmdève）：例如 Friedman 等的 NVTraverse（PPoPP 2021）讨论持久数据结构遍历一致性问题。
- 工业界近年没有产生新的"标准可扩展计数器"，但 **Linux 内核的 per-CPU 计数器**与 JUC 的 `LongAdder` 是同一思想的两个著名实现（先在局部累加、读取时再汇总）。

**工业界资料（非同行评审）**

- `ConcurrentHashMap.size()` / `mappingCount()` 直接使用了和 `LongAdder` 同款的 **CounterCell 散布计数**（见 [concepts/ConcurrentHashMap演进.md](concepts/ConcurrentHashMap演进.md)）。
- Micrometer/Dropwizard Metrics：`LongAdder` 是 HTTP QPS/延迟直方图累积的默认选择。
- JMH 基准是判断"用 Atomic 还是 Adder"的唯一可靠方法（见 [00-总览与阅读地图.md](00-总览与阅读地图.md) 的工具链一节）。

## 六、常见误区 / 本书需修正之处

1. ❌ **`LongAdder` 是 `AtomicLong` 的全面升级替代品** —— 不是：需要精确值或 CAS 读改写语义时仍然要用 `AtomicLong`；`sum()` 是遍历 cells 的快照，并发更新期间不精确。
2. ❌ **`increment()` 是原子的，所以多线程计数一定准** —— `increment()` 本身没有返回值且不计加剧，多线程下并不能获得递增值序列（想获得递增值请用 `incrementAndGet()`）。
3. ❌ **`LongAccumulator` 的 identity 随便给** —— 必须是该运算的幺元，且运算需满足结合律，否则 `get()` 结果不确定（原书 4.3 提醒过，但容易被忽略）。
4. ⚠️ **本书源码基于 JDK 8 的 `Unsafe.compareAndSwapLong`** —— 从 JDK 9 起你读 OpenJDK 源码会看到 VarHandle 版本，**语义一致但代码不同**；跟着本书读 8u 源码，看新版源码请对照 VarHandle。
5. ⚠️ **虚拟线程时代的反直觉现象**：`LongAdder` 的 cells 数组上限是 `NCPU`，意味着百万虚拟线程会压缩到 NCPU 个 Cell 上争用 —— 此时应该考虑**每个任务聚合后批量汇入**，而不是靠 LongAdder 自动扩展。

## 七、跨语言对照

| 语言 | 计数器方案的等价物 | 说明 |
| --- | --- | --- |
| Java（本书） | `AtomicLong` / `LongAdder`（分散热点 + `@Contended` 填充） | JDK 内置了 std 级别的可扩展计数器并默认做好填充，这是 Java 相对其他语言偏领先的一面 |
| C++ | `std::atomic<int64_t>`；std 无 Striped 版本。工业界做法：手工 `thread_local` 累加 + 合并（folly/abseil 中有 equivalents） | `std::atomic` 在热点竞争下与 `AtomicLong` 一样会崩 |
| Rust | `std::sync::atomic::AtomicU64`；常用 `Relaxed` ordering 求性能；可使用 `crossbeam` 提供的手工 striped counter | Rust 没有语言内置的 LongAdder 等价物 |
| Go | `sync/atomic.Int64`；Go runtime 内部广泛使用 per-P（per-processor）计数器，读取时汇总 | 与 `Striped64` 高度一致的 locality-first 思路 |
| Erlang/Elixir | `counters` 模块（OTP 21+），提供 `write_concurrency` 选项，本质就是把 counter 分散到多个 scheduling slot | **counters** 模块的 `write_concurrency` 选项本质上提供了类似 LongAdder 的效果 |
