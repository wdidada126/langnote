## 二、11.1 异步日志打印模型（pp.284-293）

**模型**：业务线程（生产者）把日志事件 `offer` 进 `ArrayBlockingQueue`，一个专门的日志线程（消费者）`take` 出来落盘。核心收益是**把磁盘 IO 从请求线程上摘掉**，避免慢磁盘拖垮响应时间。

```java
public class AsyncLogger {
    private final BlockingQueue<LogEvent> queue = new ArrayBlockingQueue<>(1024);
    private final Thread worker = new Thread(this::drain, "async-logger");

    public void log(LogEvent e) {
        // 关键：绝不阻塞业务线程
        if (!queue.offer(e)) {                 // offer 失败（队列满）-> 降级
            fallback(e);                       // 直接同步写 / 丢到另一个溢出文件 / 计数上报
        }
    }
    private void drain() {
        while (running) {
            try { write(queue.take()); }       // take 阻塞在这里
            catch (InterruptedException ie) { Thread.currentThread().interrupt(); break; }
        }
    }
}
```

**三个必须注意的坑**（本书点到了前两个）：

1. **队列必须有界**：用 `LinkedBlockingQueue` 无界会在磁盘卡顿时堆积到 OOM。**有界 + 溢出降级策略**才是正确设计。
2. **`offer` 而不是 `put`**：`put` 在队列满时会阻塞业务线程，那"异步"就白做了——IO 压力会从磁盘传导回业务线程池。**降级比阻塞好**。
3. **本书没强调的：日志丢失与顺序**。异步意味着进程崩溃时队列里的日志会丢；多线程 `offer` 也可能导致乱序（若严格要求顺序，需单生产者或用 `Mpsc` 队列 + 序号）。

**2024-2026 的实际情况**：这套手写模型在生产上基本**已被成熟框架取代**：

| 方案 | 地址 | 特点 |
| --- | --- | --- |
| **Log4j2 AsyncAppender + LMAX Disruptor** | https://github.com/LMAX-Exchange/disruptor | 现在的事实标准。用 RingBuffer 替代 `ArrayBlockingQueue`，无锁 + 无伪共享，吞吐高一个量级；`AsyncLogger` 走全异步（无需 Appender 包装） |
| **Logback `AsyncAppender`** | https://github.com/qos-ch/logback | 内部就是 `ArrayBlockingQueue`，可配 `discardingThreshold`、`neverBlock` |
| **JCTools `MpscUnboundedArrayQueue`** | https://github.com/JCTools/JCTools | 多生产者单消费者，比 JDK 队列更快的替代件 |
| **Chronicle-Queue** | https://github.com/OpenHFT/Chronicle-Queue | 内存映射文件的持久化队列，崩溃也不丢 |

> 结论：这一节的**设计思想（有界队列 + 不阻塞生产者 + 溢出降级）永不过时**，但别再手写，直接用 Log4j2 + Disruptor。

## 三、11.2 Tomcat 的 NioEndPoint 中 ConcurrentLinkedQueue 的使用（pp.293-300）

书中以 Tomcat 8 的 `NioEndpoint` 为例说明无锁队列的真实用法：

- **生产者 = Acceptor 线程**：`serverSocket.accept()` 拿到新连接，包装成 `PollerEvent` 后 `poller.register()`，内部是 `events.offer(event)`（`ConcurrentLinkedQueue` 或 Tomcat 自研的 `SynchronizedQueue`）。
- **消费者 = Poller 线程**：`events.poll()` 取出事件，把 `SocketChannel` 注册到 `Selector` 上，之后由 `SocketProcessor` 交给业务线程池（`Executor`）。

**为什么这里用 `ConcurrentLinkedQueue` 而不是阻塞队列？**

1. Acceptor 线程**绝对不能被阻塞**（阻塞了就没人 accept 新连接，直接影响建连成功率）。`ConcurrentLinkedQueue.offer()` 是**非阻塞**的。
2. Poller 线程用 `selector.select(timeout)` 已经有一个天然的"事件循环 + 等待"机制，不需要队列再提供阻塞语义——取不到就下一轮 selector 循环。
3. 事件量是**多个生产者（Acceptor/其他线程）→ 单个消费者（一个 Poller）**，正是 M-S 队列最擅长的 MPSC 场景。

**架构图（简化）**：

```
Acceptor(1)  --offer-->  events: ConcurrentLinkedQueue  --poll-->  Poller(N, 每个持一个 Selector)
                                                                        |
                                                                        v
                                                              SocketProcessor --> Executor(业务线程池)
```

> ⚠️ **版本演进提示**：本书基于 Tomcat 8。Tomcat 9/10/11 的 `NioEndpoint` 已改用**自研的 `SynchronizedQueue<E>`**（`org.apache.tomcat.util.threads` / `util.collections` 包下），它用一个 `synchronized` + `LinkedList` 实现，并支持 `SynchronizedStack` 做对象池复用——Tomcat 团队实测发现，在这个"事件量不大 + 需要复用对象减少 GC"的场景下，**朴素同步 + 对象池比无锁队列更快**。这是一个非常有教育意义的反例：**无锁不等于更快，要看场景**。
>
> 另外 Tomcat 10.1+ 还引入了虚拟线程执行器（`VirtualThreadExecutor`，JDK 21+）的实验性支持。

## 四、11.3 ConcurrentHashMap 使用注意事项（p.300）

**书中核心结论**：`ConcurrentHashMap` 的**单个方法**是线程安全的，但**复合操作不是**。

```java
// ❌ 错误：check-then-act 不是原子的，两个线程可能都 put 成功
if (!map.containsKey(key)) {
    map.put(key, value);
}

// ✅ 正确姿势 1：putIfAbsent（原子）
map.putIfAbsent(key, value);

// ✅ 正确姿势 2：computeIfAbsent（JDK 8+，且保证"计算只执行一次"）
map.computeIfAbsent(key, k -> loadFromDb(k));

// ✅ 正确姿势 3：用 LongAdder/AtomicLong 做计数，而不是 get-then-put
map.computeIfAbsent(key, k -> new LongAdder()).increment();
```

**必须记住的四点**：

1. **`size()` / `isEmpty()` 在并发下是估算值**，不要用它做精确的业务判断（如"够 100 个就刷盘"）。需要精确控制就自己维护 `AtomicLong` 或用 `LongAdder`。
2. **`computeIfAbsent` 的计算函数里不能再改这个 map**（会死锁或抛 `IllegalStateException`——递归更新）。JDK 8 的 `ConcurrentHashMap` 在 `computeIfAbsent` 里对同一个 bin 加锁，递归更新同一个 bin 会**死锁**（JDK-8062841，在 JDK 9 修复为抛异常）。
3. **迭代器弱一致**，不抛 `ConcurrentModificationException`，但可能看不到最新写入。
4. **key/value 都不能是 null**（与 `HashMap` 不同），因为 `get(key) == null` 要能明确表示"不存在"。

**演进与纠错**：
- `ConcurrentHashMap` 从 JDK 7 的 `Segment` 分段锁 → JDK 8 的 `Node` 数组 + CAS + `synchronized` 单 bin 锁 + 红黑树（>8 转树，<6 退化），并发度从"段数"提升到"数组长度"。
- **本书未提**：`ConcurrentHashMap` 在 JDK 8 之后有 `forEach`、`reduce`、`search` 等并行批量操作（`parallelismThreshold` 参数），会在**ForkJoinPool.commonPool** 上并行执行——注意这会占用公共池，CPU 密集任务要谨慎。
- 相关专篇见 [concepts/ConcurrentHashMap演进.md](concepts/ConcurrentHashMap演进.md)。

## 五、11.4 SimpleDateFormat 是线程不安全的（pp.304-309）

`SimpleDateFormat` 内部持有一个 `Calendar` **可变字段**，`parse/format` 过程中会修改它，因此**多线程共享一个实例会得到错乱结果**（甚至抛 `ArrayIndexOutOfBoundsException` 或解析出错误日期）。

**四种解法，按推荐度排序**：

| 方案 | 代码 | 评价 |
| --- | --- | --- |
| **① `DateTimeFormatter`（JDK 8+，首选）** | `private static final DateTimeFormatter F = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");` | **不可变、线程安全**，可直接 `static final`。配 `LocalDateTime`/`ZonedDateTime` |
| ② 每次 `new` | `new SimpleDateFormat(p).parse(s)` | 正确但**开销大**（每次要建 Calendar、解析 pattern），高频场景不可接受 |
| ③ `ThreadLocal` 包装 | `private static final ThreadLocal<SimpleDateFormat> TL = ThreadLocal.withInitial(() -> new SimpleDateFormat(p));` | 经典方案；**务必配合线程池的 `remove()`**（见 11.10） |
| ④ 加锁 / commons-lang3 `FastDateParser` | `synchronized` | 正确但串行化，吞吐差 |

```java
// 推荐写法（JDK 8+）
private static final DateTimeFormatter FMT = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
String s = LocalDateTime.now().format(FMT);
LocalDateTime t = LocalDateTime.parse(s, FMT);
```

> **延伸**：同样有"静态可变状态"问题的还有 `NumberFormat`、`DecimalFormat`、以及很多第三方库的老式工具类。判定标准很简单——**看它有没有可变的实例字段**。JDK 8 的 `java.time` 包（`JSR 310`）全部设计为不可变，是这个历史问题的终极答案。
> **格式化性能**：JDK 17+ 的 `DateTimeFormatter` 已做过大量优化；若仍是热点，可考虑预编译的格式化库（如 `net.time4j`、或自己缓存 `DateTimeFormatter` 实例——它本身就是线程安全的，不需要 `ThreadLocal`）。

## 六、11.5 使用 Timer 时需要注意的事情（pp.309-313）

`java.util.Timer` 的三个致命问题（本书逐一分析）：

1. **单线程**：`Timer` 只有一个工作线程。若某个任务执行很久，后面的任务全部被推迟；若任务是 `fixedRate`，还会堆积补跑。
2. **一个任务抛未捕获异常 → 整个 Timer 线程终止**，所有后续任务**永久停止**，且**没有任何日志**。
3. **使用 `System.currentTimeMillis()`（墙钟）**：系统时间被调整（NTP 校时、手动修改）会导致定时任务错乱。

```java
// ❌ 不要这样
Timer timer = new Timer();
timer.schedule(new TimerTask() {
    public void run() { doWork(); }        // 抛异常 -> 整个 timer 死掉
}, 1000, 5000);

// ✅ 正确：ScheduledThreadPoolExecutor
ScheduledExecutorService ses = Executors.newScheduledThreadPool(4, namedFactory);
ses.scheduleWithFixedDelay(() -> {
    try { doWork(); }
    catch (Throwable t) { log.error("scheduled task failed", t); }   // 兜住异常！
}, 1, 5, TimeUnit.SECONDS);
```

**为什么 `ScheduledThreadPoolExecutor` 更好**：
- 多线程（可配 `corePoolSize`），一个任务慢不影响其他。
- 一个任务抛异常只会终止**该任务自己**（但见第 9 章：周期性任务仍会静默终止，所以**异常兜底永远要做**）。
- 用 `System.nanoTime()`（单调时钟）不受墙钟跳变影响。

> *补充*：`Timer` 的 API 还有一个坑——`schedule(TimerTask, long delay)` 传的是 `Date`（墙钟）或 `long`（相对），混用容易出错。JDK 官方文档早已建议用 `ScheduledThreadPoolExecutor` 替代 `Timer`。

## 七、11.6 对需要复用但是会被下游修改的参数要进行深复制（pp.314-318）

**问题**：一个配置对象/集合被多个线程共享，其中某个下游方法**就地修改**了它（如 `list.remove()`、`map.put()`、`Date.setTime()`），于是其他线程看到被污染的数据。

**原理**：这不是"并发"问题而是**可变共享状态**问题——即使单线程，同一个对象被复用也会出事。并发只是把概率放大成必然。

**解法（按推荐度）**：

| 方案 | 说明 |
| --- | --- |
| **① 不可变对象（首选）** | `List.copyOf()` / `Map.copyOf()`（JDK 9+）、`Collections.unmodifiableList()`、Builder 模式、`record`（JDK 16+）。编译期/运行期都拒绝修改 |
| ② 防御性拷贝 | 入参进来先 `new ArrayList<>(src)`；出参返回前也拷贝。**注意是深拷贝还是浅拷贝取决于元素是否可变** |
| ③ 线程封闭 | 每个线程一份（`ThreadLocal`）或每次新建 |

```java
// JDK 9+ 的不可变集合工厂（真正的不可变，不是包装视图）
List<String> safe = List.copyOf(mutableList);
Map<String, Integer> safeMap = Map.copyOf(mutableMap);
// JDK 16+ record：天然不可变 + 值语义
public record QueryParam(String uid, List<String> tags) {
    public QueryParam { tags = List.copyOf(tags); }   // 紧凑构造器里做防御性拷贝
}
```

> **性能提醒**：无脑深拷贝会带来 GC 压力与 CPU 开销。正确做法是**分清所有权**：如果对象只在本方法内使用且下游不修改，就无需拷贝；跨层传递、进入并发容器、或交给不可信代码时才需要。Rust 的所有权系统本质上就是在编译期把这件事做完了（见第九节跨语言对比）。

## 八、11.7 创建线程和线程池时要指定与业务相关的名称（pp.319-325）

**为什么重要**：`jstack`、`arthas`、`async-profiler` 输出里看到的是 `Thread-12`、`pool-3-thread-5` 时，**你完全无法判断这段代码属于哪个业务**。一个好名字能把故障定位时间从小时级降到分钟级。

```java
// ① 单个线程
new Thread(task, "order-pay-callback").start();

// ② 线程池：自定义 ThreadFactory（不要用默认的！）
ThreadFactory named = new ThreadFactory() {
    private final AtomicInteger n = new AtomicInteger(1);
    public Thread newThread(Runnable r) {
        Thread t = new Thread(r, "order-service-pool-" + n.getAndIncrement());
        t.setDaemon(false);
        t.setUncaughtExceptionHandler((th, e) -> log.error("uncaught in {}", th.getName(), e));
        return t;
    }
};
ExecutorService pool = new ThreadPoolExecutor(8, 8, 0, MILLISECONDS,
        new ArrayBlockingQueue<>(1000), named, new CallerRunsPolicy());

// ③ 更简洁：Guava / commons-lang3
ThreadFactory f = new ThreadFactoryBuilder().setNameFormat("rpc-pool-%d").build();      // Guava
ThreadFactory g = new BasicThreadFactory.Builder().namingPattern("job-%d").build();     // commons-lang3
```

**命名规范建议**：`<服务名>-<用途>-<序号>`，如 `trade-pool-1`、`trade-scheduler-1`。同时建议配套设置：
- `UncaughtExceptionHandler`（避免异常静默消失——这与 11.9 的 `FutureTask` 异常问题直接相关）
- 是否守护线程（`daemon`）——**业务线程池必须是非守护线程**，否则 JVM 会在 GC only 时直接退出。
- JDK 21+ 可用 `Thread.ofVirtual().name("vt-", 0).factory()` 生成带名虚拟线程工厂。

> **额外建议（本书未提）**：配合 Micrometer/Arthas 把线程池的 `poolSize`、`queueSize`、`completedTaskCount`、`rejectedCount` 暴露成指标。没有监控的线程池等于"盲飞"。dynamic-tp（https://github.com/dromara/dynamic-tp）就是为此而生。

## 九、11.8 程序结束记得调用 shutdown 关闭线程池（pp.325-329）

**问题**：线程池的工作线程是**非守护线程**且持有 `workQueue.take()` 阻塞，`main` 结束后 JVM **不会退出**（因为还有非 daemon 线程存活）。在 Web 容器里则表现为**应用卸载后线程泄漏**，多次 redeploy 后线程数爆炸。

**标准优雅停机三件套**：

```java
pool.shutdown();                                   // 1. 停止接收新任务
try {
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {   // 2. 等待存量任务完成
        pool.shutdownNow();                        // 3. 超时则尽力中断
        if (!pool.awaitTermination(10, TimeUnit.SECONDS))
            log.error("pool did not terminate");
    }
} catch (InterruptedException ie) {
    pool.shutdownNow();
    Thread.currentThread().interrupt();
}
```

配套手段：
- Spring：`ThreadPoolTaskExecutor.setWaitForTasksToCompleteOnShutdown(true)` + `setAwaitTerminationSeconds(30)`；或实现 `DisposableBean` / `@PreDestroy`。
- 容器：在 `ServletContextListener.contextDestroyed` 或 Spring Boot 的 `ApplicationRunner` 对应销毁钩子里做。
- JDK 21+：`StructuredTaskScope` 的 `try-with-resources` 从语言层面保证了作用域结束即关闭——**这是结构化并发最大的实用价值**。

> ⚠️ 误区：`shutdownNow()` 不能真正杀线程（见第 8 章）。任务里必须响应中断或设定超时，否则停机仍会卡住。

## 十、11.9 线程池使用 FutureTask 时需要注意的事情（pp.329-335）

**问题 1：异常被吞**。`submit()` 返回的 `FutureTask` 会把任务抛出的异常捕获进 `outcome`，**不调用 `get()` 就永远不会暴露**。

```java
Future<?> f = pool.submit(() -> { throw new RuntimeException("boom"); });
f.get();     // 这里才抛 ExecutionException(cause=RuntimeException)
// 不调 get() -> 任务"静默失败"，日志里什么都没有
```

对比 `execute()`：异常会冒泡到 `runWorker` → 线程终止 → `UncaughtExceptionHandler`（若没设置则打印到 stderr）。所以**两者行为不同**，混用会踩坑。

**兜底方案**（三选一，建议全做）：
1. 重写 `afterExecute`，若 `Throwable == null` 且任务来自 `submit`，主动 `Future.get()` 触发异常日志（注意 JDK 的实现细节：需要把 `FutureTask` 强转）；
2. 任务体内 `try/catch(Throwable)`；
3. 设置 `ThreadFactory` 的 `UncaughtExceptionHandler` + 优先用 `execute()`。

**问题 2：`cancel()` 的语义**。
- `cancel(false)`：若任务**尚未开始**则不再执行；若**已在运行**，则**任其跑完**，只是 `isCancelled()` 为 true。
- `cancel(true)`：若已在运行，会发 `interrupt()`——但同样**不能强制停止**，取决于任务是否响应中断。
- `cancel` 后调 `get()` 会抛 `CancellationException`。

**问题 3：`get()` 无限期阻塞**。永远用带超时的版本：

```java
try { Result r = f.get(3, TimeUnit.SECONDS); }
catch (TimeoutException e) { f.cancel(true); }        // 超时即取消
```

**2024-2026 的现代写法**：

```java
// JDK 8+：CompletableFuture 的组合与异常处理链
CompletableFuture.supplyAsync(() -> query(), pool)
    .orTimeout(3, TimeUnit.SECONDS)                    // JDK 9+
    .exceptionally(ex -> fallback())
    .thenAccept(this::render);

// JDK 21+：结构化并发，作用域结束自动取消所有未完成子任务
try (var scope = StructuredTaskScope.open(Joiner.awaitAllSuccessfulOrThrow())) {
    var f1 = scope.fork(() -> queryA());
    var f2 = scope.fork(() -> queryB());
    scope.joinUntil(Instant.now().plusSeconds(3));     // 超时 -> 自动中断子任务
    return combine(f1.get(), f2.get());
}
```

结构化并发**从根本上解决了 FutureTask 的三个问题**：异常必然传播（`awaitAllSuccessfulOrThrow`）、超时必然取消、`try-with-resources` 保证没有泄漏任务。

## 十一、11.10 使用 ThreadLocal 不当可能会导致内存泄漏（pp.336-344）

这是全书最重要的一节，也是面试/生产事故最高频的一节。三个场景：

### 11.10.1 为何会出现内存泄漏

```java
static class ThreadLocalMap {
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;                                  // ← 强引用！
    }
}
```

- `ThreadLocalMap` 的 **key 是弱引用**（`WeakReference<ThreadLocal>`），**value 是强引用**。
- 当外部对 `ThreadLocal` 实例的强引用消失（如 `tl = null`），GC 后 key 变成 `null`，但 **value 仍然被 `Thread.threadLocals` 强引用链持有**：`Thread → ThreadLocalMap → Entry → value`。
- 只要线程不死，这条链就不断 → **value 泄漏**。
- `ThreadLocalMap` 在 `get/set/remove` 时会**顺带清理 key 为 null 的脏 Entry**（`expungeStaleEntry`），但这只是"机会主义清理"，**不保证及时**。
- 最坏情况：一个 static 的 `ThreadLocal`（key 永不回收）+ 线程池（线程永生）→ **value 永久泄漏，且随请求数增长**。

### 11.10.2 在线程池中使用 ThreadLocal 导致的内存泄漏

线程复用 → `threadLocals` 复用 → 上一次请求 set 的 value 会**污染**下一次请求（更常见的是**数据串号**而非 OOM，比如把 A 用户的 traceId 打到 B 用户的日志里）。

**正确写法**：

```java
try {
    tl.set(value);
    doWork();
} finally {
    tl.remove();          // ← 必须在 finally 里 remove
}
```

### 11.10.3 在 Tomcat 的 Servlet 中使用 ThreadLocal 导致内存泄漏

Tomcat 用线程池处理请求，且 **webapp 热部署时会重建 ClassLoader**。若某个 `ThreadLocal` 的 value 类型由 webapp 的 ClassLoader 加载，而线程是容器级的（不属于 webapp），则：

```
容器线程 → ThreadLocalMap → Entry → value（webapp 类）→ webapp ClassLoader → 所有 webapp 类
```

结果是 **redeploy 后旧 ClassLoader 无法被 GC**，多次部署后 Metaspace OOM。Tomcat 为此专门做了**线程泄漏检测**：关闭时会扫描所有线程的 `threadLocals`，发现 webapp 类的 value 就打 WARN 日志（`The web application [xxx] created a ThreadLocal with key of type ... but failed to remove it`），并尝试反射清理。

### 2024-2026 的新情况

| 主题 | 现状 |
| --- | --- |
| **`ScopedValue`（JDK 25 正式化，JEP 506）** | 虚拟线程时代 `ThreadLocal` 的替代品：**不可变**、绑定在**作用域**上（`ScopedValue.where(...).run(...)`）、退出作用域自动失效，无需 `remove()`，且**继承到子虚拟线程的开销是 O(1)**（结构化的，不像 `InheritableThreadLocal` 要拷贝整个 map） |
| **虚拟线程 + ThreadLocal** | 百万虚拟线程 × 每个都带 ThreadLocalMap → 内存放大严重。**虚拟线程里应避免滥用 ThreadLocal** |
| **transmittable-thread-local（TTL）** | https://github.com/alibaba/transmittable-thread-local —— 解决"线程池场景下 ThreadLocal 无法从父线程传递"的问题，是链路追踪（SkyWalking/ARMS）的事实依赖 |
| **FastThreadLocal（Netty）** | Netty 用数组下标替代 hash 表，避免 ThreadLocal 的哈希冲突与弱引用清理开销 |

```java
// JDK 25：ScopedValue 用法
static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();
ScopedValue.where(CURRENT_USER, user).run(() -> handle());   // 作用域结束自动解绑
```

> 详细专篇见 [concepts/ThreadLocal与内存泄漏.md](concepts/ThreadLocal与内存泄漏.md)。

## 十二、11.11 总结 —— 本书实践篇的 12 条军规

1. 异步化要用**有界队列**，生产者用 `offer` 不阻塞，队列满要有**降级**。
2. 无锁队列适用于"多生产单消费 + 消费者有自己的事件循环"；**无锁不一定更快**（Tomcat 的反例）。
3. `ConcurrentHashMap` 只保证单方法原子，**复合操作用 `computeIfAbsent`/`putIfAbsent`**；别用 `size()` 做精确判断。
4. 格式化用 **`DateTimeFormatter`**（不可变）；老式 `SimpleDateFormat`/`NumberFormat` 一律不共享。
5. 定时器用 **`ScheduledThreadPoolExecutor`**，任务体必须 `try/catch(Throwable)`。
6. 跨层传递的对象要么**不可变**，要么**防御性拷贝**。
7. 线程/线程池**必须命名**，并设置 `UncaughtExceptionHandler`。
8. 程序退出时 `shutdown()` + `awaitTermination()` + `shutdownNow()`。
9. `submit()` 的异常在 `Future.get()` 里，务必 `get(timeout)` 或改 `CompletableFuture`/结构化并发。
10. `ThreadLocal` 用完 **`finally { remove(); }`**；新代码优先 `ScopedValue`。
11. 线程池参数：有界队列 + 合理拒绝策略 + 监控埋点，**禁止 `Executors` 工厂**（见第 8 章）。
12. 中断是**协作式**的，`shutdownNow`/`cancel(true)` 都只是发信号。

## 十六、附录 D：跨语言对照 —— 这些坑在别的语言里存在吗

| 坑 | Java | Go | Rust | C++ |
| --- | --- | --- | --- | --- |
| 线程局部存储泄漏 | `ThreadLocal` 弱 key + 强 value → 泄漏；线程池放大 | **无 ThreadLocal**（设计上拒绝）；用 `context.Context` 显式传递 | `thread_local!` + `RefCell`；作用域结束自动 drop，`Drop` 保证清理 | `thread_local` 有析构，但线程池复用同样有残留风险 |
| 日期格式化线程不安全 | `SimpleDateFormat` 不安全 → `DateTimeFormatter` | `time.Format` 无状态，安全 | `chrono` 格式化无状态，安全 | `std::strftime` 无状态；`std::put_time` 需注意 locale（全局可变） |
| 定时器异常终止 | `Timer` 全死；`ScheduledExecutor` 静默停周期任务 | `time.Ticker` 配合 goroutine，panic 只崩自己（除非无 recover 崩进程） | `tokio::time::interval`，任务 panic 只影响该 task | asio 需自己 catch |
| 复合操作不原子 | `ConcurrentHashMap` 需 `computeIfAbsent` | map 本身不加锁，需 `sync.Map` 或 mutex | 编译期要求 `Mutex`/`RwLock`，**共享可变状态无法绕过 borrow checker** | 需显式 `std::mutex`；无编译期强制 |
| 线程池命名 | 需自定义 `ThreadFactory` | goroutine 无名字（只有 ID），调试靠 `runtime.Stack` 与 pprof 标签 | 需 `Builder::name` | 需 `pthread_setname_np` |
| 忘记关闭执行器 | JVM 不退出 | goroutine 泄漏（进程不退出） | runtime drop 时取消所有 task | 需 join |

**一句话总结**：Rust 用类型系统把 11.6/11.10 类问题**消灭在编译期**；Go 用"不要通过共享内存来通信"把 11.3/11.10 类问题**转化为 channel 问题**；Java 的选择是**提供强大的库 + 靠规范与工具（阿里手册、SpotBugs、Arthas）兜底**——本书实践篇就是这套"规范"的集大成。
