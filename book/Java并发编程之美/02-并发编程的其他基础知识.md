## 二、核心精讲

### 2.1-2.3 概念域

```
并发 concurrency：多个任务在同一时间「区间」内交替推进（宏观同时，微观可能串行）
并行 parallelism：多个任务在同一「时刻」真正同时执行（需多核）
线程安全：多线程按任意交序执行（不修改代码、不做额外同步），都能得到正确结果
```

共享变量分类（本书划分）：
- **不可变对象**（`final` + 安全发布）天然线程安全；
- **绝对线程安全**（调用方无需任何额外措施）；
- **相对线程安全**（单个操作安全，特定顺序调用仍需外部同步，如 `Vector`）；
- **线程兼容**（对象本身不安全，调用方通过同步正确使用，如 `ArrayList`/`HashMap`）；
- **线程对立**（无论怎样同步都不能并发使用，已罕见）。

> **现代视角**：Doug Lea 的 Javadoc 严格区分 *thread-safe* / *conditionally thread-safe* / *not thread-safe* / *thread-hostile* —— 这是 JUC 源码注释里最重要的阅读线索。

### 2.4 内存可见性 —— 为什么 `i++` 的"看不见"

```
Thread A (CPU-0)                       Thread B (CPU-1)
 myObj.x = 1   → 写入自己的 store buffer / L1 cache
                                        r = myObj.x → 读的是旧副本
```
原因有三层，缺一不可：
1. **CPU 缓存一致性协议**（MESI）虽然最终会同步，但存在时间窗，且 store buffer invalidation 是异步的；
2. **Store buffer / Store forwarding** 让写延迟可见；
3. **编译器/JIT 重排序**可能把看似无关的读提前、写延后（在不违反单线程语义的前提下）。

**Java 的答案：Java 内存模型（JMM）** —— 用 happens-before 规则给出"什么时候写一定对读可见"的契约。详见 [concepts/JMM与happens-before.md](concepts/JMM与happens-before.md)。

> ⚠️ **本书隐含的 x86 假设**：原书例子在 x86 上往往"跑不出问题"，因为 x86 是较强的 TSO 模型（只有 StoreLoad 一种重排序被允许）。但 **ARM/POWER/RISC-V 允许更多重排序**，苹果 M 系列与国产 ARM 服务器普及后，"在我机器上跑不出来"已不成立。这正是要多用 jcstress、少靠手跑的原因。

### 2.5 synchronized —— HotSpot 的实现与 2026 年的锁升级路径

编译后的字节码是成对的：
```java
synchronized (obj) { i++; }
// 反汇编： monitorenter ... monitorexit ... monitorexit(异常路径)
```
同步方法则靠方法表的 `ACC_SYNCHRONIZED` 标志。

**对象头 Mark Word**（64 位）承载 monitor 状态。本书讲的经典路径是：

```
无锁 → 偏向锁(Biased) → 轻量级锁(Lightweight) → 重量级锁(Heavyweight/Monitor)
```

🔴 **2026 年必须修正**：

| 阶段 | 本书（JDK 8） | 现在 |
| --- | --- | --- |
| 偏向锁 | 默认开启，`-XX:+UseBiasedLocking` | **JDK 15 JEP 374 废弃并默认关闭，后续版本移除**；相关 JVM 参数已失效 |
| 轻量级锁 | CAS 对象头 + 自旋 | 仍存在，配自适应自旋 |
| 重量级锁 | OS mutex + 内核阻塞 | 仍存在，但**JDK 24 JEP 491 之前**，若在 synchronized 内部阻塞虚拟线程会**钉住(pin)** carrier 线程；JEP 491 已修复此限制 |
| 锁粗化/锁消除 | JIT 优化（逃逸分析） | 仍成立 |

```java
// JDK 24+ 的正确理解：synchronized 里阻塞虚拟线程不再钉住 OS 线程（JEP 491）
// 因此在 JDK 24+ 可以把 synchronized 与虚拟线程自由组合；JDK 21-23 时这是个著名坑。
```

**synchronized 的内存语义**（本书 2.5.2）：
- 进入 synchronized：等价于 acquire，使本地缓存失效，因而**能看到前一个 monitor-enter 之前的所有写**；
- 退出 synchronized：等价于 release，把本地写刷新到主内存；
- 这正是 JMM 用 happens-before 描述的"**monitor 规则**"：对一个锁的解锁 happens-before 于随后对这个锁的加锁。

### 2.6 volatile

`volatile` 提供两件事，且**只提供这两件事**：
1. **可见性**：写立即对其他线程可见（写后加 StoreStore + StoreLoad 屏障，读前加 LoadLoad + LoadStore 屏障）；
2. **禁止指令重排序**：volatile 写不能与之前的读写重排；volatile 读不能与之后的读写重排。

```java
// 经典用法①：状态标志
volatile boolean shutdown;
// 经典用法②：双重检查锁定(DCL)单例 —— volatile 是必须的
class Singleton {
    private static volatile Singleton inst;   // ★ 少了 volatile 就是 bug
    static Singleton get() {
        if (inst == null) {
            synchronized (Singleton.class) {
                if (inst == null) inst = new Singleton();
            }
        }
        return inst;
    }
}
```
**为什么 DCL 必须 volatile**：`new Singleton()` 有三步 —— ① 分配内存 ② 初始化对象字段 ③ 把引用赋给 `inst`。没有 volatile 时 ②③ 可重排，另一个线程可能看到**非 null 但未初始化**的引用。

❌ **volatile 不保证复合操作的原子性**：`volatile int i; i++;` 仍是三步（读-改-写），多线程 ++ 会丢计数。要原子性请用 `AtomicInteger` / `synchronized` / `LongAdder`（第 4 章）。

### 2.7 原子性操作 & 2.8 CAS

```
CAS(V, A, B): 如果 V 的值等于期望值 A，就原子地把它更新为 B，否则失败（返回 false 或当前值）
```
在 HotSpot 里最终落到 CPU 指令：x86 的 `LOCK CMPXCHG`（带 lock 前缀，广播缓存行失效+全序）；ARM 的 `LDXR/STXR`（LL/SC 循环）。

**三大经典问题**：
1. **ABA 问题**：值从 A→B→A，CAS 误以为没变过。解决：`AtomicStampedReference`（带版本号）/ `AtomicMarkableReference`（带 bool）。
2. **循环时间长开销大**：竞争激烈时 CAS 反复失败。解决：`LongAdder` 分散热点（第 4 章）、退避、或改用锁。
3. **只能保证一个共享变量的原子操作**：多变量需要把字段打包到一个对象，用 `AtomicReference`。

🆕 **JDK 9+ 的正确写法是 VarHandle**（本书只有 Unsafe）：

```java
class Counter {
    volatile int value;
    static final VarHandle VALUE;
    static {
        try { VALUE = MethodHandles.lookup().findVarHandle(Counter.class, "value", int.class); }
        catch (ReflectiveOperationException e) { throw new ExceptionInInitializerError(e); }
    }
    void inc() { VALUE.getAndAdd(this, 1); }                 // 原子加
    boolean cas(int exp, int upd) { return VALUE.compareAndSet(this, exp, upd); }
    void lazySet(int v) { VALUE.setRelease(this, v); }       // release 语义（比 volatile 写弱）
}
```
VarHandle 提供的**五种访问模式**（这是 JDK 9 之后最重要的新概念，本书完全没有）：

| 模式 | 语义强度 | 典型用途 |
| --- | --- | --- |
| `set/get` (plain) | 无保证，但保证 word tearing 安全 | 单线程或已外部同步 |
| `setOpaque/getOpaque` | 保证不被优化掉、可见性最终性（无顺序约束） | 取消-review 标志、统计计数器 |
| `setAcquire/getAcquire` | 读侧：后续读写不能重排到它之前 | 消费 locked/acquire 语义 |
| `setRelease/getRelease` | 写侧：之前的读写不能重排到它之后 | 发布 ready 标志 |
| `setVolatile/getVolatile` | 最强：acquire+release 全序 | 等价 volatile |

> 对照 C++：`std::memory_order_relaxed / consume / acquire / release / seq_cst` —— 二者一一对应。详见 [concepts/并发模型跨语言对比.md](concepts/并发模型跨语言对比.md)。

### 2.9 Unsafe 类 —— 本章"过期最快"的一节

本书用 `Unsafe.compareAndSwapInt`、`objectFieldOffset`、`arrayBaseOffset`、`park/unpark` 示范。
**这些 API 今天的状态**：

| API | 状态（2026） | 替代 |
| --- | --- | --- |
| `sun.misc.Unsafe.compareAndSwapXxx` | JDK 9+ 内部，**JEP 471（JDK 23）标记废弃 for removal，JEP 498（JDK 24）开始警告** | `VarHandle.compareAndSet` |
| `Unsafe.objectFieldOffset` | 同上 | `VarHandle`（`MethodHandles.lookup().findVarHandle`） |
| `Unsafe.getAndAddInt` | 同上 | `VarHandle.getAndAdd` |
| `Unsafe.park/unpark` | 仍是 LockSupport 的底层实现，但用户不应直接调用 | `LockSupport.park/unpark` |
| `Unsafe.allocateMemory`（堆外内存） | 被 FFM 取代 | **`Arena` / `MemorySegment`**（JEP 454, JDK 22 GA） |
| 直接访问内部 API | **JDK 17 JEP 403 强封装** + `--illegal-access=deny` | `sun.misc.Unsafe` 反射获取已被阻断（仍可用 `--add-exports` 逃逸，但不推荐） |

```java
// JDK 22+ 堆外内存的正确写法（取代 Unsafe.allocateMemory）
try (Arena arena = Arena.ofConfined()) {
    MemorySegment seg = arena.allocate(ValueLayout.JAVA_LONG, 1024);
    seg.setAtIndex(ValueLayout.JAVA_LONG, 0, 42L);
}   // 作用域结束自动释放 —— 这是 Unsafe 永远做不到的（无 Unsafe-free 泄漏风险）
```

### 2.10 指令重排序

三个层次都可能发生重排：
1. **编译器/JIT 重排**（在不改变单线程语义的前提下）；
2. **CPU 乱序执行**（Tomasulo 算法：指令级并行 + 重排序缓冲）；
3. **内存系统重排**（store buffer 导致的可见性顺序差异）。

区别在于禁止手段：**内存屏障（Memory Barrier）** —— Java 里由 volatile / synchronized / VarHandle / Unsafe.loadFence 插入，最终落到 LFENCE/SFENCE/MFENCE (x86) 或 DMB (ARM)。

**验证方法（本书未提供）**：用 jcstress 写出最小复现。
```java
@JCStressTest
@Outcome(id = {"1, 0"}, expect = Expect.ACCEPTABLE_INTERESTING, desc = "重排序发生了！")
@State
public class ReorderDemo {
    int x, y;                // 故意不加 volatile
    @Actor void a1() { x = 1; r1 = y; }
    @Actor void a2() { y = 1; r2 = x; }
}
```

### 2.11 伪共享（False Sharing）

```
cache line = 64 B，两个「逻辑上无关」的变量落在同一行
 → 线程 A 改 long a，导致线程 B 读到 long b 的行失效（同一 cache line 被失效）
 → 逻辑上无竞争，物理上互相拖累：改 a 会导致对方的缓存行反复失效
```
解决三件套：
1. **填充**（padding）：把字段补齐到 64/128 字节；
2. **`@Contended`**（JDK 8+ `sun.misc.Contended` / JDK 9+ `jdk.internal.vm.annotation.Contended`）—— **注意 JDK 8 下需要 `-XX:-RestrictContended` 才对应用类生效**；
3. 保持字段在各自对象内 —— `LongAdder` 的 `Cell` 就是这么做的（第 4 章详述）。

工业案例见 [concepts/伪共享FalseSharing.md](concepts/伪共享FalseSharing.md)（Disruptor、`ConcurrentHashMap` 的 `CounterCell`、JOL 验证）。

### 2.12 锁的概述

| 维度 | 分类 | Java 中的对应 |
| --- | --- | --- |
| 要不要独占 | 悲观锁 / 乐观锁 | `ReentrantLock` / CAS、`StampedLock.tryOptimisticRead` |
| 是否可重入 | 可重入锁 / 非可重入 | `synchronized`、`ReentrantLock` / 本书 6.2.3 手写的 `NonReentrantLock` |
| 公平性 | 公平 / 非公平 | `new ReentrantLock(true)` / 默认非公平（吞吐高，会饥饿） |
| 是否自旋 | 自旋 / 阻塞 | 轻量锁 CAS 自旋 / 重量级 monitor |
| 读写分离 | 独占 / 共享 | `ReentrantReadWriteLock`、`StampedLock` |

## 五、近年研究与工业界实践（2020-2026）

**同行评审 / 形式化**

- **Weak memory on ARM/RISC-V 的持续形式化**：2020 年后多篇（POPL/PLDI/CAV）在 *Promising* 语义框架上扩展 ARMv8 与 RISC-V 模型，并纠结混合访问模式（mixed-size/non-atomics）。对工程的意义：**不要在 x86 上调好就上线**，国产生态（ARM、LoongArch、RISC-V）已很常见。
- **RefinedRust / RustBelt 系**：Gäher 等 *RefinedRust: A Type System for High-Assurance Verification of Rust Programs*（2024）等工作把"数据竞争不可能发生"变成可机械证明的性质。对照 Java 只能靠 JMM + 程序员纪律，这是两条技术路线的分野。
- **运行时并发 bug 检测**: ThreadSanitizer 一脉的持续改进（deadlock/annotation checking），以及 JAVA 生态里 **jcstress** 作为官方反向约束：所有 JMM/atomics 的实现都要通过 jcstress 的 pattern-matching 测试。

**工业界资料（非同行评审）**

- JEP 文档是本章最新、最权威的"活规范"：**JEP 374**（偏向锁）、**JEP 403**（强封装）、**JEP 471/498**（Unsafe 走了⑨年退役路线）、**JEP 491**（去钉住）。链接：https://openjdk.org/jeps/0

- OpenJDK `jdk/internal/vm/annotation/Contended` 在 `LongAdder.Cell`、`ConcurrentHashMap.CounterCell`、`Thread.seed` 上的实际使用，JDK 源码是最好的对照表：https://github.com/openjdk/jdk

## 六、常见误区 / 本书需修正之处

1. ❌ **"偏向锁是默认优化，synchronized 几乎免费"** —— JDK 15 起偏向锁已废弃并默认禁用（JEP 374），JDK 8 时代的调优建议需整体复查。
2. ❌ **"volatile 保证原子性"** —— 不保证复合操作；`volatile i++` 仍丢计数。
3. ❌ **"DCL 单例不加 volatile 也行"** —— 不行，是典型的半初始化对象事故。
4. ❌ **书里直接用 `sun.misc.Unsafe`** —— JDK 17 起强封装 + JDK 23/24 废弃警告，生产代码请改用 **VarHandle**；堆外内存改用 **MemorySegment + Arena**。
5. ❌ **"伪共享只影响性能，不影响正确性"** —— 对；但反过来不正确：**2.11 的 padding 不能解决可见性问题**，别把 `@Contended` 当同步用。
6. ⚠️ **本书默认 x86** —— 请在 ARM/Apple Silicon 上重跑本书的可见性示例；必要时用 jcstress 覆盖性测试来兜底。
7. ⚠️ **本书缺失的点：word tearing** —— JMS 保证 32 位以内的读写原子（除 `long`/`double` 在 JDK 5 前允许 word tearing，如今 `volatile long` 一定原子）；建议在笔记里补上 "JLS §17.7 Non-atomic Treatment of double and long"。
