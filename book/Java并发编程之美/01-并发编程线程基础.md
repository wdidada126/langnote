## 二、核心精讲

### 1.1 什么是线程——三层成本模型

```
进程 (隔离的地址空间, 独享页表/文件描述符)
 └─ 线程 (共享堆与方法区, 独享: 程序计数器 / 虚拟机栈 / 本地方法栈)
     └─ 虚拟线程 (JDK21+) : 轻量 —— 栈在 Java 堆上的 continuation stack chunks
```

本书默认讨论的是**平台线程（platform thread）**：1:1 映射到 OS 线程（HotSpot 里是 `JavaThread` ↔ OS thread）。
JDK 21 起增加了第三层，**这是本书最重要的时代差**：

```java
// JDK 21+：一个虚拟线程 ≈ 几百字节初始栈 + 一个 continuation
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000_000)
             .forEach(i -> executor.submit(() -> {
                 Thread.sleep(Duration.ofSeconds(1));   // 不再占用 OS 线程
                 return i;
             }));
}   // close() 隐式 join：结构化并发的雏形
```
> 对比 [concepts/虚拟线程Loom.md](concepts/虚拟线程Loom.md)：JDK 21 的 JVM **默认最多只有 CPU 核数个 carrier 线程**（可用 `jdk.virtualThreadScheduler.parallelism` 调整），1000 万个阻塞任务也不会换来 1000 万条 OS 线程。

**内存账**（64 位 HotSpot，缺省 `-Xss`）：

| 对象 | 默认占用 | 备注 |
| --- | --- | --- |
| 平台线程栈 | 512 KB ~ 1 MB（`-Xss1m`） | **虚拟内存预留**，实际提交按需 |
| 虚拟线程栈 | 初始约 1 KB 的 heap chunk，按需增长 | 位于 **Java 堆**（continuation stack chunks），挂起时被 GC 管理，可增长也可回收 |

### 1.2 线程创建与运行

```java
// ① 继承 Thread（不推荐：把"任务"和"执行机制"耦合）
class MyThread extends Thread { public void run() { ... } }

// ② Runnable（推荐）：无返回值、不能抛受检异常
new Thread(() -> doWork(), "biz-worker-1").start();

// ③ FutureTask + Callable：可拿到返回值与异常
FutureTask<Integer> task = new FutureTask<>(() -> 42);
new Thread(task).start();
Integer r = task.get();   // 阻塞直到完成

// ④ JDK 21+ Thread.Builder（本书没有）
Thread v = Thread.ofVirtual().name("vt-", 1).start(() -> ...);   // 虚拟
Thread p = Thread.ofPlatform().daemon().name("pt-", 1).start(...);// 平台 + daemon
```

> **本书误区提示**：本书反复强调"一定要给线程取名字"（第 11.7 节会再讲）。
> JDK 21 的 `Thread.ofVirtual().name("biz-", 0)` 把命名提升为一等 API；虚拟线程还能`setName` 但**常量序号**不能被覆盖。

### 1.3 wait / notify —— Mesa 语义（本书最容易被忽略的一节）

```java
synchronized (lock) {
    while (!condition) {     // ★ 必须用 while，不能用 if
        lock.wait();
    }
    doWork();
}
```

为什么必须是 `while`？因为 **Java 的 monitor 采用 Mesa 语义**（见 Lampson & Redell, 1980）：
被 `notify` 唤醒的线程 **不会立刻**重新持锁运行，条件可能在它被调度前再次变为假（另一个线程抢先消费了资源）；此外还有**虚假唤醒（spurious wakeup）**。Hoare 语义（唤醒即立刻交接）才允许 `if`，而 Java 不是。

**wait/notify 的语法陷阱**（本书原话整理）：
- `wait()/notify()` 必须在**同步块内**调用，否则 `IllegalMonitorStateException`——因为它们依赖对象头的 monitor；
- `wait()` 会**释放锁**，`sleep()` **不会**释放锁 —— 这是二者的本质区别；
- `notify()` 只唤醒**一个**等待线程，随机/实现相关；`notifyAll()` 唤醒全部，通常更安全但唤醒风暴开销大；
- 推荐优先使用 JUC 的 `Condition`（见 [concepts/AQS抽象同步队列.md](concepts/AQS抽象同步队列.md)）：`await/signal/signalAll` 支持多个等待队列，语义与 Condition 对象绑定而非 monitor。

### 1.4~1.7 join / sleep / yield / interrupt

| API | 释放锁? | 主要坑 | 现代替代 |
| --- | --- | --- | --- |
| `Thread.sleep(ms)` | ❌ | 持锁时睡过去 → 锁被白占 | 虚拟线程下影响大幅降低（但仍不建议在持锁时睡眠） |
| `Thread.yield()` | ❌ | 只是**提示**，传给 OS 后可能被忽略；不要用于保证正确性 | 自旋等待用 `Thread.onSpinWait()`（JDK 9+，向 CPU 发出可让流水线降速的提示） |
| `join()` | ❌ | 无超时会永久阻塞 | JDK 21+ `StructuredTaskScope.join()` / 带超时的 join |
| `interrupt()` | — | **协作式**：只置中断标志，需由代码自己检查 `isInterrupted()` 或处理 `InterruptedException` | 同左，虚拟线程亦然 |

中断的正确写法（三个层次）：

```java
// ① 阻塞方法中被中断 → InterruptedException，异常会清掉中断标志
try { Thread.sleep(1000); }
catch (InterruptedException e) { Thread.currentThread().interrupt(); } // ★ 恢复标志

// ② 长循环中主动检查
while (!Thread.currentThread().isInterrupted()) { doChunk(); }

// ③ 阻塞队列等用 take() 天然响应中断；不可用标识符 + sleep 轮询
```

> **跨语言对照**：Java 的中断是"协作式标志位"；Go 没有中断机制，用 `context.Context` 取消传播；Rust `std::thread` 也没有，靠 channel + `AtomicBool`/tokio CancellationToken；Erlang 用 `exit/2` 信号（抢占式，但也需要 trap_exit 配合）。详见 [concepts/并发模型跨语言对比.md](concepts/并发模型跨语言对比.md)。

### 1.8 上下文切换的成本

一次**平台线程**上下文切换大致要做：保存/恢复寄存器与栈指针 → 切换内核态/用户态 → TLB 与 CPU cache 局部性丢失（间接成本，往往是最大头）→ 内核调度器入队。

| 场景 | 量级 |
| --- | --- |
| syscall / 线程切换 | ~1–2 µs（同一核） |
| 因 cache/TLB miss 导致的间接损失 | 可达数十 µs |
| 自旋 + CAS 成功（无竞争） | ~10–20 ns |
| **虚拟线程挂起/恢复（JDK 21）** | ~百 ns 级，**不进内核** |

这也是为什么过去十年主流做法是"**少线程 + 事件循环 + 异步回调**"（Netty/Vert.x/Reactor），而 **JDK 21 虚拟线程让"一请求一线程"重新可行**：成本从 OS 调度层降到了 JVM 的 continuation 切换。

诊断：JFR 事件 `jdk.ThreadStart` / `jdk.ThreadEnd` / `jdk.ThreadPark`，或直接看线程数：
```bash
jcmd <pid> Thread.dump_to_file -format=json threads.json
```

### 1.9 死锁：四条件与破除

Coffman 四条件（缺一不可）：**互斥占有 / 持有并等待 / 不可剥夺 / 循环等待**。

```java
// 典型交叉死锁（本书例子精神）
// T1: lock(A) → sleep → lock(B)
// T2: lock(B) → sleep → lock(A)
```
破除手段：
1. **固定加锁顺序**（破坏循环等待）——最实用；可按 `System.identityHashCode` 排序作为兜底。
2. `tryLock(timeout)` + 回退重试（破坏不可剥夺/持有等待）。
3. 减少锁粒度、用无锁结构（见第 4、7 章）。
4. 用工具定位：`jstack` 直接输出 `Found one Java-level deadlock`；生产推荐 JFR + `jdk.JavaMonitorEnter`（可看到阻塞时长与持有者）。

> **本书遗漏**：数据库死锁/分布式死锁（等待图 + 超时回滚），以及 `ReentrantReadWriteLock` 的**锁降级/不可升级**（见第 6.4 节）。

### 1.10 守护线程 vs 用户线程

```java
Thread t = new Thread(task);
t.setDaemon(true);     // 必须在 start() 之前
t.start();
```
JVM 存活条件是"**至少还有一个非守护线程**"；守护线程（GC 线程、JIT 编译线程、定时清理线程）在最后一个用户线程结束时刻被一并终止，**不能用来做收尾**（`finally` 不保证执行）。

🆕 **JDK 21 变化（本书未覆盖）**：
- **虚拟线程永远是 daemon 线程**，且其 daemon 状态不可修改：
  ```java
  Thread vt = Thread.ofVirtual().unstarted(runnable);
  vt.setDaemon(true);    // ✗ UnsupportedOperationException
  ```
  因此纯虚拟线程程序一旦主线程退出，所有虚拟线程都会被判定"可丢弃"——这正是**必须**用 `Executors.newVirtualThreadPerTaskExecutor()` + try-with-resources / `StructuredTaskScope` 的原因。

## 六、常见误区 / 本书需修正之处

1. ❌ **"创建线程开销很大所以必须池化"** → JDK 21+ 对**阻塞型工作**应直接用 `newVirtualThreadPerTaskExecutor()`，不要人为限流——限流应放在真正的稀缺资源（DB 连接池、Semaphore），而不是线程数。
2. ❌ **"线程数上限 ≈ 几千"** → 那是平台线程时代的经验；虚拟线程可达百万级，但 **`Executors.newCachedThreadPool()` 式的无界创建仍然危险**（无限虚拟线程 + 内存）。
3. ❌ **`setDaemon(true)` 在虚拟线程上有效** → JDK 21 起抛 `UnsupportedOperationException`，虚拟线程恒为守护线程。
4. ❌ **`if (condition) wait()`** → 必须 `while`，Mesa 语义下会存在虚假唤醒与条件被抢先消费。
5. ❌ **`sleep()` 会释放锁** → 不会，只有 `wait()` 释放 monitor；反过来 `Thread.sleep(0)` 曾被用作 yield hack，JDK 9+ 请用 `Thread.onSpinWait()`。
6. ⚠️ **本书的"线程 vs 进程"图未区分虚拟线程** —— 重绘时应加第三层；参考 [concepts/虚拟线程Loom.md](concepts/虚拟线程Loom.md)。
7. ⚠️ **第 1 章没提 `Thread.stop()/suspend()/resume()` 已废弃的原因**（不安全：stop 会破坏对象一致性，suspend 会带锁挂起导致死锁）——面试必问，建议补在自己笔记里。
