## 二、10.1 `CountDownLatch`：共享模式的极简用法

```java
// 用法
CountDownLatch latch = new CountDownLatch(3);
for (int i = 0; i < 3; i++)
    new Thread(() -> { doWork(); latch.countDown(); }).start();
latch.await();          // 主线程阻塞，直到计数归零
```

内部是一个极简的 AQS 共享模式实现：

```java
private static final class Sync extends AbstractQueuedSynchronizer {
    Sync(int count) { setState(count); }              // state = 剩余计数
    int getCount() { return getState(); }

    protected int tryAcquireShared(int acquires) {
        return (getState() == 0) ? 1 : -1;            // 归零才放行
    }
    protected boolean tryReleaseShared(int releases) {
        for (;;) {
            int c = getState();
            if (c == 0) return false;                 // 已经归零，不再减
            int nextc = c - 1;
            if (compareAndSetState(c, nextc))
                return nextc == 0;                    // 减到 0 才唤醒等待者
        }
    }
}
```

**`tryAcquireShared` 返回值的含义**（第 6 章 AQS 的约定）：

| 返回值 | 含义 |
| --- | --- |
| `< 0` | 获取失败，进入队列等待 |
| `= 0` | 获取成功，但**后续**共享获取不应继续传播 |
| `> 0` | 获取成功，且后续共享获取**应继续传播**（唤醒下一个） |

`CountDownLatch` 归零后返回 `1`，配合 AQS 的**共享传播（propagation）** 机制，
一次性把所有等待线程全部唤醒——这正是 `await()` 能同时释放 N 个线程的原因。

**关键特性：一次性，不可重置**。这是它与 `CyclicBarrier` 最本质的区别。

## 三、10.2 `CyclicBarrier`：可复用 + barrierAction

```java
CyclicBarrier barrier = new CyclicBarrier(3, () -> System.out.println("本轮全部到位"));

for (int i = 0; i < 3; i++)
    new Thread(() -> {
        doWork();
        barrier.await();     // 阻塞直到凑齐 3 个
        nextPhase();
    }).start();
```

**内部实现不是 AQS，而是 `ReentrantLock` + `Condition`**（这是它与另两个同步器的关键区别）：

```java
public class CyclicBarrier {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition trip = lock.newCondition();
    private final int parties;
    private final Runnable barrierCommand;   // 可选：最后一个到达的线程执行它
    private Generation generation = new Generation();   // 「代」，用于复用与 broken 标记

    private int count;                        // 还剩几个没到

    public int await() throws InterruptedException, BrokenBarrierException {
        final ReentrantLock lock = this.lock;
        lock.lock();
        try {
            final Generation g = generation;
            if (g.broken) throw new BrokenBarrierException();
            if (Thread.interrupted()) { breakBarrier(); throw new InterruptedException(); }

            int index = --count;
            if (index == 0) {                          // 我是最后一个
                boolean ranAction = false;
                try {
                    final Runnable command = barrierCommand;
                    if (command != null) command.run(); // 先跑 barrierAction
                    ranAction = true;
                    nextGeneration();                   // 换代 + signalAll
                    return 0;
                } finally {
                    if (!ranAction) breakBarrier();     // barrierAction 抛异常 → 打破栅栏
                }
            }
            // 不是最后一个 → 在 condition 上等
            for (;;) {
                try { trip.await(); }
                catch (InterruptedException ie) {
                    if (g == generation && !g.broken) { breakBarrier(); throw ie; }
                    else Thread.currentThread().interrupt();
                }
                if (g.broken) throw new BrokenBarrierException();
                if (g != generation) return index;      // 换代了，放行
            }
        } finally { lock.unlock(); }
    }
}
```

**`Generation`（代）是复用的关键**：每次 `nextGeneration()` 新建一个 `Generation` 对象，
等待中的线程通过比较 `g != generation` 判断「新一轮开始了」，从而避免被上一轮遗留的 `signalAll` 误唤醒。

**`BrokenBarrierException`**：任何一个参与线程被中断或超时，都会 `breakBarrier()` 把栅栏标为 broken，
**所有其他等待线程都会收到 `BrokenBarrierException`**。这是「要么全员到齐，要么全员失败」的语义保障——
避免部分线程永远等待。

| | `CountDownLatch` | `CyclicBarrier` |
| --- | --- | --- |
| 底层 | AQS 共享模式 | `ReentrantLock` + `Condition` |
| 可复用 | ❌ 一次性 | ✅ 可循环（换代） |
| 计数方向 | 减到 0 放行 | 减到 0 放行后重置 |
| 谁阻塞 | **等待方**（`await()`）阻塞，**通知方**（`countDown()`）不阻塞 | **所有参与者都阻塞**（大家一起等） |
| 额外动作 | 无 | 支持 `barrierCommand` |
| 异常传播 | 无 | 有 `BrokenBarrierException` |

> **一句话区分**：`CountDownLatch` 是「**一等人**」（主线程等其他线程干完）；
> `CyclicBarrier` 是「**互相等**」（所有线程互相等到齐再一起往下走）。

## 四、10.3 `Semaphore`：Dijkstra 的 PV 操作

```java
Semaphore sem = new Semaphore(5);      // 5 个许可
sem.acquire();                          // P 操作，拿不到就阻塞
try { useResource(); }
finally { sem.release(); }              // V 操作，必须在 finally 里！
```

AQS 实现（同样极简）：

```java
abstract static class Sync extends AbstractQueuedSynchronizer {
    Sync(int permits) { setState(permits); }        // state = 可用许可数

    final int nonfairTryAcquireShared(int acquires) {
        for (;;) {
            int available = getState();
            int remaining = available - acquires;
            if (remaining < 0 || compareAndSetState(available, remaining))
                return remaining;                    // <0 表示不够，入队等待
        }
    }
    protected final boolean tryReleaseShared(int releases) {
        for (;;) {
            int current = getState();
            int next = current + releases;
            if (next < current) throw new Error("Maximum permit count exceeded");
            if (compareAndSetState(current, next)) return true;
        }
    }
}
```

**公平/非公平两版**：`FairSync.tryAcquireShared` 会先检查 `hasQueuedPredecessors()`（队列里有没有人排在我前面），
有就直接返回 -1 去排队——这一点与 `ReentrantLock` 的公平策略完全一致（第 6 章）。

**`Semaphore` 的真正用途**：

| 用途 | 说明 |
| --- | --- |
| **限流 / 资源池**（最主要） | 数据库连接池、HTTP 连接池、并发调用数上限 |
| **互斥**（permit=1） | 退化为「不可重入的锁」——**注意 `Semaphore(1)` 不是可重入锁**，同一线程再 acquire 会把自己锁死 |
| **信号量作为信号**（permit=0） | A 线程 `release()` 通知 B 线程 `acquire()`，实现 lightweight 的 handoff |

> ⚠️ `release()` **必须写在 `finally` 里**。否则一次异常就永久丢失许可，最终所有线程卡死。

## 五、10.4 本书遗漏的两个成员

### `Phaser`（JDK 7）：`CyclicBarrier` + `CountDownLatch` 的超集

```java
Phaser phaser = new Phaser(3);          // 3 个参与方
// 每个参与方：
phaser.arriveAndAwaitAdvance();          // 到达并等待其他方（等价于 barrier.await()）
phaser.arriveAndDeregister();            // 到达并注销自己（参与方数动态减少）
phaser.register();                       // 动态增加参与方
phaser.forceTermination();               // 强制终止
int phase = phaser.getPhase();           // 当前阶段号
```

`Phaser` 解决了 `CyclicBarrier` 的三个硬伤：

| 硬伤 | `CyclicBarrier` | `Phaser` |
| --- | --- | --- |
| 参与方数量固定 | ✅ 固定 | ✅ **可动态 register / deregister** |
| 无法中断单个阶段 | ❌ | ✅ `forceTermination()` |
| 分层（树形）结构 | ❌ | ✅ `new Phaser(parent)`，适合大规模参与方 |

`Phaser` 内部**不用锁**，而是用一个 `long` 同时编码 `phase`（高 32 位）、`parties`（中 16 位）、`unarrived`（低 16 位），
靠 CAS 更新——是 JDK 里位打包技巧的巅峰之作。

### `Exchanger`（JDK 5）：两线程交换数据

```java
Exchanger<String> ex = new Exchanger<>();
// 线程 A
String got = ex.exchange("data-from-A");    // 阻塞，直到 B 也来 exchange
// 线程 B
String got2 = ex.exchange("data-from-B");
```

典型场景：生产者/消费者交替填充与清空缓冲区（遗传算法、pipeline 双缓冲）。
实现用的是「槽位（slot）+ CAS + 自旋 + 退化为 `Node` 链表」的无锁技巧（JDK 8 后重写过）。

### 结构化并发：本章同步器的现代形态

```java
// 传统写法：CountDownLatch + ExecutorService + 手动异常传播
// 结构化并发（JDK 21+ 预览）：
try (var scope = StructuredTaskScope.open()) {
    Subtask<String> user  = scope.fork(() -> fetchUser());
    Subtask<String> order = scope.fork(() -> fetchOrder());
    scope.join();                                    // 等待全部完成
    return new Result(user.get(), order.get());      // 任一失败则 join 抛异常
}   // 作用域退出 → 自动取消所有未完成的子任务（不会有泄漏的线程）
```

> 结构化并发解决的正是本章同步器的**根本缺陷**：
> `CountDownLatch` / `CyclicBarrier` 的等待是「无结构」的——如果某个子任务失败或超时，
> 其他线程不会被自动取消，可能泄漏为孤儿线程。
> 详见 [concepts/结构化并发与ScopedValue.md](concepts/结构化并发与ScopedValue.md)。

## 八、近年研究与工业界前沿（2020-2026）

**同行评审论文**

- **可扩展同步原语的持续研究**：Mellor-Crummey & Scott (1991) 提出的 barrier 算法家族（sense-reversing centralized barrier、combining tree barrier、tournament barrier）至今仍是可扩展屏障的基础；近年工作主要围绕 NUMA 感知与异构（CPU+GPU）同步展开，多见于 PPoPP / SC。
- **形式化验证同步器**：2020-2025 年有多项工作用模型检测/定理证明验证 JUC 同步器的正确性（如用 Iris/Coq 验证 AQS 类结构），属于「把 1990 年代的手工证明自动化」的方向。

**工业界资料（非同行评审）**

- **Guava `RateLimiter`**：基于令牌桶（内部用 `SleepingStopwatch` + 锁），是 `Semaphore` 在限流场景的工业级封装。
  https://github.com/google/guava
- **Resilience4j `SemaphoreBulkhead`**：用 `Semaphore` 实现舱壁隔离，限制对某个下游的并发调用数。
  https://github.com/resilience4j/resilience4j
- **Netty `DefaultEventExecutorGroup` / `Promise`**：Netty 用 promise/future 链替代了大量 `CountDownLatch` 场景。
- **Phaser 的真实用户**：JDK 内部 `ForkJoinPool` 的某些同步、以及并行框架（如 Aparapi、Habanero Java）中。日常业务代码用得少，但在**多阶段并行计算**里无可替代。

## 九、常见误区 / 本书需修正之处

1. **⚠️ `CyclicBarrier` 不是基于 AQS 的**——它用 `ReentrantLock` + `Condition`。本书把它与另两个放在一起讲，容易让人误以为都是 AQS。这是本章最需要澄清的一点。
2. **⚠️ `Semaphore(1)` 不是可重入锁**：同一线程重复 `acquire()` 会死锁。要互斥请用 `ReentrantLock`。
3. **⚠️ `release()` 必须放 `finally`**，否则异常会永久丢失许可。
4. **⚠️ `CountDownLatch` 不可重置**：需要复用请用 `CyclicBarrier` 或 `Phaser`（或者直接新建 latch）。
5. **⚠️ 本书未覆盖 `Phaser` 与 `Exchanger`**——`Phaser` 尤其值得补（动态参与方 + 分层），见第五节。
6. **`CompletableFuture` 在很多场景已取代 `CountDownLatch`**：
   `CompletableFuture.allOf(...).join()` 比 `CountDownLatch` 更好用（有返回值、有异常传播、可编排）。
   见 [concepts/CompletableFuture与异步编排.md](concepts/CompletableFuture与异步编排.md)。
7. **虚拟线程下 `Semaphore` 依然必要**：它是限并发数的，与线程成本无关；但 `CountDownLatch`/`CyclicBarrier` 这类「等一批任务」的场景，应优先考虑**结构化并发**（JDK 21+）。
8. **`barrierAction` 抛异常会打破栅栏**：所有等待线程收到 `BrokenBarrierException`（见第三节源码）。
