## 二、6.1 LockSupport：JUC 的阻塞原语

```java
LockSupport.park();               // 阻塞当前线程
LockSupport.unpark(thread);       // 唤醒指定线程
LockSupport.parkNanos(1_000_000L);
LockSupport.park(Object blocker); // 带 blocker，jstack / JFR 能看到阻塞对象
```

三点必须记住：

1. **permit（许可）是一次性的 0/1 信号量**：`unpark` 把许可置 1，`park` 消耗它后立即返回；**先 unpark 再 park 不会丢** —— 这与 `wait/notify` 的顺序敏感性完全不同（`notify` 先于 `wait` 会丢失）。
2. **`park()` 可能因虚假唤醒返回**，所以所有 JUC 阻塞代码都写成 `while (!canProceed) park();` 的形式（第 1.3 节 Mesa 语义的翻版）。
3. **`park` 不要求持有锁**，这是它与 `Object.wait()` 最大的区别，也是 AQS 能自由组织等待队列的前提。

```java
Thread t = new Thread(() -> {
    System.out.println("park");
    LockSupport.park();                 // 不需要 synchronized
    System.out.println("resumed");
});
t.start();
Thread.sleep(1000);
LockSupport.unpark(t);                  // 精确唤醒某个线程（不像 notify 是随机的）
```

> **现代细节**：JDK 里 `LockSupport.park(obj)` 会把 blocker 写进 ` jdk.internal.misc.Blocker`，`jstack`/JFR 因此能显示 `sun.misc parking to wait for <0x...>`。虚拟线程同样支持 park，但**挂起的是 continuation，不占用 OS 线程**（这也是 JDK 21 后所有 JUC 阻塞 API 自动变便宜的原因）。

## 三、6.2 AQS：整个 JUC 的地基

详见专篇 [concepts/AQS抽象同步队列.md](concepts/AQS抽象同步队列.md)。此处给出本章必须的骨架。

### 三大件

```
┌──────────────────────── AbstractQueuedSynchronizer ────────────────────────┐
│ ① volatile int state                    资源的抽象状态（锁的重入次数/信号量许可数）│
│ ② volatile Node head / tail             CLH 变体的 FIFO 同步队列（双向链表）      │
│ ③ Node.waitStatus                       CANCELLED/SIGNAL/CONDITION/PROPAGATE   │
└────────────────────────────────────────────────────────────────────────────┘
                    子类只需实现 tryAcquire / tryRelease / tryAcquireShared ...
```

等待节点姿态：

| waitStatus | 值 | 含义 |
| --- | --- | --- |
| `CANCELLED` | 1 | 等待已取消（超时/中断），出队清理 |
| `SIGNAL` | -1 | 后继节点需要被唤醒 |
| `CONDITION` | -2 | 节点在 Condition 队列里，不在同步队列 |
| `PROPAGATE` | -3 | 共享模式下唤醒需要向后传播 |
| 0 | 0 | 初始状态 |

### acquire 流程（独占模式）

```java
public final void acquire(int arg) {
    if (!tryAcquire(arg) &&                                   // ① 抢一把（子类实现）
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg))         // ② 失败则入队 + 排队
        selfInterrupt();                                       // ③ 排队中被中断 → 补一次中断标志
}
```
`acquireQueued` 内部：**只有前驱是 head 才再试一次 tryAcquire**（否则 `park`）→ 被唤醒后再检查 → 成功则把自己设为 head。这就是 CLH 队列的自旋 + 阻塞混合策略：**前驱是 head 时有资格自旋抢锁**（避免不必要的 park/unpark 开销），否则乖乖 park。

**为什么这样设计**（本书没有讲透）：AQS 的队列是 **CLH 锁（Craig 1973 / CLH 见 Magnusson 等 1994）的变体**，原本 CLH 是"每个节点自旋监听前驱的状态"；AQS 改成"前驱显式地 unpark 后继"，从而**把自旋变成阻塞**，省 CPU，同时保留 FIFO 公平性。

### 6.2.2 条件变量的支持：Condition

```java
Condition cond = lock.newCondition();
// await()  → 把自己加入单向的 Condition 队列 + 完全释放 state（含重入次数）+ park
// signal() → 把 Condition 队列的首节点 transfer 到同步队列尾部，等待重新抢锁
```

> **与 `Object.wait/notify` 的关键区别**：一个 Lock 可以有**多个** Condition 队列（生产者/消费者的 `notFull` / `notEmpty` 正是这一能力，见第 7 章 LinkedBlockingQueue）。
> 另外 `awaitUninterruptibly()`、`awaitNanos()`、`awaitUntil()` 提供了 wait 没有的能力。

**signal 的正确用法**：必须在持锁状态下调用，且通常用 `while (条件不满足) await();`。

### 6.2.3 基于 AQS 实现自定义同步器（本书手写的 NonReentrantLock）

```java
final class NonReentrantLock implements Lock {
    private final Sync sync = new Sync();
    static class Sync extends AbstractQueuedSynchronizer {
        protected boolean tryAcquire(int acquires) {
            assert acquires == 1;
            if (compareAndSetState(0, 1)) {              // 只认 0→1，不支持重入
                setExclusiveOwnerThread(Thread.currentThread());
                return true;
            }
            return false;                                 // 自己已持锁再获取 → 失败（会自我阻塞）
        }
        protected boolean tryRelease(int releases) {
            if (getState() == 0) throw new IllegalMonitorStateException();
            setExclusiveOwnerThread(null);
            setState(0);
            return true;
        }
        protected boolean isHeldExclusively() { return getState() == 1; }
        Condition newCondition() { return new ConditionObject(); }
    }
    public void lock() { sync.acquire(1); }
    public void lockInterruptibly() throws InterruptedException { sync.acquireInterruptibly(1); }
    public boolean tryLock() { return sync.tryAcquire(1); }
    public boolean tryLock(long t, TimeUnit u) throws InterruptedException { return sync.tryAcquireNanos(1, u.toNanos(t)); }
    public void unlock() { sync.release(1); }
    public Condition newCondition() { return sync.newCondition(); }
}
```

> ⚠️ **本书示例中 `NonReentrantLock` 的用途是演示"不可重入会怎样"**：同一个线程二次 `lock()` 会把自己阻塞，形成自我死锁。这正说明为什么 `ReentrantLock` 要用 `state` 记录**重入计数 + owner 线程**。

其他基于 AQS 的 JDK 成员：`ReentrantLock`、`ReentrantReadWriteLock`、`StampedLock`（内部 `WNode` 是另一套）、`Semaphore`、`CountDownLatch`、`FutureTask`、`ThreadPoolExecutor.Worker`、`CyclicBarrier`（用 ReentrantLock + Condition，不用 AQS sync queue）等。

## 四、6.3 ReentrantLock

```java
// 公平与非公平的核心差别就一行代码
final boolean nonfairTryAcquire(int acquires) {
    if (getState() == 0 && compareAndSetState(0, acquires)) {   // 不排队，直接插队 CAS
        setExclusiveOwnerThread(Thread.currentThread()); return true;
    }
    return false;
}
protected final boolean tryAcquire(int acquires) {   // 公平版 FairSync
    if (getState() == 0 && !hasQueuedPredecessors() && compareAndSetState(0, acquires)) {
        setExclusiveOwnerThread(Thread.currentThread()); return true;
    }
    ...
}
```
- **非公平（默认）**：新来的线程可直接插队 —— 吞吐高（少一次 park/unpark），但可能造成**线程饥饿**。
- **公平**：`hasQueuedPredecessors()` 检查有没有比你更早排队的人。
- **可重入**：`state` 累加，同一线程每获取一次 +1，释放时 -1，归零才真正释放。

```java
ReentrantLock lock = new ReentrantLock();        // 默认非公平
// ReentrantLock lock = new ReentrantLock(true); // 公平
lock.lock();
try { critical(); }
finally { lock.unlock(); }                        // ★ 必须 finally
```

**synchronized vs ReentrantLock（2026 年视角）**

| 维度 | synchronized | ReentrantLock |
| --- | --- | --- |
| 释放 | JVM 自动（异常也释放） | 必须 `finally` 手动释放 |
| 可中断等待 | ❌ | ✅ `lockInterruptibly()` |
| 超时 | ❌ | ✅ `tryLock(timeout)` |
| 公平性 | ❌ | ✅ 可选 |
| 多个条件队列 | ❌（一个 monitor） | ✅ 多 Condition |
| **JDK 21-23 虚拟线程** | ⚠️ 阻塞会**钉住** carrier | ✅ 不钉住（用 park/unpark） |
| **JDK 24+（JEP 491）** | ✅ 不再钉住 | ✅ |
| 性能 | JDK 6 之后两者接近 | 接近；高争用下 JUC 略好 |

> 🔴 **这是本书最重要的时代修正之一**：原书写"二者性能接近"，但在**JDK 21-23 的虚拟线程环境下，在 synchronized 里阻塞会钉住 carrier 线程**，导致伸缩性崩塌 —— 这段时间里的官方建议是高并发虚拟线程场景改用 `ReentrantLock`。**JDK 24（JEP 491）已修复**，JDK 24+ 两者在虚拟线程下都安全。

## 五、6.4 ReentrantReadWriteLock

一个 `int state` 拆两半：**高 16 位 = 读锁计数，低 16 位 = 写锁的重入次数**。

```
state (32 bit): |---- read count (16) ----|---- write hold count (16) ----|
```
因此有上限：读/写各自最多 **65535** 次（够用，但是面试常问的上限）。

要点：
- **写锁可降级为读锁**（持写锁 → 获取读锁 → 释放写锁），这是合法的；共用例：先改后读防止中间被别人改。
- **读锁不能升级为写锁**：两个线程同时持有读锁都想升级会死锁。
- **非公平实现**下，为避免写饥饿，有 `readerShouldBlock()` 规则：`ApparentlyFirstQueuedIsExclusive` —— 若队首是写请求，新来的读请求要排队。
- 每线程各自的读计数放在 `ThreadLocalHoldCounter`（**这就是第 1.11 节 ThreadLocal 在 JDK 里的经典应用**，也是第 11.10 节内存泄漏问题的真实来源之一）。

```java
ReentrantReadWriteLock rw = new ReentrantReadWriteLock();
Lock r = rw.readLock(), w = rw.writeLock();
r.lock();   try { query(); } finally { r.unlock(); }   // 读并发
w.lock();   try { update(); } finally { w.unlock(); }  // 写独占
```

## 六、6.5 StampedLock（JDK 8 新增，本书最后一节）

三种模式：

| 模式 | API | 特点 |
| --- | --- | --- |
| 写锁 | `writeLock()` / `unlockWrite(long)` | 独占，返回 stamp |
| 悲观读锁 | `readLock()` | 与写互斥 |
| **乐观读** | `tryOptimisticRead()` + `validate(stamp)` | **完全不阻塞写**，读完校验 stamp，失败则退化为 `readLock()` |

```java
class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();
    double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();          // ① 乐观读，几乎零成本
        double cx = x, cy = y;
        if (!sl.validate(stamp)) {                    // ② 期间被改过？
            stamp = sl.readLock();                    // ③ 退化为悲观读锁
            try { cx = x; cy = y; } finally { sl.unlockRead(stamp); }
        }
        return Math.sqrt(cx * cx + cy * cy);
    }
}
```

⚠️ **四条红线（本书强调了但值得再敲一遍）**：
1. **`StampedLock` 不可重入** —— 同一线程二次获取会自我死锁；且 `readLock()` + `readLock()` 也不行。
2. **不支持 Condition** —— 不能 `newCondition()`。
3. **它不是 AQS 实现** —— 内部是自写的 `WNode` CLH 变体（cowait 栈用于读节点共享），这也是它能做乐观读的原因。
4. `tryOptimisticRead()` **读到的值可能是撕裂的**，必须 `validate()`。

**补充说明**：从 2026 年回看，`StampedLock` 是"**乐观并发控制**"（见 Kung & Robinson 1981 *On Optimistic Methods for Concurrency Control*）在 JDK 里的落地，与数据库的乐观锁/MVCC 同出一源。
> 实际工程中，如果乐观读的失败率高，性能反而不如 `ReentrantReadWriteLock`，务必用 JMH 实测。

## 十、常见误区 / 本书需修正之处

1. “ReentrantLock 比 synchronized 快” —— JDK 6 之后两者接近。正确依据是功能需求（可中断、超时、公平、多 Condition）与虚拟线程行为，而不是跑分神话。
2. “AQS 的等待队列是公平的” —— 默认是**非公平**（新线程可插队），只有构造时传 `true` 才公平。
3. “StampedLock 是更高级的 ReadWriteLock，可以直接替换” —— 它不可重入、不支持 Condition，乐观读必须 validate 并准备退化路径。
4. “signal 相当于 notifyAll” —— signal 只唤醒 Condition 队列中的一个节点，并把它移回同步队列重新抢锁。
5. 🔴 **JDK 24 之前，在虚拟线程里要谨慎使用 synchronized** —— JDK 21-23 会钉住 carrier，导致并发伸缩性骤降；JDK 24+（JEP 491）已修复。这是本书最重要的时代修正。
6. ⚠️ `ReentrantReadWriteLock` 的高 16 位是读计数，上限 65535；写锁的重入次数也受同宽度限制。
7. ⚠️ “AQS 只用于锁”是误解 —— 第 8 章的 `ThreadPoolExecutor.Worker`、第 10 章的 `Semaphore` / `CountDownLatch` 同样基于 AQS（且 Semaphore 用的是共享模式）。
8. ⚠️ 不要把 `Condition.await()` 与 `Thread.sleep()` 混用 —— await 会释放锁，重新抢锁之间存在窗口，条件判断必须用 `while` 复查。

## 十一、跨语言对照

| 语言 | 等价机制 | 说明 |
| --- | --- | --- |
| Java（本书） | `synchronized` + JUC（`ReentrantLock` / AQS / `StampedLock`） | AQS 是各语言中最著名、工业化程度最高的可复用同步器框架之一 |
| C++ | `std::mutex`（底层多为 futex）、`std::shared_mutex`（读写锁，C++17） | C++20 起 `std::atomic<T>::wait/notify` 提供了接近 futex 的能力；标准库没有类 AQS 的用户态框架，Meta 的 folly 提供 `folly::SharedMutex`、`folly::coro` |
| Rust | `std::sync::Mutex` / `RwLock`；生态广泛用 **parking_lot** crate | parking_lot 的精神与 AQS 最接近：全局哈希表 + parking spot + 位压缩状态；所有权与 RAII 保证不会忘记解锁 |
| Go | `sync.Mutex`（state 位 + semaphore park，含饥饿模式）、`sync.RWMutex` | Go runtime 自己做 goroutine 调度，park 不落到 OS 线程，这一点与虚拟线程思路相通 |
| Erlang/OTP | 语言层面没有锁原语，只有 process + mailbox | 不共享内存，因此从根上消除了锁的必要性 |
| Python | `threading.Lock` / `RLock` / `Condition`（封装 POSIX semaphore） | CPython 的 GIL 使多线程无法并行执行 CPU 密集任务，I/O 密集则依赖 asyncio |

> **实践口诀**：需要“可中断 / 可超时 / 多个等待队列”→ `ReentrantLock`；简单互斥保护 → `synchronized`（JDK 24+ 在虚拟线程下也安全）；读多写少且读写结构清晰 → `StampedLock`，但务必用 JMH 实测。
