# 08 数据库设计 — Database Design（原书 Step 8）

> 章题与小节题 ✅ 取自 InformIT 官方目录页；本步把 Step 5 的逻辑模型落成 **BI 目标库**的物理设计，是全书
> 建模流派的交锋点（星型/雪花 vs 规范化）。🔧 E1、E5 为本机 DuckDB/SQLite 演示，**非本书引擎/平台行为**。

## 8.1 两种设计哲学的分野（Differences in Database Design Philosophies）

✅ 官方小节先立前提：**操作型数据库（Operational Databases）** 为 OLTP（规范化、写密集、行级事务）而
**BI 目标数据库（BI Target Databases）** 为查询/聚合（读密集、宽扫描）而生，二者设计目标相反。这一步
承接 Step 5 的企业逻辑模型（偏规范化），但落到 BI 目标库时须切换到面向分析的结构——这正是 Inmon（3NF
原子 + 派生集市）与 Kimball（直接维度）路线分歧在**流程中的落点**（→ 8.6 对位）。

## 8.2 逻辑数据库设计：星型与雪花（The Star / Snowflake Schema）

✅ 官方小节「Logical Database Design / The Star Schema / The Snowflake Schema」：

- **星型（Star）**：事实表居中，维表**去规范化**一层展开——查询少 join、BI 工具友好、聚合直观。
- **雪花（Snowflake）**：维表进一步**规范化**成多级（商品→品类→部门）——省存储、保一致性，但 join 变多、
  部分报表工具不友好。
- 本册立场：与 Kimball 一致**优先星型**（面向分析可读性），仅在维表巨大或有强复用/合规需求时局部雪花化。

🔧 **实验 E1（DuckDB 1M 行事实表，非本书引擎行为）**：同一聚合分别按**星型**（维表预去规范化到 category）
与**雪花**（item→prod→cat 三级 join）执行，取最优耗时：星 **12.04ms** / 雪花 **12.48ms**——差异 <4%，
落在噪声内。结论：**在本地向量化引擎上，星 vs 雪花的墙钟代价几乎不显现**，该选择的真实差异体现在
**建模可维护性、口径一致性与报表工具兼容性**上，而非扫描速度——提醒读者别用「性能」当唯一理由（经典
MPP/行存引擎上差异会更明显，那是另一引擎行为）。

## 8.3 物理数据库设计（Physical Database Design）

✅ 官方小节「Physical Database Design」+「Implementation Options」下逐项——BI 目标库的物理开关清单：

- **物理数据集放置（Physical Dataset Placement）**：表/索引/临时空间落在哪些存储/表空间，冷热分层。
- **分区（Partitioning）**：按时间/范围切分事实表——BI 大表扫描与装载维护的关键手段。
- **聚簇（Clustering）**：让常用查询谓词列物理相邻，减少 I/O。
- **索引（Indexing）**：分析库通常少建二级索引（宽扫描无益），但点查/维表键仍需。
- **重组（Reorganizations）**：定期重整碎片，维持聚簇效果。
- **备份恢复（Backup and Recovery）**：仓库可重建但成本高，恢复策略权衡。
- **并行查询执行（Parallel Query Execution）**：聚合天然可并行，是 BI 库吞吐来源。

🔧 **实验 E5（SQLite 500k 行事实表日期区间扫描，非本书引擎行为）**：`day_id BETWEEN 100 AND 130` 聚合，
**无索引 13.79ms → 建 `INDEX(day_id)` 后 0.862ms（≈16×）**，聚合值 2,118,674 一致。直观展示物理设计项
（索引/聚簇）对 BI 查询的数量级影响——与 8.2「星/雪花几乎无差」形成对照：**真正的性能杠杆常在物理层**。

## 8.4 逻辑→物理的取舍矩阵（本章方法论 ⚠️ 编者归纳）

| 决策 | 偏规范化/雪花 | 偏星型/去规范化 |
| --- | --- | --- |
| 首要目标 | 存储/一致性/复用 | 查询可读性/BI 工具亲和 |
| 典型代价 | join 复杂度、工具适配 | 冗余、装载维护 |
| 本册倾向 | 维表巨大/合规复用 | **默认优先**（分析交付） |
| 🔧 证据 | E1：引擎上墙钟近乎持平 | E5：物理层才是主战场 |

- **交付物**：《数据库设计文档》（逻辑模式 + 物理放置/分区/索引方案 + 存储与恢复设计）。

## 核心概念速览（中英对照）

- **设计哲学分野** — Design Philosophies：OLTP 规范化 vs BI 面向分析的对立目标。
- **星型模式** — Star Schema：事实表 + 去规范化维表，少 join、工具友好（本册默认）。
- **雪花模式** — Snowflake Schema：维表多级规范化，省存储/保一致但 join 增多。
- **物理放置** — Physical Dataset Placement：对象到存储/表空间的冷热布局。
- **分区** — Partitioning：按时间/范围切分大表，利扫描与维护。
- **聚簇** — Clustering：谓词列物理相邻以降低 I/O（对照 E1/E5 的引擎差异）。
- **索引（分析库少用）** — Indexing：宽扫描收益低、点查/维键仍用（E5 示 16× 提升）。
- **重组** — Reorganizations：定期重整碎片维持聚簇。
- **并行查询执行** — Parallel Query Execution：聚合并行化=BI 吞吐来源。
- **物理层主杠杆** — Physical-Design Lever：真正的性能差异常在物理层而非星/雪花（🔧 E1 vs E5）。

## 最新演进与工业实践

2002→2026 对位（官方源 ⚠️ 转述 + URL 于 2026-10-02 验 200 ✅）：

- **物理设计七选项 → 云数仓托管 + 开放表格式**：分区/聚簇/放置多被**托管服务自动**处理（微分区/自动聚簇），
  手工物理设计权重下降；湖仓侧由 Iceberg/Delta 的分桶/分区元数据承接（对位
  [../Data_Lakehouse_in_Action/00-总览与阅读地图.md](../Data_Lakehouse_in_Action/00-总览与阅读地图.md)）。
- **星型 → 语义层下的「宽表 + 指标」**：分析亲和的星型逻辑仍在，但对外暴露改为**语义层**统一度量，
  物理形态可为大宽表/物化视图（⚠️ `https://docs.snowflake.com/en/user-guide/views-semantic/overview` ✅ 200、
  `https://cube.dev/docs/product/data-modeling/overview` ✅ 200）。

  该类引擎上被自动布局替代（对照盘上 [../Tuning_the_Snowflake_Data_Cloud/00-总览与阅读地图.md](../Tuning_the_Snowflake_Data_Cloud/00-总览与阅读地图.md)）。
- **建模流派之争 → 融合**：Data Vault 骨干（可演进/审计）+ 前端维度/星型（消费）的混用成主流（对位
  [../Data_Vault_2_0/附-Kimball与DataVault分工与混用.md](../Data_Vault_2_0/附-Kimball与DataVault分工与混用.md)）。
- **工业实践**：团队用 **dbt 声明式模型 + 语义层**把 8.2 逻辑设计与 8.3 物理由工具与平台分工——人管语义、
