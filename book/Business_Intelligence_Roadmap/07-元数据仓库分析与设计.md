## 7.1 元数据为何重要（The Importance of Meta Data）

✅ 官方小节开门见山：BI 仓库里「数据」易得、「**关于数据的数据**」（元数据）难建，而恰恰是元数据决定
使用者能否**找到、理解、信任**一个指标。没有元数据仓库，一致性维度与企业标准（Step 2B/5）就没有存放与
传播之处，BI 退化为「口口相传」。作者主张：**元数据要像主数据一样被严肃建模与治理**。

## 7.2 元数据分类与作为导航工具

✅ 官方小节「Meta Data Categories / Meta Data Classifications / Groupings of Meta Data Components /
Meta Data Repository as Navigation Tool / Data Standardization」：

- **元数据类别**：技术元数据（表/列/类型/血缘）、业务元数据（定义/口径/同义词，来自 Step 5 标准字典）、
  操作元数据（装载时间/行数/作业状态，来自 Step 9/11 ETL）。
- **分类与分组 / 优先级**：元数据组件成百上千，须**分类、分组、排优先级**，先做「高价值高频访问」的
  （血缘、口径定义）再做长尾。
- **导航工具**：元数据仓库的第一价值是「**找得到**」——从业务术语导航到物理表列，反向亦通。
- **数据标准化**：元数据里承载的标准，是让「同一个客户」在全企业唯一的路标。

🔧 **实验 E3（SQLite 递归 CTE 血缘，非本书引擎行为）**：以 `mt_table / mt_column / mt_lineage` 三表建最小
元数据仓库，对 `ods_customer.email` 做递归下游追踪，得 **3 跳链路**：
`dwd_customer.email_norm → mart_kpi.email_domain → rep_dash.domain_cnt`，深度=3。这就是「导航工具」的最小
可运行模型：一次递归查询回答「改这列会影响谁」。脚本 `D:\develops\tmp\dbwave_w9_birmap\exp.py`。

## 7.3 元模型与「元-元数据」

✅ 官方小节「The Logical Meta Model / The Entity-Relationship Meta Model / Meta-Meta Data」：

- **逻辑元模型**：先设计「描述元数据的模型」（有哪些元数据类型、彼此关系），与描述业务的逻辑模型区分开。
- **实体-关系元模型**：用 ER 方式刻画元模型（表、列、血缘、术语、所有者皆为实体）。
- **元-元数据（Meta-Meta Data）**：关于元数据本身的元数据（谁维护、何时更新、可信度）——治理自反性的关键，
  避免「元数据本身不可信」。

## 7.4 元数据仓库的挑战（Step 7 的清醒剂）

✅ 官方小节列出五类挑战（Technical/Staffing/Budget/Usability/Political）：

- **技术**：异构工具元数据格式不一、采集与同步难。
- **人力（Staffing）**：需专职元数据管理员，多数项目不设此岗。
- **预算**：元数据「看不见收益」，最易被砍。
- **可用性**：建了没人用（界面差、更新慢）。
- **政治**：口径定义即权力之争，元数据仓库被迫承载组织博弈——正需仲裁委员会（01 章）背书。

## 7.5 Step 10·元数据仓库设计

Step 10 把 Step 7 的分析落成**可构建的设计**：物理元模型（表/视图/存储）、采集机制（从 ETL 工具/DBMS
字典/BI 语义层自动抓取 vs 人工登记）、更新触发（装载即刷新血缘）、访问接口（目录 UI / API）。交付物为
《元数据仓库设计文档》；不做的风险=分析悬空、Step 14 无从开发。

## 7.6 活动·交付物·角色·不做之风险（两步并记）

- **交付物**：Step 7——元数据需求分析、优先级清单、逻辑元模型；Step 10——物理元模型设计、采集与更新机制、
  访问接口设计。
- **角色**：元数据管理员（核心团队，书中明确此岗）、数据架构师、ETL 工程师（提供操作元数据）、SME（业务元数据）。
- **不做的风险**：口径无处沉淀、血缘不可追（🔧 E3 的反面）、变更影响不可评估、治理承诺无法兑现。

## 核心概念速览（中英对照）

- **元数据仓库** — Meta Data Repository：存放技术/业务/操作元数据并可被查询导航的独立工程对象。
- **技术元数据** — Technical Meta Data：表/列/类型/血缘。
- **业务元数据** — Business Meta Data：定义/口径/同义词（源自 Step 5 标准）。
- **操作元数据** — Operational Meta Data：装载时间/行数/作业状态（源自 ETL）。
- **导航工具** — Navigation Tool：术语↔物理表列的双向查找。
- **元模型 / 元-元数据** — Meta Model / Meta-Meta Data：描述元数据的模型；关于元数据的元数据（可信度/维护者）。
- **优先级排序** — Prioritization of Components：先做高价值元数据（血缘、口径）后做长尾。
- **五类挑战** — Technical/Staffing/Budget/Usability/Political：技术/人力/预算/可用性/政治。
- **自动采集** — Automated Harvesting：从 ETL/字典/语义层自动抓元数据并装载即刷新。
- **元数据管理员** — Metadata Manager：书中明确的专职治理岗位。

## 最新演进与工业实践

2002→2026 对位（官方源 ⚠️ 转述 + URL 于 2026-10-02 验 200 ✅）：

- **元数据仓库 → 自动化数据目录/元数据平台**：手工登记退场，**主动/被动元数据自动采集 + 血缘 + 术语表**
  成标配（对位 [../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md](../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md)）；🔧 E3 的递归血缘查询即目录血缘图谱的内核。
- **口径载体 → 语义层**：业务元数据中「指标定义」的最强现代载体是**语义层**——同一份定义被所有 BI 工具消费
  （⚠️ `https://docs.getdbt.com/docs/build/semantic-models` ✅ 200、
  `https://learn.microsoft.com/en-us/fabric/data-warehouse/semantic-models` ✅ 200、
  `https://docs.snowflake.com/en/user-guide/views-semantic/overview` ✅ 200）。
- **元-元数据 → 治理属性/质量分**：可信度、Owner、SLA 成为目录对象的治理属性，接入数据治理评分（⚠️
  [../Understanding_Data_Governance/00-总览与阅读地图.md](../Understanding_Data_Governance/00-总览与阅读地图.md)）。
- **挑战演化**：Staffing/Budget 仍在，但 Usability/Political 因目录产品化与「数据产品 owner」制而缓解；
  技术异构挑战由开放表格式（Iceberg 等）统一 catalog 部分化解（对位
  [../Data_Lakehouse_in_Action/00-总览与阅读地图.md](../Data_Lakehouse_in_Action/00-总览与阅读地图.md)）。
- **工业实践**：成熟组织把本册「元数据仓库设计」实现为 **DataOps 流水线**：ETL 运行即回写血缘与操作元数据，
  口径变更走语义层 PR + 目录评审——正是 Step 7→10→14 贯穿轨道的自动化终态。
