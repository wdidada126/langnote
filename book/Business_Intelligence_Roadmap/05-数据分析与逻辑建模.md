# 05 数据分析与逻辑建模 — Data Analysis（原书 Step 5）

> 章题与小节题 ✅ 取自 InformIT 官方目录页；本步是**建模内核第一步**：以「自上而下逻辑建模 + 自下而上
> 源数据分析」双向夹逼，产出企业/项目逻辑数据模型、业务元数据标准、数据清洗策略。🔧 实验 E4 为本机
> DuckDB 演示，**非本书引擎/平台行为**。

## 5.1 本步的双向结构

Step 5 的精髓是**双向夹逼**：
- **自顶向下（Top-Down）**：从决策/需求出发做**逻辑数据建模**，得到「应该有什么数据、什么关系」。
- **自底向上（Bottom-Up）**：从真实源系统出发做**源数据分析**，得到「实际有什么数据、脏成什么样」。
两向在「标准化业务元数据」处会师，差异即清洗/转换工作量清单（喂给 Step 9/11 ETL）。

## 5.2 业务聚焦的数据分析（Business-Focused Data Analysis）

分析必须以业务语义为纲，而非以表为纲：先确认「哪些业务过程要进仓库、以什么粒度、支持哪些决策」，
再谈字段。官方小节把它置于本步之首，正是为了压住「拿到 ER 图就开画」的技术惯性。

## 5.3 自顶向下：逻辑数据建模

✅ 官方小节「Top-Down Logical Data Modeling / Project-Specific & Enterprise Logical Data Model /
Logical Data Modeling Participants」：

- **项目专属逻辑数据模型（Project-Specific LDM）**：本主动性所需的实体—关系—属性（不含物理细节）。
- **企业逻辑数据模型（Enterprise LDM）**：跨主动性共享的规范化主模型——本册站在**跨组织复用**立场，
  要求项目模型向企业模型对齐，这正是与 Kimball「以维度/业务过程建模」路线的张力点（→ 08 章讨论）。
- **建模参与者**：数据架构师 + 业务 SME + 元数据管理员同席，避免「技术闭门建模」。
- **标准化业务元数据（Standardized Business Meta Data）**：命名、定义、同义词、业务规则的字典化——
  是 Step 7/10/14 元数据仓库的**内容源头**，也是治理落点（对位数据目录/术语表）。

## 5.4 自底向上：源数据分析

✅ 官方小节「Bottom-Up Source Data Analysis」及其下：

- **技术数据转换规则（Technical Data Conversion Rules）**：编码/类型/单位/时区等技术映射。
- **业务数据域规则（Business Data Domain Rules）**：取值域、有效值、派生口径（如「活跃客户」定义）。
- **业务数据完整性规则（Business Data Integrity Rules）**：主外键、唯一性、跨行约束——**清洗的验收标准**
  来自此处与 Step 4 的 DQ 需求。

## 5.5 数据清洗（Data Cleansing）

✅ 官方小节「Data Cleansing / Data Quality Responsibility / Source Data Selection Process / Key Points of
Data Selection / To Cleanse or Not to Cleanse / Cleansing Operational Systems」——本册最有辨识度的策略主张：

- **数据质量责任归属**：清洗不是技术团队单方面兜底，**源系统数据 owner 负首要质量责任**，仓库只做「入库前
  的标准化 + 记录例外」。
- **源数据选择过程 / 选数要点**：不是所有源都进仓库，按决策价值与质量可行性**择优入仓**。
- **「洗还是不洗（To Cleanse or Not to Cleanse）」**：经典权衡——在仓库洗（集中、可控、但滞后）vs 在源
  系统洗（治本、但越权/慢）；书中倾向「**入库前在仓库侧标准化、重大问题回流源治理**」。
- **清洗操作型系统（Cleansing Operational Systems）**：承认有时必须反向修正源数据（生成异常清单交源系统处理）。

🔧 **实验 E4（DuckDB，非本书引擎行为）**：造脏源 1000 行，测得 **NULL 143、重复业务键 100、孤儿外键 77**；
按「去重（DISTINCT ON 键）+ 补空（COALESCE）+ 剔孤儿（JOIN dim 过滤）」清洗后剩 **730 行，三类问题各归零**。
量化说明「源质量差 → 清洗即删改近三成记录」，为 5.4 完整性规则与 5.5「洗不洗」提供数量级直觉。脚本
`D:\develops\tmp\dbwave_w9_birmap\exp.py`，repo 零产物。

## 5.6 活动·交付物·角色·不做之风险

- **活动**：建企业/项目 LDM、写业务元数据标准、盘源数据、定转换/域/完整性规则、定清洗策略与责任。
- **交付物**：逻辑数据模型（企业级 + 项目级）、标准化业务元数据字典、源数据分析报告、清洗规则与异常清单模板。
- **角色**：数据架构师（核心团队）主建模，SME（扩展团队）供语义，元数据管理员维护字典，源系统 owner 认质量责任。
- **不做的风险**：口径漂移（无标准）、清洗无验收（无完整性规则）、把脏数据直灌仓库（「垃圾进垃圾出」）。

## 核心概念速览（中英对照）

- **业务聚焦分析** — Business-Focused Data Analysis：以业务过程/决策为纲，先语义后字段。
- **自顶向下逻辑建模** — Top-Down Logical Data Modeling：从需求推「应有的实体与关系」。
- **自底向上源分析** — Bottom-Up Source Data Analysis：从源系统盘「实际的数据与脏度」。
- **企业 / 项目逻辑数据模型** — Enterprise / Project-Specific LDM：跨主动性主模型 vs 本主动性局部模型。
- **标准化业务元数据** — Standardized Business Meta Data：命名/定义/同义词/规则的字典化。
- **数据域规则 / 完整性规则** — Data Domain / Integrity Rules：取值域与主外键/唯一性等约束。
- **数据清洗** — Data Cleansing：入库前标准化 + 例外记录，责任归源数据 owner。
- **洗还是不洗** — To Cleanse or Not to Cleanse：仓库侧洗 vs 源侧洗的经典权衡。
- **择优入仓** — Source Data Selection：按决策价值与质量可行性选择纳入的数据源。
- **回流源治理** — Cleansing Operational Systems：重大问题生成清单交源系统治本。

## 最新演进与工业实践

2002→2026 对位（官方源 ⚠️ 转述 + URL 于 2026-10-02 验 200 ✅）：

- **企业 LDM → 湖仓统一明细层**：规范化企业模型在云湖仓以 **silver/curated 明细层**承载（⚠️
  `https://docs.databricks.com/aws/en/lakehouse/` ✅ 200），Inmon 式「单一事实来源」与湖仓融合（对位
  [../Data_Lakehouse_in_Action/00-总览与阅读地图.md](../Data_Lakehouse_in_Action/00-总览与阅读地图.md)）。
- **业务元数据标准 → 语义层术语表**：字典化的「客户/收入」定义进入**语义层**成为机器可读指标，人在目录看、
  机器在查询时强制（⚠️ `https://docs.getdbt.com/docs/build/semantic-models` ✅ 200、
  `https://docs.snowflake.com/en/user-guide/views-semantic/overview` ✅ 200）。
- **清洗策略 → 分层 + 契约**：「入库前标准化、问题回流源」落为 **bronze 原样留存 / silver 清洗** 分层 +
  **数据契约**把质量责任写进 schema/校验（对位 [../Analytics_Engineering_with_SQL_and_dbt/00-总览与阅读地图.md](../Analytics_Engineering_with_SQL_and_dbt/00-总览与阅读地图.md)）；🔧 E4 的去重/补空/剔孤儿即 silver 层测试的雏形。
- **「择优入仓」→ Schema-on-Read 与治理取舍**：湖仓按需读取降低「全都要」诱惑，但更需本步的价值—成本闸门。
- **工业实践**：现代团队把源系统质量责任以「生产者契约 + 质量 SLA」制度化，仓库侧只做准入校验——正是
  本书「DQ 责任归源」主张的当代工程化。
