## 4.1 审计两问框架精读（⚠️ 转述框架，问卷条目为编者按 TOC 重构）

**干系人侧（4.1.1–4.1.2）**——角色×问题的笛卡尔积，典型阵容：数据工程、分析/BI、数据科学家、
合规/安全、平台运维、业务域负责人、财务（FinOps）。要问的核心五类：

1. 数据新鲜度期望（T+1？分钟级？）→ 决定摄入层形态（06 章批/微批/流）；
2. 查询画像（谁、多大、多并发、点查还是扫描）→ 决定联邦层与加速手段（08 章）；
3. 合规与留存（地域限制、被遗忘权、审计年限）→ 决定 catalog 权限模型与保留政策（07/11 章）；
4. 现有资产（Hive 表数量、ETL 工具、BI 绑定）→ 决定迁移路径与联邦过渡（08.5.7 场景）；
5. 团队技能与运维预算 → 决定"自管开源栈 vs 托管服务"的总开关。

**技术侧（4.1.3）**——按五层盘点：桶与文件格式现状 / 作业编排与写入方清单 / 目录与元数据现状
（Hive metastore？多目录并存？）/ 查询引擎与接口 / BI 与 notebook 工具链。**审计产出物 = 一张现状×
痛点×迁移风险的三列表**，不是 PPT。

## 4.3 五类需求模板（本章可用的骨架，逐条通向选型章）

| 需求族（TOC 实抓小节） | 必答问题（编者按章旨重构 ⚠️） | 通向 |
| --- | --- | --- |
| 存储（4.3.1） | 云上还是自管？S3 API 硬要求？加密/版本控制/生命周期谁负责？ | 05 |
| 摄入（4.3.2） | 吞吐峰值、容忍时延、schema 变更频率、背压与重放语义？ | 06 |
| 目录（4.3.3） | 高可用等级、权限粒度（表/列/行？）、跨引擎一致性、是否要多目录联邦？ | 07 |
| 联邦（4.3.4） | 直查 vs 加速缓存？源系统数量？BI 用户自助度？语义层要不要？ | 08 |
| 消费（4.3.5） | BI 工具清单、notebook 生态、AI/agent 接入要不要预留 MCP/Flight？ | 09 |

- 模板用法（本书立场）：需求文档里**每个形容词都要被追问成数字**——"快"→ p95 查询时延目标；
  "多"→ TB/日增与行数分位；"安全"→ 等保/ GDPR 条款映射到层与组件。

## 4.2/4.4 Hamerliva Bank 样板线（⚠️ 虚构案例，按章旨转述要点）

- 银行画像（4.2 设定）：存量 Hive/传统 ETL、监管严格（留存与访问审计）、新业务要实时风控与
  自助分析——**典型的"带着镣铐迁湖仓"**。
- 审计发现样板：干系人诉求分裂（风控要分钟级、财务要 T+1 成本可控、合规要可证明的删除）→
  需求答卷（4.4）给出五族带数字的条目 → 4.5 架构图按答卷逐块标注"满足哪条需求"。
- 编者注：该案例的价值不在结论而在**痕迹**——路演节（4.5.2）演示了如何用一页需求-选型对照表
  抵挡"为什么不用现成云仓"的灵魂拷问。

## 4.5 架构计划与路演（方法要点）

1. **图随层走**：五层各一列/一区，箭头画数据流与查询流两个方向（02 章模型的图形化）。
2. **每块选型挂依据**：标注"因需求 4.4.3-c（行级权限）选 Polaris/REST catalog"式引用，拒绝审美选型。
3. **预留演进位**：v2→v3 表升级路径、catalog 迁移路径（跨目录复制工具）、加速层的可摘除性——
   路演被质疑时这三条最常救命。
4. **分阶段**：demo（03 章栈）→ 试点域 → 逐域迁移，联邦层作为旧 Hive 与新湖共存期的桥（08.5.7 场景）。

## 常见误区

| 误区 | 纠偏 |
| --- | --- |
| 跳过审计直接开选型会 | 4.1 存在的意义：没有量化诉求的选型会退化为厂商偏好战 |
| 需求写成"支持 ACID、要开放" | 那是入场券不是需求；需求是比较级（多高可用、多细粒度、几个引擎） |
| 把干系人访谈合成一份问卷群发 | 角色问题域差异极大（合规问删除证明，BI 问并发时延）——4.1.2 的分角色提纲是关键 |
| 一份架构图用到退役 | 4.5 的路演图是**决策快照**，每次层内换件要回写依据条目 |
| "迁移=全部重写" | 08 章联邦/08.5.7 渐进场景给出共存路线；存量 Hive 可先注册后渐进改写 |

## 本章速查卡

- 审计三板斧：问人（干系人×问题矩阵）→ 盘物（五层现状清单）→ 合流（发现=痛点×风险表）。
- 核心五问：新鲜度/查询画像/合规留存/存量资产/技能预算——分别锚定 06、08、07+11、08+09、06+07 章。
- 需求模板律：形容词→数字；每条需求必须能被候选方案以是/否/阈值回答。
- 路演结构：图随层走、选型挂依据、预留三个演进位（v2→v3、目录迁移、加速层可摘除）。
- 产出物三件：干系人诉求表、技术现状清单、需求-选型对照矩阵（后两件在 05–09 章反复回填）。
- 样板记法：Hamerliva Bank = "带着镣铐迁湖仓"的画像原型（监管严+诉求分裂+存量 Hive）。
- 一票否决示例：地域数据主权不过关直接筛掉三家公有云桶（05 章）——审计质量决定选型会议效率。

## 核心概念速览（中英对照）

- **平台审计** — Platform Audit：迁移前对干系人诉求与技术现状的双线盘点（4.1）。
- **干系人地图** — Stakeholder Map：数据/分析/AI/合规/运维/财务的角色-诉求矩阵。
- **技术栈盘点** — Technological Audit：五层现状清单（桶/作业/目录/引擎/工具）。
- **需求族** — Requirements by Layer：存储/摄入/目录/联邦/消费五组可量化条目（4.3）。
- **可回答性** — Answerability：需求必须能被候选方案以是/否/数值响应——模板设计的准绳。
- **架构计划** — Architectural Plan：带需求引用标注的五层图（4.5.1）。
- **路演** — Road Show：向干系人巡讲架构方案并收集否决意见的环节（4.5.2）。
- **决策快照** — Decision Snapshot：架构图+依据表的版本化存档，供变更回查。
- **共存期** — Coexistence Phase：旧 Hive 与新湖仓经联邦层并行服务的迁移窗口。
- **FinOps 干系人** — 财务代表：把"成本可预测"写进需求条目的人——云仓账单是本书立论的第一靶。
- **Hamerliva Bank** — 本书贯穿虚构客户：审计→需求→设计→路演的样板载体。

## 最新演进与工业实践

- **评估框架的公共化（⚠️ 定性）**：2024–2026 各家（Dremio/Snowflake/Databricks）发布的 Iceberg
  migration 评估清单与本书 4.1–4.3 同构——审计问卷本身已成售前标准动作；用其清单可加速但要补
  自建"否决条件"（如权限粒度不足）。
- **迁移工具线（✅ 实抓存在性）**：AWS S3 Tables 自带 Iceberg 兼容库导入路径（docs.aws.amazon.com
  的 Apache Iceberg on AWS 指南线，2026-08 更新）；GCP 有 Lakehouse for Apache Iceberg 产品线
  （https://docs.cloud.google.com/lakehouse/docs/release-notes ✅ 在更）——4.5 的"托管替身"选项
  比成书期更多，路演素材需按当期更新 ⚠️。
- **目录即审计面**：REST catalog 的访问日志/OAuth2 能力（附录 C.4.5/本册 14 章）使"谁动了哪张表"
  从作业日志审计升级为目录服务审计——11 章访问审计的落点。
