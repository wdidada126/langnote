## 9.3 三大接口精读（本章的技术脊柱）

| 接口（TOC 实抓） | 定位 | 架构要点 |
| --- | --- | --- |
| JDBC/ODBC（9.3.1） | 最宽的存量兼容面：BI/ETL/老应用全认 | 行式、驱动质量参差；湖仓经由联邦层（08 章）暴露，而非引擎裸供 ⚠️ |
| Arrow Flight（9.3.2） | 列式高吞吐 RPC：大块结果/数据科学管道 | Arrow 内存格式零拷贝跨语言——notebook/特征管道的大吞吐通道；Flight SQL 在 JDBC 语义上换 Arrow 传输 ⚠️ 支持面按服务各异 |
| **MCP（9.3.3）** | AI agent 时代的"数据工具接口" | 把"查目录/跑查询/取样本"发布为 agent 可发现的工具面——07 章权限模型在此必须贯通（agent 继承谁的凭证是核心问题） |

- 三接口并列是 2026 消费层的分水岭信号：**人用 SQL（JDBC/ODBC）、程序用列式（Flight）、
  agent 用协议（MCP）**——同一治理面（catalog 权限 + 审计日志）要罩住三条门。
- 编注（⚠️ 转述常识）：MCP 规范本身由 Anthropic 主导、生态快速跟进；本书只把它列为接口选项，
  落地细节以 MCP 官方规范当期版为准。

## 常见误区

| 误区 | 纠偏 |
| --- | --- |
| "BI 直连对象存储读 parquet 最省事" | 绕开 catalog/联邦=绕开快照隔离与权限——03 章已立的范，这里再强调：消费层站在接口上 |
| "MCP 只是聊天插件" | 它把数据访问变成 agent 的工具协议面——07 章权限与 11 章审计若不贯通就是裸奔的数据面 |
| "JDBC 性能差所以淘汰" | 存量与兼容为王；大吞吐走 Flight、agent 走 MCP，三者共存不互斥 |
| 十场景当采购清单 | 场景给的是主轴约束不是产品名——工具年抛，接口与治理面长存 |
| "消费层权限在 BI 工具里配好即可" | BI 侧权限只罩 BI 入口；notebook/agent 旁路会破功——权限要沉到 catalog/联邦层统一执行（07.6） |

## 核心概念速览（中英对照）

- **消费层** — Consumption Layer：交付业务价值的一层——前五层的意义在此兑现（2.7.5 的回环）。
- **JDBC/ODBC** — 关系驱动标准接口：最宽的 BI/应用兼容面。
- **Arrow Flight** — 基于 Arrow 列式内存格式的高吞吐 RPC：大结果/数据管道的传输答案。
- **Flight SQL** — JDBC 语义 + Arrow 传输的标准化组合 ⚠️ 支持面按服务而异。
- **MCP** — Model Context Protocol：把数据服务发布为 AI agent 可发现工具面的开放协议（9.3.3）。
- **语义模型** — Semantic Model：BI 层的指标/维度口径载体——8.3.9 悬题的消费端答案。
- **嵌入式分析** — Embedded Analytics：把报表/API 织进产品（9.5.3/9.5.8 的主轴）。
- **行级权限** — Row-Level Security：消费面最常被要求的治理原语——贯通目录才成立（07.6）。
- **导出控制** — Export Control：防"BI 变拖库"的出口治理（9.5.6 主轴）。
- **多租户投影** — Tenant-facing Access：SaaS 把内部湖仓能力按租户切面开放。
- **消费者分型** — Consumer Personas：BI 用户/notebook/AI agent 三类需求的分型法（9.2）。
