## 10.1 四类文件病的因果表（⚠️ 机理转述；量化口径见 🔧 演示四）

| 病 | 病因 | 症状 | 药（10.2/10.3） |
| --- | --- | --- | --- |
| 小文件（10.1.1） | 高频 commit、并行写者多、分区过细 | list/GET 风暴、引擎 task 数爆炸、查询慢 | rewrite_data_files 合小 |
| 数据错位（10.1.2） | 写入序与查询谓词无关 | 剪枝失效：min/max 区间互叠，扫一堆不用文件 | rewrite 时按常用谓词列排序（sort 策略） |
| 元数据膨胀（10.1.3） | manifest/快照堆积 | 规划阶段读清单本身变慢（loadTable 变重） | rewrite_manifests + expire_snapshots |
| MoR 读合并（10.1.4） | delete 文件攒多 | 读要合并数据+delete，CPU 与 IO 双倍账 | rewrite 合并 delete（delete file compaction） |

## 10.2 compaction 精读（旋钮三个，默认值全要按桶请求费与引擎重估 ⚠️）

1. **What is compaction（10.2.1）**：读旧文件→按新布局写新文件→一次提交登记"加新删旧"——
   本质是**用一次重写换读侧长期红利**；提交仍走 02 章原子指针，旧快照读者不受惊扰。
2. **Target file size（10.2.2）**：合并后的目标尺寸——太小→文件数与 manifest 膨胀，太大→并行度差、
   重写代价高；与 05 章桶的请求费模型联动（GET 次数×单价）。
3. **Files to be included（10.2.3）**：哪些文件入池（按大小阈值/分区/最近写入年龄）——
   全表重写 vs 增量分片重写的取舍。
4. **Filters to scope（10.2.4）**：谓词限定范围（近 N 天分区/热点桶）——大表常态化维护的省钱关键，
   配合 11 章编排按表定制政策。

- 引擎侧语法（Spark `CALL system.rewrite_data_files(...)`、Flink action、各托管服务任务）不在此

## 10.3 足迹管理与保留合规

- **快照过期（10.3.1）**：`expire_snapshots(older_than/retain_last)` 把出窗快照从清单退役——
  **退役≠删除文件**：真删由后续清理（orphan 文件清除）执行；两步的窗口错配是"删坏"事故源 ⚠️。
- **COW vs MOR 对保留的影响（10.3.2）**：MoR 表里被删行仍躺在旧数据文件+delete 文件里，直到
  rewrite 合并+expire 清理——"逻辑已删、物理还在"的窗口是合规审计要点。
- **监管删除（10.3.3）**：被遗忘权类请求的正确姿势=行级 DELETE（或按主体过滤重写）→ rewrite →
  expire → orphan 清理，四步都留证据链（→ 11 章审计）。仅 UPDATE 打标记≠删除。

## 10.4 元数据表：维护前的听诊器（本章给概览，逐表在附录 A/本册 12 章）

诊断套路（⚠️ 转述 + 编者实践注）：`files` 看文件大小分布（小文件比例）→ `manifests` 看清单条目数
（规划负担）→ `snapshots` 看提交频率与保留深度（expire 政策校准）→ `partitions` 看倾斜 →
再决定 10.2/10.3 的旋钮。顺序反了就是"无脑天天全表 rewrite"。

## 常见误区

| 误区 | 纠偏 |
| --- | --- |
| "compaction=定期全表重写" | 大范围重写自身制造 IO/请求费风暴——10.2.4 的 scope 过滤与增量分片才是常态（11 章编排按表定制） |
| "expire 删了历史文件" | expire 只动元数据引用；物理删除靠 orphan 清理且需安全窗口（活过所有在途读+备份点）⚠️ |
| "MoR 表删行即刻物理消失" | delete 文件只是记账——合规敏感表要把"rewrite+expire+清理"写进删除 SLA |
| "元数据膨胀不影响读" | 规划期要读 manifest list/manifests——膨胀直接拖慢每次查询的启动（loadTable 变重的连锁） |
| "小文件只影响查询" | 桶的 list/GET 计费、引擎 task 调度、备份扫描全在小文件上多交税（05/06 章联动） |

## 本章速查卡

- 因果串：摄入节拍（06）→ 四类病（10.1）→ 三旋钮（10.2）→ 两政策（expire/清理，10.3）→ 一仪表（元数据表，10.4 与 12 章）。
- 顺序铁律：先诊断后开药；rewrite → expire → 孤儿清理，窗口错配即事故。

## 核心概念速览（中英对照）

- **小文件问题** — Small Files：高频提交/过度分区的产物——湖仓头号运维病。
- **数据错位** — Poorly Colocated Data：文件内数据与查询谓词无关，min/max 剪枝失效。
- **元数据膨胀** — Metadata Sprawl：manifest/快照堆积拖慢查询规划与目录负载。
- **读合并成本** — Merge-on-Read Cost：delete 文件攒量后的 CPU/IO 双倍账（10.1.4）。
- **Compaction** — 文件重写合并：以一次提交"加新删旧"换读侧长期红利（10.2.1）。
- **目标文件大小** — Target File Size：与桶请求费、引擎并行度联动的第一旋钮。
- **范围过滤** — Scoping Filters：按分区/年龄/大小圈定重写池——常态化维护的省钱阀。
- **快照过期** — Snapshot Expiration：退役出窗快照的元数据引用（不是物理删除）。
- **孤儿文件清理** — Orphan File Removal：物理删除无人引用文件；窗口错配是高危操作。
- **COW/MoR 残留形状** — Retention Implication：同一条 DELETE 在两策略下物理消失路径不同。
- **被遗忘权工程化** — Right-to-be-Forgotten Pipeline：DELETE→rewrite→expire→清理四步留证链。
- **诊断顺序** — Metadata-first：先元数据表听诊再动旋钮——本章的操作纪律。
