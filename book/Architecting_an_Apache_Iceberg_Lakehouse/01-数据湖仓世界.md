## 1.1–1.4 演进叙事精读（⚠️ 依官方简介与公开资料转述框架，正文细节不复述）

本书第 1 章的功能是**建立动机**，四段历史线的因果链值得背下来：

```text
关系数据库（单机事务，结构化）
  → 数据仓库（面向分析的重构：星型/维度建模、ETL、schema-on-write）
    → 云数仓（存算分离、按需弹性；但按查询/存储计费，冷数据也交税）
      → Hadoop/数据湖（先存后想：廉价对象存储 + 任意格式；
        代价：没有事务、没有 schema 契约、并发写即损坏——Hive 表 metastore
        与存储目录"名实不符"是经典病灶）
        → 表格式（Iceberg/Delta/Hudi）在湖文件之上补一层"表真相"元数据
          → 湖仓：对象存储的账 + 数仓的规矩
```

- 每段迁移的驱动力都是一对矛盾：**灵活性（schema-on-read、多引擎、任意数据）**对
  **管理性（ACID、治理、性能保证）**。云数仓与 Hadoop 各取一半，湖仓用"开放表格式 +
  可插拔引擎"试图同时拿到。
- 官方书页 "what's inside" 的卖点句——"without the expense and vendor lock-in of platforms like
  Snowflake, BigQuery, and Redshift" ✅ 实抓——就是 1.3 的靶子：本书立场是**开源路线的湖仓**。

## 1.6 湖仓的"两全"要付的三张账单（本章的批判性补注 🔧视角见 02 章演示）

1. **元数据税**：表格式把"真相"搬进文件树，于是维护对象从"表+索引"变成"快照/清单/孤儿文件"——
   第 10–11 章的整章运维就是这张账单。
2. **目录耦合**：引擎找表要经 Catalog，Catalog 成为新的单点与治理抓手——第 7 章。
3. **引擎自由度的幻觉**：写入侧的引擎（Spark/Flink/Kafka Connect）与读取侧（Trino/Dremio/BI）
   对表格式版本特性的支持不齐（v2 delete、v3 DV 等），选型要按"最短板引擎"评估——第 8–9 章。

## 常见误区（本章级）

| 误区 | 纠偏 |
| --- | --- |
| "湖仓 = 湖 + 仓各建一套再同步" | 湖仓是**一份数据**（对象存储上的表格式文件）+ 多引擎；两份存储的"湖仓"是双写架构 |
| "上了 Iceberg 就自动治理" | 表格式只给事务/快照/演化的**机制**，权限、血缘、留存策略来自 Catalog 与平台层（07/11 章） |
| "本书反云数仓" | 1.6 的立场是"最佳of both"而非替代论；消费层（09 章）里 BI/AI 工具照常接入，包括商业引擎 |
| 把演进史当替代史 | 现实中四层（RDB/仓/湖/湖仓）长期并存——第 8 章的联邦层正为"并存"设计 |

## 本章速查卡

- 一句话：湖仓=湖的账+仓的规矩，Iceberg 是"规矩"的文件化定义。
- 演进五幕：RDB→仓→云仓→Hadoop 湖→表格式/湖仓；每幕解决一对"灵活 vs 管理"矛盾、留一对新债。
- 云仓三痛：按量账单、厂商锁定、冷数据税（1.3 的靶面）。
- 湖三痛：无事务、无契约、沼泽化（1.4 的靶面）。
- Iceberg 四给：ACID、演化、时间旅行、剪枝（1.5，机制展开在 02 章）。
- 湖仓三账单（编者补注）：元数据税、目录耦合、引擎支持不齐——通向 07/08/09 章。
- 记忆钩：Hive metastore 记"路径约定"，Iceberg 记"文件清单"——一字之差，治理天堑。
- 过关标准：能默画五幕演进图并说出三账单，本章即通过。
- 姊妹册分工回顾：机制原理→活用入門、Spark 语法→Use_Iceberg_with_Spark、平台职能→Practical_Lakehouse——本章只负责"为什么"。
- 现实校验：四层架构（RDB/仓/湖/湖仓）在任一企业里都同时存在——演进图是地层图，不是替换时间表。

## 核心概念速览（中英对照）

- **数据仓库** — Data Warehouse：schema-on-write、面向分析的强治理存储，星型模型为主流建模法。
- **云数仓** — Cloud Data Warehouse：存算分离、按量计费的托管仓（Snowflake/BigQuery/Redshift）。
- **数据湖** — Data Lake：对象存储上"先存后想"的原始数据区，灵活性高而事务缺失。
- **数据沼泽** — Data Swamp：无治理湖的贬称——文件在、真相不在。
- **湖仓一体** — Lakehouse：湖的成本/开放性 + 仓的事务/治理，同一份数据多引擎消费。
- **开放表格式** — Open Table Format：在数据文件之上定义"表真相"的元数据规范（Iceberg/Delta/Hudi）。
- **Schema-on-read** — 读时定形：入库不校验、查询时解释——湖的灵活性来源。
- **ACID 事务** — Atomicity/Consistency/Isolation/Durability：湖上由快照原子切换兑现。
- **时间旅行** — Time Travel：按快照 id 或时间戳查询历史表状态。
- **厂商锁定** — Vendor Lock-in：数据/格式绑定单一平台迁移高税——本书立论的反面。
- **存算分离** — Disaggregated Storage & Compute：云仓与湖仓共同的架构基线。
- **Hive metastore** — Hive 元数据库：目录只记"分区路径约定"，与文件实态易脱节——Iceberg 要革的命。
