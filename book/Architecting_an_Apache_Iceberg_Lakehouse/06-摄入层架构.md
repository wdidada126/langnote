## 6.2 三模型与"快照节拍"心智（⚠️ 概念转述）

```text
新鲜度阶梯（写入侧唯一硬约束：每次提交=一个新快照）：
  批：日/小时级一次大 commit —— 快照少、文件大、compaction 压力小
  微批：每 1–15 分钟一 commit —— Spark Structured Streaming 触发器节奏
  流：每 checkpoint/flush（秒~分钟）一 commit —— Flink/Kafka sink
代价梯度：commit 越频繁 → 小文件越多 + manifest 膨胀越快 → 读放大与请求费上升
       → 10 章 compaction 与 11 章编排必须前置预算（"摄入的账由维护还"）
对照面：Paimon 把这条阶梯做到检查点级（秒）并自带 changelog 语义——
  "Iceberg 批表顺便流" vs "流表下沉到湖"的分工见
  [../Apache_Paimon_Streaming_Lakehouse/12-多引擎生态与四大湖格式对比.md](../Apache_Paimon_Streaming_Lakehouse/12-多引擎生态与四大湖格式对比.md)。
```

### 🔧 演示三：CoW 与 MoR 的两套行数账（DuckDB 1.5.5 手写迷你清单，本机跑过）

承 02 章演示数据（快照 1001→1003）：`DELETE` 200 行后，
- **MoR 口径**（读 1002：数据 1000+2000 加 delete 文件记 -200）= **net 2800 行**；
- **CoW 口径**（读 1003：001 重写为 001b=800 行，delete 文件随合并退役）= **net 2800 行**。
两口径殊途同归是**正确性要求**（D3a/D3b 数字相同 ✅ 实测输出）；差异全在成本——MoR 写便宜读要合并，
CoW 写要重整文件读零负担。删得越狠，MoR 的 delete 文件越拖读（10 章 rewrite 的动机）。

## 6.4 九类工具速记（TOC 实抓名单 ⚠️ 行为均转述；选型考量=6.4.10）

| 工具（6.4.x） | 生态位一句话 | 典型搭配 |
| --- | --- | --- |
| Apache Spark（6.4.1） | 批+微批主力写者，转换重活的承载 | 大 ETL、回刷、compaction 作业（10 章） |

## 6.5 情境化规则（TOC 六条 ⚠️ 按题述展开）

低时延优先→流模型+MoR 与频繁 commit 的读放大对冲；高吞吐→批/微批+大文件目标（target-file-size 与
桶请求费联动）；复杂转换→Spark 承载、避免流式里塞重状态；schema 演化频繁→选容忍漂移的摄入器
（CDV 系或带 schema evolution 的 sink）；运维预算薄→云托管服务替换自管 Flink；既有云绑定→
6.4.9 就近原则但守住 S3 API 与 REST catalog 两个可移性锚（05 章 5.3）。

## 常见误区

| 误区 | 纠偏 |
| --- | --- |
| "流式摄入=新鲜度随便给" | commit 节拍即快照节拍，且要交小文件/manifest 膨胀的税——新鲜度承诺要连维护预算一起签 |
| 高频 upsert 场景用 CoW | 每改一行的整文件重写代价随删改比飙升——高比例行级改删走 MoR+定期 compaction 合并（10 章） |
| "多个写入器各开各的 catalog 没事" | 不同 catalog 实现（Hive vs REST 各服务）的 CAS 语义与重试行为不同，混用会造成冲突检测盲区 ⚠️ |
| 把 CDC 工具当 schema 演化保险 | 多数托管 CDV 对破坏性变更（改型/删列）仍要人工政策；6.1.3 问的是"演化策略"不是"演化能力" |
| "Kafka 落 Iceberg 后 Kafka 可下线" | 湖的秒级≠消息级：细粒度重放/低时延点查仍在流系统职责内（对照流式读语义 → ../Use_Iceberg_with_Spark/06） |

## 核心概念速览（中英对照）

- **摄入模型** — Ingestion Model：批/微批/流三种节拍与代价阶梯（6.2）。
- **快照节拍** — Commit Cadence：每次提交一个新快照——新鲜度与文件健康的同一枚硬币。
- **追加写** — Append：只新增文件与新快照的写入语义——最不易冲突。
- **动态分区覆盖** — Overwrite Partitions：按分区间替换，批量回刷的常规武器。
- **写时复制** — Copy-on-Write (CoW)：改删即重写整文件；读侧零合并成本。
- **读时合并** — Merge-on-Read (MoR)：改删落 delete 文件；写便宜读合并。
- **position/equality delete** — 两种 v2 删除文件：按行位删 vs 按键值删（机制在活用入門 05）。
- **乐观并发提交** — Optimistic Commit：CAS 指针 + 冲突分类 + 重试（6.3.2）。
- **CDV** — Change Data Capture/_delivery：Fivetran/Qlik/Airbyte 代表的托管复制摄入类。
- **CDC 入湖** — CDC Ingestion：数据库变更流直接物化为湖表的设计模式。
- **schema 漂移** — Schema Drift：源加列/改型与摄入器演化策略的摩擦面。
- **背压与重放** — Backpressure/Replay：流摄入的可靠性两问——at-least-once + 幂等写为常见答案。
