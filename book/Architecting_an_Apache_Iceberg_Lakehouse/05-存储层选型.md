## 5.1 四类要求的架构读法（⚠️ 章旨转述 + 编者展开）

| 要求 | 追问到数字（承 04 章） | Iceberg 侧的耦合点 |
| --- | --- | --- |
| 性能（5.1.1） | GET 时延 p95、吞吐、list 语义代价 | 元数据风暴=大量小 GET（清单文件读）；compaction 后的大文件顺序读 |
| 安全（5.1.2） | 桶策略/IAM/加密（SSE 还是 client-side）/私网端点 | catalog 的凭证置换（vended credentials，REST 规范特性）决定"引擎持不持密钥" |
| 完整性（5.1.3） | 版本控制/不可变对象（object lock）/跨区域复制 | Iceberg"只增不改"的文件纪律与桶版本控制天然配对——删旧文件才靠 expire |
| 成本运维（5.1.4） | GB·月、请求费、团队值守能力 | 请求费敏感时，清单层设计（manifest 数量）直接影响账单 |

## 5.2 块 vs 对象（概念对照，湖仓的选型前提）

```text
块存储：POSIX/文件系统在其上自建；改一字节重写一块；扩容绑实例 —— 与"多引擎共享读"错位
对象存储：HTTP PUT/GET/扁平命名空间+前缀list；不可变覆盖语义；水平扩到 EB —— 湖仓默认底座
关键错位提醒：对象存储的 list 是慢操作、rename 不是原子元数据操作——
  正因如此 Iceberg 用"写新文件+CAS 指针"而非 rename 实现提交（02 章）；
  Hadoop 目录 rename 的心智迁移到桶上必翻车 ⚠️（通识性结论，非本书实测）。
```

## 5.3 两大标准为什么是"选型锚"

- **Apache Parquet**（5.3.1）：列式 + 行组统计（min/max、null count）——Iceberg manifest 的剪枝
  与引擎谓词下推都建立在"文件是 Parquet 且统计可信"上；深读 →
  [../bigdata/09-存储与文件格式.md](../bigdata/09-存储与文件格式.md)（本册不重复文件格式机制）。
- **The S3 API**（5.3.2）：事实标准协议——**认协议不认厂商**是本章的采购军规：S3 兼容面越全，
  跨云/自建可移性越高（MinIO/Ceph 的存在意义）；写死某云私有 API 的组件会把 5.4 的记分卡变成一票否决。

| 候选（TOC 实抓） | 一句话定位 | 典型搭配场景 |
| --- | --- | --- |
| Hadoop（HDFS） | 自建老湖，NameNode 瓶颈但数据主权完整 | 08.5.5 Cloudera 现代化场景的存量 |

## 5.5 按要求回选（章末收口逻辑复述 ⚠️）

四类要求各设一票否决项再谈加权：安全不过（无加密/无私网）直接出局；完整性存疑（无版本控制且
expire 激进）要 11 章灾备加钱；性能与成本按查询画像权衡（高频小文件 list 型 vs 大件顺序扫描型）。
**结论模板**："默认公有云原生桶 + S3 API 纪律 + 对象版本控制；自建仅在数据主权/成本曲线/地缘合规
三个触发词命中时进入 MinIO/Ceph 评估。"（编者按章旨凝练）

## 常见误区

| 误区 | 纠偏 |
| --- | --- |
| "桶随便选，Iceberg 会抹平差异" | 抹平的是文件组织，抹不平 list 性能/请求费/凭据模型/区域合规——5.1 的四类要求全是桶级差异 |
| "S3 兼容=零成本迁移" | 兼容面缺（如缺 ETag 语义/条件写）会咬到 catalog 与引擎细节；按协议测试集验收而非宣传页 ⚠️ |
| "对象存储不可变所以天然安全" | 不可变是特性不是权限——桶策略配错照样整桶删；配合 vended credentials 与审计（07/11 章） |
| "Parquet 版本/压缩codec 无所谓" | codec 影响引擎 CPU/IO 权衡与谓词下推效果；团队要定一份表写入规范（承 06 章写侧） |
| 用块存储心跳管桶 | 追"挂载点/目录树"心智会在对象存储上做危险假设（rename/原子目录）——5.2 的本意 |

## 核心概念速览（中英对照）

- **对象存储** — Object Storage：HTTP API、扁平命名空间、不可变覆盖——湖仓默认底座。
- **块存储** — Block Storage：裸设备语义，文件系统自建——与共享分析负载错位。
- **S3 API** — 对象访问的事实标准协议；兼容面完整度=可移性。
- **Apache Parquet** — 列式文件格式：行组统计是剪枝的地基。
- **取回性能** — Retrieval Performance：GET 时延/吞吐/list 代价三件套。
- **桶策略** — Bucket Policy：资源侧权限——与引擎侧 IAM 形成双层。
- **SSE / Client-side 加密** — 服务端/客户端加密：密钥主权分界线。
- **Object Versioning / Lock** — 对象版本控制/不可变锁：与快照过期配合的完整性保险。
- **Vended Credentials** — 目录代发的短时凭证：引擎不再持桶密钥（REST catalog 特性）。
- **私网端点** — Private Endpoint/privatelink：合规链路的出网面控制。
- **记分卡** — Vendor Comparison Summary：5.4.1 的候选×要求打分框架。
- **MinIO / Ceph** — 自建 S3 兼容开源双雄：数据主权触发器。
- **ADLS / StorageGRID / ECS / Wasabi / Everpure** — 商业对象存储谱系：地缘合规/多站点/性价比/全闪各占位。

## 最新演进与工业实践

- **S3 主线的 2026 现状（⚠️ 定性）**：AWS S3 Tables（Iceberg 原生桶）、Express 类高 ops 桶持续
  压低"元数据风暴"的时延成本；GCP/Azure 各自的 Iceberg 兼容层在推进——05.4 厂商对比表的
  "托管 Iceberg 桶"列每年都在加行，以当期文档为准。
- **Parquet 变体之争**：列式格式侧 2025–2026 出现新一代（如面向 SIMD/新编码的开源尝试 ⚠️ 名词以
  各项目仓库为准），Iceberg 以 format-version 与 write.format 保持文件层可替换性——这正是 5.3 把
  "标准"与"厂商"分开写的红利。
- **核验入口（✅ 2026-09-27 curl 200）**：Parquet/Iceberg 规范关联面见
  https://iceberg.apache.org/spec/ ；对象存储厂商条目核实请回各自官方定价页（书内价目一律不当季）。
- **工程习惯**：把"桶级 S3 API 兼容测试 + 请求费建模（按 manifest 读放大估算）"加入选型 checklist，
  是 2025–2026 多起"自建便宜"翻车案例给出的反向教训 ⚠️（社区复盘文共识，非本书内容）。
