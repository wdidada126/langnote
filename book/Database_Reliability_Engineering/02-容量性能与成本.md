# 第 3 章（⚠️ 章序推定）：管理容量、性能与成本

> 对应原书：Managing Capacity, Performance, and Cost（⚠️ 章题推定）。
> 本章把三件事捆在一起讲——它们本质是同一个资源的三个计价面。

## 本章立场（精读重构）

容量管理不是「买更大的机器」，而是一个闭环流程：
**基线 → 需求预测 → 预算与供给 → 持续度量 → 复盘**。
性能与成本被拉进同一个讨论，是因为云把「性能问题」翻译成了「账单问题」，
从而第一次让容量决策可以财务化、可审计。

### 1. 容量管理的闭环（书中方法论的展开）

1. **基线（Baseline）**：为每个服务记录单位负载的资源画像——每 QPS 多少 ms、
   每 GB 数据多少 IOPS。没有基线，一切扩容都是拍脑袋。
2. **需求（Demand）**：来自业务的季度计划（大促、新功能、数据迁移）+ 自然增长曲线；
   自然增长按「行数/字节数的二阶导」看，索引和临时空间的放大系数单独建模。
3. **供给（Supply）**：云厂商实例/存储类型的档位、保留实例的财务承诺。
   关键约束：数据库的供给弹性远小于无状态服务（垂直扩容要重启、水平加副本要追 BINLOG）。
4. **度量与反馈**：容量水位（磁盘、连接数、缓冲池命中、复制延迟）必须进 SLO 体系；
   超阈值不是告警而是**流程事件**（触发容量评审）。

### 2. 性能是容量的影子

- 章内核心论证（重构）：绝大多数「性能退化」实为「容量越界」——
  工作集超出缓冲池、表大到统计信息失真、连接数打满。
  所以调优顺序应是**先确认容量假设仍成立，再动查询**。
- 索引的成本被显式计价（写入放大、空间、维护），不是免费的加速药：
  🔧 实测（SQLite 3.x + Python 3.13，本机，方法见下）5,000,000 行表：
  `k=999`（命中 5000 行）查询，无索引全表扫描约 **0.30 s**，加 `CREATE INDEX ix ON t(k)`
  并 ANALYZE 后约 **0.026 s**（≈11×）；索引空间代价约 **+54 MB**（表体 164 MB，+~33%）。
  复现：建 5e6 行表 → 计时查询 → 建索引 → 计时 → `DROP INDEX; VACUUM` 后按文件体积差计。
  结论与直觉一致：**加速一个数量级，空间与写放大各付一份**——这正是本章「性能=容量计价面」的最小演示。
- 与 [../千金良方_MySQL性能优化金字塔法则.md](../千金良方_MySQL性能优化金字塔法则.md) 的分工：
  该书是「单查询金字塔」（从硬件到 SQL 的自底向上诊断），本章是「服务级容量闭环」；
  前者教你把一条 SQL 从 0.3s 抠到 26ms，后者教你决定**什么时候该加索引、加完索引账单涨多少**。

### 3. 成本作为一等公民

- 本书是较早把 FinOps 语义写进数据库专著的（2016 年，FinOps 名词尚未流行，⚠️ 口径注：
  「FinOps Foundation 成立于 2021 年」）。
- 反模式清单（重构）：为峰值配置容量（over-provisioning）、开发环境克隆生产全量数据、
  永不回收的快照与备份、按服务平摊云账单导致无人对存储负责。
- 落地建议：给每张核心表/每个实例标注 owner 与月度成本；成本异常增长与故障同流程处理。

## 本章的局限（诚实注记）

- 2016 年语境的容量工具（New Relic/Graphite 时代）已过时；方法论仍成立，
  但「预测」环节在 2020s 被自动扩缩容部分接管（见下节）。
- 章内缺少对 Serverless 数据库（按请求计费）的容量语义讨论——那恰好是 2020s 的新问题。
- 「成本归因到表/到功能」在共享实例与池化架构下越来越难做，本书的 owner 标签制度
  需要与现代 FinOps 的 unit-economics（单位业务量的成本）方法合流才能落地。

## 深究：容量事件的四种形态与评审模板

### 四种形态（把「容量越界」拆成可识别的告警前形态）

| 形态 | 症状链 | 典型引爆点 | 度量先行指标 |
| --- | --- | --- | --- |
| 空间型 | 磁盘/表空间水位 → 写入 EROFS | 大促日志、备份风暴 | 字节增速二阶导 |
| 内存型 | 工作集 > 缓冲池 → 延迟悬崖 | 新查询上线、数据积累越过拐点 | 命中率 + p99 相关性 |
| 连接/线程型 | 连接池耗尽 → 排队雪崩 | 应用扩容未通知数据库 | 每实例连接配额 |
| 吞吐型 | IOPS/复制带宽见顶 → 延迟堆积 | 批量任务撞车业务高峰 | 设备利用率峰值 |

内存型是本章论证「性能退化多为容量越界」的主案例：延迟对缓冲池命中率是**超线性**
劣化的，命中率从 99% 到 95% 的「小事故」足以击穿 p99——所以容量指标必须以
「距悬崖的余量」而非「距上限的余量」来汇报。

🔧 直觉校准（沿用本章实验设定）：同一查询在 5e6 行表上，索引存在与否相差 11 倍；
而「索引在、缓冲池装不下」时差距会再次翻倍到磁盘级——**每一层容量都在决定下一层
的计价单位**，这就是性能预算要与容量预算合并评审的原因。

### 季度容量评审会议议程（重构自本章方法论，可直接抄用）

1. 水位盘点：四形态指标 × 核心实例列表，标注趋势箭头（增速是否超过预算假设）；
2. 预测对账：上季「需求」预测 vs 实际增长，误差归因（业务事件/自然增长/估算错）；
3. 悬崖距离：每个核心实例回答「工作集距内存上限多远」「距空间水位线多远」；
4. 决策单：扩容/归档/加索引/重构读写路径，各带成本估算与回滚方案（→ 05 章变更纪律）；
5. 预算联动：把 3/4 项翻译为下季度账单区间，交财务侧确认。

### 常见问答

- **Q：自动扩缩容时代还要不要做预测？**
  A：要。自动伸缩覆盖分钟-小时尺度；存储增速、许可证档位、保留实例承诺、
  分片再平衡都是**季度尺度**决策，机器替你决定不了。
- **Q：性能预算怎么定数？**
  A：从用户侧 SLO 反推（页面 p75 → API 配额 → 数据库配额），每个环节留整数倍余量；
  数据库环节用「p99 < 配额的 60%」做黄线（重构经验值，⚠️ 非本书原文）。

## 核心概念速览（中英对照）

- **容量管理** — Capacity Management：基线→预测→供给→度量的闭环工程流程。
- **容量基线** — Baseline：单位负载的资源消耗画像，一切预测的地基。
- **水位线** — Headroom/Watermark：距容量上限的安全余量策略。
- **写放大** — Write Amplification：每次写入为索引/日志付出的额外部量。
- **垂直扩容** — Vertical Scaling：换更大实例，通常伴随重启，弹性差。
- **预留实例** — Reserved Instance：以承诺换折扣的财务杠杆，锁死容量决策。
- **过度供给** — Over-provisioning：按峰值配置，云时代最贵的反模式。
- **工作集** — Working Set：热点数据规模，决定缓冲池命中与延迟形态。
- **性能预算** — Performance Budget：为延迟设定的、与容量联动的硬约束。
- **FinOps** — Cloud Financial Operations：成本归属、异常与评审制度化的实践（术语晚于本书）。

## 最新演进与工业实践

> 链接可达性为 2026-09 本会话 `curl` 实测；版本号来自 GitHub releases 页面实抓。

1. **自动扩缩容吃掉了「预测」环节，但没吃掉「基线」**：Aurora Auto Scaling、
   AlloyDB/Aurora Serverless v2 的 ACU 伸缩（⚠️ 云厂商行为，本机不可实测，转述）
   把季节预测任务自动化；但单位负载画像（基线）仍是任何预算评审的前提——本章闭环依然成立。
2. **可观测性栈换血**：Prometheus + Grafana 成为开源默认（✅ https://prometheus.io 可达），
   本书时代的 Nagios/Graphite 叙事退场；连接数、复制延迟、缓冲池命中都以 exporter 指标化。
3. **云数据库的「存储自动增长」语义**：Aurora 存储按 10GB 步进自动扩到 128TiB、
   Snowflake/BigQuery 完全存算分离（⚠️ 转述，不可本机核验）。含义变化：磁盘容量告警
   这一本书核心场景在托管服务上淡出，**IOPS/吞吐上限**与**账单**成为新水位。
4. **FinOps 制度化**：FinOps Foundation（Linux Foundation 旗下）已把本书的散落建议
   整理为框架（Inform→Optimize→Operate）；云厂商的 Cost Anomaly Detection 类产品
   即「成本异常走故障流程」的落地。⚠️ 具体产品名与口径未逐条核验，不展开。
5. **🔧 可自做的容量基线实验**：本目录 02 章的 SQLite 实验脚本即模板——用任意数据集
   测「无索引/有索引 × 数据规模倍增」的延迟曲线，5 分钟得到你机器上的工作集拐点
   （缓冲池≈OS page cache 在 SQLite 里的对应物）。临时脚本按规范放 `D:\develops\tmp\dbwave_dre\`。
