# 第 5 章（⚠️ 章序推定）：让数据保持有界（Keeping Data in Bounds）

> 对应原书：Keeping Data in Bounds（⚠️ 章题推定）。全书最具前瞻性的章节之一：
> 在「数据 = 生产资料」的隐喻下讨论数据的**体积、增长与生命周期治理**。

## 本章立场（精读重构）

**无界的数据增长是所有下游故障的母题**：备份窗口爆掉、迁移时长不可接受、
缓冲池命中崩塌、恢复时间超过 RTO——都能在「没人管数据体积」这条线上找到根因。
DBRE 的职责是把「有界」变成显式设计约束，而不是事后救火。

### 1. 有界的四个维度

1. **单表体积有界**：行数量级预算（亿级是分水岭，⚠️ 经验值非本书原文）；
   超出即触发归档或分区策略。
2. **单行体积有界**：TEXT/BLOB 的滥用是隐形炸弹——它同时污染备份、复制、
   缓冲池与行迁移。大对象外置（对象存储 + 指针列）是标准答案。
3. **热数据集有界**：性能依赖工作集适配内存；「数据总行数」不重要，
   「90 天访问窗口内的量」才重要（🔧 与 02 章 SQLite 实测同一逻辑：成本随扫描范围而非表大小）。
4. **模式（Schema）有界**：字段数量、索引数量、枚举膨胀——模式是接口契约，
   无限加列 = 契约腐烂（与 05 章 expand-contract 相互引用）。

### 2. 生命周期治理工具箱（书中实践的现代转写）

- **TTL/归档**：按业务时钟（订单完结 90 天）而非磁盘告警触发；归档任务本身
  必须幂等、可限速、可回滚——它是一个常驻的数据变更流，纳入 05 章变更纪律。
- **分区/表切分**：RANGE 按月分区让 DROP PARTITION 成为 O(1) 的物理删除，
  对比 DELETE 大表（死元组/回滚段/主从延迟三重代价，见 [../高性能mysql.md](../高性能mysql.md) 的复制与事务章）。
- **冷数据下沉**：数仓/对象存储承接历史查询，生产库只保在线窗口；
  2020s 的形态是湖仓（本系列已单列，见 [../数据库系列·总索引.md](../数据库系列·总索引.md) 数据湖线）。
- **备份体积治理**：备份时长与数据量线性相关——「备份窗口爆掉」是本章主题在
  07 章的投影；解决办法是增量 + 压缩 + 冷数据排除，而非只换更快的磁带（⚠️ 时代注脚）。

### 3. 数据最小化的组织学

- 「谁有权让表变大」：功能评审时要求新表申报量级与保留策略，是本章最激进的制度设计
  （重构表述）——数据体积是**公共负担**，产生者必须付费（保留期限、归档义务）。
- GDPR/合规是同盟而非敌人：数据最小化原则（storage limitation）与有界数据是
  同一工程实践的两种叙事。

## 本章的局限（诚实注记）

- 本书时代「删除数据的合规成本」讨论薄弱；2018 年 GDPR 生效、2021 年中国 PIPL 生效后，
  被遗忘权把「有界」从性能议题升级为法律议题。
- 章内没有讲「时间维度建模」（bitemporal/事件溯源）作为控制复杂度的替代路径。
- 「申报制」在跨时区/高流动团队中的执行成本被低估；2020s 的答案是把申报内嵌进
  migration PR 模板（表创建即要求填 retention 字段），制度只有在成为流水线属性时才存活。

## 深究：有界化的操作模型

### 「先归档还是先分片」判定流程（重构）

1. 量一下访问分布：最近 90 天数据占总读写的百分比（经验上常 >90%，⚠️ 非普适）；
2. 若高占比成立 → 问题不是「库太大」而是「在线窗口太大」：做归档/TTL（成本 O(1) 心智），
   分片被撤销为伪需求；
3. 若访问确实均匀铺在全量上 → 是真规模问题，回到 [03-扩展性与可用性设计.md](03-扩展性与可用性设计.md)
   决策树；
4. 永远先问「这张表为什么存在」：相当比例的容量焦虑由孤儿表贡献（无 owner 没人删）。

### 有界三律（本书思想的公理化转写，⚠️ 代拟）

- **守恒律**：数据不会消失，只会转移；任何「删除」都要写明去处（归档层/合规销毁记录）。
- **计价律**：每一列、每一个索引、每一个 BLOB 都在为备份窗口/复制延迟/缓冲池付费，
  账单以事故形式寄达。
- **契约律**：模式变更是契约变更（→ 05 章），数据保留期是契约条款（本章的制度侧）。

### 常见问答

- **Q：归档会不会把问题推给数仓？**
  A：会——如果数仓也无人治理。归档的终点必须有第二份「有界合同」（冷热各自的保留策略），
  否则只是换了一个更便宜的仓库堆放。
- **Q：分区是不是银弹？**
  A：分区解决「物理删除与时间窗口」的匹配问题，不解决热点分布与行宽问题；
  且分区键一旦选定难以反悔，其决策权重等同分片键（→ 03 章）。
- **Q：如何量化「数据有界」做没做好？**
  A：三个可测指标——表体积增速 vs 业务量增速的比值、恢复演练实测 RTO（→07）、
  孤儿表占比巡检值。三者都应有 owner 与趋势图。

## 核心概念速览（中英对照）

- **有界数据** — Data in Bounds：体积、增长、生命周期全部显式设限的治理约束。
- **工作集** — Hot Set：适配内存的访问窗口内数据，性能的真实对象。
- **数据生命周期管理** — Data Lifecycle Management：按业务时钟驱动的归档/降级/删除流程。
- **TTL** — Time To Live：行级存活期限及其自动化执行。
- **DROP PARTITION** — Partition Drop：用分区交换实现 O(1) 物理删除，替代 DELETE 洪峰。
- **大对象外置** — Blob Offloading：BLOB 进对象存储、行内留指针。
- **数据最小化** — Data Minimization：只采集/保留必要数据，合规与性能同源。
- **保留策略** — Retention Policy：申报制的数据存活合同。
- **归档流水线** — Archival Pipeline：幂等、限速、可回滚的常驻数据变更流。
- **备份窗口** — Backup Window：备份时长与数据量的线性契约。

## 最新演进与工业实践

> 链接可达性 2026-09 实测；不可本机核验的厂商口径标 ⚠️。

1. **合规驱动的「有界」制度化**：GDPR（2018）第 5(1)(e) 存储限制原则 + 中国《个人信息保护法》
   （2021）最短保存期限要求，把本章从性能倡议变成法务 checklist；实践中体现为
   retention job 平台化（⚠️ 具体平台无统一开源标准，未见权威单点链接，不虚构）。
2. **MySQL 8.x 的原生工具演进（⚠️ 转述，dev.mysql.com 对本会话返回 403 无法逐字核验）**：
   在线 DDL 与分区表能力持续补强，但 `DROP PARTITION` 仍是海量删除的最优解；
   PostgreSQL 侧 `TRUNCATE`/分区剥离同构（✅ 官方文档可达：
   https://www.postgresql.org/docs/current/ddl-partitioning.html ，2026-09 实测 200）。
3. **湖仓承接冷数据**：Iceberg/Delta/Hudi 成为「生产库之下」的标准冷层
   （本系列已有专目录：[../Delta_Lake_Definitive_Guide/00-总览与阅读地图.md](../Delta_Lake_Definitive_Guide/00-总览与阅读地图.md)）；
   CDC（Debezium 等 ⚠️）负责把有界化后的归档流可靠地搬运过去。
4. **TTL 的工程化样板**：MySQL 9.x Innovation 线为 InnoDB 引入了 TTL 列与后台自动清理
   （⚠️ 转述：dev.mysql.com 对本会话返回 403，无法逐字核验版本号，使用前请自行对照官方发布说明）；
   PostgreSQL 生态则普遍用 pg_cron/pg_partman 做分区轮转（⚠️ 转述）；
   Vitess（✅ 同上可达）提供 partition management / DROP_PARTITIONS 软删工作流，是本章
   「归档即变更」思想的当代实现。
5. **🔧 实测：物理删除的两条路径各有账单**（SQLite/Python 3.13，本机，2,000,000 行
   107 MB 表，脚本在 `D:\develops\tmp\dbwave_dre\`）：
   - 路径 A：`DELETE FROM t WHERE id BETWEEN 500000 AND 999999`（删 25%）耗时 **0.58 s**，
     但空间不归还，随后 `VACUUM` **3.59 s**（文件 107→80 MB）——VACUUM 是整库重建，
     期间需要双倍磁盘且无法限速/中断续跑；
   - 路径 B：影子重建（新表 INSERT SELECT 保留集 → DROP → RENAME）合计 **5.62 s**，
     略慢于 A+VACUUM 的总和，但复制段**可分批、可限速、可中断重跑**，
     RENAME 切换恒为毫秒级（见 05 章同构实验）。
   - 结论修正直觉：「谁更快」取决于规模与约束——真正的问题是**你能否在删除进行到
     一半时安全走开**，只有 B 可以。分区剥离（`DROP PARTITION`）则是第三条路：
     两秒都不用，且无第二份空间（MySQL/PG 侧行为 ⚠️ 本机无服务未实测）。
