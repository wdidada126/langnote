# 第 4 章（⚠️ 章序推定）：面向可扩展性与可用性设计数据库

> 对应原书：Designing for Scalability and Availability（⚠️ 章题推定）。
> 本章是全书架构浓度最高的一章：复制、分片、SLA 语义、故障域的显式化。

## 本章立场（精读重构）

数据库的可用性与无状态服务不同：**可用性=读写都可用**，而写可用受制于共识/复制协议，
读可用受制于副本滞后。可扩展性也不是单维度：数据量、吞吐、延迟三个方向互相拉扯，
任何「加机器」方案必须先回答动的是哪个方向。

### 1. SLA/SLO 的数据库语义

- 对数据服务要分别定义：**可用性（connection/accepting writes）、持久性（acknowledged
  write 不丢）、新鲜度（读到的多新）、延迟分布**。四者由不同机制保证，也互相牺牲：
  同步复制抬持久性降写延迟；异步复制反之；单点最高写延迟表现但无持久性冗余。
- 错误预算思想（借自 SRE）用于数据库：写不可用预算通常极小（分钟级/月），
  因为它常等价于数据丢失风险。

### 2. 复制拓扑作为可靠性原语

书中讨论谱系（重构为一张决策表；具体产品能力为 ⚠️ 转述）：

| 拓扑 | 写可用性 | 持久性 | 读扩展 | 典型代价 |
| --- | --- | --- | --- | --- |
| 主从异步（MySQL 原生复制） | 低（主死写停） | 弱（可丢尾） | 高 | 故障切换需人工判残 |
| 主从半同步/组复制 | 中 | 中 | 高 | 延迟抬升、拓扑运维复杂 |
| 共识组（Paxos/Raft：TiKV、CockroachDB、MongoDB RS 等） | 高 | 高 | 中 | 法定数宕则全停；跨区延迟 |
| 主主/多活 | 高 | 需冲突策略 | 高 | 冲突解决是把复杂度藏进未来 |
| 云托管（Aurora/Cloud SQL 等） | 高 | 高 | 高 | 黑盒 + 锁定；SLA 转嫁给厂商 |

核心立场：**多活不是圣杯而是债务证券化**——冲突解决、时钟依赖、全局索引一致性
都被推迟到更难的时刻支付。这与 [../分布式系列·总索引.md](../分布式系列·总索引.md)
各章（共识、CAP、TrueTime）结论一致：先诚实地做「读多活、写单点」。

### 3. 分片（Sharding）作为最后的可用性手段

- 分片解决的是**数据量/吞吐的纵向墙**，不解决可用性；且引入三类新故障：
  热点分片、跨分片事务、再平衡风暴。DBRE 视角下每个都是容量与变更事件。
- 书中对「手工分片」的态度：先穷举垂直拆库（按业务域）、读写分离、归档收缩，
  再谈水平分片（→ 与本目录 [04-数据有界与生命周期.md](04-数据有界与生命周期.md) 的呼应：
  很多「需要分片」的系统其实需要的是数据生命周期管理）。
- 分片键设计=多年后的查询模式设计：选错键的代价以「再平衡 + 双写迁移」计价。

### 4. 故障域显式化

- 设计评审必答题：单 AZ 故障、区域故障、脑裂（网络分区下两侧各自选主）、
  「备份可用但恢复要多久」——每个答案写进架构文档，否则 SLA 是形容词。
- 与 06 章的接口：这些命题不是文档题，是**演练题**，写了没演过等于没写。

## 深究：可用性四元语义的度量方法与选型决策树

### 四元语义各自怎么测（不可混报）

| 承诺 | 度量 | 陷阱 |
| --- | --- | --- |
| 写可用 | 故障注入下「接受写」的中位/最坏时长（→ 06 章演练） | 只测「探测到故障」不测「选主+恢复写」全程 |
| 持久性 | 已 ack 写在崩溃/切主后的可回收率 | 用异步副本测同步承诺 |
| 新鲜度 | 复制滞后的 p99（秒）+ 读己之写策略声明 | 应用侧无会话粘性却宣称强一致读 |
| 延迟 | p50/p99/p999 × 分位数随数据体积的曲线（→ 02 章） | 只报均值 |

汇报口径的原则：**任何「99.99%」必须写明是四元里的哪一元**。厂商 SLA 通常只覆盖
「连接可用」，这一事实本身就是本章「故障域显式化」的对象。

### 选型决策树（重构）

```
数据量/吞吐会撞单机墙吗？
├─ 否 → 单主 + 异步/半同步读副本 + PITR（→07）；把复杂度留给备份而非拓扑
└─ 是 → 哪一维撞墙？
    ├─ 读吞吐 → 加只读副本/引入代理路由（Vitess 类，→06 演进节）
    ├─ 写吞吐或体积 → 先垂直拆库与归档（→04），仍不够 → 分片（选键=选未来查询模式）
    └─ 区域级写可用 → 唯一诚实的选项是「多区域单写 + 队列化跨区」或
        共识组内接受跨区 RTT 延迟；「真多活写」仅在能定义冲突收敛语义时成立
```

每个分支的出口都要求回答：故障切换后 N-1 容量撑得住吗（→ 02 章）？
切换本身是变更吗，有回滚路径吗（→ 05 章）？——三章在此闭环。

### 常见问答

- **Q：直接买托管多活（Aurora Global 等）是不是就不用想这些？**
  A：想的东西从「怎么建」变成「缝隙在哪」：SWR 的 RPO 秒级、跨区提升（promotion）
  时长、区域级故障时厂商控制面是否幸存（⚠️ 转述）。四元语义表照样要逐项对账。
- **Q：分片与 NewSQL 怎么选？**
  A：团队自运维能力 > 分片；否则共识内建把再平衡/法定数管理产品化，代价是
  黑盒程度与账单结构变化（⚠️ 经验判断）。本书立场不变：**选让你能诚实回答
  故障域四问的那个**。

## 核心概念速览（中英对照）

- **可用性四元语义** — Availability Semantics：可用/持久/新鲜/延迟四个独立承诺。
- **写可用性预算** — Write Availability Budget：比读预算严苛一个量级的 SLO 拆分。
- **异步复制** — Asynchronous Replication：尾日志可丢的副本模式，故障切换需判残。
- **半同步复制** — Semi-synchronous Replication：至少一副本落盘再 ack，折中方案。
- **共识组复制** — Consensus-based Replication：Raft/Paxos 法定数写，可用性换持久性。
- **脑裂** — Split-brain：分区下双主各自接受写，须有 fencing/仲裁设计。
- **读多活写单点** — Active-passive Multi-region：当代主流妥协架构。
- **分片** — Sharding：按 key 水平切分，解决量墙但制造三类新故障。
- **再平衡** — Rebalancing：分片迁移，本身是高事故率变更。
- **故障域** — Failure Zone：AZ/region/机架边界，设计文档必须显式枚举。
- **垂直拆分** — Functional Decomposition：按业务域拆库，先于水平分片的选项。

## 最新演进与工业实践

> 链接可达性 2026-09 实测；云厂商产品行为不可本机实测，一律「转述 + ⚠️」。

1. **共识内建成为一线默认**：TiDB、CockroachDB、YugabyteDB、MongoDB（Raft 化的副本集）
   把本书当年的「展望」做成了货架商品；MySQL 侧 Group Replication/InnoDB Cluster
   进入 8.x 主流运维语汇（⚠️ 转述）。开源项目主页均 ✅ 可达：
   https://github.com/pingcap/tidb 、https://github.com/cockroachdb/cockroach 。
2. **云厂商把「多活」变成 SKU**：Aurora Global Database、Spanner（TrueTime）、
   AlloyDB cross-region（⚠️ 转述）——本书「多活是债务」的判断被修正为：
   **债务可以被厂商证券化，但利率（延迟/成本/锁定）转嫁给了你**。
3. **Serverless 与自动加读副本**改变了「容量供给」的对话形态（⚠️ 转述）；
   但「写单点 + 读扩展 + 预算显式化」的架构骨架未变。
4. **代理层复兴**：作为本书时代「智能中间件」的继任者，连接池/故障切换代理
   （ProxySQL、PgBouncer、RDS Proxy ⚠️）承担拓扑感知的读写路由；
   Vitess（✅ https://github.com/vitessio/vitess 实测 2026-09 可达）从 YouTube 内部
   分片系统演化为 CNCF 毕业项目，把「手工分片」章节整体产品化。
5. **混沌化的架构评审**：对第 4 章故障域命题的工程化回答演化为「Architectural
   Fitness Functions」与定期区域故障演练（AWS Region 级 drill，⚠️ 转述），
   与 06 章方法合流。
