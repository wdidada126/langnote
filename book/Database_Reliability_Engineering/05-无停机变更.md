# 第 6 章（⚠️ 章序推定）：不宕机地变更（Making Changes without Downtime）

> 对应原书：Making Changes without Downtime（⚠️ 章题推定）。全书工程含金量最高的一章，
> 也是后来「gitops for schema」浪潮的直接先知。

## 本章立场（精读重构）

**变更是故障第一来源**；对数据库而言停机变更不可接受（SLO 分钟级预算），
所以必须把 schema/数据/配置变更改造成**在线的、可回滚的、可分批的工程流程**。
本章给出三类手法：expand-contract、影子表/双写、把 DDL 当代码管。

### 1. Expand–Contract（扩张–收缩）模式

变更被拆成两个安全阶段：

1. **Expand**：只加不减（加可空列、加新表、加索引），新旧结构同时兼容全部在跑版本的代码；
2. **回填（backfill）**：分批把旧数据搬到新结构，限速、可中断、可重跑；
3. **Contract**：等所有代码版本都不再读写旧结构后，才删旧列/旧表/旧索引——
   删除永远是一个**独立的、滞后的**变更。

失败模式（本章反复出现的事故原型）：跳过 contract 的删除步骤直接 `ALTER TABLE DROP COLUMN`，
或直接 `MODIFY COLUMN`——旧版本代码瞬间不兼容，回滚部署也救不回被改掉的列。
**「可回滚」的定义是：任何时刻都存在一个部署回滚路径同时兼容当前数据**——这句话
是本章全部纪律的公理。

### 2. 影子表与双写（在线大表变更的物理层）

- MySQL 原生 Online DDL（`ALGORITHM=INPLACE/INSTANT`）能覆盖一部分场景，但
  copy 表语义的变更（改列类型、重建 PK）在超大表上会长时间持有元数据锁/产生巨量重做——
  详见 [../高性能mysql.md](../高性能mysql.md) 的复制与 DDL 章。
- 工具答案：**pt-online-schema-change**（触发器复制增量）与 **gh-ost**（伪装 BINLOG 拉增量）。
  共同流程：建新表 → 追增量 → 原子改名切换——🔧 本会话用 SQLite 演示了骨架的体积比例：
  2,000,000 行（86 MB）表 `INSERT INTO t_new SELECT * FROM t` 回填耗时 **0.68 s**，
  而最终 `RENAME` 切换 **≈0 ms（原子）**；回填成本随行数线性增长、切换恒定——
  这就是「复制期间业务照常、切换瞬间完成」的原型。复现脚本在 `D:\develops\tmp\dbwave_dre\shadow.db`
  构造过程（本机无 MySQL 服务，工具级行为只能 ⚠️ 转述）。
- gh-ost 比触发器方案的额外红利：可控限流、可暂停、无触发器与外键冲突（⚠️ 转述自其 README）。

### 3. 数据变更（DML）也是变更

本章同样管 UPDATE/DELETE 洪峰：批量拆小（LIMIT 分批 + 睡眠）、WHERE 走索引先行 EXPLAIN、
禁止无 WHERE 的 UPDATE（工具层直接拒绝，见 pt-kill/审核平台）。
2014–2016 年互联网大厂的「SQL 审核平台」（archery/goInception 一脉 ⚠️）是本章流程的组织化产品。

### 4. 把 DDL 当代码管（本章的制度化答案）

- migration 脚本进版本库、随应用发布、评审同 PR；
- **向前兼容的发布编排**：先 migrate 后部署（或双版本并行窗口），流水线保证顺序；
- 环境一致性：dev/staging/prod 用同一份迁移链，staging 全量重放迁移作为 CI。
- 书中这些主张在 2020s 被命名为 **gitops for schema / database devops**（见下节）。

## 本章的局限（诚实注记）

- 章内示例以 MySQL 为主，PG 的 `ADD COLUMN NOT NULL DEFAULT`（11.0 起元数据级）等
  引擎差异未覆盖；读者须按引擎重新核对每条「危险 DDL」清单。
- 「contract 何时可以做」依赖部署版本追踪（哪些旧版本还在跑），本书只提问题未给工具；
  这个洞由今天的 release tracker / schema registry 类实践补。

## 深究：expand-contract 的状态机与危险动作清单

### 一次加列改名的完整状态机（重构）

```
S0 旧结构 + 旧代码
S1 expand：ADD COLUMN c NULL                      （新旧代码同时可跑）
S2 部署代码版本 N+1：双写 (a→c)，读仍走 a           （回滚=退到 S1 代码，安全）
S3 backfill：分批把 a 的历史刷入 c，限速可中断      （任何时刻可停在半程）
S4 部署代码版本 N+2：读写 c，停写 a                 （回滚窗口 = 双写恢复）
S5 观察期满（≥ 一个发布周期 × 旧版本清零）
S6 contract：DROP a                                （独立变更，可回滚 = 重新加回）
```

每箭头是一次部署或一次变更，各自带检查点；**状态机的每个状态都满足回滚兼容性公理**，
这就是「无停机」的形式化含义。gh-ost/pt-osc 只覆盖 S1/S6 的单步执行，
S2–S5 属于应用层，工具替代不了流程。

### 危险动作速查（MySQL 语境，⚠️ 引擎版本相关，执行前查官方 Online DDL 表）

| 动作 | 风险 | 安全替代 |
| --- | --- | --- |
| DROP COLUMN | 旧代码列引用瞬间报错，回滚部署救不回数据 | contract 化：版本清零后独立执行 |
| MODIFY 列类型/长度收缩 | copy 表 + 可能截断数据 | expand：加新列迁移改名 |
| 改主键 | 多数引擎=全表重建 | gh-ost/pt-osc 影子表切换 |
| ADD INDEX 大表 | 长时间资源挤压（8.0 起 INPLACE 缓解） | 低峰执行 + 限流监控（⚠️ 版本口径） |
| 无 WHERE 的 UPDATE/DELETE | 锁放大 + 复制洪峰 + 回滚段爆炸 | 分批 LIMIT + 审核闸口 |
| 变更撞长事务/长查询 | MDL 排队级联，切换瞬间全线卡死 | 执行前查 `information_schema.innodb_trx`，超时保护（⚠️ 转述） |

### 常见问答

- **Q：双写期间两边不一致怎么办？**
  A：默认会不一致——所以 S3/S4 需要校验器（抽样和/计数比对，pt-table-checksum 同构思想），
  并把「差异修复」做进 backfill 的幂等逻辑；无校验器的双写 = 延迟引爆的定时炸弹。
- **Q：小团队做不到这么重的流程？**
  A：最低配是两条铁律：删除永远滞后一个发布周期；DDL 必须先回答「此刻回滚部署，
  新代码遇旧结构/旧代码遇新结构各会发生什么」。流程可以简，公理不能弃。

## 核心概念速览（中英对照）

- **扩张–收缩** — Expand-Contract：只加不减 → 回填 → 滞后删除的三段式变更模式。
- **回填** — Backfill：分批迁移存量数据，要求限速/可中断/幂等。
- **影子表切换** — Shadow Table / Swap：建新表追增量后原子改名。
- **双写** — Dual Write：过渡期新旧结构同写，兼容窗口的实现手段。
- **在线 schema 变更** — Online Schema Change (OSC)：变更期间读写不中断的技术族。
- **元数据锁** — MDL (Metadata Lock)：DDL 与长事务互等的死锁源，切换瞬间的头号风险。
- **INSTANT DDL** — Instant Column Addition：仅改元数据的列添加，MySQL 8.0.12+ 的捷径。
- **迁移即代码** — Migration as Code：DDL 进版本库、过评审、随发布编排。
- **部署回滚兼容性** — Rollback Compatibility：数据必须先于代码兼容两侧，回滚才成立。
- **SQL 审核平台** — SQL Review Platform：把本章纪律固化为准入闸口的组织工具。
