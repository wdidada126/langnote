# 结语章（⚠️ 主题推定）：数据是生产资料——备份、恢复与所有权

> 本文件对应原书中贯穿性最强、章序最不确定的主题（⚠️ 推定分布于第 3/5/7 章与结论）：
> 「数据作为生产资料」的组织论 + 备份恢复的工程论。作为目录的收束章独立成篇。

## 本章立场（精读重构）

全书的隐喻落点：**应用是可弃的消费品，数据是不可再生的生产资料**。
两者混用同一套轻率流程（谁都能 `rm`、谁都能 UPDATE、备份=「应该有了吧」）
是一切重大数据事故的共同根因。本章给出三层答案：

1. **物理层**：备份策略与恢复演练（下述 🔧）；
2. **流程层**：把数据变更纳入与发布同级的变更纪律（→ [05-无停机变更.md](05-无停机变更.md)）；
3. **组织层**：为每份数据指定 owner——生产资料必须有人对它的存续负责。

### 1. 备份策略的四个正交决策

| 决策 | 选项 | 约束来源 |
| --- | --- | --- |
| 什么算一次备份 | 全量/增量/快照/BINLOG-WAL 连续归档 | RPO 与存储成本（→ 02 章） |
| 备份到哪里 | 异机/异区域/异账号/异厂商 | 区域故障与账号级误删/勒索（→ 06 章） |
| 备份可用吗 | 定期恢复演练验证 | 「未经恢复验证的备份不存在」 |
| 恢复到什么点 | PITR（时间点恢复）能力 | 日志连续性与保留窗口 |

- 书中警句（重构为通用表述）：**备份不是目标，恢复才是**；备份任务的 SLI 应当是
  「最近一次成功恢复到目标时间点的实测 RTO/RPO」，而不是「昨晚 job 是否绿色」。

### 2. 🔧「热文件拷贝 ≠ 备份」的最小演示（SQLite，本机实测）

方法（Python 3.13 + sqlite3，脚本产物在 `D:\develops\tmp\dbwave_dre\`，repo 零产物）：
建 WAL 模式库 50,000 行；后台线程持续提交小事务；分别执行
(a) `Connection.backup()` 在线一致性快照；(b) 只复制主库文件（不带 `-wal` 边车）。

结果：
- (a) 备份耗时 0.04 s，**并发写全程未中断**，备份含 50,045 行（吸收了备份窗口内
  已提交的数据），`PRAGMA integrity_check` = ok；
- (b) 裸拷主文件只看到 50,000 行——**已提交的 45 笔事务随缺失的 WAL 一起蒸发**。

结论（可迁移到 MySQL/PG 心智）：一致性快照必须绑定其日志流；任何复制方案若不能
证明「页 + 日志」的原子捕获，就是在制造「看起来绿的、实际上丢数的备份」。
（MySQL 热备需 xtrabackup 锁一致位点、PG 需 `pg_basebackup`+WAL 归档，⚠️ 引擎侧转述：
本机无 MySQL/PG 服务，未实测。）

### 3. 恢复演练的分级

- **月度抽检**：自动恢复一个备份到沙箱，跑校验查询（行数/抽样和/索引完整性）；
- **季度全量**：按真实故障剧本恢复（PITR 到指定秒、单机重建集群），实测 RTO 并公示；
- **年度大演练**：区域级/账号级灾难路径（与 06 章演练清单合流）。
- 每次演练更新 runbook；演练产出的「恢复手册第 7 步已失效」类发现按缺陷管理。

### 4. 数据所有权与「生产资料」的制度含义

- 生产资料需要：保险（备份）、产权（owner 与访问审计）、折旧与处置（生命周期，→ 04 文件）、
  禁止裸奔的操作规程（变更纪律，→ 05 文件）。
- 反模式清单（重构）：共享 root 密码的「团队库」；无 schema owner 的孤儿表；
  用生产主库直接当恢复演练场；备份只存同账号同区域（勒索/账号事故一锅端）。

## 本章的局限（诚实注记）

- 2016 年语境下「备份上云/不可变备份（immutable backup）」尚未成为勒索防护主叙事；
  今天 3-2-1 之上要叠加「至少一份 WORM/隔离副本 + 恢复前的威胁扫描」（⚠️ 现状判断）。
- 组织层论证（所有权）偏倡议、少制度模板；2020s 的数据契约/DataOps 平台部分补上了这块。

## 深究：备份体系自检与误删处置手册

### 备份体系健康度十问（把本章立场变成 checklist，⚠️ 题量为代拟）

1. 最近一次**恢复演练**的日期与实测 RTO/RPO 是多少？（不是备份 job 日期）
2. 备份被删/被加密需要哪几种权限？它们是否在同一个账号域？
3. 恢复一个 10× 当前体积的库，流程还成立吗（体积有界失守时，→ 04 章）？
4. PITR 能精确到哪一秒？日志保留窗口比最大人为发现延迟（error → 察觉）长吗？
5. schema 变更前有强制快照点吗（→ 05 章 contract 步骤的兜底）？
6. 备份里含明文密钥/PII 吗？备份介质的访问面比生产库宽还是窄？
7. 多引擎/多账号/多区域各有一份「灭门隔离」副本吗？
8. 校验和：每次备份产物有完整性指纹并异地留存吗（🔧 对照本章实验 (a) integrity_check）？
9. 谁拥有这份数据？owner 离职时备份知识如何交接（→ 01 章英雄运维批判）？
10. 恢复一个「上周二 14:03」的只读沙箱给业务方自查，能在 30 分钟内做到吗？

### 误删事故的黄金时序（重构）

**冻结（停止该实例所有写入/防止 WAL 被检查点吞掉）→ 判点（从 BINLOG/归档日志定位
误操作 LSN/位点）→ 旁路恢复（恢复到新实例，绝不动生产）→ 回搬（只搬受害表，走
05 章变更纪律）→ 复盘（权限、闸口、为什么没有第二道刹车）**。
其中「冻结」窗口以分钟计——本章实验 (b) 的另一面教训：日志既是恢复的原料，
也会被检查点/回收机制不可逆地消化，反应速度就是数据本身。

### 常见问答

- **Q：厂商 PITR 开着就够了吗？**
  A：不够。PITR 保留期通常短（天级）、不跨账号、且厂商侧故障时你可能连恢复入口都
  够不到——它替代不了十问中的 2/4/7。
- **Q：备份成本压不下来怎么办？**
  A：回到第 04 章：先治体积（冷数据下沉、行宽治理），再谈备份压缩/去重；
  用架构减量的钱永远比用工具挤水分便宜。

## 核心概念速览（中英对照）

- **数据作为生产资料** — Data as a Production Asset：数据不可再生，须按资产级纪律管理。
- **RPO/RTO** — 恢复点/恢复时间目标：分别由日志连续性与演练实测决定的两个承诺。
- **时间点恢复** — PITR (Point-In-Time Recovery)：全量 + 连续日志重放到任意时刻。
- **备份窗口** — Backup Window：全量备份的可接受时长，随数据体积线性恶化。
- **一致性快照** — Consistent Snapshot：页与日志原子配对的时点拷贝（🔧 实验 (a)）。
- **恢复演练** — Restore Drill：以真实剧本验证备份有效性的活动，备份的存在性证明。
- **不可变备份** — Immutable/WORM Backup：到期前任何权限都删不掉的副本，反勒索底线。
- **3-2-1 法则** — 3 copies / 2 media / 1 offsite：经典冗余拓扑，云时代加隔离账号维度。
- **数据所有权** — Data Ownership：每份数据有明确 owner 对存续与质量负责。
- **孤儿表** — Orphaned Table：无 owner 无文档无人敢删的存量负债。

## 最新演进与工业实践

> 链接可达性 2026-09 本会话 `curl` 实测（GitHub 偶发超时项以早先实测为准）；云厂商项标 ⚠️。

1. **云托管把「备份」变成默认项，把「恢复能力」变成新考题**：Aurora/RDS/Cloud SQL/PolarDB
   自带 PITR 与跨区域复制（⚠️ 转述，厂商文档未逐条核验）。角色冲击：DBRE 的日常从
   「建备份管线」转向「审计厂商 SLA 的缝隙」——区域级恢复实测、跨账号副本（防账号灭门）、
   厂商误操作与客户误删除的责任边界（2017 S3 事故、2021 Cloudflare 数据库误删均为客户侧
   自救剧本，⚠️ 事件转述）。
2. **不可变备份与反勒索**：勒索攻击以「先烧备份再勒索」为标准打法，业界共识演进为
   对象存储 Object Lock/WORM + 独立凭证域（⚠️ 转述）。本书「异账号」思想被验证并升级。
3. **数据库 DevOps 的数据面**：数据库分支（branching）把「恢复一份生产规模的副本」
   变成秒级写时复制操作，恢复演练成本下降一个量级。代表：PlanetScale Branching（✅ 站点
   https://planetscale.com/blog 实测 200；注意其 MySQL 兼容层 2024–2025 已转向 Postgres
   优先，⚠️ 转述）； Neon（Serverless Postgres 分支）与 Snowflake Zero-Copy Cloning（⚠️ 转述）。
   「每 PR 一个数据库分支」是 05 章 GitOps 叙事的存储层兑现。
4. **备份即流水线的验证证据**：OpenTelemetry 数据库语义约定（✅
   https://opentelemetry.io/docs/specs/semconv/database/ 实测 200）把「恢复演练期间的查询延迟/
   吞吐」纳入与应用同构的 trace/metric 语义；恢复演练的产出从截图变成可回归的指标集。
5. **DataOps 与数据契约**（本书组织论的 2020s 后裔）：Data Contract / SLO 平台化
   （如 ODSS——Open Data Contract Standard，⚠️ 规范存在但版本口径未在本会话核验）。
   「谁产生数据、谁承诺其存续与质量」从本书倡议变成合同条款。
6. **🔧 延伸实验**：读者可用本节脚本模板在 MySQL/PG 上复刻 (a)/(b) 对照——
   MySQL：`FLUSH TABLES WITH READ LOCK` 前后 cp vs xtrabackup；PG：`cp` base 目录 vs
   `pg_basebackup`。预期结论同构：不带日志流的热拷贝不是备份（⚠️ 本机无服务，未代跑）。
