# 第 7 章（⚠️ 章序推定）：拥抱失败以维持可靠性（Embracing Failure）

> 对应原书：Embracing Failure to Maintain Reliability（⚠️ 章题推定）。
> 混沌思想进入数据库语境的最早专著章节之一，与 07 文件（备份恢复）构成
> 「主动找故障 ↔ 被动兜故障」的镜像。

## 本章立场（精读重构）

可靠性无法靠「避免失败」达成：故障一定会来，差别只在它是**实验**还是**事故**。
本章要求把三件事制度化：

1. **面向失败设计**（design for failure）：假设任意节点任意时刻可死，架构与运维流程
   必须在此假设下仍然收敛；
2. **主动注入故障**：在可控范围、可控时间、可控爆炸半径里制造故障，观察并修复；
3. **从失败学习**：事故复盘产出的是「系统约束的再认识」与「自动化待办」，
   不是责任认定（与 [01-导论与DBRE运动.md](01-导论与DBRE运动.md) 的无责复盘呼应）。

### 1. 数据库为什么更难「拥抱失败」

- 无状态服务的混沌（杀实例）在数据库上会触碰**数据一致性**：被杀的节点可能带着
  未同步的尾日志；恢复要处理崩溃点重放。所以数据库故障注入必须前置两件事：
  可验证的一致性探针（注入前/后的校验读）与恢复路径的自动化（无人工判残）。
- 爆炸半径控制更保守：从单副本 → 单分片 → 单 AZ 逐级；**主库故障与全量数据损坏
  是两个世界**，后者永远不碰生产（用备份恢复演练替代，见 07 文件）。

### 2. 演练清单（本章实践的现代转写）

| 演练 | 验证什么 | 频率 |
| --- | --- | --- |
| 杀一个只读副本 | 读路由自动摘除、容量水位重算 | 高（可自动化） |
| 主库故障切换 | 选主正确性、写中断时长 vs SLO | 季度 |
| 区域故障模拟（网络分区/断网） | 法定数行为、脑裂 fencing | 半年 ⚠️ 需专用工具 |
| 慢盘/IO 抖动注入 | 复制延迟、超时与重试风暴 | 季度 |
| 备份恢复演练 | RTO/RPO 实际值 | 见 07 文件（月度抽检+季度全量） |
| 认证/证书到期 | 续期流水线 | 自动巡检 |

关键立场：**任何没在演练中验证过的恢复路径，SLA 里不许承诺**。

### 3. 与容量、变更两章的三角关系

- 故障切换后的集群只剩 N-1 容量：演练必须回答「切走一半后还撑得住吗」→ 容量章的
  headroom 由演练定义，而非由表格猜测（→ [02-容量性能与成本.md](02-容量性能与成本.md)）；
- 大部分生产事故由变更触发：混沌注入应覆盖「变更中途失败」路径（DDL 做到一半、
  回填中断、切换失败回退），与 [05-无停机变更.md](05-无停机变更.md) 的工具链合流。

### 4. 事故复盘的工程学（章尾主题）

- 时间线（检测→缓解→恢复→消退）逐段度量，MTTD/MTTR 是流程 KPI；
- 行动项的归宿是 runbook 与自动化，而非培训与口号；
- 「数据库被误删」级别的复盘要回答体系问题：为什么权限、为什么没有第二道刹车
  （与 07 文件「数据作为生产资料」的所有权论证衔接）。

## 本章的局限（诚实注记）

- 2016 年混沌工具生态刚起步（Netflix SIMI 时代），章内多为原则论述，
  工具落地要等 2018+（见下节）；
- 「区域级演练」在多云/合规受限环境中的可行性被低估，今天多数团队止步于
  合成监控 + 表更故障注入（⚠️ 现状判断，非实测）。

## 深究：数据库混沌实验的设计模板

### 一次实验的六件套（重构为可直接抄的模板）

1. **假设**：「杀掉任一从库，读路由在 T 秒内收敛，错误率 < x%」——没有数值假设
   就不是实验，是玩；
2. **稳态度量**：实验前 30 分钟的 SLI 基线（错误率/延迟/复制滞后）；
3. **终止条件**：谁有权喊停、喊停后如何回退（与 [05-无停机变更.md](05-无停机变更.md)
   的回滚公理同源）；
4. **爆炸半径声明**：实例列表、时段、业务影响预告（对内公告是纪律的一部分）；
5. **注入**：kill -9 / iptables 丢包 / tc 延迟 / dm-error 慢盘 / 证书吊销；
6. **读数与行动项**：假设被证伪的部分就是 backlog；被证实的部分写进 runbook。

### 数据库特有注入矩阵（重构）

| 注入 | 想暴露的问题 | 高危副作用与对策 |
| --- | --- | --- |
| 从库宕机 | 路由收敛、N-1 容量（→02） | 低；从生产流量 1% 影子起步 |
| 主库宕机 | 选主正确性、写中断、半同步尾日志 | 中；必须在有演练环境或业务低谷+回切预案下 |
| 网络分区（主↔从） | fencing、脑裂、仲裁 | 高；恢复后跑一致性校验（pt-table-checksum 类） |
| 慢盘/IO 抖动 | fsync 放大、复制堆积、超时重试风暴 | 中；先副本后主库 |
| 连接风暴（应用侧重启） | 连接池、惊群、认证开销 | 低；常见且良性 |
| 备份恢复本身 | RTO 实测（→07） | 低；恢复的是沙箱 |

纪律：**任何注入不碰「不可恢复」路径**——数据删除类灾难永远只在演练/恢复侧模拟，
这是对「生产资料」的边界敬畏（→ 07 文件）。

### 常见问答

- **Q：老板不批演练怎么办？**
  A：把提案改写成它的对偶：「不演练」= 承诺「故障切换时长与数据完整性靠运气」。
  本章话术的全部力量在于：故障不由你选择是否发生，只由你选择是否**在观测下**发生。
- **Q：托管数据库上还能混沌吗？**
  A：能，且更有必要：注入点上移（API 限流、控制台删参数组、区域故障托管演练 ⚠️ 厂商能力
  不一），对象从进程变成「厂商控制面行为是否符合你的 SLA 假设」。

## 核心概念速览（中英对照）

- **混沌工程** — Chaos Engineering：以可控实验证伪「系统对故障的假设」的学科。
- **爆炸半径** — Blast Radius：实验允许影响的边界，数据库场景须逐副本放大。
- **稳态假设** — Steady State Hypothesis：实验前定义的可测量「正常」。
- **故障注入** — Fault Injection：杀进程/断网/慢盘/错证书等具体手段。
- **判残** — Split-brain Triage：主库故障后确认数据完整性的动作，演练目标是消灭它。
- **无责复盘** — Blameless Postmortem：产出系统约束认识而非追责的流程。
- **MTTD/MTTR** — 平均检测/恢复时间：时间线驱动的流程度量。
- **N-1 容量** — N-1 Resilience：任一单元失效后剩余容量仍可服务的约束。
- **恢复演练** — Game Day / Recovery Drill：以演练验证 SLA 承诺的活动。
- **fencing** — STONITH/隔离：阻止故障节点继续提供服务的机制。
- **runbook** — Runbook：可执行、被演练验证过的运维程序文档。

## 最新演进与工业实践

> 版本/可达性 2026-09 本会话实测；「现状判断」类标注除外。

1. **混沌工具箱成熟为 CNCF 谱系**：**Chaos Mesh v2.8.4**（✅ 版本实抓，
   https://github.com/chaos-mesh/chaos-mesh ）覆盖 K8s 上的 pod-kill/网络延迟/IO 故障/时钟偏移，
   是今天数据库跑在 K8s 上（TiDB/Patroni 集群等）时的标准注入器；
   **Litmus**（✅ https://litmuschaos.io 实测 200）与 **ChaosBlade**
   （✅ https://chaosblade.io 实测 200）同赛道。Netflix ChaosMonkey（✅ 仓库可达）
   已是历史符号，其原理文档（simian-army 一脉）不再活跃维护。
2. **理论载体制度化**：principlesofchaos.org（✅ 实测 200，2026-09）把本书与 Netflix/SRE
   社区的散落实践固化为五条公理（稳态、多变现实、生产实验、最小爆炸半径、自动化持续做）；
   O'Reilly 随后出版《Chaos Engineering》（Basiri et al., 2017）成为正式专著——
   本书是它重要的先行注脚。
3. **云厂商托管混沌**：AWS Fault Injection Simulator（✅ https://aws.amazon.com/fis/ 实测 200）
   与 re:Invent 的 "GameDays" 产品化；「区域故障演练」从禁忌变成有 SOP 的服务
   （⚠️ 转述：各厂商能力边界未逐条核验）。
4. **数据库专属探针**：一致性校验类工具（pt-table-checksum 一脉，✅ Percona Toolkit v3.7.1
   版本实抓）承担「故障切换后数据完整吗」的自动化回答——把本书「判残」变成可 cron 的脚本。
5. **可观测性补全因果链**（与 OTel 合流，详见 [07-数据作为生产资料与备份恢复.md](07-数据作为生产资料与备份恢复.md)
   的演进节）：OpenTelemetry 已把数据库语义约定独立成页且状态为 Mixed（部分 Stable、
   部分 Development，✅ https://opentelemetry.io/docs/specs/semconv/database/ 实测 2026-09
   返回 200；规范仓库 https://github.com/open-telemetry/semantic-conventions 亦可达），
   数据库客户端/连接池/慢查询遥测的属性口径逐步标准化，使「注入 → 指标畸变 → 追踪定位」
   闭环跨厂商可比——这是 2016 年做不到的实验观测条件。
