# 06 组合模式与装饰器模式（对应原书第 8–9 章）

> 对应原书第二部分（结构型）第 8 章「组合模式」、第 9 章「装饰器模式」（推定英文章题 Composite / Decorator ⚠️）。
> 合并理由：两者都构造「递归/包裹」的对象图，GoF 原图里 Decorator 甚至包裹 Component——
> 而在 C++20 中，这对组合被 ranges view 管道**整体吸收**成了标准库设施，对照讲收益最大。

## 核心概念速览（中英对照）

- **组合** — Composite：树叶与树枝实现同一接口，客户端无需区分单对象与对象集合。
- **树叶/树枝** — leaf / composite：组合模式的两类节点；树枝持有子节点集合并递归转发。
- **透明性 vs 类型安全** — transparency vs type safety：把 `add/remove` 放基类（透明但树叶上荒谬）还是放树枝（安全但客户端要 RTTI/转型）——GoF 承认的两难。
- **表达式树** — expression tree：组合模式最干净的落地——`x + y*sin(z)` 的节点即树枝/树叶。
- **装饰器** — Decorator：保持接口不变地逐层包裹对象，叠加职责（缓存/日志/压缩/转码）。
- **具体装饰** — concrete decorator：每层一种职责，`Component{ std::make_unique<InnerDeco>(...) }` 洋葱构造。
- **视图/管道** — view / pipeline：C++20 的装饰器标准化形态——`v | views::filter(p) | views::transform(f)`。
- **惰性求值** — lazy evaluation：view 不预取、逐元素按需计算，是 ranges 版装饰器的默认语义。
- **view_interface** — `std::ranges::view_interface`：自定义 view 的 CRTP 基类，补 `empty()/size()` 等便利件。
- **外饰/透明转发** — transparent forwarding：装饰层对未覆盖的调用原样转发给被装饰者。
- **装饰栈深度** — decorator stack depth：层数过多时编译期/调试成本上升——ranges 管道同样适用该警告。
- **循环组合** — recursive traversal：组合的遍历（迭代/访问/求值）与装饰的「环绕」是同构的双分派链。

## 动机：一棵树与一件件外衣

- **Composite**：客户端要统一处理「一个」和「一批」——文件系统（文件/目录）、UI（控件/容器）、
  表达式（原子/运算节点）。没有 Composite 时满屏 `if (is_dir)`。
- **Decorator**：继承做可选职责是组合爆炸（加密×压缩×缓冲×日志 = 2⁴ 个派生类）；
  把每种职责做成可拆卸的包装层，运行期按需装配。

## 机制

### 组合：variant 树与透明两难

🔧（教学示意；递归求值的 variant 树骨架与第 14 章已实测的 `overloaded{}` 同型）

```cpp
struct Num; struct Add; struct Mul;
using Expr = std::variant<double, std::unique_ptr<Add>, std::unique_ptr<Mul>>; // 树叶=double
// 树枝: struct Add { Expr lhs, rhs; };
double eval(const Expr& e) {
    return std::visit(overloaded{
        [](double d)            { return d; },
        [](const Add& a)        { return eval(a.lhs) + eval(a.rhs); },
        [](const Mul& m)        { return eval(m.lhs) * eval(m.rhs); }
    }, e);
}
```

- **运行期多态树**（GoF 原型）：`vector<unique_ptr<Component>> children` 放树枝；树叶对 `add()` 只留 `throw`。
- **C++ 的替代**：值语义让「子节点集合」变成 `std::vector<Component>`（若 Component 可值化），
  或用 `variant` 把树的形状在编译期定死（上例）——遍历与求值随之变成 `visit`。
- 组合的**遍历职责**常被拆出：结构（Composite）归模型，操作（eval/pretty-print）归 Visitor（见 [14-模板方法与访问者.md](14-模板方法与访问者.md)）——这两个模式是经典搭档。

### 装饰器：ranges view 就是标准库的 Decorator 家族

🔧（已实测 g++ 15.2；自定义 view 叠加于 `transform` 之上）

```cpp
inline constexpr auto twice = [](int x) { return x * 2; };

template <std::ranges::view V>
class DoubledView : public std::ranges::view_interface<DoubledView<V>> {
    std::ranges::transform_view<V, decltype(twice)> tv_;
public:
    DoubledView() = default;
    DoubledView(V v) : tv_(v, twice) {}
    auto begin() { return tv_.begin(); }
    auto end()   { return tv_.end(); }
};
template <std::ranges::range R>
DoubledView(R&) -> DoubledView<std::ranges::ref_view<std::remove_cvref_t<R>>>;
// for (int x : DoubledView(data)) ...  // 2 4 6 8 10 12
```

谱系对照（继承式 vs 管道式装饰器）：

| 维度 | GoF 继承式 Decorator | ranges 管道式 |
| --- | --- | --- |
| 接口 | 抽象 Component 的虚接口 | `range`/`view` 概念（迭代协议） |
| 叠加方式 | 运行期 new 洋葱 | `|` 编译期组合类型 |
| 开销 | 虚调用+堆 | 零开销（inline 迭代器） |
| 适用 | I/O 流、GUI 边框、运行时可配的加料 | 序列变换、过滤、投影 |
| 失败模式 | 忘记转发某方法 | 管道过长难编译/难调试；view 持有悬垂 range |

**反模式/何时不用**：

- **Composite 滥用于非树领域**：网状关系（依赖图、社交图）强行套树需要「虚拟树叶」补丁——那是图的算法问题不是组合问题。
- **装饰器与代理混写**：同一壳类里既加功能又做访问控制——拆两层，否则测试时无法只 mock 其一。
- **view 管道存悬垂**：view 是非拥有视图（`ref_view`），把 `data | views::take(3)` 存下来而 `data` 先亡=UB；
  长期持有请 `views::common`/物化拷贝。
- **透明性极端化**：给树叶的 `add()` 返回 `false` 不抛错——静默吞调用比抛错更难查；宁可用类型安全方案（客户端只对树枝暴露容器操作）。

## 权衡与相邻概念对比

| 模式对 | 共享 | 分歧 |
| --- | --- | --- |
| Composite vs Decorator | 都持 `unique_ptr<Component>`、都同接口 | Composite 的指针域是**复数**（子集合）且被管理；Decorator 的指针域是**单数**且仅转发 |
| Composite vs Iterator | 树遍历靠迭代器 | 迭代器是「怎么访问」（行为型），组合是「什么形状」（结构型）（见 [10-解释器与迭代器.md](10-解释器与迭代器.md)） |
| Decorator vs Adapter | 都包一层 | 装饰不改接口只加行为；适配必须改接口（见 [05-适配器与桥接.md](05-适配器与桥接.md)） |
| Decorator vs Chain of Responsibility | 环绕式叠加 | CoR 每环**可截断**传播；装饰器环必须全部执行（见 [09-职责链与命令.md](09-职责链与命令.md)） |

## 最新演进与工业实践

- **经典文献**：GoF 1994 之 Composite / Decorator 条（书目见 [../设计模式GoF/03-结构型模式.md](../设计模式GoF/03-结构型模式.md)）。
- **C++20/23**：`views::join/transform/filter/take/drop/reverse/elements`（C++20）+
  `zip/enumerate/chunk/cycles`（C++23）——标准库装饰器的品类每年在增加；
  C++20 `std::generator`/C++23 `std::generator`（GCC 15.2 实测 `-std=gnu++2b` ✅）
  让「惰性无限源」也能进管道，补齐装饰器栈的上游。
- **工业体现**：
  - **Boost.Iostreams**：`filtering_stream`——继承式装饰器在 C++ 标准库缺位时代的最后堡垒（压缩/加密/换行转换器插件）。
  - **range-v3**：Eric Niebler 的原型库，ranges TS→C++20 的输入端；其 `view::for_each/adaptor` 设计即「泛型装饰器构造器」。
  - **rocksdb**：`BlockBasedTable` 的 cache/compression 层、`DBImpl` 之上的 `FileDB/WriteController` 包裹链——存储引擎里的装饰栈。
  - **Eigen**：表达式模板把 `a + b * c` 组成编译期 Composite（expression tree），`eval` 即访问者——「Composite+Visitor 零虚函数」的工业样板。
- **2026 判断**：序列域里手写 Decorator 已基本出局（ranges 完胜）；
  I/O 流与 GUI 控件树仍是继承式装饰器/组合的残存领地，且后者正被即时模式 GUI（Dear ImGui）的「扁平数据+遍历顺序」消解。
