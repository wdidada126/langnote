# 13 状态模式与策略模式（对应原书第 21–22 章）

> 对应原书第三部分（行为型）第 21 章「状态模式」、第 22 章「策略模式」（推定英文章题 State / Strategy ⚠️）。
> 合并理由：GoF 原文承认两者源码级同构（都持一个可替换的指针域），分歧全在**语义**：
> State 的替换由**状态机自己**驱动（客户端不该关心当前是哪个状态），Strategy 的替换由**客户端**驱动（选算法）。
> 放在一起讲是本书谱系对比最密集的一对。

## 核心概念速览（中英对照）

- **状态模式** — State：对象行为随内部状态改变而改变——把每个状态做成一个类，转移时换实例。
- **转移表** — transition table：`map<State, map<Event, State>>`——FSM 的表驱动实现，状态退化为纯数据。
- **状态机** — FSM：状态集合 + 事件集合 + 转移函数 + 初始态；State 模式是其面向对象表达。
- **层次状态机** — HSM / statechart：状态可嵌套（State 模式的 Composite 延伸）；Qt 有 QStateMachine 家族（⚠️ 模块名以文档为准）。
- **策略** — Strategy：一族算法互相封装、可互换，客户端选择并持有。
- **策略接口** — Strategy interface：抽象基类或 concept——「可互换」的契约。
- **运行期策略 vs 编译期策略** — runtime policy vs policy-based：`unique_ptr<Strategy>` vs 模板参数（policy-based class，Boost.ORMM 时代术语）。
- **函数型策略** — functional strategy：`std::function`/函数指针/lambda 直接当策略——Observer 之外的第二用途。
- **投影** — projection（ranges）：算法侧接受「可调用」做键提取——标准库把 Strategy 参数化的官方姿势。
- **比较器** — Comparator：策略模式的最大规模标准化案例（`std::sort` 与 `std::ranges::sort` 的第四参数）。
- **回调/钩子对照** — callback vs strategy：回调=把「一段」行为注入框架；策略=把「一族」行为注入宿主。
- **状态泄漏** — leaked state：客户端被迫 `if (machine.state == Running)`——State 模式被做失败的标志。

## 动机：两团 if

- **State**：订单有草稿/已付/已发货/已退；每个方法开头一坨 `switch (state)`，新状态要改**所有**方法。
  State 模式把「行为按状态分组」从方法×状态二维矩阵折成一维类列表。
- **Strategy**：压缩有 gzip/zstd/无，排序有快排/计数，定价有普通/会员/促销。
  if 分支在**每个调用点重复且成对出现**（选分支与做分支），策略把「选择」集中到装配点一次。

## 机制

### 状态：虚基类、variant、转移表三档

🔧（已实测 g++ 15.2 的 variant 版，见 t3）：

```cpp
struct Idle {}; struct Running {}; struct Stopped {};
using MachineState = std::variant<Idle, Running, Stopped>;

void on_signal(MachineState& st, char key) {
    std::visit(overloaded{
        [&](Idle&)    { if (key == 's') st = Running{}; },
        [&](Running&) { if (key == 'p') st = Stopped{}; },
        [&](Stopped&) { if (key == 'r') st = Idle{}; }
    }, st);
}
```

三档谱系：

| 档 | 形态 | 适用 | 代价 |
| --- | --- | --- | --- |
| GoF 虚基类 | `State* current_`，每状态一类 | 状态多、行为重、需运行时新增状态类 | 堆+虚调用+状态类间互引 |
| `variant` 状态机 | 状态=类型分支，事件=visit | 状态集封闭、转移规则内聚 | 加新状态=改 variant（开放轴翻转） |
| 转移表 | `map<pair<State,Event>, State>` | 表可读可配（游戏 AI、协议） | 动作要外挂（表只算去向） |

- 协程版异步状态机：一个 `task<void>` 把「等待事件→推进状态」写成线性代码，状态藏在局部变量里——
  State 模式的第三次形态化（见第 12 章 generator 对偶）。

### 策略：从虚函数到 concept

🔧（教学示意）三档：

```cpp
// 1) 运行期：函数指针/std::function（零继承）
double apply(double a, double b, std::function<double(double,double)> op);

// 2) 编译期：模板参数 + concepts 约束（C++20 正解）
template <typename Op>
concept BinOp = std::invocable<Op, double, double>;
template <BinOp Op>
double apply2(double a, double b, Op op) { return op(a, b); }

// 3) 策略类（含状态/配置的算法族）
template <typename Distribution>  // policy-based：随机数发生策略
class Simulator {
    Distribution dist_;
public:
    auto step() { return dist_(rng_); }
};
```

- **标准库已把策略做成默认参数**：算法谓词、比较器、分配器、格式化 specs、ranges 投影——
  Strategy 是 C++ 里唯一「语言级泛滥」的模式。

**反模式/何时不用**：

- **只有两个状态却上 State 类族**：一个 `enum + bool` 足够；State 的起点是「行为随状态变化**且**状态会增长」。
- **状态类互相 new 下一个状态**：转移逻辑散进各状态（GoF 允许，但要防环）；集中转移表更可控。
- **策略接口只有一个方法还要抽象类**：用 `std::function`/模板参数；抽象类策略适用于「多方法算法族」（如编解码协议）。
- **策略热换与状态混淆**：客户端频繁 `set_compression(...)`=策略；对象自己 `enter_next_state()`=状态——评审时看谁发起替换。

## 权衡与相邻概念对比

| 维度 | State | Strategy | Template Method | Bridge |
| --- | --- | --- | --- | --- |
| 替换由谁发起 | 对象自身（状态转移） | 客户端/配置 | 不变（骨架固定） | 装配期选型 |
| 替换时机语义 | 「我变成了另一种东西」 | 「我换了一种做法」 | 「我从来只做同一流程」 | 「我底层换了平台」 |
| 指针域数量 | 1（当前状态） | 1（当前算法） | 0（继承换步骤） | 1（实现底座） |
| 类图形态 | **与 Strategy 源码级同构**，语义相反 | 同左 | 方法级复用 | 两棵树 |
| C++20 最优解 | variant/转移表/协程 | concepts+lambda | CRTP | 抽象基类+unique_ptr |

（GoF 名言「State 是 Strategy 的特例」只讲结构；语义上二者**正交**——这是本文件要带走的结论。）

## 最新演进与工业实践

- **经典文献**：GoF 1994 之 State / Strategy 条（书目见 [../设计模式GoF/05-策略、状态、模板方法与访客.md](../设计模式GoF/05-策略、状态、模板方法与访客.md)）。
- **C++20→26**：concepts 让编译期策略的报错从「模板深处」变成「约束不满足」一行话；
  C++23 `std::expected` 让策略返回错误不抛异常；
  C++26 senders/receivers 把「异步状态机」标准化（`std::execution` 的接收端即转移表+动作）。
- **工业体现**：
  - **rocksdb/leveldb**：`Comparator`、`MergeOperator`、`FilterPolicy`、`Env`——LSM 引擎的四大策略插槽（读 [../Database_Internals/](../Database_Internals/00-总览与阅读地图.md) 诸章看它们如何决定引擎性格）。
  - **fmtlib/fmt**：格式 specs=运行期策略（`format_to` 的填充/精度参数），`formatter<T>` 特化=编译期策略——一库双轨。
  - **EnTT/skia**：游戏与图形管线把状态机做成数据资产（设计师可编辑的转移表），State 模式从类图移进 JSON。
  - **OpenSSL/protobuf**：算法族可插拔（provider 机制）即策略模式的标准化商业形态。
- **2026 判断**：策略已「物」化——工程师不再讨论「要不要用策略」，而是讨论「策略插槽开在哪、运行期可不可换」；
  状态机则走向「图表即数据」（xState/Statecharts UI），State 模式的类图教学价值大于新建项目直接抄写价值。
