# 09 职责链模式与命令模式（对应原书第 13–14 章）

> 对应原书第三部分（行为型）第 13 章「职责链模式」、第 14 章「命令模式」（推定英文章题 Chain of Responsibility / Command ⚠️）。
> 合并理由：两模式都处理「请求的表示与传递」；CoR 决定请求**沿谁的手**传播，
> Command 决定请求**以什么形态**被存储、排队、回放——一横一纵。

## 核心概念速览（中英对照）

- **职责链** — Chain of Responsibility：请求沿候选处理者链传递，直到某环处理或链尽。
- **纯链/杂链** — pure/impure chain：每环要么处理要么转发（纯）；每环做一部分、余量下传（杂，如复合滤镜）。
- **环绕式链** — around/before-after chain：每环处理前后都拿到控制权——现代中间件（filter/middleware）形态。
- **短路** — short-circuit：某环处理后不再下传；CoR 与装饰器的关键行为差异（后者必须全链执行）。
- **命令** — Command：把「请求」对象化——持有接收者与参数，可延迟执行、排队、日志、撤销。
- **撤销/重做** — undo/redo：命令模式最大红利：`execute()` 逆操作或状态快照回放。
- **宏命令** — macro command：命令组合（Composite 的应用），一次执行一串。
- **命令队列** — command queue/processor：生产者线程投递、消费线程串行执行——GUI/游戏主循环线程安全的核心手法。
- **事务性记录** — write-ahead journaling：命令对象落日志即「请求的可重放表示」——数据库 WAL 与 Command 同构。
- **接收者** — Receiver：命令真正操作的目标对象；命令把「调用者—接收者」的直连拆成两段。
- **Invoker** — 调用者：持有并择机执行命令的一方（菜单项、快捷键绑定、任务调度器都属于它）。
- **观察者通知** — notification：命令与观察者的分界——命令是**一对一**可撤销的请求；观察者是**一对多**不可撤销的通知。

## 动机：请求不该焊在调用点上

- **CoR**：GUI 事件冒泡、异常处理栈、审批流——问题在「谁负责」无法在发送时确定，
  发送方若硬编码候选顺序就违反 OCP（新处理者=改发送方）。
- **Command**：菜单项/快捷键/网络包/测试用例都想「触发同一个动作」；撤销栈与重放日志
  需要动作变成**可存储的值**。把方法调用升格为对象，一切就顺了。

## 机制

### 职责链：从虚函数链到可组合闭包

🔧（教学示意；链式结构为 t2 管道同型）朴素链 + 现代环绕式链：

```cpp
// 朴素：每环持下一环
struct Handler {
    std::function<std::optional<std::string>(const std::string&)> next;
    virtual ~Handler() = default;
    virtual std::optional<std::string> handle(const std::string& req) = 0;
};
// 环绕式（C++20 惯用法）：链 = 函数复合
using Step = std::function<std::string(std::string, std::function<std::string(std::string)>)>;
std::function<std::string(std::string)> chain(std::vector<Step> steps) {
    std::function<std::string(std::string)> h = [](std::string s){ return s; };
    for (auto it = steps.rbegin(); it != steps.rend(); ++it) {
        auto step = *it; auto prev = h;
        h = [step, prev](std::string s){ return step(std::move(s), prev); };
    }
    return h;
}
```

- 环绕式链即 **middleware/interceptor**：gRPC C++ 的 ServerInterceptor 就是「每环处理前后 + 可截断」。
- 链的数据结构可换成 ranges 管道（`views::filter` 本质是布尔短路链）。

### 命令：`std::function` 时代的最小形态

🔧（教学示意）

```cpp
struct Command {
    virtual ~Command() = default;
    virtual void execute() = 0;
    virtual void undo() = 0;
};
class TurnDeposit : public Command {
    Account& acc_; double amt_;
public:
    TurnDeposit(Account& a, double amt) : acc_(a), amt_(amt) {}
    void execute() override { acc_.balance += amt_; }
    void undo()      override { acc_.balance -= amt_; }   // 逆操作
};
// 命令队列：主线程投递，工作线程串行消费
std::deque<std::unique_ptr<Command>> queue;   // mutex 保护略
```

- **参数化即命令**：GUI 里「菜单项 = {图标, 标签, command}」，一个 command 对象可被菜单/快捷键/脚本同时引用——
  这就是 GoF「命令把调用者与接收者解耦」的落地。
- **撤销策略二选一**：逆操作（`undo` 手写，要求操作可逆）或状态快照（备忘录回放，见 [11-中介者与备忘录.md](11-中介者与备忘录.md)）；
  浮点累加类操作不可逆——快照更稳。

**反模式/何时不用**：

- **CoR 隐藏控制流**：调试时请求「消失在链里」——每环必须有「未处理原因」日志，链长设上限。
- **命令对象里塞 if 分支选择接收者**：解耦又回来了；保持「命令=对**一个**接收者的**一个**动作」。
- **无撤销需求却上重型命令**：只是回调的话 `std::function`/协程投递即可；GoF 的完整命令家族（宏、队列、事务）按需取。
- **用命令模拟策略**：命令对象若不含「被存储/排队/撤销」的生命周期，它就退化成了策略/函数指针。

## 权衡与相邻概念对比

| 维度 | Chain of Responsibility | Command | Mediator | Observer |
| --- | --- | --- | --- | --- |
| 请求去向 | 串行多候选 | 单一接收者，可延迟 | 中心转发给指定者 | 广播给全体订阅者 |
| 发送方知道谁处理 | 不知道 | 知道（封装时已知） | 不知道（只通知中介） | 不知道 |
| 可存储/重放 | 链可存但请求一次性 | **是**（核心卖点） | — | — |
| 可撤销 | — | **是** | — | 否（通知即消费） |
| C++20 对应物 | ranges 管道/拦截器 | `std::function`+lambda/协程任务 | 信号总线/EnTT | signals/slots |

## 最新演进与工业实践

- **经典文献**：GoF 1994 之 Chain of Responsibility / Command 条（书目见 [../设计模式GoF/04-行为型模式.md](../设计模式GoF/04-行为型模式.md)）。
- **C++20→26**：协程任务（`task<T>`/sender-receiver）让「命令=可排队的一次异步调用」有标准协议可依赖；
  C++26 静态反射（P2996）对**命令序列化**（网络/日志重放）是釜底抽薪——字段级元信息自动生成，不再手写 `to_json/from_json` 样板。
- **工业体现**：
  - **gRPC C++**：`ServerInterceptor` 链=CoR 工业定型；每环 `Intercept(RecvOp, SendOp)` 环绕式。
  - **muduo/netcode 类游戏服务器**：消息处理器注册表（按消息 id 查 `function`）=枚举式链；`EventLoopThread` 投递队列=命令队列。
  - **Qt**：`QUndoStack`/`QUndoCommand`——命令模式带官方 API 的稀有案例（⚠️ 细节以 Qt 文档为准）。
  - **Godot 引擎**：编辑器动作全部走可重放命令栈；**RocksDB WriteBatch**=把一串写命令打包提交的事务性命令对象。
- **2026 判断**：CoR 以「中间件/拦截器/责任管道」之名成为后端框架默认架构件；
  Command 在「事件溯源（event sourcing）/CQRS」语境下升格为架构原则而非类模式——两者都比 1994 年更忙了。
