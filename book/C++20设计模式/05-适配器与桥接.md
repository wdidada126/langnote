# 05 适配器模式与桥接模式（对应原书第 6–7 章）

> 对应原书第二部分（结构型）第 6 章「适配器模式」、第 7 章「桥接模式」（推定英文章题 Adapter / Bridge ⚠️）。
> 合并理由：两章共享同一条设计轴——**接口与实现之间的翻译**；Adapter 在两个既有接口之间搭一次性桥，
> Bridge 把「抽象侧」与「实现侧」拆成两棵树长期独立演化。原书 Adapter 章以 vector/matrix 双向适配、
> 范围适配等展开（按第 1 版结构推定 ⚠️）。

## 核心概念速览（中英对照）

- **适配器** — Adapter：把一个类的接口翻译成客户端期待的另一个接口，不改任何一方源码。
- **目标接口/被适配者** — Target / Adaptee：客户端说的语言 vs 被包装对象说的语言。
- **类适配器** — class adapter：多重继承（派生自 Adaptee 并实现 Target），编译期焊死，灵活性低。
- **对象适配器** — object adapter：组合持有 Adaptee（常为 `unique_ptr`/引用），运行期可换，现代默认。
- **双向适配器** — two-way adapter：同一外壳同时提供 Target↔Adaptee 两向翻译。
- **范围适配器** — range adapter：把一个容器的**遍历方式**适配成另一种（如把 vector 当 reverse/stride 视图用）——ranges 已标准化。
- **桥接** — Bridge：抽象侧与实现侧各自成继承树，抽象持实现的指针（`unique_ptr<Impl>`）桥接。
- **抽象化/实现化** — abstraction / implementor：Bridge 两棵树的根类名。
- **扩展轴** — extension axis：Bridge 的价值量化——N 种抽象 × M 种实现若用继承是 N×M 个类，用桥接是 N+M 个。
- **Pimpl** — pointer to implementation：把实现细节藏进不透明指针，编译防火墙；Bridge 的单实例退化形态。
- **句柄类** — handle class：包装引用/指针语义的智能句柄，与 Pimpl 共享「间接层」血统。
- **依赖倒置** — DIP：Bridge 的实现侧接口由抽象侧定义——方向再确认。

## 动机：接口不匹配是常态

- **Adapter**：第三方库的 API 和你需要的 API 对不上，且**双方都不能改**（闭源、或改动成本高于封装）。
- **Bridge**：你**自己**的系统里，「用户看到的概念层」与「底层平台/设备层」都在生长——
  Windows/Linux/Mac 三实现 × 按钮/文本框/窗口三抽象 = 9 个类的继承爆炸，Bridge 把它压成 3+3+胶水。

GoF 的区分口径：Adapter 处理**已存在的两个不兼容接口**（事后补救）；
Bridge 在**设计期就预谋两条演化轴**（事前架构）。

## 机制

### Adapter：三种姿势

🔧（教学示意；对象适配即标准 `unique_ptr` 成员转发）

```cpp
// 对象适配器：持 vector 当栈用
struct StackAdapter {
    std::vector<int> v;
    void push(int x) { v.push_back(x); }
    int pop() { auto x = v.back(); v.pop_back(); return x; }
};
// 范围适配：C++20 已标准化，无需手写
auto odds = v | std::views::filter([](int x){ return x % 2; })
              | std::views::reverse;
```

- **类适配器**今天基本不用：多重继承 + 名字遮蔽问题 + 无法适配成员函数指针/lambda 目标。
- **双向适配器**要点：两向翻译函数都放同一个类，转换知识集中一处（原书以 matrix/vector 转置互换为例 ⚠️ 推定）。
- C++20 里**标准库自己就是适配器博物馆**：`std::reference_wrapper`（把引用适配成可拷贝对象，喂 `bind`/算法）、
  ranges 的 `ref_view/all_view/common_view`（把 range 适配成 view/sized range/公共迭代器域）。

### Bridge：抽象持实现

🔧（教学示意）

```cpp
struct RendererImpl {                    // 实现化根
    virtual ~RendererImpl() = default;
    virtual void render_circle(double, double, double) = 0;
};
struct OpenGLRenderer : RendererImpl { /* ... */ };
struct Rasterizer     : RendererImpl { /* ... */ };

struct ShapeAbstraction {                // 抽象化根
    std::unique_ptr<RendererImpl> impl;  // 桥：指针域
    virtual ~ShapeAbstraction() = default;
    virtual void draw() = 0;
};
struct Circle : ShapeAbstraction {
    double x, y, r;
    void draw() override { impl->render_circle(x, y, r); }  // 委托给实现侧
};
// main：Circle c{std::make_unique<OpenGLRenderer>(), 1, 2, 3};
```

要点：**实现接口不应模仿领域接口**——`render_circle` 是渲染语言不是几何语言，否则桥退化成了转发（GoF 的「实现接口应基于低层原语」）。

**反模式/何时不用**：

- **适配器堆叠成洋葱**：A→B→C→B' 多层互译说明接口该收敛而非继续加壳；先统一目标接口再适配。
- **万物 Bridge**：只有一种植入方式（单实现）时 Bridge 是纯间接层——Pimpl 才是你要的（且目的不同：编译防火墙 vs 演化轴）。
- **Bridge 侧实现泄漏**：抽象类方法签名里出现 `OpenGLContext&`——桥没桥好，实现细节渗进了抽象树，等于回到继承爆炸。
- **适配器里藏业务逻辑**：Adapter 只做翻译；一旦开始「顺便修正数据」，它就变成了防腐层（ACL），命名与测试策略都该升级。

## 权衡与相邻概念对比

| 维度 | Adapter | Bridge | Decorator | Proxy |
| --- | --- | --- | --- | --- |
| 包裹对象数 | 1（被适配者） | M（实现族） | 1（被装饰者） | 1（被代理者） |
| 接口变化 | **变**：A 接口→B 接口 | 不变：两侧各自稳定 | 不变：同接口加料 | 不变：同接口控访问 |
| 演化方向 | 事后一次性翻译 | 事前两轴独立生长 | 纵向无限叠加 | 控制语义（懒/权/记账） |
| 典型问句 | 「这两接口怎么对话」 | 「概念与平台怎么分家」 | 「功能怎么可拆可装」 | 「访问怎么把关」 |

（Bridge vs Strategy 见 [13-状态与策略.md](13-状态与策略.md)：同持 `unique_ptr<Policy>` 时，
Strategy 的指针域是**可热换的算法**，Bridge 的指针域是**同生同死的实现底座**——语义从属关系决定模式名。）

## 最新演进与工业实践

- **经典文献**：GoF 1994 之 Adapter / Bridge 条（书目见 [../设计模式GoF/03-结构型模式.md](../设计模式GoF/03-结构型模式.md)）。
- **C++20/23**：ranges 适配器族（`join_view`、`transform_view`、`counted`…）把「遍历接口互译」完全标准化；
  C++23 `deducing this` 让适配器写泛型转发时免 CRTP（示例：`.this`-捕获转发包装）；
  `std::expected` 用于适配层「转换失败」的返回值表达（工厂/适配器错误路径同款，见 [02-建造器模式.md](02-建造器模式.md)）。
- **工业体现**：
  - **fmtlib/fmt**：`fmt::formatter<T>` 是「把用户类型适配进格式化协议」的标准适配器——为每个类型实现一次、库侧接口永不动。
  - **rocksdb**：`Env`/`FileSystem` 抽象是教科书级 Bridge——核心引擎面向 Env 编程，POSIX/Windows/内存实现各自演化；
    `CompositeEnv` 组合多实现。
  - **Skia**：后端（OpenGL/Metal/Vulkan/Raster）与画布 API 之间即渲染 Bridge。
  - **libcurl/c-ares 等 C 库**：不透明句柄 + 平台后端 = C 语言世界的 Bridge 常态形态。
- **2026 判断**：Adapter 作为「模式」正在与**接口设计**合并教学（ACL、six-sided architecture 语境）；
  Bridge 在跨平台 SDK（图形、音频、存储引擎）里仍是默认架构，且随 WASI/多后端 GPU 生态热度上升。
