# 03 工厂方法与抽象工厂模式（对应原书第 3 章）

> 对应原书第一部分（创建型）第 3 章「工厂方法和抽象工厂模式」（推定英文章题 Factories ⚠️）。
> 原书此章涵盖工厂方法、抽象工厂、枚举式工厂、注册式工厂等变体（按第 1 版结构推定 ⚠️）。

## 核心概念速览（中英对照）

- **工厂方法** — Factory Method：把「实例化哪个类」延迟给子类钩子或回调函数。
- **抽象工厂** — Abstract Factory：一个接口产出**一族**相互约束的产品（如按钮+文本框+滚动条）。
- **简单工厂/静态工厂** — static factory / 伪模式：`T create(args)` 的集中构造点，GoF 未收录的朴素形态。
- **枚举式工厂** — factory keyed by enum：`switch`/查表按枚举选具体类，编译期可知类型集时使用。
- **注册式工厂** — factory with registration：`map<string, function<unique_ptr<T>()>>`，运行期由插件自注册，解耦产品类与工厂。
- **多态构造函数** — polymorphic constructor：工厂方法要解决的原始问题——通过基类指针造出派生对象。
- **概念约束工厂** — concepts-constrained factory：C++20 用 `requires`/concept 把「产品必须满足的接口」写进模板签名。
- **依赖倒置** — Dependency Inversion Principle (DIP)：高层模块与低层模块都依赖抽象；工厂是 DIP 的构造端执行者。
- **控制反转** — Inversion of Control (IoC)：构造决策从调用方转移到框架/容器；注册式工厂的最小形态。
- **对象生命周期钩子** — lifecycle hook：工厂返回 `unique_ptr`（转移所有权）还是引用（工厂持有），决定谁负责析构。

## 动机：`new` 的三宗罪

直接 `new Concrete(...)` 把**具体类型的知识**焊进调用点：

1. **不可替换**：测试要 mock、生产要换实现，全得改调用方（违反 OCP）。
2. **不可扩展**：新类型进入系统需要触碰中央 `switch`（注册式工厂的动机）。
3. **所有权含糊**：裸 `new` 不回答「谁删除」。现代答案：工厂返回 `std::unique_ptr<T>`（转移）或 `T&`（工厂池持有），二选一必须显式写进签名。

工厂家族的分歧只有一处：**选择具体类型的决策放在哪**——子类钩子（工厂方法）、中央 `switch`（枚举式）、
运行期注册表（注册式）、还是「一族打包选一次」（抽象工厂）。

## 机制：C++20 的四种写法

🔧（已实测 g++ 15.2）concepts 约束的枚举式工厂——产品接口成为模板签名的一部分：

```cpp
template <typename T>
concept Productish = std::default_initializable<T> && requires (T t) { t.name; };

template <Productish T>
std::unique_ptr<T> create(std::string n) {
    auto p = std::make_unique<T>();
    p->name = std::move(n);
    return p;
}
```

🔧 **注册式工厂**（原书口径的 "factory with registration" ⚠️ 术语推定）骨架：

```cpp
class ShapeFactory {
    inline static std::unordered_map<std::string,
        std::function<std::unique_ptr<Shape>()>> reg_;
public:
    static void reg(std::string key, std::function<std::unique_ptr<Shape>()> f) {
        reg_.insert({std::move(key), std::move(f)});   // 幂等 insert：防重复注册
    }
    static std::unique_ptr<Shape> create(std::string_view key) {
        if (auto it = reg_.find(std::string(key)); it != reg_.end()) return it->second();
        throw std::domain_error("no such shape");
    }
};
struct Circle : Shape { /* ... */ };
static const bool registered = []{
    ShapeFactory::reg("circle", []{
        return std::unique_ptr<Shape>{std::make_unique<Circle>()};
    });
    return true;
}();
```

要点：注册键与构造 lambda 一起放在**产品类自己的翻译单元**里；但静态初始化顺序是 C++ 著名陷阱
（翻译单元间顺序未定义）——工业做法是「显式 `register_all()` 入口」或把注册表做成函数内 static（Meyers 化），
详见 [../Effective_Modern_C++.md](../Effective_Modern_C++.md) 对静态作用域的讨论与第 [04-原型与单例.md](04-原型与单例.md) 章。

**抽象工厂**：一个 `GuiFactory` 接口含 `create_button()/create_scrollbar()/create_combobox()` 三方法，
`DarkThemeFactory` / `LightThemeFactory` 各自实现——关键不变式：**同一工厂产出的产品必须同族**。
C++20 表达：工厂方法返回值全用 `unique_ptr<ProductConcept>`（concept 定义的产品接口），
族的一致性由「客户端只持有一个工厂实例」的纪律维持，类型系统帮不了你（这是它和 Builder 的本质区别之一）。

**反模式/何时不用**：

- **万物皆工厂**：构造点本来就唯一、类型编译期可知时，直接 `T{args}` 或 `make_unique<T>`；工厂层是纯间接成本。
- **工厂方法 vs 虚构造混淆**：派生类加 `clone()` 解决的是「按对象造同类对象」（那是 [04-原型与单例.md](04-原型与单例.md) 的原型模式），不是工厂方法。
- **注册式工厂的字符串键**：拼错键要到运行期才炸；缓解：键用 `constexpr string_view` 常量或枚举，测试期做全表覆盖断言。
- **静态工厂返回引用 + 多线程**：工厂内缓存的生命周期若跨线程，需要与单例相同的初始化纪律（见第 04 章）。

## 权衡与相邻概念对比

| 变体 | 新增类型的代价 | 编译期可知性 | 跨 DLL/插件 | 典型场景 |
| --- | --- | --- | --- | --- |
| 中央 switch（枚举式） | 改工厂源码，重编译 | 全可知 | 差 | 有限集合、协议消息类型 |
| 注册式（自注册） | 新增翻译单元即可 | 运行期才知道 | 好（DLL 入口注册） | 编解码器、驱动、测试替身 |
| 工厂方法（虚钩子） | 新增派生工厂 | 半可知 | 好 | 框架留白（GoF 原始场景） |
| 抽象工厂 | 新增一族（一个工厂类） | 半可知 | 好 | 主题/平台/代际成族产品 |

**Abstract Factory vs Builder**（必须分清的一对）：AF 隐藏「造哪个类」，Builder 暴露「怎么分步造」；
AF 的方法即时返回产品，Builder 到 `build()` 才返回。两者可叠用：抽象工厂内部用 Builder 造复杂产品。
**Abstract Factory vs Prototype**：AF 用代码决定族，Prototype 用现成样本决定族（见 [04-原型与单例.md](04-原型与单例.md)）。

## 最新演进与工业实践

- **经典文献**：GoF 1994 之 Factory Method / Abstract Factory 两条（书目见 [../设计模式GoF/02-创建型模式.md](../设计模式GoF/02-创建型模式.md)）。
- **C++20→26**：concepts 让「产品接口」成为可命名的编译期契约（上例 ✅ 实测）；
  C++26 静态反射（P2996，已核实进入 C++26 标准定稿口径，2025 年草案含静态反射）落地后，
  「按名字符串反射构造类型」可能吃掉注册表的一半样板——Qt 社区已在讨论 P2996 替代 moc 的注册管线
  （来源：Qt wiki "C++ reflection (P2996) and moc"，2025 ✅ 检索可得）。
- **工业体现**：
  - **rocksdb/leveldb**：`TableFactory`、`FilterPolicy`、`Env` 都是「抽象工厂 + 策略」的 C 风格函数表形态——
    打开哪种磁盘格式由工厂决定，正是 leveldb 论文级实现里的可扩展点。
  - **fmtlib/fmt**：`formatter<T, Char>` 特化 = 编译期按类型选工厂，零运行期注册。
  - **gRPC C++**：服务/拦截器通过 `GrpcComponentBuilder`（⚠️ 名称按 2022 重构口径，未复核）与注册机制装配。
  - **LLVM/Clang**：`PassPlugin` 的 `registerPassBuilderCallback` —— 注册式工厂在编译器插件体系的标准形态。
- **2026 判断**：运行期注册表不会消失（插件边界需要字符串/动态键），但**类型集封闭**的工厂正被
  `variant` + 编译期查表整体替代——工厂的「选择」语义越来越多在编译期完成。
