# 07 外观模式与享元模式（对应原书第 10–11 章）

> 对应原书第二部分（结构型）第 10 章「外观模式」、第 11 章「享元模式」（推定英文章题 Facade / Flyweight ⚠️）。
> 合并理由：两章是结构型里的「边界组」——Facade 管**对外接口宽度**（收窄），
> Flyweight 管**对内对象数量**（压缩）；都回答「结构型模式在现代 C++ 里还剩多少手写空间」这一判断题。

## 核心概念速览（中英对照）

- **外观** — Facade：为子系统提供统一、简化的高层接口；不新增功能，只做汇聚与编排。
- **子系统** — subsystem：一组协作类/库/服务，Facade 的存在理由是它们**不该被直接组合调用**。
- **门面 vs 网关** — facade vs gateway：网关（网络/API 语境）带协议翻译，Facade 纯进程内聚合（术语对照用）。
- **API 宽度** — API surface：Facade 的直接产物；`libcurl` 的 `easy` 接口是教科书案例——一次 `curl_easy_perform` 封装 socket/TLS/DNS。
- **门面 vs 适配** — facade vs adapter：Facade **主动设计**新接口（收窄），Adapter 被动翻译旧接口（对口）——见 [05-适配器与桥接.md](05-适配器与桥接.md)。
- **享元** — Flyweight：细粒度对象大量重复时，共享不可变**内部态**、把可变态作**外部态**传入。
- **内部态/外部态** — intrinsic / extrinsic state：可共享部分（字形轮廓）vs 每次调用传入部分（位置/字体号）。
- **享元工厂** — flyweight factory：按值查表返回指针/引用（interning），客户端拿到的永远是「同一个」。
- **驻留** — interning：字符串/符号级享元（编译器符号表、`constexpr` 字符串池）。
- **结构共享** — structural sharing：函数式数据结构（持久化列表/树）以共享子树实现「伪不可变拷贝」——Flyweight 的近亲。
- **SSO** — small string optimization：`std::string` 小串内联，与享元相反的优化方向（省堆而非省份数）。
- **缓存** — cache/memoization：与享元形似（都有表）；缓存回答「重算太贵」，享元回答「副本太多」。

## 动机：宽接口的债与海量小对象

- **Facade**：客户端直接编排子系统 = 把子系统的**内部结构**变成客户端的依赖；子系统每次演化都放大成客户端改动。
  一个薄 Facade 把「使用方式」固化为函数/类，依赖收敛到一处。
- **Flyweight**：字符 a–z 的字形对象若每处实例化，百万份拷贝吃光内存；
  26 个共享实例 + 每次调用附带位置/大小 = 传统动机。现代语境下它退化为两个更具体的问题：
  ①**驻留**（同值对象归一化，加速比较与哈希）；②**结构共享**（持久化数据结构省拷贝）。

## 机制

### 外观：从函数到类再到库边界

🔧（教学示意）最小 Facade——进程内子系统聚合：

```cpp
class ReportService {   // 一个入口，编排三子系统
    Parser parser_; Engine engine_; Exporter exporter_;
public:
    std::string run(std::string_view src) {
        auto ast = parser_.parse(src);        // 子系统间流转被封装
        auto data = engine_.evaluate(ast);
        return exporter_.to_pdf(data);
    }
};
```

判据：**Facade 里的每个成员函数都应是「用例」而不是「转发器」**——若方法体只有一行转发调用，
那是 Adapter/包装退化；Facade 的价值在编排（顺序、事务、错误聚合）。

### 享元：interning 池

🔧（已实测 g++ 15.2 同型骨架，见 t4）共享不可变内核：

```cpp
struct Glyph { std::string shape; };
class GlyphPool {
    std::unordered_map<std::string, std::shared_ptr<const Glyph>> pool_;
public:
    const Glyph& get(const std::string& s) {
        auto it = pool_.find(s);
        if (it == pool_.end())
            it = pool_.emplace(s, std::make_shared<const Glyph>(Glyph{s})).first;
        return *it->second;               // 同值恒返同一对象：interning 语义
    }
};
```

- `shared_ptr<const T>` 是 C++ 享元的默认载体：共享所有权 + 不可变性（内部态被写坏=全库灾难）。
- **`string_view` 与驻留的配合**：以 `string_view` 作查表键可免一次分配（C++20 透明哈希 `std::hash<std::string_view>` ✅），
  但视图不持有存储——键的存活必须依赖池本身（interning 的正解是**池拥有字符串**，返回 view 指向池内数据）。
- **外部态纪律**：`draw(glyph, x, y, scale)` 里位置/缩放必须是参数而非 `Glyph` 成员——否则池内对象被逐个改花。
- 标准库/语言的天然享元：字符串字面量合并（link-time folding）、`std::atomic` 引用计数池、
  编译器符号表、Qt 的 `QStringLiteral` 数据段驻留。

**反模式/何时不用**：

- **Facade 变成上帝类**：所有新功能都往门面加方法——门面应只做**用例编排**，新需求先问子系统能否内聚。
- **享元的现代成本核算**：`shared_ptr` 控制块 + 哈希查表 + 间接跳转，可能比直接放 N 个 16 字节 POD 进 `vector` 更慢——
  **享元是内存受限时代的模式**；今天先量 cache miss，再谈共享（GoF 的「节省内存」前提要重估）。
- **interning 的并发与生命周期**：全局池 = 新的单例问题（见 [04-原型与单例.md](04-原型与单例.md)）；
  跨线程池需锁或分片，池不清理则内存泄漏——三条都要写进设计。

## 权衡与相邻概念对比

| 维度 | Facade | Mediator | Adapter | Flyweight |
| --- | --- | --- | --- | --- |
| 通信方向 | 客户端→子系统（单向） | 对象间多向，经中心转发 | 客户端↔被适配者 | 无通信，只有共享 |
| 谁定义新接口 | Facade（主动设计） | Mediator（仲裁规则） | Adapter（迁就既有） | 无新接口，改实例策略 |
| 目的 | 简化使用 | 解耦网状依赖 | 接口互译 | 省内存/归一化 |
| 典型规模 | 库/子系统边界 | 同模块内协作类 | 两具体类之间 | 元素类型极少、实例极多 |

**Facade vs Abstract Facade（工厂侧）**：`std::filesystem` 是 Facade（path 系统接口统一平台差异），
其 `u8path` 又是适配器——一库多模式并存是常态，别用模式名互相禁止。
**Flyweight vs Cache**：缓存存**结果**（可淘汰、可变）；享元存**规范值**（常驻、不可变）。
把 LRU 缓存叫享元会诱导你共享本该淘汰的对象。

## 最新演进与工业实践

- **经典文献**：GoF 1994 之 Facade / Flyweight 条（书目见 [../设计模式GoF/03-结构型模式.md](../设计模式GoF/03-结构型模式.md)）；
  Woolf 1998 年会的 Facade 与 Gateway 讨论（PLoP Pattern Languages of Program Design 2，⚠️ 仅书目级引用，不引编号）。
- **C++20/23**：`std::format` 把「格式化」这一传统 Facade 用例做成标准库单入口（fmt 是其前身）；
  `std::source_location`、`std::span` 等小设施持续替代手工门面转发。
- **工业体现**：
  - **libcurl**：`curl_easy_*`/`curl_multi_*`——C 语言史上最常被引用的 Facade：一次 `perform` 编排 DNS/TLS/重定向/代理。
  - **LLVM/Clang**：`clang::tooling` 库（`tooling::runToolOnCode`）把 CompilerInstance 启动、诊断消费等编排成一行 API。
  - **rocksdb**：块缓存与「相同索引块跨 SST 共享」的去重机制（⚠️ 具体类名未复核，仅取机制口径）——
    存储引擎的享元应用。
  - **游戏引擎**：字形图集、粒子模板、材质实例——Unity/Unreal 的 asset 引用体系是享元的工业化重演（⚠️ 细节口径以引擎文档为准）。
- **2026 判断**：Facade 教学已并入「API 设计」课程（`std::filesystem` 式「薄包装、厚用例」）；
  Flyweight 在「内存带宽/缓存层级」时代收缩到字符串/符号驻留与结构共享两个稳定场景，
  「为省对象而共享」的原始动机被 arena 分配器 + SoA 数据布局正面击败。
