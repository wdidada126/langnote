## 2.1 演化动力清单：四股力拧成的「必须多云」绳（⚠️ 推定自副题与 Overview）

副题 ✅「Build Multi-cloud Modern Distributed Data Warehouses with Azure and AWS」——多云是目的格而非
修饰格。四条工业动因（通说 ⚠️，本书以双云并写的事实本身背书）：

1. **组织并购史**：大企业 IT 版图=收购+部门自治的沉积岩，Azure 与 AWS 往往已在生产并存；
2. **区域合规**：数据驻留/行业监管把负载钉在特定云区（11 章细展开）；
3. **议价与韧性**：避免单一云深度锁定，关键链路保留跨云逃生门；
4. **技术错位**：某云引擎更强（Synapse 的 T-SQL 资产复用 vs Redshift 的零 ETL 生态），按负载择云。

**架构推论**：现代数仓的「数据面」可以各云分立，但「控制面」（目录/编排/治理/身份）必须全局唯一——
这条「分面异构、控制面统一」原则贯穿本册 07/08/09/10 四章（⚠️ 本书立场重构）。

## 2.3 「分布式」在多云语境下的三种含义（副题词义辨析）

副题的 Distributed 常被误读为 MPP——多云册语境应拆三层（⚠️ 推定）：

- **D1 引擎内分布式**：MPP 分片执行（Synapse 分发列/Redshift DISTKEY——对位表行「物理设计」，
  见 [../Amazon_Redshift_TDG/00-总览与阅读地图.md](../Amazon_Redshift_TDG/00-总览与阅读地图.md) §4）；
- **D2 跨引擎分布式**：一份数据多引擎各查各的（Athena/Spark/Synapse 共读湖上表，🔧G1 的「联邦税」
  即此层的成本形状）；
- **D3 跨云分布式**：数据物理分居两云，靠复制/目录同步/编排胶水拼成一张逻辑仓——本册真正的题眼。

D3 的三个热力学难题：出云流量费、双目录一致性、身份贯通（各在 03/10/11 章落刀）。

## 2.4 架构范式对：中台式 vs 网格式（为 06 章埋轴）

- **范式A 集中平台**：一支平台队建全公司的仓/湖/管道，07–11 章的编排治理都是其工具体系；
- **范式B 领域网格**：数据产品归领域，平台只做自助底座——Ch4 摘要 ✅ 明言 mesh 是对「存储、组织、
  检索、扩展、消费都难」的系统性回应。

本书把两范式**并列而非替代**处理（章序 mesh 在前编排在后 ⚠️ 推定意味）：大企业现实=集中底座上
长出领域产品；06 章 🔧G6 展示「三个独立领域库联邦成一张查询面」正是该合流的微缩模型。

## 2.7 多云非动力：把五条貌似合理的理由反过来看（⚠️ 重构）

1. **「多云=高可用」**——跨云双活成本通常高于单云多区；HA 请先在云内做满（04 章 4.5）；
2. **「多云=议价筹码」**——没有迁移预算的负载，筹码是纸面的（3.4 暗题三）；
3. **「多云=容灾备份」**——冷备可以，双仓双活是目录/身份/出云费三份账（2.3 D3）；
4. **「多云=跟风」**——2.1 四动因一条不占时，单云深耕才是最优解（让位三巨头册）；
5. **「多云=统一数据面」**——统一的是控制面不是存储面（2.2 原则逆否命题）。

## 核心概念速览（中英对照）

| 中文 | 英文 | 一句话 |
|---|---|---|
| 多云 | Multi-cloud | 同一业务栈跨两朵以上公有云部署 |
| 云锁定 | Vendor Lock-in | 深度绑定单一云带来的议价与迁移劣势，多云动因③的反面 |
| 数据面/控制面 | Data Plane / Control Plane | 负载执行层 vs 目录编排治理层；后者要求全局唯一 |
| 着陆区 | Landing Zone | 云内合规基线账户/订阅结构，多云各建一份 |
| 参考架构七层 | Reference Architecture Layers | 本册 2.2 重构：源→摄入→着陆→加工→语义→编排→治理→出口 |
| 中台式 | Centralized Platform | 平台队统建，效率与瓶颈同源 |
| 网格式 | Data Mesh | 领域自治+数据产品+联邦治理（06 章） |
| 出云流量费 | Egress Cost | 跨云/跨区数据搬运的隐形账，D3 难题① |
| 逃生门 | Exit Strategy | 主云故障或商务翻脸时的整建制切换预案 |
| 一致性镜像目录 | Mirrored Catalog | 双云目录互备的弱一致方案（10 章展开） |

## 最新演进与工业实践

- **Synapse→Fabric 迁移叙事**（2023–2026，⚠️ 转述；✅ https://learn.microsoft.com/en-us/azure/synapse-analytics/overview-what-is 与 https://learn.microsoft.com/en-us/fabric/get-started/microsoft-fabric-overview 均 2026-10-02 验 200）：微软把「云上组合体」整合为一站式 SaaS——本册的「多云组合蓝图」在 2026 视角读来恰是 Fabric 化前夜的形态，两代范式对读价值高（Fabric 纵深册在波内登记不链）。
- **Redshift 零 ETL 常态化**（2024–，⚠️ 转述；盘上实证链见 [../Amazon_Redshift_Cookbook_2e/10-ZeroETL与LakeFormation统一授权.md](../Amazon_Redshift_Cookbook_2e/10-ZeroETL与LakeFormation统一授权.md)）：DMS Serverless 把 2.2「摄入层」进一步托管化，自建管道在清单中的占比逐年下降。
- **Iceberg 作为跨云「表契约」**（⚠️ 转述；✅ https://iceberg.apache.org/docs/latest/）：D3 一致性问题出现新解——两云引擎读写同一开放表元数据，「双目录镜像」部分让位于「表格式即真相」；AWS Glue Catalog 与 Azure Databricks 均已支持（各家文档口径 ⚠️）。
- **FinOps 进入架构评审标配**（2020s 工业实践 ⚠️）：出云费与闲置弹性单元纳入 2.5 清单第 3 条已成大厂通行做法；云仓三巨头的成本纵深各在其盘上册（Tuning 册=credit 侧、BigQuery 册=slot 侧），本册保持「多云总纲不重复记账」的分工。
