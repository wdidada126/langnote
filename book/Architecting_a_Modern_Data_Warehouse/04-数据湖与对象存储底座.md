## 4.1 湖的成立三条件（⚠️ 重构，AWS 白皮书骨架 ✅AWS11）

https://docs.aws.amazon.com/whitepapers/latest/building-data-lakes/welcome.html（✅ 200）给的
经典三条件：**廉价海量存储 + 灵活 schema + 一等安全与多负载分析**。对位到本册双云：

| 条件 | Azure 侧 | AWS 侧 | 取证 |
|---|---|---|---|
| 对象存储 | ADLS Gen2（Blob 域 ⚠️） | Amazon S3 | ✅ https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html；Azure 架构域 ✅ https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/data-warehousing |
| 目录/元数据 | Purview Data Map（✅ https://learn.microsoft.com/en-us/azure/purview/） | Glue Data Catalog（✅ https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html） | 10 章主场 |
| 多负载引擎 | Synapse serverless/Databricks（✅ AZ6 域） | Athena/EMR/Redshift Spectrum 群（✅ AWS3/AWS1 域） | 03/08/09 章 |

S3 S3 的持久性分层与生命周期叙述（⚠️ 转述官方口径，✅ 页含 Durability 叙述）是
「着陆区即真相」的物理背书：湖底座选型基本=对象存储 API 兼容性竞赛，本册视角下**两云各建一个湖、共享一份目录**是默认答案，
「一云为湖、另一云直读」的跨云单湖是高危变体（出云费+权限穿越，2.3 D3 难题①③复发）。

## 4.2 入湖三路与格式层（⚠️ 通说 + 产品 ✅ 名）

- **批量**：对象拷贝/COPY 型装载（ADF 复制✅AZ2 域 / Glue Job✅AWS2 / DMS 批量✅AWS9）；
- **微批**：托管流转换（Glue 流式 ⚠️ / Databricks Structured Streaming ✅AZ6 域）；
- **变更直落**：CDC/零 ETL（DMS 到 Redshift ⚠️，对盘上 Cookbook 04 章 [../Amazon_Redshift_Cookbook_2e/04-流式摄入与Kinesis配方.md](../Amazon_Redshift_Cookbook_2e/04-流式摄入与Kinesis配方.md) 深读，本册不重复）。

文件格式三选一（通说 ⚠️）：**Parquet/ORC 列存**（分析默认）、**JSON/CSV**（交换与原始层）、
**Delta/Iceberg 托管格式**（05 章接管）。列存压缩的方向性证据可借盘上实验（[../Amazon_Redshift_TDG/00-总览与阅读地图.md](../Amazon_Redshift_TDG/00-总览与阅读地图.md) §6 🔧1：Parquet 对行存 2.5×；
[../Tuning_the_Snowflake_Data_Cloud/04-微分区.md](../Tuning_the_Snowflake_Data_Cloud/04-微分区.md) 🔧E1 有序/乱序 11×）——均为 DuckDB/SQLite 类比，**非两云行为**。

## 4.3 湖的查询面：无服务器联邦族的成本形状（⚠️+🔧 复引 G1）

Athena（✅AWS3）与 Synapse serverless SQL 池（⚠️；专页改版 404 见 00 §8）同属「不搬数据、
就地开查」的联邦族。本册 🔧G1（demo2.py，DuckDB ATTACH 双 SQLite 源，**非平台行为**）量化了其税：

| 路径 | 用时 | 60万×10万行 JOIN 结果 |
|---|---|---|
| ATTACH 跨源联邦查询 | **75.0ms** | 39,963 行 |
| 同 JOIN 物化进单引擎后执行 | **6.2ms** | 同 39,963 行 |

**联邦税 ≈12.2×**——方向性结论 ⚠️：联邦适合探索与低频交叉，高频链路应物化/表格式化沉淀
（05 章 medallion 的 silver/gold 层正是「把联邦查询逐个变成引擎内查询」的制度化）。真实云上
税基是对象存储请求费+扫描量计费+冷启动，结构与 🔧 同向但量级不可换算 📐。

## 4.4 湖与仓的边界谈判：什么时候必须「升仓」（⚠️ 重构对照三巨头表）

借 [../Amazon_Redshift_TDG/00-总览与阅读地图.md](../Amazon_Redshift_TDG/00-总览与阅读地图.md) §4 对位表口径，
湖上负载出现以下信号即应进仓/进湖仓表（⚠️ 通说）：
①并发交互用户持续攀升（对象存储按请求计费反噬）；②需要 ACID 多写者（裸文件并发覆写危险）；
③需要跨部门强一致口径（读时模式解释漂移）；④需要行级安全（湖侧 LF/RLS 补丁成本高）。
多云 twist：**「升仓」在两云是两次不同计费模型的切换**——同一负载在 Azure 侧 F1 贵还是
AWS 侧 F1 贵，取决于点②③的频率，无普适答案（03 章决策树在此闭环）。

## 4.5 湖底座的多灾与生命周期（⚠️ 转述官方口径）

- 冗余：两云均默认多副本跨区（RA-GRS 类/Glacier 分层 ⚠️ 转述，S3 Welcome ✅ 页含 Durability 叙述）；
  **跨云容灾不免费**——本册推定书立场：备份可以跨云（低频大对象走冷存储），热备不跨云（D3 难题①）。
- 生命周期规则：热→冷→归档自动沉降是湖的成本命门（⚠️ 两家文档同源概念）；
- 不可变性：对象存储「写新删旧」+版本控制，天然贴 Bill Inmon「非易失」——🔧G4（05 章）演示
  版本目录并存可读的正是该语义的最简实现。

## 4.6 本章学习检查点（⚠️ 推定）

1. 背出三条件并说出「一云为湖、另一云直读」为什么触发两个 D3 难题；
2. 🔧G1 的 12.2× 联邦税能迁移成一条链路设计纪律（探索用联邦、生产用沉淀）；
3. 列出四个「必须升仓」信号，并各给一个湖侧的临时替代与其计费暗坑。

## 4.7 入湖点的数据合同草图（⚠️ 重构）

着陆区「格式自由」要配三份最小合同，否则 05 章湖仓接不住：
- **命名与分区约定**：`{domain}/{entity}/{yyyy-MM-dd}/` 三段式——回补与裁剪都靠它
  （🔧G2 的文件名裁剪正是其机械原型）；
- **清单旁挂**：每批数据配 行数/校验和/schema 指纹 三字段 sidecar 文件（🔧G4 清单的前身）；
- **新鲜度水位**：写路径登记「该源最新完整分区」指针（10 章目录自定义实体的数据来源）。

## 4.8 湖章常见误读与纠偏（⚠️ 编者注）

## 核心概念速览（中英对照）

| 中文 | 英文 | 一句话 |
|---|---|---|
| 数据湖 | Data Lake | 廉价海量+灵活 schema+多负载引擎的原始数据底座 |
| 对象存储 | Object Storage | 键值寻址的不可变分片存储（ADLS Gen2/S3） |
| 读时模式 | Schema-on-Read | 湖哲学：装载不校验、查询时解释（01 章对位） |
| 着陆区 | Landing Zone（湖语境的 raw 区） | 原始数据「即真相」的首落点 |
| 跨源查询联邦 | Cross-source Federation | 不搬就地查；12.2× 税的出处（🔧G1） |
| 请求费/扫描计费 | Per-request / Scanned-byte Pricing | 联邦族的成本双暗线 |
| 生命周期沉降 | Lifecycle Tiering | 热→冷→归档自动搬运，湖的财务命门 |
| 列式文件格式 | Columnar File Format | Parquet/ORC：分析默认布局 |
| 多可用区冗余 | Multi-AZ Redundancy | 云内默认；跨云容灾另案（4.5） |
| 升仓信号 | Warehouse Graduation Signals | 并发/ACID/一致性/行级安全四信号（4.4） |
