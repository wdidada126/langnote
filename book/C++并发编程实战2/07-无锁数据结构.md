# 第 7 章 无锁数据结构

> **一句话**：无锁不是「不用锁的各种优化技巧」，而是**换了一整套正确性论证方式**——任何线程推进一步，系统就推进一步。

## 核心精讲

### 7.1 三种非阻塞强度

| 术语 | 保证 | 备注 |
| --- | --- | --- |
| **obstruction-free** | 单线程独享时可以完成 | 最弱，允许活锁 |
| **lock-free** | 系统整体必有线程完成 | 允许个体饿死，实践中够用 |
| **wait-free** | 每个线程在有限步内完成 | 最强，实现代价最高 |

优点：消除死锁的可能、抗抢占、理论上线性可伸缩。
缺点：正确性证明困难、**内存回收成为核心难题**、对 ABA 敏感、单线程基准常常更慢。

### 7.2.1 无锁栈：Treiber 栈（1986）

```cpp
// 教学示意：Treiber 栈的 push（不参与构建）
template <typename T>
class lock_free_stack {
    struct node { T data; node* next; };
    std::atomic<node*> head{nullptr};
public:
    void push(T const& data) {
        node* const new_node = new node(data);
        new_node->next = head.load();                       // 1) 先记下旧栈顶
        while (!head.compare_exchange_weak(new_node->next,  // 2) 期待值会被更新
                                           new_node)) {}    // 3) 失败则重试，直到成功入栈
    }
};
```

注意 `compare_exchange_weak` 会把**当前真实值**写回第一个实参，所以循环体天然不需要重新读取。

### 7.2.2 `pop` 的 CAS 循环为什么必须是 weak

```cpp
// 教学示意：pop 的 CAS 循环（不参与构建）
std::optional<T> pop() {
    node* old_head = head.load();
    while (old_head && !head.compare_exchange_weak(old_head, old_head->next)) {}
    if (!old_head) return std::nullopt;
    std::optional<T> res(std::move(old_head->data));
    delete old_head;        // 危险：别的线程可能还握着这个指针
    return res;
}
```

三个要点：

1. **必须用 `compare_exchange_weak` 加循环**：weak 版本允许**虚假失败**（ spurious failure，即便值相等也可能返回 false），换来 Arm LL/SC 等平台上的低成本实现；它本来就要配循环，这里循环反而是刚需。
2. **失败时 `old_head` 自动被更新**为新的栈顶，下一次迭代直接重试。
3. **`delete old_head` 是错的**：另一个线程的 `push` 可能已经读了同一个指针，正在访问它——这就是**内存泄漏与回收**难题。

### 7.2.3 内存回收：hazard pointer 与分裂引用计数

- **hazard pointer**（Michael，PODC 2002）：线程在访问某节点前，先把指针登记到自己的 hazard 槽；回收者扫描全体线程的槽，确认无人引用后才真正释放。
- **分裂引用计数（split reference count）**：把每个节点的计数拆成「外部引用数」加「内部 countdown」，只有两者都归零才能删除，从而绕开 ABA。

```cpp
// 教学示意：hazard pointer 的使用骨架（不参与构建）
std::atomic<void*>& slot = get_hazard_slot_for_current_thread();
node* p = nullptr;
do {
    p = head.load();
    slot.store(p);                 // 登记：告诉别人我正在用 p
} while (p != head.load());        // 再确认一次，避免登记了一个废弃指针
/* 此时 p 一定安全，可以放心访问 */
slot.store(nullptr);               // 用完注销
```

### 7.2.4 施加合适的内存序

从默认 `seq_cst` 出发，逐步放松，每一步都要能说出理由：

| 操作 | 选用 | 理由 |
| --- | --- | --- |
| `push` 的 CAS | `release`（成功）/ `relaxed`（失败） | 只需保证节点内容先于指针对他人可见，失败路径不发布任何东西 |
| `head.load()` | `acquire` | 读到指针后能看见该节点此前的所有写入，与第 5 章的 release/acquire 配对 |
| 单纯的计数器 | `relaxed` | 不携带数据依赖 |

> 观察结论：`release` 与 `acquire` 恰好构成第 5 章所述的**发布—消费**关系——写者发布节点，读者获取节点内容。凡是这种关系，都不需要 `seq_cst`。

### 7.2.5 无锁队列：Michael-Scott 队列（PODC 1996）

两个关键设计：

1. **虚拟节点（dummy node）**：使空队列也含一个节点，`head` 与 `tail` 永不相等 nullptr，`enqueue` 与 `dequeue` 互不干扰。
2. **尾指针落后（lagging tail）**：把「尾节点的 `next` 字段」与「`tail` 指针本身」分离，允许尾指针暂时滞后，再由其他线程协助推进。

```cpp
// 教学示意：MS-queue 的 enqueue 骨架（不参与构建）
void enqueue(T const& data) {
    node* new_node = new node(data);
    node* old_tail = tail.load();
    for (;;) {
        node* next = old_tail->next.load();
        if (old_tail == tail.load()) {
            if (next == nullptr) {                       // 尾节点确实是最后一个
                if (old_tail->next.compare_exchange_weak(next, new_node)) break;
            } else {                                     // tail 落后了，先协助推进
                tail.compare_exchange_weak(old_tail, next);
            }
        }
    }
    tail.compare_exchange_weak(old_tail, new_node);      // 最后更新尾指针
}
```

### 7.3 编写无锁代码的四条原则

1. **先用 `seq_cst` 做原型**：把它写对、跑通，再谈放松；正确性永远先于性能。
2. **必须配套无锁内存回收方案**：hazard pointer、epoch-based reclamation 或引用计数，缺一不可。
3. **务必防范 ABA**：地址复用会让「值相等」谎报安全，可用带标记的指针（tagged pointer）或双字 CAS 缓解。
4. **把忙等循环改成协助**：发现别人卡在中间状态时，帮他推进一步，而不是空转等待。

## 版本演进

| 版本 | 变化 |
| --- | --- |
| C++11 | `compare_exchange_weak`/`strong`、`std::atomic<T*>`、`is_lock_free()` 让无锁代码首次可移植 |
| C++17 | 明确不鼓励依赖 `consume`；`is_always_lock_free` 成为静态检查手段 |
| C++20 | `atomic::wait/notify` 取代手写的忙等；`atomic_ref` 让普通变量获得原子操作 |
| C++23 | `atomic::compare_exchange` 的 `failure` 序可以更自然地书写；并发 TS 继续推进回收设施 |
| C++26 | 预计引入 `std::hazard_pointer` 与 RCU，**本书最难的一节终于有标准库答案** |

## 近年研究与工业界开源实践

- **回收方案进入标准库**：P0566 等提案推动 hazard pointer 与 RCU 进入 C++26，届时本章 7.2.3 可大幅简化。
- **ABA 的硬件背景变化**：Arm LSE 普及后程序更容易跑在弱序机器上；同时 Intel 的 TSX/HTM 退场（2019–2021 的多次微码与架构调整），事务内存的硬件路线基本停摆。
- **无झ锁队列的工程首选**：绝大多数项目直接使用成熟实现，而非手写 Treiber 或 MS-queue。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「无锁一定比加锁快」 | 低竞争下单线程版本更快；无锁的收益体现在高竞争与不可抢占场景 |
| 2 | 「CAS 没有循环也没关系」 | 只要用 `compare_exchange_weak`，就必须循环，因为允许虚假失败 |
| 3 | 「释放节点前没人用了」 | 别的线程可能正持有该指针，必须用 hazard pointer 或 epoch 方案回收 |
| 4 | 「地址没变就万事大吉」 | ABA 问题：地址可能被释放后重新分配，需用带标记的指针或版本计数 |
| 5 | 「CAS 失败时应该用 strong 版本简化」 | strong 不解决虚假失败之外的竞争，反而可能付出重试成本 |
| 6 | 🔧 本书的手写忙等可以有更好选择 | C++20 的 `atomic::wait/notify` 会像 futex 那样让线程休眠，优于空转自旋 |
| 7 | 🔧 本书回收方案需重写 | C++26 有望提供 `std::hazard_pointer` 与 RCU 的标准实现 |
| 8 | 🔧 本书未强调 `consume` 已被弃用 | 2026 年只用 `seq_cst` 与 acquire/release 两类即可 |
| 9 | 🔧 硬件事务内存不再可依赖 | TSX 已在消费级处理器上被禁用，相关的乐观重试写法需要审查 |
