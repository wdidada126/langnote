# 第 8 章 设计并发代码

> **一句话**：设计并发代码的起点不是「多开几个线程」，而是**先把问题切成互不干扰的部分**——切分方式直接决定后面所有性能的上限。

## 核心精讲

### 8.1 三种切分任务的方式

| 方式 | 适合 | 反面例子 |
| --- | --- | --- |
| **先分数据** | 数量固定、元素彼此独立（矩阵、数组） | 块大小不均导致负载失衡 |
| **递归划分** | 问题本身可二分（排序、归并、搜索） | 递归过深导致任务过碎 |
| **按工作类别** | 流水线、事件循环、角色化线程 | 类别间耦合会退化成共享锁 |

先分数据最简单；块间工作量差异很大时应改用递归划分。**每线程 4 个任务是经验值**：太少则启动开销占比高，太多则失衡概率上升。

```cpp
// 教学示意：先分数据，用颗粒度下限防止任务过碎（不参与构建）
template<typename Iter, typename Func>
void parallel_for_each(Iter first, Iter last, Func f) {
    const unsigned n = std::thread::hardware_concurrency();
    const std::size_t g = std::max<std::size_t>(n, std::distance(first, last) / (4 * n));
    for (auto it = first; it != last; it += g) {     // 按值捕获区间，避免悬垂
        std::thread t([=] { std::for_each(it, std::min(it + g, last), f); });
        t.join();                                    // 异常需另做传播，见 8.4
    }
}
```

### 8.2 影响性能的五个因素

- **处理器数量**：并行度超过核数后多余线程只增加开销；CPU 密集取物理核数，IO 密集可适当超订。
- **cache ping-pong**：两个核反复抢夺**同一条 cache line**，一致性协议迫使他们来回往返，可能比串行还慢。**伪共享**是它最常见的原因——两个毫无逻辑关系的变量恰好同处一条 cache line。
- **数据紧凑度**：把热数据放进连续内存（SoA 而非 AoS），一次 cache miss 换来一批数据。
- **过度任务切换与线程过饱和**：线程远超可运行核数时，时间被切碎，锁与条件变量开销成倍放大。

```cpp
// 教学示意：伪共享——两个独立计数器互拖累（不参与构建）
struct cell { std::atomic<long> hits{0}; std::atomic<long> misses{0}; };  // ❌ 同一条 cache line
struct alignas(std::hardware_destructive_interference_size) cell_padded { // ✅ C++17 起
    std::atomic<long> hits{0}; std::atomic<long> misses{0}; };  // 各自独占一条
};
```

`std::hardware_destructive_interference_size`（C++17，通常 64 或 128 字节）是标准给出的**保守上界**。**不要对每个原子量都填充**——那会显著增大对象体积、降低整体缓存命中率；只对确实被不同线程同时写的变量隔离。

### 8.3 按访问模式设计结构

| 访问模式 | 症状 | 对应结构 |
| --- | --- | --- |
| 读多写少 | 写者饥饿 | `shared_mutex`（第 6 章）或读写分离的版本控制 |
| 多写同一区域 | cache line 争用 | 私有副本 + 阶段汇总（即 8.2 的数据分块） |

### 8.4 异常安全与四个设计目标

子线程的异常若无人接管就 `std::terminate`；若被吞掉，调用方一无所知。正确做法是**收集后在主线程重抛**。

```cpp
// 教学示意：用 std::exception_ptr 在并行算法里传播异常（不参与构建）
template<typename Iter, typename Func>
void parallel_for_each_ex(Iter first, Iter last, Func f) {
    std::exception_ptr error;
    std::mutex err_mutex;                                       // 保护 error
    const std::size_t g = std::max<std::size_t>(1,
        std::distance(first, last) / (4 * std::thread::hardware_concurrency()));
    std::vector<std::thread> threads;
    for (auto it = first; it != last; it += g) {
        threads.emplace_back([=] {
            try { std::for_each(it, std::min(it + g, last), f); }
            catch (...) {                                       // 抓取并类型擦除
                std::lock_guard<std::mutex> lock(err_mutex);
                if (!error) error = std::current_exception();    // 只保留第一个
            }
        });
    }
    for (auto& t : threads) { if (t.joinable()) t.join(); }      // 析构前必须 join
    if (error) std::rethrow_exception(error);                    // 主线程统一重抛
}
```

`std::current_exception()` 在 `catch (...)` 里抓取异常，得到**类型擦除的安全引用**；`std::rethrow_exception` 会在调用现场**重建原类型**。用 `future` 更短：异常塞进 `promise`，`future.get()` 时自动重抛。

**Amdahl vs Gustafson**：两者对串行部分的处理完全不同，结论能差好几倍（取串行比例 `s = 0.1`）。

| 加速比 | N=2 | N=4 | N=8 | N=16 |
| --- | --- | --- | --- | --- |
| Amdahl `1/(s+(1-s)/N)` | 1.82× | 3.08× | 4.71× | 6.40× |
| Gustafson `s+N·(1-s)` | 1.9× | 3.7× | 7.3× | 14.5× |

Amdahl 假设**问题规模固定**，加速比被串行部分卡死，8 核只剩 4.7 倍；Gustafson 假设**问题规模随机器一起变大**，串行部分被摊薄，16 核可到 14.5 倍。**用 Amdahl 标上界、用 Gustafson 推目标**——批处理与离线计算若能随数据量增长，放宽串行比例比死磕常数更划算。

**用并发隐藏等待**：一个线程等 IO、另一个继续计算，总延迟接近 `max(等待, 计算)` 而非二者之和——这是单核上并发仍值得做的主要理由。**改进响应能力**：只影响延迟与观感，与吞吐无关。

### 8.5 并行版标准算法

| 算法 | 划分方式 | 关键约束 |
| --- | --- | --- |
| `for_each` | 整除划分，每块一个任务 | 谓词必须无副作用、可拷贝，块间不共享可写状态 |
| `find` | 逐块搜索 | 命中后要能中止其余任务 |

```cpp
// 教学示意：并行 find——逐块搜索，命中即停（不参与构建）
template<typename Iter, typename Pred>
Iter parallel_find(Iter first, Iter last, Pred p) {
    const std::size_t g = std::max<std::size_t>(1, std::distance(first, last) / 1024);
    Iter result = last;
    std::mutex m;
    for (auto it = first; it != last; it += g) {
        auto end = std::min(it + g, last);
        Iter hit = std::find_if(it, end, p);
        if (hit != end) {
            std::lock_guard<std::mutex> lock(m);
            if (result == last) result = hit;    // 只留最靠前的一个
        }
    }
    return result;                                // 未命中返回 last
}
```

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「线程数 = `hardware_concurrency()` 就最优」 | 只适用纯 CPU 且零同步的场景；有锁与 IO 时应实测，通常更少 |
| 2 | 「任务切得越碎越均衡」 | 过碎会带来调度与同步开销，应保留颗粒度下限 |
| 3 | 「子线程抛异常会被自动传播」 | 不接管就 `std::terminate`；请用 `exception_ptr` 或 `future` |
| 4 | 🔧 本书未把伪共享列为独立小节 | 今日工业实践普遍要求对热点写变量做 `alignas` 隔离或数据分块 |
| 5 | 🔧 本书 8.5 手写并行算法已非首选 | 应优先使用第 10 章的执行策略，或 oneTBB 这类成熟实现 |
