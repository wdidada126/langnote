# 第 11 章 多线程应用的测试和除错

> **一句话**：多线程代码最难的不是「测出来」，而是**「测过」这个词本身就没有意义**——并发缺陷是概率性的，跑通一次只说明恰好没踩中那一条交错。

## 核心精讲

### 11.1 两类问题

| 类别 | 表现 | 代价 | 典型成因 |
| --- | --- | --- | --- |
| **多余阻塞** | 明明不需要等待却在阻塞，吞吐上不去 | 慢 | 锁范围过大、持锁做 IO、临界区里调慢函数、忙等自旋、无谓的 `join` |
| **条件竞争** | 数据竞争、丢失更新、死锁、活锁、惊群 | 错（含崩溃与静默的数据损坏） | check-then-act、共享可变状态缺同步、锁序不一致、丢失唤醒 |

**多余阻塞往往不是性能问题，而是设计问题**——它说明「哪些操作之间根本不该有依赖关系」没想清楚；条件竞争则几乎总是「不变式在某个线程看不见的状态下被破坏」。

### 11.2 测试与除错的方法

#### 11.2.1 代码审查：最便宜也最有效

集中找四类东西：**隐式共享**（两个回调都通过 `this` 拿到同一个成员，代码里却看不出共享意图）；**锁序不一致**（A 先 `m1` 后 `m2`、B 反过来，这不是「还没出问题」而是「迟早出问题」）；**在临界区里回调外部代码**（外部可能反手请求另一把锁）；**「不加锁更方便」的地方**（把只在构造期写入的成员留给多线程读写，是最常见的静默损坏源）。

#### 11.2.2 用测试定位

拿到偶发失败的标准动作：**先把它变少，再把它变小**。先加大数据量与线程数提高复现率；一旦稳定复现，就删掉无关逻辑，直到代码薄到只剩那一个竞态。

#### 11.2.3 设计可测试的代码

把「做什么」与「在哪个线程做」彻底分开，让并发只存在于一层薄薄的适配代码里：

```cpp
// 教学示意：逻辑与线程解耦，核心函数单线程可测（不参与构建）
int compute_pipeline(const stage_input& in, const progress_callback& cb);   // 纯逻辑
void start_background(const stage_input& in, const progress_callback& cb) {  // 薄适配层
    std::jthread t([=] {                     // 并发只发生在这几行
        on_finished(compute_pipeline(in, cb));   // 回调继续是单线程语义
    });
}
```

配套手段：把时间源、线程工厂、随机源都做成可注入接口（测试时换成 `test_clock`、同步线程工厂），连「等待 100 毫秒」这种依赖都能被消除。

#### 11.2.4 多线程测试技术

| 手段 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 压力测试（重复跑 N 次） | 遇到过的交错是安全的 | **几乎什么都没证明** |
| 定向交错（用屏障强制线程汇合） | 特定交错确实安全（常能找出真 bug） | 覆盖不到自然发生的其他交错 |
| 静态分析（Clang `-Wthread-safety`） | 锁的获取/释放与数据访问合规 | 逻辑错误与跨函数不变式 |
| 动态检测（TSan，见 11.3） | 已执行的路径上不存在数据竞争 | 未执行路径、逻辑竞争、死锁 |

#### 11.2.6 性能回归测试

并发引入的「变慢」（多一层锁、多一次原子写）和「变错」一样需要防回归。

```cpp
// 教学示意：基准测试作为回归防线（不参与构建）
static void BM_parallel_pipeline(benchmark::State& s) {
    for (auto _ : s) { run_pipeline(); }
}
BENCHMARK(BM_parallel_pipeline)->Iterations(1000);
// 与基线对比，超过阈值即判定失败；CI 上固定机器并关闭频率缩放
```

**为什么压力测试不等于「已测试」**：交错空间随线程数与同步点数**指数增长**，重复运行只是对这个巨大空间做随机采样。粗算一下——假设某缺陷只在某些特定交错下出现，每次运行命中概率万分之一：

| 运行次数 | 至少命中一次的概率 |
| --- | --- |
| 10 000 | 约 **63%** |
| 23 000 | 约 **90%** |

也就是说，**跑 1000 次仍有九成概率与它擦肩而过**。重复运行只能提高信心，不能给出证明：「跑了三天没崩」从来不是并发代码通过测试的证据。

### 11.3 ThreadSanitizer：原理与读法

编译：`clang++ -fsanitize=thread -fno-omit-frame-pointer -O1 -g`；运行时约慢 5 至 15 倍、内存开销数倍。运行期常用 `TSAN_OPTIONS="halt_on_error=1 history_size=7"` 让第一次违规就停下，避免被报告刷屏。

**检测原理：happens-before + 向量时钟。** TSan 不去猜两条访问是否冲突，而是给每个内存位置记下「访问过它的线程与顺序」：

1. 每个线程携带一个**向量时钟**（长度等于活跃线程数，记录该线程已知的「别的线程各自完成到哪一步」）。
2. 每次同步（互斥的加锁/解锁、带 release/acquire 的原子、线程创建与 `join`、通道收发）按规则**合并**向量时钟，从而建立**先行关系（happens-before）**。
3. 两条记录来自不同线程、访问同一位置、至少一条是写、且**不构成 happens-before**——判定为数据竞争，立即报出。

一句话概括：**TSan 判断的不是「两条访问是否巧合地同时发生」，而是「两条访问之间是否建立了因果关系」**——这正是第 5 章的 happens-before 在工具层面的落地。

**怎么读报告：**

```
WARNING: ThreadSanitizer: data race (pid=40123)
  Write of size 4 at 0x7b0400000f10 by thread T2:   #0 worker() /src/app.cpp:42
  Previous read of size 4 at 0x7b0400000f10 by thread T3:   #0 consumer() /src/app.cpp:88
  Location is heap block of size 64 allocated by main thread:   #0 operator new /src/app.cpp:20
  Mutex M0 created at:   #0 main /src/app.cpp:15
```

读的次序：**先看两个栈与行号**（定位共享的那个对象），**再看 Location**（确认没误判到别的内存），**再看同步原语段**（TSan 会指出它认为本该保护这段访问的锁；这里空着或指错，通常就是真 bug）。

**局限（必须知道）：**

| 局限 | 说明 |
| --- | --- |
| 只覆盖**实际执行到**的代码 | 未跑到的分支永远检测不到 |
| 每字只保留 4 条历史记录 | 访问者过多会挤出旧记录，可能漏报 |
| 有假阳性 / 不检测死锁 | 后者需单独开启死锁检测，结果同样不完整 |

## 版本演进

| 阶段 | 关键变化 |
| --- | --- |
| C++11 / 2011 | 内存模型落地，**数据竞争才有明确定义**，TSan 之类的工具才有了判定依据 |
| 工具（2012） | TSan v2 在 ISSTA 提出，基于 C++11 原子与 happens-before |
| C++17 / 2017 | 并行算法与执行策略写进标准，「哪些操作并行合法」有了合规边界 |
| C++20 / 2020 | `atomic::wait/notify`、`jthread`、`stop_token` 减少手写忙等，从源头消除一类阻塞型缺陷 |

## 近年研究与工业界开源实践（2015–2026）

- **TSan 成为 CI 标配**：开源项目的流水线里 `-fsanitize=thread` 与 `-fsanitize=address` 已是标准配置，配合 `history_size` 调优后误报率显著下降。
- **Dsan 接棒 MemorySanitizer**：2023 年开源的 DataSanitizer 用位级影子内存换取更快速度与更少误报。
- **认知转向**：行业逐渐接受「并发测试是概率性验证」，因此更看重**可复现的交错构造**与重放工具，而不是无脑加跑次数。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「压力测试跑了几天没崩，说明没问题」 | 交错空间指数大，重复运行只是随机采样；见 11.2.4 的计数 |
| 2 | 「TSan 没报就是没有竞争」 | 它只检测**实际执行到**的路径，且有影子记录条数上限 |
| 6 | 🔧 本书的 TSan 篇幅偏少 | 2026 年的标准动作是把 `-fsanitize=thread` 放进 CI，并配合 `TSAN_OPTIONS` 调优 |
