# 第 6 章 基于锁的并发数据结构

> **一句话**：设计并发数据结构时，**先想清「哪些组合操作必须原子」，再谈锁的粒度**；接口长错了，锁再细也救不回来。

## 核心精讲

### 6.1 并发设计的内涵：三个先决问题

动手之前必须先回答三件事：

1. **哪些操作组合必须原子**？（例如「取出并删除」必须是一个操作，不能拆。）
2. **需要提供什么级别的线程安全保证**？（是否要求线性一致，是否允许遍历时看到不一致的中间态。）
3. **真实的访问模式是什么**？（读多写少、读少写多、还是均匀混合。）

由此得到两条铁律：

- **先保证安全**：为数据结构定义清晰的**不变式**（invariant），保证每个成员函数退出时都成立。
- **再发掘并发**：识别彼此无关的操作路径，让它们走不同的锁。

> 收益并不一定来自「把锁变细」。若临界区本身只有几十纳秒，细化带来的复杂度与死锁风险远大于收益。

### 6.2.1 线程安全栈

```cpp
// 教学示意：线程安全栈（不参与构建）
template <typename T>
class threadsafe_stack {
    std::stack<T> data;
    mutable std::mutex m;
public:
    void push(T value) {
        std::lock_guard<std::mutex> lock(m);
        data.push(std::move(value));
    }
    std::optional<T> pop() {                        // C++17：用 optional 表达「空」
        std::lock_guard<std::mutex> lock(m);
        if (data.empty()) return std::nullopt;
        std::optional<T> res(std::move(data.top())); // 若构造失败，元素不会被丢掉
        data.pop();
        return res;
    }
};
```

**为什么 `std::optional` 优于 `std::shared_ptr`**：后者每次 `pop` 都在堆上分配，仅仅为了表达「可能为空」；前者按值返回，零额外分配，语义也直白得多。

### 6.2.2 接口级竞争：`empty()` 加 `pop()`

```cpp
// 教学示意：看似无害，实则错误（不参与构建）
if (!s.empty()) {       // 1) 此刻非空
    auto v = s.pop();   // 2) 但到这里可能已被别的线程取空
}
```

修法只有一个方向：**把判断与取用合并成单一操作**（返回 `optional`、抛异常，或写入出参后返回 `bool`）。任何「先查状态、后做动作」的两段式接口都有这类问题。

### 6.2.3 带条件变量的队列

```cpp
// 教学示意：mutex 加 condition_variable 的阻塞队列（不参与构建）
void wait_and_pop(T& value) {
    std::unique_lock<std::mutex> lock(m);
    cv.wait(lock, [this] { return !data.empty(); });  // 谓词循环：抵挡虚假唤醒
    value = std::move(data.front());
    data.pop();
}
void push(T value) {
    { std::lock_guard<std::mutex> lock(m);
      data.push(std::move(value)); }
    cv.notify_one();                                  // 先解锁再通知，避免被唤醒线程二次阻塞
}
```

### 6.2.4 精细粒度锁队列：虚拟节点

核心技巧是引入一个**虚拟节点（dummy node）**，使 `push` 落在 `tail` 锁、`pop` 落在 `head` 锁，两条路径互不阻塞。

```cpp
// 教学示意：head 与 tail 各持一把锁的骨架（不参与构建）
struct node { std::shared_ptr<T> data; std::unique_ptr<node> next; };
std::unique_ptr<node> head;
node* tail;
mutable std::mutex head_mutex, tail_mutex;

node* get_tail() { std::lock_guard<std::mutex> l(tail_mutex); return tail; }
```

注意 `pop` 常需先锁 `head_mutex` 判空、再锁 `tail_mutex` 取尾，此时**加锁次序必须全局一致**，否则正好凑齐第 3 章的死锁四条件。

### 6.3.1 线程安全查找表：从一把锁到哈希分段

| 方案 | 并发度 | 代价 |
| --- | --- | --- |
| `std::map` 加一把锁 | 1 | 实现最简，读写全串行 |
| 哈希分段（bucket striping） | 约等于桶数 | 桶数固定则扩容困难；无法原子地取全表快照 |
| 每桶一把 `shared_mutex` | 桶数乘读端并行 | 读多写少时收益最大 |

要点：桶数宜取**质数**，哈希函数要能把输入打散；而「取整表快照」必须**同时持有全部桶锁**，代价回到一把锁——这正是「先定原子边界」的意义所在。

### 6.3.2 线程安全链表：手递手锁耦合

遍历规则是：先拿到下一个节点的锁，再释放当前节点的锁，因此始终至少持有一把锁，不会跳到已被删除的节点上。该技巧在数据库文献中称为 **lock coupling**，在 B 树并发控制（Bayer 与 Schkolnick 1977）里早已成熟。

> **2026 年的现实**：Linux 内核与众多工业代码库中，这类遍历已被 **RCU（read-copy-update）** 取代：读者完全不加锁，写者延迟回收旧版本，伸缩性远优于锁耦合。

## 版本演进

| 版本 | 变化 |
| --- | --- |
| C++11 | `std::mutex`、`lock_guard`、`unique_lock`、`condition_variable` 齐备，本章代码全部可写 |
| C++14 | `std::shared_timed_mutex`：读写锁正式可用 |
| C++17 | `std::optional`（替代 `shared_ptr` 表达空）、`std::shared_mutex`、`scoped_lock`（一次锁多把而不必担心次序） |
| C++20 | `jthread` 与 `stop_token` 让阻塞等待可取消；`latch`、`barrier` 简化分片任务的汇聚 |
| C++23/26 | TSan 进入常规 CI；C++26 有望把 hazard pointer 与 RCU 纳入标准库，改写 6.3.2 的取舍 |

## 近年研究与工业界开源实践

- **RCU 走出内核**：liburcu 把 RCU 带入用户态 C/C++；folly 与 Linux 内核的链表遍历均已 RCU 化。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「逐个成员变量加锁就是线程安全」 | 跨变量的不变式仍无保护，应以「操作」而非「成员」为单位加锁 |
| 2 | 「锁越细越快」 | 细粒度锁改善的是争用，却抬高复杂度与死锁概率；先用剖析器确认瓶颈 |
| 3 | 「`empty()` 为真后就能安全 `pop()`」 | 典型接口级竞争，必须合并为单一操作 |
| 4 | 「分段哈希能原子地取全表快照」 | 必须锁住全部分片，代价与一把锁相同 |
| 5 | 🔧 本书的阻塞队列无法取消等待 | C++20 的 `jthread` 加 `stop_token` 已能让 `wait_and_pop` 响应停止请求 |
| 6 | 🔧 本章未提伪共享与缓存乒乓 | 见第 8 章 8.2；两把相邻的 `mutex` 若落在同一 cache line 上同样互相拖累 |
| 7 | 🔧 手递手锁耦合已非唯一答案 | RCU、hazard pointer 与有望进入 C++26 的 `std::hazard_pointer` 在多数遍历场景更优 |
| 8 | 🔧 用 `shared_ptr` 表达「空」有额外开销 | 优先用 `std::optional<T>`（C++17），需要携带错误信息时用 `std::expected`（C++23） |
