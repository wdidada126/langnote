# 第 9 章 高级线程管理

> **一句话**：管线程的核心命题是**「谁来等谁」**——线程池解决「反复创建线程的开销」，中断机制解决「等得起但走不掉」的问题。

## 核心精讲

### 9.1 线程池

创建线程要分配内核栈、进入调度器、首次访存几乎全是 miss；池化的代价是**必须解决任务依赖**。

**(1) 最简实现**：一个任务队列加 N 个工作线程。

```cpp
// 教学示意：最简线程池骨架——一个队列加 N 个工作线程（不参与构建）
class thread_pool {
    std::queue<std::function<void()>> tasks;
    std::mutex m;                                  // 等待条件须被同一把锁保护
    std::condition_variable cv;                    // 无任务则睡，有任务或被关闭则醒
    std::vector<std::thread> workers;
    bool stop_flag = false;
public:
    explicit thread_pool(unsigned n = std::thread::hardware_concurrency());
    void run_tasks();                              // cv.wait 谓词：stop_flag || !tasks.empty()
    template<typename F> void submit(F f);         // 加锁入队，解锁后 notify_one
    ~thread_pool();                                // 置停止标志 → notify_all → join 全部
};```

**(2) 等待任务完成 / 用 `future` 拿返回值**：把任务包成 `packaged_task`，返回值自动落到 `future` 上。

```cpp
// 教学示意：线程池与 future 组合——提交任务并等待结果（不参与构建）
int compute(int x) { return x * x; }
void demo(thread_pool& pool) {
    auto task = std::make_packaged_task(compute);
    std::future<int> fut = task->get_future();
    pool.submit([task = std::move(task)] { (*task)(21); });  // 任务内部设置 promise
    int result = fut.get();      // 阻塞直到完成；异常也在这里重新抛出
}
```

`std::promise` 手动版更灵活：任务尚未执行就能先拿到 `future`，用于设置超时或提前取消。**(3) 等待其他任务**有三种做法：`future` 存进 `vector` 再逐个 `get()`；用 C++20 的 `std::latch` 或 `std::barrier`（第 4 章）；或让子任务向主任务的 promise 汇聚。

**(4) 避免队列竞争**：全局单队列下所有线程抢同一把锁，线程越多争用越严重。要么**每线程一个队列**（工作线程 99% 只碰自己的），要么让提交者指定目标线程以彻底消除竞争，要么批量提交（stride）摊薄加锁成本，要么用第 7 章的无锁队列去掉互斥（内存回收仍需 hazard pointer 一类机制）。

**(5) 任务窃取**：现代运行时的标配。每个线程一个**双端队列**——本线程从**队首**取（刚来的局部性好），其他线程从**队尾**偷（与主人的冲突面最小）；偷不到时随机启发式地远离自己，最后才回落阻塞等待。

```cpp
// 教学示意：任务窃取的工作循环骨架（不参与构建）
void worker_loop(queue& mine, std::vector<queue>& all) {
    while (!done) {
        task t;                                                   // 1) 先干自己的
        if (mine.try_pop_front(t)) { t(); continue; }
        if (steal_from_others(all, mine, t)) { t(); continue; }   // 2) 从队尾偷
        mine.wait_for_work();                                     // 3) 都干了，去等
    }
}
```

> **先给每个线程喂饱自己，再让空闲的去偷。** 这层通常不必自己写——`uxlfoundation/oneTBB` 与 `boostorg/boost` 已有成熟实现。

### 9.2 中断线程

标准 C++ 没有强制型线程终止（`pthread_cancel` 不在标准里），唯一可行的是**协作式取消**：被取消的线程必须自己检查标志并退出。

**(1) 用 `future` 与条件变量配合**：把「取消请求」与「任务完成」当作两个条件，用同一把锁保护，谓词循环等待二者之一。

```cpp
// 教学示意：future 与条件变量配合的可中断等待（不参与构建）
std::mutex m;
std::condition_variable cv;
bool finished = false, cancelled = false;
std::thread worker([&] {
    std::unique_lock<std::mutex> lock(m);
    cv.wait(lock, [&] { return finished || cancelled; });  // 谓词在锁内检查
    if (cancelled) { /* 收拾现场，安全退出 */ }
});
void shutdown() {
    { std::lock_guard<std::mutex> lock(m); cancelled = true; }
    cv.notify_all();      // 必须通知，否则等待者可能永远睡下去
    worker.join();
}
```

`future` 路线更轻：用一个 `promise<void>` 表示「任务结束」，等待方 `future.wait_for(timeout)` 判断是超时还是就绪，超时就自行置取消标志。**(2) 检测中断**不要让检查散落各处——要么用 `thread_local` 的 `interrupt_flag`（`interruptible_thread` 构造时登记自己，适合「任意阻塞点都可打断」的通用库），要么用 C++20 `jthread` 自动传入的 `stop_token`（新代码的默认选择）。

**(3) 为什么 `condition_variable` 要 `unique_lock`，而 `condition_variable_any` 几乎没人用？**

`cv.wait(lk)` 的语义是：**原子地释放锁并进入等待**，被唤醒后**重新获得锁**再返回。因此它要求的锁必须能被显式解锁并再次锁定：`lock_guard` 不满足（它只能在构造与析构时加解锁，没有「中途放开再拿回来」的接口），`unique_lock` 才提供完整的 `lock()` / `unlock()` 控制权。`condition_variable_any` 把约束放松成「任何满足 `BasicLockable` 的类型」，代价是实打实的：

| 维度 | `condition_variable` | `condition_variable_any` |
| --- | --- | --- |
| 锁要求 | 必须 `unique_lock<mutex>` | 任意 `BasicLockable` |
| 典型开销 | 与底层 futex 直接对应 | 内部需额外包装与共享状态，每次 `wait` 都可能涉及堆分配 |

**2026 年的答案**：`cv_any` 的通用性需求，绝大多数已被 C++20 的另一组设施替代——`std::atomic::wait/notify` 允许等原子量变化而不必持锁，`std::latch` / `std::barrier` 覆盖「等一批任务」。自定义锁加自定义等待，在标准库里已不需要 `cv_any`。

**(4) 应用退出时中断后台任务**：退出路径必须确定性，否则就是资源泄漏与随机崩溃。

```cpp
// 教学示意：应用退出时中断后台任务（不参与构建）
void application_main() {
    std::jthread background([](std::stop_token st) {   // 析构时自动 request_stop + join
        while (!st.stop_requested()) {
            try { background_work(st); }
            catch (const std::exception& e) { log(e); }
        }
    });
    do_the_real_work();          // 离作用域即触发取消与 join
}
```

三条纪律：**先置标志、再 notify、后 join**（顺序颠倒就丢唤醒）；**取消必须是协作式**，长循环里要定期检查；**析构路径上别让任务突然消失**，给它机会释放资源。

### 9.3 小结

- 线程池的收益来自「复用线程、限制并发度」，代价是「任务依赖与取消」必须自己解决。
- 等待三种正确姿势：`future`（一次性结果）、条件变量（等条件）、`latch`/`barrier`（等一批）；取消只有一种：标志、通知、检查。

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| C++11 | 线程池所需零件齐备（线程、互斥、条件变量、`future`），但**没有可直接用的池** |
| C++17 | 并行算法、`scoped_lock`、`hardware_destructive_interference_size` |
| C++20 | **`jthread` + `stop_token` + `latch`/`barrier`/`semaphore`**：协作式取消进入标准 |
| C++26 | 以 `std::execution`（P2300）为核心的执行器仍在推进，「把任务交给谁执行」有望部分取代自研线程池 |
