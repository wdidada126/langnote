# 第 3 章 在线程间共享数据

> **一句话**：保护共享数据不是「加一把锁」就完事——**真正在出错的往往是接口设计**（返回引用、多步操作），而不是缺了一把锁。

## 核心精讲

### 3.1 条件竞争的本质

竞争的结果依赖于**线程执行的相对时序**。良性竞争（例如两个线程往队列里放任务）无害；恶性竞争（例如两个线程同时 `pop` 同一个元素）必须消除。

### 3.2 接口固有的竞争（本书最精彩的一节）

```cpp
// 教学示意：一个「看起来线程安全」却没用的栈（不参与构建）
template<typename T>
class threadsafe_stack_bad {
    std::stack<T> data;
    mutable std::mutex m;
public:
    T& top() { std::lock_guard l(m); return data.top(); }   // ❌ 返回引用
    void pop() { std::lock_guard l(m); data.pop(); }
};
```

问题不在锁，而在**接口把两个本应原子的操作拆开了**：

| 设计 | 是否安全 |
| --- | --- |
| `top()` 返回引用 + `pop()` | ❌ 引用可能在调用者使用之前失效 |
| `pop()` 返回 `T`（值） | 异常安全问题：拷贝构造抛异常会导致元素丢失 |
| `pop()` 返回 `shared_ptr<T>` | ✅ 常见做法 |
| `pop()` 返回 `std::optional<T>`（或用「输出参数 + 返回值」双接口） | ✅ C++17 后更推荐 |
| 组合成 `pop_if_nonempty()` | ✅ 消除 check-then-act |

> 这一节的真正价值：**用类型系统表达「原子操作」，而不是让调用者自己去拼；这条原则在所有语言都成立。**

### 3.3 死锁的四个必要条件

1. 互斥；
2. 持有并等待；
3. 不可抢占；
4. **循环等待**。

打破任意一个即可。工程上最有效的是打破 4：**固定加锁顺序**。

```cpp
// 教学示意：一次性锁住多个互斥（不参与构建）
std::scoped_lock lock(m1, m2);        // C++17，等价于 std::lock + lock_guard，死锁安全
// C++11 写法：
// std::lock(m1, m2); std::lock_guard<std::mutex> l1(m1, std::adopt_lock), l2(m2, std::adopt_lock);
```

其它建议（本书 3.2.5）：

- 避免「持锁再调用用户代码」（层级锁 hierarchy_mutex 可静态检查违规）；
- 用 `unique_lock` 只在必要时加锁；
- 不要原子 concealing：一个操作内的多把锁要一次性获取。

### 3.4 其他工具

| 工具 | 场景 | 注意 |
| --- | --- | --- |
| `std::call_once` + `once_flag` | 惰性初始化（单例） | 比 DCL 安全且简洁；底层就是语言标准保证的版本 |
| `std::shared_mutex`（C++17） | 读多写少 | 写者饥饿风险；不要把读锁「升级」为写锁 |
| `std::recursive_mutex` | 极少使用；多用于结构不佳的回调 | 通常说明接口需要重构 |
| `std::atomic` | 计数器、标志位 | 见第 5 章 |

```cpp
// 教学示意：call_once（不参与构建）
std::shared_ptr<Resource> get_instance() {
    static std::shared_ptr<Resource> ptr;
    static std::once_flag flag;
    std::call_once(flag, [&]{ ptr = std::make_shared<Resource>(); });
    return ptr;
}
```

## 版本演进

| 版本 | 新增 |

## 近年研究与工业界开源实践

- **读多写少有了更好的选择**：2020 年代常用的做法是让读侧完全无锁（RCU / hazard pointer，见第 7 章）。
- **静态死锁检测进入 CI**：Clang 的 Thread Safety Analysis（`-Wthread-safety`）已成为生产项目的例行检查项。
- **上无锁之前先量化争用**：工业界的共识是先细化锁粒度，等到争用确实成为瓶颈再考虑无锁。

| 实现 | star | 说明 |
| --- | --- | --- |
| `facebook/folly` | ≈**30.5k★** | `folly::SharedMutex`（读写 + 自旋 + futex 混合），`folly::Synchronized`（把锁与被保护数据绑定，从类型上避免「忘了加锁」） |
| `llvm/llvm-project` | ≈**40.6k★** | Thread Safety Analysis（`-Wthread-safety`）的实现与文档范例 |
| `google/sanitizers` | ≈**12.5k★** | ThreadSanitizer：检测数据竞争与潜在死锁的事实标准 |

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「给每个成员函数加把锁就线程安全」 | 见 3.2：接口级竞争（check-then-act、返回引用）无法通过加锁成员函数解决 |
| 2 | 「`shared_mutex` 一定比 `mutex` 好」 | 写者会饥饿；临界区很短时读写锁自身的开销可能超过收益 |
| 3 | 「递归锁方便就多用」 | 通常说明应该拆分函数，而不是依赖可重入 |
| 4 | 「`call_once` 性能差」 | 现代实现有 DCL + acquire 的快速路径，开销极小 |
| 5 | 🔧 本书多用 `lock_guard` | 2026 年建议默认使用 `std::scoped_lock`（C++17，可变参数且死锁安全） |
| 6 | 🔧 本书未提静态检查 | 生产代码建议用 `GUARDED_BY` 注解让编译器代劳 |
