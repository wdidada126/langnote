# 第 10 章 并行算法函数

> **一句话**：C++17 把「并行」做成了**算法的一个参数**——但不同执行策略给出的保证强度差别巨大，用错策略不是变慢，而是 UB。

## 核心精讲

### 10.1 哪些标准库算法接受执行策略

| 类别 | 代表算法 | 并行时的额外要求 |
| --- | --- | --- |
| 逐个映射 | `for_each`、`for_each_n`、`transform` | 操作**只读取**元素，不得写进本容器 |
| 归约聚合 | `reduce`、`transform_reduce`、`count`、`count_if`、`min_element` | 二元操作必须**可交换、可结合** |
| 扫描 | `partial_sum`、`exclusive_scan`、`inclusive_scan` | 依赖链存在，实现内部做分段扫描 |
| 查找（短路） | `find`、`find_if`、`find_first_of`、`any_of`、`all_of` | 命中顺序不确定，只保证「存在即返回某个」 |
| 排序与分区 | `sort`、`stable_sort`、`nth_element` | **要求随机访问迭代器**，元素移动开销必须可控 |
| 非序列匹配 | `search`、`mismatch` | 比较顺序不确定，行为与单线程版一致 |

### 10.2 三种执行策略的语义差异

| 策略 | 别名 | 顺序保证 | 可否向量化 / 乱序 | 典型代价 |
| --- | --- | --- | --- | --- |
| `sequenced_policy` | `seq` | 严格按迭代器顺序，**不并行** | 允许（默认行为） | 最低 |
| `parallel_policy` | `par` | **元素间**不保证顺序，同一元素不被并发处理 | 否 | 线程间同步成本 |
| `parallel_unsequenced_policy` | `par_unseq` | 无顺序保证，**同一元素上的不同操作可交错** | **是**（SIMD、乱序） | 限制最多，最易踩雷 |

关键区别不在「快不快」，而在**你能依赖什么**。

```cpp
// 教学示意：执行策略的基本用法（不参与构建）
#include <execution>
#include <vector>
#include <algorithm>

std::vector<int> v = /* ... */;

std::for_each(std::execution::par, v.begin(), v.end(), [](int& x) {
    // x 由当前线程独占；不得触碰 v 的其他元素，也不得写外部容器
    x = x * x;
});

int total = std::reduce(std::execution::par, v.begin(), v.end(), 0,
                        [](int a, int b) { return a + b; });  // 必须满足结合律

std::sort(std::execution::par, v.begin(), v.end());           // 随机访问迭代器

std::vector<double> out(3);
std::transform(std::execution::par_unseq,                     // 元素类型需适合向量化
               v.begin(), v.end(), out.begin(),
               [](int x) { return x * 1.5; });
```

调用形式只有一处变化：**第一个参数插入执行策略对象**，其余签名与单线程版相同。实现（libstdc++ 的 TBB 后端、libc++、MSVC）会把区间按策略切给任务系统——这正是第 9 章线程池的用武之地。

### 10.3 使用范例与访问计数

**坑一：`for_each` 的谓词可以并发调用，绝不能改外部的随机容器。**

```cpp
// 教学示意：❌ 错误——并行写同一个 vector（不参与构建）
std::vector<int> work(1000);
std::vector<int> locations(1000, -1);

std::for_each(std::execution::par, work.begin(), work.end(), [&](int x) {
    locations[x] = compute(x);      // 多个元素可能映射到同一个下标
});
```

正确做法有四种，各有取舍：让算法把结果写进**输出迭代器**（最常见、最优）；用 `std::vector<std::atomic<int>>` 或互斥保护需就地写的场景；用 `transform_reduce` 直接聚合；或让每个任务写自己那一段输出块。

**坑二：`std::sort` 的并行版本有两个硬约束。** 一是**要求随机访问迭代器**——`std::list` 的双向迭代器不满足，编译期就会被挡住；二是**元素移动/拷贝开销必须可控**。深拷贝类型（含 `std::string`、`std::vector`）的并行 `sort` 可能比单线程更慢，因为搬移量被放大数倍。解决办法是**先排序索引，最后落地一次**：

```cpp
// 教学示意：对昂贵元素先排索引，再落地（不参与构建）
std::vector<std::pair<Key, Value>> expensive;
std::vector<std::size_t> idx(expensive.size());
std::iota(idx.begin(), idx.end(), 0);

std::sort(std::execution::par, idx.begin(), idx.end(),
          [&](std::size_t a, std::size_t b) { return expensive[a].key < expensive[b].key; });

std::vector<std::pair<Key, Value>> sorted;
sorted.reserve(expensive.size());
for (auto i : idx) sorted.push_back(std::move(expensive[i]));
```

**坑三：`par_unseq` 下的向量化与乱序执行。** 这是本章最容易写出 UB 的地方——它同时允许多线程、SIMD 向量化，以及**不按编写顺序执行同一元素上的操作**。由此：

- 谓词里不能**有数据依赖**：`x = f(x)` 在 `par_unseq` 下是错的；
- 谓词里**不能用互斥**：要拿锁就说明你不需要 `par_unseq`，改用 `par`；
- 谓词不能有顺序敏感的副作用（改全局计数器、写日志缓冲区）；
- 谓词必须**可重入且幂等**，或者干脆是纯函数。

**访问计数怎么写**：本节标题所说的「访问计数」，指的就是统计算法实际访问了什么。

```cpp
// 教学示意：用归约代替「并发共享计数器」（不参与构建）
long total = std::transform_reduce(              // ✅ 聚合到单值
    std::execution::par, v.begin(), v.end(), 0L,
    [](long acc, int x) { return acc + (x > 0 ? 1 : 0); },   // 一元操作
    [](long a, long b) { return a + b; });                   // 二元归约
```

> `par` 下确实可以用 `std::atomic` 计数器，但在 `par_unseq` 下它同样不安全——原子只保证单变量原子性，无法阻止同元素操作交错。**结论：计数交给 `transform_reduce` 归约，不要手动加共享计数器。**

## 版本演进

| 版本 | 变化 |
| --- | --- |
| C++11 | 无任何并行算法；`async` 是唯一的官方并行手段 |
| C++14 | 无并行算法 |
| C++17 | **并行算法与三种执行策略正式进入标准**（`<execution>` 与各算法的重载） |
| C++20 | 算法与执行策略重载继续扩充；`jthread` 让并行任务的取消更干净 |
| C++26 | 以 `std::execution`（P2300）为核心的**执行器**继续推进，「策略」有望被 sender/receiver 体系取代 |

## 近年研究与工业界开源实践（2015–2026）

- **实现质量成为主战场**：libstdc++ 用 TBB 作为 `par` 的后端，libc++ 与 MSVC 各补齐；同一份代码在不同编译器上的加速比可能差很多。
- **从「策略」到「执行器」**：P2300 的 sender/receiver 模型把「在哪执行、按什么顺序、怎么取消」拆成可组合的部分；GPU / SYCL 视角下 10.1 的算法分类直接对应 kernel 的 work-group 划分。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「给了 `par` 就能随便改容器」 | `for_each` 的谓词只能读元素；改主容器是数据竞争，见 10.3 反例 |
| 2 | 「`par` 下的原子计数器可以放心用」 | `par` 不能阻止同元素操作交错；计数请用 `transform_reduce` |
| 3 | 「所有容器都能并行 `sort`」 | 只有随机访问迭代器才行（`std::list` 不满足），且移动开销要可控 |
| 4 | 「并行 `sort` 一定更快」 | 元素移动开销大时反而更慢；昂贵元素应先排索引再落地 |
| 5 | 「`par` 等价于手写线程池」 | `par` 不保证用哪个线程、也不提供取消；取消仍需第 9 章的手段 |
| 6 | 🔧 本书对 `par_unseq` 的强调已偏保守 | 2026 年共识是**默认不要用它**；向量化收益通常小于约束风险 |
| 7 | 🔧 本书未提执行器的未来 | P2300 的 `std::execution` 会逐步取代「策略参数」这一形态 |
| 8 | 🔧 本书未说明厂商差异 | 同一段 `par` 代码在 libstdc++ 与 MSVC 上的加速比可能差数倍，必须实测 |
