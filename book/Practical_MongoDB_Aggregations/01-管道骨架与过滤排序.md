# 01 管道骨架与过滤排序——$match/$sort/$limit/$skip/$count

> 第 3 波 · #127《Practical MongoDB Aggregations》(Paul Done, Packt, 2024) 精读重构 · 章 1/8。
> 组织法声明：本册不冒造原书章号，按"阶段族→SQL 对照"组织（见 [00-总览与阅读地图.md](00-总览与阅读地图.md) 第二节）。
> 红线：MongoDB 不装不跑 ⚠️；🔧 仅指 SQLite/DuckDB 真跑的**语义复现**，非 mongod 行为。

## 1. 本章主题（本书承诺域 ⚠️ 推定 + 官方文档 ✅）

聚合管道是"文档流依次穿过一组阶段（stage）"的数据加工线：`db.coll.aggregate([ {$match…}, {$sort…}, {$limit…} ])`。骨架四件套 $match/$sort/$limit/$skip 与 $count 特例，恰好整体落在 SQL 的 `WHERE / ORDER BY / LIMIT / OFFSET` 投影里——这是本册"管道⇄SQL 主线演示"的起点族。

取证：管道概念与阶段列表 ✅ https://www.mongodb.com/docs/manual/core/aggregation-pipeline/ 、阶段索引 ✅ https://www.mongodb.com/docs/manual/reference/mql/aggregation-stages/ （两 URL 本环境 curl 200 实验）。mongod 的执行细节（如 $sort 内存上限 100MB 后溢盘 ⚠️）一律文档转述。

## 2. 逐阶段精读

### 2.1 $match —— 管道里的 WHERE

- 输入任意文档流，输出满足谓词子集；**尽量前置**是本书与官方手册共同的第一军规（前置才能吃到索引，见 [07-管道优化与执行剖析.md](07-管道优化与执行剖析.md)）。
- 谓词语言与 find 查询完全同源（$gt/$in/$regex/$expr…），这是 SQL 侧没有的"复用红利"：同一段过滤器在 find/aggregate/$lookup 子管道里三处通用。
- 与 SQL WHERE 的语义差 ⚠️：Mongo 比较跨 BSON 类型序（数字<字符串<文档…），缺字段等于"该字段不存在"而非 NULL——移植到 SQL 时缺字段陷阱会变形为 NULL 语义。

### 2.2 $sort/$limit/$skip —— Top-N 与分页

- `$sort:{total:-1}, $limit:3` = `ORDER BY total DESC LIMIT 3`，语义等价度近乎 1:1（见 🔧 Q11：两引擎与预期 Mongo 心智同序同值）。
- 等值排序的**平局不稳定**：$sort 与 SQL ORDER BY 同样不承诺平局次序，管道里要补 tie-breaker 键——本册演示数据以 _id 打散。
- $skip 是"先数再扔"：与 SQL OFFSET 同罪同罚，大偏移分页在两个世界都是反模式 ✅ https://www.mongodb.com/docs/manual/reference/operator/aggregation/match/ 语境转述 + SQLite/DuckDB 文档。
- $count 阶段 ≡ `SELECT count(*)`（单文档输出）；注意它与 $group{_id:null}+$sum 是同一件事的糖。

## 3. MQL⇄SQL 对照表（本章族）

| 管道 | SQLite 3.45.3 🔧 | DuckDB 1.5.5 🔧 | 语义备注 |
|---|---|---|---|
| [$match:{status:'A'}, $count:'n'] | `SELECT count(*) FROM orders WHERE status='A'` | 同左 | 完全等价 |
| [$sort:{ts:1}, $limit:N] | `ORDER BY ts LIMIT N` | 同左 | 平局不稳定两侧同病 |
| [$skip:M, $limit:N] | `LIMIT N OFFSET M` | `LIMIT N OFFSET M`（或 `ASOF/RESPECT NULLS` 无关） | 大 OFFSET 两侧同样线性代价 |
| find 谓词复用（$gt/$in） | `BETWEEN/IN` | 同左 | Mongo 类型序无 SQL 对应 ⚠️ |
| $match 于数组字段（elemMatch 心智） | `EXISTS (SELECT 1 FROM json_each(items)…)` | `… UNNEST …` | 半结构化谓词，见 03 |

## 3.5 逐步互译演练：一条管道拆成 SQL 的三块板

场景（对位演示数据集）："把 status='A' 的订单按金额从大到小取前 3 个客户"。

| 步 | MQL 阶段 | SQL 板 | 演示数据结果 🔧 |
|---|---|---|---|
| 1 | {$match:{status:'A'}} | WHERE | 100,081 行过筛（Q1） |
| 2 | {$addFields:{total:{$sum:"$items.subtotal"}}} | SELECT 计算列 | 归 02/03 章族 |
| 3 | {$group:{_id:'$cust', t:{$sum:'$total'}}} | GROUP BY | 5,000 组 |
| 4 | {$sort:{t:-1}, $limit:3} | ORDER BY + LIMIT | c3945/c1603/c3065（Q11） |

反面读法同样成立：给一条 SQL，先圈出 WHERE 板、GROUP 板、ORDER 板，再逐板回写 MQL 阶段——本书"Aggregation Schema"式思维（把管道当可复用模式来设计 ⚠️ 转述）在骨架族上的第一训练即此。

## 3.6 骨架族的历史谱系（为何 SQL 对照几乎无损）

- $match/$sort/$limit/$skip/$group 属聚合框架 **2.2（2012）** 初代十二操作符成员（对位册 [../MongoDB_The_Definitive_Guide_3e/04-聚合框架.md](../MongoDB_The_Definitive_Guide_3e/04-聚合框架.md) 的基线时代）；概念血统直接来自 SQL 的关系代数。
- $count（3.4）、$bucket（3.2）、$facet/$lookup（3.4/3.2）、$setWindowFields（5.0）是后来"补 SQL 作业"的阶段——本册后几章的对照密度递增正与该谱系同构：**越新的阶段，SQL 对应物越成熟**。
- 这解释本书副标题为何强调 "optimal pipelines"：骨架族没有发明新语义，考验的是**次序纪律**；分析族（05/06）才发明表达能力。

## 4. 🔧 实测组（SQL 引擎复现语义，非 mongod 行为；数据集见 00 第五节）

**Q1 match+count**（`WHERE status='A'`）
- SQLite：5.9ms → **100,081**（索引 ix_status 命中）
- DuckDB：4.9ms → **100,081**（一致 ✅）
- 解读：管道 $match 前置 ≡ SQL 谓词；两引擎行数互验，等价映射在本数据集上无损。

**Q11 Top-N**（先拆 items 算金额再取前 3 客户，见 03 的拆平写法）
- SQLite：710.2ms；DuckDB：123.2ms——**同序同值**：`c3945: 51,109.50 | c1603: 50,143.07 | c3065: 50,007.68`。
- 解读：$sort+$limit 的"全量算完再取头"心智与 SQL 一致；引擎时延差属存储/执行层，不改语义（性能议题归 [07-管道优化与执行剖析.md](07-管道优化与执行剖析.md)）。

**Q6 侧证**（distinct 客户计数，sqlite 293.1ms → 5,000）说明 $match 之后的 $group 骨架与 SQL 聚合栈的衔接：管道世界每一步都是"物化一个中间流"，SQL 世界允许优化器把多步折叠——这是两个查询语言最根本的气质差，本书反复强调的"阶段顺序敏感"正源于此。

**边界小对照（空输入语义）** 🔧：`SELECT count(*) FROM orders WHERE status='Z'` 在 SQLite/DuckDB 约 1ms 出一行 `0`；而管道 `$match 无命中 → $count` 输出**空流**（无文档可数即无输出文档 ⚠️ mongod 行为转述）。下游若假定"必有一行"，两世界会走出不同分支——移植时先测空集，这是 Q13"0 天/2 天"阈值实验暴露出的同类风险。

**排序平局实验** 🔧：对 `qty` 降序取 rank=1（Q8 第三组，SQLite 904.3ms → **28,003** 行并列头名）——$sort 平局不稳与 SQL rank() 并列语义在此同框：管道里"取每组最大值文档"需要 $sort+$group+$push 组合拳或改走 $setWindowFields（见 06），一条 ORDER BY+LIMIT 偷懒在两个世界都会拿走不确定的那一行。

## 5. 常见误区（转述社区高频问题 ⚠️ + 本册演示实证）

1. **把 $match 写在 $unwind 之后**：先拆 50 万行再过滤 10 万行，白拆。SQL 侧谓词下推会救你，管道侧优化器**只做有限的阶段重排**（$match 上提、$project 裁剪），别指望它等价于关系优化器 ⚠️。
2. **$skip 深分页**：10 万偏移的 $skip 与 SQL OFFSET 一样烧全前缀；游标式续页（记上页末键 + $match 范围）两边同方。
3. **$count 与 $group+$sum 混用无脑化**：$count 无法在空输入时输出 0 文档（SQL `count(*)` 恒出一行）——边界语义差 🔧 Q13 若阈值为 0 天，SQL 出 0、管道可能出空，对照时务必检查空集行为。
4. **忽略类型序**：`{status:'A'}` 在 Mongo 匹配字符串 'A'；同值在 SQLite TEXT 亲和下宽进严出，跨引擎移植时"看起来一样"不等于"一样"。
5. **$match 里写正则不打锚**：`{status:/^A/}` 可用索引范围，`{status:/A/}` 退化为全扫 ⚠️ 转述（官方 index-and-$regex 文档线）；SQL 的 `LIKE 'A%'` ⇄ `LIKE '%A%'` 同构，两世界的"前缀可索引"定律一致。
6. **把 $limit 当安全阀**：$limit 只减下游行数，不减上游排序/拆平成本；想真正省钱要往"更前置的 $match + 索引"里找（07 章主论点）。

## 8.6 骨架族的 BSON 细节清单（移植时逐条过）

- 数字：Int32/Int64/Double 在 $sort 比较时可跨类型（1 == 1.0）；SQLite 亲和与 DuckDB 强类型各有一票否决场景 ⚠️。
- 日期：内部 UTC 毫秒，`{$sort:{ts:1}}` 即按瞬时排；SQL 侧 epoch 整数/TEXT 日期两种存法排序不同（TEXT 字典序只在 ISO 格式下正确）🔧。
- 大小写：Mongo 字符串比较按二进制码位，默认区分大小写；SQL 的 COLLATE 世界（NOCASE/RUNE）与此不同族——`WHERE status='a'` 在 SQLite 默认不匹配 'A'，恰好与 Mongo 同德，换 MySQL 则翻车（互链 [../Understanding_MySQL_Internals/00-总览与阅读地图.md](../Understanding_MySQL_Internals/00-总览与阅读地图.md)）。
- 缺字段：`{status:{'$exists':false}}` ⇄ 无 NULL 时 `IS NULL` 不成立——本册演示集无缺字段样本，留 ⚠️ 未验。

## 核心概念速览（中英对照）

1. **聚合管道** — aggregation pipeline：文档流经有序阶段序列、逐级变换的加工模型。
2. **阶段** — stage：管道的一步操作，输出新文档流，是 MQL 的最小可组合单元。
3. **$match** — match stage：管道内的谓词过滤，等价 SQL WHERE，前置才可能用索引。
4. **$sort** — sort stage：全流排序，内存上限后可溢盘；等价 ORDER BY。
5. **$limit/$skip** — limit/skip stages：取前 N / 跳过 M，等价 LIMIT/OFFSET，深分页同为反模式。
6. **$count** — count stage：输出单文档计数；与 count(*) 的差异在空输入时输出空。
7. **谓词复用** — query predicate reuse：find 过滤器语言可直接进 $match，是 Mongo 的方言红利。
8. **BSON 类型序** — BSON comparison order：跨类型比较的全序规则，SQL 无对应物，移植陷阱。
9. **阶段顺序敏感** — stage-order sensitivity：管道优化器只做有限重排，人必须自己排序阶段。
10. **游标式分页** — range/cursor pagination：以上一页末键做范围过滤替代大 $skip/OFFSET。
11. **Top-N** — top-N query：$sort+$limit 组合，两世界语义一致、平局均不稳定。
12. **语义复现** — semantics reproduction（本册纪律）：SQL 引擎演示管道语义，不背书 mongod 行为。
