# 第 1 章 概述（Introduction）

> 对应已核实中译本目录：1.1 起步走 ｜ 1.2 元程序的概念 ｜ 1.3 在宿主语言中进行元编程 ｜
> 1.4 在 C++ 中进行元编程（数值计算/类型计算）｜ 1.5 为何进行元编程（替代方案 1：运行期计算、
> 替代方案 2：用户分析、为何进行 C++ 元编程）｜ 1.6 何时进行元编程 ｜ 1.7 为何需要元编程程序库。
> 本章回答两个问题："编译期还能写程序"到底指什么，以及凭什么要用 C++ 写。

## 核心概念速览（中英对照）

- 模板元编程 — template metaprogramming (TMP)：把模板实例化过程当计算用，输入是类型/整型常量，输出也是类型/值。
- 元程序 — metaprogram：编译期"运行"、其结果是产生（或拒绝）C++ 代码的程序；作者给出的直观判据是"程序自己生成程序"。
- 宿主语言 — host language：被元程序操纵的语言；C++ 同时是宿主语言和元语言——这是本书反复利用的自举特性。
- 元语言 — metalanguage：写元程序用的语言。Lisp 的宏以 S 表达式为元语言，C++ 的元语言是模板语法本身。
- 编译期求值 — compile-time evaluation：常表达式在编译器内归约；模板实参必须是编译期可确定的常量，这条语法边界就是 TMP 的"类型系统"。
- 生成式编程 — generative programming：以更高层描述生成目标代码的方法族；C++ TMP 是其"寄生于编译器"的一支。
- 图灵完备 — Turing complete：模板机制（递归实例化 + 局部特化分支）足以模拟图灵机——正文只作史实陈述，原始证明链接无法核实 ⚠️。

## 动机：为什么 2004 年要写这样一本书

1990 年代末到 2003 年，TMP 从"编译器的彩蛋"（最著名的传说：Erwin Unruh 用模板"编译"出质数列表 ⚠️ 细节各说
不一，本书之前已广为流传）变成 Boost 的工程现实：Gurtovoy 的 MPL 把散落的技巧统一成库，Abrahams 的
Iterator/Fusion 前置工作需要把"类型上的编程"说成一套可教的语言。第 1 章的使命因此不是炫技，而是立法：
先定义"什么是元程序"，再论证"C++ 为什么恰好是一个可用的元语言"，最后引出"为什么要一整套库而不是零散惯用法"。

作者给的三大理由（1.5 的两个"替代方案"逐一被反驳）：

1. 替代方案一：运行期计算——用虚函数/查表在运行期做同样的决定。反驳：运行期方案要么把决定推迟（代价、
   安全损失），要么要求运行期信息本可编译期确定；编译期方案的本质红利是"把错误消灭在部署前"和
   "把通用代码特化成机器码里不存在分支的版本"。
2. 替代方案二：用户分析/外部代码生成器（写了程序写程序的工具，如早期 MFC 向导、Eisenecker 的 C++ Template
   Library 的预处理器路线）。反驳：外部生成器与宿主语言类型系统脱节，无法享受重载决议、模板实参推导这些
   "编译器已经免费提供的推理引擎"。
3. 为何是 C++：因为 C++ 的模板是带重载决议的类型层函数式语言（1.4 分别用"数值计算"（阶乘、编译期
   算术）和"类型计算"（判断 T 是否指针、为不同类型选不同实现）两类例子划界）——TMP 的独门价值在第二类。

## 常见误区

- 误区一："TMP 是为了写得炫"。1.6 的存在就是对它的否定——判据是收益，不是技巧可用性；
  本书作者自己把"何时不该用"写成独立小节。
- 误区二："图灵完备=应该在编译期跑通用程序"。可计算 ≠ 值得计算：附录 C 的编译期成本模型、
  第 8 章的诊断难度，共同构成"完备性的代价"；工程判断在 1.6 与附录 C 之间。
- 误区三："元编程就是预处理宏"。1.3 的三层框架正是为了区分：宏无类型系统，模板有；
  把两者混为一谈会错过本书全部论证的结构（附录 A 反过来讲"宏的合理残余领域"）。
- 误区四："这书过时了所以 1 章可跳过"。第 1 章恰恰是全书唯一"语法无关"的章——动机、判据、
  成本结构三件事到 C++26 反射时代都仍然成立，只是实现手段换代（见"最新演进"节）。

## 机制：元语言与宿主语言的关系（1.3 的概念脚手架）

作者的论证结构值得单独记住——它把"元编程"从玄学变成了相对论：

```text
任何语言 L 都同时存在三层（以 1.3 的宿主语言分析为原型）:
  对象层   : 用 L 写程序        —— 普通 C++
  元层-内嵌 : 程序在编译期操纵 L 的结构 —— 模板元程序(本书全部)
  元层-外置 : 用另一语言生成 L   —— awk 生成 C++、代码生成器
Lisp 之所以"天然元编程"，是因为它的宏让元层与对象层共享同一语法表征;
C++ 的宏(预处理器)也有这个形状,但无类型系统 —— 于是模板成为"有类型的宏"的替代。
```

1.4 的两类例子各自点破一个关键事实：

- 数值计算：`factorial<n>` 这类递归实例化把"整数运算"搬进模板参数——说明编译器是一台解释器。
- 类型计算：给 `swap` 写一套"若 T 有 trivial 拷贝赋值则用 memcpy 语义"的选路——说明类型可以像数据一样被分支。
  第二条正是后面 2–9 章的全部内容入口，也是 `iter_swap` 案例（第 2 章）的预告。

1.6"何时进行元编程"的判据（本书立场，浓缩）：当问题的决定所需信息在编译期已经具备，且运行期/外置方案
要付出可观测代价时才用；TMP 不是默认选项。1.7 给出"库"的理由：没有统一抽象时，每个团队的"类型 if/else"
互不兼容、错误信息无法管理（第 8 章专章偿还此债）——这就是 MPL 的存在合法性论证。

## 权衡

- 红利：零运行期开销的抽象（模板参数即特化蓝图）、更早的错误检测（类型计算失败=编译失败）、
  跨编译单元的一致性由链接器之外的编译器保证。
- 债务：编译期成为执行期后，构建时间成为新的性能指标（附录 C 全书唯一"成本核算"章）；
  错误信息是"实例化回溯"而非语句级诊断（第 8 章）；元程序没有调试器、没有栈快照，可观察性接近零。
- 作者的自我设限：1.6 明确 TMP 适用面窄。今天重读，这一节价值反而更高——它是对"为了元编程而元编程"的疫苗。

## 最新演进与工业实践

- 2004→2011：动机被标准吸收了一半。 C++11 起，"数值计算"路线改道给 `constexpr`——阶乘、斐波那契、
  编译期哈希都不再需要模板递归；`<type_traits>` 把 1.4"类型计算"的一半标准化。今天讲 TMP 动机，
  1.5 的反驳链依然成立（运行期方案的代价论证完全没过期），只是"实现手段"换了三件。
- 2017：if constexpr 把"类型计算选路"变成语言语句，1.6 的"何时用"判据从"技巧可用性"退化为"收益评估"。
- 2020 concepts 让"约束"进入语言，当年 1.7 论证 MPL 库必要性的"接口无法自我描述"问题被语言直接解决。
- 2023→2026：编译期反射（P2996，"Reflection for C++26"，已实测 wg21.link/p2996 当前解析到 R13，2025 文档号）
  把 1.5"替代方案二：外部生成器"的最后堡垒（读类成员数量/名字）搬进语言；反射元对象在编译期可用后，
  书中"为什么需要 tag/traits 手工关联信息"的动机在新代码里进一步缩水。提案仍在演进 ⚠️，勿用于生产。
- 工业实践现状：Boost.MPL 官方文档与仓库均保持在线维护（[mpl 文档](https://www.boost.org/doc/libs/release/libs/mpl/doc/index.html)、
  [boostorg/mpl](https://github.com/boostorg/mpl) 已核实未归档），但工业界新库几乎不再引入 MPL：
  [abseil-cpp](https://github.com/abseil/abseil-cpp) 用标准设施解决同类问题（类型擦除 `absl::AnyInvoking`、
  元组/variant 工具链），[folly](https://github.com/facebook/folly) 的 `fbcode` 元编程层（`Folly/Traits`、
  `Poly`/`Function`）是"模板元编程作为工业库骨架"的现代标本——动机不变，工具换代。
- 建议的现代讲法（若你拿本书做培训教材）：1.1"起步走"用阶乘开场，紧接着演示同题的
  `constexpr` 实现并指出模板版仅剩历史价值——把"双镜头"在第一页就立起来。

书中每章末尾有 Exercises（本目录各章同此约定）。本章值得自测的两题方向：
① 不查资料写出 `factorial` 的模板版与 `constexpr` 版并解释何时前者仍占优（提示：类型层需要用到该"值"当

论证它属于 1.6 的哪一类"不该用 TMP"。
