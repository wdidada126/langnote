# 第 4 章 整型外覆器和操作（Integral Type Wrappers and Operations）

> 对应已核实中译本目录：4.1 布尔外覆器和操作（4.1.1 类型选择 / 4.1.2 缓式类型选择 / 4.1.3 逻辑运算符）｜
> 4.2 整数外覆器和运算（4.2.1 整型运算符 / 4.2.2 _c 整型速记法）｜4.3 练习。
> 本章是第 2 章"两条返回通道"中 **值通道** 的产品化：布尔→类型选择（if_/eval_if），整数→算术与比较。

## 核心概念速览（中英对照）

- **布尔外覆器** — Boolean wrapper（`mpl::bool_<B>`、`mpl::true_/false_`）：把编译期 bool 装箱成类型，使其可被塞进 `if_c`、可比较、可存进序列。
- **类型选择** — type selection（`mpl::if_c<C, T, F>`、`mpl::if_<C1, T, F>`）：编译期三元运算符；急求值版。
- **缓式（惰式）类型选择** — lazy type selection（`mpl::eval_if<C, F1, F2>`）：分支是**元函数**而非类型，未选中支永不实例化——本章最重要的语义分界线。
- **逻辑运算符** — logical operators（`mpl::and_/or_/not_/nand_/xor_`）：返回 bool 外覆器的编译期逻辑代数，`and_/or_` 自带短路。
- **整数外覆器** — integer wrapper（`mpl::int_<N>`、`mpl::long_<N>`、通才 `mpl::integral_c<T, N>`）：值→类型桥；`integral_c` 是统一底座。
- **整型运算** — integer operations（`plus_/minus_/times_/divides_/modulus_`、`equal_to_/less_/greater_` 等比较家族）：接收外覆器、返回外覆器的运算符元函数。
- **_c 速记法** — `_c` suffixed operations（`less_c<N>`、`plus_c` 等形态 ⚠️ 确切速记以原书为准）：直接吃"裸常量"而非外覆器的便捷别名。
- **nullary 元函数** — nullary metafunction：`bool_<true>` 这类"结果即自身"的对象，让 if_/if_c 共用一套取 `::type` 协议（回链 2.6）。

## 本章地图

```text
4.1.1 类型选择      → if_/if_c: 急求值的三元, 分支是"类型"
4.1.2 缓式类型选择  → eval_if: 分支是"元函数", 未选中支不实例化 —— 本章语义中心
4.1.3 逻辑运算符    → and_/or_/not_ + 短路: 编译期布尔代数成型
4.2.1 整型运算符    → plus_/less_ 族: 外覆器→外覆器, 第 5 章 range_c/第 6 章算法的原料
4.2.2 _c 速记法     → 直接吃裸常量的便捷形态(历史包袱: 两套平行 API 的由来)
4.3 练习            → 典型: 用 and_/less 组合写"区间内整数类型"判定 ⚠️(题面按通行记载)
```

## 机制手推：eval_if 到底"惰性"在哪

```text
求值 mpl::eval_if< C, F1, F2 >::type 的三步(以 C = is_pointer<T> 为例):
  1) 计算条件: is_pointer<T>::value → 得 bool_<true/false>(装箱)
  2) 只对被选中的 F 执行 apply —— 关键: F1/F2 是"元函数名字", 不是已求值的类型
  3) 未选中的 F 从未进入任何实例化 → 若它内含"deref 非法操作"(如对 int 解引用), 不会报错
对照 if_c<C, T, F>::type:
  T、F 已是类型, 书写处就必须能解析; 一旦 F 的"产生过程"本身有错(如 T::type 对 int 无意义),
  if_c 直接爆炸 —— 这就是第 2 章 iter_swap 案例最终改用惰性形态的原因。
```

现代同一事故（已实测 g++ 15.2）：`if constexpr` 未选分支"只解析不实例化"，
所以 `if constexpr (is_pointer) { *p; } else { p->x; }` 这类写法在 GCC 15 下合法且无回溯污染；
`std::conditional` 则是急选择——**语义对照关系与 2004 年一字不差**。

## 常见误区

- **误区一：`if_` 与 `eval_if` 可以随意互换**。凡分支类型可能"构造失败"，必须 `eval_if`；
  混用是 2004 年/MPL 用户手册 FAQ 的常客 ⚠️（按通行记载归入当年社区经验）。
- **误区二：`and_` 的短路对"类型序列求值"毫无意义**。短路恰恰是避免 `is_pointer<void>` 这类
  谓词链在第二支炸掉的生命线——急求值版（如朴素 `bool_` 组合）当年需要配合 eval 技巧才能安全。
- **误区三：外覆器只是包装强迫症**。没有 `bool_<B>`，`if_`（吃元函数）与 `if_c`（吃 bool）
  就是两套类型不互通的 API；装箱换来的是 nullary 统一协议（2.6）——这是设计上的"代数数据类型"雏形。

## 动机：类型层需要一个完整的"值世界"

第 1 章 1.4 的"数值计算"（阶乘类玩具）在第 2–3 章升级为正式设施的理由有两条：

1. **算法要谓词**：`find_if`、`sort`、`count_if`（第 6 章）全部要吃"返回布尔的元函数"。没有 `bool_` 装箱，
   布尔结果只能在 `::value` 通道里以 `int` 身份流动，与类型通道互不相通，`if_` 与 `if_c` 就得两套语法。
2. **选择要惰性**：`if_c<C, T, F>` 的两个分支必须是类型，但**很多"类型"本身不能安全实例化**
   （对非法 T 展开会直接编译错误）。于是 `eval_if<C, F1, F2>` 出现——分支以元函数身份传入，只对被选中的调用。
   这一对急/惰语义的分裂，恰好是本书反复出现的"求值策略"母题的最小标本（对比 3.5.4 的 lambda 懒惰）。

## 机制：装箱→运算→选择→短路

```cpp
// 🔧 书风示意(需 Boost 头文件;本机未装 Boost,此段未实测编译 ⚠️ 历史语境)
using namespace boost::mpl;
using c1 = if_c<(sizeof(int) == 4), int32_traits, int64_traits>;   // 急:两分支都被解析
using c2 = eval_if<std::is_pointer<T>,
                   deref_traits<T>,          // 惰性:只在条件为真时实例化
                   type_traits<T>>;          // 假分支同理被跳过
using ok = and_<not_<is_void<T>>, is_integral<T>>;  // 短路:is_void 为真则不再评估后者
using n4 = int_<4>;  using b = less<n4, int_<8>>;   // 比较返回 bool_<true>
```

但本书的写法今天已全部有替身。同一问题的新旧对照**已实测 g++ 15.2**
（`D:\develops\tmp\cppsnippets_tmp\old_vs_new_sum.cpp` / `new_style.cpp`，`-std=gnu++23`）：

```cpp
// 🔧 旧(手写等价模拟 mpl 机制,实测通过: old-style: sum=10, sizeof(picked)=4)
template <bool B, class T, class F> struct if_c_impl { using type = T; };
template <class T, class F> struct if_c_impl<false, T, F> { using type = F; };  // 特化=分支

// 🔧 新(实测通过: new-style: sum=10 -> int branch)
if constexpr (sum_of_v<L> > 5) { /* 未选分支不实例化 */ }
using picked = std::conditional_t<(N > 5), int, char>;
```

要点：旧 `eval_if` 的"惰性防炸"职责被 `if constexpr` 完整接管（未选分支只解析不实例化），
且新写法把"装箱/拆箱"整个环节删除——`std::integral_constant` 保留的唯一理由是**它仍是值→类型的桥**
（比如需要把数字塞进 `type_list` 时）。

## 权衡

- **急 vs 惰的选择税**：`if_` 写起来自然但有"假分支误爆"风险；`eval_if` 安全但强制每个分支包一层元函数
  （表达税）。MPL 把选择权交给用户——现代设施（`if constexpr`）同样两难，只是代价中心从"读不懂"挪到"记得住"。
- **装箱的往返成本**：`int_ → bool_ → if_ → type` 每步一个中间类型，附录 C 的实例化计数里本章设施贡献密集；
  `constexpr` 路线下同样的计算是零类型开销（代价：结果不能直接当类型用，除非再走 `integral_constant`）。
- **相邻概念对比**：`if_` vs `if_c`（吃 nullary 元函数 vs 吃裸 bool）；`eval_if` vs `apply`（惰性的两种实现）；
  `integral_c<T,N>` vs `int_<N>`（通用 vs 速记）；`bool_` vs `is_*` 谓词（人造布尔 vs traits 原生布尔）。

## 最新演进与工业实践

- **C++11**：`std::integral_constant`（`bool_constant`/`true_type`/`false_type` 全在其下）、`std::conditional`、
  `std::enable_if`（SFINAE 型 eval_if）把本章核心设施标准化——**但 `enable_if` 只有急选择**，惰性分支要等 17。
- **C++14**：变量模板让 `std::is_pointer_v` 直接当条件用，"拆箱"仪式消亡；`std::bool_constant` 成为
  NTTP 桥的官方形态（直到 C++20/26 允许类类型非类型模板参数才彻底告别）。
- **C++17**：`if constexpr` = eval_if + if_c 的统一替身（已实测）；`std::conjunction/disjunction` =
  `and_/or_` 短路的标准化；折叠表达式让 `plus_` 链式累加一次到位。
- **C++20**：`requires` 子句本身就是"布尔外覆器的最终形态"——约束求解在语言层做逻辑代数与短路。
- **P2996 静态反射**（[已核实当前 R13](https://wg21.link/p2996)）方向上，"值当类型用"的需求（编译期 switch、
  按整数值选类型）会被元对象 API 蚕食；`consteval`/`constinit`（20）与 `std::is_constant_evaluated` 继续压缩模板路线。
- **工业实践**：Boost.MPL 仍在发布列车上（[boostorg/mpl](https://github.com/boostorg/mpl) 已核实未归档），但
  官方新库改道 Hana；标准侧 `<type_traits>` 的后继增量（`remove_cvref`、`type_identity`）都发生在"值通道"——
  说明 20 年后这条通道的语义负担已由语言接管。诊断体验：旧式 `if_` 误用的错误信息指向中间外覆器类型名
  （第 7 章实例化回溯案例库），`if constexpr` 的 GCC/Clang 诊断已是普通语句级，几乎无回溯负担。
