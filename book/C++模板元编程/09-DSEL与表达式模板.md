## 核心概念速览（中英对照）

- **DSL / DSEL** — domain-specific (embedded) language：面向狭窄领域的迷你语言；"embedded"= 寄生在宿主语法内，不造新解析器。
- **宿主语言** — host language（回链 1.3）：DSEL 借用 C++ 的语法与类型检查；代价是被 C++ 文法反绑（优先级/重载限制）。
- **Make/BNF/YACC 谱系** — DSL 前史（10.2）：作者用以说明"声明式子语言"的来历——Make 是依赖图 DSL，BNF 是文法 DSL，YACC 是"文法→代码"的生成器；DSEL 是把这条流水线搬进类型系统。
- **表达式模板** — expression templates（10.5）：把 `A + B * C` 在编译期延迟成**类型树**，最后一次性生成融合循环——Blitz++ 的发明，本书的旗舰应用。
- **终端/非终端** — terminal / nonterminal：表达式树的叶（数组/标量）与内部节点（运算符）——Spirit 文法树的术语同源。
- **Blitz++ 魔法** — 10.5.3：模板元编程在科学计算中消除临时对象与嵌套循环的整套手法（et_traits、表达式对象、惰性 eval）。
- **具名参数 DSEL** — named parameters（10.6.1）：链式方法调用构造选项对象（`p = (key=1, other=2)` 风格的逗号/括号重载技巧）。
- **匿名函数 DSEL** — anonymous functions（10.6.2）：编译期"lambda"的宿主语法形态（回链第 3 章 `mpl::lambda`——同一件事的两种暴露方式）。
- **Boost.Spirit** — 10.7：EBNF 文法直接写成 C++ 表达式，编译期解析器生成器；`rule/closure`（闭包）是其经典形态（Qi/Lex 时代之前的 Spirit Classic 术语 ⚠️ 本书讨论的形态按目录含"闭包/子规则"）。
- **FSM 案例** — 11.1–11.5：第 11 章完整演练"为一个框架（Spirit 本身）设计嵌入式 DSL"的决策过程：领域抽象→符号→转换表→实现→分析。

## 机制手推：一行赋值在 ET 里经过哪些编译期实体

```text
表达式:  C = A + B * D;   (A/B/D 为数组表达式)
  1) B * D  → 类型 expr<multiplies<ExprB, ExprD>>     ← 1 个类模板实例化, 无循环运行
  2) A + (…​) → expr<plus<ExprA, 上式>>                ← 再 1 个实例化
  3) 赋值   → assign<ExprC, 上式>::apply()             ← 唯一运行期动作
  4) apply 内 for i: C[i] = eval(i), eval 按类型树递归内联 → 融合成单循环, 无临时数组
对比朴素实现: 2 个临时 vector + 3 个循环。ET 把"循环融合"从编译器优化(不可依赖)变成类型构造(必然成立)。
代价清单: 实例化数随表达式节点数线性增长; 调试器里看到的是模板树不是算式;
         内联失败(函数太大)时性能红利反噬 —— 11.6 的"分析"教的就是算这笔账。
```

Spirit 侧同构：`rule = a >> b` 构造 `sequence<a_, b_>` 类型（文法树），`parse` 时按树遍历——
**表达式模板与组合子文法共享同一个元模式：用类型当 AST，用实例化当编译。**

## 常见误区

- **误区一：DSEL 等于"运算符重载炫技"**。10.4 的宿主分析说明：选择重载是**借用类型检查**的策略；
  同一 DSL 也可用函数调用链/字面量语法表达，关键是领域不变量能否被类型系统验证。
- **误区二：ET 总是更快**。表达式节点少、循环体大（cache/分支主导）时，ET 的模板膨胀与内联依赖
  可能输给朴素循环；现代编译器自动融合也在蚕食 ET 独占区（见"最新演进"）。
- **误区三：第 11 章是"Spirit 使用教程"**。它实际是**框架设计课**：FSM 只是靶场，
  目标是展示"如何为你的库设计一个嵌入式 DSL"——11.2/11.6 的决策表比任何 API 细节长寿。

## 动机：为什么元编程的终局是 DSL

10.1 用一个"小型语言"开场（目录如此），意图是演示 DSEL 的**最小完整闭环**：文法→对象→执行全在 C++ 里。
10.3 给出 DSL 的总账：与"通用语言 + 约定"相比，DSEL 把**领域不变量变成类型错误**——非法程序不是"跑起来
不对"，而是**编译不过**。这需要元语言设施（traits/序列/分派）当骨架，于是前 9 章在此全部回收：

- Spirit（10.7）：文法规则的组合与解析器生成 → 第 5–6 章序列/视图（文法即序列）+ 第 9 章 CRTP（生成解析器基类）；
- 具名参数/匿名函数（10.6）：通用 DSEL 配件 → 第 3 章 lambda 的宿主语法化。

## 机制：表达式模板如何"编译期改写循环"

```cpp
// 🔧 10.5 的教学模型(示意, 历史语境; 完整 Blitz++/uBLAS 代码不在此伪造 ⚠️)
// 朴素: tmp = A + B * C  → 三个循环 + 临时数组
// ET:   A + B * C 先被重载为 expr<plus<expr<A>, expr<multiplies<B,C>>>> 类型树,
//       赋值时才逐元素 eval(i) —— 融合成单个循环, 无临时数组。
template <class L, class R> struct expr_plus { L l; R r;
    double eval(int i) const { return l.eval(i) + r.eval(i); } };
```

- **机制本质**：运算符重载 + 模板实参推导把"运行期计算"换成"编译期构造表达式类型"，
  `eval(i)` 的递归内联在 -O2 下折叠成单层循环——**惰性求值（3.5.4）在值层的镜像**。
- **Spirit 的机制**：`r = *chunk >> '.' >> +digit;` 的 `>>`/`*`/`+` 重载构造文法类型，
  `parse` 输入流上按类型遍历——第 6 章算法的运行时投影。第 11 章展示的正是
  "为这样的 DSL 设计转换表与生成逻辑"的框架工程。
- **11.6 分析**：作者对 DSEL 的自省清单（编译期开销、错误信息可读性、与宿主语法的阻抗）——本章与第 8 章
  （诊断）互为镜像的证据链。

## 权衡

- **DSEL 的三大税**（10.8/11.6 归纳方向）：① 宿主语法绑架（优先级、`=` 与 `,` 重载的禁区）；
  ② 报错即天书（第 8 章问题在 DSL 用户侧放大——用户比库作者更读不懂回溯）；
  ③ 编译期成本（文法复杂度→实例化复杂度，附录 C）。
- **ET vs 手工融合**：ET 让"数学写法=最优循环"，代价是调试时表达式树不可展开、编译器内联成为正确性依赖；
  2010 年代后 SIMD/自动向量化编译器部分接管了 ET 的红利（Veldhuizen 本人亦撰文重估 ⚠️ 其
  "Expression Templates Revisited" 系列无法核实稳定 URL，仅作书目线索）。
- **相邻对比**：DSEL vs 外部 DSL+生成器（1.5 替代方案二的复辟 vs 胜利）；ET vs 运行期 AST 解释器（编译期树 vs
  堆上对象）；Spirit（编译期）vs YACC（生成期）——三处"同一问题、三个时代"的对照。

## 最新演进与工业实践

- **C++11 后 DSEL 的可写性跃升**：`auto`/lambda/移动语义让"表达式对象"从重型类型体操变成普通值；
  uBLAS/Eigen/xtensor 仍用 ET，但新库普遍加 `constexpr` 通道兜底。
- **C++20/23**：concepts 把 DSL 文法的约束变成可读错误（Spirit X3 已转向约束 + 明显更好的诊断）；
  `std::source_location`/格式化库辅助 DSL 报错定位。
- **反射前景**：P2996（[已核实当前 R13 *Reflection for C++26*](https://wg21.link/p2996)）若落地，
  第 10 章的"具名参数/匿名函数"类 DSEL 大多可由元对象 + 编译期循环直接生成——**DSEL 从"重载语法糖"
  转向"读注解生成代码"**是 2026 年进行时的路线（std::reflection 仍在演进 ⚠️）。
- **工业实践现状**：Spirit 的编译期解析器在协议解析/配置子语言仍有存量（[boostorg/xpressive](https://github.com/boostorg/xpressive)
  正则 DSEL 已核实未归档；Spirit 仓库同源维护）；ET 谱系活在 Eigen/xtensor/ad::autodiff（自动微分
  即"表达式模板的第二春"，已核实相关文献方向但具体仓库状态未逐条验证 ⚠️）；folly/abseil 的
  DSL 类设施走 constexpr 路线（如 abseil 的 flags 解析、str_format 编译期检查）。
- **诊断体验**：Spirit 经典时代"一个文法错=半屏回溯"正是第 8 章的推广场景；X3/concepts 化之后报错
  收敛到文法节点级——DSL 工程的可维护性史就是诊断史的延伸。
