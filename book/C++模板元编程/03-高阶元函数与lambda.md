# 第 3 章 深入探索元函数（A Deeper Look at Metafunctions）

> 对应已核实中译本目录：3.1 量纲分析（量纲表示/物理量表示/加减乘除）｜3.2 高阶元函数｜
> 3.3 处理占位符（lambda 元函数/apply 元函数）｜3.4 lambda 的其他能力（偏元函数应用/元函数复合）｜
> 3.5 Lambda 的细节（占位符/占位符表达式的定义/Lambda 和非元函数模板/"懒惰"的重要性）｜3.6 细节｜3.7 练习。
> 本章把第 2 章的"一阶元函数"升级为**高阶函数语言**：没有 lambda 与占位符，transform/fold 全都无从谈起。

## 核心概念速览（中英对照）

- **量纲分析** — dimensional analysis：本章贯穿案例——用类型表示物理单位（`m/s` 之类），编译期做单位运算与一致性检查；TMP 的"类型计算"最佳广告。
- **高阶元函数** — higher-order metafunction：接收元函数作参数的元函数（`transform<Seq, F>` 的 `F`）；类模板不能直接当参数传，才引出下面两个概念。
- **元函数类** — metafunction class：带嵌套 `apply` 的类对象，模拟"函数作为值"。
- **占位符** — placeholder：`mpl::arg<1..5>`（速记 `_1.._5`），表达式中"待填入的参数槽"。
- **lambda 元函数** — lambda metafunction：`mpl::lambda<plus<_1, _2>>::type` 把含占位符的表达式物化为可调用的元函数类。
- **apply** — `mpl::apply<F, A...>`：编译期函数应用，`F` 可为元函数、元函数类或 lambda 表达式。
- **偏应用** — partial application：`multiplies<_1, 2>` 先绑一部分参数。
- **复合** — composition：`mpl::compose`：编译期函数管道。
- **懒惰求值** — lazy evaluation：占位符表达式在被 `apply` 前只是"类型树"，从不提前归约——3.5.4 全章点睛。

## 机制再进一步：从手写壳到 lambda 的一格之差

```cpp
// 🔧 3.2 时代的"元函数类"手搓形态(历史语境, 未实测编译 ⚠️)
struct half {                                  // 想把 "x/2" 传给 transform?
    template <class X> struct apply {          // 就得先给它这层壳
        using type = typename divides<X, int_<2>>::type;
    };
};
using r = transform<Seq, half>::type;          // 可用, 但每个操作都要写 5 行壳
// 3.3 之后: 同一件事 = transform<Seq, divides<_1, int_<2>>>  —— 零壳
```

一格之差 = **arity 统一协议**：`apply` 的签名（`A1..A5`）与占位符编号（`_1.._5`）把"任意编译期函数"
规范成同一种可调用形态——第 6 章的算法只认这一种形态。理解这层，才能理解为什么 Hana 的
`hana::composition` 文档仍在讲同一套协议，只是宿主从"类型树"换成"constexpr 对象"。

## 常见误区

- **误区一：把 `mpl::lambda` 当 C++11 lambda**。前者构造**类型**（编译期函数对象），后者构造**闭包对象**
  （运行期可调用体）；唯一交集是"函数当参数"的抽象概念。
- **误区二：以为占位符表达式在书写处已经求值**。`divides<_1,_2>` 只是类型名；求值发生在 `apply`——
  这是 3.5.4 的全部要点，也是误读 MPL 源码的第一根因。
- **误区三：高阶设施"只是为 transform 服务"**。量纲案例（3.1）表明高阶元函数是**领域建模**工具：
  单位代数的复合本身就需要"函数作为值"。

## 动机：没有"把函数当参数"，就没有算法库

第 2 章造好了"编译期函数"（类模板 + 特化分支），但 STL 类比走到 3.2 就撞墙：
`std::transform` 可以传函数对象，MPL 的 `transform` 要传的是**元函数**——而类模板本身不是类型，
不能当模板参数。2004 年的三条出路（书里按历史顺序展开为"元函数类 → 占位符/lambda"）：

1. **手搓元函数类**：`struct F { template <class A1, class A2> struct apply {...}; };`——可行，但每个要用的
   一元函数都得包一层壳，样板爆炸。
2. **模板型模板参数（template template parameter）**：语法上能把类模板当参数（第 3 章 3.6"细节"处理其
   缺陷——参数签名必须精确匹配，`mpl::quote` 家族由此而来 ⚠️ 本节具体措辞按通行记载）。
3. **lambda + 占位符（最终形态）**：`transform<Seq, divides<_1, 2>>`——表达式即语法，编译器替你物化。

3.1 的量纲分析案例先于一切抽象出现，意图明显：**先证明"类型当单位"的实用价值**（除以速度=乘秒每米这类
量纲运算在类型层逐字实现，单位不匹配=编译错误），再告诉你这种程序没有高阶设施会写到崩溃。

## 机制：表达式→元函数的翻译管线

```cpp
// 🔧 书风示意(历史语境:需 Boost.MPL 头文件,本机未装 Boost,未实测编译 ⚠️)
using namespace boost::mpl;
using per_sec = divides_<length, time>;          // 表达式:= 只是"造类型树"
using apply_speed_to = lambda<per_sec>::type;    // 物化:得到元函数类
using result_t = apply<apply_speed_to, meter, second>::type; // 应用:归约
// 占位符展开原理: _1 是 arg<1> 的别名;表达式树里每个节点都携带"如何 apply"的延迟定义
```

三条机制要点：

- **表达式树在实例化前只是"名字"**：`divides_<a,b>` 这种带依赖参数的模板不会提前求值（依赖类型延迟实例化
  规则），所以 `lambda<...>::type` 可以安全地把整棵树重新解释成带 `apply` 的类。这就是 3.5.4"懒惰的重要性"
  的语言学根基——不是库自己实现了 thunk，而是**语言本身给了惰性**。
- **`apply` 的签名约定**：所有元函数类统一 `apply<A1..A5>`（arity≤5，当年上限）；占位符编号与槽位一一对应。
- **偏应用与复合**把"函数构造"补全：`compose<F,G>::type`、`bind` 风格构件（3.4）让 `sort<Seq, less<_1,_2>>`
  这类算法调用有完整表达力。**这套抽象就是函数式编程的高阶函数，只是每个概念都穿了一次类型外套。**

## 权衡

- **收益**：算法（transform/fold）终于能复用"自定义操作"；量纲案例证明类型层可以有真正的"应用领域逻辑"。
- **成本 1（表达税）**：同一句话的 lambda 版比手写 `apply` 壳短 5 倍，但比 C++11 的 `auto`  lambdas 抽象层级
  高一层——读者需要同时懂"模板表达式 ≠ 求值"才能看懂 `divides<_1,_2>`。
- **成本 2（arity 天花板）**：5 参上限、无 varargs、无部分求值原语，都让复杂 lambda 的表达式树在编译器里
  实例化出**大量中间类型**（附录 C 的账本在此翻倍）。
- **与相邻概念对比**：`lambda` vs `protect`（防止过早展开的括号 ⚠️ 按通行记载）；`apply` vs `apply_wrap`
  （nullary 通道的两种口味）；模板型模板参数 vs 元函数类（语法直白但签名脆断）。

## 最新演进与工业实践

- **C++11 起本案的"翻译层"全部塌缩**：算法需要的"操作"改由**变参模板 + 别名模板**直接传（`template <class F> struct transform_t`
  的手写壳不再必要，因为可以 `template <template <class> class F>` 或干脆用 type list 折叠）；
  真正的"lambda"在运行期有了（`[](auto x){...}`），编译期侧则由 Hana 的 `hana::compose`/占位符
  （`_p1` 家族）继承——**概念一比一平移，实现不再依赖模板表达式树**。
- **C++14 变量模板 / C++17 折叠表达式**：量纲分析的现代重写（`constexpr` 的 `unit<double, int Exp...>` 或
  `std::ratio` 组合）可以在几十行内完成，模板实例化数量从 O(树) 降到 O(1)——这正是附录 C"编译期性能"的代际红利。
- **P2996 静态反射**（[已核实当前 R13](https://wg21.link/p2996)）：若元对象可编译期枚举，"为类型手工编码单位 traits"
  的 3.1 案例将被"读注解/读成员"替代（反射侧仍在演进 ⚠️）。
- **Hana 的现状**：[boostorg/hana](https://github.com/boostorg/hana) 已核实**未归档**，README 表明独立发行已停止、
  随 Boost 发布维护；其占位符 `hana::_1` 是本书 lambda 概念的现代直接后继，文档明确对比 MPL。
- **诊断体验**：lambda 表达式树的错误会以"中间占位符类型名"出现在实例化回溯里，今天的 `operator""_p` 风格
  同样难读——本章设施在新代码中应整体让位给 C++20 `requires` + `if constexpr` + Hana（若必须纯编译期）。
- **已实测 g++ 15.2（同题新写法）**：`new_style.cpp` 中 `type_list` + `sum_of` 的"传操作"改走变量模板
  `sum_of_v`，一行 static_assert 完成旧式三层（lambda→apply→::type）的全部工作（输出 `new-style: sum=10`）。
