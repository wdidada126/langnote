## 核心概念速览（中英对照）

- **MPL 算法** — MPL algorithms：`for_each/find/count/transform/fold/accumulate/remove/replace/sort/partition` 等，作用于任意满足 Sequence 概念的类型序列（第 5 章契约的消费方）。
- **插入器** — inserter（`back_inserter/front_inserter/inserters`）：算法输出端的"集合构建策略"，决定结果如何进入新序列。
- **查询算法** — query algorithms：`count_if/find_if/any_of/all_of` 类，只回答不产出；消费第 4 章的布尔元函数作谓词。
- **序列构建算法** — sequence-generating algorithms：`transform/remove/reverse/insert` 类，返回**新序列**（不可变语义，5.5.2 法律）。
- **fold / accumulate** — fold：编译期归约，`fold<Seq, State, Op>` 沿序列左折叠；名字与 C++17 折叠表达式（fold expression）完全无关——**同名不同物**，本章反复强调。
- **视图** — view（`transform_view/filter_view/reverse_view/joint_view`）：第 7 章核心；包一层"遍历协议改写器"，`deref/next` 时按需计算，**从不物化底层序列**。
- **迭代器适配器** — iterator adapter：视图的实现单元——把"迭代器运算"（deref/next/prior）重新组合，零拷贝投影。
- **避免不必要的计算** — 7.1.3 案例：视图组合（如 `transform + filter`）只对最终被消费的元素做元函数应用——惰性在算法层的兑现。
- **编写你自己的算法/视图** — 6.7/7.4：教学重头——按 STL 同款方式先写概念再写实现（MPL 的"概念驱动设计"闭环示范）。

## 机制手推：fold 在编译期如何展开

```text
fold<vector<a,b,c>, z, f> 的归约(左折叠, 书风):
  f( f( f(z,a), b), c )  —— 但每一层 f 都是一次"类实例化":
  实例化计数: 3 层 f + 3 层中间结果类型 + begin/next 协议若干 ≈ 10+ 个编译期实体
对照 C++17 折叠表达式 (f 以 constexpr 函数参与 (z op a op b op c)):
  实例化计数: 1(模板本身) + 普通常量折叠, 编译器按算术直接算
这就是"同名不同物"的实质差别: 名字都叫 fold, 一个走类型层归约(可携带类型),
一个走值层语法展开(只能产出值/表达式) —— 需要"结果仍是类型"时, 仍是 fold 的主场(或 Hana)。
```

7.1.3"避免不必要的计算"案例的展开：`filter_view<transform_view<S,F>,P>` 组合后只被 `count` 消费时，
**每个元素最多经历一次 F、至多一次 P**，且跳过被 P 拒绝的元素后的 F——视图不物化任何中间序列；
急物化版（先 `transform` 再 `filter`）则会实例化整个中间序列。这就是第 7 章存在的全部理由。

## 常见误区

- **误区一：用运行时思维估算法的账**。类型层"一条语句"= 一堆实例化；`fold` 链、视图嵌套都要按
  实例化数复利计（附录 C 的工具在此启用）。
- **误区二：把 `find_if` 找到的"迭代器"当可存储对象**。迭代器是类型不是值，跨作用域"保存位置"
  只能靠序列派生/整型索引重新表达——运行时习惯在编译期最易翻车的一点。
- **误区三：视图永远优于物化**。视图每次 deref 重算 F；被多次消费的中间结果，物化一次反而省——
  与运行时 generator vs vector 完全同题。

## 动机：算法才是抽象的回报

第 5 章立法，第 6 章收租。6.1 的开章论证是全书方法论核心：

1. **复用来源**：运行时 STL 的复用率取决于"算法 × 容器 = N+M"而非 N×M；类型层同理。
2. **惯用法（idiom）一词的自觉**：6.1 标题直接把"算法、惯用法、复用和抽象"并置——作者把 TMP 从
   "聪明技巧"升格为"软件工程"的野心在这一节白纸黑字。
3. 没有序列抽象时，每个项目手写"遍历 vector 并计数满足 P 的元素"；有了它，`count_if<S, P>` 一行。
   反过来，**算法作者**（想写通用元算法的人）获得"只要满足概念就通吃所有序列"的自由——
   这正是 `mpl::at` O(1) 律（第 5 章）存在的理由：否则 `transform` 对 list 的复杂度不可预测。

第 7 章的动机更具体：编译期计算**每一步都很贵**（一个实例化=一次编译期函数调用），
`transform` 后接 `filter` 若各自物化新序列，中间成本翻倍；视图把"组合"变成"遍历协议的函数复合"，
代价只在被最终消费时支付——**惰性求值（3.5.4）在容器层的复活**。

## 机制：概念→算法→视图三层

```cpp
// 🔧 书风示意(历史语境,需 Boost.MPL,本机未装 Boost,未实测 ⚠️)
using namespace boost::mpl;
using types = vector<int, float, char>;
using ptrs  = transform_view<types, add_pointer<_1>>;   // 视图: 不构造新序列
using ok    = any_of<ptrs, is_pointer<type_of<_1>>>;     // 查询: 消费视图
using total = size_t<fold<types, size_t<0>, plus<_1, size_of<_2>>>>; // 归约: 值通道累加
```

三条机制要点：

- **算法只写一次概念调用**：`for_each` 的实现 ≈「取 begin、比较 end、deref、next」的编译期循环——
  用模板偏特化写 while（第 2 章分支 + 第 5 章协议），第 9 章 `mpl::for_each` 再把它推过编译期/运行期边界。
- **fold 的展开是实例化级的**：`fold<S, z, f>` 对 N 个元素生成 N 层嵌套 `f` 应用——**编译期复杂度 O(N) 起步**，
  序列越长实例化越多（附录 C 账本；对照 C++17 折叠表达式的"折叠"是纯语法展开，不经过类实例化，
  这是两者机制差异的成本侧）。
- **视图 = 迭代器适配器组合子**：`transform_view<S,F>` 的 `deref` 转发为 `apply<F, deref(i)>`，
  `filter_view` 的 `next` 是"内部小循环"（跳过不满足谓词的位置）——与运行时 range-v3 的管道完全同构，
  2004 年已具雏形（7.5 历史自认师承 STLport/Boost Iterator  adaptor 一族）。

## 权衡

- **急物化 vs 惰视图**：`transform` 返回新序列（可复用、可比较、可作 map 键），`transform_view` 每次 deref 重算
  （省实例化但重复消费会重复算）——与运行时"vector vs generator"同题；MPL 两种都给，逼用户做决定。
- **算法词汇表的缺口**：`sort` 在 MPL 是"可选奢侈品"（类型序列通常短且静态），当年没有 `zip/adjacent_difference`
  等；补口子的正确姿势就是 6.7/7.4——这也是本书反对"只会调库"的立场。
- **相邻对比**：MPL 算法 vs C++17 折叠（前者运行时语义完整、后者只覆盖 fold 一角但零实例化）；
  视图 vs 手工迭代器数学（joint_view 一行 vs 手写边界判断十行）；`accumulate`（带初值归约）vs `fold` 同物异名
  ⚠️ 原书两词并用，读时视为同义。

## 最新演进与工业实践

- **C++11/14**：变参模板 + 递归展开或 `initializer_list` 技巧可重写 `for_each/transform/fold`（tuple 版 `for_each`
  即 `std::apply + index_sequence`——第 8 章演示）；`std::integer_sequence` 是官方"内置整型序列"。
- **C++17 折叠表达式**：`(args + ...)` 与 `(... , f(args))` 直接吃掉"遍历+归约"两大品类；`std::apply/visit` 提供
  tuple/variant 层的 for_each。视图层则由 **range-v3 → C++20 ranges** 接管：`views::transform/filter/join` 与
  第 7 章逐字同名，且是**值层** API（编译期可在 `constexpr` 下运行，C++23 `std::ranges`  constexpr 化推进中 ⚠️）。
- **C++20/23**：concepts 让"算法只依赖概念"从文档契约变语言强制（`std::ranges::transform_view` 的约束即
  MPL 概念法的正式化）；Hana 把 MPL 算法全集在 constexpr 值层重实现一遍（`hana::transform/fold_left`），
  [boostorg/hana](https://github.com/boostorg/hana) 仓库已核实未归档。
- **工业实践**：现代 C++ 库的类型层算法普遍"就地手写 + 折叠表达式"（abseil 的 `string_view` 模板族、
  folly 的 `apply` 家族），MPL 算法仅在维护存量 Boost 代码时出现——[boostorg/mpl](https://github.com/boostorg/mpl)
  已核实未归档、维护模式。诊断体验：旧式 `fold` 里一个谓词写错，回溯深度=序列长度；折叠表达式报错是语句级。
- **已实测 g++ 15.2（同题新写法）**：`new_style.cpp` 的 `sum_of<type_list<...>>`（编译期归约）以
  `(0 + ... + Vs)` 一行实现 fold，输出 `new-style: sum=10`；旧链表版同文件输出 `old-style: sum=10`——
  两种"折叠"的语义与成本差在对照中自现。
