# 第 5 章　软件技术架构的发展

> 原书第 5 章是「学前铺垫」：从单体 → 水平集群 → 垂直集群 → SOA → 微服务讲清架构演进，
> 并引入 CAP 理论。作者明确说「学 Dubbo 前要先懂这些历史脉络」。这一章把 Dubbo 的动机
> 讲清楚了：为什么需要从单体走向分布式 RPC。2026 视角要补：**服务网格（Service Mesh）、
> 云原生、以及 CAP 的 PACELC 精化**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 单体架构 | 单进程包打天下 | 简单但无法水平扩展、迭代相互拖累 |
| 5.2 水平集群 | 同应用多副本 + 负载均衡 | 解决「并发/可用」，但不解决「业务解耦」 |
| 5.3 垂直集群 | 按业务拆成多个独立系统 | 解耦业务，但系统间仍点对点硬连 |
| 5.4 SOA | 企业服务总线（ESB）治理服务 | 服务化起点，但 ESB 易成中心瓶颈 |
| 5.5 微服务 | 小而自治、去中心化治理 | 当今主流；与 RPC/注册中心强绑定 |
| 5.6 CAP 理论 | 一致性/可用性/分区容忍 | 分布式必分区，实质是 C vs A 取舍 |

## 核心精讲

（以下为教学性梳理，图示均**教学示意，不参与构建**。） 

### 5.1–5.5 架构演进主线

```text
# 教学示意，不参与构建：从单体到微服务的驱动力
单体        -> 代码全在一个进程，扩展只能整机升配（垂直扩展有上限）
水平集群    -> 同应用多副本 + LB，解决并发与可用，但代码仍耦合
垂直集群    -> 按业务拆系统（订单/用户分离），解耦但系统间硬连、配置散
SOA         -> 引入 ESB 统一治理服务调用，中心化带来瓶颈与复杂度
微服务      -> 服务小而自治、去中心化注册发现 + RPC，独立部署扩容
```

- **微服务与本书的关系**：微服务「去中心化治理 + 服务注册发现 + 远程调用（RPC）」正是
  Dubbo 的全部用武之地——第 6/7/8 章就是这套机制的具体实现。

### 5.6 CAP 理论（本章的理论锚点）

- **C（一致性）**：所有节点同一时刻看到相同数据；
- **A（可用性）**：每个请求都能得到（非错误）响应；
- **P（分区容忍）**：网络分区时系统仍能继续工作。
- **关键结论**：分布式系统**必须容忍分区**（否则不叫分布式），所以真实取舍是 **C vs A**。
  选 CP（如 ZK）或 AP（如一些最终一致注册中心），没有「既要又要」。

```text
# 教学示意，不参与构建：CAP 与本书角色的对应
ZooKeeper        -> 偏向 CP（强一致，分区时可能拒绝写入以保证一致）
Nacos(AP 模式)   -> 偏向 AP（高可用，分区时仍可写，最终一致）
Dubbo 集群容错   -> 在「调用失败」时选 重试/降级/快速失败 等策略（见第 8 章）
```

## 版本演进

- **本书无第二版**；本节写 2022 年口径 → 2026 年视角的变化。
- **5.6 CAP 需精化为 PACELC**：CAP 只描述「分区发生时」的取舍；正常情况仍存在
  **延迟 vs 一致性**的取舍（PACELC）。现代系统更常承诺**可串行化/线性一致**而非「强一致」含糊词。
- **服务网格（Service Mesh）**：本书停留在「SDK 内嵌治理」（Dubbo 框架做治理）。
  2026 年主流补充了 **Sidecar 代理（Proxyless / Proxy 网格）** 把治理下沉，跨语言、与 Dubbo 3 的 Proxyless 网格融合。
- **云原生与 Kubernetes**：微服务的事实运行底座从「物理机/VM + 注册中心」走向
  「K8s Service + 服务网格」，注册发现的部分职责被 K8s 接管。
- **Jepsen 视角**：一致性声称需用故障注入证伪（见 01 章引），本书 CAP 讲法偏理论。

## 近年研究与工业界开源实践（2015–2026）

- **alibaba/nacos（33419★，2026-09 实测）**：同时支持 CP/AP 模式的注册+配置中心，本书 7.11 已引入，
  是 CAP 取舍在国产生态的落地代表。
- **apache/dubbo（41579★）**：微服务 RPC 框架，本章架构演进的直接受益者（见 06–08）。
- **istio / envoy（服务网格）**：将治理从 SDK 下沉到 Sidecar，是微服务架构 2026 年的重要补丁方向。
- **CNCF 生态（Kubernetes）**：微服务的事实编排底座，承接了部分注册发现职责。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「CAP 三选二」 | P 不是可选项（分布式必分区），真实取舍是 **C vs A** |
| 2 | 「微服务一定优于单体」 | 单体在小型系统更简单；微服务带来分布式复杂度，需权衡 |
| 3 | 「SOA = 微服务」 | SOA 中心化（ESB），微服务去中心化，二者治理哲学不同 |
| 4 | 🔧 CAP 未精化为 PACELC | 正常情况仍有延迟/一致性取舍，CAP 只覆盖分区态 |
| 5 | 🔧 未提服务网格 | 2026 年治理下沉到 Sidecar/Proxyless，本书只讲 SDK 治理 |
| 6 | 🔧 未提云原生/K8s 底座 | 注册发现部分职责被 K8s 接管，本书停留在传统注册中心范式 |
