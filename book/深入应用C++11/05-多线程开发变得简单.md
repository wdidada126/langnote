## 核心概念速览（中英对照）

- **线程对象与生命期协议** — `std::thread` joinable protocol：可联结的 thread 析构即 `terminate`——"没人收尾就罢工"。
- **独占/递归/定时互斥量** — mutex / recursive_mutex / timed_mutex：所有权模型与超时能力的三档。
- **作用域锁** — lock_guard / unique_lock：前者RAII一行流，后者可延迟/可转移/配合条件变量。
- **条件变量** — condition_variable：与谓词配对使用的**阻塞通知协议**，`wait(lk, pred)` 消化虚假唤醒。
- **原子变量与内存序** — atomic / memory order：无数据竞争的通信原语；relaxed/acquire-release 三档是最小够用集。
- **一次性初始化** — call_once / once_flag：标准库内建的双检锁替代品。
- **期值** — future：一次性结果的读取凭据（get 只能一次）。
- **承诺** — promise：手工生产端，set_value/set_exception 兑现。
- **任务包装** — packaged_task：可调用对象 + 内建 promise，"执行即兑现"。
- **启动策略** — launch policy：`async` 的 `async`（立即起线程）与 `deferred`（谁 get 谁跑）二态。
- **共享状态** — shared state：promise/task 与 future 之间的堆协议对象，配互斥与条件变量实现。

## 一、动机：pthread/Win32 双轨时代的终结

C++98 时代 Windows 与 POSIX 两套线程 API，代码无法带标准库跨平台。C++11 把线程/互斥/条件变量/
原子写进语言与库层——本书写作时（GCC 4.8/4.9、MSVC 2013）恰是"第一次可以只写一套"的窗口期，
章题"变得简单"是字面意义的历史事件。同时它埋下三个至今仍在讨论的语义决定（terminate、
deferred 任务、内存序），本章按机制逐个拆解。

## 二、机制

### 2.1 `std::thread` 到本地 API 的映射（跨平台≠同一实现）
libstdc++ 在 Linux 上把 `std::thread` 落在 pthread_create、`std::mutex` 落在 pthread_mutex；
Windows/MSVC 用 `CreateThread` + SRWLOCK ⚠️（通行记载）；**本机的 MinGW-Builds g++ 15.2 是
`win32` 线程模型**（`g++ -dumpmachine` 实测 `x86_64-w64-mingw32`，构建串含 `win32-seh`），
其 gthreads 层是 GCC 13 起重写的原生 Windows 实现（gcc 邮件列表 r13-4881 提交"Reimplement
GNU threads library on native Windows"，见搜索记录）——重写版有丢唤醒的既往问题（本文第五节
实测到同源现象）。结论：**"std:: 线程可移植"从来不等于"各实现等价"**，压测要按工具链来。

### 2.2 为什么析构 terminate 而不是自动 join/detach
join 会把调用者拖进任务排队（析构点不可控），detach 让悬垂捕获合法化——两个都有合理场景，
标准委员会选择"都别猜，报错"。后果：异常路径泄漏 joinable 对象。C++20 `jthread`（见第六节）
用"默认 join + stop_token"补齐了主流场景，本书 8–9 章的线程池正是 jthread 出现前最典型的
手写 RAII 包装。

### 2.3 条件变量的协议本质
`wait(lk, pred)` = `while(!pred()) { 原子地放锁睡下、醒来重新拿锁; }`。没有 pred 的裸 wait
在**虚假唤醒**下错误成立；丢通知场景要靠"通知前谓词已置真"的顺序纪律。5.3 生产者消费者骨架
+ 谓词等待，是 [08 章](08-半同步半异步线程池.md) SyncQueue 的全部原理。
### 2.4 future 家族的一张数据流图
```text
promise ──set_value/set_exception──┐
packaged_task ──operator() 自动兑现─┤→ [共享状态] ←get()/wait()── future
std::async(deferred) ──get 时才执行─┘
```
三条生产路径共享一个消费端。要点：`get` 移走结果（`wait_for` 可重复）；`shared_future` 允许多读者；
`deferred` 任务"谁 get 谁执行"——线程数不受控的风险正是 EMCA/EMC Item 35–36 的主论题。

### 2.5 原子操作的机器语义：lock-free ≠ 免费
x86-64 上 8 字节对齐的 load/store 天然原子，`memory_order_relaxed` 的加减编译成 `lock xadd`；
`acquire/release` 在 x86（TSO 内存模型）下几乎不产生额外指令，只约束编译器重排——而在 ARM 上
同一对语义会真的插入 barrier。这就解释了 🔧 实测里 `lockfree=1` 却仍要讲内存序：**无锁只是
消除 mutex 间接层，顺序保证仍由 memory order 提供**。`is_always_lock_free`（C++17）与实例的
`is_lock_free()`（C++11，实测所用）的区别也在这条版本线上。

## 三、权衡与实战提示

- 无锁不是快而是"换正确性模型"：`is_lock_free`（实测本机 int 原子 =1）只说明指令级无锁，内存序选错
  依然是竞态——relaxed 计数、release/acquire 发布订阅、seq_cst 默认兜底是最小纪律。
- `std::thread(f, args...)` 的实参在构造点**全部拷贝/移动到内部存储**（decay-copy）：传引用要
  `std::ref`，且引用对象必须比线程活得久——与 01 章"引用捕获悬垂"是同一条纪律的线程版。
- recursive_mutex 是给"接口级重入"打的补丁，出现即设计警讯；`timed_mutex` 的超时语义在低精度时钟
  上可能显著晚醒。
- `async` 返回的 future 析构**阻塞等待完成**（与 deferred 联动），把"fire and forget"做成了
  "fire and join"——想真异步请存 future 或走线程池。

## 四、相邻概念对比

| 对比 | 差异一句话 |
| --- | --- |
| thread vs jthread | 后者自动 join + 可中止（C++20），前者析构即裁决 |
| mutex vs atomic | 保护不变量 vs 单变量无竞争；atomic 不解决复合操作 |
| promise vs packaged_task | 手工兑现 vs 执行兑现；后者的异常自动进 future |
| async vs 线程池 | 每任务一线程 vs 受控复用；本书第 9 章的存在理由 |

## 五、实测（🔧 三档 + 语法探针：g++ 15.2，`ch05.cpp`、`jt.cpp`）

```text
gnu++11/gnu++17: 运行全绿——
  cv woke, state=42 / once init / atomic=8 lockfree=1 / packaged_task 9*9=81 / async 6*6=36
gnu++20/23（jthread + atomic::wait 段）:
  -fsyntax-only 探针四档：gnu++11/14/17 FAIL（'jthread' 不是 std 成员）；gnu++20/23 PASS
  运行受限：本机安全软件拦截该 exe（rc=127，多次重试同值），未获运行时输出——如实记录 ⚠️
环境缺陷标本（与本章直接相关）:
  本构建为 win32 线程模型：多线程池最小探针出现条件变量丢唤醒（worker 睡死不醒，3/3 复现，
  notify_all 亦如此；见 08 章实测）；单生产者单消费者的 cv 用例则稳定通过（本节全绿）。
  promise 二次 set_value 的跨线程 demo 在本机同样挂死——规避后改 packaged_task 同线程兑现。
```

- `atomic=8 lockfree=1`：8 线程 relaxed 累加不丢计数且无锁实现——但"不丢"是本次观察，不是保证；
  保证来自内存序，不是来自 lock-free。

## 六、最新演进与工业实践

- **C++14**：`shared_timed_mutex`。**C++17**：`shared_mutex`（读写锁入库，读多写少的标准解）。
- **C++20**：`std::jthread` + `std::stop_token`（wg21 侧 jthread 相关提案经 p2219r0 路线并入工作草案，
  wg21.link/p2219 实测解析至 2020 文档；细节对应 ⚠️ 未逐字核）、`counting_semaphore/latch/barrier`、
  `atomic::wait/notify_one`（等待队列入库，futex 思想的标准化）。本书 5.5 的 call_once 惯用法在
  jthread 时代变成 `jthread` 构造传参 + stop_source 广播。
- **C++26 方向**：senders/receivers（P2300R10，wg21.link/p2300 实测解析至 r10）把"线程/池/续体"
  统一成执行器组合子——本书第 15 章 TaskCpp 的终点站（详见 [11 章](11-LINQ并行任务与异步网络.md)）。
- **工具链对账**：MSVC/LLVM/pthread 系对本章原语的实现与验证度各不相同；gcc.gnu.org 邮件列表的
  gthreads 重写记录（2022-12 提交）是"标准 API、非标准实现"的最好提醒。生产并发代码仍需
  TSan/Helgrind 与压测背书——见 [../C++并发编程实战2/00-总览与阅读地图.md](../C++并发编程实战2/00-总览与阅读地图.md) 的测试方法论章。
