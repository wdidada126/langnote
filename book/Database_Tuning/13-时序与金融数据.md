## 这一章在讲什么

11 页聚焦**时间轴数据的存储与查询**（以金融为主）：tick/行情/账户历史这类
"按时间追加、按时间窗口消费"的负载，在 2002 年的关系库里如何落地。
与第 6 章（华尔街案例）互补：案例章讲现场，本章讲可复用的模式。

### 主题级重构（⚠️ 依章题、页幅与当时可行技术集推定）

1. **到达模式与物理布局**
   - 只增不改（append-mostly）、时间单调、最新数据最热：布局应让"新块"与"热查询"对齐 ⚠️。
   - 与 OLTP 随机写的根本差异：写路径可顺序化（日志式），但二级索引会把它拉回随机——
     本章应讨论"时间分块 + 块内索引"折中 ⚠️。
2. **窗口查询与统计**
   - 移动平均、区间聚合、**分位数/VaR**：当时 SQL 无 percentile 原语，需自连接或游标模拟，
     代价高昂——这是全章最"疼"的技术点 ⚠️ 推定（与 [06-华尔街案例研究.md](06-华尔街案例研究.md) 呼应）。
3. **采样与降精度**
   - 保留策略：原始 tick 全存 vs 按价值降采样（1s→1min 桶）；
     金融合规又要求"可重建明细"，压缩与审计的张力 ⚠️。
4. **规模治理**
   - 历史数据归档/分区卸载：老区间查询少但合规要查——冷热分层在 2002 的手工形态 ⚠️。

### 判断

本章是全书"最先知先觉"的 11 页：它描述的负载后来撑起了整个时序数据库产业
（2010s 的 InfluxDB/TimescaleDB/QuestDB、以及 kdb+ 的商业长跑），
而它抱怨的"SQL 缺分位数/窗口原语"在 SQL:2003 窗口函数标准化后永久解决。

## 2002 → 2026 的位置

时序负载的调优答案已分化为三档：

1. **通用引擎 + 表格式**：Iceberg/Hudi 的按时间分区 + Delta 变更流，适合"时序是众多维度之一"的湖仓场景。
2. **专用时序 DB**：列存 + 时间分区 + 连续聚合（TimescaleDB continuous aggregates、QuestDB 的
   by-alias 写入）+ 降采样策略（downsample/TTL）把本章手工活全部产品化。
3. **流式预聚合**：Flink 窗口聚合把"移动平均/VaR"从查询时计算移到写入侧，读侧只剩点查物化状态。

## 常见误读与澄清

- 误读：时序数据=日志加时间戳
  澄清：其查询语义（窗口/迟到/对齐）与保留治理是独立设计面；当日志存会低估索引与聚合成本
- 误读：专用时序 DB 万能
  澄清：跨维关联与既有数仓资产仍以通用引擎+表格式更省，选型看关联深度不看热度
- 误读：窗口函数普及后本章无事
  澄清：窗口函数解决表达不解决代价：窗口物化/增量维护仍是本章预聚合问题的现代形态

## 章要速览：三个要点与三个坑

- 要点：时序负载写顺序化读窗口化；冷热/保留策略是规模治理主轴；原语缺失时代 percentiles 贵得离谱。
- 坑：给只增表建一堆二级索引；历史明细既不敢删又没有降采样精度保证；时钟漂移破坏窗口对齐。

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
| --- | --- | --- |
| tick 数据 | tick data | 逐笔行情，时序负载的原型 |
| 追加写 | append-only | 以插入为主、几乎不改历史到达的形态 |
| 时间分区 | time-based partitioning | 按时间区间切表，冷热与裁剪的单位 |
| 窗口聚合 | windowed aggregation | 滚动/滑动/会话窗口上的统计 |
| 连续聚合 | continuous aggregate | 写入侧增量维护的预聚合（现代产品化物化视图）|
| 分位数/VaR | percentile / value at risk | 有序统计，风控核心且早期 SQL 缺原语 |
| 降采样 | downsampling | 高精度数据定期坍缩为低精度桶 |
| 保留策略 | retention policy | TTL/归档规则定义明细数据的生命周期 |
| 冷热分层 | tiering | 按访问频度分配存储介质的布局 |
| 迟到数据 | late arrival | 超过水位线到达的事件，窗口语义的难点 |
| 插值/对齐 | interpolation / alignment | 多源时间序列对齐到共同网格的处理 |

## 最新演进与工业实践

- **TimescaleDB**：PostgreSQL 扩展形态，`time_bucket` + continuous aggregates + retention/compression
  策略把本章手工模式全部内建，文档 https://docs.timescale.com/ （✅ 200）。
- **QuestDB**：ILP 向量执行 + 按时间分区的表，金融 tick 场景常驻基准选手，
  https://questdb.io/ （✅ 200）；ClickHouse（https://clickhouse.com/docs ，✅ 200）
  以 `TTL`/`AggregatingMergeTree`/物化视图链覆盖同类需求 ⚠️ 特性名以官方文档为准。
- **SQL 原语到位**：窗口函数（SQL:2003）与 `PERCENTILE_CONT/DISC`（SQL:2016）使
  "分位数查询"从工技巧化为声明式语句；PG/MySQL 8/SQLite 3.45+ 支持度不一 ⚠️ 转述手册。
- **流式预聚合**：Flink（https://flink.apache.org/ ，✅ 200）状态后端承担 24×7 窗口维护，
  读侧退化为 KV 点查——本章"查询时算 percentile"痛点的根治路径之一。
- **InfluxDB 路线**：line protocol + Tasks/Flux 的"写入侧预处理"哲学 ⚠️ 产品语义转述，未实测。
- 🔧 **本地小验证**：SQLite 3.45+ 无 percentile 原语，可用窗口函数 + `NTILE` 手工实现分位数并计时
  （SQLite Python 内置版本随发行，方法 10 行内；数据在 repo 外 `D:\develops\tmp\dbwave_dt\`），
  直观感受"原语缺失时代"的实现成本 ⚠️ 结果依版本而异。
