## 这一章在讲什么

把 DBMS"内脏"逐个摊开：存储布局、缓冲池、日志与检查点、锁与并发、（当年新兴的）清理/vacuum 类维护，
每一部件给出"可调什么、代价是什么、怎么用实验验证"。方法上延续第 1 章的受控实验，
对象上是 2002 年前后的多引擎横评（Illustra、DB2、Oracle、SQL Server、MySQL 等厂商产品各有专例 ⚠️ 具体名单未对照原文）。

### 1. 页与存储布局

- 页大小是"第一个旋钮"：大页摊薄 IO 头成本、利于扫描，小页利于点查与稀疏更新——
  典型代价交换 ⚠️。
- 行/列排布、溢出链（overflow chain）对扫描与随机访的影响；当年厂商普遍"页内行存 + 行迁移"，
  列存尚在数仓专用产品里 ⚠️。
- 填充因子（fill factor）与页分裂：插入有序性决定 B 树页利用率——该结论与
  [../Database_Internals/04-B树实现.md](../Database_Internals/04-B树实现.md) 的现代讲述一致。

### 2. 缓冲池（buffer pool）

- 全章的"重头旋钮"：池大小、置换策略（LRU 家族及其当年变体）、预读、pin 策略 ⚠️。
- 关键立场：**缓冲池的收益边界 = 工作集大小**。小于工作集时每加一分内存换一分性能，
  跨过饱和点后边际收益趋零甚至为负（管理开销）。
- 🔧 饱和点的最小复现（本机 Python sqlite3，方法详见文末与 [15-配置参数.md](15-配置参数.md)）：
  对约 11MB 的 30 万行表反复做全表聚合，`PRAGMA cache_size=-2000`（2MB）时约 18ms，
  `-16000`（16MB）时约 11ms，再加大到 64MB 仍为 11ms——工作集全驻后旋钮失效，曲线出现平台段。

### 3. 日志、检查点与恢复

- WAL 的写放大账：每次提交至少一次同步日志写；组提交（group commit）、日志缓冲、
  检查点频率是三个杠杆 ⚠️。
- 检查点太密→IO 抢占；太疏→恢复时间长、脏页堆积→缓冲池失效。"调优就是选一个崩溃恢复 SLA"
  的观点与 [../Database_Internals/05-事务处理与恢复.md](../Database_Internals/05-事务处理与恢复.md) 的 ARIES 叙述互为印证。
- fsync/写序依赖与电池背板缓存（write-back cache battery）是当年著名的"不可测陷阱" ⚠️。

### 4. 并发控制内部件

- 锁表大小、锁升级（行→页→表）、死锁检测周期：每项都是"省内存 vs 省并发"的交换 ⚠️。
- 闩锁（latch）与缓冲池分区：当年已提出把 buffer 分区以降低闩锁争用——此即今天
  各引擎 shard 化 buffer/LRU 的先声 ⚠️ 推定。

### 5. 维护型调优：vacuum/统计/重建

- 面向 PostgreSQL/Illustra 血统的"垃圾回收"议题：dead tuple 比例影响扫描与索引深度，
  vacuum 频率本身是调优对象 ⚠️。
- 统计信息新鲜度被反复强调为"最便宜的性能保险"——这句是全章到第 14 章（访问计划）的桥梁。

## 2002 → 2026 的位置

本章描述的"手动挡内核"今天大多已自动档化：InnoDB 自调 buffer pool、PG 自动 vacuum/autovacuum、
检查点由时间/增量双控。但内核调优知识没有作废——它变成**审查自动化正确性的能力**：
自动 vacuum 失灵的巨型表、缓冲池污染（一次性大扫描）攻防，仍是 2026 年工单常客（⚠️ 业界共识，非单一文献）。

## 章要速览：三个要点与三个坑

- 要点：缓冲池收益有饱和点；日志/检查点是恢复时间 vs 吞吐的滑块；维护型部件（vacuum/统计）是最便宜的性能保险。
- 坑：把内存加到工作集以上还继续加；fsync 语义被电池缓存欺骗；大扫描污染缓冲池挤走热点页。

## 自测题（合上笔记作答）

1. 页大小对点查与扫描的相反影响，各自的机理是什么？（提示：IO 头成本 vs 稀疏浪费）
2. 组提交为什么能提升吞吐？它牺牲了什么？（提示：单次 fsync 摊薄 vs 提交延迟）
3. 锁升级的触发条件与副作用链？（提示：内存 vs 并发度）
4. 用 1.6 倍、平台段两个关键词复述你 🔧 实验的结论。（提示：2MB→16MB 有效，16MB→64MB 无感）
5. autovacuum 失灵会造成什么可观测症状？如何与索引膨胀区分？（提示：深度/扫描行数/死元组比）

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
| --- | --- | --- |
| 页大小 | page size | IO 与并发权衡的基础单位，小页利点查、大页利扫描 |
| 缓冲池 | buffer pool | 磁盘页的内存缓存，DBMS 第一性能旋钮 |
| 工作集 | working set | 一段时间内被访问的数据页集合，决定缓冲池收益上限 |
| 置换策略 | replacement policy | LRU 及其变体，决定谁被逐出内存 |
| 预读 | prefetching | 顺序访问模式下提前拉页，摊薄 IO 延迟 |
| WAL | write-ahead logging | 修改落盘前日志先持久化的协议 |
| 检查点 | checkpoint | 把脏页批量刷盘以缩短恢复的机制，过密伤吞吐 |
| 组提交 | group commit | 合并多次提交的同步日志写，降低 fsync 次数 |
| 锁升级 | lock escalation | 行锁数量过大时折成页/表锁省内存的机制 |
| 闩锁 | latch | 保护内存结构（页、哈希桶）的轻量短期锁 |
| vacuum | vacuum / garbage collection | 回收死元组、防索引膨胀的维护动作 |
| 填充因子 | fill factor | 页预留空白的比例，用空间换页分裂率 |
| 写放大 | write amplification | 逻辑写与实际落盘量之比，日志/索引/页分裂都会抬高它 |

## 最新演进与工业实践

- **内存时代的重写**："buffer 池 + 页"范式被两股力量改写：(1) 内存数据库跳过缓冲层
  （HyPer/SAP HANA、SQL Server Hekaton）；(2) LeanStore 用 Bw-tree 变体与无闩锁并发把
  "磁盘数据库做出内存性能"，ICDE 2018，DOI: [10.1109/icde.2018.00026](https://doi.org/10.1109/icde.2018.00026)
  （✅ Crossref 200）——本章缓冲池议题在主流新引擎中已被"页面直达 + 指针固定"吸收。
- **存储分离后的日志调优**：Aurora/SWHardt 把 redo 下推到存储层，"日志即复制"，
  本章的检查点/组提交账本被整体重写：Amazon Aurora 设计论文 SIGMOD 2017，
  DOI: [10.1145/3035918.3056101](https://doi.org/10.1145/3035918.3056101)（✅ Crossref 200）。
- **LSM 接管写密集场景**：RocksDB/LevelDB/Cassandra 一族把"页分裂调优"替换为"compaction 调度调优"，
  系统学习路径见 [../Database_Internals/07-日志结构存储.md](../Database_Internals/07-日志结构存储.md)。
- **自动化的残余人工位**：MySQL 8.0 `innodb_buffer_pool_size` 在线调整、PG autovacuum 的
  `vacuum_cost_*` 细旋钮仍要求人类判断（转述官方文档语义 ⚠️ 未逐条实测）。
- 🔧 **饱和点实验（本章缓冲池结论的最小复现）**：Python 3 + 内置 sqlite3；
  建 300k 行表（4KB 页，约 10.9MB），循环 `SELECT sum(b) FROM t`，分别设
  `PRAGMA cache_size=-2000/-16000/-64000`，每组重复取最小值。本机结果：18.2ms → 11.3ms → 11.3ms，
  印证"工作集全驻后缓冲池旋钮进入平台段"；同时 first-run vs 重复跑差近 1 倍，提醒预热的重要性。
