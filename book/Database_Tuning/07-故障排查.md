## 这一章在讲什么

29 页由业界顾问执笔的**故障排查流程学**——全书最具"方法论"气质的一章，也是本书标题
"Troubleshooting Techniques"的兑现处。作者立场：性能问题大多是**流程问题**，
工具只是流程的载体。

### 1. 分诊（triage）：先问现象，别看图表

- 开场纪律 ⚠️ 推定：确认"从什么时候开始、影响哪些业务、变化了什么"（change management 三问），
  再进入数据采集；大量误诊源于跳过"最近变更"这一问。
- 区分**症状与病因**：CPU 高、锁等待长、日志同步慢常常互为表象；
  要用负载画像把症状钉到具体查询/事务上。

### 2. 系统化的等待账本

- "响应时间 = 各类等待之和 + 服务时间"的分解框架（等待：CPU 队列、IO、锁/闩锁、日志同步、网络）⚠️ 表述。
- 每类等待的取证工具（2002 年版）：OS 工具（vmstat/iostat）、DBMS 内部视图/统计、
  以及 TurboData 一类第三方实时监控（本章作者的产品背景 ⚠️ 推定）。
- 与现代 APM 的对应：今天的 eBPF 采集、Performance Insights 等待直方图是同一账本的仪器化。

### 3. 常见故障模式清单

- 统计过期 → 计划突变；锁升级 → 排队风暴；批量作业撞高峰；日志盘与数据盘争用；
  连接风暴（建连/认证打满 CPU）；"昨天的 good plan 今天变 bad plan"⚠️ 具体清单条目。
- 处理建议一律给到**可逆优先**：先计划固定/绑定，再动索引，最后才动参数——
  与第 15 章"参数是最后手段"的告诫呼应。

### 4. 复盘与防复发

- 每次事故沉淀为：负载指纹、触发条件、处置动作、预防项四件套 ⚠️ 推定。
- 本章暗含的观点在 2026 成为产品形态：**runbook 自动化 + 根因分析代理**。

## 2002 → 2026 的位置

排查流程本身高度稳定（change→symptom→wait-account→root-cause 仍是各家培训模板），
变化在取证密度与处置自动化：
eBPF/PMU 级观测、分布式追踪把"等待账本"做到单请求粒度；
LLM 代理（D-Bot/SuperDRI）开始自动跑"假设→取证→验证"循环——本章从"人肉流程"升级为"人审流程"。

## 常见误读与澄清

- 误读：等待账本必须有商业工具
  澄清：原生视图 + OS 工具即可完成第一层分解；工具只是取证密度差异，框架本身零成本
- 误读：排障快=英雄
  澄清：本章立场相反：四件套复盘与预防项才算闭环；无沉淀的快恢复会排队等下一次
- 误读：LLM 诊断上线后流程学作废
  澄清：代理接管取证与初判，人保留处置审批与复盘——流程学恰好变成'给代理写验收规范'的学问

## 章要速览：三个要点与三个坑

- 要点：先问变更再看图；等待账本让慢可分解；处置按可逆性排序（固定计划→索引→参数）。
- 坑：跳过最近改了什么直接重启；把症状当病因（CPU 高不等于 CPU 是根因）；一次事故只留已恢复不留四件套。

## 自测题（合上笔记作答）

1. 分诊三问的内容与顺序？（提示：何时起/影响面/变更史）
2. 锁风暴与慢查询风暴在等待账本上如何区分？（提示：锁等待 vs IO/CPU 占比）
3. good plan 变 bad plan 的三种常见诱因？（提示：统计/参数/版本）
4. 为什么参数调整排最后？（提示：耦合强、归因难、回滚慢）
5. D-Bot 类 LLM 代理接管的是流程的哪几步？人保留哪几步？（提示：取证自动化 vs 处置审批）

## 动手验证设想（练习，非实测结论）

- 在本地 PG/MySQL 制造统计过期→计划劣化标本：ANALYZE 前后对比计划与耗时（SQLite 用 ANALYZE 亦可，🔧 低成本）。
- 给一次历史故障补写四件套：负载指纹/触发条件/处置动作/预防项。
- 把某监控面板的指标逐条映射进等待账本框架，找出缺失项。

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
| --- | --- | --- |
| 分诊 | triage | 按影响与紧急度定级、确定排查顺序的入口动作 |
| 变更追溯 | change inquiry | 询问"最近动了什么"，性能事故的第一诊断问题 |
| 等待账本 | wait breakdown | 把响应时间分解为各类等待与服务的求和模型 |
| 负载指纹 | workload signature | 能识别同一负载的查询形状/比率/热点特征 |
| 计划回归 | plan regression | 同查询因统计/版本变化改用劣化计划 |
| 锁风暴 | lock convoy | 热点行/锁升级造成的大面积排队 |
| 绑定执行计划 | plan binding / outlining | 人工固定计划以止血的手段 |
| 根因分析 | root cause analysis (RCA) | 从症状回溯到可修复病因的过程 |
| 运行手册 | runbook | 沉淀故障处置步骤的文档/自动化脚本 |
| 可逆优先 | reversible-first | 止血动作按可回滚程度排序的操作纪律 |
| 事后复盘 | postmortem | 事故后沉淀指纹/触发条件/预防项的机制 |
