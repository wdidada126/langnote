# 03 索引调优（Index tuning）

> 原书第 3 章，pp.77–121，作者 ✅ Dennis Shasha & Philippe Bonnet（Crossref 记录）。
> DOI: 10.1016/b978-155860753-8/50004-4（✅ Crossref 200）。
> 章题与页幅 ✅ 实抓；正文为主题级精读重构，未对照原文的细断言标 ⚠️。

## 这一章在讲什么

45 页的索引专章：不是"索引入门"，而是**索引选型与索引组合的调优账本**——
每种索引结构回答三个问题：加速什么访问形状、付出什么写代价、优化器会不会真的用它。

### 1. 索引结构的种类（以 2002 年视野）

- B 树/位图（bitmap）/哈希/聚簇（clustered）四大件，加上当年偏门的空间索引与文本索引 ⚠️ 具体覆盖面。
- **位图索引**是本章时代特色：低基数列（性别、州、状态）上等值/AND-OR 组合极快，
  但对高并发写是灾难（锁粒度粗）——OLTP 慎用、数仓常用。这条边界到 PG 的
  BRIN/部分索引时代仍然成立 ⚠️ 类比。
- 复合索引的列序规则（等值列在前、范围列殿后）与"覆盖索引免回表"的账 ⚠️ 推定有讲。

### 2. "该建什么索引"的组合问题

- 索引选择是**组合爆炸 + 相互耦合**：加一个索引会改变优化器对其他索引的使用方式；
  章内强调"以负载为单位整体设计，而非以查询为单位打补丁" ⚠️。
- 索引维护成本被量化为写放大：每个二级索引都是一次额外 B 树插入 + 可能的页分裂 ⚠️。

### 3. 索引失效的形态学

- 函数包裹列、隐式类型转换、前导通配 LIKE、OR 展开、统计过期——"优化器宁走全表"的诱因清单 ⚠️ 具体条目。
- 与第 14 章（访问计划）配套使用：**从执行计划反推索引建议**，而不是反过来。

### 4. 🔧 本章结论的最小复现（本机 SQLite）

- 300k 行表上 `WHERE a BETWEEN 0.5 AND 0.501`（约 309 行命中）：无索引全表 29.3ms，
  建 `ix_a(a)` 后 0.2–0.3ms，`EXPLAIN QUERY PLAN` 显示
  `SEARCH t USING COVERING INDEX ix_a (a>? AND a<?)` ——约百倍收益，来自"扫描量从 30 万降到 309"。
- 但同一表上 5% 命中的宽范围查询里，索引路径 0.3ms 仍胜"强制表达式全扫"12ms——
  注意这只是 SQLite 的**覆盖索引窄扫**红利；换成含宽行的非覆盖二级索引 + 回表，
  范围一宽优化器就会改走全表（2002 与 2026 同理）。复现方法见文末实验记录。

## 常见误读与澄清

- 误读：百倍收益可以外推到大范围查询
  澄清：窄命中收益来自扫描量坍缩；选择率上升后回表成本反噬，收益曲线随形状陡降——先算命中行数再决定
- 误读：索引越多，优化器可选余地越大越安全
  澄清：候选索引改变统计与计划形态，重叠索引还会误导选择率估计；本章立场是负载级精选而非堆量
- 误读：位图索引已死
  澄清：在低基数过滤+读为主的分析负载里其思想以 Roaring bitmap/分区裁剪形态存活，见 [10](10-数据仓库调优.md)

## 章要速览：三个要点与三个坑

- 要点：索引按访问形状计价（读收益/写代价/回表税）；索引选择是负载级组合问题；位图属低基数数仓、OLTP 慎入。
- 坑：以查询为单位逐个加索引导致重叠冗余；函数包裹列/隐式转换弃索引；统计过期让索引存在但不被用。

## 自测题（合上笔记作答）

1. 覆盖索引为何能免回表？它的维护成本变了吗？（提示：叶内容 vs 键数）
2. 复合索引 (a,b) 能服务哪些谓词形状？（提示：前缀规则）
3. 🔧 实验里窄范围百倍收益的来源，一句话是什么？（提示：扫描量 30 万→309）
4. 位图索引在 UPDATE 一个低基数列时为什么贵？（提示：位向量维护与锁）
5. 自动索引管理（Azure 类）删索引的判据可能是什么？（提示：最后使用时间/收益评估）

## 动手验证设想（练习，非实测结论）

- 在本机 SQLite 给同一表做 3 个重叠索引（单列/复合/覆盖），跑同一负载观察插入耗时梯度——量化写放大。
- 用 PRAGMA index_list + 查询计划对比函数包裹列前后，验证索引弃用形态。
- 把某生产慢 SQL 的索引建议写成负载画像→候选索引→预期扫描量三段论。

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
| --- | --- | --- |
| 二级索引 | secondary index | 与物理行序无关、按键值定位行的辅助结构 |
| 聚簇索引 | clustered index | 叶节点即数据行的索引，一张表至多一个 |
| 覆盖索引 | covering index | 索引自带查询所需全部列，免回表 |
| 位图索引 | bitmap index | 每取值一个位向量，低基数列数仓利器、OLTP 写杀手 |
| 索引选择 | index selection | 在负载与写代价约束下挑索引子集的组合问题 |
| 回表 | table lookup / fetch by rowid | 经索引取到键后再按行位置取完整行的额外访盘 |
| 索引失效 | index bypass | 谓词形状/转换/统计导致优化器放弃可用索引 |
| 选择性 | selectivity | 谓词命中行占比，索引收益的第一变量 |
| 写放大（索引） | index write amp | 每次基表写触发的索引维护总量 |
| 索引膨胀 | index bloat | 页碎片与死元组使索引深度/体量虚胖 |
| 列序 | column order (composite) | 复合索引中列的排列，决定可服务的谓词前缀 |
| 自动索引管理 | automatic index management | 系统按负载画像自动建议/创建/删除索引的产品能力 |

## 最新演进与工业实践

- **学习型索引**：Kraska 等《The Case for Learned Index Structures》把 B 树重述为"从键到位置的回归模型"，
  SIGMOD 2018，DOI: [10.1145/3183713.3196909](https://doi.org/10.1145/3183713.3196909)（✅ Crossref 200）；
  工程落地仍以混合形态为主（如 [../Database_Internals/06-B树变体.md](../Database_Internals/06-B树变体.md) 谱系），纯 learned index 在通用 DBMS 中尚未主流 ⚠️。
- **云厂商常开自动化**：Azure SQL Database Automatic tuning 的 index management 按"最后一个计划是否索引创建/删除建议"
  自动执行并可回滚，官方文档 https://learn.microsoft.com/en-us/azure/azure-sql/database/automatic-tuning-overview （✅ 200）；
  AWS RDS/Aurora 侧以 Performance Insights + Database Activity Streams 提供决策数据面
  https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PerfInsights.html （✅ 200）。
- **PG 生态**：无内建自动索引顾问，社区以 pg_stat_statements（✅ 文档可达
  https://www.postgresql.org/docs/current/pgstatstatements.html ）+ 外部顾问工具承担"负载→索引建议"闭环 ⚠️ 工具选择转述。
- **数仓侧**：Snowflake/BigQuery 等托管数仓弱化物理索引概念（聚类键/分区取代传统索引），
  本章的"索引账本"转为"微分区+裁剪"账本——对照 [../大数据SQL优化.md](../大数据SQL优化.md) 与
  [10-数据仓库调优.md](10-数据仓库调优.md)。

  Python 3 内置 sqlite3，300k 行、4KB 页；窄范围查询 min-of-3 计时对比"建索引前后 + EXPLAIN QUERY PLAN"，
