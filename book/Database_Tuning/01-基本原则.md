# 01 基本原则（Basic principles）

> 原书第 1 章，pp.1–8，作者 ✅ Dennis Shasha & Philippe Bonnet（Crossref 记录）。
> DOI: 10.1016/b978-155860753-8/50002-0（✅ Crossref 200）。
> 章题与页幅 ✅ 实抓；小节内容为主题级精读重构，细粒度论断标 ⚠️。

## 这一章在讲什么

全书最短的"总纲"章：用 8 页把调优从"玄学手艺"拉回"有章法的工程活动"。
按两位作者一贯的实验主义立场（他们在 NYU/EPFL 长期开数据库性能实验课，本书大量实验即课程素材 ⚠️），
本章给出的不是某个参数的取值表，而是一套**思维框架**。

主题级重构（⚠️ 具体表述未对照原文）：

### 1. 性能是行为，不是数字

- 孤立的"每秒事务数"没有意义；性能必须绑定**工作负载（workload）**来谈：
  同样的 DBMS，改一改谓词形状、并发度、数据分布，结论就可能翻转。
- 由此推出本书的方法论骨架：**先刻画负载，再动手调**——负载画像（查询形状、热点、读写比、
  数据规模与分布）是第 7 章故障排查和第 15 章参数治理的共同输入。

### 2. 测量、假设、实验三步循环

- 调优 = 受控实验：一次只动一个因素（参数/索引/改写），留对照，看端到端指标；
  "凭手感连改五个参数然后宣布有效"是本枚举禁的反模式 ⚠️。
- 警惕**测量假象**：缓存预热不足、客户端瓶颈、统计口径（均值 vs 尾延迟）都能制造虚假结论 ⚠️。
  这条在 2026 年依然是 AIOps 论文的痛点（见文末演进节）。

### 3. 系统级视角：瓶颈会迁移

- 修掉一个瓶颈，系统立刻暴露下一个瓶颈（buffer 够了变锁竞争，锁少了变 IO）——
  所以调优必须是**全栈循环**：应用 → SQL → 索引 → 引擎 → OS → 硬件。
  这个"瓶颈迁移"观正是第 2 章（内核）、第 5 章（应用边界）、第 7 章（排查流程）的分章逻辑 ⚠️ 推定。

### 4. 代价模型意识

- 一切优化都是拿一种代价换另一种：索引换写放大、反规范化换一致性维护、缓存换内存。
  章末应当点出全书关键词：**没有免费的调优，只有显式的交换** ⚠️。

## 为什么说它"老"而不过时

2002 年这本书面对的是 Illustra/DB2/Oracle/SQL Server/MySQL 混战的"手动挡时代"；
今天主流 DBMS 已把大量"基本原则"内化为自治能力（自动统计、自动索引建议、自动参数）。
但"负载驱动 + 受控实验 + 代价交换"三件套恰恰是评估这些自动系统是否可信的判据——
2026 年所有 learned optimizer / auto-tuning 论文仍要在实验协议上回应本章的立场。

## 常见误读与澄清

- 误读：把本章当'可跳过的引言'——它是全书判据库
  澄清：后续各章的每个结论都默认回链到负载绑定/受控实验/代价交换三判据，跳读者会在 07/15 章失去坐标系
- 误读：'方法论=慢'，直接翻参数表更快
  澄清：无方法的参数改动在生产上是负资产；本章 8 页的用途正是防止 68 页（第 2 章）知识被误用
- 误读：实验思想属于手工时代
  澄清：自动调优系统（COSMIC/Azure）内部跑的就是同一套假设检验，只是执行者换成算法——审查者仍需本章素养

## 章要速览：三个要点与三个坑

- 要点：性能必须绑定工作负载陈述；调优是受控实验不是手感活；瓶颈会迁移，需全栈循环。
- 坑：拿均值掩盖尾延迟；一次改多个参数导致归因失败；忽略预热/测量假象把缓存效应记成调优收益。

## 自测题（合上笔记作答）

1. 为什么本书反对孤立的每秒事务数陈述？负载画像包含哪些要素？（提示：本章第 1 节）
2. 一次只动一个因素在多大程度上还适用于今天的自动调优系统？（提示：对照文末 COSMIC 的搜索式调优与单因子实验的张力）
3. 瓶颈迁移的例子：加大缓冲池后最可能新出现的瓶颈是什么？如何取证？（提示：CPU 闩锁、锁等待、日志同步三类）
4. 写出测量—假设—实验—复检四步在你的 MySQL 实例上的具体工具映射。（提示：performance_schema / sys schema / 慢日志）
5. 均值相同、p99 差 3 倍的两个配置，你如何设计实验区分？（提示：样本量、时间窗、峰谷分层）

## 动手验证设想（练习，非实测结论）

- 用 SQLite 对同一查询分别记录 first-run 与 min-of-10，感受预热差异（数据在 repo 外 tmp 目录）。
- 把一个开源应用的真实 SQL 日志按读/写/范围/点查/聚合分类，产出一页负载画像——这就是本章方法论的作业版。
- 找一次历史事故复盘，检查是否先问了最近变更了什么。

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
| --- | --- | --- |
| 工作负载 | workload | 一组绑定业务场景的查询/事务形状、频率与数据分布，性能讨论的前提 |
| 调优循环 | measure–hypothesize–experiment | 测量、立假设、单因素受控实验再测量的工程循环 |
| 端到端指标 | end-to-end metric | 以用户可见延迟/吞吐为准，而非某内部计数器 |
| 尾延迟 | tail latency | p95/p99 延迟；均值掩盖的问题在这里暴露 |
| 瓶颈迁移 | bottleneck shifting | 修掉一个瓶颈后系统暴露下一个瓶颈的现象 |
| 代价交换 | trade-off | 用一种开销（如写放大）换另一种开销（如读放大）的显式决策 |
| 性能保证 | performance guarantee | 负载不变时系统对响应时间的可验证上界陈述 |
| 全栈视角 | full-stack view | 应用—SQL—索引—引擎—OS—硬件逐层看瓶颈 |
| 测量假象 | measurement artifact | 预热不足、客户端瓶颈、口径错误造成的虚假结论 |
| 基线 | baseline | 任何"改进"所对照的未改动状态 |

## 最新演进与工业实践

- **负载刻画 → 现代基准体系**：TPC-C/TPC-H/TPC-DS 与 JobBench、StarStone 等仍在服役；
  2015 年 Leis 等的批判性测量学研究指出"基准只测优化器想得到的形状"，正是本章"负载驱动"立场的延续与实证：
  Leis et al., *How Good Are Query Optimizers, Really?*, PVLDB 8(2), 2015，
  DOI: [10.14778/2732977.2732978](https://doi.org/10.14778/2732977.2732978)（✅ Crossref 200）。
- **受控实验的自动化——knob tuning 谱系**：本章"一次动一个因素"的人工循环，2017 年起被机器学习接管：
  Padmanabhan 等（OtterTune/COSMIC）把 DBMS 旋钮配置形式化为大规模机器学习问题，SIGMOD 2017，
  DOI: [10.1145/3035918.3064029](https://doi.org/10.1145/3035918.3064029)（✅ Crossref 200）。
  实践含义：今天的"基本原则"课应当教的是**如何审查自动系统的实验协议**，而非亲手改参数。
- **LLM 时代的 DBA 自动化**：清华 D-Bot 用大模型做数据库诊断，把"测量→假设→实验"循环外包给 LLM 代理，
  PVLDB 2024，DOI: [10.14778/3675034.3675043](https://doi.org/10.14778/3675034.3675043)（✅ Crossref 200）；
  开源实现 DB-GPT（https://github.com/eosphoros-ai/DB-GPT ，✅ 2026-09 可达）。
- **工业产品化**：Azure SQL Database 的 Automatic tuning 把"识别坏计划→强制/建删索引"做成常开策略，
  官方文档 https://learn.microsoft.com/en-us/azure/azure-sql/database/automatic-tuning-overview （✅ 200）。
- 🔧 **可复现的"测量假象"小实验**（本机 Windows + Python sqlite3 即可）：同一查询重复计时取 min 与取 first
  差异显著——SQLite 页缓存预热前后同一聚合可差 1.6 倍（方法见 [15-配置参数.md](15-配置参数.md)），
  这正是本章警告的"把缓存效应误读为调优收益"的最小示例。
