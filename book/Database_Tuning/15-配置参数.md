## 这一章在讲什么

全书正文收束章：把散落在第 2 章各处的"旋钮"上升为**参数治理学**——
面对一个几十到几百个配置参数的 DBMS，人类工程师的正确姿势是什么。
它不是参数手册复述，而是"参数为什么经常帮倒忙"的元讨论 ⚠️ 依章题与篇幅推定。

### 主题级重构（⚠️）

1. **参数的分类学**
   - 结构类（页大小、文件布局——装库时定，改动如换骨）、
     容量类（缓冲池、日志缓冲、排序区——随内存伸缩）、
     策略类（LRU 变体、并发上限、检查点节奏——随负载调）、
     运维类（超时、重试、诊断开关——出事才动）⚠️ 分法为通用框架套用于本章语境。
2. **交互效应与"参数不是独立坐标"**
   - 单参数曲线常常是平台 + 悬崖；参数之间存在强耦合（缓冲池大小会改变预读收益、
     并发上限会改变锁参数效果）——逐个手调在数学上就不可靠 ⚠️。
3. **默认值的政治学**
   - 出厂默认是"装机演示兼容值"而非你的负载最优值；但"全部推倒重调"同样鲁莽——
     本章立场应是"用负载画像筛出少数敏感参数重点实验"（帕累托式调优）⚠️ 推定。
4. **变更纪律**
   - 每次一个参数、留基线、可回滚、记录到配置台账；
     把参数当作"配置即代码"管理——2002 年罕有的前瞻表述 ⚠️。
5. **饱和与平台段**
   - 核心心智模型：**多数参数存在收益平台段，越过后继续调是负作用或纯风险** ⚠️。
   - 🔧 最小复现（本机 Python sqlite3，方法：对约 11MB 工作集反复全表聚合，
     只变 `PRAGMA cache_size=-2000/-16000/-64000`，每组 min-of-3）：
     18.2ms → 11.3ms → 11.3ms——2MB 到 16MB 有效，16MB 之后进入平台段，与本章心智模型定量吻合。

## 2002 → 2026 的位置

这一章预见的问题，恰是 2010–2020 年代"自动调参研究"要吃的领域：

- **knob tuning 学术线**：从规则引擎（AutoAdmin 家族）→ 贝叶斯/强化学习（OtterTune/COSMIC）→
  因果/迁移学习（商业化的 OTT 系与云厂商内部系统）。
- **产品现状**：托管数据库把"容量类"参数收回平台侧（用户不再设 buffer pool），
  只暴露少数"意图类"开关；自建 DB 的 DBA 则面对参数数量的爆炸（PG 三百余个 GUC）。
- **DBA 角色迁移**：从"调参数的人"变成"审查自动调优建议 + 管理例外的人"——本章的
  变更纪律（一次一项、可回滚、留台账）原样写进了 2026 的 GitOps/变更管理流程。

## 常见误读与澄清

- 误读：自动调优普及后参数知识作废
  澄清：平台仍暴露意图类开关与例外通道；无参数模型的人无法判断建议是否越界
- 误读：台账是官僚流程
  澄清：台账的价值在归因速度：事故时'谁动过什么'是 30 分钟与 3 天的差
- 误读：平台段位置恒定
  澄清：平台段随负载移动；每季度对高影响参数重跑平台实验是本章纪律的现代版

## 章要速览：三个要点与三个坑

- 要点：参数强耦合、单参逐个调在数学上不可靠；多数参数有平台段，越过后是纯风险；变更纪律（一项/基线/回滚/台账）重于调对数值本身。
- 坑：全量推翻默认值；只调不改代码（负载问题误诊为参数问题）；参数无台账导致故障无法归因。

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
| --- | --- | --- |
| 旋钮（参数） | knob / configuration parameter | DBMS 可调运行时配置项的统称 |
| 参数交互 | knob interdependency | 参数效果相互调制、不可逐维独立优化的现象 |
| 平台段 | saturation plateau | 参数超过某阈值后性能不再响应的区间 |
| 敏感参数 | influential knobs | 对目标负载性能方差贡献最大的少数参数 |
| 配置漂移 | configuration drift | 环境间配置随时间分叉的运维病 |
| 配置即代码 | configuration as code | 参数入版本库、经评审与回滚流程的管理形态 |
| 变更台账 | change ledger | 记录"谁在何时为何改了什么参数"的可追溯清单 |
| 自动调参 | auto-tuning / knob tuning | 以搜索/学习算法替代人工调参的研究与产品 |
| 冷启动 | cold start | 新负载/新库缺乏历史数据使调参或模型失效 |
| 意图驱动配置 | intent-based config | 用户只声明目标（SLA），平台反推内部参数 |

  Large-scale Machine Learning*（COSMIC/OtterTune），SIGMOD 2017，

- **LLM 进入配置面**：D-Bot（PVLDB 2024，DOI: [10.14778/3675034.3675043](https://doi.org/10.14778/3675034.3675043) ，✅ 200）
  含参数类诊断；开源 DB-GPT https://github.com/eosphoros-ai/DB-GPT （✅ 200）。
- **云产品现状**：Azure SQL 自动调优文档（✅ 链接见 [14-理解访问计划.md](14-理解访问计划.md)）；
  AWS RDS 的 Parameter Group 机制承担"配置即代码 + 动态参数应用" ⚠️ 转述文档语义，未实测。
- **PG 生态**：GUC 体系 + `pg_stat_statements`（https://www.postgresql.org/docs/current/pgstatstatements.html ，✅ 200）
  仍是"负载画像→筛敏感参数"的手工闭环首选 ⚠️ 实践共识陈述。
- 🔧 **平台段实验协议（可直接抄）**：Python 内置 sqlite3；表约 30 万行/11MB；
  固定查询 `SELECT sum(b) FROM t`；依次设 `cache_size=-2000`、`-16000`、`-64000`，
  每档重复多次取最小值并记录——得到 18.2/11.3/11.3ms 的平台曲线；
  同法可迁移到任意引擎的"内存类参数"测试（改容量、留对照、取极值），数据在 repo 外 tmp 目录。
