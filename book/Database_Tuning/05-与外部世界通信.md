# 05 与外部世界通信（Communicating with the outside）

> 原书第 5 章，pp.165–184，作者 ✅ Dennis Shasha & Philippe Bonnet（Crossref 记录）。
> DOI: 10.1016/b978-155860753-8/50006-8（✅ Crossref 200）。
> 章题与页幅 ✅ 实抓；正文为主题级精读重构，未对照原文的细断言标 ⚠️。

## 这一章在讲什么

20 页讲**数据库与应用/外部数据的接口面调优**——"瓶颈经常不在肚子里，而在嘴边"：
网络往返、驱动栈、批量搬运、过程化边界。本章把"应用与 DB 的通信"本身当作一等调优对象，
这在 2002 年是超前的（当时多数调优书只谈引擎内部）。

### 1. 往返成本：连接与游标的账

- 每条"一问一答"都付一个 RTT + 协议解析 + 授权检查的税；**减少往返次数**优先于减少单次工作量 ⚠️ 表述。
- 连接池是本章时代的标配答案（当年 JDBC/ODBC 池刚普及）：建连（登录、会话初始化）是重操作，
  池化后主要成本转为"借出归还 + 会话状态残留"⚠️。
- 服务端游标 vs 客户端逐行 fetch：fetch size 太小放大往返、太大占内存并延迟首行 ⚠️。

### 2. 批量搬运：bulk load / export

- 批量装载绕过事务与逐行触发器的路径（直接页写入/表级装载命令）当年已是各厂商分水岭 ⚠️ 具体命令。
- 索引入场顺序的账：**先建表→装载→后建索引**通常优于边装边建 ⚠️ 与第 3 章互联。
- 外部表/异构数据源（Federated）的远程谓词下推：把过滤推到源端，别把全表拉回来再筛 ⚠️ 推定。

### 3. 过程化边界：SQL 里放什么，外面放什么

- 存储过程把"多语句工作流"折叠成一次调用，省往返但把 CPU/内存压力搬进数据库进程 ⚠️ 两难陈述。
- 数组/包参数、临时表传值等"减少行级往返"技巧 ⚠️。
- 立场（据两位作者风格推定）：**按数据量与并行度决定边界**——细粒度业务逻辑放应用，
  大数据量集合操作留引擎。这与第 8 章电商案例中的边界选择互相引用 ⚠️。

### 4. 应用侧协同

- ORM 的 N+1、预取的缺失、事务边界横跨网络（"在事务里等人"）——本章已具雏形地批评 ⚠️ 条目推定。
- 网络与协议层：MTU、TCP keepalive、DB 与中间件同机/跨机房放置，属 2002 年"应用服务器时代"常识 ⚠️。

## 2002 → 2026 的位置

本章的账本不但没作废，反而更重要：微服务把"一次调用"变成"跨网络的多次 RPC-DB 混合往返"，
往返成本被放大。新变量是：**CDC 取代轮询**（Debezium/Kafka）、**边缘缓存取代重复查询**（Redis 族）、
**Serverless/连接层重构**（PgBouncer→Supavisor、Aurora Serverless v2、Prisma/Data API 的 HTTP 化）。

## 常见误读与澄清

- 误读：接口面调优='加连接池'
  澄清：池只是固定成本摊销器；本章优先级是减少往返次数（批量化/折叠调用）> 复用连接 > 调池参数
- 误读：ORM 时代这章过时了
  澄清：N+1 与过度 eager-loading 恰是本章问题在 ORM 上的复现；预取/延迟加载的账仍是 RTT 账
- 误读：批量装载只关乎 DBA
  澄清：先装后建、窗口隔离需要应用与调度协同——本章是 DBA 与开发的第一联合课题

## 章要速览：三个要点与三个坑

- 要点：往返是接口面基本税；连接与游标参数决定每次调用的固定成本；装载顺序（先装后建）影响数量级。
- 坑：ORM N+1；事务里夹人机等待/远程调用；把过滤拉回应用层做（应下推）。

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
| --- | --- | --- |
| 往返时间 | RTT / round-trip time | 一次请求-响应的网络+协议周期，接口面调优的基本货币 |
| 连接池 | connection pooling | 复用已认证会话以免反复登录/初始化 |
| 服务端游标 | server-side cursor | 结果集驻留服务器、分批取回的游标 |
| 取回批大小 | fetch size | 每次游标取回的行数，太小放大往返太大占内存 |
| 批量装载 | bulk load | 绕开逐行事务路径的高吞吐写入方式 |
| 谓词下推 | predicate pushdown | 把过滤条件推到数据源端执行，减少搬运量 |
| 存储过程 | stored procedure | 在引擎内执行的多语句过程，用一次调用折叠多次往返 |
| 异构数据源 | federated source | 经网关访问的外部库，计划质量取决于远程下推 |
| N+1 查询 | N+1 queries | ORM 逐对象补查导致的往返风暴 |
| 事务跨网络持锁 | long-running transaction | 事务提交前夹入人工/远程慢操作 |
| 变更数据捕获 | CDC (change data capture) | 从日志/触发器导出变更流供外部系统消费 |

## 最新演进与工业实践

- **CDC 成为标准出口**：Debezium（https://debezium.io/ ，✅ 200）基于事务日志的变更流 +
  Kafka（https://kafka.apache.org/ ，✅ 200）承载，把本章"批量导出/轮询"替换为订阅式微批，
  是"与外部世界通信"在 2026 的主形态 ⚠️ 采用面陈述为业界共识。
- **连接层云原生化**：托管代理（PgBouncer 语义的云上版本）与"HTTP 化数据 API"消除跨可用区建连风暴 ⚠️ 厂商名未逐一实测，作转述。
- **云仓库的装载面**：Snowflake 以微批 COPY INTO + 自动克隆承担 bulk load 角色，其架构论文
  Dageville 等 *The Snowflake Elastic Data Warehouse*，SIGMOD 2016 记录，
  DOI: [10.1145/2882903.2903741](https://doi.org/10.1145/2882903.2903741)（✅ Crossref 200）。
- **Aurora 的接口侧代价**：计算/存储分离把"数据库↔存储网络"变成性能主轴，redo 下推的账见
  *Amazon Aurora* SIGMOD 2017，DOI: [10.1145/3035918.3056101](https://doi.org/10.1145/3035918.3056101)（✅ 200）。
- ⚠️ Oracle/SQL Server 的 OCI/TDS 协议层优化：转述官方文档，未本机实测。
