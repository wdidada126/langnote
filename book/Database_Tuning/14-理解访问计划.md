# 14 理解访问计划（Understanding access plans）

> 原书第 14 章，pp.337–348，12 页。作者 ✅ Alberto Lerner（Crossref 记录，与第 7 章同一人）。
> DOI: 10.1016/b978-155860753-8/50015-9（✅ Crossref 200）。
> 章题、页幅、作者 ✅ 实抓；正文为主题级精读重构，细断言标 ⚠️。

## 这一章在讲什么

12 页教一件"元技能"：**读优化器吐出来的访问计划（执行计划），并据此反推病因与药方**。
第 7 章（排障）负责"流程"，本章负责"证据"——作者同为业界顾问，两章构成一套
"观察→取证→处置"的完整闭环，是全书实操含金量最高的组合。

### 主题级重构（⚠️ 依章题、作者职业线（TurboData/Oracle 生态）与当时主流引擎计划形态）

1. **计划的两副面孔**
   - 估算值（estimated cardinality/cost）与实测值（actual rows/time）并排看：
     差异爆炸处即病因所在——统计过期、参数嗅探（bind peeking）、坏连接顺序 ⚠️ 术语。
   - "cost 是内部货币，不可跨版本比较；rows 与 time 才是可审计的事实" ⚠️ 立场推定。
2. **算子形状学**
   - 索引范围扫 vs 索引全扫 vs 表访问（回表/堆扫）、嵌套循环的内表放大、
     排序/哈希连接与内存溢出落盘 ⚠️ 清单。
   - 行源算子树的阅读顺序（由内而外/缩进法）与"每算子的 rows×cost 直觉"。
3. **常见计划病理**
   - 统计缺失/过期导致的选择率误估、绑定变量窥探导致的坏计划固化、
     隐式转换导致的索引弃用、连接次序错误造成中间结果爆炸 ⚠️ 具体条目。
4. **处置手册**
   - 止血：提示/计划固定（outlining）；根治：补统计、改写查询、增删索引；
     复检：用同一 SQL 的计划对比确认 ✅ 逻辑由第 7 章流程推得。
5. **工具面（2002）**
   - EXPLAIN/`tkprof`/DBMS_XPLAN 类原生工具与 TurboData 类第三方会话剖析 ⚠️ 具体点名。

### 为什么这 12 页值钱

计划是 DBMS 唯一"自述意图"的界面；不会读计划的人，所有调优手段都是盲操作。
本章与第 3 章（索引）、第 4 章（改写）构成三角：索引与改写制造候选计划，计划阅读负责验收。

## 2002 → 2026 的位置

工具界面现代化了，但"估算 vs 实际"的诊断法一个字没改，而且各家都把它做成了一等公民：
`EXPLAIN (ANALYZE, BUFFERS)`（PG）、`EXPLAIN ANALYZE FORMAT=JSON`（MySQL）、
SQL Server 实际执行计划 + 自适应查询处理（行反馈现在直接重排计划）、Oracle SQL Monitoring。
新前沿是**让机器读计划**：学习型优化器把计划质量当排序目标（Lero），
坏计划检测（plan regression detection）在云上做成自动回滚（Azure 自动调优）。

## 常见误读与澄清

- 误读：看懂算子名就算会读计划
  澄清：核心动作是估算/实际两列 diff 与最大行数算子定位；算子词典只是词表
- 误读：自动调优产品会替人读计划
  澄清：产品给的是结论与回滚，审查结论（为何 bad、force 是否合理）仍需人工读计划
- 误读：SQLite/PG 计划经验不可迁移到商用库
  澄清：形状/行数/回表词汇跨引擎通用，差异在 cost 单位与算子命名——迁移成本远低于重写

## 章要速览：三个要点与三个坑

- 要点：估算/实际行的背离是首要病因坐标；cost 是内部货币不可跨版本比；读计划是索引与改写两章的验收环节。
- 坑：只看形状不比行数；NLJoin 内表放大陷阱；坏计划固化在缓存里无人审计。

## 自测题（合上笔记作答）

1. NLJoin 内层预估 10 行实际 10 万行的后果量化？（提示：乘法放大）
2. 绑定变量窥探产生坏计划的完整链条？（提示：首参定型→缓存固化）
3. 🔧 实验：WHERE +a 让 SQLite 计划怎么变？为什么？（提示：SEARCH→SCAN，表达式阻断索引）
4. Azure force last good plan 对应本章处置清单哪一档？（提示：止血）
5. Lero 的排序代替代价为何弱化基数估计错误？（提示：直接偏好计划）

## 动手验证设想（练习，非实测结论）

- 采集一条真实慢 SQL 的实测计划，标出估算误差最大的算子，提一条补统计/改写建议。
- 在同一 SQL 上分别制造缺统计/函数包裹/连接逆序三种病态计划，做成计划标本册。
- 给团队列一张每次评审三问：最大行数算子？回表次数？内存溢出迹象？

## 核心概念速览（中英对照）

| 术语 | English | 释义 |
| --- | --- | --- |
| 访问计划 | access plan / execution plan | 优化器选定的算子树与执行顺序 |
| 基数估计 | cardinality estimation | 每算子输出行数的预估，计划质量之母 |
| 估算/实际行 | estimated vs actual rows | 两者背离处即诊断入口 |
| 代价 | cost | 引擎内部比较单位，不可跨版本当度量 |
| 回表 | table access by rowid | 索引命中后取完整行的开销 |
| 绑定变量窥探 | bind peeking | 首次解析按当前参数定计划并被固化 |
| 计划缓存 | plan cache | 软解析复用计划，也是坏计划滞留处 |
| 自适应连接 | adaptive join | 运行时按实际行数在 NL/hash/merge 间改道 |
| 行源统计 | rowsource metrics | 逐算子的行数/时间剖析输出 |
| 统计过期 | stale statistics | 直方图/采样落后数据演化导致误估 |
| 提示固定 | plan pinning/binding | 人工锁定计划作止血手段 |

## 最新演进与工业实践

- **实测计划普及**：PG `EXPLAIN (ANALYZE, BUFFERS)` 文档
  https://www.postgresql.org/docs/current/sql-explain.html （✅ 200）；
  MySQL 8.0 `EXPLAIN ANALYZE`/树状输出文档 https://dev.mysql.com/doc/refman/8.0/en/explain-output.html （✅ 200）。
- **坏计划的自动免疫**：Azure SQL Automatic tuning 的 "force last good plan" 策略
  https://learn.microsoft.com/en-us/azure/azure-sql/database/automatic-tuning-overview （✅ 200）——
  本章"止血三问"的托管实现。
- **统计决定计划质量的实证经典**（本章立场的学术后盾）：Leis 等，PVLDB 2015，
  DOI: [10.14778/2732977.2732978](https://doi.org/10.14778/2732977.2732978)（✅ Crossref 200）。
- **学习型优化器直接"读计划"**：Lero（PVLDB 2023，DOI: [10.14778/3583140.3583160](https://doi.org/10.14778/3583140.3583160) ，✅ 200）
  以计划排序取代代价比较；Bao（SIGMOD 2021，DOI: [10.1145/3448016.3452838](https://doi.org/10.1145/3448016.3452838) ，✅ 200）
  把"该给优化器什么提示"模型化——两者都是本章技能的机器化 ⚠️ 生产渗透率尚无权威统计。
- 🔧 **零成本复现（SQLite）**：同一谓词 `WHERE +a BETWEEN ...`（表达式包裹列）前后
  `EXPLAIN QUERY PLAN` 从 `SEARCH ... USING INDEX` 变 `SCAN`——
  本章"隐式转换弃索引"的最小标本（本机数字见 [03-索引调优.md](03-索引调优.md) 实验节）。
