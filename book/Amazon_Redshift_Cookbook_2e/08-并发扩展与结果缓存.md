## 3. 深潜一：三层并发火力（⚠️ 转述+✅ 锚）

1. **WLM 插槽**：同集群内的并行度上限（队列×slot）——加机器解决"同时快"；
2. **并发扩展**：识别短、幂等、只读型查询甩到自动伸缩的只读机群，账单按查询计——解决"人多排队"（✅ concurrency-scaling 同址 200；注意 TDG 05 已登记其 2025+ 文档线淡出，被 Serverless autoscale 叙事吸收 ⚠️）；
3. **结果缓存**：同一查询文本（含字面量）近期已跑→直接回放结果——解决"dashboard 每秒轮询"（⚠️）。
三层各自的失败模式：插槽满=排队；CS 不接非确定性函数（random/窗口无界）与大结果；缓存被 `SET ...to off` 或语句文本微差（大小写/空白/字面量）击穿（⚠️）。

## 4. 深潜二：读透仓内压测脚本（✅ 实抓重构）

`conc_scaling.sql` 的成对模式=两类代表负载：
- 单表日期过滤聚合：`SELECT SUM(l_quantity), SUM(l_extendedprice) FROM lineitem WHERE l_receiptdate='1992-01-29'`（剪枝友好，CS 理想客户 ⚠️）；
- JOIN+GROUP BY：`lineitem JOIN orders ... WHERE l_shipdate='1992-01-29' GROUP BY o_orderstatus`（重活代表）；
两型各循环数十遍+缓存关断——**"同文重复"正是测缓存关断有效性与 CS 响应一致性的最小脚本**（✅ 文件内容+⚠️ 意图推定）。日期字面量与 ch3 的 stg 表列名（orderkey/linenumber/quantity/extendedprice）互证同一数据族（✅）。

## 6. 常见坑与最佳实践（⚠️ 转述+✅ 锚）

1. 压测/评测忘记关结果缓存=把回放当性能（本章 ✅ 首行语句的全部意义）；
2. BI 工具拼 SQL 带毫秒时间戳注释→缓存永失，配 session 固定模板（⚠️）；
3. 自动 WLM 下手工调队列是"降级动作"——先信默认再拿监控证据改（⚠️；✅ 入口 mgmt/welcome 同址 200）；
4. 并发扩展按查询收费：高频小查询走 CS 可能比扩集群贵——账要算在容量规划里（⚠️）；
5. Serverless 上"并发"心智=autoscale 上限（base RPU×倍数）+ 队列挂起告警，与预置三层模型不再一一对应（⚠️；✅ serverless-whatis 同址 200）。

## 8. 深潜三：WLM 配置对照表（⚠️ 转述+✅ 入口锚）

| 配置模式 | 适用场景 | 优势 | 限制 |
|---|---|---|---|
| 自动 WLM（默认） | 混合负载、免运维 | 系统自动分类/分配 | 精细控制弱（⚠️） |
| 手工 WLM 队列 | 已知负载类型+SLA | 完全控制插槽/优先级 | 运维成本高（⚠️） |
| 混合（自动+短查询） | 大量短查询+少量长查询 | 短查询快速通道 | 阈值需调优（⚠️） |

WLM 关键参数速查（⚠️ 转述，✅ 入口 mgmt/welcome 同址 200）：
- `query_group`：查询分组标签，配合 `SET query_group TO 'report'` 路由到指定队列；
- `short_query_threshold`：低于此阈值的查询自动走快速通道（⚠️ 值以官方文档为准）；
- `auto_wlm_is_active`：系统内部标记（⚠️ 不直接设置）；
- 队列 `max_concurrency`：单队列最大并发查询数（⚠️）。

Serverless 下的 WLM 变化（⚠️ 转述，✅ serverless-whatis 同址 200）：
- 无"队列"概念→workgroup 级 `base RPU` + `max RPU` 替代；
- 优先级通过查询标签（query label）实现，而非手工队列；
- autoscale 响应时间：秒级（⚠️ 具体 SLA 以官方页为准）。

## 8b 配方演绎：结果缓存命中条件与失效场景（⚠️ 转述）

结果缓存命中**三条件**（缺一不可，⚠️ 转述）：
1. **查询文本完全一致**：包括大小写、空白、字面量——`WHERE id=1` 与 `WHERE id = 1` 视为不同（⚠️）；
2. **同一用户/角色**：权限隔离，A 用户的缓存 B 用户不可命中（⚠️）；
3. **同数据库+表未变更**：底层表有 INSERT/UPDATE/DELETE → 缓存自动失效（⚠️）。

缓存失效的常见反模式（⚠️ 工程惯例）：
- BI 工具在 SQL 中嵌入毫秒时间戳注释 → 每次文本不同 → 缓存永失；
- 字面量漂移：`WHERE date = '2024-01-01'` vs `'2024-01-02'` → 不同缓存条目；
- **对策**：BI 端参数化模板+固定会话配置（⚠️）。

缓存命中率监控（⚠️ 转述）：
```sql
-- 缓存命中统计（系统表族，⚠️ 列名转述）
SELECT query, result_cache_hit, elapsed
FROM stl_query WHERE starttime > sysdate - 1
ORDER BY starttime DESC LIMIT 20;
```

## 8c 配方演绎：并发压测方法论（✅ 脚本形态+⚠️ 方法）

基于仓内 `conc_scaling.sql` 的压测流程重构（✅ 文件形态实抓，⚠️ 方法论为重构）：

```
Step 1 ─ 关缓存：SET enable_result_cache_for_session TO off;（✅ 首行实抓）
Step 2 ─ 准备查询集：单表聚合 + JOIN 聚合成对（✅ 文件形态）
Step 3 ─ 基线测量：单会话串行执行，记录每条 elapsed
Step 4 ─ 加压：N 会话并发（psql/pgbouncer 多连接）
Step 5 ─ 监控指标：queue_time / elapsed / concurrency_scaling_instances
Step 6 ─ 判定：响应时间 P95 是否超出 SLA
```

压测结果解读（⚠️ 转述）：
- **queue_time 高 + elapsed 低** → WLM 插槽不够，加队列/加集群；
- **queue_time 低 + elapsed 高** → 单查询性能问题（→07 调优）；
- **concurrency_scaling_instances > 0** → 并发扩展已触发，检查费用（⚠️）。

## 8d 深潜四：容量规划简化模型（⚠️ 转述重构）

并发规划的"餐巾纸背面"公式（⚠️ 重构口径，数字以官方配额为准）：

```
所需 WLM 插槽 ≈ 并发用户数 × (1 + 查询平均时长_s / 目标延迟_s)
```

示例（⚠️ 纯推演非实测）：
- 20 并发用户 × 平均查询 5s / 目标延迟 5s = **20 插槽**（基线）；
- 若峰值 3× → 需 60 插槽 或 开启并发扩展承接溢出；
- Serverless：base RPU 按 20 并发选 → max RPU 按峰值 3× 设上限（⚠️）。

容量规划与成本交叉（⚠️ 转述）：
- 并发扩展按查询秒计费 → 高频小查询可能比扩集群贵（算账！）；
- 结果缓存命中 = 零计算成本 → **缓存是最高 ROI 的"扩容"**（⚠️）。

## 8e 🔧 类比补充：并发/缓存的"形状"直觉（本机真实跑过）

⚠️ 非本书引擎行为，方言已按 DuckDB 改写。DuckDB 1.5.5 无会话结果缓存子系统，类比以"预聚合回放"示形（同 D4）：

- 5e6 行基表现场聚合：**14ms**（≈"无缓存，每次重算"）；
- 2500 行汇总表直读：**0.76ms**（≈"缓存/预计算回放"）；
- 比值 ≈ **18×**——这是"有缓存 vs 无缓存"的收益上界直觉（D4 的 5× 为保守口径，18× 为理想口径，如实登记两数）。

多引擎并发模型对照（⚠️ 全表转述）：

| 引擎 | 并发机制 | 弹性方式 | 缓存层 |
|---|---|---|---|
| Redshift（预置） | WLM 队列+CS | 加节点/CS 外挂 | 结果缓存 |
| Redshift（Serverless） | autoscale RPU | 秒级扩缩 | 结果缓存 |
| Snowflake | 多仓库独立计算 | 仓库级弹性 | 结果缓存+MV |
| BigQuery | slots 共享池 | 按需/预留 | 缓存+物化 |

## 核心概念速览（中英对照）

- 并发扩展 — concurrency scaling：短查询外挂只读机群、按查询计费
