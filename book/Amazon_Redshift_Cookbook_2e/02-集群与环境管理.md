## 3. 深潜一：库-schema-角色三层规划（⚠️ 转述）

Redshift 的对象层级：集群→数据库→schema→表/视图（PG 血统）。cookbook 式建议（重构）：
1. 每业务域一 schema，`ALTER DEFAULT PRIVILEGES` 管住新对象默认授权（防"新表全库可读"事故）；
2. 角色三件套：`etl_load`（COPY/INSERT 权）、`analyst_ro`（SELECT 权）、`bi_svc`（限定 schema）——用户只进组/角色，不直接授权（与 [../PostgreSQL_16_Administration_Cookbook/00-总览与阅读地图.md](../PostgreSQL_16_Administration_Cookbook/00-总览与阅读地图.md) 安全章同款结论）；
3. 权限查询走系统表/目录：`pg_roles`/`pg_namespace` 族 + `HAS_SCHEMA_privilege()` 系函数（⚠️ 转述；✅ 目录对象可经 STV 锚 https://docs.aws.amazon.com/redshift/latest/dg/r_STV_TBL_PERM.html 同址 200 侧证"系统表看权限"姿势）。
- IAM 侧：Identity Center/外部 IdP → 角色 SSO 映射，DB 账号零口令化是 2024+ 官方主推（⚠️ 转述）。

## 5. 🔧 类比：会话参数可测性与"视图模拟权限包"（本机真实跑过）

1. **参数影响执行路径的可测性**：DuckDB 1.5.5 同一 5e6 行 csv `COPY`，`SET preserve_insertion_order=true` **696ms** vs `false` **670ms**（各取两次最优；差约 4%，属噪声级——**如实登记"本例无显著差"**）。结论只到抽象层："会话开关在任何引擎都能以计时实验观测"；Redshift 参数族（结果缓存、WLM 队列等）的真值仍只能 ⚠️ 转述+文档锚（**非 Redshift 行为，方言已按 DuckDB 改写**；脚本 ch2_demo.py，输出 ch2_demo_out.txt，存 tmp/dbwave_w5_rscb/）。
2. **权限包直觉**：Python 内置 SQLite 3.45.3 建 1e6 行 lineitem 后无 GRANT 可用，只能 `CREATE VIEW v_lineitem_e AS SELECT * FROM lineitem WHERE region='E'` 模拟"分析师只读 E 区"（视图定义即权限包雏形）——诚实暴露 SQLite 无权限子系统，反向说明 Redshift `GRANT ... TO ROLE` + 行级安全策略的必要性（⚠️ 类比局限声明，Redshift RLS 语义见本册 09 与 TDG 08）。

## 6. 常见坑与最佳实践（⚠️ 转述+✅ 锚）

1. **用户名大小写**：Redshift 标识符默认折叠小写、加引号变敏感——BI 工具拼引号会连坐权限（⚠️ PG 血统坑，同款见 [../Understanding_MySQL_Internals/00-总览与阅读地图.md](../Understanding_MySQL_Internals/00-总览与阅读地图.md) 对照的 MySQL 大小写话题）。
2. **DROP DATABASE 不能当前库**：需先 `\c` 离开（⚠️）。
3. 参数模板改动部分需重启集群/会话生效——Serverless 无重启概念，参数走 workgroup 配置（⚠️ 转述）。
4. 审计日志默认关：合规场景先开 db-auditing 到 CloudWatch/S3，再谈事后取证（✅ 锚同上 §2 表）。
5. 快照命名与保留策略对齐 RPO：跨区快照复制是 DR 第一件（✅ 锚 §2 表）。

## 5b 配方演绎：环境日常十步走（⚠️ 转述重构，每步带文档归属）

1. 建库：`CREATE DATABASE dw;`——之后所有 GRANT 都在此库内发生（✅ dg 语法族入口同 §2 表）；
2. 建域 schema：`CREATE SCHEMA sales;` + `ALTER DEFAULT PRIVILEGES IN SCHEMA sales GRANT SELECT ON TABLES TO ROLE analyst_ro;`（⚠️）；
3. 建角色：`CREATE ROLE etl_load; CREATE ROLE analyst_ro;`（⚠️）；
4. 人进角色：`GRANT analyst_ro TO "iam:role/analyst-svc";`——IAM 主体直接映射（⚠️；✅ IAM 锚同 §2 表）；
5. 服务账号零口令：应用侧只持 IAM 身份，DB 侧无静态密码可泄（⚠️ 最佳实践）；
6. 参数模板：新建 parameter group→关联集群/Serverless 配置→会话类参数灰度验证（⚠️）；
7. 审计开启：db-auditing 选用户/连接/语句三类日志→S3/CloudWatch（✅ 锚同 §2 表）；
8. 快照策略：保留天数+维护窗口+跨区复制三查（✅ 锚同 §2 表）；
9. 命名规约：`<env>-<domain>-<role>` 三位一体贯穿用户/角色/schema——一年后救你的是 grep（⚠️ 工程惯例）；
10. 季度体检：孤儿对象/零授权角色/长期空转集群三扫，配合 11 章标签认领责任人（⚠️）。

## 核心概念速览（中英对照）

- 数据库对象层级 — database/schema 层级：集群-库-schema-表四级，PG 血统
- 默认权限 — ALTER DEFAULT PRIVILEGES：对未来新对象生效的授权规则
- 角色 — role：权限包，用户经组/角色间接获权
- IAM 认证 — IAM authentication：AWS 身份直接映射 DB 用户，免口令
- 参数模板 — parameter group：集群级配置集合
- 会话设置 — session SET：查询级开关（结果缓存/时区等）
- 数据库审计 — database auditing：登录/语句级审计日志入 S3/CloudWatch
- 自动快照 — automated snapshots：默认保留窗口内的全量快照
- 跨区快照复制 — cross-region snapshot copy：区域级 DR 手段
- CFN 实验栈 — per-chapter CloudFormation stack：本书"一章一栈"实验法
- 系统目录 — system catalog（pg_*）：库内对象/权限元数据视图
- 最小权限 — least privilege：按域授 schema、按岗设角色

## 最新演进与工业实践

- **RBAC 强化（2023→）**：Redshift 引入数据库角色与 IAM 角色直连授权后，"DB 用户退化为服务主体"成为官方叙事（⚠️ 转述；✅ IAM 族同址 200 锚见 §2）。
- **Serverless 参数面**：workgroup 级配置 + `ALTER DEFAULT PRIVILEGES` 在 Serverless 同样可用，namespace 与 workgroup 分权管理（⚠️ 转述）。
- **工业实践**：多环境（dev/stage/prod）以栈参数化复制而非手工点控制台——与仓内 12 份 CFN 的示范意图一致（✅ 实抓）；Terraform 社区 provider aws_redshift/aws_redshiftserverless 为事实标准（⚠️ 转述）。
