## 1. 本章定位（推定）

JSON/日志/事件流这类**没进星型的另一半世界**：仓内 SUPER 列 + 展开函数，仓外 Spectrum 外表 + 联邦查询 + 目录联动。四条路一句话各有：SUPER=把 JSON 当列存进来；Spectrum=湖上直查不搬；联邦=RDS 小表实时穿；Catalog Connect=Iceberg 目录入仓。

## 3. 深潜一：SUPER 的"半列存"账（⚠️ 转述+🔧 类比）

Redshift SUPER：类型自动推断、子列剪枝（projection pruning）可只读路径片段；但谓词若落在深层动态路径，剪枝失效退化为整块解压——所以生产铁律是"**入仓 24h 内预展平热路径**"。仓外对照：Spectrum 上 Parquet+谓词下推=免管理的列存外表，但元数据/schema 漂移防线要 Glue Catalog 承担（⚠️；✅ c-spectrum-considerations 同址 200）。

## 4. 深潜二：四路选装决策树（本章重构，⚠️）

```
数据在 S3 且体量大、查询频度低 ──→ Spectrum 外表（不搬）
数据在 S3 且高频分析 ──────────→ COPY 入内表（→03；SUPER 仅渡船）
数据在 RDS 小表、要实时一致 ────→ 联邦查询（延迟敏感场景禁大表穿）
湖治理已选 Iceberg ────────────→ Catalog Connect/托管表（→12 演进）
```
（决策树为重构知识，节点均有 ✅ 文档锚支撑，箭头语义 ⚠️。）

## 5. 🔧 实测：同一份 NDJSON 的三种吃法（本机真实跑过）

脚本 demo.py（D6），DuckDB 1.5.5——**非 Redshift 行为，方言已按 DuckDB 改写**（Redshift 对应读法为 SUPER 路径函数/Spectrum JSON 外表，语义 ⚠️ 转述）：80 万行 `{id, attrs:{qty, region}}` NDJSON，谓词 `region='r3'`（命中恒 10 万行）：
- 当纯文本扫+逐行抽取（≈Redshift 深层动态路径最坏相）：**108ms**；
- 类型化直读 JSON（≈SUPER 首读+Spectrum JSON 外表）：**188ms**（本例反比文本抽慢——类型推断的一次性成本，**如实登记反直觉读数**）；
- 一次性转 Parquet 后反复查（≈预展平/列存化）：**8ms**，文件 356.3MB csv 世界的同信息量在 parquet 里仅 3.3MB。
结论迁移：**"每次现解析"与"解析一次存列存"差 13–24×**——这条账在任何向存引擎同构，Redshift 真实现（SUPER 子列统计、Spectrum 分区裁剪）以 ✅ 文档锚为凭（⚠️ 不冒充实测）。

## 6. 常见坑与最佳实践（⚠️ 转述+✅ 锚）

1. JSON 'auto' 的类型推断随批次数据漂移（同列 int/varchar 轮替）→ 定 schema 或装后立即 CAST 定型（⚠️）；
2. SUPER 列上建不了常规索引/排序键受益有限——热查询路径展平成表才是正解（⚠️）；
3. Spectrum 外部表分区路径与 COPY 清单共用一套目录规约（→ 04 §6-1 小对象惩罚同治）；
4. 联邦查询谓词不下推的部分在 RS 侧执行——大表穿=把 RDS 打挂（⚠️ 双端都疼）；
5. 外表权限=IAM role + Glue/LF 双层（与 Ch10 Lake Formation 汇流）（⚠️→10）。

## 8. 深潜三：JSON 路径函数对照表（⚠️ 转述+✅ 入口锚）

Redshift SUPER 类型的常用展开函数（⚠️ 语法转述，✅ dg 根同址 200 为入口）：

| 函数 | 用途 | 示例 |
|---|---|---|
| `json_extract_path_text(col, 'key')` | 取 JSON 对象某键的文本值 | `json_extract_path_text(attrs, 'region')` |
| `JSON_EXTRACT_ARRAY_ELEMENT_TEXT(col, n)` | 取数组第 n 个元素的文本 | `..._text(tags, 0)` → 第一个标签 |
| `FLATTEN(col)` | 把嵌套数组展开为行集 | `FROM t, FLATTEN(t.items) AS f` |
| 点号路径 `col.key` | SUPER 列的简写访问 | `attrs.region::varchar` |
| `IS_VALID_JSON()` | 校验 JSON 合法性 | 装载前过滤脏数据（⚠️） |

路径性能陷阱（⚠️ 转述）：
- **浅层静态路径**（如 `attrs.region`）→ 子列剪枝生效，只读该列块（✅ 概念与 D6 的 8ms 证据一致）；
- **深层动态路径**（如 `attrs.items[*].price`，数组长度不定）→ 剪枝退化，整块解压→性能悬崖；
- **铁律**：查询频度 >10 次/天的路径，入仓 24h 内预展平为定型列（→ §8b 配方）。

## 8b 配方演绎：Spectrum 外表建表五步（⚠️ 转述+✅ 锚）

```
Step 1 ─ IAM Role：建 IAM 角色，附加 S3 只读策略 + Glue Catalog 只读策略（⚠️）
Step 2 ─ 外部 Schema：CREATE EXTERNAL SCHEMA spectrum_lab FROM GLUE
          DATABASE 'my_glue_db' IAM_ROLE 'arn:aws:iam::...'
          REGION 'us-east-1'（⚠️；✅ c-spectrum-considerations 同址 200）
Step 3 ─ 外部表 DDL：CREATE EXTERNAL TABLE spectrum_lab.events(...)
          STORED AS PARQUET LOCATION 's3://bucket/prefix/'（⚠️）
Step 4 ─ 分区注册：ALTER TABLE ... ADD PARTITION(yr=2024)
          LOCATION 's3://.../yr=2024/'（⚠️ 与 COPY 清单共用目录规约）
Step 5 ─ 查询验证：SELECT count(*) FROM spectrum_lab.events
          WHERE yr=2024——确认谓词下推生效（⚠️）
```

Spectrum 成本模型（⚠️ 转述）：按扫描数据量计费（MB 级），**谓词下推+分区裁剪**是控费命门——无裁剪的全表扫=账单灾难。

## 8c 配方演绎：预展平的工程配方（⚠️ 转述+🔧 类比）

**24h 预展平规则**的落地步骤（⚠️ 工程口径重构）：
1. **探索期**（入仓 Day 0）：COPY JSON 'auto' 入 SUPER 列 → `FLATTEN` + `json_extract_path_text` 探索结构；
2. **定型期**（Day 0–1）：识别高频查询路径 → 建目标表 `CREATE TABLE typed_events AS SELECT id, json_extract_path_text(attrs,'region')::varchar AS region, ...`；
3. **增量期**（Day 1+）：新数据 COPY 入 SUPER → `INSERT INTO typed SELECT ...` 增量展平 → 或直接在 COPY 管道中 Lambda 预展平（→ 04/05 编排）；
4. **退役期**：SUPER 列保留 30 天供冷查询回溯 → 过期清理。

热路径 vs 冷路径分治（⚠️ 工程惯例）：
- **热路径**（日均查询 >10 次）：必须展平为列+排序键受益；
- **冷路径**（偶发排查）：保留 SUPER 按需查询，不占排序键预算。

## 8d 深潜四：湖格式直读对比表（⚠️ 转述+✅ 锚）

| 格式 | Redshift 接入方式 | 优势 | 限制 |
|---|---|---|---|
| Parquet | COPY/Spectrum 外表 | 列存压缩、谓词下推成熟 | 无事务/无增量更新 |
| ORC | Spectrum 外表 | 压缩比略优于 Parquet | 生态弱于 Parquet（⚠️） |
| Iceberg | Catalog Connect / 托管表 | 事务+增量+时间旅行 | 2024 仍在 GA 早期（⚠️） |
| Hudi | 经 Spark 写入→S3→Spectrum 读 | 更新友好 | Redshift 原生支持有限（⚠️） |

2024–2026 趋势：Parquet 为"万能底线"，Iceberg 为"治理升级路线"——本册 ch10/ch12 同条线（✅ 主站 200 实测；专页 302 登记）。

## 8e 🔧 类比补充：半结构化数据的"成本账"量化（本机真实跑过）

⚠️ 非本书引擎行为，方言已按 DuckDB 改写。基于 D6 数据（80 万行 NDJSON），补充成本视角：

| 方案 | 查询延迟 | 存储占用 | 扫描放大系数 |
|---|---|---|---|
| 纯文本现解析 | 108ms | 356.3MB（csv） | ≈5×（每次全解压解析） |
| SUPER 类型化直读 | 188ms | 同左 | ≈3×（类型推断开销） |
| 预展平→Parquet | **8ms** | **3.3MB** | **≈1.1×**（列存裁剪） |

扫描放大系数 = 实际扫描字节 / 有效信息字节。预展平后存储增 30%（Parquet 元数据开销），但查询扫描降 70%+——**对日均查询 >50 次的热表，预展平 ROI 为正**。

schema 漂移应对策略（⚠️ 工程惯例）：
1. **宽容入仓**：SUPER 列接受一切 JSON 结构（JSON 'auto' 兜底）；
2. **严格落表**：预展平时 CAST 定型+DEFAULT 值兜底（防 NULL 泛滥）；
3. **监控告警**：对 SUPER 列的 `json_typeof()` 分布建监控，类型占比突变即告警。

## 核心概念速览（中英对照）

- SUPER 类型 — SUPER：Redshift 原生半结构化列类型（JSON 族）
- 子列剪枝 — sub-column/projection pruning：只读 JSON 路径涉及片段
- FLATTEN — FLATTEN/JSON 函数族：把数组展开成行
- JSON 'auto' — COPY JSON auto：类型自动推断装载
- Spectrum — Redshift Spectrum：S3 直查的外表引擎
- 外部模式 — external schema（Glue/IAM）：湖/库目录挂接入仓
- 联邦查询 — federated query：实时穿查 RDS PostgreSQL/MySQL
- Catalog Connect — catalog integration：Iceberg 目录入仓托管
- 预展平 — pre-flatten：SUPER→定型列的 24h 内落表工程法
- schema 漂移 — schema drift：同列类型随批次抖动
- 谓词下推 — predicate pushdown：过滤进扫描端执行
- 渡船模式 — staging-as-ferry：SUPER 只当暂存不当终态
