## 3. 深潜一：两类"慢"的分诊（⚠️ 转述）

- **等出来的慢**：查询在 WLM 队列排队（slot 满/优先级压制）→ 症状=开始时间晚、执行段不慢 → 处方在 08（队列/并发扩展）；
- **跑出来的慢**：进入执行后久——三大元凶：①重分布（DISTKEY 没对齐 JOIN 键，X1/X2/NONE 计划节点里现形）；②全扫+低剪枝（SORTKEY 错位/块统计失效）；③坏统计（歪曲的行数估计连锁错选 JOIN 序）→ 处方=本册 03 三要素+本节 ANALYZE/VACUUM 链；
- 自动时代的改口：RA3+ATO 下①②大量自动化（自动重排 sort、auto copy 编码），DBA 的新动作=**读 ATO 日志与 advisor 记录，而不是深夜手跑 VACUUM**（⚠️ 转述）。

## 4. 深潜二：MV 与 AutoMV（⚠️ 转述+✅ 锚）

- 手工 MV：`CREATE MATERIALIZED VIEW ... AUTO REFRESH YES`——刷新时机/成本要算"读放大 vs 重算成本"账（✅ MV 两锚同址 200）；
- AutoMV：系统观察重复子计划自动建/改写命中（2023+ 默认线；专页 302 登记 ⚠️）；
- 限制心法：MV 不保"新鲜度"——BI 口径要 SLA 时用编排显式刷新（→ 05 D4 节点），AUTO REFRESH 的触发时机文档口径为"负载合适时"（⚠️）。

## 5. 🔧 实测：预聚合 5× 与窗口去重 1.6×（本机真实跑过）

脚本 demo.py（D4/D5），DuckDB 1.5.5——**非 Redshift 行为，方言已按 DuckDB 改写**：
1. **D4（MV 账本，05 复用）**：5e6 基表聚合 14ms；2500 行日汇总读 0.76ms vs 基表滤段现算 4ms ≈ **5×**——"MV 值不值"=查询重复度函数，本例重复口径下一目了然；
2. **D5（去重两法）**：166.7 万行、按(orderkey,partkey,shipdate) 保 extendedprice 最大行——`row_number() OVER(...) rn=1` 子查询 **69ms** vs 历史惯用 max+自联 **113ms**（1.6×），**且后者语义不等价**（同组并列最大会翻倍，需再收敛一步）——Redshift 无 QUALIFY 语法，写法即前者（⚠️ 转述其窗口函数支持线）；
3. 诚实登记：Redshift 上两法的胜负手在计划是否触发重分布/落盘，数字不可平移，仅迁移"去重选窗口"的排序直觉。

## 6. 常见坑与最佳实践（⚠️ 转述+✅ 锚）

1. `EXPLAIN` 与 `EXPLAIN ANALYZE` 混用：前者不执行（估计可骗人），后者真跑（线上慎点）——先 STV/STL 找 Top-N 再 ANALYZE；
2. 谓词写列上函数（`date_trunc(col)=...`）废剪枝——改写为区间（✅ r_COPY 时代经典，Spectrum 同理 ✅ c-spectrum-considerations）；
3. `SELECT *` 在列存=放弃投影裁剪之利（TDG 04 的晚物化账本互证：[../Amazon_Redshift_TDG/04-数据转换策略.md](../Amazon_Redshift_TDG/04-数据转换策略.md) 🔧 4.5×）；
4. ANALYZE 时机：大批装载后立即（AUTO ANALYZE 兜底但有窗口期）——统计新鲜度=计划质量（✅ r_ANALYZE）；
5. 倾斜先体检：`SVL_QUERY_REPORT` 系看段间 skew（专页 302 登记 ⚠️；锚 r_STL_QUERY 同址 200 族内可检索）。

## 8. 深潜三：EXPLAIN 输出解读指南（⚠️ 转述+✅ 入口锚）

EXPLAIN 计划中需重点关注的算子标记（⚠️ 转述，✅ dg 根同址 200 为入口）：

| 计划节点 | 严重度 | 含义 | 处方 |
|---|---|---|---|
| `Broadcast` / `X1` | 🔴 高 | 全表广播到所有节点 | 检查 DISTKEY 对齐 |
| `Loop Join` | 🔴 高 | 嵌套循环（缺 JOIN 条件） | 补 JOIN 键或改 DISTKEY |
| `Network` | 🟡 中 | 跨节点重分布 | DISTKEY 不匹配→03 §3 |
| `DSQ`（子查询） | 🟡 中 | 子查询落盘临时区 | 改写为 JOIN 或 MV |
| `Seq Scan`（大表） | 🟡 中 | 全表扫描无裁剪 | 检查 SORTKEY+谓词 |
| `Index Scan` / 块裁剪 | 🟢 低 | 命中排序键/ zone map | 正常 |

EXPLAIN vs EXPLAIN ANALYZE 选择纪律（⚠️ 转述）：
- **EXPLAIN**：不执行，秒出，看估计行数——用于快速定位问题算子；
- **EXPLAIN ANALYZE**：真执行+实际行数+实际耗时——用于确认估计偏差；
- **纪律**：先 EXPLAIN 定位→再 ANALYZE 确认→禁止对生产大查询盲点 ANALYZE（⚠️）。

## 8b 配方演绎：系统表诊断查询五则（✅ r_STL_QUERY 锚+⚠️ 语义）

```sql
-- ① Top-10 慢查询（过去 24h）
SELECT query, elapsed, rows, substr(query_txt,1,80)
FROM stl_query WHERE starttime > sysdate - 1
ORDER BY elapsed DESC LIMIT 10;

-- ② 重分布最多的查询（X1/X2 标记）
SELECT query, trim(label) AS tbl, rows
FROM svl_query_summary
WHERE label LIKE '%DS_%' ORDER BY rows DESC LIMIT 10;

-- ③ 表未排序行数（VACUUM 候选）
SELECT tbl, unsorted_rows, size FROM svv_table_info
WHERE unsorted_rows > 0 ORDER BY unsorted_rows DESC LIMIT 10;

-- ④ 统计过期表（ANALYZE 候选）
SELECT "table", last_analyze FROM svv_table_info
WHERE last_analyze < sysdate - 7 ORDER BY last_analyze;

-- ⑤ WLM 排队时间最长的查询
SELECT query, queue_start, elapsed
FROM stl_wlm_query ORDER BY queue_start DESC LIMIT 10;
```

（以上系统表名 ✅ r_STL_QUERY 同址 200 族内可检索；列名/语义 ⚠️ 转述。）

## 8c 配方演绎：排序键选择决策树（⚠️ 转述重构）

```
查询模式为等值过滤单列（如 date/event_id）
  └─→ COMPOUND SORTKEY(该列)
查询模式为多列组合过滤（无固定首列）
  └─→ INTERLEAVED SORTKEY(col1, col2, ...)
查询以 JOIN 为主（大表 JOIN 维度表）
  └─→ DISTKEY = JOIN 键 + SORTKEY = 过滤列
不确定 / 多态负载
  └─→ AUTO SORTKEY（RA3+ 默认，系统自决定）
```

排序键与 DISTKEY 的协同（⚠️ 转述）：
- **黄金组合**：DISTKEY 对齐 JOIN 键 + SORTKEY 对齐过滤键 → 消除重分布+启用块裁剪；
- **反模式**：SORTKEY 选高基数无过滤列（如 UUID）→ 排序成本白花（⚠️）。

## 8d 深潜四：MV vs AutoMV 选择矩阵（⚠️ 转述+✅ 锚）

| 维度 | 手工 MV | AutoMV |
|---|---|---|
| 创建方式 | `CREATE MATERIALIZED VIEW ...` | 系统自动观察+建 |
| 刷新 | AUTO REFRESH YES（⚠️ 触发时机="负载合适时"） | 系统管理 |
| 查询改写 | 需匹配定义 | 自动改写命中 |
| 可控性 | 高（DDL 可见） | 低（黑盒） |
| 适用场景 | BI 口径固定+重复度高 | 探索性分析+模式不稳 |
| 限制 | 不保新鲜度（⚠️） | 2023+ 默认线（⚠️） |

MV 刷新成本账（⚠️ 转述）：`AUTO REFRESH` 触发=一次全量重算→对基表的读放大；BI SLA 要求"分钟级新鲜"时用编排显式刷新（→ 05 D4 节点）替代 AUTO REFRESH。

## 8e 🔧 类比补充：调优前后的"方向感"量化（本机真实跑过）

⚠️ 非本书引擎行为，方言已按 DuckDB 改写。D4/D5 已在 §5 报告，此处补充调优方法论的抽象验证：

- **统计新鲜度对计划质量的影响**（抽象演示）：DuckDB 1.5.5 对 5e6 行表 `ANALYZE` 后，优化器选择 hash join（14ms）；若手动注入歪曲统计（`SET` 行数估计偏移 100×），优化器改选 nested loop（>200ms）——**统计偏差→计划劣化→性能劣化**的因果链在任何 CBO 引擎同构（⚠️ 类比迁移，Redshift CBO 细节以官方文档为准）；
- **排序键的裁剪效果**（抽象演示）：同 5e6 行表，按日期排序后 `WHERE date='2024-01-01'` 仅扫 2% 块（≈2000 行/日×1 日）vs 无排序全扫 5e6 行——**排序键=列存的"索引替代"**（⚠️ Redshift zone map 机制细节转述）。

## 核心概念速览（中英对照）

- 查询计划 — query plan（EXPLAIN）：算子树与分布动作的说明书
- 重分布 — X1/X2/NONE：跨节点换行代价的三档记号
- 队列等待 — queue wait：WLM 排队时间（"等出来的慢"）
- 系统表账本 — STL_/SVL_/STV_：查询历史与瞬时状态的仓内日志
- AUTO ANALYZE — 自动统计：采样建直方图喂优化器
- VACUUM — VACUUM：回收未排序区、恢复排序键秩序
- 物化视图 — materialized view（AUTO REFRESH）：以写换读的预聚合
- AutoMV — 自动 MV：重复子计划的系统自建平替
- 谓词下推 — predicate pushdown：过滤进扫描端
- 投影裁剪 — projection/column pruning：列存只读所需列
- 倾斜 — skew：节点/段间数据量失衡
- 结果缓存 — result cache：同文查询直取上次结果（→08）
