# 第 17–18 章：使用 SSD 解决 I/O 瓶颈 · 为最佳性能设计和监控索引

> ⚠️ 文档转述（章题取自中译本逐字目录 ✅，章内小节自拟 ⚠️；Oracle 行为为 11gR2–12cR1 口径转述，无 Oracle 实测）。类比实验见 [05 号文件 🔧G3](05-AWR分析优化.md)（统计驱动计划翻转，非 Oracle）。

## 本文件定位

第 17 章是"硬件侧扩容"（用 SSD 的随机 IOPS 与低延迟买回响应时间），第 18 章是"逻辑侧扩容"（用索引把随机 I/O 变成更少更准的访问）。排错顺序上两章互为镜像：**先用索引减少该发生的 I/O，再用 SSD 加速非发生不可的 I/O**——反过来做就是"用闪存掩盖设计债"。

## 第 17 章 使用SSD解决I/O瓶颈

### 17.1 症状定位（⚠️ 转述）

- AWR 前台等待集中在 `db file sequential read`（单块，随机读画像）且平均等待 >10ms 量级（15K 盘常规 5–8ms 的恶化形态）——这是 SSD 收益最直接的画像；集中在 `db file scattered read` 的大批量扫，加 SSD 前先想并行度与 smart scan。
- OS 面 `%ioawait`（iostat）与库内平均读时长的对账：差距大说明控制器/多路径排队，不全是"盘慢"。

### 17.2 投放策略（⚠️ 转述，按性价比排）

1. **REDON 日志**：小写高频繁，SSD 对 `log file sync` 立竿见影；老社区经验——redo 放 SSD 的"每美元收益"常高于数据文件。
2. **TEMP**：与第 15 章衔接，排序溢出落 SSD，`direct path read temp` 等待直接减半量级。
3. **热点对象**：SSD 磁盘组放 Top 段清单（第 10 章段级排行产出），配合 12c 智能存储分层（IORM/存储生命周期管理）做冷回迁。
4. **整库搬迁**：换 ASM 磁盘组即在线迁移（`ALTER DATABASE MOVE DATAFILE`/ASM rebalance），停机面小。

### 17.3 陷阱（⚠️ 社区转述）

- **写放大与寿命**：随机大块+高压缩比负载对早期企业 SSD 的 GC 干扰；GC 风暴表现为延迟尖刺（AWR 时间切片可见，第 10 章 ASH 法复用）。
- **缓存假象**：换 SSD 后"没变快"——瓶颈在 CPU 硬解析或 latch（第 16 章）而非 I/O；SSD 只兑现"等待事件真是 IO 类"的那部分收益。
- **Exadata 语境差异**：智能闪存缓存（Flash Cache）与本段通用 SSD 思路不同层，混谈会误导——原书此章为通用存储口径 ⚠️。

## 第 18 章 为最佳性能设计和监控索引

### 18.1 设计口径（⚠️ 转述）

- 列序法则：等值谓词列在前、范围列在后、排序列可尾随（消除 SORT 的隐性收益常被忽略）；覆盖索引（INCLUDE 式思路在 Oracle 即"把列补进键"）把回表清零。
- 与第 5/7 章联动：分区表上 LOCAL vs GLOBAL 的选择首先是运维语义（可单独 DROP/TRUNCATE 分区）而非查询语义；全局索引的分区维护后 ORA-01640 类 UNUSABLE 风险须有 rebuild 预案。
- 空间索引/函数索引/位图连接索引各归专用场景，OLTP 侧滥用是并发事故源（位图回看第 7 章禁令）。

### 18.2 监控与回收（⚠️ 转述）

1. **用没用**：`DBA_INDEX_USAGE`/监控视图找"零使用索引"——写入税与段空间都白付；先 INVISIBLE 观察（11g），确无人用再 DROP。
2. **胖不胖**：`INDEX_STATS`（ANALYZE INDEX ... VALIDATE STRUCTURE）看高度/叶块删除占比，决定 COALESCE（在线、释放尾部）还是 REBUILD（重建，占空间换紧凑）。
3. **漂不漂**：索引聚簇因子（clustering factor）随数据年龄恶化——CBOF 聚簇因子章的机理在此复用：同样的索引，数据重排后成本模型翻脸（衔接 🔧G3 的"依据变、计划变"母题）。
4. **统计联动**：索引段统计与表统计的同步刷新；直方图与索引列选择度的错配是第 4 章 ACS 问题的一半根因。

### 18.3 删索引的排错学

"加了索引还是慢"的两种答案：其一，计划没走它（统计/选择度骗了成本模型——第 4/12 章线）；其二，**它在写路径制造了 latch/块争用**（第 16 章线与第 3 章线）——索引是双向合同，读写各付一半。

## 17.4 案例演练：全闪上线的前后验收（⚠️ 按章主题结构化）

1. 基线：换盘前留两个完整周次的 AWR——Top Timed Events 按等待类切片 + 单块读/`log file sync` 平均与 P99。
2. 投放顺序：REDO/TEMP 先行（收益最快），Top 段其次，整库最后；每步单独立验收项（17.2 的排序原则）。
3. 验收三对比：单块平均等待、`log file sync` P99、DB Time 总量——三个都降才算还债，只看吞吐会漏掉尾延迟恶化。
4. 反向信号：等待时长降但 CPU 升=IO 债清、解析/闩债露出，转第 16 章；闪层不背这个锅。
5. 冷回迁：IORM/存储生命周期策略当周配置，否则半年后闪存层沦为"热冷同穴的大号垃圾桶"（17.3 的寿命议题）。

## 18.4 索引审计排班模板（⚠️ 按 18.2 拼装）

| 频率 | 科目 | 入口 |

## 18.5 常见误区（⚠️ 社区口径）

- "skip scan 救列序设计"——跳过扫描的前提是前导列低基数，不是把坏列序洗白的借口。
- "上了闪就可以随便加索引"——写路径的闩/块争用税不随介质变便宜（18.3 双向合同；第 3/16 章）。
- " invisible 是测试保险箱"——INVISIBLE 期间统计与维护照常计费，观察窗要有明确终点。

## 核心概念速览（中英对照）

- **单块读等待** — db file sequential read：索引式随机读的基本计时 ⚠️
- **闪存缓存** — Flash Cache：SSD 作缓冲层的加速形态（Exadata 另有专义） ⚠️
- **存储分层** — IORM/Storage ILM：热留闪存冷回落的策略面 ⚠️
- **写放大** — Write Amplification：SSD 内部 GC 代价，延迟尖刺源 ⚠️
- **ioawait** — IO Await：OS 面每 I/O 等待时间，库内外对账锚 ⚠️
- **复合索引列序** — Composite Index Order：等值在前范围在后的排序法则 ⚠️
- **覆盖索引** — Covering Index：键含全部引用列，免回表 ⚠️
- **本地索引** — Local Index：分区对齐、可随分区 DROP ⚠️
- **全局索引** — Global Index：跨分区强约束，维护有 UNUSABLE 风险 ⚠️
- **不可见索引** — Invisible Index：对优化器隐身、供下线观察 ⚠️
- **索引合并** — COALESCE：在线回收叶块空隙 ⚠️
- **聚簇因子** — Clustering Factor：索引→表块跳转成本，随数据年龄漂移 ⚠️

## 最新演进与工业实践

- **NVMe/ASM Filter 时代**：19c 的 ASM Filter Driver 与 NVMe 原生多队列把 17.2 的"投放学"简化为"全闪+分层策略"；Exadata Smart Scan/存储索引进一步把"少读块"的活儿下沉到存储层 ⚠️ 转述（docs.oracle.com 存储类文档 ✅ 域名可达）。
- **自动索引补位第 18 章**：Autonomous DB 的 Automatic Indexing 自动做"试建-验证-保留/废弃"闭环，18.2 的人工监控被代理；但"删索引的排错学"（18.3 的双向合同）仍是人工决策 ⚠️。
- **索引监视视图演进**：`DBA_INDEX_USAGE`/`MONITORING` 语义在 12c→23ai 间持续调整，社区脚本（EPI/Bulk 类索引审计工具）仍是主流落地方式 ⚠️。
- **跨引擎镜像**：SQLite 🔧G3 与 PG 的 `pg_stat_user_indexes.idx_scan`+`REINDEX CONCURRENTLY`、MySQL 的 `sys.schema_unused_indexes`——"零使用索引审计+在线回收"已是各引擎标配，本章方法论完全可移植。
