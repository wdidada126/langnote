# 第 15–16 章：临时文件 I/O 问题的诊断和恢复 · 处理闩锁和互斥锁争用

> ⚠️ 文档转述（章题取自中译本逐字目录 ✅，章内小节自拟 ⚠️；Oracle 行为为 11gR2–12cR1 口径转述，无 Oracle 实测）。类比实验见 [02 号文件 🔧G1](02-GC缓冲区忙等待、自适应游标共享与SPM.md)（锁争用二象限，非 Oracle）。

## 本文件定位

第 15 章管"排序/哈希溢出的缓冲区外空间"（TEMP 的 I/O 与容量），第 16 章管"内存结构的串行点"（latch/mutex）。两章合起来是**并发-内存故障面**：一个把压力泄给磁盘临时段，一个把并发堵在内存闸门。

## 第 15 章 临时文件I/O问题的诊断和恢复

### 15.1 症状面（⚠️ 转述）

- `ORA-01652`（无法在表空间扩展 temp 段）是终形态；前驱信号是 `direct path read/write temp` 等待暴涨、`v$tempseg_usage`（11g 前为 v$sort_usage）逼近限额。
- 排序/哈希连接溢出：workarea 请求超 `PGA_AGGREGATE_TARGET` 配额，单查询把临时段吃到几十 GB——AWR 里 `SQL ordered by user I/O` 榜点名（回看第 10 章）。
- 临时文件级故障：TEMPF 所在盘故障或 ASM 磁盘组余量不足（回看第 11 章"集群病常是存储病"）。

### 15.2 处置与恢复（⚠️ 转述）

1. **容量线**：`ALTER TABLESPACE TEMP ADD TEMPFILE ... AUTOEXTEND ON MAXSIZE ...`；同盘堆多个 temp 文件无益并发（单盘带宽是闸口），跨盘条带或 ASM normal redundancy 才是扩容正解。
2. **治理线**：会话级 temp 用量审计（`v$temp_sess_stats`/12c `v$temp_usage`）揪出失控 SQL；全局临时表改语义/物化中间结果以避开"每会话各排一遍"。
3. **参数线**：`workarea_size_policy=AUTO` 下按 SQL 调 `PGA` 或加并行度分摊；手工 `SORT_AREA_SIZE` 老路已弃用 ⚠️。
4. **12c 新维度**：临时 UNDO（`temp_undo_enabled=TRUE`）把并行/全局事务的 UNDO 挪进 TEMP——排查面合并，UNDO 压力转成 temp 压力，两章问题自此互联。
5. **恢复语义**：临时文件不需要"备份恢复"——实例重启重建即可；真正的恢复动作是**磁盘组/存储修复+配额重算**，与第 8 章的持久文件观对照。

## 第 16 章 处理闩锁和互斥锁争用

### 16.1 概念闸（⚠️ 转述）

- latch=受"持锁时间极短+竞争重试"约束的内存闩；mutex=10g 起替代共享池/库缓存部分闩的细粒度结构，带句柄防"改读竞争"。
- 经典四类：cache buffers chains（热点块）、shared pool（空间管理/碎片）、library cache（游标管理/失效风暴）、row cache objects（数据字典行）。

### 16.2 诊断路径（⚠️ 转述）

- `v$latch` 的 miss/sleep/immediate 比率，`v$latch_children` 定位子闩热点；10054 事件族/`alter session set events 'immediate trace name hands'` 是"持锁者是谁"的老取证法。
- ASH 视角（第 10 章）：latch 等待会话的 `BLOCKING_SESSION` 与其正在跑的 SQL——闩锁案 80% 是"某条 SQL 的行为异常"而非闩本身。

### 16.3 处置对照表（⚠️ 转述）

| 争用对象 | 根因画像 | 处置 |
|---|---|---|
| cache buffers chains | 单块被并发改（序列/热行/索引最右叶） | 第 3 章热点打散法；`_num_hash_latches` 老版调参不推荐 |
| library cache | 字面量 SQL 洪水、硬解析风暴、游标失效 | 绑定变量化；`session_cached_cursor`；共享池调大是止痛不是治病 |
| shared pool | 空间碎片、大量对象加载 | `ALTER SYSTEM FLUSH SHARED_POOL` 仅诊断窗使用；检查 cursor:shared mutex 行为 |
| row cache objects | 高频字典访问（递归 SQL 过量） | 降低硬解析、数据字典缓存语义核对、检查登录风暴/触发器 |
| mutex 争用 | 单游标高频执行（"cursor pin"类） | 减少子游标版本（回看第 4 章绑态）、避免失效广播 |

### 16.4 与第 3 章的分界

gc 等待=跨实例取块的排队；latch=本实例内存结构的串行点。**先看等待类（Concurrency vs Cluster，第 9 章路由），再进本/第 3 章各自的处置树**，防止"把集群问题当内存问题调参"。

## 15.3 治理细则与视图口径（⚠️ 转述）

- TEMP 的"恢复"语义：文件级灾难=存储修复+实例自动重建，演练科目是**配额重算与磁盘组余量**，不是找回旧 temp 文件（与第 8 章持久文件观对照）。
- 视图换代：11g `v$tempseg_usage` → 12c `v$temp_usage`/`v$temp_open_segment`，巡检脚本跨版本兼容最常踩的坑（社区口径）。
- GTT 与 ON COMMIT PRESERVE：会话池复用下"临时段常驻"，爆 temp 的形态从"单条大 SQL"变成"慢泄漏"——AWR 时间轴要拉长看（第 10 章方法）。
- 并行 DML 与 temp 的乘法效应：PX 每进程独立内存配额+各自临时段，`DEGREE` 翻倍≈temp 峰值翻倍。

## 16.5 案例演练：字面量洪水引发硬解析风暴（⚠️ 按章主题结构化）

1. 取数：AWR Load Profile 的 parse ratio 与每秒硬解析数、`library cache` 闩榜、`v$sql` 按 version_count 降序（第 9/10 章路由）。
2. 定性：版本数爆炸到千级 → 逐条看失效原因列（绑定类型/宽度变化、NLS 会话差异、对象重编译广播）。
3. 止血：应用整改需时日，先在诊断窗内 `CURSOR_SHIPPING=FORCE` 缓解；评估副作用（字面量语义变化、共享游标混用）后限时使用、限时撤销。
4. 内存面：shared pool 尺寸与 flush 策略核对——防"闩等待变少"换成"CPU 更高"。
5. 根治：输出应用 SQL 规范化清单（绑定变量化改造列表），并配 `v$db_object_cache` 钉住少数关键对象；风暴变计划，计划进变更管理。

## 16.6 常见误区（⚠️ 社区口径）

- "子闩调多=不争用"——分片只摊薄队列长度，热点块/热行不拆，等待换个名字继续存在。
- "TEMP 小所以不重要"——计划错误下单条 SQL 可吞几百 GB 临时段（15.1 的终形态）。
- "mutex 取代 latch 后就没锁问题"——游标版本与失效风暴是 mutex 时代的新形态（16.3 末行）。

## 核心概念速览（中英对照）

- **临时表空间** — TEMP Tablespace：排序/哈希/临时段的缓冲区外空间 ⚠️
- **临时段视图** — V$TEMPSEG_USAGE：会话级 temp 占用取证面 ⚠️
- **直接路径临时读写** — Direct Path Read/Write Temp：workarea 溢出到磁盘的等待形态 ⚠️
- **全局临时表** — GTT：会话/事务级临时数据的关系化替代 ⚠️
- **临时 UNDO** — Temporary Undo（12c）：UNDO 写入 TEMP 的并行友好形态 ⚠️
- **闩锁** — Latch：内存结构的短时串行闸门，竞争以重试退避 ⚠️
- **互斥锁** — Mutex：细粒度内存锁+句柄校验，防改读撕裂 ⚠️
- **子闩** — Latch Children：同一闩的分片计数视图 ⚠️
- **库缓存闩** — Library Cache Latch：共享 SQL 区的串行点 ⚠️
- **行缓存** — Row Cache：数据字典行缓存及其对象锁 ⚠️
- **硬解析风暴** — Hard Parse Storm：字面量洪水引发的闩/版本问题总因 ⚠️
- **等待类路由** — Wait Class Routing：Concurrency/Cluster 分流到 16/3 章 ⚠️

## 最新演进与工业实践

- **19c/23ai 延续**：自动 PGA 管理+并行粒度内存配额（PX granule）使第 15 章参数面继续收窄；临时 UNDO 在 OLAP/ETL 库被文档推荐为默认考虑项 ⚠️（docs.oracle.com 数据库性能调优指南"Temporary Undo"节 ✅ 域名可达）。
- **mutex 化推进**：共享池/库缓存的闩→互斥替代自 10g 起逐步完成；现代版本该章问题更多呈现为"游标版本与失效"形态（与 ACS/自动索引联动），社区案例库持续活跃 ⚠️。
- **ASM 自适应**：磁盘组余量告警+ASMFD 管理让 15.1 的"容量终形态"提前到告警层暴露；工业实践中 temp 爆掉的头号根因仍是失控 SQL，取证走 SQL Monitor（⚠️ 许可面同第 12 章）。
- **跨引擎镜像**：SQLite 🔧G1 的文件锁与 PG 的 LWLock（buffer mapping 分片闩）同谱系；"把单闩拆成分片"的思路在各引擎都以哈希分片形式重现——本章的处置表在 PG/MySQL 语境可直接翻译。
