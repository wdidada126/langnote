## 2.1 三次失败模式，一条演化线

读架构史的正确姿势不是"新旧替代"，而是"每种架构把哪种成本变便宜、把哪种成本变贵"：

| 代际 | 变便宜了 | 变贵了 | 典型失效模式 |
| --- | --- | --- | --- |
| 数仓（1990s–） | 可信语义：ACID、schema、治理内置 | 存储单价、闭源算力 | 非结构化数据进不来；ML 负载挤爆计费 |
| 数据湖（2010s–） | 存储单价、什么都能放 | 语义真空：无事务/无 schema 约束 | "数据沼泽"：表即目录，坏了没人知道 |
| Lambda 双链路（2011–） | 批流各干各的擅长项 | 两套代码、两套结果的口径漂移 | 批流答案不一致，运维翻倍 |
| 湖仓（2020s–） | 一份数据 + 外置语义 | 平台工程与元数据运维 | 选型过早/格式锁定（→ 第 8 章反模式） |

Kappa（以重放流代替批）的遗产被湖仓吸收：时间旅行 + 增量读取（CDF/changelog）让"重放"成了
表的内建能力，机制见
[../Delta_Lake_Definitive_Guide/07-高级特性-DV与CDF.md](../Delta_Lake_Definitive_Guide/07-高级特性-DV与CDF.md)
与 [../Apache_Paimon_Streaming_Lakehouse/07-Changelog生成机制.md](../Apache_Paimon_Streaming_Lakehouse/07-Changelog生成机制.md)。

## 2.2 "湖仓 vs 数仓"的成本争议：把 2024–2026 的仗打明白

这是本章标题级价值所在，也是本书（平台中立立场）与两家厂商叙事的最大温差：

- **厂商 A（湖仓教）说**：湖上直接跑 BI/ML，成本降一个数量级（Databricks 长期口径，
  见其 lakehouse 架构文档 <https://learn.microsoft.com/en-us/azure/databricks/lakehouse-architecture/>，已核可达）。
- **厂商 B（数仓教）说**：托管服务把运维税归零，"你雇不起湖仓"（Snowflake 对外部表/开放格式的支持
  叙事，见 <https://docs.snowflake.com/en/user-guide/tables-iceberg>，已核可达）。
- **第三方成本分析**（云账单咨询口径）给出的可核事实：Databricks 的 DBU 计费模型复杂度本身构成
  隐性成本，账单失控案例集中于**小文件重扫、未维护的表、闲时集群**三处——
  <https://www.cloudzero.com/blog/databricks-pricing/>（2025-04 文章，已核可达 ⚠️ 转述）。
- **2025 年的公开"互怼"事件**（Databricks 与 Snowflake 高管在 2025 年多次公开贬损对方架构/产品）：
  本目录检索期内未能核实到可直接引用的权威报道 URL，**只作 ⚠️ 待核验提示**，不编造引文。

给平台的收敛结论（可带走）：
1. **可比口径只有 TCO 全栈**：存储 + 计算 + 平台人力 + 运维税 + 迁移期权，缺一项的比较都是营销。
2. 湖仓的成本优势在**负载组合多样化**（BI+ML+流同数据）时才兑现；单一 SQL 分析负载常是数仓赢。
3. 争议的真正共识是**格式层向 Iceberg 收敛**（→ 第 8 章"最新演进"）：阵营之争已从"要不要开放"
   变成"目录与引擎的开放程度"。

## 2.3 现代数据平台（MDP）分层：湖仓住在哪一层

社区常说的 Modern Data Platform 栈（ingestion → storage+format → transformation → catalog →
observability → consumption）里，湖仓不是某一层，而是**第 2–4 层的组合体**：

```
接入  CDC/事件/批管道        → 机制见 ../Apache_Hudi_Definitive_Guide/03-写入Hudi.md
底座  对象存储 + 开放表格式   → 本目录 03 章
转换  SQL/批/流引擎          → 本目录 05 章
目录  元数据/契约/血缘       → 本目录 04 章（平台单点论）
消费  BI/feature store/agent → 本目录 06 章（AI 资产治理）
```

data mesh（域自治 + 数据产品 + 联邦治理）是**组织层**方案，与湖仓（技术层方案）正交：
没有技术上的共享目录与格式，mesh 会退化成 N 个新孤岛；反之湖仓不解决"谁对指标负责"。
对照阅读：[../The_Data_Lakehouse/05-数据架构与数据工程.md](../The_Data_Lakehouse/05-数据架构与数据工程.md)、
组织方法论在 [../大数据之路.md](../大数据之路.md)（阿里中台口径，可当作 mesh 的东方对照物）。

## 2.4 迁移判断树（平台视角）

```
现在在哪？                      目标负载？                 建议
──────────────────────────────────────────────────────────────
传统数仓为主          仅扩 BI 容量          留在数仓，先做下游治理
数仓 + 有 ML/流需求   负载组合扩张          湖仓（金层仍可由数仓承接 = 混合式）
Hadoop 湖遗留         成本/运维不可续       湖仓迁移（格式先行，引擎后置）
已在云数仓            想省存储              先算运维税，别只算单价 ⚠️
新建平台              一切皆可能            按第 7 章用例驱动设计法走一遍
```

混合式（lakehouse + warehouse 并存、各司其职）是 2024–2026 大企业的主流稳态，不是过渡态；
"一步到位全湖仓"的案例失败率最高（→ 本目录 08 章反模式）。

## 2.6 一页纸演讲话术（给两种听众的同一场会）

**给 CFO（成本叙事）**："我们不是在数仓和湖仓之间选信仰，是在为三类负载分别选计费模型：
稳定报表继续用托管算力（单位效率最高），增长中的 ML/流负载用开放格式 + 自有目录（期权价值最高），
两边共享的原料层只存一份。每个季度用同一张 TCO 表复查这个配比。"

**给工程负责人（风险叙事）**："迁移的验收语言只有三种：双写对账差异为零、第二引擎能独立读出、
回切演练成功。任何跳过这三问的方案，无论 PPT 里的格式多正确，都是把技术选型做成了单点故障。"

两段话的共同前提正是 2.2 的收敛结论：**争议双方都赢了——数仓拿到了湖的便宜存储，湖拿到了数仓的语义，
而平台团队拿到的是全部运维税，所以要按全栈口径做 owner。**

## 核心概念速览（中英对照）

- **失效模式** — failure mode：每代架构解决旧成本时引入的新痛点，选型按此计价。
- **数据沼泽** — data lake swamp：无约束数据湖的终态：不可信、不可发现、不可删。
- **Lambda 架构** — Lambda architecture：批流双链路各自出结果、以速度层补新鲜度的旧范式。
- **Kappa 架构** — Kappa architecture：以可重放日志统一批流；其能力被表格式的时间旅行吸收。
- **TCO 全栈** — total cost of ownership：存储+计算+人力+运维税+迁移期权的完整成本口径。
- **运维税** — operational tax：compaction、孤儿清理、小文件治理等湖仓持续成本。
- **现代数据平台** — modern data platform（MDP）：接入到消费的六层参考栈，湖仓占据中段。
- **data mesh**：组织级数据产品联邦，与技术层湖仓正交、互补。
- **混合稳态** — hybrid steady state：湖仓与数仓长期并存、按负载分工的常态而非过渡态。
- **格式收敛** — format consolidation：多阵营向 Iceberg 接口靠拢的 2024–2026 趋势。
- **用例驱动迁移** — workload-driven migration：先定 SLA 与负载再选架构的决策顺序。
