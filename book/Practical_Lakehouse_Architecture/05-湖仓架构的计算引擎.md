## 5.1 存算分离的三种粒度

"存算分离"不是一次开关，而是三个可独立选择的层级：

| 粒度 | 分离了什么 | 典型形态 | 代价 |
| --- | --- | --- | --- |
| L1 对象级 | 数据文件离开计算节点本地盘 | 一切湖仓的前提 | 网络成为带宽瓶颈 |
| L2 表语义级 | 表状态由目录持有，引擎只是会话 | REST catalog 多引擎读写 | 目录成单点（→ 04 章） |
| L3 计费级 | 查询按量弹性、闲时零成本 | serverless 查询面（Trino/云数仓 serverless） | 厂商锁回一部分（冷启动/缓存私有） |

架构评审要问"分离到哪一层"：只做 L1 的"伪湖仓"（引擎独占表状态、缓存即真相）迁移性最差。

## 5.2 引擎矩阵：湖仓上谁干什么

- **Spark**：批与大规模 ETL 主力，湖仓写路径的第一公民；湖上用法见
  [../Use_Iceberg_with_Spark/00-总览与阅读地图.md](../Use_Iceberg_with_Spark/00-总览与阅读地图.md)。
- **Flink**：流式入湖与 CDC 的主力（checkpoint 与提交对齐），Paimon 的第一生态：
  [../Apache_Paimon_Streaming_Lakehouse/11-Flink集成与CDC入湖实践.md](../Apache_Paimon_Streaming_Lakehouse/11-Flink集成与CDC入湖实践.md)。
- **Trino/StarRocks/Doris**：交互式 SQL 面（BI/API），读湖引擎 + 自带缓存/物化层补延迟；
  引擎演化全景在 [../bigdata/10-计算引擎的演进.md](../bigdata/10-计算引擎的演进.md)。
- **云数仓引擎（Snowflake/BigQuery/Redshift…）**：不可本机实测，一律 ⚠️ 转述厂商文档；
  在湖仓里的新角色是"外部表的加速面"（如 Snowflake 读 Iceberg、BigQuery 的 Iceberg 表支持——
  后者本目录网络不可达，⚠️ 未核验链接故不贴 URL）。
- **Databricks 系（SQL warehouse/DLT）**：Delta 原生 + UniForm/Iceberg 互操作双面人（5.5 专节）。

**多引擎不是福利而是账单**：每加一个引擎，就要为它的目录连接器、缓存一致性、权限映射各付一份税。

## 5.3 批流一体：三条路线与其税

| 路线 | 做法 | 代表 | 税 |
| --- | --- | --- | --- |
| 流式写表 | 微批/流式提交进湖表，新鲜度=提交间隔 | Flink+Paimon、Spark Structured Streaming+Delta | 小文件/compaction（→ 03 章） |
| 表即 changelog | 增量读（CDF/incremental scan）替代消息队列 | [../Delta_Lake_Definitive_Guide/07-高级特性-DV与CDF.md](../Delta_Lake_Definitive_Guide/07-高级特性-DV与CDF.md) | 保留期 vs 下游追平速度 |
| 一张表两种读 | 批读快照 + 流读增量并存 | [../Apache_Paimon_Streaming_Lakehouse/08-读路径批流一体读取.md](../Apache_Paimon_Streaming_Lakehouse/08-读路径批流一体读取.md)、Iceberg 增量读 | 引擎支持度参差 |

Kafka 时代的"流是一等公民"在湖仓语境下被改写为：**变更进表、表即事实流**（table-first）；
队列退居缓冲与解耦。消息底座视角可对照 [../bigdata/08-消息中间件与数据接入.md](../bigdata/08-消息中间件与数据接入.md)。

## 5.4 多租户与资源隔离

- 目录给命名空间隔离，计算侧要补齐：队列/资源组（Spark dynamic allocation、Trino resource groups、
  Flink 会话隔离）+ 存储侧限流；三侧粒度对齐是平台设计题，参考姊妹章
  [../湖仓架构大规模数据平台的设计和实现/05-湖仓架构的计算引擎.md](../湖仓架构大规模数据平台的设计和实现/05-湖仓架构的计算引擎.md)。
- 公平性反模式：一条失控全表扫拖垮共享集群 → 需要查询级熔断与按标签的成本归因（→ 07 章 KPI）。
- 缓存的正确位置：结果缓存（可丢）优于数据缓存（破坏"多引擎一份数据"前提的程度取决于失效协议）。

## 5.5 Databricks 阵营的"Delta 为体、Iceberg 为面"（2024–2026 现状）

这是本书成书后变化最快的一节，务必按 2026 口径重写心智：

- **UniForm 的现在时**：产品名逐步淡出，文档重构为 **"Iceberg reads"**（Delta 表自动异步生成
  Iceberg 元数据，Iceberg 客户端只读，不改写数据文件）：
  <https://learn.microsoft.com/en-us/azure/databricks/delta/iceberg-reads>（已核可达）；
  旧 `IcebergCompatV1` 配置移入归档页：
  <https://learn.microsoft.com/en-us/azure/databricks/archive/legacy/uniform>（已核可达）。
  已核实的关键约束（摘官方文档）：需注册 UC + column mapping + 协议 ≥2/7；开启后不可用删除向量
  （Iceberg v2 读不支持 DV，v3 支持——官方注）；Iceberg 客户端**只读**。
- **反向通道**：Unity Catalog 可充当 Iceberg REST catalog，让外部 Iceberg 引擎读 Databricks 表
  （external-access 文档，已核可达，见 04 章）；Databricks 亦提供 managed Iceberg 路线
  （<https://learn.microsoft.com/en-us/azure/databricks/iceberg/>，已核可达）。
- **平台读法**：Databricks 的开放姿态以"写入与优化仍在自家引擎、读面开放"为边界——
  评估锁定要按 01 章"数据/元数据/权限三项计价"框架执行。

## 5.7 新引擎接入验收清单（接入前先算税，接入后照单验收）

```
□ 目录连接器：走 REST 标准接口还是私有适配器？适配器的升级绑定谁？（→04章铁律）
□ 凭证路径：是否经目录 vending 单通道？有无"临时"直连桶后门？（→06.1）
□ 写权限：允许写则提交频率契约已签？（→03.7 五问之1）
□ 统计使用：是否消费文件/分区统计做裁剪？还是回退全扫？（→03.2）
□ 特性覆盖：支持目标表的格式版本与特性（DV/MOR/演化）到几成？读还是只读？
□ 成本可见性：该引擎的查询能否打上域/表标签进账单？（→07.5 KPI）
□ 缓存一致性：结果缓存的失效协议是什么？能否一键全清？
□ 退出演练：禁用该引擎后，其消费面由谁兜底、多久能兜住？
```

八项过不了三项以上的引擎，接进来只是把 08.2 的事故剧本提前写好。

**本章一句话立场**：引擎矩阵的健康度不看接了几个，而看**拔掉任何一个后，平台还剩多少读能力**——
这正是 5.1 L2/L3 分离是否做到位的压力测试。

## 核心概念速览（中英对照）

- **存算分离三粒度** — L1 object / L2 table-state / L3 billing：分离深度的评审坐标系。
- **引擎税** — per-engine integration cost：每个引擎的目录连接/权限映射/缓存一致性维护成本。
- **table-first 流** — table-first streaming：以表增量读替代专用消息主题作事实流的架构改写。
- **增量读** — incremental read / CDC scan：只消费上个快照以来的变更（CDF/incremental append）。
- **Iceberg reads（UniForm）** — Databricks 的 Delta→Iceberg 元数据异步镜像、外部只读机制。
- **managed Iceberg** — Databricks 托管的以 Iceberg 为一等表的路线。
- **凭证 vending（引擎侧）** — engine-scoped credential exchange：引擎经目录换取临时存储凭证。
- **资源队列** — resource queue/group：SQL 面与管道面的租户隔离单位。
- **查询熔断** — query circuit-breaker：按扫描量/时长的失控查询拦截。
- **结果缓存 vs 数据缓存** — result vs data cache：可丢缓存优于真相缓存。
- **只读镜像** — read-only metadata mirror：UniForm 类方案的共享边界（写仍单主）。
