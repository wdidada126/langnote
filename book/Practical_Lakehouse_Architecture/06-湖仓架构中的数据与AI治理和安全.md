## 6.1 "治理外置"的三层动作

湖仓治理的前提是：**策略附着在表/目录这层跨引擎共享的元数据上，才能一次定义、处处生效**。三步：

1. **身份统一**：人/服务账号走 IdP→目录映射，废掉引擎本地账号（否则策略可绕）。
2. **授权下移**：RBAC/ABAC 归口目录层，行级/列级策略由目录服务持有（Unity/Polaris 类，能力差异 ⚠️ 现查）。
3. **凭证收口**：桶密钥收窄为目录服务持有，引擎经目录 vending 换临时凭证（→ 04.2）。

机制层对照：[../Delta_Lake_Definitive_Guide/11-治理安全与数据血缘.md](../Delta_Lake_Definitive_Guide/11-治理安全与数据血缘.md)。
企业安全体系的全景（湖仓无关的部分）在根单文件 [../数据安全架构设计与实战.md](../数据安全架构设计与实战.md)。

## 6.2 数据保护五层（湖仓语境下的位置感）

| 层 | 通用机制 | 湖仓特有的注意点 |
| --- | --- | --- |
| 静态加密 | SSE-KMS/CMEK | 密钥粒度跟数据产品对齐；整桶一把键会让"撤销"无从下手 |
| 传输与网络 | 私网端点（PrivateLink 类） | 多引擎共读同一表 = 多条出网路径，审计要枚举全量 |
| 脱敏 | 策略下推/结果层掩码 | MOR 删除向量与旧快照仍含旧值——脱敏承诺必须绑定快照过期策略（→6.4） |
| 细粒度访问 | 行过滤/列遮罩 | 并非所有读路径都强制（引擎直读裸文件的旧习要禁，⚠️ 支持矩阵现查） |
| 审计 | 访问日志+查询日志 | "谁读了哪些文件"在对象存储层、"谁查了什么表"在目录/引擎层，两边要用 trace id 缝起来 |

## 6.3 血缘：湖仓里的血缘是删除计划的前置

- 三种用途：影响分析（改 schema 谁会碎）、合规举证（数据从哪来到哪去）、事故定位（污染扩散面）。
- 湖仓增量：**血缘要落到表版本粒度**——"gold 的某快照派生自 silver 的某快照"，
  时间旅行与血缘互相成就；medallion 晋级链天然给出主干血缘
  （[../Delta_Lake_Definitive_Guide/08-湖仓架构-Medallion.md](../Delta_Lake_Definitive_Guide/08-湖仓架构-Medallion.md)）。
- 工程纪律：血缘是管道的副产品，管道代码化 + 元数据上报自动化，**手工登记的血缘不可信**。
  方法论纵深：[../数据血缘分析原理与实践.md](../数据血缘分析原理与实践.md)（根单文件）。

## 6.4 删除权：湖仓最硬的合规题

"被遗忘权"在湖仓的真实成本 = 一次逻辑删除的**四次物理传播**：
① 新写文件/删除标记；② 旧快照（时间旅行里还活着！）；③ 生命周期冷副本；④ 缓存与派生（特征库/物化视图）。

平台级答案：**把"物理删除完成期限"写成 SLA，倒推快照保留期（TTL）与生命周期策略**，
而不是承诺"我们支持 DELETE"。机制与账目：03.4（保留期/对象锁）；
Iceberg V3 删除向量降低合规删除的写放大（来源为 AWS 官方 v3 指南，见 03 章「最新演进」）。

## 6.5 AI 资产治理："数据+AI 目录"是不是噱头

- 新对象清单：模型、特征、向量索引、评测数据集。它们的治理共性是**可复现性**：
  数据集快照版本 ↔ 训练运行 ↔ 模型版本 的三元绑定。
- 湖仓里的实现路径：表快照 + tag/branch 钉死训练集
  （[../Apache_Paimon_Streaming_Lakehouse/10-Tag分支与时间旅行.md](../Apache_Paimon_Streaming_Lakehouse/10-Tag分支与时间旅行.md)、
  [../Delta_Lake_Definitive_Guide/04-表维护-时间旅行与VACUUM.md](../Delta_Lake_Definitive_Guide/04-表维护-时间旅行与VACUUM.md)）；
  特征点时正确性依赖合并引擎语义（[../Apache_Paimon_Streaming_Lakehouse/06-合并引擎.md](../Apache_Paimon_Streaming_Lakehouse/06-合并引擎.md)）。
- 鉴别法：厂商"AI-ready 治理"表述只有落到**策略引擎、血缘 API、保留策略**三个具体挂点才可信，
  其余按营销读（Apache Polaris 官方即自述"catalog for data and AI assets"，挂点核对见其官网）。

## 6.7 治理成熟度自评（五级，评到级就去补该级的最低动作）

| 级 | 特征 | 最低补救动作 |
| --- | --- | --- |
| L1 账号线 | 权限 = 引擎账号 + 桶策略 | 先收身份：IdP→目录映射，废本地账号（6.1-1） |
| L2 目录线 | 目录有表清单但无策略挂点 | 凭证 vending 单通道试点一个域（6.1-3） |
| L3 策略线 | 有行/列策略但引擎直读可绕 | 桶策略收口 + 审计缝合定位绕行者（6.2） |
| L4 生命周期线 | TTL/冷层/删除有制度但靠人跑 | 删除权 runbook 自动化 + 期限 SLA 化（6.4/6.8） |
| L5 资产线 | 血缘/契约/复现三元组进 CI | 维持：把 08.4 checklist 纳入每次架构评审 |

大多数团队的真实位置在 L2–L3 之间，而厂商 demo 讲的都发生在 L4 之后——这个落差就是"上了目录≠有治理"。

## 6.8 合规删除 Runbook（GDPR/个保法通用骨架）

```
T+0   受理：定位主体→表→行（依赖 6.3 血缘图，无血缘先补映射）
T+0   逻辑删除：按表特性选 DV/MOR/COW（写放大预算见 03.7-1）
T+0   登记删除事件：范围、方式、完成期限 SLA（对外承诺从这里开始计时）
T+ttl 快照过期/compaction：物理清除旧文件与旧快照（保留期=SLA，03.4）
T+ttl 派生清除：缓存/物化视图/特征库/训练集 tag 的联动失效（6.4 第④份账）
T+ttl+ 出具证明：目录审计日志 + 对象存储访问日志缝合回放（6.2 审计行）
```

Runbook 的每一行都要有自动化作业归属人；手工步骤不超过一处，否则审计现场必翻车。

**治理的经济学**：L1→L2 的钱花在身份与目录集成上，L2→L3 的钱花在策略引擎上，
L3→L4 的钱花在**与时间赛跑**（TTL 与 SLA 对齐）上——级别越高越像运维，越不像采购能解决的问题。

## 核心概念速览（中英对照）

- **策略外置** — policy externalization：授权/脱敏附着于跨引擎共享元数据层的治理总纲。
- **凭证 vending** — credential vending：目录代发临时凭证、桶密钥收口的单通道设计。
- **行过滤/列遮罩** — row filter / column mask：表级细粒度策略，须防引擎直读绕过。
- **CMEK** — customer-managed encryption keys：密钥粒度=数据产品粒度的加密前提。
- **审计缝合** — audit stitching：对象层"读文件"与目录层"查表"两类日志的 trace 级拼接。
- **血缘** — data lineage：表版本级数据流图谱，删除计划与影响分析的骨架。
- **删除权四份账** — erasure fan-out：一次逻辑删除在湖仓的四次物理传播。
- **TTL 对齐** — retention alignment：合规期限与快照保留期的倒推设计。
- **可复现性三元组** — reproducibility triple：数据集快照↔训练运行↔模型版本绑定。
- **tag/branch 钉版** — snapshot pinning：用表分支冻结训练/评测数据。
- **点时正确** — point-in-time correctness：特征值与其计算时刻数据状态的一致性。
- **挂点鉴别法** — concrete-hook test：治理宣称落到策略引擎/血缘 API/保留策略才可信。
