## 3.1 对象存储的"脾气"决定了湖仓的一切

湖仓选型争论看似在表格式层，其实根在存储层的四条物理约束：

1. **对象不可变**：更新 = 写新对象（+ 删旧对象）。所以湖仓的"行级更新"全是戏法：
   COW（重写文件）或 MOR（追加删除标记，读时合并），机制对照见
   [../Apache_Iceberg活用入門/05-行级删除与删除文件.md](../Apache_Iceberg活用入門/05-行级删除与删除文件.md)
   与 [../Delta_Lake_Definitive_Guide/07-高级特性-DV与CDF.md](../Delta_Lake_Definitive_Guide/07-高级特性-DV与CDF.md)。
2. **LIST 语义弱且贵**：目录列举慢/部分云已删 LIST 可扩展性承诺 → 表格式必须以"元数据树直接列出文件"
   取代扫描（这是湖仓区别于裸 Parquet 目录的本质）。
3. **条件写/原语差异**：S3 2024 年起支持 conditional writes（If-None-Match 等）后，Hadoop 时代
   "S3 不能安全跑 commit"的旧结论失效；各格式对 DynamoDB 条件写/文件原语依赖不同（⚠️ 细节以各格式
   官方可靠性文档现查为准）。
4. **一致性窗口**：读到旧对象列表的风险必须由 catalog 的"当前快照指针"单点化解决（→ 第 4 章）。

平台结论：**把存储层当不可变、append-only、按请求计费的介质来设计**，任何"把它当 POSIX 盘"的
捷径都会在规模上来时反噬。

## 3.2 文件格式：Parquet 一超与列存三件套

- 事实标准：四大表格式的数据文件都默认/主推 Apache Parquet（ORC 退守 Hive 遗留）。列存三件套
  ——行组（row group）裁剪、谓词下推、列式压缩——决定扫描成本的第一性。
  文件内部机制精读：[../bigdata/09-存储与文件格式.md](../bigdata/09-存储与文件格式.md)。
- 平台层只需做对四件事：**目标文件尺寸**（常见 128–512MB，太小则元数据与请求爆炸，太大则裁剪失效）、
  **压缩编解码选择**（Snappy 求低 CPU，Zstd 求尺寸；注意 Databricks UniForm 表会强制 Zstd——见 3.5）、
  **schema 演进纪律**（列映射，见
  [../Apache_Iceberg活用入門/04-Schema演化.md](../Apache_Iceberg活用入門/04-Schema演化.md)）、
  **统计信息**（min/max/bloom 决定跳过率）。
- 反模式："按天 × 按租户 × 按国家"分区后单文件几十 KB —— 分区过度 + 文件过小的复合症，
  修法在 3.3。

**成本账公式（带走）**：`总存储成本 ≈ 有效数据 × 压缩率 × 副本/冗余策略 × 层单价 + (文件数 × 请求单价)`。
第二项常被忘掉：百万级小文件的 LIST/GET 请求费在大规模下可与存储费同量级。

## 3.4 多副本、容灾与"湖仓的地域观"

- 对象存储自带 region 内冗余（厂商口径，⚠️ 未实测）；**跨区域复制是平台自己的责任**：
  桶复制对"表"是异步的，灾难切换时目录指针与数据文件的版本对齐要靠 catalog 复制方案
  （Glue 复制/Databricks 湖联邦等，⚠️ 各家能力矩阵需现查），本目录不背熟数。
- 时间旅行不是备份：过期策略（`expire_snapshots`/VACUUM）会物理删除历史；"合规保留"要开对象锁/WORM
  （⚠️ 各云实现名不同，按厂商文档核）。
- 教训级反例（社区常谈，⚠️ 转述）：湖仓时代重演"删库"事故的方式变成"误跑 VACUUM/过期保留期设零"，
  维护操作要有变更评审与 dry-run。

## 3.7 存储层五问（新表准入评审用）

1. **这张表的写放大预算是多少？** COW 还是 MOR、允许什么提交频率——写进表属性而不是口头约定（3.1-1）。
2. **文件尺寸目标与当前 P50 差几倍？** 差 3 倍以上即列维护工单，不等事故（3.2/3.3）。
3. **最老的可读快照年龄多少？** 它同时回答成本（历史体积）与合规（删除承诺兑现）两笔账（3.4/06.4 联动）。
4. **删一次 LIST 会怎样？** 任何"引擎绕过目录直接扫桶"的路径都是布局优化的漏点（3.1-2）。
5. **请求费进过月度账单评审吗？** 小文件的账单显形在 GET/LIST 行，不在存储行（3.3 公式第二项）。

五问齐了，第 08 章事故四件套里的两件（小文件雪崩、VACUUM 风暴）就失去了发生条件。

**三句速记（贴工位版）**：
1. 对象存储没有"改"，只有"补"和"删慢一点"——所有更新语义都是元数据戏法；
2. 湖仓账单的隐藏项叫请求费与元数据体积，不叫存储费；
3. 任何布局优化（分区/聚类/compaction）都是**用今天的写成本换明天的读成本**，
   换不换、换多大，只由该表的读写比决定——这一句同时解释 05 章"一张表伺候所有引擎"为何是反模式。

## 核心概念速览（中英对照）

- **对象存储** — object storage：以桶/键寻址、对象不可变、按请求与存储双重计费的介质。
- **追加即更新** — append-as-update：不可变介质上"更新=写新文件"的统一底层动作。
- **COW / MOR** — copy-on-write / merge-on-read：行级更新的两大代价分配（写贵 vs 读贵）。
- **小文件问题** — small file problem：提交频率与文件尺寸的失衡，湖仓头号运维税。
- **列存/行组** — columnar layout / row group：Parquet 的裁剪与压缩单位。
- **谓词下推** — predicate pushdown：用文件统计跳过无关行组。
- **分区演化** — partition evolution：不改写数据地改变分区策略（Iceberg 招牌能力）。
- **快照过期** — snapshot expiration：物理删除历史版本以控成本，与备份是两回事。
- **WORM/对象锁** — write-once-read-many lock：合规不可变保留的存储层机制。
- **跨区域复制** — cross-region replication：湖仓灾备中平台自担的部分。
- **请求费放大** — request-cost amplification：百万小文件把 LIST/GET 费用推到存储费量级。

## 最新演进与工业实践

- 🔧 **S3 Tables（2024-11 GA 至今）**：AWS 把"开箱 Iceberg + 内建 compaction/清理 + Iceberg REST API"
  做成存储原生服务，直接吃掉本章 3.3 表格里的多数运维税：
  <https://aws.amazon.com/s3/features/tables/> 与
  <https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables.html>（均已核可达）。
  平台含义：**"要不要自建表维护"从默认 Yes 变成需要论证的选项**。
- 🔧 **Iceberg V3 用删除向量替换 v2 的 positional delete 文件**：批删/合规删的写放大显著下降，
  Puffin 二进制格式；v2→v3 升级单向、不改写数据：
  <https://docs.aws.amazon.com/prescriptive-guidance/latest/apache-iceberg-on-aws/table-spec-v3.html>（已核可达）。
- 🔧 **UniForm 表的元数据清理入 VACUUM 语义**：Databricks 文档明确 Delta+Iceberg 双元数据目录下，
  旧版本元数据只有 `VACUUM FULL` 会清（DR 17.2 起）：
  <https://learn.microsoft.com/en-us/azure/databricks/delta/iceberg-reads>（已核可达）。
- ⚠️ **Parquet v2 数据格式/Zstd 默认化**等行业传闻未过规范页核验，引用前自查
  <https://iceberg.apache.org/spec/>。
