## 4.1 先拆词：三种"目录"别混谈

| 词 | 回答的问题 | 代表 | 本章态度 |
| --- | --- | --- | --- |
| 技术目录（metastore/catalog） | "这张表**当前**是哪些文件？" | HMS、Glue Data Catalog、Iceberg REST server | 平台单点，主战场 |

## 4.2 技术目录的三件事与一条铁律

技术目录只做三件事：**(a)** 保存"表名 → 当前元数据指针"的原子切换；**(b)** 声明命名空间与
凭证 vending（谁可以读写哪级前缀，由目录发临时凭证而非桶策略）；**(c)** 作为权限/策略的挂点
（行级策略跟表走而不是跟引擎走，→ 06 章）。

铁律：**"表当前状态"必须有唯一权威**。同一张表在两个目录里各有指针 = 迟早双写分叉。
湖仓事故复盘里"目录脑裂/指针落后"是高频项（⚠️ 转述社区案例，不引具体数）。

## 4.3 REST Catalog：接口层的"HTTP 时刻"

- Iceberg REST Catalog Spec 把"目录"从各引擎的私有连接器（HMS Thrift、各云 SDK）变成
  一个可自托管/可换供应商的 HTTP 接口；规范页：见姊妹目录逐条精读
  [../Apache_Iceberg活用入門/07-Catalog生态.md](../Apache_Iceberg活用入門/07-Catalog生态.md)。
- 服务端实现 2024–2026 已成熟成生态：**Apache Polaris**（Snowflake 贡献给 ASF 的开源
  Iceberg REST 目录，"The open catalog for data and AI assets"，<https://polaris.apache.org/> 已核可达；
  其 ASF 孵化/顶级状态表述以官网与 ASF 公告现查为准 ⚠️）、**Lakekeeper**、各云托管
  （AWS Glue 的 Iceberg REST endpoints、Azure 的 Fabric/ADLS Gen2 REST catalog 等，能力矩阵 ⚠️ 现查）。
- 客户端侧：Spark/Flink/Trino/Kafka-connect 都只认"REST 接口 + 凭证"，**目录从引擎依赖变成平台服务**。

## 4.4 Unity Catalog：从私有 metastore 到开源项目

- 2024-06 Databricks 将 Unity Catalog 开源（Apache 2.0，独立仓库与社区版），意图是把"目录 + 血缘 +
  权限 + 多格式（Delta/Iceberg）"做成事实标准平台层：<https://unitycatalog.io/>、
  <https://github.com/unitycatalog/unitycatalog>（仓库存在性经 GitHub API 核验）。
- 平台视角的评估要点：UC 的"表"原语同时服务 Delta 与 Iceberg（配合 UniForm/managed Iceberg，→ 05 章），
  但其完整价值绑定 Databricks 体验；OSS 版与托管版能力差需自行对照（⚠️ 不背版本号）。
- 与 Polaris 对照的记忆法：**Polaris 是"最好的 Iceberg REST 目录之一"，UC 是"目录 + 治理平台的开源化"**；
  两者都支持被非本阵营引擎消费。

## 4.5 目录即性能与成本

- 规划链路里目录贡献两笔账：指针跳数（catalog API 延迟 × 查询并发）与 LIST 替代率（好目录把
  文件清单塞进元数据，差用法让引擎回退扫描）——细节机制在
  [../Apache_Iceberg活用入門/02-元数据三层结构.md](../Apache_Iceberg活用入門/02-元数据三层结构.md)。
- 多租户隔离的"目录粒度"选择（单目录多命名空间 vs 多目录）决定爆炸半径；
  与计算侧资源队列合看（→ 05 章 5.4）。
- 反模式：把业务目录的"血缘图"当技术目录的"依赖真相"来做删除评审——前者常滞后于后者。

## 4.6 选型问答（平台评审可直接用）

```
要跨云/跨引擎的 Iceberg 表？          → REST catalog（Polaris/Lakekeeper/云托管）
全家桶已在 Databricks？               → Unity Catalog 优先，盯 OSS 版进度
已有 Hive 资产要平滑过渡？            → HMS + 同步器是过渡态，定退出计划（→ 07 章迁移）
要"表即产品"的治理挂点？              → 业务目录 + 技术目录联动（→ 06 章），别指望单目录全包
云上小团队？                          → S3 Tables/Glue REST 这类托管目录，先别自建
```

## 4.8 目录故障模式与预案表（SRE 视角补全"单点论"）

| 故障 | 现场 | 预案（设计时就要有） |
| --- | --- | --- |
| 目录不可用 | 新提交全停；已规划的查询是否继续取决于元数据缓存 | 读路径可容忍 N 分钟目录不可用（引擎侧快照缓存）；写路径明示排队策略 |
| 指针落后（异步镜像类，如 UniForm/Iceberg reads） | 外部引擎读到旧版本却无人报错 | 对账字段进监控（官方如 `converted_delta_version`，见 05.5 来源页）；落后阈值告警 |
| 双目录并存（迁移期） | 两个入口各有增量写 | 迁移必须带**只读切换窗口**（07.4 第 4 步），窗口外单写者 |
| 凭证 vending 不可用 | 新查询无法拿临时凭证，全线失败 | 降级路径要么显式设计（只读短时效缓存凭证），要么禁止并写入 DR 演练 |
| 命名空间误删/覆盖 | 域间边界失守 | 目录变更走与数据同级的评审；命名空间按域隔离授权（→06.1） |

心跳建议：**目录 SLA 应当高于任何单引擎 SLA**——它挂了全平台挂，引擎挂了只是一类负载降级。

**目录选型的两条反直觉经验**（与 08.2 事故四件套互证）：
- "托管目录更省心"只对**读多写少**成立；高频提交管道的元数据竞争（同名表并发 commit）
  在托管服务里同样存在且更难观测（机制层见姊妹目录的 OCC 章）。
- "多目录冗余更可用"是错觉：冗余的第二个目录不是备份，是**第二个真相源**；
  真正的高可用是单目录服务自身的多副本 + 指针级回滚能力。

## 核心概念速览（中英对照）

- **技术目录** — technical catalog/metastore：持有"表→当前快照指针"的权威服务，湖仓单点。
- **业务目录** — data catalog (discovery)：人用的字典：语义、责任、质量、可发现性。
- **Iceberg REST Catalog** — 目录的 HTTP 接口规范，2024–2026 事实收敛点。
- **凭证 vending** — credential vending：目录代发临时云凭证，取代桶级宽策略。
- **Apache Polaris** — Snowflake 贡献的开源 Iceberg REST 目录服务端。
- **Unity Catalog (OSS)** — Databricks 开源的目录+治理平台（Apache 2.0）。
- **脑裂** — split-brain metadata：同一表在多处各持指针的双写分叉事故。
- **命名空间** — namespace：目录内的逻辑隔离单元，多租户爆炸半径的第一道闸。
- **同步器** — catalog sync：Hive/Glue 双写时代在目录间镜像表元数据的组件。
- **目录即性能** — catalog-as-performance：指针跳数与 LIST 替代率决定扫描规划成本。
- **过渡态** — transitional metastore：HMS+同步器类方案，必须配退出计划。
