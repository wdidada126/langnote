## 一句话主旨

**索引是 MySQL 性能杠杆里最长的那根**：硬件杠杆最小、优化器杠杆居中、索引杠杆最大；
没有索引，一切性能都退化成"拼硬件"——作者称之为**红鲱鱼**（red herring，看起来是解药其实是岔路）。

## 2.1 性能的红鲱鱼（✅ 目录，p.38）

作者的三段杠杆论（✅ Key Points）：MySQL 靠 **硬件 + 优化（techniques/algorithms/data structures）+ 索引** 三者撬动数据，
比喻是一根**支点为 MySQL 的杠杆**：

- 硬件：显然有用，但**杠杆最短**——数据一大，硬件的收益立刻被规模吃掉；
- 优化：把硬件的功率"聚焦"，作者的原话比喻是**灯泡 vs 激光**，所以杠杆比硬件长；
- 索引：**最长且最优的杠杆**，任何非平凡数据量都离不开它。

配套的两条断言（✅ Key Points/Pitfalls）：**"不要靠加硬件来提升性能——那是最后手段"**；
**"合理配置下，调 MySQL 参数对提升性能并非必要"**。作者举的真人真事：一个团队在云上**靠买更快的机器**改善性能，
直到成本失控才来问"还有别的办法吗"（✅ 作者站 Context 段）。另一侧的正例：一张表因归档 bug 从预估的
一百万行涨到**十亿行**，多年无人察觉响应时间变差——因为索引做得好。

## 2.2 MySQL 索引：通过图示介绍（✅ 目录，p.40）

本章篇幅最大的一节（p.40–74），从图讲起。可带走的机械事实（⚠️ 重构自 Key Points）：

| 论断（✅ 条目） | 工程含义 |
| --- | --- |
| 一张 InnoDB 表就是**按主键组织的 B-tree 索引** | 二级索引的"叶子"存的是主键值 → 回表是结构性的，不是可省的 |
| 访问表只有三条路：**索引查找 / 索引扫描 / 全表扫描**，索引查找最好 | 判断计划好坏只需问"走的是哪条路" |
| 要用索引，查询必须用**最左前缀**（leftmost prefix requirement） | 复合索引列序是设计决策，不是随手排列 |
| 索引用来：匹配 WHERE、给 GROUP BY 分组、给 ORDER BY 排序、**避免读行（覆盖索引）**、连接表 | 这五件事就是"加索引能买到什么"的完整清单 |

机制底图不在本册重复：页结构见 [../mysql/05-InnoDB数据页结构.md](../mysql/05-InnoDB数据页结构.md)，
B+ 树的分裂/游标见 [../mysql/06-B树索引.md](../mysql/06-B树索引.md)、[../mysql/07-B树索引的使用.md](../mysql/07-B树索引的使用.md)，
更基础的 B-tree 实现视角见 [../Database_Internals/02-B树基础.md](../Database_Internals/02-B树基础.md)。

## 2.3 编制索引：如何像 MySQL 一样思考（✅ 目录，p.75）

✅ Key Point："**EXPLAIN 打印查询执行计划，详述 MySQL 将如何执行该查询**"，以及"**编制索引要求像 MySQL 一样思考，
即理解执行计划**"。这一节是"读计划"的训练：`type`/`key`/`rows`/`Extra` 的语义细节交给
[../mysql/15-EXPLAIN详解.md](../mysql/15-EXPLAIN详解.md)，本册只留决策规则：

1. 先看**是否用索引**（`key` 为空 / `Extra: Using index condition` 缺失 → 回到 2.2 的三条路判断）；
2. 再看**用了索引的哪一段**（最左前缀是否被 WHERE 打断）；
3. 最后看**读完之后还做了什么**：临时表、文件排序、回表次数。

选择性（cardinality）决定索引是否值得用：低选择性列上建索引反而可能不如扫表
（Pitfall：**Very low cardinality**）。

## 2.4 索引降级的常见原因（✅ 目录，p.79）

✅ Key Point："**好的索引会因多种原因失去效力**"。本册按作者 Pitfalls 归为五类：

- 缺最左前缀（查询条件从中间列开始、或首列用了范围条件把后续列"截断"）；
- **索引"所有列"**（把每个列都单独建一遍索引）与**索引过多**（写放大、优化器选择变难）；
- **重复索引**：完全重复 + 前缀冗余（`(a,b)` 已存在时的 `(a)`）——本章练习正题；
- 极低基数列；
- 顺序错乱：先追高级优化、后补基础（Pitfall：**Focusing on advanced optimizations before mastering the basics**）。

还有一条更根本的（✅ Key Point）：**"索引不能提供无限杠杆"**——索引数量与收益最终会背离。
8.0 之后可以用**不可见索引**做安全实验（先 `ALTER TABLE … ALTER INDEX … INVISIBLE` 观察，再删）。

## 2.5 表连接算法（✅ 目录，p.82）

✅ Key Point："**MySQL 用三种算法连接表：NLJ（嵌套循环连接）、BNL（块嵌套循环连接）、hash join**"。
本册的决策口径：能让索引把内层循环变成"按 key 查找"的就做，退化成 BNL/hash 的就是**索引没做好**的信号；
8.0.18+ 引入 hash join 后，EXPLAIN 里的 `Join buffer` / BNL 语义有变
（⚠️ 细节见手册，机制底图在 [../mysql/15-连接查询.md](../mysql/15-连接查询.md)）。
更老的规则式优化器语境可对读 [../Understanding_MySQL_Internals/09-解析器与优化器.md](../Understanding_MySQL_Internals/09-解析器与优化器.md)。

## 🔧 本机机制类比（**这不是 MySQL**）

200,000 行、20.9 MB 的 sqlite3 库（脚本 `exp.py` / `followup.py`，结果 `results.json`/`results2.json`），
把本章五个论断各测一次：

| 场景 | 无索引 | 有索引 | 倍数 | 计划文本 |
| --- | --- | --- | --- | --- |
| `a=? AND b=?` | 13.71 ms | 0.18 ms | **76×** | `SCAN t` → `USING INDEX idx_ab` |
| 覆盖查询 vs 回表取宽列 | 1.52 ms（回表） | **0.12 ms**（覆盖） | 12.7× | — |
| `ORDER BY b`（b 上有索引） | 12.34 ms | **0.06 ms** | **205×** | `SCAN t \| USE TEMP B-TREE FOR ORDER BY` → `SCAN t USING INDEX idx_b` |
| `a=7`（命中 200/200,000 行） | 9.31 ms `SCAN t` | **0.12 ms** `SEARCH t USING INDEX idx_a2 (a=?)` | 77× | 选择性足够高才值得走索引 |
| 深翻页 `LIMIT 100000,20` | 3.0 ms | **1.04 ms**（延迟关联/deferred join） | 2.9× | — |

其他三条**没有好数字**的对照同样重要：

- **建索引不是免费的**：两次 `CREATE INDEX` 各花 **99.6 ms / 115.4 ms**（200k 行）——查询省下的时间要在写入与 DDL 侧还回去。
- **`LIKE 'pre%'` vs `LIKE '%mid%'`**：25.56 ms vs 26.77 ms，**两者都是全表扫描**（该列无索引）。
  前缀匹配能走索引这件事，只在"有索引"的前提下成立——这正是 2.4 的"降级原因"。
- **重复索引检测**（读 `PRAGMA index_list/index_info`）在只有 3 个索引的样例上准确报出
  1 组完全重复（`idx_ab` 与 `idx_ab_dup`，列序同为 `(a,b)`）+ 2 条前缀冗余（`idx_a` 被 `idx_ab`、`idx_ab_dup` 覆盖）。
- 成本模型的输入侧：`sqlite_stat1` 里 `t idx_a2 200000 200`（每值 200 行）、`t idx_pad 200000 200000`（唯一）、
  `t idx_b 200000 2`——统计信息就是"每键重复度"，与 MySQL 的索引统计/直方图同构。

## 核心概念速览（中英对照）

- **红鲱鱼** — red herring：诱人的岔路（买硬件、调参数），会转移对索引的注意力。
- **杠杆** — leverage：硬件/优化/索引三者撬动性能的能力，索引最长。
- **聚簇索引组织** — clustered (primary-key-organized) B-tree：InnoDB 表本身就是按主键组织的 B-tree。
- **最左前缀要求** — leftmost prefix requirement：查询必须用到复合索引的起始连续列段。
- **索引查找/索引扫描/全表扫描** — index lookup / index scan / full table scan：访问表的三种方式，lookup 最优。
- **覆盖索引** — covering index：索引本身含全部所需列，因而"避免读行"。
- **回表** — secondary index lookup（to the clustered index）：二级索引命中后再按主键取整行。
- **索引合并** — index merge：多索引拼合的计划形态，常是"没有合适单索引"的信号（⚠️ 手册口径）。
- **基数/选择性** — cardinality / selectivity：每键重复度，决定索引是否值得用。
- **重复索引** — duplicate index：完全重复或前缀冗余的索引，只留成本不留收益。
- **不可见索引** — invisible index：对优化器隐藏但保留结构，用于安全验证再删除。
- **NLJ / BNL / hash join** — 三种连接算法：8.0 起 hash join 取代部分 BNL 场景。
- **文件排序/临时表** — filesort / temporary table：`Using filesort`/`Using temporary` 是索引没帮上忙的痕迹。
- **在线索引变更** — online DDL / OSC：大表加索引须走在线方案（详见第 9 章）。
