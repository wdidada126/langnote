## 一句话主旨

**负载优化得好时，事务根本不是性能问题**；一旦出问题，几乎都是那四种"事务病灶"——
而它们全都能被 `performance_schema` 的锁与事务视图抓出来；
另有一条独立预警：**历史列表长度（HLL）> 100,000 必须告警**（作者原话："**厄运的先兆**"）。

## 8.1 行锁（✅ 目录，p.239）

先给前提（✅ Context）：MySQL 有非事务引擎，但 **InnoDB 是默认与推定标准**，
所以** practically 每条查询都在事务里跑，哪怕只是一条 `SELECT`**。

✅ Key Points 给的**四种基本 InnoDB 数据锁**（⚠️ 重构为表；机制细节在彼书，本册取判据）：

| 锁 | ✅ 作者定义 | 什么时候遇到 |
| --- | --- | --- |
| **记录锁 record lock** | 锁单个索引记录 | 最朴素的情形 |
| **next-key 锁** | 索引记录 **+ 它之前的间隙** | RR 下的默认加锁单位 |
| **间隙锁 gap lock** | 锁两条记录之间的**范围（间隙）** | RR 用来阻止幻读/阻止插入 |
| **插入意向锁 insert intention** | 允许向间隙 INSERT；作者原话"**更像等待条件而不是锁**" | 并发插入互相等待时 |

两条隔离级别判据（✅ Key Points）：**默认 RR 用 gap locking 来隔离被访问的行范围**；
**RC 关闭 gap locking**。→ 迁移/一致性场景里"从 RR 改 RC"往往直接消掉一批锁等待，
但也把幻读责任交回应用（⚠️ 本册补注）。
Pitfall 两条：不懂 InnoDB 行锁的基本功就上；**用 `FOR UPDATE` 却不知道自己要什么锁**。
还有一条更冷门的：**锁到 supremum 伪记录**（页尾哨兵，会让"不该等的插入"开始等）。

## 8.2 MVCC 和回滚日志（✅ 目录，p.253）

✅ Key Points 三句成链：**RR 事务用一致性快照让 `SELECT` 始终返回同一批行（哪怕别人改了它们）** →
**快照要求 InnoDB 把行改动存进 undo 日志以便重建旧版本** →
**事务结束（COMMIT/ROLLBACK）时数据锁与 undo 才一起释放**。
"读不加锁、写靠版本"的代价就藏在第二句里：**旧版本必须有人留着**，于是有了 8.3。
底图见 [../mysql/21-事务隔离级别与MVCC.md](../mysql/21-事务隔离级别与MVCC.md)、[../mysql/20-undo日志.md](../mysql/20-undo日志.md)。

## 8.3 历史列表长度（✅ 目录，p.257）

本章最可执行的一条（✅ Key Points）：

> **HLL 度量"尚未被 purge/flush 的旧行版本数量"**；
> **"HLL 是厄运的先兆（harbinger of doom）：始终监控它，并对 HLL > 100,000 告警。"**

⚠️ 重构其因果：长事务/长读视图会把 purge 的推进点钉住 → HLL 涨 →
undo 膨胀、回滚段变深、**一致性快照要翻更远的历史** → 读放大 → 更慢的查询与更大的复制量。
也就是说 **HLL 同时伤害第 1、3、7 章关切的东西**，这是本册认为它被单独列成一节的原因。
练习 8.7（"对历史列表长度发出警报"）就是把这条阈值固化进监控。

## 8.4 常见问题（✅ 目录，p.259）

✅ Key Point 给出**四类事务病灶**（本章的"体检清单"，⚠️ 每条补一句识别方法）：

1. **大事务（large）**：一次改太多行 → 看单事务影响行数、undo 量；
2. **长事务（long-running）**：从 `BEGIN` 到 `COMMIT` 响应时间慢 → 看事务存活时长；
3. **停滞事务（stalled）**：语句之间在做无关的额外等待（把应用工作搬进事务里，✅ Pitfall）；
4. **被遗弃事务（abandoned）**：客户端连接在事务活跃时消失 → 看连接与事务的对应关系（✅ Pitfall 点名）。

第 2、3 类的共同点是"**把数据库连接当变量用**"：事务开着的时候去做 HTTP 调用、算东西、等用户。
本册把这条与 `Database_Tuning` 的"事务斩切"直接对读：[../Database_Tuning/12-事务斩切.md](../Database_Tuning/12-事务斩切.md)。

## 🔧 本机机制类比（**这不是 MySQL、也不是 InnoDB**）

**（1）长读事务会钉住"日志回收点"**——这是 HLL 的机制同构物（sqlite3 WAL）：
开一个只读事务不提交，另一连接持续写 1,500 次，观察 `-wal` 文件：

| 观测 | 结果 | 对应 MySQL 概念 |
| --- | --- | --- |
| 读事务开着时 `-wal` 大小 | **4,931,672 B（≈4.9 MB）**（run1：8.3 MB） | undo/历史版本被迫保留（HLL 涨） |
| `PRAGMA wal_checkpoint(TRUNCATE)`（有 reader） | 返回 **`(1, 1197, 2)` → busy，未回收** | purge 推进点被长读事务钉住 |
| reader 退出后再 checkpoint | 返回 **`(0, 0, 0)`**，`-wal` 归 **0 字节**（耗时 31.6 ms） | 没有长视图时历史可被彻底回收 |

**（2）写写互斥与"只读事务不该挡写"**：两个写者并发时第二个直接
`sqlite3.OperationalError: database is locked`（本机 `exp.py`/`followup.py` 输出），
而**延迟打开的只读事务允许另一连接写入（True）**——
这正是"MySQL 里普通 `SELECT` 不加锁、但 RR 快照靠版本、写写会真等"的粗粒度类比。
**（3）提交路径本身可以是最大成本**：2,000 次单行提交，
`journal_mode=delete + synchronous=FULL` **6,704 ms（3.352 ms/次）**、
`synchronous=OFF` 4,777 ms（2.389 ms/次）、**WAL + `synchronous=NORMAL` 48 ms（0.024 ms/次）**，
而**同样 2,000 行放进一个事务只要 8 ms** → **耗时几乎全在 fsync/提交路径上**。
这条与第 1 章摘要页作者文章标题 "*When COMMIT Is the Slowest Query*" 遥指同一件事（✅ 作者站列出的文章名）。
**（4）原子更新 vs 读-改-写**：两个会话都读到 `v=0` 再各自写回 → 最终 **1**（应为 2，**丢失更新**）；
改成 `SET v = v + 1` 单语句 → 最终 **2**。⚠️ 数字是 sqlite3 的，只用于说明"应用层读改写=丢更新"的机制。

## 核心概念速览（中英对照）

- **数据锁 / 行锁** — data lock / row lock：InnoDB 加在索引记录上的锁，事务并发的基本单位。
- **记录锁** — record lock：锁单个索引记录。
- **next-key 锁** — next-key lock：索引记录 + 其前间隙，RR 下的默认加锁粒度。
- **间隙锁** — gap lock：锁两条记录之间的范围，用于阻止插入造成幻读。
- **插入意向锁** — insert intention lock：向间隙插入前的协调机制，作者判为"更像等待条件"。
- **supremum 伪记录** — supremum pseudo-record：页尾哨兵，被锁住会放大等待。
- **REPEATABLE READ / READ COMMITTED** — 隔离级别：前者用 gap lock，后者关闭 gap lock。
- **一致性快照** — consistent snapshot / consistent read：同事务内 `SELECT` 看到同一批行。
- **回滚日志 / undo** — undo log：保存旧版本以重建快照，事务结束时释放。
- **历史列表长度（HLL）** — history list length：未 purge 的旧版本量；作者阈值 **100,000 告警**。
- **清理** — purge：回收不再被任何快照需要的旧版本。
- **大 / 长 / 停滞 / 被遗弃事务** — large / long-running / stalled / abandoned transaction：本章四类病灶。
- **锁等待超时** — `innodb_lock_wait_timeout`：等待者以错误结束（第 6 章"等待→错误"链条的落点）。
- **`data_locks` / `data_lock_waits`** — 8.0 的数据锁视图：事务报告的取材表（⚠️ 手册口径）。

## 最新演进与工业实践

**2024–2026 现状**：

1. **8.0 时代的数据锁视图仍是唯一正道**：`performance_schema.data_locks` / `data_lock_waits`
   在 8.4/9.x 仍是首选（⚠️ <https://dev.mysql.com/doc/refman/8.4/en/performance-schema-data-lock-waits-table.html>），
   旧的 `information_schema.INNODB_LOCKS` 路线已属历史遗留（作者在本章末列有 "MySQL Data Locks: Mapping 8.0 to 5.7" 专文 ✅ 作者站）。
2. **HLL 阈值判据没有被更新推翻**：作者给的 100,000 至今仍是社区常引的经验值；
   现代实践把它做成**双级告警**（观察值/危险值）并与 `information_schema.INNODB_METRICS` 类计数联动
   （⚠️ 具体指标名以手册为准；本目录不声称已在本机验证）。
3. **长事务治理工具化**：Percona Toolkit 的 `pt-kill` 与 `pt-stalk` 是"抓现场 + 杀长事务"的通行做法
   → <https://github.com/percona/percona-toolkit>（✅ 200）；2024 年后的新趋势是把"事务存活时长"做成**发布前的 SLO 门禁**。
4. **提交路径成本可测**：若要给真实 MySQL 复现 🔧（3），用官方基准工具
   <https://dev.mysql.com/doc/refman/8.4/en/mysqlslap.html> 或 <https://github.com/akopytov/sysbench>（✅ 200），
   并把 `innodb_flush_log_at_trx_commit` 与 `sync_binlog` 作为主变量（⚠️ 手册口径）。
5. **理论谱系**：OLTP 事务尺寸/提交频率对吞吐的影响有系统实证
   —— Dam et al., *OLTP through the looking glass*, SIGMOD 2018, DOI <https://doi.org/10.1145/3226595.3226635>（✅ Crossref 校验）。
