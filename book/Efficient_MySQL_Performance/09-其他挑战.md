## 一句话主旨

作者自述本章是"**一份短但重要的清单**"：这些挑战大多**不直接是性能问题**，
但"**前两个就能毁掉一个数据库**"；而且它们**不是小概率事件**——"它们就是常见挑战，请认真对待并预期会遇到"。

## 9.1 脑裂是最大的风险（✅ 目录，p.273）

✅ Key Point："**脑裂 = 同一复制拓扑里有两个或更多实例被写入**"，
后果（✅ Key Point）："**脑裂伤害数据完整性——数据从此不可信**"。
本册补一条判定顺序（⚠️ 重构）：脑裂不是"性能下降"，是**"你不知道哪份是真的"**；
所以它的处置方式不是调优而是**恢复决策**（选一份、重做其余），代价按丢失时间计算。
HA 自动化（failover、DNS/代理切换、双主配置）是它的主要成因面。

## 9.2 数据漂移真实存在但不可见（✅ 目录，p.274）

✅ 两条 Key Point 连读："**数据漂移 = 副本与源不同步**"；"**漂移真实存在，但漂移的来源几乎不可能定位**"；
"**可以用 pt-table-checksum 检测**"。
机制解释（⚠️ 本册补注，作者在本章只给现象）：非确定性语句（`UUID()`、`NOW()` 配合 STATEMENT 格式）、
绕过复制的手工改数据、被跳过的错误、异构拓扑/字符集差异，都会造成**没人看得见**的差异——
直到某次故障切换把从库提为主库。**"不可见"才是它的危险之处**。

## 9.3 不要信任 ORM（✅ 目录，p.275）

✅ Key Point："**ORM 能生成非常糟糕的查询与整体性能**"。
与本册第 4 章同源：**坏的访问模式（N+1、过度抓取、隐式排序）多半是 ORM 替你做决定的结果**。
判据（⚠️ 重构）：性能审查要看**ORM 实际发出的 SQL**，不是看代码行数——
把慢查询日志/digest 与请求链路对上，才能知道某个页面发了 200 条还是 2 条查询。

## 9.4 模式总会改变（✅ 目录，p.276）

✅ Key Point："**Schema 总会变，所以在线改表（OSC）工具是必备品**"，
并点名 **三种流行 OSC 工具：`pt-online-schema-change`、`gh-ost`、Spirit**。
做法（⚠️ 重构为清单）：影子表 + 触发/binlog 追增量 + 原子改名 + 限流；
与第 3 章"归档批次不能太大"、第 8 章"元数据锁会排队"共同构成"改表三重风险"。

## 9.5 MySQL 扩展了标准 SQL（✅ 目录，p.276）

✅ Key Point："**MySQL 有非标准的 SQL 语句、选项与子句**"。
实际影响（⚠️ 重构）：迁移到其他数据库时最先崩的是这些方言位
（`INSERT ... ON DUPLICATE KEY UPDATE`、`REPLACE`、`GROUP BY` 与裸列、`LIMIT` 语法、
隐式类型转换、`sql_mode` 决定的严格程度）。
`sql_mode` 是本书语境里最实用的"合规旋钮"（⚠️ 手册口径，见下）。

## 9.6 吵闹的邻居（✅ 目录，p.277）

⚠️ 依小节名重构：共享资源（缓冲池、I/O 带宽、CPU、云上的存储吞吐上限）被同宿主的其他工作负载吃掉时，
你的查询响应时间会变**但你的负载没变**——这正好命中第 6 章的 Pitfall"把指标当 MySQL 的镜子"。
云上更严重（→ [10-云中的MySQL.md](10-云中的MySQL.md) 的网络与存储时延一节）。

## 9.7 应用程序不会优雅地失败（✅ 目录，p.277）

✅ Key Point："**应用默认不会优雅失败；优雅失败需要下力气**"。
落到 MySQL 侧的具体动作（⚠️ 重构）：连接失败要重试+退避（别把 MySQL 打穿）、
要有超时（`max_execution_time`、连接超时）、要有熔断/降级路径、
**并且失败时别把事务留在开着的状态**（第 8 章的"被遗弃事务"就是这条的产物）。

## 9.8 高性能 MySQL 很难（✅ 目录，p.278）

作者的收尾是一句坦白（✅ Key Point）："**High performance MySQL is difficult.**"
本册的读法：这一章把前面八章的**成功条件**列全了——
好索引、小工作集、好访问模式、可观测、低延迟、短事务、可靠复制、纪律化的 schema 变更，
**任一条缺失都会让性能退化**；"难"不在单点技术，而在**同时满足**。

## 9.9–9.11 练习（✅ 目录，p.279–281）

⚠️ 题面未获取，按三个小节位置与本章条目重构方向：
① 用校验和方式**验证你的主从是否已经漂移**；② 审查 ORM 实际生成的 SQL 并列出可疑访问模式；
③ 给一张大表设计一次**不锁表、可暂停、可回滚**的变更方案。

## 核心概念速览（中英对照）

- **脑裂** — split-brain：同一拓扑内多个实例同时可写，数据从此不可信。
- **数据漂移** — data drift：副本与源内容不一致，且成因几乎不可定位。
- **表校验和** — table checksum（`pt-table-checksum`）：分块比对主从数据是否一致的手段。
- **ORM** — object-relational mapper：开发效率的来源，也是坏查询与坏访问模式的来源。
- **在线模式变更（OSC）** — online schema change：影子表 + 追增量 + 原子改名的不锁表改表法。
- **元数据锁** — metadata lock（MDL）：DDL 与长事务互相排队的主要机制（⚠️ 手册口径）。
- **非标准 SQL** — non-standard SQL：MySQL 特有的语句、选项与子句，迁移时首先出问题。
- **`sql_mode`** — SQL 模式：控制 MySQL 对标准与严格性的取舍（⚠️ 手册口径）。
- **吵闹的邻居** — noisy neighbor：共享资源被别的负载吃掉，你的响应时间无端变差。
- **优雅失败** — graceful failure：超时、退避重试、降级，且不留开放事务。
- **被遗弃事务** — abandoned transaction：连接消失但事务还开着（第 8 章四类病灶之一）。
- **降级路径** — degradation path：数据不可用时的次优可读结果。

## 最新演进与工业实践

**2024–2026 现状**：

1. **OSC 的格局收敛为两家**：`pt-online-schema-change`（✅ 文档 200）与 **gh-ost**
   （<https://github.com/github/gh-ost>，✅ 200）；书里第三个 **Spirit** 在本环境取不到仓库（404），
   实践上已被前者取代——这是一次"书中的三选一变成二选一"的小漂移，**本目录按实测登记**。
2. **MySQL 原生在线 DDL 覆盖面继续扩大**：8.x 的 `ALGORITHM=INSTANT` 让"加列"类变更不再需要外部工具，
   但**改列类型/加索引仍要走 OSC 或长 DDL**（⚠️ <https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl.html>）。
3. **漂移检测成为例行任务**：2024 年后的通行做法是把 `pt-table-checksum` 排进**低峰周期任务**并留存差异报表，
