## 一句话主旨

**MySQL 除了执行应用的查询之外什么都不做**——所以性能的上限由应用怎么写决定；
QPS 越少越好（它是**负债**不是资产），换硬件永远是**最后**一步。

## 4.1 MySQL 什么都不做（✅ 目录，p.115）

作者在这一节把因果掰过来（✅ Key Points 原文口径）："MySQL does nothing except execute application queries."
配套的两个反例式提问（✅ 作者站 Context）至今很有画面感：

- "MySQL 现在 5,000 QPS，**为什么不到 9,000 QPS？**"
- "MySQL 现在用 50% CPU，**为什么不用到 90%？**"

作者的判定：提这种问题的人**找不到答案，因为他盯着结果（MySQL）而不是原因（应用）**；
QPS 与 CPU 使用率这类指标"关于 MySQL 说得极少——几乎什么都没说的"，它们只反映**应用如何使用 MySQL**。
结论句（✅ Context）：**"MySQL 性能受限于应用，而不是相反"**——
"有无数大型高性能应用跑在单个 MySQL 实例上"，所以**"MySQL 对应用来说足够快"从来不是问题，
真正的问题是"应用是否高效地使用 MySQL"**。

## 4.2 性能在极限位置变得不稳定（✅ 目录，p.116）

⚠️ 依小节名 + ✅ Key Point "**没有数据库能用满硬件的 100% 容量**" 重构：
负载逼近能力上限时，响应时间不是线性变差而是**发散**——排队效应让 P99 先炸、平均后炸。
工程后果（⚠️ 重构）：留余量不是为了"未来增长"，而是为了**稳定性本身**；
把机器跑到 90% CPU 当作"物尽其用"，在数据库上是错的目标。
这一节也是第 6 章"利用率推高、等待出现、等待超时变错误"那条指标因果链的前置直觉。

## 4.3 丰田和法拉利（✅ 目录，p.120）

⚠️ 依小节名重构（题面未获取）：作者的比喻落在**"能跑多快"与"该跑多快"是两件事**——
法拉利在市区没用，丰田能天天开；数据库同理，极限性能指标（最高 QPS、最低单次延迟）
不等于**可 Sustained 的、可运维的**性能。这条与 4.2 合成一句：**极限值不可持续，稳定才是可持续的性能**。
（同主题的可对照写法见 [../Pro_SQL_Server_Internals/11-系统设计考量.md](../Pro_SQL_Server_Internals/11-系统设计考量.md)。）

## 4.4 数据访问模式（✅ 目录，p.121）

✅ Key Points："**数据访问模式描述应用如何使用数据库**"，
并且（✅ Pitfalls 反向）"**有些访问模式天生不适合事务型 OLTP RDBMS**"。
作者用第 3 章的卡车比喻收尾（✅ Context）：卡车≈MySQL，
"一次只搬一块鹅卵石上山"对卡车和你都很轻松，但**效率极差**——
"卡车的价值只等于用它的人"，MySQL 的价值只等于用它的应用。

本册把常见错位模式列成表（⚠️ 重构，非原书清单）：

| 模式 | 为什么伤 OLTP | 修法 |
| --- | --- | --- |
| N+1 查询（循环里逐条查） | 把一次集合操作拆成 N 次往返 | 改批量/`IN`/`JOIN`（见下方 🔧） |
| 用 `OFFSET` 深翻页 | 前 OFFSET 行照读照丢 | 键集分页（keyset）/延迟关联 |
| 计数器热点（单行累加） | 单行变成串行点 | 分片计数 + 汇总（第 6 章 🔧） |
| 把队列/缓存/搜索塞进 MySQL | 访问模式与 B+ 树事务模型正交 | 换专用系统（第 5 章"替代选项"） |
| 报表型全表扫描打主库 | 长事务 + 大批页读 | 旁路到副本/列存（对照 [../DuckDB_in_Action/00-总览与阅读地图.md](../DuckDB_in_Action/00-总览与阅读地图.md)） |

## 4.5 应用程序修改（✅ 目录，p.129）

✅ Key Point："**要改变数据访问模式，你必须改应用**"。这一节是本章的落地段，
也是全书"间接优化"最贵的一枝：它要动代码、动契约、动发布节奏。
判据（⚠️ 重构）：**只有当第 2 章（索引）和第 3 章（数据）都做完仍不达标，才付这个成本**——
这正好对应第 1 章"先直接、后间接"的次序。

## 4.6 更好、更快的硬件（✅ 目录，p.137）

✅ Key Point 一句话：**"Scale up hardware to improve performance as the last solution."**
与第 2 章"红鲱鱼"呼应（彼处反对"先想到硬件"，此处反对"最后之外就用硬件"）。
本册补一条取证事实：作者在第 2 章摘要页讲的云上团队故事，**结局就是靠买机器把性能问题买成了账单问题**。

## 4.7 小结（✅ 目录，p.138）

三句带走：**QPS 是负债**；**指标是应用行为的回声**；**改访问模式=改应用，是最后但常常最有效的一招**。

## 🔧 本机机制类比（**这不是 MySQL**）

**（1）N+1 vs 批量**：取 1,000 个父键，两种写法。脚本 `exp.py`/`followup.py`（`results.json`/`results2.json`）：

| 写法 | 往返（查询数） | 三轮耗时 | 中位 |
| --- | --- | --- | --- |
| N+1（循环内逐条查） | **1,000** | 37.9 / 34.8 / 33.4 ms | **34.8 ms** |
| 批量（`IN(...)` 两段聚合） | **2** | 11.1 / 11.3 / 11.5 ms | **11.3 ms** |

→ **3.1× 的差距，且结果集等价**（两份聚合值差的绝对值 4.77e-6、相对值 1.75e-15，浮点噪声级）。
真实 MySQL 上这个比值只会更大，因为每次往返还带一次网络与协议开销。

**（2）集合 vs 逐点**：对 20,000 个键做点查共 **229.5 ms**，改成**一次范围扫描**取回同样数据 **3.7 ms** → **61.4×**。
这就是"卡车一趟 vs 一次一块石头"的量级差。

**（3）深翻页**：`LIMIT 100000,20` 3.0 ms vs 延迟关联改写 1.04 ms（2.9×，数据量小所以绝对值小；比值才是重点）。

## 核心概念速览（中英对照）

- **访问模式** — access pattern：应用如何读写数据库的形状（读写比、行数、往返、热点）。
- **QPS 即负债** — QPS as a liability：每次查询都是成本，越少越好，不是荣耀。
- **N+1 查询** — N+1 queries：循环里逐条发查询，把集合操作退化为往返风暴。
- **批量操作** — batching / set operation：用一条集合化 SQL 换掉 N 次点查。
- **往返开销** — round-trip cost：客户端与服务器之间每次交互的固定成本。
- **键集分页** — keyset pagination / seek method：用上一页末端的键代替大 `OFFSET`。
- **延迟关联** — deferred join：先在索引里定位主键，再回表取少量行。
- **热点行** — hot row / contention point：单行成为串行化瓶颈的访问模式。
- **利用率上限** — no 100% utilization：数据库不可能把硬件容量用满，留余量是稳定性要求。
- **饱和处的不稳定** — instability at the limit：接近能力上限时尾部延迟发散。
- **垂直扩展** — scale up：加硬件；作者判定的**最后**手段。
- **间接查询优化** — indirect query optimization：改数据与改访问模式（本章所在的枝）。
- **应用才是上限** — the application is the ceiling：MySQL 性能受限于应用，而非相反。

## 最新演进与工业实践

**2024–2026 现状**：

1. **"少查、集合查"从口号变成架构约束**：连接池 + prepared statement + 批量写入仍是 MySQL 侧最稳的收益来源；
   新增的变化是**代理层**承担了原来要靠改代码才能做的事（如 Vitess 的查询合并/连接复用
   → <https://github.com/planetscale/vitess>，✅ 200）。
2. **ORM 的账终于有人公开算了**：本章"改应用"的现实路径是 ORM 治理，
   与第 9 章 "不要信任 ORM" 构成一对（见 [09-其他挑战.md](09-其他挑战.md)）；
   2024 年后常见的工程做法是 **N+1 检测进 CI**（框架自带的 eager-loading 告警 + 每请求查询数预算）。
3. **OLTP 极限处的排队行为有权威实测**：Dam et al., *OLTP through the looking glass, and what we found there*,
   SIGMOD 2018, DOI <https://doi.org/10.1145/3226595.3226635>（✅ Crossref 校验通过）——
   与本节 4.2 的判断方向一致：**接近饱和时先崩的是尾延迟**。
4. **尾部延迟的运维共识**：Dean & Barroso, *The Tail at Scale*, CACM 2013（⚠️ 未注册 DOI，按题名+出处+年份引用）。
5. **别把 MySQL 用成别的系统**：2024–2026 的常见替代是"队列交给 Kafka/Redis、搜索交给 OpenSearch、
   分析交给列存"，本册只在第 5 章"替代选项"里点到边界，不展开——这也是本书明确放弃的范围（✅ 作者站："no … deep internals required by DBAs and experts"）。
