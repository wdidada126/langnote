## 一句话主旨

**数据越少，性能越好（Less data yields better performance）**：索引解决"怎么找"，本章解决"要找的东西有多重"——
最少数据原则（Principle of Least Data）：**只存需要的数据，只访问需要的数据**。

## 3.1 三个秘密（✅ 目录，p.87）

⚠️ 原书"三个秘密"的题面未获取；作者站在第 3+4 章合并页的开场是一个**石头类比**，本册据它重构本节要点
（这是本章的因果底座，不是装饰）：

| 类比（✅ 作者站 Context） | MySQL 对应 |
| --- | --- |
| 一堆**卵石**：单个极轻，但**总重 2 吨** | 小行海量：单行便宜，总数据量决定成本 |
| 一堆**鹅卵石**：单个可搬，总重 1 吨 | 中等宽度与行数的现实表 |
| **一块巨石**：单个搬不动，总重 0.5 吨 | 一行很宽/很大的极端情形：一次性代价高 |
| "把哪堆搬上山"取决于**重量**而非"单个好不好拿" | **查询成本由总数据量决定**，不只由"好不好写"决定 |

作者在第 1 章给的"证明"在这里被回收：**`TRUNCATE TABLE` 是最强的性能优化——也是错的优化**（✅ 作者站明写这是玩笑，
但玩笑指向的因果"less data is more performance"是真）。这条因果"很少被推演到底"，本章就是把它推到底。

## 3.2 最少数据原则（✅ 目录，p.91）

✅ Key Points 给出四句话：

1. **Principle of Least Data：只存并只访问需要的数据**；
2. **确保查询访问尽可能少的行**；
3. **不要存超出需要的数据**——作者的原文式表述：数据对你有价值，对 MySQL 是**死重（dead weight）**；
4. 删除或归档数据很重要，而且**确实能提升性能**。

落到可执行的操作面（⚠️ 依 Pitfalls 反推，逐条对应）：

- **列类型与表示**（Pitfall：Not using efficient column types or data representations）：
  宽度决定页数、页数决定缓冲池命中率；等价的紧凑表示（整数编码状态、合适的定点/日期类型）是纯收益。
- **范式化**（Pitfall：Not normalizing — and rarely: normalizing too much）：
  去重减少存储与更新面；过度范式化则换来更多 JOIN——本册不做展开，机制见
  [../数据库系统概念6/08-关系数据库设计.md](../数据库系统概念6/08-关系数据库设计.md)。
- **只选用得着的列**（Pitfall：Selecting columns that the app doesn't use）：`SELECT *` 在宽表上同时杀死覆盖索引。
- **该 LIMIT 就 LIMIT**（Pitfall：Not limiting results when app only uses limited result）。
- **别在数据库里排大序**（Pitfall：Sorting too much — instead sort in app if possible）。

## 3.3 删除或归档数据（✅ 目录，p.108）

两条动作 + 一条警告（✅ Key Points/Pitfalls）：

- **删除**（`DELETE`）或**归档**（搬到冷存/历史表）都能直接缩小工作集；
- **警告（Pitfall）**：*Archiving rows too fast, in batches too large, or both*——
  归档本身是**写负载**：批次过大、节奏过快会把缓冲池、undo 与 purge 拖垮，等于用一次事故换一次瘦身；
- 机制解释（⚠️ 手册口径，本册不重复）：`DELETE` 只标记，旧版本进 undo，回收由 purge 负责，
  所以**"删了"与"变小了"之间有一段延迟**，见 [../mysql/20-undo日志.md](../mysql/20-undo日志.md) 与第 8 章的 HLL。

## 3.4 小结（✅ 目录，p.112）

本章的判据一句话：**当索引已就位、查询仍慢，就去减数据**；
而"减数据"的收益是**全方位的**（CPU、内存、存储、复制量、备份量、DDL 时长），不像索引只在读路径上有效。

## 🔧 本机机制类比（**这不是 MySQL**）

同一份 200,000 行数据，两种"重量"：胖表（多列宽 `TEXT` 填充）与瘦表（紧凑整数 + 短字符串）。
脚本 `exp.py` + `followup.py`（结果 `results.json`/`results2.json`），计时取**三轮最小值**：

| 观测 | 胖表 | 瘦表 | 差距 |
| --- | --- | --- | --- |
| 插入 200k 行 | 957 ms | 320 ms | 3.0× |
| **落库字节** | **30,440,000 B** | **2,200,000 B** | **13.8×** |
| 全表扫描（三轮最小） | 259.0 ms | 86.6 ms | 3.0× |
| `SELECT *`（3 轮最小） | 16.4 ms | 9.2 ms | 1.8× |
| 只取 2 列（同上表） | — | **0.6 ms**（run1，2 列 vs `SELECT *` 1.8 ms） | 3.0× |

第一轮的绝对值比第二轮小一个量级（run1 全扫 51.9 vs 3.9 ms），
**波动本身就是本章的论点之一**：宽行的成本高度依赖页/缓存状态，取最小值才看得清结构性差距。

"删了 ≠ 变小了"的实证：删掉 90% 的行后，**文件仍是 69.2 MB**，全扫 7.0 ms；
显式回收（`VACUUM`）后才降到 **10.6 MB**、全扫 5.2 ms。
→ MySQL 里对应的是 undo/purge 与表重建（`OPTIMIZE TABLE` / OSC），**不要指望 `DELETE` 立刻把空间还给操作系统**。

## 核心概念速览（中英对照）

- **最少数据原则** — Principle of Least Data：只存需要、只取需要的数据。
- **死重** — dead weight：数据对应用有价值、对 MySQL 只是拖慢它的体积。
- **工作集** — working set：查询实际反复触及的数据量，决定缓冲池命中率。
- **列类型经济性** — efficient column types / representation：用最小且正确的类型表达值域。
- **覆盖索引失效** — loss of covering index：多选一列就可能把覆盖退化成回表。
- **`SELECT *`** — 反模式：把宽度成本转嫁给每一次执行。
- **`LIMIT`** — 限制结果集：应用只用前 N 行时，别让它读全表。
- **范式化 / 过度范式化** — normalization / over-normalization：去重与 JOIN 成本之间的权衡。
- **归档** — archiving：把冷数据移出主表，缩小热路径。
- **purge / undo 回收** — purge：`DELETE` 之后真正把空间释放掉的后台动作（⚠️ 手册口径）。
- **表重建** — table rebuild（`OPTIMIZE TABLE` / OSC）：把碎片与旧版本彻底清掉的重动作。
- **写负载的另一面** — write amplification：宽表不仅慢于读，也慢于插入与维护。

## 最新演进与工业实践

**2024–2026 现状**：

1. **"减数据"在今天有一个正式名字：数据生命周期管理**。Percona Toolkit 的 `pt-archiver`
   → <https://docs.percona.com/percona-toolkit/pt-archiver.html>（✅ 200）仍是 MySQL 侧最常用的小批量归档器，
   其"限流 + 小批次"的设计正是本章 Pitfall（批量太大/太快）的工程解。
2. **热冷分层的默认答案在变**：2024 年后 MySQL 8.4 LTS 把"分区表 + 归档"之外多了两条常见路线——
   把报表型扫描交给列存/分析引擎（对照 [../DuckDB_in_Action/00-总览与阅读地图.md](../DuckDB_in_Action/00-总览与阅读地图.md)），
   或把宽表读负载旁路到副本；共同点是**别让 OLTP 主库扛宽行扫描**。
3. **理论底座仍是同一句话**：O'Neil, *Database Tuning* 的"访问路径成本 ∝ 要读的页数"在本册有直接对位
   → [../Database_Tuning/01-基本原则.md](../Database_Tuning/01-基本原则.md)、[../Database_Tuning/03-索引调优.md](../Database_Tuning/03-索引调优.md)。
4. **写路径的代价可量化**（本册 🔧 的 3.0× 插入差距并非 MySQL 数字）：若要给真实 MySQL 造数据，
   用 <https://github.com/akopytov/sysbench>（✅ 200）或 `mysqlslap`
   → <https://dev.mysql.com/doc/refman/8.4/en/mysqlslap.html>。
5. **未解决的部分**：本章没有讲"如何安全地删"（权限、审计、GDPR 式合规），
   2024–2026 的合规删除流程通常落在应用层/数仓层，而不是 MySQL 里——这是本册边界的诚实声明。
