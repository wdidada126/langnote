## 一句话主旨

**当直接与间接优化都尽力之后仍不达标，说明触及了"该应用负载下的单实例上限"——
MySQL 想规模化的通行路径只剩分片；但分片不是 MySQL 的功能，它是**你的应用的一项工程**（复杂且完全应用特定）。

## 5.1 为什么单个数据库不能伸缩（✅ 目录，p.140）

✅ Key Point 给了唯一的因：**"单个数据库不能伸缩，主要因为查询+数据+访问模式（即应用负载）
显著超过单台服务器的速度与容量"**。注意作者把"单实例上限"写成**相对**概念：
不存在绝对上限，只存在"这个负载下的上限"。

✅ Context 里那句被作者刻意重复的话：**"MySQL at scale requires sharding."**
他解释为什么要反复说：**工程师不愿意接受它**——因为"分片不是 MySQL 的内在功能或能力"，
所以它复杂、且完全应用特定，**没有通用解**。同时他也安抚：分片是**已被解决的问题**（几十年工程实践）。

## 5.2 小鹅卵石而不是巨石（✅ 目录，p.147）

✅ Key Point："**管理许多小数据库（分片）显著比管理一个巨型数据库容易——要卵石，不要巨石**"。
这是第 3 章石头类比的续用：巨石（十亿行单表）动不了、备份不完、DDL 做不起；
卵石（每片可控尺寸）每一件运维动作都回到"正常大小"。

## 5.3 分片简介（✅ 目录，p.148）

术语按作者定义（✅ Key Points）：

- **分片（shard）**：把**一个数据库分成许多数据库**，每个分片通常是一个独立 MySQL 实例、跑在独立硬件上；
  物理分离、逻辑上仍是同一个（很大的）数据库。
- **分片键（shard key）**：数据按它切分，**必须慎重选择**（✅ Key Point 明示）。
- **分片策略（sharding strategy）**：把"分片键的值"映射到"具体分片"的规则。
  ✅ Key Point："最常见的是 **hash（散列）/ range（范围）/ lookup（目录表）** 三种"。

三种策略的取舍（⚠️ 由条目重构，非原书表格）：

| 策略 | 优点 | 代价 |
| --- | --- | --- |
| hash | 分布均匀、无需查表 | 范围查询要**全片扇出**；再均衡困难 |
| range | 范围查询友好、可读 | 天生热点（最新区间最忙） |
| lookup（目录） | 映射自由、可迁移 | 目录本身是**全局单点依赖**，多一次查询 |

✅ Key Point 收尾："**分片会制造必须处理的新挑战**"；
Pitfalls 把它们点名：**热点/热分片**、**没考虑高可用（只有一个分片挂掉时应用还能工作吗）**、
**低估运维复杂度**（N 个分片 × 每个的部署/监控/备份/DDL/故障处置）。
另有一条贯穿全章的横向代价：**跨分片事务与跨分片 JOIN 不再是免费的**（⚠️ 本册补注，属常识边界）。

## 5.4 替代选项（✅ 目录，p.157）

✅ Pitfall："**没有考虑用另一种技术或范式来避开分片**"。作者本人的文章名就是他的态度
（✅ 该页 "Hack MySQL Articles" 列了 *I Don't Want to Shard (MySQL)*）。
可考虑的替代（⚠️ 重构）：读负载旁路到副本、把分析型查询挪去列存/数仓、
把非 OLTP 形状的数据（队列/搜索/缓存）交给专用系统、以及**换一层自带分片能力的中间件或分布式 SQL**。

## 5.5 小结 + 5.6 练习：四年拟合（✅ 目录，p.160）

✅ Pitfall 第一条就是判据："**没有提前规划：未来 1–4 年你会需要分片 MySQL 吗？**"
"四年拟合"这个练习名正落在"提前规划"上（⚠️ 题面未获取，按小节名+该 Pitfall 重构）：
用增长曲线（数据量、QPS、增速）外推 1–4 年，判断单实例是否会被击穿，以及**如果现在就要分片，
分片键选谁**——因为分片键一旦选错，后面的迁移成本远大于分片本身。

## 🔧 本机机制类比（**这不是 MySQL**）

**这不是 MySQL 分片**：用 8 个 sqlite3 文件模拟 8 个分片，同一个键空间，总量固定，
只问三个问题——"分片买到了什么、没买到什么、代价是什么"。脚本 `followup.py`（`results2.json`）。
**关键控制**：单库 240,000 行 vs 8 片 × 30,000 行（**同总量、同列定义、同索引**）。

| 观测 | 单库 | 8 分片 | 读法 |
| --- | --- | --- | --- |
| 页数（B+ 树规模） | **1,954 页** | 每片 **242–246 页** | ✅ "卵石 vs 巨石"：树高与工作集被切实变小、变均匀 |
| 落盘体积 | 8.00 MB | 8.04 MB | 分片**几乎不省空间**（每片有自己的索引开销） |
| 30k 次点查 | **572 ms** | **581 ms** | **单行延迟没买到任何收益**——路由后每片仍做同样的树查找 |
| 10 次 scatter-gather 聚合查询 | 153.3 ms（大表单做） | **123.1 ms**（串行扇出 8 片） | 扇出型读**略有收益（1.25×）**，且这里的收益来自"每片树更小" |

第一轮（不同规模配比：200k 总量、8×25k，`results.json`）给出同方向的另一组数：
单库 494 ms vs 分片 417 ms（点查合计），20 次 scatter 214.4 ms vs 单库全扫 300.2 ms。
**两轮对比合起来的结论**：分片的收益是**容量与可运维性**（每片树小、备份快、DDL 便宜、可独立扩容），
**不是单行点查延迟**；而它的代价是**扇出**（一次业务查询 = N 次查询，本轮里 fan-out 直接乘 8）。

## ⚠️ 边界澄清（**这是 MySQL 的分区，不是分片**）

MySQL 原生提供的是**分区表（partitioning）**：仍是一个实例、一份进程与连接池，
只是把一张表物理切成片以裁剪扫描与维护（`DROP PARTITION` 式归档）。它**不解决**本章 5.1 说的
"单实例硬件速度/容量被负载击穿"问题。→ <https://dev.mysql.com/doc/refman/8.4/en/partitioning.html>
（⚠️ 手册转述，本机无 MySQL 实例验证。）

## 核心概念速览（中英对照）

- **分片** — sharding：把一个数据库切成许多数据库，物理分离、逻辑统一。
- **水平扩展 / 垂直扩展** — scale out / scale up：加实例 vs 加硬件容量。
- **分片键** — shard key：决定数据落到哪一片的列（组合），最难撤销的决策。
- **散列分片 / 范围分片 / 目录分片** — hash / range / lookup (directory) sharding：三种主流映射策略。
- **扇出** — fan-out / scatter-gather：一次业务查询要发向多个分片再汇总。
- **热点分片** — hot shard：负载集中到个别分片，使分片收益归零。
- **再均衡** — rebalancing：分片间重新分布数据，运维成本的主要来源。
- **跨分片事务** — distributed transaction：分片后不再免费的能力（本册不展开）。
- **每片高可用** — HA per shard：每个分片自带主备，故障域随分片数放大。
- **分区表** — partitioning：单实例内的物理切分，**不等于**分片（⚠️ 手册口径）。
- **中间件/分布式 SQL** — Vitess、TiDB 等：把分片从"应用的责任"上移到一层专门系统。
- **相对上限** — relative limit：单实例上限是"该负载"的上限，不是一个绝对数字。

## 最新演进与工业实践

**2024–2026 现状**：

1. **"自己写分片"已经不是默认选项**：两条主流替代各自成熟——
   **Vitess**（MySQL 兼容的连接层+分片编排，源自 YouTube；<https://github.com/planetscale/vitess>，✅ 200）
   与 **TiDB**（分布式 SQL，MySQL 协议兼容；<https://github.com/pingcap/tidb>，✅ 200）。
   两者的**成本形态不同**（Vitess 仍是 MySQL 分片，TiDB 换存储引擎），但都把本书 5.3 的"应用特定复杂度"收进了一层系统。
2. **分片键选择的教训已成共识**：范围分片（时间自增键）造成写热点、散列分片让范围查询全扇出——
   2024 年后的通行做法是**复合/加盐键 + 桶数固定化**，让再均衡可控。
3. **理论出处**：NoSQL 侧的分片+复制权衡最早由 DeCandia 等,
   *Dynamo: Amazon's Highly Available Key-value Store*, SOSP 2007 定型,
   DOI <https://doi.org/10.1145/1294261.1294281>（✅ Crossref 校验通过）；
   "计算存储分离"作为分片的另一条出路见 *Amazon Aurora: Design Considerations*, SIGMOD 2017,
   DOI <https://doi.org/10.1145/3035918.3056101>（✅ 校验通过）——但注意本书第 10 章对 Aurora 的态度是"要自己基准测试，别信宣传"。
4. **仍然没有解决的**：分片后的 schema 演进与一致性发布（第 9 章 OSC 话题 × N 片）、
   跨片事务、以及"只有一个分片坏了应用该怎么办"——**这三条至今仍是 MySQL 分片项目失败的主因**，
   也正是作者把"提前 1–4 年规划"列为第一条 Pitfall 的原因。
