## 一句话主旨

**性能就是查询响应时间（Performance is query response time）**：它是用户唯一能感知的那个量，
所以它是全书的北极星；其余一切（服务器指标、硬件、参数）都只是它的**成因解释**，不是它的替身。

## 1.1 假性能的一个真故事（✅ 目录，p.6）

作者用一个"看着很健康其实很慢"的现场故事开场：仪表盘全绿、CPU 不高、告警一条没响，
但用户抱怨卡顿。症结在于团队只看**服务器指标**（QPS、CPU、连接数），从不看**查询指标**。
要点（⚠️ 重构自 Key Points）：

- 服务器指标是**输出**，查询指标是**输入侧的因**；只看输出会把"没报警"误当成"没问题"。
- "假性能"的典型配方：**用平均值汇总**（Pitfall：Using averages instead of the P95 or a higher percentile）+
  **不按时长排序**（Pitfall：Not sorting queries by total time to find the slowest）+
  **等出事才看慢查询**（Pitfall：Waiting until there's a problem to review slow queries）。

## 1.2 北极星（✅ 目录，p.6）

查询响应时间的定义很窄，也很硬（✅ 作者站原文口径）：**从 MySQL 收到查询开始，到把结果集发给客户端为止**的这段时间。
同义词：response time / query time / execution time；**query latency 被作者点名为"不准确的说法"**。

- 这段时间内部由 **stage（执行阶段）** 与 **wait（锁等待、I/O 等待等）** 构成，
  但作者明确断言：完整、细粒度的拆分"既不可能也没必要"——基础排查就能定位绝大多数问题。
- 为什么它是北极星：**它是用户唯一体验到的指标**。这一条决定了后面所有章节的优先级排序。

## 1.3 查询报告与查询画像（✅ 目录 p.7，标题作"查询报告"）

两条数据来源（✅ Key Points）：**慢查询日志** 与 **Performance Schema**，且作者判定 **Performance Schema 是更好的来源**
（常开、不依赖阈值、能做聚合与分位数）。二者共同的加工方式是 **digest**：把字面量抹掉、把 SQL 规范化成"模板"，
再按模板聚合，否则同一类查询会被成千上万条字面不同的记录淹没。

| 概念 | 作者定义（⚠️ 重构） | 用途 |
| --- | --- | --- |
| query profile（查询画像） | 按 **total time 降序**排列的查询清单，第一条就是"最慢"的那个 | 决定**先优化谁** |
| query report（查询报告） | 某**一个**查询的全部可得信息 | 做**查询分析**时用 |

> 排序键必须用总耗时而非平均耗时（† 作者脚注：有些工具能按别的指标排，但总耗时几乎是通用默认值）。
> 这条正是 1.1 那个"假性能故事"的技术解药。

## 1.4 查询分析（✅ 目录，p.14）

作者给"分析"下了一个反直觉的目标：**查询分析的目标是理解查询执行，而不是解决慢响应时间**（✅ Key Points）。
分析需要三件东西同时在场（⚠️ 重构）：① 查询指标（digest/慢日志）；② 元数据（EXPLAIN 计划、表结构、索引定义）；
③ **对应用的了解**——同一句 SQL 在不同访问模式下可以是对的也可以是灾难。

`rows_examined : rows_sent` 是本章给出的第一个效率比值：比值 ≈ 1 说明"读多少用多少"，
比值很大说明 MySQL 在**扫描后被丢弃**大量行（对应官方示例仓库 `ch01/rows-examined.sql` ✅）。

## 1.5 改进查询响应时间：直接与间接（✅ 目录，p.29）

这是全书的**分岔口**，后面九章都挂在这两枝上：

- **直接查询优化（direct）**：改查询 + 改索引 → 第 2 章 [02-索引与索引编制.md](02-索引与索引编制.md)
- **间接查询优化（indirect）**：改**数据**与**访问模式** → 第 3、4 章 [03-数据.md](03-数据.md)、[04-访问模式.md](04-访问模式.md)

作者的次序论：先直接（改动便宜、收益快），后间接（要动代码、动数据生命周期）；
两枝都尽力之后仍不达标，才轮到第 5 章分片与第 10 章硬件/云的问题。

## 1.6 何时优化查询（✅ 目录，p.31）

⚠️ 依小节名 + Pitfalls（"Not having or reviewing query metrics"）重构：慢查询审查是**日常例行**，不是事故响应。
判据是"值不值得投入"：**按总耗时排名**，优先吃下 top 1–3（它们通常吃掉绝大部分时间，见下方 🔧 的 88% 分布）。

## 1.7 MySQL：更快一点（✅ 目录，p.32）

作者在这里放了那个著名的玩笑式"优化"：**`TRUNCATE TABLE` 能显著提升性能——但请不要这样"优化"**（✅ 作者站在第 3+4 章摘要页回顾此点）。
它证明的是"数据越少性能越好"这一因果，而这条因果的正经用法留给了第 3 章。
本节的另一层含义：**让 MySQL 更快的最好办法是提升响应时间本身**，而不是给它换机器、调参数。

## 1.8 小结（✅ 目录，p.33）

六条可带走结论（⚠️ 依 Key Points / Pitfalls 逐条重构）：性能=响应时间；响应时间是北极星；
查询指标≠服务器指标；指标来自慢日志或 PS，PS 更好；聚合靠 digest；先画像（排序）后报告（分析）。

## 1.9 练习：识别慢查询（✅ 目录，p.34）

⚠️ 题面未获取（示例仓库只给 `ch01/rows-examined.sql` 文件名）。按小节名与本章口径，练习方向应为：
开慢日志（或读 `events_statements_summary_by_digest`）→ 按总耗时排名 → 对 top 查询算 `rows_examined/rows_sent` →
判定它是"索引问题"（进第 2 章）还是"数据/访问模式问题"（进第 3、4 章）。

## 🔧 本机机制类比（**这不是 MySQL**）

用 Python 内置 `sqlite3` 造了 200,000 条查询事件（4 类 digest 模板、7.6 MB 库文件，脚本
`D:\develops\tmp\dbwave_emp\exp.py`，结果 `results.json`），只做 digest 聚合与分位数这一件事：

| digest | 调用次数 | 平均耗时(µs) | 总耗时 | 占比 |
| --- | --- | --- | --- | --- |
| `UPD_ITEM` | 23,953 | 180,242 | 4,317 s | **88.2% 的时间 / 12.0% 的调用** |
| `SEL_ORDERS_BY_USER` | 89,893 | 3,300 | 296.7 s | 6.1% |
| `SEL_REPORT_JOIN` | 6,020 | 44,413 | 267.4 s | **3.0% 的调用 → 5.5% 的时间** |
| `SEL_ORDERS_BY_ID` | 80,134 | 164 | 13.2 s | 0.3% |

聚合本身（一次 `GROUP BY digest` + `ORDER BY SUM(ms) DESC`）耗时 **98.2 ms**——量级上说明"画像"不是昂贵操作。
**平均值会骗人**的实证：尾部 digest（`SEL_REPORT_JOIN`）分位数 p50 = **8,059 µs**、avg = **44,413 µs**（差 5.5 倍）、
p95 = **181,268 µs**、p99 = **552,015 µs**、max = **7,351,463 µs**；健康的 `SEL_ORDERS_BY_ID` 则是
p50 148.7 / avg 164.5 / p95 313.1 / p99 422.5 / max 958.4 µs——分布窄，平均值才有意义。
效率比值也复现了：尾部 digest 的 `rows_examined/rows_sent` = **229.4**，其余三条 ≈ 0.9–1.0。
→ 结论只用于说明"**按总耗时排名 + 看分位数**"这两个动作的方向性价值，**不可当 MySQL 性能数字引用**。

## 核心概念速览（中英对照）

- **查询响应时间** — query response time：MySQL 收到查询到发完结果集的时间；全书唯一北极星。
- **北极星指标** — North Star metric：只有一个指标能代表用户体验，其余都是它的解释变量。
- **查询指标** — query metrics：关于查询本身的指标，区别于关于服务器的指标。
- **慢查询日志** — slow query log：越过 `long_query_time` 的语句记录，查询指标的离线来源。
- **性能模式** — Performance Schema：常驻内存的插桩体系，查询指标的在线来源（作者首选）。
- **语句摘要** — statement digest：抹掉字面量后的规范化 SQL，聚合与排名的分组键。
- **查询画像** — query profile：按总耗时降序的查询清单，用来决定先优化谁。
- **查询报告** — query report：单个查询的全量信息，用来做查询分析。
- **总耗时** — total time（`SUM_TIMER_WAIT`/`COUNT_STAR`×avg）：排名键，避免"高频小查询"掩盖"低频大查询"。
- **分位数** — percentile（P95/P99，`QUANTILE_95`）：描述尾部；平均值只描述中间。
- **检查行/返回行比** — rows examined : rows sent：查询效率比值，越大越浪费。
- **直接优化** — direct query optimization：改查询与改索引。
- **间接优化** — indirect query optimization：改数据与改访问模式。
- **执行阶段与等待** — stages and waits：响应时间的内部构成（锁等待、I/O 等待等）。

## 最新演进与工业实践

**2024–2026 现状**：

1. **观测底座没有换代，但默认值更激进**：8.4 LTS（2024-04 起）与 9.x 创新版本继续强化
   performance_schema 语句摘要与直方图；8.4 移除了若干老选项、把可观测性项往默认开靠拢
   → <https://dev.mysql.com/doc/refman/8.4/en/mysql-nutshell.html>、<https://dev.mysql.com/doc/refman/9.1/en/mysql-nutshell.html>
   （⚠️ 具体开关默认值以手册为准，本机无 MySQL 8 实例验证）。
2. **"按总耗时排名 + 看 P95/P99"已是行业标准动作**：`pt-query-digest` 的 report 输出仍是这形态，
   仓库与文档 ✅ 可达 → <https://github.com/percona/percona-toolkit>、<https://docs.percona.com/percona-toolkit/pt-query-digest.html>。
   官方示例仓库 <https://github.com/efficient-mysql-performance/examples>（`ch01/rows-examined.sql`）最后更新 2022-08，
   说明本书代码基线仍停在 8.0.22，但方法论在 8.4/9.x 下不需要改写。
3. **尾部延迟的工程学地位上升**：Dean & Barroso, *The Tail at Scale*，CACM 2013（⚠️ 未注册 DOI，按题名+出处+年份引用）
   是"平均值无用论"的常见出处；OLTP 侧的实证方法可参 CMU 10-727 路线的
   Dam et al., *OLTP through the looking glass, and what we found there*, SIGMOD 2018,
   DOI <https://doi.org/10.1145/3226595.3226635>（✅ Crossref 校验通过）。
4. **近似查询/采样是另一条战线**：如果只做统计报表而非事务，聚合+采样的 AQP 结果

   DOI <https://doi.org/10.1145/3448016.3457277> ✅）能给出比"优化单条 SQL"更大的数量级收益——
   这是本书 OLTP 边界之外的对照，repo 内可接 [../DuckDB_in_Action/00-总览与阅读地图.md](../DuckDB_in_Action/00-总览与阅读地图.md)。
