## 一句话主旨

**复制延迟就是数据丢失（Replication lag is data loss）**——尤其在默认的异步复制下；
延迟的成因主要不在网络，而在**从库只有一个（默认）应用线程**，所以最有效的解是**多线程复制（MTR）**。

## 7.1 基础（✅ 目录，p.216）

定义（✅ Context）：**延迟 = 主库写入的时刻 与 该写入在从库被应用的时刻 之差**；
并且它**是所有数据库服务器的固有属性**，因为跨网络复制必然带网络时延。

必须掌握的三型与两条线程（✅ Key Points，⚠️ 重构）：

| 类型 | 语义（✅ 条目） |
| --- | --- |
| **异步（async）** | **默认**；故障时**可能丢掉大量已提交事务** |
| **半同步（semi-sync）** | 主库提交前等**至少一个从库确认"已收到并落盘"（注意：不是已应用）**；不丢已提交事务，**每连接最多丢一个未提交事务** |
| **组复制（Group Replication）** | 把实例变成集群；作者判语："**是 MySQL 复制与高可用的未来**" |

从库侧的机制底座（✅ Key Points）：**I/O 线程**从主库拉 binlog 事件写进本地 **relay log**；
**SQL（applier）线程默认只有一个**，从 relay log 执行；**可以开启多线程复制跑多个 applier**。
地基是"事务以 **binary log 事件**编码从源传到副本"（✅ Key Point）。

## 7.2 原因（✅ 目录，p.221）

✅ Key Point 给出**三个主因**：

1. **主库事务吞吐过高**（生产速率 > 应用速率）；
2. **实例在故障/重建后追赶**（catch-up）；
3. **网络问题**。

并且给出瓶颈定位（✅ Key Point）：**SQL/applier 线程是复制延迟的限制因素，增加 SQL 线程通过并行应用事务来降低延迟**；
附带一条反直觉（✅ Key Point）：**半同步复制本身也能造成延迟**（因为提交要等确认）。

## 7.3 风险：数据丢失（✅ 目录，p.223）

本章的标题句在这里（✅ Context）："**Replication lag is data loss. Seriously. Do not dismiss it.**"
含义（⚠️ 重构）：读到旧数据的用户看到的是**与已提交事实不一致的世界**；
主库在延迟窗口内故障，**异步复制下这段未传出的已提交事务就永久丢失**。
作者同时给了另一面（✅ Context）：**复制确实降低性能，但你不会想不带复制地跑 MySQL**——
它防止的是"公司会因此倒闭"级别的数据灾难（医院、银行都在跑 MySQL）。**成本被收益抵消**。

## 7.4 降低延迟：多线程复制（✅ 目录，p.227）

✅ Key Point 的结论句：**"启用多线程复制（MTR）是降低复制延迟最好的办法。"**
机制要点（⚠️ 依手册口径补充，本册不深入）：并行度参数 + **基于逻辑时钟（LOGICAL_CLOCK）的依赖追踪**决定
哪些事务可以并行应用；8.0.26+ 的 `replica_preserve_commit_order` 语义保证从库提交顺序与主库一致
（✅ 作者站在本章末列了同名文章 "Replica Preserve Commit Order and Measuring Lag"）。

## 7.5 监控（✅ 目录，p.231）

两条判据（✅ Key Points/Pitfalls）：

- **`Seconds_Behind_Source`（旧名 `Seconds_Behind_Master`）会误导**——它不是可靠的延迟指标；
- **用专门工具在次秒级间隔测量与报告复制延迟**（✅ Key Point）；
- 配套 Pitfall：**不监控延迟**、**不为延迟告警**、**不用 GTID**、
  **计划内切换时不等从库追平**。第 6 章那条组织判据在这里回收：**延迟要告警给应用负责人**。

## 7.6 恢复时间（✅ 目录，p.233）

✅ Key Point 两句：**"从复制延迟恢复的时间很难计算、也不精确"**；
**"MySQL 最终总会从延迟中恢复——只要成因修掉了，它总是会的。"**
配套的 Pitfall 是心态类的：**花精力纠结"到底什么时候追平"**（Obsessing about when MySQL will catch up）。
本册补一条本目录的取证口径：**追平时间 ≈ 待应用事件量 ÷ 应用速率**，
分母（应用速率）随并发与热点波动，所以只能给区间——这正是下方 🔧 测出的形状。

## 7.7 小结 + 7.8 练习：监控次秒级延迟（✅ 目录，p.234–235）

⚠️ 题面未获取。按小节名与本章判据重构：练习是**在从库上以亚秒间隔测出真实延迟**
（常见做法：往主库写带时间戳的心跳行，从库读回比较；或用 `pt-heartbeat`），
并验证 `Seconds_Behind_Source` 在追赶阶段给出的是**荒谬值**（0 或 NULL 或巨大跳变）。

## 🔧 本机机制类比（**这不是 MySQL、也不是复制**）

用线程池模拟"一个消费者 vs 八个按键亲和的消费者"：生产侧按固定速率产生事件，
每个事件带一个模拟"应用成本"（`sleep`）。脚本 `followup.py`（`results2.json`）；
**8,000 个事件**：

| 应用侧 | 墙钟 | 折算能力 | 比值 |
| --- | --- | --- | --- |
| **单线程串行应用** | **4.52 s** | ≈ **1,770 事件/秒** | 基线 |
| **8 个按键亲和 worker** | **0.54 s**（墙钟=最慢 worker） | ≈ **14,686 事件/秒** | **8.3×** |

三点结论，每点都对应本章一条论断：

1. **并行度近似线性地把应用能力乘上去**（8.3×，理想是 8×）→ 支持 7.4 "MTR 是最好的解药"。
2. **墙钟等于最慢的 worker**（0.54 s 与 slowest worker 完全相同）→ **数据倾斜/依赖会吃掉并行度**，
   这就是 MTR 需要"按依赖分组"的原因（`LOGICAL_CLOCK` 语义，⚠️ 手册口径）。
3. **延迟增长 = 生产速率 − 应用速率**：生产者 50,000 事件/秒时，
   单线程**每秒落后 48,230**、8 路**仍落后 35,314**；生产者 100,000/秒时分别 **98,230 / 85,314**。
   → **并行只是把能力乘 N 倍，如果生产速率高于应用能力，延迟仍然单调增长**；
   这也解释了 7.6 的"恢复时间难以精确"：分母（应用速率）本身不稳定。

⚠️ **测量诚实声明**：第一轮脚本把毫秒当秒用（`t_ms` 返回值与键名单位不一致），产出 `serial_apply_s = 11316.55` 这类荒谬值，
已整轮弃用；另外 **Windows 的 sleep 粒度约 0.5 ms** 会把绝对时间整体放大
（8,000 个事件的"标称成本之和"只有 0.4 s，实测墙钟 4.52 s）——所以**只有比值与落后量的形状可用于论证，绝对值不可引用**。

## 核心概念速览（中英对照）

- **复制延迟** — replication lag：主库写入与从库应用之间的时间差。
- **异步复制** — asynchronous replication：默认模式，故障可丢多个已提交事务。
- **半同步复制** — semi-synchronous replication：等至少一个从库确认收到并落盘；不丢已提交事务。
- **组复制** — Group Replication：把实例组成集群，作者称为 MySQL 复制与 HA 的未来。
- **binlog 事件** — binary log event：事务在网络上传输的编码载体。
- **I/O 线程 / SQL（applier）线程** — replica threads：拉取写 relay log 与执行 relay log，默认后者只有一个。
- **中继日志** — relay log：从库本地缓存主库 binlog 事件的文件。
- **多线程复制（MTR）** — multi-threaded (parallel) replication：多个 applier 并行应用事务，降延迟首选。
- **逻辑时钟依赖追踪** — LOGICAL_CLOCK-based dependency tracking：决定哪些事务可并行的依据（⚠️ 手册口径）。
- **提交顺序保持** — `replica_preserve_commit_order`：让从库提交顺序与主库一致。
- **`Seconds_Behind_Source`** — 官方状态字段：作者判为**会误导**的延迟指标。
- **次秒级延迟测量** — sub-second lag measurement：心跳行/`pt-heartbeat` 式专用测量。
- **追赶** — catching up：故障或重建后从库回放在途事件的过程，延迟的主要场景之一。
- **恢复时间** — recovery time：待应用量 ÷ 应用速率，作者判定"难算且不精确"。

## 最新演进与工业实践

**2024–2026 现状**：

1. **术语与命令已彻底改名**：8.0.22+ 起 `SLAVE`→`REPLICA`、`Seconds_Behind_Master`→`Seconds_Behind_Source`
   （⚠️ <https://dev.mysql.com/doc/refman/8.4/en/show-replica-status.html>）；本书用的正是新名，8.4/9.x 沿用。
2. **并行度与依赖追踪持续增强**：8.4 里 `replica_parallel_workers`/`replica_preserve_commit_order`
   仍是主要旋钮（⚠️ <https://dev.mysql.com/doc/refman/8.4/en/replication-threads.html>），
   作者 2021 年的判语"加 applier 线程是最好的降延迟手段"**至今未被推翻**。
3. **半同步的可用性改善**：_lossless_ 语义（`rpl_semi_sync_*_wait_no_ack` 可配）与"确认≠应用"的区分
   仍是排查延迟的第一道认知关（⚠️ <https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html>）。
4. **工程实践侧**：心跳式次秒级监控的现成实现是 Percona Toolkit 的 `pt-heartbeat`
   → <https://github.com/percona/percona-toolkit>（✅ 200）；`SHOW REPLICA STATUS` 的自动化采集已是各监控栈标配。
5. **理论谱系**：延迟与丢失的取舍本质是复制协议的一致性选择，可参 *Dynamo*（SOSP 2007,
   DOI <https://doi.org/10.1145/1294261.1294281> ✅）里的复制/一致性权衡，以及
   教科书版恢复与复制视角 [../数据库系统概念6/16-恢复系统.md](../数据库系统概念6/16-恢复系统.md)。
