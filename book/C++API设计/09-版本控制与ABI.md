## 核心概念速览（中英对照）

- **向后兼容** — backward compatibility：新版本继续接受旧用户的用法——版本策略的默认义务。
- **向前兼容** — forward compatibility：旧版本能容忍新数据/新调用（文件格式更常见，8.4.5 的「未知字段忽略」策略）。
- **源代码兼容** — source compatibility：旧代码在新头文件下**重新编译**仍通过且行为一致——C++ 库的常规承诺档。
- **二进制兼容（ABI 兼容）** — binary compatibility：旧目标文件不重编直接链新库仍正确——最严一档，管的是符号名、布局、调用约定、虚表。
- **ABI** — application binary interface：机器级契约集合：符号改编名、对象布局、vtable 布局与槽序、异常表、构造/析构语义、名字修饰、对齐规则。
- **符号版本化** — symbol versioning：ELF 上把符号绑到版本节点（`foo@LIBA_2.0`），同一 .so 可同时服务旧新两代符号请求——书 8.5 的当代成熟答案（libstdc++ 的 GLIBCXX_* 节点族是最大规模实践）。
- **弃用** — deprecation：宣告「还能用、将被移除」的正式流程；[[deprecated]] 让机器执法（书时代靠文档口头）。
- **API 生命周期** — API lifecycle：引入→稳定→弃用→移除的四阶段；8.3 要求每阶段有明确的版本号与时间承诺。
- **分支策略** — branching strategy：维护分支（1.x 修 bug）与主干演进如何共享代码；8.2.3「并行分支」谈同一 API 两版并活的组织成本。
- **API 审查** — API review：发布/合并前的强制关口（8.6：预发布审 + 预提交审），把「改不动」的代价前置到「还没发」。
- **版本信息查询** — version info API：`LIB_VERSION_STRING` 宏 + 运行时 `version()` 函数 + 头/库版本校验（8.1.3，书用版本号三件套防「头库错配」）。

## 动机：兼容性是一笔笔「还不清但可分期」的债

不设计兼容性的库，结局是两类之一：要么每个小改动逼全量重编/重测（用户流失），
要么永远不改（设计腐死）。8 章给的出路是把「改」拆成不同兼容档位的操作序列：
**加**（源码兼容档可控）、**改**（几乎总是断代操作，需双轨期）、**弃**（给迁移时间）、**删**（有明确时限）。

## 机制

### 1. 五种变更的兼容判定（8.5 的逐条精化）

```text
加一个自由函数/静态方法        —— 通常全兼容（符号新增，无既有布局受影响）
加一个 private 成员（朴素类）  —— 断二进制（sizeof/偏移变，02 章已实测 4→16），保源码
加一个 private 成员（Pimpl 类）—— 二进制也安全（02 章实测 sizeof 恒 8）
加一个虚函数（类中部）          —— 断二进制（vtable 槽序变，旧 .o 把新槽当旧槽调）；
                                只在**类尾追加**且用版本化句柄接口才可控 ⚠️ 各 ABI 文献建议不一
改函数签名                     —— 断符号（改编名变）：除非 extern "C" + 新名字双轨
```

extern "C" 接口因此是版本化的天然单位：**一函数一意图、名字带版本或走句柄表**
（我们的 MinGW 实测：导出面 = dllexport 白名单，正符合「按符号粒度管理兼容」的前提）。

### 2. 符号版本化与导出清单（书 8.5 的当代展开）

```makefile
# 🔧 ELF version script（liba.map）——同一 .so 供两代符号名
LIBA_1.0 { global: old_api; local: *; };
LIBA_2.0 { global: new_api old_api; } LIBA_1.0;
```

- **ELF**：`ld --version-script` + `objcopy --localize-symbols` 让「旧符号继续活着」成为链接器级事实；
  glibc/libstdc++ 全靠它做到「一个 .so 服务 30 年间的多代二进制」。⚠️ 本机为 PE/MinGW，
  version script 为 ELF 专属，未能本地实测——按工具链文档口径陈述。
- **Windows/PE**：无版本脚本等价物；导出表即名字表（实测），故实践是 **DLL 文件名/目录带版本 +
  SxS 并行安装**，或干脆 C 句柄接口里带 `size/struct_version` 字段（书 8.5.1 的精神）。
- **macOS**：Mach-O 的 two-level namespace + `-compatibility_version/-current_version`（同类能力第三实现）。

### 3. 头库错配与结构体版本（8.1.3）

`#if LIB_VERSION_MAJOR < 2 #error` 与运行时 `lib_check_header(version)` 是低成本保险；
数据驱动/配置结构体跨 ABI 传递的定型方案是**自描述大小**：

```c
// 🔧 结构体带 size 字段：库看到 48 字节版按 48 解释，旧用户传 32 字节版照常工作
typedef struct { uint32_t struct_size; /* >= offsetof(first_new_field)+sizeof */ ... } Init;
#define INIT_DEFAULT { .struct_size = sizeof(Init) }   /* SQLite/SDL/Vulkan 皆此法 */
```

### 4. 弃用与移除的流水线（8.5.3/8.5.4）

弃用三段：`[[deprecated("use foo2(); will remove in 3.0")]]` + 构建警告升级策略 +
发布说明（文档册见 [10-文档与测试.md](10-文档与测试.md)）；移除四条件：迁移路径存在、替代已稳定 ≥1 个版本周期、影响面评估完成、版本号升 MAJOR。
「移除」在 ABI 档还有个硬分支：**保留符号但返回 `ERROR_REMOVED`**（二进制兼容续命）vs 真删符号（断代）。

## 权衡

| 策略 | 换来 | 付出 |
| --- | --- | --- |
| 永远向后兼容（Windows NT 式） | 生态信任、升级无脑 | 死代码与兼容层堆积；架构被历史锁形 |
| 激进断代（早期项目常见） | 设计自由、代码干净 | 用户滞留旧版 → 事实上分裂多版本并维 |
| 双轨并行（旧 API 转调新实现） | 平滑迁移 | 两套承诺同时兑现，测试面翻倍 |
| 符号版本化 | 一库多代、按符号粒度控制 | 工具链绑定 ELF；版本号与发布流程必须严格同步 |
| ABI 冻结（承诺大版本内不变） | 下游可闭眼升级 | Pimpl/句柄等手段从可选变必修（布局自由已让渡） |

## 相邻概念对比

- **源码兼容 vs 二进制兼容**：前者容忍「重编」这一补救步骤，后者不容忍——C++ 的重头戏在后者（02/07/08 章手段全为它）。
- **版本号 vs ABI 版本号**：MAJOR.MINOR 是**人读的承诺**；`soname`（Linux）/DLL 版本资源才是**加载器读的承诺**——两者要显式映射。
- **弃用 vs 文档警告**：无机器执法的弃用等于没弃（书时代靠文档；[[deprecated]] 是分水岭）。
- **格式兼容 vs API 兼容**：8.2.4 的并行发布——格式（文件）比 API 更严苛：没有重编机会，必须自描述版本 + 未知容忍。

## 最新演进与工业实践

- **SemVer 与「弃用即 MAJOR 预告」**：semver 2.0.0 把 8.1/8.3 的直觉规则成文（新增功能=MINOR、
  弃用进发布说明、移除=MAJOR）；Rust crate 生态进一步把「未声明弃用即断代」变成社区执法。
- **abi-compliance-checker / ABICC**：开源 ELF ABI 回归检测器（对比两版 .so 的符号/类型/调用的差异清单），
  「二进制兼容」从人肉承诺变 CI 断言（github.com/lvc/abi-compliance-checker，仓库存在已核实 ⚠️ 活跃度未查）。
- **LLVM 的反向立场**：官方文档明确 LLVM C++ 接口**不保证 ABI 稳定**、插件必须同版本——
  「不做 ABI 承诺、用源码兼容 + 构建系统配套」的工业选项，与本书「承诺 ABI 并用 Pimpl 守」形成两极（见 11 章）。
- **abseil / folly 的「头文件即接口、版本靠源」**：Abseil 推荐随 LTS 源码集成，绕开 ABI 承诺问题——
  现代「依赖即 vendoring（把源码搬进工程）」趋势对 8 章的全部手段都是釜底抽薪：分发方式变了，兼容档位随之改（对照 [../ModernCMakeforC++.md](../ModernCMakeforC++.md) 的获取依赖章节）。
- **[[deprecated]] 的版本策略执法**（已实测 g++ 15.2 触发 `-Wdeprecated-declarations` 警告）：
  8.5.3 弃用流程第一次有了编译器+CI 的自动化抓手；C++ 各标准委员会自身也用「deprecated → removed」
  流程处置旧特性（Stroustrup 的演化章节有制度化的自述，见 [../C++语言的设计与演化.md](../C++语言的设计与演化.md)）。
- **ODABN 的启示与小众现实**：ESI Group 的 Open Device Adapter Binary Nomenclature 把设备驱动插件的
  版本号编进**文件命名 12 字段**（编译器/运行时/平台/架构全显式）——「用命名承载 ABI 信息」思路独特，
  但行业采纳有限 ⚠️（细节以 openabi 文献为准，未逐字核实）。
