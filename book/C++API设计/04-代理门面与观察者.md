## 核心概念速览（中英对照）

- **API 包装器** — API wrapper：在既有 API 之上加一层、以改写出更好契约的模式家族——本书 3.4 的组织概念。
- **代理** — proxy：与**同一接口**的替身，转发调用并在缝隙里加料（引用计数、远端编组、惰性构造、权限）。
- **适配器** — adapter：把 A 接口转译成 B 接口，让不兼容的双方协作；跨语言/跨版本绑定的主力。
- **外观** — facade：为一整个子系统提供**一个更高层的简化入口**；「便捷 API」的模式化身（01 章 2.3.3）。
- **引用计数代理** — reference-counting proxy：拷贝时只增计数、按条件复制时才分家——3.4.1 的经典用例，直连 COW（08 章）。
- **观察者** — observer：主题维护监听者列表，状态变化时逐个通知；解耦「谁关心」与「谁发生」。
- **主题** — subject：被观察的对象本体，通知的发出端。
- **推 vs 拉** — push vs pull：推式通知附带数据（简单但冗余），拉式只发信号、观察者按需取（精确但可能重复取）。
- **MVC** — model-view-controller：观察者模式的架构级应用；视图是模型的观察者。
- **悬垂观察者** — dangling observer：观察者先于主题销毁而未注销 → 通知时回调已死对象——模式自带的第一事故点。
- **通知重入** — reentrant notification：观察者在回调里再改主题 → 通知风暴/递归；书 3.5.2 的实现细节之一。

## 动机：包装器家族为什么是「API 之间的 API」

库的下游常有既成事实：遗留 C++03 接口、第三方 SDK、操作系统 API。你不能改它们，但你的用户
要的是一个体面的契约——于是「在 API 上再做 API」成为常态。3.4 的三分法用**接口相似度**划界：

```text
代理     ：新接口 ≈ 旧接口（同型），加的是"行为"
适配器   ：新接口 ≠ 旧接口（转型），加的是"翻译"
外观     ：新接口 ≫ 旧接口（升维），加的是"抽象"
```

判据一句话：用户拿到包装后，**知道的类变多还是变少**？变少的是外观；没变但能力多了的是代理。

## 机制

### 引用计数代理（3.4.1 主推形态，🔧 现代写法）

```cpp
template <typename T>
class CountedPtr {                      // 值语义外壳，共享堆上对象
    T*        fPtr;
    std::int32_t* fCount;               // 计数随对象组共享
public:
    explicit CountedPtr(T* p) : fPtr(p), fCount(new std::int32_t(1)) {}
    CountedPtr(const CountedPtr& o) : fPtr(o.fPtr), fCount(o.fCount) { ++*fCount; }
    CountedPtr& operator=(CountedPtr o) { swap(o); return *this; }  // 复制-交换
    ~CountedPtr() { if (--*fCount == 0) { delete fPtr; delete fCount; } }
    T* operator->() const { return fPtr; }
};
```

要点：按「共享所有权」语义工作时，拷贝成本恒为一次自增——这正是「接口承诺了值语义、
实现偷了引用语义」的合法范例（合法性来自文档把共享写进契约，否则是 01 章的抽象泄漏）。
C++11 后此类几乎都该用 `std::shared_ptr` 代替——自己数引用的时代结束了；
但「给旧库套一层计数句柄」仍是常见维护形态（对照 [../More Effective C++.md](../More%20Effective%20C++.md)
Item 28/29 的 smart pointer 条款）。

### 外观：一个入口吃掉十个头文件（3.4.3）

外观的 API 设计价值在物理层面也成立：门面类 + Pimpl（02 章）可以把整个子系统的
include 集合压成一个头——「Facade 给语义降维，Pimpl 给编译降维」，两模式常配合出现。
反面约束：门面**必须可被底层原语等价表达**（01 章便捷 API 判据），否则它就垄断了逃生通道。

### 观察者实现：书 3.5.2 的形态与它的雷

```cpp
// 🔧 教科书最小形（书时代风格）
class Subject {
    std::vector<Observer*> fObservers;
public:
    void attach(Observer* o) { fObservers.push_back(o); }
    void detach(Observer* o);
    void notify() { for (auto* o : fObservers) o->update(this); }   // 重入？迭代器失效？都在这行
};
```

三条实现决定，条条有账：
(a) 存**裸指针** → 悬垂观察者（必须契约化「观察者注销先于自身销毁」）；
(b) 存 `weak_ptr` → 自动死亡但通知语义变成「尽力而为」；
(c) 回调里允许改订阅表 → 要么先复制列表再通知（快照法），要么把修改排进延迟队列。
书 3.5.3 的推/拉之别落在这里：拉式（`update(Subject*)` 让观察者自取）天然容忍中间态合并，
推式（`update(old,new)` 带增量）要求主题把「哪些字段变了」当成契约的一部分。

## 权衡

| 决定 | 换来 | 付出 |
| --- | --- | --- |
| 代理转发层 | 旧 API 不动、新能力可插拔、ABI 缓冲带 | 每次调用多一跳；「代理的代理」层层失控 |
| 适配器 | 跨版本/跨语言协作 | 语义翻译失真（错误码↔异常、所有权↔GC） |
| 外观 | 上手成本骤降、物理隐藏点 | 子系统能力被入口宽度封顶；「漏外观」时用户绕道 |
| 观察者（推式） | 实时性好、实现直白 | 通知风暴、观察者被迫了解主题细节（耦合回升） |
| 观察者（拉式） | 主题只承诺「变了」 | 取回时刻状态可能又变（一致性靠用户） |
| 装饰器（通识对比） | 运行时按层加功能、免子类爆炸 | 与代理同构，接口越长越难懂；书未单列 ⚠️ |

## 相邻概念对比

- **代理 vs 装饰器**：结构同为「包一层转发」；代理**决定被包对象**（创建/延迟/远端），装饰器**接收被包对象**（由用户叠）。
- **代理 vs 适配器**：代理同接口、适配器换接口；跨语言绑定几乎全用适配器 + 代理组合（11 章的主干）。
- **外观 vs 适配器**：外观「造新简单面」，适配器「迁就既知面」——判据是目标接口的来源。
- **观察者 vs 回调函数指针**：一对多 vs 一对一；回调更轻但注销/生命周期同样存在；观察者只是正规化的回调集合。
- **观察者 vs 信号槽（Qt）**：信号槽=带类型参数与自动断开（weak connect）的工业观察者——悬垂问题的成熟答案 ⚠️ 非原书内容。

## 最新演进与工业实践

- **std::shared_ptr/weak_ptr 接管引用计数代理**：C++11 起自写计数句柄只在「与旧 ABI 对齐」「无 RTTI/原子开销」
  两种场景才成立；对照 [../Effective_Modern_C++.md](../Effective_Modern_C++.md) item 19–22。
- **Ranges/view = 编译期装饰器家族**：C++20 `views::transform | filter` 把「层层加功能」收编进标准库，
  零运行时开销（迭代器组合代替对象包装）——装饰思想的泛型化（对照 [../C++20模板元编程.md](../C++20模板元编程.md)）。
- **观察者 → 事件总线与响应式**：Reactive Streams（`onNext/onComplete/onRequest` 带反压）是「拉式观察者」
  的当代极限；gRPC/protobuf 的 field-mask 通知则解决「推式太吵」。Java 9 起 `java.util.Observer` 被废弃——
  朴素观察者模式在工业界的名声（隐式控制流、调试困难）值得设计者引以为戒。
- **C++ 观察者的现代替身三件套**：`std::function<void(Args...)>` + RAII 令牌（析构自动注销）、
  `sigslot` 类轻量库（已实测：GitHub rsdn/sigslot 与 palacolearn/undigested（sigc-lite）等活跃样本；
  ⚠️ 星标数未核实）、或 Boost.Signals2。工程通病「悬垂」的正规解是**带生命周期的订阅令牌**，非裸 attach。
- **代理的 ABI 用法**：把 02 章 Pimpl 换成「抽象接口 + 代理」路线时，代理对象是虚表稳定性的受害者
  ——接口加虚函数即全量重编（09 章）。工业上「C 句柄代理」因此常见（LLVM/Clang 的 C API 全是这类代理壳）。
