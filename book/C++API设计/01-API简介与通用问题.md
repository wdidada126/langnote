## 核心概念速览（中英对照）

- **应用程序编程接口** — Application Programming Interface (API)：一个组件对外提供的逻辑接口，划定「我承诺什么、你依赖什么」的边界。
- **契约** — contract：API 的版本、行为与限制的双向约定；发布即承诺，升级即修约（呼应 Szyperski 的「组件 = 契约」口径，书目见文末）。
- **物理隐藏** — physical hiding：通过「声明与定义分离」（头文件只留声明）把实现挡在编译期可达范围之外。
- **逻辑隐藏** — logical hiding：通过封装（private 成员）把实现挡在语义可达范围之外。
- **抽象泄漏** — leaky abstraction：实现细节经由返回值、异常、性能特征或文档措辞渗出接口。
- **最小完备性** — minimal and complete：接口应当「小而全」——概念少、每个概念够用，宁少勿滥。
- **可发现性** — discoverability：用户不用读文档也能猜对下一步该调用什么。
- **不易误用** — hard to misuse：错误用法要么编译不过、要么行为可预期，而不是静默出错。
- **正交性** — orthogonality：一个概念一个入口，调用之间不产生意外的组合副作用。
- **松耦合** — loose coupling：模块间尽量只靠名字/契约耦合，不靠类型布局、时序、全局状态耦合。
- **管理器类** — manager class：把一组相关对象的生命周期集中托管、隔离类间直接引用的设计手段。
- **API 层次** — API layering：低级 API（性能/细节）→ 高级 API（易用/安全）的分层，用户默认接触高级层。
- **文件格式 / 网络协议** — file format / network protocol：跨进程、跨机器的「时间维度上的 API」，同样要版本化。

## 动机：为什么「写个类」不等于「设计 API」

普通代码的调用者和被调用者同仓同生命周期，错了改起来一起改；API 的调用者你**不认识、管不着、
还可能有几百个**。书在 1.2 的立论是：API 设计的难，不在语言，而在「发布之后一切都不能随意改」。
1.1.1 用「契约与承包人」类比：签了合同（发布了 1.0），后面所有施工（升级）都要在合同框架内进行。

由此推出使用 API 的三大收益（1.3）：更健壮的代码（一处修复处处生效）、代码复用、并行开发
（接口先行，两边同时动工）。而 1.4 的「何时应当避免」常被读者跳过——它其实是本目录全部权衡的起点：
团队小、无复用需求、追求极致性能（跨层调用与间接都有代价）、或者你只是想试验设计方向时，
过早固化 API 是负债。

## 机制：第 2 章的六条「好 API 特征」如何落地

### 1. 问题域建模：先有抽象，后有类（2.1）

提供良好的抽象 = 找到问题域里**稳定**的名词和动词；关键对象建模 = 让类名/方法名直接来自领域词汇。
判断标准很朴素：非领域专家读一遍 `Document::insertImage(pos, img)` 能猜对行为。

### 2. 隐藏实现细节：两层隐藏（2.2）

```text
物理隐藏：声明(.h)与定义(.cpp)分离 —— 挡的是"编译器"，改实现不触发下游重编译
逻辑隐藏：encapsulation —— 挡的是"调用者"，让非法状态无法被构造
2.2.3~2.2.5 逐级递进：隐藏成员变量 < 隐藏实现方法 < 隐藏实现类
                          （最后一级即 Pimpl/不透明指针，详见本目录 02）
```

注意二者互不蕴含：头文件里写满 private 成员，物理隐藏为零（成员布局参与 sizeof）；
全 extern "C" 的 API 逻辑隐藏为零（状态全靠约定）。

### 3. 最小完备性与便捷 API（2.3）

「不要过度承诺」：public 面每多一个符号，升级就多一副镣铐——虚函数尤其危险（改签名即断 ABI 兼容，
详见 [09-版本控制与ABI.md](09-版本控制与ABI.md)）。「便捷 API」（convenience API）是刻意的加法：
用少量薄封装换可发现性，其合法性取决于它是否**可被底层原语等价表达**（能，则只是糖；不能，则它就是新的承诺面）。

### 4. 易用性五件套（2.4）

可发现性、不易误用（类型系统帮忙：强类型句柄、枚举、`explicit`——语言细节见 [07-C++用法与符号导出.md](07-C++用法与符号导出.md)）、
一致性（命名与参数顺序统一）、正交、健壮的资源分配（RAII，异常安全）、平台独立
（不对外暴露 `long`、`wchar_t` 这类宽度随平台漂移的类型，内部统一用 `int32_t` 等定宽类型）。

### 5. 松耦合四招（2.5）

仅通过名字耦合（字符串键、注册表）；降低类间直接引用；**刻意的冗余**（为解耦宁可复制少量代码，
与 DRY 的教条正面冲突，这是本章最有味道的一节）；管理器类集中生命周期；
回调/观察者/通知把「A 需要知道 B 变了」的依赖箭头反转（细节见 [04-代理门面与观察者.md](04-代理门面与观察者.md)）。

### 6. 稳定 + 文档 + 测试 = 一个东西（2.6）

书的收束观点：三者不是并列的工序，而是「可信度」的三条腿。没有文档和测试的 API 无法安全重构，
因此事实上不敢升级——即不稳定。这条观点直接展开为第 9、10 章（本目录 [10-文档与测试.md](10-文档与测试.md)）。

## 权衡

| 决定 | 换来 | 付出 |
| --- | --- | --- |
| 公开一个类而非句柄 | 直观、可内联 | 成员布局进 ABI，改私有成员也断兼容 |
| 保留虚函数扩展点 | 用户可子类化 | 类的行为承诺扩大到「实现细节级」 |
| 便捷 API | 可发现性、少样板 | 多一个漂移点：糖和原语行为不一致时是事故 |
| 刻意冗余 | 模块解耦、独立演化 | DRY 违背、修 bug 要改多处 |
| 管理器类 | 生命周期集中、依赖清晰 | 容易长成上帝对象，成为新的耦合中心 |

## 相邻概念对比

- **API vs ABI**：API 是源码级契约（重编译即可换库），ABI 是二进制级契约（不重编译直接链接）。
  本书大量设计（Pimpl、句柄、导出面）的隐藏动机是守住 ABI——系统展开在 [09-版本控制与ABI.md](09-版本控制与ABI.md)。
- **API vs 文件格式/协议**（1.6）：后者是「跨时间的 API」，比代码 API 更难改（没有重编译这个补救机会）。
- **物理隐藏 vs 逻辑隐藏**：见上文 2.2；Qt 的 d_ptr、C 的 opaque handle 属物理隐藏流派，`private:` 属逻辑隐藏流派。
- **与单文件大纲笔记的关系**：[../C++API设计.md](../C++API设计.md) 是本书的书目级大纲 + 跨年摘录；本目录是其逐章深读版，两形态互链。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「封装 = 把成员写进 private」 | private 不改变 sizeof，不阻止重编译；物理隐藏要另做（02） |
| 2 | 「API 越小越好」 | 最小要配「完备」；缺便捷入口时用户会绕过 API 直接摸内部，耦合更糟 |
| 3 | 「先写实现，API 以后再说」 | 接口先行才可并行开发（1.3.3）；API 是合同不是注解 |
| 4 | 「加个 overload 不影响任何人」 | overload 集改变可能改变名字解析结果，源码兼容≠零影响（09） |
| 5 | 「测试和文档是收尾工作」 | 2.6：没有它们你根本不敢动 API，等于提前宣告冻结 |

## 最新演进与工业实践

- **语义化版本（SemVer 2.0.0，2013）**：与本书同年提出，此后成为 API 版本承诺的事实标准
  （MAJOR.MINOR.PATCH + 明确的兼容性定义），可直接替换书 8.1 里的多种自选方案；对应知识点：「不要过度承诺」需要量化工具。
- **Abseil 的 LTS 政策**：Google 的 abseil-cpp 仓库提供 `lts_YYYY_MM_DD` 长期支持分支 + 主干滚动两种用法，
  并明文「不做 fork 维护、鼓励直接跟 head」——是「API 稳定承诺与开发速度矛盾」的工业级答案之一；对应：8.2 分支策略。
- **LLVM 对 C++ API 的官方立场**：LLVM 文档明确其 C++ 接口**不承诺 ABI 稳定**，对外稳定性交给
  一层 C API（llvm-c 目录，不透明句柄风格）——正是本书「纯 C 风格 + 物理隐藏」的组合拳工业化（详见 [06-API风格.md](06-API风格.md)、[11-脚本绑定与插件扩展.md](11-脚本绑定与插件扩展.md)）。
- **C++ Core Guidelines（Stroustrup/Sutter，GitHub isocpp/CPP）**：I.x（接口）、SL.x（生命周期）规则族可视为
  本书 2.1–2.5 的 2020 年代公文化版本；仓库已有解析笔记 [../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md)。
- **Chromium 的 API owners 制度**：浏览器核心 API 变更须指定 owner 评审并走 deprecation 流程——
  书 8.6「API 审查」的规模化实践；对应：仓库摘录里 Chromium base 库的使用体验（[../C++API设计.md](../C++API设计.md) 文末 2020-08 摘录）。
- **组件软件思想**：Krzysztof Szyperski《Component Software: Beyond Object-Oriented Programming》
  （Addison-Wesley 初版 1998；2nd ed., ACM Press 2002，⚠️ 仅书目信息核实到常见记载，未查到 DOI）——
  「组件 = 显式契约 + 二进制兼容」是本目录 01/06/09 三章观点的共同上游。
