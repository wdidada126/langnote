## 核心概念速览（中英对照）

- **单例** — Singleton：保证某类型至多一个实例并提供全局访问点；本质是「把状态集中到一处」的**刻意耦合**（对照 01 章 2.5 松耦合）。
- **Meyers 单例** — Meyers Singleton：函数内静态局部对象 + 删除拷贝，C++11 后一行成型的标准写法（以编译器魔法线程安全为地基）。
- **魔法静态** — magic statics：C++11 [stmt.dcl] 规定「局部静态变量的初始化线程安全」，双检锁的手写时代由此终结。
- **死引用问题** — dead reference problem：析构顺序无保障——先销毁 Logger、后销毁使用它的模块，悬垂引用一触即崩（书的 3.2.1 用「泄漏单例」回避：故意不 delete）。
- **依赖注入** — dependency injection (DI)：协作者由外部构造并传入，对象不自寻全局访问点；3.2.3 用它拆单例的测试死角。
- **单一状态 vs 会话状态** — global state vs session state：单例被滥用的两种形态——进程级一个（配置）与「其实是每会话一个」（连接、事务），后者被写成单例即埋下不可并发的雷。
- **工厂方法** — factory method：返回抽象基类指针/句柄的创建函数，把具体类型的选择推迟到库内。
- **抽象基类** — abstract base class：纯虚接口，多态的锚点（3.3.1）；工厂的返回类型。
- **注册式工厂** — registry factory：类型名字符串 → 构造函数指针的映射表，3.3.3「扩展工厂」的方向——它也是插件系统的胚胎（见 11 章）。
- **多态构造** — polymorphic construction：`Shape* s = createShape(kind)` 之后 delete 必须经虚析构，否则未定义。

## 动机：为什么这书把「单例」放 API 设计里讲

单例在 GoF 语境是对象创建模式；在 API 语境它是**全局可变状态的合法化通道**——
一旦库提供了 `Logger::instance()`，就同时承诺了「初始化时机、线程安全、析构顺序、可替换性」四件事，
每件都是接口契约（01 章的「不要过度承诺」在此最易违约）。3.2.4/3.2.5 的两节标题就是本书的独创贡献：
先问「你需要的到底是哪种状态」，再谈实现。

## 机制

### 单例的四代写法（3.2.1–3.2.2 的演化线）

```cpp
// 🔧 第一代：全局指针 + 手工判空——非线程安全、析构失控（书里用来立靶）
// 🔧 第二代：双检锁 DCLP——没内存序就错；C++11 atomic 修正后仍啰嗦（并发细节见仓库并发笔记）
// 🔧 第三代（3.2.1 精神 + C++11 定型，已实测 g++ 15.2 编译通过）：
class Logger {
public:
    static Logger& instance() { static Logger inst; return inst; }   // magic static
    void log(const char* msg);
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
private:
    Logger() = default;
};
// 🔧 第四代（书 3.2.1 的「泄漏」立场的现代版）：析构顺序敏感时故意不销毁
void shutdownSafe() { /* 不调用 ~Logger，进程退出由 OS 回收 */ }
```

第三代的关键：`static` 局部对象的初始化被标准保证「恰好一次、其他线程等待」，
于是线程安全从「你要会写」变成「编译器默认给」。

### 工厂：把 `new` 关进库（3.3.1–3.3.2）

```cpp
// 🔧 库侧
class Shape { public: virtual ~Shape() = default; virtual void draw() = 0; };
Shape* createShape(const std::string& kind);   // 唯一的创建入口
// 🔧 库内
struct Circle : Shape { void draw() override; };
struct Square : Shape { void draw() override; };
Shape* createShape(const std::string& kind) {
    if (kind == "circle") return new Circle;
    if (kind == "square") return new Square;
    return nullptr;                            // 错误处理决策点——见 05 章 4.7.4
}
```

三条设计线在书中逐步收紧：
(a) **返回类型**：裸指针（书时代）→ `std::unique_ptr<Shape>`（现代默认，所有权即时交清）；
(b) **入参**：字符串键（可发现性差）→ 枚举 → 类型化 tag；
(c) **扩展**：3.3.3 把 if-链换成注册表——

```cpp
// 🔧 注册式工厂（扩展工厂示例的现代形态）
using ShapeFactory = std::function<Shape*()>;
std::map<std::string, ShapeFactory>& registry();       // Meyers 单例在此归位：真·单一状态
bool reg(const std::string& n, ShapeFactory f) { registry()[n] = std::move(f); return true; }
static bool ok_circle = reg("circle", []{ return new Circle; });   // 自注册：翻译单元级副作用
```

自注册是双刃剑：静态初始化顺序不确定（C++11 magic static 恰好治了 registry() 本身，
但 `ok_circle` 的初始化时机仍依赖链接顺序）；更稳的做法是把注册动作放进被显式调用的
`initBuiltinShapes()`，或在插件边界上做延迟注册（11 章）。

## 权衡

| 决定 | 换来 | 付出 |
| --- | --- | --- |
| 单例访问点 | 随处可用、状态天然归一 | 隐式全局依赖：单元测试被毒化（3.2.3）；并发/会话扩展要推倒重来 |
| 泄漏单例（不析构） | 死引用问题消失 | 工具报内存泄漏，需要白名单豁免 |
| 工厂 + 抽象基类 | 具体类型进库、加类型不断 ABI | 值语义丧失、虚表进 ABI、对象离开构造即裸指针 |
| 注册表工厂 | 库可被第三方扩展（通向插件） | 字符串键无编译期检查；注册时机成契约 |
| DI（构造传入） | 可测试、依赖显式 | 组装代码（composition root）上移，样板增多 |

3.2.3 的立场值得原样记住：单例与 DI 冲突的根源是「访问点即获取方式」——
`instance()` 让任何代码在任何时刻抓依赖。解法：接口注入 + 只在 composition root 出现一次 `instance()`。

## 相邻概念对比

- **单例 vs 命名空间级自由函数**：同样全局，后者无状态化更难（书 3.2.4 的问题：你真的需要对象还是只要函数？）。
- **单例 vs 线程局部存储**：`thread_local` 把「一进程一例」改「一线程一例」——会话态误用单例的急救包（并发语义见 [../C++并发编程实战2/02-线程管控.md](../C++并发编程实战2/02-线程管控.md) 一类材料）。
- **工厂 vs 类本身（构造函数）**：构造要求知道具体类型；工厂要求不知道——「谁需要知道什么」是划界标准。
- **工厂 vs 抽象工厂**：一族产品的成套创建；本书未展开 ⚠️，仓库 GoF 笔记有整卷（见下联系）。

## 最新演进与工业实践

- **C++11 标准背书**：[stmt.dcl] 的线程安全局部静态（已实测 g++ 15.2：`static` 初始化在 -O0/-O2 下
  都生成 guard 变量与线程等待路径）；`constexpr` 单例不适用、`inline` 变量（C++17）让头文件内定义全局句柄族更安全。
- **folly::Singleton**：Facebook folly 仓库把「依赖图 + 有序析构 + 线程安全」做成工业件（依赖其他单例时
  先析构依赖者），直面书 3.2.1 的死引用问题——开源可查 github.com/facebook/folly `Singleton.h`。
- **Google C++ Style Guide 明令限制全局单例**，理由与书 3.2.3 一致（可测试性）；Chromium base 提供
  `base::NoDestructor<T>`（泄漏式单例的正规工具，对应书 3.2.1 的立场）。
- **注册式工厂 → 插件 ABI 的前夜**：`createByName` 型工厂的字符串键一旦跨二进制边界，就升级为
  「接口名 + 版本号」的 ABI 协商（见 [11-脚本绑定与插件扩展.md](11-脚本绑定与插件扩展.md) 与 ODABN 一节）。
- **测试手段**：对「只能拿单例」的遗留代码，工业界通行做法是「接口包装 + 链接期替换（fakes via linker）/
  seam 技术」，与书 10.4.2「桩对象和模拟对象」直接呼应。
