## 核心概念速览（中英对照）

- **技术债** — technical debt：为短期速度牺牲设计整洁、日后须连本带息偿还的决策总额（4.1 把 API 误用当债主）。
- **功能性需求** — functional requirements：用户「用这个 API 要完成什么」的外在描述；不关心类怎么摆。
- **用例** — use case：一段「角色-目标-步骤」的散文脚本，API 的第一块试金石（4.3 给了模板）。
- **主要抽象** — key abstraction：问题域中应当成为一等概念的东西；漏识别它，API 就永远绕路表达。
- **里氏替换原则 (LSP)** — Liskov Substitution Principle：子类必须可顶替父类出现在任何契约中——「公共基类指针的合法性凭证」。
- **开闭原则** — open-closed principle：对扩展开放、对修改封闭；API 语境下即「加类型不改老代码」。
- **迪米特法则** — Law of Demeter：只和直接朋友说话（`a.b().c()` 链式穿越是耦合警报）。
- **类设计选项** — class design decisions：构造/析构/拷贝/赋值/取址/派生/虚函数——每个 C++ 类都要显式表态的清单（4.6.2）。
- **值类 vs 引用类 vs 基类** — value/reference/base-like classes：类设计的三分类，决定接口形态与隐藏程度。
- **句柄/索引参数** — handle/index parameter：以不透明小整数代对象入参——跨语言、跨版本友好、可发现性差。
- **错误返回码** — error code return：C 风格错误通道；与异常/断言/out-param 构成 4.7.4 的四大路线。
- **断言** — assertion：表达「不该发生」的内部前置条件，发布版可关；不是用户错误的处理器。
- **异常安全等级** — exception safety levels：基本保证 / 强保证（提交或回滚） / 不抛出（noexcept 承诺）。

## 动机：为什么「设计章」排在「语言用法章」之前

语言手法（第 6 章）是工具箱，流程（第 4 章）是图纸审查制度。4.1 用「好设计示例」开场
而非空谈原则，立场很清楚：**API 的设计错误是乘法错误**——实现烂可以重写，公开面烂只能
将错就错（09 章的弃用流程是给这里补的课）。4.1.3「为长期而设计」是全章总纲：先假设
「这个 API 会活十年、被一千人扩展」，再决定今天要不要开这个口子。

## 机制：从需求到函数签名的四级漏斗

### 1. 需求与用例（4.2–4.3）

用例的价值不在格式，在「**强迫你以调用者身份把代码写一遍**」：写不出自然流畅的调用序列，
就是抽象选错了。4.3.4 专门讨论了敏捷环境下的用例尺度——够用即止。

### 2. 架构：识别抽象 → 关键对象 → 约束（4.5）

4.5.2 的「约束」清单（性能、平台、既有系统、团队）是 API 设计与乌托邦设计的分界线；
4.5.6「架构的交流」提醒：画不出来的架构评审不了（图在此章是文档的预演 → 文档册见 [10-文档与测试.md](10-文档与测试.md)）。

### 3. 类设计：一张必须逐项签字的表（4.6.2）

```text
对每个 public 类回答：
  默认构造？ 显式构造？ 拷贝？ 移动？ 赋值？ 取地址？ 允许派生？ 虚析构？
  —— 每个"没回答"的项都由编译器替你回答（隐式生成），而编译器不懂你的 ABI 承诺
```

LSP（4.6.4）在 API 语境的实操判据：**子类可新增，不得改签名语义、不得收紧前置条件、
不得放宽后置条件**。违反的案例在现实里通常是「`Stack` 派生自 `std::stack` 然后重定义 push」一族。
迪米特法则（4.6.6）给出「访问器链」的诊断信号：`doc->getStyle()->getColor()->getR()`
意味着四个类的任一改动都会砸到调用方——这正是 01 章「降低类耦合」要消灭的对象。

### 4. 函数设计与错误处理（4.7）

4.7.3 函数参数清单（输入用 const 引用/值、输出用返回/引用参数、输入输出、可选参数、
数量参数 ptr+size）在书时代全部成立；当代补上了 `std::string_view`/`std::span` 两个「只读视图」成员——见下「最新演进」。

**4.7.4 错误处理**是本章必须展开的硬核（书的四大手段）：

```cpp
// 🔧 (a) 返回码 + 最后错误查询（C API 标配，跨 ABI 最稳）
int  doc_open(const char* path);        // 0 成功
const char* doc_last_error();           // 线程局部：否则并发下互踩
// 🔧 (b) 异常（C++ 库内主流；但跨 DLL 边界/跨语言慎用——运行时与栈展开不 universal）
// 🔧 (c) 断言：编程错误（null 解引用、前置条件破），发布版 NDEBUG 即消音
// 🔧 (d) 返回值内嵌错误（optional/expected 的前身：哨兵值 -1/nullptr——最易被忽略的路线）
```

三条设计律：**(1) 区分「可恢复错误」与「程序 bug」**——前者走 (a)/(b)，后者走 (c)，混用等于
让用户处理不该他处理的事、或让 bug 穿码而过；**(2) 错误通道要显式**——返回码可以被无视，
「错误码塞参数 + 函数返回 bool」的混合通道让读者猜（书批评的写法，当代用 [[nodiscard]] 机器强制）；
**(3) 承诺异常安全等级**——文档不写「本函数提供强保证」，用户就只能当没有保证用。

## 权衡

| 决定 | 换来 | 付出 |
| --- | --- | --- |
| 公开可继承基类 | 第三方扩展（开闭） | LSP 违约风险 + 虚表 ABI 责任（09 章） |
| 密封类（禁继承） | 契约面收缩 | 扩展改走插件/策略路线（11 章） |
| 异常 | 错误与正常流分离、RAII 干净 | 跨模块边界成本；库用户可能禁异常（工业常态） |
| 返回码 | ABI 简单、无展开开销 | 可忽略性；线程安全错误状态要自建 |
| 断言 | 开发期抓非法状态于现场 | 关掉后语义空洞；**绝不可有副作用** |
| 哨兵值 | 签名最短 | 与合法域纠缠，可发现性最差 |

## 相邻概念对比

- **用例 vs 单元测试**：用例是人写的「意图」，测试是机器执行的「断言」——10 章测试的选题来源即 4 章用例。
- **LSP vs 组合优于继承**：LSP 管「继承后行为契约是否可替换」，「是否该继承」由 4.6.3 的复用/多态动机判断。
- **迪米特 vs 外观**：都反对链式穿越；外观给替代码，迪米特给诊断。
- **断言 vs 错误码**：一条分界「调用者能否恢复」。把参数校验写成断言=把用户输入错误升格为程序 bug，
  服务端场景会炸掉整个进程。

## 最新演进与工业实践

- **C++11 的表态工具**：`=delete`/`=default`、`override`/`final`（4.6.2 清单第一次有了语法笔）、
  `noexcept`（异常承诺可机器检查）。**C++17 `[[nodiscard]]`**：错误返回码「可忽略」顽疾的编译器级解药，
  库函数凡不检查返回值即 UB/泄漏的都该标注（已实测 g++ 15.2：`[[nodiscard]]` 触发 `-Wunused-result` 警告）。
- **C++17 `std::optional` / C++23 `std::expected<T,E>`**：把「返回值内嵌错误」正规化——
  expected 的提案号 P2502 经 wg21.link 核实存在（标题文本未能逐字核实 ⚠️），配合 [[nodiscard]]
  即是 4.7.4(a)+(d) 路线的现代合体；仓库对照 [../C++17完全指南.md](../C++17完全指南.md)。
- **GSL 契约原语**：Microsoft Guidelines Support Library 的 `Expects()/Ensures()`（前置/后置条件断言化）
  与 `not_null<T>`——把 4.7 的参数设计写成可执行契约；与 [../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md) 的 I/N 规则族互查。
- **LLVM 的「无异常」错误处理**：`llvm::Error`/`llvm::Expected<T>` + `consumeError`——大型库
  在「用户禁异常」约束下把 (b) 路线做成类型化的返回码，工业级示范（github llvm/llvm-project，`llvm/include/llvm/Support/Error.h`，已核实存在）。
- **abseil 的 `StatusOr<T>`**：gRPC 风格的 `absl::StatusOr` 与状态码分层（`absl::StatusCode`），
  跨语言边界（11 章）时错误通道即「状态对象」——(a)+(d) 在 RPC 时代的定型形态。
- **敏捷/用例之后**：需求实践中「用户故事 + 验收标准」与 4.3 用例模板互补；API 圈对应物是
  「以示例驱动文档」（example-driven docs，见 09 章），本质仍是本章的「先以调用者身份写一遍」。
