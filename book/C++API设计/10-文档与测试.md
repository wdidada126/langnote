## 核心概念速览（中英对照）

- **接口契约文档** — interface contract documentation：写清前置/后置条件、错误语义、所有权、线程与异常保证——文档的第一职责是**定义行为**（9.1.1/9.1.2）。
- **概述文档** — overview document：从使用者视角讲「这套 API 解决什么问题、核心概念是什么」，与自动生成的参考手册互补（9.2.2）。
- **发布说明** — release notes：每次版本变更的对外账本——「告知行为的改变」（9.1.3）的正式载体。
- **Doxygen**：C/C++ 注释驱动的文档生成器（书 9.4 的主角），注释即元数据，生成 HTML/手册/API 参考。
- **文档可用性** — documentation usability：搜索可达、示例可跑、代码片段可复制——文档也是产品界面（9.3）。
- **单元测试** — unit test：隔离验证最小单元行为；集成测试跨模块、性能测试验渐近承诺（10.2 三档）。
- **测试对象** — test doubles：用可控替身（桩 stub / 模拟 mock / 假对象 fake）替换不可控依赖（10.3.2/10.4.2）。
- **可测试性设计** — testability：依赖可注入、状态可观察、时间可控制——「为可测试而设计」反向塑造 API（10.4 全节）。
- **契约编程** — design by contract：pre/post/invariant 显式化并可被测试执行——断言（10.4.4）与测试（10.4.5）的接合点。
- **记录与重放** — record & replay：录制真实交互做回归数据（10.4.6）——有状态 API 与网络栈的常规武器。
- **代码覆盖率** — code coverage：行/分支覆盖率作为「测了什么」的粗尺（10.5.2），高覆盖≠高质量。
- **持续构建** — continuous build/integration：提交即全量测试（10.5.4），API 审查（09 章 8.6）的机器岗哨。

## 动机：文档与测试是「敢改」的前提

书 10.1 的理由清单与 9.1 同构：文档让用户**正确**使用、测试让你**安全**修改。合编一册的理由在此——
二者共享同一份原料：**接口契约**。契约写成注释进文档、写成断言进代码、写成用例进测试——
三处一致则库可信，三处打架则必有一处是假话（书时代无工具执法，当代靠示例测试与 CI 对齐）。

## 机制

### 1. 文档四件套的分工（9.2）

```text
自动 API 参考（Doxygen）  —— 每个签名/参数/返回值的查表手册；不回答"该怎么用"
概述与教程               —— 回答"这是什么、怎么开始"；带一个能跑的最小示例
示例（examples）          —— 可运行代码 = 可被编译的文档（9.2.3 的书时代形态：独立文件）
发布说明 + 授权           —— 变更账本 + 法律界面（9.2.4/9.2.5；授权写错是商业事故）
```

Doxygen 注释风格（9.4.2–9.4.8）的工程要点：类注释放**职责与所有权语义**，
方法注释逐条回答——参数单位、可空性、错误通道（返回码/异常二选一要说清）、线程保证、
复杂度；这些恰是 05/07 章「契约承诺」的文档镜像。**枚举注释**（9.4.7）是书特别点名的一格——
枚举值跨版本不可重排（09 章），注释即冻结公告。

### 2. 测试金字塔与 API 的关系（10.2/10.3）

书给的三档对应 API 的三个面：单元测试测**每个入口的承诺**，集成测试测**入口的组合**，
性能测试测**文档写下的渐近承诺**（08 章）。10.3.3「关注测试工作量」的提醒到 2026 年仍然新鲜：
API 公开面 ×测试面成正比——「最小完备性」（01 章）是最便宜的测试预算策略。

### 3. 可测试性反塑 API（10.4 精选三件）

- **测试私有代码（10.4.3）**：书的立场是「别为测试破坏封装；把私有逻辑提成可注入的内部组件测」，
  而不是开一道 `friend` 后门（07 章 6.8 的账）。
- **桩与模拟（10.4.2）**：依赖抽象基类/接口才可替换——「工厂 + 抽象基类」（03 章）的另一份红利；
  单例（03 章 3.2.3）是模拟掉不掉的头号障碍。
- **记录重放（10.4.6）与国际化（10.4.7）**：有外部世界依赖（文件系统/网络/时钟/编码环境）的 API，
  要么注入「世界」（clock/rng 参数化——C++20 `<chrono>` 日历与时钟抽象使其标准库化），要么录制世界。

### 4. 🔧 最小可跑示范（已实测 g++ 15.2 编译；测试件写在仓库外临时目录）

```cpp
// widget_test.cpp —— 契约 + 单元断言的最小闭环（无框架形态，书 10.4.4/10.4.5 的手写版）
#include <cassert>
#include <cstdio>
int divide(int a, int b) {                 // 契约：b != 0，前置条件断言化
    assert(b != 0 && "divide: precondition violated");
    return a / b;
}
int main() {
    assert(divide(6, 2) == 3);              // 行为用例 = 文档的机器镜像
    #ifndef NDEBUG
    // 负例用 death-test 思路：置 NDEBUG=0 运行会 abort——框架版见下"最新演进"
    #endif
    printf("ok\n");
}
```

## 权衡

| 决定 | 换来 | 付出 |
| --- | --- | --- |
| 注释即文档（Doxygen 流） | 文档与代码同仓同版本，不脱节 | 注释质量不可自动验证（示例测试才补得上） |
| 手写 assert 契约 | 零依赖、发布可关 | 负例难断言、无失败报告聚合 |
| 测试框架 | 用例组织/断言宏/参数化/death test | 编译与二进制体积负担；header-only 框架可缓解大半 |
| 覆盖率驱动补测 | 未测代码现形 | 为指标造无断言测试 = 自欺（10.3.1 特征清单是解毒剂） |
| 面向接口写测试 | 实现可替换、ABI 演化自由 | 替身维护成本；mock 过紧致「测了个替身」 |

## 相邻概念对比

- **文档 vs 测试**：同一份契约的两种表达——文档给人、测试给机器；「示例即测试」（doctest 类工具）是第三条路。
- **桩 stub vs 模拟 mock**：stub 返回预设值（状态验证），mock 断言交互序列（行为验证）——选错则测试脆或虚。
- **性能测试 vs 剖析**：前者是回归断言（「不得慢于 X」，进 CI），后者是定位手段（08 章 7.9）。
- **契约编程 vs 错误处理**：断言处理「绝不该发生」（05 章），契约把这句判断**写进代码**并可被测试执行。

## 最新演进与工业实践

- **Doxygen 仍是事实标准但生态扩张**：m.css（mosra 的 C++ 现代文档管线，主打可读与代码高亮，
  github.com/mosra/m.css，仓库存在已核实）、Sphinx+breathe/exhale（把 Doxygen 元数据喂进 reStructuredText 站）、
  clang-doc（Clang 自带实验件，**尚未完整可用** ⚠️ 官方自述 incomplete）。「发布说明」的社区成文规范
  是 Keep a Changelog（keepachangelog.com）；授权机器可读化靠 SPDX 标识符。
- **测试框架三代目**：GoogleTest/gtest（死亡测试 `EXPECT_DEATH` 正是上节手写 assert 负例的框架化）、
  Catch2（v3 起为常规多文件库，v2 为单头）、**doctest**（单头、编译比 Catch 快是其卖点 ⚠️ 量化基准未复测）。
  三者活跃、文档好——书 10.5.1 的「选型」话题有了当代默认答案。
- **Sanitizer + fuzz 成为 API 验收标配**：ASan/UBSan/TSan/MSan（编译器内建）+ libFuzzer/AFL++/OSS-Fuzz——
  「不易误用」（01 章）的机器执法：非法输入下不崩、不报 UB，是公开 API 的现代底线。
- **示例即测试**：把文档示例抽进测试编译运行（doctest 框架名即此义；Python 圈 Sphinx doctest 早已如此）——
  9.1「文档定义行为」的闭环工具。
- **契约的类型化**：GSL `Expects/Ensures`（微软 Guidelines Support Library）、`std::expected`（C++23，
  提案号 P2502 经 wg21.link 核实存在 ⚠️ 标题未逐字核验）把 10.4.5「契约编程」从注释推进到类型系统。
- **持续构建平民化**：GitHub Actions/GitLab CI 让书 10.5.4 的「持续构建系统」零硬件起步；
  ABI 回归检查（09 章 abi-compliance-checker）可挂在同一条流水线——「发布前 API 审查」（8.6）的自动化终态。
