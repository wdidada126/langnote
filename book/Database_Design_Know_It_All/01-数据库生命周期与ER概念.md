## 2. ER 概念：一套与实现无关的业务词表（重构骨架 ⚠️）

### 2.1 核心构件

| 构件 | 定义要点 | 设计含义 |
|---|---|---|
| 实体 Entity | 可唯一标识的" Thing"（人/事/物/地） | 每个实体集必有标识符 → 映射后成主键 |
| 属性 Attribute | 实体的性质；原子性是 1NF 的前置 | 派生属性/多值属性是后两章规范化伏笔 |
| 联系 Relationship | 实体间关联，带基数(1:1/1:N/M:N)与参与(全/偏) | M:N 必须"降生"为独立关系表——设计第一课 |
| 实体集/键 | 强实体 vs 弱实体（依赖标识） | 弱实体 → 复合主键的外键复用 |

ER 模型的思想史锚点（✅ DOI 过 Crossref 200 校验）：
- Codd 关系模型 1970：*A Relational Model of Data for Large Shared Data Banks*，DOI [10.1145/362384.362685](https://doi.org/10.1145/362384.362685)；
- Chen ER 1976：*The Entity-Relationship Model—Toward a Unified View of Data*，DOI [10.1145/320434.320440](https://doi.org/10.1145/320434.320440)。
本册第 2 章的写法属于"给工程师的极简 ER 词表"，与盘上 [../数据库系统概念6/07-数据库设计E-R模型.md](../数据库系统概念6/07-数据库设计E-R模型.md) 的教科书展开、[../Database_Modeling_and_Design_5e/02-实体联系模型ER.md](../Database_Modeling_and_Design_5e/02-实体联系模型ER.md) 的 5e 版三者同题互参。

### 2.2 ER→关系的第一跳（本册第 5 章的预告）

映射规则的公共知识重建（⚠️ 非原书措辞）：实体集→表、属性→列、强键→主键、1:N→子表外键、M:N→桥表、弱实体→主键含属主键。**易错点**：把 1:1 拆成两表导致无谓 JOIN、把多值属性直接压进一列违反 1NF。

### 2.3 🔧 类比实测：外键完整性是真的会拦你（非本书引擎行为）

本机 python `sqlite3`（SQLite **3.45.3**）内存库（脚本 `dbwave_w4_knowitall/experiments.py` E1，✅ 实跑）：

```sql
PRAGMA foreign_keys=ON;               -- SQLite 默认 OFF，须显式开
CREATE TABLE department(id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE);
CREATE TABLE employee(id INTEGER PRIMARY KEY, name TEXT NOT NULL,
                      dept_id INTEGER NOT NULL REFERENCES department(id));
-- 插入 dept_id=99（不存在的部门）：
-- sqlite3.IntegrityError: FOREIGN KEY constraint failed   ← ✅ 实测回显
```

结果 ✅：合法 2 行通过、越权行被拒并回滚——"ER 图上的线"在 DDL 里的物理对应物就是它。⚠️ 注意：源书讨论的是 DB2/Oracle 的 referential integrity（含 CASCADE/隔离级别交互），SQLite 仅演示存在性约束，**不可把本实验外推到本书时代商业引擎行为**。

## 4. 常见误区清单（依章题语义与公开共识重构 ⚠️）

1. 把生命周期当瀑布：无反馈环的流程在需求变更下必炸（对读 Mullins 变更管理章）。
2. ER 图上画"外键"：外键是逻辑层产物，概念层只有联系。
3. 用 NULL 表达可选参与：全/偏参与是模式层约束，不应退化为数据层 NULL 约定。
4. 弱实体当强实体：独立主键一给，属主删除后的孤儿数据就无法在模型里禁止。

## 5. 自测题（重构 ⚠️，答案要点随题）

1. M:N 联系在生命周期哪个阶段被**识别**？哪个阶段被**消灭**？（答：概念期识别于 ER 图；逻辑期以桥表消灭——见 §2.2。）
2. 弱实体若误配独立代理键，属主删除后出现什么现象？（孤儿行；约束层无法拦截，违反标识依赖语义。）
3. "全参与→NOT NULL FK"为何仍是有损翻译？（NOT NULL 只保证列非空，不保证"对方实例必须存在且唯一"，后者靠 FK+业务规则合成。）
4. E1 实验中若漏执行 `PRAGMA foreign_keys=ON`，越权 INSERT 会怎样？（静默成功——SQLite 默认关闭外键强制的历史坑；⚠️ 商业引擎默认行为不同，不可外推。）
5. 为什么说生命周期章与维护章（本册未选的运营部分）之间存在"反馈短路"？（维护期最小的改列动作，语义上可能是一次概念重述。）

## 核心概念速览（中英对照）

- **数据库生命周期** — Database Life Cycle：需求→设计→实现→运行维护的阶段模型，设计错误成本随阶段指数增长。
- **概念设计** — Conceptual Design：与 DBMS 无关的业务数据视图，产出 ER 图。
- **实体与实体集** — Entity / Entity Set：可唯一标识的业务对象及其集合。
- **属性** — Attribute：实体的性质；原子性为 1NF 前设。
- **联系与基数** — Relationship / Cardinality：实体间关联，1:1、1:N、M:N 三型决定映射表形。
- **参与约束** — Participation（Total/Partial）：全参与要求每实例必有联系，映射后常变 NOT NULL FK。
- **弱实体** — Weak Entity：标识依赖属主实体，映射后主键含属外键。
- **多值属性** — Multivalued Attribute：违反 1NF 的"一列多值"，须拆表。
- **外键完整性** — Referential Integrity：FK 值必须存在于被引用主键集（🔧E1 实测拦截）。
- **ER 模型** — Entity-Relationship Model：Chen 1976 提出的概念建模世界语（✅ DOI 校验）。
- **关系模型** — Relational Model：Codd 1970，数据=元组集合，设计=求好分解（✅ DOI 校验）。
- **设计成本曲线** — Cost-of-fix Curve：同一缺陷在概念层修正是维护层修正代价的零头（⚠️ 转述行业共识）。

## 最新演进与工业实践

**到 2026 年，"生命周期+ER"组合的幸存与变形**（本节全部为 2026-09 视角大补，基线 2008）：

1. **ER 仍是前端语言，但落点变了**。概念建模的世界语没有换代：dbt 时代的"数据图"、Snowflake 的语义视图都把 ER 关系当作机器可读元数据复用——✅ https://docs.getdbt.com/docs/build/documentation （200 可达）。建模工具上，经典 CASE（ERwin/Rational Rose）让位于代码化建模：dbdiagram.io/DBML、PlantUML ER 皮肤等（⚠️ 转述，未逐一核 URL）。
2. **图数据库给 ER 平反**。属性图（Property Graph）本质="实体-联系"一等公民化：节点=实体、边=联系带属性，M:N 不再是必须拆表的二等货色。2023 年 SQL 标准化吸收 PGQ：ISO/IEC 9075-16 Property Graph Queries (SQL/PGQ)——⚠️ 官方页 https://www.iso.org/standard/81519.html 本次 403，仅标准号+名转述；盘上对读 [../Graph_Databases_2e/00-总览与阅读地图.md](../Graph_Databases_2e/00-总览与阅读地图.md)。
3. **生命周期被"数据工程化"重写**。瀑布式 DBLC 在云原生时代碎裂为：schema-as-code（迁移工具 Flyway/alembic）、CI 里跑数据契约、Git 管 DDL 版本——设计评审从会议室移到 PR（对读 [../Database_Administration_2e/05-设计评审与变更管理.md](../Database_Administration_2e/05-设计评审与变更管理.md) 的 2012 版流程，差异即十年）。
4. **NoSQL 建模把"先查询后建模"变成默认**：文档/键值设计从访问模式倒推集合结构，ER 的"联系拆表"律被嵌入数组/引用二选一取代——✅ AWS DynamoDB 官方设计指南 https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-general-nosql-design.html （200 可达）；盘上 [../nosql精粹.md](../nosql精粹.md)。
5. **外键的宗教战争降温**。2008 源书默认"库内完整性"；2026 高写入互联网系统常以"应用层校验+对账"替代库级 FK（分库分表的现实约束），但分析型与交易系统回归声明式约束——🔧E1 的教训仍然成立：约束要么声明并被强制，要么只是注释。
