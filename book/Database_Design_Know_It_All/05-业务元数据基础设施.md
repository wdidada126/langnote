## 1. 核心命题：元数据是数据，元数据库也是数据库（⚠️ 重构）

### 1.1 概念分层

| 层 | 内容 | 例子 |
|---|---|---|
| 技术元数据 | schema/血缘/统计/ETL 日志 | 列类型、转换脚本 |
| **业务元数据** | 定义、口径、所有者、规则、术语表 | "活跃客户=近90天有下单"由谁定、何时生效 |
| 操作元数据 | 作业执行、SLA、访问审计 | 昨晚装载 03:12 完成 |

本章论点：业务元数据若只活在 Word/Wiki 里就是**死文档**；必须落成**可查询的关系化仓库**（元数据基础设施=模型+存储+管理流程三件套），与数据仓库同构地"建模、装载、维护"。Inmon 谱系立场：元数据库自己就得先过一遍前八章的全部设计流程——**吃自家狗粮**。

### 1.2 元数据仓库的最小模式（⚠️ 依源书章族题语义重构）

```
meta_object(id, type, name, parent_id ...)          -- 对象登记：表/列/报表/术语
meta_def(object_id, definition_text, version,       -- 业务定义+版本
         effective_from, effective_to)
meta_owner(object_id, role, person_id)              -- 责任矩阵
meta_rule(object_id, rule_text, kind)               -- 口径/质量/派生规则
meta_lineage(src_id, dst_id, transform_ref)         -- 血缘边表
```

要点：**定义带版本与生效区间**（业务口径是时态数据）、**所有者是外键不是自由文本**、**血缘=边表**（图查询友好）。这三条在 2026 年分别长成了：schema 版本化、数据Owner 制、开放血缘标准。

### 1.2.1 目录装载管线（⚠️ 依源书"基础设施"语义重构的五段式）

采集（DB 字典拉取/ETL 作业日志/报表工具导出）→ 标准化（实体 ID 归一、同义对象合并）→ 版本化（effective 区间切代）→ 关系构建（lineage/ownership 边）→ 服务（检索、订阅、影响分析 API）。

典型死法：只接了采集、没接业务定义段——目录变成"技术字典的自动镜像"，业务元数据仍活在 Word 里，本章批判的"死文档"以新硬件复发。

### 1.2.2 元数据载体三代目（重构 ⚠️）

- 一代：纸质字典与 Word 术语表（1990s 前）；
- 二代：**独立元数据库**（本章时代：关系化、批处理刷新、专人维护）；
- 三代：活性目录服务（嵌入式采集+人机共编+API 优先——见演进节 1）。

本章站在二代末期：其全部判断被三代兑现，只有一条例外——**没人维护**的病灶（演进节 4 的自动激励正是奔它而去）。

### 1.3 🔧 类比实测：元数据即表（SQLite/DuckDB，✅ 实跑 E5 后半）

- SQLite 自带的 `sqlite_master`：`SELECT COUNT(*) FROM sqlite_master WHERE type='table'` → **10 条目**（实验库）——系统把"表有哪些、DDL 全文"当普通表存放，`PRAGMA table_info(...)` 即"对元数据做参数化查询"；
- DuckDB：`SELECT COUNT(*) FROM duckdb_tables()` → **3 条**——表值函数化的目录接口。

结论（概念迁移，非本书引擎行为）：**一切元数据基础设施的终点形态都是"可 SELECT 的对象清单+可 JOIN 的关系边"**——Inmon 的关系化主张在本机两秒验证。两秒现场版：

```sql
PRAGMA table_info('employee');   -- "列清单"作为普通结果集返回（cid/name/type/notnull/pk）
SELECT name, sql FROM sqlite_master WHERE type='table' ORDER BY name LIMIT 3;
-- DuckDB 对位：SELECT table_name, estimated_size FROM duckdb_tables();
```

## 2. 治理流程面（⚠️ 转述时代语境）

2008 年的"元数据管理"叙事与今天的"数据治理"词汇几乎逐条对映：术语表→业务词汇表、变更审批→schema 变更评审（对读 [../Database_Administration_2e/05-设计评审与变更管理.md](../Database_Administration_2e/05-设计评审与变更管理.md)）、元数据加载批处理→catalog 自动采集；当年痛点（**没人维护**）今天依旧，只是激励方式从"合规"变成"AI 要读你的口径"。与 Mullins 的元数据管理章对照：[../Database_Administration_2e/16-元数据管理与DBA工具.md](../Database_Administration_2e/16-元数据管理与DBA工具.md)（DBA 工具视角）。

### 2.1 治理责任矩阵（RACI 重构 ⚠️，meta_owner 的流程侧）

| 活动 | 数据 Owner | Steward | DBA/平台 | 消费者 |
|---|---|---|---|---|
| 口径定义 | A | R | C | I |
| Schema 变更 | A | R | R | C |
| 血缘修复 | I | A | R | C |
| 质量稽核 | A | R | C | R |
| 术语争议裁决 | A/R | C | I | C |

（R=执行 A=问责 C=咨询 I=知会。）矩阵本身也是元数据——存进 §1.2 的 `meta_owner` 才能被影响分析 JOIN 到。

## 4. 历史定位与三个误区（重构 ⚠️）

本章 2008 年刊行时正逢"元数据管理"行业第二波泡沫（MDA/DOOM 队列式推销）退潮，Inmon 把论题拉回"它就是个小数据库"的朴素立场，是它被选进设计合集的原因。常见误读三条：

1. **"上工具=有基础设施"**——§1.2 模式不立，任何工具只是更贵的死文档；
2. **"元数据一次建好长期受益"**——定义段是时态数据，停更六个月后错误率反而高于无目录时代（自信的错）；
3. **"业务元数据归 IT 管"**——RACI 表 A 列全部落错人（§2.1），这是当年失败项目的共同验尸报告结论（⚠️ 综述）。

## 核心概念速览（中英对照）

- **业务元数据** — Business Metadata：定义、口径、规则、所有权等"关于数据的业务事实"。
- **技术元数据** — Technical Metadata：schema/血缘/统计等实现侧知识（⚠️ 与业务元数据二分是本章纲纪）。
- **元数据基础设施** — Metadata Infrastructure：模型+存储+维护流程三件套，本章题眼。
- **元数据仓库** — Metadata Repository：以数据仓库手法建设的元数据库（关系化主张）。
- **术语表** — Glossary / Business Vocabulary：受控业务词与其定义集合。
- **口径版本化** — Versioned Definitions：effective_from/to 时态建模，业务定义的 2NF 起点。
- **数据所有者** — Data Owner/Steward：责任外键化，拒绝自由文本。
- **血缘** — Lineage：对象间派生关系的边表（列级理论见盘上专册）。
- **元数据加载** — Metadata Harvesting/Loading：批处理采集+变更侦测（⚠️ 2008 机制转述）。
- **对象登记** — Object Registration：meta_object 树，目录服务的祖先型。
- **死文档问题** — Static Documentation：无维护激励的元数据=零价值，本章的假想敌。
- **元模型** — Metamodel：描述"元数据结构"的结构，基础设施的 schema-of-schema。
- **活性目录** — Active Catalog：运行时自动采集+人可订正的现代形态（见演进 1）。
- **数据契约** — Data Contract：口径的双方签署版，meta_rule 的流程化转世。

## 最新演进与工业实践

1. **从"仓库"到"活性目录"**：2026 年元数据基础设施的工业形态是**数据目录+可观测性**一体：DataHub（✅ https://docs.datahub.com/docs/introduction ，200）、OpenLineage（✅ https://openlineage.io/ ，200）把 §1.2 的边表升级为**运行时事件流**（RUN/STATE/DATASET 三类 facet 模型），血缘由 ETL 执行自动上报而非人工登记——Inmon"必须可查询"全中，"人工维护"全灭。盘上系统展开：[../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md](../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md)。
2. **SQL 标准侧的迟到**：信息_schema（information_schema）/ 目录视图（pg_catalog、✅ DuckDB `duckdb_tables()` 同族）始终是"技术元数据"通道，业务层标准要到近年的 **Dataverse/ODCS/ISO 11179 元数据注册**等框架（⚠️ 转述，未核 URL，不给链接——诚实缺口）。
3. **语义层=业务元数据的新家**：指标定义（metric definitions）从术语表卷宗升格为**查询引擎可执行的代码**：Snowflake Semantic Views 把"口径"做成对象、被授权、被 JOIN——✅ https://docs.snowflake.com/en/user-guide/views-semantic/overview （200）；dbt Semantic Layer 同理（✅ https://docs.getdbt.com/docs/build/documentation 入口可达）。这是"元数据即数据"命题的 2026 兑现。
4. **LLM 成为元数据的第一消费者**：Text-to-SQL、AI 问数管道对业务定义/示例值/所有者的依赖，使"没人维护"的死文档问题第一次有了**自动激励**（口径错→答错→被追责闭环变短）；元数据质量工程（metadata-as-code、目录评分卡）成为数据治理新工种（⚠️ 实践综述）。
5. **合规驱动的永久化**：GDPR/个保法把"数据分类分级+访问审计"钉进操作元数据，2008 年可选的治理动作今天是审计必选项——治理册互链登记见 [00-总览与阅读地图.md](00-总览与阅读地图.md) §8（#189 Understanding Data_Governance 为同波兄弟，只登记不链）。
