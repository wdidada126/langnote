## 1. Ch.5 · 逻辑数据库设计（⚠️ 按章题语义与 Teorey 谱系公共知识重构）

### 1.1 任务定义

输入=概念模型（ER/UML），输出=目标 DBMS 可承载的**关系模式族+视图+完整性规格**。四步标准流水：

1. **映射**：实体→表、1:N→外键、M:N→桥表、多值→子表、弱实体→复合键（详表见 [01-数据库生命周期与ER概念.md](01-数据库生命周期与ER概念.md) §2.2）；
2. **规范化整形**：对每张表跑函数依赖审计（→ 本章第 2 节）；
3. **访问路径中立化**：逻辑层**禁止**出现索引/分区决定（留给 Ch.7-8），保证"一逻辑多物理"；
4. **视图与授权设计**：外模式剪裁+最小权限，2008 年语境下还含"角色工程"（对读 [../Database_Administration_2e/04-数据库设计与应用设计.md](../Database_Administration_2e/04-数据库设计与应用设计.md) 的 DBA 侧流程）。

#### 1.1.1 逻辑模式评审清单（重构 ⚠️，评审文化的可操作化）

- [ ] 每表能一句话说清"每行是什么"（粒度声明与概念层一致）；
- [ ] 主键稳定：业务值变化不牵动标识？（牵动→代理键或复合键+变更预案）
- [ ] 所有外键**显式声明**而非"代码里心照不宣"（🔧E1 教训：不声明=不强制）；
- [ ] 派生列白名单化：每处冗余有刷新契约（→ [04-物理设计与反规范化.md](04-物理设计与反规范化.md) Ch.8）；
- [ ] NULL 语义审计：未知/不存在/不适用三态是否混用一个 NULL；
- [ ] 同一业务事实是否出现在两处（冗余普查，先于反规范化决策记录基线）。

### 1.2 逻辑设计的经典取舍（⚠️ 转述该谱系公开共识）

- **1:1 联系合并 vs 拆开**：高频共查→合并；生命周期/权限/列宽差异大→拆；
- **类表继承三方案**：单表全列（可空多）/子表只放差量（JOIN 多）/关联表桥接（灵活查询难）——"Table Per Type/Subclass/Relation"的 2008 前身表述；
- **检查点**：每表须能回答"每行是什么"（粒度重述）+ 主键候选+全依赖链。

## 2. Ch.6 · 规范化（✅ 归源 Teorey 4e ⚠️ 内容重构）

### 2.1 谱系与定义

规范化理论源头（✅ DOI 过 Crossref 200）：Codd 1970 [10.1145/362384.362685](https://doi.org/10.1145/362384.362685) 提出依赖概念的雏形，1971-1972 引入 FD 与 2NF/3NF/BCNF 谱（⚠️ 年代转述）；Fagin/Armstrong 的 JD/多值依赖续写 4NF/5NF（⚠️ 转述，未核 DOI 不给出）。本章的教科书写法：

- **1NF**：属性原子（合集在第 2 章已埋伏笔）；
- **2NF/3NF**：消除部分/传递函数依赖——异常三兄弟（插入/删除/更新）为动因；
- **BCNF**：每个决定符都是候选键；**保持依赖+无损连接**的分解定理（⚠️ 定理叙述以 Date/教材为准）；
- **4NF/5NF**：多值依赖与连接依赖——工程上罕见触发，审计上值得知道存在。

4e 章的招牌落点：**规范化不是道德，是异常账本**——先用 E2 式小账本算给你看"不改几行"，再谈范式。

### 2.1.1 FD 审计四步法（⚠️ 谱系公共知识重构）

1. 列出表的全部属性集 U 与候选键全集 K；
2. 对每个真子集 X⊆U 写出 X→Y（Y⊄X）成立的最小覆盖；
3. 逐条判定：决定符 X 非超键 ⇒ 违 BCNF；X 是超键但 Y 依赖经非键中间传递 ⇒ 违 3NF；
4. 违例即拆表，拆完复跑无损连接检查（🔧E2 的 JOIN 行数核对即是它）。

对 `orders_bad(ord_no,item,qty,price,cust,cust_city)`：FD 有 `{ord_no,item}→qty`、`item→price`、`ord_no→cust`、`cust→cust_city`——后三条都是"非键决定符"，于是拆出 item_price/o_head/cust_city 三张表；每表决定符皆键，审计通过（E2 ✅ 实跑验证了这一步的账）。

### 2.2 🔧 类比实测：反常更新的账本（SQLite 3.45.3，✅ 实跑 E2）

未规范表 `orders_bad(ord_no,item,qty,price,cust,cust_city)` 3 行（pen 出现在 O1、O2 两单）：

- 改 pen 单价：`UPDATE orders_bad SET price=2.0 WHERE item='pen'` → changes()=**2**（一处业务事实，两处物理修改，漏一处即脏数据）；
- 3NF 分解后（o_item/o_head/item_price/cust_city 四表）：同操作命中 `item_price` → changes()=**1**；
- 无损性验证：四表按连接条件 JOIN 还原 → **3 行=原 3 行** ✅。

⚠️ SQLite 无自动 FD 审计能力，范式检查只能人肉；商业 CASE 工具的 FD 推断未实测不评。

### 2.3 范式边界案例（讨论题 ⚠️）

1. 分析型宽表故意违反 3NF（→ 直接进 [04-物理设计与反规范化.md](04-物理设计与反规范化.md) Ch.8 的动机）；
2. 计数列（`order_count`）是传递依赖的合法豁免吗——"派生冗余"与"反常更新"的折中；
3. JSON 列装"半结构化属性"算 1NF 还是赖账——2008 无此题，2026 面试必考（🔧 类比：SQLite JSON1 扩展把列内文档当表查，✅ https://www.sqlite.org/json1.html ，200 可达；范式语义仍属"应用层自觉"）。

以上边界题的当代总名是"**半结构化列的治理边界**"：哪些字段拍平成列（进范式管辖、进 FD 审计），哪些留在文档里（换 schema 演化自由度）——同一张力，新的名字，永远吵不完。

## 3. 两章合训：一个 20 分钟微案例

需求三句话："课程有多名讲师；学生选课带成绩；教室可容纳 N 人。"
→ 概念图（Ch.2/4 词表）→ 逻辑模式（本章映射）→ FD 审计：`grade` 依赖 (student, course)，`offeringsemester` 依赖 course？**故意留一个传递依赖**给读者抓——这正是规范化章的存在理由。对读完整案例：[../Database_Modeling_and_Design_5e/07-逻辑设计完整案例.md](../Database_Modeling_and_Design_5e/07-逻辑设计完整案例.md)。

埋雷答案（自核 ⚠️）：若把教室容量直接放"选课"表，则 `course→capacity_via_room` 不经全键传递，违 3NF；正确落点是 教室实体+排课联系。另 M:N（课程×学生）必须桥表承载 grade，学生选课直接压列即违 1NF。

## 4. 自测题（重构 ⚠️）

1. BCNF 分解是否总能同时做到无损+依赖保持？（否——依赖保持失败时退 3NF 分解，剩余校验交给全模式断言/触发器 ⚠️ 转述定理族，证明在 Date 书。）
2. 同一订单表把 `dept_name` 抄为冗余列，用 §1.1.1 清单哪两条约束它的合法性？（派生列白名单+刷新契约。）
3. 1:1 联系的三实现（合并/双表共主键/桥表）各在什么负载下胜出？（高频共查/权限隔离/两端可空演进。）
4. JSON 列内嵌数组经 `JSON_TABLE` 拍平后"满足"的是哪一范式？其 FD 谁来审计？（形式 1NF；应用层自觉——见演进节 3。）
5. E2 中为何 JOIN 还原 3=3 就能宣称无损？（对这份数据成立是**必要非充分**；一般性要证公共属性为其中一表超键 ⚠️。）

## 核心概念速览（中英对照）

- **逻辑设计** — Logical Database Design：概念模型到关系模式+视图+约束规格的转换阶段，访问路径中立。
- **映射规则** — Mapping Rules：实体/联系到表/外键的标准词典（1:1/1:N/M:N/弱实体）。
- **表-per-三型** — Table Per Type/Subclass/Relation：类表继承的三种落地策略及其 JOIN/NULL 权衡。
- **函数依赖** — Functional Dependency (FD)：X→Y 的约束，范式定义的基本原子。
- **2NF/3NF/BCNF** — Normal Forms：消部分依赖/传递依赖/凡决定符皆候选键。
- **异常三兄弟** — Insert/Delete/Update Anomalies：冗余分解不彻底的三种病征（🔧E2 量化）。
- **无损连接分解** — Lossless-Join Decomposition：JOIN 还原行数=原行数（🔧E2 实测 3=3）。
- **依赖保持分解** — Dependency-Preserving：FD 可在单表上局部校验，否则靠触发器兜底。
- **4NF/5NF** — JD/MD 范式：多值/连接依赖层，工程低频但审计必备。
- **候选键审计** — Candidate Key Review：每表列全依赖链的纪律动作。
- **视图/授权设计** — External Schema & Grant：逻辑设计的应用剪裁与最小权限收尾。
- **范式vs民俗** — Formal Theory vs Folklore：Date 谱系对手册式规则的质疑（对读 §1.3）。

## 最新演进与工业实践

1. **"规范化还是反规范化"被存算分离改写**。2026 云仓（Snowflake/BigQuery）列存+廉价扫描使 JOIN 成本不再主导，"规范化的分析库+语义层"成为新派；🔧 本册 E4（DuckDB 500 万行联表 476ms 反快于冗余单表 845ms）就是该趋势的桌面级复现——详见 [04-物理设计与反规范化.md](04-物理设计与反规范化.md) §2.3。✅ https://docs.snowflake.com/en/user-guide/views-semantic/overview （200）。
2. **约束即测试**：dbt/Great Expectations 把"每行是什么+唯一性+引用完整性"写成 CI 断言，逻辑设计的"评审会"变成"流水线"——✅ https://docs.getdbt.com/docs/build/documentation （200）；治理侧配套读 [../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md](../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md)。
3. **SQL:2023 与 JSON 关系化**：SQL/JSON（JSON_TABLE 把文档拍平成满足 FD 审计的"影子表"）让 1NF 之争有了官方仲裁工具——PostgreSQL 的 jsonb+生成列/GIN 索引路线 ⚠️ 转述，官方类型文档 ✅ https://www.postgresql.org/docs/current/datatype-xml.html （XML 同页族，JSON 见 datatype-json.html，本次未单抓 ⚠️）。
4. **范式教学位移**：多数 2020s 教材把 FD/BCNF 证明让位给"键与约束的建模纪律+反规范化案例研讨"；理论纵深直接去 Date 三部曲（§1.3 三链），工程纵深去 [../Understanding_MySQL_Internals/00-总览与阅读地图.md](../Understanding_MySQL_Internals/00-总览与阅读地图.md) 的 InnoDB 二级索引与覆盖扫描语境。
5. **逻辑设计的"多模化"**：同一概念模型要同时导出关系 DDL、文档聚合、图 schema（PGQ）三种逻辑视图——Ch.5 的"映射"词典首次变成 1→N 分支函数；合集并置的 Ch.10/11 恰是该分支的两个 2008 原型（→ [06-XML存储与移动对象建模.md](06-XML存储与移动对象建模.md)）。
6. **一句话收束两章**：逻辑设计的产物不是"漂亮的表"，是**一份可被证伪的依赖清单**——工具会过时，清单不会。
