## 1.1 为什么此刻需要「数据可观测性」（译载节题：扩展的数据团队 / 挑战 ✅）

现代数据栈的三条演化线把「数据出问题」从偶发事故变成结构性风险（⚠️ 转述归纳）：

1. **链路变长**：源系统 → 采集（CDC/事件流）→ 存储湖仓 → 转换层 → 集市 → BI/AI/运营动作。任何一环的时间语义、模式语义都可能与下游假设脱节。
2. **团队变宽**：分析工程师、数据科学家、平台工程、业务自建报表并行写入同一条链路，「谁动了我的数据」从玩笑变成审计需求。
3. **消费者变成机器**：特征库、推荐系统、LLM 检索与代理动作直接吃数据——坏数据不再只是「报表难看」，而是自动化决策被污染（译载节题「AI 障碍」✅ 对位）。

对照盘上笔记：软件侧同构问题在 [../Database_Reliability_Engineering/00-总览与阅读地图.md](../Database_Reliability_Engineering/00-总览与阅读地图.md) 中以 SRE 方法处理（可用性目标、错误预算）；本书的主张是把这套「运行态自证」思路移植到**数据资产**上（⚠️ 归纳）。

## 1.2 概念源流：从控制论到数据栈（⚠️ 常识性转述，未取一手）

- **控制论起点**：Kalman 意义上的能观测性（observability）——由系统外部输出推断内部状态的能力。它是结构性质，不是工具清单。
- **软件工程中继**：DevOps/SRE 语境把「可观测」落地为对指标、日志、追踪三类信号的采集与查询（Grafana 官方文档口径可查，✅ 见 1.6 取证表）。
- **数据域终接**：Ben Moses 在 WSDM '22 短文 *The Rise of Data Observability*（DOI `10.1145/3488560.3510007`，✅ Crossref 200 实测）把数据可观测性概括为「让数据用户能够自行发现、诊断、解决数据问题」的新兴方向——这是本册概念最接近学术定义的可核锚点；本书（⚠️ 转述）在同类口径上展开成方法论。
- **与「数据可观测性三册」的关系**：#223《What Is Data Observability?》（O'Reilly 短报告）先行给概念卡，本册给全书框架——两者疑同作者 Andy Petrella（⚠️ 转述，见 00 元数据表）；#223 与 #224《Data Observability for Data Engineering》均留第 6 波在册（本册只登记不链，见 00 第四节）。

## 1.3 定义与工作构件（⚠️ 转述重构）

把「可观测性」落到数据上，需要三类构件同时在场：

| 构件 | 内容 | 缺位后果 |
|---|---|---|
| 信号面 | 时效、量、分布、模式、血缘事件等可持续采集的运行信号 | 只能靠人肉对账 |
| 推断面 | 从信号推断「数据资产内部健康状态」的模型（阈值/基线/统计） | 有告警没诊断 |
| 行动面 | 通知到对的人、带上下文（影响范围、负责人、修复入口） | 告警疲劳、甩票 |

「五支柱」（Freshness/Monitoring/Lineage/Documentation/Alerting）即这三类构件的展开，下一章逐件拆。

## 1.4 问题的构成与后果（译载节题 ✅：问题构成与后果 / 对团队动态的影响）

- **成本面**（⚠️ 转述）：数据工程师大量工时消耗在「查数、对数、解释数」而非建设；信任折价使已建数据资产闲置。
- **组织面**：数据团队与业务团队的接口冲突（工单化、对立化），是译载目录专门列出「团队动态影响」一节的现实背景。
- **治理面**：治理制度（政策、权责、标准）若无运行信号支撑则停留在文档层——与 [../Understanding_Data_Governance/00-总览与阅读地图.md](../Understanding_Data_Governance/00-总览与阅读地图.md) 的「治理要可被验证」论点互为表里（实链互挂，义务 A）。

## 1.5 数据可观测性不是什么（⚠️ 归纳，防误读三则）

1. **不是数据质量工具的改名**：质量规则枚举「已知该查什么」；观测要求覆盖「没想到的坏法」，两者互补不互替。修复侧纵深见 [../数据清洗.md](../数据清洗.md)。
2. **不是端到端监控仪表盘**：仪表盘是行动面的呈现层；只有信号采集没有推断模型，仍是监控而非观测。
3. **不是血缘图谱的又一代销**：血缘在本书是支柱之一（静态登记 + 动态影响分析），服务于「定位与止损」，图谱本身不是目的。血缘技术纵深实链 [../数据血缘分析原理与实践.md](../数据血缘分析原理与实践.md)。

## 1.7 案例推演：一张高管周报为什么会错（⚠️ 转述重构的教例，非原书案例原文）

时间线（周一 09:30，管理层看到 GMV 周环比骤降 40%）：

1. **T-26h**：上游支付库做分库迁移，采集作业的源表指向旧分片——作业没报错，因为它还在「成功」读一张不再增长的表。
2. **T-2h**：`mart.order_daily` 数据停更。传统监控（作业成功率、资源水位）全部绿色，因为「作业成功 ≠ 数据前进」。
3. **T+0**：分析师手工对账 40 分钟定位到 mart 层；但为什么 mart 没涨、源头哪里变了，仍无链可查。
4. **T+3h**：跨团队拉群考古，才追到迁移工单。

观测框架下的同一条时间线（⚠️ 按五支柱推演）：

- **Freshness**（02 章 G1 原型）：`events/fx` 类表的滞后在 SLA 24h 内突破阈值即告警，压缩检测段 26h→<1h。
- **Monitoring**（G2/G4）：行数 z-score 断崖（G4 原型第 5 天 −3.7σ 形态）在停更首日即触发次级信号。
- **Lineage**（G3）：从 `mart.order_daily` 一跳反查上游 `stg.orders`，再一跳定位 `raw.payments` 采集作业，压缩定位段 3h→分钟级。
- **Documentation**：负责人字段 + 消费方列表让告警直达采集 owner，压缩协作段。
- **Alerting**：带影响面（下游 6 节点，G3 原型口径）与冷却去重的通知，避免「炸群后没人管」。

结论：观测体系的价值不在「多报警」，而在把 **MTTD/MTTR 两个时长**系统性压缩——这是后续各章一切工程化的度量母题（⚠️ 归纳）。

## 1.9 小结与迁移问题

本章把「为什么」讲完：链路、团队、消费者三股力量使数据资产进入「运行时不可自证」不可持续的状态。留给下一章的迁移问题是：**一个数据资产要在运行时自证健康，至少要登记哪些信息、采集哪些信号**——即五支柱的组件学拆解（[02-数据可观测性的构成要素.md](02-数据可观测性的构成要素.md)）。

## 核心概念速览（中英对照）

- **数据可观测性** — Data Observability：数据资产在运行时可被推断其内部健康状态的能力。
- **可观测性** — Observability：源自控制论，由输出推断系统状态的能力；软件域落地为指标/日志/追踪。
- **未知的未知** — Unknown Unknowns：没被预先写成规则的数据故障形态，观测框架的核心覆盖对象。
- **运行信号** — Runtime Signals：时效、量、分布、模式等可持续采集的数据侧观测输入。
- **数据信任** — Data Trust：观测的最终产品——消费者敢于自助使用数据。
- **数据栈复杂度** — Data Stack Complexity：链路变长导致故障定位成本超线性的结构性问题。
- **停更** — Staleness：数据未按承诺节奏更新的运行态故障，时效支柱的第一检测对象。
- **数据事故** — Data Incident：坏数据抵达消费点造成后果的事件；观测目标为压缩其检测与止损时长。
- **MLOps/AI 消费面** — AI-era Consumption：LLM 与特征系统直接消费数据使坏数据代价自动化放大（译载「AI 障碍」节 ✅）。
- **信号-推断-行动三构件** — Signal / Inference / Action Facet：本目录为讲清观测结构提出的归纳框架（⚠️ 笔者归纳）。
- **数据质量 vs 观测** — Data Quality vs Observability：规则枚举的「已知该查」与运行推断的「没想到的坏」互补。
- **主动元数据** — Active Metadata：运行信号回灌元数据层驱动自动化，与目录谱系汇合点。

## 最新演进与工业实践

- **概念主流化（2022–2026）**：数据可观测性从创业公司营销词进入分析平台词典；Gartner 系规划指南类文章在中文技术社区转引（⚠️ 未取一手报告，不作数字引用）。
- **与 LLM 的双向交汇**：观测信号成为上下文喂给生成式助手做「自然语言排障」；同时 LLM 应用自身催生出「LLM 可观测性」新品类（Tracing/评估），与本书谱系平行不混同——软件侧追踪对照 [../Database_Reliability_Engineering/00-总览与阅读地图.md](../Database_Reliability_Engineering/00-总览与阅读地图.md)。
