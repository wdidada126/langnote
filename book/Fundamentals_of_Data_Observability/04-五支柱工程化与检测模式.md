## 4.0 最小观测栈的五张表（工程起手式）

把 02 章五支柱翻译存储层，最小闭环只需要五张元数据表（🔧 本目录原型即按此结构建表跑通）：

```
tables_reg (tbl PK, sla_hours)              -- 登记簿：谁、承诺什么
snaps      (tbl, snap_ts, row_count, max_updated)  -- 体检流水：每次快照一行
cols       (snap, tbl, col, dtype, nullable)        -- 模式快照：漂移比对底料
lineage    (src, dst, job)                          -- 血缘边：影响/根因双向展开
alert_rule (rule, tbl, op, thr, cooldown_h)         -- 规则表：阈值与冷却
```

设计要点（⚠️ 归纳）：**只存观测元数据、不复制业务数据**——观测栈的存储成本与隐私半径由此被压到最小；`snaps` 追加式写入天然形成审计史。

## 4.1 Freshness 工程化：SLA 判定与心跳模式（🔧 G1）

原型方法：6 表登记、14 天 × 小时快照（2016 行），2 表注入停更；判定式 `(julianday(snap_ts) − julianday(max_updated)) * 24 > sla_hours`。

- 输出：违约快照行 **185**（events_hourly 94、audit_log 91），两表最大滞后 **95.0h**。
- 工程语义：**快照行 ≠ 告警**。185 行是「证据流」，需 24h 冷却窗折叠成少数持续违约事件（G4 机制）。
- 慢变表补心跳：dim_product 类表 `max_updated` 常年不动是正常态，改由「水位登记」判定（最近一次作业成功完成时间单独成列）。
- 反模式：只监控 ETL 作业成功率——1.7 案例（[01-数据可观测性导论.md](01-数据可观测性导论.md)）中「成功的空转」全部绿色。

## 4.2 Schema 工程化：快照 diff 与兼容演化（🔧 G2）

方法：列元数据两期全量快照（2026-08-01 计 11 列 → 2026-09-01 计 13 列），`EXCEPT` 求增删、同名列 join 比对类型：

- 检出 **3 起漂移**：`orders.coupon_code`（新增）、`users.phone`（新增）、`orders.amount` REAL→DOUBLE（改型）。
- 分级：新增可空列 ≈ 低风险（通知）；改型/删列 = 破坏性（门禁 + 告警），下游消费方清单由 G3 血缘现算。
- SQL 兼容演化口径对照（⚠️ 转述）：「禁止原地改型、加新列迁移双写」类规约在各治理手册通行；本原型证明**仅靠两期 INFORMATION_SCHEMA 快照即可自动检出违规**，不需要解析全部转换 SQL——解析式方案精度换成本，登记式方案反之，生产常混合。
- 入发布门禁：diff 结果非空 ⇒ 阻断部署（3.5 节合流点的可执行形态）。

## 4.3 Lineage 工程化：登记式起步、解析式升级（🔧 G3）

- 9 边小图 + `WITH RECURSIVE` 即完成影响分析（`stg.orders` → 6 下游节点）。SQLite 递归 CTE 在此充当图引擎的最小替身——生产图库/目录产品做的是同一件事的放大版（对位 [../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md](../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md) 05 血缘章、[../数据血缘分析原理与实践.md](../数据血缘分析原理与实践.md)）。
- 覆盖率优先于精度：先把「作业 → 输入/输出表」登记全（G3 结构），列级解析按投诉热点补（⚠️ 实践判断）。
- 环检测：递归展开须用 `UNION`（去重）防血缘环死循环——原型即此写法；SQLite 无原生传递闭包约束，工程上另设最大深度参数（⚠️ 归纳）。
- 血缘事件化：变更事件（谁、何时、动了哪条边）应与边表分离追加存储，供事后审计回放（⚠️ 归纳）。

## 4.4 Alerting 工程化：规则表、基线与降噪（🔧 G4）

方法：`orders` 日行数 90 天序列，前 14 天为基线（均值 μ₀/标准差 σ₀），规则 `|z|>3` 触发、24h 冷却：

- 注入 5 处异常全部命中：09-13（+3.6σ）、10-02（−3.6σ）、10-23（+3.4σ）、10-29（+3.4σ）、11-17（−3.7σ）；冷却后告警数 **5**（本例异常彼此间隔 >24h，「不漏」成立；同刻多表连锁故障的「不多」需相关性聚合，见下）。
- 基线窗口是超参而非真理：14 天短窗对周季节性敏感，生产需按指标形态选窗口/季节性模型（⚠️ 转述）。
- 降噪三件套：同源冷却（G4 实现）、风暴聚合（沿 G3 血缘把上游故障的下游伴生告警折叠为一条根告警）、认领超时升级（2.6/3.7 节 RACI）。
- 规则即数据：`alert_rule` 表让阈值可版本化、可评审、可按表继承默认——比散在平台配置里的规则更接近「运行合同」语义（⚠️ 归纳）。

## 4.5 Documentation 工程化：从登记簿自动生成

- 表级文档骨架（负责人、SLA、最近体检结论、下游影响面）全部可由四张运行表 join 生成（⚠️ 方法归纳）：G1 的滞后、G2 的漂移史、G3 的影响集就是「活文档」的数据源——这即「主动元数据」的最小可运行形态。
- 与目录产品的分工再强调：本册原型解决「生成与保鲜」，检索、协作、权限属目录域——[../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md](../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md)。
- 文档过期检测：把 `last_reviewed` 当 freshness 信号纳入 G1 判定框架——文档支柱与时效支柱同度量，闭环（⚠️ 归纳）。

## 4.6 端到端演练脚本（把 4.1–4.5 串成一次事故）

1. T0：`stg.orders` 上游停更 ⇒ G1 判定 lag>24h ⇒ 产 1 条 root 告警（含 G3 六节点影响清单）。
2. T0+α：迁移作业顺手改了列型 ⇒ G2 diff 报 retyped ⇒ 告警合并进 root（血缘同源折叠）。
3. T1：`mart.order_daily` 行数断崖 ⇒ G4 z=−3.6 ⇒ 伴生告警被风暴聚合抑制，仅计数。
4. 修复后：登记簿 `last_reviewed` 置新，G1 恢复绿色；全程 MTTD 由 G1 周期决定（小时级），MTTR 由 G3 展开速度决定（亚毫秒查询、分钟级人工决策）。
5. 复盘产出：`snaps`/`cols`/`alert_rule` 三表即事故档案，无需人肉截图归档（⚠️ 教例设计，对应 1.7 案例的正面镜像）。

## 4.7 度量观测本身

观测体系也要被观测（⚠️ 归纳）：**覆盖率**（纳管资产/全量资产）、**检出率**（先于人工上报的事故占比）、**误报率**（被驳回告警占比）、**认领时长**。四指标都可在本目录五表模型内计算——把「观测平台的元监控」留在方法层，不引任何厂商基准数字（无可核源）。

## 4.9 附录：🔧 原型核心 SQL 摘录（逐条本机跑过，SQLite 3.45.3）

```sql
-- G1 时效违约判定（julianday 差值换算小时）
SELECT s.tbl, s.snap_ts,
       (julianday(s.snap_ts)-julianday(s.max_updated))*24 AS lag_h, r.sla_hours
FROM snaps s JOIN tables_reg r USING(tbl)
WHERE (julianday(s.snap_ts)-julianday(s.max_updated))*24 > r.sla_hours;

-- G2 模式漂移三段式（增/删/改型），基于两期 cols 快照
SELECT 'added', tbl, col FROM
  (SELECT tbl,col FROM cols WHERE snap='2026-09-01'
    EXCEPT SELECT tbl,col FROM cols WHERE snap='2026-08-01')
UNION ALL
SELECT 'dropped', tbl, col FROM
  (SELECT tbl,col FROM cols WHERE snap='2026-08-01'
    EXCEPT SELECT tbl,col FROM cols WHERE snap='2026-09-01')
UNION ALL
SELECT 'retyped', a.tbl, a.col||'('||b.dtype||'->'||a.dtype||')'
FROM cols a JOIN cols b ON a.tbl=b.tbl AND a.col=b.col
WHERE a.snap='2026-09-01' AND b.snap='2026-08-01' AND a.dtype<>b.dtype;

-- G3 影响分析（正向传递展开；UNION 自带去重防环）
WITH RECURSIVE down(t) AS (
  SELECT 'stg.orders'
  UNION SELECT l.dst FROM lineage l JOIN down d ON l.src=d.t)
SELECT t FROM down WHERE t<>'stg.orders';
```

G4 的 z-score 与冷却判定在 Python 侧完成（`(v-μ₀)/σ₀` 对照 `alert_rule.thr`，`last_fire` 间隔判 `cooldown_h`）——规则留 SQL、游标留代码，是最小原型的合理分界（⚠️ 工程判断）。摘录即全部核心；完整建表与数据生成见 `proto.py`。

## 核心概念速览（中英对照）

- **最小观测栈** — Minimal Observability Stack：五张元数据表起步的自底向上路径（🔧 本章）。
- **登记式血缘** — Registration-based Lineage：作业申报输入输出的血缘采集，成本换覆盖。
- **解析式血缘** — Parse-based Lineage：SQL/运行时解析得到的血缘，精度换成本。
- **快照 diff** — Snapshot Diff：两期元数据全量比对检漂移（🔧 G2：3 起）。
- **水位登记** — Watermark/Heartbeat Registration：慢变表用作业面时间自证活跃的模式。
- **证据流 vs 告警** — Evidence vs Alert：违约快照行是证据，折叠后才是告警（🔧 G1：185 行→事件级）。
- **冷却窗口** — Cooldown：同源去重时间窗（🔧 G4：24h）。
- **风暴聚合** — Alert Storm Collapsing：沿血缘折叠伴生告警为根告警。
- **季节性基线** — Seasonal Baseline：对周内周期敏感的动态阈值形态（⚠️ 转述）。
- **规则即数据** — Rules as Data：阈值/路由以表存储，可版本化可评审。
- **活文档** — Living Documentation：由运行表 join 自动生成、随观测保鲜的文档层。
- **元监控** — Meta-monitoring：对观测体系自身覆盖率/误报率的度量（4.7）。
- **破坏性变更** — Breaking Change：删列/改型级漂移，须门禁阻断（🔧 G2 分级）。
- **传递闭包** — Transitive Closure：血缘可达集的图论名；SQLite 以递归 CTE 近似（🔧 G3）。

## 最新演进与工业实践

- **原型到产品的距离**：本章五表模型与商业观测平台的公开信息架构（元数据库 + 规则 + 通知管道）同构；差异在规模工程（多租户、采集代理、成本护栏）（⚠️ 判断句，未引具体厂商文档）。
- **dbt 生态位**：以测试 + 文档 + 语义层为中心的 dbt 线（#163/#173 登记第 6 波预备池，不链）事实上覆盖了 G2/文档支柱与部分 G4，freshness/血缘需外接平台——2024–2026 开源数据栈的常见拼装（⚠️ 综述）。
- **事件标准**：血缘与体检结论的事件化（OpenLineage 类）使 4.3 的「血缘事件化」从 bespoke 变成可采购件（⚠️ 转述，URL 可达性未核故不附）。
- **AI 辅助阈值**：静态 z-score 基线正被自动选窗/多变量异常检测替代的演示遍布厂商材料；本目录坚持先跑通 G4 式可解释基线，再谈黑盒（⚠️ 方法论立场）。
