## 1.1 一切从「问题」开始（It Starts with a Question）

本书开篇的立场不是「NoSQL 更好」，而是**「先问数据长什么样、查询长什么样，再选存储」**。作者把这条方法论拆成四个必答问题（贯穿每库每章）：

1. **数据模型**：实体如何表示——固定列的表？自包含的文档？带类型的边？稀疏的行-列簇？键到值？
2. **读写模式**：访问是「点查/聚合/多跳遍历/范围扫描」中的哪一种？谁是热路径？
3. **一致性诉求**：需要 ACID 强一致，还是可用最终一致换可用性与分区容错（CAP）？
4. **扩展方式**：靠垂直扩展 + 成熟索引，还是水平分片 + 数据模型迁就？

> ⚠️ 转述：这四问是本书「把七库塞进同一模具」的骨架，2e 序言与每库 Wrap-Up 反复回收。它们与 DDIA「数据模型 / 存储引擎 / 一致性与共识」三支柱（见 [../设计数据密集型应用/00-总览与阅读地图.md](../设计数据密集型应用/00-总览与阅读地图.md)）几乎一一对应——本册是「体验版」，DDIA 是「原理版」。

一个反直觉提醒（✅ 作者立场）：NoSQL 运动的卖点不是「抛弃 SQL / 抛弃关系」，而是「**当关系模型成为瓶颈时，存在按问题形状重排数据的可能**」。因此本书刻意把 PostgreSQL 排在最前，作为所有对比的原点——读者每学完一个 NoSQL，都被要求回头问「这事 Postgres 干不了吗」。

## 1.2 The Genres：六种数据模型家族

作者用「genre（流派）」而非「阵营」来描述 NoSQL 家族，强调**每种模型是为某类问题而生，不是要取代关系型**。本册七库落在下面五类 + 关系锚点：

| genre | 一句话抽象 | 本册代表库 | 原生强项 | 原生短板 |
| --- | --- | --- | --- | --- |
| relational | 规范化表 + 关系代数 | PostgreSQL | join、事务、约束 | 水平扩展成本、schema 迁移 |
| key-value | key→不透明 value | Redis | O(1) 点查、结构即语义 | 无二级检索、需自造索引 |
| document | 半结构化嵌套文档 | MongoDB、CouchDB | 局部读写、字段演化 | 跨文档 join 弱 |
| column-family | 行键 + 列簇 + 稀疏 | HBase、DynamoDB | 海量写、按行键范围扫 | 任意 ad-hoc 查询、聚合 |
| graph | 节点 + 带类型边 | Neo4j | 多跳遍历、关系即一等公民 | 批量聚合分析 |

> 🔧 **genre 区分的最小语义演示（非本书引擎行为，DuckDB 1.5.5）**：把「关系 join」与「文档嵌套展开」两种建模放同一 SQL 引擎里对比，可直观看到两类模型的数据流差异。
> - 关系路径（join 后聚合）：
>   ```sql
>   SELECT d.name, SUM(e.salary) FROM emp e JOIN dept d ON e.dept_id=d.id GROUP BY d.name;
>   ```
>   本机跑通：`eng=360, sales=150, hr=60`（3 部门 6 员工，✅ 数字）。
> - 文档路径（先 UNNEST 数组再聚合，模拟 `$unwind`+`$group`）：
>   ```sql
>   SELECT tag, COUNT(*) FROM (SELECT UNNEST(json_extract_string(j,'$.tags')) tag FROM docs) GROUP BY tag;
>   ```
>   本机 3 文档跑通：`y=3, x=2, z=1`（✅）。同一「统计出现次数」的问题，关系模型先 join 再分组、文档模型先展平再分组——这就是 genre 的「手感差」。
> - 声明：DuckDB 不是 MongoDB，此处只复现「展开-聚合」的**语义**，不代表 Mongo 的真实执行/存储。

## 1.3 关系型为何仍坐在桌边

2e 把 PostgreSQL 列为七库之首（「Onward and Upward」一节承认：多数 NoSQL 的对照系仍是关系型）。要点（⚠️ 转述）：
- 关系型不是「过时」，而是「默认正确答案」——除非问题明显落到文档/图/宽列/键值的形状里。
- 现代 PG 早已把「JSON 文档、全文检索、地理」等 NoSQL 卖点吸收进自己（见 02 章演进节），本册把它当「锚点」用来校准其它模型。

### 练习题（Exercises）传统

每库 Wrap-Up 附三类练习（✅ 由官方「每 Day 后设练习」的体例反推，题面 ⚠️ 转述）：
1. **巩固题**：把该库某 Day 的命令换成本人领域的数据重跑一遍。
2. **跨库题**：用另一库给本库加速——典型如「拿 Redis 当 PostgreSQL/MongoDB 的读缓存」「把 Neo4j 的关系查询结果物化回 Postgres」。
3. **思辨题**：本库在 CAP 里站哪一边、schema 迁移痛在哪。
> 跨库题是本书区别于「单库手册」的灵魂：它强迫读者在模型间来回搬运数据，形成立体直觉。本目录每章末「最新演进」会标注这些手法在 2026 的对应工程形态（如 CQRS、缓存旁路、物化视图、polyglot persistence）。

## 1.6 genre 决策树（把 1.2 变成可执行）

作者的四问落成一条「先问形状」的粗决策链（⚠️ 综合全书 Wrap-Up 口径外推，非原书逐字）：

1. 需要**任意 ad-hoc join + 事务**？→ 关系（PostgreSQL，02 章）。
2. 关系即数据、要**多跳遍历/推荐/网络**？→ 图（Neo4j，06 章）。
3. 数据**天生嵌套、字段常变、读写以整体文档为单位**？→ 文档（MongoDB 04 / CouchDB 05）。
4. **海量写入、按主键范围扫、列可稀疏**？→ 宽列（HBase 03 / DynamoDB 07）。
5. 只做**低延迟点查 + 缓存/计数/排行**？→ 键值（Redis，08 章）。
6. 以上不互斥 → **混合架构**：Redis 作缓存、Postgres 作真相、按读路径加文档/宽列（每库 Wrap-Up 都鼓励这种组合）。

> 🔧 **key-value 无内建检索的语义演示（非本书引擎行为，SQLite 3.45.3）**：把 Redis 的 hash 类比成一张 `(key, field, value)` 表，「按 field 条件查」需要自造索引——本机建 `kv(k TEXT,f TEXT,v TEXT)` 灌 1 万行（`f` 取 50 个离散值），直接 `SELECT count(*) WHERE f='f7'` 是**全表扫描**：命中 200 行、耗时 **0.00054s**；加 `CREATE INDEX ix ON kv(f)` 后同查询仍 200 行、降到 **0.00006s**（约 9×）。这正是 Redis「value 不透明、二级索引要自己在 set/zset 上拼」的 SQL 侧影。声明：SQLite 不是 Redis，此处复现的是「无索引即全扫」的**语义**，非 Redis 内存结构行为。

## 1.9 「genre 直觉」速记卡（读引擎章前先建锚）

用一句「它把什么当一等公民」记住每类模型，后续读 02–08 时反复回扣：
- 关系：**表与约束**为一等——一切皆可 join、皆可 CHECK。
- 键值：**key 与原子命令**为一等——value 越 opaque 越快。
- 文档：**自包含对象**为一等——一次读写一个完整实体。
- 宽列：**行键与列簇局部性**为一等——按 key 范围扫最省。
- 图：**关系/边**为一等——连接本身可命名、可遍历、可带权。

> 提示（⚠️ 作者语气转述）：新手最大误区是「拿最熟的模型硬套所有问题」（关系原教旨 or NoSQL 万能论）。本书的解药就是这一页速记卡——**先看数据长什么样，再决定谁是一等公民**。

## 核心概念速览（中英对照）

- **数据模型** — data model：实体与关系的形式化表示方式，本书按 genre 分五类。
- **流派 / genre** — genre：作者对 NoSQL 家族的称呼，强调「为问题而生」而非「派系」。
- **键值存储** — key-value store：key→不透明 value，无内建检索语义。
- **文档模型** — document model：自描述嵌套结构，弱化跨文档 join。
- **列簇** — column family：行键 + 稀疏列组的宽列抽象（BigTable 谱系）。
- **图模型** — graph model：节点与带类型边为一等公民，遍历优先。
- **CRUD** — create/read/update/delete：每库 Day1 的最小操作集。
- **OLTP / OLAP** — 事务型 / 分析型：本册偏 OLTP，分析型让位列存引擎。
- **分片 / 复制** — sharding / replication：水平扩展与高可用的两条正交轴。
- **选型四问** — modeling/access/consistency/scaling：贯穿全书的提问框架。
- **锚点** — relational anchor：以 PostgreSQL 校准其它模型的对照系。

## 最新演进与工业实践

- **「genre」叙事的当下形态**：2018 年的六类到 2026 已被「多模数据库（multi-model）」吸收——单引擎同时提供关系/文档/图/向量接口（如 PG + pgvector + JSONB、Azure Cosmos DB 多 API 层）。本册「先问形状再选库」的方法论反而更重要：模型在收敛，问题形状没收敛。
- **向量成为新 genre**：本册未含向量检索；今天向量索引已是独立一类，纵深见 [../Vector_Databases/00-总览与阅读地图.md](../Vector_Databases/00-总览与阅读地图.md)，与 RAG/Embedding 生态绑定。
- **时序与湖仓外溢**：宽列/键值的很多「海量写」场景迁向时序库（[../Time_Series_Databases/00-总览与阅读地图.md](../Time_Series_Databases/00-总览与阅读地图.md)）与 Iceberg/Delta 湖仓（[../设计数据密集型应用/00-总览与阅读地图.md](../设计数据密集型应用/00-总览与阅读地图.md) 的 OLAP 部分延伸）。
