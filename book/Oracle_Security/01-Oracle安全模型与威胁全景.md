# 01 Oracle 安全模型与威胁全景（主题重构章）

> 本章为**主题重构**（原书 TOC 不可达，见 [00 降级声明](00-总览与阅读地图.md)）。Oracle 侧论述全部 ⚠️ 公开文档/社区通识转述，非原书文本、不可本机实测。

## 1.1 为什么"Oracle 安全"是一个独立学科

2001 年前后的现实是：Oracle 数据库大量从内网信任域被直接推到互联网（dot-com 时代的 e-Business Suite 浪），而 DBA 知识体系里"性能"有专书、"备份"有专书、"安全"却散落在官方 Security Guide 的角落。Theriault & Heney 这本 O'Reilly 册（✅ 书目实存，见 00 元数据表）填补的正是这个空档：**把 Oracle 安全当成一门有模型、有清单、有工具的独立工程学科来讲**，而不是 DBA 手册的附录章。

体裁上它是"第三方视角"的：作者不代言厂商默认配置，通篇基调是"厂商为了兼容性给了你一堆危险的默认值，现在逐个数出来"。这个基调决定了本册与 [../CISSP认证考试指南.md](../CISSP认证考试指南.md) 的分工：CISSP 给领域无关的 AAA/纵深防御框架，本册给 Oracle 引擎内的逐参数落点。

## 1.2 共享责任模型：Oracle 到底替你做了什么

⚠️ 转述（8i/9i Security Guide 口径）：Oracle 数据库内核提供的是**机制**（mechanism）而非**策略**（policy）——

- 提供认证通道（口令/OS/外部/SSL/Kerberos），但不强制你启用哪个；
- 提供权限/角色系统，但 `CONNECT`/`RESOURCE` 这类预定义角色把"能用"与"能干"混装（03 章专辩）；
- 提供审计设施，但 `AUDIT_TRAIL` 默认 NONE——**出厂即失明**是最重的合规雷；
- 提供网络层，但监听器默认接受任意远程注册与连接（06 章）。

推论：Oracle 的"安全默认值"在 2001 语境≈"什么都不关"，安全责任几乎全压在部署者身上。这正是与 MySQL 匿名账户、PostgreSQL pg_hba 信任行并立的三大开源/商用"默认裸奔"史 Case 之一（对照阅读：../数据库系列·总索引.md 内各引擎安装章）。

## 1.4 审计者视角的方法论（本书体裁的独有价值）

⚠️ 重构自本书"第三方指南"体裁与同期社区书评通说：

1. **先清单后配置**：拿检查单（版本号、参数、授权语句、账户状态）而不是拿手册逐页读；
2. **以视图为证据源**：一切体检最终落为若干字典视图查询的导出件（见 04 章）——这使得"字典可读面"本身成为审计权的载体；
3. **区分机制缺陷与配置缺陷**：前者等厂商补丁（08 章），后者当场可修（02/03/05 章）；
4. **把兼容性当风险记账**：Oracle 的多数危险来自向后兼容（O7_DICTIONARY_ACCESSIBILITY、CONNECT 旧语义），审计者要逐项确认兼容性开关是否还在为不存在的老应用服务。

## 1.6 六个流传甚广的神话（第三方视角开章破题）

⚠️ 重构自本册"不代言厂商"体裁与同期社区清算通说：

1. **"Oracle 是最安全的数据库，开箱即用"**——混淆"可选件丰富"与"默认安全"；1.2 已逐条拆穿；
2. **"上了防火墙就安全"**——06 章：合法通道（应用服务器→DB）永远开着，攻击走的是业务端口；
3. **"DBA 会审计一切"**——05 章：审计默认关闭，且审计者自身是最大盲区对象；
4. **"加密=安全"**——07 章：加密只回答"盘上不可读"，不回答"谁有权读"；
5. **"内网可信"**——02 章 OS 信任域+1.3 合法用户威胁：多数 Oracle 事故从信任侧发起；
6. **"厂商没通知就没有漏洞"**——08 章：告警时代以月计的暴露窗，通知机制本身是漏洞放大器。

破神话的共同句式：**机制存在 ≠ 策略生效 ≠ 有人值守**。这三段论是全书八章的公理层。

| 同一动作 | CBOF 读法 | TOP2e 读法 | 本册读法 |
|---|---|---|---|
| 查 `DBA_TAB_PRIVS` | — | — | 授权账本取证 |
| 看 `V$SESSION` | 共享池效应侧窗 | 等待采样入口 | 会话归因（谁！） |
| 读字典列统计 | 选择度输入 | 计划突变嫌疑人 | 敏感列暴露面 |
| 跑一条重查询 | 成本模型解剖对象 | 诊断对象 | **审计事件源** |

## 1.8 本章自测（三问）

1. 说出 Oracle"机制/策略分离"在审计与网络两层的各一个"有机制无策略"实例（答：AUDIT_TRAIL=NONE；监听器默认无管控）；
2. 攻击面八类中，哪两类是"合法身份"通道？（越权滥用与注入）；
3. 为何预定义角色名不能出现在审计报告结论里？（语义随版本漂移，3.2 表为证）。

## 核心概念速览（中英对照）

- **共享责任模型** — shared responsibility model：内核给机制、部署者给策略，Oracle 默认值≈全开。
- **攻击面** — attack surface：认证/授权/字典/审计/网络/存储/补丁/应用八类，本册分章即其投影。
- **机制与策略分离** — mechanism vs. policy：同一开关可服务十种策略，评估以策略符合性为准。
- **默认裸奔** — insecure by default：8i/9i 时代 AUDIT_TRAIL=NONE、监听器无口令的总称。
- **兼容性风险** — backward-compatibility risk：O7_* 参数、CONNECT 旧语义等"为老应用留的后门"。
- **第三方视角** — third-party/auditor view：不代言厂商，按检查单逐项取证的体裁。
- **最小权限** — least privilege：只授予达成业务目的的最小权限集，03 章主题。
- **纵深防御** — defense in depth：网络+认证+授权+审计+加密逐层独立失效可容忍。
- **合法用户威胁** — insider/legitimate-user threat：注入与内鬼都以合法身份行动，防线退化到授权+审计。
- **预定义角色** — predefined role：CONNECT/RESOURCE/DBA 等出厂角色，历史包袱集中营。
- **选件安全** — cost-gated security：ASO/Data Vault 等收费选件造成的"知道但买不起"断层。
- **安全双线** — offense/defense pairing：本册（守方）与 #51 DBHH（攻方）互为正反面。
- **证据源视图** — evidence-by-view：体检报告=字典视图导出件，字典可读面即审计权。
- **补丁空窗** — patch exposure window：漏洞公布与补丁到位之间的可被利用区间。
- **威胁建模** — threat modeling：先枚举资产与对手再选控制，01 章方法论总纲。

## 最新演进与工业实践

- **版本与机制演进**：12c 引入统一审计与容器级分离、19c 成默认长期支持线、23ai/26ai 延续（⚠️ 以 Oracle 官方 Database Security Guide 当前版为准；本环境 docs.oracle.com 具体链接未能逐一 curl 验证，官网检索可重放）。2001 年"出厂失明"的最大单项修复是 23 时代默认开启统一审计选项的方向性变化（⚠️ 通说转述）。
- **合规驱动**：等保 2.0、GDPR、金融行业规范把"AUDIT_TRAIL 默认值"从厂商兼容问题变成法定问题；Oracle 侧 CIS Benchmark for Oracle Database 成为检查单工业化形态（⚠️ 名称与存在通识，未链）。
- **攻方镜像**：本册威胁面表在 #51 DBHH（2007）中逐条有利用代码对应；2010 年代后同类知识转入商业 DBSCA/DAF 等扫描器与红队剧本（⚠️ 通说）。
- **开源对照**：PostgreSQL pg_hba 默认拒绝、MySQL validate_password 插件等"默认收紧"路线，反过来印证 1.2 节的共享责任批评已被行业消化。
