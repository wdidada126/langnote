# 02 集群管理（豆瓣实抓章题：第2章 集群管理；原书英文章题未实证 ⚠️）

> 书目：Spark: Big Data Cluster Computing in Production（Wiley, 2016, ISBN 978-1-119-25401-0，Ilya Ganelin/Ema Orhian/Kai Sasasaki/Brennonn York 著）。
> 精读重构声明：章题 ✅ 豆瓣 27053289 目录栏实抓；本章小节全部为 ⚠️ 推定讲解域（依 DNB 副题「Big Data Cluster Computing in Production」语义、作者团队 DC/OS 任职背景与公开官方文档），非原书文本。总纲见 [00-总览与阅读地图](00-总览与阅读地图.md)。

## 1. 本章地位：全书枢纽

216 页小书里，「集群管理」独占一章且是副题的直接落点：Spark 把「资源从哪来」抽象成可插拔的 ClusterManager 接口，于是**同一引擎可跑在四种底座上**——这是本书存在的理由，也是它与所有 API 向 Spark 书的分野（分工三角见 [00-总览与阅读地图](00-总览与阅读地图.md) §4）。

## 2. ⚠️ 推定小节 A：Standalone——最小可用集群

- 架构：master（Leader/Standby + 应用管理器）+ worker（按核/内存切槽位）。语义基准 https://spark.apache.org/docs/latest/cluster-overview.html（✅ 200 预检）。
- 2016 生产评价：简单、故障域小、**无队列/无多租户/无资源优先级**——本书视角下它是「对照组」而非生产答案 ⚠️。
- 存活现状：仍是官方一等公民、单租户分析小集群与教学首选（官方 docs 线 ✅）。

## 3. ⚠️ 推定小节 B：YARN——Hadoop 系企业的事实答案

- 模型：ResourceManager + NodeManager；Spark 作业=一个 YARN Application，executor=Container；队列/容量/优先级由 YARN 侧治理。文档基准 https://hadoop.apache.org/docs/stable/hadoop-yarn/hadoop-yarn-site/YARN.html（✅ 200 预检）；作业级调度语义 https://spark.apache.org/docs/latest/job-scheduling.html（✅ 200 预检）。
- 生产要点：`spark.yarn.*` 系列参数（配置名录 ✅ 见 https://spark.apache.org/docs/latest/configuration.html）；driver 默认活在 AM Container 内=cluster 模式，提交机可下线；Kerberos 域内作业要票据转发——第 4 章安全域的 YARN 侧接口 ⚠️。
- 背景册：Hadoop/YARN 生态本体见 [bigdata·hadoop](../../bigdata/hadoop.md)（在盘 ✅ 已验名）。
- 2026 回看：YARN 仍是存量私有域主力，但「新集群选型」已大面积转向 K8s（方向 ⚠️，无本会话实证 URL 支撑不引具体报告）。

## 4. ⚠️ 推定小节 C：Mesosphere DC/OS（Mesos 系）——作者阵营与本书时代烙印

- 作者团队（DNB ✅ GND 实抓四人）与 Mesosphere 生态强关联：本书是**市面少见的 DC/OS 生产向 Spark 运维文本**，这是它的史料价值，也是它 2020 年后商业生命力的天花板。
- 模型：Marathon 应用框架 + 资源要约（offers）；Spark 经 mesos scheduler 接入；DC/OS 提供统一控制面、服务发现与多租户 ⚠️（依 2016 公开文档域转述）。
- 判决性事实（✅ 官方可查线）：Mesos 的 Spark framework 随社区退出主流；DC/OS 产品线其后亦停止商业推进（细节 ⚠️ 本会话未取到可达官方公告 URL，只作方向陈述，不引臆测链接）。
- 对读：2016 年「YARN vs Mesos」路线之争的胜负，今天看由**Kubernetes 终结**——读本章要把 Mesos 段落当「调度系统多样性」的标本而非待选项。

## 5. ⚠️ 推定小节 D：Kubernetes——章末预言位（若原书有，属 ⚠️）

Spark-on-K8s 的支持随 SPARK-18276（Kubernetes backend）进入主线（提案号属公开 JIRA 常识，本会话未预检 JIRA URL → ⚠️ 不展开单号语义）；K8s 侧扩展生态基准 https://kubernetes.io/docs/concepts/cluster-administration/addons/（✅ 200 预检）。生产形态：executor 即 Pod、driver 双模式、无队列需配合 Volcano/quotas 类方案 ⚠️（标题级，未引未验链接）。

## 6. 🔧 实测（DuckDB/SQLite 类比·非本书 Spark 引擎行为）

**底座生命周期表（本目录整理 ⚠️ 年代为量级断言，不逐月考据）**：

| 底座 | 2016（本书） | 2020s | 备注 |
|---|---|---|---|
| Standalone | 存在 | 仍一等公民 | 教学/小集群 ✅ 官方 docs |
| YARN | 事实标准 | 私有存量主力 | Hadoop 重资产惯性 |
| Mesos/DC-OS | 作者主推 | **退场** | framework 移除方向 ⚠️ 见文末 |
| Kubernetes | 前夜 | 新增主流 | ✅ addons 文档域 |

**🔧 实测组 3（单写者资源仲裁=调度器串行瓶颈，SQLite 3.45.3 WAL）**：方法——`PRAGMA journal_mode=WAL` 库上并发起 4 线程、每线程 50 次 INSERT、连接 timeout=0.05s；结果：**成功线程 1 个、`database is locked` 报错 3 个，墙钟 0.17s，落库 50 行**（脚本 `dbwave_w8_spwiley` 内可复跑）。
类比：**「全局唯一仲裁者 + 高冲突提交」时，吞吐由仲裁串行度而非算力决定**——正如 YARN RM 单点时代大集群「提交风暴」下 Container 分配排队；WAL 只解读者阻塞、不解写写互斥，恰似资源管理器加缓存不改变「一个授权点」的本质。
⚠️ 边界：SQLite 无容器/队列概念，本组仅类比「串行授权者=瓶颈」这一结构，**非本书 Spark 引擎行为**。

**🔧 实测组 4（底座损坏下的消费方可存活，DuckDB 1.5.5 read_only）**：方法——对**不存在**的库文件 `duckdb.connect('exp4_ro.duckdb', read_only=True)`；结果：`IOException: Cannot open database ... in read-only mode: database does not exist`——只读打开把「底座缺失」变成**显式启动错误**而非静默新建。另：`exp3.db` 文件头 16 字节=`SQLite format 3\x00` 明文魔数、无任何认证即可读出全部行（对照组，安全域见 `04-安全.md`）。
类比：**计算框架（只读客户端）与底座（数据库/集群管理器）的故障边界要在提交期就划清**——对应 Spark driver 启动时对 RM/Master 可达性的强依赖；⚠️ **非本书 Spark 引擎行为**。

## 7. 本章要点回收

1. 本书的「集群管理」不是 K8s 教程，而是**把 Spark 的 manager 抽象层讲透**：换底座=换一组 `spark.*` 参数+一组运维假设。
2. 读 2016 文本的正确姿势：YARN 段学「治理模型」（队列/优先级/票据），Mesos 段看「已亡路线的优良设计」，K8s 结果由 00 §5 演进节补完。
3. 与调度语义的姊妹题（作业间资源抢占/fair scheduler）在官方 job-scheduling 文档域（✅ 200 预检）；引擎侧执行语义一律回指 [Spark_The_Definitive_Guide·00总览](../Spark_The_Definitive_Guide/00-总览与阅读地图.md)。

## 8. 选型决策树（⚠️ 2016 语境复原 + 2026 覆写层）

2016 版（本书语境 ⚠️ 推定）：
- 已有 Hadoop 重资产 → YARN（治理成熟，一条队到底）。
- 混合负载（长跑服务+批）且信新栈 → DC/OS/Mesos（作者阵营答案；2026 已退场）。
- 纯 Spark 小团队 → Standalone（够用即正义）。
- 从零建且押注容器 → K8s（当时属前瞻 ⚠️）。

2026 覆写版（据 00 §9/文末演进节证据）：
- 存量 YARN：继续跑，升级窗口做双轨。
- 新增集群：K8s 单轨，Mesos 系**禁止入选项**（产品停摆，02 §4）。
- 托管优先：合规允许时直接云服务（安全面随之外包，见 `04-安全.md` 演进节）。

## 核心概念速览（中英对照）

- **集群管理器** — Cluster Manager：给应用分配容器/槽位的底座抽象，本书题眼。
- **资源管理器** — ResourceManager（YARN RM）：全局唯一授权点；🔧 组 3 的串行瓶颈类比对象。
- **容器** — Container：底座侧的资源配额单位，Spark executor 的宿主。
- **队列** — Queue（YARN）：多租户治理原语：容量/上限/调度策略挂点。
- **要约机制** — Offers（Mesos 系）：底座把空闲资源「报价」、框架决定接不接的两阶段分配。
- **应用框架** — Framework/Application（Mesos 语境）：经 scheduler 接入底座的计算系统本体。
- **调度策略** — FIFO/Capacity/Fair：RM 侧作业排序哲学，企业治理的核心开关。
- **部署模式** — client/cluster Deploy Mode：driver 落点选择=故障归属与网络暴露面选择。
- **动态分配** — Dynamic Allocation（`spark.dynamicAllocation.*`，配置名 ✅ 官方文档）：executor 随负载伸缩，队列友好特性 ⚠️ 2.0 时代渐成熟。
- **命名空间** — Namespace（K8s）：后日之「队列」，多租户与 quota 载体 ⚠️。
- **服务发现** — Service Discovery（DC/OS 卖点）：作业间互访寻址，2016 时代差异化功能 ⚠️。
- **底座抽象层** — SchedulerBackend SPI：Spark 可插拔接入管理器的代码缝——本书全部对比的成立前提。
