## 2. Catalog Explorer：治理的 UI 入口（§1）

Catalog Explorer 是 Databricks 工作区中浏览 UC 资产的 UI 组件，提供：
- 浏览 catalog → schema → table/volume/function 层级
- 查看表详情：列定义、分区信息、存储位置、所有者
- 查看血缘：上游表 → 当前表 → 下游表/笔记本/仪表板
- 预览数据：直接查看前 1000 行（受 SELECT 特权控制）
- 搜索与过滤：按名称/描述/类型/所有者/标签搜索

## 3. 自动血缘追踪（§2）

Unity Catalog 自动追踪以下类型的血缘：

| 血缘类型 | 触发条件 | 记录内容 |
| --- | --- | --- |
| **表级血缘** | CREATE TABLE AS SELECT / INSERT INTO | 源表 → 目标表 |
| **列级血缘** | 同上（更细粒度） | 源列 → 目标列 |
| **管道血缘** | DLT (Delta Live Tables) 管道 | 管道节点间的依赖 |
| **笔记本血缘** | 笔记本中执行写操作 | 笔记本 → 写入的表 |
| **仪表板血缘** | Lakeview 仪表板查询表 | 仪表板 → 读取的表 |

血缘示例：`raw_data.landing.events` → (DLT) → `analytics.finance.events_clean`
→ (notebook) → `analytics.finance.revenue`；同时 `events` → (DLT) →
`analytics.marketing.event_metrics`。

✅ 关键事实：
- 血缘信息存储在 UC metastore 中，不可手动编辑
- 通过 Catalog Explorer UI 或 System Tables 查询
- 血缘追踪跨工作区（只要共享同一 metastore）
- 支持查看列级血缘（哪个源列影响了哪个目标列）

## 4. 搜索与发现（§3）

UC 的搜索能力包括：

1. **全文搜索**：在 Catalog Explorer 中按名称/描述搜索
2. **标签（Tags）**：
   - 系统标签：自动添加（如 `data_classification`）
   - 自定义标签：用户/管理员手动添加
   - 标签传播：部分标签可从 catalog 传播到 schema 到 table
3. **业务术语**：将表/列与业务词汇关联（如"收入"="revenue"）
4. **数据分类**：自动检测敏感信息（PII、金融数据等）

⚠️ 转述：搜索与发现是数据治理的"前端"——没有发现能力，治理规则
再完善也无法被数据消费者使用。

## 5. 数据产品化与 Domain 归属（§4）

在 Data Mesh 语境下（参见 [../Data_Mesh/00-总览与阅读地图.md](../Data_Mesh/00-总览与阅读地图.md)），
UC 的 catalog 层可以映射为 **domain 边界**：

| Data Mesh 概念 | UC 实现 |
| --- | --- |
| Domain | Catalog |
| Data Product | Schema + Tables + Volumes |
| Self-serve Platform | UC + Databricks Workspace |
| Federated Governance | UC Metastore 统一策略 |

⚠️ 这是概念映射，不是 UC 的官方定位。UC 本身不声称自己是 Data Mesh 实现。

## 6. 🔧 DuckDB 模拟血缘邻接表（§5）

> ⚠️ **非本书引擎/平台行为**：以下演示用 DuckDB 1.5.5 模拟 Unity Catalog
> 的血缘存储结构（邻接表），仅做机制类比。

```python
import duckdb

con = duckdb.connect()

# 创建血缘邻接表（模拟 UC 的血缘存储）
con.execute("""
    CREATE TABLE lineage_edges (
        source_catalog TEXT,
        source_schema TEXT,
        source_table TEXT,
        target_catalog TEXT,
        target_schema TEXT,
        target_table TEXT,
        edge_type TEXT,  -- 'table', 'column', 'pipeline', 'notebook'
        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    )
""")

# 插入血缘关系
con.execute("""
    INSERT INTO lineage_edges VALUES
    ('raw_data', 'landing', 'events',
     'analytics', 'finance', 'events_clean',
     'pipeline', CURRENT_TIMESTAMP),
    ('analytics', 'finance', 'events_clean',
     'analytics', 'finance', 'revenue',
     'notebook', CURRENT_TIMESTAMP),
    ('raw_data', 'landing', 'events',
     'analytics', 'marketing', 'event_metrics',
     'pipeline', CURRENT_TIMESTAMP)
""")

# 创建列级血缘表
con.execute("""
    CREATE TABLE column_lineage (
        source_table TEXT, source_column TEXT,
        target_table TEXT, target_column TEXT,
        transform TEXT  -- 'direct', 'aggregation', 'filter', 'join'
    )
""")
con.execute("""
    INSERT INTO column_lineage VALUES
    ('raw_data.landing.events', 'event_id',
     'analytics.finance.events_clean', 'event_id', 'direct'),
    ('raw_data.landing.events', 'amount',
     'analytics.finance.revenue', 'total_revenue', 'aggregation'),
    ('raw_data.landing.events', 'campaign_id',
     'analytics.marketing.event_metrics', 'campaign', 'direct')
""")

# 查询上游血缘（谁产生了这张表？）
upstream = con.execute("""
    SELECT source_catalog || '.' || source_schema || '.' || source_table AS source
    FROM lineage_edges
    WHERE target_table = 'revenue'
""").fetchall()
print(f"revenue 的上游: {upstream}")
# [('analytics.finance.events_clean',)]

# 查询下游血缘（这张表被谁消费？）
downstream = con.execute("""
    SELECT target_catalog || '.' || target_schema || '.' || target_table AS target
    FROM lineage_edges
    WHERE source_table = 'events'
""").fetchall()
print(f"events 的下游: {downstream}")
# [('analytics.finance.events_clean',), ('analytics.marketing.event_metrics',)]

# 查询完整血缘链（递归）
chain = con.execute("""
    WITH RECURSIVE lineage_chain AS (
        SELECT source_table AS node, target_table AS next_node, 1 AS depth
        FROM lineage_edges WHERE source_table = 'events'
        UNION ALL
        SELECT lc.next_node, le.target_table, lc.depth + 1
        FROM lineage_chain lc
        JOIN lineage_edges le ON lc.next_node = le.source_table
    )
    SELECT * FROM lineage_chain
""").fetchall()
print(f"完整血缘链: {chain}")

con.close()
```

## 核心概念速览（中英对照）

| 中文 | English | 一句话 |
| --- | --- | --- |
| 目录浏览器 | Catalog Explorer | UC 资产的 UI 导航与搜索入口 |
| 数据血缘 | Data Lineage | 数据从源到目标的完整流转路径 |
| 列级血缘 | Column-level Lineage | 精确到列的数据流转追踪 |
| 标签 | Tag / Custom Tag | 附加在 securable 上的元数据标记 |
| 数据分类 | Data Classification | 自动检测敏感信息类型 |
| 数据产品 | Data Product | 以领域为导向的可复用数据资产集合 |

## 最新演进与工业实践

- **2025**：UC 血缘扩展到 AI 资产——ML 模型训练所使用的表、函数调用链
  均可追踪。⚠️ 转述自 Databricks 博客。
- **OpenLineage 集成**：UC 血缘可与 OpenLineage 标准互操作，允许外部
  编排工具（Airflow、Dagster）注入血缘信息。✅ docs.databricks.com。
- **对标**：Apache Atlas 是传统血缘方案（Hadoop 生态），UC 血缘是其
  云原生替代，优势在于自动性和与 Databricks 的深度集成。
- **趋势**：血缘从"合规工具"转向"影响分析工具"——变更前评估"改这张表
  会影响谁"，比事后审计更有价值。
