## 2. 多工作区架构模式（§1）

企业通常有多个 Databricks 工作区（dev / staging / prod / 各业务线），
UC 的多工作区治理有两种主要模式：

**模式 A：单 Metastore 多工作区（推荐）**
Account → Metastore (us-east-1) → WS-dev / WS-staging / WS-prod。
优点：治理统一、血缘完整、权限一致。缺点：单点故障、跨区域延迟。

**模式 B：多 Metastore 联邦**
Account → Metastore US (us-east-1) + Metastore EU (eu-west-1)，
跨 metastore 共享通过 Delta Sharing。
优点：数据驻留合规（GDPR）、区域隔离。缺点：治理分散、需手动同步权限。

✅ 关键事实（docs.databricks.com/en/data-governance/unity-catalog/best-practices）：
- 推荐模式 A（单 metastore）除非有数据驻留要求
- 工作区绑定 metastore 通过 `ALTER WORKSPACE ... SET METASTORE` 命令
- 一个工作区只能绑定一个 metastore（但一个 metastore 可服务多个工作区）

## 3. 从 HMS 迁移到 UC（§2）

迁移路径（✅ docs.databricks.com）：

| 阶段 | 操作 | 风险 |
| --- | --- | --- |
| **1. 评估** | 盘点工作区级 HMS 资产 | 无 |
| **2. 启用 UC** | 账户级启用 Unity Catalog | 无（不影响现有 HMS） |
| **3. 升级表** | `ALTER TABLE ... SET TBLPROPERTIES ('upgraded_to' = ...)` | 低 |
| **4. 迁移权限** | 将 HMS GRANT 映射到 UC GRANT | 中（权限模型差异） |
| **5. 切换工作区** | 工作区绑定 UC metastore | 高（需停机窗口） |
| **6. 验证** | 对比 HMS 与 UC 的查询结果 | 低 |
| **7. 清理** | 移除旧 HMS 绑定 | 无 |

⚠️ 转述：迁移的最大挑战不是技术而是**权限映射**——
HMS 的权限模型（database-level GRANT）与 UC 的三层模型
（catalog.schema.object）不完全对应，需要重新设计权限策略。

互链：Ch02 架构（[02-Unity-Catalog架构与命名空间.md](02-Unity-Catalog架构与命名空间.md)）
详述了三层命名空间与 HMS 两层模型的结构差异。

## 4. CI/CD 与治理即代码（§3）

UC 治理配置可通过基础设施即代码（IaC）自动化：

**Terraform 示例**（⚠️ 转述自 Databricks Terraform provider 文档）：
```hcl
resource "databricks_catalog" "analytics" {
  name         = "analytics"
  metastore_id = databricks_metastore.main.id
}
resource "databricks_grants" "finance_team" {
  catalog = databricks_catalog.analytics.name
  grant {
    principal  = "data-team"
    privileges = ["USE_CATALOG", "CREATE_SCHEMA"]
  }
}
```

✅ 关键实践：治理配置纳入 Git → CI/CD 自动部署 → 生产变更需 PR 审批。

## 5. 多云与跨区域部署（§4）

| 部署模式 | 说明 | 适用场景 |
| --- | --- | --- |
| **单云单区域** | 一个 metastore，一个云 | 中小企业，单一市场 |
| **单云多区域** | 多个 metastore，同一云 | 数据驻留要求 |
| **多云** | 多个 metastore，不同云 | 全球化企业 |
| **混合** | UC + 外部 catalog 联邦 | 混合云架构 |

⚠️ 转述：多云部署的挑战在于：
- 存储凭证不跨云（AWS IAM Role ≠ Azure Managed Identity）
- External Location 需在各云分别配置
- Delta Sharing 可跨云但需网络连通性

## 6. 🔧 DuckDB 模拟多工作区权限继承（§5）

> ⚠️ **非本书引擎/平台行为**：以下演示用 DuckDB 1.5.5 模拟
> 多工作区共享同一 metastore 时的权限继承，仅做机制类比。

```python
import duckdb

con = duckdb.connect()
con.execute("ATTACH ':memory:' AS metastore")

# 模拟工作区绑定
con.execute("""CREATE TABLE workspace_bindings (
    workspace TEXT PRIMARY KEY, metastore_id TEXT, environment TEXT)""")
con.execute("""INSERT INTO workspace_bindings VALUES
    ('ws-dev', 'ms-001', 'development'),
    ('ws-staging', 'ms-001', 'staging'),
    ('ws-prod', 'ms-001', 'production')""")

# 模拟 UC 权限
con.execute("""CREATE TABLE uc_grants (
    principal TEXT, object_name TEXT, privilege TEXT)""")
con.execute("""INSERT INTO uc_grants VALUES
    ('data-engineers', 'analytics', 'USE_CATALOG'),
    ('data-engineers', 'analytics.finance', 'CREATE_TABLE'),
    ('analysts', 'analytics', 'USE_CATALOG'),
    ('analysts', 'analytics.finance.revenue', 'SELECT')""")

# 模拟工作区成员
con.execute("""CREATE TABLE workspace_users (
    user_email TEXT, workspace TEXT, role TEXT)""")
con.execute("""INSERT INTO workspace_users VALUES
    ('alice@co.com', 'ws-dev', 'data-engineers'),
    ('bob@co.com', 'ws-prod', 'analysts')""")

# 查询有效权限
result = con.execute("""
    SELECT u.workspace, g.object_name, g.privilege
    FROM workspace_users u JOIN uc_grants g ON u.role = g.principal
    WHERE u.user_email = 'alice@co.com'
""").fetchall()
print(f"alice 权限: {result}")

# 跨工作区一致性验证
cross = con.execute("""
    SELECT w.workspace, g.object_name, g.privilege
    FROM workspace_bindings w CROSS JOIN uc_grants g
    WHERE g.principal = 'analysts' ORDER BY w.workspace
""").fetchall()
print(f"analysts 跨工作区: {cross}")
con.close()
```

## 最新演进与工业实践

- **2025**：Databricks 推出 **Unity Catalog CLI** 增强版，支持批量权限审计、
  权限差异检测（dev vs prod）。⚠️ 转述自 Databricks 文档更新。
- **Terraform Provider**：databricks Terraform provider 已支持 UC 全部
  资源类型（catalog/schema/table/grant/share/recipient）。✅ registry.terraform.io。
- **对标**：AWS Lake Formation 的多账户治理通过 RAM（Resource Access Manager）
  实现；Azure Purview 提供跨工作区的统一治理视图。
- **趋势**：治理从"手动配置"转向"GitOps"——所有治理变更通过 PR 审批，
  自动部署到 dev/staging/prod 工作区，类似 Kubernetes 的 GitOps 模式。
- **最佳实践**：生产工作区的 metastore 应启用**删除保护**（deletion protection），
  防止意外删除导致治理元数据丢失。
