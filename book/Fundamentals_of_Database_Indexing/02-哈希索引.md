# 02 · 哈希索引（Part II — Hashing）

> 对应原书 Part II「Low-Dimensional Index Structures」下章 Hashing（pp.15–31）。✅ 章名/页码取自 Crossref。哈希是"0 维空间"的索引：它不保留任何顺序，只把键随机散布到桶中，因此**只支持精确匹配**——这既是它 O(1) 点查的来源，也是它无法服务 range 的原因。本章精读重构静态哈希、动态/可扩展哈希与桶溢出策略，并以 🔧 校准"点查极快、范围无能为力"的直觉。

## 1. 哈希索引的基本契约

给定哈希函数 `h: Key → {0,…,B-1}`，键 k 存于桶 `h(k)`。查询 `k=?` 时算一次 `h(k)` 直达桶，期望 O(1)。

- **前提**：判据是相等。`h` 把"相等"保留为"同桶"，但把"接近"（k±1）完全打散——这就是 range 失效的根源。
- **代价模型**：以**访问桶数（≈磁盘 I/O 次数）** 计，而非 CPU 比较；本书 Part I 的"结构好坏看 I/O"在此首次兑现。
- **负载因子（load factor）λ**：已存条目 / 桶容量。λ 越接近 1，冲突越多；哈希索引全部技巧都在"控制 λ 与冲突"。

## 2. 静态哈希与其痛点

静态哈希桶数 B 固定。数据增长 → λ 上升 → 溢出链变长 → 点查退化。传统解法：溢出桶（overflow bucket）串成链，但链一长就丢掉了 O(1)。

- **闭链法（closed / open addressing）**：冲突项就近放邻近槽，扫描探测；删除留墓碑。
- **开链法（separate chaining）**：每桶挂链表，溢出挂新链节。

静态哈希的问题本质是"预知的桶数"，与"未来的数据量"不匹配。

## 3. 动态 / 可扩展哈希（⚠️ 转述经典）

为让桶数随数据伸缩，两类方案：

- **可扩展哈希（extendible hashing）**：维护一张**目录（directory）**，按键哈希值低位索引到桶；桶满且局部深度=全局深度时**分裂桶 + 倍增目录**（倍增只需复制目录指针，不改数据）。目录是"可伸缩的间接层"。
- **线性哈希（linear hashing）**：不用目录，用"下一个待分裂桶指针 + 分裂相位"，按序逐个桶分裂，负载超过阈值即提前分裂一个桶。优点：目录常驻内存的压力消失，适合无界增长。

两者共同点：把"哈希=定长数组"松绑为"哈希=可按位渐进精化的映射"，从而维持近似 O(1) 点查 + 可控 λ。

## 4. 哈希 vs 树：一次说清（连 03/04 章）

| 维度 | 哈希索引 | B+树索引（04 章） |
|---|---|---|
| 支持判据 | 仅等值 `=`、`IN` | 等值 + 范围 + 有序 + Top-k |
| 点查 | 期望 O(1) | O(log_f N)，f 为扇出 |
| 范围查询 | ❌ 不支持 | ✅ 叶链有序 |
| 顺序遍历 | ❌ | ✅ |
| 冲突/平衡维护 | 分裂/溢出 | 节点分裂/合并 |
| 高维相似检索 | ❌ | ❌（另需度量结构，见 06） |

一句话：**哈希是"牺牲全部顺序换常数点查"的极端点**；一旦 workload 含范围/排序，就必须上序结构（03/04）。

## 5. 哈希与相似检索的接口（为什么本书仍讲它）

高维相似检索里，哈希并未退场，而是改头换面为 **LSH（局部敏感哈希）**：设计 `h` 使"距离近的向量大概率同桶"，与传统哈希"仅相等同桶"正相反。这是本书 Part I"一切皆空间检索"伏笔在高维的回收（详见 08/09 章近似检索）。⚠️ 原书 Hashing 章未展开 LSH（早于 LSH 普及），此处为衔接 2026 现状补充，标明非本章原文。

## 6. 🔧 实测：哈希式点查 vs 序扫（非本书引擎行为）

SQLite/DuckDB 的常规二级索引都是 B+树/ART，非纯哈希表；本节用"点查"验证哈希最擅长的场景，并演示 DuckDB ART（前缀树式）在点查上"存在但不总被采纳"的反直觉现象。

🔧 G1（SQLite 3.45.3，2M 行内存表）：`SELECT v FROM t WHERE k=1234567` 重复 200 次——
- 无索引：**22149.0 ms**（每次全表 SCAN）
- 建 B+树索引 `ix_t_k(k)` 后：**1.2 ms**（`EXPLAIN QUERY PLAN`：`SEARCH t USING INDEX ix_t_k (k=?)`）
- 加速比 ≈ **18000×**，对应"等值直达"理想哈希契约在序结构上的近似达成（B+树点查≈log_f N，2M 行 f≈数百，仅 2–3 层）。

🔧 G5（SQLite，500k 行、1000 个不同键 → 每键约 500 重复）：非唯一索引点查 ×100 共 **41.5 ms**。因一个 `k=?` 命中 ~500 条，B+树需在叶内做小范围序扫——这解释了"哈希只存唯一/低重复键最划算；高重复度下序结构的叶内扫更稳"。

🔧 G3（DuckDB 1.5.5，2M 行）：建 ART 索引 `CREATE INDEX art_k ON t(k)` 后跑点查 ×30，从 38.8ms 降到 17.6ms，但 `EXPLAIN` 显示计划仍是 **SEQ_SCAN**（`Filters: k=1234567`）——DuckDB 的分析型优化器在单表点查上未走 ART。这是"索引存在 ≠ 索引被用"的活例，呼应本书"结构服务于查询判据"的核心：错误的查询形态下，再好的结构也不被调用。数字登记于 [00-总览与阅读地图.md](00-总览与阅读地图.md) §7。

## 7. 工程要点与坑（⚠️）

- 哈希索引对 `ORDER BY`、`>`、`<`、`LIKE 'abc%'`、`BETWEEN` 一律不帮忙；误建哈希索引后 range 仍全扫。
- 内存哈希（如引擎 buffer 内 hash join 的构建表）与磁盘哈希索引是两回事，前者生命周期仅一条查询。
- 哈希函数质量决定冲突分布：坏 `h` → 长溢出链 → 退化到线性扫描，等于没索引。
- 动态哈希的分裂是"突发"的（个别插入触发桶复制），会制造写放大尖峰，做性能画像时勿只看均摊 O(1)。

## 6.5 哈希函数选型与冲突（工程决定成败）

前述 O(1) 全都建立在"均匀散列"假设上，一旦 `h` 有偏，冲突链拉长，哈希索引退化成链表。选型要点（⚠️ 精读梳理）：

- **除法散列 `h(k)=k mod m`**：简单，但 m 取质数、且避开 2 的幂（否则低位分布不均）。
- **乘法散列（Fibonacci/Multiplicative）**：`(k·A) mod 1` 取小数部分，A 取黄金比例共轭，对连续键散得均匀——本文 🔧 里用 `(i*2654435761)%N`（Knuth 乘法常数）即此思路。
- **位混列 / Murmur / xxHash**：现代工程默认，雪崩效应强、把相邻键彻底打散，代价是算术复杂。
- **对"键位分布"的依赖**：可扩展/线性哈希用键哈希值的**低位**选桶，高位用于分裂精化——这解释了 §3 的"倍增目录"为何只多复制指针、不动数据。

## 6.6 目录·局部深度·分裂时序（把 §3 讲透）

可扩展哈希的**全局深度 g** 决定目录大小（`2^g` 个目录项），**局部深度 l** 决定某桶实际用了几位哈希。

- 插入落到桶 `b`，若 b 未满：直接写，λ 上升。
- 若 b 满且 `l_b < g`：只分裂 b（拆成两个桶，各自 `l_b+1`），更新指向 b 的那批目录项——**不动其它桶**，写放大局部。
- 若 b 满且 `l_b = g`：目录倍增（`g+1`）、再分裂 b——这是唯一"全局"动作，摊还后仍常数。

线性哈希则用"指针 next 指向下一个待分裂桶 + 相位 bit"，把"何时分裂"从"被动溢出"改成"主动按 λ 阈值提前分裂"，避免目录常驻内存的开销，适合键空间无界。**两者的分裂都是突发的**，做延迟画像要盯 p99 而非均值（呼应 §7 坑）。

## 6.7 哈希的两处"非索引"用法（别混淆）

本章讲"哈希索引（持久结构）"，但工程里哈希更常出现在两处，须区分：

- **Hash Join 的哈希表**：查询执行期的临时结构，对连接键建内存哈希，另一侧探针——生命周期仅一条查询，不是磁盘索引。它与本书"哈希只服务等值"的结论同源：hash join 也只做等值连接，`<`/`BETWEEN` 连接不能用它。
- **内存引擎 / 自适应哈希索引（AHI）**：某些引擎对热点页自动建哈希以加速等值点查，本质是"在 B+树之上盖一层哈希快捷方式"（见最新演进节 InnoDB AHI）。

理解这两处能解释 §7 的坑：为何"建了哈希索引范围查询仍慢"——因为 range 需要顺序，而这三处哈希（含 join）都只保留"相等同桶"、彻底丢弃顺序。

## 核心概念速览（中英对照）

- **哈希索引** — Hash index：以哈希函数把键映射到桶、仅支持等值检索的 O(1) 结构。
- **负载因子** — Load factor：已存条目/桶容量，衡量拥挤与冲突概率。
- **桶溢出** — Bucket overflow：桶满后追加溢出链/溢出桶，损害点查常数性。
- **开链法** — Separate chaining：每桶挂冲突链表。
- **开放寻址** — Open addressing：冲突项就近占邻近槽。
- **可扩展哈希** — Extendible hashing：用目录按哈希低位间接到桶，按需倍增目录。
- **线性哈希** — Linear hashing：无目录，按序逐桶分裂应对无界增长。
- **目录** — Directory：可扩展哈希中可倍增的间接指针数组。
- **局部/全局深度** — Local/global depth：决定桶能否分裂的哈希位数。
- **LSH** — Locality-Sensitive Hashing：使"近邻大概率同桶"的反向哈希，服务近似相似检索（本书后续/2026 补充）。
- **写放大** — Write amplification：分裂/复制导致的额外写 I/O。
- **哈希连接** — Hash join：等值连接时对构建侧建内存哈希、探测侧逐行查——同样只服务等值、不服务范围（呼应 §7）。
- **哈希函数质量** — Hash function quality：雪崩/均匀性决定冲突分布，坏函数使哈希索引退化到线性。
- **Hash Join** — 执行期对连接键建临时哈希表做等值连接，非持久索引。
- **自适应哈希索引** — Adaptive Hash Index：在 B+树之上为热点页自动加建的等值哈希快捷层。

## 最新演进与工业实践

- **纯哈希索引在通用 RDBMS 中罕见**：MySQL InnoDB 的 HASH 索引仅在 Memory/自适应哈希（Adaptive Hash Index, AHI）中出现，且只服务等值；范围优化器仍走 B+树。⚠️（转述，以 dev.mysql.com InnoDB AHI 文档为准）
- **DuckDB 不建哈希索引**：其 ART（Adaptive Radix Tree）+ 轻量 zone-map 承担主要加速，点查甚至不被 ART 采纳（🔧 G3 实测 SEQ_SCAN）——说明现代列存更信"扫描 + SIMD + min/max 剪枝"而非逐键索引。✅ 本机实测（非本书引擎）。
- **LSH / 哈希族主导近似最近邻**：2024–2026 向量检索工业方案（如各向量库的 IVF/LSH 索引、MinHash/SimHash 去重）本质是"可控冲突的动态哈希"在高维的延伸。⚠️ 趋势判断。
