# 04 · 磁盘层次索引结构（Part III — Disk-Based / Hierarchical Structures）

> 对应原书 Part III「Disk-Based Index Structures」分部标题页（p.59）与章 Hierarchical Structures（pp.61–91）。✅ 章名/页码取自 Crossref。这是全书最"落地"的一章：把内存序结构（03）放进"以页为 I/O 单位"的现实，得到 **B 树 / B+树 / B*树 / UB 树**家族——也就是几乎所有关系数据库的默认索引。本章的代价单位是**磁盘访问次数**，不是 CPU 比较。

## 1. 为什么内存树到了磁盘就不行

03 章的二叉树每节点只存 1 个键、2 个孩子。磁盘 I/O 以页（4–16KB）为单位，若一页只放得下一个节点，则一次查找要付 `O(log₂ N)` 次页读；N=2^24 就要 24 次 I/O。自平衡树"矮胖"不起来，因为它扇出恒为 2。

**关键洞察**：既然一页能装很多字节，就让一个节点装**尽可能多的键（大扇出 f）**，把树"压扁"到 2–4 层。B 树正是"高扇出的多路平衡搜索树"。

## 2. B 树 / B+树 定义（⚠️ 精读重构标准定义）

设最小度数 t（阶 m=2t 或 t，依流派）：

- **B 树**：每内节点存 1..(2t-1) 个键、2..2t 个孩子；键与数据可散布于所有层。
- **B+树**：**数据只存叶子层**；内节点仅作"分隔键 + 孩子指针"的索引；叶子层用链表横向串联（有序叶链）。

B+树胜出的三点工程理由：
1. 内节点不存数据 → 同页能塞更多分隔键 → **扇出更大、树更矮** → I/O 更少。
2. 叶子横向链表 → **范围查询/有序遍历顺叶链走**，无需回树（呼应 03 章 range 能力）。
3. 数据全在叶子 → 每次查找走**等长根到叶路径**，I/O 可预测。

## 3. 高度与扇出的定量关系（本章硬结论）

若一页可容纳 `f` 个孩子指针，则高度 h 的 B+树最多存约 `f^h` 条记录。反过来：

```
h ≈ ⌈log_f (N)⌉    （点查最坏 I/O 次数，根通常常驻内存则再 −1）
f ≈ 页大小 / 子指针大小
```

例：16KB 页、6 字节指针 → f≈2700。则 2700²≈729 万条记录 → h=2（含内存根）；2700³≈197 亿 → h=3。**这解释了为什么十亿行表点查也只要 3–4 次 I/O**——B+树扇出之大，使树"几乎永远只有三四层"。这也是为什么更高扇出反而不划算：扇出越大，内节点分裂/查找内扫描的成本上升，最优扇出落在"一页装得下"的边界。

## 4. 插入 / 分裂 / 删除与"局部性"

- **插入**：定位到叶子，若满则**分裂成两叶、向父上推一个分隔键**，父若满继续分裂，可能长高一层。分裂是"自底向上、突发"的，是写放大来源。
- **B*树 / 填充因子**：分裂前先尝试与**兄弟节点再分配**（redistribution），只有兄弟也满才分裂 → 提高节点填充率、减少分裂频率，代价是更多兄弟访问。
- **UB 树（Universal B-tree）**：用"分裂时一次拆成 k 个孩子"的通用分裂，把 B 树家族（2-way）与 B* 统一，追求更高空间利用率。⚠️ 概念转述。
- **删除**：叶子下溢时向兄弟**借键**或与兄弟**合并**，合并可能级联到父、使树缩短。

## 5. 变体一览（本书枚举的层次家族）

| 变体 | 特征 | 解决的问题 |
|---|---|---|
| B 树 | 数据散布各层 | 命中靠上层键时提前返回 |
| B+树 | 数据全在叶、叶链有序 | 范围/遍历 + 高扇出（默认选择） |
| B*树 | 兄弟再分配后再分裂（2/3 填充） | 提升空间利用、降分裂频率 |
| UB 树 | 通用 k-way 分裂 | 统一并最大化填充因子 |
| 前缀压缩 B+ | 分隔键压缩公共前缀 | 单页容纳更多键（升扇出） |

## 6. 🔧 实测：B+树点查与范围（非本书引擎行为）

SQLite 的索引即 B+树，是本族最直观的活标本。以下为 SQLite 3.45.3 单线程内存表实测（数字登记于 [00-总览与阅读地图.md](00-总览与阅读地图.md) §7）。

🔧 **G1 点查**（2M 行，等值 `k=1234567` ×200）：
- 无索引：**22149.0 ms**（每次 `SCAN t` 全表）。
- 建 B+树 `ix_t_k(k)` 后：**1.2 ms**，`EXPLAIN QUERY PLAN` = `SEARCH t USING INDEX ix_t_k (k=?)`。
- 加速 ≈ **18000×**；对应树高仅 2–3 层的"log_f N 次跳跃"。

🔧 **G2 范围**（2M 行，`k BETWEEN 1000 AND 60000` ×50）：
- 有 B+树：**130.6 ms**（`SEARCH ... (k>? AND k<?)`，跳叶 + 顺有序叶链）。
- 无索引：实测 **6058.7 ms**（全表扫描）。→ 约 **46×**，兑现"B+树叶链支持范围"（见 03 章对照）。

🔧 **G5 高重复键**（500k 行、1000 distinct → 每键 ~500 条）：非唯一索引点查 ×100 共 **41.5 ms**。因单 `k=?` 命中 ~500 叶项，B+树在叶内做小段序扫——印证"非唯一列的 B+树点查实为微型 range"，也解释了为何极高重复度下 B+树优势收窄（此时哈希/位图思路更省）。

> 方法学：三组均 `time.perf_counter()` 墙钟毫秒、`:memory:` 库以隔离磁盘噪声（故测的是"结构选择路径"而非真 I/O 延迟）；换用文件库时绝对值上升但相对关系不变。**均非本书引擎（Bhattacharya 理论不绑定 DBMS）行为**，仅作代价模型直觉校准。

## 7. 与相似检索的接口（承上启下）

B+树是**1 维序结构**的极致：它假设键可全序比较。一旦要索引多维点（图像特征向量、地理坐标），"左小右大"不再良定义——于是需要 Part IV/V 的度量与空间结构（R 树是其"把 B+树搬到 2D 包围盒"的近亲，见 06/08）。⚠️ 本节为过渡，原书 Hierarchical 章聚焦 1 维。

## 8. 常见误区（⚠️）

- "索引越多查询越快"：每个 B+树都要在 INSERT/UPDATE/DELETE 时维护（分裂/合并），写放大随行数累积；本书代价观提醒"索引是读快换写慢"。
- "B+树高度会随数据长高"：因扇出数千，十亿行仍 3–4 层；树高不是性能主因，**是否命中、是否回表、叶链走向**才是。
- "范围查询也 O(log N)"：B+树定位是 O(log_f N)，但**返回 K 条要再付 O(K) 叶访问**，大范围命中仍可能不如全扫（优化器的选择性判断，见 04 姊妹链接）。

## 6.5 一页到底装多少键：一个可复算的算例

设页 16KB（16384B）。内节点每个"分隔键 + 子指针"若为 8B 指针 + 8B 键 = 16B，则扇出 `f ≈ 16384/16 ≈ 1024`（再扣除节点头开销，实际取 900–1000）。于是：

- 高度 2（内存根 + 1 层磁盘内节点 + 叶）：可寻 `≈ f² ≈ 百万~百万级` 叶。
- 每叶若存 `64B` 一条记录，则一页装 `16384/64 ≈ 256` 条叶记录。
- 合计可承载记录数 ≈ `f · (叶记录/页) · 叶页数`，量级轻松上亿，而点查路径长度 = 3 次页读。

结论：**B+树用"大扇出 + 数据沉叶"两个杠杆，把"亿级数据的点查 I/O"钉死在个位数**——这是它压倒二叉树（log₂ 1e8 ≈ 27 次）的根本原因。

## 6.6 聚簇索引 vs 二级索引 / 覆盖索引（承 03→工程）

- **聚簇（clustered）**：叶子直接是"整行数据"，主键 B+树即表的物理顺序，范围扫叶≈顺序读数据页，最省。
- **二级（non-clustered）**：叶子只存"索引键 + 主键指针"，命中后需按主键**回表**再取整行（见术语），大范围命中会因随机回表变贵——优化器此时宁走全扫（呼应 §8 "范围也非万能"）。
- **覆盖索引（covering）**：若查询所需列**都在索引键里**，则无需回表，二级索引也能纯叶链扫完 → 本书代价观下"避免回表 = 少一半 I/O"的直接推论。

这条链解释了姊妹册反复强调的"列式复合索引让查询被索引覆盖"的几何根源。

## 6.7 B+树的维护成本与并发（写侧的隐性代价）

前述把 B+树当"读加速"，但代价模型要算全账：

- **每次写都可能触发分裂/合并**，一个插入最多沿根方向级联分裂，制造多次页写（写放大，术语已列）。
- **二级索引越多，写越贵**：一张表挂 m 个二级索引，插入一行要更新 m 棵树 → 代价近似线性于 m。这是"索引不是免费午餐"的定量版（连姊妹册的选型规则）。
- **并发**：树下降用 latch/crash-consistency（如 InnoDB 的 latching、乐观下降），分裂需锁父链，是高并发写热点来源。
- **随机 I/O 特性**：二级索引回表把顺序的表扫变成随机的点取，冷数据下这是 B+树在**大 range** 反而输给全扫的根本原因（§8）。

结论：B+树在"点查 + 选择性高的 range + 可覆盖"下最优；写密集且索引多、或大范围命中时，其优势会被维护与回表吃掉——这条判断会在 06/07 章被"选择性/重叠"以几何形式重述。

## 核心概念速览（中英对照）

- **B 树** — B-tree：高扇出多路平衡搜索树，数据可散布各层。
- **B+树** — B+tree：数据全在叶、叶链有序，关系库默认索引结构。
- **扇出（f）** — Fan-out：单内节点孩子数，≈页大小/指针大小，决定树高。
- **树高与 I/O** — Tree height ≈ ⌈log_f N⌉：B+树最坏页读次数。
- **叶子有序链** — Leaf linked list：支撑范围/有序遍历的关键设计。
- **节点分裂** — Node split：插入溢出时拆节点、上推分隔键，突发写放大来源。
- **兄弟再分配** — Redistribution：分裂前先向兄弟借/调，提升填充率（B* 树）。
- **B* 树** — B*-tree：延迟分裂 + 兄弟再分配，节点至少 2/3 填充。
- **UB 树** — Universal B-tree：k-way 通用分裂，统一 B/B*、最大化空间利用。
- **回表** — Table lookback：二级索引命中后取整行，B+树二级索引固有成本。
- **LSM 树** — Log-Structured Merge tree：B+树的写优化表亲，内存有序+顺序刷盘+分层合并。

## 最新演进与工业实践

- **B+树依旧是 OLTP 索引基石**：InnoDB 主键即聚簇 B+树、二级索引为"叶含主键"的 B+树；PostgreSQL 默认 GiST/B-tree 亦属此家族。⚠️（转述，以 dev.mysql.com / postgresql.org 文档为准）
- **列存/向量化引擎"轻索引重扫描"**：DuckDB、ClickHouse 类引擎倾向以 zone-map（min/max）、SIMD 全扫 + 低基数字典取代海量 B+树，因分析型大 range 下 B+树叶回表代价高。🔧 本机 DuckDB 建 ART 后点查仍走 SEQ_SCAN（见 02/08 章），侧面印证"OLAP 不迷信索引"。✅ 实测（非本书引擎）。
