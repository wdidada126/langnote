## 9.2 事务日志与检查点： durability 的两条腿

- 提交先写 WAL（`dbms.transaction.logs.*`），页面异步刷盘；
- `006-checkpoint`：检查点把内存页推下盘、允许日志截断——**日志截断滞后 = 磁盘膨胀**的经典运维事故源；
- `005-20k-random`：2 万随机写制造可观测的日志/页面活动，供随后 kill 演示铺垫。

## 9.3 🔪→🔧 崩溃恢复实验（书内实验，本目录不可复现 ⚠️）

脚本序列 `007-pid-find → 008-kill-neo4j → 009-start-neo4j`：

1. 写入进行中取 PID，`kill -9`；
2. 重启后按 WAL 回放至最近检查点；
3. 断言：已提交事务全存活、未提交全蒸发（ACID-D 的演示版）。

注意：**这是“书里能做、这里只转述”的实验**——Neo4j 不装不跑，本目录以 ⚠️ 标注转述性质。DuckDB 侧同构概念（WAL+checkpoint）可按 [../DuckDB_Up_and_Running/00-总览与阅读地图.md](../DuckDB_Up_and_Running/00-总览与阅读地图.md) 与 [../Database_Internals/00-总览与阅读地图.md](../Database_Internals/00-总览与阅读地图.md) 互证，不冒充 Neo4j 行为。

## 9.4 备份家族全谱（010–014）

```
neo4j-admin database backup --to-destination ... --database playlists   # 在线拉取
  --incremental                # 增量：只传自上次以来的日志段
neo4j-admin database restore --from=... --overwrite-destination        # 恢复到停机库
```

- 备份需要 Enterprise 许可（社区版无 `backup` 命令）⚠️ 转述官方文档惯例；
- `014-cloud-backup`：2025.x 起 “cloud backup”（对象存储快照）成官方通道——`neo4j-admin database backup` 的正统后继；
- 恢复即全库粒度：没有“单表回滚”这种东西，与 Ch.8 暂存库策略互为因果（先恢复到旁路库验证再切换）。

备份策略三问（本章纪律 ⚠️ 重构）：RPO 多大（增量频率）？测试过恢复吗（restore 演练脚本的存在就是答案）？异地/对象存储在哪（014）？

## 9.9 运维参数速查（本章 neo4j.conf ✅ 配套；参数族名转述 ⚠️，逐项以手册为准）

| 参数族 | 世界观 | 配错的可见症状 |
|---|---|---|
| heap（`server.memory.heap.*`） | JVM 堆：事务状态/查询中间结果 | 大写入 OOM（Ch.2 导入曲线悬崖） |
| pagecache | OS 页缓存扛图记录热区，引擎不自管 buffer pool | db hits 落盘，Ch.5 全线变慢 |
| checkpoint 阈值/周期族 | 页刷盘与日志截断的节拍 | 磁盘膨胀（截断滞后）或 fsync 风暴（过密） |
| WAL 目录（`server.directories.transaction.logs.root`） | 日志独立盘位 | 与数据文件互相放大 IO |
| 备份/TLS 族 | 014 cloud backup 的凭据通道 | 备份静默失败 |

**内存配比一句话世界观**（⚠️ 转述官方口径）：heap 定死、pagecache 尽量吃满剩余物理内存——所以“Neo4j 性能问题第一步看 pagecache 命中率”，与 Ch.11 metrics 面直接对接（page_cache 指标 ✅ commands.md 实查）。

## 9.10 恢复演练脚本卡（建议季度节奏 ⚠️ 重构）

```
1. 择期：neo4j-admin database restore --from=<上周五 全量+增量> 到 staging 库
2. 校验：行数三连（Ch.2 体检清单）+ 验收查询抽样（Ch.3 清单）
3. 比对：SHOW INDEXES state / 约束完整性（Ch.4 生命周期卡）
4. 记录：实测 RPO = now - 最后增量点；实测 RTO = 演练总时长
5. 处置：DROP staging，或 CLONE 回主（001 ✅ 的正规用法）
```

没演练过的备份等于没有备份——`010→013`（备份目录→在线备份→增量→restore ✅）三连脚本就是把“等于”变成“可证明”的最小闭环；RPO/RTO 两个数字进 Ch.11 面板做趋势。

## 9.11 崩溃恢复三断言（重读注记）

`007→009` 杀库序列（✅）拆出三条各自独立的断言：①已提交即已持久——WAL 顺序回放保证；②未提交即从未发生——脏页不泄入查询可见层；③进程死≠存储坏——记录存储“先追加、后检查点”，单事务不重写历史页面。三条分别解锁三个生产决策：①让异步刷页可接受；②让应用层免重复去重；③决定备份可否单通道（日志可信才敢增量）。⚠️ 断言措辞为 WAL/checkpoint 通用语义+脚本序的重构转写，非书中原文。

三断言之外本章还给了一条沉默的工程事实（✅ 目录树）：chapter09 是全书唯一同时携带 `neo4j.conf`、shell 脚本与 Cypher 三类工件的章——存储章的读者被默认是**能碰服务器的人**，这也解释了为什么它紧跟在权限章之后的章节序列感（Ch.6→…→Ch.9 的进阶路径 ⚠️ 编排推断）。

## 9.12 store 空间账（承接 2.8 遗留项）

- 删数据≠缩文件：记录存储以 free space 链复用空洞，**磁盘占用只跟峰值走**——2.8 表最后一行的“库文件巨大”在此结账；
- 想真正还盘：整库重导（Ch.2 admin import 反向用法）或 CLONE 到空库再切换——5.x 没有“原地 compact 单文件”的银弹 ⚠️（转述口径，工具名以 current 手册为准）;
- 增长监控三件套（接 Ch.11）：逻辑计数（节点/关系数，✅ node-count 面板存在）与**物理占用**分开画——两条曲线的剪刀差就是 free space 与日志堆积的可视化。

## 核心概念速览（中英对照）

- **记录存储** — Record Store：定长节点/关系/属性记录的磁盘结构
- **计数存储** — Counting Store：维护邻居链长度与首尾指针的伴生结构
- **事务日志** — Transaction Log (WAL)：先写日志后刷页的持久化载体
- **检查点** — Checkpoint：内存页落盘并解锁日志截断的周期动作
- **崩溃恢复** — Crash Recovery：重启时按 WAL 回放至一致状态
- **在线备份** — Online Backup：neo4j-admin backup 的拉取式全库备份
- **增量备份** — Incremental Backup：仅传输日志增量的备份流
- **库克隆** — Database CLONE：多数据库实例内的整库秒级复制
- **pagecache** — Page Cache：OS 页缓存承载图数据热区，Neo4j 不自管 buffer pool
- **属性尺寸抖动** — Record Size Change：属性类型改变引发的记录重写成本
- **RPO** — Recovery Point Objective：可容忍数据丢失窗口
