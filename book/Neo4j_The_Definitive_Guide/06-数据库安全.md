## 6.1 5.x 安全模型一页图

Neo4j 5 起，安全从“企业版插件”变成内核概念，四件套（⚠️ 转述官方文档结构）：

1. **认证（Authentication）**：本地用户（`CREATE USER`）+ 可选 LDAP/SSO（企业能力）；
2. **授权（Authorization）**：角色（`CREATE ROLE`）→ 权限（`GRANT ... ON DBMS/GRAPH ... TO role`）→ 用户挂角色；
3. **多数据库边界**：`GRANT ACCESS ON DATABASE`、`GRANT READ/TRAVERSE/WRITE ... ON ELEMENT PATTERN`——权限粒度能到“标签/关系类型”级；
4. **传输与运维面**：Bolt/HTTP TLS 配置、`dbms.security.auth_enabled`、默认密码强制修改。

## 6.2 RBAC：本章的骨架

```cypher
// 示意重构（⚠️ 非仓库原文）
CREATE ROLE analyst;
GRANT TRAVERSE, READ ON GRAPH * NODES playlists.* TO analyst;
GRANT ACCESS ON DATABASE playlists TO analyst;
CREATE USER alice SET PASSWORD '...';
GRANT ROLE analyst TO alice;
```

设计纪律（重构）：

- 按**职能**建角色，不按人；按**库×元素模式**授权，不按节点实例；
- `DENY` 优先级语义明确（deny > grant），本章给“默认拒绝”白名单式授权观 ⚠️；
- 最小权限从导入账号开始：批量加载用的服务账号只应有 WRITE 元素模式，不给 `CREATE INDEX` 之外的 schema 权。

对位必读：[../Graph_Databases_2e/05-现实世界中的图.md](../Graph_Databases_2e/05-现实世界中的图.md) 的“授权与访问控制”用例把 RBAC 建模成**图本身**（用户-角色-资源边，权限=可达性查询）；本章则是**数据库内建 RBAC**——同一领域的“应用层图建模 vs 引擎层 ACL”两种实现路径，这是 GD2e 与本册最锋利的一组对照 ⚠️（对照关系为本目录判断）。

## 6.3 子图访问控制的位置

GD2e 05 章设想了“不同租户看见不同子图”的需求；Neo4j 的现行答案是**多数据库隔离 + 元素模式授权**：

- 硬隔离：一租户一库（`GRANT ACCESS ON DATABASE tenantX`）；
- 软隔离：同库内按标签/类型授权 `TRAVERSE/READ`，配合 Ch.4 的 Genre/Tag 节点化使“可视域”可被模式表达；
- 行级安全（RLS）在 2025.x 文档中仍是产品路线图议题 ⚠️（转述，未见 GA 页实抓，勿当承诺引用）。

## 6.4 内建角色与运维面

- 默认角色：`architec`/`expo rter`/`publisher`/`reader`/`writer`/`admin`（名字与能力 ⚠️ 转述自官方手册惯例，以 current 文档为准）；

## 6.7 安全初始化时序（README 换配置流 ✅ + 惯例重构 ⚠️）

交付日顺序清单（每步的动作事实/转述已在正文标注）：

1. 仅回环地址首启 → 首登强制改默认密码；
2. `CREATE ROLE importer/app_writer/app_reader/observer;`（observer ✅ 在 Ch.11 commands.md 实际使用）；
3. 逐库 `GRANT ACCESS ON DATABASE` → 逐元素模式 `GRANT TRAVERSE, READ` / `WRITE`，白名单式放量；
4. 关测试后门：`dbms.security.auth_enabled` 回 true；收紧 LOAD CSV 连接来源开关（与 Ch.2 import 目录纪律配套 ⚠️ 参数名以手册为准）；
5. 证书入 `server.directories.certificates` → Bolt/HTTP 切 TLS → 重启后仅保留加密端口面（本章 README 的改配置-重启流 ✅ 即为此设）。

## 6.8 子图权限的设计三角（重构）

“软隔离”（同库元素模式授权）要三边同时成立：

- **模型边**：可视域必须能被标签/类型的并集表达——所以 Ch.4 的 Genre/Tag 节点化是权限工程的**前置工序**；
- **查询边**：缺 TRAVERSE 的遍历是被裁断而非报错（⚠️ 转述语义），验收查询集里必须有“越界用例”——用另一个角色跑同一条 Cypher 对拍；
- **运维边**：权限变更审计走 security.log（Ch.11 ✅ 该文件在 commands.md 实读），query.log 不承担授权留痕。

与 GD2e 05 章“RBAC 建图上”的组合姿势（⚠️ 本目录判断）：引擎 RBAC 守大门（库×模式粗粒度），应用层图 RBAC 做细粒度裁决（用户-角色-资源可达性），两层裁决合并后即 Ch.13 检索时权限裁剪的前提。

## 核心概念速览（中英对照）

- **RBAC** — Role-Based Access Control：角色为中介的授权模型
- **元素模式授权** — Element Pattern Privilege：按标签/关系类型授予 TRAVERSE/READ/WRITE
- **角色** — Role：权限集合单元，5.x 起内建于内核
- **system 数据库** — System Database：管理用户/角色/数据库的元数据实例
- **认证链** — Authentication Chain：本地/LDAP/SSO 的验证顺序
- **默认拒绝** — Deny by Default：白名单式授权观
- **TRAVERSE 权限** — Traverse Privilege：图特有权限，控制“路过”能力
- **MFA** — Multi-Factor Authentication：2025.x 起内建的第二因子
- **TLS 终止面** — TLS Termination：Bolt/HTTP 的加密端口配置
- **行级安全 RLS** — Row-Level Security：按谓词过滤可见行的能力 ⚠️ 图库侧仍短板
- **最小权限账号** — Least-Privilege Service Account：导入/应用账号分轨纪律

## 最新演进与工业实践

- **MFA 与 SSO 节奏**：Neo4j 2025.06 引入 MFA 支持是社区版安全面近年最大补强 ⚠️（转述自产品博客记忆，未实抓原文页，引用请核）；Aura 侧 SSO/私网连接为默认卖点（https://neo4j.com/product/auradb/ ，200 ✅）。
- **GQL 视角**：ISO/IEC 39075 把角色与访问控制纳入语言标准讨论域，Cypher 的 `GRANT ... ON ELEMENT PATTERN` 与标准条款的映射见符合性附录（https://neo4j.com/docs/cypher-manual/current/appendix/gql-conformance/ ，200 ✅）。
- **“权限即图”的回潮**：GraphRAG 时代权限继承进检索链路（子图权限=检索域裁剪），GD2e 05 章的“RBAC 建模为图”在 2025 年后成为知识图谱权限设计的主流叙事之一 ⚠️（趋势判断）；与 Ch.13 的向量权限过滤（检索前先裁可见域）直接相关。
- **工业教训**：把“默认密码+未启用认证”列为交付前检查项是 Neo4j 托管商与自管部署的共同 SOP ⚠️ 转述。
