# 08 · Building data pipelines with DuckDB（用 DuckDB 构建数据管道）

> 覆盖原书第 8 章。目录来源：✅ Manning 官方 TOC 实抓。本章把 DuckDB 插进现代开源 ELT 栈：**dlt 摄取 → dbt 变换 → Dagster 编排**，DuckDB 在其中充当加载目标与 SQL 执行引擎。

## 内容规格（小节地图，✅ 实抓）

- **8.1 Data pipelines and the role of DuckDB**：ELT vs ETL；DuckDB 作为"轻量级仓库替身"在开发/边缘/中小数据场景承担 warehouse 角色。
- **8.2 Data ingestion with dlt**：8.2.1 dlt 项目脚手架（`dlt init`）；8.2.2 写 source/resource（`@dlt.resource`、write_disposition：append/merge/replace、primary_key→自动 SCD 处理）；8.2.3 **探索 pipeline 元数据**（`_dlt_loads`/`_dlt_pipeline_state`/`_dlt_version` 三张系统表，schema 漂移追踪）。
- **8.3 Data transformation and modeling with dbt**：8.3.1 `dbt init` + duckdb 适配器 profile（`type: duckdb`, path 指向库文件）；8.3.2 sources 声明（把 dlt 落的 raw 表声明为 source）；8.3.3 models（`SELECT` 即表/视图，物化策略 table/incremental）；8.3.4 tests（unique/not_null/singular，`dbt test`）；8.3.5 批量变换全部 CSV。
- **8.4 Orchestrating data pipelines with Dagster**：8.4.1 资产定义（`@asset`，物化即表）；8.4.2 `dagster dev` 跑图；8.4.3 资产依赖自动构图；8.4.4 资产内高级计算（DuckDB SQL/上游回查）；8.4.5 结果上传 MotherDuck。

## 核心技术清单

- dlt：Python 声明式摄取框架；destination 支持 duckdb/motherduck/bigquery…；规范化嵌套 JSON→表。
- write_disposition 语义：append（只增）、merge+primary_key（去重 upsert）、replace（快照）。
- dbt-duckdb：`profiles.yml` 里 path 既可是本地文件也 `md:`；incremental 模型走 DuckDB 事务。
- dbt 物化策略在 DuckDB 上的实现：table=CTAS/DROP+CREATE、view、ephemeral、incremental=INSERT/UPSERT（⚠️ 细节随适配器版本）。
- Dagster 资产模型：asset = 数据对象 + 计算血缘；`materialize([...])` 本地跑，Daemon 调度生产。
- 三者组合的本地闭环：dlt 落 raw → dbt 出 mart → Dagster 编排重跑/血缘可视化。

## 🔧 实测（dlt 真跑；dbt/Dagster 转述 ⚠️）

`pip install "dlt[duckdb]"` → dlt **1.30.0** 装上即用。最小管道：`@dlt.resource(name="sensors", write_disposition=..., primary_key="id")` 生成 1000 行 merge + 500 行 append 两次 `pipeline.run()`：

- run1 **9.72 s**、run2 **6.62 s**（含建库、规范化、COPY 装载、状态提交）；
- 独立打开生成的 `ch08.duckdb` 验证：`iot.sensors` **1500 行**；系统表齐备：`_dlt_loads`/`_dlt_pipeline_state`/`_dlt_version`；每行带 `_dlt_load_id`/`_dlt_id` 元数据列 ✅。
- 结论：dlt 默认把 DuckDB 文件放管道目录（非 cwd），脚本化读取要按 `pipeline.working_dir` 找。

⚠️ dbt-duckdb / Dagster 未本机实测（依赖较重、与本章"图式编排"心智无关的重复安装），以下为转述：`pip install dbt-duckdb`；profile `type: duckdb`+`path: pipelines.duckdb`；`dbt debug/dbt run/dbt test`。

## 易错点与陷阱

- **dlt 的 merge 需要 primary_key 且表已存在语义一致**；对 DuckDB 目标，merge 靠 staging 表 + DELETE/INSERT 实现——高频小批会积累大量事务膨胀，定期 `CHECKPOINT`/重建（⚠️ 实现细节随版本）。
- **write_disposition 换策略不清历史**：append 表改 merge 只影响增量，历史重复仍在——先 replace 重灌。
- **dbt-duckdb 的 incremental + unique_key**：依赖 DuckDB 事务，跨进程持有同库文件会锁冲突（见 12 章并发实测）。
- **DuckDB 无 row-level 权限**：dbt 的 grants 配置在此基本空转，安全靠文件/云侧。
- **Dagster 资产与 dbt 模型重名**：同一物理表被两处"拥有"会互相 DROP——dbt 资产用 `@dbt_assets` 桥接而不是重复定义。
- 把整条 ELT 跑在单文件库上忘了备份：DuckDB 文件坏了=管道全没；生产要把 dlt 目标放可恢复存储或云。

## 核心概念速览（中英对照）

- **ELT** — Extract-Load-Transform：先装载后变换的管道范式。
- **摄取框架** — Ingestion framework（dlt）：声明式 source→destination 装载器。
- **写 disposition** — Write disposition：append/merge/replace 装载语义。
- **系统表** — Pipeline metadata tables：`_dlt_loads` 等运行元数据。
- **源声明** — dbt sources：把外部表纳入 dbt 血缘/测试。
- **模型物化** — Materialization：view/table/incremental/ephemeral 落地策略。
- **数据测试** — dbt tests：unique/not_null/relationship 断言即 DAG 节点。
- **资产** — Asset（Dagster）：以数据对象为中心的可物化节点。
- **编排** — Orchestration：依赖图调度、重跑、告警。
- **schema 漂移** — Schema drift：上游字段变化的自动跟踪（dlt 自动加列）。

## 最新演进与工业实践

- **dlt 现状**：dlt 已属 CLI 生态主流（v1.x，2026 年仍活跃），duckdb/motherduck 是其文档推荐默认目标（✅ pypi 可装，本机 1.30.0 实测）。
- **dbt-duckdb**：适配器持续随 DuckDB 1.x 迭代，`md:` 目标即 MotherDuck；dbt Core 1.8+ 的 `state:modified` 微增量 CI 成标配（⚠️ 转述，官方 docs.getdbt.com 未逐页 curl）。
- **Dagster 与 DuckDB**：`dagster-duckdb` 官方集成包提供 IO manager；资产血缘 + DuckDB 本地文件成为"个人数据平台"参考架构（社区口径 ⚠️）。
- **格局变化**：2026 年"湖仓摄取到 DuckLake/Iceberg 再让 DuckDB 查"开始替代"ELT 进 DuckDB 文件库"的轻量路线——见 05/11 章文件与 [../Apache_Iceberg活用入門/00-总览与阅读地图.md](../Apache_Iceberg活用入門/00-总览与阅读地图.md)；本目录判读：小团队单机管道仍以 dlt+DuckDB 为默认解。
