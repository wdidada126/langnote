# 05 · Exploring data without persistence（无持久化的数据探索）

> 覆盖原书第 5 章。目录来源：✅ Manning 官方 TOC 实抓。本章是 DuckDB 的"招牌菜"：**不导数据，文件即表**——schema 嗅探、JSON 拍平、CSV→Parquet、直查 Parquet、借道 ATTACH 查 SQLite 与 Excel。

## 内容规格（小节地图，✅ 实抓）

- **5.1 Why use a database without persisting any data?**：ETL 前探路、一次性报表、格式转换器、跨库联查——避免"先导 20 GB 再问一句话"。
- **5.2 Inferring file type and schema**：`read_csv_auto`/`sniff_csv` 自动推断列名/类型/分隔/压缩（gzip/zstd 透明）；5.2.1 CSV 解析的坑：引号转义、十进制逗号、多行表头、编码。
- **5.3 Shredding nested JSON**：`read_json_auto` 把嵌套对象/数组读成 STRUCT/LIST（"拍平到列"），`json_extract`/`unnest` 继续钻取；反向 `to_json`/`COPY ... (FORMAT JSON)`。
- **5.4 Translating CSV to Parquet**：一条 `COPY (SELECT * FROM 'x.csv') TO 'x.parquet'` 即完成格式转换 + 压缩 + 类型定型。
- **5.5 Analyzing and querying Parquet files**：`read_parquet` 谓词下推 + 列裁剪 + row-group 跳过；元数据函数 `parquet_metadata`/`parquet_file_metadata`/`parquet_kv_metadata`；分区目录 `filename=true`。
- **5.6 Querying SQLite and other databases**：`ATTACH 'x.db' AS s (TYPE sqlite, READ_ONLY)` 把 SQLite（乃至 PG/MySQL，经 mysql_scanner/postgres_scanner）当外表查；跨源 JOIN + 结果落 Parquet。
- **5.7 Working with Excel files**：`read_xlsx`/xlsx 扩展直读工作表（社区版当时为 `read_xlsx` 方言，⚠️ 细节以当前文档为准）。

## 核心技术清单

- 表函数入口统一：`FROM 'file.*'` = 隐式 read_xxx；显式 `read_csv/read_json/read_parquet` 带全部选项。
- `glob`/`union_by_name`：多文件并集读入，schema 自动对齐。
- Parquet 三件套：列裁剪（只读用到的列）、row-group min/max 跳过、page 级谓词下推。
- `WRITE_PARTITIONED`/`PARTITION_BY`：写 Parquet 时按列分区目录。
- SQLite 桥：ATTACH 后可把查询"推下去"（sqlite 扫描器下推部分谓词）或拉上来本地算。
- JSON shredding：嵌套→STRUCT/LIST 列；Parquet 2.x 的扁平化写法（列拆子列）。
- `ATTACH ':memory:'`、`ATTACH 's3://...' (TYPE duckdb)` 的多库并存心智。

## 🔧 实测（本机全链路，数字真实）

1. **CSV 直查**：5,000,000 行 / 142.2 MB CSV，`SELECT count(*), sum(mwh) FROM read_csv_auto('big.csv')` → **0.44 s**，无建表无落盘。
2. **CSV→Parquet 转换**：`COPY (...) TO 'big.parquet' (FORMAT PARQUET)` → **0.60 s**；体积 **142.2 → 58.1 MB**（随机 DOUBLE 难压，压缩比 2.4×；真实数据常见 5–10×）；文件内 **41 个 row group / 123 个 column chunk**（`parquet_file_metadata`/`parquet_metadata` 实读）。
3. **Parquet 谓词过滤**：`SELECT count(*) FROM read_parquet('big.parquet') WHERE plant=7` → **0.013 s**（CSV 同查询 0.44 s 的 ~34 倍差距——列存+跳组的直观红利）；返回恰 5000 行。
4. **SQLite 桥**：`INSTALL sqlite`（4.9 s）→ `ATTACH 'legacy.db' AS legacy (TYPE sqlite)` → 直查 `legacy.orders`（20 万行 count/sum ✅）→ `COPY (SELECT * FROM legacy.orders) TO 'from_sqlite.parquet'` 跨源落盘 ✅（1.55 MB）。
5. **嵌套 JSON**：10 万行 `{"a":..,"b":{"c":"..","d":[1,2,3]}}`，`read_json_auto` 全读聚合 **0.18 s**，b 自动成 STRUCT、d 成 LIST；`COPY` 落 Parquet 即"shredded"形态 ✅。
6. ⚠️ Excel `read_xlsx` 本机未装 excel 扩展（无样例文件），未实测；转述原书口径。

## 易错点与陷阱

- **CSV 嗅探翻车是常态**：欧洲小数逗号、混合日期格式、前 100 行碰不到空值列导致类型误判——生产要 `read_csv(..., columns={...}, sample_size=-1)` 或先 `sniff_csv` 看结论。实测中 id 列被嗅为 BIGINT 正常，但若列里有 `""` 空串会退 VARCHAR。
- **"谓词下推"别当玄学**：下推只作用于**文件内 min/max 统计能排除的 row group**；无排序的 Parquet 里等值过滤仍可能扫全文件——要快就先按过滤列 `PARTITION_BY` 排序写。
- **`sum(*)` ≠ 下推证明**（03 章同款）：想看是否真跳过行组，用 `EXPLAIN` 看 Scan 的 `Filters:` 行 + `parquet_metadata` 手工对 min/max，别靠体感。
- **ATTACH SQLite 只读心智**：SQLite 桥支持读写但**并发写无保证**，把它当"只读外表"用才是正道；跨源 JOIN 大表时注意 sqlite 扫描器并行度低。
- **union_by_name 静默加列**：多文件 schema 不齐时自动补 NULL 列，报表口径会漂；上线前对齐 `columns=` 显式 schema。
- **Parquet 字典列膨胀**：DuckDB 写高基数 VARCHAR 列时字典开销反而变大，测完两种编码（`COMPRESSION zstd`）再定。

## 核心概念速览（中英对照）

- **文件即表** — Files as tables：表函数直查文件、零导入。
- **schema 嗅探** — Schema inference：read_*_auto 采样推断列类型。
- **谓词下推** — Predicate pushdown：把过滤搬进扫描器，用统计跳过数据块。
- **列裁剪** — Column pruning：Parquet 只读用到的列。
- **行组** — Row group：Parquet 水平分块，min/max 统计的粒度。
- **分区数据集** — Partitioned dataset：目录即分区，Hive 风格。
- **JSON 拍平** — Shredding：嵌套 JSON 拆成 STRUCT/LIST 列。
- **跨源外表** — Federated attach：TYPE sqlite/postgres/mysql 挂载异库。
- **格式转换** — Format translation：COPY 一条语句完成 CSV↔Parquet。
- **数据布局元函数** — File metadata functions：parquet_metadata / glob / filename=true。

## 最新演进与工业实践

- **"无持久化"已成行业默认**：Trino/ClickHouse/BigQuery external table 与 DuckDB 互相抄作业；单机小数据的 ad-hoc 场景 DuckDB 一家几乎成为事实标准（社区共识 ⚠️ 无单一权威来源）。
- **Parquet 统计与布局工具化**：`parquet_metadata`/`parquet_file_metadata` 自 0.9/1.0 起成为标配排障手段；1.4+ 提供 `copy_to` 布局建议脚本（官方文档入口 ✅ https://duckdb.org/docs/stable/clients/overview ，细页 ⚠️ 未逐页抓取）。
- **DuckLake 落地（2025–2026）**：DuckDB 官方推出 **DuckLake**——"以 SQL 数据库为目录的湖仓格式"，仓库 2025-03-03 创建（✅ GitHub API），**1.0 于 2026-04-13 发布**（✅ https://ducklake.select/2026-04-13/ducklake-10/ ），并成为 core extension：本机 `INSTALL ducklake` + `ATTACH 'ducklake:lake_meta.duckdb' AS lake (DATA_PATH 'lake_data')` 全链路跑通——建表 10 万行 + INSERT 10 万行后 `count=200000`，`ducklake_snapshots('lake')` 列出 3 个快照（snapshot 0/1/2 带创建/插入元数据），底层即 **2 个 Parquet 数据文件** + 1 个元数据 DuckDB 文件 ✅ 实测。这正是本章"文件即表"哲学的湖仓化延伸（详见 11 章格局分析）。
- **与 Iceberg 的分工**：读 Iceberg 用 `iceberg` 扩展（需 REST catalog 配合），写能力逐步补齐；湖仓格式竞争格局见 [../Apache_Iceberg活用入門/00-总览与阅读地图.md](../Apache_Iceberg活用入門/00-总览与阅读地图.md) 与 [../Delta_Lake_Definitive_Guide/00-总览与阅读地图.md](../Delta_Lake_Definitive_Guide/00-总览与阅读地图.md)。
