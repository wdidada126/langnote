## 核心技术清单

- 加载三板斧：显式列类型、`COPY` 批量、必要时 `SET preserve_insertion_order=false`（换并行度）。
- 存储侧调优：`ENUM` 替代低基数 VARCHAR、分区目录按高频过滤列、row group 尺寸权衡。
- 计划阅读：`Filters:`（是否下推到扫描）、`ESTIMATED CARDINALITY`、`ORDER_BY/TOP_N`、`PARTITIONED`。
- 向量化直觉：算子间传 2048 批量、SIMD/分支少——**表达式越 SQL 原生越快**（对比 06 章 Python UDF 86 倍代价）。
- 并行度调优：`threads`、`memory_limit`、`temp_directory`（溢盘）；`duckdb_settings()` 盘点。
- 远端 IO：httpfs 的 range 读 + 文件元数据缓存；重复扫描要落本地或上 MotherDuck。
- 统计保鲜：大表 ANALYZE 时机与 `enable_profiling` 深度。

## 🔧 实测（TPC-H SF1 替代 Stack Overflow；16 核 / 1.5.5）

Stack Overflow dump 本机未下载（数 GB，网络受限），用官方 **tpch 扩展**做同规格"事实表大扫描"验证：

1. `FORCE INSTALL tpch; LOAD tpch; CALL dbgen(sf=1);` → **3.8 s** 生成 8 表，lineitem **6,001,215 行**。
2. 6 条代表性查询冷跑（`tpch_queries()` 取原文）：q1 0.061 s / q3 0.069 s / q6 0.010 s / q9 0.148 s / q14 0.028 s / q18 0.133 s，**合计 0.449 s**；q8 warm 0.05 s。千万行级 join+聚合在笔记本上即亚秒。
3. `COPY lineitem TO 'lineitem.parquet'`：**1.53 s / 197.5 MB**；对新文件 `SELECT l_returnflag, sum(l_extendedprice) GROUP BY ALL` **0.04 s** —— 导出后"无库查询"与库内同量级。
4. `EXPLAIN ANALYZE SELECT count(*) FROM events WHERE v>0.5`：返回带 **Total Time: 0.0249 s** 的注解计划树（每算子行数/耗时框图）✅；`EXPLAIN` 文本计划里扫描节点显示 `Filters: (v > 0.5)` 证明谓词在 SEQ_SCAN 内生效。
5. 并发限制（跨进程）：A 进程持有 `conc.duckdb` 写入间隙（sleep 3s），B 进程 `read_only=True` 打开直接 **IOException**："File is already open in python.exe (PID …)"——**数据库文件级进程互斥**；Web 多进程部署必须绕开（只读 Parquet 各自打开则无此限，实测两进程并读 big.parquet 正常）。

## 易错点与陷阱

- **默认并行是双刃剑**：`threads=16` 在共享机器上会让"礼貌的同事查询"饿死；`SET threads=4` 后 TPCH q9 类查询接近线性变慢——容量规划要量化。
- **`preserve_insertion_order`**：默认 true 时大 COPY 吃内存排队；大表导入设 false 换吞吐，但 id 顺序不再保证。
- **ENUM 过界**：基数超过 ~几千就失去收益甚至变慢（字典维护），tag 场景用之前先 `count(distinct)`。
- **plan cache 缺失的心智**：DuckDB 不缓存跨会话计划，参数化防注入但**不防计划劣化**；同一 SQL 不同过滤值可能换计划（看 EXPLAIN）。
- **S3 直查别用 `SELECT *` 探查**：一次 range 读+元数据读就是真金白银的 egress；先 `parquet_metadata` 看 row group 数。
- **溢盘不是免费午餐**：memory_limit 以下仍可能 spill（hash join 构建侧），`temp_directory` 所在磁盘 IO 会成为新瓶颈（⚠️ 未构造大内存反例）。
- 拿 TPCH/Stack Overflow 数字当 SLA：均为本地 NVMe + 空载机器，容器配额下完全不同（本目录数字同样只作量级参考）。

## 关键参数与排障工具速查

| 参数/工具 | 用法 | 什么时候动它 |
| --- | --- | --- |
| `SET threads=8` | 会话级并行度 | 共享机器/容器配额 |
| `SET memory_limit='8GB'` | 内存上限 | 防 OOM/溢盘风暴 |
| `SET temp_directory='D:/tmp'` | 溢盘目录 | 大 join/排序前 |
| `SET preserve_insertion_order=false` | COPY 吞吐 | 亿级导入 |
| `PRAGMA cpu_mode='single_threaded'` | 对照实验 | 归因并行收益 |

## 本章实测复现（TPC-H 替代 Stack Overflow；repo 零产物）

```python
# D:\develops\tmp\dbwave_duckdb\ 下执行（数字均为本机 16 核真实输出）
import duckdb, time
con = duckdb.connect()
con.execute("FORCE INSTALL tpch; LOAD tpch; CALL dbgen(sf=1);")   # 3.8s, lineitem=6,001,215
qs = con.sql("SELECT query FROM tpch_queries()").fetchall()
for i in [1,3,6,9,14,18]:
    t0=time.time(); con.sql(qs[i-1][0]).fetchall()
    print(i, round(time.time()-t0,3))     # .061/.069/.010/.148/.028/.133 合计 0.449s
con.execute("COPY lineitem TO 'lineitem.parquet' (FORMAT PARQUET)")  # 1.53s, 197.5MB
t0=time.time()
con.sql("SELECT l_returnflag, sum(l_extendedprice) FROM 'lineitem.parquet' GROUP BY ALL ORDER BY 2 DESC LIMIT 1").fetchone()
print(f"parquet groupby: {time.time()-t0:.2f}s")                    # 0.04s
print(con.sql("EXPLAIN ANALYZE SELECT count(*) FROM events WHERE v>0.5").fetchall()[0][1][:200])
# -> 注解计划树, 'Total Time: 0.0249s', SEQ_SCAN 带 Filters: (v > 0.5)
```

## 性能决策树（30 秒版）

1. 慢的是**扫描**？→ 查布局：Parquet 列裁剪/分区/跳组（05 章），`parquet_metadata` 对统计。
2. 慢的是**join/聚合**？→ 查 `memory_limit`/溢盘、`threads`，再 EXPLAIN ANALYZE 找最宽算子。
3. 慢的是**导入**？→ 禁行级 INSERT，走 COPY/appender/CTAS（12 章 2000× 实测差）。
4. 都不慢但**并发上不去**？→ 进程锁边界（实测），该上 07/11 的共享层了。

## 核心概念速览（中英对照）

- **逻辑/物理计划** — Logical/Physical plan：代数树与带算子实现的执行树。
- **优化器** — Query optimizer：谓词/投影下推、join 重排序、聚合拆分。
- **morsel 驱动并行** — Morsel-driven parallelism：按小块工作单元动态派发的执行模型。
- **向量化解释** — Vectorized interpretation：批量定长数组上解释表达式。
- **EXPLAIN ANALYZE** — 带运行时统计的计划树输出。
- **基数估计** — Cardinality estimation：计划代价的输入，误差会级联。
- **溢盘** — Spilling：内存不足时算子中间态落 temp 文件。
- **分区写入** — PARTITION_BY：按列哈希/字典切目录，跳目录即跳数据。
- **范围读** — Range read：httpfs 按 Parquet 所需字节段拉远端文件。
- **进程互斥锁** — File-level process lock：同库文件一次仅一个进程持有（实测）。
