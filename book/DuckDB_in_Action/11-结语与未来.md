## 易错点与陷阱

- 把 11.5 的乐观当采购论据：DuckDB 不替代你已有的 OLTP/大数仓；"去中心化管道"的代价是治理（目录/血缘/权限）要另建（DuckLake catalog 正是补这一刀）。
- 版本兼容性误读：DuckDB 承诺**同大版本内文件可读**，跨大版本存储格式演进（如 1.3 的 RMF→lightweight migrations 1.4）仍可能要 `EXPORT/IMPORT DATABASE` 迁移——升级演练不可省。
- 学习资源过期速度：newsletter 与 docs 比任何一本书都准；本书价值在"心智地图"，语法细节以文档为准。

## 本章实测复现（"预言 vs 现实"证据链）

# 1) 版本线：curl -s https://api.github.com/repos/duckdb/duckdb/releases?per_page=100
#    → 63 个 release；tag 日期见上表（✅ 2026-09 实抓）
# 2) DuckLake core 化实测（本机 1.5.5 全链路 ✅）：
con = duckdb.connect()
con.execute("INSTALL ducklake; LOAD ducklake;")
con.execute("ATTACH 'ducklake:lake_meta.duckdb' AS lake (DATA_PATH 'lake_data')")
con.execute("USE lake")
con.execute("CREATE TABLE facts AS SELECT i id,(i%100) c FROM range(100000) t(i)")
con.execute("INSERT INTO facts SELECT i, i+1 FROM range(100000,200000) t(i)")
con.sql("SELECT count(*) FROM facts").fetchone()                  # (200000,)
con.sql("SELECT * FROM ducklake_snapshots('lake')").fetchall()    # snapshot 0/1/2 + 元数据摘要
# 物理形态：lake_data/ 下 2 个 Parquet；湖=普通文件+SQL 目录库——"05 章哲学的湖仓化"
# 3) 示例仓库对照：duckdb-in-action/examples 目录树（ch03–ch06/08/09 + a1）与 TOC 一致 ✅

## 最新演进与工业实践

- **DuckLake 对湖仓格局的影响（2025–2026，本目录判读）**：DuckDB 团队 2025-03 建仓 `duckdb/ducklake`（"integrated data lake and catalog format"，✅ GitHub API：created 2025-03-03，~3.0k stars），**v1.0 于 2026-04-13 正式发布**（✅ https://ducklake.select/2026-04-13/ducklake-10/ ）。设计要点：数据=**普通 Parquet 文件**、元数据（快照/提交/文件清单/统计）=**放进一个 SQL 目录库**（Postgres/DuckDB 皆可），从而免掉 Iceberg/Delta/Hudi 的独立 catalog 服务与元数据文件树；代价是目录数据库成为新单点、生态写端偏 DuckDB 侧。对既有格局：小中型湖仓第一次出现"**零专管服务**"选项；REST catalog 阵营（[../Apache_Iceberg活用入門/00-总览与阅读地图.md](../Apache_Iceberg活用入門/00-总览与阅读地图.md)、[../Delta_Lake_Definitive_Guide/00-总览与阅读地图.md](../Delta_Lake_Definitive_Guide/00-总览与阅读地图.md)）则往企业治理纵深走——两条曲线在 2026 年正式分叉。湖仓架构学视角见 [../The_Data_Lakehouse/00-总览与阅读地图.md](../The_Data_Lakehouse/00-总览与阅读地图.md)；官方文档入口 ✅ https://duckdb.org/docs/current/core_extensions/ducklake.html。
- **1.x 关键里程碑（release 列表 ✅）**：v1.1 Time Travel；v1.3 VARIANT 半结构化统一类型；v1.4 加密/备份改进；v1.5（2026-03）当前线——"笔记本引擎"持续蚕食小数仓场景。
- **与 ClickHouse/SQLite 定位（2026 现状）**：SQLite 官方继续推荐"应用内分析用 DuckDB"（✅ https://sqlite.org/whentouse.html）；ClickHouse（✅ https://github.com/ClickHouse/ClickHouse）巩固服务端实时分析，两者从"竞争"转向"按并发与驻留形态分工"。
