## 3. 三元组语义矩阵（本章必须背下的表，⚠️ 重构）

| 组合 | 语义 | 典型 sink | 陷阱 |
|------|------|-----------|------|
| Append + 事件时间窗聚合 | 只发闭合窗终值 | Parquet/HDFS 目录 | 未加水位则永不闭合 |
| Update + 键聚合 | 发增量变更行 | Kafka/JDBC upsert | sink 须幂等（🔧 实验三） |
| Complete + 小状态 | 每批发全量表 | console/内存表 | 大状态全量写出=灾难 |
| Trigger ProcessingTime(0) | 尽快连续微批 | 低延迟近线 | CPU 全时占用 |
| Trigger Once | 微批跑一次即退 | 补数/测试 | 与调度器（8 章）协作形态 |

- **水位线与窗口的配合**：`withWatermark("ts","10 minutes")` + `groupBy(window(ts, "5 minutes"))`——迟到在窗内更新终值、窗外被弃；`allowedLateness` 概念在 Spark 中以「水位线放宽」形态存在 ⚠️（以指南措辞为准）。

## 4. Checkpoint 与 WAL：恢复语义的物理层（⚠️ 重构）

- 目录内容：`offsets/`（已处理位置）+ `logs/`（查询计划与状态变更 WAL）+ `caching/`、`state/`（状态算子）。
- 恢复路径：同 checkpointLocation 重启 → 从记录 offset 续读；**变更查询定义会触发不兼容告警**（plan hash），迁移需 `queryName` 或元数据搬运 ⚠️。
- 幂等性分层承诺：引擎保证「每批至少一次执行 + offset 记录精确」，端到端 exactly-once 需 sink 配合（file sink 原子移动 / idempotent sink / transactional sink 三家族，✅ 指南 Output Sinks 节）。
- 对位理论：[../Streaming_Systems/05-精确一次与副作用.md](../Streaming_Systems/05-精确一次与副作用.md)、[../Streaming_Systems/07-持久状态的实践.md](../Streaming_Systems/07-持久状态的实践.md)。

## 5. 🔧 实测·第二组：事件时间滚动窗口与迟到数据（DuckDB，非 Spark 行为）

脚本 `exp.py` 实验二，19 条事件按 40 秒间隔铺在 5 分钟桶上，前 15 条先算、随后 3 条迟到者（事件时间落回第一个窗口）插入：

- **首算**：窗口计数 `[w0:7, w1:7, w2:1]`。
- **迟到注入后全量重算**：`w0: 7→10`——3 条迟到者全部归位旧窗。
- 工程解读：全量重算**自动吸收迟到**（无状态概念）；增量路径要吸收迟到必须「重开已闭合窗」，Spark 的水位线正是对「何时可以不重开」的定价：水位未过窗尾→状态留存、结果可更新；已过→迟到被丢弃（🔧 类比止于窗口闭合逻辑，Spark 的逐窗状态机不可在 SQL 引擎复现）。
- 与实验四（09 章）互文：水位线定「哪些窗敢定稿」，本实验显示「定稿前 vs 定稿后迟到」的两种命运。
- 理论纵深：[../Streaming_Systems/04-高级开窗.md](../Streaming_Systems/04-高级开窗.md)。

## 6. Sink 工程模式集（「patterns」章名的兑现，⚠️ 重构）

- **ForeachBatch**：批 API 的自由发挥口——写 JDBC upsert、发 Kafka、落 ES；副作用不受引擎 exactly-once 保护（幂等归你管，🔧 实验三给方案）。
- **ForeachWriter**（逐行版）：open/write/finish 生命周期，乱序与重启下 at-least-once——必须可重入。
- **分区路由写**：`foreachBatch` 内按主键分桶 upsert——Update 输出的标准落地。
- **多 sink 单查询**：`foreachBatch` 里 fan-out；一致性靠同批 offset 对齐。
- **流批双入口**：同一变换模块，批入口 `read` + 流入口 `readStream`——第 7 章结构化布局的兑现。

## 8. 水位线配置口诀与状态预算（⚠️ 目录提炼，非原书口诀）

- **口诀一**：「不聚合不设水位，要 Append 必设水位」——水位线的首要功能不是正确性而是**状态释放与推进承诺**。
- **口诀二**：「滞后盖住迟到分布的 p99，再加运维余量」——纯事件延迟视角定 `10 minutes` 这类参数的方法论（批侧对位=回溯窗口天数，7 章）。
- **状态预算式**：驻留状态 ≈ 键基数 × 单键态 ×（窗口宽+水位滞后）的活跃期占比——超内存先动 TTL/ RocksDB，再动架构（外置状态，13 章演进线）。
- **升级护栏**：改水位/改窗宽会破坏 checkpoint 兼容性——「调参即发布」评审流程（§4 恢复线的工程化，⚠️ 目录建议）。

## 9. 本章实验卡（⚠️ 非原书代码）

1. 文件源 +5 分钟窗聚合 + Append：不开水位则「无输出」（窗不闭合的体感），加水位后逐窗出终值。
2. 手工制造迟到（追写旧时间戳文件）：水位未过→窗重开更新、水位已过→行消失——🔧 实验二的 Spark 化彩排（行为描述以官方指南为 ⚠️ 校核）。
3. checkpoint 断点续传演习：`stop()` → 重启同 location → 确认无重复输出；换**新** location 重启 → 历史重放灾难亲眼见。
4. 改一次查询定义（多 select 一列）重启：捕捉 plan 不兼容异常，练习迁移预案（§4 第 3 条）。
5. `StreamingQueryListener` 打印每批进度 JSON：把「触发器节奏」变成日志——接 8 章告警与 14 章观测。

## 10. 校读问答（五问五答）

- **Q：Append/Update/Complete 选哪个？** A：查 §3 矩阵——本质三问：sink 能吃变更行吗、状态全量重写付得起吗、窗闭合承诺给了吗。
- **Q：Trigger Once 算流吗？** A：算「流式语义的批执行」——7 章管道与 10 章 SS 的合流点，本书若点破此线则结构极佳（⚠️）。
- **Q：exactly-once 营销词怎么读？** A：按 §4 分层账本拆——引擎重放精确、副作用自负其责；🔧 实验三是副作用幂等的最低成本方案。
- **Q：ForeachWriter 乱序问题？** A：at-least-once + 微批内分区并行——逐行 sink 要自管去重键；能不用就不用，优先 foreachBatch（§6 工程口味）。
- **Q：与 Flink 的对应物？** A：水位线/状态后端/检查点三件套跨引擎同名异义——理论公分母读 [../Streaming_Systems/04-高级开窗.md](../Streaming_Systems/04-高级开窗.md) 与 [../Streaming_Systems/05-精确一次与副作用.md](../Streaming_Systems/05-精确一次与副作用.md)。

## 核心概念速览（中英对照）

- **流式查询** — StreamingQuery：一次 readStream→writeStream 的长跑实例。
- **触发器** — Trigger：微批节奏（processingTime/once/availableNow）。
- **输出模式** — Output Mode：Append/Update/Complete 三态发布策略。
- **水位线** — Watermark：状态清理与窗口定稿的进度承诺（🔧 实验二/四）。
- **Checkpoint 目录** — Checkpoint Location：offsets+logs+state 的恢复根。
- **WAL** — Write-Ahead Log：查询元数据与状态变更的前置日志。
- **ForeachBatch** — ForeachBatch Writer：以批 API 承接每微批副作用的自由口。
- **ForeachWriter** — ForeachWriter：逐行 sink 生命周期协议（open/write/finish）。
- **at-least-once 副作用** — Sink 侧重放容忍：exactly-once 的最后一公里（🔧 实验三）。
- **查询兼容性** — Query Plan Compatibility：checkpoint 恢复时对定义变更的守卫。
- **availableNow** — AvailableNow Trigger：有限追赶语义（2022 后新增，⚠️ 书中未必含）。
