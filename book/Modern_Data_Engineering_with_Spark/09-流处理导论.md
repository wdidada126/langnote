## 1. 本章定位

本书从批到流的大门，章名里的 "gentle" 是诚实的：不讲定理，讲**心智换轨**——把「数据是一张表」换成「数据是一条流，表是流的切片」。它是副题 mission-critical streaming 的概念地基，10/11/13 章的一切语义（触发器、偏移、状态）都挂在本章的几个轴上：时间语义、延迟/吞吐权衡、容错位置。

## 2. 心智换轨四步（⚠️ 按章题域重构）

1. **无界表**：`spark.readStream` 与 `spark.read` 的 API 对称——同一 DataFrame 类型、多一个「继续读」的时间轴；流批同码的第一眼证据。
2. **微批模型**：Structured Streaming 把流切成连续的小批（默认 1 秒触发），批引擎复用 Catalyst——这是 Spark 立场：**流是批的极限情形**（对比 Flink 的「批是流的特例」叙事）。
3. **增量视图**：每批对结果表做一次增量更新；输出模式（Append/Update/Complete）决定「谁何时看见什么」→ 第 10 章展开。
4. **容错靠重放**：源可回放（文件目录/Kafka offset）+ 状态有 checkpoint → 失败重启不丢不重（→ 10/11 章）。

对位精读（理论头部）：[../Streaming_Systems/01-流式入门.md](../Streaming_Systems/01-流式入门.md) 与 [../Streaming_Systems/02-数据处理的来龙去脉.md](../Streaming_Systems/02-数据处理的来龙去脉.md)——本书本章约等于其两章的通俗合订。

## 3. 时间三态与迟到问题（本章真正的难点预告）

- **事件时间/到达时间/处理时间**：业务问题几乎总在事件时间上成立，引擎却在处理时间上运行——错位即迟到。
- **乱序**：分布式源（Kafka 分区并发、网络重试）保证分区有序、不保证全局有序。
- **迟到数据的工程选项**：忽略（快但错）/ 更新终态（对但需要「重开口」机制）/ 分层处理（近快远准）。
- Spark 的答案是 **watermark**：引擎用「进度承诺」换「可清理的状态」——完整机制在第 10 章；概念直觉见下 🔧。

## 5. 🔧 实测·第四组：水位线 max(et)−lag vs 无水位直算（SQLite，非 Spark 行为）

脚本 `exp.py` 实验四，乱序事件序列 et=[100,102,98,105,99,110,97,120,101,103]：

- **直算**（每条到达即入 10 秒桶）：`{90:150, 100:260, 110:60, 120:80}` 立即可见——但 120 桶此刻**未收齐**，后续若有 et∈[120,130) 到达仍会继续变数。
- **水位线 lag=5**：只把 `et ≤ max(et)−5` 的桶定稿；结果 `finalized={90:150, 100:260, 110:60}`、`still_pending={120:80}`——引擎用「不再变化的承诺」换「敢删状态的自由」。
- 读数即定义：**水位线=对乱序上界的悲观估计**。lag 大→迟到少→状态久；lag 小→出数快→迟到被丢。这个权衡 Spark/Flink/本实验共享，参数名与实现各异（🔧 类比止于此；Spark 的水位线还驱动状态清理与输出推进，见 10 章）。
- 对位：水位线一般化讨论 [../Streaming_Systems/03-水位线.md](../Streaming_Systems/03-水位线.md)。

## 8. 本章实验卡（⚠️ 非原书代码）

1. `readStream.text(dir)` 文件源流：向目录追加一行，观察 4040 的微批进度事件——「无界表」十秒显形。
2. 同一批代码只改 `read→readStream`：结果逐批演化——流批同码的体感建立（4 章白名单先给绿区算子）。
3. `console` sink 三模式各跑一次聚合查询：看 Append/Update/Complete 在输出上的可见差异（10 章预习）。
4. 用 🔧 实验四的水位脚本改 lag 值（0/1/5/15）：亲手调「迟到容忍⇄状态驻留」旋钮，比任何比喻都硬。
5. 把到达序打乱重放同一数据集（`shuf`）：直算结果逐次不同、水位定稿段稳定——「乱序」从术语变成事故现场。

## 核心概念速览（中英对照）

- **无界表** — Unbounded Table：流即随时间追加行的表，Spark SQL 隐喻的基石。
- **readStream** — readStream：与 read 对称的流式读取入口。
- **微批** — Micro-batch：以连续小批消费流的执行模型，Spark SS 的默认形态。
- **增量视图** — Incremental View：每批对结果表做增量更新产生的部分结果视图。
- **事件时间** — Event Time：数据自带时间轴，与到达/处理时间三角对峙。
- **乱序** — Out-of-Order：事件时间序与到达序不一致，分布源的常态。
- **迟到数据** — Late Data：落入已定稿窗口的晚到事件，正确性/成本的拉锯点。
- **水位线** — Watermark：max(事件时间)−允许滞后，对进度的悲观承诺（🔧 实验四）。
- **延迟⇄吞吐谱** — Latency-Throughput Spectrum：微批/连续/逐事件的工程选型轴。
- **重放** — Replay：源可回溯重读 + 状态可恢复 = 流容错的公共配方。

## 最新演进与工业实践

- **Spark 4.x 流侧现状**：微批线持续增强（状态/水印 API 演进、PySpark 流式一等化），Continuous 线多年维持实验定位——低延迟逐事件场景外流至 Flink/Kafka Streams ⚠️（校核 ✅ https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html，2026-10 实测 200）。
- **Flink 2.x（2025–2026）**：Disaggregated State（计算存储分离状态后端）与 Flow API 把「批是流的特例」推进为统一 DataStream——与本书微批立场形成代际对照 ✅ https://flink.apache.org/（盘上 [../Introduction_to_Apache_Flink/00-总览与阅读地图.md](../Introduction_to_Apache_Flink/00-总览与阅读地图.md)）。
- **湖仓把「流表一体」落到存储**：Paimon/Iceberg 变更数据 feed 使「流」可被批引擎直接读——导论章隐喻的硬件化：[../Apache_Paimon_Streaming_Lakehouse/07-Changelog生成机制.md](../Apache_Paimon_Streaming_Lakehouse/07-Changelog生成机制.md)。
- **行业延迟分层常态化**：秒级（报表流）/亚秒（特征与风控）/毫秒（CEP）三层各有引擎，单一 Spark 通吃的本书叙事在 2026 已不占优（⚠️ 观察性陈述）。
