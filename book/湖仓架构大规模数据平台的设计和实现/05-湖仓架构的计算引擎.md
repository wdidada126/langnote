# 第 5 章 湖仓架构的计算引擎

> 章题按核实目录。本章**不复述书中语句**；论断以 AWS / GCP / Databricks / Apache 官方文档为据。

## 本章地图

> 一句话：**湖仓让"引擎可替换"成为可能，于是引擎选型从技术题变成经济学题——
> 谁按负载匹配单位成本最低，谁就占一个位置；同表多引擎是常态而不是例外。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 引擎的四类分工 | 重管道 / 交互 SQL / 流 / ML 与-notebook | 一类负载一台集群，别指望一个引擎通吃 |
| 5.2 存算分离的三种粒度 | 无状态 worker / 分离缓存 / 分离日志 | 粒度决定弹性速度与缓存命中率 |
| 5.3 引擎能力矩阵 | SQL 方言、格式支持、UDF、优化器、目录对接 | 兼容性检查表，选型第一步 |
| 5.4 批流一体的三条引擎路线 | 统一 API / 表即状态 / 物化视图 | 推荐"表即状态"为默认 |

| 5.6 性能与成本的联动 | 剪枝、缓存、物化、结果复用、查询守卫 | 布局收益远大于调参收益 |

## 核心精讲

### 5.1 引擎的四类分工

| 负载类型 | 特征 | 典型引擎（示例，非推荐） | 关键指标 |
| --- | --- | --- | --- |
| 重管道（ETL/ELT、回填） | 吞吐优先、可容忍分钟级、失败要能重放 | Spark、Dataflow、Flink 批模式、Glue Job | 单位数据字节成本、幂等性 |
| 交互分析（BI/Ad hoc） | 延迟优先、并发高、扫描模式多变 | Trino/Presto、Athena、BigQuery、Redshift、Spark SQL/photon 类 | P95 延迟、并发数、按扫描/按小时计费曲线 |
| 流式（连续处理） | 低延迟、有序与去重语义、状态大 | Flink、Spark Structured Streaming、各云托管流服务 | 端到端延迟、水位/迟到处理、状态可恢复性 |
| ML / 数据科学 | 随机读、特征工程、GPU、Notebook 交互 | Ray、Databricks Runtime、SageMaker/Vertex | 数据可达性（能否直读银层）、GPU 队列隔离 |

- **反模式**：把四类负载塞进同一集群 → 高峰期互相排队，最终为峰值预配（第 2.2 节的失效 3）。
- **湖仓给的自由度**：因为数据在共享存储 + 共享目录，这四类可以**各自独立扩缩、独立计费**，
  这是"引擎经济学"的基础。

### 5.2 存算分离的三种粒度

| 粒度 | 做法 | 代表形态 | 弹性速度 | 缓存代价 |
| --- | --- | --- | --- | --- |
| L1 无状态 worker + 远端存储 | 计算节点不持久化数据，全部读对象存储 | Spark on K8s / EMR 瞬时集群 | 快（分钟级） | 冷读率高，重复扫描贵 |
| L2 分离缓存层 | 本地/专用缓存（NVMe 或缓存服务）持有热文件 | 各家"结果缓存 + 数据缓存"、缓存类产品 | 中 | 需管理命中率与失效 |
| L3 分离日志/存储引擎 | 存储层自带重做日志与计算下推 | Aurora/DynamoDB 类思路；云数仓的托管存储 | 慢（受存储层约束） | 由平台内部消化 |

- 湖仓引擎基本在 L1/L2；云数仓多在 L3（平台内部优化，用户不管）。
- **实践推论**：L1 下 **布局与物化 = 性能**（因为没有本地性）；L2 要额外监控命中率，
  命中率低于阈值时"存算分离"反而比单体存储更贵。
- 与事务/目录的相互作用：L1 集群每次冷启动都要做元数据解析 → 第 4.7 节的目录延迟直接表现为
  "新集群启动慢"或"并发小查询打爆目录"。

### 5.3 引擎能力矩阵（选型第一步：填这张表）

| 检查项 | 为什么关键 | 常见意外 |
| --- | --- | --- |
| 目标表格式的**读写**支持（不只读） | 只读引擎不能承担管道 | 某引擎支持读 Iceberg 但不支持 update/delete 或 CDC |
| SQL 方言与函数集合 | 迁移成本主要在方言 | 窗口函数/半结构化函数（`EXPLODE`、JSON path）差异 |
| 目录对接方式（HMS / REST / 原生） | 决定能否享受集中权限 | 引擎只认 HMS，接了 Polaris 后权限失效 |
| 优化器能力（统计、Join 重排、动态分区裁剪、AQE） | 决定"同一 SQL 不同引擎差 10 倍" | 统计信息需要引擎回写目录，不同引擎写法不同 |
| UDF/UDAF 与语言运行时 | 既有资产能否复用 | Python UDF 在部分引擎禁用或性能极差 |
| 并发与配额模型 | 影响 SLA 设计 | 交互式队列有并发上限与超时强杀 |
| 凭证与身份传播 | 治理链路是否完整 | 引擎用统一角色访问桶，导致 per-user 审计失效（第 6 章） |
| 成本计量口径 | 账单可预测性 | 按扫描计费对未剪枝查询极敏感 |

> 提示：这张表要**逐年重填**。表格式支持矩阵、REST catalog 支持、方言兼容在 2024–2026 变动频繁。

### 5.4 批流一体的三条引擎路线

| 路线 | 引擎侧做什么 | 失败/迟到处理 | 适用 |
| --- | --- | --- | --- |
| 统一 API（微批/连续） | 同一 Dataset 逻辑，触发器决定模式 | 依赖 checkpoint + 幂等写 | 已有 Spark 资产、延迟要求 ≥ 秒级 |
| 表即状态（增量读 + 流写） | 作业读"上次快照之后"的增量，写回同表 | 快照可回滚、重放即回刷 | 湖仓默认路线：可审计、跨引擎 |
| 物化/声明式 | 声明目标，平台决定刷新 | 刷新尽力而为 | BI 出口层（gold）、指标口径统一 |

**语义上必须清楚的三件事**（对照 [../bigdata/07-实时计算与流式架构.md](../bigdata/07-实时计算与流式架构.md)）：

1. **exactly-once 是"效果"而不是"过程"**：靠幂等写（主键去重/MERGE）、事务快照与可重放来源三者合成；
   单独靠"引擎不丢数据"做不到。
2. **提交间隔 = 下游可见延迟 = 小文件粒度**：三者是同一个旋钮。要秒级可见就必须接受小文件与目录压力，
   或者把"可见性"分层（明细秒级、聚合分钟级）。
3. **迟到数据要显式策略**：更新旧分区（需要行级更新能力）、丢弃、或落入旁路表再由合并作业处理——
   选一个并写进作业规范，不要靠"反正会自动去重"。

### 5.5 多租户与资源隔离

| 机制 | 说明 | 代价 |
| --- | --- | --- |
| 队列/资源组 | 按团队或负载切分计算池 | 碎片化，整体利用率下降 |
| 会话/仓库隔离 | 每负载独立计算实例，可自动挂起 | 冷启动延迟 + 缓存丢失 |
| 优先级与抢占 | 关键管道优先，ad hoc 可被抢占 | 被抢占作业的幂等与重放必须健壮 |
| Spot/抢占式实例 | 管道成本可降一个量级 | 需 checkpoint + 幂等，失败率上升 |
| 公平调度/配额 | 防止一个团队打满 | 配置复杂，需与实际用量校准 |
| 成本标签与归因 | 按团队/用例归因 | 依赖引擎能带标签（第 7 章 FinOps） |

- **一条经验**：隔离强度应当与"负载的 SLA 差异"成正比，而不是与组织结构成正比。
  按部门建队列最后都会变成"每个部门都在为闲置付费"。

### 5.6 性能与成本的联动（收益从大到小排序）

1. **布局**（分区/排序/聚簇/文件大小）——第 3.4 节；一条 SQL 不改就能差 5–20 倍。
2. **剪枝链路完整**：目录分区裁剪 → 表格式清单统计 → 文件内统计 → 谓词下推。任一层失效即全扫。
3. **物化与复用**：gold 层聚合表、物化视图、结果缓存；高频问题不要反复算。
4. **增量代替全量**：只读新快照、只重写受影响分区；全量重刷是成本黑洞。
5. **引擎调参**（并行度、shuffle、内存、广播阈值）——重要但收益通常排在上述四项之后。
   细节见 [../bigdata/05-Spark性能优化.md](../bigdata/05-Spark性能优化.md)、[../大数据SQL优化.md](../大数据SQL优化.md)。
6. **查询守卫**：扫描上限、超时、并发上限、必须带时间过滤等强制规则——
   它保护的是共享的目录与账单，而不是某个查询的速度。

### 5.7 引擎与目录/格式的耦合点

- **提交路径**：引擎写数据 → 向目录请求 CAS；这里的耦合决定并发提交上限（第 4.7 节）。
- **凭证**：目录是否下发临时凭证（vended credentials）决定"引擎能不能绕过目录直读桶"（第 6 章）。
- **统计回写**：优化器统计存在哪里（目录 / 表格式元数据 / 引擎私有表）决定了"换引擎后性能是否掉回原点"。
- **方言与函数**：BI 工具与管道的 SQL 若依赖某引擎方言，跨引擎共享就变成一句空话——
  把可移植 SQL 与视图出口层作为平台规范（第 7 章）。
- ⚠️ **不要假设"支持同一格式 = 互通"**：三家云/开源引擎在同一张表上的可用操作集合、
  事务隔离级别、DDL 能力都有差异；上线前用**同一张表跑同一组用例**验证。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "选一个引擎解决所有负载" | 四类负载的成本函数不同；强行统一会导致为峰值预配 |
| 2 | "存算分离天然省钱" | 没有缓存或物化时，重复扫描的费用可能超过省下的存储 |
| 3 | "批流一体是引擎功能" | 是"表 + 作业语义 + 幂等写"的组合能力；引擎只提供执行 |
| 4 | "同一格式 = 多引擎互通" | 写支持、DDL、隔离级别、方言差异要用实测验证 |
| 5 | "调参是第一生产力" | 布局/剪枝/物化/增量的收益排序在前；调参排在后面 |
| 6 | "并发越高越好" | 并发打满目录与对象存储前缀吞吐后，整体吞吐下降（重试风暴） |
| 7 | "按扫描计费最透明" | 它透明但惩罚坏布局；按小时计费惩罚闲置；两者都需配额与守卫 |
| 8 | "UDF 随便写" | UDF 常破坏谓词下推与向量化；把可下推的过滤留在引擎原生表达式里 |
