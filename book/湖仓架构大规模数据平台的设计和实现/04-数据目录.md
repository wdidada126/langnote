# 第 4 章 数据目录

> 章题按核实目录。本章**不复述书中语句**；论断以 AWS / GCP / Databricks / Snowflake / Apache 官方文档为据。
> 目录背后的元数据树机制链至姊妹目录，不在此重述。所有示例为**教学示意，不参与构建**。

## 本章地图

> 一句话：**目录是湖仓唯一真正的"单点"——它同时是性能路径（找文件）、事务路径（切指针）和治理路径（定权限）**。
> 选错目录不会立刻出事，但它会在 6–18 个月后变成迁移成本最高的那一层。

| 4.2 Hive Metastore | 遗产、能力、瓶颈 | 它是事实上的兼容层，不是可扩展的控制平面 |
| 4.3 AWS Glue Data Catalog | crawler、分区、resource link、与 Lake Formation 的分工 | AWS 上目录与权限是两套服务 |
| 4.4 GCP Dataplex / BigQuery 目录 | Universal Catalog、策略标签、BigLake/托管 Iceberg | GCP 把目录当作策略与数据的绑定点 |
| 4.5 Databricks Unity Catalog | 三级命名、集中 grants、行/列策略、血缘、foreign catalog | 治理表达力最强，迁移成本也最高 |

## 核心精讲

### 4.1 三种"目录"被混用一个词

| 层 | 回答的问题 | 典型能力 | 谁实现 |
| --- | --- | --- | --- |
| **技术目录**（technical catalog） | 这张表**现在**由哪些文件组成？schema 是什么？分区怎么切？ | 表/视图/函数定义、快照指针、schema 与分区规格、统计信息 | HMS、Glue、Unity、Polaris、Dataplex |
| **业务目录**（business glossary / discovery） | 这张表**是什么业务含义**？谁负责？质量如何？ | 术语表、owner、分类打 tag、搜索、使用热度、SLA | Collibra/Alation 类、各云的元数据组件、Unity/DataPlex 的 business metadata |
| **治理平面**（policy plane） | 谁能看哪一行哪一列？数据能不能出境？留多久？ | RBAC/ABAC、行过滤、列掩码、脱敏、数据分类、审计 | Lake Formation、Dataplex data policy、Unity 的 grants + row filter + column mask、开源 Ranger |

- 三者的**耦合度**决定了架构灵活性。理想：技术目录提供稳定的元数据 API，治理平面把策略**绑定在技术对象上**，
  业务目录只做人类可读的补充。现实：很多平台把三者塞进一个服务，导致"换技术目录 = 重建权限"。
- 一个诊断问题：**"权限存在哪里？"** 若答案是"存在引擎里"（如各 BI 工具自建行列权限），说明治理平面缺位。

### 4.2 Hive Metastore：遗产与瓶颈

- **它是什么**：一个 Thrift 服务 + 关系型后端（MySQL/Postgres）的元数据仓库；表 = 位置 + 列定义 + 分区列表，
  分区值即目录名。Hive/Spark/Presto/Impala 等都以它为中心交换元数据。
- **为什么它成为"事实标准"**：几乎所有查询引擎都实现了 HMS 客户端；开源表格式为了被接纳，
  都提供 "Hive catalog" 作为最保守的接入方式。
- **结构性瓶颈**（官方与社区文档均长期记录的痛）：
  1. **分区数量上限与分区操作性能**：百万级分区后 `get_partitions` 与统计更新变慢；分区列表的批量拉取易打爆后端 DB。
  2. **锁语义粗**：仅提供表/分区级 lock 请求接口，真正的并发仲裁要靠使用方（表格式）补。
  3. **无策略表达**：只有"谁能读哪张表"级别的 SQL 标准授权（且长期不完整），没有行列级、没有数据分类。
  4. **后端数据库是隐藏单点**：容量、连接数、备份都变成平台运维事项。
  5. **无命名空间/多租户隔离**：一个 metastore 一套世界，跨团队隔离靠"多部署"。
- **迁移期常见形态**：HMS 与新目录**双写**或**镜像**（Glue 与 HMS 同步工具、Unity 的 HMS 兼容层、
  REST catalog 的 Hive 兼容实现），保证未迁移的引擎仍能工作。

### 4.3 AWS Glue Data Catalog

- **定位**：AWS 托管的技术目录（数据库/表/分区/列/serde 信息/统计），是 Athena、EMR、Redshift、
  Glue ETL、Lake Formation 共用的元数据中心。
- **关键机制**：
  - **Crawler**：扫对象前缀推断 schema 并写入目录。⚠️ 生产建议：crawler 只做发现，
    **不要让 crawler 自动变更生产表**（推断类型漂移、分区爆炸）；改为 IaC 管理表定义。
  - **分区表**：分区键 + `partition index`；大量分区时需要显式创建/导入分区（B-tree 索引、批量 API）。
  - **Resource Link / Cross-account**：把表"引用"到其他账号/区域，是多租户与共享数据集的基础件。
  - **与 Lake Formation 的分工**：Glue 存元数据，**权限在 Lake Formation**（数据过滤表达式、列级别选择）。
    引擎侧要么走 LF 代理（vended credentials），要么被 IAM 粗粒度控制。→ 第 6 章。
  - **🔧 Iceberg 支持**：Glue 作为 Iceberg REST/Catalog 后端已是一等路径（各家引擎可配置），
    与 S3 Tables 的托管 Iceberg catalog 并存——注意两者的**表注册位置与权限来源不同**。
- **典型坑**：
  1. Glue API 调用有**速率限制**，高频提交/分区写入会触发限流 → 表现为作业"偶发失败"。
  2. 分区数量巨大时，crawler 与 `get_partitions` 变成扫描瓶颈；必须用分区剪枝与批量 API。
  3. 跨区域：Glue 目录不天然跨区一致，有复制功能但需要显式配置——这是查询就近性的前提。

### 4.4 GCP：Dataplex Universal Catalog + BigQuery

- **口径**：GCP 把目录能力收敛到 **Dataplex Universal Catalog**（元数据 + 治理策略的单一入口），
  BigQuery 数据集/表/视图同样在其中注册；数据侧提供 **BigLake**（在外部存储上建表、把 GCS 当"表"来治理）
  与 🔧 **BigQuery 的 Iceberg 表支持**（外部 Iceberg / 由 BigQuery 托管的 Iceberg 两种形态）。
- **策略标签（policy tag / taxonomy）**：GCP 特色——把**数据分类**（PII/财务/…）作为一等元数据，
  与 IAM 结合实现"按标签自动限制访问"，比"逐表授权"更可规模化。→ 第 6 章。
- **数据质量与血缘**：Dataplex 提供 data quality 扫描与列级血缘（信息治理 API），可挂在表上而不是写在作业里。
- **需要注意的取舍**：BigQuery 内部表性能与服务化极佳，但它是**私有格式**；
  只有把数据落成外部/Iceberg 表才获得开放性。两种表混合使用时，
  权限与成本的来源不同（IAM 角色 vs 表级策略），必须统一在 Universal Catalog 里治理。

### 4.5 Databricks Unity Catalog

- **模型**：`catalog.schema.object` 三级命名空间；对象类型覆盖表、视图、模型（ML model）、
  卷（volumes，非结构化文件）、函数、连接（foreign catalog）。
- **为什么它在治理表达力上领先**（官方文档能力清单）：
  - **集中式 grants**：所有 ACL 存在目录里，引擎不再各自维护；支持组/服务主体、ABAC 标签式授权。
  - **行过滤（row filter）与列掩码（column mask）**：以 SQL 函数形式绑定在表上，对 BI/Notebook/Job 一致生效。
  - **血缘**：由执行计划自动捕获，含列级（⚠️ 覆盖范围以官方文档为准）。
  - **系统表（system tables）**：审计日志、表用量、lineage 都作为可查询的表提供——这是"治理可编程"的关键。
  - **foreign catalog / 互操作**：把 Iceberg REST、HMS、其他云的目录接进来，或反过来被外部引擎读取。
- **代价**：
  1. **策略与平台绑定**：从 Unity 迁出需要重建 grants、row filter、mask 表达式与血缘。
  2. **性能路径依赖**：所有元数据解析都要经 catalog 服务；跨云/跨区部署时要评估延迟与配额。
  3. ⚠️ **版本形态差异大**（开源版 / 托管版 / 不同云的能力矩阵）——以官方文档与产品页为准，别按记忆选型。
- 与 medallion 的天然配合：Unity 的 catalog 层可以用来表达 bronze/silver/gold 的信任分级与所有权。

### 4.6 Apache Polaris 与 REST Catalog：目录即 API

- **Iceberg REST Catalog Spec** 的意义：把"表状态指针 + 事务 + 凭证下发"定义成一个 **HTTP 协议**，
  于是目录实现可替换、策略可集中、凭证可在提交时下发（**vended credentials**，短时效 STS）。
- **Polaris Catalog**（Snowflake 主导、捐给 Apache 的开源实现，🔧 项目名与托管服务口径已变化，需核实）：
  按 `connection → catalog → namespace → table` 组织，**后端表状态放在关系型事务存储里**，
  把对象存储的弱语义问题彻底交给自己解决；支持多引擎、细粒度角色与跨云。
- **同类**：Gravitino（联邦元数据）、各云托管的 Iceberg REST endpoint、AWS S3 Tables 内置 catalog、
  Lake Formation Iceberg 支持。⚠️ 2026 年这一层变化极快，选型前必须现查各家能力。
- **为什么这是"最重要的一次解耦"**：
  1. 引擎与目录解耦 → 换查询引擎不改元数据；
  2. 目录与治理解耦 → 策略在 catalog 层实现一次，多引擎共享；
  3. 提交原子性与存储解耦 → catalog 的 CAS 取代 rename，跨云可行。
- **新的成本**：目录服务本身成为高可用要求对象（它是提交路径），
  需要配额、限流、跨区部署与故障演练；凭证下发链路引入安全评审事项（第 6 章）。

### 4.7 目录 = 性能路径（很多人只在治理角度看目录）

| 操作 | 目录参与方式 | 规模上限的表现 |
| --- | --- | --- |
| 查询规划 | 取表元数据 + 当前快照 + 分区/清单裁剪 | 元数据对象大 → 每次查询先读几十 MB；规划延迟 > 执行延迟 |
| 提交 | 原子替换快照指针（CAS / 事务锁 / rename） | 提交 QPS 上限 → 决定"能不能做秒级增量" |
| 并发写 | 冲突检测后重试 | 重试风暴 → 作业运行时间不可预测 |
| 增量读 | 请求"两个快照之间的文件差" | 目录需要保留历史清单；保留期变成本 |
| 小文件维护 | 注册新文件、失效旧文件 | 元数据条目膨胀 → 清单重写放大 |

- **三条经验**：
  1. 提交吞吐是**目录**的属性，不是引擎的；想提高写入频率，先证明目录能扛。
  2. **快照链保留期**是目录负载与 time travel 能力之间的旋钮，必须有公司级默认值（如 7–30 天）。
  3. **跨区读元数据**是隐形杀手：规划阶段数十次目录调用 × 每次 100ms 就足以让 P99 失控。

### 4.8 选型矩阵与迁移路线

**六维评分（每维 0–3 分，用于内部评审而非绝对结论）**

| 维度 | 提问 | 提示 |
| --- | --- | --- |
| 开放性 | 第三方引擎能否读写同一表？ | 看是否实现 Iceberg REST/标准接口 |
| 事务与提交吞吐 | 支持多少并发提交？冲突语义？ | 看 CAS/锁模型与限流 |
| 治理表达力 | 行/列策略、ABAC、数据分类 | 决定第 6 章能不能落地 |
| 血缘与可观测 | 自动血缘、系统表、审计 API | 决定事故定位速度 |
| 多租户与跨区 | 命名空间隔离、跨区域复制、凭证下发 | 决定平台规模上限 |
| 迁移成本 | 元数据导出、权限可移植、HMS 兼容层 | 通常被严重低估 |

**迁移五步（从 HMS/私有目录迁到共享 catalog）**

1. **元数据盘点**：表/视图/分区/统计/权限导出，标注"没人用的表"（往往 >40%）。
2. **影子注册**：新目录里以只读方式注册同名表，指向同一批对象（不做数据搬迁）。
3. **双写权限**：旧权限模型保持权威，新目录同步镜像，比对差异。
4. **切读**：按域切换查询引擎指向新目录，保留回退开关（表格式的历史快照使回退安全）。
5. **切写 + 清理**：DDL 与提交路径切换，退役旧目录，处理遗留权限与作业配置。

## 成本与运维取舍

| 取舍 | 便宜 | 稳妥 |
| --- | --- | --- |
| 目录部署 | 全公司一个 catalog | 按域/区域分 catalog + 联邦视图 |
| schema 发现 | crawler 自动改表 | crawler 只出建议，变更走 PR |
| 权限 | 引擎内各自控制 | 目录集中 + 引擎继承（避免漂移） |
| 历史保留 | 快照只留最新版本 | 明确保留期 + 过期作业 + 孤儿清理 |
| 高可用 | 依赖托管服务 SLA | 演练"目录不可用时平台行为"（能否只读旧快照） |

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "目录 = 数据地图/搜索工具" | 那是业务目录；技术目录还在提交路径上，是可用性关键组件 |
| 2 | "有 Glue/Dataplex 就不需要表格式" | 目录记"表定义"，事务与状态由格式定义；两者职责不可互换 |
| 3 | "权限写进目录就安全了" | 若引擎能绕过目录直读桶（IAM 过宽、桶策略缺失条件），目录策略形同虚设（第 6 章） |
| 4 | "HMS 太老，一步换掉就行" | 未迁移的引擎靠 HMS 兼容接口活着；换目录要有兼容层与双写期 |
| 5 | "crawler 让 schema 自动化了" | 推断的类型/分区在生产上是风险；变更必须受版本控制与评审 |
| 6 | "REST Catalog 只是接口偏好问题" | 它带来凭证下发与集中事务，是安全与扩展性的结构变化 |
| 7 | "分区越多越好，目录反正支持" | 目录分区数上限与批量 API 行为差异巨大，压测要针对目录而非引擎 |
| 8 | "血缘可以事后补" | 只有引擎/作业与目录直连时才能自动捕获；先接血缘再堆作业 |
