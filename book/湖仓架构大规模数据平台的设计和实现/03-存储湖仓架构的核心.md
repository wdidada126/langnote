# 第 3 章 存储：湖仓架构的核心

> 章题按核实目录。本章**不复述书中语句**；论断以 AWS / GCP / Azure / Apache 官方文档为据。
> 表格式内部机制不在本章重述，链至 [../Engineering_Lakehouses_with_Open_Table_Formats/](../Engineering_Lakehouses_with_Open_Table_Formats/00-总览与阅读地图.md)。
> 所有示例为**教学示意，不参与构建**。

## 本章地图

> 一句话：**湖仓的"存储"不是一堆文件，而是"对象存储的弱语义 + 表格式的强语义 + 布局策略"三件事的合取**。
> 只讲"Parquet 很快"或"S3 很便宜"都没抓到核心——核心是**在不提供原子 rename、不提供 POSIX 的存储上，
> 如何构造一张有 ACID 的表，并让它在 PB 级仍然能被查询**。

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 3.1 为什么必须是对象存储 | 与 HDFS/块/文件存储的语义与成本对照 | 无限容量 + 按量成本，代价是弱语义 |
| 3.2 对象存储的真实语义清单 | 强一致读、list 一致性、rename、条件写、请求计费 | 这一节决定第 4 章的目录设计 |
| 3.3 文件格式层 | Parquet/ORC/Avro/JSON 的分工与谓词下推 | 写用列存，读靠 min/max+页索引 |
| 3.4 布局优化 | 分区、分桶、排序、Z-order、文件大小 | 布局是查询性能的第一变量 |
| 3.5 表格式在存储栈里的位置 | 快照、清单、幂等写、time travel | 存储只负责字节，状态由格式定义 |
| 3.6 生命周期、分层与灾备 | 存储类别、生命周期规则、跨区域复制、不可变 | 冷数据省钱，但检索成本要预算 |
| 3.7 存储侧成本账 | 容量、请求、传输、副本、compaction 的 IO | "存储便宜"不等于"湖便宜" |

## 核心精讲

### 3.1 为什么必须是对象存储

| 维度 | 块存储（EBS/Persistent Disk） | 并行文件（FSx/Lustre） | HDFS | **对象存储（S3/GCS/ADLS）** |
| --- | --- | --- | --- | --- |
| 容量弹性 | 需预配、挂载数有上限 | 需预配带宽与容量 | NameNode 元数据是瓶颈 | 事实无限 |
| 单位成本 | 高（含副本） | 中高 | 中（3 副本） | 最低，且可按类别分层 |
| 语义 | POSIX、随机写、锁 | POSIX 子集 | 顺序写、原子 rename、无随机写 | Key-Value HTTP API；无 POSIX |
| 一致性 | 本地强一致 | 客户端缓存需处理 | 强（NameNode 单点权威） | ⚠️ 见 3.2 |
| 多引擎共享 | 差（挂载冲突） | 好 | 一般（JVM 客户端为主） | 好（HTTP，天然跨语言） |
| 谁负责副本/修复 | 卷/集群 | 文件系统 | HDFS | 平台内置（AWS/GCS 文档：多设备冗余 + 后台校验修复） |

- 结论：对象存储赢在**成本 + 弹性 + HTTP 可访问**，输在**语义弱**。湖仓的整个技术难度几乎全部来自这一进一出。
- 常见误解纠正：**"S3  durability 11 个 9" 不等于"数据不会错"**——它保证的是硬件冗余，
  不保证你的应用没写坏对象（无校验和约定、无版本原子性，除非开启版本化）。

### 3.2 对象存储的真实语义清单（决定上层设计）

以 AWS 官方文档口径为主（GCS/ADLS 类似但有细节差异，标注在表中）：

| 语义点 | S3 事实 | GCS 事实 | 对湖仓的影响 |
| --- | --- | --- | --- |
| 读-after-write（新对象） | 2020-12 起默认**强一致** | 默认强一致（最终一致旧行为早已取消） | 单对象写可见性不再是问题 |
| 覆盖写的旧版本可见性 | 短暂窗口可能读到旧版本（官方文档明确记录） | 有类似 Generation 机制 | 表格式**不能依赖覆盖写做提交** |
| list（列举前缀） | 与对象写最终一致，无边界标记（旧版有；2018 后取消） | list 强一致（⚠️ 版本口径需以 GCS 文档复核） | "目录 = 分区"模型不可靠 → 必须清单化元数据 |
| 目录级原子 rename | **不存在**（rename = 逐对象 copy + delete） | 不存在 | 不能实现 `INSERT OVERWRITE DIRECTORY` 的安全版本；原子性要靠"指针切换" |
| copy 大对象 | 服务端 copy 有 5GB 限制，超出用 multipart | 类似组成限制 | 迁移/回刷作业要分片设计 |
| 条件写（If-None-Match 等） | 🔧 S3 自 2024-04 起支持条件写（针对 PutObject，防覆盖） | 支持 precondition（ifGenerationMatch） | 让"无 catalog 的原子创建"成为可能，但仍不是事务 |
| 请求成本 | GET/PUT/LIST 均计费，list 是隐藏大项 | 操作类请求计费 | 高频小文件写入 + 频繁 list 是成本陷阱 |
| 每前缀吞吐 | 有分区热点上限（官方：每秒数千请求/单前缀，靠加随机前缀缓解） | 类似 | 表格式清单文件要**避免路径可预测的集中前缀** |

**三条硬推论**：

1. 因为**没有原子 rename**，"提交"必须是**写一个小对象 + 让某处指针原子地指向它**。
   于是原子性要么依赖目录服务（catalog）的单键 CAS，要么依赖存储的条件写/元数据服务器。→ 第 4 章。
2. 因为 **list 不可靠且昂贵**，"表包含哪些文件"必须**显式记录在清单文件里**，而不是靠扫目录。
   这正是 Iceberg manifest / Delta `_delta_log` / Hudi timeline 的共同动机。
3. 因为 **请求计费 + 前缀热点**，元数据对象要"少而大"，数据对象要"大而少"，
   两者对 compaction 策略的要求相反 → 3.4/3.7。

### 3.3 文件格式层：列存为什么是默认

| 格式 | 组织 | 典型用途 | 关键能力 | 陷阱 |
| --- | --- | --- | --- | --- |
| **Parquet** | 列式，行组(row group) + 列块(column chunk) + 页(page) | 湖仓默认分析格式 | 列裁剪、谓词下推（页/行组 min-max、字典、NULL 统计）、压缩比高 | 嵌套结构（Dremel record shredding）实现有差异；小行组 → 元数据膨胀 |
| **ORC** | 列式，stripe + index/data 流 | Hive/Presto 生态 | 内置轻量索引、极列压缩、ACID 相关的 delete 文件（Hive ACID） | 跨引擎支持不如 Parquet 普遍 |
| **Avro** | 行式，含 schema 于文件头 | CDC / Kafka / 归档 / 写多读少 | schema 内嵌、可拆分合并、写入便宜 | 无谓词下推，分析扫描慢 |
| JSON/CSV | 文本行 | 原始落地（bronze） | 无 schema 依赖、人类可读 | 扫描代价最高、类型漂移风险 |

- **谓词下推的实际收益链条**：分区裁剪（目录级）→ 表格式清单统计（文件级 min/max）→
  行组统计（Parquet footer）→ 页级索引 → 向量化解码。湖仓里"快"是这五层逐级淘汰的结果，
  任何一层缺失都会退化成全扫。对照 [../大数据SQL优化.md](../大数据SQL优化.md)。
- **写侧选择**：CDC 落地常用 Avro/JSON（写便宜），银层转 Parquet（读便宜）。
  medallion 各层可以用**不同格式**，这是湖仓相对数仓的一个自由度。
- 🔧 新增维度：列式格式上的**嵌套/半结构化演进**（如 Parquet Variant 类型、
  Iceberg v3 的几何/层次类型支持）——2026 年在各家文档里仍在演化，选型时确认引擎支持矩阵。

### 3.4 布局优化：查询性能的第一变量

| 手段 | 做什么 | 何时有效 | 副作用 |
| --- | --- | --- | --- |
| 分区（partition by） | 按列值把文件放不同目录/清单条目 | 高选择性的过滤列、时间范围 | 过度分区 → 小文件与目录爆炸；分区键难改（需 partition evolution） |
| 分桶/聚类键 | 按哈希把数据打散到固定数量文件 | join/聚合的列对齐、避免重分布 | 桶数变更需重刷；对无过滤的扫描无益 |
| 排序（sort within file） | 文件内按列排序 | min/max 淘汰率高，等值/范围过滤强 | 写入需 shuffle，成本上升 |
| Z-order / hilbert | 多维交错排序，跨列同时保留局部性 | 多列过滤组合不确定时 | 压缩比略降；聚簇作业要定期重跑 |
| 文件大小目标 | 通常建议单文件 128MB–1GB 量级（各家文档口径不一，需实测） | 扫描型查询 | 文件越大，小更新的重写代价越高 |
| 数据局部性/前缀打散 | 路径加随机前缀避免 S3 单前缀热点 | 高并发提交/列举 | 目录可读性下降，需靠元数据 |

- **本质矛盾**：读要"少而大、按查询键有序"；写要"快、可增量、可幂等"。
  **compaction 就是这笔矛盾的定期清算**，它的成本与归属是湖仓运营的头号议题（3.7 + 第 5 章）。
- 与表格式的关系：布局策略必须由表格式记录（分区规格演化、统计信息），
  否则"改了分区方式历史数据读不到"。partition evolution 的机制层讨论见
  [../Engineering_Lakehouses_with_Open_Table_Formats/03-Iceberg表格式机制.md](../Engineering_Lakehouses_with_Open_Table_Formats/03-Iceberg表格式机制.md)（hidden partitioning 与规格演化）。

### 3.5 表格式在存储栈里的位置（职责边界，一句话版）

```text
查询引擎 ──「读哪张表、什么过滤条件」
   ↓
表格式   ──「当前快照包含哪些文件、各文件的统计、schema/分区规格版本、可否 time travel」
   ↓
对象存储 ──「按 key 取字节」
```

- 表格式把 **状态定义、原子提交、增量可见性、演化** 四件事从引擎和文件里剥离出来。
- 三条边界提醒：
  1. 表格式**不做查询优化**（不做 join、不做聚合下推），只做文件淘汰的元数据支撑；
  2. 表格式**不做权限**（权限在目录层，见第 6 章）；
  3. 表格式**不保证不产生小文件**（它只是记录事实；写入频率由作业决定）。
- 三格式对照与规范细节：
  [../Engineering_Lakehouses_with_Open_Table_Formats/02-开放表格式的元数据布局总论.md](../Engineering_Lakehouses_with_Open_Table_Formats/02-开放表格式的元数据布局总论.md)、
  [03-Iceberg表格式机制.md](../Engineering_Lakehouses_with_Open_Table_Formats/03-Iceberg表格式机制.md)、
  [04-Hudi表格式机制.md](../Engineering_Lakehouses_with_Open_Table_Formats/04-Hudi表格式机制.md)。

### 3.6 生命周期、分层与灾备

| 需求 | 常见做法（官方能力名） | 注意点 |
| --- | --- | --- |
| 冷热分层 | S3 Intelligent-Tiering / Standard-IA→Glacier 生命周期；GCS Nearline/Coldline/Archive；ADLS 访问层 | 归档层**取回有费且有延迟**；time travel 快照若落在归档层，回滚会变慢变贵 |
| 保留与删除 | 生命周期规则 + 表格式快照过期；合规删除需 compaction 重写才真正消失（第 6 章） | 只删元数据不删对象 → 存储费继续涨；只删对象不删元数据 → 查询报错 |
| 版本化与误删保护 | S3 Versioning + Object Lock（WORM）；GCS 对象版本/桶锁 | 版本化会让表目录膨胀，需要与快照过期联动规划 |
| 跨区域/跨账号容错 | S3 CRR、GCS 双区域/多区域桶、ADLS GRS | 复制是异步的：RPO 非零；表快照指针的跨区一致性要单独设计 |
| 不可变审计数据 | Object Lock compliance mode、只追加桶策略 | 与 compaction 冲突（compaction 要重写文件），需分层存放 |
| 成本护栏 | 按前缀容量报表、生命周期审计、请求量监控 | 请求账单往往是失控项，不是容量账单 |

**灾备设计的一个高频坑**：湖仓的"数据"分散在三处——对象（文件）、元数据对象（清单/快照）、
目录数据库（表指针与权限）。备份计划若只覆盖对象存储，恢复时会发现**目录里的表定义与权限丢了**。
建议：目录变更纳入变更审计、元数据对象纳入备份范围、并演练"从空目录重建表"的流程。

### 3.7 存储侧成本账（湖仓最容易算错的地方）

| 成本项 | 随什么增长 | 失控信号 | 治理手段 |
| --- | --- | --- | --- |
| 容量 | 表行数 × 副本/版本 × 保留策略 | 容量斜率 > 业务数据斜率 | 快照保留期、孤儿文件清理、生命周期 |
| 请求（GET/PUT/LIST） | 文件数 × 作业频率 × 重试 | LIST 费用接近 PUT 费用 | 攒批写入、清单化元数据、并发限流 |
| 传输（跨区/出云） | 消费侧的就近性 | 下游引擎跨区拉全表 | 就近计算、跨区域复制热表 |
| Compaction/重写 | 更新频率 × 数据量 | 每天重写全量分区 | 增量 compaction、分区级重写、写入频率降档 |
| 归档取回 | 运维回滚、审计调取 | 一次回滚产生巨额取回费 | 温层（IA）而非冷层做近期历史 |

- 一个有用的估算直觉（教学示意，不参与构建）：
  **年存储成本 ≈ 容量 × 单价 × 层数系数**；
  **年计算成本 ≈ 扫描字节 × 查询次数 × 单位扫描价**。
  在按扫描计费的产品上（Athena/BigQuery on-demand），**布局与物化的收益直接折现**；
  在按集群小时计费的产品上，收益表现为"同样集群能多跑作业"。两种情形要分开评估。
- 🔧 2024–2026 新变量：**对象存储厂商开始托管表元数据**（AWS S3 Tables 等），
  把"格式 + 存储优化"打包，代价是格式版本与目录 API 由厂商推进；
  做成本对比时要把它算成"少一个自建服务 + 少一份运维人力"。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "S3 强一致了，所以表也一致了" | 对象级强一致 ≠ 集合级原子可见；仍需清单 + 指针切换 |
| 2 | "Parquet 已经压缩得很好，不用再优化布局" | 压缩省容量，布局省扫描；谓词下推收益来自排序/聚簇 |
| 3 | "分区越多查询越快" | 分区数超过阈值后 list/元数据开销反超扫描收益；小文件问题从分区开始 |
| 4 | "湖仓不用买备份" | 对象存储的 durability ≠ 误删/逻辑损坏的保护；版本/锁/快照只覆盖部分场景 |
| 5 | "生命周期规则会自动清理快照" | 存储生命周期与表格式快照过期是两套机制，需要人为对齐保留期 |
| 6 | "格式选 Parquet 还是 ORC 最关键" | 关键在表格式 + 布局；Parquet/ORC 差异远小于分区与排序设计差异 |
| 7 | "冷数据放归档最省钱" | 若归档层数据仍被表清单引用，扫描会触发取回或报错；要么先清元数据要么别移 |
| 8 | "compaction 越频繁越好" | 每次 compaction 重写数据、产生新快照；高频 + 大分区会让写放大失控 |
