# 第 2 章 传统架构与现代数据平台

> 章题按核实目录。本章**不复述书中语句**；论断以 AWS / GCP / Databricks / Apache 公开文档与公开论文为据。
> 所有架构图与 SQL 为**教学示意，不参与构建**。

## 本章地图

> 一句话：**传统架构的每一种形态都是一次"把复杂度放在哪里"的选择**——
> 数仓把复杂度放在写入端（schema-on-write），数据湖把它搬到读取端（schema-on-read），
> 湖仓把复杂度外置到元数据层，现代数据平台再把剩下的复杂度交还给组织。

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 2.1 数仓架构的完整形态 | Inmon vs Kimball、ETL、多维模型、专用一体机 | 可信度来自"写入端约束"，成本也来自它 |
| 2.2 数仓的六类失效模式 | 成本、schema 变更、负载耦合、半结构化、开放性、扩容粒度 | 每一条都能在湖或湖仓里找到对应解 |
| 2.3 数据湖的得与失 | 得到成本与自由度，失去事务、"当前状态"、治理 | 数据沼泽不是意外，是缺元数据的必然 |
| 2.4 Hadoop/Hive 路线的技术根因 | 目录即元数据、rename 伪原子、无隔离级别 | 这是第 3、4 章所有设计的问题来源 |
| 2.5 Lambda / Kappa / 湖仓 | 两套代码 vs 一管道重放 vs 表即状态 | 2026 年主流是"湖仓 + 增量管道" |
| 2.6 现代数据平台的分层 | 接入/存储/转换/编排/语义/消费/观测 | 平台层与产品层要分开算账 |
| 2.7 data mesh 与组织维度 | 域所有权、数据产品、联邦治理 | 技术架构解决不了责任分配 |
| 2.8 三家参考架构对照 | AWS / GCP / Databricks 的推荐形态与隐含锁定 | 锁定风险主要在目录与语义层 |

## 核心精讲

### 2.1 数仓架构的完整形态（先讲对的东西）

一个"传统数仓"不是只有一台 MPP 机器，它是一整套**以写入端约束换取读取端可信**的流程：

```text
源系统(OLTP) --抽取--> staging --转换/清洗(ETL)--> 仓库表(规范化/维度模型) --> 立方体/语义层 --> BI
                                     ↑
                        数据质量检查、业务规则、代理键、 slowly changing dimension
```

- **两种方法论**：Inmon（自顶向下、企业级规范化仓库 + 下游集市）与 Kimball（自底向上、总线架构 + 一致性维度）。
  教科书口径见 [../数据库系统概念6/20-数据仓库与数据挖掘.md](../数据库系统概念6/20-数据仓库与数据挖掘.md)，
  工程化细节见 [../数据仓库工具箱.md](../数据仓库工具箱.md)。
- **为什么它"可信"**：主键/外键、非空、类型、单位、口径都在**装载时**强制；读端几乎不需要防御性代码。
- **为什么它"贵"**：同一份数据要为不同负载重复存储（明细 + 汇总 + 立方体），
  计算与存储绑定，闲置时段也要为峰值买单；工程人力（ETL 开发）是最大成本项。

### 2.2 数仓的六类失效模式

| # | 失效模式 | 具体表现 | 谁解决了 | 遗留 |
| --- | --- | --- | --- | --- |
| 1 | 存储/吞吐单位成本高 | 列存 + 压缩仍是数仓级定价；冷数据也得留在仓库 | 数据湖（对象存储） | 湖上查询性能要靠布局优化 |
| 2 | Schema 变更昂贵 | 加字段要走建模评审、改表锁、回刷历史 | 湖（schema-on-read） | 湖上演化需要表格式才安全（field-id 机制） |
| 3 | 负载耦合 | ETL 大事务、BI 高峰、ML 全表扫描互相挤压，队列排队 | 存算分离 + 多计算集群（各引擎按负载伸缩） | 缓存命中率下降、成本项增加 |
| 4 | 半结构化/机器数据 | JSON、日志、事件、图像、文本进不了仓库或被迫拍平 | 数据湖 | "进了湖"≠"可用"，仍缺治理 |
| 5 | 开放性/生态绑定 | 数据只能在原厂引擎里被访问，工具与人才被绑定 | 开放格式（Parquet/Iceberg 等） | 开放后性能与治理能力要靠目录补齐 |
| 6 | 扩容粒度粗 | 只能整机/整节点升配，弹性差 | 云数仓（按 slot/DPU 弹性）与湖仓（引擎独立扩缩） | 弹性带来账单不可预测 |

> 辨析要点：**5 与 6 是"云数仓也解决了"的部分**。所以"数仓 vs 湖仓"的真实对立点是
> **1、2、4（成本 + schema 自由度 + 数据形态）**，不要把所有数仓痛点都归给湖仓叙事。

### 2.3 数据湖的得与失

Hadoop（2006 起）与对象存储湖（2010 起，AWS 官方文档长期推荐 S3 作为 data lake 底座）把
"存储"这个约束打开，但也一次性放弃了六样东西：

1. **原子可见性**：一批文件写完之前，并发读会看到半批数据；Hive 风格 `INSERT OVERWRITE`
   依赖 rename，而对象存储不提供目录级原子 rename（AWS 明确记录该限制）。
2. **"表的当前状态"没有权威定义**：目录前缀下所有文件都是数据，删除/更新只能靠重写整个分区。
3. **行级更新代价极高**：改一行要重写整个分区文件；于是"更新型业务"在湖里几乎不可做。
4. **schema 只存在于读端约定**：字段改名后历史数据仍能"读出来"，但没有任何机制保证一致性 →
   下游各自写兼容代码，形成隐性债务。
5. **治理缺位**：权限落在桶/IAM 层，无法表达"这张表的这一列对这个角色脱敏"。
6. **小文件**：高吞吐写入 + 分区过细 → 数百万 KB 级文件，list 与 open 成本压垮查询。

**"数据沼泽（data swamp）"不是使用者的失败，而是缺少 1–5 时的默认状态**。

### 2.4 Hive 路线的技术根因（一句话版本，机制细节链出去）

Hive Metastore + HDFS + Parquet 组合是"第一代湖"，它的三个结构性限制决定了后续所有设计：

- **元数据只有"目录 + 分区"两级**：分区值即目录名，于是分区键不能改、不能演化（partition evolution 缺失）。
- **一致性寄托在文件系统语义上**：HDFS 有原子 rename，所以"移动目录 = 换表状态"在 HDFS 上勉强成立；
  搬到 S3 上就失效——这是"湖必须换到对象存储"与"湖必须新增元数据层"两件事同时发生的原因。
- **锁与并发在 metastore 里是粗粒度的**：并发写与 DDL 竞争时缺乏冲突检测语义。

### 2.5 Lambda / Kappa / 湖仓：三代流式架构的取舍

| 架构 | 出处 | 做法 | 优点 | 代价 | 在湖仓时代的处境 |
| --- | --- | --- | --- | --- | --- |
| Lambda | Marz 提出的分层批 + 流（2010s 流行） | 批层保正确性，速度层补延迟，服务层合并 | 结果最终正确、可回刷 | **两套代码两种语义**，人力与口径漂移 | 被"增量管道 + 全量回刷同一逻辑"替代 |
| Kappa | Critchlow 等人的"只保留流"主张（2014 前后） | 一切皆流，重放日志重建状态 | 单一代码路径 | 重放成本高；历史查询不便；状态在引擎内不可共享 | 部分实现——把"可重放状态"从引擎状态搬到**表快照 + 增量读** |
| 湖仓增量架构 | 各家文档口径（增量查询 / change data feed / materialized view） | 表即状态；作业只消费新快照；需要时全量回刷同一 SQL | 一份逻辑、可审计、可回溯、多引擎共享 | 提交频率 vs 文件粒度、compaction 归属、目录写入吞吐 | 2026 年主流形态 |

- 与仓库既有笔记的衔接：[../bigdata/07-实时计算与流式架构.md](../bigdata/07-实时计算与流式架构.md)（引擎侧的 exactly-once/水位线）、
  [../基于Apache_Flink的流处理.md](../基于Apache_Flink的流处理.md)（状态与容错的教科书式讨论）。
- 关键理解：**湖仓把"批流一体"的实现点从引擎状态移到了表状态**，于是容错、可观测、可重放
  变成了数据平台的能力而不是某个作业的属性。

### 2.6 现代数据平台的分层（把"湖仓"放回更大的图里）

```text
L7 消费        BI / 应用 API / Notebook / Agent / 反向 ETL
L6 语义        指标定义、语义层、权限视图、业务术语表
L5 编排与运维  调度、依赖、SLA、重跑、告警、数据契约校验、CI/CD
L4 转换        dbt/Spark/Flink 作业、medallion 分层落地、质量规则
L3 目录+格式   Catalog（表状态/权限/血缘）+ Table Format（事务/演化）
L2 存储        对象存储 + 列式文件格式 + 生命周期与灾备
L1 接入        CDC、事件流、文件批量、API 拉取
L0 源系统      OLTP、SaaS、日志、IoT
```

两个工程结论：

- **平台层（L1–L3）与产品层（L4–L7）的团队规模比例应约为 1:3**；
  若反过来说明平台在替业务写逻辑，责任边界已经错位。
- **L3 是"共享的一次性投资"，L4–L7 是"每用例的可变投资"**：预算与评审应分开，否则总以为
  "上了湖仓就自动有报表"。

### 2.7 data mesh：组织维度上没被架构解决的部分

lakehouse 解决"一份数据多引擎读写"，data mesh（Zhamak Dehghani 2019 提出）解决
"谁来定义数据的正确性与价值"：

| 原则 | 在湖仓里怎么落 | 失败信号 |
| --- | --- | --- |
| 域所有权（domain ownership） | 每个 medallion 层表有 owner 字段/标签，目录里可查 | 所有表的 owner 都是平台团队 |
| 数据即产品（data as a product） | 表带 SLA、版本、契约、消费者清单 | 下游靠问人判断能不能用 |
| 联邦治理（federated computational governance） | 策略在目录层集中表达、由域内执行 | 策略靠人工评审文档，执行靠自觉 |
| 自助平台（self-serve platform） | 模板化建表、自动接目录与血缘、自动配 compaction | 建一张新表要提工单排期两周 |

> 与组织类笔记对照：[../中台架构与实现.md](../中台架构与实现.md)、[../企业IT架构转型之道.md](../企业IT架构转型之道.md)。
> 中台与 mesh 是同一矛盾（集中 vs 分布）的两种解，湖仓是它们共同的技术底座。

### 2.8 三家参考架构对照（公开文档口径）

| 维度 | AWS（S3 + Glue + Athena/EMR/Redshift） | GCP（GCS + BigQuery + Dataplex） | Databricks（对象存储 + Delta + Unity Catalog） |
| --- | --- | --- | --- |
| 默认心智 | "湖优先"，仓库是可选加速器；Lake Formation 做集中权限 | "BigQuery 优先"，湖通过外部表/Managed Iceberg 接入 | "湖仓一体"，Delta + medallion 是原生叙事 |
| 目录 | Glue Data Catalog（+ Lake Formation 权限层） | Dataplex Universal Catalog（含 BigQuery 目录与策略标签） | Unity Catalog（三级命名空间 + 行/列策略） |
| 引擎分工 | Athena（ad hoc）、EMR/Spark（重管道）、Redshift（BI 与服务） | Dataflow/Fusion（管道）、BigQuery（分析与物化）、Dataproc（Hadoop 兼容） | Jobs/Serverless（Spark）、SQL Warehouse（BI/photon）、Workflow（编排） |
| 表格式立场 | Iceberg 一等 + S3 Tables 托管；Delta/Athena Hive 兼容并存 | BigQuery Managed Iceberg（⚠️ 服务名与形态以官方文档为准） | Delta 主，Iceberg 支持逐步补齐 |
| 锁定风险最高处 | 目录 + 权限模型 + 专有存储格式（Redshift 内部表） | 语义层与 BI（Looker）+ BigQuery 专有内部格式 | Unity 权限与血缘的表达方式（可导出，但策略迁移需重建） |
| 成本模型 | 按扫描量（Athena）+ 按小时（EMR）+ 按用量（Glue API/爬虫） | 按 slot 预留/按需 + 按分析存储 + Dataplex 治理 API | DBU 计价 + 云基础设施另计 |

- **共同的架构骨架是一样的**（对象存储 + 表格式 + 目录 + 多引擎），差异在
  **"谁是主，谁是附"**：AWS/GCP 的仓库能力更强（引擎自带优化器与服务化），Databricks 的管道/ML 更强。
- 选型实操建议：**把目录层当作迁移成本最高的一层来评估**——
  存储和引擎都可以双写/并存，目录迁移要走"元数据导出 + 权限重建 + 血缘重挂"，最贵（第 4 章）。

## 成本与运维取舍

| 决策点 | 省钱选项 | 稳妥选项 | 判断依据 |
| --- | --- | --- | --- |
| 存量数仓 | 立刻全量迁到湖 | 保留数仓做热点服务，湖做全量与 ML | 看查询分布：Top 5% 查询贡献 80% 成本时先迁冷层 |
| 编排 | 每个团队自配 Airflow | 统一调度 + 模板化作业 | 看跨团队依赖比例 |
| 语义层 | 各自报表里算指标 | 集中指标定义 + 视图出口 | 看口径争议发生频率 |
| 平台组织 | 无平台团队 | 平台 + 域双轨 | 数据用例 ≥ 20 个 或 表 ≥ 数千 时，无平台团队会失控 |

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "数据湖就是廉价版数仓" | 湖放弃了事务与状态定义，代价在读取端与治理端 |
| 2 | "上了云就自动开放" | 云数仓内部格式仍是私有的；开放只发生在"对象存储 + 开放格式"这条线上 |
| 3 | "Lambda 已死，一律 Kappa" | 需要复杂历史回刷与多维口径时，"批回刷 + 增量补"混合更常见；关键是**同一套逻辑** |
| 4 | "Hive 的问题是老，换个新查询引擎就好" | 问题在元数据模型（目录即分区、无演化、无冲突检测），换引擎不解决 |
| 5 | "小文件是存储问题" | 小文件是**提交频率与文件粒度的耦合问题**，解法在写入端（攒批、异步 compaction、分区设计） |
| 6 | "参考架构图能直接抄" | 三家参考架构隐含各自的计价模型与运维责任划分；抄图前先算账单归属 |
| 7 | "data mesh 是湖仓的替代品" | mesh 是组织层；没有湖仓做技术底座，mesh 的"数据产品"无法低成本发布 |
