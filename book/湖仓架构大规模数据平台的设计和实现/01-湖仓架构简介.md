# 第 1 章 湖仓架构简介

> 章题按核实目录（机械工业出版社 2025-09，ISBN 9787111789000，前言 + 8 章）。
> 本章**不复述书中语句**；概念辨析与结论均以 AWS / GCP / Databricks / Apache 公开文档为据，
> 并尽量给出"为什么"而非"是什么"。所有示例为**教学示意，不参与构建**。

## 本章地图

> 一句话：**湖仓 = 对象存储上的开放数据 + 一层可事务演进的元数据 + 一个共享目录 + 多引擎读写**。
> 它不是第三种新的存储介质，而是把"数仓的语义能力"外置成共享服务，搬到"数据湖的单位成本"上运行。

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 三个词的历史包袱 | warehouse / lake / lakehouse 各自的承诺与失信记录 | 词是营销，矛盾才是主线 |
| 1.2 湖仓的四要素 | 存储、表格式、目录、引擎 | 缺任何一个都退化成"数据湖"或"私有数仓" |
| 1.3 为什么依次出现：数仓→湖→湖仓 | 每代解决了什么、**没解决**什么 | 成本先行、语义补课 |
| 1.4 分层建模：medallion vs ODS/DWD/DWS/ADS | bronze/silver/gold 与数仓分层的对应与错位 | medallion 是数据质量阶梯，不是维度模型替代品 |
| 1.5 批流一体在架构中的位置 | 一张表服务两种延迟目标 | 批流一体的真正含义是"一份状态机" |
| 1.6 湖仓不解决什么 | 语义层、责任边界、组织 | 技术组件买不下组织账 |
| 1.7 什么时候不该上湖仓 | 五条反向判据 | 数据量小、负载单一、合规要求强隔离时，数仓更省事 |

## 核心精讲

### 1.1 三个词的历史包袱

技术词汇的更替往往不是"新词更准确"，而是"旧词兑现不了承诺"。三个词各自欠下的债：

| 术语 | 原始承诺 | 实际失信之处 | 于是催生了什么 |
| --- | --- | --- | --- |
| **数据仓库**（Data Warehouse，Inmon/Kimball 路线，1990s） | 单一事实来源、强 schema、可信 BI、性能好 | 按吞吐量计费且**存算绑定**；半结构化数据要等建模完才能进；负载互相挤压（ETL vs BI vs ML）；扩容只能整机升配 | 廉价的对象存储/HDFS + schema-on-read |
| **数据湖**（Data Lake，2010s） | 什么都先存下来、单位成本极低、多负载共享 | **没有 ACID、没有并发写语义、没有"当前状态"的权威定义**；schema-on-read 把复杂度推给读端；文件目录即元数据 → 变成"数据沼泽（data swamp）"；ML 与 BI 各自踩坑 | 表格式 + 目录 + 治理 |
| **湖仓**（Lakehouse，Databricks 在 2020–2021 提出并写成论文，CIDR 2021） | 在湖的存储上提供仓的管理与事务语义，同时支持 BI、数据科学、ML/AI 三类负载 | 名字被云厂商与工具商复用，导致"湖仓"变成营销标签；开放程度取决于目录与格式是否可被第三方引擎读写 | 需要用**四要素**而不是标签来判断 |

> 事实来源类型：CIDR 2021《Databricks Lakehouse: A New Generation of Open Platforms...》；
> Databricks 官方文档对 lakehouse 与 medallion 的定义；AWS/GCP 官方文档对 data lake 架构的描述。
> 上表是本目录作者的整理，不是原书表格。

### 1.2 湖仓的四要素（判断"是不是湖仓"的清单）

```text
        ┌──────────────── 消费侧：BI / 数据科学 / ML / 流应用 ───────────────┐
        │  引擎（多引擎、可替换）：Spark · Flink · Trino · 云数仓 · Notebook  │
        └───────────────────────────▲───────────────────────┬──────────────┘
                                    │ 读写同一份表状态        │ 提交/回滚
        ┌───────────────────────────┴───────────────────────▼──────────────┐
        │  目录（Catalog）：表当前状态的权威指针 + 权限 + 血缘 + 业务元数据   │
        ├──────────────────────────────────────────────────────────────────┤
        │  表格式（Table Format）：快照 / 事务 / schema & partition evolution│
        ├──────────────────────────────────────────────────────────────────┤
        │  存储（Object Storage）：S3 / GCS / ADLS / HDFS + Parquet/ORC 文件 │
        └──────────────────────────────────────────────────────────────────┘
```

四条判据，任何一条不成立就不该叫湖仓：

1. **存储是开放的、可被非原厂引擎直接读的**（对象存储上的列式文件，而非某引擎专有格式）。
2. **表的"当前状态"由一份可版本化的元数据定义**，且写入是原子的（要么整个快照可见，要么不可见）。
   机制细节见 [../Engineering_Lakehouses_with_Open_Table_Formats/02-开放表格式的元数据布局总论.md](../Engineering_Lakehouses_with_Open_Table_Formats/02-开放表格式的元数据布局总论.md)。
3. **目录是共享服务**：权限、血缘、schema 在目录层表达，不埋在每个引擎里。
4. **多引擎并发读写同一张表**，且引擎可以换而不必迁数据。第 4 条是"成本换语义"这笔交易能否成立的检验点。

> ⚠️ 反面检验法（很实用）：问一句"如果明天把查询引擎换成别家的，我的数据要不要重写？"
> 要重写 → 那是数仓；不用重写但要不要重新爬元数据、重建权限 → 那是"湖 + 私有目录"。

### 1.3 为什么是"数仓 → 湖 → 湖仓"这个顺序

不是"人们先想到数仓再想到湖"，而是**约束条件按顺序打开**：

| 阶段 | 被打开的约束 | 被解决的问题 | 遗留问题（下一代的主线） |
| --- | --- | --- | --- |
| 数仓 | 计算与存储硬件可控、集中 | 数据可信：schema、主键、外键、ETL 校验、单一口径 | 单位成本；schema 变更成本高；只服务结构化 BI；ML 数据出不去 |
| 数据湖 | **存储单位成本**（对象存储按量、无限扩容、无 schema 约束） | 什么都能存：日志、事件、图像、JSON；schema-on-read；数据科学家自助 | **写入无事务**：并发写坏表、读到半写数据、无法回滚；无"当前状态"权威定义；治理与合规缺位；小文件 |
| 湖仓 | **元数据的表达力**（表格式 + 目录做在文件之上，成本几乎为零） | ACID、time travel、增量读、schema/partition 演化、行/列级策略、多引擎共享；一份数据同时支撑 BI + ML | 语义层与责任边界仍在组织侧；成本模型变复杂（存算分离后请求费、compaction 费、目录调用费都来了） |

三条推论，比"湖仓更好"更有用：

- **每一代都是在补上一代的"免费午餐"**：湖把存储做便宜了，但把事务、schema 治理、权限的账推给了读端；
  湖仓用元数据层把这些账还上，而代价是新增了**元数据维护成本**（compaction、快照过期、孤儿文件清理）。
- **"为什么不是直接改进数仓"**：数仓的语义长在引擎内部（私有存储格式 + 私有优化器），
  要让它接受无限扩容的廉价存储，等于重写存储层——这在商业上和技术上都比"在湖上补语义"难。
- **"为什么不是直接改进湖"**：纯文件系统的 list 语义、rename 语义在对象存储上不成立
  （S3 不提供目录级原子 rename；这是 AWS 官方文档明确的事实），
  所以湖必须在文件之上**新建一层元数据**，而不是修补文件系统。

### 1.4 分层建模：medallion 与数仓分层的对照

Databricks 把 lakehouse 的数据阶梯称为 **medallion（奖牌）架构**：bronze → silver → gold。
国内的**数据中台/数仓分层**（阿里《大数据之路》口径的 ODS/DWD/DWS/ADS）解决同一个问题：
把"脏、乱、变"与"稳、准、用"隔离开。二者可对照但不可等同：

| 层 | medallion | 中台/数仓分层 | 这一层的真正职责 | 常见错位 |
| --- | --- | --- | --- | --- |
| 原始层 | Bronze（raw） | ODS | **只增不改**、保留来源结构与全部字段；审计与重放的锚点 | 在 bronze 做清洗 → 丢了"可重放"这一唯一价值 |
| 清洗/明细 | Silver（cleansed） | DWD | 去重、标准化、类型化、主键唯一、质量规则生效；**事实与维度的明细粒度** | 直接把银层当报表层用；跨主题混合造成耦合 |
| 服务层 | Gold（aggregated / marts） | DWS/ADS | 面向用例的聚合、宽表、特征、语义层出口 | 把"所有需求"都堆在 gold，导致重复存储与口径漂移 |

三点辨析：

1. **medallion 是"数据质量阶梯"，不是维度建模的替代**。
   银层里仍然要做 Kimball 式的事实/维度与一致性维度——建模理论在
   [../数据仓库工具箱.md](../数据仓库工具箱.md)、[../数据库系统概念6/20-数据仓库与数据挖掘.md](../数据库系统概念6/20-数据仓库与数据挖掘.md)。
2. **层与层之间靠"表格式的增量读"衔接**，这是湖仓相对传统分层的实质优势：
   银层作业可以只读 bronze 的新快照（incremental read / change data feed），
   于是同一条 SQL 逻辑既能跑全量回刷也能跑增量——批流一体的落点就在这里（见 1.5）。
3. **分层数量不是越多越好**。每加一层就多一份存储、一套 SLA、一条血缘边；
   判据是"这一层是否被至少两个不同的下游独立消费"，否则它只是缓存。

### 1.5 批流一体在架构中的位置

先拆掉一个混淆：**"批流一体"不等于"一个引擎既能跑批又能跑流"**（Spark/Flink 早就都能）。
湖仓语境下的批流一体有三条实际不同的路线：

| 路线 | 做法 | 代表 | 解决了什么 | 没解决什么 |
| --- | --- | --- | --- | --- |
| **统一引擎** | 同一套 DataFrame/SQL API，微批或连续执行 | Spark Structured Streaming、Flink | 一份代码两种模式，减少逻辑漂移 | 结果一致性依赖 watermark/触发器调参；迟到数据与状态仍要处理 |
| **统一表（表存储即状态）** | 流的 checkpoint 就是表快照；下游直接读表 | Iceberg/Hudi/Paimon + 流式写入 | 中间状态持久化、可回溯、可增量读、失败可直接重放 | 提交频率与文件粒度的矛盾（小文件）、compaction 归属 |
| **统一语义/物化** | 声明目标视图，由平台决定增量刷新还是全量重建 | Databricks 增量物化视图、BigQuery materialized view、Redshift streaming ingestion | 用户不必关心批还是流 | 刷新延迟是尽力而为；成本随刷新频率上升 |

- 本目录把"统一表"当作湖仓的**主流路线**：因为对象存储便宜，把状态写在表里比写在引擎内部状态里更可运维
  （可查、可回放、可多引擎消费）。对照 [../bigdata/07-实时计算与流式架构.md](../bigdata/07-实时计算与流式架构.md) 的 Lambda/Kappa 讨论。
- **一个必须问的问题**：谁负责把"流式写入产生的小文件"合掉？
  引擎侧、表格式侧还是平台托管？这决定了写入频率上限与查询 P99（第 3 章、第 5 章各自展开）。

### 1.6 湖仓没有解决的四件事

| 未解决 | 表现 | 真正的解法在哪 |
| --- | --- | --- |
| **语义一致性** | 同一个"活跃用户数"在 BI、报表、模型特征里三口径 | 指标/语义层 + 数据契约与评审流程（第 7 章） |
| **新鲜度承诺** | 表存在但下游不知道它什么时候可用 | SLA/SLO 化：每层声明 freshness 与 completeness 指标（第 7 章） |
| **责任边界** | 平台团队成了所有数据问题的 bottleneck | 域所有权 / data mesh 的组织改造（第 2 章、第 7 章） |
| **成本归因** | 账单只有一个总数，不知道谁花的 | 标签、查询审计、按表/按团队归因的 FinOps 工程（第 7 章、第 8 章） |

一句话：**湖仓是一种数据平台架构，不是一种数据治理方法论**。把它当后者用，一定翻车。

### 1.7 什么时候不该上湖仓（反向判据）

1. **数据规模小于"引擎存储成本可忽略"的门槛**：几 TB 以内、并发查询不高，直接托管数仓
   （BigQuery / Redshift / Synapse）运维面更小；湖仓的四层结构在这里纯属负担。
2. **负载只有 BI 报表、且 schema 十年不变**：数仓的强 schema 与结果缓存更省人。
3. **强隔离合规场景**（如金融核心明细数据不允许共享存储桶）：多引擎共享一份数据正是湖仓的卖点，
   也是这类场景的风险点；隔离优先时选专用仓库 + 出仓审批。
4. **团队没有能力承担"元数据运维"**：compaction、快照过期、孤儿文件、目录容量与锁争用都需要人。
   没有数据平台角色时，选全托管服务（S3 Tables、BigQuery 外部目录、Databricks 托管）而不是自建。
5. **只是为了"技术先进性"**：见第 8 章事故模式——最常见的失败是"先建湖仓，再找用例"。

## 成本与运维取舍（本章层）

| 取舍 | 便宜的做法 | 贵但正确的做法 |
| --- | --- | --- |
| 判断是否要湖仓 | 直接建 | 先做用例—SLA—数据量的三维盘点（第 7 章方法） |
| 分层 | 全塞一层 | 三层，且每层显式声明消费方与 SLA |
| 批流 | 维护两套管道（Lambda） | 以表为状态的统一管道，接受 compaction 成本 |
| 元数据 | 不管快照保留期 | 明确 N 天保留 + 定期过期，写进作业 SLA |
| 组织 | 平台团队包揽 | 域所有权 + 平台只提供"铺设好的道路"（ paved roads） |

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "湖仓就是把数据湖改名叫湖仓" | 判据是四要素；没有表格式与共享目录的"湖仓"仍是数据湖 |
| 2 | "上了湖仓就能同时省成本和获得数仓性能" | 存算分离省的是**存储**；查询成本随扫描量线性走，缓存与物化要另外花钱 |
| 3 | "medallion 三层就是 ODS/DWD/ADS，直接照搬即可" | bronze 的价值在"不可变 + 可重放"；把清洗前移到 bronze 或把需求堆在 gold 都是错位 |
| 4 | "批流一体 = 用 Flink 而不是 Spark" | 真正的统一在"表即状态 + 增量读"；引擎只是执行器 |
| 5 | "湖仓天然治理良好，因为有权限" | 策略只在目录层表达才生效；绕过目录直连对象存储即可逃逸（第 6 章） |
| 6 | "Lakehouse 支持 ML，所以模型自动可信" | 模型可复现需要训练数据快照 + 特征一致性 + 血缘，全部是额外工程（第 6 章） |
| 7 | "数据量小就别上湖仓"是绝对真理 | 反判据在 1.7；但"以后会长大"的合法理由也存在——要按增长斜率而非当前量判断 |
| 8 | 认为"表格式"是可选装饰 | 没有它，并发写会损坏表；这是 S3 语义决定的硬约束（第 3 章） |
