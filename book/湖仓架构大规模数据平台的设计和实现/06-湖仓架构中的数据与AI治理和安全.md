# 第 6 章 湖仓架构中的数据（与 AI）治理和安全

> 章题按核实目录（第 6 章 湖仓架构中的数据（与AI）治理和安全）。本章**不复述书中语句**；
> 论断以 AWS / GCP / Databricks / Apache 官方文档与公开法规原则为据。所有示例为**教学示意，不参与构建**。

## 本章地图

> 一句话：**湖仓的安全模型必须"跟着数据走"而不是"跟着引擎走"**——
> 数据在共享存储上被多引擎访问，任何写在某个引擎里的权限，都会在第二个引擎接入时失效。

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 6.1 治理的四个动词 | 发现、理解、可信、合规 | 治理不是"管控"，是可执行的元数据 |
| 6.2 身份与授权的四层落点 | 存储/IAM → 目录 → 表/列/行 → 引擎 | 只在一层设防等于没设防 |
| 6.3 加密与密钥 | SSE/KMS/BYOK/HYOK、客户端加密、机密计算 | 加密解决"盘被偷"，不解决"谁在查" |
| 6.4 脱敏与最小可用 | 静态/动态脱敏、tokenization、DP | 按"用例需要的最小信息量"设计 |
| 6.5 删除权与不可变 | 逻辑删除 ≠ 物理删除；快照/备份/版本都要追 | 合规删除是"重写型"操作，需要成本预算 |
| 6.6 血缘、质量与可观测 | 列级血缘、质量门槛、SLA 指标 | 血缘是所有治理动作的证据链 |
| 6.7 AI 治理与数据合规 | 训练数据可复现、特征一致性、模型资产权限 | "湖仓支持 ML"不等于"ML 可信" |
| 6.8 治理的执行成本 | 策略 join 开销、审批流、绕过检测 | 治理要有性能预算，否则会被绕过 |

## 核心精讲

### 6.1 治理的四个动词（把"治理"拆成可交付事项）

| 动词 | 交付物 | 在湖仓里的技术抓手 |
| --- | --- | --- |
| 发现（findable） | 表/列可搜索、有 owner、有分类标签 | 目录的业务元数据、标签、扫描发现（Dataplex/Glue/Unity） |
| 理解（understandable） | 口径、单位、示例值、变更历史 | 术语表 + schema 版本 + 数据合约文档挂在表上 |
| 可信（trustworthy） | 新鲜度、完整度、质量规则通过率 | 质量作业 + SLA 指标 + 血缘定位故障源 |
| 合规（accessible with policy） | 权限、脱敏、留存、审计、可删除 | 目录策略 + 加密 + 审计日志 + 生命周期 |

> 这四条对应 Databricks/AWS/GCP 文档里反复出现的 "discoverable / understandable / trustworthy /
> access-controlled" 表述（各家措辞略异）。本目录作者的整理口径，不假装是原书表格。

### 6.2 身份与授权的四层落点

```text
L4 引擎/工具     BI 语义层权限、Notebook 角色（最脆弱：易与数据脱钩）
L3 行/列策略     row filter、column mask、数据过滤表达式（最贴近用例）
L2 目录对象      catalog/schema/table 的 GRANT、角色、ABAC 标签（集中、可审计）
L1 云身份与存储  IAM/服务主体、桶策略、KMS key policy（最粗，也是最后防线）
```

**每层的具体形态（公开文档口径）**：

| 层 | AWS | GCP | Databricks | 开源 |
| --- | --- | --- | --- | --- |
| L1 | IAM + S3 bucket policy + KMS key policy | 项目/IAM + GCS ACL/IAM + CMEK | 云 IAM + 存储凭据（storage credential） | Ranger / OPA |
| L2 | Lake Formation（数据库/表/列级 perms） | Dataplex Universal Catalog + 策略标签(taxonomy) | Unity Catalog grants（含 ABAC） | Polaris/REST catalog 角色、Gravitino |
| L3 | LF data filters、Redshift 行/列安全策略 | Dataplex data policy / BigQuery masked policies（⚠️ 以文档为准） | row filter + column mask（SQL 函数绑定表） | 引擎侧 RLS（支持度不一） |
| L4 | Athena/QuickSight 数据集权限 | Looker/Studio 角色 | SQL 仓库通道与外部引擎共享 | 各 BI 自带 |

**三条原则**：

1. **策略必须绑在数据对象上，不绑在访问路径上**。绑在表上 → 任何引擎访问都生效；
   绑在"某个 BI 数据集"上 → 换个工具就绕过。
2. **身份要一路传播**。若所有作业共用一个宽泛的执行角色，审计日志只能记录"角色查了表"，
   无法记录"某人查了表"——这在合规检查里等同没有审计。
   做法：目录/引擎支持用户级身份穿透（如 Unity 的 passthrough / delegated credentials、各云 SSO 集成）。
3. **存储层要堵住"绕过目录"的路**。桶策略限制为只允许经目录服务下发的临时凭证访问，
   并禁止公共读、开启 TLS 与 KMS 条件（AWS/GCP 官方最佳实践均如此建议）。

### 6.3 加密与密钥：解决什么、不解决什么

| 手段 | 保护对象 | 不能保护 |
| --- | --- | --- |
| 传输加密（TLS/强制 HTTPS 桶策略） | 中间人 | 落盘后访问 |
| SSE（服务商托管密钥 SSE-S3 等） | 介质失窃、越权拉取 | 有权限者滥用；对服务商不可见性无承诺 |
| SSE-KMS + 客户管理密钥（CMEK/BYOK） | 可撤销访问（禁用 key 即数据不可读）、密钥级审计 | 授权前已被合法读取的数据 |
| HYOK/外部密钥存储 | 更强的自主控制与合规边界 | 性能与可用性（KMS 调用在数据路径上） |
| 客户端加密/字段级加密 | 连服务商都看不到明文 | 无法在密文上做谓词下推（查询能力受损） |
| 机密计算/隔离环境 | 内存中数据 | 运维复杂度、成本、可用性 |

- **实施要点**：KMS key 的**权限与数据权限要分开管理**——数据科学团队通常不应持有能解密全量原始桶的 key。
  常见做法是按 medallion 层用不同 key，bronze 收紧、gold 放宽。
- **审计要点**：KMS 调用本身也是事件（CloudTrail 等），可用来发现"异常批量解密"。

### 6.4 脱敏与最小可用

| 手段 | 生效位置 | 优点 | 代价 |
| --- | --- | --- | --- |
| 静态脱敏（写入时就脱） | 银层/金层作业 | 一份策略、查询无开销、可自由分享 | 原始数据不可用；策略变更需重刷 |
| 动态掩码（读取时脱） | 目录/引擎策略（column mask、LF/BigQuery policy） | 保留原数据、按人/角色差异化 | 每次查询执行表达式；策略复杂后有性能影响 |
| Tokenization / 保留格式加密 | 采集或管道阶段 | 可逆、可跨系统关联 | 需 token vault，密钥治理是新的关键路径 |
| 差分隐私（DP） | 聚合出口层（Google DP 框架思路） | 有数学化隐私预算 | 结果带噪、实现门槛高，适合统计接口 |
| k-匿名/泛化 | 出口数据集 | 简单 | 可被连接攻击 |

**设计问题（不是技术问题）**：给数据科学家的是"金层脱敏视图"还是"银层动态掩码"？
选择依据是**用例需要的最小信息量**——如果建模只需要年龄段而非生日，就在银层泛化，
把动态脱敏留给临时排查；反过来做会把成本花在每次查询上。

### 6.5 删除权与"不可变"的正面冲突

**"删除某个用户的所有数据"在湖仓里是一次全链路重写**：

1. 找到所有含该主键的表与列（需要血缘 + 分类标签，否则只能全扫）。
2. 在表格式侧执行 delete/merge（Iceberg/Hudi/Delta 均支持行级删除，⚠️ 语义按各格式规范）。
3. **快照过期 + 文件重写（compaction/vacuum）**：只要旧快照仍可读，数据就没有真的消失。
4. **副本与衍生**：跨区域复制、备份、金层聚合、缓存、导出到 BI extract 的数据都要处理。
5. **审计留痕**：删除动作本身要记录（谁批准、影响哪些表、完成时间）。

- 与 **WORM/不可变存储**（S3 Object Lock、GCS 锁）冲突时，要按法规优先级明确"业务保留期"与
  "删除请求"的边界，常见解法：**分层隔离**——合规留存放独立表/独立桶（锁定），
  可分析副本放湖仓主体并支持删除。
- **备份策略**要写清"备份里的历史数据如何处理"：多数方案是"备份到期自然消亡 + 不再从旧备份恢复含该数据的表"。
- ⚠️ 法规依据（GDPR 删除权、PIPL 等）不在此展开；本目录只描述**技术可实现性**，法律边界请咨询合规团队。

### 6.6 血缘、质量与可观测（证据链）

| 能力 | 采集点 | 用途 |
| --- | --- | --- |
| 表级/列级血缘 | 引擎执行计划回写目录（Unity/Dataplex 等）或作业元数据 | 变更影响分析、删除权定位、事故溯源 |
| 数据质量规则 | 银层作业前后断言（空值率、唯一键、值域、行数波动） | 阻断脏数据进金层（quality gate） |
| 新鲜度/完整度 SLA | 调度与目录指标 | 让"能不能用"变成可查元数据 |
| 访问审计 | 云审计 + 目录/引擎查询日志 | 合规取证、异常检测 |
| 成本归因 | 标签 + 查询日志聚合 | FinOps（第 7 章） |

- 方法论对照：[../数据血缘分析原理与实践.md](../数据血缘分析原理与实践.md)、[../bigdata/12-数据质量与工程实践.md](../bigdata/12-数据质量与工程实践.md)。
- **一个关键顺序判断**：血缘必须在**接入与银层作业上线的当天**就有，事后补的成本是指数级的
  （因为没人记得旧作业为什么这么写）。

### 6.7 AI 治理：湖仓的"与 AI"那半句

| 需求 | 技术抓手 | 失败表现 |
| --- | --- | --- |
| 训练数据可复现 | 训练时绑定**表快照/时间旅行版本**，写入实验元数据 | 模型无法复现、审计无法回答"训练用了什么" |
| 特征一致性 | 特征视图/特征库与银层表同源；离线与在线同一份定义 | 训练/线上不一致（leakage、口径漂移） |
| 模型资产权限 | 把模型当作目录里的一等对象（Unity models/MLflow）授权 | 模型能上线但没人能解释它依赖哪些数据 |
| 数据出域限制 | 训练作业只能在数据所在区域/项目运行；导出需审批 | 训练数据被复制到宽松环境 |
| 隐私风险 | 聚合/脱敏后再入模；避免原始标识符进入特征 | 模型记住敏感个体 |
| 非结构化数据 | 目录管理"文件集/volume"，权限与表一致（Unity volumes / S3 + 前缀策略） | 向量库/文件桶成了治理盲区 |

- **可执行清单（本目录作者给出）**：任何上线模型必须能回答四个问题——
  训练数据是哪张表的哪个快照？血缘下游有哪些指标/服务？敏感列如何处置？失效/重训触发条件是什么？
- 与 AI 平台笔记对照：[../../大模型](../../大模型)（工程视角）、[../../机器学习.md](../../机器学习.md)（特征与样本的上位方法论）。

### 6.8 治理的执行成本与"被绕过"的风险

- 行过滤/列掩码是**在查询执行路径上求值的表达式**：复杂掩码函数会破坏谓词下推与向量化，
  让"加一条策略"变成"慢十倍"。缓解：把策略拆成"分类标签 + 简单谓词"、必要时为高敏数据建独立物化视图。
- **审批流不要压在平台团队身上**。域内 owner 批准 + 平台提供策略原语，是唯一能规模化的形态（联邦治理）。
- **绕过检测**要常态化：桶公开访问、跨账号策略放宽、BI extract 落盘、
  临时查询导出到本地——这些"逃逸路径"决定了实际安全水位。
- **性能预算**：给每条策略一个可测量的开销预算（P95 延迟增幅 < x%），超预算的策略要重写或改为静态脱敏。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "KMS 加密了就是安全" | 加密保护介质，不保护授权；有权限的人照样能读明文 |
| 2 | "IAM 桶策略就是湖仓权限" | 桶策略粒度太粗；行列级必须靠目录与策略层 |
| 3 | "在 BI 工具里设好权限就够了" | 策略绑访问路径而非数据对象，换个引擎即绕过 |
| 4 | "DELETESQL 执行完 = 数据已删除" | 快照、备份、副本、聚合下游仍可能存在；需要过期 + 重写 + 追踪 |
| 5 | "血缘是锦上添花" | 没有血缘，删除权、影响分析、事故定位都做不了 |
| 6 | "动态脱敏零成本" | 表达式在查询路径上求值，可能破坏下推；要性能预算 |
| 7 | "湖仓支持 ML，所以模型可信" | 可复现性来自快照绑定 + 特征同源 + 资产权限，全部额外工程 |
| 8 | "统一执行角色简化权限管理" | 代价是审计失效与横向越权；身份必须传播 |
