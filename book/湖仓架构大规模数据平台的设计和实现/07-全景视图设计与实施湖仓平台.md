# 第 7 章 全景视图：设计与实施湖仓平台

> 章题按核实目录。本章**不复述书中语句**；方法论综合自公开参考架构、平台工程实践与本仓库既有笔记。
> 所有图示与配置为**教学示意，不参与构建**。

## 本章地图

> 一句话：**设计顺序必须是"用例 → SLA → 分层 → 组件 → 组织 → 度量"**；
> 绝大多数失败的湖仓项目是从"组件"开始的（先选工具，再找用途）。

| 7.4 编排与作业工程 | 幂等、重跑、回填、迟到、依赖 | 作业规范比调度工具更重要 |

## 核心精讲

### 7.1 设计方法：从用例倒推

**第 0 步：用例清单**（每行必须能落到"谁、看什么、多快、错了会怎样"）

| 用例类型 | 延迟要求 | 完整度要求 | 消费方式 | 典型层 |
| --- | --- | --- | --- | --- |
| 监管/财务报送 | T+1 | 必须全且可追溯 | 固定报表 + 审计 | gold |
| 经营看板 | 分钟–小时 | 允许小缺口 | BI 交互 | gold |
| 风控/推荐特征 | 秒–分钟 | 关键维度不可缺 | 服务 API / 特征库 | silver→gold |
| 数据科学探索 | 小时–天 | 允许样本近似 | Notebook 直读 | silver/bronze |
| 运维可观测 | 秒 | 高基数 | 日志/时序引擎 | bronze（短期） |

- **SLA 三维模板**（每张表都要有）：新鲜度（数据到位时间）、完整度（缺失率上限）、
  保留期（快照/历史可回溯多久）。写进目录的元数据，而不是文档里。
- 反例检查：如果一个用例无法说出"晚 1 小时会怎样"，它大概率不需要流式管道（省下最大的成本）。

### 7.2 端到端参考架构（教学示意，不参与构建）

```text
 源系统            接入层                存储+格式+目录                消费
┌────────┐  CDC     ┌──────────────┐   ┌──────────────────────────┐   ┌────────────┐
│ OLTP   │────────► │ 事件总线/队列 │──►│ Bronze: 原始、只增、可重放│   │ BI/语义层  │
│ SaaS   │ 批量     │ 文件落地     │   │ Silver: 清洗、去重、维度  │──►│ 数据科学   │
│ 日志   │────────► │ Schema 注册   │   │ Gold: 聚合、特征、视图    │   │ 反向ETL    │
│ IoT    │          └──────────────┘   └──────────────────────────┘   └────────────┘
└────────┘                ▲                      ▲        ▲
                     编排/调度 ────────────────────┘        │
                     质量门槛 + 数据契约 ────────────────────┘
                     目录（元数据/权限/血缘）  观测（SLA/成本/审计）
```

要点：

1. **接入层承担"变化隔离"**：源系统改字段先打在 bronze 的原始载荷上，不影响下游（schema-on-read 的正确用法）。
2. **银层是契约生效的地方**：主键唯一、类型标准化、去重、单位换算、维度一致性——这些不是"清洗"，是**定义业务事实**。
3. **金层面向出口**：为每个消费场景建视图/聚合，而不是让 BI 直连银层（否则银层重构会打死所有报表）。
4. **两条横向能力**（编排、目录/观测）必须平台统一提供；这是"平台"与"一堆作业"的分界。

### 7.3 分层规范与数据契约

| 规范项 | 建议做法 | 原因 |
| --- | --- | --- |
| 命名 | `<层>_<域>_<实体>_<粒度>`，层前缀强制 | 让人一眼判断可信度与消费资格 |
| owner | 每张表必填负责人 + 团队标签 | 无主表是成本与风险的源头 |
| schema 变更 | 加列向前兼容；改名/改类型走 **field-id/列映射 + 评审** | 避免下游静默读错（对照姊妹目录的 schema evolution） |
| 兼容性分级 | `backward / forward / breaking` 三档，breaking 需新版本并行 | 让迁移有节奏 |
| 质量门槛 | 银层出口断言（空值率、唯一键、行数波动阈值）失败即阻断金层刷新 | 阻止脏数据扩散 |
| 版本并行 | 新逻辑上线时旧表保留 N 天双跑 | 回退保险 |
| 文档即元数据 | 口径、单位、示例、变更史挂在目录 | 文档在仓库里会过期，目录里不会 |

> 数据契约（data contract）不是新工具，而是"把 schema + SLA + 变更流程写成可执行断言"的工程习惯。
> 机制层参考：[../Engineering_Lakehouses_with_Open_Table_Formats/03-Iceberg表格式机制.md](../Engineering_Lakehouses_with_Open_Table_Formats/03-Iceberg表格式机制.md)（field-id 与演化）。

### 7.4 编排与作业工程

**湖仓作业的六条硬性规范**（比选哪个调度器重要得多）：

1. **幂等**：同一批次重跑结果一致。手段：按快照/分区覆盖写、MERGE upsert、去重键。
   —— 表格式的事务让"覆盖写"第一次变得安全（读端要么旧快照要么新快照）。
2. **可回填（backfill）**：任何增量作业必须能接受"从任意时间开始重算"的参数，并与增量共用同一 SQL 逻辑。
3. **依赖表达**：以"上游表的快照版本 + SLA 达成"作为触发条件，而不是"上游作业成功退出"。
4. **迟到数据策略**：显式声明（更新旧分区 / 旁路合并 / 丢弃），见 5.4。
5. **重试与退避**：区分可重试（限流、瞬时 IO）与不可重试（schema 不匹配、权限）。
   目录/API 限流是湖仓特有的高频瞬时错误（见 4.3）。
6. **成本可观测**：每个作业上报处理字节数、扫描字节数、提交次数——归因是治理的前提。

**常见编排反模式**：

| 反模式 | 后果 | 修正 |
| --- | --- | --- |
| 全量重刷当万能补丁 | 成本随数据量线性增长；窗口期越来越长 | 只重写受影响分区 + 定期小全量校验 |
| 作业串联成隐式依赖链 | 一处失败全线雪崩，恢复顺序未知 | 依赖以数据就绪为准 + 关键路径分级 |
| 调度器重试风暴 | 打爆目录与对象存储前缀吞吐 | 限流 + 抖动退避 |
| 每团队一个调度系统 | 无法统一 SLA 与成本视图 | 统一编排平面，允许域内自治作业 |

### 7.5 环境、发布与 IaC

- **环境矩阵**：`dev`（小样本、可随意重建）/ `test`（契约与回归）/ `prod`（真实数据，权限收紧）。
  湖仓特殊点：**元数据（表定义、权限、策略、生命周期规则）也要有环境**，否则测试环境会污染生产目录。
- **建议纳入版本控制的对象**：表 DDL、目录/桶策略、生命周期规则、compaction/过期作业参数、
  质量规则、SLA 定义、调度 DAG。
- **发布流程**：DDL 变更走评审 PR；breaking change 采用"新表并行 + 视图切换 + 弃用公告"；
  任何切换都要有可验证的回退点（表格式的历史快照/时间旅行正好是天然的回退点）。
- 对照 [../凤凰架构.md](../凤凰架构.md)、[../演进式架构.md](../演进式架构.md)：可回退性是架构演进的一等属性。

### 7.6 迁移路线：从"数仓 + Hadoop 双栈"到湖仓（六步）

| 步 | 动作 | 完成判据 | 常见坑 |
| --- | --- | --- | --- |
| 1 盘点 | 表/作业/消费者/成本/新鲜度清单；标注僵尸资产 | 覆盖率 ≥ 90% 的资产有 owner | 只盘表不盘"谁在读" |
| 2 立底座 | 存储 + 表格式 + 目录 + 编排四件套就位并打通血缘 | 新建表默认带 SLA/owner/权限 | 先建工具后定规范，规则补不回来 |
| 3 试点域 | 选一个"痛但可控"的业务域端到端迁移 | 成本/延迟/故障恢复时间有量化对比 | 选最简单的域 → 无法说服其他团队 |
| 4 双写共存 | 源系统同时进旧栈与新栈；比对结果 | 差异率低于阈值且有自动比对作业 | 只做一次性比对，不持续 |
| 5 切读 | 消费者按批次切换（BI/ML/服务） | 每个消费者签署切换记录 | 忘记"隐式消费者"（导出文件、脚本） |
| 6 退役 | 旧栈只读 → 归档 → 删除；成本复盘 | 账单出现真实下降 | 保留"以防万一"的只读副本，成本永远不降 |

- **顺序判断**：先迁**新增用例**到湖仓（增量），再迁存量（改造）。反过来会把平台能力建设拖成一年。
- 与组织笔记对照：[../中台架构与实现.md](../中台架构与实现.md)、[../企业IT架构转型之道.md](../企业IT架构转型之道.md)。

### 7.7 组织与角色

| 角色 | 职责 | 失败信号 |
| --- | --- | --- |
| 平台工程 | 存储/目录/格式/编排/观测底座，SLA 与成本护栏 | 平台团队开始替业务写 SQL 逻辑 |
| 域数据工程 | 本域建模、契约、质量规则、作业 | 域内表无 owner 或 owner 是平台 |
| 数据治理/合规 | 分类分级、策略、审批、审计 | 治理只管审批不管策略原语供给 |
| 分析/ML 消费者 | 用例与反馈 | 绕过金层直连银层 |

- **paved roads（铺设好的道路）**优于强制：把"建表模板 + 自动接目录 + 自动 compaction + 自动质量门槛"
  做成 5 分钟可用的自助能力，规范自然被采纳。
- 平台规模经验值（教学示意）：平台:业务数据工程 ≈ 1:3；表数千以内可用集中治理，
  上万张表必须域自治 + 平台策略原语。

### 7.8 平台 KPI 与 FinOps

| 类别 | 指标 | 目标形态 |
| --- | --- | --- |
| 可靠 | 关键管道 SLA 达成率、平均故障恢复时间 | ≥ 99% 且有趋势图 |
| 新鲜 | 金层可用水位延迟 P95 | 与用例 SLA 对齐 |
| 覆盖 | 有 owner/SLA/分类标签的表占比 | > 90%（低于 70% 说明治理是空谈） |
| 质量 | 质量门槛拦截次数、下游缺陷归因 | 拦截数上升是好事 |
| 成本 | 每 TB 存储月成本、每千次查询计算成本、按团队归因比例 | 归因覆盖 > 80% |
| 效率 | 新建一张合规表的时长、作业失败重跑率 | 时长应降到小时级 |
| 安全 | 绕过检测告警数、权限审批中位时长 | 告警必须闭环 |

- **FinOps 的具体抓手**：给表/作业/目录打团队标签 → 从查询日志与账单聚合出归因 →
  把"单位成本"回灌到设计决策（是否物化、是否升档存储类别、是否降写入频率）。
- ⚠️ 没有归因的成本治理一律退化为"要求大家省点用"。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 先选工具再找用例 | 用 7.1 的清单倒推；工具是用例的函数 |
| 2 | SLA 写在文档里 | SLA 必须是目录元数据 + 可监控指标 |
| 3 | 迁移=数据搬迁 | 迁移的主成本是元数据、权限、作业逻辑与消费者切换 |
| 4 | 让平台团队承担所有建模 | 平台供给原语与道路，建模是域内职责 |
| 5 | 双写只是临时手段，不用做比对 | 没有自动比对的双写等于没有验证 |
| 6 | 回填是特殊情况 | 回填是常态能力；不能重算的管道不具备生产资格 |
| 7 | 环境只区分数据不同，元数据共用 | 共用目录会让测试 DDL 直接改坏生产 |
| 8 | 成本治理靠砍资源 | 先看布局/物化/频率三处，砍资源通常砍错地方 |
