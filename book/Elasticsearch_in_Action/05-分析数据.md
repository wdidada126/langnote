## 5.1–5.3 流水线与双向分叉（⚠️ 转述）

同一段文本，索引期与分析期分析器**可以不同**（search-time analyzer），这是「索引宽进、查询严出」的旋钮。analyze API 是唯一肉眼工具：改 analyzer 后不发版也能在开发集群里验证输出词项——本章的实操记忆点。内置分析器（standard/simple/whitespace/keyword/stop/pattern…）清单今仍在（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/analysis.html 实抓、现代文档入口 https://www.elastic.co/docs/manage-data/data-store/text-analysis 实抓）。
1.x 特色：`analyzer` 直接写在 string mapping 上；餐厅书例里给菜名挂标准分析器、给标签用 keyword 分词器（不分词只留整串）——「字段级选型」框架不变。

🔧 类比组 B（SQLite 3.45.3 实跑，词干化对照）：

```sql
CREATE VIRTUAL TABLE p USING fts5(body, tokenize='porter unicode61');
INSERT INTO p VALUES ('running searches quickly');
SELECT count(*) FROM p WHERE p MATCH 'run';     -- 1（porter 把 running→run, searches→search）
-- 对照无词干表（tokenize='unicode61'）：MATCH 'run' 得 0
```

porter 过滤器≈ES 的 porter_stem/snowball；unicode61 对照 ES standard 的「不折叠裸词」侧。**FTS5 词干化在索引期固化、查询期也 stem 查询词**——与 ES index/search analyzer 可分叉的设计不同，外推到此为止。

## 5.4 三件套组装自定义分析器（⚠️ 转述）

自定义 analyzer 挂进 index settings：`char_filter`（先动字符：去 HTML、拼写纠正 mapping）→ `tokenizer`（先动切分：standard 按 Unicode 词边界、keyword 整串、ngram 滑窗）→ `token filter`（再动词项：lowercase、stop 去停用词、asciifolding é→e、synonym 同义扩展、stemmer 词干）。组合定律：**顺序即语义**，synonym 放 stem 前/后结果不同——本章留给读者的最重要工程题。
中文提醒（⚠️）：standard 分词器对 CJK 按单字切，1.x 正确姿势是 ik/smart_chinese 类**分析插件**（附录 B 语境）；今天官方立场是用 analysis-icu/smartcn（内置化）或向量语义层兜底（⚠️ 转述，✅ 同族文档 https://www.elastic.co/guide/en/elasticsearch/reference/8.17/analysis.html）。

## 5.5 ngram / edge ngram / shingles（⚠️ 转述）

- ngram：全滑窗（min~max）——用于模糊/拼写容错索引，代价是词项爆炸。
- edge ngram：左端锚定滑窗——**搜索自动补全的索引侧正解**：索引期把 salad 切成 s/sa/sal/sal…，查询期用 keyword 不分词直查前缀词项（附录 F 的 completion suggester 是另一条路线，两相对照在本册 12 章收束）。
- shingles：词元+邻近词组合，捕捉短语级意图。
第 4 章 🔧 组 D 的 FTS5 trigram 实验即本节的类比件：预切子串词项换运行时 wildcard 的线性扫（**FTS5 只有定长 trigram、无 min/max 调节，也无关掉 edge 语义**，非 ES 行为）。

## 5.6 词干化的取舍（⚠️ 转述）

词干化提召回伤精度（run→running 互相串门）；官方一贯建议**搜索型产品 AB 后再上**，且英文用 porter 系、多语用 snowball 语系包。1.x 的 language analyzers 一节已含各语 stop+stem 预配（✅ 8.17 同族 https://www.elastic.co/guide/en/elasticsearch/reference/8.17/analysis.html）——这条知识线几乎无折旧。

## 工程要点与常见坑

- 改了 search analyzer 立即生效，改了 index analyzer 必须 reindex——「一半分析器是配置，一半分析器是数据」是本册记法。
- synonym 规则文件热更在 1.x 只能靠 reload-search-analyzers API（有限制），今天仍是运维痛点（⚠️）。
- edge ngram 放索引期+keyword 放查询期的组合，忘了对称配置就会「补全能搜、完整词搜不到」（经典事故）。

## 分析器实验台（⚠️ 转述，1.x 版式）

```bash
# 自定义分析器：HTML 清洗 + 标准分词 + 小写/英语词干/同义词
curl -XPUT localhost:9200/restaurants -d '{
  "settings": { "analysis": {
    "filter": { "en_snow": { "type":"snowball", "language":"English" },
                "syn": { "type":"synonym", "synonyms":["greek,hellenic"], "updateable": true } },
    "analyzer": { "menu": { "type":"custom", "char_filter":["html_strip"],
                "tokenizer":"standard", "filter":["lowercase","en_snow","syn"] } } }},
  "mappings": { "type1": { "properties": {
    "dish": { "type":"string", "analyzer":"menu",
              "fields": { "raw": { "type":"string", "index":"not_analyzed" } } } }}}}'
curl -XPOST localhost:9200/restaurants/_analyze?analyzer=menu -d 'Hellenic <b>Salads</b>'
# → 词项：greek salad（同义词+词干+小写三连环，一屏看尽 5.4）
# edge ngram 补全索引侧：tokenizer=edge_ngram(min 1, max 20) 于索引期，查询期 keyword
```

实验台心法：analyze API 是唯一的「先验证再上线」通道——任何 analyzer 变更先在这里打样，再进 mapping；
`updateable` 同义词（1.x 有限）对应今天的 reload_search_analyzers（⚠️）。

## 章内问答（自测）

**Q1 index 与 search analyzer 分叉何时正当？**
A：索引期宽（存原形+词干）、查询期严（不做词干只做小写）等历史权衡；今天更常见的是同构配置防「解释成本」。
**Q2 synonym 放 stemmer 前还是后？**
A：先同义后词干——规则里写整词（greek,hellenic），词干化在两边各自发生；顺序反过来规则永远不命中。
**Q3 为何 keyword 分词器「反直觉」？**
A：它不切分、整串一个词项——用于枚举/ID/标签精确域；拿它做全文等于回到 term 的世界。

## 核心概念速览（中英对照）

1. **分析** — Analysis：文本→归一词项序列的索引前处理。
2. **分析器** — Analyzer：char_filter+tokenizer+token_filter 的流水线单元。
3. **索引期/查询期分析器** — Index/Search-time Analyzer：同一字段可分叉的两条分析路径。
4. **分词器** — Tokenizer：决定切分边界的组件（standard/keyword/ngram/pattern）。
5. **词元过滤器** — Token Filter：对切好的词项做变形（stem/synonym/lowercase）。
6. **字符过滤器** — Char Filter：进分词器前的字符层改写（html_strip/mapping）。
7. **N-gram** — N-gram：滑窗子串词项，模糊召回的空间预付。
8. **Edge N-gram** — Edge N-gram：左锚定滑窗，自动补全的索引侧方案。
9. **Shingles** — Shingles：邻近词元组合成短语词项。
10. **词干化** — Stemming：run/running 归一到词干提召回。
11. **同义词扩展** — Synonym Expansion：词项级映射，顺序影响结果。
12. **analyze API** — Analyze API：观察任意文本分析输出的调试工具。

## 最新演进与工业实践

- **分析器框架长寿**：analyzer 三件套 API 从 1.x 到 8.x/9.x 基本原样（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/analysis.html 与 https://www.elastic.co/docs/manage-data/data-store/text-analysis，访问 2026-09-27 均 200）——本章是全册折旧最慢的一章。
- **中文线翻案**：ik/smart_cn 插件时代 → analysis-icu/smartcn 内置化；2024+ 语义检索（semantic_text/ELSER 稀疏向量）让「中文分词不准」的部分场景被 token 级语义直接绕开（✅ https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/sparse-vector；semantic_text 官方专页本环境未验证，标 ⚠️）。
- **edge ngram 的后裔**：自动补全两路线（edge ngram 索引侧 vs completion suggester FST 侧）今仍并列（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/search-suggesters.html），新增第三条：LLM query suggestion（工业实践 ⚠️ 转述，无官方文档背书不链）。
- **搜索即对话**：RAG 时代「分析层」职责上移——embedding 模型选型（dense bi-encoder / ELSER 类 sparse）成为新的 analyzer 决策；官方把推理统一进 inference API（✅ retrievers 总面 https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrievers）。
- **工业实践**：同义词/纠错词表由 LLM 半自动生成+人工审核成常见流水线；「index analyzer 变更=reindex」的成本教训在向量索引上加倍成立（⚠️ 社区共识）。
