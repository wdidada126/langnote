# 10 · Improving performance（性能优化：请求分组、段、缓存与权衡）

## 10.1 bulk：把往返次数当钱看（⚠️ 转述）

单条 PUT 的 HTTP+fsync+refresh 三税太重；bulk 把 N 动作合一请求（NDJSON），书中量级建议「批到百 MB 前先按动作数（千级）试」——今天的官方基准同样以「先扩批再扩线程」为路标（⚠️ 转述；API ✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/docs-bulk.html 实抓）。percolate_bulk 是 1.x 特色（批量喂 percolator），今语义由「查询存成文档+percolate 查询批量刷」承接（✅ https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-percolate-query 实抓；1.x→5.x 反转细节见附录 E 对照，标 ⚠️ 转述）。

## 10.2 段：写入性能的主战场（⚠️ 转述）

Lucene 不可变段 ⇒ 更新=新段+墓碑、删除=墓碑；refresh 让 in-memory buffer 开新段（NRT 的代价：小段泛滥），merge 后台合段（IO 尖峰源），translog/fsync 决定持久性档位。1.x 旋钮 `index.refresh_interval`（批量导入时设 -1、导完再开）、`index.merge.scheduler.max_thread_count`（机械盘=1 的经典建议）、`index.translog.durability=async`。这些参数族全部存活至今（✅ 模块总面 https://www.elastic.co/guide/en/elasticsearch/reference/current/index-modules.html 实抓、https://www.elastic.co/guide/en/elasticsearch/reference/8.17/index-modules.html）。

🔧 类比组 E（本章主演示，SQLite 3.45.3/DuckDB 1.5.5 实跑数据回顾）：同一 200k 语料——FTS5 建索引一次性 **869 ms**、此后短语查询 **4.58 ms**；DuckDB 无倒排、每次扫 **9.2 ms**。三个工程结论用数字说话：①写侧预付=读侧摊销（段合并/索引构建同理）；②「查询快」与「写入快」不可能同时最大（refresh 频率=两端的滑块）；③高频小写入是索引结构最坏的输入模式（每写都触发建段）。演示为单机引擎行为，**非 ES**（无分片/副本/缓存层）。

## 10.3 1.x 缓存地图（⚠️ 转述 + 今值对照）

- **filter cache**：1.x 每个 filter 结果位图缓存（节点级 LRU），高频复用谓词（status/可见性）受益——**低复用塞 filter 只摊还失败**（第 4 章呼应）。
- **node query cache**：整查询结果按「段集未变」缓存，仪表盘时间序列的救星（refresh 风暴下命中率=0 也是它的坑）。
- **field data cache**：运行期转正排的费用所在——6.9 的 OOM 元凶在此调参（`indices.fielddata.cache.size` + breaker 雏形）。
今值三件套换形不换神：shard request cache（+`preference`）、node query cache 更名 shards/query cache、fielddata 被 doc_values 边缘化（✅ 索引级参数 `index.requests.cache.enable` 见 index-modules 实抓页；细分专页未逐验标 ⚠️）。

## 10.4 权衡清单（⚠️ 转述）

分片数↑：并行读↑但固定堆开销/文件句柄/协调成本↑——「几百个小索引各带 50 分片」是 1.x 时代最常见的自伤；副本↑换读吞吐与容错，写放大不变。慢请求定位：slow log + `profile: true` 看每段查询在每分片的耗时分解（✅ profile 今位 https://www.elastic.co/guide/en/elasticsearch/reference/current/search-profile.html 实抓）。书中「先量再调、一次改一个旋钮」的纪律毫无年代感。

## 工程要点与常见坑

- 批量导入三板斧的正确顺序：refresh_interval=-1 → bulk 灌 → 恢复 refresh → （需要时）force merge 到目标段数；漏掉恢复 refresh 会埋 NRT 测试假象。
- force merge 到 1 段只配给「不再写的只读索引」（日志按月滚动后），对活索引做是反模式（⚠️ 今官方同口径，转述）。
- 1.x `routing.partition`/分片数与节点数配比失误=热点：先按容量模型定分片（第 9 章），再谈缓存。

## 调优剧本对照（⚠️ 转述，1.x 版式）

```bash
# 剧本一：批量导入（导前关刷新，导后恢复+合并）
curl -XPUT localhost:9200/logs/_settings -d '{ "index": { "refresh_interval":"-1",
  "number_of_replicas": 0 } }'
# ...bulk 灌数（NDJSON，每批 5–15MB 量级起步再放大）...
curl -XPUT localhost:9200/logs/_settings -d '{ "index": { "refresh_interval":"1s",
  "number_of_replicas": 1 } }'
curl -XPOST 'localhost:9200/logs/_optimize?max_num_segments=1'   # 1.x 命令，2.x 更名 _forcemerge
# 剧本二：读侧观测
curl 'localhost:9200/logs/_search?profile=true' -d '{...}'        # 每分片每段耗时树
curl -XPUT localhost:9200/logs/_settings -d '{ "index.search.slowlog.threshold.query.warn":"10s" }'
# 剧本三：缓存盘点（1.x 面）
curl 'localhost:9200/_nodes/stats/indices?pretty'   # filter_cache/field_data/query_cache 字节数
```

三剧本对应三节：10.1 bulk+关刷新（把每写一次的建段与 fsync 税合并）、10.2 merge 曲线
（小段风暴→后台合并→optimize 只给只读索引）、10.3 缓存命中率决定「仪表盘是否被 refresh 打穿」。

## 章内问答（自测）

**Q1 为什么导入期关刷新又关副本？**
A：每次 refresh=开新段（后续 merge 成本），副本=二次传输与写放大；批量灌完再一次性补齐，总成本最低——「先省钱后安全」有窗口期风险，须业务确认。
**Q2 仪表盘突然变慢，与 refresh 何关？**
A：node query cache 以「段集未变」为命中前提；高频写入使段永远在变，缓存命中率趋零——解法在时间分桶/降频刷新/预聚合。
**Q3 为什么「副本数×分片数」不是读扩展的万能公式？**
A：每分片有固定堆与句柄成本，小分片×高副本把并行变成开销本身；读扩展先问查询形态（广播 vs routing 定向）。

**缓存命中率的三行算术（本章心法压缩版）**
- filter 谓词复用次数 × 缓存字节 = 收益；复用<1 次的谓词进 filter 只是给缓存交税（1.x 语境）。
- node query cache 的命中率 ≈ 1 − (refresh 频率 × 查询时间窗)：写入风暴期仪表盘必然「变慢不变卡」。
- field data 的命中不值钱——它的正确目标是**零命中**（全部走 doc_values），出现即回 03/08 章改 mapping。

**章间钩子备忘**
- 10.1 bulk 的批大小实验在 09 章的容量模型上跑；10.3 缓存的失配排查在 11 章 stats 面板上看。
- 🔧 组 E 的「869ms 预付 / 4.58ms 摊销 / 9.2ms 每扫」三口价，是全册对「索引=空间与时间的合同」最直的注脚。

## 核心概念速览（中英对照）

1. **批量写** — Bulk API：多动作合一请求，摊薄 HTTP/fsync/refresh 三税。
2. **段** — Segment：Lucene 不可变倒排文件单元，读写性能博弈的基本棋子。
3. **墓碑** — Tombstone：更新/删除留下的失效标记，merge 时才物理回收。
4. **刷新** — Refresh：buffer 开新段使其可搜；频率=NRT 与吞吐的滑块。
5. **合并** — Merge：后台段归并以抑制小段泛滥，IO 尖峰之源。
6. **事务日志** — translog：崩溃恢复的写前日志，fsync 档位决定持久性语义。
7. **filter 缓存（1.x）** — Filter Cache：谓词位图缓存，高复用才回本。
8. **节点查询缓存** — Node Query Cache：整查询级缓存，段未变才命中。
9. **字段数据缓存** — Field Data Cache：转正排的内存缓存，doc_values 的边缘化对象。
10. **请求缓存** — Request Cache（今）：分片级结果缓存，配 preference 使用。
11. **段合并策略** — Merge Policy：段数量/大小曲线的调参面（max_thread_count 等）。
12. **慢日志与 profile** — Slow Log/Profile：耗时分解的观测入口，调参前置纪律。

## 最新演进与工业实践

- **参数长寿**：refresh/merge/translog 参数族至今同名同义（✅ 8.17 与 current 的 index-modules 双页实抓）；「导入期关 refresh+事后 force merge」仍是官方日志管道标准建议（⚠️ 转述）。
- **缓存换代**：1.x filter cache 的「谓词位图」思想进了 query cache/bitset 层，shard request cache 接管仪表盘（细分页 URL 本环境未逐验，标 ⚠️；总面 ✅ index-modules）；breaker 体系（circuit_breaker）把 fielddata 的 OOM 故事改写成「先拒后安」（⚠️）。
- **硬件变迁改写权衡**：NVMe 让机械盘时代 max_thread_count=1 的告诫退役；对象存储分层（searchable snapshots）给 10.2 的成本方程新增「冷段不进本地盘」项（⚠️ 转述；锚 ✅ https://www.elastic.co/docs/deploy-manage）。
- **观测栈**：APM/slowlog 日志进 ES 自身、Kibana 性能面板替代书中手摸曲线（⚠️；profile API ✅ search-profile 实抓）。
- **工业实践**：写吞吐基准「bulk 批大小×并发」双轴扩展法沿用（✅ docs-bulk 同族）；Serverless 把 10.3/10.4 的多数旋钮收回平台，用户的调优面收敛为索引设计与查询质量（✅ https://www.elastic.co/cloud/serverless）。
