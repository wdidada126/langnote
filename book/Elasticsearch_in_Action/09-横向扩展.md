## 9.1–9.3 节点进出与迁移的账（⚠️ 转述）

书中实操：`_cat/nodes` 清点、新节点起来后观察 `_cat/shards` 从「副本缺失」到 green；摘节点先关分配（或拔副本再拔主）避免全量复制风暴。要点是**迁移成本=分片字节×网络×并发上限**，1.x 的 `cluster.routing.allocation.node_concurrent_recoveries` 等旋钮（✅ 今仍同族 https://www.elastic.co/guide/en/elasticsearch/reference/8.17/modules-cluster.html）决定「扩容后多久稳态」——这条算术 2026 未变，只是 Serverless 把它变成平台的事（✅ https://www.elastic.co/cloud/serverless）。

## 9.4 滚动升级（⚠️ 转述）

1.x minor 兼容宽松：逐节点重启即完成升级。major 跨越（1.x→2.x→5.x→8.x）则需要备份+逐个 reindex/按升级助手逐步跳版本（⚠️ 今值，✅ 升级总述 https://www.elastic.co/docs/deploy-manage/upgrade 实抓）。8.x 更严格：主版本混跑不再被允许组成长期混布集群——读 2015 文本时把「随便滚」读成「同 minor 滚」。

## 9.5 _cat：四张表吃遍集群（⚠️ 转述）

`_cat/health?v`（三色）、`_cat/indices?v`（每索引 docs/bytes/health）、`_cat/shards`（分片落点）、`_cat/nodes`（负载与角色）。`v/h` 参数控制表头与列选。该 API 家族至今原样在位，且是排障第一站（✅ https://www.elastic.co/guide/en/elasticsearch/reference/current/cat.html 实抓）。

🔧 类比组 E2→本章转译（SQLite 3.45.3 数据）：重建 200,000 文档的 FTS5 索引一次性花 **869 ms**，此后每条短语查询 **4.58 ms**。「加节点/reindex/别名切换」的全部成本结构可以浓缩成这个式子——**迁移/重建是预付，摊销靠后续查询量**。演示非 ES 行为。

## 9.6–9.7 容量规划与别名（⚠️ 转述）

分片大小经验值（书中量级：单分片数 GB 内、与节点内存/堆匹配；2026 通行口径仍引用「日志类主分片 ≤50GB 量级」⚠️ 二手转述）；**主分片数建后不可改** ⇒ 规划错误只能 reindex+别名换。别名（`_aliases` API）把「索引名」与「逻辑实体」解耦：写入别名+搜索别名分离、切换原子化——ES 运维最朴素也最长寿的发布模式（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/indices-aliases.html 实抓；数据流 data stream 是其日志场景的后裔 ⚠️，同族 deploy-manage ✅）。

## 9.8 routing：把文档钉住（⚠️ 转述）

默认路由 `hash(_id) % 主分片数`；自定义 `?routing=user_id` 让同用户文档同分片——配合第 8 章父子必须同分片，以及「只查某用户」免广播。代价：热点倾斜（大 V 压垮单分片）与**改主分片数=路由全重排**（书中警告至今有效）。`preference` 同分片重复查询享段/缓存亲和。

## 工程要点与常见坑

- 组播发现上云误合集群→9.2 的「关组播、白名单单播」在 2015 是给读者的保命符；7.0 起只剩 seed_hosts 一条路（⚠️；✅ 升级文档面 deploy-manage/upgrade）。
- 滚动升级不做「先摘副本再摘主」的编排时，一次重启触发全索引复制——书中给的分配开关顺序（10.3 缓存章同族旋钮）就是解药。
- 别名操作必须 `actions` 原子提交（移旧+添新一步），否则查询出现双索引/空窗。

## 扩缩操作流水对照（⚠️ 转述，1.x 版式）

```bash
# 观察面四张表
curl 'localhost:9200/_cat/health?v'; curl 'localhost:9200/_cat/indices?v'
curl 'localhost:9200/_cat/shards/restaurants?v'; curl 'localhost:9200/_cat/nodes?v'
# 滚动升级（同 minor）：逐节点 摘→升→回
curl -XPUT localhost:9200/_cluster/settings -d '{ "transient":
  { "cluster.routing.allocation.enable":"none" } }'      # 停自动迁移
# ...重启该节点后...
curl -XPUT localhost:9200/_cluster/settings -d '{ "transient":
  { "cluster.routing.allocation.enable":"all" } }'       # 放行补齐
# 别名原子切换（reindex 后换名不断服）
curl -XPOST localhost:9200/_aliases -d '{ "actions":[
  { "remove": { "index":"restaurants_v1", "alias":"restaurants" }},
  { "add":    { "index":"restaurants_v2", "alias":"restaurants" }} ]}'
# routing 钉文档与按域查询
curl -XPUT 'localhost:9200/restaurants/type1/9?routing=zone_1' -d '{...}'
curl 'localhost:9200/restaurants/_search?routing=zone_1' -d '{...}'
```

读法要点：`transient` 设置重启即失（持久用 persistent）；allocation none→all 的窗口
就是「升级不引发搬迁风暴」的护城河；别名 actions 数组**原子生效**，拆开两条 curl 就有空窗；
`?routing=` 写读必须同值，否则文档「查无此人」。

## 章内问答（自测）

**Q1 加节点后健康色标怎么变？**
A：正常应保持/走向 green（副本有了新家）；若新节点入场后仍黄=磁盘水位、awareness 凑不齐域或分配并发限速——迁移本身不该让容灾空窗，持续黄要查解释（11 章工具）。
**Q2 别名切换为何必须单请求？**
A：`_aliases.actions` 原子应用 remove+add；两个请求之间存在「无双索引/双索引」窗口，查询方会看到不一致集。
**Q3 分片数 1000 与 30 的集群谁先出问题？**
A：1000——每分片固定堆开销+文件句柄+广播协调成本（10 章「小分片自伤」）；分片是并行单位也是开销单位，先算「每分片多大」再算「要几个」。

## 核心概念速览（中英对照）

1. **节点发现** — Discovery：1.x zen 组播/单播自动组集群机制，7.0 后为 seed hosts。
2. **分片重分布** — Rebalancing：节点增减后分片自动搬迁，成本=字节×网络×并发。
3. **滚动升级** — Rolling Upgrade：逐节点下线-升级-回流不停服；跨 major 须逐级+数据搬迁。
4. **_cat API** — Cat API：health/indices/shards/nodes 的人话表格运维面。
5. **容量规划** — Capacity Planning：分片数/大小与节点规格的提前联立求解。
6. **别名** — Alias：逻辑名→物理索引的间接层，蓝绿换索引的机关。
7. **索引路由** — Index Routing：?routing= 把同类文档钉到同分片，倾斜为税。
8. **偏好** — Preference：查询固定到同分片复用段缓存/一致性观感。
9. **数据迁移窗口** — Recovery Window：分配并发旋钮决定的稳态恢复时长。
10. **主分片不可变** — Fixed Primary Count：建索引时定死，改=重建+别名切换。
11. **蓝绿发布** — Blue/Green Indexing：新旧双索引经别名原子切换（9.7 的工业化）。
12. **data stream** — Data Stream：append-only 多后索引的别名后裔（日志场景 ⚠️）。

## 最新演进与工业实践

- **发现与拓扑**：zen 组播→单播→7.0 只留 seed/初始主选（⚠️ 转述，✅ https://www.elastic.co/docs/deploy-manage/upgrade）；8.x 角色精细化（master/data/ingest/coordinator 专职）成默认建议部署形态（✅ modules-cluster 同族 https://www.elastic.co/guide/en/elasticsearch/reference/8.17/modules-cluster.html）。
- **冷热与分层**：书中「扩展策略」的后裔是 data tiers（hot/warm/cold/frozen）+ Serverless 自动分层（✅ https://www.elastic.co/docs/deploy-manage 总览实抓；frozen 专页本环境 404 不引用，细节 ⚠️）。
- **搜索即算力**：8.x searchable snapshots 让冷数据「对象存储+本地缓存」，重排了 9.6 的成本方程（⚠️ 转述；无逐页 URL 背书，以 deploy-manage 为锚）。
- **别名+数据流**：日志场景用户不再手写别名切换——data stream + ILM 自动滚动（⚠️；SLM/生命周期同族 ✅ https://www.elastic.co/guide/en/elasticsearch/reference/current/snapshot-lifecycle-management.html）。
- **Serverless**：加/摘节点、分片数、recovery 并发全部托管；本书该章知识转化为「为什么平台会这么设计」的成本模型（✅ https://www.elastic.co/cloud/serverless，访问 2026-09-27）。
- **工业实践**：reindex+别名仍是 mapping 变更/分片扩容的唯一正道；routing 倾斜事故（大租户压垮分片）与 2015 年形态一致（⚠️ 社区共识）。
