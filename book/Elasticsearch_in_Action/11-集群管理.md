# 11 · Administering your cluster（集群管理：默认值、感知、监控与备份）

> 取证基座：二级节 11.1–11.4（改进默认/分配感知/监控瓶颈/备份）+11.5 小结 ✅ getTocHtml?id=548 实抓；正文精读重构，⚠️ 转述，🔧 本机类比（**非 ES 行为**）。

## 章定位

「能跑」与「能在生产里活下来」的分界章：一批该改的默认值（内存/swap/文件描述符/索引前缀命名），把物理拓扑（机架/可用区）翻译进调度的 Allocation Awareness，以 _cluster/health + _nodes/stats + 附录 D 工具群盯瓶颈，最后用 snapshot/restore 把「数据会丢」这件事工程化。对位 [../Elasticsearch_The_Definitive_Guide/15-集群存活保障与生产运维.md](../Elasticsearch_The_Definitive_Guide/15-集群存活保障与生产运维.md)。

## 内容地图（原书二级节 ✅ 实抓）

- 11.1 改进默认：堆大小（≤物理内存半）、禁用 swap/压缩指针类 OS 层建议、`cluster.name` 唯一性、索引命名前缀规范
- 11.2 分配感知：`node.attr.rack/zone` + `cluster.routing.allocation.awareness.attributes`（副本不落下同故障域）
- 11.3 监控瓶颈：health 三色语义进阶（unassigned 原因要问 `_cluster/allocation/explain`，⚠️ 书涉同族）、节点 stats（cpu/mem/磁盘/线程池队列拒绝）、慢日志/热点索引
- 11.4 备份数据：repository（fs/s3/hdfs）注册→`_snapshot` 创建/恢复；快照是**分片级不可变增量**，不是文件拷贝
- 11.5 小结

## 11.1 默认值与命名纪律（⚠️ 转述）

1.x 装机清单式建议：JVM 堆=物理内存一半且不超压缩指针甜点、关 swap（`bootstrap.mlockall`，后名 `bootstrap.memory_lock`）、fd 上限、`cluster.name` 改出「elasticsearch」默认（否则组播互吞——9.2 事故的另一半）、索引名带日期与业务前缀（为 9.7 别名/滚动铺路）。JVM/OS 建议今仍写进部署文档（⚠️ 细节转述，✅ 升级/部署总面 https://www.elastic.co/docs/deploy-manage 与 https://www.elastic.co/docs/deploy-manage/upgrade 实抓）。

## 11.2 分配感知：故障域的拓扑语言（⚠️ 转述）

给节点打 `node.attr.zone: az1`，集群级声明 `cluster.routing.allocation.awareness.attributes: zone`——同分片的主副被强制分到不同 zone；zone 缺失时副本宁可**不分配**（forced awareness 语义）。这条「用属性表达物理、由调度器执行」的设计是 ES 多租/多云容灾的骨架（✅ 参数族今在 https://www.elastic.co/guide/en/elasticsearch/reference/8.17/modules-cluster.html 实抓页内）。

## 11.3 监控：从三色到拒绝队列（⚠️ 转述 + 🔧 类比 H-前置）

`_cluster/health`（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/cluster-health.html 实抓）只答「有没有问题」；`_nodes/stats` 给堆/缓存/线程池（bulk/search 队列与 rejected 计数）——**写拒绝率与 GC 尖峰是容量告警的真身**。书末把选择权交给附录 D 插件群（BigDesk/ElasticHQ/Marvel…）。
🔧 类比 H（SQLite 3.45.3 实跑，供 11.4 概念锚定）：内存库表 `VACUUM INTO 'h_snapshot.db'` 产出 8,192 字节文件，重开该文件读回 `x=42`——「快照=某时刻只读副本，恢复=以副本重建可写体」的最小模型。**差别也要说清**：ES 快照是分片级、增量段文件、可部分恢复/重命名恢复，SQLite 是整库物理拷贝；演示非 ES 行为。

## 11.4 snapshot/restore：仓库模型（⚠️ 转述）

注册只读 repository（共享文件系统/S3/HDFS，1.x 需插件）→ `PUT _snapshot/repo/name`（按索引集、增量只传新段）→ 恢复可 `rename_pattern` 回放到新名——这正是 9.7 别名蓝绿的另一块拼图：「快照=跨集群搬迁与合规备份的唯一正道；别拿 rsync 拷数据目录」（1.x/8.x 同一句）。API 面今由 SLM 策略化：`snapshot-lifecycle-management` 把「何时拍、留几份」写成 cron（✅ https://www.elastic.co/guide/en/elasticsearch/reference/current/snapshot-lifecycle-management.html 实抓）。

## 工程要点与常见坑

- red 集群先问 `_cluster/allocation/explain`（⚠️ 书涉同族诊断入口）：unassigned 九成是「awareness 凑不齐第二 zone」或磁盘水位线——不是「重启大法」。
- 磁盘高水位（flood-stage 只读锁）会把索引变 read-only，恢复要显式清 flag——1.x 就有此机制，2026 依旧年年踩（✅ 水位参数族 modules-cluster/index-modules 实抓页内；报错剧本 ⚠️）。
- 快照仓库必须**不可变/只追加**：多集群共享同一仓库覆盖写=互相损坏（1.x 经典事故，官方至今三令五申 ⚠️）。
- 线程池 rejected 持续>0 时，扩容方向是 bulk/search 分离节点（角色划分，9 章后裔），不是调大队列自欺。

## 运维剧本对照（⚠️ 转述，1.x 版式）

```bash
# 剧本一：把物理拓扑说给集群听
curl -XPUT localhost:9200/_cluster/settings -d '{ "persistent": {
  "cluster.routing.allocation.awareness.attributes": "zone" } }'
# 各节点 elasticsearch.yml：node.zone: az1（属性名自定，声明后主副本强制分域）
# 剧本二：red 的三段式问诊
curl 'localhost:9200/_cluster/health?pretty'          # 哪个索引红、缺几分片
curl 'localhost:9200/_cat/shards/red_index?v'         # unassigned 的副本/主
curl 'localhost:9200/_cluster/allocation/explain?pretty' -d '{}'  # 为什么不落位（书涉同族 ⚠️）
# 剧本三：备份三件套
curl -XPUT localhost:9200/_snapshot/fs1 -d '{ "type":"fs", "settings":{"location":"/mnt/esbackup"} }'
curl -XPUT 'localhost:9200/_snapshot/fs1/snap_2015_11?wait_for_completion=true' -d '{ "indices":"restaurants,logs_*" }'
curl -XPOST 'localhost:9200/_snapshot/fs1/snap_2015_11/_restore' -d '{ "indices":"restaurants",
  "rename_pattern":"(.+)", "rename_replacement":"restored_$1" }'
# 剧本四：洪水位误锁的解封
curl -XPUT localhost:9200/red_index/_settings -d '{ "index.blocks.read_only_allow_delete": null }'
```

读法：persistent vs transient 的「改配置会不会被重启冲掉」是 9 章同款陷阱；
快照三步=注册仓库→拍→按 rename 恢复（🔧 组 H 的整库拷贝只是心智锚，真身是分片级增量段）；
read_only_allow_delete 是磁盘水位保护的后遗症开关，先清盘再解锁，别反向。

## 章内问答（自测）

**Q1 green 的集群为什么仍可能有故障风险？**
A：green 只说「所有分片就位」，不说「主副同机/同盘」——无 awareness 时同节点/同机架放置照样团灭；健康≠容灾。
**Q2 快照为什么不能拿 `cp -r` 数据目录代替？**
A：段文件跨分片异步落盘、无一致性点——文件系统拷贝得到的是撕裂现场；快照 API 有分片级一致语义与增量复用（🔧 组 H 演示的是一致点+副本模型，机制细节 ⚠️）。
**Q3 集群频繁「假死」查什么？**
A：GC 日志+fielddata/request cache 占用、线程池 rejected、慢查询广播（分片过多回潮）——10 章三本账在 11 章的全息投影。

## 核心概念速览（中英对照）

1. **分配感知** — Allocation Awareness：按节点属性把副本推出同故障域。
2. **故障域** — Failure Domain：rack/zone 等「会一起死」的物理边界。
3. **集群健康三色** — green/yellow/red：副本缺/主分片缺的分级语义。
4. **未分配解释** — allocation explain：回答「为什么这个分片不落位」。
5. **节点统计** — _nodes/stats：堆/缓存/线程池/磁盘的体检总面。
6. **拒绝计数** — Rejected：线程池队列溢出被拒的请求数，容量告警真身。
7. **快照仓库** — Repository：注册在共享存储上的只追加备份目的地。
8. **增量快照** — Incremental Snapshot：只传新段文件，分片级不可变。
9. **重命名恢复** — Restore with rename：把快照恢复到新索引名，蓝绿搬数据。
10. **水位线** — Disk Watermark：高水位停分配、洪水位只读锁的保护机制。
11. **memory lock** — bootstrap.memory_lock（1.x mlockall）：禁 swap 的启动开关。
12. **SLM** — Snapshot Lifecycle Management：cron 化的快照策略（11.4 的后裔）。

## 最新演进与工业实践

- **参数与机制存续**：awareness 属性族、health API 原样可跑（✅ modules-cluster 与 cluster-health 8.17 双页实抓）；mlockall 更名 memory_lock、`_cluster/allocation/explain` 成为标准诊断入口（⚠️ 专页未逐验，以同族实抓页为锚）。
- **调度表达力升级**：1.x awareness → 8.x 的 data tiers + index 级 `index.routing.allocation.*` + weighted/auto balance 调参面（✅ index-modules 实抓页内含该参数族）。
- **备份即策略**：SLM 把 11.4 的手工剧本变声明式（✅ snapshot-lifecycle-management 实抓）；仓库端「写一次/对象锁」合规形态（S3 Object Lock 类）成防勒索标配（⚠️ 转述）。
- **监控换代**：附录 D 插件群全灭→Kibana 栈监控/Elastic Agent（详见 12 章演进节；✅ 观测产品面 https://www.elastic.co/search-labs 生态入口实抓，具体版本史 ⚠️）。
- **Serverless 改写本章**：故障域/水位/堆参数收归平台，用户保留的治理面=SLM 类策略与可观测数据自身——2015 读者的运维直觉仍决定「钱花在哪个 tier」的账单形态（✅ https://www.elastic.co/cloud/serverless）。
