## 3.1–3.2 mapping 与核心类型（⚠️ 转述，1.x 口径）

mapping 在 1.x 是「type 的 schema」：字段名 → 类型 + `index: analyzed|not_analyzed|no` + `analyzer` 引用 + `include_in_all`。设计三问（本章灵魂）：这字段要全文搜吗（analyzed）？要精确过滤/排序吗（not_analyzed + 之后 doc_values 议题）？要回包吗（`_source` / `store`）？动态 mapping 能跑但会把 `123` 猜成 long、把日期串猜成 date——**生产永远显式 mapping**（该结论跨版本有效）。
5.x 分家：`string` 拆 `text`（原 analyzed）与 `keyword`（原 not_analyzed），`index` 参数换成 `true/false` 语义（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/mapping-types.html 实抓；参数细节 https://www.elastic.co/guide/en/elasticsearch/reference/8.17/mapping-params.html）。

## 3.3 数组与多字段（⚠️ 转述）

1.x 里任何字段值可写成 JSON 数组，但**元素类型必须与字段 mapping 一致**；数组不改变倒排形态——每个元素各成一个词项/值。多字段 `fields: {raw: {type: string, index: not_analyzed}}` 让同一值既能全文搜又能精确聚合（今式 `text` + `fields.keyword`，即「keyword 子字段」的源头，✅ mapping-types）。

🔧 类比组 F-1（DuckDB 1.5.5 实跑）：JSON 数组语义 vs 扁平字符串——

```sql
CREATE TABLE posts(j JSON);  -- {"tags":["search","index"]} / {"tags":["deep learning"]}
SELECT list_contains(CAST(j['tags'] AS VARCHAR[]),'index') FROM posts;  -- True / False
SELECT json_contains(j['tags'],'"index"') FROM posts;                   -- True / False
```

对照 SQLite 扁平化：把 tags 存成 `'search, index'` 文本再 `MATCH 'search AND index'` 能命中（rowid 1），但**跨值关系已丢失**——这正是 ES 对象数组「扁平化串味」问题的微缩模型（第 8 章展开）。演示跑通≠ES 行为。

## 3.4 预定义字段（⚠️ 转述）

`_all`（所有 analyzed 字段拼成一个隐式大字段供无定向搜索）、`_parent`（父子关系，第 8 章）、`_ttl`/`_timestamp`（过期与时间戳，**2.x 即被移除**——书中此节是版本老化重灾区）、`_boost`（索引期加权）、`_version`（乐观锁）。2026 读法：`_all` 的继任心智是 `copy_to` 或 multi_match 跨字段，`_ttl` 的继任是 ILM 删除动作（⚠️ 转述；mapping 参数面 ✅ mapping-params 实抓）。

## 3.5–3.6 更新、删除与并发（⚠️ 转述）

- index API 同 `_id` 重 PUT = 删旧建新（Lucene 不可变段的墓碑式更新），version 自动 +1；`?version=`/`version_type=external` 走外部版本乐观锁。
- update API `{"doc": {...}}` = 读原 `_source`→本地 merge→重索引，1.x 默认重试 3 次防并发冲突；script update 同路径。
- delete by query 在 1.x 需 contrib 插件且是「搜一批再逐个删」的非原子慢路径——5.x 起才有原生 `_delete_by_query`（✅ 文档线 https://www.elastic.co/guide/en/elasticsearch/reference/8.17/docs-bulk.html 同族 API 实抓）。
- bulk API：NDJSON 两行一动作，本章收尾的性能钥匙（第 10 章复用）。

## 工程要点与常见坑

- 更新频率高的字段与全文检索字段放同索引会让段合并吃满 IO——1.x/8.x 同病：高频改值走 keyword，别让它进 text 分析链。
- `refresh` 不在写 API 的原子性承诺里：读己之写要靠 `preference`/路由或显式 refresh（⚠️）。
- version_type=external 配 Kafka 偏移/更新时间戳是反乱序的标准姿势——今天 ES Serverless 与 Kibana 数据接入仍是同一思路（⚠️）。
- 动态模板（dynamic_templates）按字段名模式定 mapping，比全局动态猜测可控——该机制今仍在（✅ mapping.html 总述 https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping.html）。

## 写侧流水对照（⚠️ 转述，1.x 版式）

```bash
# 显式 mapping：菜名全文、标签精确、评分数值、点评时间
curl -XPUT localhost:9200/restaurants -d '{ "mappings": { "type1": { "properties": {
  "name":   { "type":"string", "index":"analyzed" },
  "tags":   { "type":"string", "index":"not_analyzed" },
  "stars":  { "type":"integer" },
  "comments": { "type":"string", "index":"analyzed", "include_in_all": true }
}}}}'
# 数组与多字段一值两型
curl -XPUT localhost:9200/restaurants/type1/1 -d '{ "name":"Elastica","tags":["greek","mediterranean"] }'
# 乐观锁更新：客户端记住版本号，冲突即 409
curl -XPUT 'localhost:9200/restaurants/type1/1?version=2' -d '{ ... }'
curl -XPOST localhost:9200/restaurants/type1/1/_update -d '{ "doc": { "stars": 4 } }'
# 批量删除（1.x 需 contrib delete-by-query 插件 ⚠️）
curl -XPOST localhost:9200/restaurants/_delete_by_query -d '{ "query": { "term": { "stars": 1 } } }'
# bulk：NDJSON 两行一动作
printf '{"index":{"_id":2}}\n{"name":"Zorba"}\n{"delete":{"_id":1}}\n' > b.ndjson
curl -s -XPOST localhost:9200/_bulk --data-binary @b.ndjson
```

## 2026 复读清单

- [ ] `string(index:analyzed|not_analyzed)` 默写为 `text`/`keyword`；`include_in_all` 已死，换 `copy_to`。
- [ ] `_ttl/_timestamp` 段落整体跳过，改学 ILM（见演进节）。
- [ ] update 的「读-改-重索引」成本在向量索引上更狠：易变字段是否该移出搜索索引？
- [ ] 动态 mapping 的自动探测依旧存在（date 猜 long 事故常演常新）——显式 mapping 纪律无损。
- [ ] delete_by_query 已原生但默认按版本重试：批删大集合先 `_count` 估规模（⚠️ 常识转述）。

## 章内问答（自测）

**Q1 为什么「所有字段天然可存数组」不改变倒排结构？**
A：数组被摊平为同字段的多词项/多值，doc 级与字段级的「同位配对」不保留——这是 08 章串味问题的源头。
**Q2 `doc` merge 与整文档重 PUT 的差别？**
A：merge 要读 `_source`（关掉就废）、本地合成新 JSON 再重索引；两版本冲突靠 update 重试；重 PUT 直接换版。
**Q3 external version 何时用？**
A：上游自带单调版本（Kafka offset、更新时间秒级）防乱序与重放；`version_type=external_gte` 放宽等值但自担幂等。

## 核心概念速览（中英对照）

1. **映射** — Mapping：type 内字段→类型/分析行为的 schema 声明。
2. **动态映射** — Dynamic Mapping：首写自动猜类型，生产须显式覆写。
3. **多字段** — Multi-fields：同值多型（text 搜 + keyword 聚合）的机制。
4. **_source** — Source Field：存储原始 JSON；关它省空间但废掉 update/reindex。
5. **_all** — All Field：1.x 隐式全文大字段，6.x 移除、copy_to 继任。
6. **乐观并发控制** — Optimistic Concurrency Control：以 `_version`/external version 拒写竞态。
7. **局部更新** — Partial Update（doc merge）：读-改-重索引三合一的高成本更新。
8. **墓碑删除** — Tombstone Delete：Lucene 不可变段上的「标记删除」，合并时才物理回收。
9. **批量写** — Bulk API：NDJSON 多动作合一请求，写吞吐的默认姿势。
10. **外部版本号** — External Versioning：用 Kafka offset/时间戳当 version，天然防乱序。
11. **动态模板** — Dynamic Templates：按字段名/类型模式批量定 mapping。
12. **copy_to** — Copy To：显式合并字段进聚合搜索域，替代 `_all` 的今式。

## 最新演进与工业实践

- **类型系统大搬家**：string→text/keyword、`not_analyzed`→keyword、`_ttl/_timestamp/_all/_parent/_boost` 全部退役（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/mapping-types.html 与 https://www.elastic.co/guide/en/elasticsearch/reference/current/removal-of-types.html）；本章代码直跑 8.x 必挂，语义仍直跑。
- **新字段型**：`dense_vector`/`sparse_vector`/`semantic_text` 进 mapping 全家桶（✅ https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/dense-vector、https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/sparse-vector），「建模先问要不要向量列」成为 2024+ 新三问之一。
- **生命周期**：`_ttl` 的后裔是 ILM（index lifecycle management），hot→delete 自动化（✅ SLM/生命周期文档线 https://www.elastic.co/guide/en/elasticsearch/reference/current/snapshot-lifecycle-management.html 实抓同类）。
- **写侧 API 现状**：update/bulk/_delete_by_query/reindex 全为原生 GA（✅ docs-bulk 8.17 实抓）；Serverless 下 bulk 语义不变但吞吐按量计费（✅ https://www.elastic.co/cloud/serverless）。
- **工业实践**：CDC（Kafka→ES）用 external versioning 防乱序仍是标准方案；「高频局部更新是 ES 最贵的写模式」结论 2026 依旧成立——宽表更新走 doc 合并或干脆把易变字段移出搜索索引（⚠️ 社区共识转述）。
