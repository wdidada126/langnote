## 2.1 逻辑布局（⚠️ 转述，1.x 口径）

document 是 JSON；type 给一类文档定 mapping（字段名→core type：string/long/double/date/boolean，string 还要选 `analyzed` 或 `not_analyzed`——1.x 特色，5.x 起拆成 text/keyword ✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/mapping-types.html 实抓）；index 是 type 的容器，cluster 是 index 的容器。书中心智：**「mapping 先行」**——先 PUT `/restaurant/type?pretty` 带 `_source_enabled` 等参数定住结构，再进数据；对位本系列 #16 索引基础理论（`Fundamentals_of_Database_Indexing`，波5 兄弟目录，按纪律只登记不链）。

## 2.2 物理布局：shard 是伸缩与容错的单位（⚠️ 转述）

- 索引建立时按 setting 切成 N 个主分片 + R 个副本分片；分片=独立 Lucene 实例，落点由集群自动分配。
- 节点加入触发分片再均衡：书中用两个节点+head 插件肉眼观察 yellow→green。
- 关键推论（后续章反复使用）：**主分片数建后不可改**（改=重建索引+别名切换，第 9 章）；副本数可动态改。
- 7.x/8.x 后「单 index 单 mapping」成为默认心智（types 移除 ✅ https://www.elastic.co/guide/en/elasticsearch/reference/current/removal-of-types.html）；分片/副本模型未变。

## 2.3–2.4 第一次索引与搜索（⚠️ 转述）

`PUT /restaurant/type/1` 带 JSON 体即索引；同 ID 再 PUT 是**整文档替换并 version+1**；响应里 `_indices`/`_shard`/`_version` 字段是 1.x 版式。搜索两条面：`GET /_search?q=...`（URI 简单串）与 `POST /_search` + query DSL（下一章）；`_source` 决定回包是否带原 JSON。默认 refresh 1s——PUT 后立即搜可能看不见（NRT 之坑，本册反复出现）。

🔧 类比组 E（真实跑过：DuckDB 1.5.5 / SQLite 3.45.3）：200,000 条三词短句语料——
- E1 DuckDB `contains(msg,'aggregation shard')` 全表扫：**9.2 ms**，count=3,997；
- E2 SQLite FTS5 短语索引 `MATCH '"aggregation shard"'`：查询 **4.58 ms**，count=3,997（建索引一次性 **869 ms**）；
- E3 词项 `MATCH 'aggregation'`：count=54,488——**词项爆炸是倒排的本质代价，也是相关性打分存在的原因**。
类比结论：倒排=空间换时间+一次写入成本摊销；**非 ES 行为**（ES 的分片并行、段结构、缓存层均未在本演示中出现）。

## 2.5–2.6 配置与加节点（⚠️ 转述）

`config/elasticsearch.yml` 三件套：`cluster.name`（同名即同集群）、`node.name`（人话标签）、数据/日志路径。1.x 发现机制为 zen discovery 组播（零配置局域网互见）；书中启第二个进程（不同 path.data、可选不同 http 端口）观察分片重分布与副本补齐。head 插件页面对照 `_cluster/health`（green=所有主副就位，yellow=副本缺，red=主分片缺）——健康三色语义至今未变（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/cluster-health.html）。

## 工程要点与常见坑

- 同机跑「多节点」演示要显式错开 `path.data`/`path.logs`，否则第二个节点直接起不来（1.x 即如此）。
- 组播发现把邻居机误拉进集群是经典事故；生产 1.x 应关组播改 unicast_hosts——7.0 起组播整体删除（⚠️，升级路径 ✅ https://www.elastic.co/docs/deploy-manage/upgrade）。
- mapping 定错类型（把 ID 存成 analyzed string）后想改，只有 reindex+别名一条路——先读 03 章再动手。
- NRT 让「写入即读」测试脆弱：集成测试要么 `refresh=true` 要么容忍 1s。

## 首跑流水对照（本章闭环五连 ⚠️ 转述，1.x 版式）

```bash
curl -XPUT localhost:9200/restaurants -d '{
  "settings": { "number_of_shards": 2, "number_of_replicas": 1 },
  "mappings": { "type1": { "properties": {
      "name":    { "type": "string", "index": "analyzed" },
      "stars":   { "type": "integer" },
      "date":    { "type": "date", "format": "date_optional_time" }
  }}}} '
curl -XPUT localhost:9200/restaurants/type1/1 -d '{ "name":"Elastica","stars":5 }'
curl -XGET 'localhost:9200/restaurants/_search?pretty' -d '{ "query": { "match": { "name":"elastica" } } }'
curl -XGET 'localhost:9200/_cluster/health?pretty'    # status: yellow→green 的观察点
# 第二终端：换 path.data 再起一进程，同 cluster.name → _cat/nodes 见 2，分片迁移至 green
```

要点回放：mapping 先行（analyzed/not_analyzed 是 1.x 魂）、`_source` 决定回包与 update 能力、主分片数建索引时定死、副本可动态调；URI `q=` 与 DSL body 两条搜索面本章各走一遍。

## 章内问答（自测）

**Q1 为什么主分片数不可改而副本可？**
A：路由 `hash(_id)%主分片数` 决定文档落点，改主数=全部重算重搬；副本只是拷贝份数，不动「文档→主分片」映射。
**Q2 单节点集群 yellow 要紧吗？**
A：无家可归的副本导致 yellow 可容忍，但它是容灾空窗的伪装——多节点场景 yellow 必须查分配解释。
**Q3 为什么 PUT 后 _search 可能看不见？**
A：NRT——refresh 默认约 1s 才把 buffer 转成可搜段；测试用 `?refresh` 显式刷新。

## 核心概念速览（中英对照）

1. **映射** — Mapping：type/index 的字段类型与索引行为声明。
2. **核心类型** — Core Types：string/long/double/date/boolean 等基础字段型。
3. **分析型字符串** — analyzed string：1.x 里走分词的 string，5.x 后由 text 承担。
4. **源字段** — _source：随文档存储的原始 JSON，回包与 reindex 的底座。
5. **主分片** — Primary Shard：文档路由的写入目标，数量建索引时定死。
6. **副本分片** — Replica Shard：主分片拷贝，供读扩展与容错。
7. **节点** — Node：一个 ES 进程/实例，持有一些分片。
8. **集群健康** — Cluster Health：green/yellow/red 三级状态语义。
9. **发现机制** — Discovery：节点互相找到并组集群的机制（1.x zen 组播）。
10. **再均衡** — Rebalancing：节点增减后分片自动迁移。
11. **简单查询串** — Simple Query String（q=）：URI 参数的快捷搜索面。
12. **刷新** — Refresh：把 in-memory 段转成可搜段，默认约 1s，NRT 的开关。

## 最新演进与工业实践

- **API 版式**：`/index/type/_search` 的路径 type 段在 7.x 可用可省、8.x 必须省略——照书敲会撞 400；`PUT /restaurant/_doc/1` 是今式（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/search-request-body.html、https://www.elastic.co/guide/en/elasticsearch/reference/current/removal-of-types.html）。
- **types 之死**：一个索引多 type 的「迷你关系库」幻想被官方专文判死（✅ removal-of-types 实抓），2026 年新项目按「实体=索引（或 data stream）」建模。
- **配置面演进**：elasticsearch.yml 核心参数框架仍在（✅ https://www.elastic.co/guide/en/elasticsearch/reference/current/index-modules.html 及 modules 族），但 jvm 选项独立成 jvm.options、发现机制换成 seed_hosts/initial_master_nodes；8.x 起 TLS 与用户体系默认开（⚠️，✅ 升级总述 https://www.elastic.co/docs/deploy-manage/upgrade）。
- **Serverless 冲击**：分片数、副本、扩缩容这些「2.2 物理布局」知识在 Elastic Cloud Serverless 中大部分被平台托管（✅ https://www.elastic.co/cloud/serverless），但概念仍是理解成本模型的前提——本书该章反而更值钱：平台不会替你理解「主分片不可改」。
- **向量时代**：index 里新增 dense_vector 字段与 kNN 检索路径（✅ https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/dense-vector、https://www.elastic.co/docs/solutions/search/vector/knn），「mapping 先行」原则原样适用。
- **工业实践**：多集群按业务隔离 + 别名蓝绿发布仍是主流姿势；组播事故至今仍在 AWS/GCP 以「seed 配错集群互吞」形式重演（⚠️ 社区常见案例）。
