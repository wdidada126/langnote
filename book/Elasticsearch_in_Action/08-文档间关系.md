# 08 · Relations among documents（文档间关系：五种建模路线）

> 取证基座：二级节 8.1–8.7（选项总览/对象字段/nested/parent-child/反规范化/应用侧 join/小结）✅ getTocHtml?id=548 实抓；正文精读重构，⚠️ 转述，🔧 本机类比（**非 ES 行为**）。本章是全册「数据库通识密度」最高的一章。

## 章定位

搜索引擎没有外键与 join 算子，关系必须在**建模期**偿还。书中给出一条光谱：对象内嵌（快而串味）→ nested（配对正确而贵）→ parent-child（可独立更新而查询绕）→ 反规范化（读爽写爆）→ 应用侧 join（两次查询）。餐厅场景：餐厅带「若干条点评」，每条点评有作者+评分+日期——一对多如何进 ES。对位 [../MongoDB_The_Definitive_Guide_3e/00-总览与阅读地图.md](../MongoDB_The_Definitive_Guide_3e/00-总览与阅读地图.md) 的「内嵌 vs 引用」同题辩论。

## 8.2 对象展平与串味（⚠️ 转述）

1.x：`{"name":"p1","ratings":[{"user":"tom","stars":5},{"user":"anna","stars":3}]}` 展平成 `ratings.user=[tom,anna]、ratings.stars=[5,3]`——**数组同位关系丢失**。搜「tom 给了 5 分」时 `user:tom AND stars:5` 会命中（tom 可能只给了 3）。
🔧 类比组 F-2（DuckDB 1.5.5 + SQLite 3.45.3 实跑）：DuckDB `list_contains(CAST(j['tags'] AS VARCHAR[]),'index')` 保住数组语义 True/False；SQLite FTS5 把对象数组扁平成一行文本后 `MATCH 'search AND index'` 仍命中同一行（rowid 1）——与 ES 展平同病：AND 跨值串味。再对照范化表：`SELECT docid FROM rel WHERE tag IN ('search','index') GROUP BY docid HAVING count(DISTINCT tag)=2` 得 (1)——**「成对正确」要么 nested/路径索引，要么回关系模型**，三个引擎同一教训。演示非 ES 行为。

## 8.3 nested：路径内配对（⚠️ 转述）

`"ratings": {"type":"nested"}` 使每个子对象成为独立隐藏文档（同路径绑定），查询用 `nested query + path`，命中可回「哪个子文档匹配」；聚合同理（7.3 的 nested 桶）。代价：**子文档当独立文档计**——更新父=重建全部子，段膨胀快。书中判定：读多改少、需要子项计分/过滤的（点评列表）用它。
今值：nested 原样在，且是 **dense_vector 子字段（多向量文档）** 的官方载体（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/mapping-types.html 与 https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/dense-vector）。

## 8.4 parent-child（1.x 形态）与后裔（⚠️ 转述）

1.x：子文档写 `_parent` 字段、同 routing 保证同分片，`has_child` 返回匹配的父、`has_parent` 反向。优点：子可独立增删；缺点：`_parent` 索引内存开销大、join 靠分片内临时结构、跨分片关系直接不合法。**6.0 起 _parent 移除**，换 `join` 字段 + `parent_id`/routing（✅ 现代 mapping 面 https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping.html）；8.x 再补 `serialized` 等形态（⚠️ 细节转述）。查询族 has_child/has_parent 存续至今。

## 8.5–8.6 冗余与应用侧 join（⚠️ 转述）

反规范化：把「菜系名」抄进每餐厅文档——搜索免 join，代价是改菜系字典要重写 N 万文档（写扇出）。应用侧：先查关联集合拿 ids，再 `terms` 过滤——一致性窗口=两次查询之间。书中给「小字典表（<百级）进 query cache 的内存字典、大字典走 ids」量级建议。这两条今天分别由「document enrichment pipeline/ingest」与「应用层两段查」继续承接（⚠️，ingest 概念 ✅ 文档总入口 https://www.elastic.co/docs/manage-data/ingest）。

## 工程要点与常见坑

- 决策顺序（本章灵魂）：**先问子项要不要被单独搜/改**，再问读写比，最后才选结构——照关系数据库思维直接内嵌是串味事故主源。
- 同位数组的另一半解法：1.x 无原生 solution；今天可用 flattened 字段型（整对象数组免展平但查询力弱）或 ES 之外的关系引擎——对位 #16 波5 兄弟与 [../Graph_Databases_2e/00-总览与阅读地图.md](../Graph_Databases_2e/00-总览与阅读地图.md)（关系即公民的另一世界）。
- nested 里再套 nested 的路径书写与成本翻倍，书中的忠告在向量时代变成「多向量必须 nested」的硬规则。

## 五种路线的请求体对照（⚠️ 转述，1.x 版式）

```bash
# (2) 对象内嵌：展平（串味源）
"comments": { "properties": { "user":{"type":"string","index":"not_analyzed"},
                              "stars":{"type":"integer"} } }
# (3) nested：子文档成组，查询必须走 path
curl -XGET 'localhost:9200/restaurants/_search' -d '{ "query": { "nested": {
  "path":"comments", "query": { "bool": { "must":[
    { "term":{"comments.user":"tom"} }, { "term":{"comments.stars":5} } ]}}}}}'
# (4) parent-child：子文档带 _parent + ?parent= 路由，has_child 反查父
curl -XPUT 'localhost:9200/reviews/type1/1?parent=1&routing=1' -d '{ "user":"tom" }'
curl -XGET 'localhost:9200/restaurants/_search' -d '{ "query": { "has_child":
  { "type":"type1", "query": { "term":{"stars":5} } } } }'
# (5) 反规范化：把字典抄进每条文档，改字典=update_by_query 扇出重写
# (6) 应用侧 join：先查 ids 再 terms —— GET /users?..., 再 {"terms":{"user_id":[...]}}
```

对照读法：nested 查询的「must 同 path 内配对」与 8.2 展平的跨值命中之差，正是 🔧 组 F
里「同位关系要不要 HAVING 兜底」的 ES 版；parent-child 的 `?parent&routing`
把 8.4「同分片才合法」写进了 URL 里。

## 章内问答（自测）

**Q1 为什么 nested 更新等于重灌整个父文档？**
A：子文档与父同处一个 Lucene 文档组，段不可变——改一个子=组内全部重写；这是「配对正确性」的存储级定价。
**Q2 parent-child 何时仍优？何时让位？**
A：子项高频独立增删+按父查询的场景仍用它（今 join 字段）；父查子为主且子量小时 nested 更简单，应用侧 join 更省索引空间。
**Q3 反规范化的字典更新风暴如何缓解？**
A：小字典进缓存/脚本参数、批量 update_by_query 低峰执行、或改为「字典独立索引+两段查」——书中三条全部沿用至今。

**决策速查（照抄进设计评审）**
| 形态 | 读配对正确性 | 子项独立改写 | 索引膨胀 | 查询语法负担 |
|---|---|---|---|---|
| 对象内嵌 | ✗（串味） | ✗（整父重写） | 低 | 无 |
| nested | ✓（path 配对） | ✗（组内重写） | 高（子=文档） | nested 查询/聚合 |
| parent-child（今 join） | ✓ | ✓（子独立增删） | 中（父查子绕） | has_child/has_parent |
| 反规范化 | ✓（冗余自洽） | ✗（扇出重写） | 视扇出 | 无 |
| 应用侧 join | ✓ | ✓（各存各） | 最低 | 两段查询+一致性窗口 |

## 核心概念速览（中英对照）

1. **字段展平** — Flattening：对象按点号路径拍平成多值字段，数组同位关系丢失。
2. **串味** — Cross-talk：AND 条件被同一父文档的不同子项分别满足的假命中。
3. **nested 类型** — Nested Type：子对象独立成隐藏文档、按路径配对的结构。
4. **join 查询族** — nested/has_child/has_parent：为配对语义专设的查询入口。
5. **_parent（已废）** — Parent Field：1.x 父子机制，6.0 由 join 字段替代。
6. **routing 亲和** — Routing Affinity：父子同分片才能 join 的物理前提（第 9 章工具）。
7. **反规范化** — Denormalization：冗余数据换读速，写扇出为税。
8. **应用侧 join** — Application-side Joins：多次查询在客户端拼接结果。
9. **写扇出** — Write Fan-out：改一处字典须重写全部冗余副本。
10. **读放大/写放大三角** — Read/Write Amplification Tradeoff：五种路线的统一评价轴。
11. **flattened 字段型** — Flattened：整对象数组以 key-value 存储、免串味但查询力受限（后裔方案 ⚠️）。
12. **ingest 富化** — Ingest Enrichment：管道内补全冗余字段，反规范化的工程化。

## 最新演进与工业实践

- **机制存续与替换**：展平/nested 语义原样（✅ mapping-types 8.17 实抓）；`_parent`→`join` 字段→8.x `serialized` 父子三代；`has_child/has_parent` 查询族持续在位（⚠️ 查询族专页 slug 本环境不可达，以 mapping 总面 ✅ https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping.html 实抓为锚）。
- **向量把 nested 顶上必选**：一个文档多个向量字段/多切片必须走 nested dense_vector（✅ dense-vector/sparse-vector 文档均实抓 200），RAG 文档分块进 ES 的标准形态就是 nested 向量+正文（⚠️ 实践共识转述）。
- **关系外移**：CDC（Debezium/ES 官方 connectors）+ ingest enrichment 让「应用侧 join/反规范化」流水线化；与关系库分工「DB 保真相、ES 保投影」在 2026 仍是教科书姿势（⚠️；CDC 生态 ✅ https://www.elastic.co/docs/manage-data/ingest 同类总览实抓）。
- **工业教训**：跨分片父子的合法边界、nested 更新风暴、flattened 的取舍——书中决策矩阵被引用频率不减；「先问更新频率再选结构」与 #100 之后全部 ES 文档一致（⚠️）。
