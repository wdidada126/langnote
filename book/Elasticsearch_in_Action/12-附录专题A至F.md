## A · Working with geospatial data（地理数据）

- A.1 点与距离：1.x 的 geo_point 存法（`"41.23, -96.57"` 字符串/对象/geohash 三形态）与 `geo_distance` 排序基准
- A.2 距离进排序：多排序组合里插 geo 距离项（餐厅「按评分+距离」）
- A.3 距离过滤：geo_distance filter（半径内）
- A.4 点是否属于形状：geo_shape 索引多边形、`geo_shape`/`within` 查询
- A.5 形状相交：shape×shape 关系谓词
⚠️ 书中口径是 1.x 的 `geo_point`/`geo_shape` mapping 与 filter DSL；点字段至今同名（✅ 映射总面 https://www.elastic.co/guide/en/elasticsearch/reference/8.17/mapping-types.html 实抓；geo 专页本环境 404 不引，细节 ⚠️）。现代增量：`geo_point` 支持 index 选项与 script 距离；`shape` 查询统一进 query 上下文；地图可视化交给 Kibana（⚠️ 转述；检索总面 ✅ https://www.elastic.co/docs/solutions/search）。
🔧 类比局限声明：SQLite 空间扩展（spatialite）本机不可用、DuckDB 空间类型本波未验——**附录 A 无类比演示**，按纪律如实标 ⚠️ 全转述。

## B · Plugins（插件机制）

- B.1–B.5 插件的安装/访问/依赖声明/卸载升级：1.x 用 `bin/plugin -install …` 装 head/分析器/transport 等，`plugin.mandatory` 防漏装
⚠️ 1.x 插件=下载进 plugins 目录、重启生效；分析插件（如中文分词）是当年读侧的刚需外挂。今值：安装命令改 `bin/elasticsearch-plugin install`（⚠️ 转述；6.x 起插件须版本严格匹配）；**更大变化是商业线**——原付费 X-Pack 功能（安全/告警/ML/图形检索）并入默认发行，「插件生态」收缩为 analysis/repository/ingest 类扩展（✅ 以 mapping/ingest 实抓页为锚 https://www.elastic.co/docs/manage-data/ingest，生态细节 ⚠️）。

## C · Highlighting（高亮）

- C.1 基础：`highlight` 块圈定字段，命中词进 `<em>` 片段
- C.2 选项：fragment_size/number_of_fragments/pre_tags/post_tags
- C.3 实现：unified/plain/fvh 前身的选型与「分析器一致性」告诫（高亮词来自查询分析结果，index/query analyzer 分叉会失配）
今式 highlighter 三实现（unified/plain/fvh）与 `boundary_chars` 族参数（✅ https://www.elastic.co/docs/reference/elasticsearch/rest-apis/highlighting 实抓）。工程教训不变：高亮贵在对每个命中重走分析链，**别对大字段全量高亮**。

## D · Elasticsearch monitoring plugins（监控插件群，1.x 化石标本）

BigDesk（可视化）/ ElasticHQ（管理）/ Head（查询构造器）/ Kopf（快照/warmer/percolator 面板）/ Marvel（细粒度分析，Elastic 自家）/ Sematext SPM（全家桶）——书中逐一截图演示。⚠️ 六者的 1.x 插件形态全部退役：Head 靠 `_module` 路径存活多年也已归档；Marvel → X-Pack monitoring → Kibana Stack Monitoring；ElasticHQ 转型独立 Web 应用。2026 的对应物=Kibana + Elastic Agent/APM + 第三方 Grafana 导出（✅ 生态入口 https://www.elastic.co/search-labs 与部署总览 https://www.elastic.co/docs/deploy-manage 实抓；「Marvel→X-Pack」沿革为社区广泛记载 ⚠️）。附录 D 的阅读价值从「选型」变成「观察一轮生态生死」——插件 API 的大版本断裂正是 B 章风险的实证。

## E · Turning search upside down with the percolator（反向搜索）

- E.1 基础：**把查询存进索引、拿文档去匹配查询**。1.x 姿势：往特殊索引 `_percolator` 注册查询文档，`POST /idx/_percolate {"doc":…}` 返回「哪些已存查询命中此新文档」。餐厅用例：订阅「新菜符合我的口味查询」。
- E.2 性能：查询数量线性成本、按类型/域隔离、percolate_bulk（第 10 章呼应）
- E.3 功能技巧：高亮 percolated 查询（C 章联动）、query 带 filter 子句参与
⚠️ 1.x 的 `_percolator` 特殊索引在 5.0 被彻底重造为「普通索引里存 `percolator` 查询字段的文档 + `percolate` 查询 DSL」——书中操作面已全部作废，**反向匹配的产品思想**（告警/订阅/风控）原样长寿。今位（✅ 实抓）：https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-percolate-query；与 watcher/规则引擎组合成 ES 原生告警底座（⚠️ 转述）。

## F · Using Suggesters（自动补全与 Did-You-Mean）

- F.1 Did-You-Mean：`term` suggester 按编辑距离+词频纠错，串进第 4 章拼查询
- F.2 Autocomplete：`completion` suggester——FST 驻内存、`input/output/weight/payload`，前缀补全毫秒级；与第 5 章 edge ngram 双路线互补（精确度/新鲜度/内存三角）
今位：completion/phrase/regex suggester 族仍在（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/search-suggesters.html 实抓）；`search_as_you_type` 字段型（⚠️ 专页未逐验）把「边输边搜」做成 mapping 一行；补全的 2026 终局是「completion 打底+语义模型 query suggestion」（LLM 路线 ⚠️ 实践转述，无官方文档不背书）。
🔧 类比 D 复用（SQLite 3.45.3 实跑）：FTS5 `tokenize='trigram'` 下 `MATCH 'arch'/'lasti'` 皆中——「预切词项换子串命中」与 completion/edge-ngram 同一空间换时间原理；FST 有序遍历与 payload 返回为 ES 独有，无法类比处如实 ⚠️。

## 工程要点与常见坑（六题合讲）

- 插件类知识（B/D）是全册**折旧最快**部分：照书命令在 2.x+ 必挂；读法是学「扩展点设计」而非记命令。
- geo/percolator/suggest 三者都吃第 5 章分析器配置：任何 analyzer 分叉先想高亮与补全会不会失配。
- 「查询存起来反向匹配文档」（E）在可观测告警里已成产品标配——旧 API 名字死去，语义永生。

## 附录请求体对照（⚠️ 转述，1.x 版式；E/C/F 三题）

```bash
# E.1 反向搜索：查询存进特殊索引 _percolator
curl -XPUT localhost:9200/_percolator/queries/q1 -d '{ "query": {
  "bool": { "must": [ { "term": { "tags":"greek" } } ],
            "filter": { "range": { "stars": { "gte":4 } } } } } }'
curl -XGET localhost:9200/restaurants/_percolate -d '{ "doc": {
  "name":"Elastica", "tags":["greek"], "stars":5 } }'
# → matched_queries:[q1]：新文档「喂给」存量查询的订阅式匹配（告警/邮件推送的 2015 形态）
# C.1 高亮三件套
curl -XGET 'localhost:9200/restaurants/_search' -d '{ "query": { "match": { "dish":"salad" } },
  "highlight": { "pre_tags":["<b>"], "post_tags":["</b>"],
                 "fields": { "dish": { "fragment_size":120, "number_of_fragments":2 } } } }'
# F.2 completion 建议器：mapping 声明 + suggest 请求
#   "ac": { "type":"completion", "analyzer":"simple" }
curl -XGET 'localhost:9200/restaurants/_suggest?pretty' -d '{ "ac": {
  "text":"gr", "completion": { "field":"ac", "size":5, "fuzzy": { "edits":1 } } } }'
```

对照读法：`_percolator` 特殊索引与 `_percolate` 端点在 5.0 全部作废——今式是「文档里存
`percolator` 类型字段 + 查询里 `percolate` 动词」（✅ 专页见演进节）；高亮块几乎原样可跑；
completion 的 `input/weight/payload` 结构今仍在（✅ 8.17 search-suggesters）。

## 章内问答（自测）

**Q1 percolate 为何叫「搜索倒过来」？**
A：正常搜索=查询找文档；percolate=文档找查询。告警场景「每条新日志匹配全部订阅规则」正是批量 percolate。
**Q2 completion 与 edge ngram 的选型三角？**
A：延迟（FST 毫秒级最优）/新鲜度（completion 需重建段才更新权重，edge ngram 实时）/内存（FST 常驻、ngram 倒排膨胀）。
**Q3 高亮为什么和 05 章强耦合？**
A：高亮=对命中字段重走分析链找回词位置；index/query analyzer 分叉或 `pre_tags` 配错，命中词与展示词就两张皮。

## 核心概念速览（中英对照）

1. **geo_point** — 地理点字段：经纬度/geohash 多形态输入，支持距离排序过滤。
2. **geo_shape** — 地理形状：多边形/线索引，点内含与相交查询。
3. **插件** — Plugin：1.x 以 bin/plugin 装载的功能扩展，6.x+ 严格版本匹配。
4. **高亮** — Highlighting：返回命中词片段并包标签，依赖分析器一致性。
5. **unified/fvh/plain** — 高亮实现三选：速度/精度/大字段场景的取舍。
6. **监控插件群** — BigDesk/Head/Kopf/Marvel…：1.x 生态化石，Marvel 入 X-Pack 后继无人。
7. **percolator** — Percolator：存查询、以文档反查匹配的「反转搜索」。
8. **_percolator（已废）** — 1.x 特殊索引形态，5.0 起被 percolator 字段替代。
9. **term suggester** — Did-You-Mean：编辑距离+词频的查询词纠错。
10. **completion suggester** — 补全：FST 内存结构，input/weight/payload 毫秒前缀补全。
11. **edge ngram vs completion** — 补全双路线：倒排精确可分页 vs FST 极速重内存。
12. **search_as_you_type** — 边输边搜字段型：edge ngram 思想的 mapping 化（⚠️）。
