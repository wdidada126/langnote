## 4.2 两个世界的分界：analyzed 查询 vs 精确值查询（⚠️ 转述）

1.x 口径：`match` 查询把输入串过**同字段索引期分析器**再查倒排（`"greek salad"` → 词项 greek+salad）；`term`/`terms`/`range` 走 filter DSL **不过分析**，直接拿值比对 keyword 型倒排。经典坑：对 analyzed string 用 `term:"Green"` 查不到（索引期被小写成 green）。今式同构：match↔text 字段、term↔keyword 字段，坑原样保留（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/search-request-body.html 实抓 query DSL 总面）。
`filtered query`（1.x 把打分查询与过滤组合的容器）**2.x 被 query 上下文/filter 上下文取代**——bool 的 must/filter 分区即其后身；filter 上下文不算分、可缓存（✅ 8.x bool 文档同族 search-request-body）。

## 4.3 bool：四分区语义（⚠️ 转述）

`must`（参与打分）、`should`（加分项，配 `minimum_should_match` 可变硬条件）、`must_not`（纯过滤不算分）、`filter`（1.x 内嵌 filtered）。餐厅例子反复用：关键词匹配放 must，营业/评分区间放 filter，「不含某菜系」放 must_not。dis_max 在多字段独立打分时取「最佳字段分」，配 `tie_breaker` 混血——这是第 6 章相关性的接口。

## 4.4 高级查询与成本梯度（⚠️ 转述 + 🔧 类比组 D）

regexp/wildcard/prefix/fuzzy 直接扫词项字典，**前置通配（`*salad`）最贵**；书中建议：能用 edge_ngram 预切就不要运行时 wildcard（第 5 章呼应）。
🔧 SQLite 3.45.3 / DuckDB 1.5.5 实跑：

- FTS5 `tokenize='trigram'` 表内 `MATCH 'arch'` 与 `MATCH 'lasti'` 均命中 `'elasticsearch in action'`——子串命中靠**预切 trigram 词项**，等价于「用索引空间换 wildcard 时间」；
- DuckDB `msg LIKE 'aggregation shard%'` 200k 行前缀扫 count=1,990、4.4 ms——LIKE 无倒排可走，线性代价是结构性的。
结论类比：运行时通配=线性税，预分词=空间预付；**FTS5 trigram≠ES edge_ngram**（无打分、无分片），仅心智对齐。

## 4.5–4.6 exists/missing 与选型表（⚠️ 转述）

1.x：`exists`/`missing` filter 判字段在/不在（依赖 `_source`/doc_values 有无的旧语义）。今式：exists→`exists` query，missing→`bool.must_not.exists`（✅ search-request-body 同族）。
本章选型表精华（跨版本有效）：全文→match/multi_match；精确/枚举→terms；区间→range；存在→exists；「像用户输入一样搜」→simple_query_string；**regexp/wildcard/fuzzy 是最后手段**。

## 工程要点与常见坑

- `from+size` 深分页在 1.x 每个分片都要取前 offset+size 再归并——协调节点内存被大 offset 吃掉；scroll/之后 search_after 是为解此题而生（⚠️ 转述；现代面 ✅ https://www.elastic.co/guide/en/elasticsearch/reference/current/search-profile.html 可用于观测每片成本）。
- `query_string` 会解析用户输入里的 `AND/+/=` 语法，直接透传用户串是注脚级事故源；用户串用 `simple_query_string` 或 match（⚠️，✅ 同上 8.17 文档面）。
- filter 上下文缓存的受益者是高基数复用（status=published），低复用 range 过滤塞 filter 只是白占缓存（1.x filter cache 语境；今 node/query cache 语义已换，见 10 章）。

## 查询骨架对照（⚠️ 转述，1.x 版式）

```bash
curl -XGET 'localhost:9200/restaurants/_search?pretty' -d '{
  "from": 0, "size": 10,
  "query": {
    "filtered": {                                  # 1.x 特色容器，2.x 废除
      "query": { "bool": {
        "must":  { "match": { "name": "greek salad" } },
        "should":{ "term": { "tags": "live-music" } },
        "minimum_should_match": 1
      }},
      "filter": { "range": { "stars": { "gte": 4 } } }
    }
  },
  "sort": [ { "date": "desc" } ],
  "_source": { "include": ["name", "stars"] }
}'
# 现代等价骨架：filtered → bool 内 must/filter 双上下文；其余原样（✅ 8.17 search-request-body）
# 用户输入的安全面：
curl -XGET 'localhost:9200/restaurants/_search?q=greek\ AND\ salad&analyzer=simple'  # URI 简单串仅供调试
```

逐块读法：from/size 的深分页税（每分片取 offset+size 再归并）、`_source` include 减回包、
bool 四分区「谁计分谁不算分」的边界就是本表；`filtered` 壳子在 2.x 删除后，
must/filter 的分工反而更清晰——读旧 JSON 时把壳子拆掉即可。

## 章内问答（自测）

**Q1 term 查 analyzed 字段为何常空？**
A：查询词未经字段索引期分析（小写/词干归一未发生），与倒排词项不同域；这正是 match 存在的理由。
**Q2 filter 上下文为何快？**
A：不算分、谓词位图可缓存复用（1.x filter cache 语境），且短路跳过打分链——但低复用谓词只是白占缓存。
**Q3 prefix 与 wildcard 谁贵？**
A：同族词项字典扫描；`abc*` 尚可（prefix 走字典区间），`*abc` 全字典扫——所以第 5 章 edge ngram 用空间买时间。

## 核心概念速览（中英对照）

1. **查询 DSL** — Query DSL：以 JSON 表达倒排查询的 ES 专属语言。
2. **match 查询** — Match Query：输入过分析器后按词项匹配的全文查询。
3. **term 过滤器** — Term Filter：不过分析、精确值命中的 1.x filter DSL 成员。
4. **查询/过滤上下文** — Query/Filter Context：算分与不算分两大执行域（2.x 取代 filtered query）。
5. **bool 查询** — Bool Query：must/should/must_not/filter 四分区组合器。
6. **最低 should 匹配数** — minimum_should_match：把可选加分项变硬性门槛。
7. **dis_max** — Disjunction Max：多子查询取最高分，可加 tie_breaker。
8. **通配成本** — wildcard/regexp/fuzzy Cost：词项字典上的线性扫描，前置通配最贵。
9. **深分页惩罚** — Deep Paging：from+size 使每分片预取 offset+size。
10. **simple_query_string** — Simple Query String：语法收敛、可安全透传用户输入的查询。
11. **filter cache** — Filter Cache（1.x）：位图级过滤结果缓存，高复用谓词受益。
12. **_source 过滤** — Source Filtering：回包字段裁剪，减传输与反序列化。

## 最新演进与工业实践

- **filtered query 之死**：2.x 起 filter 上下文原生化（bool.filter、constant_score），`missing` filter 删除；查询骨架 8.x 依旧——本章心智零折旧（✅ https://www.elastic.co/guide/en/elasticsearch/reference/8.17/search-request-body.html）。
- **分页正解**：scroll→（8.x 不推荐新用）、search_after+PIT 成深分页唯一正道（✅ https://www.elastic.co/guide/en/elasticsearch/reference/current/cat.html 观测 + search 文档线；总述 ✅ https://www.elastic.co/docs/solutions/search）。
- **混合检索**：2024+ 的「查询选型表」加了新行——语义/向量查询与词法查询经 **retriever 框架（RRF）** 组合排序（✅ https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrievers、kNN ✅ https://www.elastic.co/docs/solutions/search/vector/knn，访问 2026-07/09 实抓均可达）。
- **LLM 查询改写**：工业界以 LLM 改写自然语言→ES DSL（或 ES|QL）成常见架构；官方查询语言 ES|QL 已入 core（✅ https://www.elastic.co/docs/explore-analyze/query-filter/languages/esql）。
- **工业实践**：搜索安全（禁透传 query_string）与「先 bool 骨架后调分」两准则至今是 code review 高频评语；Serverless 下 DSL 完全兼容、成本按查询算力计（✅ https://www.elastic.co/cloud/serverless）。
