## 核心精讲

### 1. 「schema 文件」是本章的暗线（7.1/7.2/7.4/7.5）

NoSQL/消息类 connector 的共性：源端没有（或不暴露）SQL 级元数据，Trino 让你**用 JSON 文件声明表**，放到 catalog 的 `etc/schema/` 目录。以 Kafka 为例（教学示意）：

```json
// etc/schema/pageviews.json —— 一条消息流的一张「表」
{
  "tableName": "pageviews",
  "schemaName": "default",
  "topicName": "pageviews",
  "message": {
    "dataFormat": "json",
    "fields": [
      { "name": "user_id", "mapping": "user_id", "type": "BIGINT" },
      { "name": "ts",      "mapping": "ts",      "type": "TIMESTAMP(3)" }
    ]
  }
}
```

- Kafka 细节三题：消息**按 partition 切 split**（并行度=分区数天花板）；默认从 earliest 或按 offset 表消费；解码器 avro/json/protobuf + Confluent Schema Registry（✅ [connector/kafka.html](https://trino.io/docs/current/connector/kafka.html)；书稿时点部分解码器名有变 ⚠️）。
- 「流上的 Trino」边界：Trino 是**在流上做批式快照查询**，不是持续计算——真·流处理归 Flink（[../基于Apache_Flink的流处理.md](../基于Apache_Flink的流处理.md)），湖上流式写读看 Paimon/Hudi 书目录版（[../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md](../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md)）。

### 2. 各源的映射哲学一句话（7.1–7.5）

| 源 | 数据模型 | 表映射策略 | 下推亮点 |
| --- | --- | --- | --- |
| HBase(+Phoenix) | 宽列 KV | Phoenix SQL 表直通 ⚠️ 392 后该 connector 存续以文档为准 | 谓词转 Phoenix SQL |
| Accumulo | 排序 KV+cell 时间戳 | 行键正则/列族列声明 | 行键前缀范围扫描 |
| Cassandra | 宽表+分区模型 | 原生表结构直映（✅ [connector/cassandra.html](https://trino.io/docs/current/connector/cassandra.html)） | 分区键等值→token 分片 |
| Kafka | 字节流 | schema 文件+解码器 | topic 时间/offset 语义 |
| Elasticsearch | 倒排索引文档 | 索引映射表（✅ [connector/elasticsearch.html](https://trino.io/docs/current/connector/elasticsearch.html)） | query DSL 谓词下推 |

共同判断框架：**源端能便宜地回答什么，就把什么交给它**（谓词/limit/聚合），剩下的回 Trino 做。

### 3. 联邦查询的代价账（7.6）

```sql
-- 教学示意：客户投诉工单 = PG 行存 + Kafka 日志 + Hive 画像 的三方 join
SELECT c.region, count(*) 
FROM postgres.main.customers c
JOIN kafka.default.complaints k ON k.customer_id = c.id
JOIN hive.crm.profiles p ON p.customer_id = c.id
WHERE k.ts > now() - interval '7' day
GROUP BY 1;
```

- 网络账：每源「下推后的剩余输出字节」走 exchange；广播还是重分布由 CBO 按统计决定（小表无统计→误判是联邦查询第一大坑，4.9 同款）。
- 延迟账：源端并发/连接池是隐形上限——PG 被 catalog 并发打满会反噬线上业务（「查 OLTP 库请限流」是 483 文档与生产共识，工程口径 ⚠️）。
- 语义账：时区/类型系统（如 ES 的 keyword vs text、Kafka 的 null 消息）在映射层先验齐。

### 4. ETL@Trino：查询驱动的搬运（7.7）

`INSERT INTO hive.x SELECT ... FROM kafka.y` / 跨 catalog `CTAS` 做**轻量回灌与格式转换**（Kafka→Parquet 入湖是书稿经典桥段）。定位判断：

- 量小、临时、SQL 团队自助 → Trino 联邦 + CTAS 够用；
- 量大、需重试/断点/血缘/调度 → 让位 Spark（[../bigdata/05-Spark性能优化.md](../bigdata/05-Spark性能优化.md)）或 Flink CDC → 表格式（06 章表格式书群）；
- 判据一句话：**失败了要不要人救**——要，就归管道引擎；不要（重跑即恢复），Trino 可行。

四问的判别标准同样适用于「要不要用 Trino 接这个源」：若源端自己 SQL 面已足够（如 ES 的 KQL 轻量查、CQL 熟手团队），联邦的边际收益要打上问号——本章 5 个例子背后是同一句反问：**缺的是「跨源」，不是「换方言」**。

### 5. 「声明表」复用检查单（7.1–7.5 通则）

写任何非 JDBC 源的 schema 文件前四问：① 主键/分区键是什么，决定 split 形态；② 哪些列值得暴露（映射成本 ∷ 下推收益）；③ 时间语义（事件时间 vs 摄取时间）放哪一列；④ null/畸形消息的处理策略（解码失败即失败 or 跳过）。四问答完，表定义即定稿。

## 常见误区

- Kafka connector 配 `auto.offset.reset=earliest` 全量扫历史 topic：查询分钟级起、还占满 worker——按 offset/时间窗裁剪（schema 文件或表属性，✅ kafka 页口径）。
- 把 Accumulo/HBase 的 rowid 全表扫与 Hive 扫等价看待：KV 源无列裁剪/无统计，成本模型完全不同。
- ES 聚合直接信下推：高基数 terms 聚合常在 Trino 端补算，先 EXPLAIN 验证（4.5 工具，12 章读法）。
- 联邦查询拿 PG 主库当数据源：只读副本 + 资源组限流是底线（10/12 章联动，工程口径 ⚠️）。

## 核心概念速览（中英对照）

1. **schema 文件** — JSON schema descriptor：为无 SQL 元数据的源声明表的文件。
2. **解码器** — decoder：Kafka 消息字节 → 列（json/avro/protobuf/raw）。
3. **模式注册表** — Schema Registry：Avro 等带 schema 演进的元数据服务。
4. **行键映射** — rowId mapping：Accumulo/HBase 行键作为虚拟列暴露。
5. **分区键** — partition key（Cassandra）：token 范围分片与并行的依据。
6. **索引表映射** — index-to-table mapping：ES 索引的字段类型投影。
7. **DSL 下推** — query DSL pushdown：ES 谓词转译为原生查询。
8. **联邦查询** — federated query：多 catalog join，下推剩余量在 Trino 汇合。
9. **只读副本** — read replica：联邦打 RDBMS 的安全垫（工程实践）。
10. **查询驱动迁移** — ETL by query：INSERT/CTAS 跨 catalog 的轻搬运模式。
11. **offset 裁剪** — offset/time window：Kafka 快照查询的范围控制。
12. **宽列存储** — wide-column store：HBase/Cassandra/Accumulo 的公共模型。
13. **文档存储** — document store：ES/Mongo 的 JSON 文档世界 ⚠️ 7.5 同族。
14. **连接池压力** — connection pool pressure：联邦查询对源端 OLTP 的反噬形态。
