## 核心精讲

### 1. 两份 config，一套二进制（5.2/5.7）

```properties
# 教学示意 —— coordinator: etc/config.properties
coordinator=true
node-scheduler.include-coordinator=false
http-server.http.port=8080
discovery.uri=http://coordinator:8080
query.max-memory=100GB
query.max-memory-per-node=16GB

# worker 仅差两行：
coordinator=false
# discovery.uri 指向 coordinator 不变
```

- `query.max-memory`（集群级）/`query.max-memory-per-node`（节点级，默认堆的 ~30–40% 动态算 ⚠️ 精确公式以 483 [properties-resource-management](https://trino.io/docs/current/admin/properties-resource-management.html) 为准）构成第一层内存护栏；12 章 spill 是第二层。
- 官方部署清单（✅ [installation/deployment.html](https://trino.io/docs/current/installation/deployment.html)）强调硬件同质、时钟同步、网络低延迟——exchange 是拉取式流水线，跨 AZ 部署要实测。

### 2. JVM 与 GC（5.5，书稿→483 差异最大）

- 392 时代书给 G1 参数模板；483 时代最低 JDK 抬升、`--add-opens`/`-XX:+UseG1GC` 组合进官方模板（逐版矩阵 ⚠️ 未核，照抄文档页而非本书）。
- 堆利用率视角：Trino 的页缓存 + exchange buffer 常驻堆，GC 停顿直接表现为 stage 卡顿；-Xmx 建议留 20–30% 堆外余量给元空间/线程栈/页外缓存（工程经验 ⚠️ 转述）。
- `var/log/` 与数据盘分离、`jvm.config` 纳入配置仓库管理（版本化基础设施）属本章最佳实践延伸。

### 3. 拓扑三形态（5.8/5.9/5.10）

| 形态 | 要点 | 适用 |
| --- | --- | --- |
| 裸机/VM + RPM/tarball | launcher 或 systemd；worker 静态 | 传统 IDC，低变更频率 |
| 云 VM 组 | 对象存储做数据/日志归档；worker 组走 ASG | 中等规模，网络同 AZ |
| Kubernetes + Helm | coordinator Deployment/StatefulSet，worker 可 HPA；拓扑标签 | 弹性优先、平台团队成熟 |

K8s 路径 483 文档并入 containers 章统一维护（✅ [installation/containers.html](https://trino.io/docs/current/installation/containers.html)）；官方 chart 仓库与书成稿时的社区 chart 结构已大改——以官方文档口径为准，别考古旧 values 文件。

### 4. 规模估算（5.11）的三段式

1. **扫描带宽**：峰值查询并发 × 平均查询扫描量 ÷ 可接受延迟 = 需求吞吐；除以单节点磁盘/网络实测带宽（本地 NVMe/云上 EBS/网络增强型 VM 差异巨大，⚠️ 数字必须自测，书中示例数字不可照搬）。
2. **内存驻留**：聚合/join 中间态峰值 → 决定 `query.max-memory-per-node` 与 spill 频率。
3. **冗余**：N+1 起步，coordinator 单独高配；worker 故障流水线重跑，需要余量吸收重调度洪峰。

### 5. 日志与可运维性（5.3）

- `server.log`（含 GC 前后配置位）、`http.log`、`launcher.log`；log.level 的类别名前缀控制 connector 噪声。
- 生产应接：指标导出（事件 API → Prometheus 生态 ⚠️ 本次未抓官方 exporter 仓名，作生态转述）、UI 访问控制（10 章）、慢查询归档（12 章）。

### 6. 上线前检查单（5.1–5.11 压缩为可执行清单）

- [ ] coordinator/worker 配置 diff 只有角色两行（5.2）
- [ ] `node.id` 每节点唯一且持久、`node.environment` 全集群一致（5.4）
- [ ] jvm.config 与所用 Trino 大版本的官方模板逐行核对（5.5，392 模板勿用于 483）
- [ ] 日志/ spill 目录在独立盘、`var/` 不被容器临时层吞掉（5.3）
- [ ] discovery.uri 从 worker 侧 telnet/DNS 可达验证过（5.7）
- [ ] 压测过「coordinator 挂掉—worker 行为」与「单 worker 消失—查询重跑」（5.11 冗余假设）
- [ ] 监控/日志采集在应用崩溃路径上自举过（launcher 崩溃时日志仍能出逃，5.3）
- [ ] worker 扩缩容演练：新节点 5 分钟内进入可调度状态且 `SHOW NODES` 可见（5.7）
- [ ] 配置以代码仓库管理，回滚 = 重新部署镜像（与 13.1 案例做法一致）

## 常见误区

- 生产开着 `node-scheduler.include-coordinator=true`：一个大查询就能把调度器饿死（4.1 的教训，5.2 的默认值坑）。
- 容器化但 worker 不固定 CPU/内存 request=limit：JVM 堆看到宿主内存，OOMKilled 循环。
- `node.id` 用模板生成却在扩缩容时复用：发现服务与历史事件错乱；每节点唯一且持久。
- 把 Helm 当银弹：exchange 流水线对网络抖动敏感，跨节点组/跨 AZ 不压测就上量，延迟长尾必炸（工程口径 ⚠️）。
- 抄书 392 的 jvm.config 到 483：模块系统参数缺 `--add-opens` 直接起不来（02 章同款，此处是生产事故版）。

## 核心概念速览（中英对照）

1. **服务端配置** — config.properties：引擎行为主配置，coordinator/worker 仅差标志位。
2. **节点配置** — node.properties：`node.environment` + 持久 `node.id`。
3. **发现服务** — discovery：worker 心跳与拓扑注册中心（内嵌于 coordinator）。
4. **启动器** — launcher：进程管理脚本（run/start/stop/status），生产配 systemd。
5. **内存护栏** — query.max-memory(-per-node)：集群/节点两级查询内存上限。
6. **G1 垃圾回收** — G1GC：书稿主推收集器；停顿-吞吐权衡在 5.5 展开。
7. **RPM 安装** — RPM packaging：`trino-server` 包 + service 单元。
8. **Helm chart** — Helm chart：K8s 模板化部署，coordinator/worker 分池。
9. **弹性伸缩** — autoscaling：worker 无状态带来的水平扩缩红利。
10. **拓扑标签** — node properties tags：`node.include-hive` 式亲和调度 ⚠️ 书稿口径，属性名以 483 为准。
11. **数据本地性** — data locality：同节点/同 AZ 存算亲和（Hive+块存储场景）。
12. **日志轮转** — log rotation：server.log 体量治理。
13. **同质硬件** — homogeneous nodes：调度器按「均质 worker」假设分片。
14. **时钟同步** — clock skew control：事件时间线与分布式排错的隐性地基。
15. **规模三段式** — sizing：扫描带宽 × 内存驻留 × 冗余的估算法（本书方法论）。
