## 核心精讲

### 1. 事务在关系模型里的位置

前两部分的公设说的是"某一时刻的状态必须满足哪些谓词"（第 6 章的断言）。事务回答的是另一个问题：**状态之间的跳跃必须满足什么**。两条直接联系：

1. 第 7.5 的"赋值是整体替换" ⇒ 一个业务动作经常需要同时改多个 relvar（发货：SP 减数量 + 库存表加流水）。这些赋值必须**一起生效**，否则中间状态会违反断言 ⇒ 这就是原子性在模型层的动机（🔧 本直 D11e 显示：SQLite 的约束违反默认只撤销**出错那一条语句**，事务并不自动整体回滚——必须由开发者显式 `ROLLBACK`，这正是"原子单位是事务还是语句"的口径差）。
2. 第 6.3 的"延迟检查" ⇒ 断言可以在**事务边界**求值；事务边界就是断言的求值时刻。

⚠️ 作者的一贯批评（转述，非逐字）：把"一致性"写进 ACID 是**误导**——一致性是应用/约束定义的目标属性，不是 DBMS 提供的机制属性；AID 才是机制。

### 2. 恢复与日志（8.2.1 / 8.2.2）

概念切片（本章的深度就到这里）：

- **日志**：按序记录"事务开始 / 前像 / 后像 / 提交或中止"的持久结构；
- **恢复**：故障后，对已提交事务做 REDO、对未完成事务做 UNDO；
- **持久性的真实含义**：`COMMIT` 返回即意味着"掉电也不丢"——这要求日志在提交前落盘（对应实现里的 fsync/WAL 顺序，细节不属本章）。

🔧 实测（D11a–D11d，SQLite 3.45.3，文件库 + 两个连接）：

```
### D11a 原子性：事务内两步，ROLLBACK 后回到起点
  事务内 -> []                       -- UPDATE + DELETE 之后表空了
  回滚后 -> [(1, 10)]                -- 两步一起被撤销
### D11b 隔离性：未提交的事务对另一连接不可见
  c2 看到 -> [(1, 10)]               -- c1 已把 V 改成 99 但未提交
### D11c 写写冲突：库级写锁
  c2 !! OperationalError: database is locked
  c1 提交后 c2 看到 -> [(1, 99)]
### D11d 持久性靠日志
  journal_mode -> [('delete',)]      -- 默认回滚日志模式，非 WAL
  同步强度 -> [(2,)]                 -- synchronous = FULL
```

四条观察正好对应 8.1/8.2/8.3/8.4 的四组概念：**原子性=撤销整个事务**、**隔离性=未提交不可见**、**并发性=锁**（SQLite 干脆把粒度降到整个库）、**持久性=日志 + 同步强度**。

### 3. 并发性与可串行化（8.3）

判据只有一条：**并发执行的结果，是否等于某个串行执行的结果**（可串行化）。三类冲突：

| 现象 | 描述 | 违反 |
| --- | --- | --- |
| 丢失更新（lost update） | 两个事务都读旧值、各自加一后写回 | 隔离性；需 2PL 或原子读改写 |
| 不可重复读（non-repeatable read） | 同事务内两次读同一行得到不同值 | 快照/可重复读隔离 |
| 幻读（phantom） | 同事务内两次范围查询，第二次多出/少掉满足条件的行 | 谓词锁范围 |

作者的立场 ⚠️ 重构：并发控制的正确性定义（可串行化）属于**理论**；SQL 的四个隔离级别是对它的**近似与让步**，且这个近似出了名地不严格——标准里对 `REPEATABLE READ` 的定义不排除幻读，"隔离级别"的名字与语义在不同厂商处含义不一致。工程后果：不能靠级别名字推理正确性，只能靠"是否可串行化"验证。深入机制见 [../数据库系统概念6/15-并发控制.md](../数据库系统概念6/15-并发控制.md) 与 [../mysql/21-事务隔离级别与MVCC.md](../mysql/21-事务隔离级别与MVCC.md)。

### 4. 锁（8.4）

- 锁类型：共享（S）/排他（X）；
- 兼容性矩阵决定调度；
- **两阶段锁（2PL）**：加锁全部在解锁之前 ⇒ 保证冲突可串行化（严格 2PL 还可保证可恢复）；
- 死锁：等待图成环 ⇒ 超时或检测回滚。

🔧 与 D11c 呼应：SQLite 的 `database is locked` 是"库级写锁 + `timeout=0.2`"的直接后果——**锁粒度**这一节在本章只有一段，但它决定实现的全部形态（行锁/页锁/库锁的取舍见 [../mysql/22-锁.md](../mysql/22-锁.md)）。

### 5. SQL 的讨论（8.5）：语句层与事务层的缝隙

SQL 提供的事务语句（⚠️ 转述）：

```
START TRANSACTION | BEGIN [WORK]        -- 开始
COMMIT | END TRANSACTION                -- 提交
ROLLBACK [TO savepoint_name]            -- 回滚（或回到保存点）
SAVEPOINT name / RELEASE SAVEPOINT name -- 保存点
SET TRANSACTION ISOLATION LEVEL ...     -- 隔离级别
SET TRANSACTION READ ONLY / READ WRITE  -- 读写属性
```

作者的批评点（⚠️ 重构，逐条都在产品里可复现）：

1. **隐式事务**：多数接口默认"每条语句即一个事务"（autocommit），使"事务"退化成默认关闭的东西；🔧 侧证：Python `sqlite3` 的 `isolation_level` 会自动在 DML 前插入 `BEGIN`，把语义搞得和 CLI 不一致（本直 D11 脚本显式设 `isolation_level=None` 才拿到可控行为）。
2. **隔离级别命名与定义不严**：`READ COMMITTED`/`REPEATABLE READ` 在标准与各产品之间语义漂移。
3. **`SET TRANSACTION` 的作用域含糊**（下一条语句？下一个事务？整个会话？）——⚠️ 转述。
4. **约束检查时机与事务边界的绑定不完整**：只有 `DEFERRABLE` 的少数字段能延迟；断言层根本没有（第 6 章 🔧 ①）。
5. 🔧 实测补充（SQLite）：`DEFERRABLE INITIALLY DEFERRED` 的外键在**事务内插入非法值不报错、`COMMIT` 时才抛 `IntegrityError: FOREIGN KEY constraint failed` 并整体回滚**——"延迟到事务边界求值"在约束层是可行的，只是各家做得不完整。

## 常见误区

| 误区 | 纠正 |
| --- | --- |
| 「ACID 的四条同级」 | C 是目标（由约束定义），AID 是手段；作者明确反对把 C 当"DBMS 提供的特性" |
| 「持久性 = 写盘即安全」 | 只有日志按序落盘（写前日志）后 COMMIT 才算持久；🔧 `synchronous=FULL` 就是这条的代价开关 |
| 「选了 SERIALIZABLE 就不用测试并发」 | 隔离级别是产品给的近似；正确性判据仍是可串行化，边界情况（谓词锁缺失时的幻读）要自己验 |
| 「加锁 = 变慢」 | 锁粒度与 2PL 是换取正确性的价格；无锁的代价是把冲突推到应用层（更慢更错） |
| 「ORM 的事务边界可靠」 | autocommit + 隐式事务是常见陷阱；事务边界必须显式（🔧 D11 需要 `isolation_level=None` 才好控制） |
| 「事务 = 一次 HTTP 请求」 | 事务是数据库层概念，边界与业务/请求边界无关；跨库时需要分布式事务（不属本章） |

## 核心概念速览（中英对照）

- **事务** — transaction：把数据库从一个一致状态转移到另一个一致状态的原子工作单元
- **原子性** — atomicity：事务的所有改动要么全生效要么全不生效
- **一致性** — consistency：事务结束时数据库满足全部断言（目标，不是机制）
- **隔离性** — isolation：并发事务互不可见中间状态
- **持久性** — durability：已提交事务的改动不受故障影响
- **恢复日志** — recovery log：按序记录前像/后像/提交点，供 UNDO/REDO
- **写前日志** — write-ahead logging (WAL)：改动落盘前日志必须先落盘 ⚠️ 转述机制名
- **可串行化** — serializability：并发结果等价于某个串行顺序，正确性的唯一判据
- **丢失更新 / 不可重复读 / 幻读** — lost update / non-repeatable read / phantom：三类并发异常
- **共享锁 / 排他锁** — shared / exclusive lock：读锁与写锁
- **两阶段锁** — two-phase locking (2PL)：加锁阶段先于解锁阶段，保证冲突可串行化
- **死锁** — deadlock：互相等待的环；靠超时或检测回滚打破
- **保存点** — savepoint：事务内可回滚到的中间标记
- **自动提交** — autocommit：每条语句自成一个事务的默认模式（SQL 的主要批评点之一）
- **延迟约束检查** — deferred constraint check：把断言求值推到事务边界（🔧 SQLite 外键实测）

## 最新演进与工业实践

- **隔离级别在 2020 年代的产品现实（⚠️ 转述）**：PostgreSQL 自 9.1 起用**快照隔离（SSI 提供可串行化）**，并明确 `READ UNCOMMITTED` 等同 `READ COMMITTED`；MySQL/InnoDB 默认 `REPEATABLE READ` 且通过间隙锁（gap lock）在很大程度上挡住幻读；SQL Server 2022+ 推荐 `READ_COMMITTED_SNAPSHOT`。这正是本章"级别名字不可用于推理"的当代注脚。机制细节见 [../mysql/21-事务隔离级别与MVCC.md](../mysql/21-事务隔离级别与MVCC.md) 与 [../数据库系统概念6/15-并发控制.md](../数据库系统概念6/15-并发控制.md)。
- **SQLite 的官方形态**（🔧 与文档一致）：默认回滚日志模式 `delete`（本直 D11d 实测），WAL 模式提升并发；锁是库级；`PRAGMA synchronous` 控制持久性强度。⚠️ 未在本目录测 WAL 性能。官方：https://www.sqlite.org/appfileformat.html ✅
- **持久性/吞吐的工程旋钮**：`synchronous=OFF/NORMAL/FULL`、WAL 的 `wal_autocheckpoint`、PostgreSQL 的 `synchronous_commit`（可降到 `off`/`remote_write` 换取吞吐，代价是故障丢失最后若干事务）——这些就是本章"持久性不是布尔而是配置"的现实版。⚠️ 转述。
- **理论侧**：并发控制的正确性判据（冲突可串行化 / 视图可串行化）与快照隔离的异常（写偏斜 write skew）在 Gray & Reuter 系著作与 15-445 课程里是标准内容；论文线的 Aries/System R 精读见 [../../db/db.md](../../db/db.md)。
- **深浅分工**：本章只给"最小必要切片"（4 页 + 练习）；**引擎怎么实现**（日志结构、检查点、MVCC 版本链）在 [../Database_Internals/05-事务处理与恢复.md](../Database_Internals/05-事务处理与恢复.md) 与 mysql/ 目录版；**运维怎么配**在 [#23](../Cost_Based_Oracle_Fundamentals/00-总览与阅读地图.md)/[#45](../Efficient_MySQL_Performance/00-总览与阅读地图.md)/[#87](../Using_SQLite/00-总览与阅读地图.md)（均已落盘，波尾闭环）。
