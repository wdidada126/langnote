# 第 9 章　数据库设计（Database Design ⚠️ 回译）

> 译本 p113–123｜小节（✅ 实抓）：9.1 无损分解 / 9.2 函数依赖 / 9.3 第二范式 / 9.4 第三范式 / 9.5 BC 范式 / 9.6 结论 / 9.7 练习 / 9.8 答案。
> 全书最短的"设计"章（11 页）。它的作用不是教你规范化流程，而是说明**范式为什么是关系模型的推论**：有损分解会造出不存在的"事实"，而那是完整性问题，不是风格问题。

## 本章地图

| 小节 | 内容 | 结论 |
| --- | --- | --- |
| 9.1 无损分解 | 把 R 分解成 R1/R2，若 `R1 ⋈ R2 = R` 则无损；判据：公共属性必须是某一方的码 | 无损性可以在分解**之前**判定，不必等数据出错 |
| 9.2 函数依赖 | FD 是"属性集决定属性集"的约束；候选码就是决定全体的极小 FD | FD 属于约束层（第 6 章），不是数据巧合 |
| 9.3 第二范式 2NF | 消除非主属性对候选码的**部分**依赖 | 只有复合码才可能违反 2NF |
| 9.4 第三范式 3NF | 消除非主属性的**传递**依赖 | 允许少量冗余但保持无损且依赖保持 |
| 9.5 BC 范式 BCNF | 每个决定因素都必须是码 | 最干净；可能丢失 FD 检查（需断言补回） |
| 9.6 结论 | 范式化 = 让每个关系"说的是同一件事" | 目的是防幽灵元组与更新异常，不是形式美 |

## 核心精讲

### 1. 无损分解：本章唯一必须记住的判据

设 R 分解为 {R1, R2}。定义：无损（lossless join）当且仅当对 R 的每个合法关系值 r 都有
`r = (r 投影到 R1 的头) ⋈ (r 投影到 R2 的头)`。

**判据（两片情形）**：`R1 ∩ R2`（公共属性）必须是 R1 或 R2 的**超码**（等价写法：公共属性能决定 R1 或 R2 的全部属性）。

🔧 无损的一例（D9，SQLite 3.45.3）：S(SN, STATUS, CITY) 按 {SN,CITY} 与 {SN,STATUS} 分解，SN 在两个片段里都是码：

```sql
CREATE TABLE S_a AS SELECT SN, CITY FROM S;
CREATE TABLE S_b AS SELECT SN, STATUS FROM S;
SELECT COUNT(*) AS original FROM S;              -- -> [(3,)]
SELECT COUNT(*) AS rejoined FROM S_a NATURAL JOIN S_b;  -- -> [(3,)]
```

🔧 有损的一例（D9b）：S(SN, CITY, STATUS) 按 {SN,CITY} 与 {CITY,STATUS} 分解——CITY 不是后者的码（同一城市可以挂两个状态）：

```sql
CREATE TABLE T9 (SN TEXT, CITY TEXT, STATUS INTEGER);
INSERT INTO T9 VALUES ('S1','Paris',20),('S2','Rome',10),('S3','Athens',40),
                      ('S6','Rome',30),('S7','Paris',10);
-- 原关系 5 个元组
SELECT COUNT(*) AS rejoined FROM
  (SELECT DISTINCT SN, CITY FROM T9) NATURAL JOIN
  (SELECT DISTINCT CITY, STATUS FROM T9);        -- -> [(9,)]
SELECT * FROM (SELECT DISTINCT SN,CITY FROM T9) NATURAL JOIN
              (SELECT DISTINCT CITY,STATUS FROM T9) WHERE SN='S1';
-- -> [('S1','Paris',10), ('S1','Paris',20)]
```

`('S1','Paris',10)` 是**数据库自己发明的事实**：原表里没有"供应商 S1 状态 10"。这就是作者说的"有损分解的后果不是效率，而是谎言"。

注意本直刻意用 `COUNT(*)` 而不是相等比较——因为 SQL 没有"关系相等"（第 4 章 🔧 D10e）；在 Tutorial D 里判据直接写成 `r1 ⋈ r2 = r`。

### 2. 函数依赖：把"约束"落到属性层面

- FD `X → Y` 在关系 r 上成立 ⇔ r 中任意两个在 X 上相等的元组，在 Y 上也相等；
- 候选码 = 决定全属性集的**极小** X（第 3 章定义的 FD 版本）；
- FD 是**意图**（业务规则），不是当前数据的巧合：换一批数据它仍须成立 ⇒ 因此 FD 必须作为约束声明（→ 第 6 章），而 SQL 只能靠 `UNIQUE (X)` 或主键来表达 `X → 全体`；对 `X → Y`（Y 非全体）没有直接语法。

⚠️ 这条限制值得单独记住：**SQL 表达不了非码决定因素**，所以违反 3NF/BCNF 的设计不会被 DDL 拦下来——只能靠设计纪律。

### 3. 三个范式的递进（作者给的是"消除什么"）

| 范式 | 定义（⚠️ 依通行表述重构） | 消除的对象 | 典型症状 |
| --- | --- | --- | --- |
| 1NF | 属性取值为标量（在作者体系里＝值属于某域） | 结构违规 | 一格里放逗号列表 / JSON |
| 2NF | 无**部分依赖**（每个非主属性完全依赖于每个候选码） | 复合码里"只依赖码的一部分"的属性 | 把 `SNO→CITY` 塞进 `(SNO,PNO)` 主键的 SP 表 |
| 3NF | 无**传递依赖**（非主属性不通过其他非主属性依赖码） | 属性链上的冗余 | `SNO→CITY→STATUS` |
| BCNF | **每个决定因素都是码** | 一切由 FD 引起的冗余 | 3NF 允许的边缘反例（多个复合候选码相交） |

每消除一次冗余，得到的都是同一件事的三种表述：

1. 更新异常（改一处忘改另一处）；
2. 删除异常（删掉唯一一条供应记录时顺手删掉了城市信息）；
3. 插入异常（没有供应关系就无法记录一个新城市）。

**BCNF 的代价**（9.5 的诚实之处）：BCNF 分解不一定**保持依赖**（dependency preserving）。分解后 FD 可能横跨多个关系，DDL 检查不到 ⇒ 需要断言/触发器。作者的立场 ⚠️ 重构：这不是"3NF 比 BCNF 好"的论据，而是"模型有断言、SQL 没有"的又一个证据——正好与第 6 章 🔧 ①② 对齐。

### 4. 结论（9.6）与本书的设计观

本章只讲"分解什么时候安全、范式为什么存在"，不讲"怎么从需求推出模式"。作者的分工是明确的：范式化是**验证工具**（给定设计，判断它是否会造成谎言/异常），不是**生成工具**（它不会告诉你该有哪些关系）。生成靠的是谓词与业务命题（→ 第 3/6 章的"约束即命题"，以及 [#8](../Database_Design_and_Relational_Theory/00-总览与阅读地图.md) 的设计流程）。

## 常见误区

| 误区 | 纠正 |
| --- | --- |
| 「范式化是为了减少存储空间」 | 目的是消除冗余引起的**语义风险**（异常与幽灵元组），存储/性能只是副产品 |
| 「反范式化提升性能是常规正确做法」 | 反范式 = 主动引入冗余 ⇒ 必须自己保证一致性（第 6 章"断言缺失"的地方你更没法保证）；见 [../SQL反模式.md](../SQL反模式.md) 的汇总表/实体化视图讨论 |
| 「有 3NF 就够了，BCNF 是洁癖」 | 3NF 允许的反例真能造出更新异常；选哪个是"依赖保持 vs 严格性"的取舍，必须知道代价 |
| 「分解后 JOIN 回来一样，就是无损」 | 必须对**所有**合法状态成立（由判据保证），当前数据巧合相等不算 |
| 「`UNIQUE(CITY)` 就能表达 CITY→STATUS」 | FD 的非码决定因素在 SQL 里无法声明（⚠️），设计纪律补不上就只能靠断言 |
| 「2NF 现在没人提了」 | 复合码 + 部分依赖（多对多表里塞从属属性）在今天仍然高频出现，只是不叫这个名字 |

## 核心概念速览（中英对照）

- **分解** — decomposition：把一个关系模式拆成若干子模式
- **无损分解** — lossless join decomposition：`r = π₁(r) ⋈ π₂(r)` 对一切合法状态成立
- **幽灵元组** — spurious tuple：有损分解连接回来后凭空出现的元组 🔧 D9b
- **函数依赖（FD）** — functional dependency：X → Y，X 相等强制 Y 相等
- **部分依赖 / 传递依赖** — partial / transitive dependency：2NF / 3NF 消除的对象
- **第二范式** — 2NF：无部分依赖（仅对复合候选码有意义）
- **第三范式** — 3NF：无传递依赖；允许某些冗余以保持依赖
- **BC 范式** — BCNF：每个决定因素都是码
- **依赖保持** — dependency preservation：分解后每个 FD 仍可局部检查；BCNF 可能丢失
- **更新 / 删除 / 插入异常** — modification anomalies：冗余的三种临床表现
- **反范式化** — denormalization：为性能主动引入冗余，代价是一致性责任转移
- **范式是验证工具** — normalization as validation：范式化不生成设计，只判定设计风险

## 最新演进与工业实践

- **教学口径的现状（⚠️ 转述）**：2020 年代教材普遍把 2NF 视为"历史条目"，重心放在 FD/多值依赖 → 4NF/5NF 与"依赖保持 vs BCNF"的取舍；本直第 9 章的极简版正好适合作为"为什么需要范式"的第一课，之后再补 4NF/5NF。学院版详见 [../数据库系统概念6/08-关系数据库设计.md](../数据库系统概念6/08-关系数据库设计.md)。
- **产品端对 FD 的支持仍停在码上**：`UNIQUE`/主键只能表达 `X → 全体`；PostgreSQL 的 `EXCLUDE`、生成列（`GENERATED ALWAYS AS ... STORED`，可表达"函数依赖式的派生属性"）、部分/表达式索引是 2024–2026 可用的补充工具 ⚠️ 转述（未在本目录逐一实测）。文档：https://www.postgresql.org/docs/current/ddl-constraints.html ✅
- **数据仓库/湖仓里的范式**：维度建模（星型/雪花）刻意保留冗余（退化维度、汇总事实），把一致性检查从 DDL 挪到 ELT 测试；与本章判据不冲突但**评价标准不同**。对照 [../数据仓库工具箱3.md](../数据仓库工具箱3.md)（Kimball）与同波 [#169 `Building_the_Data_Warehouse`](../Building_the_Data_Warehouse/00-总览与阅读地图.md)（Inmon，已落盘，波尾闭环）。
- **规范化的自动化**：现代工具链里有基于 FD/候选键推导的模式合成与"范式检查器"（数据库设计工具、`database-design-normalizer` 类开源实现 ⚠️ 未验证具体仓库地址，不给链接）。可复现的最低版本就是本章 🔧 的两条 `COUNT(*)` 比较——把它写进迁移测试即可拦截一次有损重构。
