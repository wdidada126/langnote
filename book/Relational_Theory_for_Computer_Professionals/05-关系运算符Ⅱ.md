## 核心精讲

### 1. 匹配与非匹配：把 EXISTS 提升为算子

Tutorial D 形态 ⚠️ 示意：

```
S MATCHING ( SP WHERE QTY > 250 )          -- 半联接：只保留能匹配上的 S 元组
S NOT MATCHING BY { SNO } ( SP )           -- 反半联接：按指定属性匹配
```

语义要点：

- 输入两个关系，输出**左侧关系的一个子集**，头与左侧相同 ⇒ 闭包保持；
- `BY {属性表}` 指定用哪些属性做匹配；缺省用全部同名属性；
- 与 θ-联接的区别：联接会把右侧的属性带出来（并可能复制左侧元组），匹配只回答"有没有"。

🔧 实测（D5b/D5c，SQLite 3.45.3）：

```sql
SELECT * FROM S WHERE EXISTS (SELECT 1 FROM SP WHERE SP.SN = S.SN AND SP.QTY > 250);
-- -> [('S1', 20, 'Paris'), ('S2', 10, 'Rome')]
SELECT * FROM S WHERE NOT EXISTS (SELECT 1 FROM SP WHERE SP.SN = S.SN);
-- -> [('S3', 40, 'Athens')]
```

SQL 的对应物是 `EXISTS` 谓词，不是算子——它只能出现在 WHERE 里，**不能作为一个可投影/可并的关系表达式**使用。这是"表达力缺失"的第一个样本：想对"匹配结果"再做投影，必须在 SQL 里重写一遍 EXISTS。

### 2. 扩展（EXTEND）：给关系加一个属性

```
-- ⚠️ 示意
EXTEND S : { ANNO := 2026 - TUPLE_DATE_YR(S.INITDATE) }
```

要点：

- EXTEND 增加**度**（属性数 +1），基数不变；新属性的值必须是**标量**且**类型明确**；
- 结果仍是关系，可以继续参与任何算子（闭包）；
- 它的价值在于"派生属性只算一次、并立即变成一个可查询的列"，而不是靠视图或应用代码缓存。

SQL 里最接近的是 SELECT 列表里的表达式：`SELECT S.*, (2026 - y) AS ANNO FROM S`。差别是**它处于查询的末尾**（第 11 章的求值顺序）：WHERE/GROUP BY/HAVING 里想用 `ANNO` 必须重写表达式，或者嵌套一层派生表。这正是 EXTEND 作为"算子"而非"语法位置"的意义。

🔧 反面样本（D10c，SQLite 的 GROUP BY 裸列扩展）：

```sql
SELECT SN, PN, COUNT(*) AS n FROM SP GROUP BY SN;
-- -> [('S1','P1',2), ('S2','P2',1), ('S4','P1',3)]
```

`PN` 既不在分组里也没被聚集：SQLite 取分组内**任意**一个元组的值。模型里没有这种"未定义"的元组成分——这是"SQL 的行不是元组"的直接后果（同一现象在标准 SQL 里是语法错误）。

### 3. 映像关系：本章的概念核心

**映像（image）**：对关系 r 按属性集 X 分组后，与某一组值相对应的那个子关系（r 中被该组"筛出"的元组集合）。Tutorial D 在 SUMMARIZE 里用 `IMAGE (T)` 显式命名这个子关系：

```
-- ⚠️ 示意：按城市统计"每个城市的供应商数与状态总和"
SUMMARIZE S BY { CITY }
        ADD COUNT ( ALL ) AS CNT
        ADD SUM ( STATUS ) AS TOT
```

而"明确的分类汇总"（5.4.2）版本把聚集写成对映像的应用：

```
SUMMARIZE S BY { CITY } ADD ( COUNT ( IMAGE ( ALL ) ) AS CNT )
```

为什么这重要：它说明 **GROUP BY 不是"一行行累加"，而是"把关系切成子关系、对每个子关系求值一个函数"**。这个视角立刻解释了 SQL 里几个老大难：

| SQL 现象 | 映像视角的解释 |
| --- | --- |
| `AVG` 之后不能再 `AVG` | 聚集是"子关系→标量"的函数，不满足可组合性；需要保留子关系（映像）才能二次聚集 |
| 组内"任取一行"类需求（first/last） | 需要一个作用在映像上的自定义聚集，SQL 没有这个抽象 ⚠️ 转述 |
| 空输入时 `MIN(空)` 无定义 | 函数定义域问题：Tutorial D 要求聚集声明**初值/类型下限**（第 7 章类型系统） |

🔧 空聚集的直接后果（本目录自测，SQLite）：`SELECT MIN(QTY) FROM SP WHERE 0;` 返回 `NULL` 而不是"该表达式无定义"——把"类型上不可能有值"的情形伪装成了"缺失值"。这与第 6 章 NULL 批评连成一条线。⚠️ 该行是 🔧 方法的延伸，脚本中同类断言在 D8 系列。

### 4. 广义约束（5.4.3）：用聚集写业务断言

把聚集和 `IS_EMPTY`/比较组合，就能表达无法用 CHECK 写的规则：

```
-- ⚠️ 示意："任何城市的供应商平均状态不得超过 30"
CONSTRAINT city_avg_status :
  ( SUMMARIZE S BY { CITY } ADD ( AVG ( STATUS ) AS A ) WHERE A > 30 ) IS_EMPTY ;
```

作者在此的落点是：**约束语言必须和查询语言同样强大**，否则规则只能退回应用代码（回到第 1 章的"程序系统"）。这一小节直接为第 6 章的"断言"与第 13 章"SQL 的 CHECK 不能带子查询"（⚠️ 转述）铺路。

## 常见误区

| 误区 | 纠正 |
| --- | --- |
| 「EXISTS 就是半联接」 | 语义等价，层次不同：EXISTS 是谓词（只能进 WHERE），MATCHING 是算子（可继续参与关系运算） |
| 「SELECT 里加表达式列就是 EXTEND」 | 表达式列在求值顺序末尾，不能用于 WHERE/GROUP BY；EXTEND 的结果属性是一等属性 |
| 「GROUP BY 是把行'累加'成一行」 | 是把关系切成子关系、对每个子关系求函数值；不理解这点就理解不了 NULL 与空组行为 |
| 「聚集函数返回 NULL 表示 0」 | 空输入的 `MIN/MAX` 无数学定义；SQL 用 NULL 掩盖它，业务代码再靠 COALESCE 补——两处补丁 |
| 「约束只需要 CHECK」 | 跨元组/跨关系的规则需要聚集与 `IS_EMPTY`（5.4.3 → 第 6 章断言） |

## 核心概念速览（中英对照）

- **匹配 / 半联接** — matching (semijoin)：返回左关系中能与右关系匹配的子集，头不变
- **非匹配 / 反半联接** — not matching (antisemijoin)：返回不能匹配的子集；`BY {属性}` 指定匹配依据
- **扩展** — EXTEND：为每个元组增加一个标量计算属性，度 +1
- **映像关系** — image relation：分组后与该组对应的子关系，聚集真正的操作对象
- **分类汇总** — SUMMARIZE：按若干属性分组并对每个映像求聚集，SQL 的 GROUP BY 原型
- **聚集算子** — aggregate operator：关系 → 标量的函数（COUNT/SUM/AVG/MIN/MAX/…）
- **广义约束** — generalized constraint：用聚集 + 关系比较表达的业务级断言
- **初值 / 空组定义域** — identity value / domain of aggregation：空输入下聚集是否有值的问题
- **表达式末尾问题** — select-list positioning：SQL 的 SELECT 列表在 WHERE 之后求值，派生列不可复用
- **闭包** — closure：新算子仍须"关系进关系出"，否则语言退化
- **裸列（bare column）** — bare column in GROUP BY：SQLite 允许的非分组列，取值不定 🔧

## 最新演进与工业实践

- **工业界确实把这两个算子补上了（🔧/文档口径）**：DuckDB 提供语法级 `ANTI JOIN` / `SEMI JOIN`（正是 5.1 的 MATCHING/NOT MATCHING），PostgreSQL 提供 `LATERAL` 与聚合 `FILTER`，SQL 标准（SQL:2003 起）有 `GROUP BY ... HAVING` 之外的 grouping sets。参考：https://duckdb.org/docs/sql/query_syntax/select ✅（可达性已验证）。**但"映像关系"这个抽象仍然没有产品实现**——SQL/PostgreSQL 至今没有把"子关系"作为可传递值的东西。
- **关系值聚合的现实需求在增长**：数组/JSON 聚合（`array_agg`、`json_group_array`、DuckDB `list()`/`struct_pack()`）本质上就是"把映像关系塞进一个属性"，即第 7 章 RVA 讨论的前置。SQLite 侧文档：https://www.sqlite.org/json1.html ✅。🔧 本目录 D10d 演示了用 `json_each` 把 JSON 数组炸回关系（形式上是 RVA + UNPACK 的合体）。
- **`FILTER` / `WITHIN GROUP` 的现代写法**（🔧 自拟示意，非书中原文）：条件聚集在 2020 年代已被普遍支持，它比 SQL 老式的 `SUM(CASE WHEN ...)` 更接近"对子关系求聚集"的语义：

```sql
-- 🔧 可跑：按城市统计"状态>20 的供应商数"
SELECT CITY,
       COUNT(*) FILTER (WHERE STATUS > 20) AS n_high
FROM (VALUES ('Paris',20),('Paris',30),('Rome',10)) AS t(CITY,STATUS)
GROUP BY CITY;
```

（⚠️ 注：`FILTER` 在 SQLite 3.30+ / PostgreSQL / DuckDB 支持；MySQL 8.0 不支持——属产品差异，本目录未逐一实测。）
- **理论侧**：映像关系与"第一范式 vs 允许关系值属性"的争论在 Date & Darwen 的《The Third Manifesto》体系里被推到"关系值属性合法"的立场；本目录把这层留给第 7 章与附录 B 讨论。
