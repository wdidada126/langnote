# 第 6 章　约束和断言（Constraints and Assertions ⚠️ 回译）

> 译本 p77–87｜小节（✅ 实抓）：6.1 数据库约束 / 6.2 关系变量断言 / 6.3 断言与约束 / 6.4 练习 / 6.5 答案。
> 本章是全书"声明式"立场的正面陈述：**约束 = 谓词，数据库 = 关系变量 + 必须为真的谓词**。第 5 章的广义约束在这里升格为一级概念。

## 本章地图

| 小节 | 内容 | 结论 |
| --- | --- | --- |
| 6.1 数据库约束 | 约束的分类：域/类型约束、码约束、外码（包含依赖）、元组级 CHECK、跨关系断言、数据库级（状态转移）约束 | 约束限制的是**合法状态集合**，不是"操作" |
| 6.2 关系变量断言 | relvar assertion：该 relvar 的每个取值都必须满足的谓词；每次赋值后重新求值 | 断言是"关系值上的谓词"，因此可以用整个关系代数语言表达 |
| 6.3 断言与约束 | 术语辨析：assertion 与 constraint 语义同一，"约束"更贴切；并讨论时机（即时 vs 延迟） | 叫法不重要，能不能**声明 + 被强制**才重要 |
| 6.4 / 6.5 练习与答案 | 判断给定规则属于哪一类约束、能否声明 | 大部分真实业务规则是跨关系的 ⇒ 产品最缺那一类 |

## 核心精讲

### 1. 约束的分类（作者的层次，⚠️ 依小节结构与一贯立场重构）

| 层次 | 约束形态 | 表达 | 强制时机 |
| --- | --- | --- | --- |
| 类型/域 | 值必须属于某域（类型 + 可选谓词） | 类型系统 + `DOMAIN`（SQL 有标准、产品残缺） | 每次值产生 |
| 单关系·结构 | 码（唯一性 + 极小性） | `KEY { ... }` / `PRIMARY KEY` / `UNIQUE` | 每次赋值后 |
| 单关系·内容 | 元组级谓词 | `CHECK (谓词)`（只允许引用当前元组） | 每次插入/更新 |
| 跨关系 | 包含依赖（外码）/ 任意跨关系谓词 | 外码声明 / **断言** | 每次受影响赋值后 |
| 状态转移 | "只能减少不能增加"这类跨时刻规则 | 需要时序/触发逻辑，模型层面可写成对**前后两状态**的谓词 | 事务边界 |

作者把重点放在"跨关系"这一档：真实业务规则绝大多数落在这里（"任何城市的平均状态 ≤ 30"、"已发货量不得超过库存"），而 SQL 的产品实现恰恰只有头三档。

### 2. 断言就是"必须为真的命题"

一个断言（assertion）在形式上是**闭谓词**（无自由变量的命题），其真值由数据库状态决定：

```
-- ⚠️ Tutorial D 示意：断言 = 谓词 + 必须为真
ASSERT no_orphan_shipment :
    ( SP PROJECTION { SNO } MINUS S PROJECTION { SNO } ) = TABLE_DUM ;
```

要点：

- 断言用**关系表达式**写，因此表达力等于查询语言（第 4/5 章的算子全都可用）；
- 断言的求值单位是**整个关系**，不是单个元组 —— 这就是它比 CHECK 强的地方；
- 断言与"约束"是同义词（6.3 的结论）：作者的立场是 *constraint* 更贴切，因为它是"对状态的限制"而不是"对某个变量的属性声明"。
- `TABLE_DUM`/`TABLE_DEE` 在这里第一次派上用场：把布尔值翻译成零度关系，从而让"断言"也能写成关系等式（详见附录 B）。

### 3. 🔧 实测：产品实现的表达力边界（SQLite 3.45.3）

**① 断言不存在**

```sql
CREATE ASSERTION two_per_city CHECK
  (0 = (SELECT COUNT(*) FROM (SELECT CITY FROM T_city GROUP BY CITY HAVING COUNT(*) > 2)));
-- !! OperationalError: near "ASSERTION": syntax error
```

**② CHECK 里禁止子查询**（因此"跨关系"这一档连语法入口都没有）

```sql
CREATE TABLE T_chk (SN TEXT PRIMARY KEY
                    CHECK (EXISTS (SELECT 1 FROM S WHERE S.SN = T_chk.SN)));
-- !! OperationalError: subqueries prohibited in CHECK constraints
```

**③ 唯一性只能覆盖单表**

```sql
CREATE TABLE T_city (SN TEXT, CITY TEXT, UNIQUE (SN, CITY));   -- 被接受
-- 但"每个城市最多 2 个供应商"无法用任何 CREATE TABLE 子句表达（②已封死）
```

**④ 跨关系规则退化为触发器（过程式）**

```sql
CREATE TRIGGER s_city_required AFTER INSERT ON S WHEN NEW.CITY IS NULL
BEGIN SELECT RAISE(ABORT, 'city required'); END;
INSERT INTO S VALUES ('S5', 10, NULL);
-- !! IntegrityError: city required
```

**⑤ 延迟检查（DEFERRED）SQLite 真支持**，与"断言在事务边界求值"的语义吻合：

```sql
PRAGMA foreign_keys = ON;
CREATE TABLE SP (SN TEXT REFERENCES S(SN) DEFERRABLE INITIALLY DEFERRED, PN TEXT);
BEGIN;  INSERT INTO SP VALUES ('SX','P1');   -- 无报错
COMMIT;                                     -- !! IntegrityError: FOREIGN KEY constraint failed
-- 事务整体回滚，SELECT * FROM SP -> []
```

这五条合起来正好是本章论点的实验版：**声明式约束的能力 = 语言能写多少谓词 + 实现强制多少**。SQLite 有断言缺失（①②），但有延迟检查（⑤）；标准 SQL 里 `CREATE ASSERTION` 是有的（⚠️ 转述：SQL:1999 引入 ASSERTION，多数产品未实现），"标准有、产品无"是这一章最实用的记忆点。

### 4. 即时 vs 延迟（6.3 的时机问题）

| 检查时机 | 语义 | 适用 |
| --- | --- | --- |
| 语句级（immediate） | 每条语句结束时断言必须为真 | 码、外码、CHECK；简单，但把"两个 relvar 必须同时改"的业务规则变成不可能 |
| 事务级（deferred） | 事务提交时断言必须为真 | 跨关系断言（先删父再插子的批量导入） |

作者的论点 ⚠️ 重构：延迟检查不是性能妥协，而是**语义必需**——因为断言是对"状态"的谓词，而合法的业务变更经常穿过非法的中间状态。SQL 只在少数字段上支持（约束的 DEFERRABLE 子句），断言层则整体缺失。🔧 ⑤ 说明 SQLite 在外码上把这件事做对了。

## 常见误区

| 误区 | 纠正 |
| --- | --- |
| 「约束就是 CHECK」 | CHECK 只是元组级；码/外码/断言是三档不同的表达力（🔧 ①②③） |
| 「跨表规则用触发器一样能达到目的」 | 触发器是过程式补丁：不声明"什么必须为真"，只写"何时报错"；多入口/延迟/批量场景易漏 |
| 「约束影响性能，应该放到应用层」 | 约束检查是 O(声明)，应用校验是 O(入口数 × 版本数)；见第 3 章 3.6 同一条论证 |
| 「断言和约束是两个概念」 | 6.3：同一件事的两种叫法，作者偏好"约束" |
| 「所有约束都必须即时检查」 | 跨关系规则常需要事务级检查（🔧 ⑤） |
| 「NULL 参与约束没关系」 | 3VL 下"谓词为 UNKNOWN"在 CHECK 里等于通过、在 WHERE 里等于不通过（两种相反的默认值！）→ 第 13 章、[../SQL_and_Relational_Theory/06-NULL与三值逻辑3VL.md](../SQL_and_Relational_Theory/06-NULL与三值逻辑3VL.md) |

## 核心概念速览（中英对照）

- **约束** — constraint：对数据库合法状态集合的限制，模型的定义性成分
- **断言** — assertion：一个必须为真的（闭）谓词；与"约束"同义，作者偏好后者
- **域约束** — domain constraint：值必须属于某类型（可加谓词 refinement）
- **码约束** — key constraint：唯一性 + 极小性，声明在关系类型上
- **元组级 CHECK** — tuple-level check：只引用当前元组的谓词
- **跨关系约束** — general/cross-relational constraint：可用完整关系代数表达的谓词
- **状态转移约束** — state transition constraint：约束前后两个状态的关系（"只能减不能增"）
- **即时检查 / 延迟检查** — immediate / deferred check：语句级 vs 事务级求值时机
- **`CREATE ASSERTION`** — assertion DDL：标准 SQL:1999 有、多数产品未实现（🔧 SQLite 直接语法错误）
- **触发器** — trigger：过程式的"约束替身"，是能力缺失的症状而非替代方案
- **TABLE_DUM / TABLE_DEE** — 零度关系：把布尔真值表达成关系等式的装置（附录 B）
- **表达力 = 查询语言强度** — expressive parity：约束语言不应弱于查询语言

## 最新演进与工业实践

- **产品支持矩阵（⚠️ 转述 + 本目录 🔧）**：截至 2024–2026，主流开源/商用引擎里**没有一家实现 `CREATE ASSERTION`**。可行的近似方案：(a) 用物化视图 + 约束（PG 的可更新视图与 `WITH CHECK OPTION`）；(b) 用排他约束（PG 的 `EXCLUDE USING gist`，本直 🔧 显示 SQLite 无此语法）；(c) 用触发器 + 事务后检查（🔧 ⑤ 的 deferred FK 可以承担一部分）；(d) 把断言搬到测试层（数据契约/CDC 校验）。PostgreSQL 约束文档：https://www.postgresql.org/docs/current/ddl-constraints.html ✅
- **SQLite 侧文档口径**（与本直 🔧 一致）：`CHECK` 中禁止子查询、`FOREIGN KEY ... DEFERRABLE` 被解析（延迟语义可用）、无断言——见 https://www.sqlite.org/foreignkeys.html ✅ 与 https://www.sqlite.org/lang_createtrigger.html ✅。
- **约束下推到分析引擎**（🔧 方向性事实）：DuckDB 支持 `PRIMARY KEY`/`FK`/`UNIQUE` 的**声明**（用于优化与批量导入的冲突处理，`INSERT OR IGNORE/REPLACE`），但产品定位使它不追求强约束语义；⚠️ 未在本目录实测。这类"约束主要服务于 ETL 幂等"的取向，与本书"约束是模型的骨架"是两种世界观，适合对照阅读同波 [#134 `DuckDB_Up_and_Running`](../DuckDB_Up_and_Running/00-总览与阅读地图.md)（已落盘，波尾闭环）。
- **数据契约 / 断言外移的工业趋势**：把跨表业务规则写成断言并在管道里批量执行（Great Expectations / Soda / dbt tests 一类工具，⚠️ 仅生态说明）是 2023–2026 的主流做法。它与本章的关系是：**DBMS 没做的断言层，被数据平台用批处理补了一遍**——但检查发生在写入之后，正是作者批评的"程序系统"回潮。
- **深浅分工**：本章只界定"约束有哪些档、产品缺哪档"；**如何从业务命题推出约束集合**是设计方法论，见 [#8](../Database_Design_and_Relational_Theory/00-总览与阅读地图.md)；**约束在真实 MySQL/Oracle 里的强制细节与性能**见 [../mysql/09-表级别的操作.md](../mysql/09-表级别的操作.md) 与 [#23](../Cost_Based_Oracle_Fundamentals/00-总览与阅读地图.md)。
