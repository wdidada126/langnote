## 核心精讲

### 1. 码：两个条件，缺一不可

设 K 是关系变量 R 的属性子集：

- **唯一性（uniqueness）**：R 的任一合法取值中，不存在两个元组在 K 上相等；
- **极小性（irreducibility）**：K 的任何真子集都不再满足唯一性。

两者同时成立 ⇒ K 是**候选码（candidate key）**。只满足唯一性 ⇒ **超码（superkey）**。
⚠️ 示意的 Tutorial D：

```
VAR S RELATION { SNO SNO , SNAME NAME , STATUS INTEGER , CITY CITY }
    KEY { SNO } ;

VAR SP RELATION { SNO SNO , PNO PNO , QTY QTY }
    KEY { SNO , PNO } ;
```

三个常被混掉的点：

1. **候选码可以有很多个**。作者的一贯立场：所谓"主码"只是从候选码里挑一个用来被引用（并被赋予更好的名字），其他叫"备用码（alternate key）"；**数据库的语义不因为挑了谁而改变**。
2. 码是**谓词**层面的事实：它表达的是"供应商号唯一确定一个供应商"这类业务命题，而不是"建索引快"。
3. 空关系也有码（唯一性在零元组上真空成立）——所以码是**类型/声明**层面的性质，不是当前数据的统计性质。

### 2. 外码就是包含依赖

外码定义（FK in R referencing R2's candidate key K2）：任何时刻，R 中出现的 K(FK) 值必须能在 R2 的 K2 上找到匹配，**或整体为空**（后者是第 6 章 NULL 问题的入口）。用集合语言写就是包含依赖（inclusion dependency）：

```
SP PROJECTION { SNO }  ⊆  S PROJECTION { SNO }        -- ⚠️ 示意
```

这个写法买到三件事：

- 参照完整性与"码"是同一层的东西（都是可声明的断言），不是运维手段；
- 删除/更新被引用元组时的约束检查，语义上等价于"赋值后重估断言"；
- 它给出了第 4 章"再论交运算/联接"的自然语言对照：`⊆` 就是"限定为可匹配的"。

### 3. 🔧 实测：SQL 实现里"码"的三处降级（SQLite 3.45.3，🔧 方法见 00）

**① 声明了候选码，引擎仍另发一个身份（D3）**

```sql
CREATE TABLE S (SN TEXT NOT NULL UNIQUE, STATUS INTEGER, CITY TEXT);
INSERT INTO S VALUES ('S1',20,'Paris'),('S2',10,'Rome'),('S3',40,'Athens');
SELECT rowid, * FROM S;
-- -> [(1,'S1',20,'Paris'), (2,'S2',10,'Rome'), (3,'S3',40,'Athens')]
```

**② 系统眼里没有"候选码"，只有主键 + 唯一索引（D3b）**

```sql
SELECT * FROM pragma_index_list('S');
-- -> [(0, 'sqlite_autoindex_S_1', 1, 'u', 0)]
```

`UNIQUE` 约束被实现成一条自动唯一索引，与用户索引同层；引擎不区分"这是码"与"这只是个唯一索引"，因此**优化器/统计/外键检查都不把"候选码的可替换性"当回事**，外键只能指向被叫作 PRIMARY KEY/带唯一索引的列。

**③ 不声明码也照样能用（D7f）**

```sql
CREATE TABLE no_key (A INTEGER, B INTEGER);
INSERT INTO no_key VALUES (1,1),(1,1);
SELECT COUNT(*) FROM no_key;   -- -> [(2,)]
```

模型说"关系必有码"，产品说"随你"。

**④ 外键要逐连接打开开关（D7d / D7e）**

```sql
PRAGMA foreign_keys;            -- -> [(0,)]  默认关闭
PRAGMA foreign_keys = ON;
CREATE TABLE SP_fk (SN TEXT REFERENCES S(SN), PN TEXT, QTY INTEGER);
INSERT INTO SP_fk VALUES ('S9','P1',1);
-- !! IntegrityError: FOREIGN KEY constraint failed
INSERT INTO SP_fk VALUES ('S1','P1',1);   -- 合法，通过
```

同一份 DDL 在开关两侧行为不同——参照完整性依赖**会话状态**。这与 3.1 的立场（约束是数据库的属性）直接冲突。SQLite 官方文档口径一致：外键支持默认关闭以保持兼容（⚠️ 转述）：https://www.sqlite.org/foreignkeys.html ✅

### 4. 关系变量定义与"导入数据库"（3.4 / 3.5）

作者的编排值得注意：**先给声明语法，再给装载数据的语句**。这两节合起来说明"数据库定义（schema）"与"数据库状态（state）"的分离：

- 定义：头 + 类型 + 码（3.4）；
- 状态转移：一次一个关系值地赋值/装载（3.5）。

在 SQL 里对应 `CREATE TABLE` 与 `INSERT`，但差别在于：Tutorial D 的 `KEY` 是类型的一部分（声明即约束），而 SQL 的约束是 DDL 上的可选项、且实现常给默认关闭（见 🔧 ④）。

### 5. 数据库系统 vs 程序系统，第二次对照（3.6）

3.1 前作者已经用 1.4 做过一次对照，本章做的是**约束版**对照：

| 规则 | 数据库系统（声明式） | 程序系统（过程式） |
| --- | --- | --- |
| 供应商号唯一 | `KEY { SNO }` | 保存前查重 + 建唯一索引 + 报表假设 |
| 供应商必须存在 | `KEY`/外码声明 | 每个写入口各写一段校验 |
| 删除被引用供应商 | 参照完整性自动拒绝 | 每个删除路径各写一段级联 |

作者的结论口径（⚠️ 重构）：程序系统里**"没人写那段校验"是常态**，因为规则的表达次数随入口数量增长；数据库系统把它压成一次声明，代价是必须有一个**真正强制它**的 DBMS（→ 第 13 章"约束在 SQL 里能声明多少、真强制多少"）。

## 常见误区

| 误区 | 纠正 |
| --- | --- |
| 「主码是关系必需的，其他码无所谓」 | 候选码全部同等重要；主码只是引用时的选择（备用码仍要唯一强制） |
| 「有唯一索引就有码」 | 索引是物理结构，且可被绕过/不强制（🔧 ③）；码是语义声明 |
| 「外键影响性能，去掉它，用应用保证」 | 去掉的正是 3.6 那条"一次声明"；性能问题的正确解法是索引 + 约束下推，不是删语义 |
| 「极小性可有可无」 | 漏掉极小性把超码当码，会直接导致第 9 章无损分解判据用错 |
| 「FK 指向主键是定义」 | FK 指向的是**被引用的候选码**；主码只是最常见的那个候选码 |
| 「NULL 外键是合法例外」 | 模型层面这是"两类缺失值"问题（第 6 章）；SQL 的 MATCH FULL/SIMPLE/PARTIAL 正是对这个漏洞的补丁 ⚠️ 转述 |

## 核心概念速览（中英对照）

- **完整性约束** — integrity constraint：限制数据库合法状态取值的谓词，模型的定义性成分
- **候选码** — candidate key：满足唯一性与极小性的属性组
- **超码** — superkey：只满足唯一性的属性组
- **极小性** — irreducibility：去掉任一属性即不再唯一
- **主码 / 备用码** — primary key / alternate key：被挑出来用于引用的候选码 vs 其余候选码
- **外码** — foreign key：引用他关系候选码的属性组
- **参照完整性** — referential integrity：外码值必须匹配某被引用元组（或按规则为空）
- **包含依赖** — inclusion dependency：一个关系的某投影 ⊆ 另一关系的某投影，外码的集合论表达
- **关系变量定义** — relvar definition：头 + 类型 + 码的声明式定义
- **数据库定义 vs 数据库状态** — database definition vs database state：schema（不变）与某时刻取值（可变）的分离
- **NULL 外码** — null foreign key：使参照完整性语义复杂化的边界情形
- **声明式 vs 过程式** — declarative vs procedural：一次声明 vs 每个入口各写一段校验

## 最新演进与工业实践

- **2024–2026 产品现状（⚠️ 转述，非本机实测）**：PostgreSQL 支持 `DEFERRABLE INITIALLY DEFERRED` 约束、`MATCH FULL`、以及部分表达式索引式唯一约束；MySQL/InnoDB 自 8.0.16 起才真正强制 `CHECK` 约束（此前解析但忽略）；SQL Server 无 `CREATE ASSERTION`，用筛选唯一索引（filtered unique index）表达"部分唯一性"。三者都**没有把候选码当作一等信息**（外键仍只能指向 PK/唯一索引）。参考：PostgreSQL 约束文档 https://www.postgresql.org/docs/current/ddl-constraints.html ✅（可达性已验证）
- **SQLite 的官方口径与本直实测吻合**：`PRAGMA foreign_keys` 默认关闭、UNIQUE 由自动唯一索引实现、WITHOUT ROWID 表按主键组织——见 https://www.sqlite.org/foreignkeys.html ✅ 与 https://www.sqlite.org/withoutrowid.html ✅。工程建议（业界通行）：把 `PRAGMA foreign_keys=ON` 写进连接初始化代码，否则"有外键"是自欺。
- **约束即代码 / CI 化**：现代做法是把码声明与参照关系进版本库（dbmate/Flyway/Atlas 一类迁移工具）并用测试断言"违反约束的写入必须失败"——本直 🔧 ④ 的三条 `INSERT` 正好是一个可自动化的最小测试用例。⚠️ 工具名仅作生态说明，未逐一验证。
- **理论侧进展**：包含依赖/多值依赖作为"约束家族"的研究在 Date & Darwen《The Third Manifesto》第三版（Addison-Wesley, 2007）里体系化——本直第 1 章译本节选里作者自己把它列为"更易懂的替代表述"参考。⚠️ 仅引书目信息，不引结论细节。
