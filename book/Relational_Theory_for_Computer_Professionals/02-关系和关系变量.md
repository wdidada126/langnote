# 第 2 章　关系和关系变量（Relations and Relation Variables ⚠️ 回译）

> 译本 p17–25｜小节（✅ 实抓）：2.1 关系（2.1.1 属性、2.1.2 元组、2.1.3 关系的特点）/ 2.2 关系变量 / 2.3 练习 / 2.4 答案。
> 本章是全书的地基：**关系是值，关系变量是变量**。后面所有算子（第 4/5 章）、约束（第 6 章）、模型公设（第 7 章）都建立在这对概念上。

## 本章地图

| 小节 | 讲了什么 | 结论 |
| --- | --- | --- |
| 2.1 关系 | 关系 = 头（heading）+ 体（body）；体是元组的**集合** | 集合⇒无重复、无序，这两条是定义而非纪律 |
| 2.1.1 属性 | 属性 = 名字 + 类型（域）；头是属性的**集合** | 头无序 ⇒ 第 n 列这种说法在模型里没有意义 |
| 2.1.2 元组 | 元组 = 属性名到值的**有限映射** | 元组也没有"位置"；给元组编号是物理层的事 |
| 2.1.3 关系的特点 | 无重复元组、元组无序、属性无序、每单元一个值、同列同源 | 五条"特点"合起来就是 1NF 的真实含义 |
| 2.2 关系变量 | relvar 是取值为关系的变量；数据库由 relvar 构成 | 赋值语义是**整体替换**；INSERT/DELETE/UPDATE 只是派生写法 |

## 核心精讲

### 1. 关系的形式：头 + 体

⚠️ 示意（依作者一贯写法，非书中原文编号）：

```
-- Tutorial D ⚠️：一个三元关系值
RELATION { TUPLE { SNO 'S1' , STATUS 20 , CITY 'Paris' }
         , TUPLE { SNO 'S2' , STATUS 10 , CITY 'Rome'  } }
```

- **头（heading）**：属性集合，每个属性有名字和类型（在作者的另一套用语里也叫"域/domain"）。头决定了关系**类型**。
- **体（body）**：元组的集合。空体是合法关系（度可以 > 0，基数为 0）。
- **度（degree/arity）**= 属性个数；**基数（cardinality）**= 元组个数。

因为体是**集合**（不是多重集、不是序列），直接得到三条：不存在重复元组、元组之间无序、属性之间无序。作者在这章的重点不是"规定你不能这么做"，而是"这些概念在关系上根本不存在"——你说"第 3 行"就像问"集合里排第几"，问句本身不合法。

### 2. 元组是映射，不是行

元组 = 从属性名到值的有限映射（`TUPLE { SNO 'S1', STATUS 20 }`）。这个定义买到了两件事：

1. **按名字访问**：`S.STATUS` 与书写顺序无关；
2. **头不同时可比性明确**：两个元组只在头相同的前提下才谈"相等"，因此 `UNION` 要求同头是自然的（第 4 章）。

SQL 的对应物是"行"，但行有位置：列按 CREATE TABLE 的顺序编号，复合值可以按 `(a,b) < (c,d)` 逐列比较 ⚠️ 转述。位置在 SQL 里是可观察的，因此它是接口的一部分——这正是偏离的根源。

### 3. 🔧 实测：SQL 的"行"确实带位置与身份（SQLite 3.45.3）

方法与产物：`D:\develops\tmp\dbwave_rtcp\rg_sqlite_demo.py` / `demos.txt`（Python 内置 `sqlite3`，内存库，逐条执行打印）。

**D1 重复行 + rowid 补身份**

```sql
CREATE TABLE S_dup (SN TEXT, CITY TEXT);
INSERT INTO S_dup VALUES ('S1','Paris'),('S1','Paris'),('S2','Rome');
SELECT COUNT(*) FROM S_dup;
-- -> [(3,)]
SELECT rowid, * FROM S_dup;
-- -> [(1,'S1','Paris'), (2,'S1','Paris'), (3,'S2','Rome')]
SELECT DISTINCT * FROM S_dup;
-- -> [('S1','Paris'), ('S2','Rome')]
```

三条观察：① 表允许两个内容完全相同的行（关系里只有一个元组）；② SQLite 靠隐藏 `rowid` 让"相同"的行仍可指认——**物理位置被借用来伪造元组身份**；③ 想要关系语义必须自己写 `DISTINCT`。
补充实测：`WITHOUT ROWID` 表（D3c）里 `SELECT rowid` 直接报 `no such column: rowid`，说明"身份"完全是存储引擎给的礼物，不是模型的成分。

**D2 头是有顺序的（属性名不参与匹配）**

```sql
WITH A(x, y) AS (VALUES (1, 2)),
     B(y, x) AS (VALUES (3, 4))
SELECT * FROM A UNION ALL SELECT * FROM B;
-- -> [(1, 2), (3, 4)]
```

A 的 `x` 与 B 的 `y` 被并成同一列。**SQL 的 UNION 按列位置对齐，名字只是注释**。在关系模型里这两者头不同（`x`/`y` 互换即不同属性），表达式不合法；在 SQL 里它安静地返回错答案。这就是第 1 章"逻辑数据独立性"被破坏的机制：改列序 = 静默改变程序语义。

### 4. 关系变量：值 vs 变量的分工

- **关系值**不可变（像整数 42）；**关系变量（relvar）**才有状态，可以被赋值。
- 数据库 = 一组 relvar 在某一时刻的取值集合；**关系数据库的状态就是这些 relvar 的当前值**。
- 赋值是**替换语义**（replacement）：新值完整地取代旧值。`INSERT`/`DELETE`/`UPDATE` 是替换的缩写：

```
-- Tutorial D ⚠️ 示意
S := S UNION RELATION { TUPLE { SNO 'S4' , STATUS 20 , CITY 'Athens' } } ;   -- "INSERT"
S := S MINUS ( S WHERE SNO = 'S4' ) ;                                        -- "DELETE"
```

这个"其实只有赋值"的立场在第 7 章（7.5 关系赋值）被正式纳入模型公设，在第 10 章用来对照 SQL 的逐行 DML。

### 5. 为什么说"表是 relvar 的坏近似"

| 模型概念 | SQL 对应 | 丢失的东西 |
| --- | --- | --- |
| 关系值 | 基本表 / 查询结果 | 集合语义（退化为袋） |
| relvar | 基本表 | 值/变量不分：表既是存储又是表达式 |
| 头（属性集合） | 列定义（有序） | 名字对齐、按位置可见 |
| 元组 | 行 | 映射性、按名相等 |
| 域/类型 | 列类型 | 约束（SQL 的类型很弱，见第 13 章 🔧） |

## 常见误区

| 误区 | 纠正 |
| --- | --- |
| 「加了 PRIMARY KEY 的表就是关系」 | 有了码仍不解决重复行（无主键列的查询结果照样有重复）与列序问题；见 🔧 D1 |
| 「SELECT DISTINCT 是性能选项」 | 在模型里 DISTINCT 是**默认且唯一**的行为；SQL 需要显式写才回到关系 |
| 「ORDER BY 用来给行编号是常规做法」 | 关系上没有序；给元组编号只能显式造一个属性（EXTEND，见第 5 章） |
| 「表 = 关系」 | 表是**变量**兼**物理结构**；关系是**值**。二者的相等/包含概念都不同 |
| 「视图就是虚拟表」 | 视图是**命名的关系表达式**（第 7 章 7.6.2），它的可更新性取决于表达式是否可逆 |

## 核心概念速览（中英对照）

- **关系** — relation：由头（属性集）与体（元组集）构成的值；数学上是属性到值的映射的集合
- **头** — heading：属性的集合，每项含名字 + 类型；决定关系类型
- **体** — body：元组的集合；集合⇒无重复、无序
- **元组** — tuple：属性名→值的有限映射，关系中的一个"元素"
- **属性** — attribute：有名字、有类型的列定义，不是"第几列"
- **度 / 目** — degree / arity：属性个数
- **基数** — cardinality：元组个数
- **关系类型** — relation type：由头决定的类型；`RELATION{...}` 是类型产生器（第 7 章）
- **关系变量** — relvar：取值范围为关系的变量，数据库状态的构成单位
- **替换语义** — replacement semantics：赋值用新关系整体取代旧关系
- **INSERT / DELETE 是派生操作符** — derived operators：可表示为 `r := r UNION x` / `r := r MINUS x`
- **袋 / 多重集** — bag / multiset：允许重复的集合，SQL 的默认语义
- **rowid** — rowid：SQLite 借给每一行的物理身份，模型里没有对应物 🔧

## 最新演进与工业实践

- **"关系 vs 表"的争论在 2024–2026 年的落点**：主流引擎仍统一在袋语义上（因为重复行的物化代价更低、流式写入更自然）；同时**在分析层往集合语义回摆**——`SELECT DISTINCT`、`GROUP BY` 全列、窗口函数 `ROW_NUMBER()` 造显式元组编号是常规做法。DuckDB 等分析引擎同样按袋处理，但向量化执行让"去重"代价显著下降，把"要正确就要 DISTINCT"的工程成本降到可接受：https://duckdb.org/docs/sql/query_syntax/select ✅（可达性已验证）
- **SQL/PGQ 与属性图（⚠️ 转述）**：ISO/IEC 9075-16（SQL:2023 的属性图查询）在关系表之上叠了图模式匹配，但**基表语义未变**，仍是袋。可对照 [../Graph_Databases_2e/00-总览与阅读地图.md](../Graph_Databases_2e/00-总览与阅读地图.md) 里"关系模型表达遍历的代价"一节。
- **SQLite 官方口径**（与 🔧 实测一致）：rowid 与 WITHOUT ROWID 表的行为在官方文档里定义：https://www.sqlite.org/withoutrowid.html ✅（可达性已验证）。文档明确 rowid 是"隐藏列"、WITHOUT ROWID 表按主键 B 树组织——**这就是"位置由实现提供"的标准说法**。
- **今天怎么写**：任何被当作"关系"使用的查询结果，应显式 `DISTINCT` 或由约束保证唯一，并**在接口边界把列名传给调用方**（`cursor.description` / 结果元数据），不要按位置取列。Python `sqlite3` 的 `description` 就是名字对齐的最低保障 🔧 实践建议。
