| 小节 | 内容 | 结论 |

## 核心精讲

### 1. 三层公设（7.1）

⚠️ 依作者一贯表述重构（与 Date & Darwen《The Third Manifesto》体系同源，但本书是精简版）：

| 层 | 公设内容 | 对应章节 |
| --- | --- | --- |
| **结构（Structure）** | 数据库全部由**关系**构成；关系是值；关系之间存在类型关系（头决定类型） | 第 2 章 |
| **完整性（Integrity）** | 关系必须有码；参照完整性可表达；一切约束以谓词声明、由 DBMS 强制 | 第 3、6 章 |
| **操作（Manipulation）** | 语言必须提供**关系级**读写：算子输入输出都是关系（闭包），更新以关系为单位（赋值） | 第 4、5 章 + 7.5/7.6 |

关键推论（本书最常被引用的一句式立场 ⚠️ 重构）：**"关系型"是对用户接口的断言，不是对内部存储的断言**。一个把数据存成关系、却给用户游标/行序/袋语义的引擎，按本模型不算关系型 DBMS。

### 2. 类型与关系类型产生器（7.2 / 7.3）

- **域 = 类型**：域有名字、有表示（内建或用户定义）、有可选的约束（谓词精化）。作者立场：类型系统必须**可扩展**，且"域"要能被命名并复用（→ 第 13 章 SQL `CREATE DOMAIN` 的支持情况）。
- **元组类型 / 关系类型是构造类型**：像数组/列表一样，`TUPLE {a: A, b: B}` 与 `RELATION {a: A, b: B}` 由更简单的类型**生成**。所以 7.3 的"关系类型产生器"说的是：模型里不存在"表结构只能写死在 DDL 里"这种限制——类型可以参数化生成。
- **类型安全（type safety）**：任何表达式在求值前必须类型可检查；违反就应在**定义时**拒绝，而不是运行时返回意外值。

🔧 反例（SQLite 3.45.3，域/类型形同虚设）：

```sql
CREATE TABLE T_typ (ST INTEGER);
INSERT INTO T_typ VALUES ('abc'), (3.14), (NULL);
SELECT ST, typeof(ST) FROM T_typ;
-- -> [('abc', 'text'), (3.14, 'real'), (None, 'null')]
```

SQLite 的声明类型只是 **affinity**（亲和性），不是类型约束——同一"域"里混住文本/实数/NULL。按 7.2 的公设，这个库连"结构层"都没满足，遑论完整性。⚠️ 注意：这是 SQLite 有意的设计（官方文档明言），不是 bug；工程上要么用 `CHECK` 补，要么接受"类型只是提示"。

**"允许关系值属性"的立场**（与第 5 章 EXTEND/映像连起来看）：作者允许**关系的属性其本身又是关系**（RVA），因为那仍然满足"值是类型化对象"这条公设；争议点只在 1NF 的定义版本。SQL 拒绝 RVA ⇒ 只能把子结构塞进字符串/JSON：

🔧 变通演示（D10d）：

```sql
CREATE TABLE S_json (SN TEXT, CITIES TEXT);
INSERT INTO S_json VALUES ('S7', '["Paris","Rome"]');
SELECT j.SN, c.value AS city FROM S_json AS j, json_each(j.CITIES) AS c;
-- -> [('S7','Paris'), ('S7','Rome')]
```

这个查询做的事，恰是 Tutorial D 里 `UNPACK CITIES ON C`（把 RVA 展开成普通关系）的镜像。对照 [../SQL_and_Relational_Theory/11-关系值属性与嵌套结构.md](../SQL_and_Relational_Theory/11-关系值属性与嵌套结构.md)（那本用 PACK/UNPACK 讲同一件事）。

### 3. 关系变量与赋值（7.4 / 7.5）

公设化的三条：

1. relvar 有**类型**（头），其当前值必须是该类型的关系；
2. 更新 = **赋值**（`S := <关系表达式>`），语义是整体替换；
3. `INSERT`/`DELETE`/`UPDATE` 是可派生的缩写（第 4 章 4.12 已给定义），且**必须与替换等价**——包括"中途不存在违反约束的状态"（→ 第 8 章原子性的模型依据）。

SQL 的差距 ⚠️ 转述：`UPDATE` 逐行执行、可被触发器逐行打断；`DELETE` 没有"替换语义"的等价性保证；关系值不能作为赋值的整体（没有 `T := SELECT ...` 这种"把整张表换掉"的原生语句，只能 `TRUNCATE` + `INSERT` 且未必原子）。

### 4. 算子公设与安全性（7.6.1）

"安全性（safeness）"在本书语境里指：算子的结果**永远是一个合法关系**，且不依赖数据之外的东西：

- 类型安全：算子的结果类型由输入类型静态决定；
- 范围安全：投影/限定不会产生不属于任何域的值；
- 无副作用：算子不修改 relvar（只有赋值改），这保证**表达式的可组合性与可推理性**；
- 有限性：所有关系都是有限集，所以 `MINUS`/`×` 结果总是良定义。

对照附录 D 的关系演算：演算的表达式必须加"安全"限制（否则 {t | NOT (t ∈ r)} 在无限域上不可计算），本书的算子公设是它的代数版本。

### 5. 视图（7.6.2）

作者的立场：视图 = **命名的关系表达式**（不是"虚拟表"）。由此：

- 视图的可更新性等价于"表达式是否可逆"：`π` 丢属性后无法唯一还原 ⇒ 不可更新（除非有额外的 INSTEAD OF 规则）；
- 视图必须继承完整性：一个可更新视图上的写入仍受基表断言约束；
- SQL 的实现细节（`WITH CHECK OPTION`、INSTEAD OF 触发器）是对"可逆性判断不出来"的补救。⚠️ 转述。

### 6. 结论（7.7）：判据的用法

把 7.1–7.6 当 checklist 用，就能对任意产品打分：

```
结构：接口是否给出无重复、无序的关系值？            → 第 2 章 + 🔧 D1/D2
完整性：码是否是一等信息？断言能否声明？             → 第 3、6 章 + 🔧 D3b/①②
类型：域能否命名并被强制？                          → 🔧 D7b（typeof 混住）
操作：更新是否以关系为单位？算子是否闭包 + 类型安全？  → 第 4、5 章 + 🔧 D10c
```

四行里 SQL 产品通常只有"操作/闭包"一行大致及格。这就是本书第 14 章"偏离总清单"的理论依据。

## 常见误区

| 误区 | 纠正 |
| --- | --- |
| 「关系模型 = 二维表」 | 表是展示层概念；模型说的是**类型化的关系值 + 约束 + 关系级算子**三层公设 |
| 「类型只是实现细节」 | 7.2 把类型列为公设层；域不被强制则完整性无从谈起（🔧 typeof 混住） |
| 「RVA 违反 1NF 所以模型禁止」 | 作者的立场是 RVA 合法（值仍是类型化对象）；被禁的是 SQL 的实现，不是模型 |
| 「UPDATE 就是 UPDATE」 | 模型里它必须与"整体替换"等价；产品逐行实现 ⇒ 中途状态可能违法 |
| 「视图就是虚拟表」 | 视图是命名表达式；可更新性取决于可逆性（7.6.2） |
| 「安全性 = 权限控制」 | 7.6.1 的 safeness 是"表达式良定义/类型安全/无副作用"，与 GRANT 无关 |

## 核心概念速览（中英对照）

- **关系模型** — relational model：结构 + 完整性 + 操作三层公设的总和，而非"用表存数据"
- **结构层公设** — structural part：数据库全由关系（值）构成，头决定类型
- **完整性层公设** — integrity part：码必备、约束以谓词声明并由 DBMS 强制
- **操作层公设** — manipulation part：算子闭包（关系进关系出）、更新以关系为单位
- **域 / 类型** — domain / type：命名、可扩展、被强制的值集合（可含精化谓词）
- **类型产生器** — type generator：由简单类型构造复合类型的机制；`RELATION{...}` 是关系类型产生器
- **关系类型** — relation type：由头（属性名 + 类型，无序）决定
- **类型安全** — type safety：表达式在求值前可静态检查，违反应在定义时拒绝
- **关系赋值** — relation assignment：`r := <expr>`，整体替换语义；DML 是其派生缩写
- **安全性（算子）** — safeness：结果永远是良定义的合法关系，无副作用
- **视图** — view：命名的关系表达式；可更新性取决于可逆性
- **RVA（关系值属性）** — relation-valued attribute：属性值本身是关系；作者允许，SQL 拒绝
- **接口判据** — interface criterion：判断"关系型"的唯一标准在用户接口，不在存储

## 最新演进与工业实践

- **类型层：SQL 标准在补、产品各补一半（⚠️ 转述）**：PostgreSQL 有 `CREATE DOMAIN`（含 CHECK 精化）、枚举类型、数组/复合类型——最接近 7.2/7.3 的可扩展类型系统；MySQL 有 `ENUM`/`SET` 但 `DOMAIN` 不实现；SQLite 官方立场是 affinity（🔧 已实测）。文档：https://www.postgresql.org/docs/current/ddl-constraints.html ✅
- **半结构化数据把 RVA 争论重新摆上台面**：SQL:2016 的 JSON 能力、SQL:2023 的 JSON 表函数/构造函数，以及各引擎的 `ARRAY`/`STRUCT`/`MAP` 类型（DuckDB、BigQuery、ClickHouse），事实上允许"一格里放一张表"。这与 7.2/RVA 的关系是：**工业界选择了模型允许的那条路，但绕过了类型层**（JSON 列的值在数据库内无类型）。🔧 本目录 D10d 演示 SQLite 的 `json_each` 展开。PostgreSQL：https://www.postgresql.org/docs/current/functions-json.html ✅；DuckDB：https://duckdb.org/docs/sql/query_syntax/select ✅
- **"接口是否关系型"的当代案例**：DataFrame API（pandas/Polars/Spark）把"袋 + 有序列 + NaN 语义"作为用户接口的主流形态，与本书判据高度不相容；但**表达式层的闭包性**（`filter/withColumn/groupBy` 输入输出都是 DataFrame）正是 7.6 公设的现代复刻——用代数视角看，DataFrame 是"关系语义 + 袋实现"的混合体。⚠️ 转述，未实测性能。
- **可核实的社区实现**：Tutorial D 风格的库（关系值可比较、类型化）例：https://github.com/moerkb/core.relational ✅（Clojure，2014 停更，仅作语言形态证据）。
