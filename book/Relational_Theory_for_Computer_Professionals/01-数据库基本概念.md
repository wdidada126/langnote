## 核心精讲

### 1. 定义的重量：数据库、DBMS、关系型 DBMS

作者的做法是先给最朴素的定义，再逐层加约束：

- **数据库**：一组逻辑相关的数据，外加对这些数据的描述（后者即目录/元数据）。关键在"逻辑相关"——一堆彼此无关的文件不构成数据库。
- **DBMS**：让用户**定义、创建、维护、按需访问**数据库的软件。它管理目录、提供数据独立性、负责并发/恢复/完整性/安全。
- **关系型 DBMS**：公开节选里作者的原话口径是——「关系型数据库管理系统是支持**真正实现关系模型的用户接口**的 DBMS」，并且要满足两点：它首先是个 DBMS（提供 DBMS 的全部功能），其次它的**用户接口在实现时必须是关系模型** ⚠️（节选转述）。

这条判据的直接推论是本书后面所有内容的存在理由：市面上多数"关系型"产品只在**存储层**像关系型，在**接口层**不是——接口层泄漏了行序、重复行、NULL 与逐行游标。作者给的检验办法不是看营销词，而是看接口是否满足：

1. 数据在用户看来是关系（无重复元组、元组无序、属性无序）；
2. 检索与修改可以**以关系为操作对象**（关系级操作，而非逐行）；
3. 完整性约束声明在数据库里，而不是散在应用代码里。

⚠️ 关键立场：作者明言本书「在根本不使用 SQL 的情况下解释关系模型」，替代语言是他自造的 **Tutorial D**，并称其为「可以自我说明的语言」；他对 SQL 的评价是复杂、不完整、难掌握、且在很多方面容易造成误导 ⚠️（节选转述）。这是第 10–14 章才回头拿 SQL 作对照的原因。

### 2. 数据依赖与数据独立性（1.2.1）

"数据依赖"这节讨论的是**谁依赖谁**：应用代码不该依赖存储结构。两层独立性：

| 独立性 | 含义 | 破坏它的常见做法 |
| --- | --- | --- |
| 物理数据独立性 | 换存储结构（索引、分区、B 树→哈希）不改程序 | 程序假设"表按主键物理有序" |
| 逻辑数据独立性 | 逻辑结构变（拆表、加列）不改既有程序 | 程序 `SELECT *` 后按**列位置**取字段 |

第二行的破坏方式，第 2 章的 🔧 实测会给出真凭实据：SQL 的 `UNION` 按列位置对齐，属性名根本不参与匹配——列序一变，程序静默出错。

### 3. 数据库系统 vs 程序系统（1.4）

这是本章最有辨识度的一节，也是 Date 反复使用的论证模板：

- **程序系统**：规则写在应用代码里。例：「供应商号决定状态」这条事实，写成一段 Java 校验 + 一处唯一索引 + 一处报表里的假设。三处各自演化，迟早不一致。
- **数据库系统**：规则写成数据库里的**断言/约束**，由 DBMS 在每次状态变更时强制。
- 判据：**同一份"关系"（业务事实的结构）被表达了几次？** 表达一次（在数据库里）是数据库系统；表达 N 次（在每个用到它的程序里）是程序系统。

第 3 章（码与外码）、第 6 章（约束与断言）、第 10 章（SQL 系统与程序系统）都是这条论证的具体化——作者在第 3 章和第 10 章各放了一次"对比"小节（3.6、10.7），说明他把它当成贯穿全书的主轴。

### 4. 为什么第一章要谈"DBMS 的其他功能"

作者的诚实之处：他把目录、统计、备份、性能监视列出来，然后**明确它们与关系模型无关**。这一点很重要——很多人把"有产品功能"当作"符合模型"的证据。本书的划分是：

```
关系模型（第 1–7 章）＝接口的规范
事务与恢复（第 8 章）＝状态变更的规范，模型只涉及其边界
SQL 产品现实（第 10–14 章）＝对规范的偏离清单
```

### 5. 把判据跑起来：三个可实测的提问（🔧）

1.3 的判据不是姿态，是可以对手边的产品做**三问**的（全部验证 SQL 行为，非 Tutorial D；Tutorial D 的完整语法形态见附录 A 笔记 [15-附录TutorialD dum与dee集合论与关系演算.md](15-附录TutorialD dum与dee集合论与关系演算.md)）：

| 提问 | 问法 | 关系型应答 | SQLite 3.45.3 实测 |
| --- | --- | --- | --- |
| 结果有身份吗 | `SELECT rowid, * FROM S;` | 元组无位置身份 | 否——rowid 暴露物理行号，内容相同的两行可区分（第 2 章 D1c） |
| 头参与匹配吗 | 列名同名异序的两表做 `UNION` | 按属性名配平，配不上就拒绝 | 否——按列位置静默对齐且"成功"（D2） |
| 规则在库内吗 | 声明"每城至多 2 个供应商" | 可用断言声明 | 否——CHECK 禁子查询、无 `CREATE ASSERTION`（第 6 章 ①②） |

三问全"否"即可按本书判据判定该接口**不关系型**。注意这个判定与产品质量、性能、流行度全部无关——它是语义维度的坐标声明，也正是本章把"关系型 DBMS"定义成接口判据而非营销词的用意。

## 常见误区

| 误区 | 纠正 |
| --- | --- |
| 「用了 SQL 就是关系型」 | SQL 本身对模型的偏离（重复行/NULL/列序）使它只在**不偏离**的那部分才关系型；见第 14 章 |
| 「有表就是关系型」 | 表是物理/展示概念；关系是值概念。判据是用户接口是否以关系为操作单位 |
| 「DBMS 功能越全越关系型」 | 功能与模型正交；功能很强的产品可以接口完全不关系 |
| 「数据独立性是 ORM 解决的问题」 | ORM 只是把依赖搬到了映射层；独立性来自数据库侧的显式关系与视图机制 |
| 「业务规则写在服务层更灵活」 | 规则一旦离开数据库就变成 N 份副本；第 6 章会说明声明式约束为何是更少的代码而不是更多 |
| 「有文件/KV 存储就算有数据库」 | 1.1 的定义要求**逻辑相关**且含目录：互不相关的一堆文件不是数据库，"自描述"正是它与文件系统的分界 |
| 「目录/数据字典是可选配件」 | 元数据是"数据库"定义的构成成分；没有受管理的目录，DBMS 的第一项功能就不成立 |

## 核心概念速览（中英对照）

- **数据库** — database：一组逻辑相关的数据及其描述（含元数据/目录）
- **数据库管理系统** — DBMS：让用户定义、创建、维护并按需访问数据库的软件层
- **关系型 DBMS** — relational DBMS：**用户接口真正实现关系模型**的 DBMS（唯一判据）
- **元数据 / 目录** — metadata / catalog：描述数据的数据，DBMS 必须管理它
- **物理数据独立性** — physical data independence：程序不依赖存储结构
- **逻辑数据独立性** — logical data independence：程序不依赖逻辑结构的每次变动
- **数据依赖** — data dependence：程序与数据结构之间的绑定关系，独立性即解除它
- **程序系统** — program-controlled system：业务规则散落在应用代码中，一份事实多处表达
- **数据库系统** — database system：业务规则以约束/断言显式存在于数据库中
- **Tutorial D** — Tutorial D：作者为讲模型而自造的教学语言，本书前两部分的正式载体
- **关系级操作** — relation-level operation：以整个关系为输入/输出的操作，区别于逐行游标
- **接口层偏离** — interface-level deviation：存储像关系但接口暴露行序/重复行/NULL 的现象

## 最新演进与工业实践

- **"关系型"判据在今天仍然有效**：2020 年代的"多模型数据库"（如把文档、图、关系放在一个引擎里的产品）在营销上不再自称"纯关系型"。判据反而更清晰：**看每种接口是否满足其模型的公设**。属性图/SQL/PGQ 混合查询的讨论见 [../Graph_Databases_2e/00-总览与阅读地图.md](../Graph_Databases_2e/00-总览与阅读地图.md)。
- **SQL 标准演进（⚠️ 转述，未逐条核到标准文本）**：ISO/IEC 9075 系列在 2016/2019/2023 几轮修订里补的是 JSON 能力（SQL:2023 的 JSON 表函数/构造函数）、属性图查询（SQL:2023 增补 PGQ）、以及若干对象关系特性；**本章关心的"接口是否关系型"三大痛点（重复行、NULL/3VL、列序）一条都没被修正**。标准原文可参公开镜像的 SQL-1992 文本（可达性已验证）：https://www.contrib.andrew.cmu.edu/~shadow/sql/sql1992.txt （只作历史口径依据，非最新版）。
- **Tutorial D 的现实下落**：Tutorial D 没有工业实现，作者的参考实现是 Rel（⚠️ 本次未能通过书目/代码源核实其仓库地址，不给链接）。可验证的社区实现之一是 Clojure 版的 Tutorial D 风格语言 core.relational：https://github.com/moerkb/core.relational ✅（可达性已验证，2014 年后未更新，仅供"这语言长什么样"的直觉）。
- **今天怎么写这类"判据"**：工程侧最实用的替代是**契约测试**——把"接口不泄漏行序/重复行"写成断言，在 CI 里跑。示例口径（🔧 自拟，非书中原文）：

```sql
-- 🔧 断言：这个查询的结果必须是"无重复元组"的关系
SELECT COUNT(*) AS n_rows, COUNT(DISTINCT v) AS n_tuples
FROM (SELECT SN, CITY FROM S) AS q;
-- n_rows <> n_tuples ⇒ 该"结果关系"其实是个袋
```

- **可实测的本章概念**：`数据独立性被列序破坏` 与 `重复行` 两条在第 2 章给出完整 🔧 SQLite 实测（D1/D2），结论是「SQL 的 UNION 不看属性名」⚠️ 与「表允许完全相同的两行」。
