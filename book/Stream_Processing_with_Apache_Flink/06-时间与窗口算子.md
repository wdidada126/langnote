## 核心概念速览（中英对照）

- **窗口** — window：把无界流按时间（或计数）切成有限块，从而能用批式语义计算。
- **滚动窗口** — tumbling window：固定长度、不重叠（`TumblingEventTimeWindows.of(Time.minutes(1))`）。
- **滑动窗口** — sliding window：固定长度 + 滑动步长，可重叠（长度/步长两个参数）。
- **会话窗口** — session window：由「活动间隙 gap」动态定界，同一键的会话互不重叠。
- **全局窗口** — global window：所有元素进同一个窗口，必须自带触发器，否则永不结束。
- **窗口分配器** — WindowAssigner：决定一条记录属于哪些窗口、用哪个时间字段判断。
- **触发器** — Trigger：决定窗口「什么时候可以计算」以及「什么时候清理」；可提前触发（early firing）。
- **驱逐器** — Evictor：在函数执行前/后裁剪窗口内容（`CountEvictor`/`TimeEvictor`/`DeltaEvictor`）。
- **增量聚合 vs 全窗口函数** — ReduceFunction/AggregateFunction 与 WindowFunction/ProcessWindowFunction：前者每来一条更新一个累加器（状态 O(1)），后者窗口结束时拿到整个迭代器（灵活但 O(N) 状态）。
- **水位线延迟** — watermark lag / out-of-orderness bound：`maxTs - 允许乱序` 里那个「允许乱序」，是延迟与完整性的折中。
- **计时器** — timer：`registerEventTimeTimer`/`registerProcessingTimeTimer`，由时间服务在进度到达时回调 `onTimer`。
- **侧输出** — side output：一个算子向多个具名输出流发射数据（`OutputTag`），迟到数据与分流的标准出口。
- **迟到数据与允许迟到** — late data & allowedLateness：事件时间已低于窗口结束水位线的数据，三种处置
  （丢弃 / 窗口保留状态到「结束 + 允许迟到」期间**重新发出**更新结果 / 侧输出走修正通道）。
- **间隔连接与窗口连接** — interval join / window join：前者按「另一流记录时间戳 ± 区间」配对，
  后者两流先进同窗口再关联；两者的状态都由水位线清理。
- **CoProcessFunction** — 双流协调函数：两条（键控）流共享状态与计时器的唯一入口。

## 核心精讲

### 6.1 让事件时间真正生效的三步 🔧

```scala
// 🔧 Scala（Flink 1.7 风格，教学示意）
env.setStreamTimeCharacteristic(TimeCharacteristic.EventTime)   // ① 声明语义（1.12 起不需要 ⚠️）

val raw = env.addSource(kafkaSource)
val withTs = raw
  .assignTimestampsAndWatermarks(
    new BoundedOutOfOrdernessTimestampExtractor[Event](Time.seconds(5)) {  // ② 时间戳 + 水位线
      override def extractTimestamp(e: Event): Long = e.ts
    })
  .keyBy(_.userId)
```

③ 使用时间的地方（窗口/计时器/Join）才会按事件时间推进。

水位线的三个「不完整」情形（原书「完整性问题」一节的要点化）：

| 情形 | 症状 | 处理 |
| --- | --- | --- |
| 延迟设得太小 | 大量数据迟到、结果被修正或丢弃 | 看端到端延迟分布（P99 乱序度）设界；或改处理时间 |
| 延迟设得太大 | 结果迟迟不出（窗口要等 `end + lag`） | 用触发器做提前输出 + 后续修正 ⚠️ |
| 某分区无数据（idle） | 该分区水位线不前进 → 算子 `min()` 卡住全局 | 空闲标记 `WatermarkStatus.IDLE`（新版 `withIdleness`）⚠️ 1.7 时代做法有限 |
| 源并行度 > Kafka 分区数 | 空 source 子任务永远不产生水位线 | 提高并行度匹配分区数，或用带空闲检测的策略 |

### 6.2 ProcessFunction：时间与状态的通用底座 🔧

```scala
// 🔧 会话式超时告警：点击后 30 分钟无心跳则报警（不依赖会话窗口，用 timer 手写）
stream.keyBy(_.uid).process(new KeyedProcessFunction[String, Event, Alert] {
  lazy val lastTs  = getState(ValueStateDescriptor("lastTs", Types.LONG))
  lazy val timerTs = getState(ValueStateDescriptor("timerTs", Types.LONG))

  override def processElement(e: Event, ctx: Context, out: Collector[Alert]): Unit = {
    lastTs.update(e.ts)
    val newTimer = e.ts + 30 * 60 * 1000L
    val old = timerTs.value()
    if (old == null || newTimer > old) {                 // 只在更晚的 timer 上注册，避免 timer 泄漏
      if (old != null) ctx.timerService().deleteEventTimeTimer(old)
      ctx.timerService().registerEventTimeTimer(newTimer)
      timerTs.update(newTimer)
    }
  }
  override def onTimer(ts: Long, ctx: OnTimerContext, out: Collector[Alert]): Unit =
    if (ts == timerTs.value()) out.collect(Alert(ctx.getCurrentKey, "timeout"))
})
```

三条纪律：**计时器要存进状态**（否则重启后无法删除/去重）、**旧计时器要删**（否则状态泄漏与重复触发）、
**`onTimer` 里要校验**（同一键可能有多个计时器）。

### 6.3 侧输出：一个算子，多个出口 🔧

```scala
val lateTag = new OutputTag[Event]("late-events") {}          // 匿名子类是为了保留泛型类型信息
val main = stream.keyBy(_.uid)
  .window(TumblingEventTimeWindows.of(Time.minutes(5)))
  .allowedLateness(Time.minutes(10))
  .sideOutputLateData(lateTag)                                // 兜底通道
  .reduce(_ + _, new MyWindowFn)
val late: DataStream[Event] = main.getSideOutput(lateTag)     // 送去人工修正/回流
```

侧输出的通用用途：脏数据隔离、异常事件旁路、把「同一计算的多份结果」写不同 sink。

### 6.4 窗口的组合矩阵

| 需求 | 推荐组合 | 理由 |
| --- | --- | --- |
| 每分钟计数 | `TumblingEventTimeWindows` + `AggregateFunction`（增量） | 状态 O(1)，吞吐最好 |
| 每分钟 P95 延迟 | 窗口 + `ProcessWindowFunction`（全量） | 分位数需要保留样本；可换 TDigest 之类近似 ⚠️ |
| 每 30s 更新「过去 5min」 | `SlidingEventTimeWindows(5min, 30s)` + 增量聚合 | 重叠窗口只能靠增量避免状态爆炸 |
| 用户会话切分 | `EventTimeSessionWindows.withDynamicGap` | 间隙由状态决定，静态 gap 用 `withGap` |
| 每条都发（含首次） | 全局窗口 + `CountTrigger.of(1)` 或 `ContinuousEventTimeTrigger` | 全局窗口默认永不触发，必须给触发器 |
| 早发 + 迟到修正 | 窗口 + 自定义 Trigger（`OnElement`）+ `allowedLateness` | 早期结果与最终结果同键更新，下游要能吃更新 |

🔧 增量 + 全量的组合写法：

```scala
clicks.keyBy(_.uid)
  .window(TumblingEventTimeWindows.of(Time.hours(1)))
  .aggregate(
    new AggregateFunction[Click, ClickCount, ClickCount] {   // 每键一个累加器，增量维护
      def createAccumulator() = new ClickCount
      def add(c: Click, a: ClickCount) = { a.total += 1; a.byType.inc(c.typ); a }
      def getResult(a: ClickCount) = a
      def merge(a: ClickCount, b: ClickCount) = { a.total += b.total; a }     // 会话/合并窗口需要 merge
    },
    new ProcessWindowFunction[ClickCount, UserHourly, String, TimeWindow] { // 只在窗口结束跑一次
      def process(k: String, ctx: Context, in: Iterable[ClickCount], out: Collector[UserHourly]) =
        out.collect(UserHourly(k, ctx.window.start, ctx.window.end, in.head.total))
    })
```

自定义窗口（`WindowAssigner` + `Trigger` + `Window`）的适用边界：原书给了「按 URL 会话/按元素数」的例子；
**要点**是自定义窗口的 `getWindows()` 决定归属、`isTrigger`/`onElement` 决定时机，
且自定义窗口默认不走「键组优化」，实现要保守 ⚠️（性能断言未核实）。

### 6.5 双流 Join：先决定「保留多久」

| Join 类型 | 语义 | 状态寿命 | 适用 |
| --- | --- | --- | --- |
| `intervalJoin(other).where(ts).between(-5min, 5min)` | 每条记录与另一流「时间窗内」的记录配对 | 事件时间水位线过界即清理 | 点击↔下单、请求↔响应 |
| 窗口 Join `windowJoin` + `TumblingEventTimeWindows` | 两流各自进窗，窗内做关联 | 窗口结束即释放 | 需对齐到同一时间桶的批量关联 |
| `CoProcessFunction` 手写 | 任意规则 | 你说了算 | 需要跨多轮、多键或复杂状态机 |

🔧 间隔 Join：

```scala
clicks.keyBy(_.uid).intervalJoin(purchases.keyBy(_.uid))
  .where(_.ts).between(Time.minutes(-5), Time.minutes(5))
  .timeout(Time.hours(1))                       // 超时无配对 → 侧输出（新版用 OutputTag；1.7 需 sideOutputTimeout ⚠️）
  .apply((c, p) => Attribution(c.uid, c.ts, p.ts, p.amount))
```

注意：**两条流都必须各自带事件时间与水位线**，且都必须 `keyBy` 同一键；
否则水位线无法驱动清理，状态会无限增长（这是本章最容易在生产上炸的坑）。

### 6.6 迟到数据的三档策略（原书「处理迟到数据」一节）

| 策略 | 做法 | 结果形态 | 下游要求 |
| --- | --- | --- | --- |
| 丢弃 | 默认：水位线越过即丢 | 只有一份最终值 | 无 |
| 重定向 | `sideOutputLateData(tag)` | 迟到事件进独立流 | 需要修正流程或告警看板 |
| 更新结果 | `allowedLateness(...)` 或触发器提前发 | 同一键多次发出「更好的值」 | 下游必须能吃更新（幂等 upsert / 回撤 ⚠️ 见 13 补编） |

## 版本与兼容性

- `TimeCharacteristic` 与 `assignTimestampsAndWatermarks(AssignerWithPeriodicWatermarks)` 是 1.7 的形态；
  现代写法是 `WatermarkStrategy.forBoundedOutOfOrderness(Duration.ofSeconds(5)).withIdleness(...)`（1.11+）⚠️。
- `windowJoin` 与 `intervalJoin` 的窗口版在后续版本被弱化/文档重心转向 SQL 窗口 join ⚠️（是否移除未核实）。
- `sideOutputLateData` 在 DataStream 层仍在；SQL/Table 层的迟到通过 watermark + 窗口 TVF 表达（13 补编）。
- 会话窗口的动态 gap（`withDynamicGap`）引入版本较晚 ⚠️，1.7 可能仅有静态 gap；使用前请核对该版本 API 列表。
  Flink 2.x 的 `WindowAssigner`/`Trigger` 接口亦有调整 ⚠️（未逐条核实）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「设了 EventTime 就自动按事件时间」 | 必须给每条记录分配时间戳并生成水位线，否则时间戳是 0、水位线是 `Long.Min`，窗口永不触发 |
| 「水位线 = 最大时间戳」 | 是「最大时间戳 - 乱序界」，且跨算子取最小值，因此它比任何单条记录都可能更晚 |
| 「窗口函数都能看到全部数据」 | 用增量聚合时 `WindowFunction` 收到的是聚合结果，不是原始事件；要原始数据就别配增量函数 |
| 「`allowedLateness` 能救所有迟到」 | 它只保留状态到 `窗口结束 + 允许迟到`；再晚就进侧输出或被丢弃 |
| 「注册计时器不用存状态」 | 重启后无法删除旧计时器 → 同一键触发无数次；必须把 timer 时间戳写进状态（07 章） |
| 「全局窗口不写触发器也能跑」 | 默认触发器在元素时间越界时才触发，元素时间不越界则永不输出，看起来「作业没结果」 |
