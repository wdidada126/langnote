## 核心概念速览（中英对照）

- **状态** — state：算子在事件之间保留、并参与检查点的数据；Flink 的容错与时间语义都围绕它。
- **键控状态** — keyed state：随当前记录所属键自动切换的状态，只能在 `KeyedStream` 上使用。
- **算子状态** — operator state：属于算子实例（子任务）而非键的状态，用 `ListState` 表达、按分配策略重分布。
- **状态原语** — state primitive：`ValueState`/`ListState`/`MapState`/`ReducingState`/`AggregatingState` 五种声明式接口，统一由 `StateDescriptor` + `RuntimeContext.getState` 在 `open()`（或 `initializeState`）里声明。
- **`CheckpointedFunction`** — 检查点接口：`initializeState` 拿状态、`snapshotState` 在屏障处写算子状态。
- **`ListCheckpointed`** — 旧版算子状态接口：返回一个 List 作为快照（本书使用；后续版本废弃移除 ⚠️）。
- **`CheckpointListener`** — 检查点监听：`notifyCheckpointComplete(id)` 是两阶段提交汇的提交钩子（08 章）。
- **键组** — key group：键控状态的分片单位，`maxParallelism` 决定其数量，扩缩容即重分配键组 ⚠️（术语出处为官方文档）。
- **最大并行度** — max parallelism：决定 key group 数，一旦有状态就**不能随意改**（05 章）。
- **算子 UID** — operator uid：状态的身份；改名/删算子会破坏状态映射（05/10 章）。
- **状态 TTL** — StateTtlConfig：给状态加过期时间，是防状态泄漏的第一工具。
- **状态后端** — state backend：状态存放与快照实现（堆内 vs RocksDB；全量 vs 增量检查点）。
- **增量检查点** — incremental checkpoint：RocksDB 只上传变化的 SST 文件，大状态下省带宽。
- **可查询状态** — queryable state：从作业外部按 key 读算子状态的服务（本书有整节；**已在后续版本废弃移除** ⚠️）。
- **状态兼容性** — state compatibility：升级应用时状态能否被新拓扑接住，取决于 uid、状态名与序列化器。

## 核心精讲

### 7.1 键控状态的标准形状 🔧

```java
// 🔧 Java：Rich/Process 函数里用 RuntimeContext 声明（open 之外声明会报错）
public class UserSession extends KeyedProcessFunction<String, Event, Summary> {
    private transient ValueState<Long> lastSeen;
    private transient MapState<String, Long> typeCount;
    private transient ReducingState<Long> maxTs;              // 只留一个合并值，比 ListState 省

    @Override public void open(Configuration cfg) {
        lastSeen  = getRuntimeContext().getState(new ValueStateDescriptor<>("lastSeen", Types.LONG));
        typeCount = getRuntimeContext().getMapState(new MapStateDescriptor<>("typeCount", Types.STRING, Types.LONG));
        maxTs     = getRuntimeContext().getReducingState(new ReducingStateDescriptor<>("maxTs", new MaxOf(), Types.LONG));
    }
    @Override public void processElement(Event e, Context ctx, Collector<Summary> out) throws Exception {
        lastSeen.update(e.ts);                                // 当前键由框架定位，代码里没有 key 参数
        typeCount.put(e.type, typeCount.contains(e.type) ? typeCount.get(e.type) + 1 : 1L);
        out.collect(new Summary(ctx.getCurrentKey(), e.ts));
    }
}
```

**三条硬规矩**：

1. 描述符要有**名字**（名字 + uid 共同决定升级时的状态映射）。
2. 状态句柄要 `transient`（它不属于用户对象序列化，运行期由后端注入）。
3. 不要在函数字段里放普通 Java 集合当「状态」——那不参与检查点，重启即丢，正是本书反复强调的陷阱。

### 7.2 状态原语选型表

| 原语 | 内部形态 | 读语义 | 适合 |
| --- | --- | --- | --- |
| `ValueState<T>` | 单值 | `value()/update()/clear()` | 最近一次时间戳、标志位 |
| `ListState<T>` | 可迭代列表 | `add/get()` 返回迭代器 | 事件缓冲、待配对集合 |
| `MapState<K,V>` | 键内映射 | `put/get/contains/keys()` | 每键的多维度计数、去重表 |
| `ReducingState<T>` | 单值（增量 merge） | `add()` 触发 reduce | 求和/最大/最小 |
| `AggregatingState<IN,ACC,OUT>` | 累加器 | `add()` + 自定义 `AggregateFunction` | 计数、平均值、TopN 之类 |

选型口径：**能增量就别缓冲**——缓冲全量（`ListState`）意味着窗口长度决定状态大小；
增量（`Reducing`/`Aggregating`）意味着状态大小与时间无关。

### 7.3 算子状态：source offset 的归宿 🔧

```java
// 🔧 CheckpointedFunction（现代写法）
public class MySource implements SourceFunction<String>, CheckpointedFunction {
    private transient ListState<Long> offsets;   // 算子状态：本实例负责的分区 offset
    private volatile boolean running = true;

    @Override public void initializeState(FunctionInitializationContext ctx) throws Exception {
        offsets = ctx.getOperatorStateStore().getListState(
            new ListStateDescriptor<>("offsets", Types.LONG));
        if (ctx.isRestored()) {                  // 恢复分支：把上次 offset 装回
            for (Long o : offsets.get()) resumeFrom(o);
        }
    }
    @Override public void snapshotState(FunctionSnapshotContext ctx) throws Exception {
        offsets.clear();                         // 每次快照先清空再写（常见忘 clear → 状态翻倍）
        for (Long o : currentOffsets()) offsets.add(o);
    }
}
```

- 本书同时讲了旧接口 `ListCheckpointed<T>`（`getCheckpointedState()`/`restoreCheckpointedState()`）——**1.13 起废弃、后续版本移除** ⚠️；今天一律写 `CheckpointedFunction`。
- 分配策略：默认 `even_weighted`（list 元素轮询分给各子任务）；扩缩容时想「每个实例都拿到全量」需要
  union list state ⚠️（命名以版本文档为准）——**广播状态正是这个用途**（14 补编）。

### 7.4 检查点完成通知 🔧

```java
public class TxSink extends TwoPhaseCommitSinkFunction<...> implements CheckpointListener {
  @Override public void notifyCheckpointComplete(long id) { commitPendingTransactions(); }
  @Override public void notifyCheckpointAborted(long id)  { abortPending(); }
}
```
意义：把「对外部系统可见的副作用」压到检查点成功之后，让外部世界也获得一次原子提交（08 章细讲）。
Scala 侧写键控状态可用 `lazy val s = stateValue()`（`KeyedStateFunction` 语法糖），本质一致。

### 7.5 打开故障恢复

```scala
// 🔧 Scala
env.enableCheckpointing(10000, CheckpointingMode.EXACTLY_ONCE)
env.getCheckpointConfig.setMinPauseBetweenCheckpoints(5000)
env.getCheckpointConfig.setMaxConcurrentCheckpoints(1)
env.getCheckpointConfig.setCheckpointTimeout(60000)          // 与「快照耗时 + 对齐等待」比量级
env.getCheckpointConfig.enableExternalizedCheckpoints(ExternalizedCheckpointCleanup.RETAIN_ON_CANCELLATION) // ⚠️ 名称随版本变化
env.setRestartStrategy(RestartStrategies.fixedDelayRestart(3, Time.seconds(10)))
```

模式区别（原书要点）：`EXACTLY_ONCE` 需屏障对齐并回滚到上一检查点；`AT_LEAST_ONCE` 不对齐（屏障到即快照），更快但要求算子幂等。

### 7.6 可维护性清单（本章最实用的一节）

| 项 | 决策 | 影响 |
| --- | --- | --- |
| `uid()` | 上线前给每个有状态算子定名并**写进代码库** | 改名 = 状态找不到；升级/重缩放全靠它 |
| `setMaxParallelism` | 按未来最大并行度定（默认 128 上限有讲究 ⚠️） | 改动会使 keyed 状态无法恢复（需 `--allowNonRestoredState` 或状态迁移） |
| 状态后端 | 状态 < 内存余量 → 堆内；否则 RocksDB + 增量检查点 | RocksDB 需要本地盘（`state.backend.rocksdb.localdir`）与堆外内存预算（09 章） |
| 状态原语 | 增量优先；`MapState` 优于「Map 塞 ValueState」 | 后者每次读写序列化整张 Map |
| 防泄漏 | `StateTtlConfig`（过期 + 清理策略）+ 及时 `clear()` + 删计时器 | 无 TTL 的 `MapState` 是运维事故的常客 |
| 序列化 | 避免 Kryo（`GenericTypeInfo`）；显式 POJO/Tuple/专用序列化器 | Kryo 慢且不支持增量/字段表达式；RocksDB 下每条记录都要 (反)序列化 |

🔧 TTL 写法：

```java
StateTtlConfig ttl = StateTtlConfig.newBuilder(Time.hours(24))
    .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
    .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired)
    .cleanupInRocksdbCompactFilter(1000).build();          // 后端相关的清理策略 ⚠️ 名称以版本为准
ValueStateDescriptor<Stat> d = new ValueStateDescriptor<>("stat", Types.POJO(Stat.class));
d.enableTimeToLive(ttl);                                   // TTL 只对键控状态生效
```

### 7.7 更新应用：三种动作

| 动作 | 做法 | 风险 |
| --- | --- | --- |
| 保持现有状态更新 | 不改 uid/状态名/类型，只改逻辑 → 从 savepoint 重启（10 章） | 逻辑与旧状态语义不匹配（例：累加器字段增删）要用兼容序列化器 |
| 删除有状态算子 | 从拓扑去掉该算子；恢复时状态无处安放 | 需要 `--allowNonRestoredState`（会丢那部分状态）⚠️ 参数名以版本为准 |
| 修改算子状态结构 | 新增状态描述符可以；改类型不行 | 常见做法：新增一个带新名的状态并双写一段，再弃用旧的 ⚠️（原书给的具体流程未核实） |

### 7.8 可查询状态：本节现在是「历史」⚠️

本书描述的能力：`QueryableStateClient` 按 job id + 查询名取 `ResultFuture`，
底层是 proxy 查询（路由到持键的 TaskManager）与 parameter query（自己算 key group）。
**现状**：1.10 被标记废弃、随后从发行版移除 ⚠️（具体移除版本未逐一核实）。今天的替代路径：
① 把状态写成可查结果表（upsert 到 Redis/HBase/数据湖），应用查表而非查作业内部；
② 用异步 I/O（08 章）把外部存储当状态的「可查镜像」；③ 监控走指标系统 + 外部存储（10 章）。

## 版本与兼容性

- 本书时代的类名：`MemoryStateBackend` / `FsStateBackend` / `RocksDBStateBackend`（+ `new RocksDBStateBackend(dir, true)` 的增量开关）→ 1.13 起 `HashMapStateBackend` / `EmbeddedRocksDBStateBackend`，`enableIncrementalCheckpoints()` 改名 ⚠️。
- `ListCheckpointed` 已废弃移除；`Time`（`org.apache.flink.api.common.time.Time`）在新版被 `Duration` 取代 ⚠️；
  外部化检查点保留策略的枚举与配置键名有变动 ⚠️；Queryable State 已不可用（7.8）。
- 键组 / `maxParallelism` 的约束在 2.x 仍在，但支持了部分 rescaling 场景的更灵活处理 ⚠️（未核实细节，勿据此改生产流程）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「用成员变量 `HashMap` 存状态就行」 | 不参与检查点，重启即丢、且扩缩容无法迁移；这是本书专门点名的反例 |
| 「忘 `clear()` 就没事」 | `ListState` 快照累加 → 状态翻倍增长，恢复时更慢；每次 `snapshotState` 先 clear |
| 「`maxParallelism` 可以以后调」 | 它定义 key group 数；有状态之后改它 = 状态不可恢复（需迁移工具/重建状态） |
| 「uid 可有可无」 | 不设 uid 时按拓扑位置自动编号，加一个算子就会让后面所有算子的隐式 uid 错位 |
| 「TTL 一定会立刻物理回收」 | TTL 的清理是后台策略（线程/压缩过滤器），过期值在配置 `NeverReturnExpired` 下只是不返回 |
| 「EXACTLY_ONCE 检查点 = 端到端精确一次」 | 还需源可重放 + 汇幂等/事务（08 章）；内部模式只保证状态与算子输出 |
