## 核心概念速览（中英对照）

- **有状态流处理** — stateful stream processing：算子在处理每条事件时读写并保留「过去的相关信息」，状态成为与数据同等的一等公民。
- **状态** — state：算子为后续计算暂存并可恢复的中间结果（计数器、最近一次读数、待匹配的图案等）。
- **事务型处理** — transactional processing / OLTP：以单条记录的小读写为主、追求低延迟与强一致的处理范式。
- **分析型处理** — analytical processing / OLAP：对大批历史数据做全量扫描与聚合、追求吞吐而非单点延迟。
- **事件驱动型应用** — event-driven application：状态 + 规则决定「何时产生动作」的流应用（欺诈检测、推荐、报警）。
- **数据管道** — data pipeline：以数据搬运、清洗、格式化为主的流应用，通常状态很少甚至无状态。
- **流式分析** — streaming analytics：在无界数据上持续计算聚合/窗口结果的流应用。
- **数据流** — data stream：随时间不断到达、不可完整持有的事件序列，是有界集合在时间维度上的推广。
- **转换** — transform：作用在数据流上的算子（map/filter/keyBy…），输入输出仍是流。
- **Lambda 架构** — Lambda architecture：批层保证准确、速度层保证实时、服务层合并结果的折中方案 ⚠️（原书提及，属背景性讨论）。
- **运行时** — runtime：Flink 的执行引擎（调度、网络、状态、检查点），API 只是它的不同前端。
- **DataStream API** — DataStream API：Flink 面向单条事件的元素级流处理 API，本书主线。

## 核心精讲

### 1.1 为什么说「批 + 事务」不够用

原书的论证路线值得照抄下来，因为它一句话解释了 Flink 存在的理由：

| 范式 | 处理的对象 | 状态在哪 | 弱点 |
| --- | --- | --- | --- |
| 事务型（OLTP） | 一条业务记录的增删改查 | 数据库，随取随用 | 只能看「当前值」，跨记录/跨时间的聚合要写额外报表 |
| 分析型（OLAP，批） | 固定时间窗的数据快照 | 无（每次重算） | 每来一点新数据就重跑全量：延迟高、成本随数据线性增长 |
| 有状态流处理 | 无界事件流 | 算子内，增量维护 | 需要一套容错 + 时间语义机制（这正是 Flink 的两大支柱，见 02/06/07 章） |

一句话：**批处理是「重算一切」，流处理是「只算增量」**。前者正确但慢，后者快但必须把
状态的正确性（容错）与时间顺序（乱序）解决掉，否则增量会算错。

### 1.2 三类流应用：给需求定位

原书按「状态数量 × 计算复杂度」把流应用分成三类（本表口径与官方文档一致 ⚠️ 分类命名以原书为准）：

- **事件驱动应用**：状态较少、计算较重、输出常常是「一个动作」。例：欺诈检测（对同一账户维护最近交易摘要，规则命中就下单拦截）。
- **数据管道**：几乎无状态、计算轻、吞吐优先。例：ETL、日志格式转换、Kafka ↔ 数据湖搬运（对应本书 08 章连接器）。
- **流式分析**：状态多（每键一份）、计算中等、输出持续更新的结果表/指标。例：每用户每分钟点击数、会话窗口内的推荐序列。

定位意义很实际：**类别决定你该关心哪一章**。管道关心 05/08（吞吐与连接器）；
分析关心 06/07（窗口、状态与迟到）；事件驱动关心 06/07 与补编 C（计时器、CEP）。

### 1.3 开源流处理演变：Flink 站在哪条血脉上

- **Storm（2011 前后）**：真·逐条处理，但没有事件时间与状态原语，状态要靠外部存储外挂。
- **Spark Streaming（微批）**：把流切成小批，复用批处理引擎的容错（RDD lineage），代价是延迟下限与「假的事件时间」。
- **MillWheel / Dataflow / Flink（有状态流处理）**：状态是一等公民，事件时间 + 水位线是一等公民，容错用分布式快照（见 [12 补编](12-补编-检查点机制与分布式快照.md)）。
  仓库中这几篇论文的登记位置：[../bigdata/01-大数据技术全景.md](../bigdata/01-大数据技术全景.md) 第 174–176 行、
  [../bigdata/07-实时计算与流式架构.md](../bigdata/07-实时计算与流式架构.md) 第 204–209 行。

Flink 的差异化（原书口径）：**运行时统一、API 分层**——批只是「有界的流」，
图计算/CEP/SQL 都跑在同一个带检查点的运行时上。

### 1.4 Flink 快览：三层结构

```
应用（你的 main）
  ├─ API/库：DataStream API、Table API & SQL、FlinkCEP、Gelly、ML ⚠️（后三者在原书仅第 11 章简介）
  ├─ 运行时：dataflow 图执行、任务并行、事件时间、状态、检查点、迭代
  └─ 物理部署：standalone / YARN / Kubernetes / Docker（原书第 9 章）
```

对应关系记住三条即可：

1. **API 层决定你写什么**（元素级 → 表级 → 模式级），
2. **运行时决定语义**（时间、状态、一致性），
3. **部署决定运维**（HA、扩缩容、监控）。

### 1.5 第一个 Flink 程序 🔧

> 🔧 Scala（Flink 1.7 时代的写法，教学示意，不参与构建）。原书示例即「读 socket / 读集合 →
> 切词 → 按键计数 → 打印」的骨架。

```scala
import org.apache.flink.streaming.api.scala._

object FirstJob {
  def main(args: Array[String]): Unit = {
    val env = StreamExecutionEnvironment.getExecutionEnvironment   // 执行环境：本地或集群的入口

    val text = env.fromElements("flink flink stream stream stream state")
        .flatMap(_.toLowerCase.split("\\W+").filter(_.nonEmpty))    // 一条输入可发多条输出

    text.map((_, 1L))                                              // (word, 1) 元组流
        .keyBy(0)                                                  // 按下标 0（词）分区 → KeyedStream
        .sum(1)                                                    // 增量聚合：每个键一个计数器（状态！）
        .print()

    env.execute("first stateful job")                              // 触发：此前只是构图
  }
}
```

```java
// 🔧 Java 等价写法（要点：类型信息要显式给，Java 泛型会被擦除）
DataStream<Tuple2<String, Long>> words = env
    .fromElements("flink flink stream")
    .flatMap((String s, Collector<Tuple2<String, Long>> out) ->
        Arrays.stream(s.split("\\W+")).forEach(w -> out.collect(new Tuple2<>(w, 1L))))
    .returns(Types.TUPLE(Types.STRING, Types.LONG));

words.keyBy(0).sum(1).print();
env.execute();
```

四个必须现在就建立的直觉（后面各章都从这里长出去）：

- **构图与执行分离**：`execute()` 之前程序没跑，`DataStream` 对象是图的句柄（02 章 dataflow 图）。
- **`keyBy` 不是转换而是分区**：它把 `DataStream` 变成 `KeyedStream`，之后才允许带状态的算子（05/07 章）。
- **`sum(1)` 有状态**：每个键一个计数器常驻算子内存 → 于是需要检查点（03/07 章）。
- **Java 与 Scala 的差别主要在类型信息与键的写法**（05 章）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「流处理 = 低延迟的批处理」 | 差别不在延迟而在**是否持有状态并增量计算**；把批作业跑得再快也不是有状态流处理 |
| 「Flink 快是因为逐条处理」 | 逐条处理只是延迟下限低；真正的竞争力是**运行时把状态 + 事件时间 + 快照容错统一了**（02/03 章） |
| 「Spark Streaming 不能做有状态」 | 能，但状态以 RDD 血缘/DStream 形式表达；本书论点是「把状态做进运行时才能做细粒度恢复与事件时间」（⚠️ 属对比性论断，勿当作性能结论） |
| 「WordCount 是流作业」 | 上面示例跑在有界 `fromElements` 上，实质是批；把它接上无界源 + 窗口才是流（06 章） |
| 「先学 Table API 再学 DataStream」 | 本书路径是反的：语义在 DataStream 层最透明，表层的 retime/回撤语义要靠它解释（13 补编） |
| 「事件驱动应用需要很多状态」 | 恰恰相反，事件驱动应用通常状态少但规则复杂；重状态的是流式分析 |
