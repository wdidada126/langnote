## 核心概念速览（中英对照）

- **数据流图** — dataflow graph：由算子（顶点）与事件流（边）构成的有向图，是 Flink 描述程序的唯一中间形态。
- **算子** — operator / stream operator：图中的一个转换节点，输入/输出都是流。
- **数据并行** — data parallelism：同一段逻辑被复制成多个实例，各处理数据的一个子集（并行度的来源）。
- **任务并行** — task parallelism：不同算子的子任务装进同一个线程/槽执行，靠「任务链」省掉网络与序列化。
- **子任务** — subtask：一个算子在一个并行实例上的执行单元，是调度与检查点的最小单位。
- **任务槽** — task slot：TaskManager 上固定的资源容器，允许同 TM 内不同作业的子任务共存（slot sharing）。
- **数据交换策略 / 分区方式** — data exchange strategy / partitioning：一条边把上游子任务的记录发给哪些下游子任务的规则（1:1、1:*、rebalance、broadcast、shuffle、global、rescale…）。
- **网络通道** — network channel：上下游子任务之间一条有固定缓冲区的传输管道，是反压的物理载体。
- **反压** — backpressure / credit-based flow control：下游处理不过来时通过通道缓冲与信用机制把压力回传给上游。
- **处理时间** — processing time：算子所在机器的系统时钟，性能最好、语义最简单，结果依赖到达速度。
- **事件时间** — event time：事件本身携带的时间戳，结果与到达顺序无关，但需要水位线才能推进。
- **水位线** — watermark：「事件时间已推进到 T，晚于 T 的数据基本到齐」的进度声明，驱动窗口/计时器。
- **迟到数据** — late data：时间戳小于当前水位线、在窗口被认为结束后才到达的事件。
- **至少一次 / 至多一次 / 恰好一次** — at-least-once / at-most-once / exactly-once：故障恢复后对「每条事件被处理几次」的承诺层级。
- **有效一次** — effectively-once：结果等价于一次处理，实现手段可以是幂等或事务（08 章展开）。

## 核心精讲

### 2.1 一切皆图：从 API 到执行

🔧 Scala（教学示意）

```scala
val env = StreamExecutionEnvironment.getExecutionEnvironment
env.setParallelism(4)
env.addSource(kafkaSource)          // (1) source
   .keyBy(_.userId)                 // (2) 分区边界（不是普通算子）
   .process(new UserSessionFn)      // (3) 有状态算子
   .sinkTo(printSink)               // (4) sink
```

这 4 步在运行时变成：

```
JobGraph:        [Source] --edge1--> [keyBy 后算子] --edge2--> [Sink]
ExecutionGraph:  每个顶点按并行度展开成 N 个 subtask，边展开成 channel 连接矩阵
部署:            subtask → slot → TaskManager 线程
```

**要点**：并行度、分区、检查点边界都定义在「图」上而不是「代码」上——所以同一个程序改并行度不改逻辑，
`uid` 才能作为状态的身份（07 章）。

### 2.2 两种并行：数据并行 vs 任务并行

| 维度 | 数据并行 data parallelism | 任务并行 task parallelism |
| --- | --- | --- |
| 并行什么 | 同一算子的多个实例分吃不同数据 | 不同算子的子任务在同一线程/槽内跑 |
| 提升什么 | 吞吐（横向扩展） | 资源利用率、减少序列化与网络跳 |
| 由谁控制 | `setParallelism` / `maxParallelism` | slot 数、`slot sharing group`、`disableChaining` |
| 失效场景 | 键倾斜（某个 subtask 吃下全部热点键） | 一个慢算子拖累同链上所有算子的延迟 |

Flink 的**任务链（task chaining）**把「1:1 分区 + 单线程 + 非异步」的相邻算子合成一个任务，
数据不经网络、不序列化；调试性能时先用 `disableOperatorChaining()` 或 Web UI 看是否被链化（03/10 章）。

### 2.3 边的类型学：数据交换策略

Flink 1.7 文档中的分类（本目录统一采用这套中文译名）：

| 策略 | 语义 | 典型 API | 代价 |
| --- | --- | --- | --- |
| 1:1（forward） | 上游每个子任务只发给「同号」下游 | `forward()`、链化的默认 | 几乎为零，本地或同通道 |
| 广播 broadcast | 每条记录发给所有下游子任务 | `broadcast()` | 网络 ×并行度，注意下游放大 |
| 重平衡 rebalance | 轮询均分，消解上游倾斜 | `rebalance()` | 全洗牌，跨节点 |
| 缩放 rescale | 只在本地上下游之间轮询 | `rescale()` | 只在同 TM 内洗牌，比 rebalance 省 |
| 全局 global | 全部发给下游第 0 个子任务 | `global()` | 单点，仅用于必须集中的场合 |
| 洗牌 shuffle | 随机轮询（无键） | `shuffle()` | 全洗牌 |
| 按键分区 keyed | 按 key hash 决定归属 | `keyBy(...)` | 全洗牌 + 决定状态分布 |
| 自定义 | 用户实现分区器 | `partitionCustom(...)` | 由实现决定 |

工程直觉：**`keyBy` 是「语义上的洗牌」**——它同时定义了状态的归属（哪个子任务持有哪个键的状态）
与并行边界，因此它也是检查点屏障必须对齐的位置（12 补编）。

### 2.4 延迟、吞吐与反压的三方账

- **延迟下限**来自「一条记录穿过图的时间」：序列化 + 网络 + 每算子处理。链化与 1:1 边能把常数压到最低。
- **吞吐上限**由最慢的子任务决定；攒批（微批）提高吞吐但抬高延迟——这是本书「一分钟意味着什么」一节的落点。
- **反压的物理机制**：每个 channel 有固定数量网络缓冲；下游消费慢 → 缓冲占满 → 上游收不到「信用」→ 上游停止从源读。
  所以反压会**一路传导到 source**，Kafka lag 是它的表面症状（10 章监控）。

```
下游变慢 → 输入缓冲区耗尽 → 通告信用 = 0 → 上游写阻塞 → 上游算子处理停滞 → source 拉取停滞 → Kafka lag 上涨
```

### 2.5 时间与一致性：本书的两条主轴

原书第 2 章把「时间」和「状态/一致性」并列，正是 Flink 的两大支柱。二者的耦合关系可以写成两张表：

**时间语义对照**

| 语义 | 谁定义时间 | 结果可复现？ | 窗口何时结束 | 代价 |
| --- | --- | --- | --- | --- |
| 处理时间 processing time | 算子所在机器时钟 | ❌ 取决于到达速度 | 墙上时间到点 | 最低延迟、最简单 |
| 事件时间 event time | 记录自带时间戳 | ✅ 重放同输入同结果 | 水位线越过窗口末尾 | 需分配时间戳 + 生成水位线 + 处理迟到 |
| 摄入时间 ingestion time ⚠️ | source 进入 Flink 时打戳 | 部分可复现 | 同事件时间 | 介于两者之间；原书是否展开未核实 |

**一致性模型对照**

| 故障类型 | 后果 | 需要的机制 |
| --- | --- | --- |
| 任务故障 task failure（进程/机器挂） | 状态丢失、部分结果未写出 | 周期性快照（检查点）+ 从快照恢复 + 源重放 |
| 网络分区 network partition | 子任务间不可达 | 超时 + HA（ZooKeeper）+ 重新部署 |
| 存储故障 storage failure | 快照读写失败 | 快照存到外部可靠存储（HDFS/S3），检查点目录可配（09 章） |

| 结果保障 | 含义 | Flink 的实现路径 |
| --- | --- | --- |
| 至多一次 at-most-once | 不回滚、不重试 | 关闭检查点 |
| 至少一次 at-least-once | 恢复后重放，可能重复 | 检查点 + 源重放，不做去重 |
| 恰好一次（内部）exactly-once | 状态与结果不重不漏 | 一致性检查点（Chandy-Lamport 变体）+ 全局回滚（03/12 章） |
| 端到端恰好一次 end-to-end | 含外部系统 | 恰好一次内部 + **可重放源 + 幂等或事务性汇**（08 章） |

关键认知：**「恰好一次」不是一条魔法开关**，它是「快照 + 重放 + 输出幂等/事务」三段合成的性质。
把 `EXACTLY_ONCE` 打开而 sink 不支持事务，端到端就仍然是至少一次——这是新手最常见的一次真实事故。

## 版本与兼容性

- Flink 1.7 需显式 `env.setStreamTimeCharacteristic(TimeCharacteristic.EventTime)`；
  **该 API 在 1.12 起废弃并被移除**，新版由水位线策略（`WatermarkStrategy`）决定时间语义 ⚠️ 版本细节以官方迁移文档为准。
- 旧 `SourceFunction`/`SinkFunction`（本书通篇使用）已被 FLIP-27 `Source` / 新 `Sink` API 取代；
  概念（分区、水位线在 source 处生成、两阶段提交）不变。
- 「非对齐检查点（unaligned checkpoint）」是 1.11 引入的、针对反压场景的机制，**本书未覆盖** ⚠️（12 补编给出定位说明）。
- `rescale()` 语义（本地轮询）与「hot-function update / adaptive scaling」等现代特性无关，勿混。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「并行度越大越好」 | 并行度提高会带来更多 channel、更多缓冲、更多状态分片；小数据下反而变慢且检查点更重 |
| 「keyBy 之后数据才分流，所以 keyBy 是个算子」 | `keyBy` 只是分区声明 + 逻辑边界，本身不处理数据；它产出 `KeyedStream` 这个类型变化 |
| 「处理时间结果差所以不能用」 | 只要业务只关心「多久算一次」（如秒级限频）而非「事件发生的时刻」，处理时间最省 |
| 「水位线保证不丢迟到数据」 | 水位线只是**猜测**（基于乱序界）；真正的兜底是 `allowedLateness` + 侧输出（06 章） |
| 「开了 exactly-once 就端到端 exactly-once」 | 内部恰好一次 ≠ 端到端；还需可重放源与幂等/事务汇（08 章） |
| 「反压是 Kafka 的问题」 | 反压源于作业内部最慢子任务；Kafka lag 只是末端表现（10 章定位法） |
| 「Flink 图 = SQL 执行计划」 | dataflow 图是作业的静态拓扑；关系层的逻辑/物理计划在其上另有一层（13 补编） |
