## 核心概念速览（中英对照）

- **部署模式** — deployment mode：作业与集群生命周期如何绑定的三种取向——per-job ⚠️（已废弃）、session、application。
- **会话模式** — session mode：先起一个长驻集群，再往里提交多个作业；资源固定、隔离弱、提交快。
- **应用模式** — application mode：一个容器/集群只跑一个作业，jar 在集群侧解析；资源按需、隔离强。
- **独立集群** — standalone cluster：手工维护 `masters`/`workers` 文件 + `start-cluster.sh` 的最朴素形态。
- **任务槽** — task slot：TaskManager 的资源容器；槽数 = 该 TM 能承载的 subtask 数上限。
- **槽共享** — slot sharing：不同算子的 subtask 可共用一个槽，使「并行度不必等于槽数」，并让慢算子不独占资源（10 章）。
- **高可用** — high availability (HA)：JobManager 故障后由 ZooKeeper 选主并从持久化元数据恢复作业。
- **leader 选举与元数据存储** — leader election / storageDir：`high-availability.storageDir` 存放作业图与检查点元数据。
- **YARN 集成** — YARN integration：`flink yarn session` / `-t yarn-application`，容器化申请资源、队列与抢占交给 YARN。
- **Kubernetes 集成** — Kubernetes integration：本书时代多为「YARN on K8s / 手工镜像」；native K8s 集成后续版本才有 ⚠️。
- **网络内存** — network memory：`taskmanager.memory.fraction`/`network` 相关项，决定 channel 缓冲与吞吐上限（02 章）。
- **托管内存** — managed memory：RocksDB 与批排序用的堆外预算 ⚠️（1.10 新内存模型才成型，本书为旧模型）。
- **类加载顺序** — classloader resolve order：`child-first`（用户 jar 优先，默认）/`parent-first`，依赖冲突第一开关（04 章）。
- **检查点目录** — `state.checkpoints.dir` / `state.savepoints.dir`：快照与保存点落地的持久存储（HDFS/S3）。

## 核心精讲

### 9.1 部署模式与作业生命周期

| 模式 | 集群由谁创建 | jar 解析位置 | 提交退出后作业 | 适合 |
| --- | --- | --- | --- | --- |
| session | 预先手工/脚本起 | 客户端上传 | 是（在集群里跑） | 开发调试、多短作业共享 |
| per-job ⚠️ | 客户端起、作业结束销毁 | 客户端上传 | 客户端需常驻（1.15 移除该模式 ⚠️） | 本书时代的生产隔离 |
| application | 集群侧创建并跑主方法 | **集群侧**（省上传与大 jar 序列化） | 是 | 云原生生产、每作业独占 |

选择判据：**是否需要「作业之间互不影响资源」**。需要 → application（或独立作业独占 YARN 队列）；
不需要、追求秒级提交 → session。

### 9.2 独立集群最小配置 🔧

```yaml
# 🔧 conf/flink-conf.yaml（本书时代键名；新版为 config.yaml + 分层键 ⚠️）
jobmanager.rpc.address: jobmanager
jobmanager.rpc.port: 6123
jobmanager.memory.process.size: 1600m        # 旧版为 jobmanager.heap.mb ⚠️
taskmanager.memory.process.size: 1728m
taskmanager.numberOfTaskSlots: 2
parallelism.default: 2
rest.port: 8081
state.checkpoints.dir: hdfs:///flink/checkpoints
state.savepoints.dir: hdfs:///flink/savepoints
execution.checkpointing.interval: 30000
execution.checkpointing.mode: EXACTLY_ONCE
```

```bash
# 🔧 起停与提交
bin/start-cluster.sh                # 读 conf/masters 与 conf/workers
bin/flink run -d -c com.example.Job ./job.jar
bin/flink list ; bin/flink cancel <jobId>
bin/flink stop --type native -s ./savepoints <jobId>     # ⚠️ 参数形态随版本变化，见 10 章
bin/stop-cluster.sh
```

### 9.3 YARN：三种用法与退出码

```bash
# 🔧 会话集群
bin/yarn-session.sh -n 8 -jm 1024m -tm 4096m -d
# 🔧 直接提交（application 模式，1.10+ 成熟；本书时代多用 per-job）
bin/flink run -t yarn-application -Djobmanager.memory.process.size=1024m job.jar
bin/flink run -t yarn-per-job -d job.jar                  # ⚠️ per-job 已废弃
# 🔧 查看/停止
bin/flink list -r ; yarn application -kill <app-id>
```

要点：YARN 模式下 `parallelism.default`/槽数不再限制总资源（由 YARN 容器申请），
但**最大并行度**受队列与容器上限约束；作业卡在 `created`/`scheduled` 先看 YARN 队列剩余。

### 9.4 HA：三件套缺一不可

```yaml
# 🔧 flink-conf.yaml（ZooKeeper HA）
high-availability: zookeeper
high-availability.zookeeper.quorum: zk1:2181,zk2:2181,zk3:2181
high-availability.storageDir: hdfs:///flink/ha/         # 作业图/checkpoint 元数据（不含状态本体）
state.checkpoints.dir: hdfs:///flink/checkpoints        # 状态本体，必须也在共享存储
recovery.task-manager.process-deployment ...            # ⚠️ 细项随版本差异大，此处不展开
```

三段语义：**ZooKeeper 选新 JobManager → 从 storageDir 读作业图 → 从最近的检查点恢复状态**。
如果只配 ZK 而检查点在本地盘，TM 换机后仍然无状态可用。

### 9.5 内存与网络缓冲的账（本书时代模型）

| 区域 | 配置 | 影响 |
| --- | --- | --- |
| JVM 堆 | `taskmanager.memory.flink.size`（旧 `taskmanager.heap.mb`）⚠️ | 对象、堆内状态、用户代码 |
| 网络 | `taskmanager.memory.fraction` + `taskmanager.network.memory.min/max`、`buffers-per-channel` | channel 数 = Σ(上游并行度 × 下游并行度)（非链化边）；不足直接限吞吐 |
| 堆外/RocksDB | `taskmanager.memory.managed.fraction`、`state.backend.rocksdb.memory.managed` | RocksDB 容量与磁盘 IO |
| 元空间/开销 | `jobmanager.memory.jvm-metaspace.size`、off-heap | 类加载器泄漏（大量 jar 热部署）常打爆 metaspace |

**磁盘**：RocksDB 需要本地 SSD 或足够 IOPS 的盘；多 TM 同机时给不同进程不同 `localdir`，
否则 IO 互相拖累（03 章 3.5、10 章调优）。

### 9.6 类加载与依赖冲突 🔧

```yaml
classloader.resolve-order: child-first        # 默认：用户 jar 优先
classloader.parent-first-patterns.default: java.;scala.;org.apache.flink.;com.esotericsoftware.kryo;...
classloader.check-leaked-classloader: true    # 泄漏检测，关闭会掩盖问题 ⚠️ 默认值随版本变化
```

排障三步（原书与社区共识）：

1. 出现 `ClassCastException: X cannot be cast to X` → 同名类被两个加载器加载 → 检查用户 jar 是否打了 `flink-dist`（04 章）。
2. 连接器找不到驱动类 → 把驱动放 `plugins/` 目录（1.13 起插件机制成型 ⚠️）或打进 fat jar。
3. Scala 版本不匹配（2.11/2.12 混用）→ `NoClassDefFoundError scala/...` → 统一 `scala.binary.version`。

### 9.7 检查点与状态后端的配置面

```yaml
execution.checkpointing.interval: 30000
execution.checkpointing.mode: EXACTLY_ONCE
execution.checkpointing.min-pause: 10000
execution.checkpointing.max-concurrent-checkpoints: 1
execution.checkpointing.timeout: 600000
execution.checkpointing.tolerable-failed-checkpoints: 3
execution.checkpointing.externalized-checkpoint-retention: RETAIN_ON_CANCELLATION
state.backend: rocksdb
state.backend.incremental: true
state.checkpoints.num-retained: 3
```

（键名以对应版本文档为准 ⚠️；本书时代部分键为 `state.checkpointing.*` 与代码内配置。）

## 版本与兼容性

- **配置体系换代**：`flink-conf.yaml` → `config.yaml`（1.18+ 引入、2.0 成为默认）⚠️；
  本目录所有键名以「语义正确」为主，落生产前请对照所用版本官方页。
- **内存模型**：1.10 引入「Billed/Process size + 分层内存」模型，本书时代的 `taskmanager.heap.mb` 已失效 ⚠️。
- **per-job 模式**：1.15 废弃、2.0 移除 ⚠️；native Kubernetes 支持 1.10 起，`Kubernetes Operator` 独立仓库。
- **安全性**：本书仅提纲（SASL/Kerberos、REST 认证）；生产加密与认证在后续版本才成体系 ⚠️。
- ZooKeeper 依赖版本与独立/内嵌 ZK 的取舍随版本变化 ⚠️。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「槽数 = 并行度」 | 槽共享让一个槽承载不同算子的多个 subtask；所需槽数 ≈ 作业的最大并行度（同作业内） |
| 「session 模式最省事所以生产就用它」 | 一个坏作业占满槽会拖垮所有共享作业；隔离性差、版本升级要重启整个集群 |
| 「不配 HA 也能容错」 | 检查点解决 TM/任务故障；JobManager 挂掉而无 HA 时作业彻底丢失（03 章） |
| 「storageDir 就是检查点目录」 | storageDir 存元数据（作业图、leader 信息），状态本体在 `state.checkpoints.dir` |
| 「给 TaskManager 越多内存越好」 | 堆过大导致 GC 停顿拉长，处理延迟抖动；状态大应走 RocksDB + 托管内存 |
| 「网络缓冲不够只是慢一点」 | 会表现为持续反压 + 检查点对齐超时失败，看起来像「检查点不稳定」 |
| 「metaspace OOM 是内存配小了」 | 多为反复提交/热部署导致的类加载器泄漏（04 章 fat jar、`check-leaked-classloader`） |
| 「Docker 部署等于云原生部署」 | 容器化不等于有 K8s 编排/重启策略/持久卷；RocksDB 本地盘在容器里需要考虑卷与生命周期 ⚠️ |
