## 核心概念速览（中英对照）

- **保存点** — savepoint：人工触发的、带规范目录格式的全局快照，用于升级、重缩放、迁移与回滚。
- **停止并保存点** — stop with savepoint：按排水（drain）语义结束作业：处理完在途事件、水位线推到最大、再落保存点。
- **排水** — drain：让所有算子收到「时间结束」信号，从而输出最终窗口结果，避免升级时丢尾窗。
- **从保存点恢复** — restore from savepoint：`-s <path>`；并行度、算子拓扑可在规定范围内变化（07 章状态兼容）。
- **允许非恢复状态** — `--allowNonRestoredState`：丢弃新拓扑中不存在算子的旧状态（危险开关）。
- **状态处理器 API** — StateProcessorAPI ⚠️：程序化读写/迁移保存点的接口（书中未逐条核实）。
- **指标系统** — metric system：计数器/仪表/直方图/水位（counter/gauge/meter/histogram）+ 可插拔 reporter（Prometheus 等）。
- **延迟标记** — latency markers：周期性注入并统计穿越全图时间的机制（`metrics.latency.interval`），代价不小。
- **水位线指标** — `currentInputWatermark` / `watermarkLag`：判断「事件时间是否卡住」的第一指标。
- **端到端延迟** — end-to-end latency / business lag：事件时间戳与处理时刻之差，比「作业是否 RUNNING」更有意义。
- **反压面板** — backpressure monitoring：UI 按 subtask 采样 busy/idle 比例给出 high/ok/low 判定。
- **检查点看板** — checkpoint history：每次对齐时间、快照时间、上传大小、状态增量，是调优的主数据源。
- **REST API** — WebRestAPI：`/jobs`、`/jobs/:id/savepoints`、`/jobs/:id/stop`、`/checkpoints`、`/metrics`，自动化运维的入口。
- **任务链接控制** — operator chaining / `disableChaining` / slot sharing group：调度层的两根杠杆。

## 核心精讲

### 10.1 生命周期命令（含新旧形态差异）🔧

```bash
# 🔧 提交并分离
bin/flink run -d -m <jobmanager> -c com.example.Job job.jar
# 🔧 人工保存点（先拿 job id）
bin/flink savepoint <jobId> file:///flink/savepoints
# 🔧 无损升级：停止并落点（drain 让尾窗输出）
bin/flink stop --savepointPath file:///flink/savepoints <jobId>
# 🔧 从保存点重启 + 改并行度
bin/flink run -d -s file:///flink/savepoints/<dir> --parallelism 8 job.jar
# 🔧 旧命令（rescale 已废弃，改由 stop + run -s 完成 ⚠️）
bin/flink rescale <jobId> --parallelism 8 <savepointPath>
# 🔧 取消（状态不回滚，只是停）
bin/flink cancel -s file:///flink/savepoints/<dir> <jobId>
```

**判据**：`cancel` = 立即停止（可能丢掉未输出结果）；`stop --type native -s` = 有序排水并留下可用保存点。
升级/迁移一律用后者，这是 10.2 流程能成立的前提。

### 10.2 保存点升级的标准流程

```
1. 触发保存点（或 stop-with-savepoint）→ 得到 <path>，并在作业文档里登记
2. 停作业（若第 1 步用的是 savepoint，则再 cancel）
3. 变更：改并行度 / 改代码（保持 uid 与状态名，见 07 章）/ 换 Flink 版本
4. `run -s <path>` 启动新版本；观察 Web UI：
   - 各算子接收到的状态是否恢复（"Restored state from savepoint" 日志）
   - 记录数是否从 0 起步（若为 0 说明源没接上而非状态丢）
   - 检查点是否连续成功
5. 失败退回：再用同一 <path> 起旧版本 jar
```

风险开关 `--allowNonRestoredState`：只有你确认「那个算子的状态可以丢」时才用，
否则等于静默删除一部分业务状态（07 章 7.7）。

### 10.3 REST 自动化 🔧

```bash
# 🔧 上传 jar 并运行
curl -s -X POST --form "jar=@job.jar" http://jm:8081/jars/upload
curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"entryClass":"com.example.Job","programArgs":"--ckpt 30000"}' \
  http://jm:8081/jars/<jar-id>/run
# 🔧 触发保存点并轮询进度
curl -s -X POST -H 'Content-Type: application/json' -d '{"target-directory":"file:///flink/sp","cancel-job":true}' \
  http://jm:8081/jobs/<job-id>/savepoints
curl -s http://jm:8081/jobs/<job-id>/savepoints/<trigger-id>
# 🔧 读指标（先列再取）
curl -s http://jm:8081/jobs/<job-id>/metrics | jq '.[] | [.id,.name]'
curl -s "http://jm:8081/jobs/<job-id>/subtasks/metrics?get=numRecordsInPerSecond,currentInputWatermark&agg=min,max"
```

REST 版本前缀随大版本变化（`/v1`、`/v2` ⚠️），自动化脚本要把路径配置化而不是硬编码。

### 10.4 调度层的两根杠杆

| 杠杆 | 做什么 | 什么时候动 |
| --- | --- | --- |
| 链化 `disableOperatorChaining()` / `disableChaining()` | 拆掉算子链 → 每个算子独立线程，延迟更平滑但序列化/上下文切换增加 | 单算子内需要独立 CPU 预算、或要看清每段耗时（调试）时拆 |
| 槽共享组 `slotSharingGroup("heavy")` | 把重算子集中到独占槽，轻算子共槽 | 某算子（如外部 IO、大状态窗口）与别的算子争抢同一线程导致周期性尖峰 |
| 非本地调度/`shuffle` 分布 | 影响跨 TM 流量 | 网络成为瓶颈时减少跨节点 shuffle（02 章） |

### 10.5 检查点调优顺序（本目录的推荐流程）

1. **先看形状**：Web UI → Checkpoints → Summary：
   `Alignment Duration`（等屏障）/`Async Duration`（上传快照）/`Checkpointed Data Size`（全量或增量）。
2. **对齐时间长** → 说明有反压或并行度过高：先治反压（找最慢 subtask），
   再考虑 `max-concurrent-checkpoints=1` + `min-pause`，或 1.11+ 的**非对齐检查点** ⚠️（本书未覆盖，见 12 补编）。
3. **上传慢** → 换 RocksDB + `state.backend.incremental: true`；或减少不必要状态（07 章 7.2）。
4. **状态总量大** → 检查是否缺 TTL、是否 `ListState` 在缓冲全窗口（06 章）。
5. **间隔选择**：恢复时间目标 RTO 决定下限（最多丢一个间隔的数据需重放），
   作业吞吐决定上限（快照开销约占处理时间的比例 ⚠️ 具体比例依状态大小）；
   典型起点 30s–2min，大状态可到 5–10min 并配合增量。
6. **失败恢复**：`tolerable-failed-checkpoints`、`restart-strategy`（fixed-delay / failure-rate / exponential-delay）
   与 `execution.checkpointing.externalized-checkpoint-retention` 三者配套，否则「作业重启后无点可恢」。

### 10.6 监控面板：四类指标缺一不可

| 类别 | 关键指标 | 告警判据（示例口径 ⚠️ 阈值按业务定） |
| --- | --- | --- |
| 时间进度 | `currentInputWatermark`、watermark 与 now 的差 | 差值持续增长 = 时间卡住（源空闲/分区倾斜/上游延迟） |
| 吞吐 | `numRecordsIn/OutPerSecond`、每 subtask 记录数分布 | 分布极不均 = 键倾斜（02/05 章） |
| 反压 | busy/idle 比、`inPoolUsage`/`outPoolUsage` | 某段持续 100% 即瓶颈；上游 buffer 满 |
| 容错 | 检查点成功率、耗时、失败原因、状态大小趋势 | 大小单调上涨 = 状态泄漏（07 章） |

🔧 业务延迟的透明做法（把事件时间戳带出来）：

```java
// 🔧 在汇侧计算「处理时刻 - 事件时刻」并注册为 gauge/meter
public class LagSink extends RichSinkFunction<Event> {
  private transient Gauge<Long> lag;
  @Override public void open(Configuration c) {
    lag = getRuntimeContext().getMetricGroup().gauge("eventLagMs",
            new ThreadLocalGauge<>());
  }
  @Override public void invoke(Event e, Context ctx) {
    ThreadLocalGauge.set(System.currentTimeMillis() - e.ts);   // 各子任务分别记录，聚合看 max
  }
}
```

指标上报（Prometheus reporter）配置示意 ⚠️ 键名随版本：

```yaml
metrics.reporter.prom.factory.class: org.apache.flink.metrics.prometheus.PrometheusReporterFactory
metrics.reporter.prom.port: 9249-9259
metrics.latency.interval: 60000          # 延迟标记开销不小，生产上常关闭而改用业务延迟指标
```

### 10.7 日志与定位路径

```
TaskManager 日志：log4j 分级（INFO→DEBUG 定位单键问题），文件名含 TM id；
按「jobId → 作业图 → 哪个算子 → subtask index → 哪个 TM」链路定位；
stdout（.out）与 log 分家：print() 与 System.out 走 .out，日志框架走 .log；
开启 `jobmanager.execution.failover-strategy: region`（局部恢复）⚠️ 默认值与名称以版本为准。
```

## 版本与兼容性

- `bin/flink rescale` 已废弃（由 stop-with-savepoint + run -s 取代）⚠️。
- Web UI 的反压采样与指标名多次调整（1.13+ 的 `/subtasks/metrics` 聚合参数形态不同 ⚠️）。
- 延迟标记（latency markers）在新版仍可用但官方建议改用业务时间戳指标 ⚠️。
- 非对齐检查点、`local recovery`、`checkpoint after all task finish` 等均晚于本书 ⚠️（12 补编定位说明）。
- 2.x 的 REST 路径与 `config.yaml` 键名有变化 ⚠️；本目录命令以「可核对语义」为准。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「作业 RUNNING 就说明健康」 | RUNNING + 水位线停滞 + 输出无更新 是典型「假活」，必须看时间进度指标 |
| 「升级用 cancel 也行」 | cancel 不排水，尾窗/未触发计时器的结果丢失；升级要 `stop --savepointPath`（drain） |
| 「加大 `execution.checkpointing.interval` 就稳了」 | 间隔变大后单次状态更多、恢复需重放更多事件；治标不治本，先治反压与状态量 |
| 「`--allowNonRestoredState` 是兼容性开关」 | 它是「丢弃状态」开关，误用等于删数据 |
| 「并行度加倍就一定更快」 | 若瓶颈是外部系统（sink）或单键热点，加倍只会增加检查点与 buffer 开销 |
| 「打开 latency markers 很便宜」 | 标记要穿过全图并聚合，生产大流量作业常因此可见延迟上涨 |
| 「RocksDB 增量检查点没有代价」 | 增量小、但恢复需要合并 SST 列表且更依赖存储一致性；`num-retained` 要留出恢复窗口 |
| 「日志级别 DEBUG 只是慢一点」 | 高频路径 DEBUG 会显著拖慢并刷爆磁盘，容器里可能直接触发 IO 反压 |
