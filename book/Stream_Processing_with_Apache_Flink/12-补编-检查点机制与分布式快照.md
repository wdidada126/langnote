## 核心概念速览（中英对照）

- **分布式快照** — distributed snapshot：在不暂停全局计算的前提下，采集一个「一致的全局状态切面」。
- **一致切面** — consistent cut：若某消息的接收事件在切面内，则其发送事件也必须在切面内；快照正确性的充要条件。
- **检查点** — checkpoint：Flink 中周期性、由 JobManager 驱动、用于故障恢复的分布式快照。
- **屏障** — barrier：不带数据、只标记位置的流内控制事件；屏障把状态流切成「属于本次快照」与「属于下次」。
- **屏障对齐** — barrier alignment：多输入算子等所有输入的同一屏障到齐后才快照，保证恰好一次语义。
- **非对齐检查点** — unaligned checkpoint ⚠️（1.11 引入，本书未覆盖）：不等对齐，改为把在途缓冲数据一并快照。
- **异步快照** — asynchronous snapshot：算子先把状态拷成可上传的一致性副本，上传在后台线程完成，不阻塞处理。
- **增量检查点** — incremental checkpoint：RocksDB 后端只上传新增/变化的 SST，避免每次全量重写。
- **检查点协调器** — CheckpointCoordinator：JobManager 侧触发、计时、确认、决定提交或回滚的组件。
- **最小完成水位** — lowest committed checkpoint id：任一算子失败即整个作业回滚到「所有算子都完成」的那一次。
- **源重放** — source replay：把源恢复到快照里记录的 offset，使快照边界之前的数据不重复不遗漏。
- **两阶段提交汇** — 2PC sink：把外部提交推迟到检查点成功后，让外部世界共享同一次原子性。
- **保存点** — savepoint：人为触发、格式规范且跨版本可移植的检查点，服务于运维而非容错。
- **有效一次** — effectively-once：语义目标（结果等价一次处理），可由幂等或事务实现，不必执着于「恰好一次」字面。

## 核心精讲

### 12.1 问题设定：三件事一起恢复

批处理引擎（以及 Flink 的 Dataflow/Spark 类血脉）恢复靠**重算**：血缘允许从输入重建 RDD。
有状态流处理不行——状态是**跨事件累积**的，重算意味着从头重放整个历史，代价不可接受。
所以必须回答：

1. **算子状态**如何在一个「逻辑时刻」被整体保存？
2. **在途消息**（已发出未被处理）如何处置，才能既不在快照里、又不在重放里出现两次？
3. **外部副作用**（已经写进 Kafka/数据库的行）如何撤回或推迟，才不违反「恰好一次」？

原书第 2 章把这三件事归到「一致性模型」的讨论里，第 3 章给出 Flink 的答案（1、2 用快照 + 回滚，
3 交给第 8 章的幂等/事务汇）。

### 12.2 Chandy-Lamport：不停世界的一致切面

原始论文的机制（本目录口径，非论文原文逐字 ⚠️）：

- **前提假设**：通道 FIFO、消息可丢失但不会乱序、进程可崩溃但不做拜占庭行为。
- **动作**：某进程发起快照 → 记录自身状态 → **在自己的每条出边上发送 marker**；
  收到某入边的第一个 marker 时：若自己尚未快照，则记录自身状态并把 marker 转发到所有出边，
  同时把「该通道上从此刻起到收到 marker 之间收到的消息」记为该通道的状态；
  若自己已快照，则继续处理并把 marker 转发，通道状态按已定义规则记录。
- **结论**：所有进程与通道状态合起来构成一个**一致切面**——它等价于某个真实发生过的全局瞬时状态，
  于是可以从这个「虚拟瞬时」恢复。
- **关键性质**：无需全局时钟、无需停机（非阻塞）；代价是快照描述的并非「采集结束时」的状态，
  而是某个介于开始与结束之间的瞬时。

一句话记忆：**marker 把「发送/接收」这条因果边切断，切面自动一致。**

### 12.3 Flink 的变体：改了哪四点

| 论文做法 | Flink 做法 | 为什么改 |
| --- | --- | --- |
| marker 是独立的控制消息，与数据并行传递 | **barrier 插在数据流里**，与记录同通道同序 | 复用 FIFO 通道保证顺序；省去带外同步 |
| 快照含通道内容（记录在途消息） | **不等在途消息**：靠对齐把在途数据交给接收方先处理完再快照 | 通道缓冲可能很大，快照在途数据代价高 ⚠️（非对齐检查点正是把这条改回去了，1.11+） |
| 进程状态是原子的整体 | 状态按 **key group 分片**、由状态后端异步上传到外部分布式存储 | 让恢复可换机器、可扩缩容（07 章） |
| 只谈进程与通道 | 显式纳入 **source（重放）与 sink（幂等/2PC）** | 外部系统不在图内，快照无法覆盖它们（08 章） |
| 无中心协调 | **JobManager 中心化触发与提交**，失败则全局回滚到最小完成水位 | 流作业需要所有分区在同一逻辑时刻，任一失败即整体无效 |

### 12.4 一次检查点的完整时序 🔧

```
t0  CheckpointCoordinator: trigger checkpoint n (id=n)
      └─ 向所有 source subtask 注入 barrier(n)
t1  source 处理完 barrier 之前的记录 → 把「offset + 状态」异步快照 → 转发 barrier(n)
t2  中间算子：对每个输入通道等 barrier(n)（对齐）
      ├─ 对齐期间到达的其它通道数据：**照常处理**（计入 n+1 的切面，不计入 n）⚠️ 实现细节以版本代码为准
      └─ 全部到齐 → 快照状态 → 上传 → 转发 barrier(n)
t3  sink：快照（含未提交事务标识）→ ack
t4  所有 ack → coordinator 标记 n 完成 → 向算子发 notifyCheckpointComplete(n) → sink 提交事务
失败：任一子任务失败 / 超时 → 丢弃 n → 从最近的完成检查点恢复**所有**算子 → source 回到快照中的 offset
```

**恢复语义的完整链条**（本目录推荐背诵）：
`最近完成检查点的全局状态 + 源 offset + 未提交事务` → 回滚 → 从 offset 重放 → 幂等/事务保证输出侧不重复。

### 12.5 对齐为什么是正确性要求（用一个反例说明）

设算子 X 有两个输入通道，各来自键相同的一条流；检查点 n 的 barrier 在 A 通道先到：

```
不对齐的做法：收到 A 的 barrier 就立刻快照 → 快照里的状态已含 A 的未来数据，
             而 B 通道的历史数据尚未处理。
恢复时：A 从 offset 重放到「快照点」→ A 的那批数据被处理两次；B 的数据只处理一次。
结果：状态与真实历史不等价 → 破坏 exactly-once。
```

对齐的实质：**用「等待」换「同一逻辑时刻」**，代价是等待时间等于最慢通道的到达延迟。

### 12.6 代价与四条出路

| 症状 | 根因 | 出路 |
| --- | --- | --- |
| 检查点耗时随反压飙升 | 对齐等待被下游拖长 | 治反压；增大 `min-pause`；或用非对齐检查点 ⚠️；或降 `CheckpointingMode` 至 AT_LEAST_ONCE |
| 大状态上传慢、超时 | 全量快照 + 远端存储 | RocksDB + `state.backend.incremental: true`（07/09 章） |
| 频繁小检查点挤占吞吐 | 快照与处理抢 CPU/带宽 | 拉长间隔；`max-concurrent-checkpoints=1` |
| 恢复后重复计算太多 | 间隔过长导致重放大 | 缩短间隔 + 保证源可重放（08 章）；RTO/RPO 权衡要显式写进 SLO |

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「Flink 就是照搬 Chandy-Lamport」 | 骨架同源，但 barrier 随流、异步快照、key group 分片、外部源汇纳入方案这四点都是为流处理改的（12.3） |
| 「快照记录的是触发那一刻的状态」 | 它记录的是一个等价于某个真实瞬时的**一致切面**，位置在触发与完成之间 |
| 「非对齐检查点更快所以没有代价」 | 代价转为「快照包含在途缓冲」，状态变大、恢复变慢、且某些算子语义限制更多 ⚠️ |
| 「检查点失败就会丢数据」 | 失败则回滚到上一个完成点并重放，丢的是「两次检查点之间的处理进度」，不是数据 |
| 「savepoint 与 checkpoint 只是触发方式不同」 | 还有格式与生命周期差别：savepoint 面向跨版本/跨作业移植，checkpoint 面向本作业自动恢复（10 章） |
| 「AT_LEAST_ONCE 模式一定不安全」 | 它放弃的是「状态不重复」，若所有状态更新幂等则结果仍等价；这是工程权衡不是错误 |
| 「检查点覆盖外部系统写入」 | 外部系统不在图内，必须靠源重放 + 汇幂等/事务补齐（08 章 8.1） |
