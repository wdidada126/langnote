## 三条阅读主线

1. **两大支柱线（时间 + 状态）**：`06` → `07` → `12`。本书真正的思想密度全在这两章：
   时间决定「什么时候算得出正确结果」，状态决定「结果要多大代价才能持续更新」。
2. **API 分层线（DataStream → Table/SQL）**：`05` → `11` → `13`。
   原书第 11 章只给了 Table/SQL 的引子，13 补编把「表 = 变更流」这条语义主线补完（含回撤/upsert）。
3. **工程落地线（写外部系统 → 部署 → 运维）**：`08` → `09` → `10`。
   端到端恰好一次、保存点升级、反压与检查点调优，是这本书区别于「API 手册」的部分。

**最短上手路径**：`04` → `05` → `06`（前 3 节）→ `08`（Kafka 读写）→ `09`（跑起来）。

## 读完应该能回答的十个问题

1. 一个作业什么时候值得有状态，什么时候该把状态推给外部 KV？（`01`、`07`）
2. 处理时间、事件时间、合并时间各自的正确性与代价在哪？（`02`、`06`）
3. 为什么水位线取的是「所有输入的最小值」？（`03`、`06`）
4. 同一业务，`rebalance`、`keyBy`、`broadcast` 分别会把状态切成什么形状？（`05`）
5. 加算子链、调槽共享为什么能改变吞吐与延迟？（`02`、`10`）
6. 屏障对齐阻塞了什么？不阻塞的代价是什么？（`03`、`12`）
7. RocksDB 后端 + 增量检查点在什么状态下才划算？（`07`、`09`）
8. 端到端恰好一次的三前提是什么？（`08`）
9. 改并行度、改拓扑、换版本时，状态能不能活下来？（`07`、`10`）
10. 一段作业该写 DataStream 还是 Table/SQL，什么时候退回 `ProcessFunction`？（`11`、`13`）

| 键控流 | keyed stream | `keyBy` 后的流；只有它按键分区，才允许键控状态与窗口 | 05 |

| 状态 | state | 算子在事件之间保留、并参与检查点的中间结果 | 01、02、07 |
| 键控状态 | keyed state | 随当前记录所属键自动切换的状态，只能在 `KeyedStream` 上使用 | 03、07 |
| 算子状态 | operator state | 属于算子实例而非键的状态，用 `ListState` 表达并按策略重分布 | 03、07 |
| 状态原语 | state primitive | `ValueState/ListState/MapState/ReducingState/AggregatingState` 五种声明式接口 | 07 |
| 状态 TTL | StateTtlConfig | 给键控状态加过期与清理策略，防状态泄漏的第一工具 | 07 |

| 屏障对齐 | barrier alignment | 多输入算子须等各通道同一屏障到齐再快照，避免恢复后重复/丢失 | 03、12 |
| 异步 / 增量快照 | asynchronous / incremental snapshot | 后台线程上传一致性副本；RocksDB 只上传变化的 SST | 03、07、12 |
| 恰好一次 | exactly-once | 每条事件对状态的影响恰好一次；由可重放源 + 快照 + 幂等/事务汇合成 | 02、08、12 |
