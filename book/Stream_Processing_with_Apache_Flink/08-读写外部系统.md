## 核心概念速览（中英对照）

- **连接器** — connector：把 Flink 与外部系统（消息队列、KV、文件、数据库）对接的源/汇实现。
- **端到端恰好一次** — end-to-end exactly-once：内部快照之外，还要求源可重放、汇幂等或事务化。
- **可重放源** — replayable source：能按记录的位置/偏移重新读取的源（Kafka offset、文件路径 + 行号）。
- **位置** — offset / position：源里「读到哪了」的标识，必须进算子状态才能随检查点一起恢复。
- **幂等写** — idempotent write：同一结果重复写不改变最终状态（按主键 upsert 到 Cassandra/ES/Redis）。
- **事务性写** — transactional write：外部系统支持提交/中止，且提交与检查点原子对齐。
- **两阶段提交** — two-phase commit (2PC)：预提交随检查点快照、检查点成功后正式提交；Flink 汇侧的标准做法。
- **`TwoPhaseCommitSinkFunction`** — 事务汇基类：把事务的生命周期挂到检查点三个阶段上（本书核心类）。
- **`StreamingFileSink`** — 流式文件汇：分桶（bucket）+ in-progress/pending/finished 三段状态文件，配 2PC 精确一次。
- **分桶** — bucket assigner / policy：决定记录写到哪个目录、何时关闭文件（滚动与提交时机）。
- **异步 I/O** — async I/O operator：把「等待外部响应」的线程阻塞换成回调/`CompletableFuture`，在不提并行度的前提下提高吞吐。
- **有序/无序输出** — ordered / unordered output mode：异步算子是否保持输入顺序，无序更快。
- **背压与异步容量** — capacity：异步算子在途请求上限，超过即反压（02 章）。
- **语义等级** — `FlinkKafkaProducer.Semantic`：`AT_LEAST_ONCE` / `AT_LEAST_EXACTLY_ONCE`（后者依赖 Kafka 事务与幂等 producer）。

## 核心精讲

### 8.1 端到端一致性的组合公式

```
端到端 exactly-once
  = 恰好一次的内部状态（检查点 + 对齐，03/12 章）
  + 源可重放且位置随检查点一起快照（offset 进算子状态）
  + 汇要么幂等，要么事务且提交与检查点原子绑定（2PC）
```

三个失败案例（生产上最常见）：

| 组合 | 结果 |
| --- | --- |
| 内部 exactly-once + 不可重放源（如 HTTP 拉取无位置记录） | 重启后事件缺失或重复，「精确一次」名不副实 |
| 内部 exactly-once + 普通 `addSink(jdbc)` | 恢复后重放 → 目标表出现重复行 |
| 汇开了事务但没设外部事务超时 | JobManager 崩溃留下悬挂事务，Kafka consumer 读不到也未提交（需 `transactional.id` 清理逻辑） |

### 8.2 幂等写 🔧

```java
// 🔧 按主键 upsert 到 Cassandra：重复执行同一条写不改变最终值
stream.keyBy(r -> r.id)
      .addSink(new CassandraSinkFunction("INSERT INTO t (id, v) VALUES (?, ?) USING TIMESTAMP ?"));
```

成立条件（原书论证的核心）：

- 写操作**只由记录本身决定**（不依赖「之前有没有写过」）；
- 多个写可交换顺序（同一 key 的两次写，后写覆盖 → 需要写入携带时间或版本）；
- 目标系统提供 upsert / insert-or-replace。

不适用：累加型写（`count = count + 1` 在数据库侧）——重复一次就多算一次，这类要么把累加放 Flink 状态里
（07 章），要么改用事务汇。

### 8.3 事务写：2PC 与检查点的三个阶段 🔧

```java
// 🔧 继承基类，把外部事务映射到检查点生命周期
public class KafkaTxSink extends TwoPhaseCommitSinkFunction<Event, KafkaTransaction, Void> { ... }
// 四个必须实现的钩子：
//   beginTransaction()        —— 每条记录所属事务的起点（或在 open 里开一个）
//   invoke(tx, value, ctx)    —— 写入但不提交（producer.send）
//   preCommit(tx)             —— 随检查点快照调用：flush + 等待可提交状态
//   commit(tx)                —— notifyCheckpointComplete 之后：真正提交
```

时序（与 12 补编的屏障流对应）：

```
屏障到达汇算子 → preCommit + 把事务标识写进状态快照 → 快照上传成功 → 屏障继续
     → JobManager 收到全部确认 → notifyCheckpointComplete(id) → commit(tx)
失败路径：超时/失败 → 回滚到上一检查点 → 状态里保存的未完成事务由恢复逻辑 abort
```

**要点**：提交发生在「检查点完成之后」，所以外部可见性有一个检查点间隔的延迟；
Kafka 事务的 `transaction.timeout.ms` 必须 **大于** 检查点间隔 + 快照耗时，否则事务被 broker 侧超时中止 ⚠️
（原书亦强调这一关系，具体默认值以版本文档为准）。

### 8.4 内置连接器清单（本书时代）

| 连接器 | 源 | 汇 | 一致性能力 |
| --- | --- | --- | --- |
| Kafka | `FlinkKafkaConsumer`（分区 offset 进算子状态） | `FlinkKafkaProducer`（`Semantic.EXACTLY_ONCE` 用事务） | 端到端可做到恰好一次 |
| 文件系统 | `readTextFile` / 监控目录 ⚠️ | `StreamingFileSink`（分桶 + pending 文件 rename） | 配 2PC 恰好一次；`in_progress` 依赖 checkpoint 提交 |
| Cassandra | ⚠️ 本书只讲汇 | `CassandraSink`（批式）/ 自定义（异步 driver） | 幂等 upsert |
| ElasticSearch/HBase/JDBC ⚠️ | 原书是否逐个展开未核实 | 多为至少一次（按 key 幂等可达一次效果） | 需自行保证幂等 |

### 8.5 自定义源：可重放 + 时间戳 🔧

```java
// 🔧 一个「可重置 + 自带水位线」的自定义源（骨架）
public class MyRescalableSource implements ParallelSourceFunction<Rec>, CheckpointedFunction {
    private transient ListState<Long> pos;      // 关键：位置进状态（07 章 7.3）
    private volatile long lastTs = Long.MIN_VALUE;
    private volatile long lastWm = Long.MIN_VALUE;

    @Override public void run(SourceContext<Rec> ctx) throws Exception {
        while (running) {
            Rec r = fetchFrom(pos.value());
            synchronized (ctx.getCheckpointLock()) {   // 与快照互斥：保证「发数据」与「记位置」原子
                lastTs = Math.max(lastTs, r.ts);
                ctx.collectWithTimestamp(r, r.ts);
                if (nowWall() - lastWm > 200) {        // 周期性水位线
                    lastWm = nowWall();
                    ctx.emitWatermark(new Watermark(lastTs - 5000));
                }
            }
        }
    }
}
```

三个细节值得背下来：

1. `getCheckpointLock()` 是**必须**的：屏障到达时会拿同一把锁快照，无锁则位置与发出记录不一致（丢/重）。
2. 在源里生成水位线（`SourceContext.emitWatermark`）与在下游 `assignTimestampsAndWatermarks` 二选一即可。
3. 并行源要处理「分区 → 子任务」的映射（Kafka 分区数与源并行度不匹配会造成空子任务卡水位线，06 章）。

### 8.6 自定义汇与异步 I/O 🔧

```java
// 🔧 异步查外部存储并富化（不阻塞算子线程）
DataStream<Enriched> enriched = AsyncDataStream.unorderedWait(
    keyed,
    new AsyncFunction<Req, Enriched>() {                  // 实现 AsyncFunction
        private transient AsyncClient client;             // driver 的异步客户端
        @Override public void open(Configuration c) { client = new AsyncClient(cfg); }
        @Override public void asyncInvoke(Req r, ResultFuture<Enriched> out) {
            CompletableFuture.supplyAsync(() -> client.get(r.key))
                .thenAccept(v -> out.complete(Collections.singletonList(new Enriched(r, v))));
        }
        @Override public void timeout(Req r, ResultFuture<Enriched> out) { out.complete(emptyList()); }
    },
    800, TimeUnit.MILLISECONDS,   // 超时
    100);                         // capacity：在途请求上限 → 反压点
```

选型：`orderedWait` 保序（下游依赖顺序时用）、`unorderedWait` 吞吐更高；
`capacity` 太小 → 吞吐受限，太大 → 外部系统被打爆 + 状态膨胀。

## 版本与兼容性

- 本书使用 `SourceFunction`/`SinkFunction`/`StreamingFileSink`/`FlinkKafkaConsumer/Producer`：
  现代 Flink 已转向 **FLIP-27 `Source` API**（`KafkaSource`）、**`FileSink`/新 `Sink` 接口**（`Sink2` → `Sink`）
  与 `flink-connector-kafka` 独立仓库发布 ⚠️ 版本号与迁移路径以官方 connector 文档为准。
- `TwoPhaseCommitSinkFunction` 在新 sink 接口下由 `Committer`/`SinkWriter` 分层表达 ⚠️。
- Kafka 精确一次依赖 broker 侧事务（Kafka ≥0.11）与幂等 producer；跨版本升级时注意 `transaction.timeout.ms` 上限（broker `max.transaction.timeout.ms` 默认 15min ⚠️ 数值未核实）。
- 原书的「Cassandra 汇」写法在 `flink-connector-cassandra` 中仍在维护但更新较慢 ⚠️。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「`Semantic.EXACTLY_ONCE` 一开就完事」 | 还需 Kafka broker ≥0.11、事务超时 > 检查点周期、consumer 用 `read_committed` 隔离级别 |
| 「源记录 offset 就行，不需要和发送原子」 | 必须与 `collect` 同处 `getCheckpointLock()` 临界区，否则恢复后重放/跳读 |
| 「幂等汇可以随便重试」 | 幂等的前提是「写入由记录决定 + 可交换」；累加型/追加型写不幂等 |
| 「文件汇就是 `writeAsText`」 | 流式场景需要 `StreamingFileSink`（分桶、pending、按检查点 rename），否则文件永远不可见或重复 |
| 「异步 I/O 提的是并行度」 | 它提的是**在途并发**，不加算子实例；与 `setParallelism` 是两种杠杆 |
| 「`unorderedWait` 结果顺序乱所以没用」 | 只要下游按键聚合就无所谓；追求顺序用 `orderedWait`，代价是队头阻塞 |
| 「外部维表查询不需要超时」 | 没有超时 + 容量限制时，一次外部抖动就会把作业顶成反压甚至 OOM |
| 「检查点间隔短 = 端到端延迟短」 | 事务汇对外可见性由检查点驱动，间隔越短可见越快但快照开销越大（12 章） |
