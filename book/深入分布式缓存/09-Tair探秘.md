# 第 9 章　Tair 探秘

> 框架篇的第二个国产系统（淘宝/阿里）。与 Redis 的「单线程 + 服务端分片」不同，Tair 走的是
> 「中心化 Config Server + Data Server 集群 + 桶分布 + 多引擎可插拔」路线。本章对照 [08-分布式Redis.md](08-分布式Redis.md)
> 看会非常清晰。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 9.1 架构 | 一个 Config Server（一主一备）+ 若干 Data Server | 中心节点只管路由表，负载极低；客户端缓存路由 |
| 9.2 四种引擎 | mdb（内存，基于 Memcached）、rdb（基于 Redis）、kdb（基于 Kyoto Cabinet）、ldb（基于 LevelDB） | 同一套分布式外壳，可插拔不同单机引擎 |
| 9.3 数据分布 | `hash(key) -> Q 个桶`，桶是迁移/均衡最小单位（Q 远大于机器数） | 「桶」与 Redis Cluster 槽、Dynamo 虚拟节点同构 |
| 9.4 容错与迁移 | Data Server 故障由 Config Server 提升副本；迁移期间转发+路由保证不中断 | 中心化让一致性简单，无需向量时钟/反熵 |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 9.1 中心化架构

```text
# 教学示意，不参与构建：Tair 拓扑
ConfigServer(主) -- 同步 --> ConfigServer(备)     # 只存路由表（桶->DataServer）
Client <-- 拉取/缓存路由表 --> ConfigServer
Client -> DataServer(按路由表直连)  # 正常路径不经过 ConfigServer
DataServer 故障 -> ConfigServer 检测 -> 提升副本为主
```

- 关键：**客户端缓存路由表**，日常读写不触碰 Config Server；Config Server 只存极小的元数据，
  所以「中心节点成为瓶颈」的担忧在 Tair 里基本不成立（对比 [02-分布式系统理论.md](02-分布式系统理论.md) 2.6）。

### 9.3 桶（bucket）是分布的最小单位

```text
# 教学示意，不参与构建
Q = 10240                         # 桶数，远大于机器数
bucket = hash(key) % Q
每台 DataServer 负责若干桶
扩容加机器: ConfigServer 把部分桶从旧机迁移到新机（迁移单位=桶，粒度细）
           迁移期间旧机转发请求到新机 -> 对外不中断
```

- 与 [08-分布式Redis.md](08-分布式Redis.md) 8.3 的 16384 槽完全同构：都是「把 key 空间切成大量可迁移单位」。
  Tair 的 Q 取值哲学（» 机器数）与 Redis 的 16384 槽、Dynamo 的虚拟节点一致。

### 9.2 多引擎可插拔

- `mdb`：内存引擎（基于 Memcached），适合纯缓存；
- `rdb`：基于 Redis，支持更丰富数据结构；
- `kdb`：基于 Kyoto Cabinet（持久 KV）；
- `ldb`：基于 LevelDB（LSM，持久 + 大容量）。
- 这是「分布式外壳 + 可插拔单机引擎」思想，与 [大规模分布式存储系统/05](../大规模分布式存储系统/05-分布式键值系统.md) 中 Dynamo 5.1.6 同构。

## 版本演进

- **本书无第二版**；本节写 2017 年口径 → 2026 年视角的变化。
- **🔧 Tair 开源与云托管**：Tair 开源仓库为 `alibaba/tair`（**2314★**，2026-09 实测）；
  阿里云提供「云数据库 Tair（Redis 版）」托管服务，是本书「自建 Tair」的 2026 年延伸。
- **🔧 与 Redis 生态融合**：Tair 的 rdb 引擎直接基于 Redis，说明「Tair 外壳 + Redis 内核」是可行路线；
  2026 年很多业务用 Tair 托管版当作「带企业特性的 Redis」。
- **🔧 中心化思想的现代形态**：本书 9.1 的中心是「主备 Config Server」，2026 年这类中心多升级为
  **Raft 共识组**（如 etcd），自动容错更强（见 [02-](02-分布式系统理论.md) 2.8 补丁）。
- **🔧 多副本共识化**：Tair 的副本提升靠中心调度；现代系统更多把每分片的副本交给 Raft 组自动选主。

## 近年研究与工业界开源实践（2015–2026）

- **实测 star（2026-09，`gh api` 实测）**：

| 项目 | 定位 | star |
| --- | --- | --- |
| `alibaba/tair` | 淘宝 Tair 开源版（本章主角） | 2314 |
| `redis/redis` | Tair rdb 引擎底层参照 / 对照对象 | 76487 |
| `memcached/memcached` | Tair mdb 引擎底层参照 | 14285 |
| `google/leveldb` | Tair ldb 引擎底层参照 | 39448 |

- **「分布式外壳 + 单机引擎」成为通用范式**：今天 TiKV（RocksDB）、CockroachDB 都走这条路；
  Tair 在 2010 年就已实践，是本章的先见之明。
- **桶/槽分片范式普及**：Redis Cluster 槽、Tair 桶、Cassandra vnode 同构，说明中心化 vs 去中心化只在
  「谁维护路由」上分歧，分片单位思想完全统一。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Tair 就是 Redis」 | Tair 是分布式外壳，rdb 引擎才基于 Redis；还支持 mdb/kdb/ldb 多种引擎 |
| 2 | 「中心节点必成瓶颈」 | Config Server 只存路由表且客户端缓存路由，负载极低（见 9.1） |
| 3 | 「桶数随便取」 | 桶数 Q 须远大于机器数才能细粒度均衡与迁移（本书例子 10240） |
| 4 | 「Tair 和 Dynamo 一样处理冲突」 | 中心化后无需向量时钟/反熵/冲突合并，机制更简单（对比 [大规模分布式存储系统/05](../大规模分布式存储系统/05-分布式键值系统.md)） |
| 5 | 🔧 本书未提 Tair 云托管 | 2026 年阿里云 Tair 托管版是主流用法，应补 |
| 6 | 🔧 本书中心仅靠主备 | 🔧 2026 年中心多升级为 Raft 共识组，应补 |
| 7 | 🔧 本书未提 Tair 与 Redis 融合路线 | rdb 引擎即「Tair 外壳+Redis 内核」，应补 |
