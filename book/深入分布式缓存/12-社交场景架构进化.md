# 第 12 章　社交场景架构进化：从数据库到缓存

> 实践篇开篇，用「社交」这个典型互联网场景串起前面所有技术：为什么直接查 DB 撑不住、
> 怎么一步步引入缓存、缓存与数据库如何保持一致。这一章是理论到落地的桥梁。
> 注：本章逐节小节标题公开目录未逐节展开，以下内容依据公认架构知识整理。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 12.1 社交场景特点 | 读多写少、关系链/Feed 热点集中、峰值明显 | 典型「缓存友好」负载 |
| 12.2 从 DB 到缓存的架构演进 | 裸 DB → DB+本地缓存 → DB+分布式缓存 → 多级缓存 | 演进方向是「把热数据尽量推到离用户近的地方」 |
| 12.3 缓存与数据库一致性 | Cache-Aside 的读写顺序、延迟双删、binlog 订阅 | 一致性是缓存落地最难的工程点 |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 12.2 架构演进示意

```text
# 教学示意，不参与构建
阶段1:  App -> DB                        # 简单但峰值扛不住
阶段2:  App -> LocalCache -> DB          # 进程内挡一层（见第4章）
阶段3:  App -> Redis/Tair -> DB          # 分布式共享缓存（见第7-9章）
阶段4:  App -> LocalCache -> Redis -> DB # 多级，命中率与抗压最优
```

### 12.3 缓存与 DB 一致性（Cache-Aside 的坑）

```text
# 教学示意，不参与构建：常见「先更新DB再删缓存」+ 延迟双删
写请求:
  1. update DB
  2. delete cache
  3. sleep(short); delete cache again     # 延迟双删，消并发读回填的旧值
读请求:
  get cache -> miss -> get DB -> 回填 cache
风险: 步骤2后、回填前的并发读会把旧值写回 -> 双删降低概率; 更稳用订阅 binlog 异步删
```

- 这与 [01-缓存为王.md](01-缓存为王.md) 1.6（Cache-Aside）和 [14-典型电商应用与缓存.md](14-典型电商应用与缓存.md) 的一致性难题是同一主题。

## 版本演进

- **本书无第二版**；本节写 2017 年口径 → 2026 年视角的变化。
- **🔧 CDC 异步保证一致**：2026 年主流用 **Canal / Debezium** 订阅 MySQL binlog，异步淘汰/更新缓存，
  比手写「延迟双删」更可靠，把 12.3 的难题工程化。
- **🔧 多级缓存成为默认**：Caffeine（本地）+ Redis/Tair（分布式）+ CDN 三级联动（见 [01-](01-缓存为王.md) 补丁），
  2026 年社交/电商几乎都是这个形态。
- **🔧 客户端缓存（Redis 6.0 tracking）**进一步降低读路径延迟，是 12.2 演进的最新一级。

- **CDC 驱动缓存失效**是 2026 年「缓存与 DB 一致」的事实标准，取代了手写延迟双删的脆弱方案。
- **多级缓存框架化**：Spring Cache 抽象可同时桥接 Caffeine + Redis，业务无感。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「加了缓存就一致」 | Cache-Aside 有写后不一致窗口，需删缓存/订阅 binlog |
| 2 | 「先删缓存再更新DB更安全」 | 仍有并发读把旧值回填；延迟双删或 CDC 更稳 |
| 3 | 「缓存能完全替代DB」 | 缓存是加速层，系统记录源仍在 DB（除非用 Aerospike 类系统，见第 11 章） |
| 4 | 🔧 本书 12.3 偏手写策略 | 🔧 2026 年用 CDC(binlog) 保证一致是主流，应补 |
| 5 | 🔧 本书未提多级缓存框架化 | Spring Cache + Caffeine + Redis 已成默认，应补 |
