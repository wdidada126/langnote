# 第 6 章　Memcached 周边技术

> 第 5 章讲了 Memcached 自身，这一章讲它「一个人搞不定的事」如何被周边生态补上：
> 代理/集群、复制、客户端路由。这些技术也正是 Memcached 走向「生产可用」的关键拼图。
> 注：本章逐节小节标题公开目录未逐节展开，以下内容依据公认技术知识整理。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 6.1 代理：把分布式责任上收

```text
# 教学示意，不参与构建：Twemproxy 角色
Client -> Twemproxy (分片/路由/连接复用) -> [ memcached1, memcached2, ... ]
        代理负责: 一致性哈希选节点、失败剔除、连接池
好处: 客户端只连一个地址，拓扑变更对应用透明
代价: 代理成为额外一跳；需保证代理自身高可用（多实例）
```

### 6.2 复制：给「无状态」补一个副本

```text
# 教学示意，不参与构建：repcached 主备
memcached_master  <--(异步复制)-->  memcached_slave
写: 主接收并复制给备
主宕: 备顶上（需外部健康检查/VIP 切换）
限制: 通常是单主单备，非多副本；复制为异步，故障切换可能丢最近写入
```

- 这正是 [02-分布式系统理论.md](02-分布式系统理论.md) 2.8 故障转移的工程落地：Memcached 自己不做，
  由代理/复制组件 + 外部选主来补。

## 版本演进

- **本书无第二版**；本节写 2017 年口径 → 2026 年视角的变化。
- **代理生态稳定但被服务端分片稀释**：Twemproxy（twitter/twemproxy，**12339★**）仍是常用，
  但 Redis Cluster 把分片做进服务端后，新系统更少依赖外部代理；Memcached 侧依旧靠代理补分片。
- **自动化高可用代理出现**：`bilibili/overlord`（**2247★**）把「代理 + 集群管理 + 自动故障转移」打包，
  是本书成书后（2018 起）的工程进展，代表「缓存即服务」方向。
- **复制方案未成主流**：repcached 等 Memcached 复制方案始终小众；需要副本时，业界倾向直接换 Redis（天然主从），
  见 [08-分布式Redis.md](08-分布式Redis.md) 8.1。

## 近年研究与工业界开源实践（2015–2026）

- **实测 star（2026-09，`gh api` 实测）**：

| 项目 | 定位 | star |
| --- | --- | --- |
| `twitter/twemproxy` | Memcached/Redis 代理，分片上收 | 12339 |
| `bilibili/overlord` | Go 写 memcache/redis 代理 + 集群管理（自动化高可用） | 2247 |
| `memcached/memcached` | 集中式缓存本体 | 14285 |
| `redis/redis` | 服务端分片对照（Redis Cluster） | 76487 |

- **「代理即控制面」趋势**：Overlord 这类项目把「路由表维护、故障转移、扩缩容」自动化，
  正是 [02-分布式系统理论.md](02-分布式系统理论.md) 2.6「路由表」与 2.8「故障转移」的 2026 年工程形态。
- **Sidecar / Service Mesh 接管**：云原生里，缓存的路由与熔断越来越多交给定向代理/网格（如 Envoy），
  与应用解耦。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Memcached 自带集群」 | 无；集群/复制/路由都靠代理或第三方（本章全部内容即是补这些） |
| 2 | 「加代理就万事大吉」 | 代理是额外一跳且需自身高可用，否则从「缓存单点」变成「代理单点」 |
| 3 | 「repcached 复制等同 Redis 主从」 | 多为单主单备、异步，能力弱得多；需强副本直接选 Redis |
| 4 | 🔧 本书未提 Overlord 类自动化代理 | 🔧 `bilibili/overlord`（2247★）是成书后的自动化高可用方案，应补 |
| 5 | 🔧 本书未谈 Service Mesh 接管路由 | 2026 年缓存路由常下沉到网格/sidecar，应补 |
