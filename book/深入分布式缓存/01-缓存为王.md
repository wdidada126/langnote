# 第 1 章　缓存为王

> 全书的引子。这一章没有给出具体某个缓存系统的实现，而是把「缓存」这件事本身讲清楚：
> 它是什么、为什么有效、怎么度量、怎么分类、怎么选型。这是后面所有章节的公认底座。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 什么是缓存 | 缓存的通用定义：用更快/更近的介质保存高频访问数据的副本，以空间换时间 | 缓存的本质是「用更靠近计算的更快介质换延迟」 |
| 1.2 为什么使用缓存 | 降低后端（DB）负载、削峰填谷、提升吞吐与可用性、抵抗慢依赖 | 高并发系统几乎必备，但引入了「一致性」与「失效」两个难题 |
| 1.3 命中率 | hit rate = hit / (hit + miss)；与容量、访问局部性、过期策略相关 | 命中率是缓存健康度的第一指标，低于阈值的缓存不如不用 |
| 1.4 缓存分类 | 本地缓存（进程内）、分布式缓存、客户端缓存、CDN/浏览器缓存、CPU/OS 多级缓存 | 选型取决于「数据共享范围」与「一致性要求」 |
| 1.5 缓存淘汰策略 | FIFO / LRU / LFU / ARC / 2Q / W-TinyLFU 等 | 没有万能策略，要匹配真实访问模式 |
| 1.6 缓存模式 | Cache-Aside、Read-Through、Write-Through、Write-Behind（Write-Around 等变体） | 读写路径决定了「一致性复杂度」与「失效代价」 |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 1.3 命中率：缓存的「体温计」

```text
# 教学示意，不参与构建
hit_rate   = hits / (hits + misses)
miss_rate  = 1 - hit_rate
# 对同一个 key 的连续访问称为「时间局部性」；
# 访问一个元素后附近元素也被访问称为「空间局部性」。
# 局部性越强，命中率越高，缓存性价比越高。
```

- 命中率不是越高越好到 100%：命中率逼近 1 往往意味着缓存容量过大或数据几乎不变，
  需要权衡「内存成本 vs 收益」。常用「命中率 + 内存占用 + 驱逐率」三个指标联合看。

### 1.5 淘汰策略：缓存满了怎么办

```text
# 教学示意，不参与构建：经典 LRU 的「访问即置顶」思路
struct Node { key; value; prev; next }   # 双向链表 + hash 表
get(k):   node = map[k];  move_to_head(node);  return node.value
put(k,v): node = map[k]
          if node: node.value=v; move_to_head(node)
          else:    node = new(k,v); map[k]=node; push_head(node)
                   if size > cap:  remove_tail()   # 淘汰最久未用
```

- **FIFO**：按写入顺序淘汰，实现简单但无视访问频率，命中率差。
- **LRU**（Least Recently Used）：淘汰最久未访问；对「扫描型」访问（一次性遍历大量 key）很脆弱，会冲掉热数据。
- **LFU**（Least Frequently Used）：按访问频次淘汰；抗扫描但冷启动慢、历史计数难以衰减。
- **ARC / 2Q / LRU-K**：在 LRU 基础上引入「历史/频率」补偿，命中率更高（见 1.4 文献）。
- **W-TinyLFU**（🔧 2015 后）：用 Count-Min Sketch 近似计数 + 窗口/主区双段 + 基于成本的准入（TinyLFU），
  是 Caffeine 的核心，明显优于纯 LRU（见第 4、16 章补丁）。

### 1.6 四种缓存模式

| 模式 | 读路径 | 写路径 | 一致性 / 复杂度 |
| --- | --- | --- | --- |
| **Cache-Aside（旁路）** | 先查缓存，未命中查 DB 并回填 | 写 DB，再删/更新缓存 | 最常用；有「缓存与 DB 短暂不一致」窗口（见第 14 章） |
| **Read-Through** | 应用只查缓存，缓存未命中时由缓存层负责加载 DB | 同 Cache-Aside | 应用更简单，缓存层承担加载逻辑 |
| **Write-Through** | 同 Read-Through | 写缓存，缓存同步写 DB | 读一致好，但写延迟高 |
| **Write-Behind（回写）** | 同 Read-Through | 写缓存，异步批量写 DB | 写吞吐极高，但宕机可能丢数据，难度最大 |

## 版本演进

- **本书无第二版**；本节写 2017 年口径 → 2026 年视角的变化。
- **W-TinyLFU / Caffeine 取代 Guava Cache**：本书第 4 章主推 Guava Cache（见 [04-Ehcache与GuavaCache.md](04-Ehcache与GuavaCache.md)），
  但 2026 年 Java 本地缓存的事实标准是 **Caffeine**（ben-manes/caffeine，**17878★**），
  采用 W-TinyLFU，命中率与并发表现显著优于 Guava。这是本地缓存一线最大的演进。
- **客户端缓存（Client-side caching）**：Redis 6.0 引入 tracking/客户端缓存（见 [07-Redis探秘.md](07-Redis探秘.md) 补丁），
  把「读路径」从「应用→缓存」进一步压缩到「应用进程内」，是 1.4「客户端缓存」分类在 2026 年的落地形态。
- **多级（Tiered）缓存成为标配**：本地（Caffeine/Guava）→ 分布式（Redis/Tair）两级甚至三级（+CDN）联动，
  比单级分布式缓存在读放大上更优；本书偏重「分布式单级」，2026 年视角需补「多级联动」。
- **命中率可观测性**：从「拍脑袋配容量」到「按命中率/驱逐率做弹性扩缩」，Prometheus + 自适应 TTL 成为常规。

## 经典论文与原始文献

| 文献 | 出处 | 贡献 |
| --- | --- | --- |
| Gray, Putzolu《The 5 Minute Rule for Trading Memory for Disc Accesses》 | VLDB 1987 | **缓存性价比的经典判据**：数据访问频率超过阈值就值得常驻内存 |
| Megiddo, Modha《ARC: A Self-Tuning, Low Overhead Replacement Cache》 | FAST 2003 | **ARC 自适应替换算法**，兼顾 recency 与 frequency，命中率优于 LRU |
| O'Neil, O'Neil, Weikum《The LRU-K Page Replacement Algorithm》 | SIGMOD 1993 | **LRU-K**，用「最近 K 次引用」估计频率，抗扫描 |
| Johnson, Shasha《2Q: A Low Overhead High Performance Buffer Management Replacement Algorithm》 | SIGMOD 1994 | **2Q**，用两段队列近似频率，开销低 |
| Corbató《A Paging Experiment with the Multics System》 | 1968 | **Clock 算法**思想源头（近似 LRU 的环形扫描） |
| Tanenbaum, Bos《Modern Operating Systems》 | 教材（多版） | 多级缓存层级与局部性原理的教科书底座 |
| Gil Einav, et al. 关于缓存一致性协议 | — | 多级缓存一致性（MESI 等）的体系结构基础，见计算机体系结构教材 |

- **W-TinyLFU 论文支撑**：Gil Einat、R. Friedman 等《TinyLFU: A Highly Efficient Cache Admission Policy》

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「缓存命中率越高越好，逼近 100%」 | 命中率要高但需结合容量成本；逼近 1 往往说明数据几乎不变或容量浪费 |
| 2 | 「LRU 永远够用」 | LRU 对「一次性扫描」极脆弱；高并发下常需 LRU-K / ARC / W-TinyLFU |
| 3 | 「缓存一定能提升性能」 | 命中率低、写放大、网络开销大的缓存反而拖慢系统；缓存也可能成为瓶颈（见第 15 章运维问题） |
| 4 | 「Cache-Aside 写后删缓存就绝对一致」 | 存在「并发读写导致旧值回填」窗口，需结合延迟双删/订阅 binlog（见第 14 章） |
| 5 | 🔧 本书主推 Guava Cache，未提 Caffeine | 2026 年 Java 本地缓存事实标准是 **Caffeine（W-TinyLFU，17878★）**，命中率与并发显著优于 Guava |
| 6 | 🔧 本书讲「客户端缓存」只是概念 | Redis 6.0 tracking 已实现真正的客户端缓存，是 2026 年读路径优化的关键手段 |
| 7 | 🔧 本书偏「单级分布式缓存」 | 2026 年普遍采用「本地 + 分布式 + CDN」多级联动，单级视角需补多级架构 |
