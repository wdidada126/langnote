# 第 11 章　Aerospike 原理及广告业务应用

> 框架篇的最后一个系统，也是「类缓存」里最特殊的：Aerospike 是**混合存储（DRAM + SSD）**的
> 强一致 KV/宽列数据库，常用来扛广告竞价（ad tech）的超低延迟高并发。它与纯内存的 Redis 不同，
> 把 SSD 当作一级存储来用，是「缓存 vs 数据库」边界模糊的代表。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 11.1 混合存储架构 | 索引在 DRAM，数据在 SSD；绕过文件系统直写裸盘 | 用 SSD 价格获得近内存速度，容量远超纯内存缓存 |
| 11.2 索引与数据放置 | 分布式哈希分片 + 副本；smart partition 跨节点放置 | 数据与索引分离，扩容/故障可控 |
| 11.3 广告业务应用 | 广告竞价需要毫秒级查用户画像/预算 | Aerospike 的低延迟 + 大容量正好契合 ad tech |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 11.1 混合存储：索引在内存，数据在 SSD

```text
# 教学示意，不参与构建
写: 索引(主键->位置) 放 DRAM; 数据块 直接写 SSD(绕过 OS page cache)
读: 先在 DRAM 查索引 -> 拿到 SSD 位置 -> 直接读盘(SSD 随机读 ~0.1ms 级)
收益: 容量 = SSD 规模( TB 级), 延迟 ≈ 内存查索引 + 一次 SSD 读
```

- 这与 Redis「全内存」形成对照：Aerospike 用「内存索引 + SSD 数据」把**成本/容量**做到内存方案达不到的量级，
  同时延迟仍可满足广告竞价（毫秒级）。

### 11.2 分布式分片

```text
# 教学示意，不参与构建
partition = hash(key) % 4096        # Aerospike 固定 4096 分区
每个 partition 有副本(通常 2), 跨节点/failure-domain 放置
节点变更: 只迁移受影响分区的数据(类似桶/槽思想)
```

- 同样是「把 key 空间切成大量可迁移单位」的分片范式（与 8.3 槽、9.3 桶同构）。

## 版本演进

- **本书无第二版**；本节写 2017 年口径 → 2026 年视角的变化。
- **🔧 Aerospike 开源与云化**：Aerospike 服务端已开源（`aerospike/aerospike-server`，**1382★**，2026-09 实测），
  并提供托管/企业版，常被用作「大容量低延迟 KV」，广告与风控场景常见。
- **🔧 SSD 作为一级存储成主流思路**：Aerospike 的「索引内存 + 数据 SSD」被 RocksDB/LSM-on-SSD、
  以及 Redis 的「内存 + 磁盘分层」借鉴；2026 年 NVMe SSD 让这条路更顺。
- **🔧 与 Redis 的边界继续模糊**：Redis 的 `SEARCH`/`JSON` 模块、Aerospike 的 KV+二级索引，
  两者都在向「缓存 + 数据库」合体方向走。

  Aerospike 在 2010 年代就把它产品化。
- **广告/风控场景仍是主战场**：毫秒级大容量 KV 的需求（用户画像、频次控制、预算）让 Aerospike 持续活跃。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Aerospike 是缓存」 | 它是**强一致 KV/宽列数据库**，可作缓存也可作系统记录源（system of record） |
| 2 | 「SSD 慢不能用」 | Aerospike 绕过文件系统、索引内存化，SSD 随机读延迟足够广告竞价 |
| 3 | 「和 Redis 二选一」 | 关注点不同：Redis 偏全内存热数据；Aerospike 偏大容量低延迟；可并存 |
| 4 | 🔧 本书未提 Aerospike 已开源 | 2026 年 `aerospike-server` 已开源并云化，应补 |
| 5 | 🔧 本书未提 NVMe 对混合存储的增益 | 🔧 NVMe SSD 让「索引内存+数据SSD」更顺，应补 |
