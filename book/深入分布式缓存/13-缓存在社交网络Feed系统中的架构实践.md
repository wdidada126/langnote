# 第 13 章　缓存在社交网络 Feed 系统中的架构实践

> 承接第 12 章的社交场景，聚焦最经典的「Feed（信息流）」问题：微博/Twitter 的时间线、
> 粉丝动态如何靠缓存扛住读放大。这是缓存模式（[01-](01-缓存为王.md) 1.6）在超大读负载下的实战。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 13.1 推 vs 拉

```text
# 教学示意，不参与构建
拉模式(Pull): 用户打开首页 -> 查自己关注的人 -> 各自最新 N 条 -> 合并排序
              优点: 实现简单, 存储省; 缺点: 关注多时读放大恐怖
推模式(Push): 某人发帖 -> 扇出写入每个粉丝的 "收件箱" 缓存/列表
              优点: 读极快(直接读自己收件箱); 缺点: 大V粉丝多 -> 写放大
混合: 普通用户用推, 大V用拉(或读时合并)  -> 兼顾两边
```

### 13.2 用缓存承接读

```text
# 教学示意，不参与构建
1) 时间线缓存: 每个用户的收件箱(推模式结果)存 Redis 链表/ZSET, 读时直接取前 N
2) 热用户预计算: 大V主页/热门 Feed 提前算好放缓存, 避免每次实时聚合
3) 多级: 本地缓存(自己首页) + Redis(共享) + CDN(公开热门)
```

### 13.3 热点与降级

- **大 V 热点**：某明星发帖瞬时千万读，缓存 key 集中 → 用「多副本 key 打散 + 本地缓存」防单点；
- **缓存雪崩**：批量 key 同时过期 → TTL 加随机抖动；
- **降级**：缓存全失效时返回兜底页/旧数据，保护 DB（见 [03-](03-动手写缓存.md) 3.4 三坑）。

## 版本演进

- **本书无第二版**；本节写 2017 年口径 → 2026 年视角的变化。
- **🔧 客户端缓存 + 边缘缓存**：Redis 6.0 tracking（[07-](07-Redis探秘.md)）与 CDN 边缘把 Feed 读路径进一步压缩，
  2026 年公开 Feed 普遍多层缓存。
- **🔧 推模式成本被新存储吸收**：大 V 扇出的写放大可由 Aerospike/宽列存储（[11-](11-Aerospike原理及广告业务应用.md)）
  或物化视图承接。
- **🔧 实时性要求提升**：2026 年 Feed 更强调「近实时」，CDC（[12-](12-社交场景架构进化.md)）驱动缓存更新成为常态。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Feed 用推或拉二选一」 | 实际多为混合：普通用户推、大V拉，避免写放大 |
| 2 | 「缓存时间线永不失效」 | 需 TTL + 写时失效；大V发帖要实时刷新粉丝收件箱 |
| 3 | 「缓存挂了读DB顶上」 | Feed 读放大下 DB 顶不住，必须有降级兜底 |
| 4 | 🔧 本书未提客户端/边缘缓存 | 🔧 2026 年 Feed 多层缓存含客户端与 CDN 边缘，应补 |
| 5 | 🔧 本书未提 Feed + 推荐/向量 | 🔧 2026 年 Feed 与向量召回结合，缓存内容已扩展，应补 |
