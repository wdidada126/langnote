# 第 2 章　分布式系统理论

> 缓存是分布式系统的一部分，本章把「分布式」这个前提讲清楚：CAP/BASE、一致性哈希、
> 数据分片、全局 ID、路由表、数据拆分、故障转移。这些是后面 Redis Cluster / Tair / EVCache
> 等分布式缓存的通用语言。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 2.2 CAP 与缓存的取舍

```text
# 教学示意，不参与构建
CAP:
  C 一致性   —— 所有副本同一时刻看到同一值
  A 可用性   —— 每个请求（无论成功/失败）都有响应
  P 分区容错 —— 网络分区时系统仍继续工作
定理: 三者最多同时满足两个；在必须 P 的网络环境里，只能选 CP 或 AP。

BASE（对 AP 的放宽）:
  Basically Available 基本可用
  Soft state         软状态（允许副本短暂不一致）
  Eventually consistent 最终一致
```

- **缓存系统几乎都是 AP**：宁可返回稍旧的数据，也要保证可读可写（见第 5 章 Memcached、第 9 章 Tair）。
  需要强一致的场景（如库存扣减）要额外机制（见第 14 章）。

### 2.3 一致性哈希（本章最硬核的一块）

```text
# 教学示意，不参与构建：一致性哈希 + 虚拟节点
hash_ring = 0..2^32 的环
for each physical_node p:            # 虚拟节点：一个物理机映射多个 token
    for i in 1..V: ring[hash(p+"#"+i)] = p
key_node(k) = clockwise_first_node( ring, hash(k) )

扩容加一台机器 N_new:
    只需把「落在 N_new 顺时针前序区间」的 key 从原节点迁到 N_new
    —— 迁移量 ≈ 1/节点总数，而非全量
```

- **虚拟节点（V 个/物理机）**的作用：① 让性能异构的机器分到不同数量虚拟节点；
  ② 摊薄扩缩容的迁移量（每台只迁约 1/N）。这与 [09-Tair探秘.md](09-Tair探秘.md) 的「桶」、
  [08-分布式Redis.md](08-分布式Redis.md) 的「16384 槽」是同一思想的三种落实。

### 2.5 全局 ID：SnowFlake

```text
# 教学示意，不参与构建：Twitter SnowFlake（64bit）
| 1bit 符号 | 41bit 时间戳(ms) | 10bit 机器ID | 12bit 序列号 |
特点: 时间有序 -> 可少建索引、冷热易分离；64bit 利于 long 操作；机器ID隐含分片信息。
缺点: 依赖时钟；时钟回拨会导致冲突/重复（需检测与拒绝）。
```

- 本书指出全局 ID 要满足：无单点、含时间序、可控制分片（ShardingId）、不要太长（最好 64bit）。

## 版本演进

- **本书无第二版**；本节写 2017 年口径 → 2026 年视角的变化。
- **Raft 成为选主事实标准**：本书 2.8 讲故障转移时以「心跳 + 选主」泛泛带过，
  但 2014 年 Raft（Ongaro & Ousterhout，USENIX ATC 2014）已成熟，2026 年几乎所有需要选主的
  系统（etcd、TiKV、Redis Sentinel 的协作层、ZooKeeper 的 ZAB 同类）都以 Raft/Paxos 族落地。
- **一致性哈希的工业进化**：从「客户端一致性哈希」到「服务端托管槽/桶 + 客户端缓存路由」
  （Redis Cluster 的 16384 槽、Tair 的桶、Cassandra 的 vnode），本书 2.3/2.6 的两条线索在 2026 年已合流。
- **全局 ID 的新选项**：SnowFlake 之外，UUIDv7（带时间序，🔧 2024 RFC）、号段（Leaf-segment）、
  以及把 ID 生成下沉到数据库序列/专用服务（如美团 Leaf）成为主流，本书只覆盖 SnowFlake 与号段思路。
- **服务发现取代静态路由表**：2.6 的「路由表」在云原生里演化为服务注册中心（如 etcd、Consul、Nacos），
  缓存集群的拓扑变更自动广播。

- **一致性哈希库**：Java 的 `consistent-hash`、Go 的 `stathat/consistent`、Redis Cluster 的 CRC16 取模到槽，
  都是 2.3 的直接实现；`vnode`（虚拟节点）已成为 Cassandra/ScyllaDB 的默认。
- **SnowFlake 现代化**：美团 Leaf、百度 UidGenerator、Twitter 的 `snowflake`（Scala，已归档）等开源实现；
  UUIDv7（RFC 9562，🔧 2024）把时间序纳入标准 UUID，是 2.5 的新选项。
- **Raft 在缓存生态**：Redis Sentinel 的协作、TiKV 的多 Raft、etcd 的租约，都是 2.8 故障转移在 2026 年的成熟形态。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「CAP 三个能全要」 | 网络分区 P 不可避免，只能 CP 或 AP 二选一 |
| 2 | 「一致性哈希加节点只迁 1/N → 零代价」 | 仍有 1/N 迁移与短暂不一致窗口；虚拟节点数需远大于机器数才能平滑 |
| 3 | 「路由表一定放在中心节点」 | 现代做法是「中心存路由 + 客户端缓存路由」（Tair/Redis Cluster），中心只做变更广播 |
| 4 | 「全局 ID 用 UUID 随机即可」 | 随机 UUID 无序，不利索引与分片；高并发偏好时间序（SnowFlake/UUIDv7/号段） |
| 5 | 🔧 本书 2.8 选主未提 Raft | 2026 年选主/共识事实标准是 **Raft（2014）**，本书成书时泛泛带过，应补 |
| 6 | 🔧 本书 2.6 路由表偏静态 | 云原生里路由表由服务发现（etcd/Consul/Nacos）动态托管，应补 |
| 7 | 🔧 本书 2.5 只提 SnowFlake/号段 | 🔧 UUIDv7（2024 RFC）、Leaf-segment 等已 mainstream，应补 |
| 8 | 🔧 本书未谈「分区再平衡（rebalance）自动化」 | 2026 年扩缩容多由控制器自动再平衡，而非人工迁移 |
