# 第 3 章　动手写缓存

> 理论之后，亲手写一个最小可用的缓存。这一章的价值在于：把第 1 章的「淘汰策略」、第 2 章的
> 「并发与线程安全」落到代码层面，让抽象概念变成可感知的实现。代码均为教学示意。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 3.1 缓存接口设计 | get/put/remove/clear 的最小接口契约 | 好的接口把「存储」与「策略」解耦 |
| 3.2 LRU 实现 | 双向链表 + HashMap，或 Java LinkedHashMap | 经典 LRU 的 O(1) 实现是本章重点 |
| 3.3 超时与清理 | TTL、定期扫描、惰性过期 | 过期策略决定内存不会无限增长 |
| 3.4 并发与线程安全 | synchronized / 读写锁 / 并发容器 | 高并发下「缓存击穿/雪崩」由此而来 |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 3.2 用 LinkedHashMap 实现 LRU（Java 示意）

```java
// 教学示意，不参与构建
import java.util.LinkedHashMap;
import java.util.Map;

public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxSize;
    public LruCache(int maxSize) { super(maxSize, 0.75f, true); this.maxSize = maxSize; }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxSize;           // 超过容量即淘汰最久未访问
    }
}
// 说明：accessOrder=true 让 get/put 把节点移到队尾，队首即最久未用。
```

- 手写双链表版本（见 [01-缓存为王.md](01-缓存为王.md) 1.5）更直观，但工程上直接复用 `LinkedHashMap` 即可。

### 3.3 过期清理：惰性 + 定时

```text
# 教学示意，不参与构建
put(k, v, ttl): store[k] = (v, expire_at = now + ttl)
get(k):   if k not exists: return MISS
          if now > store[k].expire_at: del(k); return MISS   # 惰性过期
# 另起一个后台线程：定期扫描一小批 key，删除已过期者（避免惰性只在访问时才回收）
```

### 3.4 并发三个坑

| 现象 | 成因 | 应对（教学示意） |
| --- | --- | --- |
| **缓存击穿** | 热点 key 失效瞬间，海量请求打到 DB | 单飞（singleflight）：同一 key 只放一个请求去回源，其余等待 |
| **缓存雪崩** | 大量 key 同一时刻过期 / 缓存宕机 | 过期时间加随机抖动；多级缓存兜底 |
| **缓存穿透** | 查询不存在的 key，永远 MISS 打到 DB | 布隆过滤器拦截；空值也缓存短期 |

## 版本演进

- **本书无第二版**；本节写 2017 年口径 → 2026 年视角的变化。
- **单飞（singleflight）成为标配**：本书 3.4 讲并发安全时偏「加锁」，但 2026 年应对击穿的
  标准做法是用 singleflight（Go `golang.org/x/sync/singleflight`、Java 的 `duplicate request coalescing`）而非粗粒度锁。
- **并发容器取代手拧锁**：`ConcurrentHashMap` + `Caffeine`（ben-manes/caffeine，**17878★**）已把 3.2/3.4 的工程难点封装好，
  2026 年几乎不会从零手写缓存，而是基于 Caffeine/Redis 组合。
- **布隆过滤器普及**：3.4「缓存穿透」的应对在 2026 年几乎必配布隆过滤器（Guava 的 `BloomFilter`、Redis 的 `BF.*` 模块）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「LRU 就是用一个队列」 | 需要**双向链表 + 哈希表**才能 O(1) 找到并移动节点 |
| 2 | 「加了 TTL 内存就不会涨」 | 纯惰性过期只在访问时才回收，需后台定期扫描兜底 |
| 3 | 「并发安全=给方法加 synchronized」 | 粗锁吞吐差；击穿要用 singleflight，而非无差别加锁 |
| 4 | 🔧 本书 3.4 偏手拧锁 | 2026 年标配 **singleflight** 去重 + Caffeine 封装并发，应补 |
| 5 | 🔧 本书 3.4 未提布隆过滤器 | 缓存穿透防护 2026 年几乎必配 **布隆过滤器**（Guava/RedisBloom），应补 |
| 6 | 🔧 本书让读者从零写缓存 | 2026 年现实是**组合 Caffeine + Redis**，少有人从零实现；手写价值为「理解原理」 |
