# 第 14 章　典型电商应用与缓存

> 实践篇里最「接地气」的一章。电商是缓存的最大用户群：商品详情页、购物车、库存、秒杀……
> 每个场景的缓存策略与一致性要求都不同。这一章把前面所有知识点落到具体业务。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 14.1 商品详情页缓存 | 静态化 + Redis 缓存 + CDN | 读多写少，最典型的缓存友好场景 |
| 14.2 购物车 | 用户维度 KV，Redis Hash 承载 | 结构相对稳定，可长 TTL |
| 14.3 库存与秒杀 | 缓存预扣减 + 异步落库 + 防超卖 | 高并发写，缓存与 DB 强一致最难 |
| 14.4 缓存与数据库一致性 | 围绕 Cache-Aside 的电商实践 | 不同场景选不同一致级别（最终/强） |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 14.1 商品详情页

```text
# 教学示意，不参与构建
读商品页: CDN(静态部分) -> Redis(聚合后的详情JSON) -> 未命中回源服务 -> 写回Redis
写(价格/库存变): 更新DB -> 删Redis key(或发消息异步删) -> 下次读回填
```

### 14.3 秒杀与库存防超卖

```text
# 教学示意，不参与构建
1) 预热: 活动开始前把库存加载到 Redis  (SET stock:item:1001 500)
2) 扣减: 用原子操作, 避免超卖
        val = DECR stock:item:1001
        if val < 0: 回补(INCR) + 返回"已售罄"     # 原子扣减, 单线程Redis保证安全
3) 落库: 扣减成功的订单异步写 DB (削峰)
```

- 这里利用了 [07-Redis探秘.md](07-Redis探秘.md) 7.1 的「单线程串行执行」特性，使 `DECR` 天然原子，
  是秒杀缓存设计的核心 trick。

### 14.4 一致性的分级

| 场景 | 一致要求 | 策略 |
| --- | --- | --- |
| 商品详情 | 最终一致即可 | Cache-Aside + TTL + 写删缓存 |
| 购物车 | 基本不丢 | 写 DB + 写缓存（或异步对账） |
| 库存/余额 | 强一致 + 不超卖 | 缓存原子扣减 + binlog 对账（见 [12-](12-社交场景架构进化.md) CDC） |

## 版本演进

- **本书无第二版**；本节写 2017 年口径 → 2026 年视角的变化。
- **🔧 CDC 保证库存/详情一致**：2026 年用 Canal/Debezium 订阅 binlog 异步删缓存（[12-](12-社交场景架构进化.md)），
  比手写延迟双删可靠，电商一致性主流手段。
- **🔧 本地+分布式多级**：Caffeine + Redis 两级承接详情页/购物车，抗峰值更强。
- **🔧 缓存击穿防护自动化**：singleflight + 布隆过滤器（[03-](03-动手写缓存.md) 3.4）成为秒杀/热点商品的标配。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「库存放缓存就安全」 | 缓存宕机会丢预扣减；需 DB 持久 + 对账，不能只信缓存 |
| 2 | 「秒杀直接 INCR/DECR 不超卖」 | 扣到负数要回补；且要防缓存与 DB 最终不一致 |
| 3 | 「所有场景用同一致策略」 | 详情/购物车/库存要求不同，需分级（见 14.4） |
| 4 | 🔧 本书未提 CDC 保证一致 | 🔧 2026 年电商用 binlog 异步删缓成主流，应补 |
| 5 | 🔧 本书未提多级缓存 | 🔧 Caffeine+Redis 两级承接电商峰值，应补 |
| 6 | 🔧 本书未提布隆/singleflight 防护 | 🔧 热点商品击穿防护 2026 年标配，应补 |
