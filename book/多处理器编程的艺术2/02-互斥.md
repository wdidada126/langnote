# 第 2 章 互斥

> **本章地图**：临界区与三大性质（互斥 / 无死锁 / 无饥饿与无饿出）→ 只用读写的经典算法（**Peterson 锁 → 过滤锁 → Bakery 锁**）→ 基于 RMW 的 **TAS / TTAS + 指数退避** → 可扩展队列锁（**Anderson 数组队列锁、CLH、MCS**）→ 各类锁的时空开销对比 → 与 JUC / Linux 内核的对应关系。

## 二、核心精讲

### 2.1 问题定义与三个性质
- **互斥（Mutual Exclusion）**：任意时刻至多一个线程处于临界区。
- **无死锁（Freedom from Deadlock）**：只要有线程试图进入，最终必有线程能进入（系统整体不卡死）。
- **无饥饿（Freedom from Starvation）/ 无饿出（No Lockout）**：每个尝试进入的线程最终都能进入；后者更强（要求有限的等待步数），前者只要求"终能通过"。
- 🔧 注意：这三个性质描述的是**互斥算法**本身；不要与第 3 章描述**并发对象方法**的进展条件（wait-free / lock-free / obstruction-free）混为一谈。

### 2.2 只依赖读写的经典算法

**Peterson 锁（双线程，最简正确版本）**

```java
// （教学片段，不参与构建）经典 Peterson 锁：只用读写，不需要 RMW 指令
class Peterson implements Lock {
    private volatile boolean[] flag = new boolean[2];   // 各线程的「意向旗标」
    private volatile int victim;                         // 最后表示谦让的线程编号

    public void lock() {
        int i = ThreadID.get();              // 0 或 1
        int j = 1 - i;
        flag[i] = true;                      // ① 先举旗，宣布自己想进
        victim  = i;                         // ② 再谦让：让别人优先
        while (flag[j] && victim == i) { }   // ③ 只有当对方也想进、且自己是谦让者时才等待
    }
    public void unlock() {
        int i = ThreadID.get();
        flag[i] = false;                     // 放下旗，放对方通过
    }
}
```

- 🔧 **Peterson 锁最经典的 bug**：把 ① 与 ② 的顺序颠倒（`victim = i; flag[i] = true;`），两个线程会同时进入。它同时也是一个**内存可见性**的教学例子：Java 里两个字段必须 `volatile`（或有恰当的 happens-before），否则指令重排序会直接毁掉算法正确性。
- 🔧 Peterson 锁**只能用于 2 个线程**；推广到 n 线程要用到**过滤锁（Filter Lock）**——像一个"多级门厅"，每一级至多放行 n-1 个线程，层层筛到只剩一个。
- 🔧 **Bakery 锁（Lamport 1974）**：多线程版本的实用经典。每个线程进门前先取一个号码（`max + 1`），按 `(票号, 线程号)` 的字典序进入；关键是"取号"这一段（Doorway）必须在有限步内完成，从而自动满足无饥饿。

### 2.3 基于 RMW 原子指令的自旋锁

```java
// （教学片段，不参与构建）
class TASLock implements Lock {            // Test-And-Set：每一次自旋尝试都是一次独占 RMW
    AtomicBoolean state = new AtomicBoolean(false);
    public void lock()   { while (state.getAndSet(true)) { } }   // 每次都写共享变量 → 总线风暴
    public void unlock() { state.set(false); }
}

class TTASLock implements Lock {           // Test-Test-And-Set：先本地读，看起来空闲才去抢
    AtomicBoolean state = new AtomicBoolean(false);
    public void lock() {
        while (true) {
            while (state.get()) { Thread.onSpinWait(); }          // 本地自旋，不产生写流量
            if (!state.getAndSet(true)) return;
        }
    }
    public void unlock() { state.set(false); }
}

class BackoffLock implements Lock {        // 加强版：抢不到就随机退避一段时间再试
    AtomicBoolean state = new AtomicBoolean(false);
    public void lock() {
        int delay = MIN_DELAY;
        while (true) {
            while (state.get()) { Thread.onSpinWait(); }
            if (!state.getAndSet(true)) return;
            Thread.sleep(random() % delay);                       // 退避，瓦解「同时惊醒」
            if (delay < MAX_DELAY) delay = 2 * delay;
        }
    }
    public void unlock() { state.set(false); }
}
```

- **为什么 TTAS 明显快于 TAS**：`getAndSet` 是一条带锁前缀的读改写指令（`lock xchg`），会独占 cacheline 并产生缓存一致性流量；而 `get()` 在本地 cache 副本上自旋（**本地自旋 local spinning**），仅在释出时才尝试 RMW。
- 🔧 **`Thread.onSpinWait()`**（JDK 9+，对应 x86 `PAUSE`）向 CPU 提示"我在自旋"，可放松流水线并省电。

### 2.4 可扩展队列锁

**Anderson 数组队列锁**：线程用 `getAndIncrement() mod n` 领取自己的槽位，只在自己的槽上自旋；需要预知最大线程数 n，空间 O(L·n)。

**CLH 队列锁**（Craig–Landin–Hagersten，基于**隐式链表**，自旋在**前驱**节点上）：

```java
// （教学片段，不参与构建）CLH：每个线程自旋在「前驱」的 locked 字段上
class CLHLock implements Lock {
    AtomicReference<QNode> tail = new AtomicReference<>(new QNode());   // 虚拟尾节点
    ThreadLocal<QNode> myNode = ThreadLocal.withInitial(QNode::new);
    ThreadLocal<QNode> myPred = new ThreadLocal<>();

    public void lock() {
        QNode qnode = myNode.get();
        qnode.locked = true;                            // 我自己处于等待状态
        QNode pred = tail.getAndSet(qnode);             // 把自己挂到队尾
        myPred.set(pred);
        while (pred.locked) { Thread.onSpinWait(); }    // 自旋在前驱节点上
    }
    public void unlock() { myNode.get().locked = false; }   // 释放 → 后继观察到 → 进入临界区
}
```

**MCS 队列锁**（Mellor-Crummey & Scott，自旋在**自己**的节点字段上）：

```java
// （教学片段，不参与构建）MCS：自旋在自己的 locked 字段上，NUMA 友好
class MCSLock implements Lock {
    AtomicReference<QNode> queue = new AtomicReference<>();
    ThreadLocal<QNode> myNode = ThreadLocal.withInitial(QNode::new);

    public void lock() {
        QNode qnode = myNode.get();
        QNode pred = queue.getAndSet(qnode);
        if (pred != null) {                       // 队列非空 → 排到前驱后面
            qnode.locked = true;
            pred.next = qnode;                    // 让前驱能找到我
            while (qnode.locked) { Thread.onSpinWait(); }   // 自旋在自己的字段上
        }
    }
    public void unlock() {
        QNode qnode = myNode.get();
        if (qnode.next == null) {
            if (queue.compareAndSet(qnode, null)) return;   // 我是最后一个，摘掉队列
            while (qnode.next == null) { }                  // 等后继把它挂上来
        }
        qnode.next.locked = false;                // 手递手，把锁交给后继
    }
}
```

- 🔧 **CLH vs MCS**：CLH 自旋在前驱节点上（SMP 上很好，NUMA 下可能跨节点故性能下降），MCS 自旋在自己节点所在的本地内存上（NUMA 友好）。
- 🔧 **与 JUC 的关系**：`AbstractQueuedSynchronizer`（AQS）的等待队列就是**CLH 队列锁的变体**（加了前驱 status 驱动的 unparkSuccessor、节点的 cancel 处理、共享模式传播）。详见 `book/Java并发编程之美/concepts/AQS` 与 `book/Java并发实现原理/` 的源码剖析章。
- 🔧 **与 Linux 内核的关系**：内核的 `qspinlock` 源自 MCS，见"近年研究"一节。

### 2.5 各类锁的开销对比

| 算法 | 空间 | 每次获取所需的 RMW 次数 | 本地自旋 | 备注 |
| --- | --- | --- | --- | --- |
| TAS | O(1) | 每次尝试都 RMW | 否 | 惊群 + 总线风暴 |
| TTAS | O(1) | 1（抢到时） | 是 | 简单且够快 |
| 指数退避 | O(1) | 1 | 是 | 不建队列，性价比高 |
| Anderson 队列锁 | O(L·n) | 1 次 getAndIncrement | 是 | 需预知线程数上界 |
| CLH | O(L+n) | 1 次 getAndSet | 是 | SMP 优、NUMA 略差 |
| MCS | O(L+n) | 1 次 swap + 1 次 CAS | 是 | NUMA 友好，内核常用 |

## 四、近年研究与工业界开源实践

- **近年研究**：Linux 内核 **qspinlock**（Waiman Long 2013–2015）—— 把 MCS 压缩进一个 32 位字（pending 位 + 编码后的 tail CPU id），单 CAS 即可完成常见路径，兼顾 NUMA 与空间；**CNA（Compact NUMA-Aware）spinlock**（2019，Doshi / Panwar / Gupta）进一步按 NUMA 节点分组手递手，在超多核（>100 核）机器上显著降低跨节点通信。
- **工业界开源**（star 数 2026-09 实测）：
  - `openjdk/jdk`（≈23.4k★）：`AbstractQueuedSynchronizer.java` 是 CLH-like 队列锁最完整的工业实现（含取消/超时/共享模式/条件队列）。
  - `torvalds/linux`（≈190k★ 量级）：`kernel/locking/qspinlock.c`、`mcs_spinlock.h`、`osq_lock.c`（MCS 变体用于 mutex spinning）。
  - `facebook/folly`（≈30.5k★）：`MicroSpinLock` / `PicoSpinLock` 等自旋锁工程变体 + hazard pointer 内存回收。
  - `openjdk/jcstress`（≈2.1k★）：验证 volatile 语义与重排序事实；写新锁算法时应用它在 x86 / ARM 上分别压测。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "Peterson 锁能在工程中使用" | 它用于**建立正确性直觉**；工程上只用比它更高效的 RMW 方案，且必须先处理 volatile / 内存屏障 |
| 2 | "TTAS 与 TAS 只是写法不同" | TTAS 把每次 RMW 变成缓存读，争用下差距可达一个数量级 |
| 3 | "自旋锁总是比阻塞锁快" | 只有当临界区时间 ≤ 两次上下文切换开销时才更快；持锁时间长应 `park`（JDK 的自旋 + 阻塞混合策略即为此） |
| 4 | "CLH 与 MCS 可随意互换" | CLH 自旋前驱（NUMA 差）、MCS 自旋自己（NUMA 好）；且 CLH 依赖 GC 或手工回收节点内存 |
| 5 | "CAS 在任何平台上都一样" | x86 上是 `lock cmpxchg`；ARM 用 LL/SC 可能**伪失败**，必须循环 + 校验（weak CAS 语义） |
| 6 | 🔧 本书视角 | 本章算法用 Java volatile 表达，但**未充分展开语言级内存模型**差异（JMM / C++11 model），工程落地必须配合第 4 章与附录 A 一起看 |
