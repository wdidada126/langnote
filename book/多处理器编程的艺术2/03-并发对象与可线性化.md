# 第 3 章 并发对象与可线性化

> **本章地图**：为什么"看起来对"的并发对象其实是错的 → 方法调用历史与**顺序规格说明** → **可线性化（Herlihy & Wing 1990）**：定义、线性化点、**可复合性** → **可线性化 vs 顺序一致性 vs 静默一致性** → **进展条件**：wait-free / lock-free / obstruction-free → 如何对一个实现给出可线性化证明。

## 二、核心精讲

### 3.1 三类"看起来对"，其实是错的实现

```java
// （教学片段，不参与构建）三类经典错误
// ① 原子性违反：读-改-写不是原子操作
class UnsafeCounter { private long c = 0; public void inc() { c = c + 1; } }

// ② 加了 volatile 依然错：volatile 只保证可见性与单次读写的原子性，不保证复合操作原子
class VolatileCounter { private volatile long c = 0; public void inc() { c = c + 1; } }

// ③ 每个方法各自原子，但方法之间的组合不原子
class AtomicishQueue {
    AtomicReference<Node> head = ..., tail = ...;
    public boolean isEmpty() { return head.get() == tail.get(); }  // 与另一线程的 enqueue 交错：
}                                                                  // check-then-act 依然会出问题
```

- 教训：**正确性必须是整个对象的性质，而不是单个方法的性质**。

### 3.2 历史、未完成调用与顺序规格
- 一次并发执行记录为一串事件：方法**调用事件（invocation）**与**响应事件（response）**。
- 尚未配对的调用称为**未完成调用（pending invocation）**（任何可被 `get()` 观察的数据结构都必须考虑它们的可见性）。
- **顺序规格说明（sequential specification）**：对象在顺序执行时行为的合法定义。例如队列：`enqueue(x)` 无返回值；`dequeue()` 要么返回队首元素，要么返回空。

### 3.3 可线性化（Linearizability）的定义
一个执行历史 H 是**可线性化的**，当且仅当它能被"补齐"为一个等价的顺序历史 S，使得：

1. S 与 H 包含同样的方法调用，且每个调用的返回值符合顺序规格；
2. **保持实时顺序（real-time order）**：若调用 A 在调用 B 开始之前已经返回，则 S 中 A 必须排在 B 之前。

每一个方法调用都被映射到它执行区间内的一个瞬间点，即**线性化点（linearization point）**。

```java
// （教学片段，不参与构建）无锁实现同样可线性化：CAS 成功那一步就是唯一的线性化点
public V getAndSet(AtomicReference<V> ref, V newValue) {
    while (true) {
        V oldValue = ref.get();
        if (ref.compareAndSet(oldValue, newValue)) {   // ← 唯一的线性化点
            return oldValue;
        }
    }
}
```

三条最重要的直觉：
1. 方法调用看起来是在**一个不可分割的瞬间**发生（这就是"可线性化"名字的来源）；
2. 它是**可复合的（local / composable）**：若系统中的每个对象都可线性化，则整个系统也可线性化 —— 这是它压倒其他正确性条件的决定性优点；
3. 它**不要求实现真的加锁**：只要能找到线性化点，无锁实现同样可线性化。

### 3.4 三种正确性条件的强弱

| 正确性条件 | 是否保持实时顺序 | 是否可复合 | 典型应用 |
| --- | --- | --- | --- |
| **可线性化 Linearizability** | 必须保持 | 是 | `java.util.concurrent` 并发容器的实际目标；分布式共识/寄存器的强一致语义 |
| **顺序一致性 Sequential Consistency**（Lamport 1979） | 不要求，只保持单线程程序次序 | **否**（两个 SC 对象组合未必 SC） | 硬件内存模型的默认假设；x86-TSO 比它更弱 |
| **静默一致性 Quiescent Consistency** | 只在系统静默期之后要求一致 | 是，但弱得多 | `ConcurrentHashMap` 的迭代器/聚合视图、计数器的某些放宽语义 |

- 🔧 三者构成严格包含关系：**可线性化 ⊂ 顺序一致性 ⊂ 静默一致性**。

### 3.5 进展条件（Progress Conditions）

| 条件 | 定义 | 现实选择 |
| --- | --- | --- |
| **Wait-free** | 每个线程在**有限步内**必然完成自己的方法 | 最强，但实现复杂、常数大 |
| **Lock-free** | 系统整体**总有人**完成；个别线程可能反复重试而饥饿 | Treiber 栈、Michael-Scott 队列等主流无锁算法属于此 |
| **Obstruction-free** | 只要其他线程都暂停（独占执行），本线程能在有限步完成 | 最弱；HTM / STM 常只保证这一层，靠争用时的退避与加锁补偿兜底 |

```java
// （教学片段，不参与构建）wait-free 的思想雏形：各线程宣告自己的操作，无需争抢同一个热点
class WaitFreeCounter {
    private final long[] announce;                 // 每线程一个槽位
    public WaitFreeCounter(int nThreads) { announce = new long[nThreads]; }
    public void inc() { announce[ThreadID.get()]++; }   // 有限步完成，无 CAS 重试循环
    public long get() { return Arrays.stream(announce).sum(); }
}
```

- 🔧 工程上：**几乎不用纯粹的 wait-free**（常数太大），而是用"分段 + 局部争用 + 兜底退避"。JDK 8 的 `LongAdder` 就是这个思想的产物：以 cell 数组消除单点争用，读时才求和（弱化实时性、换取可扩展性）。

## 四、近年研究与工业界开源实践

- **近年研究**：**线性化的自动化验证** —— JetBrains 的 `Lincheck`（把"可线性化"变成可执行的模型检查：随机生成并发历史，检查是否存在合法的线性化序列），以及基于 refinement mapping 的交互式证明（Coq / Iris 中的 logically atomic 规范，`logically atomic triples`，POPL 2017）。
- **近年研究 2**：**relaxed / quantitative linearizability**（Henzinger, Kirsch, Payer, Sezgin, Sokolova, *Quantitative Relaxation of Concurrent Data Structures*, POPL 2013）—— 允许方法结果在时间上有界放宽，为高可扩展但有偏的数据结构（如 relaxed FIFO queue、approximate counter）提供正确性框架。
- **工业界开源**（star 数 2026-09 实测）：
  - `openjdk/jdk`（≈23.4k★）：`ConcurrentHashMap`、`ConcurrentSkipListMap`、`ConcurrentLinkedQueue` 的 Javadoc 明确写明了"哪些操作之间的关系是可线性化的"，是最好的规范性材料。
  - `JetBrains/lincheck`（≈1.5k★ 量级）：自动化线性化压力测试工具。
  - `openjdk/jcstress`（≈2.1k★）：验证 JMM 层面的可见性/原子性细节，常与 lincheck 配套使用。
  - `JCTools/JCTools`（≈3.9k★）：无锁队列/集合的工程实现，javadoc 中标明每个队列的进度保证与适用场景。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "每个方法本身线程安全，对象就线程安全" | 必须考虑**方法之间的组合**（如 `isEmpty` + `dequeue` 的 check-then-act） |
| 2 | "volatile 能保证自增的原子性" | volatile 只保证可见性与单次读写原子性，复合操作仍需锁或 CAS |
| 3 | "顺序一致性与可线性化差不多" | 顺序一致性**不可复合**且**不保持实时顺序**；可线性化严格更强 |
| 4 | "lock-free 就是 wait-free" | lock-free 允许个别线程饥饿；wait-free 要求每个线程有限步完成 |
| 5 | "只有加锁实现才可线性化" | 无锁实现同样可线性化，关键是能否指出**线性化点** |
| 6 | 🔧 本书视角 | 本章以队列 / 集合等简单对象为例；工业界面临的是读写混合负载与放宽语义（如 CHM 的 relaxed 迭代），需要结合 relaxed/quantitative 正确性框架一起看 |
