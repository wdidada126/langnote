# 第 6 章 共识的普适性

> **本章地图**：**普适性定理（Universality Theorem）**：共识数 ≥ n 的对象可以用 wait-free 的方式实现**任意** n 线程的并发对象 → **通用构造（universal construction）**：节点链表 + 每个节点一个共识对象 + announce 数组 → 线性化的正确性论证 → 复杂度代价（O(n) 每操作）→ 为什么它"理论上万能、实践中太慢" → 由此引出 Part II：**为具体对象手工设计可扩展实现**。

## 二、核心精讲

### 6.1 普适性定理
- **定理**：若对象 X 的共识数 CN(X) ≥ n，那么存在一个算法，仅使用 X 与读写寄存器，**wait-free 地实现任意** n 线程的并发对象。
- 这是第 5 章层次理论的另一半：共识数既刻画了"能不能做"（不可能结果），也刻画了"做到什么程度"（普适结果）。

### 6.2 通用构造 Universal Construction
结构三件套：
1. **announce 数组**：每个线程把自己的调用 `(方法名, 参数)` 写入自己的槽位，供所有线程读取；
2. **节点链表（history list）**：每个节点代表一次被"裁定"的方法调用，含 `seq`、`invocation`、`next`，以及一个用于决定"谁来接这个节点"的**共识对象**；
3. **线程 Procedure**：遍历链表，依次把每个节点的 invocation 应用到本地对象副本上，直到遇到自己的调用为止 → 返回自己的结果。

```java
// （教学片段，不参与构建）通用构造的骨架
class Universal {
    private Node head;                          // 头：最近落到链表里的操作
    private Invoc[] announce = new Invoc[n];    // 每线程宣告自己的调用

    public Response apply(Invoc invoc) {
        int i = ThreadID.get();
        announce[i] = invoc;                    // ① 宣告

        Node decide = new Node(invoc);          // ② 构造自己的候选节点
        decide.seq = head.seq + 1;

        while (decide.decided == null) {        // ③ 参与"谁来占据下一个位置"的共识
            Node current = head;
            Node next;

            while ((next = current.next) != null) current = next;   // 找到链尾
            // 把候选节点 CAS 上去；失败则重试（共识对象是 CAS-based 的）
            if (current.next == null) {
                Node win = current.decide.compareAndSet(null, decide) ? decide : current.decided;
                // 应用胜出节点后再把自己的候选节点重新尝试接到更长的位置
            }
        }

        // ④ 从头遍历链表，把每个已裁定的调用作用到本地副本上
        Object localState = copy(initialState);
        Node walk = head;
        while (walk != decide) {
            localState = applyCall(localState, walk.next.invoc);   // 按序应用
            walk = walk.next;
        }
        return applyCall(localState, decide.invoc).response;        // ⑤ 返回自己的结果
    }
}
```

- **线性化点**：每个节点的共识对象被决定的那一刻。所有线程遍历的是同一条链表，因此它们看到的是同一个"已裁定顺序" —— 这天然满足线性化。
- **wait-free 性**：每个线程最多遍历 n 步（链长上界与活跃线程数相关），因此有限步完成。

### 6.3 代价：为什么不用它
- 每次调用要维护 **O(n)** 的对象副本复制与链表遍历 —— 即便只有一个线程，也要付出 O(n) 而不是 O(1)。
- 内存开销同样随参与者线性增长，而且还要处理回收节点的问题（见第 19 章）。
- 🔧 因此本章的核心目的不是让你用它，而是论证：**只要提供一个足够强的原语（CAS），所有并发对象在原理上都是可构造的**；剩下的 Part II 全部是在追求"比通用构造更好的常数"。

### 6.4 两种变体
| 变体 | 同步方式 | 进展保证 | 说明 |
| --- | --- | --- | --- |
| **阻塞（locking）通用构造** | 用锁保护链表与状态 | blocking（非 wait-free） | 简单，但线程阻塞会导致整体停顿 |
| **非阻塞 / wait-free 通用构造** | 每个节点一个共识对象 | wait-free | 本章主体；常数大但理论意义最强 |

## 四、近年研究与工业界开源实践

- **近年研究**：**帮助机制（helping）与 combining** 的工程化 —— 把"通用构造"的遍历/帮助代价摊销到批量操作（flat combining，Hendler/Incze/Shavit/Shafiei, SPAA 2010）；**Flat combining** 已被用于实现可扩展的计数器、栈、队列、堆甚至 `PriorityQueue`（实质上让一个线程串行化一批操作，反而利用了局部性与向量化）。2020 年代还有 **opportunistic combining** 与 **wait-free 编译器自动生成**（Usui et al., DISC 2014）等方向。
- **工业界开源**（star 数 2026-09 实测）：
  - `JCTools/JCTools`（≈3.9k★）：工程的落脚点是"为特定对象手写"，而不是通用构造；阅读它的 `MpscArrayQueue` 与通用构造对照，最能体会常数的差距。
  - `openjdk/jdk`（≈23.4k★）：JUC 里每个容器都是手工优化版本，无一使用通用构造 —— 这正是本章结论的现实印证。
  - `google/nsync`、`facebook/folly`（≈30.5k★）：folly 中的批处理思想组件（如 `folly::FunctionScheduler`、批量队列消费）体现了"把操作批量合并、减少争用"的工程取向。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "既然有通用构造，就不需要学具体算法" | 通用构造的常数是 O(n)，生产系统全部是手工优化版本 |
| 2 | "wait-free 一定最有吸引力" | wait-free 的常数往往远大于 lock-free 版本；工业实现多为 lock-free + 兜底 |
| 3 | "普适性意味着所有对象一样难" | 普适性只说明"原则上可行"；难的是常数与内存回收 |
| 4 | "共识对象和 CAS 是两回事" | CAS（CN=∞）本身就是解决共识的具体手段，全书二者基本同义 |
| 5 | 🔧 本书视角 | 本章未讨论**内存回收**导致的复杂度（通用构造会持续产生节点），实际使用时必须叠加第 19 章的HP/EBR |
