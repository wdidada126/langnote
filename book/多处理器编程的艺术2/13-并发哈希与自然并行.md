# 第 13 章 并发哈希与自然并行

> **本章地图**：哈希表的两种基础布局（**链地址法 vs 开放寻址**）→ 三种并发同步粒度（整表锁 / 分段锁 / **桶级同步**）→ **自然并行（natural parallelism）**：哈希操作本就定位到单一位置，真正难点是**扩容（resize）**→ 增量/协作式扩容 → 提升缓存友好性：**cache-oblivious 布局、Hopscotch、布谷鸟哈希** → 与 JDK `ConcurrentHashMap`、ClickHouse/Redis 哈希结构的对照。

## 二、核心精讲

### 13.1 两种基础布局
| 布局 | 冲突解决 | 内存访问 | 评价 |
| --- | --- | --- | --- |
| **链地址法（separate chaining）** | 冲突元素串成链表 | 指针跳转，cache 不友好 | 实现简单，容忍高负载因子 |
| **开放寻址（open addressing）** | 线性/二次探测、双哈希 | 数组连续，cache 友好 | 删除需要墓碑 tombstones；高负载时探测链长 |

### 13.2 同步粒度演进：从整表到桶级

```java
// （教学片段，不参与构建）三种粒度的对照（示意）
// ① 整表锁：正确但完全串行
synchronized void putGlobal(K k, V v) { bucket(hash(k)).put(k, v); }

// ② 分段锁（JDK 7 ConcurrentHashMap）：把表分成 segments，每段一把锁
class StripedMap<K,V> {
    final ReentrantLock[] locks = new ReentrantLock[N_STRIPES];
    void put(K k, V v) {
        int idx = stripeIndex(hash(k));
        locks[idx].lock();
        try { buckets[idx].put(k, v); } finally { locks[idx].unlock(); }
    }
}

// ③ 桶级同步（JDK 8 ConcurrentHashMap）：只对命中的那个 bin 的第一个节点 synchronized/cas
void putBucket(K k, V v) {
    int h = spread(hash(k));
    int i = h & (n - 1);                        // 落到哪个 bin
    synchronized (binAt(i)) { ... }             // 或 CAS 首节点（JDK 8 的实际做法）
}
```

- 🔧 **JDK 8 的关键变化**：从 **Segment（JDK 7）** 改为 **bin 首节点加锁 + CAS 插入 + 树化（红黑树，bin 长度 ≥ 8 且容量 ≥ 64 时）**。动机是：分段锁在大表上有不必要的互斥，而"首节点即线程/锁"更细，且不需要预分配大量锁对象。

### 13.3 自然并行（natural parallelism）
- **洞察**：一次 `get/put/remove` 只涉及**一个**（或少数几个）位置；若不引入跨位的同步（如一次 resize），操作之间无需协调 —— 这就是"自然并行"。
- 因此哈希表的关键难点不是 put/get，而是 **rehash / resize 如何不牺牲并行性**。
- 🔧 三种解法：
  1. **停止世界式扩容**：简单但违背可扩展性（几乎没有现代库这么做）；
  2. **增量协作扩容**（JDK `ConcurrentHashMap` 的 `helpTransfer` / `transfer`）：扩容期间新旧表并存，访问者一边干活一边"帮忙搬运"若干 bin；
  3. **无需搬运的映射**（**split-ordered lists**，Shalev & Shavit, JACM 2006）：用**可无限扩展的逻辑哈希顺序**把元素挂在一条有序链表上，桶数组只是"索引加速器"，扩容时不必移动元素。

### 13.4 增量扩容：协作 transfer 的要点
```java
// （教学片段，不参与构建）协作式扩容的核心骨架（模仿 JDK CHM 的做法）
final Node<K,V>[] nextTable;                 // 扩容中的新表
volatile int transferIndex;                  // 下一个待迁移的区间，多个线程来"领任务"

void helpTransfer(Node<K,V>[] tab, Node<K,V>[] nextTab) {
    while (transferIndex > 0) {
        int stride = MIN_TRANSFER_STRIDE;                        // 每个线程领一段
        int nextBound = Math.max(0, transferIndex - stride);
        int bound = transferIndex; transferIndex = nextBound;    // CAS 抢占任务区间
        for (int i = bound; i > nextBound; i--) {                // 迁移 [nextBound, bound)
            Node<K,V> src = tabAt(tab, i);
            if (src != null) migrateBin(src, nextTab);           // 把该 bin 拆到新表的两个位置
        }
    }
}
```
- 双指针 transfer 在移动需要同时迁移多个 bin 时要特别注意 **`sizeCtl` / forwarding node (`MOVED` 标记)** 的使用 —— 这是把"访问到半迁移状态"的请求**重定向到新表**的关键。
- 🔧 这是 JDK 8 `ConcurrentHashMap` 最难的一段代码（也是面试/源码阅读的高频考点），建议对照源码 `resizeStamp` / `transfer` 阅读。

### 13.5 缓存友好的并发哈希
| 方案 | 思路 | 出处 |
| --- | --- | --- |
| **Cache-oblivious / van Emde Boas 布局** | 用递归布局使任意层级的 cache 都友好，无需知道 line size | Bender et al., SIGMOD/SPAA 2000s |
| **Hopscotch hashing** | 冲突时把该元素"跳"到邻近位置（只要属于同一 cache 块），用 bitmask 记录 | Herlihy, Lev, Shavit, DISC 2008 |
| **Cuckoo hashing** | 两个哈希函数两个位置，冲突时踢来踢去 | Pagh & Rodler, ESA 2001（SOSP-only: 并行版本参见本文下面） |
| **Linear probing + SIMD** | 与 SIMD 结合标杆 losing shadow | 见近年工作与工业实现 |

- 🔧 **实践主流是**：链地址法 + 桶级锁 + 树化 + 增量扩容（JDK CHM）。开放寻址/布谷鸟更多出现在**分析型引擎的内存哈希表**（ClickHouse、DuckDB 的聚合哈希表），因为那里以批处理读为主、几乎无并发单行写。
