## 16.1 核心精讲：THE 模型与贪心调度

### 三个量

- **`T₁`（work）**：单线程串行完成全部工作的时间；
- **`T∞`（span / critical path）**：依赖图上的最长链，即无限多处理器时的最短时间；
- **`P`**：可用处理器数。

**Brent 引理 / 贪心调度定理**（Blumofe & Leiserson, JACM 1999）：

```
执行时间上界：  T_P  ≤  T₁ / P + T∞        （期望意义下为 O(T₁/P + T∞)，含对数因子的变体见原文）
```

推论（实务上的评审更用）：
- 是否值得并行：看 **`T₁ / T∞`（并行度 PAR）**是否远大于 P；
- 调度器本身的开销如果能保持「窃取值 ≈ 0」的比例低于某个常数，就达到了**贪心最优**。

这是本章真正的价值：**给出一个几乎没有中心协调的分布式调度策略，同时在理论上接近最优**。

## 16.2 Chase-Lev 双端队列（SPAA 2005）

```java
// 教学示意：WSQ 的核心三个操作（不参与构建）
public final class ChaseLevDeque<E> {
    private volatile int bottom;                 // 只有 owner 写
    private volatile int top;                    // owner 与 thieves 竞争
    private volatile CircularArray<E> active;    // 可增长数组

    public void pushBottom(E e) {                // owner：无需 CAS（除了扩容）
        int b = bottom, t = top;
        CircularArray<E> a = active;
        if (b - t > a.size() - 1) active = a = a.grow(b, t);
        a.put(b, e);
        bottom = b + 1;                          // publish：写 bottom 在此发布
    }

    public E popBottom() {                       // owner：取 Return Bottom（最快路径）
        int b = bottom - 1;
        CircularArray<E> a = active;
        bottom = b;                              // 先移动 bottom（乐观占为己有）
        int t = top;
        E x = null;
        if (t <= b) { x = a.get(b); if (t == b) /* 最后一个元素：需要 CAS top 竞速 */ 
                      if (!CAS(top, t, t + 1)) x = null; bottom = t + 1; }
        else { bottom = t + 1; }
        return x;
    }

    public E steal() {                           // thief：从 top 端取，必须 CAS
        int t = top, b = bottom;
        CircularArray<E> a = active;
        if (t >= b) return null;                 // 空（或正在被 owner 掏空）
        E x = a.get(t);
        return CAS(top, t, t + 1) ? x : ABORT;   // ABA：单独 sentinel 处理
    }
}
```

要点：

1. **owner 与 thief 从不同端访问**，通常不会发生实际冲突 → 绝大多数操作是**无原子指令**的普通读写；
2. `top` / `bottom` 是 `int` 而不是对象引用 → **不存在 ABA 问题**（值单调递增，不需要 GC 支持），这是 work-stealing deque 在工程上比 stack/queue 好实现的关键原因；
3. 扩容用**可增长的环形数组（ treap-like CircularArray）**，旧数组由 owner 与 thieves 各自 ` (before stale rows)` 地保留，避免 UAF；在 Java 中旧 buffer 由 GC 回收，在 Rust 中需要小心处理所有权（crossbeam-deque 用 `*mut Buffer` + epoch/unsafe）。

### 常见工程优化

| 变体 | 行为 | 取舍 |
| --- | --- | --- |
| **窃取一半（steal half）** | thief 一次取走 `(top+bottom)/2` | 减少窃取次数；但对 locality 惩罚更大 |
| **每次偷 1 个** | ForkJoinPool 默认 | steal 频繁但 locality 更好 |
| **随机 victim** | 随机挑一个 worker | Go/Rust Tokio 均使用，简单且可证明良好期望行为 |
| **NUMA-aware** | 优先在本地 NUMA 节点内窃取 | 2020 年代的重点方向 |

## 16.3 三种并行分工模式的对比

| 模式 | 适用场景 | 通信方向 |
| --- | --- | --- |
| **生产者-消费者（共享队列）** | 任务同质、节拍稳定 | 单向：生产者 → 消费者 |
| **工作共享（work sharing）** | 任务一旦发生就立即推送给别人 | 立刻分散，中央 Contact 争用高 |
| **工作窃取（work stealing）** | 递归分治、任务数量动态增长 | 空闲方主动索取，**忙碌的线程从不被打扰** |

直觉：**忙者从不被打扰** —— 这是 work stealing 在真实系统里战胜中央队列的根本原因：争用方是「空的人」，而不是「忙的人」。

## 16.5 近年研究与工业界开源实践（2015–2026）

**研究侧**：

- ** locality-aware / NUMA-aware stealing**：多 socket 机器上远程内存访问代价 2–4 倍，2019 年后的工作开始把「窃取谁」作为调度决策的一部分（例如分层 stealer / hierarchical stealing 的各类工作）。
- **协作式 + 抢占式混合**：Go 1.14 引入异步抢占（原先只在函数调用点协作式切换），Tokio 1.x 引入 task budget / cooperative budgeting，避免单个任务霸占 worker。这是本书不曾讨论的**运行时 flavor**，但今天已成标配。
- **窃取 = priority + relaxation**：把 Ch15 的 relaxed PQ 思想转过来，用「近似最深任务的优先」换取更低的窃取争用。

**工业实现**：

| 实现 | 语言 | star | 特点 |
| --- | --- | --- | --- |
| `openjdk/jdk` | Java | ≈**23.4k★** | `ForkJoinPool`：Chase-Lev deque 的 Java 版本（Lea 亲自实现），双层级数组（victim stealing）；自 **JDK 21（JEP 444）** 又成为**虚拟线程调度器** |
| `golang/go` | Go | ≈**139.0k★** | 调度器包含 P/M/G 三元组 + 全局 run queue + per-P local queue + 随机 stealing；自 1.14 起实现异步抢占 |
| `tokio-rs/tokio` | Rust | ≈**33.2k★** | 1.x 的多线程调度器：global injector queue + per-worker run queue，自带任务预算抢占 |
| `rayon-rs/rayon` | Rust | ≈**13.3k★** | `split/nay join` 语义的直接 derivative of Cilk；底层依赖 crossbeam-deque |
| `crossbeam-rs/crossbeam` | Rust | ≈**8.6k★** | `crossbeam-deque` 是 Chase-Lev 的完整 Rust 实现，`Injector` 为 MPMC FIFO 的对接处 |
| `uxlfoundation/oneTBB` | C++ | ≈**6.8k★** | Intel TBB 的后继；task stealing + task_arena，历史上曾 Extend 得很像 Cilk Plus |
| `netty/netty` | Java | ≈**35.1k★** | 虽然不是通用调度器，但 `NioEventLoopGroup` 的 children 分配 + 单线程执行的思想，是另一种避开共享结构的工程手法 |

## 16.6 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「work stealing 总是最快」 | 任务粒度太细 schedules steal 开销主导；粒度太粗则尾部长（`T∞` 决定尾巴），必须配合 **cutoff** |
| 2 | 「窃取一定要 CAS」 | owner 一侧 `pushBottom/popBottom` 在只有一个 owner 的情况下根本**不需要原子指令**，这是性能的根本来源 |
| 3 | 「只用一个共享队列也一样」 | 共享队列在 P 大时成为 Exponential 争用点；stealing 把争用摊到每个 worker 的两端 |
| 4 | 🔧 **虚拟线程 + ForkJoinPool 的固定问题** | JDK 21 起 `ForkJoinPool` 成为虚拟线程调度器；在 `synchronized` 块内阻塞会 **pin 住 carrier**（JDK 23+ 引入了对部分 synchronized 的 unpin）。本书完全未覆盖这一层 |
| 5 | 🔧 `parallelStream()` 默认是公共池 | `ForkJoinPool.commonPool()` 被所有 parallelStream 共享；一旦里面有阻塞 IO，整个应用的并行流都会饥饿（详见 `book/Java并发编程之美/concepts/CompletableFuture.md`） |
| 6 | 🔧 「空闲线程就该立刻窃取」 | 真实调度器要做**指数退避 + park**，避免小偷们在空队列上忙等烧 CPU |
