# 第 7 章 自旋锁与争用

> **本章地图**：争用的来源（临界区长度 × 线程数）→ **本地自旋 + 指数退避**能否解决问题 → cache-coherence 层面的代价模型（**独占持有、写失效、总线流量**）→ 公平性 vs 吞吐量（handoff vs barging）→ 可扩展队列锁（Anderson / CLH / MCS）实测对比 → NUMA 与分层争用 → 何时应该放弃自旋、改为阻塞（park）。

## 二、核心精讲

### 7.1 争用的三个决定因素
- 争用强度 ≈（**临界区长度**）×（**并发线程数**）×（**锁粒度**）。
- 一个关键观察：**加锁代价 = 无争用开销 + 争用导致的串行化 + 缓存一致性流量**。三者中往往第三项被严重低估。
- 🔧 工程结论：降低争用的优先级排序应先做 **缩小临界区** 与 **细化粒度（striping / per-item lock）**，最后才考虑换锁算法。

### 7.2 本地自旋与指数退避（为什么够用很久）
```java
// （教学片段，不参与构建）典型的自旋 + 退避模板
class TTASBackoffLock implements Lock {
    private AtomicBoolean state = new AtomicBoolean(false);
    private static final int MIN_DELAY = 1 << 1, MAX_DELAY = 1 << 20;

    public void lock() {
        int delay = MIN_DELAY;
        while (true) {
            while (state.get()) { Thread.onSpinWait(); }        // 本地读缓存，无总线写
            if (!state.getAndSet(true)) return;                 // 看起来空闲才尝试 RMW
            Thread.sleep(random() % delay);                     // 抢输就退避
            if (delay < MAX_DELAY) delay = 2 * delay;
        }
    }
    public void unlock() { state.set(false); }
}
```
- 退避的意义在于**瓦解惊群**：多个线程同时看到锁被释放而一起发起 RMW，会让 cacheline 在多个核之间来回迁移；退避把它们错峰。
- 🔧 **`Thread.onSpinWait()`**（JDK 9+，x86 的 `PAUSE`）向 CPU 提示正在自旋，减少功耗与流水线冲刷开销。

### 7.3 缓存一致性层面的代价
- 每个 `getAndSet` 是一次**写独占**操作：先把其它核的 cacheline 副本失效，再从内存取 recht (mesi) 状态。
- 多个线程反复争抢时，该 cacheline 在每个核之间**来回迁移**，每次迁移 ~ 数百周期的互联延迟。这就是所谓 **cache line ping-pong**。
- 因此衡量锁的好坏，**RMW 次数比自旋次数更重要**：本地自旋读不断低频流逝 cacheline 持有权，而 RMW 每次都在抢占。

### 7.4 公平性 vs 吞吐量
| 策略 | 特点 | 评价 |
| --- | --- | --- |
| **Barging（闯入）** | 释放后谁抢到谁用，允许后来者先拿 | 吞吐量高，个别线程可能饥饿 |
| **Hand-off（手递手）** | FIFO 公平继承所有者 | 无饥饿，但强制串行移交 + 更多 RMW |
- 🔧 `ReentrantLock` 支持两种：非公平（默认，barging，吞吐高）与公平（`fair=true`，近似 FIFO）；JDK 实测非公平约高 1–2 个数量级吞吐（因它减少了 park/unpark）。

### 7.5 可扩展队列锁的实测关系
- **Anderson 数组队列锁**：预先 n 个 slot，线程 `getAndIncrement() mod n` 领取 slot，只在该 slot 上本地自旋 → 每次释放只波及一个后继。
- **CLH**：隐式链表，自旋在前驱的 `locked` 字段上；**SMP 上最好**（访存局部性好）；存在 NUMA 跨节点自旋的风险。
- **MCS**：自旋在自己的节点字段上；**NUMA 友好**（每个人都在自己本地内存上打转）。
- 🔧 它们共同的收益是：**一次 RMW 获取 + 一次释放**，与争用线程数基本无关（对比 TTAS 会随着线程数增加而线性增多争抢成功的尝试）。

### 7.6 NUMA 与分层争用
- 在 NUMA 机器上，跨 socket 的 cacheline 迁移代价远大于同 socket；故工业界主流实现使用**分层方案**：优先在同 socket 内 hand-off，只有整个 socket 队列空了才跨节点取任务。
- Linux 内核的 **CNA spinlock**（2019）就是这个思想的产品形态（详见本章末文献）。

### 7.7 何时不应自旋
- 临界区较长（例如含 I/O、内存分配、极低概率的长尾操作）→ 必须换成 **阻塞 + 唤醒（park/unpark）**。
- 只有少量线程时，自旋才有意义（线程数远超核数时自旋就是纯浪费）。
- 🔧 JDK 的实际做法：短暂自旋 + 快速失败，然后转入 `LockSupport.park` 交给 OS；内核互斥锁（mutex）也是先 optimistic spinning 再睡眠。

## 四、近年研究与工业界开源实践

- **近年研究**：**qspinlock**（Linux 2013–2015，把 MCS 压缩到 4 字节并保持异常情况下的单 CAS）；**lock cohorting / HMCS**（层次化 NUMA 队列锁，2012–2015）；**spin-lock hazard 的动态检测**（用 PMU/perf c2c 找伪共享与 true sharing）；**不同 "waiting strategy" 的自动选择**（2020 年之后的 adaptive spin-then-park 研究）。
- **工业界开源**（star 数 2026-09 实测）：
  - `openjdk/jdk`（≈23.4k★）：`AbstractQueuedSynchronizer`（CLH 系 + park/unpark）与 `ReentrantLock` 的公平/非公平两套策略。
  - `torvalds/linux`（≈190k★ 量级）：`kernel/locking/qspinlock.c`、`osq_lock.c`、`mutex.c` 的 optimistic spinning 版本，是"自旋多久就该睡"的最成熟参考答案。
  - `facebook/folly`（≈30.5k★）：`folly::MicroSpinLock`、`folly::SharedMutex`（读写锁 + 自旋混合）的实际权衡。
  - `perf` 工具链 / `pmu-tools`（≈10k★ 量级）：用 `perf c2c` 定位哪些 cacheline 在跨核争抢，是量化"争用成本"的标准手段。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "自旋锁比阻塞锁快" | 只在临界区短于两次上下文切换时才成立；长临界区应 park |
| 2 | "退避参数凭感觉给" | 应做 sweep：不同延迟上下限 + 不同线程数，吞吐曲线是"先升后降"的 |
| 3 | "公平锁能解决延迟不均" | 公平锁吞吐明显低；除非有强延迟约束，一般选非公平 |
| 4 | "CH CSS帧 CLH 在 NUMA 上一样快" | CLH 自旋前驱 → 可能跨节点；NUMA 上选 MCS 或 CNA |
| 5 | "锁的开销就是 CAS 的开销" | 真正的开销是 cacheline 迁移与豪争RMW 抑总线流量 |
| 6 | 🔧 本书视角 | 本书以单点多核 CPU 为主；今天更多系统 multiprocessor 已经分解成 NUMA socket 与 chiplet，必须将本章的代价模型向上扩展到 NUMA 层级 |
