# 第 15 章 优先队列

> **一句话**：线性一致的并发优先队列天然有一个**争用热点**（堆顶/最小元素），所以要真正 scalable，就必须**放弃严格的线性一致**，接受「近似最优」的返回值。

## 15.1 核心精讲：把跳表改造成 PQ

### 线性一致版本

用第 14 章的 LazySkipList：

```java
// 教学示意：基于惰性跳表的最小优先队列骨架（不参与构建）
public class SkipListPQ<E> {
    private final LazySkipList<E> sl;              // Ch14 的结构

    public boolean offer(E e) { return sl.add(e); }

    public E poll() {
        while (true) {
            Node<E> pred, curr;
            // 1) 从 head 的第 0 层顺链找到最小节点，并记录其前驱
            FindResult<E> r = sl.findMinWithPred();
            Node<E> pred = r.pred, curr = r.curr;
            if (curr == null) return null;                 // 队列空
            // 2) 尝试标记删除 curr（线性化点）
            // 2) 先 CAS crashing marked，再 CAS 改 pred.next（双阶段删除，见 Ch14）
            if (sl.tryRemove(pred, curr)) {
                return curr.item;                          // 成功 ⇒ 我取走了它
            }
            // 失败：别人抢走了，重试
        }
    }
}
```

**线性化点**：`poll` 成功的 `marked = true`；`offer` 的 `fullyLinked = true`。

**痛点**：`poll` 的线性化点永远是「最小元素的 marked 标志」，N 个线程抢同一个 cacheline → 吞吐随线程数**下降**（比单线程还差）。这就是本章要解决的问题。

### 为什么这是不可避免的？

直觉上：若规定「必须返回全局最小」，则任意两个并发的 `poll` 的返回值必须互不相同且分别是他们线性化时刻的最小——这强制它们必须**串行**地在同一个点上竞争。**放宽语义**是唯一出路。

## 15.2 版本演进

| 阶段 | 代表 | 松弛策略 |
| --- | --- | --- |
| 1993 | Israeli & Rappoport 的无等待 PQ | 不松弛，用通用构造，慢但保证最强进展条件 |
| 1998 | Hunt-Michael-Parthasarathy-Scott 并发堆 | **每个可用的 Filter 型堆**，仍强一致 |
| 2013 | k-LSM（Lindén & Jonsson，OPODIS 2013） | 把 k 个串行的 skiplist 堆起来，轮询选择，`k` 越大并行度越高、误差越大 |
| 2015 | **SprayList**（PPoPP 2015） | `deleteMin` 不从堆顶开始，而是**随机向下走**（spray），然后在落点附近向上/向下做短距离精确定位；在 O(log n log log n) 时间内完成，换来低争用 |
| 2015 | MultiQueues | N 个内部串行 PQ；插入随机选一个，删除随机挑两个比较取小者（power of two choices） |
| 2018 | Distributional Linearizability（PODC 2018） | 把松弛提升到「分布保证」的高度：返回的元素在剩余元素中的 rank 服从某个分布 |

## 15.3 经典论文与原始文献

| 论文 | 出处 | 关键点 |
| --- | --- | --- |
| Israeli & Rappoport, *Efficient Wait-Free Implementation of a Concurrent Priority Queue* | WDAG 1993 | 早期把通用构造用于 PQ 的代表，说明「最强保证」的成本 |
| Hunt et al., *An Efficient Algorithm for Concurrent Priority Queue Heaps* | IPDPS 1998 | 细粒度锁 + 堆去重入；工业实现常参考的对象 |
| Lindén & Jonsson, *A Skiplist-Based Concurrent Priority Queue with Minimal Memory Contention* | **OPODIS 2013** | k-LSM，明确 trade-off：`k` 与最大 rank 误差 |
| Alistarh, Kopinsky, Li, Shavit, *The SprayList: A Scalable Relaxed Priority Queue* | **PPoPP 2015** | 把随机 walking 用于「取近似最小」，首个在高并发下真正甩开强一致 PQ 的工作 |
| Alistarh, Brown, Kopinsky, Li, Shavit, *Distributionally Linearizable Data Structures* | **PODC 2018** | 松弛语义的形式化：不只是「rank 误差 ≤ k」，而是随机分布保证 |

## 15.4 近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **松弛程度成为可调参数**：2020 年代的方向是把「松弛量」做成显式参数并用 Hoare-style / separation-logic 给出证明（quantitative relaxation 方向），使得同一份代码可以在「强一致」与「高吞吐」之间滑动。
- **Relaxed → 下沉并行算法**：SprayList 论文本身的动机就是 Branch-and-bound / Dijkstra 单源最短路这类允许「近似最优」的应用；后续工作把这些启发式算法的性能收益量化出来。
- **硬件 bolt-on**：近年有把这类松弛结构映射到 **PMEM / CXL 内存池** 的工作，关注点是松弛 PQ 在远程访问延迟下的收益更大（因为争用代价被放大）。

**工业实现**：

- `openjdk/jdk`（≈**23.4k★**）：`PriorityBlockingQueue` 用**一把全局锁 + 数组二叉堆**（强一致、完全不可扩展），而 `ScheduledThreadPoolExecutor.DelayedWorkQueue` 同样是一把锁 + Leader-Follower 优化（详见 `book/Java并发编程之美/concepts/` 中的池相关专篇）——二者的共同点正是本章批评的「单点争用」。
- `rayon-rs/rayon`（≈**13.3k★**）：Rust 的 work-stealing 调度器，每个 worker 一个本地 deque；任务队列本身**不带优先级**，说明工业界常常直接绕开通用并发 PQ 的需求。
- `tokio-rs/tokio`（≈**33.2k★**）与 `netty/netty`（≈**34k★**）：定时器不用堆而用**分层时间轮（`HashedWheelTimer` / Timer Wheel）**，把「优先级」离散化为 O(1) 桶，是工程上避开争用堆的经典做法。
- `facebook/folly`（≈**30.5k★**）：`folly::MPMCQueue`、以及 `HazardPointer` 下方的各类 F14/AtomicStructOfArrays 数据结构；folly 优先选择**无优先级的多生产者多消费者队列**，也是同一现实。

## 15.5 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「并发 PQ 就该用堆」 | 二叉堆的顶层是唯一出入口；并发场景下**跳表-based / van Emde Boas 变体**反而更合适 |
| 2 | 「松弛就是不保证正确」 | relaxed PQ 有明确理论保证（rank error bounded / distributional），并非随机 err |
| 3 | 「SprayList 一定更快」 | 低争用、小负载下引入的随机游走反而是净损失；只在 **高争用 + 允许近似** 的应用场景收益明显 |
| 4 | 🔧 本书对工业措施着墨少 | 实际中大量系统直接**不用通用并发 PQ**：时间轮、sharded PQ、后台批替换 PG 单线程删除Heap，都是常见替代方案 |
| 5 | 🔧 `PriorityBlockingQueue` unbounded | 它会无限增长导致 OOM，且**不支持 comparable 变更后的自动重堆**——这是常见的线上事故来源 |
