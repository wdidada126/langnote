# 第 4 章 共享内存基础

> **本章地图**：**顺序一致性 SC**（Lamport 1979）→ **寄存器分级**：safe → regular → atomic → 从 SRSW 逐级构造到 MRMW 原子寄存器 → **atomic snapshot**（Afek et al. 1993）→ 现实机器的弱内存模型（x86-TSO、ARM/POWER、RVWMO）与语言级模型（JMM、C++11）→ 内存屏障与 volatile 的正确用法。

## 二、核心精讲

### 4.1 顺序一致性 vs 可线性化
- **SC**：存在某个等价的合法顺序执行，且每个线程自身的程序次序在该顺序中被保持；**不要求遵守墙钟时间顺序**。
- **可线性化**：在 SC 的基础上进一步要求**保持实时顺序**，且可复合（见第 3 章）。
- 🔧 SC 是**不可复合的**，但它是内存模型层面最自然的底层假设 —— 因此硬件往往只承诺 TSO 这类比 SC 更弱的模型，再由语言（JMM / C++）在更上层把 SC 语义还给程序员。

### 4.2 寄存器分级：safe / regular / atomic
| 级别 | 行为约束 | 评价 |
| --- | --- | --- |
| **Safe（安全）** | 读若**不与写交叠**，则必须返回上一个写的值；与写交叠时返回值**完全不受约束** | 仅具理论意义 |
| **Regular（正则）** | 读一旦读到新值，就不能再在这次读之后的交叠中"退回"读到更旧的值；与写交叠时允许返回新旧之一 | 很多非对齐访问的实际表现 |
| **Atomic（原子 / 可线性化）** | regular + 整个执行中存在唯一线性化点 | 真正的"一个内存字"；`AtomicInteger` 提供的语义 |

- 🔧 教学价值：单核上的普通变量天然满足 atomic；但在多处理器上，一个跨 cacheline 或未对齐的变量访问可能连 regular 都不是。关键结论是 —— **内存字本身就是一个并发对象**，它的正确性也需要分级定义。

### 4.3 从 SRSW 逐级构造 MRMW 原子寄存器
构造链（每层只用更低层的寄存器保证正确性）：

1. **SRSW safe → SRSW regular**：给每个写附加单调递增的时间戳，读者据此丢弃过期值。
2. **SRSW regular → SRSW atomic**：读者**连读两次**；若两次读到的时间戳相同，说明期间没有写与之交叠，该值即为合法读取。

```java
// （教学片段，不参与构建）双读（double read）技巧：SRSW atomic register
public V read() {
    while (true) {
        StampValue<V> first  = slot.get();     // 第一次读
        StampValue<V> second = slot.get();     // 第二次读
        if (first.stamp == second.stamp)       // 时间戳未变 → 期间无写交叠
            return first.value;
    }
}
```

3. **SRSW atomic → MRSW atomic**：为每个读者维护一份 SRSW 副本，写者广播（写代价 O(n)）。
4. **MRSW atomic → MRMW atomic**：写者之间先用 max-timestamp 共识确定全局次序，再广播。

- 🔧 这条链的寓意是：**同步能力是可以分层构造的**；它直接引出第 5 章的"原语能力层次"。

### 4.4 Atomic Snapshot（Afek et al., JACM 1993）
- 目标：**wait-free** 地一次性读取多个寄存器的瞬时一致状态。
- 方法要点：
  1. 每个线程写入 `(值, 序号, 最近一次看到的快照)`；
  2. scan 时连续收集两轮：若两轮中每个寄存器的序号都未变，则该视图就是合法快照；
  3. 若发生变化，则**借用**被 overwritten 线程记录的视图（helping），因为它在同一 lineage 上保持一致。
- 🔧 这是**非平凡 wait-free 并发对象的第一个范例**，也是理解 helping 机制与 Java GC 环境下 clean memory 回收的基准模型（配合第 19 章读）。

### 4.5 现实世界的内存模型
| 模型 | 重排序规则 | 代表平台 |
| --- | --- | --- |
| **SC** | 无重排序 | 理想模型（教科书默认） |
| **TSO（Total Store Order）** | 仅允许 store buffer 造成的 **store→load** 重排 | x86 / x86-64 |
| **弱内存模型** | 读写之间无全局次序，仅靠屏障维持 | ARM / POWER / RISC-V RVWMO |
| **JMM（JSR-133）** | happens-before + volatile 的 acquire/release；**无数据竞争 ⇒ 表现为 SC**（SC-for-DRF） | JVM（跨平台统一抽象） |
| **C++11 model** | `seq_cst` / `acq_rel` / `acquire` / `release` / `consume` / `relaxed` | C/C++11 及以后 |

```java
// （教学片段，不参与构建）JMM 视角下正确的双重检查锁定（volatile 不可省略）
class Singleton {
    private volatile static Instance instance;   // volatile 写具备 release 语义并禁止重排序
    public static Instance getInstance() {
        if (instance == null) {                  // 第一次检查：无同步的快速路径
            synchronized (Singleton.class) {
                if (instance == null)            // 第二次检查：加锁后才构造
                    instance = new Instance();   // volatile 写：发布一个已完全构造的对象
            }
        }
        return instance;
    }
}
```

- 🔧 **"在 x86 上跑过"不等于在 ARM 上正确**：x86-TSO 只放开 store→load 重排，而 ARM/POWER 放开更多。跨平台的内存模型 bug 必须用 litmus 工具复现，不能靠"我这台机器没出问题"。

## 四、近年研究与工业界开源实践

- **近年研究**：ARMv8 与 RISC-V **RVWMO** 的公理化模型（2017–2019 用 herd7 大规模 litmus 验证）；**Linux Kernel Memory Model（LKMM）**（2017 起，`tools/memory-model`）成为内核事实标准；**持久内存五 volum fail-atomicity 模型**（*Memory Persistency*, ISCA 2016），对应 Optane 退场后的新趋势（CXL 内存池化又带来了新的顺序问题）。
- **工业界开源**（star 数 2026-09 实测）：
  - `openjdk/jcstress`（≈2.1k★）：用成千上万的压力用例实测 JVM 在各平台上的代表行为，是验证 JMM 断言最实用的工具。
  - `herd/herdtools7`（≈1k★ 量级）：CAT + diy 套件，用于**公理化内存模型**仿真，检查某段 litmus test 在 ARMv8/x86/POWER/RVWMO 下是否被允许。
  - `torvalds/linux`（≈190k★ 量级）：`tools/memory-model/` 是 LKMM 的官方实现与测试集。
  - `facebook/folly`（≈30.5k★）：folly 的 `hazptr`、`AtomicStruct` 等组件大量使用基于 acquire/release 的精确 memory order，是学习精确内存序用法的最佳源码参考。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "单个变量的读写天然是原子的" | 未对齐或跨 cacheline 访问可能连 regular 都不是；32 位 JVM 上的 long/double 允许非原子 |
| 2 | "没有数据竞争就一定正确" | JMM 的 SC-for-DRF 只对**无 race 程序**承诺 SC 表现；一旦存在 race，推理基础就消失了 |
| 3 | "volatile 能替代锁" | volatile 只保证可见性与单变量操作的 acquire/release 语义；复合操作仍需 CAS 或锁 |
| 4 | "x86 上跑得通就没问题" | TSO 允许 store→load 重排，ARM/POWER 允许更多；必须用 litmus 工具验证 |
| 5 | "内存屏障越多越安全" | 屏障昂贵（数十至上百周期），应尽量用 release/acquire 配对而非处处 seq_cst |
| 6 | 🔧 本书视角 | 本章只在 SCM 模型下讲清楚注册的层级构造；现实工程必须配合 JMM / C++11 的形式化标准与工具（jcstress / herd7）一起学习 |
