# 第 19 章 乐观与手工内存管理

> **一句话**：无锁算法真正难的不是「不用锁」，而是**什么时候可以 `free`**——读线程可能正握着一个即将被别人释放的节点指针，这是 C/C++ 无锁编程的第一大坑（Java 靠 GC 免费获得，但换来的是 GC 停顿与对象池中的 ABA）。

## 19.1 核心精讲：为什么不能立刻 `free`

考虑第九、第十章的惰性链表，线程 A 读到 `curr`，正要读 `curr.value`；此时线程 B 完成 `CAS(pred.next, curr, curr.next)` 并调用 `free(curr)`：

```
A:  Node curr = pred.next;      ← 读到地址 p
B:  CAS 成功解链；free(p)        ← p 处的内存可能被 allocator 复用
A:  x = curr.value;             ← ❌ use-after-free（可能读到垃圾或新对象字段）
```

在 Java 里这不会崩溃（引用让对象存活），但在 C/C++/Rust(unsafe) 里是 UAF 漏洞。**GC 帮语言修复了这一半问题，但是**：

- GC 语言里仍然有 **ABA**（对象池 / `Recycler` 复用同一对象实例）；
- GC 语言为了根本原因（stop-the-world）会引入停顿；延迟敏感系统仍然要自己管理。

于是产生了两类解法：

| 类别 | 思路 | 代表 |
| --- | --- | --- |
| **保护式（protect）** | 读之前先**声明保护**，回收前检查是否有保护 | **Hazard Pointer** |
| **延迟式（defer）** | 先记下来，**等确定无人引用后再释放** | **EBR（epoch-based）**、RCU、引用计数、quiescent-state |
| **混合式** | 兼取两者所长 | HP + EBR 混合、`reclamation-free`（免回收）数据结构 |

## 19.2 乐观 + 校验（Validation）

本书 Ch9 的「乐观链表」套路：

```
1)找到 (pred, curr)，不持有锁
2)重新读 pred.next，确认它仍然 == curr     ← validate
3)再 CAS(pred.next, curr → new)             ← 只有 validate 通过才提交
```

**关键**：CAS 本身自带「条件 + 写入」的原子性 ⇒ **validate 与 commit 合并为一个 CAS**，不需要额外的同步。Java 里 `ConcurrentLinkedQueue` 的 `offer` 就是这个套路。

```java
// 教学示意：乐观 + 校验（不参与构建）
boolean insertAfter(Node pred, Node curr, Node node) {
    node.next = curr;
    // validate + commit 一步完成：只有当 pred.next 还是 curr 才写入 node
    return CAS(pred.next, curr, node);
}
```

但请注意：**validate 只能保证「此刻 pred.next 没变」，不能保证 curr 的内存还活着**（这就是 19.1 的 UAF 问题）。乐观 ≠ 回收安全。

## 19.3 风险指针（Hazard Pointer）

Michael 于 PODC 2002 提出：

```
读线程：                                 回收线程：
  hp[i] = p;              // 声明保护        retire(p)      // 把 p 放入自己的 retire list
  if (p 仍然可达) 使用它;                    当 retire list 大小 > R 时扫描所有线程的 hp[]：
  hp[i] = null;           // 解除保护        若没有任何 hp 指向 p  ⇒ free(p)
                                            否则保留到下一轮
```

要点：
- **声明保护的顺序至关重要**：必须是 `hp[i] = p` **之后再重新验证 `p` 仍然可达**（若重新验证失败则放弃）；
- 复杂度：读操作时的一次普通写（store-release）+ 一次重读；回收时扫描 `O(T · K)` 个 hazard pointer；
- **K = 每个线程需要的保护槽数**，通常一个算法只需要 1–2 个；`R = batch` 大小，典型取值 `R ≈ T · K · 2` 到几百；
- 优点：**有界内存占用**（retired list 不超过 R），与线程数呈线性；且**非阻塞**（lock-free）；
- 缺点：每次读多一次写屏障（~10–20% 开销）。

```java
// 教学示意：逻辑上的 hazard pointer 使用（不参与构建）
V read() {
    Node p;
    do {
        p = head.get();
        hazardSlot.set(p);                 // 1) 发布保护
    } while (head.get() != p);             // 2) 重新验证（validate）
    V result = p.value;                    // 3) 安全读取
    hazardSlot.set(null);                  // 4) 解除保护
    return result;
}
```

**现代变体**：`Hazard Eras`（Ramalhete & Correia, SPAA 2017）把 per-pointer 保护替换成 per-era 保护，可做到几乎无写开销且无 ABA；`Interval-Based Reclamation`（PPoPP 2018）保留 sliding windows 内的所有 retire 对象，牺牲内存换更低的读开销。

## 19.4 时期回收 EBR 与延迟式方案

### Epoch-Based Reclamation（Fraser 2004 提出理论）

```
全局 epoch e
每个线程：  进入临界区 → localEpoch = e（声明自己是本时期的读者）
           离开临界区 → localEpoch = ⊥
回收线程：  把 retire(p, e) 挂在 epoch e 的 retire list 上
           当**所有**线程的 localEpoch 都 ≠ e 且 > e 时，e 的所有 retire list 可以安全释放
           然后回收 e-1 / e-2 两个时期的 retired list（三重时期的由来）
```

- 读侧开销仅为「写自己的 localEpoch」（可用 relaxed 读写，几乎无额外代价）；但因为 localEpoch 是 per-thread 变量，**不会有 cacheline 争用**；
- 缺点：一个线程若不进入临界区（如阻塞很久），会**拖住整个回收**（这是 EBR 的最大工程痛点）；
- 变体：**NEBR/DEBRA**（ Trevor Brown 2015 的 deploy/disable epochs）、**stamp-it** 等，都是为了让 `retire` 与 `read` 解耦。

### RCU（Linux）

Linux 内核的 RCU 与 EBR 同一思想，差异在于内核语义允许「**基于定额状态 quiescent state**（发生了上下文切换 ⇒ 一定无形 CAS 引用）」：

```
synchronize_rcu() {
    for_each_online_cpu(cpu) 等待该 CPU 经历一次 quiescent state;
}
call_rcu(callback)  // 异步版本；高峰期用 list'' 批量
kfree_rcu(ptr, rh)            /* kfree 的 RCU 延迟版本 */
```

```c
/* 教学示意：RCU 读侧（不参与构建） */
rcu_read_lock();
p = rcu_dereference(gp);       /* 读侧仅为 barrier，无需原子指令 */
do_something(p);
rcu_read_unlock();             /* 读侧几乎零开销 */
call_rcu(&p->rh, free_cb);     /* 在所有读者 quiescent 之后回调 free_cb */
```

**RCU vs HP 的工程取舍**：

| | Hazard Pointer | EBR / RCU |
| --- | --- | --- |
| 读侧开销 | 一次 store + 重读（~10–20%） | 几乎零（仅 barrier / 禁用抢占计数） |
| 最坏内存占用 | 有界（O(T · K · R)） | **无界**（一个阻塞的读者能挡住全部） |
| 是否要求 cooperative 线程 | 否 | 是（必须定期宣布 quiescent） |

## 19.6 近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **混合方案成为主流**：近期工作普遍把 HP（有界）与 EBR（快速）结合：读侧用 epoch，**某个 epoch 拖太久时用 hazard eras 作为 fallback**；或者反过来。
- **形式化验证回收**：2020 年代以来，用分离逻辑（Iris / VerCors）证明 HP/EBR 下的无 UAF 已成为一条成熟线；这对 Rust 的 unsafe 尤其重要。
- **语言层集成**：Rust 社区在 `crossbeam-epoch` / `haphazard` / `seize` 等库之间持续演进；C++ 标准提案也把 hazard pointer 与 RCU 纳入标准库（`std::hazard_pointer`）。这是本章理论走向语言层标准化的一个近期例子。
- **持久内存**：PMEM 上还需解决 「CAS 前 flush 的顺序」与 「崩溃后的 retire list 自身持久性」，相关研究持续在 ISMM / ASPLOS 出现。

**工业实现**：

| 实现 | star | 说明 |
| --- | --- | --- |
| `facebook/folly`（≈**30.5k★**） | C++ | `folly::hazptr`，含 **hazard eras** 与 `hazptr_obj`/`hazptr_domain`，是目前工业界最完整的 HP 实现之一（并被容器 `ConcurrentHashMap` 于异步清理使用） |
| `crossbeam-rs/crossbeam`（≈**8.6k★**） | Rust | `crossbeam-epoch` 提供 EBR；`crossbeam-skiplist` / `crossbeam-deque` 都建立在它之上 |
| `torvalds/linux`（≈**250.1k★**） | C | RCU 的工业实现之最：tree-RCU、`rcu_barrier`、以及在 `Documentation/RCU/` 下有近百篇文档；几乎修改了所有 SAMODEL 子系统 |
| `openjdk/jdk`（≈**23.4k★**） | Java | 虽然有 GC，但 JVM 自身用 `Thread-local allocation buffers` + **GC 的 SATB / mark-barrier** 解决同样的「谁来кан free」问题；panama/hotspot 内部也有 hand-rolled reclamation |
| `pmem/pmdk`（≈**1.4k★**） | C | PMDK 的 `libpmemobj` 事务与 `POBJ_FREE` 的延迟回收，是持久内存回收的典型开源实践 |

## 19.7 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Java 有 GC 就不需要关心」 | **(a)** Netty `Recycler` / 自建对象池会把 ABA 带回；**(b)** 堆外内存（DirectBuffer / native memory）本就不受 GC 管理，是另一类回收问题 |
| 2 | 「validate 能保证内存安全」 | 见 19.2：validate 只保证**拓扑没变**，不保证**内存没被 free** |
| 3 | 「HP 一定慢」 | 有了 **per-thread retire list + batch** 后，HP 的读开销摊薄到几乎可忽略；真正贵的是 `free()` 系统调用本身，批量 retire 是关键 |
| 4 | 「EBR 的内存占用有界」 | 一个 sleep 很久的线程能挡住全局回收，导致 retire list 无限增长；这是选择 EBR 时必讲的代价 |
| 5 | 🔧 本书对 PMEM 与语言层集成覆盖不足 | 2020 年代最重要的两件事：C++ 标准库引入 HP/RCU；PMEM 下回收必须以事务方式持久。本书讨论是 shared-memory volatile 语境 |
| 6 | 🔧 Rust 的痛点 | Rust 的所有权能解决常规单所有权场景下的内存管理，但**无锁结构本质上无法静态证明**（多个所有者在无 happens-before 下存在），因此 crossbeam 用 unsafe + epoch 而非纯类型系统；这一点本书无法覆盖 |
