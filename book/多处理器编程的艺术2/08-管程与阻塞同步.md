# 第 8 章 管程与阻塞同步

> **本章地图**：为什么需要"阻塞"（自旋在长等待下纯属浪费）→ **管程（monitor）** 与 **条件变量（condition variable）** → **Hoare 语义 vs Mesa 语义**（决定了 `notify` 之后要不要立刻交出锁）→ Java 的 `synchronized` + `wait/notify/notifyAll` → 三个经典陷阱（**丢失唤醒、虚假唤醒、notify 用错**）→ 显式 `Lock` + `Condition` → 读写锁（Readers-Writers）与乐观读（`StampedLock`）→ 阻塞 vs 非阻塞的选择。

## 二、核心精讲

### 8.1 管程模型
- **管程（monitor, Hoare 1974 / Brinch Hansen）**：把共享数据与**操作这些数据的过程**封装在一起，编译器/运行时保证**互斥**（同一时刻只有一个线程在管程中）。
- 管程内部线程往往还需要等待某个谓词成立（例如"缓冲区非空"）→ 引入**条件队列（condition queue）**与 `wait/notify`。

### 8.2 Mesa 语义 vs Hoare 语义（本章最重要的概念）
| 语义 | 被唤醒者的行为 | 后果 |
| --- | --- | --- |
| **Hoare 语义** | `signal` 者**立即**把管程交给被唤醒者，自己挂起 | 谓词在苏醒时必然为真，但实现复杂、多一次切换 |
| **Mesa 语义**（工业界标准） | `signal` 者**继续持有**锁直到退出管程；被唤醒者只是重新进入竞争 | 苏醒时**谓词可能已被别人破坏** → 必须**用 while 循环重新检查** |

```java
// （教学片段，不参与构建）Mesa 语义下的标准写法：wait 必须在 while 循环里
public synchronized void put(T x) throws InterruptedException {
    while (count == capacity) wait();       // ← 必须是 while，绝不能用 if
    buf[tail] = x; tail = (tail + 1) % capacity; count++;
    notifyAll();                            // 通知等待 "非空" 的一方
}
public synchronized T take() throws InterruptedException {
    while (count == 0) wait();              // ← 同上
    T x = buf[head]; head = (head + 1) % capacity; count--;
    notifyAll();
    return x;
}
```

### 8.3 三个经典陷阱
1. **丢失唤醒（lost wakeup）**：在没有持有锁的情况下检查谓词（check-then-act 被分离）→ `notify` 在 `wait` 之前发生 → 永久阻塞。
2. **虚假唤醒（spurious wakeup）**：POSIX/JVM 允许 `wait` 无缘无故返回 → 因此必须 **while 重新检查**（这就是 Mesa 语义与 spurious wakeup 双重要求的结果）。
3. **`notify` vs `notifyAll` 误用**：`notify` 只唤醒**一个**线程；若多个线程等待**不同谓词**（如"非空"与"非满"混合在一个条件队列里），可能唤醒了错误的那个，导致所有线程都睡着 → **必须 `notifyAll`，或用多个 Condition**。
   - 这也是 `java.util.concurrent` 引入**显式 Condition**（一个锁可有多个等待队列）的直接原因：
```java
// （教学片段，不参与构建）显式 Condition：把不同谓词的等待队列分开
final ReentrantLock lock = new ReentrantLock();
final Condition notFull  = lock.newCondition();
final Condition notEmpty = lock.newCondition();

public void put(T x) throws InterruptedException {
    lock.lock();
    try {
        while (count == capacity) notFull.await();
        enqueue(x);
        notEmpty.signal();                 // 只唤醒 take 一侧
    } finally { lock.unlock(); }
}
```

### 8.4 读写锁与乐观读
- **Readers-Writers Lock**：允许多个读者并发；写者独占。衡量标准：是否偏向读者（适合读多写少）。
- 🔧 JDK 的 `ReentrantReadWriteLock`（公平/非公平、可降级不可升级）与 `StampedLock`（提供**乐观读** `tryOptimisticRead` + `validate`，无 CAS 争用的读路径）：
```java
// （教学片段，不参与构建）StampedLock 乐观读：完全不加写锁，读后校验
long stamp = lock.tryOptimisticRead();      // 获取一个乐观戳
double x = point.x, y = point.y;            // 读取多个字段
if (!lock.validate(stamp)) {                // 期间是否被写入过？
    stamp = lock.readLock();                // 退回悲观读
    try { x = point.x; y = point.y; } finally { lock.unlockRead(stamp); }
}
return Math.sqrt(x * x + y * y);
```
- 🔧 **乐观读的语义警告**：`StampedLock` 的乐观读期间读到的字段可能来自不同版本的写（不是原子快照），因此只适合"读一组不变式可被 validate 检查的字段"。

### 8.5 阻塞 vs 非阻塞
- 阻塞的代价：上下文切换 + 优先级反转风险 + 死锁（持���等待）。
- 阻塞的好处：等待期间不浪费 CPU；临界区可以很长。
- 🔧 现实 conclusion（重要）：**绝大多数生产代码用 blocking（锁+条件队列）**，非阻塞只在极热点路径（`ConcurrentHashMap` 的桶、队列入队出队、JCTools）才值得写 —— 因为非阻塞算法的可维护性与内存回收成本（第 19 章）都很高。

## 四、近年研究与工业界开源实践

- **近年研究**：**synchronization-aware schedulers**（ Linux 已有的 `EEVDF`、`sync-aware priority inheritance`）；**bias-free locks**（偏向锁被 JDK 15 默认关闭并在 JDK 18 移除，JEP 374，避免膨胀/取消膨胀的开销）；基于静态/动态分析的**条件等待死锁自动检测**工具，以及 2020 年代协程时代对 monitor 语义的重新审视。
- **工业界开源**（star 数 2026-09 实测）：
  - `openjdk/jdk`（≈23.4k★）：`ObjectMonitor` / `AbstractQueuedSynchronizer` / `ConditionObject` / `StampedLock` 的源码 — 本章所有概念的最完整实现。
  - `facebook/folly`（≈30.5k★）：folly 的 `SharedMutex`（读者 optimized 的 RW 锁）展示了 RW 锁在高争用下的多种 tradeoff。
  - `google/abseil-cpp`（≈13k★ 量级）：`Mutex` 的自旋/��塞混合策略的实现，同时也是 Abseil 的 condition usage guidelines 的来源。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "`wait()` 用 `if` 就够了" | 虚假唤醒 + Mesa 语义双重要求：**必须用 while** |
| 2 | "`notify` 比 `notifyAll` 高效，优先用" | 多谓词场景下会丢失唤醒；除非能证明只有一个等待谓词，否则用 `notifyAll` 或多个 Condition |
| 3 | "synchronized 已经过时了" | JIT 锁优化（膨胀/偏向已移除但仍有 escape analysis + lock coarsening）让它在多数场景足够好；换来的是 JVM 可自动���优化与更安全的语义 |
| 4 | "读写锁一定比互斥锁快" | RW 锁自身状态争用 +内存开销大于简单互斥；读/写比不够高时反而更慢 |
| 5 | "乐观读读到的就是完整快照" | `validate` 只能证明期间无写，不能保证多字段的一致性；需要 snapshot 时应用不可变对象一次性发布 |
| 6 | 🔧 本书视角 | 本章用 Java `synchronized` 讲解，本书未涉及 JDK 对 `ObjectMonitor` 的内部优化路径，也未覆盖虚拟线程（JEP 444）下 `synchronized` 固定平台线程（pinning）这一当代重要议题 |
