# 第 9 章 链表与加锁粒度

> **本章地图**：Set 的顺序实现（基于有序链表）→ **粗粒度锁（coarse-grained）**：一个锁锁整表 → **细粒度锁（fine-grained / hand-over-hand，手递手）**：每把锁只锁相邻节点 → **乐观细粒度同步（optimistic）**：先遍历、后校验 → **惰性同步（lazy）**：把删除拆成"逻辑删除 + 物理删除"两步 → **无锁（lock-free）**：用 `AtomicMarkableReference` 把标记位塞进指针 → 四个版本的代价/正确性/适用场景对比 → 与 `ConcurrentHashMap`、`ConcurrentSkipListMap` 的对应。

## 二、核心精讲

### 9.1 目标对象：基于有序链表的 Set
- 接口：`add(x)`、`remove(x)`、`contains(x)`。**不变式**：元素按 key 升序；不包含重复元素。
- 这是讲解并发数据结构的最好样本：操作需要遍历（读）+ 修改（写）混合，正好暴露各种同步策略的差异。

### 9.2 粗粒度锁：正确但不可扩展
```java
// （教学片段，不参与构建）
class CoarseList<T> {
    private Node head = new Node(Integer.MIN_VALUE);
    private Node tail = new Node(Integer.MAX_VALUE);
    private final ReentrantLock lock = new ReentrantLock();

    public boolean add(T item) {
        Node pred, curr; int key = item.hashCode();
        lock.lock();
        try {
            pred = head; curr = pred.next.getReference();
            while (curr.key < key) { pred = curr; curr = curr.next.getReference(); }
            if (key == curr.key) return false;
            Node node = new Node(item); node.next = new AtomicMarkableReference<>(curr, false);
            pred.next.set(curr, false);                 // 简单的插链
            return true;
        } finally { lock.unlock(); }
    }
}
```
- 优点：简单、可线性化、易证明。缺点：**所有操作串行化**，退化成单线程吞吐量。

### 9.3 细粒度锁：手递手（hand-over-hand / lock coupling）
- 思想：每把锁只保护一个节点；遍历时**必须先拿到下一个节点的锁，才释放前一个节点的锁**。
- 后果：**插入/删除只锁住相邻两三个节点**，读写不必等待整表。
- 代价：①每个操作需要 O(k) 次加锁/解锁（k = 遍历长度）；②必须严格保持加锁顺序（总是从头到尾），否则死锁。

```java
// （教学片段，不参与构建）手递手加锁遍历的关键三步
private Node traverse(Node start, int key) {
    Node pred = head, curr = pred.next;
    pred.lock();                                      // ① 锁住头
    try {
        if (curr != null) curr.lock();                // ② 先拿到后继的锁
        try {
            while (curr.key < key) {                  // ③ 依次推进：先锁下一个，再放开的这一个
                Node next = curr.next;
                if (next != null) next.lock();
                else break;
                pred.unlock();                        //    放掉前驱
                pred = curr; curr = next;
            }
        } finally { if (curr != null) curr.unlock(); } //    最终只留 pred 被锁（调用者负责）
    } finally { }                                     //    简化省略，实际需精确异常处理
    return pred;
}
```
- 🔧 现代工程视角：JDK 8 之前的 `ConcurrentHashMap` 用的是**分段锁（Segment）**，可看作"hand-over-hand 的粗粒度版本"；JDK 8 之后改为**桶级同步**（数组每个 bin 的第一个节点作为锁），本质是"按位置分片"而不是"相邻节点"。

### 9.4 乐观细粒度同步（optimistic）
- 观察：遍历过程中，**大多数节点的指针不会被修改**（只有少数冲突位置会变）；因此可以先"乐观地"不加锁地遍历，最后再校验。
- 方法：遍历时不加锁；到达目标位置后再**校验**中间链路有没有被改过（`validate(pred, curr)`：从头重新走一遍，确认 pred 仍可达 curr 且 pred 未被标记删除）。若校验失败，则退化为加锁版本重试。

```java
// （教学片段，不参与构建）乐观遍历 + 校验失败退化的骨架
public boolean optimisticAdd(T item) {
    int key = item.hashCode();
    while (true) {
        Node pred = head, curr = pred.next.getReference();
        while (curr.key < key) { pred = curr; curr = curr.next.getReference(); }  // 无锁遍历
        pred.lock(); curr.lock();                   // 只锁目标相邻两节点
        try {
            if (validate(pred, curr)) {             // ← 关键：确认中间链路没有被人改过
                if (curr.key == key) return false;  // 已存在
                Node node = new Node(item);
                node.next.set(curr, false);
                pred.next.set(node, false);
                return true;
            }
        } finally { pred.unlock(); curr.unlock(); }
        // 校验通过但因故失败：退化为加了粗粒度锁的版本重试（省略）
    }
}
```

### 9.5 惰性同步（lazy synchronization，Heller et al., OPODIS 2005）
- **核心思想**：把 `remove` 拆成两步 ——
  1. **逻辑删除**：把节点的 `marked` 位置为 true（此时 `contains` 已认为它不存在）；
  2. **物理删除**：之后再把它从链表里摘掉。
- 收益：遍历时只需检查 `marked` 位，**不必每次 acquire 多个锁**；`contains` 可以完全**无锁**。
- 具体不变式：
  - 未被标记的节点总是可达的；
  - 已被发现 marked 的节点不会被"复活"；
  - `contains(x)` 返回 false ⟺ 遍历路径上要么不存在，要么发现已被标记。
- 🔧 这是 JDK `ConcurrentHashMap`（分���内的链表）、`ConcurrentSkipListMap`（marker 节点）的实际做法；本书后续第 14 章跳表与第 10 章队列都将复用这一思想。

### 9.6 无锁链表（lock-free list）
- 用 `AtomicMarkableReference<Node>` 把 **标记位与引用打包在一个原子变量** 中，从而可以"原子地同时看 / 同时改"它们：
```java
// （教学片段，不参与构建）无锁删除：先用 CAS 打标记，再用 CAS 摘除
public boolean remove(T item) {
    int key = item.hashCode();
    while (true) {
        Window window = find(head, key);       // 返回 (pred, curr)
        Node pred = window.pred, curr = window.curr;
        if (curr.key != key) return false;
        Node succ = curr.next.getReference();
        // ① 逻辑删除：CAS 把 curr 的 next 打上标记（不影响其 next 指针的值）
        if (!curr.next.compareAndSet(succ, succ, false, true)) continue;
        // ② 物理删除：CAS 把 pred.next 从 curr 改成 succ
        pred.next.compareAndSet(curr, succ, false, false);   // 失败会被后续的 find 清理
        return true;
    }
}
```
- 其中 `find` 负责清理沿路遇到的已标记节点（**helping**）。
- 🔧 **Java 特有的便利**：因为有 GC，节点直到没有任何引用才被回收，因此"删除后仍有别人持有旧引用"在 Java 中是安全的（在非 GC 语言（C/C++/Rust）里必须叠加第 19 章的风险指针/时期回收）。

### 9.7 五种方案的对比
| 方案 | 是否阻塞 | 并发粒度 | 正确性条件 | 适用 |
| --- | --- | --- | --- | --- |
| 粗粒度锁 | 阻塞 | 整表 | 可线性化 | 简单场景、低争用 |
| 手递手细粒度锁 | 阻塞 | 相邻节点 | 可线性化 | 中等争用、遍历成本高时更不划算 |
| 乐观 | 阻塞（退化时） | 相邻节点 | 可线性化 | 高读少写 |
| **惰性（lazy）** | 阻塞（写） / 无锁（读） | 相邻节点 | 可线性化 | **工业最广**（CHM 的思想之一） |
| 无锁 | 无阻塞 | 相邻节点 | 可线性化 | 极高争用热点，代价高风险高 |

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "锁粒度越细越好" | 细粒度带来 O(k) 加锁解锁开销 + 死锁风险；遍历长时反而不如乐观/惰性 |
| 2 | "手递手锁可以任意顺序解锁" | 必须总是从头到尾严格推进，否则会死锁 |
| 3 | "无锁就是不用 any lock" | 无锁算法用 CAS 替代锁，代价是把"多���内存 ___x0005 的原子性"压缩进一个字，复杂度更高 |
| 4 | "惰性同步不线性化" | 逻辑删除那一刻就是线性化点；惰性只影响"物理摘除"的时机，不影响外部可见语义 |
| 5 | "Java 的代码能直接搬到 C/C++" | Java 依赖 GC 兜住"被移除但仍被遍历持有"的节点；无 GC 语言必须叠加 HP/EBR（第 19 章） |
| 6 | 🔧 本书视角 | 本章以"链表 Set"为样本；工业实现（如 `ConcurrentHashMap`）实际混合了哈希分桶 + 树化 + 桶级同步，是一个"混合策略"，应把本章作为理解其演化的基础而非直接套用 |
