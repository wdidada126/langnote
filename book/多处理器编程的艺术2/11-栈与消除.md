# 第 11 章 栈与消除

> **本章地图**：栈的先天劣势（只有一个出入口）→ **Treiber 栈**（无锁栈最简形态）与它的 ABA 危险 → 退避缓解争用 → **消除（elimination）**：让 `push` 与 `pop` 互相抵消 → 消除数组的范围与时长策略 → **Dual data structure** 的推广 → 工程对照（`Exchanger`、`LinkedTransferQueue`）。

## 二、核心精讲

### 11.1 为什么栈难以并行
- 栈只有一个热点 `top`，所有 `push` / `pop` 都在同一个 CAS 上竞争，没有任何分治空间。
- 但它有一个队列不具备的特性：一次 `push(x)` 与一次并发的 `pop()` **可以互相抵消** —— 值不必真正写入数据结构，双方即可完成。这就是本章的主题。

### 11.2 Treiber 栈（1986）

```java
// （教学片段，不参与构建）Treiber 栈：每次 push / pop 各只需一次 CAS
public class TreiberStack<T> {
    AtomicReference<Node<T>> top = new AtomicReference<>(null);

    public void push(T item) {
        Node<T> newHead = new Node<>(item);
        while (true) {
            Node<T> oldHead = top.get();
            newHead.next = oldHead;                       // 新节点指向旧栈顶
            if (top.compareAndSet(oldHead, newHead))      // ← 线性化点
                return;
        }
    }

    public T pop() {
        while (true) {
            Node<T> oldHead = top.get();
            if (oldHead == null) return null;             // 空栈
            Node<T> newHead = oldHead.next;
            if (top.compareAndSet(oldHead, newHead))      // ← 线性化点
                return oldHead.item;
        }
    }
}
```

**ABA 危险**：设 `top == A`，线程 T1 读到 `oldHead = A`、`newHead = B` 后被挂起；期间别的线程执行了 `pop A`、`pop B`、`再 push 同一个节点 A`（无 GC 语言中地址复用，或 Java 中复用了同一个对象）→ T1 恢复后 CAS 依然成功，但链表已被改错。
- 🔧 解法：版本戳（`AtomicStampedReference`），或让节点根本不可能被复用（第 19 章的风险指针 / 时期回收）。

### 11.3 退避与消除的分工
- 退避（backoff）只是降低同时抢 CAS 的密度，**没有减少热点本身**。
- 真正可扩展的办法是消除：让并发的 push/pop 在热点之外配对完成。

### 11.4 消除数组（Elimination Array）

```java
// （教学片段，不参与构建）带消除的栈：先试 Treiber，失败后进消除数组等待配对
public class EliminationStack<T> {
    private final TreiberStack<T> stack = new TreiberStack<>();
    private final Exchanger<T>[] exchanger;          // 消除数组：每个槽位是一个"交换器"

    public EliminationStack(int capacity) {
        exchanger = (Exchanger<T>[]) new Exchanger[capacity];
        for (int i = 0; i < capacity; i++) exchanger[i] = new Exchanger<>();
    }

    public void push(T item) {
        int slot = random(capacity);
        try {
            exchanger[slot].exchange(item);          // 被某个 pop 取走 → 直接完成
        } catch (TimeoutException timeout) {
            stack.push(item);                        // 超时无人配对 → 退回 Treiber 栈
        }
    }

    public T pop() {
        T item = stack.pop();                        // ① 先尝试直接出栈
        if (item != null) return item;
        int slot = random(capacity);                 // ② 失败后进消除数组等 push 配对
        try { return exchanger[slot].exchange(null); }
        catch (TimeoutException timeout) { return null; }
    }
}
```

- **为什么可扩展**：负载高且 push / pop 数量相当时，大部分操作在消除数组里配对成功，完全绕开了热点 `top`。
- **两个调优点**（本书强调）：
  1. **槽位选择范围**：范围应随负载自适应（负载高时缩小范围以提高配对概率）；
  2. **等待时长**：太短会过早放弃，太长会在低负载下拖慢单次操作。
- 🔧 **可线性化性**：配对成功那一刻就是线性化点；由于 push 与 pop 在这一刻互相抵消，外部观察到的历史依旧等价一个合法的栈操作序列。

### 11.5 Dual data structure（互逆操作配对）
- 更一般的思想：任何操作都可以找一个**反操作**配对消除。
  - 栈：`push` ↔ `pop`
  - 队列：`enqueue` ↔ `dequeue`（不同端时形成 dual queue）
  - 计数：`increment` ↔ `decrement`
- 该系统化思路来自 Herlihy / Luchangco / Moir / Shavit 关于非阻塞 dual 数据结构的工作，也呼应本书第 12 章的"组合"思想：都是**用一个协作点替代全局热点**。

## 四、近年研究与工业界开源实践

- **近年研究**：消除策略与 flat combining 的**自适应切换**（按负载在"自旋/消除/批处理"之间迁移）；现代 hazard pointer 实现同时解决回收与 ABA；工作窃取双端队列（第 16 章）也可看作 dual 思路的变体 —— 窃取者与拥有者从两端取任务。
- **工业界开源**（star 数 2026-09 实测）：
  - `openjdk/jdk`（≈23.4k★）：`Exchanger` 本身就是消除思想的官方实现；`LinkedTransferQueue`、`SynchronousQueue` 的"生产者等待并直接交付给消费者"模式与之同源。
  - `JCTools/JCTools`（≈3.9k★）：各类 SPSC / MPSC 队列的实现，注释中明确说明内存布局与伪共享控制策略。
  - `openjdk/jcstress`（≈2.1k★）：可用来验证 Treiber 栈在不同 JVM / 硬件上的 ABA 与可见性行为。
  - `facebook/folly`（≈30.5k★）：`hazptr` 实现可作为"无 GC 环境下如何补上 ABA 防护"的现实答案。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "无锁栈代码简单，所以比并发队列好用" | 栈只有一个热点，扩展性最差；本书正是用它来"先把问题做到最坏，再用消除解决" |
| 2 | "消除可以抵消任意两个操作" | 只有**互逆**的调用才能合法抵消，否则会破坏线性化 |
| 3 | "消除数组越大越好" | 范围过大会降低配对概率，一般按核数与负载自适应调整 |
| 4 | "Treiber 栈可以随便搬到任何语言" | 无 GC 语言必须叠加第 19 章的内存回收，否则节点重用导致 ABA |
| 5 | "`Exchanger` 只是双线程小工具" | 它正是消除思想的标准化载体；JUC 的 `LinkedTransferQueue` 采用了同类思路 |
| 6 | 🔧 本书视角 | 本书用 `Exchanger` 讲解消除；工程上应优先使用 JUC 已有的 transfer / exchange 组件，而不是自己实现消除数组 |
