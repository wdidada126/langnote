# 第 18 章 栅栏（Barrier）

> **一句话**：屏障的核心矛盾是「**N 个线程对同一变量的争用**」，所以所有可扩展屏障都做同一件事——**把 O(N) 的集中争用摊成树形 O(N) 总通信量、O(log N) 关键路径**。

## 18.1 感反式屏障（Sense-Reversing Barrier）

### 为什么不能用简单的「共享计数器 ++」

```java
// 反例：看似正确，实则不可复用（不参与构建）
class BrokenBarrier {
    volatile int count = 0;                 // 到达计数
    volatile boolean go = false;            // 放行标志
    void await(int n) {
        if (++count == n) { go = true; }    // ❌ ++count 不是原子操作
        while (!go) Thread.onSpinWait();    // ❌ 第二轮需要用 go=false，会引发丢失唤醒/重入问题
    }
}
```

两个致命缺陷：
1. `++count` 非原子（必须 CAS 或原子类）；
2. **屏障不可复用**：第二轮必须把 `count` 和 `go` 复位，但复位时机很难找（某个线程刚醒来就把 flag 复位，会让还没醒的线程永久等待 —— 这就是丢失唤醒）。

### 感反式（sense reversing）

让「相位」而不是「标志值」携带信息：每个线程**waiting 上一个 arrival-phase**，而不是等待「某一个 boolean 变成 true」。

```java
// 教学示意：感反式 barriers（不参与构建）
class SenseBarrier {
    private final AtomicInteger count = new AtomicInteger(0);
    private volatile boolean sense = false;             // 全局放行相位
    private final ThreadLocal<Boolean> mySense = ThreadLocal.withInitial(() -> true);

    void await(int n) {
        boolean my = mySense.get();                     // 我这一轮的本地相位
        if (count.incrementAndGet() == n) {             // 最后一个到达者
            count.set(0);
            sense = my;                                 // 翻转全局相位
        } else {
            while (sense != my) Thread.onSpinWait();    // 自旋等相位翻转
        }
        mySense.set(!my);                               // 翻转自己的相位，迎接下一轮
    }
}
```

要点：
- **不需要显式复位**，天然可复用（每轮的「我的相位」与「全局相位」交替错位）；
- 但仍然是**集中式**——N 个线程 CAS 同一个 `count`，`O(N)` 争用。

## 18.2 组合树屏障（Combining Tree Barrier）

把 N 个线程组织成树，每个内部节点只等自己的两个子节点：

```
        level log N (root)
         /        \
      ...        ...
     /   \      /   \
    T0   T1   T2   T3        ← 叶节点各为代表一个线程运送 sense 相位
```

- **通信总量**：`O(N)`（每个线程向上一次 + 向下一次），
- **关键路径**：`O(log N)`，
- **争用**：每个内部节点只有 2–4 个参与者（取决于 arity），不再有全局热点。

```java
// 教学示意：组合树节点（不参与构建）
static class Node {
    final int radix;                        // 每个节点的孩子数（实践中取 2 或 4）
    final Node parent;
    final AtomicInteger count = new AtomicInteger(0);
    volatile boolean sense = false;
    Node(Node parent, int radix) { this.parent = parent; this.radix = radix; }
}
```

**为什么 arity 常设为 2 或 4？** 太小则树太深（延长关键路径），太大则每个节点又成为局部热点；实践中还要考虑把节点**按 cacheline 对齐**并在 NUMA 上分形分组。

## 18.3 Tournament vs Dissemination

| 算法 | 论文出处 | 轮数 | 适用 |
| --- | --- | --- | --- |
| **Tournament barrier** | TOCS 1991 的可扩展同步一文 | `O(log N)` 下行 + `O(log N)` 上行 | 共享内存、线程数已知且固定 |
| **Dissemination barrier** | Hensgen, Finkel, Manber（IJPP 1988） | `O(log N)` 轮，每轮 `O(N)` 消息总量 | **无 butterfly 中心**；适合分布式/INC |
| **感反式集中屏障** | 教科书级 | 到达 `O(N)` 争用 | 线程数很小（≤ 8）时反而最快 |

**工程直觉**：线程数小（≤ 核数）时，集中式屏障因为几乎无 cacheline 迁移往往**更快**；只有当 N 大到几十上百（或跨 NUMA 节点），树形/传播式才真正占优。

## 18.5 近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **NUMA-aware barrier**：现代服务器是 NUMA 拓扑，把树形屏障的节点按 socket 分组（local barrier → global barrier）成为标准做法；多篇 2015 后文献把这类称为 **hierarchical barrier**。
- **异步/协程时代的屏障**：虚拟线程（JEP 444）与 goroutine 数量可达百万级，`Thread.activeCount()` 规模下的屏障几乎不再适用；于是 Go 的 `sync.WaitGroup`（引用计数，不等待 barrier 相位）成为事实标准。
- **GPU 侧的硬件屏障**：CUDA 的 `cooperative_groups::sync()` / `__syncthreads()` 由硬件 warp barrier 实现，代价远低于软件屏障；但当宽 wg across blocks 时仍需 multi-device barrier。
- **分布式屏障**：MPI_Barrier 使用 recursive doubling/dissemination（dissemination barrier 的现代版）；2020 年代 GPU 直连通信（NVLink / GPUDirect）让它进一步专业化。

**工业实现**：

| 实现 | star | 屏障形态 |
| --- | --- | --- |
| `openjdk/jdk`（≈**23.4k★**） | Java | `CyclicBarrier`（内部 `ReentrantLock` + `Condition`，集中式 + 支持 `breakBarrier`）；`Phaser`（分 phase 支持动态注册/注销参与者，最接近 PPoPP 2008 论文）；`CountDownLatch` 是一次性屏障 |
| `rust-lang/rust`（≈**119.1k★**） | Rust | 标准库 `std::sync::Barrier`（感反式 + Mutex 实现）；**C++20 的 `std::barrier`** 更是标准化了 **arrive / wait / arrive_and_drop** 三件套，本质是带 phase completion function 的组合树友好的接口 |
| `golang/go`（≈**139.0k★**） | Go | `sync.WaitGroup`（ Add/Done/Wait，没有「相位」概念的计数式屏障）；实践中大量使用 channel 做 rendezvous 式同步 |
| `NVIDIA/libcudacxx`（≈**2.3k★**） | GPU | `cuda::barrier` 在 shared memory 上实现 arrive/wait，直接对接硬件 MBarrier（Hopper 架构） |
| `open-mpi/ompi`（≈**2.6k★**） | HPC | MPI collective 的 barrier 实现了 dissemination / recursive doubling 等算法，并可由用户选择 |
| `abseil/abseil-cpp`（≈**18.1k★**） | C++ | `absl::Barrier` 是可动态参与的动态屏障；`absl::Mutex` 内部也大量使用 shared wakeup 优化 |

## 18.6 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「屏障可以随便 usize 复用」 | 感反式屏障的**每轮只允许同一批线程各进入一次**；重复使用需保证参与者集合一致 |
| 2 | 「屏障比互斥便宜」 | 屏障包含 **唤醒所有等待者**的开销；频繁调用时往往是 `park/unpark` 的系统调用代价主导，而不是所用同步算法 |
| 3 | 「线程数越多树形越快」 | 小规模下集中式更快（局部性好、开销小）；只有当线程数远大于核数时树形才显出优势 |
| 4 | 「屏障能顺便保证内存可见性」 | 屏障本身确实提供了同步-with 关系（release/acquire），但**屏障之间修改的数据**仍需遵守内存模型；在宽松内存序下要显式 `acquire/release` |
| 5 | 🔧 **`CyclicBarrier` 的线程必须多于 parties** | 若某競爭线程在 `await` 前异常退出，屏障将永久等待（generation 被 broken 需要显式 `reset()`）；这是线上常见的「卡住」来源 |
| 6 | 🔧 本书未讨论 spin vs block | 真实实现在自旋若干次后会 `park` 挂起线程；只讲自旋版本会高估 CPU 消耗 |
