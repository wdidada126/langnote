# 第 5 章 同步原语的相对能力

> **本章地图**：如何比较两个同步原语"谁更强" → **共识任务（consensus）** → **共识数（consensus number）** → 各类对象的共识数表（寄存器=1、TAS/FAA/swap=2、CAS/LL-SC=∞）→ **层次定理（hierarchy theorem）**：共识数为 n 的对象无法 wait-free 实现共识数 > n 的对象 → 一个重要推论：**共识数 ≥ n 的对象是通用的（universal）**，可以 wait-free 实现任意 n 线程对象（第 6 章）→ 并发计算中这些概念的现实意义。

## 二、核心精讲

### 5.1 用"共识"作为能力标尺
- **共识任务（Consensus）**：n 个线程各自持有一个私有的输入值，它们必须通过调用同一个对象的一组方法来达成：
  - **一致性（Agreement）**：所有线程决定同一个值；
  - **有效性（Validity）**：决定的值必须是某个线程的输入；
  - **可终止性（Termination）**：所有线程在有限步内完成决定（wait-free 语义）。
- 之所以选"共识"作为标尺：它是**最小非平凡协作任务**，反映出对象协调冲突的基本能力。

### 5.2 共识数（consensus number）
- 对象 X 的**共识数 CN(X)** 定义为：能用 X 与读写寄存器在 wait-free 条件下解决共识任务的**最大线程数 n**（若对所有 n 都成立，则为无穷）。
- 关键定理（Herlihy, TOPLAS 1991）：
  1. 若 X 能 wait-free 实现 Y，则 CN(X) ≥ CN(Y)；
  2. 因此可以形成**严格层次**：共识数低的对象不可能 wait-free 实现共识数高的对象。

### 5.3 常见对象的共识数（全书最值得记住的一张表）

| 对象 / 原语 | CN | 说明 |
| --- | --- | --- |
| **读写寄存器**（atomic register） | **1** | 只能解决 1 个线程的"共识"（无争抢情形） |
| **test-and-set, swap（getAndSet）, fetch-and-add, fetch-and-increment, fetch-and-decrement** | **2** | 只能解决 2 个线程的共识 |
| **queue, stack, deque, set, multi-valued fetch-and-add** | **2** | 看起来丰富但本质上与 TAS 同层 |
| **compare-and-swap（CAS）, load-link / store-conditional（LL/SC）, fetch-and-cons, move（memory-to-register move）** | **∞** | 可解决任意数量线程的共识 |

```java
// （教学片段，不参与构建）用 CAS 解决 n 线程共识：第一个 CAS 成功者决定所有人的返回值
public class Consensus {
    private final AtomicInteger r = new AtomicInteger(-1);   // 共识位点
    public V decide(V value) {
        agree(value);                                      // 把自己的提议写入 propose 数组
        return get proposal from propose[r.get()];         // r 一旦被填，所有线程读同一个槽位
    }
    private void agree(V value) {
        propose[ThreadID.get()] = value;                   // ① 各写各的
        if (r.compareAndSet(-1, ThreadID.get())) {         // ② 只有一个人 CAS 成功
            return;                                        //    成功者已被选中
        }
    }
}
```
- 上面的代码就是 **CAS ⇒ CN=∞** 的构造性证明（CAS 成功的那个线程，其 index 被所有人看到）。
- 反过来，**为什么 FAA 只有 CN=2**？核心原因：两个线程可以先用 FAA 争 "谁是第一个"，但第三个线程到来时无法在不覆盖前序信息的情况下判断"应该跟随谁"（informally：FAA 只能暴露一个计数，而 TAS/fetch&add 无法在其它线程的数量上编码"选择了谁"的信息）。

### 5.4 层次定理与推论
- **层次定理**：若 CN(X) = n < CN(Y)，则**不存在**只用 X 与寄存器 wait-free 实现 Y 的算法。
- 推论（三个最有用的结论）：
  1. 只有 CN ≥ n 的对象，才能作为 n 线程系统的"万能 goto"（第 6 章的通用构造）；
  2. **CAS 与 LL/SC 可以互相 wait-free 实现**（等价），且它们与 "fetch&cons" 处于同一层（∞）；
  3. 仅仅"看起来很强的"数据结构（队列、栈）其实比 CAS 弱很多 —— 一个只有入队/出队接口的对象，无法用来实现 lock-free 的任意算法。
- 🔧 实用意义：
  - 硬件为何必须提供 CAS（x86 `lock cmpxchg`、ARM LL/SC `ldxr/stxr`）：因为它是唯一能被证明可用于任意线程数通用构造的原语。
  - 为什么现代 CPU 上的原子指令普遍用 LL/SC 实现：它可以自然地实现 CAS 并具有更好的 ABA 行为相关 flags。
  - 为什么 Java 的 `AtomicInteger.getAndIncrement()` ≈ FAA（CN=2）却仍够用：因为 JVM 底层实际用 CAS 循环实现了它。
- 🔧 **m 值相关数据**的现实性：现代 **Fetch-and-add 是 CN=2**，因此一个只有 fetch-and-add 的系统（例如某些 GPU 上只有 atomicAdd）在理论上无法 wait-free 实现任意共识；这也是为什么 因此 GPU 编程通常依赖 SIMT 与相对确定的调度，而不是随意使用 CAS 算法。

## 四、近年研究与工业界开源实践

- **近年研究**：**共识层级思想在现代语言中的回应** —— Rust 的 `Send/Sync` 与 "typical type cannot be shared without atomics"、C++ `std::atomic` 的 `is_lock_free()` 与 `required_alignment` 设计；以及 **GPU/TPU 上的 collective primitives**（梯子使用 atomicAdd 而不是随机 CAS，正是 CN 理论的反应）。
- **工业界开源**（star 数 2026-09 实测）：
  - `openjdk/jdk`（≈23.4k★）：`VarHandle` 的 `compareAndSet` / `getAndAdd` / `getAndBitwiseXor` 是 SUTEME (JDK9+ JEP 193)；CPU 上 `getAndAdd` 会试图编译成 `lock xadd`（x86）而非 CAS loop，从而性能更好 —— 但理论上它 CN 更低，这就是理论与工程的一个有趣张力。
  - `rust-lang/rust`（≈100k★ 量级）：`AtomicUsize::compare_exchange`（含 `compare_exchange_weak`，呼应 LL/SC 的伪失败）与 `fetch_update`。
  - `JCTools/JCTools`（≈3.9k★）：其 ring buffer 使用明确的 CN=∞ 原语；注释里反复强调在某些平台上必须使用具有 set-associative CAS 的实现。
  - `google/nsync`、`abseil/abseil-cpp`（≈13k★ 量级）：Abseil 对 mutex/atomic 的底层抽象，展示了如何在不同 CPU 原语能力之间做适配。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "fetch-and-add 很强，可以替代 CAS" | FAA 的 CN=2，无法 wait-free 实现 3 线程共识，更写不出通用无锁结构 |
| 2 | "队列/栈这类结构可以拿来当同步原语" | 它们的 CN=2；能做的事不如一个 CAS 多 |
| 3 | "CAS 是推荐给应用开发者的终极工具" | CAS 虽然万能，但用错会 ABA、会 livelock；设计上应优先选组合好的结构（见 Ch9-15） |
| 4 | "有 FLP 不可能性就别管共识了" | FLP 是异步+故障下确定共识的不可能；共享内存模型下 CAS 的 wait-free consensus 依旧可行（两者前提不同） |
| 5 | 🔧 本书视角 | 本章是理论核心，但工程上绝大多数人写的是 lock-free 而非 wait-free；且现代 runtime 大量使用 hybrid approach（先 CAS 自旋、再 park），应把理论层次当作"能力上限"来读，而不是日常直接使用的工具 |
