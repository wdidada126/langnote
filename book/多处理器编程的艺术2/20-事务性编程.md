# 第 20 章 事务性编程

> **一句话**：事务内存试图把「加锁」的成本从程序员转移给运行时和系统——**乐观执行 + 冲突检测 + 回滚**；思想赢了（今天的数据库 MVCC/OCC 都在此列），但硬件实现（Intel TSX）已经退场。

---

## 本章地图

| 节 | 内容 | 关键结论 |
| --- | --- | --- |
| 20.1 | 事务的语义 | 原子性 + 可串行化 +（可选）隔离级别 |
| 20.2 | 硬件 HTM | cacheline 粒度冲突检测、容量限制、以及 TSX 的兴衰 |
| 20.3 | 软件 STM | 写缓冲 + 版本时钟（TL2 风格） |

| 20.5 | 今日现状 | HTM 退场，STM 退化为特定语言/数据库内部组件 |

**先修**：Ch3 可线性化（STM 把它扩展到一组操作）、Ch19 内存回收（STM 也引用旧版本）。

## 20.1 核心精讲：什么是事务

```java
// 教学示意：事务的编程模型（不参与构建）
atomic {                       // atomic { ... } 块
    if (a.balance >= amount) {
        a.balance -= amount;
        b.balance += amount;
    }
}
```

语义要求：

1. **原子性**：块内的所有写要么全部生效、要么全部不生效。
2. **可串行化**：并发事务的执行效果等价于某个串行顺序。
3. **隔离**：事务内部读到的中间状态对外不可见（由屏障/版本实现）。

与锁的本质区别：**冲突检测的时机**。悲观锁在「可能发生冲突」时就串行化；事务则假设不冲突、执行完再验证，赌率低时有收益。

### 冲突检测的两个流派

| 流派 | 何时检测 | 代表 |
| --- | --- | --- |
| **乐观读 + 提交校验**（快照版本时钟） | 提交前校验整个读集的版本号是否未变 | **TL2**（Dice, Shalev, Shavit, DISC 2006） |
| **写集加锁（悲观）** | 执行过程中就锁住写集的每一项 | 2PL 风格的 STM |
| **乐观执行 + 提交时验证** | 提交时才检测冲突 | **OCC 家族**（含数据库中的 Calvin / TicToc / BOHM） |

## 20.2 硬件事务内存 HTM

**基本原理**：

```
xbegin
  ... 读写被记录到 L1 cache 的 read-set / write-set ...
xend
  fallback handler（常用 "commitConflict handling"）
```

- 冲突粒度 = **cacheline**（这也是 HTM 最被诟病的一点：伪共享会直接导致事务无法提交）；
- 容量限制：read-set + write-set 通常不超过 **L1 的一半**（几十 KB）；
- 事务内不能做的事：系统调用、`cpuid`、cache-verifier 的某些指令、也许还有磁盘/网络 IO → **不可组合、不可取消工作的 Composite**。

**重要历史**：

| 年份 | 事件 |
| --- | --- |
| 1993 | Herlihy & Moss 提出 **TCC（Transactional Memory Coherence and Consistency）**，ISCA 1993 |
| 2004 | Hammond 等提出 **TCC 语言/体系**，以及 Sun 的 Rock 处理器草案（后来取消） |
| 2012 | Intel **TSX**（Haswell）发布：`RTM` / `HLE` 指令 |
| 2013 | IBM Power8 也引入 HTM；IBM Blue Gene/Q 早已到达更早版本 |
| 2019 | TSX 因微架构侧信道类安全漏洞（ZombieLoad 一类）在微码更新中被**禁用** |
| 2021 | Intel 在部分新 CPU 中完全移除 TSX；**Arm 引入 TME（Armv9-A，2021）** |

今天的结论：**HTM 作为一个通用编程模型已经退场**，只剩少量用途（例如把 TSX 作为锁的快速路径）。本书第 2 版成书时 TSX 尚可用，因此对这段结局只能做前瞻而无法改写。

## 20.3 软件 STM：TL2 的核心思路

```
全局版本时钟 GST
每个共享字 o 有一个 write-lock + version

开始事务 rv = GST
读 o：读 (o.value, o.version)；若 o 被加锁 或 o.version > rv ⇒ abort
      把 o 加入 read-set
写 o：写入线程的 private write-set（不直接写内存）
提交：
  1) 获得 write-set 中所有对象的锁（版本号 >= rv+1）
  2) 递增 GST（得到 cv），校验 read-set 中所有版本号是否仍 <= rv
  3) 若全部通过，把 write-set 的值写回内存并置 version = cv；释放写锁
```

**正确性直觉**：读集校验保证了「读到的数据在提交时仍然有效」（对应快照隔离中的 SSI 检查），写锁保证了提交的原子性。

```java
// 教学示意：STM 的核心读写标量（不参与构建）
final class TRef<V> {
    volatile V value;
    volatile long version;                  // 版本戳
    final ReentrantLock lock = new ReentrantLock();
}

// 简化版的 read/write/set/commit 省略失败回滚与 read-set 校验细节
```

**STM 的两难**：
- 读操作数 intrusive vs non-intrusive（是否需要修改被事务共享的数据布局）；
- **强隔离 vs 弱隔离**：事务与非事务代码混合访问同一对象时，强不可illustrate直观且代价高；弱隔离（例如 `weak atomicity`）需要与内存模型仔细互动。

## 20.4 事务提升（Transactional Boosting）

Herlihy & Koskinen（PODC 2008）提出：**不要试图让任意数据结构变成事务性的，而是利用它的 commutativity（可交换性）**。

做法：
1. 每个被事务管理的对象要提供**逆操作**（如 `push/pop`、`insert/remove`）；
2. 事务在提交前先取得所有被调用方法的抽象锁；
3. 若两个操作**可交换**（例如同一个集合上的两个 `add(x)`），则它们之间不必串行化。

```
直觉：锁的粒度 = 方法级；Boosting 的粒度 = 「是否可交换」，比方法级更粗。
```

这是本节最值得记住的思想：它把「锁的粒度」从方法级提升到「操作是否可交换」的代数层面，是今天 CRDT 与各类可交换复制研究的先驱。

## 20.6 近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **HTM 作为加速器而非主角**：2020 年代的主流不再是「让用户写 `atomic{}`」，而是把 HTM 用于_mutex 的快速路径。著名的失败案例包括 **Intel TSX 与 glibc 的锁消除实现**（因 Micro-Architectural Data Sampling 类漏洞而在 2019 后被回滚）。
- **数据库中的 newer 事务**：第 14–16 章（本书指 filesystem 侧的数据库教材，见 `book/数据库系统概念6/`）里的 MVCC、OCC、**SSI**（串行化快照隔离）、**确定性事务**（Calvin）本质上全是本章思路的后裔；近年的 **TicToc（VLDB 2016）**、**BOHM / Adaptive OCC** 等是把聘用时钟改为动态时间戳的直接延续。
- **持久内存上的事务**：PMEM 时代的事务要求 crash-consistency 与 concurrency control 同时成立，催生了少日志（logging-less）与无重做（no-redo）的新体系。

**工业实现**：

| 实现 | star | 说明 |
| --- | --- | --- |
| `clojure/clojure`（≈**11.0k★**） | Clojure | 唯一把 STM 作为语言级一等公民的主流语言：`ref` + `dosync`，基于 MVCC + 本质 (retry)，且接入了 `commute`（对应 boosted / commutative 操作） |
| `pmem/pmdk`（≈**1.4k★**） | C | `libpmemobj` 的事务 API（`TX_BEGIN/TX_END`），是今天仍活跃的「显式事务 API」工业实践之一，也说明本书第 20 章关心的问题在 PMEM 语境下重新变得重要 |
| `crossbeam-rs/crossbeam`（≈**8.6k★**） | Rust | 虽然不含 STM，但它的 `crossbeam-utils::CachePadded` 与 epoch 回收是写 TSX/STM 加速结构的标准配件 |
| `openjdk/jdk`（≈**23.4k★**） | Java | JVM 曾有 `Deuce STM`（科研项目）等尝试；HotSpot 内部的 GC 则有自己的 STW-transactional 概念。官方并没有 STM 支持 |
| `facebook/rocksdb`（≈**32.1k★**） | C++ | 有分布式的 `TransactionDB`，并且有乐观佩斯 options；这是本章事务 API 在存储引擎层的实际采用之处 |

## 20.7 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「STM 能取代锁」 | STM 只能在**可撤销、无副作用**的块内工作；IO、系统调用、native call 都无法回滚，必须放到事务之外 |
| 2 | 「HTM 冲突检测是变量级的」 | 是 **cacheline 级**；两个相邻变量会让事务反复冲突失败（这是 HTM 最大的工程陷阱） |
| 3 | 「TSX 现在还能直接用」 | 2019 年后 Intel 用微码禁用了 TSX（部分新 CPU 直接移除），Arm TME（2021）尚未普及；2026 年不应再做 HTM-first 的设计 |
| 4 | 「STM 的开销只来自重试」 | 写集缓冲 / 读集校验 / 全局版本号递增的成本同样重要；低争用下 STM 通常仍慢于手写的有锁或无锁结构 |
| 5 | 🔧 本书无法预知 HTM 的商业结局 | 本书第 2 版写于 TSX 停用之前；2020 年代的读者应把 HTM 部分当作技术史阅读，而把**「乐观 + 校验 + 回滚」的方法论**当作长期价值 |
| 6 | 🔧 与数据库事务混为一谈 | STM 的事务不要求持久化，也不需要 WAL / redo；数据库事务的 ACID 由 WAL/ARIES 保证。二者可以互相印证，但不应直接照搬 |
