# 第 12 章 计数、排序与分布式协调

> **本章地图**：看似平凡的**共享计数器**为什么不可扩展 → **软件组合（software combining）**：等待者把请求合并给 Leader → **组合树 / diffracting tree / flat combining** → **计数网络（counting networks / balancing networks）**：理论上彻底摆脱热点 → 并行排序（**bitonic sort / 并行归并 / sample sort**）→ 与第 18 章屏障的关系。

## 二、核心精讲

### 12.1 为什么朴素的共享计数器不可扩展

```java
// （教学片段，不参与构建）
// ① 朴素版：一个热点；所有线程在同一个 cacheline 上 CAS → 线程越多越慢
AtomicLong globalCounter = new AtomicLong();

// ② 分段版（JDK 8 LongAdder 的思想）：每线程/核一个 cell，读时求和
class StripedCounter {                                   // 每个 cell 单独pad 以避免伪共享
    long[] cells;  long base;
    public void increment() { cells[ThreadID.get() % cells.length]++; }   // 写路径无争用
    public long get() { return base + Arrays.stream(cells).sum(); }       // 读时才合并
}
```

- 🔧 代价：**`get()` 不再可线性化**（读到的是弱一致聚合）。这是典型的"用更弱语义换可扩展性"权衡；JDK 文档明确说明 `LongAdder.sum()` 只是最终一致。

### 12.2 软件组合（software combining）与组合树

**核心思想**：与其所有线程争抢同一个对象，不如让它们排队，并把请求沿树**合并**上来。

1. 树形结构，每个叶子/内部节点维护若干槽位；
2. 线程到达某节点后写入自己的操作，并尝试成为该节点的 Leader；
   - 成为 Leader 者：继续向上走到父节点参与更高层组合；
   - 失败者：留在原节点等待，Leader 返回时把该子树所有请求**打包执行**并回填结果；
3. 结果：k 个线程在该子树的多次自增最终只产生**一次对父/根的写**。

```java
// （教学片段，不参与构建）组合树节点协议（高度简化）
class CombiningNode {
    private final CombiningNode parent;
    private final AtomicReference<Object> locked = new AtomicReference<>(null);
    private final AtomicReference<Object> value  = new AtomicReference<>(null);

    Object visit(Object op) {
        CombiningNode stop = null;
        while (true) {
            if (locked.compareAndSet(null, current)) {        // ① 抢到本节点
                Object oldValue = value.getAndSet(null);
                if (oldValue == null) return parent.visit(op);// ② 继续向上成为 Leader
                return merge(oldValue, op);                   // ③ 把别人的操作并下来返回
            } else {                                          // ④ 未抢到：交给 Leader 帮做
                if (stop == null) stop = this;
                if (value.compareAndSet(null, op)) return combine(op);
            }
        }
    }
}
```

- **现代形态**：
  - `LongAdder` / `Striped64`：扁平化的组合（cells + 动态扩容）；
  - **flat combining**（Hendler et al., SPAA 2010）：极端简化 —— 一个线程拿到全局锁，然后**代表所有人**执行操作；多核上常常快过传统无锁结构；
  - 共同洞察：**争用本身的开销，远大于"让一个线程替大家干活"的成本**。

### 12.3 计数网络与平衡网络（Aspnes, Herlihy, Shavit）

- **平衡网络（balancing network）**：由若干 balancer 组成的网络；每个 balancer 把输入的 token 交替输出到两条输出线。
- **计数网络（counting network）**：若输出满足 **step property**（各输出线 token 数至多相差 1），即可在其上构造并行计数器 —— 线程从任意输入线进入，从输出线离开时取走一个预先安排好的值。
- **优势**：实现无锁甚至 wait-free，且不依赖某个中心热点；线程被分散到网络各入口。
- **局限（重要）**：线性化的计数网络必须足够宽 —— 存在"不能完全线性化且宽度更小"的不可能结果；且常数极大，工程几乎不用。

### 12.4 并行排序

| 算法 | 思路 | 特点 |
| --- | --- | --- |
| **Bitonic sort** | 固定结构的比较交换网络 | 结构规整，硬件/SIMD 友好，GPU 排序常用 |
| **并行归并排序** | 分治 + 并行多路归并 | CPU 上的主流（`Arrays.parallelSort`） |
| **Sample sort / PSRS** | 采样划分保证负载均衡 | 分布式 / 多机排序首选 |
| **Radix / Counting sort** | 非比较，线性复杂度 | 键域有限时的最优选 |

- 🔧 Java 对照：`Arrays.parallelSort` 内部用 `ForkJoinPool` + 并行归并，且**小数组会退化为顺序排序**（任务切分与合并的开销 > 并行收益）。并行流（`parallelStream`）同理，只有数据量大、无共享副作用、切分便宜时才划算。

### 12.5 与第 18 章的关系
- 屏障（barrier）= **计数器 + 唤醒机制**；组合树天然就是"感反式组合树屏障"的骨架，详见第 18 章。
- 本章只记住一句：**分布式协调（barrier）与共享计数（counter）是同一枚硬币的两面**。

## 四、近年研究与工业界开源实践

- **近年研究**：批处理天然适合 SIMD，因此出现了把 flat combining 与向量化结合的工作；**自适应 hybrid counter**（低争用用单原子变量，检测到争用后自动切换到 cells 集合）已成为标准做法，JDK 8 的 `Striped64` 就是其代表；**松弛计数（approximate counter）的可证明误差界**研究也与本章的"用语义换扩展"一脉相承。
- **工业界开源**（star 数 2026-09 实测）：
  - `openjdk/jdk`（≈23.4k★）：`LongAdder` / `Striped64`（cells + 动态扩容 + 伪共享填充）与 `Arrays.parallelSort` 的退化阈值实现，是本章概念最直接的对照。
  - `openjdk/jmh`（≈4.5k★）：测量并发计数器扩展曲线的正确工具。
  - `JCTools/JCTools`（≈3.9k★）：带填充的原子变量与伪共享测试集。
  - `rayon-rs/rayon`（≈12k★）：Rust 侧的并行排序 / 并行迭代器，`par_sort` 与 Java 的并行归并可直接对照阅读。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "`AtomicLong` 已经足够可扩展" | 高争用下是 cacheline ping-pong；热计数应用 cells / 分段 |
| 2 | "`LongAdder.sum()` 精确" | 只保证最终一致；需要精确值时仍用 `AtomicLong` |
| 3 | "计数网络应该在项目里用" | 常数太大，几乎无落地；真正落地的是 cells 与 flat combining |
| 4 | "`parallelSort` 总比顺序排序快" | 小数组会因阈值退化；并行流也有同样问题 |
| 5 | "批处理/组合一定是无锁的" | flat combining 通常用锁，收益来自局部性而非无阻塞 |
| 6 | 🔧 本书视角 | 本章的计数网络部分理论价值大于工程价值；应把注意力放在"组合 ⇒ cells / batching"这条演化主线上 |
