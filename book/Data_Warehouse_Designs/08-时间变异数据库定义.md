## 8.1 主力形态：Type2 区间维（⚠️ 重构 DDL 骨架）

```sql
CREATE TABLE cust_scd2 (
  customer_id   INT,          -- 业务键（非唯一！）
  segment       VARCHAR,      -- 时变属性
  valid_from    DATE,         -- 版本生效日（含）
  valid_to      DATE          -- 版本失效日（含），开放版本用哨兵 '9999-12-31'
);
```

- 与星型主键的区别：`customer_id` 不再唯一，唯一性让位于 `(customer_id, valid_from)`；
- 事实关联从 `JOIN USING(customer_id)` 升级为 **BETWEEN 谓词**——07 章 as-of 纪律的物理落点；
- 哨兵值 vs NULL：本册统一哨兵（7.5 反模式之对治）；书中是否如此 ⚠️ 不可考。

## 8.2 🔧 实测 E4：双口径的账面分裂（DuckDB 1.5.5，非本书示例引擎）

数据：客户 1（Silver→2010-07-01 升 Gold）、客户 2（Bronze→2011 升 Silver）、客户 3
（Silver→2011 升 Gold）；六笔订单跨 2010/2011。2010 全年聚合，真实输出（`exp.py`）：

```text
[Type1 现状口径] 2010 汇总按客户『现在的』segment:
  ('Gold', 1400)
  ('Silver', 400)
[Type2 时点口径] as-of 订单日的 segment（BETWEEN valid_from/valid_to）:
  ('Silver', 1100, 2)
  ('Bronze', 400, 1)
  ('Gold', 300, 1)
```

**解读（本章的全部论点浓缩在此六行里）**：同一批订单，「按今天的等级」Gold 拿走 1400，
「按当时的等级」Gold 只有 300——2010 年的 Gold 贡献**几乎全部是升级后的幻影**（客户 1 升 Gold
前的 500 与客户 3 的 600 都发生在其还是 Silver/Bronze 之时）。6.2-2 所谓幸存者偏差不是修辞，
是 1400 与 300 的差。两口径没有谁「对」：**答哪一问就用哪张表**——这正是第 12 章要「定义」
的东西：现状表 `cust_current` 与时点表 `cust_scd2` 并存、各司其职 ⚠️（双表并存策略是否书中
原案不可考，标 ⚠️ 重构立场）。

## 8.3 装载器：Type2 的版本手术（⚠️ 重构伪码）

```text
对源侧每条 (customer_id, segment_new):
  若 现开放版本.segment == segment_new: 忽略（幂等）
  否则:
    UPDATE cust_scd2 SET valid_to = d-1 WHERE customer_id=? AND valid_to='9999-12-31';
    INSERT cust_scd2 VALUES (?, segment_new, d, '9999-12-31');
迟到更正（07 章 7.1-2）: 目标日 d 落在既有版本区间内部 ⇒ 原版本劈为两段+新插——
  2012 手工 ETL 之痛；今日 MERGE/宏的标准化对象（演进节）。
```

- **变化检测面**：单列比较即可（segment 一属性时）；多时变属性时须**整行指纹**
  （校验和/hashdiff——与 vault 同题，9.2 🔧E5 见）⚠️。

## 8.4 查询面：as-of 的三种写法与坑（⚠️ 工程清单）

1. **区间 BETWEEN**（🔧E4 所用）：`ON id=id AND d BETWEEN from AND to`——要求版本全覆盖，
   缺区间即丢行；
2. **向前最近**（向前取最近版本）：相关子查询 `valid_from=(SELECT max(...) WHERE valid_from<=d)`——
   稀疏版本表容错，但 2012 引擎上慢 ⚠️；DuckDB 1.5.5 一行 `ASOF JOIN` 即此语义 🔧（✅ docs 页）；
3. **双口径并呈**：一条查询同时 JOIN 两表出 `revenue_asof` 与 `revenue_current` 两列——
   7.2 命名规约的查询示范 ⚠️ 编者加。

## 8.5 🔧 实测 E6：SQLite 3.45.3 跨引擎复现（补充组，非本书引擎）

同一 SCD2 数据与 as-of 查询（`substr(d,1,4)='2010'` 代 `year()`）：

```text
sqlite as-of 2010: [('Silver', 1100), ('Bronze', 400), ('Gold', 300)]
与 E4 DuckDB Type2 口径对比: 逐值一致
```

结论：as-of 语义是**纯 SQL 逻辑**，不依赖 2012 年某方言特性——本册所有时态论证可在家用级
引擎复演；Type1/Type2 的「口径分裂」同样在 SQLite 复现（改 JOIN 目标即得 1400/400 版），
读者动手 ⚠️。

## 8.6 表形态选型一览（第 12 章「数据库定义」的重构总结）

| 形态 | 结构税 | 能答 | 不能答 |
| --- | --- | --- | --- |
| Type1 覆盖 | 无 | 现状口径一切 | 任何「当时」 |
| Type2 区间 | 行数×版本 | 当时+现状（现状=哨兵行） | —（全能，代价是纪律） |
| Type3 旧值列 | 一列 | 一步历史 | 两步前 ⚠️（7.6-3 实验） |
| 快照表 | 行数×全史长度 | 任意周期点 | 周期内变更 |
| 固化进事实 | 事实加宽 | 该属性当时值 | 属性的过去未来 |

## 8.7 精读要点与思考题

1. 🔧E4 若把客户 3 的升级日改到 2010-05-01：两口径各变多少？（600 从 Silver/Bronze 侧迁 Gold 侧，
   区间重叠检查随之而来——8.3 手术的正确性测试。）
2. 为什么「现状」可以**不建表**而用 `WHERE valid_to='9999-12-31'` 从 Type2 派生？——派生口径
   与书中（⚠️ 不可考）双表并存策略之争：双写税（一致性）vs 每查过滤税（性能），7.3 矩阵思维。
3. 8.3 的整行指纹若用 `md5(status||'|'||amt)` 且字段含 NULL：DuckDB 里 `||` 遇 NULL 吞整串——
   对勘 vault 阵营的 NULL 填充盐值惯例（9.2 对照）。

## 核心概念速览（中英对照）

- **Type2 区间维** — SCD2 Interval Dimension：`(键, 有效起, 有效止)` 版本行，业务键非唯一（8.1）。
- **哨兵开区间** — Sentinel Open Range：`valid_to='9999-12-31'` 表当前版本（8.1/7.5）。
- **口径分裂** — Divergent Totals：同事实集在 Type1/Type2 下聚合值不同（🔧E4 1400 vs 300）。
- **版本手术** — Version Surgery：闭旧段+开新段；迟到则劈区间（8.3）。
- **整行指纹** — Row Hash / Hashdiff：多属性变化检测的摘要列（8.3，vault 同题）。
- **BETWEEN 关联** — Interval Join：as-of 的覆盖完备写法（8.4-1）。
- **向前最近** — As-of Nearest：取 ≤t 的最新版本；DuckDB `ASOF JOIN` 语义（8.4-2）。
- **双口径并呈** — Dual-Perspective Columns：一查询同时出 as-of 与 current 两值（8.4-3）。
- **快照表** — Snapshot Table：周期点全量切片，区间法的对价形态（8.6）。
- **跨引擎复现** — Portability Check：E6 SQLite 逐值=E4 DuckDB，论证纯 SQL 性（8.5）。

## 最新演进与工业实践

2012→2026（✅ URL 均 2026-10-02 `curl -L` 200；机制 ⚠️ 转述）：

- **原生时态表**：SQL:1999/2011 temporal 子集与商用实现（Postgres 扩展、BigQuery
  system-versioned）把 8.3 版本手术下沉为 DDL 一行 `SYSTEM_TIME`——本册手工区间维护成为

- **ASOF JOIN 大众化**：DuckDB/Spark/Iceberg 生态把 8.4-2 的向前最近从相关子查询提速为
  一等算子（✅ https://duckdb.org/docs/；本机 1.5.5 实测语法可用，**非本书引擎**）；
  SQLite 仍无原生 as-of，8.5 的 BETWEEN 写法是其上限。
- **dbt snapshots / incremental SCD2 宏**：8.3 伪码的工业模板化（hash 对比、自动闭段）——
  变化检测面从单列到整行指纹已被宏封装（盘上 dbt 册 ls ✅ 登记级）。

  `Data_Lakehouse_in_Action` 方向登记 ⚠️ 未逐页核）。
- **编者按**：🔧E4 六行输出值得背下来——它是「时变维 ROI」的最短证明：**1400 与 300 都真，
  问题决定用哪个数**；第 12 章「定义」的从来不是表，是回答权。
