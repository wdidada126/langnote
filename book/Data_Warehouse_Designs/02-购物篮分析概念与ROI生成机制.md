## 2.1 MBA 是什么（第 2 章主场，⚠️ 重构）

- **业务问题**：哪些商品被同一顾客在同一交易（篮）中一起购买？「啤酒与尿布」式发现只是传播梗，
  工程问题是一般化的：**从交易流水中提取商品间共现结构，并使其可随数据滚动持续刷新**。
- **数据原子**：篮-商品二部关系。一行 = (basket_id, product)，篮是事务键——这正是 04 章
  集市形态（fact 粒度到篮×商品行）的种子。
- **三个度量**（本章的概念内核，⚠️ 教科书通用定义对位）：
  - 支持度 support(X,Y) = 同含 X、Y 的篮占比——「值不值得看」；
  - 置信度 confidence(X→Y) = 含 X 的篮里也含 Y 的占比——「规则有多灵」；
  - 提升度 lift(X,Y) = P(Y|X)/P(Y)——「是相关还是随大流」（>1 正相关，≈1 独立，<1 互斥）。

## 2.2 🔧 实测 E3：support/confidence/lift 的手术台式复现（DuckDB，非本书示例引擎）

10 个篮子（bread 6 篮、butter 5、milk 5…）自连接共现表，真实输出（`exp.py`，DuckDB 1.5.5）：

```text
('bread', 'eggs',   1, 10.0, 0.17, 1.67)
('bread', 'butter', 4, 40.0, 0.67, 1.33)
('bread', 'milk',   3, 30.0, 0.5, 0.83)
('bread', 'juice',  1, 10.0, 0.17, 0.83)
```

列序：`(x, y, 共现篮数, support%, conf x→y, lift)`。读数 ⚠️：bread&butter 共现 4/10 篮
（support 40%、conf 0.67）是**高频强规则**；bread&eggs 仅 1 篮但 lift 1.67（eggs 稀少，共现即
强信号）——support 与 lift 分歧正是「先定义你要哪类规则」（03 章难点）的最小实证。SQL 形态：
自连接 `a.basket_id=b.basket_id AND a.product<b.product` 去镜像，`cnt` 子查询供分母。

## 2.3 MBA 如何产生 ROI（第 3 章主场，⚠️ 重构）

按章题「How Does … Produce ROI?」，收益通道可枚举为四类 ⚠️：

1. **货架与动线**：高 lift 对 → 邻近陈列/关联端架，直接拉动连带率；
2. **交叉销售**：篮内下一件推荐（电商「买了 X 的人也买 Y」的前身即离线 MBA）；
3. **促销组合**：捆绑定价、满减门槛设到共现峰上（bread+butter 组合毛利结构）；
4. **异常与漏损**：某门店强规则突然衰减 → 缺货/陈列异常的早期信号（监控型 ROI）。

**ROI 机制的数仓侧要求**（本章与第 1 章总纲的钩子）：四类收益全部要求「**规则随新数据自动
刷新**」——一次性挖掘报表不产生持续 ROI；这直接推出 04 章的增量 ETL 设计与 05 章装载细节。
⚠️ 编者重构：这是书题把 MBA 与「Achieving ROI」绑定的原因。

## 2.4 MBA 与「分析在库内还是库外」的路线问题

- 第 3/5 章解法定义 ⚠️ 的一个关键取舍：关联规则计算（Apriori 式枚举）本质是组合爆炸，
  2012 年工程现实是「**数仓供料 + 算法引擎出规则 + 规则回写集市供 BI 消费**」三段式。
- 本书站队（按 Part I「Architecture and Database Design」章存在性推定 ⚠️）：数仓内保留
  **篮粒度原子事实与规则结果表**，重计算外包给算法工具——数仓做「可核对的事实底座」。
- 今日对照 ⚠️：从 Spark/MLlib 到向量检索式推荐，「库供料、外计算、回写」三段式依旧成立
  （feature store 是其变体）——本册 🔧E3 的纯 SQL 共现只适用于低维度小商品集，但教学价值
  在于**规则形态的白盒理解**。

## 2.8 三测度手算演练（读 🔧E3 之后的纸笔配套）

用 2.2 的十篮数据集在纸上走一遍，建立对 SQL 输出的直觉：

```text
单品篮数: bread 6, butter 5, milk 5, eggs 1, juice 2, cereal 2
bread&butter 共现: 篮 {101,102,105,109} = 4
support(b,butter) = 4/10 = 40%
confidence(bread→butter) = 4/6 = 0.67
P(butter) = 5/10 = 0.50  →  lift = 0.40/(0.60×0.50) = 1.33
bread→eggs: 共现 1 篮 → conf 1/6=0.17；P(eggs)=0.10 → lift=0.10/(0.60×0.10)=1.67
```

- **对照读数**：butter 规则胜在「量」（40% 覆盖），eggs 规则胜在「质」（lift 更高）——
  促销选前者做流量款捆绑、陈列选后者做边缘货架信号，**同一份共现表两种用法**；
- 若把 eggs 那一篮（103）复制 20 次：support(eggs) 暴涨、lift 回归 1 附近——
  「稀有品的共现含金量」在分母里的数学原因（练习 ⚠️，改 `exp.py` 数据段即可验证）；
- 手算与 SQL 的差：CTE 版 `cnt` 的分母来自**同一次扫描**，手算来自清单——两边对不上时
  先查篮键去重（4.5 的漂移反模式在这里已能伏击）。
- 教学顺序建议：先 🔧E3 再 2.8（眼见数字→手上复现），倒过来则实验沦为验证而失去发现感 ⚠️。


## 核心概念速览（中英对照）

- **购物篮分析** — Market Basket Analysis, MBA：从交易流水提取商品共现结构并持续刷新的分析形态（✅ 章题）。
- **篮** — Basket / Transaction：一次购买的商品集合，MBA 的事实粒度单位。
- **支持度** — Support：同含一对商品的篮占比；「值不值得看」的门槛（🔧E3 第 4 列）。
- **置信度** — Confidence：P(Y|X)，规则 X→Y 的命中率（🔧E3 第 5 列）。
- **提升度** — Lift：P(Y|X)/P(Y)，剥离单品流行度后的真相关信号；>1 为正关联（🔧E3 第 6 列）。
- **共现自连接** — Co-occurrence Self-Join：`basket_id` 等值 + `product<product` 去镜像的 SQL 模式（🔧E3）。
- **收益四通道** — ROI Channels：货架动线/交叉销售/促销组合/异常监控（2.3 ⚠️ 重构枚举）。
- **三段式** — Warehouse-to-Algo-to-Mart：数仓供料、算法出规则、结果回写集市（2.4 ⚠️ 立场推定）。
- **序列模式** — Sequential Pattern：跨时间先后链，本章边界外登记（2.5）。
- **规则刷新** — Rule Refresh：MBA 区别于一次性挖掘的持续 ROI 要件（2.3 钩子）。

## 最新演进与工业实践

2012→2026（✅ URL 均 2026-10-02 `curl -L` 200；机制 ⚠️ 转述）：

- **从 Apriori 到嵌入**：经典支持度枚举被「向量相似 + LLM 重排」的推荐管线吸收，但**离线共现
  白盒规则**在货架陈列、合规促销审批场景仍是不可替代口径（可解释性溢价 ⚠️）。
- **特征库化**：2.4 的三段式 今日常以 feature store 面世——规则表作为下游模型的受治理特征，
  口径登记走数据目录线（盘上 The_Enterprise_Data_Catalog_2e，ls ✅）。
- **湖上共现**：DuckDB/ClickHouse 类引擎让 🔧E3 这种「小商品集纯 SQL MBA」在中数据量
  （亿级行内）重新可行：列存聚合 + `count DISTINCT` 优化使「库内直接出规则」的 2012 禁忌
  部分解封（✅ https://duckdb.org/docs/ 聚合与 JOIN 序；本机 1.5.5 实测即证，**非本书引擎**）。
- **实时化残余**：促销期分钟级规则刷新仍靠流式窗口聚合（Flink 线，盘上波6册登记级）；
  本书「按周刷新」的 ETL 节奏在 2026 已成下限而非上限 ⚠️。
- **反例教学**：「lift>1 即上架捆绑」是流传最广的误用——须叠加毛利与时区稳定性检验；
  2.2 数据里 bread&eggs（1 篮，lift 1.67）即「小样本假强规则」的活标本（⚠️ 编者按）。
