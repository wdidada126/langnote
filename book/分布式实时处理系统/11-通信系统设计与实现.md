## 核心精讲

### 11.1 为什么必须 I/O 多路复用

呼应第 4 章 4.3：流处理框架有海量长连接（Executor 间、Executor 与 President），
「每连接一线程」撑不住。Meshy 用**单/少数线程 + epoll/kqueue** 监听所有 fd 的可读/可写事件。

```text
# 教学示意，不参与构建：epoll 事件循环(定性)
epfd = epoll_create()
for each fd: epoll_ctl(epfd, ADD, fd, {IN})
loop:
    events = epoll_wait(epfd, timeout)      # 一次等所有 fd
    for ev in events:
        if ev.IN:  onReadable(ev.fd)        # 收字节, 攒成消息帧(11.3)
        if ev.OUT: onWritable(ev.fd)        # 把发送缓冲刷出去
```

### 11.3 把 TCP 字节流切成消息帧

原书强调网络库必须解决「**粘包/拆包**」：TCP 是字节流，应用消息（tuple 帧）边界要自己定。
常见做法：长度前缀帧（4 字节长度 + body）。

```cpp
// 教学示意，不参与构建：长度前缀帧解包(Meshy 思路)
// 发送: [uint32 len][payload]
// 接收: 先读 4 字节 len, 再按 len 读 body, 凑齐才算一条消息
struct Frame {
    uint32_t len;
    std::vector<char> body;  // 反序列化出 Tuple(见6.6)
};
```

> 这正呼应 [02-](02-分布式系统通信基础.md) 2.5 的「TCP 可靠 ≠ 应用消息可靠」：
> Meshy 在 TCP 之上补**消息边界 + 序列化**，tuple 才能正确复原。

### 11.5 跨平台：epoll vs kqueue

原书用宏隔离两套实现（Linux 用 epoll，macOS 用 kqueue），上层事件循环接口统一。
这是 C++ 网络库的典型做法（类似 libevent/libuv）。

## 版本演进

- **本书无第二版**；本节写 2016 年口径 → 2026 年视角的变化。
- **自研 Meshy vs 现成库**：2026 年 C++ 项目多用 **libevent / libuv / Boost.Asio /
  seastar** 而非自研 epoll 封装；自研易在边界情况（半关闭、EPOLLET 惊群、缓冲区管理）出错。
- **io_uring**：Linux 5.x 的 `io_uring` 提供比 epoll 更高效的异步 I/O，
  是 2026 年高性能网络库的新选项（🔧 补 11.1）。
- **HTTP/2 + gRPC**：11.4 手写 HTTP 在现代被 gRPC（基于 HTTP/2）取代，C++ 有原生支持。
- **零拷贝 / DPDK**：极致吞吐场景绕过内核协议栈（见第 4 章 🔧 补丁）。

## 近年研究与工业界开源实践（2015–2026）

- **Seastar 用户态网络**：`scylladb/seastar` 用 DPDK + 共享无关 + 纤程，
  把 C++ 网络性能推到硬件极限，是 11.1/11.3 思路的激进演进。
- **Boost.Asio / libuv**：工业级跨平台事件循环，省去 11.5 自研跨平台分支。
- **gRPC（C++）**：`grpc/grpc` 让管控/数据面直接获得 HTTP/2 多路复用，弱化手写 11.4 HTTP 的必要性。
- **io_uring 生态**（如 `tokio-uring`、C++ 的 `liburing++`）：2026 年高性能服务端新宠。

## 常见误区与本书需修正之处

| # | 误区 | 事实 | 书目 |
| --- | --- | --- | --- |
| 1 | 「TCP 会自动分好消息」 | 必须自己处理粘包/拆包（长度前缀等） | 11.3 |
| 2 | 「epoll 比 select 只是快一点」 | select 有 fd 数量上限与 O(N) 扫描；epoll 无上限 O(1) 就绪 | 11.1 |
| 3 | 「自研网络库最可控」 | 边界情况极多，易错；2026 应优先成熟库 | 11.1/11.3 |
| 4 | 🔧 应补「io_uring」 | 比 epoll 更高效的新异步 I/O | 11.1 |
| 5 | 🔧 应补「零拷贝/DPDK」 | 极致吞吐需绕过内核栈 | 11.3 |
| 6 | 🔧 应补「背压如何经网络传递」 | 背压信号需在网络层表达，本书未覆盖 | 11.6 |
