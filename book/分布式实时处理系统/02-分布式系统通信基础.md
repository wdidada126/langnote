## 核心精讲

### 2.5 为什么流处理框架要自己管 TCP

原书把 TCP 的可靠传输机制讲清楚，是为了说明：Storm/Hurricane 在 TCP 之上还要再建一层
**（ZeroMQ / Meshy）来保证「消息不丢、不重、有序」**，因为 TCP 只保证**字节流**可靠，
不保证**应用消息**（tuple）的可靠——断连重传后应用层要自己识别重复与缺失。

```text
# 教学示意，不参与构建：TCP 可靠 ≠ 应用消息可靠
TCP 保证:  字节流按序、不丢、不重到达对端内核
但不保证:  应用层把字节流切成"消息"后对还是错

所以流框架要建:
  1) 消息边界(定长/分隔符/长度前缀)  -> 把字节流还原成 tuple
  2) 序列号/acker                      -> 检测丢失与重复(见第10章)
  3) 背压(🔧 2026)                     -> TCP 流控不等于应用背压
```

### 2.7 自定义「公告牌」协议

原书用一个「公告牌（Bulletin Board）」场景串起应用层协议设计：节点用自定义报文
（含消息类型/长度/负载）互相发布/订阅信息。这是后面第 3 章 Thrift 公告牌、第 11 章
Meshy 报文格式的设计雏形。

> 🔧 2026 视角：2016 年手写私有二进制协议很常见；今天更常用 **Protobuf/gRPC**
> 或 **JSON over WebSocket**，手写协议的成本与出错率都高，仅在极致性能场景保留。

### 2.8 MapReduce 的「存储即通信」

原书指出 MapReduce 的 worker 之间**不直接通信**，而是都读写 HDFS：
map 输出落 HDFS，reduce 再读。这是一种「以共享存储代替消息传递」的范式，
与 Storm/Hurricane 的「消息流直连」恰好对照——后者延迟更低但耦合更强。

## 版本演进

- **本书无第二版**；本节写 2016 年口径 → 2026 年视角的变化。
- **2.7 的私有协议 → 标准 IDL**：2026 年手写二进制协议基本被 Protobuf/FlatBuffers
  取代；序列化详见 [03-通信系统高层抽象.md](03-通信系统高层抽象.md) 3.4。
- **2.6 的 HTTP**：第 11 章手写 HTTP 在 2016 年合理，今天直接用 **libcurl / Boost.Beast /
  gRPC** 即可；且流框架管控面多用 gRPC 而非裸 HTTP。
- **2.8 的「存储即通信」**：2026 年演变为 **Kafka/Pulsar 作为流存储总线**——
  既像共享存储（可重放）又像消息流，是 MapReduce 与 Storm 两种范式的融合。

## 近年研究与工业界开源实践（2015–2026）

- **HTTP/2 与 gRPC 普及**：`grpc/grpc`（C/C++ 一等公民）让 2.6 的裸 HTTP 退居数据面，
  管控面几乎都用 gRPC；这对 C++ 流框架尤其友好（原生支持）。
- **eBPF 与可观测网络**：2020 年后 eBPF 让内核态网络观测/加速成为可能，
  是 2.4/2.5 网络层在云原生时代的新工具（本书未涉及）。
- **QUIC/HTTP3**：基于 UDP 的可靠传输（RFC 9000, 2021）重新思考「传输层可靠」，
  与本书 2.5 的 TCP 视角形成对照——未来高性能框架可能绕过 TCP 内核栈。
- **RDMA**：在 2.5 可靠传输之上提供内核旁路超低延迟，是 2026 年高性能分布式系统的
  网络层选项（本书未涉及，且 C++ 直连 RDMA 仍小众）。

## 常见误区与本书需修正之处

| # | 误区 | 事实 | 书目 |
| --- | --- | --- | --- |
| 1 | 「TCP 可靠 = 我的消息可靠」 | TCP 只保字节流；应用消息的边界/去重/丢失检测要自己建（见 10 章） | 2.5 |
| 2 | 「分层只是教科书概念」 | 分层让各层独立演进；违反分层（如应用层绕过 TCP 直接吃 IP）会埋坑 | 2.3 |
| 3 | 「去中心化一定优于集中式」 | 两者各有适用；集中式（如本书 President，第 8 章）协调简单，代价是单点 | 2.1 |
| 4 | 🔧 应补「背压不在传输层解决」 | TCP 流控 ≠ 应用背压；流系统需独立背压机制（Flink/Storm 都有） | 2.5 |
| 5 | 🔧 应补「QUIC/RDMA 等现代传输」 | 2026 年高性能传输已不只 TCP 一条路 | 2.5 |
| 6 | 🔧 手写私有协议应被 IDL 取代 | 2026 年 Protobuf/FlatBuffers 是默认，手写二进制协议易错 | 2.7 |
