## 核心精讲

### 9.3 Collector::emit——连接「用户逻辑」与「框架传输」

`emit` 是用户代码与框架内部唯一的出口。它要做三件事（教学要点）：

```cpp
// 教学示意，不参与构建：emit 的内部职责(简化)
void Collector::emit(const Tuple& t, Grouping g) {
    // 1) 按分组策略 g 决定下游 Task 集合(shuffle/fields/all...)
    auto targets = resolveTargets(t, g);
    // 2) 序列化 tuple (见6.6/第3章序列化)
    auto bytes = serialize(t);
    // 3) 交给网络层发送给 targets; 同时通知 acker 登记(见第10章)
    for (auto tid : targets) network->send(tid, bytes);
    acker->register(t);   // 锚定: 这条 tuple 进入"待确认"树
}
```

> `emit` 同时是 [10-可靠消息处理.md](10-可靠消息处理.md) acker 机制的**钩子点**：
> 发出的 tuple 必须登记到 acker，才能在其完整处理后被 ack。

### 9.1 / 9.2 基类降低用户负担

原书提供 `BaseSpout` / `BaseBolt` 之类基类，预置空实现与通用字段
（如 collector 引用、messageId 生成），用户只覆盖业务方法：

```cpp
// 教学示意，不参与构建：用户只需填业务
class WordSpout : public BaseSpout {
    void nextTuple() override {
        Tuple t; t.push_back(randomWord());
        collector->emit(t);              // 9.3 的 emit
    }
};
```

## 版本演进

- **本书无第二版**；本节写 2016 年口径 → 2026 年视角的变化。
- **emit 与状态分离**：本章 `emit` 只管发 tuple；2026 年 Flink 把**状态（keyed state）**
  作为一等公民内建于算子，用户不必自己在 Bolt 里维护外部存储的状态，也不必由 acker 兜底。
- **API 表达力**：声明式（Flink `map`/`filter`/`window`、Kafka Streams DSL）取代
  命令式 emit，代码更短、优化空间更大。

## 近年研究与工业界开源实践（2015–2026）

- **Flink 算子 + 状态后端**：`apache/flink`（26367★）的 `RichMapFunction` 带
  `open()`/`getRuntimeContext().getState()`，把「emit + 状态」合并管理，比本书
  9.1/9.2/9.3 分离式更内聚。
- **Kafka Streams DSL**：`apache/kafka`（33849★）的 `stream.map().filter().to()`
  全声明式，省略手写 Collector。
- **Beam SDK**：跨引擎（Flink/Spark）统一的 `ParDo`/`DoFn`，是 9.x 接口抽象的升华。

## 常见误区与本书需修正之处

| # | 误区 | 事实 | 书目 |
| --- | --- | --- | --- |
| 1 | 「emit 只是发数据」 | emit 还负责分组路由、序列化、acker 登记 | 9.3 |
| 2 | 「Bolt 里自己管状态最灵活」 | 自管状态难容错；现代框架内建状态后端 | 9.2 |
| 3 | 🔧 应补「状态后端/checkpoint」 | 可靠性由框架 checkpoint 兜底，非用户手搓 | 9.2/9.3 |
| 4 | 🔧 应补「声明式 API 优势」 | 命令式 emit 表达力弱、优化空间小 | 9.1/9.3 |
