> 原书第 6 章进入**「动手时间」第一篇**：正式设计 Hurricane 的对外编程接口。

## 核心精讲

### 6.1 Hurricane 总体架构（角色划分）

原书给出 Hurricane 的组件拓扑，对应 Storm 但自研了主控：

```text
# 教学示意，不参与构建：Hurricane 逻辑架构
President  (主控/协调者, 类 Storm Nimbus + ZooKeeper 合一, 见第8章)
   │  管理 Topology 分配、节点注册、任务调度
   ▼
Executor   (工作进程, 类 Storm Worker, 见第7章)
   ├─ Task(Spout)  -> 跑 ISpout, 经 Collector 发 Tuple
   └─ Task(Bolt)   -> 跑 IBolt, 收 Tuple, 经 Collector 再发
        │
        ▼  Tuple 流 (经 Meshy 网络, 第11章)
   下游 Task(Bolt)
```

### 6.2 / 6.3 / 6.4 三个核心接口（契约）

原书把编程接口定义成纯虚接口，让用户只填业务逻辑：

```cpp
// 教学示意，不参与构建：Hurricane 接口契约(简化)
struct Tuple { /* 字段列表 + 流ID + messageId, 见6.5 */ };

struct Collector {
    virtual void emit(const Tuple& t, Grouping g = shuffle) = 0; // 6.4
};

struct ISpout {
    virtual void open() = 0;              // 初始化数据源
    virtual void nextTuple() = 0;          // 拉/推下一条, 经 collector->emit
    virtual void ack(int64_t msgId) = 0;   // 该 tuple 被完整处理(见第10章)
    virtual void fail(int64_t msgId) = 0;  // 处理失败 -> 重发
};

struct IBolt {
    virtual void prepare() = 0;
    virtual void execute(const Tuple& input) = 0; // 处理并可能 collector->emit
    virtual void cleanup() = 0;
};
```

> 这套接口与 Storm 的 `ISpout`/`IBolt` 几乎同名同构——本书明确是「复刻 Storm 范式」，
> 差异在 C++11 实现细节与自研 President/Meshy。

### 6.5 / 6.6 Tuple 与序列化

Tuple 是字段的异构容器（类似 Storm 的 `Values`）。6.6 要求 tuple 能被序列化跨节点传输，
呼应第 3 章 3.4 的序列化抽象与第 9 章的具体实现。

## 版本演进

- **本书无第二版**；本节写 2016 年口径 → 2026 年视角的变化。
- **6.1 的「自研 President 主控」**：Hurricane 把「Nimbus（调度）+ ZooKeeper（协调）」
  合一成自研 President；2026 年更稳妥的做法是用 **Kubernetes + 内嵌 etcd/Raft** 或
  现成协调服务，而非自研主控（自研易在容错上踩坑）。见第 8 章 🔧 补丁。
- **6.2/6.3 接口范式**：2026 年 Flink 的 `DataStream API` / `ProcessFunction`
  已取代「Spout/Bolt」这种细粒度算子，提供窗口/状态/时间等内建原语；Storm 式接口偏底层。
- **6.4 分组策略**：现代框架内建 keyed state + 按 key 分区，比「fields grouping」更自然。

## 近年研究与工业界开源实践（2015–2026）

- **Flink DataStream API**：`apache/flink`（26367★）的编程模型把「Source/Operator/Sink」
  取代 Spout/Bolt，并内建**状态（StateBackend）+ 窗口 + 事件时间**，应用无需自己管
  acker/事务（对比本书 6.2/6.3 + 第 10/12 章）。
- **Kafka Streams DSL**：`apache/kafka`（33849★）的 `KStream`/`KTable` 用声明式 API
  取代命令式 Spout/Bolt，体现「流批一体 + 表流双语义」。
- **Storm 自身**：`apache/storm`（6695★）仍提供 Spout/Bolt API，但已非主流。
- **多语言 Source/Sink 生态**：Flink/Beam 的 connector 体系（Kafka/Pulsar/JDBC/…）
  远比 Hurricane 第 13 章的自研多语言接口工程化。

| # | 误区 | 事实 | 书目 |
| --- | --- | --- | --- |

| 2 | 「自研主控最灵活」 | 自研 President（Nimbus+ZK 合一）容错易踩坑；2026 多用 K8s+etcd | 6.1 |

| 5 | 🔧 应补「connector 生态」 | 数据源/落地靠标准 connector，而非每项目自研 | 6.2 |
