# 第 13 章　大数据

> 原书第 13 章是全书收尾，讲「分布式存储技术的第二个应用域：大数据」。
> 这一章在 2013 年是**技术前沿快照**，今天读则是**一部换代史**：
> 13.2 的 MapReduce、13.4 的 S4/Storm、13.5 的 Greenplum/Vertica/Dremel，
> 在 2026 年分别被 **Spark/Flink、Flink/Kafka Streams、ClickHouse/DuckDB/BigQuery** 取代或演化。
> **但这一章的问题框架依然有效**：批处理 / 图计算 / 流式计算 / 交互式分析，
> 四类负载的划分今天仍然是大数据平台的组织方式。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 13.1 大数据的概念 | **4V**：Volume（大量）、Velocity（高速）、Variety（多样）、Value（价值） | 大数据不是「数据多」，而是**多到/快到/杂到传统系统处理不了** |
| 13.2 MapReduce | Map 阶段（拆分并行）、Shuffle（按 key 汇聚，**性能瓶颈所在**）、Reduce 阶段（聚合） | 用**简单的两阶段模型**换来自动并行与容错 |
| 13.3 MapReduce 扩展 | Google Tenzing（SQL on MR）、Microsoft Dryad（DAG 通用化）、Google Pregel（图计算） | MR 太死板 → 上层加 SQL、底层换成通用 DAG、特化出图计算 |
| 13.4 流式计算 | 原理、**Yahoo S4**、**Twitter Storm** | 批处理回答「过去发生了什么」，流处理回答「现在正在发生什么」 |
| 13.5 实时分析 | MPP 架构、EMC Greenplum、HP Vertica、Google Dremel | 交互式分析要靠 **MPP + 列存 + 嵌套列存** |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 13.1 4V：大数据的定义

| V | 英文名 | 含义 | 处理手段 |
| --- | --- | --- | --- |
| 大量 | Volume | 数据规模到 PB 级 | 分布式存储 + 分布式计算 |
| 高速 | Velocity | 数据产生快，要求实时处理 | 流式计算 |
| 多样 | Variety | 结构化 / 半结构化 / 非结构化混杂 | 多模存储、schema-on-read |
| 价值 | Value | 数据总量大但价值密度低 | 分析挖掘、机器学习 |

### 13.2 MapReduce：两阶段模型与它的瓶颈

```text
# 教学示意，不参与构建：MapReduce 的三段
Map(k1, v1)      ->  list(k2, v2)     # 并行地"拆"：输入分片 -> 中间键值对
Shuffle          ->  group by k2       # 把相同 key 的值搬到一起（**全量网络传输**）
Reduce(k2, list(v2)) -> list(v3)       # 并行地"合"：每个 key 一个 reduce 任务

为什么 Shuffle 是瓶颈:
    - 它是**全量数据的一次重新分布**，网络与磁盘都要扛
    - Map 端能做 combiner（本地预聚合）缓解，但无法消除
    - 落盘 + 排序 + 跨机拉取，是 MR 延迟居高不下的根本原因
```

- **MapReduce 的真正贡献不是「两个函数」**，而是把
  **并行化、数据分发、容错（重算失败的任务）、负载均衡** 全部藏进框架。
  这是本书 3.x 分布式系统思想在计算层的直接应用。

### 13.3 MapReduce 的三条扩展路线

| 项目 | 思路 | 贡献 |
| --- | --- | --- |
| **Google Tenzing** | 在 MR 之上实现 **SQL 查询**（编译器把 SQL 翻译成 MR DAG） | 让分析人员用 SQL 而不是 Java 写分析（后来的 Hive/Impala/Presto 一脉） |
| **Microsoft Dryad** | 把「Map → Shuffle → Reduce」泛化成**任意 DAG** | 表达能力远超两阶段，是现代 DAG 执行引擎（Spark/Flink）的祖先 |
| **Google Pregel** | 面向**图计算**的 BSP（整体同步并行）模型：以顶点为中心、超步迭代 | 图算法不必再扭曲成 MR 的多轮迭代 |

```text
# 教学示意，不参与构建：三条扩展路线指向同一个结论
MR 的问题: 表达的模型太窄（只有两阶段），迭代计算代价极高（每轮都要读写 HDFS）
Tenzing:  在 MR 上加一层 SQL        -> 解决"好不好用"
Dryad:    把两阶段换成任意 DAG      -> 解决"能不能表达"
Pregel:   为迭代型负载换模型        -> 解决"迭代能不能快"
=> 三者合流 = 2026 年的通用 DAG 引擎 + SQL 层 + 迭代优化（Spark/Flink）
```

### 13.4 流式计算：从「批」到「流」

- **原理**：数据以**事件流**形式持续到达，系统在事件到达时就处理，
  而不是攒成一批。核心问题是：
  1. **时间语义**：事件时间（event time） vs 处理时间（processing time）——乱序是常态；
  2. **窗口**：滚动 / 滑动 / 会话窗口，用来把无限流切成有限的桶；
  3. **投递语义**：at-least-once / at-most-once / **exactly-once**；
  4. **状态管理**：聚合状态要能容错恢复（checkpoint / savepoint）。
- **Yahoo S4（13.4.2）**：早期的分布式流计算平台，
  以**去中心化 + 对称节点**为特点，处理单元（PE）按 key 路由。
- **Twitter Storm（13.4.3）**：以 **topology（spout + bolt 组成的 DAG）** 为核心抽象，
  提供「至少一次」语义，曾是最广泛使用的实时计算框架。

> **读这一节的正确姿势**：S4 与 Storm 是**流式计算的史前形态**。
> 它们证明了「实时处理有刚需」，但**没有解决事件时间与 exactly-once** 这两个真问题。

### 13.5 实时分析：MPP 三杰

| 系统 | 路线 | 特点 |
| --- | --- | --- |
| **MPP 架构**（13.5.1） | 大规模并行处理：数据分片 + 每个节点独立计算 + 结果汇总 | 交互式分析的通用骨架 |
| **EMC Greenplum**（13.5.2） | 开源/商业 MPP 数据库，基于 PostgreSQL | 用 SQL 跑大规模分析，后来的开源 MPP 一脉 |
| **HP Vertica**（13.5.3） | **列式存储** MPP（C-Store 的商业化） | 列存 + 压缩 + 向量化，分析查询的标杆形态 |
| **Google Dremel**（13.5.4） | **嵌套列存 + 树状聚合服务树**，秒级响应 | BigQuery 的直接前身 |

```text
# 教学示意，不参与构建：Dremel 为什么能"秒级"扫 PB
1. 嵌套列存: 把嵌套数据结构（protobuf 式）按列切开存储
             -> 只扫描查询涉及的列
2. 重复/定义级别（Repetition/Definition Levels）: 记录嵌套结构信息
             -> 列存也能还原嵌套记录
3. 服务树（serving tree）: 多级聚合，根节点汇总
             -> 把一次大查询拆成上百个并行子任务
```

## 版本演进

- **本书无第二版**；本节写 2013 年 → 2026 年的变化。**本章是全书换代最彻底的一章。**
- **13.2 MapReduce 已被取代**：2026 年主流批处理引擎是 **Spark**（内存 RDD/Dataset +
  DAG 调度）与各类 SQL 引擎（Presto/Trino）。MapReduce 作为**模型**仍在教材里讲，
  但作为**生产引擎**已很少使用。
- **13.4 的 S4 / Storm 已被取代**：
  - Storm 的核心抽象（spout/bolt DAG）被 **Apache Flink** 继承并超越——
    Flink 补上了本书时代缺失的两件事：**事件时间 + 水印（watermark）** 与
    **exactly-once 状态一致性**（基于分布式快照）；
  - 轻量的流处理需求大量由 **Kafka Streams / 各类 CDC 管道**承接。
- **13.5 的格局变化**：
  - Dremel → **BigQuery**（商业化托管），并影响了一整代云原生数仓；
  - 列存 MPP 的开源代表变成 **ClickHouse**（MergeTree 列存）与 **DuckDB**（嵌入式向量化列存）；
  - SQL-on-HDFS 的中间层从 Hive 演进为 **Trino/Presto** 与 Spark SQL。
- **流批一体成为共识**：本书把 13.3（批）与 13.4（流）分开讲，
  2026 年主流是**同一套引擎同时支持批与流**（Flink 的「有界流/无界流」、
  Spark 的 Structured Streaming），并用 **湖仓表格式**统一存储。
- **存储层的底座也换了**：本书默认 HDFS；2026 年是**对象存储 + Parquet/Iceberg/Delta/Hudi**。
  这与第 4、12 章的补丁是同一件事。

## 近年研究与工业界开源实践（2015–2026）

- **实测 star（2026-09，`gh api` 实测）**：

| 项目 | 与本章的关系 | star |
| --- | --- | --- |
| `apache/hadoop`（含 MapReduce/HDFS） | 本章 13.2 的开源实现（存量巨大） | 15669 |
| `apache/iceberg` | 大数据存储的现代表格式 | 9276 |
| `delta-io/delta` | Delta Lake 表格式 | 9020 |
| `apache/hudi` | Hudi 表格式（增量处理） | 6275 |

- **MapReduce 的退场与 Hadoop 的存续**：
  `apache/hadoop`（15669★）仍被大量使用，但**主要是 HDFS 与 YARN**，
  计算层多半已换成 Spark/Flink/Trino。**「Hadoop」这个词今天主要指存储与调度，不是 MapReduce。**
- **流批一体取代 Storm/S4**：Flink 成为事实标准之一，
  关键差异正是本书 13.4 缺的两点：**事件时间语义**与 **exactly-once 一致性**。
  本书 13.4 介绍的两个系统今天只具有**历史价值**。
- **实时分析的开源主力更替**：ClickHouse（列存 MergeTree）与 DuckDB（嵌入式向量化列存）
  承接了本书 13.5 的 Vertica/Greenplum 角色；云上则是 BigQuery（Dremel 后裔）
  与各云的数仓服务。
- **湖仓表格式把存储层换了**：Parquet 成为列存文件事实格式，
  Iceberg/Delta/Hudi 在其上提供 ACID 与 schema 演进——
  这与第 4 章（DFS → 对象存储）、第 12 章（云存储成为底座）的补丁是同一件事。
- **AI 负载进入大数据栈**：2026 年的大数据平台普遍要同时服务
  报表分析、特征工程与向量检索，这使得「一种引擎通吃」更加不成立，
  本书 13.x 按负载分类的思路反而更实用了。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「MapReduce 就是 map 和 reduce 两个函数」 | 真正的贡献是**并行化 + 数据分发 + 容错 + 负载均衡**全部由框架承担 |
| 2 | 「Shuffle 只是中间步骤」 | 它是 MR 的**性能瓶颈**：全量数据重新分布 + 落盘 + 排序 |
| 3 | 「流处理和批处理是两套无关技术」 | 2026 年主流是**流批一体**（有界流 = 批）；本书分开讲是时代局限 |
| 4 | 「Storm 提供 exactly-once」 | Storm 的基础语义是**至少一次**；exactly-once 需要上层保证（且代价高） |
| 5 | 「Dremel 只是快」 | 它的关键是**嵌套列存 + 重复/定义级别**，使半结构化数据也能列存化 |
| 6 | 「Vertica / Greenplum 只是商业 MPP」 | 它们分别代表**列存派**与 **PostgreSQL 派**两条 MPP 路线，思想影响持续至今 |
| 7 | 🔧 13.2 的 MapReduce 作为生产引擎已被 Spark/Flink/Trino 取代 | 2026 年 MapReduce 主要在教学与少量存量作业中出现 |
| 8 | 🔧 13.4 的 S4 / Storm 已被 Flink / Kafka Streams 取代 | 本书时代缺的**事件时间 + 水印 + exactly-once** 是换代的核心 |
| 9 | 🔧 13.x 默认 HDFS 为存储底座 | 2026 年是**对象存储 + Parquet + 表格式（Iceberg/Delta/Hudi）** |
| 10 | 🔧 本书没有「湖仓」这一层 | 表格式把「数据湖」与「数据仓库」合并成湖仓，是本章 13.5 之后的重大演进 |
