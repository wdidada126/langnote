# 第 10 章　数据库功能

> 原书第 10 章讲 OceanBase 0.x 的**上层**：SQL 层与事务层。
> 前一章（第 9 章）解决「数据怎么放」，本章解决「**SQL 怎么跑、事务怎么做**」。
> 四节内容正好构成今天任何数据库的四个必备模块：
> **只读查询（10.2）/ 写事务与 MVCC（10.3）/ 分析型负载（10.4）/ 场景化特色能力（10.5）**。
> 2026 年读这章的重点是：10.4 的 OLAP 支持在本书里还只是「附加能力」，
> 而今天它已经长成 **HTAP（行存 + 列存 + 资源隔离）** 这条主线——
> OceanBase **2024 年推出列式存储**正是本章思路的完成形态。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 10.1 整体结构：一条 SQL 的分布式之旅

```text
# 教学示意，不参与构建：分布式 SQL 的五步
1. 解析（Parser）       : SQL -> 语法树（AST）
2. 校验（Resolver）     : 语义检查（表/列是否存在、权限、类型）
3. 优化（Optimizer）    : 逻辑改写（谓词下推、列裁剪、常量折叠）
                          + 物理计划（选 join 算法、选索引、决定是否并行）
4. 分布式化（Scheduler）: 把计划切成可在多台机器上执行的片段（fragment）
5. 执行（Executor）     : 各片段在 ChunkServer/MergeServer 上运行，
                          通过 exchange/shuffle 交换数据，最终汇总返回客户端
```

- **物理操作符接口**：本书采用经典的**迭代器模型**
  （`open / next(row) / close` 三方法），每个算子（表扫描、过滤、投影、连接、分组、排序）
  都实现同一接口，从而可以**任意嵌套组合**成算子树。

```text
# 教学示意，不参与构建：算子树（Volcano/迭代器模型）
project(cols)
└── hash_join(orders.user_id = users.id)
    ├── table_scan(orders)  WHERE amount > 100   ← 可被下推到 ChunkServer A/B/C
    └── table_scan(users)                        ← 可被下推到 ChunkServer D/E
# 每个算子: open() 初始化; next() 取一行; close() 收尾
# 分布式化: 在 table_scan 之上插入 exchange 算子，把结果跨机搬运
```

### 10.2 只读事务：快照读 + 执行本地化

- **只读事务的语义**：读的是**某个版本号的快照**（由 UpdateServer 分配），
  因此**读不阻塞写、写不阻塞读**——这正是第 2 章 MVCC 的分布式版。
- **单表操作**：表扫描（全表 + 过滤）、**索引扫描**（利用 SSTable 的块索引与布隆过滤器）、
  投影、聚合、排序、`LIMIT`（可下推，避免全量搬运）。
- **多表操作**：连接（join）。
  - **嵌套循环连接**：适合外层结果集小、内层有索引；
  - **归并排序连接**：两边有序时最优（在有序 SSTable 上天然友好）；
  - **哈希连接**：大表对大表的主力算法（本书 10.5 的「大表左连接」就是它的优化）。
- **SQL 执行本地化**（本节的核心工程经验）：

```text
# 教学示意，不参与构建：为什么要"SQL 执行本地化"
naive:  ChunkServer 把原始数据全部传给 MergeServer，由它算
        -> 网络传输量 = 原始数据量（可能是结果集的几千倍）
better: 把过滤/投影/部分聚合**下推**到数据所在的 ChunkServer
        -> 网络只传"已经算过的中间结果"
        -> 这就是"计算靠近数据"，也是本书 2.1 硬件前提的直接后果
```

### 10.3 写事务：执行流程与 MVCC

- **写事务执行流程**（0.x 的单点写版本）：
  1. 客户端把写 SQL 发给 MergeServer；
  2. MergeServer **先读基线**（判断行是否存在、是否满足 WHERE）；
  3. 生成修改操作（insert/update/delete）发给 **UpdateServer**；
  4. UpdateServer 在内存 B+ 树上应用修改、检测写写冲突、写 commit log 并强同步到备机；
  5. 提交成功返回；**版本号**随之推进。
- **多版本并发控制（MVCC）**：

```sql
-- 教学示意，不参与构建：OB 0.x 的快照读规则（与本书 2.4.2 InnoDB 版同构）
-- 每行带"创建版本号 / 删除版本号"，读事务持有一个读版本号 read_version
SELECT * FROM t WHERE pk = ?
-- 可见条件: create_version <= read_version AND (delete_version > read_version OR 未删除)
-- UPDATE: 记为 (旧行 delete_version = 本事务版本) + (新行 create_version = 本事务版本)
```

- **关键设计**：
  - 读事务**不加锁**，只读自己版本号的快照；
  - 写事务在 UpdateServer 上（0.x）天然串行化，因此**写写冲突在单点上解决**；
  - 分区化之后（1.0+），跨分区写需要 **2PC**，冲突检测与 MVCC 仍按版本号进行。

### 10.4 OLAP 业务支持：并发查询与列式存储

- **并发查询**：把一个大查询**拆成多个子查询并行执行**
  （按 tablet 范围切分，多台 ChunkServer 同时算），结果再汇总。
  这与本书 3.3 的「顺序分布 + 子表」直接相关：**子表就是天然的并行单位**。
- **列式存储**：分析型查询通常只碰少数几列，
  本书的做法是在 SSTable 里**按列组（column group）**组织数据，
  使扫描只读取需要的列——即本书 2.6.2 列存思想的存储引擎落地。

> 本章 10.4 是全书**最容易被低估的一节**：2013 年它还只是「附加能力」，
> 而 2026 年「一份数据同时跑 TP 与 AP」已经是主流诉求（HTAP）。

### 10.5 特色功能：真实业务倒逼出来的两个能力

- **大表左连接**：典型场景是收藏夹——
  「商品大表 LEFT JOIN 用户收藏小表」，数据量悬殊。
  优化思路是**把小表广播/建哈希，大表按分片并行扫描**，
  避免对大表做全量排序或全量网络传输。
- **数据过期与批量删除**：
  很多业务数据只保留 N 天（如日志、临时记录）。
  做法是把**过期条件写进元数据**（按时间分区/按版本），
  删除时**只改元数据或在合并时顺带回收**，而不是逐行 DELETE——
  这与本书 9.4 的「定期合并」天然配合（墓碑 + 合并时回收）。

## 版本演进

- **本书无第二版**；本节写 2013 年（OB 0.x SQL 层）→ 2026 年的变化。
- **10.1 优化器的代差**：本书的优化器以**规则改写为主**；
  2026 年主流是**代价基优化（CBO）**——收集直方图与基数估计、
  枚举 join 顺序与物理算子、按代价选计划，并加入**自适应执行与计划反馈**。
- **10.2 执行模型的代差**：本书是**行式迭代器模型**（一次一行）；
  2026 年分析型执行普遍用**向量化（一次一批，MonetDB/X100 一脉）+ 编译时代码生成**。
  这条差别决定了 OLAP 性能的数量级。
- **10.4 从「附加能力」变成主线（HTAP）**：
  - OceanBase **2024 年推出列式存储**，行存 + 列存共存，一份数据同时服务 TP 与 AP；
  - 2023 年起官方口径为「**一体化（all-in-one）数据库**」：OLTP + OLAP + KV（OBKV）+ AI 负载；
  - 这是本章 10.4「并发查询 + 列式存储」的**完成形态**。
- **10.3 写事务的架构变化**：0.x 的写集中在单点 UpdateServer；
  2016 年 V1.0 之后是**分区 + 多副本共识 + 跨分区 2PC + 全局时间戳（GTS）**。
  MVCC 的核心思想（版本号 + 快照读）不变，但**版本号的来源从单机递增变成全局时间戳**。
- **SQL 兼容成为一等目标**：本书 10.1 只要求兼容 MySQL 协议；
  2026 年国产数据库普遍追求 **MySQL / Oracle 双兼容**（OB 官方口径强调兼容 Oracle 与 MySQL），
  因为迁移成本是选型的第一约束。

## 近年研究与工业界开源实践（2015–2026）

- **实测 star（2026-09，`gh api` 实测）**：

| 项目 | 与本章的关系 | star |

| `cockroachdb/cockroach` | 对比参照：分布式 SQL 执行 + HLC 事务 | 32508 |

- **HTAP 的三条实现路线**（本章 10.4 的 2026 年答案）：
  1. **同份数据行列混合**（OB 4.x 列存）：一份数据既有行存也有列存，
     优化器按负载选择，一致性最好；
  2. **独立列存副本**（TiDB 的 TiFlash）：行存主副本 + 列存 learner 副本，
     通过 Raft 日志同步，隔离性好但有复制延迟；
  3. **资源隔离下的混合执行**（多数商业库）：同一引擎靠资源组隔离 TP 与 AP。
- **向量化 + 编译执行成为 OLAP 标配**：本书 10.1 的行式迭代器模型
  在分析场景下已被**向量化（批式）**取代；这条演进与本书 2.6.2 列存一节相辅相成。
- **代价优化器的工业水平**：2026 年的优化器普遍具备
  直方图/采样统计、多列相关性估计、自适应 join 顺序、plan cache 与 plan baseline。
  本书 10.1 的优化器描述属于「能用」级别，与现代 CBO 不是一个代际。
- **OceanBase 的功能演进（与本章直接对应）**：
  - 2022 V4.0 单机分布式一体化 → SQL 层要同时支持单机与分布式计划；
  - 2023 一体化概念 → TP/AP/KV/AI 多种负载共一套 SQL 引擎；
  - 2024 列式存储 → 本章 10.4 的完成形态；
  - 官方口径强调**兼容 Oracle 与 MySQL**（语法、过程语言、数据类型）。
- **多模能力**：OB 提供 OBKV、兼容 HBase API 等接口，
  使「SQL 层」不再是唯一入口——这与本书 10.1「SQL 是唯一接口」的假设不同。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「分布式 SQL 只是把 SQL 发到多台机器执行」 | 关键是**计划切分 + 数据交换（exchange/shuffle）+ 下推**；下推不到位会让网络成为瓶颈 |
| 2 | 「join 只是 join」 | 三种 join 算法（嵌套/归并/哈希）的适用场景完全不同；大表左连接要专门优化（本书 10.5） |
| 3 | 「MVCC 的版本号是时间」 | 是**逻辑版本号**（事务号/全局时间戳）；分布式下由 GTS/TSO/HLC 提供 |
| 4 | 「读快照不需要版本号协调」 | 分布式下**读哪个版本**必须由一个全局时钟决定，否则会读到「半截的事务」（→ 第 3、7 章） |
| 5 | 「列存只是为了省空间」 | 更重要的是 **I/O 裁剪 + 向量化**；本书 10.4 只强调了压缩与扫描量 |
| 6 | 「批量删除就是 DELETE 一堆行」 | 应走**元数据标记 + 合并时回收**（本书 10.5 的思路），否则写放大与合并压力巨大 |
| 7 | 🔧 本书 10.1 的优化器/执行器是 2013 年水平 | 2026 年是**CBO + 向量化 + 编译执行 + 自适应**；本书的行式迭代器模型只适合理解原理 |
| 8 | 🔧 本书 10.4 的 OLAP 只是附加能力 | 2026 年是 **HTAP 主线**；OB 2024 年推出列式存储，行存 + 列存共存 |
| 9 | 🔧 本书 10.3 的写事务基于单点 UpdateServer | 2016 年 V1.0 起改为**分区 + 共识 + 跨分区 2PC + GTS**；MVCC 思想不变但版本来源变了 |
| 10 | 🔧 本书只有 MySQL 兼容目标 | 2026 年国产库普遍追求 **MySQL + Oracle 双兼容**（迁移成本是选型第一约束），且提供多模接口（OBKV / HBase API） |
