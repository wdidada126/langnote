### 2.1 硬件基础：把延迟刻进脑子

本书给出的经典数量级（原书 2.1.4 性能参数表，2026 年仍需背诵，但**数值需按新硬件打折**，见「版本演进」）：

| 操作 | 原书数值 |
| --- | --- |
| 访问 L1 Cache | 0.5 ns |
| 访问 L2 Cache | 7 ns |
| 内存访问 | 100 ns |
| 千兆网络发送 1MB 数据 | 10 ms |
| SATA 磁盘寻道 | 10 ms |
| SSD 访问延迟 | 0.1 ~ 0.2 ms |

以及存储层次架构（原书把「容量 / 延迟 / 带宽」按**单机层 / 机架层 / 集群层**三档列出）：

| 层级 | DRAM | Disk | SSD |
| --- | --- | --- | --- |
| 单机层 | 24GB, 100ns, 20GB/s | 4TB, 10ms, 300MB/s | 1TB, 0.1ms, 300MB/s |
| 机架层 | 1TB, 300µs, 100MB/s | 160TB, 11ms, 100MB/s | 40TB, 2ms, 100MB/s |
| 集群层 | 30TB, 500µs, 10MB/s | 4.8PB, 12ms, 10MB/s | 1.2PB, 3ms, 10MB/s |

**这张表要这样读：** 从单机层到集群层，**延迟涨一个数量级、带宽掉一个数量级**。
于是整个分布式存储的设计哲学可以浓缩成一句：

> **尽量把计算推到数据附近，尽量让跨机器的交互变成顺序批量 I/O。**

CPU 架构一节（SMP → NUMA）在此只记结论：

```text
SMP（对称多处理）：所有 CPU 共享同一套内存与总线  →  核数一多总线就成瓶颈
NUMA（非一致内存访问）：每个 CPU 节点带本地内存，跨节点访问更慢  →  可扩展，但软件须感知「内存离谁近」
```

> 补一条现代事实：**现代多核 CPU 内部也有类似 NUMA 的非对称结构**（每核独享 L1/L2、共享 L3），
> 「NUMA 感知」在 2026 年已下沉到数据库内核的**内存分配器与线程绑核**层面。

### 2.2 三种单机存储引擎

#### 2.2.1 哈希存储引擎（以 Bitcask 为例）

- 磁盘：**只追加（append-only）**的日志文件，每条记录是
  `key / value / key_sz / value_sz / timestamp / crc`；
- 内存：哈希表 `key → (file_id, value_pos, value_sz)`；
- 读写：写 = 一次追加 + 一次内存更新（极快）；读 = 一次哈希 + 一次磁盘读（O(1) 次寻道）；
- 维护：**定期合并（merge）**扫描老数据文件、同一 key 只留最新值；
- 恢复：把内存哈希表**转储成索引文件**（hint file），重启时读索引文件而不是重放全部数据。

```text
# 教学示意，不参与构建：Bitcask 的读写与合并
put(k, v):  append(active_log, crc_record(k, v))      # 顺序写一次
            mem_index[k] = (file_id, offset, len)     # 内存更新一次
            # 无原地修改，旧值留在老文件里，由 merge 回收
get(k):     (fid, off, len) = mem_index[k]            # 一次哈希
            pread(file(fid), off, len)                # 一次随机读
merge():    扫描老数据文件，同 key 只留最新 -> 生成新数据文件 + 新索引文件
```

- 天花板：**所有 key 必须装进内存**（本书给的例子：value 平均 1KB、索引 32 字节时
  磁盘/内存比约 32:1）；且**不支持范围扫描**。

#### 2.2.2 B 树存储引擎

- 以**页（page，典型 4KB）**为单位，与磁盘块对齐；每个节点一个页，分支因子几百；
  百万级键的树高通常 3–4 层；
- 写是**原地更新**：改一个值要读出页、修改、写回，还要先写 **WAL（redo 日志）**保证崩溃安全；
- 关键代价：**页分裂**带来写放大与碎片；并发靠 **latch（锁存器）**保护树结构；
- MySQL InnoDB 的 B+ 树是这一族的工程标准形态（叶子带链表，便于范围扫描）。

#### 2.2.3 LSM 树存储引擎（以 LevelDB 为例）

- **LSM-Tree（Log-Structured Merge-Tree）**：把随机写变成顺序写，靠后台合并来偿还。
- 写路径：写**操作日志** → 应用到**MemTable**（内存有序结构，常为跳表）→
  MemTable 满则冻结为 Immutable MemTable → 后台线程**转储为 SSTable（L0）**；
- 读路径：先查 MemTable，再按**由新到旧**查各级 SSTable；靠**布隆过滤器**避免无谓的磁盘读；
- 合并：
  - **minor compaction**：内存数据转储到 SSTable；
  - **major compaction**：多路归并，丢弃被覆盖与删除（墓碑）的记录。

```text
# 教学示意，不参与构建：LSM 的读写路径与三种放大
write(k,v):  WAL append -> MemTable.put(k,v)        # 顺序写，故写吞吐高
read(k):     MemTable -> Immutable -> L0 -> L1 -> ... -> Ln
             # 层数越多读越慢；每层配 Bloom filter 挡掉"肯定没有"
compaction:  归并相邻层 SSTable，删除旧版本与墓碑
  写放大 = 同一字节被反复重写的倍数
  空间放大 = 同一 key 多版本并存造成的冗余
  读放大 = 一次点查要看的文件数
```

> **三种放大（write / read / space amplification）**是 2026 年讨论存储引擎的标准语言，
> 本书 2013 年只给了定性描述，量化框架是后来补的（见「近年研究」段）。

### 2.3 数据模型：从文件到关系，是一条「语义递增」的路

- **文件模型**：以目录树 + 字节流组织，系统不理解内容；
- **关系模型**：二维表 + schema，SQL 是声明式接口（**只说要什么，不说怎么取**），这是「易用性」的来源，也是分布式化的难点；
- **键值模型**：只有一个主键维度，`get/put/delete`，语义最弱、最容易拆分；
- **SQL 与 NoSQL**：NoSQL 不是在反对 SQL 语法，而是在**放弃一部分模型能力**（join、二级索引、强事务）换取可扩展性。

### 2.4 事务与并发控制

- **ACID**：原子性（全做或全不做）、一致性（约束不被破坏）、隔离性（并发事务互不看见中间态）、持久性（提交后不丢）。
- **四种隔离级别与五类异常**（本书 2.4.1 的经典对照表）：

| 隔离级别 | 丢失更新(第一类) | 脏读 | 不可重复读 | 第二类丢失更新 | 幻读 |
| --- | --- | --- | --- | --- | --- |
| Read Uncommitted | 否 | 可能 | 可能 | 可能 | 可能 |
| Read Committed | 否 | 否 | 可能 | 可能 | 可能 |
| Repeatable Read | 否 | 否 | 否 | 否 | 可能 |
| Serializable | 否 | 否 | 否 | 否 | 否 |

- **2.4.2 并发控制的四条路线**（本书给了三条，这里按现代口径整理成四条）：

  1. **锁**：读锁（共享）与写锁（排他）；死锁用**超时回滚**或**等待图检测**；
  2. **写时复制（COW）**：从叶到根拷贝路径上的节点 → 修改拷贝 → 原子切换根指针，读不加锁（LMDB 一系）；
  3. **多版本并发控制（MVCC）**：每行维护「创建/删除版本号」，读按版本号判可见性，**读写互不阻塞**；
  4. （本书未列，2026 年主流）**乐观并发控制 + 验证阶段**，如 Calvin 的确定性调度与各类 OCC 实现。

```sql
-- 教学示意，不参与构建：MVCC 可见性规则（本书 2.4.2 描述的 InnoDB 版）
-- 每行隐含 create_version / delete_version 两列，值为事务号（不是墙上时钟）
SELECT * FROM t
WHERE create_version <= :my_txn_id
  AND (delete_version IS NULL OR delete_version > :my_txn_id);
-- INSERT: create_version = :my_txn_id; DELETE: delete_version = :my_txn_id
-- UPDATE: 旧行 delete_version = :my_txn_id + 新行 create_version = :my_txn_id
```

> 「版本号不是时间而是事务号」这一点极其重要：它是第 3 章讲一致性、
> 第 10 章讲 OB 的多版本并发控制时反复出现的思想——**用逻辑序代替物理时钟**。

### 2.5 故障恢复：两条公理与三个优化

- **操作日志的三种形态**：
  - UNDO 日志 `<T, X, old_value>`：记录改之前，用于回滚；
  - REDO 日志 `<T, X, new_value>`：记录改之后，用于重做；
  - UNDO/REDO 日志 `<T, X, old, new>`：两者都记。
- **重做（redo）日志的两条公理**（本书 2.5.2 的核心）：
  1. **WAL 规则**：修改内存中的元素 X 之前，与该修改相关的日志必须已经刷盘；
  2. 提交返回成功之前，日志必须已经落盘（否则宕机后事务丢失）。
- **三个优化**（2.5.3）：
  1. **成组提交（group commit）**：日志先入缓冲区，满 512KB 或距上次刷盘超过 10ms 时一次性刷出，
     把「每个事务一次 fsync」摊成「一批一次 fsync」；
  2. **检查点（checkpoint）**：记 `START CKPT` → 内存数据转储成 checkpoint 文件 → 记 `END CKPT`，
     恢复时只需回放 `START CKPT` 之后的日志；
  3. 恢复流程：加载 checkpoint → 定位回放点 → 顺序回放 redo 日志。

> OceanBase 的 UpdateServer 就是这套单机 redo 思想的**分布式放大版**：
> 一个内存表 + 一份强同步的 commit log（见 [09-分布式存储引擎.md](09-分布式存储引擎.md)）。

### 2.6 数据压缩

- **压缩算法谱系**（本书 2.6.1）：
  - **Huffman 编码**：前缀编码，按出现频率变长编码；
  - **LZ 系列（LZ77/LZSS）**：用「(距离, 长度)」替换重复串，字典在滑动窗口里；
  - **Snappy（Google Zippy）**：为速度不为压缩比——只保存长度 4 的子串、重复匹配长度 ≥ 4 才输出匹配、
    按 32KB 分块、匹配长度 < 12 且位置 < 2048 时用 2 字节编码；
  - **BMDiff**：按长度 b（默认 32）切段并存每段的哈希值，哈希表大小为 N/b。
- **列式存储（2.6.2）**：同一列的值连续存放 → 熵低 → 压缩比高；再加**位图索引**（低基数列每取值一个位图）与**向量化执行**（一次算一列块）。

```text
# 教学示意，不参与构建：行存 vs 列存，为什么列存压得动
行存: (1,张三,男,28) (2,李四,女,31) ...  -> 一页混着多种类型，压缩器无从下手
列存: id: 1|2|3|...   age: 28|31|25|...   gender: 男|女|男|...
      -> 每列同类型、值域集中 -> 字典/游程/位图编码都好用，且 OLAP 只扫需要的列
```

> 本书把列存放进「数据压缩」一节，说明当时作者的视角是「列存是为了压得动」。
> 2026 年的视角要补一句：**列存更重要的收益是向量化执行与 I/O 裁剪**，
> 压缩只是顺带的（见「版本演进」）。

## 版本演进

- **本书无第二版**；本节写 2013 年口径 → 2026 年视角的变化。
- **2.1 硬件基础（变化最大的一节）**：
  - **SSD/NVMe 已成默认**：2026 年 NVMe SSD 的随机读延迟在**几十微秒**量级、
    队列深度拉满时吞吐可达数 GB/s；原书「磁盘寻道 10ms」只适用于 HDD 冷归档。
    **「顺序写远快于随机写」这一 LSM 的原始动机在 NVMe 上被显著削弱**——这是本章最需要打的补丁。
  - **持久化内存（Optane）已退市**：Intel 于 2022 年退出 Optane 业务；今天**不能**把它当作
    设计选项，涉及 PMem 的方案必须标注「已退市/不可用」（相关研究只作学术成果看待）。
  - **网络**：25/100/200 Gbps + RDMA 让「跨机架 ≈ 跨数量级」的差距收窄，远程内存访问
    （FaRM 一系）使「把内存池化」成为可行设计。
  - **ZNS（Zoned Namespace）SSD** 把顺序写约束暴露给主机，反而**利好 LSM**，是 2020 年代的新变量。
- **2.2 存储引擎**：LSM 与 B 树的分野从「谁更快」变成「三种放大的配比 + 延迟方差」；RocksDB 系（LSM）在 2026 年成为嵌入式引擎的事实标准。
- **2.6 压缩**：ZSTD 在压缩比/速度权衡上普遍优于 Snappy 时代的选择，成为新一代默认；原书列举的算法仍是正确原理，但**工程默认已变**。

## 近年研究与工业界开源实践（2015–2026）

- **LSM vs B+ 树的现代对决**（本章 2.2 的 2026 答案）：`facebook/rocksdb`（32136★，2026-09 实测）
  是 LSM 事实标准，被 TiKV、CockroachDB、Flink state backend 等广泛嵌入；
  `google/leveldb`（39448★）是祖先，生产多用 RocksDB 及其衍生。**MyRocks**（Facebook 用 RocksDB
  替换 InnoDB，PVLDB 2020）是「LSM 打赢 B+ 树」的工业实证；另一侧的实证是**现代 B+ 树在 NVMe 上
  依然稳**（延迟方差小、不需调 compaction），这是 TiDB/OceanBase 事务路径仍用类 B+ 树行存的原因之一。
- **compaction 研究的十年演进**：WiscKey（键值分离，2016）→ Monkey（布隆过滤器最优分配，
  2017）→ Dostoevsky（自适应合并，2018）→ VLDB Journal 2020 综述，主线是**把三种放大从
  「二选一」变成连续可调**。本书 2013 年只有 leveled vs size-tiered 的定性描述，这条线是必补内容。
- **列存与向量化成为 OLAP 标配**：本书 2.6.2 的列存在 2026 年已是 ClickHouse/DuckDB/BigQuery
  的默认形态；OceanBase **2024 年推出列式存储**，把列存引入 HTAP 主路径
  （详见 [10-数据库功能.md](10-数据库功能.md) 与 [08-OceanBase架构初探.md](08-OceanBase架构初探.md)）。
- **硬件与压缩的定量修正**：NVMe 让随机读降到微秒级，LSM「用顺序写换随机写」的收益下降，
  但 **compaction 的写放大在 SSD 上更贵**（影响盘寿命与写带宽），故现代引擎以**降写放大**为主目标；
  压缩默认选型也迁移到 **ZSTD**（本书列举的 Snappy 细节应理解为原理示例）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「LSM 写快读慢，B 树相反，绝对成立」 | 是**三种放大的配比**不是二分；LSM 的范围扫描很快，B 树的写放大也不小；真正的差异在**延迟方差与调优成本** |
| 2 | 「compaction 是后台活，不影响前台」 | 大 compaction 与前台共享 I/O 与缓存，**延迟毛刺是 LSM 生产事故高发点**；OB 里就有「定期合并限速」（9.4） |
| 3 | 「哈希引擎因为快所以更好」 | 它只能点查、且 key 必须全在内存；更常作为**缓存**而不是主存 |
| 4 | 「MVCC 的版本号是时间戳」 | 是**事务号/逻辑序**；分布式下演化为 TSO、HLC、TrueTime（→ 第 3、7 章） |
| 5 | 「WAL 只用于崩溃恢复」 | WAL 同时是**复制日志**（→ 3.4）、**CDC 事件源**（→ 第 13 章）与存算分离架构的写入通道 |
| 6 | 「列存只是为了压缩」 | 更重要的收益是**I/O 裁剪 + 向量化执行**；原书把它放在「压缩」一节会让人低估它 |
| 7 | 「四种隔离级别是标准答案」 | 快照隔离（SI）不在经典四级表里，却是 2026 年主流默认；写偏斜/幻读边界要读现代文献 |
| 8 | 🔧 原书 2.1 的延迟表已全面过时 | SSD 0.1ms → NVMe 几十 µs；「磁盘寻道 10ms」只适用于 HDD；**跨机架带宽今天可达 25–200Gbps**，原书「机架层 100MB/s」是 2013 年口径 |
| 9 | 🔧 原书的「顺序写优于随机写」前提被 NVMe 削弱 | NVMe 上随机/顺序差距缩小；现代引擎改以**降写放大**为主目标（WiscKey/Monkey/Dostoevsky 一系） |
| 10 | 🔧 原书完全没有 Optane/持久化内存，2026 年也不能补 | Intel 2022 年退出 Optane 业务，**已退市**；涉及 PMem 的方案必须标注不可用；压缩默认也已迁到 **ZSTD** |
| 11 | 🔧 原书没有「键值分离」这一现代优化 | WiscKey（FAST 2016）之后，大 value 场景普遍把 key 与 value 分开存，本书的 LSM 描述缺这一笔 |
