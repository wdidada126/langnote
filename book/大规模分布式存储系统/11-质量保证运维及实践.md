# 第 11 章　质量保证、运维及实践

> 原书第 11 章是实践篇的收尾，也是全书**最不像技术书、却最像工程师手记**的一章：
> 质量保证流程（11.1）、运维（11.2）、三个真实业务（11.3）、最佳实践（11.4）。
> 这一章的内容**随时间衰减最慢**——2013 年写下的「系统发展路径」「经验法则」今天依然成立，
> 但**运维这一节的具体手段已经完全换代**（可观测性、混沌工程、DBaaS）。
> 本章还留下一句值得抄下来的话（豆瓣原文摘录，引自本章）：
> 「通用分布式存储系统不是设计出来的，而是随着应用需求不断发展起来的。」

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 11.1 质量保证 | RD 开发（单元测试 + 代码审核 + 持续集成）、QA 测试（功能/性能/压力/兼容）、**试运行**（小规模生产验证） | 数据库这种「错了就丢钱」的系统，质量靠**流程分层**而不是靠个人能力 |
| 11.2 使用与运维 | 使用（部署、接入、监控）、运维（扩容、升级、故障处理、备份恢复） | 运维能力是分布式系统**能否真正上线**的门槛 |
| 11.3 应用 | 收藏夹（大表左连接 + OLTP）、天猫评价（海量写入）、直通车报表（OLAP） | 三个案例分别压到系统的三个不同侧面 |
| 11.4 最佳实践 | 系统发展路径、人员成长、系统设计、系统实现、使用与运维、工程现象、**经验法则** | 「**简单就是美**」——方案很复杂，一般是实践者没想清楚 |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 11.1 质量保证：三层漏斗

```text
# 教学示意，不参与构建：质量保证的三道闸门
RD 开发:  单元测试 + 代码审核（review）+ 持续集成
          -> 拦住"实现错误"与"回归"
QA 测试:  功能测试 / 性能测试 / 压力测试 / 兼容性测试 / 异常注入测试
          -> 拦住"行为错误"与"容量不足"
试运行:   小规模生产环境（灰度）真实流量验证
          -> 拦住"实验室里看不出来的问题"
```

- **试运行（灰度）是数据库上线的特有环节**：再完备的测试也覆盖不了真实负载的形状，
  所以必须先在**可控的小流量**上跑一段时间。
- **异常注入测试**尤其关键：杀进程、断网、拔盘、时钟回拨——
  本书时代叫「异常测试」，2026 年叫**混沌工程 / 故障注入**。

### 11.2 使用与运维：把系统交出去之后

| 主题 | 要做的事 |
| --- | --- |
| **部署** | 一键部署、配置模板化、环境检查（磁盘/网络/内核参数） |
| **监控** | 指标（QPS/TPS、延迟分布、缓存命中率、磁盘/网络、副本健康）+ 告警阈值 |
| **扩容** | 在线加节点、数据自动再平衡、限速避免影响线上 |
| **升级** | 滚动升级（逐个节点、保证副本多数派在线）、可回滚 |
| **故障处理** | 明确的止损顺序（先恢复服务，再查根因）、故障复盘 |
| **备份恢复** | 全量备份 + 增量/日志备份；**定期验证恢复流程**（备份不验证等于没备份） |

```text
# 教学示意，不参与构建：滚动升级为什么必须"保证多数派在线"
副本数 N=3（多数派 = 2）时:
    一次只能升级 1 个节点，升级完成后再升下一个
    -> 任意时刻至少 2 个副本可用 -> 写入不中断
若同时升级 2 个 -> 只剩 1 个副本 -> 达不到多数派 -> 写阻塞
# 这条规则对所有基于共识/多数派的系统都成立（Raft/Paxos 同理）
```

### 11.3 三个真实业务：分别压到系统的不同侧面

| 业务 | 负载形状 | 压到系统的哪一面 |
| --- | --- | --- |
| **收藏夹** | 海量数据 + 点查/范围查 + 大表左连接 | 考验 **SQL 层与连接优化**（本书 10.5 的「大表左连接」就来自这里） |
| **天猫评价** | 海量写入 + 读多写少的评论 | 考验 **写入吞吐与存储成本**（直通 UpdateServer/写路径） |
| **直通车报表** | 大范围扫描 + 聚合 | 考验 **OLAP 能力**（并发查询 + 列式存储，本书 10.4） |

> 这一节的方法论价值：**不要问「这个系统快不快」，要问「它在哪种负载形状下快」**。
> 三个业务就是三种负载形状，系统必须分别给出答案。

### 11.4 最佳实践：本书最经得起时间考验的一节

- **系统发展路径**（豆瓣原文摘录，引自本章）：

> 「通用分布式存储系统不是设计出来的，而是随着应用需求不断发展起来的。
> 它来源于具体业务，又具有一定通用性，能够解决一大类问题。」
> 「通用分布式存储平台的优势在于规模效应……主要有两种成长模式：
> 1. 公司高层制定战略大力发展通用平台……往往会因为离业务太远而在中期暴露大量问题；
> 2. 来源于具体业务并将业务需求通用化……会面临更大的技术挑战，但团队成员能得到更多锻炼。」

- **经验法则**（本书 11.4 末尾的清单，转述其精神）：

| 法则 | 含义 |
| --- | --- |
| **简单就是美** | 系统开发中，如果某个方案很复杂，一般是实践者**没有想清楚** |
| 从简单开始 | 先实现核心功能，再逐步完善 |
| 性能优先 | 设计时就要考虑性能瓶颈，而不是事后调优 |
| 容错设计 | 假设**任何组件都可能故障** |
| 监控完善 | 没有监控的系统等于不可运维 |
| 自动化运维 | 减少人工干预（人工操作是事故的主要来源） |

- **工程现象**与**人员成长**两节讲的是团队侧的经验（本书原意本目录不逐条转述，
  只记录其存在与主题）。
- **这几条法则与前面章节是一一对应的**：「假设任何组件都可能故障」对应第 3 章的异常模型；
  「性能优先」对应第 2 章的延迟数量级；「自动化运维」对应 11.2 的滚动升级。

## 版本演进

- **本书无第二版**；本节写 2013 年 → 2026 年的变化。
- **「质量保证」的手段升级**：
  - **混沌工程**（Netflix Chaos Monkey 一系，2010 年代普及）把「异常注入」产品化、常态化；
  - **Jepsen 式一致性测试**（2013 年起）用线性一致性检查器验证「声称的一致性」是否成立；
  - **确定性模拟测试**（FoundationDB 一系，SIGMOD 2021 获奖论文）把分布式系统的
    随机故障变成**可复现的确定性测试**——这是本书时代不可想象的手段。
- **「运维」的形态升级**：
  - **可观测性**（metrics + logs + traces 三件套，OpenTelemetry 成为事实标准）
    取代了「看监控图」；
  - **DBaaS / 云数据库**把扩容、备份、升级做成托管能力，
    本书 11.2 描述的手动流程今天大量由平台承担；
  - **SRE 方法论**（SLO / 错误预算）给「可用性」定了可度量的目标，
    本书只有定性描述。
- **备份恢复的重要性上升**：
  勒索软件与误操作使得 **PITR（时间点恢复）** 与**备份不可变（immutable backup）**
  成为标配；本书的「全量 + 增量」思路不变，但要求更严格。
- **不变的部分**：11.4 的经验法则几乎没有一条过时。
  「简单就是美」「假设任何组件都可能故障」在 2026 年依然是第一原则。

## 近年研究与工业界开源实践（2015–2026）

- **实测 star（2026-09，`gh api` 实测）**：

| 项目 | 与本章的关系 | star |
| --- | --- | --- |
| `oceanbase/oceanbase` | 本章描述的系统；开源后运维生态由社区共同建设 | 10291 |
| `etcd-io/etcd` | 运维侧的典型：滚动升级、多数派、备份（snapshot） | 52310 |
| `apache/hbase` | 大规模集群运维的经典对象 | 5560 |

- **开源改变了质量保证的形态**：OceanBase **2021-06-01 开源**
  （`oceanbase/oceanbase`，10291★）之后，
  本书 11.1 描述的「内部 RD + QA」流程扩展为**社区 issue + PR review + CI**。
  **这是本章最直接的 2026 年变化**：质量保障从封闭流程变成公开流程。
- **可观测性成为默认要求**：本书 11.2 的「监控」今天等价于
  **指标 + 日志 + 链路追踪**（OpenTelemetry 生态），
  且要求**按租户/按 SQL 指纹**下钻，而不是只看机器级指标。
- **DBaaS 把运维托管化**：本书 11.2 的扩容/升级/备份今天多数由云平台承担
  （OB 的 OCP、阿里云数据库服务、AWS RDS/Aurora 等），
  但**容量规划与故障止损的判断仍然是人要做的事**。
- **PITR 与不可变备份成为标配**：勒索软件与误删推动
  「可恢复到任意时间点 + 备份不可被篡改」成为合规要求；
  本书的「全量 + 增量 + 日志备份」三件套仍在，但验证要求更严。
- **尾部延迟（tail latency）是运维的真实战场**：本书的性能指标是吞吐与平均延迟；
  2026 年运维看的是 **p99/p999**（《The Tail at Scale》一脉），
  因为用户体验由最慢的那部分请求决定。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「测试通过就可以上线」 | 必须**试运行/灰度**：真实负载形状无法在实验室复现 |
| 2 | 「备份了就安全」 | 必须**定期验证恢复流程**；未验证的备份等于没有备份 |
| 3 | 「滚动升级可以一次升多台以节省时间」 | 必须保证**多数派在线**；N=3 时一次只能升一台 |
| 4 | 「监控有图就够了」 | 2026 年需要 metrics + logs + traces 三件套，并能按租户/SQL 下钻 |
| 5 | 「性能优化是上线后的事」 | 本书明确写「性能优先」：设计时就该考虑瓶颈位置 |
| 6 | 「自动化运维只是省人力」 | 它的核心收益是**减少人为操作**——人工操作是事故的主要来源 |
| 7 | 🔧 本书的「异常测试」手段已升级 | 2026 年是**混沌工程 + Jepsen 一致性测试 + 确定性模拟测试**；本书只有定性描述 |
| 8 | 🔧 本书的运维是「自建集群手动运维」 | 2026 年主流是 **DBaaS 托管 + 可观测性平台 + SLO 驱动**；本书流程被平台大量吸收 |
| 9 | 🔧 本书的性能指标是吞吐/平均延迟 | 2026 年运维看 **p99/p999 尾部延迟**（《The Tail at Scale》）；平均延迟会掩盖长尾 |
| 10 | 🔧 本书的备份思路缺 PITR 与不可变备份 | 勒索与误删推动**时间点恢复 + 不可变备份**成为合规标配 |
