# 第 6 章　分布式表格系统

> 原书第 6 章是**承上启下**的一章：向上接第 4 章的分布式文件系统（Bigtable 建在 GFS 上），
> 向下接第 7 章的分布式数据库（Megastore 是 Bigtable → Spanner 的中间态）。
> 三个案例恰好落在「表格语义强度」的三个刻度上：
> **Bigtable（无跨行事务）→ Megastore（实体组内事务）→ Spanner（全局事务）**。
> 2026 年读这一章的要点是：Megastore 已成历史名词，但它的**实体组 + Paxos 复制**
> 思想被 Spanner 完整继承，是理解现代分布式数据库的必经一站。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 6.1 Bigtable：一张有序的、稀疏的、多维的映射表

- **数据模型**：`(row_key, column_key, timestamp) → value`。
  - **行键**按字典序全局有序（这是表格系统与键值系统最本质的差别）；
  - **列族（column family）**是访问控制与存储的基本单元：`family:qualifier`；
  - **时间戳**保留多版本（可配置保留最近 N 个版本或最近 N 秒）。
- **架构**：
  - **客户端程序库**：直接与 Tablet Server 通信（不经 Master 传数据）；
  - **主控服务器（Master）**：分配 tablet、负载均衡、检测 tablet server 的加入/退出、GC；
  - **子表服务器（Tablet Server）**：管理一组 tablet（10~1000 个），处理读写与分裂；
  - **Chubby 锁服务**：保存 schema、访问控制列表、tablet 位置根目录，**tablet server 在 Chubby
    上获取独占锁来表示自己还活着**。
- **数据分布与定位**：按 row key 范围切 tablet；定位用**类 B+ 树的三层 METADATA 表**
  （Root tablet → METADATA tablets → User tablets），客户端缓存 tablet 位置。

```text
# 教学示意，不参与构建：Bigtable 的 tablet 定位（三级元数据）
lookup(row_key):
    # 1. Chubby 里的文件拿到 root tablet 位置（几乎不变）
    # 2. root tablet 找 METADATA tablet 的位置
    # 3. METADATA tablet 找目标 tablet 的位置
    # 4. 客户端缓存，下次直接访问 Tablet Server
    # 失效时递归重来（最坏 6 次网络往返）
```

- **复制与一致性**：**数据本身不在 Bigtable 里复制**——它建在 GFS 上，由 GFS 保证 3 副本；
  Bigtable 提供的是**一层分布式索引**。本书这个判断（「Bigtable 本质是构建在 GFS 上的一层
  分布式索引，通过它解决了 GFS 遗留的一致性问题」）是全章最精炼的一句。
- **单机存储**：**SSTable + MemTable + Commit Log**，即教科书式的 LSM：
  写先落 commit log、进 memtable；memtable 满则冻结并转储为 SSTable；
  后台合并 SSTable（minor/major/合并三种，major compaction 会真正删除被墓碑标记的数据）。
- **分裂与合并**：tablet 超过阈值（默认 100~200MB）自动分裂；合并较少触发。
- **垃圾回收**：major compaction 时才真正回收删除标记下的数据；
  另外 SSTable 的 bloom filter 是读路径的关键优化。

> **Bigtable 没有跨行事务**（只提供单行事务）。这正是 Megastore 要解决的问题。

### 6.2 Megastore：用「实体组」把事务圈起来

- **动机**：Bigtable 好用但没有跨行事务，很多应用（社交、邮件、协作）需要
  「少量跨行但强一致」的更新；Spanner 还没成熟。
- **核心抽象：实体组（Entity Group）**——
  把需要一起更新的行**划分到同一个实体组内**；
  **实体组内部用 Paxos 做强一致复制（多副本、跨机房）**，
  **跨实体组用两阶段提交（2PC）或异步队列**。

```text
# 教学示意，不参与构建：Megastore 的两种一致性边界
同一个实体组:
    - 组内所有写入经 Paxos 定序 -> 组内强一致 + 可串行化
    - 读: current（等所有提交回放完）/ snapshot（读某个已同步快照）/ inconsistent（最快）
跨实体组:
    - 2PC（慢，慎用）或 异步消息队列（最终一致，推荐）
```

- **并发控制**：**多版本并发控制（MVCC）** + 乐观读；
  每个实体组内写事务由 Paxos 选出「下一个日志位置」，写事务之间靠锁与版本检查串行化。
- **复制**：每个实体组有独立的 **Paxos 复制组（replica group）**，
  副本可跨机房；这是「一个数据中心一组副本」传统的重大改进。
- **协调者（Coordinator）**：每个副本所在的数据中心有一个协调者进程，
  记录「本副本是否已同步到最新」，使得 **current 读可以走本地副本**（否则要跨机房 Paxos 读）。
- **索引**：本地索引（组内）、全局索引（跨组，最终一致）。
- **历史地位**：Megastore 是 **Bigtable → Spanner 的中间态**：
  它证明了「在 NoSQL 之上做适度强一致」可行，Spanner 则用 TrueTime + 全局事务把它做大。

### 6.3 Windows Azure Storage：强一致 + 分层

- **整体架构**：**文件流层（Stream Layer）+ 分区层（Partition Layer）** 两层，
  再加前端（Front-End）层。
  - **Stream Layer**：一个 **append-only 的分布式文件系统**，只支持「追加」和「封存（seal）」；
    文件由 **extent**（若干 **block** 追加而成）组成，extent 封存后不可变，
    由分区层负责把多个 extent 逻辑上拼成一个大文件。
  - **Partition Layer**：提供 **表语义**——按主键范围分区（RangePartition），
    内部维护若干系统表（如 Blob Table / Entity Table / Schema Table），
    日志追加（commit log）在流层、数据（row data / blob data）也在流层。
- **强一致的来源**：因为**只追加 + 封存后不可变**，副本之间只需就「追加顺序」达成一致
  （流层用类似 PacificA 的**封存时定序**机制），不需要复杂的并发控制；
  分区层的每个 RangePartition 由**一个分区服务器**服务（租约保证唯一），
  因此**写天然是串行的**——强一致由此而来。

```text
# 教学示意，不参与构建：WAS 的"分层 + 只追加"如何换来强一致
流层:   extent 追加期间由主副本定序 -> seal 时确定最终长度与内容 -> 之后只读
        副本之间没有"并发改写"，只有"定序后的唯一内容"
分区层: 每个 RangePartition 由唯一分区服务器（持租约）服务
        -> 写事务串行 -> 不需要分布式锁
结果: 强一致（linearizable 读写），且能在廉价硬件 + 多副本下实现
```

- **与 GFS 系的对照**：GFS 显式**放弃**部分一致性（undefined-but-consistent）以换取简单与性能，
  **WAS 选择提供强一致**，代价是分层设计与只追加约束。**这是本书最漂亮的一组对照案例**。

## 版本演进

- **本书无第二版**；本节写 2013 年口径 → 2026 年视角的变化。
- **Megastore 已退居历史**：Google 自己在 Spanner 成熟后，
  Megastore 的角色被 Spanner 取代（Google 内部将其迁移到 Spanner 系的公开叙述存在，
  但**具体迁移完成时间与范围本目录未能核实原文**）。
  读 Megastore 的正确姿势是**理解它的思想继承者**（Spanner 的 Paxos 组 + 跨组 2PC），
  而不是当成要选的产品。
- **Bigtable 变成托管服务**：Google Cloud Bigtable 是托管版，
  **开源对应物是 HBase**（`apache/hbase`，5560★）。HBase 的架构（HMaster / RegionServer /
  WAL / MemStore / HFile）与 Bigtable 论文几乎逐项对应，是本章最好的动手对象。
- **「表格系统」这一格的边界在移动**：
  - 向上：HBase 上叠 SQL 层（Apache Phoenix），表格系统开始提供部分数据库语义；
  - 向下：NewSQL（TiDB/OB/CockroachDB）原生提供 SQL + 事务，
    把「表格系统」挤成了「数据库内部的存储层」。
- **WAS 的架构思想被存算分离全面验证**：「只追加的分布式流层 + 上层表语义分区层」，
  正是 2026 年**对象存储 + 湖仓表格式（Iceberg/Delta/Hudi）**的原型。
  本书把 WAS 放在「范型篇」末尾，今天看它是**最有前瞻性的一节**。
- **Chubby 的开源替代**：Chubby 从未开源，工业界的等价物是 **ZooKeeper/etcd**；
  etcd（52310★）在 Kubernetes 生态里事实上承担了 Chubby 的角色。

## 近年研究与工业界开源实践（2015–2026）

- **实测 star（2026-09，`gh api` 实测）**：

| 项目 | 定位 | star |
| --- | --- | --- |
| `apache/hbase` | Bigtable 的开源实现（HDFS 之上） | 5560 |
| `apache/hadoop` | HBase 的底座 HDFS | 15669 |
| `etcd-io/etcd` | Chubby 的现代等价物（Raft 协调服务） | 52310 |
| `tikv/tikv` | Multi-Raft 的有序 KV（表格语义 + 强一致） | 16878 |
| `facebook/rocksdb` | 现代 SSTable/memtable 引擎 | 32136 |
| `apache/cassandra` | 宽列阵营的另一支（Dynamo 血统） | 10102 |

- **Bigtable 思想的两种现代落地**：
  1. **HBase 路线**（Bigtable 直系）：HMaster + RegionServer + HDFS + LSM，
     仍在大量存量系统服役；
  2. **Raft 路线**（TiKV/CockroachDB）：把「tablet」换成「range/region」，
     每个 range 一个 Raft group，**在 Bigtable 的分区模型上叠加了强一致复制**——
     这正是 Megastore「实体组 + Paxos」思想的大众化版本。
- **「表格系统」正在被 NewSQL 吞并**：2026 年新建系统很少直接选 HBase/Cassandra
  作为业务主存储，更多是把它们用作**特定负载**（宽表、时序、大吞吐写入），
  主存储交给原生分布式 SQL 数据库（OB / TiDB / PolarDB / CockroachDB）。
- **WAS 思想的两条后继**：
  1. 存算分离的云盘/对象存储（append-only 段 + 上层索引）；
  2. **湖仓表格式**：Iceberg（9276★）/ Delta（9020★）/ Hudi（6275★）在对象存储上
     提供「表 + ACID + schema 演进」，与 WAS 分区层承担的职责高度同构。
- **多模与 HTAP**：OceanBase 等系统在同一份数据上同时提供 SQL、KV（OBKV）、
  甚至 HBase API 兼容，使得「表格系统 vs 数据库」的分类边界进一步模糊
  （详见 [01-概述.md](01-概述.md) 的 2026 年补丁）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Bigtable 自己复制数据」 | 它把持久化与复制交给 GFS；Bigtable 提供的是**索引与表格语义** |
| 2 | 「Bigtable 支持事务」 | 只有**单行事务**；跨行需要上层（Megastore/Percolator）实现 |
| 3 | 「列族与列是同一层概念」 | 列族是**存储与访问控制的基本单元**，列限定符只在族内有效；列族数量要少（存储按族分文件） |
| 4 | 「Megastore 是 Spanner 的前身所以已无意义」 | 它的**实体组 + Paxos 组 + 跨组 2PC** 是今天几乎所有分布式数据库的分片-复制结构原型 |
| 5 | 「WAS 与 GFS 是同类系统的两种实现」 | 两者的一致性选择相反：GFS 接受 undefined-but-consistent，WAS 提供强一致；约束也不同（WAS 只追加 + 封存） |
| 6 | 「Chubby 就是 ZooKeeper」 | Chubby 是 Google 内部服务、未开源；ZooKeeper/etcd 是工业界的等价替代，协议不同（ZAB/Raft vs Paxos 系） |
| 7 | 🔧 本书把 Megastore 当作「当前可用范型」介绍 | 2026 年它已成**历史名词**：Google 自身以 Spanner 为主；读它是为了理解思想的继承 |
| 8 | 🔧 本书的 Bigtable/Chubby 组合在 2026 年有开源替代 | Chubby → ZooKeeper/etcd；Bigtable → HBase 或 Raft 系的 range 分区（TiKV/CockroachDB） |
| 9 | 🔧 本书没有湖仓表格式这一层 | WAS 的「流层 + 分区层」在对象存储时代等价于「对象存储 + Iceberg/Delta/Hudi」；这一层是本书之后才出现的 |
| 10 | 🔧 本书的「表格系统」分类边界今天已模糊 | HBase 上有 SQL 层、NewSQL 内部就有表格层；分类仍在用，但选型时的实际问题是「要不要原生 SQL + 事务」 |
