# 第 3 章　分布式系统

> 原书第 3 章是全书**方法论密度最高**的一章：异常模型、一致性、数据分布、复制、容错、
> 可扩展性、分布式协议、跨机房部署——今天所有分布式数据库的宣传材料里出现的词，
> 八成在这一章都能找到原始定义。
> 但它也是**最需要 2026 年补丁**的一章：3.7 只讲 Paxos 与 2PC，而 **Raft 论文发表于
> 2014 年（本书成书后一年）**，今天工业界的默认共识算法是 Raft/Multi-Raft；
> 3.4 的 CAP 讨论也需要用「PACELC + 可串行化」的现代语言重新表述。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 3.1 基本概念：先承认「一切都会坏」

- **异常类型**：服务器宕机、网络异常（消息丢失 / 消息乱序 / 数据包错误）、
  磁盘故障（**磁盘损坏** 与 **磁盘数据错误**——后者更阴险，静默损坏）。
- **RPC 三态**：成功、失败、**超时**。超时的可怕之处在于——
  **客户端不知道服务端到底做过没有**。本章后面所有「幂等 / 重试 / 租约」的设计
  都是为这一态擦屁股。

- **一致性的两个视角**（本章最值得抄下来的一张表）：

| 视角 | 层级 | 说明 |
| --- | --- | --- |
| 客户端 | 强一致性 | A 写入后，后续 A/B/C 的读都返回最新值 |
| 客户端 | 弱一致性 | 不保证读到最新 |
| 客户端 | 最终一致性 | 若不再更新，A/B/C **最终**都会读到最新值 |
| 客户端 | 读写一致性 | A 自己写后自己能读到最新（不保证其他用户） |
| 客户端 | 会话一致性 | 会话期间保证读写一致（换会话不保证） |
| 客户端 | 单调读一致性 | 读到过某值后，不会读到更早的值 |
| 客户端 | 单调写一致性 | A 的写按顺序完成 |
| 存储系统 | 副本一致性 | 多个副本之间数据是否一致 |
| 存储系统 | 更新顺序一致性 | 各副本是否按**相同顺序**执行更新 |

- **衡量指标**：性能（吞吐 QPS/TPS + 响应延迟）、可用性、一致性、可扩展性。
  注意本书把「一致性」单独列为一项指标而不是默认前提，这在 2013 年是清醒的。

### 3.3 数据分布：哈希还是顺序，这是第一个岔路口

```text
# 教学示意，不参与构建：三种分布策略的取舍速查
hash_distribution:
    做法: hash(key) % N  或  一致性哈希（环 + 虚拟节点）
    优点: 均匀、无需全局元数据
    缺点: 破坏 key 的有序性 -> 不支持范围扫描
    扩容: 一致性哈希只迁移 1/N 的数据（虚拟节点把迁移量摊平）
    坑:   大用户/热点 key 始终落同一节点（数据倾斜）-> 需手动或自动拆分

range_distribution:
    做法: 大表按主键切成连续范围（子表/tablet），总控服务器分配给存储节点
    优点: 保留有序 -> 范围扫描友好，且元数据是小而规整的
    缺点: 需要总控节点 + 子表分裂/合并机制，系统复杂度显著上升
    坑:   子表分裂与合并是长期运维的主要风险源

load_balancing:
    机制: 工作节点心跳上报负载 -> 总控节点全局调度 -> 执行数据迁移
    迁移: 切走读写 -> 目标节点建副本并追平 -> 删除源副本
```

- **一致性哈希的三种路由表**（本书 3.3.1 的经典对照）：

| 位置信息维护策略 | 定位复杂度 | 备注 |
| --- | --- | --- |
| 每节点只记前后邻居 O(1) | O(N) 跳查找 | Chord 之前的朴素做法 |
| 维护大小 n 的路由表 O(logN) | O(logN) 跳 | Chord / Pastry / Kademlia 一脉 |
| 维护全部节点位置 O(N) | O(1) 跳 | 节点数不多时的务实选择（Tair 的 ConfigServer 思路） |

- **顺序分布的关键代价**：子表的**分裂与合并**。

> 读这段时请对照 [06-分布式表格系统.md](06-分布式表格系统.md) 的 Bigtable：
> Bigtable 的子表（tablet）分裂与合并、OceanBase 的 RootServer 子表管理（9.2），
> 都是这一节的直接实现。

### 3.4 复制：一致性与可用性的那台天平

- **两种复制协议**（按「谁负责写」分）：
  1. **基于主副本（primary-based）**：写先到主，主再推给备；强同步/异步的区别在于
     **是否需要等备返回**；
  2. **基于写多个存储节点（replicated-write）**：不区分主备，客户端直接写 W 份、
     读 R 份，**W + R > N** 时可读到最新（NWR / quorum）。
- **NWR**：`N` 副本数、`W` 写成功份数、`R` 读成功份数。`W+R > N` ⇒ 读写集合必有交集。
  典型配置：`N=3, W=2, R=2`。
- **CAP**（本书在 3.4.2 引入）：一致性、可用性、分区容忍性三者不可兼得；
  而分布式系统**必须**容忍分区（否则不叫分布式），所以实质是 **C 与 A 的取舍**。
- **三种工程档位**（本书借 Oracle DataGuard 的术语给出，这个对照非常实用）：

| 模式 | 本质 | 代价 |
| --- | --- | --- |
| 最大保护模式 | 强同步复制，写必须同步到至少一个备 | 备故障 → 写阻塞，**可用性受损** |
| 最大性能模式 | 异步复制，主本地成功即返回 | 主故障 → **可能丢数据** |
| 最大可用性模式 | 正常时强同步，网络故障时降级为异步 | 折中，但**降级时机**是最难写对的代码 |

### 3.5 容错：频率表、租约与双层结构

- **常见故障频率**（原书 3.5.1 的统计表，这本书最被反复引用的一张表）：

| 故障类型 | 频率 | 影响范围 |
| --- | --- | --- |
| 配电装置故障 | 0.5 次/年 | 5 分钟内大部分机器断电 |
| 数据中心过热 | 1 次/年 | 500–1000 台机器瞬间下线 |
| 机架故障 | 5 次/年 | 40–80 台机器瞬间下线 |
| 单机故障 | 1000 次/年 | 该机器无法提供服务 |
| 硬盘故障 | 几千次/年 | 该硬盘数据丢失 |

> 这张表的价值不在于数字精确，而在于**结论**：故障是常态，且**相关故障**
> （机架/机房级）远比想象中频繁，所以副本必须跨机架、最好跨机房。

- **故障检测**：心跳（定时上报）+ **租约（lease）**。

```text
# 教学示意，不参与构建：租约与"提前量"
A 给 B 发放租约，有效期 10s；B 只在持有有效租约时才提供服务。
B 在租约快到期前向 A 续约。
A 判断 B 过期的时间点 = 10s + 提前量（比如 1s），即 11s 后才能认为 B 已死。
为什么要有提前量：B 的时钟与 A 的时钟不同步，且续约消息在路上要花时间；
                 没有提前量就会在"网络抖一下"时误判 B 死亡 -> 双主。
```

- **故障恢复的两种结构**：
  - **单层结构**：每个数据分片自维护多副本（一个分片一组副本）；
  - **双层结构**：**存储层**多副本 + **服务层**单副本提供服务（故障时快速切主），
    这是 OceanBase 与多数现代系统的做法。
- **总控节点的高可用**：状态实时同步到备机 + 故障时由**分布式锁服务**选主
  （本书明确指出这套锁服务由 Paxos 实现）。

### 3.6 可扩展性：中心化不是原罪

- **总控节点的两大职责**：执行全局调度、维护目录树（元数据）。
- **瓶颈**：元数据全放内存 → 内存成为瓶颈。**解法是两级结构**：
  在总控节点与工作节点之间插一层**元数据节点**，每个元数据节点只维护一部分元数据。
- **数据库扩容**：按分片迁移 + 双写追平 + 切流；**异构系统**（不同机型混布）
  是扩容的现实约束（旧机器不能扔）。

### 3.7 分布式协议：2PC 与 Paxos，各管一半

- **两阶段提交（2PC）**：
  - 阶段 1（Prepare）：协调者问所有参与者「能不能提交」，参与者投票；
  - 阶段 2（Commit）：全部同意才提交，否则取消。
  - **致命问题**：协调者宕机 → 参与者**既不能提交也不能回滚**，只能阻塞等待。
  - 缓解：协调者把事务状态写日志并同步给备用协调者。
- **Paxos**：
  - 正常流程：Proposer 发 `accept` → 多数派接受 → 发 `acknowledge` 生效；
  - 完整流程（有并发 Proposer 时）：`prepare`（带序号 n）→ `accept` → `acknowledge`；
  - 保证：即使多个 proposer 并存，也只会有**一个值**被选定。
- **Paxos 与 2PC 的关系**（本章最有洞察力的一句）：

```text
2PC   -> 保证"多个数据分片上的操作"的原子性（all-or-nothing）
Paxos -> 保证"2PC 的协调者"本身不成为单点（选主 + 状态复制）

两者叠加 = 可用的分布式事务：
    每个分片内部用 Paxos（或 Raft）保证副本一致与高可用
    分片之间用 2PC 保证原子性
    协调者由 Paxos 选出的主担任
```

> 这段是全章的枢纽：本书第 7 章的 Spanner、第 8–10 章的 OceanBase，
> 本质上都是这个模式的两个实例。

### 3.8 跨机房部署

- 三种常见形态：**同城双机房**（延迟低，可做强同步）、**两地三中心**、**异地多活**。
- 核心约束：跨机房 RTT 从亚毫秒涨到几毫秒~几十毫秒，**强同步写会被直接拖慢**；
  所以跨机房方案实质上都在回答「哪些写必须强同步、哪些可以异步」。

## 版本演进

- **本书无第二版**；本节写 2013 年口径 → 2026 年视角的变化。
- **3.7 的最大补丁：Raft**。Raft 论文《In Search of an Understandable Consensus Algorithm》
  发表于 **USENIX ATC 2014**，比本书晚一年。今天工业界的事实标准是
  **Raft / Multi-Raft**（etcd、TiKV、OB 4.x、CockroachDB 全都用它），
  Multi-Paxos 的理论地位仍在，但**教学与工程实现几乎全用 Raft**。
  读本节时应把「Paxos」理解成「共识算法」的占位符，具体算法去
  [../深入理解分布式共识算法/07-Raft.md](../深入理解分布式共识算法/07-Raft.md) 补。
- **3.4 的 CAP 表述需要精化**：
  - CAP 只描述**网络分区发生时**的取舍，未描述正常情况；**PACELC**
    （Else: 延迟与一致性之间仍有取舍）是更完整的表述；
  - 现代系统更常承诺**可串行化（serializability）**而非「强一致性」这个含糊词：
    Spanner 的 external consistency、OB 的快照读/写，都是可串行化的不同实现；
  - **Jepsen 测试**（2013 年起，Kyle Kingsbury）把「声称的一致性」变成可证伪的测试项，
    这是本书完全没有的视角。
- **3.7.1 的 2PC 需要补**：
  - **Percolator 式乐观事务**（OSDI 2010，Google；TiDB 直接采用）用
    **客户端驱动 + 全局时间戳 + 悲观锁/乐观提交**绕开了中心协调者；
  - **Calvin**（SIGMOD 2012）用**确定性调度**消除提交期的协调；
  - 3PC 在理论上解决阻塞但在工程上很少使用（网络分区下仍不安全）。
- **3.1 的一致性谱系需要补**：线性一致性（linearizability）与可串行化（serializability）
  是**两个不同维度**（单对象 vs 多对象），本书的「强一致性」一词没区分开。
- **3.6 的总控节点**：2026 年的做法是**元数据也用 Raft 分片**（Multi-Raft 元数据组），
  本书的「两级元数据节点」思路仍在，但实现方式换成了共识组。
- **3.8 跨机房**：2026 年的新形态是**多地域多活 + 单元化**（OB 的「三地五中心」、
  CockroachDB 的多区域表），并引入了 HLC/TrueTime 这类**全局时钟**作为支撑。

## 近年研究与工业界开源实践（2015–2026）

- **Raft 的工程化普及（本章 3.7 的现实答案）**：
  - `etcd-io/etcd`（52310★，2026-09 实测）是 Raft 最广泛部署的实现（Kubernetes 的元数据存储）；
  - `tikv/tikv`（16878★）用 **Multi-Raft** 把数据切成上万个 Raft group，
    是「每个分片一个共识组」这一模式的代表（本书 3.7 的 Paxos 锁服务思想的大规模版）；
  - `pingcap/tidb`（40591★）与 `cockroachdb/cockroach`（32508★）分别代表
    **TSO + Percolator** 与 **HLC + 串行化**两条分布式事务路线；
  - `apache/zookeeper`（12811★）仍在大量存量系统中服役，是本书时代的活化石。
- **共识算法的中文系统材料**：仓库
  [../深入理解分布式共识算法/00-总览与阅读地图.md](../深入理解分布式共识算法/00-总览与阅读地图.md)
  有 Paxos/Multi-Paxos/ZAB/Raft/EPaxos 的逐算法推导，是本章 3.7 的必配对读材料。
- **一致性测试的工业化**：Jepsen（2013 年起）用故障注入 + 线性一致性检查器
  把「我们保证强一致」变成可证伪命题，多个知名系统在其测试下被发现问题。
  这是本书 3.1 完全没有的工程维度。
- **全局时钟的两条路线**（对应 3.1 的「更新顺序一致性」）：
  - **TSO（中心化时间戳）**：简单、严格单调，代价是单点与跨地域延迟（TiDB、OB 的 GTS）；
  - **HLC（混合逻辑时钟）**：无中心、容忍时钟漂移，代价是因果序而非全序（CockroachDB、YugabyteDB）；
  - **TrueTime（GPS + 原子钟）**：Spanner 的硬件解法，依赖专用硬件，**不是通用可复制方案**。
- **跨机房部署的 2026 年形态**：OceanBase 的「三地五中心」城市级容灾
  （RPO=0、RTO<8s 为官方宣传口径）与单元化（zone + 租户级弹性），
  是本书 3.8 思路的产品化结果。
- **Multi-Raft 已成为元数据层的默认**：本书 3.6 担心的「总控节点内存瓶颈」，
  今天靠**把元数据本身也切成 Raft group** 解决，而不是靠两级元数据节点。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「超时 = 失败」 | 超时是**三态之一**，服务端可能已执行；重试必须幂等，或靠序号去重 |
| 2 | 「强一致性就是线性一致性」 | 「强一致」在本书是含糊词；现代要区分**线性一致性**（单对象实时序）与**可串行化**（多对象事务序），两者正交 |
| 3 | 「CAP 是三选二」 | P 不是可选项（分布式必分区）；真正的取舍是 **C vs A**，且分区结束后还要取舍（PACELC） |
| 4 | 「一致性哈希解决了一切分布问题」 | 它解决**扩容迁移量**，不解决**热点**（大用户问题需单独拆分），也不支持范围扫描 |
| 5 | 「NWR 配置一次定终身」 | W/R 可**按请求**调整（写多读少 vs 读多写少）；且 W+R>N 只保证交集，冲突解决还要版本向量 |
| 6 | 「2PC 加上超时重试就安全了」 | 协调者宕机期间参与者必须阻塞；2PC 是**阻塞协议**，需 Paxos/Raft 保障协调者高可用才能真正可用 |
| 7 | 「Paxos 就是选主算法」 | 选主是 Multi-Paxos/Raft 的用法；Paxos 本质是**对单个值达成共识**（状态机复制是上层构造） |
| 8 | 🔧 3.7 完全没有 Raft | Raft（ATC 2014）晚于本书一年，今天已是工业界默认；读本章必须配 Raft 材料补上 |
| 9 | 🔧 3.7 的 2PC 没有 Percolator / Calvin 两条现代路线 | 2026 年的分布式事务主流是 **TSO + 乐观提交（Percolator 系）**与**确定性调度（Calvin 系）**，本书只有 2PC 一途 |
| 10 | 🔧 3.1 的一致性谱系缺 HLC / TrueTime | 全局时钟是分布式事务的前提；本书成书时 TrueTime（2012）刚出现、HLC（2014）尚未发表 |
| 11 | 🔧 3.6 的总控节点方案已被 Multi-Raft 元数据取代 | 2026 年元数据层本身用共识组分片，不再依赖「两级元数据节点」的人工分层 |
| 12 | 🔧 本书无「一致性测试/故障注入」视角 | Jepsen 一系把一致性变成可证伪的工程实践，是选型时必须问的一项 |
