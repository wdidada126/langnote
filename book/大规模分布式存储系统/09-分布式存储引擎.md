# 第 9 章　分布式存储引擎

> 原书第 9 章把第 8 章的五个角色**逐个拆到实现层**：公共模块（9.1）是地基，
> RootServer / UpdateServer / ChunkServer（9.2–9.4）是三个核心服务的内部机制，
> 而 **9.5「消除更新瓶颈」是本章最耐人寻味的一节**——
> 它在 2013 年就已经预告了「单点 UpdateServer 撑不住」，并给出了**数据分区**这条出路。
> 换句话说：**OB 1.0（2016）的架构升级，在这一章里已经写好了伏笔**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 9.1 公共模块 | 内存管理、基础数据结构、锁、任务队列、网络框架、压缩与解压缩 | 分布式系统的**性能与稳定性**多半死在这些「不起眼」的公共模块上 |
| 9.2 RootServer 实现机制 | 数据结构、子表复制与负载均衡、子表分裂与合并、UpdateServer 选主、RootServer 主备 | 中心节点只存**元数据**，职责是「让每个子表都有足够副本且在合适的机器上」 |
| 9.3 UpdateServer 实现机制 | 存储引擎（内存 B+ 树 + commit log）、任务模型（异步批量）、主备同步 | 单点写的性能靠**内存 + 批量 + 异步**三件套撑住 |
| 9.4 ChunkServer 实现机制 | 子表管理、SSTable、缓存实现、IO 实现、定期合并与数据分发、**定期合并限速** | 读路径优化（缓存/批量 IO/预读）与后台合并的**限速**是运维稳定的关键 |
| 9.5 消除更新瓶颈 | 读写优化回顾、**数据旁路导入**、**数据分区** | 单点的三条出路：写更快、绕过写、拆开写 |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 9.1 公共模块：性能的真正战场

| 模块 | 要解决的问题 | 典型做法 |
| --- | --- | --- |
| **内存管理** | 频繁 `malloc/free` 的开销与碎片；长跑服务的内存泄漏 | **内存池 / 对象池 / slab 分配器**；定长块复用；按生命周期分代 |
| **基础数据结构** | 内存表用什么？索引用什么？ | 内存 B+ 树（有序、范围友好）、哈希表（点查）、跳表（并发友好）、定长数组 |
| **锁** | 并发访问共享结构；锁竞争是吞吐杀手 | **读写锁**（读多写少）、**无锁/RCU** 数据结构、细化锁粒度（按桶/按行）、避免锁内做 I/O |
| **任务队列** | 把同步阻塞变成异步流水线 | 多队列 + 线程池；按优先级分队列（前台 vs 后台）；**批处理能力**（一次处理一批请求） |
| **网络框架** | 海量并发连接 + 小包 | **事件驱动（epoll）+ 非阻塞 I/O**；连接复用；发送/接收缓冲批处理 |
| **压缩与解压缩** | 磁盘空间与网络带宽 vs CPU | **按块压缩**（SSTable 以块为单位压缩，读只解压需要的块）；可插拔算法（Snappy/LZO/ZSTD 一系） |

```text
# 教学示意，不参与构建：任务队列为什么能救吞吐
naive:  每个请求一个线程 -> 上下文切换 + 锁竞争 -> 吞吐在几百核上不去
better: 前台线程只做"收包 + 校验 + 入队"
        工作线程按批取出 N 个请求 -> 一次加锁 + 一次批量 I/O -> 一次批量应答
        => 摊薄了锁、系统调用与 I/O 的固定开销（这就是"成组提交"的通用形式）
```

> **本书 9.1 的价值**：这一节不讲分布式，但它是**工程上真正决定成败的部分**。
> 2026 年读依然句句成立（只是具体库换成了 Rust/C++ 的现代等价物）。

### 9.2 RootServer：中心节点的全部职责

- **数据结构**：维护 tablet（子表）的元信息——范围、副本位置、版本、大小；
  采用类似 Bigtable 的**分层元数据**（root table → meta table），元数据本身也多副本。
- **子表复制与负载均衡**：
  - 副本数不足时**补副本**（从现有副本拷贝）；
  - 负载不均时**迁移子表**：在目标机建副本 → 追平增量 → 切换服务 → 删除源副本；
  - 调度依据是 DataServer 心跳上报的负载（CPU、内存、磁盘、网络、读写次数/量）。
- **子表分裂与合并**：子表过大则分裂（保持迁移粒度与并行度），过小则合并（减少元数据与开销）。
- **UpdateServer 选主**：RootServer 负责**选出一个 UpdateServer 作为主**，
  通过租约/心跳机制维持；主不可用时在备中选新主。
- **RootServer 主备**：自身也要高可用（主备 + 状态同步 + 选主）。

```text
# 教学示意，不参与构建：子表迁移的三步（保证迁移中不停服）
migrate(tablet_id, from_node, to_node):
    1. to_node 上创建 tablet 副本，从 from_node 拷贝基线 + 追增量
    2. 追平后，把该 tablet 的读写服务切到 to_node（元数据版本 +1）
    3. 删除 from_node 上的副本
    # 全程对外服务不中断；客户端通过 RootServer 的元数据版本感知切换
```

### 9.3 UpdateServer：单点写的三件套

- **存储引擎**：
  - 结构是**内存 B+ 树**（支持范围扫描与有序合并），行数据存在内存池里；
  - 每次修改先写 **commit log**（redo 日志），**主备强同步**落盘后才应答客户端；
  - 内存占用到阈值时**冻结**当前活跃内存表、转储为 SSTable 交给 ChunkServer
    （相当于一次 minor compaction），从而释放内存。
- **任务模型**：**异步 + 批量**。
  - 写请求入队 → 批处理线程一次取出一批 → 一次写日志（成组提交）→ 一次应用内存 → 批量应答；
  - 这是**单点能撑住高 TPS 的核心原因**：把每次请求的一次 fsync 摊成一批一次 fsync。
- **主备同步**：commit log 强同步到备机（本书 8.4「一致性选择」给出的强一致路线），
  主故障时备机接管，**RPO = 0**（已提交数据不丢）。

### 9.4 ChunkServer：读路径的全部优化

- **子表管理**：每个子表 = 一组 SSTable（基线）+ 对应的增量（来自 UpdateServer）；
  子表是**迁移、复制、分裂合并**的基本单位。
- **SSTable 结构**：数据按**块（block）**组织，块内可压缩；
  块索引（稀疏索引）+ **布隆过滤器**（避免读不存在的 key 时扫全表）。
- **缓存实现**：多级缓存（块缓存 block cache + 行缓存 row cache），
  常用 **LRU（及其变体）**淘汰；热点行的行缓存对点查效果最好。
- **IO 实现**：**批量 I/O**（把多个随机读合并批量提交）+ **预读**（顺序扫描时提前加载）。
- **定期合并 & 数据分发**：把增量合并进基线生成新版 SSTable，并分发到各 ChunkServer。
- **定期合并限速**（本节最实用的一条经验）：

```text
# 教学示意，不参与构建：为什么要给后台合并限速
后台合并是"正确但贪婪"的工作：它会吃满磁盘带宽与 CPU
-> 前台读写延迟会被拖垮（表现为毛刺）
-> 所以必须对合并限速（限制每秒合并的数据量 / IOPS / 带宽）
-> 并在业务低峰放开限速、高峰收紧
# 这条经验对今天所有 LSM 系引擎（RocksDB/HBase/TiKV）同样成立
```

### 9.5 消除更新瓶颈：三条出路（本章最有前瞻性的一节）

- **读写优化回顾**：把 9.1–9.4 的所有优化（内存表、成组提交、批量、异步、缓存）再收一遍，
  但作者承认：**优化只是延后瓶颈**。
- **数据旁路导入**：批量导入数据时**绕过 UpdateServer**，直接生成 SSTable 交给 ChunkServer。
  这是「绕开写路径」的思路——代价是这些导入数据要**走独立的正确性校验**。
- **数据分区**：**把 UpdateServer 按数据范围拆成多组，每组只负责一部分数据**
  （各分区有自己的内存增量、commit log 与主备）。

```text
# 教学示意，不参与构建：9.5「数据分区」正是 1.0 的方向
0.x:   [ UpdateServer ] -- 负责全部数据的写
       ↓ 分区
1.x:   [ UPS 组 A: key ∈ [a, m) ] [ UPS 组 B: key ∈ [m, z) ]
       每组独立选主、独立 commit log、独立主备强同步
       -> 写能力随分区数线性扩展
       -> 跨分区事务需要 2PC（正是本书 3.7 + 第 7 章 Spanner 的模式）
```

> **读这一章的方法论结论**：
> 当一个系统出现「单点」时，作者给出的三条出路是——
> **让它更快（优化）/ 绕过它（旁路导入）/ 拆开它（分区）**。
> 这三条是通用的架构解题法，比 OceanBase 本身的细节更有长期价值。

## 版本演进

- **本书无第二版**；本节写 2013 年（OB 0.x 实现）→ 2026 年的变化。
- **9.3 UpdateServer 已成历史**：单点写在 **2016 年 V1.0** 被分区化取代
  （本书 9.5 已经预告了这条路）。今天 OceanBase 的写入路径是
  **分区 + 多副本共识 + 分布式事务**，不再有全局唯一的 UpdateServer。
- **9.4 SSTable/定期合并的思想仍在，但形态变了**：
  今天的 OB 存储引擎是 **LSM 系行存（4.x 又加了列存）**，
  「内存表 + 转储 + 合并」的骨架与本书一致，
  但合并策略、限速、压缩算法、缓存结构都已重写为现代版本。
- **LSM 引擎的十年研究**（本书 9.4 的学术续集）：
  **WiscKey（FAST 2016）键值分离** → **Monkey（SIGMOD 2017）布隆过滤器最优分配** →
  **Dostoevsky（SIGMOD 2018）自适应合并** → **VLDB Journal 2020 综述**。
  主线是把「写/读/空间放大」从二选一变成连续可调。
- **硬件变化改写本章的前提**：
  - **NVMe** 让随机读降到微秒级，本书 9.4 大量「把随机读变顺序读」的技巧收益下降；
  - 但 **SSD 写寿命**让本书没提的**写放大**变成一等公民；
  - **Optane / 持久化内存已于 2022 年退市**，不能作为设计选项（本书时代也没有）；
  - **RDMA** 让网络不再是主瓶颈，本书 9.1 网络框架的一些优化前提被削弱（但批量思想不变）。
- **多租户与资源隔离**：本书只有「定期合并限速」这一条限速；
  2026 年 OB 提供**租户级资源隔离**（CPU/内存/IOPS），把「限速」从后台任务扩展到多租户维度。

- **「定期合并限速」的普适性**：本书 9.4 这条经验在今天所有 LSM 系系统里都存在对应物——
  RocksDB 的 rate limiter、HBase 的 compaction throttle、TiKV 的 compaction 限流。
  **这是本章最值得直接迁移到 2026 年的一条工程经验**。
- **旁路导入已经产品化**：本书 9.5 的「数据旁路导入」今天叫
  **批量加载 / direct load / external table load**（绕过事务路径直接生成数据文件），
  是 HTAP 与数仓场景的标准能力。
- **数据分区成为默认**：本书 9.5 的「数据分区」在 2016 年 V1.0 落地，
  今天所有原生分布式数据库都是「分区 + 每分区一个共识组」的形态。
  **本书 9.5 是理解这场演进的钥匙。**
- **缓存结构的现代形态**：本书 9.4 的多级 LRU 今天普遍升级为
  **分代/扫描友好型缓存**（如 RocksDB 的 block cache + row cache、
  各类 clock/tinyLFU 变体），核心矛盾不变：**避免大扫描把热点缓存冲掉**。
- **列存的加入**：OB **2024 年推出列式存储**后，
  存储引擎不再是单一的「行存 SSTable」，而是**行存 + 列存共存**（HTAP），
  这与本书 9.4 只描述行存 SSTable 的局面完全不同。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「公共模块不重要，架构才重要」 | 9.1 的六个模块（内存/结构/锁/队列/网络/压缩）是**吞吐与稳定性的真正战场**；多数线上事故出在这里 |
| 2 | 「内存池只是为了避免 malloc 慢」 | 更重要的是**避免内存碎片与长跑退化**，以及让内存占用可预测（便于容量规划） |
| 3 | 「备份越多越安全，强同步没问题」 | 强同步下任一备故障会**阻塞写**（可用性下降）；这是 C/A 取舍，不是配置失误 |
| 4 | 「后台合并应该尽快跑完」 | 必须**限速**；不限速的合并会吃满 I/O 与 CPU，造成前台延迟毛刺（本书 9.4 明确写了） |
| 5 | 「旁路导入是取巧」 | 它是批量场景的**正规解法**，代价是需要独立的正确性校验与元数据管理 |
| 6 | 「数据分区只是为了性能」 | 它同时改变了事务模型：跨分区需要 **2PC**——性能和正确性是一起变的 |
| 7 | 🔧 9.3 的 UpdateServer 单点写已不存在 | 2016 年 V1.0 起改为分区化；本章描述的是 0.x，读时必须配官方现代架构文档 |
| 8 | 🔧 9.4 的 SSTable/合并讨论缺少「三种放大」框架 | 2026 年用**写/读/空间放大**来量化；WiscKey/Monkey/Dostoevsky 一系给出了调优空间 |
| 9 | 🔧 9.1 的硬件前提已变（NVMe / RDMA） | 随机读不再昂贵，但**写放大与 SSD 寿命**成为新的一等公民；Optane 已于 2022 年退市，不可作为选项 |
| 10 | 🔧 9.4 只有行存 | 2024 年 OB 推出列式存储，行存 + 列存共存（HTAP）；本章的存储引擎世界观需要扩展 |
