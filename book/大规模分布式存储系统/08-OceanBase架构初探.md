# 第 8 章　OceanBase 架构初探

> 原书第 8 章是实践篇的开篇，也是全书**最独特、最不可替代的一章**——
> 它记录了中国第一个自研分布式关系数据库 **OceanBase 0.x** 的完整架构与取舍。
> 但这一章也是**与今天产品差距最大的一章**：
> 0.x 的「单点 UpdateServer」在 2016 年 V1.0 就被彻底推翻了。
> 读这一章的正确姿势是**把它当架构史与设计方法论读**，而**不是**当作今天 OceanBase 的说明书。
> 本文件的「版本演进」与「🔧 修正」两段是全目录中最重要的补丁。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 8.1–8.2 背景与设计思路：一个假设撑起整个架构

- **需求背景**：阿里的收藏夹、评价等场景——**数据量是 PB 级，但需要关系模型与事务**，
  而当时的方案（分库分表 + MySQL）削掉了 join 与分布式事务。
- **核心洞察（这是 OceanBase 0.x 的全部前提）**：

```text
# 教学示意，不参与构建：OceanBase 0.x 的负载假设
数据总量:  大（TB ~ PB），必须分布到多台 ChunkServer
单次修改量: 小（一天的增删改相对总量占比很低，通常 < 1%）

=> 把"一天的修改"全部放进**一台机器的内存**（早期几十 GB 级）
=> 于是"写"可以集中到一个节点（UpdateServer）
   而"读"仍然分布到上千台 ChunkServer
=> 这就是**单写多读（single-write multi-read）**架构
```

- **由此推出的读写分离设计**：

| 角色 | 存什么 | 在哪 | 特点 |
| --- | --- | --- | --- |
| **基线数据（baseline）** | 昨天及以前的全部数据 | ChunkServer（SSTable，磁盘） | 只读、可压缩、可多副本 |
| **增量数据（增量 / delta）** | 今天的修改 | UpdateServer（内存 B+ 树） | 可写、单点、靠 commit log 持久化 |
| **查询结果** | 基线 + 增量的合并视图 | MergeServer 计算 | 读路径要**合并**两处数据 |

> 一句话：**OceanBase 0.x = 分布式只读基线图 + 一个可写的内存增量层 + 每日合并**。

### 8.3 系统架构：五个角色

```text
# 教学示意，不参与构建：OceanBase 0.x 的角色图
                    ┌────────────┐
       客户端 ──────▶│ MergeServer│  解析 SQL、定位、执行、合并结果
      (兼容 MySQL)   └──────┬─────┘
                            │ 读基线 + 读增量
              ┌─────────────┼─────────────┐
              ▼                           ▼
      ┌──────────────┐           ┌────────────────┐
      │ ChunkServer  │×N         │  UpdateServer  │  单点写（主备强同步）
      │ (基线 SSTable)│           │  (内存 B+ 树)   │
      └──────────────┘           └────────────────┘
              ▲                           ▲
              │   元数据 / 选主 / 负载均衡  │
              └─────────── RootServer ─────┘
                    （一主一备，Paxos/租约选主）
```

- **客户端**：兼容 MySQL 协议，应用基本无需改造；维护 tablet 位置缓存。
- **RootServer**：管理 tablet（子表）到 ChunkServer 的映射、执行负载均衡与子表迁移、
  **UpdateServer 选主**、集群状态监控。元数据量小，主备即可。
- **MergeServer**：接收 SQL，解析、生成执行计划，向 ChunkServer 与 UpdateServer 取数并合并。
  **这一层是查询的并发与并行所在**。
- **ChunkServer**：存基线数据（SSTable），负责子表管理、缓存、定期合并、数据分发。
- **UpdateServer**：**唯一的写入点**，内存 B+ 树 + commit log（redo 日志）；
  主备**强同步**复制保证不丢数据。
- **定期合并与数据分发**：每天把增量合并进基线（生成新版本的 SSTable），
  并分发到各 ChunkServer——**这是 OceanBase 0.x 日常最重要的后台动作**。

### 8.4 架构剖析：八个问题的答案

| 议题 | 0.x 的答案 | 代价 / 说明 |
| --- | --- | --- |
| **一致性选择** | **强一致**：UpdateServer 主备强同步，读可看到最新 | 写延迟包含一次跨机同步；但语义干净 |
| **数据结构** | 基线 **SSTable**（不可变、有序、可压缩）+ 增量 **内存 B+ 树** | 读要合并两处；写只碰内存 |
| **可靠性与可用性** | UpdateServer 一主多备强同步；RootServer 主备 + 选主；ChunkServer 多副本 | 备故障会阻塞写（典型 C/A 取舍） |
| **读写事务** | 写事务集中在 UpdateServer（天然串行化）；读事务用**版本号**读快照 | 写事务无分布式 2PC，简单；但写吞吐有上限 |
| **单点性能** | 靠 内存写 + **批量提交（成组提交）** + 网络/磁盘批处理 撑住 | 这是全架构最被质疑的一点，也是 1.0 被推翻的原因 |
| **SSD 支持** | 基线数据放 SSD（随机读友好），日志仍用磁盘顺序写 | 2013 年 SSD 尚贵，这个选择很前沿 |
| **数据正确性** | 校验和、多副本比对、回放校验等**多级校验** | 静默数据损坏是副本系统最阴险的敌人 |
| **分层结构** | 物理上分机架/机房，逻辑上 tablet，服务上 Root/Chunk/Merge/Update | 层次清晰，便于运维与定位问题 |

```text
# 教学示意，不参与构建：读路径的一次"合并"
SELECT * FROM t WHERE pk BETWEEN 100 AND 200;
  -> ChunkServer: 扫描基线 SSTable 中 pk∈[100,200] 的行（可能来自多个子表）
  -> UpdateServer: 取 pk∈[100,200] 的**增量修改**（内存 B+ 树，很快）
  -> MergeServer: 按 (tablet, row_key) 归并，增量覆盖基线 -> 返回结果
     因此：**读放大 = 基线扫描 + 增量查表**，但两者都在可控范围
```

> **单点 UpdateServer 的真实理由**（本书论证的精髓）：
> 不是「造不出分布式写」，而是**在「修改量小」这个负载假设下，单点写的成本最低、正确性最好**。
> 一旦假设不成立（写量涨到单机内存撑不住），这个架构就必须改——
> 这正是 2016 年 V1.0 做的那次**架构级升级**。

## 版本演进

- **本书无第二版**；本节写 2013 年记录（OB 0.x）→ 2026 年（OB 4.x+）的变化。
  这是全目录**跨度最大**的一段，务必读完再去看今天的 OceanBase 文档。
- **已核实的 OceanBase 时间线**（来源：OceanBase 官网、开源社区页、官方开发者大会材料）：

| 时间 | 事件 |
| --- | --- |
| 2010 | OceanBase 启动自主研发（官方口径「100% 根自研」） |
| 本书成书（2013） | 描述的是 **0.x 架构**：单点 UpdateServer + 每日合并（本章内容） |
| 2016 | **V1.0**：架构级升级为**全分布式**（去掉单点写，改为分区 + 多副本共识） |
| 2019-10-19 | 首次参加 **TPC-C**，以 **6088 万 tpmC** 打破 Oracle 保持了约 9 年的世界纪录 |
| 2020-05-20 | **TPC-C** 再次刷新：**7.07 亿 tpmC**（官方表述为较上次提升约 11 倍） |
| 2021-05-19 | **TPC-H**：基于 64 台 ECS（共 5120 核）以 **1526 万 QphH @30000GB** 创世界纪录 |
| **2021-06-01** | **正式开源**（`oceanbase/oceanbase`），首个社区版 3.1.0，开源约 300 万行代码，MulanPubL-2.0 许可 |
| 2022 | **V4.0「小鱼」**：业内首个**单机分布式一体化**架构；获 2022 年世界互联网大会「领先科技成果奖」 |
| 2022 | VLDB 2022 论文《OceanBase: A 707 Million tpmC Distributed Relational Database System》 |
| 2023 下半年 | 提出 **一体化（all-in-one）数据库**概念：OLTP + OLAP + KV（OBKV）+ AI 负载 |
| 2024 | 推出**列式存储**，强化 TP/AP 一体化；提供 SQL + NoSQL 多模能力 |
| 2024-09 | 首批通过中国信息安全测评中心分布式数据库「安全可靠测评」（第 2 号结果） |

- **需要澄清的两条**（涉及任务描述中的说法）：
  1. **「2009 年 TPC-C 世界纪录」未能核实**——可核实的只有 2019 与 2020 两次 TPC-C
     与 2021 一次 TPC-H。**不存在 OceanBase 于 2009 年打榜的公开记录**
     （2009 年前后 OceanBase 尚在起步期，官方口径 2010 年启动研发）。
  2. 原书作者杨传辉的职务在本书出版时为**阿里巴巴高级技术专家**；
     仓库大纲文件另记「现任蚂蚁金服 OceanBase 团队研究员」——这是**2013 年之后的职务**，
     与本文件记录的 2013 年口径不冲突，但引用时应注明时间。
- **架构演进的三跳（本书内容 → 今天）**：

```text
0.x（本书）  : 单写多读，UpdateServer 单点，每日合并
                ↓ 写量增长 + 需要水平扩展写能力
1.0（2016）  : 全分布式，分区 + 多副本共识，无单点写
                ↓ 小客户也要用，但不需要分布式部署
4.0（2022）  : 单机分布式一体化 —— 同一套代码，既能单机部署也能分布式部署
                ↓ 一份数据既要 TP 又要 AP
4.x（2024+） : 行存 + 列存一体化（HTAP）、多模（OBKV / HBase API / 向量）
```

## 近年研究与工业界开源实践（2015–2026）

- **`oceanbase/oceanbase` 实测 star：10291**（2026-09，`gh api` 实测）。
  > 注意：star 数衡量的是**开源社区关注度**，不等于装机量或市场份额；
  > 官方口径称社区版部署集群数过万、客户 4000+（**具体数字本目录未逐项核实**）。
- **TPC-C / TPC-H 打榜的意义**（本章 8.1「背景简介」的 2026 年续集）：
  - TPC-C 要求**可串行化隔离级别 + 抗单点故障 + 一定比例的分布式事务**，
    并由 TPC 授权审计员审计——**不接受**用 BenchmarkSQL 等工具自测后自称「符合 TPC-C 规范」的结果；
  - 两次 TPC-C 打榜（2019 / 2020）验证了「原生分布式架构 + 强一致事务」能跑进第一梯队；
  - **读法提醒**：基准测试成绩不等于业务性能，选型时应回到自己的负载形状。
- **对比其他国产分布式数据库**（2026 年）：

| 系统 | 复制/共识 | 全局时钟 | 存储 | 一体化 |
| --- | --- | --- | --- | --- |
| OceanBase | 多副本（Paxos 系） | GTS（TSO） | LSM 系行存 + 列存（4.x） | 单机分布式一体化 + HTAP |
| TiDB | Multi-Raft | TSO（PD） | RocksDB（LSM） | HTAP（TiFlash 列存） |
| PolarDB | 共享存储 + 一写多读 | 单机时钟 | 自研存储引擎 | 存算分离 |
| CockroachDB | Raft | HLC | Pebble（LSM） | 多区域 + HTAP 方向 |

- **开源生态**：OB 开源采用 **Open Core 模式**（内核 + 分布式组件 + 驱动完全开源，
  生态工具 OCP/ODC/OMS 等另有社区版），许可为 **MulanPubL-2.0**。
  这与本书 8–11 章描述的「内部系统」状态完全不同。
- **存算分离与云原生**：本书 8.3 的 ChunkServer 是**本地盘 + 本地计算**的耦合形态；
  2026 年主流是**存算分离 + 共享存储 + 租户级弹性**（OB、PolarDB、Aurora 同向）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「OceanBase 有一个单点 UpdateServer」 | 这是 **0.x 架构**（2013 年本书描述）；**2016 年 V1.0 已改为全分布式**，不再有单点写 |
| 2 | 「OB 每天必须做一次全量合并」 | 0.x 的「每日合并」是**把增量并入基线**的后台动作，不是重建全库；且 1.0 之后机制已完全不同 |
| 3 | 「UpdateServer 是瓶颈所以设计失败」 | 它是**在特定负载假设（修改量小）下的最优解**；架构随负载变化而演进，这正是本书的价值所在 |
| 4 | 「读路径只查 ChunkServer」 | 0.x 的读要**合并基线与增量**两处（MergeServer 负责），这是理解该架构的关键 |
| 5 | 「强同步复制会让写入不可用」 | 它换来的是 RPO=0（不丢数据）；本书的取舍是**选 C 而非 A**，是有意识的工程决策 |
| 6 | 「TPC-C 成绩可以直接换算成业务 TPS」 | TPC-C 是特定混合事务模型 + 严格审计下的结果，与业务负载形状不同，不能套用 |
| 7 | 🔧 本章描述的是 0.x，与今天产品差距极大 | 2016 年 1.0 全分布式、2022 年 4.0 单机分布式一体化、2024 年列存——**读本章必须配官方现代文档** |
| 8 | 🔧 本章没有 HTAP / 列存 / 多模 | 2024 年 OB 推出列式存储，2023 年提出一体化（TP/AP/KV/AI）；本书只有行存 TP |
| 9 | 🔧 本章的系统是闭源内部系统 | **2021-06-01 已开源**（`oceanbase/oceanbase`，10291★）；今天可以直接读源码验证本章描述 |
| 10 | 🔧 本章没有「单机分布式一体化」这一维度 | 4.0（2022）之后同一套代码支持单机与分布式部署，这是国产数据库的重要差异化，也是本章完全不存在的设计目标 |
