# 第 1 章　概述

> 原书第 1 章只有两节（1.1 分布式存储概念、1.2 分布式存储分类），却是全书的**分类学地基**：
> 后面四篇十三章的分工，全部由这一章「按数据特征把存储系统分成四类」的决定推导出来。
> 本书成书于 2013 年，本章的四类分法今天依然好用，但**第四类（分布式数据库）的内涵
> 已经完全变了**——这是本章最需要补的地方。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 分布式存储概念 | 定义分布式存储系统；列出特性（可扩展、低成本、高性能、易用）；给出技术来源（分布式系统 + 数据库）；罗列核心技术点（数据分布、一致性、容错、负载均衡、事务与并发控制、易用性、压缩/解压缩） | 分布式存储 = 把单机存储问题在不可靠硬件上重做一遍；可扩展是**第一目标**，其余都是代价 |
| 1.2 分布式存储分类 | 先按「结构与内容的关系」分为非结构化 / 结构化 / 半结构化三类数据；再按系统形态分为四类：分布式文件系统、分布式键值系统、分布式表格系统、分布式数据库 | 数据的**结构程度**决定系统的形态；四类分别对应后四篇的范型（4/5/6/7 章） |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 1.1 分布式存储概念：一句话定义与四句话展开

本书给的定义可以压缩成一句：

> **分布式存储系统 = 把大量普通（不可靠）服务器上的存储资源组织起来，对使用者呈现为
> 一个可扩展、低成本、高性能、易用的存储服务。**

四个特性的内在张力（这是本章真正的骨架，书上分散在各处，这里集中）：

| 特性 | 含义 | 与谁冲突 |
| --- | --- | --- |
| 可扩展 | 加机器就能加容量与吞吐，最好线性 | 与「强一致」冲突：机器越多，达成一致越贵 |
| 低成本 | 用普通 PC 服务器 + 廉价磁盘，靠软件容错 | 与「高性能 / 低延迟」冲突：廉价硬件故障率高 |
| 高性能 | 高吞吐（QPS/TPS）+ 低延迟 | 与「低成本」冲突，也与「副本数」冲突（副本多写多份） |
| 易用 | 对外接口简洁（SQL/文件/键值） | 与「可扩展性」冲突：接口越像单机，越难拆开 |

「易用」这一条常被读者跳过，但它是本书后半部分的暗线：OceanBase 之所以要兼容 MySQL 协议、
之所以要自己实现 SQL 层，就是为了在分布式的前提下把「易用」抢回来。

**技术来源的两个领域**（本书的一个漂亮提法）：

```
分布式存储技术
├── 来自「分布式系统」：数据分布、一致性、容错、负载均衡
└── 来自「数据库」：事务与并发控制、易用性（SQL）、压缩/解压缩
```

这条分界线解释了本书的篇章结构——第 3 章讲前者，第 2 章讲后者，
第 8–11 章（OceanBase）则是两者的合流。

### 1.2 分布式存储分类：先分数据，再分系统

**第一步：按「结构与内容的关系」分数据。**

| 数据类别 | 结构与内容的关系 | 例子 |
| --- | --- | --- |
| 非结构化数据 | 只有内容、没有结构 | 文档、文本、图片、音视频 |
| 结构化数据 | 结构（schema）与内容分离 | 关系型二维表 |
| 半结构化数据 | 结构与内容混在一起 | HTML、XML、JSON |

**第二步：按系统形态分四类**（本章的结论，也是全书的目录骨架）：

```text
# 教学示意，不参与构建：把四类范型写成一张速查表
storage_taxonomy = {
    "分布式文件系统": {
        "数据": "非结构化（Blob / 定长块 / 大文件）",
        "数据单位": "块（chunk），典型 64MB",
        "接口": "文件/对象语义，无 schema",
        "典型": "GFS、HDFS、TFS、Haystack",
        "本书": "第 4 章",
    },
    "分布式键值系统": {
        "数据": "关系简单的半结构化",
        "数据单位": "单条 key-value",
        "接口": "基于主键的 CRUD（get/put/delete），一般无范围扫描",
        "典型": "Dynamo、Tair",
        "本书": "第 5 章",
    },
    "分布式表格系统": {
        "数据": "复杂的半结构化（多维映射表）",
        "数据单位": "行 + 列族，按主键全局有序",
        "接口": "主键 CRUD + 范围扫描，弱事务",
        "典型": "Bigtable、HBase、Megastore、Azure Table",
        "本书": "第 6 章",
    },
    "分布式数据库": {
        "数据": "结构化（二维关系）",
        "数据单位": "行（关系元组）",
        "接口": "SQL，通常要有事务",
        "典型": "MySQL Sharding、SQL Azure、Spanner、OceanBase",
        "本书": "第 7 章 + 第 8–11 章",
    },
}
```

**这张表要横着读，也要竖着读：**

- 横着读：每一类都是「数据有多结构 → 系统能承担多少语义」的结果；
- 竖着读：从文件系统到数据库，**系统的语义能力递增，可扩展的上限递减**。
  文件系统能存 EB 级，数据库能存 TB~PB 级还要保证事务——这不是实现水平差异，
  是**语义承诺带来的本质代价**。

### 1.3 一个容易漏掉的点：四类不是四个孤岛，而是分层

原书在分类时把它们并列，但工程上它们常常**上下叠放**：

```text
# 教学示意，不参与构建：四类系统的常见层叠关系
[ 应用 ]
    |
[ 分布式数据库 ]  ← 提供 SQL 与事务（第 7 章）
    |
[ 分布式表格 ]    ← 提供有序主键 + 范围扫描（第 6 章）
    |
[ 分布式键值 ]    ← 提供主键点查，常作缓存（第 5 章）
    |
[ 分布式文件系统 ]← 提供 Blob / 块持久化底座（第 4 章）
    |
[ 单机存储引擎 ]  ← B 树 / LSM 树 / 哈希（第 2 章）
```

- Bigtable 建在 GFS 之上（本书 6.1 明确说「Bigtable 本质是构建在 GFS 上的一层分布式索引」）；
- OceanBase 的 ChunkServer 用 SSTable，语义上就是一层表格系统；
- Tair 常用作上层数据库的缓存。

**读法建议**：把本章这张分类表当成一张**分层图**而不是四个并列的盒子，
后面读第 4–7 章时会顺畅很多——每一章都在回答「上面那一层要我提供什么」。

## 版本演进

- **本书无第二版**（未见公开的第二版书目记录）。本节写的不是版次差异，而是
  2013 年口径 → 2026 年视角的变化。
- **2013 年口径的四类**：文件 / 键值 / 表格 / 数据库，按「结构程度」分。这个分法
  在 2026 年依然是最清晰的教学分类之一，值得保留。
- **2026 年真正变了的是边界**：
  1. 类与类之间的墙变薄了——HBase 支持 SQL 层（Phoenix）、OceanBase 兼容 MySQL 又提供
     HBase API、对象存储上直接跑表格式（Iceberg/Delta/Hudi）；
  2. 多出了「文件系统的另一种形态」——云对象存储（S3/OSS/COS）取代了自建 DFS 的位置，
     成为绝大多数新建系统的底座（详见 [04-分布式文件系统.md](04-分布式文件系统.md)）；
  3. 多出了 2013 年没有的第五类候选——**向量数据库 / 多模数据库**，
     它服务的「数据」是 embedding，结构程度介于半结构化与非结构化之间，
     语义上最接近键值系统，但查询语义是「最近邻」而非「点查」。
- **术语口径**：原书用「分布式数据库」指 2013 年的形态（中间层 + 分库分表、SQL Azure、
  Spanner）。2026 年这个词的默认含义已经变成 **NewSQL / 原生分布式数据库**
  （OceanBase、TiDB、CockroachDB、PolarDB 等），见 [07-分布式数据库.md](07-分布式数据库.md)。

- **分类学本身的两条新趋势**：
  1. **「存算分离」把四类重新洗牌**——计算层（Spark/Flink/Presto）与存储层
     （对象存储 + 表格式）解耦后，「文件系统」这一层的名字从 HDFS 换成了
     S3/OSS + Parquet + Iceberg；
  2. **湖仓表格式成为新的第四类候选**——Iceberg（`apache/iceberg`，9276★）、
     Delta（`delta-io/delta`，9020★）、Hudi（`apache/hudi`，6275★）提供的是
     「对象存储上的表语义」，它们既不是文件系统也不是数据库，
     但承担了 2013 年数据库的一部分职责（ACID 提交、schema 演进、时间旅行）。
- **OceanBase 的时间线（本章分类里「分布式数据库」这一格的直接后续）**：
  2010 年启动自主研发 → 2016 年 V1.0 转为全分布式 → 2021-06-01 正式开源
  （`oceanbase/oceanbase`）→ 2022 年 V4.0「单机分布式一体化」→ 2024 年推出列式存储。
  这条线把本书 8–11 章描述的 OB 0.x 与今天的产品连起来，详见
  [08-OceanBase架构初探.md](08-OceanBase架构初探.md)。
- **国产数据库格局（2026 年）**：OceanBase、PolarDB（阿里云，存算分离 + 共享存储）、
  TiDB（PingCAP，Raft + Percolator 事务）、GaussDB/openGauss（华为，openGauss 开源）
  构成第一梯队。四者的差别主要在**存储是否共享、事务用哪种时钟、是否一体化 HTAP**，
  这正是本书第 3 章（一致性/复制）与第 7 章（架构）在 2026 年的具体化。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「分布式存储 = 分布式数据库」 | 数据库只是四类之一，且是**语义最重、扩展上限最低**的一类；文件系统/键值/表格各自有独立场景 |
| 2 | 「四类系统是并列的，选一个用」 | 工程上它们是**层叠**的：Bigtable 建在 GFS 上、OB 的 ChunkServer 是一层表格；选型往往是「选哪两层」 |
| 3 | 「半结构化 = JSON」 | 原书口径是「结构与内容混在一起」，HTML 是典型例子；JSON 只是今天最常见的形态 |
| 4 | 「文件系统只能存图片视频」 | 它还是表格系统与数据库的**持久化底座**（GFS→Bigtable、HDFS→HBase），也是今天对象存储的前身 |
| 5 | 「分布式就一定比单机快」 | 分布式解决的是**容量与吞吐**，单条请求的延迟通常更差（网络跳数）；原书 1.1 把「高性能」列为特性，要理解成**集群吞吐**而非单请求延迟 |
| 6 | 🔧 原书 2013 年分类里没有「对象存储」这一格 | 2026 年主流底座已从自建 DFS 换成**云对象存储**（S3/OSS/COS）；第 4 章的 GFS/HDFS 知识要翻译成「元数据服务 + 对象存储」的等价问题 |
| 7 | 🔧 原书没有湖仓表格式 | Iceberg/Delta/Hudi 在对象存储上提供表语义（ACID、schema 演进、时间旅行），是 2013 年不存在的**新一层**，建议插入本章四类之后作为第五格候选 |
| 8 | 🔧 原书「分布式数据库」的默认形态已过时 | 2013 年指中间层 + 分库分表 / SQL Azure / Spanner；2026 年默认是**原生分布式 NewSQL**（OB/TiDB/PolarDB/CockroachDB），中间层方案已退居二线 |
| 9 | 🔧 原书完全没有向量/多模数据 | 2026 年向量检索已进入主流数据库（OB 4.x 提供向量能力、pgvector、Elasticsearch dense vector），「按结构程度分类」需要为 embedding 这类数据留位置 |
