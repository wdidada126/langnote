# 第 7 章　分布式数据库

> 原书第 7 章是范型篇的收尾，也是**全书技术含量最高的一章**：
> 三个案例分别代表 2013 年「做分布式数据库」的三条路——
> **中间层（把单机库拼起来）/ SQL Azure（把单机库托管并复制）/ Spanner（从零设计分布式）**。
> 作者在「讨论」里的倾向很清楚：中间层是**过渡方案**，Spanner 式的设计才是终局。
> 2026 年回头看，这个判断基本应验了：**中间层已被原生分布式 NewSQL 大规模取代**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 7.1 数据库中间层 | 架构（应用 → 中间件 → 多个 MySQL 分库）、扩容（数据迁移 + 双写）、讨论 | 实现简单、成本低，但**跨库 join 与分布式事务是硬伤**，扩容代价大 |
| 7.2 Microsoft SQL Azure | 数据模型、架构（四层）、复制与一致性（一主两备 + quorum）、容错、负载均衡、多租户、讨论 | 把单机 SQL Server **托管化 + 多副本化**，语义不变、扩展性有限 |
| 7.3 Google Spanner | 数据模型（半关系 + 层次表）、架构（universe/zone/spanserver）、复制与一致性（Paxos 组）、**TrueTime**、并发控制、数据迁移、讨论 | **用硬件时钟换全球一致的外部一致性**，把分布式事务做成可用 |

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 7.1 数据库中间层：把单机库拼成分布式

- **架构**：应用 → **中间层**（解析 SQL、路由、改写、聚合结果）→ 后端多个**单机 MySQL 分库**。
  中间层承担：SQL 解析、分库路由、结果合并、读写分离、连接池。
- **扩容**：增加分库 → 需要**数据迁移**（按分片键重新分布）→ 迁移期常需**双写 + 追增量 + 切流**。
- **硬伤**（本书「讨论」的核心）：
  1. **跨库 join**：要么不支持，要么把数据拉到中间层做——代价随数据量爆炸；
  2. **分布式事务**：中间层只能做尽力而为的 2PC，性能与正确性都难保证；
  3. **自增主键 / 全局唯一 ID**：需要一个独立的发号器；
  4. **扩容与再分片**：是运维噩梦（本节「扩容」讲的就是这件事）。

```sql
-- 教学示意，不参与构建：中间层把一条 SQL 拆成多条
-- 应用写的是:
SELECT o.id, o.amount, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.user_id IN (1, 2, 10086);

-- 中间层实际可能执行:
--   shard_0: SELECT ... FROM orders_0 o JOIN users_0 u ... WHERE o.user_id IN (1, 2)
--   shard_7: SELECT ... FROM orders_7 o JOIN users_7 u ... WHERE o.user_id = 10086
--   -> 中间层合并结果（排序/聚合在这里做）
-- 若 users 与 orders 的分片键不同 -> join 无法下推 -> 只能拉回来算
```

- **本节的正确读法**：中间层是**成本最低的起步方案**，它的收益是「不用改数据库内核」，
  代价是「语义被削掉一半，且削掉的部分恰好是数据库的价值所在」。

### 7.2 SQL Azure：把 SQL Server 搬上云并复制三份

- **数据模型**：仍是**关系模型 + T-SQL**，物理上每个逻辑数据库有 **3 个副本**
  （1 primary + 2 secondary），副本由底层 fabric 管理，用户看不到。
- **架构（四层）**：
  - **Client Layer**：协议网关（TDS 协议），把连接路由到正确的物理机器；
  - **Services Layer**：逻辑数据库的管理、计费、 provisioning；
  - **Platform Layer**：物理机器上的 SQL Server 实例、fabric（故障检测与副本重建）；
  - **Infrastructure Layer**：物理硬件与操作系统。
- **复制与一致性**：写事务在 **primary + 至少一个 secondary** 上提交成功才返回（quorum），
  即**强同步**；副本故障时 fabric 自动补副本。
- **容错与负载均衡**：fabric 检测节点故障并重建副本；
  **负载均衡**通过把逻辑数据库在物理机器间迁移来实现（小库粒度，搬迁成本低）。
- **多租户**：一台物理 SQL Server 上跑多个逻辑数据库，需要**资源隔离与限流**
  （CPU/IO/连接数），且大库会被移到独占机器上。

> SQL Azure 的范式是 **scale-up（单机变大）+ 多副本 + 托管**，
> 而不是 scale-out。它解决的是「运维与可用性」，不是「扩展性上限」。

### 7.3 Spanner：用硬件时钟做全球一致的数据库

- **数据模型**：**半关系型**——有 schema、有表、支持 SQL，
  额外提供**层次结构**：`INTERLEAVE IN PARENT` 让子表与父表按主键前缀物理共存，
  从而把「经常一起访问的行」放在一起（这是对 Bigtable 列族思想的改进）。
- **架构**：

```text
# 教学示意，不参与构建：Spanner 的层级
universe（一个部署，全球级）
└── zone（一个数据中心单元；一个 universe 有多个 zone）
    ├── zonemaster: 把 tablet 分配给 spanserver
    ├── spanserver: 服务 100~1000 个 tablet
    ├── location proxy: 帮客户端定位 tablet 所在的 spanserver
    └── placement driver: 跨 zone 的数据迁移决策

tablet:   (key, timestamp) -> string 的有序映射
directory: 一组连续 key，是**数据放置与复制的基本单位**
paxos group: 一个 directory 的所有副本组成一个 Paxos 组（可跨 zone）
```

- **复制与一致性**：每个 directory 一个 **Paxos 组**，组内强一致；
  跨 directory 的事务用 **2PC**（协调者由参与者之一担任，且协调者本身是 Paxos 组，所以高可用）。
- **TrueTime**（本章最著名的部分）：
  - 每个数据中心配备 **GPS 接收机 + 原子钟**（两种时钟互为备份，失效模式不同）；
  - `TT.now()` 返回一个**时间区间 [earliest, latest]**，
    真实时间落在该区间内，区间半宽为 **ε**（论文给的典型值约几毫秒，工程上按 1~7ms 量级理解）；
  - **提交等待（commit wait）**：事务提交时间戳 `s` 必须等到 `TT.now().earliest > s`
    才允许对外可见 → 保证「提交后发生的读一定看得到这次提交」。

```text
# 教学示意，不参与构建：TrueTime + commit wait 换来外部一致性
1. 事务 T1 在副本 A 提交，取提交时间戳 s = TT.now().latest
2. 等待，直到 TT.now().earliest > s（等待时长约 = ε）
3. 之后任何机器上开启的事务 T2，其时间戳必然 > s
   -> T2 一定看到 T1 的写入
   -> 这就是**外部一致性（external consistency）**：
      按真实时间顺序发生的提交，其可见顺序与之一致
```

- **并发控制**：
  - **读写事务**：**两阶段锁（2PL）+ wound-wait 死锁预防**（老事务抢新事务的锁）；
  - **只读事务**：**无锁快照读**——客户端给出时间戳（或读最新），
    spanserver 用 MVCC 提供该时刻的快照；
  - **快照读**时间戳的选择由 TrueTime 保证不读到「未完成的事务」。
- **数据迁移**：`movedir` 后台任务把一个 directory 从一组 Paxos 组搬到另一组
  （用于跨 zone 的负载均衡、把数据挪近访问方）。

### 7.4 三条路的对比（本章的结论）

| 维度 | 数据库中间层 | SQL Azure | Spanner |
| --- | --- | --- | --- |
| 扩展方式 | scale-out（分库） | scale-up（单机变强）+ 托管 | scale-out（原生分片 + Paxos） |
| 事务 | 跨库事务难，常降级 | 单机事务（强） | **全球分布式事务**（强） |
| 一致性 | 依赖下层单机库 | 强同步 quorum | **外部一致性**（TrueTime） |
| SQL 语义 | 被削（join/事务受限） | 完整 | 完整（但需 schema 设计配合） |
| 改造成本 | 低（不动数据库内核） | 中（云厂商承担） | 高（从零造） |

## 版本演进

- **本书无第二版**；本节写 2013 年口径 → 2026 年视角的变化。
- **7.1 中间层已大规模退场**：2026 年新建核心系统绝大多数直接选**原生分布式数据库**
  （OceanBase / TiDB / PolarDB / CockroachDB / GaussDB），
  分库分表中间件（Cobar/MyCat/ShardingSphere 一系）退到
  「存量系统平滑迁移」与「轻量分片」场景。**这一节的历史价值大于选型价值。**
- **7.2 SQL Azure 的形态延续**：Azure SQL Database 仍在演进（Hyperscale 引入
  日志服务 + 页面服务器，走向**存算分离**），核心变化是
  **从「单机多副本」转向「日志即数据库 + 共享存储」**（与 AWS Aurora 同路）。
- **7.3 Spanner 成为范式输出者**：Spanner 论文（OSDI 2012）催生了
  CockroachDB、YugabyteDB、TiDB（部分思想）等一大批系统。
  2026 年 Google Cloud Spanner 仍是托管服务，并增加了 **PostgreSQL 接口**等能力
  （**具体版本与功能集本目录未逐条核实**）。
- **TrueTime 的两条替代路线**（本书未预见，因为 HLC 论文发表于 2014）：
  - **TSO（中心时间戳分配器）**：简单严格，OceanBase 的 GTS、TiDB 的 PD 都是这条路；
  - **HLC（混合逻辑时钟）**：无专用硬件，CockroachDB/YugabyteDB 用它做无中心时间戳。
  **结论：TrueTime 依赖 GPS/原子钟硬件，不可复制；通用系统只能走 TSO 或 HLC。**
- **国产数据库格局（2026 年）**：

| 系统 | 路线要点 | 与本章的对应 |
| --- | --- | --- |
| OceanBase | 原生分布式，Paxos 多副本，TSO（GTS），**单机分布式一体化**（4.x，2022） | 继承 Spanner 的 Paxos + 2PC，另加「一体化」 |
| TiDB | Raft（Multi-Raft）+ **Percolator 乐观事务** + TSO | 分片复制同 Spanner，事务模型走 Percolator |
| PolarDB | **共享存储 + 一写多读**（存算分离），日志即数据库 | 更接近 SQL Azure Hyperscale / Aurora 路线 |
| GaussDB / openGauss | 国产化路线，多形态（主备/分布式） | 偏工程形态多样 |

- **实测 star（2026-09，`gh api` 实测）**：

| 项目 | 定位 | star |
| --- | --- | --- |
| `oceanbase/oceanbase` | 国产原生分布式数据库，Spanner 一脉 + TSO | 10291 |
| `pingcap/tidb` | NewSQL：Multi-Raft + Percolator 事务 + TSO | 40591 |
| `cockroachdb/cockroach` | Spanner 的开源精神继承者：Raft + HLC | 32508 |
| `tikv/tikv` | TiDB 的 Multi-Raft 存储层 | 16878 |
| `polardb/polardb-x` | PolarDB 分布式版（开源） | 102 |

> `polardb/polardb-x` 的 star 数远低于其知名度，因为 PolarDB 的主线产品并不以
> 该仓库为主要形态；**star 数不等于装机量**，读这张表时请注意。

- **中间层的现代形态**：Apache ShardingSphere 一系仍在活跃，但定位从
  「分布式数据库的替代品」变成「**迁移与分片工具**」；
  本书 7.1 讲的四个硬伤（join/事务/ID/扩容）今天仍然是它的边界。
- **Spanner 范式的三条落地分支**：
  1. **TSO + Paxos/Raft + 2PC**：OceanBase、TiDB（事务走 Percolator 但仍用 TSO）；
  2. **HLC + Raft**：CockroachDB（无中心时钟，靠 HLC + 因果序 + 读重启保证可串行化）；
  3. **共享存储 + 一写多读**：PolarDB、Aurora（放弃 scale-out 换单机语义完整性）。
- **HTAP 成为新维度**：本书 7.3 只谈 OLTP；2026 年 Spanner/TiDB/OB 都提供
  **HTAP**（行存 + 列存 + 资源隔离），OceanBase **2024 年推出列式存储**，
  把「一套数据同时跑 TP 与 AP」变成主流诉求（详见 [10-数据库功能.md](10-数据库功能.md)）。
- **OceanBase 的关键时间线**（第 8–10 章描述的 0.x 与此相连）：
  2010 启动 → 2016 V1.0 全分布式 → 2021-06-01 开源 → 2022 V4.0 单机分布式一体化 →
  2024 列式存储。详见 [08-OceanBase架构初探.md](08-OceanBase架构初探.md)。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「中间层 + 分库分表 = 分布式数据库」 | 它削掉了 join 与跨库事务，**语义损失**是使用它的前提；2026 年它主要是迁移/分片工具 |
| 2 | 「多副本就是分布式扩展」 | SQL Azure 的三副本解决的是**可用性**不是**扩展性**；写吞吐仍受单机上限约束 |
| 3 | 「Spanner 靠 TrueTime 才需要原子钟，通用系统也能照抄」 | TrueTime 依赖 GPS + 原子钟硬件；通用系统只能走 **TSO** 或 **HLC** |
| 4 | 「外部一致性 = 可串行化」 | 外部一致性要求**提交顺序与真实时间顺序一致**（比可串行化更强）；可串行化只要求等价于某个串行序 |
| 5 | 「commit wait 只是等一下，无所谓」 | 它直接把事务延迟抬高约 ε（毫秒级），是 Spanner 用**延迟换一致性**的显式代价 |
| 6 | 「只读事务需要加锁」 | Spanner 只读事务是**无锁快照读**，靠 MVCC + 时间戳；这是它读吞吐高的关键 |
| 7 | 🔧 本书把中间层当作「分布式数据库的实现方式之一」介绍 | 2026 年它已被**原生分布式 NewSQL** 大规模取代，本节的历史价值大于选型价值 |
| 8 | 🔧 本书没有 HLC / Percolator 两条现代事务路线 | HLC（2014）晚于本书；Percolator（2010）虽早于本书但本章未涉及；两者是 2026 年事务模型的主流 |
| 9 | 🔧 本书无 HTAP 概念 | 2026 年主流分布式数据库都同时承担 TP 与 AP；本书 7.3 只讲 OLTP，需补行存/列存一体化视角 |
| 10 | 🔧 本书的国产数据库格局完全不存在 | 2026 年第一梯队是 OceanBase / PolarDB / TiDB / GaussDB-openGauss；选型必须把它们纳入比较 |
