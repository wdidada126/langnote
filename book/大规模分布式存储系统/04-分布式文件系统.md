# 第 4 章　分布式文件系统

> 原书第 4 章讲四类范型里的第一类：**分布式文件系统**。它的定位很特别——
> 既直接服务「存图片/视频这类 Blob」，又是**分布式表格系统与数据库的持久化底座**
> （GFS 之上是 Bigtable，HDFS 之上是 HBase）。
> 本章四个案例（GFS / TFS / Haystack / CDN）的共同命题是：
> **元数据服务怎么做、大文件怎么分块、小文件怎么摊销、热点内容怎么前置**。
> 2026 年最需要补的一点是：**这一层的主流形态已经从「自建 DFS」换成「云对象存储」**。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 4.1 GFS：教科书级的「单 Master」设计

- **角色划分**：
  - **Master（总控节点）**：维护命名空间、文件→chunk 映射、chunk 位置信息、访问控制；
    全部元数据**驻留内存**（这是它敢单点的前提，也是它的容量上限）；
  - **ChunkServer**：存实际数据，每个 chunk 默认 **64MB**，默认 **3 副本**；
  - **Client**：从 Master 拿元数据，然后**直接与 ChunkServer 交互传数据**。
- **关键设计决策与理由**（本章最值得抄的四条）：

| 决策 | 理由 |
| --- | --- |
| chunk 64MB（远大于传统文件系统的块） | 减少元数据量（元数据能装进 Master 内存）、减少 client 与 Master 的交互、便于大文件顺序读写 |
| **单 Master** | 极大简化设计（全局视图 → 能做全局的副本放置与负载均衡）；代价靠「元数据小 + 影子 Master + 日志复制」扛住 |
| **追加写为主（record append），而非随机改写** | GFS 的主要负载是大数据批量处理与日志追加；追加写让一致性模型可简化为「至少一次成功」 |
| **控制流与数据流分离**（数据沿 ChunkServer 链流水线推送） | 把 Master 从数据路径上彻底拿掉，带宽瓶颈落在 ChunkServer 上 |

- **租约（lease）机制**（GFS 一致性的核心）：

```text
# 教学示意，不参与构建：GFS 的写流程与租约
1. Client 向 Master 请求 chunk 的租约持有者（primary）与副本位置
2. Master 把 chunk 的写租约（默认 60s，可续）授予某个 ChunkServer -> 它就是 primary
3. Client 把数据沿副本链**流水线推送**（每个 ChunkServer 收到即转发给下一个）
4. 数据到齐后，Client 向 primary 发写请求；primary 决定**变更顺序**
5. primary 把该顺序下发给所有 secondary，副本按同一顺序应用
6. 全部成功后 primary 应答 Client

作用：把"多个副本上的变更顺序"交给**一个租约持有者**决定 -> 副本间顺序一致
     租约到期/网络分区时，Master 等待租约过期再选新 primary -> 规避双主
```

- **一致性模型**：GFS 明确区分 **defined（已定义）** 与 **undefined but consistent（未定义但一致）**：
  串行写成功是 defined；并发追加成功是「至少一次」但各副本区间可能不同 → undefined。
  **这层不完美被有意留给了上层**（Bigtable 用日志 + 版本号把遗留的一致性问题解决掉）。
- **Master 设计**：命名空间用**前缀压缩**存于内存；操作日志（operation log）先落盘再应答，
  日志复制到多台机器；checkpoint（B 树形式）加速恢复；**影子 Master** 提供只读服务。
- **ChunkServer 设计**：chunk 以普通 Linux 文件存储；**惰性垃圾回收**（删除只是重命名 + 记时间，
  心跳时批量回收）；chunk 带**版本号**识别陈旧副本；校验和（checksum）分块检测数据损坏。

> **一句话读法**：GFS 的全部设计都在服务一个目标——
> **让 Master 尽可能少做事、让数据流量尽可能不经过 Master。**

### 4.2 TFS：为海量小文件而生

- **背景**：电商的图片（几 KB ~ 几百 KB）。用 GFS 那套 64MB chunk 存小图片，
  元数据会爆炸、随机读会退化。
- **架构**：**两个 NameServer（一主一备）+ 多个 DataServer**。
- **核心技巧**：
  - **大文件 / 小文件两级命名空间**：一个「大文件」（物理文件，通常 64MB 级）
    里塞进很多「小文件」（逻辑图片），小文件用 `(block_id, file_id)` 定位；
  - **追加写**：图片更新 = 写一份新的 + 改映射，与 GFS 一脉相承；
  - **图片去重**：用哈希算法为图片计算「指纹」，去重本身退化成一个**键值系统**的问题。

> 这个「大文件里装小文件」的技巧今天仍在用：**对象存储之上的日志结构合并**
> （LSM 思想搬到文件系统）、以及各类「小文件合并（har / sequence file）」方案。

### 4.3 Haystack：把元数据的开销压到极致

- **Facebook 的痛点**：数十亿张照片，每读一张照片要走若干次磁盘 I/O 拿目录元数据
  （POSIX 目录树的 inode/dentry 开销），磁盘 I/O 被元数据吃光。
- **三个组件**：
  - **Directory（目录）**：逻辑卷 → 物理卷的映射、CDN 与浏览器路由的 URL 生成；
  - **Store（存储）**：物理卷（volume，约 100GB 一个文件），
    内部是**扁平的 Needle 序列**（每条 Needle = 一张照片 + 元数据 + 校验和）；
  - **Cache（缓存）**：命中率高时直接挡掉 Store 的读。
- **核心技巧**：
  - **扁平化**：取消目录层次，用 `(volume_id, offset)` 直接定位 Needle，
    元数据量从「每文件一条」降到「每卷一条」；
  - **写只追加**：删除只是打标记，更新写新的 Needle；
  - **内存索引**：每个 Store 在内存里维护 `photo_id → (volume, offset, size)`，
    **一次磁盘读**就能取到照片。

```text
# 教学示意，不参与构建：Haystack 读照片的路径
read(photo_id):
    lookup Directory  -> 得到 CDN URL 或 Store URL
    if CDN hit: return CDN          # 大多数热点照片在此止步
    Store: 内存索引查 (volume, offset, size)
           -> 一次 pread(volume_file, offset, size)  # 没有目录树遍历
```

> TFS 与 Haystack 是同一个问题的两个答案：**小文件 + 海量 + 读多写少**。
> 差别是 TFS 用「大文件装小文件」，Haystack 用「扁平卷 + 内存索引」。

### 4.4 CDN：把内容推到用户门口

- **架构**：两级 Cache（边缘节点 + 区域节点）+ 源站；回源时逐级上溯。
- **负载均衡**：本书给的实例是 **LVS（四层）+ HAProxy（七层）**的组合——
  LVS 扛吞吐，HAProxy 做七层路由与健康检查。
- **本质**：**用边缘的存储空间 + 缓存命中率，换掉跨运营商/跨地域的网络延迟**。
- 与前三节的关系：CDN 是「分布式文件系统」在**地理维度**上的延伸，
  一致性问题变成**缓存失效（purge）与版本化 URL**。

## 版本演进

- **本书无第二版**；本节写 2013 年口径 → 2026 年视角的变化。
- **最重要的一条：这一层的主流形态变了**。
  2013 年的语境是「公司自建分布式文件系统」（GFS/HDFS/TFS）；
  2026 年的默认答案是**云对象存储**（Amazon S3、阿里云 OSS、腾讯云 COS 等）+
  **兼容 S3 语义的自建方案**（Ceph RGW、MinIO）。
  变化不是技术细节，而是**责任主体**：文件系统从「自己运维的服务」变成「云厂商的托管服务」。
- **HDFS 的地位下降**：Hadoop 生态仍在，但新建数据平台普遍把冷数据放对象存储、
  热数据放本地 NVMe 或缓存层，「HDFS 是唯一底座」的假设不再成立。
  这是本书第 4 章最需要标注的现实变化。
- **S3 语义的演进**：2020 年前后主流对象存储先后提供**强一致（read-after-write）**语义，
  把本书时代「对象存储只能最终一致」的假设推翻——这也正是**湖仓表格式**
  （Iceberg/Delta/Hudi）能在对象存储上提供 ACID 的前提。
- **存算分离**：计算层（Spark/Flink/Trino）与存储层解耦后，
  「文件系统的性能」这个命题被拆成「对象存储的带宽/请求速率」+「本地缓存命中率」两个问题。
- **接口变化**：POSIX/HDFS API → **S3 HTTP API** 成为事实标准接口；
  云原生文件系统（JuiceFS、Alluxio、CephFS）多数以「对象存储 + 元数据服务」的形态出现，
  这正是 GFS「Master + ChunkServer」结构的**现代翻版**。

## 近年研究与工业界开源实践（2015–2026）

- **开源实现与实测 star（2026-09，`gh api` 实测）**：

| 项目 | 定位 | star |
| --- | --- | --- |
| `apache/hadoop`（含 HDFS） | GFS 的开源实现，存量最大的自建 DFS | 15669 |
| `apache/hbase` | HDFS 之上的表格系统（→ 第 6 章） | 5560 |
| `apache/iceberg` | 对象存储上的**表格式**（湖仓） | 9276 |
| `delta-io/delta` | 对象存储上的表格式（Delta Lake） | 9020 |
| `apache/hudi` | 对象存储上的表格式（Hudi） | 6275 |

- **湖仓表格式是本章的 2026 年续集**：Iceberg/Delta/Hudi 做的事，
  本质上是**在对象存储（新时代的分布式文件系统）之上补一层「文件 → 表」的映射与 ACID**，
  正如当年 Bigtable 在 GFS 之上补一层「文件 → 有序表」的映射。
  对照读效果最好：[../湖仓架构大规模数据平台的设计和实现/03-存储湖仓架构的核心.md](../湖仓架构大规模数据平台的设计和实现/03-存储湖仓架构的核心.md)。
- **对象存储成为新底座**：2026 年新建数据平台的默认形态是
  **对象存储 + 列式文件（Parquet）+ 表格式 + 弹性计算**。
  本书 4.1 讨论的「chunk 多大」的问题，今天等价为「Parquet 文件多大 / row group 多大」。
- **HDFS 依然活着但不再是唯一**：它仍在大量存量集群服役（Hadoop 生态与 HBase 场景），
  但新建项目普遍走对象存储路线。**选型时的真实问题**是
  「要不要为 HDFS 的运维成本买单」，而不是「HDFS vs GFS」。
- **小文件问题的现代解法**：仍是 TFS/Haystack 那套思想——
  合并成大文件（Parquet 的多行组、Iceberg 的 data file 合并）+ 内存/外部索引。
  本书 4.2/4.3 的两个技巧在 2026 年依然是标准答案。
- **CDN 的演进**：边缘计算（在 CDN 节点上跑函数）与 QUIC/HTTP3 普及，
  使「分发」从纯缓存变成「缓存 + 计算」；本书 4.4 的两级 Cache 结构依然成立。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「GFS 单 Master 是缺点，已被淘汰」 | 单 Master 换来的是**全局调度能力**与实现简洁；GFS 的 Master 只存元数据，不参与数据路径。今天的对象存储元数据服务、JuiceFS/CephFS 的元数据节点仍是这个思路 |
| 2 | 「chunk 越大越好」 | 大 chunk 省元数据但带来**热点与迁移成本**；64MB 是 2003 年针对当时磁盘/网络的取值，不是物理常数 |
| 3 | 「GFS 保证强一致」 | GFS 明确区分 defined / undefined-but-consistent；并发追加是「至少一次」语义，**重复记录要上层处理** |
| 4 | 「追加写只是优化」 | 它是 GFS 一致性模型能成立的前提；把 GFS 当随机写文件用会立刻暴露（FAST 2014 的 HBase 案例研究） |
| 5 | 「Delete 就是删除」 | GFS 是**惰性回收**（重命名 + 心跳时批量删）；Haystack 删除只是打标记；对象存储同理（版本 + 生命周期规则） |
| 6 | 「TFS 和 Haystack 是两种不同问题的系统」 | 都是**海量小文件、读多写少**；解法差异在「大文件装小文件」vs「扁平卷 + 内存索引」 |
| 7 | 🔧 本章默认「自建 DFS」是唯一形态 | 2026 年默认答案是**云对象存储**（S3/OSS/COS）；GFS/HDFS 的知识要翻译成「元数据服务 + 对象存储」的等价问题 |
| 8 | 🔧 本章关于对象存储一致性的假设已过期 | 主流对象存储已提供**强一致（read-after-write）**；「对象存储只能最终一致」是 2013 年的旧认知 |
| 9 | 🔧 本章没有湖仓表格式这一层 | Iceberg/Delta/Hudi 在对象存储上提供表语义与 ACID，是 2013 年不存在的新层，也是本章内容的直接延伸 |
| 10 | 🔧 本章没有「存算分离」视角 | 现代架构把「文件系统性能」拆成对象存储带宽 + 本地缓存命中率，调优方法论与本章完全不同 |
