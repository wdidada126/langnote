# 04 · 分片与容量规划

> 章题 ⚠️ 推定（重构依据：✅ 官方导读句「Automatically shard your NoSQL databases based on SLA」+「Work closely with AWS services … collaborate efficiently」的容量侧切面，见 [00-总览与阅读地图.md](00-总览与阅读地图.md) §2/§6）。三态：✅ / ⚠️ / 🔧（**非 DynamoDB 行为**）。

## 1. 章定位：把 SLA 翻译成容量数字

2014 年的 DynamoDB 没有按需计费：**预留读写吞吐量（RCU/WCU）是唯一容量语言** ⚠️，「基于 SLA 自动分片」的实际含义=
- 用分区键把逻辑表切成物理分区 ⚠️；
- 用吞吐量预留换 SLA 承诺 ⚠️；
- 服务端按负载自动拆分/合并分区，用户只对配额负责 ⚠️。

这是全书最「时代错位」的一章：2018 年后 On-demand 承接了大半叙事 ✅（how-it-works.working-with-dynamodb-on-demand.html，台账 §7）。

## 2. 容量单位与换算（概念面 ⚠️，现状口径 ✅）

| 概念 | 定义 | 换算记忆点 |
|---|---|---|
| 读容量单位 RCU | 强一致读 1/秒×4KB 的倍数 ⚠️ | 最终一致读半价 ✅ |
| 写容量单位 WCU | 写 1/秒×1KB ⚠️ | batch 仍按项计费 ⚠️ |
| 突发桶 | 表预留量的 300 秒缓冲 ⚠️ | 长期高峰必须抬预留 ⚠️ |
| 自动分裂 | 流量增长→分区数增加 | 单分区吞吐有天花板 ⚠️ |
| 分区键=分片键 | 相同键落同分区 | 400KB 项+键基数共同决定分布 ⚠️ |

- 官方页 ✅：Introduction.html（RCU/WCU 现行定义、按需口径）、WorkingWithTables.html（表/容量操作）。

## 3. SLA → 键设计的推导链（本书方法论 ⚠️）

1. 估算 QPS 峰谷（读:写比）。
2. 平均项大小 → 单项消耗单位数。
3. 单位总量 ÷ 分区能力上限 = 需要的**最小分区数**。
4. 反推分区键基数下限 + 均匀性要求。
5. 热点预案：bucketing 加盐 / 缓存层 / 写合并 ⚠️。
6. 索引容量并入总盘（GSI 独立配额，→ [03-索引体系GSI与LSI.md](03-索引体系GSI与LSI.md)）。

这条链是 2014「容量驱动的键设计」原型；今天 On-demand 把 2–3 步变成「事后账单优化」问题 ✅，但 4–6 步（基数/均匀性/热点）仍是硬约束 ⚠️。

## 4. 吞吐治理工具箱（2014 面 ⚠️ → 2026 面 ✅）

| 手段 | 2014 | 2026 |
|---|---|---|
| 手动调预留 | 控制台/CLI update-table ⚠️ | 仍可用 ✅ |
| 定时伸缩 | 自写脚本 ⚠️ | Application Auto Scaling ✅(文档线) |
| 计费模式 | 仅预留 ⚠️ | 预留/On-demand 双模+容量模式切换 ✅ |
| 读放大治理 | 投影+最终一致读 ⚠️ | 同左+DAX 缓存 ⚠️ |
| 突发吸收 | 300 秒桶 ⚠️ | 按需无桶概念 ✅/⚠️ |

## 5. 🔧 本机类比实验（**非 DynamoDB 行为**）

| 组 | 实验与真实输出 | 类比点 |
|---|---|---|
| D3 | DuckDB 批插 200,000 行耗时 **0.099s** | 「批量>逐行」的形状 |
| D4 | 同表单行循环插 2,000 行耗时 **1.989s**（单行均摊≈1ms，比批插慢 4 个数量级/行） | 单位消耗/往返成本可视化 |
| T7 | 约束冲突→ROLLBACK 后 0 行 | 容量未满但语义失败也要回滚：预留≠保证 |
| D6 | `BETWEEN 's2' AND 's6'` 键范围 11 行 | 分区内数据布局影响读取量 |

诚实边界：本机实验只演示**吞吐形状**（批 vs 行、键范围 vs 全扫）；DynamoDB 的配额、突发桶、自动分裂、按分区限流在本机**无一可复现**——全部 ⚠️ 转述，禁以类比冒充服务行为。

## 6. 反模式清单（本章收尾 ⚠️）

- 时间戳做分区键：单调键→写全落尾分区 ⚠️。
- 低基数键（城市/状态）：热点常驻 ⚠️。
- 大项+ALL 投影索引：写成本立方级放大 ⚠️。
- 用「表级配额」思考：限流实际发生在分区/键粒度 ⚠️。
- On-demand 后放弃容量审查：按请求计费让坏设计「贵得静悄悄」⚠️（2026 补充）。

## 7. 容量自查清单（12 问 ⚠️+✅）

1. 峰值 QPS 是均值几倍？突发桶吃不吃得下 ⚠️？
2. 平均项大小与 RCU/WCU 换算复核过吗 ⚠️→✅？
3. 强一致读是否真的必需（否则半价换掉）✅？
4. 分区键基数 ≥ 需求分区数×冗余度 ⚠️→✅？
5. 键分布偏度（P99 分区流量）估过吗 ⚠️？
6. 写路径上有几个 ALL 投影索引 ⚠️→✅？
7. BatchWrite 的 Unprocessed 重试有预算上限吗 ⚠️→✅？
8. 容量告警接了自动化（伸缩/降载/熔断）吗 ⚠️？
9. 有无时间序列写导致尾分区热点 ⚠️？
10. 回填/导入任务是否错峰或走原生导入 ✅（S3DataImport.html）？
11. 表拆分时在线切流预案存在吗 ⚠️？
12. On-demand 切换的回退成本算过吗 ⚠️→✅？

## 8. 走查示例：读多写少信息流（演示域自拟 ⚠️；数字为本目录推演，非原书例题）

设：100 万活跃用户，峰值 2000 QPS 读（平均项 10KB）、200 QPS 写（平均项 2KB），GSI 视图 1 个（ALL 投影）。

1. 单项读成本：10KB ÷ 4KB（强一致口径）= 2.5 → 向上取整 3 RCU；最终一致减半口径 ⚠️→✅。
2. 读总需求：2000 × 3 = 6000 RCU。
3. 写总需求：2KB ≤ 1KB 基数？否 → 2 WCU/项 ⇒ 200 × 2 = 400 WCU。
4. GSI 写放大：ALL 投影 ⇒ 同量再 400 WCU 级消耗 ⚠️→✅。
5. 投影瘦身：改 INCLUDE 两列 ⇒ 写侧消耗显著回落 ⚠️。
6. 分区下限：若单分区能力按当时量级 ⚠️，6000 RCU ⇒ 至少若干十级分区 ⇒ **键基数下限=百级且需均匀** ⚠️。
7. 键形校验：`userId` 高基数均匀 ✅ 合格；若改 `country` 低基数 ⇒ 分裂失效 ⚠️。
8. 时间戳类单调键 ⇒ 写全落尾分区，book 时代标准解=日期反转+桶前缀 ⚠️。
9. 突发：大促 3 倍 ⇒ 预留抬升或错峰 ⚠️；2018 后=切 On-demand 吸收 ⚠️→✅。
10. 复盘：容量数字最终都回指**键设计+投影**两个自由度——04 章与 01/03 章闭环。

## 核心概念速览（中英对照）

| 中文 | 英文 | 一句话 |
|---|---|---|
| 预留读写吞吐量 | provisioned throughput（RCU/WCU） | 2014 唯一容量语言 ⚠️ |
| 按需容量 | on-demand capacity | 2018 起按请求计费 ✅ |
| 自动分片 | automatic sharding | 分区随负载增删 ⚠️ |
| 分区键 | partition key | 逻辑键同时是物理分片路由 ⚠️ |
| 突发容量 | burst capacity | 预留量的短时缓冲 ⚠️ |
| 限流 | throttling | 超配额返回 400/ProvisionThroughputExceededException ⚠️ |
| 键基数 | key cardinality | 决定分区数下限 ⚠️ |
| 加盐 | salting / bucketing | 热点键前缀分桶 ⚠️ |
| 最终一致读 | eventually consistent read | RCU 减半的读语义 ⚠️ |
| 容量模式切换 | capacity mode switch | 预留⇄按需互转 ✅(on-demand URL) |
