# 第6章 数据库

> **一句话**：第 6 章是全计算机功底部分最重的一章。**读懂 redo log 与 ARIES，你就读懂了整个"日志即事实"的世界观**——消息队列的持久化、K8s 的 etcd、分布式事务的补偿，都是同一套思想的变体。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 6.1 范式与反范式 | 范式约束冗余、反范式换查询性能 | 权衡的判据是**读写的比例与一致性要求**，不是"哪个更高级" |
| 6.2.1 为什么要分 | 单库连接数、单表数据量、单磁盘 IOPS 上限 | 分表的三个硬约束：连接数、索引深度、I/O 能力 |
| 6.2.2 分布式 ID | UUID / 数据库号段 / Snowflake 及其变体 | 号段与 Snowflake 是主流；**"全局唯一"不等于"趋势递增"** |
| 6.2.3 拆分维度的选择 | 按用户维度 vs 按商品/时间维度 | 选错拆分维度会让后续所有跨维度查询都变成难题 |
| 6.2.4 Join 查询问题 | 分库后无法本地 JOIN、跨库分页与排序 | 只能在应用层拼装或用**冗余宽表 / 异步宽表** |
| 6.2.5 分布式事务 | 跨库事务的代价与几条出路 | 分库后强一致通常不可接受，答案几乎总是**最终一致 + 补偿** |
| 6.3 B+树 | 逻辑结构、物理结构、非主键索引（回表） | B+树高扇出、叶子链表，适合磁盘；**层数 ≈ log(扇出)**，3~4 层即可存亿级行 |
| 6.4 事务与锁 | 四个隔离级别、悲观锁乐观锁、死锁检测 | InnoDB 的 RR 因为有 next-key lock 而无幻读，比标准定义更强 |
| 6.5 Redo Log | WAL、physiological logging、double write、LSN、ARIES | **先写日志后写数据**；崩溃恢复靠"重放 + 回滚未决事务" |
| 6.6 Undo Log | MVCC、版本链、undo 与 redo 的关系 |  undo 不是"回滚用的日志"那么简单，**它是版本存储的载体** |
| 6.7 Binlog 与主从复制 | 与 redo 的差异、内部 XA、三种复制方式、并行复制 | 主从一致性靠**内部 XA**保证 binlog 与 redo 不丢不重 |

## 核心精讲

> 以下为**教学示意，不参与编译、不参与任何构建**，仅用于说明机制。

**示意 1：WAL 与 LSN 的关系（一条更新在数据库里的旅程）**

```text
  1) 客户端发来 UPDATE t SET x=9 WHERE id=1
        │
  2) 事务写 undo（把旧值记下来，用于回滚/MVCC）
        │
  3) 事务写 redo（physiological log：改哪个页、页内什么偏移、新值是多少）
        │        ※ 顺序：先 undo 后 redo（同一个事务内）
        v
  4) InnoDB buffer pool 里把页改成新值（脏页）→ 后台异步刷盘
        │        ※ 此时磁盘上还是旧值，但日志已经落盘
        v
  5) 事务提交：把 redo log 从 log buffer 刷盘（fsync）
        │        ※ "提交"的语义 = 日志落盘，而不是数据落盘
        v
  6) 之后某时刻脏页才真正写进 .ibd 文件

  崩溃恢复（ARIES）时：
        从最后一个 checkpoint 开始，向前重放所有 redo（重放 = 把页改回当时的样子）
        → 遇到未提交事务的 redo，用 undo 回滚（回滚也是靠日志完成）
```

> 这张图解释了一个常被误解的事实：**数据文件的"正确"是由日志重建出来的，不是本来就有的**。所以"重建 redo log 比备份数据文件更快"是 InnoDB 崩溃恢复快的根本原因。

**示意 2：Physiological Logging 到底是什么**

```text
纯物理日志：记录"字节怎么变的"         → 恢复最安全，但日志量大、跨引擎不可共享
纯逻辑日志：记录"update t set x=9 …"  → 日志小，但恢复要重放整条 SQL，慢且不确定

physiological（物理-逻辑）日志： 【页号 + 页内偏移】+【逻辑上的新值】
  ⇒ 定位精确到页（重放时不必扫描全库），内容又是逻辑的（压缩率高、跨版本可读）
  ⇒ InnoDB / PostgreSQL / Oracle 全都是这一类，这是"折中的最优解"
```

**示意 3：Double Write（解决"半页写"）**

```text
  场景：一个 redo 条目对应 16KB 的页，刷盘时只写了 8KB 就断电
        → 磁盘上出现一个"半新半旧"的页，重放 redo 会把它改得更乱，无法恢复

  解法：
    1) 脏页刷盘前，先把页**连续的**写到 share 表空间里的 doublewrite buffer（一次大块写）
    2) 再把这些页拷到各自的 .ibd 位置
    3) 崩溃恢复时：如果 .ibd 里的页校验失败，从 doublewrite buffer 里找回原始副本，重放 redo
```

> 现代说明（🔧）：SSD 普及与 4K 物理扇区对齐之后，半页写概率下降，但 **InnoDB 8.0 之前仍默认开启 doublewrite**；同时 PostgreSQL 用的是另一套机制（full-page writes，只有在 checkpoint 之后的第一个修改才写整页）。

**示意 4：Undo Log 不只是"回滚日志"**

```text
  ┌── 事务 T1：UPDATE t SET name='B' WHERE id=1（原 name='A'）──┐
  │                                                              │
  │  undo 记录：(id=1, name='A', trx_id=81, roll_pointer=NULL)   │
  │                     │                                        │
  │                     └─> 形成**版本链**（通过 roll_pointer 串联）│
  └────────────────────────────────────────────────────────────────┘
         ▲                              ▲
         │ 回滚时：顺着链把 'A' 写回去      │ 读时：ReadView 判断该看哪个版本
         │                              │ → MVCC 的**全部**读一致性都靠这条链
         │                              v
         │                     SELECT 不需要加锁，因为它只是"挑一个历史版本"
```

**示意 5：内部 XA —— binlog 与 redo log 的一致性问题**

```text
  主线程写： ① 改内存页 + 写 redo(buffer)  →  ② 写 binlog  →  ③ fsync binlog →  ④ fsync redo

  失败组合（历史上有名的 bug 类问题）：
    ①②完成、②③之间的 binlog 已落盘而 redo 未 fsync  → 主库崩溃，slave 复制了这条 binlog，
       但主库数据没了 → **主备不一致**
  解法（两阶段 + 事务ID 对齐，即内部 XA）：
    提交时先做"准备"阶段：把 redo 写盘并打上 prepare 标记
    再写 binlog 并 fsync
    最后做"提交"阶段：redo 打上 commit 标记
  崩溃恢复时：prepare 且 binlog 完整的 → 提交；prepare 但 binlog 不全 → 回滚
```

**示意 6：并行复制的冲突判定（为什么不同库可以并行）**

```text
  slave 上：同一个 schema/库里，只要两个事务**操作的是不同行**，就可以并行回放
  判定依据（MySQL 5.7+ 的 WRITESET）：用"受影响行的哈希集合"判断冲突
        trx A 改 row(5,9)   trx B 改 row(10,20)  → 无交集 → 可并行
        trx A 改 row(5,9)   trx C 改 row(9,30)   → 有交集 → 串行
```

## 版本演进

| 版本 / 时间 | 与本章相关的变化 |
| --- | --- |
| 2019（原书基线） | 原书基线：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` 是"最强"默认；分库分表是主流扩容手段 |
| 2018 | **MySQL 8.0 GA**：undo 表空间可独立、默认字符集 utf8mb4、InnoDB DDL 原子化、redo log 不可覆盖式复用优化 |
| 2018 | **MySQL 8.0 引入 `innodb_redo_log_archive`** 与 improved redo 归档；MVCC 读视图实现改为更轻量 |
| 2018 | **MySQL 8.0 默认使用 "Lossy" 死锁检测与 `innodb_deadlock_detect` 可关闭选项**，高并发下可换取吞吐（代价是等待超时） |
| 2021 | **MySQL 8.0.23 引入 instant ADD COLUMN**（仅改元数据），大表加列不再需要重建表 |
| 2019–2022 | **PostgreSQL 的 redo/MVCC 演进**：PG 13 引入增量备份与逻辑解码改进；PG 15（2022）加入 `pg_stat_io`、更强的并行与 IO_URING 选项 |

| 2020–2024 | **HTAP 分化**：TiDB 的列存副本（TiFlash）、ClickHouse 与 Doris 的湖仓路线、Vitess 在 MySQL 侧做存算分离 |
| 2024–2026 | **存算分离与 Serverless 数据库**：日志与数据分离成为共识；Kafka/Pulsar 之外，**事务消息队列（RocketMQ 5.0 的事务消息）** 成为分布式事务的另一条落地路径 |

## 近年研究与工业界开源实践（2015–2026）

- **趋势**：2015 年之后数据库领域的主线变化有三条：① **"分库分表"让位于"先选对引擎"**（NewSQL 把分片与分布式事务做到透明）；② **存算分离成为共识**（Aurora、PolarDB、TiDB 分离架构）；③ **HTAP 与实时分析fusion**（列存副本、湖仓一体）让"OLTP 与 OLAP 分离到两套系统"的旧范式松动。
- **分布式 ID（🔧 本章必须补）**：
  - **数据库号段（segment/idalloc）**：一次取 1000 个 ID，用完后下次再取；简单可靠，是"分布式 ID"最容易被忘掉的解法。
  - **Snowflake 及其变体**：41 位时间戳 + 10 位机器 ID + 12 位序列号；**时钟回拨会破坏唯一性**，因此工业界都加了回拨保护（如改为等待或抛错）。
  - **百度 UidGenerator / 美团 Leaf（号段 + Snowflake 双模式）**：前者把 64 位时间戳进一步压缩以适配业务量，后者是国内最常被落地的开源方案。
- **分布式事务（🔧 本章必须补）**：
  - **Seata（阿里 / 现 Apache 顶级项目）**：AT（自动补偿，基于 undo log 反向 SQL）、TCC、Saga、XA 四模式的开源主力实现。
  - **Saga**：分布式事务的补偿型方案，2024 年前后因 **Dapr 的 Saga 工作流**与 **RocketMQ/Temporal/Cadence 的编排集成**重新活跃。
  - **TCC 现状**：被大量金融与库存场景使用，但**侵入性强、每个接口要写 try/confirm/cancel**，在微服务规模下维护成本高，因此近年有"用 Saga + 幂等替代 TCC"的趋势。
  - **NewSQL 的冲击**：`pingcap/tidb`（**40588★**）把分布式事务做到透明，让"分库分表 + 分布式 ID + 分布式事务"这一整套 2019 年的标准答案变成了**可选项而非必选项**。
- **典型仓库（star 为 2026-09-25 用 `gh api` 实测）**：
  - `mysql/mysql-server`（**12438★**）：InnoDB 的 `log0log.cc`、`trx0roll.cc`、`ib0btree.cc` 是本章全部结论的一手出处。
  - `postgres/postgres`（**22190★**）：MVCC 与 SSI 的另一个实现现场；PG 的 undo 与 InnoDB 思路不同（多版本存堆内 + HOT 更新）。
  - `pingcap/tidb`（**40588★**）：Percolator 的开源实现，事务与存储分离。
  - `apache/shardingsphere`（**20804★**）：分库分表 + 读写分离 + 分布式事务的中间件事实标准。
  - `seata/seata`（**26013★**）：分布式事务的开源主力。
  - `vitessio/vitess`（**21355★**）：YouTube 起源的 MySQL 集群编排系统，是"分库分表"这条路线的成熟工程答案。
  - `facebook/rocksdb`（**32131★**）：LSM 的工业实现，与 B+ 树对照阅读。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "undo log 是为了回滚的" | 回滚只是用途之一；**MVCC 的读一致性完全建立在 undo 版本链上**（原书 6.6.2 已点出，但 6.6.1/6.6.3 容易被跳读错过） |
| 2 | "redo 是物理日志" | 实际是 **physiological logging**（页 + 偏移 + 逻辑值），这是 6.5.3 的核心 |
| 3 | "提交 = 数据落盘" | 提交 = **redo 日志落盘**；数据页异步刷盘，崩溃恢复时用日志重建 |
| 4 | "RR 隔离级别会有幻读" | **InnoDB 的 RR 因为有 next-key lock 而无幻读**；SQL 标准定义的 RR 有，这是两者的关键差异 |
| 5 | "乐观锁不需要版本号" | CAS 式"更新时比较旧值"就是乐观锁；但如果业务判定依赖"读到的状态"，仍需显式版本号 |
| 6 | "并行复制一定更快" | 取决于冲突度；单库热点行场景下并行复制可能比单线程更慢（线程调度开销 + 冲突回退） |
| 7 | 🔧 **本书未覆盖：分布式 ID 的现代形态** | 原书 6.2.2 只点出"需要一个分布式 ID 服务"。2026 年的答案是**号段模式 / Snowflake 变体（美团 Leaf、百度 UidGenerator）** 双主流；必须补的是 **时钟回拨问题**——这是 Snowflake 类算法在生产上最大的坑 |
| 8 | 🔧 **本书未覆盖：分布式事务的真实代价与取舍** | 原书 6.2.5 只列了"问题"。今天应补：**Seata 的 AT 模式基于 undo log 反向补偿，对跨异构数据源无效**；TCC 侵入性强；Saga 需要幂等与补偿链路；NewSQL 把成本转移到引擎里 |
| 9 | 🔧 **本书未覆盖：NewSQL / HTAP** | 本章的分库分表是 2019 年的主流答案。今天应补：`pingcap/tidb` 的 Percolator 与 Raft 副本、`cockroachdb` 的 HLC 串行化快照、Spanner 的 TrueTime、Aurora 的存算分离、TiFlash/Doris 的 HTAP 路线 |
| 10 | 🔧 **本书未覆盖：MySQL 8.0 与 PostgreSQL 的演进** | 例如 MySQL 8.0 的 instant ADD COLUMN（大表加列不再重建）、undo 表空间独立化、PG 15 的 `pg_stat_io` 与 IO_URING 支持；这些都是原书成书后发生的重要变化 |
| 11 | 🔧 **本书未覆盖：LSM 树与 B+ 树的取舍** | 本章只讲 B+ 树。2026 年的现实是：写多读少的在线场景大量使用 **RocksDB/LSM**，而 LSM 的写放大与读放大问题正是与 B+ 树对比的全部意义 |
| 12 | 🔧 **本书未覆盖：长事务对 purge 的影响** | undo 版本链依赖 purge 线程回收；**一个开了大事务的会话会让 undo 无限膨胀**（这是线上最常见的故障之一），原书完全没有提到这条运维常识 |
