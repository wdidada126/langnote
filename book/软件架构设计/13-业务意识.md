# 第 13 章 业务意识：从需求到业务架构

> 原书第 13 章「业务意识」（P196–201），对应 13.1「产品经理 vs. 需求分析师」、13.2「什么叫作一个'业务'」、13.3「'业务架构'的双重含义」、13.4「'业务架构'与'技术架构'的区分」。
> 这是全书第 4 部分（业务架构之道）的开篇，也是第 14、15 章的方法论前提：**不懂业务，任何架构都是技术炫技。**

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 13.1 产品经理 vs. 需求分析师 | 目标导向 vs 需求导向；谁对什么负责 | 两者是**责任不同**而非**等级不同**；架构师要同时具备两种视角 |
| 13.2 什么叫作一个"业务" | 业务 = 一组有输入、有规则、有输出的闭环活动 | 把业务拆到「业务能力」这一层，就可以画成图、分配给人、分配给系统 |
| 13.3 "业务架构"的双重含义 | ① 方法论/思考方式 ② 产物/文档 | 说"业务架构"时必须先问一句：**你说的是动词还是名词** |
| 13.4 "业务架构"与"技术架构"的区分 | 关注点、产物、受众、时间尺度不同 | 分工的边界不在"技术 vs 业务"，而在**决策权与责任边界** |

> 一个具体的对话样本，帮助体会"双重含义"造成的误会：
>
> - A："业务架构这块你来出一份。"
> - B："好，我明天交付业务架构。"
> - A："我要的是能指导开发的那份。"
> - B："我给的就是业务架构图啊。"
>
> 两人可能都没错：A 要的是名词（产出物），B 做的是动词（方法论工作）。**消除误会的方式不是解释，而是命名**：以后说"业务架构文档"（名词）还是"业务架构工作坊"（动词）。

## 核心精讲

### 13.1 产品经理 vs. 需求分析师

原书的划分很有代表性：

| 维度 | 产品经理 | 需求分析师 |
| --- | --- | --- |
| 关注 | **目标（Goal）**：为什么做、值不值得、成功长什么样 | **需求（Requirement）**：把目标翻译成可验证的陈述 |
| 时间尺度 | 季度到年度 | 一次迭代 |
| 输出 | 产品规划、路线图、验收标准 | 需求文档、用例、原型、验收条件 |
| 失败的样子 | "做了一堆没人用的功能" | "写得很详细，但要求本身是错的" |

关键在于：**这两种失败都发生在架构师身上**。所以原书说架构师应该两种角色都沾一点，这直接影响后面 16 章的「影响力塑造」—— 你能不能影响产品经理，决定了你能否在需求阶段就把架构约束塞进去。

可操作的推论（教学示意，非规范）：

- 需求进入开发前，架构师要问三个问题：**这个需求改变了哪条业务规则？它影响哪个领域对象？它的失败形态是什么？** 回答不上来，说明需求还没"落地"；
- 反过来，架构师也要能写出**对用户负责的**材料，而不只是技术方案。

一段可复用的评审清单（教学示意，非规范）：

```
[] 这个需求改了哪条业务规则？（找不到 → 需求描述可能不是"变更"）
[] 它影响哪个领域对象？该对象上还有哪些不变式可能受影响？
[] 失败形态是什么？异常态的数据由谁清理（对账/补偿/人工）？
[] 它的价值如何度量？上线后用什么指标证明它值得做？
[] 它是否会引入分布式事务？（引入则回到第 10 章的选型顺序）
[] 它是否改变了"业务能力"的边界？（变了则业务架构图要同步更新）
```

🔧 2026 年的补充：这三者（产品/需求/架构）的角色在**产品工程（Product Engineering）**语境下进一步融合，出现了 Technical Product Manager、架构师兼产品负责人（Head of Engineering 兼 PM）等形态；但**责任边界的划分逻辑**没有变，只是被压缩到更小团队内。

### 13.2 什么叫作一个"业务"

原书对这个问题的回答偏"工程视角"：业务不是"公司"，而是一组**可命名、可测量、可复用**的能力与活动。把它抽象出来，就得到了架构设计的输入：

```
业务 = 输入（数据/请求） --[规则/流程]--> 处理 --[规则/流程]--> 输出（结果/承诺）
                 |                                 |
                业务规则（不变式）                业务能力（可复用资产）
```

拆解的层次（自上而下）：

1. **价值（Value）**：客户为什么付钱 / 用户为什么留下来；
2. **业务能力（Business Capability）**：组织"会做什么"，与技术无关（如"资金结算能力"、"履约调度能力"）；
3. **业务流程（Process）**：能力在特定场景下的编排（如"下单履约"）；
4. **业务对象 / 领域模型**：能力操作的数据及其不变式；
5. **业务规则（Rule）**：不变式的可执行表达（如"优惠券不能与活动的互斥"）。

> 这一层的拆分正好是 14 章「边界思维」与 15 章「限界上下文」的雏形：**先分能力，再分流程，最后才分系统**。

教学示意（伪码，非可运行，仅表达结构）：

```
// 业务能力地图（示意）
order_service = {
   capabilities: [下单, 取消, 支付, 履约, 退款],
   domain_objects: [Order, OrderItem, Payment, Shipment],
   invariants: ["已取消订单不能支付", "退款金额 <= 支付金额"],
   process: [创建订单 -> 锁定库存 -> 支付 -> 发货]
}
```

### 13.3 "业务架构"的双重含义

这是原书最容易被读者漏掉、却最实用的一段。原文意思是：**"业务架构"这个词同时指两样东西**：

| 含义 | 性质 | 典型产物 |
| --- | --- | --- |
| ① 业务架构**工作**（动词） | 是一套方法论与思考方式：站在业务视角去识别能力、流程、规则、领域模型 | 业务能力地图、领域模型、上下文映射 |
| ② 业务架构**结果**（名词） | 是设计产出物：描述业务域的结构与关系 | 《业务架构说明书》、限界上下文图、领域模型 |

后果：**沟通时 90% 的纠纷来自两个人说的不是同一个含义**。所以原书建议：讨论时明确说清"我们在做业务架构这一块工作"还是"我们看的是业务架构那份产出"。

### 13.4 "业务架构"与"技术架构"的区分

| 维度 | 业务架构 | 技术架构 |
| --- | --- | --- |
| 回答的问题 | 业务是什么、规则怎么变、能力怎么复用 | 系统怎么分、数据怎么存、流量怎么走 |
| 核心产物 | 业务能力地图、领域模型、业务规则、流程 | 系统分层/服务划分、存储选型、部署拓扑、技术选型 |
| 受众 | 业务方、产品、管理层 | 开发、测试、SRE |
| 稳定性 | **慢变**（业务能力 Stable，流程可变） | 相对易变（技术栈更替频繁） |
| 判断标准 | 是否满足业务目标、是否可复用 | 是否可维护、可扩展、可用 |

重点在最后一行：**业务架构的稳定性远好于技术架构**。这也是为什么 15 章讲「领域模型」值得投入 —— 它是少数穿过技术浪潮的东西。

### 🔧 一个易被忽略的对应关系

| 业务架构概念 | 技术架构对应物 |
| --- | --- |
| 业务能力 | 服务 / 模块 / 限界上下文 |
| 业务规则（不变式） | 领域模型内的聚合一致性 / 校验 |
| 业务流程 | 系统流程、编排（orchestration） |
| 业务对象 | 实体 / 值对象 / 数据表 |
| 业务事件 | 领域事件 / 消息 |

这张表是 15 章「业务流程 ≠ 系统流程」的伏笔，也是 14 章「正交分解」的落点。

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1968 | Conway 提出「系统设计的结构与组织结构同构」，后经 Raymond 在《大教堂与集市》中推广为"康威定律" |
| 1990s | 企业架构（Zachman Framework、TOGAF、ArchiMate）把"业务架构"确立为**企业架构中的一个正式层**，与数据/应用/技术架构并列 |
| 1998 | Kotonya & Sommerville《Requirements Engineering》确立需求工程的学科定位 |
| 2003 | Evans《Domain-Driven Design》提出领域与限界上下文，为"业务架构"提供模型语言 |
| 2009–2014 | 用户故事地图（Patton）、Impact Mapping（Adzic）、Lean UX（Gothelf）等**价值导向**的需求方法兴起 |
| 2013 起 | 事件风暴（Event Storming，Brandolini）：把业务理解变成一次**可协作的建模工作坊** |
| 2019 | Team Topologies 用"流式/赋能/平台/复杂子系统"四象限重塑康威定律的现代版 |
| 2021–2023 | **中台退潮**：大量中台项目收缩，社区重新强调"回到业务价值"与"单体优先" |
| 2023–2026 | **产品工程一体化**：产品、设计、研发在同一交付流内工作，"业务架构"从交付物回归为**持续的沟通产物** |

## 近年研究与工业界开源实践（2015–2026）

- **DDD 的调整与回归**：2015 年后的 DDD 社区重心从"战术模式"（Aggregate/Repository/Service）转向**战略设计**（限界上下文、上下文映射、统一语言），事件风暴成为标准仪式。`ddd-crew` 等社区组织持续发布实施手册；中文社区亦大量引入。
- **"中台退潮"与"回到单体"**：2021–2024 年间，大量企业缩减中台投入，Martin Fowler 等人重新强调 **"Monolith First"** 与"分布式系统的复杂度税"。这与原书 2019 年的语境相比是一次明显的反旋，也再次印证 13.4 的结论——**业务架构要稳定，技术架构要可退**。
- **事件驱动与领域事件成为主流**：`EventStore/EventStore`（≈5.9k★，事件溯源数据库）、`apache/kafka`（≈33.8k★）、`apache/pulsar`（≈15.3k★）把"业务事件"从文档里的方框变成了可落地的产物；`rabbitmq/rabbitmq-server`（≈13.9k★）在金融侧依旧强势。
- **架构决策记录（ADR）**：`npryce/adr-tools`（≈5.7k★）与 `thomvaill/log4brains`（≈1.6k★）让"业务/技术决策"从口头结论变成**可追溯的一页文档**（详见 15 章）。
- **企业架构标准的现代化**：ISO/IEC/IEEE 15288 与 IEEE 2418 系列把三层需求（业务需求 / 用户需求 / 系统需求）固化为标准术语，恰好对应本章 13.1 的角色划分 —— 想看规范原文可查 IEEE Xplore，此处不引用具体 ISBN。
- **产品工程一体化**：以 `temporalio/temporal`（≈23.3k★）为代表的"工作流即代码"把流程定义权部分交还给业务语义（工作流是一个可执行的业务描述），与本章 13.2 的业务拆解形成呼应。

## 常见误区与本书需修正之处

| # | 误区 | 修正（含 2026 视角） |
| --- | --- | --- |
| 1 | "需求文档写完就完了" | 需求要能回答"失败形态"，否则架构无法设计；验收条件应包含异常与降级路径 |
| 2 | 🔧 "业务架构 = 画一张架构图" | 业务架构的产物是可执行的：限界上下文、领域事件、不变式都要落到代码里；"只画图不落地"是 2019 年咨询式业务的遗留问题 |
| 3 | 🔧 本书对"产品经理 vs 需求分析师"的二元划分需要补充 | 2020 年后流行的是**角色融合**（Technical PM / Embedded PM / 双通道），但**责任边界**依然清晰；关键是避免三个角色同时缺位 |
| 4 | 🔧 本书未覆盖"中台退潮"这一反例 | 2019 年本书语境下"平台化/中台化"是主流正确方向；2023 年后的共识是：**先单体、后拆分；先内聚、后复用**，中台的价值在于收敛重复而非提前部门化 |
| 5 | 🔧 本书未覆盖"业务能力地图 vs 领域模型"的差距 | 前者是**组织视角**（易被政治化），后者是**模型视角**（可落地）。两者可以不一致，但要能解释差距的来源 |
| 6 | 🔧 本书未覆盖需求价值度量 | 从"故事点吞吐"转向 DORA 四指标与 DevEx 度量（见 17 章），产品侧也从投票式 Backlog 转向 Impact Mapping 式的目标拆解 |
| 7 | 🔧 未覆盖"合规与数据治理"作为业务约束 | GDPR、《个人信息保护法》 etc. 把"用户权利实现"（删除/导出/可携带）变成了**不可回避的业务能力**，这是 2019 年国内架构很少讨论的 |
