## 核心精讲

### 15.1 各式各样的方法论

原书这一节的态度是温和的怀疑论：方法论能被传播，往往是因为它**好用且好讲**；但把它当银弹是危险的。一个更实用的看法（教学示意，非规范）：

```
方法论 = 一组约束 + 一套词汇 + 一份决策清单
成熟度 ≈ 它能在多大程度上减少"重复踩坑"，而不是"减少思考"
```

判断"要不要上某个方法论"的三个问题：

1. 它解决的是**当前**这个项目真实存在的一个问题吗？
2. 团队里有几个人能正确执行它？（执行者数量决定它能落地多深）
3. 不执行它的代价，是否比学习它的代价更高？

> 🔧 2026 年补充一句：2020 年代的方法论争论（DDD 深水区 vs 三段式 CRUD、中台 vs 单体）从未产生"赢家"，只产生了**能被证伪的经验**。把方法论当约束集使用，就还是对的；当口号使用，就必然滑向"伪分层"。

### 15.2 为什么要"领域驱动"

原书的核心论证是：**技术架构的复杂度不是技术自己长出来的，而是业务复杂度在代码上的投影**。于是：

- 业务复杂 → 领域模型复杂 → 技术架构被迫复杂；
- 反过来，若先做技术架构（选框架、分库分表、上缓存），再去追业务，就会得到"CRUD 框架 + 一堆 if"式的系统。

这条论证推导出一个非常实用的结论：**架构设计的第一笔投入应该花在领域模型上**。

### 15.3 "业务流程" ≠ "系统流程"

这是本章最值得反复读的一节。举个典型例子（教学示意，非可运行）：

| | 业务流程（人怎么操作） | 系统流程（机器怎么流转） |
| --- | --- | --- |
| 时间 | 分钟到天（用户慢慢填、慢慢付款） | 毫秒到秒 |
| 中断 | 用户关页面、打电话、改主意 | 进程重启、网络断了 |
| 状态语义 | "待支付"可能持续一周 | 必须定义超时后的自动关单 |
| 顺序 | 人们不严格按流程执行 | 必须严格且可重放 |

结论：**业务流程是"期望路径"，系统流程是"所有路径的并集"**。设计系统流程时的做法：

1. 从流程反推状态机（状态 + 合法事件）；
2. 为每一种"业务上会发生的异常"补一条系统流程（超时、取消、回滚、部分成功）；
3. 把系统流程固化下来，作为测试的输入集 —— 这一步就是 14 章"建模"的验收。

### 15.4 为何很难设计一个好的领域模型

原书列出困难，我把它整理成四类可直接应对的障碍：

| 障碍 | 表现 | 对策 |
| --- | --- | --- |
| 语言缺失 | 需求文档、开发、代码里三套叫法 | 建**统一语言**，写进事件风暴工作坊 |
| 模型被技术分片 | 一个业务对象被拆到订单库、库存库、ES 里 | 先按业务画完整模型，再决定如何分片 |
| 变更被局部化 | "改一个小需求"却动五个服务 | 检查边界是否切在变更轴上（14.9 正交分解） |
| 领域知识在少数人脑中 | 只有一个人懂结算规则 | 把规则写成可执行的状态机/规则表，而不是口头知识 |

好模型的判据（可自检）：

```
[] 能用业务语言向非技术同事解释清楚
[] 每条业务不变式都能找到一个"归属于它"的聚合
[] 修改规则时不需要跨上下文改动数据模型
[] 模型能解释"为什么"，而不只是"是什么"
```

### 15.5 DDD 与微服务架构的"合"

原书的立场是"合"而非"分"：DDD 的**限界上下文**与微服务的**服务边界**应当重合。顺序很重要：

```
正确：识别限界上下文 → 确认业务能力边界 → 决定要不要拆服务
错误：先拆一堆服务 → 再想办法找边界 → 得到分布式单体
```

拆与不拆的判据：

| 拆的标志 | 不拆的标志 |
| --- | --- |
| 上下文间有稳定契约且频繁同时变更 | 上下文之间只是"通过数据库共享表" |
| 上下文由不同团队拥有 | 一个团队同时维护两个上下文的所有细节 |
| 需要独立的伸缩/隔离（某部分资源消耗差异巨大） | 所有部分的技术栈与容量需求一致 |

🔧 2026 年的修正性经验（重要）：**拆分是有成本的**（网络、分布式事务、可测试性）。2021–2024 年间大量组织缩减了微服务规模、退回模块化单体（modular monolith），因为"模块化单体"能以 1/5 的运维成本拿到 80% 的好处。**拆分的正确顺序是：先模块化，后分布式**。

### 15.6 DDD 与 CQRS（读写分离）

CQRS（Command Query Responsibility Segregation）的要点：

| | 写模型 | 读模型 |
| --- | --- | --- |
| 目标 | 保证不变式（领域模型） | 快速、灵活、可聚合 |
| 范式 | 领域模型 + 聚合根 | 扁平 DTO / 物化视图 / 报表结构 |
| 变更 | 命令 → 领域事件 | 事件 → 更新读模型 |
| 一致性 | 强一致（事务内） | 最终一致（秒级或更宽松） |

为什么和 DDD 契合：读的多样性天然不能用**一个**模型满足，而写的一致性只关心不变式。两者一结合就得到事件驱动的链路：

```
命令 → 聚合（校验不变式）→ 领域事件 → 投影（projection）→ 读模型
```

配合事件溯源（Event Sourcing）时，领域事件即事实上的"存储内容"，当前状态由事件重放得到（配合快照优化）。

🔧 2026 视角的重要提醒：**CQRS 的主流价值是"读模型与写模型解耦"，不是"读写库分离"**。很多人把 CQRS 简化成"主库写、从库读"，那是复制不是 CQRS；后者是 8 章"读写分离"的论域。

### 15.7–15.10 四个架构模式

#### 15.7 业务分层架构模式

要点：分层解决**依赖方向**，而不是"分几层"。落地形态（经典四层，教学示意，非可运行）：

```
接口层  ->  应用层（用例编排）  ->  领域层（不变式）  ->  基础设施层（存储/中间件）
```
- 领域层**不依赖**任何层（纯业务）；
- 应用层定义用例，是对外的用例边界；
- 基础设施层实现接口，靠依赖注入反向装配；
- 与前 14.1 的"真分层"判据完全一致 —— 这一节其实是 14.1 在 DDD 语境下的具体形态。

#### 15.8 管道—过滤器架构模式

适用特征：流程由**有序步骤**组成，每一步可独立复用、可插拔。

教学示意（伪码，非可运行）：

```
class RiskFilter extends PipelineStage<OrderContext> {
   Result handle(ctx) { ... return next(ctx); }
}
pipeline = [AuthFilter, InventoryFilter, RiskFilter, PriceFilter]
```

优点：可组合、易测试、易加规则；缺点：调试链路长、**进程内状态需要显式传递**，且步骤间顺序含义是硬编码的。典型适用：风控、计费、数据清洗、营销优惠试算。

#### 15.9 状态机架构模式

适用特征：业务对象有**状态 + 合法事件**。

教学示意（伪码，非可运行）：

```
transitions = {
  '待支付':  ['已支付', '已关闭'],
  '已支付':  ['已发货', '已退款'],
  '已发货':  ['已完成'],
  '已完成':  [],
}
def dispatch(order, event):       # 非法事件直接拒绝，不进存储
    if event not in transitions[order.state]: raise IllegalTransition
    apply(event)
```

价值：把隐式规则显式化，能生成状态流转图，也能直接映射成测试矩阵。原书把它单列一节的用意就在这里 —— **业务闭环最可靠的表达形式就是状态机**。

#### 15.10 业务切面 / 业务闭环架构模式

原书的提法："业务切面"指把一个业务切成若干**可独立复用的切面**（能力），"业务闭环"指这些切面围绕一个核心对象收口，形成有明确状态的闭环。

```
               ┌── 优惠券切面 ──┐
订单聚合 ──────│ 库存切面       │──────> 订单状态机（业务闭环）
               │ 支付切面       │
               └── 积分切面 ────┘
```
- 切面内部强一致（同一次事务）；
- 切面之间若跨数据源，则由第 10 章的柔性事务/领域事件串联；
- 闭环的可观测性靠状态机 + 事件日志，而不是靠日志 grep。

## 近年研究与工业界开源实践（2015–2026）

- **战略 DDD 定型**：限界上下文 + 上下文映射（合作/客户-供应商/分离）成为组织设计输入；DDD Crew 与事件风暴社区持续发布实施手册，`ddd-crew` 的"限界上下文设计"手册是典型代表。
- **事件溯源的落地样本**：`EventStore/EventStore`（≈5.9k★，事件流数据库）及 `get-eventstore/...` 生态；`temporalio/temporal`（≈23.3k★）以"工作流代码 + 重放"实现"可回溯、可补偿的业务闭环"，规避了手写状态机的很多坑。
- **事件驱动普及**：`apache/kafka`（≈33.8k★）、`apache/pulsar`（≈15.3k★）、`apache/rocketmq`（≈22.6k★）成为领域事件的标准载体；业务事件从"文档里的方框"变成"基础设施里的 topic"。
- **ADR 与可追溯决策**：`npryce/adr-tools`（≈5.7k★）、`thomvaill/log4brains`（≈1.6k★）让 15.1 所说"方法论的约束"沉淀为可 Review 的决策记录（见 14 章）。
- **架构文档的代码化**：`structurizr/java`（≈1.1k★）与 C4 模型让架构图随仓库演进，解决"图与代码不一致"的老问题。
- **"回到单体"的实证**：2021 年后多篇公开复盘（如各大厂中台收缩、微服务拆分后的成本复盘）表明：**模块化单体 + 清晰的模块边界**在多数业务下比微服务更经济；真实的拆分理由应当是"组织与伸缩"，不是"技术先进"。
- **大模型辅助**：2023 年后出现从需求/代码生成领域模型与 C4/PlantUML 图的工具链探索，但目前更稳妥的用法是**用 LLM 做草稿与一致性检查，由人做边界决策**。

## 常见误区与本书需修正之处

| # | 误区 | 修正（含 2026 视角） |
| --- | --- | --- |
| 1 | "DDD 就是一堆设计模式（聚合/仓储/领域服务）" | 那是**战术设计**；DDD 今天的主要价值是**战略设计**（限界上下文、统一语言），见 Evans & Capra 2017 |
| 2 | "CQRS 就是主从读写分离" | CQRS 的核心是**模型分离**（写模型保不变式、读模型保查询多样性），不是数据库复制 |
| 3 | "上 DDD 就必须上事件溯源" | 事件溯源带来回放、审计、时间旅行，也带来存储膨胀与查询复杂度；**不是必选项** |
| 4 | "先拆微服务，再用 DDD 找边界" | 顺序反了会得到分布式单体。正确顺序：模块化 → 明确边界 → 必要时才分布式 |
| 5 | 🔧 本书未覆盖"中台退潮与模块化单体回归" | 2023 年后的共识：拆分成本远高于收益，除非有真实的组织或伸缩动因。原书 2019 年对"平台化"的乐观需要事后修正 |
| 6 | 🔧 本书未覆盖 ADR 与架构决策的可追溯性 | 方法论落地后要留下**决策记录**（选项、后果、日期），否则半年后没人知道为什么这么设计 |
| 7 | 🔧 本书未覆盖"事件驱动取代部分编排"的成本 | 事件驱动（choreography）的优点是可伸缩，代价是可观测性极差；今天的主流是**编排式**（Temporal/Cadence 或 CMM 式编排器） |
| 8 | 🔧 本书未覆盖"大模型对建模的影响" | 生成图容易，**边界决策仍然是人责**；DCI/上下文映射这类概念在 LLM 时代更值钱，而非贬值 |
| 9 | 🔧 本书未覆盖聚合大小的实操争议 | 大聚合（强一致但并发差）与小聚合（并发好但要柔性事务）之间没有通用答案；Vernon 与后来的讨论都强调**按业务并发热点**决定 |
