# 第9章 高可用与稳定性

> **一句话**：第 9 章回答"系统怎么在出错时还能活"。前两节是**被动防御**（多副本、隔离、限流、熔断、降级），后两节是**主动控制**（灰度发布与回滚、监控与报警）。**没有监控的熔断，等于没做熔断**——这是本章最容易被漏掉的一半。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 9.1 多副本 | 数据/服务冗余；主从复制、半同步、多数派 | 多副本解决"机器坏了"，**不解决"代码错了"**——错误会同步复制到所有副本 |
| 9.2 隔离 | 线程池/连接池隔离、舱壁模式、资源配额 | 隔离的目的是**让一个慢下游不会拖垮整个进程** |
| 9.2 限流 | 单机限流、集群限流、令牌桶与漏桶、网关层限流 | 限流是"系统对上游说不"的权利；没有限流就没有过载保护 |
| 9.2 熔断 | 失败率阈值、快速失败、半开试探 | 熔断要**先错后快**；阈值与冷却时间必须可调，不能写死 |
| 9.2 降级 | 关功能、读缓存、简化流程、拒绝非核心 | 降级方案必须**预先定义**，不能临时想；最好用开关控制 |
| 9.3 灰度发布与回滚 | 按流量/用户/百分比灰度，一键回滚 | 回滚速度决定发布风险；**回滚是常态手段，不是失败标志** |
| 9.4 监控体系 | 指标（Metrics）、日志（Logging）、追踪（Tracing）三层 | 指标用于告警，日志用于归因，追踪用于跨节点串联 |
| 9.4 日志与报警 | 结构化日志、链路 ID、告警分级与降噪 | 报警的价值在**可执行**；一条没人处置的告警等于噪声 |

## 核心精讲

> 以下为**教学示意，不参与编译、不参与任何构建**，仅用于说明机制。

**示意 1：熔断状态机（三个状态与三种失败模式）**

```text
       ┌──────────── Closed（正常）─────────────┐
       │  正常转发；累计失败率                    │
       └───────────────┬─────────────────────────┘
                       │ 失败率 > 阈值（连续失败 N 次）
                       v
                 ┌──── Open（熔断）─────┐
                 │ 立即失败，不占资源     │  ← 这段时间里对下游零调用
                 │ 启动冷却计时器        │
                 └────────┬─────────────┘
                          │ 冷却结束，进入**半开**
                          v
                 ┌── Half-Open（半开）──┐
                 │ 放行少量探测请求      │
                 └───┬─────────────┬────┘
              成功→回到 Closed        失败→回到 Open（重新计时）
```

> 三个关键细节：**① 熔断期间要快速失败，而不是继续等待超时（等待超时会占满线程池）；② 半开状态必须真的试探；③ 冷却时间要可配置**。原书 9.2 讲了熔断，但没强调"熔断 ≠ 重试"——**两者叠加会造成重试风暴**。

**示意 2：重试风暴（熔断与重试的经典相互作用）**

```text
  场景：A → B → C，C 挂了，B 的调用方 A 有 3 次重试，B 对每个请求也重试 3 次
  ⇒ 上游 1 个请求放大为 3 × 3 × 3 = 27 个对 C 的请求
  ⇒ C 恢复后也会被这 27 倍流量立刻打挂（retry amplification / 雪崩式重试）

  解法清单：
    ① 只在**可重试错误**（超时/503/网络错）上重试，不在业务错误上重试
    ② 重试次数 ≤ 2，且带指数退避 + 抖动（避免重试同步化形成尖峰）
    ③ 链路上的重试必须**跨整条调用链只做一次**（用幂等键 + 上游已重试则下游不重试）
    ④ 熔断先行：下游已经熔断时，直接本地失败，不再重试
```

**示意 3：限流的层次与维度**

```text
  层次（由外到内，逐层收敛）：
    网关 / Ingress  ──>  接入层限流（按 IP、按 UA、按 API）
    框架 / RPC       ──>  单机限流（按 QPS、按并发数、按线程池占用）
    业务            ──>  按用户、按商户、按商品（防热点与刷子）
    依赖            ──>  对下游的调用速率（相当于"客户端侧限流"）

  维度：QPS（速率）/ 并发数（在途请求）/ 配额（日调用上限）
  算法：令牌桶（允许突发） / 漏桶（匀速） / 并发窗口（简单可靠）
```

**示意 4：多副本解决不了什么（原书 9.1 最容易误读的一点）**

```text
  多副本能解决：  机器宕机、磁盘坏、机房断电、进程崩溃
  多副本不能解决： ✗ 代码 bug（所有副本跑同样的错代码，切换后照样错）
                  ✗ 数据误删（删库命令会被同步复制到所有副本）
                  ✗ 流量过载（副本变多只是分摊，总量没变）
                  ✗ 依赖方的区域性故障
  ⇒ 所以**备份 + 回滚 + 演练**必须与多副本同样重要；一致的多副本是"双刃剑"
```

**示意 5：三层可观测性与一条请求的完整画像**

```text
  Metrics（指标）：  聚合后的数字，用于**告警与容量**
      http_requests_total{code="500",route="/order"}   →  每秒 37
      p99_latency_seconds{route="/order"}               →  0.82
      特点：提前定义、成本低、可长期保存、看不到细节

  Logging（日志）：  离散事件原文，用于**归因**
      {"ts":"...","level":"error","trace_id":"a1b2","msg":"db timeout",
       "sql":"select ...","cost_ms":3021}
      特点：信息全、成本高、需要结构化（JSON）才能被检索

  Tracing（追踪）：  一次请求跨服务的调用链，用于**定位**
      order-service ──> coupon-service (12ms)
                   └──> storage-service (3002ms)  ← 慢在这里
      特点：需要全链路埋点 + 上下文透传（W3C traceparent 头）

  ⇒ 三者的连接点只有一个：**trace_id / request_id 贯穿始终**
```

**示意 6：灰度发布的最小闭环**

```text
   1) 新版本部署在独立环境（与生产同构，但只接 1% 流量）
         │
   2) 流量切片：按 UID 哈希 / 按运营商 / 按地域 / 按 header（内部员工优先）
         │
   3) 观测：对比新旧版本的错误率、P99、业务指标（下单成功率等）
         │
   4) 决策：全量 / 扩大灰度 / 回滚（回滚 = 把流量切回旧版本，是常态手段）
         │
   5) 数据库变更必须与代码**双向兼容**（新代码能读旧结构，旧代码也能读新结构），
        否则回滚不掉 —— 这是最容易踩的坑
```

## 版本演进

| 版本 / 时间 | 与本章相关的变化 |
| --- | --- |
| 2019（原书基线） | 熔断靠 Hystrix（线程池隔离 + 熔断）；监控靠 Zabbix / ELK；发布靠人工切流量 |
| 2018 | **Hystrix 宣布不再迭代**（2018-11）；熔断实现转向 Resilience4j / Sentinel |
| 2016–2019 | **SRE 与错误预算概念推广**（Google SRE Book 2016）；SLI/SLO/错误预算成为可用性的量化表达 |
| 2017–2021 | **OpenTracing → OpenTelemetry**（CNCF，OpenTelemetry 于 2019 年从 OpenTracing/OpenCensus 合并而来）；追踪从各厂商私有协议走向统一 |
| 2019–2022 | **Prometheus + Grafana 成为监控事实标准**（取代 Zabbix）；日志侧 Elastic 生态仍强，但 **OpenTelemetry 统一了采集 SDK** |
| 2020–2023 | **混沌工程产品化**：ChaosBlade（阿里，内核层故障注入能力强）、Litmus（CNCF）、Chaos Mesh |
| 2021–2025 | **Service Mesh 的熔断与重试下沉**：Istio（**38407★**）/Envoy 提供 L7 级熔断、重试预算、异常点自动剔除；同时 **Kubernetes 的 PDB + 滚动更新**让发布与回滚成为平台能力 |
| 2024–2026 | **可观测性走向统一与成本优化**：OpenTelemetry 成为默认采集层（metrics/logs/traces 同一 SDK 与协议）、eBPF 补齐无侵入的内核层数据；同时" observability 的成本"成为一线重点 |

## 近年研究与工业界开源实践（2015–2026）

- **趋势（2015 → 2026）**：稳定性建设的重心发生了三次迁移：
  1. **从"设计"到"验证"**：熔断到底生不生效，靠混沌工程反复验证，而不是靠评审时口头确认。
  2. **从"单点防御"到"全局策略"**：限流/熔断从应用内库变成平台级配置（网关与 Service Mesh），但也因此**必须有应用级兜底**。
  3. **从"三层各建各的"到"一套 SDK 三合一"**：OpenTelemetry 统一了 metrics/logs/traces 的采集，避免了每种语言都写三遍埋点。
- **混沌工程（🔧 本章必须补）**：
  - **ChaosBlade**（`chaosblade-io/chaosblade`，**6522★**）：支持 CPU/内存/网络/磁盘/进程/DNS 乃至容器与云的故障注入，是国内最常用于"生产级演练"的工具。
  - **Litmus**（`litmuschaos/litmus`，**5622★**）：CNCF 沙箱项目，实验以 CRD 描述，可直接编排进 K8s 流水线。
  - **实践要点**：混沌实验必须**可停止、可回滚、有开关**，并且只在有完整监控与快速回滚能力时才允许在生产执行。
- **错误预算与 SLO（🔧 本章必须补）**：原书 9.2 讲降级靠经验阈值。现代答案是把可用性写成 **SLO + 错误预算**：一个季度内失败请求比例超过预算，就冻结变更、优先修稳定性。这让"要不要回滚""要不要灰度"变成有据可依的谈判，而不是领导拍板。
- **OpenTelemetry 统一可观测性（🔧 本章必须补）**：原书 9.4 把日志、指标、追踪当作三套系统各建各的。2026 年的标准是 **OpenTelemetry（同一 SDK、同一 exporter 协议）**，并可配合 eBPF 获得无侵入的内核/网络层数据。
- **典型仓库（star 为 2026-09-25 用 `gh api` 实测）**：
  - `resilience4j/resilience4j`（**10766★**）：熔断/限流/重试/舱壁的轻量化实现，是本章策略的代码化。
  - `prometheus/prometheus`（**66221★**）：指标采集与告警规则的事实标准；`rate()` 与 `histogram_quantile()` 是 P99 告警的标准写法。
  - `grafana/grafana`（**76907★**）：统一可视化；可同时接 Prometheus（指标）、Loki（日志）、Tempo/Jaeger（追踪）。
  - `jaegertracing/jaeger`（**23238★**）：CNCF 毕业项目，OpenTracing 兼容的实现，是链路追踪的经典选型。
  - `open-telemetry/opentelemetry-collector`（**7596★**）：可观测数据的统一采集与转发层（pipeline + 多种 exporter）。
  - `istio/istio`（**38407★**）：把重试、超时、熔断、异常点自动剔除（outlier detection）变成平台级策略。
  - `chaosblade-io/chaosblade`（**6522★**）、`litmuschaos/litmus`（**5622★**）：让"熔断是否真的生效"变成可重复的实验。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "多副本 = 高可用" | 多副本只防机器故障，**不防代码 bug 与误操作**（那些会被同步复制到所有副本）。必须配备份 + 回滚 + 演练 |
| 2 | "熔断是保护下游的" | 熔断同时保护**自己**：熔断期间快速失败，避免占满线程池后被拖垮 |
| 3 | "重试能提升成功率" | 在依赖已经过载时，重试是**放大器**；必须限制次数、指数退避，并跨调用链只重试一次 |
| 4 | "限流阈值定一个安全值就行" | 阈值必须**按容量标定**（来自压测拐点）且**按层次配置**（网关粗、单机精）；集群限流需要额外的协调机制 |
| 5 | "降级是临时方案" | 降级的正确形态是**预先定义的功能开关清单**（关什么、读什么、返回什么），临时想出来的降级在故障当时没人想得出来 |
| 6 | "回滚是失败标志" | 回滚是**常态手段**；真正的风险是"数据库变更与代码不兼容导致回滚不掉"（因此要求变更双向兼容） |
| 7 | "有监控就够" | 监控不告警 = 没有监控。要检查的是"告警里有多少是可执行的、有多少被长期忽略" |
| 8 | 🔧 **本书未覆盖：混沌工程** | 原书 9.2 是"设计上防御"。2026 年的标准动作是**主动 injecting 故障并验证**：`chaosblade-io/chaosblade`（**6522★**）与 `litmuschaos/litmus`（**5622★**）让"熔断与降级是否真的生效"从假设变成实验结论 |
| 9 | 🔧 **本书未覆盖：SRE 与错误预算** | 原书的可用性表达是百分比口号。现代答案：定义 SLI/SLO → 换算成错误预算 → 预算耗尽则冻结变更。这是"何时该降级、何时该回滚"的决策依据 |
| 10 | 🔧 **本书未覆盖：OpenTelemetry 统一可观测性** | 原书 9.4 假设三层各自建设。2026 年的标准是 `open-telemetry/opentelemetry-collector`（**7596★**）做统一采集；**eBPF（`bpftrace`/`bcc`）补齐了"不改代码也能观测"的那一段** |
| 11 | 🔧 **本书未覆盖：Service Mesh 侧的熔断与重试** | 原书把治理写死在应用里。今天 `istio/istio`（**38407★**）/Envoy 能在 L7 做熔断、并发限制、异常点剔除；**但平台故障时必须保留应用级兜底** |
| 12 | 🔧 **本书未覆盖：K8s 时代的发布与回滚** | 原书 9.3 讲"切流量灰度"。今天滚动更新、就绪/存活探针、PDB、Argo Rollouts（按指标自动分析与自动回滚）已把灰度与回滚平台化，发布风险由平台兜底 |
| 13 | 🔧 原书表述需补充 | 原书 9.1 讲多副本时未区分**"主从异步复制"与"多数派/强一致复制"**；两者在故障切换时的数据损失行为完全不同，选择时必须明说（见 `11-多副本一致性.md`） |

## 与其他章 / 其他书的联系

- 本章与 `08-高并发问题.md` 是一体两面：**高并发是症状，不稳定往往是其后果**。8.4 的容量评估输出，正是 9.2 限流阈值的输入。
- 与 `06-数据库.md` 的主从复制：9.1 的多副本在数据库侧的现役形态；半同步与并行复制的取舍是"一致性与可用性的第一道选择题"。
- 与 `07-框架软件与中间件.md`：熔断/限流/降级从"框架里的库"（Hystrix 时代）变成"平台里的策略"（Mesh / 网关时代），这是 7.3 的延伸话题。

- 与 `02-架构的道与术.md` 的误区 4：「错误预算」正是"取舍能被量化"的样板。
- 跨书：
  - `book/高伸缩性系统/10-水平伸缩容量与可观测性.md`：本章 9.4 与之高度重合，但后者有背压与抢救性支持的 Erlang 视角。
