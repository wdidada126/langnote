# 第5章 网络

> **一句话**：第 5 章把"从浏览器到服务端"这几百毫秒里的每一层都拆开了一遍。**这一章的实用价值不在记住握手挥手的报文顺序，而在于：当你看到一次 P99 抖动时，能把它定位到这一层中的哪一层。**

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 HTTP 1.0 → 5.2 HTTP 1.1 | Keep-Alive、Content-Length、Pipeline、HOL Blocking | 1.1 解决了"每条请求一个连接"，但**没有解决队头阻塞** |

| 5.7 QUIC | FEC 与连接迁移、更少的 RTT | 把传输层与加密层合并，解决"队头阻塞 + 连接迁移 + 启动延迟"三件事 |

## 核心精讲

> 以下为**教学示意，不参与编译、不参与任何构建**，仅用于说明协议机制。

**示意 1：HTTP/1.1 的队头阻塞 vs HTTP/2 的多路复用**

```text
HTTP/1.1（Pipeline 也不解决）：
  ┌─ 请求1 ──────── 响应1（慢！）───────┐
  ├─ 请求2 ──>  （被阻塞）              ├─ 请求3 ──>  （被阻塞） ─
  → 后到的请求必须等前一个响应回来才被处理，连接利用率低

HTTP/2（同一条连接上并发多个流）：
  ┌─ 帧(流1 header) ─┐
  ├─ 帧(流2 header) ─┤
  ├─ 帧(流1 data)  ──┼─> 同一条 TCP 连接，多条流交错
  ├─ 帧(流2 data)  ──┤    （流1 慢不再阻塞流2 的传输，但流1 的
  └─ 帧(流3 header) ─┘     TCP 丢包仍会阻塞整条连接）
```

**示意 2：TLS 握手为什么是"四次"（一次往返的真相）**

```text
  客户端                                          服务端
     │  ClientHello（支持的版本/套件/key_share）  ──>
     │                                            │ 选套件、选 key_share
     │  ServerHello + Certificate + [证书状态]    <──
     │  ServerKeyExchange（RSA/ECDHE 场景）       <──
     │  ── [CertVerify] ── [Finished] ─────────────>
     │  <── [NewSessionTicket / ChangeCipherSpec] ──
     │                                            │
   ① 客户端确认"我俩对上密钥"      ② 服务端确认"客户端能对上"
   ⇒ 两个方向都要各自确认一次，所以看起来是"四次"，实际只多了一个 RTT
```

> 原书 5.4.8 强调"四次握手"，但要注意重点其实是**两个方向的密钥确认**。TLS 1.3（RFC 8446, 2018）把这个流程压到 **1-RTT**（会话复用时 0-RTT），并已在现代浏览器中默认启用。

**示意 3：TCP 三次握手的"2 将军问题"本质**

```text
  客户端                                          服务端
     │  SYN                                       ──>
     │                                            │ 分配资源，进入 SYN_RCVD
     │  SYN-ACK + 自己的 ISN                      <──
     │                                            │ 分配资源，进入 ESTABLISHED
     │  ACK                                       ──>
     │                                            │ 进入 ESTABLISHED

   为什么不能两次？   → 服务端无法区分"这就是新连接"
                        还是"一个迟到的重复 SYN"，会让资源被晚到的报文耗尽
   代价是什么？       → 必须等最后一个 ACK；SYN 队列（半连接队列）承受 SYN Flood
                         SYN Cookie 是对这个代价的工程解答
```

**示意 4：四次挥手与 TIME_WAIT**

```text
  客户端                                          服务端
     │  FIN ──>                                   （主动方结束发送）
     │  <── ACK
     │  <── FIN                                   （被动方也结束发送）
     │  ACK ──>
     │  主动方进入 TIME_WAIT，等 2MSL
```

> `TIME_WAIT` 存在两个原因：① 保证最后一个 ACK 能到达（否则被动方重发 FIN 会收不到 ACK）；② 让本次连接的残余报文在网络中消散，避免污染后续使用同一四元组的新连接。**这也是高并发短连接服务上"端口耗尽"与"timewait socket 太多"的根源。**

**示意 5：QUIC 的三件事（相对 TCP+TLS 的净收益）**

```text
① 更少的 RTT：QUIC 把传输与 TLS 合并进同一套握手
     TCP + TLS1.2（有证书链）：1.5 ~ 2 RTT
     TLS 1.3：1 RTT；会话复用：0-RTT（注意 0-RTT 有重放风险，不可用于写操作）
② 消灭队头阻塞：QUIC 的流是**帧级别**隔离的，一个流丢包不影响其他流
     （HTTP/2 over TCP：一个 TCP 段丢失 → 整条连接的所有流都卡住）
③ 连接迁移：用 (src_ip, src_port, dst_ip, dst_port) 之外的一个 **Connection ID**
     手机从 Wi-Fi 切到 4G、或 NAT 端口被重映射，连接不断
```

> 原书 5.7.1 提到"不丢包（Raid5 算法和 Raid6 算法）"——这里需要谨慎：**QUIC 早期草案确实讨论过前向纠错（FEC）**（一度设想用类似 RAID 的冗余分组在丢包时直接恢复），但**最终标准化的 QUIC（RFC 9000, 2021）并未引入这类 FEC**，丢包恢复完全依靠重传与拥塞控制。FEC 在 QUIC 上并未成为标准的一部分，因此本章不将其列为 QUIC 的现役特性。
>
> 需要说明：原书此处想要表达的是"QUIC 用冗余来对抗丢包的**思路**"，这与 RAID 的**思路**确实同源（都是"宁可多发一点冗余，也不等重传"）。但**思路同源不等于标准如此**——实现上 QUIC 选择的是重传而非 FEC，因为 FEC 会显著增加头部开销与实现复杂度，且对延迟的改善有限。

**示意 6：三次握手的关键参数与运维现实**

```text
  半连接队列（SYN Queue）与全连接队列（Accept Queue）都溢出时，新连接会被丢弃
      → 表象：客户端看到"连接超时"，服务端日志里可能什么都没有

  典型事故：短连接高并发服务，端口/文件描述符耗尽 + TIME_WAIT 堆积
      → 表象：localhost 或内网地址连不上；net.ipv4.ip_local_port_range 被打满
      → 缓解：net.ipv4.tcp_tw_reuse、调大端口范围、改用长连接/连接池

  心跳与保活：
      应用层心跳（业务可感知） vs TCP Keepalive（内核层，默认 2 小时，太慢）
      ⇒ 生产环境应使用应用层心跳，超时设在网络层超时之下
```

**示意 7：TLS 证书链与信任链（原书 5.4.7 的具象化）**

```text
   浏览器 ──> ┌ 服务端证书（含签发者）──┐
              │   subject: example.com │  ← 叶证书
              └────────┬───────────────┘
                       │ 验证签名（用签发者的公钥）
              ┌────────▼───────────────┐
              │  中间 CA 证书            │  ← 可有多个层级
              │  签发者：Root-G2        │
              └────────┬───────────────┘
                       │ 验证签名
              ┌────────▼───────────────┐
              │  根证书（预置在操作系统/  │  ← 信任的**起点**，不可验证，只能先验
              │  浏览器信任库里）        │
              └────────────────────────┘

   ⇒ 根证书一旦被信任，它签发的一切都被信任；这就是"信任链的起点"的脆弱之处
      （ misissuing 事故、根 CA 被 compromise，影响面是全局的）
   ⇒ 运维现实：证书链要**配齐中间证书**，否则某些客户端（尤其移动端与旧库）会验证失败
```

**示意 8：HTTP/2 与 HTTP/1.1 的实际性能差异（为什么值得迁移）**

```text
  同一个页面 60 个资源：
    HTTP/1.1 + 6 连接：  6 并发 × 10 个资源/连接，串行感明显，HOL 阻塞
    HTTP/1.1 + 域名分片：12~30 个子域名（工程手段绕过 6 连接限制）
                        → 代价：DNS 查询、TCP 握手 ×N、TLS 握手 ×N、Cookie 累积变大
    HTTP/2 单连接：      60 个流交错于一条连接，头部用 HPACK 压缩
                        → 代价：所有流共享一条 TCP 连接，丢包会阻塞全部流
    HTTP/3（QUIC）：     60 个流各自独立，单流丢包只影响自己
                        → 代价：UDP 可能被中间件拦截；无内核级优化与长期拥塞控制调优
```

## 版本演进

| 版本 / 时间 | 与本章相关的变化 |
| --- | --- |
| 2015 | **RFC 7540（HTTP/2）**：二进制分帧 + HPACK 头部压缩 + 多路复用 |
| 2018 | **RFC 8446（TLS 1.3）**：1-RTT 握手，前向安全成为默认 |
| 2019（原书基线） | HTTP/2 已普及，QUIC 仍是 Chromium 实验特性（draft-23 前后） |
| 2021-05 | **RFC 9000（QUIC）正式发布**；**RFC 9114（HTTP/3）于 2022 年发布**，把 HTTP/3 确立为标准 |
| 2018 | **RFC 8446（TLS 1.3）发布**，1-RTT 握手、加密扩展全部前向安全 |
| 2020–2022 | **HTTP/3 大规模部署**：Cloudflare、Google、CDN 厂商全面支持；但存在中间件（UDP 被企业防火墙拦截）问题 |
| 2021–2023 | **gRPC 成为云原生 RPC 事实标准**：基于 HTTP/2 + Protobuf，与 Service Mesh 深度绑定 |
| 2023–2025 | **HTTP/3 在 CDN 与移动网络成为默认**：QUIC 连接迁移与 0-RTT 大规模验证；TCP BBR 成为主流拥塞控制 |
| 2026 | 现状：**HTTP/1.1 仍在大量存量系统使用；HTTP/2 是新服务默认；HTTP/3 在 CDN/移动场景占比高但非通用**；TLS 1.3 已是事实基线，TLS 1.2 逐步退役 |

## 近年研究与工业界开源实践（2015–2026）

- **趋势（2015 → 2026）**：传输层的主线是「**合并协议层 + 消灭队头阻塞 + 降低握手成本**」。
  1. **HTTP/3 正式标准化（RFC 9114, 2022）**：QUIC 从 Chromium 实验特性变成 RFC 标准，但**部署仍受 UDP 中间件限制**。
  2. **HTTP/2 的内部矛盾被认清**：HTTP/2 解决了"应用层队头阻塞"，但**跑在 TCP 上仍然吃 TCP 的队头阻塞**——这正是 HTTP/3 存在的直接理由。
  3. **gRPC 与 HTTP/2 绑定**：云原生 RPC 生态（Service Mesh、K8s API）几乎全部构建在 HTTP/2 之上，使得"理解 HTTP/2 流"成为基础设施层的必备知识。
  4. **eBPF 成为网络排查的主力**：`bpftrace`/`bcc` 可以在不改代码的前提下定位丢包、重传与延迟尖刺；Cilium/XDP 把转发逻辑放进内核。
- **典型仓库（star 为 2026-09-25 用 `gh api` 实测）**：
  - `grpc/grpc`（**45341★**）：HTTP/2 + Protobuf 的工业级实现，是"HTTP/2 流"最广泛的生产实践。
  - `quic-go/quic-go`（**11782★**）：纯 Go 的 QUIC/HTTP/3 实现，RFC 9000 的一线参考实现。
  - `curl/curl`（**42925★**）：HTTP/1.1→2→3、TLS 1.2→1.3 的完整客户端实现，是"协议现状"的活体样本。
  - `envoyproxy/envoy`（**28992★**）：把 HTTP/2 与 HTTP/3 的协议处理、重试、超时、熔断做成了基础设施，业务代码因此不必再自己写这些逻辑。
  - `cloudwego/kitex`（**8051★**）：国内 Go RPC 框架，THeader 协议 + 多协议编解码，体现 HTTP/2 之外的另一条 RPC 路线。
  - `torvalds/linux`（**250115★**）：TCP 拥塞控制（BBR 的实现）与 eBPF/XDP 的现场。
- **一条排障顺序建议**：**先分层，再猜**。看到延迟升高时，按「应用埋点 → 服务端日志 → `bpftrace`/`bcc` 网络统计 → `tcpdump` 抓包」的顺序逐层下沉。**多数"网络问题"其实是应用层问题**（连接池耗尽、GC 停顿、序列化慢），而多数"确实的网络问题"是丢包与重传。跳过分层直接抓包，是效率低下的主要原因。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "HTTP/2 解决了队头阻塞" | 只解决了**应用层（HTTP 消息级）**的；TCP 段的丢失仍会阻塞整条连接。这就是 HTTP/3 要换掉传输层的理由 |
| 2 | "QUIC 因为用了 RAID 式前向纠错所以不丢包" | 🔧 **这一点需要修正**：QUIC 早期草案讨论过 FEC，但**RFC 9000 并未包含 FEC**，丢包恢复靠重传 + 拥塞控制。"不丢包"的说法不成立 |
| 3 | "QUIC 一定比 TCP 快" | 首次连接不一定更快（0-RTT 才有明显优势）；UDP 可能被企业/移动网络中间件拦截；内核态实现缺失会带来用户态拷贝成本 |
| 4 | "HTTPS 只是加了个加密层" | 它同时**改变了排查手段**（流量不可见、必须靠 eBPF 或服务端日志）并引入了新的性能维度（握手成本、密钥协商、证书链长度） |
| 5 | "TCP 三次握手是因为'三个包能确认双方收发正常'这么简单" | 更准确的说法是它在**资源分配时机**上取得了平衡；SYN Cookie 与半连接队列是这个问题的工程答案 |
| 6 | 🔧 **本书未覆盖：HTTP/3 正式标准化** | 原书把 QUIC 当作"更激进的未来选项"。2026 年的现实是 **RFC 9114 已确立 HTTP/3**（2022），CDN 与移动网络大规模部署，**但它与 HTTP/1.1 长期共存**，并非全面取代 |
| 7 | 🔧 **本书未覆盖：TLS 1.3 全面落地** | 原书 5.4.8 描述的是 TLS 1.2 的四次握手流程。现代默认应是 **TLS 1.3（RFC 8446）：1-RTT 握手、全程前向安全、会话复用 0-RTT** |
| 8 | 🔧 **本书未覆盖：gRPC / HTTP2 的普及** | 原书以浏览器 HTTP 为主线的视角已不足以覆盖基础设施层。2026 年的多数内部服务调用跑在 **gRPC over HTTP/2** 上，"HTTP/2 的流、头部压缩、单连接多路复用"是必须掌握的内容 |
| 9 | 🔧 **本书未覆盖：eBPF 在网络可观测性上的角色** | 原书没有"如何证明你猜的瓶颈是对的"这一环。2026 年排查网络抖动，`tcpdump` 之外应有 `bpftrace`/`bcc`（丢包点、重传、RTT 分布），可观测性上 OpenTelemetry 统一了应用层，eBPF 补齐了内核与网络层 |
| 10 | 🔧 **本书未覆盖：0-RTT 的重放风险** | 原书 5.7.2 只讲"更少的 RTT"。0-RTT 数据可被重放，**绝不可用于非幂等（写）操作**，这是工程上必须明确的边界 |
| 11 | 🔧 原书表述需补充 | 原书 5.2.3 罗列了 HTTP/2 之前的性能技巧（域名分片、雪碧图、合并请求），今天是**反模式**——它们是为绕过 HTTP/1.1 限制而生的，采用 HTTP/2 后反而增加复杂度 |
| 12 | 🔧 本书未覆盖 | **QUIC 的连接迁移在生产上的实际形态**：原书 5.7.3 只讲概念。现实中连接迁移主要解决"移动网络切换"与"NAT 重映射"，但服务端需要支持 Connection ID 路由；且在无连接迁移能力的中途设备（负载均衡）存在时，收益会被削弱 |
| 13 | 🔧 本书未覆盖 | **HTTP/3 的部署现实**：UDP 被企业防火墙拦、部分代理不支持、以及"HTTP/3 的 TLS 证书仍然要配全链"这些运维细节，是迁移时必须评估的成本项 |
