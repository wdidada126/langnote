# 第4章 操作系统

> **一句话**：第 4 章是全书 computer fundamentals 最硬的一块。**看透了"一次 read/write 到底发生了什么"，就看懂了缓存、分片、异步化、串行化这一整串招式背后的共同动机——都是在绕开 I/O。**

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 4.1 缓冲 I/O 和直接 I/O | 页缓存（page cache）作为通用缓存层；`read`/`write` 与 `O_DIRECT` 的差别 | 缓冲 I/O 省系统调用、聚合随机写；直接 I/O 省一次内存拷贝但**丢掉了聚合与预读** |
| 4.2.1 内存映射文件 | `mmap` 把文件映射进虚拟地址空间 | 用户态直接访问页缓存，省一次拷贝，但**缺页中断是隐藏成本** |
| 4.2.2 零拷贝 | `sendfile` / `splice` / `mmap+write` / 内核态聚合 | 零拷贝省的是**CPU 拷贝与上下文切换**，不是网络带宽 |
| 4.3.1 网络 I/O 模型 | blocking / non-blocking / IO multiplexing / signal-driven / async | 前四个都是" yourself poll 或等"，只有 AIO 是内核替你做完 |
| 4.3.2 Reactor 与 Proactor | 前者"事件就绪你自己读"，后者"内核帮你读完给你结果" | 现代主流是 Reactor（epoll + 非阻塞）；Proactor 在 Windows IOCP 与 io_uring 上以新形态复活 |
| 4.3.3 select / epoll 的 LT 与 ET | 水平触发 vs 边缘触发的语义与写法差异 | ET 必须**一次性读干**，LT 更安全；二者都能写出正确的服务器，ET 更省CPU但更易错 |
| 4.3.4 1+N+M 模型 | 1 个 acceptor + N 个 IO/Worker 进程/线程 + M 个业务处理 | 把"连接管理"与"业务处理"解耦，是 1.0 时代的通用服务器骨架 |
| 4.4 进程、线程和协程 | 切换成本、栈大小、调度、资源边界 | 协程是**用户态的调度**，省钱但不省内核；进程是最强隔离但最贵 |
| 4.5.1 内存屏障 | 编译器重排与 CPU 重排；`acquire`/`release`/`fence` | 无锁的前提不是原子指令，而是**正确的内存序** |
| 4.5.2 CAS | compare-and-swap、ABA 问题、伪共享、自旋 vs 退避 | CAS 只保证"此刻未被改"，不保证"我看到的是最新" |

## 核心精讲

> 以下为**教学示意，不参与编译、不参与任何构建**，仅用于说明机制。

**示意 1：一次 `read()` 的实际路径（缓冲 I/O vs 直接 I/O）**

```text
        ┌───────────── 用户态 ─────────────┐
        │  buf[]                            │
        └──────┬──────────────▲─────────────┘
               │ read(fd,buf) │ ② 拷贝
               v               │
        ┌───────────────────────────────┐
        │  ① 系统调用（上下文切换 ~1µs） │
        └──────┬──────────────▲──────────┘
               v              │
        ┌───────────────────────────────┐
        │  VFS → 文件系统 → 页缓存(page cache) │
        │  （缓冲 I/O：命中则省掉磁盘 I/O）      │
        └──────┬──────────────▲──────────┘
               v              │ DMA
        ┌───────────────────────────────┐
        │  块设备层 → 磁盘控制器          │
        └───────────────────────────────┘

  直接 I/O（O_DIRECT）：跳过页缓存，① 与页缓存两层被省掉
    代价：写必须对齐（块大小）、无法利用 readahead、无法共享页缓存
```

> 原书 4.1 的关键洞察：**页缓存不是"额外的"，它是 VFS 与磁盘之间的缓存层，也是为什么"写文件后立刻读通常很快"**。

**示意 2：零拷贝的四种形态（省的是拷贝与切换次数）**

```text
传统 read+write：  磁盘 → 页缓存 → 用户buf → 内核socket缓冲 → 网卡   （4 次拷贝，4 次切换）
mmap + write：     磁盘 → 页缓存 →(用户态直接写)→ socket缓冲 → 网卡 （3 次，但用户态写即内核态写）
sendfile：         磁盘 → 页缓存 → socket缓冲 → 网卡                （2 次，无用户态拷贝）
splice/tee：       在内核页缓存与 socket 之间搬家，**全程不碰用户态**
```

```c
/* 教学示意，不参与编译、不参与任何构建 */
/* 现代 Linux 首选：把文件从 in_fd 直接送到 socket，零拷贝 */
// ssize_t sent = splice(in_fd, NULL, out_fd, NULL, len, SPLICE_F_MOVE);
/* epoll 时代的经典写法 */
// ssize_t n = sendfile(out_fd, in_fd, &offset, count);
```

**示意 3：epoll 的 LT/ET 语义差别（同一个"读事件"的处理方式）**

```text
LT（水平触发，默认）：只要 socket 里还有未读数据，每次都会再通知你
    → 写法：read 一次也行，剩下了下次继续给你
    → 优点：漏读也不会卡死；缺点：一次循环里被反复唤醒

ET（边缘触发）：只在"有数据到达的那一刻"通知一次
    → 写法：必须循环读到 EAGAIN，否则剩下的数据要等下一批
    → 优点：事件次数少、开销低；缺点：**漏读一个字节 = 这条消息永久丢失**
```

```c
/* 教学示意，不参与编译、不参与任何构建 */
/* ET 模式下的正确骨架：读到 EAGAIN 为止 */
// while (1) {
//     ssize_t n = read(fd, buf, sizeof(buf));
//     if (n < 0) {
//         if (errno == EAGAIN || errno == EWOULDBLOCK) break;  /* 读干了 */
//         return error;
//     }
//     if (n == 0) return peer_closed;                            /* 对端关闭 */
//     handle(buf, n);
// }
```

**示意 4：1+N+M 模型的职责划分**

```text
        ┌────────────┐   accept   ┌────────────────────────────┐
        │  1 Master  │ ─────────> │  N 个 IO 进程/线程          │
        │ 只 accept  │            │  读写 socket、解析协议       │
        │ 不接受业务 │            └───────────┬────────────────┘
        └────────────┘                        │ 的任务被投递
                                              v
                                   ┌──────────────────────────┐
                                   │  M 个 Worker（业务线程池） │
                                   │  查库 / 调下游 / 计算      │
                                   └──────────────────────────┘
```

> 这个模型回答的是"**谁负责连接、谁负责计算**"。2019 年前后它是 Nginx、Memcached 及国内网关的标准骨架；今天它在 Go 里退化成"一个 goroutine 一个连接"，但**思路没变，只是把 N 放在了语言运行时里**。

**示意 5：内存屏障在干什么（以 x86-TSO 为例）**

```text
期望语义（程序员心里）：  a=1 先发生， 再看 b
CPU/编译器真实行为：      store a 可能后于 load b 被观察到（StoreLoad 重排）

  无屏障：            store(a,1) ... load(b)      → 可能读到 b=0
  加 StoreLoad 屏障：  store(a,1); smp_mb(); load(b) → 一定读到 b=1

四种必要屏障（老教材常只提"读写屏障"）：
  LoadLoad / LoadStore / StoreStore / **StoreLoad**（最贵，几乎所有 x86 上它就一条 mfence 或依赖 LOCK 前缀）
```

```java
/* 教学示意，不参与编译、不参与任何构建 */
/* volatile 写后面跟 volatile 读，就是一条 StoreLoad 屏障 */
// volatile boolean flag; int value = 0;
// 写线程： value = 42; flag = true;        （value 的写在 flag 之前可见）
// 读线程： if (flag) { assert value == 42; }
```

**示意 6：CAS 与 ABA**

```text
  线程1 读到 value = A
  线程2 把 value 改成 B，再改回 A
  线程1 的 CAS(A → C) 成功 —— 但它以为"中间没人动过"
  → ABA 问题（常见于无锁栈/链表，需要版本号、hazard pointer 或 tagged pointer）
```

## 版本演进

| 版本 / 时间 | 与本章相关的变化 |
| --- | --- |
| 2019（原书基线） | 主线是 **epoll + Reactor + 线程池**；Linux 上异步 I/O（`io_setup`/`io_submit`）长期"不好用" |
| 2019 | **io_uring 合入 Linux 5.1（2019-03）**：首个稳定可用版本，把"提交/完成"统一到一个环形缓冲区，接近零系统调用开销 |
| 2020–2021 | io_uring 相关严重漏洞（如 CVE-2021-21834 系列）暴露了**新内核接口的成熟度问题**；`io_uring` 的 `IORING_SETUP_SQPOLL` 与直接注册（registered files/fixed buffers）成为性能关键点 |
| 2021–2022 | **io_uring 走向成熟**：`io_uring` 在 fio（8.0+）中被设为默认引擎；`OPENAT`/`STATX`/`FALLOCATE` 等新操作陆续支持 |
| 2022–2023 | **网络可观测性转向 eBPF**：`bpftrace`、`bcc` 成为排查"丢包 / 重传 / 延迟尖刺"的标配；Cilium 用 eBPF 实现内核态 LB |
| 2023–2026 | **io_uring 成为高负载服务主流选项**：dpdk 之外的用户态高性能 I/O 多了一条路；同时 io_uring 的**内核旁路安全性**仍是被讨论的焦点 |
| 2026 | 现实选择：成熟服务多半是 **epoll + io_uring 并存**；排查工具主力从 `strace`/`tcpdump` 转向 **eBPF 工具集**（`bpftrace`、`bcc`、`pixie` 一类），连接追踪（Connection Migration）等 QUIC 特性落到用户态库 |

## 近年研究与工业界开源实践（2015–2026）

- **趋势（2015 → 2026）**：本章的 I/O 栈在十年间发生了三处结构性变化：
  1. **从"系统调用密集"走向"批量 + 无锁环形缓冲"**：`io_uring` 用共享内存环形队列把一次 I/O 的代价压到接近零。
  2. **从"用户态轮询"到"内核态程序化"**：eBPF 让内核可编程，XDP 在网卡层面过滤/转发，把一部分网络处理搬出用户态。
  3. **从"观测靠 strace"到"观测靠 eBPF"**：无需改应用即可获得系统调用、网络、调度、块 I/O 的画像。
- **典型仓库（star 为 2026-09-25 用 `gh api` 实测）**：
  - `torvalds/linux`（**250115★**）：`io_uring` 与网络子系统的实现现场；`Documentation/io-uring.txt` 是一手规范。
  - `libuv/libuv`（**27200★**）：跨平台异步 I/O 封装（epoll/kqueue/IOCP 的统一抽象），Node.js 的底座。
  - `golang/go`（**138996★**）：`runtime/netpoll` 是 epoll 的工业级实现，直接印证 4.3.2 的 Reactor 模式。
  - `redis/redis`（**76472★**）：单线程 + Reactor 的极致样本；**它的性能上限恰恰是"绕不开的那一次 read/write"**，是全章最好的反例教材。
  - `openresty/openresty`（**14044★**）：`cosocket` 把 epoll 暴露成协程语义，1+N+M 在脚本语言里的现代形态。
  - `quic-go/quic-go`（**11782★**）：在用户态完整实现 QUIC，是"现代网络 I/O 模型"的活标本。
  - eBPF 生态：内核自带 `bpftrace`/`bcc`（工具在 `torvalds/linux` 的 `tools/bpf` 与独立发行包中），是 2022 年之后排查网络抖动的主力工具。
- **值得记录的事实**：`io_uring` 在 2019 年合入时曾因接口复杂与安全争议被质疑，2021 年又出现多个高危漏洞，直到 2022 年后才在数据库与高负载网关中被严肃采用。**这本身是一个架构教训：新内核接口的成熟度曲线远比它的性能曲线慢。**

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "零拷贝=数据不用过 CPU" | 零拷贝省的是**用户态与内核态之间的拷贝和上下文切换**；DMA 与协议栈检查仍要过 CPU |
| 2 | "直接 I/O 更快" | 直接 I/O 跳过页缓存，**失去了 readahead 与写聚合**；除非是数据库这类自己 manages buffer pool 的场景，否则通常更慢 |
| 3 | "ET 比 LT 更快所以一定用 ET" | ET 的正确性依赖"读到 EAGAIN"，写错就丢数据；**LT 的容错性对多数业务更划算** |
| 4 | "epoll 快在开销小" | epoll 快在**没有 select/poll 的 O(n) 扫描与 fd_set 拷贝**；单次调用的常数开销其实并不低 |
| 5 | "协程一定比线程快" | 协程省的是**内核态切换与栈管理**，一旦协程内做阻塞系统调用，整个进程会被拖住 |
| 6 | "CAS 就是无锁，无锁就是最快" | 高争用下 CAS 自旋会烧满 CPU；且 CAS 只保证原子性，**不保证内存可见语义**（仍需正确内存序） |
| 7 | 🔧 **本书未覆盖：io_uring** | 原书 2019 年成书，`io_uring` 刚合入 5.1 且极不成熟。2026 年它已是**高负载服务（数据库、K8s 节点组件、网关）的高性能 I/O 首选之一**：批量提交 + 完成事件队列 + fixed buffers/registered files，把一次 I/O 的系统调用开销降到极低。选型时应与成熟但朴素的 epoll 路线并列比较 |
| 8 | 🔧 **本书未覆盖：io_uring 与 POSIX AIO / Windows IOCP 的对照** | 原书 4.3.1 把 AIO 一笔带过。今天应该讲清：**Linux 的 POSIX AIO 长期是靠内核线程模拟的，性能与语义都不理想**，这恰恰是 io_uring 存在的理由；而 Windows 的 IOCP 是真正的 Proactor，是本章 4.3.2 里"Proactor"一词的现实来源 |
| 9 | 🔧 **本书未覆盖：eBPF 在网络可观测性上的角色** | 原书 9.4 的监控思路建立在"应用自己上报"。2026 年的现实是 **`bpftrace`/`bcc` 可以不改代码就拿到丢包、重传、慢系统调用、块 I/O 延迟分布**；Cilium/XDP 更进一步把部分转发逻辑放进内核 |
| 10 | 🔧 **本书未覆盖：内核旁路（io_uring + 用户态协议栈）** | 本章缺一条"什么时候该考虑绕过内核"的判断准则：通常是**超低延迟（µs 级）且 I/O 模式可预测**的场景，代价是可维护性显著下降 |
| 11 | 🔧 原书表述需补充 | 原书 4.2.2 讲零拷贝时未区分**"省 CPU 拷贝"与"省内存带宽"**；在 100GbE 环境下内存带宽才是瓶颈，这点必须区分 |
| 12 | 🔧 原书表述需补充 | 原书 4.3.4 的 1+N+M 隐含"进程/线程切换贵"的前提；在协程调度器成熟之后，**N 的语义已可以下沉到运行时**，这个模型今天仍成立但实现形态变了 |
