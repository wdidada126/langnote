## 3. 阅读路径建议

- **主线（技术侧）**：`01 → 02 → 04 → 05 → 06 → 07 → 08 → 09`。第 3 章（语言）可按需跳读，但 4.5（内存屏障与 CAS）必须留到第 6 章一起看。
- **主线（业务侧）**：`13 → 14 → 15`。这三章是全书的"另一半"，很多技术书籍完全不写。
- **管理者视角**：`02（道与术）→ 16 → 17`，可略过 4–7 章的技术细节，但保留 8.4（容量规划）和 9.4（监控）两节。
- **面试/查漏**：直接看每章开头的「本章地图」表格，三列（节 / 内容 / 结论）本身就是一页速查卡。

## 4. 本书刻意规避 / 未覆盖的缺口（2026 视角）

原书 256 页要覆盖 17 章，必然做了取舍。以下几个缺口是**最需要补的**：

- **云原生与弹性**：本书的容量观是"预估峰值 → 买机器 → 压测"，2026 年的默认答案是 **K8s HPA + 弹性伸缩 + Serverless**，容量规划从" procurement"变成"策略配置"。见 `08-高并发问题.md` 的「版本演进」。
- **Service Mesh 与统一治理**：本书的熔断限流写在代码里（Hystrix 时代）。2026 年的主流是 **Istio/Envoy 侧的统一策略 + 代码里的 Resilience4J 兜底**。见 `09-高可用与稳定性.md`。
- **可观测性**：本书 9.4 只讲"监控体系与日志报警"，2026 年的统一答案是 **OpenTelemetry（metrics + logs + traces 一套 SDK）**，不是三套系统各建各的。
- **NewSQL / HTAP / 存算分离**：第 6 章的分库分表是 2019 年的主流答案，今天 6000 万 QPS 的订单主链路可能直接选 TiDB / PolarDB，而不是自己做 Sharding + 分布式 ID + 分布式事务。见 `06-数据库.md`。
- **AI/LLM 对架构的影响**：2023 之后大量新系统的流量形态被推理服务改变（显存成为新的"瓶颈资源"，像 CPU 一样被纳入容量规划），本书完全没有此议题。

## 7. 写作约定

每章固定七段：

1. `## 本章地图` —— 表格（节 | 内容 | 结论），一页速查卡。
2. `## 核心精讲` —— 教学示意，**明确标注「教学示意，不参与构建」**；示例片段一律不参与编译、不参与运行。
3. `## 版本演进` —— 从原书出版年（2019）到 2026 的时间轴。
4. `## 经典论文与原始文献` —— 只列可核实出处；不确定的一律不写。
5. `## 近年研究与工业界开源实践（2015–2026）` —— star 数用 `gh api` 现查，标注实测日期。
6. `## 常见误区与本书需修正之处` —— 表格；`🔧` 开头的行 = 原书 2019 年出版、2026 年**必须补的新内容**。
7. `## 与其他章 / 其他书的联系` —— 章内互链 + 跨书互链。
