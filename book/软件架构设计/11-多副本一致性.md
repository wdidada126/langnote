## 核心精讲

> ⚠️ 以下为**教学示意，不参与构建**。所有代码为伪码/结构示意，不代表任何项目的真实实现。

### 11.1 从 Kafka 的两个问题开始

原书用 Kafka 的坑引出「高可用且强一致性到底有多难」，这个开场在 2026 年依然成立——只不过答案已经变了（见误区表）。

**消息丢失**（原书列举的配置陷阱）：

| 配置 | 后果 |
| --- | --- |
| `acks=0` | 网络一丢就丢 |
| `acks=1` | leader 收到但 follower 没同步，leader 宕机 → **丢** |
| 异步发送 | 缓冲区 OOM 或掉电 → 消息还在内存里就没了 |
| unclean.leader.election.enable=true | 落后太多的副本被选为新 leader → **丢** |
| rebalance 期间 | offset 提交滞后 → 重复/丢失 |

**消息错乱**：分区是「顺序」的边界，但分区数 > 1 或消费者并发 > 1 时，全局顺序不成立；`max.in.flight.requests` > 1 且发生重试时，同一条消息的不同版本可能乱序入栏。

核心的一句结论：**Kafka 只提供 partition 级别的顺序性与 at-least-once 语义，"恰好一次"必须由应用 + 幂等 + 事务共同保证。**

### 11.2 Paxos

#### 11.2.1–.2 Paxos 解决什么问题 / 复制状态机

```
复制状态机 = 确定性状态机 + 一致的操作序列
            = 状态机 + 共识（决定下一个操作）+ 复制日志
```

也就是说：**只要多副本能就「日志顺序」达成共识，状态机的状态自动一致**。这就是 Paxos/Raft/Zab 共同的骨架。

#### 11.2.3–.4 一个朴素而深刻的思想 / Basic Paxos

角色：proposer（提议）、acceptor（投票）、learner（学习）。核心机制三条：

1. **提议编号递增**：新提议要用更大的编号，防止被旧的覆盖；
2. **多数派接受即选定**：任两个多数派必有交集，交集里的 acceptor 会告诉 proposer「你之前有个更高的提议被接受过」，从而**必须把那个值带上去**（这是 Paxos 最难懂也最漂亮的一步）；
3. **承诺（Promise）**：acceptor 承诺不再接受更小编号的提议。

教学示意（伪码，非可运行）：

```
proposer(n, v):
  promises = acceptors.map(a => a.prepare(n))     # 阶段一：询问
  if 多数派回应:
      v' = 所有回应中编号最大者对应的值（若存在）
      v = v' if v' exists else v                   # 关键：不自由了
      acceptors.map(a => a.accept(n, v))           # 阶段二：写入
proposer 收到多数派 accepted 后通知 learners
```

安全性结论（safety）：**只有已经被多数派接受的值才可能被选定，且一个值一旦被选定就永远不可改变**（这是 Paxos 安全性的直观表述）。

活性问题：**两个 proposer 交替提出更高编号 → 活锁（livelock）**，这是 Basic Paxos 已知的活性缺陷，也正是工程上必须引入「稳定 leader」的原因。

#### 11.2.5 Multi Paxos

优化点：选出一个**稳定 leader**，之后的提议跳过 prepare 阶段或大幅减少交互；磁盘 `fsync` 时机与 batch 优化让吞吐提升一个量级。工业界说的 "Paxos" 基本都是 Multi Paxos。

### 11.3 Raft

#### 11.3.1 为「可理解性」而设计

Raft 论文（Ongaro & Ousterhout, USENIX ATC 2014）明确把「可理解性」作为设计目标之一，并为此做了三件事：问题**分解**（选举/复制/安全）与**简化状态空间**（随机化选举超时、日志只从一个方向增长）。作者甚至做了对照实验验证 Raft 比 Paxos 更易理解。

> 这一点值得每一个做架构的工程师记住：**一个架构能否被正确实现，取决于它的可理解性，而不是它的优雅程度。**

#### 11.3.2–.3 单点写入与日志结构

- **单点写入**：所有写都走 leader，简化为单向日志复制（没有任何并发写需要仲裁）；
- **日志结构**：日志是唯一的状态变更载体，`log matching` 性质（若两条日志 term 和 index 相同则内容相同、且前序全同）使得**只需比对一条记录就能恢复全量一致性**。

#### 11.3.4–.7 三个子问题

**1）Leader 选举**：随机化选举超时（150–300ms 区间）避免选票瓜分；`RequestVote` 携带 lastLogIndex/term；**只有日志足够新（term 更大，或 term 相同但日志更长）的节点才能当 leader**。

**2）日志复制**：leader 追加 → 并行 `AppendEntries` → 多数派确认 → 提交（`commitIndex` 前进）→ 应用状态机；`AppendEntries` 里的 `leaderCommit` 让 follower 能推断提交点。

**3）恢复阶段（与 leader 不一致时如何收敛）**：leader 为每条记录维护 `nextIndex[]`，用 `AppendEntries` 的失败信息回退指数（或线性 + 二分），把不一致的日志**截断并覆盖**。

**4）安全性保证**：
- **选举限制**（谁有资格当 leader）：候选者日志必须足够新；
- **只有当前 term 的日志才能被提交**：这是 Raft 的证明核心（否则**已提交日志可能被覆盖**）；
- **状态机安全性质**：一旦一条日志被应用，所有后续 leader 一定带它。

教学示意（伪码，非可运行）：

```
if appendEntries.log_conflict(myLog):
    nextIndex[i] -= 1; send nextEntry(i)
# 直到多数派确认，再推进 commitIndex 并 apply
```

### 11.4 Zab

#### 11.4.1 RSM vs Primary-Backup

ZooKeeper 自述属于 **primary-backup** 而非严格的 RSM 取经：它不要求「所有副本接受全部写」的多数派确认，而是「写由 leader 批准、多数派持久化后即可」。

#### 11.4.2 zxid

```
zxid = <epoch, counter>      # 高位：leader 纪元；低位：本纪元内的单调递增序号
```

- **epoch**：等价于 Raft 的 term，用于识别新旧 leader；
- 用 zxid 可以比较两个提议的先后，也用于在恢复中判断**谁的数据更新**。

#### 11.4.3 乱序提交 vs 顺序提交

ZooKeeper 采用**顺序提交（ordered delivery）**：先到先得，写请求按 FIFO 交给 leader 处理，保证全局顺序。这也是 ZooKeeper 能作为分布式锁/选主协调器的重要原因。

#### 11.4.4 FLE 选举

Fast Leader Election：候选广播 `sid + zxid`，节点只投给 **zxid 最大（数据最新）** 的候选；相比完整选举协议更快，但依赖配置得当（多数派在线）。

#### 11.4.5–.6 正常阶段两阶段提交与恢复阶段

- **正常阶段**：leader 本地写入即向 follower 发提案；达到法定数后向全体 `COMMIT`；
- **恢复阶段（最复杂）**：三件事——① **发现**哪些提议在崩溃前已被提交；② **丢弃**所有未提交的提议；③ 新 leader 与 follower **同步**到一致状态。为此 Zab 引入了 disk FIFO 与「zxid 必须大于某一阈值才能当 leader」等约束。

### 11.5 三种算法对比（原书 11.5）

| 维度 | Basic/Multi Paxos | Raft | Zab (ZooKeeper) |
| --- | --- | --- | --- |
| 提出 | Lamport 1998/2001 | Ongaro & Ousterhout 2014 | ZooKeeper 团队，DSOM 2011 |
| 角色模型 | proposer/acceptor/learner | leader/follower/candidate | leader/follower/observer |
| 选主 | 无内建，靠稳定 leader | 随机化选举超时 + term | FLE + zxid epoch |
| 顺序语义 | 单值共识 | 日志顺序 | **全局顺序 + FIFO 客户端顺序** |
| 可理解性 | 低 | **高（论文目标之一）** | 中 |
| 生态 | Chubby/Spanner/Megastore | etcd / Consul / TiKV / KRaft | ZooKeeper / Kafka 旧版元数据 |

star 数均为 2026-09 通过 `gh api repos/OWNER/REPO --jq '.stargazers_count'` 实测。

| 主题 | 仓库 / 项目 | star |
| --- | --- | --- |
| 共识库的参考实现 | `etcd-io/etcd` | ≈52.3k★ |
| 可嵌入的 Raft 库 | `hashicorp/raft` | ≈9.1k★（配套 `hashicorp/raft-boltdb` ≈0.7k★） |
| Raft 算法的「教科书实现」 | `etcd-io/raft` | ≈1.1k★ |

| 一致性检验 | `jepsen-io/jepsen` | ≈7.5k★ |

要点解读：

- **Raft 的工程实现已高度成熟**：`etcd` 的 `raft` 包把算法与状态机解耦，`hashicorp/raft` 提供可嵌入的日志/快照/存储抽象。2019 年本书出版时「实现一个 Raft」还是面试级难题，今天「读 Raft 源码」是架构师的常规功课。
- **Multi-Raft 是真正的工程演进方向**：单组的共识受限于少数派延迟，分片后每个 region 一个 Raft 组，吞吐随机器线性扩展；难点转移到**调度（region 分裂/合并/ Balance）** 与 **跨地区复制（follower + learner）**。
- **Zab 仍在演进**：ZooKeeper 3.5+ 引入了 `--reconfig` 在线成员变更、`Observer` 增强与 NIO/Epoll 连接工厂调整；3.8/3.9 持续修补稳定性问题。 Kafka 在 3.x 又绕回了 ZooKeeper 之外的 KRaft 方案。
- **Paxos 的工业变体**：Google Chubby（Paxos Made Live）、Spanner（TrueTime + Paxos）、TiDB（Percolator + Multi-Raft Paxos 组成员）都是「Basic Paxos + 稳定 leader + 工程补丁」的真实形态。
- **EPaxos 的遗产**：Leaderless 思路在今天的 **Raft + 无主读 / 多主数据库**（CockroachDB 的 gossip-based 时钟、YugabyteDB 的 leaderless read）中仍有回响。
- **Jepsen 的实测结论（2020）**：etcd 在 leader lease 与一致性读的交互中存在**线性一致性违反**，修复涉及 lease 判定的细节。这是「算法正确 ≠ 实现正确」的最好例证。

## 常见误区与本书需修正之处

| # | 误区 | 修正（含 2026 视角） |
| --- | --- | --- |
| 1 | "Paxos 是唯一正确的共识算法" | 共识祖师是 **Viewstamped Replication（PODC 1988）**；Raft 是 2014 年才出现的可理解性重写 |
| 2 | "Raft 就是 Paxos 的简化版" | Raft 是**重新设计**而非简化：用 term/random timeout/日志匹配性质换取可理解性，二者在证明结构上并不互相归约 |
| 3 | "Raft 保证已提交的日志永不丢失" | 算法正确，但**实现**可能违反（Jepsen etcd 2020 的实测）；快照/磁盘 fsync/lease 都是真实的风险面 |
| 4 | "Kafka 用 ZooKeeper 存元数据，所以它的复制用的是 Zab" | 元数据用 Zab；消息数据走的是 ISR + leader 复制，**不是共识协议**。这两条路径的原书表述容易被读者合并 |
| 5 | 🔧 "Kafka 的消息丢失要按 2019 年的配置手册去防" | 现在有 **幂等 producer（`enable.idempotence`，KIP-98）+ 事务 API + `read_committed` + `exactly_once_v2`**，配合 `acks=all`、禁 unclean election、精确一次语义已可落地。原书的分析仍对（根因不变），但**解法已经现代化** |
| 6 | 🔧 "KRaft 还没做，ZooKeeper 会一直依赖下去" | **KIP-500 的 KRaft 已 GA**（Kafka 3.3 起可用、3.5 稳定），Kafka 正在彻底去掉 ZooKeeper 依赖；这恰好是本书讲 Paxos/Raft/Zab 的现实交点 |
| 7 | 🔧 本书未覆盖 Multi-Raft | 单组共识不是 2026 年的工程形态；分片 + 调度才是。读 Raft 要往前走一步看 `tikv/tikv` 的 region 调度 |
| 8 | 🔧 本书未覆盖成员变更 | 论文面：Raft《Reconfiguration》USENIX ATC 2016；工程面：ZooKeeper 3.5+ 的 `--reconfig`、etcd 的 membership API。离线扩缩容不是现代共识组件的用法 |
| 9 | 🔧 本书未覆盖「一致性读 / 租约」 | leader lease 是 Raft 工程实现的关键且争议最大的部分，Jepsen 的实测正是打在这里 |
