## 核心精讲

### 14.1 "伪"分层

原书对"伪分层"的批评非常直接：很多系统按 `controller / service / dao` 切三刀，看起来是三层架构，**实际上只是把文件放在三个目录里**。判断标准只有一个：

```
如果我把 service 层换成另一个实现，controller 与 dao 需要改吗？—— 需要，那这就是伪分层。
```

真分层的三条判据：

1. **依赖方向单向**：外层依赖内层，内层**不认识**外层（没有反向调用、没有到 controller 的回调）；
2. **契约稳定**：层与层之间靠接口通信，接口先设计再实现；
3. **可独立演化**：某一层可以被替换（如换 ORM、换 RPC 框架）而不波及其他层。

教学示意（伪码，非可运行）：

```
// 伪分层：service 里出现了 web 概念，反向依赖已发生
class OrderService {
   display() { return webContext.render(...) }   // 越界
}

// 真分层：契约先于实现
interface PaymentGateway { boolean pay(OrderId, Money); }
class OrderService { private PaymentGateway gw; ... }
```

> 判断"伪分层"最有杀伤力的手段是问一句：**这一层能否被另一个团队独立重写？** 不能，就还不是边界。

### 14.2 边界思维

原书的顺序是「先划边界，再设计内部」。原因：内部设计错了可以重构，边界错了只能拆散重来。

边界的来源（按优先级）：

1. **组织结构**（康威定律的正面用法）：团队边界 → 系统边界；
2. **业务能力**（见 13 章）：能力边界比功能边界稳定；
3. **变更频率**：频繁一起变更的东西应该在同一个边界内（DCI 的 "classifies objects by their behavior in a particular context"）；
4. **数据主权和隐私**：涉及个人信息、资金、合规数据的边界通常不可跨服务泄露。

🔧 2026 年的补充：**边界的验收方式**是在生产环境画"调用图"——用链路追踪（OpenTelemetry / `openzipkin/zipkin` ≈17.5k★）观察实际调用关系，与设计的边界图比对。多数团队的问题不是"没设计边界"，而是"设计的边界从未被执行过"。

### 14.3 系统化思维

要点三条：

- **局部最优导致全局最优的失败**：给每个子系统都加一层缓存，端到端延迟反而可能上升（缓存一致性成本 + 瀑布式失效）；
- **要优化的是端到端**：用 **OLP（Operation Level Performance，操作级性能）** 而非 "component level performance" 做决策；
- **反馈回路**：系统行为由信息流与决策流构成。改进反馈速度（监控 → 决策 → 行动）的收益常大于单个组件的优化。

教学示意（伪码，非可运行，仅表达结构）：

```
end_to_end_latency = 生产 + 传输 + 处理 + 排队 + 校验
# 只优化处理时间，排队与校验常占大头 → 局部最优陷阱
```

### 14.4 利益相关者分析

原书把利益相关者（Stakeholder）分两类，这是可以直接填进表格的形状：

| 类型 | 定义 | 典型代表 |
| --- | --- | --- |
| **Affected by**（受影响） | 系统的结果会影响他们 | 一线客服、运营、财务、最终用户 |
| **Affects**（影响） | 他们的行为会改变系统 | 产品经理、上游部门、监管、供应商 |

操作建议：

- 每个需求都列出 **Affected by** 名单，逐个问"这个变更对你是好是坏"，因为**感受不一致的需求才有争论价值**；
- 冲突时按**利益**排序，而不是按**职级**或"谁先提"；
- 写需求时把"我们假定谁会用它"写清楚，这就是最初版的利益相关者假设。

### 14.5 非功能性需求分析（以终为始）

原书强调 NFR 必须"以终为始"——即先想清楚**验收场景**，再推导约束。一份可验收的 NFR 长这样（教学示意，非规范）：

| 类别 | 反面写法（无效） | 正面写法（可验收） |
| --- | --- | --- |
| 性能 | "响应要快" | 读接口 p99 ≤ 200ms，QPS ≥ 3000（压测电压测） |
| 一致性 | "数据要一致" | 扣款操作线性一致；订单详情陈旧 ≤ 2s |
| 可用性 | "高可用" | 月度可用率 ≥ 99.95%；降级方案在依赖全挂时仍可下单（只读） |
| 安全 | "要安全" | 支付接口通过 PCI-DSS 4.0；密钥不出 HSM |
| 可维护性 | "要易维护" | 新同学可在 2 周内独立完成一次常规发布；关键决策有 ADR 记录 |
| 可观测 | "要有监控" | 关键路径 100% 覆盖 trace；告警可定位到服务+接口 |

🔧 2026 年的一条经验：**NFR 必须有 owner 和度量方式**。写"as many nines as possible"没有任何工程价值；而"99.95% 可用 + 明确列出牺牲的功能"才是有约束力的承诺。

### 14.6 视角（横看成岭侧成峰）

原书的比喻来自苏轼。架构文档的正确形态是多视图（4+1 的来源）：

| 视图 | 回答的问题 | 受益者 |
| --- | --- | --- |
| 逻辑视图 | 系统是哪些构件、什么关系 | 开发者 |
| 进程视图 | 运行时并发与通信 | 集成/运维 |
| 开发视图 | 源码/模块组织 | 开发者 |
| 物理视图 | 部署到哪些机器 | 系统工程师 |
| 场景（+1） | 关键用例如何被支持 | 所有人 |

🔧 今天的现实版本就是 **C4 模型**（Context / Container / Component / Code，c4model.com）：四层正好对应上面四个视图，且更强调"给谁的图就画到哪一层"。想用图即代码的方式维护它，可用 `plantuml/plantuml`（≈13.3k★）、`mermaid-js/mermaid`（≈90.4k★）与 `structurizr/java`（≈1.1k★）这类工具。

### 14.7 抽象

抽象的定义（教学示意，非可运行）：

```
抽象 = 选择"忽略什么" + 稳定地"承诺什么"
```

- 抽象层级越高，能复用但粒度越粗；越低越具体但复用越差；
- 抽象的错误成本极高：选错抽象层级后，**每一处修改都会被这一层级的粒度放大**；
- 好的抽象能"让错误不发生"，而不是"让错误可以被发现"。

### 14.8 建模

建模是把抽象固定下来的动作。业务架构阶段常用的四类模型：

| 模型 | 用途 | 语言/工具 |
| --- | --- | --- |
| 业务流程 | 端到端流程与时间线 | BPMN、 swimlane 图 |
| 领域模型 | 领域对象与不变式 | 类图、限界上下文图 |
| 状态模型 | 状态流转与合法事件 | 状态机图（Statechart） |
| 数据模型 | 数据结构与关系 | ER 图（见本书第 6 章） |

🔧 建模的**价值在协作**：原书与 2019 年的工业实践都指向同一个结论 —— 用**事件风暴**（Event Storming）这类"一次性工作坊"把建模做成一次多人共创，产出的统一语言会自然变成代码里的命名。建模若是单人闭门画图，代码与图脱节只是时间问题。

### 14.9 正交分解

原书的核心主张：**分解要"正交"** —— 一次只改一个维度，改动的影响面应只落在一条轴上。

判据（Parnas 1972 的准则）：

- **信息隐藏**：模块边界对应"可能变化的决策"，而不是"执行步骤"；
- **变更轴数量**：一个模块应当只对应**一条**变更轴（如"存储引擎"对应迁移轴，"结算策略"对应业务规则轴）；
- **耦合/内聚**：耦合要低而明确，内聚要高且语义一致（Constantine & Yourdon 的耦合/内聚度量）；

教学示意（伪码，非可运行）：

```
// 非正交：一个模块同时承担"规则"与"存储"两轴
class PriceCalculator { readDB(); applyRule(); writeDB(); }

// 正交：拆成策略 + 存储，两轴独立演化
interface PricingRule { Money calc(Order); }
interface PriceRepository { Price load(OrderId); void save(Price); }
```

> 这份正交清单的源头是 Parnas《On the Criteria To Be Used in Decomposing Systems into Modules》（CACM 1972），40 多年后依然是"如何切分"的第一性原理。

## 近年研究与工业界开源实践（2015–2026）

- **C4 模型成为文档主流**：`structurizr/java`（≈1.1k★）与其 DSL 让 C4 图成为**代码一样的产物**（版本化、可 diff）；`plantuml/plantuml`（≈13.3k★）、`mermaid-js/mermaid`（≈90.4k★）让图直接进 Markdown。
- **ADR 成为决策载体**：`npryce/adr-tools`（≈5.7k★）、`thomvaill/log4brains`（≈1.6k★）。ADR 的价值正对应 14.5 的"可验收"——决策有了日期、背景、选项、后果，NFR 才不会被遗忘。
- **架构度量化**：`sonarsource/sonarqube`（≈11.0k★）提供重复度、耦合、测试覆盖等指标；`openzipkin/zipkin`（≈17.5k★）与 OpenTelemetry 提供"真实调用边界"，用于校验 14.2 的边界假设。
- **战略 DDD 与事件风暴的工业化**：DDD Crew 发布的限界上下文/上下文映射实施手册、事件风暴工作坊模板，把 14.8 的"建模"从个人技能变成团队仪式。
- **大语言模型进入建模环节**：2023 年后，用 LLM 从代码生成 C4/PlantUML 图、从需求草稿抽取实体与关系，已成为常见的提效手段；但要警惕它放大"伪分层"——**模型不会替你做边界决策**。
- **架构治理从文档转向流水线**：把 ADR、C4 图、依赖约束检查（如 ArchUnit 类工具）放进 CI，是 2020 年后最有效的一条"让边界被执行"的通路。

## 常见误区与本书需修正之处

| # | 误区 | 修正（含 2026 视角） |
| --- | --- | --- |
| 1 | "分层就是三层目录" | 分层看依赖方向；判断法是"这一层能否被另一团队独立重写" |
| 2 | "边界先按技术分层划" | 边界优先服从组织结构与业务能力；技术边界是结果不是原因 |
| 3 | "多写几张图就代表多视角" | 每张图必须写明**给谁看、回答什么问题、到第几层**；不给受众的图是噪音 |
| 4 | "NFR 写进文档即可" | NFR 必须有 owner、度量方式、验收场景；否则它就是形容词 |
| 5 | 🔧 本书未覆盖"边界从未被执行"的系统性风险 | 2020 年后的主流做法是把边界约束**放进 CI**：依赖检查、调用图比对、契约测试 |
| 6 | 🔧 本书未覆盖架构决策记录（ADR） | 2011 年 Nygard 提出的 ADR 在 2015 年后成为标准实践；它是"以终为始"的载体：写下选项与后果 |
| 7 | 🔧 本书未覆盖 C4 模型 | C4（Context/Container/Component/Code）是 4+1 的现代简化版，配合图即代码工具已相当成熟 |
| 8 | 🔧 本书未覆盖"架构文档版本化" | 文档应随仓库一起版本化并参与 Code Review；散落在 Wiki 上的架构图必然腐烂 |
| 9 | 🔧 本书未覆盖"LLM 辅助建模"的边界 | 可以自动生成图，但**边界决策仍必须由人做**，否则复杂度只是被更快地复制 |
