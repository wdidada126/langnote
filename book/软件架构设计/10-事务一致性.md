# 第 10 章 事务一致性：分布式事务解决方案汇总

> 原书第 10 章「事务一致性」（P138–152），对应 10.1「随处可见的分布式事务问题」与 10.2「分布式事务解决方案汇总」的 8 个小节（2PC、最终一致性、TCC、事务状态表、对账、弱一致性+状态补偿、重试+回滚+报警+人工修复、总结）。
> 本章的立场是**工程立场的**：不追求完美的强一致，而追求「可解释、可观测、可修复」的一致性。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 10.1 随处可见的分布式事务问题 | 跨库/跨服务/跨异构存储的写放大与失败形态 | 分布式的本质是**失败是常态**，超时 ≠ 失败，这是所有方案的共同前提 |
| 10.2.1 2PC | 协调者/参与者两阶段、阻塞与单点故障 | 强一致但吞吐低、可用性差，**只在少数场景可用** |
| 10.2.2 最终一致性（消息中间件） | 本地消息表 / binlog 订阅 / 事务消息 | 吞吐最高、**侵入业务**，无法回滚，需要幂等兜底 |
| 10.2.3 TCC | Try/Confirm/Cancel 三接口与业务资源预留 | 把一致性下放到业务层，性能可控，但三大坑（空回滚/悬挂/幂等）必须处理 |
| 10.2.4 事务状态表+重试+幂等 | 调用方本地状态机 + 接收方幂等键 | **最通用的一档**，成本在中台而非框架 |
| 10.2.5 对账 | 以可信源为准的双向/单向对账与差异修复 | 「最终一致」的**兜底验证手段**，不是主链路 |
| 10.2.6 弱一致性+状态补偿 | 只保证状态最终正确（订单状态流转等） | 幂等操作 + 补偿任务，替代事务 |
| 10.2.7 重试+回滚+报警+人工修复 | 退避重试、告警分级、订正平台 | 承认人会犯错，**可人工介入**是可追认的架构属性 |
| 10.2.8 总结 | 7 种方案的横向对比与选型顺序 | 先「避免分布式事务」，再「柔性一致」，最后才考虑强一致 |

## 核心精讲

> ⚠️ 以下为**教学示意**，不参与构建，仅用于说明算法/机制的结构，不是任何项目的可直接运行代码。

### 10.1 先认清失败形态，再谈方案

原书开篇强调「随处可见」，指的是同一个业务动作往往要写多个数据源：

```
下单 = 订单库写入 + 库存库扣减 + 账户库扣款 + 积分累加 + 消息投递（给搜索/风控/推荐）
```

在这种放大下，失败形态只有四种，其余都是它们的组合：

- **部分成功**：前面的写成功了，后面的失败；
- **超时未知**：请求没回来，但对方**到底提交没有不知道**（这是 2PC 阻塞与幂等问题的根源）；
- **部分失败后重试**：重试本身可能重复生效，产生**副作用**；
- **成功但通知失败**：数据对了，下游没拿到（消息丢失）。

🔧 2026 年补充的一条经验：**先做故障注入再上生产**。上面四种形态若没有在压测/演练中被真实触发过，所谓「最终一致」只是纸面承诺。

### 10.2.1 2PC（Two-Phase Commit）

阶段划分：

1. **投票阶段（Prepare）**：协调者向参与者发 `prepare`，参与者写 undo/redo 日志、锁定资源、返回 `yes/no`；
2. **提交阶段（Commit/Rollback）**：协调者根据投票结果下发全局指令，参与者执行并在最后阶段释放锁定。

问题清单（原书重点）：

- **同步阻塞**：参与者在 prepare 后到收到全局指令前，资源一直被锁 → 吞吐随参与者数量线性劣化；
- **协调者单点**：协调者宕机 → 参与者永远拿不到指令，只能靠**超时后自杀式中止**（仍有不一致窗口）；
- **数据不一致（脑裂）**：协调者在 commit 到一半时宕机，收到 commit 的参与者提交了，没收到的回滚了；
- **网络分区**：分区期间无法形成多数派。

配套的两种改良必须说清楚：

- **3PC（三阶段提交）**：引入 PreCommit + 参与者超时自主决策，**减少阻塞**，但在网络分区下依然可能产生不一致。它降低了「永久阻塞」的概率，没有消灭「不一致可能」。
- **协调者 Paxos 化 / 协调者多副本**：把协调者本身变成高可用组件（etcd/ZooKeeper 选主 + 日志），这是工业界最常见的一种「改良」，本质是**与 11 章的共识算法联用**。

教学示意（伪码，非可运行）：

```
coordinator:
  write(prepare_log)          # 先落盘，保证可恢复
  r = [p.prepare(x) for x in participants]
  if all(r == YES):
     write(commit_log); [x.commit() for x in participants]
  else:
     write(abort_log);  [x.rollback() for x in participants]
```

🔧 **2PC 的现实归宿**：JTA/XA 在**同构单集群**的本地事务 + 少量参与者场景仍可用（如 MySQL XA、JDBC 的全局事务）；一旦跨越异构存储（MySQL + Redis + ES + 第三方 HTTP 接口），XA 就完全失效，必须退回到柔性事务。

### 10.2.2 最终一致性（消息中间件）

三种落地形态：

| 形态 | 机制 | 典型实现 |
| --- | --- | --- |
| 本地消息表 | 业务库与「消息表」在同一本地事务里写入，后台扫描投递 | 自研、Spring 生态常见 |
| binlog 订阅 | 数据库变更通过 CDC 投递到 MQ，下游消费 | Canal / Maxwell / Debezium |
| 事务消息 | 半消息 → 本地事务 → 提交/回滚（回查本地状态） | Apache Rocketmq（原书 2019 年时该特性尚不成熟） |

共有的前提：**消费端必须幂等**（否则重试即出错）。

优点：吞吐高、与业务解耦；缺点：链路变长、调试困难、无法回滚上游、消息顺序与堆积问题要单独处理。

### 10.2.3 TCC（Try-Confirm-Cancel）

TCC 把资源操作拆成三段，隔离性由**业务自己**实现：

- **Try**：预留业务资源（冻结库存、预扣款）；
- **Confirm**：正式提交预留资源（要求幂等）；
- **Cancel**：释放预留资源（要求幂等，且必须能空执行）。

教学示意（伪码，非可运行）：

```
try:     freeze_stock(orderId, 1); freeze_account(orderId, 99)
confirm: deduct_frozen(orderId, 1); deduct_frozen(orderId, 99)
cancel:  unfreeze_stock(orderId, 1); unfreeze_account(orderId, 99)
```

三大坑（工程上最难的部分）：

1. **空回滚**：Try 没成功（或根本没收到），全局却要 Cancel → Cancel 必须能识别「无预留可退」；
2. **悬挂**：Cancel 先到，Try 后到 → Try 必须检查「本事务已取消」并拒绝执行；
3. **幂等**：Confirm/Cancel 因超时重复调用 → 必须带事务 ID 幂等。

与 2PC 的本质区别：TCC 是**应用层 2PC**，资源锁由业务语义保证而非数据库锁，因此可以做到「分散锁定、最终提交」，吞吐远高于 XA。

### 10.2.4 事务状态表 + 调用方重试 + 接收方幂等

这是原书最认可的一档，也是最"土"但最通用的一档。结构：

1. 调用方在本地事务中写一条 `tcc_status`（或 `invocation_log`）记录：全局事务 ID、目标接口、参数、初始状态 `INIT`；
2. 调用接口；
3. 写入调用结果（`SUCCESS` / `FAIL_RETRYABLE`）；
4. 异步线程（或定时任务）扫描未完成记录 → 重试推进；
5. 接收方用**全局幂等键**（唯一索引或 Redis `SET key nx`）保证同一请求只生效一次。

教学示意（伪码，非可运行）：

```
def invoke_with_retry(ctx, target, payload):
    with db.begin():                       # 与业务同库，保证原子
        ctx.status = 'INIT'
        db.insert('tx_status', ctx)        # 全局事务 ID + 重试次数
    for attempt in range(N):
        if ok = target.invoke(payload, idempotency_key=ctx.txid):
            db.update('tx_status', status='DONE'); return ok
        backoff(attempt)                   # 指数退避 + 抖动
    db.update('tx_status', status='FAILED') # 转人工/补偿
```

幂等设计的两个层次不要混淆：

- **接口幂等**：同一 key 重复调用产生同样效果（靠唯一索引 + 状态判断）；
- **消息幂等**：MQ 的 at-least-once 导致重复投递，靠业务键去重。

### 10.2.5 对账

对账是「最终一致性」的**校验装置**，不是主链路。要点：

- **先定义可信源（source of truth）**：通常是账务/订单库，下游是不可信方；
- **双向 vs 单向**：有下游流水表则双向对账，没有只能从主库造对账文件单向核对；
- **三类差异**：漏处理（下游没收到）、多处理（下游收到了但主库没有）、错处理（都有一份但金额/状态不一致）；
- **时效**：原书成书于 2019 年，主流是 T+1 对账；2026 年的现实是**实时/准实时对账**（流批一体 + 分钟级 diff），T+1 只作为兜底。

### 10.2.6 弱一致性 + 基于状态的补偿

这一档放弃了「操作原子」，只保证「状态最终正确」。典型是订单：

```
待支付 ->(超时) 已关闭 -> 释放库存/预扣
待支付 ->(支付成功) 已支付 -> 扣库存/扣款 -> 已发货
```

做法是把业务规则写成**状态机 + 补偿任务**，由定时任务扫描超时记录做收口。原书把它称为「妥协方案」，我认为它才是电商/履约领域使用频率最高的一档。

### 10.2.7 重试 + 回滚 + 报警 + 人工修复

这是最后一道防线，原书特别强调「报警 + 人工修复」的合理性 —— 承认系统不完美，为**人的介入**留出通道（这与 14 章的非功能性需求、17 章的风险把控同源）。

工程要点：

- **重试**：区分可重试/不可重试错误；指数退避 + 随机抖动；带熔断，避免重试风暴把下游打垮；
- **回滚**：能自动补偿就自动补偿，补偿脚本必须**先声明后执行**（审批 + 幂等 + 不重复）；
- **报警**：分级（电话/即时消息），可自动修复的自愈不打扰人，无法自愈的必须到人；
- **人工修复**：提供**数据订正平台/后台工具**，而不是让工程师登录服务器跑 SQL。

### 10.2.8 总结：方案对比与选型顺序

| 方案 | 一致性强度 | 吞吐 | 业务侵入 | 典型代价 |
| --- | --- | --- | --- | --- |
| 2PC/XA | 强一致 | 低 | 无（框架层） | 阻塞、单点、DB 依赖 |
| 最终一致性（MQ） | 最终一致 | 高 | 中（幂等+投递） | 调试难、无法回滚 |
| TCC | 最终一致（应用定义） | 高 | 高（三接口） | 三坑 + 代码量 |
| 状态表+重试+幂等 | 最终一致 | 中高 | 中 | 中台代码 |
| 对账 | 验证手段 | — | 中 | 差异修复成本 |
| 弱一致+状态补偿 | 状态级最终一致 | 高 | 中 | 状态机复杂度 |
| 重试+回滚+报警+人工 | 事后一致 | 高 | 低 | 人力 |

**选型顺序**（原书结论的现代版）：

1. **能不用分布式事务就不用**：合并数据源、同库事务、把跨服务调用改成事件通知；
2. 用**最终一致性**替代强一致；
3. 只有涉及**资金/账务**时才上 TCC 或强一致（此时可用性可以适度让步）；
4. 无论哪一档，都要配**可观测**（链路追踪 + 事务状态表 + 对账结论）。

## 版本演进

| 时期 | 代表做法 | 特征 |
| --- | --- | --- |
| 1980s–1990s | 2PC / 事务监控（TP monitor）+ XA | 强一致、集中式、昂贵 |
| 2000s | JTA + Spring 声明式事务 | 同构 JDBC 场景的工程化 |
| 2007 起 | Pat Helland 的「分布式事务已死」思潮 | 一致性下放到应用，TCC/消息/幂等成型 |
| 2010s | Alibaba 中间件（Seata 前身）、RocketMQ 事务消息 | 大量互联网公司的柔性事务实践 |
| 2016–至今 | Seata（AT/Saga/TCC）、Temporal/Cadence 工作流编排 | 框架化、声明式、可重放 |
| 2017–至今 | NewSQL（TiDB / CockroachDB / YugabyteDB） | 把分布式事务压回数据库内部 |
| 2020s | 确定性事务（FoundationDB、Calvin 思路）、事件驱动 + 事件溯源 | 用「先定序再执行」规避分布式提交 |

🔧 **重要趋势**：2019 年本书出版时，「分布式事务」几乎只能靠中间层解决；2026 年的主流答案是——**能上分布式数据库就上**（省掉整个中间层），不能上才退回到柔性事务。

## 近年研究与工业界开源实践（2015–2026）

- **框架化TCC/AT**：`seata/seata`（≈26.0k★）提供 AT（基于 undo log 的自动补偿）、TCC、Saga、XA 四种模式，是国内 2019–2023 年分布式事务的事实标准。
- **工作流即补偿**：`temporalio/temporal`（≈23.3k★）与 Uber 的 Cadence 把 Saga 的补偿逻辑写进 workflow 代码，靠**确定性重放**实现「随时中断、随时恢复」，比手写状态表可靠得多；uber/cadence 亦可参考。
- **把事务压回数据库**：`pingcap/tidb`（≈40.6k★，Percolator + 乐观/悲观事务）与 `cockroachdb/cockroach`（≈32.5k★，HLC + 串行化快照）在 2019 年后迅速成熟，跨机房强一致成为开箱能力，直接替代了大量自研柔性事务。
- **事务消息工业化**：`apache/rocketmq`（≈22.6k★）的事务消息（半消息 + 本地事务回查）在 2019 年前后补齐，`apache/kafka`（≈33.8k★）通过 Kafka Transaction API（idempotent producer + `read_committed`）提供「事务性生产」，消费端仍需自己过滤。
- **CDC 与实时对账**：`debezium/debezium` 与 `apache/flink` 让「binlog → 下游」变成实时通道，T+1 对账逐步被「分钟级对账」替代；`apache/iceberg`（≈9.3k★）等湖格式让对账可以直接在 lake 上做集合 diff。
- **一致性检验的利器**：`jepsen-io/jepsen`（≈7.5k★）的线性一致性检测被反复用于检验各种「最终一致」方案是否真的正确，本章所有方案的语义都应接受一次 Jepsen 式拷问。
- **确定性事务**：Apple FoundationDB 以纯 OCC + 确定性模拟测试著称（参考 `apple/foundationdb`），用「先定序再执行」消解分布式提交的并发不确定性。

## 常见误区与本书需修正之处

| # | 误区 | 修正（含 2026 视角） |
| --- | --- | --- |
| 1 | "2PC 能保证分布式强一致" | 协调者单点、commit 半途宕机、网络分区都会造成**不一致或永久阻塞**；3PC 只减阻塞不消灭不一致 |
| 2 | "最终一致性可以随便用" | 必须先写明**客户端能看到什么**（读己之写 / 单调读 / 因果），否则"最终一致"对用户就是"偶发读到旧值" |
| 3 | "幂等加个 Redis key 就行" | 幂等要业务语义 + 状态判断；TTL 到期后又收到一次旧消息就会重复生效。正确做法是**唯一索引 + 状态机 + 幂等键与业务键绑定** |
| 4 | "对账只是核对数据" | 对账的价值在**差异修复通道**：发现容易，修复难。没有自动对平/订正平台的对账等于没有 |
| 5 | 🔧 本书未覆盖「框架替代」浪潮 | 2026 年的首选路径是**分布式数据库/NewSQL**（TiDB、CockroachDB、OceanBase）直接提供跨行跨表事务；中间层柔性事务更多用于**跨组织/异构/第三方接口**场景 |
| 6 | 🔧 本书未覆盖 Saga 的编排分歧 | 补偿现在分「编排式（orchestration，Temporal/Cadence）」与「协作式（choreography，事件链）」两派，前者可观测性碾压后者，已成为新主流 |
| 7 | 🔧 本书未覆盖确定性事务 | Calvin / FaunaDB / FoundationDB 的「先定序再执行」把分布式提交从运行时挪到定序阶段，是 2PC 问题的一条真实出路 |
| 8 | 🔧 本书未覆盖「对账的实时化」 | 2019 年 T+1 是主流，2026 年要求分钟级；延迟对账意味着差异窗口内的错误~用户已经看到 |

## 与其他章 / 其他书的联系

- **第 6 章 6.2.5「分布式事务」/ 6.4「事务与锁」/ 6.5–6.6「Redo/Undo」**：本章的 2PC、TCC 都建立在单机事务之上；不理解 undo/redo 与 isolation level，就无法判断柔性事务的语义边界。
- **第 8 章 8.2.4「读写分离（CQRS）」**：CQRS 与「最终一致性」是同一枚硬币的两面 —— 引入读模型就必然放弃强一致。

- **第 17 章 不确定性与风险把控**：「重试+回滚+报警+人工修复」正是风险把控在一致性领域的落地。
