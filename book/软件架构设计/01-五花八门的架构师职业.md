# 第1章 五花八门的架构师职业

> **一句话**：第 1 章先把"我是谁"这个问题解决掉。**架构师不是一个头衔，而是一组决策域**；判断一个人是不是架构师，不看他管几个人，看他为哪些"不得以而不这样做"的约束负责。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 架构师职业分类 | 系统架构师 / 平台架构师 / 业务架构师 / 数据架构师 / 前端架构师 / 运维架构师… | 分类的**真正依据是决策域（为哪些约束负责）**，不是职级也不是权力大小 |
| 1.2 架构的分类 | 技术架构（计算机功底那一套）与业务架构（业务目标那一套） | 二者是**两套语言、两个利益相关者集合**，只会一套就叫"技术好但做不了架构" |
| 1.1 的隐藏前提 | 架构师的价值 = 减少决策数量而非增加 | 一个每天做 50 个重大决策的架构师，通常是把决策推给了别人 |
| 1.2 的隐藏前提 | 架构必须**可沟通** | 说不清的架构不是没做，是没做出来，只是没被看见 |

## 核心精讲

> 以下为**教学示意，不参与编译、不参与任何构建**，仅用于说明概念关系。

**示意 1：按"决策域"而不是"职级"来切分架构师类型**

```text
                    为"技术约束"负责                     为"业务约束"负责
                            |                                   |
        +-------------------+                                   +-------------------+
        |                                                                            |
  系统/平台架构师                                                              业务架构师
   - 谁做技术选型                                                          - 谁划分业务边界
   - 谁定标准与规范                                                        - 谁定义"这个业务是什么"
   - 谁对容量/性能负责                                                     - 谁决定"不做什么"
        |                                                                            |
        +-------------------+                                   +-------------------+
                            |                                   |
                    数据架构师 / 安全架构师 / 前端架构师 / 测试架构师    | 技术架构师与业务架构师
                            |                                   | 「融合」的地带
                    都是"某类约束的专职负责人"                    v
                                                         DDD / CQRS / 技术选型要服从业务语言
```

**示意 2：一次架构决策的最小记录（文本模板，非代码）**

```text
决策：为什么订单库的订单表按 user_id 拆分而不是按 order_id 拆分？
- 背景：用户维度查询（我的订单）占订单读流量的 68%
- 备选方案：A 按 order_id 哈希 / B 按 user_id 哈希 / C 按时间范围
- 决策：B
- 理由：读多写少的查询集中在用户维度；C 会导致"历史数据冷热不均 + 扩容困难"
- 代价（显式写出来才叫决策）：按 order_id 的全局查询与跨用户 JOIN 无法在本地完成
- 补偿措施：异步宽表 + 对账（见 06-数据库.md 的分布式事务一节）
```

> 这个模板的价值在于**把"代价"和"补偿"写成必填项**。原书第 1 章没有给出这样的工具，但整本书的每一章其实都在示范"带代价的决策"。

**示意 4：架构师的时间去向（原书没写，但决定了他能不能做成事）**

```text
  典型的一周（健康状态）：
    40%  写代码 / 做 PoC（保持手感，也验证方案可行性）
    25%  讨论与评审（需求澄清、方案对齐、代码评审）
    20%  推进落地（帮团队解决阻塞、拉通缺的依赖）
    15%  思考与书写（架构决策记录、技术规划）

  典型的一周（不健康状态）：
    60%  救火（别人留下的坑）
    25%  重复解释同一个决策（因为没记录、没沉淀成文档或工具）
    15%  写代码
    ⇒ 不健康状态的根源通常是：决策没有被记录，于是被反复重述
```

**示意 5：识别"伪架构师"的三个信号**

```text
  ① 所有决策都指向"技术上更先进"，从不提"业务上更划算"
  ② 无法说清一个方案"在什么条件下不成立"（答"任何时候都成立" = 没想过）
  ③ 一笔带过代价："这个方案有点代价，但总体是好的"
     —— **凡是用"总体是好的"收尾的方案，通常没有代价清单**
```

**示意 6：三个容易被忽略的职业问题**

```text
  ① 架构师要不要写代码？  要，而且必须写。
       理由：保持手感、验证方案可行性、在评审时拥有真实发言权。
       长期不写代码的架构师，方案会越来越脱离实现约束。

  ② 架构师与产品经理的边界？
       架构师：**在业务给出的约束内，把技术实现做到最优**；越界改需求 = 同时承担两个角色的失败风险。
       但架构师**必须参与需求讨论**——需求决定的成本，往往高于技术优化省下的。

  ③ 架构决策如何"去职级化"？
       靠三样东西：方案本身的说服力、对代价的诚实表述、记录的完整性。
       任何一个缺失，方案就会被"先做了再说"。
```

**示意 3：职业分类的四个切分轴（比"系统/应用/业务"更有解释力）**

```text
  轴① 按**决策域**：对哪些品质属性负责（性能 / 可用性 / 扩展性 / 安全 / 成本）
  轴② 按**组织层级**：平台层（跨团队标准） vs 应用层（单系统内部）
  轴③ 按**时间尺度**：长期架构（1 年+，如技术栈演进） vs 短期设计（1 季内，如模块划分）
  轴④ 按**交付形态**：设计文档 vs 可执行规范（ADR / 架构守护规则 / 平台默认路径）

  一条有用的推论：
      大多数"架构师之间的沟通困难"，其实是**不在同一条轴上**造成的
      （平台架构师在谈时间尺度，应用架构师在谈交付形态）
```

> 原书 1.1 用的是"职位式"分类（系统/应用/业务/数据/前端），简单但容易失真；上面四个轴更适合用来**对齐两个不同角色到底在谈什么**。

**示意 3b：架构师能力雷达（自评用的五个维度）**

```text
计算机功底（4/5） #################
业务理解（2/5）    ######                 <- 最容易被严重低估的一格
设计表达（3/5）       #########
推动落地（3/5）        ##########
权衡取舍（4/5）           ##############
```

> 行业里失败的架构师，画像高度一致：**前四格满、最后一格空**，或者反过来**技术格虚高、业务格长期空白**。

## 版本演进

| 版本 / 时间 | 与本章相关的变化 |
| --- | --- |
| 2019（原书基线） | 架构师分类以"系统 / 应用 / 业务"三段式为主；架构师的主要产出是**设计文档**与**技术选型** |
| 2020–2021 | **云原生化**：架构师的一部分决策从"写代码"转移到"选托管服务能力"，K8s 成为事实平台层，SRE 从运维中独立成一支 |
| 2022–2023 | **Service Mesh 普及**：服务间治理（熔断/重试/超时）从代码下沉到基础设施，"平台架构师"与"应用架构师"的边界第一次被制度性切分 |
| 2020 | **架构守护概念提出**（Building Evolutionary Architectures，Ford / Hughes / Olsson，2017 提出，2020 年第二版完善）：把架构约束写成" fitness function"并可自动执行，是本章"职业定义"在技术侧的一次升级 |
| 2023–2025 | **LLM 进入研发流程**：编码助手承担了大量"模板级"设计执行，架构师的注意力进一步上移到**边界划分与契约设计** |
| 2024–2026 | **平台工程（Platform Engineering）体系化**：内部开发者平台把"标准"做成自助服务，架构师从"写方案的人"变成"**定义平台默认路径与逃生舱口的人**" |
| 2026 | 主流共识：架构师的核心产出是**可执行的决策记录（ADR）与边界**，而不是 PPT；"T 型能力"被更严格地理解为**在某一域内足够深，在相邻域内能对话** |

## 近年研究与工业界开源实践（2015–2026）

- **趋势**：架构师角色的重心从"技术选型"滑向"**边界与契约**"。三件标志性事实：① ADR（Architecture Decision Record）成为跨团队通用语言；② 架构守护（architecture fitness function）从理念变成 CI 里的可执行文件；③ 平台工程（Internal Developer Platform）让"标准"从文档变成"自助服务"。
- **工具链（star 为 2026-09-25 用 `gh api` 实测）**：
  - `sonarqube/sonarqube`（**11024★**）：把"架构约束"写成**可执行的规则**（包依赖方向、循环依赖、分层禁止跨层调用），是架构守护最成熟的开源实施路径。
  - `golangci/golangci-lint`（**19398★**）：把命名、分层、错误处理的规范固化到 lint 阶段——**规范如果不进 CI，就只是建议**。
  - `open-telemetry/opentelemetry-collector`（**7596★**）：让"架构可观测"有了统一口径（metrics/logs/traces 一套 SDK），架构师第一次能拿到**跨服务的端到端事实**而不是各系统自报的数字。
  - `openfeign/feign`（**9801★**）：声明式 HTTP 客户端，是"架构师定的契约如何低成本落地"的典型样本。
- **行业事实**：Netflix 的 ADR 实践、Spotify 的"架构 guild + 部落"治理、以及国内阿里/腾讯的"架构评审委员会（ARC）"，共同指向同一件事——**架构师的产出是决策，决策的载体是记录，记录的检验是评审**。
- **三条可直接照做的工程结论**：
  1. **任何跨团队的技术约定，都要有一个"违反时会被 CI 拦住"的形式**。做不到这一点的约定，三个月后必然失效。
  2. **每一个重大决策都要写"如果半年后要改，代价是什么"**。写不出代价的决策，等于没做权衡。
  3. **架构师必须保有一定的写代码时间**。这不是情怀，是保持对实现约束的感知力。
- **一条关于"职业分类"的实用提醒**：原书 1.1 的分型是"职位式"的，简洁但容易失真。真实团队里更有效的切分方式是上面示意 3 的四条轴。**当两个架构师互相听不懂对方在说什么时，通常不是水平问题，而是不在同一条轴上。**

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "架构师是技术职位，管技术就行" | 原书 1.2 已经指出架构分技术架构与业务架构两类；**只做技术架构、不碰业务，等于放弃了架构师一半的决策域** |
| 2 | "有了架构师，开发就不需要懂架构" | 架构决策最终由写代码的人执行；不理解约束的开发者会引入大量"合法但不合意图"的实现 |
| 3 | "架构 = 设计文档" | 文档只是载体。2026 年的检验标准是：**半年后新人能否照着它把约束复述出来** |
| 4 | 🔧 本书未覆盖 | **平台工程 / 内部开发者平台**：架构标准从"文档 + 评审"变成"自助平台的内置默认”；架构师的日常从写方案变成定义平台的默认路径与逃生舱口 |
| 5 | 🔧 本书未覆盖 | **架构守护（fitness function）**：把"分层正确""无循环依赖"做成 CI 门禁，比任何评审会都有效 |
| 6 | 🔧 本书未覆盖 | **架构决策记录（ADR）工具链**：`MADR`、`adr-tools` 一类轻量化模板已普遍化，原书的"架构分类"缺一个**可落地的决策载体** |
| 7 | 🔧 本书未覆盖 | **AI 辅助架构**：2023 之后大量"方案起草"工作可由模型完成，架构师的价值进一步集中到**边界判断与代价取舍** |
| 8 | 🔧 分类过时风险 | 原书的职业分型隐含"单体时代"的组织形态；今天"平台架构师 / 应用架构师 / SRE"三分法比原书的分类更贴近 2026 年的实际岗位 |
| 9 | 🔧 本书未覆盖 | **架构师与 SRE 的职责边界**：原书把稳定性归给架构；2016 年 Google SRE Book 之后，稳定性成为独立职能（错误预算、可靠性目标由 SRE 与业务共同商定）。架构师应负责"设计上的可用性"，SRE 负责"运行上的可靠性" |
| 10 | 🔧 本书未覆盖 | **架构决策的沟通成本量化**：原书假定决策一旦做出就会被执行。实际研究表明，架构失败的常见原因不是决策错误，而是**决策未被真正理解**；因此"读懂一次决策需要几页文档"是评估方案质量的有效指标 |
| 11 | 🔧 本书未覆盖 | **架构师的"退出路径"设计**：原书讲"怎么做架构"，没讲"这个人休假/离职后架构还成不成立"。2026 年成熟的做法是 ADR + 架构守护 CI 一起上，让架构**独立于某个人**而存在——离开任何单个架构师，系统仍能维持约束 |

- 本章是全书的地基：`01 → 02` 讲"我是谁"，`13 → 14 → 15` 讲"业务那一边是谁"，两边在 `15-技术架构与业务架构的融合.md` 汇合。
