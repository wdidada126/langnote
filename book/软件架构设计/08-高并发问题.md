# 第8章 高并发问题

> **一句话**：第 8 章是全书"技术架构之道"的核心，也是被引用最多的一章。它把高并发拆成三类问题（读 / 写 / 读写），给每个问题三条到五条策略。**真正值得记住的不是这八条策略，而是每条策略省的是什么、代价是什么。**

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 8.1.1 高并发读的系统 | 读远多于写，压力落在存储与缓存 | 症状是"连接数不够、QPS 上不去"，解法方向是**让 90% 的读不打到库** |
| 8.1.2 高并发写的系统 | 写远多于读，或写带宽饱和 | 症状是"锁竞争、死锁、日志刷盘跟不上"，解法方向是**削峰 + 分片 + 异步** |
| 8.1.3 读写的系统 | 两类压力同时存在且互相干扰 | 只有 CQRS（读写分离架构）能同时解决，代价是**模型不一致与延迟** |
| 8.2.1 策略1：加缓存 | 本地缓存 → 分布式缓存 → 穿透/击穿/雪崩 | 缓存是解决读问题的第一手段，也是**引入一致性问题的最快方式** |
| 8.2.2 策略2：并发读 | 一次请求并发调用多个下游 | 省的是**串行等待的时间**；代价是**线程池占用翻倍** |
| 8.2.3 策略3：重写轻读 | 改数据结构/减少字段/去 JOIN | 最便宜的一招，也最容易被忽略；**有时加个索引就能减 90% 的耗时** |
| 8.2.4 读写分离（CQRS） | 写模型与读模型分开，读模型可冗余 | 这是高并发读问题的**结构性答案**，也是第 15 章 CQRS 的伏笔 |
| 8.3.1 策略1：数据分片 | 按维度切分到多个库表 | 彻底解决单点容量，代价是 Join 与事务 |
| 8.3.2 策略2：任务分片 | 把大任务拆成可并行的小任务 | 与数据分片的区别：这里拆的是**计算**，不是存储 |
| 8.3.3 策略3：异步化 | 同步改异步、请求入队 | 省的是**用户等待时间**，代价是**实时性与可追踪性** |
| 8.3.4 策略4：批量 | 批量写、批量提交、group commit | 把随机 I/O 变顺序 I/O，是数据库侧最有效的一招 |
| 8.3.5 策略5：串行化+单进程+异步I/O | Redis/Nginx/Go 的经典形态 | 极简模型 + 无锁，性能上限高但**只适合无复杂业务逻辑** |
| 8.4.1 吞吐量、响应时间与并发数 | 吞吐 ≈ 并发 / 响应时间；Little's Law | 三者只能固定其二；压测本质是找拐点 |
| 8.4.2 压力测试与容量评估 | 压什么、压到什么程度、如何换算机器 | 必须压到**饱和点之后**，否则看不到拐点 |

## 核心精讲

> 以下为**教学示意，不参与编译、不参与任何构建**，仅用于说明策略形态。

**示意 1：高并发读的三层缓存与三种失效灾难**

```text
      请求 → ┌ 本地缓存（进程内，纳秒） ── 命中 → 返回
             │    未命中 ↓
             ├ 分布式缓存（Redis，百微秒）─ 命中 → 回填本地 → 返回
             │    未命中 ↓
             └ 数据库（毫秒级）
                                                                     （真实存在的坑）
   ① 缓存穿透：查一个根本不存在的 key，缓存不命中，每次都打到库
        → 解法：缓存"空值" + 布隆过滤器（提前拦掉不存在的 key）
   ② 缓存击穿：某个热点 key 恰好过期，瞬间百万请求同时回源打库
        → 解法：热点 key 永不过期（后台异步更新）+ 互斥重建（single flight）
   ③ 缓存雪崩：大批 key 在同一时刻集体过期，数据库瞬时被打满
        → 解法：过期时间加随机抖动 + 多级缓存 + 限流兜底
```

```text
  多级缓存的实际布局（现代标准形态）：
  ┌────────────┐   ┌────────────┐   ┌────────────┐   ┌──────────┐
  │ 浏览器/CDN │→│ 服务端本地  │→│ Redis 集群 │→│ DB 只读  │
  └────────────┘   └────────────┘   └────────────┘   └──────────┘
       静态资源           进程内              分布式              兜底
```

**示意 2：异步化的三条路径（按"松耦合程度"排序）**

```text
  ① 调用方异步（Future / 回调 / 协程）
       返回值立刻返回，实际工作交给线程池/协程池
       → 省：用户等待时间        → 代价：错误反馈变晚、线程池仍是瓶颈

  ② 请求入队（消息队列削峰）
       写请求全部进 MQ，后端按消费能力匀速处理
       → 省：瞬时峰值            → 代价：延迟（从 ms 到 s 甚至 min）+ 需要幂等

  ③ 纯异步落盘（写缓冲 / group commit）
       先写内存与日志，后台批量落盘
       → 省：I/O 次数            → 代价：宕机可能丢少量数据（需 WAL 兜底）
```

**示意 3：批量写与 group commit（数据库侧收益最大的一招）**

```text
  未批量：  T1 写日志(fs) → 刷脏页   T2 写日志(fs) → 刷脏页   T3 写日志(fs) → 刷脏页
            ⇒ 3 次 fsync + 3 次随机写

  批量后：  T1/T2/T3 的日志攒到 4KB/1 个 IO 单元，一次 fsync，一次连续写
            ⇒ 1 次 fsync + 1 次顺序写   （吞吐提升常达数倍）

  这就是 06-数据库.md 里 redo log 的 group commit，也是 Kafka 的 batch.size / linger.ms 的同一个道理
```

**示意 4：串行化 + 多进程单线程 + 异步 I/O（策略 5 的模型）**

```text
  为什么"单线程"反而快？
    - 没有锁竞争、没有上下文切换、没有 GC 停顿的并发干扰
    - 一个连接对应一个状态机，所有 I/O 都是非阻塞的
    - 天然"按连接排序"，无需处理共享数据结构的并发问题

  极限形态：
    master: accept → 交给 worker
    worker: 单线程 + 非阻塞 + 事件循环（Reactor），无共享状态

  它的天花板：
    ✗ 业务逻辑复杂 → 一旦有阻塞操作，整个 worker 停住
    ✗ 多核利用靠"多进程"而非"多线程"，进程间数据共享困难
    ✓ 所以它是 Redis / Nginx / Memcached 的形态，不是业务服务的形态
```

**示意 5：吞吐、响应时间与并发数的三角关系**

```text
  Little's Law（排队论）：  并发数 L = 到达率 λ × 平均停留时间 W

  推论（容量规划的核心）：
    想降低并发数 L，只有两条路：要么降低 λ（削峰），要么降低 W（让请求更快或更少做事）
    "加机器"只能在 λ 不变的前提下提高系统的饱和点，不会改变拐点形状

  拐点形状：
    利用率 ρ < 0.7    → 吞吐近似线性，延迟缓慢上升
    ρ ≈ 0.8~0.9       → 吞吐接近饱和，延迟开始非线性放大（排队论 M/M/1 的 L = ρ/(1-ρ)）
    ρ > 1             → 队列无界增长，系统"假死"
    ⇒ **把系统跑到 70% 左右的利用率，队列延迟就已经很危险了**
```

## 版本演进

| 版本 / 时间 | 与本章相关的变化 |
| --- | --- |
| 2019（原书基线） | 缓存以 Redis 单实例/哨兵为主；异步化以线程池 + ActiveMQ/RabbitMQ/Kafka 为主 |
| 2018–2020 | **Redis 集群化成为默认**（Cluster 模式 + 代理）；缓存三大问题（穿透/击穿/雪崩）成为面试与实战的固定议题 |
| 2020–2022 | **Kafka 成为异步化主力**：顺序写 + 零拷贝 + 分区并行；同时暴露"消息丢失与错乱"的运维现实 |
| 2020–2023 | **K8s HPA 与弹性伸缩成熟**：容量规划从"买机器"变成"配策略"；Serverless（FaaS）把"峰值应对"部分外包给云厂商 |
| 2022–2024 | **Redis 6.0 多线程 I/O 与 Redis 7 的增强**：单线程模型被打破；同时 Redis 在超大规模下的运维复杂度（bigkey、hotkey、集群扩缩容）成为新瓶颈 |
| 2024–2026 | **新一代消息队列分流**：Pulsar（存算分离、共享订阅）在需要"海量 topic + 多消费模型"的场景挑战 Kafka；**RocketMQ 5.0 的事务消息**为异步化补上了一致性拼图 |

## 近年研究与工业界开源实践（2015–2026）

- **趋势（2015 → 2026）**：高并发的解法重心从"单机压榨 + 堆机器"转向"**多级缓存 + 异步解耦 + 弹性容量**"。三处最实质的变化：
  1. **缓存从"单级"变成"多级"（🔧）**：本地缓存（Caffeine/Go `bigcache`）+ 分布式缓存（Redis Cluster）+ CDN，构成标准三层；缓存三大问题（穿透/击穿/雪崩）成为**必须内置**的防御，而不是事故复盘时的发现。
  2. **异步化的载体从线程池变成消息中间件与流式引擎（🔧）**：Kafka（**33836★**）与 Pulsar（**15339★**）承担削峰，Flink 承担实时聚合，让"异步"从"丢个消息"升级为"一条可重放的数据流"。
  3. **容量规划从"静态预估"变成"动态弹性"（🔧）**：K8s HPA + 云上弹性 + Serverless，让"峰值"不再是采购问题。但要注意：**扩容有延迟（数十秒到数分钟），因此仍需限流兜底**。
- **必须补的一致性事实（🔧）**：
  - **Kafka 的顺序与丢失（对应原书 11.1.1/11.1.2 的论断）**：原书指出"消息会丢、会乱序"，这个判断**在默认配置下是成立的**：`send()` 返回不代表落盘，未回调的异常会丢；`enable.auto.commit=true` 时 consumer 可能在处理完之前就提交了 offset。但**技术现状已可解决**：`acks=all` + `enable.idempotence=true`（幂等 producer，避免 retry 造成重复与乱序）+ 单分区 + `max.in.flight.requests.per.connection≤5`，可以做到"不丢且单分区有序"。跨分区仍无序——**这是选型时必须向业务说清的语义边界**。
  - **RocketMQ 5.0 的事务消息**：把"本地事务 + 半消息 + 回查"标准化，是异步化补上一致性的路径（见 `10-事务一致性.md`）。
- **典型仓库（star 为 2026-09-25 用 `gh api` 实测）**：
  - `redis/redis`（**76472★**）：缓存事实标准；其 Cluster 模式与多线程 I/O（6.0+）是本章策略 1 的现役形态。
  - `apache/kafka`（**33836★**）：异步化的主力载体；源码里 `RecordAccumulator` 的批量与 linger 正是"策略 4：批量"的教科书实现。
  - `apache/pulsar`（**15339★**）：存算分离 + 共享订阅架构，解决 Kafka 在"海量 topic / 多消费模型"下的痛点。
  - `apache/rocketmq`（**22621★**）：国内电商场景的主力消息中间件，事务消息与顺序消息能力最完整。
  - `cloudwego/kitex`（**8051★**）：高并发 Go RPC 框架，连接池与异步调用，直接对应本章"并发读"的策略 2。
  - `grpc/grpc`（**45341★**）：多路复用长连接，是"减少连接数、提高单连接吞吐"的现代答案。
  - `grafana/grafana`（**76907★**）与 `prometheus/prometheus`（**66221★**）：容量评估的闭环——压测之后必须有可见的曲线，否则拐点只是猜测。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "加缓存就能扛高并发" | 缓存引入了**一致性、序列化、失效策略**三重复杂度；缓存失效时的回源风暴往往比原问题更严重 |
| 2 | "异步化 = 不会出问题" | 异步化把问题从"调用失败"变成"消息丢失 / 重复消费 / 顺序错乱 / 难以调试"。**没有幂等设计的异步化是故障放大器** |
| 3 | "并发读就是多线程" | 8.2.2 的并发读消耗的是**线程池和连接数**；在高并发下线程池本身常成为新瓶颈 |
| 4 | "分片一定能解决问题" | 分片选择与热点会决定它是否生效；**单一超热 key 分片后仍在同一实例上**（如爆款商品），需要二级散列或本地缓存 |
| 5 | "串行化 + 单进程就是最快" | 该模型只在**业务逻辑极简**时成立（见 04 章 4.3.4 的 1+N+M）；一旦引入阻塞业务，单线程会整体停摆 |
| 6 | "压测跑到不报错就结束" | 压测的价值在**拐点之后**：饱和点在哪、过载后吞吐是升是崩、降级是否生效 |
| 7 | 🔧 **本书未覆盖：缓存三大问题（穿透/击穿/雪崩）的现代解法** | 原书 8.2.1 只写"加缓存"。2026 年的标准答案是**多级缓存（本地 + 分布式 + CDN）+ 空值缓存与布隆过滤器防穿透 + single flight 防击穿 + 过期时间加随机抖动防雪崩**。这是本章最需要补的内容 |
| 8 | 🔧 **本书未覆盖：Redis 集群与缓存运维现实** | 原书假设 Redis 是可靠的。真实约束包括：bigkey 导致网络拥塞、hotkey 导致单实例 CPU 打满（需要本地缓存或二级散列）、集群扩缩容期间的数据迁移、以及"Redis 不可用就会导致大面积雪崩"的单点问题 |
| 9 | 🔧 **本书未覆盖：Serverless / K8s HPA 与弹性容量** | 原书 8.4 的容量观是"预估峰值 → 准备资源"。2026 年的默认答案是**弹性伸缩**，但要注意三点：扩容有延迟、需要有上限与冷却、扩容前必须先有限流，否则"雪崩式扩容"会把问题推后而不是解决 |
| 10 | 🔧 原书局部表述需修正 | 原书 11.1.1 讨论"Kafka 消息会丢"——**前提需补明**：在 `acks=all` + 幂等 producer + 手动 offset 提交的现代配置下，可以做到不丢；原书描述的是默认配置下的行为，直接照搬"Kafka 会丢数据"作为结论会误导 |
| 11 | 🔧 **本书未覆盖：Kafka 顺序性的真实边界** | 原书 11.1.2 指出消息乱序。准确表述是：**Kafka 只在分区内有序**；跨分区无序。配合幂等 producer 与单分区，可以实现严格有序，但会牺牲并行度——这个 trade-off 必须向业务方明说 |
| 12 | 🔧 **本书未覆盖：异步化带来的"可观测性债务"** | 一旦请求异步化，链路追踪（trace）就从"可选"变成"必需"。2026 年的统一方案是 **OpenTelemetry**，否则你无法回答"这条消息到底哪一步慢了" |
