## 核心精讲

### 18.1 度量工作量

| 指标 | 正当用途 | 被滥用时的后果 |
| --- | --- | --- |
| **故事点 / 速度** | 团队内部预测下一轮能做什么 | 变成 KPI → 拆任务刷点、故意灌水 |
| **工时 / 投入** | 成本核算与容量规划 | 变成「坐班时长」的代理 → 摸鱼与加班表演 |
| **吞吐（完成数）** | 与周期时间配合做预测 | 单独看 → 鼓励拆小和无脑堆数量 |

> 一句话原则：**预测用速度，考核用结果。**（结果 = 业务指标、缺陷逃逸率、客户满意度）

### 18.2 度量工作质量

| 质量指标 | 说明 | 陷阱 |
| --- | --- | --- |
| 缺陷密度 / 缺陷数 | 质量的基础口径 | 只数不修 → 数字好看，债务变重 |
| **逃逸率**（发现于生产环境的缺陷占比） | 最能反映「检测防线是否有效」 | 需要跨阶段统一缺陷录入口径 |
| 返工率 | 说明上游质量 | 定义不清容易被玩坏 |
| 覆盖率（辅助） | 测试覆盖的宽窄 | 见下：覆盖率不是质量 |

> 🔧「**测试覆盖率即质量**」是 2020 年代最普遍的误用之一。有效替代或从旁补充：
> - **变异分数**（测试能否真正发现改动后的缺陷）
> - **缺陷逃逸率 / 漏测率**
> - **关键路径的人工审查比例**

### 18.3 度量的一般注意事项

原书给出的注意事项可归纳为四条前置条件：

| 前提 | 说明 |
| --- | --- |
| 1. 过程先稳定 | 流程还在剧烈变化时，度量全是噪声 |
| 2. 口径先统一 | 「缺陷」「任务」「完成」的定义必须全组织一致 |
| 3. 用途先声明 | 度量为改进服务还是为考核服务，动手前就要说清 |
| 4. 数据先可信 | 自动采集的数据要先自检是否被流程绕过 |

### 18.4 谨慎使用来自工具的数据

| 工具默认数据 | 可能的问题 |
| --- | --- |
| 提交数 / PR 数 | 一次提交可能含 800 行，也可能是 3 行 |
| 代码行数 | 重构会「减少」行数，看起来像减产 |
| 覆盖率 | 只统计被加载的分支，测不到的地方天然为 0 |
| 会议时长 | 无法说明决策质量 |
| 打开 issue 数 | 越大说明越快发现，不是越差 |

### 19.1–19.2 基线、生产力

| 步骤 | 说明 |
| --- | --- |
| Step 1：建立基线 | 先把 Scrum 跑起来并收集数据（19.1） |
| Step 2：定位瓶颈 | 用价值流图找真正的等待点（19.3） |
| Step 3：动手改 | 只改最靠前、影响最大的那一个 |
| Step 4：再度量 | 用同样的口径复测，确认是不是有效 |

> 这一节最常见的组织错误是：**没有基线就宣布改进了 30%**。没有可比口径的百分比，等于没测。

### 19.3 价值流图与在制品（WIP）

```
价值流：需求 → 分析 → 开发 → 测试 → 发布 → 用户反馈
                  ↓       ↓       ↓
               等待   等待   等待    ← 真正的浪费所在（通常占大头）

在制品上限（WIP limit）示例：
├─ 进行中的需求：≤ 团队能同时「真正推进」的数量
├─ 已开始未完成的编码：≤ 2× 并行人数
└─ 排队中的测试/发布：≤ 1
```

| WIP 的作用 | 说明 |
| --- | --- |
| 暴露真实瓶颈 | 某个状态长期堆满 = 那里是瓶颈 |
| 限制并行 | 并行越多，单件流转越慢 |
| 防止「个人堆量」 | 谁的卡片多不代表谁的进展快 |

### 19.4 / 19.6 敏捷回顾与检视调整

| 有效回顾的标准动作 | 无效回顾的表现 |
| --- | --- |
| 有时间盒（45–90 分钟） | 无时间盒，想到哪说到哪 |
| 有明确规则（不说人、只说事） | 变成对个人的批评 |
| 产出行动项并指定 owner | 「大家觉得还可以」 |
| 下次回顾先检查上次行动项 | 上次的问题从未被追 |
| 领导者不追责 | 领导在场就等于追责 |

### 19.5 谨防应付度量（Gaming the metrics）

这是全章最值得反复读的一节。原书把它单列一节，本笔记把它展开成一条**「度量被优化」的演化路径**——你只要不给干预，它就会自动走到最后一步：

```
Step 1  指标被用于考核
Step 2  团队发现「满足指标」比「达成目标」更容易
Step 3  出现配合指标的行为：拆任务刷点、只数不改、把问题藏起来
Step 4  数字变好，真实情况变坏
Step 5  管理层失去唯一诚实的信号源 → 只能靠加大管控
───────────────────────────────────────
破解：把「改进」与「考核」两条线分开；
      用过程指标做改进，用结果指标做评价。
```

| 典型「被优化」的症状 | 对应的指标 |
| --- | --- |
| 任务被拆到极小以获得更多点数 | 故事点 / 任务数 |
| 覆盖率靠写无断言的测试冲高 | 覆盖率 |
| 缺陷被改状态而非修复 | 缺陷数 |
| 需求被关掉但没有交付 | 完成率 |
| 站会记录「无阻塞」，实际全堵着 | 站会出席与阻塞声明 |

### 19.7 度量个人生产力

| 反对理由 | 说明 |
| --- | --- |
| 个人贡献无法隔离 | 一个功能是多人的产物 |
| 会扭曲行为 | 一切以指标为准做取舍 |
| 抑制求助 | 请求帮助显得产能低 |
| 与心理安全冲突 | 见 `10` 的 17.2 |

> 结论：**度量个人生产力，损失的一定比得到的多。**

> 教学示意（价值流与 WIP 示意、「度量被优化」路径均为**教学示意，不编译、不运行、不参与构建**）。

## 近年研究与工业界开源实践（2015–2026）

1. **DORA 2024 修订（2024-07）**：Google Cloud 发布《2014–2024: The Evolution of DevOps Metrics》，调整并改称 Software Delivery Performance（SDP），同时说明了阈值的更新与「四把钥匙」口径的变化。**这是本书 18 章在 2026 年必须补的一课**。
2. **Flow Metrics 的流行**：DORA 2024 之后更强调流动指标（部署频率、前置时间、变更失败率、恢复时间之外的 flow metrics），其中「在制品数量」与「流动效率」几乎零成本可得，正对应 19.3。
3. **Metric gaming 的实证**：研究者与工业界反复记录了「指标一旦被设为目标，数据就会向目标漂移」（19.5 的机理），所以工业界普遍采取「过程指标只用于改进、结果指标用于评价」的双轨制。
4. **可观测性数据进入度量层**：OpenTelemetry 让「变更前置时间」「恢复时间」可以从真实系统自动算出，减少人工填报的失真。
5. **AI 带来的新度量陷阱（2023–2026）**：AI 生成代码的占比一旦成为 KPI，就会激励「多生成少审查」；审查覆盖率与「关键路径人工签字率」成为新的反向指标。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **DORA 指标口径已在 2024 年修订** | 仍用旧的「四指标 + 旧阈值」设目标 | 补读 DORA 2024 说明；指标改称 Software Delivery Performance（见 `09` 与 `11` 的近年实践小节） |
| 2 | 🔧 **「测试覆盖率即质量」未被正面批驳** | 用覆盖率晋升 / 用覆盖率发奖金 | 用变异分数 + 缺陷逃逸率 + 人工审查比例交叉验证 |
| 3 | 🔧 **故事点被当 KPI 的副作用**：原书 18.1 提及但不具体 | 拆任务刷点、速度政治化 | 明确规则：速度只用于预测；跨团队比较一律禁止 |
| 4 | **把度量当成汇报工具** | 每周给领导一张完成度饼图 | 度量的第一读者应是改进者，不是汇报对象 |
| 5 | **个人生产力度量**（19.7 给了反对理由） | 用提交数/行数给个人排名 | 坚持反对；改为团队级 + 结果级 |
| 6 | **有基线前就宣布改进幅度** | 「我们提效 30%」 | 先统一口径并至少跑一个完整基线周期 |
| 7 | 🔧 **AI 相关指标尚无成熟口径** | 「AI 采用率」变成新的考核指标 | 用审查覆盖率、逃逸率、回滚率作为反向约束 |
| 8 | **工具数据直接进dashboard 就当结论** | 「Sonar 说质量好」 | 先自检口径：哪些没被工具看到 |
| 9 | **复盘会变成追责会** | 领导在场且不表态 | 17.2 心理安全 + 明确「只说事不说人」 |
