## 核心精讲

### 2.1 的机制：好处来自「反馈环长度」，不来自「迭代」这个形式

本书最有解释力的一句话可以概括成下面这条因果链。**关键的判断标准是「反馈环有多长」，而不是「是否在冲刺」。**

```
传统批量模式：
  需求 → 设计 → 编码 → 集成 → 测试 → 上线 → 才知道对不对
                  ↑______________________________|
                      反馈环可能长达数月甚至一年

敏捷（以垂直切片为特征）：
  需求 → 切片 → 编码 → 自动化测试 → 上生产 → 用真实反馈调整
                             ↑______________|
                          反馈环缩短到天/小时级
```

由此推出三条可核查的推论（这也是本笔记给读者的自检表）：

| 推论 | 自检问题 |
| --- | --- |
| **反馈越短，越值得采用敏捷** | 我们的「想法 → 用户真实反应」之间有几次人工环节？ |
| **任何「形式上的敏捷 + 长反馈环」都是伪敏捷** | 我们两周开一次会，但需求半年才验证一次——迭代只是节奏，不是反馈 |
| **没有自动化测试支撑的短迭代，只会更焦虑** | 每次发布需要几天？回滚需要几分钟？ |

> 本笔记提醒（呼应本地旧摘录「甘特图是瀑布模型」）：**用甘特图排软件项目，等于在声明「我不需要反馈」。**甘特图适合「需求冻结、技术已知、顺序依赖明显」的硬件建造式工作；把它套到需求会变的软件上，只是把风险往后推。这不是说甘特图不能用，而是说**用它来管理会变的软件，本身就是一种瀑布心态**。

### 1.1 / 1.2：有效的敏捷为何重要 + 目标读者

| 角色 | 你需要从这本书拿到的东西 |
| --- | --- |
| 企业技术管理者 | 判断团队是否在**真敏捷**，而不是「有站会、有看板、有迭代」 |
| 敏捷教练 / Scrum Master | 失败模式清单与评分卡（见 `03-Scrum入门与失败模式.md`） |
| 有经验的开发 | 「技术债管理」「垂直切片」「完成定义」的**领导视角解释** |
| 无技术背景的业务方 | 一句话：敏捷不是「开发想怎么干」，而是**用更短周期确认钱花得值** |

### 2.2 敏捷边界：给敏捷划四条线

本书只在第 2 章点出「敏捷边界」这个方向，全书的边界讨论在 Ch20（可预测性与敏捷边界）与 Ch21（受监管行业）展开。本笔记把它整理成四条可操作的边界线。

| 边界类型 | 说明 | 典型反例（伪敏捷信号） |
| --- | --- | --- |
| **需求边界** | 需求几乎不变、变更成本远低于变更收益时，计划驱动更划算 | 需求冻结、合同禁止变更，却照搬 Sprint 做「两周一变」 |
| **复杂度边界** | 系统本身简单、无外部不可控接口时，反馈环并不是瓶颈 | 用一个简单的 CRUD 系统硬上完整 Scrum，只剩形式 |
| **合规边界** | 有强制审计与证据要求的场景，需要额外流程（见 Ch21） | 用敏捷口头沟通应付 IEC 62304 的证据链 |
| **组织边界** | 组织不支持跨职能、不支持授权时，敏捷会退化成「加班换节奏」 | 「名为敏捷、实为外包加周报」（本地旧摘录里的真实观察） |

### 「给领导者的行动建议」的落地版

| 领导动作 | 具体做法 | 不做的后果 |
| --- | --- | --- |
| 说清价值 | 用「更短反馈 / 更少返工 / 更快上市」表述，而不是「拥抱变化」 | 预算被砍时无法自证 |
| 划边界 | 明确哪些项目不强制敏捷，由项目特性决定 | 全部项目一刀切，资源错配 |
| 配环境 | 为跨职能团队配齐决策权、测试与发布能力 | 团队「自组织」但因为没权限而空转 |

### 一张「真敏捷 / 伪敏捷」对照表（本地旧摘录的直接应用）

本地笔记旧摘录里有两条随手记：**「甘特图是瀑布模型」** 和 **「某语音公司是敏捷」**。这两句话不够精确，但它们指向的问题是真的——**读者最想知道的是「怎么识别伪敏捷」**。下表把这两个直觉升级成可核查的判据。

| 维度 | 真敏捷 | 伪敏捷（「某语音公司是敏捷」这一类） |
| --- | --- | --- |
| 反馈环 | 想法到真实反馈以天/小时计 | 需求半年验证一次，迭代只是节奏 |
| 需求 | 需求细到可验收，随认知更新 | 需求是一份冻结的 PRD，迭代只是拆任务 |
| 团队 | 跨职能、有决策权、能发布 | 只负责实现，决策在别处 |
| 发布 | 每次迭代可上线 | 发布要跨部门协调，一个月一次 |
| 度量 | 用于改进，不进个人考核 | 速度当 KPI，或干脆没有数据 |
| 领导 | 管理结果与清除障碍 | 管理活动细节，用甘特图压进度 |

| 关于「甘特图是瀑布模型」的精确表述 | 说明 |
| --- | --- |
| 成立的部分 | 用甘特图排软件项目、且假定需求不变，就等于把项目当成瀑布——**它承认没有反馈机制** |
| 需要修正的部分 | 甘特图本身不是罪：需求稳定、依赖顺序强的场景（机房迁移、多行实施）用它反而更清楚 |
| 可操作的判据 | 问一个问题：**这份计划里有没有「到某一天就能真实验证想法」的里程碑？** 没有，就是瀑布心态 |

### 常见误读速查

| 常见说法 | 是否成立 | 更准确的说法 |
| --- | --- | --- |
| 「敏捷就是快」 | 不成立 | 敏捷是**反馈快**；快而不准等于返工更快 |
| 「敏捷就是不要文档」 | 不成立 | 敏捷要**够用的文档**；把「不要文档」当成省事，会在人员流动时付出全部代价 |
| 「敏捷适合所有项目」 | 不成立 | 见上文四条边界；本书 Ch20 会正式处理可预测性问题 |
| 「上了 Scrum 就是敏捷组织」 | 不成立 | 形式不等于机制；本书 Ch4 的失败模式就是为此写的 |

## 近年研究与工业界开源实践（2015–2026）

原书 2021 年出版，以下为 2026 年必须补的部分。

1. **DevOps / 平台工程**：2023 年 CNCF 发布《Platform Engineering Whitepaper》，「内部开发者平台（IDP）」被 Gartner 列为当时十大战略趋势之一；Google Cloud 同年发布《Accelerating DORA: The Science of Platform Engineering》，把 IDP 与交付效能直接挂钩。本书只在 Ch15 讲 CI/CD 的工作实践，**没有**平台层视角——这是本书最大的时代缺口之一。
2. **AI 编码助手对反馈环的影响**：Copilot / Cursor 一类工具显著提高了「写代码」这段的产出，但把瓶颈推向「需求是否清晰」与「变更是否可验证」。争论焦点是：AI 是否让敏捷更有效，还是让**更多低质量代码更快堆积**。
3. **混合办公常态化**：2021 年本书已讨论分布式敏捷，2023–2026 年的新增结论是：**异步协作工具成熟后，「反馈环」的瓶颈更多在决策权而非时区**。
4. **「伪敏捷」的工业识别清单**：社区反复出现的实证信号是——看板上没有在制品上限、迭代承诺靠领导施压、自动化回归跑不起来却仍宣称持续交付。

| 工具 / 仓库 | 用途 | star（2026-09-25 实测） |
| --- | --- | --- |
| `github/spec-kit` | 规格驱动开发，把「需求 → 可执行规格」变成 AI 时代的反馈环 | **138,840★** |
| `microsoft/playwright` | 让「验证」这一步可以自动化，缩短反馈环的必备件 | **96,659★** |
| `backstage/backstage` | 内部开发者平台，补本书缺失的平台工程视角 | **34,497★** |
| `coder/coder` | 远程开发环境，混合办公下的反馈基础设施 | **16,685★** |
| `qodo-ai/pr-agent` | 自动化 code review，替代「人工看有没有对齐意图」 | **13,149★** |

> 用法建议：把上面五个工具当成**「缩短反馈环」的具体实现**，再回头对照 2.1 的自检表——你会发现工具只是手段，环长不长取决于组织是否有决策权与验证能力。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **把「用 AI 生成代码」等同于「提升了敏捷效能」 | 「我们有 AI 助手，交付更快了」缺乏证据，实际可能是技术债加速累积 | 用 DORA 四指标与缺陷逃逸率交叉验证；AI 只管写，不管反馈环长度 |
| 2 | 🔧 **敏捷边界缺少「AI 依赖风险」这一条** | 用 AI 生成高风险行业（医疗/航空/金融）代码却无验证证据链 | 边界表增列：受监管 + 高风险场景需强制验证证据（见 `12`） |
| 3 | **把「敏捷」当成「不做计划」 | 「敏捷就是拥抱变化，所以不写计划」 | 本书 2.1 已否定；计划的是**反馈环与切片，不是完整规格** |
| 4 | **把「站会」当成敏捷的好处来源 | 每天站着开会一周，交付反而变慢 | 回到机制：站会价值在暴露阻塞，不在形式 |
| 5 | **「甘特图是瀑布模型」被误读为「甘特图完全不该用」 | 拖甘特图 = 落伍 | 精确表述：**用甘特图管理会变的软件需求 = 瀑布心态**；需求稳定、顺序依赖强的场景（基建迁移、多行程实施）用甘特图反而更清楚 |
| 6 | 🔧 **目标读者假定「人还在现场」 | 书里默认沟通成本低，未处理混合办公的异步协商成本 | 补 `05-分布式团队与沟通.md` 的异步决策记录做法 |
| 7 | **「有效的敏捷为何重要」只给了方向，没有量化 | 领导层仍可用「感觉没效果」砍项目 | 用 DORA / 交付预测偏差（见 `11`、`12`）把价值货币化 |
