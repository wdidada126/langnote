## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 9.1 保持项目规模小 | **规模是复杂度的乘数** | 拆项目比优化流程更能提升成功率 |
| 9.2 保持 sprint 短小 | 迭代越长，反馈越迟 | 短迭代是反馈机制，不是管理仪式 |
| 9.3 基于速度的计划 | 用历史速率做预测，而不是承诺 | 速度用于预测；拿去考核会立刻失真 |
| 9.4 垂直切片交付 | 每次交付横跨各层的「可用功能」 | 垂直切片是「可交付价值」的最小完整单位 |
| 9.5 管理技术债 | 债务要有台账与偿还计划 | 无台账的技术债等于无上限的利息 |

## 核心精讲

### 9.1 / 9.2 / 9.4：三个「变小」的机制

本书 9.1「保持项目规模小」是全章的锚点。规模与成功率的关系不是线性的：

```
项目数 = 1                  →  组织无法快速切换方向
项目数 = 6 个并行的大项目   →  每个都难以反馈，风险集中
项目数 = 30 个小区块        →  可排序、可砍掉、可快速验证
```

| 机制 | 作用对象 | 典型尺度建议 | 违背的后果 |
| --- | --- | --- | --- |
| 保持项目规模小（9.1） | 并行项目的工作总量 | 同时在进行的「大块」项目尽量少 | 资源被摊薄，谁都做不好 |
| 保持 sprint 短小（9.2） | 反馈周期 | 1–2 周（长则 1 个月内） | 反馈延迟，宁可延长也别误报 |
| 垂直切片交付（9.4） | 交付单位 | 一次交付横跨 UI/服务/数据、可真实使用 | 看似在迭代，实际仍是批量整合 |

**「垂直切片」是本笔记最推荐读者反复体会的概念**，它与常见的「水平切片」对照如下：

```
水平切片（反面）：           垂直切片（正面）：
├─ 第 1 周：所有模块的接口层   ├─ 切片 A：一个真实业务场景全链路可用
├─ 第 2 周：所有模块的服务层   ├─ 切片 B：下一个真实业务场景全链路可用
├─ 第 3 周：所有模块的 UI      └─ ……
└─ 第 4 周：联调 + 测试        （每次都能演示、都能发布）
     ↑ 到第 4 周才知道能不能跑
```

### 9.3 采用基于速度的计划

| 要点 | 说明 |
| --- | --- |
| 速度是**预测参数**，不是绩效指标 | 用它回答「下个季度能做多少」，不回答「谁偷懒」 |
| 需要足够样本 | 前 3–4 个 sprint 的数据不稳定，不要拿去承诺 |
| 口径必须干净 | 9.7「与项目无关的软件开发工作」不能混进速度分母 |
| 只用于团队内部校准 | 对外承诺要用发布日期 + 范围可协商（见 `12`） |

### 9.5 关键原则：管理技术债

| 技术债管理动作 | 具体做法 |
| --- | --- |
| 识别 | 用重构书里的坏味道作为识别清单（`book/重构/00-总览与阅读地图.md`） |
| 登记 | 建立技术债台账，记录触发原因、影响范围、偿还成本 |
| 排序 | 按「偿还收益 ÷ 偿还成本」排，不要按「谁先抱怨」排 |
| 排期 | 在迭代中固定拨出比例（例如 15%）用于还债，形成节奏而非运动 |
| 防止新增 | 用完成定义（DoD）守住「不留新债」（见 `07`） |

### 9.6 合理分配工作，避免心力交瘁

| 症状 | 原因 | 对策 |
| --- | --- | --- |
| 个别关键人物长期过载 | 分配不考虑个体状态 | 用 WIP 限制与工作分布看板 |
| 速度忽高忽低 | 「英雄式」压榨后反弹 | 稳定节奏，不可用极限压榨补进度 |
| 隐性瓶颈在上游（环境、审批） | 只盯着开发环节 | 用价值流图找真实瓶颈（见 `11`） |

### 10.3 布鲁克斯法则

**往一个延期的项目上加人，只会让它更延期。**原书用这一节提醒大项目主管别指望「堆人换时间」。本笔记补上它的机制解释：

| 加人带来的额外成本 | 说明 |
| --- | --- |
| 沟通路径增加 | 沟通开销随人数**组合式**增长（n(n-1)/2） |
| 理解成本 | 新人要理解上下文，老成员要花时间解释 |
| 产出稀释 | 新增的人本身没有产出，只有消耗 |

> 可操作推论：**项目已经延期且需要加人时，先把范围变小，而不是加人。**这也是 9.1 的另一面。

### 10.4 康威定律与架构（10.4 / 10.5）

```
                 组织沟通结构
                       │
                       ▼
              系统设计方案（架构形状）
                       │
                       ▼
              团队反复修改/维护它 → 「架构」就这样固化了
```

| 推论 | 用法 |
| --- | --- |
| 团队边界 = 系统边界 | 按业务能力划团队，而不是按技术分层 |
| 跨团队的接口是最容易腐化的地方 | 接口要有契约测试与明确 owner |
| 想改变系统形状，得先改变组织结构 | 拆分/合并团队是架构变更的前置动作 |

**10.5「通过架构支撑大型敏捷项目」**的核心是把「架构为可改性服务」：

| 架构属性 | 对敏捷的意义 |
| --- | --- |
| 模块清晰、依赖方向稳定 | 团队可以独立推进而不互相阻塞 |
| 变更局部化 | 一次改动只影响一个小团队 |
| 自动化验证完备 | 快节奏下安全网足够 |
| 可独立部署 | 团队能独立发布，不绑在发布大船上 |

> 这部分的要求与《Clean Architecture》高度一致：`book/架构整洁之道/00-总览与阅读地图.md` 讲的「依赖方向」，就是「大项目能否敏捷」的架构答案。

### 10.8 大型敏捷项目的评分卡

原书给了一套规模化诊断评分卡。它的用法与 Ch4.8 一致：定期打分、看趋势。

| 检查项 | 不健康信号 | 健康信号 |
| --- | --- | --- |
| 跨团队接口 | 接口靠会议对齐，文档长期缺失 | 契约测试 + 接口 owner 明确 |
| 发布流程 | 多团队必须同步发布 | 团队可独立发布 |
| 需求来源 | 多个产品待办列表互相矛盾 | 统一的成品路线与优先级 |
| 架构状态 | 每次改动都要跨团队评审 | 团队内部即可完成绝大多数改动 |

> 教学示意（切片对比图、康威关系图、布鲁克斯成本表均为**教学示意，不编译、不运行、不参与构建**）。

## 近年研究与工业界开源实践（2015–2026）

1. **规模化框架之争持续**：SAFe / Large Scale Scrum / Nexus / Scrum of Scrums 并存。本书的取向更务实（10.8 评分卡 + 10.2 重点实践），读者可把评分卡当作「要不要引入完整框架」的前置体检。
2. **团队拓扑与认知负载（2019 起）**：Skelton & Pais 给出四型团队（业务交付 / 平台 / 复杂子系统 / 效能），并强调**协调团队数量越少越好**——这是对布鲁克斯法则的现代化表述。
3. **平台工程降低「大项目协调成本」**：IDP 把公共能力（CI、环境、发布、观测）收归平台团队，让业务团队之间的接口从「会议」变成「自助调用」，直接缓解 10.6/10.7 描述的协作挑战。
4. **AI 对大项目的影响（2024–2026）**：单团队产出提高，但跨团队接口、合规证据链、验证负担同步增加；**团队数量减少、单团队规模不变**成为很多组织的现实。
5. **技术债的量化实践**：社区开始用静态分析与覆盖率之外的数据（变更失败率、回滚率）来评估债务的真实成本，比「代码坏味道打点」更接近本书 9.5 的意图。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **AI 时代「加人没用」需要新条件** | 用 AI 后新人上手变快，布鲁克斯法则似乎失效 | 沟通开销变小的同时**验证开销变大**；加人仍不改善验证瓶颈 |
| 2 | 🔧 **大型敏捷的评分卡缺少「AI 生成代码的合规与验证维度」** | 规模化评分不覆盖 AI 产出质量 | 评分卡增加一列：关键路径验证与审查比例 |
| 3 | **把「垂直切片」理解成「一次做一个功能」** | 功能很大，仍要数周 | 切片必须**小到可以在一次迭代内走完全链路并可发布** |
| 4 | **把技术债台账当成一次性整理** | 建过一次台账就没人维护 | 9.5 的要点是**持续登记**：新增债务必须进台账 |
| 5 | **康威定律被当成「组织怎么改系统就怎么长」口号** | 只调整团队标签，不改职责 | 要改的是**职责与所有权**，而不是组织结构图上的连线 |
| 6 | **速度被当成产能指标用于跨团队比较** | 团队开始灌水 | 回到 9.3：速度只用于预测；见 `11` 的度量陷阱 |
| 7 | 🔧 **缺少「发布频率 vs 团队数」的量化关系** | 说不清多少团队共享一条流水线时开始拥塞 | 实践参考：一条发布流水线 / CI 队列是瓶颈，需要排队与分片 |
| 8 | **把 9.7「与项目无关的工作」排除掉就算干净** | 隐性工作（on-call、面试、培训）仍然挤占 | 口径要按「本团队本迭代为本项目投入的人力」统计 |
