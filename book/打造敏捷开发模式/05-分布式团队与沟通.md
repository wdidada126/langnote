## 核心精讲

### 7.1 关键原则：加强反馈循环

本书对分布式敏捷的核心判断可以概括为一句话：**分布式放大了已有的问题**。如果团队本身反馈就慢，分布式会让慢变成「错」。

```
共置团队：  想法 ──► 编码 ──► 验证 ──► 反馈        反馈延迟：小时级
             ↑______________________|

分布式团队： 想法 ──► 编码 ──► 验证 ──► 反馈        反馈延迟：跨时区 = 一天起
             ↑______________________|
             问题：反馈到达时，做决定的人可能已经在下班/睡觉

因此分布式的正确做法是：把「决策权」跟着「信息」走，而不是把「信息」送去做reporting
```

| 反馈环节 | 分布式的常见断点 | 修补动作 |
| --- | --- | --- |
| 需求澄清 | 业务方在本地，开发在异地 | 用就绪定义（DoR）+ 书面澄清记录（见 `08`） |
| 技术验证 | 环境在另一个手里的 | 开发环境与流水线自助化（见下表工具） |
| 发布上线 | 发布窗口在本地运维手上 | 团队自建发布能力（见 `09`） |
| 用户反馈 | 客服在本地，开发端没有通路 | 建立最短的「用户声音 → 团队」通道 |

### 7.2 迈向成功的分布式敏捷团队

原书给出的成功要素可归纳为四类，本笔记补上「可核查标志」一列：

| 要素 | 具体含义 | 可核查标志 |
| --- | --- | --- |
| **共同目标** | 各远端团队知道自己为什么做这个东西 | 能说出所在切片对应什么业务价值 |
| **共同工具** | 版本库、流水线、文档平台一致 | 任意远端成员能自助跑起来并发布 |
| **共同流程** | 定义完成（DoD）在各处一致 | 同一个 DoD 不需要逐个口头确认 |
| **持续沟通** | 沟通是常态而非事件 | 阻塞出现后 4 小时内有回应通道 |

### 7.3 关键原则：修正系统，而不是处理个人

这是本章最「领导者」的一条。它的推论是：**当协作出问题，先看制度与环境，再谈人的态度**。

| 问题现象 | 「处理个人」的做法（无效） | 「修正系统」的做法（有效） |
| --- | --- | --- |
| 远端总是迟到 | 批评个别成员 | 调整重叠工作时间或把会议改为异步 |
| 文档没人看 | 要求「必须看文档」 | 把决策写进决策记录（ADR），让文档成为唯一入口 |
| 代码 review 慢 | 催评审者 | 设定 review SLA 与值班轮换 |
| 需求理解有偏差 | 让远端「更认真一点」 | 用就绪定义 + 验收标准模板（见 `08`） |

> 这条原则与本地旧摘录「某语音公司是敏捷」可以对照：那类观察记录里常见的是「流程有、但决策在别处」。**这类问题没有一个是靠「态度更端正」解决的。**

### 7.4 内部决策与效率

| 决策类型 | 应在哪里做 | 若集中到别处的代价 |
| --- | --- | --- |
| 技术细节（框架、库、写法） | 离代码最近的人 | 每次都要等 → 反馈环断裂 |
| 接口与集成方式 | 双方团队共同 | 接口反复返工 |
| 范围与优先级 | 产品负责人（可远程） | 等待成本可控，但要记录 |
| 对外承诺与时间 | 与业务同一侧的组织层 | 最容易产生「承诺靠喊」 |

### 8.1 / 8.2 关注个体 → 培养个人能力 → 提高团队能力

本书第 8 章把视角从团队压回个体，逻辑链条是：**团队产出 ≈ 个体能力 × 协作效率**。

```
个体能力：技能、判断力、效率、职业习惯   ← 可 Investment（培训/结对/复盘）
协作效率：沟通、反馈、共同理解           ← 可 Investment（流程/文档/工具）

团队能力不是「个体能力的平均」，而是它们叠加后的样子
```

| 培养方式 | 面向 | 与敏捷的关系 |
| --- | --- | --- |
| 结对编程 / 配对调试 | 技能传递 | 最直接的「知识不掉线」手段 |
| 代码评审 | 质量 + 共享 | 分布式的替代品之一 |
| 复盘 / 回顾 | 判断力 | 需要心理安全（见 `10`/`11`） |
| 内部技术分享 / 实践者社群 | 专精（Ch6.4「建立实践者社群」） | 让「专精」在组织内流通 |

### 8.3 卓有成效的团队沟通

| 沟通类型 | 目的 | 频率建议 | 常见失败 |
| --- | --- | --- | --- |
| **同步（会议）** | 需要当场决策的 | 高优先级事项 | 用来同步信息（该用文档） |
| **异步（文档/讨论区）** | 记录决策与上下文 | 默认选项 | 没有明确 owner 与结论 |
| **正式报告** | 给组织层看进度 | 每周/每迭代 | 与决策脱钩，只呈现「完成度」 |

> 2026 年的经验法则：**默认异步，例外同步。**原书 2021 年已经涉及这个方向，2023–2026 年的实践进一步确认：跨时区团队如果主要靠会议推进，成本会随团队数量线性上升。

> 教学示意（反馈环示意、能力叠加公式均为**教学示意，不编译、不运行、不参与构建**）。

## 近年研究与工业界开源实践（2015–2026）

1. **混合办公常态化后的分布式敏捷（2023–2026）**：最常见的结论是——**混合办公把「会议」当成默认同步手段的团队效率最差**；把决策文档化、异步化的团队受影响最小。原书 2021 年的判断（7.1 加强反馈循环）得到了进一步确认。
2. **平台与开发环境即协作基础设施**：远程团队的生产力差距，主要来自「能不能自助拿到环境/权限/数据」，而不是「人合不合」。
3. **AI 对沟通的改造**：2024–2026 常见实践包括会议自动生成纪要与待办、PR 模板自动生成、决策记录（ADR）自动生成。**但注意 7.3 的原则**：这些工具改变的是系统，不改变决策权；如果决策权仍在别处，工具只会让等待更制度化。
4. **跨时区重叠时间的经济账**：多家组织在 2023–2026 重新计算了「重叠工作小时数」的成本，结论是与其要求远端迁就，不如**把工作按「决策需要同步 / 执行可以异步」切分**。
5. **DevEx 研究**：微软等机构对开发者体验的研究表明，工具摩擦与上下文切换是开发效率的主要损耗——这是 8.2「培养个人能力」之外的**系统侧**解释。

| `coder/coder` | 远程/混合开发环境自助供给，解决 7.1 的「环境断点」 | **16,685★** |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **混合办公时代的会议依赖没有被覆盖** | 原书默认「会议可用」，2026 年多数组织是混合 | 明确默认异步；会议只在需要当场决策时开；会议必须有决策记录 |
| 2 | 🔧 **AI 纪要工具可能削弱「共同理解」** | 开会变成「走过场 + 自动记录」，人不再在场思考 | 用「会后 24 小时内有人复述结论并确认」做校验 |
| 3 | **把时区差当成主要障碍** | 「跨 8 个时区所以做不好敏捷」 | 真正的断点常是决策权与环境；时区只是放大器 |
| 4 | **把「修正系统」当成「换个人」** | 一个协作问题就换掉一个人 | 7.3 的立场：先改制度与环境，再谈人 |
| 5 | 🔧 **缺少「异步决策记录」的具体形态** | 说要文档化，但没人知道写在哪 | 落成年轮式 ADR / RACI 表，纳入版本库 |
| 6 | 🔧 **「培养个人能力」在 AI 时代需要重新定义** | 培训仍以「写代码」为主 | 培训重心转到设计、验证、判断与跨职能沟通 |
| 7 | **把沟通量当成沟通有效性** | 「我们沟通很频繁」 | 看的是「做决定的时长」与「返工率」 |
| 8 | **分布式下 DoD 被各自解释** | 各远端团队对「完成」不同理解 | 复用 Ch11.2 完成定义（DoD），写清并统一 |
