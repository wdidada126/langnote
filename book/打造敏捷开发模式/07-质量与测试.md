# 第 11–12 章 敏捷质量与敏捷测试

> **一句话**：这两章把质量从「测试阶段」拉回到「缺陷检测的时间成本」上——**缺陷发现得越晚，代价指数级上升**；而唯一能让缺陷早发现的结构性手段是：**由开发团队编写自动化测试，并把「完成定义（DoD）」写死**。

## 核心精讲

### 11.1 关键原则：使缺陷检测的时间最短

本书把质量的核心指标定成「缺陷检测时间」，而不是「缺陷数量」。原因是代价曲线：

```
                      代价
                        ↑
                        │                                    ╱ 生产环境
                        │                                 ╱
                        │                             ╱      （修复 + 声誉 + 客户）
                        │                         ╱
                        │                     ╱           ╱ 集成/测试阶段
                        │                 ╱           ╱
                        │             ╱           ╱
                        │         ╱       ╱  接受/验收
                        │     ╱   ╱  ╱
                        │ ╱  ╱ ╱ ╱
                        └──┬──┬──┬──┬──┬──┬──┬──► 时间轴
                        需求 设计 编码 集成 测试 发布
```

| 检测点 | 典型代价量级 | 本笔记的说明 |
| --- | --- | --- |
| 编码时（本地、单测） | 最低（分钟级） | 需要自动化测试作为抓手 |
| 提交/集成时 | 低 | CI 是第一道闸门 |
| 接受/验收时 | 中 | 演示环节的真实反馈 |
| 生产环境 | 高 | 修复成本 + 业务损失 |

> 推论非常直接：**如果你们的缺陷大多在「集成/测试阶段」才被发现，那么加人加流程都用处不大，唯一有效的是把自动化测试左移到开发者手上**（12.1）。

### 11.2 关键原则：制定并采用完成定义（Definition of Done）

DoD 是这两章里最应该被写进组织规范的一件工具。

```
一条可用的 DoD 示例（团队级，可核查）
├─ 代码实现并自测通过
├─ 有自动化测试覆盖关键路径
├─ 通过代码评审
├─ 无新增静态分析告警（严重/阻塞）
├─ 手工验证过主要用户路径
├─ 文档与配置已更新
└─ 可以在生产环境发布（含回滚方案）
```

| DoD 的用法 | 说明 |
| --- | --- |
| 作为「完成」的判据 | 未完成的任务不许进入「已完成」列 |
| 作为质量的守门人 | 新债务（缺测试、缺文档）直接在 DoD 阶段被拦下 |
| 避免被当标准降低 | 如果 DoD 反复被打折，它就失去了意义 |

### 11.3 / 11.4：质量维持可发布水平 & 减少返工

| 维度 | 常见做法 | 本书倾向 |
| --- | --- | --- |
| 质量与进度冲突时 | 砍测试、砍文档换上线 | **质量是可发布水平，砍掉的应该是范围，而不是质量** |
| 返工来源 | 归咎于开发粗心 | 治上游：需求歧义（见 `08`）、缺少验证假设的机制（见 `02`） |
| 技术债 | 无账可查 | 有台账 + 返还能力（见 `06` 的 9.5） |

### 12.1 关键原则：由开发团队编写自动化测试

这是第 12 章的核心主张，也是与市面上「独立测试团队」模式最大的冲突点。

```
模式 A：开发写代码 → 测试团队 later 发现缺陷
        缺陷检测时间：晚（代价高）
        认知：测试是「另一群人」的事

模式 B：开发写代码 + 自己写自动化测试
        缺陷检测时间：早（代价低）
        认知：测试是「质量责任的一部分」
```

| 常见反对意见 | 本书/本笔记的回应 |
| --- | --- |
| 「开发不会写测试」 | 这是**培训与工具问题**，不是分工原则问题 |
| 「测试要独立才客观」 | 客观来自**自动化 + 评审 + 探索性验证**，不来自组织距离 |
| 「测试团队可以专注」 | 专业分工可以保留，但**质量责任必须在开发侧** |

### 12.2 使敏捷测试卓有成效的更多要领

原书在这一节给出若干要领。本笔记把它们整理成一个「测试可信度」自检清单：

| 要领 | 落地做法 | 失效信号 |
| --- | --- | --- |
| 分层：金字塔而非冰淇淋 | 单元 → 集成 → 端到端，越上层越少 | 90% 的测试都是最贵的端到端 |
| 测试要快 | 主流程分钟级 | 跑一次 40 分钟，没人愿意等 |
| 测试要可信（不 flaky） | 禁止随机、禁止依赖时序 | 有 3% 的 flaky 测试，且被 ignore |
| 测试要独立可重复 | 不依赖本地私有数据 | 「在我机器上是好的」 |
| 端到端只覆盖关键路径 | 用契约测试替代跨系统 E2E | 每次发版都要跑全套系统 |

> 教学示意（代价曲线、测试金字塔位置、模式对照均为**教学示意，不编译、不运行、不参与构建**）。

## 近年研究与工业界开源实践（2015–2026）

1. **测试可信度成为研究焦点**：flaky test 检测、分类、自动隔离在 2015–2026 年持续有研究，工业界工具（例如自动重试与 quarantine）普及。本书 12.2「测试要可信」这一条，现在有了明确的量化对象：**flaky 率**。
2. **覆盖率之外**：覆盖率作为质量代理被广泛质疑，工业界开始关注**变异测试（mutation testing）与「有效断言」比例**——这与本书「缺陷检测时间最短」的目标更一致。
3. **AI 生成测试（2023–2026）**：Copilot / Cursor 一类工具可批量生成单测与 E2E。争论的核心问题是：**AI 写的测试是「守卫」还是「镜像」**——如果测试只是复述实现，就会把 bug 也一起复制。**结论倾向：测试仍须由对代码负责的人审阅并拥有。**这正是本书 12.1 在 AI 时代反而更重要的原因。
4. **契约测试与消费者驱动契约**：跨团队接口的可信验证从「跑全套 E2E」转向契约测试，直接支撑 `06` 中「大项目独立发布」。
5. **生产环境作为测试场**：feature flag、影子流量、渐进发布把「可发布水平」这件事工程化，让 11.3 不再依赖「发布前全量验证」。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **AI 生成测试的「镜像陷阱」未被覆盖** | 用 AI 补测试覆盖率，测试只是复述实现，bug 被复制两份 | 测试必须经「这个断言能失败吗」的检验；要求关键路径人工评审 |
| 2 | 🔧 **「测试覆盖率即质量」的误用没有正面批驳** | 覆盖率从 40% 冲到 85%，逃逸缺陷不降反升 | 用变异分数与缺陷逃逸率交叉验证覆盖率；覆盖率不作为个人 KPI |
| 3 | **把 12.1 理解成「取消测试角色」** | 独立测试被完全消化进团队，失去专家视角 | 正确做法是「责任在团队 + 专精在少数人」；测试专家成为实践者社群（Ch6.4） |
| 4 | **flaky 测试被当成小问题** | 有 5% flaky 就整体 ignore | 把 flaky 率作为可见指标；flaky 是质量信号，不是技术债的小项 |
| 5 | **DoD 被当成一次性文档** | 写完锁进抽屉，实际逐次打折 | DoD 要复述、要 review；每次打折都要显式记录 |
| 6 | **把「可发布水平」当成最终状态** | 于是「基本可发布」成为永久借口 | 明确「可发布」的定义并写进 DoD；必要时缩小范围而非降低质量 |
| 7 | 🔧 **缺少 AI 生成代码的安全/许可证审查环节** | AI 产出代码直接合并，合规风险无人负责 | DoD 增加一条：来源与许可审查（尤其受监管场景，见 `12`） |
| 8 | **自动化测试只覆盖「能自动化的部分」** | UI 不稳定的部分永远手工 | 用契约测试 + 关键路径 E2E 覆盖，把人工留给探索性验证 |
