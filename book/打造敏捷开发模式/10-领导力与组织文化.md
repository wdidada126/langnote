## 核心精讲

### 16.1–16.2 管理结果 + 指挥官意图

这两条是一对：**给意图，不给步骤**。

```
领导者给出：      意图 + 约束 + 判断标准 + 何时来找我
                    ↓
团队自行决定：    怎么做、谁做什么、分几次、用什么技术
                    ↓
领导者验收：      结果是否符合意图、约束有没有被突破
```

| 指挥官意图的四个要素 | 说明 | 反面 |
| --- | --- | --- |
| **意图 Intent** | 你想达成什么（可观测的证据） | 「把这个项目做好」 |
| **约束 Constraints** | 不能越过的边界（预算、合规、技术栈） | 没有边界，团队会试出无限方案 |
| **判断标准 Measures** | 怎么算达成 | 「感觉快多了」 |
| **联系节奏 Check-ins** | 什么时候同步、什么时候必须叫停 | 「有问题随时来找我」= 永远不会有问题 |

> **一个关键的边界条件**：指挥官意图只在**团队拥有方法与决策权**时成立（见 `04` 的 Ch5.6「你的组织愿意创建敏捷团队吗」）。如果团队没有权限，只给意图等于把失败的责任推给没有权力的人。

### 16.3 关注吞吐量，而不是关注活动

| 活动（Activity） | 吞吐量（Throughput） |
| --- | --- |
| 写了多少个任务 | 多少个可发布的功能到达 |
| 开了多少会 | 前置时间从多长缩到多短 |
| 提交了多少次代码 | 变更失败率 |
| 点了几次「已完成」 | 返工率 |

> 这一条与 Ch18 的度量 pitfalls 直接衔接：**任何「活动类」指标一旦被用作考核，就会立刻变成向下博弈的对象**（详见 `11`）。

### 16.4 关键原则：在关键敏捷行为上以身作则

| 领导者应当示范的行为 | 常见反例 | 后果 |
| --- | --- | --- |
| 参加并认真对待复盘 | 派个代表来，中途离开 | 团队知道了复盘不重要 |
| 保护「不做假」的数据 | 「这个数字我不能看」 | 数据开始失真 |
| 承认自己的判断错了 | 从不公开纠正之前的决定 | Orient 环节失效（见 `02`） |
| 不在压力下要求牺牲质量 | 每次赶工都要求「这次先上线」 | 质量承诺变成空话 |

### 17.1 / 17.2 正向看待错误 → 心理安全

这是第 17 章最核心的一对概念，也是全书的价值观底座。

```
正向看待错误：  「这个功能上线后指标变差，我们的假设错在哪？」
        │
        └─ 需要的前提：说出来没有代价
                    │
                    ▼
              心理安全（Edmondson 的定义）：
              团队中「承认错误 / 提出异议 / 请求帮助」不被惩罚的状态
```

| 心理安全的 observable 行为 | 缺乏时的表现 |
| --- | --- |
| 主动报告最近的错误 | 错误只在爆炸后才被发现 |
| 提出与领导不同的意见 | 会上没有异议，会后广泛抱怨 |
| 请求帮助（不装懂） | 一个人硬扛到延期 |
| 承认「我不知道」 | 猜着做，错了也不说 |

> 判断方法：**复盘会上第一次出现沉默的十几秒，通常是心理安全的真实温度**。

### 17.3 以量化的团队产能制定计划

| 步骤 | 说明 |
| --- | --- |
| 1. 采集 | 记录每个迭代实际完成的工作（口径干净，见 Ch9.7） |
| 2. 计算 | 计算平均产能与波动范围 |
| 3. 计划 | 用「历史产能」而非「期望产能」排下一轮/下一季度 |
| 4. 复盘 | 预期与实际的偏差要归因（是范围变还是估计错） |

### 17.4 建立实践者社群

| 社群类型 | 例子 | 作用 |
| --- | --- | --- |
| 测试社群 | 测试专家定期分享 | 保持测试能力不退化 |
| 平台社群 | 平台团队与业务团队的技术沙龙 | 防止平台变成黑箱 |
| 架构社群 | 架构决策记录与评审 | 让架构决策可讨论 |
| 复盘社群 | 跨团队的经验交换 | 避免各团队重复踩坑 |

### 17.5 公司在敏捷中扮演的角色

| 公司应当做的 | 公司不该做的 |
| --- | --- |
| 提供平台与工具 | 下发统一的流程规范 |
| 授权团队（放决策权） | 用审批链把决策收回 |
| 保护反馈通路（用户、合规） | 只考核交付数量 |
| 投资培训与实践者社群 | 只把培训当作福利 |

> 教学示意（指挥官意图示意图、活动 vs 吞吐量对照均为**教学示意，不编译、不运行、不参与构建**）。

## 近年研究与工业界开源实践（2015–2026）

1. **心理安全的持续实证**：Edmondson 及其合作者持续研究心理安全与学习行为、绩效的关系；工业界常用「团队安全感问卷」做年度扫描。本书 17.1/17.2 因此不再只是价值观，而是可测量的组织状态。
2. **DevEx（开发者体验）与领导者动作挂钩**：2020 年代研究指出，开发者的「摩擦」主要来自工具、流程与组织摩擦。**消除摩擦是领导者最该做的一件事**，这与 16.1「管理结果」完全一致。
3. **速度 / 吞吐量的政治化问题（2018–2026）**：《Accelerate》之后，大量组织开始用 DORA 指标，但随之出现「指标被 KPI 化」的副作用；2024 年 DORA 对指标口径进行修订，也部分回应了这些争议（见 `11`）。
4. **AI 时代领导者的新真空**：AI 让「执行」变得更便宜，**区分「什么是好想法」和「什么是好执行」的能力成为领导者的核心价值**。这与 16.2 的「意图清晰度」直接相关：意图含糊时，AI 只会更快地产出无人负责的方案。
5. **实践者社群在远程时代的形态**：2023–2026 主流做法是「以文档与评审为载体的常设社群」，而不是临时性的技术分享。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **AI 让「管理细节」的诱惑更大** | 领导开始逐行 review AI 生成的代码 | 回到 16.1：管结果与约束，不看实现细节；评审用工具与清单 |
| 2 | 🔧 **心理安全在 AI 时代需要新定义** | 「不能有 AI 生成代码进生产」的惩罚文化 | 区分「错误」与「未澄清的假设」：前者追制度，后者不追人 |
| 3 | **指挥官意图 = 少给信息** | 只说「搞定支付」，不给约束和背景 | 16.2 的四要素缺一不可，尤其 Measures |
| 4 | **以身作则被理解为「带头加班」** | 领导冲刺时在场，团队跟着连轴转 | 以身作则示范的是行为准则，不是体力投入 |
| 5 | **吞吐量指标被当成个人 KPI** | 「本周 throughput 必须 ≥ X」 | 16.3 关注的是系统吞吐；落到个人就是反向激励 |
| 6 | **心理安全只靠团建** | 做几次信任练习就认为安全了 | 用可见行为检验：错误主动上报数、无异议的会议占比 |
| 7 | 🔧 **17.5 缺少「AI 治理」这一公司职能** | 公司层未定义 AI 使用的边界与审批 | 公司层职责增加：AI 使用政策、数据合规与审查清单 |
| 8 | **产能预测不更新** | 用去年的数字排今年的计划 | 产能是滚动量，每个季度重新校准（17.3） |
