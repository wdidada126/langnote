# 《卓有成效的敏捷》总览与阅读地图

> **一句话**：这不是一本「教你 Sprint 怎么写」的敏捷手册，而是**一份给软件组织领导者的「有效敏捷」识别指南**——它把敏捷从口号拉回到证据：哪些实践真的产生业务价值、哪些实践只是看起来在敏捷、以及一个组织在 242 页里能踩的坑。
>
> 原书 *More Effective Agile: A Roadmap for Software Leaders*，Steve McConnell（史蒂夫·迈克康奈尔，《代码大全》作者）著，任发科、林从羽 译，人民邮电出版社 / 异步图书，**2021-10-01**，ISBN **978-7-115-56491-7**，**242 页**。

## 4. 这本书的方法论特色：为什么它是「证据驱动」而不是「信仰驱动」

这是本目录反复强调的一点，也是本书与市面上绝大多数敏捷书的**根本差异**。

| 维度 | 典型敏捷书 | 《卓有成效的敏捷》 |
| --- | --- | --- |
| 论证方式 | 「敏捷四大价值观 / 十二原则」→ 由此推出实践 | **先问实践带来了什么结果**，再反推哪些实践有效 |
| 对失败的态度 | 多为成功案例倡导 | **专门用一整章列「常见的 Scrum 失败模式」，并归纳共同点**（Ch4.2 / 4.3） |
| 对边界的态度 | 「敏捷适用于所有项目」 | **Ch2「敏捷边界」+ Ch20「可预测性与敏捷边界」**——明确承认敏捷不是万能解 |
| 对度量的态度 | 多数回避 | **Ch18「度量的一般注意事项」+ Ch19.5「谨防应付度量」**——把度量副作用当成头号风险 |
| 对读者的设定 | 一线开发者 | **软件组织领导者**（Ch1.2），全程以「给领导者的行动建议」收束 |

因此本目录在每一章都会追问三个问题，读者也可照此读书：

1. **这条原则成立的机制是什么？**（例如：敏捷的好处来自减少反馈时间，而不是来自「迭代」这个形式）
2. **什么情况下它会失效？**（例如：团队把故事点当 KPI，速度立刻政治化）
3. **2026 年的环境变了什么？**（AI 编码助手、平台工程、混合办公、合规科技）

## 6. 本书刻意规避 / 2026 年必须补课的缺口

| 缺口 | 具体表现 | 补到哪里 |
| --- | --- | --- |
| **没有 DevOps / 平台工程的系统论述** | 只在 Ch15 讲 CI/CD 的工作实践，没有内部开发者平台（IDP）、自助能力、黄金路径 | 各章「近年研究与工业界实践」小节；平台工程 whitepaper、Backstage 类工具 |
| **没有 AI 编码助手的影响分析** | 2021 年成书，AI 对估算/测试/需求一致性的冲击完全缺席 | 🔧 每一章都补 2–4 条（见各章「常见误区」🔧 行） |
| **度量章偏保守** | 主要警示「别用错了」，但未展开 2020 年代 DORA / DevEx 的量化证据 | `11-度量与过程改进.md` 的 🔧 行 |
| **受监管行业只讲原则** | Ch21 正面讨论但篇幅短，缺少 IEC 62304（医疗器械软件）、ISO 26262（汽车）、SOX ITGC、FDA 审计的**证据链细节** | `12-` 章的 🔧 行 |
| **对「伪敏捷」的识别只给了零散信号** | 「甘特图是瀑布模型」「名为敏捷、实为外包加周报」这类判断散落在 Ch2/Ch4 | 🔧 集中在 `01`/`03` 章的误区表 |
| **假设单人单团队上下文** | 对多团队协同只讲 Scrum of Scrums（Ch10.8 评分卡），没有 OKR / 组合管理的 2026 演进 | `12-` 章 WSJF 与 OKR 部分 |
| **参考文献偏旧** | 以 2001–2015 年资料为主，2020 年代的研究占比低 | 各章「经典论文与原始文献」补 2020 年代条目 |
