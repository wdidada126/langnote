## 核心精讲

### 4.1 关键原则：从 Scrum 开始

本书的建议是：**把 Scrum 当作方案空间里的默认起点**，理由不是 Scrum 最好，而是：

| 理由 | 说明 |
| --- | --- |
| **共享词汇** | 组织里所有人（包括不写代码的人）对「sprint / 待办列表 / 站会」有共识，沟通成本最低 |
| **可诊断** | 出现问题时，能定位到「是流程错了还是纪律松了」，其他框架则难以归因 |
| **有参考基线** | 后面 Ch19.1 会把 Scrum 当过程改进的基线——基线需要先存在一个 |
| **失败模式已被记录** | 本书 4.2 一大节就在做这件事；踩过的坑已经被写下来了 |

> 注意本书的态度：**从 Scrum 开始，不等于必须用 Scrum 到底**。环境不同（分布式、受监管、组合管理）时后面的章节会给出调整建议（见 `05`/`12`）。

### 4.2 / 4.3 常见失败模式及其共同点

原书把失败模式逐条列出后，归纳出共同点。本笔记按「机制」重新分组，方便对照自查。

| 失败模式（本笔记归类） | 典型表现 | 背后的共同点 |
| --- | --- | --- |
| **形式化：把仪式当敏捷** | 站会变成进度汇报；看板只记录不动； retrospective 永远「大家都很棒」 | 只执行 Practices，没有 Goals |
| **承诺错位：用「承诺」替代「应变」** | sprint 背上的任务被领导锁定，需求进来只能加班 | 把迭代计划当成不可变的合同 |
| **伪跨职能：团队缺关键角色** | 测试、运维、业务决策在外，团队仍需等别人 | 「跨职能」只是名字里有 |
| **无发布能力：迭代结束不能发布** | 每个 sprint 结束都要上线协调会，实际发布周期一个月 | 缺少 CI/CD 与可发布性（见 `09`） |
| **指标政治化**：见 `11` | 速度被拿去和其他团队比较，团队开始灌水 | 度量被用于考核而非改进 |
| **领导缺位：SM 变成了协调员** | 教练只负责排会议，不做障碍清除 | 「管理结果，而不是管理细节」的原则没有落地（见 `10`） |

**共同点（4.3）可归纳为两条**：

```
共同点 ①：目标缺失 —— 只搬来了 Practices（实践），没有建立 Goals（目标）。
          → 检验：问团队「你们这个 sprint 想验证什么假设？」，答不上来即为缺失。

共同点 ②：反馈断裂 —— 有了节奏，但没有「真实反馈」进入循环。
          → 检验：一个 sprint 结束时，有多少东西真的被用户/业务用过并产生了调整？
```

> 本笔记特别强调一条本地旧摘录里出现的现实：**「名为敏捷、实为外包加周报」**。它的判定标准非常清晰——需求在外包侧、决策在外包侧、业务验收在另一边，中间的「团队」只是把任务转手。这种结构下**任何 Agile 流程都只是传声筒**，因为反馈环被组织边界切断了。这也是 4.3「反馈断裂」的极端形式。

### 4.4 Scrum 中的成功因素

与失败模式互为镜像，本书给出的成功因素可整理成下面这张「先做什么」的顺序表。

| 顺序 | 成功因素 | 落地标志 |
| --- | --- | --- |
| 1 | 明确目标（Goal 而非仅 Tasks） | 每个 sprint 都写「验证什么假设 / 交付什么价值」 |
| 2 | 建立可发布的能力 | 每个迭代末都能真正上线或演示真实可用功能 |
| 3 | 让团队真正跨职能 | 测试与生产支持在团队内（详见 `04`） |
| 4 | 保护节奏，同时允许变更 | 版本范围可变，时间盒不变 |
| 5 | 用数据（速度）做预测，不做考核 | 速度只用于预测，不进 KPI（详见 `11`） |

### 4.5 / 4.6 一个成功的 sprint 与典型时间分配

原书用一节讲时间分配，本笔记把它转成一个更直观的「一周节奏示意」（教学示意）。

```
 Sprint（2 周示例，仅结构示意）
 ├─ Day 1    计划会：从产品待办列表中取本轮切片 → 建立 sprint 目标
 │            （半小时，只写目标与大致范围，不做详细分解）
 ├─ 每日 Scrum  15 分钟 × 10 天：检视进度、暴露阻塞（不是汇报）
 ├─ 持续      开发 + 自动化测试 + 每日集成
 ├─ 随时      细化（refine）下一个 sprint 的待办，保持列表健康
 └─ Day 10   评审（展示可工作软件）→ 回顾（检视与调整）
```

> 时间分配的核心提示：**会议时间应显著小于开发时间**。如果站会、计划会、评审会加起来超过团队时间的 20%，团队就在「谈敏捷」而不是「做敏捷」了。

### 4.7 向 Scrum 过渡的问题

| 过渡阶段 | 典型问题 | 建议动作 |
| --- | --- | --- |
| 刚起步 | 团队不清楚要「改行为」而不是「加会议」 | 先只做三件事：时间盒、可发布切片、每日暴露阻塞 |
| 遇到阻力 | 业务方不愿参与优先级决策 | 先明确「谁是产品负责人」，无人认领时领导者要自己上（见 `08`） |
| 速度不稳 | 用速度做承诺，导致压榨 | 前 3–4 个 sprint 只用速度预测，不做考核 |
| 遇到外部依赖 | 需求依赖上游或外包，节奏被打乱 | 调整切片粒度，把等待期变成有价值的准备工作 |

### 4.8 Scrum 计分卡（用法说明）

原书 4.8 给了一套计分卡。计分卡的**正确用法是「定期打分 + 记录趋势」**，而不是「一次打分定生死」。

| 维度 | 打 1 分的信号（不健康） | 打 5 分的信号（健康） |
| --- | --- | --- |
| 目标清晰度 | sprint 只有任务列表 | 有明确目标与验证假设 |
| 可发布性 | 迭代末仍需大规模协调才能上线 | 每次迭代都能真实发布 |
| 跨职能程度 | 测试/运维在团队外 | 关键角色在团队内且决策在本地 |
| 变更响应 | 范围锁定，需求进来只能加班 | 范围随优先级调整，时间盒稳定 |
| 检视有效性 | 回顾会从不产出行动项 | 回顾产出行动项并有人负责 |
| 度量健康度 | 速度被当 KPI | 速度只用于预测 |

## 近年研究与工业界开源实践（2015–2026）

1. **「伪敏捷」的工业识别**：2020 年代社区与咨询界反复确认本书 4.2 的失败模式仍在——形式化站会、速度政治化、迭代末不能发布。判断真伪的硬指标是**「迭代末能否真正上线」**。
2. **Scrum Guide 2020 的争议**：官方把 Scrum 定为「轻量框架 + 问责制」，而很多组织的实践更接近 2009 版。本书的取向偏向管理实用，读者可按 4.8 计分卡自行裁定。
3. **DORA 与 Flow Metrics**：DORA 2024 修订版把「四把钥匙」调整后改称 **Software Delivery Performance**，同时流出 flow metrics（流动效率四类指标）。这为「sprint 里发生了什么」提供了比「速度」更实在的口径（详见 `11`）。
4. **AI 进入站会与评审**：2024–2026 常见的做法是用 AI 生成站会纪要、会议摘要、评审演示脚本，把人从记录工作里解放出来，**守住 15 分钟**是这个做法的前提。
5. **远程/混合后的每日 Scrum**：时区跨越大时，每日 Scrum 常常被迫取消或改成异步文字。此处必须遵守 4.9 的原则——**暴露阻塞优先于同步沟通**，详见 `05`。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **AI 让「速度」更不可信** | 用 AI 助手后，故事点的产出可能虚增，速度曲线被污染 | 速度改与「交付前置时间 / 缺陷逃逸率」交叉验证；速度彻底退出 KPI |
| 2 | 🔧 **计分卡缺少「AI 使用」维度** | 团队用 AI 生成大量代码，质量维度无人打分 | 计分卡增加一列：验证覆盖率与关键路径的人工审查比例 |
| 3 | **把 sprint 目标写成任务清单** | 「本轮完成 37 个故事点」 | 目标应写「验证/交付什么」，见 4.4 |
| 4 | **把速度当 KPI**（原书 4.8 未展开此副作用） | 跨团队速度排名 → 灌水、拆任务刷点 | 见 `11-度量与过程改进`，重点读 Ch18.3「度量的一般注意事项」 |
| 5 | **每日 Scrum 变成状态汇报** | 站着reporting 给经理听 | 回到 4.9：暴露阻塞；同步沟通需求（如需要详细进度）应在会后单独进行 |
| 6 | **迭代末不能发布却仍宣称敏捷** | 「我们做增量交付」但发布周期一个月 | 用 CI/CD 与部署流水线补底座（见 `09`） |
| 7 | 🔧 **向 Scrum 过渡的顺序在 2026 年被重写** | 原建议「先上流程」，现在更常见的是「先上 CI/CD 与自动化测试」 | 过渡顺序建议改为：先建立可发布能力，再谈框架；见 `09` 与 `07` |
| 8 | **「外包加周报」被当成敏捷** | 需求与决策都在外包侧，只剩周会 | 明确判定：反馈环被组织边界切断即非敏捷；优先补决策权与内联测试 |
