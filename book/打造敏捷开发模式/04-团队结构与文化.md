## 核心精讲

### 5.1–5.4：团队结构的四条硬要求

本书在结构上给出的建议可以压缩成一张「能力完整度」自检表。**判断标准不是组织图，而是能力清单**。

```
一个「跨职能」团队的能力自检（打勾为具备）
├─ 需求能力：能自己澄清需求、写清验收标准（不必等别人翻译）
├─ 设计能力：能做出满足质量与可维护性的设计
├─ 实现能力：能写代码并写自动化测试（见 Ch12）
├─ 验证能力：能构造并执行回归、性能、端到端验证（测试在团队内）
├─ 发布能力：能自己把东西部署上线并观测（运维在团队内）
└─ 决策能力：能当场决定优先级与范围（业务代表在决策链上）
```

| 缺口 | 后果 | 本书对应小节 |
| --- | --- | --- |
| 测试在团队外 | 缺陷检测时间变长（Ch11.1 的核心成本项） | 5.2 / 5.3 |
| 生产支持在团队外 | 「持续交付」无法兑现，只能靠发布协调会 | 5.4 |
| 业务决策在团队外 | 团队只能执行不能选择，速度再快也不解决问题 | 6.3 |
| 整个团队被当黑盒外包 | 反馈环被组织边界切断 | 5.5 |

> **「被视为黑盒的敏捷团队」（5.5）**是本笔记最想强调的一条。它的典型形态是：公司 A 外包给公司 B，B 用敏捷流程交付，A 那边只收文档与演示。**流程在 B 内部是正常的，但整个交付链路上没有任何反馈机制**——A 不知道做的是什么水平的东西，B 也不知道做得对不对。这类项目的敏捷程度再高，业务价值也接近零。

### 5.6：你的组织愿意创建敏捷团队吗

原书在这一节把问题抛回给组织。本笔记把它翻译成转型前的三个硬性自问：

| 自问 | 若答案为「否」的现实含义 |
| --- | --- |
| 组织愿意把决策权下放到团队吗？ | 团队只能执行，敏捷必然退化成「更快的瀑布」 |
| 组织愿意让团队对生产负责吗？ | 团队没有发布权，无法承诺「每次迭代可发布」 |
| 组织愿意为跨职能付出人力成本吗？ | 为了省一个人而把测试推到别处，等于用长期成本换短期编制 |

> 这三个问题的答案决定了敏捷转型的**天花板**。很多失败不是因为执行差，而是因为组织根本没打算放权。

### 6.1 关键原则：通过自主、专精和目标来激励团队

本书的激励模型可以看做是对「如果员工不受激励，就无法做好工作」这一假设的否定。

| 激励项 | 落地做法 | 反面做法 |
| --- | --- | --- |
| **自主 Autonomy** | 让团队自己决定怎么做、分多少次、谁做什么 | 每一步都批准，只给「目标」不给「方法权」 |
| **专精 Mastery** | 让工作「有难度且能学会」，为技能提升留时间 | 全是重复劳动，无学习空间 |
| **目标 Purpose** | 说清为什么做、为谁做 | 只说「这是老板要的」 |

### 6.2 关键原则：培养成长思维

成长思维（growth mindset）来自 Carol Dweck 的研究：人的能力可以通过努力发展。**它与敏捷的复盘（retrospective）直接耦合**——如果一个组织是「固定思维」（业绩差 = 人不行），复盘就必然变成追责现场，而追责会直接杀死反馈。

```
成长思维： 「这个功能上线后流失率上升了，我们的假设错在哪？」  → 学到东西
固定思维： 「这个功能上线后流失率上升了，谁负责的？」          → 学到沉默
```

### 6.3 关键原则：培养以业务为中心

| 维度 | 以技术为中心 | 以业务为中心 |
| --- | --- | --- |
| 拆分方式 | 按技术分层拆（前端组/后端组/DBA 组） | 按业务能力或垂直切片拆（见 Ch9.4） |
| 验收标准 | 「按需求文档实现完毕」 | 「业务指标 / 用户行为是否改善」 |
| 优先级 | 谁嗓门大谁先做 | 按价值与成本排序（见 Ch14） |

> 教学示意（能力自检树、成长思维对照均为**教学示意，不编译、不运行、不参与构建**）。

## 近年研究与工业界开源实践（2015–2026）

1. **DevEx（开发者体验）进入研究视野**：2020 年代实证研究（如 Microsoft 研究团队的 DevEx 相关研究）指出，**开发者的摩擦（friction）主要来自工具与系统，而不是人的积极性**——这与本书 5.1「结构决定上限」的结论完全一致。
2. **You Build It, You Run It 回归**：平台工程（IDP）把「谁开发谁运维」的成本内部化，本书 5.4「生产支持要纳入团队」在 2023–2026 获得了新证据：把运维推到别处，团队对质量的感知会显著下降。
3. **团队规模与认知负载**：Conway 猜想 + Team Topologies 的「认知负载」概念，被大量组织用来决定「团队该拆到多小」。本书没有给具体人数，这里可以补一条工程实践：**一个团队能同时理解的上下文总量决定了它的上限**。
4. **远程/混合下的团队文化**（2023–2026）：心理安全在异步环境里更依赖**书面记录与公开复盘**，口头善意无法跨时区传递。
5. **AI 对「专精」的挑战**：AI 助手让初级开发者写作速度快速接近资深，**「专精」的重心从「写代码」迁到「设计、验证与判断」**。这直接影响 6.2 的落地方式：给初级工程师的成长路径必须重写。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **AI 编码让「测试在团队外」更致命** | 用 AI 生成代码，验证责任更集中；测试在外部团队时无人对正确性负责 | 坚持 5.3：测试内联；关键路径保留人工审查清单 |
| 2 | 🔧 **「专精」的定义需要随 AI 重写** | 成长路径还是「练手写代码」，但那部分已被自动化 | 成长路径改为「设计 / 验证 / 判断 / 沟通」四类能力 |
| 3 | **把跨职能理解成「人人都是全栈」** | 要求所有人什么都做，结果没人做得深 | 跨职能是**能力完整**，允许专精分工，只是瓶颈环节要能自己补 |
| 4 | **把「将测试人员整合进团队」理解成取消测试岗** | 测试被压成「点点的」 | 正确做法是把测试能力**分配进团队**，同时保留测试专家作为社群（6.4） |
| 5 | 🔧 **黑盒外包的判定标准需要量化** | 只凭直觉说「这是黑盒」 | 增加判据：反馈环是否有至少一条「开发 ↔ 真实用户/业务」的直接通路 |
| 6 | **自主被误解为「无管理」** | 领导完全退出，问题无人拍板 | 6.1 的自主是「方法自主 + 目标共同」，领导者对目标负责 |
| 7 | **成长思维只写在墙上** | 组织仍按「谁搞砸谁走人」运作 | 用复盘不追责 + 心理安全（Ch17.2）把它做成制度 |
| 8 | 🔧 **团队拓扑缺少「平台团队」这一型** | 让每个团队各自重复造流水线 | 引入平台团队承担公共能力，正是 5.1 的规模化版本 |
