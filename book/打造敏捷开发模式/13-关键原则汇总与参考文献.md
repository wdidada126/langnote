## 核心精讲

### 「享受劳动果实」：这本书的態度

原书结尾只用很短的篇幅写这段，但它是全书最「作者本人」的一段。它提醒读者两件事：

1. **敏捷的产出是能用的东西**（working software），不是看板、不是站会记录、不是成熟度分数；
2. **别把过程当目的**——这也是为什么本书的每一章都以「给领导者的行动建议」收尾，而不是以「更多要做的事」收尾。

> 本笔记给这段的最实用翻译：**如果一个组织能列出 30 条它坚持做对的敏捷事项，却说不出它上次因为敏捷而更早交付了什么，那它只是在做敏捷的外科手术。**

### 一句话决策表：五问自检

把全书的判断压缩成一次 20 分钟的团队自检，可以作为季度回顾的收尾动作：

| 问题 | 如果是「否」 |
| --- | --- |
| 1. 我们最近一次「想法 → 真实反馈」有多长？ | 反馈环太长，其他改动都不重要 |
| 2. 每个迭代结束，能不能真的上线？ | 先修发布能力，别谈别的改进 |
| 3. 关键角色（测试、运维、业务决策）在不在团队里？ | 跨职能只是名字 |
| 4. 我们有没有一次review 真的改了什么？ | 检视已经退化成仪式 |
| 5. 度量有没有被用来考核个人？ | 先停止考核，数据才会诚实 |

### 原书「参考文献」导读（p.235）

原书参考文献不是罗列，而是有结构的。本笔记按主题给一个读法建议：

| 主题簇 | 大致构成 | 建议读法 |
| --- | --- | --- |
| **敏捷的起源与宣言** | 敏捷宣言（2001）、XP/Scrum 早期著作、敏捷宣言背后的论文 | 只读宣言 + 早期两本经典，够用了 |
| **复杂性与决策** | Cynefin（Snowden 系列）、OODA（Boyd）相关文献 | 读 HBR 2011 那篇 + Boyd 的《Patterns of Conflict》摘要 |
| **度量与实证** | Accelerate（2018）、DORA 年度报告、Construx 的实践调查 | 只信任有口径的研究；注意指标口径会变（2024 修订） |
| **过程改进与风险** | Boehm 系列论文（风险与计划驱动/敏捷的平衡） | 读 Boehm & Turner 2003 一篇即可 |
| **受监管行业** | IEC 62304、AAMI TIR57、FDA 相关问答、ISO 26262、DO-178C、GAMP 5 | 按自己所在行业只读对应的那份标准 |
| **工程实践底座** | Continuous Delivery、Test-Driven Development、Refactoring 类著作 | 这些是 `07`/`09` 章的外部依据 |

> 读参考文献的正确姿势：**它们是树，不是清单。**选一棵树种下去（例如「敏捷的起源」这一簇），读完三篇就能解释一大类现象；每篇都浅读一遍，收获接近于零。

## 近年研究与工业界开源实践（2015–2026）

1. **「原则 → 指标 → 改进」的三段式成为组织常规**：把原则落成可跟踪的少量指标，再每周只看趋势。
2. **度量口径本身成为研究对象**：2024 年 DORA 修订说明了一个反复出现的教训——**指标必须能被真实数据支撑，否则会被流量与定义污染**。
3. **AI 时代原则的重排正在发生**：2026 年还没有公认的「AI 敏捷原则」，但已经形成的共识是：**责任必须明确到人，AI 不能成为责任的接口**。
4. **平台工程把「关键原则」变成默认路径**：当 DoD、审计留痕、发布能力都由平台提供时，原则不再需要靠培训传达。
