## 核心精讲

### 13.1 敏捷需求的生命周期

原书把需求当成有生命周期的对象。本笔记把它画成一条可被监控的流水线：

```
【需求来源】业务/用户/数据/技术债/合规
     │
     ▼
【故事化】写成一个可讨论的卡片（13.4）
     │
     ▼
【进入产品待办列表】准入规则（13.6）
     │
     ▼
【细化 refine】不断补细节、拆粒度（13.7）
     │
     ▼
【就绪 DoR 检查】是否可以进入本轮（13.8）
     │
     ▼
【进入迭代】本轮交付，形成验收标准
     │
     ▼
【验收】真实的可用功能 / 可验证假设
     │
     └──► 反馈回到需求来源 → 决定是否继续 / 砍掉 / 重新排序
```

| 常见卡点 | 症状 | 对应小节 |
| --- | --- | --- |
| 卡在「故事化」 | 需求以大段文字交付，没人能拆 | 13.4 |
| 卡在「列表」 | 待办列表上千条，没人看得完 | 13.5 |
| 卡在「细化」 | 承诺了才发现细节没定 | 13.7 |
| 卡在「就绪」 | 半成品需求进了迭代 | 13.8 |

### 13.2 / 13.3：敏捷需求的区别与 Cynefin 分域

**敏捷需求与传统规格的关键差异**：

| 维度 | 传统规格（前置完整） | 敏捷需求（持续澄清） |
| --- | --- | --- |
| 完成时机 | 开发前全部定稿 | 进入迭代前刚好够用 |
| 交付物 | 需求文档 | 可讨论的故事 + 验收标准 |
| 变更 | 走变更控制 | 预期内，按优先级调整 |
| 验证 | 事后验收 | 每个切片都验收 |

**13.3 用 Cynefin 处理需求**（呼应 `02` 章）：

| 需求复杂度 | 举例 | 处理方式 | 不要做的事 |
| --- | --- | --- | --- |
| 简单 Obvious | 「把按钮颜色改成品牌蓝」 | 直接做，不细化的 | 写三页规格 |
| 繁杂 Complicated | 「接入第三方支付」 | 专家分析、可选方案评审 | 靠试错碰答案 |
| 复杂 Complex | 「我们的定价模型要不要变」 | 先做小实验、用户访谈、再决定 | 提前写完整规格（注定作废） |

> 这条分表是本章最实用的部分：**同一个待办列表里的需求，复杂度不同，细化的投入应该完全不同**。把所有需求拉平到同一种规格书格式，是典型的时间浪费。

### 13.4–13.6：故事、容器与入口

| 元素 | 作用 | 关键判据 |
| --- | --- | --- |
| **故事 Story**（13.4） | 引发对话的邀约 | 「如果能……我会很高兴」，写不下说明该拆 |
| **产品待办列表 Product Backlog**（13.5） | 需求的容器与排序载体 | 要维护、要清理、要有 PO 拥有 |
| **准入规则**（13.6） | 控制列表质量 | 没有准入 = 垃圾进、垃圾出 |

| 待办列表健康度自检 | 不健康 | 健康 |
| --- | --- | --- |
| 条目数量 | 上千条且长期不动 | 保持「下一步看得完」的量级 |
| 粒度分布 | 全是超大条目 | 下一步的条目足够小 |
| 最近更新 | 三个月没动过 | 持续 refine（13.7） |
| 排序 | 无排序或由领导随手插队 | 有明确 PO 与排序依据（见 14.2） |

### 13.7 / 13.8：细化与就绪定义（DoR）

```
细化（refine）：只细化「下一步要用的」——约 1–2 个 sprint 的量
   ├── 拆粒度：大故事拆成小故事
   ├── 补细节：业务规则、边界、异常、数据要求
   └── 定验收标准：可被验证的观测点

就绪定义（DoR）：进入迭代的准入检查清单
   ├── 已拆到足够小
   ├── 验收标准明确
   ├── 依赖项已识别并有人负责
   ├── 与既有系统的一致性已考虑
   └── 业务价值已说明
```

| DoR 与 DoD 的区别（易混点） | 说明 |
| --- | --- |
| **DoR（就绪定义）** | 需求「能不能进这一轮」 |
| **DoD（完成定义）** | 任务「算不算做完」（见 `07`） |

### 14.1 产品负责人

| PO 的有效特征 | 无效特征 |
| --- | --- |
| 有决策权并愿意用 | 「我需要先问老板」 |
| 持续投入，不是兼职 | 每周出现一次 |
| 理解技术与业务两头 | 只承接业务要求向下传递 |
| 愿意为需求负责而不是为排期辩护 | 只做传声筒 |

> **本地旧摘录的现实提醒**（「某语音公司是敏捷」一类观察）：PO 缺位是伪敏捷最常见的组织症状之一。团队再自组织，只要优先级决策不在现场，节奏就只能在原地打转。

### 14.2 T 恤估算法

T 恤法（XS/S/M/L/XL）的价值在于：**它是排序工具，不是估算工具**。

```
步骤 1  产品负责人用 T 恤尺码给每条需求排序（不用点，只分档）
步骤 2  按尺码分档后（XS < S < M < L < XL）揭示「哪些明显更大」
步骤 3  只对最大的那几档做进一步估算（故事点或人日）
步骤 4  用排序结果做本轮取舍：「这轮做 XS+S+M 三件，还是不做 M」
```

| 与其他排序法的对照 | 特点 | 代价 |
| --- | --- | --- |
| **T 恤法**（本书 14.2） | 快、非数字、易被业务接受 | 精度低，不适合做长期合同承诺 |
| MoSCoW（Must/Should/Could/Won't） | 易沟通、强约束 | 尺度模糊，容易全都是 Must |
| Kano（基本型/期望型/兴奋型） | 抓住用户满意度非线性 | 需要用户调研数据支撑 |
| RICE（Reach×Impact×Confidence÷Effort） | 可计算、可复现 | 参数靠拍，容易变成伪精确 |
| WSJF（加权最短作业优先，见 `12`） | 组合与前置依赖排序 | 相对权重主观 |

> 本章立场：**先用故事地图建立全景（14.3），再用 T 恤法排序（14.2）**，不要用无数据的 RICE 制造精确感。

### 14.3 故事地图

```
用户旅程（横轴）              ↑ 优先级 / 深度（纵轴）
────────────────────────────────────────────
注册 ──► 登录 ──► 选品 ──► 下单 ──► 支付 ──► 售后
 │        │        │       │        │        │
 │        │        │       │        │        └─ 退换货（M）
 │        │        │       │        └─ 多种支付方式（S）
 │        │        │       └─ 优惠券（S）
 │        │        └─ 搜索与筛选（XS）
 │        └─ 记住设备（XS）
 └─ 第三方登录（XS）

第一行：用户旅程主干（ backbone ）
下面：  每一段的功能与升级项（ user tasks ）
排序：  在纵横两个方向上分别排序
```

| 故事地图解决的问题 | 说明 |
| --- | --- |
| 只见树木不见森林 | 有待办列表但看不出端到端体验哪里缺失 |
| 需求互相冲突 | 并列展示可发现矛盾假设 |
| 排序脱离用户路径 | 优先级可以按「主干 vs 支线」判断 |

> 教学示意（生命周期流水线、T 恤排序流程、故事地图均为**教学示意，不编译、不运行、不参与构建**）。

## 近年研究与工业界开源实践（2015–2026）

1. **需求优先级的研究持续**：学术界对 MoSCoW / Kano / RICE / WSJF 等方法的对照研究长期存在，结论反复指出：**方法的精度不是关键，关键是决策权与一致性**。这与本书 14.1（PO 授权）的立场一致。
2. **AI 生成需求与故事（2023–2026）**：从会议录音自动生成故事卡、验收标准、待办条目，已成为常见实践。真实收益是**省掉记录工作**；真实风险是**生成一堆看起来合理、但没有真实用户依据的需求**。因此补充证据显示：**「AI 写需求」的有效前提是已经有真实的用户输入**。
3. **「需求到发布」的流动效率可视化**：DORA 与 flow metrics 的推进，让「需求停在待办列表里多久」第一次成为可度量的指标——这直接补充了本笔记 13.1 流水线的卡点诊断。
4. **就绪定义被工具化**：部分平台把 DoR 校验做成「进入迭代前的自动检查」，减少口头确认。
5. **产品负责人角色的再定位**：2020 年代社区更强调 PO 的「决策密度」而非「决策次数」，即一次决策要尽量把相关需求一次定清。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **AI 生成需求的「看似合理」陷阱** | 用 AI 从纪要生成一堆故事，含大量无依据需求 | AI 只做记录与结构化；真实需求必须来自用户/业务输入，PO 逐条背书 |
| 2 | 🔧 **DoR 缺少「来源可追溯」这一条** | 需求无法回答「为什么要做」 | DoR 增加：来源（用户访谈 / 数据 / 合规）与验证方式 |
| 3 | **把 T 恤法当成估算工具** | 用 T 恤尺寸换算成程序员天数 | 14.2 是排序工具；需要绝对量时再补细粒度估算 |
| 4 | **把 DoR 和 DoD 混用** | 「这个需求还没 DoR」其实是说完成标准 | 明确区分：DoR 管准入，DoD 管完成（见 `07`） |
| 5 | **PO 缺位被当成个人问题** | 寄希望于换一个 PO 解决 | 缺位是授权问题；没有决策权的人不能当 PO（14.1） |
| 6 | **一次性细化全部需求** | 迭代前集中细化两小时，产出大量用不上的细节 | 只细化下一步（13.7），并按 Cynefin 分域投入（13.3） |
| 7 | 🔧 **优先级排序缺少「可撤回性」维度** | 排进去的东西一旦开工就很难砍 | 复杂区（13.3）的需求优先选可撤回的小实验，见 `02` |
| 8 | **把故事地图当成画图练习** | 画完收进抽屉 | 故事地图用于「排序」和「识别主干缺失」，每次排期前更新 |
