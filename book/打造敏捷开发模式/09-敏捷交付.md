## 核心精讲

### 15.1 关键原则：自动化重复性工作

本书的第一条建议极其朴素：**找出所有「每次都要人做一遍」的动作，把它们变成脚本或配置。**

```
候选自动化清单（按投入产出排序）
├─ 构建与打包                 → 每次提交都要做，必须自动化
├─ 自动化测试（单元/集成/契约）→ 每次提交都要跑，必须自动化
├─ 代码质量与静态检查         → 每次提交都要做，必须自动化
├─ 环境创建与配置             → 每次新环境都要做，必须自动化
├─ 数据库迁移                → 每次都要做，必须自动化且可回滚
├─ 部署与回滚                → 每次发布都要做，必须自动化
├─ 制品与版本管理            → 必须自动化（避免「这台机器上是好的」）
└─ 报告与统计（发布说明、变更单）→ 可自动化，但要小心过度自动化
```

| 判断标准 | 说明 |
| --- | --- |
| 频率高 | 越频繁的事，自动化的收益越大 |
| 人工易错 | 人工做 100 次就会错一次 |
| 阻塞反馈 | 需要人等的环节会拖慢整个环 |
| 可重复 | 需要人工判断的不适合全自动化 |

### 15.2 支撑 CI/CD 的工作实践

这是本章最容易被跳过、却最关键的一节：CI/CD 不是「装一套工具」，而是**一系列工作习惯的副产品**。

| 需要改变的工作实践 | 为什么必须改 | 不改的后果 |
| --- | --- | --- |
| 频繁提交到主干（trunk） | CI 只有在频繁提交时才有意义 | 分支堆积，最后合并地狱 |
| 每次提交都触发构建与测试 | 反馈必须到达个人 | 失败要等一天才被发现 |
| 测试足够快 | 快到可以每次提交都跑 | 于是只能在夜间跑，反馈延迟一整夜 |
| 失败要立刻修 | 「红」超过一天就等于放弃这条流水线 | 红灯常态化，CI 变成装饰 |
| 环境可自助获取 | 不依赖某个人的机器 | 环境不一致，问题无法复现 |
| 用版本库管理配置与迁移脚本 | 部署可重现 | 「手工改过几台机器」不可审计 |
| 有回滚方案 | 失败时能倒回去 | 出事只能往前冲 |

### 15.3 采用 CI/CD 的好处

原书把好处落在这几处，本笔记补上它与全书的接口：

| 好处 | 机制 | 与本书其他章的关系 |
| --- | --- | --- |
| **反馈更快** | 缺陷在提交时就被发现 | 直接支撑 Ch11.1「缺陷检测时间最短」 |
| **风险更低** | 小步发布意味着单次变更影响面小 | 支撑 Ch9.4 垂直切片 |
| **可预测性提升** | 发布成为常规操作，不再是大事件 | 支撑 Ch20 可预测性讨论 |
| **团队敢改** | 有自动化安全网，重构才有底气 | 支撑 Ch9.5 技术债管理（`book/重构/`） |
| **减少协调成本** | 团队自己能发布，不必等别人 | 支撑 Ch5.4 生产支持在团队内 |

```
没有 CI/CD：发布 = 事件（需要排期、需要人盯、出错要通宵）
     ↓
有 CI/CD：发布 = 操作（随时可以，出错就回滚）
     ↓
持续交付：可发布状态永远是「真」的，选择何时发布是业务问题
```

### 15.4 其他考虑：持续交付

| 概念 | 含义 | 常见混淆 |
| --- | --- | --- |
| **持续集成 Continuous Integration** | 频繁向主干合并并自动验证 | 与「每天合并一次」混淆（那不是 CI） |
| **持续交付 Continuous Delivery** | 随时可以安全发布到生产的能力 | 被误读成「必须自动发布」 |
| **持续部署 Continuous Deployment** | 每次通过验证的变更自动上线 | 与持续交付混淆 |
| **持续交付 ≠ 频繁发布** | 有能力随时发布，是否发布由业务决定 | 「我们做了 CD，但半年才发一次」 |

> 判断一个团队是否真有「持续交付能力」，用一个问题就够了：**现在让你在生产环境上线这个功能，需要几个人、多久、能不能回滚？** 如果答案是「要协调三个人、两天、回滚要手动处理」，那就还没有。

## 近年研究与工业界开源实践（2015–2026）

1. **GitOps 成为主流范式**（2019 起，2020–2026 普及）：以声明式配置 + 版本库为唯一事实源，让「发布」这件事本身可审计；这直接满足 `12` 中受监管行业的证据链要求。
2. **DORA 2024 修订（2024-07）**：Google Cloud 发布《2014–2024: The Evolution of DevOps Metrics》，对「四把钥匙」做了调整，并把「AI 辅助开发的采用情况」纳入调研。**读过本书 15 章的读者应该补这一条**，因为度量口径变了（详见 `11`）。
3. **AI 进入交付流水线（2023–2026）**：自动写发布说明、自动回归定位、AI 评审配置变更、AI 生成测试用例。这里要守 15.2 的一条原则：**自动化的对象是「重复性工作」，不是「责任」**。
4. **部署频率与业务节奏解耦**：2020 年代的共识是「能不能发布」是技术问题，「什么时候发布」是业务问题——正是本书 15.4 的立场。
5. **回滚能力成为硬指标**：多人规模的实践开始把「回滚耗时中位数」当作与部署频率同等重要的指标，因为它是**发布安全的下限**。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **DORA 指标口径 2024 年已修订** | 仍按旧的「四指标」对齐目标 | 补读 DORA 2024 的修订说明；指标名改为 Software Delivery Performance（见 `11`） |
| 2 | 🔧 **「CI/CD 已建成」不等于「可发布能力存在」** | 有流水线但发布仍要人工协调 | 用「几个人 / 多久 / 能否回滚」三问现场验证 |
| 3 | **把持续交付理解成「必须每天发布」** | 为了频率而频率，制造不必要风险 | 15.4 的立场：能力 ≠ 频率，频率由业务决定 |
| 4 | **红灯常态化** | 流水线长期红着，最后靠「人肉验证」放行 | 回到 15.2：失败必须立刻修，红灯不过夜 |
| 5 | **自动化了但没有 owner** | 脚本没人维护，慢慢腐化 | 每个自动化环节都要有明确的负责人与值班安排 |
| 6 | 🔧 **AI 生成的发布内容未经人工确认** | 自动生成变更单，写错影响用户 | 涉及对外沟通的自动化内容必须人工复核 |
| 7 | **把环境差异当成「暂时问题」** | 「生产是另一套配置」 | 15.2 明确要求配置与迁移脚本进版本库 |
| 8 | **只自动化「构建」，不自动化「验证」** | 构建很快，但验证要人跑一遍 | 自动化的重点在验证环节，否则反馈并未缩短 |
