## 核心精讲

### 20.1–20.2：可预测性的类型

本书最有价值的一组区分：

```
可预测性类型
├── 进度可预测性：什么时候能有一个「大致可用的东西」
└── 结果可预测性：这个功能上线后业务结果会怎样
```

| 类型 | 敏捷能做得多好 | 现实约束 |
| --- | --- | --- |
| 进度（时间 + 大致范围） | 较好（靠速度与历史产能） | 范围必须可协商 |
| 结果（业务指标改善） | 差（取决于市场、用户、实现方式） | 不能拿结果与日期互换承诺 |
| 精确需求（功能细节） | 随临近而升高 | 别用「高保真原型」伪装确定性 |

> 一个精明的领导者做法：**承诺「时间 + 可协商范围」，不承诺「功能清单 + 日期」**，同时把结果指标与验证机制事先约定（这也呼应 `08` 的验收标准与 `02` 的 OODA）。

### 20.3–20.4 边界与灵活性

| 场景 | 对可预测性的要求 | 建议做法 |
| --- | --- | --- |
| 业务需求高度不确定 | 低 | 用范围换时间，快速验证 |
| 有固定发布日期（如品牌活动） | 中 | 固定时间，砍范围；提前识别「不做不可」的核心 |
| 合同固定需求 | 高 | 计划驱动 + 敏捷改进（见 `01` 的边界） |
| 合规硬期限 | 高 | 见 Ch21，需要证据链与时间缓冲 |

### 21.1–21.2：受监管行业中的敏捷

原书 Ch21 的正向论点成立：**迭代与增量更容易满足「早期验证 + 变更留痕」的要求**。本笔记按 2026 年可查的合规体系补充证据链要点。

| 领域 | 常见标准要求 | 敏捷落地的证据链 |
| --- | --- | --- |
| **医疗器械软件** | **IEC 62304**（医疗器械软件生命周期，2006+AMD1:2015；IEC 62304:2022 版已发布）；美国 **FDA** 对软件生命周期相关要求的说明；**AAMI TIR57**（2017）专门讨论受监管环境下的敏捷应用 | DoD 中固化「验证与确认记录」；每个切片的评审与批准留痕 |
| **汽车功能安全** | **ISO 26262**（2018），第 6 部分规定汽车安全生命周期 | 安全相关需求的验证证据 + 工具鉴定 + 变更影响分析 |
| **航空航天** | **DO-178C**（2011）与其工具鉴定要求 | 高关注点代码通常不适合纯敏捷，需混合流程 |
| **食品 / 药品 / GxP** | **ISPE GAMP 5**（第 2 版，2022） | 按「系统复杂度与风险」分类，敏捷用于低风险部分 |
| **财务报告相关 IT** | **SOX**，通常落在 **ITGC**（IT 通用控制）上 | 变更管理、访问控制、审计日志必须完整 |

| 敏捷与审计的接合处 | 做法 |
| --- | --- |
| 把 DoD 当作「记录点」 | 每个切片的完成都有其证据（测试、评审、批准） |
| 把版本库当审计对象 | GitOps + 语义化版本 + 发布说明，形成可追溯链 |
| 把风险分类前置 | 在需求就绪时判定该条需求是否属于受控范围 |
| 把人工检查写进流程 | 高风险部分保留人工评审与签字，不要为了快而跳过 |

### 21.3 受监管系统的敏捷边界

```
可以较自由敏捷的部分：  业务逻辑、用户界面、内部工具、数据管道
需要额外控制的部分：   安全关键逻辑、算法模型、受控文档生成、对外承诺的合规声明
—— 区别不是「能不能敏捷」，而是「证据链要写多细」
```

### 22.1 加权最短作业优先（WSJF）

WSJF 是原书 22.1 的核心，也是本书少见的**可计算**方法：

```
WSJF = (用户价值 + 时间收益 + 风险降低 + 机会赢得) / 工作总量

其中「成本 = 相对规模估计（如斐波那契数）+ 推迟到未来的延迟成本」
```

| 步骤 | 说明 |
| --- | --- |
| 1. 粗估规模 | 用斐波那契（1,2,3,5,8,13…）而不是绝对天数 |
| 2. 评估各分量 | 用户价值、时间收益、风险降低、机会赢得，各给相对分 |
| 3. 求和作分子 | 相对加权 |
| 4. 除以规模 | 得到 WSJF 值 |
| 5. 排序 | 从高到低；**并把前置依赖（spike）优先安排** |

> WSJF 的关键不是公式，而是**「延迟成本」这一项**——它把「现在不做会更贵」这件事显式化了，正是组合层最容易被拍脑袋忽略的部分。
>
> 与本书 14.2 T 恤法的分工：**T 恤法做单团队内的粗排序（不需数据），WSJF 做跨团队 / 跨季度的组合排序（需要相对打分）**。

### 22.2 其他考虑：T 恤估算法

T 恤法在本章是作为「WSJF 的输入」出现的——先用尺码做粗筛，再对少数几个大件做详细评估，避免给几十条需求都算精确分。

### 23.1–23.2：一般变革方法与多米诺变革模型

原书 23.2 提出「多米诺变革模型」。它的要点是：**变革要按「人—过程—工具—实践—制度」的顺序依次倒下，顺序错了就推不动。**

```
        制度（激励、考核、组织结构）
              ▲
              │ 支持
              │
        实践（Standup / CI / TDD 等具体做法）  ← 最先看起来最容易做
              ▲
              │
        工具（流水线、看板、自动化）             ← 通常最先被采购
              ▲
              │
        过程（流程定义）

⚠ 常见错误：先买工具 → 先定流程 → 看起来什么都有了，但人没动
```

| 变革顺序 | 说明 |
| --- | --- |
| 先有痛感 | 不痛就不要变革 |
| 先有小而可见的胜利 | 多米诺需要第一个倒下的支点 |
| 再制度化 | 把有效的做法写进考核与组织结构 |
| 允许回滚 | 转型也是实验，失败要能退 |

### 23.3–23.4 传播变革 & 再谈高层推广

| 传播机制 | 做法 | 反例 |
| --- | --- | --- |
| 先锋团队（pioneer） | 选一支愿意试的团队，做成样板 | 让所有人同时开始 |
| 可见成果 | 让高层看见先锋团队的真实产出 | 只在内部报告里说好 |
| 教练 / 社群 | 从先锋团队长出教练 | 外请顾问讲三天就走 |
| 制度固化 | 把 DoD / 发布能力写进规范 | 只靠口头倡导 |

### 23.5 检视和调整

第 23 章用一个「检视和调整」收尾，含义是：**敏捷转型本身也要被当成一个项目来检视**——用同一套指标（交付前置时间、发布频率、缺陷逃逸率、团队心理安全）来评估转型效果，而不是用「大家觉得更敏捷了」。

> 教学示意（可预测性类型、WSJF 计算、多米诺模型均为**教学示意，不编译、不运行、不参与构建**）。

## 近年研究与工业界开源实践（2015–2026）

1. **合规科技（RegTech）与审计自动化**：2020 年代大量组织把「审计留痕」做成自动化（策略即代码、发布说明自动生成、变更记录不可篡改），这直接补强了本书 21.1「敏捷支持受监管工作」的论断——**只要证据链是自动生成的，敏捷节奏与合规并不冲突**。
2. **平台工程降低合规成本**：IDP 把「安全基线 + 审计日志 + 访问控制」做成默认路径，团队想做得不合规都难。
3. **AI 在受监管行业的验证难题（2023–2026）**：AI 生成的代码与模型很难满足「可解释 + 可追溯 + 可复现」的证据要求。当前常见做法是：**AI 只用于低风险/辅助环节，高风险部分保留人工验证与完整记录**——正是 21.3 边界判断的直接应用。
4. **组合管理从 WSJF 到 OKR**：2020 年代很多组织把 WSJF 与 OKR 结合，用季度目标约束 WSJF 的权重来源，避免「权重靠拍」。
5. **转型评估的量化**：用与前同样的指标评估转型（前置时间、发布失败率、员工体验），而不是「敏捷成熟度评分」。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 表现 | 修正与补强 |
| --- | --- | --- | --- |
| 1 | 🔧 **受监管行业未覆盖「AI 生成代码的验证证据」** | 用 AI 生成受控代码，却拿不出验证记录 | 高风险部分：AI 只用于辅助；完整保留人工验证与签字记录 |
| 2 | 🔧 **IEC 62304 的新版（2022）与 ISO 26262 的实际落地细节未涉及** | 按旧版理解医疗器械与汽车的合规要求 | 按现行版本核对；关注工具鉴定与变更影响分析 |
| 3 | 🔧 **度量口径（DORA 2024 修订，改名 SDP）应与预测模型对齐** | 预测用旧阈值的历史数据 | 用修订后的口径重新校准基线，见 `11` |
| 4 | **把 WSJF 当成精确公式** | 给一个小数点后两位的「科学性」 | WSJF 的输入是主观打分，价值在于显性地讨论权重 |
| 5 | **把「可预测」等同于「提前定死功能」** | 要可预测就锁需求 | 20.4 的正解：时间可承诺，范围可协商 |
| 6 | **受监管 = 全部流程加严** | 所有需求都按最高标准管控 | 21.3 的边界判断：按风险分级，不是一刀切 |
| 7 | 🔧 **变革路径在 2026 年被重写** | 原书顺序（工具/过程先）与当下实践（平台 & 数据先）有差异 | 现代顺序建议：先做「可发布能力 + 度量」，再推流程与制度 |
| 8 | **转型效果用「成熟度评分」衡量** | 花几周填问卷，分数上升但交付没变 | 用交付指标与团队体验数据双向验证（23.5） |
