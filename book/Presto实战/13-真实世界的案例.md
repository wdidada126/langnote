## 精讲

### 1. 本章的正确读法：合上书本题自答
本章原书着墨短（约 5 页），本质是**案例叙事**而非机制清单。建议读法：
拿前 12 章各出一条"现场决定"，反推依据——
- 为什么拆多集群？→ 5.10 协调器带宽 + 10.9 敏感度隔离 + 12.8 资源组只管集群内；
- 为什么强调分区与文件格式？→ 6.4 剪裁红利 + 12.2 收敛再 Join；
- 为什么 BI 与 adhoc 分资源组分时段？→ 12.1 状态滞留诊断 + 12.8 调度策略族；
- 为什么统计信息必须进管道？→ 4.11/4.12 CBO 燃料。
（本文件按此逻辑把"案例→机制"的映射做全，作为全书整合练习。）

### 2. 规模的一页算术（13.2 展开）
交互式分析集群的经验结构（转述社区公开分享，非原书数字）：
- worker 以"每节点核数 × 并发 driver"估 CPU 容量；查询以 CPU-time 计费（4.11 代价模型的真实镜像）；
- 协调器瓶颈信号：QUEUED 长但 worker 空闲、Web UI 渲染卡、规划时间占比高 → 拆集群/升协调器内存/降单查询复杂度；
- Exchange 瓶颈信号：缓冲满、网络饱和而 CPU 空闲 → 先治理重分布写法（12.2/12.6）。
当代对照：小红书在线查询案例中"扩容 Task/Router 节点以应对突发并发"即协调器/执行器分离扩容的云上表述
（[腾讯云开发者社区 EMR×小红书](https://cloud.tencent.com/developer/article/2704655) ✅ ⚠️ 厂商转述）。

### 3. Hive 迁移的账本（13.3）
迁走：分钟级新鲜度要求的探索、跨源联查、交互式报表、数据探查/DQC；
留下：深度 Shuffle 的批 ETL、超宽表全量重排、既有调度资产沉没成本高的作业；
**中间地带**：把迁移做成"路由+降级"（B 站 Dispatcher 自动降级即此 ⚠️ 转述）——
Presto 失败或语法不兼容时回落 Spark/Hive。这与"引擎商品化、差异化上移格式与服务层"的当代论断一致
（[../bigdata/10-计算引擎的演进.md](../bigdata/10-计算引擎的演进.md)）。

### 4. 数据治理视角的补充（书中 13.4 的延长线）
多源并存的真实成本不在技术接入而在**口径**：同名指标跨源漂移、分区字段方言不一——
2026 年的解法是把口径钉在表格式+catalog 服务层（Iceberg REST/统一语义层），
互链 [../Apache_Iceberg活用入門/00-总览与阅读地图.md](../Apache_Iceberg活用入門/00-总览与阅读地图.md)、
[../数据架构之道.md](../数据架构之道.md)（书根存在 ✅）。

## 常见误区

| 误区 | 现实 |
| --- | --- |
| 照抄案例集群参数 | 案例数字是"当时当地"产物；可迁移的是决策逻辑（本文件精讲 1 的映射法） |
| 大规模=多买 worker | 协调器/Exchange/元数据服务的非线性瓶颈先到；13.2 的三条信号先学会看 |
| 迁移是一次性项目 | Hive↔Presto 长期双轨（路由+降级+物化分层）才是稳态 |
| 流量画像=QPS 一个数 | 探索型（突发/大扫描）与例行型（平稳/缓存友好）的资源行为完全不同 |

## 本章小结与行动清单

三句话带走：
1. 案例章的价值=**决策考古学**：给每个现场决定找回它的机制依据（精讲 1 映射法），这比记住任何数字有用；
2. 规模、迁移、流量三节合读出一个平台公式：`SLA = 引擎能力 × 资源制度(12) × 平台路由(11/13)`，三者不可互救；
3. 国内三家（美团/B 站/小红书）公开资料的共同点：**没有单引擎神话**，全部是编组+分层；
   书里"真实世界"是 Meta 集群，书外"真实世界"是你的流量画像——先画像，再借书。

选型报告写作骨架（借本章素材即可成文）：
- [ ] 流量画像：查询 QPS 分布、扫描量分布、新鲜度要求三张直方图（09 章 histogram 函数思维应用到自己身上）；
- [ ] 场景对表：1.3 十场景打勾 → 本组织命中几项、每项的失败代价；
- [ ] 编组方案：Presto/Trino 在栈中承担的位置 + 与 OLAP 库/批引擎的边界与降级关系；
- [ ] 风险清单：协调器单点、内存溢出、源库过载（06/12/10 三章素材）与缓解设计；
- [ ] 成本模型：按扫描（Athena 型）vs 按容量（自建型）的盈亏平衡估算；
- [ ] 回退路径：新引擎故障时，关键报表/查询的老执行路径保留多久（双轨退出条件）。

自测：
- [ ] 三条规模信号（QUEUED 长但空闲/缓冲满 CPU 闲/规划占比高）分别指向哪个瓶颈层？
- [ ] "Hive 留下什么、Presto 迁走什么"的一页纸判据？（13.3 账本复述）

一句话总结：本章把前 12 章从"知识"压成"手感"的关键动作只有一个——**每见一个现场决定，强制自问它兑现了哪章的哪条机制**；
答得出章号，才算读完这本书。另注：原书本章仅约五页且无量化数字，本文件的"规模算术/账本"均为社区公开资料的转述扩展（⚠️ 已在各处标注，勿作原书数据引用）。
