# 05 · 历史数据上的分析与可视化 BI

> 主题重构章（非原书章题）。
> 证据锚：MARC 520「Ways to build analytics and visualizations for business intelligence on historical data」+「through several real-time use cases, you'll learn how to quickly identify the right metrics to make actionable business decisions」。
> ⚠️ 原书 BI 部分的具体工具清单未证实，本章为公共谱系重构并标注。

## 1 章定位：ML 叙事之外的「另一半户口」

本书标题主打 AI，但 520 明确保留 BI 板块——「在历史数据上构建分析与可视化」。

- 工程读法：**同一数仓底座养两种消费者**——BI 看过去、ML 赌未来；
- 本章记「看过去」一侧与「赌未来」一侧的共享件与分叉件；
- 这是全书与纯 MLOps 书的差异点：它没有把 BI 当遗产嘲，而是当 ML 的地基数据源；
- 「on historical data」的措辞也提醒：即便实时 ML 世界观下，**历史层仍是 BI 的第一公民数据**，两节拍在仓内共存而非一方吞并。

## 2 BI 在数仓上的三层供给（重构表）

| 层 | 职责 | 共享给 ML 的部分 | BI 独有 |
|---|---|---|---|
| 聚合层（汇总事实+维度） | 报表/仪表板读 | 趋势特征、同比环比源 | 口径一致性 |
| 明细层 | 钻取、自助分析 | 训练样本回放 | 即席查询弹性 |
| 语义层（指标定义） | 「right metrics」的所在 | **特征定义即语义层复用** | 权限内指标可见性 |

**关键句**：「quickly identify the right metrics」在三层表里被升格为**语义层问题**——

- 指标若散在报表工具与 notebook 两侧各定义一份，BI 与 ML 必然口径分裂；
- 后世「headless BI/指标层」运动正解决此病（演进节接管）；
- 「identify」一词暗示书中有指标选取方法论，重构口径不冒充原书清单（⚠️）。

## 3 历史数据→训练样本的通路（与 02 章 E2 对读）

- BI 聚合层是 ML 趋势特征的**免费供应商**：滚动窗口指标早已算好，特征直接 SELECT；
- 但**聚合级复用有泄漏风险**：
  - 聚合若含决策时点之后的数据（如「当月销售」用于次月首日预测），
  - 必须回到 E2 的时点正确性纪律（06 章 E1 给了实验形态）；
- 分叉件：
  - BI 容忍 T+1 小错（人工判读会纠偏）；
  - ML 不容忍系统性偏（模型把偏差放大成决策）；
  - 同一份数据两用的质量阈值不同——装载闸门（03 章 E3/E4）按更严者定标。

## 4 可视化在「预测在场」后的角色变化（工程评论）

- 传统 BI 可视化=描述过去；引入预测后出现第三种图：**预期带（forecast band）与告警叙事**；
- 仪表板从「读数」变「对账模型承诺」；
- 这要求可视化层拿到模型元数据（版本、置信、漂移指标），即 BI 栈与 ML 栈的**接口扩张**；
- 本书 2017 提出「双向奔赴」时该接口尚未标准化——它的出现本身就是本章命题的后续验证（演进节）。

## 7 语义层落地四问（重构方法）

评审「指标层建在哪」时问四句：

1. 定义权：指标口径的唯一作者是谁（分析师/数仓工程师/领域团队）？
2. 复用面：报表、特征、告警是否引用同一 ID（还是三份 SQL 各自抄写）？
3. 时延元数据：每个指标是否登记「可作特征的安全时延」（06 章 E1 的制度化为它预留的行）？
4. 演进治理：口径变更如何触发下游模型回归（接 02 §6 暗面条）？

四问全过=语义层真的在供两代人；缺一=又一块「看板层假语义」，BI 与 ML 将继续口径分裂。

## 8 章小结

BI 板块在本书不是 AI 的陪衬，而是**特征的上游与模型的监工**：上游供聚合特征，监工以仪表板核对预测承诺。语义层是两者接口处最值钱的一块地——07 章 buy/build 矩阵里，「指标层建在哪」常比「模型跑在哪」更早决定平台命运。

## 9 三层供给的落地检查单（重构）

对聚合层：

- [ ] 每个汇总表登记消费方（报表/特征/告警）与刷新节拍；
- [ ] 被特征引用的聚合字段全部带「安全时延」元数据（06 章 E1 制度化行）。

对明细层：

- [ ] 训练样本回放的查询有独立资源组，不拖垮早高峰报表；
- [ ] 钻取路径与血缘同步，防「明细被管道改版、报表还在引用」。

对语义层：

- [ ] 指标唯一 ID 被 SQL/notebook/仪表板三侧引用（抽查三处文本比对）；
- [ ] 口径变更有通知订阅者机制；变更即触发模型回归（02 §6 暗面条的执法点）；
- [ ] 每季度做一次「口径分裂审计」：grep 报表工具与特征仓里的同名不同义指标。

## 最新演进与工业实践

- **Headless BI/指标层运动**（2020s）：
  - Looker 的 LookML 早潮之后，dbt Semantic Layer、Cube、AtScale 等把「指标定义」抽成独立服务；
  - SQL 与 BI 工具共用一份定义——本书「right metrics」问题获得工程正名；
  - ML 特征定义并入指标层（feature-as-metric）为 2024+ 讨论热点。
- **仓原生可视化与 notebook 融合**：
  - 各云仓挂接原生仪表板（Looker Studio/Power BI Fabric 线/Sigma 等）；
  - SQL notebook 与仪表板双形态共存；「预测带」成为主流工具一等图型；
  - 模型元数据接口仍未完全标准化——§4 的接口扩张仍在进行时。
- **Agentic 分析前夜**（2025–2026）：
  - 自然语言问数（仓边 LLM+语义层）让「identify right metrics」从人类共识问题变成机器检索问题；
  - 语义层质量直接决定问数准确率——本章 §2 三层表比 2017 年更显关键。
- 实践口径：BI 与 ML 共用聚合层时，在指标目录里**给每个指标登记「可作特征的安全时延」**——这是把 06 章 E1 泄漏教训制度化的一行元数据。
