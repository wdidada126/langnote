# 07 · 自建还是采购 ML 管道与展望

> 主题重构章（非原书章题，全书收束章）。
> 证据锚：MARC 520「gives practical advice on how to make the choice between building an ML pipeline or buying an existing solution」+ 末句「If you need to use data accurately and efficiently, a real-time data warehouse is a critical business tool」。

## 1 章定位：把前六章折成一张决策单

buy vs build 是 2017 技术册罕见的坦率条目（多数厂商系书默认「都自己搭在我引擎上」）。本章笔记把该条目**升格为全书的收束逻辑**：

- 每一层组件都有自建/采购两价；
- 选错层的代价=为不差异化的部分付运维税、为差异化的部分失控；
- 「practical advice」的措辞显示书中有面向管理者的一页——本重构章承接这一页的功能位。

## 2 分层决策矩阵（重构 · 与 03 章六段对表）

| 层（03 章六段映射） | 倾向采购 | 倾向自建 | 判据一句话 |
|---|---|---|---|
| 捕获 | 托管 CDC/云服务 | 自研轮询 | 业务库权限与出箱改造意愿 |
| 传输 | 托管 Kafka | 裸集群 Kafka | 峰值留存与跨区复制需求 |
| 处理 | dbt/托管流 SQL | Flink 深定制 | 状态规模与延迟 SLA |
| 质量闸门 | Expectations 服务 | 自研规则引擎 | 口径是否真资产（05 章 §7） |
| 装载 | 仓原生流写入 API | 自研 merge | 主键表语义成熟度 |
| 服务面 | 特征平台托管 | 仓内 KV 自建 | 点查延迟与隔离要求 |
| 模型层 | 仓内 CREATE MODEL | 外挂训练集群 | 算法迭代频率 vs 数据吞吐瓶颈 |

判读原则（重构标注 ⚠️）：

- **差异化在数据（01 章世界观），不在模型**——故采购可大胆下探到模型层；
- 自建应死守在**特征契约与语义层**；
- 这与 Inmon「方法论自建、工具采购」的老格言同构，实链对读 [../Data_Warehousing_2_0/00-总览与阅读地图.md](../Data_Warehousing_2_0/00-总览与阅读地图.md)。

## 3 「practical advice」的时代错位检查（2017→2026）

- 2017 的可买清单短：云数仓未全托管、特征平台未诞生、仓内 ML 是营销词——
  - 本书建议若逐条执行会买到今天已不存在的组件；
  - **方法论可迁移、采购目录必须换版**。
- 2026 的反向风险：**什么都可买**导致「全栈采购+薄集成」团队出现新的隐性锁定：
  - 身份/计费/血缘三方各一套；
  - buy 的尽头也是契约治理——§2 表右侧列的价值因此回升。
- 收束句（「a real-time data warehouse is a critical business tool」）在 LLM 时代的再读：
  - 数据准确与高效仍是模型效果的上游约束；
  - 这条 2017 判断被 2020s「数据质量决定模型天花板」行业共识追认。

## 5 评审用五问（重构工具，接 §2 矩阵）

1. 这一层是不是我们的差异化？（不是→默认采购）
2. 三年后换供应商，这层的**数据与定义**能否整体迁走？（不能→先补契约再采购）
3. 采购项的运维税谁付？SLA 违约的对价写在哪？
4. 自建项的 bus factor 是否 >1？离职文档流是否闭环？
5. 该层与特征契约/语义层（死守区）之间是否有清晰接口版本？

## 8 一页收束：本书五句主义

1. 预测分析之难在数据管道，不在算法（01）；
2. 现代数仓应与 ML 互为地基与升级动力（02）；
3. 实时是合同不是口号：选档、契约、闸门（03/06）；
4. 部署与来源都是矩阵题：选址×选型正交，边界协议兜底（04/07）；
5. BI 与 ML 共用底座时，质量阈值按更严者（模型）定标（05/06）。

## 9 附：五句主义的逆向读法（把每一句当风险单）

1. 难在管道 → 风险：只买算法平台不买管道治理，问题原样复发；
2. 双向奔赴 → 风险：仓变更未联动模型回归，「奔赴」变「互踩」；
3. 实时是合同 → 风险：无 SLA 的「实时」只是更快出错；
4. 矩阵题+边界协议 → 风险：混合架构无口径保险，四象限各长一套真相；
5. 按更严者定标 → 风险：按报表容忍度定质量阈值，模型静默变笨。

（逆向清单为重构工具 ⚠️；与 §5 五问配套作评审双表。）

## 最新演进与工业实践

- **可买清单换了三代**（2017→2026）：
  - 特征平台（Feast/Tecton/Vertex）→ 托管仓内 ML（BigQuery ML/Snowflake Cortex/Redshift+SageMaker）；
  - 平台整体化（Databricks 统一特征/训练/监控/向量；Snowflake 全栈收拢）；
  - §2 矩阵的「采购」列在每代都变宽。
- **MLOps 制度化**：
  - 模型注册表（MLflow）、CI/CD for ML、LLM Ops 监控；
  - 「buy or build」问题从管道层扩展到评估/对齐层；
  - 新变量是**推理 API 采购 vs 私有模型自建**之争（与大模型自训 vs 调用之争同构）。
- **反向运动**（2024+）：「去平台化」声音——
  - 平台费+锁定+迁移难使部分团队回归开源薄栈（dbt+Iceberg+Airflow+Evidently）；
  - 恰好验证 §3「buy 的尽头是契约治理」的判断。
- 实务基线（2026）：
  - buy/build 评审以「**三年退出成本**」为第一问：若供应商停服/涨价 3×，替代路径与数据可迁性是什么？
  - 答不出即把该项从采购列移回自建或中间契约列；
  - 本书五句主义（§8）在 2026 仍是有效的评审检查表。
