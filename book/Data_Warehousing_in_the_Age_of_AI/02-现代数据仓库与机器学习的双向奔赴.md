# 02 · 现代数据仓库与机器学习的双向奔赴

> 主题重构章（非原书章题）。
> 证据锚：MARC 520「This book shows how to automate and accelerate that process using machine learning (ML) on a modern data warehouse that runs on any cloud」+「Product specialists from MemSQL explain how today's modern data warehouses provide the foundations to implement ML algorithms that run efficiently」+「How data warehouses accelerate deployment and simplify manageability」+「explores foundational ML and artificial intelligence concepts」。
> ⚠️ 原书章题/页码未证实。

## 1 章定位：全书的「底座命题」

本章承载本书的中央主张，一个双向箭头：

- **正向（数仓→ML）**：现代数仓为 ML 提供「能高效跑算法的地基」——统一存储、SQL 计算面、并发分析吞吐；
- **反向（ML→数仓）**：ML 让数仓从 BI 报表库升级为决策自动化引擎，「加速部署、简化管理」（520 明文的 how 条目）；
- 附带锚点：本书宣称同时讲解「foundational ML and AI concepts」——
  - 即它是**给数据人写的 ML 入门 × 给 ML 人写的数仓入门**的双向教材册；
  - 这决定了 06 章建模内容偏概念级而非研究级的判断。

## 2 「现代数仓」的引擎特征清单（2017 口径 + MemSQL 语境标注）

520 未展开引擎细节，但「modern data warehouse / runs on any cloud」的组合在当年有明确所指。
以下清单按行业语境复原**该词族的公共含义**（登记为语境推断，非本书逐句核对，⚠️）：

| 特征 | 对 ML 的意义 |
|---|---|
| 列式存储+向量化执行 | 训练集扫描/聚合快，特征回算成本低 |
| 内存计算层 | 高频小查询（在线特征读取）可行 |
| 分布式 MPP+弹性伸缩 | 批量数据准备与 ad-hoc 分析并发共存 |
| 标准 SQL+分析函数内置（当年 MemSQL 话术含 built-in analytics） | 模型逻辑贴近数据，减少搬运 |
| 云托管/混合部署选项 | 对接 04 章云-线下抉择 |

**批判账**：

- 「数仓能跑 ML」在 2017 是差异化卖点，2026 已是货架标准（BigQuery ML/Snowflake 生态/Redshift ML，见 05/07 演进节）；
- 读本章命题要给年代折扣；
- 但它提出的**接口问题**——特征该在哪算、训练数据在哪备——至今没有唯一答案。

## 3 「双向奔赴」的三个技术支点

1. **数据不动模型动**：
   - 把训练/推理逻辑下推到数仓 SQL/UDF 层，免去导出 CSV 的「分析师走私数据」链路；
   - 治理收益巨大——对读 [../Data_Governance_in_the_Era_of_AI_2e/00-总览与阅读地图.md](../Data_Governance_in_the_Era_of_AI_2e/00-总览与阅读地图.md)。
2. **一套数据两种节拍**：
   - BI 走 T+1 聚合层，ML 走明细+实时层；
   - 数仓内部分层（原始/明细/汇总）天然对应 ML 三需求（回放训练/近线特征/在线服务）；
   - 这是盘上数仓册群与本书最有化学反应的读法。
3. **管理与运维单点化**：
   - 「simplify manageability」的实质=用数仓已有的权限/审计/备份体系罩住 ML 资产；
   - 避免另建一套平行栈；对照 07 章 buy/build 矩阵。

## 4 🔧 实测（两组 · 概念类比 · **非本书语境平台行为**——本书语境为 MemSQL/云 MPP，本地以 SQLite 3.45.3 / DuckDB 1.5.5 类比）

### E2 · SCD2 维表：数仓给 ML 的「可回放历史」

- 命题：数仓慢变维（SCD Type 2）保留历史版本，正是 ML 训练集「特征必须回到决策时点」的结构前提（与 06 章 E1 呼应）。
- 构造（SQLite，`experiments.py`）：源维 5 行；一个装载周期内 2 行属性变更 → 关旧版插新版。
- 实测结果：
  - dim 总版本 **7 行** / current=1 的当前版 **5 行**（源 5 + 变更 2）；
  - order3 历史链：`[('E',80,'2017-01-01','2017-01-02'), ('E',999,'2017-01-02','9999')]`。
- 读数：
  - 版本行数=源行数+累计变更数——**历史保真是线性存储税**；
  - 若源换成「属性高频抖动的事件实体」，SCD2 会爆炸；
  - 这正是 06 章特征仓常用「按时间桶快照」替代通用 SCD2 的原因。
- 类比限度：真引擎的分区裁剪/压缩让此税低得多，勿把 7/5 外推成生产容量结论。

### E3 · 数据质量画像：ML 前置闸门的量化

- 命题：Garbage in, garbage learned——装载前画像+清洗是可自动化环节（01 章病灶②）。
- 构造（DuckDB）：合成 10000 行，按模数注入 NULL（i%13）、复合键重复、异常状态（i%29）。
- 实测结果：
  - 画像层：完整性 **92.3%**、复合键冗余行 **4733**、状态失效行 **345**；
  - 清洗层：`QUALIFY ROW_NUMBER() OVER (PARTITION BY k ORDER BY city_id NULLS LAST)=1` + 状态过滤 → **94 行、残留重复键 0**。
- 读数：质量指标全部可 SQL 化=可编排化（03 章闸门位）、可报警化（可观测性册群对读）。
- 限度：DuckDB 单机 QUALIFY 语义/性能与 MPP 实现不同，标**非本书平台行为**。

## 6 底座命题的暗面（批判笔记）

- 「寄生论」的风险：ML 生命周期并入数仓后，仓的变更管理（模式升级/引擎换代）会直接冲击模型稳定性——需要把「仓 schema 变更=模型回归测试触发器」写进流程（03 章契约的回环）；
- 「简化」的举证责任在买方：simplify manageability 是厂商承诺，落地时以「新增了几套身份/审计/备份体系」来验收；
- 2017 年的「内存+列式」组合与 2026 年「存算分离+表格式+缓存层」组合在账本结构上完全不同——底座叙事每五年要重新算一遍。

## 7 章小结与钩子

底座命题的本质：**把 ML 的生命周期寄生到数仓已有的数据生命周期上**，用后者的成熟面（权限/审计/历史/质量）换新生的自动化。它没有回答的三个问题分别被后续章接住：

- 谁定义特征口径 → 05 章语义层；
- 模型算不算数据资产 → 07 章治理接口；
- 漂移报警归谁 → 06 章监控分级。

## 最新演进与工业实践

- **仓内 ML 全面商品化**（2020s）：
  - BigQuery ML 的 CREATE MODEL SQL、Snowflake 的 Snowpark/容器化 UDF、Redshift ML 直连 SageMaker；
  - SingleStore（本书母体）转向「实时+向量」——2017 的差异化卖点全部民主化。
- **质量闸门产品化**：
  - E3 的手工 SQL 画像已被 Great Expectations / dbt tests / Soda / OpenDataContract 体系接管；
  - 「测试即管道节点」成为默认工程实践。
- **特征供给的架构辩论**：
  - E2 暴露的「历史税」推进为**特征平台 vs 仓内特征表**路线之争；
  - Feast 物化到在线 KV vs Databricks 仓内 Feature Table；
  - 盘上 [../Data_Fabric_and_Data_Mesh_with_AI/00-总览与阅读地图.md](../Data_Fabric_and_Data_Mesh_with_AI/00-总览与阅读地图.md) 把供给面再升维到「编织/网格」抽象。
- 选型实操口径：
  - 评估「仓内 ML」时用**训练吞吐（仓外集群）×特征服务延迟（仓内/仓边 KV）双指标**打分；
  - 勿被「一条 SQL 出模型」的单指标营销遮蔽；
  - 本书底座命题在 2026 的正确打开方式=「仓是特征真相源，不是训练算力主场」。
