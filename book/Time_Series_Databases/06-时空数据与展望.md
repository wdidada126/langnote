# 第 6 章 时空数据与展望（⚠️ 章题为推定）

> 对应原书末章（章位/章题 ⚠️ 推定）。主题域有封底官方文案 ✅ 实据（豆瓣内容简介学习点末条）：
> "How to handle the added complexity of geo-temporal data"。本章把"时间"升维为"时间 × 地理"，
> 是全书设计原则的压轴试炼场。所涉 GeoHash/HBase 协索引机制全部 ⚠️ 文档转述，不装不跑；
> 🔧 演示仅复现"前缀分桶把二维问题降为一维"的概念。

## 章定位与中心论题

监控/IoT 数据常自带第二维度——**位置**。查询从"某序列某时段"变成"某时段 + 某地理围栏内
某类序列"，一个谓词从时间轴上的区间变成平面上的区域。本章（重构）的论点：
时序存储的 rowkey 思想仍可用，但必须把空间维度**编码进键的前缀结构**，
代价是空间查询退化为"候选前缀枚举 + 精确过滤"的两段式。

## 逐节精读重构

### 6.1 时空查询的形态学

- ⚠️ 转述重构的查询四象限（时间区间 × 空间区域 的开闭组合）：
  1. 同时空窗（"过去 1h、A 港各泊位温度"）——最典型；
  2. 固定空间扫时间（轨迹回放）；
  3. 固定时间扫空间（快照热力图）；
  4. 跨窗聚合（"上周围栏内均值"）。
- 与纯时序的本质差异：**空间相邻 ≠ 键相邻**，一维 rowkey 无法同时保两轴的连续性——
  降维编码因此成为唯一出路（6.2）。

### 6.2 GeoHash：空间→字符串前缀的降维

- ⚠️ 文档转述（GeoHash 通行定义，与本书语境一致）：经纬度交替二分 → base32 字符串；
  前缀越长格越细，**共享前缀 ≈ 空间邻近**（有边界撕裂伪邻问题）。
- 设计移植：把 GeoHash 前缀拼进 3.3 的 rowkey（序列 ID 侧或盐位侧），
  "围栏查询" = 枚举覆盖围栏的 GeoHash 前缀集合 → 批量 rowkey 扫描 → 精确多边形过滤。
  这正是 Twitter  geo 时序案例（本书所引，⚠️ 转述）的骨架：**用键前缀模拟空间索引**，
  把二维问题降解为"一维区间扫描的并"。
- 权衡表（⚠️ 重构）：精度 = 前缀长度 = 枚举量；围栏越大枚举越少但撕裂过滤越多；
  与 4.2 的盐化问题同构（前缀既服务打散又服务定位，一图两用）。
- 🔧 **概念演示 D5（sqlite3，非任何空间引擎，脚本 `demo3.py`）**：验证"前缀分桶把二维查询
  降为一维"：100,000 个 (lat,lon,bucket,value) 随机全球点（5min×720 桶），手工实现
  4 级位交织玩具 GeoHash（经纬各取高 4 位交织 → 256 个粗格），入库建 `(gh,bkt)` 复合索引
  （🔧 装载 0.22s，格-桶组合 77,243 个）。围栏查询 box(30°–45°N, 120°–150°E)：
  枚举命中前缀 **4 个** → 索引扫得候选 **1,484 点** → 精确过滤 **654 点**；
  🔧 实测前缀扫描 **0.222ms** vs 全表暴力 **7.85ms**（约 35× 提速、**67× 候选缩减**）。
  注明：玩具编码粒度粗（每格 ≈ 11°×14°），真实 GeoHash/S2 用更深前缀换更小候选集，
  但"两段式（候选+精滤）"结构与此完全一致；与 PostGIS 等真实空间索引无关
  （脚本 `D:\develops\tmp\dbwave_w3_timeseries\demo3.py`，输出 `demo3_out.txt`）。

### 6.3 时空数据的第二重复杂性：基数乘法

- 6.1 的空间维度直接乘进 2.3 的基数账：序列数 × GeoHash 精度级 = 索引/UID 表规模；
  粗前缀省空间但放大过滤代价——**精度-基数-过滤量三角**（⚠️ 重构表述），
  与 05 章"分辨率自适应"是同一权衡的两副面孔。
- ⚠️ 转述：本书对"移动对象轨迹"（坐标随时间连续变化 → 序列身份本身不稳定）点到为止，
  该问题后来由轨迹数据库/移动对象模型文献展开，不在本目录盘上版图，不硬凑互链。

### 6.4 全书展望（⚠️ 推定重构：末章收束段）

- 三句话的重构总结：时序 = 一种操作剖面（01/02）；剖面决定布局，布局 = rowkey 上的
  时间几何（03）；开源参照会过时，权衡结构不过时（04–06）。
- 2014 年作者未言明的走向（本目录代答，详见演进节）：观测性（observability）三信号
  metrics/logs/traces 中，本书的 metrics 路线被 Prometheus 系接管，logs/traces 走了
  倒排 + 列存融合路线——"时序专用布局 vs 通用列存"的边界至今仍在重画。

### 6.5 时空扩展的三条一般化教训（重构收束）

1. **任何第二维度都会把"一维键"逼成"编码 + 两段式"**：空间维如此（🔧D5），
   向量维如此（相似性无法编码进有序键，只好发明图/聚类结构——见 00 互链表向量册挂点），
   租户维亦如此（多租户 TSDB 的 namespace 前缀）。rowkey 范式的扩张史就是编码史。
2. **降维编码的伪邻/撕裂代价不可消除，只能定价**：GeoHash 边界撕裂 → 扩边枚举；
   与 4.2 盐化"打散热点必付扇出账"同构——本书全章反复出现的守恒律。
3. **消费形态决定要不要把维度做进存储层**：围栏查询低频 → 导出到 PostGIS/湖上批处理
   （6.2 的替代路线）往往胜过 TSDB 内建空间索引；本书未言明，🔧D5 的 67× 候选缩减
   说明"做进去"的收益上限其实不高（对粗粒度玩具编码而言）。

## 核心概念速览（中英对照）

- **时空数据** — geo-temporal data：时间戳 + 地理坐标双维时序，本书复杂度压轴
- **GeoHash** — 经纬度交替二分编码为 base32 前缀串，前缀共享 ≈ 空间邻近
- **边界撕裂** — edge effect：邻近点落入不同前缀格，伪非邻需扩边枚举
- **两段式查询** — candidate + refine：前缀枚举粗筛 → 精确几何过滤
- **键前缀模拟索引** — index-in-the-key：用 rowkey 前缀承担空间索引职责（6.2 主旨）
- **精度-基数-过滤三角** — precision/cardinality/filtering trade-off：前缀长度的三向代价
- **围栏查询** — geofence query：时段 × 多边形交集，时空形态学的原型
- **轨迹** — trajectory：坐标连续变化使序列身份不稳定，本书未展开的外延
- **快照热力图** — snapshot heatmap：固定时间扫空间的读形态
- **基数乘法** — cardinality multiplication：空间维直接乘进 2.3 序列数账本
- **观测性三信号** — metrics/logs/traces：6.4 代答的 2024–2026 版图坐标
