## 逐节精读重构

### 3.1 最简路线：平面文件及其天花板

- ✅ 译文实抓论点：可以扩展简单二维表，用更聪明的文件格式（**点名 Parquet**）存储；
  给出两种 Parquet schema 对比（译文图 3-1 描述）：
  1. **固定列名式**：t/tempIn/pressureIn/tempOut/pressureOut——序列数写死在 schema 里，
     加序列要改 schema；适合场景确定的嵌入式分析；
  2. **tag 分组 block 式**：把若干（time,value）对按 tags 分组进单独 block，抽象层次更高、
     序列数不设限——"如果你想构建一个给其他人使用的时间序列库，右边格式更合适"（✅ 译文原话）。
- ✅ 失效机制（译文完整论证）：文件内序列数增长 → 查询读到的数据里有用比例下降；
  文件时间跨度 ≫ 查询区间 → 同样读放大；两害相权只能**增文件数**，而 HDFS 上小文件过多
  引发稳定性问题（MapR 能扛小文件但检索管理仍低效）。
- 系列定位注记：本节是本书与列存世界的接口——Parquet 的正面向导见
  [../bigdata/09-存储与文件格式.md](../bigdata/09-存储与文件格式.md)；
  2014 年"平面文件到顶"的判断在"湖上时序"（Parquet + 分区裁剪 + 引擎谓词下推）时代
  部分被推翻，见本章演进节。

### 3.2 转向"真数据库"之一：RDBMS 与星型模式之困

- ✅ 译文实抓：初入库者常被**星型模式**吸引——事实表（Time, Time series ID, Value）
  引用维表（序列细节/Value 含义）；核心假设"维表小而稳定"。
- ✅ 译文论证的失效点（重构）：时序场景下"维表"即序列清单，**它恰恰是又大又快变的**
  （设备增删、标签变更），星型假设破产；且事实表逐行携带序列 ID，
  行存下"序列 × 区间"扫描要跨海量行跳读。
- ⚠️ 转述补强（本书之后十年的工程常识）：RDBMS 路线的续命手段 = 分区表 + BRIN 索引 +
  时序扩展（TimescaleDB），盘上对照读物：
  [../Database_Tuning/13-时序与金融数据.md](../Database_Tuning/13-时序与金融数据.md)
  （关系路线的调优视角）与 [../设计数据密集型应用.md](../设计数据密集型应用.md)
  （"为访问模式建模"的一般原则）。

### 3.3 转向"真数据库"之二：NoSQL 宽表基本设计（本章高潮）

- ✅ 译文实抓的立场句："非关系型 NoSQL 数据库是首选方案，因为它可扩展性好、高效、
  能快速响应基于时间段的查询"。
- ✅ 基本设计（译文路线图段原话）："使用包含时间序列 ID 的唯一 row key，列是不同时间偏移
  的数值"——即 **rowkey = 序列身份，列限定符 = 时间偏移，一行装多段历史**；
  检索一个序列一段时间 = 一次 rowkey 定位 + 连续列切片，天然消除 3.1/3.2 的读放大。
- ✅ "存储多于一个时间序列"：多 rowkey 自然分布到 region/服务器，按序列分片零成本。
- ⚠️ 转述重构（译文明示存在但未展开的机制）：时间偏移作列限定符要求列按字典序存储
  （HBase 语义），"同族序列共享 rowkey 前缀"以支持多序列合并扫描——这两条 OpenTSDB
  式细化放到了第 4 章（✅ 译文路线图段："第四章会提供如何使用现有开源软件……的建议"）。

### 3.4 可选设计谱系（✅ 译文路线图段点名三项）

1. **宽表逐点存储**（每点一列）：与基本设计同族，粒度到单点；
2. **混合宽表 + blob**：整段时间打包成二进制 cell，读整段快、插中间难；
3. **内存缓存 + blob 直写**：新点先进内存聚合，成段后以 blob 落盘——
   写放大与读粒度的折中，OpenTSDB/Graphite 均有此形态（⚠️ 转述，04 章对表）。
- 🔧 **概念演示 D1/D2（sqlite3 3.45.3，非时序引擎行为）**：为把"聚合层"从比喻变成数字，
  用普通关系表模拟"原始层 + 降采样层"双层结构（脚本 `D:\develops\tmp\dbwave_w3_timeseries\demo.py`，
  输出 `demo_out.txt`）。数据：500 序列 × 400 点 @10s 间隔 = 200,000 行，
  `PRIMARY KEY(series, ts) WITHOUT ROWID`（rowkey 语义的玩具化），库文件 5.5 MB。

  **D1 分桶聚合**（"列是时间偏移"的关系化替身——按 300s 桶 group by）：

  ```sql
  SELECT series, ts/300*300 AS bkt, COUNT(*) n, AVG(value) avg_v,
         MAX(value) max_v, MIN(value) min_v
  FROM raw GROUP BY series, bkt ORDER BY series, bkt;
  ```

  🔧 实测：全表扫描得 **7,000 个桶，0.087s**；首桶样例
  `('m0000', 1699999800, 10, 64.0169, 66.048, 61.55)`（10 点/桶，恰合 300s÷10s）。

  **D2 降采样物化**（3.4 的"blob 聚合层"替身）：把 D1 结果 `CREATE TABLE rollup5m AS ...`
  并建索引。🔧 实测：建表 **0.12s**，rollup 7,000 行 vs 原始 200,000 行，
  **压缩比 28.6:1**；此后"上周趋势"类查询从扫 20 万行降到扫 7 千行。
  注明：sqlite 无时序原语，桶粒度/物化/失效策略全靠手工——这正说明 TSDB 把这些做成了
  一等公民的价值；数字也不代表任何真实 TSDB 的吞吐。

### 3.5 本章结论（✅ 译文路线图段的重构）

平面文件 = 受限工具（增长快、查询低效）；RDBMS 星型 = 扩展性差；
NoSQL 宽表 rowkey = 首选，配"逐点/混合 blob/内存+直写"三档可选设计。
这个 2014 年的判断在监控用例上被 Prometheus 类**倒排索引 + 块存储**路线接管、在 IoT 用例上
被列存路线部分蚕食（见演进节），但"序列身份进 rowkey、时间段连续存"的骨架至今活在所有
TSDB 的 chunk/segment 层里。

## 核心概念速览（中英对照）

- **平面文件路线** — flat-file approach：列存文件存时序，小规模利器、大规模读放大
- **读放大** — read amplification：有用字节/实际扫描字节之比恶化
- **小文件问题** — small-file problem：HDFS 元数据与稳定性压力，文件切分两难的来源
- **星型模式** — star schema：事实表 + 维表；时序下维表又大又快变，假设失效
- **事实表/维表** — fact/dimension table：(Time, SeriesID, Value) 与序列元数据清单
- **rowkey 设计** — rowkey design：序列 ID（+ 时间偏移列）的物理布局第一决策
- **列限定符 = 时间偏移** — column qualifier as time offset：基本设计的核心机关
- **逐点宽表** — per-point wide column：每采样点一列的极限粒度布局
- **blob 打包** — blob packing：整段（time,value）序列化为一个 cell，换读整段之速
- **内存缓存直写** — in-memory cache + blob flush：新点聚合后成段落盘，写放大折中
- **降采样层** — rollup/downsample layer：🔧D2 实测 28.6:1 的粗粒度物化层
- **分桶** — time bucketing：`ts/300*300` 式固定粒度聚合键（🔧D1）
