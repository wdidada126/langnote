## 1.1 装载是数仓的「第一配方」：路径地图

本章（⚠️ 重构口径）解决一个问题：**数据怎么进专用 SQL 池最合理**。Learn 装载总览 ✅
`azure/synapse-analytics/sql/load-data-overview` 给出的路径族 ⚠️ 转述：

| 路径 | 机制 | 适用 |
| --- | --- | --- |
| 外部表 + CTAS（PolyBase 引擎） | 湖/存储上的 CSV/ORC/Parquet 映射为外部表，`CREATE TABLE AS` 拉入内表 | 大批量首装、ETL 落地 |
| `COPY INTO` | T-SQL 语句直接从对象存储批量导入（自动并行/通配符/压缩文件）✅ `sql/t-sql/statements/copy-into-transact-sql` | 中等批量、脚本化装载 |
| Synapse 管道 Copy 活动 | 编排层的源→汇复制（可增量、可监控）✅ `quickstart-copy-activity-load-sql-pool` | 企业调度、多源汇聚（02 章主场） |
| 不装载：服务器端点/Spark 直读 | 数据留湖，查询时读 ✅ `sql/on-demand-workspace-overview` | 探索期/低频查询（「never load」思想，05 章展开） |

配方叙事（⚠️ 依章题「Choosing the Optimal Method」推定）：先问**频率×体量×延迟要求**，
再在「装载/直读」两极间选路径——这是全章的决策树骨架。

## 1.2 装载前置配方：密钥、凭据与外部数据源

仓库代码文件夹给出的实操序列（✅ 文件夹名实抓，步骤语义 ⚠️ 转述）：

1. `CREATE DATABASE MASTER KEY` → 数据库主密钥，加密后续凭据 ⚠️；
2. `CREATE SCOPED DATABASE CREDENTIAL`（存储账户 SAS/密钥）⚠️；
3. `CREATE EXTERNAL DATA SOURCE`（指向 ADLS/Blob 端点 + 凭据绑定）⚠️；
4. `CREATE EXTERNAL TABLE`（列定义 + 文件格式 + LOCATION）⚠️（✅ `sql/develop-tables-external-tables`）；
5. CTAS 拉取成内表（1.4）。

README 软件清单含 **SSMS**——本章「connect to sqlpool」文件夹印证：专用池按 SQL Server
端口 1433 TDS 协议连接，SSMS/azuredatastudio 皆可 ⚠️。

## 1.3 类型陷阱与统计：两个「隐性配方」

- **unsupported datatypes**（✅ 文件夹名）：外部表/装载链路对部分类型有黑名单与映射差异
  ⚠️——装载失败的第一排查项；转内表后再补列类型（如 `GEOMETRY` 等专用池支持面 ⚠️）。
- **auto create stat**（✅ 文件夹名）：`SELECT name, is_auto_create_stats_on FROM sys.databases`
  正是 README 展示的代码片段——专用池默认自动统计开关影响首装后查询计划质量 ⚠️
  （✅ `sql-data-warehouse/sql-data-warehouse-tables-statistics`；README 片段 ✅ 实抓）。
- 🔧E3 侧证：装载完的表若按查询键有序（CTAS 带 `ORDER BY` 语义的分布+分区设计），列存段
  min/max 剪枝收益实测 1.6ms vs 乱序 3.7ms（≈2.3×，**非 Synapse 行为**）——「装载即布局」的
  算术根据。

## 1.4 CTAS：装载与建模的合体配方

✅ `azure/synapse-analytics/sql-data-warehouse/sql-data-warehouse-develop-ctas` ⚠️ 转述：
CTAS 一步完成「建内表 + 选分布策略 + 拉数据」，是官方推荐的大批量落地姿势；表选项三件套——
`DISTRIBUTION (HASH|REPLICATE|ROUND_ROBIN)`、`CLUSTERED COLUMNSTORE INDEX`（默认）、
`PARTITION RANGE`——**装载时定终身，改要重建**（03 章展开调优面）。
🔧E6（DuckDB 直查 CSV 101.4ms vs 含装载 115.2ms，结果一致）演示「直读 vs 落地」的盈亏
平衡直觉：一次性查询直读占优，高频复用装载摊薄成本（**非 Synapse 行为**）。

## 1.5 列存压缩与「装载窗口」经济学

✅ `azure/synapse-analytics/sql/data-load-columnstore-compression` ⚠️ 转述：CCI 以
~60k 行段压缩存储，装载期间有 ROW_GROUP 状态机（TINY→LOCAL→PENDING→FINAL），
大批装载后需触发压缩合并（`sys.pdw_column_store_row_groups` 观察 ⚠️）。
装载窗口三杠杆 ⚠️：DWU 档位（供给，03 章）、并发复制数（PolyBase/COPY 资源类）、
文件切分度（每分布切片至少一文件）。🔧E1 的扩展衰减曲线（1→8 线程仅 6.2×）提醒：
「堆并发不堆文件」不会无限变快（**非 Synapse 行为**）。

## 1.6 配方体检单（编者归纳 ⚠️）

1. 目标表三选项（分布/索引/分区）在 CTAS 语句里写全了吗？
2. 外部表列类型跑过类型矩阵核对吗（1.3 黑名单）？
3. 装载后统计是否更新（auto create 之外，大表手动 `CREATE STATISTICS` ⚠️）？
4. 文件数 ≥ 分布数？压缩状态机是否回到 FINAL？
5. 失败重放幂等吗（先删后插/分区切换 `SWITCH` ⚠️）？

## 1.8 配方范例细读：从 CSV 到内表的最小闭环（⚠️ 重构，对位 chapter 1 代码文件夹序列）

以「湖上一堆 CSV → 可查内表」为例把 1.2–1.4 串成一条可背诵的配方（语句骨架为编者
按 Learn 语义改写，**非书中原文** ⚠️）：

1. 连接专用池（SSMS，1433/TDS，1.2 步 0）⚠️；
2. `CREATE DATABASE MASTER KEY ENCRYPTION BY PASSWORD = ...` ⚠️；
3. 建作用域凭据（存储账户 SAS 或托管标识，后者免密 ⚠️）；
4. `CREATE EXTERNAL DATA SOURCE lake` 指向容器端点 ⚠️（✅ develop-tables-external-tables）；
5. `CREATE EXTERNAL TABLE stg_csv (...) WITH (LOCATION=..., FILE_FORMAT=CSV)`——
   先跑类型矩阵核对（1.3 黑名单 ⚠️）；
6. 试查外部表验证行数/乱码/坏行；
7. `CREATE TABLE fact_x WITH (DISTRIBUTION = HASH(k), CLUSTERED COLUMNSTORE INDEX)
   AS SELECT * FROM stg_csv`（CTAS 三件套定终身，1.4）⚠️（✅ develop-ctas）；
8. `CREATE STATISTICS` / 确认 auto-create 生效（1.3）⚠️（✅ tables-statistics）；
9. 检查 CCI 段状态回到 FINAL（1.5）⚠️（✅ data-load-columnstore-compression）。

每步失败模式一句话：2/3 密钥链断→凭据错；5 类型/转义错→装载脏；7 分布键错→
下游全 shuffle（🔧E2）；9 未合并→扫描放大。**「配方=步骤+失败模式」**是 cookbook
体裁的读法（00 §4 呼应）。

## 核心概念速览（中英对照）

- **装载路径选型** — Loading method choice：外部表+CTAS / COPY INTO / 管道 Copy / 直读不装载四路 ⚠️（✅ load-data-overview）。
- **数据库主密钥** — Database Master Key：凭据加密链根节点，装载前置配方 ⚠️。
- **外部数据源/外部表** — External data source / table：对象存储的 T-SQL 投影 ⚠️（✅ develop-tables-external-tables）。
- **COPY INTO** — COPY INTO：语句级批量导入，通配符+自动并行 ⚠️（✅ copy-into-transact-sql）。
- **CTAS** — CREATE TABLE AS SELECT：建表+分布+装载三合一 ⚠️（✅ develop-ctas）。
- **类型黑名单** — Unsupported data types：装载链路映射差异第一排查项 ⚠️（✅ 仓库文件夹名）。
- **自动统计** — Auto-create statistics：`is_auto_create_stats_on` 开关影响首查计划 ⚠️（✅ tables-statistics）。
- **列存段状态机** — Columnstore row group states：TINY/LOCAL/PENDING/FINAL 压缩生命周期 ⚠️（✅ data-load-columnstore-compression）。
- **文件切分度** — File split granularity：装载并行度的供给侧下限 ⚠️ 编者归纳。

## 最新演进与工业实践

2022→2026（URL 均 ✅ 200；状态 ⚠️ 转述）：

- **COPY INTO 成为首推面**：本书出版时 PolyBase 外部表仍是主力，现行装载总览把 COPY INTO
  与外部表并列且新增 `WITH (AUTO_CREATE_TABLE)` 一键建表能力 ⚠️（✅ copy-into-transact-sql 现行版）——
  读 1.2 序列时注意「外部表五步」在部分场景已被一步 COPY 吸收。
- **服务器端点成熟**：`sql/best-practices-serverless-sql-pool` ✅ 把「湖上直读」从探索玩具
  升格为生产路径（文件布局/统计/资源治理三前提），1.1 表格第四行权重上升 ⚠️。
- **Fabric 迁移语境**：专用池可挂 Fabric 容量运行（✅ `fabric/data-warehouse/migration-synapse-dedicated-sql-pool-warehouse`），
  装载配方不变、计费面变化（03/07 章演进节展开）。
- **工业实践**：企业装载体检普遍制度化——「类型矩阵回归库 + 装载 SLA + 幂等重放脚本」三件套；
  与 Redshift COPY 的 manifest/COMPROWS 经验同构（[../Amazon_Redshift_Cookbook_2e/03-表设计与装载转换配方.md](../Amazon_Redshift_Cookbook_2e/03-表设计与装载转换配方.md) 互鉴）。
- 🔧 数字口径：E1/E3/E6 为 DuckDB/SQLite 本机实测，只证「布局影响剪枝、直读与装载各有盈亏、
  并发有扩展税」三定律的跨引擎普适性，**不可换算成 Synapse 参数**。
