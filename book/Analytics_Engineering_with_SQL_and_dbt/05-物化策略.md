# 05-物化策略

> **对应章节**: Ch5 — Materializations
> **核心命题**: view / table / incremental / ephemeral 四种物化策略的选择与权衡

---

## 5.1 什么是物化？

### 物化的本质

dbt 模型是**逻辑定义**（一个 SELECT 语句），物化决定其**物理存储方式**：

| 物化类型 | 物理表现 | 刷新方式 | 存储成本 | 查询性能 |
|---------|---------|---------|---------|---------|
| **view** | 视图（不存数据） | 查询时实时计算 | ✅ 低 | ⚠️ 慢（复杂查询） |
| **table** | 物理表 | 全量重建 | ⚠️ 高 | ✅ 快 |
| **incremental** | 物理表 | 仅插入/合并增量 | ✅ 中 | ✅ 快 |
| **ephemeral** | 不存在（CTE 注入） | 被引用时内联 | ✅ 零 | 取决于最终物化 |

✅ 物化选择是 dbt 性能优化的**第一杠杆**。

---

## 5.2 View 物化

```sql
{{ config(materialized='view') }}
-- 或目录级配置（dbt_project.yml）
```

**适用场景**:
- Staging 层模型（轻量清洗/重命名）
- 数据量小、逻辑简单的模型
- 下游模型需要实时数据的场景

**不适用**:
- 复杂聚合（每次查询都重算）
- 大表 JOIN（性能差）

✅ View 是 staging 层的**默认选择**——零存储成本，数据始终最新。

---

## 5.3 Table 物化

`CREATE OR REPLACE TABLE ... AS SELECT ...`——每次全量重建（DROP + CREATE）。

✅ **适用**: Mart 层、频繁查询 | ⚠️ **不适用**: 大表全量重建成本高

---

## 5.4 Incremental 物化

### 核心机制

```sql
{{ config(materialized='incremental', unique_key='order_id') }}

SELECT * FROM {{ ref('stg_orders') }}

{% if is_incremental() %}
    WHERE order_date > (SELECT MAX(order_date) FROM {{ this }})
{% endif %}
```

| 概念 | 说明 |
|------|------|
| `is_incremental()` | 判断是否增量运行（首次运行 = False） |
| `unique_key` | 用于 MERGE/UPSERT 的去重键 |
| `{{ this }}` | 引用当前模型已存在的物理表 |

### Incremental 策略

| 策略 | 适用引擎 | 行为 |
|------|---------|------|
| **append** | 所有 | 只插入新行 |
| **delete+insert** | 所有 | 按 unique_key 删除旧行再插入 |
| **merge** | Snowflake/BigQuery/DuckDB | MERGE 语句（UPSERT） |
| **insert_overwrite** | BigQuery/Spark | 按分区覆盖写入 |

✅ Incremental 是**大数据量场景的核心优化**——将 O(n) 重建降为 O(Δn) 增量。

### Incremental 的陷阱

| 陷阱 | 说明 | 缓解 |
|------|------|------|
| 数据漂移 | 增量窗口遗漏更新行 | 用 `lookback` 参数 |
| Schema 变更 | 新增列不自动同步 | `--full-refresh` |
| 首次运行 | `is_incremental()` = False，全量 | 预期行为 |
| 调试困难 | 增量状态难以复现 | `--full-refresh` 重置 |

⚠️ Incremental 模型的复杂度显著高于 view/table——优先用 view/table，有性能瓶颈再升级。

## 5.5 Ephemeral 物化

```sql
{{ config(materialized='ephemeral') }}
```

Ephemeral 模型**不产生物理对象**——其 SQL 作为 CTE 注入到下游模型中：

```
下游模型编译结果:
WITH ephemeral_model AS (
    SELECT ... FROM upstream  -- ephemeral 模型的 SQL
)
SELECT * FROM ephemeral_model
```

**适用场景**:
- 轻量级中间计算（如通用日期维度生成）
- 不需要直接查询的逻辑片段

**不适用**:
- 多个下游模型引用（会导致重复计算）
- 需要直接查询验证的模型

⚠️ Ephemeral 过度使用会导致下游 SQL 膨胀——保持简洁。

## 5.6 🔧 DuckDB / SQLite 类比（物化本地化）

| # | dbt 物化 | DuckDB 本地实现 | SQLite 本地实现 | 标注 |
|---|---------|----------------|----------------|------|
| 1 | `materialized='view'` | `CREATE VIEW model AS SELECT ...` | 同：`CREATE VIEW` | 🔧 非本书引擎行为 |
| 2 | `materialized='table'` | `CREATE TABLE model AS SELECT ...`（每次 DROP + CTAS） | 同：`DROP TABLE IF EXISTS` + `CTAS` | 🔧 非本书引擎行为 |
| 3 | `materialized='incremental'` | `INSERT INTO model SELECT ... WHERE date > (SELECT MAX(date) FROM model)` | `INSERT OR IGNORE INTO model SELECT ...` | 🔧 非本书引擎行为 |
| 4 | `materialized='ephemeral'` | 手动将 SQL 复制为 CTE 到下游查询 | 同：手动 CTE 注入 | 🔧 非本书引擎行为 |
| 5 | `is_incremental()` 判断 | 手动检查 `SELECT COUNT(*) FROM model` 是否 > 0 | 同 | 🔧 非本书引擎行为 |

> 🔧 以上均为**非本书引擎行为**——物化策略由 dbt 自动管理，此处仅展示底层 SQL 等价操作。

## 5.7 物化选择决策树

```
模型是否被 BI/用户直接查询？
├── 否 → 数据量是否 > 1000 万行？
│        ├── 否 → view
│        └── 是 → 是否需要增量更新？
│                 ├── 否 → table
│                 └── 是 → incremental
└── 是 → 数据量是否 > 1000 万行？
         ├── 否 → table（快速响应）
         └── 是 → incremental + unique_key
```

⚠️ 此决策树为经验法则，实际需结合引擎特性和成本考量。

## 5.8 本章关键术语

| 英文 | 中文 | 定义 |
|------|------|------|
| Materialization | 物化 | dbt 模型在仓库中的物理存储方式 |
| Full Refresh | 全量刷新 | 删除并重建整个表 |
| Incremental | 增量 | 只处理新增/变更数据的物化策略 |
| unique_key | 唯一键 | incremental 中用于 MERGE 去重的键 |
| is_incremental() | 增量判断 | Jinja 函数，区分首次运行与增量运行 |
| Ephemeral | 瞬态 | 不产生物理对象，以 CTE 形式注入下游 |

## 核心概念速览（中英对照）

| 中文概念 | English Term | 一句话定义 |
|---------|-------------|-----------|
| 物化 | Materialization | dbt 将逻辑模型转化为物理存储的策略 |
| 视图物化 | View Materialization | 不存储数据，查询时实时计算的物化方式 |
| 表物化 | Table Materialization | 每次运行全量重建物理表的物化方式 |
| 增量物化 | Incremental Materialization | 仅处理新增/变更数据的高效物化方式 |
| 瞬态物化 | Ephemeral Materialization | 不产生物理对象、以 CTE 注入下游的物化方式 |
| 全量刷新 | Full Refresh | 忽略增量状态、完全重建表的运行模式 |
| MERGE 策略 | MERGE Strategy | 基于 unique_key 的 UPSERT 增量策略 |
