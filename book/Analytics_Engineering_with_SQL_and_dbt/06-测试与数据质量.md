## 6.1 dbt 测试体系概览

### 测试的两层防线

```
第一层: Schema Tests（声明式）
  → unique, not_null, accepted_values, relationships
  → 在 YAML 中声明，零 SQL 编写

第二层: Data Tests（自定义 SQL）
  → 返回行即为失败的 SELECT 语句
  → 表达复杂业务规则
```

✅ dbt 的测试哲学：**声明优先，自定义兜底**。

---

## 6.2 Schema Tests（声明式测试）

### 四种内置测试

```yaml
# models/schema.yml
models:
  - name: stg_orders
    columns:
      - name: order_id
        tests:
          - unique          # 唯一性
          - not_null        # 非空
      - name: status
        tests:
          - accepted_values:
              values: ['placed', 'shipped', 'completed', 'returned']
      - name: customer_id
        tests:
          - relationships:
              to: ref('stg_customers')
              field: customer_id
```

| 测试 | 验证内容 | 生成 SQL |
|------|---------|---------|
| `unique` | 列值唯一 | `SELECT col FROM t GROUP BY 1 HAVING COUNT(*)>1` |
| `not_null` | 列无 NULL | `SELECT col FROM t WHERE col IS NULL` |
| `accepted_values` | 列值在枚举内 | `SELECT col FROM t WHERE col NOT IN (...)` |
| `relationships` | 外键引用完整性 | `SELECT * FROM child WHERE fk NOT IN (SELECT pk FROM parent)` |

✅ 四种内置测试覆盖 **80% 的常见数据质量问题**。

### 测试配置

```yaml
tests:
  - unique:
      severity: warn    # warn 或 error
      config:
        where: "order_date > '2023-01-01'"  # 过滤条件
  - not_null:
      severity: error
```

| 参数 | 说明 |
|------|------|
| `severity: warn` | 测试失败不阻断管道 |
| `severity: error` | 测试失败阻断下游执行 |
| `where` | 限定测试范围 |
| `enabled: false` | 禁用特定测试 |

## 6.3 Data Tests（自定义测试）

### 编写自定义测试

```sql
-- tests/assert_positive_amount.sql
-- 返回行 = 失败行
SELECT order_id, amount
FROM {{ ref('fact_orders') }}
WHERE amount < 0
```

✅ 自定义测试的本质：**一个返回失败行的 SELECT 语句**——简单而强大。

### 通用测试（Generic Tests）

```sql
-- macros/test_positive_value.sql
{% test positive_value(model, column_name) %}
SELECT *
FROM {{ model }}
WHERE {{ column_name }} < 0
{% endtest %}
```

```yaml
# 使用自定义通用测试
columns:
  - name: amount
    tests:
      - positive_value
```

✅ 通用测试 = 可复用的自定义测试，像函数一样参数化调用。

## 6.4 测试策略与分层

### 各层测试重点

| 层 | 测试重点 | 示例 |
|----|---------|------|
| **Staging** | 源数据完整性 | not_null, unique (主键), row_count |
| **Intermediate** | 业务逻辑正确性 | 非负金额、日期范围合理 |
| **Mart** | 消费端 SLA | 与 BI 指针对齐、跨模型一致性 |

### 测试覆盖率策略

```
关键模型（Mart）:  所有主键 unique + not_null，关键列 accepted_values
中间模型:         主键 unique + not_null
Staging:          主键 unique + not_null + source freshness
```

⚠️ 100% 测试覆盖率不现实——优先保证 **Mart 层和主键列**。

## 6.5 🔧 DuckDB / SQLite 类比（测试本地化）

| # | dbt 测试概念 | DuckDB 本地实现 | SQLite 本地实现 | 标注 |
|---|-------------|----------------|----------------|------|
| 1 | `unique` 测试 | `SELECT col FROM t GROUP BY 1 HAVING COUNT(*)>1` | 同：标准 SQL | 🔧 非本书引擎行为 |
| 2 | `not_null` 测试 | `SELECT col FROM t WHERE col IS NULL` | 同：标准 SQL | 🔧 非本书引擎行为 |
| 3 | `relationships` 测试 | `SELECT * FROM child WHERE fk NOT IN (SELECT pk FROM parent)` | 同：标准 SQL | 🔧 非本书引擎行为 |
| 4 | `accepted_values` 测试 | `SELECT col FROM t WHERE col NOT IN ('a','b','c')` | 同：标准 SQL | 🔧 非本书引擎行为 |
| 5 | 自定义 data test | 任何返回失败行的 `SELECT` 语句 | 同 | 🔧 非本书引擎行为 |
| 6 | `severity: warn` | 无自动机制，需手动检查查询结果 | `CHECK` 约束可强制（更严格） | 🔧 非本书引擎行为 |

> 🔧 以上均为**非本书引擎行为**——dbt 测试框架的自动执行和 severity 管理是 dbt 独有功能。
