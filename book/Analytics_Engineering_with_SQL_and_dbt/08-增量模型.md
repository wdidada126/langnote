## 8.1 为什么需要增量模型？

### 全量重建的瓶颈

| 数据量 | Table 物化耗时 | Incremental 耗时 |
|--------|--------------|-----------------|
| 10 万行 | ~5 秒 | ~5 秒（首次）/ ~0.5 秒（增量） |
| 1000 万行 | ~3 分钟 | ~3 分钟（首次）/ ~2 秒（增量） |
| 10 亿行 | ~30 分钟+ | ~30 分钟（首次）/ ~10 秒（增量） |

✅ 增量模型的核心价值：**将 O(n) 重建成本降为 O(Δn) 增量处理**。

## 8.2 增量模型模板

### 基本模式

```sql
{{ config(
    materialized='incremental',
    unique_key='event_id'
) }}

WITH events AS (
    SELECT * FROM {{ ref('stg_events') }}
    {% if is_incremental() %}
    WHERE event_date > (SELECT MAX(event_date) FROM {{ this }})
    {% endif %}
)
SELECT
    event_id,
    user_id,
    event_type,
    event_date,
    created_at
FROM events
```

### 关键组件

| 组件 | 作用 |
|------|------|
| `is_incremental()` | 区分首次运行（全量）与后续运行（增量） |
| `{{ this }}` | 引用当前模型已存在的物理表 |
| `unique_key` | MERGE 去重键（可选） |
| `WHERE` 过滤 | 限定增量数据范围 |

⚠️ `is_incremental()` 在 `dbt run --full-refresh` 时返回 False。

## 8.3 增量策略

| 策略 | SQL 行为 | 适用场景 |
|------|---------|---------|
| **append** | `INSERT INTO` | 不可变事件日志 |
| **delete+insert** | `DELETE WHERE key IN ...; INSERT` | 有更新的交易数据 |
| **merge** | `MERGE INTO ... USING` | 需要 UPDATE 的维度 |
| **insert_overwrite** | 按分区覆盖 | BigQuery/Spark 大表 |

### merge 配置

```sql
{{ config(materialized='incremental', unique_key='order_id',
    merge_update_columns=['status', 'updated_at']) }}
```

## 8.4 SCD（缓慢变化维度）

- **Type 1（覆盖）**: `unique_key` + merge → 直接覆盖旧值
- **Type 2（历史链）**: `valid_from`/`valid_to` + `is_current` 列 → 保留完整历史

### SCD Type 2 核心逻辑

```sql
-- 关闭旧记录 + 插入新记录（含 valid_from/valid_to/is_current 列）
-- 首次运行：全部插入，is_current=TRUE
-- 增量运行：UPDATE is_current=FALSE + INSERT 新行
```

| SCD 类型 | 行为 | 适用场景 |
|---------|------|---------|
| **Type 1** | 覆盖旧值 | 不关心历史的字段 |
| **Type 2** | 新增行 + 有效期 | 需要审计追踪的维度 |
| **Type 3** | 新增列存前值 | 只关心"上一个值" |

✅ SCD Type 2 是维度建模中**最重要的增量模式**。

## 8.5 增量模型调试

| 陷阱 | 症状 | 解决 |
|------|------|------|
| 数据漂移 | 更新行被遗漏 | 添加 `lookback` 窗口 |
| Schema 变更 | 新列未出现 | `--full-refresh` |
| 重复数据 | unique_key 不唯一 | 检查源数据 + 去重逻辑 |
| 性能退化 | 增量 WHERE 子查询慢 | 用 `max_is` 缓存或 microbatch |

> 调试命令：`dbt run --full-refresh --select model`（重置）、`dbt compile --select model`（查看编译 SQL）。

## 8.6 🔧 DuckDB / SQLite 类比（增量模型本地化）

| # | dbt 增量概念 | DuckDB/SQLite 本地实现 | 标注 |
|---|-------------|----------------------|------|
| 1 | `is_incremental()` 判断 | `CASE WHEN EXISTS(...)` 区分首次/增量 | 🔧 非本书引擎行为 |
| 2 | MERGE 策略 | DuckDB `MERGE INTO`；SQLite 3.35+ `INSERT ... ON CONFLICT` | 🔧 非本书引擎行为 |
| 3 | SCD Type 2 | `UPDATE is_current=FALSE` + `INSERT` 新行 | 🔧 非本书引擎行为 |
| 4 | `--full-refresh` | `DROP TABLE` + 重新 CTAS | 🔧 非本书引擎行为 |

> 🔧 以上均为**非本书引擎行为**——增量编排是 dbt 框架能力。

## 8.7 Microbatch 增量（新范式）

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='microbatch',
    event_time='event_date',
    batch_size='day'
) }}
```

| 特性 | 说明 |
|------|------|
| **按批次处理** | 每天/每小时一个批次 |
| **可重试** | 失败只重试特定批次 |
| **可回溯** | 指定日期范围重跑 |

⚠️ Microbatch 在 dbt-core 1.9+ 可用，是对传统 incremental 的演进。

## 核心概念速览（中英对照）

| 中文概念 | English Term | 一句话定义 |
|---------|-------------|-----------|
| 增量模型 | Incremental Model | 仅处理新增/变更数据的高效 dbt 模型 |
| 缓慢变化维度 | Slowly Changing Dimension (SCD) | 处理维度数据随时间变化的策略体系 |
| MERGE 策略 | MERGE Strategy | 基于唯一键的 UPSERT 增量处理方式 |
| 微批次 | Microbatch | 按时间窗口分批次处理的增量范式 |
| 数据漂移 | Data Drift (in incremental) | 增量窗口遗漏延迟到达数据的問題 |
| 全量刷新 | Full Refresh | 忽略增量状态、完全重建模型的操作 |
| 回溯窗口 | Lookback Window | 防止数据漂移的时间缓冲机制 |
