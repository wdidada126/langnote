## 1.1 从数据仓库到分析工程

### 数据仓库的三次演进

| 代际 | 时间 | 特征 | 代表技术 |
|------|------|------|---------|
| **1.0 传统 DW** | 1990s-2000s | Inmon/Kimball、ETL、本地硬件 | Oracle, Teradata, Netezza |
| **2.0 云仓库** | 2010s | 存算分离、按需付费 | Snowflake, BigQuery, Redshift |
| **3.0 分析工程** | 2020s+ | ELT + 版本控制 + 测试 | dbt + 云仓库 + CI/CD |

✅ 云仓库的存算分离是 ELT 范式的**基础设施前提**——计算廉价到可以反复重跑变换。

### 为什么需要新角色？

```
传统链路:  数据工程师 → ETL → 数据仓库 → BI 工具 → 业务用户
                        ↑ 黑盒 SQL，无版本控制，无测试

分析工程链路: 数据工程师 → EL → 数据仓库 → [分析工程师: SQL 变换 + 测试 + 文档] → BI → 业务
                                          ↑ 版本化、可测试、有文档的 SQL 模型
```

⚠️ 本书未深入讨论的空白地带：谁负责 EL（Extract-Load）？实践中通常由数据工程师用 Fivetran/Airbyte/dbt 完成。

## 1.2 Analytics Engineer vs 相邻角色

| 维度 | Data Engineer | Analytics Engineer | Data Analyst |
|------|--------------|-------------------|--------------|
| **主要产出** | 数据管道、基础设施 | 可信赖的数据模型 | 洞察报告、仪表盘 |
| **核心语言** | Python/Scala/Java | SQL + YAML | SQL + Python/R |
| **工具链** | Airflow, Spark, Kafka | dbt, Git, CI/CD | Looker, Tableau, Jupyter |
| **质量关注** | 管道可用性 | 模型正确性 | 指标准确性 |
| **面向对象** | 下游数据消费者 | 分析师 + 产品 | 业务决策者 |

✅ 分析工程师的核心价值：**用软件工程实践（版本控制、测试、CI/CD）改造分析师的 SQL 代码**。

## 1.3 ELT 范式深度解析

### ETL vs ELT

```
ETL:   源 → [Extract] → [Transform in ETL server] → [Load] → 仓库
ELT:   源 → [Extract] → [Load raw] → 仓库 → [Transform in warehouse] → 模型
```

**ELT 的三大优势**:
1. **原始数据保留**: Load 阶段不做变换，保留完整审计轨迹
2. **仓库算力复用**: Transform 利用仓库的分布式计算能力
3. **敏捷迭代**: 变换逻辑可随时修改，无需重跑 Extract

⚠️ ELT 的代价：仓库存储成本增加（原始数据 + 变换数据并存）。在云仓库按存储付费的模式下，这通常是可接受的。

### ELT 与分析工程的关系

> 分析工程 = ELT 范式 + 软件工程实践 + 数据建模方法论

dbt 是 ELT 的**编排层**——它不执行 Extract/Load，只负责 Transform 阶段的 SQL 管理。

## 1.4 现代数据栈（Modern Data Stack）

### MDS 核心组件

| 层 | 功能 | 代表工具 |
|----|------|---------|
| **Extract/Load** | 数据入仓 | Fivetran, Airbyte, Stitch |
| **Warehouse** | 存储 + 计算 | Snowflake, BigQuery, Redshift |
| **Transform** | SQL 变换 | **dbt** (核心) |
| **Reverse ETL** | 模型出仓 | Census, Hightouch |
| **Orchestration** | 调度 | dbt Cloud, Airflow, Dagster |
| **Observability** | 监控 | dbt Cloud Insights, Monte Carlo |

✅ dbt 占据 Transform 层的**事实标准**地位。

### 🔧 DuckDB / SQLite 类比（本地 MDS 模拟）

| # | MDS 组件 | 生产引擎 | DuckDB 本地替代 | SQLite 本地替代 | 标注 |
|---|---------|---------|----------------|----------------|------|
| 1 | Warehouse | Snowflake/BigQuery | DuckDB（分析型 OLAP） | SQLite（事务型 OLTP） | 🔧 非本书引擎行为 |
| 2 | Transform | dbt + SQL | DuckDB VIEW/CTE 链模拟 ref 依赖 | SQLite VIEW 链 | 🔧 非本书引擎行为 |
| 3 | Extract/Load | Fivetran | `read_csv_auto()` / `read_parquet()` | `.import` CSV | 🔧 非本书引擎行为 |
| 4 | Reverse ETL | Census | DuckDB `COPY TO` 导出 | SQLite `.export` | 🔧 非本书引擎行为 |

> 🔧 以上均为**非本书引擎行为**——本书以 Snowflake/BigQuery/Redshift 为目标引擎。DuckDB/SQLite 类比仅用于本地学习理解概念。

## 1.5 软件工程实践应用于 SQL

### 分析工程师的"软件工程工具箱"

| 实践 | 传统 SQL 脚本 | 分析工程方式 |
|------|-------------|-------------|
| **版本控制** | SQL 文件散落在文件夹 | Git 仓库，分支策略 |
| **代码复用** | 复制粘贴 SQL | dbt ref()、宏（macros） |
| **测试** | 手动 `SELECT COUNT(*)` | dbt schema tests（声明式） |
| **文档** | Word/Confluence 页面 | dbt docs（自动生成） |
| **CI/CD** | 手动部署 | GitHub Actions + dbt Cloud |
| **代码审查** | 无 | PR review + SQLFluff lint |

✅ 这些实践的核心目标：**让 SQL 模型像软件代码一样可维护、可信赖**。

## 1.6 数据建模方法论概览

### Kimball 维度建模

本书以 **Kimball 方法论**为基础：

- **事实表（Fact Table）**: 记录业务事件（订单、点击、支付）
- **维度表（Dimension Table）**: 描述业务上下文（客户、产品、时间）
- **星型模型（Star Schema）**: 事实表 + 直接关联的维度表
- **雪花模型（Snowflake Schema）**: 维度表进一步规范化

⚠️ 本书以 Kimball 为主，但现代实践中 One Big Table（OBT）模式也越来越流行。

### 分层架构

```
Source → Staging → Intermediate → Mart → Reporting
  ↑        ↑           ↑            ↑
原始数据  清洗/重命名  业务逻辑复用  面向主题  BI/仪表盘
```

✅ 分层是分析工程的**核心架构模式**——每层职责清晰，依赖方向单一。

## 1.7 数据治理与分析工程的交汇

分析工程师在数据治理中的角色：

1. **模型文档**: 每个 dbt 模型都有 description、column-level docs
2. **数据质量**: dbt tests 提供自动化质量检查
3. **血缘追踪**: dbt DAG 自动生成列级血缘
4. **访问控制**: 通过 warehouse 权限 + dbt 模型权限管理

> 📖 与 `../Data_Governance_Elsevier/`（#186）的关联：
> - #186 的治理框架 → dbt 的 docs/test 是治理的**技术实现层**
> - #186 的数据质量章节 → dbt tests 是**操作层工具**
