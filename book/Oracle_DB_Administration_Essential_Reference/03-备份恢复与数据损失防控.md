# 03 · 备份、恢复与数据损失防控（⚠️ 主题重构章）

> 本章按出版社文案任务单元"preventing data loss"重构，是全书"危机时刻翻那一页"体裁浓度最高的章。小节划分为本目录自拟（[00-总览与阅读地图.md](00-总览与阅读地图.md) §二）；Oracle 行为全部 ⚠️ 文档转述；🔧G3 为 SQLite/DuckDB 类比实验、**非本书引擎行为**。

## 3.1 故障分类学：本书时代的损失分类（⚠️）

| 损失层 | 典型触发 | 第一响应（Oracle7/8 语境） |
|---|---|---|
| 语句级 | 应用 bug 发错 UPDATE/DROP TABLE | 应用回滚；误 DROP 只能靠导出重导（无闪回！） |
| 用户级 | 误删数据、批量作业跑歪 | 时间点恢复（TTR）到独立实例导出找回 |
| 实例级 | 断电/进程崩 | 重启即 SMON 实例恢复，redo 前滚自动完成 |
| 介质级 | 数据文件/控制文件所在盘坏 | 备份+归档日志介质恢复（本章主场） |
| 灾难级 | 整机房不可用 | 本书时代=Standby Database（8i Data Guard 前身，⚠️ 时间注脚） |

"误 DROP 只能重导"是 1999 与 2026 之间最痛的时代差：闪回查询（9i）、闪回表/删除（10g）、闪回数据库（10g）三层后悔药在本书里一颗都没有——本书的"防数据损失"因此极端依赖备份纪律与归档完整性。

## 3.2 备份矩阵（⚠️）

```
             物理                         逻辑
        ┌────────────────         ┌────────────────┐
 脱机   │ 冷备份：SHUTDOWN │         │ （导出通常联机， │
        │ NORMAL 后拷三件套│         │  归入联机格）    │
        ├────────────────┤         ├────────────────┤
 联机   │ 热备份：表空间级  │         │ EXP：用户/表/全库 │
        │ BEGIN/END BACKUP │         │ 行式转储，dmp 文本 │
        │ + 归档日志连续性 │         │ 可传输性极强      │
        └────────────────┘         └────────────────┘
```

- 冷备份三件套=数据文件+控制文件+pfile（redo 不备，实例恢复后干净）；
- 热备份的协议核心：`ALTER TABLESPACE users BEGIN BACKUP;` → 拷文件 → `END BACKUP;`——BEGIN 后块镜像进 redo（防"分裂块"），代价是 redo 量暴涨；表空间必须 ARCHIVELOG 模式；
- 归档连续性=生命线：`ARCH` 进程挂起（归档目的地满）会直接挂起数据库——本书"数据库挂起十大原因"级条目（⚠️ 通说）；
- RMAN：Oracle8 已随 Enterprise Manager Back Office 出现（8.0/8.0.4 线），但本书主体仍是文件级备份+恢复命令学（⚠️ 推断自出版社文案未提 RMAN，登记为不确定项）。

## 3.3 介质恢复剧本（⚠️ 本目录自拟骨架）

单文件介质丢失的标准剧本（控制文件与其余文件完好）：

```sql
ALTER DATABASE DATAFILE '/disk2/users01.dbf' OFFLINE;
ALTER DATABASE OPEN;                                  -- 库先救活，坏文件隔离
-- 从备份恢复文件到原路径（cp/restore）
RECOVER DATAFILE '/disk2/users01.dbf';               -- 应用归档+在线redo前滚
ALTER DATABASE DATAFILE '/disk2/users01.dbf' ONLINE;
```

变体要点：
- 路径变了：`RECOVER ... FROM '备份位置'` 或先 `ALTER DATABASE RENAME FILE`；
- 控制文件丢失：从备份拷回后 `ALTER DATABASE BACKUP CONTROLFILE TO TRACE` 重建脚本路线，`USING BACKUP CONTROLFILE` + `UNRESETLOGS/RESETLOGS` 分支是全书最凶险的决策点（RESETLOGS 重置日志序列，旧备份链作废——必须立刻全量重备）；
- 时间点恢复：`RECOVER DATABASE UNTIL TIME '2026-...'` 配合 `SET UNTIL`——找回"两小时前误删的表"的标准姿势（恢复到另一台机器再导数）；
- `CANCEL`：恢复过程被坏归档卡住时的逃生阀，代价是放弃 RESETLOGS 前的连续性。

## 3.4 导出/导入：逻辑备份的语法面（⚠️）

`exp scott/tiger file=full.dmp log=full.log full=y buffer=1048576 rows=y` 与 `imp system/manager file=full.dmp fromuser=app touser=app ignore=y commit=y`——参数速查归 08 章，本章记三件纪律：
1. 导出不是备份的替代而是"第二账本"：一致性靠 `CONSISTENT=y`（全库导出）或应用静默，普通用户级导出可能撕裂跨表约束；
2. dmp 是版本单向阀：高版本 exp 的 dmp 低版本 imp 读不了，本书时代升库前先留一手低版本导出；
3. `commit=y` 用导入速度换中断后的脏块返工——1999 年磁盘慢时代的权衡参数。

## 3.5 🔧G3 实验：在线备份的两种现代极简形态（非本书引擎行为）

**SQLite 页级在线快照**（对应"冷/热"光谱上的热档）：

```python
dst = sqlite3.connect(snapfile); c.backup(dst)
```

实测（Python 3.13.2 + SQLite 3.45.3）：

```
G3 live-db vs snapshot sha256[:12]: 0d79b49b07d0 99590f5e0089 identical: False
```

**字节级不同但逻辑一致**——backup API 是页级一致拷贝而非 `cp`：活库文件含空闲页/未合并 WAL，快照是紧凑一致态。这恰好演示了 Oracle 备份恢复的第一原理：**"备份=某一致时刻的逻辑状态"，文件字节一致从来不是目标**（对照 Oracle：热备份文件单独拿出来是"损坏"的，必须配归档才能恢复——同一原理的两侧）。

**DuckDB 逻辑导出**（对应 exp 的"第二账本"档）：

```
EXPORT DATABASE 'w10exp'   -- duckdb 1.5.5 实测产出
G3 duckdb EXPORT DATABASE files: ['e.csv', 'load.sql', 'schema.sql']
```

schema.sql+load.sql+数据 CSV 三件套 ≈ exp 的 dmp+log：文本、可跨平台、可部分回放（只跑 schema 再选择性 LOAD）。**非 Oracle 行为**：DuckDB 无归档日志概念，EXPORT 即全量逻辑快照，不存在"备份+日志前滚"的增量链。

## 3.6 备份域速查卡（⚠️ 自拟）

| 症状/任务 | 命令入口 | 关联参数/视图 |
|---|---|---|
| 库是否归档模式 | `ARCHIVE LOG LIST` | `log_archive_start`、`V$DATABASE.LOG_MODE` |
| 归档去哪了 | — | `V$ARCHIVED_LOG`（序列断档=恢复断链） |
| 表空间热备中 | `SELECT * FROM V$BACKUP WHERE STATUS='ACTIVE'` | BEGIN/END BACKUP 配对 |
| 恢复卡住 | `RECOVER ... CANCEL` | 缺的归档序列号在报错里 |
| 控制文件镜像 | `ALTER DATABASE BACKUP CONTROLFILE TO 'f'` / `TO TRACE` | `control_files` |
| 冷备份清单 | 三件套+`SELECT name FROM v$datafile;` 快照 | pfile 一起拷 |

## 核心概念速览（中英对照）

| 中文 | 英文 | 一句话 |
|---|---|---|
| 冷备份/热备份 | cold / online backup | 停机三件套拷贝 vs 联机表空间 BEGIN BACKUP |
| 归档日志 | archived redo log | 在线 redo 的循环覆盖前抢救出的连续历史 |
| 介质恢复 | media recovery | 备份文件+归档前滚到指定时刻 |
| 时间点恢复 | point-in-time recovery (TTR) | UNTIL TIME/SCN 的定向恢复 |
| 重置日志 | RESETLOGS | 备份控制文件路线的分叉闸，旧链作废 |
| 逻辑备份 | export/import (EXP/IMP) | dmp 行式转储，跨版本"第二账本" |
| 实例恢复 | instance recovery | 重启后 SMON 用在线 redo 自动前滚+回滚 |
| 分裂块 | fractured block | 热备期 OS 半块拷贝事故，BEGIN BACKUP 的防御对象 |
| 备份一致性 | read-consistent backup | 逻辑状态一致≠文件字节一致（🔧G3 实证） |
| 备份策略 | backup strategy | 全量/增量/归档保留期的周期编排 |

## 最新演进与工业实践

- **RMAN 全面接管**（⚠️）：9i 起 RMAN 成为唯一推荐物理备份接口，BEGIN BACKUP 手工协议退役；增量备份（level 0/1）、块介质恢复（BLOCKMEDIARECOVERY，只修坏块不修文件）、备份加密、DUPLICATE 建备库都在本书之后长大。✅ 现行手册（实抓经重定向 200）：https://docs.oracle.com/en/database/oracle/oracle-database/23/bradv/ （Backup and Recovery User's Guide，/26/bradv/）。
- **后悔药三层**（⚠️）：9i 闪回查询（`AS OF TIMESTAMP`）、10g 闪回删除（回收站）/闪回表/闪回数据库、11g 保留点（RESTORE POINT）+ 快速恢复区——3.1 表格里"误 DROP 只能重导"一行被彻底改写。
- **Data Guard 与云备份**（⚠️）：8i Standby → 9i Data Guard 品牌化 → 现代 MAA 架构（快照备库、自动故障转移）；云上 OBACE/Azure/OCI 把"备份目的地满挂库"转为对象存储无限桶问题。
- **exp/imp 退役**（⚠️）：10g Data Pump（expdp/impdp，服务器端作业、并行、网络模式导入）替代；本书 3.4 语法仅存于遗留脚本考古。✅ Utilities 手册（实抓 200）：https://docs.oracle.com/en/database/oracle/oracle-database/23/sutil/ 。
- **工业实践**（⚠️ 通说）：3-2-1 备份纪律、恢复演练（不演练的备份等于没有）、RPO/RTO 指标化——本书"preventing data loss"章的清单思维正是今天 runbook 文化的直系祖先。
- **类比锚点**（🔧G3，非本书引擎行为）：SQLite backup API 与 DuckDB EXPORT 分别演示了"页级一致快照"与"逻辑转储"两极；Oracle 备份体系=这两极+归档日志链的完整组合。
