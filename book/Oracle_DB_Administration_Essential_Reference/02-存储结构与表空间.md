# 02 · 存储结构与表空间（⚠️ 主题重构章）

> 本章按出版社文案"DBA reference: the Oracle instance and database"与任务单元"preventing data loss"的存储侧重构。小节划分为本目录自拟（降级声明见 [00-总览与阅读地图.md](00-总览与阅读地图.md) §二）；Oracle 不可本机实测，全部 ⚠️ 文档转述；🔧G2 为 SQLite 类比实验、**非本书引擎行为**。

## 2.1 三级存储世界观：库—文件—块（⚠️）

Oracle 存储模型自 Oracle V6/V7 定型，本书把它压缩成一张速查图（本目录重述）：

```
数据库 (database)
 ├── 数据文件 dbf × N        ← 物理层：OS 看得见的一切
 ├── 控制文件 ctl × ≥2       ← 库的"账本"：文件清单/检查点/日志序列
 ├── 重做日志 redo × ≥2组    ← 物理层：改变的先写记录（03 章主场）
 └── 逻辑层：
      表空间 tablespace ── 段 segment ── 区 extent ── 块 block(2KB~8KB, db_block_size)
```

关键映射关系（DBA 查表必背）：一个表空间含多个数据文件；一个段只属于一个表空间，但可跨该表空间内多个文件；区是段的分配单位；块是 IO 与锁的最小单位。表、索引、回滚段、临时段都是"段"——所以 `DBA_SEGMENTS`/`DBA_EXTENTS` 是全书存储域的万能入口（08 章字典速查）。

## 2.2 Oracle8 的分水岭：本地管理表空间（⚠️）

本书"covers Oracle7 and Oracle8"的最大实质差异就在本章：

| 维度 | 字典管理表空间 (DMT，Oracle7 唯一形态) | 本地管理表空间 (LMT/LOCAL，Oracle8.0 引入) |
|---|---|---|
| 空闲空间记账 | 存在数据字典表（FET$/UET$ 类），集中热点 | 存在每个数据文件头部的位图（extent map） |
| 分配竞争 | 字典回滚段串行化，DD 锁等待 | 位图按文件分散，无集中字典更新 |
| 碎片 | 需要 `ALTER TABLESPACE ... COALESCE` 手工整理 | 统一大小区（UNIFORM SIZE）天然防碎片 |
| 回收段 | 需要手工 DEALLOCATE UNUSED | 自动收缩记账 |

`CREATE TABLESPACE ts1 DATAFILE '...' SIZE 100M EXTENT MANAGEMENT LOCAL UNIFORM SIZE 1M;` 这一行是 1999 年 DBA 的"新世界语法"。本书同时保留两套速查——正是它"为仍跑 Oracle7 的站点提供旧知识、为 Oracle8 站点提供新知识"的双轨定位（✅ 出版社文案明言）。

## 2.3 回滚段与读一致性（⚠️）

Oracle8 时代 undo 仍叫回滚段（rollback segment）：

- 规划公式（通说）：`所需回滚段数 ≈ 并发事务峰值 / MAX_TRANS_PER_SEGMENT`，`TRANSACTIONS` 参数联动；
- 系统回滚段（SYSTEM 表空间内）+ PUBLIC 回滚段 + 私有回滚段（`rollback_segments` 参数点名）三态；
- 读一致性（read consistency）：查询按 SCN 从回滚段 reconstruct 过去镜像——"ORACLE-1002 snapshot too old" 是长跑查询撞碎 undo 的标志性错误；
- Oracle8i（本书出版后数月）才有 UNDO 表空间与 `UNDO_MANAGEMENT=AUTO`（⚠️ 时代注脚：本书成稿停在手工回滚段世界）。

## 2.4 临时表空间与排序（⚠️）

Oracle8 引入临时表空间（TEMPORARY TABLESPACE）替代把 SYSTEM 当排序溢出的灾难惯例：`CREATE TEMPORARY TABLESPACE temp TEMPFILE ...`。用户 `TEMPORARY TABLESPACE` 属性、`sort_area_size` 溢出入临时段的链路，是 06 章调优"排序类等待"的物理前提。

## 2.5 块大小与未来伏笔（⚠️）

`db_block_size` 在 Oracle8 时代建库定死；Oracle9i 引入多块大小缓存（`db_cache_size` + `db_nk_cache_size`），为传输表空间（transportable tablespace）铺路——本书"prevent data loss"单元里"跨平台迁移靠导出导入"的笨重感，正是被这个后续演进解除的（对照见 §最新演进）。

## 2.6 🔧G2 实验：ATTACH 多文件 vs 表空间抽象（非本书引擎行为）

SQLite 没有表空间概念——它的"多文件"靠 `ATTACH` 手工拼：

```python
c = sqlite3.connect(d1)                      # main = w10a.db
c.execute("ATTACH ? AS aux", (d2,))          # aux  = w10b.db
c.execute("CREATE TABLE aux.s1(y)")          # 表可以显式指定"落哪个文件"
```

实测输出（Python 3.13.2 + SQLite 3.45.3，2026-10-02）：

```
G2 databases: [('main', 'w10a.db'), ('aux', 'w10b.db')]
G2 main.s1 err: no such table: main.s1
```

两组发现（均标**非 Oracle 行为**，仅作概念对照）：
1. SQLite 的 schema 名（main/aux）≈ 命名空间级"文件路由"，需要人肉指定目标文件；Oracle 表空间把"对象→文件"的映射交给分配器（段头/位图），用户只说表空间名——**抽象层差一级**，这正是 Oracle 能在线搬文件（`ALTER DATABASE DATAFILE ... RESIZE/OFFLINE`）而 SQLite 不能的原因；
2. `main.s1` 报错证明文件间命名空间严格隔离，无 Oracle"一个实例统一字典视图（`DBA_TABLES` 一览全局）"的对应物。
DuckDB 侧对照：单文件数据库，无 ATTACH 等价物参与本实验（duckdb 1.5.5，见 08 章 🔧G6 的字典对照）。

## 2.9 章前自测与本章边界

- 自测三题：①一个表的段能否跨两个表空间？（不能——段属单一表空间，但可在其内多文件）②为什么 LMT 不需要 COALESCE？（位图+统一区天然防碎片）③ORA-01555 为什么既是存储问题又是时间问题？（undo 镜像被覆盖=空间回收踩到读一致性时间窗）。
- 本章边界：undo/redo 的进程与日志缓冲机制归 07 章解剖、恢复剧本归 03 章、容量事故排错在盘另有 [../Oracle_Database_Problem_Solving/03-DDL优化与大型数据库.md](../Oracle_Database_Problem_Solving/03-DDL优化与大型数据库.md)（已验名实链）。
- 版本坐标提醒：本章的"新语法"（LMT/TEMPORARY TABLESPACE）在 1999 是明日、在 2026 是昨日——读速查书老版本时，先给每个条目找"引入版本/退役版本"两个锚，是本目录各章通用的考古方法（00 §九有同款声明）。
- 证据锚点：LMT 为 Oracle8.0 引入、UNDO 表空间属 8i 两条 ⚠️ 断言，可在 00 §六登记的 11g 存档 URL（实抓 200）与 23ai admin 手册中回查版本史叙述；本目录未获原书页码级证据，维持 ⚠️ 级。

## 核心概念速览（中英对照）

| 中文 | 英文 | 一句话 |
|---|---|---|
| 表空间 | tablespace | 逻辑分配域：对象归属单位，物理由数据文件承载 |
| 数据文件 | datafile | OS 层实体，一个表空间可含多文件 |
| 段/区/块 | segment / extent / block | 分配三级：对象—分配单位—IO 单位 |
| 字典管理表空间 | dictionary-managed tablespace (DMT) | Oracle7 唯一形态，集中记账有热点 |
| 本地管理表空间 | locally-managed tablespace (LMT) | Oracle8 位图记账，防碎片防竞争 |
| 回滚段 | rollback segment | undo 手工时代载体，读一致性镜像来源 |
| 快照过旧 | ORA-01555 snapshot too old | 长跑查询把 undo 覆盖掉的标志错误 |
| 临时表空间 | temporary tablespace | 排序/哈希溢出的专用段容器 |
| 高水位线 | high-water mark (HWM) | 段内已格式化块边界，全表扫描的起点 |
| 统一区大小 | UNIFORM SIZE | LMT 防碎片策略：区一律等大 |

## 最新演进与工业实践

- **LMT 一统天下**（⚠️）：DMT 在 10g 后仅存兼容价值，11g 起 SYSTEM 表空间必须 LOCAL；今天 DBA 手册里"extent management local autoallocate"是默认句。✅ 现行概念文档入口（实抓经 /23/ 重定向 200）：https://docs.oracle.com/en/database/oracle/oracle-database/23/admin/ （Database Administration Guide，/26/admin/）。
- **UNDO 表空间**（⚠️）：8i 的 `UNDO_MANAGEMENT=AUTO` + `UNDO_RETENTION` 彻底废除手工回滚段速查表；12c 起支持在线迁移 undo 表空间。本书 2.3 整节转为考古知识。
- **大-SBC 与 ASSM**（⚠️）：32KB 块（8.1 时代为 RMAN 块对齐引入）后来长到 32K 实用；11g 自动段空间管理（ASSM）替代 FREELISTS——2.5 的"块大小建库定死"在 9i 多块缓存后松动。
- **统一表空间与 OMF**（⚠️）：12c BigFile 表空间（一表空间一文件、TB 级）、Oracle 管理文件（`DB_CREATE_FILE_DEST`）把 2.7 的"加文件"手工动作整行删除。
- **工业实践**（⚠️ 通说）：现代容量治理从"表空间位图"上移到 ASM 磁盘组与存储层快照；但 ORA-01653（无法扩段）报错文案三十年未变，考古本章仍对得上症状。
- **类比锚点**（🔧G2 结论复述，非本书引擎行为）：SQLite ATTACH 的"人肉文件路由"与 Oracle 表空间"声明式分配域"的层级差，是理解"为什么 Oracle 需要 DBA 而 SQLite 不需要"的最小样本。
