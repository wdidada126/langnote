## 核心概念速览（中英对照）

- **跟踪实例** — Instance Tracking：给类装上计数器，观察构造/拷贝/析构发生的**次数与位置**——本书第 1 章的全部，也是全书方法论"先看见，再优化"的第一步。
- **构造代理** — Tracking Proxy/Base：把计数逻辑放进基类或成员，业务代码零改动的插桩手法。
- **构造次序** — Construction Order：基类→成员（声明序）→自身；**析构严格逆序**。
- **复合成本** — Composition Cost：一个对象的构造 = 其全部成员构造之和；"廉价的构造函数"可能只是把账单转给了成员。
- **数组构造** — Array Construction：`new T[n]` 触发 n 次构造，是"一个 new"背后最大的隐藏循环。
- **缓式构造** — Lazy Construction：昂贵成员推迟到首次使用才构造（空间换时的反向：时点换时）。
- **冗余构造** — Redundant Construction：`X x; x = value;`＝默认构造+赋值两步，应写成 `X x(value);`。
- **隐式默认构造** — Implicit Default Constructor：无用户构造时编译器生成的按成员默认初始化，可能悄悄初始化了整个基类链。

## 动机：为什么第一章不讲任何"优化"，只讲"数数"

Bulka/Mayhew 的背景是 IBM 网络栈调优：他们见过的性能问题几乎从不是"算法慢"，而是
**对象流量远超设计者想象**——一个请求处理过程中创建/销毁了几千个对象，而程序员以为只有几个。
所以第 1 章的"跟踪实例"不是玩具，而是全书的地基仪器：

```cpp
// 🔧 教学示意：原书 1.1 思路的极简重写
struct Tracked {
    static long ctors, copies, dtors;
    Tracked()               { ++ctors; }
    Tracked(const Tracked&) { ++copies; }
    ~Tracked()              { ++dtors; }
};
long Tracked::ctors, Tracked::copies, Tracked::dtors;
// 跑完真实负载后打印三个数：ctors+copies 应等于 dtors；
// 不等 → 有对象逃逸/泄漏；copies 巨大 → 后面第 4/5/12 章的问题找上门。
```

机制层面：计数器是**可观测副作用**，它禁止编译器做任何省略——这也是本次实测的伏笔
（见 [03 章](03-返回值优化RVO与临时对象.md)实测 #1：一旦拷贝构造带全局计数，`-O2` 仍能把
"每循环一次 ++"折叠成 `+= N`，闭式优化比想象的更凶；但只要计数与数据相关就折不动）。
跟踪的代价是每实例 3~4 次内存写，所以它是**诊断构建**的工具，不是产品代码。

## 机制：一条 `new Derived` 背后的真实工作量（2.1/2.2）

第 2 章把构造函数从"语法糖"还原成"函数调用序列"：

1. 分配内存（`operator new`，若有多态还要小心 vptr 时序）；
2. 依次构造：虚基类 → 直接基类（声明序）→ 非静态数据成员（**声明序，不是初始化列表序**）；
3. 才执行派生类构造函数体——体执行的永远是最后。

两条推论直接决定性能账：

- **成本可加性**：`Derived` 的"空构造" `Derived() {}` 一点都不空——它调用基类默认构造 + 每个成员默认构造。复合十层，每个对象就是十几次函数调用的流水线。这正是 [../深度探索C++对象模型/02-构造函数语意学.md](../深度探索C++对象模型/02-构造函数语意学.md) 讲的"构造函数语意学"，Lippman 从编译器角度、本书从账单角度，同一枚硬币。
- **数组放大**：`new Rational[10000]` 展开为一万次构造循环；若默认构造里有除法/字符串，成本随 n 线性爆炸。第 2 章的警告在 C++11 后有了体面出口：`std::vector` + `resize/assign` 的批量语义 + 移动语义，见下文演进节。

## 权衡：缓式构造与冗余构造（2.3/2.4）

**缓式构造**（2.3）：`class GpsPosition { Time now_; }` 里 `Time` 的构造要取系统时间，
而 90% 的 GpsPosition 从不读 `now_`——于是把成员换成指针/`optional`，用到才造。
权衡三角很清晰：**内存**（多一个空态表示）、**速度**（首次使用变慢、分支变多）、
**线程安全**（"检查-然后-构造"是竞态，1999 年单线程假设今天必须明说）。

**冗余构造**（2.4）：最廉价也最常见的修复——

```cpp
// 🔧 原书 2.4 场景重写
Rational r;      r = computeRate(a, b);   // 坏：默认构造 + 完整赋值
Rational r2(computeRate(a, b));           // 好：一步到位
// C++11 后首选：auto r3 = computeRate(a, b);  // 配合 RVO 常为零零开销，见 03 章
```

它与 [../More_Effective_C++/01-基础技法.md](../More_Effective_C++/01-基础技法.md) 里"Meyers 8 条"式的
条款建议同源；区别是本书用实测数据（IBM 项目上冗余构造占了多少 ms）论证，而不是条款说教。

## 相邻概念对比

| 手法 | 消灭的成本 | 引入的成本 | 现代对应 |
| --- | --- | --- | --- |
| 跟踪实例 | （不消灭，暴露） | 每实例数条指令 | 分配采样/构造插桩 profiler |
| 缓式构造 | 未用成员的构造 | 空态、分支、线程安全负担 | `std::optional`、`std::call_once` |
| 消除冗余构造 | 一次默认构造+赋值 | 无（纯改写） | 列表初始化 `T x{...}` 成惯用法 |
| 声明序敏感 | —— | —— | 编译器 `-Wreorder`/clang-tidy 已强制 |

## 最新演进与工业实践

- **移动语义改写了一半结论**（✅ 标准事实）：C++11 起"默认构造+移动赋值"往往只比直接构造多一个
  寄存器搬运；冗余构造从性能问题降级为风格问题。但**跟踪实例**揭示的"对象流量超预期"依旧成立——
  只是今天流量的单位成本更低。
- **插桩的后裔**：现代工具把"数数"做成了产品级——gperf 的 `--collect-allocation`、
  jemalloc 的 prof、**abseil allocation sampling**（官方文档 `abseil.io/docs/cpp/guides/allocation`，
  ⚠️ 本次未连通核验）把 HeapSample 变成生产可常开的采样；概念与 1.1 完全同构：观测分配/构造事件流。
- **`std::optional` 是制度化的缓式构造**：值语义 + 显式空态 + 无额外堆分配，替代当年"成员换指针"
  的手艺（⚠️ trivially-destructible 优化仍依赖实现）。
- **数组构造问题今天的答案**：`std::vector<T>(n)` 依然 n 次构造（POD 例外：分配器可为平凡类型
  走 `malloc` 不初始化——glibc/MSVC 对 `vector<int>` 均如此 ⚠️ 未逐一实测）；想要"分配不构造"
  用 `std::unique_ptr<T[]>`+自定义初始化或 `uninitialized_fill` 家族（C++20 起并行算法亦可）。
- **结论**：第 1 章方法论**完全成立**（今天的名字是 allocation profiling）；第 2 章的具体技巧里，
  消冗余构造仍然要写进 code review 清单，缓式构造则优先考虑 `optional`/`call_once` 的标准形态。

## 常见误区与自查

- **误区 1："`Derived() {}` 是空构造"**——它至少是"基类默认构造 + 每个成员默认构造"的转发函数；
  类越深越贵，而调用点完全看不出来。自查：对热点类跑一次跟踪实例，比较 `ctors()` 与你的直觉。
- **误区 2："成员初始化列表决定构造次序"**——决定次序的是**声明次序**；列表顺序与声明顺序
  不一致时，编译器告警（`-Wreorder`）不是洁癖而是 bug 预告（引用了尚未构造的成员）。
- **误区 3："缓式构造总是更快"**——它把成本摊给"首次使用 + 每次判空"；若对象 100% 会被用到，
  缓式构造稳输。书中 2.3 的判据（使用概率）今天仍然要先量化再动手。
- **误区 4：把计数器留在产品里**——跟踪是诊断构建技术；生产环境要换成采样式观测（见演进节）。
- **自查三连**：① 你的热点类拷贝构造被调用过吗（`copies()`>0）？② 有没有 `T x; x = ...;` 句式？
  ③ 数组/容器批量构造的对象，能否改用带初值的 `resize`/`assign` 或直接少造？
