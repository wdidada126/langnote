## 核心概念速览（中英对照）

- **内联** — Inline Expansion：以函数体副本替换调用点；`inline` 关键字的本意（链接模型）与"请求展开"的俗意在 C++ 里长期纠缠。
- **调用约定** — Calling Convention：参数/返回值在寄存器还是栈上、谁清理、哪些寄存器被 clobber——8.2 的成本清单一半来自它。
- **调用开销** — Call Overhead：call/ret 指令对、参数搬运、寄存器保存恢复、流水线断点；小函数场景下可超过函数体本身。
- **调用间优化** — Interprocedural Optimization：内联的真正目的——让常量传播、拷贝传播、死代码消除跨越函数边界。
- **内联屏障** — Inlining Barrier：显式阻止展开（当年的宏/编译开关；今天的 `__attribute__((noinline))`），保住调试性与代码体积。
- **代码膨胀** — Code Bloat / I-cache Pressure：展开换大小——指令缓存与预取解码带宽是内联的真实预算线。
- **递归内联** — Recursive Inlining：沿调用链多层展开后再整体优化；10.3 的手工技巧今天由编译器自动执行。
- **条件/选择性内联** — Conditional/Selective Inlining：把冷分支拆成真函数、热路径留在原地——现代编译器的 cold/likely 属性与机器学习内联器（⚠️ 具体实现细节未逐项核实）的雏形。
- **基于配置的内联** — Configuration-based Inlining：按构建配置（调试/性能）切换展开策略，9.4 的主题。

## 动机：调用一个"两个除法"的函数贵过两个除法本身？

8.2 把方法调用解剖成一张税单：①参数入栈/入寄存器；②call 跳去、跳回（ret）；③被调函数
保存/恢复寄存器（callee-saved 搬家）；④返回后调用方继续用不到的中间结果占着栈槽。
对 1–5 条指令的小函数，税单常比货款贵。但**最重要的洞见在 8.3/9.1**：
内联的价值与其说是"省了 call"，不如说是**把函数边界这堵墙拆了**——边界一侧看不见的
常量、条件、死代码，边界合并后全部可优化。书里 `operator+` 的例子：展开后编译器发现
其中一个操作数是编译期常量，整个表达式折叠成更少的运算。这种"二阶收益"是 1999 年
手工内联的真正动机，也是今天 `-O2` 的日常工作。

## 机制 → 实测：内联收益是"上下文相关"的（00 总表 #6）

已实测 g++ 15.2（-std=gnu++23，2 亿次 3 维点积，本机单次样本）：

| 构建 | `noinline` 版 | `always_inline` 版 |
| --- | --- | --- |
| `-O2` | 134.5 ms | 140.3 ms（**差异淹没在噪声里**） |
| `-O0` | 638.1 ms | 558.9 ms（展开收益 ~12%） |

诚实解读：`-O2` 下两版瓶颈都是循环携带的浮点加法依赖链（每迭代一条 FADD 延迟），
call 开销被乱序执行完全掩盖——**当别的瓶颈更硬时，内联赚不到钱**。这恰好实证 9.2
"何时避免内联"的深层逻辑：内联不是普适增益，是把"调用成本"和"后续优化空间"摆上天平。

机制层面三种展开路径要分清：

1. **关键字 `inline`**：本意是链接模型（允许重复定义/ODR 豁免），**不构成展开义务**——类内定义天然 inline，头文件里的函数定义没有它就链接报错；
2. **编译器启发式**：按体积预算（GCC 的 `--param inline-*` 一族 ⚠️ 参数名未逐一核对）+ 调用频次自动决策；
3. **强制**：`__forceinline`/`always_inline`——附带前提"违反体积约束是 UB 邻近区"（MSVC 超预算即拒绝）。

**虚方法的内联**（8.5）：调用点不知道去哪，展开无从谈起——除非整个 SCC 里该动态类型可证
（去虚化，见 [02 章](02-虚函数开销与模板继承.md)演进节）。这解释了 02 章实测里 CRTP 对
虚函数的碾压性优势：静态分发让内联 + 后续一切优化重新上线。

## 权衡：9.2/9.3 的"反内联清单"今天更长

| 内联有害的情形 | 机制原因 |
| --- | --- |
| I-cache 未命中的巨型函数 | 解码/取指带宽比省两条 jmp 贵几个数量级 |
| 需要帧信息的可调试性 | 展开后 gdb 步进混乱、backtrace 失真——9.3"开发阶段"主题 |
| 返回值地址被逃逸（`&local`） | 必须落栈，"寄存器化返回"红利消失（与 9.5 规则相关） |
| 尺寸未知即无法决策 | 当年编译器视野窄；今天 PGO/LTO 补证据 |
| 热更新/插件 ABI | 函数体进邻居二进制=版本锁死——1999 年不存在的约束 |

9.4"基于配置的内联"（同一代码在性能构建展开、调试构建不展开）在现代以 `__attribute__((always_inline))`
+ `#if NDEBUG`、或干脆交给 `-Og`/`-O2` 分层实现——思想存活，手艺消失。

## 相邻概念对比

- **内联 vs 宏**（当年真实辩论）：宏=文本替换、无类型检查、调试为 0；内联=函数实体、类型系统完好。9.4 的配置技巧本质是"带类型检查的宏"。
- **内联 vs 模板**：模板函数天然邀请全函数进头文件——接口即实现，展开是默认期待（代价：编译时间与错误信息，见 [../C++模板元编程.md](../C++模板元编程.md) 的语境）。
- **内联 vs 池化/[04 章](04-单线程内存池.md)**：都在打"每次动作的固定税"，一个搬代码到调用点，一个搬分配到预存块——方法论语异同。

## 最新演进与工业实践

- **决策权完全移交编译器**（✅ 通行事实）：现代 GCC/Clang 的内联器是体积预算 + 频率画像 +
  （LLM 路线）机器学习的组合（⚠️ 各实现细节未逐项核文献）；手工 `inline` 对展开决策的影响≈0，
  它的真实职责是 ODR/链接。当年"决定哪些函数手工内联"的职业手艺，今天只剩 `always_inline`/`noinline`
  两个逃生舱（写 benchmark、控制栈深度、保尾调用）。
- **LTO/PGO 吃掉了"跨文件内联"技巧**：10.3 的递归内联、9.1 的调用间优化，在 `-flto -fprofile-use`
  下自动跨 TU 发生——当年靠头文件搬家实现的"让编译器看见调用链"，现在一条编译选项。
- **新约束**：Spectre 类缓解让间接调用变贵（IBRS/Retpoline，Intel/AMD 文档 ✅ 概念、具体代价依平台 ⚠️）；
  这给"去虚化后变直接 call"再添一分现代红利。
- **工业实践对应**：Google C++ Style 明确"不基于性能理由手写 inline"（风格指南 ⚠️ 未连通核验原文）；
  Abseil 的 `ALWAYS_INLINE` 宏仅用于已 profile 的热点；`__builtin_expect`/`[[likely]]` 与冷热拆分（de-inlining，
  把冷分支**搬出去**）是反向手艺的现代版——为热路径腾 I-cache。
- **结论**：第 8–10 章**结论几乎全部被编译器接管，但机制知识 100% 保值**——读懂"profile 里
  为什么这函数没被展开/为什么 LTO 后反而变慢/为什么加了内联 I-cache miss 暴涨"仍需要这三章。
  当年"技巧"（手工挑内联点）今天不成立；当年"视角"（内联是打开优化之门的钥匙）今天仍是真理。

## 机制补充：调用税的清单与两个逃生舱

1999 年税单（8.2）对应到今天 x86-64 System V：参数前 6 个整数值进寄存器、更多落栈；
callee-saved（rbx/rbp/r12–r15）被函数碰到就得保存恢复；返回值一超寄存器就暗传指针
（接 [03 章](03-返回值优化RVO与临时对象.md)的隐藏暂存）。两个当代逃生舱：

- **尾调用优化（TCO）**：`return f(x);` 可编译成 `jmp f`——不压新帧，递归变循环；
  与内联互补（GCC 对 `-O2` 尾位置有限度执行 ⚠️ 触发条件依版本与 ABI 细节，未实测）。
- **`noinline` 作为测量工具**：写 benchmark 时给对照组加 `__attribute__((noinline))`
  才能隔离"函数体本身"与"边界效应"的贡献——本次实测 #6 正是这么做的。

## 常见误区与自查

- **误区 1："头文件里的成员函数都自动展开了"**——`inline` 关键字只保证链接合法，
  展开与否看编译器预算；模板在 `-O0` 下常常不展开，"模板=必然内联"是错觉。
- **误区 2："内联越多越快"**——实测 #6 的 `-O2` 平局就是反例；更大的反例是链式大函数
  全展开后 I-cache/解码带宽爆炸（16.4 的缓存效应在指令侧），性能不升反降。
- **误区 3："性能问题先查内联"**——顺序反了：先 profile 定热点（[09 章](09-编码优化与设计优化.md)
  的 80-20），再确认该处是否被"没展开"卡住（看汇编或 `-fopt-info-inline` 类报告 ⚠️ 选项名以版本为准），最后才动属性。
- **自查**：你的"手工内联"收益能用 `-flto -O2` 复现吗？若能，删掉手艺保留意图注释；
  若真复现不了（跨动态库边界、运行期选型），你面对的其实是 [02 章](02-虚函数开销与模板继承.md)的分派问题，不是内联问题。
