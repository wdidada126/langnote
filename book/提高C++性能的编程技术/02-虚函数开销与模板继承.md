# 02 · 虚函数开销与模板继承（原书第 3 章）

> 覆盖：3.1 虚函数的构造、3.2 模板和继承、3.3 要点。
> 大纲版见 [../提高C++性能的编程技术.md](../提高C++性能的编程技术.md)；总览见 [00-总览与阅读地图.md](00-总览与阅读地图.md)。

## 核心概念速览（中英对照）

- **虚函数表** — Virtual Table (vtable)：每类一表的函数地址数组；`virtual` 的运行时载体。
- **虚表指针** — Virtual Table Pointer (vptr)：对象头部隐藏的指针，指向其动态类型的 vtable。
- **虚调用** — Virtual Call：`载入 vptr → 载入表项 → 间接 call` 三连，运行时才知道去向。
- **构造中的虚函数** — Virtuals During Construction：构造期 vptr 逐级"降级"，虚分派在构造/析构中不穿越继承层——本书 3.1 用性能视角重讲这条语意规则。
- **奇异循环模板基类** — Curiously Recurring Template Pattern (CRTP)：`struct D : Base<D>`，把"虚"搬到编译期；书中 3.2 的"模板和继承"即其雏形。
- **模板方法** — Template Method：非虚骨架函数 + 虚钩子；骨架省一次虚调用，钩子照付。
- **去虚化** — Devirtualization：编译器证明动态类型后把虚调用改成直接调用（现代 GCC/Clang 才有，LTO 扩大射程）。
- **内联与虚** — Inlining vs Virtuality：虚调用阻断调用点内联（除非去虚化成功），这是第 8–10 章内联收益谈不上的根因之一。

## 动机：一次 `p->f()` 到底花了什么

1999 年多数教材把虚函数当纯语意话题。本书的问题不同：**热循环里每个对象都过一次虚函数，
值多少钱？** 机制拆到指令层（x86-64 System V，本目录实测反汇编格式）：

```asm
; 🔧 已实测 g++ 15.2 -O2，bench3 run_dyn 内层循环（b3.o objdump 节选）
mov    (%rax,%rdx,8),%rcx   ; rcx = vector[i&3]，即 Base*
mov    (%rcx),%rax          ; rax = 对象第 0 槽：vptr
call   *0x10(%rax)          ; 跳到 vtable 偏移 0x10 的表项（op()，虚析构占前一槽）
```

三笔账：(a) 两条**依赖链上的 load**（对象→vtable→函数地址），vtable 常是缓存冷数据；
(b) 一条**间接 call**——BTB 猜错就是十几周期报废；(c) 编译器**看不见被调函数体**，
参数常量传播、向量化、跨函数重排全部作废，除非整个调用链都进了 LTO 且类型可证。

## 机制 → 实测：贵的主要是"不可预测"（3.1 + 8.5 的先行结论）

已实测 g++ 15.2 -O2（3 亿次调用，本机单次样本；实验号对应 00 总表 #3）：

| 场景 | 耗时 | 相对 |
| --- | --- | --- |
| 虚调用，4 目标混合轮转（多态） | 1985.4 ms | 29.5× |
| 虚调用，全部同一目标（单态） | 295.0 ms | 4.4× |
| CRTP 静态分发 | 67.4 ms | 1× |

- 单态虚调用只比 CRTP 贵 ~4 倍——这 4 倍就是 vtable load + call/ret + 阻断内联的裸成本。
- 混合目标再贵 7 倍——**间接分支预测失败**才是大头（⚠️ 未用 perf 计数器直接证明 mispredict 率，
  归因依据是 3.1/16.6 的机制与学界共识）。
- 诚实脚注：本例 CRTP 版被 GCC 折叠成闭式求和（反汇编里循环没了），67 ms 低估了"逐次调用"的
  静态分发音速；即便如此，动态:静态 ≥4.4× 的下界结论不变。

**构造中的虚函数**（3.1 的性能侧）：基类构造期间 vptr 指向基类 vtable，虚调用不会跑到派生层——
编译器干脆静态化（去虚化）这些调用；想"构造时按派生类初始化"只能靠二阶段初始化（init 钩子），
而那又引入"对象半构造态"的语意税。这与 [../深度探索C++对象模型/06-执行期语意学.md](../深度探索C++对象模型/06-执行期语意学.md) 的 vptr 时序分析互为表里。

## 权衡：CRTP 与"模板和继承"（3.2）

```cpp
// 🔧 书中 3.2 思路的现代写法
template <class Self> class Counted {          // 静态"虚"钩子
public: void tick() { static_cast<Self*>(this)->doTick(); }  // 编译期解析，可内联
};
class Widget : public Counted<Widget> {
    friend class Counted<Widget>;
    void doTick() { ++n_; }  long n_ = 0;
};
```

| 维度 | 虚函数 | CRTP |
| --- | --- | --- |
| 分派时机 | 运行期 | 编译期 |
| 内联/LTO 视野 | 阻断（除非去虚化） | 天然可内联 |
| 异构容器（`vector<Base*>`） | ✅ 唯一选择 | ❌ 模板参数即类型，容器装不了"一族" |
| 编译耦合 | 实现文件隔离 | 基类定义必须可见（头文件膨胀） |
| 循环约束 | —— | `Self` 不能是虚基、错误信息古老 |

结论同本书 3.3：**多态需求真实存在（异构、插件、运行期选型）就付虚的钱；单态热点
（每种类型分别走一遍的循环）用模板/CRTP 特化**。这正是 25 年后 "type erasure vs templates"
辩论的原型。

## 相邻概念对比

- **vs 函数指针表**（手写 vtable）：本书 3.1 演示过两者等价——vtable 本来就是带隐藏 load 的函数指针数组；收益在编译器自动维护。
- **vs `std::function`**：类型擦除 = 堆/小缓冲 + 间接调用 + 不可内联，成本结构同虚函数但常数更大（[../C++标准库/06-函数对象与Lambda.md](../C++标准库/06-函数对象与Lambda.md)）。
- **vs 重载（静态多态）**：零成本但要求编译期已知类型——见 [07 章](07-STL容器与函数对象.md)函数对象一节。

## 最新演进与工业实践

- **去虚化与 LTO 是制度性缓解**（✅ 编译器事实）：GCC/Clang 的 `-fdevirtualize`、`-fprofile-speculative-devirtualization`（PGO 提供单态证据后"赌"一个目标并保留回退）、`final`/`override` 提示、匿名命名空间内部链接类型——现代工具链把"虚=必间接"弱化为"虚=默认间接，可证则直接"。⚠️ 具体开关默认状态随版本变化，未逐项实测。
- **PGO 的现实意义**：生产中大量虚点实际单态（例如 IO 层 Reader 抽象），profile 引导的推测去虚化常常吃掉了当年"改用 CRTP 重写"的收益；改写的编译期成本（模板扩散全 TU）反而更贵。
- **间接分支预测硬件演化**：ITTAGE/ITTARO 类历史基预测器（现代 x86/Arm 服务器核 ⚠️ 具体核微架构未核实）让"规律轮转"的虚调用 mispredict 大幅下降——本实验 7× 差距在强预测器 + 真实工作负载上通常更小；乱序目标仍贵。
- **游戏引擎/ECS 语境**：虚函数缓存不友好（指针追逐 + 冷 vtable）是 data-oriented design 兴起动机之一；`std::polymorphic_allocator`、`std::type_index` 分派表等是当代折中 ⚠️ 与本书无直接承继关系，仅语境补充。
- **结论**：第 3 章的**排序结论今天仍然成立**（热点单态循环不该走虚）；但"CRTP 是默认答案"过头了——先 PGO/去虚化，再考虑模板化，最后才做侵入式改造。

## 机制补充：vtable 的物理样子

```text
对象内存（单继承，Itanium/MSVC x64 大体一致）:
+--------+     +-----------------------------+
| vptr -----------> vtable (每类一张，只读段)  |
+--------+     | [0] offset_to_top / 元数据    |
| 成员... |     | [1] &~Derived::~Derived()    | ← 0x08
+--------+     | [2] &Derived::op             | ← 0x10  ← call *0x10(%rax) 打这里
                +-----------------------------+
```

- 虚**析构**几乎总是第一个被"顺路买下"的虚函数——一旦类有虚函数，`delete via Base*` 才正确，
  而虚析构本身又把每个派生类拉进析构链（回扣 [01 章](01-跟踪实例与构造析构的代价.md)的析构次序）；
  这就是 3.1 "虚函数的构造"标题的双关：构造虚函数表与（虚）构造函数的纠缠。
- 多重继承下还要经 **thunk**（调整 `this` 的跳板）二次跳转——成本更高，机制详见
  [../深度探索C++对象模型/04-Function语意学.md](../深度探索C++对象模型/04-Function语意学.md)。

## 常见误区与自查

- **误区 1："虚函数总是慢一个数量级"**——本实测单态场景只有 ~4.4×（且大头是内联缺失的连锁反应），
  对象操作本身略大的方法（μs 级）虚调用税可忽略。**先量再改**。
- **误区 2："CRTP 一定比虚快所以全用 CRTP"**——CRTP 把类型烧进模板参数：容器异构性、插件加载、
  ABI 稳定性全丢；且基类实现进头文件，编译时间付账。
- **误区 3："构造函数里调虚函数多态会生效"**——不会（vptr 时序），且这是语意缺陷不是性能特性；
  想要"构造期行为"用工厂函数两段式。
- **自查**：profile 里出现高占比 `call *` / io_commit 类间接调用热点 → 先看能否 PGO 去虚化，
  再看循环是否可单态特化（把 `for(Base*) ` 改成模板 `for<T*>`），最后才是重构类图。
