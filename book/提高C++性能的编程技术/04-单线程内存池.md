# 04 · 单线程内存池：从 new() 到自由链表（原书第 6 章）

> 覆盖：6.1 版本0（全局 new/delete）、6.2 版本1（专用 rational 内存管理器）、6.3 版本2
> （固定大小对象的内存池）、6.4 版本3（单线程可变大小内存管理器）、6.5 要点。
> 大纲版见 [../提高C++性能的编程技术.md](../提高C++性能的编程技术.md)；总览见 [00-总览与阅读地图.md](00-总览与阅读地图.md)。

## 核心概念速览（中英对照）

- **内存池** — Memory Pool：一次性向系统预留大块，之后按对象粒度自给自足的分配器。
- **版本演进法** — Versioned Design：本书的教学骨架——同一问题从版本 0 一路改造到版本 5（第 7 章），每步只换一个权衡维度。
- **专用管理器** — Class-Specific Allocator：`operator new/delete` 类级重载，把某类的分配引到自家池（版本1）。
- **固定大小池** — Fixed-Size Pool：只服务单一尺寸的分配请求，块之间无需搜索/切分（版本2）。
- **自由链表** — Free List：空闲块用链表串起来的零开销"空闲表"；LIFO 取还自带缓存亲和。
- **位图** — Bitmap：版本2 管理块归属的紧凑标记法。
- **可变大小管理器** — Variable-Size Allocator：first-fit / best-fit / quick-fit（分级）：一般尺寸需求的池化（版本3）。
- **内部碎片 / 外部碎片** — Internal / External Fragmentation：请求被向上取整到块粒度的浪费 vs 空闲空洞凑不出连续大块。
- **释放即归还** — Deallocation-not-return：`delete` 只还给池、不还 OS——"内存没被回收"的观感与 RSS 上涨是池的天性。

## 动机：new 到底贵在哪（6.1，版本 0）

`new Rational` 的机器路径：**查空闲链/分箱 → 加锁（多线程运行时）→ 切块/写元数据头 →
（可能）brk/mmap 向 OS 补货 → 返回**；`delete` 反向再做一次，附带合并相邻空洞。
glibc 的 ptmalloc 每个 chunk 前置 8–16B 元数据、bins 操作含指针追逐；Windows 的 heap 亦有
free-list + lookaside。抽象成一句话：**通用分配器为"任何尺寸、任何生命周期"买单，
而服务器程序 90% 的分配是"同尺寸、短生命周期"**——这正是池化的套利空间。

已实测 g++ 15.2 -O2（00 总表 #4；MinGW 运行时默认分配器，32B 节点，100 万×20 轮，
分配后立即逆序全释放）：

| 路径 | 耗时 | 倍数 |
| --- | --- | --- |
| `new Node` / `delete` | 995.7 ms | 13.0× |
| 自由链表池（一次 reserve 1M 块） | 76.4 ms | 1× |

约 13 倍（≈46 ns vs 3.5 ns/次，含链表组装写入）。注意诚实口径：这测的是"本机的通用分配器
够不够快"，Linux glibc tcache、jemalloc、mimalloc 会显著缩小差距 ⚠️ 未在本机对照（Windows 无 glibc）。

## 机制：版本 1→3 的三连跳（6.2–6.4）

**版本 1（类专用）**：给 Rational 重载 `operator new/delete`，内部转发给一个静态池对象。
关键设计：`new Rational` 语法一字不改，分配策略换引擎——C++ 少有的"无侵入换实现"钩子。
代价：每个想要池的类都要复制粘贴这套（模板化后解决，即 `MAllocator<T>` 一族）。

**版本 2（固定大小池）**：核心数据结构只有两根指针：

```cpp
// 🔧 教学示意：版本2 的心脏（原书 6.3 的极简重写）
union Block { Block* next; char payload[32]; };  // 空闲时前 8B 就是链表指针——零元数据
class FixedPool {
    Block* free_ = nullptr;
public:
    void* alloc() { if (!free_) refill(); Block* b = free_; free_ = b->next; return b; }
    void dealloc(void* p) { auto b = (Block*)p; b->next = free_; free_ = b; }
    void refill();  // 一次 malloc(sizeof(Block)*N) 切成 N 块串链——摊薄系统调用
};
```

要点：O(1) 分配/释放、无块头（用 payload 前缀存 next）、块等尺寸 → **无碎片可言**；
LIFO 归还让刚释放的块最热（缓存友好）。这就是今天所有 slab/small-object 路径的原型。

**版本 3（可变大小）**：块尺寸不一后出现三件套难题——搜索策略（first-fit 快而碎、best-fit
省而慢、quick-fit 按尺寸分级）、切分与回收合并、以及位图/块头管理。本书用"请求尺寸直方图"
驱动选型：真实负载里尺寸分布高度集中时，可变大小池退化为"少数几个固定池"——**这判断
25 年后仍是分配器设计主流**（见演进节）。

## 权衡：池的天性账单

| 维度 | 池化的收益 | 池化的税负 |
| --- | --- | --- |
| 速度 | 13×（本实测）| 预 reserve 的启动延迟 |
| 内存 | 无块头、粒度精确 | 释放不还 OS：RSS 单调爬、多池各占一块"最小水位" |
| 碎片 | 固定池无碎片 | 可变池策略不当反而制造外部碎片 |
| 通用性 | 尺寸/生命周期均匀时极赚 | 对象谱系复杂时退化成"慢版 malloc"（比通用分配器少做全局调剂）|
| 调试 | —— | double-free/越界写会撕烂自由链，崩溃点远离案发现场 |

与 [01 章](01-跟踪实例与构造析构的代价.md)呼应的诚实提醒：版本 2 之后"new 变快了"，
于是程序员**更敢造临时对象**——分配降价会诱导用量上升，本书第 12 章引用计数一章会再撞见这个循环。

## 相邻概念对比

- **vs 栈分配/SCR（编译期存储）**：池管堆，栈连"分配"这步都免了（挪 RSP）；能活过表达式生命周期的才轮到池。`std::pmr::monotonic_buffer_resource` 是"只进不还"的极端池，适合请求级 arena。
- **vs [05 章](05-多线程内存池与锁定策略.md)多线程池**：单线程版的自由链在并发下立刻破产——两条路线（加锁 vs 每线程缓存）见 05。
- **vs [../STL源码剖析/02-空间配置器.md](../STL源码剖析/02-空间配置器.md)**：SGI 两级配置器=本书版本 2+3 的工业完成态（<16B 走 16 个 free list 分级，大者直接 malloc），侯捷逐行源码版。
- **vs GC**：池消灭分配成本，GC 消灭释放义务；1999 年 C++ 圈二选一辩论，今天 arena+RAII 常被证明是第三条路。

## 最新演进与工业实践

- **自由链表池的后裔遍地**（✅ 项目事实）：jemalloc 的 tcache+small bins、mimalloc 的 small
  free list（"mimalloc: Free List Sharding in Action"，Leijnse et al., APLS 2019，✅ DOI
  [10.1007/978-3-030-34175-6_13](https://doi.org/10.1007/978-3-030-34175-6_13)，实测 Crossref 可达）、
  Linux 内核 SLUB（名字就是 slab+自由链）、abseil 的 `absl::low_level_alloc`（供哈希容器整块
  生长的小对象滑阶分配器）——都是版本 2 的族谱直系。
- **`std::pmr`（C++17）**：标准委员会把"版本 1 的思路"制度化——`polymorphic_allocator` +
  memory_resource 层次，容器不改用法换分配策略；比类级 `operator new` 重载干净（后者会随
  全局 `new` 劫持传染，社区长期争议其作为通用手段的适配性，见 P0201 等提案讨论 ⚠️ 编号未逐一实测）。
- **请求级 arena 成为服务器主流**：网络/查询框架（Seastar、WASM 运行时、各类 RPC 框架 ⚠️ 泛称）
  按"一请求一 arena，结束整体 reset"回收——正是本书"释放不还 OS"缺点的正解：**生命周期对齐的
  群体不需要个体释放**。
- **Ditto（自适应语义数据结构，⚠️ 论文 TOOLS 2002，Crossref 未核到 DOI，仅标题年份）/ tinyalloc
  （GitHub rErrMsg/tinyalloc，非论文）**等学术池继续验证同一命题：知道对象寿命分布就能赢通用分配器。
- **结论**：第 6 章**仍部分成立但语境收窄**——直接手写类专用 `operator new` 的场合今天大多是
  反模式（先换 mimalloc/jemalloc、先 pmr::arena、先 profile）；而固定大小自由链+尺寸分级这套
  **机制知识**是读懂一切现代分配器的入场券，这部分教学价值不降反升。

## 常见误区与自查

- **误区 1："池化 = 释放变快了所以内存会降"**——正相反：池化后 RSS 只升不降（块留在自由链，
  不还 OS）。批处理长跑任务里"内存缓慢爬升到平台期"是池的天性，不是泄漏；要会区分
  （平台期=正常，线性爬升=真泄漏或链上对象失控）。
- **误区 2："固定大小池永远优于 malloc"**——尺寸不匹配（对象谱系分散）时你得到的是
  "多个半空池各占水位"，比通用分配器的全局调剂更碎更费。书中"先画请求直方图"的
  流程就是防这个坑：**数据驱动选池，而不是信仰驱动**。
- **误区 3："自由链表是过时教学代码"**——它是读懂 jemalloc/mimalloc 源码的前置词汇；
  区别只在它们把"一条链"切成"每线程×每尺寸档"的网格并处理跨线程归还。
- **自查**：heap profile（01 章手法的现代版）显示分配函数 self-time 占比 >5%？分配尺寸是否
  高度集中？对象是否同批生同批死（→ arena 直接整体 reset，比池更省）？三问定路线。
- **延伸思考（原书 6.5 要点复述向）**：把版本 0→3 的演进重推一遍——每一步只回答一个问题：
  谁付钱（元数据）、付多少（指令数）、省下的钱从哪来（摊薄+布局）。这套"版本演进法"
  本身就是应对任何性能课题的工作模板。
