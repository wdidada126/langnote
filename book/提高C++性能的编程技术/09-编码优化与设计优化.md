## 核心概念速览（中英对照）

- **编码优化** — Coding Optimization：不改架构、在写代码层面省成本的手法集合（13 章十条）。
- **设计优化** — Design Optimization：在类图/接口/数据结构定稿前就避免成本的产生（14 章）——"最快的代码是不存在的代码"。
- **数据缓存** — Data Caching（13.1）：把重复计算/查询的结果存下来复用；与 CPU 缓存（13.7/16 章）一词双义，本书特意先后用之。
- **预先计算** — Precomputation：启动期算好表，运行期只查表（三角函数表、转换矩阵、合法状态集）。
- **降低灵活性** — Reducing Flexibility：运行期可配的（表大小、协议版本号）改成编译期常量，换来越层优化空间。
- **80-20 法则** — 80-20 Rule：八成时间在两成代码；先优化热路径，冷路径保持通用可读。
- **延迟计算** — Lazy/Delayed Computation：没用到就不算（13.5 函数级、14.4 对象级，接 2.3 缓式构造）。
- **无用计算** — Unnecessary Computation：每循环都做的不变量计算搬到循环外；跨语句冗余的肉眼版 CSE。
- **系统调用合并** — Batching Library/System Calls（13.9）：一次大调用胜过十次小调用——内核交叉税（16.10）的编码层应对。
- **失效代码** — Dead Code（14.7）：没人调用的虚影分支；留着=持续缴维护税与体积税。
- **getpeername() 案例** — 书中 14.5 招牌故事：一个"显然需要"的系统调用，因为设计时问了一句"这数据从哪来"，整层删除——设计优化的原型寓言。

## 动机：前 12 章数完微观税，13–14 章给出"少欠债"的两种时机

13 章是**手边清单**：拿到一段慢代码，逐条过——热路径在哪（profile 说话，13.4）、
有没有每圈重算的不变量（13.6）、有没有可以用表换的重复计算（13.2）、
有没有把"配置"当"运行时决定"（13.3）、有没有链式小系统调用（13.9）。
14 章把时钟拨回**画类图之前**：书中反复出现的论证是——编码技巧救不了错误的设计，
`getpeername()` 寓言里若当初选择"连接对象自己缓存对端地址"的设计，
十行编码优化全都不需要存在。**设计决策是十倍杠杆，编码优化是一倍杠杆**，这个排序是两章的全部要旨。

## 机制：每条技巧背后的成本模型

| 技巧（节号） | 省的是什么 | 机制 | 代价 |
| --- | --- | --- | --- |
| 数据缓存 13.1/14.2 | 重复的计算/IO | 空间换时间；失效协议是关键 | 一致性 bug 温床；内存占用 |
| 预先计算 13.2 | 运行期算术 | 复杂度搬到启动期 | 启动延迟、表本身的缓存足迹 |
| 降低灵活性 13.3 | 分支与间接 | 常量使编译器折叠一切下游 | 可维护性；"将来要配置"风险 |
| 80-20 13.4 | 无效努力 | profile 定位热 20% | 需要度量基础设施（回扣 01 章） |
| 延迟计算 13.5/14.4 | 未用值的全套构造 | 把成本挂到首次使用 | 空态分支；线程安全（见 01 章缓式构造） |
| 无用/失效计算 13.6/14.6/14.7 | 根本不需要的功 | 删除与外提 | ——（纯收益，只要行为等价） |
| 库调用批处理 13.9 | 用户/内核往返 | 摊薄陷入成本与上下文切换 | 延迟上升（攒批 vs 及时） |
| 编译器优化 13.10 | —— | 信任 `-O2`，别与优化器搏斗 | 需理解其能力边界（03/06 章实测的教训） |

两章的方法论骨架是同一句话的两次采样：**先问"这功该不该做"（14），再问"这功怎么做便宜"（13）**。

后面的所有技巧都是在给错误结构打补丁。

## 权衡：缓存一致性与灵活性曲线

13.1 的数据缓存与 14.2 的设计级缓存是本章最重的权衡体：**缓存引入"副本"，副本引入
"何时失效"**。书中给的经验判据：写少读多 + 计算贵 + 失效可静态确定 → 缓存；三缺一 → 慎。
今天读来更锋利——分布式缓存、memoization、CDN 的 bug 谱系与这条判据一一对应。
13.3 降低灵活性则与当代"配置驱动一切"的文化相抵牾：本书立场是**灵活性要有价签**——
每次"运行期可配"都要回答"谁在改、多久改一次、为 TA 付的常数税值不值"；多数答案是不值
（模板参数/`constexpr`/LTO 时代尤其如此，见 [06 章](06-内联三讲：基础·性能·技巧.md)演进节）。

## 相邻概念对比

- **13 vs 14 章**：同一目录条目（缓存/延迟/无用计算在 13、14 各出现一次）不是重复——13 在函数内动手，14 在类图前动手；把 13 章清单背熟而没读过 14 章的人，会成为"高效地做错事"的典范。
- **预先计算 vs 延迟计算**：把成本推向启动 vs 推向首次使用——两者的取舍变量相同：使用概率与概率分布。都算不清 → 都不做，用 profile 先回答（01 章）。
- **降低灵活性 vs 模板化**：1999 年的"编译期常量"要靠宏与 #ifdef；今天叫 `template`/`constexpr`/`if consteval`，且获得类型检查——方向复活，工具换代。
- **数据缓存 vs [08 章](08-引用计数.md)引用计数**：都是"共享副本 + 失效协议"问题的特例；计数处理"何时销毁"，缓存处理"何时重算"。

## 最新演进与工业实践

- **profile 工具链是本章的当代主角**：perf 生态（Brendan Gregg 的站点与《Systems Performance》第 2 版 2020 是该领域事实教材 ⚠️ 本次未连通核验页面）、Intel VTune（前身即书中 Hotspots 一脉）、火焰图（FlameGraph，广泛使用的项目级工具）把 13.4 的"找那 20%"从手工计时变成一行命令。
- **memoization 制度化**：`std::memoized` ❌ 不存在（截至 C++26 未入标准 ⚠️ 以 wg21 文档为准）；工业界用 folly `ConcurrentHashMap` 缓存层、计算图框架的重用机制承接 13.1。
- **13.9 的当代放大版**：io_uring/DPDK/RDMA 把"批处理系统调用"推到内核接口层——当年"合并 write"的技巧如今是一种系统架构（✅ 通行事实）；"减少内核交叉"至今是 eBPF 之外的性能铁律。
- **13.10 的边界转移**：现代编译器能自动做循环不变量外提（13.6 的主体）；自动记忆化至今未进标准（`std::memoized` ❌ 不存在，⚠️ 以 wg21/C++26 现状为准），大表缓存决策仍是框架/应用层职责——**手工 13 章清单里"编译器已代劳"的比例逐版上升**；仍属人力的只剩 13.3（给编译器喂常量）与 13.9/14.5（减少外部世界交互）——恰是 25 年后仍然成立的两个硬核。
- **失效代码（14.7）的工程化**：`-ffunction-sections` + 链接器 GC、覆盖率引导的测试删除、clang-tidy deadcode 检查——当年的"敢删"美德有了量化工具。
- **结论**：两章**排序律（设计>编码）与 getpeername() 寓言永生**；13 章十条里，约一半已并入编译器的义务清单，剩下的一半（缓存一致性直觉、批量化、砍配置灵活性）仍是人肉决策——与 1999 年唯一的区别是 profile 工具让它们执行起来便宜一百倍。

## 代码标本：三分钟过一遍 13 章清单

```cpp
// 🔧 13.6 无用计算：每圈重算循环不变量
double scale_all(double* v, int n, const Params& p) {
    for (int i = 0; i < n; ++i) v[i] *= std::pow(p.base, p.exp) * p.k;   // pow 每圈一次
    // 修法：k = pow(p.base,p.exp)*p.k 外提——现代 -O2 若能证明 pow 纯/无副作用会自己做，
    //       但 pow 走 libm（可能置 errno/非内联纯）时常常提不出来：这条 1999 年手艺仍活。
}
// 🔧 13.2 预先计算：运行期逐元素算 → 启动期建表
// 🔧 13.9 批处理：for (msg) ::send(fd,msg)  →  writev/io_uring 一次多发
// 🔧 14.7 失效代码：profile+覆盖率指出 0 命中的配置分支 → 连配置项一起删
```

四段分别是清单四条的"指读版"；共同前提只有一个：**先有 profile 告诉你哪圈值得动手**（13.4）。
反过来，四段也各自埋着债务：外提改变浮点结合序（严格 IEEE 下合法，跨 fast-math 要再核）、
建表有冷启动、批处理引入延迟、删代码不可逆——技巧从来不是免费午餐，是换一种付法。

## 常见误区与自查

- **误区 1："技巧清单=可以不开 profile 直接套"**——13 章十条全是"条件句"；无热区证据的
  预先计算/缓存是在给冷代码贴膜，还倒贴内存与维护。
- **误区 2："缓存加一层总比没有强"**——13.1/14.2 的失效协议才是本体：没有明确失效点的缓存
  = 潜伏的脏读 bug 库存。问自己：这份副本被谁、在什么事件下作废？答不出就不配缓存。
- **误区 3："设计优化是玄学"**——getpeername() 寓言的可操作版：对每个"取数据"调用问三连
  （谁产生？多久变？能推给我吗？），把拉模型改推模型/构造期注入——这是设计评审能执行的动作。
- **误区 4："13.10 说信任编译器，所以不用管代码写法"**——信任的前提是喂给优化器可证明的输入：
  `const` 引用、无别名指针（`__restrict` 语义意识）、可内联的小单元、编译期可见的常量。
  写法阻碍证明时，编译器也无能为力——"为优化器写代码"从未过时，只是对象从人换成了机器。
- **自查**：拿最近一次性能工单，判定它属于 13（代码层）还是 14（结构层）；若你发现修复
  最终落在"删掉一个需求/换一次数据流向"，恭喜，你做了 14 章的事。
