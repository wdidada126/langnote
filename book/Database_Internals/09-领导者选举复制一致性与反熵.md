## 核心概念速览（中英对照）

- **领导者选举** — Leader Election：在可能分区的群体里产生「唯一且被多数承认」的协调者；本质是共识的第一次出场。
- **选举经典四件套** — Bully / Next-In-Line / Invitation / Ring：蛮牛按最大 ID「宣战」（分区下选出多头 ⚠️ 反面教材）；顺位是主备名单接管；邀请让继任者存活兼作领导心跳；环形收成员最大者胜——四种「无共识的选举」，各在分区或成员维护上翻车。
- **CAP** — Consistency, Availability, Partition tolerance：分区发生时只能在「一致」与「可用」间二选一的直觉定理（Brewer 提出、Gilbert-Lynch 形式化）；本书强调「日常运维即分区，P 不可弃」。
- **收割与让渡** — Harvest and Yield：读写落在分区两侧时的可用比例账：hA+yB=1 ⇒ 两侧 harvest 之和可超 100%，交集才是强一致域。
- **线性一致** — Linearizability：每个操作看似在「调用与返回之间」的某一刻原子生效，且与实时序一致——单副本寄存器的幻觉。
- **顺序一致** — Sequential Consistency：存在一个保程序序的全局序即可，**不要求贴合实时墙钟**（买卖家手机例子是教科书经典）。
- **因果与会话** — Causal Consistency / Session Guarantees：因果一致只保因果链有序；会话保障（单调读/单调写/读己之写/前缀读）把一致性收缩到「单用户视角」的工程档位。
- **可调一致** — Tunable Consistency：R+W>N 类旋钮（Dynamo/Cassandra），让业务按操作挑读写副本数。
- **见证副本** — Witness Replica：只投票不存数据的成员（R=2/2/3 之 3）：把法定人数的存储成本降下来，不降延迟。
- **强最终一致 / CRDT** — Strong Eventual Consistency：收敛函数满足交换律+结合律+幂等 ⇒ 任意顺序应用终会一致，无需协调。
- **读修复** — Read Repair：读路径上发现副本分叉就顺手补齐；把反熵成本分摊给前台流量（热数据优先同步）。
- **提示移交** — Hinted Handoff：收件副本宕机时先托邻居代存，复活后补投——可用性换「邻居也可能丢」。
- **默克尔树** — Merkle Tree：自底向上哈希的树根当「状态指纹」，比对指纹可 O(log n) 下钻定位差异子树（Dynamo/BTC 双料明星）。
- **版本向量** — Version Vectors：每副本一维计数，向量比较=判定因果「谁见过谁」；位图版（Bitmap Version Vectors）以节点位图压缩。
- **部分视图 gossip** — Partial Views：每轮随机采样常数邻居，流行病式覆盖 O(log n) 轮收敛全网。

## 动机：为什么这三章必须连读

复制的全部难点是一个字：**序**。多副本要一致，先得对「操作顺序」有一致意见——
谁提序（领导，10 章）、序强到什么级别（一致性模型谱，11 章）、序错了/丢了怎么纠（反熵，12 章）。
作者刻意把「选举」放最前，因为后面 CAP/线性一致的所有讨论都默认「有个可信任的定序者或没有」。

## 机制：三章各挑一台戏

### 1. 选举四件套的失效模式（第 10 章）

```text
Bully   : 分区 → 两侧各选出"最大 ID" → 双主 writes 分叉（没有法定人数概念的代价）
Next-in-line: 依赖故障检测器"猜对"；检测器误判 = 无分区也双主
Invitation: 现领导即心跳源；领导失联=继任者也未获确认 → 保守降级
Ring    : 成员表本身要维护 → 递归问题：给环选举又要选举？
收敛结论: 安全的选举 ≡ 共识（第 11/14 章）；本章算法的价值是让你看清"为什么需要 Paxos"。
```

```text
N 副本，读 R 个、写 W 个：R+W>N ⇒ 读写集合必相交（可调一致的算术基础）
3/3/2: 强一致倾向(写要 2/3，挂 1 台仍可读写)；3/1/1: 快但分叉全靠反熵收拾。
```

### 2. 一致性模型谱：一条强度递减的梯子（第 11 章）

```text
严格一致(物理瞬时) ⊃ 线性一致(实时序) ⊃ 顺序一致(存在全局序) ⊃ 因果一致 ⊃ 最终一致
                        │                    │
                   读己之写靠会话层补丁   并发分支不保证
工程落点: 每往下一级，省的是「协调轮次/同步阻塞」，欠的是「异常故事」。
线性一致≠顺序一致的差价示例: 两进程并发读同一寄存器，线性一致禁止"各自看到对方的写都没发生"的循环故事。
```

**CAP 的使用说明（作者原话精神）**：别拿它当「三选二」的禅宗——分区是现实背景噪声，
真正的问题是按操作划分「这个写要不要全局立即可见」；harvest/yield 给出连续谱而非二值开关。

### 3. 反熵工具箱（第 12 章）

```text
读修复   : 前台顺带，热数据收敛快；冷数据永远没人读 → 永不修复
摘要读   : 只比对指纹不拖数据，带宽省、分叉后仍需二次拉取
提示移交 : 写路径容灾；hstore 有 TTL，超期未补投则数据真丢
Merkle   : 后台全量对比的最优解——但每次重写都要重算整棵子树，写多的库开销大
版本向量 : 因果账本；节点数增长时向量线性膨胀 → 位图版/稳定副本 ID 缓解
gossip   : 以上"消息怎么送到"的传输层：反熵、成员管理共用一套流行病协议
```

## 权衡

| 轴 | 强的一端 | 弱的一端 | 本书提醒 |
| --- | --- | --- | --- |
| 选举 | 共识派（安全、慢一拍） | 蛮牛/顺位派（快、分区下裸奔） | 没有故障检测配合的选举都是抽奖 |
| 一致性 | 线性一致：每操作一次跨副本协调 | 最终一致：读本地副本 | 按操作分档，别让一个全局开关背锅 |
| 反熵 | 全量 Merkle：确定无死角 | 读修复：零后台成本 | 冷数据死角 + 大表 Merkle 重算成本，两头都要预算 |
| CRDT | 免协调、可离线 | 语义受限（可合并才行） | 「无冲突」是设计出来的，不是天上掉的 |
| 反熵触发 | 定时全量（可预算） | 事件驱动（读修复省后台） | 冷数据死角与风暴期后台带宽，两头都要预算 |

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「CAP = CP 或 AP」 | 分区只强制分区期间的选择，且可按操作分档；平时一致可用兼得（"Use CAP carefully"） |
| 2 | 「最终一致 = 弱一致没保证」 | 强最终一致（CRDT）给出的是**确定性**收敛保证，弱的是「过程中读到旧值」 |
| 3 | 「R+W>N 就是线性一致」 | Dynamo 论文自己承认：读修复+提示移交的组合下并不成立；要线性一致还需额外的读阶段协调 ⚠️ 本书展开程度以原文为准 |
| 4 | 「Merkle 树反熵完美」 | 频繁重写 → 根到叶全重算；写多读少的巨型表上它比全量比对还贵 |
| 5 | 「选个领导很简单，随便实现」 | 第 10 章四个算法全在「分区+不完全失效」下翻车；安全选举只能长在共识上 |
| 6 | 「顺序一致=线性一致换词」 | 差在是否贴实时：SC 允许全局序偏离墙钟序，线性一致不允许 |
