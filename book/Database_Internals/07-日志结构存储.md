## 核心概念速览（中英对照）

- **LSM 树** — Log-Structured Merge-tree：写先进内存表并追加日志，满后成批沉入盘上有序文件，靠后台归并保持有序。
- **内存表** — Memtable：盘上文件的内存对应物，常用跳表实现；冻结后 flush 成第一个不可变文件。
- **排序字符串表** — Sorted String Table (SSTable)：键有序的不可变块文件（数据块+索引块+尾块），LSM 的盘上原子单位。
- **归并迭代** — Merge-Iteration：多路归并若干有序文件得到全局有序视图；点查则逐文件二分。
- **对账** — Reconciliation：归并中同一键多版本并存时，按「较新覆盖、墓碑生效」的规则定唯一真相。
- **压实/合并** — Compaction：后台把小文件归并成大/少文件的过程；size-tiered 与 leveled 两大流派。
- **墓碑** — Tombstone：删除与键范围清理的「负记录」，读要挡、compaction 才真删。
- **读放大** — Read Amplification：一次逻辑读触发的实际块读取次数；LSM 的账在「查几个文件」。
- **写放大** — Write Amplification：一条逻辑写引发的盘上字节写总量倍数；compaction 是主要债主。
- **空间放大** — Space Amplification：盘上字节数 / 逻辑数据量；旧版本与墓碑的未回收部分。
- **RUM 猜想** — RUM Conjecture：Read/Update/Memory 三角不可同时最优（注意：是 Memory 不是 Space——本仓库常流传的「读改写空间三角」是通俗版 ⚠️）。
- **布隆过滤器** — Bloom Filters：挡「键不存在」的概率结构，LSM 读路径的守门人；假阳性可来、假阴性绝无。
- **键值分离** — Key-Value Separation（WiscKey）：大 value 直写 blob 文件，SSTable 只留指针，compaction 不再搬值。
- **日志堆叠** — Log Stacking：引擎日志/WAL × 文件系统日志 × SSD 闪存转换层（FTL）三层「追加换耐久」互相套娃的浪费与干扰。

## 动机：B 树阵营还不清的两笔债

第 4/6 章的所有变体都在修补同一件事：**每次写至少触碰 O(log n) 个页**，且随机写对 HDD 是寻道、
对 SSD 会撞上 FTL 的「读-改-写整擦除块」。LSM 的解法釜底抽薪：**写路径只有一次顺序追加 + 一次内存插入，
所有随机性推迟到后台批量归并**。天下没有免费的午餐——债没有消失，只是换了科目：
读要多文件归并（读放大）、compaction 重复搬数据（写放大）、旧版本滞留（空间放大）。
本章的伟大之处在于把这三笔债**全部量化成可调节的参数**。

## 机制：一条写的完整生命周期

### 1. 结构与写/读/删

```text
写: WAL 顺序追加 → memtable(跳表)插入        [2 次操作，1 次顺序 IO]
读: 定位链: memtable → immutable → L0 各文件 → L1..Ln 逐层
        每站: 布隆挡"不存在" → 索引块二分 → 数据块解压比对
删: 写一条墓碑 ⟨key, DELETE, ts⟩，与更新同构
compaction: 选文件 → k 路归并 → 同键留最新、墓碑+无旧版则丢弃 → 落新文件 → 换清单
```

L0 特殊：**层内文件键区间可重叠**（flush 直接落 L0），所以 L0 要全数检查；L1 起层内不重叠、层容量 ×10。

### 2. 三放大与 leveled/size-tiered 的对账表

| 策略 | 写放大 | 读放大 | 空间放大 | 适用 |
| --- | --- | --- | --- | --- |
| 不分层（纯级联 compaction，LevelDB 原型） | 低 | 中 | 低 | 批量导入 |
| size-tiered（Cassandra 默认） | 最低（每字节平均搬常数 O(1) 次量级 ⚠️ 书中给近似界） | 高（同键散布多文件） | 高（归并前新旧并存 ~2×） | 写极重 |
| leveled（LevelDB/RocksDB 默认） | 高（典型 10–30×：每下一层重抄 ~10 倍） | 低（层内不重叠，每层最多 1 文件） | 低（层间键区间对齐） | 读写均衡 |
| FIFO/Tiered+TTL | — | — | 近 0 | 时间序列直接过期 |

**「leveled 写放大为什么是 10–30×」的算法**：1GB 数据每下沉一层都要与上一层 10% 重叠区重归并，
共 log₁₀(大小) 层 → 每字节平均被重写 ≈ 层数×(1+0.1+…) ≈ 10~30 遍。这是评估 SSD 寿命与后台 IO 预算的第一公式。

### 3. RUM 三角：优化提案的照妖镜

```text
        Read(放大)
          /      \
   Bloom/缓存/    \  多留层、少compaction
   块索引          \
 Update(写) -------- Memory(空间)
   调大层级比、      键值分离、提前回收
   攒批 flush
```

RUM（Read/Update/Memory，Dayan & Ravid 论文，书中引用）：任意两边改善必恶化第三边。
布隆过滤器降读放大但吃内存；键值分离降写放大但值 GC 与「读多一跳」是新的 M/R 债。
**评审任何引擎参数调优，先在三角上画出钱从哪挪到哪。**

### 4. 无序路线与并发深坑

- **Bitcask**：彻底放弃有序（哈希索引全内存 + 追加 + 活键 hint 定期重写）；换 O(1) 点读点写、范围查询归零，键集受内存限制。
- **WiscKey**：LSM 保留键序、value 挪 blob —— 大 value 负载写放大从 20× 降到 <2× ⚠️（数量为书中示例口径），代价是值 GC 与点读 +1 IO。
- **log stacking**：引擎 WAL 刷一次、fs journal 再刷一次、FTL 又搬一次——三层各自「为耐久而追加」，叠加即三倍写。
  解法谱：绕开 FS（直接块设备/裸盘）、**open-channel SSD 把 FTL 还给引擎**（LightKV 一脉）、LLAMA 用内存映射+页版本对账三层。

## 权衡

| 决策 | 倾向 LSM 的理由 | 倾向 B 树/COW 的理由 |
| --- | --- | --- |
| 写密集/高压缩比 | 顺序写吞吐、天然批量压缩 | — |
| 点查尾延迟 | — | B 树稳定 log 页读；LSM 遇 L0 堆积抖动 |
| 全表/范围扫描 | 层多时归并路数可控 | 叶链单遍；LSM 要堆归并堆 |
| 空间敏感 | — | LSM 版本/墓碑滞留 |
| 崩溃恢复 | WAL+重放 memtable 简单 | COW 免 WAL；原地派靠 ARIES |
| SSD 寿命 | FTL 视角：LSM 大块覆盖写更友好 | 小页随机写触发 FTL GC 风暴 |

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「LSM 写无限快」 | 写便宜≠系统便宜：compaction 抢 IO/CPU，风暴时点查 P99 反噬（第 5 章缓冲池排队） |
| 2 | 「墓碑很快被清」 | 墓碑必须盖过所有更老版本才能删，常要等到沉底 compaction；大删表后空间放大飙升 |
| 3 | 「布隆过滤器管一切读放大」 | 它只否「不存在」；存在但多版本并存仍需逐文件查 |
| 4 | 「RUM 是读-写-空间三角」 | 原论文 Memory 含内存与存储两个维度；口语版「写/读/空间」丢了内存轴 ⚠️ |
| 5 | 「value 越大 LSM 越赢」 | 大 value 不分离时写放大按 value 计——WiscKey 的动机正是纠正这个直觉 |
