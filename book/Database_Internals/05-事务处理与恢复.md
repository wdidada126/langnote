# 第 5 章 事务处理与恢复（Transaction Processing and Recovery）

> 覆盖原书第 5 章三大块：Buffer Management（Caching Semantics / Cache Eviction / Locking Pages in Cache /
> Page Replacement）、Recovery（Log Semantics / Operation Versus Data Log / Steal and Force Policies / ARIES）、
> Concurrency Control（Serializability / Transaction Isolation / Read and Write Anomalies / Isolation Levels /
> Optimistic / Multiversion / Pessimistic & Lock-Based Concurrency Control）。
> **本章是 Part I 的枢纽**：第 2–4 章造了「会做手术的树」，本章给它装上内存（缓冲池）、
> 保险丝（WAL/ARIES）与红绿灯（并发控制）。用户预期的「缓冲管理」「WAL」「MVCC」三站都在此章。

## 核心概念速览（中英对照）

- **缓冲池** — Buffer Pool：内存里按页缓存盘上数据的固定大池，是「页级工作集」的唯一宿主。
- **缓存语义** — Caching Semantics：全缓存/部分缓存/无缓存策略；数据库要的是「指定页优先在内存」，与 OS 页缓存的无差别对待相对。
- **淘汰与页面替换** — Cache Eviction / Page Replacement：LRU 家族（clock、LRU-K、ARC ⚠️ 书中点到为止）决定谁被逐出；扫描污染是头号敌人，解药是分段 LRU + 大扫描旁路（bypass/pass-through）。
- **页钉住** — Pinning a Page：页在被使用期间计数 +1，钉住者不还手淘汰器就不能换出它。
- **提前写日志** — Write-Ahead Logging (WAL)：页落盘之前，描述该修改的日志记录必须先持久化。
- **操作日志 vs 数据日志** — Operation Versus Data Log：记「做了什么操作」（逻辑，重放要算）vs 记「改前改后字节」（物理，重放即抄写）；折中是 redo-no-undo 之类的混合。
- **窃取与强制** — Steal / Non-Steal, Force / Non-Force：脏页可否在提交前落盘（steal）、提交时是否必须落盘（force）；两维四象限定出恢复协议强度。
- **检查点** — Checkpoint：把「重放起点」定期钉进日志，恢复时间与日志长度解耦。
- **ARIES** — ARIES：以 LSN 为主键、支持逻辑 undo（补偿记录）与历史表（dirty page table）的工业恢复算法。
- **可串行化** — Serializability：并发执行效果等价于某串行顺序；冲突可串行化（CSR）与 2PL 是其实现支柱。
- **隔离级别** — Transaction Isolation：SQL 标准（RU/RC/RR/序列化）以「允许哪些异常」定义，本书按异常谱系重讲。
- **写偏斜** — Write Skew：两事务读同一约束、各写不同侧而共同违约——RR 都挡不住（在快照实现上）的典型。
- **乐观并发控制** — OCC：读不挡、写时验证读写集冲突再提交；低冲突负载之王。
- **多版本并发控制** — MVCC：读旧版本快照、写新版本，读写不互斥；与 2PL 的核心分野是「用空间与 GC 换阻塞」。
- **两阶段锁** — Two-Phase Locking (2PL)：锁的获取与释放在时间上分两阶段；加锁即排队，冲突率一高吞吐悬崖。

## 机制精讲

### 1. 缓冲池：一个带锁的页工作集

```text
页描述符: { page_id, pin_count, lock(读写), dirty_lsn?, state }
淘汰器   : 双链表 LRU 拆成 young/old 两段，新页进 old 头，
           只有被再次命中的页才升 young —— 防「一次扫描杀光热页」
替换协议 : 挑中 victim 若 pin_count>0 跳过（并发下页可能正被改）;
           脏页换出前 → 交给 WAL 检查（见下）
```

作者特别点名**「页锁与闩（latch）之分」** ⚠️ 措辞：保护内存结构的是短期闩，
跨事务的锁归并发控制层——混用会死锁域扩散。OS 页缓存为什么不够：它没有「这张 B+ 树的根页请常驻」的表达力，
而缓冲池的 pin + 分段淘汰可以。15-445 Project #1（LRU-K + 旁路）是本章的实操版。

### 2. WAL：页可以乱序，日志必须有序

```text
写页协议（steal + 页级原子由第 3 章 checksum/双写兜底）:
  改内存页前: 日志记录 L=〈page,lsn,前像,后像〉 进日志缓冲
  页落盘前   : L 及其之前所有记录必须已 fsync   —— WAL 铁律
  提交       : commit 记录 fsync（可选组提交：攒 N 个事务一次 fsync）
恢复三趟（ARIES）:
  analysis: 从最后 checkpoint 扫日志，重建「谁脏了」
  redo    : 对所有脏页重放 ≥ 其 rec_lsn 的后像（redo 幂等）
  undo    : 对未提交事务逆序回滚（补偿记录使 undo 本身可崩溃恢复）
```

**组提交（group commit）**是本章对延迟工程最大的交付：fsync 是设备级串行点，
「一次 fsync 替一车事务买单」把 10μs 的单提交延迟换成 1ms 一批的均摊成本。
steal/no-force 的组合表背下来：

| | 提交时强制刷页 force | 不刷 non-force |
| --- | --- | --- |
| 允许脏页先落盘 steal | 正常（恢复要 redo） | 最强吞吐（ARIES 此档） |
| 禁止 no-steal | 可免 undo，但回滚要挡 | 少用 |

### 3. 并发控制：三族算法一张表

```text
读侧异常                   写侧异常
脏读 dirty read            丢失更新 lost update
不可重复读 non-repeatable  写偏斜 write skew
幻读 phantom               （读写交错的环 → 破坏可串行化）
```

- **2PL（悲观）**：读加 S 锁、写加 X 锁、按序排队。冲突率低时几乎免费；
  冲突率高时吞吐悬崖 + 死锁检测成本（等图/wound-wait）。锁粒度（页/行/键范围）是第 4 章页结构的直接下游。
- **OCC（乐观）**：执行期记录读写集，提交时验证「我的读是否被他人写」，失败重试。
  适合读多写少 + 短事务；长分析事务一碰就重跑，代价爆炸。
- **MVCC（多版本）**：每事务持一个快照点，读「对我可见的最新版本」，写生成新版本；
  **读者永不阻塞**，写冲突只在同版本竞争时发生。版本链/增量靠 GC 回收，空间换不阻塞。
  本书给 MVCC 的定位：可串行化（SSI 检测读写环）与高性能的交点——
  Postgres 的快照隔离、Cassandra LWT 外的常规路径都从此流出。

## 权衡

| 轴 | 一端 | 另一端 | 本书立场 |
| --- | --- | --- | --- |
| 日志 | 纯物理（重放快、体积大） | 纯逻辑（体积小、重放依赖上下文） | 混合：物理为主 + 逻辑补偿（B 树删除的 undo 即此） |
| 淘汰 | 命中率高（保留久） | 抗扫描污染（尽快放） | 分段 LRU 是工程默认 |
| 并发 | 2PL 冲突排队 | MVCC 版本空间 | 冲突率是旋钮：高并发写同键区 → MVCC 胜；长事务读 → 快照胜 |
| 提交延迟 | 每事务 fsync | 组提交攒批 | 攒批 = 用崩溃窗口换吞吐 |

## 相邻概念对比

- **B 树 vs LSM 的恢复**：LSM 提交只需追加 WAL + 写 memtable，天然 no-steal/no-force 弱一档（第 7 章）；本章的缓冲池脏页协议主要是原地更新阵营的负担。
- **MVCC vs 第 13 章 Percolator**：单机 MVCC（版本在 undo 段/版本链）与跨机 MVCC（时间戳做 TSO，锁塞进列）的映射关系，本目录 `10` 展开。
- **ARIES vs etcd/RocksDB 的「重放即恢复」**：共识阵营直接用日志重放替代 undo/redo 三趟——本章立理论，第 14 章（本目录 `11`）收编。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「WAL 保证页原子写」 | 不，WAL 保证「改前有日志」；页级撕裂要 checksum/双写补位（第 3 章） |
| 2 | 「MVCC 提供可串行化」 | 多数系统的 MVCC 默认快照隔离，写偏斜仍需 SSI/锁补刀 |
| 3 | 「缓冲池越大越好」 | 不配淘汰策略的大池只会把扫描污染放大；大小与策略同权重 |
| 4 | 「2PL 一定比 MVCC 慢」 | 低冲突时 2PL 近零开销（锁只是内存计数），MVCC 反而常驻 GC 成本 |

## 思考题

1. 给定 steal+no-force：写出「崩溃时存在已落盘脏页 + 其事务未提交」的恢复序列，说明为什么必须有 undo。
2. 双 11 场景：热点账户行更新，QPS 5 万。2PL、OCC（含重试）、MVCC 各给出预估吞吐与尾延迟来源。
3. 组提交攒 1ms 批：推导 fsync=1ms 设备上的最大提交吞吐与崩溃窗口，说明「客户端等待确认」语义是否被破坏。
