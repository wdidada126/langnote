> Optimizations / Wide Column Stores / Data Files and Index Files / Primary Index as an Indirection /
> Buffering, Immutability, and Ordering / Summary。
> 这一章是全书地图：作者先回答「数据库引擎由哪些层组成、每层在为哪个假设下注」，后面 6 章逐层兑现。

## 核心概念速览（中英对照）

- **数据库管理系统架构** — DBMS Architecture：从 WAL 到缓冲池、访问方法（索引）、事务管理、查询处理的分层，本书只深入前三层。
- **内存数据库 vs 磁盘数据库** — Memory- Versus Disk-Based DBMS：前者假设数据可驻留内存，索引/恢复设计围绕「重启后重建」，后者围绕「页的随机 IO」。
- **内存库的持久化** — Durability in Memory-Based Stores：用周期快照 + 增量 WAL（或 HDFS 式主日志+增量日志分层）在重启时重放恢复。
- **行式布局** — Row-Oriented Layout：一条记录的列连续存放，服务「取一整行」的 OLTP；顺序扫全列时浪费 IO。
- **列式布局** — Column-Oriented Layout：同一列的值聚在一起，压缩率与列扫描吞吐极高，但「拼回一行」需要按位置对齐。
- **PAX 布局** — Partitioning Across ⚠️：页内先按列分组、组内按行排列，行存与列存的页级折中（本书提及，作为两种布局的桥梁）。
- **宽列存储** — Wide Column Store：把「行」变成稀疏、列可动态增长的映射（Bigtable/Cassandra/HBase 谱系），本质仍是按行组织便于局部性。
- **数据文件** — Data File：记录的有序真相（primary key 序），所有派生结构都指向它。
- **索引文件** — Index File：secondary key → primary key 的映射，是「间接层」而非真相。
- **主索引作为间接层** — Primary Index as an Indirection：二级索引不存偏移量而存主键，更新一行只需改主索引路径，索引文件免动。
- **缓冲、不可变性、有序性** — Buffering, Immutability, and Ordering：页进了缓冲池才可改、落盘即不可变字节、写路径必须保序——第 5/7 章一切机制的地基。

## 动机：为什么要从「架构」讲起

单机引擎的每个经典难点都源于一个资源假设：磁盘随机 IO 比顺序 IO 贵几个数量级（第 2 章展开）、
内存比磁盘快但会丢（本章持久化一节）、CPU 与内存带宽的差距大于磁盘与内存的差距（第 6 章 cache-oblivious 呼应）。
作者的做法是把「假设」先摊开，再让读者看到：**B 树与 LSM 不是两种算法，而是两种假设组合的解**。

## 机制：三组对立面

### 1. 内存库怎么持久化（快照 + 日志重放）

```text
恢复 = 最近一次快照 checkpoint ⊕ 其后的所有增量日志
     HDFS 的做法：editlog(增量) 定期与 fsimage(快照) 合并 —— WAL 思想用在元数据节点上
```

内存库（如早期的 VoltDB、Redis）不需要缓冲池，但需要「重启后重建索引」的路径：
要么全量重放日志（慢启动），要么把索引也序列化进快照（大快照）。这是 ⚠️ 本书点名的工程两难。

### 2. 行存 vs 列存 vs 宽列（布局即访问模式的下注）

```text
行存: [id|name|age|addr] [id|name|age|addr] ...   取一行 1 次 IO；扫 age 列读 4 倍废数据
列存: [id id id ...][name name name ...]           扫 age 列恰好读必要字节；取一行拼 4 个文件
PAX : 页内 [所有行的id][所有行的name]...            页级局部性两全，页内仍是列组
宽列: 行 = map(列族 → map(列名 → 值, 时间戳))       列可稀疏、可动态加，仍是按行聚
```

列存的红利在**压缩**（同列同类型相邻，delta/RLE 直接可吃）与 **SIMD**（同类型连续可向量比较）——
这两点本书只点名，深讲转介给 [../数据库系统概念6/10-存储和文件结构.md](../数据库系统概念6/10-存储和文件结构.md)。

### 3. 数据文件与索引文件：间接层的位置

```text
错误做法: 二级索引 → 记录物理偏移        （更新导致行挪位 ⇒ 所有索引跟着抖动）
正确做法: 二级索引 → 主键 → 数据文件     （行挪位只改主索引一条路径）
```

「索引是间接层」这一句话，解释了为什么第 2 章花整章讲 B 树的键布局——**主索引的效率决定一切派生索引的代价**。

```text
插入一行 ⟨id=42, name=..., age=...⟩ 的完整写账（本章节视角）:
  1. 数据文件: 按 id 序插入(可能引发页分裂 → 第 2/4 章)
  2. 二级索引 age: ⟨age → id=42⟩ 追加(第 2 章同款结构，键更小扇出更大)
  3. WAL 日志: 上述两者的改前/改后记录(第 5 章接管)
派生视角(DDIA 同款): 索引 = 数据文件之上、按键重新物化的「视图」。
```

## 权衡

| 决策点 | 选项 A | 选项 B | 决定因素 |
| --- | --- | --- | --- |
| 驻留假设 | 磁盘分页（InnoDB） | 全内存（Rockset 类/Redis） | 数据量/成本 vs 重启恢复时间 |
| 布局 | 行存 | 列存（或 PAX/宽列） | 点读整行 vs 分析扫列；写放大方向相反 |
| 真相 | 数据文件为真相 | 日志为真相（LSM/事件溯源） | 原地更新 vs 追加+整理，第 7 章分野 |
| 索引 | 存偏移 | 存主键 | 更新代价 vs 多一跳查找 |

## 相邻概念对比

- **本章 vs DDIA 第 2/3 章**：DDIA 从「日志是真相」抽象出事件溯源，本书直接落到页与文件的物理层；先读 DDIA 再读本章会有「对上号」的快感。
- **本章 vs 15-445 导论讲**：Pavlo 的 DBMS 分层图与本书几乎一致，但本书把「访问方法」拆成 B 树系/LSM 系两条平行线讲到底。
- **宽列 vs 列存**：名字都带「列」，方向相反——宽列是「行更肥」（一行内成百上千列，按行聚存），列存是「列更瘦」（跨行同列聚存），别混。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「内存数据库不需要日志」 | 只是不需要缓冲池；持久化仍靠快照+日志，否则重启裸奔 |
| 2 | 「二级索引应该指向行地址」 | 指向主键，让数据文件消化挪位；这是本章间接层结论的直接推论 |
| 3 | 「列存一定比行存先进」 | 列存牺牲点读与更新（写要拆到 N 列），OLTP 主战场仍是行存 |
