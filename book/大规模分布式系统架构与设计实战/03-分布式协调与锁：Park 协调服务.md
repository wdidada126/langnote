## 核心精讲

（以下为教学性梳理，伪代码/示意均**教学示意，不参与构建**。）

### 3.1 协调服务的本质难点

协调服务不是「存个地址那么简单」，它必须回答三个硬问题：

```text
# 教学示意，不参与构建：协调服务必须保证的三件事
1. 选主不脑裂：两个节点不能同时认为自己是大主
   -> 需要共识算法（ZAB / Raft）或可靠的锁
2. 临时节点随会话失效：进程挂了，它注册的地址/锁必须自动释放
   -> 需要会话 + 租约（lease）机制
3. 变更可观测：配置/成员变化要能通知到关心方
   -> 需要 Watch / 事件推送，且需保证不丢事件
```

> 这三件事里任意一件做错，都会导致**脑裂、锁丢失、雪崩**。ZooKeeper 用 ZAB 共识 +
> 临时节点 + Watch 解决，并有十余年生产验证；Park 是否等价实现，书中未给可复核证据。

### 3.4 分布式锁的最小正确实现（教学示意，对照 Park 应有的能力）

```text
# 教学示意，不参与构建：一把不会丢、不脑裂的分布式锁该长什么样
acquire_lock:
    在协调服务创建「临时顺序节点」/locks/req-<seq>
    取 /locks 下所有子节点，若自己是最小序号 -> 获锁
    否则 Watch 比自己小一号的节点，等它释放
release_lock:
    删除自己的临时节点（会话断开也会由协调服务自动删除）
防脑裂关键:
    锁必须带「租约 / fencing token」：
    即使旧持有者因 GC 暂停后误以为仍持锁，新持有者的 token 更大，
    存储层用 token 拒绝旧请求（fencing）
```

- 上述「fencing token」机制（Google Chubby 提出）是分布式锁的**标配**；
  笔记原文与本书都未明确 fourinone 的锁是否具备 fencing，**未能核实原文，存疑**。

## 版本演进

- 本书无第二版记录。
- **2013 年口径**：ZooKeeper 已成熟（2010 论文），但「自己写个轻量协调」仍有吸引力。
- **2026 年视角**：协调服务的事实标准是 **ZooKeeper（ZAB）** 与 **etcd（Raft，52310★）**；
  二者都有共识算法保证、有 Jepsen 类测试、有庞大生产部署。自研协调服务基本退出主流。
- 🔧 **必须补入**：Raft（2014）让「自己实现一个正确协调服务」变得有章可循，但 fourinone
  成书时未采用；今天再评估 Park，应直接对照 etcd/ZK 的共识保证，而非把它当黑盒。

## 近年研究与工业界开源实践（2015–2026）

- **ZooKeeper** `apache/zookeeper` **12811★**（2026-09-27 实测）：仍是大量存量系统的协调底座。
- **etcd** `etcd-io/etcd` **52310★**（与存储系统书同口径实测）：Raft 实现，K8s 元数据存储，
  是「轻量 + 共识正确」的标杆，恰好反衬 Park「轻量但正确性未证」。
- **fourinone** `fourinone/fourinone` **85★**：社区与验证规模远不足以支撑协调服务的信任门槛。
- **一致性测试工业化**：Jepsen（2013 起）把「协调服务是否真安全」变成可证伪测试；
  这是本书完全没有的视角——Park 是否经得起此类测试，未知。
