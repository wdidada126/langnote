# 第 1 章　概述与「四合一」定位

> 原书开篇交代 fourinone 的设计动机：用**一个** Java 小框架同时覆盖「分布式协调 /
> 并行计算 / 分布式文件 / 分布式缓存」四大需求，号称「四合一（four in one）」，
> 对标 Hadoop + ZooKeeper + memcached + MQ 的组合。
> 本章是全书立论的根，但也正是**争议最集中**的地方：一个 100 多 K、不依赖第三方 jar
> 的框架，真能替代四个成熟生态吗？

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 fourinone 是什么 | Java 框架，号称集成 Hadoop/ZK/memcache/mq 于一身 | 本质是「一个框架重做四件事」，不是「四个系统」 |
| 1.2 「四合一」动机 | 降低分布式入门门槛、少依赖、轻量 | 动机可理解，但代价是每项都做不深 |
| 1.3 不依赖第三方 jar 的实现路径 | 用 JDK 自带 RMI（通讯）+ JDK6 HttpServer（文件） | 真「零三方依赖」靠的是 JDK 内置组件，而非自研轮子 |
| 1.4 定位争议 | 自称「四不像超级神器」 | 🔧 与 85★ 的真实生态活跃度严重不符，属过度自夸 |

## 核心精讲

（以下为教学性梳理，伪代码/示意均**教学示意，不参与构建**。）

### 1.1 「四合一」到底合了哪四样

| fourinone 自认的能力 | 它想取代的成熟系统 | 真实生态 star（2026-09-27 实测） |
| --- | --- | --- |
| 分布式协调 / 注册 / 锁（Park） | ZooKeeper | `apache/zookeeper` 12811★ |
| 并行计算（Worker/DomainNode） | Hadoop MapReduce | `apache/hadoop` 15670★ |
| 分布式文件（FttpAdapter/fttp） | HDFS / GFS | Hadoop 含 HDFS 同 15670★ |
| 分布式缓存（基于 Park 的 KV） | memcached / Redis | `memcached/memcached` 14285★、`redis/redis` 76498★ |
| （书中亦含消息能力） | Kafka / ActiveMQ | `apache/kafka` 33854★ |

> 这张表是全书的「照妖镜」：fourinone 想用一个框架覆盖的所有对象，
> 每一个的真实生态活跃度都**数量级**高于 fourinone 自己的 85★。
> 「四合一」在商业宣传上是「少依赖」，在工程现实上是「每个都弱于专业系统」。

### 1.3 「不依赖任何第三方 jar」的实现真相

仓库笔记原文点破：fourinone 宣称 100 多 K、不依赖第三方 jar，但它的通讯与文件传输
**并没有真的从零造轮子**，而是借用了 JDK 内置能力：

```text
# 教学示意，不参与构建：fourinone 的"零三方依赖"实际构成
通讯层:  JDK 自带的 RMI（Remote Method Invocation）
         -> RMI 在 JDK 内部仍是 BIO（one request per one thread）
         -> 序列化用 JDK 原生序列化（性能/体积均不占优）
文件层:  JDK6 以后自带的 com.sun.net.httpserver.HttpServer
         -> 通过 HTTP 上传/下载文件，即 fttp（fourinone 的 "ftp over http"）
缓存层:  java.util.LinkedHashMap（用 removeEldestEntry 做 LRU）
         -> 通过 RMI 把缓存操作暴露为远程调用
```

- **「不依赖第三方 jar」≠「不依赖底层实现」**：RMI 与 HttpServer 都是 JDK 的一部分，
  所以打包体积小、无外部 jar；但这也意味着它继承了 JDK 这些组件的**性能天花板**（BIO、原生序列化）。
- 与之对比，memcached/Redis 用 C + epoll（非阻塞 IO），Kafka 用 JVM + Netty，
  都在传输层下了真功夫。fourinone 的「轻量」是**用性能换来的**。

## 版本演进

- 本书无第二版记录（未见公开书目）。
- **2013 年口径**：Hadoop 1.x 时代，ZooKeeper 已成熟，Redis 刚起步，Docker/K8s 未出现。
  「四合一」想填补「轻量一站式」空白。
- **2026 年视角**：一站式诉求被**云原生编排**满足——Kubernetes（128032★）统一调度，
  上面各自跑专业的 ZK/etcd、Spark/Flink、对象存储、Redis、Kafka。
  「一个框架包打天下」的路线被证明不经济、不可维护。
- 🔧 **必须补入**：容器化（2013）与 K8s（2014）之后，「自研四合一」的必要性基本消失；
  今天选型的默认答案是「专业组件 + 统一编排」，而非「单一全栈框架」。

## 近年研究与工业界开源实践（2015–2026）

- **fourinone 自身**：`fourinone/fourinone` **85★**（2026-09-27 实测），社区极小、
  近年提交稀疏，与其书中所称「超级神器」完全不匹配；且仓库笔记原文称其「未完全开源」。
- **被对标对象的真实体量**（同日期实测）：
  Hadoop 15670★、Kubernetes 128032★、ZooKeeper 12811★、
  Redis 76498★、memcached 14285★、Kafka 33854★。
- **一站式框架路线在业界基本被证伪**：没有主流公司用「自研四合一」替代专业组件；
  相反趋势是「专业组件 + 编排层」（K8s 之上各跑各的）。
- **轻量分布式协调的后来者**：`etcd-io/etcd`（Raft，K8s 元数据存储）走的是
  「只做协调、用共识算法保证正确」的窄而深的路线，而非 fourinone 的「宽而浅」。

## 常见误区与本书需修正之处

| # | 误区 | 事实 | 书目 |
| --- | --- | --- | --- |
| 1 | 「不依赖第三方 jar = 自己造了轮子」 | 实际复用 JDK 内置 RMI / HttpServer，继承其 BIO/原生序列化性能天花板 | 🔧 本书 |
| 2 | 「四合一 = 四个专业系统」 | 是「一个框架各做一层」，每项深度与生态远不及专业系统 | 🔧 本书 |
| 3 | 「轻量 = 高性能」 | 轻量靠 BIO + 原生序列化，高并发下反而吃力（见笔记原文对 RMI 的质疑） | 笔记原文 |
| 4 | 「四不像超级神器」 | 与 85★ 真实活跃度严重不符，属过度自夸 | 🔧 本书 + 笔记原文 |
| 5 | 「少依赖就更好维护」 | 单一全栈框架把四类问题的复杂度耦合在一个小项目里，反而难维护难演进 | 🔧 2026 视角 |
| 6 | 书中未引原始文献 | 全书以 API 演示为主，缺 MapReduce/ZK 等原始论文对照，读者无法溯源 | 本书存疑 |
