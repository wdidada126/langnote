# 第 5 章　分布式文件：FttpAdapter · fttp

> 原书用 FttpAdapter（fourinone 的「ftp over http」）提供分布式文件读写。
> 仓库笔记原文已点破：fttp 实为基于 JDK6 `HttpServer` + `HttpURLConnection` 的远程文件访问，
> **必须明确知道文件在哪台机器的哪个目录**，并非真正的分布式文件系统
> （无分块、无副本、无元数据服务器、无故障透明恢复）。
> 这一章是「过度自夸」争议最具体的一处。

| 节 | 内容 | 结论 |

## 核心精讲

（以下为教学性梳理，伪代码/示意均**教学示意，不参与构建**。）

### 5.1 fttp 的真实形态（依笔记原文与公开文档重构）

```text
# 教学示意，不参与构建：fttp 的实际工作方式
服务端:  JDK6 自带 com.sun.net.httpserver.HttpServer（内嵌，非 Netty）
客户端:  java.net.HttpURLConnection（PUT 上传 / GET 下载）
寻址:    用户必须写死 fttp://host:port/目录/文件名
         -> 笔记原文："你用过必须制定 host 以及文件目录的分布式文件系统吗...
            读写文件时，必须清楚地知道文件在那台机器的那个目录下，orz"
```

- 这与 HDFS / GFS 的「逻辑路径 → 元数据服务 → 透明定位多个块副本」**完全不同**：
  fttp 把「定位」的职责甩给了使用者，根本没有元数据层。

### 5.3 一个真·分布式文件系统必备的（fttp 缺的）

| 能力 | HDFS / GFS 怎么做 | fttp 是否具备（存疑） |
| --- | --- | --- |
| 分块（chunk/block） | 大文件切块，默认 64/128 MB | 否，整文件传输 |
| 多副本 | 每块默认 3 副本，跨机架 | 否，单点文件 |
| 元数据服务 | NameNode / Master 管映射 | 否，靠用户写死路径 |
| 故障透明恢复 | 副本自动补齐、读写重试 | 否，失败即失败 |
| 高吞吐顺序读 | 为顺序 IO 优化 | 否，HTTP 小文件语义 |

### 5.4 高并发隐忧（笔记原文直引要点）

- 每个 request 创建一个 buffer，未做内存池管理 → 高并发时 **GC 负担大**；
- Selector 使用粗放（读写注册到另一 selector，每 request 一个 selector，虽有池化仍有锁开销）；
- 作者自称有「伙伴系统 + slab」内存管理方案，但笔记原文称读代码感觉「比较粗放，和 Netty 没法比」。
- 传输层用 HTTP（BIO 心智），对比 HDFS（自有 RPC + 零拷贝）、对象存储（经 CDN/多副本），
  在吞吐与并发上都不占优。

## 版本演进

- 本书无第二版记录。
- **2013 年口径**：HDFS 已成熟，对象存储（S3，2006）兴起；「内嵌 HttpServer 做文件」属极简方案。
- **2026 年视角**：**对象存储（S3 及兼容实现）已成为文件/ blob 的事实底座**，
  存算分离、湖仓表格式（Iceberg/Delta/Hudi）建立在其上；HDFS 地位下降但仍广泛使用。
  fttp 这种「写死 host+目录」的方案完全不符合现代「逻辑名 + 透明寻址」的范式。
- 🔧 **必须补入**：对象存储 + 存算分离是 2013 年后最重要的演进，本书完全缺席；
  今天做「分布式文件」默认答案是对象存储或 HDFS，而非自研 HTTP 文件服务。

## 近年研究与工业界开源实践（2015–2026）

- **HDFS** 随 `apache/hadoop` **15670★**（2026-09-27 实测）仍广泛部署。
- **对象存储生态**：MinIO（`minio/minio`，高性能 S3 兼容，star 量级数万）、Ceph
  等是「分布式文件/blob」的现代答案；而 fourinone 的 fttp 仅 `fourinone/fourinone` **85★**，
  且定位都不同（远程文件访问 ≠ 对象存储）。
- **高并发网络层事实标准**：Netty（`netty/netty`，海量 star）是 Java 非阻塞 IO 的基座，
  笔记原文也已指出 fttp 的 HttpServer 实现「和 Netty 没法比」。

## 常见误区与本书需修正之处

| # | 误区 | 事实 | 书目 |
| --- | --- | --- | --- |
| 1 | 「fttp 是分布式文件系统」 | 实为写死 host+目录的 HTTP 远程文件访问，无分块/副本/元数据 | 笔记原文 |
| 2 | 「不依赖三方 jar 很先进」 | 用 JDK 内置 HttpServer，继承 BIO/粗放 selector，高并发吃力 | 笔记原文 |
| 3 | 「轻量文件方案够用」 | 缺副本/容错，单机文件挂即丢，不能称生产级 | 🔧 本书 |
| 4 | 内存管理宣称 vs 实现 | 自称 slab/伙伴系统，笔记读代码称粗放、GC 负担大 | 笔记原文 |
| 5 | 「四不像神器」之文件维度 | 与 HDFS/对象存储差数量级（85 vs 15670/数万） | 🔧 本书 |
