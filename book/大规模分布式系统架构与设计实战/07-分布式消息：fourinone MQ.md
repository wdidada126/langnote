## 核心精讲

（以下为教学性梳理，伪代码/示意均**教学示意，不参与构建**。）

### 7.1 消息队列必须回答的硬问题

```text
# 教学示意，不参与构建：一个生产级 MQ 必须明确的事
1. 投递语义:  at-most-once / at-least-once / exactly-once ?
2. 持久化:    消息落盘了吗？broker 挂了丢不丢？
3. 消费组:    多消费者如何划分分区、如何重平衡？
4. 顺序性:    同一 key 的消息是否保序？
5. 背压/积压: 消费者慢时如何不压垮 broker？
```

> 这些问题是 Kafka / Pulsar / RocketMQ 花大力气解决的。fourinone 的 MQ 在书里以 API 演示为主，
> 上述任一项是否具备、如何保证，**未能核实，存疑**。

### 7.3 为什么建在 RMI 上的 MQ 先天吃力

- RMI 是 BIO（每请求一线程）+ JDK 原生序列化；消息场景恰恰是**高吞吐、小消息、突发流量**，
  与 BIO 模型相悖。
- 对比 Kafka：顺序写盘 + sendfile 零拷贝 + 分区并行，吞吐可达百万级 msg/s；
  这是架构层面的差距，不是调参能补的。

## 版本演进

- 本书无第二版记录。
- **2013 年口径**：ActiveMQ（JMS）、RabbitMQ（AMQP）是主流；Kafka（2011 开源）刚起步。
- **2026 年视角**：消息事实标准是 **Kafka（33854★）/ Pulsar / RocketMQ**；
  云厂商托管的托管 MQ 也已成主流。自研轻量 MQ 基本无生存空间。
- 🔧 **必须补入**：流式处理（Flink，2015 前后）与「日志即事实源（log-centric）」架构
  （Kafka 推动）是 2013 年后最重要演进；fourinone 的 MQ 既无流处理能力，也无 log 抽象。

## 近年研究与工业界开源实践（2015–2026）

- **Kafka** `apache/kafka` **33854★**（2026-09-27 实测）、
  **Pulsar** `apache/pulsar`、`RocketMQ` `apache/rocketmq` 是消息主流；
  **fourinone** `fourinone/fourinone` 仅 **85★**，其 MQ 模块采用可忽略。
- **流处理融合**：Kafka + Flink 成为「消息 + 计算」的事实组合，
  反衬 fourinone「四合一」中 MQ 与计算都偏弱、且无协同优化的困境。
