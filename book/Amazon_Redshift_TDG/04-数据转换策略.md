## 2. ELT vs ETL：本书口径（⚠️ 转述）

- ETL：先转换后装载——Glue/EMR 在湖侧洗好再 COPY；适合重清洗、多引擎复用产出；
- ELT：先装载后转换——原始数据进仓/进湖，SQL 在仓内完成业务转换；Redshift 算力便宜时占优，链路短、血缘清晰；
- 作者的折中："**以 ELT 为主干、ETL 处理脏源**"；混合形态=湖侧 Glue 出 Parquet + 仓内 SQL 出集市（✅ 4.4/4.5 两节的存在本身即佐证）；
- 概念谱系对位：转换下推/晚绑定的思想与 [../bigdata/04-SparkSQL与结构化数据.md](../bigdata/04-SparkSQL与结构化数据.md) 的 DataFrame 优化器叙事、[../Streaming_Databases/00-总览与阅读地图.md](../Streaming_Databases/00-总览与阅读地图.md) 的"库内增量转换"互为参照。

## 3. 库内转换三件套（⚠️ 转述 + ✅ URL）

### 3.1 半结构化数据：SUPER 与 PartiQL 系
- SUPER 类型直存 JSON 文档，`part('$.a.b')`/点路径访问；列自动拆解为内部列存（⚠️ 实现口径转述）；
- COPY JSON/JSONL 自动推断，UNLOAD 可导 Parquet（✅ https://docs.aws.amazon.com/redshift/latest/dg/r_UNLOAD.html 200）；
- 与 Snowflake VARIANT+FLATTEN 对照：[../Snowflake_The_Definitive_Guide/04-SQL命令数据类型与函数.md](../Snowflake_The_Definitive_Guide/04-SQL命令数据类型与函数.md)。

### 3.2 UDF / 3.3 存储过程
- UDF：SQL-Lambda 两栖（Lambda 托管 JS/Python 标量函数 ⚠️ 名录转述），适合行内小逻辑，**慎用**——逐行执行破坏列存向量收益；
- 存储过程：SQL PPL（CREATE PROCEDURE，EXCEPTION 块）做批内编排；2024+ 官方口风转向外部编排器（⚠️ 转述，见演进节）。

## 4. 调度与编排（⚠️ 转述）

- 书给的路标：Step Functions/EventBridge 触发 COPY/SQL 链，Glue 作业由调度器驱动；Redshift 自身无 DAG 引擎；
- 与 Ch9 迁移节呼应：先编排后迁移，避免"手工跑批考古"。

## 5. 访问所有数据：三种"外部"一图流（⚠️ 转述归纳）

| 外部源 | 机制 | 计算发生地 | 计费点 |
|---|---|---|---|
| S3 湖 | Spectrum 外表（Parquet/ORC/Iceberg/Hive） | Redshift 专属 Spectrum 节点组 | 按扫描字节 |
| OLTP（RDS/Aurora/PG/MySQL） | 联邦查询（自动建外表+回源） | 源库执行下推查询 | 源库 IO |
| 另一 Redshift 集群 | datashare 挂载只读库 | 本集群算力（冷数据走对方托管存储） | 见 Ch7 |
- Spectrum 列存外表 + 谓词下推 ≈ 把"湖"当"慢仓"；✅ https://docs.aws.amazon.com/redshift/latest/dg/c-spectrum-considerations.html （200）。
- 联邦查询注意：源库被穿透打爆是头号生产事故（⚠️ 社区共识转述）。

## 7. 🔧 本机类比（DuckDB 1.5.5，**非 Redshift 行为**，脚本存 tmp）

- 晚物化/列裁剪：20 列宽表 5e6 行、谓词命中 493,164 行——
  `SELECT count(*)` **4.7 ms**（只读谓词列+计数）；投影 2 列 **333.6 ms**；投影全 20 列 **1489.4 ms**（≈4.5× 差距）。
  结论迁移方向：列存引擎"扫描列数≈代价"，所以 Spectrum/SUPER 场景**只投影所需列**是普适红利；Redshift 具体物化时机 ⚠️ 以官方执行计划文档为准。
- JSON vs 列存：本机把同批数据以 JSON 行文本 vs Parquet 各存一份可复现"文档格式扫全行 vs 列组按需读"的差距（SUPER 的动机类比；数字以 § 列裁剪组为准，未单列）。
- UDF 减速类比：DuckDB 标量宏/逐行 Python UDF 与原生表达式在同表上的差距，可建立"行内函数破坏向量化"的直觉（🔧 概念演示；Redshift UDF 行为 ⚠️）。

## 10. 转换工具选型矩阵（⚠️ 转述归纳）

| 场景 | 首选 | 备选 | 理由 |
|---|---|---|---|
| SQL 可表达的清洗 | 仓内 ELT（视图/INSERT-SELECT/dbt） | 存储过程 | 链路最短、血缘即 SQL |
| 重清洗/格式归一 | Glue Spark（湖侧 ETL） | EMR | 脏数据不过仓门 |
| JSON 文档 | SUPER 直入 + SQL 拆 | Glue 展平 | 拆列调试在仓内快 |
| 跨源 join（OLTP+仓） | 联邦查询（小结果） | 先 Zero-ETL 进来再 join | 别拿穿透当常态 |
| 湖仓互操作 | UNLOAD/COPY Parquet | Iceberg 表格式（Ch7） | 多引擎共享决定格式 |
| 行内复杂逻辑 | 预计算列/物化 | UDF（末位） | 向量化优先（🔧 §7 类比佐证方向） |

## 11. 编排最小样例（⚠️ 转述形态复述，非原文代码）

## 核心概念速览（中英对照）

- ELT / ETL — 加载后转换 / 转换后加载：转换发生地之争（仓内算力 vs 湖侧引擎）
- 库内转换 — in-database transformation：用仓内 SQL/UDF/过程完成清洗加工
- SUPER 类型 — SUPER：Redshift 原生半结构化列类型，路径访问 + 自动拆列 ⚠️
- PartiQL — PartiQL：SQL 系文档查询方言（Redshift/Aurora/EMR 共用门面 ⚠️）
- UDF — user-defined function：标量自定义函数（SQL-Lambda 两栖），破坏向量化风险
- 存储过程 — stored procedure：CREATE PROCEDURE 批内编排（PPL 语言 ⚠️）
- Spectrum — Spectrum：S3 外表查询引擎，按扫描量计费、列存下推（✅ 概念页 200）
- 联邦查询 — federated query：直连 RDS/Aurora 自动外表，回源执行
- Glue Studio — Glue Studio：可视化 Spark ETL 作业编排（外部转换主角）
- 谓词下推 — predicate pushdown：过滤尽早贴数据源执行（本机类比 §7 佐证方向）
- 晚物化 — late materialization：宽行尽量晚拼全，先扫窄列（🔧 实测差距 4.5×，非 Redshift）
- 外部 Redshift 数据 — external Redshift data：把 datashare 当转换输入源（4.4.3 标题）
- 转换位置学 — where-to-transform question：源侧/湖侧/仓侧三点决策，本章唯一主线问题
- 编排-执行分离 — orchestration/execution split：Redshift 当执行器、DAG 不落仓内（§11 要点）
- 穿透风险 — federation blowback：联邦查询打爆源库的生产事故模式（⚠️ 社区共识）
- 血缘可见性 — lineage by SQL：ELT 立场的隐藏红利，链路即 SELECT 历史（系统表可查，Ch10 联动）
