## 2. 湖优先 vs 仓优先（⚠️ 转述归纳）

- 湖优先：S3+Glue Catalog 先行，Redshift 只做查询面（Spectrum/外部表/Catalog Connect）——灵活、冷数据便宜、治理难；
- 仓优先：COPY 进内表吃满 RA3/排序/统计——性能确定性高、贵一档；
- 本书口径：热事实表进仓、长尾与多引擎共享留湖，**Zero-ETL/流式摄入把两者黏合**。
- 对位：Snowflake 册同样命题在 [../Snowflake_The_Definitive_Guide/00-总览与阅读地图.md](../Snowflake_The_Definitive_Guide/00-总览与阅读地图.md) 的"数据云"节；开源口径见 [../bigdata/09-存储与文件格式.md](../bigdata/09-存储与文件格式.md)。

## 4. DISTKEY/SORTKEY/压缩编码（本章技术核心，全部 ⚠️ 转述 + ✅ URL）

### 4.1 分布式风格（distribution style）
MPP 下 join/聚合的代价=跨节点**重分布（repartition/shuffle）**。四种 DISTSTYLE（✅ CREATE TABLE 文档 200 佐证其存在）：
- KEY(k)：按分布键哈希切片——大事实表选**高频 join 键**（如 student_id），两表同键即 **collocated join 零重分布**；
- ALL：小表全复制（<~5M 行口径 ⚠️），broadcast join；
- EVEN：轮转均布（历史默认），倾斜免疫但 join 必重分布；
- **AUTO**：现代默认，系统自决（RA3/Serverless 上的行为差异 ⚠️ 转述官方口径）。
倾斜诊断入口：`SVV_TABLE_INFO` 的 tbl_rows/min/max 比例（⚠️ 转述）。
概念对位：单机世界里没有"重分布"——但"按 join 键聚组"的收益同构于本地哈希聚集：🔧 类比见 §6-D 组（非 Redshift 行为）。

### 4.2 排序键（sort key）
- COMPOUND（多键左到右组合序）vs **INTERLEAVED**（bit-interleave 多维序，多谓词友好、维护贵）；现代默认 AUTO SORT + ATO 自动选；
- 作用对象=**1MB 块的区域映射（min/max）**：Redshift **没有二级索引**，靠有序让"时间范围/高选择率谓词"跳过整块（Ch5 查询调优接棒）；
- ✅ URL：https://docs.aws.amazon.com/redshift/latest/dg/t_Sorting_data.html （200）。

### 4.3 压缩编码
列存块级编码（BYTED/ZSTD/DICT/DELTA/DeltaDelta 等 ⚠️ 名录转述），COPY 时自动分析列样本选码；编码影响 Spectrum 导出与 UNLOAD 格式选择（Ch4）。

## 5. 摄入路径全景（⚠️ 转述归纳）

| 路径 | 时效 | 要点 |
|---|---|---|
| COPY（S3/manifest） | 批量 | 官方推荐主路径；并行、列自动解码；✅ https://docs.aws.amazon.com/redshift/latest/dg/r_COPY.html （200） |
| 手动 SQL/编辑器 V2 | 临时 | INSERT...SELECT/小修补 |
| Glue ETL | 微批 | 湖侧转换后 COPY（Ch4） |
| DMS | 准实时 CDC | 迁移+持续复制双身份（Ch9） |
| **Zero-ETL（Aurora→Redshift）** | 秒级 | 免管道托管同步；表映射/冲突策略 ⚠️ 转述 |
| AppFlow | 事件/定时 | SaaS 源（Salesforce 等） |
| 流式摄取 Kinesis/MSK | 分钟级 | 直写内表，WLM 外通道；"开始步骤+最佳实践"两小节 |
对比 Snowflake：COPY↔COPY INTO（[../Snowflake_The_Definitive_Guide/06-数据加载与卸载.md](../Snowflake_The_Definitive_Guide/06-数据加载与卸载.md)）；流式↔Snowpipe Streaming。语义分工极像，Redshift 把"湖/OLTP 黏合"做成托管服务数量更多（⚠️ 评价）。

## 6. 🔧 本机类比（DuckDB 1.5.5 + python sqlite3，**非 Redshift 行为**，脚本存 tmp）

- A 列存压缩（类比 §4.3）：5e6 行 ×5 列订单表 → Parquet **64.7 MB** vs SQLite 行存 **163.8 MB**（2.5×）；低基数列（cust_bucket=i%50）贡献最大，印证"字典/RLE 吃重复"。
- B 装载路径（类比 §5-COPY）：`COPY stg FROM 'fact.parquet'` 5e6 行 **134.4 ms**；逐条参数化 INSERT 2 万行 **14.5 s**（线性外推 5e6 ≈ 1 小时）→ "批量 COPY vs 裸 INSERT"差 4 个数量级，与 Redshift"COPY 优先于 INSERT"的告诫方向一致（幅度不可迁移）。
- C 排序键/块跳过（类比 §4.2）：同一 Parquet 数据集按 d 排序后查 d∈[0,292]（0.4% 行）**6.9 ms**，乱序版 **16.4 ms**（2.4×）→ 有序文件的行组 min/max 跳过就是"排序键+区域映射"的单机投影；Redshift 真值以 ⚠️ 官方为准。
- D "collocation 收益"玩具演示：本机 DuckDB 按 student_id 预分组聚合 vs 全表扫描聚合，差异体现"数据局部性省 pass"而非省网络——概念桥，不代表 DISTKEY 行为。

## 8. 表设计检查清单（从本章提炼，⚠️ 转述；✅ 语法锚 https://docs.aws.amazon.com/redshift/latest/dg/t_create-tables.html 200）

- [ ] 事实表 DISTKEY=最高频 join 且高基数列；维度表小→DISTSTYLE ALL；
- [ ] SORTKEY 贴时间/主查询谓词列；不确定就 AUTO 交给 ATO；
- [ ] COPY 前完成编码：AUTO 分析或显式 ENCODE；事后改码=重写表；
- [ ] 装载路径默认 COPY（S3 并行分片）；流式需求评估 Kinesis/MSK 直连；OLTP 源评估 Zero-ETL；
- [ ] 上线后看 SVV_TABLE_INFO：倾斜>1.5x 或空块率高→回炉重选键（⚠️ 阈值口径转述）；
- [ ] 湖侧留一份：重要内表定期 UNLOAD 回 S3 作湖备份/他引擎共享（Ch7 联动）。

## 9. 星型建模走查（学生数据集，✅ 小节实抓 + ⚠️ 细节转述）

- 事实表：grade_events（成绩事件）类大表——DISTKEY=student_id，SORTKEY=event_date；
- 维度：students/courses/assignments 小表 ALL 分布；
- 反规范化裁决：维度属性稳定→直接摊平进维度；变化快→拉链（SCD 思路，回链 [../Building_the_Data_Warehouse/11-关系模型与多维模型.md](../Building_the_Data_Warehouse/11-关系模型与多维模型.md)）；
- 装载顺序：维先行、事实后行，外键完整性由过程保证（Redshift **不强制 FK 约束**，仅优化器提示用途 ⚠️ 转述）。

## 10. 摄入路径选择 FAQ（⚠️ 转述）

- 文件已到 S3？→ COPY + manifest；持续落新文件→S3 事件驱动或"连续摄取"小节方案；
- 源是 Aurora/RDS？→ 优先 Zero-ETL（托管、秒级、有配额与冲突规则 ⚠️）；需要复杂转换再回 DMS+Glue；
- 源是事件流？→ Kinesis/MSK 流式摄取直写；延迟敏感于一致性？评估其"最终一致可见"语义（⚠️ 转述）；
- 一次性回填历史？→ COPY 分片并行 + 避开维护窗（ATO 错峰，Ch5）。

## 核心概念速览（中英对照）

- MPP 重分布 — repartitioning/shuffle：跨节点搬数据以满足 join/聚合 co-location 的代价
- 分布键 — DISTKEY：决定行落哪个 compute 切片的哈希列（KEY/ALL/EVEN/AUTO）
- 全复制表 — DISTSTYLE ALL：小表复制到每节点，换 broadcast join
- 数据倾斜 — skew：分布键选择不当导致节点冷热不均
- 排序键 — SORTKEY（compound/interleaved/AUTO）：块内物理序，喂给区域映射
- 区域映射 — zone map：每 1MB 块的列 min/max，**无索引**时代的块跳过元数据
- 压缩编码 — compression encoding：列存块编码（ZSTD/DICT/DELTA…⚠️ 名录转述）
- COPY — 批量装载命令：S3→内表官方主路径，并行+自动解码
- 清单文件 — manifest：COPY 的显式文件列表模式
- Zero-ETL — 零 ETL 集成：Aurora/RDS/DynamoDB→Redshift 托管近实时同步（书中仅 Aurora ⚠️）
- 流式摄取 — streaming ingestion：Kinesis/MSK 直写 Redshift 内表通道
- 数据湖优先/仓库优先 — lake-first / warehouse-first：建模起点之争（本章开篇命题）
- 星型模式 — star schema：事实表+反规范化维度，Redshift 默认推荐
- 自动表优化 — ATO：后台自动重排/重压缩/重分布的托管优化器（Ch5 详解）
- 拉链/SCD — slowly changing dimension：维度演化标准手法，Redshift 靠表重写实现（⚠️ 转述）
- 文件分片 — file partitioning：COPY 并行的前提，S3 侧小文件合并是装载调优第一刀（⚠️ 实践）
- 可见性时延 — ingestion freshness：流式/Zero-ETL 路径的 SLA 维度（分钟/秒级 ⚠️ 口径）
