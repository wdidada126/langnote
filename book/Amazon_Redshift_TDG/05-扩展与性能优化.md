## 2. 两条扩展轴（⚠️ 转述）

- 吞吐轴（scale-out）：加节点/加 RPU——Serverless autoscaling 按 workgroup 上探，预置集群改节点数需重启窗口（RA3 托管存储使扩容不再搬全量数据 ⚠️）；
- 并发轴（**concurrency scaling**）：主集群之外临时拉起托管计算簇接尖峰，用多少付多少，透明路由；
  ✅ 概念页 https://docs.aws.amazon.com/redshift/latest/dg/concurrency-scaling.html （200）。
- 对位：Snowflake 用多集群自动扩仓库（[../Snowflake_The_Definitive_Guide/02-架构与虚拟仓库.md](../Snowflake_The_Definitive_Guide/02-架构与虚拟仓库.md)），BigQuery 用 slot 弹性——三家在"并发扩展"上抽象层级不同：Redshift 保留主集群实体最久（⚠️ 评价）。

## 3. WLM 全家桶（⚠️ 转述归纳）

| 件 | 作用 | 现状口径 |
|---|---|---|
| 队列 + 并发份额 | 按规则把查询分队列，限并发/内存占比 | 自动 WLM 默认托管 |
| SQA 短查询加速 | <1s 的 BI 点查走旁路，免排队 | RA3/Serverless 特性，按秒计费 |
| QMR 查询监控规则 | 超时/超资源自动取消或重路由 | 治理必备 |
| 参数组 | 会话参数（statement_timeout 等）打包 | 集群级绑定 |
| 动态内存分配 | 队列内存按实时负载再分配 | 自动 WLM 增强 |
- 旧文档页 r_wlm.html 实测 302→文档根（2026 改版），概念以 mgmt/dg 根 + 上表 200 页为准（✅ 取证方式）。
- 心智模型：WLM 决定"**谁能同时跑**"，优化器/ATO 决定"**单条跑多快**"——排障先分层。

## 4. 自主优化军团（⚠️ 转述 + ✅ 命令页）

- **ATO（自动表优化）**：后台自动做重排（sort）、重压缩、重分布 + 维护窗口；
- **自动 VACUUM**：DELETE/UPDATE 产生未排序混合区（unsorted region）→ 自动回收重排；✅ https://docs.aws.amazon.com/redshift/latest/dg/r_VACUUM_command.html （200）；
- **自动 ANALYZE**：列统计采样（直方图）供优化器估卡片数；✅ https://docs.aws.amazon.com/redshift/latest/dg/r_ANALYZE.html （200）；
- **AutoMV**：监控重复子计划自动生成/改写命中物化视图；MV 本体 ✅ https://docs.aws.amazon.com/redshift/latest/dg/materialized-view-overview.html （200）；
- **Advisor**：把上述之外的人工建议（如缺统计的列）打包送审。
- 与 Snowflake 对照：SF 靠微分区+自动聚簇把同类问题"设计掉"，Redshift 是"旧机制+自动化外壳"——理解这层，两册的调优章就是同一部《统计与布局维护学》两种封面（[../Snowflake_The_Definitive_Guide/09-查询性能分析与优化.md](../Snowflake_The_Definitive_Guide/09-查询性能分析与优化.md)）。

## 5. 查询调优方法论（⚠️ 转述）

1. 定位：STL/SVL 系统表 + 查询警报（如百万行级表扫描告警）+ Top Queries 视图；
2. 读计划：EXPLAIN（静态）vs EXPLAIN_ANALYZE（运行时真实行数）——重点看 **BROADCAST/REPARTITION 节点**（重分布信号）与估算偏差；✅ EXPLAIN 语义 ⚠️ 旧页 302，命令族在 dg 根可查；
3. 处方：DISTKEY 对齐消重分布 / SORTKEY 贴谓词 / 列裁剪与聚合下推 / 倾斜改写（拼 key 打散）/ 必要时 MV 固化。

## 6. 🔧 本机类比（**非 Redshift 行为**，数据存 tmp demo_out.txt）

- 排序键+块跳过（对应 §5.8"索引与区域映射"）：5e6 行 Parquet，查 d∈[0,292]（0.4%）——按 d 有序 **6.9 ms** vs 乱序 **16.4 ms**（2.4×）。
  Redshift 同理但载体是 1MB 块 zone map，且**没有二级索引**（✅ t_Sorting_data.html 200 页明示排序键替代索引角色 ⚠️ 转述）；
- ANALYZE 价值（对应 §4）：SQLite 2e6 行、b=7 AND a>1.5e6 查询，ANALYZE 前 **29.3 ms**→后 **38.0 ms**（结果一致 10,000 行）：
  诚实记录——**统计改变计划方向≠必变快**，Redshift 自动分析同理看趋势不看单查（⚠️ 类比推论）；
- 宽表投影代价（对应 §5.9 列裁剪）：DuckDB 20 列全投影是 2 列投影的 4.5×（见 04 章 §7，同一脚本）；
- 晚物化在 Redshift 的镜像 ⚠️ 转述：执行器按列族推进、必要时才拼行——本机 DuckDB 属"向量化+晚物化"现代实现，概念可互相印证。

## 9. 排障决策树（本章方法论压缩，⚠️ 转述）

1. 单查询慢 or 全局慢？——全局：看并发/队列深度/资源利用率（Ch10 控制台三表）→ 扩或隔离（WLM/多仓库）；单条：进第 2 步；
2. 计划对不对？——EXPLAIN_ANALYZE 估算 vs 实际行数：偏差大→统计/ANALYZE、倾斜；
3. 数据摆得对不对？——重分布节点大→DISTKEY 错位；全表扫块多→SORTKEY 未贴谓词（🔧 §6 zone-map 数字给方向感）；
4. 写法对不对？——列全取（🔧 4.5× 教训）、标量 UDF、低效递归/CTE 物化选择；
5. 值不值得固化？——高频聚合上 MV；重复子计划看 AutoMV/Advisor 建议；
6. 都对了还慢→容量问题：加 RPU/节点或并发扩展兜底（§2）。

## 核心概念速览（中英对照）

- 并发扩展 — concurrency scaling：尖峰期自动拉起临时计算簇承接查询（Redshift 招牌）
- 自动扩展 — autoscaling：Serverless RPU 按负载在上下限内伸缩
- WLM — workload management：按规则分队列限并发/内存的调度层
- 短查询加速 — SQA：低延迟小查询旁路通道，按激活秒计费 ⚠️
- 查询监控规则 — QMR：超时/超量查询自动取消或重路由的策略
- 自动 WLM — auto WLM：队列与并发由系统托管分配
- 物化视图 — materialized view：预聚合结果表，查询可改写命中
- 自动物化视图 — AutoMV：系统发现重复子计划后自建 MV ⚠️
- ATO — automatic table optimization：自动重排/重压缩/重分布的后台优化器
- VACUUM — 真空：回收标记删除+整理未排序区（✅ 命令页 200）
- ANALYZE — 统计收集：列直方图/NDV 采样喂优化器（✅ 命令页 200）
- 区域映射 — zone map：块级 min/max 实现无索引块跳过
- EXPLAIN / EXPLAIN_ANALYZE — 静态/运行时执行计划：调优第一听诊器
- Redshift Advisor — 顾问：性能/成本改进建议清单服务
- 查询警报 — query alerts：按行数/耗时阈值触发监控告警（✅ query-analytics-monitoring.html 200）
