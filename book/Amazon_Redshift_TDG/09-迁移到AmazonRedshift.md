## 2. 三策略决策表（⚠️ 转述重构）

| 策略 | 停机 | 复杂度 | 适用 |
|---|---|---|---|
| 单步 big-bang | 长（窗口=全量搬运+回归） | 低 | 小仓（TB 内）、冻结期可得 |
| 两步 | 短（仅切换窗） | 中：CDC 追平+双写校验 | 主流：书中耗时演算例（✅ 译文有"20 天 13 小时"等带宽×体量推表实抓） |
| 迭代 | 几乎无 | 高（波次治理） | 大仓/多域/组织阻力大 |
带宽推算法（数据量/有效吞吐，10GbE 例、45Mbps 小例）是本章少见的"可带走方法论"（✅ 小节实抓）。

## 3. 工具三角：SCT + DMS + Snow（⚠️ 转述 + ✅ URL）

- **SCT**：源仓（Teradata/Oracle/Hive/PDW…）方言→Redshift SQL 批量转换，迁移评估报告给"可转率"；数据提取代理加速抽数；BLOB→S3+外表是经典降维打击（✅ 译文小节实抓）；
- **DMS**：全量+CDC；迁移任务与持续复制分离——"两步策略"的服务化身；**Serverless 化（2024-11）后免管复制实例**（⚠️ 演进，见 §6）；✅ https://aws.amazon.com/dms/ （200）；
- **Snow Family**：PB 级冷搬——Snowball Edge 客户端以 NFS/S3 网关姿态充当"在线扩展盘"（⚠️ 转述）；
- 组合拳：SCT 转 schema/DML → COPY 或 DMS 灌数 → DMS CDC 追增量 → 双写对账切换。

## 4. 迁移过程三步与回归要点（⚠️ 转述）

1. 模式/主题域转换：顺带做"搬家式清理"（废弃表不迁，9.1 清单法落地）；
2. 初始加载：并行分片 COPY（Ch3 技能复用）；
3. 增量 CDC 追平：切换前冻结写或双写；
4. 切换后：统计/真空/权限/性能基线重做（Redshift 无索引但**必须重跑 ANALYZE/VACUUM 语义**由 ATO 接管 ⚠️；对位旧 DBA 习惯的"重建索引"焦虑——Redshift 答案是排序键与区域映射，✅ Ch3 §4.2 回链）。

## 5. 🔧 本机类比（**非 Redshift 行为**，DuckDB 1.5.5）

- 方言转换直觉：DuckDB `SELECT i, j FROM t` 与 PG 系日期函数差异（`date_trunc` 同款、`::` 强转方言）——把"评估报告=可转率"具象化：本机把一段 SQLite 日期 SQL 手工改到 DuckDB 只需处理 `strftime`→`date_trunc` 一类点，规模化即为 SCT 存在的理由；
- 两步迁移直觉：本机 SQLite 全量导出 CSV + 追增量（按更新时间戳二次 COPY）≈"初始+变更"最小模型；CDC 日志捕获不可类比（诚实 ⚠️）；
- BLOB 降维：把大文本列从主表拆出存文件、表内留路径——DuckDB/SQLite 均可演示"仓不养 BLOB"的布局收益（概念类比）。

## 9. 迁移常见翻车点（⚠️ 经验归纳，帮读）

- 把"可转率 90%"当"性能达标 90%"：语法过≠计划过，回归必须带数据量测；
- 忽略字符集/大小写语义差异：旧仓不区分大小写→Redshift 区分，迁移加速小节专治此项（✅ 9.6 实抓）；
- BLOB/大字段直迁：仓内当字节存，扫描全坏——拆 S3+路径列（🔧 §5 类比）；
- 统计缺位即宣判"新仓慢"：装载完成≠可服务，先 ANALYZE/等 ATO 首轮（Ch5 联动）；
- 权限照搬旧库：角色模型不匹配导致"人人 superuser"回潮（Ch8 联动）。

- 双写对账 — dual-run reconciliation：切换期新旧仓一致性验证实践（⚠️ 行业惯例归纳）
- 冻结切换 — code freeze & cutover：停机窗内只读→切流→观察的标准三段
- 回归基线 — regression baseline：迁移前录制旧仓关键查询集，切后逐条对齐耗时/结果
- 可转率 — conversion rate：SCT 报告的语法自动转换比例，项目排期核心输入（⚠️）
- 停机推表 — downtime math：数据量÷有效带宽×并行度→窗口估算（✅ 9.1 小节方法实抓）
- 波次划分 — wave planning：按主题域切迭代迁移的批次设计（9.2 迭代策略落地）
- 提取代理 — extraction agent（SCT）：源端就近并行抽数，绕开源库导出瓶颈（✅ 9.3 小节实抓）
- BLOB 降维：大对象拆 S3+外表路径列，仓内只留指针（✅ 9.3 小节实抓，🔧 §5 有布局直觉）
- 主题域切波 × 停机容忍：9.1 六项考虑=策略选择输入，9.2 三策略=输出，考试常把两者倒装来问（⚠️ 帮读）。

## 10. 自测四题（合书作答，⚠️ 依本章要点）

1. PB 级历史+日增 100GB 的 Teradata 仓，选哪策略？——迭代分波+两步追增量混合；带宽账先于工具选型；
2. SCT 显示可转率 95%，为何还不能宣布完工？——剩余 5% 是存储过程/宏长尾+性能回归未跑（§4/§9）；
3. DMS 与 Zero-ETL 都叫"持续同步"，差别？——DMS 通用可控含转换；Zero-ETL 托管免管道但源/目标矩阵与配额受限（⚠️ 演进节）；
4. 迁移后首周最该盯的三张表？——未 VACUUM 占比、统计新鲜度、倾斜（SVV_TABLE_INFO）——对应 §9 翻车点 4/5；
5. 何时该"迁湖不建仓"？——多引擎共享+低算力需求+表格式成熟域；否则仓仍是 BI 确定性首选（⚠️ 评价，见演进节新路径）。

## 11. 术语误用纠偏（⚠️ 评价性）

- "平移（lift & shift）"：仓迁移几乎不存在真平移——方言/物理设计/权限三层都要动，书中 9.6"加速"清单即平移幻觉的反证；
- "割接=上线"：割接只是切换读路径，写路径/调度/告警的移交常被漏项（§8 模板 W9 专门收口）；
- "DMS 全量=初始加载"：大仓初始加载官方仍推荐 COPY 并行路径，DMS 的强项在 CDC 段——两工具在 9.4 三步里各管一段，别混用词。

## 核心概念速览（中英对照）

- 单步/两步/迭代迁移 — big-bang / two-step / iterative：停机与复杂度的三角权衡
- 废弃与保留清单 — deprecate/retain analysis：搬家先扔，迁移项目第一杠杆
- AWS SCT — Schema Conversion Tool：方言与对象批量转换+可转率评估
- AWS DMS — Database/Repository Migration Service：全量+CDC 持续复制
- 复制实例 — replication instance：DMS 载具（2024-11 起有 Serverless 形态 ⚠️）
- CDC — change data capture：日志/触发式增量捕获，两步迁移的第二条腿
- Snow Family — 离线大宗物理搬运设备线（Snowball Edge 客户端≈在线扩展盘 ⚠️）
- 迁移评估报告 — migration assessment：SCT 的转换可行性/工作量账单
- 数据提取代理 — extraction agent：源端并行抽数加速器（⚠️ 转述）
- 递归 CTE — recursive CTE：Redshift 原生支持项，旧仓过程式逻辑改写落点
- 大小写不敏感比较 — case-insensitive comparison：迁移加速特性（避免 LOWER() 全包 ⚠️）
- 双写对账 — dual-run reconciliation：切换期新旧仓一致性验证实践（⚠️ 行业惯例归纳）

## 最新演进与工业实践

- 2024–2026 迁移栈刷新：**DMS Serverless GA（2024-11）**自动扩缩免容量选型；**Zero-ETL 管理任务**把"Aurora/RDS/DynamoDB→Redshift"从项目变开关——本章"两步+迭代"方法论对 OLTP 源基本失效（升级而非否定 ⚠️ 转述）；
- 旧仓（Teradata/Netezza/On-Prem Oracle）→Redshift 大单仍靠 SCT+DMS+人工改写三段式；2025 起 AI 辅助 SQL 方言迁移（transform 类工具/LLM 改写）成为咨询新宠（⚠️ 行业观察，无权威统计，谨慎引用）；
- Lakehouse 分流：一部分"迁移"目标从"仓"改为"表格式"——"先迁湖再选择性建仓"是 2025-2026 常见新路径（⚠️ 转述；盘上对位 [../Apache_Iceberg活用入門/00-总览与阅读地图.md](../Apache_Iceberg活用入門/00-总览与阅读地图.md)、[../Use_Iceberg_with_Spark/00-总览与阅读地图.md](../Use_Iceberg_with_Spark/00-总览与阅读地图.md)）；
- 取证：✅ aws.amazon.com/dms/ 200；SCT 专页 aws.amazon.com/dms/schema-conversion-tool/ 301→dms/features/（改版实证）；Snow Family 文档未逐页验，标 ⚠️。
- 迁移工具生态 2024–2026 增量（⚠️ 转述）：SCT 持续扩展源端（Sybase/SAP Hana 系评估增强）与"转换后性能建议"；DMS 校验任务支持全表级对比；两工具与 CloudEndure 型整机迁移的边界日益清晰——**数据仓迁移=对象+SQL+数据三轨**，本章框架仍是三轨教材；
- AI 辅助改写：旧仓 SQL→Redshift 方言的 LLM 转译 PoC 在咨询界流行（2024+），但"可转率"口径下人工分诊未过时（⚠️ 行业观察，无权威统计）；
- 反模式提醒（⚠️ 评价）：把"迁移"当一次性项目而非资产盘点机会的團隊，9.1 清单法被跳过的比例最高——这也是本章放在全书倒数第二位的原因：作者要你先有 Ch2–8 的目标形态认知，再谈搬家；
- 带宽账复算模板（✅ 方法实抓+⚠️ 数字自填）：TB×8÷有效 Gbps÷86400=天；再乘 3~5 倍真实折损（重传/并行不满/维护窗）——书中 10GbE/45Mbps 两例即是示范，任何规模迁移第一晚就该重跑这道算术；
- 与 Ch3 的闭环：迁移完成时，新仓的 DISTKEY/SORTKEY/编码应已按 Ch3 清单重设计——"平移党"把旧仓布局当资产带走，是迁移后性能债的最大单一来源（⚠️ 评价）。
