# 05 近实时搜索（print 第 6 章）

> 内容锚点（✅ 实抓官方仓库）：075_Inside_a_shard 部之 40_Near_real_time、50_Persistent_changes、60_Segment_merging 等文件；056_Sorting/95_Fielddata（与本章"排序件"话题相关）。转述 ⚠️。

## 1. "近实时"的精确含义

书中定义：**文档写入 ≠ 立即可搜**。可见性由三段流水线决定：

1. 写入：文档进 in-memory buffer + 追加 **translog**（持久，防丢）；
2. **refresh（默认 1s）**：buffer→新段、打开新 searcher → 此刻起可搜；新段进文件系统缓存，暂不落盘；
3. **flush（translog 满或周期）**：Lucene commit，fsync 落盘，**截断 translog**——"translog 只保护自上次 commit 以来的增量"是本章金句。

工程推论（书中原文口径）：**refresh 间隔=吞吐与可见延迟的旋钮**。日志类场景设 `refresh_interval: 30s` 甚至 `-1`（批量导入），交互式搜索保留 1s。此建议在 2026 年官方索引调优文档里仍原样存在（⚠️ 转述；✅ 索引管理总览 https://www.elastic.co/docs/manage-data ）。

## 2. "实时"怎么补（书中三个技巧）

- `refresh=true` 写后强刷（**仅测试/演示可用**，生产中每次刷=段爆炸）；
- **直接 GET 按 id 读**：书 9 章的"以 id 取文档走 translog+段，不受 refresh 影响"——**读写路径分离**是 NRT 系统的通用止痛药（对照 [../设计数据密集型应用/05-复制.md](../设计数据密集型应用/05-复制.md) 的"读己之写"三方案）；
- 外部版本 `version_type=external` 同步 RDB→ES 时防乱序覆盖。

## 3. 段合并的账（60_Segment_merging 节）

- 每 ~1s 一个段 × 高写入 = 段数失控 → merge 线程持续降级（throttling，1.x 有 `indices.merge.scheduler.max_thread_count` 一类设置，书中专讲**旋转盘上 max_thread_count=1 否则 I/O 爆炸**；SSD 时代该劝告放松，但设置健在 ⚠️ 转述）；
- merge 策略：tiered（同尺寸层级合并，Lucene 4 系默认）——**段合并是 ES 三大隐形税之一**（另两个：refresh、translog fsync）；
- 书中给出的观测法：`/_stats/merge`、`/_cat/segments`。

## 4. 为什么"倒排 + 段不可变"能同时做到快写与快读

本章用一句话总结设计动机：可变倒排必须原地改 posting，并发与崩溃恢复是地狱；不可变段把问题拆成"造新段"（append，便宜）+"合并"（后台批处理）+"位图标记删除"（O(1)）——**这是把 B 树的更新成本摊平到列存式重写的检索版**（对照 [../Database_Internals/02-B树基础.md](../Database_Internals/02-B树基础.md)）。

## 5. 与事务语义的边界

书中明确（⚠️ 转述）：ES 只有单文档级"写入原子 + 乐观版本"；**跨文档无原子性**，`_bulk` 只是打包不是事务。2.x 之后 ES 也没有等到这个能力；2026 年仍按"无多文档事务"使用（Elasticsearch 主页对其定位是 search/analytics engine，✅ https://www.elastic.co/elasticsearch ）。这条边界是"能否拿 ES 当主库"辩论的焦点，见 [14 章](14-数据分布扩展与冗余.md)的"ES 不是数据库"节。

## 5.1 写入路径八步法（把 4/9/12 章的零件串成一条时间线）

1. 请求落协调节点 → 路由定位主分片（[14 章](14-数据分布扩展与冗余.md)数学）；
2. 主分片解析文档 → 分析 → 写 in-memory buffer；
3. 同笔：translog **append**（OS 缓存，未必落盘）；
4. 并行转发副本（尽力而为，[14 章](14-数据分布扩展与冗余.md)）；
5. ≤1s：**refresh**——buffer→新段、reopen searcher（此刻可搜）；
6. 段文件写入文件系统缓存，OS 决定何时刷盘；
7. 攒够阈值（translog 大小/时间）→ **flush** = Lucene commit + fsync translog + 截断 translog；
8. 崩溃恢复：重放 translog 补"上次 commit 之后"的段（书中专节，⚠️ 转述）。

**故障注入读法**（运维心法，书中未明说、由该时间线直接可推）：第 5 步前进程崩=translog 重放救回；第 7 步前掉电=OS 缓存中的段文件丢、translog 仍在=可救；translog fsync 也失败=该笔 ack 已发则数据丢——**ack 时机与持久化时机的错位是所有 NRT 系统的审计重点**。

## 5.2 三本旋钮账（refresh / translog / merge）

| 旋钮 | 书代默认与选项 | 调它动的是什么 |
|---|---|---|
| refresh_interval | 1s；-1 关闭 | 可见延迟 ↔ 段数/搜索开销 |
| translog durability | request（每笔 fsync）/ async | 崩溃丢数据窗口 ↔ 吞吐（⚠️ 书代默认值以在线版为准） |
| merge 系列 | `indices.merge.scheduler.*`、max_thread_count | 索引速度 ↔ 搜索段数 ↔ I/O 竞争 |

> 三旋钮互为对手戏：把 refresh 调大→段变大→merge 更猛→搜索更舒服但可见更慢——书中没有一句"银弹"，全是"观测 `_stats` 后调"。

## 核心概念速览（中英对照）

- **近实时** — Near Real-Time (NRT)：写入到可搜间隔一个 refresh（默认 1s）
- **refresh** — Refresh：buffer→新段+开 searcher；可见性开关
- **flush/commit** — Flush/Commit：Lucene 提交+fsync+截断 translog
- **translog** — Transaction log：段间 WAL；默认 fsync 策略 request/index ⚠️
- **in-memory buffer** — Indexing buffer：未成段的文档暂存区
- **可见性≠持久性** — Visibility vs durability：可搜与不丢是两个独立轴
- **refresh_interval** — Refresh interval：吞吐/延迟旋钮；批量导入调大
- **GET by id** — Direct GET：绕过 searcher 的读路径，读己之写
- **外部版本** — External versioning：用 RDB 时间戳做增量同步的防乱序件
- **tiered merge** — Tiered merging：同尺寸分层合并策略
- **merge throttling** — Merge throttling：后台合并限速；SSD 时代仍要观测
- **单文档原子性** — Single-doc atomicity：无跨文档事务的自白 ⚠️

## 最新演进与工业实践

1. **旋钮健在**：`refresh_interval`、translog durability 选项、`_forcemerge` 等本章三件套在 8.x/9.x 官方文档中同名存续（✅ https://www.elastic.co/docs/manage-data ；细节参数 ⚠️ 转述）；"批量导入先 refresh=-1 后恢复"仍是官方教程第一句。
2. **idle 自动化**：书中"每 1s 必造段"的浪费，被 5.x 后陆续引入的按需/空闲优化（如 `index.search.idle.after` 的 idle 语义、软 deletes 等）部分缓解（⚠️ 未逐项核，不展开）。
3. **日志栈的 NRT 取舍**：ELK/Loki 式平台普遍把 ES 索引设 30s+ refresh 换 2–5 倍索引吞吐——工业口径与本章完全一致；时序场景另用 ILM 把老段 forcemerge 降热（✅ https://www.elastic.co/docs/manage-data/lifecycle/index-lifecycle-management ）。
4. **对比其他系统**：读己之写三策略 → [../设计数据密集型应用/05-复制.md](../设计数据密集型应用/05-复制.md)；Cassandra 的"写时段不可变+读修复"与"refresh 模型"的相似性 → [../cassandra实战.md](../cassandra实战.md)；论文线（WAL/LSM 谱系）→ [../../db/db.md](../../db/db.md)。
5. **语义不变，管道变长**：2026 年数据入 ES 多为"Kafka→Logstash/Connect 或 ingest pipeline→ES"（🔧 未实测，⚠️ 转述），NRT 延迟预算里要加上上游队列——书中"1 秒可见"如今是"1 秒+管道"。
6. **软删除与保留策略**：5.x 引入软 deletes 后，删除文档可参与 translog 回放与 PIT 一致性读，"删除立刻不可见"的旧直觉在深分页快照场景失效 ⚠️ 转述；调试"删了还在"类工单先看是否持有 PIT。
7. **serverless 视角**：托管形态下 refresh/flush 旋钮部分由平台代管，用户手册的"读己之写"建议升级为"用 GET API 或一致性读参数"，而不是自己调 refresh（⚠️ 各厂商口径不同，未逐一核）。
8. **教科书口径落点**：本章是"LSM 写路径 vs B 树写路径"差异的最佳展示窗——段不可变使 ES 的写放大集中在 merge，与 RocksDB 家族同谱（论文线见 [../../db/db.md](../../db/db.md)）。
