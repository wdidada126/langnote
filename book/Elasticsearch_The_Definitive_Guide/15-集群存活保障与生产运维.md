## A 篇 · Ensuring Viability in a Distributed Cluster（print 第 17 章）

### 1. 故障矩阵：同一集群的 12 种死法

书中用一系列"拔掉一台机器"的推演覆盖：master 挂、data 节点优雅离/硬崩、网络分区、分片写入失败、mapping 冲突、`_id` 重复引发版本漂移、磁盘满、GC 停顿引发节点被踢……每条配 `/_cluster/health`+`/_cat` 的观测序列。方法论价值大于条目价值：**"分布式集群的常态是局部坏"**。

### 2. 三个高潮案例（书中重点）

1. **僵尸主（zombie master）**：旧主网络恢复后试图发布过期集群状态——1.x 的 `publish_timeout`/`master-ack` 机制应对；现代由协调层代数（cluster state publication + voting config）根治（⚠️ 对位，细节未逐一核）；
2. **复制-失败链**：副本写失败→被移出→新副本重建（recovery 源=主分片；translog 不可用时全量 copy 段文件）——书中把 recovery 流量画成容量风险；
3. **mapping 漂移**：同名字段不同索引类型冲突→多索引搜索整请求失败——把 [11 章](11-映射与索引的本质.md)的 dynamic 纪律升级为"集群级事故源"。

### 3. 防损设置包（1.x 清单 → 今昔）

| 书代设置 | 今况 |
|---|---|
| `discovery.zen.minimum_master_nodes` | **删除**（voting config）；[13 章](13-均衡集群.md) |
| `gateway.expected_nodes/recover_after_time` | 语义弱化/换代（⚠️ 现代以 quorum+自动延迟分配） |
| `cluster.routing.allocation.*_enable`、水位线 | 健在 |
| circuit breaker（fielddata/request/parent） | 健在，家族扩大 |
| `_shutdown` API | 1.x 手工三步 → 8.x 原生 `_shutdown`（节点退役编排）⭐ |
| snapshot 仓库（shared fs/S3） | 健在且为**官方唯一推荐备份路径**（✅ https://www.elastic.co/docs/manage-data 族） |

## B 篇 · Managing a Cluster in Production（print 第 18 章）

### 4. 硬件与 JVM 账本

书中部署基线（2014 口径，⚠️）：64GB RAM、SSD、万兆网；**堆 ≤ 31GB 保 compressed oops**、剩给文件系统缓存（Lucene 段靠 OS pagecache）；`bootstrap.mlockall` 锁堆防 swap；swap 内核参数（vm.swappiness）；ulimit 64k；GC：CMS 调优示范。

现代翻译（00 表 §4-19）：**31GB 法则仍被官方引用**；捆绑 JDK、G1→8.x 默认、9.x 世代 ZGC（⚠️ 转述发布材料）；mlockall → `bootstrap.memory_lock`；"SSD+少内存"的书中倾向被对象存储分层（searchable snapshots）部分改写。

### 5. 生命周期操作剧本

- **滚动重启**：`_cluster/reroute` 排干→重启→回血（书代无 _shutdown 的完整仪式）；
- **snapshot/restore**：仓库注册（`path.repo`）、SLM 前身的手工 cron；**注意书中警告：snapshot 不是备份"分片"而是备份"索引逻辑内容"**（跨版本兼容性由此来）；
- **升级路径**：大版本升级必须先走"重建索引/别名切换"（[10 章](10-索引管理与调优.md)）——"升级=迁移"在 8/9 时代依旧官方口径（✅ https://www.elastic.co/docs/deploy-manage/upgrade ），且现代有 **Upgrade Advisor** 预检工具 ⚠️ 转述；
- **监控**：`_nodes/stats`、`_cluster/stats`、slowlog、head 插件（1.x 的 HQ 时代）→ 现代 Elastic Agent/Metrics 栈（⚠️ 转述）。

### 6. 上线前清单（书中 Checklist 的 2026 重印版）

最小三主、专用主节点、协调层隔离、感知分机架、水位线校准、熔断默认核对、slowlog 常开、snapshot+SLM 日备、ILM 热温冷、安全默认开（书中"裸奔+网络隔离"的做法今天官方明确反对 ✅）、压测按"索引峰值+搜索 P99"双负载。

## 6.1 故障剧本清单（17 章推演的完整目录，⚠️ 按书列点重构）

1. 单 data 节点优雅下线（重启前不排干）→ 副本升主→恢复→**可避免的黄/红**；
2. 单 data 节点硬崩 → 同上但 recovery 流量冲击；
3. 无副本索引 + 节点丢 → **数据真丢**（书中把"replicas≥1 或接受丢"列为上线第一问）；
4. 主节点挂（法定数健在）→ 秒级重选举、集群状态重发布；
5. 主节点挂（quorum 失）→ 全集群拒绝发布，**写入停摆但查询活着**（状态与数据路径分离的设计显形）；
6. 网络分区（多数派/少数派）→ 书代靠 m_m_n 设置防双发布，现代靠 voting config；
7. 僵尸主回归 → 旧状态发布超时自动退位（1.x publish timeout 剧本）；
8. 磁盘写满 → flood-stage 只读块，索引全停（**删数据也解不了锁**，要 `_settings` 手动解锁——18 章清单条目）；
9. GC 长停顿 → 节点被踢出，连锁重平衡雪崩（"堆 31GB + 慢查询熔断"两道防线）；
10. mapping 漂移 → 多索引查询整请求红（[11 章](11-映射与索引的本质.md)纪律的集群级后果）；
11. 副本重建风暴（维护窗口集中重启）→ `max_bytes_per_sec` 节流剧本；
12. 版本混跑（rolling upgrade 中途）→ 功能降级矩阵（书代简表，现代有正式 rolling-upgrade 文档 ⚠️）。

## 6.2 snapshot 的正确心智（18 章最被低估一节）

- 快照是**按段文件的增量逻辑备份**：仓库里存的是"这个索引由哪些不可变段组成"——增量便宜、恢复并行（Lucene 段不可变的红利第三次变现，前两次见 [04/05 章](04-Lucene入门.md)）；
- 仓库类型：shared FS（书中主例）、S3 系对象存储（书代插件生态 → 现代官方 repo）；**"仓库不是同步盘"**：多集群共享仓库的锁与污染警告书代已有；
- 恢复粒度：整索引/别名/部分分片，可改名恢复（reindex 式迁移的官方通道，✅ https://www.elastic.co/docs/manage-data ）；
- 现代继任：SLM 调度、searchable snapshots（备份即冷存储）、CCS 跨集群读（✅ https://www.elastic.co/docs/explore-analyze/cross-cluster-search ）。

## 6.3 容量与预算模板（书中公式的现代重排）

- 磁盘：`源数据 × (1 + _source 副本≈1.1) × (1+副本数) × 1.2 段余量 ÷ 水位线安全系数 0.8`（书代口径 ⚠️ 系数随 codec/版本有出入）；
- 堆：`Σ分片 × 每分片固定开销` 主导 → 分片数是堆的敌人（[13 章](13-均衡集群.md)预算表）；
- 页缓存：覆盖"热分片的 .tim/.doc/.dvd 族"——**热数据=页缓存能罩住的段**，这是全书"内存=缓存"的终极表述；
- 网络：恢复与复制流量分池估算，万兆是书代底线、25/40GbE 是当下通行规格（⚠️ 转述）。

## 跨代误读备忘（本章专属换算清单）

1. `bootstrap.mlockall` → `bootstrap.memory_lock`；`node.max_local_storage_nodes`（书代多节点同机调试神器）→ 8.x 删除（容器时代不再需要）；
2. 书中 `path.repo` 手工仓库 + cron 快照 → 现 SLM/`snapshot_lifecycle`；恢复端点加 `partial`/`include_aliases` 等新开关（⚠️ 转述）；
3. 书代监控主角 Big Head/HQ 插件、Marvel（付费）→ 免费 X-Pack Monitoring → 现代 Elastic Agent/集成资产——**监控从"装什么插件"变成"开什么集成"**；
4. 1.x 安全章（Shield）整章为化石：现代 security 内置（角色/空间/API Key），书中"靠网络隔离裸奔"在 8.x 默认 TLS 下反而"跑不起来"——按 [00 §4-18](00-总览与阅读地图.md) 读；
5. JVM 参数文件位置/旗标（`ES_JAVA_OPTS`、jvm.options）代际多改：31GB 堆经验与"堆:缓存=1:多数"的资源分配观**照抄仍对**；
6. 升级剧本：书中"滚动升级 1 个小版本"→ 现代跨大版本升级官方路径是 **8.x 全量 reindex 迁移 + Upgrade Advisor 预检**，1.x/2.x 的集群不可能滚动追到 9.x——**这就是"书止于 2.x"的物理含义**（✅ https://www.elastic.co/docs/deploy-manage/upgrade ）；

## 核心概念速览（中英对照）

- **僵尸主** — Zombie master：过期主发布旧状态，旧协调层经典病
- **集群状态发布** — Cluster state publication：主→全员的变更广播，超时即事故信号
- **分片恢复流** — Shard recovery：copy/translog 回放，带宽风险源
- **voting configuration（后出）** — 投票配置：书代手调 quorum 的继任者
- **circuit breaker** — 熔断器：堆保护三家族（fielddata/request/parent）
- **compressed oops 31GB** — 堆上限经验法则：跨越 12 年仍有效
- **pagecache 优先** — 堆外内存策略：Lucene 依赖 OS 缓存
- **memory lock** — mlock：锁堆防换页（mlockall→memory_lock 改名 ⚠️）
- **snapshot 仓库** — Snapshot/restore：逻辑备份+跨版本迁移载体
- **滚动重启** — Rolling restart：排干-重启-回血仪式
- **升级即重建** — Upgrade as reindex：别名切换流的原场景
- **slowlog/统计端点** — 观测三件套：_cat/_stats/slowlog
- **专用主节点** — Dedicated masters：三主最小生产单元
