# 14 数据分布、扩展与冗余（print 第 16 章：Distributing Data for Scale and Redundancy）

> 内容锚点（✅ 实抓官方仓库）：040_Distributed_CRUD（"Distributed Document Store"：05_Routing、10_Shard_interaction 等）、410_Scaling、030_Data/10_Index。本章讲路由数学与"为什么写不协调"。转述 ⚠️。

## 1. 路由公式与不可变分片数的真正原因

**`shard = hash(routing) % number_of_primary_shards`**（默认 routing=id）。

书中由此推出两条铁律：
1. 主分片数**建索引后不可改**——改数=重哈希=全部文档重定位，所以 ES 拒绝在线改（与 [10 章](10-索引管理与调优.md)呼应；想"改"只能 reindex/shrink/split API：书代尚无 split，登记对位 ⚠️）；
2. **写入永远一跳定位**：任何协调节点独立算出路由，无需查全局映射表——"无中心路由表"是本章与一致性哈希的共同卖点。

对比 Cassandra 的 token 环/vnode：分区语义同源、元数据路径不同 → [../cassandra实战.md](../cassandra实战.md)。

## 2. "为什么不需要分布式事务"——本章的标题级论证

书中对"索引文档"的成本分析（转述）：

| 步骤 | 是否跨节点协商 |
|---|---|
| 定位主分片 | 否（本地算路由） |
| 写主分片 | 否（单分片内：buffer+translog） |
| 并行转发副本 | 是，但**副本写是"尽力而为"**：失败副本被移出集群，主写不中止 |
| 刷新/合并 | 各分片自治 |

结论原话（意译）："**索引与搜索都是 scale-out 操作：没有跨分片 2PC、没有全局锁**；用最终一致的可搜索性换线性可扩展的写入"。搜索侧同理（[06 章](06-搜索内览.md)两阶段=部分结果归并）。这是"检索系统为何放弃原子性"的最干净表述，直接衔接 [../设计数据密集型应用/07-事务.md](../设计数据密集型应用/07-事务.md)。

## 3. 扩展性来自共享 nothing 的边界

- 分片=自治 Lucene：CPU/内存/磁盘按分片切片，堆内堆外预算可逐分片核算；
- 副本三职责：高可用、读扩展（查询轮转副本）、**复制是"文档级全量重放"**（无主从 binlog，每分片自己跑 [09 章](09-单节点索引与搜索.md)的索引流程）——书代与 MySQL 异步复制的对照（→ [../高性能mysql.md](../高性能mysql.md)）；
- `wait_for_active_shards`/写一致性参数：书中给出"写多少副本才算 ack"的旋钮（现代 `index.write.wait_for_active_shards` 同名 ⚠️）。

## 4. 为什么"实时分析"也归它管

书中演示用 routing 把租户/时间切片钉到分片上获得"单分片查询"性能（`search.routing`、`_routing` 字段），并警告**热点分区风险**（大租户=大分片=节点倾斜）——多租户 SaaS 搜索的分区键设计第一课。

## 4.1 路由的具象算例（⚠️ 转述示意）

设 `number_of_primary_shards=4`：
- `id=user:1234` → `hash % 4 = 2` → 永落分片 2；改 6 主片 → `hash % 6 = 5`——**同一文档两个答案**，这就是"不可变"的全部原因（不是实现懒，是数学不允许）；
- 写入时 `?routing=user_id` 把"同用户文档"钉进同分片 → 查询单分片、聚合免合并——**多租户与事务局部性的来源**；
- 倾斜警报：某租户占 30% 文档 → 其分片体积/查询时延全集群第一——书中"custom routing 双刃剑"的定量版；
- 别名/数据流把"分片数决策"外化成"索引生命周期决策"（[10 章](10-索引管理与调优.md)），现代滚动索引天然"小索引多"，单索引分片数压力大幅下降（⚠️ 转述）。

## 4.2 复制的七步时序与三种失败结局

1. 协调节点 → 主分片；2. 主写 buffer+translog；3. 主**并行**转发副本（bulk 攒批转发是书代性能关键 ⚠️）；
4. 副本各自全量走本机索引流程（**文档复制=重放索引，非字节复制**——与 MySQL binlog/row 的差异点，链 [../高性能mysql.md](../高性能mysql.md)）；
5. 副本 ack 主；6. 主凑齐 `wait_for_active_shards` → ack 协调 → ack 客户端；
7. 未 ack 副本 → 标记 stale → 移出同步组 → 集群另找地方重建副本。

三种失败结局（书中逐一推演）：主崩副本升（**可能丢最后一拍未同步文档**——NRT+尽力而为的一致性账单）；副本慢被踢（读扩展暂时降级）；网络分区（少数侧副本全停写、多数侧继续——由 [13 章](13-均衡集群.md)仲裁层保障不双主）。

## 4.3 "那它凭什么敢叫数据库替代品？"——书外的对位回答

- 书中定位（转述）：ES 适合"搜索+分析"，不适合"系统 of record"：无 join、无事务、复制不保证强一致、mapping 弱类型；
- 2026 年边界未移动反而更清晰：Elastic 官方对 ES 的定义仍是 search & analytics engine（✅ https://www.elastic.co/elasticsearch ），"主库"需求在 DDIA 框架里对应的是"以持久化与并发正确性为核心的存储"→ [../设计数据密集型应用/07-事务.md](../设计数据密集型应用/07-事务.md)；
- 工业常见架构：RDB/文档库为真源、Kafka 广播、ES 做检索投影——**书中"ES 是副本不是原库"的告诫以另一种形态统治至今**。

## 跨代误读备忘（本章专属换算清单）

1. `indices.replica`/type 级路由（1.x 按 type 分链）、`?consistency` 参数——**现代均已不存在**：写一致性旋钮只剩 `wait_for_active_shards`（且只影响"等谁 ack"，不改变尽力而为本质）；
2. 书中"shard 转移=Lucene 文件级 copy + translog 回放"仍是现代 recovery 模型的主干（peer recovery），观测端点从 REST 命令升级为 `?detailed`+`_recovery` 任务 API（⚠️ 转述）；

## 核心概念速览（中英对照）

- **路由函数** — Routing：hash(routing)%主分片数，一跳定位
- **主分片不可变** — Immutable primaries：重哈希禁止在线变的根因
- **尽力而为复制** — Best-effort replication：副本失败即隔离不阻塞主写
- **无 2PC 写** — No distributed transaction：分布式事务的刻意缺席
- **文档级复制** — Document replication：副本全量重放索引而非字节流复制
- **部分结果语义** — Partial results：写 ack/读结果都可"不完整"
- **副本读轮转** — Replica rotation：查询负载均衡的机制
- **热点分片** — Skewed shards：自定义 routing 的倾斜风险
- **wait_for_active_shards** — 写一致性旋钮：书代已有同名思想
- **shrink/split（后出）** — 分片数变更的离线方案：书代缺 split ⚠️
- **共享无架构** — Shared-nothing：分片自治的资源模型
- **最终一致可搜索性** — Eventual searchability：ES 的核心交易（trade）
