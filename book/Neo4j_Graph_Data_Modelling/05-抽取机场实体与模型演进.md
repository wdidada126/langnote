# Ch.5 抽取机场实体与模型演进：全书灵魂（✅ 仓库实证章）

> **证据声明**：英文原题未取得 ⚠️。`chapter_5/snippet/snippet_1..8.txt` + `for_reader/hotels.cqy`（9.5KB，Hotel 全挂 Airport）✅ 实抓。本章是「**属性→实体**」升级重构的完整一手样本：新增 Airport、重挂 360 条航班两端、**删除 180 条旧边**、然后才长出新实体 Hotel。

## 一、重构前的债：Ch.2 故意留的双份真相

Ch.2 的 Flight 同时带着 `source_airport_code:"JFK"` 字符串和挂在 `City` 下的两条边。到本章开头，图里其实有**三套并存事实**：City 边、机场码字符串、（Ch.4 起）Journey 查询。snippet_2 的解法：

```cypher
// snippet_2（✅）：从既有事实派生新实体，全程 MERGE 保幂等
MATCH (source:City)-[:HAS_FLIGHT]->(f:Flight)-[:FLYING_TO]->(destination:City)
WITH source, f, destination
MERGE (source_airport:Airport{code: f.source_airport_code})
MERGE (destination_airport:Airport{code: f.destination_airport_code})
WITH source, destination, source_airport, destination_airport
MERGE (source)-[:HAS_AIRPORT]->(source_airport)
MERGE (destination)-[:HAS_AIRPORT]->(destination_airport);
```

读法：机场码是「**还没当上节点的实体**」，`MERGE on 业务键(code)` 就是它的授封仪式；同时把 City↔Airport 关系（`HAS_AIRPORT`）补成显式边。

## 二、重挂与清债：snippet_3+4 的「先立后破」

```cypher
// snippet_3（✅）：航班两端改挂 Airport
MATCH (f:Flight) ... MERGE (source_airport)-[:HAS_FLIGHT]->(f)-[:FLYING_TO]->(destination_airport)

// snippet_4（✅）：拆掉 City 直挂航班的旧边，并抹掉已完成使命的字符串
MATCH (f:Flight)-[r]-(:City)
DELETE r
SET f.source_airport_code = null, f.destination_airport_code = null;
Output: Set 360 properties / Deleted 180 relationships   ← 一手账本
```

- **顺序即安全**：新边建完、查询验证过（snippet_5 重跑伦敦→墨尔本成功），才 DELETE 旧边——图重构的「双写-切读-清理」三步，与微服务 schema 迁移同构（⚠️ 类比表述）。
- **`Deleted 180 relationships` 的算术**（🔧 推理）：360 Flight × 2 端 = 720 条候选，实删 180——说明作者只清「仍连 City」的那部分旧边（部分航班在 snippet_2 阶段已被模式改写），**账本数字与操作范围必须互相咬合**，这是 snippet 里白送的一课：重构脚本自带影响面统计。
- **字符串清债**：`SET code = null` 把 Ch.2 的冗余双写正式销户。⚠️ 批评位：生产上更稳的是保留一版+打标退役期，一次性 null 掉丧失回滚锚点（本书教学场景可接受，归纳评论）。
- snippet_5：Ch.3 的同一问题改写为 `(:City)-[:HAS_AIRPORT]->(:Airport)-[:HAS_FLIGHT|FLYING_TO*0..6]->(:Airport)<-[:HAS_AIRPORT]-(:City)` ——**模型演进 = 查询模式演进**，两侧要一起付钱（回链 [./03-变长路径与旅程遍历.md](./03-变长路径与旅程遍历.md) 第二节）。

## 三、Airport 当锚，Hotel 落地

```cypher
// hotels.cqy（✅）：新实体直接长在重构后的骨架上
CREATE (hotel:Hotel{_id:"...", name:"Ibis", price:80}) WITH hotel
MATCH (airport:Airport{code:"BOM"}) WITH airport, hotel
MERGE (airport)-[:HAS_HOTEL]->(hotel);
// snippet_8：机场码 IN ["JFK","LAX"] 查两地酒店价
```

- **本章的隐含论点**：有了 Airport 这个「物理世界的锚」，Hotel/Review/AccessGroup（Ch.6/7/8）全部有地方挂。**实体化不是洁癖，是给未来实体预留接口**。
- ⚠️ 可争议决策：Hotel 挂 Airport 而非 City——机场邻域酒店场景成立（书中价格档也确实是转机旅馆味），但「巴黎市中心酒店离 CDG 40km」这类语义就丢了。作者未给辨析文本（不可取证），本目录立场：**用真实查询负载审锚点**（Ch.8 snippet_10/11 的推荐全按 `Airport{code:"IST"/"ORD"}` 圈酒店，说明在他们的负载里机场=城市代理，自洽）。

## 四、🔧 关系式对照：同一场重构在 SQLite 里什么代价（3.45.3，360 航班→26 机场，**非 Neo4j 行为**）

exp.py E4 把本章重构原样翻成 SQL 跑过：建 `airports` 表→`INSERT DISTINCT`→`flights_new(src_airport FK, dst_airport FK)` 整表重建迁移 360 行→`DROP` 旧表：

| 观测点 | 数字/行为 |
|---|---|
| 迁移总耗时 | **2.0ms**（360 行，量级内 SQL 不吃亏） |
| 孤儿防护 | `DELETE FROM airports WHERE code='AP6'` 当场 **`FOREIGN KEY constraint failed`** ——关系引擎**拒绝**你删被引用实体 |
| 图侧对照（⚠️ 转述） | snippet_4 的 `MATCH (f)-[r]-(:City) DELETE r` **主动删边不受「FK」拦**——Neo4j 无强制外键语义，删除合法性全靠查询写对；想拦要用应用层/约束过程（5.x 无原生 FK 约束 ⚠️ 转述+手册） |
| 「先清引用再删父」 | 复刻 Neo4j 双写-切读-清理序：先 `UPDATE flights_new SET src/dst=NULL WHERE 'AP6'`（0.34ms）再 `DELETE airports` ——两世界各自的手艺，方向相反：**SQL 债由约束强管，图债由纪律自管** |

结论限定在「重构手感」层：FK 拦截给关系模型兜底，图模型把这份兜底换成了snippet_5 式的遍历表达力（代价模型理论源 [../Graph_Databases_2e/02-关联数据的存储选择.md](../Graph_Databases_2e/02-关联数据的存储选择.md)）。

## 五、本章反模式清单（✅ 数字/一手 + ⚠️ 归纳混合）

- 反模式⑩：**属性养到该当实体还不放**（`source_airport_code` 被查询 WHERE 用过的那一刻就该升格；本书在 Ch.5 才动，前四章的查询都在替这笔债打滚）。
- 反模式⑪：**破而不立或立而不破**。snippet_2/3（立）与 snippet_4（破）成对出现才是完整迁移；只立新不删旧=双写永挂，只删旧没验证=断读。
- 反模式⑫：**删改无账本**。「Set 360 / Deleted 180」的输出面统计=迁移影响面快照；5.x 时代等价物是 `COUNT{}` 子查询+查询洞察 ⚠️（TDG Ch.11 对位，[../Neo4j_The_Definitive_Guide/11-可观测性：指标日志与查询洞察.md](../Neo4j_The_Definitive_Guide/11-可观测性：指标日志与查询洞察.md)）。
- 反模式⑬：重构不重跑回归查询——本章作者每改一步就重放 Ch.3 路径查询（snippet_5 即旧题重解），最便宜的回归测试。

## 核心概念速览（中英对照）

- **属性→实体升级** — Property-to-Entity Promotion：字符串码 `source_airport_code` 升格为 Airport 节点，本册冠名级动作。
- **先立后破** — Dual-Write Then Cutover：snippet_2/3 立新、验证、snippet_4 破旧的迁移序。
- **双写-切读-清理** — Expand/Backfill/Migrate/Rollout 的图版：与 schema-evolution 四步法同构 ⚠️ 类比。
- **MERGE 派生实体** — MERGE on 业务键去重建 Airport，重放安全。
- **影响面账本** — Migration Metrics：`Deleted 180 relationships / Set 360 properties` 输出一手留痕。
- **锚点实体** — Physical Anchor：Airport 成为 Hotel/AccessGroup/推荐的挂载点。
- **查询模式同步演进** — Query Co-Migration：snippet_5 旧题重解=回归测试。
- **无外键世界** — No Enforced Referential Integrity：删边合法性靠纪律，FK 拦截是关系模型专属（🔧 E4 实证）。
- **代理键 vs 自然键** — Hotel 用 `_id`、Airport 用 `code` 自然键——按实体来源选键（⚠️ 归纳）。
- **负载审锚** — Workload-Driven Modeling：Hotel 挂 Airport 是否合理，由 Ch.8 查询形态裁决。

## 最新演进与工业实践

- **工具化**：2016 年手写 MERGE 迁移脚本 → 今天的标准路径是 **Neo4j Bloom + Data Modeling 课的「设计-预览-导入」流**（✅ https://neo4j.com/product/bloom/ 、https://graphacademy.neo4j.com/courses/data-modeling/ ）；关系库→图的模式搬运有官方 migration 语料 ⚠️（厂商文档叙事）。
- **约束语法**：`CREATE CONSTRAINT ON (airport:Airport) ASSERT airport.code IS UNIQUE` → `REQUIRE ... IS UNIQUE`（✅ https://neo4j.com/docs/cypher-manual/current/schema/constraints/ ）；5.x 还有 `CREATE BLOCK FOR ...` 等存在性/属性约束族可兜「立而不破」类事故 ⚠️（细节以手册为准）。
- **在线迁移**：大库重挂边在 5.x 用 `CALL{} IN TRANSACTIONS` 分批 + 查询洞察盯展开量（[../Neo4j_The_Definitive_Guide/04-建模演进：重构索引与Genre.md](../Neo4j_The_Definitive_Guide/04-建模演进：重构索引与Genre.md) 同款手艺）；停机窗口迁移→近零停机是 2017→2025 的最大运维差异 ⚠️ 转述。
- **参照完整性讨论**：GQL/Cypher 社区对「图上的外键/引用约束」的路线争论持续（无强制 FK 仍是属性图现状 ⚠️），本册 E4 的「两世界补偿机制对照」是该议题的最小实验。
