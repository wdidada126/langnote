## 二、属性图（Labeled Property Graph）最小术语表

以本书旅行域为样本（术语定义域外通用，正式定义见 GD2e 链接）：

- **Node 节点**：实体锚点。`Flight{code:"AA9", carrier:"American Airlines", duration:314, departure:1300, arrival:114}`。
- **Label 标签**：节点类型集。一个节点可多标签——Ch.7 snippet_6 `MATCH (city:City),(country:Country) SET city :Region, country :Region`（`Labels added: 26`）是全书最强的多标签证据，City 同时是 City 和 Region。
- **Relationship 关系**：有向、有类型、可带属性。`(source:City)-[:HAS_FLIGHT]->(flight)-[:FLYING_TO]->(destination)`——注意本书偏爱「关系链穿过实体」（Flight 本身是节点而非边上的属性，这一决策 Ch.2 就做出、Ch.3/5 全程受益）。
- **Property 属性**：挂在节点/关系上的键值。**属性不能独立查询**——这是 Ch.5「把 `source_airport_code` 字符串升级为 Airport 节点」演进的动机。
- **Path 路径**：`snippet_1` 的 `path = (london)-[:HAS_FLIGHT|FLYING_TO*0..6]->(melbourne)`，类型交替 + 变长。
- **Id 与业务键**：输出里 `Node[1]{...}` 是内部 id；本书工程纪律是**永远用约束保护业务键**（`_id`/email/code），内部 id 不外泄——snippet 全章贯彻。

## 三、这本书的世界观主张（从代码文本归纳，⚠️ 归纳非转述）

1. **关系即数据（relationships as data）**：`HAS_FLIGHT`/`FLYING_TO` 二元关系把「航班连接」从外键提升为可遍历对象；Ch.4 更进一步把「一次订票」物化成 `Booking` 节点（事件→实体）。
2. **方向是建模决策不是物理事实**：snippet_11 用 `-[:FLYING_TO]-(destination)` 少写一个 `>`，Neo4j 直接**拒绝**并给 WARNING——3.x 起 CREATE 只认有向关系；后续查询仍可用无向 `-[:r]-` 匹配（Ch.8 snippet_4 `(:Flight)-[r]-(airport)`）。作者把这次报错原样收进 snippet，⚠️ 推定正文用它的教学意味很足：**图模型的「语法严格性」逼你把方向想清楚**。
3. **约束先行**：每章新实体的第一个语句都是 `CREATE CONSTRAINT`（全书约束 12+ 个），建索引在批量导数之前——与 #88 TDG Ch.4「索引先行」结论跨书一致（见 [../Neo4j_The_Definitive_Guide/04-建模演进：重构索引与Genre.md](../Neo4j_The_Definitive_Guide/04-建模演进：重构索引与Genre.md)）。
4. **模型会被反悔两次**：Ch.5 把 Flight 上的机场码抽成 Airport 实体并重挂全部边；Ch.8 snippet_9 给全部 159 条 Review 回填 `overall_rating` 属性（`Properties set: 159`）——**演进不是事故，是本书的主线剧本**。

## 附四：初学者高频误解纠正（⚠️ 教学加工，非原书内容）

- 误解 1：「图数据库=不用 schema」。正解：本书每章第一条语句都是约束——图弱化的只是**外键联表**，不是**键纪律**。
- 误解 2：「节点越多越好」。正解：Ch.2 故意让 country 停留在属性层，实体化要等查询负载逼（Ch.5/7 两次还债就是「早建不如该建」的对照实验）。
- 误解 3：「关系方向无所谓，反正能反向查」。正解：CREATE 强制有向（Ch.2 snippet_11），方向承载业务语义（谁回复谁/谁订的票），写反一处、读错一章。
- 误解 4：「Neo4j 慢查询是索引没建够」。正解：先看看是不是 god node/无界变长（本册 03/07/08 三章的 🔧 数字都指向度分布而非索引）。
- 误解 5：「3.x 的书 2026 年不能看」。正解：本册的建模决策剧本（属性→实体、事件物化、约束先行、演进收网）零版本依赖；要换的只有语法糖——每章演进节已列对照卡。

## 核心概念速览（中英对照）

- **属性图模型** — Labeled Property Graph (LPG)：节点/关系皆一等公民、各带标签/类型与属性的图数据模型。
- **节点** — Node：实体锚点，如 `Flight{code:"AA9"}`，内部 id 不外泄、业务键靠约束保护。
- **标签** — Label：节点类型集，可多标签；本书 Ch.7 用 `SET city :Region` 追加。
- **关系类型与方向** — Relationship Type & Direction：`HAS_FLIGHT`/`FLYING_TO`；3.x CREATE 强制有向（snippet_11 告警实证）。
- **属性** — Property：节点/关系上的键值；「属性不可独立遍历」是 Ch.5 实体化演进的根因。
- **业务键约束** — Uniqueness Constraint：`CREATE CONSTRAINT ON (n:L) ASSERT n.k IS UNIQUE`（旧式），本书每章第一句。
- **范围索引** — Range Index：`CREATE INDEX ON :City(country)`（旧式），非唯一属性的检索加速。
- **事件物化** — Event Reification：把「订票/行程」从外键组合升格为 `Booking`/`Journey` 节点（Ch.4）。
- **演进式建模** — Evolutionary Modeling：先跑通再重构，Ch.5 抽 Airport、Ch.8 回填属性为标志事件。
- **neo4j-shell** — Neo4j Shell：3.x 时代交互客户端，本书 `find . -name "*cqy" -exec neo4j-shell --file {} \;` 的加载方式即其时代指纹。
- **精读重构** — Close-reading Reconstruction：本目录体裁名——基于目录/代码/公开资料的再组织，非原书复制。
- **三态标注** — Evidence Tagging (✅/⚠️/🔧)：实证/转述推定/本机类比实测的强制分层记法。

## 最新演进与工业实践

- **术语层**：LPG 概念在 2024 年有了国际标准背书写——GQL（ISO/IEC 39075:2024）的图数据模型章节；Cypher 对 GQL 的符合性声明见 https://neo4j.com/docs/cypher-manual/current/appendix/gql-conformance/ （200 ✅，访问 2026-09-27）。本册 3.x 语法↔标准语义的差异以该附录为准，⚠️ 不逐条展开。
- **语法层**：`CREATE CONSTRAINT ... ASSERT` 已换代为 `CREATE CONSTRAINT ... REQUIRE ... IS UNIQUE`（✅ https://neo4j.com/docs/cypher-manual/current/schema/constraints/ ）；`neo4j-shell` 与 `curl | bash` 时代客户端整体退役，交互入口变为 `cypher-shell` 与 Neo4j Browser；本册所有 `.cqy` 文件直接投喂新版会报错——「概念可移植、语句需翻译」是本册一切章文件的标准读法。
- **工具层**：2016 年拿白板讲 LPG、2025 年有官方可视化建模工具 **Bloom**（https://neo4j.com/product/bloom/ ，200 ✅）与 GraphAcademy 免费 **Data Modeling** 短课（https://graphacademy.neo4j.com/courses/data-modeling/ ，200 ✅）——本书「咨询式建模」体裁的产品化后继者；工业实践上「建模先行 + 业务键约束 + 演进剧本」三件套已是 Neo4j 解决方案架构师方法论文的标准动作 ⚠️（厂商叙事，转述）。
- **理论层**：多标签、类型交替路径（Ch.3）等概念的形式化与代价分析，盘上对位 [../Graph_Databases_2e/03-使用图进行数据建模.md](../Graph_Databases_2e/03-使用图进行数据建模.md)；2025 后生产案例与向量混合检索见 [../Neo4j_The_Definitive_Guide/00-总览与阅读地图.md](../Neo4j_The_Definitive_Guide/00-总览与阅读地图.md)。
