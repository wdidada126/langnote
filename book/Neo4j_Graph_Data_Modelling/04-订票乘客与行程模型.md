# Ch.4 订票乘客与行程模型：事件物化与幂等写入（✅ 仓库实证章）

> **证据声明**：英文原题未取得 ⚠️。`chapter_4/for_reader/users.cqy`、`bookings.cqy` 与 `snippets/snippet_1..8.txt` ✅ 实抓。本章把 Ch.2/3 的「航班世界」接上「人的世界」：User/Booking/Passenger/Journey 四元结构 + 一套 MERGE 幂等写入法。

## 一、图长什么样：一次订票 = 一个事件节点簇

```cypher
// bookings.cqy 骨架（✅ 原文摘录）
CREATE CONSTRAINT on booking:Booking ASSERT booking._id IS UNIQUE;
MERGE (user:User{email:"john.doe@gmail.com"})
MATCH (f1:Flight{code:"UA49"})
MERGE (p1:Passenger{email:"vishal.p@gmail.com"}) ON CREATE SET p1.name="Vishal Punyani", p1.age=30
MERGE (user)-[m:MADE_BOOKING]->(booking:Booking{_id:"b5489547-...", booking_date:1417790677.274862, year:2014, month:12, day:5})
// ...booking 再挂 HAS_PASSENGER→Passenger、HAS_JOURNEY→Journey、Journey-[:BY_FLIGHT]->Flight
```

模式识别（⚠️ 归纳为通用口径）：**Booking 是把「User×Flight×Passenger×日期」这个多元关系降二元化的枢纽节点**——关系数据库里它是「订单主表+明细表」两张表，图里它是一个带属性的节点向外伸三条边。这就是 Ch.2 判定口诀「属性有查询价值→节点」的最强案例：订单要按日期切片（snippet_8 `WHERE j.date_of_journey >=1418055307`）、要聚合出票量（Ch.8 snippet_12 `booking.month` 分布），当然配当实体。

## 二、四个决策逐条拆

1. **`_id` 用 UUID + UNIQUE 约束**（snippet_3 ✅）：订票是机器生成的流水，没有自然键——与 Ch.2 City 用 name 形成对照。**代理键的入场券：无稳定业务标识 + 高频写入**。
2. **`MERGE ... ON CREATE SET` 全程幂等**（snippet_5 ✅ 带注释的「教科书段」：先拿 flight 和 user、再建 booking、再 MERGE 乘客）：同一脚本重跑不重样——`.cqy` 文件要支持 README 那种 `find ... -exec neo4j-shell --file {} \;` 全库重放，幂等是**工程纪律而不是语法炫耀**（对应 5.x 的 `MERGE` 约束：对 `MERGE` 的模式部分必须有索引/约束支撑，否则锁扫描——✅ 手册约束页旁证 ⚠️ 细节以手册为准）。
3. **时间是拆property 存的**：`booking_date:1417790677.274862`（epoch 浮点）+ `year/month/day` 三列冗余。3.x 无日期类型的典型求生姿势——range 查询走 `date_of_journey`、分组走 `month`。**代价是双写一致性自己扛**（⚠️ 归纳）。5.x 起原生 `Date()/DateTime()` 属性化，本册 Ch.8 的旺季统计在当年只能靠冗余列，现在一行 `date(datetime(e.stayed_on))` 系的事 ✅（手册 temporal types 页；URL 未单独验证，标 ⚠️ 转述）。
4. **User 和 Passenger 是两个标签、同一个 email**：`MERGE (p1:Passenger{email:...})` 与 `(user:User{email:...})` 并行存在，靠 email 字符串对齐。⚠️ 批评性阅读：这是**实体解析（entity resolution）问题**的当年简化版——#88 TDG 用整章讲 resolved-entity 模式（[../Neo4j_The_Definitive_Guide/08-生产查询模式：子查询与实体解析.md](../Neo4j_The_Definitive_Guide/08-生产查询模式：子查询与实体解析.md)），两册同一坑位的 2016/2025 对照样本。

## 三、查询侧：「我的行程单」怎么读出来

```cypher
// snippet_8（✅）：Mahesh 的 2015 起所有行程，逐日列出航班
MATCH (user:User{email:"mahesh.lal@gmail.com"})-[:MADE_BOOKING]->(:Booking)-[:HAS_JOURNEY]-(j:Journey)
WHERE j.date_of_journey >=1418055307
WITH COLLECT(j) as journeys
MATCH (j:Journey)-[:BY_FLIGHT]->(f:Flight) WHERE j in journeys
WITH j.date_of_journey as date_of_journey, COLLECT(f) as flights
MATCH (source:City)-[:HAS_FLIGHT]->(f)-[:FLYING_TO]->(destination:City) WHERE f in flights
RETURN date_of_journey, source.name as from, f.code as by_flight, destination.name as to;
```

- **模式先行、集合过桥**：`(:Booking)-[:HAS_JOURNEY]-` 用无向匹配吸收方向决策（Ch.2 告警的反面教材使用位）；`COLLECT + IN` 把「多集合笛卡尔」手动圈小——3.x 无 `CALL {}` 子查询时代的防爆炸手艺（#88 TDG Ch.8 的 CALL{} 是其现代替代，✅ 见 [../Neo4j_The_Definitive_Guide/08-生产查询模式：子查询与实体解析.md](../Neo4j_The_Definitive_Guide/08-生产查询模式：子查询与实体解析.md)）。
- **一次答案跨 Ch.2/3/4 三层模型**：User→Booking→Journey→Flight→City×2 ——五段边、全程无表级组合；关系版等价物是 4-way JOIN 的中间积（数量级体感见 [./03-变长路径与旅程遍历.md](./03-变长路径与旅程遍历.md) 第四节 E2 与 [./08-类别标签与推荐分析.md](./08-类别标签与推荐分析.md) 第三节 E1 的 16,477 对）。
- snippet_7：`RETURN b._id` 直接吐一串 UUID——**内部 id 不在输出面出现**，本章再次印证 Ch.1 的业务键纪律。

## 四、🔧 关系侧对照（SQLite 3.45.3，真实跑过，**非 Neo4j 行为**）

用 exp.py 的数据形态核对「事件物化在 SQL 里是什么」：`bookings(id, uid, flight_id, ts)` 表本身就是 Booking 节点的孪生——**关系模型并不缺「事件表」，缺的是让事件表之间免 JOIN 互达的邻接**。本册 Ch.4→Ch.8 的所有查询在 SQL 侧都要把「订单→明细→航班→城市」翻译成一串 FK JOIN，其中「同订单多乘客×多行程×多航班」三层嵌套一对多的中间积规模，与 [./08-类别标签与推荐分析.md](./08-类别标签与推荐分析.md) E1 的 16,477 对同族（🔧 数字见 08 章）。

## 五、本章反模式清单（⚠️ 归纳）

- 反模式⑥：**用边的属性堆事件**。`-[:BOOKED_AT{date,price,...}]->` 一多属性就查不动、多实体就挂不住——Booking 节点是它的解药。
- 反模式⑦：**CREATE 一把梭**。重放即翻倍；本章通篇 MERGE 就是在教幂等。
- 反模式⑧：**裸 epoch 当唯一时间表示**。month/year 冗余是当年无奈，今天用原生日期或至少生成列维护派生（🔧/⚠️ 分述如上）。
- 反模式⑨：**同实体多标签间没有解析策略**。User.email ≡ Passenger.email 全靠字符串巧合对齐。

## 核心概念速览（中英对照）

- **事件物化** — Event Reification：Booking/Journey 节点把多元关系降为二元边簇，等价订单主明细表。
- **枢纽节点** — Hub/Reified Node：多条边围绕一个带属性节点展开的建模形。
- **MERGE 幂等** — Idempotent MERGE：重放安全；`ON CREATE SET` 只在首建时赋值。
- **代理键** — Surrogate Key：UUID `_id`+UNIQUE，vs City 的自然键 name。
- **时间冗余派生列** — Derived Time Properties：epoch+year/month/day 三写，3.x 无日期类型的求生姿势。
- **无向匹配** — Undirected Matching：`-[:HAS_JOURNEY]-` 吸收方向，查询侧的宽容度。
- **集合过桥** — COLLECT + IN Bridge：`WHERE f in flights` 手动限制中间积，子查询的前代手艺。
- **实体解析雏形** — Entity Resolution：User 与 Passenger 同 email 的松耦合，留给 TDG Ch.8 的现代解。
- **全库重放** — Replayable Scripts：README 的 `find -exec neo4j-shell` 决定的工程纪律。
- **锚点-过滤-展开** — Anchor/Filter/Expand：`{email:...}` 锚定→`WHERE date>=` 过滤→逐段展开，本章查询的三段节拍。
- **一源多视图** — Same Entity, Multiple Roles：User/Passenger 双留影，交易域快照模式。
- **注释体剧本** — Commented Playbook：snippet_5 的 `//` 三步曲=订单写入事务八股的图版。
- **锁的二相性** — MERGE Match-or-Create：并发正确性从显式锁转为模式语义 ⚠️。

## 最新演进与工业实践

- **MERGE 安全线**：5.x 手册明确 MERGE 模式部分需索引支撑 + `CREATE CONSTRAINT` 防竞态 ⚠️（✅ 约束页 https://neo4j.com/docs/cypher-manual/current/schema/constraints/ ，竞态细节转述）；导入大流量的当代答案是 `CALL{} IN TRANSACTIONS`（[../Neo4j_The_Definitive_Guide/02-数据导入与批量加载.md](../Neo4j_The_Definitive_Guide/02-数据导入与批量加载.md)）。
- **日期类型**：temporal types（Date/DateTime/Duration）自 Neo4j 3.4 进入 Cypher，2025 年本册的 year/month 冗余列模式应整体退役 ⚠️（版本线 3.4 记自厂商发布史，未逐项机检）。
- **实体解析工业化**：「同人/同乘客识别」现在是 Neo4j 解决方案语料的固定章节（GraphAcademy 建模课 ✅ https://graphacademy.neo4j.com/courses/data-modeling/ 对位）；LLM 辅助实体解析是 2024+ 新战线（#88 TDG 13 章向量线的上游话题，[../Neo4j_The_Definitive_Guide/13-向量检索、LLM摘要与混合推荐.md](../Neo4j_The_Definitive_Guide/13-向量检索、LLM摘要与混合推荐.md)）。
- **订单域图化**：工业上「订票链路+风控」仍是图建模教科书场景 ⚠️（厂商案例叙事转述，无独立机检）。
