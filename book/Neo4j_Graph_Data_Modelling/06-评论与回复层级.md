## 一、评论=又一次事件物化

```cypher
// snippet_2（✅ 原文骨架）
CREATE (review:Review{_id:"d11f1d66-...", value_for_money:2, comfort:3, food:4, service:3,
  stayed_on:1388670309.210871, created_on:1391157765.857148,
  stay_year:2014, stay_month:1, stay_day:2, description:"Was a comfortable stay..."})
WITH review
MATCH (hotel:Hotel{_id:"19397f48-..."}), (user:User{email:"mahesh.lal@gmail.com"})
MERGE (user)-[:WROTE]->(review)-[:FOR_HOTEL]->(hotel);
```

- `(User)-[:REVIEWED{stars}]->(Hotel)` 的诱惑被拒绝：**评论要带四维评分、两个时间戳、自由文本，还要长出自己的回复树**——边属性方案当场不够用。Ch.4 的判定口诀在此复利（回链 [./04-订票乘客与行程模型.md](./04-订票乘客与行程模型.md) 第一节）。
- **`stayed_on` vs `created_on` 双时间**：住的时间与写的时间分离——内容系统的基本功，3.x 没日期类型所以仍是 epoch+拆列冗余（Ch.4 反模式⑧同款，⚠️ 归纳）。
- 评分是**四个 1-5 整数维度**，无综合分：综合分哪里来？本章 snippet_4 在**读时**用 REDUCE 现场平均，Ch.8 snippet_9 把它**物化回填**成 `overall_rating`——一章埋钩、八章收网的全书暗线（🔧 数字锚：159）。

## 二、读时聚合：snippet_4 的「报表查询在图上写」

```cypher
// snippet_4（✅ 原文骨架）：纽约全部酒店按综合分排序
MATCH (city:City{name:"New York"})-[:HAS_AIRPORT]->(airport:Airport)-[:HAS_HOTEL]->(hotel:Hotel)<-[:FOR_HOTEL]-(review:Review)
WITH DISTINCT hotel.name AS hotel_name,
  COLLECT(review.comfort) AS comfort_ratings, ..., COUNT(review) as total_reviews
WITH hotel_name,
  tofloat(REDUCE(total = 0, rating in comfort_ratings | total + rating)) / ...
```

- 模式跨 Ch.2→Ch.5 三代结构（City→Airport→Hotel→Review），**重构过的模型让新查询只是拼积木**——本章是 Ch.5 价值的验收现场。
- `COLLECT`+`REDUCE` 把「分组聚合」放在遍历结果流上做，语义=GROUP BY+SUM；与 SQL 对照的体感规模见 08 章 E1（🔧，同一自连接族）。
- 方向混用示范：`<-[:FOR_HOTEL]-` 反向入边匹配——评论「关于」酒店的阅读向命名，写时方向、读时任意（Ch.2 方向纪律的完整闭环，⚠️ 归纳）。

## 三、回复树：自指关系 + 变长遍历

```cypher
// snippet_6/7/8（✅）：评论挂在 Review 上、也挂在 Comment 上
MERGE (review)<-[:IN_REPLY_TO]-(comment)<-[:WROTE]-(user);        // 一级回复
MERGE (user)-[:WROTE]->(new_comment)-[:IN_REPLY_TO]->(comment);   // 回复的回复——树！
// snippet_9：整棵树一次拉出
MATCH p = (review:Review{_id:"d120a06e-..."})<-[:IN_REPLY_TO*1..]-(comment:Comment)<-[:WROTE]-(user:User)
RETURN p;
```

- **树=带环禁令的递归图**：`IN_REPLY_TO` 是同标签自指关系，`*1..` 变长反向遍历吃整棵子树。关系世界等价物：`parent_id` 邻接表 + 递归 CTE，每层一次迭代、深度不显式写就烧行（🔧 参 03 章 E2 第四行的教训——**无剪枝的层级/路径展开在 SQL 是显式义务**）。
- 树的形态选择 ⚠️ 归纳：本书是**自由讨论树**（回复可挂回复）；若产品只要「评论+平铺跟帖」，深度上界 1 的扁模型更稳——`*1..` 一把梭前先问语义。
- 时间线纪律：comment 只有 `created_on` 无拆列——因为查询只按「树形」消费它，**冗余列只配给要 WHERE/GROUP 的字段**（与 stay_year/month 对照，这是本书「什么时候拆时间」的隐性判例，⚠️ 归纳）。
- 无向 vs 有向：snippet_6 的 `MERGE (review)<-[:IN_REPLY_TO]-(comment)` 明确「回复指向被回复」，Ch.8 拉线程时方向决定 `*1..` 前缀还是反向——树查询先把根与箭头画对（对应反模式②的延伸）。

## 核心概念速览（中英对照）

- **评论实体化** — Review Reification：User×Hotel×时间的三元关系+四维评分+文本，边属性装不下。
- **双时间戳** — Bitemporal-ish Properties：`stayed_on`（事件时间）≠`created_on`（记录时间）。
- **自指关系** — Recursive/Self-Referencing Relationship：`IN_REPLY_TO` 挂同标签 Comment，树与 DAG 只在允许多父一念之间。
- **反向变长遍历** — Backward Variable-Length Match：`<-[:IN_REPLY_TO*1..]-` 一拉到底。
- **路径返回子树** — Path as Subtree：`RETURN p` 把整棵回复树交回客户端。
- **读时聚合** — Read-Time Aggregation：`COLLECT`+`REDUCE`+`tofloat` 现场平均。
- **物化派生值** — Materialized Derived Property：`overall_rating` 由 Ch.8 回填，读时→写时的换代。
- **方向语义命名** — Direction-Semantic Naming：`WROTE`/`FOR_HOTEL`/`IN_REPLY_TO` 箭头皆有读法。
- **新实体先立键** — Constraint-First Per Entity：Review/Comment 进场各一条 UNIQUE，全书肌肉记忆。
- **按需拆时间** — Selective Time Denormalization：被 WHERE/GROUP 的时间才拆列，纯展示留 epoch。
- **事件实体三部曲** — Reification Trilogy：Booking/Review/Comment 三章三连，同一手法变奏。

## 最新演进与工业实践

- **聚合语法**：3.x `REDUCE/FILTER` 家族在 5.x 与小写函数/推导式并存；同型报表今天首选 `count()/avg()` 聚合函数 + `COLLECT{}` 子图模式 ⚠️（✅ 手册 cypher-manual/current 总入口 200，具体页未逐一验证）。
