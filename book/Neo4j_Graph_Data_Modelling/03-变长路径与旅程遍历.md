# Ch.3 变长路径与旅程遍历（✅ 仓库实证章）

> **证据声明**：英文原题未取得 ⚠️，章题按仓库证据逆推。`chapter_3/snippets/` 仅两个 snippet，但都是**全书查询语言的枢纽**（✅ 原文全文见下）。本章正文不可达 ⚠️，内容按 snippet + 上下游章节消费关系重构。

## 一、本章的两句 Cypher（✅ 一手文本）

```cypher
// snippet_1：伦敦→墨尔本，最多 6 段，两种关系交替
MATCH path = (london:City{name:'London'})-[:HAS_FLIGHT|FLYING_TO*0..6]->(melbourne:City{name:'Melbourne'})
RETURN path;

// snippet_2：把路径拆成「城市序列 + 航班序列 + 承运人 + 时刻」四列
MATCH path = (london:City{name:'London'})-[:HAS_FLIGHT|FLYING_TO*0..6]->(melbourne:City{name:'Melbourne'})
WITH
FILTER(f in nodes(path) WHERE  "Flight" IN labels(f)) as flights,
FILTER(city in nodes(path) WHERE "City" IN labels(city)) as cities
RETURN
EXTRACT(city IN cities| city.name) as city,
EXTRACT (flight IN flights| flight.code) as code,
EXTRACT (flight IN flights| flight.carrier) as carrier,
EXTRACT (flight IN flights| flight.departure) as departure, ...
```

## 二、模式语言三件套，为什么本章是枢纽

1. **变长 `[k1|k2]*0..6`**：`City-Flight-City-Flight-...` 的类型交替被压成一条模式。`0..` 下界含零跳意味着「同城即达」也算答案；上界 6 是**成本阀门**（见第四节 🔧）。Ch.5 重构后同一问题改写成 `-[:HAS_AIRPORT]->(:Airport)-[:HAS_FLIGHT|FLYING_TO*0..6]->(:Airport)<-[:HAS_AIRPORT]-`（snippet_5 ✅）——**模型演进会重写查询模式，但不改变问题**：这就是「为什么值得重构」的判据。
2. **`path` 一等对象 + 路径内省**：`nodes(path)`、`labels(f)`、`FILTER`/`EXTRACT` 把返回的图结构当场转成报表列。对应关系世界：SQL 要把递归结果集按节点类型拆列，得靠**深度列+类型列手工 pivot**（第四节 E2 演示里给的就是这个手工环节）。
3. **列表函数 3.x 风味**：`FILTER(...)`/`EXTRACT(...)`/`REDUCE(total=0, x in xs|...)`（Ch.6 snippet_4 再见 REDUCE）——5.x 已换代为 `extract()/filter()` 小写内建 + 推导式，写法同源（✅ patterns/列表函数手册）。⚠️ 具体 5.x 兼容性表未逐项机检。

## 三、遍历语义：trail（路径内关系不重复）

3.x 的 `*0..6` 默认语义是**路径中同一关系不出现两次**（trail），同一节点可以被路过多次（城市经停复访合法、同一段航班重复坐不合法）。这层语义**没有写进任何一个字符里**——它是引擎默认值。建模启示（⚠️ 归纳）：依赖默认语义的查询，升级/换引擎时要显式重审；5.x 文档对可变长模式的唯一性约束有专节表述 ✅（00 第十一节 patterns 链接），对照读。

## 四、🔧 关系式类比：跳数查询的真实成本曲线（SQLite 3.45.3，seed=42，**非 Neo4j 行为**）

方法：内存 SQLite 造 360 条航线边（对齐书中 360 Flight）、26 城，`flights(src,dst)` 双边索引；跑四类查询（脚本 `D:\develops\tmp\dbwave_w5_n4jmodel\exp.py`）：

| 查询 | 结果/规模 | 耗时 |
|---|---|---|
| 直飞 `src=NY AND dst=LA` | 0 条 | 0.17ms |
| 1 转（自连接 `a.dst=b.src`） | 7 条 | 0.09ms |
| 2 转（三连 JOIN） | 134 条 | 0.65ms |
| 递归 CTE BFS 展到深度 6，**无环剪枝** | **12,082,397 行** | **10,574ms** |

读数：
- 固定跳数下 SQL 并不慢——**成本随跳数近似指数爬升**（7→134→…），且每加一跳要**人肉重写 JOIN**。Cypher 把「跳数」收进 `*0..6` 一个 token，工程差异在表达力，性能差异在遍历器策略（⚠️ Neo4j 侧行为为文档转述）。
- 第四行是本节的重头戏：**递归 CTE 不会自动记住「这段边我用过了」**，深度 6 的 walk 枚举直接 1.2e7 行。想要 trail 语义，得自己在递归里背路径数组并做 `NOT contains(edge)` 剪枝——即 SQL 里**默认语义是 walk，显式编码才是 trail；Neo4j 里默认就是 trail**。一句默认值，省掉 12M 行的防御代码，这是本章 snippet 背后最可感的语言红利（对照结论限定在本数据形态 ⚠️，非引擎优劣总判）。
- `path` 拆列对照：上表递归 CTE 若要产出 snippet_2 那种「城市串+航班串+承运人串」，需要 depth 列排序 + group_concat 手工拼装，且不保证顺序正确——图路径返回即带序（⚠️ 转述）。

## 五、建模侧的承接：为什么 Ch.2 的二段式让 Ch.3 成为可能

- 若 Flight 做成边属性（`(:City)-[:FLIGHT{code,duration}->(:City)`），变长遍历依旧可写，但 snippet_2 的 `nodes(path)` 拆列变成 `relationships(path)` 拆列，且**中转信息（承运人时刻）与路径拓扑混在边上**，Ch.5 的 Airport 升级将无路可走。Ch.2「事件实体化」+ Ch.3「变长遍历」是一组配套决策（⚠️ 归纳）。
- 反模式⑤：**无界变长 `*`（不带上下界）**——在本图密度下等价于第四节的 12M 行事故。上界当预算用，是 2016 年薄书没明说、但数据替它说完的一句话（🔧 数字见上表）。

- `(london:City{name:'London'})`：锚点走 name 上的 UNIQUE 约束（Ch.2 snippet_1 所立）。
- `-[:HAS_FLIGHT|FLYING_TO*0..6]->`：一个中括号里叠三层语义——类型并集（`|`）、长度区间（`0..6`）、方向（`->`）；`0` 让「同城」成为合法零跳答案。

## 附二：3.x→5.x 阅读对照卡（本章涉及）

| 书中写法（✅ 3.x 原文） | 现代等价（✅/⚠️） |
|---|---|
| `FILTER(x in xs WHERE ...)` | 列表推导 `[x IN xs WHERE ...]`（✅ 手册函数族页，200 见 00 第十一节） |
| `EXTRACT(x IN xs| f(x))` | `extract(x IN xs | f(x))`/推导式（✅ 兼容线 ⚠️ 细节以手册为准） |
| `RETURN path` 看 ASCII 图 | Browser/Bloom 可视化（✅ Bloom 产品页 200）；`length(p)` 等谓词仍成立 |
| 无界 `-[*]-` 可用 | 生产红线：显式上界 + `PROFILE` 验证展开量 ⚠️ 实践规范 |

**预算公式（🔧 本册数据外推法，⚠️ 非精确模型）**：设平均出度 d、上界 k，则无剪枝 walk 枚举 ≈ d^k——本图 d≈14（360 边/26 城）、k=6 → 14^6≈7.5e6，与实测 1.2e7 行同数量级（双向边计入）；k 每 +1，成本 ×14。**把 `*0..6` 改成 `*0..8` 之前，先默念这个乘法**。对照实验建议：把 exp.py 的深度改 5 重跑，行数应缩 ~14 倍（读者可自行复现，脚本在 tmp 目录）。

**snippet 之外的一问**（⚠️ 推想原书正文话题位）：为何选「6」？城市对间 360 条航线的玩具图上，1 转基本全覆盖，6 已属宽裕——上界取「答案可达 + 常数余量」而非「越大越保险」；保险是加在 `WITH ... LIMIT` 与超时上的。

**术语钉**：本章遍历的问题在运筹学里是 route search（受限跳数可达），在图数据库产品叙事里常被「relationship-heavy queries」 umbrella 覆盖；盘上两册分别的正式处理——GD2e 给代数、TDG 给 PROFILE——见第五节互链，本册只贡献一个「模式语言侧」的最小样本。

## 核心概念速览（中英对照）

- **变长路径模式** — Variable-Length Path：`[:HAS_FLIGHT|FLYING_TO*0..6]`，类型交替+跳数区间。
- **上界即预算** — Upper Bound as Budget：无界展开在真实密度下的指数灾难（🔧 12M 行实证）。
- **trail 默认语义** — Uniqueness of Relationships in a Path：同路径关系不复用；SQL 递归 CTE 默认无此保险。
- **路径变量** — Path Variable：`path = (...)` 让遍历结果一等可内省。
- **路径内省** — Path Introspection：`nodes(path)`+`labels()`+`FILTER/EXTRACT` 现场把图拆成报表列。
- **类型交替遍历** — Alternating Type Traversal：City/Flight 两层节点换来的单模式表达。
- **锚点唯一化** — Anchor Uniqueness：首尾 `{name:'London'}`/`{name:'Melbourne'}` 走索引，中段纯邻接。
- **模型-查询耦合** — Model-Query Coupling：Ch.5 重构后本章模式被改写（snippet_5），演进要付查询迁移成本。
- **walk vs trail** — Walk vs Trail：枚举语义之差，12,082,397 行 vs 受控展开的鸿沟（🔧，非 Neo4j 行为）。
- **REDUCE/FILTER/EXTRACT** — List Functions：3.x 大写函数族，5.x 换小写与推导式。
- **可达性 vs 最优性** — Reachability vs Optimality：模式遍历答「可达与枚举」，最短路交给算法库——本册止于前者。

## 最新演进与工业实践

- **语法**：可变长模式在 GQL 标准（ISO/IEC 39075:2024）中有对应子语；Cypher 手册模式总览 ✅ https://neo4j.com/docs/cypher-manual/current/patterns/ （GQL 符合性附录 https://neo4j.com/docs/cypher-manual/current/appendix/gql-conformance/ ，均 200 ✅）。
- **语义显式化**：现代 Cypher 对路径内关系/节点唯一性的控制粒度更细（如节点重复约束谓词方向的能力持续增补）⚠️ 演进细节未逐项机检，迁移以手册为准——本书 `*0..6` 的基本形态今日原样可用。
- **函数换代**：`FILTER/EXTRACT/REDUCE` → `filter()/extract()/reduce()` 兼容线 + 列表推导式；5.x 起 `ANY/ALL/NONE` 谓词族成熟 ✅（手册列表函数页；具体废弃表 ⚠️）。
- **生产姿势变化**：跨城多跳「最短路」在工业系统里更多交给 **GDS 最短路径算法**（https://neo4j.com/docs/graph-data-science/current/ ，200 ✅）而非无界模式展开——模式适合「找一条/枚举小深度」，算法适合「最优+规模」；#88 TDG Ch.12 有对位工程化重述（[../Neo4j_The_Definitive_Guide/12-图数据科学与GDS.md](../Neo4j_The_Definitive_Guide/12-图数据科学与GDS.md)）。
- **性能治理**：变长模式在生产中配 `PROFILE` 看展开行数、配最大跳数策略与 API 层超时——2016 年靠自觉，2025 年靠查询洞察与 Aura 配额 ⚠️（转述）。
