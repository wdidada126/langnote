# 第 2 章 协议构件（Protocol Building Blocks）

> **一句话**：第 2 章是全书唯一的「工具箱章节」——**单向函数、单向哈希、公钥加密、数字签名、伪随机序列生成**这五种零件，第 3 章之后所有复杂协议都只是它们的排列组合。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 2.1 | 协议概念 | 协议是「多方按确定顺序交换消息」；**协议的安全性不能只看单条消息** |
| 2.2 | 用对称密码通信 | 需要分发共享密钥，天然缺少**访问控制**与**不可否认** |
| 2.3 | 单向函数 | 正向易算、反向难算；是公钥密码存在的**唯一理由** |
| 2.4 | 单向哈希函数 | 把任意长度压成定长「指纹」；是 MAC 与签名的地基 |
| 2.5 | 用公钥密码通信 | 解决了密钥分发，但引入了**公钥本身可信吗**的新问题 |
| 2.6 | 数字签名 | 签名的本质是**用私钥「加密」只有自己能验证的一段信息** |
| 2.7 | 带加密的数字签名 | 同时提供保密与签名的组合方式，以及它们的顺序陷阱 |
| 2.8 | 随机与伪随机序列生成 | 整个安全体系最脆弱的一环：**熵不足则一切归零** |

## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### 单向函数：只有「 computable in one direction」才算数

单向函数没有严格数学定义（因为有 P ≠ NP），工程上按「反演代价」理解：

```python
# 教学示意，不参与构建、不编译、不运行
import hashlib

def one_way(x: int, modulus: int) -> int:
    """模幂：正向 O(log e) 次乘法，反向需要求离散对数。"""
    return pow(x, 3, modulus)

def compress(data: bytes) -> bytes:
    """哈希：正向一次扫描，反向要撞生日。"""
    return hashlib.sha256(data).digest()

assert compress(b"hello") == hashlib.sha256(b"hello").digest()
```

### 签名与加密的三种组合方式（2.6 / 2.7）

| 目标 | 做法 | 经典坑 |
| --- | --- | --- |
| 只要签名 | `sign(hash(m))` | 对裸消息签名会吞掉哈希的输入校验 |
| 只要加密 | `enc(pk, m)` | 无完整性，Mallory 可重排 |
| 既加密又签名 | **先签名后加密** 或 **先加密后签名** | 顺序选错会泄露签名者身份或丧失不可否认 |

顺序的本质差别（与第 9 章的工作模式遥相呼应）：

```python
# 教学示意，不参与构建、不编译、不运行
sign_then_encrypt = encrypt(sk, sign(pk_verifier, m))   # 接收方必须先验签
encrypt_then_sign = sign(signer_sk, encrypt(pk, m))     # 若签名值可被中间人替换则危险
```

> 本书用整整一节讲这个，而 2015 年之后的工程结论更狠：**不要自己组合**。AEAD（AES-GCM / ChaCha20-Poly1305）与「encrypt-then-MAC」是标准答案，自己拼 RSA 解密 + 裸 CBC 是填充预言机的温床（见 16 章 POODLE 与 Lucky13）。

### 伪随机序列：安全性的单点故障

第 2.8 节的警示在 2008 年被 Debian 事件验证得彻头彻尾（CVE-2008-0166，随机性被砍成极小空间）：

```python
# 教学示意，不参与构建、不编译、不运行
import os

def csprng_bytes(n: int) -> bytes:
    """唯一正确姿势：用经过认证的加密级 RNG。不要用 random 模块！"""
    if n < 0:
        raise ValueError("negative length")
    return os.urandom(n)

import random as _bad_random          # 只读反面教材，禁止在生产中使用
assert _bad_random.random() != os.urandom(8)   # 前者可被回溯，后者不可
```

三条铁律：

1. **熵源必须超过要生成的密钥空间**；
2. **种子绝不可预测**（Debian 事件的直接原因）；
3. **状态必须保密且周期足够长**——Crypto++ 与 libsodium 的 `randombytes` 都做了种子扩展与定期重播种。

## 版本演进

| 阶段 | 关键差异 |
| --- | --- |
| **1976/1978** | DH 与 RSA 让 2.3/2.5/2.6 从「理论」变成「可实现的模块」 |
| **1996** | 本书成书：2.8 节的 PRNG 讨论止步于 LCG/LFSR 的构造 |
| **1999–2001** | PRNG 的密码学化：状态扩展、seed 拒绝采样、CSPRNG 概念成型 |
| **2008** | **CSPRNG 成为默认**：NIST SP 800-90 系列、eSTREAM 的推荐流密码 |
| **2013–2014** | **Heartbleed** 与 2008 年的 Debian 缺陷一起证明：PRNG 是全局单点故障 |
| **2015** | **RFC 5869 HKDF**、**RFC 7539** 让「从主密钥派生一切」成为标准做法；本书 2.8 节完全没写 KDF |
| **2024** | FIPS 203/204/205 把「用哈希替代乘法群」的构件思想推向后量子 |
| **2025–2026** | 现代实践：用 `randombytes_buf` / `getrandom(2)` / `SecureRandom`，**不再允许应用自己播种** |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：2.6 的「签名 + 加密手工组合」在库层面被封装（Tink、libsodium 的 `crypto_box`），2.8 的 PRNG 则被操作系统接管（`getrandom(2)`、Windows `BCryptGenRandom`）。安全研究的重心已经从「这几个构件对不对」转移到「**组合方式**与**实现细节**」。

| 仓库 | star | 说明 |
| --- | --- | --- |
| `openssl/openssl` | **30844★**（2026-09-25 实测） | `RAND_bytes` / `EVP_DigestSign` / `EVP_Seal*` 的现成构件 |
| `jedisct1/libsodium` | **13962★**（实测） | `crypto_sign` + `crypto_secretbox` 已经替你定好组合顺序 |
| `pyca/cryptography` | **7784★**（实测） | 教学复现本书协议流程最方便的一组 API |
| `golang/go` | **138993★**（实测） | `crypto/rand` 直接走 `getrandom`，省掉播种这一整类 bug |
| `google/tink` | **13536★**（实测） | 「不要自己组合」这条工程原则的库化产物 |
| `C2SP/wycheproof` | **3114★**（实测） | 针对这些构件的**攻击用例集**，可当作算法的回归测试套件 |

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **「签名 + 加密」的顺序被当成风格问题** | 2.7 节把它当组合建议；实际 NIST SP 800-56C 与 RFC 8446 都对顺序有硬性要求，乱序会导致签名泄露或可重放 |
| 🔧 **2.8 节缺少 KDF** | 书里没有 HKDF（RFC 5869），现代实践要求「主密钥 → HKDF → 各用途子密钥」，而不是一个密钥干所有事 |
| 🔧 **PRNG 的「可种植」假设** | 2.8 节仍保留了手动播种的思路；2008 年 Debian 事件后，正确做法是**永不手动播种** |
| **单向函数 = 单向可算** | 2.3 节只给直觉，没有说明「反向难」必须对**所有**求解算法成立（现代研究用「平均情况下的硬度」表达） |
| **公钥可信性被跳过** | 2.5 节讲完公钥加密就转向 2.6，但「我拿到的公钥是谁的」要靠第 7 章 PKI 或第 16 章 PGP 信任网回答 |
| 🔧 **未提 CSPRNG 的「预测阻绝」与「后向安全性」** | 现代要求 PRNG 满足 **forward secrecy**（状态泄露后不能回溯之前的输出），书里的 LCG/LFSR 讨论完全没有这个维度 |
