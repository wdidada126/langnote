## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### 位承诺与公平硬币：所有「公平协议」的原子操作

```
位承诺（commitment）
  A → B : commit(value)     # B 只知道一个承诺值，不知道 value
  A → B : reveal(value)     # 之后 A 不能改口

公平硬币（由双方共同生成一个不可预测的比特）
  双方各自提交一个随机值，异或或相乘后取模，超出一方控制
```

```python
# 教学示意，不参与构建、不编译、不运行
import hashlib, os

def commit(value: bytes) -> bytes:
    salt = os.urandom(16)
    return salt + hashlib.sha256(salt + value).digest()

def revealed(commitment: bytes, value: bytes) -> bool:
    salt, digest = commitment[:16], commitment[16:]
    return hashlib.sha256(salt + value).digest() == digest
```

### 盲签名：签名者看不到内容

```python
# 教学示意，不参与构建、不编译、不运行
def blind(message: bytes, blind_factor: int, n: int, e: int) -> int:
    """用盲因子 r 把消息乘进 RSA 的模幂里，签名者只看到 blinded value。"""
    return (int.from_bytes(message, "big") * pow(blind_factor, e, n)) % n

def unblind(signature: int, blind_factor: int, n: int) -> int:
    """签名者签完 blinded 值后，发起者除以盲因子还原真正的签名。"""
    return (signature * pow(blind_factor, -1, n)) % n
```

> 盲签名是电子现金（6.4）与「CA 预发布证书」的理论基础；今天它最实用的形态是 **PKI 里对 CSR 的盲签**，以及现代匿名（如 e-cash 与凭证系统）。

### 零知识证明的骨架（5.1）

大定理场景：证明者知道一个数 `w` 使得 `y = g^w mod p`，但不想透露 `w`：

```
重复 t 次：
  1. 证明者选随机数 r，发送 R = g^r mod p
  2. 验证者随机发一个 bit 挑战 c ∈ {0,1}
  3. 若在「证明知道 w」的分支，证明者发 s = r + c*w (mod q)
  4. 验证者检查 g^s == R * (g^w)^c (mod p)
```

```python
# 教学示意，不参与构建、不编译、不运行
def zk_prove_once(w: int, g: int, p: int, q: int, challenge: int):
    r = 1 + (w * 0 + 7) % (q - 1)          # 示意用随机数，实际必须 CSPRNG
    R = pow(g, r, p)
    s = (r + challenge * w) % q
    assert pow(g, s, p) == (R * pow(g, w, p)) % p
    return R, s
```

> 1996 年之后的重大变化：**非交互式零知识证明（NIZK）** 用 Fiat-Shamir 变换把交互轮次压成一次哈希；2020 年之后的 **zk-SNARK** 把这个思想做到工程可用，反而回到了本书 5.1 的骨架上——只是把「离散对数」换成了配对友好的曲线。

### 不经意传输与公平交换的困境

```
1-out-of-2 OT（示意）
  发送方给两个候选值；接收方只得到其中一个，发送方不知道是哪个。
  实现方式：用 RSA 的半可逆性（发送方用两个不同的指数），
            或现代用 ECDH + 编码（BC22 之后的实现）。
```

> 本书 4.10–4.11 用「公平硬币 + 位承诺」构造公平交换；**2016 年之后的结论是：在纯对等网络（无可信第三方）下，公平交换或合同签署不可能无条件实现**（Mora-Cantallops 等关于 fair exchange 的不可能性结果）。本节的所有协议因此都必须引入一个「有点可信」的第三方——这也解释了为什么 4.1 的时间戳服务与 4.14 的密钥托管在真实系统里反而活得最好。

## 版本演进

| 阶段 | 关键差异 |
| --- | --- |
| **1985/1986** | 零知识概念（Goldwasser-Micali-Rackoff）与 Fiat-Shamir 变换 |
| **1982/1983** | Chaum 的盲签名与数字现金 |
| **1991** | **Shamir 的 ID-based 密码**（5.4 的理论来源） |
| **1996** | 本书成书：本节全部协议都停留在「本章所列的候选方案」状态 |
| **2001–2004** | Boneh-Franklin 的 **IBE**（5.4 的第一个可实用方案） |
| **2008** | BN 曲线与配对密码学成熟，IBE/身份若干方案可落地 |
| **2010** | **配对友好曲线**（Barreto-Naehrig）标准化后，5.4 才真正进工程 |
| **2016** | 公平交换的**不可能性**结果确立；本书 4.10–4.11 的构造在理论上限被划清 |
| **2018–2020** | **zk-SNARK 工程化**（Groth16、PLONK），5.1 的 DNA 被彻底改写 |
| **2023–2026** | FHE（全同态加密，对应 4.8）进入可部署阶段——Cloudflare/Apple 的隐私计算正是 4.8 的兑现 |

> 一个值得玩味的对比：本书 4.8「在加密数据上计算」在 1996 年只能靠「公钥同态加密」勉强实现，而 2009 年之后 **BFV/CKKS** 等 FHE 方案让它变成现实；**4.14 密钥托管**则几乎原地踏步——Clipper 失败了，但执法接入（law enforcement access）在 2023 年之后的讨论里又回来了。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **「有这么多协议」被误读为「这些都能直接实现」** | 4/5 章的每一个方案都只给出骨架，且多为 1980 年代的手工构造；**没有一个是现代可证明安全模型下被验证过的** |
| 🔧 **公平交换被当成无条件的** | 2016 年前后的不可能性结论说明：4.10/4.11/5.7/5.9 的公平性必须在「某一方可能中途放弃」的现实下重新定义 |
| 🔧 **IBE 被当成「省掉证书」的免费午餐** | 5.4 只讲 Shamir 的构想；第一个可实用方案（Boneh-Franklin）要等到 2001 年，且引入**密钥托管**这一新信任中心 |
| **盲签名的「盲」被当成匿名** | 5.3 的盲签名不等于 sender 匿名；若签名者与消息有关联则仍可追踪 |
| 🔧 **4.14 密钥托管的历史教训被淡化** | Clipper（24.16）实质失败，但本章仍把它作为「一个可选工具」列出；现代评论普遍认为：**托管密钥的工程复杂度被严重低估** |
| **ZK 的「零知识」被宣传成「不泄露任何信息」** | 5.1 的语义是「不泄露额外的知识」，泄露的信息量仍是协议设计的核心指标 |
| 🔧 **未提 FHE/安全计算的实际代价** | 4.8 在 1996 年只是概念；今天 FHE 仍比明文运算慢 3–5 个数量级，工程上只能用于特定场景 |

- **↔ `book/数据库系统概念6/23-XML.md`**：该文讨论 XXE 与序列化攻击，核心是「解析器默认信任外部引用」；4.1 的时间戳服务同样默认「时间源可信」——**信任假设一旦被写进协议，就必须在实现层面复述一遍**，否则就会出现「协议安全、系统不安全」的局面。
- **↔ `book/Java并发编程之美/concepts/` 中的并发模型条目**：位承诺的「先提交后揭示」与并发里的「先写后读、且不可改口」是同一个**原子性**诉求，只是前者抗的是人，后者抗的是调度器。
