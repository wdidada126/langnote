## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### 签名的本质：私钥「加密」只有自己能验证的部分

```python
# 教学示意，不参与构建、不编译、不运行
import hashlib, hmac, os

def sign_hmac_sha256(sk: bytes, message: bytes) -> bytes:
    """对称侧的签名类比：只有持有 sk 的一方能生成这段「消息摘要的掩码」。"""
    return hmac.new(sk, message, hashlib.sha256).digest()

def verify_hmac_sha256(pk: bytes, message: bytes, sig: bytes) -> bool:
    return hmac.compare_digest(sign_hmac_sha256(pk, message), sig)
```

> 第 20 章的公钥版本把上面的 `sk` 换成私钥、`pk` 换成公钥即可——**签名的全部难点不在这段代码，而在「公钥怎么分发与吊销」（07 章 8.4、24 章）**。

### DSA 的签名骨架（20.1）

```python
# 教学示意，不参与构建、不编译、不运行
import secrets

def dsa_like_sign(p: int, q: int, g: int, x: int, k: int, h: int):
    """示意：k 必须是真随机（不能重复！），否则可以从两个签名解出私钥。
       r = (g^k mod p) mod q
       s = k^-1 * (h + x*r) mod q
    """
    r = (pow(g, k, p) % q)
    s = (pow(k, -1, q) * (h + x * r)) % q
    return r, s

def dsa_like_verify(p: int, q: int, g: int, y: int, h: int, r: int, s: int) -> bool:
    w = pow(s, -1, q)
    u1 = (h * w) % q
    u2 = (r * w) % q
    v = ((pow(g, u1, p) * pow(y, u2, p)) % p) % q
    return v == r
```

> 两个致命细节（1996 年的书没有写得这么明确）：
> 1. **k 绝不可复用**——复用 k 时，两个签名可以联立解出私钥 x（这是无数次真实事故的根源）；
> 2. **k 必须使用 CSPRNG**——用非安全随机数生成的 k 会让签名可被追溯（2008 年 Debian 事件之后，DSA 的这一风险被公开讨论过）。

### Fiat-Shamir：从识别到签名的通用转换（21.4）

```
交互式识别：    承诺 R → 挑战 c ∈ {0,1}^t → 响应 s，验证 g^s = R·(g^w)^c
Fiat-Shamir：  把「验证者发的挑战」换成「对承诺 R 做哈希」
               c = H(R)            ← 无信任第三方、无交互轮次
```

```python
# 教学示意，不参与构建、不编译、不运行
import hashlib

def fiat_shamir_challenge(commitment: bytes, context: bytes = b"") -> int:
    """把交互挑战替换为哈希；这正是把识别方案变成签名方案的通用手术刀。"""
    return int.from_bytes(hashlib.sha256(context + commitment).digest(), "big")
```

> **这条变换的影响远超出第 21 章**：今天几乎所有实用签名（Schnorr、Spartan、STARK、多数后量子签名）都靠它把「交互证明」压成「一次哈希」。

### 三者的对比

| 方案 | 数学基础 | 速度特征 | 今天的位置 |
| --- | --- | --- | --- |
| RSA 签名 | 因子分解 | 签名快、验签慢（小 e/d 时可优化） | 仍是主流之一，需 3072 位 |
| DSA/ECDSA | 离散对数 | 签名慢、验签快 | 遗留系统与部分嵌入式场景 |
| **Ed25519（21.3 路线）** | 椭圆曲线（Twisted Edwards） | **签名与验签都快**，且实现简单 | TLS 1.3、SSH、PGP 的现代首选 |
| ML-DSA（FIPS 204） | 模格 | 签名快、签长约 2–3 KB | 后量子签名主力 |

## 版本演进

| 年份 | 事件 |
| --- | --- |
| **1978** | RSA 签名（CACM） |
| **1985** | ElGamal 签名（离散对数签名族，20.4） |
| **1988** | **Feige-Fiat-Shamir**；1990 年 **Guillou-Quisquater**、**Schnorr** 三个识别方案 |
| **1991–1994** | **DSA** 提出并成为 FIPS 186-1；因 RSA 专利争论拖延至 2000 年才被 NSA 接受 |
| **1996** | 本书成书：20 章以 DSA 为主角，21 章以 Fiat-Shamir 系列为主 |
| **2001** | **FIPS 186-2** 加入 ECDSA 与 RSA 签名 |
| **2003** | **Boneh-Venkatesan** 的随机消去让「DSA 的 k 有偏则私钥外泄」被系统研究 |
| **2008** | **Debian 缺陷**使 DSA 的 k 外泄风险公开化 |
| **2009** | **RFC 5656**：SSH 支持 ECDSA |
| **2012** | **RFC 6188 / 6741**：ECDSA 与 Ed25519 进入 OpenSSH |
| **2015** | **RFC 7748** 定义 X25519/X448；**TLS 1.3** 默认 Ed25519 或 ECDSA P-256 |
| **2016** | **EdDSA（RFC 8032）** 成为事实标准签名方案 |
| **2024-08-13** | **FIPS 204（ML-DSA）**：格上签名；**FIPS 205（SLH-DSA）**：哈希签名 |
| **2025–2026** | 混合签名（ECDSA + ML-DSA）在证书体系中试点；「签名长度」成为后量子迁移的现实约束 |

> 第 20、21 章的价值在 2026 年反而更清楚了：**认「谁说的」这件事，从 1988 年的三个识别方案一路走到今天的 Ed25519 与 ML-DSA，中间只有一条主线——把「交互式证明」变成「一次性验证」。**

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **DSA 的「k 随机性」被当作细节** | 20.1 没有强调 k 必须来自 CSPRNG；复用 k 或用弱随机 k 会直接泄露私钥，这是 DSA/ECDSA 历史上最高频的事故 |
| 🔧 **签名可延展性（malleability）** | 20 章没有这个概念；2008 年前后出现的「ECDSA 签名可被篡改而不被发现」提醒我们：**签名必须验证编码规范**，否则 malleable 签名会被用来重放交易 |
| 🔧 **把「识别方案」当成过时的东西** | 21.1–21.3 的三个方案正是今天所有 NIZK 签名的思想祖先；Schnorr 尤其（BIP-340 与 Ed25519 都源于它） |
| **「签名 = 加密 + 哈希」就够** | 缺少对**签名者匿名性/不可否认性边界**的讨论；法律意义上的抗抵赖还要加上时间戳与证书（见 24.1、24.12） |
| 🔧 **未提后量子签名** | ML-DSA（约 2.4 KB 签名）与 SLH-DSA（可达数十 KB）会把签名长度推高一到两个数量级，**这是 2026 年签名方案选型的首要现实约束** |
| **「签名验证通过 = 内容可信」** | 签名只证明「这段字节由某人签过」，不证明签名时内容是那条消息（历史篡改、编辑重签是另一个治理问题） |
| 🔧 **未区分「私钥签名」与「公钥加密」的对称性假设** | 20 章默认读者已经理解 RSA 签名就是「用私钥做 RSA 解密运算」，但这一步对初学者仍是最容易搞混的地方 |
