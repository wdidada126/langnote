## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### Kerberos 的三跳（24.5）：票据授予的完整流程

```
① A → KDC      : 请求「用 K_B 跟我通信」的票（AS-REQUEST，含 A 的身份）
② KDC → A      : {会话密钥 K_AB}pk_A ‖ {A, 有效期}pk_B        （AS-REPLY）
③ A → B        : {A}K_AB ‖ {票据} = {A, 有效期, 会话密钥}pk_B  （TGS/AP-REQUEST）
④ B → A        : {时间戳}K_AB                                  （双向认证）
```

```python
# 教学示意，不参与构建、不编译、不运行
import hashlib, hmac, os

def kdc_issue(shared_pk_as: bytes, target_pk: bytes, identity: bytes, ttl: int):
    """KDC 用「用户与 KDC 的长期密钥」封一封信封，
    里面同时装着给靶服务的票据（靶服务用自己的密钥打开）。"""
    k_session = os.urandom(32)
    ticket = hmac.new(target_pk, identity + str(ttl).encode(), hashlib.sha256).digest()
    envelope = hmac.new(shared_pk_as, k_session, hashlib.sha256).digest()
    return envelope, ticket, k_session

def service_verify(ticket: bytes, identity: bytes, ttl: int, service_key: bytes) -> bool:
    return hmac.compare_digest(ticket,
                               hmac.new(service_key, identity + str(ttl).encode(),
                                        hashlib.sha256).digest())
```

> Kerberos 的三个固有弱点在 1996 年就被作者点出，至今仍是它的主要问题：**① 需要时钟同步（重放保护依赖时间戳）；② KDC 是单点（必须高可用）；③ 口令在客户端从不消失**。后来的 Kerberos v5（RFC 4120）与 FAST 机制都是在给这些问题打补丁。

### PGP 的信任网 vs X.509 的证书链（24.12 / 24.9）

```python
# 教学示意，不参与构建、不编译、不运行
def trust_chain_verification(certificates: list[dict]) -> bool:
    """X.509 路线：证书里写着「谁签的」，一路验到根 CA。
       PGP 路线：没有根，每个用户都可以「证明」别人的密钥。"""
    for cert in certificates:
        if not hmac.compare_digest(cert["signature"], cert["stored_signature"]):
            return False
    return True
```

| 维度 | PGP 信任网 | X.509 / PKI |
| --- | --- | --- |
| 信任根 | 每个用户自己 | 有限的 CA 集合 |
| 撤销 | 广播「撤销声明」 | CRL / OCSP / 短寿命证书 |
| 规模 | 小群体有效 | 大规模、可审计 |
| 失败模式 | 「信任被误传」难察觉 | 「根 CA 被信任」风险集中 |

> **2026 年的答案其实是两者的混合**：浏览器用 PKI（带浏览器内置根库），而 Signal/PGP 用 TOFU（trust-on-first-use）；企业里则用 SPIFFE 一类「工作负载身份」框架，既不是 CA 也不是信任网。

### Clipper 的教训（24.16/24.14）：密钥托管为什么失败

```
Clipper 的设计：                   失败的三条原因：
  加密芯片内嵌一个 Law Enforcement Access Field  ① 芯片被翻版（Skipjack 泄露，13.12）
  执法机关可凭密钥 ID 直接解密                   ②「可审计性」被证明无法真正保证
  声称「可审计」的第三方接入机制                  ③ 算法 Skipjack 本身被反向工程
                                              ④ 消费者转向了「不托管」的 PGP 与 SSL
```

## 版本演进

| 年份 | 事件 |
| --- | --- |
| **1983–1985** | **Kerberos** 在 MIT 诞生（Project Athena） |
| **1988** | **PGP** 由 Zimmermann 发布，随后因「武器出口」被起诉（著名的 PGP 案） |
| **1990** | **PEM（RFC 1421–1423）**；邮件安全的第一次标准化 |
| **1991** | **X.509 证书**体系成型；**PKCS** 系列开始 |
| **1993** | **S/MIME**（RFC 1847/1848）；**PKCS#7** 定义 |
| **1993–1995** | **Clipper / Capstone**（美国政府密钥托管）；1996 年 Skipjack 被泄露 |
| **1994** | **PGP 案结束**（法院认定软件出口不构成武器出口） |
| **1995** | **Netscape** 推出 SSL 3.0；同年 Netscape Navigator 的「40 位出口版」争议 |
| **1996** | 本书成书：24 章的这些方法正是当时的主流 |
| **1999** | **RFC 2459**（X.509 v3 证书路径）；**TLS 1.0（RFC 2246）** |
| **2001** | **9·11 之后美国出口管制放松**（第 25.14 节的前提终结）；NSA 反而转向更严格的技术管控 |
| **2002** | **IETF 的 TLS 工作组成立**；业界开始质疑「密码强度被政治阉割」的旧账 |
| **2005** | **RFC 4120**（Kerberos v5 更新）；**Firefox 加密扩展（GUID 公钥）** |
| **2008** | **Let's Encrypt 构想提出**（2016 年上线）：免费证书 + 自动化，彻底解决 CA 的商业难题 |
| **2013** | **「Doublespend」文件**曝光，NSA 对加密的介入被公开讨论；**Heartbleed** 爆发 |
| **2015** | 出口管制彻底成为历史；**TLS 1.3** 草案开始剔除旧算法 |
| **2018** | **RFC 8446**（TLS 1.3）；PGP 的 **RFC 9580（OpenPGP 经典化）** |
| **2020–2026** | 后量子迁移、CT 日志普及、「数字权利」议题从美国转向全球监管（如欧盟 eIDAS、中国《密码法》2019） |

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **第 25 章的政治前提整体失效** | 25.14 的美国出口管制在 2001 年之后基本失去意义；把它当作「当代政治」阅读会误导，它应被当作**历史文献** |
| 🔧 **Kerberos 被当作「已解决的标准方案」** | 24.5 已点出时钟同步、KDC 单点、口令留存三大问题；今天部署 Kerberos 仍要面对它们，且「域信任」一旦跨出企业边界就极脆弱 |
| 🔧 **PGP 与 X.509 被当成「两种都可行」** | 实际两者在各自场景里几乎不可替代：浏览器必须 PKI，端到端 IM 必须 TOFU；混用的失败案例极多 |
| 🔧 **S/MIME / PEM 的地位被低估** | 电子邮件仍是最高危的传输介质之一；邮件安全在 2026 年的重心已转向 **DKIM/DMARC/MTA-STS** 而非 S/MIME 本身 |
| **「Clipper 失败 = 密钥托管不可行」** | 更准确的说法是「**政府主导的强制托管**失败」；今天的司法接入（law enforcement access）讨论仍会回到这一章 |
| 🔧 **未覆盖 Let's Encrypt 之后的证书生态** | 24.9 讲 CRL/OCSP 时没有 ACME（RFC 8555）与短寿命证书；后者把「吊销」这个难题几乎消解了 |
| 🔧 **未提 CT（Certificate Transparency）** | 证书透明日志（2013 年提出、2018 年 Chrome 强制）是对 24.9「CA 被信任」这一失败模式的直接回答 |
| **把第 24 章当「可复制的实现」** | 这些是 1990 年代的工程样本；今天用它们前必须核对 RFC 与 CVE，尤其是智能卡与硬件部分 |
| 🔧 **TLS 1.0–1.2 的篇幅与 TLS 1.3 的缺席** | 24.x 的实例多来自 SSLv3/TLS 1.0；**TLS 1.3（RFC 8446）** 删掉了静态 RSA 密钥传输、CBC、RC4、静态 DH，这些章节的实例在今天基本不可复用 |
