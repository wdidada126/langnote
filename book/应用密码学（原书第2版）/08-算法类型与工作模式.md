## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### CTR 模式：现代 AEAD 的心脏

```python
# 教学示意，不参与构建、不编译、不运行
import hashlib, os

def ctr_keystream(counter: int, length: int, key: bytes) -> bytes:
    """把 key 与 counter 当作 PRF 的输入，产出密钥流（不调用真实块密码）。"""
    return hashlib.sha256(key + counter.to_bytes(8, "big")).digest()[:length]

def ctr_encrypt(plaintext: bytes, key: bytes, nonce: int = 0) -> bytes:
    out = bytearray()
    for block_no, i in enumerate(range(0, len(plaintext), 16)):
        chunk = plaintext[i:i + 16]
        ks = ctr_keystream(nonce + block_no, len(chunk), key)
        out += bytes(a ^ b for a, b in zip(chunk, ks))
    return bytes(out)

def ctr_decrypt(ciphertext: bytes, key: bytes, nonce: int = 0) -> bytes:
    return ctr_encrypt(ciphertext, key, nonce)   # 流密码的自反性
```

> **CTR 的三条铁律**（第 9 章讲了模式，没把这三句写进正文）：
> 1. **同一个 (key, counter) 绝不可复用两次**——复用即明文异或暴露（见 11 章 nonce 重用事故）；
> 2. 计数器必须**覆盖完整消息**，不能中途重置；
> 3. CTR **不提供任何完整性**，必须与 MAC 或 GCM 组合。

### ECB 的经典失败：「ECB 企鹅」

```
ECB 加密一张大象图片：
  相同的 16 字节明文块 → 完全相同的 16 字节密文块
  => 轮廓、条纹、背景色全部原样保留
  => 攻击者不需要密钥也能看出图片结构
```

```python
# 教学示意，不参与构建、不编译、不运行
def ecb_blocks(plaintext: bytes, block: int = 16) -> dict[bytes, int]:
    """ECB 的致命特征：块重复。出现频率直方图 ≈ 明文统计。"""
    counts: dict[bytes, int] = {}
    for i in range(0, len(plaintext), block):
        counts[plaintext[i:i + block]] = counts.get(plaintext[i:i + block], 0) + 1
    return counts
```

### 完整性：被第 9 章跳过的一半

```python
# 教学示意，不参与构建、不编译、不运行
import hashlib, hmac, os

def encrypt_then_mac(key: bytes, nonce: bytes, plaintext: bytes) -> bytes:
    """encrypt-then-MAC：正确顺序是「先加密，再算 MAC」。"""
    enc = ctr_encrypt(plaintext, key)
    tag = hmac.new(hashlib.sha256(b"mac" + key).digest(), enc + nonce,
                   hashlib.sha256).digest()
    return nonce + enc + tag

def open_it(key: bytes, blob: bytes) -> bytes:
    nonce, enc, tag = blob[:16], blob[16:-32], blob[-32:]
    expect = hmac.new(hashlib.sha256(b"mac" + key).digest(), enc + nonce,
                      hashlib.sha256).digest()
    if not hmac.compare_digest(tag, expect):        # 常量时间比较，绝不用 ==
        raise ValueError("authentication failed")
    return ctr_decrypt(enc, key)
```

> 第 9.11 节只说「如何选模式」，没说「模式必须自带完整性」。现代结论（Rogaway 的《谁怕模式化加密？》）：**语义安全但无完整性的加密方案在主动攻击者面前毫无意义**，必须把 MAC 纳入设计。今天一个库里只有 `AES-GCM`/`ChaCha20-Poly1305` 可用，就没有这个争论。

## 版本演进

| 阶段 | 关键差异 |
| --- | --- |
| **1980** | DES 与 ECB/CBC/OFB/CFB 模式（FIPS 81，1980） |
| **1996** | 本书成书：9.9 只有「Counter Mode」一小节，CTR 尚未成为主流 |
| **1997–2001** | **AES 竞赛**期间，模式研究集中在 CTR/OFB/CBC 的抗攻击性 |
| **2002** | **Vaudenay 的填充预言机**（CBC 解密的错误提示泄露） |
| **2004** | **Chosen-prefix MD5 碰撞**出现；模式层的哈希碰撞威胁被澄清 |
| **2005** | 模式安全的形式化（Rogaway 的 CPA/CCA 与「不可区分性」框架） |
| **2008** | **CCM、GCM、OCB** 等 AEAD 模式进入实用；**ChaCha20**（Bernstein）发布 |
| **2011** | **Lucky13**（CVE-2011-3389）：CBC 填充检查的定时侧信道 |
| **2014** | **POODLE**（CBC 填充预言机 + 降级到 3DES） |
| **2015** | **RFC 7539**：ChaCha20-Poly1305 的 AEAD 标准；**TLS 1.3** 淘汰 CBC 与 RC4 |
| **2016** | **SWEET32**：64 位分组密码在长连接下的生日碰撞（3DES/Blowfish 的软肋） |
| **2021** | **SHA-1 证书退役**（Chrome 2020、2021 彻底禁 SHA-1 签名） |
| **2024–2026** | 后量子 AEAD（ML-KEM + X25519 混合）与更长 nonce 的处理成为模式层新议题 |

> 一条清晰的因果链：本书 9.3 讲 CBC，2011–2014 年 CBC 连出三次事故，2018 年 TLS 1.3 **直接删掉 CBC**——**一种「用了三十年的正确模式」被整个协议族抛弃**，这在工程史上很少见。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **9.11 把「选模式」当成参数问题** | 现实是：无完整性的模式在主动攻击者面前等于没加密；2011 Lucky13、2014 POODLE 都是这一条的代价 |
| 🔧 **CTR 的 nonce 唯一性被轻描淡写** | 9.9 只把 CTR 当作「随机数生成」；**nonce 重用会直接泄露明文异或**，OpenSSL/NaCl/各类库的 nonce 重用事故至今不断 |
| 🔧 **本书没有 AEAD 概念** | 2007 年 Bellare-Hoang-Rogaway 提出的 AEAD，1996 年的书里一个字都没有；今天默认是 `AES-GCM`/`ChaCha20-Poly1305` |
| **「加密压缩数据」的顺序** | 10.6 明确要求先压缩后加密，这条至今有效（云端加密前先压缩也会泄露） |
| 🔧 **10.5 硬件加密的视角过时** | 书中以智能卡与专用硬件为主；2026 年的答案更多是 HSM/KMS + CPU 侧的内存保护，而**内存侧的密钥泄露**（Heartbleed 一类）仍未消失 |
| **「加密存储 = 数据不可读」** | 10.4 忽略了侧信息泄露：文件大小、访问时间、块访问模式都可能泄露明文结构 |
| 🔧 **未提 64 位分组的生日碰撞** | 9.3/9.13 推荐时使用 3DES/Blowfish 时未提示 64 位块的安全上限；SWEET32 之后应明确 64 位块只适合短消息 |
| **「加密流量看不出来」的误解** | 10.7 明明说了流量指纹存在，但后来的 QUIC 加密与 TLS 指纹（JA3/JA4）说明**握手元数据**仍是可观测面 |

## 与其他章 / 其他书的联系

- **→ 本目录 10 章**：9.9（CTR）与 11 章的 PRNG 是同一件事的两面：**密钥流的质量取决于底层 PRNG**。
- **→ 本目录 12 章**：9.11 缺少的完整性，最终由 18.14 的 MAC 与 HMAC 补上。
- **→ `concepts/密码分析与侧信道.md`**：Lucky13 与 POODLE 都是**实现侧**的问题，侧信道章节会展开「为什么 `if (bad) return error;` 这一行就是攻击面」。
- **↔ `book/计算机程序的构造和解释（原书第2版）/`**：9.1 的 ECB「块独立、同样输入同样输出」与 SICP 的**纯函数**同构——纯函数正因为「同样输入同样输出」才可预测，而密码学恰恰需要这种可预测性，却又不希望它被外部观察到；这一矛盾是理解「为什么需要随机 IV」的最好切入点。
- **↔ `book/设计模式GoF/`**：工作模式与《设计模式》的模式是同构的（都是「同一算法的不同变体」），但密码学的工作模式**不能随意组合与嵌套**——装饰者模式在这里失效，因为顺序错了会直接破坏安全。
- **↔ `book/数据库系统概念6/23-XML.md`**：该文讲 XXE 与序列化安全，指出「解析器如何处理输入」决定安全；与 9.2「块重放」对照：**同样的字节块在不同上下文里会携带不同含义**，这正是重放攻击与 XXE 的共同结构。
- **↔ `book/Java并发编程之美/concepts/伪共享FalseSharing.md`**：CTR 的并行性来自「块之间无依赖」，而伪共享说明「看似无关的两块数据放在同一个缓存行会互相拖慢」——密码学要**刻意**打破并行，性能学要**刻意**利用并行。
