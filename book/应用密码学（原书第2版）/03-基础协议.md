# 第 3 章 基础协议（Basic Protocols）

> **一句话**：第 3 章是全书的胜负手——**把第 2 章的零件拼成「认证 + 会话密钥」**，而认证协议的三类经典缺陷（重放、反射、类型缺陷）在这里就已定型，至今仍是绝大多数漏洞的源头。

## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### 三条消息的握手：从 SKIP 到 Needham-Schroeder

```
Alice → Bob     : A, Na                     # Na = 现时（nonce），防重放
Bob   → Alice   : B, Na, Nb, fk(B, Na, Nb)  # 用共享密钥 k 签出的「我确实收到了」
Alice → Bob     : fk(B, Nb)                 # 只回 Nb，证明我也在线
```

这条最朴素的双向鉴别协议能清楚地暴露三类攻击：

```python
# 教学示意，不参与构建、不编译、不运行
class ReplayAttack:
    """重放：攻击者只是把旧消息再发一次。"""

class ReflectionAttack:
    """反射：把发给 B 的凭据原路发回给 A，A 会用自己的密钥解开自己的挑战。"""

class TypeFlawAttack:
    """类型缺陷：消息里的 A/B/Na/Nb 没有区分标签，攻击者可以重排字段。"""
```

| 攻击类型 | 一句话描述 | 修复方式 |
| --- | --- | --- |
| **重放（replay）** | 录下旧消息，在会话中途重发 | 时间戳、nonce、挑战-响应、会话标识 |
| **反射（reflection）** | 把消息发回给发起者自己，让对方「自证」 | 消息里写明自己的身份、双向绑定 |
| **类型缺陷（type flaw）** | 不同语义的字段被互换，协议仍能跑通 | 明确的格式标签与长度前缀 |

### 会话密钥的三条路（3.1）

```python
# 教学示意，不参与构建、不编译、不运行
# ① 对称预置：密钥分发中心的 ST 协议（Needham-Schroeder / Kerberos 的骨架）
# ② 公钥加密会话密钥：A -> B: {Ks}pk_B
# ③ 协商式：A -> B: g^a mod n ; B -> A: g^b mod n ; 共享 g^(ab) mod n

def dh_shared(prime: int, g: int, a: int, b: int) -> int:
    """Diffie-Hellman：两端算出的结果必须相等。"""
    return pow(g, a * b, prime)      # = pow(g, b * a, prime)

assert dh_shared(23, 5, 6, 15) == dh_shared(23, 5, 15, 6) == 2
```

> 注意 ③ 的**中间人问题**：`g^a mod n` 本身不携带任何身份信息，攻击者插在中间各自握手即可。本书在 3.1 与 22.1 两处都讲了这件事，而解决方案（用签名或公钥加密包裹 DH 参数）正是 **STS 协议**和 TLS 1.3 的「签名 + 密钥共享」结构。

### 秘密分割与共享（3.6 / 3.7）

```python
# 教学示意，不参与构建、不编译、不运行
import hashlib, os

def share(secret: bytes, parts: int, threshold: int) -> list[bytes]:
    """Shamir 式 sharing 的骨架：用多项式在有限域上取值。"""
    if not 2 <= threshold <= parts:
        raise ValueError("threshold must satisfy 2 <= k <= n")
    coeffs = [int.from_bytes(secret, "big")] + [int.from_bytes(os.urandom(16), "big")
                                                 for _ in range(threshold - 1)]
    return [hashlib.sha256(str(coeffs).encode() + str(i).encode()).digest()
            for i in range(1, parts + 1)]
```

> 本书 3.6 只演示最简单的分割，3.7 才给出「无需可信第三方」的共享方案；现实中二者都依赖素数域上的多项式求值，而 1996 年的实现没有一个是常量时间的——这是侧信道会撬开的地方（见 `concepts/密码分析与侧信道.md`）。

## 版本演进

| 阶段 | 关键差异 |
| --- | --- |
| **1978–1980** | Needham-Schroeder 与 Kerberos 的雏形（Kerberos 来自 MIT，1980 年代） |
| **1996** | 本书第 3 章：形式化分析（3.4）只介绍到 BAN 逻辑层面 |
| **1997** | Bellare-Rogaway 提出 **CK 模型**，把会话密钥安全讲成可证明的 |
| **1998** | **Kerberos v5** 定型；公钥 Kerberos 的方向被讨论 |
| **2001** | **TLS 1.0** 把 3.3 的握手固化成 RFC 2246 |
| **2011** | **BEAST**（TLS 1.0 的 CBC 生日攻击）；**Lucky13**（填充预言机定时侧信道） |
| **2014** | **POODLE**：CBC 填充预言机 + 降级，直接昭示 TLS 1.x 的设计错误 |
| **2018** | **TLS 1.3（RFC 8446）**：握手只剩一轮，签名与密钥共享绑定，彻底去掉静态 RSA 密钥传输 |
| **2024–2026** | 后量子密钥交换（ML-KEM / X25519 混合）进入 TLS；**「所有会话密钥终将被量子计算机攻破」成为新的设计前提** |

> 一条清晰的线索：本书 3.3 的「鉴别 + 密钥交换」在 22 多年里被重写了三轮，但**三类攻击（重放、反射、类型缺陷）一次都没被淘汰**——它们至今仍出现在每一年的 API 安全报告里。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **形式化分析被当作「协议已证明正确」** | 3.4 节明确只做了介绍；2001 年之后 Buttyán 等人的工作说明形式化工具只能发现**模型里已建模**的攻击，未建模的攻击（如计时侧信道）照样长驱直入 |
| 🔧 **「认证成功」被等同于「对方是本人」** | 3.2 节常见的误读；现代区分 **entity authentication** 与 **key authentication**，别把它们混为一谈 |
| 🔧 **重放防护只看时间戳** | 3.1 里时间戳是选项之一；移动网络与离线系统不能用时间戳，必须用 nonce + 会话标识 |
| **类型缺陷只存在于 1996 年** | 今天它变成了「JSON 字段顺序被重排」「HTTP 头大小写差异」「OAuth 的 scope 串拼接未加分隔符」——同一个错误的现代形态 |
| **3.6/3.7 的分割假设「分发者诚实」** | Shamir 的分享方案本身无法防止恶意分发者给不同份额不同的曲线；现代实现要用 verifiable secret sharing（Feldman / Pedersen） |
| 🔧 **未区分「前向安全性」** | 3.1 的静态 DH / 密钥传输方案没有前向保密；TLS 1.3 强制 **ephemeral** 是多年事故换来的结论 |
| 🔧 **未提 post-compromise security** | 现代协议要求「一次密钥泄露后不会永久破坏后续通信」，本书的国产协议没有这个概念 |

## 与其他章 / 其他书的联系

- **→ 本目录 15 章**：3.1 的密钥交换在 22.1（Diffie-Hellman）展开，22.2（STS）给出「带认证的 DH」的标准形态。
- **→ 本目录 16 章**：3.3 的工程实例就在 24.5（Kerberos）与 24.6（KryptoKnight）；TLS 的实例可看 24.10–24.13。
- **→ `concepts/密码分析与侧信道.md`**：反射攻击与重放攻击的**实现根源**往往是时序与错误提示泄露，侧信道章节有对应内容。
- **↔ `book/Java并发编程之美/concepts/AQS抽象同步队列.md`**：AQS 用 CAS 保证「一次只有一个赢家」，协议里的 nonce 用「一次只有一个新鲜值」保证「只有一次有效」——同属**互斥与新鲜性**问题。
- **↔ `book/Java并发编程之美/concepts/ThreadLocal与内存泄漏.md`**：ThreadLocal 泄漏是「该销毁的资源没销毁」，重放攻击是「该销毁的会话票据没销毁」，都是生命周期管理。
- **↔ `book/计算机程序的构造和解释（原书第2版）/`**：3.4 的形式化推理用 SICP 的**声明式 vs 命令式**语言读很有意思——BAN 逻辑是纯声明式的协议语义，而实现必然是命令式的，两者的落差正是漏洞的温床。
- **↔ `book/数据库系统概念6/`**：3.8「数据库密码保护」的思路（加密索引而保留查询能力）与数据库中同态加密/可搜索加密是同一问题的两条路线，可对照阅读。
- **↔ `book/设计模式GoF/`**：3.3 的握手在代码里常被写成一个个 `State` 对象的**状态机**（状态模式），这解释了为什么 TLS 实现的代码量往往超出算法本身的十倍。
