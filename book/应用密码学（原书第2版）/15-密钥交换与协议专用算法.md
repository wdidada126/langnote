## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### DH 为什么必须「认证」：三种形态

```
① 裸 DH：                   A→B: g^a     B→A: g^b      => 无认证，中间人可插入
② DH + 公钥加密（Key Transport）：A→B: {g^a}pk_B        => 只有 B 能解，但无前向保密
③ DH + 签名（STS / TLS 1.3）：A→B: g^a, sig_A(g^a)     => 双向认证 + 前向保密
```

```python
# 教学示意，不参与构建、不编译、不运行
def dh_exchange(prime: int, g: int, a: int, b: int):
    """缺少认证时，攻击者 Mallory 可以分别与双方握手：
       与 A 用 a'，与 B 用 b'，两者得到完全不同的共享秘密。"""
    return pow(g, a, prime), pow(g, b, prime), pow(g, a * b, prime)

p, g = 23, 5
A_pub, B_pub, shared = dh_exchange(p, g, 6, 15)
assert shared == 2
```

> 第 22.1 节最重要的结论是：**DH 本身完全不携带身份信息**，「中间人攻击」不是 DH 的缺陷，而是「用 DH 搭建协议」时必须显式补上的一步。TLS 1.3 的第三次迭代（2018）正是把这一步写成了强制规则——**删掉静态 RSA 密钥传输、只保留签名的密钥共享**。

### EKE：用口令保护 DH（22.5）

```python
# 教学示意，不参与构建、不编译、不运行
import hashlib

def eke_exchange(pwd: bytes, g: int, p: int, a: int):
    """示意：把 DH 参数用「由口令派生的密钥」加密后再发送。
       注意：口令的最后一位熵决定了整个方案的上限（见 07 章口令哈希）。"""
    key = hashlib.sha256(b"eke" + pwd).digest()
    pub = pow(g, a, p)
    return key, pub
```

> 22.5 的 EKE 在 1990 年代因为实现复杂而沉寂；直到 2010 年代 **PAKE 协议**（SPAKE2、OPAQUE）被标准化，这条路才走通——而 **OPAQUE 已被 OIDC 与 cloud 产品采用**。

### 第 23 章的价值：把协议变成可执行清单

| 协议需求（23.x） | 对应算法要点 |
| --- | --- |
| 秘密共享（23.2） | 素数域上的多项式插值，或 CFRP 方案（无需可信第三方） |
| 公平硬币（23.7） | 双方各自承诺一个随机值，最后公开并异或 |
| 单向累加器（23.8） | 用模幂累积，用于「成员证明」与证书撤销列表 |
| 概率加密（23.15） | ElGamal 的概率性语义安全：同一明文多次加密结果不同 |
| 量子密码（23.16） | 基于单量子态不可克隆；但**只能做密钥分发，不能做签名** |

```python
# 教学示意，不参与构建、不编译、不运行
def probabilistic_encrypt(pk_g: int, p: int, m: int, k: int) -> list[int]:
    """ElGamal 式概率加密：同一条明文重复加密会得到不同的密文，
       这正是「语义安全」与「确定性加密」的分界线。"""
    return [pow(pk_g, k, p), (m * pow(p, k, p)) % p]
```

## 版本演进

| 年份 | 事件 |
| --- | --- |
| **1976** | Diffie-Hellman 提出（22.1 的起点） |
| **1987** | **STS 协议**提出，把签名与 DH 绑定（22.2 的理论来源） |
| **1990** | **EKE**（Belly-Pellow-Maes）提出（22.5） |
| **1992** | **Fortified Key Negotiation**（22.6）与「弱随机源下的安全协商」 |
| **1996** | 本书成书：23.16 已经讨论**量子密码**（当时主要指 BB84 与脉冲） |
| **1999** | **IKEv1** 把 DH 与认证组合起来，成为 IPSec 的核心 |
| **2004** | **Logjam 的先声**：Weak DH 参数被验证（2015 年才爆发为 CVE-2015-4000） |
| **2008** | **RFC 5114** 定义了若干「弱 DH 参数组」——后来成为 Logjam 的靶子 |
| **2013** | 一些国密算法与 MODBUS/ICS 协议被发现用「固定 DH 参数」 |
| **2015** | **Logjam**：512 位 DH 参数可被现成算力攻破；**FREAK**（CVE-2015-0204）暴露出口级 RSA |
| **2018** | **RFC 8446（TLS 1.3）**：只保留「认证 + 临时 DH」一种形态 |
| **2022** | **CNSA 2.0**：后量子密钥交换进入 NSA 套件 |
| **2024-08-13** | **FIPS 203（ML-KEM）**：后量子密钥封装的标准答案 |
| **2025–2026** | 混合 ECDH + ML-KEM 成为主流默认；**「认证 DH」的密钥材料必须双栈共存** |

> **这一章的现代结论**：22.1 之后的所有研究都在回答同一个问题——**「协商出的秘密归谁」**。今天的标准答案是「临时 DH + 签名认证 + 前向保密」，而 1996 年本书给出的方案集合里，真正活下来的只有这一条。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **22.1 的裸 DH 被当成「标准做法」** | 1996 年的语境下 DH 主要用于「混合系统」，但大量 1990 年代的示例代码至今仍在复用，**中间人攻击随之长盛不衰**（2015 年 FREAK 与 Logjam 都与此同源） |
| 🔧 **「DH 参数越大越安全」** | 真正的风险是**参数是否有可疑的小因子**（Logjam：512 位 DH 参数可被现成算力攻破）；必须验证 p-1 与 q 的结构 |
| 🔧 **23.16 的量子密码被当成解决方案** | QKD 只能做密钥分发，**不能做数字签名**，且依赖专用硬件；本书把它与公钥密码并列容易误导 |
| **「双方都算出了相同秘密 = 安全」** | 第 22.1 节的结论说明：共享秘密相同不代表通信双方就是对方；缺少认证的 DH 在中间人面前「仍然算出相同秘密」 |
| 🔧 **EKE/PAKE 的价值被 1996 年低估** | 22.5 的 EKE 当时因实现复杂而沉寂；2010 年代的 OPAQUE/SPAKE2 才真正落地，现在已进入标准化与产品化 |
| 🔧 **未提「前向保密」作为强制属性** | 22.x 的方案集合里混杂着带与不带前向保密的；今天 TLS 1.3 把它写成默认 |
| **「第 23 章 = 可直接复制的代码库」** | 23.x 是**算法要点**而非完整实现；直接用会漏掉参数校验、错误提示统一与常量时间等必要条件 |

## 与其他章 / 其他书的联系

- **→ 本目录 03 章**：22.1 是 3.1 的展开，22.2（STS）是 3.3「鉴别 + 密钥交换」的标准答案。
- **→ 本目录 16 章**：23.16（量子密码）与 TLS 1.3 的实例在那里；Kerberos 的密钥分发是 22.7 的工程化版本。
- **→ `concepts/密码分析与侧信道.md`**：22.6「在弱随机源下协商」——随机源的质量直接决定协商安全，这正是侧信道与熵源的交叉点。
- **↔ `book/计算机程序的构造和解释（原书第2版）/`**：22.1 的 DH 是典型的**交互式计算**——双方各贡献一部分输入并合起来产生同一个输出；SICP 第 3 章讲「流可以表示无限序列」，这里的「密钥流」也是一个「双方各自推进、最终结果相同」的分布式计算；区别是 SICP 的参与者共享同一个求值模型，而 DH 的参与者必须**先在参数上达成一致**。
- **↔ `book/设计模式GoF/`**：22.2 的 STS 与 **Mediator（中介者）** 结构相同——中介者保证双方「都绑定在同一个协调者上」；但密码学要求这个绑定必须**可验证**（签名），否则中介者自己就是中间人，这一点是设计模式的盲区。
- **↔ `book/数据库系统概念6/`**：23.8（单向累加器）用于「成员证明」，与数据库中「索引/哈希用于成员查询」是同构的；而 23.15（概率加密）与数据库同态加密/可搜索加密是同一问题的两条路线。
- **↔ `book/Java并发编程之美/concepts/` 中的并发模型条目**：把 DH 的两次消息交换看作一次「两阶段提交」——两个阶段都必须完成，否则「会话」不成立；而并发里的部分失败会导致不一致，密码学里的部分失败会导致安全性消失。
