## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### LCG 的致命弱点：可被还原

```python
# 教学示意，不参与构建、不编译、不运行
def lcg(seed: int, a: int, c: int, m: int, count: int) -> list[int]:
    out, x = [], seed
    for _ in range(count):
        x = (a * x + c) % m
        out.append(x)
    return out

# 已知连续两个输出即可解出 a、c、m（经典「截断 LCG 攻击」的简化版）
def recover(a: int, c: int, m: int, seed: int, n: int = 3) -> None:
    seq = lcg(seed, a, c, m, n + 1)
    diffs = [(seq[i + 1] - seq[i]) % m for i in range(n)]
    print("输出序列差值：", diffs)
```

> 16.1 的结论用一句话概括：**LCG 的输出是前一个输出的线性函数，所以「过去可以倒推，未来可以预测」**。任何用 LCG 生成密钥的系统，其安全性等于「攻击者不知道你用了 LCG」。

### LFSR 的两种配置与状态恢复

```python
# 教学示意，不参与构建、不编译、不运行
class LFSR:
    """以「Fibonacci 配置」为例：若干抽头做异或后反馈回移位。
           注意：输出是线性函数，因此整体线性组合可被代数求解。"""
    def __init__(self, taps: list[int], init: list[int]):
        self.state = list(init)
        self.taps = taps

    def step(self) -> int:
        bit = sum(self.state[i] for i in self.taps) % 2
        self.state = self.state[1:] + [bit]
        return bit
```

> 「Fibonacci 配置」这个说法正来自 Kahn 的那篇 Fibonacci 文章（本专篇「经典论文」里列出）——**移位寄存器的 taps 选择就是一串 Fibonacci 式的递推系数**。这也是为什么本书 16.2 会顺带提 Fibonacci：它讲的是 LFSR 的代数结构，而不是数字链。

### 流密码的正确用法：密钥流 = PRF(密钥, nonce)

```python
# 教学示意，不参与构建、不编译、不运行
import hashlib, os

def keystream(key: bytes, nonce: bytes, length: int) -> bytes:
    """现代替代方案：用带 nonce 的 PRF 生成密钥流（如 ChaCha20 / CTR 模式的 AES）。
       nonce 与密钥的组合必须唯一。"""
    out = bytearray()
    counter = 0
    while len(out) < length:
        out += hashlib.sha256(key + nonce + counter.to_bytes(8, "big")).digest()
        counter += 1
    return bytes(out[:length])
```

### 对比：1996 年的首选 vs 2026 年的首选

| 维度 | RC4（17.1） | ChaCha20 / AES-CTR |
| --- | --- | --- |
| 设计哲学 | 不规则、面向软件速度 | 规整、可通过 PRF 证明 |
| 状态 | 256 字节 S 盒，可变索引 | 固定状态 + 计数器 |
| 攻击 | 密钥恢复（2005）、偏向性、315 万次即可恢复状态（2013） | 主要威胁是 nonce 重用 |
| 现状 | **RFC 7465（2014）起禁止在 TLS 使用**；浏览器与服务器陆续移除 | TLS 1.3 的默认 AEAD 之一 |

## 版本演进

| 年份 | 事件 |
| --- | --- |
| **1967** | LFSR 与 Fibonacci 递推的结构被形式化（Kahn 的 Fibonacci 文章是通俗侧的经典） |
| **1987** | **RC4 公开**（1994 年流出，作者本人 1995 年在 Usenet 证实） |
| **1990s** | A5/1 用于 GSM；1999 年被 Karachi 与 Briceno 反向工程 |
| **1996** | 本书成书：17.1 单列 RC4 一整节，并称其「似乎是最快的软件流密码」 |
| **1999** | **A5/1 与 A5/2 被攻破**（Briceno、Karachi、Goldberg 的公开分析） |
| **2005** | **Knudsen 等提出 RC4 的状态恢复攻击**；同年 RC4 的密钥恢复被证明可行 |
| **2008** | **eSTREAM**（ECRYPT）结束征集：推荐 HS1/HS2/Rabbit、Salsa20 等 |
| **2008** | **Debian PRNG 缺陷**：OpenSSL 的种子空间被砍到极小，密钥可复现 |
| **2011** | **CVE-2011-3389（Lucky13）** 与 WPA 的 RC4 相关密钥碰撞攻击（7921、401KW） |
| **2013** | **RFC 7465 禁止 RC4**；同年 Knudsen 等给出 RC4 315 万次输出的密钥恢复 |
| **2014** | **Heartbleed**（CVE-2014-0160）：私钥与内存被读走，流密码的前提彻底动摇 |
| **2015** | **RFC 7539**：ChaCha20-Poly1305 成为标准 AEAD |
| **2016** | TLS 1.3 草案明确移除 RC4 与 CBC |
| **2018** | **RFC 8446（TLS 1.3）**：只保留 AEAD，RC4 彻底出局 |
| **2024–2026** | 研究热点转向「**量子随机数发生器（QRNG）**」与后量子伪随机性 |

> 这条时间轴只有一个主题：**一个算法的安全寿命，往往短于它的流行寿命**。RC4 从 1994 年公开到 2014 年被禁用，整整二十年；而它的实际「安全寿命」不足十年。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **RC4 仍被当作「可用」** | 17.1 把它作为主流选择（TLS、WEP、RDP 都用过）；**RFC 7465 起 TLS 全面禁用**，且 2005/2013 两次密钥恢复攻击已给出充分理由 |
| 🔧 **LFSR = 安全随机源** | 16.2 的 LFSR 输出是线性组合，只要拿到 2n 位输出就能解出状态；现代 CSPRNG 必须基于哈希或块密码，而非 LFSR |
| 🔧 **LCG 的「快」被当作优点** | 16.1 讨论的正是它不安全，但历史上仍有大量系统用 LCG 生成「密钥」（Java 早期 `Random` 是最著名的案例） |
| **「级联多个流密码更安全」** | 17.11 明确不代表性增强；若两个发生器线性相关，级联反而放大攻击面 |
| 🔧 **未提 nonce 唯一性这一现代核心议题** | 书中把 nonce 当作「可选的初始化向量」；今天「**每个 (key, nonce) 对只能使用一次**」是密码学里最容易违反、后果最严重的一条 |
| 🔧 **A5 的历史教训被淡化** | 16.5 把 A5 当作「A5 用了很久很成功」；实际它在 1999 年就被攻破，是「**封闭算法的必然结局**」的教科书案例 |
| **「真随机源 = 安全」** | 17.14 指出物理熵源更好，但熵源若被污染（热噪声采样偏差）仍会产出弱随机；现代做法永远是「真随机源 + CSPRNG 扩展」两段式 |
| 🔧 **未覆盖 eSTREAM/ChaCha 的竞赛结论** | 本书 16–17 章的知识在 2008 年 eSTREAM 之后就被系统性替代，这是全书最过时的两章之一 |
