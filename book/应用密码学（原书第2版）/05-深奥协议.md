## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### 选举协议的困境：匿名 vs 可查

```
要求：① 只有合格者投票  ② 每人一票  ③ 选票内容保密  ④ 结果可统计
冲突：③ 要求「无人能追踪这张票」，④ 要求「计票方能证明票没被改」
```

```python
# 教学示意，不参与构建、不编译、不运行
from collections import Counter

def tally(ballots: list[bytes]) -> dict:
    """匿名性由盲签名提供，可核算性由混洗+零知识提供。"""
    return Counter(ballots).most_common()

if __name__ == "__main__":
    print(tally([b"yes", b"no", b"yes", b"yes"]))
```

> 6.1 的八种投票方案在 2026 年的现实里只有两条活下来：**「盲签名 + 混洗」**（Helios 一类电子投票系统）与**「先看后写」的信任模型**（大选用的纸质备份）。其余方案的共性是：要么要求选民高度在线，要么要把「选民名单」变成新的隐私风险。

### 多方计算的最小样例：百万富翁问题

```python
# 教学示意，不参与构建、不编译、不运行
def millionaires_compare(alice_secret: int, bob_secret: int) -> bool:
    """用「位承诺 + 安全比较协议」的示意，不追求真实安全性。"""
    if alice_secret == bob_secret:
        raise ValueError("inputs must differ to keep the protocol meaningful")
    return alice_secret > bob_secret
```

> 6.2 的严格版本需要**不经意传输（oblivious transfer）** 与 **混淆电路（garbled circuit）**；1996 年 Secure Multiparty Computation 只是理论，2020 年后它成了 ** MPC 钱包与隐私计算平台** 的技术底座。

### 数字现金的骨架：盲签名 + Deposit 协议

```python
# 教学示意，不参与构建、不编译、不运行
def mint(coin_serial: bytes, bank_blind_sig: bytes) -> bytes:
    """(e-cash 的提取阶段) 用户把 coin_serial 与盲因子结合后让银行盲签，
    之后除以盲因子得到可花费的硬币；银行事后无法把硬币与那次签名对上。"""
    return coin_serial + b"::" + bank_blind_sig
```

三条无法同时满足的性质（Chaum 的三难）：

1. **匿名性**（银行不能追踪硬币轨迹）；
2. **可追踪性**（发现双重花费时能揪出罪犯）；
3. **离线交易**（不依赖在线银行）。

> 现实答案：多数银行系统放弃离线（在线转账），或采用「半匿名」（双阶段花费，第一次花费后暴露身份）——这恰好印证了 6.4.5「数字现金和高明的犯罪」一节的悲观结论。

## 版本演进

| 阶段 | 关键差异 |
| --- | --- |
| **1983** | Chaum 的数字现金构想；1988 与 Fiat、Naor 给出可追溯方案 |
| **1986** | **Dining Cryptographers**（Chaum）登场，6.3 匿名广播的理论原型 |
| **1987** | Yao 的混淆电路与百万富翁问题，6.2 的核心工具 |
| **1996** | 本书成书：本节的方案多为「实验室级」构造 |
| **2001** | **Helios** 出现前的电子投票研究；Bulletin Board 模型定型 |
| **2004–2008** | **Camenisch-Stadler** 成员证明成为数字现金与匿名凭证的标准件 |
| **2016–2019** | **zk-SNARK 工程化**，让 6.1/6.2 的「可验证的匿名」第一次不那么昂贵 |
| **2009**之后 | **比特币**（本目录 16 章）以「公开账本 + 无需匿名」的方式绕开了 Chaum 的全部难题——6.4 的「双重花费」在这里被**游戏论 + 共识**解决，而不是密码学 |
| **2023–2026** | 隐私 L2（zk-Rollup）与匿名凭证把 MPC + ZK 变成常态基础设施 |

> **最戏剧性的一条**：本书用了整章 + 整节讨论「如何做出可转移、离线的匿名现金」，而 2009 年比特币的成功说明——**如果账本足够公开、惩罚足够经济化，你根本不需要盲签名**。这是「密码学与机制设计分道扬镳」的一次经典案例。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **把本章当作「可用方案清单」** | 6.1–6.4 的每一个方案在 1996 年都只是**候选**；它们的价值在于展示了「社会需求如何被翻译成密码学原语」 |
| 🔧 **数字现金被误读为「比特币的前身且已被实现」** | Chaum 的 e-cash 从未大规模商用；6.4.7 的「其他数字现金协议」同样停留在纸面 |
| **匿名性与可核算性的取舍被跳过** | 6.1 的八个方案其实在一条 trade-off 曲线上滑动，本章缺少一条统一的对比轴 |
| 🔧 **未提「 quorum / 可信执行环境」的现代替代** | 今天解决「互不信任的多方计算」多半靠 TEE（SGX/TrustZone）或 MPC 二者取一，而不是 6.2 的纯密码学构造 |
| **MPC 被宣传成「万能」** | 6.2 的严格安全性需要诚实多数或可证明的 abort 语义；把半诚实模型的结果当诚实模型用，是常见的事故来源 |
| 🔧 **「匿名广播」与「暗网」的伦理含混** | 6.3 讲匿名广播时不谈滥用风险；技术与伦理应一并讲，见 16 章 25.12（Cypherpunks）的历史语境 |

- **↔ `book/计算机程序的构造和解释（原书第2版）/`**：6.2 的混淆电路把「计算」变成「可传输的电路」，与 SICP 第 5 章「把解释器当作可传递的对象」在思想上同构——**都是把「如何计算」与「计算结果」分离**。
- **↔ `book/设计模式GoF/`**：6.1 的投票协议很像 **Chain of Responsibility**（每个检查项依次过），6.2 的 MPC 则像 **Mediator**（多方协调而不互相暴露）；区别是密码学里这些模式的**顺序不可打乱**。
- **↔ `book/数据库系统概念6/`**：6.2 的保密多方计算与数据库中「同态加密 / 可搜索加密」是同一问题的两种落地；该书的 23-XML 讲序列化安全，提醒我们「数据如何被解释」本身就是安全边界。
- **↔ `book/Java并发编程之美/concepts/` 中的并发模型条目**：MPC 与 6.3 的匿名广播都要求「每个参与者只看到自己该看的信息」，这与并发里**信息隐藏（information hiding）**的诉求一致，实现手段却一个是协议一个是语言级封装。
