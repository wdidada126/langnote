# 第 8 章 密钥管理（Key Management）

> **一句话**：第 8 章是全书最实用的一章——**「算法选得对不对」的 90% 由密钥管理决定**，而它用十二个小节把密钥的一生（产生、传递、验证、使用、更新、存储、备份、泄密、销毁）走了一遍。

## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### 密钥派生：一个密钥只干一件事

```python
# 教学示意图，不参与构建、不编译、不运行
import hashlib, os

def derive(master: bytes, purpose: bytes, length: int = 32) -> bytes:
    """域分离：给 purpose 加标签，避免「同一个密钥用在两处」。"""
    return hashlib.sha256(master + b"|" + purpose).digest()[:length]

master = os.urandom(32)
enc_key = derive(master, b"aes-256-gcm/data")
mac_key = derive(master, b"hmac-sha256/metadata")
assert enc_key != mac_key
```

> 8.5 节说「一个密钥不要用于多个目的」，却没有给出实现机制；**HKDF（RFC 5869）** 正是这个机制的标准化答案，而它 2010 年才成为 RFC——这是本书最明显的技术缺口之一。

### 口令到密钥：最容易被低估的一步

```python
# 教学示意图，不参与构建、不编译、不运行
import hashlib, os, time

PBKDF2_ITERATIONS = 600_000     # 示意值；2026 年的推荐量级已远高于本书的 1000

def kdf_password(password: bytes, salt: bytes, iterations: int) -> bytes:
    """口令被猜是常态，所以要用慢哈希；本书 8.1.4 提到 passphrase 却没给参数。"""
    d = hashlib.pbkdf2_hmac("sha256", password, salt, iterations)
    return d

t0 = time.time()
k = kdf_password(b"correct horse battery staple", os.urandom(16), PBKDF2_ITERATIONS)
print(f"{PBKDF2_ITERATIONS} iters -> {time.time() - t0:.2f}s")
```

> **关键点**：口令的熵远低于「长度」，但用户记不住长随机串。第 8 章的处理是「用长 passphrase」；现代答案是 **Argon2id / scrypt**，且必须给 salt（每个用户唯一）。

### 密钥状态的有限状态机（8.7–8.11）

```python
# 教学示意图，不参与构建、不编译、不运行
from enum import Enum

class KeyState(Enum):
    PENDING = "等待首次使用"
    ACTIVE  = "在用"
    STALE   = "超过轮换周期"
    COMPROMISED = "已泄密（必须吊销 + 轮换）"
    DESTROYED = "已销毁（需可证明）"

LEGAL_TRANSITIONS = {
    KeyState.PENDING:     [KeyState.ACTIVE],
    KeyState.ACTIVE:      [KeyState.STALE, KeyState.COMPROMISED, KeyState.DESTROYED],
    KeyState.STALE:       [KeyState.DESTROYED, KeyState.ACTIVE],
    KeyState.COMPROMISED: [KeyState.DESTROYED],
    KeyState.DESTROYED:   [],
}
```

> 这张状态机的存在，本身就是「密钥管理不是一次动作而是一条流水线」的证明；**本书把它们散落在十二个小节里，读起来像清单，工程上其实是一个状态机**。

## 版本演进

| 阶段 | 关键差异 |
| --- | --- |
| **1996** | 本书成书：密钥管理以「对称密钥的传递与存储」为主轴 |
| **1999–2001** | **PKI 商业化**：X.509 证书、CA 体系（对应 8.12）大规模部署 |
| **2006–2008** | **Debian 缺陷**证明 8.1（产生密钥）错了会让整个体系失效 |
| **2010** | **RFC 5869 HKDF** 落地，「域分离」正式可标准化 |
| **2013–2014** | **Heartbleed** 之后，业界开始把「私钥在服务器明文存储」视为不可接受 |
| **2015** | **RFC 7624 / 密码输入编码器**；FIPS 140-2/3 对 HSM 的强调达到新高度 |
| **2018** | **TLS 1.3** 强制会话密钥短期化，与 8.10 的判断一致 |
| **2020–2022** | **密钥管理转向 HSM/KMS 托管**：云 KMS（AWS KMS、GCP KMS、Tink 的 cloud 模式）成为默认 |
| **2024** | FIPS 203/204/205 之后，**密钥体系必须按「经典 + 后量子双栈」重建** |
| **2025–2026** | 后量子迁移的核心工程难题变成「**如何无中断地轮换密钥**」，正是 8.6 的议题被重新点燃 |

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **缺少 HKDF 与域分离的标准做法** | 8.5 给出「一个密钥一个用途」的建议却没给实现；现在必须补 HKDF（RFC 5869） |
| 🔧 **没有慢哈希的参数表** | 8.1.4 只说「用通行短语」，没有给出迭代量级与内存硬度要求；今天必须换成 Argon2id/scrypt |
| 🔧 **「存储密钥」的默认答案是文件** | 8.7 的默认建议是口令保护的文件/智能卡；2026 年的默认应是 **HSM / KMS**，因为密钥材料的泄露往往来自备份与日志 |
| 🔧 **8.8 备份被轻描淡写** | 现实中「密钥备份泄露」是最常见的事故路径之一；备份必须与主密钥同等保护，并纳入轮换范围 |
| **轮换密钥=更安全** | 8.6 提醒轮换会引入新风险；频繁轮换在有状态回滚与离线设备的场景反而制造漏洞 |
| 🔧 **吊销机制被当作「有就行」** | 8.9 之后的吊销（CRL / OCSP / 短寿命证书）在 2026 年已偏向「证书有效期 90 天 + 自动续期」，而非在线查询 |
| 🔧 **未覆盖后量子密钥管理** | 迁移的核心不在算法而在 **双密钥栈与轮换**；8.6 与 8.10 会被重新设计为「同时持有 ML-KEM 与 ECDH 的双栈密钥」 |
| **「公钥可以长期不变」的前提被高估** | 8.10 的「长期公钥」假设在量子时代崩溃：今天的公钥会被保存并日后解密 |

- **↔ `book/设计模式GoF/`**：8.7 的「密钥存储」非常像 **Singleton + Proxy**（全局唯一、代理访问）；但密码学要求 Singleton 的构建过程也防侧信道，这是设计模式的盲区。
- **↔ `book/计算机程序的构造和解释（原书第2版）/`**：8.5 的「域分离」与 SICP 第 2 章「数据导向编程」的 tag 机制是同一个思想——**用类型标签决定解释方式**；区别是密码学的标签错了会导致密钥被复用，后果严重得多。
- **↔ `book/数据库系统概念6/`**：8.8（备份）与数据库中「备份的一致性与恢复演练」是同构的工程问题；该文 23-XML 讲的序列化安全也提醒我们：**密钥被「解释」的方式（格式解析）本身就是攻击面**。
- **↔ `book/Java并发编程之美/concepts/ThreadLocal与内存泄漏.md`**：密钥与 ThreadLocal 一样——「放了进去却没有显式销毁」就会永远存在；ThreadLocal 泄漏是内存侧的泄露，泄露的密钥则是安全侧的泄露，两者的共同根源是**缺少显式的生命周期 API**。
