## 核心精讲

> 以下全部是**教学示意代码，不参与构建、不编译、不运行**。

### 定时攻击的最小形态

```c
/* 教学示意，不参与构建、不编译、不运行 */
#include <string.h>

/* 危险写法：一旦发现不同就提前返回，耗时与匹配长度相关 */
int bad_compare(const char *a, const char *b, size_t n) {
    size_t i = 0;
    for (; i < n; ++i) {
        if (a[i] != b[i]) break;       /* 提前退出 => 时序泄露 */
    }
    return (i == n);
}

/* 正确写法：始终遍历完，最后再做一次性比较 */
int good_compare(const char *a, const char *b, size_t n) {
    unsigned char diff = 0;
    for (size_t i = 0; i < n; ++i)
        diff |= (unsigned char)(a[i] ^ b[i]);
    return diff == 0;
}
```

> 2011 年的 **Lucky13（CVE-2011-3389）** 就是把这个差距放在 TLS 的 CBC 填充检查里；2014 年的 **POODLE** 则用「填充合法/非法的时间差」逐位解密。**教训不是「别写 `break`」，而是「任何与秘密相关的分支都会变成信道」。**

### 差分能量分析的骨架

```python
# 教学示意，不参与构建、不编译、不运行
def dpa(traces,猜测的中间值函数, 假设密钥字节):
    """ traces: 每条是一次功耗采样序列；
        对每个候选密钥字节、对每条轨迹计算「中间值函数」的汉明重量；
        把预测功耗与实际功耗做皮尔逊相关，相关系数最大的候选即为泄露点。 """
    best = None
    for candidate in range(256):
        corr = correlate(traces, [hw(candidate ^ t) for t in traces])
        if best is None or corr > best[1]:
            best = (candidate, corr)
    return best
```

> 《应用密码学》从未提到功耗分析，但它的 **附录 C 源代码（取自 Dr. Dobb's Journal）** 恰好是这类攻击的最佳靶子：那些以查表和数组索引为主的实现，功耗与中间值高度相关。

### 相关密钥攻击的关键思路

```
AES-256 的密钥扩展存在对称性攻击窗口：
  攻击者知道 K1 与 K1 ⊕ δ（相关密钥）时，
  可以构造出线索，把 256 位主密钥的恢复成本从 2^256 降到约 2^39 量级（Biryukov 等）。
```

```python
# 教学示意，不参与构建、不编译、不运行
def related_key_attack_hint(pairs):
    """示意：攻击者拿到 (K1, K2) 且 K1 ⊕ K2 已知时，
    不需要知道完整密钥就能把某些轮密钥的差异追踪出来。"""
    return [k1 ^ k2 for k1, k2 in pairs]
```

> **工程推论**：1996 年的书里，密钥编排只被当作「把密钥展开成长度」；今天它被视为**可被攻击的结构**——这也解释了为什么后量子方案（如完全背靠背 MLWE 结构的 Kyber/Saber 早期版本）在标准化时被迫改设计。

## 版本演进

| 年份 | 事件 |
| --- | --- |
| **1990** | 差分密码分析（Biham-Shamir）：对称密码分析的分水岭 |
| **1993** | 线性密码分析（Matsui） |
| **1996** | 本书成书：12.4 只讲这两条 |
| **1996** | **Kocher 的定时攻击**发表（同年！），但本书没有引用 |
| **1999** | **Differential Power Analysis**（Kocher-Jaffe-Juniper）与 **CORONER 的 TEMPEST 手册**；Boneh-Durfee 从另一头威胁 RSA |
| **2002** | Vaudenay 的**填充预言机**把「预言机接口」变成攻击面 |
| **2003** | **Kuhn 的 DPA in realtime**：把功耗分析变成可实时演示的攻击 |
| **2005** | 积分攻击（integral cryptanalysis）被提出（LFSR 与 And-rule/Sum-rule 一族） |
| **2008** | 相关密钥攻击（Biryukov 等）显著削弱 AES-256 的代价 |
| **2011** | Lucky13；同年 **WPA/TKIP 的 RC4 相关密钥碰撞攻击（7921/401KW）** |
| **2013–2014** | Heartbleed 之后，「**实现缺陷 = 算法失效**」成为共识 |
| **2018** | **Spectre/Meltdown** 提醒：侧信道不止于加密库，还在于 CPU 推测执行 |
| **2018** | **RFC 8476**：常量时间比较的普遍缺失被标准化文件点名 |
| **2020–2026** | 侧信道防御工程化：RustCrypto 的 `subtle`、`consttime`、OpenSSL 的 `CRYPTO_ct_eq`；以及「掩码（masking）」在高阶 DPA 中的实践 |

> 一条贯穿 30 年的线索：**算法安全的证明从不包含「我的代码长什么样」。** 侧信道把「实现」重新拉回安全论证的核心，这使本书「算法 + 源码」的结构反而显得先知——只不过那些源码需要一半是为了防御侧信道而重写。

## 防御 checklist（本章最实用的一页）

| 项 | 要求 |
| --- | --- |
| 比较 | 用常量时间比较（`CRYPTO_ct_eq` / `subtle` / `hmac.compare_digest`），**绝不用 `==` 或提前 `break`** |
| 分支 | 与秘密相关的分支必须写成查表 + 掩码，不能 `if (secret bit) ...` |
| 秘密数据的内存访问 | 数组索引不能由秘密值决定（AES 的 T-table 是双刃剑） |
| 错误提示 | 加密失败与认证失败返回**同一个错误码**，且耗时一致 |
| 模逆/模幂 | 用固定窗口与常量时间的 Montgomery 乘法 |
| 功耗 | 敏感场景做 DPA 测试（固定/随机化中间值、掩码） |
| 库 | 调用经过审计的库，而不是本书附录的源码 |
