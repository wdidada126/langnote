## 10.1 本章定位

单机天花板之上的两条路：**向上（scale-up，配硬件/参数，12 章负责）与向外（scale-out，本章）**。
向外又分读扩展（08 章主从已覆盖）与写扩展/自动故障转移（本章主场）：
InnoDB Cluster = Group Replication + Shell AdminAPI + Router 三件套，外加老牌 NDB Cluster 支线。
2026 视角下本章是全书**保鲜度最低**的一章：三件套仍在，但功能面与许可线都已位移（见演进节）。

## 10.2 Group Replication 机制卡（⚠️ 转述）

- 成员间经 **XCom 共识协议**（Paxos 家族实现）对事务达成全局顺序；单主模式（默认，自动选主）
  与多主模式（冲突 certification 后回滚败者，业务要会处理 1213 类冲突错误码口径 ⚠️）。
- 事务提交流程：本地提交→认证（与在途集无冲突）→共识定序→成员各自回放（before/after 两种应用顺序）。
- 冲突粒度=主键/唯一键集合：这是"表必须有主键，最好单列"的硬纪律来源。
- 成员加入：全新=Clone Plugin 物理拷贝（联动 08 章）或分布式恢复（追 binlog）；网络分区→多数派存活、少数派自我驱逐，
  `group_replication_unreachable_majority_timeout` 决定滞留行为。
- 监控词汇：`performance_schema.replication_group_members` / `_member_stats`（12 章指标线复用）。

## 10.3 InnoDB Cluster 三件套（书内新能力的 2026 复核）

| 组件 | 职责 | 命令面孔（⚠️） |
| --- | --- | --- |
| MySQL Shell（AdminAPI） | 拓扑编排：建组/加节点/切主/修复 | `dba.createCluster()` / `dba.addToInstance()` / `cluster.rebootClusterFromCompleteOutage()` |
| Group Replication | 共识数据层 | 10.2 全部 |
| MySQL Router | 客户端路由/故障转移透明层 | bootstrap 生成缓存，读写走 metadata cache 定主 |

- 变体：**InnoDB ClusterSet**（跨地域多集群异步复制+定向切换，8.0.27 成熟，书成后物 ⚠️）；
  **InnoDB Replicated Cluster**（复制型集群，社区版可用性见演进节许可注记）。
- NDB 支线（8.0 的 NDB 7.6+）：内存+磁盘、自动分片、同步多主——真"可扩展写"，但运维心智成本把 99% 用户挡回
  InnoDB Cluster（⚠️ 书内同样口径）。

## 10.4 HA 方案光谱（把本章放回决策桌）

1. 手工主从+脚本探测+VIP/改配置：最老最便宜，脑裂风险最高（对读
   [../Efficient_MySQL_Performance/09-其他挑战.md](../Efficient_MySQL_Performance/09-其他挑战.md) 脑裂一节）。
2. MHA/Orchestrator 类外部仲裁器：GTID 补洞切换，社区时代主力（⚠️ 存活度见演进节）。
3. **组复制/InnoDB Cluster**：内建共识、RPO≈0（多数派持久化后返回）、切换自动化——书主推。
4. Galera 家族（含 MariaDB 线，#57 主场）：同属写集认证范式，许可与发行不同谱。
5. 云托管（RDS Multi-AZ/Aurora 等）：把 1–4 全部折叠成一个开关，但语义（共享存储复制）与本章行级复制不同（08 章演进节）。
6. 选型三问：能容忍多长 RTO？愿意为 RPO=0 付多少吞吐税（认证+共识往返）？团队养得起几层组件？

## 核心概念速览（中英对照）

- **MGR** — MySQL Group Replication：基于 XCom 共识的行级认证复制组（✅ group-replication 页）。
- **单主/多主** — single-/multi-primary：自动选主写一点 vs 全点可写、冲突认证定胜负。
- **认证（certification）** — 写集冲突检查：等价"全局唯一索引校验"，主键设计因此成为集群设计。
- **法定数** — quorum：多数派存活组才可用，少数派自我驱逐防脑裂。
- **InnoDB Cluster** — 三件套产品化：Shell AdminAPI + MGR + Router。
- **ClusterSet** — 集群集：跨域多集群+异步复制+受控切换（书后增强 ⚠️）。
- **MySQL Router** — 协议路由层：读写分离与故障转移对客户端透明化。
- **rebootClusterFromCompleteOutage** — 全停重建：AdminAPI 的"一键复活"路径。
- **NDB Cluster** — 无共享分布式引擎：内存数据节点+ndb_mgmd 仲裁，MySQL 世界的另一物种。
- **RPO/RTO** — 本章的度量衡：共识=用吞吐换 RPO，自动探测=用复杂度换 RTO。
- **Orchestrator/MHA** — 外部仲裁器流派：书时代社区主力，2026 见演进节存亡表。
- **分布式恢复** — group 成员经 binlog 追平入组，对照 Clone 的物理拷贝入组。

## 最新演进与工业实践

- **许可与版本位移**（⚠️+✅）：AdminAPI/Router 功能线在 8.x 后期部分收敛企业版口径的争议持续存在；
  社区可用面以 8.4 LTS 手册为准（dev.mysql.com 403，本目录只作书目引用；✅ 日期轴 endoflife）。
- **仲裁器存亡表**（⚠️ 转述）：GitHub orchestrator 项目活跃度自 2023 后显著下降（Percona Orchestrator 分叉续命）；
  MHA 事实停更——"外部仲裁"路线在 MySQL 圈让位于组复制与云托管。
- **云与代理层重构由**：ProxySQL+脚本仍是互联网大厂自建主流（写扩展分片交给中间件而非多主 MGR）；
  Oracle 侧 HeatWave/MySQL 即服务承接企业 HA 叙事（⚠️ 转述公开分享）。
- **2026 建议**：新集群首选 **8.4 LTS + InnoDB Cluster（单主）**，跨域用 ClusterSet 或直接应用层双写+对账；
  多主仅留给"多地写热点+能处理冲突"的窄场景（与 09 章分区弃用同理：书内能力清单要做存活度复核）。
