## 9.1 本章定位

分区=**一个逻辑表、N 个物理片段**，由存储引擎在表内部执行的路由规则管理——与 05 章"分库分表"的
应用层水平拆分（本仓口径见 [../Efficient_MySQL_Performance/05-分片.md](../Efficient_MySQL_Performance/05-分片.md) 的 sharding）
是两种物种。8.0 语境读本章要做一次心态调整：**它是"声明式大表治理"，不是扩展性答案**——
且官方已在 8.0 就预告分区废弃（演进节兑现）。

## 9.2 四种分区策略（⚠️ 转述）

| 策略 | 路由函数 | 典型场景 | 陷阱 |
| --- | --- | --- | --- |
| RANGE | `PARTITION BY RANGE (col)` / RANGE COLUMNS(多列) | 时间序列月切、归档 `DROP PARTITION` 秒删 | 值落不进任何分区→INSERT 报错（MAXVALUE 兜底） |
| LIST | 枚举值映射 | 地区/租户白名单分桶 | 新值无家可归，需 DEFAULT 分区（8.0.2+） |
| HASH | `MOD(表达式, N)` 均衡 | 均匀打散并发 | 加/减分区触发全量重分布，规划时要留余量 |
| KEY | 服务器内置哈希（列数≥1） | 类 HASH 但免表达式 | 只认列，不能用表达式，均衡性黑盒 |

- **分区裁剪（pruning）**：WHERE 带分区键谓词时只扫相关分区——收益全押在查询模式配合上；
  函数包裹分区键、类型隐式转换都会让裁剪静默失效（`EXPLAIN PARTITIONS`/`EXPLAIN` 的 partitions 列核验，
  对读 [../mysql/15-EXPLAIN详解.md](../mysql/15-EXPLAIN详解.md)）。
- 二级索引两形态：**本地索引**（每分区各建，非分区键查询要扫全分区索引）与唯一索引必须包含全部分区列（硬约束，⚠️）。

## 9.3 分区约束名册（选型前必读，⚠️）

1. **不支持外键**——有 FK 的表无法分区（数据完整性与分区的路由假设冲突）。
2. 分区键必须是**所有唯一约束（含 PK）的组成列**：跨分区唯一性无法本地校验。
3. 全文索引不支持分区（8.0 仍如此）；空间列限制另见 7.2。
4. 每表分区数上限 8192（5.7 的 1024 被上调，⚠️）。
5. 分区不是并行查询，也不改变单表事务语义；MAX_ROWS 等仍是 InnoDB 单表空间内的多 .ibd 文件。
6. 运维红利：**EXCHANGE PARTITION** 秒级换表（冷数据归档/批量装载通道）、ADD/DROP/REORGANIZE PARTITION 的
   局部化重建，这才是 MySQL 分区的真实价值面。

## 9.4 🔧 类比实测：ATTACH 手工分片 vs 声明式路由（非 MySQL 行为）

python sqlite3 3.45.3 实跑（脚本 `D:\develops\tmp\dbwave_w5_myadmin\`，2026-09-27）：

- 建 `shard1.db`（行 (1,'s1')）与 `shard2.db`（行 (2,'s2')）→ 主连接
  `ATTACH 'shard1.db' AS s1; ATTACH 'shard2.db' AS s2` →
  `SELECT id,tag FROM s1.u UNION ALL SELECT id,tag FROM s2.u` 返回 `[(1,'s1'), (2,'s2')]`。
- 读出的机制直觉：**"多文件、一查询门面"是分区/分片的共同物理观**；SQLite 把路由责任完全丢给
  SQL 作者（手写 UNION ALL），MySQL 分区把路由内化进存储引擎（声明 RANGE 后 INSERT 自动落位、SELECT 自动裁剪）。
  两极之间正是 #45 第 5 章"应用层分片"（中间态）的位置。**非 MySQL 行为**：无裁剪、无 EXCHANGE、无原子多文件提交。
- 附加观察：ATTACH 跨库写不保证原子回滚（各文件独立 journal）→ 类比"InnoDB 分区同属一表空间栈"的一致性优势话术。

## 核心概念速览（中英对照）

- **分区** — partitioning：单逻辑表→多物理片段，引擎内路由；≠分库分表（9.1 物种声明）。
- **RANGE/LIST/HASH/KEY** — 四大路由策略：COLUMNS 变体放宽到多列/非整型。
- **分区裁剪** — pruning：谓词含分区键才免扫无关分区，收益/风险双高。
- **MAXVALUE 兜底分区** — 越界值收容所：没有它，越界 INSERT 直接失败。
- **DEFAULT 分区** — LIST 专用：未列举新值的去向（8.0.2+）。
- **本地索引** — local index：每分区独立索引段；非分区键条件=全分区索引扫描。
- **唯一性硬约束** — 唯一列集 ⊇ 分区列集：MySQL 分区的第一设计税（9.3-2）。
- **EXCHANGE PARTITION** — 换分区：`.ibd` 级秒换空表，归档/装载双神器。
- **REORGANIZE PARTITION** — 重切：SPLIT/MERGE 的执行原语，代价=分区内数据重写。
- **8192 上限** — per-table partition limit：设计粒度讨论的天花板。
- **重分布** — rebalance：HASH/KEY 加减分区引发的数据大迁徙，容量规划前置项。
- **声明式路由 vs 手工 UNION** — 🔧 ATTACH 实验呈现的两极（9.4），中间态=中间件分片。

## 最新演进与工业实践

- **分区弃用长刀**（⚠️→✅）：官方 8.0 手册即声明"native partitioning 未来版本移除，届时仅 NDB 保留分区"；
  **MySQL 9.0（Innovation 首版，2024-07-01 ✅ endoflife 实抓）起表分区已从社区版移除**——
  本章内容在 8.4 LTS 上仍受支持至 2029（✅ 8.4 EOL 2032-04-30），但 2026 新系统**不应再选 MySQL 原生分区**。
- **迁移路线共识**：时间类分区→按"分表+视图/中间件路由"或**归档到列存湖仓**（Iceberg/Paimon 表天然按天分目录，
  本仓双专册见 9.5 链接）；热冷分层由对象存储生命周期策略接管（⚠️ 转述工业口径）。

- **云 RDS 现状**：托管 MySQL 8.4 实例仍含分区；大厂普遍用自研分片中间件（Vitess 谱系等）替代之（⚠️ 转述）。
