## 4.1 本章定位

数据类型是 DBA 唯一"写错了要用一年"的决策：列类型决定行宽→缓冲池效率→索引深度→备份体积→复制兼容。
本章在 8.0 语境下的三件大事：**整数显示宽度退役、JSON 转正、空间类型与字符集默认值换血**。

## 4.2 8.0 类型地图（管理员口径速览，⚠️ 手册转述）

| 家族 | 成员与 8.0 要点 | 决策要点 |
| --- | --- | --- |
| 数值 | TINYINT…BIGINT（UNSIGNED）；DECIMAL(M,D) 定点；FLOAT/DOUBLE 近似 | **宽度声明如 INT(11) 已弃用**（仅显示层残留，约束由类型自身决定）；主键用 BIGINT UNSIGNED 防 2^31 墙 |
| 位 | BIT(M) | 稀疏开关位集合的压缩存法，慎用（工具链兼容性差） |
| 字符 | CHAR(n)/VARCHAR(n)，n 是**字符数**（utf8mb4 下行存按字节动态计） | VARCHAR 上限 65535 字节/行约束；TEXT 家族（TINY…LONGTEXT）溢出页存储——大列拖慢扫描 |
| 二进制 | BLOB 家族 / VARBINARY | 图片入库 vs 入盘的老争论；8.0 默认字符集变化不波及二进制 |
| 日期时间 | DATE / TIME / DATETIME(fsp) / TIMESTAMP(fsp) / YEAR | DATETIME vs TIMESTAMP：时区换算与 2038 问题；**microsecond 精度自 5.6.4 起 .6 位可用**；TIMESTAMP 隐式转换属性（CURRENT_TIMESTAMP ON UPDATE） |
| 枚举 | ENUM / SET | 字典序比较陷阱（''与 NULL）；新增值是 DDL（INSTANT 化见 05 章） |
| JSON | 原生 JSON：二进制树存储 + 路径抽取 | 8.0 引入部分 JSON 列类型；虚拟生成列+多值索引组合拳见 07 章 |
| 空间 | GEOMETRY/POINT/POLYGON… + 空间索引 | GIS 列必须 NOT NULL 才能建空间索引（⚠️ 8.0 手册通知） |
| 生成列 | VIRTUAL/STORED GENERATED COLUMN | 类型系统的"逃生舱"：函数索引、JSON 拍平、约束强化的底座 |

## 4.3 类型选择的五条工程铁律（书体裁的"注意事项"重写）

1. **最小够用**：能 TINYINT 不 INT——行宽直接乘出缓冲池命中率（性能轴对读
   [../Efficient_MySQL_Performance/03-数据.md](../Efficient_MySQL_Performance/03-数据.md) "最少数据原则"）。
2. **NOT NULL + 哨兵值优于 NULL 海洋**：NULL 让索引统计与三值逻辑复杂化；数值用 0、日期用'1970-01-01'的纪律（⚠️ 实践口径）。
3. **字符串长度是上限承诺**：utf8mb4 VARCHAR(255) 的索引预算=255×4 字节前缀——超长一律考虑前缀索引（07 章）或迁 TEXT。
4. **时间列三选一**（创建时间 DATETIME(3)、带时区事件 TIMESTAMP、统计日 DATE），先想清楚时区策略再落 DDL。
5. **枚举演进**：状态机字段用 CHAR(1)+CHECK 还是 ENUM？8.0 的 ENUM 值追加可 INSTANT（8.0.12 起），旧顾虑减半（⚠️）。

## 4.4 🔧 类比实测：类型系统严格性对照（非 MySQL 行为）

**实验 A：SQLite 类型亲和（affinity）vs MySQL 严格模式**（python sqlite3 3.45.3，脚本在
`D:\develops\tmp\dbwave_w5_myadmin\`，2026-09-27 实跑）：

- `INSERT INTO aff(i,txt) VALUES('123abc','abc')`（i 声明为 INTEGER）→ `typeof(i)='text'`，值原样存为文本；
- `INSERT INTO aff VALUES('45','45')` → `typeof(i)='integer'`（可无损解析则强转）。
- **类比结论**：SQLite 的"亲和性"=类型只是建议；MySQL 严格模式（8.0 默认）下同类插入直接报错 `1366 Incorrect integer value`
  （⚠️ MySQL 侧未实测，口径转述自手册数据类型的"存储严格性"通知）。**这是"能不能把脏数据写进去"的分水岭，
  非 MySQL 行为，仅用 SQLite 演示另一极。**

**实验 B：字符序（collation）能力边界**：表 s(name) 插入 'Ünïcode'/'unicode'/'UNICODE'，
`WHERE name COLLATE NOCASE='UNICODE'` 命中 **2/3 行**——SQLite NOCASE 只折叠 ASCII。
- **类比结论**：MySQL 8 的 utf8mb4_0900_ai_ci 是 UCA 9.0 全量排序（口音不敏感、大小写不敏感，'Ü'=u 命中）（⚠️ 转述）；
  SQLite 无等价物 → 把 MySQL 依赖 ai/ci 的查询搬到 SQLite/多数嵌入式引擎会**静默少匹配**，
  这是"换引擎前先审 collation 依赖"的实证（非 MySQL 行为）。

## 核心概念速览（中英对照）

- **显示宽度** — display width：INT(11) 的"11"仅是渲染残留，8.0 弃用；类型即约束。
- **类型亲和** — type affinity：SQLite 的弱类型存储建议机制，🔧 实验 A 用作严格模式对照。
- **utf8mb4** — 全 Unicode 字符集：8.0 默认；每字符至多 4 字节，索引长度预算须按此重算。
- **collation** — 字符序：utf8mb4_0900_ai_ci 为 8.0 默认排序规则（UCA、口音/大小写不敏感）。
- **DATETIME vs TIMESTAMP**：前者裸时间 9999 年上界；后者带时区换算、2038 上界（32 位纪元秒）。
- **fsp 小数秒** — fractional seconds precision：.0~.6 微秒精度声明，5.6.4+ 起。
- **ENUM/SET** — 枚举/集合：字符串形态的位压缩类型；追加值 8.0.12+ 可 INSTANT。
- **JSON 列** — 原生 JSON：二进制树存储、路径访问、与生成列/多值索引配套使用。
- **生成列** — generated column：VIRTUAL/STORED 两态，是函数索引与约束强化的载体。
- **空间类型** — spatial types：GEOMETRY 家族；建空间索引要求列 NOT NULL（⚠️）。
- **严格 SQL 模式** — strict mode：8.0 默认 STRICT_TRANS_TABLES，脏值拒收（对照 🔧 实验 A）。
- **CHECK 约束** — check constraint：8.0.16 起真正强制执行（此前解析后忽略）——书内演示已过时口径。

## 最新演进与工业实践

- **8.0→8.4/9.x 类型面变化**（⚠️ 转述 + ✅ endoflife 日期轴）：显示宽度与 YEAR(2) 等弃用项在 8.4 完成移除线；
  9.x Innovation 在类型层的增量属尝鲜面，**生产口径以 8.4 手册为准**（dev.mysql.com/doc/refman/8.4/en/data-types.html，本环境 403 仅书目引用）。
- **JSON 生态位再定位**：MySQL 8.4 的 JSON 函数面继续扩充（JSON_TABLE/JSON_SCHEMA_VALID），但工业实践把"文档+分析"
  负载更多分流到 **列存/湖仓**（本仓对照：[../DuckDB_in_Action/00-总览与阅读地图.md](../DuckDB_in_Action/00-总览与阅读地图.md) 的半结构化读取——✅ 盘上存在）；
  MySQL 侧留"业务主库携带轻 JSON"的折中。
- **向量类型传闻**：2026 社区对 MySQL 原生向量的期待集中在 HeatWave/外围方案，**主社区版尚无定论**（⚠️ 不作结论）。
- **字符集长期战**：utf8mb3 在 8.0.36+ 标记弃用、8.4 彻底更名告警——升级检查单新增 `ALTER DATABASE … CHARACTER SET utf8mb4` 批处理项（⚠️）。
