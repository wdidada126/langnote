## 7.2 索引名册（管理员口径，⚠️ 转述）

| 索引类型 | 8.0 状态 | 一句话任务 |
| --- | --- | --- |
| 主键（聚簇） | 每表唯一事实标准 | 短、增、单调；二级索引叶子挂 PK 回表 |
| 二级索引 | B+ 树+回表 | 覆盖索引免回表；最左前缀决定可用性 |
| 唯一索引 | 含 NULL 语义特例 | 业务约束优先于查询优化来用它 |
| 前缀索引 | VARCHAR 截断建 | 选择性测试 `COUNT(DISTINCT LEFT(col,n))/COUNT(*)` 定长度 |
| 全文索引 FTS | InnoDB 原生（MyISAM 版弃用） | ngram（CJK）解析器；大流量检索别硬扛（6 章 ES 口径） |
| 空间索引 R-Tree | 仅 InnoDB，NOT NULL | GIS 场景，配合 SRID 校验 |
| 降序索引 | **8.0 新增**（此前 DESC 被忽略） | 多列混合方向的排序消除 |
| 函数索引 | **8.0.13 新增**（隐藏虚拟生成列） | 表达式查询可走索引；约束强化副产物 |
| 不可见索引 | **8.0 新增** | "先隐身观察一周再删"的安全下线流程 |
| 多值索引 | **8.0.17 新增**（JSON 数组列） | JSON 数组成员查询进索引；与生成列互补 |
| 哈希/自适应 | Adaptive hash index | InnoDB 内部加速器，AHI 命中率决定开关价值（12 章指标） |

## 7.3 索引生命周期管理（本章的 DBA 味所在，⚠️）

1. **上线**：`ALTER TABLE ADD INDEX ... , ALGORITHM=INPLACE, LOCK=NONE`；大表评估临时表空间与 redo 洪峰（联动 5.3）。
2. **观察**：`EXPLAIN`/`EXPLAIN ANALYZE`（8.0.18+ 真执行计时）；`sys.schema_unused_indexes` 找僵尸索引
   （对读 [../Efficient_MySQL_Performance/02-索引与索引编制.md](../Efficient_MySQL_Performance/02-索引与索引编制.md) 的索引杠杆论）。
3. **下线**：先 `ALTER TABLE ALTER INDEX idx INVISIBLE`，业务无感后再 DROP——8.0 给"删索引"装上回滚按钮。
4. **重复/冗余检测**：information_schema.STATISTICS 按列前缀关系自join（本册 🔧 未覆盖 MySQL 系统表，SQL 化写法 ⚠️ 转述）。
5. **统计信息**：`innodb_stats_persistent`、`ANALYZE TABLE`（8.0 起不再全局互斥，stale 计算绑定直方图，12 章）。

## 7.4 🔧 类比实测：索引≠自动变快（非 MySQL 行为）

DuckDB 1.5.5 实跑（脚本 `D:\develops\tmp\dbwave_w5_myadmin\`，2026-09-27）：

- `CREATE TABLE big AS SELECT range id FROM range(2000000)` → `CREATE INDEX art ON big(id)` →
  `EXPLAIN SELECT * FROM big WHERE id=123456` 计划节点仍是 **SEQ_SCAN（Type: Sequential Scan, Filters: id=123456）**，
  ART 索引未被选用。
- 读出的机制直觉：有没有索引、用不用索引、划不划算，是三件事——优化器按成本模型自主放弃索引是**跨引擎通病**；
  MySQL 侧对应物是基数估计失准导致的"该走索引不走"（⚠️ 转述，其解法：直方图/ANALYZE，见 12 章）。
- 类比边界：DuckDB 是列存/无回表概念的分析引擎，其"不用索引"的动机（向量化扫描太快）与 InnoDB 相反；
  **本实验仅证"索引选择是优化器决策而非 DDL 承诺"，非 MySQL 行为、数字不可引用。**
- 配套直觉（同库）：DuckDB 对 2M 行 `COPY TO 'snap.parquet'` 仅 **0.05s / 16437KB**（15 章复用），
  与 InnoDB"索引即物化排序"的写放大哲学互为镜像。

## 核心概念速览（中英对照）

- **聚簇索引** — clustered index：InnoDB 表按 PK 组织，二级索引叶子存 PK → 回表成本根源。
- **覆盖索引** — covering index：查询列全在索引内则免回表，EXPLAIN 里的 Using index。
- **最左前缀** — leftmost prefix：复合索引可用性由列序前缀决定，7.2 表的元规则。
- **降序索引** — descending index：8.0 真实支持 DESC，消除多向排序的 filesort。
- **函数索引** — functional index：以隐藏 VIRTUAL 生成列为载体的表达式索引（8.0.13）。
- **多值索引** — multi-valued index：JSON 数组元素建索引（8.0.17），关系-文档混合的桥。
- **不可见索引** — invisible index：优化器无视但照常维护，安全下线流程的开关（7.3）。
- **全文索引** — FULLTEXT + ngram parser：InnoDB 倒排表实现；CJK 需 ngram（与 ES 谱系对照见 6 章）。
- **空间索引** — R-Tree：GIS 专用，要求列 NOT NULL（⚠️）。
- **自适应哈希** — adaptive hash index：InnoDB 热页等值加速，12 章指标决定去留。
- **回表** — table lookup：二级索引→PK 的第二次 B+ 树查找，索引设计的隐形税（🔧 类比边界见 7.4）。
- **ANALYZE TABLE** — 统计刷新：8.0 持久化统计+直方图两条线，优化器眼睛的镜片布。

## 最新演进与工业实践

- **索引面 8.0→8.4/9.x**（⚠️ 转述）：多值索引/降序索引在 8.4 已属基线能力；9.x Innovation 未再大动索引框架，
  优化器增量集中在成本模型与并行扫描预告——"索引武器库"进入消化期。
