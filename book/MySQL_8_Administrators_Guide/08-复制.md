## 8.1 本章定位

复制是 MySQL 管理员的"第二心脏"：读写分离、备份卸载、异地容灾、升级灰度全建在它上面。
8.0 的复制叙事三根主线：**binlog 格式默认 ROW、GTID 默认 ON、并行回放持续加速**。
本章给任务流，延迟的病理学在
[../Efficient_MySQL_Performance/07-复制延迟.md](../Efficient_MySQL_Performance/07-复制延迟.md)，
机制在 [../Effective MySQL之深入解析复制技术.md](../Effective MySQL之深入解析复制技术.md) 与

## 8.2 复制底座（⚠️ 转述）

- 三线程经典模型：dump（主）→ relay log（从 IO）→ SQL applier（从）；8.0 起 applier 可并行。
- **binlog 格式**：ROW（默认，事件记"行像"）/ STATEMENT（不确定性函数是历史包袱）/ MIXED；
  ROW+大事务=巨型 binlog 事件，`binlog_row_image` 可调 MINIMAL 换体积。
- **GTID 模式**：`gtid_mode=ON` + `enforce_gtid_consistency`，事务获得 `server_uuid:序号` 全局身份；
  收益=拓扑漂移时"按事务号找位点"，代价=禁 CREATE TABLE ... SELECT 等不确定语句（8.0 逐步解禁，⚠️）。
- **半同步**（`rpl_semi_sync_master/replica` 插件，8.0.21 后新命名 SOURCE/REplica）：AFTER_COMMIT 语义下
  "已确认≠已落盘"的窗口与 `rpl_semi_sync_master_timeout` 退化行为是面试与事故复盘双料常客。
- **崩溃安全**：`sync_binlog=1` + `innodb_flush_log_at_trx_commit=1` 的"双 1"才是持久复制源；
  relay_log_recovery 兜底从库重放一致性（联动 5 章双写/redo 讨论）。

## 8.3 拓扑与运维任务（书体裁清单）

1. 主从搭建：COPY（老）vs **Clone Plugin**（8.0.17+，物理级"克隆建从"，本章书内新武器，13 章扩展框架同源）；
2. 单向链/星形/树形与循环复制（`log_slave_updates`/`log_replica_updates` 是级联与 MGR 的前提）；
3. 过滤：`replicate-wild-do-table` 等（从库侧）与 `binlog-do-db`（主库侧）的语义陷阱（⚠️ 手册明言不推荐主库侧过滤）；
4. 监控基线：`SHOW REPLICA STATUS` 的 `Seconds_Behind_Source`（仅事件时间差，非滞后真相，

5. 延迟从库（`SOURCE_DELAY`）当"误删后悔药"，与 5 章 PITR 组成双保险。

## 8.4 🔧 类比实测：序号空洞与"事务号"语义（非 MySQL 行为）

python sqlite3 3.45.3 实跑（脚本 `D:\develops\tmp\dbwave_w5_myadmin\`，2026-09-27）：

- 表 `log(seq AUTOINCREMENT)`：插入 'a'（seq=1）→ 事务内插入 'b' 后 **ROLLBACK** → 再插 'c' →
  存活序列 **[1,2]**，且 `sqlite_sequence` 计数=2：SQLite 的自增计数器随回滚**一并回滚**，序号被复用、无空洞。
- 对照 MySQL（⚠️ 转述未实测）：InnoDB 自增与 GTID 序号在回滚时**不回收**——"分配即消耗"，
  集合天然容忍空洞（GTID 集 `uuid:1-5,7-9` 中 6 缺失合法）。**这一差异正是"日志序号"两类语义的分水岭**：
  序号=行号（SQLite，会收缩）vs 序号=发票号（MySQL，会跳号）。
- 因此排错口径不同：MySQL 里 GTID 空洞≠数据丢失（可能只是回滚/跳过事务，`gtid_next=EMPTY` 可人工补洞）；
  而在"计数器回滚型"系统里空洞反而更可疑。**非 MySQL 行为，仅用 SQLite 演示语义两极。**

## 核心概念速览（中英对照）

- **binlog** — 归档日志：Server 层的逻辑事件流，复制与 PITR 的共同货币（✅ replication 页）。
- **ROW 格式** — 行镜像事件：记前后行像，确定性最高、体积最大；8.0 默认。
- **GTID** — 全局事务标识符：`uuid:number`；8.0 默认 ON，拓扑自由度的来源。
- **GTID 集/空洞** — gtid_executed 集合：区间压缩表示，回滚/跳过产生的洞合法存在（🔧 8.4）。
- **半同步复制** — semi-sync：至少一从确认收到（AFTER_SYNC/AFTER_COMMIT 两模式）才回客户端。
- **relay log** — 中继日志：从库落盘待回放事件，relay_log_recovery 保崩溃一致。
- **并行回放** — parallel applier：`replica_parallel_workers` + 依赖追踪（8.0 组提交增强）；单大事务仍是串行墙。
- **双 1** — sync_binlog=1 & trx_commit=1：持久化金标准，性能/安全交换的锚点（⚠️）。
- **级联复制** — cascading：从库开 log_replica_updates 再喂下游，扇出解法。
- **延迟从库** — delayed replica：SOURCE_DELAY 人为滞后，误删急救与 PITR 互补。
- **Clone Plugin** — 克隆插件：物理拷贝快速建从/加 MGR 成员（13 章组件线，8.0.17+）。
- **SOURCE/REPLICA 术语** — 8.0.22+ 政治正确改名：SHOW SLAVE STATUS → SHOW REPLICA STATUS 等同义映射。

## 最新演进与工业实践

- **8.4 复制面**（⚠️ 转述）：异步连接（async connection）线程模型、副本降级（demote）、
  `SHOW REPLICAS`、binlog 未提交事务压缩等增强让"本章任务流"的命令名继续漂移；术语全面切换
  MASTER/SOURCE→SOURCE 单一词汇表，书中老命令按映射表读。
- **8.0.26+ 事务写集并行**：`binlog_transaction_dependency_tracking=WRITESET` 大幅松绑同表不同行冲突（书成书后物，⚠️），
  已是 2026 自建高吞吐从库默认建议。
- **拓扑主流**：MGR/InnoDB Cluster 吃掉的正是本章"手工主从+脚本切换"的地盘（10 章主场）；
