## 11.1 本章定位

MySQL 安全=四条战线：**认证**（谁能进门）、**授权**（进门后能干什么）、**传输加密**（路上别被看）、
**静态加密与密钥管理**（磁盘上别被拷）。8.0 在这四条线各扔了一枚重磅：caching_sha2 默认、角色落地、
TLS 自动化、表空间密钥体系（keyring）。本章是全书与合规审计贴得最近的一章。

## 11.2 认证与账户生命周期（⚠️ 转述）

- 账户身份=`user@host` 二元组；`CREATE USER`/`ALTER USER` 族，密码策略走 validate_password **组件**（13 章框架）。
- caching_sha2_password：SHA-256+全 TLS 或 RSA 密钥交换双路径，服务端内存缓存加速重复认证；
  兼容层 mysql_native_password 8.4 起默认停用（演进节）——**"升级 8.0 第一件事盘连接器"** 的出处。
- 账户管理细节：`FAILED_LOGIN_ATTEMPTS n PASSWORD_LOCK_TIME`（临时锁）、`expires_interval` 口令有效期、
  `RENAME USER`、`SHOW GRANTS` 永远是排权限问题的第一句。

## 11.3 授权模型与角色（⚠️ 转述，✅ privileges-provided 页）

- 权限层级：GLOBAL（`*.*`）→ DATABASE（`db.*`）→ TABLE/COLUMN/ROUTING；动态权限（SYSTEM_VARIABLES_ADMIN 等）
  承接最小特权颗粒。
- 高危权限清单（审计必查）：`FILE`（OUTFILE/LOAD DATA 任意读写盘）、`SUPER`（8.0 拆分为 20+ 动态权限）、
  `PROCESS`（看别人 SQL）、`GRANT OPTION`（权限传染）、`SET_USER_ID`/`PROXY USER`。
- **角色**：`CREATE ROLE auditor; GRANT SELECT ON app.* TO auditor; SET DEFAULT ROLE ALL TO 'u'@'%'`；
  角色=可授予的账户，激活语义（ACTIVATE/SET ROLE）要与客户端会话管理配合，这是 8.0 角色"能用但易误用"的点。
- 最小特权流程模板：应用账户只给 DML+EXECUTE；迁移账户按需临时 GRANT DDL；运维跳板账户强制 TLS+审计（⚠️ 通行纪律）。

## 11.4 传输与静态加密（⚠️ 转述）

1. TLS：`require_secure_transport=ON` 全局强制；`ALTER USER ... REQUIRE [SSL|X509]` 账户级；
   8.0.28+ 首启自动生成证书（书内手工 mysql_ssl_rsa_setup 流程已成历史，联动 03 章）。
2. 表空间加密：`ENCRYPTED=YES`（表/表空间级）+ keyring 组件族（keyring_file 文件版 / KMIP/Vault 企业版）；
   **密钥轮换纪律**（master key rotation）比开关本身更重要。
3. binlog/redo 加密（8.0.14 表空间以外扩展到日志，⚠️），redolog 明文时代结束。
4. 审计线：社区版无 Enterprise Audit 插件 → 常规日志/performance_schema 拼装土办法，企业版另计（许可线见演进节）。

## 11.5 🔧 类比实测：权限系统的"有与无"（非 MySQL 行为，局限声明版）

**实验 A：SQLite 完全没有账户/授权对象**（python sqlite3 3.45.3，2026-09-27 实跑）：

- `SELECT type||':'||name FROM sqlite_master` 只有 table/index 类对象——**没有 user/role/privilege 任何目录项**；
  能打开文件=全权读写，数据库层不存在"进门后能干什么"这一层。
**实验 B：DuckDB 1.5.5 同样无授权面**：`GRANT SELECT ON big TO someuser` → `ParserException: syntax error at or near "GRANT"`；
`SELECT * FROM duckdb_users()` → `Catalog Error: Table Function ... does not exist`——无用户目录。

- **类比要说明的（诚实边界）**：这两个嵌入式引擎**不是"权限弱的 MySQL"，而是"没有这层"**——
  MySQL 的 `mysql.user`/`columns_priv`/`role_edges` 系统表体系在它们这里根本没有对位物，
  所以 11.2–11.3 的任何 MySQL 行为**无法在 🔧 中实测**，本实验只兑现一个反向直觉：
  **"进程级信任域"（谁能开文件谁全得）是绝大多数嵌入式/分析引擎的真实安全模型**；
  MySQL 服务器模型的价值恰恰是"多租户共享一个进程"时的语句级裁决。
  生产上给 SQLite/DuckDB 补权限=把它们包进有 ACL 的文件系统/服务层（应用层实现），**非 MySQL 行为**。

## 核心概念速览（中英对照）

- **caching_sha2_password** — 8.0 默认认证插件：SHA-256+缓存快速路径，兼容 TLS/RSA 双通道。
- **account** — 账户：user@host 二元组，同名不同 host=不同账户不同权限。
- **动态权限** — dynamic privileges：SUPER 拆分后的细粒度管理权（SYSTEM_VARIABLES_ADMIN 等，⚠️）。
- **角色** — role：可授予/可激活的权限包（8.0 落地），默认角色语义须显式设置。
- **GRANT OPTION** — 授权传染位：审计高危项，应用账户永远不给。
- **REQUIRE SSL/X509** — 传输约束：账户级强制加密/证书 CN 校验。
- **validate_password 组件** — 口令强度闸门：插件→组件化迁移的标本（13 章框架）。
- **keyring** — 密钥环：表空间加密的密钥后端抽象（file/KMIP/Vault 谱系）。
- **表空间加密** — encrypted tablespace：ENCRYPTED=YES + 主密钥轮换纪律；防"拷走 ibd 文件"。
- **口令生命周期** — password expiry/lock：FAILED_LOGIN_ATTEMPTS+expires_interval 的合规三件套。
- **审计（社区版缺位）** — auditing：企业 Enterprise Audit vs 社区 p_s 拼装，选型时的许可分水岭（⚠️）。
- **进程级信任域** — 🔧 实验提炼：SQLite/DuckDB 的安全模型本体，与 MySQL 语句级裁决对照记忆。

## 最新演进与工业实践

- **mysql_native_password 退场线**（⚠️ 转述）：8.4 默认停用（`--mysql-native-password=OFF` 口径），
  9.x 进一步收紧；2026 升级清单第一行=清点存量 native 账户与老驱动（JDBC/PHP 版本矩阵）。
- **TLS 全面默认化**：证书自举+自动轮换进入默认路径，"明文 3306 内网通配"在合规审计里已不可辩护（⚠️ 实践共识）。
- **加密边界外移**：云 KMS 托管密钥（RDS 一键加密=KMS 集成）、TDE 类能力成为 Aurora/PolarDB 标配叙事；
  社区 keyring_file 仅覆盖"冷盘失窃"最低线（⚠️）。
- **RLS 缺口**：社区 MySQL 至今无行级安全（对比 PG 的 RLS，见 11.6 链接册）；多租户隔离在 MySQL 上=视图+应用层谓词或独立账户，
  本章权限模型讨论在 2026 语境的最常见延伸题。
