## 5.1 本章定位

"库"的全生命周期管理：建/改/删（DATABASE、SCHEMA 同义）、字符集与排序规则的库级默认、
在线 DDL（ALGORITHM/LOCK 三态）、TRUNCATE 语义、以及**备份恢复**这一 DBA 的立身任务。
本章与 6/7 章共用"对象管理"骨架：对象 → DDL → 物理效果 → 可回退性。

## 5.2 库与模式对象管理（⚠️ 手册转述）

- `CREATE DATABASE db DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci`：库级默认是"继承根"，
  表/列可覆写——三层默认链是排"乱码到底哪层坏了"的路标。
- 8.0 数据字典后，`SHOW DATABASES`/information_schema.SCHEMATA 与物理目录**一一对账**（frm 时代"孤儿文件"类故障绝迹，⚠️）。
- 对象命名：库名=目录名，跨大小写敏感 OS 迁移（Linux 默认 lower_case_table_names=0 vs Windows=1）
  必须在初始化时定死（8.0 起 lower_case_table_names 初始化后不可改，改了起不来，⚠️）。
- ALTER DATABASE 即时生效；DROP DATABASE 无回收站——生产一律先 RENAME 观察再 DROP（⚠️ 通行纪律）。

## 5.3 在线 DDL：INPLACE / INSTANT / COPY（⚠️ 转述）

| 算法 | 语义 | 典型可 INSTANT 项 |
| --- | --- | --- |
| COPY | 建临时表全量搬 | 大多数类型改写、ROW_FORMAT 变更（书时代） |
| INPLACE | 原地+允许并发 DML（LOCK=NONE） | 二级索引创建（仍耗时长）、加列（8.0.12 起转 INSTANT） |
| INSTANT | 只改元数据，秒级 | 加列（末尾）、列默认值、ENUM 追加值（8.0.16+）；有"行版本"上限（8.0.29 起 64 次） |

- 治理口径：`ALTER TABLE ... ALGORITHM=INSTANT` 显式声明，拿不到 INSTANT 直接报错，防止半夜 OOM 式 COPY（⚠️ 实践）。
- 第三选项：外部工具 gh-ost/pt-online-schema-change 承担超大表——书内提理念，运维轴细读
  [../MySQL运维内参.md](../MySQL运维内参.md)（⚠️ 存在性见 00 藏书地图）。

## 5.4 备份与恢复任务流（本章的的重头，⚠️ 转述）

1. **逻辑备份**：mysqldump `--single-transaction`（InnoDB 一致性快照，不锁表）+ `--master-data`/`--source-data`
   （binlog 位点）→ 恢复=RTO 换 RPO 的经典算式；压缩管道 `| zstd` 是书时代标配。
2. **物理热备**：备份锁（LOCK INSTANCE FOR BACKUP，8.0 新）让"拷文件"与"改文件"解耦；
   XtraBackup 类工具依赖它（⚠️ 演进：XtraBackup 后继状态见演进节）。
3. **时间点恢复（PITR）**：全量 dump + binlog 重放至 `--stop-datetime`（工具用法见 [03-使用程序和实用工具.md](03-使用程序和实用工具.md) 速查）。
4. **备份的四重身份**：恢复源 / 从库初始化 / 审计证据 / 测试数据——只当恢复源用是低估。
5. 一致性等级地图（⚠️）：冷备（停服）＞单事务快照（表间一致）＞逐表 dump（单表一致/跨表可能撕裂）＞文件级拷贝（可能根本不可用）。

## 5.5 🔧 类比实测：在线备份的"快照 vs 活库"一致性（非 MySQL 行为）

用 python `sqlite3` 3.45.3 复现"边写边备"的一致性语义（脚本 `D:\develops\tmp\dbwave_w5_myadmin\`，2026-09-27 实跑）：

- 建表灌入 1000 行 → 开后台线程以 ~2ms/行持续 INSERT → 主连接执行 `src.backup(dst)` 在线快照 →
  停线程后对账：**快照 1000 行，活库终态 1168 行**。
- 读出的机制直觉（与引擎无关）：一致性备份=把"某时刻视图"冻结外送，快照行数 ≤ 终态行数，且快照内部无撕裂；
  MySQL `mysqldump --single-transaction` 的等价物是**一个 REPEATABLE READ 长事务+MVCC 旧视图**
  （⚠️ MySQL 侧口径转述，未实测），SQLite `backup()` 则走页级复制。
- 局限声明：SQLite 无 binlog/位点概念，本实验**只类"快照自洽"**，PITR 的"全量+日志"两件套须另配 🔧 日志表实验
  （见 [08-复制.md](08-复制.md) 的序列号类比）。**非 MySQL 行为，数字不可当 MySQL 备份性能引用。**

## 核心概念速览（中英对照）

- **schema/database** — 模式/数据库：MySQL 中同义；库=目录，对象默认值的继承根。
- **字符集默认链** — charset inheritance：server→database→table→column 四层覆写，乱码定位路标。
- **lower_case_table_names** — 大小写策略：初始化定死、运行期不可变（8.0），跨平台事故高发点。
- **ALGORITHM=INSTANT** — 元数据级 DDL：加列/默认值/ENUM 追加秒完成，行版本数有上限（⚠️）。
- **INPLACE + LOCK=NONE** — 在线原地 DDL：并发 DML 允许但需建临时结构，二级索引主路径。
- **备份锁** — LOCK INSTANCE FOR BACKUP：8.0 新原语，物理热备与 DDL 的隔离阀。
- **--single-transaction** — 一致性逻辑备份开关：一个 RR 长事务+MVCC 视图冻结全库（🔧 类比见 5.5）。
- **PITR** — point-in-time recovery：全量+binlog 时间截取重放，RPO 由 binlog 保留粒度决定。
- **RTO/RPO** — 恢复时间/时点目标：备份策略的两个约束轴，演练是唯一验证手段。
- **TRUNCATE** — 截断：DDL 级清空（隐式提交、不触发行扫描），自增值按版本语义归零（8.0 重启持久，⚠️）。
- **gh-ost / pt-osc** — 外部在线改表工具：大表触发器/影子表两流派，书提理念、运维册纵深。

## 最新演进与工业实践

- **8.0→8.4 管理面变化**（⚠️ 转述）：INSTANT 的行列限制（64 行版本）促使头部厂商引入"OPTIMIZE 重建消化版本"巡检项；
  8.4 强化 binlog 安全性（`binlog_transaction_dependency_tracking` 等）反哺恢复并行度。
- **物理热备工具断代**（⚠️）：Percona XtraBackup 对 8.4 的支持节奏与 Oracle 官方 **MySQL Enterprise Backup** 并行存在；
  开源替代收敛到"dump+云对象存储"与文件级快照（存储层一致性）两条线——书内"XtraBackup 一枝独秀"语境已变。
- **自动化备份位**：云 RDS 默认自动全量+binlog 连续备份（PITR 到秒）已成用户默认预期，自建实例的 5.4 流程转为私有化合规需求（⚠️）。
- **工业口径**：Netflix/Google 级 MySQL 运维公开材料强调"备份必须定期自动回放验证"（⚠️ 转述常识，未逐条取证，故不引 URL）。
