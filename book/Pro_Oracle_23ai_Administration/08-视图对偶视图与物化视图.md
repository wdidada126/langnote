# 08 · 视图、对偶视图与物化视图（原书 Ch.9, pp.269-302）

> 章题 ✅ Crossref 实抓（DOI 10.1007/979-8-8688-1038-1_9, "Views, Duality Views, and Materialized Views"）。章内小节自拟 ⚠️。**duality 视图为 23ai 旗舰特性**：本章是全书现代性浓度最高处，Oracle 行为一律 ⚠️ 转述 + ✅ 官方文档（JSON Relational Duality Guide：https://docs.oracle.com/en/database/oracle/oracle-database/23/adjsn/index.html ，2026 起 301 至 /26/ 同名）。含 🔧 类比 1 组（非本书引擎行为）。

## 8.1 普通视图：安全与复用的第一层皮

- 视图=命名的查询，不存数据；权限以视图持有者链计算（definer 语义），"用视图收表权"是 05 章最小权限的落地件 ⚠️。
- 管理细节：`with read only` 防通过视图的意外 DML；依赖链（视图上视图）在 09 章字典视角有 `dba_dependencies` 工具位 ⚠️。
- 内联（view merging）与否归优化器（本册不开课，转盘上 [../Cost_Based_Oracle_Fundamentals/09-查询变换.md](../Cost_Based_Oracle_Fundamentals/09-查询变换.md)）⚠️。

## 8.2 物化视图：把查询变成资产

MV = 存查询结果的表 + 自动维护协议。三旋钮（⚠️）：

| 旋钮 | 选项 | 运维含义 |
|---|---|---|
| 刷新方式 | complete/fast(on commit|on demand)/forced | fast 依赖物化视图日志（mlog）与聚合可增量性 |
| 刷新时机 | commit 同步 / next 定时 / dbms_mv.refresh | 同步刷新的提交延迟 vs 定时窗口的陈旧窗口 |
| 查询重写 | enable/disable + 信任等级 | 优化器拿 MV 答原始查询=MV 的"第二生命" |

- 依赖位：快速刷新对主键/ROWID 两种 mlog、聚合 MV 的 count 伴生列要求 ⚠️——"为什么不能 fast refresh"的排查从 `dba_mview_analysis` 开始 ⚠️。
- 系统：`dba_mviews` 状态、刷新原子性（`refresh ... for upgrade`/一致性组）、回滚段压力（大 complete 刷新=04 章 UNDO 的租户）⚠️。
- 重写验证纪律：上线 MV 前后用执行计划证实/证伪"重写发生"（→09/14 取证法）⚠️。

**🔧 类比（非本书引擎行为）——MV = 触发器维护的汇总表**：SQLite 无 MV；用触发器手搭增量维护，本机 sqlite 3.45.3：

```
$ python - <<'EOF'
import sqlite3
m = sqlite3.connect(':memory:')
m.executescript("""
create table sales(amt int);
create table mv_sum(tot int); insert into mv_sum values(0);
create trigger tr after insert on sales begin update mv_sum set tot=tot+new.amt; end;
insert into sales values(5); insert into sales values(7);
""")
print(m.execute('select tot from mv_sum').fetchone())   # (12,)
print(m.execute('select sum(amt) from sales').fetchone())  # (12,) 与全量重算一致
EOF
(12,)
(12,)
```

对照点：trigger-on-insert ↔ Oracle 的 on commit 快速刷新（变更捕获→增量应用）；手搭版必须自己保证幂等/回滚/并发，Oracle 的 mlog+刷新组正是把这些坑产品化。**差异**：SQLite 无查询重写（优化器不会拿 mv_sum 答 `sum(amt)`），Oracle MV 的双身份（物化+重写）只完成了一半类比。演示于 tmp/dbwave_w4_ora23，非本书引擎行为。

## 8.3 JSON Relational Duality：23ai 的第三种范式（⚠️ 转述主干）

**问题陈述**（官方叙事 ✅ adjsn）：关系模型防脏写靠 ACID+规范化，文档模型防"对象-关系阻抗"靠 JSON 整体读写——两者互斥了二十年。Duality 的答案：**duality 视图**把一个 JSON 文档形态"映射"到一组规范化关系表，**同一数据同时是文档和关系表**，两形态原子一致。

**机制要点**（⚠️ 转述，语法细节以文档为准）：

- 元数据映射写在视图上：表/键列/嵌套集合/引用（跨表关联）声明为 JSON 形状（`json_table` 风格映射 + ORDS 注解线）；
- 写路径：客户端以整文档 upsert（INSERT/UPDATE/MERGE/DELETE 作用在视图上），引擎拆解为底层多表 DML，保持 ACID 与规范化；读路径：按形状组装文档返回；
- 冲突控制：`JSON_DUALITY$ID`/乐观锁字段族防"最后写入覆盖" ⚠️；
- 生态位：与 ORDS/REST、JDBC/Spring Data 等文档式 API 对接——"给应用开发者 DBaaS 手感、给 DBA 关系底座"（✅ adjsn 文档定位句 ⚠️ 措辞转述）。

**DBA 管理面**：duality 视图=普通对象生命周期（建/改权限/依赖进 09 字典视图族）；性能面回归 06/07 基本功（底层表的索引才是真索引——"文档是皮，B 树是骨" ⚠️ 本目录提炼）；升级注意：注解/映射元数据在 Data Pump 导出导入中的完整性（→16 章）⚠️。

## 8.4 三兄弟选择树（视图家族全景）

```
要藏复杂度?           → 普通视图
要算得起大聚合+能重写? → 物化视图
要给应用文档手感+保关系 integrity? → duality 视图(23ai)
三者可叠加: duality 视图底表上再建 MV 做分析出口 ⚠️(合法性无文档禁忌,组合案例社区尚少)
```

## 8.5 本章陷阱清单（⚠️ 原书性格重构）

1. MV fast refresh 静默退化为 complete（不满足增量条件/日志被清）——刷新时间曲线是唯一预警；
2. on commit 刷新链拉长提交延迟，OLTP 高峰期 MV 是隐形锁等待源；
3. duality 视图的嵌套集合过深→单文档 upsert 拆出的 DML 扇出爆炸，"文档简单写"的成本在底表行数；
4. 把 duality 当 ORM 自动迁移器：视图映射变更仍要版本化与回归测试（映射即 schema）；
5. 重写使测试"变快了"却答错（MV 陈旧+信任配置过宽）——`query_rewrite_integrity` 的 enforced/stale-tolerances 语义先行读懂。

## 8.6 MV 运维手册（⚠️ 命令骨架+排障树）

```sql
-- 建: 聚合增量 MV 的最小合法形(count 伴生列是 fast refresh 的门票)
create materialized view log on sales with rowid including new values;
create materialized view mv_sales_day build immediate
  refresh fast on demand enable query rewrite as
  select day_id, sum(amount) amt, count(*) cnt
    from sales group by day_id;
-- 刷: 定时窗(14 章 Scheduler 挂点)+原子性
begin dbms_mview.refresh('MV_SALES_DAY','?'); end;  -- ?=一致性模式字母示意
-- 诊: 为何退化成全量?
select mview_name, rewrite_enabled, staleness from user_mviews;
call dbms_mview.explain_mview('MV_SALES_DAY');      -- 逐Capability打钩表
select detail_msg, possible from mv_capabilities_table;
```

排障树三问：**日志在不在/新值含不含/查询形态可不可增量**——`mv_capabilities_table` 逐条给答案；"MV 上线后原始查询变慢"第一反应是重写未发生（看计划，09 章取证法），第二是 MV 自身陈旧被禁用 ⚠️。

## 8.7 duality 视图管理增量（承 §8.3，⚠️ 转述+立场）

- 对象形态盘点：duality 视图进 `dba_views`/`dba_objects` 家族（09 章视野）但**元数据映射**藏在注解/声明文本里——备份件（Data Pump）与版本控制要把"视图定义=schema 资产"级别对待（16 章联动）；
- 授权新面：应用拿"文档写权"=对视图的 DML 权，底表权限不再暴露——05 章最小权限在文档 API 时代的天然红利 ⚠️；
- 演进纪律：映射变更（加字段/改键）与底层表 DDL 是同一变更单的两半，拆开必产生"文档形与表形分叉"事故；
- 与 ORM/JPA（盘上 ../ProJPA2中文版.md 谱系）的关系一句话：**duality 视图把"映射层"从应用配置搬进数据库字典**——应用团队与 DBA 的边界重划，组织成本>技术成本 ⚠️ 本目录立场。

## 自测（能默写=过关）

- MV 三旋钮矩阵与 fast refresh 的两个前置件。
- duality 视图"一数据两形态"的读写拆解路径与乐观锁字段。
- 三种视图各自解决的成本问题一句话。

## 核心概念速览（中英对照）

- **视图** — view：命名查询，权限与复用的封装层。
- **物化视图** — materialized view：结果持久化+可自动刷新的查询资产。
- **物化视图日志** — materialized view log (mlog)：捕获底表变更供增量刷新的伴生表。
- **查询重写** — query rewrite：优化器用 MV 代答原始查询的透明加速。
- **fast/complete refresh** — 增量/全量刷新：MV 维护的两档引擎。
- **刷新组/一致性** — refresh group/atomic：多 MV 同刻度更新的成组语义。
- **对偶视图** — duality view：JSON 文档形态与关系表的同源映射对象（23ai）。
- **阻抗失配** — impedance mismatch：对象/文档与关系模型间的结构性错位。
- **JSON_DUALITY$ 字段族** — duality 内建列：文档身份与乐观锁元数据。
- **嵌套集合** — nested collection：duality 映射中一对多的数组表达。
- **ORDS** — Oracle REST Data Services：REST/文档 API 生态的承载件。
- **陈旧容忍** — stale tolerance：重写决策中对 MV 新鲜度的信任等级。

## 最新演进与工业实践

- **Duality 的 2024→2026 轨迹**：23ai GA 后文档线持续加密（✅ adjsn 主页），26ai 更名后并入 /26/ 路径（✅ 重定向实证）；社区采用集中在"Java/Spring 系应用去 ORM 化"与"遗留库加文档 API"两类场景 ⚠️ 通说；对照盘上文档/关系双模叙事：../MongoDB_The_Definitive_Guide_3e/00-总览与阅读地图.md（纯文档系）——duality 是关系阵营对同一需求的应答。
- **MV 的当代席位**：实时数仓/物化增量计算谱系（Materialize、Databricks DLT、Paimon 流式 MV）把"刷新"改写为"流"——理论线在盘上 [../Streaming_Databases/00-总览与阅读地图.md](../Streaming_Databases/00-总览与阅读地图.md) 与 [../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md](../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md)；Oracle 的 on commit/定时刷新仍是 OLTP 伴生聚合的最稳解（锁语义内建于事务）⚠️ 立场句。
- **向量时代的"视图"新解**：AI Vector Search 的检索结果组装（✅ vldbg）常用视图/duality 形态承载"向量+业务字段"的混合返回——07/08 两章在 2026 年新工作负载里合流 ⚠️ 趋势转述。
- **跨引擎对照（盘上）**：PG 物化视图（REFRESH 手工/增量无原生 fast ⚠️）与 MV 重写（query rewrite 非内建、靠扩展）的落差见 ../PostgreSQL_16_Administration_Cookbook/00-总览与阅读地图.md；DuckDB 无持久 MV（🔧 类比止步于 §8.2 的触发器方案）见 ../DuckDB_Up_and_Running/00-总览与阅读地图.md——Oracle MV 全家桶在轻量引擎普遍缺位，是"重库护城河"的活标本。
