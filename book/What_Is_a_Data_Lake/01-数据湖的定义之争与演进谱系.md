# 01 数据湖的定义之争与演进谱系

> 本章为**精读重构**：原书为 O'Reilly REPORT 短册，TOC 不可实证（见 00 §2/§3），

## 1. 为什么"什么是数据湖"在 2021 年还需要一本书来回答

短册的立题本身就是证据：到 2021 年，"data lake" 已被用了十五年，行业却仍然**没有共识定义**——
厂商说它是对象存储，架构师说它是表格式+元数据层，治理团队说它是"未经管制的仓库坟场"。
封面副题 "Evolution of Data Lakes in the Age of Cloud Computing" ✅ 把本书押注在**演进叙事**上：
不是给一个静态定义，而是讲清楚"湖"这个概念如何从本地 Hadoop 时代漂移到云时代。

作者 Alex Gorelik 的写作语境（✅ 封面署名+AWS 联名角标）：这是一本云厂商生态位上的科普短册，
目标读者是要向管理层解释"我们为什么已经/应该有一个湖"的人。

## 2. 术语起源与前史（⚠️ 转述，多源交叉）

- 2005–2006：James Dixon（Inside Analysis 分析师）被普遍追溯为 "data lake" 一词的推广者，
  动机是给"廉价、原始、可探索的分析数据池"一个与"数据仓库"对立的意象 ⚠️（原博客不可达，二手转述）。
- 2009–2014：Hadoop 分布式文件系统成为"湖"的事实载体——"湖=HDFS+Hive"是第一代通俗定义。
- 2014–2018：对象存储（S3/ADLS/GCS）接管存储层，"湖=云上对象存储+分析服务"成为第二代定义。
- 2019–2021：表格式（Delta/Iceberg/Hudi）与目录服务兴起，"湖=存储+开放表格式+统一元数据"
  成为第三代定义——本书正卡在第二代向第三代过渡的时间点上 ⚠️ 推定。

## 3. 一个可操作的解剖式定义

综合本书体裁同类册的通行讲法 ⚠️ 与 2026 年回看，可以给出一个"可证伪"的定义：

> **数据湖 = 以对象存储为底座、以开放格式存放原始到半加工各阶段数据、
> 以中央元数据目录供多引擎按需读取、读写解耦的数据存储形态。**

四个判据逐条拆：

| 判据 | 含义 | 反例（不是湖） |
|---|---|---|
| 存储与计算解耦 | 数据不活在某台服务器的本地盘里 | 单机 MySQL 的 datadir |
| 开放格式 | Parquet/ORC/JSON/原始字节，任何引擎可写 | 私有存储格式独占 |
| 多引擎按需读 | 同一份数据供 SQL/ML/流多种负载 | 每团队各拷一份 |
| 原始数据留存 | 落地先存原始，加工可重放 | 只进"清洗后"数据的管道 |

第四条最容易被忽略，却是湖与"一堆文件"的分水岭——第 04 章用 🔧 实验给数字感。

## 4. schema-on-read：定义之争背后的经济账

湖的招牌卖点"读时定形"（schema-on-read）常被说成免费午餐。🔧 E3 给出它的**真实价格**：

```
E3 schema-on-read json_extract over 5000 raw rows: 3.54ms (n=484)
   vs schema-on-write indexed column: 0.06ms (n=484)
```

同一问题（金额>450 的事件数），在原始 JSON 上现取字段比在已定型+索引的表上贵 **约 59 倍**
（答案一致，n=484）。结论不是"schema-on-read 是骗局"，而是：

1. 它的价值在**写入侧**——落地零建模、模式演进不阻塞采集（第 04 章 E1 续此线）；
2. 它的成本在**读取侧**——每次现解析，且随"湖变仓"的成熟度提升而应被逐步偿还；
3. 定义之争其实是**偿还节奏之争**：仓库派要求先建模后落地，湖派要求先落地后建模。

## 5. 与相邻概念的辨析表

| 概念 | 一句话 | 与湖的关系 |
|---|---|---|
| 数据仓库 | 写时定形、面向 BI 的成熟模型 | 对偶概念，见 03 章 |
| 数据湖仓(lakehouse) | 湖的存储+仓的语义(ACID/治理) | 湖的第三代形态，见 03 章 |
| 归档/备份存储 | 冷数据、少读、合规导向 | 湖可含归档层，但归档不是湖 |
| 对象存储桶 | 只有判据一的裸存储 | 缺格式/目录/多引擎，不算湖 |
| 特征存储 | 面向 ML 的低延迟特征层 | 湖常作其上游原料库 |
| 数据网格(data mesh) | 组织与权责架构，非存储形态 | 正交互补，对位读 [../Data_Mesh/00-总览与阅读地图.md](../Data_Mesh/00-总览与阅读地图.md) |

## 6. 常见误区（短册的"祛魅"段，⚠️ 主题重构）

1. **"买了对象存储就有湖"**——缺元数据目录与写入规范的对象存储只是文件堆（E3 的 59 倍税单）。
2. **"湖自动消灭 ETL"**——只是把 ETL 推迟成 ELT 并转移给读方，团队技能要求反而更高。
3. **"一个湖装所有负载"**——高并发低延迟点查不是湖的强项，硬上会催生沼泽（05 章）。
4. **"开源组件越多越像湖"**——组件堆砌不等于四判据齐备；判据表比产品清单可靠。

## 7. 演进谱系三段表（2026 回看补全）

| 世代 | 时期 | 存储 | 格式/元数据 | 引擎 | 本书位置 |
|---|---|---|---|---|---|
| 一代 | 2006–2015 | HDFS | Hive Metastore | MapReduce/Spark | 前史 |
| 二代 | 2015–2020 | S3/ADLS/GCS | 裸 Parquet+Glue | Athena/Presto | 本书主叙 |
| 三代 | 2020–2026 | 同上 | Delta/Iceberg/Hudi+开放目录 | 多引擎+SQL 网关 | 本书尾声⚠️/演进节 |

三代不是替代而是**叠加**：2026 年大量生产湖仍停在二代，一代残存于传统行业——
这正是"什么是数据湖"难以一句话说死的原因：不同读者的湖处在不同世代。

## 8. 本章小结

定义之争=世代错位+偿还节奏之争。带走三件东西：四判据解剖式定义、E3 的 59 倍读侧税单、
三段演进谱系。它们分别服务于沟通（对外解释"我们有什么"）、成本（对内解释"为什么慢"）、
路线（向上解释"下一步去哪"）。

## 核心概念速览（中英对照）

| 英文 | 中文 | 一句话释义 |
|---|---|---|
| data lake | 数据湖 | 对象存储+开放格式+中央目录+原始留存的解耦存储形态 |
| schema-on-read | 读时定形/读模式 | 写入不建模，读取时才解释结构；写侧免费读侧收税 |
| schema-on-write | 写时定形 | 入库前强制建模；仓库式，读快写慢 |
| object storage | 对象存储 | 扁平命名空间的云存储，湖的存储底座 |
| Hadoop Distributed File System (HDFS) | 哈杜普分布式文件系统 | 第一代湖的存储载体 |
| Hive Metastore | Hive 元数据存储 | 第一代目录服务，表→路径映射 |
| table format | 表格式 | 在文件之上补 ACID/演进的元数据协议（二代→三代分水岭） |
| ELT | 抽取-加载-转换 | 先落原始后加工，湖的默认加工次序 |
| evolution narrative | 演进叙事 | 本书副题承诺的讲法：概念随云时代漂移而非静态定义 |
| definition dispute | 定义之争 | 存储派/格式派/治理派各执一词的根因=所处世代不同 |

## 最新演进与工业实践

**2021→2026 定义漂移实录**（本书出版窗口之后，逐条标证据状态）：

1. **"data lake" 一词在厂商语境中退居幕后**，"lakehouse" 成为对外默认词——湖没有消失，
   是叙事重心从"存下来"移向"存得住且管得住"。对位实链：
   [The Data Lakehouse 总览](../The_Data_Lakehouse/00-总览与阅读地图.md)、
   [Practical Lakehouse Architecture 总览](../Practical_Lakehouse_Architecture/00-总览与阅读地图.md)。
2. **Iceberg 成为跨引擎"湖的通用语"**：规范稳定、多实现中立，2024–2026 年被各云与引擎
   竞相原生支持。规范 ✅ https://iceberg.apache.org/spec/ ；文档 ✅ https://iceberg.apache.org/docs/latest/ 。
3. **目录从附属升格为战场**：统一目录（catalog）之争取代了 2021 年"存储之争"的头条位。
   盘上对位：[Apache Polaris TDG 总览](../Apache_Polaris_TDG/00-总览与阅读地图.md)、
   [Data Governance with Unity Catalog 总览](../Data_Governance_with_Unity_Catalog/00-总览与阅读地图.md)。
4. **AWS 侧持续把"湖"产品化为托管件**（Glue 目录、Lake Formation 权限、S3 分析前缀）：
   ✅ https://docs.aws.amazon.com/glue/latest/dg/what-is-glue.html 、
   ✅ https://docs.aws.amazon.com/lake-formation/latest/dg/what-is-lake-formation.html 、
   ✅ https://aws.amazon.com/big-data/datalakes-and-analytics/ 。
5. **工业实践提醒**：写选型文档时，用本章四判据逐项打分比引用任何厂商定义都可靠；
   判据二/三在 2026 年的具体化就是"有没有开放表格式+有没有中立目录"两个问题。
6. 本书当年引用的部分组件名（如早期 EMR/Hive 组合话术）已过时 ⚠️，读时以三代表定位段落世代。
