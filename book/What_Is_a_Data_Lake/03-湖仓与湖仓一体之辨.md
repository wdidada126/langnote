## 1. 一张对账单：湖与仓的八维对照

| 维度 | 数据仓库 | 数据湖（二代） | 湖仓(lakehouse，三代) |
|---|---|---|---|
| 定形时机 | 写时定形 | 读时定形 | 写时定形可选（表格式担保） |
| 数据形态 | 结构化为主 | 全形态含原始 | 全形态+事务表 |
| ACID | 原生 | 无（靠约定） | 快照+乐观并发 |
| 新鲜度 | 批窗口 | 落地即可见但无保障 | 分钟级提交可见 |
| 负载画像 | BI/报表高并发读 | 探索/ML/批加工 | BI+探索+ML 混载 |
| 成本曲线 | 存算一体，偏贵 | 存算分离，冷数据极廉 | 近湖 |
| 治理抓手 | 库权限+约束 | 目录+约定（易沼泽） | 目录+表格式+行列权限 |
| 失败模式 | 建模慢、需求积压 | 沼泽（05 章） | 元数据层厂商绑架 |

短册式的一句话：**仓库是"先立法后建房"，湖是"先建房后立法"，湖仓是"装配式建筑"** ⚠️ 重构比喻。

## 4. 🔧 E2b/E2c：用"刷新语义"切开三者

湖/仓/湖仓最容易被忽略的分水岭是**"表更新"在物理上意味着什么**。单机实验（SQLite 3.45.3）：

```
E2b gold MV full refresh(5000 silver rows): 5.14ms vs incremental 1-partition refresh: 3.55ms
E2c quirk: 'INSERT INTO t SELECT ... ON CONFLICT(d) DO UPDATE' raises
   'near DO: syntax error' in SQLite 3.45.3 because ON after FROM-subquery
   binds as JOIN-ON; lakehouse engines' MERGE has no such trap
```

三层读法：
1. 湖（二代）没有"更新"：改一行=重写分区，所谓刷新就是 E2b 的全量重建——小数据无感，
   TB 级即灾难，这就是当年"湖不能当仓用"的物理学理由；
2. 仓有行级 UPDATE+事务，代价是存算耦合与许可成本；
3. 湖仓用 MERGE/快照把"更新"变成**元数据提交**（写新文件+换快照指针）——E2c 顺带录得的
   SQLite 语法坑（`ON CONFLICT` 在 INSERT…SELECT 形态下被解析为 JOIN-ON）恰好具象化了
   "合并语义不是 SQL 方言小事，而是存储引擎能力声明"：湖仓阵营的卖点就是把 MERGE
   做成一等公民 ✅ https://iceberg.apache.org/spec/ 。

## 5. 三选一？决策树（⚠️ 主题重构）

```
数据全形态且要留存原始？ ──否──► 传统仓库/云仓够用
        │是
需要 BI 级并发与行级权限直接压在湖上？ ──否──► 二代湖+独立集市
        │是
接受引入表格式+中立目录的复杂度？ ──否──► 云厂商托管湖仓套件 ⚠️
        │是
        ▼
      湖仓（三代湖），并预留"目录迁移"退路
```

2021 年本书能给出的答案止于前两行；第三、四行是出版窗口后三年才成形的行业共识 ⚠️——
这正是短册的宿命：**它负责让你问对问题，答案要自己续**。

## 6. 与"云数据仓库"的三角关系

湖⇄仓⇄湖仓之外还有第四极：云仓（Snowflake/BigQuery/Redshift）自带存储抽象，
与湖的关系是"互相伸向对方领地"：云仓长出对湖表的直读（Iceberg 支持竞赛），
湖长出云仓级语义。盘上对位实链：[Snowflake TDG 总览](../Snowflake_The_Definitive_Guide/00-总览与阅读地图.md)、
[Amazon Redshift TDG 总览](../Amazon_Redshift_TDG/00-总览与阅读地图.md)。
选型时把"谁拥有你的字节"问三遍，胜过读十页对比文章。

## 7. 成本视角的老实话

湖便宜在**冷数据与探索负载**，贵在**工程人力与失控治理**；仓贵在每个字节的许可与算力，
省在没人也能跑。E2b 的"全量重建 vs 增量刷新"在真实体量下就是两家的成本曲线交叉点：
数据量×重算频率×单价，三个乘数谁大都足以翻盘——用自家账单算，别用任何一本书的直觉算 ⚠️。

## 8. 本章小结

八维对账单管沟通、验收清单管选型、E2b/E2c 管物理直觉。湖仓不是湖与仓的中间态，
而是"湖补上了仓欠的账"——ACID、MERGE、时间旅行、统一权限四张欠条在 2021–2026 间陆续兑付。

## 核心概念速览（中英对照）

| 英文 | 中文 | 一句话释义 |
|---|---|---|
| data warehouse | 数据仓库 | 写时定形、面向 BI 的成熟模型化存储 |
| lakehouse | 湖仓一体 | 湖存储+仓语义（ACID/时间旅行/统一权限） |
| ACID transactions | 事务原子性一致性隔离持久性 | 湖仓的入场券，二代湖的缺失项 |
| time travel | 时间旅行 | 按快照读历史/回滚，元数据指针切换 |
| MERGE / upsert | 合并写入 | 湖仓一等公民；SQLite 语法坑反证其非小事 |
| materialized view refresh | 物化视图刷新 | 全量重建是二代湖之痛，增量刷新是能力声明 |
| optimistic concurrency | 乐观并发控制 | 表格式靠冲突检测让多写者共存 |
| dimensional modeling | 维度建模 | Kimball 路线，金层尽头仍是模型 |
| cloud data warehouse | 云数据仓库 | 存算分离但字节归属需警惕的第四极 |
| verification checklist | 验收清单 | 把"湖仓"从口号还原为五问 |

## 最新演进与工业实践

**2021→2026 兑付进度表**（逐条标证据状态）：

1. **MERGE/ACID 已成湖表默认期待**：三格式均提供冲突可检测的提交协议，规范入口 ✅
   https://iceberg.apache.org/spec/ ；Delta 文档 ✅ https://docs.delta.io/index.html ；
   Hudi ✅ https://hudi.apache.org/docs/overview/ 。
2. **云仓直读开放表格式竞赛**（2024–2026 头条）：湖与仓的边界从"格式墙"变成"目录墙"，
   对位实链 [Apache Polaris TDG 总览](../Apache_Polaris_TDG/00-总览与阅读地图.md)（开放目录栈）。
3. **流进湖仓**：03 章的"分钟级提交可见"在 2026 年由流式表格式承接，盘上实链
   [Apache Paimon Streaming Lakehouse 总览](../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md)。
4. **工业实践**：迁移评估用 §3 五问逐项打分；对任何"湖仓"产品先问"快照存在谁的元数据里"；
   BI 并发压测必须在自家权限模型下做，跨引擎的裸性能数字无意义 ⚠️。
5. **本书原叙事的时效注脚**：2021 年"湖仓是否伪概念"之辩已熄火，代之以"目录中立性"之争——
   问题在演进，方法（对账单+验收清单）不过时。
