## 1. 五层解剖总览

把"云上数据湖"当作一台机器拆开，自下而上五层（2021 二代湖典型切分，⚠️ 主题重构）：

| 层 | 职责 | AWS 代表件 ⚠️ | 对位概念锚 |
|---|---|---|---|
| 存储层 | 廉价持久、无限扩展的字节 | S3（含存储类别分层） | 对象=键+值+元数据 |
| 格式层 | 字节的结构语义 | Parquet/ORC/JSON/Avro | 列式 vs 行式 |
| 表/元数据层 | 文件集合→可查询的"表" | Glue Data Catalog；（三代补）Iceberg/Delta/Hudi | 目录=湖的门面 |
| 接入层 | 把数据搬进湖并保持可重放 | Kinesis/Firehose/Glue 爬虫与作业 | 批/流/变更三入口 |
| 计算层 | 按需读取回答问题 | Athena/EMR/Redshift Spectrum | 引擎与存储解耦 |

短册的叙事价值在于反复强调：**层间解耦才是湖，堆齐五件产品不等于湖**。

## 2. 存储层：对象存储不是"云盘"

- 扁平命名空间：路径里的 `/` 只是键名前缀，没有真目录；"列目录"是前缀扫描，
  海量小文件会让最普通的 `ls` 变成性能事故——这是湖运维的第一课 ⚠️。
- 持久性与局部性：设计假设是"对象即宇宙"，任何计算节点可死，数据不跟节点走。
- 成本分层：标准/低频/归档等存储类别按访问画像降钱 ✅
  https://aws.amazon.com/s3/storage-classes/ 。湖的原始层是分层策略的最佳客户（04 章续）。

## 3. 格式层与"原始留存"的落点

湖对格式的态度是**分层宽容**：原始落地层允许任意字节（JSON/CSV/日志/二进制），
加工层再收敛到列式（Parquet/ORC）。🔧 E1 在单机上复演这套"原始先行"的账本：

```
E1 bronze insert 5000 rows: 30.8ms | silver build: 5.7ms | gold agg: 1.5ms
E1 layer counts (bronze,silver,gold): (5000, 5000, 1)
E1 re-derive silver from retained bronze after logic change: 12.6ms;
   new col prem non-null rows=0 (field absent in 2026-10-01 raw)
```

三行读法：
1. 原始层(bronze)只追加存 JSON 文本，5000 行 30.8ms——写入侧零建模，兑现 01 章 E3 说的"写侧免费"；
2. 银层/金层是**投影**不是仓库：5.7ms/1.5ms 随时可弃可重建；
3. 逻辑变更后从留存的 bronze 重导 silver 仅 12.6ms——**可重放性是原始留存的全部意义**；
   但新字段 `premium` 在当天原始数据里根本不存在（non-null=0），重放也造不出来——
   原始留存保的是"已发生的事实"，不是"未采集的字段"。这条边界在 04 章展开。

## 4. 表/元数据层：湖的门面，三代的分水岭

- 二代形态：目录=「表名→S3 前缀→分区列表」的映射（Glue 爬虫靠猜 schema ⚠️）。
- 痛点：文件列表即真相，缺 ACID、缺快照、缺模式演进保障 → 05 章沼泽的制度根源。
- 三代形态：表格式在文件之上加一层**事务性元数据**（快照清单），引擎先读快照再读文件。
  盘上深读实链：[Apache Iceberg 活用入門 总览](../Apache_Iceberg活用入門/00-总览与阅读地图.md)、
  [Architecting an Apache Iceberg Lakehouse 总览](../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md)、
  [Apache Hudi TDG 总览](../Apache_Hudi_Definitive_Guide/00-总览与阅读地图.md)、
  [Engineering Lakehouses with Open Table Formats 总览](../Engineering_Lakehouses_with_Open_Table_Formats/00-总览与阅读地图.md)。

## 5. 分区与裁剪：🔧 E5 的诚实读数

湖的查询性能第一杠杆是**少读文件**（分区裁剪），第二才是格式列裁剪。单机类比：

```
E5 31000-row fact: single-table date filter 1.61ms vs partitioned-view pruned 0.77ms;
   results equal: True
   plan: SCAN fact_p1 / SCAN fact_p2   (两个分支都被扫描)
```

诚实解读：SQLite 的执行计划**并没有做分支消除**（两个分表都扫了），0.77ms 的优势来自
分表更小、扫描局部性更好，而非真裁剪。这恰好反证：**分区裁剪必须是引擎/表格式的合同义务**
——Iceberg 在规范层承诺分区演进与谓词裁剪 ✅ https://iceberg.apache.org/docs/latest/partitioning/ ；
裸目录分区（Hive 式）则全靠查询方自觉，Athena 类引擎用分区投影等技巧打补丁 ⚠️。
在对象存储上，"列文件清单"本身就是钱和时间，裁剪失效的代价比单机大几个数量级。

## 6. 接入层：三种入口，一个纪律

| 入口 | 典型件 ⚠️ | 纪律 |
|---|---|---|
| 批量投递 | Glue 作业/第三方 ETL | 每批带清单(manifest)，失败整批重放 |
| 流式追加 | Kinesis/Firehose | 落地先原样存，窗口合并小文件 |
| 变更捕获(CDC) | 数据库日志→湖 | 事件带源时间戳，湖内不就地改 |

共同纪律一句话：**入口层永远写"发生了什么"，不写"我认为它意味着什么"**——
解释留给银层以下，这是 04 章新鲜度工程的前提。

## 7. 计算层：多引擎共享一份真相

Athena（交互式 SQL）/EMR Spark（重加工与 ML）/Redshift Spectrum（仓查湖表）⚠️ 同读一份
S3 数据是"湖"对"每队一库"的核心优势。对位读：
[Trino TDG 总览](../Trino_The_Definitive_Guide_2e/00-总览与阅读地图.md)（开源联邦 SQL 引擎视角）。
注意二代湖的多引擎共享是**读共享、写独占**：两个引擎同时写一张 Hive 表=事故；
写共享要等三代表格式的并发控制（03 章）。

## 8. 参考架构一图流（文字版）

```
源系统/事件/日志
   │ (批/流/CDC 三入口，写"发生了什么")
   ▼
S3 raw/ ──── 原始留存+存储类别分层（04 章）
   │ ELT（Glue/Spark，解释语义）

Athena / EMR / Spectrum / ML 训练集（多引擎读同一真相）
```

## 9. 本章小结

五层各自可换、解耦是本质；E1 给了原始留存的账本与边界，E5 给了"裁剪是合同义务"的反证。
架构选型评审时按层提问：存储换得起吗？格式开放吗？目录中立吗？入口可重放吗？引擎被绑架吗？

## 核心概念速览（中英对照）

| 英文 | 中文 | 一句话释义 |
|---|---|---|
| decoupled storage & compute | 存算解耦 | 湖架构的第一性原理，节点可死数据不动 |
| flat namespace | 扁平命名空间 | 对象存储无真目录，前缀扫描即"列目录" |
| storage class | 存储类别 | 按访问频度分档计价，原始层是最佳客户 |
| bronze/silver/gold | 铜/银/金三层 | 原始→清洗→汇总的投影链，下层可重放上层 |
| raw retention | 原始留存 | 保已发生事实，使逻辑变更可重放；救不了未采集字段 |
| replayability | 可重放性 | 从原始层重算一切的能力，湖的保险单 |
| data catalog | 数据目录 | 湖的门面：表→路径→分区的中央登记处 |
| partition pruning | 分区裁剪 | 少读文件的引擎级承诺，裸目录不担保 |
| CDC (change data capture) | 变更数据捕获 | 以事件日志形式把源库变更追加进湖 |
| shared reads, exclusive writes | 读共享写独占 | 二代湖的多引擎现实，写共享属三代 |

## 最新演进与工业实践

**2021→2026 架构层演进**（逐条标证据状态）：

1. **表格式三代战争以 Iceberg 中立性胜出为主调**：分区演进、隐藏分区、快照回滚进入
   规范承诺 ✅ https://iceberg.apache.org/spec/ ；盘上深读
   [Apache Iceberg 活用入門](../Apache_Iceberg活用入門/00-总览与阅读地图.md)。
2. **对象存储侧出现"托管湖表"形态**（存储厂商直接内建 Iceberg 表服务）⚠️ 本书出版后事项，
   方向与 04 节"目录升格"合流；选型时注意别把表服务用成新的厂商绑架件。
3. **Delta 阵营文档入口迁移** ✅ https://docs.delta.io/index.html ；Hudi 概览
   ✅ https://hudi.apache.org/docs/overview/ ——两格式与 Iceberg 的"元数据层三选一"
   仍是 2026 年架构评审的常规议题，对位实链
   [Data Lakehouse in Action 总览](../Data_Lakehouse_in_Action/00-总览与阅读地图.md)。
4. **Azure 侧对位件**：ADLS Gen2 给对象存储补了真目录语义 ✅
   https://learn.microsoft.com/en-us/azure/storage/blobs/data-lake-storage-introduction ，
   证明"扁平命名空间之痛"是行业共识而非 AWS 独有。
5. **工业实践清单（2026 通行）**：小文件合并作业常态化；raw 层禁止一切 UPDATE/DELETE；
   目录登记纳入 CI 检查（表未登记=不许上线）；入口层 manifest 化以便整批重放。
6. 🔧 读数边界再声明：E1/E5 全部为 SQLite 3.45.3 单机水位，**非本书平台（S3/Glue/Athena）
   行为**，只用于建立"重放成本/裁剪收益"的数量级直觉。
