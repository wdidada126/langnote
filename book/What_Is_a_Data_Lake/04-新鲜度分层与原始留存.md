# 04 新鲜度、分层与原始留存工程

> 本章为**精读重构**（原书 TOC 不可实证，见 00 §2/§3），是短册"演进"副题在工程侧的纵深：
> 2021 年云湖叙事里最含糊的三件事——多快、分几层、原始留多久——本章用 🔧 实验钉出数字感。
> 实验为 SQLite 3.45.3 单机类比，**非本书平台行为**。

## 1. 新鲜度是三层账，不是一层

一条数据从世界发生到金层可查，经过三个时刻：**事件时间(event time) → 入湖时间 → 提交时间**。
任何一层的水位都可能落后于前一层，所以"湖里的数据新鲜吗"必须按层分别回答。🔧 E2：

```
E2 freshness watermark lag at ref 2026-10-02T00:00:
   silver event-time lag=420s; bronze ingest-time lag=43200s
```

同一时刻查两套水位：银层事件时间水位差 7 分钟，铜层入湖时间水位差 12 小时——
因为 bronze 的 ingested_at 记录的是投递批次时刻，而事件时间戳来自流内。**汇报新鲜度时
说清你在报哪一层的哪一个时间**，是湖治理的第一条军规。工程语义的正源在流处理的水位线：
实链 [Streaming Systems 总览](../Streaming_Systems/00-总览与阅读地图.md)、
[Streaming Databases 总览](../Streaming_Databases/00-总览与阅读地图.md)。

## 2. 新鲜度 SLO 的分解式

把"报表要 15 分钟内的数据"拆成延迟预算（⚠️ 通行方法论转述）：

| 段 | 典型延迟 | 压缩手段 |
|---|---|---|
| 采集→入湖 | 秒~分钟（流）/小时（批） | 换流式入口、加投递并发 |
| 入湖→银层提交 | 调度周期（5–60 分钟） | 增量批、事件驱动触发 |
| 银→金刷新 | 全量重建分钟~小时 | 增量刷新（见 03 章 E2b） |
| 查询可见 | 引擎缓存/快照隔离 | 快照提交即见（三代湖优势） |

🔧 E2b 复演了第二行的账：全量刷新 5.14ms vs 增量 3.55ms（5000 行规模下差 1.5 倍；
规模上去后差距按数据量比放大——这正是 03 章"重算物理学"的续集）。

## 3. 分层：medallion 是职责合同不是目录名

铜/银/金（bronze/silver/gold）在 2021 年由加工叙事流行 ⚠️。本章把它读成**三张职责合同**：

| 层 | 承诺 | 禁止 |
|---|---|---|
| bronze | 原样、全量、只追加 | 禁止 UPDATE/DELETE/清洗 |
| silver | 定型、去重、口径一致 | 禁止聚合（保行级可追溯） |
| gold | 面向消费品的聚合/宽表 | 禁止作为重放源（可弃） |

🔧 E1 的三行读数（30.8ms 入铜 / 5.7ms 建银 / 1.5ms 炼金）说明分层在计算上近乎免费，
贵的是**纪律**：谁破坏"bronze 只追加"，谁就把 12.6ms 的重放保险单撕掉了。

## 4. 原始留存的价值与边界

E1 第四行是全章最重要的一条实测：逻辑变更后从 bronze 重导 silver 只要 12.6ms，
但新字段 `premium` 的 non-null 行数=0——**重放能恢复"没算对的"，不能恢复"没收到的"**。
推论出原始留存的三条硬规则：

1. 留存的对象是**完整 payload**（含未来才想用的字段），不是查询投影后的列；
2. schema 演进按"只加不减"管理，删字段=丢历史（SQLite 类比里 bronze 存 JSON 原文正是此意）；
3. 留存期由"最晚可能改主意的那天"决定，不由磁盘价格决定——成本问题交给存储类别分层
   ✅ https://aws.amazon.com/s3/storage-classes/ （归档层放 raw 是教科书搭配）。

## 5. 小文件：新鲜度的暗税

把 E2 的 SLO 分解倒过来看：每缩短一档提交间隔，文件数按倍数涨。对象存储的每请求计费与
清单扫描成本（02 章扁平命名空间之痛）意味着**新鲜度提升的账单在存储侧**。通行对策 ⚠️：
入口微批合并、后台 compaction 作业、查询引擎侧元数据缓存。三代表格式把 compaction
做成了提交协议的一部分 ✅ https://iceberg.apache.org/docs/latest/ ，二代湖只能靠自研工单。

## 6. 观测：把三层账变成日报

新鲜度/分层/留存三件事各自的可观测指标（⚠️ 主题重构，对位深读
[What Is Data Observability 总览](../What_Is_Data_Observability/00-总览与阅读地图.md)）：

| 面 | 指标 | 报警语义 |
|---|---|---|
| 新鲜度 | 各层水位滞后秒数 | 超 SLO 预算即呼人 |
| 分层 | 层间行数守恒（bronze→silver 对账） | 缺口=丢数据或违约清洗 |
| 留存 | raw 最早日期、恢复演练通过率 | 从未演练=没有备份 |
| 小文件 | 单分区平均文件字节数 | 低于阈值触发合并 |

🔧 E4 的教训（见 05 章）也属此表：无对账时，100 个重复键与空主键会静默进入银层。

## 7. 落地节奏建议（短册的"明天做什么"层）

1. 第一周：给现有湖的每张出口表标注"它属于铜/银/金哪张合同"，标不出的就是沼泽信号；
2. 第一月：水位滞后日报上线（E2 式两行 SQL 即可起步）；
3. 第一季：做一次"从 raw 重放重建某张金表"的演练（E1 式），记录耗时与缺口字段；
4. 半年：把"没收到的字段"清单（E1 的 prem 教训）反馈给采集侧，闭环 schema 演进。

## 8. 本章小结

新鲜度=三层账（按层按时间报），分层=三张合同（纪律比结构贵），原始留存=有边界的保险单
（救算错、不救漏收）。三件武器都能用 🔧 实验在三十秒内向团队演示——短册的深度不在页数，
在于给了可执行的追问句式。

## 核心概念速览（中英对照）

| 英文 | 中文 | 一句话释义 |
|---|---|---|
| event time / ingest time / commit time | 事件/入湖/提交时间 | 三个水位，报新鲜度先说报哪个 |
| freshness SLO | 新鲜度服务等级目标 | 延迟预算分解到四段，逐段可压 |
| watermark | 水位线 | 流语义中"该时间前数据已齐"的声明，湖侧借用 |
| medallion architecture | 奖牌分层架构 | 铜/银/金=三张职责合同而非三个目录 |
| append-only | 只追加 | bronze 的天条，重放保险单本身 |
| payload retention | 完整载荷留存 | 存原文不存投影，为未来字段留门 |
| schema evolution | 模式演进 | 只加不减；删字段=销毁历史 |
| small file problem | 小文件问题 | 新鲜度提升的存储侧暗税 |
| compaction | 文件合并 | 把暗税摊回后台的机制，三代湖内建 |
| recovery drill | 恢复演练 | 从未从 raw 重放过=没有留存 |

## 最新演进与工业实践

**2021→2026 新鲜度与留存工程演进**（逐条标证据状态）：

1. **提交间隔从小时级卷到分钟级**：对象存储出现托管式自动分区/自动合并服务 ⚠️（本书后事项），
   "小文件"作为日常运维话题在托管栈中淡出，在自管栈中仍是头号事故源。
2. **流式湖仓合流**：新鲜度 SLO 的极限形态（秒级提交可见）由流原生表格式承接，盘上实链
   [Apache Paimon Streaming Lakehouse 总览](../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md)；
   Iceberg 侧行级模式变更与删除向量进入规范 ✅ https://iceberg.apache.org/spec/ 。
3. **可观测平台化**：水位滞后/完整性对账成为数据可观测产品的标配探针，对位实链
   [What Is Data Observability 总览](../What_Is_Data_Observability/00-总览与阅读地图.md)。
4. **合规留存与删除的双向工程**：原始留存义务（§4）与"被遗忘权"删除义务在 raw 层相遇，
   2026 年通行做法是 raw 层加密分箱+删除清单传播 ⚠️，治理侧深读
   [Understanding Data Governance 总览](../Understanding_Data_Governance/00-总览与阅读地图.md)。
5. **工业实践**：把 §7 四步做成季度例行（演练留痕），新鲜度数字进数据产品页脚（用户可见）；
   存储类别生命周期规则与重放演练互为保险 ✅ https://aws.amazon.com/s3/storage-classes/ 。
6. 🔧 读数边界：E1/E2/E2b 为 SQLite 3.45.3 单机水位，**非本书平台行为**；真实云湖的
   延迟构成多出的网络/排队/冷启动项，预算表要按自家链路重测。
