## 核心精讲

### 2.1 四层抽象：从"当前版本"到"扫描任务"

```text
L0 指针     当前版本是谁（catalog / 最新完成文件 / 最大版本号）
L1 快照     一次提交 = 一个新快照（snapshot / instant / version）
L2 清单     打包的文件元数据（分区值、行数、列统计）
L3 数据     Parquet/ORC + 行级"影子文件"（delete file / log / DV）
```

规划 = L0→L1 一跳，然后**只读需要的那部分 L2**，产出 L3 任务列表。
分层的全部动机：亿级文件规模下，让绝大多数文件在绝大多数查询里
**连统计都不必被读出**。

### 2.2 通用原子提交：三条公理推出同一套协议

对象存储提供：①整文件原子可见（写完才能读到）；②强一致读（2020 后主流云）；
③（有限提供的）条件创建（`If-None-Match:*`，S3 于 2024-11 🔧）。
由此三格式收敛到同一提交形状：

```text
并行写 L3 数据（不可变）
→ 写 L2 清单与 L1 快照文件（自身不可变）
→ 【原子一步】切换"当前版本"指针
     Iceberg：catalog CAS（metadata-location A→B）
     Hudi：   instant 文件状态推进（requested→inflight→completed）
     Delta：  原子创建 _delta_log/(N+1).json（先到先得）
失败方：清理或留下孤儿，等异步回收；读端永远看到完整快照。
```

对照 [../数据库系统概念6/16-恢复系统.md](../数据库系统概念6/16-恢复系统.md)：
L1/L2 文件即 WAL；checkpoint/manifest 即 fuzzy checkpoint 的产物；
"删除孤儿"即对未提交事务的 undo。不同处：湖仓没有后台 fsync，
**每一次提交都是一次"全量 WAL 截断 + 快照"**。

### 2.3 Iceberg 布局（详版见第 3 章）

```text
metadata.json ─ snapshots[] ─▶ manifest-list ─▶ manifest(Avro) ─▶ DataFile 条目
                                   │裁剪①：分区字段摘要            │裁剪②：列 min/max
```

特征：清单**树状且可复用**——新提交只追加新 manifest、重写一层 manifest-list；
当前状态是**写进去的**（快照直接引用可见文件集），规划不需要重放历史。

### 2.4 Hudi 布局（详版见第 4 章）

```text
.hoodie/<instant>_<action>.<state>          ← Timeline：可见性 = 最新 completed
.hoodie/metadata/                            ← 内部元数据表（record index、
                                                files、column_stats、txn…）
<data>/pt=.../filegroup-<uuid>_<ts>.parquet  ← file group + (MOR) log files
```

特征：**时间线是首要抽象**、且 Hudi 把大量清单信息搬进"表内的表"（MDT），
读端按 instant 定位有效文件集，增量消费沿时间线推进——布局为管线服务。

### 2.5 Delta 布局（详版见第 5 章）

```text
_delta_log/0…0.json      每版本一个 commit（动作流：metaData/txn/add/remove/…）
_delta_log/…checkpoint   每 N 版物化一次"当前状态"（V2 checkpoint 含统计与 DV 摘要）
```

读版本 V = 最近 checkpoint + 重放其后至 V 的 commit。
当前状态是**算出来的**：commit 极轻（追加动作），重放成本靠 checkpoint 摊平。
这与 2.3 构成元数据设计的两极，第 6 章会看到它如何影响高频小提交的稳定性。

### 2.6 规划裁剪链与元数据经济学

| 阶段 | 裁剪依据 | 跳过的代价 |
| --- | --- | --- |
| manifest/checkpoint 级 | 分区值摘要 | 漏写统计 → 整层失效 |
| 文件级 | 列 min/max、null 计数 | 统计随重排失真（8 章） |
| 行组级（引擎/Parquet） | footer 统计 | 表格式不管理，但受文件布局影响 |

维护的"隐性账本"：清单本身要写（提交放大）要读（规划延迟）。
Iceberg 用树控制写放大、Hudi 用 MDT 控制读放大、Delta 用 checkpoint 折中。
**表格式的第一性能指标不是扫描吞吐，而是"规划一跳读多少字节"。**

### 2.7 time travel：三套版本坐标系

| 维度 | Iceberg | Hudi | Delta |
| --- | --- | --- | --- |
| 版本形态 | snapshot-id + parent 链 | instant time（毫秒） | 单调递增 version |
| 锚定手段 | refs（branch/tag） | savepoint / branch | tag / branch（🔧） |
| 可回放下界 | expire 保留（默认 5 天类） | cleaner 保留 instant 数 | VACUUM retention（默认 7 天） |
| 跨版本读文件 | 旧 manifest 仍完整 | 旧文件组版本 + MDT | 重放至该 version |

共同结论：**time travel 的能力上限 = 元数据保留 ∩ 数据保留**；
任何"永久审计"需求都要把它翻译成保留策略（8.5），而不是依赖格式魔法。

## 三格式布局速记

```text
Iceberg：快照是"引用树"（当前状态写出来）      ——提交稍重、规划最省
Hudi：  快照是"时间线"（可见性+动作状态机）    ——为增量/CDC 而生
Delta： 快照是"日志尾"（重放+checkpoint 缓存） ——提交最轻、规划靠缓存
```

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "元数据树 = 目录结构" | 树是文件引用集合的逻辑结构，物理目录可以完全打散（隐藏分区） |
| "有元数据就不用管统计" | 裁剪只信统计；统计滞后/缺失时布局再优雅也全表扫 |
| "三格式版本可互换" | 版本坐标系不同，互操作期要按"同一份数据的哪一刻"对齐（10 章增量读） |
