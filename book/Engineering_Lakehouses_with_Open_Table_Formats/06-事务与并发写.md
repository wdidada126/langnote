## 核心精讲

### 6.1 锁不了文件，就锁版本

数据库悲观锁依赖"锁管理器 + 可阻塞的资源"。湖仓里：
数据文件**不可变**、元数据提交是**一次性切换指针**——冲突只可能发生在
"两个快照对同一文件集有互斥意图"时。这正是教科书 OCC 的成立条件
（[../数据库系统概念6/15-并发控制.md](../数据库系统概念6/15-并发控制.md) 15.5 节多版本+乐观路径）：

```text
悲观：读时加锁、写时等待      → 对象存储无租约、引擎无协调者，放弃
乐观：随便写、提交时检验交集  → 代价 = 校验元数据 + 可能的整作业重跑
```

所以三格式**全部是乐观并发 + 快照隔离读**；差异在：
① 校验什么（冲突粒度），② 在哪里仲裁（原子性锚点），③ 允许多弱的一致性意图。

### 6.2 通用提交生命周期

```text
① 准备：并行写数据/清单文件（各自不可变，互相不干扰）
② 检测：从"当前版本"出发，比较本事务的
        读窗口（我扫过哪些文件/谓词）× 竞态事务的写窗口（它 add/remove 了什么）
③ 仲裁：原子换指针（CAS / 条件写 / rename）
失败 → 基于新"当前版本"重算可安全保留的部分；不能保留则重跑或报错
```

关键工程事实：**②的"读窗口"从哪来，三家不同**——Iceberg 用操作声明的
"保护/删除集合"，Delta 用查询计划期埋的谓词注解（预测读集），
Hudi 用索引层面"同 key 重叠"判定。粒度越接近真实读集，假冲突越少、吞吐越高。

### 6.3 Iceberg：按操作对做校验（Spec 附录 E）

提交 = 追加新 snapshot + metadata.json，catalog `commit(当前指针, 新指针)` CAS。
CAS 失败后，对"期间竞态提交"做 **validation**（教学示意，规则依据 Spec 概念整理）：

| 竞态写 | 我的操作 | 典型判定 |
| --- | --- | --- |
| 并发 append 了新文件 | overwrite/replace 分区 | 通常**可合并**：把竞态新增保留为新文件（或按引擎策略） |
| 竞态删除/替换了我要读的文件 | delete/update（coordinated writes） | **冲突**：基于旧快照的行位置失效 |
| 竞态做了 schema/partition spec 更新 | 我的提交带元数据变更 | **序列化合并**（append-type）或要求重新基于新元数据规划 |
| 竞态 expire snapshots | 任何引用被删快照的事务 | 提交失败（引用已死） |

Spark 命令映射：append=盲加最宽松；`overwrite`/`delete`/`update`/`merge`
会声明"被删文件集"作为校验对象。特性旁路：`write.validate-from-latest` 类表属性
（各实现命名略异）控制校验严格度。

### 6.4 Delta：两档隔离级别 + 预测读集

协议定义（Transaction Log Spec）：

- **Serializable**：读写集都要校验；
- **WriteSerializable**（默认）：仅写-写与"读窗口被覆写"时冲突，
  允许盲覆写型并发（ETL 常态）。

冲突检测依赖 **verified annotation**：读端在扫描计划里记录
`AddFilesReadPredicates`（我用了什么谓词+读到的文件指纹），提交时与竞态
commit 的 `remove/add` 做谓词-分区匹配。🔧 **Predictive Read Optimization** 把
读集从"显式文件列表"换成"谓词"，竞态提交不必精确枚举文件也能判无冲突——
**大幅削减"元数据读放大导致的假冲突"**。

典型矩阵（概念版）：

```text
        append     blind-overwrite    UPSERT/DELETE(带读集)
append    合并         合并               合并
overwrite 合并        后提交者胜出?      冲突→重试
upsert     合并        冲突→重试          读集重叠才冲突
```

（"后提交者胜出"仅 writeSerializable 且无读依赖时成立；细节以协议表为准。）

### 6.5 Hudi：Timeline 状态机 + MDT 锁表

- **无 MDT（传统）**：instant 文件名推进即仲裁——两个写者同时
  `x_commit.requested` 只有一个能 rename 成功；失败者整体回滚重来。
  粗粒度、易在流+批混合时产生 **写者饥饿**；
- **MDT 开启（OCC 正规军）**：`txn` 元数据表承担"当前活动写者注册 +
  冲突检测"：写者登记 requested instant，完成时校验竞态 instant 的
  文件重叠（按 record key 范围/文件布局），再推进 timeline；
- Hudi 特有交错：**compaction 作为 replacecommit** 与增量写并发是
  教科书级"读旧写新"案例——协议保证读端在 compact 完成前继续读旧 base、
  完成后原子切新，期间进来的 upsert 会重放/迁移到新文件组。
- 表服务与写者的配额纪律（第 8 章）：`async` 服务积压 = 冲突概率上升。

### 6.6 原子性锚点：换指针到底靠什么

| 格式 | 首选锚点 | 无 catalog/裸存储时的退化 |
| --- | --- | --- |
| Iceberg | catalog 事务（JDBC/REST/锁表；Nessie 级联） | Hadoop catalog 的 fs rename（非原子，需 lock） |
| Delta | _delta_log 条件创建（S3 条件写🔧/DynamoDB 锁/HDFS） | 无：多版本竞争会**丢版本或脑裂**（"S3 不安全时代"靠 multipart 技巧） |
| Hudi | Timeline 原子 rename / MDT txn | S3 条件写或 Timeline Service（DynamoDB） |

历史注脚：2024-11 S3 推出**条件写**（`If-None-Match`）前，"原子创建"在
主流对象存储上要么没有、要么靠脆弱技巧；**这是"湖仓必须先有 catalog 层"
的根本原因**，也解释了第 9 章 catalog 为何成为竞争焦点。

### 6.7 实践手册

1. **编排写者**：同表多管线是常态而非例外——用"分层写"（append 层与
   UPSERT 层分离）或"单写者 + 队列"（第 10 章）压制冲突；
2. **重试要可重放**：数据文件已写完、仅指针没换成功的事务，
   重试应复用已写文件（Iceberg `ReplacedFile` 重用/Delta 重规划），
   否则一次冲突 = 重跑整个 Spark job；
3. **盯三个指标**：提交重试率、单事务元数据读字节、
   冲突错误类型分布（`ConcurrentAppend` vs `ConcurrentDeleteOfReadFile`）；
4. **隔离现象自测**：开两个 session，A 读快照中、B 提交覆写、
   A 继续执行——验证"读到的是快照还是混合态"，可加深快照隔离理解
   （对照 [../数据库系统概念6/14-事务.md](../数据库系统概念6/14-事务.md)）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "OCC = 有冲突就重跑作业" | 三家的冲突检测都在**提交时刻**；多数竞态可"合并后重提交"，重跑的是少数 |
| "快照隔离保证不丢更新" | 否：盲写/写Serializable 语义下，后写者静默盖掉前写者是**特性**；要防丢需可串行化档或管线编排 |
| "catalog 只是找表的目录" | catalog 同时是**并发仲裁点**：它的吞吐与可用性直接等于表的写可用性（第 9 章） |
| "读端不提交就不会影响写端" | 长读 → 阻碍 expire/vacuum → 元数据链变长 → 写端校验变慢；读写成本在时间维度耦合 |
