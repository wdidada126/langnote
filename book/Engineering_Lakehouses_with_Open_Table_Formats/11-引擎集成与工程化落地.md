## 核心精讲

### 11.1 集成深度矩阵（谁支持到什么程度）

| 能力 | Iceberg | Hudi | Delta |
| --- | --- | --- | --- |
| Spark 读/写/DDL | 原生（DS v2） | 原生 + 视图 | 原生（最顺） |
| Flink 流读/流写 | ✅（UPSERT 靠 eq delete） | ✅✅（最成熟） | 有限（社区 connector/轮询） |
| Trino/Presto | ✅（读强，写/DML 渐进） | ✅（读为主） | ✅（读为主） |
| Flink/Spark 之外的 Python/DuckDB/ClickHouse | 通过 REST/直读，生态扩张最快 | 弱 | 中（deltalake-rs/Delta-rs） |
| 维护过程（compaction 等） | Spark/Flink/独立作业 | 内置服务（表服务自带） | Spark 作业/平台托管 |

读法：**写路径看事务集成，读路径看规划集成，维护路径看谁来跑作业**。
三列没有一个"全能冠军"，这就是第 12 章选型矩阵的输入。

### 11.2 Spark：一张表的三副面孔

```scala
// 教学示意，不参与构建 —— 同一逻辑表，三家的访问姿势
spark.read.format("iceberg").load("cat.db.t")            // 或 catalog 注册后直接 SQL
spark.read.format("hudi").load("s3://bucket/db/t")       // 或 hudi 表名（经 metastore）
spark.read.format("delta").load("s3://bucket/db/t")      // 或 TABLE 形式（delta catalog）
```

- Iceberg 走 **DS v2**：`Catalog/Schema/PartitionSpec` 全部由格式侧提供，
  Spark 只消费 `ScanTask`（规划外置）——换格式几乎不动查询代码；
- Hudi 历史上走 relation/表视图，RTQ（realtime）与 RO（read-optimized）
  两种视图语义要在引擎侧显式选择（4.2 的代价）；
- Delta 与 Spark 耦合最深（Catalyst 规则、`MERGE` 语法糖同源），
  换到非 Spark 引擎时体验落差最大。

性能联动：AQE 的合并/动态过滤收益依赖**上游 ScanTask 数量**
——元数据裁剪差（8.1）会让 AQE 在错误的基础上优化（对照
[../bigdata/05-Spark性能优化.md](../bigdata/05-Spark性能优化.md)）。

### 11.3 Flink：流式集成的三种哲学

```text
Iceberg：checkpoint 对齐提交；无状态 upsert = equality delete 缓冲，
         等 compaction 收敛（3.4）——"写入便宜，债务后付"
Hudi：    状态化 bucket index + log blocks append，MOR 为 Flink 而生（4.4）
         ——"写入带索引成本，读债务由表服务还"
Delta：   读端 micro-batch 轮询 _delta_log；写端多为 Spark 主导，
         Flink 写靠社区路径——"流式是一等公民之外的二等体验"（坦率评估）
```

工程要点：Flink sink 的提交间隔与 checkpoint 间隔**必须同参**，
否则 exactly-once（10.4）与新鲜度（10.4 旋钮）二者至少失一个。

### 11.4 交互引擎（Trino/DuckDB/平台 SQL）

交互查询的 SLA 在秒级，元数据链长度直接进关键路径：
Iceberg 规划=若干 manifest GET（2.6），Delta 重放=日志尾巴 GET，
Hudi 依赖 MDT 新鲜度。因此：

- 高频小表（几百文件内）三家无感；
- **万级文件 + 高选择率查询**时差距显现：需要
  `RewriteManifests`（3.5）、checkpoint 及时（5.1）、
  MDT 无滞后（4.5）——**交互层把维护质量的账显式化**；
- DuckDB/Delta-rs 等嵌入式读端兴起意味着：**规范的元数据即 API**，
  引擎生态从"官方 connector"扩展到"任何按 Spec 实现者"（Iceberg 的最深护城河）。

### 11.5 对象存储的工程账

| 事项 | 事实与对策 |
| --- | --- |
| 一致性 | 现代 S3 已读己之写强一致（2020-12）；跨云/网关兼容层仍需实测"list 一致性" |
| 条件写 | S3 2024-11 起 `If-None-Match:*`——裸存储上的 Delta/Hudi 提交首次可脱离锁服务（6.6） |
| LIST | 计费且慢：**表格式的存在理由之一就是不 list**（2.6）；孤儿扫描、迁移脚本才是 LIST 大户 |
| GET 放大 | 规划链每跳一次 GET：metadata.json 膨胀、碎 manifest、日志尾巴过长都是 GET 账 |
| 提交吞吐 | catalog CAS/日志尾版本竞争设定**单表提交上限**；高频管线要按表数摊薄，不是把一张表推到极限 |
| 请求配额 | 桶级带宽/QPS 配额在规划风暴（大表全读）时触发 503——需要退避与分桶策略 |

### 11.6 落地 SOP（模板化）

1. **建表模板**：格式 + 分区策略 + 排序/聚簇声明 + retention
   + 维护作业参数一次成型（7.6 守则、8.6 预算）；
2. **写者登记**：一张表允许的写者类型（append/UPSERT/维护/回填）
   与重试预算写进管线元数据（6.7）；
3. **双演练**：季度演练"回滚到 T-3"与"catalog 故障降级"（6.6、9.4 思考题的落地）；
4. **观测面板**：提交延迟/重试率、文件数/删除文件数、
   compaction lag、规划 GET 数——前三个是格式指标，后两个是成本指标；
5. **版本纪律**：引擎/格式/Spec 三者兼容矩阵入库，
   升级走 canary 表（table feature 协商，5.6）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "connector 装上就集成了" | 规划、DML、维护三条路径各自有 connector 成熟度差异（11.1） |
| "对象存储 = 无限并发的 POSIX" | LIST/GET 配额与条件写缺失会直接改写提交协议设计（11.5） |
| "换引擎只要换 catalog" | 视图语义（RO/RTQ）、语法糖（MERGE）、维护入口都不跨引擎平移 |
| "流式写表不需要维护" | Flink+Iceberg 的 eq-delete 债务、Hudi 的 log 债务都靠第 8 章动作还 |
