## 核心精讲

### 1.1 为什么会有"湖仓"这个词

三段演进，每段都留下了上段的遗产：

```text
① 数据仓库（1990s–2010s）
   Schema-on-Write、ACID、BI 工具链；但存储贵、schema 僵、
   半结构化/机器数据进不来。
② 数据湖（Hadoop/S3 时代）
   对象存储 + Parquet/ORC + Hive Metastore：便宜、什么都能放；
   但"表"只是一个目录前缀 + 一份分区列表，没有事务、
   并发写会互相踩、部分失败留下半张表。
③ 湖仓（2019–今）
   在②的存储之上加一层"表格式"，把①的语义（ACID、时间旅行、
   schema 约束）搬进②的成本结构。
```

关键认知：**湖仓的"仓"不在计算引擎，而在元数据层**。同一批 Parquet 文件，
底下多一棵带版本的事务元数据树，就同时拥有湖的开放性（文件可被任何引擎直读）
和仓的可靠性（读到的永远是某个完整快照）。

### 1.2 Hive 表模型的具体失效模式

Hive 式表（`location` 指向目录、分区 = 子目录）的三个公认失效模式：

1. **非原子写入**。`INSERT OVERWRITE` 靠目录 rename 近似原子；
   对象存储上 rename = copy+delete，中途失败即产生"半新半旧"的目录。
   并发两个作业写同一分区，结果是文件级混合，无任何冲突报告。
2. **元数据与数据漂移**。Metastore 里的分区列表是"第二份真相"，
   与对象存储实际文件靠 `MSCK REPAIR` / `INVENTORY` 手工对齐；
   删文件不更新元数据 → 查询报错或静默返回错数。
3. **无演化能力**。分区即目录布局：改分区键 = 重写全表；
   改列名只能 `ALTER ... REPLACE COLUMNS`，旧文件里的列位置一旦错位，
   Parquet 按列名读对不上就静默丢数据。

对照教科书定义（[../数据库系统概念6/14-事务.md](../数据库系统概念6/14-事务.md)）：
Hive 表在 **A（原子性）和 I（隔离性）上直接缺失**，D 靠对象存储自身。
表格式要补的就是 A/I，并把 C 定义清楚（快照隔离下的"一致性"= 读到一个完整版本）。

### 1.3 开放表格式的最小定义

一个开放表格式必须提供（三格式无一例外）：

- **快照（snapshot/version/instant）**：表在某一时刻的完整文件清单，不可变；
- **元数据树**：快照被分层组织（Iceberg：snapshot → manifest-list → manifest →
  data files；Hudi：instant → commit metadata → 文件组；Delta：version → commit JSON
  的 add/remove 动作流）——目的是让**规划器不 list 目录也能拿到可裁剪的文件集**；
- **原子提交协议**：把"指向新快照"这一件事变成单次原子操作；
- **演化协议**：schema、分区、统计信息随快照版本化，旧读取路径仍可解释旧文件。

反面界定：表格式**不是**存储格式（Parquet/ORC 才是）、**不是**查询引擎、
**不是** catalog（但依赖 catalog，见第 9 章笔记）。

### 1.4 三格式一览（详细机制各见专章）

| 维度 | Apache Iceberg | Apache Hudi | Delta Lake |
| --- | --- | --- | --- |
| 起源 | Netflix，2017 开源/2018 顶级 | Uber，2017 开源 | Databricks，2019 开源 |
| 核心叙事 | 开放规范、引擎中立 | 管线：upsert/CDC 一等公民 | 平台体验：Spark 原生、协议清晰 |
| 当前元数据 | `metadata.json` + manifest 树 | `.hoodie` Timeline + 元数据表 | `_delta_log` JSON + checkpoint |
| 行级更新 | v2 起 MOR delete files | COW/MOR 双模式 | 早期 COW，后补 deletion vectors |
| 分区演化 | 原生（隐藏分区） | 弱（靠分区路径记录键） | 早期无，后靠 Liquid Clustering 绕开 |
| 典型绑定 | 多引擎中立方（Snowflake/BigQuery/AWS 均支持） | 流式入湖 + 主键表 | Databricks 生态中心 |

一个有帮助的心智模型：**三格式解决的是同一组问题，差异来自"第一个付费场景"**——
Iceberg 的第一场景是 PB 级分析表的可靠重写，Hudi 是 CDC 入湖 upsert，
Delta 是 Spark 作业的可重复读。场景决定机制侧重，详见第 12 章选型笔记。

### 1.5 表格式在技术栈中的位置

```text
┌ BI / ML / ad-hoc SQL
├ 查询引擎：Spark / Flink / Trino / DuckDB / ClickHouse …
├ 【开放表格式】Iceberg | Hudi | Delta   ← 本笔记全部章节
├ Catalog：Hive Metastore | REST | Glue | Polaris | Unity
├ 列存文件格式：Parquet | ORC | Avro
└ 存储：S3 / ADLS / GCS / HDFS（+ 本地磁盘）
```

两条边界纪律（贯穿全书的工程判断）：

- **表格式不管理数据内容的物理编码**（compaction 改变的是"文件清单"，
  Parquet 写文件仍由引擎完成）；
- **表格式不承诺跨表事务**——需要的是"单表 ACID"；多表原子性要靠
  管线设计（幂等重放或 saga），这是第 10 章增量管线的一个考点。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "用了 Parquet + Hive 就是湖仓" | 缺事务元数据层则缺 ACID，只是"带列存的数据湖" |
| "表格式会加速查询因为引擎变快了" | 加速来自**元数据裁剪**（跳过文件）与布局优化（排序/聚簇），扫描本身仍是原引擎 |
| "Delta/Iceberg/Hudi 的表可以互相直接读写" | 数据文件可互读，事务元数据不互通；互操作靠 catalog 镜像/元数据表（第 9 章） |
| "上了表格式就不用管小文件" | 表格式让 compaction **可做且安全**，但不会自动做（除非平台代做） |
