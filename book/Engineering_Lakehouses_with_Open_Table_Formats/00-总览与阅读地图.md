## 全书主线（一句话版）

**湖仓 = 对象存储上的 Parquet/ORC 数据 + 一层"可事务演进的元数据树"。**
开放表格式解决的核心矛盾是：对象存储便宜、可靠但**没有目录级 rename、没有 POSIX、
list 慢且贵、只保证最终一致之外的很弱语义**；而分析引擎需要**ACID、time travel、
schema/partition 演化、增量读**。于是三种格式殊途同归地采用了同一套设计：

1. **把"表当前状态"编码成一个不可变的元数据文件**（Iceberg 的 `v<N>.metadata.json` /
   Hudi 的 instant 完成文件 / Delta 的 `<version>.json` commit）；
2. **用一次原子操作切换指针**（catalog 原子替换 / 文件名不存在即创建 / 条件写）；
3. **失败方基于最新状态做冲突检测后重试**——即乐观并发控制（OCC）。

三格式的差异全部长在细节上：元数据树的形状（manifest 文件树 vs Timeline vs 重放日志）、
行级更新的实现（MOR delete file vs log blocks vs deletion vector）、
并发控制的仲裁点（catalog vs `.hoodie` timeline vs 文件系统协议）、
以及"谁负责表维护"（引擎作业 vs 内置 async service vs 平台托管）。

- **机制优先路线**（推荐）：01 → 02 → 03 → 04 → 05 → 06。
  第 02 章是全系列的"公共课"，三格式各自的章（03–05）只需读你选型涉及的那一个。

- **选型/迁移路线**：01 → 09 → 12，再回补 06–08 的细节。
- 每章固定结构：**本章地图 → 核心精讲（机制/为什么/例子）→ 三格式对照 → 常见误区 → 思考题**。
