# 04 数据库建模设计与用户界面（原书第 5–6 章）

> 书目：《Database Systems: A Pragmatic Approach》，Elvis C. Foster & Shripad V. GodBole，Apress 2014，章 DOI `…_5`（pp.83–118）/ `…_6`（pp.119–127）。
> 证据级：章题/页码/DOI ✅ Crossref 一手；两章首段 ✅ Springer 摘要逐字；小节展开 ⚠️ 重构；🔧 为 SQLite 3.45.3/DuckDB 1.5.5 实测，**非本书引擎行为**。

## 1 本章定位

ch5（36 页，全书最长设计章）+ ch6（9 页短章）合为"把模型变成能用的系统"单元。ch5 首段亮明方法论立场（✅ 逐字）：

> "Some database systems textbooks make much ado about having separate chapters for database modeling and database design. In this course, we will not, and the reason will become clear shortly. All discussions in chapters 3 and 4 contribute to database modeling and…"（截断）

——**建模与设计在本册是一件事的两面**：ch3 的名词+ch4 的法则直接就是设计动作；这与 DMD5e（盘上 #11）把 ER/UML/转换/案例切成五章的写法构成光谱两端。ch6 首段（✅ 逐字）：

> "This chapter covers the essentials of good database user interface design. A properly designed database system typically includes a user interface that facilitates end users accessing the system. The chapter presumes that you are familiar with basic software…"（截断，⚠️ 补：software development/concepts）

## 2 ch5 内容主讲（⚠️ 重构，锚=章题+ch3/4 承接句）

- **设计过程骨架**：需求收集→概念结构→逻辑关系集→物理落地；ch29 附录"信息收集技术"被此处显式回指（✅ ch29 摘要："Mastery of the techniques discussed will enable you to readily identify information entities"——识别实体即建模第一步）。
- **从实体/联系到关系**：一对一/一对多/多多的外键化与中间表化（college 域例库 ✅ ch8 确认其于 ch7 已成型，反推 ch5 沿用 ⚠️）。
- **用 ch4 规则审查设计**：异常驱动重构；键的选择与命名规约。
- **设计⇄需求的回路**：变更管理、与用户确认视图覆盖度（ch13 视图的外挂动机在此埋下）。
- ⚠️ 声明：本册是否讲 E-R 图法（Chen 记法/鸦脚记法）摘要未露——同年代教材大概率用鸦脚式图示；证据缺失，此处不下断言。

## 3 ch6 内容主讲（⚠️ 重构，9 页容量决定其"清单式"体裁）

- 表单/网格/报表三件套与录入效率（字段顺序、 Tab 流、下拉替代自由文本）。
- 校验前置：客户端检查+服务器/DBMS 检查双保险（与 ch4 用户定义完整性衔接）。
- 屏幕一致性与"以任务为中心"布局（2014 桌面富客户端口径——ch20 Delphi 正是其实现工具，两章同部类 ⚠️ 推断）。

## 4 🔧 把"逻辑→物理"落成可跑 DDL（非本书引擎）

- **建模产物=DDL**：E7 实验的 `o_norm(cid…) + c_norm` 双表与反范式 `o_den` 单表由同一逻辑模型派生，装载 `INSERT INTO o_den SELECT … JOIN …` 一步完成——"反规范化是设计决策，不是复制粘贴"的现场示范（数字：50万行 JOIN 装载后点查 157.26ms→27.32ms）。
- **造数据即建模型**：E7 用 `WITH RECURSIVE` 生成 5 万客户/50 万订单（SQLite 3.45.3 支持递归 CTE，SQL:1999 特性落地开源引擎）；DuckDB 一行 `range(1000000)` 造百万行（E4）——建模评审时先跑数据量级再谈范式，成本观感立现。
- **约束即文档**：E2 `DESCRIBE emp` 输出 `('ename','VARCHAR','NO',…)`——NOT NULL/类型/键都在目录里可读，UI 校验规则可从物理模型**生成**而非手写（ch6 的 2026 解法预告）。
- ⚠️ Oracle 10g 语境下这步还包括 tablespace/存储参数（✅ ch11 摘要"table-spaces, data-files"），本工作区不可实测，登记不展开。

## 7 深挖与自测

### 概念辨析十问
1. 本册为何拒绝拆分建模/设计两章？——作者自供"much ado"派之别（✅ 摘要逐字）。
2. 概念模型必须画图吗？——本册图形法无逐字证据 ⚠️；DMD5e 有 ER/UML 双图法实链对照。
3. 多对多联系为何必须中间表？——两端 FK 放不下可变基数；中间表=联系实体化。
4. 一对一联系何时合并何时拆？——属性少则合并；拆的动机是生命周期/权限/稀疏大字段。
5. 需求变更最先冲击哪层？——概念词汇表→外视图；概念模式最扛打（ch2 独立性回收）。
6. UI 章为何只有 9 页？——教材自限（presumes basic software ✅）；重心是数据侧对 UI 的承诺。
7. 录入校验放前端还是库内？——双保险：库内是底线，前端是体验。
8. 下拉代替自由文本的建模意义？——把域枚举提前写进 UI 契约（目录可生成，E6 已证可查）。
9. 设计评审最低三问？——键唯一吗？NULL 分布合理吗？三类异常可发生吗？
10. 反规范化何时进设计文档？——负载画像明确读多写少（E7），且写明冗余同步策略。

### 常见误区六条
- 把 ER 记法之争当圣战——交付物（关系集+约束）才是目的，本册"过程骨架"论。
- 需求收集一次性——ch29 技术是循环工序，不是开场礼炮。
- UI 与模式脱耦——控件类型/校验规则本应从目录生成（E6）。
- 中间表只建不管——它是事实表，同样要约束与索引（ch11/17）。
- 设计文档只画当前态——变更历史才是 DBA 协作面（ch21）。
- 把"逻辑→物理"当一键生成——Oracle 表空间/存储参数是设计决策（⚠️ ch11 高级对象）。

### 🔧 加餐：建模落地可跑三件（非本书行为）
- E7 递归 CTE 造数=模型可测第一步（50 万行）。
- E2 DESCRIBE=逻辑模型的物理回显，评审对账单。
- E1/E2 约束密度=同一模型在两引擎的"法典对照"。

### 一分钟版
- ch5 说"建模=设计"，ch6 说"UI 是数据的人权"。
- 流程四拍：收集→概念→逻辑→物理；ch29 给第一拍的扳手。
- 36+9 页的篇幅比，本身就是本册"重设计轻界面"的立场。
