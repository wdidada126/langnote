> 书目：《Database Systems: A Pragmatic Approach》，Elvis C. Foster & Shripad V. GodBole，Apress 2014，章 DOI `10.1007/978-1-4842-0877-9_4`（pp.57–81）。

## 2 内容主讲（⚠️ 重构，锚点=章题+"fundamental rules"课堂口径）

**完整性三件套**（本册术语按名册期教材惯例）：

- **实体完整性（entity integrity）**：主键非空且唯一——"每行可寻址"。
- **参照完整性（referential integrity）**：外键值要么 NULL 要么存在于被引关系——"跨行承诺不悬空"。
- **用户定义完整性（user-defined integrity）**：CHECK/NOT NULL/UNIQUE/域规则——"业务自己的法"。

**规范化阶梯**：

- 1NF（原子性，回收 ch3"正规化表"）→ 2NF（消除部分函数依赖）→ 3NF（消除传递依赖）→ BCNF（每个决定因素都是候选键）。是否讲到 4NF/多值依赖 ⚠️ 无证据，81 页篇幅按教材惯例以 3NF/BCNF 收口。
- 典型路径：college 域的"平坦大表"→ 分解演示（插入/更新/删除异常作驱动力）→"无损连接+保持依赖"直觉化（术语严格版在盘上 [../Database_Design_and_Relational_Theory/06-保持依赖.md](../Database_Design_and_Relational_Theory/06-保持依赖.md)）。
- 反规范化在本册仅 ch5"设计权衡"处暗示（⚠️），理论纵深请走 §5 对位。

## 3 🔧 约束执法现场（双引擎实测，非本书引擎）

**实体/参照/用户定义三类完整性 = 引擎里的 PK/FK/CHECK+NOT NULL+UNIQUE**，E1/E2 全量记录：

| 规则 | SQLite 3.45.3 | DuckDB 1.5.5 |
|---|---|---|
| 实体完整性 | `did INTEGER PRIMARY KEY` 强制 ROWID 别名、PK 查重拦 | PK 违例：`Duplicate key "did: 10" violates primary key constraint.` |
| 参照完整性 | **默认不执法**：`PRAGMA foreign_keys`→0，孤儿行 `(1,'ann',99,50.0)` 入库；开后 `IntegrityError:FOREIGN KEY constraint failed` | 默认执法：`Constraint Error: Violates foreign key constraint because key "did: 99" does not exist in the referenced table` |
| CHECK | `CHECK constraint failed: budget>=0`（-5 拒绝） | `CHECK constraint failed on table dept with expression CHECK((budget >= 0))` |
| UNIQUE | `UNIQUE constraint failed: dept.dname` | 列级 UNIQUE 拦重复 |
| 事后补约束 | `ALTER TABLE ... ADD CONSTRAINT` 语法可 | **`ALTER TABLE emp ADD CONSTRAINT u CHECK (salary>0)` → `No support for that ALTER TABLE option yet!`** |
| 例外通道 | upsert：`ON CONFLICT(did) DO UPDATE SET budget=excluded.budget` → 999.0 | 同风格支持（E3 系列验证） |

- 教学金句（由实测得出，非本书）：**"完整性规则不是 DDL 写了就生效"**——SQLite 的 FK 开关与 DuckDB 的 ALTER 缺口是两条 2026 年仍然活着的工程陷阱。
- **规范化的性能账单**（E7）：50 万订单×5 万客户，`o_norm JOIN c_norm` 聚合 157.26ms vs 反范式 `o_den` 单表扫 27.32ms（5.8×）——教科书"为了查询快而反规范"的正当理由，也是 ch5 设计章"平衡"一词的量化注脚。

## 6 教学与实操要点

1. 讲 2NF 前先确认表有复合主键，否则 2NF 段可以整段跳过——多数课堂在此省时间，本册 25 页篇幅同样不会每个范式给足例题（⚠️ 推断）。
2. 用 E7 的 5.8× 数字开辩论：规范化=维护质量，反规范化=读取性能，没有免费午餐。

## 7 深挖与自测

### 概念辨析十问
1. 实体完整性为何不能靠应用自觉？——并发竞态；引擎约束是唯一低成本最后防线（E1/E2）。
2. ON DELETE CASCADE 属三类完整性哪类？——参照完整性的执行策略（⚠️ 本书按标准口径）。
3. 2NF 为何常"自动成立"？——违例需复合主键；单列键表可整段跳过。
4. 3NF 与 BCNF 的分界例子长什么样？——"课程⇒学分、教授⇒系、系⇒预算"式传递链（16 号 Q2 型）。
5. 无损连接与保持依赖不可兼得时怎么办？——3NF 保依赖/BCNF 尽范式：写明取舍的设计文档才是答案。
6. 反规范化何时正当？——读远大于写且冗余有同步策略（E7 5.8× 提供量化正当性）。
7. CHECK 与触发器选谁？——能 CHECK 不触发器；DuckDB 事后补 CHECK 还不支持（E2），设计期前置。
8. FK 延迟检查存在吗？——标准有 DEFERRABLE（PG/Oracle 系 ⚠️ 转述）；SQLite 无，装载顺序病由此生。
9. 规范化伤害性能——那不规范化伤害什么？——伤害"修改的可能性"（插入/更新/删除异常）。
10. 如何验证分解正确？——chase 手推（盘上 DRDRT 11）；🔧 E7 双表 JOIN 装载一致性实跑。

### 常见误区六条
- "分解到 BCNF 才算好设计"——过度分解=JOIN 税+语义碎（E7 现场）。
- 把范式当目标——它只是"无免费午餐"的中间解。
- UNIQUE 与 PK 随便选——PK 有参照目标/集群倾向/优化器信任三特权。
- CHECK 写了就完事——引擎缺口与重建成本是运行期暗坑（E2）。
- 认为 FK 拖慢一切——合理索引下 FK 列点查可 267× 提速（E4）。
- 拿 5.8× 当万能钥匙——它只测单谓词聚合，写入放大没算账。

### 🔧 加餐：三件套执法速查（非本书行为）
- 实体：两引擎 PK 全拦（E1/E2）。
- 参照：SQLite 开关制（默认 0）、DuckDB 默认执法（E1/E2）。
- 用户定义：CHECK/UNIQUE 新建即拦；upsert 是受控违例通道（E1→999.0）。

## 8 术语快卡与跨书对位

| 术语 | EN | 一句话定位 |
|---|---|---|
| 实体完整性 | Entity Integrity | 主码属性不得为 NULL |
| 参照完整性 | Referential Integrity | 外码要么 NULL 要么命中被引用码 |
| 函数依赖 | Functional Dependency | X 决定 Y：规范化的度量衡 |
| 1NF | First Normal Form | 属性原子化，表格不套表格 |
| 3NF | Third Normal Form | 非主属性不传递依赖码 |
| BCNF | Boyce-Codd NF | 每个决定因素都是候选码 |
| 分解/无损 | Decomposition/Lossless | 拆表必须能原样拼回 |

## 最新演进与工业实践

- **引擎方言对照的 2026 版**：Oracle 23ai/PostgreSQL 17 均支持约束的 `NOT ENFORCED`/`VALIDATE` 分级（数据迁移期先建后验）——把本册"规则"与"执法"分离的语法化，✅ https://learn.microsoft.com/en-us/sql/relational-databases/security/authentication-access/database-level-roles 同站内 CHECK 约束文档域（200 验真口径）。
