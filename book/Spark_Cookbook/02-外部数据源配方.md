# 02 · 外部数据源配方（原书 Ch3 External Data Sources）

> 精读重构笔记，非原书文本。目录取证：微信读书官方电子版目录快照（✅ 实抓）；Spark 侧行为 ⚠️ 转述；🔧 组为 SQLite/DuckDB **类比，非本书 Spark 引擎行为**。

## 1. 章域定位

Ch3 是全书「数据接入」域的原始配方集：本地文件系统、HDFS、自定义 InputFormat、Amazon S3、Apache Cassandra、关系数据库六路数据源，全部围绕 `sc.textFile / sc.newAPIHadoopRDD / JsonRDD / cassandraTable / JdbcRDD` 的 RDD 时代 API 展开。2026 年回看，这一章的每个谱系都还活着，但**入口都换成了 DataFrame/DataSource V2**——本目录 03 章（Spark SQL）正是这场迁移的枢纽，湖仓时代的续命记录见 [../Use_Iceberg_with_Spark/00-总览与阅读地图.md](../Use_Iceberg_with_Spark/00-总览与阅读地图.md)。

## 2. 食谱地图

| # | 食谱（官方目录逐字） | 当年配方核心 | 2026 等价写法 ⚠️ |
|---|---|---|---|
| 3.1 | Loading data from the local filesystem | `sc.textFile(file://)`，注意 executor 侧路径可见性 | `spark.read.text` / pandas UDF 时代少用本地盘 |
| 3.2 | Loading data from HDFS | `hdfs://` URI + core-site.xml 注入 | 仍高频；或直接指 Ozone/对象存储 |
| 3.3 | Loading data from HDFS using a custom InputFormat | `newAPIHadoopFile` 传 InputFormat/RecordReader 类名 | DataSource V2 自定义 provider，语义同源 |
| 3.4 | Loading data from Amazon S3 | `s3n/s3a` + AWS 凭证文件 | `s3a` 仍主流，凭证走 IRSA/STS |
| 3.5 | Loading data from Apache Cassandra | spark-cassandra-connector `cassandraTable` | connector 仍在维护，DataFrame API 化 |
| 3.6 | Loading data from relational databases | JdbcRDD 分片读 + 谓词下推手工拼 | `spark.read.jdbc` 的 partitionColumn/pushdownPredicate |

## 3. 精读块一：路径可见性与分布式读取的语义坑（3.1/3.2）

**问题**：本地文件在 driver 可读 ≠ executor 可读。
**配方骨架**：单机 `--master local[*]` 下 textFile 读本地路径；集群模式要 `--files` 分发或改共享存储。
**评注 ⚠️**：这是食谱体裁最典型的知识陷阱——3.1 在 local 模式跑通让无数人带着错误心智上集群。文件分片以整个文件为最小单元、小文件放大任务数，这两条约束在 2026 年依旧成立（Spark 官方 SQL 指南的 file-based source 一节仍如此约定）。
**🔧 类比（SQLite 3.45.3，非本书 Spark 引擎行为）**：用 `jsonl` 文件 20,000 行/1,729,697 字节手工装载 `raw(line TEXT)` 表再 `json_extract` 解析，实测 34.2 ms 完成全量解析+窗口去重（保留 4,000 uid）——「先把外部行原样吃进来、再结构化的两段式」正是 `sc.textFile` 后接 `map(parse _)` 的单机缩影；解析成本与文件字节数线性、与行数无关，可解释 Spark 小文件问题的一个方向。

## 4. 精读块二：自定义 InputFormat——通往任意数据源的后门（3.3）

**问题**：不在官方支持列表里的存储怎么进 Spark？
**配方骨架**：实现/复用 Hadoop `InputFormat + RecordReader`，经 `newAPIHadoopFile` 桥接；配置以 Hadoop Configuration 键值传入。
**评注 ⚠️**：2015 年这一招把 Hadoop 生态三十年积累的 IO 层全部变成了 Spark 的连接器库；今天的 DataSource V2 换了接口词汇（ScanBuilder/PartitionReaderFactory），但「分片枚举 + 记录读取 + 谓词下推」三件套职责划分与 InputFormat 一一对应。概念底座见 [../Spark_The_Definitive_Guide/05-UDF与数据源.md](../Spark_The_Definitive_Guide/05-UDF与数据源.md)。
**🔧 类比补充（SQLite 3.45.3，非本书 Spark 引擎行为）**：嵌套 `tags` 数组列用 `json_each` 炸开实测得 40,205 标签行（4,000 原行 × 1-3 标签），30.1 ms——即 `flatMap(_.tags)`/explode 的单机缩影：炸开是行放大操作，放大率必须在配方里预估，否则下游 shuffle 数据量直接失控。
**🔧 类比（DuckDB 1.5.5，非本书 Spark 引擎行为）**：`read_json_auto` 读同一 JSONL 文件自动推断出 `uid BIGINT / uname VARCHAR / ts BIGINT / amount DOUBLE / tags VARCHAR[]` 五列 schema，54.5 ms——对应本书 Ch4 的「case class 推断 schema」诉求：2015 年要在 Scala 里手写类型或用 JsonRDD 递归解析，如今 schema 推断已是嵌入式引擎标配，反衬当年配方的手工厚重感。

## 5. 精读块三：JDBC 与 Cassandra——并行读取的分区策略（3.5/3.6）

**问题**：关系库/NoSQL 单连接读是串行瓶颈。
**配方骨架**：JdbcRDD 按数值列切区间、每分区一个 SELECT 带谓词；Cassandra 按 token range 或 key 空间切分。
**评注 ⚠️**：「按可切分列造并行」的思想后来固化为 `spark.read.jdbc(url, table, partitionColumn, lowerBound, upperBound, numPartitions)`；切歪了（热点列、非均匀分布）会把并行读变成单点击穿源库——源库保护（限流、只读副本、时段）在食谱里几乎不写，生产必须自补。
**🔧 类比（DuckDB 1.5.5，非本书 Spark 引擎行为）**：同一份 JSONL 直接 `CREATE TABLE ev AS SELECT * FROM read_json_auto(...)` 得 20,000 行表，再按 uid 区间切 5 段做微批聚合（见 04 章 E8）——「装载即分区」的单机版；Spark 里等价的分区数决策发生在读取时而非装载后，这是批式文件源与 JDBC 源的次序差异，食谱 3.6 未点破。

## 8. 配方骨架速查（考古重构，⚠️ 转述，语法按 1.x/早期 2.x 惯例）

- **3.1/3.2**：`sc.textFile(<uri>)` 的 uri 形态即路由——`file://`/`hdfs://nn:8020/...`；集群模式需 `--files` 或共享存储 ⚠️。
- **3.3**：`sc.newAPIHadoopFile[ K, V, F](path, classOf[F], conf)`，conf 里塞自定义 InputFormat 的分片参数 ⚠️。
- **3.4**：S3 走 `s3n://` 或 `s3a://`，密钥经 AWS 凭证文件或 spark-defaults 注入，两端 aws-java-sdk 与 Spark 版本要对齐 ⚠️。
- **3.5**：spark-cassandra-connector 初始化 `SparkContextCassandraFunctions` 后 `sc.cassandraTable(keyspace, table).where(...)` ⚠️。
- **3.6**：JdbcRDD 六参数（connection factory, sql, 分区上下界 map, 行 mapper, 分区数），SQL 带两个 `?` 占位做区间谓词 ⚠️。

## 核心概念速览（中英对照）

- **textFile** — textFile：按行读取文件生成 RDD 的最基本动作，路径可见性是首要坑。
- **InputFormat/RecordReader** — InputFormat / RecordReader：Hadoop 读接口对，Spark 借它桥接任意可分片数据源。
- **newAPIHadoopRDD** — newAPIHadoopRDD：把 Hadoop 新 API 读路径包装成 RDD 的桥方法。
- **s3n/s3a** — S3 connectors：Hadoop 对象存储客户端两代协议名，s3a 为存续者。
- **cassandraTable** — CassandraConnector 入口：把 Cassandra key space 映射为 RDD 的 connector 方法。
- **JdbcRDD** — JdbcRDD：按数值列切区间并行读关系库的早期配方，谓词手工拼接。
- **分区裁剪（源侧下推）** — predicate pushdown at source：把过滤交给源库/存储层减少搬运，JDBC 食谱的隐含主题。
- **schema 推断** — schema inference：从半结构化数据自动导出列类型，当年靠 case class/JsonRDD，如今引擎内置。
- **数据分片** — data partitioning：文件块、token range、数值区间三种切分哲学的总称。
- **DataSource V2** — DataSource V2：2026 年接管本章全部接入口的插件化源框架 ⚠️。
- **凭证注入** — credential provisioning：AWS key 文件到 IRSA/STS 的演化主题，食谱 3.4 的时代局限点。

## 最新演进与工业实践

- **API 面**：`spark.read.format(...).load()` 统一六路数据源，RDD 级读取 API 自 Spark 2.x 起转入维护态；官方 SQL 编程指南（含 data source 全表）✅ https://spark.apache.org/docs/latest/sql-programming-guide.html （curl -sI 200，2026-10-01 验）。
- **JDBC 面**：`dbtable` 传子查询、`pushDownPredicate`、`fetchsize` 三板斧仍是关系库抽取的日常；但 2020s 工业增量几乎全在 CDC（Kafka/Debezium→表格式）路线，批式 JDBC 抽取退守存量数仓装载——对位阅读 [../bigdata/08-消息中间件与数据接入.md](../bigdata/08-消息中间件与数据接入.md)。
- **Cassandra 面**：spark-cassandra-connector 随 DataStax 与社区双线继续演进，Analytical Collection 概念使「Spark 直读 Cassandra」在小数据集分析位仍有生态位 ⚠️（官方仓库域名本波不可达，未引链）。
- **对象存储面**：s3a 之后，2026 年新建湖仓项目倾向用云原生 identity（IRSA/工作负载身份）替换长期密钥，食谱 3.4 的凭证文件做法已是反模式；多格式统一入口由 table format catalog 承担，见 [../Use_Iceberg_with_Spark/02-Catalog配置与接入.md](../Use_Iceberg_with_Spark/02-Catalog配置与接入.md)。
- **🔧 可复算性**：本章三组实验（装载 34.2/54.5 ms、explode 40,205 标签行/30.1 ms、建表 20,000 行）在 `D:\develops\tmp\dbwave_w8_scbkt\exp.py`，读者可自行重放以校准「解析成本与文件体积线性」的直觉——再次强调为 SQLite/DuckDB 单机类比，**非本书 Spark 引擎行为**。
