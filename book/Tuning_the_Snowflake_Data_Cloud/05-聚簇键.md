## 5.1 聚簇要解决的问题（回接 04 章）

微分区按装载顺序切块 ⇒ 过滤列值域高度交错时裁剪失效（03 章读放大症状）。聚簇键
（`CLUSTER BY (col [,...])`）声明后，Snowflake **自动重聚簇**（auto reclustering）把表物理重排成
「按声明键有序」的近似线性聚簇，使常用谓词的分区重叠度坍缩 ⚠️（转述
`https://docs.snowflake.com/en/user-guide/tables-clustering-keys` ✅、
`https://docs.snowflake.com/en/user-guide/tables-auto-reclustering` ✅）。

- 表可声明多个键列，但**有效聚簇前缀只有少数列**：官方口径为「深度统计只对靠前的少量列有意义」
  ⚠️——键列次序=谓词频率次序，这是本章的第一处方。
- 无需（也不能）手工 `RECLUSTER`：旧版手动重聚簇语句已被官方标 **Deprecated** ✅（
  `https://docs.snowflake.com/en/user-guide/tables-clustering-manual` 页面题名即带 *Deprecated* ✅
  llms 索引实抓），现行机制全自动。

## 5.2 度量：聚簇深度（Clustering Depth）

- 概念 ⚠️：值域重叠的分区群越多深度越大；1.0≈完美线性聚簇；深度↔扫描分区数近似线性相关。
  官方给出 `SYSTEM$CLUSTERING_INFORMATION` / `SYSTEM$CLUSTERING_DEPTH` 两个表函数入口（
  语法细节以 tables-clustering-keys 页现行版为准 ⚠️，本册不背参数）。
- 判读纪律（本章方法论）：深度要和**表大小、谓词命中率**三方对表——小表深度差无所谓；
  大表但无固定谓词列，深聚簇=白烧 credit ⚠️。
- 成本面 ⚠️：重聚簇消耗服务层 credit（后台自动，按官方 storage/autorefresh 口径计费）——
  聚簇是**用可预测的写放大买不可预测的读节省**，10 章成本闭环里要算这笔账。

## 5.3 什么时候该聚、什么时候别聚（处方式清单 ⚠️ 按官方主题归纳）

适用（收益侧）✅ 主题/⚠️ 细节：

1. 大表（官方经验口径：持续被查询且聚簇收益可测的大表才值得 ⚠️）；
2. 固定高频谓词列（日期范围、租户 ID、状态列）且当前重叠严重（深度高、裁剪率 <50%）；
3. 装载无法保持源序（乱序微批流）时的兜底。

不适用（副作用侧）：

1. 点查等值高频——交给 SOS（07 章），聚簇解决不了「单行大海捞针」；
2. 谓词列发散/全表扫描型负载——聚簇只添重排成本；
3. 已有完美装载定序（4.4「先排序再落文件」）——零成本近似已达成，再声明键是重复付费；
4. 高频写入表的**尾部重排放大**：新数据持续落入需重排区，官方对写重表的聚簇收益持保留口径 ⚠️。

## 5.4 线性聚簇 vs 其他布局范式（对照视野）

- 与 Redshift SORTKEY/INTERLEAVED 对照：Redshift 手工两难（distkey 选择痛苦），Snowflake 用
  自动重聚簇把运维负担吃掉——同一问题不同工程形态（
  [../Amazon_Redshift_TDG/00-总览与阅读地图.md](../Amazon_Redshift_TDG/00-总览与阅读地图.md) 登记对位）。
- 与湖仓 Z-Order/Hilbert 对照：Snowflake 只做**线性**（逐列前缀）聚簇，无多列曲线填充布局；
  代价是前缀后列快速失效，收益是行为可解释、可全自动 ⚠️（对照
  [../Data_Lakehouse_in_Action/00-总览与阅读地图.md](../Data_Lakehouse_in_Action/00-总览与阅读地图.md)、
  [../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md](../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md)——二者 00 实名已 ls 验名 ✅）。

## 5.5 🔧 实测 E1 复用 + 延伸：有序度梯度（DuckDB/SQLite，非 Snowflake 行为）

E1 主数据（见 04 章 4.5 表）：有序 2.2ms / 打乱 25.3ms / 全扫 62.7ms。补充读数（同一脚本
`D:\develops\tmp\dbwave_w8_snowtune\exp.py` 🔧）：打乱版 25.3ms **优于**全扫 62.7ms ≈ 1.9/4.7，
对应「深度>1 但 zone-map 仍部分有效」的中间态——说明聚簇收益曲线**前段陡后段平**：
从「完全乱序」到「粗略有序」拿大头，从 1.5 抠到 1.0 的边际收益要和服务层重排 credit 对赌 ⚠️
类比外推（外推自机制，非官方数字）。SQLite 侧对照：同一张表按索引列聚簇物理页（`INSERT`
有序 vs 随机再 `VACUUM`）影响页内局部分组，粒度粗但机制同名——仅课堂演示级，数字不引。

## 5.6 诊断-处方流程（本章收束）

1. 03 章读放大确认症状 → 2. 表函数看深度与重叠直方图 ⚠️ → 3. 谓词列盘点（谁值得进键前缀）→
4. 声明 `CLUSTER BY` 并观察自动重聚簇的 credit 曲线 ⚠️ → 5. 复跑同查询取剖面 diff（03 章纪律）→
6. 不值则撤键（撤销聚簇键后表停止重排，存量布局不回收 ⚠️——注意这是「只停未来」语义）。

## 5.8 聚簇键选型评议单（三列表裁决 ⚠️ 编者模板）

给「要不要给这张表声明聚簇键」的会前裁决模板（每行都要能当场填出证据，填不出即否）：

| 评议项 | 通过线 | 证据来源 |
| --- | --- | --- |
| 表规模与查询频次 | 大表且被高频范围/等谓词查询 | Query History（03 章） |
| 谓词列集中度 | 前 2 列覆盖 ≥70% 过滤谓词 | 负载普查（10 章 10.2-1） |
| 当前裁剪率 | <50% 且读放大 >50× | 剖面读数（03 章 3.3） |
| 深度读数 | 明显 >1 且趋升 | 表函数（5.2，⚠️ 语法以现行页为准） |
| 装载可控性 | 无法上游定序（否则走免费项） | 管道盘点（04 章 4.4） |
| 写放大容忍 | 服务层重排费在预算内 | 资源监视器余量（6.5） |
| 副作用检查 | 非点查主场（点查让位 SOS）、非整表重写型 | 7.4 反面清单 |

**裁决规则**：七项全过→声明 `CLUSTER BY (按频序列)`，进入 5.6 流程；任一硬伤（点查主场/小表/
谓词发散）→否决并转 07 章或改写路线。「**先免费后付费**」（装载定序优先于聚簇、聚簇优先于 SOS）
是本单贯穿始终的排序原则 ⚠️ 编者归纳——它把 05 章从「参数题」变成「流程题」，也正是本书
project-oriented 定性 ✅ 在布局层的体现。

## 核心概念速览（中英对照）

- **聚簇键** — Cluster Key：`CLUSTER BY` 声明的布局意图，驱动自动重聚簇逼近线性有序 ⚠️（✅ 官方页）。
- **线性聚簇** — Linear Clustering：逐列前缀重排；后位列收益递减是前缀纪律的根源 ⚠️。
- **聚簇深度** — Clustering Depth：重叠分区群规模读数，1.0≈完美；大表高深度=裁剪失效 ⚠️。
- **自动重聚簇** — Automatic Reclustering：服务层后台重排，消耗 credit，无人工干预现行机制 ⚠️（✅ 两 URL）。
- **手动重聚簇（弃用）** — Manual Recluster, Deprecated：旧 `RECLUSTER` 语句路径，官方页题名即标弃用 ✅。
- **重叠税** — Overlap Tax：交错值域造成的扫描放大（04 章 4.2 同词），聚簇的直接靶子 ⚠️。
- **键序=频序** — Key Order Discipline：聚簇列次序应镜像谓词频率次序（5.1 第一处方）⚠️。
- **尾部重排** — Tail Recluster Cost：新数据落入有序区引发的重排放大，写重表慎聚 ⚠️。
- **撤销只停未来** — Uncluster Semantics：撤键停止重排、不回滚存量布局 ⚠️ 转述口径。
- **Z-Order 对照** — Z-Order Comparison：多列曲线布局 vs 线性前缀的范式分歧（5.4，湖仓册对位）。
- **裁剪率** — Pruning Ratio：跳过分区占比，<50% 触发聚簇评估的本书经验阈值 ⚠️。

## 最新演进与工业实践

2024→2026（URL 均 ✅ 200；状态 ⚠️ 文档转述）：

- **手动 RECLUSTER 正式退场**：官方弃用页（tables-clustering-manual，题名 *Deprecated* ✅ 实抓）
  确立全自动现行线；本书成书（2024）时部分示例含过渡期口径，2026 读法以自动聚簇为唯一正途 ⚠️。
- **Search Optimization 分工强化**：官方把「点查/子串/半结构化」明确划给 SOS、把「范围扫描布局」
  留给聚簇（tables-clustering-keys 与 search-optimization-service 两页主题分工 ⚠️），07 章联动。
- **托管 Iceberg 的布局语义**：开放表格式侧无 Snowflake 式自动重聚簇，布局责任回给写入端
  （sort/rewrite 作业）——对照 [../Data_Lakehouse_in_Action/00-总览与阅读地图.md](../Data_Lakehouse_in_Action/00-总览与阅读地图.md)；
  Snowflake 托管表产品线扩展后，「何时用托管 Iceberg、何时用内部表」成为 2025+ 布局决策的新前置 ⚠️。
- **工业实践**：多租户 SaaS 分析库把「租户 ID + 事件日期」双列聚簇作为标准动作；对照 Redshift
  INTERLEAVED sort 的人工维护成本，Snowflake 路线的运维优势在 2026 实践中被反复验证 ⚠️ 评价性转述。
- **本机教学** 🔧：E1 有序/打乱对照（2.2ms vs 25.3ms）仍是课堂上演示「布局≈数量级」的最低
  成本实验；重申 DuckDB 粒度/执行模型不同，**非 Snowflake 平台行为**。
