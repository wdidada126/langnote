## 1.1 本章在全书中的位置

第 1 章与书名同名（Tuning the Snowflake Data Cloud），是方法论开篇：定义「调优 = 性能与成本的
联合约束求解」，给出全书的工单式路径——先学会**观测**（第 2–3 章优化器与剖析器），再进入**存储
布局**（第 4–5 章微分区与聚簇）、**计算供给**（第 6 章仓库、第 8 章并行化）、**专用服务**（第 7 章
SOS）与**传输侧**（第 9 章客户端），最后第 10 章收束为端到端方法论。Springer 官方简介 ✅ 明示本书
三大承诺：识别性能瓶颈根因、解决性能问题、减少昂贵错误并管控成本。

## 1.2 双目标：credit 与延迟的权衡

Snowflake 计费主线 ⚠️（转述 docs `user-guide/cost-optimize` ✅ 200 与
`user-guide/cost-understanding-data-storage` ✅ 200）：

- **计算**：虚拟仓库按 credit 计费，秒级粒度起步、开机/唤醒与首查询有冷启动开销；仓库停即止损，
  空闲不计费。→ 调优的第一杠杆是「**让查询落在刚好够大的仓库上，并尽快回到暂停**」。
- **存储**：按压缩后字节计费，与查询性能解耦但通过微分区布局影响扫描量（第 4 章）。
- **服务层**：元数据维护（自动重聚簇、克隆、复制）消耗额外 credit ⚠️——本书特色是把「看不见的
  后台开销」也纳入调优视野（对应 05/06 章处方）。

反直觉要点（本书叙事的成本侧）：**更快的仓库不总是更贵**——scaling up 缩短占用时长，credit 消耗
可能持平甚至下降；反之小仓库排队会同时伤害延迟与吞吐（06/08 章）。

## 1.3 迁移问题识别（Springer 简介 ✅ 点名的 hands-on 主线）

工作负载从本地数仓/其他云仓迁入 Snowflake 的典型病灶 ⚠️ 推定归纳（转述官方性能总纲
`guides-overview-performance` ✅ 200 的主题框架）：

1. **索引思维**：源库依赖 B-tree 索引与物化视图；Snowflake 无用户索引，微分区 zone-map 承担
   粗裁剪，选择性点查需 SOS 替代（07 章）。
2. **分布键思维**：Redshift DISTKEY 式手工分片 ↔ Snowflake 自动分片由仓库尺寸决定（08 章）。
3. **常驻集群思维**：传统 MPP 7×24 开机 ↔ Snowflake 按需启停 + 自动暂停改变成本结构（06 章）。
4. **过度装载**：小批量 INSERT 流造成微分区碎片化，恶化裁剪（04 章；装载侧见 09 章与 TDG 06）。
5. **结果集滥取**：BI 工具拉全表回客户端渲染，网络与客户端成瓶颈（09 章）。

## 1.4 调优循环方法论

本章给出的工作法（⚠️ 依章题语义与官方文档主题重构）：**度量 → 归因 → 处方 → 回归 → 记账**。

- 度量：Query Profile / Query History / Performance Explorer（✅ URL 见 03 章清单；顶层
  `guides-overview-performance` ✅）。
- 归因：先分类瓶颈——扫描量过大（布局）、算子慢（并行/仓库）、排队（供给）、回传慢（客户端）。
- 处方：每类瓶颈对应后续章的开关（聚簇键/仓库尺寸/SOS/多集群/COPY）。
- 回归：用同一查询集对比前后 credit 与墙钟时间，**两条曲线都要看**。
- 记账：资源监视器与成本归因（06/10 章；`user-guide/resource-monitors` ✅ 200）。

## 1.5 🔧 概念类比实验 E3：Time Travel vs SQLite 就地覆盖（非 Snowflake 平台行为）

本机实测（DuckDB 1.5.5/SQLite 3.45.3，脚本 `D:\develops\tmp\dbwave_w8_snowtune\exp.py`）：

- SQLite `UPDATE emp SET salary=150 WHERE id=1` 后原值 `(1,100)` **物理不可回查**——就地覆盖、
  版本不留（🔧 实测输出登记）。
- 模拟方案：另建 `hist(id, salary, valid_from, valid_to)` 历史表，
  `SELECT * FROM hist WHERE '2024-03-01' BETWEEN valid_from AND valid_to` 命中旧值 100（🔧 实测）。
- 对照 Snowflake ⚠️（转述 `user-guide/data-time-travel` ✅ 200）：Time Travel 由元数据+不可变
  微分区天然保留历史版本，as-of 查询**无需**手写历史表；FCR（Fail-safe）为额外兜底期。
- 类比结论：「版本表模拟 as-of」是理解零拷贝时间旅行的最小模型；但 Snowflake 的版本粒度绑定
  存储层不可变块，成本形态完全不同（保留期占存储费，不占计算费）。

## 1.7 常见误解纠偏清单（本章收束 ⚠️ 编者归纳）

Springer 官方 What-You-Will-Learn 五点 ✅（识别根因/解决问题/深谙选项/少犯错/控成本）转译成
五条「先破后立」的误清单，供全书校验阅读姿势：

1. **「调优=改 SQL」**——错。SQL 形状只是四杠杆之一（形状/布局/供给/传输），且是最弱的一个；
   剖面显示扫描量过大时，改 SQL 不动布局等于白改（02/04 章联动）。
2. **「性能=把仓库调大」**——错。升尺寸有次线性折扣（🔧E2 类比：8 线程仅 7.2×），而布局错误
   （小分区/重叠税）在大仓库上照样按读放大付费（04/05 章）。
3. **「控成本=砍仓库/删数据」**——错。第一刀应是免费项：结果缓存复用、暂停窗校准、碎文件装载
   治理；砍尺寸动的是延迟 SLO，须有双账单证据才动（10 章收口）。
4. **「看 P50 均值就够」**——错。云仓上 credit 常烧在尾部：P95 等待、偶发全扫、周期重聚簇；
   03 章画像必须抽尾部样本。
5. **「文档数字直接抄进容量计划」**——错。尺寸-分片映射与代际相关（Gen2 重排 ✅ 见 06 章），
   机制可移植、数字须账户内实测；本册 🔧 数字同样只做量级类比不做换算依据。

## 核心概念速览（中英对照）

- **调优双目标** — Cost-Performance Joint Tuning：延迟与 credit 消耗必须同曲线评估，单目标优化常互相拆台。
- **信用计费** — Credit Billing：仓库按运行秒数消耗 credit，停即止损；服务层后台操作另计 ⚠️。
- **冷启动** — Warehouse Startup Cost：唤醒/首查询的固定开销，高频小负载应复用已启动仓库 ⚠️。
- **无索引引擎** — Index-Free Engine：Snowflake 不建用户 B-tree 索引，靠微分区统计信息与可选 SOS 服务。
- **迁移病灶** — Migration Anti-Patterns：索引/分布键/常驻集群/碎片装载/滥取结果五类旧习惯。
- **度量归因处方** — Measure-Attribute-Prescribe Loop：本章提出的调优工作法，后续章按类展开。
- **时间旅行** — Time Travel：基于元数据与不可变分区的 as-of 历史查询（对照 🔧 SQLite 版本表模拟）。
- **故障安全期** — Fail-safe：Time Travel 之后的 7 天不可自助回滚兜底期 ⚠️（转述 data-time-travel）。
- **资源监视器** — Resource Monitor：账户/仓库级 credit 上限与告警，成本侧的硬闸（10 章主场）。
- **性能总纲** — Performance Overview（docs）：官方把优化分为查询/存储/仓库/客户端四平面，与本书章序一致 ✅。
