## 7.1 无索引引擎的受控例外

Snowflake 内部表**没有用户索引**（04 章 4.3 世界观）。搜索优化服务（Search Optimization Service,
SOS）是官方提供的**表级托管服务**：对声明的列（含表达式列）在后台构建并维护一张把「点查谓词」
映射到微分区位置的辅助结构，使选择性查询跳过大段扫描 ⚠️（总纲
`https://docs.snowflake.com/en/user-guide/search-optimization-service` ✅）。

- 它是「服务」不是「索引对象」：无 B-tree 供你调参，建/维护/计费都走托管路径 ⚠️。
- 与聚簇的分工线（05 章 5.3 呼应）：**范围扫描布局归聚簇，高选择性点查归 SOS**——官方
  queries-that-benefit 页（✅）给的就是这条判别线。

## 7.2 SOS 加速的谓词族（逐条 ✅ 主题页实抓，⚠️ 细节转述）

官方专页组（user-guide/search-optimization/ 下，2026-10-01 均 ✅ 200）：

| 谓词族 | 官方页（省略前缀 ✅） | 调优注记 |
| --- | --- | --- |
| 点查（等值/IN 列表） | point-lookup-queries | 经典 OLTP 式查找，SOS 主场 |
| JOIN 侧加速 | join-queries | 小结果集驱动大表侧的点查化 |
| 结构化列 | structured-queries | 常规列表达式列皆可 |
| 半结构化（VARIANT 路径） | semi-structured-queries | `attr['city']=...` 类谓词的官方解药 |
| 子串/正则 | substring-queries | `LIKE '%x%'` 从全扫到受控定位 |
| 文本 | text-queries | 注意：SOS≠全文检索引擎，语义以该页为准 ⚠️ |
| 标量函数/子查询 | scalar-functions、scalar-subqueries | 表达式列索引化的边界案例 |
| 地理空间 | geospatial-queries | 范围+包含类谓词 |
| AND/OR 语义 | conjunctions-disjunctions | **关键限制页**：OR 跨列组合的受益判定 |

读法纪律：某条查询是否受益**不是直觉题**，官方 conjunctions-disjunctions 页给了逐形态判定表 ⚠️——
这正是本章存在的意义（把「像索引」的直觉关进「何时真有效」的文档牢笼）。

## 7.3 建/用/监控的工程面（⚠️ 转述框架）

- `ALTER TABLE ... ADD SEARCH OPTIMIZATION`（语法以现行 search-optimization-service 页为准 ⚠️）；
  后台逐步建结构，大表非即时生效。
- 监控：Snowsight 表监控面板 + `MONITOR` 类 SQL 函数入口（monitoring-search-optimization ✅ 页名
  「Monitoring search optimization using Snowsight」实抓）。
- 受益确认：view-benefits / queries-that-benefit 两页（✅）给出「先验证查询确实受益再付费」的
  官方流程——本书 10 章「处方前后双读数」纪律的服务版。
- 费用：SOS 按存储+服务持续维护计费 ⚠️（cost-estimation ✅ 页）；**写重表慎用**：每次维护都是
  对新数据的持续索引化成本（与 05 章「写重表慎聚」同构的副作用清单）。

## 7.4 判例：什么表不该开 SOS（本章反面清单 ⚠️ 归纳）

1. 小表：全扫本就毫秒级，纯交维护费；
2. 低选择性谓词：每分区都要命中，辅助结构无从跳起；
3. 高频整表重写（TRANSIENT/批量回填型）：维护费追不上重建成本；
4. 把 SOS 当全文检索/搜索引擎用：语义与能力边界以官方 text-queries 页为准 ⚠️，需求超出时
   对照专用引擎（repo 内 ES 谱系单文件散见，登记不展开）。

## 7.5 🔧 实测 E4：二级索引对点查的量级差（SQLite，非 Snowflake 行为）

200k 行表点查 `a=199999`：无索引 **7.7ms**（全扫）→ `CREATE INDEX ix ON t(a)` 后 **0.05ms**
（≈150×，🔧 实测，脚本 `D:\develops\tmp\dbwave_w8_snowtune\exp.py`）。

- 该差值**不属于** Snowflake：SOS 的收益模型是「点查从全分区扫描降为定位少数分区」，量级
  介于「聚簇改善（E1 的 11×）」与「真索引（E4 的 150×）」之间，且官方明确要求逐查询验证受益
  （queries-that-benefit ✅，⚠️ 转述）。
- 教学口径：E4 演示的是「索引为什么天然快」的最小模型；E1 演示的是「布局改善的天花板」；
  SOS 站在这两极之间，这就是 04/05/07 三章必须连读的原因 ⚠️ 编者归纳。

## 7.7 SOS 引入七步流程（把 7.2–7.4 串成工单 ⚠️ 编者重构）

1. **候选捞取**：从 Query History（✅ 03 章 URL）按「高频×等值谓词×大表」筛查询族，按表聚合。
2. **形态核对**：逐条对官方 queries-that-benefit 与 conjunctions-disjunctions 两页（✅）查「该
   谓词形态是否真在受益名单」——OR 跨列、低选择性 IN 巨列表等当场剔除（7.2 关键限制页）。
3. **现测裁剪基线**：记录候选查询当前读放大/分区命中数（03 章 3.7 模板），无基线不进第 4 步。
4. **灰度开启**：对目标表加 SOS（5.8 式的「先免费后付费」原则同样适用：聚簇未做不先上 SOS）。
5. **受益验证**：官方 view-benefits 流程页（✅）+ 复跑剖面 diff；「表已开 SOS」≠「查询用了 SOS」。
6. **账单复核**：cost-estimation 口径（✅）对维护费与节省 credit 做双账单（10 章纪律前置演练）。
7. **例行监控与退出**：纳入月度巡检（monitoring 页 ✅）；写重化/形态变更后重走 2–5，必要时撤服务。

**七步的失败模式预告**（工业常见 ⚠️ 转述归纳）：跳过第 2 步「直觉当索引开」、跳过第 5 步
「开了就当有效」、忘记第 6 步「维护费长期挂账」——三者都会把 SOS 从「受控例外」变回「新病灶」，
这正是本章 22 页（pp.247–268 ✅）的防御性写法动机。

## 核心概念速览（中英对照）

- **搜索优化服务** — Search Optimization Service (SOS)：表级托管服务，为点查型谓词建「定位结构」⚠️（✅ 总纲页）。
- **无索引例外论** — Controlled Exception：SOS 是「跳区」范式内对「跳读」需求的受控让步（7.1）。
- **点查** — Point Lookup：等值/IN 高选择性谓词，SOS 主场 ✅（point-lookup-queries 页）。
- **表达式列** — Target Columns/Expressions：可优化谓词列与 VARIANT 路径的声明面 ⚠️。
- **受益验证** — View Benefits / Queries That Benefit：官方强制的「先证明有效再付费」流程页 ✅。
- **AND/OR 语义表** — Conjunctions & Disjunctions：跨列 OR 组合常失效的关键限制页 ✅（7.2）。
- **半结构化加速** — Semi-structured Query Optimization：VARIANT 路径谓词的官方定位方案 ✅。
- **维护计费** — Ongoing Maintenance Cost：SOS 持续服务费（存储+服务），写重表的隐性税 ⚠️（✅ cost-estimation 页）。
- **全文≠SOS** — Not a Search Engine：SOS 不替代专用检索引擎，能力边界以 text-queries 页为准 ⚠️。
- **量级位阶** — Speedup Spectrum：聚簇（E1 ~11×）< SOS（逐查询验证）< 真索引（E4 ~150×）的直觉标尺 🔧。

## 最新演进与工业实践

2024→2026（前缀 `https://docs.snowflake.com/en/user-guide/` 均 ✅ 200；⚠️ 转述）：

- **文档体系产品化**：search-optimization/ 专页族（9+ 页 ✅ 实抓清单见 7.2）在 2024 后细分持续
  加密——substring/正则、地理、JOIN 加速、标量子查询各有专页，本书成书时的「一页总纲」已扩成
  「按谓词族自查」体系，读法应先对页再动 DDL ⚠️。
- **监控面增强**：Snowsight 监控页（search-optimization/monitoring-search-optimization ✅）与
  Performance Explorer（performance-explorer ✅）联动成为「受益/失效」的常规取证通道 ⚠️。
- **与托管 Iceberg/新表类型的边界**：SOS 语义面向内部表；开放表格式侧的对应能力以各表类型文档
  现行版为准 ⚠️（对照 [../Data_Lakehouse_in_Action/00-总览与阅读地图.md](../Data_Lakehouse_in_Action/00-总览与阅读地图.md) 的格式内统计线）。
- **工业实践**：SaaS 应用「租户+业务 ID」双等值点查的 API 化查询是 SOS 最典型受益场景 ⚠️ 转述；
  反模式是把 SOS 用于报表型范围聚合（付费无益，官方受益页即为此劝退设计 ✅）。
- **对照系**：其他云仓的「自动索引/物化建议」（Redshift/BigQuery 线）与 SOS 的「托管定位结构」
  是两条不同的自动化哲学——人工可选型 vs 服务黑箱型；两册 00 已实链（见 7.6），评价 ⚠️ 转述口径。
