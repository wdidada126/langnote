## 2.1 Snowflake 优化器的定位：自动、无提示、统计驱动

Snowflake 查询优化器为**基于代价的自动优化器**（CBO）⚠️（转述
`https://docs.snowflake.com/en/user-guide/guides-overview-performance` 与 `sql-reference/sql/explain`，
均 ✅ 200）：

- 不接受用户 hint（无 `/*+ ... */` 类通道），SQL 即意图，计划由引擎自选 ⚠️。
- 统计信息不来自 ANALYZE 式全表采样，而是**内嵌在微分区元数据**：每列 min/max、分区数、
  越界率等由存储层自动维护（第 4 章主场）——这是本章放在微分区章之前的原因：优化器的「眼睛」
  就是 zone-map 元数据。
- 编译产物为多阶段计划：解析→分区（partition）→编译（compile）→执行，剖析器中可见（第 3 章）。

## 2.2 优化器能自动做什么（本章知识主干 ⚠️ 转述框架）

按官方性能文档主题归纳的四类自动决策 ⚠️：

1. **谓词下推与分区裁剪**：WHERE 谓词尽量推到扫描算子，用微分区 min/max 跳过不重叠分区
   （选择性布局的收益公式在 04 章展开；🔧 类比见 E1）。
2. **JOIN 顺序与策略选择**：自动重排 JOIN 次序；按输入规模选 hash join / broadcast 形态；
   `EXPLAIN` 输出中可见 JOIN 类型标注（✅ explain 页）。
3. **聚合/投影提前**：group-by 下推、无用列早剪，减少 shuffle 数据量。
4. **改写与缓存利用**：子查询解相关、常量折叠；结果缓存命中时直接跳过执行（06 章 cache 面）。

**调优者杠杆的边界**：既然不可提示，工程师影响计划的手段只剩——**改写 SQL 形状**、
**改数据布局**（聚簇，05 章）、**改计算供给**（仓库，06 章）、**用观察反推**（剖析，03 章）。
这正是本书后续八章的存在理由，也是「优化器」章只有 13 页（pp.25–37 ✅ 页区间实抓）的原因：
优化器本体不可调，可調的是它消费的元数据与资源。

## 2.3 EXPLAIN：优化器的公开接口

`EXPLAIN [ LOGICAL | EXTENDED | JSON ] <query>` ⚠️（语法与示例以
`https://docs.snowflake.com/en/sql-reference/sql/explain` ✅ 200 为准，不背旧版细节）：

- 输出逻辑计划行（JOIN/AGGREGATE/FILTER/TABLE SCAN），**不含运行期统计**——看真实耗时必须用
  Query Profile（Snowsight 运行后视图，03 章主场）。
- 工业用法：上线前用 EXPLAIN 检查「谓词是否下推到扫描」「JOIN 是否变成大表笛卡尔」，上线后用
  Profile 验证分区裁剪比例——两件套互补 ⚠️ 转述自性能文档线。
- 与 Redshift/BigQuery 对照：Redshift EXPLAIN 可看 DISTKEY 驱动的计划；BigQuery 干跑
  （dry run）预估扫描字节——三家中只有 BigQuery 把「预估字节」做成成本工具，Snowflake 侧的
  对应物是 EXPLAIN 之外看分区裁剪估计（⚠️ 转述）。

## 2.4 优化器的盲区（本章的「坑」面 ⚠️ 归纳）

- **布局盲区**：min/max 重叠严重时裁剪估计失真——优化器再聪明也救不了乱序装载（04/05 章处方）。
- **UDF/外部函数**：行级 JS/Python UDF 破坏集合式下推，代价在剖析器中以「Step 行数放大」显形（03 章）。
- **隐式类型转换**：谓词列被转换会使 zone-map 失效（写法纪律，09 章客户端参数绑定同题）。
- **TOP 优化**：`ORDER BY ... LIMIT` 场景有专门的 Top-K 剪枝优化路径 ⚠️（转述
  `https://docs.snowflake.com/en/user-guide/querying-top-k-pruning-optimization` ✅ 200），
  旧版习惯的手工子查询改写可能画蛇添足。

## 2.5 🔧 类比实验（引用 04 章 E1，非 Snowflake 引擎行为）

本机 DuckDB 1.5.5 复算「统计驱动裁剪」的最小模型（数字与 04 章 E1 同源，
`D:\develops\tmp\dbwave_w8_snowtune\exp.py`）：同一谓词 `k BETWEEN 4000000 AND 4010000` 在
8M 行表上，按 k 物理有序时 2.2ms、hash 打乱后 25.3ms（≈11×），全表基线 62.7ms（🔧 实测）。
结论迁移到本章语义：**优化器的选择率估计质量 = 底层元数据的区分度质量**；引擎不同（DuckDB
为单进程 row-group zone-map，Snowflake 为分布式微分区统计），量级机制同类 ⚠️ 类比声明。

## 2.7 优化器观察自检单（十问 ⚠️ 编者按官方主题归纳）

拿到一条「慢查询」，进入 03 章精细剖查之前，先用本单做 30 秒粗筛（每问都指向一个后续章）：

1. 谓词列是常用过滤列吗？——否 → 布局问题先天（05 章键序题）。
2. WHERE 里有函数包裹列/隐式转换吗？——有 → zone-map 失效嫌疑（2.4 盲区三）。
3. JOIN 键两侧类型一致吗？大表在哪一侧？——不一致/大侧 build → 形状改写（02 章 2.2-2）。
4. 有 `SELECT *` 吗？——有 → 列裁剪白给不要（04 章列式语义）。
5. `ORDER BY+LIMIT` 场景吗？——是 → 确认当前版本 Top-K 路径已生效，别手写等价子查询（2.4）。
6. 同语句上次执行是否 0 秒？——是 → 结果缓存已被你绕过（改了参数？06 章缓存面）。
7. 表是刚经历大批量乱序装载吗？——是 → 先等重聚簇/改装载序（04/05 章）。
8. 查询走的是 UDF 行级逻辑吗？——是 → 集合式化或移出主路径（2.4 盲区二）。
9. EXPLAIN 里扫描算子下方有没有 FILTER 谓词？——没有下推 → 检查改写（✅ explain 页口径）。
10. 以上全过仍慢？——移交 03 章按剖面分段归因，大概率不再是「优化器问题」而是供给/传输问题。

**十问的设计逻辑**：把「怪优化器」这一最常见误诊，压缩成可证伪的粗筛；Snowflake 的 hint-free
架构（2.1）意味着工程师的价值不在「指挥计划」，而在「喂给优化器更好的元数据与形状」——十问
正是这一立场的操作化 ⚠️ 编者归纳。

## 核心概念速览（中英对照）

- **基于代价优化** — Cost-Based Optimizer：以分区统计估计选择率，自动选计划；Snowflake 不接受 hint ⚠️。
- **无提示设计** — Hint-Free：意图由 SQL 表达，计划归引擎，人调元数据与资源而非计划本身。
- **谓词下推** — Predicate Pushdown：过滤尽量贴近扫描，配合 zone-map 跳过微分区（04 章）。
- **分区裁剪** — Partition Pruning：用 min/max 元数据判定分区与谓词无交集而免读（🔧E1 类比）。
- **JOIN 重排** — Join Reordering：引擎自动调整连接顺序与策略（hash/broadcast）⚠️。
- **执行计划** — EXPLAIN Output：逻辑计划公开接口，仅静态信息，不含运行统计（✅ explain 页）。
- **查询剖析** — Query Profile：运行期算子级统计视图，本章的「事后真相」（03 章主场）。
- **解相关改写** — Decorrelation：将相关子查询转为 JOIN 形态以便集合式执行 ⚠️。
- **Top-K 剪枝** — Top-K Pruning：`ORDER BY+LIMIT` 的专用优化路径，减少排序全量 ⚠️（✅ URL 见 2.4）。
- **zone-map 失效** — Statistics Bypass：隐式转换/UDF/布局重叠使列统计失去区分度，本册反复出现的病灶。

## 最新演进与工业实践

2024→2026（URL 均 `curl -sI` ✅ 200；机制为文档转述 ⚠️）：

- **优化面自动化**：官方把「优化器不可调」的补偿做成产品面——Top-K pruning
  （https://docs.snowflake.com/en/user-guide/querying-top-k-pruning-optimization ✅）等引擎侧
  默认优化持续上线，本书 2024 版中的手工改写建议在 2026 应先用默认路径复测 ⚠️。
- **观测配套演进**：Snowsight Query Profile 与 Performance Explorer
  （https://docs.snowflake.com/en/user-guide/performance-explorer ✅）持续增强计划-执行联动，
  工业实践主流已是「EXPLAIN 预检 + Profile 复盘 + Performance Explorer 横截面」三件套 ⚠️ 转述。
- **Dynamic Tables/增量物化**：官方 query-options 线（https://docs.snowflake.com/en/user-guide/
  performance-query-options ✅）把「改写查询换增量刷新」列为一等优化手段，属本书方法论的 2025+
  延伸 ⚠️。
- **跨平台对照**：Trino/BigQuery/Redshift 的 CBO 均持续引入运行时统计反馈；共同趋势是
  「统计来源从 ANALYZE 转向写路径内嵌」——Snowflake 微分区元数据是该路线的最早工业化实现之一
