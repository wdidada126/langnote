## 4.1 微分区是什么（⚠️ 转述官方定义框架）

权威页：`https://docs.snowflake.com/en/user-guide/tables-clustering-micropartitions` ✅、
`https://docs.snowflake.com/en/user-guide/tables-micro-partitions` ✅。要点 ⚠️ 转述：

- 表数据切成**不可变、压缩、列式**的微分区；目标规模约 16MB（官方以「~64MB 压缩前」一类口径
  出现过版本表述差异——具体数字以现行文档为准 ⚠️，本册不锁死单一数值以免臆写）。
- 每个微分区自动维护**列级元数据**：min/max、distinct 估计、越界值等，服务层维护、用户不可见
  亦不可改——这就是 02 章优化器统计信息的物理来源。
- 装载顺序决定分区内容：批量 COPY 按文件顺序切分区；持续小 INSERT 造成大量小分区与值域交错
  （01 章迁移病灶④的物理机制）。
- **不可变 + 元数据版本** = Time Travel/Zero-Copy Clone 的地基（01 章 🔧E3 对照）：改数据=写新
  分区+改元数据指针，旧版本天然留存。

## 4.2 裁剪经济学：微分区如何变成钱

- 查询谓词 vs 分区 min/max：无交集→整分区跳过（scan 行数为 0 的「免费」裁剪）⚠️。
- 重叠税：值域交错的分区群使谓词「每个分区都可能命中」→ 读放大（03 章症状①）。
- 成本双侧 ⚠️（`cost-understanding-data-storage` ✅）：存储按压缩字节计费——布局本身不省存储费，
  省的是**扫描时长 → credit**；这就是「微分区章」紧挨「聚簇章」的原因：布局是性能杠杆不是成本杠杆。
- Top-K/分区级 early-out：官方 Top-K pruning 页 ✅（02 章 URL）属同一裁剪家族的算子级延伸。

## 4.3 与「索引范式」的根本分歧

传统 RDBMS：二级索引 → 指针跳读；Snowflake：无用户索引 → **批量顺序读 + 元数据跳区** ⚠️。
推论（本章的调优世界观）：

1. 高频等值点查（OLTP 式）在纯微分区模型下不经济 → 07 章 SOS 是「补索引」的受控例外。
2. 大范围扫描型分析查询反而是主场景：顺序读 + 列裁剪 + 压缩，分区越大越理想。
3. 「让常用过滤列在分区间尽量不重叠」= 聚簇（05 章）——微分区给出机制，聚簇键给出手段。

## 4.4 装载路径对布局的塑造（⚠️ 转述，细节以官方装载文档为准）

- COPY（批量、文件内有序）→ 天然连续分区；
- 微批/流式 INSERT（Snowpipe 类）→ 小分区堆积，服务层合并但值域仍交错；
- 「先排序再落文件」的卸载/装载侧预处理（把 ORDER BY 做进导出文件）是**零成本聚簇近似** ⚠️——
  工业实践中常比事后重聚簇更省钱（10 章成本闭环联动）。

## 4.5 🔧 实测 E1：zone-map 剪枝的有序/乱序对照（DuckDB，非 Snowflake 行为）

脚本 `D:\develops\tmp\dbwave_w8_snowtune\exp.py`，DuckDB 1.5.5，8M 行 `(k,v,p)`：

| 表布局 | 谓词 `k BETWEEN 4000000 AND 4010000`（读 v 与 p） | 用时（5 次取最优） |
| --- | --- | --- |
| 按 k 物理有序 | 命中 0.125% 行 | **2.2ms** |
| hash 打乱 | 同谓词同行数 | **25.3ms**（≈11×） |
| 全表扫描基线 | 无谓词 | 62.7ms |

解读 ⚠️：有序表使 row-group min/max 高度可分，绝大多数行组被剪枝——与 Snowflake 微分区
「按过滤列有序 ⇒ 裁剪率↑」同机制；DuckDB 是单进程 row group（默认 12 万行组粒度），
**规模、粒度、执行模型均与 Snowflake 不同，数字不可换算**，仅证机制方向 📐。
进一步：乱序表 25.3ms 优于全扫 62.7ms，说明即使交错仍有部分剪枝——对应聚簇深度
「1.0–2.0 已可用、不必强迫症到 1.0」的官方口径 ⚠️（05 章）。

## 4.6 诊断读数与处方挂钩

- 读 03 章「读放大」指标：比值 >50× 且谓词列固定 → 进入 05 章聚簇评估流程。
- 比值高但谓词列多变 → 聚簇无解，考虑 07 SOS 或改写（热点谓词固化为聚簇首列的取舍）。
- 分区过小（小 INSERT 流）→ 先治装载（4.4）再谈布局。

## 4.8 存储侧账单读法（微分区经济的成本面 ⚠️ 转述）

权威页：`https://docs.snowflake.com/en/user-guide/cost-understanding-data-storage` ✅ 200。与本章
机制直接挂钩的四条账目口径：

1. **压缩后计费**：微分区列式压缩（官方口径典型压缩比以现行页为准 ⚠️），同样的逻辑行，
   装载序影响物理布局但**基本不影响账单字节数**——布局优化省扫描 credit，不省存储费（4.2 重申）。
2. **Time Travel/Clone 占用计入存储账**：不可变分区的历史留存要付费 ⚠️（data-time-travel ✅ 联动
   01 章 🔧E3）——长保留期+多克隆的账户，「看不见的旧分区」是存储账单常态项。
3. **Stage 与 Failsafe 分列**：内部 stage 文件、Fail-safe 期数据各有独立计量线 ⚠️（以现行页
   分类为准），调优报告应把「表存储」与「账户总存储」分开陈述。
4. **小分区的隐性税**：碎分区使元数据行膨胀与服务层合并工作量上升（tables-micro-partitions ✅
   主题延伸），装载治理（4.4）同时改善性能账与后台服务账。

**读法结论**：微分区章的「成本」是双元的——扫描时长驱动的 credit（本册主战场）与留存字节驱动的
存储费（TDG 08 入门线）；混淆两者是「用布局优化去砍存储账单」这类误诊的根源 ⚠️ 编者归纳。

## 核心概念速览（中英对照）

- **微分区** — Micro-partition：不可变、压缩、列式的表物理单元，自动带列统计 ⚠️（✅ 官方定义页）。
- **区域图** — Zone Map / min-max Statistics：分区块级值域摘要，粗裁剪的元数据基础（🔧E1 同机制）。
- **裁剪** — Partition Pruning：谓词与分区值域无交集则整区跳过，读放大读数直接受益 ⚠️。
- **读放大** — Read Amplification：扫描量 ÷ 结果量；布局病灶的成本化身（03 章症状挂钩）。
- **不可变存储** — Immutable Storage：写=新分区+元数据指针，历史留存支撑 Time Travel/Clone。
- **克隆零拷贝** — Zero-Copy Clone：只复制元数据引用，不改数据字节（01 章 🔧E3 对照面）。
- **小分区病** — Small-Partition Fragmentation：连续小 INSERT 切碎布局，裁剪与服务层开销双输 ⚠️。
- **装载定序** — Load-Order Clustering：COPY 文件内有序≈免费聚簇近似（4.4 处方）。
- **无索引范式** — No-User-Index Philosophy：跳区代替跳读，点查例外走 SOS（07 章）。
- **存储费≠布局费** — Storage vs Scan Cost 分离：布局影响扫描 credit，不省压缩存储费 ⚠️。
- **Top-K 早停** — Top-K Pruning：ORDER BY+LIMIT 在分区元数据层的专用短路 ⚠️（✅ 02 章 URL）。
