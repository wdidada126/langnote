## 6.1 仓库 = 计算供给的唯一旋钮

虚拟仓库是按需启停的 MPP 计算集群 ⚠️（`https://docs.snowflake.com/en/user-guide/warehouses-overview` ✅）。
调优者面对的不是「集群」而是**一张属性表**（本章逐项展开）：

- **尺寸 SIZE（T 恤码 XS→XLL）**：每升一档算力×2、并行分片×2、credit 速率×2 ⚠️——「更快不一定更贵」
  的算术根据：时长减半抵消速率翻倍，且排队消 loss 是净赚面。
- **自动暂停 AUTO_SUSPEND / 自动恢复 AUTO_RESUME**：空闲止损与免运维唤醒的折中；暂停过频=冷启动
  税（03 章 Pending 段），不过频=空转烧钱 ⚠️。
- **类型**：Standard / Snowpark-optimized（大内存作业）两线 ⚠️（
  `https://docs.snowflake.com/en/user-guide/warehouses-snowpark-optimized` 于 user-guide 索引实抓 ✅）。
- **多集群 AUTO_SCALE + 扩容上限**：并发轴，见 6.3 与 08 章。

官方专页组（均 ✅ 200）：尺寸选择 performance-query-warehouse-size、队列
performance-query-warehouse-queue、缓存 performance-query-warehouse-cache、并发上限
performance-query-warehouse-max-concurrency、查询加速 performance-query-warehouse-qas、
仓库总优化面 performance-query-warehouse、仓库考量 warehouses-considerations。

## 6.2 Scaling Up：单查询变快的主路径（✅ 页主题 ⚠️ 细节）

- 症状定位（03 章）：Spill 落盘、Sort/Aggregate 长段、扫描带宽受限 → 升尺寸。
- 反例：小查询升尺寸只交「冷启动+更高费率」学费；**先问延迟目标是否存在**，再问尺寸。
- 成本记账 ⚠️：credit 消耗 = 运行秒 × 尺寸费率 ×（多集群时）活跃集群数——三个因子都有独立旋钮，
  本章给的是「按因子归因」而非「一刀切升档」；排队损失的消解是升档收益中常被低估的一项 ⚠️。

## 6.3 Scaling Out：多集群与并发供给

- 单集群并发超限→排队（warehouse queue ⚠️ 转述）；多集群 AUTO_SCALE 让并发查询分布到镜像集群，
  **不加速单查询**，只削队列头 ⚠️（warehouses-multicluster ✅）。
- max concurrency 限流：防止突发并发吃穿预算的阀门 ⚠️（performance-query-warehouse-max-concurrency ✅）。
- 排队三选择（本章框架 ⚠️）：加集群（并发）、加尺寸（单查询吞吐）、接受排队（低峰错峰）——
  与 08 章并行化共用「供给三态」心智模型。

## 6.4 缓存三层与「重复查询不重复付费」

⚠️ 转述 performance-query-warehouse-cache ✅ + result cache 口径：

1. **远端对象存储**：所有表数据的真源，慢而无限；
2. **仓库本地磁盘缓存**：已启动仓库的热分区落本地，重查显著提速（🔧E5 升温类比）；
3. **结果缓存**：同查询 24h 窗内直接返回（口径以现行文档为准 ⚠️），BI 仪表盘重复问题的第一道免费闸。

调优含义：仓库「保活」与「暂停」的取舍，本质是**本地缓存价值 vs 空转 credit** 的持续对赌 ⚠️；
高频小查询负载倾向保活+小仓库，扫描型大查询倾向即开即停+大仓库。

## 6.5 查询加速与自适应供给（2024→2026 的自动挡）

- **Query Acceleration Service（QAS）**：突发大查询可借用额外算力跑扫描/重排部分 ⚠️（
  performance-query-warehouse-qas ✅ 页名 Trying query acceleration 实抓）。
- **Adaptive Compute / Gen2 仓库**：官方 2024+ 自动化供给线——自动调整尺寸/集群以省 credit；
  Gen2 重排尺寸阶梯（warehouses-adaptive ✅、warehouses-gen2 ✅）——读本书 6.2 的尺寸换算时
  先做代际核对（演进节展开）。
- **资源监视器硬闸**：credit 上限、告警阈值、 suspend 动作 ⚠️（resource-monitors ✅）——
  尺寸/自动扩一切的「预算护栏」，10 章方法论收口处再引用。

## 6.6 🔧 实测 E2/E5：并行度与缓存温度（DuckDB，非 Snowflake 行为）

- **E2（尺寸≈并行分片）**：20M 行分组聚合，`SET threads=1` 3.79s vs `threads=8` 0.53s ≈ 7.2×
  （🔧 实测）——升尺寸的收益模型是**近线性但非完美线性**（服务发现/倾斜/固定开销侵蚀），
  与 6.2「时长减半抵消费率翻倍」的算术同构；DuckDB 线程≠Snowflake 节点，数字不可换算 ⚠️。
- **E5（缓存升温）**：同查询 7ms→6ms→4ms（🔧 三连实测）——量化「第一次慢」的结构性成分；
  对应 6.4 保活对赌：Snowflake 的暂停即清本地缓存（冷仓库首查多读远端 ⚠️），代价比 DuckDB
  进程内缓存高一个数量级，故对赌天平更偏向「热窗口保活高频负载」⚠️ 类比外推。

## 6.8 仓库属性表年审清单（把 6.1 变成巡检制度 ⚠️ 编者归纳）

每仓库逐项打表（示例槽位，不含结论数字——须账户内实测）：

1. **用途与 SLO 标签**：交互/批量/ETL/沙箱？无标签仓库=孤儿资源，排队互相污染（8.3-5）。
2. **尺寸↔负载匹配**：抽近 30 天剖面，扫描/内存瓶颈型长尾是否指向升档？「快而闲」是否指向降档？
3. **AUTO_SUSPEND 值**：与负载到达间隔分布对照（高频小负载→加长；潮汐批任务→缩短），记录冷启动
   税变化（03 章 Pending 段读数）。
4. **多集群与 AUTO_SCALE 上限**：上限×尺寸费率=最坏小时账单，超预算即削上限（而非事后追认）。
5. **资源监视器挂接**：每仓库至少一条阈值线 + 一条动作线（notify/suspend）⚠️（resource-monitors ✅）。
6. **类型正确性**：大内存 Snowpark 负载是否错用 Standard（snowpark-optimized 页 ✅ 适用口径）。
7. **代际与自动挡覆盖**：Gen2/Adaptive Compute 可用而未用者，列「为何手工」例外清单 ⚠️（6.5）。
8. **Owner 与命名纪律**：无主仓库是「看不见的账单」第一来源（10 章记账联动）。

**年审的元教训**：仓库是本书全部处方中**唯一直接花钱**的一类——布局/SOS 有账单回声，而尺寸与
暂停策略本身就是账单主体；故 6.8 的清单排在剖面模板（03 章 3.7）之后、成本闭环（10 章）之前，
承上启下 ⚠️ 编者归纳。

## 核心概念速览（中英对照）

- **虚拟仓库** — Virtual Warehouse：按需启停的 MPP 计算集群，调优供给侧唯一旋钮 ⚠️（✅ overview 页）。
- **尺寸阶梯** — Warehouse Size（T-shirt）：每档算力/分片/费率×2 的代际梯子；Gen2 重排 ⚠️（✅ gen2 页）。
- **自动暂停/恢复** — AUTO_SUSPEND / AUTO_RESUME：空闲止损与免运维唤醒；频率=冷启动税与空转费的折中 ⚠️。
- **扩容（向上）** — Scaling Up：加大尺寸提单查询速度；小查询升档纯交学费 ⚠️（✅ size 页）。
- **扩展（向外）** — Scaling Out：多集群镜像并发，削队列不加速单查询 ⚠️（✅ multicluster 页）。
- **排队** — Queuing：并发超限时的工作等待，Pending 段的病灶之一 ⚠️（✅ queue 页）。
- **最大并发** — Max Concurrency：仓库级限流阀，防突发吃穿预算 ⚠️（✅ max-concurrency 页）。
- **三层缓存** — Remote/Local-Disk/Result Cache：远端真源→仓库本地→结果捷径；重复查询的三道免费闸 ⚠️（✅ cache 页）。
- **查询加速** — Query Acceleration Service：突发算力借用面 ⚠️（✅ qas 页）。
- **自适应算力** — Adaptive Compute：2024+ 自动供给线，自动挡替代人工尺寸学 ⚠️（✅ adaptive 页）。
- **资源监视器** — Resource Monitor：credit 硬闸/告警/暂停动作，护栏设施 ⚠️（✅ 页）。
- **Snowpark 优化型** — Snowpark-optimized Warehouse：大内存单节点型仓库，重内存作业专用 ⚠️（✅ 索引实抓）。

## 最新演进与工业实践

2024→2026（URL 均 ✅ 200；状态 ⚠️ 转述）：

- **Adaptive Compute 成为默认叙事**：官方 warehouses-adaptive 页（✅）把自动尺寸/自动集群推到
  产品前台，2026 实践中「手工 T 恤尺寸学」让位于「给约束、让引擎选」——本书 6.1–6.3 的属性表
  读法仍成立，但处方排序应变：先评估自动挡覆盖度，再手工补刀 ⚠️。
- **Gen2 仓库代际**：Standard 2nd Generation（warehouses-gen2 ✅）重排尺寸-性能映射，旧版
  XS–XLL 换算数字须按代际重校 ⚠️。
- **QAS 与预算护栏联动**：算力借用计入成本的新科目，资源监视器口径同步扩展（qas/resource-monitors
  两页现行版 ⚠️）。
- **工业实践**：FinOps 成熟团队的仓库治理清单≈本章属性表——「每仓库有延迟 SLO？有 AUTO_SUSPEND
  策略？有监视器硬闸？有无用仓库？」四问制；对照 BigQuery slot 预留/弹性与 Redshift RA3/Serverless
  的同类治理（两册 00 已实链，见 6.7）。
- **成本工具面**：Optimization insights（cost-optimize ✅ 线）自动给出「右型化仓库/休眠调度」
  建议，2026 已成常规入口 ⚠️——与本书「按因子归因」方法论同向，工具化落地。
