## 3.1 为什么剖析器占全书篇幅第一

第 2 章结论「优化器不可调」的直接推论：**调优者的主要工作 = 读执行现场**。Query Profile 是
Snowsight 中单次查询的运行期算子级视图 ⚠️（转述
`https://docs.snowflake.com/en/user-guide/performance-query-exploring` 与
`https://docs.snowflake.com/en/user-guide/ui-snowsight-activity`，均 ✅ 200）；本章教「从剖面图
反推处方」的模式识别术，后续 04–09 章每条处方都回接到这里的症状编码。

## 3.2 剖析对象的读法（⚠️ 转述官方主题框架）

一次查询的生命周期分段 ⚠️（Query Profile 视图的分段命名以官方页为准）：

1. **Pending/启动段**：仓库唤醒与排队等待——若此段占比高，处方在 06/08 章（供给），不在 SQL。
2. **Compile/优化段**：编译耗时——复杂超长 SQL 或对象过多时显形，处方是拆语句/治理对象数。
3. **Execute 算子段**：
   - **Table Scan 行/分区数**：读入行数 ÷ 结果行数 = 裁剪效率的直接读数（04/05 章处方挂钩点）。
   - **Join 段**：两侧输入规模、是否出现「大表 build 侧」反选择——02 章自动重排的失效现场。
   - **Aggregate/Sort 段**：分组基数、 spill/磁盘落写信号——尺寸不足的读数（06 章 scaling up）。
   - **Exchange 段**：跨节点数据重分布量——倾斜（skew）由节点间最慢 worker 显形（08 章）。

配套工具面 ⚠️ 转述：Query History（筛选慢查询/高 credit 查询，✅ ui-snowsight-activity）、
Performance Explorer（账户级横截面，✅ performance-explorer）、`ACCOUNTS`/`QUERY_HISTORY` 类
元数据查询（TN 表函数细节标 ⚠️：语法以官方 SQL 参考为准，本章不复写以免版本漂移）。

## 3.3 症状→处方编码表（本章精华，按 ⚠️ 推定整理为可执行清单）

| 剖面症状 | 根因候选 | 本书处方章 |
| --- | --- | --- |
| Scan 读入行数远超输出（百倍级） | 布局重叠/谓词非聚簇列 | 04 微分区、05 聚簇键 |
| Scan 行数合理但单节点长尾 | 数据倾斜或 JOIN 键热点 | 08 并行化 |
| Pending 段恒定数秒 | 仓库已暂停冷启动 | 06 仓库（auto suspend 时长权衡） |
| Pending 段随并发增长 | 队列（并发超限） | 06/08（多集群/QAS ✅ 页见 6.5） |
| Sort/Aggregate 磁盘落写 | 内存不足 | 06 scaling up（✅ performance-query-warehouse-memory 主题） |
| 点查高频但每次都全扫 | 缺 SOS 且聚簇收益低 | 07 搜索优化服务 |
| 结果行数巨大、Execute 后回传慢 | 客户端拉取模式 | 09 客户端侧 |
| 相同 SQL 第二次 0 秒完成 | 结果缓存命中 | 06 缓存面（🔧E5 类比） |

## 3.4 度量纪律：先基线后改动

作者方法论（⚠️ 依 Springer 简介 hands-on 口径归纳）：

- 任何处方前先固定「三读数」：墙钟时间、读入分区/行数、credit（由时长×尺寸推算 ⚠️）。
- 同一查询在不同仓库尺寸/聚簇状态下跑矩阵，剖面 diff 而不是只看总时长（06 章实验范式）。
- 警惕**编译正确但画像异常**：EXPLAIN（02 章）静态计划无法暴露倾斜/落盘，只有 Profile 可以——
  这就是两章分拆的教科书式分工。

## 3.5 🔧 类比实验引用 E5：缓存升温改变读数（非 Snowflake 平台行为）

本机 DuckDB 1.5.5：同一随机谓词查询连续三次 7ms→6ms→4ms（🔧 实测，
`D:\develops\tmp\dbwave_w8_snowtune\exp.py`）——首次含冷缓存开销。对应本章语义：剖析读数
必须区分「冷/热仓库」场景；Snowflake 侧的三层缓存（远端对象存储→仓库本地磁盘→内存）与结果
缓存 ⚠️（转述 `https://docs.snowflake.com/en/user-guide/performance-query-warehouse-cache` ✅ 200）
使「第一次慢」可能是**结构性**的而非病灶。另引 DuckDB `EXPLAIN ANALYZE`（本机可用）作为
「算子级运行统计」的最小可跑模型：与 Snowflake Profile 同构的动机（静态计划不够看），不同
的载体（单进程 vs 分布式）⚠️ 类比声明。

## 3.7 剖面精读模板（提交给团队的标准件 ⚠️ 编者重构）

作者 hands-on 立场 ✅ 的落地形态：一次「有处方价值的」剖面记录应含以下槽位（模板不含具体数字，
数字必须来自真实账户——本册不可实测纪律）：

- **头部**：查询指纹（脱敏 SQL 骨架）/ 仓库名+尺寸+代际 / 时间窗（冷热声明：当日首跑 or 复跑，
  关联 🔧E5 缓存教训）/ 结果缓存命中与否。
- **三读数基线**：墙钟 ms、扫描行与分区数（读放大比值）、credit 估算（运行秒×尺寸费率 ⚠️ 口径）。
- **分段占比**：Pending / Compile / Execute(Scan·Join·Agg·Sort·Exchange) 各段 ms 与%，
  标注「与上次记录的差」。
- **异常签名**：对照 3.3 表勾选（如「Scan 读放大 120× + 无 Pending」= 布局单因子）。
- **处方假设**：一句话可证伪假设（例：对谓词列 date_col 声明聚簇首列，预期读放大降 10×）。
- **回归计划**：同查询集版本号 + 复跑时刻 + 预期双账单（延迟↓、credit 净额判断）。

**为什么模板重要**（本章方法论收束 ⚠️）：Profile 截图人人会看，但「无基线不比较、无假设不处方、
无回归不结案」才是把 63 页章读成生产力的关键；三件套同时也是跨团队沟通的最小协议。

## 3.8 剖面的边界与取证纪律（⚠️ 编者注）

- 画像数据有**保留期与采样口径**问题：过旧的查询、被截断的统计在复盘时会失真——引用画像
  结论必须带时间戳与视图版本注记（3.7 模板的「时间窗」槽位即为此设）。
- 跨账户/跨地域画像不可直接互比：仓库代际（06 章 Gen2）、数据布局状态均入混淆因子；
  「别人账户的处方数字」只能当假设，不能当结论 ⚠️。
- 本册不可实测纪律在此章最硬的落点：所有症状-处方对（3.3 表）给的是**读法**而非**阈值**，
  阈值一律由你的账户基线生成。

## 核心概念速览（中英对照）

- **查询剖析** — Query Profile：运行期算子级统计视图（行数/耗时/内存/IO），调优的第一现场 ✅ 主题。
- **查询历史** — Query History：账户级查询流水与筛选面板，找「该治的查询」而非「在看的治疗」⚠️。
- **性能透视** — Performance Explorer：横截面聚合分析面（模式识别用）⚠️（✅ URL 见 3.2）。
- **读放大** — Read Amplification：扫描行数 ÷ 输出行数，裁剪失效的直接读数（04/05 章挂钩）。
- **长尾 worker** — Skew/Straggler：节点间耗时不齐，倾斜诊断信号（08 章处方）。
- **磁盘落写** — Spill to Local Disk：内存不足时算子落盘，延迟陡增信号（06 章尺寸处方）⚠️。
- **等待段** — Pending/Queue Time：仓库启动与排队耗时占比——供给问题的分诊标志（06/08）。
- **编译段** — Compile Time：优化器编译耗时，超长 SQL 病灶（02 章联动）。
- **结果缓存** — Result Set Cache：相同查询短窗内秒回，读数须注明冷热 ⚠️（3.5 章 🔧E5）。
- **三读数纪律** — Time/Rows/Credit Baseline：处方前后同口径对比，双目标（性能×成本）留痕。
- **剖面对比矩阵** — Profile Diff：同一查询跨尺寸/布局/并发的画像族，作者 hands-on 方法核心 ⚠️。
