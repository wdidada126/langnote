# 第 11 章 性能与可伸缩性（原书 pp.251-272）

> **"线程能提升性能，但用错了会更慢。"**
> 本章给出三样东西：**Amdahl 定律（收益上限）、线程的三类开销、减少锁竞争的四招**。
> 本仓库原笔记只记了 "Amdahl 定律" 一个词，本篇补全。
>
> 配套专篇：[concepts/Amdahl定律与可伸缩性.md](concepts/Amdahl定律与可伸缩性.md)

## 一、本章地图

```
性能 ≠ 可伸缩性（两个不同维度）
        ↓
Amdahl 定律：串行部分决定收益上限
        ↓
线程引入的三类开销：上下文切换 / 内存同步 / 阻塞
        ↓
减少锁竞争的四招：快进快出 / 锁分解 / 锁分段 / 换掉独占锁
        ↓
避免热点域（AtomicLong 计数器）；不要对象池
        ↓
如何度量：CPU 利用率、JMH、JFR
```

## 二、性能 vs 可伸缩性（pp.251-253）

| 概念 | 定义 | 度量 |
| --- | --- | --- |
| **性能（performance）** | 单个任务"多快做完" | **延迟 / 服务时间** |
| **可伸缩性（scalability）** | 增加资源（CPU）时**吞吐增长多少** | **吞吐随核数的增长曲线** |

> 本书的核心提醒：**"更快"与"更多"常常互相冲突**。
> 追求单任务最快往往要串行化；追求吞吐则要并行化 + 牺牲单任务延迟。

**三个层次的目标**（本书 pp.252）：更短的响应时间 / 更高的吞吐 / 更好的资源利用率。

## 三、Amdahl 定律（pp.253-256）

```
                        1
加速比 = ────────────────────────
            F + (1 - F) / N
```

| 符号 | 含义 |
| --- | --- |
| `F` | 程序中**必须串行**的比例 |
| `N` | 处理器数量 |

| `F` | `N = 8` | `N = 16` | `N → ∞` 的上限 |
| --- | --- | --- | --- |
| 0（全并行） | 8.0× | 16.0× | ∞ |
| 0.05 | 5.9× | 9.2× | **20×** |
| 0.10 | 4.7× | 6.7× | **10×** |
| 0.25 | 2.9× | 3.4× | **4×** |
| 0.50 | 1.8× | 1.9× | **2×** |

> **本书 pp.254 的震撼结论**：即使只有 **5%** 的串行部分，
> 加速比上限也只有 **20 倍**；10% 就只剩 10 倍。
> 所以**优化的重点永远是"找出并消除串行部分"**，而不是"加更多线程"。

**串行部分的常见来源**：

| 来源 | 例子 |
| --- | --- |
| 全局锁（一把锁保护所有状态） | 老式同步容器 |
| 单线程阶段 | 串行 I/O、串行解析 |
| 串行的数据结构更新 | 单一计数器（见"热点域"） |
| 不可并行的算法 | 顺序依赖的递推 |

> **扩展**：异构多核下的 Amdahl（Hill & Marty 2008）见
> [concepts/Amdahl定律与可伸缩性.md](concepts/Amdahl定律与可伸缩性.md)。

## 四、线程引入的开销（pp.256-262）

| 开销 | 说明 | 数量级 |
| --- | --- | --- |
| **① 上下文切换** | 保存/恢复寄存器、内核态切换、**TLB 与缓存失效** | 数千~数万周期 |
| **② 内存同步** | `volatile` 写、锁的获取/释放会触发**内存屏障**与缓存行失效 | 见《Java并发编程之美》volatile 篇（x86 上写约 20-100 周期） |
| **③ 阻塞** | 线程挂起/唤醒（两次上下文切换）+ 等待 | 最贵 |

> **本书的关键观察（pp.257）**：**上下文切换的开销不是"纯浪费"**——
> 新线程会带来**缓存冷启动**，切换回来时缓存已被污染。
> 这就是为什么"线程数远超核数"会让吞吐**下降**。

### 4.1 阻塞的代价：锁竞争 vs 无竞争

| 情形 | 代价 |
| --- | --- |
| **无竞争的 `synchronized`** | JDK 6+ 已优化（偏向/轻量锁），**极廉价**（JEP 374 后偏向锁移除，但轻量锁仍在） |
| **有竞争的锁** | **一次阻塞 = 两次上下文切换** |
| `volatile` 读 | x86 上**几乎免费**（普通读） |
| `volatile` 写 | 需要 StoreLoad 屏障，较贵 |

## 五、减少锁竞争（pp.262-270）

> **本书的判断**：并发程序中，对可伸缩性**最主要**的威胁就是**独占方式的资源锁**。

### 5.1 四招（本书 pp.262-270）

| 招式 | 做法 | 效果 |
| --- | --- | --- |
| **① 缩小锁的范围（快进快出）** | 减少持锁时间 | 减少竞争**概率** |
| **② 减小锁的粒度（锁分解 lock splitting）** | 一把锁 → 多把锁（保护不同状态） | 不同状态互不阻塞 |
| **③ 锁分段（lock striping）** | 把一个大结构分成 N 段，每段一把锁 | **可伸缩的并发度提升到 N** |
| **④ 换掉独占锁** | 并发容器 / 读写锁 / 不可变对象 / 原子变量 | 彻底避免独占 |

### 5.2 锁分解（lock splitting）示例

```java
// 前：一把锁保护两个独立的状态
public class ServerStatus {
    @GuardedBy("this") public final Set<String> users;
    @GuardedBy("this") public final Set<String> queries;
    public synchronized void addUser(String u)    { users.add(u); }
    public synchronized void addQuery(String q)   { queries.add(q); }   // 与 addUser 互相阻塞
}
// 后：拆分两把锁 —— users 与 queries 完全独立，可并行
public class ServerStatus {
    @GuardedBy("users")   public final Set<String> users;
    @GuardedBy("queries") public final Set<String> queries;
    public void addUser(String u)  { synchronized (users)   { users.add(u); } }
    public void addQuery(String q) { synchronized (queries) { queries.add(q); } }
}
```

> **前提**：两个状态之间**没有不变性条件**需要跨它们维护（否则要同一把锁，见第 4 章）。

### 5.3 锁分段（lock striping）示例

```java
// 本书 pp.267：分段的散列表
public class StripedMap {
    private static final int N_LOCKS = 16;
    private final Node[] buckets;
    private final Object[] locks;            // 每 N_LOCKS 个桶共享一把锁
    public Object get(Object key) {
        int hash = hash(key);
        synchronized (locks[hash % N_LOCKS]) { /* 只锁这一段 */ }
    }
}
```

| 效果 | 说明 |
| --- | --- |
| 并发度 | 从 1 提升到 **N_LOCKS** |
| 代价 | 需要为"整个结构"的操作（如 `size()`）**锁住所有段** |
| **历史** | **JDK 5/6 的 `ConcurrentHashMap` 正是这么做**（16 段）；**JDK 8 已改为 CAS + 桶头 synchronized**，段数从 16 变成"**等于桶数**"，粒度再降一个数量级 |

> 详见 [../Java并发编程之美/concepts/ConcurrentHashMap演进.md](../Java并发编程之美/concepts/ConcurrentHashMap演进.md)。

### 5.4 避免"热点域"（Hot Field，pp.268-270）

> **本书 pp.268 明确点名**：`AtomicLong` 计数器和 `size()` 这类"单一的热点域"
> 会**成为可伸缩性的瓶颈**，即使它本身是"无锁"的。

| 热点域 | 问题 | 解法 |
| --- | --- | --- |
| `AtomicLong hits` | 所有线程 CAS 同一缓存行 | **`LongAdder`**（分段累加） |
| `ConcurrentHashMap.size()` | 遍历所有计数单元 | 缓存一个估计值 / 用 `mappingCount()` |
| 单一 `volatile` 状态字段 | 写者互相失效缓存行 | 分片 + `@Contended` |

```java
// 本书时代（JDK 5/6）：只能自己分段或用 AtomicLong（慢）
// JDK 8+：直接用 LongAdder
private final LongAdder hits = new LongAdder();
hits.increment();            // 高争用下比 AtomicLong 快一个数量级
long total = hits.sum();     // 注意：非原子快照
```

> 原理与代价见 [../Java并发编程之美/concepts/LongAdder与分段累加.md](../Java并发编程之美/concepts/LongAdder与分段累加.md)
> 与 [../Java并发编程之美/concepts/伪共享FalseSharing.md](../Java并发编程之美/concepts/伪共享FalseSharing.md)。

### 5.5 一些替代独占锁的方法（pp.269）

| 方法 | 适用 |
| --- | --- |
| **并发容器**（`ConcurrentHashMap`） | 替代同步容器 |
| **读-写锁**（`ReentrantReadWriteLock`） | 读多写少 |
| **不可变对象** | 彻底不需要锁 |
| **原子变量** | 单一变量的原子更新 |

### 5.6 **向对象池说"不"**（pp.270）

> **本书的结论**：**对象分配的成本远低于同步的成本**。
> 用对象池（尤其早期的做法）会引入同步开销与生命周期管理问题，**得不偿失**。

| 时代 | 结论 |
| --- | --- |
| 2000s（本书） | 对象分配已经很廉价；**不要为了"省分配"而池化** |
| 2020s | 分配更廉价（TLAB、逃逸分析、标量替换、分代 GC）；**更不该池化** |
| **例外** | **创建成本极高**或**持有稀缺资源**的对象（线程、连接、`ByteBuffer`）——这类仍要池 |

> **JDK 21 的延伸**：虚拟线程非常廉价 → **连线程都不该池化**（见第 8 章）。
> 但**数据库连接、HTTP 连接池**依然必要（因为瓶颈在下游）。

## 六、如何度量（pp.270-272）

### 6.1 CPU 利用率的"三档判据"（本书 pp.270）

| 观察到的 CPU 利用率 | 说明 | 对策 |
| --- | --- | --- |
| **远低于 100%** | 有阻塞（I/O、锁、外部依赖） | 找阻塞点 |
| **接近 100% 但吞吐上不去** | 锁竞争 / 上下文切换过多 | 减少锁竞争 |
| **100% 且吞吐随核数线性增长** | 健康 | — |

> **本书提醒**：不要把"CPU 打满"当成好事——
> 在高争用下，CPU 被**自旋和上下文切换**吃掉了，实际有用工作很少。

### 6.2 现代工具

| 工具 | 用途 |
| --- | --- |
| **JMH** | **微基准**（本书第 12 章详述）；不要用 `System.nanoTime()` 手写循环 |
| **JFR** | `JavaMonitorEnter`（锁等待）、`ThreadPark`、GC、分配 |
| **async-profiler** | 火焰图；`--alloc`、`--lock` 模式 |
| **`perf` / `perf c2c`** | 缓存行争用、伪共享 |
| **JOL** | 对象布局与填充 |
| **`ThreadMXBean.getThreadCpuTime()`** | 测 W/C 比率（第 8 章池大小公式） |

## 七、JDK 5 → 25 的演进

| 本书论断 | 2020s 的状态 |
| --- | --- |
| "`synchronized` 慢" | 早已不慢（JDK 6 优化）；**偏向锁在 JDK 15（JEP 374）被默认禁用并移除** |
| "减少锁竞争是第一要务" | 依然成立 |
| 锁分段（自己实现） | `ConcurrentHashMap` 已在 JDK 8 做得更好；不需要自己写 |
| `AtomicLong` 热点 | **`LongAdder`**（JDK 8） |
| 对象池不划算 | **更不划算**；但**虚拟线程不该池化**这一条是新的 |
| Amdahl 定律 | 依然成立；**异构多核下要用 Hill-Marty 修正**（见专篇） |
| 上下文切换昂贵 | **虚拟线程把切换成本降到用户态**，I/O 密集场景的"线程数天花板"被抬高几个数量级 |

## 九、近年研究与工业界前沿

### 近年研究

- **可伸缩性定律的扩展**：USL（Gunther）近年被广泛用于容量规划；研究界继续讨论"NUMA 与缓存一致性导致的超线性/次线性伸缩"。
- **锁消除与无锁化**：近年 JIT 与运行时在**锁粗化/锁消除/偏向消除**上持续演进；无锁数据结构（LCRQ、环形队列）在多生产者场景超越传统锁。
- **伪共享的自动检测与修复**：SHERIFF（OOPSLA'11）之后，近年转向低开销在线检测 + NUMA 感知布局（见伪共享篇）。
- **虚拟线程的可伸缩性实测**：近年的工业报告一致显示——**I/O 密集吞吐显著提升，CPU 密集无收益**，这与 Amdahl 定律完全一致（I/O 密集的"串行部分"被虚拟线程消除，CPU 密集的没有）。

### 工业界开源实现

| 项目 | Stars | 与本章关系 |
| --- | --- | --- |
| **openjdk/jmh** | — | **微基准的唯一正确工具**；内置 `@State`、`@Group`、`Blackhole` 防死代码消除 |
| **async-profiler** | — | `-e lock` 直接量化锁等待；火焰图定位热点 |
| **JCTools/JCTools** | 3.9k | 专用队列（SPSC/MPSC/MPMC）替代通用阻塞队列以消除竞争 |
| **LMAX-Exchange/disruptor** | 18.5k | 无分配环形缓冲；把"锁竞争"彻底移除的极端案例 |
| **ben-manes/caffeine** | 17.9k | 缓存的高可伸缩实现（对比"自己用 ConcurrentHashMap + 一把锁"） |
| **openjdk/jdk** | 23.4k | `LongAdder`、`StampedLock`、`ConcurrentHashMap`（JDK 8 重写） |

## 十、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "线程越多吞吐越高" | Amdahl + 上下文切换；超过核数后 CPU 密集任务**变慢** |
| 2 | "`AtomicLong` 是无锁的，所以可伸缩" | 单一热点域 → **所有线程 CAS 同一缓存行**；用 `LongAdder` |
| 3 | "对象池能提升性能" | 通常**更慢**（引入同步）；只有"创建极贵/资源稀缺"的才池化 |
| 4 | "CPU 打满 = 性能好" | 可能是**自旋/切换**在烧 CPU；要看有用吞吐 |
| 5 | "锁分段越多越好" | 段数有代价（内存 + 全结构操作要锁所有段）；JDK 8 的 CHM 直接改成了桶级粒度 |
| 6 | "微基准用 `System.currentTimeMillis()` 跑个循环就行" | 会被 JIT 优化掉、没有预热、受 GC 干扰；**必须用 JMH** |
| 7 | "锁分解随便拆" | 如果两个状态之间有**不变性条件**，拆了会破坏正确性（第 4 章） |
| 8 | "`volatile` 一定比锁快" | `volatile` 写有 StoreLoad 屏障；且它**不能**替代锁的原子性 |
| 9 | "Amdahl 定律只关心 `F`" | 还要关心**一致性开销**（USL）与 NUMA |
| 10 | "虚拟线程提升所有性能" | 只提升**阻塞 I/O 密集**的吞吐；CPU 密集仍受 Amdahl 限制 |
