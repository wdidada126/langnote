# 第 7 章 取消与关闭（原书 pp.165-186）

> 本章的主题一句话：**"如何安全、快速、可靠地停止一个正在做的事？"**
> Java 的答案不是 `Thread.stop()`（早已废弃），而是**协作式中断**。
> 2020s 的补充：**结构化并发把"取消"从手工协议升级为作用域级的语言机制。**

## 一、本章地图

```
为什么不能用"取消标志"（阻塞操作永远检查不到）
        ↓
中断：协作式机制；中断策略；响应中断的两条正确做法
        ↓
通过 Future 取消；处理"不可中断的阻塞"
        ↓
停止基于线程的服务：shutdown / 毒丸 / shutdownNow 的局限
        ↓
处理非正常终止：UncaughtExceptionHandler
        ↓
JVM 关闭：关闭钩子、守护线程、终结器（已废弃）
```

## 二、取消标志的局限（pp.165-167）

```java
@NotThreadSafe
public class PrimeGenerator implements Runnable {
    @GuardedBy("this") private final List<BigInteger> primes = new ArrayList<>();
    private volatile boolean cancelled;     // 取消标志
    public void run() {
        BigInteger p = BigInteger.ONE;
        while (!cancelled) {
            p = p.nextProbablePrime();
            synchronized (this) { primes.add(p); }
        }
    }
    public void cancel() { cancelled = true; }
}
```

**缺陷**：如果循环里有**阻塞操作**（`BlockingQueue.take()`、`Thread.sleep()`、I/O），
`cancelled` 永远不会再被检查 → **取消失效**。

> **结论**：`volatile` 标志只能用于**纯粹计算型**的循环；
> 涉及阻塞就必须用**中断**。

## 三、中断（pp.167-177）

| 方法 | 语义 |
| --- | --- |
| `thread.interrupt()` | 请求中断（**设置中断标志**；若线程正在阻塞则抛 `InterruptedException` 并**清除标志**） |
| `Thread.isInterrupted()` | 查询标志（**不清除**） |
| `Thread.interrupted()` | 查询并**清除**（静态方法，作用于当前线程） |

**中断是协作式的**：它**不会**强行杀掉线程，只是"请求"；被中断的线程自己决定怎么响应。

### 3.1 响应中断的两条正确做法

```java
// ① 传递（propagate）—— 最优：让上层策略决定
public void run() {
    try { while (!Thread.currentThread().isInterrupted()) { doWork(); } }
    catch (InterruptedException e) { /* 清理 */ throw e; }  // 或声明抛出
}

// ② 恢复中断状态（restore）—— 不能抛时（如实现 Runnable.run()）
public void run() {
    try { doWork(); }
    catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // ★ 必须恢复，否则上层永远不知道
    }
}
```

> ❌ **绝对不要**：`catch (InterruptedException e) { /* 什么都不做 */ }`
> 这是最隐蔽的一类 bug——**取消请求被静默吞掉**。

### 3.2 中断策略（本书 pp.171）

> **每个线程都应该有明确的中断策略**：收到中断时该做什么（取消任务、清理、退出）。
> **但只有任务的所有者才能中断线程**——不要随便中断别人的线程。

**线程池的策略**：`shutdownNow()` 中断池中所有线程；
`Future.cancel(true)` 只中断**执行该任务的那个线程**（且只在任务还"属于"该 Future 时）。

### 3.3 通过 `Future` 取消（pp.172）

```java
Future<?> f = executor.submit(task);
f.cancel(true);              // mayInterruptIfRunning = true → 中断执行线程
```

| `cancel` 结果 | 条件 |
| --- | --- |
| 成功 | 任务尚未开始，或虽已开始但被中断 |
| 失败 | 任务已完成 / 已取消 / 无法取消（`mayInterruptIfRunning=false` 且任务正在跑） |

> **注意**：`cancel(true)` 只对**响应中断**的任务有效；
> 不响应中断的任务会跑完，只是 `get()` 会抛 `CancellationException`。

### 3.4 不可中断的阻塞（pp.173-176）

| 阻塞类型 | 是否响应中断 | 可替代方案 |
| --- | --- | --- |
| `Thread.sleep()`、`Object.wait()`、`BlockingQueue.put/take` | ✅ | — |
| `Lock.lockInterruptibly()` | ✅ | — |
| **`synchronized` 等待获取锁** | ❌ | 用 `ReentrantLock.lockInterruptibly()` |
| **阻塞式 I/O（`InputStream.read`、老式 `Socket`）** | ❌ | 用 **NIO `SocketChannel`/`InterruptibleChannel`**（关闭通道会导致阻塞线程抛 `AsynchronousCloseException`） |
| `Selector.select()` | 部分 | `select(timeout)` 或 `wakeup()` |
| `ReentrantLock.lock()`（普通版） | ❌ | `lockInterruptibly()` |

> **本书的关键提醒**：**"看起来能取消"不等于"真的能取消"**。
> 必须为每种阻塞操作准备一个可中断的替代路径。

### 3.5 用 `newTaskFor` 封装非标准取消（pp.176）

```java
// 通过自定义 Future 把"非标准的取消"（如关闭 socket）接入 cancel()
public class CancellableTask<T> implements Callable<T> {
    public T call() { ... }
    public void cancel() { socket.close(); }   // 自定义取消动作
}
// ThreadPoolExecutor.newTaskFor(Callable) → 返回自定义 RunnableFuture
```

## 四、停止基于线程的服务（pp.177-183）

### 4.1 关闭 `ExecutorService`

```java
executor.shutdown();                                  // 平缓
if (!executor.awaitTermination(10, TimeUnit.SECONDS)) // 等
    executor.shutdownNow();                           // 超时则强制
```

| 方法 | 语义 | 局限 |
| --- | --- | --- |
| `shutdown()` | 不再接收，已提交跑完 | 慢任务会拖很久 |
| `shutdownNow()` | 中断正在执行的 + 返回未执行的 | **只中断，不保证停**；**不返回正在执行的任务**（这是最大的局限） |

> **`shutdownNow()` 的局限性**（本书 pp.181 明确列出）：
> 你拿不到"正在执行但没停下来"的任务列表，因此**无法知道哪些工作丢失了**。
> 需要可靠的"全部记账"时，要自己维护未完成任务集合 + `try/finally` 里移除。

### 4.2 毒丸（Poison Pill）对象（pp.182）

```java
// 用于"生产者-消费者 + 队列"的服务：放一个特殊对象表示"结束"
private static final File POISON = new File("");
// 生产者：queue.put(POISON);
// 消费者：if (f == POISON) break;
```

| 适用 | 不适用 |
| --- | --- |
| 队列数量已知、生产者与消费者数量已知 | 多生产者/多消费者（需要 N_producers × N_consumers 个毒丸） |
| 只在**无界队列**上可靠 | **有界队列**上毒丸可能被 `put` 阻塞 |

## 五、处理非正常的线程终止（pp.183-185）

```java
Thread t = new Thread(r);
t.setUncaughtExceptionHandler((thread, ex) -> logger.error("...", ex));
Thread.setDefaultUncaughtExceptionHandler(handler);   // 全局兜底
```

| 要点 | 说明 |
| --- | --- |
| 只在**线程因未捕获异常而死**时触发 | 不替代 `try/catch` |
| 通过 `execute()` 提交的任务，异常会**被框架吞掉**（走 `afterExecute` 或 Future） | 通过 `submit()` 提交则异常封装在 `Future` 里，只有 `get()` 才抛出 |
| **`submit()` 的静默吞异常**是高频坑 | 要显式 `future.get()` 或用 `execute()` |

> **实践**：线程池里**永远用 `Future` 或显式 try/catch**；
> 用 `execute()` 时配 `UncaughtExceptionHandler`。

## 六、JVM 关闭（pp.185-186）

| 机制 | 说明 |
| --- | --- |
| **关闭钩子（Shutdown Hook）** | `Runtime.getRuntime().addShutdownHook(new Thread(...))`；**并发执行、顺序不定、必须快速完成** |
| **守护线程（Daemon）** | `setDaemon(true)`；JVM 退出时**不等待**守护线程，`finally` 也不会执行 |
| **终结器 `finalize()`** | ❌ **已废弃**（JEP 421, JDK 18: Deprecate Finalization for Removal）；替代是 **`Cleaner`**（JDK 9+）或 try-with-resources |

> **本书明确反对用 `finalize()` 释放资源** —— 20 年后这个反对已经写进 JDK 了。

## 七、JDK 5 → 25 的演进

| 本书论断 | 2020s 的状态 |
| --- | --- |
| "用中断实现取消" | 依然成立，但**结构化并发**提供了更上层的机制 |
| `Thread.stop()/suspend()/resume()` 废弃 | 早已废弃；**JDK 20 起 `Thread.stop()` 在所有情况下都抛 `UnsupportedOperationException`** |
| `finalize()` | **JEP 421（JDK 18）废弃待移除**；改用 `Cleaner` |
| 手工 `shutdown()` + `awaitTermination()` | **JDK 19+ `ExecutorService extends AutoCloseable`** → `try (var es = ...) {}`；`close()` 会等待已提交任务完成 |
| `Future.cancel(true)` | 仍是唯一标准手段；但结构化并发下 **`scope.shutdown()`** 会自动取消所有子任务 |
| 手工毒丸 | 虚拟线程 + `StructuredTaskScope` 场景下基本不需要 |
| `UncaughtExceptionHandler` | 仍在；虚拟线程也支持（JDK 21 `Thread.Builder.uncaughtExceptionHandler()`） |

```java
// JDK 21+：取消变成"作用域级"的
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<String> a = scope.fork(() -> callA());
    Subtask<String> b = scope.fork(() -> callB());
    scope.join().throwIfFailed();
    // a 若失败 → b 自动被取消
}   // 退出作用域时保证所有子任务已结束（成功/失败/取消）
```

> **对比**：本书时代的取消是"**你记得去 cancel 每一个 Future**"；
> 现在是"**离开作用域，一切自动结束**"。详见
> [../Java并发编程之美/concepts/结构化并发与ScopedValue.md](../Java并发编程之美/concepts/结构化并发与ScopedValue.md)
> 与 [concepts/中断与取消策略.md](concepts/中断与取消策略.md)。

## 九、近年研究与工业界前沿

### 近年研究

- **结构化取消（structured cancellation）**：近年共识是三条规则——取消**向下**传播、错误**向上**传播、取消是**协作式且幂等**的。Swift SE-0304、Kotlin 协程、JEP 453 都在收敛到同一套语义。
- **取消泄漏（cancellation leakage）研究**：近年对大型异步系统的实证研究发现，"忘记取消"导致的资源泄漏与"取消不及时"导致的性能问题是最常见的两类并发缺陷。
- **确定性取消测试**：FoundationDB 的确定性模拟器、CHESS 等工具把"不同取消时序"作为可枚举的测试维度。

### 工业界开源实现

| 项目 | Stars | 与本章关系 |
| --- | --- | --- |
| **openjdk/jdk** | 23.4k | `Thread.interrupt`、`StructuredTaskScope`、`Future.cancel` |
| **Kotlin/kotlinx.coroutines** | 13.8k | **结构化取消**的先驱：`coroutineScope` 取消父协程会自动取消所有子协程 |
| **tokio-rs/tokio** | 33.2k | `JoinHandle::abort()` + `CancellationToken`；Rust 的取消也是协作式 |
| Go `context.Context` | — | Go 的取消事实标准：`ctx.Done()` 通道 + `WithCancel/WithTimeout` |

> **跨语言对照**：Java 用**中断标志**，Go 用 **channel + context**，Kotlin/Trio 用**作用域**，
> Rust 用 **`CancellationToken` / `abort()`**——**全部是协作式的**，没有例外。

## 十、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "`volatile boolean cancelled` 能取消所有任务" | 遇到**阻塞操作**就永远检查不到；必须用中断 |
| 2 | "`interrupt()` 会立刻停掉线程" | 协作式：只设标志；阻塞方法抛 `InterruptedException` |
| 3 | "`catch (InterruptedException e) {}` 没问题" | **吞掉中断**是最隐蔽的 bug；至少恢复标志 |
| 4 | "`shutdownNow()` 能拿到所有没做完的任务" | 只返回**队列中未执行**的；**正在执行又停不下来的拿不到** |
| 5 | "`submit()` 的任务抛异常会被 `UncaughtExceptionHandler` 捕获" | 被封装进 `Future`；**只有 `get()` 才抛**（不 get 就静默丢失） |
| 6 | "`synchronized` 等待可被中断" | **不能**；用 `ReentrantLock.lockInterruptibly()` |
| 7 | "阻塞 I/O 可被中断" | 老式 `Socket`/`InputStream` 不能；用 NIO `InterruptibleChannel` |
| 8 | "`finalize()` 可以做兜底清理" | 已废弃（JEP 421）；用 `Cleaner` / try-with-resources |
| 9 | "关闭钩子可以慢慢跑" | **必须快速完成**；多个钩子**并发执行、顺序不定**；不能在其中做 `awaitTermination(永久)` |
| 10 | "取消是可选优化" | 不做取消 → 线程池关闭卡住、资源泄漏、JVM 不退出 |
