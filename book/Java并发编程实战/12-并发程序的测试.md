# 第 12 章 并发程序的测试（原书 pp.204-227）

> 配套概念专篇见 `concepts/`（本目录暂未单列，关键内容并入本章「近年研究」一节）。
> 版本基线：JDK 5/6 写作时代；测试工具链在 JDK 8+ 已全面现代化，但方法论（安全性/活跃性/性能三类测试）至今有效。

## 一、本章地图

| 小节 | 主题 | 关键产出 |
| --- | --- | --- |
| 12.1 | 正确性测试 | 安全性测试 `putTakeTest`、资源管理测试、回调测试、**人为制造更多交替**（`yield`/`sleep` 注入） |
| 12.2 | 性能测试 | 在正确性测试上加计时；多算法对比；响应性衡量 |
| 12.3 | 性能测试陷阱 | GC / 动态编译（无预热）/ 不真实采样 / 不真实竞争 / 死代码消除 —— 五类"假数据"来源 |
| 12.4 | 其他测试方法 | 代码审查、静态分析、AOP 插桩、分析监测工具 |

**三件必须测的事**：① 安全性（什么都不该出错）；② 活跃性（该发生的总会发生）；③ 性能（够快 + 可伸缩）。并发 bug 的恶魔在于——**它只在特定交错下出现**，单测绿了不代表对了。

## 二、核心精讲

### 2.1 安全性测试：用"不变量"当探针
- 经典例子 `PutTakeTest`：有界缓存 `BoundedBuffer`，用**多生产者多消费者**持续 `put/take`，周期性校验"缓冲区元素数 ∈ [0, capacity]"这一不变量。
- 单测无法穷举交错，所以用**大量线程 + 大量迭代 + 随机休眠**提高"撞上坏交错"的概率。
- 比单测更狠：**并发安全测试本质是统计测试**——跑得够久、交错够多，才能给"暂未发现 bug"一个置信度。

### 2.2 制造更多交替（12.1.6）
- 注入 `Thread.yield()` / `Thread.sleep(0)` / `LatencyGenerator` 让调度器更频繁切换，把"只在 rare 交错下出现"的 bug 放大成可复现。
- 现代替代：在测试里用**确定性调度器**（见 3.x 工业界）强制某条交错，这就从"概率撞"变成"必然撞"。

### 2.3 资源管理测试
- 验证"线程不会泄漏""池子不会耗尽""临时对象不会无限堆积"。
- 关键：跑完要让所有 worker 真正退出，否则**测试进程挂住 = 隐性泄漏**。

### 2.4 性能测试的五类陷阱（12.3，至今每一条都还在坑人）
1. **GC**：一次 Full GC 能把延迟拉高一个数量级 → 必须固定 GC、跑稳态、丢弃预热段。
2. **动态编译**：JIT 没预热时测的是解释执行 → **先 warmup 再计时**。
3. **不真实采样**：把计时代码本身放进热路径改变编译 → 用 JMH 的 `Blackhole` 消费结果。
4. **不真实竞争**：单线程压测看不出锁瓶颈 → 并发度要贴近真实。
5. **死代码消除**：返回值没被消费，JIT 直接整段删掉 → 用 `Blackhole.consume()` 或返回给调用方。

> 结论：**不要用 `System.nanoTime()` + for 循环自己写微基准**。JIT 会在你毫无察觉时把循环删光、把对象优化掉。JDK 8+ 的唯一正确工具是 **JMH**（OpenJDK 官方）。

## 三、版本演进

- 写作时（2006）性能测试靠手写 `System.currentTimeMillis()`；JDK 8 引入 **JMH**（源自 Oracle 内部 `microbench`，后捐给 OpenJDK），成为工业标准。
- JDK 9 `jlink` + `jfr`（JDK Flight Recorder 开源）→ 性能/活跃性观测从"外部猜测"变"内核级采集"。
- JDK 21 虚拟线程让"线程泄漏"测试的意义下降，但让"**调度器是否公平、结构化并发是否真关闭**"成为新的测试重点。

## 四、经典论文 / 原始文献

- **Arikan, "Testing Concurrent Programs" / 本书第 12 章**——工业界"安全性+活跃性+性能"三分法的源头性表述。
- **Burnim & Sen, "Asserting and Checking Determinism for Multithreaded Programs" (ICSE 2009)**——用确定性调度做并发测试的早期系统（与 12.1.6 "制造交替" 思想一脉）。
- **Olson et al., "Maple: A Coverage-Driven Testing Tool for Multithreaded Programs" (ISSTA 2009)**——交错覆盖驱动的测试。
- **JMH 官方样例仓库 `openjdk/jmh`** —— 微基准的权威参考实现。

## 五、近年研究与工业界前沿

### 5.1 把"概率撞 bug"变成"必然撞 bug"
- **确定性调度 / 记录回放**：
  - `rr` (Mozilla, 7.9k★)——Linux 下给任意多线程 C/C++/Rust 程序录屏回放，复现竞态。
  - `time-travel-debugging` 思路进入 Java：通过字节码插桩强制交错。
- **并发模糊测试（Concurrency Fuzzing）**：
  - .NET 的 **`Microsoft/Coyote`**（2.7k★）——用系统化的"调度探索"找出死锁/活锁/竞态，并给出确定性复现。思想可直接迁移到 Java 任务编排。
  - Java 生态：**`vmlens` / `concunit`** 等商用/开源工具做 @Atomic / @Threaded 注解式交错测试。

### 5.2 静态分析与数据竞争检测
- **`google/error-prone`** + **`@ThreadSafe`/`@NotThreadSafe`** 注解（源自本书 Goetz 本人的 JSR-305 思路）→ 编译期把关。
- **SpotBugs + `find-sec-bugs`** 的并发规则：**`DC_DOUBLECHECK`**（DCL 坏写法）、`UG_SYNC_SET` 等直接对应本章与第 16 章。
- **ThreadSanitizer（C/C++）** 的思路在 JVM 层由 **`jucier`** 与 OpenJDK 的 **`×intrinsic` race detector** 部分落地。

### 5.3 运行时观测（替代"打印时间戳"）
- **`async-profiler`**（11k★）——`-e lock` 直接量化锁等待比例；`-e cpu`/`alloc` 火焰图定位真正的瓶颈，完全绕开 12.3 五类陷阱。
- **JFR（JDK Flight Recorder）** + **`JDK Mission Control`**——生产环境低开销录屏，看"锁等待/线程阻塞/GC 停顿"三位一体。
- **`openjdk/jcstress`**（2.1k★）——**专门测 JMM 与内存可见性的并发模糊测试框架**，是验证第 16 章语义的工业级工具（见 16 章）。

### 5.4 测试并发设计的范式转移
- 虚拟线程 + 结构化并发（JEP 453/505）→ 测试重点从"我有没有正确关线程"转向"**作用域退出时任务是否真的全结束**"，JUnit 5 的 `Executable`/参数化测试配合 `StructuredTaskScope` 天然适配。

## 六、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "通过所有单测 = 并发正确" | 并发 bug 靠**交错**，单测几乎永远碰不到；必须做安全性/活跃性专项测试 |
| 2 | "自己写个计时循环测性能" | 必踩 12.3 五类陷阱；用 JMH |
| 3 | "跑一次没出错就 release" | 要跑**足够久 + 足够多交替**给置信度；或用确定性调度复现 |
| 4 | "注入 `sleep(0)` 越多越好" | 过度注入会让调度不自然、掩盖真实竞争；现代用确定性调度更干净 |
| 5 | "测试过 = 线上没问题" | 线上有 GC/CPU 争用/网络；JFR + 影子流量才能补完最后一块 |
| 6 | 书里推荐 `yield` 注入 | 现代已被 **Coyote / rr / jcstress** 的"确定性交错"取代，更可复现 |
