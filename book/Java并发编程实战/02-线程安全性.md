# 第 2 章 线程安全性（原书 pp.19-40）

> 本书给出的**"线程安全"定义**被引用了二十年，值得逐字记住。
> 本章只讲两件事：**原子性**（竞态条件）和**加锁**（`synchronized` 的互斥 + 可见性）。
> 可见性的完整故事在第 3 章，JMM 的形式化在第 16 章。

## 一、本章地图

```
线程安全的定义（本书的原话）
        ↓
无状态对象 → 天然线程安全
        ↓
原子性：竞态条件的两种典型形态（check-then-act / read-modify-write）
        ↓
复合操作与"不变性条件（invariant）"
        ↓
加锁：synchronized 的两重语义（互斥 + 可见性）与"重入"
        ↓
用锁保护状态：每个共享可变变量都要由同一个锁保护
        ↓
活跃性与性能：别在锁里做慢操作
```

## 二、本书对"线程安全"的定义（pp.19）

> **一个类是线程安全的，当且仅当：**
> 多个线程访问它时，**不管运行时环境采用何种调度方式、线程如何交替执行**，
> 并且在**调用方代码中不需要任何额外的同步或协同**，
> 这个类都能表现出**正确的行为**。

三个关键限定词：

| 限定 | 含义 |
| --- | --- |
| **不管调度方式** | 不能依赖"恰好不会被打断" |
| **调用方不需要额外同步** | 不能把同步负担转嫁给使用者（客户端加锁是设计失败） |
| **正确的行为** | 需要有明确的**规约（specification）**与**不变性条件** |

> 这个定义与 **Herlihy & Wing 的线性化性（linearizability）** 是同一种直觉的工程表达：
> "并发执行看起来像某个合法的串行执行"。

## 三、无状态对象一定线程安全

```java
// 无状态：没有字段，也就没有共享状态（典型如无状态 Servlet）
@ThreadSafe
public class StatelessFactorizer implements Servlet {
    public void service(ServletRequest req, ServletResponse resp) {
        BigInteger i = extractFromRequest(req);        // 局部变量（栈封闭，见第 3 章）
        BigInteger[] factors = factor(i);
        encodeIntoResponse(resp, factors);
    }
}
```

- 局部变量存在**线程栈**上，天然不共享（第 3 章的"栈封闭"）；
- **瞬时状态只存在于局部变量** → 无状态 → 线程安全。

> **这是最重要的设计原则**：能无状态就不要有状态；能不可变就不要可变。

## 四、原子性与竞态条件（pp.21-27）

### 4.1 两类典型竞态条件

| 类型 | 模式 | 例子 |
| --- | --- | --- |
| **check-then-act** | 先检查一个可能为失效的结果，再据此行动 | `if (!set.contains(x)) set.add(x);` |
| **read-modify-write** | 基于对象之前的状态来定义下一状态 | `count++`、`lazyInit` |

```java
// ① check-then-act：懒初始化的竞态（可能 new 两次）
private ExpensiveObject instance;
public ExpensiveObject getInstance() {
    if (instance == null) instance = new ExpensiveObject();   // 竞态！
    return instance;
}

// ② read-modify-write：计数器的竞态（可能丢更新）
private long count;
public long getCount() { return count++; }   // 读-改-写三步
```

### 4.2 为什么"原子"不够

```java
// 即使 count 是 AtomicLong，下面仍然不是原子的（两个独立操作之间的窗口）
if (counter.get() < LIMIT) {         // check
    counter.incrementAndGet();       // act
}
```

> **"原子变量 + 复合操作"依然是竞态**。正确做法是把复合操作整体同步，
> 或用 `AtomicLong` 的 CAS 循环 / `LongAccumulator`（见第 15 章）。

### 4.3 非原子的 64 位操作（pp.29，也是本仓库原笔记提到的点）

**JLS §17.7** 明确允许：对**非 `volatile` 的 `long`/`double`** 的一次读写，
可以被当作**两个独立的 32 位写**。

| 情形 | 结果 |
| --- | --- |
| 32 位 JVM + 非 `volatile long` | **可能撕裂**：高 32 位与低 32 位来自不同写入 |
| 64 位 JVM（现代主流） | 硬件层面通常是原子的，但**规范不保证** |
| **`volatile long` / `volatile double`** | **规范要求原子**（JDK 5 起） |

> **实践结论**：在多线程间共享的 `long`/`double` 计数器，**要么用 `volatile`，要么用 `AtomicLong`**。
> 更推荐后者（还带原子自增）。

## 五、加锁机制（pp.27-36）

### 5.1 `synchronized` 的两重语义

```java
synchronized (lock) {
    // ① 互斥：同一时刻只有一个线程能进入（保护不变性条件）
    // ② 可见性：退出时把修改刷新到主存；进入时能看到之前的修改（第 3 章展开）
}
```

| 形式 | 锁对象 |
| --- | --- |
| `synchronized` 实例方法 | `this` |
| `synchronized` 静态方法 | `Class` 对象 |
| `synchronized (obj) { }` | `obj`（推荐用**私有 final 对象**） |

```java
private final Object lock = new Object();   // 私有锁，防止外部代码也来锁它（避免死锁与干扰）
public void f() { synchronized (lock) { ... } }
```

### 5.2 重入（Reentrancy）

**内置锁是可重入的**：线程可以再次获取自己已持有的锁（计数器 +1）。

```java
public class Widget {
    public synchronized void doSomething() { ... }
}
public class LoggingWidget extends Widget {
    public synchronized void doSomething() {
        System.out.println(toString());   // 需要锁
        super.doSomething();              // 再次获取 this 的锁 —— 若不可重入则会死锁
    }
}
```

> 重入意味着锁的粒度是**线程**而非"调用"。JVM 用"每锁一个 owner 线程 + 计数器"实现
> （对象头 Mark Word → 偏向锁/轻量锁/重量锁，详见《Java并发编程的艺术》）。

### 5.3 用锁保护状态（pp.31）

> **核心规则**：**每个共享的可变变量，都必须由同一个锁来保护。**
> 维护不变性条件涉及的**所有**变量，必须由**同一个**锁保护。

```java
// 错误：两个变量由两个不同的锁保护，但它们共同维护一个不变性条件
private long lower, upper;   // 不变性：lower <= upper
// 正确：同一个锁保护 two variables
```

### 5.4 活跃性与性能（pp.34-36）

| 建议 | 说明 |
| --- | --- |
| **缩小同步块** | 只在真正需要互斥的部分加锁 |
| **不在锁内做慢操作** | I/O、网络、阻塞式 `BlockingQueue.take()`、长循环 → 严重损害吞吐 |
| **不要过度拆分** | 过度拆分会增加获取/释放次数，也可能破坏原子性；需要**度量**（第 11 章） |

```java
// 反例：把整个 service 都同步，Servlet 退化为串行
public synchronized void service(...) { ...slow I/O... }
// 正解：只同步共享状态那一小段
```

## 六、JDK 5 → 25 的演进

| 本书论断（2006） | 2020s 的状态 |
| --- | --- |
| `synchronized` 是"重量级"操作 | **JDK 6 起**有偏向锁/轻量锁/自适应自旋，低争用下极廉价；**JDK 15 (JEP 374) 起偏向锁被默认禁用并逐步移除**（现代负载下撤销成本 > 收益） |
| 用 `ReentrantLock` 追求性能 | JDK 6 之后 `synchronized` 与 `ReentrantLock` 性能**接近**；`ReentrantLock` 的价值转向**可中断/可定时/公平性/多 Condition**（第 13 章） |
| 锁是 JVM 内置的唯一选择 | JUC 的 `ReentrantLock`/`StampedLock`/`Semaphore` 都基于 **AQS**（第 14 章 + 《Java并发编程之美》AQS 篇） |
| `synchronized` 阻塞 OS 线程 | **JDK 21-23：虚拟线程在 `synchronized` 里阻塞会钉住（pin）载体线程**；**JDK 24 (JEP 491) 修复** |

> **虚拟线程时代的实践建议**：JDK 21-23 上，把长时间阻塞的 `synchronized`
> 换成 `ReentrantLock`（不 pin）；JDK 24 起不必再替换。

## 八、近年研究与工业界前沿

### 近年研究

- **数据竞争的定义与检测**：近年共识是把"是否有 data race"与"是否 linearizable"分开——**无 race 不等于正确**（如本书 `AtomicLong` + check-then-act 的例子）。
- **自动化的原子性违规检测**：把"复合操作应原子"做成静态/动态分析（如 *Atomizer*、*Velodrome*、*RaceMob* 一类的研究；近年转向基于采样与学习的检测器）。
- **锁的自动优化**：偏向锁退场（JEP 374）之后，HotSpot 转向更保守的自适应自旋；近年研究在"何时该自旋而非阻塞"上继续。

## 九、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "线程安全就是给每个方法加 `synchronized`" | 还要保证**不变性条件**涉及的所有变量由**同一把锁**保护 |
| 2 | "`i++` 是原子的" | 三步（读-改-写），必须同步或用原子类 |
| 3 | "用了 `ConcurrentHashMap` 就线程安全了" | 容器本身安全，**复合操作**（`contains` + `add`）仍不安全（见第 4/5 章） |
| 4 | "`AtomicLong` 能保证复合逻辑原子" | 只能保证**单个**操作原子；check-then-act 要 CAS 循环或加锁 |
| 5 | "`synchronized` 很慢" | JDK 6 后已大幅优化；**先度量再优化**（第 11 章） |
| 6 | "`long`/`double` 读写是原子的" | **规范允许撕裂**（JLS 17.7）；共享的 64 位变量要 `volatile` 或原子类 |
| 7 | "重入只是个冷知识" | 没有它，`super.doSomething()` 的经典写法会**直接死锁** |
| 8 | "锁可以随便换对象" | 保护同一状态的锁必须始终一致；用**私有 final 对象**最安全 |
| 9 | "同步块越小越好" | 过度拆分会破坏原子性并增加获取/释放开销；要**度量** |
| 10 | "虚拟线程下 `synchronized` 没问题" | **JDK 21-23 会 pin 载体线程**；JDK 24（JEP 491）才修复 |
