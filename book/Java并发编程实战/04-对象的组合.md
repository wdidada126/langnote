# 第 4 章 对象的组合（原书 pp.71-98）

> **本书最"设计"的一章**，也是 JCiP 区别于其他并发书的核心价值。
> 前面几章讲"什么是线程安全"，本章讲**"怎么构造出一个线程安全的类"**：
> **实例封闭 → 委托 → 扩展既有类 → 文档化**。
> 本仓库原笔记对「实例封闭机制」有专门的长篇记录，本篇做了结构化整理。

## 一、本章地图

```
① 收集同步需求：状态空间 / 不变性条件 / 后验条件 / 先验条件
        ↓
② 实例封闭（Instance Confinement）+ Java 监视器模式
        ↓
③ 线程安全性的委托（Delegation）—— 以及委托何时失效
        ↓
④ 给现有线程安全类"加功能"的四种方式（含为什么不推荐继承与客户端加锁）
        ↓
⑤ 把同步策略写进文档（@GuardedBy 等，见 concepts/线程安全文档化与注解.md）
```

## 二、设计线程安全类的三个步骤（pp.71-78）

| 步骤 | 问题 | 产出 |
| --- | --- | --- |
| ① **收集同步需求** | 哪些状态是共享可变的？ | 状态空间 |
| ② **找出不变性条件** | 哪些状态组合是合法的？ | 不变性（invariant） |
| ③ **规定后验/先验条件** | 操作执行后/执行前必须满足什么？ | 状态的合法性检查 |

```java
// 例子：一个计数器
@ThreadSafe
public class Counter {
    @GuardedBy("this") private long value = 0;
    // 状态空间：value ∈ [0, Long.MAX_VALUE]
    // 不变性：value >= 0
    // 后验条件：getNext() 返回后，value 增加了 1
    public synchronized long getNext() { return value++; }
}
```

### 2.1 依赖状态的操作（state-dependent）

有些操作有**先验条件**（如"队列非空才能 `take()`"）。
本书在此留了个伏笔 → **第 14 章**讲如何自己实现这种"状态依赖的管理"：

```java
// 阻塞直到条件满足（正确的实现要用条件队列，第 14 章）
while (!conditionHolds()) wait();
```

> **不要用忙等待**（`while (!ready) Thread.yield()`）——浪费 CPU 且不保证可见性。

### 2.2 状态的所有权（Ownership）

- 状态的所有者决定**加锁协议**；
- 如果状态被**发布**出去（返回引用、存入外部容器），所有权就不再独占 → **委托失效**。

## 三、实例封闭（Instance Confinement，pp.78-85）

> **把数据封装在对象内部，把对数据的访问限制在对象的方法上，
> 从而更容易确保线程在访问数据时总能持有正确的锁。**

### 3.1 Java 监视器模式（Java Monitor Pattern）

```java
@ThreadSafe
public class PrivateLock {
    private final Object myLock = new Object();   // ← 私有锁
    @GuardedBy("myLock") private Widget widget;
    void someMethod() {
        synchronized (myLock) { /* 访问或修改 widget */ }
    }
}
```

| 变体 | 锁对象 | 何时用 |
| --- | --- | --- |
| **Java 监视器模式** | `this`（`synchronized` 方法） | 简单、默认 |
| **私有锁对象** | `private final Object lock` | **推荐**：防止外部代码拿到同一把锁干扰/死锁 |
| **私有锁 + 客户端可见的状态** | 同上 | 需要发布状态时要返回**副本**（见下） |

### 3.2 经典反例：`VehicleTracker` 与"返回可变状态"

```java
// 危险：把可变的 Point 直接返回 → 调用方可以绕过锁修改它
@NotThreadSafe
public class MutableTracker {
    @GuardedBy("this") private final Map<String, Point> locations;
    public synchronized Map<String, Point> getLocations() {
        return locations;                       // ← 逸出！外部能改
    }
    public synchronized Point getLocation(String id) {
        return locations.get(id);               // ← 同样逸出
    }
}
```

**两种正解**：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **① 返回深拷贝（defensive copy）** | `return new HashMap<>(locations);` 且 `Point` 也拷 | 拷贝开销 |
| **② 让 `Point` 不可变** | `public class Point { public final int x, y; }` | **最优**：不可变对象可以随意发布（见第 3 章 final 字段语义） |

> **本书的结论**：**"不可变 + 返回引用" 优于 "可变 + 返回拷贝"**。
> JDK 16 的 `record` 让这一条几乎没有成本：
> `public record Point(int x, int y) { }`

### 3.3 监视器模式的理论来源

| 概念 | 出处 |
| --- | --- |
| **Monitor（管程）** | **Hoare, C. A. R. 1974. "Monitors: An Operating System Structuring Concept." CACM 17(10): 549-557.**；Brinch Hansen 1973《Operating System Principles》 |
| Java 的实现 | 每个对象一个 monitor；`synchronized` + `wait/notify`（**Mesa 语义**，见第 14 章） |

## 四、线程安全性的委托（Delegation，pp.85-92）

### 4.1 委托给单个线程安全状态变量

```java
@ThreadSafe
public class DelegatingCounter {
    private final AtomicLong count = new AtomicLong(0);   // 委托给 AtomicLong
    public long getCount() { return count.get(); }
    public void inc() { count.incrementAndGet(); }
}
```

### 4.2 委托给多个**互相独立**的状态变量

```java
@ThreadSafe
public class DelegatingTracker {   // 两个状态各自安全，且彼此独立 → 组合仍安全
    private final ConcurrentMap<String, Point> locations;
    private final Map<String, Point> unmodifiableMap;
    public DelegatingTracker(Map<String, Point> points) {
        locations = new ConcurrentHashMap<>(points);
        unmodifiableMap = Collections.unmodifiableMap(locations);
    }
    public Map<String, Point> getLocations() { return unmodifiableMap; }   // 只读视图，安全
    public Point getLocation(String id) { return locations.get(id); }      // Point 不可变 → 安全
    public void setLocation(String id, int x, int y) { locations.put(id, new Point(x, y)); }
}
```

### 4.3 **委托失效**的三种情形（最易踩坑）

| # | 情形 | 例子 | 后果 |
| --- | --- | --- | --- |
| ① | **多个状态变量之间有不变性条件** | `NumberRange`：`lower <= upper` 由两个 `AtomicInteger` 分别维护 | 分别原子 ≠ 组合原子 → **可能违反不变性** |
| ② | **底层状态被发布出去** | 把内部的 `ConcurrentHashMap` 直接返回 | 调用方可绕过你的协议 |
| ③ | **委托给非线程安全的状态** | 内部用 `HashMap` | 显然失效 |

```java
// 反例：委托失效（pp.88）
public class NumberRange {
    private final AtomicInteger lower = new AtomicInteger(0);
    private final AtomicInteger upper = new AtomicInteger(0);
    public void setLower(int i) {
        if (i > upper.get()) throw new IllegalArgumentException();  // check
        lower.set(i);                                               // act —— 竞态！
    }
    // 正确做法：用同一个锁保护 lower 与 upper
}
```

> **判据**：**只要不变性条件跨越多个变量，委托就失效，必须加锁。**

## 五、给现有线程安全类添加功能（pp.92-96）

四种方式，**本书明确推荐第 ④ 种**：

| # | 方式 | 评价 |
| --- | --- | --- |
| ① | **修改原始类的源码** | ✅ 最优（能理解并统一同步策略），但常常做不到（第三方库） |
| ② | **扩展（继承）** | ⚠️ **脆弱**：同步策略被分散到基类与子类；基类一旦换锁，子类**静默失效** |
| ③ | **客户端加锁（client-side locking）** | ⚠️ **更脆弱**：必须**恰好用原类内部使用的那个锁**，否则完全无效 |
| ④ | **组合（composition）** | ✅ **推荐**：把对象封装进自己的类，用自己的锁保护 |

### 5.1 客户端加锁的正确与错误写法

```java
// ❌ 错误：锁的是新建的 List，而 synchronizedList 用的是它自己的 mutex
List<E> list = Collections.synchronizedList(new ArrayList<>());
synchronized (list) { if (!list.contains(x)) list.add(x); }   // 取决于实现：JDK 的 synchronizedList 确实锁 wrapper…但这是实现细节

// ✅ 正确姿势：按文档使用"wrapper 对象本身"作为锁（JDK 文档明确说明），
//    但本书建议干脆别这么写 —— 用组合
@ThreadSafe
public class ImprovedList<T> implements List<T> {
    private final List<T> list;
    public ImprovedList(List<T> list) { this.list = list; }
    public synchronized boolean putIfAbsent(T x) {          // ← 自己的锁
        if (list.contains(x)) return false;
        list.add(x); return true;
    }
    // ... 其余方法委托
}
```

> `Vector` 的复合操作（"若没有则添加"）必须**锁 `Vector` 实例本身**（它的同步用 `this`），
> 这就是"客户端加锁"的经典场景 —— 但**依赖实现细节**，所以本书建议用组合。

## 六、将同步策略文档化（pp.96-98）

```java
@ThreadSafe
public class Counter {
    @GuardedBy("this") private long value;    // ← 明确写出"由哪个锁保护"
}
```

| 注解 | 含义 |
| --- | --- |
| `@ThreadSafe` | 可以安全地被多线程使用 |
| `@NotThreadSafe` | **默认**；需要外部同步 |
| `@Immutable` | 不可变，天然安全 |
| `@GuardedBy("lock")` | 由 `lock` 这个锁保护（可以是 `this`、字段名、`Class.class`） |

> 完整说明与 `javax.annotation.concurrent` 包的现状，见
> [concepts/线程安全文档化与注解.md](concepts/线程安全文档化与注解.md)。

**面向两类读者**：

| 读者 | 需要知道 |
| --- | --- |
| **维护者** | 哪个锁保护哪个字段，避免以后改坏 |
| **使用者** | 是否需要外部同步；哪些方法是原子的 |

## 七、JDK 5 → 25 的演进

| 本书论断 | 2020s 的修正 |
| --- | --- |
| "返回防御性拷贝" | **JDK 16 `record` / 不可变优先**：不可变就不用拷贝，也没有拷贝成本 |
| "给 `synchronizedList` 客户端加锁" | 现在直接用 **`ConcurrentHashMap.computeIfAbsent`** / `CopyOnWriteArrayList` / `ConcurrentLinkedQueue`，不必客户端加锁 |
| "委托给 `ConcurrentHashMap`" | JDK 8 重写后连 `computeIfAbsent`/`merge` 都能原子化复合操作（见 [../Java并发编程之美/concepts/ConcurrentHashMap演进.md](../Java并发编程之美/concepts/ConcurrentHashMap演进.md)） |
| "手写 `putIfAbsent`" | `ConcurrentMap` 已内置 `putIfAbsent` / `computeIfAbsent` / `merge`；**但注意 JDK 8 的 `computeIfAbsent` 递归更新问题（JDK 9+ 抛 IllegalStateException）** |
| "不可变类要手写" | `record`（JDK 16）+ `List.of()`（JDK 9）+ 密封接口（JDK 17） |
| "同步容器（Vector/Hashtable）" | 基本**不应再用**；仅遗留代码 |

## 九、近年研究与工业界前沿

### 近年研究

- **把线程安全写进类型系统**：Rust 的 `Send`/`Sync` 把本书"文档化"升级为**编译期强制**；近年研究（如 RustBelt、Proving Rust）致力于证明标准库 `unsafe` 的封装真的安全。
- **并发对象的模块化验证**：近年（如 Iris、Viper 一类的分离逻辑框架）能证明"两个独立的线性化对象组合后仍线性化"——正是本章 4.2 委托规则的形式化。
- **不变式与不可变数据结构**：持久化数据结构（HAMT）让"不可变"在性能上变得可行，从而简化本章几乎所有问题。

### 工业界开源实现

| 项目 | Stars | 与本章关系 |
| --- | --- | --- |
| **ben-manes/caffeine** | 17.9k | 把"线程安全的缓存"做成开箱即用的库（W-TinyLFU）；**比自己组合 ConcurrentHashMap 更正确** |
| **google/guava** | 51.9k | `ImmutableList`/`ImmutableMap`（不可变集合的工业标准）、`ForwardingList`（**组合模式**的现成抽象基类） |
| **openjdk/jdk** | 23.4k | `java.util.ImmutableCollections`（JDK 9+）、`record`（JDK 16）、`ConcurrentHashMap.computeIfAbsent` |
| Rust 标准库 | — | `Send`/`Sync`：把本章"文档化"变成编译器检查 |

> **实践建议**：能用 Guava/Java 9+ 的**不可变集合** + **ConcurrentHashMap/Caffeine** 时，
> 就不要自己用 `synchronized` 组合一个容器——本书这一章的价值在于**理解取舍**，
> 而不是让你手写每一个组合。

## 十、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "每个字段都用 `AtomicXxx` 就线程安全" | **跨字段的不变性条件**会让委托失效（4.3 ①） |
| 2 | "返回 `Collections.unmodifiableMap` 就万无一失" | 只是**包装**视图，底层被改它也会变；要彻底不可变用 `Map.copyOf`（JDK 10+）/ Guava `ImmutableMap` |
| 3 | "客户端加锁很方便" | 依赖原类的**实现细节**（锁对象），是最脆弱的方案 |
| 4 | "继承一个线程安全类并加同步方法即可" | 同步策略分散到两个类，基类改锁就静默失效 |
| 5 | "`Vector`/`Hashtable` 是线程安全的，放心用" | 单个方法安全，**迭代与复合操作仍要加锁**；且性能差（第 5 章） |
| 6 | "防御性拷贝总是必须的" | **优先让状态不可变**，`record` 时代几乎零成本 |
| 7 | "`putIfAbsent` 是原子的，所以 lazy init 没问题" | 如果初始化函数本身**耗时长**，会阻塞同一 bin；推荐 `ConcurrentHashMap` + `FutureTask`/`CompletableFuture`（第 5 章 memoizer） |
| 8 | "线程安全是类的属性" | 更是**协作协议**：谁拥有状态、谁负责加锁、如何发布 —— 必须写进文档 |
