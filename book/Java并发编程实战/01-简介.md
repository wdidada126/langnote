# 第 1 章 简介（原书 pp.1-18）

> 本章回答两个问题：**为什么要并发？** 以及 **并发会带来什么风险？**
> 成书于 2006 年，正是"摩尔定律靠频率提升"终结、**多核成为主流**的转折点。
> 20 年后再看，本章的**动机论述比当年更有说服力**，但"线程"这个载体已经换了形态。

## 一、一句话概括

并发的动机从"**更好地利用多处理器**"和"**更自然地建模**"，
代价是三种风险：**安全性（正确性）、活跃性（能否推进）、性能**。

## 二、并发简史（本书 1.1）

| 年代 | 驱动力 | 形态 |
| --- | --- | --- |
| 1950s-60s | 分时、I/O 重叠 | 进程 + 中断 |
| 1970s-80s | 多处理器、数据库 | 进程间通信、事务 |
| 1990s | GUI、网络服务器 | **线程**成为主流抽象 |
| **2000s（本书成书时）** | **频率墙 → 多核** | 线程 + `java.util.concurrent`（JSR 166, 2004） |
| **2010s** | 云、C10K | 事件驱动、异步 I/O、reactor |
| **2020s** | 核数暴涨 + I/O 密集 | **虚拟线程 / 协程**（JDK 21, Go, Kotlin） |

> **关键转折**：2005 年前后单核频率停止增长（功耗墙），
> 性能提升全部转向**更多核**。这就是为什么"并发"从"可选优化"变成"必备技能"。

## 三、线程的四个优势（本书 1.2）

| 优势 | 说明 | 2020s 的现状 |
| --- | --- | --- |
| ① **发挥多处理器的能力** | 单线程程序最多用满一个核 | 仍然是核心动机（Amdahl 定律见第 11 章） |
| ② **建模的简单性** | 一个任务一个线程，比状态机直观 | 仍是；且虚拟线程让这个优势**成本更低** |
| ③ **异步事件的简化处理** | 每个请求一个线程，阻塞式 I/O 代码简单 | 变强了：虚拟线程让"一请求一线程"重新可行 |
| ④ **响应更灵敏的 UI** | 后台线程做重活，UI 线程不卡 | 见第 9 章；移动端/Swing 仍适用 |

## 四、线程的三个风险（本书 1.3）

```
安全性（Safety）："永远不会发生糟糕的事情"      → 竞态条件、数据竞争
活跃性（Liveness）："某件正确的事情最终会发生"   → 死锁、饥饿、活锁
性能（Performance）："正确的事情要尽快发生"     → 上下文切换、锁竞争、内存同步开销
```

### 4.1 安全性：一个能跑出错误结果的例子

```java
// 典型的 check-then-act 竞态条件（本书 1.3 / 第 2 章详述）
public class UnsafeSequence {
    private int value;
    public int getNext() { return value++; }   // 三个动作：读、加、写
}
```

`value++` 不是原子的 → 两个线程可能拿到同一个值。

### 4.2 活跃性：死锁的最小例子

```java
// 锁顺序死锁：A→B 与 B→A（第 10 章详述）
synchronized (left)  { synchronized (right) { ... } }   // 线程 1
synchronized (right) { synchronized (left)  { ... } }   // 线程 2
```

### 4.3 性能：上下文切换与内存同步

- 上下文切换：保存/恢复寄存器、TLB 与缓存失效，约 **数千到上万周期**；
- `volatile` / 锁的写会让其他核的缓存行失效（见《Java并发编程之美》的伪共享篇）；
- 过度同步会把并行度压回 1。

## 五、"线程无处不在"（本书 1.4）—— 最容易被忽略的一节

**即使你不主动创建线程，框架也会替你创建**：

| 场景 | 谁创建了线程 | 你要注意什么 |
| --- | --- | --- |
| Servlet / Spring MVC | 容器为每个请求分配线程 | **Servlet/Controller 必须是线程安全的**（通常是无状态的） |
| 定时任务（`@Scheduled`、Quartz） | 调度器线程池 | 任务之间可能并发（或串行，看配置） |
| JMX / RMI | 远程调用线程 | 被管理的 MBean 要线程安全 |
| Swing / JavaFX | EDT / Application Thread | 见第 9 章 |
| 日志框架 | 异步 appender 线程 | 日志对象要线程安全 |
| JDBC 连接池 | 连接是复用的 | `Connection` 不能跨线程共享 |

> **结论**：写任何会被框架调用的代码时，都默认"它可能被多线程同时调用"。

## 六、JDK 5 → 25：本章论断的更新

| 本书论断 | 2020s 的修正 |
| --- | --- |
| "线程是稀缺资源，创建线程开销大" | **虚拟线程下不再稀缺**（JEP 444）：一个 JVM 可承载百万级 |
| "一请求一线程在 C10K 下不可行" | 虚拟线程让它重新可行（Go 早已证明） |
| "`Thread` 直接对应 OS 线程" | JDK 21 起有**两层**：虚拟线程 → 载体线程（平台线程） |
| "上下文切换几千周期" | 虚拟线程切换是**用户态**的，只有载体线程切换才贵 |
| "线程默认栈 512KB-1MB" | 虚拟线程栈**按需增长、可收缩**，初始仅几百字节 |

> 但**风险三条不变**：虚拟线程下竞态、死锁、性能问题**一个都没少**。
> 甚至因为并发数暴涨，**资源耗尽型问题（连接池、信号量）更容易出现**。

## 八、近年研究与工业界前沿

### 近年研究

- **"暗硅（Dark Silicon）"与功耗墙**：2010s 的研究指出，受功耗限制芯片上大部分区域无法同时全速运行——这比本书时代更强化了"必须并发且必须省电"。
- **异构计算（GPU/TPU/NPU）**：并发从"多核 CPU"扩展到"主机 + 加速器"，数据并行模型（CUDA/OpenCL/SYCL）成为第二条主线。
- **虚拟线程的可伸缩性研究**：近年工业报告（如 Oracle、Netflix、Spring 团队）系统评测了虚拟线程在真实服务上的吞吐/延迟表现，结论是**I/O 密集场景吞吐显著提升，CPU 密集场景无收益**。

### 工业界开源实现

| 项目 | Stars | 与本章关系 |

## 九、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "并发是性能优化手段" | 首要目的是**正确性与建模**；性能是次要且需要度量的（第 11 章） |
| 2 | "我不写多线程代码就不用管并发" | **框架会替你创建线程**（Servlet、定时任务、回调） |
| 3 | "多核时代单线程代码没意义了" | 单线程代码在 GUI、脚本、大量业务服务里仍是主流；并发是**手段**不是目的 |
| 4 | "虚拟线程解决了并发的所有问题" | 只解决"线程昂贵"这一个问题；**竞态/死锁/资源耗尽照旧** |
| 5 | "线程越多越快" | 超过核数后 CPU 密集任务只会因切换变慢（Amdahl + 切换开销） |
| 6 | "线程安全就是加 `synchronized`" | 那是**互斥**；线程安全还包括**可见性**（第 3 章）与**设计策略**（第 4 章） |
| 7 | "安全性、活跃性、性能是三个独立问题" | 它们**互相拉扯**：提高安全性的同步会降低性能并引入死锁风险 |
