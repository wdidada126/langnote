> 对应《Java并发编程实战》附录 A 与第 4 章"在文档中说明线程安全性"。这是把"我心里知道它线程安全"变成"编译器/审查者/同事也能验证"的桥梁。

## 二、核心精讲

### 2.1 为什么需要线程安全注解
- 并发 bug 的根因之一是：**调用方不知道一个方法是否要求外部加锁**。注解把隐含契约显式化。
- 四类核心注解（源自本书 + JSR-305）：
  - `@ThreadSafe`：类自行保证并发安全，调用方无需加锁。
  - `@Immutable`：状态不可变（所有字段 `final`、且引用对象也不可变）→ 天然线程安全。
  - `@NotThreadSafe`：明确"不安全"，禁止无保护共享（警告后来者）。
  - `@GuardedBy("lock")`：字段/方法**必须在指定锁的保护下访问**，否则被视为 bug。

### 2.2 JSR-305 的尴尬现实
- JSR-305（2006）**从未正式发布 GA**，规范停滞，但 `javax.annotation.concurrent.*` 注解被**事实标准**采用。
- 风险：不同库自带不同包名的 `@GuardedBy`，类型系统不互通 → 用 **SpotBugs 的 `edu.umd.cs.findbugs.annotations`** 或 **error-prone** 统一。

### 2.3 工业工具链如何消费注解
- **`google/error-prone`**（6.9k★）+ **`NullAway`**：编译期查空指针与并发误用；配合 `@GuardedBy` 风格的自定义检查。
- **`spotbugs/spotbugs`**（3.8k★）+ **`find-sec-bugs`**：并发规则 `DC_DOUBLECHECK`（DCL）、`UG_SYNC_SET`（未同步集合）、`JLM`（锁误用）直接对应本书第 16/13 章。
- **`@CheckReturnValue`（Error Prone / JSR 305）**：`Executor.execute` 返回 void 但 `submit` 返回 `Future`——若忽略 `Future` 即吞掉异常，注解能强制 caller 处理。

### 2.4 跨语言对照
- **Rust**：`Send`（可跨线程转移所有权）+ `Sync`（可跨线程共享引用）是**类型系统级**的线程安全契约——编译器在编译期拒绝"把 `Rc`（`!Send`）传给线程"。这是本书"在文档里说明线程安全"主张的**终极形态**：从文档变成类型。
- **C++ (Clang ThreadSanitizer)**：`GUARDED_BY(mu)` 宏 → TSan 运行时检测"未在 `mu` 保护下访问字段"。
- **Swift / Kotlin**：`@ThreadSafe` 思路被 `Sendable` 协议（Swift 5.5+）/ `kotlinx.coroutines` 的 `@DelicateCoroutinesApi` 继承。

## 三、版本演进

- **2006 JSR-305**：定义 `javax.annotation.concurrent` 与 `jsr305` 包，停滞但未死。
- **2013+**：Google `error-prone`、Square `NullAway`、SpotBugs（FindBugs 继任）把注解变成**可执行的契约**。
- **2019 Swift `Sendable`**：把线程安全契约送进类型系统。
- **2023+ 结构化并发**：`StructuredTaskScope` 让"作用域内任务"的线程安全由**作用域**保证，部分替代"逐方法标注 `@ThreadSafe`"。

## 六、常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "加了 `@ThreadSafe` 就真安全" | 注解是**文档**，不强制；要靠工具消费才有用 |
| 2 | "注解越多越好" | `@GuardedBy` 标错锁比不标更危险 |
| 3 | "JSR-305 官方包最权威" | 它从未 GA；用统一的库（error-prone/SpotBugs） |
| 4 | "线程安全靠评审口述" | 用 `Sendable`/`Send`/`Sync` 这类**类型级**契约才是终点 |
