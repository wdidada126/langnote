# 概念专篇：中断与取消策略

> 对应《Java并发编程实战》第 7 章"取消与关闭"。把"怎么优雅让一个任务停下来"讲透，并接入虚拟线程 / 结构化并发的现代替代。

## 一、本章地图（专篇结构）

| 主题 | 内容 |
| --- | --- |
| 取消的协作本质 | Java 没有"强制杀线程"，只能**请求**取消（协作式） |
| `interrupt` 机制 | 设置中断标志 + 唤醒 `wait`/`sleep`/`join`；`InterruptedException` 必须处理 |
| 取消策略契约 | 任务如何响应中断、清理、向上传播 |
| 关闭 `ExecutorService` | `shutdown()`（温和）/ `shutdownNow()`（尝试中断）/ 配合 `awaitTermination` |
| 现代替代 | 虚拟线程 + `StructuredTaskScope` 的作用域级取消（JEP 453/505） |

## 二、核心精讲

### 2.1 协作式取消（没有"kill -9"）
- `Thread.stop()`/`suspend()`/`resume()` **已废弃**：强制停会留下**对象处于不一致状态**（锁已释放但没写完）→ 数据损坏。
- 正确做法：**设置取消标志**，任务在合适的取消点主动检查并退出。

### 2.2 `interrupt` 是 Java 的"取消信号"
- 调 `thread.interrupt()`：① 设置中断标志；② 若线程在 `wait/sleep/join`/可中断的 `lock` 上阻塞，**抛出 `InterruptedException`** 并**清除标志**。
- **`InterruptedException` 处理的两条正路**：
  1. 自己就是顶层任务 → **抛出**（让上层知道被取消）；
  2. 不能抛（实现 `Runnable.run`）→ **重新 `interrupt()`**（恢复标志，别吞掉），或保存"已取消"状态后清理退出。
- **最经典错误**：catch 了 `InterruptedException` 却既不处理也不 `reInterrupt` → 中断信号**丢失**，任务永远停不下来。

### 2.3 `ExecutorService` 的关闭
- `shutdown()`：拒绝新任务，等已提交任务跑完（温和）。
- `shutdownNow()`：拒绝新任务 + **尝试中断所有运行中的任务**（通过 `interrupt`，非强制），返回未开始的任务列表。
- 必须 `awaitTermination(timeout)` 等待，否则"关闭"只是发起，进程可能挂住。
- `Future.cancel(true)`：对 `FutureTask` 实际就是 `interrupt` 底层线程。

### 2.4 不可中断的阻塞
- **同步 I/O（`Socket`/`InputStream`）**：`interrupt` 无效，只能**关底层资源**（关闭 socket → 读抛异常）或设超时。
- **同步 `NIO`**：`InterruptibleChannel` 会响应中断（抛 `ClosedByInterruptException`）。
- **`synchronized` 阻塞**：**不响应中断**！要可中断得用 `ReentrantLock.lockInterruptibly()`（见 13 章）。

### 2.5 现代替代：结构化并发
- 虚拟线程 + `StructuredTaskScope`（JEP 453/505）：任务在**作用域**内运行，作用域关闭时**自动取消并等待所有子任务**——"取消"从"手动调 interrupt + 自己清理"变成"作用域退出即全清"。
- 配合 `ShutdownOnFailure`/`ShutdownOnSuccess` 策略：任一子任务失败或第一个成功即整体取消，天然实现第 7 章的"取消策略"。
- 见 `concepts/结构化并发与ScopedValue.md`（《Java并发编程之美》目录）。

## 三、版本演进

- **JDK 1.0**：`stop`/`suspend` 早期存在，后证明危险而废弃。
- **JDK 5**：`ExecutorService.shutdownNow` + `Future.cancel` 标准化协作取消。
- **JDK 8**：`CompletableFuture` 的 `cancel` 仍是 interrupt 风格（但很多异步回调不检查）。
- **JDK 21–25**：`StructuredTaskScope`（JEP 453 预览 → JEP 505 二次预览 → JDK 25 目标 GA）把取消变成结构化、作用域级、自动传播。

## 四、经典论文 / 原始文献

- **Goetz, "Java Concurrency in Practice" 第 7 章**——取消策略的工业权威论述。
- **Dijkstra, "Cooperating Sequential Processes" (1965)** / **"GOTO Statement Considered Harmful" (CACM 1968)**——"结构化"思想源头：取消/控制流应受作用域约束。
- **JEP 453/505 Structured Concurrency**——现代作用域取消规范。
- **Lamport, "Time, Clocks..." (1978)**——中断/事件序的形式化背景。

## 六、常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "catch `InterruptedException` 空着就行" | 必须 reInterrupt 或向上传播，否则信号丢失 |
| 2 | "调用 `stop()` 立刻停" | 已废弃且危险（破坏不变性）；用 interrupt |
| 3 | "interrupt 能打断 `synchronized`" | `synchronized` 不响应中断；用 `lockInterruptibly` |
| 4 | "interrupt 能打断 socket 读" | 同步 I/O 不响应；要关 socket/用 NIO |
| 5 | "新代码手写 interrupt 取消" | 虚拟线程 + `StructuredTaskScope` 作用域取消更稳 |
