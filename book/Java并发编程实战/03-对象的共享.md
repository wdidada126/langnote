# 第 3 章 对象的共享（原书 pp.41-70）

> 本章是全书**最容易学完就以为懂了、但一到生产就出事**的一章。
> 它讲的不是"加锁"，而是**可见性**——即"一个线程写了，另一个线程**什么时候**能看到"。
> 核心四件套：**可见性 / 发布与逸出 / 线程封闭 / 不变性与安全发布**。
>
> 形式化的规则在第 16 章；硬件层（内存屏障、x86 屏障代价）见
> [../Java并发编程之美/concepts/volatile与内存可见性.md](../Java并发编程之美/concepts/volatile与内存可见性.md)。

## 一、本章地图

```
可见性：失效数据（stale data）与非原子的 64 位操作
        ↓
加锁与 volatile：两条保证可见性的路径
        ↓
发布（Publishing）与逸出（Escape）：this 逸出是构造函数里的定时炸弹
        ↓
线程封闭：Ad-hoc / 栈封闭 / ThreadLocal（含 C++ pthread TSD 对照）
        ↓
不变性（final 字段）+ 初始化安全性
        ↓
安全发布的五种模式与"事实不可变"
```

## 二、可见性（pp.41-47）

```java
public class NoVisibility {
    private static boolean ready;      // 非 volatile
    private static int number;
    private static class ReaderThread extends Thread {
        public void run() {
            while (!ready) Thread.yield();   // ① 可能永远看不到 ready=true
            System.out.println(number);      // ② 可能打印 0
        }
    }
    public static void main(String[] args) {
        new ReaderThread().start();
        number = 42; ready = true;
    }
}
```

**两种失败**：① 读线程永远看不见 `ready`（甚至被优化成死循环）；② **重排序**导致先看到 `ready=true` 却看到 `number=0`。

### 2.1 失效数据与"最低安全性"

- **失效数据**：读到的是旧值；
- **最低安全性（out-of-thin-air safety）**：读到的值至少是**某个线程曾经写过的值**，不会凭空出现
  （**例外**：非 `volatile` 的 `long`/`double` 撕裂，见第 2 章与 JLS §17.7）。

## 三、加锁与 `volatile`（pp.47-52）

### 3.1 加锁不只是互斥，还保证可见性

> **A 线程在同步块里做的所有修改，对随后进入**同一个锁**的同步块的线程 B 可见。**
> 这正是"A 释放锁 happens-before B 获取同一把锁"（第 16 章的监视器锁规则）。

**所以：`synchronized` 能同时解决原子性与可见性；`volatile` 只能解决可见性与禁止重排序。**

### 3.2 `volatile` 的正确用法

| 可以做 | 不能做 |
| --- | --- |
| 状态标志（`volatile boolean shutdownRequested`） | 计数器（`count++` 非原子） |
| 一次性安全发布（配合不变对象） | 依赖其他变量的不变性条件（`lower <= upper`） |
| 独立的观察变量（温度、开关） | 复合操作（`if (!flag) set()`） |

> **本书的判据（pp.49）**：写 `volatile` 变量时，**不要依赖它当前的值**，
> 且它不参与其他变量的不变性条件 → 才可以用 `volatile` 代替锁。

## 四、发布与逸出（pp.52-57）

**发布（publish）**：让对象能在当前作用域之外被使用（返回引用、存到静态字段、传给外部方法、注册监听器）。
**逸出（escape）**：发布了**不该发布**的对象。

### 4.1 `this` 逸出（构造函数里的定时炸弹）

```java
public class ThisEscape {
    public ThisEscape(EventSource source) {
        source.registerListener(new EventListener() {
            public void onEvent(Event e) { doSomething(e); }
        });                     // ← 内部类持有外部 this，对象还没构造完就发布出去了
        // ... 更多初始化
    }
}
```

**其他常见逸出形式**：

| 形式 | 风险 |
| --- | --- |
| 构造函数里 `start()` 一个线程 | 新线程可能在构造完成前就开始读状态 |
| 构造函数里调用**可覆写的**方法（非 `final`/`private`） | 子类覆写后可能发布 `this` |
| 把 `this` 传给一个静态方法或外部对象 | 同上 |

**正解：私有构造函数 + 静态工厂**

```java
public class SafeListener {
    private final EventListener listener;
    private SafeListener() { listener = e -> doSomething(e); }
    public static SafeListener newInstance(EventSource source) {
        SafeListener safe = new SafeListener();     // ① 先构造完
        source.registerListener(safe.listener);     // ② 再发布
        return safe;
    }
}
```

## 五、线程封闭（pp.57-63）

> **不使用共享，就不会有共享的问题。** 本仓库原笔记对这一节记录最详细。

| 方式 | 机制 | 强度 | 说明 |
| --- | --- | --- | --- |
| **① Ad-hoc 线程封闭** | 靠程序员约定，"这个对象只由某线程访问" | ⚠️ **最弱** | 脆弱：没有语言/框架保证，维护者容易破坏；本书建议**尽量少用** |
| **② 栈封闭** | 局部变量只在方法内使用 | ✅ **强** | 天然安全；**唯一风险是把引用发布出去**（如返回、存入共享结构） |
| **③ `ThreadLocal` 封闭** | 每线程一份副本 | ✅ **强** | 最常用；但有**内存泄漏**与**线程池复用**两个坑 |

### 5.1 栈封闭

```java
public int loadTheArk(Collection<Animal> candidates) {
    SortedSet<Animal> animals;                 // 局部变量 → 封闭在该线程的栈上
    int numPairs = 0;
    animals = new TreeSet<>(new SpeciesGenderComparator());
    animals.addAll(candidates);                // 只要不把 animals 发布出去，就绝对安全
    return numPairs;
}
```

### 5.2 `ThreadLocal` 的两个坑

| 坑 | 说明 | 对策 |
| --- | --- | --- |
| **内存泄漏** | `ThreadLocalMap` 的 key 是**弱引用**，value 是**强引用** → key 被回收后变成 `(null, value)`，value 永不释放（**线程池里线程不死，泄漏就是永久的**） | 在 `finally` 里 `remove()`；详见 [../Java并发编程之美/concepts/ThreadLocal与内存泄漏.md](../Java并发编程之美/concepts/ThreadLocal与内存泄漏.md) |
| **线程池复用导致串数据** | 线程复用时 `ThreadLocal` 没有清理 → 下一个任务读到上一个任务的值 | 同上，务必 `remove()` |

> **JDK 21+ 的现代替代**：**`ScopedValue`**（JEP 506，JDK 25 转正）——
> 有明确作用域、不可变、自动清理，**天然没有泄漏问题**。
> 详见 [../Java并发编程之美/concepts/结构化并发与ScopedValue.md](../Java并发编程之美/concepts/结构化并发与ScopedValue.md)。

### 5.3 跨语言对照：`ThreadLocal` 在 C++ 里的样子

本仓库原笔记里有一个完整的 `pthread` 实现，这里给出对照表：

| 语言 | 机制 |
| --- | --- |
| Java | `ThreadLocal<T>`（JDK 5 泛型化）；JDK 21+ 可用 `ScopedValue` |
| C++11 | **`thread_local`** 关键字（语言级，最简洁） |
| POSIX C | `pthread_key_create` / `pthread_setspecific` / `pthread_getspecific`（**TSD**）+ 需手工 `pthread_key_delete` |
| Rust | `thread_local!` 宏（配合 `RefCell`） |
| Go | 无官方 TLS（语言刻意不支持，鼓励显式传参） |
| Python | `threading.local()` |

```cpp
// C++11 版本（比 pthread 版本简洁得多，且自动析构）
#include <thread>
thread_local int data = 0;   // 每线程一份，线程结束时自动销毁
void f() { ++data; }
```

> **对照要点**：C++ 的 `thread_local` 在**线程结束时自动析构**，
> 而 Java 的 `ThreadLocal` 在线程池里**不会**自动清理——这就是泄漏问题的根源。

## 六、不变性（pp.63-67）

> **不可变对象一定是线程安全的。**

不可变对象的三个条件（本书 pp.63）：

1. 对象创建后**状态不可修改**；
2. **所有字段都是 `final`**；
3. 对象**创建期间 `this` 没有逸出**。

### 6.1 `final` 字段的"初始化安全性"（第 16 章展开）

**JMM 给 `final` 字段的特殊保证**：正确构造的不可变对象，
即使**没有同步**地被发布，任何线程看到的 `final` 字段都是构造时写入的值
（不会看到默认值 `null`/`0`）。

```java
// 安全：即使 holder 本身没用 volatile 发布，value 也不会读到默认值
public class Holder { private final int value; public Holder(int v){ value = v; } }
```

> **这条保证是 JSR 133（JDK 5）才确立的**——JDK 4 及之前没有。
> 见 [../Java并发编程之美/concepts/JMM与happens-before.md](../Java并发编程之美/concepts/JMM与happens-before.md)。

## 七、安全发布（pp.67-70）

### 7.1 五种安全发布模式

| # | 模式 | 机制 |
| --- | --- | --- |
| ① | **静态初始化器**中初始化对象引用 | JVM 的类初始化锁保证（`static` 字段的初始化 happens-before 任何使用） |
| ② | 引用保存到 **`volatile`** 字段或 `AtomicReference` | volatile 写-读的 happens-before |
| ③ | 引用保存到**正确构造对象的 `final` 字段** | final 字段语义 |
| ④ | 引用保存到**由锁保护的**字段 | 监视器锁规则 |
| ⑤ | 放进**并发容器**（`ConcurrentHashMap`、`BlockingQueue` 等） | 容器内部保证（put happens-before get） |

### 7.2 可变对象 vs 事实不可变对象

| 类别 | 定义 | 发布要求 |
| --- | --- | --- |
| **不可变对象** | 状态创建后永不改变 | 任意发布（有 final 字段语义兜底） |
| **事实不可变（effectively immutable）** | 技术上可变，但**发布后不再修改** | **必须安全发布** |
| **可变对象** | 发布后还会被修改 | **必须安全发布 + 每次访问都要同步** |

> `Date` 就是典型"技术上可变但你当它不变"的对象——
> 所以要**安全发布**（`volatile`），否则另一个线程可能读到"构造到一半"的 `Date`。

## 八、JDK 5 → 25 的演进

| 本书论断 | 2020s 的修正 |
| --- | --- |
| `ThreadLocal` 是线程封闭的主力 | JDK 25 起 **`ScopedValue` 转正**（JEP 506）：有作用域、不可变、自动清理；虚拟线程下**强烈推荐**替代 |
| 不可变类要手写 `final` 字段 | **JDK 16 `record`**：一行生成不可变类（全 `final` + 自动 equals/hashCode） |
| `volatile` 与锁是可见性的全部手段 | **JDK 9 `VarHandle`** 提供 5 档内存语义（plain / opaque / acquire-release / volatile），可按需降级省掉屏障开销 |
| 静态初始化是最简单的安全发布 | 依然成立；且 **JDK 9+ 的 `ImmutableCollections`**（`List.of()`、`Map.of()`）提供开箱即用的不可变容器 |
| `final` 字段语义已在 JDK 5 确立 | 仍是 JMM 的基石；**`record` 与密封类（JDK 17）让它更常用** |

## 十、近年研究与工业界前沿

### 近年研究

- **弱内存模型的普及**：ARM/Apple Silicon/RISC-V 都是弱内存模型，本书基于 x86-TSO 的很多"看起来安全"的直觉在 ARM 上会失效。近年研究大量集中在 **ARMv8 与 RISC-V 内存模型的形式化**（如 Pulte 等 POPL'18 的 "Simplifying ARM Concurrency"、 RISC-V 的 RVWMO）。
- **ScopedValue / 结构化并发**：把"线程封闭"从"线程级 + 手动 remove"提升为"**作用域级 + 自动清理**"，是本书这一节最直接的现代化。
- **不可变数据结构的性能**：持久化（persistent）数据结构（Clojure/OCaml 的 HAMT、Rust `im` crate）让"不可变"不再意味着"拷贝整个集合"。

### 工业界开源实现

## 十一、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "`volatile` 能替代锁" | 只保证**可见性**与禁止重排序；**不保证复合操作的原子性** |
| 2 | "没加 `volatile` 就一定会读到旧值" | 是"**不保证**能读到"，实际可能碰巧读到；**这类 bug 最难复现** |
| 3 | "`final` 字段就够了" | 还要保证**构造期间 `this` 不逸出** |
| 4 | "`ThreadLocal` 不会泄漏" | 线程池 + 弱 key/强 value → **永久泄漏**；必须 `remove()` 或用 `ScopedValue` |
| 5 | "局部变量一定安全" | 只要**不把引用发布出去**才安全（返回、存进共享容器都算发布） |
| 6 | "不可变对象在任何发布方式下都安全" | 有 `final` 字段语义兜底才成立；**没有 `final` 的"事实不可变"对象必须安全发布** |
| 7 | "`static` 字段天然线程安全" | 本仓库原笔记里有这句话——**不准确**。static 只影响**初始化**的可见性（类初始化锁），**之后的可变读写仍要同步** |
| 8 | "可见性问题只在多核上出现" | 单核上 JIT 也可能把读取提升到循环外（本书 `NoVisibility` 的例子） |
| 9 | "ARM 上和 x86 一样" | ARM 是弱内存模型；x86 上"看起来对"的代码在 ARM/Apple Silicon 上可能错（第 16 章） |
| 10 | "`ScopedValue` 只是 ThreadLocal 的换皮" | 它**不可变**且**有作用域**，虚拟线程下没有泄漏问题，语义更强 |
