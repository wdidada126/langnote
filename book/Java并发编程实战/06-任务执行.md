# 第 6 章 任务执行（原书 pp.135-164）

> 本章回答：**"如何把工作组织成任务，并把任务交给线程去执行？"**
> 核心结论只有一个：**不要自己管理线程，用 `Executor`。**
> 2020s 的补充是：**用 Executor，但线程本身换成了虚拟线程。**

## 一、本章地图

```
三种"执行任务"的方式：串行 / 每任务一线程 / Executor
        ↓
无限制创建线程的三个危险
        ↓
Executor 框架：接口、生命周期、线程池工厂
        ↓
延迟与周期任务：Timer 的三个缺陷 → ScheduledThreadPoolExecutor
        ↓
找出可利用的并发：页面渲染器三版演进（串行 → Future → CompletionService）
```

## 二、三种执行方式的对比（pp.136-143）

| 方式 | 吞吐 | 响应性 | 资源 | 问题 |
| --- | --- | --- | --- | --- |
| **① 串行执行** | 最差 | 最差（一个慢请求阻塞全部） | 最省 | 完全没利用多核 |
| **② 每任务一线程** | 好 | 好 | **差** | 见下 |
| **③ `Executor` + 线程池** | 好 | 好 | **好** | ✅ 推荐 |

```java
// ② 的天真写法 —— 本书明确不推荐
void bad(Runnable r) { new Thread(r).start(); }
```

### 2.1 无限制创建线程的三个危险（pp.138）

| # | 危险 | 说明 |
| --- | --- | --- |
| ① | **线程生命周期开销** | 创建/销毁不是免费的；请求率高时这个开销会变成主要成本 |
| ② | **资源消耗** | 每个线程默认栈 **512KB-1MB**（`-Xss`）；几千个线程就是 GB 级；还有内核数据结构 |
| ③ | **稳定性** | 线程数超过某个点后 **OOM**；不同平台的阈值差异很大 → 代码不可移植 |

> **20 年后唯一的改变**：虚拟线程把 ② 的成本降到近乎零，因此 ① ③ 也基本消失。
> 但**线程的"任务边界"设计原则不变**。

## 三、`Executor` 框架（pp.143-152）

```java
public interface Executor { void execute(Runnable command); }
```

**为什么是接口？** 因为它把**任务提交**与**执行策略**解耦：

| 执行策略维度 | 例子 |
| --- | --- |
| 在什么线程执行 | 主线程 / 池线程 / 虚拟线程 |
| 任务按什么顺序 | FIFO / LIFO / 优先级 |
| 多少任务并发 | 固定 / 弹性 / 无限制 |
| 多少任务排队 | 有界 / 无界 / 不排队（直接交付） |
| 如何拒绝 | 抛异常 / 调用者执行 / 丢弃 |
| 执行前后做什么 | 统计、日志、`ThreadLocal` 传递 |

### 3.1 线程池的四个工厂方法（及各自的坑）

| 工厂方法 | 实现 | 坑 |
| --- | --- | --- |
| `newFixedThreadPool(n)` | `core=max=n` + **`LinkedBlockingQueue`（无界）** | 队列永不拒绝 → `maximumPoolSize` 无效；任务堆积 → OOM |
| `newCachedThreadPool()` | `core=0, max=Integer.MAX_VALUE` + `SynchronousQueue` | 来一个任务开一个线程 → 高并发下线程爆炸 |
| `newSingleThreadExecutor()` | `core=max=1` + **无界队列** | 同第一个；且**单线程 → 易发生饥饿死锁**（第 8 章） |
| `newScheduledThreadPool(n)` | `ScheduledThreadPoolExecutor` | 相对安全 |

> **本书 pp.145 已经提示过无界队列的问题，但 2006 年的工程实践仍普遍用工厂方法。**
> **今天的结论更明确：生产环境不要使用 `Executors` 的工厂方法**
> （阿里 Java 开发手册、Sonar 规则 S2094 等均已列为强制项），
> 应显式 `new ThreadPoolExecutor(...)`。详见 [08-线程池的使用.md](08-线程池的使用.md)。

### 3.2 `ExecutorService` 的生命周期（pp.146-149）

```
  运行中 (RUNNING)
    │  shutdown()      → 不再接收新任务，队列任务继续跑完
    ▼
  关闭中 (SHUTDOWN)
    │  shutdownNow()   → 尝试中断正在执行的任务，返回队列中未执行的任务
    ▼
  已终止 (TERMINATED)
```

| 方法 | 语义 |
| --- | --- |
| `shutdown()` | 平缓关闭：不再接收，已提交的执行完 |
| `shutdownNow()` | 立即关闭：返回**未执行的**任务列表，并**中断**正在执行的（**不保证能停**，见第 7 章） |
| `awaitTermination(t, u)` | 等待到终止或超时 |
| `isShutdown()` / `isTerminated()` | 状态查询 |

> **JVM 退出的规则**：`Executor` 创建的线程默认是**非守护线程**，
> 因此**不调用 `shutdown()`，JVM 就不会退出**（这是最常见的"程序跑完不退出"原因）。

## 四、`Timer` 的三个缺陷（pp.152-156）

| # | 缺陷 | 说明 | `ScheduledThreadPoolExecutor` 的改进 |
| --- | --- | --- | --- |
| ① | **只有一个线程** | 一个任务执行时间长 → 后续任务全部延迟/堆积 | 多线程 |
| ② | **`TimerTask` 抛未检查异常 → 整个 `Timer` 挂掉** | 已调度的任务全部取消，新任务也无法提交 | 任务异常被隔离（但**周期性任务仍会静默停止**，见本书第 9 章笔记） |
| ③ | **基于绝对时间**（`Date`） | 对**系统时钟**变化敏感（NTP 校时、手动改时间） | 基于**相对时间**（`nanoTime`） |

```java
// 今天的写法：完全不要再用 Timer
ScheduledExecutorService ses = Executors.newScheduledThreadPool(1);  // 或自建 ThreadPoolExecutor
ses.scheduleAtFixedRate(cmd, initialDelay, period, unit);
ses.scheduleWithFixedDelay(cmd, initialDelay, delay, unit);
```

> 源码层面的 `DelayedWorkQueue`、leader-follower、`period` 正负号编码三种语义，见
> [../Java并发编程之美/09-ScheduledThreadPoolExecutor.md](../Java并发编程之美/09-ScheduledThreadPoolExecutor.md)。

## 五、找出可利用的并发：页面渲染器（pp.156-164）

本书用一个"渲染 HTML 页面"的例子演示**如何把串行任务改成并行**，三版演进：

### v1：串行 —— 总耗时 = 文本 + 全部图片

```java
void renderPage(CharSequence source) {
    renderText(source);
    List<ImageData> info = new ArrayList<>();
    for (ImageInfo i : scanForImageInfo(source)) info.add(i.downloadImage());
    for (ImageData d : info) renderImage(d);
}
```

### v2：`Future` 并行下载 —— 但渲染仍要等最慢的一张

```java
List<Future<ImageData>> futures = new ArrayList<>();
for (ImageInfo i : info) futures.add(executor.submit(() -> i.downloadImage()));
for (Future<ImageData> f : futures) renderImage(f.get());   // 仍按提交顺序等待
```

> **问题**：`f.get()` 按**提交顺序**等待，即使第 1 张最慢，后面的也出不来。
> 只有"提交完所有任务"这步并行了，**渲染仍是串行的**。

### v3：`CompletionService` —— 谁先完成就先渲染谁

```java
void renderPage(CharSequence source) throws InterruptedException {
    CompletionService<ImageData> cs = new ExecutorCompletionService<>(executor);
    for (ImageInfo i : scanForImageInfo(source))
        cs.submit(() -> i.downloadImage());
    int n = info.size();
    for (int j = 0; j < n; j++) {
        Future<ImageData> f = cs.take();        // ★ 按"完成顺序"取
        renderImage(f.get());
    }
}
```

| 版本 | 并行度 | 首屏时间 |
| --- | --- | --- |
| v1 串行 | 1 | 最慢 |
| v2 Future | 下载并行、渲染串行 | 中等 |
| v3 CompletionService | **下载 + 渲染都按完成顺序** | **最快** |

> **`CompletionService` 的语义（Javadoc 原文要点）**：
> 把"产生新异步任务"与"消费已完成任务的结果"**解耦**；
> 内存一致性：`submit` 前的操作 happens-before 任务执行，任务执行 happens-before `take()` 成功返回。
> 本仓库原笔记里把它写成 `CompleteService`，正确名称是 **`CompletionService`**（接口）
> 与 `ExecutorCompletionService`（实现）。

## 六、JDK 5 → 25 的演进

| 本书写法 | 现代替代 |
| --- | --- |
| `new Thread(r).start()` | **永远不要**；用 Executor 或虚拟线程 |
| `Executors.newFixedThreadPool()` | 显式 `new ThreadPoolExecutor(...)`；**I/O 密集用 `newVirtualThreadPerTaskExecutor()`** |
| `Executors.newCachedThreadPool()` | **JDK 21 起用 `Executors.newVirtualThreadPerTaskExecutor()`**（语义相同但无线程爆炸风险） |
| `Timer` | `ScheduledThreadPoolExecutor` |
| `CompletionService` + `Future.get()` | **`CompletableFuture`（链式组合）** 或 **`StructuredTaskScope` + 扇出**（JDK 21+，见下） |
| `ExecutorService.shutdown()` + `awaitTermination()` | **JDK 19+ `ExecutorService` 实现 `AutoCloseable`**：`try (var es = ...) { }` 自动关闭 |
| 提交任务后手工 `Future.get()` | `invokeAll(tasks)` / `invokeAny(tasks)` |

```java
// JDK 21+：扇出-聚合的现代写法（替代 v3 的 CompletionService）
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    List<Subtask<ImageData>> subs =
        infos.stream().map(i -> scope.fork(() -> i.downloadImage())).toList();
    scope.join().throwIfFailed();
    for (var s : subs) renderImage(s.get());
}
```

> 详见 [../Java并发编程之美/concepts/结构化并发与ScopedValue.md](../Java并发编程之美/concepts/结构化并发与ScopedValue.md)。
> 注意：`StructuredTaskScope` 的 `join()` **本身是阻塞的**（按完成顺序取要自己处理），
> 若需要严格"先完成先处理"，仍可用 `CompletionService` 或多个 CompletableFuture。

## 八、近年研究与工业界前沿

### 近年研究

- **自适应线程池与背压**：SEDA 之后，研究集中在"队列长度驱动的自动扩容/降级"（Netflix 的 adaptive concurrency limit、Google 的 *SRE book* 里的 "queue management"）。
- **协程/虚拟线程调度**：近年工业报告系统评测了百万级并发单元在真实 Web 服务上的收益；结论是**吞吐提升主要来自"不再需要异步写法"，而非调度器本身更快**。
- **任务窃取 vs 任务队列**：CPU 密集场景用工作窃取（见 [../Java并发编程之美/concepts/ForkJoin与工作窃取.md](../Java并发编程之美/concepts/ForkJoin与工作窃取.md)），I/O 密集场景用简单的 FIFO 队列 + 虚拟线程即可。

## 九、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "`new Thread().start()` 简单够用" | 无限制创建线程会 OOM；用 Executor |
| 2 | "`Executors.newFixedThreadPool` 是安全的" | **无界队列** → 任务堆积会 OOM；`maximumPoolSize` 永不生效 |
| 3 | "任务跑完 JVM 就会退出" | `Executor` 线程是**非守护线程**；必须 `shutdown()`（或 JDK 19+ 用 try-with-resources） |
| 4 | "`shutdownNow()` 能停掉正在跑的任务" | 只是**中断**；不响应中断的任务停不下来（第 7 章） |
| 5 | "`Timer` 够用了" | 单线程 + 异常即整体挂掉 + 对系统时钟敏感；**不要用** |
| 6 | "`Future.get()` 按完成顺序返回" | **按提交顺序等待**；要按完成顺序用 `CompletionService` |
| 7 | "`CompletionService` 叫 `CompleteService`" | 正确是 **`CompletionService`**（接口）/ `ExecutorCompletionService`（实现） |
| 8 | "虚拟线程下线程池就没用了" | **CPU 密集 + 需要限制并发数**时仍需池化或用 `Semaphore` 限流；虚拟线程解决的是**阻塞代价**不是**资源无限** |
| 9 | "任务之间可以随便互相依赖" | 在有界线程池里，任务等待另一个任务 → **线程饥饿死锁**（第 8 章） |
