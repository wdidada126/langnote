## 二、核心精讲

### 2.1 状态依赖：前提条件不满足怎么办
- 例：有界缓存 `put` 要求"不满"，`take` 要求"不空"。前提不满足时三种策略：
  1. **传给调用者**（抛异常 / 返回失败码）——最简单，但调用方得自己处理。
  2. **轮询 + `sleep`**——忙等变傻等，浪费 CPU 且响应慢、易活锁。
  3. **条件队列**——`wait/notify`，前提满足时被唤醒，最优雅。
- **条件队列的本质**：把"我在等某个前提"挂进一个队列，前提满足时别人 `notify` 我。这是 AQS 出现前的原始形态。

### 2.2 `wait/notify` 的四道鬼门关（14.2，必考）
1. **条件谓词（guard predicate）**：`wait` 必须包在 `while(!<条件>)` 里，**绝不用 `if`**——因为会"过早唤醒"（spurious wakeup + 被别人抢先消费）。
2. **丢失的信号（lost signal）**：若先改状态再 `notify`，但等待方在两者间进入 `wait` → 信号丢失、永久挂起。必须**先 `notify` 权属内的状态变更与等待顺序正确**（典型错：开放调用下丢失信号）。
3. **通知策略**：`notifyAll` 安全但慢（全唤醒）；`notify` 快但要求"所有等待者同质、且只改一个前提"——多数时候用 `notifyAll` 更稳。
4. **子类安全 / 封装**：基类用条件队列时，子类覆盖方法可能破坏不变性；用**私有条件队列 + 入口/出口协议**封装。

### 2.3 显式 `Condition`（14.3）
- `Lock.newCondition()` 可以有**多个独立等待集**（如 `ArrayBlockingQueue` 的 `notEmpty` / `notFull`），而 `wait/notify` 一个对象只有一个。
- 支持 `awaitNanos` / `awaitUninterruptibly` / `signal` / `signalAll`，语义比 `wait/notify` 清晰且可控。
- 现代代码**一律用 `Condition` 而非 `wait/notify`**（除非维护老代码）。

### 2.4 AQS 是什么（14.5，详见 `concepts/AQS抽象同步队列.md`）
- 通用同步器骨架，含三件套：**同步状态 `state`**（int）、**阻塞线程队列**（CLH 变体）、**`acquire/release` 模板方法**。
- 使用者只实现 4 个钩子：`tryAcquire`/`tryRelease`（独占）、`tryAcquireShared`/`tryReleaseShared`（共享）、`isHeldExclusively`。
- AQS 负责：排队、阻塞/唤醒（Unsafe park/unpark）、取消、公平性。

### 2.5 J.U.C 全是 AQS（14.6）
| 同步器 | AQS 模式 | 状态 `state` 语义 |
| --- | --- | --- |
| `ReentrantLock` | 独占 | 持有线程 + 重入次数 |
| `Semaphore` | 共享 | 剩余许可数 |
| `CountDownLatch` | 共享 | 剩余倒数 |
| `ReentrantReadWriteLock` | 独占+共享 | 高 16 位读计数 / 低 16 位写持有 |
| `FutureTask` (旧) | 独占 | 任务状态（NEW/COMPLETING…） |

## 三、版本演进

- **JDK 5**：`AbstractQueuedSynchronizer` 随 J.U.C 引入（Doug Lea），**整个 `java.util.concurrent` 同步器家族的基石**。
- **JDK 7+**：`FutureTask` 内部实现从 AQS 改为 `state` + `Treiber` 栈（更轻），但外部语义不变。
- **JDK 8**：`StampedLock` **刻意不继承 AQS**（用 CLH 的另一种变体 + 乐观读），因为 AQS 的 `state` 模型装不下乐观读。
- **JDK 9+**：`VarHandle` 逐步替换 AQS 内部的 `Unsafe` 字段操作（JEP 193 之后），为 `Unsafe` 废弃（JEP 471/498）铺路。
- **JDK 21**：AQS 的 `park` 路径与虚拟线程协作——AQS 等待时虚拟线程可挂起（不像 `synchronized` 会 pin），是虚拟线程时代 AQS 相对 `synchronized` 的优势来源。

## 四、经典论文 / 原始文献

- **Doug Lea, "The java.util.concurrent Synchronizer Framework" (SCIENCE 2004 / 技术报告)**——**AQS 的权威论文**，讲清 CLH 变体、状态机、`acquire`/`release` 模板。必读。
- **Craig, "Building FIFO and priority-queuing spin locks from CAS" (1993)**——CLH 原始队列锁。
- **Magnussen, Landin, Hagersten, "Queue Locks on Cache Coherent Multiprocessors" (IPPS 1994)**——MCS 锁，AQS `tail` 链表的近亲。
- **Hoare, "Monitors: An Operating System Structuring Concept" (CACM 1974)**——`wait/notify` 监视器语义的理论源头。
- **Birrell & Mitchell, "Synthesis of an Efficient Synchronization Primitive" (SOSP 1993)**——条件变量的工程化。

## 五、近年研究与工业界前沿

### 5.1 AQS 之外的新同步器范式
- **`StampedLock`**：乐观读（见 13 章、concepts 待补），为 AQS 装不下的语义而生。
- **无锁 / 等待无关（wait-free）同步器**：工业界高频路径（Disruptor、JCTools、caffeine）基本**绕开 AQS**，用 CAS + 内存屏障手写，换取极致吞吐。
- **`SequenceLocks`**（Linux 内核 `seqlock`）思想影响了 `StampedLock` 的乐观读设计。

### 5.2 条件变量的现代替代
- **结构化并发 `StructuredTaskScope`**（JEP 453/505）：把"等前提满足再继续"变成"作用域内所有子任务结束"，再见手工 `Condition`（见 `concepts/结构化并发与ScopedValue.md`）。
- **`CompletableFuture`**：把"等待某前提"变成"完成后回调"，是条件变量的异步化形态（见 concepts/CompletableFuture）。

## 六、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "`wait` 用 `if` 判断就行" | **必须 `while`**（过早唤醒 + 被抢），这是最经典死锁/活锁源 |
| 2 | "用 `notify` 更省" | 多数场景用 `notifyAll`；`notify` 仅在"同质等待 + 单前提"时安全 |
| 3 | "手写同步器从零开始" | 99% 情况继承 `AQS` 实现 4 个钩子即可 |
| 4 | "`FutureTask` 是 AQS" | JDK 7+ 改为 `state`+栈实现，外部语义不变 |
| 5 | "新代码用 `wait/notify`" | 用 `Lock + Condition`；新架构优先 `CompletableFuture`/结构化并发 |
| 6 | "AQS 是万能骨架" | `StampedLock`、无锁队列都**刻意不用 AQS**——极端吞吐场景另起炉灶 |
