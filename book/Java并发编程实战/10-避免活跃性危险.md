# 第 10 章 避免活跃性危险（原书 pp.227-250）

> **活跃性（liveness）**：某件正确的事情**最终会发生**。
> 本章讲四种"卡住"：**锁顺序死锁、资源死锁、饥饿、活锁**。
> 本仓库原笔记记录了用 `jstack` 抓到的真实死锁输出，本篇收录并扩展。

## 一、本章地图

```
四种活跃性故障的分类
        ↓
锁顺序死锁（静态 / 动态 / 协作对象之间的开放调用问题）
        ↓
资源死锁（外部资源池，jstack 检测不到）
        ↓
避免与诊断：tryLock 定时锁、线程转储、JFR
        ↓
饥饿（优先级 / 无法获取资源）与活锁（过度谦让）
```

## 二、四种活跃性故障

| 类型 | 表现 | 能否被 `jstack` 自动检测 |
| --- | --- | --- |
| **① 锁顺序死锁**（`synchronized`/monitor） | 两个线程互相持有对方要的锁 | ✅ **能**（`Found one Java-level deadlock`） |
| **② `ReentrantLock` 死锁** | 同上，但用的是 AQS | ❌ **不能**（JVM 看不到 AQS 的等待关系） |
| **③ 资源死锁** | 等外部资源（连接池、信号量、远程调用） | ❌ **不能** |
| **④ 线程饥饿死锁** | 池线程全部在等池内其他任务（第 8 章） | ⚠️ 部分（表现为线程 WAITING 在 `Future.get`） |
| **⑤ 饥饿 / 活锁** | 线程一直得不到资源 / 一直重试失败 | ❌ 不能（表现为 CPU 高或线程一直 RUNNABLE） |

## 三、锁顺序死锁（pp.227-236）

### 3.1 静态锁顺序死锁

```java
public class LeftRightDeadlock {
    private final Object left  = new Object();
    private final Object right = new Object();
    public void leftRight() { synchronized (left)  { synchronized (right) { f(); } } }
    public void rightLeft() { synchronized (right) { synchronized (left)  { g(); } } }
}
```

**这正是本仓库原笔记里 `Run_13` 的例子**——`jstack` 输出：

```
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x...1be406d8 (object 0x...76b437618, a java.lang.Object),
  which is held by "Thread-0"
"Thread-0":
  waiting to lock monitor 0x...1be3dce8 (object 0x...76b437628, a java.lang.Object),
  which is held by "Thread-1"
Found 1 deadlock.
```

> **JVM 能对 monitor（内置锁）死锁做自动检测**，因为 HotSpot 维护了
> 线程的 "waiting to lock / locked" 图，能做**环检测**。
> 但对 `ReentrantLock`（AQS）**不行**——那是纯 Java 代码里的等待关系。

### 3.2 动态的锁顺序死锁（pp.230）

```java
public void transferMoney(Account from, Account to, int amount) {
    synchronized (from) { synchronized (to) { /* ... */ } }
}
// A→B 与 B→A 同时发生 → 死锁（顺序取决于参数，静态看不出来）
```

**本书的解法**：**定义一致的全局锁顺序**（如按对象身份哈希排序，或按账户 ID 排序）。

```java
private static final Object tieLock = new Object();
public void transferMoney(final Account from, final Account to, final int amt) {
    int fromHash = System.identityHashCode(from);
    int toHash   = System.identityHashCode(to);
    if (fromHash < toHash) { synchronized (from) { synchronized (to) { doTransfer(); } } }
    else if (fromHash > toHash) { synchronized (to) { synchronized (from) { doTransfer(); } } }
    else { synchronized (tieLock) { synchronized (from) { synchronized (to) { doTransfer(); } } } }
}
```

| 要点 | 说明 |
| --- | --- |
| 用 `System.identityHashCode` | 不用 `hashCode()`（可能被覆写，不保证唯一/稳定） |
| **哈希冲突的兜底**（`tieLock`） | 极罕见但必须处理；也可用**账户 ID**（有唯一 ID 时最优） |
| 更简单的替代 | 用一个**全局锁**保护所有转账（牺牲并发度换正确性） |

### 3.3 ★ 协作对象之间的死锁：开放调用（pp.233-236）

```java
// 危险：持有锁时调用"外部方法"（可能被覆写、可能去拿别的锁）
class Taxi {
    @GuardedBy("this") private Point location, destination;
    public synchronized void setLocation(Point p) {
        location = p;
        if (location.equals(destination))
            dispatcher.notifyAvailable(this);   // ← 外部方法，可能拿 Dispatcher 的锁
    }
}
class Dispatcher {
    @GuardedBy("this") private final Set<Taxi> taxis;
    public synchronized void notifyAvailable(Taxi taxi) { taxis.add(taxi); }
    public synchronized Image getImage() { /* 遍历 taxis 并调用 taxi.getLocation()（synchronized） */ }
}
// Taxi.setLocation(持有 taxi 锁) → notifyAvailable(要 dispatcher 锁)
// Dispatcher.getImage(持有 dispatcher 锁) → taxi.getLocation(要 taxi 锁)   → 死锁
```

**本书的解法：开放调用（Open Call）** —— **调用外部方法时不持有锁**。

```java
public void setLocation(Point p) {        // ① 不再 synchronized
    boolean reachedDestination;
    synchronized (this) { location = p; reachedDestination = location.equals(destination); }
    if (reachedDestination) dispatcher.notifyAvailable(this);   // ② 释放锁后再调用
}
```

| 好处 | 说明 |
| --- | --- |
| **消除死锁** | 不存在"持锁等待外部锁"的环 |
| **提高并发度** | 临界区更短 |
| **可分析性** | 锁的获取变成**词法可见**的，容易审计 |

> **这是本章最重要的一条工程规则**：
> **永远不要在持有锁的时候调用"你无法完全掌控"的方法**（覆写的方法、回调、外部对象）。

## 四、资源死锁（pp.237-239）

```java
// 两个不同资源池：两个线程各持一个连接，都想拿第二个
// 数据库连接池只有 2 个连接，两个线程各执行"需要 2 个连接"的查询
```

| 特点 | 说明 |
| --- | --- |
| **资源**可以是任何有限的东西 | 连接池、信号量、CPU 线程、文件描述符 |
| **`jstack` 检测不到** | 等待发生在库内部（如阻塞在 `BlockingQueue` 上） |
| **解法**：设定**资源获取顺序** | 与锁顺序同理；或用**资源池 + 一次性申请全部** |
| **更实用的解法**：**有界等待 + 回退重试**（`tryLock(timeout)`） | 见下 |

## 五、死锁的避免与诊断（pp.239-243）

### 5.1 支持定时的锁：`tryLock`

```java
// 本书 pp.240：用 tryLock 打破"无限等待"
public boolean trySend(ReentrantLock from, ReentrantLock to, long timeout, TimeUnit unit) {
    long stop = System.nanoTime() + unit.toNanos(timeout);
    while (true) {
        if (from.tryLock()) {
            try { if (to.tryLock()) { try { return doSend(); } finally { to.unlock(); } } }
            finally { from.unlock(); }
        }
        if (System.nanoTime() > stop) return false;      // 超时放弃
        Thread.sleep(FIXED + random(1, FIXED));          // ★ 随机退避，避免活锁
    }
}
```

| 要素 | 说明 |
| --- | --- |
| `tryLock(timeout, unit)` | **可中断 + 可定时**的锁获取（第 13 章） |
| **随机退避** | 关键：否则两个线程会**同步重试** → 活锁 |

### 5.2 通过线程转储分析死锁

| 工具 | 命令 | 能看什么 |
| --- | --- | --- |
| **`jstack`** | `jstack <pid>` | **自动报告 monitor 死锁**；显示每个线程的 `waiting to lock` / `locked` |
| **`jcmd`** | `jcmd <pid> Thread.print` | 同上（推荐，`jstack` 在新版中仍可用） |
| **`jcmd Thread.dump_to_file`** | JDK 21+：`jcmd <pid> Thread.dump_to_file -format=json dump.json` | **虚拟线程也能完整 dump**（传统 `jstack` 对百万虚拟线程输出会爆炸） |
| **JFR** | `jcmd <pid> JFR.start ...` 或 JDK 21+ JFR 事件 `JavaMonitorEnter` | **锁竞争的持续时间**与热点锁 |
| **JConsole / VisualVM** | GUI | "检测死锁"按钮（对 monitor 有效） |
| **async-profiler** | — | 采样火焰图，看线程卡在哪 |

> **生产建议**：**定期采集 JFR**，而不是等出事了才 `jstack`。
> 死锁发生后再抓栈是"事后取证"，JFR 能给出"事发过程"。

## 六、其他活跃性危险（pp.243-250）

### 6.1 饥饿（Starvation）

| 成因 | 说明 |
| --- | --- |
| **线程优先级不当** | Java 有 10 个优先级，但**映射到 OS 优先级不可靠**；本书建议**不要依赖优先级** |
| **无法获取资源** | 持锁时间过长、池太小 |
| **非公平锁下的插队** | `ReentrantLock(false)` 允许后来的线程插队（吞吐优先） |

> **本书明确建议**：**不要改变线程优先级**（会让程序依赖平台，且可能引发饥饿）。
> 若必须，用 **`ReentrantLock` 的公平模式**（性能有代价）。

### 6.2 糟糕的响应性

- 临界区太长、线程池太小、大对象 GC —— 都会表现为"响应慢"。

### 6.3 活锁（Livelock）

> **活锁**：线程**没有阻塞**（都是 RUNNABLE），也**在做事**，但**永远无法取得进展**。

| 场景 | 说明 |
| --- | --- |
| **过度谦让** | 两个线程同时发现冲突，同时退让，又同时重试（"走廊里两个人互相让路"） |
| **消息重试风暴** | 消息处理失败 → 回滚并重放 → 又失败 |
| **无误的重试循环** | `tryLock` 失败后**立即**再试（没有退避） |

**解法**：**随机化退避**（本书 pp.247 的 `random(1, FIXED)` 正是为此）。

```java
// 活锁的经典写法（错）：
while (!lock.tryLock()) { /* 什么都不做，立刻重试 */ }
// 正解：随机退避
while (!lock.tryLock()) { Thread.sleep(randomBackoff()); }
```

## 七、JDK 5 → 25 的演进

| 本书论断 | 2020s 的状态 |
| --- | --- |
| `jstack` 是死锁诊断的主要手段 | 依然是第一手段；**JDK 21+ 用 `Thread.dump_to_file -format=json`** 处理虚拟线程 |
| "JVM 能自动报告死锁" | **只针对 monitor**；AQS 锁与资源死锁要靠 JFR/人工分析 |
| 用 `tryLock` + 随机退避 | 仍是标准做法 |
| 手工避免锁顺序死锁 | **结构化并发**减少了"fire-and-forget 任务互相等待"的场景；但**数据级锁顺序死锁依然是开发者责任** |
| 虚拟线程带来的新风险 | 并发量暴涨 → **下游资源（连接池）成为新的死锁/饥饿来源**：N 个虚拟线程各持一个 DB 连接再要第二个 → 资源死锁。**限流（Semaphore）是必修课** |
| 线程优先级 | 依然不建议用；**虚拟线程优先级无效**（始终 NORM_PRIORITY） |

> **虚拟线程的一条硬规则**：虚拟线程**不能设置优先级**（JEP 444 明确：
> `setPriority()` 对虚拟线程无效，始终为 `Thread.NORM_PRIORITY`）。
> 这从机制上终结了"靠优先级调度"的做法。

## 九、近年研究与工业界前沿

### 近年研究

- **死锁的静态与动态检测**：从等待图（Holt）到近年基于**锁图（lock graph）静态分析**与运行时采样检测；JVM 侧仍只覆盖 monitor。
- **分布式死锁**：微服务与数据库事务层面，"跨服务的循环等待"无法靠单一 JVM 检测；近年实践用**超时 + 幂等重试 + 分布式追踪**替代检测。
- **确定性模拟测试**：FoundationDB 的确定性模拟器、Tokio 的 `turmoil`、Madsim 等把"不同调度时序"变成**可枚举的测试维度**，能重现本书时代只能"碰运气"的死锁。
- **活锁与重试风暴**：近年研究（尤其在网络与分布式事务领域）强调**指数退避 + 抖动（jitter）**，与本书的随机退避一脉相承。

### 工业界开源实现

| 项目 | Stars | 与本章关系 |
| --- | --- | --- |
| **openjdk/jdk** | 23.4k | `ThreadMXBean.findDeadlockedThreads()`（**只查 monitor** 与 **ownable synchronizers** 两种）、`jcmd Thread.print` |
| **async-profiler** | — | 火焰图定位"卡在哪"、JFR `JavaMonitorEnter` 事件统计锁等待 |
| **tokio-rs/turmoil** / **madsim-rs** | — | **确定性模拟测试**：把调度时序变成可枚举的测试 |
| **foundationdb** 确定性模拟器 | — | 学术转工业的确定性并发测试范例 |
| **jepsen-io/jepsen** | — | 分布式系统的线性化性与一致性测试 |

> **实用技巧**：`ThreadMXBean.findMonitorDeadlockedThreads()` 只查 monitor；
> **`findDeadlockedThreads()`** 还会查 **ownable synchronizers（`ReentrantLock`）**——
> 后者能覆盖一部分 AQS 死锁，是 `jstack` 之外的补充手段。

## 十、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "`jstack` 能发现所有死锁" | **只发现 monitor 死锁**；AQS 锁、资源死锁、活锁都发现不了 |
| 2 | "死锁只要小心加锁顺序就行" | 还有**资源死锁**（连接池）、**线程饥饿死锁**（第 8 章）两类 |
| 3 | "用 `hashCode()` 排序锁顺序" | 要用 **`System.identityHashCode`**（`hashCode()` 可能被覆写） |
| 4 | "哈希冲突不会发生" | 会；必须有 `tieLock` 之类的兜底（或用唯一 ID） |
| 5 | "持有锁时调用一下别的方法没关系" | **开放调用原则**：外部方法必须在**释放锁之后**调用 |
| 6 | "`tryLock` 失败立刻重试" | 会**活锁**；必须随机退避 |
| 7 | "调高线程优先级能解决饥饿" | 优先级到 OS 的映射**不可靠**；**虚拟线程优先级完全无效** |
| 8 | "公平锁更好" | 公平锁吞吐显著更低；只在确实需要防饥饿时用 |
| 9 | "活锁就是死锁的一种" | 不同：活锁的线程是 **RUNNABLE 且在消耗 CPU**，不会阻塞 |
| 10 | "虚拟线程让死锁消失了" | 数据级死锁照旧；且**并发量暴涨**反而让资源饥饿更常见 |
| 11 | "先到先得地获取所有锁就不会死锁" | 其实"一次性申请全部资源"是有效的防死锁手段，但要能原子地申请 |
