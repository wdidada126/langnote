# 第 8 章 线程池的使用（原书 pp.187-210）

> 上一章讲"为什么用 Executor"，本章讲 **"怎么把 `ThreadPoolExecutor` 配对"**。
> 本书最重要的两个原创洞察：
> **① 任务与执行策略之间存在"隐性耦合"（尤其会导致线程饥饿死锁）；
> ② 线程池大小有公式，不是拍脑袋。**
>
> 本仓库原笔记对 7 个构造参数有完整记录，本篇做了校正与补充。

## 二、任务与执行策略之间的隐性耦合（pp.188-194）

有些类型的任务**只在特定执行策略下才正确**，这就是隐性耦合：

| 任务类型 | 与策略的耦合 | 风险 |
| --- | --- | --- |
| **① 依赖性任务** | 任务 A 等任务 B 的结果 | **线程饥饿死锁**（见下） |
| **② 采用单线程 Executor 的任务** | 假定"同一时刻只有一个任务" | 放到多线程池会破坏其内部假设 |
| **③ 对响应时间敏感的任务** | 需要快速得到线程 | 排在长任务后面会被拖慢 |
| **④ 使用 `ThreadLocal` 的任务** | `ThreadLocal` 绑定到**池线程** | 线程复用 → **数据串台 / 内存泄漏** |
| **⑤ 需要长时间阻塞的任务** | 占住线程不放 | 池被耗尽 |

> **本书的建议**：文档化你的任务对执行策略的要求；
> 不要用"通用的"线程池跑所有类型的任务——**按任务类型分池**（I/O 池 / CPU 池 / 定时池）。

### 2.1 ★ 线程饥饿死锁（Thread Starvation Deadlock，pp.190）

```java
// 在单线程 Executor 里，一个任务提交另一个任务并等待它的结果
ExecutorService exec = Executors.newSingleThreadExecutor();
Callable<String> inner = () -> "inner";
Callable<String> outer = () -> {
    Future<String> f = exec.submit(inner);   // 排进队列
    return f.get();                          // ★ 等它 —— 但唯一的线程正在执行 outer
};
exec.submit(outer).get();   // 永久阻塞
```

**机理**：`outer` 占着唯一的线程，等 `inner`；`inner` 在队列里等线程 → 死锁。

| 触发条件 | 例子 |
| --- | --- |
| 单线程/有界线程池 + 任务内部提交任务并等待 | 上面的例子 |
| 有界线程池 + **互相等待**的任务 | A 等 B、B 等 A |
| 池太小 + 任务阻塞在等待池内其他任务 | 递归并行化 |

**对策**：

1. **不要在同一个池里做"等待同池其他任务"的事**；
2. 用**无界池**（`newCachedThreadPool` / 虚拟线程）——但这只是回避，不是解法；
3. 用 `Future` 之外的方式（如把依赖任务**预先 fork**）；
4. **JDK 21+ 用 `StructuredTaskScope` + 虚拟线程**：`fork()` 不消耗池线程，从根上消除这类死锁。

> **这是虚拟线程最有价值的一点**：`StructuredTaskScope.fork()` 出来的子任务
> **不需要等待线程**，因此"父任务等子任务"不再会耗尽线程。

## 三、线程池大小的估算（pp.194-196）

### 3.1 本书公式

```
N_threads = N_cpu × U_cpu × (1 + W / C)
```

| 符号 | 含义 |
| --- | --- |
| `N_cpu` | CPU 核数 = `Runtime.getRuntime().availableProcessors()` |
| `U_cpu` | 期望的 CPU 利用率（0..1） |
| `W / C` | **等待时间 / 计算时间** 的比率 |

| 负载 | W/C | 建议 |
| --- | --- | --- |
| **纯 CPU 密集** | ≈ 0 | `N_cpu`（或 `N_cpu + 1`） |
| **典型 Web 服务** | 10-100 | 几十到几百 |
| **纯 I/O 密集** | 很大 | 池要大；**JDK 21+ 干脆用虚拟线程，不设上限** |

**如何得到 W/C**：用 JMH/APM 实测，或用 `ThreadMXBean.getThreadCpuTime()` 统计。

### 3.2 Little 定律的视角

```
并发数 = 到达率 × 停留时间
L = λ × W
```

若每秒来 100 个请求、每个请求耗时 0.1 秒 → 需要 **10 个**并发执行单元。
这个关系解释了为什么"线程池太小 → 队列无限增长"。

> **边界**：池太大 → 上下文切换 + 内存；池太小 → 排队延迟。
> **本书 pp.195 的判断**：线程池的"正确大小"很难精确，但**必须有一个上限**。

## 四、配置 `ThreadPoolExecutor`（pp.196-202）

```java
public ThreadPoolExecutor(int corePoolSize,
                          int maximumPoolSize,
                          long keepAliveTime,
                          TimeUnit unit,
                          BlockingQueue<Runnable> workQueue,
                          ThreadFactory threadFactory,
                          RejectedExecutionHandler handler)
```

| 参数 | 语义 | 注意 |
| --- | --- | --- |
| **`corePoolSize`** | 核心线程数；**默认一直存活**（即使空闲） | `allowCoreThreadTimeOut(true)` 可让核心线程也超时退出（本仓库原笔记第 1 条正确） |
| **`maximumPoolSize`** | 最大线程数 | **只有在队列有界时才会生效**（本仓库原笔记第 3 条正确） |
| **`keepAliveTime`** | 非核心线程空闲多久后退出 | 达到后缩到 `corePoolSize`（若允许核心超时则缩到 0） |
| **`workQueue`** | 任务队列 | ⚠️ **必须用有界队列**（`ArrayBlockingQueue`） |
| **`threadFactory`** | 线程工厂 | 命名、优先级、daemon、异常处理器 |
| **`handler`** | 饱和（拒绝）策略 | 见下 |

### 4.1 任务进入池的**三级流程**（关键！）

```
① 线程数 < corePoolSize  → 直接创建新线程（即使有空闲线程）
② 线程数 >= corePoolSize → 放入 workQueue 排队
③ 队列已满 且 线程数 < maximumPoolSize → 创建新线程
④ 队列已满 且 线程数 >= maximumPoolSize → 触发 RejectedExecutionHandler
```

> **很多人的误解是"先到 core，再到 max，最后才排队"——错了！**
> 实际是**先 core → 再排队 → 队列满了才扩到 max**。
> 这直接导致：**无界队列下 `maximumPoolSize` 永远不生效**。
> 源码级的 `ctl` 位运算与 `execute()` 三段流程，见
> [../Java并发编程之美/08-线程池ThreadPoolExecutor.md](../Java并发编程之美/08-线程池ThreadPoolExecutor.md)。

### 4.2 队列的四种选择（pp.199）

| 队列 | 特点 | 适用 |
| --- | --- | --- |
| **无界 `LinkedBlockingQueue`** | 永不拒绝；`maxPoolSize` 无效 | ❌ 生产禁用（会 OOM） |
| **有界 `ArrayBlockingQueue`** | 需要配合饱和策略 | ✅ **默认推荐** |
| **`SynchronousQueue`** | 不存储，直接交付 | 配合 `maxPoolSize=Integer.MAX_VALUE`（`cachedThreadPool`） |
| **`PriorityBlockingQueue`** | 按优先级出队 | 需要优先级调度时 |

## 五、饱和策略（RejectedExecutionHandler，pp.200-202）

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| **`AbortPolicy`（默认）** | 抛 `RejectedExecutionException` | 需要显式感知失败 |
| **`CallerRunsPolicy`** | **由提交任务的线程自己执行** | ✅ **最实用**：天然的**反压**（提交者变慢 → 提交速率下降） |
| **`DiscardPolicy`** | 静默丢弃 | 几乎不该用 |
| **`DiscardOldestPolicy`** | 丢弃队列里**最老**的任务，然后重试提交 | **不能**和 `PriorityBlockingQueue` 一起用（会丢掉最高优先级） |

```java
// 本书推荐的"降级"写法：饱和时改为自己跑，但要保证不影响主流程
new ThreadPoolExecutor(..., new ThreadPoolExecutor.CallerRunsPolicy());
```

| 其他做法 | 说明 |
| --- | --- |
| 自定义 handler | 记日志 + 持久化 + 稍后重试（`new LinkedBlockingQueue` 暂存） |
| **用 `Semaphore` 限流**（本书 pp.201） | 在有界池里，用信号量限制**任务提交速率**而非限制线程数 |

```java
// 本书 pp.201：用 Semaphore 控制"同时提交"的数量
public class BoundedExecutor {
    private final Executor exec;
    private final Semaphore semaphore;
    public BoundedExecutor(Executor exec, int bound) {
        this.exec = exec;
        this.semaphore = new Semaphore(bound);
    }
    public void submitTask(final Runnable command) throws InterruptedException {
        semaphore.acquire();
        try {
            exec.execute(() -> { try { command.run(); } finally { semaphore.release(); } });
        } catch (RejectedExecutionException e) { semaphore.release(); throw e; }
    }
}
```

## 六、定制 `ThreadFactory`（pp.202-204）

```java
public class MyThreadFactory implements ThreadFactory {
    private final String poolName;
    private final AtomicInteger n = new AtomicInteger(1);
    public Thread newThread(Runnable r) {
        Thread t = new Thread(r, poolName + "-" + n.getAndIncrement());   // ① 有意义的名字
        t.setUncaughtExceptionHandler((th, e) -> log.error("...", e));     // ② 异常处理器
        t.setDaemon(false);                                                // ③ 明确 daemon
        return t;
    }
}
```

**为什么要定制？**

| 原因 | 说明 |
| --- | --- |
| **线程命名** | `jstack` 时能一眼看出是哪个池；**生产必备** |
| 异常处理 | 避免 `execute()` 提交的任务异常被静默吞掉 |
| 优先级 / daemon | 明确策略，不依赖默认 |
| 需要特权线程 | `AccessController.doPrivileged` |

> 如果不需要定制，用 `Executors.defaultThreadFactory()`；
> JDK 9+ 的 `Thread.ofVirtual()...factory()` 可得到虚拟线程工厂。

## 七、构造后再定制 / 扩展（pp.204-208）

| 方式 | 说明 |
| --- | --- |
| **setter** | `setCorePoolSize` / `setMaximumPoolSize` / `setKeepAliveTime` / `setRejectedExecutionHandler` / `setThreadFactory` / `allowCoreThreadTimeOut` |
| **`Executors.unconfigurableExecutorService()`** | 包装成不可配置的，**防止调用方改配置** |
| **子类化** | 重写三个钩子（本书 pp.206） |

```java
public class TimingThreadPool extends ThreadPoolExecutor {
    private final ThreadLocal<Long> startTime = new ThreadLocal<>();
    private final AtomicLong numTasks = new AtomicLong();
    private final AtomicLong totalTime = new AtomicLong();

    protected void beforeExecute(Thread t, Runnable r) {
        super.beforeExecute(t, r);
        startTime.set(System.nanoTime());
    }
    protected void afterExecute(Runnable r, Throwable t) {
        try {
            long e = System.nanoTime() - startTime.get();
            numTasks.incrementAndGet(); totalTime.addAndGet(e);
        } finally { super.afterExecute(r, t); }
    }
    protected void terminated() { /* 池关闭时的清理与汇总 */ }
}
```

| 钩子 | 用途 | 注意 |
| --- | --- | --- |
| `beforeExecute` | 计时、日志、**传递 `ThreadLocal` 上下文**（如 traceId） | 抛异常会导致任务**不执行** |
| `afterExecute` | 统计、**必须 `finally` 调 `super`**；`Throwable` 非 null 表示任务抛了异常 | `submit()` 的任务异常**不会**出现在这里（被 Future 吞了） |
| `terminated` | 池完全关闭后的汇总/告警 | |

> **`beforeExecute` 里传 `ThreadLocal`（MDC/traceId）是生产环境的常见做法**，
> 但务必在 `afterExecute` 里 `remove()`，否则**池线程会串数据 + 泄漏**。
> JDK 25 起可用 **`ScopedValue`** 更安全地做这件事。

### 7.1 递归算法的并行化（pp.208-210）

```java
// 串行递归
void processSequentially(List<Element> es) {
    for (Element e : es) if (!e.compute()) processSequentially(e.children);
}
// 并行版本：把每层提交给 Executor
void processInParallel(Executor exec, List<Element> es) {
    for (Element e : es) exec.execute(() -> { if (!e.compute()) processInParallel(exec, e.children); });
}
```

> **⚠️ 本书警告**：这种"在任务里再提交任务"的写法在**有界线程池**里会**死锁**
> （父任务等子任务，池被占满）。
> 正确做法：① 用无界池；② 用 `ForkJoinPool`（见
> [../Java并发编程之美/concepts/ForkJoin与工作窃取.md](../Java并发编程之美/concepts/ForkJoin与工作窃取.md)）；
> ③ **JDK 21+ 用虚拟线程**（最省心）。

## 八、JDK 5 → 25 的演进

| 本书论断 | 2020s 的修正 |
| --- | --- |
| "线程池大小要精心估算" | I/O 密集 → **虚拟线程下不必估算**（`newVirtualThreadPerTaskExecutor`）；CPU 密集仍需按核数配置 |
| "`newCachedThreadPool` 有风险" | 风险依旧；**JDK 21+ 用虚拟线程执行器替代** |
| "队列要用有界" | 依然成立 |
| "有界池任务嵌套会死锁" | 虚拟线程下**不再死锁**（fork 不占线程） |
| "用 `beforeExecute` 传 `ThreadLocal`" | 仍可用，但 **`ScopedValue`（JDK 25 转正）更安全** |
| 手工 `shutdown()` | **JDK 19+ `ExecutorService` 实现 `AutoCloseable`** |
| `Executors.defaultThreadFactory()` | 新增 `Thread.ofPlatform().factory()` / `Thread.ofVirtual().factory()`（JDK 21） |
| 提交任务返回 `Future` | 另加 **`StructuredTaskScope.Subtask`**（JDK 21+） |

**虚拟线程下的新准则**：

```
CPU 密集（W/C ≈ 0）  → 固定池，大小 ≈ N_cpu
I/O 密集（W/C 大）   → newVirtualThreadPerTaskExecutor（不池化）
需要限制并发访问外部资源 → 池化 + Semaphore，或虚拟线程 + Semaphore
```

> **虚拟线程不该池化**（这是 JDK 官方文档的明确建议）：
> 虚拟线程创建成本极低，池化只会带来额外复杂度且毫无收益。

## 十、近年研究与工业界前沿

### 近年研究

- **自适应并发限制（adaptive concurrency limits）**：近年工业界（Netflix concurrency-limits、Google、Envoy）用 **TCP 拥塞控制算法（如 Vegas）** 动态调整并发数，比静态池大小更鲁棒。
- **队列管理的反直觉结论**：Google SRE 文献指出"**队列比线程池更危险**"——排队时间会随负载非线性增长，因此**有界队列 + 快速失败/反压**优于大队列。这与本书"用有界队列"的建议一致。
- **虚拟线程下的资源治理**：并发数不再受线程限制后，**下游资源（连接池、DB）成为新的瓶颈**，研究与实践转向"按下游容量限流"（bulkhead + 信号量）。

### 工业界开源实现

| 项目 | Stars | 与本章关系 |

| **openjdk/jdk** | 23.4k | `ThreadPoolExecutor.java`（`ctl` 位运算、`execute()` 三段）、`VirtualThread.java` |

## 十一、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "先扩到 `maximumPoolSize` 再排队" | **先 core → 排队 → 队满才扩到 max**（2.1 节的三级流程） |
| 2 | "`maximumPoolSize` 总能生效" | **无界队列下永不生效**（这也是 `newFixedThreadPool` 的隐患） |
| 3 | "核心线程永不退出" | 默认如此，但 `allowCoreThreadTimeOut(true)` 可改变 |
| 4 | "`newFixedThreadPool` 是安全的" | 内部是**无界 `LinkedBlockingQueue`** → 任务堆积会 OOM |
| 5 | "`ThreadLocal` 在线程池里可以传上下文" | 会**串数据 + 泄漏**；必须 `remove()`，或用 `ScopedValue` |
| 6 | "`DiscardOldestPolicy` 通用" | **不能**配 `PriorityBlockingQueue`（会丢最高优先级任务） |
| 7 | "`AbortPolicy` 是好的默认" | 会抛异常打断调用方；**`CallerRunsPolicy` 提供天然反压，通常更好** |
| 8 | "`beforeExecute` 里抛异常无所谓" | **任务不会被执行** |
| 9 | "池越大越好" | 超过核数后 CPU 密集任务只会变慢；I/O 密集才需要大池 |
| 10 | "虚拟线程该池化" | **不该**；创建成本极低，池化无收益且增加复杂度 |
| 11 | "有界池里任务嵌套没问题" | 会**线程饥饿死锁**；用虚拟线程或 `ForkJoinPool` |
