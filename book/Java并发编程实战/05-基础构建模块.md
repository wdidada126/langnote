# 第 5 章 基础构建模块（原书 pp.99-134）

> 本章把 JUC 的"现成零件"过一遍：**并发容器、阻塞队列、同步工具类**，
> 并以一个**可伸缩的结果缓存（Memoizer）**收尾——这是全书最漂亮的一个例子。
>
> ⚠️ **本仓库原笔记在本章有多处拼写错误**，本篇顺手更正，见文末「笔误更正表」。

## 一、本章地图

```
同步容器（Vector/Hashtable/synchronizedXxx）为什么不够用
        ↓
并发容器（ConcurrentHashMap / CopyOnWriteArrayList / ConcurrentLinkedQueue / SkipList）
        ↓
阻塞队列与生产者-消费者（put/take 与 InterruptedException）
        ↓
同步工具类：闭锁 / FutureTask / 信号量 / 栅栏
        ↓
★ 实例：可伸缩的结果缓存（ConcurrentHashMap + FutureTask）
```

## 二、同步容器类的问题（pp.100-105）

`Vector`、`Hashtable`、`Collections.synchronizedXxx`：

| 问题 | 说明 |
| --- | --- |
| ① **复合操作不安全** | `if (!v.contains(x)) v.add(x)` 仍需客户端加锁 |
| ② **迭代需要加锁** | 迭代期间若被修改 → `ConcurrentModificationException`（**fail-fast**） |
| ③ **性能差** | 所有方法都锁整个容器，吞吐低 |
| ④ 隐藏的锁对象 | `Collections.synchronizedList` 的锁是 **wrapper 对象本身**（JDK 文档说明），客户端加锁必须锁它 |

```java
// 迭代同步容器的正确写法（本书 pp.102）
synchronized (list) {                          // 必须锁 wrapper
    for (E e : list) { ... }
}
```

> 危险写法：即使加了这个锁，若**其他线程不加锁**就修改，仍然会 CME——
> 这是"协议"而非"机制"，要靠文档与纪律维持。

## 三、并发容器（pp.105-114）

| 容器 | 替代谁 | 特点 |
| --- | --- | --- |
| **`ConcurrentHashMap`** | `Hashtable` / `synchronizedMap` | 分段锁（JDK 5/6）→ **JDK 8 彻底重写**（CAS + 桶头 synchronized + 树化），**读无锁** |
| **`CopyOnWriteArrayList`** | `synchronizedList`（读多写极少） | 写时**复制整个数组**；读完全无锁、迭代器**不会 CME**；**写代价 O(n)** |
| **`ConcurrentLinkedQueue`** | `synchronizedList` 当队列 | 无界无锁 FIFO（Michael-Scott） |
| **`ConcurrentSkipListMap`** | `synchronizedSortedMap` | 有序、并发；**O(log n)** |
| **`PriorityQueue`** | — | **没有**并发版本；需要优先级用 `PriorityBlockingQueue` |

### 3.1 `ConcurrentHashMap` 的关键特性（本书 pp.106-110）

| 特性 | 说明 |
| --- | --- |
| **任意读、有限并发写** | 本仓库原笔记的这句话是对的：读**永不阻塞** |
| **`size()` / `isEmpty()` 不精确** | 并发下是**估计值**；本书原话："这些值的用途有限，因为它们在并发下是不断变化的" |
| **复合操作需要新方法** | `putIfAbsent`、`remove(k,v)`、`replace(k,old,new)`、`computeIfAbsent`（JDK 8+）、`merge` |
| **弱一致迭代器** | 不抛 CME |

> 本书 pp.108 的提醒很实用：**不要用 `size()` 来做判断**（如 `if (map.size() == 0)`），
> 它在并发下既慢（JDK 8 后要遍历 `CounterCell[]`）又不准。用 `isEmpty()` 或直接用 `computeIfAbsent`。

### 3.2 `CopyOnWriteArrayList` 的适用边界

| 适合 | 不适合 |
| --- | --- |
| 事件监听器列表（**遍历多、增删极少**） | 频繁写入 |
| 配置/路由表的快照 | 元素数量大（复制成本 O(n)） |
| 需要"迭代时不加锁且不 CME" | 需要实时看到最新写入 |

> **陷阱**：`CopyOnWriteArrayList` 的迭代器是**创建时的快照**，
> 遍历期间的新写入**不可见**。这在监听器场景是优点，在"读最新状态"场景是 bug。

## 四、阻塞队列与生产者-消费者（pp.114-122）

| 方法 | 行为 |
| --- | --- |
| `put(e)` / `take()` | **阻塞**；`take()` 抛 `InterruptedException` |
| `offer(e)` / `poll()` | 立即返回（`false`/`null`） |
| `offer(e, t, u)` / `poll(t, u)` | 超时返回 |

**用队列解耦生产者与消费者**是本书推荐的首选结构（比"直接共享一个 List + wait/notify"简单得多）。

### 4.1 处理 `InterruptedException`（pp.118，本书的明确建议）

| 策略 | 适用 |
| --- | --- |
| **① 传递（propagate）** | 能抛出就抛出（最优；让上层策略决定） |
| **② 恢复中断状态** | 不能抛时：`Thread.currentThread().interrupt();` |
| ❌ **不要吞掉** | 空的 `catch (InterruptedException e) {}` 是**严重错误** |

> 完整讨论见第 7 章与 [concepts/中断与取消策略.md](concepts/中断与取消策略.md)。

### 4.2 有界队列才是"资源治理"

> **本书的核心建议**：用**有界**队列防止生产过快耗尽内存。
> 这与第 8 章"线程池不该用无界队列"是同一个道理（见 [08-线程池的使用.md](08-线程池的使用.md)）。

## 五、同步工具类（pp.122-130）

| 工具类 | 语义 | 一次性？ | 本书比喻 |
| --- | --- | --- | --- |
| **`CountDownLatch`（闭锁）** | 等待 N 个事件都发生 | ✅ 一次性（计到 0 不能再改） | "起跑门" |
| **`FutureTask`** | 一个可取消、可获取结果的异步计算 | ✅ | "带结果的闭锁" |
| **`Semaphore`（信号量）** | 控制同时访问某资源的线程数 | 可释放任意次 | "许可池" |
| **`CyclicBarrier`（栅栏）** | 所有线程互相等待到齐后一起放行 | ♻️ 可重用 | "集合点" |
| **`Exchanger`** | 两线程在汇合点交换数据 | — | "双线程栅栏" |

### 5.1 `CountDownLatch` 的典型骨架（本书 pp.123）

```java
public long timeTasks(int nThreads, Runnable task) throws InterruptedException {
    final CountDownLatch startGate = new CountDownLatch(1);   // 起跑门
    final CountDownLatch endGate   = new CountDownLatch(nThreads);  // 终点门
    for (int i = 0; i < nThreads; i++) {
        Thread t = new Thread(() -> {
            try { startGate.await();              // 等发令
                  try { task.run(); }
                  finally { endGate.countDown(); }  // 必须 finally，否则永远等
            } catch (InterruptedException ignored) { }
        });
        t.start();
    }
    long start = System.nanoTime();
    startGate.countDown();      // 发令
    endGate.await();            // 等全部完成
    return System.nanoTime() - start;
}
```

> **`countDown()` 必须放 `finally`** —— 否则任务抛异常会导致永久等待。

### 5.2 `FutureTask` 与"可取消的异步计算"

```java
FutureTask<T> ft = new FutureTask<>(callable);
new Thread(ft).start();      // 或 executor.execute(ft)
T result = ft.get();         // 阻塞
ft.cancel(true);             // 取消（若已运行则中断）
```

> JDK 8 之后，`CompletableFuture` 在**组合与异常传播**上远超 `FutureTask`
> （见 [../Java并发编程之美/concepts/CompletableFuture与异步编排.md](../Java并发编程之美/concepts/CompletableFuture与异步编排.md)），
> 但 **`FutureTask` 作为"一次的、可取消的任务"仍有用**（且它是 `Runnable`，能直接交给线程）。

### 5.3 `Semaphore` 用于资源池

```java
// 本书 pp.129：用信号量给"有界集合"加边界
public class BoundedHashSet<T> {
    private final Set<T> set;
    private final Semaphore sem;
    public BoundedHashSet(int bound) {
        set = Collections.synchronizedSet(new HashSet<>());
        sem = new Semaphore(bound);
    }
    public boolean add(T o) throws InterruptedException {
        sem.acquire();             // 先取许可
        boolean wasAdded = false;
        try { wasAdded = set.add(o); return wasAdded; }
        finally { if (!wasAdded) sem.release(); }   // 没加进去就把许可还回去
    }
    public boolean remove(Object o) {
        boolean wasRemoved = set.remove(o);
        if (wasRemoved) sem.release();
        return wasRemoved;
    }
}
```

> **这是本书的一个精巧例子**：用 `Semaphore` 把"无界容器"变成"有界容器"。
> 同样的思路现在可以直接用 `Semaphore` + `ConcurrentHashMap`，
> 或干脆用 `BlockingQueue` 做有界缓冲。

## 六、★ 实例：可伸缩的结果缓存（pp.130-134）

这是本章**最有价值的一段**。三种实现逐级演进：

### 6.1 v1：`HashMap` + 全同步 —— 串行

```java
public synchronized V compute(A arg) {
    V result = cache.get(arg);
    if (result == null) { result = c.compute(arg); cache.put(arg, result); }
    return result;
}
// 问题：整个 compute 被锁住，并发度为 1
```

### 6.2 v2：`ConcurrentHashMap` —— 有重复计算的竞态

```java
V result = cache.get(arg);
if (result == null) { result = c.compute(arg); cache.put(arg, result); }
// 问题：两个线程可能同时发现 miss，都去算一遍
```

### 6.3 v3：`ConcurrentHashMap<K, Future<V>>` —— 本书的答案

```java
public class Memoizer<A, V> implements Computable<A, V> {
    private final ConcurrentMap<A, Future<V>> cache = new ConcurrentHashMap<>();
    private final Computable<A, V> c;
    public V compute(final A arg) throws InterruptedException {
        while (true) {
            Future<V> f = cache.get(arg);
            if (f == null) {
                FutureTask<V> ft = new FutureTask<>(() -> c.compute(arg));
                f = cache.putIfAbsent(arg, ft);   // ★ 原子地"占位"
                if (f == null) { f = ft; ft.run(); }   // 我抢到了 → 我来算
            }
            try { return f.get(); }                     // 没抢到 → 等别人的结果
            catch (CancellationException e) { cache.remove(arg, f); }
            catch (ExecutionException e) { throw launderThrowable(e.getCause()); }
        }
    }
}
```

**这个模式的三个要点**：

| 要点 | 说明 |
| --- | --- |
| ① **`putIfAbsent` 占位** | 保证同一个 key **只算一次**（先到者算，后到者等） |
| ② **`Future.get()` 传播异常** | 计算失败时异常传给所有等待者 |
| ③ **失败要移除缓存** | `cache.remove(arg, f)`（`remove(k, v)` 是原子的条件删除），否则**失败被永久缓存**（缓存污染） |

> **"缓存失败结果"是生产事故高频原因**——本书这个细节很值得记住。

## 七、JDK 5 → 25 的演进

| 本书写法 | 现代替代 |
| --- | --- |
| `ConcurrentHashMap<K, Future<V>>` + `FutureTask` 手写 memoizer | **`cache.computeIfAbsent(k, k2 -> CompletableFuture.supplyAsync(...)).join()`** —— 但要注意 **JDK 8 `computeIfAbsent` 递归更新问题** 与"计算期间持有 bin 锁" |
| `FutureTask` | **`CompletableFuture`**（组合、超时、异常链）+ `StructuredTaskScope`（JDK 21+，扇出聚合） |
| `Hashtable`/`Vector` | 完全废弃 |
| `synchronizedXxx` | 用 JUC 容器 |
| `new Thread(...).start()` | **永远用 Executor** 或虚拟线程（第 6 章） |
| 手写有界缓冲 | `ArrayBlockingQueue` / `Semaphore` / JCTools 队列 |
| 手写缓存 | **Caffeine**（ben-manes/caffeine，17.9k）：自带过期、淘汰、统计、无缓存污染 |

> **仍然推荐的本书内容**：`CountDownLatch` 的"起跑门 + 终点门"基准骨架、
> `Semaphore` 给无界容器加边界、以及 **memoizer 的"占位 + 失败移除"思想**——
> 这些在 JDK 25 上依然是最优雅的写法。

## 九、近年研究与工业界前沿

### 近年研究

- **缓存的并发与淘汰**：本书 memoizer 只处理"并发重复计算"，未处理容量。近年研究（TinyLFU/W-TinyLFU、S3-FIFO、SIEVE）集中在**命中率**；Caffeine 把这些做成了生产级实现。
- **无锁/无等待容器**：JDK 的 `ConcurrentHashMap` 仍是"锁 + CAS"混合；研究界近年偏向 **flat combining** 与 **asynchronized concurrency**（见 ConcurrentHashMap 篇）。
- **缓存污染（cache stampede / dogpiling）**：本书 v3 的 `putIfAbsent` 占位正是解决 **cache stampede** 的经典手段；近年研究扩展到分布式场景（如 Facebook 的 "lease" 机制、probabilistic early expiration）。

| 项目 | Stars | 与本章关系 |

## 十、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "`ConcurrentHashMap` 的 `size()` 准确" | 并发下是估计值且遍历 `CounterCell[]`；不要用它做判断 |
| 2 | "`CopyOnWriteArrayList` 读的是最新数据" | 迭代器是**快照**；遍历期间的新写入不可见 |
| 3 | "`putIfAbsent` 里的初始化函数可以随便写" | **JDK 8 下递归更新同一 map 可能死循环**；JDK 9+ 抛 `IllegalStateException`；且初始化慢会阻塞同 bin |
| 4 | "缓存 miss 时直接 `computeIfAbsent` 就好" | 计算失败会被**永久缓存**；要移除（本书 v3 的 `cache.remove(arg, f)`） |
| 5 | "`CountDownLatch` 可以重置" | **不能**（一次性）；要重用用 `CyclicBarrier` 或 JDK 7+ 的 `Phaser` |
| 6 | "用 `while(true) Thread.yield()` 等条件" | 用**闭锁 / 阻塞队列 / 条件队列**（第 14 章） |
| 7 | "`Vector` 是线程安全的，可以用" | 复合操作与迭代仍需客户端加锁，且所有方法串行为 1 |
| 8 | "`interrupt` 会立刻杀掉线程" | 只是**设置中断标志**；阻塞方法抛 `InterruptedException` 时**标志已被清除**（第 7 章） |
