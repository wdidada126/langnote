# 08 · 对象关系设计（第 8 章 Object-Relational Design, pp.139-160）

> 本章文件为**精读重构**，非原书文本。章题与页区间 ✅ Crossref 实抓；22 页。⚠️ 章内小节与原书例题（涉及 Oracle/DB2 具体语法年代）未能实抓，按 SQL:1999 标准与两厂商公开文档口径转述，一律不标 🔧。

## 一、本章定位：第 5 章"约束缺口"的补票

第 5 章承认过：关系层无法优雅表达多值属性、ISA 完整语义、递归结构的整树查询。对象关系（Object-Relational, OR）路线的答复是：**不推翻关系底座，在 SQL 里加"类型系统"这层脚手架**。本章把 ER 构造逐个对照到 SQL:1999 型体系与各厂商实现（Oracle objects/VARRAY/NESTED TABLE、DB2 structured types），并给出"何时值得用"的冷静判据——教科书立场一贯：先关系映射，OR 特性是逃生舱不是主舱。

## 二、SQL:1999 类型体系速览（转述骨架 ⚠️）

| 机制 | 内容 | 对应 ER 痛点 |
|---|---|---|
| 域/用户定义类型 (UDT) | CREATE TYPE 带属性的行类型 | 概念域的取值纪律（比 CHECK 可复用） |
| 子类型与超类型 | UNDER 关键字，类型继承 | ISA 的原生表达（含多表值方法占位） |
| REF 引用 | 存"对象指针"，Deref 解引用 | 实体引用语义——外键的面向对象替身 |
| 大对象 | BLOB/CLOB（B/NCLOB/LOB） | 多媒体属性（照片、文档） |
| 集合类型 | VARRAY（有序定容）/NESTED TABLE（无序） | 多值属性/1:N 的"内嵌"方案 |
| 表的不嵌套与查询 | TABLE() 把嵌套集合"拍平"回关系 | 内嵌与 JOIN 的两用 |

## 三、ISA 与 1:N 的三种落法对照（本章主戏）

以 PERSON/STUDENT/INSTRUCTOR 与 STUDENT→PHONE 为例：

1. **关系派**（第 5 章 M1/M2/R3）：表+外键+桥接表；标准兼容、工具生态最好；
2. **REF 派**：属性即引用，`DEREF`/路径表达式 `s.school.name` 一跳化；JOIN 从查询里消失、进入模式里——**引用完整性改由"悬空 REF 检测"运维**（Oracle 提供 SCOPE/CHECK 约束 ⚠️ 转述）；
3. **嵌套派**：VARRAY/NESTED TABLE 列；读整棵小树的访问局部性极佳，改一个元素 vs 加桥接表的更新代价两分法。
- 判据（重构 ⚠️）：集合基数小且整体读写→嵌套可赢；需要独立检索/约束/历史→回到关系映射；ISA 层次要"行为+查询双栈"→UNDER 子表法，纯数据→M2 足够。

## 四、为什么本章在 2011 年之后仍要读（历史解剖价值）

- OR 路线是 1990s "OO vs RDBMS"战争（third-manifesto 年代）的制度化产物：SQL:1999 吸收了对象派诉求，但市场用 ORM（Hibernate 2001-）从应用侧完成了同一目标，**服务器内对象体系自此边缘化**。
- 读本章的正确姿势=把它当"厂商扩展 SQL 的标本"：今天 PG 的 composite type/table inheritance/domain 特性，几乎就是本章三件套（UDT/子类型/域）的 PostgreSQL 方言残照 ⚠️ 对照转述。
- 对建模读者的净收益：**理解"引用完整性由谁担保"**（声明式 FK / 悬空 REF 运维 / 应用层）这条光谱，直接迁移到评估 JSON 文档与图库的约束能力。

## 五、易错点与自测

**易错**：① 把 REF 当"自动 JOIN 优化"（无 SCOPE 时是逐行解引用惩罚）；② NESTED TABLE 无上限嵌套撑爆行迁移 ⚠️；③ VARRAY 当历史表用（定容截断丢数据）；④ 用表继承代替规范化建模（PG 继承的约束/索引不自动上卷，查询易漏子表 🔧 可本机 SQLite 无此特性 → 标 ⚠️ PG 文档转述）；⑤ 忘记 ORM 已替你实现多数 OR 需求的时代判断。

**自测五问**：① REF 与 FK 在"更新级联"上的语义差；② TABLE() 函数的桥梁作用；③ 给出 VARRAY 优于桥接表的两个硬条件；④ 为什么 BLOB 不等于"数据库该存文件"；⑤ SQL:1999 哪些 OR 特性今天进了 PG/Oracle 主文档、哪些死了（列三例）。

## 补充一、三场"ER 痛点→OR 药方→市场裁决"完整对照

| ER 痛点（第 2/5 章遗留） | OR 药方（本章 2011） | 市场实际裁决（2026 回望） |
|---|---|---|
| 多值属性必须爆表 | NESTED TABLE/VARRAY 内嵌列 | JSON 数组列（jsonb 等）——内嵌思想胜出，类型系统出局 |
| 递归整树查询写不动 | REF 路径表达式一跳化 | 递归 CTE（标准 SQL 吸收）+ 图库（专用场景） |
| ISA 语义靠应用补 | UNDER 子类型表 | 逻辑保留在应用/视图层，服务器子类型成为冷门特性 |
| 值语义（同值同身份） | UDT 自定义类型+MAP | 引擎内建类型扩容（XML/JSON/ARRAY/RANGE） |
| 大对象与关系"两张皮" | BLOB+CLOB+LOB 定位器 | 对象存储（S3 类）外置+URL 列成为主流形态 |
- 读法：本章每一小节都是一次"平行宇宙"快照——**它记录的是 SQL 标准化进程中对象派赢下的纸面条款与输掉的实战**。

## 补充二、时间线：对象关系三十年（骨架 ✅/⚠️ 混合）

- 1989-1993：POSTGRES（Berkeley，Stonebraker）演示规则/自定义类型——OR 概念孵化器 ⚠️ 史实广为人知，细节未核验；
- SQL:1999：UDT/REF/集合类型/表继承入标准 ✅（标准存在性公开可查，条款细节不引）；
- 2000s 初：Oracle 9i 全面铺开 objects/VARRAY，DB2 UDB 走 structured type 路线——两厂商两套方言 ⚠️；
- 同期：Hibernate（2003 定型）从应用侧吃掉 80% 需求，"O/R 阻抗失配"叙事压过服务器内对象化；
- 2011：本章成稿，立场已是"OR 特性=逃生舱"；
- 2014-：JSON 列（PG jsonb 2014）接管"嵌套派"；SQL:2023 SQL/PGQ 接管"图遍历派" ⚠️ 年份按公开口径；
- 结论：**本章不是失败者的墓碑，是需求分流图**——每种 OR 需求都还活着，只是换了容器。

## 补充三、判据速查（今天还要不要用 OR 特性）

1. 想要嵌套读局部性→JSON 列+表达式索引，不用 VARRAY（可移植性+工具链压倒原生集合类型）；
2. 想要类型化域约束→PG domain/CHECK 组合足够，UDT 的"带方法类型"几乎总有应用层替代；
3. 想要表继承→先想"继承=共享存储还是共享语义"：语义用 M2+视图，物理用声明式分区（PG 官方立场 ✅ ddl.html）；
4. 想要对象标识→业务键+代理键仍是主航道，REF 式"系统级 OID"在多副本/分布式世界已失去立足点；
5. 唯一仍值得原生用的：大对象走 LOB 定位器流式读写——但先问"为什么不放对象存储"。

## 补充四、REF vs FK 深度对照（本章最难考的一题）

| 维度 | 外键（第 5 章世界） | REF（本章世界） |
|---|---|---|
| 存储内容 | 目标行的键值 | 目标行的逻辑指针（含表 OID） |
| 完整性担保 | 引擎即时检查 | SCOPE 子句范围内才检查，越界成悬空 REF |
| 目标迁移/改键 | UPDATE 一处（键不变则零成本） | 需重打引用（REF 随目标行身份浮动） |
| 连接成本 | 索引 JOIN，优化器可重排 | DEREF 逐行，可纳入索引但方言依赖 |
| 级联删除 | ON DELETE 声明式 | 无原生声明（厂商扩展 ⚠️），常靠运维脚本 |
| 跨库/复制友好度 | 高（值自包含） | 低（指针不随行导出） |
- 一句话裁决：**FK 把引用完整性编译进引擎，REF 把它外包给运维**——2011 年后分布式与云复制成为默认部署形态，这条对照就是 REF 退场的判决书。

## 补充五、本章一页总结

- OR 扩展的历史功能=为 ER 语义中"关系表达不了"的三件事（多值/层次/整树）提供服务器内答案；
- 三派落法（关系/REF/嵌套）的判据是读写画像，不是意识形态；
- 市场把三派分别改名为：JSON 列、递归 CTE+图库、应用层 ORM——**需求永生，容器轮替**；
- 建模者的收获是一套"约束由谁担保"的光谱思维：声明式（FK）→类型式（SCOPE）→运维式（脚本）→应用式（ORM），评估任何新存储引擎都先站队这条光谱。

## 核心概念速览（中英对照）

1. **对象关系 DBMS** — object-relational DBMS：在关系底座上加类型系统的路线
2. **用户定义类型** — user-defined type (UDT)/domain：可复用的取值与结构约束
3. **类型子表** — subtype table / UNDER：服务器内的 isa 原生表达
4. **REF 值** — reference value：存对象指针的属性类型
5. **解引用** — DEREF / path expression：沿引用一跳取属性
6. **作用域约束** — SCOPE clause：把 REF 钉在指定表上的完整性声明
7. **悬空引用** — dangling REF：无目标的引用，需运维检测
8. **变长数组** — VARRAY：有序定容集合列
9. **嵌套表** — nested table：无序集合列，行外存储
10. **TABLE() 函数** — unnesting：集合列拍平为派生表
11. **大对象** — BLOB/CLOB：二进制/字符大值的外置存储通道
12. **ORM** — object-relational mapping：本章需求在应用层的最终归宿

## 最新演进与工业实践

- **市场裁决（2024-2026）**：Hibernate/EF/Prisma/SQLAlchemy + 关系底座统治 OLTP；服务器内对象类型仅剩 Oracle 存量系统与 PG 轻量类型特性（composite/domain）日常使用 ⚠️ 生态综述转述。
- **PG 对照**（✅ https://www.postgresql.org/docs/current/ddl.html 域/类型/表继承在官方 DDL 章节可查）：PG 表继承被官方建议改用**声明式分区或显式关系建模**——本章 M2 方案在 2020s 的再确认。
- **JSON 的接管**：多值/嵌套/半结构化需求整体迁往 JSON/JSONB 列（Oracle JSON、PG jsonb、SQL Server 2025 原生 JSON 类型 ⚠️ 版本口径转述）——OR 章的"嵌套派"以文档列形式活了下来，"REF 派"消亡。
- **图库分走**：路径/整树查询由 property graph + SQL/PGQ（SQL:2023 图查询）承接 ⚠️ 标准年份按公开口径，无 DOI。
- 🔧 **本目录实测边界**：VARRAY/REF 不可本机复现（需 Oracle/DB2）→ 全章断言 ⚠️ 转述；SQLite 3.45.3 无类型继承与集合列，仅可演示"嵌套派"平替：JSON1 扩展 `json_each()` 拍平多值属性列（方法：`SELECT j.value FROM t, json_each(t.phones) j`）——作为"TABLE() 思想"的最小标本 🔧。
