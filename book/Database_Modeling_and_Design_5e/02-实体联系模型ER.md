# 02 · 实体-联系模型 ER（第 2 章 The Entity–Relationship Model, pp.13-34）

> 本章文件为**精读重构**，非原书文本。章题与页区间 ✅ Crossref 实抓；二级小节为重构骨架（⚠️）。本章是全书、也是整个 ER 书脉（第 1 版由 Chen 独著，1980 ⚠️ 二手谱系）的概念地基。

## 一、本章定位

22 页讲完一门"数据本体语言"的完整语法：**实体集、属性、联系集、基数比、参与约束、弱实体、ISA**。Teorey 版的讲法偏工程：每个构造都立即给出"它将映射成什么表/约束"的预告，让语法课始终带着语义落地感。读本章请配合 Chen 1976 原文（DOI 10.1145/320434.320440 ✅）与 [../数据库系统概念6/07-数据库设计E-R模型.md](../数据库系统概念6/07-数据库设计E-R模型.md) 的教材口径互勘。

## 二、实体集与属性

- **实体/实体集** — entity / entity set：现实中可唯一区分的对象及其同类集合（某大学里的各位教授 → PROFESSOR 实体集）。
- **实体类型 vs 实体 occuence**：ER 的"型-值"两级区分是后文所有映射规则的前提。
- **属性分类**（本章的清单式讲法）：
  - 简单/复合（simple/composite）：NAME 可拆 LAST/FIRST；
  - 单值/多值（single/multi-valued）：多值属性（PHONE）画双椭圆，映射时必爆一张表——第 5 章规则 R7 的伏笔；
  - NULL 语义：未知/不适用/待填三种含义混用一个 NULL，是数据质量事故的温床；
  - **派生属性** — derived attribute：虚线椭圆（年龄 vs 出生日期），原则上不落库、算出来。
- **键** — key：超键→候选键→主键的收缩链；主键是**语义承诺**（唯一+非空+稳定），代理键（surrogate）vs 自然键（natural key）之争本书倾向保守：能用稳定自然键就别造代理键 ⚠️（口径转述）。

## 三、联系集：ER 的心脏

- **联系/联系集** — relationship / relationship set：跨实体集的语义关联（TEACHES ⊂ PROF × COURSE）。
- **度** — degree：二元为主；**三元联系**（教授-课程-学期）不能机械拆成三个二元而不丢约束——"同一教授同一学期只开一门课"这类跨边约束拆完即失 ⚠️（该反例属 ER 文献共识，具体例题以原书为准）。
- **基数比** — cardinality ratio：1:1、1:N、M:N；ER 图上的标注决定第 5 章外键落在哪一侧（两侧映射代价差一整张桥接表）。
- **参与约束** — participation：全参与（双线下划）/部分参与；"员工必须属于部门"= 全参与 + NOT NULL 的语义等价预告。
- **角色** — role：递归联系（MANAGES：员工管员工）必须显式命名角色，否则外键语义不可读。
- **弱实体与识别联系** — weak entity / identifying relationship：无独立全局键（DEPENDENT 靠员工编号+序号）；识别联系是**存在依赖**，映射为复合主键 + 级联删除语义。

## 四、ISA：泛化/特化

- **ISA（is-a）** — superclass/subclass：STUDENT 是 PERSON 的子类；属性下沉、键上浮。
- **消斥约束** — disjoint（E 标记）/overlap（U 标记）：助教-教授可否重叠直接决定映射方案数。
- **完全/不完全特化** — total/partial specialization：子类覆盖是否穷尽，决定"只查超表会不会漏人"。
- 本章立场（第 3 版以来延续）：ISA 是"共享属性"工程手段，不是对象继承的"行为多态"——这是 ER 与 UML 在语义浓度上的著名分歧，衔接第 3 章对照表。

## 五、本章的规则预告（与第 5 章映射的镜像）

| ER 构造 | 预告的逻辑产物 |
|---|---|
| 强实体 | 1 表，主键照搬 |
| 弱实体+识别联系 | 1 表，PK=(超类FK+局部键)，CASCADE |
| 1:1 联系 | 合并或外键上挂一侧 |
| 1:N 联系 | 外键进"N 侧"表 |
| M:N 联系 | 独立桥接表 |
| 多值属性 | 独立两列表 |
| 派生属性 | 不落库 |
| ISA | 三方案之争（见 05 文件） |

## 六、易错点与自测

**易错**：① 把"外码放 1 侧"记成"放 1:N 的 1 侧"（正确：放 N 侧）；② 弱实体忘了识别联系也是主键一部分；③ 三元联系拆二元时丢跨边约束；④ 派生属性入库后与源属性打架（生日改了年龄没跟着改）；⑤ 用 NULL 兼职表达"不适用"，聚合函数悄悄丢行。

**自测五问**：① 1:1 联系什么时候该独立成表？② overlap 的 ISA 为何会破坏"每子类一表"方案的键约束？③ 给出一个必须用角色名的递归联系。④ 全参与如何用约束表达？⑤ 多值属性与桥接表的同构性。

## 补充一、记法三方对照（开会必备的一页）

同一个"学生选多门课"事实，三种画法读法互译：

| 元素 | Chen 原记法 | 鸦爪（IE/Barker） | Mermaid ER（代码化） |
|---|---|---|---|
| 实体集 | 矩形 | 圆角框+属性内列 | `STUDENT { int sid PK }` |
| 属性 | 椭圆 | 框内行 | 框内列 |
| 多值属性 | 双椭圆 | 独立子表旁挂 | 注释+桥接实体 |
| 联系集 | 菱形 | 动词短语标签线 | 关系线 |
| M:N | 菱形两端 `M/N` | 鸦爪对鸦爪 | `||--}o` 等符号 |
| 弱实体 | 双矩形+双菱形 | 非标识外键+依赖记号 | 复合 PK 表达 |
| ISA | 椭圆 is-a 或 E/U 圈 | 圆圈+单/双弧 | 独立子类实体+ `{xor}` 注释 |

- 评审现场的教训：**同一张图混用两种记法必出歧义**（E 圆 vs `{xor}` 被不同人读出 disjoint/overlap 两种约束）；模型文档开头放记法图例是第 11 章工具治理话题的入口。

## 补充二、构造判定流程（拿到一句话怎么落图）

1. 句子主干是"X 是 Y 的一种"？→ ISA，否则下一步；
2. 名词有无独立标识（能被单独查询/引用/加约束吗）？→ 能则实体，不能则属性；
3. 该"属性"会一人多值吗？→ 多值属性候选，先问"值会被独立检索吗"：会→联系/弱实体，不会→R3 桥表；
4. 动词有属性/有历史吗？→ 联系升格实体（reification）；
5. 两端各有键吗？基数比标两端；"必须存在吗"？参与标双线；
6. 拿不准的，写出**正反两个实例数据**（哪一行会被删/会冲突），约束自然现形。

## 补充四、把本章讲给 SQL 老手的五个"为什么值得回头"

1. 你写过的 `LEFT JOIN ... IS NULL` 反连接，多半源于当年 1:N 外键放错侧；
2. 你的"通用状态表"设计病根：把弱实体（依赖识别者）错当独立实体；
3. 你的 CHECK 约束写不完：因为参与/消斥约束本该在概念层裁决，不是 DDL 层补锅；
4. 你的报表多表 JOIN 爆炸：某处 M:N 被拆成两个 1:N，"联系"降级成了"巧合"；
5. 你说不清"这列能不能删"：ER 图上该属性挂在哪个实体、被哪些联系消费，就是删除影响分析的原始地图。

## 补充五、本章一页总结

- 实体=名词，属性=形容词，联系=动词的名词化——语法隐喻是 ER 易学易教的根本原因；
- 真正决定模式质量的是**约束的完整度**：基数比、参与、键、消斥四件套一个都不能省；
- 弱实体与 ISA 是唯二"会在映射时产生方案分叉"的构造，务必带着第 5 章规则表重读一遍；
- 图不是艺术：每张图必须能被"反例数据"检验（哪两行会让它出错），能过反例的模型才有资格进 DDL 车间。

## 核心概念速览（中英对照）

1. **实体** — entity：可唯一辨识的现实对象
2. **实体集** — entity set：同型实体的集合
3. **属性** — attribute：实体的描述特征
4. **多值属性** — multi-valued attribute：一个实体可拥有多个值，映射须独立表
5. **派生属性** — derived attribute：可由其他属性算出，原则上不落库
6. **候选键/主键** — candidate key / primary key：最小超键 / 被选定的唯一非空标识
7. **联系集** — relationship set：实体集间的语义关联集合
8. **基数比** — cardinality ratio：1:1 / 1:N / M:N，决定映射方向
9. **参与约束** — participation constraint：全参与/部分参与
10. **弱实体** — weak entity：无独立主键、依赖识别联系存在
11. **识别联系** — identifying relationship：支撑弱实体存在的双线联系
12. **ISA / 泛化** — generalization/specialization：类间 is-a 层次
13. **消斥/重叠约束** — disjoint/overlap constraint：子类可否共存
14. **代理键** — surrogate key：无业务含义的人造主键
15. **递归联系** — recursive relationship：同一实体集内部关联，需角色名
