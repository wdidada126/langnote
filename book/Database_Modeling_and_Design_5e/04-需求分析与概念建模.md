# 04 · 需求分析与概念建模（第 4 章 Requirements Analysis and Conceptual Data Modeling, pp.55-84）

> 本章文件为**精读重构**，非原书文本。章题与页区间 ✅ Crossref 实抓；全书最长正文章（30 页），二级小节为重构骨架（⚠️）。

## 一、本章定位

前三章给了语言（ER/UML），本章给**流程**：如何从一团乱的需求谈话出发，走到一张可以评审、可以映射的概念图。Teorey 书脉此章的方法论底色是"自顶向下 + 视图集成"——先抓主干实体与联系，再按部门视图逐步合并，冲突驱动细化。它也是第 7 章大学案例的输入端：案例里的每张局部视图都出自本章规程。

## 二、需求收集的工程化

- **信息来源**：业务文档、表单/报表样本（最诚实的需求——它们暴露保留字段与隐含联系）、关键用户访谈、现有系统数据剖析（data profiling：值域、空值率、依赖疑似）。
- **访谈纪律**：按"名词—动词—约束"三遍扫问题清单：有哪些东西？彼此怎么关联？什么情况下不允许？第三遍的"不允许"就是未来的约束与检查。
- **需求规格的最小可行物**：用例清单（承接第 3 章）+ 候选实体清单 + 已知业务规则清单。

## 三、概念模式设计策略（本章的骨架决策）

| 策略 | 做法 | 适用 | 风险 |
|---|---|---|---|
| 自顶向下 top-down | 先画抽象主干实体（如 COURSE/PERSON），再特化 | 领域结构稳定 | 过度泛化、评审者看不懂 |
| 自底向上 bottom-up | 从表单字段聚合实体 | 遗留系统改造 | 只见树木、联系遗漏 |
| Outside-in | 从用例边界的数据产物倒推 | 敏捷/特性团队 | 全局命名失序 |
| 视图驱动 view integration | 每部门一张局部 ER 图，再合并 | **本书主推** | 合并冲突工作量 |

## 四、局部视图与视图集成（冲突分类学）

合并两张局部图时的四类冲突（本章的"背诵重点"）：

1. **同物异名** — synonym：教务处的 `INSTRUCTOR` 与人事处的 `FACULTY` → 统一名；
2. **异物同名** — homonym：两处都用 `COURSE`，一处含学期段一处不含 → 拆分命名；
3. **结构冲突** — structural：同一事物一边画**实体+属性**、另一边画**联系/多值属性/弱实体** → 以语义较强者为准统一；
4. **约束/键冲突**：主键选择不同、基数标注不同、参与假设不同——最隐蔽，常映射成两套互相矛盾的表。

- 合并顺序：先归一"实体集"，再归一"联系集"，最后统一键与约束；每步留下可追溯的决策日志（CASE 章第 11 章说：这是元数据模型要管的事）。
- **视图集成的判定终点**：合并后的全局图能复现每一张局部视图（无损）——与第 6 章"无损连接分解"恰成对偶，一个在概念层、一个在关系层。

## 五、设计质量原则（评审清单的前身）

- **代表性**：图能"接住"每个用例的数据需求——沿用例走查图的边；
- **最小冗余**：概念层避免可推导的重复联系（派生属性入库的同类错误）；
- **灵活性**：对"未来大概率变化的基数"做压力测试（1:1 会不会长成 1:N？弱实体要不要转正？）；
- **可读性**：一张图 ≤ 7±2 个实体；超了就分层（主图 + 子图），这是 Hoberman"模型是沟通物"立场在教科书里的孪生表述（[../数据建模经典教程.md](../数据建模经典教程.md)）；
- **可扩展性**：ISA 与命名规范为新增子类/新部门视图留缝。

## 六、从概念图到"可评审物"的产物清单

| 产物 | 内容 | 下游消费者 |
|---|---|---|
| 全局 ER/UML 图 | 实体/联系/约束全集 | 业务方评审 |
| 对象目录 | 每个实体集的业务定义+负责人 | 治理 |
| 业务规则表 | 约束的自然语言→谓词化 | 第 5 章映射、第 7 章验收 |
| 用例-元素追踪矩阵 | 用例 ↔ 图元素 | 验收与变更影响分析 |

**易错点**：① 把报表列直接当属性（报表列多是派生值/联系路径）；② 需求未冻结就画细图（返工黑洞）；③ 视图集成时"就近合并"不登记决策（三个月后无人记得为何）；④ 用外键思维画 ER（图应回答"业务上有几种联系方式"，不是"哪张表挂键"）。

**自测五问**：① 结构冲突给出一个具体双例；② 何时放弃视图驱动改自顶向下；③ 追踪矩阵在模式变更评审中如何减少漏检；④ 弱实体转正的三信号；⑤ 概念模型要不要出现代理键（立场+理由）。

## 补充一、迷你演练：三张局部图合并成诊所全局图

**局部输入**（每部门一张，虚构演示数据 ⚠️）：
- 挂号处：PATIENT、VISIT（带时间与诊室）、DOCTOR；
- 药房：PRESCRIPTION（药品名、剂量、开方医生）——其 DRUG 是**属性**；
- 检验科：LAB_TEST（项目编码、参考值区间）、执行护士 NURSE。

**冲突扫描（对号入座）**：
1. 挂号的 DOCTOR vs 药房的"开方医生" → 同物异名（synonym）：合并为 DOCTOR，开方成为联系 PRESCRIBES；
2. 药房 DRUG（属性）vs 检验科"项目"（也是文本属性）vs 财务"药品目录"（有编码/单价的实体）→ **结构冲突**：财务视图信息量大，DRUG 升格实体，药房属性降级为外键+数量；
3. VISIT 在挂号处是 1:N 的 N 端，在药房/检验科各自挂 patient+日期 → 局部视图重复表达"就诊" → 统一为 VISIT 弱实体（识别者 PATIENT），PRESCRIPTION/LAB_TEST 改挂 VISIT；
4. NURSE 与 DOCTOR 同属性骨架 → 引入 PERSON 超类 + 两个 ISA 子类，留待第 5 章定 M1/M2；
5. 两处都有"日期"但一名 DATE 一名 WHEN → 命名标准裁决（数据字典先行）。

**合并后检查**：三张局部图能否各自从全局图**投影**回来？不能投影=合并过界（丢语义）。

## 补充二、访谈题库（按"名词-动词-约束"三遍扫）

- 名词遍：这些东西有几个名字？谁维护？删除前要先处理什么？
- 动词遍：一次操作动几样东西？会不会只改一半（引出事务边界与约束）？
- 约束遍：什么情况下系统必须说不？（每个"不"登记为业务规则表一行，标注责任人与例外）
- 历史遍：报表要不要"上个月的这个值"？（引出 SCD/时间维度，预告第 10 章）
- 例外遍：有没有人工兜底流程？（例外即未建模的联系——经验高频金矿）

## 补充三、概念模型的"验收定义"（何时算画完）

1. 每个用例三行全部能在图上指认；
2. 全局图对每张局部视图可投影；
3. 业务规则表逐条有落点（键/约束/触发器预留位）；
4. 追踪矩阵零孤儿（需求↔元素双向可查）；
5. 两名不参会的评审者能据图写出一致 DDL 骨架——**一致性是模型的单元测试**。

## 补充四、常见"需求陷阱→模型病灶"对照表

| 需求现场症状 | 大概率模型病灶 | 修复动作 |
|---|---|---|
| "都要，但还没定" | 属性清单无限膨胀 | 冻结 MVP 实体集，其余进 backlog 注记 |
| 每人一个 Excel | 报表列被当属性（派生值入库） | R4 派生属性回推源列 |
| "偶尔有个例外" | 约束过度严格，例外通道=隐形多值 | 例外规则显式建模（标志列+策略） |
| 老系统字段名黑话 | 同义词库缺失 | 命名标准+数据字典先行（第 11 章联动） |
| "先把表建起来再说" | 概念层被跳过 | 本章流程重放——用三张局部图换一次会议共识 |

## 核心概念速览（中英对照）

1. **需求收集** — requirements collection：从文档/表单/访谈/数据剖析中提取数据需求
2. **数据剖析** — data profiling：对现存数据的值域、空值、依赖做统计探查
3. **自顶向下设计** — top-down design：从抽象主干逐步特化
4. **自底向上设计** — bottom-up design：从字段/表单聚合实体
5. **视图集成** — view integration：合并多个局部 ER 图为全局图
6. **局部视图** — local/global view：部门级概念图与合并后的全局图
7. **同物异名** — synonym：不同名同语义的建模元素冲突
8. **异物同名** — homonym：同名不同语义的建模元素冲突
9. **结构冲突** — structural conflict：同一业务事实的建模构造不一致
10. **业务规则** — business rule：需落入约束的强制性事实
11. **可追溯性** — traceability：需求↔模型元素↔表的映射链
12. **模型评审** — model review：以分层图与目录驱动的结构化走查

## 最新演进与工业实践

- **敏捷化（2024-2026）**：完整的"访谈→局部图→集成"瀑布被"每迭代一张增量 ER"取代；但企业级主数据/合规域（金融、医疗）仍按本书式全量建模——两条路线的分工在 Hoberman 的"just adequate modeling"里表述得最清楚（[../数据建模经典教程.md](../数据建模经典教程.md)）。
- **工具链**：erwin/PowerDesigner 的模型比较（model compare）功能本质是自动视图集成冲突检测（商业工具 ⚠️ 转述）；开源侧 dbdiagram.io、Navicat Data Modeler、pgModeler（GitHub 直连本机超时 ⚠️ 仅登记仓库名）承担轻量合并评审。
- **LLM 新变量**：从访谈纪要/工单文本自动抽取候选实体与关系的 prompt 工作流在 2024-2026 成为咨询现场新工具；**同物异名/异物同名判定**仍是人机分工焦点 ⚠️（社区实践口径，无权威统计）。
- **论文线**：视图集成经典（Greier 1983、Navathe 系 ER2 工具论文）可沿 [../../db/db.md](../../db/db.md) 检索；本次未做 DOI 校验，故不给 DOI。
- **与 repo 衔接**：本章的"冲突分类学"在数仓集成场景以另一副面孔出现——Kimball 一致性维度与主数据管理（[../数据仓库工具箱3.md](../数据仓库工具箱3.md)）。
