## 1. Gartner 源流：从"编织"隐喻到架构品类

- 2016 年 Gartner 在 *Data Management Trend* 中首次将 data fabric 作为**独立架构品类**提出，区别于点对点的集成方式。
- 核心隐喻：数据管理不应是"一堆管道"，而应像织物（fabric）一样——**纤维（数据源）通过经纬（元数据+集成）交织成统一面料**。
- Gartner 的后续 hype cycle（2018–2023）将 fabric 从"创新触发"逐步移至"生产力高原"，说明概念已完成**从营销到工程**的过渡。
- ⚠️ 本书（#212）作为 Packt 实操向手册，定位在 Gartner 品类定义已被市场接受之后——"怎么建"而非"要不要建"。

> 与 #210 的 [01 章](../Data_Fabric_as_Modern_Data_Architecture/01-数据架构的演进-从孤岛到编织.md) 互补：#210 讲"为何编织是架构演进的必然答案"，本目录讲"照着做第一步"。

**定义交集**（三厂商共识）：
1. 跨异构环境（混合云 / 多数据库 / 多格式）
2. 元数据驱动（不是硬编码管道）
3. 逻辑访问优先于物理搬运
4. 治理内建而非外挂

> ⚠️ 各厂商定义偏向自家产品线：IBM 偏 AI 自动化，Denodo 偏虚拟化，Informatica 偏全栈平台。本书作为实操手册，需在 02 章拆解这些组件的**功能边界**。

## 3. Fabric 与传统 ETL / ESB 的分野

| 维度 | 传统 ETL 管道 | ESB（企业服务总线） | Data Fabric |
|---|---|---|---|
| 数据流动 | 批量物理搬运 | 消息路由 | 逻辑优先，按需物化 |
| 元数据角色 | 附属文档 | 无内建元数据 | **一等公民**，驱动自动化 |
| 扩展模式 | 加新管道 | 加新适配器 | 加新元数据描述 |
| 治理嵌入 | 事后审计 | 无 | **策略即代码**内建 |
| 适用规模 | 单仓/单湖 | 应用集成 | 企业级混合数据生态 |

**关键分野**：
- ETL 回答"怎么把 A 搬到 B"；fabric 回答"怎么让 B 不需要搬就能被 A 的消费者看到"。
- ESB 面向**应用间消息路由**；fabric 面向**数据消费者与数据源之间的语义统一**。
- ⚠️ fabric 不替代 ETL——大规模分析场景仍需物理物化——而是把 ETL 作为 fabric 内的一种**可选执行策略**。

## 4. Fabric 与 Data Mesh 的架构路线之辩

> 详细对照见 [Data_Mesh/00](../Data_Mesh/00-总览与阅读地图.md)。此处仅摘核心差异。

| 维度 | Data Fabric | Data Mesh |
|---|---|---|
| 核心隐喻 | 统一织物 | 联邦生态 |
| 数据所有权 | 集中/共享 | **领域团队自治** |
| 治理模式 | 中央策略引擎 | 联邦计算治理 |
| 技术核心 | 元数据+虚拟化 | 自助平台+数据产品 |
| 适用组织 | IT 中心化企业 | 领域驱动型组织 |

⚠️ 二者并非互斥——#210 的 [07 章](../Data_Fabric_as_Modern_Data_Architecture/07-编织与网格-两条现代架构路线对照.md) 和 #202 的 [08 章](../Data_Fabric_and_Data_Mesh_with_AI/08-混合云格局下的两条路线.md) 均讨论了**混合路线**的可能性。本目录 08 章在选型框架中展开。

## 4.5 Fabric 架构的工程模式分类

⚠️ 综合 IBM / Denodo / Informatica 文档推定的三种典型部署模式：

| 模式 | 核心引擎 | 元数据策略 | 适用场景 |
|---|---|---|---|
| 虚拟化优先（Virtualization-First） | Denodo / Trino | 远程源注册+逻辑视图 | 查询延迟可接受、数据敏感不允许搬运 |
| 集成优先（Integration-First） | Informatica ICS / dbt | 物理物化+CDC 同步 | 大规模分析、需要统一存储 |
| 混合模式（Hybrid） | IBM Cloud Pak / 自建 | 热数据虚拟化+冷数据物化 | 企业级全场景覆盖 |

⚠️ 本书作为实操向著作，大概率以混合模式为主线展开——因为单一模式无法覆盖企业全部用例。

> 🔧 DuckDB 演示（「非本书引擎行为」）：DuckDB 可作为混合模式中的轻量物化引擎，通过 `ATTACH` 语法实现跨源查询联邦：
> ```sql
> -- 「非本书引擎行为」DuckDB 跨源联邦示例
> ATTACH 'postgresql://host/db' AS remote_pg (TYPE postgres);
> CREATE TABLE local_cache AS SELECT * FROM remote_pg.schema.heavy_table;
> SELECT * FROM local_cache JOIN remote_pg.schema.live_table USING(id);
> ```
> 此模式演示了"热数据虚拟化 + 冷数据物化"的混合策略最小实现。

## 7. 常见误区与反模式

1. **"fabric = 数据虚拟化"**：虚拟化是 fabric 的关键组件之一（02 章 §2.3），但不是全部——元数据管理、集成编排、治理嵌入同样不可或缺。
2. **"fabric 替代 ETL"**：fabric 主张"逻辑优先"（03 章），但大规模分析场景仍需物理物化；fabric 把 ETL 作为**可选执行策略**，而非消灭它。
3. **"fabric = 某个厂商产品"**：fabric 是架构范式（⚠️ Gartner 品类定义），不等于 IBM Cloud Pak / Denodo / Informatica 中的任何一个——产品是实现之一。
4. **"fabric 与 mesh 二选一"**：04 节已述，二者可混合——#210 07 章与 #202 08 章均有详细讨论。
5. **"上了 fabric 就不需要治理"**：fabric 的"治理内建"（07 章）意味着治理**自动化**，但治理策略本身仍需组织层定义（→ [Data_Governance_Elsevier](../Data_Governance_Elsevier/00-总览与阅读地图.md)）。

⚠️ 误区 3 尤其值得注意：Microsoft Fabric（产品名）≠ Data Fabric（架构范式），8.4 节的"防混硬点"。

## 核心概念速览（中英对照）

| 中文 | English | 一句话 |
|---|---|---|
| 数据编织 | Data Fabric | 跨异构环境的元数据驱动统一数据管理架构 |
| 元数据驱动 | Metadata-Driven | 元数据作为一等公民驱动自动化决策 |
| 逻辑访问 | Logical Access | 不搬数据即可查询远程源 |
| 物理搬运 | Physical Movement | ETL/CDC 等将数据实际复制到目标 |
| 策略即代码 | Policy-as-Code | 治理策略以可执行代码形式内建于管道 |
| 联邦治理 | Federated Governance | 中央策略+领域自治的混合治理模式 |
| 数据虚拟化 | Data Virtualization | 不搬数据即可查询异构源的逻辑统一层 |
| 主动元数据 | Active Metadata | 元数据回路自动触发编排与治理动作 |
| 集成债 | Integration Debt | 点对点管道累积的维护成本与风险 |
| 语义层 | Semantic Layer | 跨源统一业务术语的逻辑映射层 |
| 织点 | Fabric Node | fabric 架构中一个可独立交付的集成单元 |

## 最新演进与工业实践

- **2024 Gartner**：将 data fabric 与 data mesh 合并讨论为"现代数据架构"的两大路线，不再作为独立 hype cycle 条目——标志着**概念成熟**。
- **IBM watsonx.data**（2024）：把 fabric 概念落地为具体产品，强调"AI 助手 + 开放表格式 + 统一治理"三支柱。
- **Denodo 5.0**（2024）：强化 Active Metadata 能力，元数据回路从"推荐"升级为"自动执行"。
- ⚠️ 厂商营销密度极高——本目录始终以 IBM/Denodo 官方定义为锚（✅ URL），功能宣称标 ⚠️。
- **2025 Gartner**：进一步将 fabric 与"复合 AI 系统"（Composite AI Systems）概念融合——元数据回路不再只是治理工具，而是 AI 系统的**数据供应层**（✅ gartner.com）。
- **开源阵营**：Apache Atlas + OpenMetadata 在 2024 年后加速追赶商业平台的元数据管理能力，自建 fabric 的工程门槛下降（⚠️ 社区趋势转述）。
