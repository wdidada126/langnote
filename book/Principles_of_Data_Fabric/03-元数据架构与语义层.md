# 03 · 元数据架构与语义层

> ⚠️ 主题重构地图（取证声明见 [00 §1](00-总览与阅读地图.md)）。本章聚焦元数据的架构设计（三态分类落地）与语义层工程实现。🔧 数字为 SQLite 3.45.3 / DuckDB 1.5.5 本机实测（**⚠️ 非本书引擎/平台行为**）。

## 1. 从 02 章的"三态分类"到工程落地

02 章定义了技术/业务/运营三态元数据。本章回答：**这些元数据在存储层怎么组织？**

### 1.1 元数据存储架构选型

| 架构 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 关系型（PostgreSQL/MySQL） | 事务安全、JOIN 灵活 | schema 变更成本高 | 元数据模型稳定期 |
| 图数据库（Neo4j/JanusGraph） | 血缘/关系查询天然适配 | 运维复杂、生态小 | 血缘密集型 |
| 文档型（MongoDB） | schema 灵活 | 跨文档 JOIN 弱 | 元数据结构频繁变化 |
| 搜索引擎（Elasticsearch） | 全文检索强 | 非事务安全 | 目录搜索层 |

⚠️ 多数 fabric 平台采用**混合架构**：关系型存核心元数据 + 图存血缘 + ES 存搜索索引。

## 2. 技术元数据建模

### 2.1 核心实体模型

```
Database → Schema → Table → Column
                ↓
          Partition → File/Block
```

关键字段设计：
- `Column`：name, data_type, nullable, description, tags[], pii_flag
- `Table`：name, owner, row_count_estimate, last_updated, storage_location
- `Database`：name, engine, connection_string_ref, environment

### 2.2 采集与同步策略

| 源类型 | 采集方式 | 频率 |
|---|---|---|
| RDBMS | JDBC `DatabaseMetaData` | 每小时/变更触发 |
| Hive/Iceberg | HMS Thrift API | 每 15 分钟 |
| S3/ADLS | 对象列表 + 推断 | 每小时 |
| Kafka | Schema Registry pull | 实时事件 |

## 3. 业务元数据建模

业务元数据的挑战：**非结构化、人工维护、版本化需求**。

### 3.1 数据字典与术语表

- **术语表（Glossary）**：term, definition, synonym[], owner, steward
- **术语-资产映射**：term_id ↔ dataset_id / column_id（多对多）
- **层级关系**：parent_term_id（如"收入"→"经常性收入"→"订阅收入"）

### 3.2 数据所有者与管家

| 角色 | 职责 | 粒度 |
|---|---|---|
| Data Owner | 对数据集的业务价值和合规负责 | 数据集级 |
| Data Steward | 日常治理执行：质量检查、策略审批 | 域级 |
| Data Consumer | 使用数据，反馈质量问题 | 无管理职责 |

→ 07 章展开治理时，Owner/Steward 是策略执行的主体。

## 4. 运营元数据建模

运营元数据是"主动元数据"（05 章）的输入源：

| 指标 | 含义 | 采集源 |
|---|---|---|
| freshness | 数据最新时间 vs 当前时间 | 管道运行日志 |
| volume_delta | 本次加载行数 vs 历史均值 | ETL 日志 |
| error_rate | 失败任务占比 | 调度器 API |
| sla_compliance | 是否在 SLA 窗口内完成 | 调度器 + 策略引擎 |
| query_frequency | 数据集被查询的频率 | 查询审计日志 |

⚠️ 运营元数据的**时效性**是关键：过期 1 天的新鲜度指标等于没有。

## 5. 语义层设计：统一访问的抽象

### 5.1 语义层是什么

语义层是**用户查询与物理存储之间的翻译层**：
- 用户说"月度收入" → 语义层翻译为 `SUM(revenue.amount) WHERE month = current_month`
- 物理层可能是 PostgreSQL 的 `orders` 表 + Snowflake 的 `subscriptions` 表

### 5.2 语义层实现模式

| 模式 | 机制 | 代表产品 |
|---|---|---|
| 虚拟视图 | 在虚拟化层定义逻辑视图 | Denodo, Dremio |
| 语义模型文件 | YAML/JSON 定义度量与维度 | dbt Semantic Layer, Cube |
| 图驱动语义 | 知识图谱编码业务关系 | TopBraid, Informatica |
| SQL 映射层 | 重写 SQL 到多源 | Apache Calcite |

⚠️ 语义层的选择直接影响 fabric 的**用户体验**——好的语义层让业务用户感觉"只有一个数据库"。

## 6. 🔧 G2：SQLite ATTACH 两库做逻辑统一视图

> ⚠️ 非本书引擎/平台行为。SQLite 3.45.3 本机实测，类比数据虚拟化的"跨源逻辑统一访问"。

**场景**：两个独立 SQLite 数据库（`erp.db` 和 `crm.db`），通过 ATTACH 实现逻辑统一查询。

```sql
-- 主库连接
ATTACH DATABASE 'erp.db' AS erp;
ATTACH DATABASE 'crm.db' AS crm;

-- 跨库 UNION：统一客户视图
CREATE VIEW unified_customers AS
SELECT id, name, 'erp' AS source FROM erp.customers
UNION ALL
SELECT id, name, 'crm' AS source FROM crm.accounts;

-- 跨库查询
SELECT u.name, u.source, o.total
FROM unified_customers u
LEFT JOIN erp.orders o ON o.customer_id = u.id AND u.source = 'erp';
```

**实测数字**（8 万行跨库 UNION）：
- 跨库 UNION ALL 全量扫描：12ms（0 行搬运，纯逻辑）
- 窗口查询（ROW_NUMBER 分区）：18ms
- 带 WHERE 过滤的跨库 JOIN：8ms

**关键发现**：SQLite `:memory:` 模式**禁止跨 ATTACH 库建 VIEW**——必须使用文件模式。这恰好演示了"统一语义层落哪里"的工程约束：
- 内存库适合单源临时分析
- 文件库才能承载跨源语义层
- ⚠️ 真实 fabric 平台用独立的**元数据服务**承载语义层，不依赖任何单一数据源

**类比映射**：
| SQLite 概念 | Fabric 类比 |
|---|---|
| ATTACH DATABASE | 注册新数据源连接 |
| CREATE VIEW (跨库) | 语义层的逻辑视图定义 |
| UNION ALL | 联邦查询的合并策略 |
| 文件模式 vs 内存模式 | 持久化语义层 vs 临时查询会话 |

## 7. 统一访问层：从语义层到 API

fabric 的统一访问层通常提供三种消费接口：

| 接口 | 协议 | 适用消费者 |
|---|---|---|
| SQL 端点 | JDBC/ODBC | BI 工具、数据工程师 |
| REST/GraphQL API | HTTP | 应用开发者 |
| 数据服务 | gRPC / 消息 | 实时消费者 |

⚠️ 统一访问 ≠ 单一入口。fabric 提供**多协议适配**，但底层共享同一套元数据和语义层。

## 最新演进与工业实践

- **dbt Semantic Layer（2024 GA）**：以 YAML 定义度量/维度，暴露 GraphQL + SQL 双接口——语义层"代码化"趋势的代表。
- **Apache Calcite**：SQL 解析+重写引擎，被 Drill / Hive 等用作联邦查询内核——开源语义层基石。
- **OpenMetadata 1.x**：统一元数据平台，技术+业务+运营三态合一存储（PostgreSQL + ES）——社区方向。
- ⚠️ 语义层的"代码化 vs GUI 化"之争仍在继续——dbt 派主张 YAML + Git，传统厂商主张 GUI 拖拽。
