# 08 · 实施路径与平台选型

> ⚠️ 主题重构地图（取证声明见 [00 §1](00-总览与阅读地图.md)）。本章是"照着做"的最终落点——从评估到试点到扩展的路线图，以及商业/开源平台选型框架。与 [Data_Fabric_and_Data_Mesh_with_AI](../Data_Fabric_and_Data_Mesh_with_AI/00-总览与阅读地图.md)（#202）的 [10 章](../Data_Fabric_and_Data_Mesh_with_AI/10-数据治理与厂商供给.md) 互补：#202 讲厂商供给全景，本章讲**怎么选、怎么落地**。

## 1. 成熟度评估框架

### 1.1 五维评估模型

在启动 fabric 实施前，需在五个维度评估当前状态：

| 维度 | 初始（L1） | 发展（L2） | 成熟（L3） |
|---|---|---|---|
| 元数据管理 | 无/散落在 Wiki | 技术元数据自动采集 | 三态全覆盖 + 主动回路 |
| 数据集成 | 点对点 ETL | 中央 ETL 平台 | 事件驱动 + 按需物化 |
| 数据虚拟化 | 无 | 部分源有虚拟视图 | 统一语义层 |
| 治理 | 文档化策略 | 部分自动化 | 策略即代码 + 全量审计 |
| 组织 | IT 中心化 | 部分领域自治 | 联邦治理 + 数据产品 |

### 1.2 评估方法

1. **利益相关者访谈**（2–3 周）：CTO / 数据负责人 / 业务线代表
2. **技术栈盘点**：现有数据库 / ETL / BI / 数据目录清单
3. **痛点排序**：数据孤岛 / 重复搬运 / 质量事故 / 合规风险
4. **成熟度打分**：五维各打 1–3 分，识别最短板

⚠️ 评估的目的不是"得一个分数"，而是**识别第一个织点**——从哪里开始编织。

## 2. PoC 设计：最小可行 Fabric

### 2.1 PoC 范围选择

**原则**：选一个"痛但可控"的场景——足够痛以证明价值，足够可控以在 8–12 周内完成。

| 好的 PoC 场景 | 差的 PoC 场景 |
|---|---|
| 2–3 个源系统的联邦查询 | 全公司 50+ 系统接入 |
| 一个业务域的数据目录 | 全域数据目录 |
| 一条端到端血缘 | 全企业血缘 |
| 一个治理策略自动化 | 全部策略自动化 |

### 2.2 PoC Checklist

- [ ] 明确业务问题（"解决什么痛点"）
- [ ] 选定 2–3 个数据源
- [ ] 选定技术栈（参考 §4 选型框架）
- [ ] 定义成功标准（查询延迟 / 用户满意度 / 质量提升）
- [ ] 组建团队（数据工程师 + 业务代表 + 架构师）
- [ ] 建立 ADR 习惯（06 章模板）
- [ ] 规划 PoC → 生产的迁移路径

⚠️ PoC 最常见的失败原因不是技术问题，而是**没有明确的业务问题**——"为了 fabric 而 fabric"。

## 3. 扩展路线图：渐进式编织

### 3.1 三阶段路线

```
阶段 1（3–6 月）：基础织点
├── 元数据采集上线（技术元数据）
├── 数据目录 MVP（搜索 + 浏览）
├── 1–2 个虚拟化视图
└── 基础治理策略（访问控制）

阶段 2（6–12 月）：扩展编织
├── 业务元数据 + 术语表
├── 端到端血缘（列级）
├── 质量引擎上线
├── 主动元数据 MVP（告警回路）
└── 扩展到 5–10 个数据源

阶段 3（12–24 月）：智能 fabric
├── 知识图谱上线
├── 主动元数据全功能（推荐/自动分类）
├── 策略即代码（OPA/Cedar）
├── 联邦部署（如需要）
└── AI 增强（ML 驱动的质量/推荐）
```

### 3.2 扩展节奏控制

| 信号 | 含义 | 动作 |
|---|---|---|
| PoC 用户主动要求更多源 | 价值已证明 | 启动阶段 2 |
| 元数据质量投诉增多 | 采集覆盖过快 | 暂停扩展，修复质量 |
| 治理策略执行率 < 60% | 策略过多或过严 | 精简策略，加强培训 |
| 虚拟化查询性能投诉 | 需要物化优化 | 引入增量物化 |

## 4. 平台选型：商业与开源谱系

### 4.1 商业平台谱系

| 平台 | 核心定位 | fabric 覆盖度 | 适用场景 |
|---|---|---|---|
| Informatica (IDMC) | 全栈数据管理 | ★★★★★ | 大型企业、已有 Informatica 投资 |
| Denodo | 数据虚拟化核心 | ★★★★☆ | 虚拟化优先、Oracle 生态 |
| IBM (watsonx.data) | AI + fabric | ★★★★☆ | IBM 生态、AI 驱动 |
| Talend (Qlik) | 集成 + 质量 | ★★★☆☆ | 集成优先、中型企业 |
| SAP (Datasphere) | SAP 生态 fabric | ★★★☆☆ | SAP 重度用户 |

⚠️ 厂商宣称的"fabric 覆盖度"通常基于自家产品功能映射——**独立评估不可少**。

### 4.2 开源组件栈

| 组件 | 开源选择 | 成熟度 |
|---|---|---|
| 元数据存储 | OpenMetadata / DataHub | ★★★★ |
| 数据目录 | DataHub / Apache Atlas | ★★★★ |
| 数据虚拟化 | Trino / Dremio | ★★★★ |
| 数据集成 | Airbyte / Debezium + Airflow | ★★★★ |
| 质量引擎 | Great Expectations / Soda | ★★★ |
| 知识图谱 | Neo4j Community / Apache Jena | ★★★ |
| 策略引擎 | OPA | ★★★★★ |

⚠️ 开源栈的**集成成本**不可忽视——各组件独立演进，接缝需要自建。商业平台的溢价本质上包含"集成已完成"的价值。

> 🔧 DuckDB 演示（「非本书引擎行为」）：DuckDB 可作为 PoC 阶段的轻量 fabric 原型：
> ```sql
> -- 「非本书引擎行为」DuckDB 最小 fabric 原型
> ATTACH 'postgresql://host/prod' AS remote_prod (TYPE postgres);
> ATTACH 'csv:///data/dim.csv' AS dim_csv (TYPE csv);
> CREATE VIEW unified_customer AS
>   SELECT p.id, p.name, d.segment
>   FROM remote_prod.public.customer p
>   JOIN dim_csv.dim_customer d USING(id);
> ```
> 此演示展示"虚拟化优先"模式的最小实现——跨源联邦查询无需物理搬运。
> 🔧 SQLite 演示（「非本书引擎行为」）：SQLite 可用于 PoC 阶段的本地元数据存储原型：
> ```sql
> -- 「非本书引擎行为」SQLite 元数据存储原型
> CREATE TABLE datasets(id TEXT PRIMARY KEY, source TEXT, owner TEXT, pii BOOLEAN);
> CREATE TABLE lineage(upstream TEXT, downstream TEXT, transform TEXT);
> INSERT INTO lineage VALUES('src.customer','unified.customer','JOIN+project');
> SELECT * FROM lineage WHERE downstream LIKE '%customer%';
> ```

## 5. 自建 vs 购买决策框架

| 因素 | 倾向购买 | 倾向自建 |
|---|---|---|
| 团队规模 | < 10 人数据团队 | > 20 人数据团队 |
| 时间压力 | 需要 6 月内上线 | 可以 12+ 月迭代 |
| 定制需求 | 标准场景 | 高度定制化 |
| 预算 | 许可预算充足 | 许可预算有限，人力充足 |
| 技术栈 | 多厂商混合 | 统一技术栈偏好 |

⚠️ 多数组织的实际选择是**混合模式**：核心虚拟化/集成用商业产品，元数据/目录用开源，策略引擎用 OPA。

## 6. 实施风险清单

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| PoC 无法迁移到生产 | 高 | 高 | 从 PoC 第一天按生产标准建设 |
| 元数据采集覆盖率不足 | 高 | 中 | 优先覆盖核心数据源，不追求 100% |
| 组织抵制（"又一个平台"） | 中 | 高 | 选痛点最大的业务线做 champion |
| 性能不达预期 | 中 | 中 | 虚拟化 + 物化混合，性能基准测试前置 |
| 治理策略过度 | 中 | 中 | 从最少策略开始，逐步增加 |
| 厂商锁定 | 低 | 高 | 坚持开放标准（SQL/ICEBERG/OpenLineage） |

## 最新演进与工业实践

- **fabric 平台整合趋势**（2024–2025）：Informatica + Tabular（Iceberg）、Qlik + Talend——大厂通过并购补齐 fabric 全栈。
- **"fabric-lite" 运动**：中小型组织不追求"完整 fabric"，而是用 Trino + DataHub + dbt 搭建"最小 fabric"——成本降一个数量级。
- **AI 辅助选型**（⚠️ 早期）：用 LLM 分析组织技术栈和需求，自动推荐 fabric 组件组合——准确率待验证。
- **Data Mesh 作为 fabric 的组织补充**：越来越多组织在技术层选 fabric、在组织层选 mesh——"技术集中、组织联邦"的混合模式。
- ⚠️ fabric 实施的最大风险始终是**组织问题**而非技术问题——"谁 owns 元数据""谁为质量负责"比"选哪个引擎"重要 10 倍。
- **跨册参照**：#210 09 章（落地路径理论基础）与 #202 08 章（混合云两条路线）为选型提供架构层视角；#209 学术体裁中的参考架构模式为平台评估提供学理框架。
- **Iceberg 作为开放存储事实标准**（2025）：Apache Iceberg 的 tabular 被 Informatica 收购后，开放表格式成为 fabric 物化层的默认选择——厂商锁定风险从"平台层"下移到"存储层"（⚠️ 趋势转述）。
