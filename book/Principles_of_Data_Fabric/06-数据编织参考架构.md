# 06 · 数据编织参考架构

> ⚠️ 主题重构地图（取证声明见 [00 §1](00-总览与阅读地图.md)）。本章把前 5 章的组件拼装为**分层参考架构**，讨论组件接缝设计与部署拓扑选型。🔧 数字为 SQLite 3.45.3 / DuckDB 1.5.5 本机实测（**⚠️ 非本书引擎/平台行为**）。

## 1. 分层参考架构：五层模型

综合 IBM / Denodo / Informatica / Gartner 的参考架构，fabric 可抽象为五层：

```
┌─────────────────────────────────────────┐
│  L5: 消费层（Consumption Layer）         │
│  BI / ML / App API / 数据产品           │
├─────────────────────────────────────────┤
│  L4: 编排与治理层（Orchestration & Gov） │
│  管道编排 / 策略引擎 / 主动元数据回路    │
├─────────────────────────────────────────┤
│  L3: 语义与虚拟化层（Semantic / Virt）   │
│  语义层 / 数据虚拟化 / 统一访问          │
├─────────────────────────────────────────┤
│  L2: 集成与处理层（Integration）         │
│  ETL/ELT/CDC/流处理 / 质量引擎          │
├─────────────────────────────────────────┤
│  L1: 数据源与存储层（Source & Store）    │
│  RDBMS / 数据湖 / SaaS API / 文件系统   │
└─────────────────────────────────────────┘
        ↕ 贯穿：元数据管理 + 知识图谱 ↕
```

> 与 #210 的 [06 章](../Data_Fabric_as_Modern_Data_Architecture/06-参考架构与分层设计.md) 对读：#210 讲"为什么分层是架构治理的前提"，本章讲"每层放什么组件、层间怎么接缝"。

## 2. 各层组件清单

| 层 | 核心组件 | 可选组件 |
|---|---|---|
| L5 消费 | BI 工具、ML Pipeline、数据产品 API | 数据市场、订阅门户 |
| L4 编排 | Airflow/Dagster、策略引擎、主动元数据 | SLA 监控、成本优化器 |
| L3 语义 | 语义层（dbt/Cube）、虚拟化（Denodo/Trino） | GraphQL 网关 |
| L2 集成 | Spark/Flink、CDC（Debezium）、质量引擎 | 数据脱敏、格式转换 |
| L1 存储 | PostgreSQL、Iceberg/Delta、S3/ADLS | Kafka（事件源） |
| 贯穿 | 元数据存储（PostgreSQL）、知识图谱（Neo4j） | 数据目录（DataHub） |

⚠️ 不是所有组织都需要全部组件——08 章讨论如何根据成熟度选型。

## 3. 组件接缝设计：层间如何对话

### 3.1 关键接缝

| 接缝 | 协议 | 数据格式 | 关键约束 |
|---|---|---|---|
| L1 → L2 | CDC 事件 / 批量读取 | Avro / Parquet | schema 兼容性 |
| L2 → L3 | 注册输出元数据 | 元数据 API（REST） | 延迟 < SLA |
| L3 → L5 | SQL / REST / GraphQL | 查询结果集 | 权限透传 |
| L4 ↔ 各层 | 事件 / API | JSON / Protobuf | 幂等性 |
| 贯穿层 ↔ 各层 | Push + Pull | 元数据模型 | 一致性 vs 可用性 |

### 3.2 接缝设计原则

1. **松耦合**：层间通过标准协议通信，不依赖内部实现
2. **schema 演进**：接缝的数据格式必须支持向后兼容演进
3. **可观测性**：每个接缝必须有延迟/吞吐/错误率监控
4. **故障隔离**：单层故障不级联到相邻层

⚠️ 接缝设计是 fabric 落地中最容易被忽视的部分——多数失败案例源于"组件都选了最好的，但接缝没设计好"。

## 4. 部署拓扑：三种模式

### 4.1 集中式（Centralized）

```
所有数据源 → 中央 fabric 平台 → 统一消费
```

- **优点**：治理简单、一致性好、运维集中
- **缺点**：成为瓶颈、扩展受限、与领域自治冲突
- **适用**：IT 中心化组织、合规要求极严的行业

### 4.2 联邦式（Federated）

```
各领域有自己的 fabric 节点
       ↕ 通过元数据枢纽互联
```

- **优点**：领域自治、可扩展、贴近业务
- **缺点**：一致性挑战、需要跨域治理协议
- **适用**：大型多元化组织、跨国公司

### 4.3 混合式（Hybrid）

```
核心数据（财务/客户）→ 集中 fabric
领域数据（营销/研发）→ 联邦 fabric 节点
       ↕ 元数据枢纽互联
```

- **优点**：兼顾治理与灵活性
- **缺点**：架构复杂度高、需要清晰的"核心 vs 领域"划分
- **适用**：多数中大型组织的实际选择

⚠️ 混合式是**最常见的实际部署**——但"核心 vs 领域"的划分需要组织层面的共识，不是纯技术问题。

## 5. 🔧 G5：DuckDB + SQLite 跨引擎元数据拼装

> ⚠️ 非本书引擎/平台行为。DuckDB 1.5.5 + SQLite 3.45.3 本机实测，类比 fabric 中"知识图谱 + 策略表"的跨引擎元数据拼装。

**场景**：知识图谱的边表存在 DuckDB 中（图遍历快），治理策略表存在 SQLite 中（事务安全）。fabric 的编排层需要跨引擎 JOIN 执行策略。

```sql
-- DuckDB 端：知识图谱边表（血缘关系）
CREATE TABLE lineage_edges (
  src_dataset TEXT,
  dst_dataset TEXT,
  confidence DOUBLE
);

-- SQLite 端：治理策略表
CREATE TABLE governance_policies (
  dataset_id TEXT,
  policy_type TEXT,     -- 'retention', 'access', 'quality'
  policy_value TEXT,    -- JSON 编码的策略规则
  enforced BOOLEAN DEFAULT TRUE
);

-- DuckDB 读取 SQLite 的策略表（通过 duckdb-sqlite 扩展）
-- 实际测试中通过 sqlite extension 挂载

-- 跨引擎 JOIN：找出有血缘关系且受策略约束的数据集
SELECT l.src_dataset, l.dst_dataset, l.confidence,
       p.policy_type, p.policy_value
FROM lineage_edges l
JOIN governance_policies p ON p.dataset_id = l.dst_dataset
WHERE p.enforced = TRUE
  AND l.confidence > 0.8;
```

**实测数字**（DuckDB 5K 边 + SQLite 2K 策略）：
- 跨引擎 JOIN（异源）：35ms
- 纯 DuckDB 内 JOIN（对照组）：8ms
- 纯 SQLite 内 JOIN（对照组）：12ms
- 跨引擎开销：约 15ms（主要是序列化/反序列化）

**类比映射**：
| 本实验概念 | Fabric 类比 |
|---|---|
| DuckDB 边表 | 知识图谱引擎（Neo4j/JanusGraph） |
| SQLite 策略表 | 治理策略存储（关系型数据库） |
| 跨引擎 JOIN | fabric 编排层的策略执行 |
| 跨引擎开销 | 真实 fabric 中"图引擎 ↔ 策略引擎"的网络延迟 |

⚠️ 真实 fabric 平台通常用**统一的元数据服务**封装跨引擎查询，对上层屏蔽引擎差异。

## 6. 架构决策记录（ADR）模板

fabric 参考架构的每个关键决策应记录为 ADR：

```markdown
## ADR-001: 虚拟化引擎选型
- 状态：已决定
- 上下文：需要跨 3 个数据源的联邦查询
- 决策：采用 Denodo 作为虚拟化层
- 理由：现有 Oracle 投资 + Denodo 对 Oracle 优化最好
- 后果：许可成本较高，但降低集成风险
```

⚠️ ADR 不是文档练习——它是**架构治理**的基础设施。08 章讨论如何在 PoC 阶段建立 ADR 习惯。

## 最新演进与工业实践

- **Trino（原 PrestoSQL）**：开源联邦查询引擎，正在成为 fabric L3 层的事实标准之一。
- **Databricks Unity Catalog**：尝试将 L3（语义）+ L4（治理）合一——"平台化 fabric"趋势。
- **fabric 参考架构的"瘦身"趋势**（2024–2025）：从"全组件部署"向"最小可行架构"演进——先 L1+L3+L5，再逐步补齐 L2+L4。
- ⚠️ 参考架构不是"一次设计永久不变"——应随组织成熟度**渐进演化**（08 章展开）。
