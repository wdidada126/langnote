# 04 · 数据集成与编排模式

> ⚠️ 主题重构地图（取证声明见 [00 §1](00-总览与阅读地图.md)）。本章覆盖 fabric 中数据集成与管道编排的工程模式。02 章定义了"数据集成"组件边界，本章深入其内部实现。

## 1. 集成模式谱系：从批量到事件

Data fabric 不排斥物理搬运——当虚拟化性能不足时，需要选择合适的集成模式：

```
延迟 ↑
  毫秒级  │  事件驱动（CDC → Kafka → Consumer）
  秒级    │  流式 ELT（Flink/Spark Streaming → Iceberg）
  分钟级  │  微批 CDC（Debezium → 目标）
  小时级  │  批量 ETL（Spark/Airflow DAG）
  天级    │  文件传输（SFTP / 对象存储复制）
          └──────────────────────────────→ 吞吐量 →
```

⚠️ 选择标准不是"越实时越好"，而是**消费者 SLA × 源端容忍度 × 成本**的三角平衡。

## 2. ETL vs ELT：架构决策矩阵

| 维度 | ETL（先转换后加载） | ELT（先加载后转换） |
|---|---|---|
| 转换位置 | 中间服务器/Spark 集群 | 目标仓库内部 |
| 目标要求 | 可以是任意存储 | 需要**有计算能力**的存储（云仓/湖） |
| Schema 演进 | 管道需同步修改 | 原始数据保留，转换可后改 |
| 适用规模 | 中小批量 | 大规模/原始数据湖 |
| 代表工具 | Informatica, Talend | dbt, Fivetran, Airbyte |

⚠️ 现代 fabric 中 ELT 已成主流——但 ETL 在合规场景（如 PII 必须在加载前脱敏）仍不可替代。

## 3. CDC（变更数据捕获）：实时集成的基石

### 3.1 CDC 三种实现

| 方式 | 机制 | 优缺点 |
|---|---|---|
| 基于日志 | 读取数据库 WAL/binlog | ✅ 低侵入、低延迟；⚠️ 依赖数据库支持 |
| 基于查询 | 定时 SELECT WHERE updated_at > last | ✅ 通用；⚠️ 有延迟、漏变更风险 |
| 基于触发器 | 数据库触发器写入变更表 | ✅ 精确；⚠️ 性能开销大、侵入性强 |

### 3.2 CDC 在 fabric 中的角色

CDC 是**运营元数据**的重要来源（03 章）：
- 每次 CDC 事件携带时间戳 → 驱动新鲜度指标
- CDC 延迟监控 → 驱动 SLA 告警
- CDC schema 变更检测 → 驱动元数据自动更新

→ 05 章"主动元数据"的很多输入来自 CDC 管道。

## 4. 事件驱动集成：从解耦到实时

事件驱动模式在 fabric 中承担**异步解耦**和**实时响应**双重角色：

### 4.1 核心模式

| 模式 | 说明 | fabric 应用 |
|---|---|---|
| Event Sourcing | 以事件序列为事实源 | 血缘记录、审计日志 |
| CQRS | 读写分离 | 目录搜索索引 vs 元数据存储 |
| Saga | 分布式事务协调 | 跨系统数据同步 |

### 4.2 消息中间件选型

| 中间件 | 语义 | 适用场景 |
|---|---|---|
| Apache Kafka | 持久化日志、消费者组 | 高吞吐 CDC 事件流 |
| Apache Pulsar | 多租户、分层存储 | 跨团队 fabric |
| RabbitMQ | 路由灵活 | 低吞吐告警/通知 |
| NATS | 超低延迟 | 实时告警/触发 |

## 5. 管道编排：从 DAG 到声明式

### 5.1 编排引擎演进

| 代际 | 代表 | 模型 |
|---|---|---|
| 第一代 | Cron + Shell | 时间触发、无依赖图 |
| 第二代 | Airflow | Python DAG、任务依赖 |
| 第三代 | Dagster / Prefect | 软件工程化（类型/测试/CI） |
| 声明式 | dbt + orchestrator | SQL-first、编排器只管调度 |

### 5.2 Fabric 中的编排定位

⚠️ Fabric 通常**不自带编排引擎**——而是通过元数据回路**驱动**编排引擎：
1. 元数据变更 → 触发编排器重跑受影响管道
2. SLA 违规 → 编排器提升优先级
3. 新数据集注册 → 编排器自动添加质量检查任务

→ 这是 05 章"主动元数据"驱动编排的具体场景。

## 6. 幂等性与重试：工程纪律

fabric 中的管道必须满足**幂等性**——同一输入多次执行产生相同输出：

| 策略 | 机制 | 适用场景 |
|---|---|---|
| INSERT OR REPLACE | 覆盖写入 | 全量刷新表 |
| MERGE / UPSERT | 按主键合并 | 增量更新 |
| 分区覆盖 | 按日期分区重写 | 时间序列数据 |
| 事务性写入 | 原子提交 | 一致性要求高的场景 |

**重试策略**：
- 指数退避（exponential backoff）：1s → 2s → 4s → 8s
- 最大重试次数：通常 3–5 次
- 死信队列（DLQ）：超过重试上限的事件进入 DLQ 等待人工处理

⚠️ 幂等性不是可选的——fabric 的自动化回路会**自动重跑管道**，非幂等管道会导致数据重复或丢失。

## 7. 模式对比总结

| 模式 | 延迟 | 吞吐 | 复杂度 | fabric 角色 |
|---|---|---|---|---|
| 批量 ETL | 高 | 高 | 低 | 历史数据加载 |
| 流式 ELT | 中 | 高 | 中 | 湖仓持续摄入 |
| CDC | 低 | 中 | 中 | 准实时同步 |
| 事件驱动 | 极低 | 可变 | 高 | 实时响应/解耦 |

## 核心概念速览（中英对照）

| 中文 | English | 一句话 |
|---|---|---|
| 变更数据捕获 | Change Data Capture (CDC) | 捕获数据库增量变更的技术 |
| 事件驱动集成 | Event-Driven Integration | 以事件消息解耦数据生产与消费 |
| 管道编排 | Pipeline Orchestration | 管理任务依赖与调度的引擎 |
| 幂等性 | Idempotency | 多次执行产生相同结果的性质 |
| 指数退避 | Exponential Backoff | 重试间隔逐次翻倍的策略 |
| 死信队列 | Dead Letter Queue (DLQ) | 超过重试上限的事件暂存区 |
| DAG | Directed Acyclic Graph | 有向无环图，编排引擎的任务依赖模型 |

## 最新演进与工业实践

- **Apache Airflow 2.x / 3.0**：引入 dynamic task mapping、Stream execution——向流式编排演进。
- **dbt + Airflow/Dagster**：dbt 管转换逻辑、编排器管调度——"声明式 + 命令式"混合模式成为主流。
- **Debezium 2.x**：CDC 连接器覆盖更多数据库（MongoDB、Cassandra），Schema 变更自动传播。
- **Fivetran/Airbyte**：ELT 自动化——"零代码"数据复制，降低集成门槛但增加黑盒风险。
- ⚠️ 编排引擎选型是 fabric 落地中最常见的**争论点**——本目录建议以"团队已有技能栈"为第一优先级。
