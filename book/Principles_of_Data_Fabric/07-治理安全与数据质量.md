# 07 · 治理安全与数据质量

> ⚠️ 主题重构地图（取证声明见 [00 §1](00-总览与阅读地图.md)）。本章聚焦 fabric 中治理、安全、数据质量的工程实现——"治理内建而非外挂"原则的落地。与 [Data_Governance_Elsevier](../Data_Governance_Elsevier/00-总览与阅读地图.md)（#186）互补：#186 讲治理的制度设计与流程，本章讲治理的**代码化实现**。

## 1. 治理内建：从"事后审计"到"管道嵌入"

### 1.1 传统治理 vs fabric 治理

| 维度 | 传统治理 | Fabric 治理 |
|---|---|---|
| 执行时机 | 事后审计（季度/年度） | **管道内实时执行** |
| 策略形式 | Word/Excel 文档 | **可执行代码（Policy-as-Code）** |
| 执行主体 | 治理委员会人工审批 | 策略引擎自动裁决 |
| 变更周期 | 月级 | 分钟级（CI/CD 发布策略） |
| 覆盖范围 | 抽样 | **全量** |

⚠️ "内建"不意味着取消治理委员会——委员会制定策略，策略引擎自动执行。

## 2. 策略即代码（Policy-as-Code）

### 2.1 策略生命周期

```
定义（YAML/DSL）→ 版本控制（Git）→ 测试（单元测试）
    → 审批（PR Review）→ 部署（CI/CD）→ 执行（策略引擎）
    → 监控（策略命中率）→ 迭代
```

### 2.2 策略 DSL 示例

```yaml
# 数据保留策略
- name: "eu_data_retention"
  scope:
    datasets:
      region: "eu"
  rules:
    - type: "retention"
      max_age_days: 90
      action: "archive"  # archive | delete | alert
    
    - type: "access"
      condition: "pii == true"
      require: ["rbac:eu_dpo", "purpose:analytics"]
      
    - type: "quality"
      min_freshness_hours: 24
      on_violation: "alert_steward"
```

### 2.3 策略引擎选型

| 引擎 | 语言 | 适用场景 |
|---|---|---|
| Open Policy Agent (OPA) | Rego | 通用策略引擎，云原生生态 |
| AWS Cedar | Cedar | AWS 生态，细粒度访问控制 |
| 自研 DSL | YAML/Python | 与 fabric 元数据深度集成 |

⚠️ OPA 是最广泛采用的开源策略引擎——但 fabric 场景的策略通常与**元数据**强耦合（如"PII 列的访问需要特定角色+特定目的"），需要策略引擎能查询元数据存储。

## 3. 访问控制模型

### 3.1 三种模型对比

| 模型 | 机制 | 粒度 | 适用场景 |
|---|---|---|---|
| RBAC（基于角色） | 用户 → 角色 → 权限 | 粗粒度 | 组织结构稳定的企业 |
| ABAC（基于属性） | 用户属性 + 资源属性 → 策略裁决 | 细粒度 | 合规要求高的场景 |
| ReBAC（基于关系） | 用户与资源的**关系**决定权限 | 上下文感知 | 协作文档、数据共享 |

### 3.2 Fabric 中的访问控制层次

```
L1: 数据集级（谁能看哪张表）
L2: 列级（谁能看 PII 列）
L3: 行级（谁能看哪个区域的数据）
L4: 动态脱敏（同一列，不同角色看到不同格式）
```

⚠️ Fabric 的虚拟化层（L3）是实施列级/行级控制的**最佳位置**——查询在虚拟化层被拦截和改写，不需要修改底层存储。

### 3.3 血缘与审计

完整的访问审计需要：
- **谁**（who）：用户身份 + 认证方式
- **访问了什么**（what）：数据集 + 列 + 行范围
- **何时**（when）：时间戳
- **为什么**（why）：关联的业务目的（ABAC 的 purpose 属性）
- **血缘链路**（lineage）：数据从源到消费的完整路径

→ 05 章的知识图谱提供血缘查询能力，此处用于审计。

## 4. 数据质量规则引擎

### 4.1 质量维度

| 维度 | 含义 | 检测方式 |
|---|---|---|
| 完整性（Completeness） | NULL 率、缺失率 | 列级统计 |
| 准确性（Accuracy） | 值域合规、引用完整性 | 规则匹配 |
| 一致性（Consistency） | 跨源数据一致 | 跨源比对 |
| 时效性（Timeliness） | 数据新鲜度 | 时间戳检查 |
| 唯一性（Uniqueness） | 重复率 | 去重检查 |
| 有效性（Validity） | 格式/范围合规 | 正则/范围规则 |

### 4.2 质量规则分层

| 层级 | 规则类型 | 执行时机 | 违规动作 |
|---|---|---|---|
| L0 基础 | NOT NULL, 类型检查 | 写入时 | 拒绝写入 |
| L1 业务 | 值域范围、引用完整性 | 写入后/批检查 | 告警 + 隔离 |
| L2 统计 | 分布偏移、异常值检测 | 定期扫描 | 告警 + 暂停下游 |
| L3 跨源 | 源间一致性比对 | 日级/周级 | 报告 + 人工审查 |

### 4.3 质量引擎实现模式

| 模式 | 代表工具 | 特点 |
|---|---|---|
| SQL 规则 | Great Expectations, dbt test | SQL 表达式定义规则 |
| DSL 规则 | Soda, Monte Carlo | 自定义 DSL 定义检查 |
| ML 检测 | 自动异常检测 | 无需手写规则，但需训练数据 |

⚠️ 质量引擎应嵌入管道（L2 层），而非独立运行——否则"检测到了但没人处理"等于没有检测。

> 🔧 DuckDB 演示（「非本书引擎行为」）：DuckDB 可作为轻量质量规则执行引擎：
> ```sql
> -- 「非本书引擎行为」DuckDB 质量检查
> SELECT COUNT(*) FILTER(WHERE col IS NULL)*100.0/COUNT(*) AS null_pct FROM t;
> SELECT pk, COUNT(*) AS dup FROM t GROUP BY pk HAVING COUNT(*)>1;
> ```
> 生产级用 Great Expectations / Soda Core，DuckDB 适合 PoC 验证规则逻辑。

## 5. 血缘审计：端到端可追溯

血缘审计是治理的**法律合规基础**（GDPR、SOX、BCBS 239 等）：

### 5.1 血缘粒度

| 粒度 | 说明 | 实现成本 |
|---|---|---|
| 表级 | 表 A → 表 B | 低（管道级日志即可） |
| 列级 | 表 A.col_x → 表 B.col_y | 中（需 SQL 解析） |
| 行级 | 特定行的完整变换历史 | 高（需 event sourcing） |
| 值级 | 特定值的计算过程 | 极高（需 lineage cache） |

⚠️ 多数合规要求**列级血缘**即可——行级/值级仅在金融风控等极端场景需要。

### 5.2 血缘审计的工程实现

```
SQL 解析器（如 sqlglot / calcite）
    → 提取表/列引用
    → 写入血缘图（05 章知识图谱）
    → 策略引擎查询血缘图
    → 生成审计报告
```

## 核心概念速览（中英对照）

| 中文 | English | 一句话 |
|---|---|---|
| 策略即代码 | Policy-as-Code | 治理策略以可执行代码形式管理 |
| RBAC | Role-Based Access Control | 基于角色的访问控制 |
| ABAC | Attribute-Based Access Control | 基于属性的访问控制 |
| 数据质量 | Data Quality | 数据满足预期用途的程度 |
| 血缘审计 | Lineage Audit | 数据从源到消费的完整路径追踪 |
| 动态脱敏 | Dynamic Masking | 根据角色实时改写敏感数据 |
| 策略引擎 | Policy Engine | 自动裁决访问/治理策略的组件 |
| 数据可观测性 | Data Observability | 质量/新鲜度/血缘/成本的统一监控 |
| ReBAC | Relationship-Based Access Control | 基于实体间关系的上下文感知权限 |

## 最新演进与工业实践

- **OPA + Cedar 生态**（2024–2025）：策略即代码从"DevOps 圈"向"数据治理圈"渗透——数据策略与基础设施策略统一引擎趋势。
- **Great Expectations / Soda**：数据质量引擎走向"测试化"——像写单元测试一样写数据质量规则。
- **Monte Carlo**：数据可观测性（Data Observability）平台——将质量/新鲜度/血缘/成本统一监控。
- **GDPR/中国《数据安全法》执法趋势**：血缘审计从"最佳实践"变为**法律义务**——fabric 的治理层不再是可选项。
- ⚠️ 治理过度是真实风险——规则太多导致"策略疲劳"，反而降低合规水平。
- **跨册参照**：#186 Data_Governance_Elsevier 提供治理制度设计的基本功；#210 08 章讲治理五维与可观测性的架构原理；#202 10 章提供治理内建论的厂商视角。
- **Unity Catalog（2025）**：Databricks 将 RBAC+ABAC 内建于湖仓层，fabric 治理的工程门槛进一步下降——但"内建"不等于"自动"，策略仍需人工定义（⚠️ 趋势转述）。
