# 第 5 章　数据分析

> 原书第 5 章是「数据怎么变成决策」：日志收集（inotify/ActiveMQ-CPP/Chukwa）、离线分析
> （Hadoop/MapReduce/Hive）、流式分析（Storm）、数据同步（离线与实时）、数据报表（Highcharts）。
> 这一章是**技术栈换代最猛**的一章：MapReduce/Storm/Chukwa 几乎都被 Spark/Flink/Iceberg 取代，
> 批流一体的理念（Beam）彻底改写了「离线 vs 流式」二分法。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 5.1 日志收集：先把数据收上来

- **inotify 机制**（5.1.1）：Linux 内核提供的文件系统事件通知（文件新增/修改），
  收集 agent 监听日志目录，文件变更即推送。
- **架构和存储**（5.1.3）：收集 agent → 消息/队列缓冲 → 落地 HDFS/存储。消息系统在此复用
  [02](02-分布式系统基础设施.md) 的 ActiveMQ（2026 视角见下）。
- **Chukwa**（5.1.4）：构建于 Hadoop 之上的日志收集系统（今日已停止活跃开发）。

### 5.2 离线数据分析：批处理

- **Hadoop/MapReduce**（5.2.1–5.2.3）：核心思想是「移动计算而非移动数据」——
  把计算分发到数据所在的节点，map（映射）+ reduce（归约）两阶段。

```text
# 教学示意，不参与构建：WordCount 的 MapReduce 骨架
map(line):
    for word in line.split():  emit(word, 1)
reduce(word, counts):
    emit(word, sum(counts))
# 框架负责: 分区/排序/洗牌(shuffle)/容错
```

- **Hive**（5.2.4）：把 SQL 翻译成 MapReduce（今多为 Tez/Spark 引擎），让分析师用 SQL 而非 Java
  跑批处理；这是「SQL on Hadoop」的开端。

### 5.3 流式数据分析：实时

- **Storm**（5.3）：以「拓扑（topology）」描述数据流，spout 接数据源、bolt 做处理，
  数据逐条（tuple）流经处理链，实现秒级实时计算。本书 2014 年的流式默认选型。

### 5.4 数据同步

- **离线同步**：定时把业务库数据抽到数仓（如 Sqoop 式全量/增量）。
- **实时同步**：用 CDC（变更数据捕获，如 binlog 订阅）把库变更近乎实时同步到下游
  （搜索索引/缓存/数仓），是「业务库 → 多消费方」的关键管道。

### 5.5 数据报表

- **报表能提供什么**（5.5.1）：核心指标、趋势、对比、下钻；服务于运营/风控/产品决策。
- **Highcharts**（5.5.2）：前端图表库，把数据渲染成折线/柱状/饼图等。

## 版本演进

- **本书无第二版**；本节写 2014 年口径 → 2026 年视角的变化。
- **5.2 离线：MapReduce → Spark**：`apache/spark`（44057★）以内存计算 + DAG 取代
  MapReduce 的磁盘反复读写，快 1–2 个数量级；Hive 的引擎也从 MR 切到 Spark/Tez。
- **5.3 流式：Storm → Flink**：`apache/flink`（26367★）以**精确一次（exactly-once）**语义、
  事件时间与水位、流批统一 API 取代 Storm（`apache/storm` 6695★，今多用于存量）；
  本书的「流式 vs 离线」二分被打破。
- **5.4 同步：CDC + Kafka 化**：实时同步从自研变为 Debezium + `apache/kafka`（33850★）
  的 binlog 流，对应 [02 章](02-分布式系统基础设施.md) 消息系统补丁。
- **5.1 收集：Chukwa → 现代管道**：`apache/flume`、Filebeat（Elastic）+ Kafka +
  `apache/spark`/`apache/flink` 消费，形成标准「采集→队列→计算」链。
- **5.5 报表 → 湖仓 + BI**：报表底层演进为**湖仓一体**（Iceberg/Delta/Hudi 表格式），
  配合 Superset/Metabase 等 BI；Highcharts 退居前端组件。

## 近年研究与工业界开源实践（2015–2026）

- **离线计算**：`apache/spark`（44057★）主导；`apache/hadoop`（15669★）退居存储（HDFS）与遗留批处理；
  `apache/hive`（6027★）作为元数据/SQL 层存续，引擎切到 Spark/Tez。
- **流式计算**：`apache/flink`（26367★）主导；`apache/storm`（6695★）存量。
- **批流一体**：`apache/beam`（8674★）用统一 API 表达批与流（底层跑 Spark/Flink），
  把本书「5.2 离线 vs 5.3 流式」的分裂范式收口。
- **湖仓表格式**：Iceberg/Delta/Hudi（2026 主流）成为报表与分析的存储层，配合 `apache/spark` 写、
  `apache/flink` 流读，取代「数仓分层靠脚本同步」的旧模式。
- **同步/采集**：`apache/kafka`（33850★）是 5.1/5.4 的缓冲与实时同步中枢；
  CDC（Debezium）把业务库变更实时化为事件流。
- **可观测与数据质量**：本章未涉及「数据血缘/质量/治理」，2026 年由 DataHub/Amundsen 等补位
  （超出本书范围，列入缺口）。

## 常见误区与本书需修正之处

| # | 误区 | 事实 | 书目 |
| --- | --- | --- | --- |
| 1 | 「MapReduce 还能写新业务」 | 新项目几乎都用 Spark/Flink；MR 仅存量与教学 | 5.2 |
| 2 | 「离线/流式是两套路」 | 批流一体（Beam/Flink）已统一编程模型 | 5.2–5.3 |
| 3 | 「Storm 是流式默认」 | 2026 默认 Flink（精确一次、事件时间） | 5.3 |
| 4 | 「Hive 就是 MapReduce」 | Hive 是 SQL 层，引擎可切 Spark/Tez，与 MR 解耦 | 5.2.4 |
| 5 | 「日志收集=写脚本」 | 需 agent + 队列 + 容错 + 背压的标准管道 | 5.1 |

| 7 | 🔧 5.2 缺 Spark | MapReduce 已被 Spark 内存计算取代，速度数量级提升 | 5.2 |
| 8 | 🔧 5.3 缺 Flink/精确一次 | Storm 的 at-least-once 不足，Flink 精确一次成主流 | 5.3 |
| 9 | 🔧 5.4 缺 CDC/Kafka 化同步 | 实时同步靠 binlog→Kafka→消费方，非定时抽数 | 5.4 |
