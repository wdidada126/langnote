# 第 2 章　分布式系统基础设施

> 原书第 2 章是「数据往哪放、消息怎么传、内容怎么搜」的技术底座：分布式缓存（memcache）、
> 持久化存储（MySQL 扩展、HBase、Redis）、消息系统（ActiveMQ/JMS）、垂直化搜索引擎（Lucene/Solr）。
> 这一章是**最容易被 2026 年现实改写**的一章：memcache 基本被 Redis 取代，ActiveMQ 在大数据管道里
> 被 Kafka 取代，Solr 在大多数场景被 Elasticsearch 取代。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 2.1 分布式缓存：把热数据挡在数据库前面

- **memcache 的分布式**（2.1.2）：客户端用 `hash(key) % N` 选节点；扩容时 N 变化导致大量 key
  重新映射、缓存集体失效（「缓存雪崩」）。本书强调用**一致性哈希**缓解——
  节点变化只迁移相邻区间的数据。

```text
# 教学示意，不参与构建：一致性哈希 vs 取模
取模:    node = hash(key) % N        -> N 变化时 ~100% key 重映射 -> 雪崩
一致性哈希: 环上按 hash 取顺时针最近节点 -> N 变化时只迁移 1/N 的 key
```

- **分布式 session**（2.1.3）：用户登录态不能只存单机内存（否则负载均衡到另一台就掉登录）。
  解法：session 存入集中缓存（memcache/Redis），或客户端 cookie 携带（签名防篡改）。

### 2.2 持久化存储：三类存储各司其职

| 存储 | 适用 | 关键权衡 |
| --- | --- | --- |
| MySQL 扩展 | 强一致、事务、结构化 | 单机有上限 → 需分库分表/读写分离（本书「MySQL 扩展」即此） |
| HBase | 海量、稀疏、按 rowkey 范围 | 列式、LSM、无强事务，吞吐高、延迟低 |
| Redis | 高速 KV、缓存、简单结构 | 内存级速度，可持久化；本书把它放在「持久化存储」与「缓存」双场景 |

- **MySQL 扩展**（2.2.1）：垂直分库（按业务）、水平分表（按 key 取模/按时间）、读写分离
  （主写从读）。本质是「单机装不下，就拆」。
- **Redis**（2.2.3）：内存数据结构（string/hash/list/set/zset），既当缓存也当轻量存储；
  这是它比 memcache（只 KV）更强的点。

### 2.3 消息系统：用队列把「同步」变「异步」

- **ActiveMQ & JMS**（2.3.1）：JMS 定义点对点（Queue）与发布订阅（Topic）两种模型。
  消息系统的价值：解耦（生产者不关心谁消费）、削峰（突发流量进队列慢慢处理）、异步（主流程不必等）。

```text
# 教学示意，不参与构建：削峰填谷
正常:   下单 -> 直接写库  (QPS 1000 扛得住)
大促:   下单 -> 发消息到 MQ -> 消费者按自己节奏落库 (MQ 缓冲了瞬时洪峰)
```

### 2.4 垂直化搜索引擎：站内搜索的底座

- **Lucene**（2.4.1–2.4.2）：核心数据结构是**倒排索引**（term → 文档列表）。写入时分词建索引，
  查询时查倒排拿文档。这是一切搜索引擎的内核。
- **Solr**（2.4.3）：在 Lucene 之上提供 HTTP 接口、分布式、高亮、 facet 等服务能力，
  让 Lucene 从「库」变成「搜索服务」。

```text
# 教学示意，不参与构建：倒排索引一眼懂
文档1: "淘宝 分布式 架构"
文档2: "分布式 缓存 设计"
倒排:
  淘宝 -> [1]
  分布式 -> [1, 2]
  架构 -> [1]
  缓存 -> [2]
  设计 -> [2]
查询 "分布式" -> 命中 [1,2]
```

## 版本演进

- **本书无第二版**；本节写 2014 年口径 → 2026 年视角的变化。
- **2.1 memcache → Redis 主导**：`redis/redis`（76487★）几乎通吃缓存场景，
  memcache（`memcached/memcached`，14285★）退居存量；Redis 的丰富数据结构让「缓存」能承担更多。
- **2.2 MySQL 扩展 → 云数据库 + 分布式中间件**：分库分表从手工（书里的方式）演进到
  ShardingSphere、Vitess（`vitessio/vitess`），再到云厂商的托管型分布式数据库
  （PolarDB / TiDB / OceanBase，见仓库 ../分布式数据库入门进阶与实战/）。
- **2.3 ActiveMQ → Kafka 主导大数据管道**：`apache/kafka`（33850★）以「日志即事实源」的
  高吞吐模型成为流处理底座；ActiveMQ（`apache/activemq`，2464★）多用于传统企业 JMS 场景。
- **2.4 Solr → Elasticsearch 主导**：`elastic/elasticsearch`（77998★）基于 Lucene
  （`apache/lucene`，3568★）提供开箱即用的分布式搜索 + 分析，Solr（`apache/solr`，1677★）
  退居特定场景；且 2026 年检索已走向「倒排 + 向量」混合（语义/AI 搜索）。
- **2.2 HBase 的边界**：`apache/hbase`（5560★）在「海量稀疏宽表」仍有一席，但被
  更通用的 NoSQL/湖仓方案部分替代。

## 近年研究与工业界开源实践（2015–2026）

- **缓存**：`redis/redis`（76487★）事实标准；`memcached/memcached`（14285★）存量。
  Redis 7 的演进（多线程 IO、RedisJSON、向量集）让它从「缓存」走向「多模数据平台」。
- **消息/流**：`apache/kafka`（33850★）主导事件流与管道；`apache/activemq`（2464★）传统 JMS。
- **搜索**：`elastic/elasticsearch`（77998★）主导；`apache/solr`（1677★）与
  `apache/lucene`（3568★，ES/Solr 共同内核）仍在。2026 年「向量检索 + 倒排」混合（RAG/语义搜索）
  成为新热点。

  仍是关系型主力（本书 2.2.1 的「MySQL 扩展」今天由 ShardingSphere/Vitess 接管）。
- **存储引擎纵深**：想深究 LSM/B+ 树与 SSTable，见仓库

## 常见误区与本书需修正之处

| # | 误区 | 事实 | 书目 |
| --- | --- | --- | --- |
| 1 | 「缓存只是把数据放内存」 | 缓存要解决一致性、失效、雪崩、击穿、穿透，工程细节远多于「存一下」 | 2.1 |
| 2 | 「取模分片最省事」 | 节点数变化导致大面积 key 重映射 → 雪崩；应一致性哈希或预分片 | 2.1.2 |
| 3 | 「session 放本地内存就行」 | 多实例下会掉登录；需集中存储或客户端携带 | 2.1.3 |
| 4 | 「HBase 能替代 MySQL」 | 二者正交：HBase 无强事务、适合海量稀疏；MySQL 强一致事务 | 2.2 |
| 5 | 「消息系统只是解耦」 | 它还承担削峰、异步、最终一致、事件溯源；但引入「至少一次/精确一次」语义难题 | 2.3 |
| 6 | 「Solr 和 Elasticsearch 随便选」 | 今天 ES 生态与易用性占优；Solr 多用于既有系统 | 2.4 |
| 7 | 🔧 2.1 memcache 已被 Redis 取代 | 2026 年缓存默认 Redis，memcache 退居存量 | 2.1 |
| 8 | 🔧 2.3 ActiveMQ 已非流处理主流 | Kafka 以日志模型主导管道/流处理，JMS 退居传统企业 | 2.3 |
| 9 | 🔧 2.4 Solr 已被 Elasticsearch 取代 | ES 开箱即用的分布式搜索/分析成为默认 | 2.4 |
| 10 | 🔧 2.2 缺「云数据库/分布式数据库」视角 | PolarDB/TiDB/OceanBase 把「MySQL 扩展」产品化，不再手工分库分表 | 2.2.1 |
