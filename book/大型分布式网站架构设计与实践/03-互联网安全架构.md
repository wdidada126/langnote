# 第 3 章　互联网安全架构

> 原书第 3 章是「网站怎么不被打穿」：常见 Web 攻击（XSS/CSRF/SQL 注入/文件上传/DDoS）、
> 安全算法（摘要/对称/非对称/签名/证书）、摘要认证、签名认证、HTTPS/TLS、OAuth。
> 这一章的**底层原理十年不变**（加密、哈希、签名），但**实现标准已大版本更迭**：
> OAuth 1 → OAuth 2.0 / OIDC、JWT 取代临时签名、mTLS 取代简单网关鉴权、WAF 成为标配。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 3.1 常见 Web 攻击：输入即战场

| 攻击 | 本质 | 防御 |
| --- | --- | --- |
| XSS（跨站脚本） | 把脚本注入到页面，在受害者浏览器执行 | 输出编码、CSP、输入校验、HttpOnly Cookie |
| CSRF（跨站请求伪造） | 借受害者的登录态，伪造请求 | 同源校验、CSRF Token、SameSite Cookie |
| SQL 注入 | 把 SQL 片段拼进查询，改变语义 | 预编译（参数化查询）、白名单、最小权限 |
| 文件上传漏洞 | 上传可执行文件并被当作代码执行 | 类型校验、存储与执行分离、重命名 |
| DDoS | 用海量请求压垮带宽/连接/算力 | 限流、清洗、CDN、Anycast |

```text
# 教学示意，不参与构建：SQL 注入 vs 参数化
危险:  "SELECT * FROM user WHERE name='" + name + "'"   -- name="x' OR '1'='1" 改变语义
安全:  "SELECT * FROM user WHERE name=?"  + 参数绑定     -- 输入永远当数据，不被当指令
```

### 3.2 安全算法：三个基本动作

- **数字摘要**（3.2.1）：MD5/SHA 把任意长度输入映射成定长摘要，单向不可逆。用于**校验完整性**
  （文件是否被改）。注意 MD5/SHA-1 已被攻破碰撞，今天用 SHA-256。
- **对称加密**（3.2.2）：同一把密钥加密解密（AES）。快，适合加密大量数据；难点是**密钥分发**。
- **非对称加密**（3.2.3）：公钥加密、私钥解密（或用私钥签名、公钥验签）（RSA/ECC）。慢，适合
  密钥交换、签名，不适合直接加密大块数据。
- **数字签名**（3.2.4）：`签名 = 私钥加密(摘要)`；验签用公钥解密摘要并比对原文摘要，证明
  「来源 + 完整」。
- **数字证书**（3.2.5）：把「公钥 + 身份」用 CA 的私钥签名，解决「你怎么证明这个公钥确实是他的」。

### 3.3 摘要认证 & 3.4 签名认证

- **摘要认证**（3.3）：客户端和服务端共享一个口令；服务端发一次性 `nonce`，客户端回
  `H(口令相关摘要 + nonce)`，服务端校验。相比「明文密码」，网络上只传一次性摘要，降低泄露风险。
- **签名认证**（3.4）：开放接口/服务间调用常用。请求方用私钥对「参数+时间戳+nonce」签名，
  服务端用公钥验签，并校验时间戳/nonce 防重放。

```text
# 教学示意，不参与构建：签名认证四要素
sign = RSA_sign(privateKey, H(sorted(params) + timestamp + nonce))
服务端: 验签(publicKey, sign, 原文) 通过 且 timestamp 在窗口内 且 nonce 未用过 -> 放行
```

### 3.5 HTTPS / TLS

- **原理**（3.5.1）：HTTPS = HTTP over TLS。TLS 握手阶段用**非对称**协商出**对称会话密钥**
  （兼顾安全与性能），之后用对称加密传输。证书链验证服务端身份，防冒充。
- **部署**（3.5.3）：获取证书（CA 签发或自签用于内网）、服务器启用 TLS、HSTS 等。

### 3.6 OAuth 授权

- **OAuth**（3.6）：解决「用户想让第三方应用访问自己在某服务商的数据，但不想把账号密码给第三方」。
  核心是**授权（access token）**而非认证：第三方拿 token 代表用户访问受限资源，用户可随时吊销。
  本书讲的是 OAuth 1.0a 的签名式流程；2026 视角见下。

## 版本演进

- **本书无第二版**；本节写 2014 年口径 → 2026 年视角的变化。
- **3.2 算法升级**：MD5/SHA-1 退出安全用途，统一 SHA-256/SHA-3；RSA 让位于 **ECC**
  （同等安全更短密钥，TLS 1.3 默认）。对称用 AES-GCM 等 AEAD 模式（同时保机密+完整）。
- **3.5 TLS 1.3**：握手从 2-RTT 降到 1-RTT（甚至 0-RTT），废弃大量不安全套件；本书写的是
  SSL/旧 TLS，今天默认 TLS 1.3。
- **3.3/3.4 认证现代化**：开放接口从「自建签名」演进到 **JWT（JSON Web Token）**——
  自包含声明、签名防篡改、无状态校验；**OAuth 2.0 + OIDC** 取代 OAuth 1.0a 成为 SSO/第三方登录标准；
  服务间用 **mTLS（双向 TLS）** 取代简单签名，由 Service Mesh 自动注入证书（见 01 章补丁）。
- **3.1 防御体系化**：从「逐点补漏洞」到 **WAF（Web 应用防火墙）+ RASP + 安全开发生命周期**；
  DDoS 防御依赖云厂商清洗与 CDN/Anycast。
- **密钥管理**：从「配置里写死密钥」到 **KMS / Vault** 集中托管 + 自动轮换，杜绝明文密钥泄露。

## 近年研究与工业界开源实践（2015–2026）

- **传输安全**：TLS 1.3（RFC 8446, 2018）已成默认；Let's Encrypt（ACME 协议）让免费证书普及，
  本书 3.5.3「部署 HTTPS」从「买证书」变成「自动签发」。ECC 曲线（P-256/Ed25519）成主流。
- **认证/授权**：OAuth 2.0（RFC 6749）+ **OIDC**（2014）+ **JWT**（RFC 7519, 2015）是
  SSO/开放接口事实标准；服务网格把 **mTLS**（`istio/istio` 38408★、`envoyproxy/envoy` 28995★）
  做成默认——对应本书 3.4 签名认证在「服务间」场景的现代替身。
- **WAF/防护**：云厂商 WAF、ModSecurity、Cloudflare 等把 3.1 的各类攻击防护产品化；
  OWASP Top 10 每年更新，是防御清单的权威来源。
- **密钥与机密管理**：HashiCorp Vault、云 KMS 取代「配置文件写密钥」，呼应 3.2 的安全算法落地。
- **可观测的安全**：本章未涉及「安全日志/审计」，2026 年与 [04-系统稳定性.md](04-系统稳定性.md)
  的可观测性打通（SIEM、异常登录检测）。

## 常见误区与本书需修正之处

| # | 误区 | 事实 | 书目 |
| --- | --- | --- | --- |
| 1 | 「MD5 还能用于安全摘要」 | MD5/SHA-1 已可构造碰撞，安全场景用 SHA-256+ | 3.2.1 |
| 2 | 「HTTPS 只是加密」 | HTTPS 还解决**完整性**与**身份认证**（防冒充） | 3.5 |
| 3 | 「签名认证只防篡改」 | 签名同时证明**来源**（持有私钥方）与**完整** | 3.4 |
| 4 | 「OAuth 是认证协议」 | OAuth 是**授权**（token 访问资源），认证靠 OIDC | 3.6 |
| 5 | 「SQL 注入靠过滤关键词」 | 过滤易被绕过；根本解是**参数化查询** | 3.1.3 |
| 6 | 「CSRF Token 万能」 | 还需 SameSite Cookie、同源校验配合 | 3.1.2 |
| 7 | 🔧 3.5 的 SSL/旧 TLS → TLS 1.3 | 握手更快、废弃不安全套件，2026 默认 TLS 1.3 | 3.5 |
| 8 | 🔧 3.6 的 OAuth 1.0a → OAuth 2.0/OIDC | 2014 年后标准，本书出版时 OIDC 刚发布，未及纳入 | 3.6 |
| 9 | 🔧 3.3/3.4 缺 JWT/mTLS | 无状态令牌与双向 TLS 是 2026 接口/服务间认证默认 | 3.3–3.4 |
| 10 | 🔧 缺 WAF/密钥托管视角 | 安全从「逐点补」到「平台化防护 + 机密集中管理」 | 3.1–3.2 |
