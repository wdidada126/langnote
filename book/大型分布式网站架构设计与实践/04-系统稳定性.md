# 第 4 章　系统稳定性

> 原书第 4 章是「线上怎么稳」：在线日志分析、集群监控（指标/心跳/容量评估）、流量控制
> （限流/服务稳定性/高并发设计）、性能优化（找瓶颈/压测/优化措施）、Java 应用故障排查。
> 这一章的**工程方法论不过时**，但**工具栈被云原生整体替换**：命令行 grep → ELK/OpenTelemetry，
> 心跳脚本 → Prometheus/Grafana，手工限流 → Sentinel/熔断，且新增「混沌工程/全链路压测」范式。

## 核心精讲

（以下为教学性梳理，伪代码/SQL 均**教学示意，不参与构建**。）

### 4.1 在线日志分析：第一现场

- **常用命令**（4.1.1）：`grep`/`awk`/`sed`/`sort`/`uniq` 做实时过滤与统计；`tail -f` 跟日志流。
- **分析脚本**（4.1.2）：把「统计 ERROR 数、按 URL 聚合耗时、找慢请求」写成脚本，定时跑。

```text
# 教学示意，不参与构建：统计每分钟错误数
grep "ERROR" app.log | awk '{print substr($0,1,16)}' | sort | uniq -c
# 输出: 2026-09-26 10:01  3 ; 2026-09-26 10:02  0 ; ...
```

### 4.2 集群监控：看不见就管不了

- **监控指标**（4.2.1）：CPU/内存/磁盘/网络、QPS、响应时间、错误率、连接数、队列堆积等。
- **心跳检测**（4.2.2）：节点定时上报心跳，监控中心据此判断存活；与 [01](01-面向服务的体系架构SOA.md)
  的服务发现共用「心跳」机制。
- **容量评估及应用水位**（4.2.3）：算「当前负载占最大能力的比例（水位）」，超过阈值就扩容。
  这是**伸缩性**的工程落地——本书虽无独立「伸缩性」章，但容量评估已触及。

### 4.3 流量控制：过载时不崩

- **流量控制实施**（4.3.1）：限流（令牌桶/漏桶）、降级（非核心功能暂时关闭）、熔断
  （依赖故障时快速失败、半开探测恢复）。
- **服务稳定性**（4.3.2）：隔离（线程池/舱壁）、超时、重试（带退避与上限，防雪崩）。
- **高并发系统设计**（4.3.3）：无状态化（便于横向扩展）、缓存前置、异步化、分库分表、读写分离。

```text
# 教学示意，不参与构建：令牌桶限流
tokens = capacity
每请求: if tokens>0 { tokens--; 放行 } else { 拒绝 }   // 另有一定时钟按速率 refill
```

### 4.4 性能优化：先测后改

- **找瓶颈**（4.4.1）：自顶向下——先看是 CPU 满、IO 等、锁竞争、还是外部依赖慢（数据库/下游）。
- **压测工具**（4.4.2）：模拟并发流量（如 Apache ab、JMeter），拿到吞吐量/延迟曲线，定位拐点。
- **优化措施**（4.4.3）：缓存、减少锁粒度、批量、异步、连接池、SQL 优化、JVM 调优等。

### 4.5 Java 应用故障排查

- **常用工具**（4.5.1）：`jstack`（线程栈，查死锁/卡住）、`jmap`/堆 dump（查内存泄漏）、
  `jstat`（GC 统计）、`arthas`（在线诊断）。
- **典型案例**（4.5.2）：死锁、OOM、频繁 Full GC、线程池打满、慢 SQL 拖垮连接池——
  这些也是 [../大规模分布式存储系统/11-质量保证运维及实践.md](../大规模分布式存储系统/11-质量保证运维及实践.md)
  里运维经验的通用版。

## 版本演进

- **本书无第二版**；本节写 2014 年口径 → 2026 年视角的变化。
- **4.1 日志 → 可观测性三支柱**：命令行/grep 演进到 **ELK**（`elastic/logstash` 14950★、
  `elastic/kibana` 21302★）+ **OpenTelemetry**（`open-telemetry/opentelemetry-collector` 7600★），
  且从「日志」扩展到 **metrics + traces + logs** 三位一体。
- **4.2 监控 → Prometheus/Grafana**：`prometheus/prometheus`（66251★）的 pull 模型 +
  `grafana/grafana`（76928★）可视化成为事实标准；`apache/skywalking`（24963★）补 APM/链路追踪。
- **4.3 流量控制 → Sentinel/熔断框架**：`alibaba/Sentinel`（23146★）把限流/降级/熔断产品化；
  熔断思想源自 Netflix Hystrix（已停更），今天与 Mesh 的熔断能力融合。
- **4.4/4.5 新增范式**：**全链路压测**（影子库/流量打标）让容量评估从「估」变「实测」；
  **混沌工程**（Chaos Mesh / Litmus）主动注入故障验证韧性——本书只有「被动排查」，缺「主动验证」。
- **稳定性工程化**：从「事后排查」到 SRE 的 SLI/SLO/Error Budget，稳定性成为可量化目标。

## 近年研究与工业界开源实践（2015–2026）

- **监控/可视化**：`prometheus/prometheus`（66251★）+ `grafana/grafana`（76928★）事实标准；
  `apache/skywalking`（24963★）做 APM/链路追踪。对应 4.2。
- **日志/可观测性**：`elastic/logstash`（14950★）、`elastic/kibana`（21302★）、
  `open-telemetry/opentelemetry-collector`（7600★）是 4.1 的现代化替身（traces/metrics/logs 统一）。
- **流量治理**：`alibaba/Sentinel`（23146★）限流/降级/熔断；熔断源自 Netflix Hystrix 思想，
  今天与 Service Mesh 边车（`istio/istio` 38408★）的熔断能力合一（见 01 章）。
- **全链路压测/混沌**：Chaos Mesh（`chaos-mesh/chaos-mesh`）、Litmus（`litmuschaos/litmus`）
  把「主动注入故障验证韧性」产品化——这是本书 4.5「被动排查」的重要补丁。
- **容量评估自动化**：Kubernetes HPA（基于指标自动扩缩容）把 4.2.3「容量评估 + 扩缩容」自动化，
  对应本书未单独成章的「伸缩性」能力。

## 常见误区与本书需修正之处

| # | 误区 | 事实 | 书目 |
| --- | --- | --- | --- |
| 1 | 「看日志就能排查一切」 | 日志要可搜/可聚/可关联（traceId），散落文本日志效率低 | 4.1 |
| 2 | 「监控=看 CPU 曲线」 | 需覆盖指标/链路/日志三支柱，且要有关联定位能力 | 4.2 |
| 3 | 「限流就是拒绝请求」 | 完整是限流+降级+熔断+超时+重试退避，组合才稳 | 4.3 |
| 4 | 「性能优化凭感觉」 | 必须先压测定位瓶颈，否则可能越改越慢 | 4.4 |
| 5 | 「Java 排障只看日志」 | 线程栈/堆 dump/GC 日志三件套缺一不可 | 4.5 |
| 6 | 「容量靠拍脑袋」 | 需水位评估+全链路压测，否则大促必出事 | 4.2.3 |
| 7 | 🔧 4.1 缺 OpenTelemetry/可观测性三支柱 | 2026 标准是可观测性（metrics/traces/logs 统一），非单点日志 | 4.1 |
| 8 | 🔧 4.2 缺 Prometheus/Grafana | 今天监控事实标准，本书是自定义心跳脚本 | 4.2 |
| 9 | 🔧 4.3 缺 Sentinel/熔断框架与 Mesh 融合 | 限流熔断已产品化并下沉到边车 | 4.3 |
| 10 | 🔧 缺混沌工程/全链路压测 | 从「被动排查」到「主动验证韧性」，是 2014 后新范式 | 4.4–4.5 |
