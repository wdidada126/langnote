## 3.1 S3 的架构原语（⚠️ 转述 ✅ `AmazonS3/latest/userguide/Welcome.html`）

- **桶=名字空间+策略边界**：对象键是扁平字符串，「目录」只是前缀约定——这决定了
  清单(list)成本随键数量增长，分区设计（05 章）与批写入模式（04 章）都要绕着它做。
- **强一致性语义**：写后读一致（over-write 语义版本化可配）——分析管线可安全地做
  「先写数据文件、后提交清单/指针」的乐观协议，Iceberg/Delta 的原子提交正建在这上面 ⚠️
  （表格式语义对位见 12 章与盘上
  [../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md](../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md)）。
- **版本控制/复制/加密**是桶级开关，为「湖作为系统记录源」提供最低保障 ⚠️。

## 3.2 存储类别体系（✅ `AmazonS3/latest/userguide/storage-class-intro.html`，⚠️ 转述）

| 类别族 | 定位 | 检索特征 | 分析场景直觉（⚠️ 推定） |
| --- | --- | --- | --- |
| 标准 | 热数据/活跃处理 | 即时 | 近 7–30 天分区 |
| 低频族（IA/一键冗余） | 温数据 | 即时但有取回费/最短存储期 | 历史但偶查 |
| 归档族（Glacier 系） | 冷/合规留存 | 分钟到小时级恢复 | 合规审计、重放底牌 |
| 生命周期策略 | 类别间自动迁移 | 按前缀/标签/日期规则 | 分区路径天然成规则键 |

要点 ⚠️：**归档族不可直查**——Athena/Redshift 面对归档对象只会失败，分层策略必须与
查询面共设计（「可查的最冷层」才是真分层），这是 3.4 实验的落点。

## 3.3 对象键设计 = 湖的物理设计

- 惯例 `table/dt=YYYY-MM-DD/shard-file.parquet`：前缀即分区谓词（05 章目录裁剪的对象面）。
- 单分区目标尺寸：过碎（KB 级百万件）则 list 与开文件成本压顶，过大则并行度受限 ⚠️——
  成书语境与现行指南均给「MB 级对象为健康区」一类口径 ⚠️，本册不锁具体阈值。
- 哈希前缀 vs 日期前缀：写热点与读裁剪的经典对偶；分析负载优先读裁剪，日志海量写入才考虑
  散列段（⚠️ 通识重构，非页内原话）。

## 3.4 🔧E1 分层与生命周期类比（**非 S3 行为**）

本机 SQLite 3.45.3：20 万行事件表（20.0MB ATTACH 热库文件）按 `day<'2022-03'` 执行一次
「生命周期动作」——CREATE TABLE cold AS SELECT … WHERE 边界 + DELETE 热侧：
**迁移 44,446 行耗时 51.7ms，冷侧文件 4.6MB，热侧余 155,554 行**。三个可迁移的直觉：
①分层是**数据位置变更**而非应用变更（消费方 SQL 未改一个字）；②边界谓词一次索引扫即可
划定（对应 S3 按前缀/日期规则转储 ⚠️）；③回迁成本对称且更痛（S3 取回费概念在本地无对应——
**差异恰在计费面**，标非 S3 行为）。

## 3.5 湖上格式选择（承 01 章、启 06/12 章）

Parquet（列式、谓词友好，Athena/Glue/EMR 全线通吃 ⚠️）为分析默认；
JSON/CSV 只配当「着陆格式」，落地即转换 ✅（`glue/latest/dg/what-is-glue.html` 转换面）；
ORC 在 Hive 血统栈里与 Parquet 平行 ⚠️。压缩 codec 与可切分性（split-ability）是
「为什么不用 gzip 单文件」的标准答案 ⚠️（通识）。

## 3.6 S3 之上的新抽象：表桶（✅ `s3/latest/userguide/s3-tables.html`，⚠️ 转述）

2024+ 才有的产品面：S3 原生日志化托管 Iceberg 表（表桶/命名空间/表三级），后台自动做
小文件压缩与快照维护——**把 3.3 的对象键设计与湖表维护从用户日程里拿走**。
对本册 2022 语境的修正 ⚠️：成书时「好湖=好键设计」，现在退化为「好湖=开托管维护」。

## 3.9 生命周期规则设计问答（⚠️ 重构操作课）

- **规则键选什么？** 前缀/日期分区（3.3 键设计兑现处）> 标签 > 全桶通配——通配规则
  误伤在途表是经典事故 ⚠️。
- **转储边界怎么定？** 以「最后访问时间 vs 查询面最冷层」双条件夹逼（3.2 表第三列）：
  边界=可查最冷层的访问衰减窗口，不是日历常数 ⚠️。
- **转储能撤回吗？** 技术上能、预算上疼（取回费+最短存储期，3.2 ⚠️）：故规则要
  「进档慢、出档急」——观察窗口宁长勿短 ⚠️。
- **删除规则单独审**：生命周期过期删除是全架构里唯一的「合法数据湮灭器」，
  评审等级对齐权限系统的 Deny ⚠️（09 章双门的写侧镜像）。
- **验收方式** 🔧：E1 脚本改两行日期阈值即可演示「规则变更→影响行数→两侧体量」的
  推演（本机无费用维度——再标非 S3 行为）。

## 3.10 章间连线题（⚠️ 重构自测，答案在括号）

- 为什么 05 章坚持「分区键=时间列」？（3.3 前缀即谓词，裁剪从 IO 问题变元数据问题）
- 为什么 06 章的 compaction 计划要看 3.3 的阈值口径？（小文件治理的「小」由读侧并行度
  定义，不是字节强迫症）
- Zero-ETL/S3 Tables 时代（12.2）本章还剩什么手工活？（规则验收与删除审计两条 ⚠️）
- 一句话复述 3.7 的提交协议：（先数据文件、后清单指针，写失败=无指针=无部分可见）

**一句话收束** ⚠️：对象存储章的终极交付物不是「桶建好了」，
而是「每条生命周期规则都能被回答——保护什么、省什么、疼什么」；答不出规则的账单
与事故面，规则就是迷信的日历 ⚠️（重构句）。

| 中文 | 英文 | 一句话 |

| 对象键/前缀 | Object Key / Prefix | 扁平名字空间的目录幻象 |

| 着陆区 | Landing Zone | 原始数据的先到缓冲层 |
| 写后读一致 | Read-After-Write Consistency | 提交即可见的存储承诺 |
| 清单提交 | Manifest Commit | 以最后小写实现批次原子 |
| 表桶 | Table Bucket | S3 原生的托管 Iceberg 表容器 |

## 最新演进与工业实践

2022→2026（✅ URL 200；⚠️ 转述）：

- **S3 Tables 落地**：湖表运维（compaction/孤儿文件/过期快照）产品化，前文 3.6；Athena/

  与波8 盘上 [../BigQuery_for_Data_Warehousing/00-总览与阅读地图.md](../BigQuery_for_Data_Warehousing/00-总览与阅读地图.md)

- **本机互鉴重申** 🔧：E1 脚本可让学生 30 秒内体感「转储=位置变更」；但**切记无取回费、
  无一致性窗口、无版本化对象模型**——类比边界即差异清单（非 S3 行为）。
