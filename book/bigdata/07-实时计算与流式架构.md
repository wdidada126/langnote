## 二、核心精讲

### 7.1 流处理要回答的四个问题

1. **时间语义**：我的时间是「事件发生的时刻」还是「引擎处理的时刻」？
2. **乱序**：事件晚到怎么办？允许晚多久？
3. **状态**：聚合到什么程度？要不要保留历史？什么时候丢？
4. **一致性**：失败的作业重跑后，结果会变吗？

> **一句话**：**流处理 = 有状态的、基于时间的、可容错的分布式计算**。四者之中任何一个是错的，另外三个都不成立。

### 7.2 时间与窗口

| 概念 | 含义 | 用途 |
| --- | --- | --- |
| **Event time** | 事件在业务系统里发生的时间 | **正确性**；报表口径必须用这个 |
| **Ingestion time** | 数据进入流系统的时间 | 折中，介于两者之间 |
| **Processing time** | 算子处理它的时间 | 低延迟；会随机器的负载漂移 |
| **Watermark** | 「推测时间已经推进到 T」的水位线 | 决定 **什么时候认为某个窗口不会再有新数据** |
| **Allowed lateness** | 水位线过了之后还允许迟到多久 | 用 side output / retract 流处理迟到数据 |

```scala
// 教学示意，不参与构建；一个「时间 + 水位线」的最小骨架（Flink DataStream API 风格）
// 目的：说明 event time / watermark / window 三件套的关系
DataStream<Event> stream = ...
stream
  .assignTimestampsAndWatermarks(
      WatermarkStrategy.<Event>forBoundedOutOfOrderness(Duration.ofSeconds(10))
          .withTimestampAssigner((e, ts) -> e.eventTime()))   // 允许 10 秒乱序
  .keyBy(Event::getUserId)
  .window(TumblingEventTimeWindows.of(Time.minutes(1)))       // 1 分钟滚动窗口（event time）
  .windowAll(...)                                            // 或 sliding
  .reduce((a, b) -> new Event(a.userId, a.amount + b.amount)) // 有状态的折叠
```

- **懒人结论**：
  - 报表类需求 → **event time + window**（默认）；
  - 实时告警/风控类需求 → **processing time**（延迟优先，容忍一点重复）；
  - 水位线**不要拍脑袋给固定值**，先观测 P99 乱序时间再定；给太松 → 数据等太久；给太紧 → 丢迟到数据。
- **三类窗口**：**滚动 tumbling**（固定大小、不重叠）、**滑动 sliding**（重叠）、**会话 session**（按活跃度切，适合用户行为分析）。Flink 还有 **over 窗口**（与 SQL 的 `OVER (PARTITION BY ... ORDER BY ... ROWS BETWEEN ...)` 对应）。

### 7.3 三种一致性语义

| 语义 | 含义 | 怎么实现 | 典型风险 |
| --- | --- | --- | --- |
| **At-most-once** | 最多处理一次，可能丢 | 不做任何恢复 | 计数偏小 |
| **At-least-once** | 至少处理一次，可能重 | 失败后重放（source 可重放 + 输出幂等或不管） | 计数偏大（重复累加） |
| **Exactly-once** | 有且仅有一次 | **可回滚的处理 + 幂等或事务性输出** | 实现复杂；上有非幂等 sink 就破功 |

```scala
// 教学示意，不参与构建；exactly-once 的组合条件（不是可运行代码）
// 1) 数据源可重放   —— Kafka offsets
// 2) 处理可回滚     —— checkpoint（保存状态快照 + offsets）
// 3) 输出幂等/事务  —— 幂等 UPSERT / Kafka 事务 / 支持 XA 的外部系统
// 三者缺一，恰一次就不成立
```

> **关键洞察（这是本章最重要的结论）**：**引擎的 exactly-once 只覆盖「算子状态」；输出到外部系统时，除非那次输出是幂等的或事务的，否则结果仍然会是 at-least-once。** 许多团队以为「开了 checkpoint 就是端到端 exactly-once」，这是最普遍的一个误解（详见本章误区表）。

### 7.4 状态管理与 checkpoint

- **State backend**（Flink 为例）：

| Backend | 状态位置 | 特点 |
| --- | --- | --- |
| `HashMapStateBackend` | JVM 堆内存 | 快，但受 GC 与堆大小限制 |
| `EmbeddedRocksDBStateBackend` | 本地磁盘（LSM） | 支持超大状态、**增量 checkpoint**；读写有序列化成本 |
| 自研（如 `RocksDBIncremental`） | 同上 | 大状态作业的事实标准 |

- **Checkpoint 机制**：基于 **Chandy-Lamport 的分布式快照**（Flink 采用轻量异步快照）。触发时：
  1. source 注入一个 **barrier**，Barrier 随数据流向下游；
  2. 算子收到 barrier 时把**状态**异步存到远端（HDFS/S3/OSS）；
  3. 全图对齐完成后，算子确认 checkpoint 完成；
  4. 失败时从最近的完成 checkpoint 恢复（**整体重放 + 状态回退**）。

```scala
// 教学示意，不参与构建；checkpoint / savepoint 的差异
// Checkpoint：自动化、增量、失败时用于恢复
// Savepoint：手工触发、全量、用于「升级作业版本 / 迁移集群 / 双跑切换」
//   —— 这是生产上做「不停机升级 Flink 作业」的唯一正道
```

- **状态 TTL**：状态不是免费的。聚合类作业必须设 `StateTtlConfig`（如只保留 7 天），否则磁盘会被撑爆、恢复时间会无限增长。
- **状态大小管理**：keyed state 的大小 = **key 基数 × 每 key 状态**。因此「按 uid 聚合一年」与「按 uid 聚合一天」的代价差 365 倍。

### 7.5 实时数仓的现实形态

《离线和实时大数据开发实战》第三篇的结构（Storm → Spark Streaming → Flink / Beam）记录了 2018 年的流计算生态。今天回看，它反映的演化路径是：

```
2018：Lambda  ——  离线 HIVE 数仓（T+1）  +  实时 Storm/Spark 指标（秒级）
      ↓
2020：Kappa   ——  一套 Flink + Kafka 长保留，重放替代重算
      ↓
2023：湖仓    ——  CDC 直入 Iceberg/Hudi/Delta，流式写入 + 批量修正
      ↓
2026：实时数仓 ——  一份 SQL（Flink SQL / Iceberg 上的 SQL），
                   流是增量写、批是重算修正，物化表由引擎负责刷新
```

- **实时数仓的层次**（与《离线》第 7 章的 Hive 分层同构）：

| 层 | 含义 | 实时化难点 |
| --- | --- | --- |
| ODS（贴源） | 原始数据 | CDC 落湖，字段变更难跟踪 |
| DWD（明细） | 明细事实 | 需要维表 join（要处理维表变更） |
| DWS（汇总） | 轻聚合 | 窗口聚合 + 状态管理 |
| ADS（应用） | 指标/宽表 | **事务性输出**到 Redis/MySQL/HBase |

- **实时数仓最大的坑永远是「维表」**：离线数仓可以用 T+1 的维表快照，实时数仓必须处理**维表变更**（ upsert Kafka、维表 join 的状态、维表变更后的回补）。这是《离线》第 6 章「维度变化」（缓慢变化维 SCD）在实时侧的完整重演。

### 7.6 事务性输出：端到端 exactly-once 的关键

| 方案 | 原理 | 适用 |
| --- | --- | --- |
| **幂等写** | 写入时用 `(key, version)` 去重，重复写入覆盖 | 支持 UPSERT 的存储（MySQL、HBase、Redis、Iceberg） |
| **Kafka 事务性生产者** | 依赖 Kafka 的 `read_committed` + 事务标记，跨分区原子 | 输出到 Kafka（下游是另一个 Flink 作业） |
| **两阶段提交 Sink** | 预提交阶段先写临时数据，checkpoint 完成后再提交 | 自定义 sink（Flink 的 `TwoPhaseCommittingSink`） |
| **归档 + 重放** | 输出到不可变文件，name-based 幂等（同一次 checkpoint 的文件不会重复生成） | 落对象存储/湖 |

```scala
// 教学示意，不参与构建；幂等写的要点
// (1) 输出的每一行都带一个「幂等键」，重复写入是覆盖而不是累加
//     INSERT INTO ads_metrics  VALUES (..., ...)  -- 天然幂等
//     INSERT INTO ads_metrics  VALUES (..., ...);  -- 非幂等（重复就翻倍）
// (2) 或者：先算 delta，再按 key 排序做 retract（旧值撤销 + 新值写入）
```

> **一个常被忽略的事实**：**幂等的前提是「写入顺序确定」**。在 checkpoint 恢复、并发写入、或者下游是直接 append 的场合，幂等会失效。因此生产上更常见的做法是：**让 sink 支持 UPSERT，并把输出侧的更新做成「先 retract 再 insert」**。

### 7.7 版本演进与 2026 的现实

| 时间 | 事件 |
| --- | --- |
| 2011–2013 | Storm（Twitter）、Spark Streaming（微批）、**Naiad**（SOSP 2013，timely dataflow） |
| 2015 | Flink 开源；*MillWheel* 与 *Dataflow Model* 论文确立水位线语义 |
| 2016 | Kafka Streams、Flink 1.0；Google Cloud Dataflow（SIGMOD 2015）商业化 |
| 2017 | Flink 的流式 SQL（Flink Table & SQL API）成型 |
| 2019 | Flink 的 **Savepoint**、Event Time 三态语义；Delta Lake 开源 |
| 2020–2021 | Flink 1.12/1.13 的 **Table/SQL 成为一等公民**； licensed ASF 退出 |
| 2023 | Flink 的 **Materialized Table（物化表）** API 出现；Apache Paimon 进入 ASF |
| 2025–2026 | 流式写入湖仓成为默认模式；「流批一体」从概念进入工程标配 |

🔧 **2026 必须补的四条**：

1. **CDC + 流处理取代「离线 T+1 抽取」**：MySQL binlog 经 Debezium → Kafka → Flink SQL → Iceberg，这张链路在 2026 年已是主流；《离线》第 1.2.1 节列出的「数据采集传输主要技术」里只有 Flume/Sqoop/DataX，**没有 CDC**。
2. **Flink 的 SQL 化与「流为纲，批为流」**：Flink 的 Table/SQL API 让批处理只是「有界的流」，Materialized Table 进一步把「建表 + 调度 + 刷新」收进引擎。
3. **状态与 checkpoint 的工程化**：**增量 checkpoint**、**savepoint 做不停机升级**、**状态 TTL**；三件事在 2018 年的书里都只是提一句。
4. **湖仓的时间旅行与 schema evolution**：实时数仓的「回补三天前的数据」在 2026 年是 `SELECT ... AT TIMESTAMP`（Iceberg 的 time travel）而不是「重跑一遍历史流」。

## 三、核心精讲（续）：教学示意代码

```java
// 教学示意，不参与构建；一个最小化的「幂等 sink + 状态」骨架
// 目的：说明 exactly-once 的组合条件，不要运行
class IdempotentSink {
  // 幂等键：(业务主键, 版本来自 checkpoint id)
  void write(String key, long version, String value) {
    // 1) 同一 (key, version) 重复写入是覆盖
    // 2) 不同 version 覆盖旧值
    store.upsert(key, value, version);
  }

  void onCheckpointComplete(long checkpointId) {
    // 只有 checkpoint 完成之后才对外「可见」
    store.publish(checkpointId);
  }
}
```

> 注意这里传达的核心思想：**「计算侧」与「可见性」要分开**。计算重放是常态，可见性切换才是关键动作。

## 五、近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **乱序与水位线自适应**：从固定 `allowedLateness` 到**基于观测延迟的自适应水位线**（按历史分布动态提前/推迟），是 2019 年后的主要方向。
- **状态与容错**：增量 checkpoint 的 MVCC 存储设计（RocksDB 的 SST 复用）、超大规模状态的**调度感知恢复**、以及 **savepoint 的成本**。
- **事件驱动的物化视图**：把流作业当作「增量维护的物化视图」，与数据库的**查询改写 / 视图维护**理论对接；相关研究关注「流视图与批视图收敛」及「视图的增量维护代价」。
- **流式 SQL 的语义**：确定性（determinism）、retraction 流、以及 upsert 语义的形式化。

**可直接照做的清单**：

1. 先定「**这个需求的正确时间语义是 event time 还是 processing time**」，再写代码。
2. 水位线给一个比观测 P99 略大的值，然后用 `sideOutputLateData` 观察迟到量，而不是直接丢弃。

5. Sink 一定要验幂等性：在测试环境人为重放一次同一批数据，看输出是否翻倍。

## 六、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | 「开了 checkpoint 就是端到端 exactly-once」 | **不是**。引擎的 exactly-once 只保证**算子状态**；输出到外部系统时，除非 sink 幂等或支持事务，仍然是 at-least-once | 《离线》第 8.4 节（spout/bolt 的可靠性）；也是本书语境下最常见的误解 |
| 2 | 「实时数仓就是把离线 SQL 改成流作业」 | 差异在**维表变更、状态管理、输出幂等、乱序容忍**四处；离线是一次性全量，流是持续增量 | 《离线》第三篇；第 6 章的维度变化在实时侧被放大 |
| 3 | 「Spark Streaming 是实时计算的最优解」 | 微批（默认 500ms）在延迟与吞吐上受结构限制；2026 年新项目首选 **Flink** 或 Spark 的 Structured Streaming | 《离线》第 9 章；《Spark 大数据实时计算》第 10 章 |
| 4 | 「Storm 已经足够成熟，不用换」 | Storm 已进入**退役**状态（社区基本停止演进），2026 年不应再用于新项目；但它仍是理解流处理概念的良好入门（见《离线》第 8 章） | 《离线》第 8 章 |
| 5 | 「水位线设得越保守越正确」 | 太保守 → 窗口迟迟不触发、状态堆积、延迟飙升；太激进 → 数据被判为迟到甚至丢弃。**要用观测数据来定，而不是拍脑袋** | 《离线》第 8–9 章未提水位线（2018 年的书写时 Flink 的 event time 尚在普及） |
| 6 | 🔧 本书未覆盖 **CDC 取代离线抽取** | 2018 年的数据采集靠 Sqoop/DataX 每日全量/增量抽取；2026 年的主流是 **Debezium + Kafka + Flink SQL 直入湖仓** | 《离线》第 1.2.1、1.2.2 节 |
| 7 | 🔧 本书未覆盖 **Flink 的 SQL 化与 Materialized Table** | 《离线》第 10–11 章只把 Flink 当作一个「框架」介绍；2026 年的重点是 **Flink SQL**（`CREATE TABLE` + window TVF + upsert）与**物化表**（声明式刷新） | 《离线》第三篇第 10–11 章 |
| 8 | 🔧 本书未覆盖 **湖仓的时间旅行 / schema evolution 对实时数仓的意义** | 「回补历史数据」在 2026 年是读旧表版本（`SELECT ... /*+ OPTIONS */` 或 Iceberg 的 `AT TIMESTAMP`）而不是重跑历史流 | 《离线》第 7.5 节「数据平台新架构——数据湖」只一句话带过；详见 `10` |
