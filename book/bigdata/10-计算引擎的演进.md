> **本章地图**：**引擎格局的三次迁移**（MapReduce → Spark → Flink/湖仓）→ **Spark 的三次代际**（RDD 时代、Catalyst/Tungsten 时代、ANSI/DPP/AQE + Photon 时代）→ **Flink 的路线**（流为纲、批为流、状态与水位线）→ **Lakehouse 与其冲击**（Databricks / Snowflake / 开放表格式）→ **执行层的竞争**（向量化、编译执行、存算分离）→ 2026 年的选型建议。

## 二、核心精讲

### 10.1 三次迁移

| 迁移 | 从 → 到 | 动力 |
| --- | --- | --- |
| 第一次 | MapReduce → Spark | **迭代计算**：MapReduce 每次迭代都落盘；Spark 用 RDD 复用工作集 |
| 第二次 | Spark 批 → Spark SQL / Flink 流 | **结构化数据与实时性**：需要 schema 优化与秒级/毫秒级延迟 |
| 第三次 | 独立集群 + HDFS → 对象存储 + 湖仓 | **成本与收敛**：存算分离、多引擎共享同一份数据、削掉重复存储 |

> **记住这个思路**：引擎之争本质上不是「性能之争」，而是「**谁解决了上一个时代最疼的那个问题**」。《离线》第三篇把 Storm → Spark Streaming → Flink → Beam 依次介绍，正是第二次迁移的现场记录。

### 10.2 Spark 的代际

| 代际 | 代表版本 | 核心特征 | 留下的遗产 |
| --- | --- | --- | --- |
| **1.x：RDD 时代** | 1.0–1.5 | RDD、DStream、Hash shuffle、无 Tungsten | RDD 的血缘与容错模型仍活在引擎内部 |
| **2.x：结构化时代** | 2.0–2.4 | Dataset/Catalyst/Tungsten/Structured Streaming | 「优化器可见 schema」成为共识 |
| **3.x：自适应与标准化** | 3.0–3.5 | **ANSI 模式、DPP、AQE、SPIP 流程** | 优化从「计划时」前移到「运行时」 |
| **4.x：语义收敛（进行中）** | 4.0+ | **ANSI/SI 默认化**、Photon 化方向、新一批 SI 提案 | 老代码的隐式转换与溢出行为会变 |

🔧 **Spark 4.0 要关注的三件事**：

1. **ANSI 默认开启**的影响面：从「静默容错」到「严格报错」。**迁移策略**：先在老的兼容开关下跑一遍全量 SQL，把报错清单列出来，再逐条决定「是改数据、改 SQL，还是保留兼容模式」。
2. **SI（Spark Improvement Proposal）流程**：Spark 社区把「行为变更」规范化为 SI 提案，意味着**未来的变化会更可预期、更易追踪**（这一点对已经积累大量作业的公司特别重要）。
3. **Photon 与执行层竞争**：Databricks 的 Photon（SIGMOD 2024 公开）把「向量化 + 原生执行 + 容错」作为一个整体推进；开源侧 Velox 在做同样的事。

### 10.3 Flink 的路线

Flink 的核心主张可以概括成一句话：**「流为纲，批为流」**（streaming is the primitive，batch is a special case of streaming）。

| 维度 | Flink 的做法 |
| --- | --- |
| 执行模型 | 事件驱动；批 = 有界流 |
| 时间语义 | event time 一等公民（watermark、window、allowed lateness） |
| 状态 | 内嵌 state backend（RocksDB / heap），checkpoint 与 savepoint |
| API | DataStream / DataSet（逐步合并）→ **Table & SQL 为主** |
| 新形态 | **Materialized Table（物化表）**：声明式定义「这张表怎么刷新、多久刷」，由引擎负责调度与刷新 |
| 生态 | Flink CDC、Flink SQL Connector（Kafka、JDBC、Hive、Iceberg、Paimon） |

```sql
-- 教学示意，不参与构建；Flink SQL 的流批一体写法（示意）
-- 一张「持续写入」的表（流）
CREATE TABLE order_events (
  order_id  STRING,
  amount    DOUBLE,
  event_time TIMESTAMP(3),
  WATERMARK FOR event_time AS event_time - INTERVAL '10' SECOND
) WITH ('connector'='kafka', ...);

-- 一张物化表：引擎负责「每秒增量刷新」（可以是连续刷新，也可以是周期刷新）
CREATE MATERIALIZED TABLE daily_gmv
WITH ('refresh.mode' = 'continuous') AS
SELECT DATE_TRUNC('day', event_time) AS day, SUM(amount) AS gmv
FROM order_events GROUP BY DATE_TRUNC('day', event_time);
```

> **物化表是 2020 年代最重要的「工程收敛」**：它把「建表 + 调度 + 刷新 + 查询改写」四件事收进引擎。这正是《离线》第 2 章描述的「数据平台大图」由人堆平台组件完成的工作，现在交给引擎。

### 10.4 Lakehouse 的冲击

| 玩家 | 形态 | 关键主张 |
| --- | --- | --- |
| **Databricks** | Lakehouse（Delta + Photon + MLflow） | 「数据湖 = 数据仓库 + 数据湖的成本」 |
| **Snowflake** | 云数仓 + Open Catalog（原 Polaris） | 「存算分离、零管理」；后期向开放格式靠拢 |
| **开源表格式** | Iceberg / Hudi / Delta / Paimon | 「引擎中立、ACID、时间旅行、schema 演进」 |
| **传统数仓** | Teradata / Vertica / Greenplum | 存量迁移压力 |

🔧 **对传统数仓的实际影响**：

1. **「事实表 + 维度表」的建模语言没变**，变的是物理底座（从专有集群 → 对象存储 + 表格式）。《离线》第 6 章的维度建模仍然完全适用。
2. **「跑批」这个动作被重新定义**：从「在 Hive 上跑一遍」变成「读某个表快照 / 写新版本」，时间旅行让「回退到上一版结果」成为一行语句。
3. **竞争已经从「引擎」转向「格式 + 服务」**：引擎（Spark/Flink/Trino）正在商品化，差异化落在表格式、catalog、治理与服务化能力上。

### 10.5 执行层的竞争

| 路线 | 代表 | 特点 |
| --- | --- | --- |
| **编译执行（Codegen）** | Spark Whole-Stage Codegen、Photon | 生成原生代码，避免虚调用；适合复杂表达式 |
| **向量化（Vectorized）** | Arrow + Velox、DuckDB、ClickHouse、Doris | 批量列处理，cache 友好；适合扫描与简单聚合 |
| **嵌入式本地引擎** | DuckDB、ClickHouse、DataFusion | 「一个进程干完」，在 TB 以内往往快过分布式 |
| **存算分离 + 弹性** | Trino/Presto on S3、Spark on K8s | 弹性与成本优先 |

> **一个务实的观察**：对于小于几 TB 的数据集，**本地引擎（DuckDB/ClickHouse）的延迟常常低于启动一个分布式集群**；分布式引擎的价值在 PB 级与并发隔离。这也是 2020 年代「分析引擎小型化」趋势的来源。

## 五、近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **自适应执行**：AQE（Spark 3.0）与 Flink 的自适应并行度，把优化从静态计划推向运行时决策；研究方向是「**运行时代价估准**」与「**自动参数调优**」。
- **湖仓一体**：Delta Lake（SIGMOD 2020）之后，表格式成为存储层的研究焦点；关注 ACID、时间旅行、schema evolution 与跨引擎一致性。
- **向量化与本地执行**：Velox（Meta，2022 开源）、DuckDB（2019 起）与 DataFusion 把「内存列格式 + 向量化算子 + 嵌入式执行」做成完整引擎，对 Spark 形成压力。
- **存算分离**：对象存储上的 shuffle、状态与 join 是 2022 年后的研究热点；核心难题是延迟与小请求数。

**工业界开源（star 数为 2026-09-25 用 `gh api` 实测）**：

| 项目 | star | 定位 |
| --- | --- | --- |
| `apache/spark` | **44036** | 批处理与 SQL 的事实标准 |
| `apache/flink` | **26362** | 流处理与流批一体 |
| `apache/iceberg` | **9271** | 最中立的开放表格式 |
| `delta-io/delta` | **9021** | Databricks 生态的表格式 |

**2026 年的一条务实结论**：

> **把「引擎」当商品，把「表格式 + 治理 + 语义正确性」当护城河。** 两本书成书时的世界观是「选一个引擎」（2018 年是 Storm/Spark Streaming，2022 年是 Spark），2026 年的现实是「引擎可替换，数据资产与语义不可替换」。

## 六、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | 「Spark 是最流行的实时计算引擎」（2018 年前后的常见判断） | **2026 年的现实**：流处理新项目的默认选择是 **Flink**；Spark 仍是批与 SQL 分析的首选。两本书的表述反映成书时的共识，已不成立 | 《离线》第 9 章把 Spark Streaming 当作实时计算主力；《Spark 大数据实时计算》第 10 章的立场 |
| 2 | 「Storm 是当前主流，Flink 只是未来」 | Storm 已进入**退役**状态（社区基本停止演进）；Flink 是 2026 年流处理的默认选择。《离线》第 8 章的描述是历史档案，不是当代建议 | 《离线》第 8 章 |
| 3 | 「Spark 3.x 与 2.x 的行为一致，升级无风险」 | ANSI 模式、ANSI 默认化、溢出报错等行为变更会让「原来能跑的作业」失败或变慢；升级前必须做兼容性测试 | 《Spark 大数据实时计算》第 8–9 章 |
| 4 | 「批与流是两个不同的东西，需要两套引擎」 | 2026 年的现实是「一套 SQL、两种执行模式」；Flink 的「流为纲，批为流」与 Spark 的批流一体是同一目标的两条路径 | 《离线》第三篇的结构即暗示两套；详见 `01`、`07` |
| 5 | 「数据湖就是 HDFS 上放文件」 | 真正的湖仓需要**表格式**（ACID、时间旅行、schema 演进）；缺了它就没有并发安全 | 《离线》第 7.5 节 |
| 6 | 🔧 两书均未覆盖 **Lakehouse 冲击** | Databricks 2021 年提出 Lakehouse，2026 年已是主流叙事；Snowflake 也在向开放格式靠拢。「选引擎」正在变成「选格式 + 选服务」 | 两书均无；`10` 的主要缺口 |
| 7 | 🔧 两书均未覆盖 **Materialized Table（物化表）** | 物化表把「建表 + 调度 + 刷新」收进引擎，是批流一体从概念走向工程的关键一步；《离线》第 2 章的数据平台大图正是人工做的同一件事 | 《离线》第 2.2 节；《Spark 大数据实时计算》第 8 章 |
| 8 | 🔧 两书均未覆盖 **向量化与本地引擎的竞争**（Arrow/Velox/DuckDB/ClickHouse） | 小数据量下本地引擎常常更快；执行层已从「Spark 一家」变成多条路线并存 | 《Spark 大数据实时计算》第 9 章；详见 `04` |
