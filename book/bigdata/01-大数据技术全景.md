## 二、核心精讲

### 1.1 三种范式与四类延迟

| 范式 | 数据形态 | 延迟量级 | 典形代表 | 一致性语义 |
| --- | --- | --- | --- | --- |
| **批处理 Batch** | 有界数据集 | 分钟 ~ 小时 | MapReduce、Spark RDD、Hive | 通常 exactly-once（输入确定、输出确定） |
| **流处理 Stream** | 无界数据流 | 毫秒 ~ 秒 | Flink、Spark Streaming、Storm | at-least-once / exactly-once（端到端靠 checkpoint） |
| **交互分析 OLAP** | 有界数据集 + 高并发查询 | 亚秒 ~ 十秒 | Trino、ClickHouse、Doris、Presto | ACID（表格式层保证） |
| **搜索 / 向量检索** | 文档或向量集 | 毫秒 | Elasticsearch、Milvus | 最终一致 |

> 概念澄清：**「实时」这个词在中文语境里被用坏了**。它通常指三种完全不同的东西——
> ① **实时性（timeliness）**：结果有多快出来；
> ② **流式（streaming）**：数据是否是一条一条来；
> ③ **精确一次（exactly-once）**：结果是否正确。
> 三者可以任意组合。批处理也能做到「分钟级实时」，流式也能做到「乱序数据的正确结果」。《离线和实时大数据开发实战》第 8 章开头把 Storm 称作「流计算技术的鼻祖」，正是把「流处理」等同于「实时计算」这一中文语境的典型表现——**方向对，但要把它们当作三个正交维度看**。

### 1.2 Lambda 架构及其代价

Lambda 的核心思路：同一份逻辑用**两套实现**跑两遍。

```
                 ┌────────────────┐   ┌────────────────┐
   数据源 ──────► │  speed layer   │   │ batch layer    │
   (Kafka)  │    │ (Storm/Spark   │   │ (Hadoop/Hive/  │
             │    │  Streaming)   │   │  Spark)        │
             │    │  ~秒级，实时视图 │   │ ~小时级，权威视图 │
             │    └───────┬────────┘   └───────┬────────┘
             │            │  merge             │
             └──────────► ┴──► service layer（合并两者，对外提供）
```

- **优点**：批层保证**正确性与可重算**（历史数据随时可以重新全量算一遍），速度层保证**及时性**。
- **代价（这是 2026 年仍然成立的判断）**：
  1. **同一份业务逻辑写两遍**（SQL 一次、Java/Scala streaming 一次）→ 语义漂移是必然的，两份结果不一致是常态；
  2. **两套技术栈的运维成本**（一套批调度、一套流集群、两套监控告警）；
  3. **状态与回溯困难**：速度层的中间状态无法「重算三个月前的某一天」；
  4. **服务层的合并逻辑复杂**：实时表与批表如何对齐、如何判断 who wins。
- 《离线和实时大数据开发实战》第二篇铺开讲离线平台、第三篇铺开讲实时平台，本质上就是**把这个「两个 layer」的组织结构讲透**——这在 2018 年是合理的，在 2026 年则应理解为「**一种**被历史验证过的架构，但不是**唯一**的」。

### 1.3 Kappa：把批处理当成流处理的特例

Kappa 的化简主张（出自 Jay Kreps 在 2014 年前后的系列博客，*Question: Lambda Architecture? Reality: Lambda Architecture* 与 *The Log: What every software engineer should know about real-time data*）：

1. **a stream is a bounded batch**（批处理 = 一个有界的流， replay 一个有界区间即可）；
2. 只保留**一套**（流）处理系统；
3. 需要「历史重算」时：**从消息队列的早期 offset 重新消费 + 新起的副作用写到一个新表**，而不是在旧系统上原地回退；
4. 因此消息队列必须**能长时间保留数据**（Kafka 的 log 天然合适）。

```
      Kafka(topics, 保留 7 天 ~ 数年)
        │  │  │
        │  └──► 流处理作业 v1 ──► 服务表 v1（对外）
        │
        └──► 流处理作业 v2（重算模式，从旧 offset 起）──► 服务表 v2（对外，切换）
```

- **Kappa 的现实约束**：重算期间的**双写与切换**仍然复杂；重算一个大分区时的**吞吐**受流引擎限制（Flink 打 batch 模式的 batch slot 可以缓解）；**回溯窗口不能长于消息保留期**（于是出现「归档 + 重放」的折中）。
- 🔧 **2026 的修正**：纯粹的 Kappa 与纯粹的 Lambda 都不流行了，流行的是**混合形态**：
  - **OLTP 侧 CDC 出门**（Debezium 读 MySQL binlog）→ **流处理直接进湖仓**（Iceberg/Hudi/Delta 的表），这一步消灭了「离线 T+1 抽取」；
  - **表格式层提供「批的语义」**（时间旅行、schema evolution、ACID 提交），于是流作业写出去的表可以被「批量地」重算、回滚、修正；
  - **结果层（服务表 / 指标库）则由批作业做「权威修正」**——这正是 Lambda 中 batch layer 的正确位置，只不过它不再从 0 到 1 重复实现一遍流式逻辑，而是**基于同一份 SQL 语义在表格式上重跑**。
  - 换句话说：**代码层面统一（一套 SQL / 一个引擎），数据层面分层（流是增量写、批是重算修正）**。

### 1.4 批流一体的两条路线

| 维度 | Spark DStream / Structured Streaming | Apache Flink |
| --- | --- | --- |
| 执行模型 | **微批**：把流切成小批次（默认 500ms 左右的 batch interval） | **事件驱动**：每条事件触发算子；批是流的一种特例 |
| 时间语义 | 主要靠 **processing time**；Structured Streaming 支持 event-time + watermark | 一等公民：**event time / processing time**，水位线（watermark）机制 |
| 状态管理 | 依赖 shuffle service / HDFS 检查点，状态在外部存储 | 内嵌 **RocksDB / Heap state backend**，自带 checkpoint & savepoint |
| 「一体化」的路径 | 同一套引擎同时支持 `spark.sql` 批与流；Structured Streaming 复用 Spark SQL 的 Catalyst | 「**流为纲，批为流**」：DataSet 的批量作业在内部被当作 bounded 流执行（Flink DataSet API 已逐步收敛到 Table / SQL） |
| 典型延迟 | 亚秒 ~ 秒级（微批） | 毫秒级 |
| 现状（2026） | Structured Streaming 仍在维护，但新项目首选 Flink 或 Spark 的结构化流 | 流处理的默认选择 |

```scala
// 教学示意，不参与构建；仅用于说明「同一份逻辑的两种写法」，不是可提交作业
// (A) 微批思路：把流看成一串小数据集
val lines: DStream[String] = ssc.socketTextStream("localhost", 9999)
val counts: DStream[(String, Int)] =
  lines.flatMap(_.split(" ")).map((_, 1)).reduceByKey(_ + _)
counts.print()

// (B) 批流统一的思路：流 = 一张只不断追加的表
val df: DataFrame = spark.readStream.format("kafka").load()
val agg = df
  .withWatermark("event_time", "10 minutes")          // 允许 10 分钟乱序
  .groupBy(window($"event_time", "1 minute"), $"uid") // 窗口聚合
  .agg(sum($"amount").as("total"))
val sink = agg.writeStream
  .format("kafka")
  .option("checkpointLocation", "/tmp/ck")
  .outputMode("append")
  .start()
```

> 两者在 2026 年已经**收敛到同一句话**：「流是增量写、批是全量重算，用同一套 SQL 语义」。差别只在于引擎**内部**怎么执行，以及**状态放在哪里**。

### 1.5 数据平台的层次划分

《离线和实时大数据开发实战》第 1.1 节把数据流程拆成「数据产生 → 数据采集和传输 → 数据存储处理 → 数据应用」，第 1.2 节再按这四段分别列举**的主要技术**。这是本章最该被记住的**骨架图**：

| 环节 | 典型技术（2018） | 2026 的常见形态 |
| --- | --- | --- |
| 数据产生 | 业务库、埋点、日志、IoT | 同上，外加应用直连的 binlog |
| 数据采集传输 | Flume、Sqoop、Kafka、DataX | **CDC（Debezium/Flink CDC）+ Kafka/Pulsar + 对象存储直传** |
| 数据存储处理 | HDFS、Hive、Spark、MapReduce | **对象存储（S3/OSS）+ 开放表格式（Iceberg/Hudi/Delta）+ Flink/Spark/Trino** |
| 数据应用 | 报表、推荐、风控、Ad-hoc 查询 | 报表 + **特征平台/在线服务（Feature Store）+ 湖仓一体** |

《离线和实时大数据开发实战》第 1.3 节列出的**角色划分**（数据平台开发运维工程师、数据开发运维工程师、数据分析工程师、算法工程师、业务人员）至今仍成立——**分工没有变，变的是工具链**。

## 五、近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **批流统一的形式化**：Dataflow 模型之后，学界与业界共同的关注点是「**同一次计算的三种输出（twitter/table/done-retraction）**」在物化视图上的语义，以及「流上的增量物化视图能否与批视图收敛」。
- **近似与取舍**：提前触发（early triggering）与 `allowedLateness` 的取舍研究；** watermark 的自适应生成**（不在固定延迟上拍脑袋，而是按观测延迟动态调）。
- **流式状态与容错**：当时以 Flink 的异步快照（*Lightweight Asynchronous Snapshots*，Carbone 等，IEEE Data Eng. Bull. 2015）、Chandy-Lamport 的分布式快照在流引擎中的落地为主。
- **Lakehouse 的学术回应**：Delta Lake（SIGMOD 2020）、以及围绕「数据湖上的 ACID 与 MVCC」的一系列工作，是 OLAP 与 OLTP 语义在存储层的重新合流。

**工业界开源（star 数 2026-09-25 用 `gh api` 实测）**：

| 项目 | star | 与本节的联系 |
| --- | --- | --- |
| `apache/flink` | **26362** | Kappa 路线的主流实现；「流为纲，批为流」的落点 |
| `apache/spark` | **44036** | 批主导、流为辅；本章 1.4 节两种写法的左边 |
| `apache/kafka` | **33836** | Kappa 的前提：长保留期、可重放的提交日志 |
| `apache/pulsar` | **15339** | 存算分离的日志（Broker 无状态 + BookKeeper 存储） |
| `apache/iceberg` | **9271** | 让「数据湖」获得表语义（ACID、时间旅行、schema evolution） |
| `delta-io/delta` | **9021** | 同一赛道；与 Iceberg 在 2020 年代走向互操作（conversion 工具） |
| `apache/hudi` | **6273** | 面向 upsert 与增量读取的表格式，早期偏「流式入湖」 |
| `apache/paimon` | **3408** | 流式湖仓：LSM + Flink 一体化写入 |
| `debezium/debezium` | **13151** | CDC，取代 2018 年的「Sqoop 每日抽取」 |
| `apache/storm` | **6695** | 已退役，但《离线》第 8 章仍以其为「鼻祖」，可作为历史阅读 |

**一些可复用的工程结论**：

1. **不要为了「统一」而统一**：如果一个需求是「每天一次的报表」，用批；不要为了架构洁癖上流式。
2. **「实时」需求的正确问法**：「你真正需要的是延迟（latency）、是新鲜度（freshness），还是恰好一次（exactly-once）？」三者不同，技术选型完全不同。
3. **Lambda 的遗留资产仍在发挥作用**：2018 年建起来的离线数仓（ODS/DWD/DWS/ADS 分层）到 2026 年仍是绝大多数公司的主体，只是**新技术层在它之上叠加**，而不是推倒重来。

## 六、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | 「『实时』就是『流处理』」 | 三个正交维度：**延迟 / 流式 / 恰好一次**。批处理也能秒级输出，流式也能保证乱序正确 | 《离线和实时大数据开发实战》第 8 章开头「流计算技术的鼻祖」 |
| 2 | 「Lambda 已经过时了」 | 更准确的说法：**Lambda 的「双写」过时了，Lambda 的「批层做权威修正」没有过时**。2026 年常见形态是「一份 SQL + 表格式上的流增量写 + 批层重算修正」 | 两书共有；《离线》第 2、7 章的架构 |
| 3 | 「Kappa 完全取代 Lambda」 | Kappa 的痛点在**重算期间的切换与双写**，以及**消息保留期限制了回溯跨度**。现实中大量系统仍在「流 + 批」并存 | 《离线》第三篇（Flink/Beam 一笔带过） |
| 4 | 🔧 「Spark Streaming 就是实时计算」 | DStream 是**微批**（500ms 级），不是事件级；其继任者 Structured Streaming 才具备 event-time/watermark，且目前新项目更常选 Flink | 《Spark 大数据实时计算》第 10 章；也是《离线》第 9 章的立场 |
| 5 | 🔧 本书未覆盖 **CDC + 流处理取代「离线 T+1 抽取」** | 2018 年前后建数仓靠 Sqoop/DataX 每日抽取；2026 年主流是 **Debezium CDC + Kafka + Flink/SQL 直接落湖仓**，离线抽取层大量消失 | 《离线》第 1.2.1「数据采集传输主要技术」未提 CDC |
| 6 | 🔧 本书未覆盖 **Lakehouse 对传统数仓分层（ODS/DWD/DWS）的冲击** | Databricks 2021 年提出 Lakehouse，2026 年 Iceberg/Hudi/Delta/Paimon 已成标配；分层仍在，但「重算单位」从「跑一遍 Hive」变成「读一次表版本」 | 《离线》第 7.5 节「数据平台新架构——数据湖」仅一段带过 |
| 7 | 🔧 本书未覆盖 **Materialized Table（物化表）** | Flink 后期引入的**物化表**概念（周期性/连续刷新、由引擎负责刷新与查询改写），把「建表 + 调度 + 刷新」三件事收进引擎，是批流一体走向工程化的关键一步；《离线》第 2 章的「数据平台大图」正是等价能力的人工实现 | 《离线》第 2 章 |
| 8 | 🔧 两书都未覆盖 **Spark 3.x/4.x 的语义变化** | ANSI 模式、动态分区裁剪、AQE 直接改变了「同一段 SQL 的行为」，而两书都基于 Spark 2.x 的行为书写 | 《Spark 大数据实时计算》第 8、9 章；详见 `04`、`10` |
