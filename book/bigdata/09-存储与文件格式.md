## 二、核心精讲

### 9.1 三层存储结构

```
┌────────────────────────── 表格式（Table Format）─────────────────────────┐
│  Iceberg / Hudi / Delta Lake：ACID 提交、schema、分区演进、时间旅行        │
├────────────────────────── 文件格式（File Format）────────────────────────┤
│  Parquet / ORC：列存 + 统计信息 + 编码                                   │
├────────────────────────── 存储层（Object Storage）───────────────────────┤
│  S3 / OSS / HDFS：几乎无限、按前缀寻址、无 rename 原子性                  │
└─────────────────────────────────────────────────────────────────────────┘
```

> **理解 2018 与 2026 的最大差别，就看这三层**：《离线》第 7.5 节「数据平台新架构——数据湖」只写了一句话，因为它成书时**表格式这一层还不存在**。今天的「数据湖」= 对象存储 + 表格式 + 计算引擎，缺了表格式就只能靠「跑批 + 覆盖」这种粗放方式。

### 9.2 行存 vs. 列存

| 维度 | 行存（MySQL、HBase、Aurora） | 列存（Parquet、ORC、ClickHouse、Doris） |
| --- | --- | --- |
| 读一行 | 一次 I/O | 要跨多个列（跳转） |
| 读一列 | 读出所有无关列 | **只读需要的列**，省一个数量级 |
| 压缩 | 行内相关性弱 | **同列同类型，压缩率高得多**（字典 + 差分 + RLE） |
| 适用 | OLTP（点查、更新） | OLAP（扫描 + 聚合 + 宽表） |
| 更新 | 原地 | 通常 **append-only + merge on read** |

> 这解释了为什么「Spark 不适合做点查与更新」，而《数据库系统概念》第 11 章讲的 B+ 树索引在 Spark/Hive 的批处理世界里几乎不存在 —— **OLAP 用扫描替代索引**。

### 9.3 Parquet 的内部组织

```
Parquet 文件
├─ footer（元数据：schema、row group 的列统计信息、bloom filter 位置）
└─ row group 0（默认 128MB 左右）
   ├─ column chunk: id      → page0(dictionary) + page1(RLE) ...
   ├─ column chunk: name   → ...
   └─ column chunk: amount → ...
```

要点：

1. **row group**：Parquet 的读单位；太小 → 元数据膨胀、小文件；太大 → 读不到想要的。
2. **dictionary encoding**：基数低的列（字符串枚举）用字典，省空间也加速。
3. **RLE / delta encoding**：数值有序时用增量编码 + RLE 压缩效果极好。
4. **statistics（min/max/null count）**：**这是谓词下推能否生效的关键**，写在 footer 里。
5. **bloom filter**（Parquet 的 `BLOOM_FILTER` 元数据、ORC 同样支持）：等值过滤时进一步跳过 page。
6. **ORC 的特点**：自带 **ACID 事务表**（OrcFileAcidTable，事务性写），压缩比通常略好于 Parquet，但生态（尤其与非 JVM 引擎）稍弱。

```scala
// 教学示意，不参与构建；写入时的关键选择
val df = spark.read.option("header", "true").csv("hdfs:///raw/orders")
df.write
  .format("parquet")                        // 或 "orc"
  .mode("overwrite")
  .partitionBy("dt", "hour")                // 分区：按日期/小时切
  .option("parquet.block.size", "134217728")// row group 大小（128MB）
  .save("s3a://lake/warehouse/orders")      // 目标：对象存储
```

### 9.4 谓词下推与统计信息

**谓词下推的四个层级**（从粗到细）：

| 层级 | 粒度 | 依赖 |
| --- | --- | --- |
| 分区裁剪 | 目录级（`dt=2026-09-25`） | 表格式的分区元数据 |
| 文件跳过 | 文件级 | footer 里的 row group 统计（min/max） |
| row group / page 跳过 | 块级 | 更细的统计与 bloom filter |
| 行级过滤 | 行级 | 必须真的读数据 |

```scala
// 教学示意，不参与构建；验证下推是否生效
spark.conf.set("spark.sql.parquet.filterPushdown", "true")       // 默认开
spark.conf.set("spark.sql.parquet.enableVectorizedReader", "true") // 向量化读
// 写完表之后
spark.sql("ANALYZE TABLE orders COMPUTE STATISTICS")             // 表级统计
val plan = spark.sql("SELECT ... FROM orders WHERE dt='2026-09-25' AND amount > 1000")
plan.explain()      // 看 PushedFilters 是否出现，看扫描的文件数是否变少
```

> **最常见的失败诊断**：`PushedFilters: []` 为空 → 过滤条件**没有**被下推，原因通常是：
> ① 列上没有统计信息（新建的表没跑过 `ANALYZE`）；
> ② 过滤条件写在 UDF 里（`where myUdf(x)` 不可下推）；
> ③ 比较的类型与列类型不匹配（字符串列与数字比较，在 ANSI 模式下还会报错）。

### 9.5 分区、分桶与文件管理

- **分区（partition）**：把数据按列值放到不同**目录**（`dt=2026-09-25/`）。**最廉价、最有效的裁剪手段**。
- **分桶（bucket）**：对列做 hash 后切固定数量的文件。用途：① 减少小文件；② **join 时避免 shuffle**（相同桶号可以本地 join，即 sort-merge bucket join）。
- **小文件问题**：流式写入每 checkpoint 一个小文件、Spark 输出未 `coalesce` 都会产生海量小文件 —— **小文件是数据湖的头号性能杀手**（每个文件都要付出元数据与 I/O 的代价）。

```scala
// 教学示意，不参与构建；控制输出文件数的三种手段
// 1) 输出前重分区到目标数量（代价：一次 shuffle）
df.repartition(100).write.mode("overwrite").parquet("s3a://lake/orders")
// 2) 写入后自动压缩（湖仓表格式的 compaction，见 9.6）
// 3) 流式写入用「小文件合并」表（Hudi/Iceberg 的 rewrite_data_files）
```

### 9.6 开放表格式

| 能力 | Iceberg | Hudi | Delta Lake |
| --- | --- | --- | --- |
| ACID 提交 | ✅（乐观并发 + manifest） | ✅ | ✅（单写多读 MVCC） |
| 时间旅行 | ✅（snapshot + `at_timestamp`） | ✅ | ✅（`VERSION AS OF`） |
| Schema evolution | ✅（add/rename/delete，需显式开启） | ✅ | ✅（merge schema） |
| 分区演进 | ✅（meta-data only，不改数据） | ✅ | 有限 |
| 流式写入 | ✅ | ✅（upsert 最强） | ✅ |
| 与引擎解耦 | **最强**（Spark/Flink/Trino/Athena 都能读） | 中 | 弱（Spark 为主，其他引擎支持较弱） |

🔧 **2026 的现实与选择建议**：

1. **新项目首选 Iceberg**：引擎中立、元数据设计干净（manifest/metadata 分裂成三层）、时间旅行与 schema 演进完善；`apache/iceberg`（**9271★**）。
2. **需要高频 upsert + 近实时更新** → Hudi 的 copy-on-write / merge-on-read 更成熟；`apache/hudi`（**6273★**）。
3. **Databricks 生态内** → Delta Lake（**9021★**），且 Spark 的 `delta` connector 仍是主流之一。
4. **流式湖仓** → `apache/paimon`（**3408★**），LSM + Flink 一体化写入，2023 年进入 ASF。

```sql
-- 教学示意，不参与构建；时间旅行与 schema 演进（示意，非可执行）
-- 读取 3 天前的数据快照（Iceberg 语法示意）
SELECT * FROM orders VERSION AS OF 2026-09-22 ;
-- 或者按快照 id
SELECT * FROM orders FOR SYSTEM_TIME AS OF '2026-09-22T10:00:00' ;
-- schema 演进：加一列表，不改历史数据
ALTER TABLE orders ADD COLUMN remark STRING ;
```

## 三、核心精讲（续）：教学示意代码

```python
# 教学示意，不参与构建；说明「统计信息与小文件」对查询的实际影响
# 目的：给出量级直觉，不要运行
def scan_cost(files, rows_per_file, target_rows):
    """粗算：扫描 N 个小文件 vs 少数大文件的字节数（在对象存储上每个文件都有元数据成本）"""
    bytes_scanned = files * rows_per_file * row_size_bytes
    metadata_cost = files * 1_000          # 每个文件的元数据/HTTP 请求成本
    return bytes_scanned, metadata_cost

# 1000 个小文件（1MB each）→ 元数据成本主导
# 10 个大文件（100MB each）→ 字节数相近但元数据成本降 100 倍
```

> 结论：**在对象存储上，「文件数」本身就是一种成本**。这也解释了为什么湖仓体系必须有 compaction / small-file-compaction 这类后台任务。

## 五、近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **湖仓一体**：以 Delta Lake（SIGMOD 2020）为标志，研究重点转向「数据湖上的 ACID + MVCC + 时间旅行」，以及 OLAP 与 OLTP 语义在存储层的合流。
- **元数据与 catalog**：**REST Catalog 规范**（表格式与元数据服务解耦）、Glue/Hive Metastore 的互操作；研究关注「跨引擎一致读」。
- **小文件与 compaction**：湖仓上的自动 compaction 策略（热度感知、增量合并）是 2022 年后的工程研究热点。
- **列存的现代形态**：Arrow（2016 起）把内存列格式标准化；Velox（2022 起）与 DuckDB（2019 起）把「列格式 + 向量化 + 本地执行」做成嵌入式引擎；Parquet/ORC 也在持续加入 bloom filter、encrypted column 等能力。

**工业界开源（star 数为 2026-09-25 用 `gh api` 实测）**：

| --- | --- | --- |

| `delta-io/delta` | **9021** | 同上，Databricks 生态 |
| `apache/hudi` | **6273** | upsert 与近实时入湖 |
| `apache/paimon` | **3408** | 流式湖仓 |

**可直接照做的清单**：

1. **表一定跑到统计信息**：`ANALYZE TABLE ... COMPUTE STATISTICS`，否则谓词下推形同虚设。
2. **输出前 `repartition`/`coalesce` 到目标数量**，避免把小文件问题甩给下游。
3. **分区键选择**：高基数、查询常过滤、且值域稳定（如 `dt`、`region`）；**不要把性别、是否删除这类低基数列当分区键**（分区爆炸）。
4. **格式的现实选择**：Hive/Hadoop 存量 → ORC；跨引擎与长期演进 → **Parquet / Iceberg**。
5. **上线前验证**：`SELECT * FROM t WHERE 过滤条件` + `explain`，确认 `PushedFilters` 非空、扫描文件数合理。

## 六、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | 「数据湖就是对象存储上放一堆文件」 | 少了一层**表格式**（ACID、schema、时间旅行）。没有表格式，多作业并发写会互相覆盖 | 《离线》第 7.5 节「数据平台新架构——数据湖」只一段带过 |
| 2 | 「Parquet 一定会跳过不需要的数据」 | 只有 footer 里有**统计信息**且谓词可下推时才跳过；新建表没跑 `ANALYZE` 时几乎不跳过 | 《Spark 大数据实时计算》第 8 章；《离线》第 4.3 节 |
| 3 | 「分区越多越快」 | 分区数过多 → 目录爆炸、元数据膨胀、Listing 变慢；**反过来拖垮查询** | 《离线》第 4.2.4 节（Hive 表）；第 7 章数仓规范 |
| 4 | 「覆盖写（overwrite）就够用了」 | 多作业并发写 + 部分失败 = 数据不一致；需要 **ACID 提交**的表格式 | 《离线》第 7 章（Hadoop 数仓开发实战，全量覆盖思路） |
| 5 | 「ORC 和 Parquet 差不多，随便选」 | 压缩比、ACID、生态支持有差别；**跨引擎场景 Parquet 更中立** | 《离线》第 4.5 节「其他 SQL on Hadoop 技术」 |
| 6 | 🔧 两书均成书时表格式尚未成为共识 | 2026 年新建数仓几乎默认选 Iceberg/Hudi/Delta 之一；**「数据湖」一词在两书里的含义与今天不同** | 《离线》第 7.5 节；《Spark 大数据实时计算》第 8 章 |
| 7 | 🔧 本书未覆盖 **时间旅行与 schema evolution** | 回补历史数据、误删恢复（rollback）、加列不改历史数据，在 2026 年是表格式的标配能力 | 两书均无；详见 `10` |
| 8 | 🔧 本书未覆盖 **小文件治理** | 流式写入与高频 `overwrite` 产生海量小文件；2026 年靠 compaction 任务解决，并纳入运维 | 《离线》第 5、7 章的 Hive 优化没有这一维度 |
