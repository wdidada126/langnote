## 二、核心精讲

### 11.1 资源模型对比

| 维度 | YARN | Kubernetes |
| --- | --- | --- |
| 资源抽象 | **Container**（CPU + 内存，2.x 之后支持 GPU） | **Pod**（container + volume + 网络策略） |
| 调度粒度 | 应用为主（AM 向 RM 申请） | Pod 级，天然支持与 Deployment/StatefulSet 等编排 |
| 隔离 | Cgroup（较弱） | Cgroup + namespace（更强） |
| 生态整合 | Hadoop 生态原生（Hive/Spark/HBase/MR） | 通用（把大数据与其他负载放同一个集群） |
| 现状（2026） | 仍是大量存量集群的运行时；新集群越来越倾向 K8s | **主流方向**；Spark/Flink 都有一等公民的 operator/支持 |
| 主要痛点 | 无法与其他负载混布、隔离弱、静态划分 | 学习成本、JVM 的资源描述（堆外内存）需要精细调 |

```bash
# 教学示意，不参与构建；两种提交方式的等价关系（示意命令，不要执行）
# YARN
spark-submit --master yarn --deploy-mode cluster \
  --executor-memory 8G --executor-cores 4 --num-executors 40 \
  --class Main app.jar

# Kubernetes（等价意图）
spark-submit --master k8s://https://k8s-apiserver:6443 \
  --deploy-mode cluster --name my-app \
  --conf spark.kubernetes.container.image=my-image:1.0 \
  --conf spark.executor.instances=40 \
  --conf spark.executor.memory=8g --conf spark.executor.cores=4 \
  --class Main app.jar
```

### 11.2 Spark 的部署模式

| 模式 | 适用 | 特点 |
| --- | --- | --- |
| **local[*]** | 本地开发调试 | 用本机线程模拟 executor；**不要用来跑有 shuffle 的作业** |
| **Standalone** | 简单小集群 | Spark 自带资源管理器；无 YARN/K8s 依赖 |
| **YARN cluster/client** | 传统 Hadoop 集群 | **生产最常见**；cluster 模式下 driver 在 AM 里 |
| **K8s cluster/client** | 云原生集群 | driver/executor 都是 Pod；支持 `spark-on-k8s-operator` |

> **部署模式的两个坑**：
> 1. `driver` 的内存在 **client 模式下运行在提交机**上 —— driver 内存不足或网络不通会导致「作业看起来卡住」；
> 2. `--num-executors` 与实际资源要匹配：核心数 × executor 数不能超过单节点可分配的核心总数，否则会排队（YARN）/  Pending（K8s）。

### 11.3 Flink 的资源模型

- **TaskSlot**：每个 TaskManager 划分若干 slot；每个 slot 跑一个并行算子子任务。
- **Slot sharing**：同一 Job 的不同算子尽量放进同一个 slot（Flink 默认开启），这样「并行度 = slot 数」即可，不必每个算子都占满。
- **部署模式**：
  | 模式 | driver/client 在哪 | 适用 |
  | --- | --- | --- |
  | Per-Job Cluster（已演进为 Application Mode） | JobManager 内 | 生产推荐 |
  | Application Mode | JobManager 内，整个应用作为一个单元 | **2026 年的默认推荐** |
  | Session Mode | 共享集群 | 开发调试或小作业；**多作业互相影响，不推荐生产** |

```bash
# 教学示意，不参与构建；Flink 提交（示意命令，不要执行）
flink run-application -t application \
  -Djobmanager.memory.process.size=2048m \
  -Dtaskmanager.memory.process.size=4096m \
  -Dtaskmanager.numberOfTaskSlots=8 \
  -c com.example.JobApp app.jar
```

### 11.4 动态资源与弹性

| 机制 | 引擎 | 前提条件 |
| --- | --- | --- |
| **Dynamic resource allocation** | Spark | **必须开启 External Shuffle Service**（否则 executor 退出会丢 shuffle 数据） |
| **Adaptive elasticity** | Flink（自适应并行度） | 需要 `pipeline.job.graph` 可自适应；对 source 有限制 |
| **K8s HPA / VPA** | 通用 | 基于指标扩缩副本；对 Spark driver/executor 这类「有状态伸缩」不够好 |
| **Serverless / 弹性队列** | 云服务 | 按请求分配资源；小作业成本显著下降 |

```scala
// 教学示意，不参与构建；动态资源分配的必要组合
spark.conf.set("spark.dynamicAllocation.enabled", "true")
spark.conf.set("spark.shuffle.service.enabled", "true")   // 缺一不可
```

> **最常见的线上事故**：开了 dynamic allocation **但没开 shuffle service** → executor 被回收时 stage 失败。这是两本书都未覆盖、但运维一定会踩的坑。

### 11.5 监控与可观测性

**看三个层面的指标**：

| 层 | 指标 | 用途 |
| --- | --- | --- |
| 集群 | 队列使用率、Pending 应用数、节点健康 | 容量规划 |
| 应用 | executor 数、GC 时间、shuffle 读写、stage 时长 | 性能诊断 |
| 算子/业务 | 消息速率、水位线、状态大小、背压 | 流式作业健康 |

```bash
# 教学示意，不参与构建；指标查询的示例（示意，不要执行）
# Spark 的 REST API（driver 侧）与 Prometheus  exporter 是两条主要路径
curl http://driver:4040/api/v1/applications/<app-id>/stages
```

**Spark UI 的正确用法（按优先级）**：

1. **Stages**：task 分布、shuffle 读写、GC 时间 → 定位慢 stage；
2. **SQL**：`explain` 的运行时版本、AQE 是否生效、DPP 是否命中；
3. **Executors**：内存与 GC 曲线 → 判断是否内存不足；
4. **Environment**：配置是否正确（AQE、ESS、Kryo）；
5. **Storage**：缓存的数据块（只有用了 `cache`/`persist` 才有内容）。

> **流式作业特别要看**：**水位线是否推进**。水位线停止推进 = 作业实际上已经积压（常见原因：反压、source 有停断层、或 `maxIdleTime` 没配导致空闲分区阻塞）。

### 11.6 反压（Backpressure）

- **定义**：下游处理不过来时，把压力传导回上游，直到数据源降速。
- **它是特性不是 bug**：反压说明系统在「安全降速」，而不是在丢数据。
- **Flink 的 credit-based flow control**：下游按可缓冲容量给上游发 credit，上游按 credit 发送。
- **排查顺序**：
  1. 先看**哪个算子是瓶颈**（吞吐最低的那个）；
  2. 看是不是外部 I/O（sink 写慢、维表 join 偶发查询慢）；
  3. 看是不是 GC 停顿或状态过大；
  4. 最后才考虑调并行度。

```scala
// 教学示意，不参与构建；常见反压源
// (1) 外部 sink 写入慢（JDBC 同步写）

// (3) 状态过大导致 GC 频繁
// (4) 数据倾斜导致某一个 subtask 成为瓶颈
```

### 11.7 多租户、配额与成本

《离线和实时大数据开发实战》第 2.1 节描述的**离线数据平台整体架构**，隐含了一个前提：平台属于多个团队共用。因此必须有：

| 机制 | YARN | K8s | 备注 |
| --- | --- | --- | --- |
| 队列 / 命名空间 | ✅ queue | ✅ namespace + ResourceQuota | YARN 的队列树更贴合大数据场景 |
| 资源配额 | `yarn.scheduler.capacity.*` | ResourceQuota / LimitRange | 保证「最小可用」与「上限」 |
| 优先级与抢占 | 支持（fair/DRF） | PriorityClass + preemption（Preemption API） | 优先给交互式查询 |
| 成本归因 | 按 queue/app 标签打标 | 按 namespace + label | **2026 年最重要的一件事：给每个作业打成本标签** |

```bash
# 教学示意，不参与构建；给作业打标签以便成本归因（示意，不要执行）
spark-submit --conf spark.app.resourceProfileId=rp-offline-batch \
  --conf spark.yarn.tags=cost-center=retail,team=data-platform  app.jar
```

> **成本治理的最小可行方案**：① 每个作业必须有 owner 与 cost-center 标签；② 设置队列配额上限；③ 每周跑一次成本报表，把「跑一年比买机器贵」的作业列出来。

### 11.8 版本演进与 2026 的现实

| 时间 | 事件 |
| --- | --- |
| 2011–2018 | YARN 成为事实标准（MapReduce/Spark/Tez/Samza 都跑其上）；《离线》第 2.1.1 节的架构即此形态 |
| 2018–2020 | Spark 2.x 支持 K8s 后端（beta）；Flink 支持 K8s |
| 2020–2022 | Kubernetes 成为主流目标；Spark on K8s 转正；Flink Operator 出现 |
| 2022–2024 | **存算分离成为默认**：对象存储 + 弹性算力；Serverless Spark（阿里云/阿里 MaxCompute、Databricks SQL、AWS EMR Serverless）流行 |
| 2024–2026 | **算力感知调度**（NUMA、GPU、分层存储）、自动扩缩成为平台标配；成本治理进入常态 |

🔧 **2026 必须补的四条**：

1. **K8s 是现在的默认目标平台**：Spark/Flink 都在 K8s 上有一等公民支持；两书写成时（2018/2022）YARN 才是默认。
2. **Serverless / 弹性算力**：小作业跑不完、大作业资源不够，是常驻集群的根本痛点；Serverless 与弹性队列解决了成本问题。
3. **存算分离下的运维变化**：shuffle 可能走远端、状态可能放对象存储、缓存与本地盘不再是默认 —— 监控指标随之改变。
4. **成本治理成为一等公民**：配额 + 标签 + 报表 + 自动降级（哪些作业可以容忍更长时间）。

## 三、核心精讲（续）：教学示意代码

```scala
// 教学示意，不参与构建；一个「资源与需求匹配」的粗算模型
// 目的：提交作业前先算一遍需要的资源，不要运行
object ResourcePlanning {
  def plan(dataGB: Double, coresPerExecutor: Int = 4, gbPerCore: Double = 3.0): Unit = {
    val executors = math.ceil(dataGB / 64.0 / coresPerExecutor).toInt   // 每 executor 处理 64GB/批
    val memPerExecutor = (coresPerExecutor * gbPerCore).toInt
    val totalCores = executors * coresPerExecutor
    println(s"数据 ${dataGB}GB -> executor=$executors, 每 executor ${memPerExecutor}G, 总核数=$totalCores")
  }
}
```

## 五、近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **多租户公平与抢占**：容量/公平调度中的**主导资源公平（DRF）**与抢占策略；在混布（离线批处理 + 在线服务）场景下如何避免互相干扰。
- **弹性与秒级伸缩**：Serverless 数据系统（如 AWS Lambda 上的数据处理、弹性 Spark）研究「冷启动 + 状态迁移」的成本。
- **可观测性**：流式系统的指标语义标准化（Flink 的 Metric Group、OpenTelemetry 的推广）；尾延迟的可观测性（用 HdrHistogram 测量）。
- **反压与队列理论**：反压本质上是排队系统，相关研究关注「**如何在反压时不牺牲尾延迟**」。

**工业界开源（star 数为 2026-09-25 用 `gh api` 实测）**：

| 项目 | star | 与本节的联系 |
| --- | --- | --- |
| `kubernetes/kubernetes` | **127976** | K8s 是 2026 年的默认目标平台 |
| `apache/hadoop` | **15669** | YARN 与其上的存量生态 |
| `apache/spark` | **44036** | Spark on K8s / YARN |
| `apache/flink` | **26362** | Flink on K8s / YARN |

| `facebook/rocksdb` | **32131** | 状态后端与本地存储 |

**可直接照做的运维清单**：

1. **提交前算资源**：用本章的教学示意模型估算 executor 数与内存，再和队列配额比对。
2. **开启 dynamic allocation 前先确认 shuffle service 已开**。
3. **建立三个告警**：① 队列 Pending 应用数 > 阈值；② 单作业耗时超过历史 P95；③ 流式作业「水位线停滞」。
4. **流式作业加空闲检测**：分区长时间无数据也要推进水位线（`maxIdleTime`），否则下游窗口永远不触发。
5. **区分「反压」与「数据积压」**：反压是降速（安全），数据积压才是风险。

## 六、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | 「YARN 是唯一选择」 | YARN 仍是大量存量集群的运行时，但 **2026 年新建集群的默认目标是 Kubernetes**；Spark/Flink 都有一等公民支持 | 《Spark 大数据实时计算》第 5 章（YARN/Standalone 假设）；《离线》第 2.1.1 节 |
| 2 | 「local 模式能跑通就能上集群」 | local 模式没有 shuffle 服务与网络传输，也无 GC 竞争；本地能跑不代表集群上正确 | 《Spark 大数据实时计算》第 5 章 |
| 3 | 「executor 越多越快」 | 超过集群可用核数只会排队；而且 executor 过多会导致 shuffle 请求爆炸与小文件 | 《Spark 大数据实时计算》第 5、7 章 |
| 4 | 「开了 dynamic allocation 就自动伸缩」 | 必须与 **External Shuffle Service** 一起开，否则 executor 回收会导致 stage 失败 | 《Spark 大数据实时计算》第 7 章未提这一组合 |
| 5 | 「反压意味着系统有故障」 | 反压是**设计良好的降速机制**；真正要排查的是「哪个算子是瓶颈」 | 《离线》第 8.4.3 节 Storm 的反压机制（概念同类） |
| 6 | 🔧 两书均未覆盖 **Flink on K8s 与 Application Mode** | 《离线》第 10–11 章只把 Flink 当框架介绍；2026 年的部署实践以 **Application Mode + K8s** 为主 | 《离线》第三篇；《Spark 大数据实时计算》第 5 章 |
| 7 | 🔧 两书均未覆盖 **Serverless / 弹性算力** | 常驻集群在成本上并不经济；2026 年弹性队列与 Serverless Spark 已成为一部分场景的默认选择 | 两书均无 |
| 8 | 🔧 两书均未覆盖 **成本治理（配额 + 标签 + 报表 + 自动降级）** | 《离线》第 2.3 节的数据管理只有「探查/集成/质量/屏蔽」四件事，**没有成本维度**；成本治理是 2020 年代才被提上日程 | 《离线》第 2.3 节数据管理四件套 |
