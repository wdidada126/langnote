## 二、核心精讲

### 8.1 为什么需要统一入口

《离线和实时大数据开发实战》第 1.2.1 节列举的采集传输技术（Flume、Sqoop、DataX 一类）解决的是「**把数据搬出来**」；但它们共同的局限是：**搬出来的数据是一次性的**，重复消费要重新采集。

消息中间件解决的正是这一点：

| 价值 | 说明 |
| --- | --- |
| **可重放** | 数据留在日志里，任何时刻可以从任意 offset 重读 —— Kappa 架构的前提（见 `01`） |
| **削峰** | 前端突发流量先进队列，下游按自己的节奏消费 |
| **解耦** | 生产方与消费方互不知晓；新增一个消费方不需要改生产方 |
| **顺序保证** | 在**分区内**保证顺序（全局顺序代价太高） |

### 8.2 Kafka 的模型

```
                    ┌──────────── topic: order_events (3 partitions) ─────────────┐
   producer ───────► │ P0: [o1][o2][o3][o4]...  offset 0,1,2,3                    │
                     │ P1: [o2][o4]...                                            │
                     │ P2: [o1][o3]...                                            │
                     └─────────────────────┬─────────────────────────────────────┘
                                           │ consumer group A 各自认领一部分区
                                           ├──► group A: c1 读 P0/P1，提交 offset
                                           └──► group B: c2 读 P2（不同消费者组互不影响）
```

要点（这些是理解一切 Kafka 问题的前提）：

1. **分区是并行的单位**：一个 topic 的并行度 = 分区数；**分区数一旦只能增加不能减少**（减少会丢数据）。
2. **offset 是游标**：消费者自己决定从哪里读；**自动提交（enable.auto.commit）是数据丢失的头号原因**（读到就提交，但处理可能失败）。
3. **consumer group 再均衡（rebalance）**：成员变化时重新分配分区；再均衡期间**停止消费**，大分区表上可能停顿数分钟。
4. **顺序只在分区内**：想保证「同一个订单的事件有序」→ **用订单 id 做 key**（写入时做分区映射，消费时单线程/并行度控制）。
5. **保留策略**：`retention` 决定日志保留多久（时间或大小）。**这直接决定了「能重放多久的历史」**——Kappa 式回补窗口不能超过这个。

```java
// 教学示意，不参与构建；一个「正确消费」的最小骨架（Java 风格，示意）
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id", "dw-consumer");
props.put("enable.auto.commit", "false");              // 关键：不要自动提交
props.put("isolation.level", "read_committed");        // 配合事务生产者
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Arrays.asList("order_events"));
while (running) {
  ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
  for (ConsumerRecord<String, String> r : records) {
    process(r);                                        // 处理
  }
  consumer.commitSync();                               // 处理成功后才提交
}
```

### 8.3 Pulsar 与 Kafka 的差异

| 维度 | Kafka | Pulsar |
| --- | --- | --- |
| 架构 | 每个 broker 既是计算也是存储（分区的 leader 负责读写） | **计算与存储分离**：broker 无状态，存储交给 BookKeeper |
| 扩展 | 扩分区要重分配数据 | broker 与 storage 独立扩缩 |
| 消费者模型 | consumer group（pull + offset） | subscriber 有多种（Exclusive / Shared / Failover），游标由服务端维护 |
| 多租户 | 主题级 ACL 为主 | **租户/命名空间**是一等公民，配额更好做 |
| 持久化 | 分区日志文件 | BookKeeper 的 ledger（多副本写入） |
| 生态 | 更成熟，几乎所有流引擎都有连接器 | Flink/Spark/Pulsar Functions 支持良好 |

> **工程选择建议**：单集群、简单场景 → Kafka 生态更省事；多租户、需要存算分离与分层存储的大平台 → Pulsar 更合适。**两本书成书时（2018 / 2022）Pulsar 的用户远少于今天，但趋势是增长的。**

### 8.4 Exactly-once 摄入

端到端 exactly-once 需要三件事同时成立（见 `07` 第 7.3 节）。在摄入侧：

| 手段 | 机制 | 适用 |
| --- | --- | --- |
| **幂等生产者** | 生产者带 `idempotence` / sequence number，重复发送被服务端去重 | 防止生产者重试造成的重复 |
| **事务生产者 + `read_committed`** | 一批消息原子写入；消费者只看到已提交事务 | **需要「一批要么全见要么全不见」时** |
| **外部系统幂等** | 写入端按主键去重 | 落到 DB/湖仓时的最后一道防线 |
| **消费-处理-提交三步一致** | 处理成功后才 `commitSync` | **必须做，否则是 at-least-once** |

```java
// 教学示意，不参与构建；事务性生产者的要点
// 目的：说明「一批消息原子可见」需要生产者与消费者两侧配合
props.put("enable.idempotence", "true");            // 幂等：重试不产生重复
props.put("transactional.id", "dw-writer-1");       // 事务标识
producer.initTransactions();
producer.beginTransaction();
producer.send(new ProducerRecord<>("ods_events", key, value));
producer.commitTransaction();
// 消费者侧：isolation.level=read_committed，才不会读到未提交事务的数据
```

> **重要提醒**：**幂等不等于精确一次的业务结果**。如果业务上「同一笔订单发两次也要算两次」，那幂等生产者帮不上忙 —— 幂等只解决「传输层重复」，不解决「语义层重复」。

### 8.5 CDC：把数据库当作数据源

2018 年的做法是 Sqoop/DataX 每日抽取；2026 年的主流是 **CDC（Change Data Capture）**：

```
MySQL binlog ──► Debezium（或 Flink CDC connector）──► Kafka ──► 流引擎 ──► 湖仓
     │                        │                                    │
   行的变更事件            快照 + 增量                      upsert 到 Iceberg/Hudi
```

- **捕获模式**：
  | 模式 | 原理 | 优点 | 缺点 |
  | --- | --- | --- | --- |
  | 基于日志（log-based） | 读 binlog / WAL（MySQL binlog、Postgres WAL、MongoDB oplog） | 低延迟、无侵入、保留全部变更历史 | 需要数据库权限、DDL 变更要处理 |
  | 基于查询（query-based） | 定期 `SELECT` + 比对 | 简单 | 有侵入、延迟高、可能漏更新 |
- **Debezium 的形态**：每个表一个 topic（或按 key 分区），事件形态是「**前后镜像**（before/after）+ 操作类型（c/u/d）+ 提交 LSN」；初始快照用 `snapshot.mode` 配置（initial / when_needed / never）。
- **Flink CDC**：直接在 Flink SQL 里 `CREATE TABLE mysql_suppliers WITH ('connector'='mysql-cdc', ...)`，与 `UPSERT INTO` 结合即可把 OLTP 变更实时同步到湖仓。

```sql
-- 教学示意，不参与构建；CDC 数据的典型形态（示意，不是可执行 SQL）
-- {"before":null,"after":{"id":1,"name":"A","amount":100},
--  "source":{"lsn":1234,"table":"orders"},
--  "op":"c","ts_ms":1710000000000}
-- op 的取值：c(创建) / u(更新) / d(删除) / r(读取快照)
```

> **CDC 的三个坑**：① **DDL 变更**（加列、改类型）会让下游 schema 不一致，需要 schema 演进机制；② **删除事件**需要下游表支持墓碑或 soft delete；③ **快照阶段与增量阶段的边界**（LSN 对齐），这是全量+增量一体化工具要解决的核心问题。

### 8.6 反压与背压传递

- **什么是反压**：下游处理变慢时，压力沿数据流**向上游传导**，最终让数据源也慢下来；而不是让数据无限堆积在内存里。
- Kafka Consumer 侧：靠的是**消息拉取的节奏**（`max.poll.records`、`fetch.max.bytes`）；注意 Kafka 是 pull 模型，**天然不会「推垮」下游**，但也可能「拉爆」本地内存（一次拉太多）。
- Flink 侧：网络层的 **credit-based flow control** 是反压的实现（下游给上游发 credit，上游按 credit 发送）。
- 一个常见的错误：**用「丢数据」来解耦**（比如设 `max.poll.records` 太小 + 超时太大，导致消息被跳过）。**丢数据永远不是解耦手段**。

### 8.7 版本演进与 2026 的现实

| 时间 | 事件 |
| --- | --- |
| 2011 | Kafka 论文（Kreps 等，NetDB 2011），最初是「日志处理」系统 |
| 2014–2017 | 日志作为架构核心的概念扩散（Kreps 的 *The Log* 博客）；Lambda 与 Kappa 之争 |
| 2017–2019 | Confluent 商业化；Kafka Streams、ksqlDB 出现；Exactly-once 语义在流引擎中确立 |
| 2018–2020 | Debezium 成熟（2019 年成为 CNCF 项目，2020 年后进入 LF 生态）；Flink CDC 前身 |
| 2021–2023 | **Schema Registry 普及**；Pulsar 分层存储；流引擎直连数据库（Flink CDC） |
| 2024–2026 | **Kafka 迁移到 KRaft（去 ZooKeeper）成为默认**；对象存储上的分层存储（tiered storage）商用；Pulsar 的存算分离成熟度提升 |

🔧 **2026 必须补的四条**：

1. **KRaft 与去 ZooKeeper**：Kafka 已能完全脱离 ZooKeeper 运行（KRaft 控制器），运维模型发生实质变化；两书写成时 ZooKeeper 仍是默认。
2. **CDC 取代离线抽取**：2018 年书里没有 CDC，2026 年它是实时数仓的第一入口；`debezium/debezium`（**13151★**）与 Flink CDC 是主流选择。
3. **Schema Registry 与数据契约**：Protobuf/Avro/JSON Schema 的中央注册表 + 兼容性策略，是「上游改字段不炸下游」的唯一可行方案。
4. **分层存储与对象存储**：Kafka/Pulsar 把冷数据放到 S3/OSS，这让「长时间保留（数月）用于回补」成为现实。

## 三、核心精讲（续）：教学示意代码

```java
// 教学示意，不参与构建；一个「幂等落库」的摄入骨架
// 目的：说明摄入链路中幂等性的落点，不要运行
public class IdempotentIngest {
  // 幂等键用业务主键，而不是自增 id
  void upsert(String bizKey, String payload) {
    // INSERT ... ON DUPLICATE KEY UPDATE ...  → 重复调用结果不变
    storage.upsert(bizKey, payload);
  }

  // 消费侧三步：poll → 处理 → 提交 offset
  // 若 process 抛异常，绝不 commit，让 Kafka 重投
}
```

> 这个骨架与 8.4 节呼应：**「重投 + 幂等」= at-least-once 上搭建 exactly-once**。

## 五、近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **流批统一的输入抽象**：把表当作「一个不断追加/更新的 changelog 流」，OLTP 与流处理在语义上统一（Flink CDC 与 Database Change Streams 的核心主张）。
- **乱序与延迟投递**：而这一方向的核心问题是「**如何在可重放的日志上表达「当前状态」**」—— 物化视图 + upsert 是答案。
- **多租户与隔离**：Pulsar 的分层存储与配额研究；Kafka 的 rack-aware 副本放置与配额（quota）机制。
- **存储成本**：日志类系统的分层存储（热在 SSD、冷在对象存储）是 2022 年后的热点，目标是把「保留一年数据」的成本降低一个数量级。

**工业界开源（star 数为 2026-09-25 用 `gh api` 实测）**：

| 项目 | star | 与本节的联系 |
| --- | --- | --- |
| `apache/kafka` | **33836** | 本章 8.2 节的对象；Exactly-once 摄入的现实基础 |
| `apache/pulsar` | **15339** | 8.3 节的对照对象 |
| `debezium/debezium` | **13151** | 8.5 节的 CDC 实现 |
| `apache/flink` | **26362** | 消费侧与 CDC connector 的主要运行平台 |
| `apache/spark` | **44036** | Structured Streaming 的 Kafka source/sink |
| `apache/nifi` | **6244** | 数据接入的另一条路线（可视化 ETL，逐渐被 CDC + 流引擎替代） |

**可直接照做的清单**：

1. **永远关掉 `enable.auto.commit`**，改成处理成功后 `commitSync`。
2. **分区数按「未来 1–2 年的并行度」一次给足**（只能增不能减），但别给太多（每个分区都是一份副本 + 文件句柄）。
3. **用业务 key 做分区键**，保证同一实体的顺序。
4. **保留期要大于你的最大回补窗口**：Kappa 式回补需要历史日志，只留 24 小时就无法回补一个月前的数据。
5. **上 Schema Registry + 兼容性检查**：上游改字段前先验证下游是否兼容。
6. CDC 上线前先做快照与增量的边界校验（同一条记录的全量值与增量值是否一致）。

## 六、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | 「消息中间件只是管道，数据不会丢」 | 只靠中间件不保证；**消费失败后不提交 offset**，并让消息重投，才是 at-least-once 的正确姿势 | 《离线》第 1.2.1 节（把中间件当管道描述） |
| 2 | 「自动提交 offset 最省事」 | 读到就提交 = **可能丢数据**（处理失败但 offset 已提交）；这是线上第一大丢数原因 | 《离线》第 8.4.1 节 spout 的可靠性（讲的是 Storm 的 ack，逻辑同类） |
| 3 | 「消息是有序的」 | 只在**同一分区内**有序；全局有序需要单分区（代价：无并行） | 《离线》第 8.2 节 Storm 的关键概念（并发度与并行） |
| 4 | 「Kafka 只能保留几天，不能做历史数据」 | 配置分层存储 / 更长的 retention 后，保留数月可行；这也是 Kappa 式回补的前提 | 《离线》第 2.2.2 节流计算技术未提保留期设计 |
| 5 | 「Exactly-once 是中间件的承诺」 | 中间件只提供**幂等与事务**两个工具；**业务幂等必须自己做**（否则重复消费照样重复结果） | 两书共有：《离线》第 8.4 节；《Spark 大数据实时计算》第 10 章 |
| 6 | 🔧 本书未覆盖 **CDC 取代离线抽取** | 《离线》第 1.2.1 节的采集技术（Flume/Sqoop/DataX）里没有 CDC；2026 年 MySQL/Postgres 的变更捕获是实时链路的第一入口 | 《离线》第 1.2.1、1.2.2 节 |
| 7 | 🔧 本书未覆盖 **Schema Registry 与数据契约** | 上游改字段导致下游作业失败是 2018→2026 年最常见的线上事故之一；Schema Registry（兼容性检查）是标配 | 两书均无 |
| 8 | 🔧 两书均未覆盖 **Kafka 去 ZooKeeper（KRaft）与分层存储** | 2024–2026 年 Kafka 的运维模型与成本结构已发生实质变化；「冷数据放对象存储」改变了保留策略的经济性 | 《Spark 大数据实时计算》第 5 章；详见 `10`、`11` |
