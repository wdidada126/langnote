## 二、核心精讲

### 12.1 数据质量的四类问题

| 类型 | 表现 | 常见根因 | 检测手段 |
| --- | --- | --- | --- |
| **重复** | 同一笔记录出现两次 | 消费侧 at-least-once 未幂等、上游重试、多路径写入 | 主键去重计数、`count(distinct key)` 与 `count(*)` 对比 |
| **丢失** | 记录根本没进来 | offset 自动提交后处理失败、上游丢数、分区写错 | 端到端计数对账（源端条数 vs. 下游条数） |
| **乱序或迟到** | 同一实体的事件顺序颠倒 | 多分区、网络延迟、重放 | 同 key 的 event time 单调性检查 |
| **不一致** | 同一指标在两个表里对不上 | 批流两套代码语义漂移、口径变更未同步 | 同名指标双写对比、快照对比 |

> **一句话方法论**：**先对账，再报警**。对账是「源端条数 = 经过 n 跳之后下游条数」这对最朴素的等式；报警是在对账发现偏差之后才发出的。

```scala
// 教学示意，不参与构建；一个最朴素的对账骨架
// 目的：说明「每一跳都记数」是质量工程的地基，不要运行
case class HopCount(stage: String, source: Long, downstream: Long) {
  def rate: Double = if (source == 0) 1.0 else downstream.toDouble / source
}
// 例如：ODS 1000000 → DWD 998000（99.8%）→ DWS 997500 → ADS 997500
// 任何一跳的比率突然下降，就是一次质量事件的信号
```

### 12.2 五条校验规则（可直接落到管道里）

| 规则 | 示例 | 实现位置 |
| --- | --- | --- |
| **唯一性** | `count(*) = count(distinct order_id)` | 管道内的 assert，失败即 fail 或 quarantine |
| **非空** | `null` 比例 < 1% | 同上 |
| **参照完整 / 值域** | `status in (0,1,2)`、`amount >= 0` | 同上 |
| **分布/趋势** | 日活波动不超过历史 ±30% | 事后看板 + 告警 |
| **及时性** | 数据落在 `dt` 分区的时间 < 约定 SLA | 调度系统的超时告警 |

```sql
-- 教学示意，不参与构建；一个典型的「数据质量检查」查询（示意，非可执行）
SELECT
  count(*)                                AS total,
  count(DISTINCT order_id)                AS distinct_keys,
  sum(CASE WHEN amount < 0 THEN 1 ELSE 0 END) AS negative_amounts
FROM dwd.orders
WHERE dt = '2026-09-25'
-- 期望：distinct_keys = total 且 negative_amounts = 0
```

> **工程取舍**：不要给每一跳都加「完整性校验」，那会让成本翻倍。经验做法是：**入口（source）与出口（ADS/服务层）强校验、中间层抽样式校验**。

### 12.3 数据血缘

| 类型 | 内容 | 获取方式 |
| --- | --- | --- |
| **技术血缘（physical lineage）** | 表 → 表、列 → 列的映射关系 | 解析 SQL（`sqllineage`、Calcite 的 SqlNode 遍历）、扫描调度配置 |
| **业务血缘（semantic lineage）** | 指标定义、口径来源 | 人工标注 / 指标平台 |

- **自动解析血缘的实际难点**：**不是解析，而是「上下文」**。同一句 `SELECT * FROM t` 在不同调度上下文（分区参数、视图展开、UDF 内部）里含义不同；而且大模型时代新增了一类血缘来源——**Notebook 与 AI 生成的代码**。
- **血缘的最大用途是「影响分析」**：改一张表的 schema 之前，先知道有多少下游作业会受影响。这正是《离线》第 7.3.2 节「开发规范」想解决的问题，只是 2018 年要靠文档与会议，2026 年要靠工具。

### 12.4 元数据与 catalog

| 元数据类别 | 例子 | 谁维护 |
| --- | --- | --- |
| 技术元数据 | 表结构、分区、格式、统计信息、文件位置 | 引擎 / 表格式自动 |
| 业务元数据 | owner、口径、SLA、敏感级别 | 人工（或数据平台） |
| 运行元数据 | 作业名、执行时间、成本、失败记录 | 调度系统 / 执行引擎 |
| 成本元数据 | 每作业消耗的算力与存储金额 | 计费系统 / 标签 |

```sql
-- 教学示意，不参与构建；schema 演进与生命周期管理的现实操作（示意）
-- (1) 加列不改历史数据（表格式能力）
ALTER TABLE dwd.orders ADD COLUMN remark STRING ;
-- (2) 时间旅行用于「误操作回滚」
CALL rollback_to_version('dwd.orders', 12345) ;   -- 各格式语法不同，示意
-- (3) 生命周期：冷数据转低成本存储或过期删除
ALTER TABLE dwd.orders SET TBLPROPERTIES ('write.format.default'='parquet') ;
```

> **为什么 schema 演进重要**：OLTP 侧改了字段（比如 `amount` 从 `int` 改 `decimal(18,2)`），OLAP 侧如果跟不上，就出现「下游看到的值跳变」。2026 年的解法是表格式的 schema evolution + Schema Registry 兼容性检查（见 `08`）。

### 12.5 成本治理

| 步骤 | 做法 |
| --- | --- |
| ① 打标签 | 每个作业必须有 `owner`、`cost-center`、`tier`（黄金/白银/青铜） |
| ② 设配额 | 队列或命名空间级别的资源上限；黄金 tier 可抢占青铜 |
| ③ 出报表 | 每周按 cost-center 汇总算力与存储成本 |
| ④ 自动降级 | 青铜 tier 允许更长延迟；超限自动限流或迁移到弹性队列 |
| ⑤ 优化清单 | 最长作业 Top 10、最大 shuffle 作业 Top 10、最大表 Top 10 |

> **一个常被忽略的存储成本**：**数据副本与中间结果**。多份 Hive 表 + 多份导出 + 历史全量快照，往往比计算成本更贵。因此「生命周期策略 + 去重建模」是成本治理里 ROI 最高的一步。

### 12.6 版本与迁移的工程纪律

| 场景 | 纪律 |
| --- | --- |
| Spark 升到 3.x/4.x | **先以兼容模式跑全量 SQL，收集行为变更清单**，再逐条修；用表格式的 time travel 保留可回滚点 |
| 表格式上线 | 先影子跑（新旧两条链路对比结果），确认一致再切流 |
| Flink 作业升级 | **用 savepoint**，并验证状态兼容性（算子 UIDs、状态结构） |
| 指标口径变更 | 保留旧指标名 + 新指标名双写一个周期，再下线旧的 |
| 数据结构变更 | 走 Schema Registry 的兼容性检查（backward/forward compatible） |

### 12.7 常见踩坑清单（按事故频率排序）

1. **offset 自动提交** → 处理失败但 offset 已提交 → 数据丢失。**关掉自动提交**（`08`）。
2. **算子里有副作用**（写外部系统、发消息、累加计数器）→ 重放时副作用重复执行 → exactly-once 失效。**算子写成纯函数**（`06`）。
3. **非幂等 sink** → 重放导致结果翻倍。**sink 必须支持 UPSERT 或事务**（`07`）。
4. **统计信息未采集** → 谓词下推失效、CBO 选错 join 顺序 → 查询慢十倍（`09`）。
5. **小文件泛滥** → 下游扫描变慢、元数据膨胀 → 定期 compaction（`09`）。
6. **倾斜** → 单 task 跑几小时 → broadcast join / 打散 / AQE（`03`、`05`）。
7. **状态无 TTL** → 磁盘被状态撑爆 → 设状态 TTL 并压测（`07`）。
8. **水位线不推进** → 窗口不触发、作业看似空闲实则积压 → 加空闲检测（`11`）。
9. **开了 dynamic allocation 没开 shuffle service** → executor 回收导致 stage 失败（`11`）。
10. **schema 变更未通知下游** → 下游作业直接失败 → Schema Registry + 血缘影响分析（`08`、`12`）。
11. **本地跑通就上线** → 集群上的网络/序列化/GC 问题完全没被覆盖（`11`）。
12. **没有回滚方案** → 上线新逻辑后结果错了只能重跑。**上线前先定「怎么回滚」**（12.6 节）。

## 三、核心精讲（续）：教学示意代码

```scala
// 教学示意，不参与构建；「quarantine（隔离）」机制的最小形态
// 目的：质量校验失败时的正确处置是隔离而不是静默丢弃，不要运行
object QualityGate {
  def check(rows: Seq[Row]): (Seq[Row], Seq[Row]] = {
    // 通过的行进入主链路，不通过的行进入 quarantine 表供人工排查
    val (good, bad) = rows.partition(isValid)
    (good, bad)
  }

  def isValid(r: Row): Boolean =
    r.getAs[String]("id") != null && r.getAs[Double]("amount") >= 0
}
```

> 这个模式的价值在于：**「坏数据」不是要被删掉，而是要被保存下来并归因**。删掉坏数据会让对账永远「看起来正常」。

## 五、近年研究与工业界开源实践（2015–2026）

**研究侧**：

- **数据质量的形式化**：把质量规则表达为**断言（assertion）/ 约束（constraint）**，并在查询计划中「免费」验证（例如利用统计信息证伪某些断言）；这是 2020 年代的一个值得关注研究方向。
- **血缘的形式化**：**column-level lineage** 的正确推导（多源合并、条件分支、聚合的语义），以及 UDF 与 AI 生成代码带来的新挑战。
- **可观测性**：OpenTelemetry 在数据管道中的落地；流式系统的端到端因果追踪。
- **成本模型**：云上的数据系统成本归因研究（区分计算、存储、网络与人工），以及「**绿色计算**」方向（能耗与碳足迹治理）。

**可直接照做的清单**：

1. **每个作业都写一行对账 SQL**（源端 vs. 下游），把结果作为调度任务的**断言**。
2. **坏数据进 quarantine 表，不要静默丢弃**。
3. **上线前明确回滚方案**：表格式回滚 / savepoint / 影子跑对比，三选一。
4. **所有作业打标签**（owner、cost-center、tier），每周出成本报表。
5. **schema 变更走 Schema Registry + 血缘影响分析**。

## 六、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | 「数据质量靠事后看板发现」 | 质量规则要**落在管道里**（每跳的对账、出口的断言）；看板只能发现，不能止损 | 《离线》第 2.3.3 节（数据质量仅列为一名词） |
| 2 | 「坏数据直接过滤掉就好」 | 坏数据要**隔离（quarantine）+ 归因**；直接过滤会让对账永远看起来正常 | 《离线》第 2.3.3 节 |
| 3 | 「血缘只能靠人工维护」 | 技术血缘可以自动解析（SQL 解析、调度配置扫描）；业务血缘才需要人工标注。**两者都要有** | 《离线》第 2.3.2 节数据集成未涉及血缘 |
| 4 | 「加了校验规则性能会明显下降」 | 正确的做法是**入口与出口强校验、中间层抽样校验**；在每一跳都加校验会让成本翻倍 | 《离线》第 5 章（Hive 优化不涉及质量开销） |
| 5 | 「上线前没想好怎么回滚也能凑合」 | 表格式的时间旅行、Flink 的 savepoint、影子跑对比，都能在**几分钟内**完成回滚；没有回滚方案的上线不要做 | 《离线》第 7.3.3 节流程规范只提到开发流程 |
| 6 | 🔧 两书均未覆盖 **成本治理维度** | 《离线》第 2.3 节的数据管理只有「探查/集成/质量/屏蔽」四件事；2026 年必须补上**成本治理**（标签、配额、报表、自动降级） | 《离线》第 2.3 节 |
| 7 | 🔧 本书未覆盖 **Schema Registry 与不兼容变更的治理** | 上游改字段是 2020 年代以来最常见的线上事故之一；需要**兼容性检查 + 影响分析**双保险 | 《离线》第 7.3.2 节开发规范；《Spark 大数据实时计算》第 8 章 |
| 8 | 🔧 本书未覆盖 **ANSI 迁移作为质量事件** | Spark 的 ANSI 化会让一批「偷偷能跑」的隐式转换作业**开始报错**；这是一次需要清单化管理的变更，而不是单纯的升级 | 《Spark 大数据实时计算》第 8–9 章；详见 `04`、`10` |
