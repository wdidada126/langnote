> 以及「什么时候别指望移动」。

## 核心概念速览（中英对照）

- **移动语义** — move semantics：以窃取资源实现 O(1)「转移」的构造/赋值；被移对象进入有效未定状态。
- **右值引用** — rvalue reference：`T&&`（T 已定），只接将亡值；存在的唯一理由是给移动操作当锚点。
- **转发引用** — forwarding reference：`T&&`（T 被推导），左值实参推 `T=U&`、右值实参推 `T=U`。
- **`std::move`** — std::move：**无条件**把表达式转成右值引用名字的函数模板——不产生任何机器码，不移动。
- **`std::forward`** — std::forward：**条件**转换：`T=U&` 转回左值，`T=U` 转成右值；「完美」的保真部分。
- **引用折叠** — reference collapsing：`X& &&`→`X&`、`X&& &&`→`X&&`；只在模板推导/typedef/`using`/`decltype` 四场合发生。
- **依转发引用重载** — overloading on forwarding reference：万能引用吃掉一切重载（`T=std::string` 可精确匹配
  任何实参），是接口设计的经典反模式。
- **完美转发失败** — perfect forwarding failure：0/NULL、裸 `{…}`、`std::array`、位域、模板/重载函数名、
  默认模板实参——实参在转发点「失真」的清单。
- **移动假定三律** — assume move…：可能不存在（老类型）、可能昂贵（`std::array`、`std::string` 的 SSO 时代）、
  可能未被使用（调用方不写 `std::move` 就永远不会发生）。

## 动机：三个语法零件其实只解决两个问题

问题一：**怎样把「资源窃取」表达为函数 overload 的选择信号？** → 右值引用 + `std::move`。
问题二：**怎样写一个包装函数，不丢失实参的类别信息？** → 转发引用 + `std::forward` + 引用折叠。
Item 23–28 把这四件事拆到实现层（两个 cast + 一条折叠规则），Item 29–30 再告诉你
这套机器在什么输入下失灵。

## 机制：把两个 cast 讲透

### 1. `std::move` 与 `std::forward` 都是纯类型运算（Item 23/25）

```cpp
// 🔧 已实测（脚本 s3_move_forward.cpp，g++ 15.2 -std=gnu++23）：自己实现 move
template<typename T>
constexpr std::remove_reference_t<T>&& my_move(T&& v) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(v);   // 注意：返回引用，不是「移动后的对象」
}
static_assert(std::is_same_v<decltype(std::move(x)), int&&>);  // x 仍是 int 左值
```

`std::move(x)` 之后，`x` **还是那个 x**；是否发生移动，取决于是否有接 `T&&` 的构造函数
被选中。这就是 Item 25 的分工依据：

- 形参是**右值引用**（`std::string&& name`）：它只可能从右值绑来 → 无条件 `std::move(name)` 交给下游。
- 形参是**转发引用**（`template<typename T> … T&& name`）：它可能从**任何**类别绑来 →
  必须 `std::forward<T>(name)` 把当年推导记下的类别信息还原。
- **两个都不是**：普通左值引用/按值形参——别画蛇添足地 move，否则破坏 NRVO/具名返回值拷贝。

### 2. 转发引用识别四步程序（Item 24）

1. 形参/变量声明形如 `T&&` 或 `auto&&`？
2. 存在**正发生的类型推导**（模板 `T`、`auto`、`using` 别名模板实参）？
3. 是用**纯实参**直接初始化（`T&& x = expr;`，不是 `T&& x = std::declval<T&&>();` 之类）？
4. 右值引用路径排除：`std::vector<int>::iterator&&`、`Widget&&` 里没有任何推导 → 真右值引用。

`auto&& w = std::move(v);` 是转发引用（推 `T=Widget`，得 `Widget&&`）；
`Widget&& w = std::move(v);` 是右值引用——两行都能用，第二行没有「类别记忆」，也就
没资格当转发参数。

### 3. 引用折叠：唯一一条「不对称」规则（Item 28）

```text
X& &    → X&         X& &&   → X&        ← 只要沾一个左值引用，结果左值引用
X&& &&  → X&&        （仅 右值&&右值 得右值引用）
```

数组类型没有折叠；模板参数被推为「引用类别」这件事，唯一出口就是 `T&&` 的折叠。
左值实参推 `T = X&` 的设计，使 `std::forward<T>` 能靠「T 是否带引用」做条件 cast——
整个完美转发是「推导规则（第 1 章）× 折叠规则（本章）」的乘法。

### 4. 万能引用重载为什么会吞一切（Item 26）

```cpp
// 🔧 示意：f 想接 short，实参给 int——重载版报编译错误，转发引用版静默接受
void g(short);                       // 窄化需转换 → int 实参可匹配（整型提升路径），但 f(Widget…) 族灾难更深
template<typename T> void f(T&&);    // int 实参：T=int，精确匹配，零转换，永远赢过 g
```

真正致命的是三类实参：整数字面量/`0` 想传指针（转发引用优先匹配 → `p` 收到 0，
`*p` 即 UB，Item 8 的 nullptr 在这里回魂）、派生类指针想传基类引用、
以及「单参构造函数」提供的隐式转换（`std::function`、`std::string` 的 ctor 都会输给 T&&）。
Item 27 的药方按代价排序：**按值（廉价可移动类型）→ 显式两重载 → tag dispatch →
CRTP 静态多态**；C++20 后首选 concepts 约束（见演进节）。CRTP 的讲解本仓库有专文：
[../../cpp/CRTP.md](../../cpp/CRTP.md)。

### 5. 完美转发失败清单（Item 30）+ 🔧 实测

```cpp
// 🔧 已实测（脚本 s3_move_forward.cpp 的 Holder::set）：
h.set(std::pair<int,int>{1, 2});   // OK
h.set({1, 2});                     // 编译失败：no matching function for call to 'Holder::set(<brace-enclosed…
```

清单与根因：裸 `{…}`（推导拒绝无类型列表）、`0`/`NULL`（整数身份，见 Item 8）、
`std::array`（聚合初始化没有构造函数可转发）、位域（不能取引用 → 绑不上 T&&）、
模板函数/重载函数名（缺类型上下文，`decltype` 都救不了）、带默认模板实参的函数名。
前三个都有显式构造解；位域与函数名需要包装 lambda——「转发一切」从来不是免费承诺。

### 6. Item 29 三律的量化版

- **不存在**：C 风格数组、`std::array`（按成员拷贝语义）、未写移动的老类型（对照
  [03 章](03-转向现代C++.md) Item 17 矩阵：一个空析构即出局）。
- **昂贵**：`std::array` O(N)；`std::string` 的 SSO 下小串退化为 memcpy（实现相关）；
  含 `shared_ptr` 的容器移动仍需处理控制块？——不需要（指针即资源），但**移动后
  `empty()` 承诺**是 libstdc++ 习惯而非标准保证。
- **未被使用**：调用方忘了 move，一切机制原地拷贝；`-Wpessimizing-move`/clang-tidy
  `performance-move-const-arg` 是工业补救。🔧 实测佐证：`Legacy`（只有析构+拷贝）在 vector
  扩容中 copies=15 moves=0；换 noexcept 移动类型后 moves=15 copies=0（脚本 s4）。

## 权衡

移动优化的收益边界在**大资源对象**（堆缓冲、句柄）；对平凡可拷贝小类型，
`std::move` 反而可能抑制 NRVO/寄存器传参。完美转发换的是「泛型库作者的心智负担」，
付的是「错误信息变长、Item 30 清单变坑」——业务代码用「按值 + move」（Item 41）
常比转发引用便宜一层抽象税。

## 相邻概念对比

| 对子 | 分界 |
| --- | --- |
| 右值引用 vs 转发引用 | 有无推导；`T&&` 的身份由声明处决定，不由实参决定 |
| `std::move` vs `std::forward` | 无条件 cast vs 条件 cast；前者服务重载选择，后者服务类别保真 |
| 引用折叠 vs 类型衰减 | 折叠发生在**类型层**（引用组合化简），衰减发生在**推导层**（数组/函数/顶层 const 丢弃） |
| 转发引用 vs C++20 `auto` 参数 | `auto&&` 保类别，`auto` 按值切类别；语义差即「零转发」vs「必拷贝/移动」 |

## 最新演进与工业实践

- **C++17 保证的拷贝消除**：prvalue 不再物化临时对象（`return Widget{…}` 直接构造在目标处），
  Item 23/25 关于「返回局部对象」的部分论证被改写在更干净的语义上；移动仍然必要，
  但「移动作为返回优化」的叙事让位给「prvalue 直接初始化」。
- **概念约束（C++20）**：`template<std::copyable T>`、`same_as`/`derived_from` 可以把
  Item 26 的「万能引用吞一切」直接改写成**约束重载**——tag dispatch/CRTP 两大替代方案
  的多数用途退休（本仓库 [../C++20模板元编程.md](../C++20模板元编程.md) 有体系化展开）。
- **deducing this（C++23）**：[P0847R7「Deducing this」](https://wg21.link/P0847R7)（Ažman/Brand/Deane/Revzin，
  经 wg21.link 解析核实存在）让成员函数按实参类别取 `this`（`this auto&&`），CRTP 的
  「静态多态转发」部分职能被语言本身吸收。🔧 已实测链式 `add` 示例（见 [09 篇](09-专题-书后演进时间线.md)）。
- **`std::forward_like`（C++20）**：按「引用类别 + const」转发类型而非值，补上嵌套转发（如
  转发 `tuple` 元素）的最后一块。
- **工业体现**：[Folly](https://github.com/facebook/folly) 的 `folly::futures` 与
  `try`/`semi` 链、[range-v3](https://github.com/ericniebler/range-v3) 的 `pipeable` 机制
  都是「转发 + 类别保真」的重度用户；libstdc++ 对 `std::vector` 扩容的移动选择
  （`move_if_noexcept` 的 `_GLIBCXX_USE_NOEXCEPT` 路径）可直接读源码验证
  （[microsoft/STL](https://github.com/microsoft/STL) 的同名文件也有注释版）。
- **对本书结论的修订**：机制全部存活；Item 26/27 的「替代方案清单」头部插入了
  concepts 约束这一新首选；Item 29 的「假定移动不存在」在 C++20 时代可降级为
  「假定移动存在但 noexcept 要自己挣」。

## 常见误区

1. 「`std::move` 会移动」——它只是命名成右值；移动由**被选中的构造函数**做（🔧 s3 实测）。
2. 「`T&&` 声明的形参都可以 forward」——只有**发生过推导**的才有资格；对 `Widget&&` 形参
   写 `std::forward<Widget>(w)` 是合法但错误的伪装（真右值引用该 move）。
3. 「完美转发保证零开销」——类别保真是语义层的；构造/移动该发生还是发生（Item 29 的「贵」）。
4. 「移动后的对象只能用一次」——只能用**接口保证的**操作；标准容器普遍保证可重新赋值，
   但别赌 `size()`（🔧 s5 的移动后空 pImpl 即教训：有效未定状态可以是「解引用即崩」）。
5. 「引用折叠适用于数组」——只折叠引用；数组左值绑 `T&&` 得 `T = U(&)[N]`（🔧 s1 实测）。
