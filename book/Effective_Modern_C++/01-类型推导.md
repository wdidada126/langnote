# 第 1 章 型别推导（Type Deductions，Items 1–4）

> 对应原书第 1 章（Items 1–4）。单文件大纲见 [../Effective_Modern_C++.md](../Effective_Modern_C++.md)；
> 本目录导航 [00-总览与阅读地图.md](00-总览与阅读地图.md)｜系列索引 [../C++系列·总索引.md](../C++系列·总索引.md)。
> 本章是全书的「语法物理学」：后面 38 条里几乎所有现象（转发引用、`auto`、`decltype(auto)`、
> lambda 闭包、完美转发失败）都建立在「编译器如何从实参推出形参类型」这一件事上。

## 核心概念速览（中英对照）

- **模板型别推导** — template type deduction：函数模板调用时由实参反推 `T` 的规则，分按值/按引用/`T&&` 三档。
- **转发引用（万能引用）** — forwarding (universal) reference：`T&&` 且 `T` 正在被推导且初始化是纯实参时，
  能同时接左值与右值的引用形参。
- **型别衰减** — type decay：按值推导时数组→指针、函数→指针、顶层 `const`/引用被剥除的统一化。
- **auto 型别推导** — auto type deduction：与模板推导几乎同规则，唯一分叉是 `{…}` 一律推成 `std::initializer_list`。
- **decltype** — decltype：按表达式的**语法类别**取类型：具名实体取声明类型；除具名外的左值表达式取 `U&`；右值取 `U`。
- **表达式类别** — expression categories：lvalue / rvalue / xvalue 等，是推导与重载决策的输入而非输出的属性。
- **初始化列表推导** — initializer-list deduction：`std::initializer_list` 参与推导是 auto 与模板的分裂点。
- **推导结果查看** — inspecting deduced types：`static_assert` + `typeid`、`abi::__cxa_demangle`、cppinsights 等工具。

## 本章地图

| Item | 核心论点（复述，非原文引用） |
| --- | --- |
| 1 | 模板推导三规则：按值（衰减）、按 `const T&`（保 const 不衰减）、`T&&`（左值推 `T=U&`，靠引用折叠收口） |
| 2 | `auto` 推导 = 模板推导 + 一条大括号特例；`auto&&` 因此几乎总是转发引用 |
| 3 | `decltype` 从语法取类型；`decltype((x))` 因括号是左值表达式而得 `x&`——这是 C++11 保留的坑 |
| 4 | 用 `static_assert`/`typeid`+demangle/编译器报错文本/cppinsights 四类手段看清推导结果 |

## 动机：为什么从推导讲起

C++11 引入 `auto` 和转发引用后，「写了什么类型」与「实际是什么类型」脱钩。
Meyers 把推导放在第 1 章，是因为后面每一条建议的判断力都来自这里：Item 24「区分转发引用与
右值引用」的判定程序、Item 28「引用折叠」、Item 33「对 `auto&&` 形参用 decltype 再 forward」、
Item 6「auto 推出代理类型」——全是推导规则的直接推论。不理解推导规则的人，只能靠记忆口诀，
而口诀在 `decltype((x))`、`const auto& x = expr`、数组实参这些边角上必然出错。

## 机制：三套规则的系统化

### 1. 模板推导（Item 1）

```text
参数声明           实参类别        推导结果 T        形参实际类型
T (按值)          int&           int               int
T (按值)          const int      int               int         ← 顶层 const 被剥
const T&          const int      int               const int&  ← const 由 & 承担，不衰减
T&                int            int&              int&        ← 无折叠歧义
T&&               int 左值        int&              int&        ← 引用折叠 & + && = &
T&&               int 右值        int               int&&
```

两条特殊路径：**数组**按值推导退化为元素指针（`void f(T)` + `int[3]` → `const int*`，
若 `T` 同时承担默认实参则推成 `const int*` 而非 `int*`）；**函数指针**同理。
转发引用的识别要同时满足三点：写法是 `T&&`、`T` 正被推导、初始化是**纯实参**
（`std::vector<int>&& r = std::move(v);` 里没有任何推导，是货真价实的右值引用）。

### 2. auto 推导（Item 2）

把 `auto` 当模板形参、`auto&&` 当 `T&&` 即可套用全部规则，唯一例外：

```cpp
// 🔧 已实测（g++ 15.2 -std=gnu++23）：模板遇 {1,2} 推导失败，auto 遇 {1,2} 得 initializer_list
auto x1 = {1, 2};              // std::initializer_list<int>
// template<typename T> void f(T p);  f({1, 2});   // 编译失败：T 无法从裸大括号推导
```

「模板推不出、auto 能推出」的非对称性是 Item 31/33 与 lambda 形参（C++20 前无 `auto` 参数）
诸多讨论的源头。另一个后果：`auto x = 5; x = {1,2};` 合法但语义是单元素初始化列表赋值——
把 5 换成 0 会安静地清掉语义，属于大括号规则的暗面。

### 3. decltype（Item 3）

`decltype` 不做任何值分析，只看表达式语法：具名变量/函数 → 声明类型；
函数调用 → 返回值类型（除非返回引用）；**其余表达式**：左值 → `U&`，右值 → `U&&`，将亡值 → `U&&`。

```cpp
// 🔧 已实测：四行 static_assert 全部编译通过
int x = 0;
static_assert(std::is_same_v<decltype(x),   int>);    // 具名：声明类型
static_assert(std::is_same_v<decltype((x)), int&>);   // 括号：左值表达式 → 带引用
static_assert(std::is_same_v<decltype(x+0), int>);    // 纯右值 → 无引用
```

数组/表达式不能折叠：`decltype((arr))` 是 `int(&)[3]`，而 `int&&` 接不了数组左值——
这是 `decltype(auto)` 返回悬垂引用的经典入口（`return (local);` 加括号即从「移动返回值」
变成「返回局部变量引用」）。

### 4. 查看工具（Item 4）

- 🔧 `static_assert(std::is_same_v<decltype(v), Expected>::value, "")`：编译期钉死，成本最低。
- `std::cout << typeid(v).name()` + ABI demangle：运行时快查（注意 `typeid` 会再做一次衰减，
  对引用/顶层 const 失真——书里点过，本章实测确认）。
- 编译器报错文本（故意赋错类型）与 [cppinsights.io](https://cppinsights.io)（把 auto/lambda
  展开成等价代码）是两把零依赖的梯子；本仓库另有笔记登记该工具：[../../cpp/cppinsights.md](../../cpp/cppinsights.md)。

## 权衡

- 推导让接口**与实参类别同构**（转发引用零开销），也让接口**失去可诊断性**：
  模板错误从「类型不符」变成「找不到重载」。Item 4 的存在本身就是对 Item 1–3 复杂性的坦白。
- `const auto&` 延长临时对象生命期而 `auto` 不（拷贝后临时销毁）：对 `vector<bool>::operator[]`
  的代理引用取 `const auto&` 会把代理（而非位值）的多生命期绑上——语义从「快照」变成「活引用」。
- 数组推导退化的例外（默认实参是 `const int*` 时元素 const 保留）说明：规则的目的不是对称，
  而是「让常见代码按预期工作」——这与 D&E 里 Stroustrup 对兼容性的执念一脉相承
  （见 [../C++语言的设计与演化.md](../C++语言的设计与演化.md)）。

## 相邻概念对比

| 对子 | 分界 |
| --- | --- |
| 模板推导 vs auto 推导 | 唯一差异是大括号：模板拒绝、auto 给 `initializer_list` |
| `auto&&` vs 右值引用 `T&&`（T 已知） | 有无「正在发生的推导」；写法相同语义相反 |
| `decltype(x)` vs `decltype((x))` | 具名 vs 一般表达式；括号改变类别而不改变值 |
| `decltype(auto)` vs `auto` | 前者套用 decltype 规则（带引用），后者套用模板按值规则（衰减） |

## 最新演进与工业实践

- **CTAD（C++17）**：类模板实参可由构造函数推导（`std::pair p{1, 2.0};` 即 `pair<int,double>`），
  并可用推导指南定制。它把「推导」从函数参数扩展到对象声明，Item 2「auto 无处不在」的口径
  在声明处进一步兑现。🔧 已实测：`Box b{42};` + `static_assert(std::is_same_v<decltype(b), Box<int>>)`。
- **约束 auto / 缩写模板（C++20）**：`void f(const Numeric auto& x)` 是 `template<Numeric T> void f(const T& x)`
  的糖——推导规则一字未改，但可以在推导层就拒绝非法实参，部分回收了「失去可诊断性」的代价。
- **标准文本与查阅**：推导规则的权威表述见 [cppreference 的 Deducing auto 与 Template argument deduction 页](https://en.cppreference.com/w/cpp/language/auto)；
  `decltype` 的括号规则在 [cppreference decltype 页](https://en.cppreference.com/w/cpp/language/decltype)有与本章实测一致的示例。
- **工业体现**：[Abseil](https://github.com/abseil/abseil-cpp) 的 `absl::string_view` 工厂函数
  与 ranges 类模板（如 `std::ranges::subrange a(b, c)`）都吃 CTAD 红利；
  [range-v3](https://github.com/ericniebler/range-v3) 的管道 `|` 组合子把「实参类别决定拷贝/移动」
  的推导规则用到了机制层（view 必须可平凡拷贝，否则推导出的闭包会悬垂）。
- **对本书结论的修订**：Item 1/2 的机制全部存活；Item 4 的工具生态从「故意赋错类型」升级为
  cppinsights + [Compiler Explorer](https://godbolt.org) 双件套（均已实测于本目录各章）。

## 常见误区

1. 「`T&&` 就是右值引用」——忘记「`T` 正在被推导 + 纯实参」判定（Item 24 专讲）。
2. 「`decltype` 会对表达式求值」——它是纯语法运算，`decltype(i++)` 中 `i` 不会自增。
3. 「auto 推出的类型和初始化表达式一样」——`auto b = vb[0];` 推的是代理类型不是 `bool`（第 2 章主场）。
4. 「数组当模板实参永远退化」——`f(arr)` 中若 `T` 被数组引用绑住（`T&&`），保留维度信息。
