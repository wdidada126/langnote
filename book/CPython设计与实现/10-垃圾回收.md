# 10 垃圾回收（循环引用）

> 原书 pp. 第 10 章（具体页码以实体书为准 🔧）

## 本章地图

| 节 | 内容 | 结论 |
|---|---|---|
| 引用计数为主 | 即时释放 | 多数对象靠它 |
| 循环 GC | 分代收集 | 兜底循环引用 |
| 分代模型 | 0/1/2 代 | 新对象更易死 |
| GC 阈值与暂停 | 性能代价 | 大对象图触发慢 |
| __del__ 陷阱 | finalizer | 循环 + __del__ 难回收 |

## 核心精讲

**1. 引用计数即时释放**。对象 `ob_refcnt` 归零立即 `tp_dealloc` 释放，确定性强、无停顿——这是 Python 默认的内存回收主力。

**2. 循环收集器**。引用计数无法处理循环引用（a 引用 b、b 引用 a），由**循环 GC**（`gc` 模块，基于分代+可达性）兜底。对象分 0/1/2 三代，新对象在第 0 代，存活则升级；阈值触发扫描。

**3. 代价与陷阱**。GC 扫描大对象图会暂停；含 `__del__` 的循环引用因终结顺序不确定，收集器保守地放入 `gc.garbage`，需手动处理。容器类型（list/dict/set/自定义）才入 GC 跟踪，原子类型不入。

```python
# 教学示意，不参与构建
import gc
class Node:
    pass
a = Node(); b = Node()
a.other = b; b.other = a      # 循环引用
del a, b                       # 引用计数不为 0，靠 gc 回收
gc.collect()                   # 显式触发
```

## 版本演进

- 3.4 起循环 GC 用「并行引用计数 + 增量/并发」思路改进，减少长暂停。
- 3.12 `gc` 支持 `freeze`/`disabled` 更细控制；`sys.monitoring`（PEP 669）可观测 GC 事件。
- immortal 对象（PEP 683，3.12）不参与引用计数变动，减少 GC 干扰。

## 近年研究与工业界开源实践（2015–2026）

- 工业界「对象池/缓存」要避免无意循环引用；`weakref` 打破循环。
- 长生命周期服务监控 `gc`  Stats，定位停顿。

## 常见误区与本书需修正之处

- 🔧 误：原书（3.10 基线）未含 immortal 对象与 GC 关系；应补。
- 误：以为「有 GC 就不会泄漏」——全局 dict 缓存、未关资源、循环 + `__del__` 都会泄漏。
- 误：`gc.collect()` 很便宜——大对象图扫描有真实成本，勿高频调用。
