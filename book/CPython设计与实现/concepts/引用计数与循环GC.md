# 概念专篇：引用计数与循环 GC

> 跨章概念：与第 02 章（对象模型）、第 09 章（内存）、第 10 章（GC）强相关。
> 校准到 2026（含 immortal 对象 PEP 683）。

## 1. 引用计数（主回收）

- 对象 `ob_refcnt` 创建=1，赋值/传参 +1，`del`/出作用域 -1，归零立即 `tp_dealloc` 释放——确定性强、无停顿。
- 是 Python 默认的内存回收主力，绝大多数短命对象靠它即时释放。

## 2. 循环引用（GC 兜底）

- 引用计数无法处理 `a↔b` 互相引用，由**循环垃圾收集器**（`gc` 模块）基于可达性兜底。
- 分代模型：0/1/2 代，新对象在第 0 代，存活升级；阈值触发扫描。只跟踪容器类型（list/dict/set/自定义），原子类型不入。

## 3. 代价与陷阱

- 大对象图扫描会暂停（GC 停顿）；含 `__del__` 的循环引用因终结顺序不确定被放入 `gc.garbage`，需手动处理。
- 全局缓存、未关资源、循环 + `__del__` 是常见「内存泄漏」来源——引用计数 ≠ 不会泄漏。
- 打破循环用 `weakref`。

## 4. 3.12+ 变化

- **immortal 对象（PEP 683）**：常量/单例引用计数冻结，减少 GC 与原子操作干扰，是 no-GIL（PEP 703）前置。
- `sys.monitoring`（PEP 669）可观测 GC 事件；`gc.freeze()`/`gc.disable()` 更细控制。

## 5. 常见误区

- 误：「有 GC 就不会泄漏」——全局 dict 缓存、未关连接、循环 + `__del__` 都漏。
- 误：`sys.getrefcount(x)` 读数是真实值 +1（含函数参数自身引用）。
- 误：高频 `gc.collect()` 很便宜——大图扫描有真实成本。
