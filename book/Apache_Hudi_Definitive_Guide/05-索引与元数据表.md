# 第 5 章 通过 Index 提高效率（索引与元数据表）

> 原书章题（译系列核实）：通过 index 提高效率。小节地图：Hudi 中的索引概览 → 写入加速的索引（通用多模态索引、写侧索引、写侧索引选择对比）→ 读路径上的索引加速（数据跳过、等值匹配、表达式索引）→ 构建合适的索引 → 总结。
> 机制口径以官方文档 Indexes / Metadata 两章为准。本章与第 6 章互为因果：索引降低写放大，表服务偿还读放大。

## 本章地图

> 一句话：**Hudi 的索引不是数据库的 B+ 树，而是"给文件贴标签"的查找结构——写侧回答"这个 key 在哪个 file group"，读侧回答"哪个文件可能满足这个谓词"；metadata table 把这些标签本身也变成一张 Hudi 表。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 索引的双重身份 | 写侧定位 file group / 读侧裁剪文件 | 两套问题，两套结构 |
| 5.2 metadata table | record_index/column_stats/files/partitions 等 partition | 索引的地基，可回退纯文件系统 |
| 5.3 Bloom index | 文件级 bloom filter + 列统计 | 默认老选手，高基数更新弱 |
| 5.4 Simple/Bitmap/Partition/Bucket | 各种写侧索引的权衡 | global vs non-global 是分水岭 |
| 5.5 Record index | key → (partition,fileID) KV 直查 | O(1) tagging，推荐默认 🔧 |
| 5.6 HFile/RocksDB 索引后端 | metadata 表支持存原生索引 | 规模与写吞吐的兜底 |
| 5.7 读侧加速 | column stats、数据跳过、表达式/函数索引 | 非键谓词的救星 🔧 |
| 5.8 选型决策树 | 按更新模式/分区语义/规模选 | 一张表收敛全章 |

## 核心精讲

> **教学示意，不参与构建。**

### 5.1 索引在写流程里的位置（回链 03 章 ②）

```text
tagging：输入 N 条记录 × "key 属于哪个 file group?"
无索引（裸扫） = N × 全表文件扫描 → 不可能
索引的存在意义：把该查找从 O(文件数) 压到 O(1) 或 O(候选文件数)
```

- **local vs global（非分区 vs 全局）**：
  - local index：只在记录所属分区内找 file group → 要求 record key 不跨分区移动。
  - global index：跨分区回答"这行现在在哪" → 支持"分区键变化 = 迁移"语义，但更新面更大（要删旧分区引用）。
  - 官方参数口径：`hoodie.index.type = GLOBAL_BLOOM | BLOOM | SIMPLE | GLOBAL_SIMPLE | RECORD_INDEX | BUCKET | PARTITION`。

### 5.2 metadata table：表之下的表

- 位置 `.hoodie/metadata/`，本身是一张 MOR 内部 Hudi 表；由写入提交时异步/同步维护。
- 官方列出的 partition 类型（节选）：

| Partition | 内容 | 服务的查询 |
| --- | --- | --- |
| `record_index` | (partitionPath, recordKey) → fileID | record index 的存储 |
| `column_stats` | 每文件每列的 min/max/nullCount/avgLen | 写侧 bloom/simple 索引加速 + 读侧数据跳过 |
| `bloom_filters` | 文件级 record key bloom | bloom 索引加速 |
| `files` / `files_small` | 当前有效 file slices 清单 | 读规划（免扫 .hoodie） |
| `partitions` | 分区摘要 | 目录/统计 |
| `functional_index` | 表达式派生列的索引数据 🔧 | 表达式索引 |

- **回退与修复**：`hoodie.metadata.enable=false` 可退回纯文件系统索引；`init metadata table` / `rollback` / CLI 重建（第 9 章表操作）。
- 书中（及官方 RFC）把 metadata table 视作 1.x 一切"记录级操作 O(1) 化"的前提。

### 5.3 Bloom index（默认老选手）

```text
读每个候选 base file 的 footer：
  ① 用列统计先粗筛（min/max）
  ② 再用 record key 的 bloom filter 精筛
  → 得到"可能含此 key"的文件集合，再在 merge 阶段真校验
```

- 优点：零维护、无额外存储（bloom 在 Parquet footer 里）。
- 痛点：**写放大随历史增长**——一个 key 曾经出现在 100 个文件里，bloom 假阳率 ×100 就是 100 次打开文件；频繁换分区的表尤甚（GLOBAL_BLOOM 才处理跨分区）。
- 加速：metadata 表的 `bloom_filters`/`column_stats` 可把 ①② 变成一次元数据表扫描而非打开数据文件。

### 5.4 其他写侧索引速览

| 索引 | 机制 | 适用 | 代价 |
| --- | --- | --- | --- |
| SIMPLE | 读候选分区的 `recordKey→fileID` 列（走 column_stats 同路） | 分区稳定 + key 有序性一般 | 全候选分区记录级扫描 |
| BITMAP | 文件内 key 集合位图 + column stats | 低基数 key | 已弱化，少用 |
| PARTITION | 只索引分区路径 | 覆盖索引式 prune；分区内再 bloom | 不解决记录级定位 |
| BUCKET(SIMPLE) | hash(key) % N → 固定桶数 file group | 写扩展性好，桶需重算 | 桶数变化触发 rescale（第 6 章 clustering 再平衡） |
| BUCKET(Consistent Hashing) | 一致性哈希环 + 桶分裂 | 避免全局 rescale | 环状态维护 |
| RECORD_INDEX | metadata `record_index` 直查 | 高频 upsert 首选 | 依赖 metadata table |

### 5.5 Record index 🔧

```text
upsert 到达 → 在 metadata record_index partition 做 KV 查找 → (partition, fileId)
→ 与输入做 RDD join 完成 tagging，全程不碰数据文件
```

- 1.x 官方推荐默认；写放大近似 O(1)/记录。
- 跨分区更新：record_index 记录的是当前真实位置，天然处理"key 换分区"（global 语义内置）。
- 风险：metadata 表损坏 = 索引失明 → 生产必备 `rollback`/`rebuild` 手册（第 9 章）。

### 5.6 HFile / RocksDB 索引后端

- metadata 表记录级 partition（record_index、bloom_filters、column_stats）支持三种头部文件格式：`PARQUET`（默认）、`HFILE`、`RocksDB`（嵌入式 KV）。
- 官方权衡：HFILE/RocksDB 在**海量小 KV 的随机读写**上远胜 Parquet（Parquet 每次改写整文件块）；启用方式为 `hoodie.metadata.*` 配置族中的 hfile/rocksdb 相关开关（1.x 参数面有调整，口径以官方 Configurations 页为准）。
- 选择经验：表记录数到数十亿且 upsert 密集 → RocksDB 后端；中等规模保持默认 Parquet 以少一个依赖。

### 5.7 读侧索引加速

- **数据跳过（data skipping）**：查询规划用 column_stats（min/max/null count）剔除不可能命中的文件；对**排序后写入**（clustering 按该列排序，第 6 章）效果最好——"索引列的邻近性"是书中反复强调的搭配。
- **等值匹配**：key 谓词走写侧同一索引体系。
- **表达式/函数索引（functional index）** 🔧：
  - 场景：谓词不在存储列上，如 `WHERE substring(city,1,2)='Sh'`、`WHERE toDate(ts)=...`。
  - 机制：声明表达式 → 后台 index 表服务物化派生列并建索引（metadata `functional_index`），查询自动改写命中。
  - 官方口径：`hoodie.expression.index.*` 配置族 + 函数索引声明语法（口径以官方文档为准）。
- 书中"构建合适的索引"要点：**按查询模式建，不建"预防性索引"**——每个索引都是一份写放大 + 一份表服务预算。

### 5.8 选型决策树（本目录收敛版，依据官方推荐整理）

```text
主键更新为主？
├─ 是：metadata table 开
│    ├─ key 跨分区移动 → RECORD_INDEX（global 语义）
│    └─ 不跨且想省 metadata → BLOOM(+metadata 加速) 或 PARTITION 组合
├─ 纯追加/只按时间分区 → 无需写侧索引（insert/bulk_insert）+ BUCKET 若要控制文件数
└─ 高并发写、key 无序、规模超大 → BUCKET(ConsistentHashing) 或 RECORD_INDEX + RocksDB 后端
读侧：报表谓词列 → 对该列 clustering + column_stats；非列上函数 → functional index
```

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "record index 是 B+ 树" | 它是"key→fileID 的 KV 清单"，存在 metadata 表分区里；无层次结构、无范围语义 |
| "索引建好就一劳永逸" | metadata 表与数据表可能漂移（写失败、外部改动），要定期 schedule/重建（第 9 章） |
| "global index 总是更好" | global 索引每次跨分区更新要触碰旧分区的记录，写面更大；能 local 就 local |
| "bloom filter 假阳性无所谓" | 假阳性 = 打开文件做真校验；历史版本多的文件集上假阳性会累积成主要成本 |
| "开了 column_stats 就自动快读" | 数据跳过依赖值的**聚簇程度**；随机分布的列 min/max 区间重叠，等于没开 |
