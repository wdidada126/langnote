## 阅读路径建议

- **主线 A（存储机制派，全书骨架）**：01 → 02 → 03 → 04 → 05 → 06 → 07。
  从「文件怎么摆」到「写怎么落」到「读怎么找」再到「后台怎么收拾」，最后补上「多个写者怎么不打架」。
  05（索引）与 06（表服务）互为因果：索引让写不打架，compaction 让读不打架。
- **主线 B（管线工程派）**：02 → 08 → 04（增量/CDC 读）→ 09 → 10。
  先会建表，再会用 Streamer 灌数，再学增量消费，最后到生产运维与端到端案例。
- **速查路径**：只关心 MOR 读慢 → 06 的 compaction；只关心 upsert 慢 → 05 的索引选型；
  只关心多任务写同一张表报错 → 07 的 OCC 与 lock provider。
- **对照本仓库大数据笔记**：读 [../bigdata/09-存储与文件格式.md](../bigdata/09-存储与文件格式.md) 理解 Parquet 基线文件，
  读 [../bigdata/04-SparkSQL与结构化数据.md](../bigdata/04-SparkSQL与结构化数据.md) 理解 DataSource 扩展点，
  读 [../bigdata/07-实时计算与流式架构.md](../bigdata/07-实时计算与流式架构.md) 理解 Flink 两阶段提交与 Hudi timeline 的对接。

## 核心机制速查（跨章索引）

| 机制 | 一句话 | 主章 | 关联章 |
| --- | --- | --- | --- |
| timeline instant 三态 | requested → inflight → completed，完成态文件出现即原子可见 | 02 | 06、07、09 |
| file group / file slice | 更新的载体；快照=每 group 选 ≤t 的最大 slice | 02 | 04、05 |
| COW vs MOR | 合并成本放写侧还是读侧；read-optimized 用新鲜度换延迟 | 02 | 06 |
| tagging | upsert 的全部开销："key 在哪个 file group" | 03 | 05 |
| 三阶段提交 + OCC | preCommit 分配 instant → 写数据 → commit 时回放并发清单+解析冲突 | 07 | 03、09 |
| compaction / clustering / cleaning / archival | 四笔债四个服务，均走 timeline 生命周期 | 06 | 04、05、09 |
| 增量查询 / CDC 模式 | latest_state 给终态，cdc 给 op/before/after 三件套 | 04 | 08、10 |
| metadata table | 索引与统计的物化底座，坏了可重建 | 05 | 07、09 |
| Hudi Streamer | 微批循环 + checkpoint 随提交前移 | 08 | 03、04 |
| savepoint / restore | 版本钉住与回滚 = 湖仓版闪回 | 09 | 06、10 |

## 核心概念一次记（ASCII 版）

```text
表 = .hoodie(timeline + metadata table) + 分区目录 × file group
file group = 一个 fileId 的全部历史 slice；slice = base file + 0..n 个 log file
写事务 = 造新 slice + 盖章(completed instant)；读快照 = 选 slice；表服务 = 官方后台"改卷宗"事务
```

- 本目录**不提供可运行环境**：所有 Spark SQL / Flink SQL / Streamer 命令均为**教学示意，不参与构建**。
- 第 2 章的「文件组/文件切片」、第 5 章的「metadata table」、第 6 章的「schedule vs execute」是全书三个最容易被跳读、
  又撑起其余章节的地基——建议先读这三个概念段。
