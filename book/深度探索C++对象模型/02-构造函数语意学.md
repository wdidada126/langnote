# 第 2 章 构造函数语意学（The Semantics of Constructors）

> 对应《深度探索C++对象模型》第 2 章：2.1 Default Constructor 的构造操作（四种合成时机）/
> 2.2 Copy Constructor 的构造操作（memberwise initialization、bitwise copy semantics、vptr 重设、虚基处理）/
> 2.3 程序转化语意学（显式初始化、参数与返回值初始化、使用者/编译器层面的拷贝优化）/
> 2.4 成员们的初始化队伍（member initialization list）。
> 阅读地图见 [00-总览与阅读地图.md](00-总览与阅读地图.md)；单文件大纲版见 [../深度探索C++对象模型.md](../深度探索C++对象模型.md)。
> 本章是全书"编译器替你写了什么"主题的第一次正面回答。

## 核心概念速览（中英对照）

- **默认构造函数** — default constructor：无参或全参有默认值的 ctor；**你声明 ≠ 编译器合成**，合成只在被需要时发生。
- **合成默认构造函数** — synthesized default constructor：仅在四种条件下产生（见"机制"），且不递归进入 POJO。
- **拷贝构造函数** — copy constructor：以同类对象初始化新对象；cfront 时代默认 **memberwise**（逐成员）展开。
- **位逐次拷贝** — bitwise copy semantics：对 POD 直接 `memcpy`；当成员含 vptr 或虚基偏移时必须**放弃** bitwise。
- **memberwise initialization** — 逐成员初始化：把合成拷贝构造理解为"对每个成员依次执行拷贝构造"。
- **vptr 重设** — vptr reset：拷贝构造开头把新对象 vptr 指向**自己类**的 vtable（第 5 章 vptr 语意学的先声）。
- **程序转化语意学** — program transformation semantics：编译器对 `X x = val;` 之类源码的隐式改写。
- **返回值优化** — copy elision / RVO / NRVO：以构造位置换取拷贝消除；C++17 起部分场景为**强制**。
- **成员初始化列表** — member initialization list：唯一能在进入 ctor 函数体**之前**完成初始化的通道。
- **初始化顺序** — initialization order：按**声明顺序**执行，与列表书写顺序无关——书中反复敲打的大坑。

## 动机：为什么"需要"才"存在"

cfront 的翻译经济学：每个合成函数都是代码膨胀。所以默认 ctor 只在**程序语义必须有人做事**时才生成。
Lippman 列出的四种"需要"（2.1，书中语境）至今仍是心智模型：

1. **成员类对象带有默认 ctor**——外层类的合成 ctor 必须调用它（递归只到这里停：POJO 成员**不**被初始化）；
2. **基类带有默认 ctor**——派生类合成 ctor 必须调用基类 ctor；
3. **类带有虚拟函数**——需要合成 ctor 设置 vptr（实测 g++ 15.2：`V::V(){...}` 开头即
   `lea rdx, V的vtable; mov (%rax), %rdx`——把 vptr 写入对象偏移 0）；
4. **类带有虚基类**——构造时必须登记虚基偏移（实测符号 `_ZTC7Diamond0_4Mid1`，见"机制 4"）。

对应地，`void func(POJO pojo)` 里 `POJO x;` 完全可能一个初始化指令都没有——**未初始化内存**。
这是书中"默认构造只是承诺，不是保证"的原意。

## 机制

### 1. 合成默认构造的展开（🔧 示意）

```cpp
class Bar { public: Bar(); int val; };          // 有用户 ctor
class Foo { public: Bar b1; Bar* p; int ival; }; // 成员 b1 需要构造
// 编译器合成（书中语意）：
Foo::Foo() { b1.Bar::Bar(); /* p、ival 不管！ */ }
```

实测 g++ 15.2 符号：`_ZN3FooC1Ev` 内调用 `_ZN3BarC1Ev`；指针与 int 成员保持原值（-O0 下为栈残值）。

### 2. 拷贝构造：memberwise 与 bitwise 的分界

```text
class Word { string _str; int _begin,_end,_linenum; };
Word w2 = w1;   // cfront 合成: w2._str = w1._str(调用 string 拷贝构造)
                //            + 三个 int 直接赋值  —— "memberwise"
POD 之间: 编译器有权 bitwise(copy构造被省略为 memcpy/寄存器搬运)
不可 bitwise: 成员含 vector/string(拷贝有深含义)、类多态(要重设 vptr)、虚基(要复制偏移表)
```

书中"不要 Bitwise Copy Semantics！"一节讲 cfront 的两个 bug 级教训（对 `virtual` 函数表指针的盲拷、
对 string 成员的浅拷），机制结论今天依然成立；cfront 的具体故障细节属历史内容 ⚠️。

### 3. 程序转化语意学：拷贝发生在哪里

```cpp
string f(string s);                 // 参数: 拷贝构造
string g(){ string t("hi"); return t; }  // 返回值: 书中时代=一次拷贝(可被 NRVO 优化)
void h(){ string s = f(g()); }      // 初始化: 拷贝 elision 候选
```

书中区分"在使用者层面优化"（传引用）与"在编译器层面优化"（elide 拷贝、以构造代赋值）。
实测 g++ 15.2（🔧 计数实验）：`P byval(){ P p(1); return p; }` 在 **-O0 下拷贝构造调用次数 = 0**——
NRVO 已发生；书中"两个临时对象"的时代图景今天多数时候不成立。C++17（P0135R1）进一步把
"从 prvalue 初始化"的拷贝**强制消除**（guaranteed copy elision），`std::vector::emplace_back` 等接口即建立在此上。

### 4. 虚基类：拷贝与构造都要"记账"

实测（g++ 15.2，MinGW x64，🔧 t18 十六进制 dump）`Diamond` 布局：`Mid1@0 Mid2@16 z@28 共享VBase@32`；
`Mid1` 完整对象 32 字节 = vptr(8)+x(4)+padding(4)+内嵌 VBase 子对象(16)——**对象里没有"虚基偏移字段"**：
Itanium ABI 把"到各虚基的距离"记在**虚表的 vbase offset 区**（虚表组件顺序：vcall offsets → vbase offsets →
offset-to-top → type_info → 函数槽，✅ 规范 §2.5.2），
而 MSVC 才是在对象里存一根 vbptr 指向 vbtable（实测符号 `??_8Diamond@@7B...`）。同一份虚基记账，两家把账本
放在不同地方——详见 [08-专题-现代编译器视角Itanium与MSVC.md](08-专题-现代编译器视角Itanium与MSVC.md)。
虚基子对象在完整对象中的位置
直到 `Diamond` 才知道，所以 GCC 为完整对象生成 **complete object constructor**
（nm 实测符号：`_ZTC7Diamond0_4Mid1`、`_ZTC7Diamond16_4Mid2`，Itanium ABI §2.6 的 VTT 机制——
文档 ✅ [itanium-cxx-abi.github.io](https://itanium-cxx-abi.github.io/cxx-abi/abi.html)）。

### 5. 成员初始化列表（2.4）

```cpp
class X { int i; const int j; int& r; X(int v): r(i), j(v), i(v) {} };
// 实测(g++ -Wall -Wreorder 报警): 真正执行顺序 = 声明顺序 i, j, r
//   -> r 绑定的 i 此刻尚未由 v 初始化! 书写顺序骗过了眼睛。
```

书中强调 const/reference 成员**只能**经列表初始化；"先列后体"的本质是：列表负责**初始化**，
函数体执行的是**赋值**——对有 ctor 的成员，走体赋值等于多做一次构造+析构。

## 权衡

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| 按需要才合成 ctor | 代码体积、POD 零开销 | "有的初始化有的没有"的心智负担 |
| bitwise 拷贝 | 快（一次 memcpy） | 对 vptr/vbase/深拷贝成员**错误** |
| 以构造代替赋值 | 少一次临时对象 | 源码可读性下降（书中"在使用者层面做优化"） |
| 初始化列表 | 唯一能初始化 const/ref/成员类对象 | 顺序陷阱；与声明顺序无关 |

## 相邻概念对比

- **构造 vs 赋值**：构造决定 vptr 初值与成员生死；赋值发生在完整对象之上（第 5 章展开）。
- **默认构造合成（本章）vs 拷贝构造合成**：前者条件苛刻（4 种），后者只要"有人拷贝且你没写"就可能生成——
  C++11 后直接以 `=default` 语义化。
- **NRVO vs move（C++11）**：elision 是"消灭拷贝"，move 是"廉价拷贝"；顺序上先尝试 elision 再尝试 move
  （见 [../Effective_Modern_C++.md](../Effective_Modern_C++.md) Item 29 的讨论）。

## 最新演进与工业实践

- **`=default / =delete`（C++11）**：把"编译器会不会替我合成"变成可声明的意图；
  `X(const X&) = delete;` 是 googler/Chromium 风格指南推荐的禁拷贝写法。
- **类内成员初始化器 NSDMI（C++11）**：`int i = 0;` 直接写进声明，缓解"有的构造忘初始化"。
- **三/五/零法则**：需要自定义析构/拷贝/移动的任一项就三项全定义或全不定义——本章的 bitwise 陷阱是它存在的理由。
- **强制拷贝消除（C++17）**：prvalue 不再创建临时对象；`std::vector<std::string>::emplace_back`
  之类的接口即建立在"原地构造、零拷贝"语意上（g++ 15.2 实测编译通过并正常运行，🔧 计数实验从简——
  语意由 API 保证：emplace 直接在存储区调用 `basic_string(size_type, char)` 构造）。
- **constexpr ctor（C++11/14/20）**：把构造搬进编译期——实测 `static_assert(cobj.v == 3)` 通过（g++ 15.2，
  `constexpr struct C { int v; constexpr C(): v(3) {} } cobj;`），"memberwise"在常量求值语境下变成纯符号操作。

## 常见误区与自查

1. ❌"没写 ctor 编译器一定给一个无副作用的默认 ctor"——POD 成员不会被清零（2.1 的核心）。
2. ❌"初始化列表决定顺序"——决定顺序的是声明顺序；`-Wreorder` 实测会报警。
3. ❌"`X x = y;` 是赋值"——是拷贝初始化，调拷贝构造（第 6 章会补"临时对象"的账）。
4. ✅ 自查：能否说出 `class Z { std::vector<int> v; };` 的默认构造为什么"需要"编译器合成版本？
