## 核心概念速览（中英对照）

- **对象模型** — object model：语言的数据布局与"数据 ↔ 函数如何衔接"的一整套运作模型；C++ 的口号是
  "不用者零代价"（what you don't use, you don't pay for）与"用得少者用得妙"。
- **封装** — encapsulation：语言层用访问控制/friend/成员语法兑现"接口与实现分离"的承诺；
  **对象模型**才是兑现这个承诺的运行时布局与寻址机制。
- **非静态数据成员** — nonstatic data members：唯一被放进每个对象内存里的成员类别。
- **静态数据成员** — static data members：全类唯一一份，置于对象之外（实测：落在 BSS，符号 `_ZN5Empty1sE`），
  不影响 `sizeof`。
- **成员函数** — member functions：全类共享一段机器码，不占对象空间；非静态版本被编译器改写为隐式 `this` 首参的普通函数。
- **vptr / vtable** — virtual table pointer / virtual table：多态对象头部（实测 Itanium：偏移 0）追加的表指针，与每类一张函数指针表。
- **POD** — plain old data：可用 `memcpy` 直接拷贝、布局与 C 兼容的类；cfront 把"对象差异"分级的前提。
- **aggregate / non-POD class / polymorphic class** — 聚合类 / 非 POD 类 / 多态类：1.3 节的四个差异层次，
  决定编译器往你的对象里"塞"多少看不见的机制。
- **虚拟函数** — virtual functions：运行期绑定机制；只有经由**指针或引用**传递对象时才生效。
- **多态** — polymorphism：同一句调用按对象动态类型分派；代价是一次"vptr→vtable→槽"的间接寻址 + 2 个字的内存占用。

## 动机：封装收了我们什么税

C++ 让程序员用"对象"思考，但机器只认字节。编译器必须回答：`class` 的数据怎么排、
成员函数放哪、继承时对象长成什么样、虚拟调用怎么找实现。这些裁决合起来就是对象模型。
Lippman 指出，**加上封装后的布局成本几乎为零**：成员函数不进对象、静态数据成员不进对象，
`class X { int a; double b; char c; }` 的 `sizeof` 与等价 C struct 完全一致——
实测 g++ 15.2：`NonVirt{int a; double b; char c;}` 为 **24 字节**（含对齐填充），无一个字节属于"机制"。
成本出现在**多态**处：一旦类有虚拟函数，每个对象多出 vptr；实测 `Virt{int a; 两个虚函数}` 为 **16 字节**
（vptr@0，a@8；MSVC x64 实测同为 16）。这就是全书要逐层拆开的"看不见的账本"。

## 机制：三种候选模型与 C++ 的选择

### 1. 如果让你设计对象模型（🔧 书中思路，ASCII 复现）

```text
简单对象模型 (A Simple Object Model)        表格驱动对象模型 (Table-driven)
每个对象 = 一个 struct，成员全塞进去：        对象只存指针，机制外置成三张表：
+----------------------+                    +----------+   +----------------+
| int a; double b;     | <- 数据与函数       | void* mfp|--->| name->函数指针  |
| void (*mf)();        |    同侧、同对象      | void* vt |--->+----------------+
| ...所有成员函数指针     |    缺点：每个对象都    | int a    |   +----------------+
+----------------------+    背全类函数指针，     +----------+   | name->vtable   |
                            sizeof 随函数数量     缺点：间接      +----------------+
                            膨胀                 两次查表        缺点：数据也要查表?
C++ 对象模型（折中）：对象内只放 nonstatic 数据成员（+ 必要时 vptr）；
成员函数全类共享一份；静态数据成员置于对象外。——只有"每对象可变的状态"才进对象。
```

三模型的取舍是本章的骨架：**cfront 时代就否决了**"每对象背函数指针"（内存爆炸）与"全查表"（两次间接、
链接期才定址），选择"数据内联 + 函数外置 + 多态才加 vptr"。这个折中延续至今：clang 的
`clang::ASTRecordLayout`（llvm/clang `lib/AST`）仍是按"字段按序 + 对齐 + 基类前置 + 需要时 vptr"生成布局。

### 2. 对象模型如何影响程序（书中 1.1 末节）

- **类的生命周期成本**：是否有 ctor/dtor 合成、拷贝要复制什么（第 2、5 章）。
- **转型成本**：derived→base 隐式向上转型在单继承下零指令（实测：MSVC/GCC 均如此，因为基类子对象在偏移 0）；
  **向下**转型才需要 RTTI 检查（第 7 章 `__dynamic_cast`）。
- **优化例外**：虚拟调用挡在编译期内联前（第 4 章）。
- **编程风格**：泛型（值语义，零机制）与多态（指针语义，vptr 机制）是两条成本曲线迥异的抽象路线。

### 3. 关键词所带来的差异（1.2）

书中语境：`class` 与 `struct` 只是默认访问级与默认继承级的差别，但 cfront 用 typedef 技巧模拟
"前向声明"时二者不可互换；嵌套声明、`struct` 被 C 语言同名 tag 遮蔽等问题都源自 cfront 的翻译策略。
**现代编译器已无这些限制**（实测 g++ 15.2：`struct S; class S {}` 直接编译通过）。这一段今天应作为
**C++ 演化史**读，而非可操作的知识。

### 4. 对象的差异（1.3）

```text
POD ──> aggregate ──> non-POD class ──> polymorphic class
memcpy 即正确     ={} 初始化         ctor 可能被合成        + vptr、dtor 常为虚
（int、指针）    （public 无基类      （有私有/保护成员、       （第 5、7 章机制全开）
                  无用户 ctor）       有基类或 ctor）
```

实测数据链（g++ 15.2，x86-64）：`Virt` 16 字节 → `Derived : Virt { int d; }` 16 字节（d@12）→
`Diamond`（虚拟继承）48 字节、虚基子对象固定排在最后（VBase@32）。每上一级，"你写的"与"编译器塞的"差距都在扩大。

## 权衡

- **vptr 放对象头**（Itanium 与 MSVC x64 实测均为偏移 0）：一次 `load` 即可取表；代价是每个多态对象 +8 字节，
  且**破坏了与"裸 C struct"的布局兼容**（有虚函数的类不再是 standard-layout，见 C++11 定义）。
- **成员函数外置**：`sizeof` 与函数个数无关，这是 C++ 相对 Smalltalk 式模型的最大胜利。
- **静态成员外置**：类当命名空间用几乎零成本（实测 `Empty{static int s}` sizeof=1，且 1 字节只为保证
  不同对象地址可辨；空基类被 EBO 后 `Eb : Empty { int x; }` 为 4 字节）。

## 相邻概念对比

| 问题 | POD | non-POD（无多态） | polymorphic |
| --- | --- | --- | --- |
| `sizeof` = 数据？ | 是 | 是 | 否（+vptr） |
| 能 `memcpy` 吗 | 能 | 看 ctor/dtor 语意 | 子类对象切片风险 |
| 转型开销 | 0 | 0（单继承向上） | 向下需 RTTI |

## 最新演进与工业实践

- **`[[no_unique_address]]`（C++20）**：把 EBO 从"继承技巧"变成"成员属性"。实测 g++ 15.2：
  `Wrap{[[no_unique_address]] Empty e; int x;}` 为 4 字节，与非空的 `NoEb{Empty e; int x}`（8 字节）对照。
  libc++/MSVC STL 均已在 `pair`/`tuple` 中启用。
- **standard-layout 与 interop（C++11 起）**：`std::is_standard_layout` 的判据（无非静态数据成员的基、
  无虚、首成员规则等）正是"1.3 对象差异"的现代化表述，用于与 C 布局互操作断言。
- **编译器源码**：clang `lib/AST/ASTContext.cpp` 的 `computeRecordSize` 与 `ItaniumCXXABI.cpp`、
  `MicrosoftCXXABI.cpp` 是本章结论的第一手当代依据（仓库 ✅ [llvm/llvm-project](https://github.com/llvm/llvm-project)）。
- **规模代价意识**：LLVM 长期以 `-fno-rtti` 构建（类层级改用 `isa<>`/`dyn_cast<>` 自实现），
  是"不需要全对象模型机制就不付钱"口号的工业级实践。⚠️ 构建参数以项目当前 CMake 选项为准。

## 常见误区与自查

1. ❌"成员函数存在对象里"——不在；实测 `sizeof` 与成员函数个数无关。
2. ❌"有虚函数就有动态绑定"——只有**指针/引用**传递才走 vtable；值传递（切片）永远静态。
3. ❌"`class` 和 `struct` 布局不同"——布局完全一致，只差默认访问级（cfront 时代的差异见 1.2 节说明）。
4. ✅ 自查：能否解释 `Virt{int a; 虚×2}` 为什么是 16 而不是 12？（vptr 8 + int 4 + 尾填充 4，对齐到 8。）
