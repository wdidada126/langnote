# 第 7 章 站在对象模型的尖端（On the Cusp of the Object Model）

> 对应《深度探索C++对象模型》第 7 章：7.1 Template（实例化行为、错误报告、名称决议法、Member Function
> 的实例化）/ 7.2 异常处理（快速检阅、对 Exception Handling 的支持）/
> 7.3 执行期类型识别 RTTI（Type-Safe Downcast、Type-Safe Dynamic Cast、References 并不是 Pointers、typeid）/
> 7.4 效率有了，弹性呢？（动态共享函数库、共享内存）。
> 阅读地图见 [00-总览与阅读地图.md](00-总览与阅读地图.md)；单文件版见 [../深度探索C++对象模型.md](../深度探索C++对象模型.md)。
> 全书收尾：模板、异常、RTTI 三个"语言扩展"如何继续榨取对象模型，以及对象模型的边界（DLL/共享内存）。

## 核心概念速览（中英对照）

- **模板实例化** — template instantiation：按需、惰性生成代码；cfront 的"每 TU 全量实例化"造成符号爆炸与
  链接期去重，ELM（External Template Mechanism，书中处方）即 today 的 `extern template`（C++11）。
- **延迟实例化** — instantiation of member functions：类模板的成员函数**用到才**实例化——
  省下"没用到的虚函数拖垮整类"的代码量（第 4 章 vtable 强制物化全表是它的对偶）。
- **两阶段名称查找** — two-phase name lookup：模板定义期查依赖无关名、实例化期查依赖名；
  书中"名称决议法"一节记录的是 cfront 未做阶段一的混乱前史。
- **零成本异常模型** — zero-cost / table-driven EH：正常路径不插桩，抛出时查 `.eh_frame`/`.xdata`+ LSDA
  找处理区；实测 MinGW 异常相关符号：`__cxa_allocate_exception/__cxa_throw/__cxa_begin_catch/__cxa_end_catch/_Unwind_Resume`
  +  personality 例程 `__gxx_personality_seh0`。
- **RTTI 三件套** — `std::type_info` 家族：`__class_type_info`（无基/单父）/ `__si_class_type_info`（单继承）/
  `__vmi_class_type_info`（多继承含虚基）——实测 nm 引用了全部三个 vtable。
- **`dynamic_cast`** — 运行时向下/交叉转换：实测调用 `__dynamic_cast(src, src_type, dst_type, offset)`，
  沿 type_info 链搜索；失败：指针返 nullptr、引用抛 `bad_cast`。
- **`typeid`** — 多态表达式上经 vptr→COL/type_info 字段取动态类型；非多态静态解决；实测
  `typeid(*p).name()` 返回 Itanium 修饰名 `"1A"`。
- **多态引用** — polymorphic references：引用即别名，"引用不指向引用"；把 polymorphic **值**绑给引用=
  **切片**（书中"References 并不是 Pointers"一节的核心陷阱）。
- **共享对象边界** — shared library / shared memory：vtable 跨进程/跨镜像的**稳定性**是 7.4 的主题——
  对象里存的是**指针**，指针值只在单一地址空间内有意义（书中告诫至今有效：共享内存别放带 vptr 的 C++ 对象）。

## 动机：对象模型的三块"_extensions_"都在花布局的钱

模板要求编译期代码可见（实例化时机=代码体积账）；异常要求为每个可能抛点准备元数据（表驱动=体积换时间）；
RTTI 要求 vtable 头旁挂类型信息（每多态类一份 COL/type_info=空间）。Lippman 在 1996 年给出的
"实现成本表"，今天的 ABI 文档里都能找到对应段落。

## 机制

### 1. 模板（7.1）

```text
cfront: 声明即全类实例化 → 符号/编译时间双爆炸
现代(GCC/Clang): 隐式=按需+延迟成员实例化; 显式实例化=强制; extern template=禁止隐式(ELM)
  注：本目录未对"延迟实例化省代码"单独跑 nm 对照，此条按标准语意与编译器文档陈述，非实测断言。
```

错误报告演进：书中"在实例化处报错、报告现场在库里"的噩梦，经两阶段查找 + concept（C++20）
变成"在**使用点**给结构化诊断"。名称决议：书中 cfront 不做阶段一，导致"模板里漏写 typename/
template 前缀"这类至今还在的语法，正是为**补齐**阶段一而设计的补丁——理解历史才懂语法为何长这样
（对照 [../C++模板元编程.md](../C++模板元编程.md) 与 [../C++20模板元编程.md](../C++20模板元编程.md)）。

### 2. 异常处理（7.2）

书中对比"状态表方案（setjmp 式，每次 try 注册）"与"零成本表驱动"。现代 Linux x64/Windows SEH 都是表驱动：

- 编译器为每个函数发射 **调用帧信息（.eh_frame/.xdata）** + **本地数据区 LSDA（.gcc_except_table/.try_block）**；
- 抛出：`__cxa_throw` 携带 value+type_info+dest → 运行期 unwinder（`_Unwind_RaiseException`/
  `__CxxFrameHandler4`）沿栈查表匹配 catch、中途跑析构（实测符号见上）。
- 代价画像：正常路径≈0；**代码体积/启动时间↑**、栈展开表占 .eh_frame 数个百分点——
  LLVM 因此提供 `-fno-rtti`/`-fno-exceptions` 组合（第 1 章"不用者不付"再兑现）。
- 书中"EH 让每个函数变成多入口多出口，内联/寄存器分配变保守"——表驱动时代正常路径已恢复大半。

### 3. RTTI（7.3）

```text
vtable 头部两字 (Itanium, ✅ 规范 §2.5.3): [-2]=offset_to_top [-1]=type_info* ; 虚基/vcall 偏移再向负索引延伸
; MSVC: vftable 前置 COL(`??_R...` 符号族)
        |
type_info: { vptr, 名字串*(_ZTS...), [基类指针/偏移表] }
dynamic_cast<A*>(poly):
  __dynamic_cast(this, 对象的type_info(=vtable[-1]), &A的type_info, 路径调整量)
     → 无多态基? 编译期静态判定  → 是? BFS type_info 链, 命中则返回调整后的 this
实测 t10: cast 成功返回对象地址; typeid name="1A"(Itanium mangled)
实测 t1 nm: __si_class_type_info / __vmi_class_type_info 全被引用
```

书中"Type-Safe Downcast"史前史：Lippman 本人在 cfront 实现过 `safe_cast` 原型，
最终标准化为 `dynamic_cast`（含 `std::bad_cast`）。**References 并不是 Pointers**：
`Base& br = derived_val;` 若 derived 是值则切片成立、引用只是别名；
`typeid(br)` 在 polymorphic 时穿透到真实对象类型——引用的"透明"与指针的"实体"两条语意不可混。

### 4. 效率有了，弹性呢（7.4）

vptr 指向**进程内**的 vtable 地址。因此：
- 共享内存里放带 vptr 的对象 = 跨进程解引用野地址（书中判例）；POSIX 时代的解法——
  对象内存**偏移/名字**、表外置——今天由**序列化 + 类型注册表**（protobuf、class loader）与
  **COM 接口**（`QueryInterface` 本质是手写 dynamic_cast）分别继承。
- DLL 升级改 vtable 布局 → 旧二进制新表序=错位调用（第 3 章"布局是 ABI 契约"的运行期版）；
  Itanium 用 vtable **按声明序** + 虚函数只增不改的"接口演化纪律"缓解，COM/Qt 用接口 ID 隔离。

## 权衡

- 模板：编译期多态零运行时成本，但**代码膨胀 + 诊断困难**（书中两大痛点），concepts 只治了后者。
- RTTI：`dynamic_cast` 比 `static_cast` 贵一个栈搜索；游戏/嵌入式常 `-fno-rtti` + 手写 tag 枚举
  （书中"以 type_info 换 enum"的建议在 Chromium 里活成了 `isa_cast` 家族）。
- EH：零成本对正常路径零成本，对**尺寸敏感**系统仍是负担 → `std::expected`/error_code 作为
  返回值的反-异常路线（C++23），是 7.2 与 7.4 弹性讨论的现代合流。

## 相邻概念对比

- **`dynamic_cast` vs `static_cast` vs `reinterpret_cast`**：查表搜索（安全、慢）/ 编译期偏移（假设正确）/
  无视类型；多态类型间三者生成的机器码差异恰好就是本章内容。
- **`typeid` vs `decltype`**：前者运行期（经 vptr）或静态，后者纯编译期且**不求值**。
- **异常 vs 返回码**：栈展开能力（自动析构）是异常的核心卖点，也是它的成本来源。

## 最新演进与工业实践

- **`extern template`（C++11）= ELM 标准化**：libstdc++/libc++ 对 `basic_string`、`vector` 等广泛使用
  `extern template class`，把模板实例化收编进库本身（书中 7.1 处方的官方落地）。
- **concepts（C++20）**：约束替代 SFINAE，把"名称决议"从两阶段升级为"声明期即查约束"；
  clang `lib/Sema` 的 `CheckConstraintSatisfaction` 是实现锚点（✅ llvm/llvm-project）。
- **RTTI 的取舍**：`-fno-rtti`（LLVM、Chromium 部分目标）与 MSVC `/GR-`——"要不要 type_info"
  仍是每个大型工程的活决策；`std::type_identity`、`source_location` 等则把"类型/位置信息"做成零运行时对象。
- **异常模型文档**：Itanium ABI 的 exception handling 章节 + Microsoft 的 x64 异常（unwind info/funclet）——
  ⚠️ MSVC 官方 learn 文档相关老页面多已 404（本次核实过程中 `/build/virtual-containers-visual-c++` 等链接失效），
  建议以 `llvm.org/docs`（✅ 可达）中的 LangSpec 注记与 win64 build 约定为替代来源。
- **论文锚点**：Stroustrup, "A history of C++"（HOPL-III 分章，DOI 10.1145/234286.1057836，
  ✅ Crossref 可达）——模板/异常/RTTI 三兄弟的标准化时间线以本文为准，书中 7 章正是该时间线的实现侧快照。

## 常见误区与自查

1. ❌"模板实例化发生在声明处"（cfront 迷思）——现代是"用到才实例化，成员函数各自独立"。
2. ❌"零成本异常=白拿"——正常路径免费，代价搬到了体积、启动与不可抛出边界（noexcept）。
3. ❌"`dynamic_cast` 可以跨进程/共享内存用"——type_info 与 vtable 都是进程内指针（7.4）。
4. ✅ 自查：说出 `typeid(*pp)` 从对象地址到字符串 "1A" 的完整 load 链（vptr→vtable[-1]→type_info→name）。
