# 03 · 第 3 章 The Data Warehouse and Design（数据仓库与设计）

> 章题与小节题 ✅ 取自 Wiley 官方 Contents PDF；正文为依据 Inmon 公开著述的**精读重构**，非原书文本。本章是全书工程量最大的一章（英文原书约 71–138 页）。

## 1. 立场：设计从操作型数据开始（✅ Beginning with Operational Data）

Inmon 反对「先画企业主题蓝图再找数据」的空降式建模：仓库的**输入**是操作型系统的既有数据与过程模型，建模从盘点、解析源系统开始。第 1 层模型（high-level）只回答「有哪些主题域与关联」，第 2 层（mid-level）展开关键实体属性，物理模型（physical）才落到表/索引/分区。⚠️ 三段论的具体命名以中译本 3.3.1–3.3.3「仓库数据模型/中间层数据模型/物理数据模型」为据（机工页目录 ✅）。

- **Process and Data Models and the Architected Environment（✅）**：操作型的过程模型（功能视角）不直接迁移，只抽取其**数据效应**（留下什么记录）。
- **The Data Model and Iterative Development（✅）**：他承认迭代——但迭代发生在**主题域内部**，整体架构不迭代；这与 Kimball「按总线逐个交付集市」的迭代观分野（[../数据仓库工具箱3.md](../数据仓库工具箱3.md) 第 2 章项目方法）。

## 2. 规范化/反规范化（✅ Normalization and Denormalization）

Inmon 的招牌论证：**EDW 用规范化（至 3NF/BCNF 口径 ⚠️ 具体范式措辞未实抓）**，反规范化只发生在集市侧。理由链：

1. 决策需求**未知**（future unknown needs）——规范化是唯一能容纳未知查询的结构（此论点在第 13 章与多维模型正面对撞）；
2. 集成只能在规范化上表达（外键=语义对齐的物证）；
3. 冗余的代价在 TB 级原子数据上不可承受；
4. 集市的星型/宽表是**派生视图**，可随意重建——规范化是「不可重建性」的保存位置。

与 Celko 的同盟与分歧：[../Database_Tuning/09-Celko论数据仓库.md](../Database_Tuning/09-Celko论数据仓库.md) 里 Celko 同样挺 3NF、嘲星型，但连「仓库」概念本身一起嘲——读三方才知 Inmon 的规范化是**为企业集成**，Celko 的是为**关系理论纯洁**。

## 3. 记录形态学：快照、触发与概要记录（✅ Snapshots / Triggering the Data Warehouse Record / Events / Components of the Snapshot / Profile Records）

- **事件记录 vs 快照记录**：业务事件（交易、状态变迁）入仓为「一次一行」；周期快照（余额、库存）按周期拍平 ⚠️ 术语对位 Kimball 的 transaction/periodic snapshot 事实表类型（工具箱3 第 2 章）。
- **记录的触发**：仓库记录何时产生？Inmon 给三种触发器：事件发生、快照周期到达、**变更本身**（changed data capture：不是所有字段都新，而是值变了才成行 ⚠️ 通说）——这是 DV 卫星表「仅变更行」与 CDC 语义的先声（[../Data_Vault_2_0/03-DataVault20方法论.md](../Data_Vault_2_0/03-DataVault20方法论.md)）。
- **Profile Records（概要档案记录）**：以客户/保单为中心的「全历史横截面」宽档，供操作型回查与集市装配；✅ 该概念在 14/16 章反复出现（Granularity Manager 与 ODS 的原料）。
- **Managing Volume / Creating Multiple Profile Records（✅）**：档案记录按分区/压缩控制体积，多份档案按主题分治。

## 4. 元数据与参照表（✅ Metadata / Managing Reference Tables）

第 3 章把**元数据**抬到与数据同权重：仓库数据模型本身就是最重要的元数据；参照表（代码表/汇率/日历）是「业务语义的字典页」，必须集中治理——Inmon 称其为环境的「社会胶水」（⚠️ 转述，具体措辞未实抓）。对位 2026：代码表治理≈现代 data contract/参考数据管理（RDM），目录化载体见 [../湖仓架构大规模数据平台的设计和实现/04-数据目录.md](../湖仓架构大规模数据平台的设计和实现/04-数据目录.md)。

- **Cyclicity of Data — The Wrinkle of Time（✅）**：数据的周期律（月结/季末/节假日）像布上的褶皱，影响快照切法与汇总口径。
- **Complexity of Transformation and Integration（✅）**：转换复杂度按「语法清洗→语义映射→跨源对账」递增；只有最后一级才是真集成——与阿里 OneData「统一建模消灭二义性」呼应（[../大数据之路.md](../大数据之路.md)）。

## 5. 反向供数：仓库→操作型（✅ 小节题全实据）

Inmon 很大胆地写了**从仓库回到操作型世界**的三条路：

- **Direct Operational Access / Indirect Access**（直接 vs 间接访问）：直接=操作型系统实时读仓库表（Inmon 警告耦合）；间接=把仓库加工结果**回灌**成新操作型功能。三个实例 ✅：**航空公司佣金计算系统、零售个性化系统、信用评分（credit scoring）**——2005 年的「数据产品化」，正是 2026 年 reverse ETL 与特征平台（feature store）的前史 ⚠️ 转述。
- **Supporting the ODS（✅）**：ODS 是仓库与操作型之间的缓冲带，详见 [13-成本论证与ODS.md](13-成本论证与ODS.md)。
- **Star Joins（✅）**：他在 EDW 章承认星型连接作为**集市侧手段**与查询优化技巧，但拒绝它做 EDW 的组织方式——对撞点见 [11-关系模型与多维模型.md](11-关系模型与多维模型.md)。
- **Requirements and the Zachman Framework（✅）**：用 Zachman 六面体定位「谁的视图/什么数据/在哪/何时/如何/为何」，把需求工程挂进架构化环境。

## 6. 🔧 本机原型（本章可实测部分）

`dbwave_bdw/proto_edw.py`（DuckDB 1.5.5）：staging 原表 → **3NF 原子事实 + SCD2 客户维（valid_from/valid_to/current_flag）** → 月度累积快照（profile/snapshot 思想的落地）→ E2L 派生集市。实测结论 🔧：①集市 `sum(amt)` 与原子层 `sum(amount)` 对账相等（集成唯一性）；②订正原子层一条金额后重建集市确定收敛（440.0），非易失的「修正=新态」在演示中以重算代替归档搬迁；③按 `ord_date` 区间扫描计数验证时间分区裁剪直觉。SCD2 的 valid_from/valid_to 闭开区间口径为自定，与原书细节无涉 ⚠️。

## 核心概念速览（中英对照）

- **从操作型数据开始** — Beginning with Operational Data：建模输入是源系统真实数据，不是空中蓝图
- **三层数据模型** — High-level / Mid-level / Physical Data Model：主题域→关键实体→物理落地的递进
- **EDW 规范化** — Normalization：企业级明细层用 3NF，为未知需求与集成保结构
- **集市反规范化** — Denormalization：星型/宽表只作派生视图，可重建
- **事件记录** — Event Record：业务事件一行的时点记录
- **快照记录** — Snapshot：周期拍平的余额/库存类记录
- **变更数据捕获思想** — Changed Data Capture：值变化才触发的记录生成方式
- **概要档案记录** — Profile Records：以企业实体为中心的全历史横截面
- **参照表** — Reference Tables：代码/日历/汇率等业务语义字典，集中治理
- **时间褶皱** — Cyclicity of Data：数据的周期律对快照与汇总形状的影响
- **回灌操作型** — Indirect Access to Operational：仓库产物变成交换系统（佣金/个性化/信用分）
- **Zachman 框架** — Zachman Framework：以 6W 矩阵对齐仓库需求与干系人视图

## 最新演进与工业实践

- **Reverse ETL / 数据激活（⚠️ 转述）**：Hightouch/Census 类工具把「仓库→操作型」产品化为订阅同步，实现 Inmon 2005 年的「间接访问」设想；批处理时代它只是书里一节，2026 它是独立赛道。
- **特征平台**：零售个性化/信用评分案例的当代正统形态是 feature store（Feast/Tecton），仓库离线特征 + 在线低延迟服务两段式 ⚠️。
- **3NF 现状**：企业级规范化 EDW 在云仓时代并未死——DV 复兴了它（[../Data_Vault_2_0/00-总览与阅读地图.md](../Data_Vault_2_0/00-总览与阅读地图.md)），OneData 的 ADS/CDM 分层也继承其集成职责（[../大数据之路.md](../大数据之路.md)）；但中小规模团队的主流仍是「dbt + 星型/宽表直接出仓」的轻量 Kimball ⚠️（[getdbt.com](https://www.getdbt.com/) curl 200）。
- 🔧 **SCD2/快照可复现**：上文 DuckDB 原型即方法；对位实做见 [04-数据仓库中的粒度.md](04-数据仓库中的粒度.md) 的双重粒度演示。
- **书目实证**：[Wiley 产品页](https://www.wiley.com/en-us/Building+the+Data+Warehouse%2C+4th+Edition-p-9780764599446)、[官方目录 PDF](https://media.wiley.com/product_data/excerpt/45/07645994/0764599445.pdf)。
