# 05 · 第 5 章 The Data Warehouse and Technology（数据仓库和技术）

> 章题与小节题 ✅ 取自 Wiley 官方 Contents PDF；正文为依据 Inmon 公开著述的**精读重构**，非原书文本。

## 1. 本章性质：给「仓库专用 DBMS 需求清单」的章

2005 年没有云数仓，Inmon 用本章论证：**仓库负载（批量装载+大范围扫描+只读并发）是 OLTP DBMS 的坏消息**，需要按清单逐项评估技术。英文小节密度全书最高，可归为四组：装载、访问路径、容量与结构、元数据/刷新/测试。

## 2. 装载组（✅ Managing Large Amounts of Data / Efficient Loading of Data / Refreshing the Data Warehouse）

- **有效装载**：绕开逐行 INSERT——批量装载、直接路径、先装后建索引（load-then-index）⚠️ 通说；「装载占仓库 CPU 时间的百分比」应被监控（接第 1 章 monitoring）。
- **刷新（Refreshing）**：仓库刷新=增量装载的调度问题：哪些表按事件刷新、哪些按快照周期、哪些按「变化才触发」（接第 3 章触发论）。对位 2026：MERGE/upsert 原语与 dbt incremental models（[getdbt.com](https://www.getdbt.com/) curl 200，⚠️ 转述）。
- **测试（Testing ✅）**：装载管道的正确性测试（行数对账、金额对账、抽样字段比对）——Inmon 把「对账」当数仓的单元测试 🔧（我们的原型里 `mart sum == atomic sum` 即其最小实现）。

## 3. 访问路径组（✅ Indexing and Monitoring Data / Efficient Index Utilization / Index-Only Processing / Lock Management / Fast Restore）

- 仓库索引三原则 ⚠️（转述）：只为已知集市查询建索引、优先位图/聚合索引类结构（2005 年口径）、**索引本身是容量成本**。
- **Index-Only Processing**：覆盖索引避免回表——2005 年属高级 DBMS 特性，2026 年是列存引擎默认（DuckDB/ClickHouse 的 zone map + projection，🔧 见第 6 节）。
- **Lock Management**：只读环境里锁冲突主要来自「装载 vs 查询」，故分区级装载/双缓冲（shadow load）是解法；云仓的 micro-partition + transactional clone 把它平台化 ⚠️。
- **Fast Restore**：装载失败要能秒级回到上个一致点——2005 靠备份/重做日志，2026 靠 Snowflake fail-safe/time travel 或 Iceberg snapshot 回滚（[../Apache_Iceberg活用入門/](../Apache_Iceberg活用入門/) 有 snapshot 机制；⚠️ 转述）。

## 4. 容量与结构组（✅ Compaction of Data / Compound Keys / Variable-Length Data / Parallel Storage and Management of Data / Programmer or Designer Control of Data Placement / Data Warehousing across Multiple Storage Media / Interfaces to Many Technologies / Language Interface）

- **压缩（Compaction）**：字符字典压缩、NULL 位图等——仓库列重复度高，压缩收益远超 OLTP ⚠️；2026 年 Parquet RLE/字典编码即其直系后代。
- **复合主键**：仓库记录的键常是多列业务键组合——Inmon 提醒：复合键撑大所有二级索引，代理键在集市侧更好（**与 Kimball 代理键教义的差异点**，工具箱3 维度章节）。
- **变长数据**：VARCHAR 膨胀与定长列存的矛盾——现代解是列式格式的内联短字符串优化 ⚠️。
- **并行存储与数据放置控制权**：DBA/设计者（而非程序员）掌控物理布局——是「架构化环境」在存储层的化身；云仓把控制权收进平台自动聚簇（Snowflake clustering service ⚠️），Inmon 的「人工控制」半失效，「放置即设计」的半存活。
- **多介质仓库（Multiple Storage Media）**：本章已为第 12 章分层埋线（在线/近线/归档）。
- **语言接口**：SQL 之外（COBOL/C 宿主变量 ⚠️ 2005 残留），分析侧 ODBC/JDBC/OLEDB——今天只剩 JDBC/ADBC 一支。

## 5. DBMS 选型组（✅ DBMS Types and the Data Warehouse / Changing DBMS Technology / Multidimensional DBMS and the Data Warehouse / Metadata Management / Context and Content）

- **DBMS 类型清单（2005）**：关系型（行存 RDBMS）扛 EDW；**多维 DBMS（MOLAP cube 服务器）**只配站在集市/报表侧——Inmon 明确反对多维当仓库（第 13 章全面展开）。⚠️ 当年语境：Essbase/Oracle OLAP Option/SSAS 前史。
- **Changing DBMS Technology**：仓库是 20 年资产，选型要看迁移成本与 SQL 可移植性——云仓 egress 锁定讨论的 2005 版。
- **元数据管理 / 上下文与内容（Three Types of Contextual Information / Capturing and Managing / Looking at the Past ✅）**：技术元数据（结构/血缘）、业务元数据（口径）、操作元数据（装载日志）三分法在 1996 版已有 ⚠️；「内容之外还有上下文」=今天 data catalog 的立论（[../湖仓架构大规模数据平台的设计和实现/04-数据目录.md](../湖仓架构大规模数据平台的设计和实现/04-数据目录.md)）。

## 6. 🔧 DuckDB 侧的 2026 印证（本机可跑，DuckDB 1.5.5）

用 DuckDB 对位本章六条清单（方法可复现）：

- 批量装载+先装后查：`CREATE TABLE AS SELECT` 直读 VALUES/Parquet，无逐行成本感 🔧；
- 压缩：写 Parquet 后对比 csv 体积（字典+RLE 效应）🔧；
- index-only：列存扫描只取投影列，`SELECT count(*) WHERE ord_date BETWEEN ...` 无回表 🔧（与第 4 章分区裁剪同型）；
- fast restore：DuckDB 的 MVCC 事务回滚在内存库即时生效 🔧，概念同 Iceberg snapshot rollback；
- 装载对账测试：`sum(mart.amt) == sum(atomic.amount)` 断言 True（本目录 `proto_edw.py` 实测）🔧；
- 多维/立方体：DuckDB `PIVOT`/`GROUP BY ROLLUP` 可做轻量子立方演示 🔧——印证 Inmon「汇总从细节派生」而非「立方体当主存」。

## 核心概念速览（中英对照）

- **仓库负载画像** — Warehouse Workload：批量写+大范围读+只读并发的独特负载型
- **直接路径装载** — Efficient Loading：绕过事务层的高吞吐装载方式
- **刷新策略** — Refreshing：按事件/周期/变更三类触发的增量装载调度
- **装载对账** — Load Reconciliation：行数与金额的一致性校验，数仓的单元测试
- **覆盖索引处理** — Index-Only Processing：不回表即完成查询的访问路径
- **影子/双缓冲装载** — Shadow Load：新分区建好后原子切换的装载手法
- **快速恢复** — Fast Restore：回到上一一致快照的能力（现代=snapshot 回滚）
- **数据压缩** — Compaction：字典/位图类编码，仓库容量的一等杠杆
- **复合主键税** — Compound Keys：宽业务键对索引体积的放大效应
- **多介质仓库** — Warehousing across Multiple Storage Media：在线/近线/归档共存布局
- **MOLAP 定位论** — Multidimensional DBMS：cube 引擎只配集市侧，不得作 EDW
- **三类元数据** — Technical/Business/Operational Metadata：结构口径与运行日志的三分
- **上下文与内容** — Context and Content：数据之外还需描述数据的数据才可信
