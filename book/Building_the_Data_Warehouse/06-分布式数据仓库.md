# 06 · 第 6 章 The Distributed Data Warehouse（分布式数据仓库）

> 章题与小节题 ✅ 取自 Wiley 官方 Contents PDF；正文为依据 Inmon 公开著述的**精读重构**，非原书文本。英文原书约 193–238 页，Inmon 各版中被低估的一章。

## 1. 问题陈述：企业不会只建一个仓库

2005 年的现实：并购、事业部自治、全球时区、IT 预算分散——「一个企业一个 EDW」经常是纸面理想。Inmon 在本章给分布式仓库做**类型学**并给出治理办法，立场一以贯之：**分布是执行策略，不是架构原则**；逻辑集成（统一模型+统一元数据）不可因物理分布而放弃。

## 2. 三类分布式仓库（✅ Types of Distributed Data Warehouses）

1. **局部与全局仓库（Local and Global Data Warehouses ✅）**：
   - 局部仓库=为一个地区/事业部建的**真仓库**（有自己的细节层）；
   - 全局仓库=承载企业级共享细节与全局主题的仓库；
   - **交集问题（Intersection of Global and Local Data ✅）**：两边都有的数据以什么为准？Inmon 答：全局主题必须在全局层定义与存储，局部只能引用不能另立口径；
   - **冗余（Redundancy ✅）**：为性能/可用性容忍物理冗余，但冗余必须**入元数据登记**（谁是权威副本）；
   - **访问局部与全局数据（Access of Local and Global Data ✅）**：跨节点查询的寻址规则由元数据分发（2005 年语境：联邦查询/DB link ⚠️）。
2. **技术上分布式仓库（The Technologically Distributed Data Warehouse ✅）**：同一逻辑库因容量/负载切开放在多物理节点——今天的**分片/多区域数仓**，Inmon 视其为最无害的一类。
3. **独立演化式分布式仓库（The Independently Evolving Distributed Warehouse ✅ + Completely Unrelated Warehouses ✅）**：各处自建、互不相认——**病理型**，即第 1 章蜘蛛网的仓库版；Kimball「信息工厂化前的孤岛集市」在 Inmon 眼中正属此类 ⚠️（立场对照见工具箱3 总线架构的解法差异）。

## 3. 开发项目的本质与协调（✅ The Nature of the Development Efforts / Coordinating Development across Distributed Locations）

- 分布式建设的失败模式不是技术同步，而是**口径分裂的时间差**：各节点进度不一，同名概念先建者定义事实。对策：主题域评审前置、企业数据模型集中发布（下节）。
- **The Corporate Data Model — Distributed（✅）**：企业数据模型是分布环境的宪法——各节点的物理模型必须能对号入座到统一主题图；⚠️ Inmon 一贯主张「模型即集成协议」，与 DV 的「契约化散列键」思路同题（[../Data_Vault_2_0/03-DataVault20方法论.md](../Data_Vault_2_0/03-DataVault20方法论.md)）。
- **Metadata in the Distributed Warehouse（✅）**：分布式元数据要有**单一逻辑入口**（目录服务/元数据库），节点可分布、目录不可碎片化——2026 的 data catalog 治理学（[../湖仓架构大规模数据平台的设计和实现/04-数据目录.md](../湖仓架构大规模数据平台的设计和实现/04-数据目录.md)）。

## 4. 多层构建与多团队细节层（✅ Building the Warehouse on Multiple Levels / Multiple Groups Building the Current Level of Detail / Different Requirements at Different Levels / Other Types of Detailed Data / Multiple Platforms for Common Detail Data / Metadata）

- **在当前细节级上多团队并存**：Inmon 接受「细节层由多个团队分主题共建」，但给出边界条款：主题所有权唯一、交叉引用只读、公共细节数据（common detail）落公共平台 ⚠️（转述其「平台中立、口径唯一」通说）。
- **不同层不同需求（Different Requirements at Different Levels ✅）**：细节层服务集成与回查，汇总层服务响应——两层需求冲突时，**保细节层的正确性优先**，汇总可重建（接第 4 章「真相重放点」）。
- **公共细节数据多平台（Multiple Platforms for Common Detail Data ✅）**：同一公共数据允许在异构平台留副本，但必须能由元数据回答「权威在哪、差异多大」。

## 5. 与 2026 分布式现实的对照

- **数仓内分片 vs 数据网格（Data Mesh）**：Inmon 的解法是「逻辑集中、物理分布」；Data Mesh 是「域自治、产品化、计算策略联邦」——本章恰是两派的分界标本（Mesh 目录版：[#201 `Data_Mesh`](../Data_Mesh/00-总览与阅读地图.md)，已落盘，波内兄弟互链义务波尾闭环）。
- **湖仓多区域复制**（Delta/Iceberg 跨区复制 + catalog 统一 ⚠️ 转述）≈ 技术上分布式仓库的现代实现；Snowflake Multiple Databases/Data Sharing ≈ 局部-全局问题的平台答案 ⚠️。
- **OneData**：阿里集团「一套模型、多处部署」是中文化 Inmon 分布式方案——公共层（CDM）唯一、BU 只能引用（[../大数据之路.md](../大数据之路.md)）。
- 教科书对照：分布式数据库的原理面在 [../分布式数据库原理、架构与实践/](../分布式数据库原理、架构与实践/) 与论文线 [../../db/db.md](../../db/db.md)（Inmon 本章只谈组织与语义分布式，不谈共识协议——两互补）。

## 6. 🔧 最小语义演示（DuckDB，可复现）

「局部/全局交集」的语义实验：两张局部表 `local_orders_ny`、`local_orders_ca` + 全局维度 `cust_dim`，用 `UNION ALL` 装配全局视图后验证：①同一客户在两个局部仓库出现时，以全局维表 region 为准（JOIN 覆盖局部列）；②冗余行（同 order_id 双副本）用 `QUALIFY row_number() OVER (PARTITION BY order_id ORDER BY ts DESC)=1` 去重并声明权威——对位 Inmon「冗余允许、权威唯一、元数据登记」。🔧 本目录原型 `proto_edw.py` 的 cust_dim SCD2 结构即该模式的单节点版。

## 本章论证链复原（⚠️ 依 ✅ 小节序列重建的推理骨架）

1. 前提：企业分权现实使「一个物理仓库」经常不可行（193–198）；
2. 分类：先分清「分的是数据、机器还是治理权」（局部-全局/技术分布/独立演化，194–215）；
3. 判据：只有**治理权分散**（独立演化）才是病，数据与机器的分散是工程参数（211–215）；
4. 处方：模型宪法（219）+ 元数据单入口（223/234）+ 主题所有权唯一（226）；
5. 兜底：冗余允许，但「谁是权威」必须是可查询的元数据事实（206/235）。

- 这条链在 2026 的原样复刻：central governance / federated execution（one catalog, many engines）；
- 它与 Data Mesh 的全部分歧压缩在第 3 步：Mesh 恰把「治理权分散」翻正为第一原则 ⚠️（待链 `Data_Mesh`，登记于 [00-总览与阅读地图.md](00-总览与阅读地图.md)）。

## 核心概念速览（中英对照）

- **局部数据仓库** — Local Data Warehouse：面向地区/事业部的完整细节仓库
- **全局数据仓库** — Global Data Warehouse：承载企业级共享主题与细节的权威层
- **交集治理** — Intersection of Global and Local Data：全局定义优先、局部不得另立口径
- **登记过的冗余** — Redundancy：允许物理副本，权威副本必须入元数据
- **技术上分布式** — Technologically Distributed：同一逻辑库的多物理节点分布
- **独立演化式分布** — Independently Evolving：无协调的自建仓库群，病理型
- **企业数据模型分布式** — Corporate Data Model, Distributed：统一主题图作为跨节点宪法
- **公共细节数据** — Common Detail Data：多节点共用的细节层，落公共平台
- **目录不可碎片化** — Centralized Metadata Entry：节点可分布，元数据入口须唯一
- **细节层多团队共建** — Multiple Groups at Current Detail：主题所有权唯一+交叉只读

## 最新演进与工业实践

- **Data Mesh 对撞（⚠️+待链）**：2019 后 Dehghani 把「独立演化」从病理翻正为纲领（域即真理）；Inmon 派反驳集成不可让渡——论战全景待波内 `Data_Mesh` 目录版（互链义务见 [00-总览与阅读地图.md](00-总览与阅读地图.md)）。
- **云仓全球化（⚠️ 转述）**：Snowflake 跨区域复制+data sharing、BigQuery 多区域数据集把「局部-全局」变成配置项；口径唯一性靠治理不靠平台（[docs.snowflake.com/en/](https://docs.snowflake.com/en/)）。
- **开放表格式联邦**：Iceberg 统一元数据层（catalog）+ 多引擎读写=「目录唯一、物理随便」的 2026 实现（[../Apache_Iceberg活用入門/](../Apache_Iceberg活用入門/)，[iceberg.apache.org](https://iceberg.apache.org/)）。
- 🔧 **复现**：上文 UNION+SCD2 权威覆盖模式可 5 分钟在 DuckDB/SQLite 重放；结论：去重后全局 sum 与权威层对账相等，副本差异被元数据规则消解。
