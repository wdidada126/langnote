# 05 · SQLite Design and Concepts（设计与理念）

> 原书第 5 章（Crossref 章题 ✅：`..._5` "SQLite Design and Concepts"）。小节划分 ⚠️ 推定。
> 🔧 环境同册；E5 含**真崩溃实验**（子进程 `os._exit` 模拟断电级死亡）。

## 1. 本章在 2010 年的语境

第 5 章是全书的"解剖学前奏"：把 SQLite 拆成六件套（⚠️ 组件命名按书谱系推定，机制 ✅ 官方文档）——
接口层（SQL parser→VDBE）、后端（B 树存储 pager）、以及横跨其间的六件子系统：

1. **数据库文件与磁盘 I/O（VFS）**：单文件、页式布局、可替换的 unix/win 抽象层。
2. **页缓存与 pager**：`DEFAULT_CACHE_SIZE=-2000`（2000 KB 页缓存，🔧 E1 compile_options 可见）。
3. **排序与索引**：临时 B 树做 ORDER BY/GROUP BY 外排。
4. **事务与锁协议**：SHARED→RESERVED→PENDING→EXCLUSIVE 五级文件锁（2010 全部叙事的物理地基；
   官方 lockingv3 文档，⚠️ 页未 HEAD 但为长期文档）。
5. **回滚日志的两阶段提交式协议**：写 journal（含初始化记录/扇区对齐）→ 同步 → 覆写主文件
   → 删 journal。**崩溃在任一点都可恢复**——本章给了逐步图解（⚠️ 图未核验，协议 ✅）。
6. **完整性**：`PRAGMA integrity_check`、schema cookie、file change counter 三件校验。

2010 版新增的语境是移动平台：文件即数据 = 应用容器里可直接同步/备份的资产，这个理念在
第 9/10 章开花。

## 2. 精读要点（重构）

- **file change counter 是回滚日志世界的"缓存一致性地基"**：每次提交 +1；任何连接在复用
  schema 页缓存前比对它 + version-valid-for（🔧 E1/E11 直接看到 2→3、提交 +1）。
- **PENDING 锁的"排队礼让"设计**：新读者在 PENDING 后不得再加入——保证写者必能拿到
  EXCLUSIVE，防写者饿死（🔧 E6 里 idle 读者卡提交，正是该协议的镜像事故）。
- **auto_vacuum 三种人格**：NONE/FULL/INCREMENTAL；INCREMENTAL 把"回收空闲页"变成分批任务，
  但**只能截断文件尾部的空闲页**——散落在中间的空闲页要等 FULL VACUUM 重整（🔧 E5 实测出
  这个残酷细节）。
- **rowid 是公民**：每张非 WITHOUT ROWID 表都有隐式 rowid；`INTEGER PRIMARY KEY` 是它的别名；
  删除最大 rowid 后它会被复用（B 树 seek-max+1 规则）——书中"SQLite 没有序列"讨论的根。

## 3. 🔧 实测（E5）：空间回收、崩溃恢复、WAL 三文件显形

| 观察 | 数字/结果 |
| --- | --- |
| 300 行 ×4 KB 大字段建库 | 1.24 MB / 303 页（page_size 4096） |
| 删除一半行 | `PRAGMA freelist_count` = **150** 页空闲 |
| `PRAGMA incremental_vacuum(50)` | 只释放**尾部可截页**：303→302 页（**仅 1 页**！其余 149 页散落中段，须 FULL VACUUM 搬家）✅ 行为级新知（书 2010 只讲"能分批还空间"） |
| 崩溃实验：子进程 BEGIN+2 INSERT 后 `os._exit(9)` | 残留 `e6.db-journal`（热日志）|
| 重新打开+COUNT | **0 行**——未提交内容自动回滚 ✅ 2010 协议今天仍一字不差 |
| 关闭后文件表 | `-journal` 仍在（恢复读完成后由**下一次写+干净关闭**清除：再次 INSERT+close 后目录只剩 `e6.db` ✅ 细节修正书叙述 ⚠️ 官方未明文，属实测现象） |
| WAL 模式 3000 行事务进行中 | 三文件：`e7.db` 4096 B / `-shm` 32768 B / `-wal` 8272 B；提交后 `-wal` → **45352 B**（未 checkpoint） |
| `PRAGMA wal_checkpoint(TRUNCATE)`（事务外） | 返回 `(0,0,0)`（busy=0 全部完成）；wal 文件截断但**不删除**（最后连接关闭才删，对照 E9 CLI 退出后 -wal/-shm 消失） |

## 5. 常见误区

1. "删了数据文件会变小" ⇒ 空闲页进 freelist，尺寸不动（🔧 1.24 MB 全程不变）；`incremental_vacuum`
   也只削尾巴（E5 铁证：150 空闲页只还 1 页）。
2. "有热日志说明库坏了" ⇒ 恰恰相反：热日志在场意味着**可恢复**；删日志才是核弹（书的告诫
   + 🔧 崩溃实验：恢复后行数=0 而非损坏）。
3. "WAL 也是单文件" ⇒ 三文件；-wal/-shm 的生命周期与连接数相关（🔧 E5/E9 两处证据链）。
4. "rowid 永不复用" ⇒ 删最大行后其 rowid 立刻可复用；需要全局唯一请显式计数器/UUID。

## 7. 锁协议速查（五级锁的请求方/兼容矩阵，journal 世界）

| 锁态 | 谁持有 | 允许共存 | 崩溃后果 |
| --- | --- | --- | --- |
| NONE | 空闲连接 | 全部 | — |
| SHARED | 任意读者（含 deferred 开局） | SHARED 互相 | 无（只读） |
| RESERVED | 欲写的单连接（BEGIN IMMEDIATE/首条写） | +SHARED | 无（未动主文件） |
| PENDING | RESERVED 升格提交中，拒新读者 | 仅既有 SHARED | journal 在场=热日志 |
| EXCLUSIVE | 覆写主文件阶段 | 无 | 覆写一半也有 journal 可回滚 |

（✅ 协议骨架出自官方 lockingv3/atomiccommit 叙事，⚠️ 本页未逐字核；🔧 行为证据：E5 崩溃回滚、
E6 SHARED 卡提交、E2 journal 生灭时间线。）

## 9. 本章自检卡（一问一答）

1. Q：提交时日志协议的动作顺序？ A：journal 同步→主文件覆写→删 journal（⚠️ 图转述 ✅ 行为）。
2. Q：删一半数据文件为何不小？ A：页入 freelist 不还 OS（🔧 1.24 MB 不变）。
3. Q：incremental_vacuum 的天花板？ A：只能截"尾部连续空闲页"（🔧 E5 铁证）。
4. Q：看到 -journal 先做什么？ A：直接打开让恢复协议跑完（🔧 0 行），千万别手删日志。
5. Q：change counter 何用？ A：缓存/页有效性判定（🔧 E1 2→3）。
6. Q：-shm 是什么？ A：WAL 索引共享内存映射（🔧 32 KB 显形）。
7. Q：wal_checkpoint 返回三元组含义？ A：busy/log/done（🔧 (0,0,0)=全成）。
8. Q：rowid 会烧号吗？ A：删最大即用，不保证单调（02/03 章伏笔回收）。
9. Q：PENDING 的礼让设计防什么？ A：防写者被源源不断的新读者饿死（⚠️ 官方叙事）。
10. Q：WAL 的代价清单？ A：多两文件、网络盘禁用、checkpoint 抖动（✅/⚠️ 见 wal.html）。

## 核心概念速览（中英对照）

- **五级文件锁** — SHARED/RESERVED/PENDING/EXCLUSIVE(+UNKNOWN)：journal 世界的并发协议。
- **热日志回滚** — hot journal rollback：打开即恢复，🔧 崩溃实验行数归 0。
- **文件变化计数器** — file change counter：页 1 bytes 24-27，提交 +1（🔧 E1/E11）。
- **version-valid-for** — 与 change counter 配对的"谁写的"戳记（🔧 E11：4）。
- **空闲页链表** — freelist：删除不还空间，只入链（🔧 150 页）。
- **增量 VACUUM** — incremental vacuum：只能截尾（🔧 150 空闲页仅还 1 页）。
- **pager/页缓存** — pager cache：`DEFAULT_CACHE_SIZE=-2000`（KB 语义）。
- **VFS** — virtual file system：SQLite 可移植性的抽象缝。
- **rowid 复用** — rowid reuse：max 删除后立刻回锅，无序列语义。
- **WITHOUT ROWID 表** — 3.7.0 引入 ⚠️ 通识（本册未单独实测，见姊妹册）。
- **schema cookie** — schema_version：模式代际戳（🔧 E11=3）。
- **WAL 三文件** — db/-wal/-shm：🔧 尺寸/生命周期实测（-wal 8272→45352→截断）。
- **自动 checkpoint** — WAL 每 1000 页（🔧 E1 compile option 证据）。
- **两阶段日志协议** — journal 写序：init→sync→覆写→删日志（⚠️ 图转述，✅ 行为）。
- **integrity_check** — 全库结构体检 PRAGMA：官方长期特性。

## 最新演进与工业实践

- 2010→2026 本章机制的"不变量"最多：文件锁协议、热日志恢复、freelist 语义、change counter
  一字未改——**这是老书仍可读的部分**；变化集中在 WAL 叠加层与在线备份（3.6.11 hot-backup ✅）。
- 工业侧：Android/iOS 应用容器里"单文件=可云同步资产"的理念已成标准实践（iCloud/DRIVE 同步
  SQLite 的官方告诫也演变出 `PRAGMA journal_mode` 组合指引 ⚠️ 转述）。
- 空间管理最佳实践 2026：预分配 + `auto_vacuum=INCREMENTAL` + 定期小批量 `incremental_vacuum(N)`
  只在"尾部空闲页足够"时有效（🔧 E5 的教训），真实场景常需配合 REINDEX/低峰 FULL VACUUM。
- 取证边界：mmap 引入版本（3.7.1）标 ⚠️；`-shm` 精确 32 KB 属本实例观察，非规范值。
