# 02 · Getting Started（快速上手）

> 原书第 2 章（Crossref 章题 ✅：`..._2` "Getting Started"）。小节划分 ⚠️ 推定。
> 🔧 环境：Python 3.13.2 / SQLite 3.45.3；CLI 3.50.6；输出存 `D:\develops\tmp\dbwave_w3_dgsqlite\exp_out.txt`。

## 1. 本章在 2010 年的语境

第 2 章把读者从"概念"推进到"第一次写库"：打开连接、建表、插入、事务、以及 2010 年最要紧的
心智模型——**每一次提交都同步落盘，日志文件是事务的可见躯体**。当时没有 WAL（3.7.0 于
2010-07-21 才发布 ✅ changelog，本书成稿在 3.6.23 时代），所以书里"事务"一章的全部物理直觉
都建立在 rollback journal 上：BEGIN → 出现 `xxx.db-journal` → COMMIT → journal 消失。

本章的骨架（⚠️ 小节推定，机制 ✅）：

1. **打开/创建**：`sqlite3_open` 语义 = 文件不存在就创建，无"服务器握手"；错误码即返回值。
2. **第一个事务**：autocommit 是默认态，每条语句一个事务；显式 BEGIN/COMMIT 把 fsync 摊薄——
   本章埋下全书最重要的性能伏笔（🔧 E2 实测：**776 倍**）。
3. **锁的最初印象**：第二个连接写同库会拿到 SQLITE_BUSY；`sqlite3_busy_timeout`/busy handler
   是唯一对策（2010 年无 `PRAGMA busy_timeout` 的 URI 参数写法，⚠️ 推定）。
4. **SAVEPOINT**：3.6.8 起完整可用的嵌套事务原语（⚠️ 引入版本转述），书里当作存储引擎级
   回滚点讲——比"整事务回滚"细粒度的唯一手段。

## 2. 精读要点（重构）

- **"文件出现了又消失"是最好的教具**：journal 的存在周期 = 未决事务的存在周期；进程猝死时
  journal 变"热"，下次打开自动回滚（本册 [05-设计与理念.md](05-设计与理念.md) 有 crash 复现实验）。
- 书中反复叮嘱 **synchronous 默认 FULL 是安全线**，想快应当"攒批提交"而不是调低该 PRAGMA——
  2026 年这条告诫仍然成立，只是 WAL 之下多了一个可接受的 `NORMAL` 档位。
- **PRAGMA 是会话级的**：新连接一切归零。书里建议应用启动时集中设置（journal_mode/synchronous/
  foreign_keys/temp_store），这一实践今天仍是各家风格指南的第一条。
- 2010 的"上手三件套"是 shell.exe + 一种语言绑定 + 文档页打印；今天的对应物是任意发行版 CLI、
  Python 内置 sqlite3、sqlite.org——渠道变了，**顺序没变**：先 shell 看文件行为，再进语言。

## 3. 🔧 实测（E2 + E6 佐证）：journal 世界的收支表

| 观察 | 数字 |
| --- | --- |
| 5000 条单语句 autocommit 插入（`isolation_level=None`, synchronous=FULL） | **18.16 s** |
| 同量插入包进一个显式 BEGIN/COMMIT | **0.023 s** → **776×** |
| 事务进行中目录列表 | 出现 `e2.db-journal`；COMMIT 后只剩 `e2.db` |
| `PRAGMA journal_mode` / `PRAGMA synchronous` 默认值 | `delete` / `2`(FULL) |
| SAVEPOINT：BEGIN 内 `ROLLBACK TO sp1` 后提交 | 只留 `'kept'` 行，`'inner'` 消失 ✅ |
| busy 行为（E6 同法复测） | `PRAGMA busy_timeout=0`：0.000 s 即 SQLITE_BUSY；`=2000`：等待至对端 0.4 s 提交后 **0.534 s** 成功 |
| fsync 成本拆解（E10） | 单条 autocommit 插入：FULL 3.0 ms/条、OFF 1.2 ms/条；**NORMAL 反而 5.6 ms/条**（journal 模式 NORMAL 仍同步 journal 目录项，Windows 下抖动大——⚠️ 单次采样，方向性结论仅到"OFF 明显快于 FULL"） |

方法注：计时均为 `time.perf_counter` 包裹 + 冷文件新建；本机机械盘/系统缓存状态未控制，
数字用于说明**量级与比值**，不用于跨机比较。

## 4. 2010 语境 vs 2026 现状对位

| 本书设定（3.6.x） | 2026 现状 | 锚点 |
| --- | --- | --- |
| 只有 rollback journal（delete 模式） | `PRAGMA journal_mode` 六选项：delete/truncate/persist/memory/wal/**off**；WAL 为并发默认推荐 | 3.7.0 WAL ✅ changelog 原句；[wal.html](https://www.sqlite.org/wal.html) ✅200 |
| 显式事务是最有效的提速手段 | 依旧成立（E2 776×）；但 WAL 把"读不阻写"补上了，写仍单流 | 🔧 E2 |
| busy_timeout 需 C 层回调才优雅 | `PRAGMA busy_timeout=N`（3.5 时代即有 ⚠️）+ Python 侧 `set_busy_timeout`(3.13+) | [c3ref/busy_timeout.html](https://www.sqlite.org/c3ref/busy_timeout.html) ✅200 |
| "热 journal 自动回滚"是玄学 | 可复现（见 05 章 crash 实验） | 🔧 E5 |
| 锁粒度=库级写锁 | WAL 下仍是**单写者**，但读者不再挡 `EXCLUSIVE` 提交前的升级 ⚠️（细节以 wal.html/lockingv3 原文为准） | — |

## 5. 常见误区

1. **Python 开发者的"隐形事务"**：默认 `isolation_level=""` 会在 DML 前偷偷 BEGIN——
   想复现书里 C 语义的 autocommit 必须 `isolation_level=None`，否则你的"单条提交"攒到
   close 才落盘（E10 首版实验就因此全部 0.00s，教训见文末勘误记录）。
2. **idle 的 deferred 事务会卡死别人的 COMMIT**（E6 实锤：写失败的连接持有 SHARED，
   对端 COMMIT 升 EXCLUSIVE 被挡 → 先 `commit()` 释放再谈锁）。
3. 把 `synchronous=OFF` 当"性能开关"——E10 里它省下的只是 ms 级 fsync，代价是断电丢整个
   未 checkpoint 的事务集；书的告诫在 WAL 时代加倍适用。

## 7. 日志模式六态速查（journal 世界全家福 + WAL 来客）

| `journal_mode` | 提交时对 journal 的处理 | 适用语境 | 本机可验 |
| --- | --- | --- | --- |
| delete（默认） | 建了又删（🔧 E2 文件表两态） | 2010 书的默认世界 | 🔧 |
| truncate | 截零不删（保留 inode） | 减少创建开销 | ⚠️ 未逐一跑 |
| persist | 写头标记复用 | 省元数据操作 | ⚠️ |
| memory | journal 进内存 | 崩溃安全换速度 | ⚠️ |
| off | 无 journal | 单连接极速/危险 | ⚠️（书有专节 ⚠️） |
| wal | 另一套协议（-wal/-shm，🔧 E5） | 2026 默认推荐 | 🔧 |

## 8. 本章自检卡（一问一答）

1. Q：journal 文件什么时候存在？ A：未决事务期间（🔧 BEGIN 后现身、COMMIT 后消失）。
2. Q：提速第一杠杆？ A：显式事务攒批（🔧 776×），不是调 synchronous。
3. Q：savepoint 与 rollback 的分工？ A：savepoint=事务内局部回滚，RELEASE≠提交（🔧 只留
   'kept' 行）。
4. Q：SQLITE_BUSY 第一对策？ A：`PRAGMA busy_timeout=N`（🔧 0→立败，2000→等到 0.534 s）。
5. Q：Python 里怎么获得 C 语义 autocommit？ A：`isolation_level=None`（否则隐式 BEGIN 攒批）。
6. Q：谁在阻止我 COMMIT？ A：常见为闲置 deferred 事务持 SHARED（🔧 E6 实验炸点即此）。
7. Q：BEGIN IMMEDIATE 何时用？ A：确定要写、想早失败时（预约 RESERVED）。
8. Q：synchronous=OFF 省什么？ A：每条 ~1.8 ms 的 fsync 差（🔧 3.0→1.2 ms），省不掉风险。
9. Q：`PRAGMA` 要不要持久化？ A：会话级，不写进文件；每次连接重设（journal_mode=wal 除外）。
10. Q：WAL 之后"单写者"变了吗？ A：没变，只改了"读者不挡写"。

## 核心概念速览（中英对照）

- **自动提交** — autocommit：无显式事务时每条语句独立成事务，SQLite/Python 默认态。
- **回滚日志** — rollback journal：提交前把旧页写入 `-journal`，崩溃时以它还原（🔧 可见可消失）。
- **热日志** — hot journal：进程死亡后残留的 journal，下次打开触发自动回滚。
- **同步等级** — synchronous：FULL/NORMAL/OFF，控制 fsync 强度（🔧 3.0 vs 1.2 ms/条）。
- **忙等超时** — busy timeout：拿锁失败的内建重试窗口（🔧 0 ms 立败 / 2000 ms 等到 0.534 s）。
- **保存点** — savepoint：事务内命名回滚点，RELEASE≠COMMIT。
- **立即锁** — BEGIN IMMEDIATE：开局抢 RESERVED，避免延迟升级死锁。
- **库级写锁** — database-level write lock：2010 全部并发故事的物理根源。
- **摊薄提交** — batch commits：显式事务把每语句 fsync 摊成一次（🔧 776×）。
- **会话级 PRAGMA** — per-connection pragma：新连接全部重置，需启动时集中配置。
- **SHARED 钉子户** — idle deferred txn：失败/闲置的读事务会卡住他人 EXCLUSIVE 提交（🔧 E6）。
- **journal_mode=delete** — 默认模式：journal 建了又删，文件系统时间戳即事务时间线。
- **deferred 事务** — deferred transaction：BEGIN 默认形态，首次访问才拿锁。
- **锁升级** — lock escalation：RESERVED→PENDING→EXCLUSIVE 的提交路径。
- **零配置≠零设置** — zero config, all pragmas：SQLite 把配置面全部押在 PRAGMA 上。

## 最新演进与工业实践

- WAL（3.7.0，2010-07-21 ✅）发布恰与本书出版同年——第 2 版付印时该特性对读者仍是"下版本预告"，
  这是本册必须逐章对位的根源；到 2026 年 WAL 已是移动端/桌面端事实默认（🔧 05 章三文件实验）。
- 2026 建议姿势：应用层统一 `journal_mode=WAL; synchronous=NORMAL; busy_timeout=5000;`
  起步，写路径显式事务或 `Connection.backup()`；纯批量装载再临时 `synchronous=OFF`（社区通行做法 ⚠️）。
- Python 3.12+ 的 `autocommit` 属性（🔧 E8：`True/False/LEGACY_TRANSACTION_CONTROL` 三态）
  终结了 2005 年 `pysqlite` 时代自创的"隐式事务"方言——但 legacy 模式仍是默认值 `''`，
  迁移期务必显式设定，勿再让库替你猜。
- 工业实践：嵌入式设备上"提交即 fsync"与闪存写放大的矛盾催生 `F2FS`/`O_DIRECT` 层面的配套
  讨论（⚠️ 趋势转述）；SQLite 官方立场未变——durability 优先，快不是它的承诺。
