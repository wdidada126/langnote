# 03 · 存储结构：表空间、段、区、块与 ASM

> **本章地图**：**三层映射**（逻辑：表空间→段→区→块；物理：数据文件→数据块）→ **表空间类型**（SYSTEM/SYSAUX/UNDO/USERS/TEMP + 只读/离线）→ **数据块的内部格式**（块头 / 行目录 / 行数据 / 空闲空间 / 尾块）→ **区与段管理**：字典管理（DMT，**已废弃**）vs **本地管理（LMT）** 与 **ASSM（自动段空间管理，位图）**→ **PCTFREE/PCTUSED 的现代含义**→ **行链接与行迁移**→ **ASM（Automatic Storage Management）** 与 12c 之后的 GI 整合 → **存储相关的高并发问题**（热点块、freelist 争用、`buffer busy wait`）。

## 一、核心精讲

> 以下 SQL/DDL 均为**教学示意，不参与构建**，不可也不必在真实实例上执行。

### 1.1 逻辑结构与物理结构的映射

```
【逻辑】 表空间 TABLESPACE ──► 段 SEGMENT（表 / 索引 / LOB / 回滚段 / 临时段）
            └──► 区 EXTENT（连续块集合，是分配/回收的最小单位）
                    └──► 块 BLOCK（8KB，I/O 的最小单位）

【物理】 一个表空间 = 一个或多个数据文件 *.dbf
         一个数据文件 = 若干个操作系统块（通常 512B 或 4K 对齐）
```

关键结论：**区（extent）是 Oracle 分配空间的单位，块（block）是 I/O 的单位**。二者的差别决定了两种极端症状：

- **区分配太碎**（大量小 extent）→ 空间看起来够，但 `dbl` 场景下 I/O 放大、段头争用；
- **块太小 / 行太长** → 一次读取拿不到整行，触发 **`db file sequential read`（单块读）次数暴涨**。

### 1.2 表空间清单（教学示意，不参与构建）

| 表空间 | 装什么 | 能否 offline |
| --- | --- | --- |
| **SYSTEM** | 数据字典、PL/SQL 源码、SYSTEM rollback segment（11g 后一般没有） | 不能（除非整个库关） |
| **SYSAUX** | AWR、ASM 元数据、OEM/EM、Statspack、Oracle Text、EM 仓库等"辅助字典" | 可以 |
| **UNDO** | 回滚段 / undo segments（11g+ 自动 undo 管理） | 不能 |
| **USERS** | 用户对象（表、索引）默认落点 | 可以 |
| **TEMP** | 排序、临时结果、临时 LOB | 可以 |

创建表空间的教学示意，不参与构建：

```sql
CREATE TABLESPACE app_data
  DATAFILE '/u01/oradata/ORCL/app_data01.dbf' SIZE 2G
  AUTOEXTEND ON NEXT 64M MAXSIZE 8G
  EXTENT MANAGEMENT LOCAL                  -- 本地管理，必须显式或默认
  SEGMENT SPACE MANAGEMENT AUTO;           -- ASSM，12c 起推荐
```

> 12.1 及以后，`EXTENT MANAGEMENT LOCAL` 已是**默认**（DMT 在 9i 之后基本被废弃，`_SYSTEM_TRIGGER_ENABLED` 之类的老话题也随之消失）。**真正值得关注的不是"本地 vs 字典"，而是 `SEGMENT SPACE MANAGEMENT AUTO`（ASSM）**。

### 1.3 数据块的物理布局（这是理解"为什么更新会变慢"的关键）

```
 ┌──────────────────────────────────────────┐
 │ 块头 (block header)                      │  16 字节固定开销 + 事务槽（ITL）
 │   • 块类型、SCN、检查点信息               │  12 字节/事务槽 × 初始 1~255
 │   • ITL（Interested Transaction List）   │  ← 行锁就记在这里，不是单独的对象
 ├──────────────────────────────────────────┤
 │ 行目录 (row directory)                   │  每行一个 24 字节的槽位
 │   rowid 的"行号"部分 + 行首偏移           │
 ├──────────────────────────────────────────┤
 │ 行数据 (row data)                        │  ← 行变长时在这里"搬家"
 ├──────────────────────────────────────────┤
 │ 空闲空间 (free space)                    │  ← PCTFREE 要求的保留量
 ├──────────────────────────────────────────┤
 │ 尾块 (tail slot / chk)                   │  ← 用于一致性校验，防止读到旧的 I/O
 └──────────────────────────────────────────┘
```

三点必须记住：

1. **行锁在块头，不在行里**——所以"锁住一行"实际是"在块头的 ITL 里占一个槽"，这也是为什么 `ITL` 槽不够（`ORA-01555 snapshot too old` 与 `ITL wait`）会直接导致更新失败或极慢；
2. **PCTFREE 是给"将来更新预留的空间"**，PCTUSED 是"空闲到多少才重新允许插入"。在 **ASSM 下 PCTUSED 已无意义**（位图管理替代了 freelist），只保留 PCTFREE；
3. 🔧 **行迁移（row migration）与行链接（row chaining）** 是 12c/19c 上最常见的"表变慢但什么都没改"的原因：一次 `UPDATE` 使行放大、块内放不下 → 行被搬到另一个块，原位置留一个指针。**读取这张表的每一次全表扫都要多跳一次**。诊断：

```sql
-- 行链接/迁移统计（教学示意，不参与构建）
SELECT table_name, chains_cnt FROM user_tables;             -- 需先 gather
SELECT table_name, pct_free, avg_row_len, blocks, empty_blocks
FROM user_tables WHERE table_name = 'EMP';
```

### 1.4 ASSM 与位图： freelist 的消失意味着什么

| 对比项 | 旧方式：freelist + 手动段管理（MSSM） | ASSM（位图管理，AUTO） |
| --- | --- | --- |
| 空间管理元数据 | ** freelist 链表（段头的链表块）** | **位图块（level 1/2/3 bitmap blocks）** |
| 空闲块查找 | 从 freelist 头开始找 | 直接按位图找 |
| PCTUSED | 有意义（控制何时回收到 freelist） | **已无意义**（忽略） |
| 段头争用 | **严重**——多会话抢同一段头块（`buffer busy wait`） | 大幅缓解（位图块可分布在多个块上） |
| 高并发插入场景 | 尾部插入争用严重 | 明显更好，但**位图块本身可能成为新的热点块** |

结论：**ASSM 解决了"段头争用"，但把争用挪到了位图块上**。所以当 `buffer busy wait` 出现在批量插入的表上时，第一个要问的是"这张表是不是 ASSM，位图块是不是成了热点"。

### 1.5 ASM：为什么 11gR2 之后它属于 GI 而不是数据库

- **ASM 是"存储管理平台"**，不是一个数据库实例概念。它有自己的实例（asset management 的 `ASM` 实例），管理 `+DG` 磁盘组；
- 从 **11gR2 开始，ASM 随 Grid Infrastructure（GI）安装**，而不是随数据库安装——所以"装 Oracle 集群"其实是"装 GI，GI 自带 ASM 和 Clusterware"；
- **ASM 提供的是条带化 + 镜像 + 在线重平衡（rebalance）**，把数据打散到磁盘组里所有磁盘上。这带来一个重要的推论：**Oracle 的 I/O 分布由 ASM 负责，DBA 不应该再用"手工分表分盘"来打散 I/O**；
- **ASM 的元数据完全在 ASM 磁盘里（不是放在 OCR/voting disk）**，这是 12c 之后的一个关键运维事实：ASM 盘全部不可用 → 库 Hung，因为 ASM 实例起不来。

教学示意，不参与构建：

```sql
-- 在 ASM 里建磁盘组（通常经 asmca/ASMCMD，命令行也可以，但生产谨慎）
CREATE DISKGROUP DATA NORMAL REDUNDANCY
  FAILGROUP fg1 DISK '/dev/sdc1','/dev/sdc2'
  FAILGROUP fg2 DISK '/dev/sdd1','/dev/sdd2'
  ATTRIBUTE 'compatible.asm'='12.2','compatible.rdbms'='12.2';
-- 让 ASM 自动在线重平衡（教学示意，不参与构建）
ALTER DISKGROUP DATA REBALANCE POWER 5 WAIT NO;
```

### 1.6 存储视角下的高并发问题（与 `13` 章的接口）

| 症状 | 等待事件 | 根因通常在这里 |
| --- | --- | --- |
| 批量插入后应用变卡 | `buffer busy wait` | 位图块（ASSM）成为热点块 |
| 某个表被大量并发更新 | `buffer busy wait`（`buffer busy wait` 对经典 RAC/单点都出现） | 同一批数据块被多会话改写 |
| 改写同一索引的右侧 | `latch: cache buffers chains` | 索引叶子块右侧插入，块被反复拆 |
| **RAC 上**改写同一块 | `gc buffer busy acquire` | **Cache Fusion** 下同一个块的跨节点争用（见 `11`） |
| 单块读次数暴涨 | `db file sequential read` | 索引深度增加、行迁移/行链接、或 `index fast full scan` 被误用 |

> 原笔记第 1 章批注里记了缩写 `OASM（Oracle Automatic Storage Management）`。**现如今的官方缩写就是 ASM**，OASM 是早期文献里的异写；同时它已经不再是"Oracle 自动存储管理"这个动词短语式名称，而是 **Oracle ASM** 这个产品名。

## 二、版本演进

| 版本 | 存储相关变化 |
| --- | --- |
| 9i | 本地管理表空间（LMT）成熟；ASSM 引入 |
| 10g | ASM 独立成"Oracle Cluster ASM/Automatic Storage Management"；`OMF`（Oracle Managed Files）成熟 |
| 11gR2 | **ASM 并入 GI**；`celldb` 相关 Exadata 集成 |
| 12.1 | 大文件表空间限制提高；`EXTENDED` 字符串；ASM `compatible` 属性体系成型 |
| 12.2 | ASM 的 `compatible.asm`/`compatible.rdbms` 成为跨版本混部的门槛参数 |
| 19c | **持续 PRC（贯穿式更新）**影响块上的 "in-memory" 与行存的一致性，见 `14` |
| 23c | JSON Relational Duality 引入新的存储形态（同一份 JSON 既做文档又做关系表），见 `14` |

🔧 **2026 年必须补的三条**：
1. **ASM 的版本混部规则**（`compatible.asm` **不能降**，降了会导致 ASM 实例拒绝启动）是后来国产化/老集群扩容时的高频故障；
2. **闪回技术家族**（Flashback Query / Flashback Database / Flashback Table / Flashback Drop）依赖 **回滚信息保留时间（`undo_retention` + `undo` 表空间大小）**，12c 起还有 **Flashback Data Archive（FDA）** 可长达数年——本书时代只提"闪回是 12c 第 16 章的一节"，2026 年它是合规审计的常规手段；
3. **块大小与存储对齐**：SAN/NVMe 的 I/O 队列深度与块大小对齐问题，是"物理读很高但 AWR 看不出问题"的常见解释。

## 四、近年研究与工业界开源实践（2015–2026）

- **近年研究**：**列式与行存的混合布局**（Citus、Parquet/ORC 湖格式、Oracle 的 In-Memory Column Store）在存储层重新讨论"一个表该有几个副本"；**多版本存储布局**（undo 表空间的版本链 vs PostgreSQL 的堆内多版本 vs TiDB 的 MVCC 分离）值得和 Oracle 的 undo 表空间对照阅读。
- **工业界开源**（star 为 2026-09-25 `gh api` 实测）：
  - `postgres/postgres`（≈22192★）：PG 的"堆内多版本 + HOT 更新"与 Oracle 的"undo 表空间 + 旧版本在回滚段里"是**两种截然不同的版本存储**，是理解 Oracle undo 的最好反例。
  - `facebook/rocksdb`（≈32.1k★，见 `数据库系统概念6` 目录的对照表）：LSM 的追加写模型与 Oracle 的 redo 追加写思路相通，但方向相反。
  - 🔧 `polardb/PolarDB-for-PostgreSQL`（≈3205★）与 `opengauss-mirror/openGauss-server`（≈790★）：国产替代里最常见的两种形态——**"PG 内核 + 自研分布式层"**与**"自研内核"**，二者的存储层与 Oracle 差异最大，迁移时块级/表空间级概念大多要重建（见 `14`）。
  - 🔧 `apache/shardingsphere`（≈20804★）：分库分表中间件。ASM 打散 I/O 之后，"用中间件做水平拆分"反而是最后手段；从 Oracle 迁出的项目里，ShardingSphere 是出现频率最高的组件之一。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | "PCTFREE/PCTUSED 都要调" | ASSM 下 **PCTUSED 被忽略**，只保留 PCTFREE；调 PCTUSED 是 MSSM 时代的习惯 | 12c 教材（第 5 章"表空间"）未点明 |
| 2 | "DMT 和 LMT 都能用，看喜好" | DMT 已在 9i 之后基本废弃，LMT 是默认且唯一推荐 | 全部 9 本 |
| 3 | "ASM 只是个可选的东西" | 11gR2 起 **ASM 属于 GI**，是 RAC 与 ASM 存储的标准配置；ASM 元数据在磁盘里，ASM 全挂 → 库 Hung | OracleRAC核心技术详解（ASM 章）是对的，12c 教材把它当"可选项"偏误导 |
| 4 | "表空间小 = 出问题" | 表空间大小不是关键；**区分配碎片程度、块大小、行迁移率**才是 | DBA 攻坚指南（第 2 章运维）有碎片案例 |
| 5 | "业务量不大就不需要管存储" | 行迁移/行链接在上线半年后才爆发，是很典型的"先快后慢"型故障 | 高并发 Oracle 书（内部扩展维）讲索引与表设计，未专门讲行迁移 |
| 6 | 🔧 "建表空间不用设 `compatible` 属性" | ASM 的 `compatible.asm`/`compatible.rdbms` **不能降级**，且决定能否混部新旧节点、能否用新特性 | 🔧 全部 9 本（成书早于 2018） |
| 7 | 🔧 "行迁移是老 Oracle 的说法，现在没这个概念" | 行迁移在 12c/19c 依然常见，尤以"大量 UPDATE 的表"为甚，手段是 `PCTFREE` 调大或 `SHRINK SPACE` | 🔧 全部 9 本未覆盖 |
| 8 | 🔧 "闪回能救命，所以 undo 表空间随便设" | Flashback Query 依赖 **当前 undo 保留时间**；Flashback Database 依赖 **Flashback Log**（需开 `RECOVERY_FILE_DEST` 且不能 open 过）。二者差别巨大 | 🔧 12c 教材第 16 章只做功能介绍，未讲保留期与限制 |
