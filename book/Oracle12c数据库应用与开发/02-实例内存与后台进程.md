# 02 · 实例内存结构（SGA / PGA）与后台进程

> **本章地图**：**实例 = 内存 + 后台进程**（这是理解一切 Oracle 性能问题的起点）→ **SGA 五大池**（共享池 shared pool / 缓冲缓存 buffer cache / 大型池 large pool / Java 池 / streams pool；12c 起还要算 In-Memory Area）→ **Buffer Cache 的命中与现代替代方案**（KEEP/RECYCLE、结果缓存）→ **PGA 与工作区**（排序区、hash join 区、PGA_AGGREGATE_TARGET 到 PGA 的自动管理）→ **后台进程九件套**（DBWn / LGWR / CKPT / SMON / PMON / ARCn / MMON / MMAN / CJQn）→ **共享池里的三条队列**（library cache / dictionary cache / server result cache）→ **诊断入口**（`v$buffer_pool`、`v$sgastat`、`v$process`、`v$instance`）。

## 一、核心精讲

> 以下 SQL/DDL 均为**教学示意，不参与构建**，不可也不必在真实实例上执行。

### 1.1 实例与数据库的关系

```
  ┌──── 实例（Instance）────┐        ┌── 数据库（Database）──┐
  │  SGA（共享内存）       │        │  数据文件             │
  │  后台进程（DBWn/LGWR…） │  ←──→  │  控制文件             │
  └────────────────────────┘        │  redo 日志文件        │
                                     │  参数/口令/临时文件    │
                                     └──────────────────────┘
```

Oracle 的两个关键设计，值得记住：

1. **内存是共享的、数据是通过文件持久化、状态通过进程协作**——所以"内存里发生了什么"几乎等价于"数据库在做什么"；
2. **写前日志（WAL）**：任何修改先写 redo 到内存再改数据块，所以"内存里的数据块"和"磁盘上的数据块"在任意时刻**不一致**，这是 Oracle 与"纯内存计算"最根本的差别（参见 [`数据库系统概念6/16-恢复系统.md`](../数据库系统概念6/16-恢复系统.md) 的 ARIES 部分）。

### 1.2 SGA：五块池子各管什么

| 池 | 全名 | 装什么 | 监控视图 | 调错的后果 |
| --- | --- | --- | --- | --- |
| Shared Pool | 共享池 | **SQL 与 PL/SQL 的执行计划/解析树**、数据字典、结果缓存、锁与 latch | `v$sgastat`、`v$sqlarea`、`v$librarycache` | 太小 → 硬解析暴涨、library cache latch 争用；**是"绑定变量 vs 量价拼接"争论的战场** |
| Buffer Cache | 缓冲缓存 | 数据块的**最新副本**（8K/16K 块） | `v$buffer_pool`、`v$buffer_statistics`、`v$sysstat` | 太小 → 物理读暴涨；太大 → PGA 被挤压 |
| Large Pool | 大型池 | RMAN 备份/恢复内存、parallel 执行消息缓冲、Shared Server 的会话内存 | `v$sgastat` 里 `large pool size` | 不用时设了也没用；用 MTS/并行时太小 → 报 ORA-04031 |
| Java Pool | Java 池 | JVM 堆 | `v$sgastat` | 只在用 JDBC inside DB、`JServer`、部分 AQ 时才吃紧 |
| Streams Pool | Streams 池 | Streams / GoldenGate 捕获应用内存（12c 已弱化） | `v$sgastat` | 老版本里做复制时才需要 |
| 🔧 In-Memory Area | In-Memory 列存 | 列式副本（IM column store），12.1.2 起可选 | `v$im_segments`、`v$sgastat` | 见 `01` 表与 `14` 章 |

**Buffer Cache 的"命中率"是骗人的**——这是本章最需要纠正的一条。真正有用的三个指标是：

- **物理读 / 秒**（`v$sysstat` 的 `physical reads`）——机械盘时代 > 2000 就是警报线；
- **读一致性命中率**（`consistent gets - consistent gets from cache` 与 `consistent gets` 之比）——**这个比例下降**才是 buffer cache 小的信号，因为"读到Undo 构造的旧版本"意味着大量一致性读失败；
- **写命中率**（`db block gets from cache` 中因找不到空块而被迫刷脏的比例，即 `db block gets` vs `free buffer waits`）——`free buffer waits` 高说明脏块回写跟不上。

### 1.3 PGA：会话私有的那块内存

- **PGA 是私有的**，每个会话一份，不由 `sga_target` 管理，由 `pga_aggregate_target`（11g+ 更常用 `pga_aggregate_target` 或者让 `memory_target` 自动分配）约束；
- 主要消耗者：**排序（sort area）、hash join（hash area）、位图合并、并行 slaves、PL/SQL 里的 `DBMS_SQL`/大数组**；
- PGA 太小 → **一次排序溢出到临时表空间**（`v$tempsegstat` 里看 `Sorts (disk)`）；
- PGA 太大 → **实例内存整体被 OS 换页 / ORA-04031 unable to allocate memory**；
- 🔧 **12c 起**：`_pga_max_size`（隐藏参数）与 `PGA_AGGREGATE_LIMIT`（12.1 起**可动态设置**的硬上限）成为防 OOM 的钥匙。

教学示意，不参与构建：

```sql
-- 看内存分配现状
SELECT * FROM v$pgastat ORDER BY name;

-- 12.1 起可动态限制 PGA，防止单个会话把实例拖死（教学示意，不参与构建）
ALTER SYSTEM SET pga_aggregate_limit = 8G SCOPE = BOTH;

-- 看哪个会话在吃 PGA
SELECT sid, program, status,ROUND(pga_used_mem/1024/1024,1) AS pga_mb,
       ROUND(temp_space_allocated/1024/1024,1) AS temp_mb
FROM v$session WHERE pga_used_mem > 0 ORDER BY pga_used_mem DESC;
```

### 1.4 后台进程：DBWn 与 LGWR 的"双人舞"

这是 Oracle 最核心的一段并发设计，理解它就理解了 `04` 章：

| 进程 | 全名 | 干什么 | 关键参数 |
| --- | --- | --- | --- |
| **DBWn** | Database Writer | 把 buffer cache 里的**脏块写回数据文件**。可以多个（`db_writer_processes`） | `db_writers`（旧）/ `db_writer_processes` |
| **LGWR** | Log Writer | 把 **redo 缓冲区**写进 redo logfile，**越快越好**，由提交或阈值触发 | `log_buffer`（12.2 起仍存在但不可动态改，且 `_use_adaptive_log_file_size` 会自动伸缩） |
| **CKPT** | Checkpoint | 发信号让 DBWn 刷脏，并**更新控制文件里的检查点信息（LRBA/检查点 SCN）** | `log_checkpoint_timeout`、`fast_start_mttr_target` |
| **SMON** | System Monitor | 实例恢复、临时段整理、undo 表空间自动扩容、**SMCO/W000** 并行恢复子进程 | 自动 |
| **PMON** | Process Monitor | 杀掉僵死会话、回滚其事务、**清理 PGA**、注册到监听 | 自动 |
| **ARCn** | Archiver | 把 online redo log 复制成归档日志（**归档模式**下才有） | `log_archive_max_processes` |
| **MMON** | Memory Monitor | AWR 快照、ADDM 分析、`v$memory`  advisor | `MMON_SLAVE` |
| **MMAN** | Memory Manager | 内存 advisor / 可一致地调整 SGA 各池 | `memory_target` |
| **CJQn** | Job Queue | 跑 `DBMS_JOB`（`DBMS_SCHEDULER` 用 `DWnn` / `Jnnn`） | `job_queue_processes` |

**DBWn 什么时候写？** 记住这六条，比背"脏块超过阈值"有用：

1. 提交时（其实只触发**LGWR** 写 redo，DBWn 通常在 LGWR 之后或之前按组提交）；
2. `DBWR` 发现 **脏块列表超过 `db_block_buffers × _db_block_lru_wakeup_threshold`**（隐藏参数）；
3. buffer cache 里**找不到干净可复用的块**（触发 `free buffer waits`）；
4. 发生**检查点**（CKPT 请求）；
5. 表被 **drop / truncate** 或**表空间 offline / read only**；
6. 表被 **drop** 时 Oracle 会直接把块丢进废弃列表（不需要回写）。

**为什么 LGWR 比 DBWn 快？** 因为 LGWR 是**顺序追加写**到 redo log（append-only，机械盘上顺序写快得多），而 DBWn 是**随机写**数据文件。这个"顺序 vs 随机"的差异，是整套 Oracle 日志机制存在的理由——也是 `07` 章里 `log file sync` 与 `log file parallel write` 两个等待事件的来源。

### 1.5 共享池里的三条队列（解析为什么慢）

```
         ┌────────────────────────────────────────┐
 SQL ──► │  Shared Pool                            │
         │   ├─ library cache  （SQL/PLSQL 对象）  │
         │   ├─ dictionary cache（数据字典行）      │
         │   └─ server result cache（查询结果）     │
         └────────────────────────────────────────┘
            命中 → 软/软软解析        未命中 → 硬解析（编译）
```

- **硬解析**：语法分析、语义检查、生成执行计划——最贵，会持有 **library cache latch / mutex**；
- **软解析（soft parse）**：找到已缓存的游标，但还要做用户权限校验等；
- **软软解析（soft-soft parse，12c 概念）**：连权限校验都跳过，靠**结果缓存 + 客户端缓存定位（session cursor cache）**；
- 🔧 **12c 的自适应游标共享（ACS）与结果缓存默认行为漂移**：12.1 起 `client_result_cache` 相关设置更激进，绑定变量在峰值列上会触发**多次计划**（一个变量多个执行计划），这既是优化也可能造成计划抖动（与 `06` 章的绑定变量窥探联动）。

教学示意，不参与构建：

```sql
-- 硬解析率（教学示意，不参与构建）
SELECT ROUND((a.value - b.value) / a.value * 100, 2) AS hard_parse_pct
FROM v$sysstat a, v$sysstat b
WHERE a.statistic# = (SELECT statistic# FROM v$statname WHERE name='parse calls (hard)')
  AND b.statistic# = (SELECT statistic# FROM v$statname WHERE name='parse calls (total)');

-- 谁在抢 library cache
SELECT event, count(*) FROM v$active_session_history
WHERE event LIKE 'latch%' OR event LIKE 'cursor: pin%'
GROUP BY event ORDER BY 2 DESC;
```

## 二、版本演进

| 版本 | 内存 / 进程相关变化 |
| --- | --- |
| 9i | `pga_aggregate_target` 引入，PGA 自动管理开始；DBW0 命名 |
| 10g | `sga_target` 自动共享内存管理（ASMM）登台；AWR/ADDM 成为默认诊断工具（见 `07`）；MMON/MMAN 出现 |
| 11g | `memory_target`（AMM）登台，`10g` 的 `sga_target` 仍可用；**大量事件由 latch 改为 mutex**（这一改动彻底改变了"latch 争用"的诊断方式，见 `07`） |
| 12.1 | In-Memory 列存（12.1.2）；`pga_aggregate_limit` 可动态设；`_use_adaptive_log_file_size` 让 log buffer 自动伸缩 |
| 12.2 | log buffer 可自动伸缩（仍需重启）；PDB 级内存参数 |
| 19c | LTS 版本；**持续 PRC（贯穿式更新）**让 IM 列存与行存的更新统一，影响内存与事务交互（见 `14`） |
| 23c | 继续强化 In-Memory、自动索引与内存侧的自治管理 |

🔧 **2026 年必须补的四条**：
1. **"latch 已死，mutex 当立"之后**，老 DBA 背的 `latch: cache buffers chains` 诊断口诀需要更新成 `buffer busy wait`、`cursor: pin S wait on X`、`mutex` 系列等待；
2. **共享池的调优热点已经从"调大小"变成"减少解析"**：`session_cursor_cache`、`result_cache`、`_cursor_obsolete_threshold`（12.2 起更激进的游标淘汰）才是关键；
3. **AMM（`memory_target`）在 Linux 上有 /dev/shm 限制**，容器化部署时必须改回 ASMM 或显式设 `memory_target`，否则实例启动即 ORA-00845；
4. **AWR/ASH 属于 Oracle 的诊断包（Diagnostics Pack）许可范围**，把 `v$active_session_history` 当免费监控数据源用会踩许可（见 `07`）。

| --- | --- | --- |
| Jim Gray《The Transaction Concept: Virtues and Limitations》 | VLDB 1981 | 事务与 **WAL（写前日志）** 的出处，redo 机制的理论底座 |
| Mohan 等《ARIES: A Serializability-Preserving Recovery Algorithm With Repeating History》 | SIGMOD 1992 | **通用理论，非 Oracle 专属**：dirty block 的 **STEAL / NO-FORCE / DICTIONARY / WRITE-AHEAD** 四象限由 Haerder & Reuter (ACM CSUR 1983) 提出 |
| Theo Haerder & Andreas Reuter《Principles of Transaction-Oriented Database Recovery》 | ACM Computing Surveys 15(4), 1983 | **通用理论，非 Oracle 专属**：提出恢复算法的设计空间分类法 |
| Stonebraker 等《The End of an Architectural Era (It's Time for a Complete Rewrite)》 | VLDB 2007 | **通用理论，非 Oracle 专属**：实测 OLTP 的时间去向——缓冲池管理、闩争用、日志 fsync、B 树维护占了绝大部分，正好解释为什么本章这些内存池的参数这么关键 |
| Oracle《Oracle Database Administrator's Guide》"Instance Memory / Background Processes" | Oracle 官方文档（非论文） | DBWn/LGWR/CKPT 等的权威定义 |

> 说明：Oracle 的内存结构与后台进程是**产品实现**，没有对应的顶级会议论文。上述均为**通用的事务与恢复理论**，用来给本章提供原理支撑，明确**不是 Oracle 专属论文**，也不代表 Oracle 内部实现完全一致。

## 四、近年研究与工业界开源实践（2015–2026）

- **近年研究**：**无锁/免闩数据结构**（Bw-tree, ICDE 2013；Masstree, EuroSys 2012；Hekaton, SIGMOD 2013）正对应 Oracle 11g 把 latch 换成 mutex 的路线；**持久内存（PMem/CXL）**研究则重新审视"buffer cache 该多大"这个老问题（[`Linux内核完全剖析/13-内存管理.md`](../Linux内核完全剖析/13-内存管理.md) 可以看页缓存与直接 I/O 的对照视角）。
- **工业界**：
  - **容器化部署下的内存管理**：在 Kubernetes 里给 Oracle 设 `memory_limit`，若 SGA + PGA + OS 开销超过 cgroup 上限，会触发 **OOM kill**（实例直接消失，不是慢，是**没**）。生产上的做法是显式 `memory_target` 或干脆 ASMM，并给 OS 留 1.5 GB 余量。
  - 🔧 **`oracle/python-oracledb`**（star 实测 **453**，2026-09-25）与 **UCP（Oracle Universal Connection Pool）/ DRCP**：连接池不再是"每个请求一个进程"而是"池化会话"。DRCP（Database Resident Connection Pool）在 12c 之后支持跨应用共享会话内存，**在短事务、高并发的 Web 场景能显著压低 PGA 总量**——这条正好对应 `13` 章的会话模型讨论。
  - 🔧 **监控栈**：`alibaba/Druid`（star 实测 **28178**）是最常见的 Java 侧连接池，它能直接打印出 Oracle 的慢 SQL 与执行计划，是"共享池问题从应用侧被看见"的工具。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | "buffer cache 命中率低于 90% 就该加大" | 命中率不是 Oracle 的有效指标；应看 **物理读/秒、consistent gets 命中率、`free buffer waits`** | 全部 9 本（成书早于 2015 的居多） |
| 2 | "共享池调小一点，把内存让给 buffer cache" | 共享池小 → 硬解析暴涨 → 反而更快耗尽 buffer cache 且引发 latch/mutex 争用 | DBA 攻坚指南（内存章节）未强调这一因果 |
| 3 | "PGA 是共享的，所以调大 SGA 会挤压它" | PGA 由 `pga_aggregate_target` / `pga_aggregate_limit` 独立管理，与 SGA 之间是 AMM 下**竞争关系**但也各有上限 | 性能优化方法论（资源章）把二者并列，值得对照 |
| 4 | "提交时 DBWn 会立刻把脏块写完" | 提交触发的是 **LGWR**；DBWn 按检查点/脏块阈值/空间压力异步写 | 全部 9 本 |
| 5 | "归档模式下 ARCn 只是复制文件，无关紧要" | ARCn 跟不上会导致**归档目标满 → 实例挂起（等待 `log archive impossible`）**，是生产重大故障 | DBA 攻坚指南（运维章）有案例，12c 教材（第 15 章 RMAN）几乎不提 |
| 6 | "latch 争用是 11g 之前的事" | 11g 改 mutex 后**等待事件换了名字，问题还在**；`cursor: pin S wait on X` 至今是硬解析风暴的第一信号 | 全部 9 本（成书 2009–2021，均未系统更新到 mutex 时代） |
| 7 | 🔧 "`/dev/shm` 不够就把 `memory_target` 调小就行" | 容器里 `memory_target` 与 cgroup limit 冲突会直接 OOM kill；应改用 ASMM + 显式 `sga_target`/`pga_aggregate_target` | 🔧 全部 9 本均未覆盖容器化（Docker/K8s）部署 |
| 8 | 🔧 "把 `v$active_session_history` 当免费监控用" | AWR/ASH 属 **Oracle Diagnostics Pack 许可**，需要核实合同是否包含；云端（OCI/ACRDS）按实例类型另有一套计费 | 🔧 全部 9 本均未覆盖许可边界 |
| 9 | 🔧 "12c 讲的内存知识 2026 年还够用" | 需补 **In-Memory Area**（12.1.2）、**19c 持续 PRC 对内存一致性的影响**、**23c 自动索引占用的内存** | 🔧 12c 教材与 SQL 优化最佳实践均只写到"PGA/SGA 参数怎么调" |
