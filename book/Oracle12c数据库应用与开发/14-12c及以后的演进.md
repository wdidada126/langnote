# 14 · 12c 及以后的演进（19c / 23c / 国产化 / 生态迁移）

> **本章地图**：**时间线**：11g → 12c(12.1/12.2) → 18c → 19c(LTS) → 21c → 23c → 26c 路线 → **12c 时代的版本坑清单**（`optimizer_adaptive_features`、`result_cache`、`MAX_STRING_SIZE`、TDE 与钱包、隐式参数漂移）→ **19c/23c 的新能力**：持续 PRC、JSON Relational Duality、向量搜索与 AI、自动索引、Autonomous Database → **升级/迁移的实操路径**（PDB 改造、滚动升级、停机窗口）→ **国产化与开源替代**：OceanBase / PolarDB / GaussDB / TiDB / PG 系 → **与 PostgreSQL / MySQL 迁移对照表** → **生态**:驱动、连接池、CDC、监控。

### 1.2 🔧 12c 时代的版本坑清单（从 11g/12.1 升上来最容易翻车的六条）

| # | 坑 | 表现 | 处理 |
| --- | --- | --- | --- |
| 1 | **`optimizer_adaptive_features` 默认值反转** | 12.1 默认 **TRUE**、12.2 默认 **FALSE**；同一条 SQL 在两个版本上执行计划不同 | 升级前先在这个参数上做 A/B 对比（`ALTER SESSION SET optimizer_adaptive_features = ...`） |
| 2 | **`result_cache` 与 `CLIENT_RESULT_CACHE` 的行为** | 结果缓存更激进，可能出现"数据不刷新" | 明确哪些结果可缓存、哪些加 `RESULT_CACHE RELAXED` 或关闭 |
| 3 | **`MAX_STRING_SIZE`（STANDARD vs EXTENDED）** | 建库时确定；EXTENDED 下 `VARCHAR2(32767)` 可能**超过块大小**造成行链接 | 升级前跑 `Pre-Upgrade` 脚本检查；升级后测最宽的行 |
| 4 | **TDE 与钱包的路径变化** | 钱包位置从 `?/wallet` 变成 `tns_admin` 下的 `sqlnet.ora` + `cwallet.sso`；不同版本的 `ENCRYPTION_WALLET_LOCATION` 语义有差异 | 迁移时把 wallet 作为**迁移资产**一起搬，并测试自动登录 |
| 5 | **隐式参数（underscore parameters）漂移** | 文档不载、版本间默认值变化；按老书里的隐式参数调性能，在 19c 上可能失效或有害（例如盲目调 `_sync_io` 类参数解决物理读问题） | **先验证再采用**：用 AWR 看 `db file sequential read` 的实际毫秒数，确认瓶颈真在 I/O 再动手 |
| 6 | **PDB 与非 CDB 的互转** | 非 CDB 库要变成 PDB 需跑 `noncdb_to_pdb.sql`；反之要 `UNPLUG` + 重建 | 升级路径设计时就定好目标形态 |

### 1.4 JSON Relational Duality 值得单独理解

传统做法里，"JSON 文档存储（MongoDB 式）"与"关系表"是**两份数据 + 一条同步链路**。JSON Relational Duality 的改写是：

```
        ┌──────────────────────────────────────┐
        │   同一份底层数据（duality view）      │
        └───────────────┬──────────────────────┘
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
  JSON 视图（文档 API）          关系视图（SQL/OR）
  应用「面向对象」读写            报表「面向列」读写
```

**工程含义**：

- 免去一份"关系化 JSON"的同步与一致性维护；
- 支持从关系表生成 JSON、也可以从 JSON 更新关系列；
- 🔧 它是**混合/多模数据库路线**的关键一步，也是 Oracle 对抗"关系 + NoSQL + 向量"三种数据形态的核心叙事。

### 1.5 🔧 从 Oracle 迁出：与 PostgreSQL / MySQL 的对照表

这是 2026 年最实用的一张表，也是本目录 9 本书**完全没覆盖**的内容。

| 能力 | Oracle | **PostgreSQL** | **MySQL（InnoDB）** |
| --- | --- | --- | --- |
| schema | **schema = user**，一个用户一个 schema | `database` → `schema`（层级更自由） | 只有 `database`（≈ Oracle schema） |
| 空串与 NULL | **`''` 就是 `NULL`** | **`''` 与 `NULL` 严格不同** | 近似 Oracle，`''` 与 `NULL` 有别（依 sql_mode） |
| NULL 索引 | **可以索引 `NULL`**（`IS NULL` 走索引） | **默认不索引 `NULL`**（除非表达式索引 `IS NOT NULL` 或用 `NULLS NOT DISTINCT`） | 可以索引 |
| `NULL` 排序 | 默认 **NULLS LAST** | 默认 **NULLS LAST**（PG 14+ 可配） | `ASC` 时 NULL **最前** |
| 分页 | `ROWNUM`（旧）/ **`FETCH FIRST`**（12c+） | **`LIMIT/OFFSET`** | `LIMIT/OFFSET` |
| 伪表 | **`DUAL`** | **无 `DUAL`**（直接 `SELECT 1`） | 可选 `FROM DUAL` |
| 条件表达式 | **`DECODE`**（专有）+ `CASE` | `CASE` | `CASE` |
| 序列 | **`SEQUENCE`**、identity | **`serial` / `GENERATED ALWAYS AS IDENTITY`** | **无序列**（用 `AUTO_INCREMENT`） |
| 过程化 | **PL/SQL**（强、包、自治事务） | **PL/pgSQL**（弱一些，无包） | **无过程化语言**（MySQL 8 有简单的 `CREATE PROCEDURE`） |
| 事务隔离 | 默认 **Read Committed**；Serializable 需指定 | 默认 **Read Committed**；有 **SSI**（可串行化快照隔离） | 默认 **可重复读（RR）** |
| 多版本版本存放 | **undo 表空间**（旧版本在回滚段） | **堆内多版本 + HOT 更新** | **undo 日志回滚段** |
| 诊断工具 | **AWR / ASH / ADDM**（需 Diagnostics Pack） | **`pg_stat_statements` + `EXPLAIN ANALYZE`**（免费） | `performance_schema` / `Slow Query Log` |
| 分区 | 原生强 | 声明式**声明式分区**（PG 11+ 完善） | 分区（MySQL 8 完善） |
| 许可 | **商业授权（按 processor/核心）** | **BSD** | **GPL** |

**迁移时最常踩的四个点**：

1. `ROWNUM` / `DUAL` / `DECODE` 的替换；
2. **`''` 与 `NULL` 的语义差异**（会导致"筛不出来"的静默错误）；
3. **PL/SQL 资产**（存储过程、触发器、包）需要重写为 PG 的 PL/pgSQL 或应用代码——这是工期的大头；
4. **序列与主键策略**（Oracle 的 `SEQUENCE.NEXTVAL` 无法直接映射到 PG 的 `serial`，因为并发下会跳号/缓存差异）。

### 1.6 🔧 国产化与开源替代的现状

| 方案 | 路线 | 与 Oracle 的相似度 | 迁移要点 |
| --- | --- | --- | --- |
| **OceanBase**（`oceanbase/oceanbase`，star 实测 ≈10291） | 分布式多副本（Paxos），**有 Oracle 兼容模式（租户级 Oracle 租户支持 PL/SQL 语法）** | **最高** | 序列/PL/SQL 兼容度高；分布式事务与 SQL 调优模型需重新学 |
| **PolarDB**（`polardb/PolarDB-for-PostgreSQL`，star 实测 ≈3205；`polardb/polardbx` ≈102） | 存算分离 + **共享存储的读写分离节点**（架构上最接近 RAC） | PG 系，需从 PG 语义切入 | 共享存储 + read-only 节点带来的"RAC 平替"体验 |
| **GaussDB / openGauss**（`opengauss-mirror/openGauss-server` star 实测 ≈790） | 自研内核 + 开源社区版 | PG 系 | 内核差异大，PL/SQL 需改写 |
| **TiDB**（`pingcap/tidb`，star 实测 ≈40586） | 分片 + Raft，NewSQL | **最低**（MySQL 协议兼容） | 分片键设计决定一切；事务模型是 Percolator |
| **ShardingSphere**（≈20804） | 中间件（分库分表 + 读写分离 + 分布式事务） | 不含数据库内核 | 通常作为"过渡层"，先把 SQL 打散再换内核 |

**"去 Oracle"的真实成本结构**（这是 2026 年才有答案的题）：

```
   驱动/连接改造   ▏ 10%   （python-oracledb / OJDBC → JDBC/PG 驱动，通常最轻）
   SQL 语法重写    ▏ 20%   （DUAL / ROWNUM / DECODE / 序列 / 函数）
   PL/SQL 资产重写 ▏ 55%   ★ 大头（包、触发器、自治事务、批处理）
   架构重画        ▏ 15%   （分片键、分布式事务、读写路由、HA 方案）
```

### 1.7 🔧 升级与迁移的实操路径（停机窗口从"天"压到"分钟"）

四条常见路径，按停机时间从长到短排列：

| 路径 | 做法 | 停机窗口 | 适用 |
| --- | --- | --- | --- |
| **A. 原地升级 → PDB 化** | 建新版 GI/DB → `UNPLUG` 老库 → `PLUG IN` 到新 CDB → 跑 `noncdb_to_pdb.sql`（若原库非 CDB） | 小时级 | 老版本（11g/12.1）迁到 19c/23c 的常规做法 |
| **B. 逻辑复制做滚动升级** | 把物理 DG 转成逻辑 DG → 备库升级 → 备库转主 → 原主重建为备 | **分钟级** | 给停机窗口极紧的核心系统（DBA 攻坚指南讲过这条） |
| **C. 数据泵 + 前置校验** | `expdp/impdp` 全量迁移 + 数据比对 + 试运行切流 | 分钟级（仅切流） | 跨平台/跨版本、有停机窗口许可的场景 |
| **D. 应用双写 + CDC 追平** | 新库上线，应用双写，用 `debezium` 类 CDC 追平差异 → 灰度切流 | **接近零** | 两地三中心/不停机要求极高时；复杂度也最高 |

> **无论选哪条，都不要跳过"回退方案"**：升级前把老环境的**备份、参数文件、口令文件、wallet、listener/tnsnames、以及应用连接串**全部打包存档。这是本目录 9 本书里唯一反复提到却人人说"下次一定"的纪律。

### 1.8 🔧 生态替换清单（2026 年视角）

| 原来 | 现在 | 备注 |
| --- | --- | --- |
| `cx_Oracle` | **`oracle/python-oracledb`**（star 实测 ≈453） | Thin 模式免装 Oracle Client，容器镜像体积与安全面都变小 |

## 四、近年研究与工业界开源实践（2015–2026）

- **近年研究**：
  - **向量检索**：HNSW、IVF-PQ、DiskANN 与 `pgvector`（≈23.2k★）、`faiss`（≈41.0k★）；23c 的 AI Vector Search 与之同构；
  - **HTAP 的学术与工业共识**：行存 + 列存的"双引擎"（Oracle In-Memory、SQL Server 的 Columnstore、TiFlash、ClickHouse 的 MergeTree + 事务）；
  - **自动索引与 ML 优化器**：Agrawal 等《Automatic Database Index Tuning》（SIGMOD 2000）→ 21c/23c 自动索引的学术 lineage；Deep-Learned Cardinality Estimation（SIGMOD 2019）等；
  - **自治数据库**：Aurora Serverless、Autonomous Database、Self-Driving Database（微软）、以及 **Physics-based / learned 索引**（如 SOSD、DEXDB）。
- **工业界**（star 为 2026-09-25 `gh api` 实测）：
  - `oracle/python-oracledb`（≈453）：Thin 模式免装客户端；`oracle/node-oracledb`（≈2368）同步演进；
  - `debezium/debezium`（≈13152）：**CDC 的既定标准**，Oracle 侧可用 LogMiner 或二进制读 redo，是"迁出/入"时最重要的中立组件；
  - `pingcap/tidb`（≈40586）、`oceanbase/oceanbase`（≈10291）：国产替代的主力开源形态；
  - `polardb/PolarDB-for-PostgreSQL`（≈3205）、`opengauss-mirror/openGauss-server`（≈790）：PG 系替代路线；
  - `apache/shardingsphere`（≈20804）、`alibaba/Druid`（≈28178）：过渡期的中间件与连接池；
  - `postgres/postgres`（≈22192）：迁移落地的**主要目的地**之一。

| 3 | 🔧 "自动索引开了就省心" | **自动索引会偷偷建索引**：消耗空间、拖慢 DML、且会改变执行计划；必须显式开关与监控 | 🔧 全部 9 本 |
| 4 | 🔧 "国产库兼容 Oracle 语法就可以直接迁" | 兼容的是**语法**，不是**语义**（如 `''` vs `NULL`、序列语义、事务隔离）；PL/SQL 资产才是大头 | 🔧 全部 9 本 |
| 5 | 🔧 "向量搜索是 AI 部门的事，和数据库无关" | 23c 把向量索引做进数据库内核；`pgvector`（≈23.2k★）已在 PG 生态证明"在库内做向量检索"是主流形态 | 🔧 全部 9 本 |
| 6 | 🔧 "Autonomous Database 就等于云上 Oracle" | 它是"打补丁/调优/备份自动化"的产品化，**并非所有工作负载都更省成本**（按 OCPU 计费时小库可能更贵） | 🔧 全部 9 本 |
| 7 | "Oracle 的 `MAX_STRING_SIZE` 事后可以改" | **建库时确定，之后不能改**（要重建库） | 全部 9 本 |
| 8 | "12.2 只是 12.1 的补丁" | 它是**兼容性变化最多的一版**（自适应特性默认值反转、Flex Cluster、PDB 资源限额） | 全部 9 本（成书早于 12.2 或刚好覆盖） |
| 9 | 🔧 "驱动不重要" | `cx_Oracle` → `oracle/python-oracledb`、`sqlplus` → `SQLcl` / `python-oracledb`，Thin 模式改变了容器镜像与安全攻击面 | 🔧 全部 9 本 |
| 10 | 🔧 "21c/23c 可以随便用在生产" | Oracle 的版本支持策略把 21c 定为 **STS（短期支持）**，生产应选 **LTS（19c/23c）** | 🔧 全部 9 本 |
