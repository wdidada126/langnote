# 13 · 高并发系统的架构与设计

> **本章地图**：**"高并发"到底卡在哪一层**（数据库 vs 应用 vs 网络）→ **会话模型**：`dedicated` vs `shared server`（MTS）→ **连接池**（ODP.NET/JDBC/UCP/DRCP/Druid）与"连接风暴"→ **缓存层**（把读压力前移）→ **读写分离**（DG 物理备库 / GoldenGate 逻辑备库 / 中间件）→ **锁等待与热点块**（`enq: TX - row lock contention`、`buffer busy wait`、`gc buffer busy acquire`）→ **短事务与批量提交**→ **分库分表与中间件**→ **TimesTen 内存库（本书里唯一的纵向扩展方案）**→ **一条完整的 3000 TPS 排查路径**。

## 一、核心精讲

> 以下 SQL/DDL 均为**教学示意，不参与构建**，不可也不必在真实实例上执行。

### 1.1 先划清边界：数据库承担高并发的哪一段

一条请求从前端到落到行，会经过：

```
浏览器 → CDN/网关 → 应用集群（N 个实例）→ 连接池 → 数据库实例（1~N 个 RAC 节点）→ 数据文件
                        ↑
                   读多时/cache 命中
                        ↓
                   缓存层（Redis/Memcached）
```

数据库能承担的高并发，取决于**最硬的三件事**：

1. **会话与连接数**（每会话消耗 PGA，敲钟内存）；
2. **单行/单块的写冲突**（这是唯一真正上不去的部分）；
3. **单条 SQL 的执行效率**（一次全表扫能拖垮整个实例）。

**所以"高并发架构"的正确顺序是**：先让**读**尽量不到数据库 → 再把**写**拆到不同行/不同表 → 最后才轮到"扩容数据库实例"（RAC/分布式）。

### 1.2 会话模型：dedicated vs shared server

| 维度 | **Dedicated Server** | **Shared Server（MTS）** |
| --- | --- | --- |
| 会话结构 | 每个会话一个专属服务器进程 | 多个会话**共享**少量服务器进程（dispatcher + shared server） |
| PGA | 每个会话一份，量大 | 总量小得多（共享 server 的内存可共享，或用 `SERIALLY_REUSABLE`） |
| 适用场景 | 长事务、复杂 PL/SQL、报表 | **大量短小事务、连接数巨大** |
| 代价 | 连接数 × 每连接的内存可能把实例拖死 | **一个耗时的长 SQL 会占住一个 shared server**，阻塞其他会话；PL/SQL 状态与会话绑定 |

**判断规则**：

- **OLTP、短事务、连接数上千** → 可以考虑 **shared server 或 DRCP**；
- **长事务、复杂 PL/SQL、批量作业** → 必须 **dedicated**（否则一个长跑作业会饿死一批会话）。

🔧 **2026 的现实**：**"用 shared server 省内存"这条路今天基本被连接池取代了**——因为应用侧用连接池（HikariCP/Druid/UCP）复用会话，根本不需要靠 shared server 来省内存。Shared server 现在主要用于"极大量短连接"的特定场景。

### 1.3 连接池与"连接风暴"

**连接数是数据库最容易失控的资源**：1000 个会话 × 每会话 10MB PGA = 10GB，可能直接 OOM。

| 客户端方案 | 特点 |
| --- | --- |
| JDBC（Oracle OJDBC） | 经典，配 `oracle.jdbc.ReadTimeout` 等 |
| **UCP（Universal Connection Pool）** | Oracle 官方 Java 连接池，支持 **DRCP 集成**、会感知 RAC 服务与故障 |
| **DRCP（Database Resident Connection Pool）** | **会话内存驻留在数据库里**，多个应用进程可共享同一批会话；适合"大量短连接、同一类 SQL" |
| **alibaba/Druid** | 国内 Java 事实标准，能打印慢 SQL 与执行计划 |
| 🔧 **python-oracledb / node-oracledb** | 现代驱动支持 `call_timeout` 与语句级 API，能在不买诊断包的情况下观测语句级延迟 |

**典型事故模式**：应用启动时"连接风暴"——几十个应用实例同时启动，每个都要建 200 条连接 → 数据库瞬间被 1 万会话淹没 → 实例无响应 → 所有应用超时 → 应用重试 → 雪崩。**缓解手段**：

1. **渐进式连接（connection pool warm-up 限速）**；
2. **数据库侧的会话数上限**（`sessions` 参数，或 12c 起的 **Resource Manager 的会话并发限制**）；
3. **熔断与快速失败**（不要让请求堆积在客户端）；
4. 🔧 **`call_timeout` / 语句级超时**：早期版本只有 `sqlnet.outbound_connect_timeout` 这类粗粒度设置，现代驱动能拿到语句级超时。

教学示意，不参与构建：

```sql
-- 用 Resource Manager 限制并发会话数，防止连接风暴打垮实例（教学示意，不参与构建）
BEGIN
  DBMS_RESOURCE_MANAGER.CREATE_PLAN(plan => 'OLTP_PLAN');
  DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
    plan => 'OLTP_PLAN', group_or_subplan => 'OLTP_GROUP',
    max_session_per_user => 50,            -- 每用户最多 50 个会话
    cpu_p1 => 100);
END;
/
```

### 1.4 缓存层：把读压力前移

| 层 | 作用 | Oracle 侧注意 |
| --- | --- | --- |
| 应用级缓存（本地 map / Caffeine） | 防热点 key 打穿 | 与 Oracle 的 `result cache` 不同：它是**应用进程内**的 |
| 分布式缓存（Redis/Memcached） | 共享缓存、抗高并发读 | **缓存与数据库的一致性**（失效 vs 双写 vs 延迟双删） |
| Oracle `result_cache` | 数据库内的查询结果缓存 | **注意结果陈旧问题**（12.x 与旧版行为不同，见 [`06`](06-SQL执行计划与CBO.md)） |

**缓存的失效策略是高并发设计的真难点**：不是"要不要缓存"，而是"缓存与数据库不一致时谁负责通知谁"。常见答案是**写穿透（write-through）+ 失效（invalidate）**，并对关键数据配**延迟双删**。

### 1.5 读写分离：Oracle 的三种做法

| 方案 | 机制 | 延迟 | 适用 |
| --- | --- | --- | --- |
| **物理 DG 备库** | Redo Apply，块级复制 | 通常 **秒级**（LGWR + sync 可压到近乎实时） | 报表、查询、备份、**Active Data Guard 下可读** |
| **GoldenGate 逻辑链路** | 解析 redo 成 SQL 并在目标库执行 | 亚秒级可配 | 跨版本/跨平台复制、多向同步 |
| **中间件路由** | 把 `SELECT` 发到备库、`INSERT/UPDATE/DELETE` 发到主库 | 取决于底层的分离方式 | 应用无感知；**但"读写都在同一事务里"时会出错** |

**读写分离的三个陷阱**：

1. **写完立刻读**：刚写的主库数据不会在备库出现（延迟窗口内）→ 需要"读己之写（read-your-writes）"约定（按主键/用户路由到主库）；
2. **事务内混读写**：一个事务里先写再读，路由到备库就会读到旧数据；
3. **统计类查询**对延迟敏感 → 需要显式标为"要求强一致"。

### 1.6 锁等待与热点块（高并发最常见的三类）

```sql
-- 找"谁在等谁"（教学示意，不参与构建）
SELECT s.sid, s.serial#, s.username, s.event, s.blocking_session,
       s.final_blocking_session, s.wait_class, s.seconds_in_wait,
       q.sql_text
FROM v$session s, v$sql q
WHERE s.sql_id = q.sql_id (+) AND s.blocking_session IS NOT NULL
ORDER BY s.seconds_in_wait DESC;
```

| 等待 | 根因 | 对策 |
| --- | --- | --- |
| `enq: TX - row lock contention` | **应用逻辑**：没提交、忘记提交、长事务持有 | 缩短事务、批量提交、加超时；用 `final_blocking_session` 找根（DBA 攻坚指南的手法） |
| `buffer busy wait` | **同一数据块被多会话并发访问**（ASSM 位图块、热点块） | **分区**（把热点打散到多个块）、减少单块行数 |
| `gc buffer busy acquire`（RAC） | **跨节点热点块** | 把热点行的读写收敛到**同一实例**（服务/实例亲和性）或做**行级 hash 分区** |

**"热点行"的经典解法（按代价从低到高）**：

1. **短事务 + 批量提交**（最有效，成本最低）；
2. **避免"计数器的单点更新"**（如 `UPDATE t SET cnt = cnt + 1 WHERE id = 1` 高并发下必然串行）——改为**先插明细、后聚合统计**（异步汇总）；
3. **分区/分表**把单行热点变成多行热点；
4. **应用层排队/合并**（把同 key 的请求合并成一个写）；
5. 🔧 **换存储形态**（内存库、KV、分布式数据库的行级冲突处理）。

### 1.7 短事务与批量提交

**事务越长，锁持有越久、undo 越大、回滚代价越高**（见 [`04`](04-事务与redo-undo-归档.md)）。高并发下"把长事务改成一批一批提交"通常能带来数量级的吞吐提升：

```sql
-- 反模式（教学示意，不参与构建）：一个大事务更新 500 万行
UPDATE big_t SET flag = 1 WHERE flag = 0;

-- 正解：分批提交（教学示意，不参与构建）
BEGIN
  LOOP
    UPDATE big_t SET flag = 1 WHERE flag = 0 AND ROWNUM <= 10000;
    EXIT WHEN SQL%ROWCOUNT = 0;
    COMMIT;
  END LOOP;
END;
/
```

> **注意**：分批提交**破坏了原子性**——中途失败会留下部分结果。所以必须让分批作业**可重入**（用 `flag` 或业务时间戳做幂等），这是"分批提交"能上生产的**前提条件**。

### 1.8 分库分表与中间件

- **为什么要分**：单实例的写吞吐、单表的索引深度、单表的备份恢复时间都有上限；
- **代价**：**分布式事务、跨分片 join、跨分片排序/分页**都要在应用层或中间件里解决；
- **Oracle 内的"伪分表"**：**分区表（partitioning）** 能在单实例内把热点打散、把维护窗口切成小块（这是 RAC/单机上性价比最高的"分表"）；
- 🔧 **中间件生态**：`apache/shardingsphere`（star 实测 ≈20804）是 Java 生态里最常见的分库分表 + 读写分离中间件；`Vitess`（≈21.4k★，见 `数据库系统概念6` 对照表）在 MySQL 生态里是同类。

### 1.9 TimesTen：本书里唯一的"纵向扩展"答案

《高并发 Oracle 数据库系统的架构与设计》是国内第一本系统讲 TimesTen 的书。它的定位是：

| 维度 | Oracle 数据库 | **TimesTen** |
| --- | --- | --- |
| 数据位置 | 内存 + 磁盘（WAL） | **全内存**（可选小持久化） |
| 事务 | ACID、MVCC、redo | ACID、MVCC、日志（用于恢复） |
| 容量 |  TB 到 PB | **受内存容量限制**（几十 GB ~ TB） |
| 适用场景 | 通用 OLTP/OLAP | **亚毫秒级交易**（金融撮合、会话存储、参考数据缓存） |
| 高可用 | DG/RAC | **Active Standby Pair**（复制对） |

**TimesTen 的现代位置（🔧 必须补的）**：2026 年 TimesTen 不再是"高并发 Oracle"的默认答案——它被三类东西取代或补充：

1. **Redis / Key-Value 数据库**（纯缓存语义、内存级、易扩展）；
2. **In-Memory Column Store（Oracle 12.1.2+ / 19c / 23c）**（在 Oracle 内部直接做内存列存，不必引入 TimesTen 这个独立产品）；
3. 🔧 **国产内存/分布式数据库**（OceanBase 的"内存租户"、PolarDB 的内存节点等）。

### 1.10 一条完整的 3000 TPS 排查路径

把本章和 [`07`](07-SQL性能诊断与调优实践.md)、[`06`](06-SQL执行计划与CBO.md) 串起来，形成可执行动作：

| 步骤 | 看什么 | 工具 |
| --- | --- | --- |
| 1. 是变忙还是变慢 | `DB Time per Sec`、`Executes per Sec` 的趋势 | AWR Load Profile |
| 2. 哪类资源在等 | Top 10 等待事件（先按 `wait_class` 分类） | AWR / ASH |
| 3. 定位到 SQL/对象 | Top SQL（`ELAPSED_TIME`）、Top Segment（`buffer gets`） | `dba_hist_sqlstat` / `dba_hist_segstat` |
| 4. 看计划与绑定值 | `DBMS_XPLAN.DISPLAY_CURSOR(+PEEKED_BINDS)` | — |
| 5. 修 | 改写 SQL / 补直方图 / SQL Profile | [`06`](06-SQL执行计划与CBO.md) |
| 6. 如果是锁 | `blocking_session` → `final_blocking_session` | `v$session` |
| 7. 如果是热点块 | DBA（块地址）→ 对象 → 改设计（分区/短事务/异步） | 本章 1.6 |
| 8. 如果还是不够 | 缓存层 / 读写分离 / 分片 | 本章 1.4–1.8 |

## 二、版本演进

| 版本 | 高并发相关变化 |
| --- | --- |
| 11g | Shared Server 增强；DRCP 雏形；`_use_adaptive_log_file_size` |
| 12.1 | In-Memory Column Store（12.1.2）；`pga_aggregate_limit`；PDB 资源隔离雏形 |
| 12.2 | **PDB `_CPU_PER_CPU` 与 memory limit**（真正的多租户资源隔离）；Flex Cluster |
| 19c | 持续 PRC；自动索引；ADG 与云整合 |
| 23c | 自动索引、向量搜索；自治运维 |

🔧 **2026 年必须补的四条**：
1. **"加内存/加 CPU 就能扛住高并发"的幻想**：真正的瓶颈往往是**单行写冲突**（`enq: TX`）与**单块热点**，扩容解决不了；
2. **连接池的现代化**：`python-oracledb` 的 `call_timeout`、UCP/DRCP、以及**云原生数据库连接器**（代理层）正在取代"每个应用实例直接连库"的模式；
3. **缓存与一致性**：Redis + 延迟双删、Canal/Debezium 做缓存失效通知，已成为高并发读场景的标配；
4. **国产化替代中的"架构重画"**：从 Oracle RAC + DG 的"共享一切"到分布式数据库的"分片 + 共识"，**读写分离、分片键、分布式事务都要重新设计**，不是简单换驱动。

## 四、近年研究与工业界开源实践（2015–2026）

- **近年研究**：
  - **冲销/冲突消解**：**Aria（VLDB 2020）、Orion、FaRM（SIGMOD 2015）**等确定性/高并发数据库研究；
  - **无锁与硬件事务 memory**：Masstree（EuroSys 2012）、Bw-tree（ICDE 2013）；
  - **存算分离下的高并发**：Aurora（SIGMOD 2017）与 PolarDB Serverless，把"写"与"读"解耦；
  - **尾延迟工程**：HdrHistogram 与 PTTP（Tail-at-P99）。
- **工业界开源**（star 为 2026-09-25 `gh api` 实测）：
  - `alibaba/Druid`（≈28178★）：连接池 + 监控，是"高并发 Oracle 应用"最常见的第一道防线。
  - `apache/shardingsphere`（≈20804★）：分库分表 + 读写分离，替代 RAC 的扩展职能。
  - `debezium/debezium`（≈13152★）：缓存失效与数据同步，把"读前移"的缓存层与数据库接起来。
  - `redis/redis`（≈76.5k★，见 `数据库系统概念6` 对照表）：高并发读的事实标准缓存层。
  - `pingcap/tidb`（≈40586★）/ `oceanbase/oceanbase`（≈10291★）：国产分布式数据库，"写扩展"问题的主流答案（见 [`14`](14-12c及以后的演进.md)）。
  - `polardb/PolarDB-for-PostgreSQL`（≈3205★）：共享存储的多节点架构，最接近 RAC 的国产替代形态。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | "RAC 能横向扩展写" | RAC 共享同一份数据与同一个 redo，写并不横向扩展；它提升可用性 + 读扩展 | OracleRAC核心技术详解（第 10–13 章）讲得准 |
| 2 | "把连接数堆上去就能提高并发" | 连接数是内存消耗大户；1000 会话 × 大 PGA 会 OOM。要池化 | 高并发 Oracle 书（会话与连接章） |
| 3 | "用 shared server 就能省内存" | 长事务会占住 shared server 饿死其他会话；2026 年这条路基本被连接池取代 | 🔧 高并发 Oracle 书（2014）的 MTS 建议已部分过时 |
| 4 | "读写分离做完就高并发了" | 有"写后立刻读"与"事务内混读写"两个陷阱；需要"读己之写"约定 | 全部 9 本 |
| 5 | "热点行更新用 `cnt = cnt + 1` 就行" | 高并发下必然串行；改为**先插后聚合**或**异步汇总** | 全部 9 本 |
| 6 | "分批提交会破坏原子性，所以不能用" | 用**可重入 + 幂等**换取吞吐，是工业界的标准取舍 | 全部 9 本 |
| 7 | "分库分表是万能解" | 带来分布式事务、跨片 join、分页与排序的复杂度 | 高并发 Oracle 书（横向扩展维）讲 GoldenGate 数据群，未充分展开分库分表的代价 |
| 8 | 🔧 "TimesTen 还是内存库的首选" | 它的位置被 Redis、Oracle In-Memory Column Store、国产内存/分布式数据库瓜分 | 🔧 高并发 Oracle 书（2014）是"国内首本 TimesTen 专著"，但本书主题已过时 |
| 9 | 🔧 "加机器就能扛住更高并发" | 瓶颈常在**单行写冲突**与**单块热点**，扩容不解决 | 🔧 全部 9 本 |
| 10 | 🔧 "换国产库只要改连接串" | 分片键设计、分布式事务、读写路由语义、PL/SQL 资产都要重画 | 🔧 全部 9 本 |
