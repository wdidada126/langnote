# 05 · 索引与约束

> **本章地图**：**为什么需要索引**（读多写少、定位即快）→ **B-tree 索引的物理布局**（根/枝/叶、叶块双向链表、索引高、聚簇因子）→ **访问路径五选一**（全表扫、索引唯一扫、索引范围扫、索引全扫、索引快速全扫）→ **复合索引与"前导列"规则**（**最容易被记错的一条**）→ **位图索引**（适合低基数列的 OLAP）→ **函数索引与虚拟列索引**（12c 起 `CREATE INDEX ... ON t (expr)`）→ **索引失效的六种情形**→ **索引重建 `REBUILD`/`COALESCE` 的真相**→ **约束**（NOT NULL / UNIQUE / PRIMARY KEY / FK / CHECK，以及 FK 触发的直接/延迟约束与锁表）→ 与 [`数据库系统概念6/11-索引与散列.md`](../数据库系统概念6/11-索引与散列.md) 的对照。

## 一、核心精讲

> 以下 SQL/DDL 均为**教学示意，不参与构建**，不可也不必在真实实例上执行。

### 1.1 B-tree 索引长什么样

```
                    ┌──────────┐        根块 (root)
                    │  15 |    │
                    ├──────────┤
                    │ 875 |    │
                    └────┬─────┘
                          │
              ┌───────────┴───────────┐
        ┌─────┴─────┐           ┌─────┴─────┐
        │  1 | 6 | 9│           │ 20 | 40 | 60│     枝块 (branch)
        └─────┬─────┘           └─────┬─────┘
              │                       │
        ┌─────┴─────┐           ┌─────┴─────┐
     ┌──┴──┐   ┌──┴──┐       ┌──┴──┐   ┌──┴──┐
     │1|row │   │4|row│  ...  │20…  │ … │60…  │    叶块 (leaf)
     └──────┘   └─────┘       └─────┘   └─────┘
        ←————— 叶块之间双向链接，支持索引范围扫描与排序 —————→
```

- **叶块**里存的是 `(索引键值, rowid)`，且**键值有序**，相邻叶块之间**双向链接**——所以 `ORDER BY index_col` 可以不排序；
- **索引高度（BLEVEL/INDEX HEIGHT）** 决定一次索引访问要读几个块：越高的索引（值域大、`DELETE` 很多）越慢；
- **聚簇因子（CLUSTERING_FACTOR）**：索引里相邻 rowid 对应的数据行在表里是否物理相邻。**接近表块数 = 好**（索引范围扫时省 I/O）；**接近表行数 = 差**（一次范围读要跳遍全表）。这是"索引建了但还是慢"的头号原因。

### 1.2 访问路径五选一（教学示意，不参与构建）

| 路径 | 触发条件 | 典型 `PLAN_HASH` 里的行 |
| --- | --- | --- |
| **TABLE ACCESS FULL** | 表小 / 需要大部分行 / 无可用索引 | `SELECT * FROM emp` |
| **INDEX UNIQUE SCAN** | `WHERE pk = :v` | 只访问一个索引块 |
| **INDEX RANGE SCAN** | `WHERE col > :v AND col < :v2`；复合索引按前导列 | 扫一段叶块 |
| **INDEX FAST FULL SCAN** | 只读索引列本身（覆盖索引）、并行可用 | 只读索引段 |
| **INDEX FULL SCAN** | 需要索引全序，且索引比表小 | 顺序读整个索引 |

一个辅助判断：

```sql
-- 看聚簇因子与索引高度（教学示意，不参与构建）
SELECT index_name, clustering_factor, num_rows, leaf_blocks, blevel
FROM user_indexes WHERE table_name = 'EMP';
-- 判断 CBO 为什么选它
SELECT * FROM table(DBMS_XPLAN.DISPLAY_CURSOR(null, null, 'ALL'));
```

### 1.3 复合索引：前导列规则（本章最深的一条坑）

**复合索引 `INDEX (a, b, c)` 相当于按 `(a, b, c)` 排序的一棵树。因此：**

| WHERE 条件 | 是否用索引 | 理由 |
| --- | --- | --- |
| `a = 1` | ✅ | 命中前导列 |
| `a = 1 AND b = 2` | ✅ | 更精确 |
| `a = 1 AND b = 2 AND c = 3` | ✅ | 最精确 |
| **`b = 2`** | ❌（除非用 **index skip scan**，代价通常高于全表扫） | 跳过了前导列 |
| **`b = 2 AND c = 3`** | ❌ | 同理 |
| `a > 1 AND b = 2` | ⚠️ | `a` 是**范围**，`:b` 无法继续用于过滤（除非 `a` 的选择性极好，CBO 可能做 index range scan + filter） |
| `a = 1 ORDER BY b` | ✅ 且**免排序** | 索引天然有序 |
| `ORDER BY b, a` | ❌ | 顺序与索引相反 |

**工程结论**（比背规则更有用）：

1. **等值列在前，范围列在后**（`INDEX (status, created_at)` 而不是反过来）；
2. 若必须支持"只按 `b` 查"，就**另建一个以 `b` 开头的索引**，或者反过来建 `(b, a)`；
3. `NULL` 在 Oracle B-tree 索引里**能被存进索引**（这是 Oracle 与 PostgreSQL 的重要区别！PG 默认不索引 NULL，除非写 `NULLS NOT DISTINCT` 的表达式索引）——所以在 Oracle 里 `WHERE indexed_col IS NULL` **是可以用索引的**，但在 PostgreSQL 里不行。这条极易跨书出错。

### 1.4 函数索引与虚拟列索引

Oracle 11g 起支持函数索引，12c 起更完善。教学示意，不参与构建：

```sql
-- 函数索引：让 TO_CHAR 上的谓词重新可用（教学示意，不参与构建）
CREATE INDEX idx_emp_hiredate ON emp (TO_CHAR(hiredate,'YYYY'));
SELECT * FROM emp WHERE TO_CHAR(hiredate,'YYYY') = '1981';   -- 走索引

-- 更推荐的写法：虚拟列 + 普通索引，可统计、可被约束、可读
ALTER TABLE emp ADD (hire_year NUMBER GENERATED ALWAYS AS (EXTRACT(YEAR FROM hiredate)) VIRTUAL);
CREATE INDEX idx_emp_hireyear ON emp (hire_year);

-- 大小写不敏感检索的经典做法（教学示意，不参与构建）
CREATE INDEX idx_emp_upper_name ON emp (UPPER(ename));
```

> **为什么"函数导致索引失效"这条要单独成节**：因为 CBO 要求**索引表达式与谓词表达式必须逐字节一致**才能匹配。写 `WHERE TO_CHAR(hiredate,'YYYY')='1981'` 而索引是 `TO_DATE(hiredate)`，或反过来，就完全用不上。这也是 `08` 章反模式清单的核心一条。

### 1.5 位图索引：什么时候该用、什么时候是灾难

| 维度 | B-tree | 位图（Bitmap） |
| --- | --- | --- |
| 适用 | OLTP、高基数列、单行定位 | **OLAP、低基数列**（性别、状态、地区） |
| 存储 | 键值 + rowid 列表 | 每个键值一个位串 |
| 写入 | 行级锁，互不干扰 | **一个键值一个位图段** → 改同一键值的所有行会互相锁 |
| 致命场景 | —— | **在 OLTP 高并发写入的表上位图索引 → 严重争用** |

**位图索引在 Oracle 里是 OLTP 的禁区**：因为它把"所有 rowid"压缩进一个位串，UPDATE 同一状态值时会在同一位图段上产生强烈争用（表现为 `buffer busy wait` / enqueue 争用）。所以"给状态列加个索引以加快筛选"这个直觉，在 OLTP 上是错的。

### 1.6 六种"索引失效"情形（按发生频率排序）

1. **谓词上有函数/运算/拼接**（`TO_CHAR(col)`、`col + 0`、`col || ''`、`UPPER(col)` 未建函数索引）；
2. **隐式类型转换**：列是 `VARCHAR2`，谓词给数字 `WHERE phone_no = 13800000000` → 实际执行 `TO_NUMBER(phone_no) = 138...`；
3. **前导列缺失**（复合索引 1.3）；
4. **`NOT`/`!=`/`<>`**：**并不必然导致索引失效**（CBO 可以把 `!=` 转成 `OR` 的范围），但 `NOT IN` 遇到 `NULL` 会直接返回空集（见 `08`）；
5. **`LIKE '%xxx%'` 前导通配符**：可以用索引做**前缀匹配**（`LIKE 'xxx%'` 可以，因为索引有序），但 `'%xxx'` 不行；
6. **统计信息陈旧 / 表行数过少 / 选择性好但 CBO 估计错了**——这类"不是失效而是优化器放弃"，需要用 `DBMS_STATS` 或 hint 干预。

### 1.7 索引重建：真相

| 手段 | 作用 | 真相 |
| --- | --- | --- |
| `ALTER INDEX ... REBUILD` | 重建索引结构 | **需要空间**（约原索引大小），**在线重建**（`ONLINE`）要等所有 DML 结束，且**仍会锁住基表的部分操作**；不必停机，但代价不低 |
| `ALTER INDEX ... COALESCE` | 合并相邻叶块 | 轻量，**不能真正降低高度**，只缓解碎片 |
| `DROP` + `CREATE` | 最干净 | 会锁表，且索引可用性的瞬间丢失 |

**什么时候真的需要重建？** 只有这几类：索引高度异常高（`blevel` 明显偏大）、大量删除后想回收空间、索引损坏（ORA-08102 / ORA-01450）。**"索引碎片导致变慢"这个说法被过度传播**——叶块空不影响单次读的块数（因为 Oracle 仍读所有叶块），只影响空间利用率。现代做法是：先 `COALESCE`，测了没效果再 `REBUILD`，而不是条件反射地重建。

### 1.8 约束：Oracle 的实现方式与代价

| 约束 | 是否建索引 | 代价 |
| --- | --- | --- |
| `NOT NULL` | 不需要 | 最便宜（可走 `CHECK` 约束或索引） |
| `UNIQUE` / `PRIMARY KEY` | **自动建唯一索引** | 保证唯一性的同时提供访问路径 |
| `FOREIGN KEY` | **不自动建** | 父表删除子表相关行时**要扫描子表** → 必须在子表外键列上建索引，否则父表 DML 锁死 |
| `CHECK` | 不需要 | 校验开销 |

**外键的两条硬规则**（生产事故高发）：

1. **父表做 DELETE / PK 更新时，若子表没有外键索引，会对整个子表加锁** → 表现为"删除主表一条记录，另一个会话被卡住"；
2. **FK 的 `ON DELETE CASCADE` 在大表上会一次性删除巨量子行**，undo/redo 爆炸。

教学示意，不参与构建：

```sql
-- 检查外键是否缺索引（教学示意，不参与构建）
SELECT c.constraint_name, c.table_name, cc.column_name
FROM user_constraints c, user_cons_columns cc
WHERE c.constraint_type = 'R' AND c.constraint_name = cc.constraint_name
  AND NOT EXISTS (
    SELECT 1 FROM user_ind_columns ic
    WHERE ic.table_name = cc.table_name
      AND ic.column_name = cc.column_name
      AND ic.column_position = 1);
```

> 上面这条是 DBA 巡检脚本的经典一项，也是 DBA 攻坚指南"日常运维"章的思路。

## 二、版本演进

| 版本 | 索引相关变化 |
| --- | --- |
| 8i | 位图索引、函数索引（8.1.5） |
| 10g | **索引跳过扫描（skip scan）** 引入；`MONITORING` 索引使用 |
| 11g | 数据库索引压缩（Advanced Index Compression）、`INVISIBLE` 索引、`SYS_OP_MAP_NONNULL` 让 `NULL` 也能进函数索引 |
| 12.1 | **更大索引块（16K/32K）**、`MAX_STRING_SIZE=EXTENDED` 下 `VARCHAR2(32767)` 的上限索引问题 |
| 12.2 | 优化器默认变化（见 `14`）、`optimizer_adaptive_features` |
| 19c | **自动索引（Auto Indexing）**——见 `14`；索引 advisor 更智能 |
| 23c | 向量索引（AI vector search）加入索引体系；JSON 索引与 JSON Relational Duality 配套 |

🔧 **2026 年必须补的三条**：
1. **索引跳过扫描（skip scan）不是"前导列缺失的万能解"**：CBO 只对**前导列基数很低**（如性别）的复合索引才考虑，且往往代价高于全表扫。本书时代的"加个 `INDEX_SS` hint"建议现在基本没人用了。
2. **不可见索引（INVISIBLE）成了发布流程的标配**：先建 invisible 索引验证性能，确认后再 `VISIBLE`，避免"上线即慢"。
3. **自动索引（Auto Indexing，21c 起正式、19c 有 `DBMS_AUTO_INDEX`）会"偷偷建索引"**，如果不关掉，生产库上会出现一批无法解释的索引（且消耗空间与 DML 性能）。这条必须在 19c/23c 环境里显式管理。

## 四、近年研究与工业界开源实践（2015–2026）

- **近年研究**：
  - **向量索引与 AI 检索**：HNSW、IVF-PQ、DiskANN；23c 的 AI Vector Search 与之同构（见 `14`）。相关开源实现 `pgvector/pgvector`（≈23.2k★，见 `数据库系统概念6` 目录对照表）与 `facebookresearch/faiss`（≈41.0k★）可作对照。
  - **自动索引调优**：Agrawal 等《Automatic Database Index Tuning》（SIGMOD 2000）是自动索引的理论源头，2020 年代又随 ML 优化器回归——这正是 19c/23c 自动索引（见 `14`）的学术 lineage。
  - **列存跳过索引（zone maps / min-max）**：Parquet 的 row group 统计、ClickHouse 的 primary index，与 B-tree 是"有序 vs 分区裁剪"的不同取舍。
- **工业界开源**（star 为 2026-09-25 `gh api` 实测）：
  - `postgres/postgres`（≈22192★）：PG 的 B-tree 实现（GiST/SP-GiST/BRIN 更丰富）+ **PostgreSQL 默认不索引 NULL**（与 Oracle 相反），是本章 1.3 那条对照的最好注解。
  - `pingcap/tidb`（≈40586★）：TiKV 的 RocksDB + 上层 `coprocessor` 索引，跨节点索引访问路径与 Oracle 的单机索引不同。
  - `oceanbase/oceanbase`（≈10291★）：国产分布式数据库，兼容 Oracle 语法与 PL，索引实现可直接与本章对照。
  - 🔧 `apache/shardingsphere`（≈20804★）：分库分表中间件。分片键上建"本地索引 + 全局索引"的取舍，与本章"复合索引前导列"是同一类问题的分布式版本。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 | 书目 |
| --- | --- | --- | --- |
| 1 | "索引建了就一定会用" | CBO 决定是否用，**与建没建无关**；小表、选择性好但估计错误时都会放弃 | 12c 教材（第 10 章）、SQL 优化最佳实践（原理篇） |
| 2 | "`!=` 一定不走索引" | 不一定；CBO 可转成范围条件。真正致命的是**函数包装与隐式转换** | SQL 优化最佳实践（访问方式章） |
| 3 | "`NOT IN` 只是慢" | **遇到 `NULL` 直接返回零行**（不只是慢）。详见 `08` | SQL 应用及误区分析（第 3–6 章）有案例 |
| 4 | "位图索引适合高并发 OLTP" | **恰恰相反**：改同一键值的所有行会争用同一个位图段，是 OLTP 禁区 | 全部 9 本（位图索引部分普遍未强调这一风险） |
| 5 | "索引碎片了就重建" | 叶块空不影响单次读块数；先 `COALESCE`，测过再 `REBUILD` | SQL 优化最佳实践未展开；DBA 攻坚指南有索引维护流程 |
| 6 | "外键不建索引没关系" | 父表 DML 会对子表加锁，是锁等待与卡死的经典成因 | 全部 9 本未作为巡检项强调 |
| 7 | "Oracle 的 `IS NULL` 不能用索引" | Oracle **索引里能存 `NULL`**（`IS NULL` 可用索引）；**PostgreSQL 恰恰相反**（除非建 `NULLS NOT DISTINCT` 的表达式索引）——跨库迁移时这是高频错误 | 全部 9 本 |
| 8 | 🔧 "索引跳过扫描能救所有前导列缺失" | skip scan 只对**前导列低基数**有收益，且常被 CBO 判为贵于全表扫；不要用它当默认方案 | 🔧 全部 9 本（成书 2009–2021，skip scan 的建议已过时） |
| 9 | 🔧 "19c/23c 环境里索引不用管" | **自动索引（Auto Indexing）会自己建索引**（消耗空间、拖慢 DML，且需显式管理）；同时"函数索引 + JSON 索引 + 向量索引"已构成多类型索引体系 | 🔧 全部 9 本均未覆盖 19c/23c 的自动索引 |
