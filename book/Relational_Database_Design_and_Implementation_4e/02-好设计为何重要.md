# 02-好设计为何重要（Ch3 Why Good Design Matters, pp.47–53 ✅）

> 三态：✅ 书页 TOC/Crossref 页码实抓 · ⚠️ 转述/推定展开 · 🔧 本机 SQLite 实测（**非本书示范行为**）。
> 本章只有 7 页（47–53 ✅ 区间实测），是全书最短的正文章——它的角色是 Part II 的「病因学导论」：先用三种异常把「坏设计」的成本说清，再把后面六章（实体/模型/代数/规范化/调优/Codd 规则）立为处方。

## 一、精读札记（官方二级小节 ✅ 逐条）

- **Effects of Poor Database Design** —— 总起：设计缺陷不是审美问题而是运维负债。
- **Unnecessary Duplicated Data and Data Consistency** —— 冗余的代价＝同一事实多副本，副本更新不同步即「陈旧不一致」（staleness）。
- **Data Insertion Problems** —— 有些事实「进不去」：外键/结构缺位迫使插入伪造或搁置（insertion anomaly）。
- **Data Deletion Problems** —— 删一条业务记录顺带销毁了另一类事实（deletion anomaly）。
- **Meaningful Identifiers** —— 标识列设计：代理键 vs 语义键；好的标识应短、稳、不承载业务含义变化 ⚠️（页内措辞不可达）。
- **The Bottom Line** —— 结论节：坏设计的成本在「每一次」增删改里摊销。

## 二、主题深读

### 2.1 🔧 E1 实测：三异常在 SQLite 里一次跑穿（非本书示范行为）
反规范表 `orders_bad(order_no, cust, cust_city, item1, qty1, item2, qty2)`（重复组列位），demos.txt 实录：
```
update异常: 改ACME城市后 102 仍为 NY
insert异常: 新客户无订单必须留整行空重复组位(无法只存客户)
delete异常: 删101(唯一含Boston的行)后, ACME 城市只剩陈旧值: [('NY',)]
```
同一 UPDATE 语句作用域只盖住一行——**副本陈旧是结构性的，不是纪律性的**。
拆成 3NF 五表（customers/orders/items/order_items+FK）后：
```
3NF后: 单行更新生效 ACME= Boston ; 删102后商品目录仍存 2 件; 客户表仍存 2 家
```
插入异常（只存新客户）与删除异常（删订单不毁目录）同时消失。这就是本章 7 页想要的全部——教材用一屏数据演示，本目录用 24 行 SQL 复现。

### 2.2 异常（anomaly）概念的谱系位置
三种异常是 Codd 1972 冗余理论的教学化遗产：Elmasri&Navathe 用几乎同样的「供应商-项目」例题讲同一 trio（见 [../Database_Modeling_and_Design_5e/06-规范化.md](../Database_Modeling_and_Design_5e/06-规范化.md)）；Date 则拒绝把它停在轶事层面，直接上函数依赖代数（[../Database_Design_and_Relational_Theory/00-总览与阅读地图.md](../Database_Design_and_Relational_Theory/00-总览与阅读地图.md) 的 FD/BCNF 章群）。三册对读＝同一病理的三种表述层级：故事级（本章）→范式级（DMD）→公理级（Date）。

### 2.3 Meaningful Identifiers：代理键论战的 2016 版措辞
本章点名的「有意义的标识符」议题在 2026 只是更尖锐：自然键（身份证/邮箱/税号）携带隐私与变化风险，纯代理键（自增/UUID）又丢了业务可辨性；行业实践滑向「代理主键 + 自然键 UNIQUE + 时间有效性」三件套（SQL:2011 时期区间的工业化，⚠️ 通说转述）。Harrington 在 Ch3 埋的伏笔要到 Ch11 DDL 与 Ch21 索引才全部兑现。

### 2.4 与 Ch25 数据质量的镜像关系
Ch3 讲的是**结构造成的**不一致；Ch25 讲**数据本身**的四型脏值（缺/错/不可解/不一致）。同一枚硬币两面：设计防「陈旧」，质量流程防「进错」。[17-数据仓库与数据质量](17-数据仓库与数据质量.md) 的 E6 实测与本章 E1 构成全书质量叙事闭环。

### 2.5 The Bottom Line：「设计债」的教材原型
Ch3 末节（✅ 节题）走成本叙事——三异常→维护代价的因果链是 technical debt 概念在数据库教材里的具体化（评注 ⚠️）。三异常的事故学翻译：**更新异常**=改一处漏一处的补丁工单（E1 🔧 实录：改 ACME 城市后 102 仍为 NY——一次「修完仍错」的完整标本）；**插入异常**=为存目录被迫造占位行/空键 hack（E1 实录：新客户无订单必须占整行重复组位）；**删除异常**=业务事实被静默删没（E1 实录：删 101 后 ACME 城市只剩陈旧值 [('NY',)]）。规范化收益同样可双面复现：3NF 后「单行更新生效、删 102 商品目录仍在、客户表仍存 2 家」（demos ✅ 行）——本章 7 页（✅ 47–53）的全部论证在一份 6 行脚本里成立，这就是它作为「痛点章」的底气。

### 2.6 Meaningful Identifiers 的 2026 补件：ID 技术谱系（⚠️ 综合 + 🔧 载体注）
§2.3 已开代理键论战；此处补现代 ID 选型谱：自然键（证件号/SKU）→自增整数（单机默认）→UUID（随机性破坏局部性、索引代价大）→ULID/Snowflake（时间有序+分布式）→业务哈希（幂等去重键）。每一代都是对「有意义且稳定」两难的新补丁。🔧 载体小事实（非本书示范行为）：SQLite 的 AUTOINCREMENT 只允许挂在 INTEGER PRIMARY KEY 上（本机报错实录，demos 前置调试记录）——「代理键在方言里是有门槛的特性」的最小证据；纵深读盘上 [../Using_SQLite/00-总览与阅读地图.md](../Using_SQLite/00-总览与阅读地图.md)（00 §七在册 ✅）。

### 2.7 与 Ch5 域、Ch10 完整性线的接缝
Effects of Poor Database Design（✅）的三异常本质是「事实被存了多次」——对策有两层：结构层（Ch7 分解，06 文件）与执法层（域/约束/触发器，04 §2.6、08 §2.1）。本章故意不讲 FD（推定 ⚠️，小节清单无 FD 字样 ✅ 佐证）——它只负责让读者**疼**；Ch3→Ch7 的 28 页间距就是「先案例后理论」的教学斜线。读毕本章应能回答：三异常各在 E1 的哪一行输出里？——答案全部在 demos 台账，一字不缺。

### 2.8 本章课堂剧本（教学转译 ⚠️）
2026 自学者最小实验（30 分钟，SQLite，非本书示范行为）：①照 E1 建反模式宽表；②UPDATE 城市→SELECT 验证 102 陈旧；③DELETE 唯一含 Boston 的行→验证目录事实蒸发；④同数据拆 3NF 重放三步。疼痛在前、术语在后——这正是作者把本章放在理论部（Part II）第一章的编排意图（评注）。

## 最新演进与工业实践
- 2026 共识：更新异常论仍是 OLTP 建模第一课；其「反命题」——为读性能显式反规范——由物化视图/OLAP 列存（DuckDB 类）制度化，关键是**冗余必须声明来源并保持单点写**。
- SQLite 官方把 FK 强制做成显式开关（默认 OFF）的设计文档仍是约束教学最佳读料：https://www.sqlite.org/foreignkeys.html ✅ URL 实查 2026-10-02；本目录 E2 实测的「事务中 PRAGMA 是 no-op」陷阱是该页机制的直接推论。
- 代理键工业化：UUIDv7/ULID 时间有序方案普及，解决纯随机键对 B 树索引局部性的破坏（与 Ch21 索引节合读，见 [14-视图_CTE与索引](14-视图_CTE与索引.md)）。
- 数据质量框架（Great Expectations 类）可视为 Ch3+Ch25 的自动化执行器：结构约束进 schema、内容断言进 pipeline（详见 [../Data_Observability_for_Data_Engineering/00-总览与阅读地图.md](../Data_Observability_for_Data_Engineering/00-总览与阅读地图.md)）。
- 三异常可量化为「变更放大率」（一次业务改动触碰行数）——坏设计的 CI 指标化（⚠️ 综合）。
- 设计债利息按 schema 变更半径计——迁移工具链是还债通道（⚠️）。
- ID 工程账：UUID 索引随机写代价 vs Snowflake 时钟回拨风险——每代 ID 是新权衡（⚠️ 通识）。
- 代理键休战形态：对外自然键、对内代理键+唯一约束兜底（⚠️ 综合）。
- 复现成本归零：Ch3 全论证在 SQLite 单机 30 分钟完成（§2.8；🔧 非本书示范）。
