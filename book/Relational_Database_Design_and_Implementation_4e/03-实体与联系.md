## 一、精读札记（官方二级小节 ✅ 逐条）

- **Entities and Their Attributes** —— 实体=可唯一辨识的事物；属性=实体的性质；一次实例化=一行。
- **Domains** —— 属性的取值全集（含数据类型与约束语义）；为 Ch11 SQL DOMAIN 与 CHECK 埋线。
- **Basic Data Relationships** —— 一对一/一对多基数；联系的读法（父子、引用、归属）。
- **Documenting Relationships** —— ER 记号（鸦脚/Crow's foot 系 ⚠️ 通说）与关系图的文档化。
- **Dealing with Many-to-Many Relationships** —— 核心手术：M:N 不能直接落成表，必须**分解为两个 1:N + 一座交叉表（junction table）**。E1 的 order_items 就是该手术刀。
- **Relationships and Business Rules** —— 基数与存在性依赖最终都是业务规则的编码；规则变化=模式迁移。
- **Data Modeling Versus Data Flow** —— 静态结构 vs 动态流程：ER 图不画「先后」，流程归 DFD/CASE（接 Ch12）。
- **Schemas** —— 概念/逻辑/物理三层的前置定义（接 Ch9 物理/逻辑独立性）。

## 二、主题深读

### 2.1 M:N 分解：本章唯一的「定理级」操作
教材把多对多处理放在第 5 小节是有意的：**分解交叉表同时完成三件事**——满足 1NF（消灭重复组列位）、给联系本身发键（交叉表 PK=(左FK,右FK)）、为联系属性留位（qty/日期挂在交叉表而非任何一侧）。E1 实测五表模型里 `order_items(order_no,item_no)→(PK) + qty` 即教科书形态；🔧 补充实证（demos.txt E3）：闭包机器检验「{ENO} 唯一候选码」的判定法可直接推广到验证交叉表超键极小性——**联系属性的存在性决定交叉表要不要再加独立代理键**（联系自身还有联系时）。

### 2.2 域（Domain）的两副面孔
Ch4 里 Domain 是语义层（「州码∈{NY,NJ,…}」），Ch11 才拿到 SQL 语法身（CREATE DOMAIN/CHECK）。2026 现场：SQLite 无 CREATE DOMAIN ⚠️ 官方文档无该语句（本目录 🔧 用 CHECK 模拟，见 08 文件）；DuckDB 有 CHECK 无 DOMAIN（1.5.5 本机实证，constraints 文档页 ✅ https://duckdb.org/docs/stable/sql/constraints ）。语义域在工业界的替身是「共享枚举字典+校验管道」。

### 2.3 数据建模 vs 数据流——被低估的一节
这节反对的是初学者最常见错误：把处理顺序画进 ER（「先下单后发货」的箭头）。ER 只回答「什么与什么相关」，时序属于需求侧流程模型。与 Date 的关系模型静态观（[../Relational_Theory_for_Computer_Professionals/01-数据库基本概念.md](../Relational_Theory_for_Computer_Professionals/01-数据库基本概念.md)）完全同调：关系代数无「顺序」，只有「依赖」。

### 2.4 与盘上 ER 纵深对照
DMD5e 的 ER/UML 两章（[../Database_Modeling_and_Design_5e/02-实体联系模型ER.md](../Database_Modeling_and_Design_5e/02-实体联系模型ER.md)、[../Database_Modeling_and_Design_5e/03-UML对象建模.md](../Database_Modeling_and_Design_5e/03-UML对象建模.md)）覆盖弱实体/特化泛化等本章未走深的部分；本书把那些留给 Ch27 对象关系一章（架构取舍：设计先行、OO 后置 ⚠️ 评注）。Enhanced ER 概念可经 Wikipedia 条目族旁读 ⚠️（本机维基不可达，URL 不列 ✅ 级）。

### 2.5 🔧 概念→表的最小翻译（非本书示范行为）
```sql
CREATE TABLE customers(cust VARCHAR PRIMARY KEY, city VARCHAR);          -- 实体+属性
CREATE TABLE order_items(order_no INT REFERENCES orders(order_no),
  item_no INT REFERENCES items(item_no), qty INT,
  PRIMARY KEY(order_no,item_no));                                        -- M:N→交叉表
```
E1 全程：坏表单行 UPDATE 漏改 102（陈旧）；翻译后 `UPDATE customers SET city='Boston'` 一行生效、删订单 102 后目录 2 件/客户 2 家俱在。**基数约束的可执行子集只有 PK/FK/UNIQUE/CHECK 四件套**——ER 图上鸦脚的双侧强制在 2016 与 2026 都需要应用层补位（⚠️ 工程通说）。

### 2.6 Domains 小节的双重纪律：语义约束 vs 物理约束
Domains（✅ 节题）是本章最易被跳、却最不该跳的一节：一个字段的允许值集合就是半条业务规则。现代两副面孔：**语义面**——CHECK/枚举/域对象（🔧 E2 实录：DuckDB 1.5.5 拦下 `CHECK((a > 0))` 违例，Constraint Error 原文在 demos——域执法面有机器标本）；**物理面**——类型/宽度/编码/排序规则（大小写与尾空格之祸，🔧 E6 的 'new york ' 标本即域不完整的代价，见 17 §2.1）。Ch4 概念层讲域、Ch11 语法层讲 DOMAIN（08 §2.2 已开方言落差）——两章对读，「域」才不会退化成「都是 VARCHAR」。

### 2.7 Relationships and Business Rules：把基数词翻译成执法矩阵
小节题 ✅；本册将其「基数与模态」语汇翻成可执行对照（综合 ⚠️+🔧）：

| 业务规则 | DB 执法件 | 实测状态 |
|---|---|---|
| 一而二、二而一（1:1） | 一侧 FK+UNIQUE | 🔧 E2：UNIQUE 强制 ✅ |
| 至少一（强制参与） | NOT NULL+FK | 🔧 E2：FK 强制 ✅ |
| 至多一 | UNIQUE/复合 PK | 🔧 E2：复合 PK 拦 duplicate key "1, 1" ✅ |
| 多数（1:N/M:N） | FK/中间表 | §2.1 定理 |
| 值域/区间 | CHECK | 🔧 DuckDB 强制、SQLite 亦强制 |

矩阵外的规则（跨行/跨时点约束）就是应用层校验与触发器的出生证——「规则即代码」在 2026 的对应物是迁移脚本里的约束+CI 断言（⚠️）。

### 2.8 Schemas 小节与 schema 演化工程
Schemas（✅ 节题，本章首现「模式」术语）在教材只有定义义务；2026 的对应工程是**迁移纪律**：模式变更要版本化、可回放、可评审（Flyway/dbt/Atlas 类，⚠️ 通识登记）。🔧 载体注（非本书示范行为）：SQLite 的 ALTER TABLE 能力是裁剪过的（官方 lang_altertable 页 ✅，00 取证链在册；「12 步重建舞」的操作代价见 08 §2.6 对位）——教材一句「修改表结构」，在弱 DDL 方言里是一整套备份-迁移-重命名流程：概念章与执法章（08/09）的温差在此再确认。

## 最新演进与工业实践
- ER 建模的 2026 工业位：仍是一切关系设计课第一课，但交付物从「图」变为「图+可执行 DDL 双轨」，M:N 分解在迁移工具（如 dbt 关系组件）中自动检查（⚠️ 通说）。
- DuckDB 约束文档页实测在线（✅ URL 见 §2.2），其 CHECK/PK/UNIQUE/FK 全强制姿态与 2026 分析型引擎「约束是元数据也是执法者」路线一致；SQLite 则维持「声明宽松+显式开关」的嵌入式哲学（foreignkeys 页 ✅）。
- 本波取证联动：K10plus MARC 著录本身即「实体-联系」思想在元数据工业的活样本（100/245/264 字段=实体属性，ISBN→著录=1:N），与本章可互相注解（00 §二方法复用）。
- 域→语义→执法三级读法（Ch4 概念→Ch11 语法→E2 机器）贯穿 04/06/08/09。
- 2026 建模工具把 §2.7 演化纪律产品化：图、库、脚本三态合一（⚠️）。
