> 22 页把「多用户」难题摊开：并发三祸（丢失更新/脏读/不可重复读之属）、三解（悲观锁/乐观锁/多版本）、隔离级别、Web 与分布式外延。教材以分类学为主、实现细节点到——🔧 E4 恰好提供分类学的机器标本。

## 一、精读札记（官方二级小节 ✅ 逐条）

- **The Multiuser Environment** —— 共享+时长交叠=冲突母体；单用户 DBMS 世界的边界。
- **Problems with Concurrent Use** —— 丢失更新/不一致读/幻读问题谱 ⚠️（书内措辞不可达，按标准分类学对位）。
- **Solution #1: Classic Locking** —— 2PL 传统：共享/排他、粒度（行/页/表）、锁升级与死锁检测。
- **Solution #2: Optimistic Concurrency Control (Optimistic Locking)** —— 校验版本号/时间戳，冲突即回滚重试；Web 时代默认心智。
- **Solution #3: Multiversion Concurrency Control (Timestamping)** —— 读旧写新、快照隔离的机理（MVCC 与时间戳排序同节讲授 ⚠️ 书内合并处理）。
- **Transaction Isolation Levels** —— READ UNCOMMITTED/COMMITTED/REPEATABLE READ/SERIALIZABLE 四级与异常的映射表。
- **Web Database Concurrency Control Issues** —— 无状态 HTTP 下事务窗口=页面往返，长事务禁行。
- **Distributed Database Issues** —— 两阶段提交、复制延迟下的一致性观（接 Rule 11 分布独立）。

## 二、主题深读

### 2.1 🔧 E4 实测：锁分类学的嵌入式标本（非本书示范行为）
demos.txt 全录：
```
busy_timeout=0: 写锁冲突 database is locked, 0.5ms 即弃
deferred 事务内 UPDATE 遇写锁: 等满 500ms 后放弃（实测 580ms database is locked）
WAL 读不阻塞: 写事务进行中并发读=0（旧值=快照隔离雏形）
回滚+锁释放后重试成功 g.v=2
DuckDB: 同进程双连接共享可行; 跨进程双写→ IO Error: Cannot open file "...另一个程序正在使用此文件"（单写者文件锁）
```
对应教材坐标：SQLite=WAL 下「单写多读+读快照」，是 Classic Locking（写锁排他）与 MVCC（读旧值）的**混合最小实现**；DuckDB=「一写多读、进程级独占」把分布式问题的答案换成「别让两个人写」。教材的三解法在两引擎上各取一瓢——E4 让分类学落地为可观察行为。
### 2.2 隔离级别的「实现真空」
书内 SERIALIZABLE 靠强锁/强快照达成；🔧 现场：SQLite 全库写序列化天然接近 SERIALIZABLE（单写者队列），但 deferred 事务的升级失败（E4 的 580ms 案例）说明**可达性不等同无冲突**——应用重试层仍必需。工业教条「悲观改乐观+版本号列」在书内 Solution #2 已有名分，2026 的化身是 ORM 的 version 列与 ETag/If-Match 语义（Web 节的外延扩展 ⚠️）。
### 2.3 Web 节的先知与缺口
「事务窗口=页面往返」是 2016 教材里少见的好论断；缺口在 2026 形态：Serverless 函数冷启动/异步队列把「会话内事务」变成「 Saga 编排+补偿事务」（微服务语境盘上 ../Database_Reliability_Engineering 在册 ✅ 可纵读其一致性章）。
### 2.4 死锁的沉默
本章 TOC 无死锁专节 ✅——教材假设单库短事务世界死锁罕见；E4 的 deferred 锁升级死锁模式（两个未提交事务互等升级）正是教科书式前奏：写事务一律 BEGIN IMMEDIATE 即可预防（SQLite 官方口径 ✅ 见 foreignkeys/locking 文档族；本目录 E4 的 IMMEDIATE 用法即处方）。

### 2.5 锁粒度阶梯：本书分类学的载体检验（🔧 E4 复用，非本书示范行为）
书内 Classic Locking（✅）按共享/排他与粒度（行/页/表）分类；本机两栈给的是**粗粒度极端样本**：SQLite 写锁是库级的（demos：写冲突 `database is locked`，busy_timeout=0 时 0.40ms 即弃；deferred 事务内 UPDATE 遇锁等满 500ms 后放弃、实测 554ms——超时作用于语句而非 BEGIN 的升级陷阱同场登记）；DuckDB 是文件级单写者（跨进程开库得 IO Error，同文件即拒——比「表锁」更粗的「库锁」实锤）。结论：教材的粒度阶梯在嵌入式载体上塌缩为「一读全开、一写全关」——**读 MVCC 写粗锁**恰是 2016 章内三种方案（✅ 经典锁/乐观/MVCC）在单机时代的合体形态。

### 2.6 隔离级别矩阵与命名漂移（补 §2.2 的实现真空）
书内 Transaction Isolation Levels（✅ 节题）对应标准的四级：RU/RC/RR/Serializable，配三异常名：脏读、不可重复读、幻读（⚠️ 通识表）。2026 的现实注记三条：①各引擎命名漂移（Postgres 的 Repeatable Read 已防幻读、其 RC 成为事实默认；快照隔离=RC 的工程化身 ⚠️）；②SQLite 的 deferred 事务**升级竞态**（读位点后被他人改写——demos 的回滚-重试成功 g.v=2 标本就是这个竞态的处置循环，🔧 非本书示范）；③WAL 的「读不阻塞写」（demos：并发读旧值=0，快照雏形）给 MVCC/Timestamping 一节（✅）的最便宜教具。

### 2.7 乐观锁的落地形态与 Web 节对账（§2.3/§2.4 合流）
Optimistic Concurrency Control（✅）在生产里的标准形态=**版本列谓词更新**：UPDATE … SET ver=ver+1 WHERE id=? AND ver=?——影响行数 0 即冲突，重试或并轨；ORM 的 rowversion/optimistic locking 特性就是这个三行 SQL 的封装（⚠️ 综合）。Web Database Concurrency Control Issues（✅ 节题）2016 年点的坑（长会话、连接池、表单重提交）2026 各有制度化填法：无状态令牌、池化代理、幂等键。Distributed Database Issues（✅ 收尾节）的后裔是微服务 saga 与 Outbox 模式——教材用它收尾的直觉正确：**并发的终局是分布式事务的经济学**（盘上纵深可接 15→18 的 NoSQL 一致性线）。
