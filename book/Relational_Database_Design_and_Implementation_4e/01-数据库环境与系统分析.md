# 01-数据库环境与系统分析（Part I, pp.1 ✅；Ch1 The Database Environment, pp.3–26 ✅；Ch2 Systems Analysis and Database Requirements, pp.27–43 ✅）

> 三态：✅ 本工程实抓（书页 TOC/Crossref 章页码）· ⚠️ 转述/推定展开 · 🔧 本机 SQLite/DuckDB 实测（**非本书示范行为**）。
> 本篇定位：全书的「问题陈述层」——先讲数据库为何存在、谁拥有数据、DBMS 处在什么环境，再讲数据库需求如何从系统分析中产生。教材写法（Harrington 自 1984 年起写数据库教科书 ⚠️ 小传转述），面向无强先修的高年级/研究生入门课。

## 一、精读札记（官方二级小节 ✅ 逐条）

**Ch1 The Database Environment**（3–26）
- Defining a Database —— 数据库＝按主题组织、供多应用共享的持久数据集合；与「一堆文件」的边界在**共享**与**结构**。
- Systems that Use Databases —— 事务处理/报表/决策支持三类消费形态（⚠️ 通说转述）。
- Data “Ownership” —— 数据所有权归业务部门，DBA 是「监护者」而非「所有者」；这是组织学论点，技术书常跳过。
- Database Software: DBMSs —— DBMS 职能：存储管理、并发、恢复、安全、语言接口；文件系统方案的失败是教材标准论证。
- Database Hardware Architecture —— 客户端-服务器/三层/浏览器-服务器拓扑（2016 版语汇，尚无云原生分节 ⚠️）。
- Other Factors in the Database Environment —— 备份窗口、审计、法规等行业差异。
- Open Source Relational DBMSs —— MySQL/PostgreSQL 双开源支柱点名（⚠️ 页内细节未可达，仅 TOC 实证）。

**Ch2 Systems Analysis and Database Requirements**（27–43）
- Dealing with Resistance to Change —— 需求阶段的最大变量是人。
- The Structured Design Life Cycle —— 瀑布式生命周期：需求→分析→设计→实现→维护（教材立场，2016 未纳敏捷 ⚠️）。
- Conducting the Needs Assessment —— 访谈/观察/文档取证三件套。
- Assessing Feasibility / Generating Alternatives / Evaluating and Choosing —— 可行性三分（技术/经济/操作）与备选方案矩阵。
- Creating Design Requirements —— 产出：数据需求清单＋处理需求清单，喂给 Part II 的 ER 建模。
- Alternative Analysis Methods —— 原型法、JAD 等替代路径（⚠️ 通说）。

## 二、主题深读

### 2.1 「数据所有权」为何值得单独一节
Harrington 把组织学议题写进技术开篇，工程含义是：**需求失真多半不是问不出，而是没人有权回答**。数据库设计失败模式里「部门各存一份」正是不愿确权的结果——直接呼应 Ch3 的重复数据病根。

### 2.2 生命周期与需求→模型的接缝
Ch2 的输出物（设计需求）恰好是 Ch4「实体/属性/联系」的输入词表：需求句里的名词≈实体、动词≈联系、量词≈基数。教材没明说这条映射，但三个案例（Ch13–15）全部按这个接缝展开（⚠️ 由案例结构推定）。

### 2.3 开源 DBMS 小节的时代切片
2016 版以 MySQL/PostgreSQL 为开源代表；今天（2026）同一节要重写的清单是：PostgreSQL 家族、SQLite（嵌入式事实标准）、DuckDB（分析内嵌引擎）、云托管（Aurora/AlloyDB/Cloud SQL 等 ⚠️ 未验 URL 不列）。本目录的 🔧 实验选 SQLite/DuckDB 正是该节「开源关系」血脉的 2026 延伸——但**本书未示范任何这两个引擎的行为**。

## 三、原书 → 2026 对位

| 书内论点 (2016) | 2026 现状 |
|---|---|
| 客户端-服务器/浏览器-服务器拓扑 | 云托管+无服务器 DB、读写分离、向量检索前端成为新课件 |
| 开源=MySQL/PostgreSQL | +SQLite(3.45+)/DuckDB(1.5+)/LibSQL 等嵌入式与分析分支 |
| 瀑布生命周期 | 敏捷/数据网格时代需求持续演进，但「所有权确权」议题原样成立 |
| 纸质 CASE 报告 | 需求工程工具链（Jira/Confluence 类）承接 ⚠️ 通说 |

### 2.6 硬件架构小节的 2026 反题：弹性成为默认前提
Ch1 的 Database Hardware Architecture（✅ 节题）讲单机→客户-服务器→三层拓扑（展开 ⚠️ 推定）。2026 云原生把「拓扑设计」问题本身清算了：存算各自伸缩、副本与分区是配置项而非架构决定，容量从「设计量」变成「订购量」。教材不变量仍在：**读写画像决定数据布局，数据布局决定架构选项**——Ch1 时代这条链靠画拓扑图兑现，今天靠选型清单（对象存储/表格式/托管引擎）兑现。Data "Ownership"（✅ 节）在云上多了新维度：数据在谁的桶里、谁能读、退出时怎么搬走——所有权从组织内政治升级为合同条款（评注 ⚠️）。

### 2.7 Ch2 是全书最「人」的一章
Ch2 的官方小节（✅）：Dealing with Resistance to Change / The Structured Design Life Cycle / Conducting the Needs Assessment / Assessing Feasibility / Generating Alternatives / Evaluating and Choosing an Alternative / Creating Design Requirements / Alternative Analysis Methods——前四节与后四节是两种文体：前者讲人，后者讲方法。2026 产品流程逐节对位（综合 ⚠️）：resistance→变更管理与发起方经营；needs assessment→discovery 访谈与用例梳理；feasibility→技术/成本/时间三角评审；alternatives→build/buy/SaaS/open-source 决策矩阵；design requirements→PRD 与验收标准。The Structured Design Life Cycle 一节整体是瀑布时代骨架（⚠️），但其产物清单（需求→可行→备选→选择→规格）在迭代制里一步未减——**流程换代，因果链不换**。

### 2.8 Open Source Relational DBMSs 节的 2016 名单与 2026 版图（⚠️ 综合）
小节题 ✅；正文 2016 年视角的开源名单（MySQL/MariaDB/PostgreSQL 阵营 ⚠️ 通说推定）。2026 复核的关键位移：PostgreSQL 成为事实上的开源默认与方言供体；MySQL 系在云厂商托管化中稀释；**DuckDB 类嵌入式引擎是 Ch1「Other Factors」小节完全没预见的物种**——本书 🔧 实验栈本身就是一条 2026 注脚：教材的「DBMS 形态=服务器进程」前提已经分化出「库形态引擎」（in-process）。读者应以本小节为基准线，观察此后十年开源数据库权力地图的重画。

## 最新演进与工业实践
- SQLite 官方文档持续是「嵌入式 DBMS 五职能」的最干净活教材：视图与 WAL 两页已验 200：https://www.sqlite.org/lang_createview.html 、https://www.sqlite.org/wal.html ✅（URL 实查 2026-10-02）。
- 2026 教学环境默认件：SQLite（python 内置 3.45.3）+DuckDB（1.5.5）即可完成本书全部 DDL/DML 教学点（本目录 🔧 六组即证），无需装机 DBMS——「DBMS 环境」章节的课堂形态已变。
- 需求侧工业化演进：数据契约（data contract）、schema registry 把 Ch2 的「设计需求」变成版本化机读件；数据网格把「所有权」升级为域所有权（盘上 ../Data_Mesh/00-总览与阅读地图.md 有工程级展开 ✅在盘）。
- 云托管对 Ch1 拓扑节的替代：单机→存算分离成为主流叙事 ⚠️（本波云仓册各 00 有对位表，波内兄弟 #161/#164/#179 等只登记不链）。
- 2026 需求工程工具（Jira/Confluence 类）是 Ch2 生命周期的电子化；「替代方案分析」变成架构决策记录 ADR（⚠️ 通说）。
- Feasibility 三角在云时代重新定价：技术风险下降，按量计费的成本模型成为新主战场（⚠️）。
- Ch1 开源小节的 2026 续集：PostgreSQL 事实标准+DuckDB 嵌入式新品类——本波 🔧 栈即教材名单外的物种（§2.8）。
- 所有权节的合规复活：GDPR/个保法把「谁拥有」改问「谁负责」——责任比所有权可执行（⚠️ 综合）。
- 「反改变阻力」的产品语言=champion 用户与内部营销；方法不变，载体换代（⚠️）。
- 本章与 02 的接缝：Ch1/2 定「为谁建」，Ch3 定「建坏会怎样」——需求→痛点教学桥。
- Ch2 输出直接喂 Ch12 CASE 工具（09）；2026 等价管道=PRD→schema 评审→迁移 PR（⚠️）。
