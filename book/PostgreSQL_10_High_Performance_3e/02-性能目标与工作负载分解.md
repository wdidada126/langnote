# 02 性能目标与工作负载分解

> 章题 ⚠️ 推定（书系 1e/2e 第 2 章惯例 "PostgreSQL Performance Goals and How to Achieve Them"；
> 官方 README ✅ 实抓内容简介与本章主题域对位）。内容为主题级精读重构，非原书文本。

## 本章主轴：先分解，后调优

README（✅）给出的全书骨架："选对硬件 → 调 OS 与服务器内存 → 用对的索引优化查询 → 从硬件到查询
逐层监控；到顶后用连接池/缓存/分区/复制/并行扩展"。这段话展开就是本章的方法论：
**任何参数值都是"工作负载画像"的函数，不存在脱离画像的黄金配置**。

## 工作负载分解四步（书中框架的复原，⚠️ 推定级）

1. **读写比与事务画像**：OLTP（短事务、随机小 IO）/ 分析（顺序大扫描）/ 混合（最危险）。
   PG 的进程模型、vacuum 压力、缓冲池策略三件事全部由这个比例决定 ⚠️ 转述社区共识。
2. **体量画像**：热数据集是否进得了 `shared_buffers`、是否进得了 OS page cache、
   是否进得了内存——三档决定瓶颈在 IO 还是 CPU 还是锁 ⚠️。
3. **并发画像**：连接数/活跃事务数曲线；PG 每连接一进程，连接风暴的代价比线程模型引擎更贵 ⚠️，
   这是连接池（pgbouncer 等）在 PG 生态地位高于其他引擎的原因 ⚠️ 社区共识。
4. **时间画像**：峰谷、批量窗口、维护窗口——决定 vacuum/备份/分析任务的排程空间（联动 07/12 章）。

🔧 类比实验 X-A（sqlite3 3.45.3，Windows，Py3.13；**非 PG 行为**）：
20 万行插入用时 ~0.18s（约 1.1M 行/s，单写事务批量提交），而同一文件上 50 次范围扫描
`SELECT count(*) FROM t WHERE v>100` 用时 ~0.60s——写与读的"单位成本"完全不在一个量纲。
数据文件 `D:\develops\tmp\dbwave_w3_pgperf\wl.db`（10.6MB）。方法：`exps.py` 段落 A。
这一步在任何引擎上都成立：**先把"读秒/写率"两个数字分开量出来，再谈参数**。

## 目标的工程化表述

- 用 SLO 而非"越快越好"：延迟分位数（P50/P95/P99）+ 吞吐上限 + 恢复目标（RPO/RTO）。
  PG10 时代（2018）社区话术还是 "response time goal"，2026 视角已全面 SLO 化 ⚠️ 转述。
- 每个目标必须绑定一个**可测的代理指标**：如 P99 延迟 ↔ pg_stat_statements 的 mean_time、
  膨胀目标 ↔ 表死元组比（联动 07/09/11 章）⚠️ 转述。
- 目标分层：硬件层（IOPS/带宽）、引擎层（tuples fetched/ms）、应用层（业务事务/秒）。
  跨层归因是调优失败的第一大根因——本册 11 章的等待事件视角由此引出 ⚠️。

## 常见反模式（⚠️ 转述社区共识）

1. 抄论坛参数表而不看自己的读写比——shared_buffers 玄学之争全部源于此。
2. 用峰值并发做容量规划，忽略 PG 每连接进程模式的内存放大（work_mem 是"每排序节点"预算！05/06 章）。
3. 只量平均延迟：P99 被 vacuum wraparound 急停、checkpoint 风暴等偶发事件支配（07/11 章）。
4. 把基准环境当生产：缓存冷热、数据倾斜、Schema 复杂度三大失真（03 章）。

## 细案：一页纸画像模板（⚠️ 教材性，可直接抄用）

```
系统名：____   日期：____   采集窗：____（起止与时区）
读写比：写 __% / 读 __%（按事务数与字节数各算一栏）
事务画像：平均语句数 __；平均持锁时长 __ms；长事务(>1min) 数 __
体量：总量 __GB；日增 __GB；热集估计 __GB（对照 shared_buffers+page cache 两档）
并发：峰值活跃连接 __ / 总连接 __；连接池有无与模式
时间：峰谷比 __:1；批量/维护窗口 周__日 __:__–__:__
目标：P99 __ms；TPS 下限 __；RPO __min；RTO __min
本次假设：瓶颈在 ____（CPU/IO/锁/膨胀/计划），预期证据：____
```

使用规则：
- "本次假设"一行禁止留空——没有可证伪假设就不许动参数（测量-假设-实验循环的最小执行体，
  通史论证见 [../Database_Tuning/00-总览与阅读地图.md](../Database_Tuning/00-总览与阅读地图.md)）；
- 画像每月重做：读写比与热集会随业务漂移，PG10 时代多起"参数没改怎么变慢了"事故的通解；
- 该模板与 pg_stat 快照（11 章）绑定使用：数字从视图来，判断在模板上做。

## 章内自测（五问五答）

- **问：为什么 PG 对连接数比对查询数更敏感？**
  答：每连接一进程，内存与调度成本随连接线性放大，池化前先问画像（06/11 章呼应）。
- **问：work_mem 在并发账里怎么乘？**
  答：并发活跃查询数 × 每查询排序/哈希节点数 ×（并行时再 ×workers）——"每节点"语义常被漏乘（05 章）。
- **问：P99 由什么支配？**
  答：偶发事件（检查点风暴、freeze 急停、长 vacuum），均值调优对其无效（07/11 章）。
- **问：何时拒绝调优？**
  答：五条架构路（池化/缓存/分区/复制/并行）任一条明显未用时——参数救不了方向错误。
- **问：🔧 X-A 的 1.1M 行/s 能写进容量报告吗？**
  答：不能——它是 SQLite 单机无 WAL-fsync 语义的方向性标本，只可用作"读写量纲分离"的教学数字。

## 核心概念速览（中英对照）

- **工作负载分解** — Workload Decomposition：把负载拆成读/写/并发/时间四维画像再调优的方法。
- **SLO** — Service Level Objective：以分位数延迟+吞吐定义的服务级目标。
- **代理指标** — Proxy Metric：能在引擎侧观测、与业务目标强相关的量。
- **热数据集** — Working Set：高频访问数据子集，决定内存/IO 层瓶颈归属。
- **进程模型开销** — Process-per-Connection Cost：PG 每连接一进程带来的内存与调度成本。
- **连接风暴** — Connection Storm：瞬时大量新连接拖垮 postmaster 的现象。
- **work_mem** — Per-node Sort Memory：每个排序/哈希节点每 worker 的内存预算（乘法放大）。
- **维护窗口** — Maintenance Window：可安全执行 vacuum/备份/升级的谷值时段。
- **跨层归因** — Cross-layer Attribution：在硬件/引擎/应用三层间定位瓶颈的能力。
- **缓存分层** — Caching Layer：以应用/中间件缓存吸收读放大。
- **读写分流** — Read Scaling：用复制/物化把分析读移出主库。
- **峰谷画像** — Temporal Profile：负载随时间分布，决定任务排程的余量。
- **黄金参数谬误** — Golden Config Fallacy：无视画像直接抄参数值的反模式。

## 最新演进与工业实践

- **SLO 驱动已制度化**：2024–2026 托管 PG（各云）普遍内置 P99 仪表盘与自动告警；
  论文线可追 Database Reliability 谱系（盘上 [../Database_Reliability_Engineering/00-总览与阅读地图.md](../Database_Reliability_Engineering/00-总览与阅读地图.md) ✅ 在盘互链）。
- **可观测性栈标准化**：Prometheus + postgres_exporter 采集 pg_stat_* 全家桶成为事实标准 ⚠️ 转述；
  官方统计视图语义权威页 ✅ https://www.postgresql.org/docs/10/monitoring-stats.html （curl 200）。
- **连接治理产品化**：PgBouncer/PgCat 类池化器与"无服务器 PG"（Neon 类）把连接成本问题
  直接虚拟化掉 ⚠️ 转述；2026 视角下本章"五条路"的池化一路已前移到平台层。
- **基准方法学文献**：OLTP 基准的代际讨论可读 Overview of TPC Benchmark E（DBTest 2008,
  DOI: 10.1007/978-3-642-10424-4_7 ✅ Crossref 200）；TPC-C 之后的 OLTP 画像更碎片化是共识 ⚠️。
- **工业教训**：多租户与 serverless 场景下"按峰值容量规划"进一步被"按预算弹性"取代 ⚠️ 转述；
  但"先分解再调优"的顺序从未被推翻——这正是本册 2018 年框架的长寿之处。
