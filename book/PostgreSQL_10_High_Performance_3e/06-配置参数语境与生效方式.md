# 06 配置参数语境与生效方式

> 章题 ⚠️ 推定；主题域 ✅ 实证：官方代码仓 `Chapter06/6_1.sql` 全文即
> `SELECT distinct context FROM pg_settings`（backend/internal/postmaster/sighup/superuser/
> superuser-backend/user 六类），并逐参数列 name→context 对照（archive_command→sighup、
> archive_mode→postmaster、block_size→internal）。本章以这六类语境为骨架展开。非原书文本。

## 一、六种 context 的运维含义（6_1.sql ✅ 原文枚举）

| context | 生效方式 | 运维含义 |
| --- | --- | --- |
| internal | 不可改（编译期/初始化） | 如 block_size，容量规划的物理常数（联动 04 章）|
| postmaster | 重启整个集群 | 大改窗口规划的核心约束（shared_buffers 在此类）|
| sighup | `pg_ctl reload` / SELECT pg_reload_conf() | 多数运行时参数：分钟级变更 |
| superuser | reload 即可但仅限超管设置 | 权限维度的"敏感参数" |
| superuser-backend | 新连接生效，仅超管 | 角色级模板参数的常态 |
| backend / user | 新连接/会话内即生效 | search_path、work_mem 类细粒度治理入口 |

🔧 类比说明：语境分层思想在任何可配置引擎通用——DuckDB 的 `SET threads=8`（会话级）与
SQLite 的 `PRAGMA journal_mode`（库持久级/连接级混杂）是"同一谱系的粗糙版"（🔧 exps.py 段 D/E
即分别用会话级 SET 与库级 PRAGMA 完成；语义与 PG 不同，仅作分层概念类比，非 PG 行为）。

## 二、配置的分层覆盖模型（⚠️ 转述官方语义）

postgresql.conf → postgresql.auto.conf（ALTER SYSTEM 写入）→ 命令行 → per-database →
per-role → per-role-in-database（ALTER ROLE ... IN DATABASE ... SET）。
同一参数在不同层出现时**最后命中者胜**；`pg_settings.source/sourcefile` 字段是唯一的现场真相 ⚠️。
书系立场复原：调优事故的一半来自"改了没生效/生效了不知道在哪层改的"，
故 6_1.sql 式的 context 审计应先于任何参数变更 ⚠️ 框架性。

## 三、WAL 与检查点参数在此章的定位（⚠️ 转述）

6_1.sql 中 archive_command/archive_mode 均为 sighup——归档/复制类参数"改了即换轨"，
但其**性能税**（WAL 量、fsync 行为）在 04/07/13 章分别展开。PG10 的关键变化：
recovery 配置并入主配置体系（standby.signal 类文件机制是该变化的后代 ⚠️ 精确表述未逐字核验）；
`max_wal_size/min_wal_size` 取代 checkpoints_* 成为检查点节流的主旋钮 ⚠️ 转述（两者关系：
checkpoints_completion_target 控制铺开斜率，max_wal_size 控制触发水位）。
权威锚点：✅ https://www.postgresql.org/docs/10/runtime-config-resource.html 与
✅ https://www.postgresql.org/docs/10/runtime-config-replication.html （均 curl 200）。

🔧 类比实验 X-E（sqlite3 WAL 模式，**非 PG**）：8 万行提交后 `-wal` 文件涨到 17.4MB；
`PRAGMA wal_checkpoint(TRUNCATE)` 后归零（0.00MB）。这演示了"日志随事务增长、检查点/回收决定
回落时机"的通用形态；但注意 SQLite 的 checkpoint 是**回写主库文件**，PG 的检查点是
**把脏页刷下、令 WAL 可截断**——方向同为"限制日志体量"，机制不可类比过深。
（exps.py 段 E；waldb.db-wal。）

## 四、参数变更的工程纪律（⚠️ 教材性复原）

1. 变更前抓 `pg_settings` 快照（name/setting/source/context 四列）；
2. 一次只动一组因果相关的参数（见 05 章四本账），并登记预期指标变化；
3. reload 后 `pg_reload_conf()` 返回值 + `pg_stat_activity` 确认已连接会话是否吃到新值
   （backend 类只影响新连接！）；
4. 可回滚路径：保留两份 conf 与 ALTER SYSTEM 清单（PG10 尚无 `RESET ALL` 级别的自动快照 ⚠️）。

## 五、反模式清单

- 把 `work_mem` 设为 postmaster 大值"一刀切"（应 user/backend 级精细化，05 章乘法账）；
- 用 ALTER SYSTEM 覆盖却不记录，sourcefile 显示 postgresql.auto.conf 时全组懵圈；
- 在 sighup 参数上做重启窗口审批（浪费）；在 postmaster 参数上只 reload（无效）——
  context 审计（6_1.sql 的动机）就是把这两类错误各归其位；
- 无单位习惯：conf 里裸写数字，wal_buffers 的 8×8kB 陷阱（5_1.sql）即前车之鉴 ✅。

## 细案：变更窗口决策树（⚠️ 教材性复原；语境数据 ✅ 实抓自书仓 6_1.sql）

```
要改的参数 X
├─ 查 pg_settings.context（6_1.sql 手法）
│  ├─ internal   → 改不了：这是编译期/初始化常数（如 block_size），
│  │               想动=新集群+逻辑迁移（14 章路线）
│  ├─ postmaster → 排重启窗口：shared_buffers 在此；
│  │               窗口成本 vs 收益 → 用 02 章画像定价
│  ├─ sighup     → reload 即生效：多数运行时参数；
│  │               变更后 SELECT pg_reload_conf() + 抽查 pg_settings.source
│  ├─ superuser* → 先权限审计：谁能改，改错半径多大
│  └─ backend/user → 会话级灰度：ALTER ROLE ... SET 做金丝雀，
│                   新连接才吃新值（老连接维持旧值——回滚也要按此语义设计）
└─ 无论哪档：抓 before/after 两份 pg_settings 快照入档
```

常见误档三例（⚠️ 社区事故通稿的抽象化）：
1. 把 work_mem 当 postmaster 参数去申请重启（其实 user 级，秒级可灰度）；
2. 把 max_connections 当 sighup（实为 postmaster，重启档！连接风暴时才发现要重启窗口）；
3. ALTER SYSTEM 后以为"进版本库了"——postgresql.auto.conf 常年无人 review（06 章反模式第 2 条）。

## 章内自测（三问三答）

- **问：reload 成功但指标没变，第一查什么？**
  答：该参数 context——backend/user 类只影响新连接，老池化连接不吃新值。
- **问：检查点太频繁，先动哪个旋钮？**
  答：max_wal_size（水位）与 checkpoint_completion_target（斜率）成对审，
    且先看 11 章 checkpoints_req/timed 比再定性。
- **问：🔧 X-E 的 WAL 归零和 PG 的 checkpoint 是一回事吗？**
  答：方向同（限制日志体量）、机制异（SQLite 回写主文件；PG 刷脏页以放行 WAL 截断）——边界声明在此重申。

## 核心概念速览（中英对照）

- **context** — 参数语境：pg_settings 中标记生效方式/权限的字段（六类）。
- **reload** — 配置重载：SIGHUP 驱动的在线参数刷新。
- **postgresql.auto.conf** — ALTER SYSTEM 落点：主 conf 之后的自动覆盖层。
- **分层覆盖** — Configuration Layering：全局→库→角色→会话的命中链。
- **source/sourcefile** — 生效来源：pg_settings 中定位参数最终定义处的手续字段。
- **max_wal_size** — WAL 体量上限：检查点节流的水位主旋钮（PG9.5+）。
- **checkpoint_completion_target** — 检查点斜率：把 IO 摊开的铺开系数。
- **archive_mode/archive_command** — 归档双参：WAL 段级归档的开关与命令。
- **ALTER ROLE ... IN DATABASE ... SET** — 最细层：角色×库粒度的参数模板。
- **快照审计** — Settings Snapshot：变更前全量抓 pg_settings 的纪律。
- **fsync/synchronous_commit** — 耐久双旋钮：分层语境不同（postmaster/sighup-user）⚠️ 转述。
- **block_size** — internal 代表：编译期常数，不可调（6_1.sql 样本）。

## 最新演进与工业实践

- **参数即代码**：2024–2026 云原生操作子（CloudNativePG、PgBouncer 配套 CRD 等）把
  postgresql 参数纳入声明式管理，context 语义映射为 rolling restart vs reload 两类编排动作 ⚠️ 转述；
  书里的手续在平台层重演。
- **可观测的参数治理**：pg_settings 快照 diff 工具化（各导出器/Grafana 面板）⚠️；
  权威文档现行页 ✅ https://www.postgresql.org/docs/17/runtime-config-resource.html （curl 200）。
- **recovery 配置合并的后日谈**：PG12 起 standby.signal/recovery.signal 定型，PG10 的过渡形态
  在升级检查单里仍是重灾区 ⚠️ 转述；pg_upgrade 手册（✅ https://www.postgresql.org/docs/16/pgupgrade.html ）
  是 2026 视角处理该遗产的标准路径。
- **WAL 预算制**：现代版本对 WAL 体积/速率的监控视图与自动节流增强 ⚠️ 转述；X-E 类比出的
  "日志体量-回收节奏"模型在逻辑复制槽场景（14 章）会以"槽滞留→WAL 暴涨"的新事故形态复现。
