# 05 内存与缓冲区配置

> 章题 ⚠️ 推定；主题域 ✅ 实证：官方代码仓 `Chapter05/5_1.sql` 演示 postgresql.conf 内存单位
> （`SHOW wal_buffers` → 64kB 与 `pg_settings` 中 setting=8 × unit=8kB 的换装关系），
> `5_7.sql` 用 **pg_buffercache** 统计"每张大表当前占了多少个共享缓冲页"的分布查询
> （pg_class ⋈ pg_buffercache ⋈ pg_database GROUP BY relname ORDER BY count DESC）。
> 这两段代码定义了本章的骨架：**单位语义 → 预算分配 → 用缓冲占用真相反推配置**。非原书文本。

## 一、内存参数的"单位陷阱"（5_1.sql ✅ 现场）

PG 配置值 = `setting × unit`，而 `postgresql.conf` 里写的是带单位的字符串：
`wal_buffers = -1`（自动，约 224 个 WAL 段页的 1/32 ⚠️ 转述官方口径）显示为 `64kB` 的机制
正是 5_1.sql 展示的两条通道：`SHOW wal_buffers` 给人看，`pg_settings.setting/unit` 给脚本看。
调优纪律：**任何内存数字先问三件事——谁的内存、什么粒度、是否乘并发** ⚠️ 教材性。

## 二、四本内存账（⚠️ 框架复原）

| 账本 | 参数 | 归属 | 陷阱 |
| --- | --- | --- | --- |
| 全局池 | shared_buffers | 所有后端共享的缓冲池 | 调过大挤掉 OS page cache（WAL/临时文件在其外）|
| 每操作 | work_mem | 每排序/哈希节点每 worker | 乘法放大：并发×节点数 |
| WAL | wal_buffers | 提交批写缓冲 | 一般自动即可，超大事务才需干预 ⚠️ |
| OS 层 | page cache / huge pages | 隐式第二级缓存 | 换页(swap)是 PG 延迟的头号杀手 |

- shared_buffers=25% 的"惯例"来自 2010 年第 1 版语境，2018 年书里已是"起点而非答案"⚠️ 转述；
  真相由 5_7.sql 类查询给出：**热表在 pg_buffercache 里的实际驻留分布**决定你该不该加大池子。
- `effective_cache_size` 纯规划器假设值，不是分配值——它应约等于"shared_buffers + 可用 page cache"
  中查询可利用的部分 ⚠️ 转述（详见 09/10 章成本模型）。
- huge_pages（`on/try/off`）配合 OS 侧配置缓解 TLB 压力；容器/共享机环境常用 `try` ⚠️ 社区共识。

🔧 类比实验 X-C（sqlite3 3.45.3，**非 PG**）：10 万行含 200 字节填充的表 = 21.6MB 文件；
DELETE 60% 后文件仍 21.6MB，`VACUUM` 0.10s 后回落到 8.7MB。说明"空间驻留与重组"在任何
页式存储里都存在，但 PG 的对应物是**共享缓冲池里的死元组 + 表空间膨胀**双层面，
SQLite 只演示了后者。数据与代码：`D:\develops\tmp\dbwave_w3_pgperf\bloated.db` / exps.py 段 C。
本章用它校准直觉：**"删了"不等于"空了"**——缓冲池视角（07 章）与磁盘视角要分开审计。

## 三、pg_buffercache 工作流（5_7.sql ✅ 展开）

1. `CREATE EXTENSION pg_buffercache;`
2. 跑缓冲占用 Top-N 查询（书仓 5_7.sql 原文形态）；
3. 判读三态：热表驻留高 → 池子够用；大表驻留低且 blks_read 高 → 加池子或改查询；
   驻留高但 seq_scan 也高 → 是索引缺失不是内存缺失（移交 09 章）。
   ——步骤 3 的判读树 ⚠️ 推定重构，两步骤的 SQL 形态 ✅ 实抓自代码仓。

## 四、每查询内存的治理

- `log_temp_files ≥0` 抓盘上溢出的排序/哈希（⚠️ 转述参数语义）：temp file 数量是 work_mem
  预算失配的直接证据；
- PG10 无每查询内存硬上限（后续版本的内存上下文观测增强 ⚠️ 转述），治理靠"并发×预算"审计；
- 与 07 章的联动：per-query 工作内存与共享池无关，但**并行 worker 会按份复制 work_mem**，
  这是 PG10 并行调优里最常见的内存超支来源 ⚠️ 转述。

## 五、共享内存的边界与 OS 内核参数

- `SHMMAX/SHMALL/shmall` 等 SysV 限制决定 shared_buffers 能否开大（Linux 上现代发行版多为
  hugepages/透明大页语境下的新故事 ⚠️ 转述）；
- 容器化 PG 的内存 limit 与 shared_buffers 的互动坑（OOMKiller）在 2018 刚出现、2026 已成常识 ⚠️；
- 官方权威参数页：✅ https://www.postgresql.org/docs/10/runtime-config-resource.html （curl 200）；
  pg_buffercache 函数表 ✅ https://www.postgresql.org/docs/10/pgbuffercache.html 。

## 细案：内存审计的标准作业序列（⚠️ 教材性复原 + ✅ SQL 形态实抓自书仓 5_7.sql）

```sql
-- 步骤1：单位与来源审计（5_1.sql 手法）
SELECT name, setting, unit, source, context
FROM pg_settings
WHERE name IN ('shared_buffers','work_mem','maintenance_work_mem',
               'effective_cache_size','wal_buffers','huge_pages');
-- 步骤2：缓冲池真话（5_7.sql 骨架，需 CREATE EXTENSION pg_buffercache）
SELECT c.relname, count(*) AS buffers,
       pg_size_pretty(count(*) * 8192) AS resident
FROM pg_class c JOIN pg_buffercache b ON b.relfilenode = c.relfilenode
GROUP BY c.relname ORDER BY buffers DESC LIMIT 15;
-- 步骤3：溢出取证
SELECT datname, temp_files, temp_bytes FROM pg_stat_database;
```

判读三棱镜（🔧 X-C 的"删了≠空了"意象在此的第二用途）：
- 步骤 2 的 Top-N 与 02 章热集估计对表：驻留 << 估计 → 池子不足或查询模式变了；
- 步骤 3 非零即回查 work_mem 账（乘法清单见 02 章自测第 2 问）；
- 三步骤数字必须同一时窗（03 章对齐纪律），跨窗结论一律 ⚠️ 降级。

## 章内自测（四问四答）

- **问：shared_buffers 越大越好错在哪？**
  答：挤出 OS page cache 后，WAL/临时文件/直接 IO 路径反受其害；池子只是四本账之一。
- **问：wal_buffers 显示 64kB，conf 里 -1，谁在说谎？**
  答：都没有——-1 是自动档，64kB 是 setting×unit 的换算结果（5_1.sql ✅ 现场）。
- **问：huge_pages=off 在容器里为什么常是对的？**
  答：宿主大页池与 cgroup 记账的互动复杂，`try`/`off` 换取可移植性 ⚠️ 社区共识。
- **问：effective_cache_size 调大会发生什么？**
  答：只改计划器假设（更多 index scan 偏好），不分配任何内存——名字是历史误会。

## 核心概念速览（中英对照）

- **shared_buffers** — 共享缓冲池：PG 自管的页缓存，默认远小于 InnoDB 惯例占比。
- **work_mem** — 操作节点内存：每排序/哈希节点每 worker 的预算，乘法放大。
- **wal_buffers** — WAL 缓冲：提交前攒 WAL 的小环形缓冲，单位换算经典案例（5_1.sql）。
- **effective_cache_size** — 规划器缓存假设：纯成本模型输入，非分配值。
- **pg_buffercache** — 缓冲池内窥镜：逐页展示共享缓冲当前驻留对象的扩展（5_7.sql）。
- **页驻留率** — Buffer Residence：热表在池中的页占比，调池依据。
- **临时文件** — Temp Files：排序/哈希溢出到磁盘的产物，work_mem 失配证据。
- **大页** — Huge Pages：降 TLB 压力的 OS 页策略（huge_pages 参数）。
- **透明大页** — THP：Linux 自动大页，数据库负载下常建议关闭 ⚠️ 社区共识。
- **SHMMAX** — SysV 共享内存上限：OS 内核参数对 shared_buffers 的硬边界。
- **OOMKiller** — 内存过杀：容器/主机内存耗尽时内核杀进程，PG 经典事故源。
- **setting×unit** — 两通道读法：pg_settings 数值与展示字符串的换算关系。

## 最新演进与工业实践

- **参数权威文档**：现行 runtime 配置总览 ✅ https://www.postgresql.org/docs/17/runtime-config-resource.html
  （curl 200）；共享池、work_mem、huge_pages 的语义主线十年未变，变的是默认值与观测面。
- **观测面扩张**：PG 17 的 `pg_buffercache_summary()`、内存上下文统计视图（PG16 前后逐步落地 ⚠️ 转述）
  把 5_7.sql 手join变成一行函数；2026 实践中仍常见书里这段 SQL 的衍生脚本在跑 ⚠️。
- **容器化调优共识**：云原生 PG（含 CloudNativePG、Percona 等发行）普遍把 shared_buffers 按
  cgroup limit 比例模板化，且默认关 THP、谨慎 huge_pages ⚠️ 转述生态现状。
- **自动内存管理未上车**：与 Oracle ASMM/AMM 对照，PG 至今坚持"预算制 + 外置治理"，
  本册的"四本账"心智模型仍是 2026 年 DBA 面试标准答案 ⚠️ 评价性。
- **工业数据点**：各大云托管 PG 的 sizing 文档把"page cache 命中率 + temp file 率"并列为
  一级指标——即 5_7.sql 与 log_temp_files 的现代化身 ⚠️ 转述。
