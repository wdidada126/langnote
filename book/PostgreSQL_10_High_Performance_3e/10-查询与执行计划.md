# 10 查询与执行计划

> 章题 ⚠️ 推定（书系惯例 "Querying"）；主题域 ✅ 实证：官方代码仓 `Chapter10/10_3.sql` 为
> `EXPLAIN ANALYZE SELECT * FROM products,customers;`（dvdrentals 系示例库上的笛卡尔积演示），
> `10.1.sql` 用 `pg_size_pretty(pg_relation_size('customers')/7.994*1000)` 做体量-速率换算；
> README ✅ 实抓的"代码形态示例"即嵌套循环伪码（for each outer row / for each inner row）。
> 本章以"连接算法选择 + EXPLAIN 解读"为轴。非原书文本。

## 一、三种连接与它们的物理账单（README 伪码 ✅ 引子）

| 算法 | 内存/IO 画像 | 何时是答案 | 何时是事故 |
| --- | --- | --- | --- |
| Nested Loop | 内侧重复扫描，靠索引撑 | 小外层×高选择率内层 | 行数误估时灾难（09 章统计伏笔回收）|
| Hash Join | work_mem 哈希+溢出分桶 | 等值大表互连 | work_mem 不足→多轮批（temp 文件暴涨，05 章）|
| Merge Join | 双边有序/排序 | 已有序或范围连接 | 排序成本失控时回退 NL |

`SELECT * FROM products,customers`（10_3.sql ✅）是教科书式负例：无连接谓词的笛卡尔积
必然 NL+全扫，EXPLAIN 上 rows 估计乘爆——用它对照真实查询里"缺 WHERE 谓词/谓词不可索引"的形状。

## 二、EXPLAIN 的读法纪律（⚠️ 教材性 + 官方文档语义转述）

1. `EXPLAIN ANALYZE` 看事实，`EXPLAIN` 看计划形状；PG18 语境里还有 `EXPLAIN (ANALYZE, MEMORY)`
   类演进 ⚠️ 注记，本册 2018 版式参数为准；
2. 从最内层节点向上读"估计行 vs 实际行"，误估 >10× 即立案（关联 09 章扩展统计）；
3. `actual time` 是**每行均摊累计**（含子节点），行总耗时 = ×loops；新手把节点 time 当总时长
   是第一大误读 ⚠️ 转述 using-explain 文档口径；
4. Buffers: shared hit/read 行把 IO 归因到缓存层（联动 05 章 pg_buffercache、09 章效益视图）；
5. 并行计划：Gather 之上的 workers 数与其下每 worker 的 work_mem 账（05/09 章）⚠️。

## 三、SET 语义、子查询与改写杠杆（⚠️ 社区共识）

- ANY→IN→EXISTS 的选择在 PG 优化器面前多数已等价（拉平/上提能力 ⚠️），
  但**关联子查询物化失败**仍是 2018 高频坏计划形态；
- `enable_*` 系列参数（enable_nestloop 等）只作诊断用，禁入生产配置——成本模型缺项时才逼你关算法，
  补统计才是正解 ⚠️；
- CTE 物化屏障：PG12 前 `WITH` 默认物化（优化不穿透），本册 PG10 语境下"CTE 当优化单元"
  多是负收益 ⚠️ 版本注记；
- 批量侧：多行 `INSERT ... VALUES` 打包、`COPY` 优先、`INSERT...SELECT` 配并行——装载通道选择
  决定 03 章 X-A 类"装载速率"指标（🔧 X-A 的 20 万行 executemany 批提交 ~0.18s≈1.1M 行/s 即
  "打包 vs 逐条"量纲差的最小演示，**非 PG** 行为）。

## 四、并行查询在本章的位置（PG10 语义，⚠️ 转述）

9.6 并行扫表 → 10 补并行索引构建/更多节点 → 11+ 并行 UNION/聚合深化。
规划器以 `min_parallel_table_scan_size` + 成本阈值决定 workers 数；小查询并行反而慢
（启动 worker 的进程级成本 🔧 呼应 X-D：负载噪声机上 8 线程比 1 线程还慢 1.09s→2.64s 的教训，
**并行度是预算不是信仰**，非 PG 演示）。

## 五、查询层面的容量治理

- 慢查询日志：`log_min_duration_statement` + 与 pg_stat_statements 双轨（视图字段 ✅ monitoring-stats 页）；
- 语句级资源治理在 PG10 仅有粗手段（statement_timeout、优先级靠连接数），
  cgroup 化才是当代正解 ⚠️ 演进注记；
- "到顶五路"（README ✅）中的 caching/parallel 两路在本章交汇：并行是纵向换时，缓存是横向换量。

## 细案：一次坏计划归因的完整走查（✅ 以书仓 10_3.sql 现场为标本）

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM products, customers;
-- 典型形态：Nested Loop -> Seq Scan products(cost=..rows=100)
--                      -> Seq Scan customers(cost=..rows=10000)
```

走查七步：
1. **形状定性**：笛卡尔积无谓词——先问 SQL 是不是写漏了连接条件（10_3.sql 是刻意负例 ✅）；
2. **估计审计**：每个 Seq Scan 的 rows 估算 vs actual 行倍数；>10× 进统计支线（09 章）；
3. **缓冲归因**：Buffers shared read 占大头 → 热集超池（05 章）；hit 高仍慢 → CPU/算法选择问题；
4. **内存痕迹**：Hash Join 节点出现 "Batches: N>1" → work_mem 溢出（05 章乘法账）；
5. **并行审视**：Gather 下 workers=0 → 阈值/预算未达（01 章），勿盲目调小 parallel 阈值（🔧 X-D 教训）；
6. **改写试验**：补谓词/改 JOIN 显式化后重跑，禁 enable_* 硬掰（09 章反模式同源）；
7. **固化**：修好的样本进回归集，auto_explain 抓同形新罪（11 章）。

装载侧同法（三态标注示范）：dellstore 万行级 `COPY orders.csv` 与逐行 INSERT 的时长差，
方向与 🔧 X-A（SQLite executemany 批提交 ~1.1M 行/s vs 逐条量纲）一致；
**PG 的具体倍数 ⚠️ 本目录未实测（PG 不装不跑），引官方 COPY 语义为方向依据**。

## 章内自测（四问四答）

- **问：actual time=0.02..1.30 rows=5000 loops=3 的节点总耗时？**
  答：约 (1.30−0.02)×3——loops 乘回去是最常见读数事故（第 3 节纪律 3）。
- **问：rows 估计 1 实际 100 万，第一反应动什么？**
  答：统计（ANALYZE/CREATE STATISTICS）而非索引——先修地图再怪路线（09 章）。
- **问：CTE 在 PG10 为什么常是优化黑洞？**
  答：默认物化屏障使谓词不穿透；PG12 起才可按需内联 ⚠️ 版本注记。
- **问：并行一定更快吗？**
  答：X-D 现场反例：噪声机上 8 线程慢 70%——并行度是预算与隔离度的函数（03 章契约）。

## EXPLAIN 输出要素速查（术语卡片，⚠️ 转述官方 using-explain 语义）

- **cost=起始..总** — 累计启动/总成本（相对单位，禁跨版本比大小 ⚠️）；
- **rows / width** — 估计行数/平均行宽；与 actual 的倍差是本章走查第 2 步的原料；
- **actual time** — 每行均摊（ms）：启动+总，乘 loops 才是节点总账；
- **loops** — 该节点被外层驱动次数（NL 内侧会 >1）；
- **Buffers**（加 BUFFERS 才显示）— shared hit/read/dirtied/written，IO 归因到块层（05/11 章）；
- **Rows Removed by Filter** — 扫了又丢的量：索引选择错误的直接证词（09 章）；
- **Sort Method: external merge Disk: xxxkB** — work_mem 溢出铁证（05 章 temp 账）；
- **Batches**（Hash Join）— >1 即哈希表分批，同上调 work_mem 候选；
- **Workers Planned/Launched** — 并行预算兑现度（Gather 上读，01 章）。

## 核心概念速览（中英对照）

- **EXPLAIN ANALYZE** — 执行剖析：计划形状+逐节点实测行数/时间/缓冲。
- **嵌套循环连接** — Nested Loop：外层驱动内侧重复访问的连接形态（README 伪码）。
- **哈希连接** — Hash Join：构建+探测两阶段，work_mem 决定溢出。
- **归并连接** — Merge Join：双边有序上的范围友好算法。
- **笛卡尔积** — Cross Join：无谓词连接的事故基准（10_3.sql）。
- **估计/实际比** — Misestimate Ratio：坏计划的第一线索（>10× 立案）。
- **loops 计数** — 节点循环数：actual time 均摊口径的乘数。
- **Gather 节点** — 并行汇合点：worker 结果回收边界的计划器标记。
- **CTE 物化** — CTE Materialization：PG12 前 WITH 的优化屏障（版本注记）。
- **COPY 装载** — 批量通道：比逐条 INSERT 快量级的主批量方式。
- **statement_timeout** — 语句熔断：牺牲可用性保系统的最后防线。
- **pg_stat_statements** — 语句画像：聚合执行统计的扩展（需共享内存预载）。
