# 03 基准测试与统计采集

> 章题 ⚠️ 推定（书系 1e/2e 均有 "Benchmarking and Statistics Collection" 一脉）；
> 章号与主题域 ✅ 实证：官方代码仓 `Chapter03/3_1.sql`（✅ 实抓）内容为
> `\timing` + `SELECT sum(generate_series) FROM generate_series(1,1000000)` + 建表插 10 万行 +
> `EXPLAIN ANALYZE SELECT COUNT(*)`——正是"计时-造数-看计划"的基准三板斧。

## 基准的第一定律：你在量的可能不是你以为的东西

3_1.sql（✅）三段式暗含方法：
1. `\timing` 纯计算（generate_series 求和）→ 估 CPU 地板；
2. 建表 + 10 万行 INSERT（generate_series 批量）→ 估装载速率；
3. `EXPLAIN ANALYZE count(*)` → 校验计划器在真实统计下的行为。
**先测"什么都不做"的成本，再测增量**——这是本章可移植到任何引擎的骨架 ⚠️ 框架性复原。

## pgbench：官方基准的姿态与陷阱

- PG10 的 pgbench 已内置 TPC-B-like 脚本（✅ https://www.postgresql.org/docs/10/pgbench.html ），
  `-n`（vacuum 豁免）、`-c/-j`（客户数/线程数）、`-l`（逐事务日志）是画像三件套 ⚠️ 文档转述。
- 陷阱清单（社区反复验证的口径 ⚠️ 转述）：
  - 默认 scale=1 太小，缓冲池完全命中，测的是内存不是存储；
  - `unlogged table` 装载后再改回logged会留下 WAL 计数错觉；
  - 首次运行的冷缓存曲线要截断（warmup 期不入账）；
  - 统计采集器（pg_stat）自身有开销，对照实验要同一开关状态。
- 书中立场复原 ⚠️：pgbench 不是"给你业务数字"的工具，是"给你引擎极限形状"的工具。

## 统计采集：从 pg_stat 到系统层

- 引擎内：`pg_stat_user_tables`（seq_scan/idx_scan/tup_*）、`pg_statio_*`（块命中）、
  `pg_stat_database`（deadlocks、temp files）✅ 视图族见 monitoring-stats 文档页（curl 200）。
  PG10 尚无 IO Timing 全量视图（PG13+ 强化 ⚠️ 转述），IO 归因更多依赖 `pg_stat_progress_*` 前身
  的缺位经验 + OS 层工具。
- OS 层：`iostat -x` 看设备 util/await、`pidstat` 看后端 CPU、`vmstat 1` 看换入换出与 free；
  PG10 时代监控栈尚未被 Prometheus 一统 ⚠️ 转述。
- 关联规则：引擎数字与 OS 数字必须**同一时钟窗**采集，否则 checkpoint 尖峰会被平均掉（联动 11 章）⚠️。

🔧 类比实验 X-D（DuckDB 1.5.5，**非 PG 行为**）：同一查询
`SELECT sum(range), max(range) FROM range(400000000)`，各跑 3 次取 min：
threads=1 → 1.55s；threads=8 → 2.64s（并行反而更慢）。分组聚合变体：1.55/5.63→5.66s（≈0.99x）。
逐次原始值（threads=1）：1.55/1.87/2.80s——离散度极大。**本机为 24 路代理并行的共享环境**，
这正是"基准第一噪声源是环境而非引擎"的现场教材：没有独占机时，任何并行度结论都不可信。
脚本 `D:\develops\tmp\dbwave_w3_pgperf\exps.py` 段落 D 可复现该现象本身（数字会漂移）。

🔧 类比实验 X-A 补充（sqlite3，非 PG）：写入 ~1.1M 行/s 与读扫描 ~0.6s/50 次的量纲差（见 02 章），
在基准报告里必须分别呈现为"装载速率"与"查询延迟"两栏，混报是新手最常见错误。

## 基准报告的最小完备字段（⚠️ 教材性复原）

事务类型 × 并发档 × 数据集规模 × 冷/热缓存 × 持续时长 × P50/P95/P99 + 吞吐曲线，
缺一项即不可比对；每项附采集时刻与机器代号。

## 何时不要用 pgbench（书中五例的复原，⚠️ 推定）

1. 真实查询含复杂 JOIN/聚合（TPC-B 只有点更新/点查询）；
2. 冷热分层明显的超大库（合成负载无法复现倾斜）；
3. 复制/故障切换路径（要专用故障注入，不是 TPS 曲线）；
4. 升级回归（用生产流量回放/影子库）⚠️ 2018 年已有 pg_test 类工具但非主流；
5. 云实例间对比（邻居噪声未受控）。

## 细案：一次合格基准的 runbook（⚠️ 教材性流程复原）

1. **定环境契约**：机器代号、独占声明、OS/文件系统/参数快照（pg_settings 全量导出，06 章纪律）；
2. **定负载契约**：脚本版本、scale、读写混合比、并发档位表（如 1/8/32/128）；
3. **预热与截断**：固定预热时长，曲线入账起点人工标注；
4. **重复与取统计量**：每档 ≥3 次，报告 min 与离散度（🔧 X-D 的 1.55–2.80s 区间即离散度示范）；
5. **同窗采集**：pg_stat_* 快照差 + iostat 日志对齐时间轴（11 章回读）；
6. **结论三态化**：每条结论标 ✅（本次实测）/ ⚠️（外推）/ 作废（环境不满足契约）；
7. **归档**：原始曲线与 conf 同库存放，报告只作指针。

pgbench 起步命令示意（参数语义 ✅ 锚 https://www.postgresql.org/docs/10/pgbench.html ）：

```bash
pgbench -i -s 150 benchdb            # 装载：scale150≈22GB 量级，压出真实缓存压力
pgbench -c 32 -j 4 -T 300 -r benchdb # 32客户/4线程/5分钟/报每语句延迟
pgbench -n ... benchdb               # 预清场景专用（禁 vacuum 干扰计时）
```

## 章内自测（三问三答）

- **问：为什么 scale=1 的 pgbench 分数几乎无外推价值？**
  答：全内存命中使 IO 子系统不参与，测的是 CPU/锁通路，与生产冷热分布脱节。
- **问：报告里必须出现的两个"非结果"字段？**
  答：环境独占声明与统计窗对齐说明——缺任一，数字不可比。
- **问：🔧 X-D 能证明"DuckDB 并行差"吗？**
  答：不能——它证明的是"共享机基准不可信"；对引擎的结论必须来自独占环境（边界声明见 00）。

## 核心概念速览（中英对照）

- **pgbench** — 官方基准工具：TPC-B-like 脚本驱动的事务压测器。
- **TPC-B-like** — 简单账本事务模式：点更新+点查询的合成负载。
- **预热期** — Warmup：冷缓存启动段，基准入账前截断。
- **离散度** — Jitter：同参数多次运行的波动，噪声的直接读数。
- **吞吐-延迟曲线** — Throughput/Latency Curve：并发扫描下的性能主曲线。
- **采集窗对齐** — Clock-window Alignment：引擎与 OS 指标同窗采样。
- **统计收集器** — Statistics Collector：pg_stat_* 族背后的累积进程（pgstat）。
- **IO Timing** — 块级 IO 计时视图：PG13+ 强化，PG10 缺位（⚠️ 转述）。
- **影子回放** — Shadow Replay：生产流量复制到测试库做回归。
- **unlogged table** — 不落 WAL 的表：装载加速装置，崩溃即失。
- **邻居噪声** — Noisy Neighbor：共享环境的第三方可变性。
- **最小完备报告** — Minimal Report Fields：可比对基准报告的字段集约定。

## 最新演进与工业实践

- **pgbench 能力演进**：PG 13+ 引入 `-b`（select-primary 等内置脚本细分）与 IO 计时增强 ⚠️ 转述；
  权威页仍是 https://www.postgresql.org/docs/10/pgbench.html （本册语境）与同 URL 换版本号的现行页。
- **基准即代码**：2024–2026 主流做法把 sysbench/pgbench/tpcc 参数入 CI，配合性能回归看板 ⚠️ 转述；
  CMU 的 PBD 基准框架（busbench 工具线）是开源事实标准之一 ⚠️（未核验 URL，故不给出链接）。
- **并行度校准**：本目录 X-D 的教训与社区"先隔离噪声再谈 max_parallel_workers"建议一致 ⚠️；
  现代云数据库以 vCPU 预算制隐藏该参数（Aurora 的存储侧解耦见 SIGMOD 2017 论文
  DOI: 10.1145/3035918.3056101 ✅ Crossref 200）。
- **嵌入式分析基准**：DuckDB 的轻量并行模型（论文 SIGMOD 2019 demo,
  DOI: 10.1145/3299869.3320212 ✅ Crossref 200）适合快速复现"方法学"，不适合外推 PG 结论——
  两言并存恰是本册类比 🔧 实验的边界声明。
- **统计视图现代化**：pg_stat_activity 的 wait_event 族、pg_stat_progress_create_index（PG12+）
  等让"基准中的等待"可归因 ⚠️ 转述；PG10 用户当时只能靠 pg_locks+OS 拼图。
