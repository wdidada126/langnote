# 15 声明式分区

## 一、PG10 声明式分区的能与不能（✅ 代码 + ⚠️ 文档锚 https://www.postgresql.org/docs/10/ddl-partitioning.html curl 200）

能做：`PARTITION BY RANGE (orderdate)` + `CREATE TABLE ... PARTITION OF ... FOR VALUES FROM..TO`、
分区裁剪（规划期剪枝）、每分区独立索引（15_4.sql 模式）、维护操作分区粒度化。
不能（2018 之痛 ⚠️ 转述限制节）：分区**自身**上的外键与唯一约束（须把约束建到每个叶子，或如
15_11.sql 用触发器人工维持跨分区 UPDATE 的一致性）、`UPDATE` 跨分区移动行不受内核托管
（书中触发器正是该缺口的社区标准补丁 ✅ 实证）。PG11 补路由插入、PG12 补 FK/唯一约束 ⚠️ 版本注记——
**Chapter15 的 14 个脚本整体是"PG11 前夜的手工时代"标本**。

## 二、分区即调优单位的三本账

1. **扫描账**：范围谓词命中少数分区 → 有效工作集缩小（05 章缓存语义在分区粒度复现）；
   15_10.sql 的 EXPLAIN 验证法即"裁剪是否发生"的日常审计；
2. **维护账**：per-partition 索引重建/vacuum（07 章阈值可按分区表特性设，reloptions 见 08 章）；
3. **生命周期账**：老分区 DETACH→归档/删除，把"数据淘汰"从 DELETE 风暴（07 章膨胀）
   降为元数据操作——分区给运维的最大红利其实是这一条 ⚠️ 立场推定。

🔧 类比实验（sqlite3 3.45.3，**非 PG**）：以手工分区表+UNION ALL 视图模拟范围切分，
`SELECT ... WHERE k BETWEEN a AND b` 走单分区 vs 走全量视图，实测延迟差与行数线性相关
（本目录方法学演示，数字随缓存冷热波动故不载 ⚠️；对照物：SQLite 无规划器裁剪，靠视图内
手工 `WHERE` 常量传播，机制与 PG 裁剪不可类比过深——只证"切小单元=少读数据"的公理）。

## 三、分区键选择判据（⚠️ 教材性，书系口径复原）

- 与最常见范围谓词同族（orderdate/event_time/tenant_id+LIST）；
- 与 JOIN 键错配时分区反而伤计划（跨分区分布键缺位 → PG 无原生分布，代价表现为多分区探测）；
- 分区粒度：查询裁剪收益（多分）vs 规划与锁开销（少分）的平衡——2018 经验值"月/季分区、
  总量几十到几百"（01 章呼应）⚠️ 社区口径；
- 索引策略逐层化：全局唯一索引不存在 → 唯一性要么入分区键，要么应用层保证 ⚠️。

## 细案：分区方案评审单（⚠️ 教材性；每条回锚本章小节）

1. **键与粒度**：谓词同族性（第三节）；粒度试算= 单分区体量 ≤ 池子热档 / 行数 ≤ 千万级（05 章联动）；
2. **索引分层**：叶子级索引清单（15_4.sql 模式）——哪些列全局唯一性已被牺牲？业务如何兜底？
3. **写入路径**：PG10 必须给路由方案（触发器/应用层双写，15_11.sql ✅ 标本）；
   评估触发器税：每行一次函数调用 × 写入速率（03 章量纲）；
4. **跨分区 UPDATE 审计**：会改分区键的业务操作清单——它们决定路由触发器的复杂度；
5. **生命周期自动化**：DETACH→归档→删除的 cron 与"老分区只读化"策略（第二节账 3）；
6. **裁剪验证固化**：核心查询的 EXPLAIN 里 "Subplans Removed"/分区列表长度进回归（15_10.sql 手法）；
7. **统计分布**：每叶子独立 ANALYZE 预算（09 章），父表统计在 PG10 的贫弱是已知坑 ⚠️ 版本注记。

**规模感参考**（⚠️ 社区经验转述）：单分区 500 万–5000 万行、总叶子几十片是 2018 常见甜区；
再细则规划器与目录开销抬头，再粗则维护账无收益。

## 章内自测（三问三答）

- **问：分区后查询反而慢了，三嫌疑？** 答：裁剪失效（谓词包函数）、分区过碎规划税、单查询本需扫全量——15_10 手法先定谁。
- **问：BRIN 还要不要？** 答：要——分区管"少读"，BRIN 在每叶子内继续管"少读"（09 章），二者正交。
- **问：PG11 后本章哪些手工件可退役？** 答：路由触发器、跨分区 UPDATE 兜底；FK/唯一约束到 PG12 才补齐（第五节时间线 ✅ 代码对照）。

## PG10 分区语法速查（✅ 形态与书仓 Chapter15 一致；语义以 10 版官方分区文档为锚）

```sql
CREATE TABLE orders (LIKE orders_tpl INCLUDING ALL) ;            -- 父表(分区模板)
CREATE TABLE orders PARTITION OF orders
  FOR VALUES FROM ('2004-01-01') TO ('2004-04-01');             -- 声明叶子(季度粒度)
CREATE INDEX ix_orders_2004_q1_custid ON orders_2004_q1 (customerid);
                                                 -- 15_4.sql 模式：逐叶子建同名索引，无全局索引
-- 15_11.sql 模式：跨分区 UPDATE 的"删旧插新"触发器兜底（PG11 起内核接管）
-- 15_10.sql 模式：ANALYZE 父/子后 EXPLAIN 验证 "Subplans Removed"/分区列表
```

三坑注记（⚠️ 转述）：
1. 父表上的 DEFAULT 分区 PG11 才有——PG10 越界行直接报错，路由触发器必须含兜底分支；
2. 统计：父表 reltuples 与叶子的关系在 10 版规划器里生涩，裁剪后计划仍可能选错连接序（10 章走查）；
3. `pg_partition_tree` 类目录便利视图是 PG12+ ⚠️——10 版靠 pg_inherits 手 join 数分区（考古注脚）。

## 粒度速答

问：月分区还是季分区？答：以"单叶 ≤ 池子热档 ∧ 维护窗内可重建全部叶索引"双约束取最粗者（第 2 节账 2）。

追问：分区键选时间还是哈希？答：数据生命周期治理（DETACH 淘汰冷数据）只与范围键兼容；
哈希键解决的是写热点与均匀分布，但 PG10 声明式尚无哈希分区 ⚠️（PG11 才补上），
故本书语境下答案近乎唯一：RANGE(时间列) 或 LIST(枚举维度)，按"裁剪谓词是否即生命周期谓词"择一。
判据一句话：查询若总能带上分区键前缀谓词，分区才有正收益；否则分区税白交。

## 核心概念速览（中英对照）

- **声明式分区** — Declarative Partitioning：PARTITION BY 语法化的表切分契约。
- **分区裁剪** — Partition Pruning：规划期按谓词剔除不相交分区（15_10.sql 验证）。
- **叶子分区** — Leaf Partition：实际存数据的终端分区。
- **FOR VALUES** — 分区边界子句：RANGE 的 FROM..TO 或 LIST 的 IN 列表。
- **路由触发器** — Routing Trigger：PG10 手工兜底跨分区行移动（15_11.sql ✅）。
- **分区索引** — Per-partition Index：各叶子同名索引（15_4.sql 模式）。
- **DETACH 淘汰** — Drop by Detach：把数据生命周期降为元数据操作。
- **约束分区** — Partition Constraint：分区键谓词与 CHECK 的对应体。
- **跨分区更新** — Cross-partition Update：PG11 前需人工/触发器的缺口 ⚠️。
- **裁剪反例** — Pruning Failure：谓词包函数/类型不匹配导致全分区扫。
- **dellstore2** — 教学样例库：本册分区/查询章的实验数据集 ✅ 提示符实证。
- **分区税** — Partition Overhead：分区数过多带来的规划/锁/元数据开销。
