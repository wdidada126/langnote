# 14 逻辑复制：发布与订阅

> 章题 ⚠️ 推定（"Logical Replication (Pub/Sub)" 意译）；主题域 ✅ 强实证：
> 官方代码仓 `Chapter14`（唯一文件 `14_1..sql` ✅ 全文实抓）是一段完整的**双库操作实录**：
> db1 建 `replicator` 角色（REPLICATION LOGIN）+ 表 mynames + `CREATE PUBLICATION mynames_pub`；
> db2 建同名表 + `CREATE SUBSCRIPTION mynames_sub CONNECTION 'dbname=db1 host=node1
> user=replicator password=...' PUBLICATION mynames_pub`。本章围绕这一最小闭环展开。非原书文本。

## 一、从 14_1..sql 读出全部要件（✅ 逐行讲解）

1. **角色三权**：`REPLICATION` + `LOGIN` +（因订阅端走密码连接）`PASSWORD`；
   主库 `pg_hba.conf` 还须放行复制连接（06 章语境审计在此落地）⚠️ 转述；
2. **wal_level=logical**：发布库必须重启级开启（06 章 postmaster 语境 + 01 章 WAL 税 ⚠️）；
3. **两端表结构**：PG10 订阅端**不会自动建表**（initialization 仅拷数据不拷结构，
   后续版本才补 `create_subscription ... copy_data` 相关增强 ⚠️ 版本注记）——14_1.sql 在 db2
   手工 CREATE TABLE 的原因；
4. **主键依赖**：无 PK 表的 UPDATE/DELETE 复制要么报错要么慢（全行匹配），
   PG10 时代即要求副本标识意识（`REPLICA IDENTITY FULL` 是性能下策 ⚠️）；
5. **连接串明文**：书仓示例把密码写进 CONNECTION 字符串——生产须用
   `.pgpass`/channel binding 等现代姿势 ⚠️ 安全注记（2018 示例代码的时代印记）。

## 二、机制与性能剖面（⚠️ 转述官方文档；✅ 锚 https://www.postgresql.org/docs/10/sql-createpublication.html curl 200）

- 解码在**发布端**进行（逻辑解码器把 WAL 元组变化译成行事件流），订阅端以 apply worker
  重放 SQL——**CPU/内存税在源头**，这是与物理复制最大的成本结构差异；
- 初始同步（copy_data=true）是一次全表 COPY：装载窗口算术同 12 章（🔧 X-A 的装载速率量纲 ⚠️ 类比边界见 10 章）；
- apply 延迟度量：`pg_stat_subscription` 与 LSN 差（11 章面板并入）；
- **序列不复制**：切换/故障接管时序列须手工对齐（01 章伏笔回收 ⚠️）；
- DDL 不同步、大对象/系统目录表不同步等限制清单 ⚠️ 转述官方限制节。

## 四、膨胀与槽的暗礁（07/06 章联动）

订阅端 apply worker 是长事务源 → 发布端对应复制槽把 `xmin` 水位钉住 →
**主库 vacuum 追不动 = 全库膨胀**（07 章模型 + 11 章监控的复合事故）；
2018 年至今该事故形态未变，处方不变：槽延迟告警 + `max_slot_wal_keep_size`（PG13+ 才有保险丝 ⚠️ 版本注记）。

## 五、演进时间线（PG10 → 今）

PG10 内核化 → PG11 并行 apply、PgBouncer 会话模式兼容 → PG13 冲突日志化/排除约束改进 →
PG15 行过滤（发布端 WHERE）→ PG16 merge 命令协同、混合慢启动收敛、`pg_createsubscriber`
把物理备库整体转逻辑订阅（升级救星 ⚠️ 转述版本史，逐条特性以 17 版本文档为准）→
2026 年逻辑复制已是默认数据集成底座之一 ⚠️ 评价口径。

## 细案：零停机大版本升级六步舞（⚠️ 教材性；组件全出自 13/14/15 章）

场景：PG10 生产 → PG16+，禁停机窗口。

1. **搭新巢**：目标版本集群就绪（参数模板按 02 画像重做，不抄旧 conf）；
2. **通管道**：旧库建发布（全库或白名单表，wal_level=logical 若未开需一次重启 ⚠️ 06 章语境账）；
   新库建订阅 `copy_data=true, synchronize_data=...`（选项语义随版本演进 ⚠️ 以现行文档为准）；
3. **对齐序列**：切流前最后一轮，用 pg_dump --sequences-only 类片段或手工 setval 对齐（01 章缺口回收）；
4. **追平验证**：LSN 差归零 + 抽样一致性查询（行数/校验和切片）；
5. **切流**：连接串漂移（池化层单点切换，避免应用改配置），旧库转只读探针；
6. **观察窗**：auto_explain+错误日志盯新库一周（11 章），旧库留降级回梯（反向订阅可选 ⚠️ 高阶）。

## 章内自测（三问三答）

- **问：发布端 CPU 突然高 20%，订阅端刚重启，因果链？** 答：槽积压后一次性解码追账——延迟预算要盯"重启后 30 分钟窗口"（11 章面板三）。
- **问：两库同名表结构漂移会怎样？** 答：apply 报错卡死或错列写坏数据——pub/sub 不校验 schema 演化，迁移类切换必须先冻结 DDL ⚠️ 转述限制。
- **问：为什么示例里订阅端手工建表？** 答：14_1..sql 的 `create table mynames` 在 db2 再现，正是 PG10 不自动建表的实证（✅ 代码）。

## 运维 SQL 卡（⚠️ 语义转述自官方文档，SQL 形态为本册 14_1..sql 的展开）

```sql
-- 发布侧：看订阅者进度与冲突
SELECT subname, received_lsn, latest_end_lsn,
       now()-latest_end_time AS since_last_msg
FROM pg_stat_subscription;
-- 发布侧：解码/槽健康
SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;
-- 发布管理：增删表不停订阅（对象粒度是逻辑复制的日常手术刀）
ALTER PUBLICATION mynames_pub ADD TABLE orders;
-- 订阅侧重启动 apply：
ALTER SUBSCRIPTION mynames_sub DISABLE;  -- 注意：断开不消费，retained 会涨（07 章暗礁）
ALTER SUBSCRIPTION mynames_sub ENABLE;
```

**告警三件套**：since_last_msg 突增 / retained 单调上涨 / 订阅端 apply 错误日志——
三者同时进 11 章面板三（槽曲线即本章的呼吸图）。

## 核心概念速览（中英对照）

- **发布/订阅** — Publication/Subscription：逻辑复制两端对象（14_1..sql 全件）。
- **逻辑解码** — Logical Decoding：WAL → 行事件流的源头翻译层（CPU 税在发布端）。
- **wal_level=logical** — 解码前提：postmaster 级参数（06 章语境）。
- **初始快照拷贝** — copy_data：订阅建立时的全表装载窗口。
- **副本标识** — Replica Identity：无主键表 UPDATE/DELETE 复制的定位依据。
- **apply worker** — 回放进程：订阅端 SQL 重放执行体。
- **槽钉水位** — Slot xmin Pin：延迟槽→膨胀雪崩的机制根（07 章）。
- **序列缺口** — Sequence Not Replicated：逻辑复制不搬序列的切换陷阱。
- **双向复制环路** — Bidirectional Loop：PG 原生 pub/sub 的弱区 ⚠️。
- **订阅冲突** — Apply Conflict：主键重复等，日志可见但处理原始（13/PG13 演进点）。
- **CDC** — Change Data Capture：以解码出口喂养下游管道的工业用法。
- **pg_createsubscriber** — 物理转逻辑工具：升级/容灾混合路线的新砖（版本注记）。

## 最新演进与工业实践

- **行级/列级过滤**：PG15 发布端行过滤（WHERE 列强类型 ⚠️）、PG 后续版本持续补
  分区根表发布语义；权威现行页 ✅ https://www.postgresql.org/docs/17/logicaldecoding.html （curl 200）。
- **Dezines 等消费工具与 Kafka Connect**：基于解码输出的开源管道成熟，书内"双库直连"
  最小样态已延伸为企业事件总线 ⚠️ 生态转述（不给未验证 URL）。
- **多写仍交外部方案**：Patroni+逻辑组合、BDR 商用线 ⚠️ 转述；原生 pub/sub 在 2026 的定位是
  "单向数据流 + 受控迁移"，不是多活数据库。
- **升级平台化**：跨大版本蓝绿（13 章第五节）完全建立在逻辑复制上，本章 14_1..sql 那六条
  DDL 即其最小基因 ⚠️ 实践口径。
