## 核心概念速览（中英对照）

- **strace** — 系统调用追踪器：经 ptrace 拦「进程→内核」边界，`-f` 跟线程、`-e trace=` 过滤、`-O` 计时
- **僵尸进程** — zombie process（故事7）：已 exit 未被 wait 的进程仍占 PID 表项——`fork` 后不收割的经典竞态
- **perf** — Linux 性能观测器：采样（`record -g`）、计数（`stat`）、追踪（`sched`/`tracepoint`）三合一
- **火焰图** — flame graph：Brendan Gregg 的调用栈聚合可视化，宽度=包含占比（工具：FlameGraph 脚本栈）
- **eBPF** — extended Berkeley Packet Filter：内核内的安全验证虚拟机；kprobe/uprobe/tracepoint 挂探针
- **uprobe** — 用户态静态探针：给任意函数入口（含 so 内偏移）挂钩子，读参数、记直方图——「无侵入插桩」
- **bpftrace** — eBPF 的单行 DSL：`uprobe:/lib/x.so:f '...'` 即席观测，降低编写-编译-加载门槛
- **崩溃上报管线** — crash reporting pipeline（第 13 章）：客户端捕获→压缩脱敏→服务器聚合→终端集成器（工单/告警）
- **符号化服务** — symbolication service：服务端按 Build-ID 配对符号做「地址→函数:行」，崩溃单才可读
- **链接问题（故事8）** — 符号解析/装载顺序类故障：`ldd -r`、`LD_DEBUG`、`nm -D` 三板斧的典型靶子
- **临时变量生命周期（故事9）** — 悬垂引用故事：绑定到 `const T&` 的临时量寿命延至引用本身，函数返回局部引用/
  按值返回被缓存引用则是反例

## 1. 动机：调试器看不到的那一层

前九章的武器都作用于**进程内**。但有三类问题只在边界上可见：
① 进程与内核的对话（系统调用：文件、网络、wait——strace 的主场，僵尸故事）；
② 全系统视角的性能与调度（perf 采样、eBPF 聚合——「不在现场也能看见」）；
③ 崩溃之后（第 13 章：现场不在工程师手里而在千万用户机器上，必须**自动化地把现场搬回来**）。
这三样合起来是「调试器之外的第二观测面」，也是本书从工具书跨到工程书的分水岭章节。

## 2. 机制

### 2.1 strace： syscall 边界的审计员（12.1）

`strace -f -e trace=process -tt ./prog` 三参含义：跟子进程/只看进程族 syscall/带时间戳。
故事7（僵尸进程）的读法：看到 `wait4(-1, ...)` 缺失或 `clone` 后无收割，即可断「不收割」类泄漏；
僵尸占 PID 不占内存，监控只看 RSS 会漏——**指标盲区**要靠 syscall 视角补。
Windows 对位工具：Process Monitor（Sysinternals）与 ETW。

### 2.2 perf 与火焰图（12.3）

`perf record -F 99 -g -- ./prog && perf script | stackcollapse-perf.pl | flamegraph.pl`：
99Hz 避开锁相、`-g` 保留调用链。火焰图回答「CPU 时间都包在哪个父帧」，与调试器的断点采样互补：
不暂停、可生产常开（配合 `perf top`）。Windows 对位：ETW/xperf、VTune。

### 2.3 eBPF：把「关键区日志」写进内核（12.4，对应原书 准备环境→编写→编译→加载四小节）

原书四步的实质：verifier 约束下的 C 片段编译为 BPF 字节码→`bpf()` 系统调用加载→挂载到
kprobe/uprobe/tracepoint→经 perf ring buffer 把聚合结果（直方图/计数）送用户态。
对调试的意义：给生产实例挂「只读探针」采参数分布，零重启、开销微秒级——
[07 篇](07-调试多线程程序.md) 7.4 关键区日志的**免重编内核级版本**。
bpftrace 单行样例（Linux；⚠️ 未本机实测）：

```text
# 某 malloc 封装的分配尺寸直方图（生产安全）
bpftrace -e 'uprobe:/usr/lib/libfoo.so:my_alloc { @ = hist(arg0); }'
```

### 2.4 崩溃发送机制（第 13 章）

客户端（信号/VEH 捕获 + minidump/core 生成 + 脱敏）→ 服务器（去重聚类、Build-ID 符号化、留存策略）→
终端集成器（告警/工单/看板）。关键设计三则：

1. **采样与限流**：同指纹崩溃每设备每日一次，否则服务器被风暴淹没；
2. **隐私分级**：栈+模块表（minidump 默认）先传，完整 core 走升级通道（[06 篇](06-进程镜像与CoreDump.md) 权衡）；
3. **符号匹配自动化**（1.4.3 的管线级兑现）：Build-ID/GUID+age 不匹配的报告直接丢弃，宁缺毋滥。

开源参照：Breakpad/Crashpad（客户端+符号化）与 Sentry/Symbolicator（服务端聚合）。

## 3. 两个实战故事的现代复演

### 3.1 故事8「链接问题」（12.5）——装载顺序与符号解析

通用侦查顺序：`ldd -r`（未定义引用列表）→ `LD_DEBUG=bindings`（谁绑到哪个 so，[06 篇](06-进程镜像与CoreDump.md) 表）→
`nm -D` 比对两侧导出 → 查 RPATH/LD_LIBRARY_PATH 与多版本 so。
🔧 **本仓库同构实测**（Windows 即 [02 篇](02-堆数据结构.md)/[03 篇](03-内存损坏.md) 记的 PATH 混载案）：
Git-Bash 自带 `libstdc++-6.dll` 抢在目标 MinGW 之前被装载→堆跨运行时→假「UAF 崩溃」+错位符号栈；
`export PATH=/d/develops/tools/mingw64/bin:$PATH` 后同程序静默通过。**结论同故事8：先审装载清单，再疑代码。**

### 3.2 故事9「临时变量的生命周期」（12.6）

经典样本：`const auto& s = std::string(buf) + "x";` 寿命延至引用销毁（OK），但
`std::string_view sv = Short();` 存入 `map`、或 lambda 捕获 `const T&` 指向已亡临时——
「读出来全是垃圾但内存没坏」。与 [03 篇](03-内存损坏.md) 的 UAF 判据（值过合理=残骸）共用取证法；
GDB 里看「引用绑到了谁的地址」（`p &ref` 对照 `info locals` 各成员地址）即可定案。

## 4. 相邻概念对比

- **strace vs eBPF**：前者全量逐条（适合单次深读），后者可编程聚合（适合常开观测）；strace 本身拖慢
  I/O 密集程序 10 倍+，Heisenbug 温床。
- **perf 采样 vs 记录回放（rr/TTD）**：采样给「统计真相」不给单次现场；回放反之——生产用前者，
  工单用后者（能复现前提）。
- **崩溃上报 vs 日志**：上报管线是「拉现场」，日志是「提前自述」；第 18 章把两者都归入「尽量不要调试」的
  监控体系（[12 篇](12-泄漏协程远程容器与预防.md)）。

## 最新演进与工业实践

- **bpftrace/CO-RE 取代手写 eBPF C**：原书 12.4「准备环境→编译→加载」四步在 2026 年基本被
  bpftrace 单行 + BCC 库 + eBPF CO-RE（libbpf）免内核头文件方案吞并；Windows 无对位（ETW 生态）。
- **持续性能剖析（continuous profiling）**：Parca/Pyroscope/Grafana Pyroscope 以 perf+eBPF 为底、
  火焰图进 APM 看板——perf（12.3）的「一次性命令」变成「组织级常态数据」。
- **崩溃管线标配化**：Crashpad（Chromium 系）+ Symbolicator（Sentry 系）开源可用；minidump 事实上
  成为跨端崩溃格式；Linux 发行版侧 systemd-coredump + coredumpctl 提供单机版全套。
- **AI 辅助（⚠️ 前沿观察）**：崩溃聚类（栈指纹+LLM 摘要去重）已见于商用 APM；自动修复仍停留演示阶段。
- **开源仓库逐点对应**：`iovisor/bcc`、`bpftrace/bpftrace`（12.4 的现代替身）、`google/breakpad`、
  `getsentry/symbolicator`（13 章三件套的开源件）。
- **平台适用性**：本章工具全 Linux；本仓库 Windows 用户可在 WSL2 内使用（eBPF 需较新内核），
  原生侧以 ETW/Sysinternals/VS 诊断中心对标使用。
