## 核心概念速览（中英对照）

- **调试版/发行版** — debug vs release build：`-g -O0` 与 `-O2` 的组合差异；5.1 逐项对比表是本章纲领
- **内联** — inlining：被调函数并入调用者，栈帧消失——「回溯里找不到函数」的第一原因
- **尾调用优化** — tail call optimization：`jmp` 复用帧，调用链在回溯中被「压扁」
- **寄存器分配** — register allocation：局部变量驻留寄存器或干脆消失；`<optimized out>` 的机制解释
- **位置表达式** — DWARF location expression（DW_OP_…）：告诉调试器「此刻这个变量在 $rax+8 / 栈槽 / 不存在」
- **调用惯例** — calling convention：x86-64 SysV（rdi/rsi/rdx/rcx/r8/r9 传参）与 Win64（rcx/rdx/r8/r9）两大主流，跨 ABI 必读
- **被调用者保存寄存器** — callee-saved（rbx/rbp/r12–r15）：跨函数保值的寄存器；**caller-saved** 则随时可被覆写
- **帧指针** — frame pointer（rbp）：省略它（`-fomit-frame-pointer`）省一个寄存器，但栈展开只剩 `.eh_frame` 可依赖
- **RIP 相对寻址** — RIP-relative addressing：PIC 代码用 `lea 0x1234(%rip),%rax` 与加载地址解耦
- **反汇编读法** — disassembly reading：从 `disassemble /m` 的「源码-汇编混排」倒推编译器对代码的改写
- **`-Og`** — optimize for debugging：保留调试语义的轻量优化档位，GCC/LLVM 均支持

## 1. 动机：只有生产环境才复现的 bug

第 3 章说过 Heisenbug；本章是其第一大成因的系统化：优化把「源码模型」重写成「硬件模型」，
调试器赖以翻译的假设（变量有地址、行号有对应指令、函数有帧）被逐条打破。典型症状清单：

- `print sum` → `value has been optimized out`；
- `next` 在源码行间**跳跃/倒退**，一行执行两遍；
- 回溯里没有中间函数（全被内联）；
- 停在第 4 行却发现第 3 行「已经生效」——指令调度/提前计算；
- 变量「值是对的，地址是假的」（被消除，DWARF 位置表达式只在个别区间存在）。

## 2. 机制

### 2.1 汇编素养的最低配置（5.3）

不必会写，必须会读四件事：**寄存器家谱**（rax..r15 及 al/ax/eax 别名）、**数据搬移族**
（mov/lea/movsx/movzx）、**分支与调用**（cmp+jcc、call/jmp、ret）、**寻址式**（`base + index*scale + disp`）。
栈帧模板：入口 `push rbp; mov rbp,rsp` 为保留帧指针版；`sub rsp,0x28` 划局部区；参数按调用惯例落位。
调用惯例差异是 Windows/x64 排障第一坑：SysV 第 4 个整型参数在 rcx，Win64 第 4 个在 r9——
用错地图读出的全是「函数收到了一堆垃圾」。仓库内纵深：[../Intel开发人员手册.md](../Intel开发人员手册.md)（指令语义终极出处）。

### 2.2 -O0 与 -O2 的本机实测对照

🔧 **已实测**（MinGW g++ 15.2，同一 11 行求和函数：循环体 `for i<n: sum+=a[i]`）。

断点落点与局部变量：

```text
# -O0：停在函数第一行，行号逐条推进，locals 完整
Breakpoint 1, checksum (a=0x5ffe30, n=16) at opt.cpp:3
3  int sum = 0;              (gdb) next → 4 → 5，sum 一路可见

# -O2：停在第 4 行（第 3 行「不存在」），参数带 @entry 注解
Breakpoint 1, checksum (a=a@entry=0x5ffe40, n=n@entry=16) at opt.cpp:4
4  for (int i = 0; i < n; ++i) { sum += a[i]; }
(gdb) info locals → i = 0 / sum = 0      # 仅入口处可查，循环中途 next 直接飞出函数
```

要点：`a@entry` 表示「该值来自函数入口时的寄存器快照，当前已不可追踪」——DWARF 位置表达式
退化为「仅入口有效」的教科书样本；`break checksum` 两版行号不同（3 vs 4），因为 `.debug_line`
里第 3 行的指令在 -O2 被合并进循环初始化。

优化后的循环被重写成指针递增式（`disassemble` 实测节选）：

```asm
=> 0x…1450 <checksum+16>:  add    (%rcx),%eax     ; sum += *p++
   0x…1452 <checksum+18>:  add    $0x4,%rcx
   0x…1456 <checksum+22>:  cmp    %rdx,%rcx       ; 上界指针预计算 (rcx,rdx,4)
   0x…1459 <checksum+25>:  jne    0x…1450
```

循环变量 i 从「计数器」变成「指针步进」，`n` 被预先折算成终止地址——这正是「print i 还在、
值却是 0」类幻觉的机制。

### 2.3 发行版取证三板斧（5.4/5.5 的方法论化）

1. **`disassemble /m`**：源码-汇编混排，把「这条指令属于哪行」摆明（GDB；LLDB 用 `disassemble` 搭配源文件对照）；
2. **`info scope 变量名`**：列出该变量的 DWARF 位置表达式分段（哪段在寄存器、哪段不存在）；
3. **寄存器考古**：调用惯例已知 → 回溯入口时参数曾在 rcx/rdx/r8/r9（Win64）；rbx/rbp/r12-r15
   在帧链上保守可信。core 分析里这是「符号失效区的最后一层地图」。

### 2.4 为什么「带 -g 的 -O2」是可行折中

现代编译器保证 -O2 -g 的调试信息**正确**（不撒谎）但**不完整**：允许 optimized out、允许行号合并，
不允许显示错误的值。所以发行版调试的正解不是「回退 -O0」（改变被调对象本身=最大 Heisenbug），
而是：-g -O2 + 接受不完整性 + 三板斧补齐 + （必要时）`-fno-omit-frame-pointer`、`-fno-inline`
按函数粒度局部降档（`__attribute__((optimize("O0")))`）重编复现。

## 3. 权衡

- **-Og vs -O1**：-Og 是「行为最接近源码」的复现档；-O1 起行号即开始失真。CI 里可留 -Og 产物做二线现场。
- **PDB/DWARF 分离发布**：符号留服务器（debuginfod/Breakpad），二进制 strip——体积与安全收益换一次
  「符号匹配」流程责任（01 篇）。
- **frame pointer 取舍**：-fomit-frame-pointer 省 1 个 GPR，perf/栈采样与部分 gdb 回溯依赖它；
  现代方案是 `.eh_frame`/`--enable-frame-pointers` 二选一，perf 用户普遍全栈保留帧指针。

## 4. 相邻概念对比

- **优化调试 vs 反汇编调试（无符号）**：前者有 DWARF 但信息不完整；后者连类型都没有，全靠调用惯例与
  字符串引用——「断点不工作」（01 篇）的极端形态。5.3 的汇编功底正是后者的门票。
- **Heisenbug（优化）vs Heisenbug（竞态/UB）**：优化型可「同一二进制换观测手段」逼近；竞态型必须
  换时间控制（[07 篇](07-调试多线程程序.md)）；UB 型必须换检测器（[03 篇](03-内存损坏.md)）。
- **张海洋书第 9 章「发行（Release）版调试」**：那本讲 VC「去优化/保留优化」开关与 gdb 符号提取的**操作**，
  本章给的是为什么这些开关有效（[../C++代码调试的艺术.md](../C++代码调试的艺术.md)）。

## 最新演进与工业实践

- **perf + 火焰图**：-O2 生产二进制不再需要「调试」而是「观测」——`perf record -g` 采栈，
  Brendan Gregg 火焰图（brendangregg.com/flamegraphs.html，已实测 HTTP 200）聚合展示；
  Windows 侧对应 ETW/xperf 工具族。
- **rr / WinDbg TTD**：优化代码难单步 → 干脆录制执行、反向回放（Linux: mozilla/rr；Windows: WinDbg
  Time Traveling Debugging，文档已实测 HTTP 200），把「跳跃的单步」变成「可倒带的录像」。详见
  [07 篇](07-调试多线程程序.md)、[08 篇](08-调试方法论与复现.md)。
- **clang 调试友好选项**：`-Xclang -fast-isel` 之外的 `-gdwarf-5` + 源代码参考表（DWARF5 line table
  列号支持）让「同一行多语句」可区分；`gdb` 的 `layout asm` 与 VS 的「反汇编窗口」同思路。
- **MSVC 对照（本机双栈适用性）**：/O2 + Program Database 的 `@entry` 语义与 GCC 相同；VS「在汇编中
  立即窗口」等价三板斧第一式；/GL（LTCG）的行号失真比 GCC 更重，复现优先 /Od /RTC1 局部重编。
- **AI 辅助（⚠️ 前沿观察）**：LLM 读反汇编/解释优化行为的公开演示仍不可靠，生产建议以
  混排视图+位置表达式为准，把 AI 用于生成「该函数的 -Og 复现桩」这类机械工作。
