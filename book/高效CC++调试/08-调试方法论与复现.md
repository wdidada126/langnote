## 核心概念速览（中英对照）

- **归因** — attribution（8.1.1）：把「故障」映射到「首次可区分的差异点」：哪个版本/输入/环境/时序
- **环境信息收集** — environment capture（8.1.2）：版本矩阵、配置、内核参数、依赖 so 清单——复现的原料
- **环境重建** — environment reconstruction（8.1.3）：容器/快照把「那台机器」搬到你面前
- **分治法** — divide and conquer（8.3.1）：对代码（注释掉）、对输入（裁剪）、对时间（二分回放）、
  **对版本（git bisect）** 的四轴折半
- **最小复现** — minimal repro：删到「再删即不坏」；价值在**构造过程**——每删一步都在检验归因假设
- **调试历史** — debugging log（8.3.3）：假设-实验-结果三元组流水；防「绕圈」与「记忆篡改」
- **假设-实验循环** — hypothesis–experiment loop：调试的科学方法内核：一次只检验一个假设，
  实验必须可证伪
- **逆向调试** — reverse debugging（8.4）：从崩溃点倒带回「值第一次变坏」的瞬间，continue with negative step
- **rr** — record & replay（8.4.1）：录制全部非确定性事件；回放时任意重演+反向执行
- **知识保留** — knowledge retention（8.2.1）：postmortem/缺陷库把个人排障经验变成组织资产
- **可调试性设计** — debuggability by design（8.2.3）：不变量断言、唯一 ID、环形缓冲、慢路径日志——
  「为未来的自己写日志」

## 1. 动机：调试是「有方法的犯错」

不会复现就不会调试——原书把第 8 章放在全部机制章之后，正是把散在各章的手法回收成一套流程：
**收集→归因→假设→实验→（复现不了就）重建环境**。多数低效调试的共同点不是命令不熟，而是跳过了
假设直接乱改、或一次改三处再看「好了没」（对照 [03 篇](03-内存损坏.md) 的 watchpoint 单点抓获范式）。

## 2. 机制：方法论的四块基石

### 2.1 重现错误 = 归因 + 环境（8.1）

- **归因**先问「何时开始坏」→ 版本二分：`git bisect run ./test.sh` 把「谁引入的」交给机器
  （前提=有自动判定，这又反过来要求最小复现）；
- **收集环境信息**：原书清单（OS 版本、内核参数、库版本、locale、时区、硬件特性）在容器时代
  收敛为一条命令级别：`docker inspect` + 锁文件 + `/proc/version`；
- **重建环境**：复现失败常因环境差而非代码差——本仓库的活证据：同一 UAF 程序，PATH 里混入
  Git 自带 MinGW 运行时即段错误、换回发行版运行时静默通过（[02 篇](02-堆数据结构.md)、[03 篇](03-内存损坏.md)
  实测）。「换目录就崩」类报告先查装载清单（`info sharedlibrary` / `ldd`）。

### 2.2 分治与二倍的杠杆（8.3.1）

四轴二分的最小配方：代码轴（注释/替换桩）、输入轴（二进制裁剪输入文件）、时间轴（rr 的
`reverse-continue`/日志时间戳回溯）、版本轴（git bisect）。**每折一半=一次可证伪实验**——
这就是分治法与假设-实验循环的合流点。

### 2.3 保留调试历史（8.3.3）

三元组流水（假设 | 实验 | 结果）对抗两个天敌：「我记得刚才已经试过」（其实没试过）与
沉没成本式恋战（在错误子系统上叠加第 7 个假设）。8.3.2「退一步」的操作化定义：换抽象层重述问题——
栈问题改看堆、代码问题改看数据流、单机问题改看环境差集。

### 2.4 逆向调试与 rr（8.4）

正向断点回答「从这里开始发生了什么」；逆向调试回答「到这里为止发生了什么」。崩溃取证的最短路径：

```text
$ rr record ./prog         # Linux/x86-64；此后 rr replay 无限次、任意交错重演
(rr) continue              # 跑到崩溃
(rr) reverse-continue      # 倒放：回到「上一次写坏该内存」处
(rr) watch var @ -1        # 倒着单步看值如何一步步烂掉
```

8.4.2「rr 注意事项」今天依然成立：不支持部分 AVX-512/新指令、`rr record` 开销约 1.2–2×，
含大量设备交互/共享内存的进程录不动（Windows 侧改用 WinDbg TTD）。

## 3. 防止未来的 bug（8.2）——把本章反向装订到第 18 章

- **增强提前检查**：断言=可执行的文档（`assert` 只该保护「绝不该发生」）；参数校验前移到边界；
- **编写更好调试的代码**：每个错误路径带上下文（变量值、状态 ID）、环形缓冲代替刷屏日志、
  `__LINE__` 级别的状态机 dump——这些是**为未来的调试会话写的接口**；
- **知识保留**：postmortem 模板里必须有「最小复现在哪个仓库哪个测试号」一栏，否则归因经验不落地。

### 3.1 反模式清单（与 8.3 规则互为镜像）

| 反模式 | 病灶 | 处方（对应小节） |
| --- | --- | --- |
| 先改代码再找原因 | 无假设的随机修复 | 一次一个可证伪实验（8.3 规则 1） |
| 「在我机器上是好的」 | 环境差集未采集 | 收集装载清单/内核参数（8.1.2） |
| 在错误子系统守了三天 | 沉没成本+无调试历史 | 三元组流水+强制「退一步」（8.3.2/3） |
| 复现一次丢一次现场 | 只顾推进忘留证据 | 每次成功复现即固化：脚本+core+版本号（8.2.1） |
| 用调试器代替思考 | 观测不建模型 | 先写下「如果假设成立，下一步应看到什么」（8.3.1 分治的前提） |

## 4. 权衡

- **复现 vs 取证**：能重建现场就复现（实验可控、可上检测器）；不能就保 core/minidump（一次性、
  信息冻结但完整度受 dump 策略限制——[06 篇](06-进程镜像与CoreDump.md) 的 coredump_filter 权衡）。
- **自动化二分的前提成本**：git bisect 要求判定脚本可靠；为一次性 bug 写判定常常不划算，
  但同族 bug 出现第二次即回本。
- **逆向调试的「作弊感」**：时间机器让你跳过建模阶段，代价是对平台与工具链的强绑定；
  方法论（假设-实验）是跨平台的，rr 不是——先学前者。

## 5. 相邻概念对比

- **分治（空间折半） vs 回放（时间折半）**：前者切「谁负责」，后者切「何时坏」；内存损坏类常需连用
  （二分定位肇事写→再对肇事函数做输入二分）。
- **调试历史 vs 日志/监控**：前者是给「人-问题」的会话记录，后者是给「程序-生产」的自动输出；
  第 13/18 章（上报、监控）与本章互补而非重叠。
- **rr vs TTD vs 自研日志**：录全 vs 采样 vs 手选点位——信息量、开销、平台三轴上的连续谱，
  选型依据见 [07 篇](07-调试多线程程序.md)演进节。

## 最新演进与工业实践

- **rr 生态成熟（Linux）**：`rr dump`、Python 绑定、与 VS Code 调试面板（`rr replay -a` 暴露 DAP）打通；
  mozilla/rr 持续维护；服务器发行版内核默认开 `perf_event` 即可用。
- **WinDbg TTD（Windows）**：`ttd -r` 一条命令把「录制-回放-反向」产品化进官方调试器
  （文档实测可达 HTTP 200）——本仓库双栈结论：Linux 用 rr、Windows 用 TTD，方法论同一套。
- **reduction 工具化**：c-reduce/CVise 自动裁剪测试用例（LLVM 回归测试标准流程）；
  输入侧 fuzzing 最小化（AFL++ `-minimize`）把「最小复现」变成流水线工序。
- **持续模糊**：*Continuous Fuzzing with libFuzzer and AddressSanitizer*（SecDev 2016，
  DOI 已实测：`10.1109/secdev.2016.043`）——OSS-Fuzz/ClusterFuzzLite 的方法论来源，
  「复现」在 CI 里被自动化到每天发生。
- **AI 辅助归因（⚠️ 前沿观察）**：LLM 代理已能自动执行「读 issue→写复现测试→定位补丁」链路
  （AutoCodeRover，arXiv:2404.05427 已实测存在；SWE-bench 类基准衡量其战绩），但「环境差集归因」
  这类依赖真实系统观测的环节仍不可靠——人机分工：人定假设，机器跑二分。
- **开源仓库逐点对应**：`mozilla/rr`（8.4 全节）、`llvm/llvm-project`（c-reduce 后继 CVise 生态）、
  `google/oss-fuzz`（持续前移复现）。
