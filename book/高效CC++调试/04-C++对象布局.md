## 核心概念速览（中英对照）

- **对齐** — alignment：类型要求的地址整除性与对象间距（`alignof`/`__alignof__`、`#pragma pack`），padding 的来源
- **大小端** — endianness：多字节整数的字节序；x86/ARM(默认) 小端，网络字节序与部分硬件描述符为大端
- **对象表示** — object representation：对象占用的字节序列；调试器读内存「还原」对象全靠它+类型信息
- **虚表指针** — vptr：多态对象头部隐藏指针，指向虚表（vtable）；跨虚调用与 `dynamic_cast` 的运行时凭据
- **虚函数表** — vtable：编译器生成的函数指针数组；GNU ld 视角下是 `.data.rel.ro` 里的全局符号 `_ZTV…`
- **this 调整** — this adjustment：多继承/虚继承下不同基类子对象视图需要平移 this——调试时「同一对象两个地址」的根源
- **空基类优化** — empty base optimization (EBO)：无数据成员基类可零开销，改变 `sizeof` 与成员偏移
- **位域** — bit-field：按位排布成员；调试器按「字节可读、按位失真」的老问题多发地
- **引用树搜索** — reference tree search：从疑似对象出发，找「谁还指着它」（水平）与「它指着的每个字节能否还原为合法对象指针」（垂直），第 11 章 Core Analyzer 的算法基础
- **悬垂引用** — dangling reference：引用/指针指向已销毁对象；4.3 实战故事的主题（与 UAF 同一枚硬币的两面）

## 1. 动机：调试器眼里的对象=字节+规则

第 1 章说过符号提供「类型」；本章回答「类型如何落到内存」。排障中最常见的四个瞬间，答案全在布局：

1. `print obj` 打出合理值但行为诡异——位域/padding/大小端翻译错误；
2. 虚调用跳进飞地址——vptr 被写坏（内存损坏的「高频受害者位」：对象头 8 字节）；
3. 同一对象在不同基类指针下地址不同——多继承 this 调整；
4. 堆里满是指向已释放对象的指针，怎么找肇事者——引用树搜索（4.4）。

## 2. 机制

### 2.1 对齐与大小端（4.1）

- 布局规则（Itanium ABI，MinGW/Linux 通用；MSVC x64 同族但 pack 默认 8）：成员按
  `max(自身 alignof, 前面积累)` 对齐补足 padding；整个结构体的大小是 `alignof` 的整数倍。
- 调试含义两条：其一，**padding 字节是未初始化读的高发区**（结构体整体 memcmp/哈希时踩雷）；
  其二，**对象头 8 字节（vptr）+ 紧随的成员**是最常被越界写命中的布局，「vptr 变 0x4141414141414141」
  几乎必为 memset 类覆写（呼应 [03-内存损坏.md](03-内存损坏.md) 实测）。
- 大小端本身不换字节，**解读方式**才换：抓包/共享内存/跨平台 core 分析时，先把「谁是宿主字节序」写进假设，
  再验证「整齐错位一格」型脏数据（4.3 与「神秘的字节序转换」故事共享该判据）。

🔧 **已实测**（本机 g++ 15.2 输出，x86_64 小端）：

```cpp
struct A { char c; int n; char d; };      // 12 字节：c@0 pad n@4 d@8 pad
struct B { int n; char c; char d; };      // 8 字节
struct Poly { virtual void f(); char c; };// 16 字节：vptr@0，c@8
uint32_t x = 0x04030201;                  // 内存字节序: 01 02 03 04（小端实证）
static_assert(alignof(A) == 4 && sizeof(A) == 12);
```

实际程序输出：`A=12 B=8 Poly=16 bytes: 01 02 03 04`。

GDB 里对照验证：`p/x *(unsigned*)&x` 与 `x/4bx &x` 两行输出即可完成一次字节序判定。

### 2.2 C++对象布局（4.2）

- 单继承无虚函数：子对象=基类子对象+派生新增，地址恒等；
- 有虚函数：对象头 vptr → vtable（含 offset-to-top、RTTI 指针、函数指针数组）；GDB `info vtbl obj`
  直接列出解析结果，`x/8a *(void**)&obj` 手工展开 vtable 是核心场景「虚调用去哪了」的标准手法；
- 多继承：一个完整对象多个地址（每个基类子对象一个），`static_cast` 编译期完成 this 平移——
  调试时看到 `p der` 与 `p (Base2&)der` 地址不同不是 bug；
- 虚继承：vptr 旁再加 vbase 偏移表，对象「谁负责初始化共享基类」成为运行时间接查表——
  布局最复杂也最易误读的一块，与 [../深度探索C++对象模型.md](../深度探索C++对象模型.md) 的
  章节一一互补（那本书讲**为什么这样设计**，本章讲**怎么在内存里认出来**）。

### 2.3 访问已经释放的数据（4.3 实战故事4）

对象视角的 UAF：内存可能已被**复用为另一种对象**。识别法：

- 读头部 8 字节：若是 vptr 候选（落在只读/数据段且指向合法 vtable）→ 新对象；若为 ASCII 脏值/
  小整数 → 仍是残骸或被数据块复用；
- 用「成员偏移一致性」假设：按旧类型解读各字段，若多个字段值「过于合理」（指针都在合理段内、
  整数都是小值），大概率没被复用，反之是「李代桃僵」；
- 该判断链的程序化即 4.4 的引用树搜索。

### 2.4 搜索引用树（4.4）

- **水平搜索**：给定对象 A，在堆/栈/全局区找所有值==&A 的字——回答「谁还持有我，为什么会用到已释放的它」；
- **垂直搜索**：给定可疑字 w，检验 w 可否作为某类型 T 的合法指针：把 w 当作 T*，逐成员递归验证
  其子指针也落在合法映射区（需要进程映射表知识，[06-进程镜像与CoreDump.md](06-进程镜像与CoreDump.md)）；
- 两向合围即可在 core 里重建「对象引用图」，配合第 11 章 Core Analyzer 落地为工具命令。

## 3. 权衡

- **布局稳定 vs 演化自由**：C++ 标准不规定成员顺序——依赖布局的代码（序列化、共享内存、调试脚本硬编码偏移）
  随编译器版本/命令行开关静默失效。对策：显式序列化层，或 `offsetof` 断言+双端校验。
- **`#pragma pack` 诱惑**：省几个字节 padding 换来原子性破坏（对齐 8 的 `std::atomic<int64>` 变未对齐→
  x86 上性能跳水、ARM 上直接 SIGBUS）。打包应只发生在跨 ABI 边界处。
- **虚表开销 vs 手工类型标签**：调试时「有 vptr 反而好认」——手工 tag 结构一旦 tag 被写坏无从发现，
  vptr 被写坏则虚调用立刻爆炸，现场更清晰。这是布局影响可调试性的实例。

## 最新演进与工业实践

- **C++23/26 布局话语**：`std::start_lifetime_as`（C++23）正式承认「把已有字节重新解释为对象」的场景
  （网络缓冲/共享内存），旧「placement new 覆盖裸内存」有了标准姿势；对象表示与 padding 位语义的
  严格化仍在演进（`std::layout_contiguity` ⚠️ 论文阶段，未并入）。
- **vtable 校验工具**：LLVM `-fbounds-safety`/VirtualGuard 类研究与 CFI（`-fsanitize=cfi`，clang 独有）
  把「vptr 被改写即劫持虚调用」变成编译期+运行期双保险。
- **GDB xmethods/pretty printer**：标准容器与自定义类型的美化打印（[09-拓展调试器能力.md](09-拓展调试器能力.md)）
  本质是「用 Python 重放本章布局规则」。
- **开源仓库逐点对照**：`llvm/llvm-project` clang/lib/AST 的 Itanium/MS ABI 实现（`ItaniumVTableContext.cpp`
  等）是布局问题的最终仲裁；`gdb` 的 `gnulib/std` 容器打印器直接消费本章偏移知识。
- **Windows 平台适用性**：本仓库双栈实测显示 MinGW(GCC) 走 Itanium ABI、MSVC 走自家 ABI——
  同一源码两种二进制里 vptr 位置一致（头部 8 字节），但多虚继承/名称改编差异大，跨栈分析前先确认符号文件同源。
