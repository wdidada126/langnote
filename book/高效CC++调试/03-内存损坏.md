## 核心概念速览（中英对照）

- **内存溢出/下溢** — memory overflow / underflow：读写越过对象边界（越上界=overflow，越下界=underflow），本书分栈/堆/全局三态讨论
- **访问已释放内存** — use-after-free (UAF)：读/写已归还给分配器的对象，值可能「看起来正常」而长期沉默
- **未初始化值** — uninitialized read：读从未写入的栈/堆内存，结果依赖历史比特，典型「换台机器就正常」
- **海森堡 bug** — Heisenbug：观测行为本身改变其发生条件的缺陷——优化、竞态、未定义行为三大成因
- **观察者效应** — observer effect：调试器附加改变时序/内存布局（allocators 走 debug 路径、线程暂停），让竞态与布局敏感 bug 消失
- **二分定位** — bisection：对「输入/代码/时间」三个轴做折半：何时引入（git bisect）、何处写入（watchpoint）、哪个输入（裁剪复现）
- **最小复现** — minimal reproducible example：删到「再删就不坏」的最小代码+环境，一半的调试工作量在此完成
- **假设-实验循环** — hypothesis–experiment loop：提出成因假设→设计只检验该假设的实验→按结果修正；本书方法论骨架
- **数据观察点** — data watchpoint：CPU 调试寄存器在目标地址被写时陷入，把「延迟暴露」拉回「当场抓获」
- **金丝雀值** — stack canary：帧内哨兵值，函数返回前校验，检测返回地址覆写（编译器自带，非通用调试手段）
- **字符串告警** — `-Wstringop-overflow`：编译期发现 `memcpy/memset` 尺寸越过对象边界——「不调试」的第一道闸（第 18 章主题）

## 1. 动机：崩溃现场是案发现场的「下游」

原书 3.2 的初始调查清单归结为一句话：**先接受「你看到的不是错误发生地」这个事实**。
栈/堆/全局三类内存的「写入→破坏→暴露」链路不同：

- 栈：帧被越界数组写坏 → 常在函数返回（rip 来自被改写的返回地址）或后续逻辑读脏值时暴露；
- 堆：踩到邻块元数据 → 在下一次 malloc/free 走链表时暴露（见 [02-堆数据结构.md](02-堆数据结构.md)）；
- 全局：相邻全局变量互相污染 → 表现为「另一个模块的变量莫名其妙」，最易误诊为逻辑 bug。

## 2. 机制与实测：覆写栈变量（对应 3.4 实战故事3）

🔧 **已实测**（本机 MinGW g++ 15.2，`-g -O0 -fno-stack-protector`）。构造：`guard` 与 8 字节 `buf`
同帧相邻，`memset(buf,'A',12)` 多写 4 字节恰好吞掉 `guard`：

```cpp
int guard = 0x1234567;
char buf[8];
std::memset(buf, 'A', 12);        // off-by-4
std::printf("guard=%08x\n", guard);
```

**第一层：编译器先说话**（未参与构建的运行结果，但告警真实输出）：

```text
warning: 'void* memset(void*, int, size_t)' writing 12 bytes into a region of size 8
         overflows the destination [-Wstringop-overflow=]
```

**第二层：不修告警直接跑**——`guard=41414141`。**无崩溃**，数据悄悄烂掉。这就是内存损坏的常态。

**第三层：watchpoint 当场抓获**：

```text
(gdb) break stackbug.cpp:6        # 停在 memset 之前
(gdb) watch guard                  # Hardware watchpoint 2: guard
(gdb) continue
Hardware watchpoint 2: guard
Old value = 19088743               # 0x1234567
New value = 1094795585             # 0x41414141 —— 'AAAA'
0x00007ffae095de18 in ucrtbase!memset () from C:\Windows\System32\ucrtbase.dll
```

一条 `continue` 完成「谁、何时、把值从什么改到什么」三问。注意停在 ucrtbase 内时
`print guard` 会报 `No symbol "guard" in current context`（当前帧无 DWARF 局部符号）——
用 `frame 1` 或直接看 Old/New 即可，这本身是「符号决定视野」的又一次实证（[01 篇](01-调试符号与调试器.md)）。

### 2.1 UAF 的两种脸色（本机实测）

同一份 `new→delete→继续写` 的小程序：

- 运行时统一时：**静默成功**，`printf` 打出写入值 7，exit 0——Windows 默认堆没有立刻解除提交，
  写到了仍映射的内存；
- PATH 混入 Git 自带 MinGW 的 `libstdc++-6.dll` 后：**段错误**，栈如 [02 篇](02-堆数据结构.md) 第 1 节所示全陷在
  ntdll 堆函数里——两个 CRT 堆各管各的账，跨堆 free 直接踩烂元数据。

结论：「不复现」和「换目录就崩」都优先怀疑**环境与分配器状态**，而不是「代码变了」。

## 3. 方法论：假设-实验循环在三类损坏上的落地

| 阶段 | 堆损坏 | 栈损坏 | 未初始化读 |
| --- | --- | --- | --- |
| 假设来源 | 崩溃在分配器内部→「元数据被写」 | 崩溃在返回/跳飞→「返回地址被写」 | 值随机但可重跑一致→「读而非写」 |
| 关键实验 | 遍历 bin 找脏指针（02 篇 2.4） | watchpoint 受害者变量 | 把嫌疑区 memset(0xCC) 重跑；MSan/valgrind |
| 二分轴 | 哪个分配点之后出现异常块 | 哪层栈帧先被污染 | 哪个字段最先被读到 |
| 工具 | ASan、MALLOC_CHECK_、Core Analyzer | 编译器告警、canary、观察点 | MSan、`-Wuninitialized`、g++ `-ftrivial-auto-var-init` |

原书 3.3「神秘的字节序转换」提供另一范式：**当数据「全都错位一格」时，怀疑翻译层而不是数据本身**
——大小端/序列化协议/类型宽度不匹配都会产生这种「整齐的错误」（与 [04-C++对象布局.md](04-C++对象布局.md)
的对齐/大小端节互读）。

### 3.1 Heisenbug 的三大成因（本仓库统一口径）

1. **优化**：变量被消除/复用，`print` 读到寄存器残影；单步跳跃。见 [05-优化后的二进制.md](05-优化后的二进制.md)。
2. **竞态**：调试器暂停改变线程交错——实测同一竞态程序 `-O0` 三跑皆错（counter=1074548/1506840/1231216，
   期望 2000000），`-O2` 三跑全对 2000000：**「发行版不出现」不等于不是 bug**。完整版见 [07-调试多线程程序.md](07-调试多线程程序.md)。
3. **未定义行为**：UB 的暴露依赖历史比特与布局；UAF 静默成功即典型。

## 4. 权衡

- **每步都上 Sanitizer？** 2 倍开销可常开（CI），10 倍开销（MSan/Valgrind）只用于疑难；见 10 篇工具对比表。
- **watchpoint 广度 vs 成本**：硬件观察点只有 4 个地址槽；大范围（如 64 字节对象）需分段或退回
  「页保护 + 异常处理」（mprotect/guard page）思路。
- **复现成本 vs 现场保全**：能复现就赢了一半；不能复现时，core/minidump 是唯一证人（[06 篇](06-进程镜像与CoreDump.md)）——
  先保现场再谈调试，这正是第 13 章崩溃上报机制的动机。

## 5. 相邻概念对比

- **内存损坏 vs 竞态条件**：前者破坏「值与元数据」，现场可事后取证；后者破坏「时序不变量」，错过即无痕——
  需要记录-回放（rr）或 TSan。判据：把线程数压到 1 后问题是否还在。
- **栈损坏 vs 堆损坏**：见上表；核心差异是布局可预测性（编译器决定 vs 历史依赖）。
- **调试内存损坏 vs 防内存损坏**：告警、`-Wstringop-overflow`、`std::span`/`at()` 边界检查、
  clang-tidy 属于「让损坏不发生」，第 18 章与 [12 篇](12-泄漏协程远程容器与预防.md)收束。

## 最新演进与工业实践

- **AddressSanitizer 正名**：K. Serebryany, D. Bruening, A. Potapenko, D. Vyukov,
  *AddressSanitizer: A Fast Address Sanity Checker*, USENIX ATC 2012（官方页已实测 HTTP 200；
  USENIX 论文不在 Crossref 注册 DOI——实测查无，故不给 DOI 而给会议名+页）。redzone+影子内存机制详解见
  [10-内存调试工具与CoreAnalyzer.md](10-内存调试工具与CoreAnalyzer.md)。
- **平台现状（本机实测）**：MinGW-w64 GCC 15.2 传 `-fsanitize=address` **链接失败**
  （`ld.exe: cannot find -lasan`）——该发行版未打包 ASan 运行时。Windows 双栈可用路径：
  MSVC `/fsanitize=address`（VS2019 16.9+ 起支持，链接 `/RTC` 之外的独立开关；版本号按微软文档
  `learn.microsoft.com/cpp/build/reference/fsanitize`，已实测可达 HTTP 200）或 clang-cl。
- **CI 前移**：clang-tidy / cppcheck 把 `memset` 越界、未初始化读变成 PR 评论；GitHub 代码扫描
  已内建 CodeQL。对应本章告警层（「编译器先说话」）的体系化。
- **生产采样**：GWP-ASan 抽样守卫（[02 篇](02-堆数据结构.md)演进节）+ Continuous Fuzzing
  （*Continuous Fuzzing with libFuzzer and AddressSanitizer*, SecDev'16，DOI 已实测：`10.1109/secdev.2016.043`）。
- **AI 辅助（⚠️ 前沿观察）**：LLM 已用于「根据脏值模式猜肇事函数」类辅助归因，公开研究见修复代理
  AutoCodeRover（arXiv:2404.05427，已实测存在）；确定性定位仍以 Sanitizer/watchpoint 为准。
