## 核心概念速览（中英对照）

- **内存管理器/分配器** — memory allocator：把 `malloc/new` 请求翻译成对 OS 大块内存（brk/mmap）切分的库
- **堆块/chunk** — heap chunk：分配器管理的基本单元，头部（大小+标志位）+ 用户区
- **ptmalloc（glibc 分配器）** — ptmalloc2：按大小分 fast/unsorted/small/large bins + tcache 的多空闲链表分配器
- **arena** — malloc arena：为降低多线程锁争用而设的多个独立堆管理域
- **TCMalloc** — Thread-Caching Malloc：Google 的线程缓存分配器：thread-local free list → central → page heap 三级
- **空闲链表** — free list：未使用块串成的链表；freed 块的「前/后邻指针」就写在块内用户区里
- **堆元数据** — heap metadata：chunk 头、bin 链表、页映射表等**分配器私有**的数据结构
- **堆遍历** — heap walking：沿 bin/链表把所有块走一遍，检查一致性、找损坏点、做用量统计（第 11 章 Core Analyzer 的核心功能）
- **多个堆** — multiple heaps：进程可同时存在多个分配器实例（静态链入不同分配器、Windows 多 Heap、`HeapCreate`）
- **毒化填充** — poison pattern：调试堆把 freed 内存填成可识别字节（Windows debug heap `0xDD`、glibc MALLOC_PERTURB_）
- **守卫页** — guard page：块边界放不可读写页，让 off-by-one 立刻撞页表异常而非悄悄扩散

## 1. 动机：为什么调试内存问题必须先懂分配器

内存损坏类 bug 的崩溃现场几乎总是「在 malloc/free 里面炸了」——调用栈顶端是
`_int_free`、`malloc_consolidate`、`RtlAllocateHeap` 之类的分配器内部函数，看起来和肇事代码毫无关系。
原因就在本章：**空闲块的元数据（大小、链表指针）与用户数据共用同一块内存**。一旦越界写/UAF 写
踩到邻块头部或已释放块内的链表指针，破坏会「冻结」，直到下一次分配器操作顺链表读到脏指针才崩。
不懂这套数据结构，你会把分配器当成凶手；懂了，你就知道去哪儿找血手印。

🔧 **已实测**（本机 MinGW，一个 UAF 写程序在不同运行时混载下崩进 Windows 分配器，栈顶全是 ntdll 堆函数）：

```text
Thread 1 received signal SIGSEGV, Segmentation fault.
#0  ntdll!RtlGetSuiteMask ()          ← 名字也不可信（无 PDB，最近导出符号）
#1  ntdll!RtlAllocateHeap ()
#2  ntdll!RtlFreeHeap ()
...
#6  msvcrt!free ()
```

两点教训：其一，崩在分配器≠分配器有 bug；其二，Windows 系统 DLL 无 PDB 时栈符号名可能整体错位
（符号化失败的另一副面孔，呼应 [01-调试符号与调试器.md](01-调试符号与调试器.md)）。

## 2. 机制

### 2.1 ptmalloc（2.1.1）

- 每个 chunk 前置 `size` 字段（低 3 位是 PREV_INUSE/IS_MMAPPED 等标志）；**空闲**小块的 fd/bk 指针
  写在用户区前 16 字节——这就是「free 之后指针域被改写」现象的出处。
- fast bins（LIFO，无合并）→ unsorted → small/large bins，外加 tcache（每线程）优先供给；
  分配路径决定「刚 free 的小块几乎立刻被同一地址复用」——UAF 读常读到「自己的旧值」而沉默。
- 堆顶收缩/合并（consolidation）时检查邻块 size 与 prev_size 一致性，不一致即 abort
  （`free(): invalid next size` 类消息），这类 glibc 报错消息本身就是**元数据自检**的产物。

调试侧可操作点：`MALLOC_CHECK_`（第 10 章）、`MALLOC_PERTURB_`（free 后把用户区填成指定值，
malloc 时反向填充，把「读 freed」从沉默变显式）、`mtrace`/`mallinfo`。

### 2.2 TCMalloc（2.1.2）

三级结构：thread-local cache（无锁，size class 单向链表）→ central cache（自旋锁，按 span 管理）→
page heap（以页为单位的大块，来自 sbrk/mmap）。size class 把请求向上取整（8/16/32…），
**`malloc(13)` 返回 16 字节**——「越界 3 字节不崩」的常见根源。调试模式
（`DEBUGGING=1` 重编）才会 quarantine、栈痕迹记录。Chromium 的分区分配器（PartitionAlloc）与
GWP-ASan 是这条路线的生产化后代。

### 2.3 多个堆（2.1.3）

进程视角的堆不是「一个」：静态链入的第三方库自带 mini-allocator、Windows 的默认堆+`HeapCreate`
私有堆、`dll` 各自 CRT 的堆（**跨 DLL 边界 free 即事故**）。排障动作：先判断指针所属堆
（对照模块映射表，见 [06-进程镜像与CoreDump.md](06-进程镜像与CoreDump.md)），再谈损坏。
本仓库实测的「Git 自带 libstdc++ 经 PATH 混入、new/delete 跨运行时」正是多堆错配的活案例
（细节与修复记录见 [03-内存损坏.md](03-内存损坏.md) 第 3 节）。

### 2.4 利用堆元数据（2.2）

把元数据当「免费的时间机器」：

- 从 chunk header 反推**邻块边界与 size class** → 猜申请尺寸，匹配「谁可能写到我头上」；
- 沿 unsorted/fast bin 走一圈 → 哪些块空闲、空闲多久（结合 tcache 顺序）；
- freed 块里的 fd/bk 若指向栈/代码段地址 → 大概率是溢出源而非随机脏数据；
- 第 11 章 Core Analyzer 的「垂直搜索」（地址→底层对象）就是这套手工流程的程序化。

## 3. 权衡

- **速度 vs 可调试性**：现代分配器的无锁线程缓存、size class 取整都为吞吐服务，代价是错误延迟暴露。调试选择：换 debug 分配器（guard 块、redzone、每块独立页）= 把「越界 3 字节」变成当场 SIGSEGV。
- **元数据位置**：写在块内（ptmalloc）省内存、损坏面大；集中存放（TCMalloc span 表、arena 表）抗
  单块越界，排障要会查集中表。
- **多个 arena 的取舍**：并发扩展性 ↑，但「堆损坏现场」分散在多块区域，遍历成本 ↑。

## 4. 相邻概念对比

| 维度 | 栈（第 3 章覆写案例） | 堆（本章） |
| --- | --- | --- |
| 布局决定者 | 编译器（帧内偏移固定、可查） | 分配器（历史依赖、运行时才知道） |
| 损坏暴露时机 | 常在函数返回/后续使用时 | 常在**下一次** malloc/free 时 |
| 主要武器 | 编译告警、watchpoint、canary | 元数据阅读、调试分配器、Sanitizer |
| 「读旧值」为何沉默 | 帧未复用 | free 块被同 size class 立刻复用 |

与 [../C++标准库/00-总览与阅读地图.md](../C++标准库/00-总览与阅读地图.md) 第 10 讲的 allocator：那里是
**标准接口层**（`std::allocator` 协议），本章是它**底下**的系统分配器；两层之间还夹着 operator new。

## 最新演进与工业实践

- **GWP-ASan（Chromium 出品，随 PartitionAlloc 开源）**：抽样把少量分配放到带 guard page 的
  「隔离槽」里，用可忽略的开销在生产环境捕获 UAF/溢出的**准确现场**——书后「元数据换现场」思想的产品化。
- **mimalloc（Microsoft）**：.NET/PowerShell 等采用其做分配器；`MI_DEBUG` 构建带完整 redzone
  校验，排障体验接近调试分配器。
- **Windows 段堆（Segment Heap）**：Win10+ 可选默认堆（`GetProcessHeap` 实验开关），链表元数据大幅精简，
  WinDbg 的 `!heap` 子命令族仍是标准入口；多堆问题在 Windows 上表现为 `@heap` 作用域符号。
- **C++23 `std::pmr` 资源**（[../C++标准库/00-总览与阅读地图.md](../C++标准库/00-总览与阅读地图.md) 演进节）：
  把「换分配器」变成换 `memory_resource`，测试里注入 `pool_resource`+统计即可复现「分配风暴」类性能 bug。
- **开源仓库逐点对照**：glibc 源码 `malloc/malloc.c`（ptmalloc 注释即教科书）、
  `google/sanitizers`（ASan 拦截器视角下的 malloc/free，见 [10-内存调试工具与CoreAnalyzer.md](10-内存调试工具与CoreAnalyzer.md)）、
  `microsoft/mimalloc`（调试 redzone 实现）。
