## 核心概念速览（中英对照）

- **调试符号** — debugging symbols：把机器码地址反向映射回源文件、行号、变量名与类型的元数据总称
- **DWARF** — DWARF debugging format：ELF/PE(MinGW) 中 `.debug_*` 段承载的跨平台调试信息标准，当前主流为 DWARF5
- **程序头/节区** — program headers / sections：链接器布局；调试段不参与执行，只被调试器读取
- **符号表** — symbol table（ELF `.symtab`/`.dynsym`，COFF）：函数与全局变量的地址-名字映射，是「最薄的一层符号」
- **PDB** — Program Database：MSVC 把调试信息放独立 `.pdb` 文件的方案，与 GCC「信息嵌在可执行文件内」相对
- **剥离** — strip：用 `strip` 删符号与调试段以缩小发布物；配合「分离调试信息」仍可事后还原
- **符号化** — symbolication：把裸地址/栈回溯翻译为 `函数名 + 源文件:行号` 的过程，崩溃上报系统的核心步骤
- **用户界面层** — UI layer：调试器三层结构的最上层（CLI/IDE/DAP），只发意图不碰被调试进程
- **符号管理模块** — symbol manager：解析并缓存 DWARF/PDB，向 UI 提供「名字↔地址/类型」双向查询
- **目标管理模块** — target/execution manager：经 ptrace(Windows DebugApi) 控制被调试进程，读写内存寄存器、装卸断点
- **数据断点** — watchpoint：靠 CPU 调试寄存器在「变量被写」时中断，区别于「执行到某地址」的断点
- **断点实现** — software breakpoint：GDB 在目标地址写入 `int 3`/`break` 指令陷入，因此改写了目标内存

## 1. 动机：为什么全书第一章不讲命令讲格式

调试器是「翻译官」。你提出「打印 sum」，它必须回答三个问题：sum 在哪个地址（位置表达式）、
地址里的位怎么解释成值（类型系统）、当前执行点算不算「停在第 5 行」（行号表）。这三个问题的答案
全部来自调试符号，而不是来自可执行代码。所以：

- 符号缺失/错位 → 「断点不工作」「变量全是 `<optimized out>`」「栈回溯只剩地址」——很多看似调试器
  的 bug 实为符号问题；
- 崩溃分析、core/minidump 后处理、容器与生产环境排障，都是「拿着现场 + 符号文件做翻译」；
- 理解调试器三层结构（UI / 符号管理 / 目标管理），才知道哪些能力取决于符号、哪些取决于内核接口。

## 2. 机制

### 2.1 DWARF 到底提供了什么

原书 1.1.2 用相当篇幅逐段讲 DWARF。抓住四张表就够日常使用：

| 段 | 回答的问题 | 常用入口 |
| --- | --- | --- |
| `.debug_info` | 变量/类型/作用域树（DIE） | GDB `ptype`、`info scope` |
| `.debug_line` | 地址→(文件,行) 映射，断点落点靠它 | GDB `info line`、`break file:line` |
| `.debug_str`/`.debug_line_str` | 字符串/路径表（DWO/DWP 打包） | `dwz`、`readelf --debug-dump=str` |
| `.debug_frame` / `.eh_frame` | 栈展开：如何从任意 PC 找回调用帧 | 异常处理与 backtrace 共用 |

MinGW 编出的 Windows PE 同样可以携带 DWARF 段（这是「同一格式、两种容器」的实例；MSVC 走 PDB/CodeView）。

🔧 **已实测**（本机 MinGW g++ 15.2，`-g -O0` 编译一个 11 行小程序后）：

```text
$ objdump -h stackbug.exe | grep debug
  9 .debug_aranges   00000080 ...
 10 .debug_info      00001af7 ...
 11 .debug_abbrev    00000203 ...
 12 .debug_line      00000124 ...
 13 .debug_frame     00000088 ...
 14 .debug_str       000000a3 ...
 15 .debug_line_str  0000037c ...
$ ls -la stackbug.exe stackbug_strip.exe   # strip -g 之后
87233 stackbug.exe
72279 stackbug_strip.exe                   # 调试信息约占 17% 体积
```

出现 `.debug_line_str` 说明已是 DWARF5 产出。

### 2.2 调试器三层结构（1.3）

- **UI**：GDB CLI、VS/CLion 图形界面、DAP（Debug Adapter Protocol）都只是第 1 层的不同皮肤；
- **符号管理**：懒加载 DIE（只解析当前编译单元）、类型缓存；原书 1.4.3 的「符号匹配自动化」即在此层做
  「符号文件与二进制是否同一构建」的校验（Build ID / PDB GUID+age）；
- **目标管理**：Linux 走 ptrace，Windows 走 WaitForDebugEvent 家族（DebugApi，见 [../C++代码调试的艺术.md](../C++代码调试的艺术.md) 第 10 章的操作视角）；
  断点=写 `int 3`，单步=设 EFLAG.TF 或硬件 step，观察点=DR0–DR3 调试寄存器。

### 2.3 三种调试信息载体：DWARF / PDB / core（本书贯穿线，1.4.4 前期铺垫）

| 载体 | 内容 | 产生时机 | 典型消费方 |
| --- | --- | --- | --- |
| DWARF | 类型、变量位置、行号、栈展开 | 编译期写进 ELF/PE（或 `.dwp` 分离） | GDB/LLDB |
| PDB | 同上 + 全程序类型库 | MSVC 链接期生成独立文件 | WinDbg/VS |
| core / minidump | **运行现场**：内存镜像+寄存器+（minidump 可选带栈/模块表） | 崩溃时由内核 dump | 事后离线分析 |

三者正交：现场（core）提供「是什么状态」，符号（DWARF/PDB）提供「状态叫什么名字」。第 6 章进程镜像与
附录 B（PE/Minidump）分别展开。

## 3. 权衡

- **内嵌 vs 分离**：GDB 读内嵌 DWARF 零配置；发行版做法是 `objcopy --only-keep-debug` 分离 +
  `--add-gnu-debuglink`，运行时体积不受影响（配合 debuginfod 见「最新演进」）。
- **`-g` 与 `-g3`**：多出的宏信息让「print 宏」可用，但 `.debug_info` 显著膨胀；`-g` 本身不影响代码生成。
- **strip 之后还能不能调**：函数级回溯靠 `.eh_frame` 可部分幸存（GDB 能给出函数名却无行号）；
  行级断点彻底失效——这是原书 1.4.6「断点不工作」最常见成因：断点设到了与运行实例**非同一构建**的二进制上。

## 4. 相邻概念对比

- **符号表 vs 调试符号**：`.symtab` 只有名字-地址；类型/变量/行号属 DWARF/PDB。`nm` 能看到的只是前者。
- **GDB 断点 vs 数据断点**：断点消耗「写指令的时机」，可无限个；watchpoint 消耗 4 个硬件调试寄存器，
  超数退化为软件模拟（慢几个数量级）——用第 3 章栈覆写案例体会其价值。
- **调试器 vs 记录器**：调试器是「拉」（attach、查当前态）；rr/eBPF 是「推」（全程记录再回放查询），见第 8、12 章文件。

## 最新演进与工业实践

- **debuginfod（elfutils）**：HTTP 服务按 Build-ID 分发调试符号，GDB 自动拉取系统库符号；主流发行版已默认开启，
  文档见 `sourceware.org/elfutils/Debuginfod.html`（已实测 HTTP 200）。这是「符号匹配自动化」（1.4.3）的工业化答案。
- **DWP 打包**：`dwz`/`gdb-add-index`/`.dwp` 在大工程中把逐二进制的 `.dwo` 合并，符号加载从秒级降到亚秒级；
  配合 `-gsplit-dwarf` 可执行文件立减体积。
- **DAP 统一前端**：VS Code / neovim / Zed 经 Debug Adapter Protocol 复用 gdb/lldb-dap，
  「UI 层」与「目标层」解耦已成事实标准（gdb 14+ 内置 `gdb --init-eval-command "_mi (no-op)"` 级支持，lldb-dap 独立组件）。
- **Windows 平台适用性（本仓库双栈视角）**：MinGW-w64 走 DWARF-in-PE，GDB 直读；MSVC 走 PDB，
  WinDbg/VS 直读，GDB 对 PDB 支持有限——同一份 DWARF/PDB 概念要在两套栈各配一次工具。
- **AI 辅助（⚠️ 前沿观察）**：2024–2026 出现 LLM 自动补全崩溃符号链与解读 DWARF 的工具探索
  （修复类代理如 AutoCodeRover，arXiv:2404.05427 已实测存在），但「符号正确性」仍是确定性工具的地盘。
