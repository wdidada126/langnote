## 三、键家族逐态重构（p244–261）

| 态 | 定义（转述） | 设计动作 |
|---|---|---|
| 候选键（245） candidate key | 能唯一标识行的最小字段组（唯一性+**不可约性**；元素细则见附录 C ✅p544） | 每表先穷举全部候选键 |
| 主键（253） primary key | 候选键中被**选中**者（确立规则汇编 ✅p545） | 按选键守则择一（见 3.1） |
| 替代键（260） alternate key | 落选候选键，**仍必须 UNIQUE+NOT NULL 存活** | 防"落选即弃"导致重复涌入 |
| 非键（261） non-key | 其余字段 | 进第 9 章字段规范流水线 |

### 3.1 选主键守则（p253–259 + 附录 C "Rules for Establishing a Primary Key" ✅p545）

- 选**单字段**优于复合（引擎与工具兼容性，本书明言的务实理由）；
- 选**永不变化**的业务值，否则用代理键（surrogate）：Hernandez 态度=**不得已而用之**，业务键的可预测性优先（对照 Date 代理键教义 ⚠️ 见 [../Database_Design_and_Relational_Theory/16-附录-主键冗余与论文回顾.md](../Database_Design_and_Relational_Theory/16-附录-主键冗余与论文回顾.md)——主键之争两极在盘）；
- 人人**记得住、说得清**（凡人判据再次上岗）。

### 3.2 Table-Level Integrity + Reviewing（p261–262）

"表级完整性"= 主键非空唯一 + 替代键存活 + 每行可标识三律检查单；"Reviewing the Initial Table Structures"把 07 章产出的每张表回炉过键检——13 章总复查的表级分项在此写定。

## 4. 🔧 类比实测：键三态的引擎执法（非本书引擎行为）

实验 D 组（`D:\develops\tmp\dbwave_w5_mmortals\exp_out.txt`）：

- **D1** SQLite 3.45.3：`email TEXT UNIQUE, ssn TEXT UNIQUE, PRIMARY KEY(staff_no)` 三候选键并立，重复 email → `UNIQUE constraint failed: staff.email`——**替代键必须执法**的最小演示；
- **D2** SQLite 特例（教学金矿）：`staff_no INTEGER PRIMARY KEY` 塞 NULL **未报错**——SQLite 的 INTEGER PRIMARY KEY 是 rowid 别名，NULL 被自动填号。⚠️ **非本书引擎行为、非通用 SQL 行为**，恰证 Hernandez"选键要看引擎兼容性"的务实警告；
- **D3** DuckDB 1.5.5：第二候选键重复 → `duplicate key "a@x.com"`（ConstraintException）——两引擎对替代键一致执法 ✅；
- **对照 A2**（FK 引用主键被拦，见 10 章）：键的"可引用性"是关系层的地基属性。

## 4.1 🔧 键执法矩阵速记（非本书引擎行为）

| 键职能 | 本书文书动作 | SQLite 3.45.3 实测 | DuckDB 1.5.5 实测 |
|---|---|---|---|
| 唯一性 | 候选键登录册 | UNIQUE 违约 `IntegrityError: UNIQUE constraint failed` | `ConstraintException: Violation PRIMARY KEY/UNIQUE` |
| 行标识 | 主键确立规则（附录 C） | PK=UNIQUE+NOT NULL；**INTEGER PRIMARY KEY 另开 rowid 别名后门**（🔧D2：插 NULL 被自动填号） | PK 严格执法，无 rowid 概念 |
| 可引用性 | FK 要素表（10 章回指） | 被引用列须 UNIQUE/PK（FK 执法需 PRAGMA 前提） | 同要求，报错自带键值 |
| 不可约性 | 去列测试（3.1） | 引擎无感知——纯文档判据 | 同左 |

- **矩阵读法**：前两行"引擎管得住"，第三行"引擎看前提"（SQLite 的 PRAGMA 开关），第四行"引擎完全不管"——键的四职能里恰好一半是文书专属，这就是 08 章必须先于任何 DDL 存在 🔧 实证理由；
- **可移植性警示**（误区 4 展开）：rowid 别名是 SQLite 独有人格——依赖"整数主键自动填号"的隐含语义做去重/排序/分页的 SQL，换引擎即漂移；逻辑键文档才是跨引擎资产。

## 六、常见误区

1. "每表自动加个 id"迷信：代理键无业务含义→用户验收（第 2 章目标四）断链，本书要求仅作最后手段；
2. 复合键里塞可空列：候选键完整性判据（附录 C 要素）当场否决；
3. 忘记替代键落地 UNIQUE：文档里写了候选键、DDL 里只建主键=13 章复查必揪出的"文档-执行偏差"；
4. 用 rowid 方言键跨引擎裸奔：🔧D2 的教训——键的可移植性是逻辑设计资产；
5. 把"主键越小越好"绝对化：小而不可记忆违反三优守则第三条——大小是务实权重不是律条；
6. 候选键穷举只做一个候选就交卷：3.2"回炉初检表结构"的触发器正是"候选键列不出第二个"；
7. 替代键只存在于文档：无 UNIQUE 落地的候选键在 13 章复查记为"未执法的键"。

## 核心概念速览（中英对照）

1. **候选键** — candidate key：唯一+不可约，每表先穷举再择主。
2. **主键** — primary key：被选中的候选键；单字段/不变/可记忆三优。
3. **替代键** — alternate key：落选候选键，UNIQUE 义务不灭。
4. **非键** — non-key：主/替之外的字段，进字段规范流水线。
5. **代理键** — surrogate key：无业务含义的人造键，不得已而用。
6. **自然键/业务键** — natural/business key：来自业务现实的候选键。
7. **表级完整性** — table-level integrity：每行唯一可标识的总检查。
8. **不可约性** — irreducibility：候选键去掉任何元素即失唯一。
9. **rowid 别名** — rowid alias（SQLite）：INTEGER PRIMARY KEY 特例，警示选键的引擎差异。
