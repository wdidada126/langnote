## 核心精讲（⚠️ 文档转述重构）

### 1. 为什么 PG 的"维护"是一门独立学问

MVCC 把 UPDATE 变成"插新行 + 标旧行死亡"（03 章元组头 xmin/xmax），DELETE 只标不删。于是：
- **死元组**要 vacuum 回收（页面重用、线指针整理）；
- **可见性**要靠快照判定，旧快照不能读被立即复用的空间 → 长事务是 vacuum 的天敌
  （`pg_stat_activity.xmin` 视角/`lxid`，07 章监控项）；
- **文件系统不缩**：vacuum 只归还页给 FSM 重用，`pg_repack`/VACUUM FULL 才还盘
  （03 章 relfilenode 换号的典型现场）。
这三条解释了为什么 MySQL 运维手册（对照 [../高性能mysql.md](../高性能mysql.md) 的 purge 章节）
在 PG 语境必须整体重写：purge 是后台常态流水，vacuum 是阈值触发 + 手工兜底的双轨制。

### 2. autovacuum：默认值是起点不是终点

```sql
-- 判读样例（⚠️ 转述）：谁最欠 vacuum
SELECT relname, n_dead_tup, n_live_tup, last_autovacuum,
       age(relfrozenxid) AS xid_age
FROM pg_stat_user_tables JOIN pg_class ON relname=relname
ORDER BY n_dead_tup DESC LIMIT 10;
```

- 触发公式：`threshold + scale_factor × 估计行数`；**亿行大表用默认 scale=0.2 等于放任膨胀到
  两成死元组**——大表改绝对阈值（scale→0.01~0、threshold 固定值）是本章第一教条 ⚠️。
- 成本限速：`vacuum_cost_limit/delay` 让 vacuum 自我节流，SSD 时代普遍放松；
  PG17 起对"扫完即弃"的缓冲策略优化（不挤热页）进一步降本 ⚠️ 转述。
- worker 并发 `autovacuum_max_workers` 不含 launcher，表多库多时看 `pg_stat_activity` 里
  autovacuum 的占比决定是否加 worker（重启参数）。

### 3. 冻结与回卷：不可协商的硬期限

XID 32 位循环使用，逼近上限会**强制 vacuum 并拒写**（`database is XID wrapped around`/
`embedded XID near wraparound` 告警线）。水位口径：`age(datfrozenxid)`（库级，autovacuum_freeze_max_age
默认 20 亿触发强制作业）与表级 `age(relfrozenxid)`。运维动作（⚠️ 转述）：
月检清单跑 `SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;`，
逼近 15 亿量级即对涉事库安排 `VACUUM FREEZE`（可选 `trim_xid` 式逐表降序法），**绝不留到紧急线**。
VM 的 all-frozen 位（03 章）就是"免再扫描"的进度条。

### 4. 索引/表在线整理

- `REINDEX INDEX CONCURRENTLY` / `REINDEX TABLE CONCURRENTLY`：不停写重建，代价是两遍扫描 +
  不能用于共享目录（PG14 起放宽部分限制 ⚠️ 转述）；损坏索引/B-tree 深度治理的常规拳。
- `pg_repack`（第三方，社区事实标准）：在线清表与索引膨胀，替代锁表的 VACUUM FULL/CLUSTER；
  注意它对 TRUNCATE 的触发器兜底（03 章换号风险的工具侧回应）⚠️。
- CLUSTER 慎用为大招：全表重写 + 索引重建，只在"读主导 + 局部性敏感"表评估。

### 5. 统计与膨胀计量

- `ANALYZE` 保鲜是计划质量的地板（05 章 PG16 Cookbook 性能线互证）；表达式索引需要单独
  `CREATE STATISTICS` 类扩展统计 ⚠️。
- 膨胀定量：`pgstattuple('tbl')` 给 dead_tuple_percent 精确账；粗账法=实际大小 vs
  `pg_size_pretty(行数×平均行长)` 对偶表。🔧 本机对照见下节。

### 6. 🔧 本机概念演示：删除之后空间去哪了（SQLite，非 PG 结论）

方法：Python sqlite3 **3.45.3**（本机实测，rollback-journal 模式），建 20k 行×120 字符文本表后
删掉 98.5% 行，分别看文件尺寸、freelist 与 VACUUM 效果（脚本存盘 `D:\develops\tmp\dbwave_w3_pgadmin\`）：

```
full:    2,662,400 B / 650 pages
DELETE 98.5% 行后: 2,662,400 B（分毫未缩），PRAGMA freelist_count → 644 页
VACUUM 后:          24,576 B / 6 pages（整库重写回收）
```

**可迁移概念与差异点**（✅ 方法论）：共性——"删除释放的是内部空间，不释放文件"（SQLite 的
freelist ≈ PG 的空洞 + FSM 记账）；差异——SQLite 的 VACUUM 是全库重写（≈ PG 的 VACUUM FULL 而非
普通 VACUUM），PG 的普通 VACUUM 永远不还盘、且受活跃快照约束不能回收仍被看见的死元组
（SQLite 无此 MVCC 负担）。一句话带走的判读法：**先分清工具属于"重用空间"档还是"归还磁盘"档** ⚠️。

## 常见坑与判读

| 现象 | 第一判读 | 取证动作（⚠️ 转述） |
| --- | --- | --- |
| 大表 n_dead_tup 常年几百万 | autovacuum 阈值/并发双不足，或长事务卡快照 | 查 `pg_stat_activity` 最老事务；调该表阈值 |
| "Emergency VACUUM" 日志刷屏 | 冻结水位告急（库/表级） | age(datfrozenxid) 排序定位，低峰 VACUUM FREEZE |
| VACUUM VERBOSE 说 "cannot remove tuples" | 死元组被旧快照钉住 | 找持有者：备库长查询/hot standby 反馈/wal_level 相关 ⚠️ |
| REINDEX CONCURRENTLY 中途失败 | 留 INVALID 索引占坑 | 查 pg_index.indisvalid，DROP 后重跑 |
| pg_stat_user_tables 数字"一夜归零" | 统计被 pg_stat_reset/崩溃清零 | 用快照差值监控，别信绝对值（07 章） |
| 维护窗口没做完 vacuum 业务高峰到 | 缺预估模型 | 用 dead_tup/速率估时长，成本限速调平（第 2 节） |

## 核心概念速览（中英对照）

1. **死元组** — dead tuple：被更新/删除但仍被快照可见的旧行版本，vacuum 的作业对象。
2. **表膨胀** — bloat：死元组+空洞造成的"尺寸>有效数据"状态。
3. **自动清理** — autovacuum：阈值触发的清理/分析进程族，参数逐表可覆写。
4. **触发公式** — threshold + scale_factor×rows：autovacuum 的作业开工线。
5. **成本限速** — vacuum cost limiting：以延迟换业务 IO 公平的自我节流。
6. **事务回卷** — XID wraparound：32 位事务号循环，PG 唯一"不改就拒服务"的硬期限。
7. **冻结** — freezing (VACUUM FREEZE)：把行标记为"对所有未来快照可见"，推进水位。
8. **冻结水位** — relfrozenxid/datfrozenxid + age()：回卷风险的进度条。
9. **在线重建** — REINDEX CONCURRENTLY：不停写的索引治理拳。
10. **pg_repack**：在线回收表/索引膨胀的社区标准工具（VACUUM FULL 替代）。
11. **pgstattuple**：膨胀精确计量的官方扩展。
12. **长事务** — long-running transaction：vacuum 的头号天敌，监控常驻项。

## 最新演进与工业实践

- **PG17**：VACUUM 顺序扫描改流式读缓冲（不再把整表灌进 shared_buffers），大表 vacuum 对热数据
  的扰动显著下降；`truncate` 阶段优化同批（⚠️ 转述，✅ 入口 https://www.postgresql.org/docs/release/17.0/ 实抓 200）。
- **PG16 及前**：单表 vacuum 可并行（`PARALLEL` 子句/autovacuum 并行参数）、`VACUUM-INSERT` 竞态缓解
  （vacuum 的 truncation 阶段不再钉住全表扫描 ⚠️ 转述）。
- **反回卷工具线**：`tid` 冻结式分批、社区脚本 trimxid 类长期流传；云厂商托管实例多数把
  autovacuum_freeze_max_age 托管调低并加告警（RDS 文档口径 ⚠️ 转述）。
