## 核心精讲（⚠️ 文档转述重构）

### 1. 两条正交路线

- **逻辑备份**：`pg_dump -Fc -j4 -d app > app.dump`（自定义压缩格式，可并行、可选择性还原
  `pg_restore -j4 -L` 列表编辑）；`pg_dumpall` 只管全局对象（角色/表空间）。性质是"导出再导入"，
  恢复时间 ∝ 数据量 × 索引重建成本，TB 级慎作主路线；但它是跨大版本升级与清膨胀的万能胶（02/06 章）⚠️。
  PG16 起 `pg_dump` 支持 `--sync-method` 等细节增量 ⚠️。
- **物理备份**：`pg_basebackup -D /backup/base -X stream -P` 拷贝数据目录 + 备份期间 WAL
  （03 章文件拓扑即其作用域）。**单独一份 basebackup 只能回到"备份结束点"**，要任意时刻恢复必须配
  WAL 归档（下一节）。一致性来源不是"文件不改动"而是"日志重放抹平"（🔧 类比见第 5 节）。
  PG15+ 备份底层协议用 `pg_backup_start()/pg_backup_stop()` 两阶段（非独占式，不再阻塞
  清理旧 WAL 的 checkpoint ⚠️）。

### 2. PITR 三件套与恢复定靶

```conf
# postgresql.conf（主库侧）⚠️ 转述
archive_mode = on
archive_command = 'test ! -f /arch/%f && cp %p /arch/%f'
```

恢复侧在新数据目录放 `recovery.signal` +（recovery.conf 自 PG12 起已废除）：
`restore_command` 从归档取段、`recovery_target_time | recovery_target_xid |
recovery_target_name`（配合 `pg_create_restore_point('before_release')` 打锚）、
`recovery_target_action='promote'|'pause'`。三种常见靶型：误删回拨（时间点）、发布锚点（命名）、
一致性校验（pause 后只读检查再 promote）。备份提速与保留策略（7 天全量 + 归档）在第 4 节工具位展开。⚠️

### 3. 归档空间的账

`wal_status`（`pg_replication_slots`）与 `pg_archiver_stats`/归档目录监控：孤儿槽与失败
archive_command 是磁盘写满的两大惯犯（07 章监控必配告警项）。`max_slot_wal_keep_size`
给槽钉 WAL 设上限（超限槽失效、复制断，换磁盘活命）——**"保复制还是保磁盘"写进参数即政策** ⚠️。

### 4. 工具矩阵与 PG17 增量备份

| 维度 | 原生 pg_basebackup | pgBackRest | Barman |
| --- | --- | --- | --- |
| 增量 | PG17 起 `--incremental`（配合上一全量的 manifest）⚠️ | 原生支持（diff/incr） | 配合 rsync 快照 |
| 并行/压缩/加密 | 有限 | 强 | 中 |
| 保留策略/GC | 无 | 有 | 有 |
| 仓库形态 | 目录 | 本地/S3 多仓库 | 本地/S3 |
（后两列 ✅ 仓库主页实抓 200：https://github.com/pgbackrest/pgbackrest ；⚠️ Barman 特性为文档转述。）
选型判据：**备份窗口、恢复演练自动化、对象存储直传**三项谁一票否决谁。

### 5. 🔧 本机概念演示：日志检查点与在线热备（SQLite，非 PG 结论）

方法：Python 3.13.2 内置 **sqlite3 3.45.3**（本机实测），WAL 模式下灌 5000 行，观察 -wal 附属日志文件、
执行检查点、再走在线备份 API（脚本存盘 `D:\develops\tmp\dbwave_w3_pgadmin\demo.py`）：

```python
c2 = sqlite3.connect("pgd_ch5.db"); c2.execute("PRAGMA journal_mode=WAL")
# INSERT 5000 rows
os.path.getsize("pgd_ch5.db-wal")            # → 98912 B（未检查点的"待回放日志"）
c2.execute("PRAGMA wal_checkpoint(TRUNCATE)") # → (0, 0, 0)  [busy, log, checkpointed]
os.path.getsize("pgd_ch5.db-wal")            # → 0 B（日志已并回主文件并截断）
dst = sqlite3.connect("backup.db"); c2.backup(dst)
dst.execute("PRAGMA page_count")             # → 22 == 源库 22（API 内带读锁的页级一致拷贝）
```

**可迁移概念**（✅ 方法论）：①"数据文件 + 待回放日志"两段式状态是 WAL 型引擎的共同形态——
PG 的 pg_wal 未归档段/检查点与此同构，**检查点前拿的备份必须带上日志才自洽**，解释了 `-X stream`
参数为什么存在；② `wal_checkpoint(TRUNCATE)` 的返回三元组对应 PG 里
`pg_stat_checkpoints`/`pg_current_wal_lsn()` 的"推进了多少"判读习惯；③ `backup()` API 的
"边读边防写坏"正是 `pg_backup_start/stop` 协议要解决的同一问题。SQLite 结论不背书 PG 数字与语义细节。

## 常见坑与判读

| 现象 | 第一判读 | 取证动作（⚠️ 转述） |
| --- | --- | --- |
| 归档目录暴涨 | archive_command 静默失败堆积 pg_wal | `pg_stat_archiver.failed_count`；再查目标盘权限 |
| 恢复卡在 "waiting for WAL" | restore_command 取不到段（归档不完整） | 核对段号连续性；未来得及归档的段还在主库 pg_wal |
| basebackup 单独还原数据"倒退" | 未接归档链，只能到备份结束点 | 属预期；配 PITR 链或缩短全量周期 |
| pg_dump 中途报错 "canceled" | 长事务阻塞快照清理/超时 | 查 `pg_stat_activity` 老事务；错峰或用 --no-sync 类豁免 ⚠️ |
| 备份任务总"成功"但恢复失败 | 从未演练 | 建还原验证流水线：pg_verifybackup + 定期恢复到临时实例跑校验 SQL |
| 复制槽导致磁盘满 | 钉住的 WAL 不清 | `wal_status='lost'` 告警 + max_slot_wal_keep_size 兜底 |

## 核心概念速览（中英对照）

1. **逻辑备份** — logical backup (pg_dump)：对象级导出，跨版本与选择性还原的万能胶。
2. **基础备份** — base backup (pg_basebackup)：数据目录级物理拷贝，PITR 链的锚。
3. **持续归档** — WAL archiving：archive_command 把 16MB 段送往仓库，任意时刻恢复的前提。
4. **时间点恢复** — PITR：basebackup + 重放归档到 recovery_target_* 定靶。
5. **恢复信号** — recovery.signal：PG12+ 进入恢复模式的开关文件（recovery.conf 已死）。
6. **还原命令** — restore_command：恢复期从归档取段的脚本位。
7. **恢复锚点** — restore point (pg_create_restore_point)：命名靶心，发布窗口标配。
8. **备份清单** — backup manifest / pg_verifybackup：文件级校验与离线验真。
9. **复制槽** — replication slot：钉 WAL 保订阅者，孤儿槽=磁盘炸弹（wal_status 监控）。
10. **增量备份** — incremental backup：PG17 起原生 `--incremental`，基于上次 manifest 差集 ⚠️。
11. **预写日志** — WAL：备份一致性的最终仲裁（🔧 类比见本章第 5 节）。
12. **恢复演练** — restore drill：把备份 SLA 从"文件存在"升级为"服务可回"。
