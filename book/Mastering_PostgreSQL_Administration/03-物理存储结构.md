## 核心精讲（⚠️ 文档转述重构）

### 1. 三层定位：库 → 文件 → 页

`CREATE TABLE` 产生的不是"库里的对象"而是**磁盘上的文件族**：主文件 + 可选 `_fsm`/`_vm`/`_init` fork。
文件名不用表名用 `relfilenode` 数字，链路：

```sql
SELECT pg_relation_filepath('orders');      -- base/16384/24577 之类 ⚠️
SELECT relfilenode, reltable FROM pg_class WHERE relname='orders';
```

relfilenode 在 TRUNCATE/VACUUM FULL/REINDEX 时会换号（旧文件 unlink）——**"表膨胀治理会换身份证"**
是 06 章维护与 08 章迁移工具选型（基于文件级的同步为何被 TRUNCATE 打穿）共同的关键事实。⚠️

### 2. 8KB 页解剖

页 = PageHeaderData（24B）+ ItemId 线指针数组（页头向下长）+ tuple 区（页尾向上长）+ Special 区
（索引页放 B 树页级信息）+ 中间空洞。三个高频字段（⚠️ 转述）：
- **pd_lsn**：页内最近修改的 WAL 位置——崩溃恢复时"页比日志新就丢日志记录"的比对锚；
- **pd_checksum**：开了 data checksums 后的页 CRC（02 章装机决策的兑现处）；
- **pd_lower/pd_upper**：线指针/元组的生长边界，空洞大小 = 页内可用连续空间；
  删除行只把 ItemId 标 DEAD（线指针复用），**页不会自动缩小**——表空间"只涨不缩"的物理根源。

行堆元组：23B 元组头（含 xmin/xmax/cid/ctid）+ 对齐填充 + 用户列；一行两个 int 实际占 ~32B，
"行很便宜、页很贵"的空洞会计问题由此展开 ⚠️。页内碎片整理靠 **vacuum 的 line pointer 回收**（06 章）。

### 3. FSM 与 VM：两张"元数据小抄"

- **_fsm**：每页 1 字节的 0–255 空闲档位图（四档映射），INSERT 找位置先看 FSM，避免全表扫页头；
  它的准确度依赖 vacuum 回填，长事务积压时"FSM 说有空页、页实际没空"导致插入退化探测 ⚠️。
- **_vm**：每页 2 个位（all-visible / all-frozen）。all-visible 让**index-only scan 免回表验行**；
  all-frozen 让 vacuum 跳过该页（冻结水位推进的物理凭据，06 章反冻结一线）。VM 太旧 → IOS 回表，
  监控里表现为"有覆盖索引还大量 heap fetches"（pg_stat_user_tables.pd_fetch 对偶）⚠️。

### 4. TOAST 与分段

单行超过 ~2KB（页的 1/4 强制度，阈值 1996B）即把大列切 ~1998B chunk 存入
`pg_toast_<oid>`，主行留 16B 指针；策略 EXTENDED（压缩+外置）/EXTERNAL/MAIN/INLINE ⚠️。
关系文件按段切：`24577`、`24577.1`…每段上限 1GB。物理拓扑的"库→段→扩展(32页/256KB)→页"四级
与 06 章膨胀测量、05 章文件级备份粒度直接相关。

### 5. 🔧 本机概念演示：页头是取证第一站（SQLite，非 PG 结论）

方法：Python 3.13.2 内置 sqlite3 **3.45.3**（本机实测），建表灌 300 行 80 字符文本后**直接按二进制读文件头**
（`struct.unpack` 官方布局），对照 PG"页头放 LSN/校验和"的设计：

```python
c = sqlite3.connect("pgd_ch3.db")
c.executescript("CREATE TABLE t(id INTEGER PRIMARY KEY, s TEXT); INSERT ...")  # 300 行
h = open("pgd_ch3.db", "rb").read(100)
```

实测输出（🔧 2026-09-27，脚本存盘 `D:\develops\tmp\dbwave_w3_pgadmin\demo.py`）：
- `PRAGMA page_size` = **4096**（对比 PG 默认 8192——页大小是引擎级装机常量，SQLite 可 per-db 改、PG 编译期定 ⚠️ 类比）；
- 偏移 0：魔数 `SQLite format 3\0`；偏移 16 回读页大小 **4096**（头内自描述，同 PG 控制文件思路）；
- 偏移 24 文件修改计数 **2**（对应 PG 页头 pd_lsn 的"新旧裁决"职能——两引擎都要回答"这份页/日志谁新"）；
- 偏移 40 schema cookie **1**（对应 PG 系统目录快照失效检测的思路）；
- 文件 **36864 B = 9 页**（300 行×80B ≈ 24KB 数据 + 页头/B 树分叉开销，空洞会计肉眼可见）。

**迁移出的概念**（✅ 方法论，⚠️ 非 PG 数字）：任何页式引擎的 DBA 取证第一步都是"头 → 页 → 行"的
降级阅读；PG 侧工具位是 `pageinspect` 扩展（`get_raw_page()` 把页交给你 hex 解剖）。

## 常见坑与判读

| 现象 | 第一判读 | 取证动作（⚠️ 转述） |
| --- | --- | --- |
| 表文件"莫名"变成新 relfilenode | TRUNCATE/VACUUM FULL/CLUSTER/REINDEX 换号 | 对照事件时间线；文件级 CDC 要防打穿（09 章呼应） |
| DELETE 98% 行文件不缩 | 空洞+线指针保留是特性不是 bug | 要缩身用 VACUUM FULL（锁表）或 pg_repack；🔧 类比见 06 章演示 |
| index-only scan 仍大量回表 | VM all-visible 位太旧 | 查 pg_stat_user_tables.n_mod_since_analyze/真空龄，调 autovacuum（06 章） |
| 大字段查询反而变慢 | TOAST 外置后多一跳索引查找 | 看 attstorage 策略，高频小切片用 MAIN/INLINE 权衡 |
| 磁盘监控找不到"表" | 看到的是 base/<db>/<filenode> 数字名 | 系统目录建映射脚本（07 章监控的预处理） |

## 核心概念速览（中英对照）

1. **数据目录树** — PGDATA topology：base/global/pg_wal/pg_xact… 的文件系统全景。
2. **关系文件号** — relfilenode：表在磁盘上的身份证号，TRUNCATE/重写会换号。
3. **页头** — PageHeaderData：pd_lsn/pd_checksum/pd_lower/pd_upper 组成的页级元数据。
4. **线指针** — ItemId (line pointer)：页内槽位间接寻址，删除行只改它不动数据本体。
5. **元组** — heap tuple：23B 头 + 列体；xmin/xmax/ctid 是 MVCC 与行定位的坐标。
6. **空闲空间图** — FSM fork：页级空闲档位小抄，INSERT 寻位加速器。
7. **可见性图** — VM fork：all-visible/all-frozen 两位图，index-only scan 与 vacuum 跳页的依据。
8. **TOAST** — The Oversized Attribute Storage System：>1996B 列切 ~2KB chunk 外置存储。
9. **段文件** — segment：关系文件 1GB 一切，`.1/.2` 后缀续号。
10. **扩展区** — extent：32 页/256KB 的分配单位，空间增长以它为步长 ⚠️。
11. **页校验和** — checksum：initdb 决策、页级损坏检测，pd_checksum 字段的兑现。
12. **pageinspect**：官方扩展，把上述结构变成可 SELECT 的取证工具。

## 最新演进与工业实践

- **PG16/17 稳定线**：页/TOAST/FSM/VM 结构多年未变；变的是周边——PG16 的 `pg_stat_io` 把"哪类后端
  在做哪类 IO"对到本章的对象粒度（07 章衔接）⚠️ 转述，官方口径 https://www.postgresql.org/docs/release/17.0/ （✅ 实抓 200）。
- **PG18 异步 I/O**：AIO 子系统重排"backend 读页"的执行方式（io_method=worker/io_uring），
  页格式不变但**页读取的并发画像变了**，容量规划/监控口径需跟进 ⚠️ 转述
  （https://www.postgresql.org/docs/current/release-18.html ✅ 实抓 200）。
- **工具链**：pageinspect + pgstattuple（膨胀定量，06 章用）持续随主包；第三方可视化如
  pgadmin 的 ER 侧不碰页级，页级浏览器生态仍以官方扩展为事实标准 ⚠️。
- **工业实践**：云盘 4K/16K 扇区与 PG 8K 页的写放大问题（RAID stripe unit 对齐）仍是选型检查项；
  16kB 块编译（`--with-blocksize=16`）在老 PG 的讨论未随块选项移除而死——PG12 起固定 8KB 的口径
  在团队文档里要统一 ⚠️ 转述。
- **取证数字复核入口**：本章 🔧 输出可在 `D:\develops\tmp\dbwave_w3_pgadmin\demo_out.txt` 重放验证
  （repo 外零产物纪律）。
