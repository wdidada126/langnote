## 1. 一个古老的两分法：OLTP 与 OLAP

数据库工业长期把负载劈成两半：

| 维度 | 联机事务处理 OLTP | 联机分析处理 OLAP |
|---|---|---|
| 服务对象 | 业务前台（下单、支付、状态变更） | 决策后台（报表、集市、数据仓库） |
| 操作形态 | 高频短事务，点查点写 | 低频长查询，大范围扫描聚合 |
| 数据新鲜度 | 最新一行（read-your-writes） | 秒~天级可容忍 |
| 存储布局 | 行式为主，B 树索引 | 列式为主，扫描压缩友好 |
| 一致性 | 强一致、ACID | 快照级、最终一致多可接受 |
| 失败代价 | 丢一笔即事故 | 晚一小时多可解释 |

这个两分法在仓库时代有充分理由：分析扫描会把事务缓冲池冲垮、长查询锁住写路径，
所以业界宁可搭一条「事务库 → ETL → 数仓」的搬运管线，代价是**新鲜度**与**架构复杂度**。

## 2. 操作分析（Operational Analytics）是什么

操作分析指：**把分析能力前移/下沉到事务数据现场，让"运行中的业务"本身可被即时查询与决策**。
典型触发场景（均为通识转述 ⚠️，非原书列举）：

- 风控/反欺诈：在交易链路上实时评分，不能等 T+1 数仓；
- 个性化运营：客服/营销面板需要「此刻」的聚合视图；
- 运维监控与业务指标：对同一份事实表既做点查又做聚合；
- 决策自动化：分析结果直接回写业务库，驱动下一个事务（闭环）。

概念坐标：它站在三个传统的交叉点上——HTAP（同库混合）、流处理（数据在动中算）、
数据集成（CDC/ELT 让两地数据同步）。本书题目中的「Rise」即指这三条线在 2020 年前后的汇流 ⚠️。

## 3. 分离为什么开始松动

1. **硬件前提变了**：内存廉价 + NVMe 吞吐，使「同一份数据两种访问模式」不再必然互相踩踏；
2. **新鲜度成为产品功能**：报表可以等，「推荐/风控」不能等——分析输出进入了事务路径；
3. **搬运管线太贵**：ETL 的 schema 漂移、延迟、成本不断爆出事故，「少搬数据」有直接经济价值；
4. **引擎技术供给跟上**：行存引擎长出列存索引/物化视图（见 05），日志长出可订阅的解码接口（见 03），
   湖仓格式长出流式提交协议（见 07）。

## 4. 一张「新鲜度—耦合度」定位图

把方案按「分析距事务数据多近」排序（本目录通用地形图，⚠️ 非原书图表）：

```
耦合度/新鲜度 由低到高：
T+1 数仓  →  准实时 ETL/ELT  →  CDC+流聚合  →  湖仓流式表  →  同库列存/HTAP  →  同进程嵌入式分析
(Redshift 类)   (管道分钟级)     (秒级, 见03)    (分钟→秒级, 见07)   (亚秒级, 见02)      (即时, 见05)
```

每往右一格，**新鲜度**上升、**搬运**下降，但**对生产库的侵入/风险**与**引擎选型约束**上升。
操作分析的工程本质就是在这条轴上为具体业务选一个「够新且可控」的刻度。

## 5. 术语校准：操作分析 ≠ 全部同义词

- **Operational Analytics**：目的论命名（服务于运营决策的分析），可以跨库实现；
- **HTAP**：架构论命名（一个引擎同时吃 OLTP+OLAP），是实现操作分析的一种路线（见 02）；
- **Real-time Analytics**：时限论命名（强调延迟 SLA），含流式与同库两条实现路线；
- **Zero-ETL**：2022 年后云厂商营销命名（免搬运），本质是把「耦合度」拉满的商业化包装。

四者外延交叠但出处不同，读任何一本 2020 年前后的书都要先确认作者用的是哪个词。

## 8. 四种常见认知误区

**误区一：「上了 CDC 就是操作分析」。**
CDC 只解决「数据到过分析侧」这一步；若分析侧本身是 T+1 调度的批作业，端到端新鲜度并未改变。
操作分析的判据在**端到端 SLA 与决策回路**，不在某条管道的有无。

**误区二：「HTAP 等于取消数仓」。**
即便同库能跑聚合，仓库侧的治理职责（口径统一、历史版本、访问控制、成本隔离）不会消失；
2020 年前后的多数务实方案是「HTAP 承接分钟级运营视图 + 仓库承接全量口径」，各守一段新鲜度区间
（湖仓侧的镜像论述见 07）。

**误区三：「同库混合零风险」。**
分析查询进入事务库意味着：缓冲池污染、长读事务拖住 vacuum/checkpoint/日志截断、
突发聚合挤占前台延迟预算。06 的 🔧 实验（WAL 下写者不再被读者挡在门外）说明了**可行性**，
也别忘了它同时演示了**读者与写者从此互相可见彼此的资源占用**——这正是需要资源隔离/只读副本的原因。

**误区四：「新鲜度越高越好」。**
秒级与毫秒级之间往往差一个数量级的成本；业务侧很多决策的真实需求是「一小时内不再变」而不是
「此刻」。选刻度（§4 的轴）而不是追极限，是这类架构评审里最省钱的一句话。

## 核心概念速览（中英对照）

- **操作分析** — Operational Analytics：让运行中的业务数据可被即时分析并反哺业务决策的能力集。
- **联机事务处理** — OLTP：高频短事务负载，强调强一致与点查点写效率。
- **联机分析处理** — OLAP：大范围扫描聚合负载，强调吞吐与新鲜度可放宽。
- **新鲜度** — Data Freshness/Staleness：分析视图落后于生产数据的程度，操作分析的核心 SLA 维度。
- **耦合度** — Coupling：分析引擎与事务引擎共享存储/进程的程度，本目录定位轴的另一维。
- **搬运管线** — ETL/ELT Pipeline：分离时代的连接组织，也是操作分析试图缩短的对象。
- **HTAP** — Hybrid Transactional/Analytical Processing：同一引擎同时承载两种负载的架构路线。
- **零 ETL** — Zero-ETL：云厂商对「免搬运」数据库直连能力的后起营销命名。
- **闭环决策** — Closed-loop Decisioning：分析输出直接写回业务路径触发新事务的形态。
- **读写两难** — Read/Write Interference：分析扫描与事务写互相干扰的经典问题，一切路线的动因。

## 最新演进与工业实践

到 2024–2026，「操作分析」一词的商业浓度下降、技术浓度上升，分化为三条可见主线：

1. **命名迁移**：云厂商把方案装进「零 ETL」叙事——2022 年 AWS 率先在事务库与 Redshift 间推
   免管道直连；其官方文档入口 https://docs.aws.amazon.com/redshift/latest/dg/ 可达（curl -sI 200，
   具体 zero-ETL 子页经跳转 ⚠️）；同类能力各云（⚠️ 平台行为不作本机实测）陆续跟进。
2. **论文线锚点**：HTAP 分类综述见 Muehle 与 Jaedicke（SAP/HPI 系）
   "Classical and Modern Research in Hybrid Transaction/Analytical Processing — A Survey"，
   SIGMOD Record，2020 年（⚠️ DOI 未能经 api.crossref.org 校验通过，故只记标题+载体+年份）；
   更早的「一套架构同时服务事务与分析」主张常归于 M. Stonebraker（IEEE Data Engineering Bulletin，2014，
   ⚠️ 无 DOI，转述）。
3. **工业落地面**：PostgreSQL 物化视图+逻辑解码、MongoDB Change Streams、TiDB 行列双存
   等机制在 2020 后全部进入稳态版本（详见 02/03/06 各节官方 URL 核验结果）。
