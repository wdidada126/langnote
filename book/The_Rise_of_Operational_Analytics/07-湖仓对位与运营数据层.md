# 07 湖仓对位与运营数据层

> 主题重构笔记（非原书章对位，⚠️ 降级声明见 [00-总览与阅读地图.md](00-总览与阅读地图.md) §2）。
> 本篇执行「操作分析 ⇄ 湖仓对位」硬义务：湖仓与 HTAP 是同一枚硬币的两面还是两条道路？

## 1. 对位总公式

**HTAP 把分析拉到数据身边；湖仓把数据送到分析身边。**
两者的收敛点是同一个东西：一份可被事务引擎与分析引擎**同时承认**的版本化数据。

| 维度 | HTAP/同库路线（02/05） | 湖仓路线（波6 在盘对位） |
|---|---|---|
| 数据位置 | 生产库内/旁路 | 对象存储+开放表格式 |
| 新鲜度上限 | 亚秒~秒（D1/D2） | 提交间隔（分钟→秒，压缩中 ⚠️） |
| 一致性单位 | 事务 | 快照/表提交（原子替换元数据） |
| 隔离性 | 与生产共命运（06 §3 钉住风险） | 天然物理隔离 |
| 历史可重放 | 受日志保留限制 | 时间旅行/多版本（格式自带） |
| 治理位点 | 库权限体系 | 元数据/目录层（Polaris/Glue 类） |

结论（⚠️ 本目录判断）：2020 年本书叙事的「崛起」主战场在 D1/D2；到 2024–2026，
相当部分运营分析需求被 **D4+流式湖表**截流——因为它用「稍旧一点」买断了「不伤害生产库」，
而多数业务决策档位本就不需要亚秒（01 §8 误区四的制度化版本）。

## 2. 湖仓侧的「运营化」改造清单（转述 ⚠️，细节以官方文档为准）

- **提交间隔压缩**：流式写入器（Flink 型）把湖表新鲜度从「天」拉进「分钟~秒」，
  盘上专册 [../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md](../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md)
  正是「LSM+湖表」的HTAP化样本；
- **行级变更入湖**：equality/positional deletes 与 merge-tree 表类型
  （规范 https://iceberg.apache.org/spec/ ✅ curl 200）；
- **变更数据出口**：湖表增量读（read changes）让「湖」反向成为 CDC 源——
  数据曾流向湖，现在从湖再分发（⚠️ 版本细节以规范为准）；
- **低延迟查询面**：OLAP 引擎直读湖格式（Trino/ClickHouse/DuckDB 各线），
  盘上对位 [../Trino_The_Definitive_Guide_2e/00-总览与阅读地图.md](../Trino_The_Definitive_Guide_2e/00-总览与阅读地图.md)、

## 3. 运营数据层（ODS 的另一含义）在两条路线中的形态

操作分析落地时常见的「中间层」：从生产系统到消费端之间的**运营视图存储**。两条路线各自长出的形态：

1. 库内形态：物化视图/摘要表/影子表（D2，02 §4 维护税矩阵管辖）；
2. 库外形态：Kafka 压缩 topic + 物化存储（P3，04 §2 图的中枢）或湖表 + 服务层（D4）。

判别问题只有一个：**该层的正确性由谁背书**——生产事务域（同库）还是重放确定性（外部投影）。
前者新鲜但耦合，后者解耦但新鲜度=管道延迟。

## 4. 「Zero-ETL」是湖仓对 HTAP 的侧翼进攻

## 6. 🔧 类比实验登记（非本书引擎/平台行为）

- **E1/E2 的湖仓读法**：06 的 WAL/rollback 对照在湖仓语义下对应「追加+原子提交 vs 原地改写」：
  湖格式选追加（快照替换），于是读者永远不被写者挡路——与 🔧 E1 的 WAL 行为同构；
  而 compaction（原地整理）正是湖仓版的「journal 检查点」，同样要付「读者撞上整理窗口」的税
  （06 §2 结论 3 的跨形态平移）。本条为**推理类比**，非新增计时数据 ⚠️。

## 6.1 湖仓承接操作分析的三个真实缺陷

公平起见的反面清单（⚠️ 通识转述）：

1. **提交间隔的地心引力**：小文件/元数据压力使「秒级」在高频小事务源上代价陡增，
   很多「实时湖仓」落地后调回 1~5 分钟——新鲜度叙事与工程稳态的常态落差；
2. **点查仍是客场**：湖表毫秒级主键点查依赖额外服务层（索引/物化/缓存），
   「统一存储」常以「统一存储+双查询面」收场，运维心智并没有省掉一半；
3. **回写回路缺失**：分析结果反哺在线系统时，湖的写路径（批合并语义）天然慢，
   硬闭环场景最终还是要绕回库/流内（§1 结论的推论）。

三条缺陷共同解释了 08 §2 的「变形」：湖仓吃下运营视图的**读侧**，
把**写回侧**让渡给库内混合——对位不是替代。

## 核心概念速览（中英对照）

- **湖仓** — Lakehouse：对象存储+开放表格式上重建仓库语义（ACID/时间旅行/治理）的架构。
- **快照替换** — Snapshot Replacement：以新元数据指针原子切换读者所见版本，湖式并发基础。
- **时间旅行** — Time Travel：按版本/时间戳读历史快照的能力，重放与审计的底料。
- **删除文件** — Delete Files（positional/equality）：列存湖表在不重写文件前提下表达行级变更的结构。
- **增量读** — Incremental Read：从上次读位点继续消费表变更的查询模式。
- **流式提交** — Streaming Commit：写入器以短间隔持续生成快照的形态，湖仓新鲜度的来源。
- **运营数据层** — Operational Serving Layer：面向消费端的中间视图存储（§3 两形态）。
- **零ETL** — Zero-ETL：托管控制面内建的库→仓/湖免管道直连（§4）。
- **背书问题** — Correctness Sponsor：中间层新鲜度由事务域还是重放确定性保证的追问。
- **物理隔离红利** — Isolation Dividend：湖仓以稍旧换「不伤生产库」的结构性收益。

- **流式湖仓**：Paimon 把 LSM 写优化与湖表提交合流，「湖上的 HTAP 化」成为 2023+ 新品类

- **运营查询面直读湖**：ClickHouse/DuckDB/Trino 对湖格式的直读与物化层持续演进，
  文档入口分别 ✅（见 05/02 各节 URL）。
- **对 2020 叙事的再判断**（⚠️ 观点）：「操作分析崛起」的预言部分兑现、部分被改道——
  实时闭环决策（风控型）留在库内/流内（D1~D3），运营报表型大规模迁入湖仓（D4）；
  两条线的边界即本篇 §1 表格的隔离性/新鲜度权衡，至今没有一边吃掉另一边。
