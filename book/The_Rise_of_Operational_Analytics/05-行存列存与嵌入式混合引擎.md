# 05 行存、列存与嵌入式混合引擎

> 主题重构笔记（非原书章对位，⚠️ 降级声明见 [00-总览与阅读地图.md](00-总览与阅读地图.md) §2）。
> 本篇给「为什么 D1 双表征不是玄学」补微观证据：行存与列存在两套负载上的不对称优势，
> 并用嵌入式引擎（SQLite/DuckDB）做可复现的对照实验。

## 1. 布局决定性格

- **行存（NSM, n-ary storage model）**：一行的列连续存放。点查/短事务一行只碰一个页；
  代价：聚合扫全表时搬运大量无关列，解压/反序列化浪费带宽。
- **列存（DSM, decomposition storing model）**：一列的值连续存放。扫描型聚合吃满向量带宽、
  同列同类型压缩比极高；代价：还原「一行」要跨多列拼接（位置对齐/rowid），点查与窄写变昂贵。

由此得到操作分析的第一性工程结论：**「一份数据两种姿势」要么是双表征（D1，同步问题见 02 §3），
要么是旁路结构（D2），要么老实搬运（D3/D4）**——没有第三种物理奇迹。

## 2. 🔧 实验 E3b：同一批 100 万行，两种引擎各干各的擅长事

本机方法（临时件 `D:/develops/tmp/dbwave_w8_rosa/exp2.py`；SQLite 3.45.3 行存 / DuckDB 1.5.5 列存；
DuckDB 经 sqlite 扩展 ATTACH 原样导入同一张表，非本书引擎行为，数字仅演示**布局差异**）：

| 负载 | SQLite（行存） | DuckDB（列存） | 观察 |
|---|---|---|---|
| `SELECT SUM(v) FROM t`（全表聚合，1e6 行） | **50.9 ms** | **2.3 ms** | 列存约 22× 优势：只读所需列+向量化 |
| `WHERE id=777777` 主键点查 | **0.11 ms** | 1.8 ms | 行存约 16× 优势：一次页命中 |
| 导入/搬运 | —（数据本就在） | 399.6 ms（ATTACH+CTAS+CHECKPOINT） | 双表征的「同步成本」微观样本 |

三行表格讲完 HTAP 存在的理由：**同数据两种姿势的差距是两个数量级，而搬运一次要付全价**——
D1/D2 的全部工程投入都在回答「这份差距值不值得用一致性复杂度来换」。

## 3. 列存引擎的「事务化」补课史（⚠️ 通识转述）

2010s 的列存分析引擎（Parquet 文件仓、早期 MPP）普遍不擅长行级 UPDATE；
2020s 的收敛方向是给湖/仓格式补**行级变更的代价分摊**：
- Iceberg：DELETE/位置文件（equality deletes）、增量读（见规范 https://iceberg.apache.org/spec/ ✅）；
- Delta：事务日志+ROW-tracking/变更数据读能力（⚠️ 版本细节转述，以官方文档为准）；
- Paimon 类「流式湖仓」：把 LSM 结构直接做进湖表，让高频行变更与列式扫描同表共存
  （盘上专册对位 [../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md](../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md)）。

LSM 行存（RocksDB 型）与列存湖表的合流，是 2020 年「崛起」叙事中最具持续性的一支 ⚠️（趋势判断）。

## 4. 嵌入式 HTAP？「一个人乐队」的真实边界

🔧 E4 实验（见 02 §7）已证明：DuckDB 库文件**跨进程独占**——第二进程连 open 都失败
（`IO Error: Cannot open file`，0.34s 内报错）。因此：

- 嵌入式列存的正确定位是**进程内分析加速件**（应用自带「随身数据仓库」），
  不是多人共享的事务-分析混合库；

## 5. 压缩与「扫描税」的算术（转述 ⚠️，不给厂商数字）

列存红利的主要来源：同列同类型→位图/RLE/字典压缩，扫描时**解压即计算**（谓词在压缩态粗筛）；
代价是写侧：新数据先落差分/增量区（delta buffer），后台再 compaction 进压缩区——
**列存引擎的「写便宜/读便宜」切换点就是 compaction 调度器**。这与 LSM 行存的读写放大谱完全同构，
也解释了 D1 引擎「更新风暴时分析查询变慢」的微观原因（compaction 饥饿）。

## 6. 混合布局的三种成本形态总结

| 形态 | 谁付钱 | 什么时候爆 |
|---|---|---|
| 双表征（行+列各一份） | 更新路径 + 存储翻倍 | 高频 UPDATE 表 |
| 旁路结构（物化视图/列索引） | 写路径维护税（🔧 E5：113ms/5万行） | 视图多且刷新频繁 |
| 搬运（D3/D4） | 管道运维 + 新鲜度上限 | 源 schema 漂移/延迟尖峰 |

「操作分析选型」的本体就是这张表：**为每条数据流挑一种税，再验证税基不会失控**。

## 6.5 行/列决策速查（评审用清单）

问自己五个问题，落到 02 §1 的密度表上（⚠️ 通识清单，非原书内容）：

1. 负载画像里「点查:聚合」的比例是多少？9:1 与 1:9 的库根本不该同一个产品；
2. 聚合读需要多新？分钟可接受→旁路/搬运（D2/D3/D4）；毫秒→只剩 D1 且要隔离承诺；
3. 写放大容忍度？高频 UPDATE 宽表上双表征/列存的 compaction 会持续吃 CPU（§5）；
4. 谁负责一致性？同库=引擎负责；搬运=你的管道负责；双写=对账脚本负责；
5. 单机还是共享？嵌入式（DuckDB/SQLite 组合，§4）只在单进程/受控并发里成立（🔧 E4）。

## 6.6 为什么「列存索引」救不了所有行存库

行存库常见的「分析加速件」是 B 树上的覆盖索引或物化视图，它们在**选择率高的谓词**上有效；
而对全表聚合（`SUM`/直方图类）本质仍是逐行访问。列存的优势从来不是「索引聪明」，
而是**免读无关列 + 压缩态计算**。因此「加个索引转成 HTAP」在物理上不成立——
需要的是第二种布局（D2 旁路表/D1 双表征/D4 湖表三选一），这正是 02 谱系存在的理由。
🔧 E3b 的第二行（行存聚合 50.9ms 且点查 0.11ms）就是该论断的单机复现：
两种姿势的毫秒数各自被对方布局的物理性质惩罚。

## 核心概念速览（中英对照）

- **NSM/DSM** — 行式/列式存储布局：n-ary 与分解存储模型，扫描与点查优势互换的根源。
- **向量执行** — Vectorized Execution：按列批量处理以摊薄解释开销、吃满 SIMD/带宽的执行方式。
- **差分缓冲** — Delta Buffer：列存中承接新写、未压缩的暂存区，compaction 前的读改写区。
- **Compaction** — 合并整理：差分区并入压缩区的后台工序，列存写放大的集中体现。
- **双表征同步** — Dual Representation Sync：行存改动传播到列存副本的一致性协议与延迟。
- **嵌入式分析** — Embedded Analytics：分析引擎以库（而非服务）形态进入应用进程。
- **ATTACH/CTAS** — 跨源装载：DuckDB 挂载外部库并转存为本机列存表的操作（🔧 实验方法）。
- **独占文件锁** — Exclusive File Lock：单进程引擎（如 DuckDB）跨进程并发写的物理上限（🔧 E4）。
- **一个人的 HTAP** — Single-process Pseudo-HTAP：SQLite 扛点查+DuckDB 跑报表的单机组合（🔧 类比）。
- **税基** — Tax Base：某种维护/同步成本随负载增长的规模，选型验算对象。
