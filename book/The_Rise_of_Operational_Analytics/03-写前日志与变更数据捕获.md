# 03 写前日志与变更数据捕获

> 主题重构笔记（非原书章对位，⚠️ 降级声明见 [00-总览与阅读地图.md](00-总览与阅读地图.md) §2）。
> 本篇讲操作分析的「供血机制」：日志如何从恢复设施演变为可订阅的事件源。

## 1. WAL 的两副面孔

写前日志（Write-Ahead Logging, WAL）诞生时只有一个义务：**崩溃恢复**——
任何页变更落盘前，描述该变更的日志记录必须先持久化（ARIES 传统的弱化表述，⚠️ 教科书转述）。
操作分析看中的是它的第二副面孔：**日志即事实流**——数据库内一切变更的有序、持久、可重放的编码。

同一份日志的三种消费方式，构成三条工程路线：

| 消费方式 | 机制名 | 消费者得到什么 | 代表 |
|---|---|---|---|
| 字节级回放 | 物理复制 | 主库的精确镜像（含全部写） | PG base backup/流复制、MySQL 物理复制 |
| 行级事件解码 | 逻辑解码/Change Streams/binlog 行事件 | 表/行粒度的 insert-update-delete 事件流 | PG logical decoding、MongoDB Change Streams、MySQL row binlog |
| 快照差分 | 轮询时间戳/CDC-less | 近似变更集（有漏采风险） | 自研 `WHERE updated_at > ?` |

判别力在哪：**逻辑解码是唯一能把「变更」与「谁改的、改了哪行、旧值新值」都带出来的形式**；
物理复制只保证镜像，轮询连「删除」都可能丢。

## 2. PostgreSQL 线：从恢复日志到事件总线

官方文档（均 ✅ curl 200）：
- WAL 概念 https://www.postgresql.org/docs/current/wal-intro.html
- 逻辑解码 https://www.postgresql.org/docs/current/logicaldecoding.html

机制要点（转述官方口径）：逻辑解码需要 `wal_level=logical`，解码器基于快照/历史保留的元组重建行事件；
发布/订阅（pub/sub）把解码输出产品化为可路由的表级复制通道。对操作分析的意义：

1. **分析侧可以只订阅关心的表**——带宽与权限双收缩；
2. **解码消费是「拉」模型**：消费端（如 Debezium）不追平之前，WAL 与解码槽不能无限膨胀——
   **槽（replication slot）滞留会反噬生产库**，这是 PG 系 CDC 的第一运营风险；
3. 盘上运维对位：复制槽监控与 WAL 膨胀处理在
   [../PostgreSQL_16_Administration_Cookbook/00-总览与阅读地图.md](../PostgreSQL_16_Administration_Cookbook/00-总览与阅读地图.md) 与
   [../Mastering_PostgreSQL_Administration/00-总览与阅读地图.md](../Mastering_PostgreSQL_Administration/00-总览与阅读地图.md) 的复制章节；
   内核侧 WAL/检查点行为见单文件 [../PostgreSQL数据库内核分析.md](../PostgreSQL数据库内核分析.md)。

## 3. MongoDB 线：oplog 升格为公共 API

Change Streams 把分片副本集的 oplog 包装成聚合管道可过滤的会话级事件流，
文档 https://www.mongodb.com/docs/manual/changestreams/（✅ curl 200）。
与 PG 路线的差异（⚠️ 文档口径转述）：

- 事件形态是**文档级 delta**（updateDescription 带 changedFields），不是行级旧值/新值对；
- 天然跨分片聚合为一条流，省去分片场景下的多路合并；
- resume token 的持久化义务等价于「消费者的位点就是它的复制槽」。

## 4. 工具链层：Debezium 与 Flink CDC

- Debezium：把「数据库服务器 → Kafka 变更事件」固化为连接器的开源项目，
  文档 https://debezium.io/documentation/reference/stable/（✅ curl 200）。
  关键工程概念：snapshot + binlog/wal 增量衔接、事务顺序保证、schema 变更事件的旁路通道。
- Flink CDC：在流引擎内直接以 SQL 源表形式吃 CDC，文档
  https://nightlies.apache.org/flink/flink-cdc-docs-stable/（✅ curl 200）。
  它代表的路线是：**CDC 不作为管道，而作为流计算的一个表**——下游直接是窗口聚合/join，
  新鲜度由反压与 checkpoint 决定，而非调度周期。

## 5. 「至少一次/恰好一次」在这里怎么落

CDC 管道绕不开投递语义：源端位点与目的端写入不同事务域时，只有
**幂等落地**（按主键 upsert+全行镜像）或**事务对齐**（位点随目的端提交原子推进）两条正解。
操作分析读路的特殊宽容度：**聚合视图天然可被重放修正**（重复事件对 SUM 可加，对 COUNT DISTINCT
需去重键），这让「至少一次+可重放」成为成本最低的主流组合 ⚠️（通识结论，非原书命题）。
语义细账回看：[../Design%20Data-intensive%20Applications.md](../Design%20Data-intensive%20Applications.md)
第 11 章流处理三件套（批流同构、反压、最终一致性）。

## 6. 反模式清单（评审时直接引用）

1. **把轮询当 CDC**：删除事件丢失、时间戳列无索引时全表扫拖垮生产库；
2. **解码槽无人监控**：槽滞留 → WAL 膨胀 → 生产库磁盘告警——故障发生在「数据库」而不是「管道」；
3. **在事务内同步推远端**：跨网络写进本地事务，锁持有时间=网络抖动，隔离级别帮不了你；
4. **schema 变更不通知下游**：加列没断、删列炸裂——CDC 事件必须带 schema 演进信道（Debezium 一等公民）；
5. **用分析副本兜底所有读**：副本延迟峰值期，业务页读到旧值——需要 read-your-writes 的读留在主库
   （事务域语义见 [06-新鲜度一致性与读写并发.md](06-新鲜度一致性与读写并发.md)）。

## 7. 顺序、分区与「单表有序」的代价

日志订阅给消费者的顺序保证是有层次的：库内全局有序 → 表级有序 → 分区/文件级有序。
Kafka 落地时常见做法是按主键哈希分区（表内单行有序、表级乱序），
这对「行级 upsert 幂等」足够，但对「跨行事务可见性」（如先建订单再建明细）并不足够——
要么按事务分发（单分区串行，吞吐受限），要么下游自带乱序缓冲（watermark/重试窗）。
**问清下游对乱序的容忍度，是 CDC 拓扑设计的第一问**（⚠️ 通识工程结论）。

## 8. 首刷与增量的衔接点设计

P3 冷启动的标准难题：快照读到 t0，日志从 t1 开始消费，(t0,t1) 区间靠日志回补
要求日志保留 ≥ 快照耗时；快照期间源表仍在写则要求快照本身可重放或有事务锚点。
Debezium 文档将 snapshot 模式做成显式配置项（✅ 文档 URL 见上），
其存在本身就说明：**「首刷-增量衔接」从来不是透明的，只是被工具收敛成了参数**。

## 核心概念速览（中英对照）

- **写前日志** — WAL/Write-Ahead Logging：变更先写日志再改数据的持久化协议，恢复与复制的共同底座。
- **物理复制** — Physical Replication：字节级重放日志，得精确镜像，无行级事件表达力。
- **逻辑解码** — Logical Decoding：把 WAL 解码为行级/文档级变更事件的机制（PG 术语）。
- **复制槽** — Replication Slot：为慢消费者保留日志的注册物，滞留时反噬生产库磁盘。
- **oplog/Change Streams** — MongoDB 的日志→事件流 API 化产品。
- **快照衔接** — Snapshot+Incremental Handoff：CDC 首刷与日志增量的时间线拼接点。
- **位点（offset/resume token）** — 消费者进度指针，重放与去重的依据。
- **幂等落地** — Idempotent Sink：以 upsert/全镜像消化「至少一次」重复目的端写法。
- **可重放修正** — Replayability：聚合视图可被重灌纠错的宽容属性，降低投递语义要求。
- **事件信道** — Schema-Change Channel：随数据事件旁路广播 DDL 演进的专用流。

## 最新演进与工业实践

- **PG 线**：逻辑解码与 pub/sub 在 2024–2026 的 PG17/后续版本中保持稳态演进，
  官方文档 URL 均 ✅（见上）；版本支持节奏 https://www.postgresql.org/support/versioning/（✅）。
- **MongoDB 线**：Change Streams 文档线 ✅（URL 见上），Atlas 平台把其升格为应用触发器入口 ⚠️（云平台转述）。
- **工具线**：Debezium stable 文档 ✅；Flink CDC 进入 Flink 子项目序列（nightlies.apache.org ✅），
  2024–2026 方向是「CDC 即源表 + schema evolution 内建」。
- **湖仓接口**：CDC 事件的落点从 Kafka topic 扩展到开放表格式——Iceberg 规范的事务/隐藏分区/
  增量读取章节 https://iceberg.apache.org/spec/（✅），使「日志→湖→运营查询」三段式成为 2024+ 默认叙事
  （湖仓侧对位见 [07-湖仓对位与运营数据层.md](07-湖仓对位与运营数据层.md)）。
- **运维警戒线不变**：解码槽膨胀仍是 PG 系 CDC 的头号生产事故来源 ⚠️（社区经验转述，无本机可复现指标）。
