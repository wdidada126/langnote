## 机制精讲

### 附录 A：主键是良好的，但不是必需的

论证骨架（与 01 章 1.4、02 章键定义接榫）：
1. 模型层只承认**候选键**：唯一性+极小性；"主键"是从中等**挑一个**用来引用——纯粹的外交便利 ⚠️ 措辞重构。
2. 挑主键的正当理由：外键短、稳定、少变；**没有**正当理由的说法："每表必须有一个且语义神圣的主键"。
3. SQL 现实的纠偏：`FOREIGN KEY ... REFERENCES` 的目标列在很多产品里必须 PK/UNIQUE（✅ 通识；
   SQLite/MySQL 接受任意 UNIQUE 列，PG 亦然）——把"可选的惯例"错读成"模型的要求"是概念腐败。
4. 代理键（surrogate）与自然键之辨：代理键是**新增事实**（"本元组的编号"），不是被选的既有候选键
   ——它改变谓词（15.2 的透镜下，代理键表=带存在断言的 relvar）⚠️ 作者口径重构。
5. 处方：所有候选键都声明（UNIQUE），引用点选**最合适的**标 PRIMARY KEY——"良好，但非必需"。

🔧 旁证（本机 sqlite3 ✅ 语义核对）：`create table SP(S text references S7(S))` 中被引用列仅需唯一性——
测试中引用非主键但 UNIQUE 的列被接受（建 `S7b(S text unique)` 后 FK 指向 S7b.S 成功）；
"必须主键"确系实现方言而非模型律。

## 常见误区

- 「每表必须有 ID 自增主键」：A 节整篇的反题；代理键先问"引入了什么新谓词"。
- 「主键会变的列不能当主键」：正确焦虑、错误处方——该说的是"引用要稳定"，选稳定候选键即可，
  不必升"万物皆 ID"。
- 「冗余=坏，NULL=坏」：B 节把它们同根化：坏的是"谓词混载"，冗余与 NULL 是两位症状。
- 「附录可跳过」：本目录的读法排序里，A/B 分别回收 01 与 08/15 两条主线，跳过=欠两条线的收尾。

## 附录 A 判例练习（🔧 每题先答"模型层怎么说"，再答"SQL 层怎么做"）

1. 表 `PHONE(USER_ID, NUMBER)` 允许一人多号、一号一人：键选哪个？需要 ID 代理键吗？
   （模型：复合候选键已尽职责；代理键仅当"行号"成为被引用事实时才**新增谓词**。）
2. `CITY(NAME)` 唯一但改名频繁、被 12 张表引用：怎么办？
   （A 节的"外交便利"正是此景：引入稳定的 CITY_ID 不是破律而是尽礼。）
3. 有人坚持"没主键的表不配进生产库"：用 5.1/A-1 的语言写出反驳的两段论。
4. 🔧 复核：sqlite3 里分别用 PK、UNIQUE 非 PK、无约束列做被引用目标，记录三种 DDL 结果；
   再开 `PRAGMA foreign_keys=ON` 重跑（本机 ✅：无约束目标直接报
   `foreign key mismatch`——引用需要**声明过的**唯一性，但不需要"主"字）。

## 核心概念速览（中英对照）

- **候选键** — candidate key：唯一+极小的键；模型层唯一的"键"概念
- **主键** — primary key：被选中承担引用的候选键；惯例而非律令
- **代理键** — surrogate key：人为新造的存在编号（自带新谓词）
- **自然键** — natural key：源自业务的既有候选键
- **外键目标列** — referenced column：多数 SQL 实现仅要求唯一性（🔧 实测）
- **命题式冗余** — proposition-based redundancy：同一命题多载体（附录 B 核心定义）
- **值巧合** — value coincidence：不同命题同值，不计冗余
- **派生事实** — derived fact：汇总/物化列——冗余分类学的独立一栏
- **NULL 的表亲关系** — NULL as cousin：与冗余同根（一表多谓词）
- **文献地图** — paper trail：附录 C 的功能——本书引用网络的索引
- **习题文化** — exercises per chapter：每章设问的体例（✅ 中译目录）
- **稳定引用** — stable reference：选主键的真实需求所在
- **ID 崇拜** — surrogate dogma：A 节点名的业界迷信
- **两层对表** — theory/physical ledger：逻辑非必需 vs 物理成本的区分术

## 最新演进与工业实践

- **SQL 标准与产品的键灵活度（✅ 文档）**：SQL 标准要求 REFERENCES 目标为 UNIQUE/PK 列——
  PG/MySQL/SQLite 皆照办（PG 语法文档 https://www.postgresql.org/docs/current/sql-createtable.html
  curl 200 ✅；SQLite 同理，🔧 本机实测 UNIQUE 非主键可被引用）。"主键神圣"在产品层并无依据；
  反而 UUIDv7/雪花 ID 等**代理键基础设施**的繁荣（各云厂商文档 ⚠️ 未逐一核）说明 A 节的
  "外交便利"判断精准——只是便利的规格化了。
- **主键选择的现代账**：InnoDB 聚簇主键让"选哪个候选键"有了真实物理后果（顺序写 vs 随机写），
  工程口径见 [../mysql/06-B树索引.md](../mysql/06-B树索引.md)；这与"逻辑上无特权"不矛盾——
  正是本附录"两层对表"要防的混线。
- **冗余计量的研究现状** ⚠️：FD 满足度近似度量（e.g. tDEP/GDEP 类指标，数据挖掘文献常用）与
  B 节命题定义**不等价**（它们按值统计=恰是 15.16 枪毙的路数）；引用时注意口径。工具现状未逐一核验。
