## 机制精讲

### 2.2 关系及关系变量

- 属性（attribute）：名字 + 类型（作者更倾向"域" domain）；头（heading）= 属性全集。
- 元组（tuple）：属性到值的映射；度（degree）= 属性数，基数（cardinality）= 元组数。
- 关系（relation）：同一头下的元组**集合**——数学集合意味着：无序、无重复。
- 关系变量（relvar）：取值为关系的变量；对 relvar `S` 的赋值产生某时刻的值 `S`。
- 数据库 = 某时刻所有 relvar 取值的集合。

形式化写法（🔧 自拟，非原书编号）：

```
S# ∈ SUPPLIES_NO, SNAME ∈ NAME, STATUS ∈ INTEGER, CITY ∈ CITY_NAME
S = { <s1, 'Smith', 20, 'London'>, ... }   -- 关系：值
```

SQL 对照：`CREATE TABLE` 声明的是"头 + 约束"，表当前的行集**应当**是关系——但 SQL 允许
重复行、允许有序游标，这是作者毕生批评的偏差（详见兄弟目录 03/09 两章）。

### 2.3 谓词和命题

- 谓词：含自由变量的陈述，如 `供应商 x 名为 y、状态 z、住 w`。
- 命题：变量代入后的可判真假陈述：`供应商 s1 名为 Smith、状态 20、住 London` → 真。
- **relvar = 其谓词为真的全体命题之当前外延**。元组在 S 中 ⇔ 对应命题为真。
- 由此得到设计的判据：一个 relvar 只能有一个谓词。若把两个谓词混进一个头
  （例如"供应商当前状态"与"供应商曾有的状态数"），依赖异常必然出现——这就是规范化
  要修的"病根"（第 3 章起逐一展开）。

该读法与逻辑侧完全一致，见 [../SQL_and_Relational_Theory/04-谓词与命题-关系模型的逻辑地基.md](../SQL_and_Relational_Theory/04-谓词与命题-关系模型的逻辑地基.md)。

### 2.4 更多的供应商和零件

扩展 S_P_J：给 P/J/SP/SPJ 逐一书写谓词，并声明键与引用：

| relvar | 谓词（重构表述） | 候选键 🔧 |
| --- | --- | --- |
| S | s 是编号 S#、名 SNAME、状态 STATUS、驻 CITY 的供应商 | S# {S# 唯一} |
| P | p 是编号 P#、名 PNAME、重 WEIGHT 的零件 | P# |
| J | j 是编号 J#、名 JNAME、驻 CITY 的工程 | J# |
| SP | 供应商 s 向零件 p 供货数量 QTY | {S#,P#} |
| SPJ | 供应商 s 为工程 j 供应零件 p，数量 QTY | {S#,P#,J#} |

注意：`SP` 的存在本身就是一条设计论断（"供货"与"为某工程供货"是两个谓词）——若世界事实只支持
SPJ 谓词，硬造 SP 就是**信息丢失**（投影有损）。这是 5NF（第 9/10 章）的伏笔。

> 🔧 可复现实验（SQLite）：用 UNIQUE 索引强制候选键，观察违例被拒：
> `create table S(S text primary key, SNAME text, ST int, CITY text);`
> 插入重复 S# 报 `UNIQUE constraint failed`（Python sqlite3 实测 ✅ 本机可跑，下同）。

## 常见误区

- 「关系变量就是表」：丢了"值是关系"这一层，就无法理解为什么"重复元组不合法"。
- 「元组 = 一行数据」：元组是**命题的真值见证**；删元组 = 撤销一条断言（第 3 章删除异常的根源分析需要这个视角）。
- 「先有表再想约束」：作者立场是先想清谓词，头和键只是谓词的投影。
- 把 NULL 当"值的一种"塞进属性域：三值逻辑污染（在兄弟目录 06/07 章有专病讨论，本书第 13 章 ED 一节再碰）。

## 核心概念速览（中英对照）

- **属性** — attribute：名字+类型（域）的列定义，关系头的组成单元
- **头** — heading：relvar 全部属性的集合，两关系可 UNION 的前提是头相同
- **元组** — tuple：属性→值的映射；关系中的"行"，命题的外延
- **度 / 基数** — degree / cardinality：属性个数 / 元组个数
- **关系** — relation：同头元组的集合；值，无序无重复
- **关系变量** — relvar：取值为关系的变量；SQL 基表的理论对应物
- **谓词** — predicate：relvar 所表达的开语句（命题函数）
- **命题** — proposition：代入具体值、可判真假的陈述
- **外延** — extension：谓词当前为真的命题全体（即 relvar 之值）
- **域** — domain：属性可取值之集合（类型+约束），SQL 仅 PG 有真 CREATE DOMAIN
- **引用完整性** — referential integrity：SP.S# 必须出现在 S.S#（本章预告，兄弟目录专章）
- **投影有损** — lossy projection：SP 若从 SPJ 造出，会丢"哪次供货对应哪个工程"
- **闭世界假设** — closed world assumption：元组不在则命题为假（非"未知"）
- **S_P_J 谓词表** — running predicates：每 relvar 恰一谓词的设计基线

## 最新演进与工业实践

- **约束声明的现状**（✅ 文档核对 + 🔧 本机 sqlite3 行为核对）：PostgreSQL 的键/CHECK/唯一约束见官方
  文档 https://www.postgresql.org/docs/current/ddl-constraints.html （curl 200 ✅）；`CREATE DOMAIN` 真域仅
  PG 等少数引擎支持，MySQL/MariaDB/SQLite 均无（SQLite 语法清单 https://sqlite.org/lang_createtable.html ✅ 无 DOMAIN）。
- **引用完整性工程化**：SQLite 需 `PRAGMA foreign_keys=ON` 才强制外键（🔧 本机验证：默认 OFF，

  是历史上的性能妥协，不应被理解为"外键可选"。

  形态的是 Datalog 家族（如 Flix/Datomic/LogicBlox 线）⚠️ 转述，未见与本理论谱系的正式接轨。
- **谓词观的应用侧回响**：dbt "data contract" 与 schema 测试（generic tests 本质=每 relvar 一个谓词）
