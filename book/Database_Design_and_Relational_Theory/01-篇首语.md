## 本章定位

篇首语是全书的"为什么"：用一个贯穿始终的例库（S_P_J）和一组文献引语，回答"数据库设计理论
到底管不管用"。作者在此把本书与两类书划清界限——只讲操作不问原理的实践书，与只推公式不接
地气的理论书（O'Reilly 北京页文案 ✅：「许多数据库设计实践图书对基本理论的解释不清晰，而那些
侧重设计理论的图书又主要面向理论研究人员」）。

## 机制精讲

### 1.1 文献引语的作用（对应原书 1.1）

作者开宗明义引用业界文献证明两件事：①设计不当的数据库会长期拖累系统；②关于"设计要凭直觉、
理论无用"的行话由来已久且错误。这不是修辞：全书后续每一章都会回到这个主张，用依赖理论
（FD/JD/MVD）把"设计好坏"从主观审美变成**可判定的性质**。

### 1.2 术语说明：三个词的分层（对应原书 1.2）

Date 的固定术语纪律（与兄弟目录 [../SQL_and_Relational_Theory/01-关系模型核心概念与语言教程.md](../SQL_and_Relational_Theory/01-关系模型核心概念与语言教程.md) 完全同源）：

| 理论层 | 实现层（SQL） | 备注 |
| --- | --- | --- |
| 关系变量 relvar | 基表 base table | 取值随时间变化的"变量" |
| 关系 relation | 表当前的值 | **值**：无重复、无序 |
| 元组 tuple | 行（但 SQL 行可有重复） | ⚠️ 这正是差异所在 |
| 属性 attribute | 列 | |
| 头 heading | 列定义集合 | 属性名+类型（域） |

> ⚠️ 本书讲"设计"，因此 relvar/谓词是主语；"表、行、列"只在打比方时出现。

### 1.3 运行示例 S_P_J（对应原书 1.3）

全书用经典的"供应商-零件-工程"例库（Date 自 70 年代沿用，✅ 该例库谱系可追溯到 Codd 及作者历部著作；
下述具体属性表为 🔧 笔记自拟的通行版本，与原书逐字段口径可能有出入 ⚠️）：

- `S{S#, SNAME, STATUS, CITY}` 供应商
- `P{P#, PNAME, COLOR, WEIGHT}` 零件
- `J{J#, JNAME, CITY}` 工程
- `SP{S#, P#, QTY}` 供货
- `SPJ{S#, P#, J#, QTY}` 工程供货（第 3、9 章的主战场）

关键读法：**每个 relvar 对应世界的一个谓词**。SPJ 的谓词是"供应商 S 向工程 J 供应零件 P，数量为 QTY"。
设计理论的第一个动作就是把"命题"和"承载命题的 relvar"一一对上——这条主线直通第 15 章。

### 1.4 键（对应原书 1.4）

候选键 = 唯一性 + 极小性；主键只是**选出来用的**那个候选键。作者在此埋伏笔：
"数据库设计得好不好，很大程度看约束声明得好不好"——键是最常用的约束。附录 A（见
[16-附录-主键冗余与论文回顾.md](16-附录-主键冗余与论文回顾.md)）将论证主键并不享有神圣地位。

### 1.5 设计理论的地位（对应原书 1.5）

三点立场（重构表述）：
1. 设计理论是**论证工具**，不是流程教条：它不告诉你第一步做什么，而是告诉你"这样拆为什么对/错"。
2. 理论与实现之间的落差（SQL 支持度不足）**不是拒绝理论的理由**——正如 3VL 之弊（见兄弟目录
   [../SQL_and_Relational_Theory/06-NULL与三值逻辑3VL.md](../SQL_and_Relational_Theory/06-NULL与三值逻辑3VL.md)）。
3. 设计问题的持久性：数据库寿命以十年计，代码可重写，schema 迁移代价极高。

### 1.6 本书的目的（对应原书 1.6）

O'Reilly 北京页文案 ✅ 给出的"本书回答的问题"清单，恰是各部分的预告：
- 为什么**希思定理**如此重要？→ 第 5 章
- **正交设计**的原则指什么？→ 第 14 章
- 为什么一些 **JD 可约**而另外一些不可约？→ 第 11 章
- **保持依赖**为什么有问题？→ 第 6 章
- 是否应该始终**避免数据冗余**？这可以做到吗？→ 第 8/15/16B 章

## 常见误区

- 「理论归理论，实践归实践」：作者全书的反题。范式不是官僚表格，是对"更新异常"的**证明**。
- 把 S_P_J 当"教学玩具所以无意义"：它的价值是最小充分的谓词结构，异常/依赖都藏不住。
- 混淆 relvar 与"表"：一旦混淆，就会接受重复行、ORDER BY 进 schema 这类病（兄弟目录 13 号误区清单详述）。

## 本章自测（合卷判卷标准：能写出论证，不是能复述名词）

1. 用一句话区分 relvar 与"表"，并给出一个因混淆而产生的 SQL 坏习惯（提示：重复行 / ORDER BY）。
2. 为 `SP{S#,P#,QTY}` 与 `SPJ{S#,P#,J#,QTY}` 各写一个谓词句子；说明为什么"从 SPJ 投影出 SP"
   需要论证而不是默认成立（伏笔：第 9 章）。
3. "设计理论不规定第一步做什么"——这与本书后面给出大量**定理**矛盾吗？写出你的解释
   （参考答案方向：判据 vs 流程，见 1.5/3.5）。
4. 从 1.6 的五个问题里挑一个，写出你**目前的**直觉答案，读完对应章后回来对答案——
   这是本目录推荐的贯穿读法。
5. 🔧 热身实验：Python sqlite3 里建 `S(S text primary key, SNAME text, ST int, CITY text)`，
   插入两个重复 S#，记录报错文本；再删掉 PRIMARY KEY、不加任何约束重插——观察数据库
   **一声不吭**。结论：约束不会自己出现，它出现在声明里（1.5 的"地位"所在）。

## 核心概念速览（中英对照）

- **关系变量** — relvar：取值为关系的变量，数据库由 relvar 组成，SQL 基表是其实现
- **关系** — relation：头一致的元组集合，是值：无序、无重复
- **头** — heading：属性名与其类型/域的集合，决定"哪些谓词可在此为真"
- **候选键** — candidate key：唯一决定所有属性且极小的属性集
- **主键** — primary key：被选中执行参照的候选键，理论上非必需（附录 A）
- **谓词** — predicate：含自由变量的命题函数；relvar 即谓词的外延
- **正在运行的示例** — running example：贯穿全书的 S_P_J 例库
- **设计理论** — design theory：以依赖/范式论证 schema 好坏的可判定工具
- **更新异常** — update anomaly：设计不当导致的插入/修改/删除病（第 3 章定义）
- **S_P_J** — suppliers/parts/projects：经典数据库教学例库
- **约束声明** — constraint declaration：把业务规则写进 schema 而非应用代码
- **理论-实现落差** — theory/implementation gap：SQL 支持不足不构成弃理论的理由
- **正交设计** — orthogonal design：relvar 谓词间互不掣肘（第 14 章）
- **希思定理** — Heath's theorem：无损分解的奠基定理（第 5 章）
- **依赖保持** — dependency preservation：分解后约束能否在原 relvar 上局部检验（第 6 章）
