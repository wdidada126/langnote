## 机制精讲

### 8.1 "反规范化是为了性能"吗

行话的潜台词："规范化的代价是连接，反规范化省连接"。作者的反驳链 ⚠️ 口径重构：
1. 规范化到 BCNF **不必然**引入昂贵的自然连接——连接键都是键（希思/4NF/5NF 分解的性质），
   索引化的键连接在成熟引擎上并不离谱（性能账要**实测**，见 🔧 与本目录纪律）。
2. 就算某些查询真的慢，正确处方是**视图**（虚拟）或**系统维护的副本**（物化视图/索引），
   不是把冗余写回基表。
3. 反规范化者隐含承诺"我会手工维护一致性"——8.5 证明这个承诺几乎必然违约。

### 8.2 反规范化是什么意思

**准确定义（本书）**：在数据库中**额外存储**可由现有 relvar 导出的数据（重复事实或派生事实），
并**由手工/程序而非系统**维持其一致性。三要件缺一不可：额外存储 + 可导出 + 人工一致性。

### 8.3–8.4 什么不是反规范化（I/II）

作者点名澄清的"假反规范化"（按节拆分 ⚠️ 条目归属为笔记重构）：
- **索引/散列/集群**：物理层冗余，系统自动维护 → 是物理设计（对照
  [../Physical_Database_Design/00-总览与阅读地图.md](../Physical_Database_Design/00-总览与阅读地图.md)）；
- **视图（虚表）**：不存储 → 与反规范化无关；
- **物化视图**：存了，但一致性归**系统**管 → 严格说是"受控冗余"，是反规范化的**替代药方**而非本尊 ⚠️
  （本书成书年代多数引擎物化视图需手工 REFRESH，作者对"系统维护"的怀疑有此背景；见文末现状）；
- **规范化后的连接本身**：SPJ 与 SP 是两个谓词两回事，不是"把 SPJ 反规范化成 SP"（05/09 章反复强调）；
- **聚合/汇总表的错误用法**（手工 UPDATE ... SET TOTAL=...）：这才是真反规范化。

### 8.5–8.6 反规范化是有害的（I/II）

- **I（逻辑账）**：每处副本都是第二事实源 → 回到第 3 章三异常，且此时异常是**自愿引入**的；
  完整性约束无法声明"派生列 = 查询结果"（CHECK 表达不了跨 relvar 聚合 ⚠️ 产品限制）。
- **II（组织账）**：维护代码侵入应用层；每次 schema 演进要同步改 N 处；一致性 bug 是"安静的"
  （错了也不报错，只是数字不对）。作者结论：反规范化不是权衡，是**推迟还债**。
- 🔧 最小演示（思路，本机 sqlite3 ✅）：`SPJ` 上加 `TOTAL_QTY` 手工汇总列，插入三条供货后只更新
  一处 → `select P, sum(QTY) from SPJ` 与 `TOTAL_QTY` 分歧可查询复现；无任何约束能阻止该分歧。

## 常见误区

- 「宽表/拉链表=反规范化，数仓都这么干」：分析型副本是**另一条数据流水线**（ETL 边界外复制），
  不是把基表设计改坏；OLTP 基表仍应按 03–07 章维护。见 [../数据仓库工具箱3.md](../数据仓库工具箱3.md)
  的"源系统 vs 展现层"分工。
- 「我加了触发器就安全了」：触发器是承诺的书面化，不是兑现——它把一致性逻辑从声明层拖进过程层
  （对照 [../SQL_and_Relational_Theory/10-约束的声明式力量.md](../SQL_and_Relational_Theory/10-约束的声明式力量.md)）。
- 「MySQL 没有真视图性能所以只能冗余」：混淆了"视图不物化"与"物化必手工"——8.3/8.4 的分类学就是治这个的。
- 「列存/索引也是冗余，所以反规范化无罪名」：系统维护与人工维护的分界才是罪名所在（8.2 三要件）。

## 三要件核查表（🔧 把 8.2 定义变成评审动作）

对任何"疑似反规范化"的对象逐项问：

| 问项 | 索引 | 物化视图(PG) | 汇总列(手工) | 数仓副本 |
| --- | --- | --- | --- | --- |
| ①是否额外存储 | 否 | 是 | 是 | 是 |
| ②是否可由现有 relvar 导出 | 是 | 是 | 是 | 是 |
| ③一致性由**系统**维持? | 是 | 否(须手工 REFRESH) | 否 | 流水线重建(半) |
| 判定 | 物理设计 ✅ | **落入反规范化** ⚠️ | 反规范化 ❌ | 界外复制 ⚠️ |

用法：③栏任一"否"即触发 8.5 的账目要求——要么补对偶校验（发现机制），要么撤销冗余。
这张表也是读云产品 MV/DT 宣传页的滤镜：自动刷新程度决定它站在①②③哪一格。

## 核心概念速览（中英对照）

- **反规范化** — denormalization：额外存储可导出事实且人工保持一致性（三要件）
- **冗余副本** — redundant copy：第二事实源；异常温床
- **派生数据** — derived data：可由查询重算出来的值
- **受控冗余** — system-maintained redundancy：物化视图/索引——不算反规范化
- **物理设计** — physical design：索引/集群/分区，声明层之外的正当自由
- **一致性承诺** — consistency promise：手工维护者的隐性契约，本书判其不可靠
- **安静错误** — silent error：冗余分歧不触发任何异常，只污染结果
- **视图** — view：虚表，不存储
- **物化视图** — materialized view：存储的查询结果；系统维护程度决定其性质
- **宽表** — wide/denormalized table：OLAP 展示层产物，勿与 OLTP 设计混谈
- **ETL 边界** — ETL boundary：跨边界复制与界内冗余的分界线 ⚠️ 现代口径
- **延迟还债** — deferred debt：作者对"为了性能"的定性
- **声明不可表达** — inexpressible constraint：跨 relvar 聚合约束在 CHECK 里无处安放 ⚠️
- **处方 vs 病名** — remedy not excuse：视图/索引是性能问题的处方

## 最新演进与工业实践

- **物化视图的分化（2024–2026，✅ 文档/⚠️ 云）**：PostgreSQL 的物化视图仍需手工
  `REFRESH MATERIALIZED VIEW`（https://www.postgresql.org/docs/current/sql-creatematerializedview.html
  与 https://www.postgresql.org/docs/current/rules-materializedviews.html 均 curl 200 ✅）——按 8.2 三要件，
  **PG 的 MV 恰恰落回"反规范化"**；而 Snowflake 自动刷新的动态表/物化视图由系统维护一致性
  （https://docs.snowflake.com/en/user-guide/views-materialized 可达 ✅，行为系文档转述 ⚠️ 不可本机实测）——
  才是作者认可的"受控冗余"。作者的立场在引擎演进后变成一个**产品问题**：你的 MV 是哪种。
- **湖仓宽表的正名**：DuckDB/湖仓场景以扫描吞吐换连接成本（https://duckdb.org/ 可达 ✅，定性转述 ⚠️）；
  用 8.2 定义检验：分析副本经流水线重建、单一真源在基表 → 属"受控冗余"，不是本书反对的对象；
  反对的是把这种形态搬回 OLTP 基表。
- **度量分歧的检测工程化**：对偶校验（对账查询）进入数据可观测性产品（Great Expectations/dbt 等 ⚠️ 未附链）；
  8.5 的"安静错误"正是这类工具存在的理由——冗余一旦自愿引入，须为它建发现机制。

  （https://doi.org/10.1007/978-1-4842-5540-7_19 curl 200 ✅）继续扩论一致性——作者的炮口 2019 年并未收回。
