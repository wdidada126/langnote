# 第 8 章 类型规则与静态检查

> **一句话**：P.20–P.23 是全书最「薄」的一章，却也是工业界做得最狠的一章——它只给了四种够用的模式，而真实的泛型推断、多态检查、错误诊断，全在这四个模式之外。

| 节 / 模式 | 内容 | 结论 |

## 核心精讲

### 类型检查的 visitor 骨架（P.20/P.22，教学示意，不编译、不运行、不参与构建）

```java
// 教学示意代码，不编译、不运行、不参与构建
class TypeChecker extends CalcBaseVisitor<Void> {
  @Override public Void visitAdd(AddContext ctx) {
    visit(ctx.left); visit(ctx.right);
    Type l = ctx.left.type, r = ctx.right.type;
    if (isNumeric(l) && isNumeric(r)) { ctx.type = promote(l, r); return; }  // P.21
    if (l == STRING || r == STRING)   { ctx.type = STRING;   return; }
    throw new TypeError("bad operand types: '" + l + "' and '" + r + "'");
  }
  @Override public Void visitAssign(AssignContext ctx) {
    visit(ctx.rhs); visit(ctx.lhs);
    if (!isAssignable(ctx.lhs.type, ctx.rhs.type))                            // P.22
      throw new TypeError("cannot assign " + ctx.rhs.type + " to " + ctx.lhs.type);
    return null;
  }
}
```

### 类型提升表（P.21 的教学实现，教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
static Type promote(Type a, Type b) {        // 窄 → 宽，按「排名」取大
  int ra = rank(a), rb = rank(b);
  return ra >= rb ? a : b;                   // 真实实现还要管浮点/字符串与整数比较
}
static boolean isAssignable(Type from, Type to) {
  return promote(from, to) == to;            // widening 允许，narrowing 报错
}
```

### 多态检查（P.23 的容器版，教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
class ListType extends Type {
  Type element;
  boolean isAssignableFrom(Type other) {                  // 协变的简化版
    if (!(other instanceof ListType)) return false;
    return element.equals(((ListType) other).element);     // 严格不变（invariant）
  }
}
```

### TypeScript 侧的类型检查器骨架（对照本书 P.20–P.23，教学示意）

```typescript
// 教学示意代码，不编译、不运行、不参与构建
type Type = { kind: "number" } | { kind: "string" } | { kind: "array"; element: Type };
function checkBinary(op: string, l: Type, r: Type): Type {
  if (op === "+" && (l.kind === "string" || r.kind === "string")) return { kind: "string" };
  if (l.kind === "number" && r.kind === "number") return l;
  throw new TypeError(`Operator '${op}' cannot be applied to '${typeName(l)}' and '${typeName(r)}'`);
}
```

### 诊断信息的质量（比类型规则更决定体验，教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
class Diagnostic {
  int line, column, endColumn; String severity; String code; String message;
  boolean isError() { return severity.equals("error"); }
  String formatSource(String lineText) {   // 带波浪线定位的一行输出
    return lineText + "\n" + " ".repeat(column) + "^".repeat(Math.max(1, endColumn - column));
  }
}
```

## 版本演进

| 阶段 | 形态 |
| --- | --- |
| 1960s | Algol 60 无类型；Pascal 引入静态类型 |
| 1978 | ML 的 Hindley-Milner（算法 W）让「推断」成为主流 |
| 1978–1990s | OOP 多态（子类型）与泛型（参数化多态）分野；Eiffel 的 covariant 重定义 debate |
| 2004 | Cardelli & Wegner 综述定型「类型、抽象、多态」的坐标系 |
| 2004–2012 | Java generics 的类型擦除、C# 的协变逆变、Scala 的隐式参数，把类型系统推向「语言设计的政治」层面 |
| 2015–2026 | 「渐进类型」成为主流形态（TypeScript、Python 的类型注解 + mypy/pyright、PHP 的类型系统）；类型检查器从编译器的一部分变成**常驻服务**（Language Server） |

## 常见误区与本书需修正之处

| 误区 / 需修正之处 | 说明 |
| --- | --- |
| 🔧 **本书的类型系统只够玩具**：只有 P.20–P.23 四个模式，没有 subtyping 的完整规则、没有 Hindley-Milner、没有 generics 的擦除/替换 | 需要严肃类型系统时请直接读 TAPL 与 `book/现代编译原理-虎书.md` 第 8 章；不要把本书 P.21 的 promote 表当成通用规则 |
| 🔧 「自动类型提升是好设计」 | P.21 的 `promote` 与 `isAssignable` 会让 C 的整型提升、JS 的 `+` 重载这类历史包袱固化 |
| 🔧 中译本对 `promotion`（提升）与 `inference`（推断）的译法不统一 | 建议统一：promotion = 隐式转换/类型提升，inference = 类型推断 |
| 「类型检查放在解析之后一次做完」 | 生产级实现要增量、要跨文件、要能并行；类型错误的**定位**往往比判定更难 |
| 「静态类型 = 报错」 | 诊断信息质量（列位置、相关代码、修复建议、related information）是产品竞争力，本书这一块几乎没写 |
| 「加了类型就等于安全」 | 内存安全还取决于运行时检查（数组边界、空指针、联合类型标签），这些在本书中未涉及，见 `book/自己动手写编译器链接器.md` 运行时章节 |
