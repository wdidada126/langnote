# 第 5 章 树的遍历与重写

> **一句话**：树建好之后所有活儿都在这章完成——统计、标注、重写、生成；P.12–P.15 给的是四个正交选择：**遍历写在树里还是写在树外、匹配用规则还是用代码、以及要不要真的改树**。

| 节 / 模式 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 Walking Trees and Visitation Order | 前序 / 后序 / 层级序，以及「先算子树还是先算自己和谁」 | 顺序不是风格问题，而是**语义依赖**问题 |

| 5.4 Decoupling Tree Traversal from Pattern Matching | 遍历与「匹配某类节点」解耦 | 匹配规则可与遍历方向独立演进 |

## 核心精讲

### 遍历顺序决定语义（教学示意，不编译、不运行、不参与构建）

```java
// 教学示意代码，不编译、不运行、不参与构建
// 后序：先算子树（解析声明才知道名字，再算引用）
int evalPost(Node n) {
  switch (n.type) {
    case ADD:  return evalPost(n.left) + evalPost(n.right);   // 先 children
    case ID:   return scope.lookup(n.text).value;             // 再自己（依赖 scope 已建）
    ...
  }
}
// 前序：适合「建作用域 → 往里加符号 → 再进子树」
```

### P.13 External Tree Visitor 的 `dispatch` 用法（教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
public interface TreeVisitor<R> {
  R visitAdd(AddNode n);
  R visitVar(VarNode n);
}

public class TypeAnnotator implements TreeVisitor<Void> {   // 边遍历边给节点打标签
  Scope scope;
  public Void visitAdd(AddNode n) {
    n.left.dispatch(this); n.right.dispatch(this);         // 先子后己
    n.type = unify(n.left.type, n.right.type);             // 再写自己的属性
    return null;
  }
  public Void visitVar(VarNode n) {
    n.type = scope.lookup(n.text).type;                    // 依赖已建好的 scope
    return null;
  }
}
// 调用端
tree.dispatch(new TypeAnnotator());
```

### P.15 Tree Pattern Matcher 的思路（教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
// 目标：把所有形如 "a * 0" 的乘法折叠成 0（常量折叠 + 代数化简）
class FoldingMatcher {
  boolean matchMulZero(Node n, Node[] binds) {   // 模式：X * 0 或 0 * X
    if (n.type != MUL) return false;
    if (isConstZero(n.left))  { binds[0] = n.right; return true; }
    if (isConstZero(n.right)) { binds[0] = n.left;  return true; }
    return false;
  }
}
```

> 现代语言实现的做法（如 `book/LLVM编译器原理与实践.md` 里的 Instruction Combining pass）：用**一整套 IR 遍历框架 + 模式匹配库**替代手工 visitor，匹配器还能直接生成 C++ 代码。

### 语法级重写的形状（P.14，ANTLR 3 风格；教学示意）

```antlr
// 教学示意代码，不编译、不运行、不参与构建
// ANTLR 3 tree grammar：用语法描述「如何改写树」
tree grammar Rewrite;
options { output=AST; }
mul : ^(MUL a=expr b=expr) -> ^(MUL {$a}* {$b}*) ;   // 命中则重写
    | expr ;
```

### TypeScript 侧的现代替代：联合类型 + 手写递归（教学示意）

```typescript
// 教学示意代码，不编译、不运行、不参与构建
type Node = { kind: "add"; left: Node; right: Node } | { kind: "num"; value: number };
// 用 discriminated union 表达 P.11 的异构树，避免 visitor class 层次
function evalNode(n: Node, scope: Scope): number {
  switch (n.kind) {                    // TypeScript 在此处做穷尽性检查
    case "add": return evalNode(n.left, scope) + evalNode(n.right, scope);
    case "num": return n.value;
  }
}
```

## 版本演进

| 阶段 | 形态 |
| --- | --- |
| 语法导向翻译（1970s） | 属性文法在解析时一次性算出，不产树 |
| ANTLR 1/2 | 动作写在 grammar 里，遍历与语义合一 |
| ANTLR 3（2006） | tree grammar（P.14）成熟：用语法描述遍历与重写；StringTemplate 配合输出 |
| 2013（ANTLR 4） | **tree grammar 被弃用**，改用 listener/visitor + 语法动作；重写逻辑回到过程式代码 |
| 2015–2026 | 主流语言实现转向「**IR 上的 pass**」（LLVM pass manager、rustc MIR pass、TS 的 checker pass）；visitor 退居-secondary 角色，只有「语法层的结构化处理」（格式器、重构）还用它 |

## 常见误区与本书需修正之处

| 误区 / 需修正之处 | 说明 |
| --- | --- |
| 🔧 「visitor 一定比手写 switch 好」 | ANTLR 官方在 P5.0 勘误里讨论过：基于 `switch (token/ruleType)` 的 visitor 在「加一个节点类型」时改动更集中，而传统双分派 visitor 要改所有 visit 方法；两者取舍取决于语言规模 |
| 🔧 P.14 Tree Grammar 在 ANTLR 4 已被放弃 | 本书基于 ANTLR 3 的 tree grammar 与 `output=AST` 写法不再推荐；新项目用 visitor/listener + 过程式重写 |
| 🔧 中文版基于 2009–2012 前的示例，遍历代码风格偏「一个 visitor 干所有事」 | 现代实践是拆成多个单一职责的 visitor/pass（annotator、checker、optimizer 各一个） |
| 「遍历顺序随便选」 | 顺序就是依赖图：作用域标注必须前序、类型求值通常是后序、常量折叠则要看 pass 顺序 |
| 「重写一定要原地改树」 | 生成新树（functional rewriting）在并发、编辑器、增量场景里更安全，代价是分配开销 |
| 「模式匹配只是语法糖」 | 在树/IR 优化里它就是核心机制；JS 生态 2022 年才推进「模式匹配提案」，与该思路长期缺席有关 |
