## 核心精讲

### 语言应用的通用骨架（伪代码，非任何语言）

```
输入流 ──[ 词法 : 字符 → token ]──> TokenStream
TokenStream ──[ 语法 : 递归下降 / 生成器 ]──> 中间表示（Parse Tree / AST / Holder Tree）
中间表示 ──[ 语义 : 符号表 / 类型检查 / 重写 ]──> 标注后的树
标注后的树 ──[ 后端 : 模板展开 / 解释执行 / 字节码 ]──> 输出（源码、配置、字节码、副作用）
```

> 这张骨架就是全书 P.1–P.31 的坐标轴：**左边两格是解析（Ch2、Ch3），中间一格是分析（Ch4–Ch8），右边一格是生成与执行（Ch9–Ch12），Ch13 是四个综合案例。**

### 用 ANTLR 表达同一骨架的骨架代码（教学示意，不编译、不运行、不参与构建）

```antlr
// HelloLang.g4  —— 一个最小的语言应用骨架
grammar HelloLang;

// ① 词法层：字符 → token（大写开头）
ID   : [a-zA-Z_][a-zA-Z_0-9]* ;
INT  : [0-9]+ ;
WS   : [ \t\r\n]+ -> skip ;          // 跳过，不进 token 流
LINE : '//' ~[\r\n]* -> skip ;

// ② 语法层：token → 语法结构（小写开头）
program : stat+ EOF ;
stat    : 'print' '(' ID ')' ';'                          # 打印语句
        | 'def' ID '(' ID (',' ID)* ')' block             # 函数定义
        | 'if' '(' ID ')' block                           # 条件语句
        ;
block   : '{' stat* '}'                                   # 语句块
        ;
```

### 手写版骨架（对照 P.1 Mapping Grammars to Recursive-Descent Recognizers）

```java
// 教学示意代码，不编译、不运行、不参与构建
class Parser {
  Lexer lexer;  TokenStream tokens;  Token lookahead;
  void program() {                    // 对应 grammar 的 program 规则
    while (lookahead.type != EOF) stat();
  }
  void stat() {
    switch (lookahead.type) {         // LL(1)：用前看 token 选择分支
      case PRINT: match(PRINT); match(LPAREN); match(ID); match(RPAREN); match(SEMI); break;
      case DEF:   ...                 break;
      case IF:    ...                 break;
      default:    throw new SyntaxError("unexpected " + lookahead.text);
    }
  }
  void match(int t) { if (lookahead.type == t) consume(); else throw new SyntaxError(...); }
}
```

> P.1 的核心洞察：**语法规则与递归下降函数是同构的**；把 grammar 的每条规则翻译成一个方法、每个选项翻译成一个 `switch` 分支，就得到解析器。这也是为什么 ANTLR 生成的代码「可读但很啰嗦」。

### 用 lark 表达同一件事（Python 侧对照，教学示意）

```python
# 教学示意代码，不编译、不运行、不参与构建
from lark import Lark, Transformer

grammar = """
    ?start: statement+
    ?statement: "print" "(" NAME ")" ";"
             | "def" NAME "(" [NAME ("," NAME)*] ")" block
             | "if" "(" NAME ")" block
    ?block: "{" statement* "}"
    %import common.CNAME -> NAME
    %import common.INT
    %import common.WS
    %ignore WS
"""

parser = Lark(grammar, parser="lalr")   # 也可试 parser="earley"
tree = parser.parse("def f(x) { print(x); }")
```

## 版本演进

- **1990s 的「语言应用 = 编译器」心智**：一提处理输入文件就想 lex + yacc，结果为一个 20 行的配置格式造了一整套工具链。本书标题里刻意去掉 "compiler"，改叫 "language application"，正是在反这件事。
- **ANTLR 1 / 2 时代（1992–1998）**：语法与代码分离靠 syntactic predicate，代价是语法里混入大量 Java 代码片段。
- **ANTLR 3（2006）**： grammar 与 action 完全分离，模板（StringTemplate）与树语法（tree grammar）成为一等公民——**本书就是这套世界观的产物**。
- **ANTLR 4（2013）之后**：`*_listener` / `*_baseVisitor` 取代 tree grammar，`StringTemplate` 从核心方案降级为「可选模板库」，本书 Ch12 的经验需要重新落地一次。
- **2015–2026**：语言应用的主战场从「编译器前端」漂移到「编辑器里的实时反馈」，Tree-sitter 一代把「解析」变成**增量、容错、毫秒级**的服务；ANTLR 则退回「离线、一次性、要完整语义」的场景。

## 近年研究与工业界开源实践（2015–2026）

**趋势**：语言应用的实现成本在下降（生成器更聪明、运行时更多语言），但「维护一门语言的成本」并没有下降——真正的成本在语义规则、诊断质量和测试。同时，增量解析与 LLM 让「语言」从编译器的附属品变成了产品接口。

| 仓库 | star（2026-09-25 `gh api` 实测） | 说明 |
| --- | --- | --- |
| `antlr/antlr4` | **19,014★** | 本书的官方工具；最新稳定版 4.13.2（2024-08） |
| `tree-sitter/tree-sitter` | **27,043★** | 增量解析 + 容错解析，现代编辑器语法的事实标准 |
| `lark-parser/lark` | **5,991★** | Python 侧的「本书对位物」，语法极短，适合验证小 DSL |

## 常见误区与本书需修正之处

| 误区 / 需修正之处 | 说明 |
| --- | --- |
| 🔧 「这本书有 44 个模式」 | 官方目录给出的是 **P.1–P.31，共 31 个模式**；中译本简介也写 31 种。流传的「44」与「三大部分」都不准确，原书实际是 **4 个 Part、13 章** |
| 🔧 「中译本与原文同版」 | 中译本 2012-03 出版，比原书晚两年多，且**未翻译附录 A Bibliography**；页码、术语（如 "Pattern" 有的译作「模式」有的混用）与原书不一致 |
| 🔧 「ANTLR 是唯一可行工具」 | 本书世界观基于 ANTLR 3 + StringTemplate；今天做小 DSL 直接上手 `lark` / `Tree-sitter` / 手写递归下降往往更快，ANTLR 适合「语法复杂 + 要多语言运行时」的重活 |
| 「语言应用都很简单」 | 1.4 的选型表看着轻松，但真正的成本在符号表、类型规则、诊断信息与测试；「自己写一门语言的 DSL」的工期常被低估 3–5 倍 |
| 「先有语法再有代码」 | 实践中通常是**先有代码里的字符串处理，被逼着长大成 DSL**；本书 1.4 给出的判断标准是：出现第 3 处同样的字符串解析时，就该造语言 |
| 「本书覆盖完整编译器」 | 不覆盖。IR、优化、寄存器分配一律不谈（详见 `00` 的缺口表） |
