# 第 2 章 基本解析模式（递归下降与词法）

> **一句话**：P.1–P.4 是全书的地基——把 grammar 翻译成递归下降函数（`P.3`/`P.4`），把字符流切成 token（`P.2`），而 `P.1` 告诉你翻译这件事在结构上和解释是同一回事。

---

## 本章地图

| 节 / 模式 | 内容 | 结论 |
| --- | --- | --- |
| 2.1 Identifying Phrase Structure | 用「短语结构」描述语言，语法与语义分离 | 语法 ≠ 语义；先把短语结构写清楚，动作代码才有地方挂 |
| 2.2 Building Recursive-Descent Parsers | 语法规则 → 一个函数；选项 → `if/switch` | 递归下降是本书所有解析模式的默认形态 |
| P.1 Mapping Grammars to Recursive-Descent Recognizers | grammar 到代码的机械映射 | 映射是**机械的**，所以可以交给生成器 |
| P.2 LL(1) Recursive-Descent Lexer | 字符 → token 的手写分词器 | 词法其实就是一个「有状态的正则匹配器」，不需要正式 DFA |
| P.3 LL(1) Recursive-Descent Parser | 一个前看 token 就能决策的解析器 | 简单、可调试；代价是只能吃 LL(1) 语法 |
| P.4 LL(k) Recursive-Descent Parser | 需要 k 个 token 前看时的三种写法（前看缓冲 / 参数传下去 / 语法改写） | 前看 k 越大代码越丑，**改语法比加前看便宜** |
| 2.3 Parser Construction Using a Grammar DSL | 用 grammar 文件驱动生成，而不是手写 | 语法变了不用改代码；这是 ANTLR 的立足点 |
| 2.4 Tokenizing Sentences | 词法细节：token 类型、跳空白、把 token 与文本对应起来 | 词法层的决定会一路影响错误提示质量 |

## 核心精讲

### 一个完整的 .g4 语法骨架（教学示意，不编译、不运行、不参与构建）

```antlr
// Calc.g4 —— P.1/P.4 的教学骨架：LL(1) 能表达的部分先写清楚
grammar Calc;

// 词法规则（大写开头）
MULT : '*' ;
ADD  : '+' ;
LPAREN : '(' ;
RPAREN : ')' ;
INT  : [0-9]+ ;
WS   : [ \t\r\n]+ -> skip ;      // skip：完全丢弃；channel(HIDDEN)：留给词法高亮用

// 语法规则（小写开头）；直接左递归在 ANTLR 4 里自动改写
calc : expr EOF ;
expr : expr ADD expr      # 加法（左结合）
     | expr MULT expr     # 乘法（左结合）
     | INT                # 数字
     | LPAREN expr RPAREN # 括号
     ;
```

> 对照 P.4（LL(k)）：ANTLR 3/4 会自动把上述左递归改写成循环形式；手写递归下降时你得自己决定「是先拉前看再决定，还是把整棵子树传下去」。

### 手写 LL(1) lexer（P.2，教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
class Lexer {
  String input; int p = 0;
  List<Token> tokens = new ArrayList<>();
  Token next() {                     // 跳过空白 → 按首字符分派 → 消费最长匹配
    skipWhitespace();
    if (p >= input.length()) return new Token(EOF, "<EOF>", p);
    char c = input.charAt(p);
    if (Character.isDigit(c)) { int start = p; while (p < input.length() && Character.isDigit(input.charAt(p))) p++;
                                return new Token(INT, input.substring(start, p), start); }
    if (c == '+') { p++; return new Token(ADD, "+", p - 1); }
    // ... 其余 token 同理
    throw new LexerError("bad char '" + c + "' at " + p);
  }
}
```

### 手写 LL(1) parser（P.3，教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
class Parser {
  List<Token> ts; int i = 0;
  Token LA() { return i < ts.size() ? ts.get(i) : ts.get(ts.size() - 1); }
  void match(int type) { if (LA().type == type) i++; else throw new SyntaxError(expected(type), LA()); }

  Node program() {                    // bottom-up：边解析边建树
    Node root = new Node("program");
    while (LA().type != EOF) root.add(statement());
    return root;
  }
  Node statement() {
    switch (LA().type) {
      case ID:   match(ID); match(EQ); Node e = expr(); match(SEMI);
                 return new Assign(lastID, e);
      case INT:  return expr();        // 表达式语句
      default:   throw new SyntaxError("unexpected token " + LA());
    }
  }
  Node expr() {
    Node n = term();
    while (LA().type == PLUS || LA().type == MINUS) {  // 左结合靠 while 而非递归
      int op = consume().type; n = new BinOp(op, n, term());
    }
    return n;
  }
  Node term() { Node n = primary(); while (LA().type == STAR) { ... } return n; }
  Node primary() { if (LA().type == INT) return new IntLit(consume()); match(LPAREN); Node e = expr(); match(RPAREN); return e; }
}
```

### 用 lark 做同一件事（Python 对照，教学示意）

```python
# 教学示意代码，不编译、不运行、不参与构建
from lark import Lark, Transformer, v_args

calc_grammar = """
    ?start: expr
    ?expr: term (ADD term)*
         | term
    ?term: atom (MULT atom)*
         | atom
    ?atom: INT
         | "(" expr ")"
    %import common.CNAME -> ID
    %import common.INT
    %import common.WS
    %ignore WS
"""

class Calculate(Transformer):
    @v_args(inline=True)
    def expr(self, *args):
        result, right = args
        return result + right

parser = Lark(calc_grammar, parser="lalr", maybe_placeholders=False)
print(Calculate().transform(parser.parse("(1+2)*3")).value)
```

### ANTLR 侧的树产出与访问（教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
ParseTree tree = parser.calc();            // 默认产出 parse tree（CST）
ParseTreeWalker.DEFAULT.walk(new CalcBaseListener() {
  @Override public void exitExpr(ExprContext ctx) { /* 语法动作位置 */ }
}, tree);
// 或走 visitor
Integer v = new CalcBaseVisitor<Integer>() {
  @Override public Integer visitInt(IntContext ctx) { return Integer.valueOf(ctx.INT().getText()); }
  @Override public Integer visitMul(MulContext ctx) { return visit(ctx.expr(0)) * visit(ctx.expr(1)); }
}.visit(tree);
```

## 版本演进

| 阶段 | 形态 |
| --- | --- |
| 手写时代 | lex + yacc：`y` 文件里写语法、`%.o` 里写动作，调试靠打印；LL(1) 冲突全靠 %left 手工消 |
| 1992–1998（ANTLR 1/2） | 语法谓词 `{...}?` 让前看变成「跑一段代码看看成不成」，代价是语法里混 Java |
| 2006（ANTLR 3） | 语法与动作彻底分离，生成可读的递归下降代码——本书 Ch2/Ch3 的代码形态 |
| 2013（ANTLR 4） | ALL(\*) 让「前看多少」不再由人指定；左递归自动改写；listener/visitor 取代 tree grammar |
| 2015–2026 | 手写递归下降（尤其 Rust/TS 生态）重新流行，因为**小语法手写比 generator 更快**；生成器退守「大语法 / 多语言 / 要 IDE」场景 |

## 常见误区与本书需修正之处

| 误区 / 需修正之处 | 说明 |
| --- | --- |
| 🔧 「LL(1) 不够就加前看」 | 加前看会让代码指数变丑。P.4 给的替代路径是**改写语法**（提取公共前缀、引入中间规则），本书在歧义那一章反复强调这点 |
| 🔧 「词法可以交给正则引擎」 | 真实 lexer 要处理最长匹配优先、共享前缀、`-> channel(HIDDEN)`（供高亮用）等；`P.2` 手写的几十行其实更接近真实 lexer 的形状 |
| 🔧 本书基于 ANTLR 3，示例里 `options { k=2 }` 之类的写法在 ANTLR 4 已废弃 | 现在应依赖 ALL(\*) 自适应预测，不要手设 `k` |
| 🔧 「递归下降 = 慢」 | 对绝大多数语言应用（配置文件、SQL、DSL）完全够用；真正的性能瓶颈通常在语义阶段（符号表、类型检查）而非解析 |
| 「token 类型越少越好」 | token 划分直接决定错误提示质量；`channel(HIDDEN)` 是个被低估的开关 |
| 「语法写完就完事」 | 语法也要维护：改一个规则要同步改 visitor/listener/测试；这是 LDTA 2010 论文的核心结论 |
