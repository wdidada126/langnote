# 第 11–12 章 翻译计算机语言与用模板生成 DSL

> **一句话**：P.29–P.31 解决「把一门语言翻译成另一门语言」，Ch12 解决「把语言应用变成代码生成器」；本书用的是 StringTemplate——**这套技术栈如今已进入维护状态，但模式骨架仍然有效，只是要换引擎**。

## 核心精讲

### P.30 Rule-Based Translator 的骨架（教学示意，不编译、不运行、不参与构建）

```java
// 教学示意代码，不编译、不运行、不参与构建
class Translator extends CalcBaseVisitor<Void> {   // 每条规则 = 一条翻译规则
  StringBuilder out = new StringBuilder();
  @Override public Void visitAssign(AssignContext ctx) {
    visit(ctx.lhs); out.append(" = ");
    visit(ctx.expr());       out.append(";\n");
    return null;
  }
  @Override public Void visitAdd(AddContext ctx) {
    out.append("("); visit(ctx.left); out.append(" + "); visit(ctx.right); out.append(")");
    return null;             // 括号保留 = 避免优先级错误
  }
}
```

### 模板方案（StringTemplate 语法；教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
STGroup group = new STGroupFile("Java.stg");          // 目标语言模板组
ST file = group.getInstanceOf("memberFile");
file.add("package",  "com.example");
file.add("imports",  "java.util.List");               // 列表会自动展开
file.add("members",  new MemberModel("x", "int"));    // 每个成员渲染成一个片段
file.add("methods",  new MethodModel("getX", "int", "x"));
System.out.println(file.render());                    // 输出目标语言源码
```

```text
// Java.stg（模板文件）
memberFile(package, imports, members, methods) ::= <<
package <package>;
<imports:{i|import <i>;}>
public class Foo {
  <members:{m|private <m.type> <m.name>;\n}>
  <methods:{m|public <m.ret> <m.name>() { return <m.body>; }\n}>
}
>>
```

> 这就是 P.31 的「同一份输入模型 + 不同的模板组 = 不同的目标语言」。

### 输出导向 vs 模型导向的差别（教学示意）

```python
# 教学示意代码，不编译、不运行、不参与构建
# ① 输出导向：边遍历边 print（P.29 风格，简单但不能回看）
def gen_assign(node, out): out.write(f"{node.name} = {gen(node.expr, out)};")

# ② 模型导向：先造目标模型，再渲染（P.30/P.31 风格，可测试、可复用）
class Ir: pass
def to_ir(node) -> Ir:
    if node.kind == "add": return Ir("add", to_ir(node.left), to_ir(node.right))
    if node.kind == "num": return Ir("num", node.value)
def render(ir) -> str:
    if ir.op == "add": return f"({render(ir.left)} + {render(ir.right)})"
    return str(ir.value)
```

### lark + Jinja 的等价做法（Python 侧对照，教学示意）

```python
# 教学示意代码，不编译、不运行、不参与构建
from lark import Lark, Transformer
class ToPython(Transformer):
    def number(self, t): return f"({t.value})"
    def add(self, a, b): return f"{a} + {b}"
def gen(tree):  return ToPython().transform(tree)
```

## 版本演进

| 阶段 | 形态 |
| --- | --- |
| 1968 | Knuth 的属性文法、语法导向翻译：翻译规则写在语法里 |
| 1970s | 「翻译方案」理论与 L-attributed 翻译 |
| 1990s | StringTemplate（Parr 的第二个作品）与 codegen 模板文化 |
| 2006 | ANTLR 3 把 StringTemplate 深度绑进 tree grammar 的重写输出 |
| 2013 | ANTLR 4 去掉 tree grammar、StringTemplate 降为可选；翻译重回过程式 visitor |
| 2013–2026 | **StringTemplate 进入维护**（最后一次重要版本是 4.0.x）；替代品换成 Jinja2 / Mako / Handlebars / Go text/template / C# 的 Razor 与 T4；而「代码生成」的主流形态变成 **IR → 目标语言** 与 **DSL → 配置**（如 Kubernetes 的 CUE、KCL） |
| 2022–2026 | LLM 生成模板与模板反向生成文档/代码成为新用法；模板本身成为「人类可读、模型可写」的契约 |

## 常见误区与本书需修正之处

| 误区 / 需修正之处 | 说明 |
| --- | --- |
| 🔧 **StringTemplate 已经不是新项目的选择**：本书 Ch12 整章依赖它，而 ST4 已进入维护 | 模板思想依然成立，但请换成 `python` 的 Jinja2、Go 的 `text/template`、或语言自带的生成工具；语法差异见 `09-翻译与模板生成.md` 的示例代码注释 |
| 🔧 中译本对 StringTemplate 的译名不统一（有的译「字符串模板」） | 建议保留英文 StringTemplate，译作「字符串模板引擎」时加注 |
| 🔧 P.31 Target-Specific Generator Classes 是 ANTLR 3 概念 | ANTLR 4 的等价物是「visitor 生成目标代码 + 模板文件」，用法见 `book/antlr4权威指南.md` |
| 「模板生成 = 字符串拼接」 | StringTemplate 的独门是「模板属性作用域 + 自动缩进 + 列表展开」，正是这些让它比朴素拼接更可控 |
| 「先生成代码再编译」总是最快的」 | 生成的代码往往下一跳就要调试；保留源位置（source map 思路）比生成得漂亮更重要 |
| 「模板方案不可测试」 | 正确做法是「输入模型 + 模板 = 输出」三段式；把输入模型做成纯数据结构，模板就变成可单测的渲染函数 |
