# 第 9–10 章 解释器与字节码虚拟机

> **一句话**：P.24–P.28 给出解释器家族的五级台阶——语法直接翻译（P.24）→ 树上求值（P.25）→ 字节码汇编（P.26）→ 栈式 VM（P.27）→ 寄存器式 VM（P.28）；台阶越高越难写，但启动越快、越接近真实运行时。

## 核心精讲

### P.25 树遍历解释器的骨架（教学示意，不编译、不运行、不参与构建）

```java
// 教学示意代码，不编译、不运行、不参与构建
class TreeInterpreter extends CalcBaseVisitor<Object> {
  CallStack frames = new CallStack();

  @Override public Object visitAssign(AssignContext ctx) {
    frames.peek().put(ctx.ID().getText(), visit(ctx.expr()));    // 变量存在环境里
    return null;
  }
  @Override public Object visitAdd(AddContext ctx) {
    Object a = visit(ctx.left), b = visit(ctx.right);
    return asNum(a) + asNum(b);
  }
  @Override public Object visitCall(CallContext ctx) {           // 函数调用 = 新环境 + 递归
    Env saved = frames.peek();
    Env env = new Env(saved);  env.define("arg", visit(ctx.arg()));
    frames.push(env);
    Object r = visit(ctx.func());
    frames.pop(); frames.setTop(saved);
    return r;
  }
}
```

### P.27 栈式字节码 VM（教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
class StackVM {                     // 教学示意：只需要理解「栈 + pc + 大 switch」
  int[] code; int pc = 0;
  Object[] stack = new Object[256]; int sp = -1;
  void push(Object v) { stack[++sp] = v; }
  Object pop() { return stack[sp--]; }

  void run() {
    while (pc < code.length) {
      int op = code[pc++];
      switch (op) {
        case ICONST: push(code[pc++]);                 break;   // 常量入栈
        case IADD:   { Object b = pop(), a = pop(); push(asNum(a) + asNum(b)); } break; // 二元运算消费栈顶
        case ISTORE: { int slot = code[pc++]; locals[slot] = pop(); } break;           // 存到局部变量槽
        case ILOAD:  { int slot = code[pc++]; push(locals[slot]); }    break;          // 从槽加载
        case HALT:   return;
      }
    }
  }
}
```

### P.28 寄存器式 VM 的差别（教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
// 栈式：  ICONST 1; ICONST 2; IADD; ISTORE 0
// 寄存器： ADDR 0, 1, 2      → 一条指令完成「取两数相加存入 r0」
class RegVM {
  int[][] code; int pc = 0;
  int[] regs = new int[16];
  void run() {
    while (pc < code.length) {
      int op = code[pc][0], a = code[pc][1], b = code[pc][2], c = code[pc][3];
      switch (op) {
        case ADD: regs[a] = regs[b] + regs[c]; break;   //  operands 显式给出，不需要栈
        case MOVE: regs[a] = regs[b];          break;
      }
      pc++;
    }
  }
}
```

### P.26 字节码汇编器的形状（教学示意）

```java
// 教学示意代码，不编译、不运行、不参与构建
class Assembler {
  ByteArrayOutputStream code = new ByteArrayOutputStream();
  Map<String, Integer> labels = new LinkedHashMap<>();
  Map<Integer, String> pendingFixes = new LinkedHashMap<>();  // 前向引用待回填
  void emit(int op) { code.write(op); }
  void emitLabel(String name) { labels.put(name, code.size()); }
  void patch(String label) { int at = pendingFixes.remove(label); writeAt(at, labels.get(label)); }
}
```

## 版本演进

| 阶段 | 形态 |
| --- | --- |
| 1962 | Knuth 的 MIX 机与 Algol 的 syntax-directed 翻译；解释执行一度是主流（APL、BASIC、LISP 都在解释） |
| 1970s–80s | 编译成机器码成为性能共识；但 SCRATCHPAD、Smalltalk 的 image 模型让「解释器 + 增量重编译」复活 |
| 1995 | JVM 与 CLR 用栈式字节码，把 P.27 标准化 |
| 2005–2010 | Dalvik（寄存器式）、LuaJIT、Lua 5.1 之后，P.28 在移动端与脚本场景胜出 |
| 2013–2018 | JavaScript 的 JIT（V8 Ignition 栈式 → TurboFan 优化）与「解释器 + 基线编译 + 优化编译」三层结构成为教科书 |
| 2018–2026 | WASM（栈式字节码）、PyPy 的 RPython tracing JIT、以及「把语言应用跑在 WASM 上」成为新常态 |

## 常见误区与本书需修正之处

| 误区 / 需修正之处 | 说明 |
| --- | --- |
| 🔧 本章的 VM 是**玩具**级别：没有尾调用优化、没有异常处理、没有 GC、没有并发 | 真实运行时要处理的远比这多；见 `book/虚拟机设计与实现.md` 与 `book/C++并发编程实战2/` 的并发部分 |
| 🔧 ANTLR 4 的模型是「解析 → 遍历 → 生成」，本书第九章用 grammar 动作直接产出字节码的写法已过时 | 新项目建议「前端只产树，后端用 IR/模板」分离，参考 `book/antlr4权威指南.md` 与 `book/LLVM编译器原理与实践.md` |
| 🔧 中译本用「字节码解释器」译 bytecode interpreter，与 bytecode compiler 容易混淆 | 建议区分：bytecode = 字节码；VM = 虚拟机；JIT = 即时编译器 |
| 「栈式一定比寄存器式慢」 | 差别在于指令条数与局部变量访问；现代 VM（WASM、JVM）选栈式是因为**流验证（verification）与实现简单性**更值钱 |
| 「解释器不能做优化」 | 现代解释器都带内联缓存、栈上替换、以及内联缓存 + 类型反馈；本书的模型太简单 |
| 「自己写一门 DSL 的解释器就行」 | 真正难的是错误诊断、栈回溯（stack trace 要带行号与源码行）、以及和宿主语言的互操作成本（见 `10-工程实践与综合案例.md`） |
