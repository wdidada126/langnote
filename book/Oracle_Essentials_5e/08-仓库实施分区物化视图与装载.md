# 08 仓库实施：分区、物化视图与装载（⚠️ 推定重构章 · 对应原书"DW Implementation/Population"主题域）

> 章名与章号为 ⚠️ 主题重构（[00 §二降级声明](00-总览与阅读地图.md)）。本章把 [07 章](07-数据仓库基础与体系结构.md) 的蓝图落成工程四件套：分区、物化视图、并行、装载窗口。Oracle 侧一律 ⚠️ 转述；🔧 为 SQLite/DuckDB 实测，非 Oracle。

## 1. 分区：把大表切成可管理的片（⚠️ 转述）

- 动机三分：查询**分区消除**（只扫相关片）、装载**窗口管理**（按片交换/删除）、备份**粒度细化**（按片备份）——导游册强调"分区首先是管理工具，性能收益是第二性的" ⚠️。
- 方法谱系：范围（时间轴主力）/列表（地区类离散值）/哈希（打散热点）/间隔（自动扩范围片）/复合（两级组合）⚠️。
- 关键机制词：分区消除（优化器裁剪）、**交换分区**（EXCHANGE PARTITION=毫秒级把装载好的表挂成一片）、全局 vs 本地索引 ⚠️。
- 成本侧纵深：分区对统计/选择度的影响链见 [#23 CBOF/09-查询变换.md](../Cost_Based_Oracle_Fundamentals/09-查询变换.md)；物理设计权衡见 [#42 TOP/16-优化物理设计.md](../Troubleshooting_Oracle_Performance_2e/16-优化物理设计.md)。

## 2. 🔧 T13 · 伪分区实验：无裁剪的教训（非 Oracle）

```
子表 sales_2022/sales_2023/sales_2024 + 视图 sales_all(UNION ALL 带 yr 常量列)
查询 WHERE yr='2024' -> 结果正确 ('2024','x',2024.0)
EXPLAIN QUERY PLAN -> "COMPOUND QUERY / UNION ALL / SCAN sales_2022 / SCAN sales_2023 / ..."
```

- 实测判读（🔧）：谓词**没有**剪掉 2022/2023 分支——视图计划里每个子表都 SCAN。SQLite 的 UNION ALL 视图不做约束消除。
- 教学结论：这正是 Oracle "分区消除"（⚠️ 优化器按分区键谓词裁剪）与"手工分表"的分水岭：**分片≠可裁剪**。导游册里一句带过的特性，被 🔧 反例放大了价值。
- 外推登记：PG 的继承+约束排除、DuckDB 的按文件/row-group 剪枝属另一谱系 ⚠️ 转述（本波未实测，留主代理选型）。

## 2b. 分区收益的分层拆解（⚠️ 转述；导游册式判断树）

- 第一层（必得）：管理粒度——DROP/TRUNCATE 一片=瞬时归档旧数据，对比 DELETE 百万行+undo/redo 洪水 ⚠️。
- 第二层（常见）：扫描量——消除后只碰相关片的块（[02 章](02-物理存储结构与表空间.md) 的块算术×[07 章](07-数据仓库基础与体系结构.md) 的第二套算术）。
- 第三层（条件得）：并行对齐——片数≥DOP 时 PX 从属进程负载均衡 ⚠️；索引维护成本随全局/本地选择反向变化 ⚠️。
- 判断树一句话：**没有生命周期管理需求就不要为了"看起来像仓库"而上分区**——成本侧的统计/裁剪失效案例见 [#42 TOP/16-优化物理设计.md](../Troubleshooting_Oracle_Performance_2e/16-优化物理设计.md)。

## 3. 物化视图：预聚合格子的制度化（⚠️ 转述）

- MV=真实段（占 [02 章](02-物理存储结构与表空间.md) 空间、有段生命周期）——与"视图是查询别名"的根本差异 ⚠️。
- 刷新体制：ON COMMIT（事务内同步，OLTP 税重）vs ON DEMAND（装载窗口驱动）；FAST（增量）vs COMPLETE（重算）；刷新组与原子性 ⚠️。
- **查询改写**（query rewrite）：优化器把基表查询自动改道 MV——本章与 [#23 CBOF/09-查询变换.md](../Cost_Based_Oracle_Fundamentals/09-查询变换.md) 的正式接口；改写前提（一致性保证/维度对齐）⚠️。
- 设计循环：格子上"哪些组合被反复问"来自 [05 章](05-数据字典与动态性能视图.md) 统计与 AWR 的重复 SQL 画像（⚠️ 观测闭环）。

## 4. 🔧 T11 · MV 经济学的可测版本（非 Oracle）

- 实测链（SQLite，30 万行事实表）：即席 join 聚合 **155.2ms** → `CREATE TABLE mv_region AS SELECT...GROUP BY` 构建 **131.0ms** → 改读 MV **0.11ms**，三值同源（13499865000.0 一致）。
- 三条判读：① "一次构建反复摊销"的 MV 第一定理被 3 个数字钉死；② 构建成本≈一次即席查询——**刷新代价**才是 MV 的长期税（对应 ⚠️ FAST refresh 的存在动机）；③ MV 正确性需重算对齐——Oracle 侧由刷新机制+约束保证 ⚠️，🔧 侧只能手工（装载窗口后重建）。
- T12 补充（DuckDB）：同一数据经 sqlite_attach 聚合 31.2ms（[07 章](07-数据仓库基础与体系结构.md) 复用了该组）——列存引擎下"即席够快，是否还要 MV"成为新的三角权衡 ⚠️ 类比。

## 4b. 🔧 T11 三数字的最小复现代码（非 Oracle；数字=实测）

```python
import sqlite3, time
s = sqlite3.connect("g5.db")   # 同 07 章 2b 的星型库
t0 = time.perf_counter()
row = s.execute("SELECT SUM(f.amt) FROM fact_sales f"
                " JOIN dim_store d ON f.store_id=d.store_id"
                " WHERE d.region='R1'").fetchone()
t1 = time.perf_counter()      # 🔧 155.2ms 即席聚合
s.execute("CREATE TABLE mv_region AS SELECT d.region,"
          " SUM(f.amt) s FROM fact_sales f JOIN dim_store d"
          " ON f.store_id=d.store_id GROUP BY 1")
t2 = time.perf_counter()      # 🔧 131.0ms MV 构建
res = s.execute("SELECT s FROM mv_region"
                " WHERE region='R1'").fetchone()
t3 = time.perf_counter()      # 🔧 0.11ms 改读 MV
# 断言：res[0] == row[0] == 13499865000.0（三值同源）
```

- 复算提示：数值随机器波动，**比值结构**（构建≈即席、读取≈即席的 1/1000）才是可带走的部分；此段与 `exp2.py` G5.1–G5.3 同源。

## 5. 并行执行与装载窗口（⚠️ 转述）

- 并行查询：PX 从属进程（P00x，[03 章](03-实例内存与后台进程.md) 名册）按 DOP 切片扫描/连接/聚合 ⚠️；粒度天然对齐分区（[07 章](07-数据仓库基础与体系结构.md) §5 第一项的工程化）。
- 装载窗口剧本（导游册式流程，⚠️）：暂存表装载（SQL*Loader/外部表，[06 章](06-服务器工具与实用程序.md)）→ 清洗/转换（T 在暂存侧做）→ 索引维护择时 → **EXCHANGE PARTITION** 秒挂 → 统计刷新 → 旧窗口片 DROP——"分区交换+本地索引+并行"三件套的编年史。
- 反模式登记（⚠️ 社区通识）：装载时逐行提交；全局索引随分区移动而失效重建；并行度过拟（从属进程饥饿）。
- 🔧 对照：SQLite 无并行/无交换挂载——装载窗口的最简形态是"新表建好→ALTER RENAME 换名→DROP 旧表"（🔧 事务内三步，实测可行路径即 exp2.py G5.1 的建表改读逻辑）；"分钟级停机"与 Oracle"秒级交换"的差=本章工程叙事的存在意义 ⚠️。

## 5b. 数据生命周期与归档（⚠️ 转述；分区管理动机第一层的延长）

- 保留策略（retention）以分区为单位表达："只留 N 个月"=每月一片+月末 DROP 旧片 ⚠️——比 DELETE 快几个数量级且不留碎片（[02 章](02-物理存储结构与表空间.md) 高水位语境）。
- 归档出口三选：DROP（丢弃）/ 交换出到归档表（库内降温）/ 导出工具落文件（[06 章](06-服务器工具与实用程序.md) Data Pump）⚠️。
- 🔧 侧对应物：SQLite 按年分表+DROP TABLE 即最原始版本——T13 的教训提醒：**分完还得手工路由**，生命周期自动化正是 ⚠️ 分区制度买走的那部分心智负担。

## 核心概念速览（中英对照）

- **分区** — Partitioning：按片管理大表的制度 ⚠️。
- **分区消除** — Partition Pruning：优化器按谓词裁片 ⚠️（🔧 反例钉价值）。
- **交换分区** — EXCHANGE PARTITION：装载表与分区片的秒级对接 ⚠️。
- **本地/全局索引** — Local/Global Index：随片维护 vs 跨片维护 ⚠️。
- **物化视图** — Materialized View：有段实体的预聚合 ⚠️。
- **查询改写** — Query Rewrite：基表查询自动改道 MV ⚠️。
- **增量刷新** — Fast Refresh：按快照差集补格子 ⚠️。
- **DOP/从属进程** — Degree of Parallelism / PX slaves：并行军团的编成 ⚠️。
- **装载窗口** — Load Window：T/L 的时序容器 ⚠️。
- **UNION ALL 视图** — 🔧 伪分区载体（实测无裁剪）。
- **EXPLAIN QUERY PLAN** — 🔧 SQLite 计划查看器（T13 判据）。
- **CTAS** — CREATE TABLE AS SELECT：🔧 最小 MV 形态（实测 131.0ms 构建）。
