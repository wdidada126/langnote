# 01 · 数据架构的演进：从孤岛到编织

> 主题章（⚠️ 推定归属本书的"问题史"部分）。本章回答一个前置问题：为什么 2010 年代被宣判"已死"的**总体架构叙事**（enterprise architecture）会在 2020 年代以 data fabric 的名义复活？答案不在技术清单里，而在每一代架构留下的**集成债**里。全章论断为公共知识综述（标 ✅ 处为可取证源），与 [../数据架构之道.md](../数据架构之道.md)、[../The_Data_Lakehouse/00-总览与阅读地图.md](../The_Data_Lakehouse/00-总览与阅读地图.md) 对读。

## 1.1 四代架构的钟摆：中心化—去中心化—再中心化

把 1970-2025 的数据架构史压缩成一个钟摆模型：

| 代际 | 主导形态 | 解决了什么 | 制造了什么债 |
|---|---|---|---|
| G1 主机时代（1970-90） | 单库单系统，IMS/VSAM→RDBMS | 一致性与事务 | 数据孤岛随部门复制出现 |
| G2 数仓/集市时代（1990-2010） | Inmon/Kimball 分层，ETL 泵水 | 分析口径统一 | N×M 拷贝、集市烟囱、变更迟缓 |
| G3 大数据/湖时代（2006-2018） | Hadoop→数据湖，schema-on-read | 吞吐与成本、半结构化 | 数据沼泽、治理缺位、重复建设 |
| G4 湖仓/云原生（2019-今） | 对象存储+开放表格式+托管仓 | 存算分离、ACID on lake | **多引擎多副本的再孤岛化** |
| G5 编织层（话语上 2019-今） | 元数据驱动的统一语义与自动集成 | 不再新增存储，而是缝住 G1-G4 | 语义抽取本身成为新债（10 章） |

关键观察：每一代都宣称终结上一代，实际是**叠层**——今天任何一家 20 年历史的企业，机房里 G1-G4 同时活着。这就是 ⚠️ 本书标题"as Modern Data Architecture"的立论前提：fabric 的"新"不在存储，而在承认叠层现实后，把**集成与语义**升格为架构一等公民。

## 1.2 为什么"再总纲化"发生在 2019 之后

三条独立线索在同一时点合流：

1. **湖仓证明"物理统一"是幻觉** ✅（对照 [../The_Data_Lakehouse/00-总览与阅读地图.md](../The_Data_Lakehouse/00-总览与阅读地图.md) §湖仓定义）：表格式统一了存储层，但 Snowflake/Databricks/BigQuery/自建 Iceberg 之间，数据、身份、策略仍然割裂——Gartner 所谓"fabric 覆盖 hybrid/multi-cloud"的市场语境正来自这里（⚠️ 转述 Gartner 口径，其原文 403 不可直引）。
2. **元数据技术第一次够用**：开放 catalog（Iceberg REST catalog、Polaris、Unity Catalog 等，见 06 章）+ 知识图谱工具链 + 采集 SDK 成熟，使"给全企业数据建索引"从咨询项目变成平台功能。
3. **AI 消费端倒逼**：特征、嵌入、评测集需要跨源**就近组装**；G2 时代"先入仓再分析"的时延模型在 LLM 检索增强（RAG）面前完全不成立（10 章展开）。

## 1.3 谱系辨析：fabric 吸收/淘汰了哪些旧概念

| 旧概念 | fabric 里的命运 | 辨析 |
|---|---|---|
| EII/数据虚拟化（1990s, Denodo 系） | **被吸收为访问面** ✅（Denodo 官方把 data fabric 作为其虚拟化平台之上的编织叙事，见 05 节链接） | 虚拟化只解决"读"，fabric 额外要求写路径编排与语义推荐 |
| ESB/EAI 总线（2000s） | 被淘汰：消息级耦合≠语义级耦合 | fabric 的"总机"是元数据图谱，不是运行时消息 |
| 主数据管理 MDM（2000s） | 被吸收为黄金记录服务 | MDM 靠人肉治理委员会，fabric 靠主动元数据回路（05 章） |
| 数据湖仓（2020s） | 被包裹而非替换 | fabric 主张"零新增拷贝"，湖仓仍是物化落点（06 章） |
| 数据中台（中国语境 2015-） | 平行物种 | 中台=组织化复用工程，fabric=元数据驱动自动化；目标同、机制异，07 章对照 mesh 时可类比 |

> ⚠️ 推定：本书作为 O'Reilly 概念向著作，谱系辨析（"它不是什么"）大概率占据前部相当篇幅；本表为公共知识重构，具体取舍以原书为准（00 §8 待闭环）。

## 1.5 本章论证线小结（可反驳形式）

- 论题：现代数据架构的问题已从"往哪存"转为"如何在不增拷贝的前提下让数据被发现、被理解、被自动组装"。
- 论证：叠层现实（1.1）+ 三线索合流（1.2）⇒ 集成与语义必须升格为架构层，而不是继续作为项目附属物。
- 反论（须诚实面对）：fabric 语义层的元数据由谁持续供给？若仍靠人工登记，则只是把 ETL 债改写为语义债——本目录立场：**若无 05 章的主动元数据闭环 + 10 章的 AI 打标，fabric 论题不成立**（这也是它 2019 年首倡、2024 年后才真正可用的原因）。

## 1.7 三个反问（对钟摆论的最强异议）

1. **"fabric 只是 DAMA 框架换皮？"**——DAMA-DMBOK 把元数据/集成列为职能而非运行时；fabric 的差异在于要求**机器可执行**（L3→L5 回路）。换皮论忽略了这个从文档到执行体的相变。
2. **"每代架构都说自己不新增存储？"**——不成立：数据湖当年明确以"替代仓"销售；fabric 罕见地把"包住存量"写进定义（02.2 IBM 口径 ✅ 混合/多云适配）。
3. **"钟摆注定再摆回集中？"**——可能，但摆幅衰减：mesh 的组织成果（域契约）不可逆，回摆只能发生在语义平面而非所有权平面（07 章推论）。

## 1.9 债务换算练习（把钟摆模型用在自己的库存上）

方法：列出你企业 Top5 数据消费者（报表平台/风控引擎/特征库/监管报送/对外 API），对每个消费者回答三问——
1. 它消费的数据副本有几份？（拷贝度，G2/G3 遗产）
2. 新增一个同类消费者要动几条管道？（N×M 度）
3. 上次源端变更造成下游事故是什么时候？（集成债利息支付日）

三个答案分别对应 fabric 三必答项（组合交付/逻辑优先/主动回路）的痛点强度；总分高者才值得启动 09 章剧本，总分低者请先做治理基本功（8 章与治理册）。

## 1.10 本章时间假设声明

本章把"fabric 复活总纲叙事"定位于湖仓定型之后（G4→G5），该定位依赖 02.2 的 IBM/Denodo 口径与本书书名的联合推定 ⚠️；若原书实际成书于湖仓论战高峰期（2021-2022），则 1.2 的三线索权重需重排（湖仓线索后移）——此为可被原书目录证伪的开放项（00 §8 待闭环）。

| 数据中台 | data middle platform | 中国语境的复用工程，机制与 fabric 平行 |

## 最新演进与工业实践

- **2024→2026 演进线**：湖仓与编织合流为"元数据驱动的平台"话语——IBM 把 data fabric 定义为"协调、连接、统一整个数据基础设施与管道"的方法论（✅ https://www.ibm.com/think/topics/data-fabric ，状态码 200 实测）；Informatica 则将"现代数据架构"叙述为 lakehouse+mesh+fabric 三件套共存的图景（✅ https://www.informatica.com/resources/articles/modern-data-architecture.html ，200 实测）。⚠️ 各家均把 fabric 解释为自家平台的自然延伸，读官方定义时须剥离营销层。
- **工业实践锚点**：企业侧 G1-G4 叠层可观测为——同一逻辑实体同时存在于 Oracle 主库、Snowflake、湖内 Parquet、湖仓表（⚠️ 转述自上述 IBM/Informatica 文章对 hybrid/multi-cloud 现状的描述，非本目录实测）。
- **平台侧动向（⚠️ 转述）**：Microsoft Fabric 虽借名"fabric"，实为**统一 SaaS 平台**而非编织方法论，两者辨析见 06/10 章与其目录版对链（盘上实测在盘：[../Fundamentals_of_Microsoft_Fabric/00-总览与阅读地图.md](../Fundamentals_of_Microsoft_Fabric/00-总览与阅读地图.md)，名册态差异已在 00 §5 申报）。
