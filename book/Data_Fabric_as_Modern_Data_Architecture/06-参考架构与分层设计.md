# 06 · 参考架构与分层设计：把叙事拆成组件

> 主题章（⚠️ 推定归属本书"架构"部分）。02.3 给了能力模型，本章把它落成**可画图的参考架构**：七层组件树、每条接缝的契约、以及"哪些层必须自建、哪些层买/用开源"的判断。湖仓侧的分层基线对照 [../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md](../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md) 的五层法——两套分层在 catalog/元数据一层咬合。

## 6.1 七层参考架构（本目录重构，⚠️ 非原书图）

```
L7 消费     BI·notebook·应用API·特征·Agent(10章)
L6 交付     数据产品注册·契约(模式/SLA)·市场化发现
L5 编排     管道生成与调度·物化开关(4.2)·主动回路运行时(5.2)
L4 语义     知识图谱+本体·指标语义层·实体归一服务(3.2)
L3 元数据   三合一采集·对账·版本化存储·事件总线(3.1)
L2 访问     虚拟化/联邦引擎·连接器·身份穿透(4.5)
L1 底座     既有存储与计算:湖仓/仓/事务库/流(原样保留)
```

铁律三条：
1. **L1 零改动是 fabric 的入场券**——任何要求"先迁到我这"的方案都是平台推销不是架构（对照 6.6 同名歧义）。
2. **L3 是唯一有强制顺序的层**——L4 以上全部饿死于 L3 覆盖不足；实施排期以此为准（09 章）。
3. **每条接缝要有契约测试**：L2↔L1 的下推率回归、L3 的采集 SLA、L5 的护栏回滚演练——架构文档里没有回归测试的层等于没有该层。

## 6.2 关键接缝一：L2↔L1（连接器的真实成本）

连接器矩阵的工程量估算（⚠️ 经验值）：读路径连接器（JDBC/文件/REST/Kafka）约占 70% 工作量，而其中**方言适配与下推回退**又占读路径的多数；写路径连接器（回写治理动作、物化装载）复杂度再高一档。判断：

- 开源谱系优先：Trino/Iceberg REST catalog 覆盖主流湖仓锚点（对位盘上 [../Trino_The_Definitive_Guide_2e/](../Trino_The_Definitive_Guide_2e/00-总览与阅读地图.md)）；SaaS 源（CRM/ERP）走 API 织（4.4 右列）。
- 自留地只剩长尾专有系统——恰是老集成厂商护城河（⚠️ Denodo/Informatica 连接器资产叙事即此，✅ 两厂页 200 实测见 00 清单）。

## 6.3 关键接缝二：L3↔L4（元数据模型即宪法）

L3 向 L4 的供数契约，本目录推荐的最小实体集（承 3.2 三层归一）：

| 对象 | 必含字段 | 说明 |
|---|---|---|
| PhysicalAsset | uri, system, schema_hash, observed_at | 技术层，采集器直管 |
| LogicalEntity | id, domain, mapsTo[], merged_from[] | 归一层，实体解析产物 |
| BusinessTerm | id, vocab, defines[], conflicts[] | 语义层，含冲突显式化(2.5-3) |
| Event | type, subject, ts, payload, confidence | 供 L5 消费的统一事件形 |

契约核心：**Event 必须带 confidence**（5.2-4 的数据前提）；`conflicts[]` 不许在 L3→L4 途中被静默合并——静默裁决是语义层的原罪（3.5）。

## 6.4 关键接缝三：L5↔L6（自动化到产品化的最后一公里）

L5 生成的物化/管道若没有 L6 的契约注册（谁消费、SLA 几何、废弃条件），三个月后必然长出僵尸资产——这是 G2 集市烟囱病在 fabric 层的复发形态（⚠️ 历史类比论证）。对策两条：交付即注册（无契约不上线）、注册即血缘（L6 消费记录回流 L3 运营元数据，喂 5.6 推荐）。

## 6.5 分层与流派：三张阵营图

| 阵营 | 主打层 | 代表叙事 | 盲区 |
|---|---|---|---|
| 虚拟化系（Denodo 等） | L2+L4 语义 | "逻辑优先统一访问"(✅ 其标签页口径) | L5 写路径自动化薄弱 |
| 集成平台系（Informatica/MuleSoft 等） | L5+L1 老连接器 | "active metadata 驱动集成"(✅ 其文章口径) | L2 性能叙事吃亏 |
| 目录/平台系（Atlan 等及云厂商 catalog 线） | L3+L4 | "元数据即产品" | L5 动作面浅 |

⚠️ 三阵营都在向"全栈"收编——采购验证以 6.1 铁律+2.5 判据清单逐层试，不信"一个平台全包"。

## 6.6 命名陷阱：Microsoft 的 "Fabric" 与本书的 fabric

盘上已验收对照（实测在盘；名册态申报见 00 §5）：[../Fundamentals_of_Microsoft_Fabric/00-总览与阅读地图.md](../Fundamentals_of_Microsoft_Fabric/00-总览与阅读地图.md)。二者关系一表说清：

| | data fabric（本书范式） | Microsoft Fabric（产品） |
|---|---|---|
| 本体 | 架构方法论，不新增底座 | 统一 SaaS 分析平台（OneLake+引擎矩阵） |
| 对 L1 | 原样保留 | **要求入湖**（Shortcuts 缓解但仍以 OneLake 为轴） |
| 语义核心 | 图谱+主动元数据 | 统一寻址+权限+治理平面 |
| 互操作 | 多引擎中立 | 以 Power BI/Spark 系为原生 |

结论（⚠️）：名字撞车是营销事件不是架构事件；把 Microsoft Fabric 部署起来≠拥有 data fabric——除非其上长出 6.1 的 L3-L5。反向，fabric 参考架构可把 Microsoft Fabric 当作 L1 底座之一。全系列检索时此辨析必须前置（00 §3 四册分工表同源问题的姊妹项）。

## 6.7 尺寸分形：部门级 fabric 是否成立

追问：这套七层是不是大厂专属？本目录判断否，但**裁剪有定式**：部门级（<200 资产、<10 系统）时 L4 可降为词表+轻图谱（SQLite 级元数据库即够，G1/G3 实验的规模感），L5 只留新鲜度巡检+变更通知（G5），L2 用 DuckDB/Trino 直查即可（G2/G4 的毫秒下限支撑）。分形规则：**L3 元数据模型不自定义缩水**——部门 fabric 的表结构照 6.3 走，将来并入企业级时才有对账基础（⚠️ 方法论，与 #212 兄弟册实操线的可能主张相洽）。

## 6.9 架构演进管理（分层版的"改图纪律"）

- 每层维护 `AS-IS / TO-BE / 接缝测试` 三件套；缺接缝测试的 TO-BE 不进路线图。
- 层间新增能力优先做"寄生式"（复用下层的注册/事件机制）而非新平面——平面数是企业 fabric 的肥胖指数（⚠️ 格言）。
- 与 #201 平台架构的映射：L1-L2≈基础设施平面，L3-L5≈治理/观察平面，L6-L7≈消费平面；两书分层可互换作评审双镜（07.7 补表）。

## 6.10 一图速记（分层记忆卡）

"底座不动(L1)、连接器统一地址(L2)、三合一进总线(L3)、图谱语义层(L4)、回路带护栏(L5)、注册有契约(L6)、消费者分人与机(L7)"——七句口诀用于评审开场；任何一句缺失即触发 6.8 十问的该组问题（⚠️ 自研教具）。

## 6.12 分层与能力模型的换算

02.3 三层五面 ≡ 6.1 的 L1-L7：地基=元数据层+语义层(L3-L4)、三面=发现(L4→L6 前半)/编排(L5)/交付(L6-L7)、访问层=L2、底座=L1——两套图同一拓扑，评审时任选一种说法（速记用后者）。
