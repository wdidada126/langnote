# 05 · 主动元数据与自动化：编织的纬线

> 主题章（⚠️ 推定归属本书核心创新论述）。经线（03 章元数据/图谱）是"静"的地图，纬线是"动"的回路：**主动元数据（active metadata）= 元数据不再等人查，而是自己触发行动**。fabric 能否兑现 02.1 的五个必答项，全看这条纬线。本章 🔧 两组实验（G3 血缘闭包、G5 新鲜度扫描）给回路成本一个可跑的下限。目录侧的主动元数据前史见 [../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md](../The_Enterprise_Data_Catalog_2e/00-总览与阅读地图.md) 07 章。

## 5.1 从被动到主动：元数据消费范式的三级跳

| 级 | 范式 | 交互形态 | 局限 |
|---|---|---|---|
| P1 被动 | 人搜目录 | 搜索框+详情页 | 覆盖率取决于工程师自觉，长期<60%（⚠️ 经验区间） |
| P2 半主动 | 事件通知 | schema 变更→订阅者邮件/工单 | 通知疲劳，动作仍靠人 |
| P3 主动 | 元数据驱动执行 | 回路自动打标/生成管道/改物化/调策略 | 需要置信度分级与回滚闸，误动作即事故 |

fabric 的立论在 P3；P3 与 P2 的分界线是**动作是否绕过人**。绕不过人，"自主集成(autonomous data integration)"就是修辞（⚠️ 对 Gartner 口径的批判性转述，原报告 403 不可直引）。

## 5.2 主动回路的四元组

每条 active metadata 规则的形式化：`WHEN 元数据事件 ∧ 条件 → DO 动作 ∧ VERIFY 护栏`。

1. **事件源**：DDL 变更、血缘边增删、新鲜度越限、访问模式漂移、标签缺失。
2. **条件**：多跳闭包（这张表的下游含密级 PII 资产）、统计阈值（7 日扫描成本>X）。
3. **动作**：自动物化/撤销物化（4.2 开关的执行体）、生成/重排管道、下发策略（08 章）、推荐（"你可能还需要 join 这张维度"）。
4. **护栏**：置信度门限、速率限制、可回滚声明（动作即变更，变更即要有版本）。

第 4 项最常被厂商略过（⚠️ 本目录立场）：让元数据触发自动动作=给平台装自动驾驶，护栏设计就是其安全框架——这也是与"workflow 触发器"的本质区别。

## 5.3 🔧 G3：血缘闭包作为回路条件（SQLite 类比）

场景类比：999 条血缘边，节点变更时求其上游闭包（模拟"影响半径/根因回溯"类条件评估）。

- 实测：节点 999 的上游闭包=**7 节点**，递归 CTE 用时 **0.102ms**（SQLite 3.45.3，`lineage(dst)` 索引；**非本书引擎/平台行为**）。
- 读数：千边级图上千次/分钟的闭包评估毫无压力（0.1ms×QPS 预算充裕）；真实难点依旧不在算，在**边是否新鲜**——边若滞后一天，闭包全错。故 active metadata 的第一性工作是采集管道的 SLA（3.1 对账问题），不是规则引擎的漂亮。

## 5.4 🔧 G5：新鲜度驱动的巡检回路（DuckDB 类比）

场景类比：三个"源"（各 8 万行 CSV）挂进一次巡检，按源聚合 `COUNT/MAX(ts)` 判定新鲜度——模拟 P3 里"新鲜度越限→自动物化/告警"的触发前提。

- 实测：合计 24 万行扫描+分组 **46.99ms**，三源最大 ts 均得 `2026-09-27`（DuckDB 1.5.5，`read_csv([...], filename=1)` 单查询多文件；**非本书引擎/平台行为**）。
- 读数：元数据巡检在引擎侧的单价极低（百毫秒/百文件），意味着**高频巡检在成本上完全可行**——巡检不再是月度报表而是常驻回路。对位 #224/#223/#226 可观测册群（波5 `Fundamentals_of_Data_Observability/` 实测在盘、名册态申报见 00 §5：[../Fundamentals_of_Data_Observability/00-总览与阅读地图.md](../Fundamentals_of_Data_Observability/00-总览与阅读地图.md)）：可观测五支柱的探测信号=fabric 的运营元数据事件源，两册语言可互换处即本章接口。

## 5.5 自动集成的三个档位

fabric 承诺的"autonomous integration"按自动化深度分档（⚠️ 重构分类）：

| 档 | 形态 | 人的角色 | 现实成熟度 |
|---|---|---|---|
| A1 推荐 | "检测到 join 键相似/口径冲突，是否采纳？" | 确认者 | 主流目录已普及（✅ 概念见 IBM 页 metadata 能力叙述） |
| A2 生成+人审 | 自然语言→管道骨架，人审后上线 | 审稿人 | 2024-2026 LLM 加持后快速落地（10 章） |
| A3 闭环自运维 | 物化/重排/降级全自动，人事后审计 | 审计者 | 先锋区，护栏不足即回滚潮 |

本目录对 A3 的怀疑是结构性的：语义冲突（3.5 的同词不同义）**不可全自动裁决**，A3 的上界由业务元数据质量而非算法决定（⚠️ 立场，可辩）。

## 5.6 推荐系统的元数据三原料

fabric 的"发现"体验（搜索框背后的排序）由三类运营元数据喂养：

1. **共现**：经常被一起查询/一起 join 的资产互推（G4 章的行为边，03.4）。
2. **人群**：同角色/同域工程师的采纳轨迹（协同过滤位）。
3. **质量分**：新鲜度（G5 信号）、完整度（标签覆盖）、稳定性（变更频率）合成排序先验。

工程警示：共现原料在冷启动的新源接入期恒零——新资产永不被推荐→永无人用→恒零，**死循环需靠 A1 的相似性推荐（schema 指纹近邻）强制破冷**（⚠️ 方法论，非取证数）。

## 5.7 与 03 章的合流检查单

上线一条主动规则前问五句（承 3.6 反模式）：边从哪来、多久新（5.3）；动作可否回滚（5.2-4）；置信度是否进门限（3.6-4）；误动作的通知给谁（P2 残留）；规则本身有没有版本（策略即代码，08 章）。五句答不上一个，就把规则降级为报表（P1）。

## 5.8 规则 DSL 解剖（示意骨架，⚠️ 非任何产品语法）

```yaml
rule: demote-materialization-on-cold
when:   event == "access-window-updated"
with:   f7d < 3                    # 7日访问次数骤降
and:    asset.tags.domain in scope_hot
do:     action = "unmaterialize"   # 撤销物化, 回直读
verify:
  confidence_min: 0.8
  rate_limit: 5/day
  rollback: within 1 query-profile-refresh
  shadow_days: 14
```
逐字段对位：when/with=5.2 事件+条件；do=动作面；verify=护栏四件套（置信/限速/回滚/影子）。**读任何厂商规则引擎时按此四段拆**，缺 verify 段的"自动化"直接扣分。

## 5.9 回路的降级与熔断

- 采集断供>24h：全回路自动降 P2（只通知不执行）——元数据陈旧时自动动作比手动更危险。
- 误动作率滑动窗超阈（8.6-4）：对应规则族熔断进人审队列。
- 事件总线积压：按规则族优先级丢弃低阶推荐事件，保血缘/新鲜度高阶事件（丢哪个不丢哪个=业务定序，平台提供机制）。

## 5.10 🔧 复现提示

G3：`WITH RECURSIVE u(x) AS (SELECT 999 UNION SELECT src FROM lineage JOIN u ON dst=x) SELECT COUNT(*) FROM u;`（999 边/0.102ms）
G5：`SELECT filename, COUNT(*), MAX(ts) FROM read_csv(['f_a.csv','f_b.csv','f_c.csv'],filename=1) GROUP BY 1;`（24 万行/46.99ms；DuckDB 1.5.5。均非本书引擎/平台行为。）

## 5.11 事件契约的最小字段集

`{event_id, type, subject_uri, occurred_at, observed_at, confidence, rule_ref, payload_hash}`——subject_uri 必须可解析回 6.3 的 PhysicalAsset/LogicalEntity；observed_at 与 occurred_at 分离是对账采集延迟的生命线（G3 的"边新鲜度"命题由此入约）。

## 5.12 本章三数速记

闭包 0.102ms（G3）、巡检 46.99ms/24 万行（G5）、降档时限 24h（5.9）——回路设计的成本感、节奏感与敬畏感各有一个数可背。

## 5.13 与 04 章的交接复核

回路生成的物化/撤销动作必须落在 4.7 的层位表里并可被 4.10 的 SLO 度量——两章互为对方的执行面与验证面（⚠️ 交差校验为本目录自设纪律）。
