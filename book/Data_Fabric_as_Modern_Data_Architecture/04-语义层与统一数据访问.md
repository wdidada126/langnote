# 04 · 语义层与统一数据访问：逻辑优先的经济学

> 主题章（⚠️ 推定归属本书"访问面"部分）。统一访问是 fabric 对用户最可感的承诺：**一个入口、一套语义、按需组装，尽量不搬运**。本章给出逻辑访问的成本模型、虚拟化⇄物化的开关设计，并用 🔧 G2 实验给出"零搬运联邦查询"的可跑下限。EII/虚拟化的历史位置见 01.3。

## 4.1 统一访问的三个层次

| 层次 | 提供什么 | 典型载体 | 失败形态 |
|---|---|---|---|
| L1 地址统一 | 一个连接串看全部源 | 查询联邦引擎（Trino/DuckDB 附件式） | 只统一了 JDBC，没统一含义 |
| L2 语义统一 | 一个词表/指标口径消费全部源 | 语义层（指标定义+映射规则） | 口径委员会产出无人消费的字典 |
| L3 交付统一 | API/文件/数据集/特征按消费者形状交付 | fabric 交付面（02.3） | 每消费者一条 bespoke 管道，回到 N×M |

本目录的判断（⚠️）：多数"我们上了 fabric"的企业停在 L1；本书式论述的价值在把 L2/L3 讲成**架构义务**而非项目选项。

## 4.2 逻辑优先的经济学：搬运什么时候才划算

逻辑访问≠永不复制。设源 S、消费者 C，查询频次 f，单次扫描成本 s，物化成本 m（构建+存储+维护滞后 Δ）。粗模型：直读总成本 ≈ f·s；物化总成本 ≈ m + f·(s' )，s' 为本地扫描成本且有陈旧风险。搬运划算的三条件（任一）：
1. **f·(s−s') > m**：高频热数据（BI 大盘）——物化。
2. **s 不可接受**：源侧延迟/并发保护（生产库不敢直查）——物化或走只读副本。
3. **消费者要求离线一致性快照**：审计/训练集——按窗口物化。
其余场景保持逻辑直读。fabric 的角色是把这三条件变成**引擎自动决策**（读运营元数据 3.1 决定），而不是架构师手工裁决——这就是 02.3"逻辑⇄物理开关"。

对照湖仓现实：Iceberg 等开放表格式让"物化"这步的代价持续下降（托管 compaction 维护、schema 演进），因此 ⚠️ 趋势判断是：**fabric 的"零拷贝"理想会向"少拷贝+可追溯拷贝"妥协**，湖仓 5 层里 catalog/元数据层与 fabric 语义层会互相咬合——详见 [../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md](../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md) 的存储/Catalog 两章与 [../The_Data_Lakehouse/00-总览与阅读地图.md](../The_Data_Lakehouse/00-总览与阅读地图.md) 的集成章。

## 4.3 🔧 G2：零搬运联邦查询的下限（SQLite ATTACH 类比）

场景类比：两个"异构系统"（src_a.db 5 万行订单、src_b.db 3 万行），经 ATTACH 挂入同一会话，做跨源窗口聚合——问：不搬运任何一行，代价几何？

- 实测：窗口 `dt>='2026-09-20'` 联合命中 **23700 行**，`SUM(amt)=1192725.73`，**8.22ms**，搬运行数 0（SQLite 3.45.3，本机文件库；wall-clock；**非本书引擎/平台行为**）。
- 读数一：千行级到十万行级的逻辑联邦聚合在小引擎上就是毫秒级——**"虚拟化必然慢"是伪命题**；真实世界的慢来自：跨网络往返、源侧并发保护、方言下推失败回传全表。虚拟化厂商产品力（✅ Denodo 标签页 https://www.denodo.com.cn/zh-hans/tags/data-fabric 的"统一访问"叙事）竞争的正是**下推率与连接池治理**，不是扫描本身。
- 读数二（重要工程发现）：SQLite 在 `:memory:` main 库上**禁止**创建引用 ATTACH 库的 VIEW（报错 `view cannot reference objects in database b`），只能内联 UNION ALL。类比 fabric：**统一语义层"落"在哪里不是免费的**——视图/物化对象必须与它引用的对象同库同权；所以真实系统要么把语义层定义存为"引擎外置 DSL"（dbt/语义层产品路线，对位登记：兄弟波册 `Analytics_Engineering_with_SQL_and_dbt/`、`Unlocking_dbt/` 盘上尚无目录，只登记），要么接受物化（把视图定义搬进每个引擎）。这一条是本章比任何厂商 PPT 都诚实的地方。

## 4.4 查询联邦 vs API 编织：两种"统一入口"的路线

| | 查询联邦（SQL everywhere） | API 编织（数据产品化） |
|---|---|---|
| 消费者 | 分析师/BI/引擎 | 应用/服务/低代码 |
| 契约 | 表/视图，schema 即契约 | OpenAPI/GraphQL，端点即契约 |
| 语义挂点 | 视图/指标层 | 端点参数与字段字典 |
| 故障模式 | 一个慢源拖垮全局查询 | 端点爆炸、组合复用低 |
| fabric 归属 | 访问层主干 | 交付面（02.3 L3） |

成熟 fabric 两者并存：联邦供"探索性连接"，API 供"生产性消费"。⚠️ 推定本书对 API 面着墨不多（2023 前后 O'Reilly 系著作普遍以分析消费为主轴），2024 后新书写法则必然加重——10 章 AI 消费端是第三波冲击。

## 4.5 统一身份与就近执行

统一访问最被低估的难点不是 SQL 方言而是**身份穿透**：消费者身份→联邦引擎→源系统权限映射，需要策略语义层与元数据层同源（08 章）。工程上 2024-2026 的收敛方向（⚠️ 转述自 ✅ IBM/Informatica 文章的治理叙事）：策略以标签为锚（密级/域标签在 3.1 元数据里），执行点下沉到 catalog/网关两处校验；"网络打通即权限打通"的旧虚拟化部署被判定为反模式。

## 4.6 语义层落位决策树（文本版）

```
需要跨引擎同一口径?
├─ 否 → 引擎内视图即可（别建层，防过度）
└─ 是 → 引擎支持外部定义注入?
    ├─ 能 → 中心化语义服务(BI 语义层类)
    └─ 不能 → 外置 DSL+编译分发(dbt/指标层路线)
         └─ 分发一致性谁负责? → 纳入 L3 版本对账(9.4 W5-6)
```
- SQLite G2 教训（视图不能引用 ATTACH 库）在此树第三分支重现为通用事实：**没有免费的全局视图**，中心化语义服务本质是"编译期展开"的伪装。

## 4.7 缓存⇄物化分层策略

| 层 | 载体 | 失效驱动 | 适用 |
|---|---|---|---|
| 结果缓存 | 引擎/网关内存 | TTL+源版本戳 | 高频小聚合 |
| 预连接视图 | 热 join 物化 | 上游 DDL/水位事件 | BI 大盘（4.2 条件 1） |
| 快照副本 | 湖仓表 | 调度+审计窗口 | 合规快照（4.2 条件 3） |
| 直读 | 联邦执行 | —（其余一切默认） | 探索性/长尾 |

纪律：每层都要在 L3 登记"谁、为何、何时废"（6.4 僵尸条款在访问面的投影）。

## 4.8 🔧 G2 复现

```sql
-- SQLite 3.45.3: 零搬运联邦聚合
ATTACH 'src_a.db' AS a; ATTACH 'src_b.db' AS b;
SELECT COUNT(*), ROUND(SUM(amt),2) FROM
 (SELECT amt,dt FROM a.orders UNION ALL SELECT amt,dt FROM b.orders)
 WHERE dt>='2026-09-20';      -- 23700 行 / 1192725.73 / 8.22ms / 0 搬运
```
（非本书引擎/平台行为；`:memory:` 上建引用 ATTACH 库的 VIEW 被禁——4.6 的注脚。）

## 4.9 反问三则

1. "全直读零拷贝最纯粹？"——否，4.2 是经济学不是道德学；拒绝物化的架构师在 f·(s−s')>m 处烧钱。
2. "语义层归 BI 团队管？"——口径服务所有交付面（API/特征/Agent），中心化与否按 4.6 树裁决。
3. "下推率能当唯一性能指标？"——不能，需与回传字节、P99 并发保护并列（4.3 读数一的三兄弟）。

## 4.10 访问面 SLO 模板（可直接改写进 9.4 试点）

| 指标 | 定义 | 建议初值 ⚠️ |
|---|---|---|
| 联邦 P95 延迟 | 按用例分桶的端到端查询延迟 | 探索 5s / BI 2s |
| 回传字节预算 | 单查询从源侧拉取的原始字节上限 | 按源保护策略设定 |
| 下推失败率 | 执行计划中"拉回本地算"占比 | <15% 连续四周方可扩用例 |
| 身份穿透审计 | 决议记录覆盖率（8.6-2 在 L2 的投影） | =100%，缺口即旁路整改 |
| 源侧惊扰度 | 直读对生产库 CPU/连接的冲击分位 | 零事故为硬线 |

注：五指标全部从 4.2 成本模型的参数化派生（s、Δ、风险约束），不是运维清单——**SLO 与经济学同源**是 fabric 与传统 DBA 实践的方法论差异。

## 最新演进与工业实践

- **2024→2026**：开放表格式+REST catalog 把"地址统一"免费化（对位 ✅ 实践：见 [../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md](../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md) 07-Catalog 章），竞争上移到语义统一与身份治理——Denodo/Informatica 的 fabric 叙事均转向"语义+治理"（✅ 两 URL 200 实测，内容口径 ⚠️ 转述）。
- **平台对照（⚠️+实链登记）**：Microsoft 的 Microsoft Fabric 走的是**平台一体化**路线（OneLake 统一寻址+引擎矩阵），恰好构成"逻辑优先"的反命题——用统一物理底座逼近统一体验；其目录版实测在盘（[../Fundamentals_of_Microsoft_Fabric/00-总览与阅读地图.md](../Fundamentals_of_Microsoft_Fabric/00-总览与阅读地图.md)，名册态差异见 00 §5 申报），对照阅读 4.2 的成本模型可立刻看出两派"搬运经济学"的分歧：Fabric 把 s−s' 做成零（同底座），代价是所有数据必须入湖。
- **端侧实践**：DuckDB/SQLite 级别"便携联邦"在 2024-2026 成为数据工程师的日常（attach/read_csv/mysql_scanner 扩展），G2 的类比在真实工具链里有直接对应物；但扩展式直连生产库受 4.2 条件 2 约束（源侧保护），生产形态仍以受控物化为主（⚠️ 社区共识）。
