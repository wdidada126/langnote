# 12 多引擎生态、Catalog 与四大湖格式对比：选型与迁移

> 《Apache Paimon 官方文档与源码精读》终章。主源：文档 Ecosystem / Catalog / Migration /
> Iceberg Compatibility 板块 + 四格式公开资料。收束全书：Paimon 在引擎矩阵里的真实位置、
> 与 Delta/Iceberg/Hudi 的取舍，以及已经落湖的存量表怎么迁。

## 核心概念速览（中英对照）

- **目录服务** — Catalog：表注册与提交仲裁的载体；Paimon 支持 filesystem / hive / jdbc / REST 四型。
- **REST Catalog** — Paimon 生态的"Iceberg REST"对位：中心化元数据服务、多引擎共享 🔧。
- **元数据同步** — 元数据双写：Paimon 提交时向 Hive metastore 同步表/分区信息（sync 工具）。
- **Iceberg 兼容元数据** — Paimon→Iceberg 投影：每次提交同步产出 Iceberg metadata，让 Iceberg 引擎直读 Paimon 表 🔧。
- **查询下推引擎** — 读侧生态：Spark / Hive / Trino / Presto / Doris / StarRocks / Flink / (Python/DuckDB 等新链路 🔧)。
- **写入引擎** — 写侧生态：Flink 为主，Spark SQL 批写/MERGE，程序 API 兜底；其余引擎多只读。
- **湖流一体终局** — Streaming Lakehouse 目标架构：一份存储同时喂流、批、交互分析三张桌子。
- **格式迁移** — Migration：湖内互迁（Hudi/Iceberg→Paimon 及反向）用批读+批写+双读灰度。
- **多模态表** — Multimodal Table / Blob 存储 / 向量与全文检索：面向 AI 数据的新板块 🔧。
- **写服务器化** — 中心化提交协调：锁与冲突治理的托管化趋势（各格式同题）。
- **选型矩阵** — 以"流写流读强度、引擎中立性、团队栈"三轴定格式。

## 精讲

### 12.1 四种 Catalog 与锁

| 类型 | 存储 | 锁/并发 | 适用 |
| --- | --- | --- | --- |
| filesystem | 仓目录内（默认） | 文件原子性/轻量锁 | 单机验证、简单部署 |
| hive | Hive Metastore | 依赖 HMS + 表锁配置 | Hadoop 存量栈、多引擎共享 |
| jdbc | 关系库 | 事务行锁 | 中小规模、要 ACID 元数据又不想起 HMS |
| REST | HTTP 元数据服务 | 服务端集中仲裁 | 云托管/多引擎多租户，跨 region 治理 🔧 |

要点：catalog 决定"引擎怎么找到表 + 提交时谁仲裁"——**多作业并发写同一表的冲突治理，一半在
catalog 层（锁），一半在快照层（5.4 冲突检测）**。生产建议：湖上写者≥3 或跨引擎写 → 优先
hive/jdbc/REST 而非裸 filesystem。

### 12.2 引擎矩阵实况（🔧 能力边界随版本变，以官方各引擎页为准）

```text
            写(主流式)  写(批)  读(批/交互)  流读  备注
Flink        ✅          ✅      ✅           ✅    全家桶：CDC/级联/lookup join
Spark        —           ✅      ✅           ✅*   *Structured Streaming 微批读 🔧
Trino/Presto —           —       ✅           —     联邦查询入口
Hive         —           —       ✅           —     依赖格式 reader jar
Doris/       —           —       ✅(高并发)    —     DV 模式直读主键表(09.3)，OLAP 主力
StarRocks
Python/AI    🔧 PyPaimon/向量检索等新板块     —     1.x 新增，边界扩张中
```

工程含义：**"Flink 写、Spark/OLAP 读、Trino 联邦"是 Paimon 最自然的分工**；
反向（Spark Streaming 写、Flink 读）技术可行但违背格式的设计重心，遇到时优先复核为什么不用 Flink 写。

### 12.3 六维对比

| 维度 | Delta Lake | Iceberg | Hudi | Paimon |
| --- | --- | --- | --- | --- |
| 出身/默认用户 | Spark/批事务 | 中立元数据/批 | Uber 增量管线/微批 | Flink 流/持续读写 |
| 更新物理模型 | 重写 + DV/CDF | MOW/MOR 删除文件 | COW + MOR 日志块 | **LSM 树（桶内）** |
| 行级变更新鲜度 | 分钟~小时 | 分钟~小时 | 分钟（表服务节拍） | **秒~分钟（检查点节拍）** |
| 流语义完整度（-U） | CDF（列级旧值）| 有限（等值删除推理）| CDC 模式 | **原生 changelog 四 producer（07）** |
| 维护负担 | OPTIMIZE/VACUUM | rewrite/expire/orphan | 四表服务+索引 | compaction 为主，动态桶索引 |
| 生态中立性 | Databricks 中心 | **最强（REST 联盟）** | 强（Onehouse 推进）| 中强（Flink 系中心，ASF 顶级项目）|

一句话定位各还一债：Delta 欠流式原生语义、Iceberg 欠高频小提交、Hudi 欠运维简单性；
Paimon 欠的是**生态广度与 compaction 之外的全栈工具成熟度**。
对照阅读：[../Engineering_Lakehouses_with_Open_Table_Formats/12-格式选型与迁移.md](../Engineering_Lakehouses_with_Open_Table_Formats/12-格式选型与迁移.md) 给出该对比的总论框架。

### 12.4 迁移与共存：把选择题改成连线题

1. **Hudi/Iceberg/Delta → Paimon**：批读源表 + 批写 Paimon（Spark/Flink 皆可）→ 双读对账
   （行数/校验和，对账方法见互链的数据质量笔记）→ 流作业切源。高频技巧：迁移后先 producer=none 省成本，
   确认有流读下游再开 lookup（07.5 切换纪律）。
2. **Paimon → Iceberg 生态**：① Iceberg 兼容元数据投影（🔧 表参数开启后 Paimon 提交同步写 iceberg
   metadata，Iceberg 引擎直读同一份数据文件）——为"必须用 Iceberg 工具链"的下游兜底；
   ② 出湖：批读 Paimon 最新快照 + 写 Iceberg。
3. **共存原则**：同一事实表尽量单一写入格式；"一份数据多份元数据视图"（兼容投影）优于"两份数据双写"。
4. **迁移排期信号**：当下游流作业≥批作业、且团队 Flink 能力在线时，Paimon 收益最大；
   反之先把"湖上流语义"需求做减法（很多"实时"其实是 5 分钟新鲜度的批）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "选格式是技术问题，与组织无关" | catalog 治理权、引擎团队栈、供应商绑定三件事通常比格式特性更决定成败 |
| "Paimon 支持 Spark 读写所以可以 Flink 换 Spark" | 写路径节拍与运维心智（consumer、级联、CDC）按 Flink 设计；Spark 强在批读/批维护 |
| "Iceberg 兼容 = 两种格式随时互换" | 投影方向与能力子集有限（删除向量/复杂类型映射等，🔧 以文档为准），别当双向同步用 |
| "Doris/StarRocks 直读湖表就不用 Paimon compaction 了" | 直读靠的是 DV/合并后的干净文件（09.3）；合并饿死时查询照样塌方 |
| "四个格式会收敛成一个" | 现实是分层共存：各格式通过兼容层互读，选型压力从"站队"转向"默认视图放在哪" |
