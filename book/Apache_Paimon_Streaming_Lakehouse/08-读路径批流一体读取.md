# 08 读路径：批流一体读取、扫描模式与 Lookup 连接

> 《Apache Paimon 官方文档与源码精读》第 8 章。主源：文档 Primary-Key Table Read / Query /
> Flink Lookup Join 板块。同一张表、同一份文件，批读要"最新全貌"，流读要"增量流水"——
> 读路径如何同时兑现两种承诺，是湖格式 API 设计的精华。

## 核心概念速览（中英对照）

- **快照读** — Snapshot Read（批）：绑定某个快照号做全量扫描 + 按键合并，得到该时刻终态。
- **流读** — Streaming Read：按快照序列连续消费增量：changelog 文件（有 producer）或新增文件（追加表）。
- **扫描模式** — scan.mode：流/批起始位点策略：`latest-full`、`latest`、`from-snapshot`、`from-snapshot-full` 等 🔧。
- **快照 ID 起点** — scan.snapshot-id / scan.timestamp-millis：从指定快照或时间点开始读。
- **增量读取** — incremental-read：批式只读两个快照区间内的变更（喂给下游 ETL 一段增量）。
- **消费者 ID** — consumer-id：把流读进度持久化在表侧（`consumer/` 目录），防快照过期断链 + 观测滞后。
- **全量-增量拼接** — Bootstrap：流作业冷启动先读全量快照再无缝接增量，一条管道完成初始化。
- **合并读 vs 非合并读** — Merge on Read vs Read-optimized：主键表终态读要堆合并；read-optimized 系统表只读已合并层 🔧。
- **维表连接** — Lookup Join：Flink 双流不对称 join，Paimon 表作维表，`FOR SYSTEM_TIME AS OF proc_time`。
- **动态分区裁剪** — Dynamic Filter Pruning：批查询用探测侧值裁剪构建侧文件/分区（引擎能力相关）。
- **限制扫描** — Scan Limit / 谓词下推：利用 manifest 统计做分区/桶/键范围/列 min-max 四级裁剪。

## 精讲

### 8.1 批读路径

```text
SELECT ... WHERE dt='...' AND user_id=...
  ① 分区裁剪：目录级（dt 谓词命中分区）
  ② 桶裁剪：user_id 等值命中 hash 桶（bucket-key 表）
  ③ 文件裁剪：manifest 中 min/max key、value 统计跳过不相关文件
  ④ 行组裁剪：ORC/Parquet footer 统计（引擎下推）
  → 命中文件按桶开 LSM 堆：跨 sorted run 归并，同键取最新（第 02 章）
```

前两级吃"布局设计"（分区/桶选得好不好，第 02/03 章），后两级吃"统计与合并健康度"
（第 09 章）。**批查询劣化的三大归因**就按这条链排查：布局错、统计糊（列无序）、compaction 落后（level-0 堆积）。

### 8.2 流读 = 快照序列上的状态机

流读作业内部维护"下一个要消费的快照号"：

```text
bootstrap 阶段：定位起始快照（scan.mode）→ 产出全量（可选，见 8.3）
增量阶段：轮询/通知发现 snapshot-N+1 →
  ├─ 有 changelog 文件（producer≠none）：读 changelogManifestList → 得 +I/-U/+U/-D，直送下游
  └─ 无 changelog（producer=none）：读 deltaManifestList 的新增数据文件 + 读侧 normalize 兜底（07.5）
每成功处理一个快照 → 更新进度（state 或 consumer-id）
```

关键不变式：**每个快照的 delta 被完整消费一次且仅一次**。因此流读吞吐受"快照发现节拍"限制，
检查点间隔长的表，流读再快也快不过它的提交；跨引擎时（Spark Structured Streaming 读 Paimon 🔧）
这一模型同样成立，微批 = 每次取 k 个快照。

### 8.3 scan.mode 家族

| 取值 | 行为 | 典型用法 |
| --- | --- | --- |
| `latest-full`（流读默认）🔧 | 先读起始时刻**最新快照全量**，再接增量 | 冷启动的流作业/物化视图刷新 |
| `latest` | 跳过全量，只读之后每个快照的 changelog/增量 | 只要"从今往后"的变更 |
| `from-snapshot`（配 snapshot-id） | 从指定快照开始读增量 | 断点重放、指定版本追流 |
| `from-snapshot-full` | 指定快照开始：先出该快照全量再增量 | 回放到某天的完整状态重建 |
| `consumer-id`（独立参数） | 起始位点读表侧记录的进度 | 与上表组合使用，见 8.4 |

> 批侧的孪生参数：Time Travel（快照/tag/分支，第 10 章）与 `incremental-read`（区间增量批）。
> "一段增量的批处理"（例：每天只处理昨天的变更）是湖仓 ETL 的省钱利器，Iceberg 的
> read_incremental 概念同构（见互链）。

### 8.4 consumer-id：进度是数据的一部分

痛点：下游流作业停 3 天，上游快照过期（默认保留 1h 量级 🔧），回来发现 changelog 已被清——只能全量重放或重表。
Paimon 的解法：**消费者把进度注册回表里**：

```sql
-- 流读作业带上 consumer-id 后，进度持久化到表目录 consumer/ 下
SELECT * FROM my_table /*+ OPTIONS('consumer-id'='my-job', 'consumer.mode'='exactly-once') */;
```

- 表侧据此知道"最慢消费者还没读的快照不能清"（与过期策略联动）；
- 作业重启自动续读，`表$consumers` 系统表可观测 lag、手工 reset（🔧 系统表与参数以文档为准）；
- 纪律：**长期挂死的 consumer 会拖住快照过期**，造成元数据膨胀——监控 lag 与清理僵尸 consumer 是运维 SOP 必选项；
- 对照方案：producer=none 的历史表想保回放能力，用 tag 把快照钉住（第 10 章）。

### 8.5 Lookup Join：湖表当维表

Flink SQL 经典形态：

```sql
SELECT o.*, u.city
FROM orders /*+ OPTIONS('lookup.dynamic-partition'='...') */ AS o
JOIN dim_user FOR SYSTEM_TIME AS OF o.proc_time AS u
  ON o.user_id = u.id;
```

Paimon 维表的实现（官方 Flink 文档板块 🔧）：

- 维表侧把整表（或按分桶/动态分区裁剪后的子集）物化进**本地 RocksDB**，按快照增量刷新；
- 主键表上按主键点查走 LSM 层间查找（与 lookup changelog 共用点查设施，第 07/09 章）；
- 动态分区维表（维表按 dt 分区、永远只用最新分区）有专门的分区切换策略，避免"整天缓存旧分区"；
- 与"把维表塞进 Flink state 做常规 temporal join"相比：**状态从作业挪到了湖+本地磁盘**，
  作业可扩性、重启恢复显著变好——这是 Paimon 生态对 Flink 工程痛点的直接回答，
  也是"湖流一体"在 join 场景的落点（第 11 章级联作业复用该机制）。

### 8.6 read-optimized：不合并的读

交互查询（BI/OLAP 直连）对延迟敏感、对"秒级新鲜"不敏感——主键表的堆合并是主要延迟源。两条官方路线：

1. **read-optimized 系统表**：`表$ro` / read-optimized 模式只暴露"已合并层"的文件，跳过 level-0
   未合并部分——数据新鲜度=最近一次 compaction 节拍（🔧 表后缀与开关以文档为准）；
2. **删除向量 + 专用查询引擎**（第 09 章）：DV 把"过滤被删行"变成位图查，免堆合并，StarRocks/Doris
   直读主键表的主流路线（第 12 章）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "流读 Paimon = 流读 Kafka，位点想设哪设哪" | 起点只能是快照边界；changelog 被过期清掉后，任意位点重放物理上不存在（8.4 的 tag/consumer 就是为此）|
| "consumer-id 会自动管理永远不清理" | 它是"钉住过期"不是"无限保留"；僵尸 consumer 会让快照/清单膨胀，需监控 reset 🔧 |
| "批读慢就是引擎问题" | 先按 8.1 三步归因：布局、统计、compaction 健康度，多数不冤枉引擎 |
| "lookup join 维表每次查询都全量重读" | 本地 RocksDB + 增量刷新，只有 bootstrap 全量；维表越大首刷越重（可裁剪分区缓解）|
| "producer=none 的表流读一定算错" | 读侧 normalize 能保正确性，但要付下游状态与恢复的代价——是成本问题不是对错问题（07.5）|
