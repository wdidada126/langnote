# 04 元数据层：快照、清单与三层结构

> 《Apache Paimon 官方文档与源码精读》第 4 章。主源：文档 "Concepts"（File System Layout / Snapshot /
> Schema / Manifest）板块。元数据是 Paimon 事务、时间旅行与流读的公共地基，值得单独一章拆文件级细节。

## 核心概念速览（中英对照）

- **快照** — Snapshot：一次提交的产物 JSON 文件，指向本次表状态的全量清单入口；表状态的"账本页"。
- **清单列表** — Manifest List：快照引用的 avro 文件，逐条记录若干 manifest 文件及其统计摘要。
- **清单文件** — Manifest File：avro 存储的条目集合，每条描述一个数据文件的**增加/删除**事件。
- **清单条目** — Manifest Entry：kind(ADD/DELETE) + 分区 + 桶 + 文件元信息（DataFileMeta）。
- **基础/增量清单** — baseManifestList / deltaManifestList：全量继承的清单 vs 本次新产生的清单。
- **变更清单** — changelogManifestList：本次提交对应 changelog 文件的清单（流读的物证，第 07 章）。
- **索引清单** — indexManifest：哈希索引、删除向量等索引文件的登记入口 🔧。
- **提交用户/提交类型** — commitUser / commitKind(APPEND|COMPACT)：谁提交的、提交的是什么性质。
- **数据文件元信息** — DataFileMeta：文件名、大小、行数、min/max key、列统计、LSM level、序列号区间。
- **模式文件** — Schema：schema-N 版本化存储；表结构演进留痕不覆盖。
- **提示文件** — LATEST/EARLIEST hint：缓存最新/最旧快照号，避免枚举目录。
- **系统表** — System Table：`表$snapshots`、`表$manifests`、`表$files`、`表$schemas`、`表$options`、`表$branches`、`表$tags`、`表$consumers`。
- **孤儿文件** — Orphan Files：无快照引用的物理文件（失败提交残留），靠 remove_orphan_files 清理 🔧。

## 精讲

### 4.1 三层（+索引）结构

```text
snapshot-N  (JSON, 每提交一个)
 ├─ baseManifestList   → manifest-m-1, manifest-m-2 …（继承自上一快照、仍有效的）
 ├─ deltaManifestList  → manifest-m-7（本次新增/删除条目，体量小、单独成文件）
 ├─ changelogManifestList → 本次提交的变更日志文件清单（存在时）
 ├─ indexManifest      → hash index / deletion vector 等 🔧
 └─ 摘要字段：commitUser, commitKind, schemaId, totalRecordCount,
              deltaRecordCount, watermark, timeMillis …
manifest-m-k (Avro) 每条 = {ADD|DELETE, partition, bucket, level, DataFileMeta}
data file (ORC/Parquet/Avro 🔧默认格式按版本以文档为准)
```

与 Iceberg 的元数据树（table metadata → snapshot → manifest list → manifest）同构——Paimon 有意选择了
业界已经验证的分层：**快照只增不改，读方从 hint 进**，任意深度的目录枚举都被转化为几次列文件读。

设计要点：

1. **清单文件按"提交批次"小体量滚动生成**，旧清单不重写——manifest 本身也会碎，所以 compaction
   家族里还有"manifest 合并"这一项（快照过期时顺带做，见 4.3 与第 10 章）。
2. **DataFileMeta 携带 LSM level 与 min/max key、序列号区间**：元数据层直接支撑"键范围裁剪 + 统计裁剪"，
   不必打开数据文件就能判断"这个桶要不要归并读、这个文件能不能整个跳过"。
3. **watermark 字段**让"数据进度"成为一等公民：流读作业可用 `scan.watermark` 类策略按事件时间等待数据（🔧）。

### 4.2 一次提交的原子性从哪来

提交协议（谁触发、两阶段在哪，见第 05 章）最终落到文件系统上只有**一个原子动作**：
写出完整的 `snapshot-N+1` 文件（对象存储 overwrite 语义下依赖原子 rename/条件写 🔧 各文件系统行为差异，
官方文档按 atomic / 非 atomic 两类讨论）。在此之前写者可以随便写数据与清单文件——**没有引用的文件不可见**。
这就是为什么：

- 崩溃的提交留下孤儿文件（4.5 清理），但不破坏表状态；
- 读者永远从 LATEST hint 拿快照号，再按快照内的清单列表读，枚举目录只是 hint 缺失时的兜底；
- "快照隔离"免费得到：清单引用固定，后续 ADD/DELETE 条目都在新快照里。

### 4.3 清单即变更日志：ADD/DELETE 条目的复利

当前快照的**有效文件集** = 对 base+delta 清单按提交历史回放，抵消同一文件的 ADD 与 DELETE。
两个推论极其重要：

- **compaction 的账也记在这里**：合并把 3 个 level-0 文件归成 1 个 L1 文件 = manifest 里 3 条 DELETE + 1 条 ADD
  （commitKind=COMPACT 的快照）。流读方看到 COMPACT 快照知道"别按新数据消费"，Delta 的优化事务、
  Hudi 的 compaction instant 是同一问题的三种记法。
- **delta manifest 就是"这批提交改了什么"的最小完备描述**：追加表流读直接消费 delta 里的 ADD 文件；
  主键表流读消费 changelogManifestList 指向的变更文件（第 07 章）。快照、增量读、时间旅行共用一套机制。

### 4.4 Schema：版本化演进的安全边界

schema 目录按 `schema-0, schema-1, …` 只增不覆盖，快照记录 schemaId。允许与拒绝的边界（文档口径 🔧）：

- 允许：加列（默认值回填）、**数值类型加宽**（INT→BIGINT、FLOAT→DOUBLE 等）、列改名（带 `ALTER TABLE RENAME` 元数据操作）；
- 拒绝/危险：类型收窄、删列后再加同名异型列、分区/主键列变更——直接报错而不是默默坏数据。
- 引擎侧行为差异：Flink 写作业遇到上游 schema 变更的自动跟随，依赖 CDC 入湖链路的 schema evolution 开关（第 11 章）。

### 4.5 系统表：湖上的"information_schema"

```sql
SELECT * FROM my_table$snapshots ORDER BY snapshot_id DESC LIMIT 5;  -- 提交历史：谁、何时、多少行
SELECT * FROM my_table$files;        -- 当前文件清单：桶、level、大小、统计
SELECT * FROM my_table$manifests;    -- 清单文件与条目数
SELECT * FROM my_table$schemas;      -- schema 演进史
SELECT * FROM my_table$options;      -- 当前表参数
```

实战排障三板斧（每章都会回收）：

1. 数据"没到"？→ `$snapshots` 看提交间隔与 deltaRecordCount，定位卡在检查点还是写入。
2. 查询"变慢"？→ `$files` 看小文件数与 level 分布（level-0 堆积 = compaction 跟不上）。
3. 想回滚/审计？→ `$snapshots` + time travel（第 10 章）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "snapshot 文件里存了全部数据" | 快照只是**指针+统计摘要**（KB 级 JSON）；数据在文件层，清单负责展开 |
| "DELETE 条目=删数据文件" | 先记账后清理：文件物理删除发生在快照过期/清单合并后（否则时间旅行会瞎） |
| "改了 schema 老快照就读不了" | schema 版本化，老快照按其 schemaId 可读——这正是能跨版本 time travel 的前提 |
| "系统表是实验玩具" | `$snapshots/$files` 是生产排障主入口；但注意它们本身也有新鲜度/扫描成本，别放高频作业 |
| "对象存储上和 HDFS 上行为一致" | 原子可见性依赖 rename 语义；各文件系统适配器不同，官方文档专页讨论 atomic 性，部署湖前必读 |

## 本章记忆桩

```text
一条链：hint → snapshot → (base+delta) manifest-list → manifest entries → data files。
一次提交 = 写数据 + 记 delta 账 + 挂新 snapshot；可见性全压在那个 JSON 上。
账本思想：ADD/DELETE 条目既是当前状态，又是增量流，又是 compaction 的痕迹——一物三用。
```
