# 05 写入路径与提交协议：从记录到快照

> 《Apache Paimon 官方文档与源码精读》第 5 章。主源：文档主键表写入/Flink DataStream API/
> File-Based Data Formats 相关页与源码提交类（FileStoreCommit）行为。写路径是"流式"与"湖"两种
> 世界观真正交锋的地方：节拍、幂等、冲突都在这章解决。

## 核心概念速览（中英对照）

- **写入器** — FileStoreWriter：按（分区,桶）实例化的写单元；主键表即该桶的 LSM 写者。
- **提交器** — Committer：汇聚所有写并行度的提交消息（commit messages），原子产出快照。
- **两阶段提交** — Two-Phase Commit：写作业先 prepare（收文件清单）再 commit（挂快照），以检查点为事务边界。
- **提交消息** — CommitMessage：某桶本次新增/变更文件与索引的凭证，由 writer 产生、committer 消费。
- **检查点提交** — Sink端 commit on checkpoint：Flink 检查点成功 ⇒ 快照可见；检查点间隔 = 数据新鲜度。
- **幂等重放** — Idempotent Redo：恢复后同一提交用户重发同样消息不会产生重复数据。
- **冲突检测** — Conflict Detection：新快照与已存在快照的文件集合冲突（如同桶 LSM 结构被抢写）则失败。
- **独立提交** — 非流式提交：批作业/Program API 每条 SQL 即时提交，不等检查点。
- **动态桶分派器** — Bucket Assigner：动态桶模式下在写前查/更新 key→bucket 状态映射。
- **归一化节点** — Normalize（ChangelogNormalize）：Flink 里为无完整 changelog 的输入补旧值的算子（第 07 章呼应）。
- **反压-写停摆** — Write Stall：compaction 落后触发 sorted run 超限，写者暂停等合并（第 09 章机制）。

## 精讲

### 5.1 写路径流水线

```text
输入记录(+I/-U/+U/-D)
  → 分区路由（分区列）+ 桶路由（hash 或动态索引）
  → （动态桶：先查 key→bucket 状态，未见则分配新桶——见 2.3）
  → 桶内写缓冲：内存排序、按主键+序列组织
  → flush：生成 level-0 文件（主键表）或直接滚动文件（追加表）
  → 产出 CommitMessage：[{ADD file, partition, bucket, level…}]
  → committer（算子链末端单并行度）聚合全部消息
  → 检查点 barrier 到达 → prepareCommit → 两阶段协议 → 写 snapshot-N+1
```

要点：**可见性节拍（提交）与持久化节拍（flush）解耦**。flush 频繁（缓冲满即落盘，保证内存可控），
commit 按检查点（保证一致性）；中间态的 level-0 文件在提交前只是"孤儿"，崩了不脏表（4.2 的账本逻辑）。

主键表写入对 Flink 撤回流的语义处理：`-U` 与 `+U` 在同键对上净效果是"值变了"，Paimon 默认
把 -U 视作删除标记参与合并（`merge-engine=deduplicate` 下 `-D` 也物化为删除记录，读时过滤）。
这也是 07 章 changelog producer 存在的原因——湖上合并会把旧值物理压掉，**不主动留档就没人能恢复流语义**。

### 5.2 两阶段提交：把检查点协议翻译成湖协议

Paimon Flink sink 复用 Flink 的 TwoPhaseCommitSinkFunction 家族框架：

1. **预提交（prepareCommit）**：每个 writer 并行度把内存+已 flush 文件的凭证打包成 CommitMessage 发往下游 committer；
2. **提交（commit）**：committer 单点收集齐所有消息后，读当前 LATEST 快照 → 冲突检测 → 写出新快照文件 → 更新 hint；
3. **中止**：提交失败则消息缓存保留，下个检查点重试（快照冲突可安全重放，因为数据文件不可变）。

**检查点间隔决定新鲜度、也决定小文件规模**——05/03/09 三章共用这一定律：
提交周期内所有打开的（分区,桶）各至少产出一个文件。

🔧 关键参数（文档口径）：`sink.committer-memory`? 以当前文档为准；核心是检查点本身
（Flink `execution.checkpointing.interval`）+ `write-buffer-size` + `target-file-size`。参数名随版本漂移，本笔记不背具体键名，标 🔧。

### 5.3 恢复与幂等：为什么"至少一次"够用

失败恢复后 writer 从上一个成功检查点重放记录：

- 同一 **commitUser** 重放已提交过的检查点消息时，committer 依据快照内记录的提交用户+提交序号识别并跳过（幂等）；
- 已 flush 但**未提交**的文件会被重写——旧文件变孤儿（4.5 清理工具收尸）；
- 因此不需要"精确一次文件写入"，只需"精确一次快照提交"——**把分布式一致性锚点收敛到一个 JSON 文件**，
  这是湖格式相对消息队列 EOS 方案的巨大简化。Hudi 的 replacecommit/inflight 三段、Delta 的原子 rename 同理，
  Paimon 的特别处在于还要合并"同检查点内多 writer 的消息"。

### 5.4 多写者：能力与红线

| 场景 | 支持度 | 协议 |
| --- | --- | --- |
| 两作业写同表**不同分区/桶** | ✅ | 快照冲突检测按（分区,桶）粒度，互不覆盖即可 |
| 两作业写**同桶** | ❌ 红线 | 各自维护独立 LSM，合并视图错乱；冲突检测会频繁失败 |
| 写作业 + **专用 compaction 作业**（同桶） | ✅ 设计如此 | 压缩作业以 COMPACT 快照改结构，写作业检测到结构变化会调整自己的提交或重试（第 09 章）|
| 批 OVERWRITE 与流写并行 | ⚠️ | 语义上等于"换表"，要停流或走分支（第 10 章）|

> 动态桶模式补充：key→bucket 索引存在**单个写作业的 state** 里，因此动态桶表事实上强制"全表单写者"，
> 多作业并发写动态桶表是被文档明确警告的行为 🔧。需要并发写就切固定桶。

### 5.5 不只有 Flink：批式与编程接口

- **Spark SQL 批写**：`INSERT INTO / INSERT OVERWRITE / MERGE INTO`（版本支持面以 12 章生态表为准 🔧）；批写即"作业结束一次性提交"，节拍问题消失、小文件问题以单次大提交形式缓解。
- **Java Program API**：`FileStoreTable` → `TableWrite`/`TableCommit` 成对使用，自己控制 flush/commit 节奏——
  自研写入器/接 Spark Streaming 微批时照抄 5.2 的消息聚合结构即可（官方 "Program API" 页有完整示例 🔧）。
- **Flink DataStream API**：`PaimonSinkBuilder`（旧）/`FlinkSinkBuilder`，允许自定义 KeySelector 与桶分配，
  CDC 整库入湖的底层就是它（第 11 章）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "检查点间隔=10s 就是 10 秒级数据仓库" | 10s 节拍 × 多桶 × 多分区 → 小文件风暴 + manifest 膨胀；新鲜度是预算不是福利，需与 09 章合并预算一起谈 |
| "提交失败会丢数据" | 提交失败丢的是"这次尝试"，数据文件还在，下个检查点重放；真正丢数据的是检查点禁用的伪流式配置 |
| "Paimon 支持多流并发写同一张主键表随便写" | 只有桶/分区不重叠这一种安全并行；跨流同键更新请走 partial-update（第 06 章），那是语义层方案不是并发层方案 |
| "批写作业会破坏正在跑的流读" | COMPACT/APPEND 快照都有清晰语义，流读按快照序列前进；唯一真杀手是**快照过期太快**把流读没消费的旧快照清了（第 08/10 章）|
| "upsert 吞吐 = 网络/磁盘吞吐" | 主键表吞吐上限 = 桶数 × 单桶（写缓冲+compaction 摊薄后）能力；桶数不足时加并行度无用（2.3）|
