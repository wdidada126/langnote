# 03 追加表与数据布局：分区、桶与 append 场景

> 《Apache Paimon 官方文档与源码精读》第 3 章。主源：文档 "Append Table" 板块与 Partition/Bucket 相关页。
> 追加表是 Paimon 的"另一张脸"：没有主键、没有 LSM 合并，却有自己的一套布局权衡。🔧 标文档示例。

## 核心概念速览（中英对照）

- **追加表** — Append-Only Table / Log Table：无主键、只追加写入的 Paimon 表，适合日志、事件、埋点。
- **无序桶模式** — Unaware Bucket Mode：`bucket = -1`，写者不感知桶、任意落文件；读侧并行扫描 🔧（1.x 中桶=-1 即 unaware）。
- **分桶追加表** — Bucketed Append Table：指定 `bucket>0` + `bucket-key`，同桶键聚拢，为点查与流读局部性服务。
- **桶键** — Bucket Key：追加表上自定义的哈希列（不必是主键），如 user_id，让同键数据物理聚簇。
- **分区** — Partition：`PARTITIONED BY` 的目录级裁剪单位；湖表的第一索引。
- **分区裁剪** — Partition Pruning：查询带分区谓词时只读对应目录——最便宜也最有效的加速。
- **小文件问题** — Small File Problem：高频提交 × 多并发写者 → 碎文件爆炸，元数据与 list 开销失控。
- **增量聚类** — Incremental Clustering：后台把碎文件按分桶/排序键归并成大文件 🔧（1.x 'cluster' 相关能力）。
- **排序** — Sort / Order：批式 `INSERT ... ORDER BY` 或聚类提升读局部性，牺牲写吞吐换读效率。
- **流读追加表** — Streaming Read on Append：按文件产生顺序增量消费，天然就是"无更新流"（+I only）。
- **写入并行度** — Sink Parallelism：追加表下决定同时打开的文件数，与小文件大小直接挂钩。

## 精讲

### 3.1 追加表：把 Paimon 当"能流读的 Hive 表"用

无主键表没有 upsert/delete（严格说没有键合并语义），写入路径退化为：
`记录 → 分区路由 → （可选桶哈希）→ 列式文件追加 → 提交登记`。没有内存排序、没有 level、没有合并读——
所以**没有 compaction 税**，代价是**没有更新能力**。两类典型用户：

- **日志/事件类**：App 埋点、审计流、-binlog 之外的纯 append 流。下游要么批分析，要么流读（+I）。
- **ODS 原样落地层**：先把 Kafka 内容一比一入湖（保留重放能力），清洗作业再写入 DWD 主键表（11 章）。

🔧 建表示例（官方文档口径）：

```sql
CREATE TABLE log_events (
  user_id BIGINT,
  event   STRING,
  ts      TIMESTAMP(3),
  dt      STRING
) PARTITIONED BY (dt) WITH (
  'bucket' = '-1'                      -- unaware：默认，随便写
);

CREATE TABLE user_messages (
  msg_id BIGINT,
  user_id BIGINT,
  content STRING,
  dt STRING
) PARTITIONED BY (dt) WITH (
  'bucket' = '4',
  'bucket-key' = 'user_id'             -- 同用户消息物理聚簇，查一人只扫一桶
);
```

### 3.2 unaware vs bucketed：局部性与弹性的交换

| 维度 | Unaware（bucket=-1） | Bucketed（bucket>0 + bucket-key） |
| --- | --- | --- |
| 写并行 | 不受桶数限制，随 sink 并行度扩 | 每桶单写者，并行度≤桶数 |
| 文件大小控制 | 靠目标文件大小滚动（默认 128MB 量级 🔧） | 同左，但桶多文件小 |
| 键点查/键流读 | 全分区扫（无聚簇） | 命中单桶 |
| 规模增长 | 弹性最好，加机器就行 | 改桶数麻烦（同主键表） |
| 典型用途 | 通用日志湖 | 按 user 查详情、按设备回放 |

经验法则：**默认 unaware；只有"查询/流读总是带某个键等值条件"时才上 bucket-key**。
bucket-key 选错（基数低、热点）会让某些桶巨大、某些空，比主键表更糟。

### 3.3 分区：目录即索引，也是生命周期手柄

- 分区列选择与粒度：时间（dt/hour）最常见；基数过高（如 user_id 当分区）会把目录打碎——
  分区的本质是**查询谓词与生命周期的锚点**，不是负载均衡手段（那是桶的活）。
- 分区裁剪生效条件：谓词直接落在分区列上（`WHERE dt='2026-09-01'`）；对分区列套函数常致裁剪失效（引擎相关）。
- 生命周期：`partition.expiration-time` 自动过期旧分区（元数据删除 + 物理清理异步，细节归第 10 章）。
- 非分区表：Paimon 支持不分区（适合中小维表/事实表），避免 dt 目录的 list 开销；但过期管理粒度变粗。

### 3.4 小文件问题：追加表的头号运维事故

小文件从哪来？`快照提交间隔 × sink 并行度 × 打开分区数` 就是每周期新增文件数下限。
Flink 检查点 1 分钟、并行度 64、每作业写 10 个分区 → 一天最多 92160 个小文件——**这就是实时湖的常态**。
治理工具箱（按性价比排序）：

1. **拉大提交节拍 / 降 sink 并行度**：最直接；牺牲新鲜度（新鲜度预算 = 检查点间隔，谈钱再定）。
2. **目标文件大小滚动**：`target-file-size`（默认约 128MB 🔧）——但单 writer 单分区内生效，救不了"多分区 × 高并行"的碎。
3. **专用压缩作业**：append 表的 compaction 把小文件合并成大文件（无键合并，纯物理重写）。
4. **聚类/排序**：`sort-compaction` 或增量聚类按指定列重排合并 🔧——为大扫描查询买局部性。

manifest 数量与 list 操作代价随文件数线性涨（对象存储 list 是延迟大户）——第 04 章的元数据视角会说明
为什么"一百万个小文件"会让一次快照枚举都变成分钟级操作。

### 3.5 追加表的流读：最简单的一种流

没有更新就没有 -U/+U 的烦恼：流读追加表 = 按提交顺序消费**新增文件**，产出 +I 流。
注意点（文档口径 🔧）：

- 起始位点同样走 scan.mode 家族（latest / from-snapshot / consumer-id，第 08 章统一讲）。
- 同一批数据若被 compaction 合并重写，流读以**文件清单增量（delta manifest）**为准，不会因合并重读。
- 想要"按键的更新流"请回到主键表——追加表的流读顺序只是**落盘顺序**，不承诺业务时序。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "追加表没有主键就一定能随便并发写" | 同一分区+桶组合仍建议单写者；unaware 模式下多写者各写各文件相对安全，但 compaction 作业与写作业并跑需要按文档配置角色 🔧 |
| "bucket-key 没指定会报错" | bucketed 追加表必须显式 bucket-key；不指定桶语义时默认走 unaware |
| "分区越多查询越快" | 超过裁剪收益后，分区数上涨只增加 list/元数据成本与空分区扫描 |
| "Paimon 能当 Kafka 用（流读就有消息队列语义）" | 流读提供的是"按快照增量"，没有分区内严格有序、没有毫秒延迟、没有 TTL 队列模型；替代的是**重放与回溯**场景 |
| "append 表不需要 compaction" | 不需要键合并，但**物理小文件合并**仍要做，否则元数据与扫描会先崩 |
