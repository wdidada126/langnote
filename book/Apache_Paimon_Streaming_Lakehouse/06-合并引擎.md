# 06 合并引擎：deduplicate、partial-update、aggregation 与 first-row

> 《Apache Paimon 官方文档与源码精读》第 6 章。主源：文档 Primary-Key Table / Merge Engine 板块。
> merge engine 决定"同键多条记录归并成什么"——这是 Paimon 从"能 upsert"升级为"能做流式预处理"的关键。

## 核心概念速览（中英对照）

- **合并引擎** — Merge Engine：LSM 归并时同键记录的胜出规则：`merge-engine` = deduplicate / partial-update / aggregation / first-row。
- **去重引擎** — Deduplicate（默认）：同键只留序列最新一条（-D 则删除）。
- **部分更新引擎** — Partial Update：同键各列独立取最新非 null 值，实现多流拼接宽表（打宽）。
- **序列组** — Sequence Group：为不同列组各设比较序列，让"每组列谁新"独立裁决 🔧。
- **聚合引擎** — Aggregation：同键按字段级聚合函数折叠（sum/max/last_value…），湖上预聚合。
- **聚合函数** — Aggregate Function：内置 sum、product、count、max、min、last_value、last_non_null_value、first_value、listagg、bool_and、bool_or、rbm32/rbm64（位图基数）等 🔧 以当前文档为准。
- **字段聚合声明** — fields.<col>.aggregate-function：逐列指定聚合函数的表参数。
- **首行引擎** — First Row：同键只留第一条，流读免合并且拒绝后续更新/删除 🔧。
- **忽略删除** — ignore-delete：部分/聚合引擎下选择让 -D 不生效（防脏 CDC 删除）的开关。
- **序列字段** — Sequence Field：合并的胜负裁判（见第 02 章），与 merge engine 正交组合。
- **局部合并** — Local-Global Aggregation：写侧先局部聚合再落盘，压平乱序与膨胀 🔧。
- **回撤不支持** — Retraction Not Supported：partial-update/aggregation 对 -U/-D 语义天然困难，需显式策略。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 6.1 | deduplicate：默认的"终态表" | 最像 OLTP 的语义，一切流读都靠 changelog producer 补 |
| 6.2 | partial-update：流式打宽表 | 替代"多流 JOIN 打宽"的无状态写法 |
| 6.3 | aggregation：湖上预聚合 | DWS 层直接长在湖表里 |

| 6.5 | 组合矩阵与撤回难题 | 与 changelog-producer 的搭配是配置重点 |

## 精讲

### 6.1 deduplicate：终态视图的地基

规则最简：同主键，序列大者活；收到 -D 就物化删除记录，读时过滤。产出的表 = 主键维度的**当前值表**。
注意三点：

1. "最新"由 sequence.field 定义，没有它则按到达顺序（乱序风险见 2.4）。
2. 删除不是物理消失：-D 变成一条特殊标记记录进入 LSM，compaction 后可能长期与更新记录同存（第 09 章）。
3. 对下游流读而言，deduplicate 表**自身不产 changelog**——旧值被合并碾碎，必须有 07 章的 producer 才能还原 -U/+U。

### 6.2 partial-update：把"打宽"从 JOIN 变成写姿势

**问题原型**：实时数仓里订单流要拼用户流、商品流形成大宽表。Flink 里是双流 JOIN/维表 lookup，
状态巨大；Paimon 的答案：**同一张主键表，多路作业各写自己那几列**。

🔧 官方示例口径（Flink SQL 仿写）：

```sql
CREATE TABLE merged_orders (
  order_id BIGINT,
  -- 来自主流
  amount   DECIMAL(10,2),
  status   STRING,
  -- 来自支付流
  pay_time TIMESTAMP(3),
  channel  STRING,
  -- 来自物流流
  ship_time TIMESTAMP(3),
  PRIMARY KEY (order_id) NOT ENFORCED
) WITH ('merge-engine' = 'partial-update');

-- 三个作业各自 INSERT：缺的列写 NULL，NULL = "这列我不更新"
```

语义要点：

- **NULL 不覆盖**：各流只填自己的列——这是"partial update"的本义。想写 NULL 本身需要额外配置 🔧；
- **撤回困境**：流里 -U/-D 表达"值消失"，而 NULL 已被用作"不更新"，语义冲突。文档明确：partial-update
  默认**不接受上游撤回**（`ignore-delete` 可让 -D 被忽略）；上游若是纯 append/带完整变更的 CDC，
  按 `full` 压缩模式+正确 producer 组合（6.5）；
- **完成度判断**：下游想知道"这行的列拼齐了吗"——常见做法是用某个"必到列"非 NULL 作哨兵，或用
  聚合列计数达到列数阈值；1.x 围绕 partial-update 的辅助能力仍在演进，以当前文档为准 🔧；
- **序列组（Sequence Group）**：多流各有时钟（pay_time 与 ship_time 不可比），给每组列指定各自的
  比较列，避免"用 order 流的 update_time 压住支付流的旧记录"这类误判。

### 6.3 aggregation：湖上长出 mini-DWS

规则：同键折叠 = 按列配置聚合函数。典型用途是把"每小时店铺 GMV"这类 DWS 预聚合直接做进湖表：

🔧 示例（官方文档口径仿写）：

```sql
CREATE TABLE shop_gmv (
  shop_id BIGINT,
  dt      STRING,
  gmv     DECIMAL(18,2),
  uv      BIGINT,          -- 位图/基数列可用 rbm64 等函数 🔧
  primary_key_last_update TIMESTAMP(3),
  PRIMARY KEY (shop_id, dt) NOT ENFORCED
) WITH (
  'merge-engine' = 'aggregation',
  'fields.gmv.aggregate-function' = 'sum',
  'fields.uv.aggregate-function' = 'rbm64',            -- 去重计数思路，以文档为准
  'fields.primary_key_last_update.aggregate-function' = 'max'
);
```

- 默认（不写配置）列函数是 last_non_null_value（第 02 章 sequence 参与排序）🔧；
- **回撤支持有限**：sum 等可减函数需要上游带 -U/-D（部分函数支持 retract），last_value 类无所谓——
  每个聚合函数是否处理撤回，文档有函数表（6.5 的矩阵会用到）；
- compaction 前先局部聚合（local-global）可显著压 level-0 膨胀 🔧；
- 聚合引擎表天然产不出行级 -U 全貌（值是被折叠的），流读它的正确性依赖 lookup/full-compaction
  changelog producer（第 07 章）。

### 6.4 first-row：给"只关心第一次"的流省内存

规则：同键第一条胜出，后续同键记录直接丢弃。官方场景：上游带回撤的流想变成"无回撤的 append 流"、
按事件 id 去重且旧事件不变。约束（🔧 文档）：

- 不能配 partial-update/aggregation（互斥）；上游出现 -U/-D 对该键的**更新**会直接报错（first-row 拒绝任何对已存在键的变更消息）；
- 想要流读不产生合并读（changelog 免生成，直接以首行为 +I）——必须 `changelog-producer = 'lookup'` 或
  deletion-vectors 模式配合，否则读时仍需合并判断"是否首行"。

first-row 是"湖上当 dedup 中间算子"的捷径：省掉 Flink 去重 state，代价全在 LSM 写放大上。

### 6.5 组合矩阵：merge-engine × changelog-producer × 上游流类型

| 上游 | deduplicate | partial-update | aggregation | first-row |
| --- | --- | --- | --- | --- |
| 纯 append（无回撤） | producer=none 即可流读（等价 +I 流）或 input 保序 | ✅ 主流用法 | 多数列函数可用 | ✅ 去重流 |
| CDC 完整变更（+I/-U/+U/-D） | producer=input 直拷 changelog（最省）| ⚠️ 撤回语义冲突：需 ignore-delete/按文档 | ⚠️ 函数逐个查撤回支持 | ❌ 报错（6.4）|
| Flink 聚合/回撤流 | input 不成立（半截 changelog），用 lookup/full-compaction | ⚠️ 同上 | 部分支持 | ❌ |

> 经验总结成一句话：**merge engine 决定"表里留什么"，changelog producer 决定"外面流里传什么"；
> 两者共同决定"正确性"，上游流类型决定"可选集合"**。任何"实时报表对不上"的排障都从这张矩阵开始。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| "partial-update 用 null 能清空一列" | NULL 的保留语义就是"不更新"；清列需要哨兵值或额外配置 🔧 |
| "aggregation 表 = 物化视图，查询永远正确" | 结果的正确性依赖**所有写入都走同一套键/序列纪律**；一个乱序批次能把 sum 永久做歪——湖上没有 OLTP 行锁兜底 |
| "deduplicate 表流读一定给 -U/+U" | 默认（producer=none）不能保证完整 changelog，见 07；很多人把"能流读"误当"有 changelog" |
| "first-row 就是 deduplicate 反过来" | 反向只是规则描述；first-row 的流读免合并与拒绝更新行为是独立引擎实现，配置面也不同 |
| "四个 merge engine 随时可改" | 改引擎=改历史数据的折叠规则；存量 level 文件按旧规则折叠，需重刷/重建路径谨慎评估 |
