# 第 3 章 模块化、对象和状态（3.2 环境模型 / 3.3 变动数据模拟 / 3.4 并发）

> **一句话**：并发的难点不在调度，而在**「时间」本身进入语言语义**；约束传播系统则给出了另一种答案——**不去描述步骤，只描述关系，让系统自己收敛**。

## 核心精讲

> 教学示意，**不参与构建、不编译**。

### 变动数据的模拟：中心管制员

```scheme
; 电梯：局部状态 + 调度器，全部通过消息交互
(define (make-elevator state)
  (define (dispatch m)
    (cond ((eq? m 'turn-on) (set! state (list 'on)))
          ((eq? m 'shut-down) 'shut-down)
          ((eq? m 'move) (set! state (list 'moving)))
          ((eq? m 'passenger-requests) (set! state (list 'requesting)))
          ((eq? m 'update) (set! state (list 'update)))
          ((eq? m 'destination-reached) (set! state (list 'lift-open)))
          (else (error "Unknown request" m))))
  dispatch)

(define (dispatch-elevator operation)
  (if (eq? (car operation) 'request)
      (let ((elevator (make-elevator '(idle))))
        (elevator 'update)
        (elevator 'move)
        (elevator 'passenger-requests)
        (elevator 'destination-reached))
      (dispatch-elevator '())))
```

> 这个例子（3.3.1）的要点是：**没有中心化的调度表，每个实体只维护自己的状态**。这正是后来 Actor 模型与 reactive 系统（Akka、Celluloid、Rx）的思想源头。

### 串行化约束：把系统描述成关系

```scheme
; 约束的三件套：值、约束集、操作
(define (make-connector)
  (let ((value #f) (constraints '()))
    (define (dispatch m)
      (cond ((eq? m 'has-value?) value)
            ((eq? m 'set-value!) ...)
            ((eq? m 'forget!) ...)
            ((eq? m 'connect) ...)
            ((eq? m 'constraints) constraints)
            (else (error "Unknown operation" m))))
    dispatch))

; 用约束描述一句「x + y = z」
; adder 的三个端口 a、b、sum 都是 connector，谁被赋了值都能反推剩下两个
(define (make-adder a b sum)
  (define this 'an-adder-constraint)
  (define (process-new-value)
    (cond ((and (has-value? a) (has-value? b))
           (set-value! sum (+ (get-value a) (get-value b)) this))
          ((and (has-value? a) (has-value? sum))
           (set-value! b (- (get-value sum) (get-value a)) this))
          ((and (has-value? b) (has-value? sum))
           (set-value! a (- (get-value sum) (get-value b)) this))))
  (define (process-forget-value)
    (forget-value! sum) (forget-value! a) (forget-value! b)
    (process-new-value))
  (connect a this) (connect b this) (connect sum this)
  (process-new-value)
  this)
```

> 调用形态（示意，不代表原书的完整写法）：

```scheme
(define x (make-connector))
(define y (make-connector))
(define z (make-connector))
(install-adder x y z)     ; 声明关系：x + y = z

(set-value! x 3 'user)
(set-value! y 4 'user)
; z 自动变成 7 —— 传播发生，程序里没有任何一句「算 z = 」的赋值
```

> 注意 `set-value!` 的第二个参数是**来源标签**，它决定了 `forget!` 时该撤销哪条来源——这个细节是传播式系统能正确回滚的前提。

> **这是「声明式」的第一次完整亮相**：你描述的是**关系**而不是**步骤**。这一思想在 2020 年代以「电子表格引擎」「Bloom/reactive programming」「约束求解（Z3、MiniZinc）」的形式重新流行。

### 数字电路：传播 + 事件队列

```scheme
; 逻辑门也是约束
(define (make-inverter input output)
  (define (action) ...)
  (define (forget-action) ...)
  'ok)

; 延迟通过「after-delay」排进事件队列
(define (after-delay delay action)
  (add-to-agenda delay action))
```

> 电路模拟里，约束传播需要**处理「顺序」这件事**（3.3.4）。这一步为 3.4 的并发做好了铺垫：**传播系统本质上就是一个并发系统，只是它的调度是确定的**。

### 并发：共享 `set!` 的险恶

```scheme
(define (make-account balance)
  (define (withdraw amount)
    (if (>= balance amount)
        (begin (set! balance (- balance amount))
               balance)
        "Insufficient funds"))
  withdraw)

(define (test-account n)
  (define acc (make-account 100))
  (define (test-loop) ...)
  (parallel-execute
    (lambda () (let loop ((i 0)) (if (= i 100) 'done (begin ((acc 'withdraw) 1) (loop (+ i 1))))))
    (lambda () (let loop ((i 0)) (if (= i 100) 'done (begin ((acc 'deposit) 1) (loop (+ i 1))))))))
```

> 交错执行会让某些 `withdraw` 在「检查余额」与「扣款」之间被另一线程插入，导致**余额为负或丢失更新**。这是 3.4 的招牌案例。
> 1996 年的答案：给 `withdraw` 加 `define` 互斥（`(define (withdraw amount) ...)` 前加串行化），或者干脆**重新设计成不带共享状态的形式**。

### 顺序视图：把并发当成可交换的事件序列

```scheme
; 3.4.2：并发执行 = 一串按某种顺序排列的事件
(define (parallel-execute p1 p2)
  (let ((t1 (make-thread p1)) (t2 (make-thread p2)))
    (schedule t1 t2)))
```

> 「把并发执行看成按顺序取出的事件流」是 3.4 的核心洞见；它直接通向 2026 年的 **RBW（sequential consistency 的可交换交换）、Deterministic Parallel Java、以及 Chan/serializability 理论**。

## 版本演进

| 阶段 | 要点 |
| --- | --- |
| **1962 Dijkstra** | 「Cooperating Sequential Processes」；并发从操作系统走向语言 |
| **1974 Hoare** | CSP 与监控器（monitor）；与 SICP 3.3 的串行化约束同一思路 |
| **1978 Reversi/Scheme 的并发扩展** | SICP 3.4 讨论了 `define` 加 mutex 的写法 |
| **1986 Actors 论文** | Hewitt 的 Actor 模型；SICP 3.3.1 的中心管制员是它的先驱 |
| **1990 年代** | 线程库（pthreads）与事件循环（Node.js 之前是 Tcl/Perl 的 event loop）分道扬镳 |
| **2005–2010** | Erlang/OTP、Akka（Scala）把 Actor 带回主流；Clojure 的 `ref`/`agent` 给出软件事务内存化的答案 |
| **2013 Rust** | 所有权 + 类型系统把「共享 vs 独占」变成编译期问题 |
| **2020 Rust async / Go 1.x** | async/await、`tokio` 提升了事件循环的表达力；C++20 atomics/coroutine 补齐 |
| **2021 Java Loom** | 虚拟线程（Project Loom）让「每个请求一个线程」重新可行，直接呼应 3.4 的顺序视图 |
| **2026 现状** | 共识是「**共享可变状态是万恶之源**」；主流解法定型为三选一：不可变数据、显式所有权、消息传递/通信顺序进程 |

> **1996 → 2026**：3.4 的 mutex 方案今天仍在用（pthread/mutex/ReentrantLock），但工业界的**默认语气已经变了**——从「用锁保护它」变成「别让它被共享」。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **3.4 的并发原语已过时** | 本书写于 1996 年，用 `define` + 串行化约束表达互斥；今天应直接对照 pthread mutex / `synchronized` / Rust `Mutex<T>` / Go channel |
| 🔧 **「时间是一个本质问题」的表述** | 这句判断在 2026 年更成立（AI 时代大量推理框架依赖确定性）；但本书**没有给出形式化模型**（如线性一致性），这是缺口 |
| **约束传播被误读为「声明式编程」全部** | 3.3 的传播系统需要**终止性保证**（循环约束会无限传播），本书只在练习里提；现代解法是加入 fixed-point 检查与依赖图分析 |
| 🔧 **电梯/飞机例子的工程细节过时** | 3.3.1 的中心管制员假设「消息传递足够快」；2026 年的分布式系统必须考虑消息丢失与延迟，需要超时与重试 |
| **互斥与无锁的对立被简化** | 3.4 只讨论互斥；2020 年代的无锁数据结构（hazard pointer、RCU）是另一条路线，本书完全没有覆盖 |
| 🔧 **缺少线性类型/所有权视角** | 3.4 讨论「共享状态出错」时没有类型工具的帮助；Rust 的所有权系统是同一问题的编译期答案，建议对照阅读 |
| **练习要求过高** | 3.3.4 的数字电路模拟与 3.4 的调度器练习在中文版无提示，是全书公认最难的三组练习之一 |
