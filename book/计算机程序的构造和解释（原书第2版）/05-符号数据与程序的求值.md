# 第 2 章 构造数据抽象（2.3 符号数据 / 2.4.1–2.4.4 带标志数据与求值模型）

> **一句话**：一旦 `quote` 让数据与程序同形，程序就能**把数学当成数据来操作**；而一旦给数据打上类型标签，`eval` 也就能**按标签选择处理方式**。

## 核心精讲

> 教学示意，**不参与构建、不编译**。

### 引号：让符号不再被求值

```scheme
; 不带 quote：'abc 这个符号会被求值成变量值（通常是错误）
; 带 quote：得到符号本身
(define a 5)
(quote a)          ; ==> 符号 a
'abc               ; ==> 符号 abc（语法糖）
''a                ; ==> (quote a)，即「quote 这个符号」
(list 'a 'b)       ; ==> (a b)：列表里装的是符号，不是变量
```

> **这是整本书的分水岭**：在此之前数据只是数字和列表；在此之后，**「符号」成为可操作的一等公民**，程序可以处理「程序」。2.3.2 的符号求导完全建立在这一件事上。

### 符号求导：规则即数据

```scheme
; 抽象语法：+ 与 * 用列表表示
(define (deriv exp var)
  (cond ((number? exp) 0)
        ((variable? exp)
         (if (same-variable? exp var) 1 0))
        ((eq? (operator exp) '+) (make-sum (deriv (addend exp) var)
                                          (deriv (augend exp) var)))
        ((eq? (operator exp) '*) (make-product (deriv (multiplier exp) var)
                                               (deriv (multiplicand exp) var)))
        (else (error "unknown expression type -- DERIV" exp))))

; 谓词与选择器
(define (variable? x) (symbol? x))
(define (same-variable? v1 v2)
  (and (variable? v1) (variable? v2) (eq? v1 v2)))
(define (operator e) (car e))
(define (addend e) (cadr e))
(define (augend e) (cddr e))
(define (multiplier e) (cadr e))
(define (multiplicand e) (cddr e))

; 构造器：顺手做化简
(define (make-sum a1 a2)
  (list '+ a1 a2))
(define (make-product m1 m2)
  (list '* m1 m2))

(deriv '(+ x 3) 'x)       ; ==> (+ 1 0)
(deriv '(* x y) 'x)       ; ==> (* y x)
```

> 三步走的设计（练习 2.58 是它的升级版）：
> 1. **把表达式表示为数据**（列表）；
> 2. **把规则写成选择器/构造器**（`operator/addend/make-sum`）；
> 3. **化简放在构造器里**，而不是调用方——这是「**决策内聚**」的经典范例。

### 集合的两种表示

```scheme
; 有序表：θ(n)
(define (element-of-set? x set)
  (cond ((null? set) #f)
        ((equal? x (car set)) #t)
        ((< x (car set)) #f)
        (else (element-of-set? x (cdr set)))))

; 二分树：θ(log n)
(define (make-tree entry left right)
  (list entry left right))
(define (entry tree) (car tree))
(define (left-branch tree) (cadr tree))
(define (right-branch tree) (cddr tree))
```

> 同一套操作契约（`element-of-set?`/`adjoin-set`/`union-set`）配两种表示之间可自由切换，正是 2.1.2 抽象屏障的复现——**但这次屏障之下是数据结构的选择**。

### 带标志数据：给数据贴类型标签

```scheme
; 通用选择器与构造器
(define (attach-tag type-tag contents)
  (cons type-tag contents))
(define (type-tag datum)
  (if (pair? datum) (car datum) 'primitive))
(define (contents datum)
  (cond ((pair? datum) (cdr datum))
        (else datum)))

; 复数：直角坐标表示
(define (make-rectangular x y)
  (attach-tag 'rectangular (cons x y)))
(define (real-part-rect r) (car r))
(define (imag-part-rect i) (cdr i))

; 极坐标表示
(define (make-polar r a)
  (attach-tag 'polar (cons r a)))
(define (magnitude-polar p) (car p))
(define (angle-polar p) (cdr p))

; 通用操作：按标签分派
(define (real-part z)
  (cond ((eq? (type-tag z) 'rectangular) (real-part-rect (contents z)))
        ((eq? (type-tag z) 'polar) (* (magnitude-polar (contents z))
                                      (cos (angle-polar (contents z)))))
        (else (error "bad reason"))))

(define (magnitude z)
  (cond ((eq? (type-tag z) 'rectangular) (sqrt (+ (square (real-part-rect (contents z)))
                                                  (square (imag-part-rect (contents z))))))
        ((eq? (type-tag z) 'polar) (magnitude-polar (contents z)))
        (else (error "bad reason"))))
```

> 问题立刻暴露：每加一种表示，就要**修改所有通用操作**——违反开放封闭原则。2.4.3 给出解法。

### 数据导向编程：`put`/`get` 操作表

```scheme
; 全局两张表：操作 × 类型 → 实现
(define *op-table* (make-hash))   ; 示意实现，实际用 alist 或 hash-table

(define (put op type proc)
  (hash-set! *op-table* (list op type) proc))

(define (get op type)
  (hash-ref *op-table* (list op type) #f))

; 第三方可以「新增操作」而不用改已有代码
(define (apply-generic op args)
  (let ((type-tags (map type-tag args)))
    (let ((proc (get op type-tags)))
      (if proc
          (apply proc args)
          (error "no method for these types" op type-tags)))))

; 注册（在直角坐标包里）
(define (install-rectangular-package)
  (define (real-part z) (car z))
  (define (imag-part z) (cdr z))
  (define (make-from-real-imag x y) (cons x y))
  (put 'real-part '(rectangular) real-part)
  (put 'imag-part '(rectangular) imag-part)
  (put 'make-from-real-imag 'rectangular make-from-real-imag)
  'done)
```

> **这就是「可加性」（extensibility）**：新增一种数据类型时，**只需往表里 `put`，不必修改现有操作**。这是 SICP 2.4.3 的核心命题，也是今天 Go 泛型、Rust trait、C++ concept 想达到的目标。
> 缺点同样明显：`get` 返回 `#f` 才发现错误——**错误发现得晚**。

### 消息传递：把操作放进数据

```scheme
(define (make-account balance)
  (define (withdraw amount)
    (if (>= balance amount)
        (begin (set! balance (- balance amount)) balance)
        "Insufficient funds"))
  (define (deposit amount)
    (set! balance (+ balance amount))
    balance)
  (lambda (m)
    (cond ((eq? m 'withdraw) withdraw)
          ((eq? m 'deposit) deposit)
          (else (error "unknown request" m)))))

(define acc (make-account 100))
((acc 'withdraw) 50)    ; ==> 50
```

> 与 `put/get` 的对照是本章最重要的收获：**数据导向（外部表）vs 消息传递（内部 dispatch）**——前者利于新增类型，后者利于新增操作，两者是「可加性的两个方向」。
> 这条主线在 2.5 汇合成泛型操作，在 3.1.3 变成真正的对象系统。

### 内部定义、`letrec` 与块结构

```scheme
; letrec：让内部定义的名字在**求值之前**就可见（互相递归可以）
(define f (letrec ((is-even? (lambda (n) (or (= n 0) (is-odd? (- n 1)))))
                   (is-odd?  (lambda (n) (and (> n 0) (is-even? (- n 1))))))
             is-even?))

; let 的定义：内部定义只是 lambda 的参数绑定
(define (sqrt x)
  (let ((guess 1.0))
    (define (good-enough? g) (< (abs (- (square g) x)) 0.001))
    (define (improve g) (average g (/ x g)))
    (define (try g) (if (good-enough? g) g (try (improve g))))
    (try guess)))
```

> **`let` ≡ `lambda` 应用**，而 `define` 的内部定义 ≡ `letrec`。这套等价关系解释了 3.2 环境模型的全部行为：**局部状态 = 一次调用创建的环境帧**。

## 版本演进

| 阶段 | 演进要点 |
| --- | --- |
| **1960 LISP** | `quote` 即存在（早期叫 `'`），符号处理是 LISP 区别于 ALGOL 的核心能力 |
| **1975 Scheme** | 引入词法作用域，`letrec` 的内部定义语义才有了干净的定义；2.4.4 的消息传递因此成立 |
| **1978 Rears Report / 1998 R5RS** | `quote`/`eq?`/`pair?`/`list?` 进入标准；`letrec` 的语义被精确化（`letrec*` 的变体也随之出现） |
| **Common Lisp / CLOS** | 走向**通用函数 + 类 + 多重分派**（CLOS 的 `defmethod`），是「数据导向」在动态语言里的成熟形态 |
| **Racket（2007+）** | `define-struct` 默认生成「构造器 + 选择器 + 谓词 + 可打印」，并把「打印格式」也做成可定制的 `prop:custom-write`；`match` 让带标志数据的分派代码短一半 |
| **2026 的对应物（静态语言）** | Rust trait / C++20 concept / Go 泛型约束 / Java 的 sealed interface —— 都在做「**按类型分派操作，且编译期检查**」；SICP 2.4 的 `put/get` 是它们的动态原型 |
| **2026 的趋势** | 双重分派与 trait object 的开销问题推动「单态化（monomorphization）」；Rust 与 C++ 的通用代码在 2026 年已经**性能等价于手写专用代码** |

> **1996 → 2026**：2.4 的「可加性」理想今天大多由**泛型 + trait** 实现，只是把「运行期 `get` 返回 `#f`」换成了「编译期找不到 impl 就报错」。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **两张表与 hash 表** | 1996 年的 `put/get` 用 **alist**（线性查找）；2026 年替换成 `hash-table` 是等价改写，但**删除项的语义**（`get` 返回 `#f` vs 抛异常）需要显式约定 |
| 🔧 **方言内部定义可见性** | `define` 的内部定义在 R5RS 与 R6RS/Racket 里语义不同（`letrec` vs `letrec*` 的区别在深链递归时会露头），照抄本书写法在 Racket 里可能出现「未定义变量」 |
| **消息传递 vs 数据导向的取舍被模糊** | 2.4.3/2.4.4 并列出现，容易读成「两种写法二选一」；实际上前者利于**新增类型**，后者利于**新增操作**，选择标准应显式写出 |
| 🔧 **符号求导的化简缺失** | 本书的 `make-sum` 只做了平凡化简；真实的符号代数系统（2.5.3）需要处理嵌套化简与顺序约定，`deriv` 的输出 `'(+ 1 0)` 这样的**未化简形式**在数学上不美观 |
| **练习 2.58 的嵌套表达式** | 中译本对 `(8 (* 3 x) ...)` 这类「中缀混合」的过渡语法处理含糊，容易读不懂题目要求 |
| 🔧 **对象系统叙述过时** | 2.4.4 提及 Smalltalk/CLOS 的对象观；2026 年的对象更多与「可变状态 + 所有权」绑定（Java 的 record、Rust 的 `&mut`），**消息传递不再是对象的主要卖点** |
| **练习无答案** | 2.4 的 Huffman 编码树与集合表示练习在中文版无官方答案，建议配合标准题解仓库自行验证 |
