# 专篇：尾递归与迭代（SICP 1.2 的现代展开）

> **一句话**：尾调用优化解决的问题不是「递归太慢」，而是**「递归的形状限制了你能表达的迭代」**；它至今是所有语言争论不休的一块飞地。

---

## 1. 四个容易被混用的概念

| 概念 | 指什么 | 谁决定 |
| --- | --- | --- |
| **递归过程**（recursive process） | 解释器要记住「回来之后还要做什么」 | 调用是否在尾部 |
| **迭代过程**（iterative process） | 状态显式携带在参数里，只需常量空间 | 同上 |
| **递归函数**（recursive function） | 语法上调用了自身 | 程序员写法 |
| **尾调用优化**（TCO） | 编译器把尾部自调用改成跳转 | 编译器/运行时 |

> 关键区分：**「递归函数」与「递归过程」无关**。`fact-iter` 语法上是递归函数，执行上是迭代过程。

```scheme
; 递归函数 + 迭代过程
(define (fact-iter n)
  (define (iter count product)
    (if (= count 1) product (iter (- count 1) (* count product))))
  (iter n 1))

; 递归函数 + 递归过程（栈深 O(n)）
(define (fact-rec n)
  (if (= n 1) 1 (* n (fact-rec (- n 1)))))
```

---

## 2. 为什么尾递归值得单独一章

尾调用允许你**用递归的语法写迭代的程序**，好处有三：

1. **数据结构天然递归**（树、列表），用递归写遍历最自然；
2. **尾递归让「累加器模式」成立**——把中间状态显式带在参数里，等价于循环变量；
3. **无状态的语言里，尾递归是唯一的迭代手段**。

代价是一个 1996 年没人担心、2026 年人人都在意的问题：**栈回溯信息丢失，调试变难**。

---

## 3. 各语言在 2026 年的实际立场

| 语言/运行时 | 尾调用优化 | 备注 |
| --- | --- | --- |
| Scheme / Racket（R5RS/R7RS） | **保证**（Racket 甚至支持深递归的 continuation） | SICP 的全部前提 |
| OCaml / Haskell | 保证 | 函数式默认形态 |
| Clojure | 用 `recur` **显式声明** | 不加 `recur` 就是真递归 |
| Kotlin | `tailrec` 注解（编译器检查） | 显式优于隐式 |
| Scala 3 | `@tailrec` 注解 | 同上 |
| Rust | 无 TCO，但 `loop` 是尾表达式 | 循环是首选形态 |
| Java / JVM | **无 TCO**（栈帧可复用≠尾调用） | 递归上限约 1000–10000 |
| Python | **无 TCO** | 递归上限 `sys.setrecursionlimit` |
| C / C++ | C 语言标准未规定；实践上 gcc/clang 通常优化尾调用，但**调试信息可能丢失** | 未定义行为的灰区 |
| JavaScript | 2018 年重新提出，**因调试栈冲突被搁置** | 至今无标准 TCO |
| Go | 无 TCO | 靠 goroutine 栈增长 |
| Swift | 无 TCO | 循环是主流 |

> **这张表本身就是 SICP 1.2 在 2026 年的答案**：尾递归不是「有没有」的问题，而是「**愿不愿意牺牲调试能力**」的问题。

## 4. 尾递归的三种实现手法

```scheme
; 手法一：累加器（accumulator）—— 最通用
(define (reverse-tr lst)
  (define (iter rest acc)
    (if (null? rest) acc (iter (cdr rest) (cons (car rest) acc))))
  (iter lst '()))

; 手法二：延迟的 let 绑定（Scheme 的 let 表达式尾部）
(define (safe-sum lst)
  (let loop ((rest lst) (acc 0))
    (if (null? rest) acc (loop (cdr rest) (+ acc (car rest))))))
```

> `let loop` 是 Scheme 里最标准的「命名 let」，它等价于一个 self-call 的 lambda，语义上完全就是尾调用。

```scheme
; 手法三： continuation 传递风格（CPS）—— 递归变尾递归的通用变换
(define (sum-cps lst k)
  (if (null? lst)
      (k 0)
      (+ (car lst) (sum-cps (cdr lst) k))))

; 转成 CPS + 尾部调用
(define (sum-cps lst k)
  (if (null? lst)
      (k 0)
      (sum-cps (cdr lst) (lambda (rest-sum) (k (+ (car lst) rest-sum))))))
```

> CPS 是「**把递归改成尾递归的通用手术**」。代价：分配 continuation、栈变成堆。这正是编译器在SPJ（speculative）优化里做的事，也是调试器讨厌它的原因。

## 5. 尾递归不等于快（反例清单）

| 反例 | 为什么慢 |
| --- | --- |
| `count-change`（SICP 1.2 练习） | 两个分支都递归 → 指数级时间 + 指数级栈深 |
| 树形 `fib` | 重复子问题，形状问题不是栈问题 |
| 未记忆化的 memo 表 | 每次查找 O(n) |
| 深表上的非尾递归 `map` | 栈深与表长成正比 |

> **记忆化能把树形递归变成线性**：把 `(define (fib n) ...)` 换成用 `delay` + 记忆化的形式，θ(φⁿ) → θ(n)，且不改算法结构。见 `concepts/惰性求值.md`。

---

## 6. 与 2026 年工程实践的连接

- **尾递归的替代方案**：循环 + 累加器（Java/Go/Rust）；
- **栈安全**：尾递归不行时，用**显式栈**（while + 自己的栈）或**惰性序列**（流）；
- **调试代价**：Racket 提供 `call/cc` 与可控 continuation；JS 无 TCO 的理由正是「保留栈」；
- **静态检查**：`tailrec`/`@tailrec` 注解把「我以为我写的是尾递归」变成「编译器确认它是」——**这正是 SICP 的精神在 2026 年的产物形式**。
