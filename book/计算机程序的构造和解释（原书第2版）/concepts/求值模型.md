# 专篇：求值模型（代换模型 → 环境模型 → 显式控制求值器）

> **一句话**：Scheme 的求值模型讲了三轮——**代换模型**（讲对了吗）、**环境模型**（讲清了吗）、**显式控制求值器」（跑得快吗）——三轮都不是替换关系，而是同一件事的三个抽象层次。

---

## 1. 三种模型各自的适用场景

| 模型 | 诞生位置 | 能解释什么 | 不能解释什么 |
| --- | --- | --- | --- |
| **代换模型**（substitution model） | SICP 1.1.5 / 3.2 开头 | 纯计算的正确性；「先算哪个」不影响结果 | `set!`、局部状态、递归过程的空间开销 |
| **环境模型**（environment model） | SICP 3.2 / 4.1 | 词法作用域、闭包、对象与私有状态、递归过程如何各自持有一份状态 | 栈的空间复杂度；控制流为何消耗栈 |
| **显式控制求值器**（explicit-control evaluator） | SICP 5.4 | 递归如何变成跳转；栈从哪里来、到哪里去 | 可读性；求解规则本身 |

> **记住这一点**：很多读者把这三章读成「作者不断推翻自己」，其实它们是**逐层增加机器细节**。SICP 后面每一章都会回来用前面模型的语言，所以必须分清哪一层在回答哪个问题。

---

## 2. 代换模型的两个致命缺陷

```scheme
; 缺陷一：没有「同一时刻」的概念 —— 顺序在这里没有意义
(define (test x) (set! x 10))
; 一旦引入 set!，(f (+ a 1)) (f (+ a 2)) 与 (f (+ a 2)) (f (+ a 1)) 结果可能不同

; 缺陷二：没有「局部状态」的概念 —— 同一个过程两次调用必须互不干扰
(define (counter)
  (define n 0)
  (lambda () (set! n (+ n 1)) n))
; 代换模型无法解释 (define c (counter)) 之后 n 存在哪里
```

代换模型是**纯计算**的理想模型；一旦引入可变状态，就必须引入「时间」与「标识」，于是有了环境。

---

## 3. 环境模型的形式化

```scheme
; 环境 = 帧的链；帧 = 名字 → 值的映射
; E = [ | count -> 42 | ] ↑ [ | counter -> #[closure]| ] ↑ 全局环境

; 三条规则
; 1. 求值变量：沿链找第一个含此名字的帧
; 2. 求值 define：在当前帧建立绑定（值 = 闭包，闭包 = (参数, 体, 定义时的环境)）
; 3. 应用过程：新建帧（形参 = 实参），父环境 = 闭包捕获的环境，在其中求体
```

这套规则直接解释了三个常见困惑：

| 现象 | 环境模型的解释 |
| --- | --- |
| 闭包能看见外层的 `x` | 闭包捕获的是**定义时的环境**，不是调用时的环境 |
| 递归过程各自有独立状态 | 每次调用创建新帧，名字解析独立于其他调用 |
| `set!` 只改当前可见的那个绑定 | `set!` 找到第一个含此名字的帧就停止向上 |

> **闭包的环境捕获**是 2026 年任何语言里最容易出 bug 的地方：JS 早期用 `var` 造成的「循环中的闭包捕获同一变量」就是环境模型没被正确理解的表现（ES6 的 `let` 用块级帧正是修正）。

## 4. 从环境模型到显式控制求值器

```
求值器递归（4.1）              显式控制求值器（5.4）
(eval exp env)                 (goto (label eval-dispatch))
  ├─ 变量 → lookup                 ├─ 变量 → (assign val (op lookup) ...)
  ├─ lambda → make-procedure       ├─ lambda → (assign val (op make-closure) ...)
  ├─ 应用 → apply(...)             ├─ 应用 → (goto (label eval-application))
  └─ 序列 → eval-sequence          └─ 序列 → (goto (label eval-sequence))
```

被「显式化」的东西一共只有四个：

| 隐式的东西 | 显式的寄存器 |
| --- | --- |
| 调用栈 | `stack` + `continue` 寄存器 |
| 环境 | `env` 寄存器 |
| 当前表达式 | `exp` 寄存器 |
| 实参列表 | `argl` / `unev` 寄存器 |

> **这是一次「把调用栈变成数据」的变换**——也是 continuation 概念的全部动机。今天 JS 的 `async/await`、C++ 的 coroutine、Rust 的 `async fn`，底层都在做同一件事：**把 `(goto (reg continue))` 存进堆**。

## 5. 与虚拟机模型的对应

| SICP 的寄存器机 | 现代 VM |
| --- | --- |
| 寄存器 | 局部变量槽 / 寄存器分配后的物理寄存器 |
| 指令序列 | 字节码 |
| `stack` | 操作数栈 / 帧栈 |
| `make-machine` + 模拟器 | JVM 的 interpreter + JIT |
| `compile` 生成指令树 | 前端 → IR → 优化 → 代码生成 |

> 想深一步，可以看 **SECD machine**（函数式语言的另一种抽象机）与 **Krivine machine**（lambda 演算的抽象机）— 它们与寄存器机是同一枚硬币的三面。

## 6. 常见误区

| 误区 | 正解 |
| --- | --- |
| 「代换模型是错的，环境模型是对的」 | 各有适用域：纯计算用代换更直观；有状态用环境 |
| 「闭包 = 匿名函数」 | 闭包 = **函数 + 定义环境的引用**；没有捕获环境的匿名函数不是闭包 |
| 「作用域是词法/动态的选择」 | 现代语言几乎都选**词法作用域**，因为可静态推理；动态作用域只在少数嵌入式语言里存活 |
| 「尾调用优化是性能优化」 | 它是**语言语义的一部分**（R5RS 允许），不是锦上添花；缺了它，很多算法无法表达 |
| 🔧 「环境模型不含栈」 | 环境模型隐含了栈（过程调用创建帧）；显式控制求值器把它显式化是为了控制空间 |
