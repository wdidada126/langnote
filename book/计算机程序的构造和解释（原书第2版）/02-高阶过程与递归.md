# 第 1 章 构造过程抽象（1.2：递归过程、迭代过程与尾递归）

> **一句话**：递归过程与迭代过程的差别不是「递归 vs 循环」，而是**解释器要不要替你记住「回来之后还要做什么」**——尾调用把这份记忆交还给程序员。

## 核心精讲

> 全部代码为**教学示意，不参与构建、不编译**。

### 递归过程 vs 迭代过程：同一个 `fact`

```scheme
; 递归过程：解释器必须记住每层「回来后还要乘 n」
(define (fact-rec n)
  (if (= n 1)
      1
      (* n (fact-rec (- n 1)))))

; 迭代过程：状态本身被显式携带在参数里
(define (fact-iter n)
  (define (iter count product)
    (if (= count 1)
        product
        (iter (- count 1) (* count product))))
  (iter n 1))
```

判断标准（一句话）：**看 `if` 分支里是否还有对自身的调用需要「求值完之后再继续」**。
`fact-rec` 的 `(fact-rec (- n 1))` 先求出来还要 `* n`，所以栈深 O(n)；
`fact-iter` 的调用在尾部，栈深 O(1)。

> 关键在于：**Scheme 语言语义（R5RS）要求尾调用被优化为迭代**，这不是实现细节，而是标准。所以 `fact-iter` 在 Scheme 里不会爆栈 —— 但同样代码在 Java/Python 里会。
> 展开见 `concepts/尾递归与迭代.md`。

### 树形递归：`fib` 的经典对比

```scheme
; 树形递归：每次调用分裂成两次，规模 T(n) = T(n-1) + T(n-2) + O(1)
(define (fib n)
  (cond ((= n 0) 0)
        ((= n 1) 1)
        (else (+ (fib (- n 1))
                 (fib (- n 2))))))

(fib 5)   ; ==> 5，但调用次数是斐波那契数列本身，θ(φⁿ / √5)，φ≈1.618

; 尾递归版本：把「已经算过的部分」显式带在参数里
(define (fib-iter n)
  (define (iter a b count)
    (if (= count 0)
        a
        (iter b (+ a b) (- count 1))))
  (iter 0 1 n))

; 也可以用 let 表达同一结构
(define (fib-let n)
  (let iter ((a 0) (b 1) (count n))
    (if (= count 0)
        a
        (iter b (+ a b) (- count 1)))))
```

> `(fib 25)` 的树形版本在解释器中要跑数秒，迭代版本瞬间返回。**差 1000 倍量级**不是因为机器变快，而是形状不同——这是本书最著名的一课。

### 求幂：把「重复」变成「分治」

```scheme
; 线性：θ(n)
(define (expt-iter b n)
  (define (iter a b n)
    (if (= n 0)
        a
        (iter (* a b) b (- n 1))))
  (iter 1 b n))

; 快速幂：θ(log n)
(define (fast-expt b n)
  (cond ((= n 0) 1)
        ((even? n) (square (fast-expt b (/ n 2))))
        (else (* b (fast-expt b (- n 1))))))

(define (even? n) (= (remainder n 2) 0))
```

`fast-expt` 本体是递归的，但**栈深是 O(log n)** —— 说明「递归形态」和「栈深」是两件不同的事，第三个变量是「是否存在尾位置」。

### GCD：迭代过程的教科书范例

```scheme
(define (gcd a b)
  (if (= b 0)
      a
      (gcd b (remainder a b))))

; 同样的算法，尾递归 + 内部定义
(define (gcd-local a b)
  (define (iter a b)
    (if (= b 0)
        a
        (iter b (remainder a b))))
  (iter a b))
```

> `gcd` 在 Scheme 里天然是尾递归，因为**最后一步恰好就是下一次整个调用**——这就是「尾位置」的直觉来源。

### 计数找零：本书最著名的尾递归练习

```scheme
; 尾递归版本：状态 = (已用面额数, 剩余金额)
(define (count-change amount kinds)
  (define (cc amount kinds)
    (cond ((= amount 0) 1)
          ((< amount 0) 0)
          ((= kinds 0) 0)
          (else (+ (cc amount (- kinds 1))
                   (cc (- amount (first-denomination kinds))
                       kinds)))))
  (define (first-denomination kinds)
    (cond ((= kinds 1) 1)
          ((= kinds 2) 5)
          ((= kinds 3) 10)
          ((= kinds 4) 25)
          ((= kinds 5) 50)))
  (cc amount kinds))
```

> 注意这里**两个递归都不是尾递归**（`(+ (cc ...) (cc ...))` 需要两者都求完再相加），所以 `count-change` 的复杂度是指数级且**栈深也指数级**——真正降到线性的写法要引入记忆化（memoization）或动态规划，那是 2.2 节之后的话题。
> 这个反例很有价值：**尾递归不等于快**。

### 素数检测

```scheme
; 试除法，θ(√n)
(define (prime? n)
  (define (smallest-divisor n)
    (define (find-divisor n test-divisor)
      (cond ((> (square test-divisor) n) n)
            ((divides? test-divisor n) test-divisor)
            (else (find-divisor n (+ test-divisor 1)))))
    (find-divisor n 2))
  (= n (smallest-divisor n)))

; 概率化：费马小定理
(define (fermat-test n)
  (define (try-it a) (= (remainder (fast-expt a n) n) 0))
  (try-it (+ 2 (random (- n 2)))))

(define (fast-prime? n times)
  (cond ((= times 0) #t)
        ((fermat-test n) (fast-prime? n (- times 1)))
        (else #f)))
```

> 从这里 SICP 引导到 Miller-Rabin：把「确定性」换成「重复 k 次的可信度」。这是 2026 年仍在处理 RSA 密钥生成时的标准做法。

## 版本演进

| 阶段 | 与本章相关的关键变化 |
| --- | --- |
| **1960 LISP 1.5** | 递归存在，但**没有尾调用保证**，深递归必然崩栈 |
| **1975 AI Memo 394** | Sussman & Steele 把「尾部调用可被优化为赋值跳转」写进 Scheme 设计目标，1.2 节的全部内容才成立 |
| **R5RS (1998)** | 明确：过程调用在**尾部位置**时允许以常量空间执行 —— 但注意规范用词是 `should` 级别的实践惯例（实现确实普遍遵守），非绝对强制 |
| **R6RS/R7RS (2007/2017)** | 增加 `(let loop ...)` 的正式支持、`do` 的保留；`iterate` 概念在各方言里趋于一致 |
| **Common Lisp** | 同样强调尾递归，但 `(loop ...)` 显式提供迭代语法，两者**并存**（SICP 只讲并存的一种） |
| **Java / Python（2026）** | CPython 无尾调用优化（递归上限约 1000），JVM 规范要求所有方法栈帧可复用 —— **TCO 至今是未解决的争论**：加它会破坏栈回溯调试，不加它程序员就写不出深迭代 |
| **2026 的函数式运行时** | Scala 3 显式记录 `@tailrec` 注解做静态检查；Kotlin/Rust 也有类似的 `tailrec` 或循环展开；**「显式声明尾递归」正在取代「隐式保证」** |

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **1996 年硬件前提** | 1.2 的复杂度对比建立在当时解释器的常数开销上；2026 年 `fib 25` 的两版差距从「分钟 vs 秒」变成「秒 vs 毫秒」，**量级结论仍在，绝对数字全变** |
| 🔧 **「尾递归 = 快」的过度推广** | `count-change` 是反例：两个分支都是递归，`count-change 100 5` 依然指数级。**形状决定复杂度，不是关键字决定** |
| 🔧 **TCO 被写成语言保证** | R5RS 对尾调用的实际约束比很多读者以为的弱；Java/Python 至今不做，读者按 Scheme 习惯写深递归会崩 |
| **混淆递归过程与递归函数** | 「递归过程」指的是**执行时解释器是否保留待办**，与函数本身的语法无关；`fact-iter` 语法上递归、执行上迭代 |
| **忽略树形递归的记忆化机会** | 1.2.2 只给了解法（改用迭代），没提记忆化；`memoize` 是 2.2 之后的话题，容易让读者以为只能二选一 |
| 🔧 **素数检测的叙述过时** | 1.2.6 的费马测试在 1996 年被当作「快且实用」，今天必须与 Miller-Rabin 一起讲，并明确「概率性」的含义 |
| **练习难度陡增** | 1.2 的练习（如 1.11 的双重递归）在中文版无答案 checking，容易卡住；建议配合 `exercism/scheme` 或本书题解仓库 |
