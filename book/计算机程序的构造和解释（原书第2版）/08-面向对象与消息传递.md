# 第 3 章 模块化、对象和状态（3.1 赋值、局部状态与环境模型）

> **一句话**：对象就是把「一段局部状态 + 一组操作这段状态的过程」打包成一束消息；**环境问题不在对象，而在「谁有那份环境」**。

## 核心精讲

> 教学示意，**不参与构建、不编译**。

### `set!`：可变状态的最小装置

```scheme
; 没有 set! 的世界：所有过程都是纯函数
(define (count-1 x) (+ x 1))

; 有了 set!：名字可以「重新绑定」
(define counter 0)
(set! counter (+ counter 1))
counter          ; ==> 1
```

> **SICP 对 `set!` 的态度是克制的**：3.1 只用十几页就建立起来，然后 3.3 立刻展示它的凶险（顺序依赖、并发问题）。这不是随口一说，**1996 年的 Scheme 社区正在经历「纯函数式 vs 命令式」的大辩论**。

### 带局部状态的账户对象

```scheme
(define (make-account balance)
  (define (withdraw amount)
    (if (>= balance amount)
        (begin (set! balance (- balance amount))
               balance)
        "Insufficient funds"))
  (define (deposit amount)
    (set! balance (+ balance amount))
    balance)
  (lambda (m)
    (cond ((eq? m 'withdraw) withdraw)
          ((eq? m 'deposit) deposit)
          (else (error "Unknown request -- MAKE-ACCOUNT" m)))))

(define acc (make-account 100))
((acc 'withdraw) 40)     ; ==> 60
((acc 'deposit) 10)      ; ==> 70
```

> 这段代码在 2026 年任何一个面向对象语言里都长这样（Java：`this.balance`；JS：`this._balance`）。**SICP 第 3 章就是 OO 的第一性原理**——对象没有别的秘密。

### 共享状态与身份

```scheme
(define (make-simplified-withdraw balance)
  (lambda (amount)
    (set! balance (- balance amount))
    balance))

(define w1 (make-simplified-withdraw 100))
(define w2 w1)             ; w1 和 w2 是**同一个对象**
(w1 50)                    ; ==> 50
(w2 25)                    ; ==> 25（不是 75！）
```

> `(eq? w1 w2)` 为 `#t`，`(equal? w1 w2)` 也为 `#t`——**但它们的行为不完全相同**？不，恰恰相反：它们完全共享同一份状态，这才是 `eq?` 有意义的地方。
> 三个等价性操作的区别（练习 3.11/3.12）：
> - `eq?`：判断**身份**（是否同一个对象/指针）
> - `equal?`：判断**结构等价**（递归比较内容）
> - `=`：只用于数值

### 环境模型：把求值放回环境里

```scheme
; 环境是「帧的链」；帧是「名字 → 值」的映射
; E1: | balance -> 100 |           （make-account 调用创建的环境）
;      ↑
; E0: | withdraw -> #[proc] ... |  （全局环境）

(define (make-with-drawer balance)
  (define (withdraw amount)
    (set! balance (- balance amount))
    withdraw))
```

环境模型的三条规则（`eval` 在 4.1 会被重新实现）：

1. **变量查找**：沿环境链向上传，找到第一个含该名字的帧就停；
2. **过程定义**：`(define (f x) body)` 在当前帧建立 `f → closure(f, current-env)`；
3. **过程应用**：`(f a)` 创建一个**新环境**，其父环境是 `closure(f, env)` 的捕获环境，新帧绑定形参到实参，然后在其中求值 body。

### 用环境模型解释「同一个过程、不同状态」

```scheme
; 三个独立的 counter，每个都有自己的 balance
(define (make-counter)
  (let ((count 0))
    (lambda ()
      (set! count (+ count 1))
      count)))

(define c1 (make-counter))
(define c2 (make-counter))
(c1)   ; ==> 1
(c1)   ; ==> 2
(c2)   ; ==> 1   ← c2 的 count 与 c1 无关
```

> **`let` 在这里的作用不可替代**：`(let ((count 0)) ...)` 相当于一次 `lambda` 调用，创建的新环境帧就是「对象的私有状态」。这是本书对 OO 最锋利的一击：**对象的私有状态只是环境帧，别无其他**。

## 版本演进

| 阶段 | 要点 |
| --- | --- |
| **1960 LISP 1.5** | 只有**动态作用域**，`set!` 语义混乱；`defun` 定义的是全局变量 |
| **1975 Scheme** | 改为**词法作用域**；`define` 变成局部绑定，`set!` 才有清晰语义；3.2 环境模型由此成立 |
| **Common Lisp** | 引入 `multiple-value-bind`、`symbol-value` 等；也保留了 `defvar`/`setf` 的动态变量（`*foo*` 约定） |
| **Smalltalk（1980）** | 真正把「一切皆对象 + 消息传递」做成语言；SICP 3.1.3 的实现与之几乎一致 |
| **Java / C++（1996–）** | 把「状态」放进字段，`this` 成为隐式环境引用；**环境模型被藏进运行时** |
| **Racket（2013+）** | `set!` 保留但更强调不可变数据；`box`/`unbox` 显式地表征「可变单元」 |
| **Rust（2015–）** | **所有权**：一次只能有一个可变引用（`&mut`），把「共享状态」的坑在编译期堵住 |
| **Kotlin/Scala/JS（2026）** | 局部可变状态被允许但鼓励 `val`/不可变；JS 的 `let` 就是 SICP 的 `let`（块级作用域） |

> **1996 → 2026**：SICP 3.1 的 `set!` 在 Java/C++/Go 里是字段赋值；在 Rust 里是 `&mut`；在函数式语言里被**取消**（返回新值）。**「共享可变状态」这个问题，2026 年的答案是「尽量别用，用不可变数据 + 显式同步」**——SICP 在 1996 年已经给出了这个建议，只是当时没被重视。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **方言与 `define` 的内部定义** | 3.1 的 `(define (withdraw amt) ...)` 内部依赖 R5RS 对内部 `define` 的 `letrec` 语义；在 Racket 中需确认 `(define (make-account b) (define (withdraw a) ...) ...)` 的可见性规则一致 |
| 🔧 **1996 年环境模型描述过于简化** | 本书用「环境的链式帧」示意，没谈**环境帧的垃圾回收**（5.3 才补）；2026 年的实现必须回答「闭包捕获的环境何时被回收」 |
| **把对象当成类** | 3.1.3 的对象**没有类**；读者从 Java/C++ 迁移过来，容易把「对象 = 类的实例」的先入之见带进来，从而错过本书「对象 = 闭包 + 状态」的洞察 |
| 🔧 **`eq?/equal?/= ` 的边界** | 本书只给结论，未说明 R5RS 对 `eq?` 在**复合数据**上是实现相关的；`equal?` 的递归深度也可能爆栈 |
| **顺序依赖被淡化** | 3.1 的例子都是顺序执行；一旦引入并发（09 章）就会发现 `set!` 的语义无法组合。这是本书刻意留下的伏笔 |
| 🔧 **缺少现代对象系统内容** | 继承、多态、接口、字段封装在 3.1 里完全没有；2026 年的对象系统（Rust trait 对象、Go 接口）需要另找资料 |
| **练习 3.11 的环境图太难** | 3.2 的 `make-simplified-withdraw` 环境图是全书公认的难点之一，中文版没有额外图示，建议手画三遍 |
