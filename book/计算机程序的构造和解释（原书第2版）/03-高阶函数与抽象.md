# 第 1 章 构造过程抽象（1.3 后半：过程作为返回值、lambda、curry 与不动点）

> **一句话**：一旦「过程」这个值可以像数字一样被传入、传出、被计算出来，抽象就从「命名一个东西」升级成「**描述一个模式，然后按需生成具体过程**」。

## 核心精讲

> 教学示意代码，**不参与构建、不编译**。

### 高阶过程：把「模式」抽成参数

```scheme
; 通用求和骨架：三个不同版本共享同一个形状
(define (sum-integers a b)
  (if (> a b) 0 (+ a (sum-integers (+ a 1) b))))

(define (sum-primes a b)
  (if (> a b) 0 (+ (prime? a) (sum-primes (+ a 1) b))))

(define (sum-cubes a b)
  (if (> a b) 0 (+ (cube a) (sum-cubes (+ a 1) b))))
```

三个函数只有一个地方不同，于是：

```scheme
(define (sum term a next b)
  (if (> a b)
      0
      (+ (term a) (term (term a)))) ; 示意：实际写法见下
```

正确的骨架版：

```scheme
(define (sum term a next b)
  (if (> a b)
      0
      (+ (term a) (sum term (next a) next b))))

(define (sum-cubes a b)
  (sum cube a inc b))
(define (sum-integers a b)
  (sum identity a inc b))
```

> 这里出现了 2.4 节「抽象屏障」的完整形态：**`sum` 的用户不需要知道 `term`/`next` 是什么，只要知道它们必须构成一条柯里化的路径**。

### `lambda`：匿名过程

```scheme
; 有名字
(define (f x) (* x x))
; 无名字，直接传入
(define g (lambda (x) (* x x)))
(g 3)                 ; ==> 9
(map (lambda (x) (* x x)) '(1 2 3 4 5))   ; ==> (1 4 9 16 25)
```

`lambda` 的三个部分：**形参表 / 过程体 / 所在环境**。第三点决定闭包的语义，是 3.2 环境模型的核心。

### `let`：语法糖还是状态装置

```scheme
; let 本质是 lambda 应用
(let ((x 5) (y 6))
  (+ (* x y) (+ x y)))         ; ==> 41

; 等价展开（var 是 let 的语法糖，不是新语义）
((lambda (x y) (+ (* x y) (+ x y))) 5 6)

; let* 是嵌套 let：后面的绑定能看见前面的
(let* ((x 10) (y (+ x 5)))
  (* x y))                     ; ==> 150
```

> **本书的关键洞察**：`let` 与 `lambda` 在语义上完全等价。这个等式（`(let ((x v)) body)` ≡ `((lambda (x) body) v)`）是理解 3.1「局部状态」的钥匙——因为局部状态就是**一次 lambda 调用所创建的环境**。

### 柯里化与函数复合

```scheme
; 柯里化（currying）
(define (add-one x) (+ 1 x))
(define add-one-curried
  (lambda (x) (lambda (y) (+ x y))))
((add-one-curried 3) 4)        ; ==> 7

; 只固定一个参数的变体
(define (make-adder n) (lambda (x) (+ n x)))
(define add2 (make-adder 2))
(add2 5)                       ; ==> 7

; 复合
(define (compose f g)
  (lambda (x) (f (g x))))
((compose square add1) 3)      ; square(add1(3)) = 16
```

> `compose`/`make-adder` 就是 1.3.4 的「过程作为返回值」：它们返回的不是数据，而是**一颗尚未应用的计算**。这与现代 JS 的 `(x) => (y) => x + y`、Python 的 `functools.partial` 完全一致。

### 牛顿法统一为不动点

```scheme
; 不动点：找 x 使 f(x) = x
(define (fixed-point f first-guess)
  (define (close-enough? v1 v2)
    (< (abs (- v1 v2)) 0.00001))
  (define (try guess)
    (let ((next (f guess)))
      (if (close-enough? guess next)
          next
          (try next))))        ; try 在尾部 → 尾递归
  (try first-guess))

; 求平方根 = 求 x ↦ x/2 + a/(2x) 的不动点
(define (sqrt a)
  (fixed-point (lambda (x) (average x (/ a x))) 1.0))

(sqrt 2)   ; ==> 1.4142135...
```

### 平均阻尼：让迭代重新收敛

```scheme
; 不动点迭代可能振荡（如 x ↦ sin x + x 在 1 附近不收敛）
(define (average-damp f)
  (lambda (x) (average x (f x))))

(define (sqrt-damped a)
  (fixed-point (average-damp (lambda (x) (/ a x))) 1.0))

; 放缓因子：进一步压低步长
(define (slow-iter f slow first-guess)
  (define (try guess)
    (let ((next (- guess (* slow (- guess (f guess))))))
      (if (= guess next)
          next
          (slow-iter f slow next))))
  (try first-guess))
```

> **`average-damp` 是整个 SICP 抽象观的缩影**：它不关心你在求平方根还是解方程，只关心「把振荡的迭代平均一下」。这种「把算法拆成一个可替换的策略 + 一个通用引擎」的做法，就是 later 说的**策略与机制分离**。

### 用不动点统一求逆与求根

```scheme
; 求 f 的根：等价于求 x ↦ f(x) 的不动点（牛顿法版）
(define (newton-transform f)
  (lambda (x) (- x (/ (f x) ((deriv f) x)))))

(define (newton-solve f guess)
  (fixed-point (newton-transform f) guess))

; 求 y = 1/x 的倒数（练习）
(define (inverse x)
  (newton-solve (lambda (y) (- (* x y) 1)) 1.0))
```

> 至此 1.1 的 `sqrt`、1.3 的 `fixed-point`、1.3 的 `newton-solve` 是**同一个模式的三层抽象**——这正是本书要教的东西：**先抽象，再实例化**。

## 版本演进

| 阶段 | 演进要点 |
| --- | --- |
| **lambda 演算（Church 1936）** | 纯函数式，无柯里化语法但有 currying 语义；SICP 1.3 是它的一次「工程化落地」 |
| **LISP 1.5** | `lambda` 存在但**匿名函数难复用**，实践中普遍先 `define` 再传参；`funcall`/`apply` 才出现 |
| **Scheme 1975** | `lambda` 成为一等公民，词法作用域让闭包真正可用；1.3 节得以成立 |
| **Common Lisp** | 引入 `#'(lambda ...)` 与 `funcall`/`apply`，柯里化需手写；强调宏而非高阶函数 |
| **R5RS (1998)** | `(lambda (args) body)` 语法定型；`let`/`let*`/`letrec` 三件套明确区分 |
| **现代多语言（2026）** | **高阶函数成为主流语法**：JS 箭头函数、Python 的 `lambda`/`functools.partial`、Java 的 lambda（函数式接口）、C++ 的 lambda 表达式（C++11 起）；cooperative：JS 的 `Array.prototype.map/filter/reduce` 已是标准 |
| **2026 的趋势** | 静态类型 + 高阶函数正在和解：Scala 3、Kotlin、TypeScript 都补上了类型化的高阶函数签名；同时「不可变数据 + 高阶函数」成为并发安全的主流范式（见 10 章的流） |

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **方言差异** | 1.3 的 `(define (sum term a next b) ...)` 与 R5RS 完全兼容，但 `let` 缺 `letrec` 的严格写法、`define` 的内部定义在不同实现里可见性有差别，迁移到 Racket 时需微调 |
| 🔧 **「高阶函数一定更强」的误解** | 1.3 只呈现了高阶函数的优点，C/Go 的反例说明**抽象成本要被记账**：每次回调都有分配与内联损失 |
| **把 `lambda` 当成 `let` 的替代品** | 二者等价但**意图不同**：`lambda` 表达「一次性函数」，`let` 表达「一次绑定 + 局部作用域」；混用会让代码可读性下降 |
| 🔧 **不动点不收敛的处理缺失** | 1.3.3 里 `fixed-point` 默认一定能收敛；现实中的振荡需要 damping/放缓，本书只在练习里提，容易被读者忽略 |
| **练习 1.34 的「返回过程的过程」陷阱** | `(define (f g) (g 2))` 当 `g` 本身是过程时语义会漂移；这是本书著名的「参数遮蔽过程名」陷阱，中文版无注释，建议自行验证 |
| 🔧 **1996 年性能前提** | 高阶过程在当年的解释器里是「分配闭包」的昂贵操作；2026 年的 JIT（如 Chez、V8、HotSpot）会内联掉大部分，性能直觉需要重标定 |
| **未引入类型** | 1.3 的 `sum`/`compose` 完全没有类型标注；Typed Racket 可以给 `(compose f g)` 一个精确的签名——**抽象屏障从约定变成检查** |
