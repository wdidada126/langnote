# 第 3 章 模块化、对象和状态（3.5 流与惰性求值）

> **一句话**：流把「时间」从数据模型里删掉——**一串无穷的序列可以像列表一样被逐步消费**，因为「还没算」和「算完了」在类型上长得一样。

## 核心精讲

> 教学示意，**不参与构建、不编译**。

### 延迟序列：从有限列表到无穷流

```scheme
; 引入 delay/force/stream-car/stream-cdr
(define-syntax-rule (delay exp) (cons 'function (lambda () exp)))
(define (force promise)
  (cond ((eq? (car promise) 'function)
         (let ((result ((cdr promise))))
           (set-car! promise 'memoized)
           (set-cdr! promise result)
           result))
        ((eq? (car promise) 'memoized) (cdr promise))
        (else (error "not a promise"))))

; 惰性表：cons 的延迟版
(define (cons-stream a b) (cons a (delay b)))
(define (stream-car s) (car s))
(define (stream-cdr s) (force (cdr s)))

; 整数的无穷流
(define (integers-starting-from n)
  (cons-stream n (integers-starting-from (+ n 1))))
(define integers (integers-starting-from 1))

; 取前 5 个：不必「算完」整个流
(define (stream-ref s n)
  (if (= n 0) (stream-car s) (stream-ref (stream-cdr s) (- n 1))))
(define (stream-map proc s)
  (cons-stream (proc (stream-car s))
               (stream-map proc (stream-cdr s))))
(define (stream-filter pred s)
  (cond ((pred (stream-car s))
         (cons-stream (stream-car s) (stream-filter pred (stream-cdr s))))
        (else (stream-filter pred (stream-cdr s)))))

(stream-ref integers 99)                                 ; ==> 100
(stream-ref (stream-filter prime? integers) 20)          ; 第 21 个素数
```

> 这里的 `(integers-starting-from 1)` **没有终止条件却能被部分消费**——因为 `(delay ...)` 只是「记下要做的事」，不立即做。

### 惰性求值带来的模块化

```scheme
; 两个互相依赖的量，用约束/流表达就没有顺序问题
(define (sqrt-stream x)
  (define guesses
    (cons-stream 1.0
                 (stream-map (lambda (guess)
                               (average guess (/ x guess)))
                             guesses)))
  guesses)

(stream-ref (sqrt-stream 2) 4)   ; ==> 约 1.41421
```

> `(define guesses (cons-stream 1.0 (stream-map ... guesses)))` 中 `guesses` 在被定义时**还没算出来**，却仍然被引用——这在及早求值里是不可写的（无限递归）。
> 这就是 3.5 的核心论点：**求值时机决定了你能不能模块化**。

### 记忆化：把树形递归变回线性

```scheme
; 不记忆化的斐波那契：树形
(define (fib n)
  (cond ((< n 2) n)
        (else (+ (fib (- n 1)) (fib (- n 2))))))

; 记忆化的斐波那契：线性
(define (memo-fib n)
  (let ((memo '()))
    (define (lookup x)
      (cond ((null? memo) #f)
            ((= (car (car memo)) x) (cadr (car memo)))
            (else (lookup x (cdr memo)))))
    (define (fib-iter x)
      (let ((found (lookup x)))
        (cond ((< x 2) x)
              (found found)
              (else
               (let ((result (+ (fib-iter (- x 1)) (fib-iter (- x 2)))))
                 (set! memo (cons (list x result) memo))
                 result)))))
    (fib-iter n)))

(memo-fib 50)   ; 立即返回，而朴素版要跑很久
```

> 用 `delay` + 记忆化的版本（`memo-delay`）只需把 `(delay exp)` 换成 `(memo-delay exp)`，`fib` 就自动从 θ(φⁿ) 降到 θ(n)。**这是惰性求值最直接的价值**：不用改算法就能消掉重复子问题。

### 流形式的 `accumulate` 与反馈循环

```scheme
; 用流表达「累加到给定次数」
(define (stream-take s n)
  (if (= n 0) '() (cons (stream-car s) (stream-take (stream-cdr s) (- n 1)))))

(stream-take (stream-filter prime? integers) 5)   ; ==> (2 3 5 7 11)
```

> 反馈循环（练习 3.63–3.66）是本章最难的部分：把 `(define (sqrt x) ...)` 改写成**显式输出流**的形式，再用 `stream-map` 把「一步迭代」叠加到自身上，形成自引用的信号流图。
> 信号流图的思想最终汇入 2020 年代的**响应式编程（RxJS、ReactiveX）与 streaming 处理**。

## 版本演进

| 阶段 | 要点 |
| --- | --- |
| **1960 LISP** | 只有及早求值；惰性求值要靠 `macro` 手工实现 |
| **1974 惰性求值的提出** | Wadler 等人的 **PAL / LISP 的惰性列表**；SICP 3.5 的 `delay/force` 是其教学简化版 |
| **1980s** | Haskell 采用**默认惰性求值**，成为纯粹函数式语言的标志 |
| **1998 R5RS** | `(delay ...)`/`(force ...)`/`promise?` 进入标准；`delay` 的语义被明确为「只求值一次」 |
| **2007 R6RS / Racket** | Racket 提供 `delay`/`force` 与 `lazy`；同时提供**显式 delimited continuation** 让惰性可控 |
| **2010s JavaScript 生成器** | 生成器（`yield`）成为惰性的**命令式**写法，JS 生态大量使用 |
| **2015 Python generator** | 生成器表达式 `(x for x in ...)` 是惰性的平民版 |
| **2020 React Hooks / RxJS** | 响应式与流处理进入前端主流；Python 的异步生成器把「流」变成一等公民 |
| **2026 趋势** | **默认求值的 Rust/Swift 用 `Iterator`（惰性）而非 `lazy` 变量**；「惰性」在主流语言里以**迭代器协议**形式存在，`collect()` 才触发计算 |

> **1996 → 2026**：SICP 的 `delay/force` 今天对应 Python 生成器、JS 迭代器、Rust `Iterator`、Java Stream（拉式）。**惰性的名字换了，思想成了标准件**。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **副作用与 `set-car!`** | 3.5.2 的实现用 `set-car!`/`set-cdr!` 改写 promise；Scheme 的 `set-car!` 在 R6RS/Racket 里被废弃（改用 box），迁移时需替换 |
| 🔧 **「惰性求值 = 更省内存」的误解** | 惰性可能**更耗内存**：未求值的 thunk 会堆积（`memoize` 出错时尤其严重）；空间开销是惰性的真实代价 |
| 🔧 **惰性求值不保证顺序** | 本书没有强调惰性求值下**求值顺序与副作用顺序脱钩**；对于有副作用的程序，惰性求值会破坏可推理性 |
| **练习 3.63–3.66 难度陡增** | 反馈循环（自引用流 + `stream-map`）是全书最难的四道练习，中文版无提示；建议先理解 3.5.5 的 `sqrt-stream` 自引用写法，再上反馈 |
| 🔧 **1996 年性能前提** | 本书对「惰性求值开销」的讨论基于当时解释器的 thunk 分配成本；2026 年的 JIT 会内联掉一部分，但**惰性数据结构的缓存局部性通常更差** |
| **未区分拉式与推式** | 3.5 的流是**拉式**（pull）；2020 年代的流处理更多是**推式**（push）与背压（backpressure）。两者统一在「流」这个词下，容易混淆 |
| **缺少与约束传播的关联说明** | 3.5 与 3.3 是同一思想的两个方向（约束传播是拉式，流是推式）；本书未点破，导致两章读起来割裂 |
