## 核心精讲

> 教学示意，**不参与构建、不编译**。

### 元循环求值器的骨架

```scheme
(define (eval exp env)
  (cond ((self-evaluating? exp) exp)
        ((quoted? exp) (text-of-quotation exp))
        ((variable? exp) (lookup-variable-value exp env))
        ((assignment? exp) (eval-assignment exp env))
        ((definition? exp) (eval-definition exp env))
        ((lambda? exp) (make-procedure (lambda-parameters exp)
                                       (lambda-body exp)
                                       env))
        ((if? exp) (eval-if exp env))
        ((cond? exp) (eval (cond->if exp) env))
        ((and? exp) (eval-and exp env))
        ((or? exp) (eval-or exp env))
        ((let? exp) (eval (let->combination exp) env))
        ((application? exp)
         (apply (eval (operator exp) env)
                (list-values (operands exp) env)))
        (else (error "Unknown expression type -- EVAL" exp))))

(define (apply procedure arguments)
  (cond ((primitive-procedure? procedure)
         (apply-primitive-procedure procedure arguments))
        ((compound-procedure? procedure)
         (eval-sequence
           (procedure-body procedure)
           (extend-environment
             (procedure-parameters procedure)
             arguments
             (procedure-environment procedure))))
        ((lambda-expression? procedure)
         (apply (make-procedure (lambda-parameters procedure)
                                (lambda-body procedure)
                                (procedure-environment procedure))
                arguments))
        (else (error "Unknown procedure type -- APPLY" procedure))))
```

> **这段代码是整个计算机科学里最著名的 40 行**。它同时做到了三件事：
> 1. 证明「解释器」这个概念本身可以用几页代码讲清；
> 2. 说明「一门语言 = 一组表达式 + 一组求值规则」；
> 3. 为第 5 章埋下伏笔——把 `eval` 的递归结构拆成显式的机器指令，就得到了编译器。

### 环境的结构

```scheme
; 环境 = 帧的链；帧 = 名字列表 + 值列表
(define (make-frame variables values)
  (cons variables values))
(define (frame-variables frame) (car frame))
(define (frame-values frame) (cdr frame))

(define (make-environment) '())
(define (extend-environment vars vals base-env)
  (cons (make-frame vars vals) base-env))

(define (lookup-variable-value var env)
  (define (lookup-in-frame var frame)
    (cond ((null? frame) #f)
          ((eq? var (frame-variables frame)) (car (frame-values frame)))
          (else (lookup-in-frame var (cdr frame)))))
  (cond ((eq? env '()) (error "Unbound variable" var))
        ((lookup-in-frame var (car env))
         (lookup-in-frame var (car env)))
        (else (lookup-variable-value var (cdr env)))))
```

> 3.2 说的「环境是帧的链」，在这里拿到了实现。`lookup-variable-value` 的递归向下遍历，就是 **SICP 里第一次看到「控制递归的显形」**。

### 尾递归与「显式控制」的动机

```scheme
; 4.1 的 eval 是尾递归的：解释了「尾位置」在解释器里的位置
(define (eval-if exp env)
  (if (true? (eval (if-predicate exp) env))
      (eval (if-consequent exp) env)
      (eval (if-alternative exp) env)))
; ↑ 为什么 eval-if 不占栈？因为 eval 的自调用都在尾部
```

> 这一段之后，SICP 在第 5 章用**寄存器机**重画同一棵递归树。理解 4.1 与 5.4 的关系，靠的就是这句话：**解释器的递归就是机器的跳转**。

### 语法分析：解析与分派

```scheme
; 语法分析不做语义，只做「形状检查」
(define (self-evaluating? exp)
  (cond ((number? exp) #t)
        ((string? exp) #t)
        (else #f)))

(define (quoted? exp) (tagged-list? exp 'quote))
(define (tagged-list? exp tag)
  (and (pair? exp) (eq? (car exp) tag)))

; 语法变形：把糖展开成内核
(define (cond->if exp)
  (expand-clauses (cond-clauses exp)))
(define (expand-clauses clauses)
  (if (null? clauses) #f
      (let ((first (car clauses)) (rest (cdr clauses)))
        (if (eq? (cond-predicate first) 'else)
            (cond-consequent first)
            (make-if (cond-predicate first)
                     (cond-consequent first)
                     (expand-clauses rest))))))
```

> 4.3 的方法是：**先把源程序变形（desugar），再解释内核形式**。今天每个主流编译器都实施同一策略——AST →  lowering → IR。

### 延迟求值的语法变形

```scheme
; 4.2：把惰性求值实现为语法变形
(define (delay->thunk exp)
  (list 'function (list 'lambda '() exp)))

; 或者作为求值器的一个特殊形式
(define (eval-delay exp env)
  (list 'promise (cons 'env env) (cadr exp)))
```

> 差别在于「变形发生在解析时还是解释时」——4.3 给出的答案倾向前者：**把语言扩展实现为语法扩展，能复用已有的求值器**。这正是宏系统（Common Lisp macro、Racket macro）的价值。

## 版本演进

| 阶段 | 要点 |
| --- | --- |
| **1960** | McCarthy 的 `METALISP`：LISP 解释 LISP，`eval` 的第一次出现 |
| **1962** | `LISP 1.5` 的 `eval` 约一页纸，成为「元循环」的原型 |
| **1975 Scheme** | 简化为 `eval`/`apply` 两个互递归函数；环境模型确立 |
| **1982 AI Memo 505** | 「解释器即抽象机器」的连续谱：求值器 → 非确定性 → 约束传播 → 编译器 |
| **1996 SICP 第 2 版** | 用 4.1 的完整代码 + 4.3 的语法分析构成教学版求值器 |
| **1998 R5RS / 2007 R6RS** | `eval` 的语义被精确化（环境作为参数 vs 全局环境） |
| **2010s Racket** | `syntax-case` / `syntax-parse` 提供带**语法位置信息**的语法对象；`compile` 与 `eval` 分离 |
| **2020s** | **编译器即服务**：LLVM、WASM、`cranelift` 把「语言实现」变成可组合的库；同时 JVM/JS 引擎把「解释器 → JIT」优化到极致 |
| **2026 趋势** | 语言实现的主流形态：Rust 写前端 + LLVM/WASM 写后端；**SICP 第 4 章那段 `eval` 依然是理解这一切的最短路径** |

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **4.1 的 `cond`/`let` 变形非标准** | 本书用 `cond->if`/`let->combination` 做语法变形；这些变形函数不在 R5RS 标准里，迁移到 Racket 时需要自行实现或改用 `match` |
| 🔧 **`apply` 的参数表处理** | 4.1 的 `(list-values operands env)` 是本书自造的函数；标准写法是 `(map (lambda (x) (eval x env)) operands)` |
| **把 `eval` 当安全函数** | 4.1 的 `eval` 可以在任意环境求值任意表达式；2000 年代因为误用 `eval` 造成大量安全漏洞（如 eval-injection）。今天 `eval` 在多数语言里被标记为不安全 API |
| 🔧 **1996 年的性能表述** | 4.1 强调「解释器的开销是每次都走一遍分派」；2026 年的 JIT 会把热路径内联，**同样的 eval 结构性能可差百倍** |
| **缺少错误恢复与栈限制** | 4.1 的代码遇到未绑定变量直接 `error`；生产级解释器需要可控的栈深度与错误信息（如 Racket 的 `continuation` 与限深） |
| 🔧 **未区分解释与编译的分界** | 4.3 只说「先变形再解释」；2026 年的实践是「先变形 → 检查信息（携带位置/类型）→ 生成 IR」。Racket 的 syntax object 补上了缺失的一环 |
| **练习缺口** | 4.1 的练习 4.8（`cond` 的多个 `else`）与 4.2 的惰性求值改造，在中文版无提示；建议对照题解仓库 |
