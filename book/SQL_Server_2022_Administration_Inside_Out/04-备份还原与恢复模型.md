## 一、恢复模型：把 RPO 写成合同

- SIMPLE：日志在检查点后复用、**无日志备份能力**，恢复到最近备份——小库/DEV 的默认 ⚠️。
- FULL：完整日志链，支持时点恢复（STOP AT）——生产标准 ⚠️；BULK_LOGGED：Bulk 操作最小日志换体积，链完整性代价是"日志备份期间不可 Bulk"窗口纪律 ⚠️。
- 三种模型对应三种"重放剧本"：崩溃恢复 ARIES 式 REDO/UNDO 的机理在 [../SQL_Server_2012_Internals/03-日志与恢复.md](../SQL_Server_2012_Internals/03-日志与恢复.md)；本章只管"合同怎么签"。
- 🔧 跨引擎注：SIMPLE≈"日志不保值"，与 SQLite `journal_mode=delete`（提交即截断）同构；FULL≈`wal` 长驻追加+外部归档——E6 谱系（见 [03-数据库存储与文件组管理.md](03-数据库存储与文件组管理.md)）在本章兑现。

## 二、备份类型矩阵与链代数

- 全量（FULL）→ 差异（DIFF，基于最近全量的变化图）→ 日志（LOG，延续 LSN 链）⚠️；恢复顺序=1 全 + 1 最晚所需差异 + 一串日志，任何一环断裂（改恢复模型/未备份日志截断）都会让链失效 ⚠️。
- "日志链断裂"三大元凶 ⚠️ 转述：备份间隙把 FULL 改 SIMPLE 又改回；`BACKUP LOG WITH TRUNCATE_ONLY` 时代遗产（已废）；复制/镜像类操作隐式截断。msdb 里有"是否被截断"的诊断列可查 ⚠️。
- 文件/文件组备份：大历史库（readonly FG 一次备份）+ 增量只盯活跃 FG，把窗口从"整库"缩到"活跃切片" ⚠️，接 03 章只读红利。
- 压缩与加密：备份压缩（算法随版演进）与 `WITH ENCRYPTION`（证书/非对称密钥保护）⚠️——加密备份的密钥备份**必须**独立于备份文件存放，否则"锁和钥匙同箱"。
- 备份设备（Backup Device）：磁盘/URL/磁带逻辑名与镜像集 ⚠️ ✅ 官方设备页 https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/backup-devices-sql-server。
- 到 URL（Azure Blob）的备份出海口：2017+ GA 路线，SAS 凭证管理是运维要点 ⚠️（backup-to-url 专页当前不可达 404，以设备页内链与 What's new 页为准绳 ⚠️）。

## 三、还原剧本与窗口工程

- 还原语义三档 ⚠️：`WITH RECOVERY`（开门营业）/ `NORECOVERY`（链未完，等着续日志）/ `STANDBY`（可读备用，undo 文件当后悔药）——AG 种子与日志传送都拼这三档。
- 时点恢复（STOP AT / STOP AT MARK）：先全后差再日志逐步 NORECOVERY，最后一段用 STOP AT 收尾；标记载点（MARK）给应用事务打时间戳，是"回滚到发版前"的工程化写法 ⚠️。
- 单页恢复（PAGE RESTORE）：坏页局部手术，前提 FULL 链完整 ⚠️——对应 05 章：副本能当"备用的备用"。
- 迁移式还原：`WITH MOVE` 重排文件路径，是 01 章并行迁移路线的落地招式 ⚠️。
- 还原演练制度 ⚠️（管理册纪律）：**没演练过的备份等于没有备份**——定期把生产备份还原到隔离实例、CHECKDB、抽验业务查询，结果归档 msdb 之外单独台账。

## 四、DBCC CHECKDB：一致性审计的日常化

- 官方语义：检查逻辑+物理完整性，`PHYSICAL_ONLY` 轻量档与 `ALL_ERRORMSGS` 全披露 ⚠️ ✅ https://learn.microsoft.com/en-us/sql/t-sql/database-console-commands/dbcc-checkdb-transact-sql
- 节奏处方 ⚠️ 转述：大库周级全检+每日 PHYSICAL_ONLY；CHECKDB 开销≈一次全扫，容量与 IO 预算先算再排班（接 02 章内存/卷规划）。
- 检出损坏后的剧本分级 ⚠️：`REPAIR_REBUILD`（可接受停机内的结构重建）vs `REPAIR_ALLOW_DATA_LOSS`（最后手段，可能丢页）vs "还原+日志链"（数据损失最小，窗口最长）——三选一前先问业务 RPO/RTO。
- 🔧 **实验 E5（SQLite 3.45.3，非本书引擎行为）**：`PRAGMA integrity_check` → `('ok',)`——单命令全库页级一致性审计的开源同构；SQL Server 侧的 DBCC CHECKDB 承担相同角色但输出错误矩阵。仅通用机制演示。

## 五、🔧 WAL 双子实验（E1/E2，SQLite 3.45.3，非本书引擎行为）

- **E1 日志形态与并发**：`PRAGMA journal_mode=wal` 返回 `('wal',)`；主库 4096B 旁挂 `-wal` 12392B + `-shm` 32768B——"主文件+追加日志+共享内存索引"三件套与 SQL Server 的 mdf/ldf/（缓冲池）形态同构；写事务未提交期间，另一连接读取仍见已提交 200 行、提交后见 201 行（快照语义）；第二个写者立刻 `database is locked`（WAL 不解决写写互斥）。
- **E2 检查点与截断**：2000 行提交后 `-wal` 长到 49472B；`PRAGMA wal_checkpoint(PASSIVE)` 返回 `(0,12,12)` 且文件**不缩短**（页已回写主库、空间待复用）；`wal_checkpoint(TRUNCATE)` 返回 `(0,0,0)`，`-wal` 归 0 字节；`wal_autocheckpoint` 默认 1000 页触发。
- 类比管理概念：PASSIVE/TRUNCATE ≈ SQL Server 的"检查点把脏页刷盘"与"日志备份后 VLF 复用"两步——**日志文件逻辑截断≠物理收缩**，这条认知直接迁移到"ldf 很大能不能 SHRINK"的经典争论（答案默认是不能轻率 ⚠️）。
- **E5 前半（在线备份）**：`VACUUM INTO 'e5snap.db'` 产出 8192B 独立快照，期间原库可继续写；快照后主库再插 1 行，快照内仍只见 1 行——一致性快照点（backup LSN 语义）的开源同构：FULL BACKUP 同样是"某一 LSN 的成像"。

## 七、常见坑清单（⚠️ 转述整理，非原书条文）

1. **改回 FULL 不补全量**：SIMPLE→FULL 后日志链从新全量起算，中间无锚点 ⚠️。
2. **日志备份作业停摆一夜**：链断在无人知晓处，时点恢复只剩"昨天那个全量" ⚠️。
3. **证书私钥与备份同箱**：DR 现场"备份都在、钥匙没了" ⚠️（密钥台账回 07 章）。
4. **CHECKDB 只跑 PHYSICAL_ONLY 却报"一致性 OK"**：逻辑损坏漏检，报告口径要写明档位 ⚠️。
5. **STANDBY 副本 undo 文件放共享盘单点**：备用可读变备用不可用 ⚠️。
6. **把差异备份当增量**：DIFF 基于最近 FULL 不是基于上次 DIFF，取错文件还原出"时光倒流" ⚠️。
7. **缩小 ldf 后不重建日志备份节奏**：VLF 碎片回归，两章联动知识 ⚠️。

## 八、实操速查卡（⚠️ 示意语法，参数以官方文档 ✅ backup-devices 域为准）

```sql
BACKUP DATABASE Sales TO DISK='Z:\Sales_full.bak' WITH COMPRESSION, CHECKSUM, STATS=5;
BACKUP LOG Sales TO URL='https://store.blob.core.chinacloudapi.cn/container/...' WITH CREDENTIAL='mycred';
RESTORE DATABASE Sales FROM DISK='Z:\Sales_full.bak' WITH NORECOVERY;
RESTORE LOG Sales FROM ... WITH STOPAT='2026-01-01T18:00:00', RECOVERY;
DBCC CHECKDB ('Sales') WITH ALL_ERRORMSGS, PHYSICAL_ONLY;  -- 轻量档
```

- 链完整性快查：`RESTORE HEADERONLY/VERIFYONLY` 两兄弟——HEADERONLY 看 LSN 序列能否续接，VERIFYONLY 验证介质可读+结构合法 ⚠️。

## 十、复现与延伸（可选自修）

- 🔧 复现 E1/E2（SQLite 3.45.3，非本书引擎行为）：`journal_mode=wal` → 批量 INSERT 后看 `-wal` 尺寸 → `wal_checkpoint(PASSIVE)` 与 `wal_checkpoint(TRUNCATE)` 各跑一次，对比返回值三元组 `(busy, log, checkpointed)` 与文件字节；结论亲手验证"截断≠收缩"。

## 核心概念速览（中英对照）

- **恢复模型** — Recovery Model：FULL/SIMPLE/BULK_LOGGED 三剧本，决定日志链可恢复性。
- **日志备份链** — Log Chain：以 LSN 续接的增量序列，断裂即失时点能力。
- **差异备份** — Differential Backup：相对最近全量的页位图切片。
- **文件组备份** — Filegroup Backup：大库按活跃/历史切片压缩窗口。
- **备份设备** — Backup Device：磁盘/URL/磁带的逻辑命名与镜像集。
- **NORECOVERY/STANDBY** — 还原状态三档：续链与可读备用的开关组合。
- **时点恢复** — Point-in-Time Recovery (STOP AT)：把库回滚到日志链内任意时刻。
- **标记事务** — Marked Transaction：给日志链打业务书签，实现"回滚到发版前"。
- **页还原** — Page Restore：坏页局部手术，FULL 链完整为前提。
- **DBCC CHECKDB** — 一致性审计：逻辑+物理完整性的全库体检。
- **检查点** — Checkpoint：脏页刷盘节拍，SIMPLE 下的日志复用触发器。
- **VLF** — Virtual Log File：日志内部分段，收缩与碎片的当事方。
- **wal_checkpoint** — SQLite 检查点（🔧E2）：PASSIVE 回写不截断 / TRUNCATE 归零，日志截断≠物理收缩的同构演示。
- **VACUUM INTO** — SQLite 在线快照（🔧E5）：不冻结写入的一致性成像点类比。
