# 第 15 章 JUnit 内幕与重构 SerialDate（第 15、16 章合读）

> **一句话**：上一章把 `SerialDate` 改到「能接受了」，这一章继续改到「像样」——**同时借 JUnit 的内部结构，演示「好框架长什么样」**。

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：先跑起来，再改对（15.1 / 15.2）。

```text
# 教学示意，不参与构建：典型的改进节奏（每一步都能提交）
第 1 步  加测试，跑绿            —— 只加不删
第 2 步  改一个含糊的名字         —— 低风险、高回报
第 3 步  提取一个方法             —— 测试仍然是绿的
第 4 步  把魔法数字收成常量       —— 测试仍然是绿的
第 5 步  拆一个小类出来           —— 最高风险，留到最后
```

示例二：改进前后对照（15.5）。

| 项目 | 原始 | 第二轮 | 第三轮（最终形态） |
| --- | --- | --- | --- |
| 方法数 | 十几个混杂方法 | 方法变小、变专 | 每方法只做一件事 |
| 最长方法 | 数十行 | 十几行 | 个位数 |
| 参数个数 | 常带 3–5 个 | 收敛到 2 个左右 | 1–2 个，必要时收成参数对象 |
| 抽象层级 | 混杂 | 分层 | 一层到底，自顶向下可读 |
| 名字 | `getXxx()` 系列 | 用领域语言命名 | 名字即文档 |

示例三：JUnit 内幕给设计师的启发（15.3）。

| JUnit 设计点 | 对普通代码的启发 |
| --- | --- |
| 测试类与测试方法是「公开的一等公民」 | 别用私有方法藏测试逻辑 |
| `setUp`/`tearDown` 把夹具标准化 | 资源的获取与释放要集中、对称 |
| `assertXxx` 提供更强的失败信息 | 断言要给出可读的失败原因 |
| 测试失败不会互相污染 | 测试之间要独立（见 `09-单元测试.md`） |
| 框架本身没有「上帝类」 | 框架代码同样遵守 `10-类.md` 的 SRP |

示例四：什么时候该停（16.2）——一份可执行的「干净判据」。

| 判据 | 通过标准 |
| --- | --- |
| 每个方法是否只做一件事？ | 是 |
| 名字能否念出来、能否搜到？ | 是 |
| 有没有重复的逻辑？ | 无 |
| 有没有魔法数字与死代码？ | 无 |
| 测试是否已覆盖行为？ | 是 |
| 新成员读它时能否一次读懂？ | 是 |

当这五项都满足时，就可以停了——**再往后改，收益开始为负**。

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1998 | `SerialDate` 的原始实现（jFreeChart） |
| 2002 | JUnit 3 的 `setUp`/`testXxx` 约定成为事实标准 |
| 2006 | JUnit 4 引入注解，JUnit 内部的类结构随之变化 |
| 2008 | 第 15、16 章出版，用的是 JUnit 3/早期 4 的内部结构 |
| 2012 | JUnit 4.10 之后 `Assert` 类的静态方法重构，内部组织进一步变化 |
| 2014 | JUnit 5（Jupiter）的开发启动（2017 年释放），断言 API 明显变化 |
| 2017 | JUnit 5 正式发布；`org.junit.Assert` 的用法在社区快速更新 |
| 2020s | 参数化测试与「测试模板」成熟，本章提到的「重复测试代码」问题被框架接受 |
| 2023–2026 | 测试框架继续向「可生成、可组合」演进；AI 生成的测试大量复用本章主张的结构 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **把 JUnit 3 时代的内部结构当经典** | 本章讲的 `setUp`/`TestSuite` 今天已换成 JUnit 5 的 `@BeforeEach`/`@Nested` | 读它的**设计思想**（夹具标准化、断言可读），别照抄类名 |
| 2 | 🔧 **「再改一轮」被理解成可以无限改** | 本章没给停下来的判据，容易陷入无止境的重构 | 用上面那份「干净判据」作为终点 |
| 3 | 🔧 **对「重构顺序」的描述偏理想** | 现实中会被需求、他人分支、deadline 打断 | 每步留出可提交边界；改到一半先提交到分支 |
| 4 | 🔧 **Java 断言 API 已变** | `assertEquals` 精确签名与 JUnit 5 不同 | 按现代 API 重写示例，不要照抄 |
| 5 | 🔧 **AI 时代「让它跑起来」这一步被自动化** | LLM 可直接改代码，但仍需人确认「行为没变」 | 用 characterization test 守住行为，再谈改进 |
| 6 | **案例只有一份，缺少反例** | 只有「越改越好」的单向叙事 | 同时读 `00-总览与阅读地图.md` 第 4 节的缺口清单，了解本书没讲的部分 |
