# 第 5 章 格式

> **一句话**：格式不决定程序对不对，却决定了**团队每分钟读代码的体验**；既然没人真的会去写《代码排版规范》，那就**让机器来统一**。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 格式的原因 | 代码今天写、Tomorrow 维护；格式影响可读性、可维护性与工作效率 | 格式是**经济问题**，不是审美问题 |
| 5.2 垂直格式 | 源文件应该像报纸：标题（类）→ 导语（static/public 常量）→ 正文；类内部按「静态变量 → 实例变量 → 方法」；函数间留空行；逻辑相关的行相邻，无关的行隔开 | 行数越少层次越浅；空行是「段落标记」 |
| 5.3 水平格式 | 一行代码的宽度：用空格把「运算符与操作数」分开、把「函数与其参数」分开；缩进体现块结构；括号风格 | 别超过 120 列（团队自定）；空格是「把相关词绑在一起」的手段 |
| 5.4 团队规则 | 一份团队范围内的格式约定；关键在「让所有代码看起来出自同一人之手」 | 规则本身不重要，**一致**才重要 |
| 5.5 关于「格式可以交给工具」 | 作者承认，理想状态是把格式规则自动化 | 现代工程实践正是这么走的 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：垂直格式——用空行划分层次，这是本章最有可操作性的一条。

```python
# 教学示意，不参与构建：反例 —— 所有内容挤在一起，层次靠空行也看不出来
class Order:
    MAX_RETRY=3
    def __init__(self, customer_id):
        self.customer_id=customer_id
        self.lines=[]
    def add(self,sku,count):
        if count<=0: raise ValueError("count must be positive")
        self.lines.append(Line(sku,count))

# 正例：类内部按「常量 → 状态 → 构造 → 行为」排布，段落之间留空行
class Order:
    MAX_RETRY = 3

    def __init__(self, customer_id: str):
        self.customer_id = customer_id
        self.lines: list[Line] = []

    def add(self, sku: str, count: int) -> None:
        if count <= 0:
            raise ValueError("count must be positive")
        self.lines.append(Line(sku, count))
```

示例二：水平格式——空格的作用是把「相关的东西绑紧、把无关的东西分开」。

```java
// 教学示意，不参与构建：反例 —— 相关词没绑紧，参数与函数名糊在一起
for(int i=0;i<list.size();i++){process(list.get(i));}

// 正例：关键字与操作数分开，缩进体现块
for (int i = 0; i < list.size(); i++) {
    process(list.get(i));
}
```

对照表（团队最容易统一的分项）：

| 项目 | 常见约定 | 建议 |
| --- | --- | --- |
| 行宽 | 80 / 100 / 120 | 100–120 较常见；硬折行靠 formatter 自动完成 |
| 缩进 | 2 / 4 空格 | 用空格不用 tab |
| 函数与函数之间 | 1 个空行 | 必选 |
| 变量声明与语句 | `int  x = 1;` 加空格 | 等号两侧都加 |
| `if` 与括号 | `if (cond)` | 关键字后留一个空格 |
| 类的成员顺序 | 静态 → 公有 → 私有 | 同一仓库内必须一致 |
| 文件长度 | 作者建议 500 行以内 | 超长通常说明职责过多（见 `10-类.md`） |

示例三：一份可直接执行的「团队格式规则」（本章 5.4 的落地形态）。

```yaml
# 教学示意，不参与构建：把 5.4 的「团队规则」写成配置
# pre-commit.yaml
repos:
  - repo: https://github.com/psf/black
    rev: stable
    args: ["--line-length=110"]
  - repo: https://github.com/pre-commit/mirrors-clang-format
    rev: v17.0.6
```

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1960s | FORTRAN / COBOL 的固定列格式，「代码有标准的长相」的起点 |
| 1970s | K&R 风格确立（`{` 紧跟 `if` 行尾），影响至今 |
| 1979 | Kernighan & Pike，*The UNIX Programming Environment* 强调一致性 |
| 1980s | 缩进风格之争（K&R vs Allman / GNU）成为宗教级争论 |
| 1990s | 一行的宽度：80 列成为默认；编辑器普遍支持自动缩进 |
| 1999 | Google 发布 Java 风格指南，「团队规则文档化」成为大型组织常态 |
| 2008 | 本章出版；同一年 Google Java Style 成为事实标准之一 |
| 2008 | Go 语言发布，自带 `gofmt`——**格式的裁决权首次交给工具** |
| 2013 | `clang-format` / `black`（2018）把「不可协商的格式」推向主流 |
| 2018 | `psf/black` 发布，「无需配置的格式化」成共识 |
| 2019 | Python 的 black、`golangci-lint`、Kotlin ktlint 陆续默认开启格式检查 |
| 2020s | 「prettier 一切」成为前端默认；格式争论基本消失 |

## 近年研究与工业界开源实践（2015–2026）

趋势：**格式的争议已经终结**。今天没人会在 review 里争论加不加空格——这部分的收益已被格式化器全部拿走，人类的评审精力转向上层问题。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `psf/black` | **41,851★** | 「合作式格式化」的代表：不给配置，只给结果 |
| `astral-sh/ruff` | **49,779★** | 现代版本的 `black` + lint 二合一，多语言覆盖面广 |
| `pre-commit/pre-commit` | **15,594★** | 团队格式规则的**实际载体** |
| `golang/go` | **138,994★** | `gofmt` 的维护者；自带格式化器是「格式即法律」的样板 |
| `swiftlang/swift` | **70,401★** | Swift 的编译期格式化建议与 `swift-format` 一并推动一致性 |
| `qodo-ai/pr-agent` | **13,146★** | 早期阶段做格式对齐，后期转向语义建议 |
| `github/codeql` | **10,122★** | 可检测超宽行、深层嵌套等格式类坏味道 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **把格式当成「人的纪律」来推行** | 书里强调团队规则，但没说怎么让 30 个人同时遵守 | 直接上 formatter + pre-commit，让规则不可协商 |
| 2 | 🔧 **对行宽的建议没有给出现代答案** | 作者列的规则偏 80 列时代的编辑器 | 按语言定 100–120；超宽处靠表达式换行而非硬折 |
| 3 | 🔧 **Java 的括号/缩进惯例对其他语言是错的** | Java 用 `if (x) {`，但 `case` 语句、switch 落块在 C++/JS 中的惯例不同 | 各语言跟随各自生态，不要跨语言照抄 |
| 4 | 🔧 **「类内部成员顺序」的说法与今天的写法有出入** | Java 的「公有先、私有后」与 Go 的「导出先、未导出后」在道理上一致，但具体项目更常用「按重要性而非可见性」排列 | 团队定一条，然后全程一致 |
| 5 | 🔧 **格式问题在 AI 时代反而回潮** | 不同 LLM 输出的缩进/命名/括号风格不同，混合代码里格式一致性会退化 | 强制「先跑 formatter 再提 PR」，把格式交给 black/ruff |
| 6 | **格式争论的消失让本章的说服价值下降** | 本章最有力的论点是「格式是经济问题」，但市场已经替它论证完了 | 把它当历史文献读，看它如何预言了 `gofmt`/`black` 的胜利 |
