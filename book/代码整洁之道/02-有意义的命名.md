# 第 2 章 有意义的命名

> **一句话**：名字是代码里最便宜的文档——**改一个名字的成本为零，代价是所有人一直读错**。命名不是风格问题，而是把「作者的意图」从脑子里搬到读者脑子里。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 2.2 名副其实 | 名字要说明「它做什么、存什么、返回什么」 | 看到名字就知道用途，才是好名字 |
| 2.3 避免误导 | 别用 `list`、`foo`、别拼错、别用有歧义的前后缀 | 错误的名字比没名字更糟 |
| 2.4 做有意义的区分 | `getActiveUser` vs `getUser` 不是区分；`airportCode` vs `airportName` 才是 | 区分的粒度在**语义**，不在字数 |
| 2.5 使用读得出来的名称 | 名字要能念出来（避免 `aixxxx`、`dataMatrix`） | 念不出来的名字说明概念本身没想清 |
| 2.6 使用可搜索的名称 | 常量用大写 + 长名；用 IDE 搜索要能找到全部用法 | 短名字只在作用域内极小时可接受 |
| 2.7 避免使用编码 | 匈牙利标记法、成员前缀 `m_`、`_foo`、`isXxx` 接口前缀 | 编码在IDE时代是噪音；例外：真需要区分的类型标记 |
| 2.8 避免思维映射 | 别让读者去查你的缩写词典 | 读者不该维护「作者专用缩写表」 |
| 2.9 类名 | 类名是名词短语（`Customer`、`AccountParser`），不应该是动词 | 方法名是动词短语 |
| 2.10 方法名 | 方法名是动词（`sendPayment`），getter 例外 | 同一个方法在不同类里应取同名（2.12 的每个概念一个词） |
| 2.11 别抖机灵 | 别用 `whack()`、`holyGrail()` | 机灵的名字牺牲了可搜索性与可解释性 |
| 2.12 每个概念对应一个词 | `fetch/retrieve/get` 只选一个并全程统一 | 术语一致性 > 局部表达力 |
| 2.13 别用双关语 | 同一个词别在两个概念上用 | 双关让搜索失效 |
| 2.14–2.15 领域名词 | 用解决方案领域名（计算机术语）或问题领域名（业务名） | 术语表（Ubiquitous Language，领域驱动设计里的统一语言）是命名的上游 |
| 2.16 添加有意义的语境 | 用类名、包/命名空间、静态工厂补语境 | 别靠注释补语境 |
| 2.17 不要添加无用的语境 | 别给每个类都加 `Application`、`Utility` 前缀 | 语境不足用容器补，语境不足不靠前缀 |
| 2.18 最后的话 | 「选名字是编程中最难的事之一」 | 难在对概念的理解，不在对词的搜索 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

反例一：名字不说明意图（书中 2.2 的经典反例）。

```java
// 教学示意，不参与构建：反例 —— 名字不说明意图
int theYear;   // 是日历年？财年？还是合同年？
int d;         // 是天？是日期？是数据？
String2 t;     // 是什么的 2？
```

正例：

```java
// 教学示意，不参与构建：正例 —— 名字即文档
int fiscalYear;            // 财年，读者一眼知道口径
Date subscriptionRenewal;  // 续订日期
String customerId;         // 明确是编码，不是对象
```

反例二：伪区分（2.4）与伪语境（2.17）。

```java
// 教学示意，不参与构建：伪区分 —— 两个名字只差一个词，语义边界不清
void getActiveUser();        // 与下面的区别是什么？
void getUser();              // 都取用户，那到底哪个被调用？

// 正例：把差异体现在语义上
User findEnabledAccount();   // 是「状态查询」
User loadUserById(Id id);    // 是「读取」
```

反例三：编码（2.7）——中译本批注最集中的一段。

```java
// 教学示意，不参与构建：反例 —— 匈牙利标记法 / 成员前缀 / 接口前缀
String mUserName;          // m_ 前缀：IDE 时代的信息量几乎为零
String sUserName;          // 类型编码
IFoo foo;                  // I 前缀：Java/C# 里接口与类的区分靠类型系统或惯例即可
```

正例（用类型系统与作用域表达同样的信息）：

```java
// 教学示意，不参与构建：正例 —— 让结构自己说话
class User {
    private final String name;   // 只读字段：final 已说明「不可变」
    public String name() { return name; }
}
```

反例四：可搜索性（2.6）——同一个概念在不同作用域用不同名字，搜索就失效。

```java
// 教学示意，不参与构建：搜 "e" 或 "tmp" 你会发现不了它们
long e;         // 毫秒级超时？错误码？纪元？
int tmp;        // 临时变量活不过 20 行，名字短点可以，但要能搜
```

一个可兜底的检查清单（可直接贴进 PR 模板）：

| 检查项 | 反例 | 正例 |
| --- | --- | --- |
| 名字是否被注释解释？ | `// 超时时间（毫秒） int t;` | `int timeoutMs;` |
| 名字是否只在局部作用域内存活？ | 类字段 `d`，全局 `int d` | 局部变量 `elapsedDays` |
| 同义词是否被混用？ | `get/fetch/retrieve` 混用 | 统一为 `load` |
| 名字是否念得出来？ | `genymdhms` | `generationDate` |
| 名字是否带编码？ | `m_arrItems`、`_private` | 靠作用域与访问修饰符 |

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1972 | Parnas，「On the Criteria To Be Used in Decomposing Systems into Modules」提出信息隐藏——命名的学术根源之一 |
| 1988 | Meyer 的 *Object-Oriented Software Construction* 把「每个概念一个名字」变成契约的一部分（Design by Contract 中的命名约定） |
| 1990s | 匈牙利标记法在微软体系内流行（Simonyi 的开创性讨论），Clean Code 明确反对 |
| 2008 | 本章出版，「Use Intention-Revealing Names」成为最常用的重构理由 |
| 2013 | 域名驱动设计流行（Evans 2003 原著后再次升温），「统一语言（Ubiquitous Language）」把命名从代码推向业务词汇表 |
| 2017 | *Clean Architecture* 强调「命名要能被业务方看懂」，反对工程师自造的技术黑话 |
| 2020s | 类型系统补位：`final`、`typed`、`newtype`/`type alias`、`enum class`，把不少命名义务转交给编译器 |
| 2023–2026 | 命名规范被 linter 强制（命名风格检查进入 `ruff`/`klint`/`golangci-lint` 默认规则），命名争议从「人评」变成「机评」 |

## 近年研究与工业界开源实践（2015–2026）

趋势：命名正在**两层分化**——机械层交给 linter/格式化器/类型系统，语义层交给域名词汇表与代码评审；与此同时，实证研究者开始测量「命名质量」对理解成本的影响。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `astral-sh/ruff` | **49,779★** | 内置命名风格规则（N 系列 pep8-naming），可直接卡住本章 2.7 的编码禁例 |
| `psf/black` | **41,851★** | 名字与格式都强制，减少评审中的主观争执 |
| `sonarsource/sonarqube` | **11,024★** | 「给标识符起个更有意义的名字」是它规则库里最常触发的条目之一 |
| `github/codeql` | **10,122★** | 语义查询可批量发现「同一概念多个名字」的术语不一致 |
| `qodo-ai/pr-agent` | **13,146★** | AI 评审里最常见的建议就是「把这个名字改得更表意」 |
| `swiftlang/swift` | **70,401★** | Swift 的 `API Design Guidelines` 是「方法名即文档」的现代范本 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **把「长名字」当成整洁的同义词** | 为了表意把变量写成 `theMaximumValueForTheOrderDiscountInCents`，可读性反而下降 | 「好名字恰好说明意图」，宁可拆短函数，不要堆长名 |
| 2 | 🔧 **对编码的反对过于绝对** | 匈牙利标记法在跨接口边界（COM、C++ 模板类型 `T_`、`pfn` 函数指针）里仍有信息量 | 按语言与场景判断：Go/Groovy 的 `b`、C++ 的 `p` 等前缀在类型晦暗处仍有用 |
| 3 | 🔧 **「每个概念对应一个词」只说了选一个词，没说怎么选** | 实践中更需要的是**词表 + 评审**，不是个人记忆 | 建立团队术语表，PR 里明确「新概念要进词表」 |
| 4 | 🔧 **几乎没谈非 ASCII / 中文命名的可搜性** | 中文注释 + 英文标识符是中文团队的常态，但书中没有相关讨论 | 标识符坚持英文，把解释放在术语表与注释 |
| 5 | 🔧 **AI 生成代码把命名问题放大** | Copilot/LLM 产出大量 `data1`、`result2` 之类名字，且不会主动改名 | 把命名纳入自动化检查，并在 PR 里强制 LLM 输出带名称说明 |
| 6 | **Java 示例带来跨语言误用** | 「类名用名词、方法名用动词」在 Go/Python 里不完全适用 | 结合语言惯例调整，别照抄 Java 风格规则 |

## 与其他章 / 其他书的联系

- 本章的「类名/方法名」直接决定 `10-类.md` 中「一个类只有一个职责」的可验证性：名字含糊通常意味着职责含糊。
- 「每个概念对应一个词」与 `03-函数.md` 的「动词与关键字」呼应：`03-函数.md` 3.6.7 要求参数名体现语义。
- 「避免编码」与 `05-格式.md` 的团队规则部分是同一件事的两面：**规则越依赖团队共识，越容易被 linter 接管**。
- 跨书：*Clean Architecture* 的「业务语言」章节补上本章缺失的上游（术语从哪来）；GoF 的 23 个模式名则是「已经想好的最高级命名」，看 `book/设计模式GoF/00-总览与阅读地图.md`。
- 语言侧：C++ 命名实践见 `book/C++代码整洁之道.md`（仓库既有大纲单文件），与本目录互链。
