# 第 11 章 系统

> **一句话**：**系统的价值不在「它做成了什么」，而在「它能不能持续被改」**——把构造与使用分开，把依赖注入进来，架构才有可演化性。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 11.1 系统的构造与使用分离 | 「main / 启动代码」负责创建所有对象；其余代码只接收它们 | 让「怎么组装」与「怎么用」互不干扰 |
| 11.2 工厂 | 复杂的构造过程交给工厂；工厂本身也是「构造逻辑」的一部分 | 别把构造逻辑散落在业务代码里 |
| 11.3 依赖注入（DI） | 构造器注入 / 参数注入 / 注入容器；本质是「别让对象自己 `new` 依赖」 | DI 让测试与替换成为可能 |
| 11.4 工厂的边界 | 工厂只在组装层出现，业务代码不该知道工厂存在 | 分层原则：谁负责组装 |
| 11.5 扩容（Scaling） | 系统要能从单进程扩到多进程/多线程；策略与机制分离 | 先把「能跑」，再谈「能扩」 |
| 11.6 无状态 | 无状态的部分可以被任意复制；有状态的部分是复杂度的来源 | 把状态集中管理，把逻辑写成无状态 |
| 11.7 AOP 与代理 | 横切关注点（日志、事务、权限）用代理/织入实现 | 别用复制粘贴实现横切 |
| 11.8 边界的测试 | 用测试确认「边界之间真的解耦了」 | 一个粗粒度集成测试即可，别动不动全E2E |
| 11.9 测试驱动的系统架构 | TDD 让「可测试性」成为架构约束 | 难测的系统，架构一定有问题 |
| 11.10 架构与设计的规则 | 单体里也可以有干净的架构；架构就是「改动的成本结构」 | 见 `12-迭进.md` 与 `00-总览与阅读地图.md` 第 4 节 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：构造与使用的分离（11.1 / 11.3）。

```python
# 教学示意，不参与构建：反例 —— 业务代码自己 new 出所有依赖
class OrderService:
    def __init__(self):
        self.repo = SqlOrderRepository("jdbc://...")     # 依赖被写死
        self.notifier = SmtpNotifier("smtp://...")

# 正例：启动代码负责组装，业务代码只接收
def main() -> None:
    repo = SqlOrderRepository.from_env()       # 唯一的组装点
    notifier = SmtpNotifier.from_env()
    service = OrderService(repo, notifier)     # 业务代码只接收
    service.run()

class OrderService:
    def __init__(self, repo: OrderRepository, notifier: Notifier) -> None:
        self.repo = repo          # 接口类型：可替换、可测试
        self.notifier = notifier
```

```java
// 教学示意，不参与构建：正例——构造器注入让「替换实现」变成一行配置
public class OrderService {
    private final OrderRepository repository;
    private final Notifier notifier;
    public OrderService(OrderRepository repository, Notifier notifier) { ... }
}
```

示例二：把「策略」与「机制」分开（11.5 / 11.6）。

| 关注点 | 该由谁决定 |
| --- | --- |
| 用几个线程 | 部署配置（扩容策略） |
| 用哪个数据库实现 | 组装层（工厂/DI） |
| 业务逻辑怎么写 | 业务代码 |

违反这条的典型表现：`if (clusterMode) { ... }` 出现在业务方法里——扩容策略漏进了领域逻辑。

示例三：横切关注点（11.7）。

| 反例：复制粘贴 | 正例：代理/装饰器 |
| --- | --- |
| 每个服务方法开头写 `log.info("enter")` | 一个装饰器统一织入 |
| 每个方法手写事务 begin/commit | 框架/中间件统一处理 |
| 权限判断散落各处 | 统一的拦截点 |

示例四：架构的检验方式（11.8 / 11.9）。

| 检验 | 做法 |
| --- | --- |
| 能不能用测试替换实现？ | 业务测试里注入一个内存实现 |
| 改一处要不要改五处？ | 用 grep 数调用点 |
| 能不能在测试环境全速跑起来？ | 环境依赖可注入 |
| 新增一种实现要不要改业务代码？ | 只改组装层 |

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1994 | GoF 的 Factory Method / Abstract Factory 给出「别直接 new」的第一代解法（`book/设计模式GoF/`） |
| 2000 | Martin 的 SOLID 把「依赖倒置」定为架构级原则 |
| 2002 | 依赖注入的概念在敏捷圈成形；Spring（2004）把它变成 Java 企业开发默认 |
| 2004 | Spring Framework 发布；同年 Guice 尚在酝酿（2007） |
| 2008 | 本章出版，把「构造和使用分离」写进代码整洁的教科书 |
| 2009 | PicoContainer、Guice 等轻量容器流行，注解式注入（@Inject）开始 |
| 2013 | Spring Boot 让「约定优于配置」成为组装层的主流形态 |
| 2017 | *Clean Architecture* 把本章的 DI 上升到组件层「依赖方向」规则 |
| 2015–2018 | Docker/Kubernetes 让「扩容」变成部署问题，11.5 的价值被大大强化 |
| 2020–2023 | Rust 的所有权 + 无 GC 让「无状态优先」成为新默认；GoF 模式进一步被语言替代 |
| 2024–2026 | AI 生成的服务类普遍自带「自己 new 依赖」的老毛病；DI 容器在 AI 生成代码里的可读性问题被讨论 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **DI 书籍化的讨论落后于框架现实** | 书里讲「用工厂创建对象」，但今天大部分项目用注解式容器，对象寿命由容器管理 | 关注「谁决定创建哪些对象」，而不是具体用哪个框架 |
| 2 | 🔧 **对「无状态」的提倡缺少落点** | 无状态不等于无配置、无实例缓存；纯函数之外的状态无处安放 | 状态集中到明确的「存储/会话」层，逻辑写成纯函数 |
| 3 | 🔧 **AOP 的门槛与代价被低估** | 代理/织入让调用栈变深、调试变难，作者没提代价 | 优先用显式装饰器；AOP 只留给真正横切的关注点 |
| 4 | 🔧 **「边界的测试」说法含糊** | 「用测试确认解耦」容易被理解成多写一堆集成测试 | 只写少数粗粒度集成测试守边界，其余用单元测试 |
| 5 | 🔧 **对「扩容」几乎没给方法** | 11.5 只有原则，没有具体的容量规划与实现 | 结合云原生实践：`book/凤凰架构.md`、`book/高伸缩性系统/` |
| 6 | 🔧 **AI 生成代码经常违反本章** | LLM 倾向于在每个类里自己 new 出依赖，导致测试无法替换 | review 时强制要求构造器/工厂注入，禁止在业务对象里 new |

## 与其他章 / 其他书的联系

- 11.1 的「构造与使用分离」与 `03-函数.md` 3.7「无副作用」是同一个思想：**副作用要集中在明确的区域**。
- DI 是 `10-类.md` SRP 的工程支撑：类要小、要专，前提是它的依赖能被替换。
- 与 `08-边界.md` 的适配层合起来，就是 *Clean Architecture* 的依赖方向规则在本书里的雏形。
- 跨书：GoF 的工厂模式是 DI 的前身（`book/设计模式GoF/`）；*Clean Architecture*（本仓库暂无中译条目，最接近的是 `book/软件架构设计/`、`book/Fundamentals_of_Software_Architecture.md`）把本章的规则推到组件层；*Dependency Injection*（Seemann，2006）是 DI 的专门著作。
- 并发场景下的「无状态」补充见 `13-并发编程.md`；C++ 侧的构造与生命周期实践见 `book/C++代码整洁之道.md`。
