# 第 3 章 函数

> **一句话**：函数是「把一段意图装进一个名字」的容器——**名字好、短、只做一件事，是代码可读性的杠杆点**；本章是全书写得最实、也最容易被机械执行的一章。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 3.1 短小 | 函数越短越好；作者给出的标准是「20 行上限」，嵌套不超过一两层 | 长函数几乎总是坏味道的根源 |
| 3.2 只做一件事 | 做了不止一件事，就得改名；「一件事」= 一个抽象层级 | 拆分函数的正确性判据在**抽象层级** |
| 3.3 每个函数一个抽象层级 | 高层函数里不该出现低层细节（`+= 1` 与 `getWidget()` 混排是大忌） | 「自顶向下读」是函数的结构属性 |
| 3.4 switch 语句 | `switch`/`if-else` 太长就抽成多态或查表 | 只在必要时用，别把它当分支工具 |
| 3.5 描述性的名称 | 长名字好过注释；描述性 > 短 | 函数的名字要能当句子读 |
| 3.6 函数参数 | 零参数最好，一元次之，标识参数（boolean）最差；参数对象；动词与关键字 | 参数多说明「职责还没收拢」 |
| 3.7 无副作用 | 函数只做一件事；副作用是隐藏的耦合 | 得电脑的动作（`deleteFrom` 同时删除）要显式区分 |
| 3.8 分隔指令与询问 | 要么做点什么，要么回答点什么，不要都做 | `contains()` 不该顺手把元素加进去 |
| 3.9 使用异常替代返回错误码 | 错误码会让主流程被 `if` 淹没 | 异常把「错误处理」从主流程里拿掉 |
| 3.9.1 抽离 try/catch | try/catch 里只放「出错才知道的事」 | 错误处理本身要成为一个函数 |
| 3.9.2 错误处理就是一件事 | 一个函数里若只有错误处理，也可以拆成一个函数 | 让错误路径保持单一形态 |
| 3.9.3 Error.java 枚举 | 别把错误码当枚举到处传 | 用类型化的异常/结果类型 |
| 3.10 别重复 | 重复是本章反复出现的坏味道 | 同一逻辑只写一次（见 3.11 与 Ch17「重复」启发式） |
| 3.11 结构化编程 | 单一出口（Dijkstra 论 goto）：直上直下的控制流 | 「一个函数一个 return」在今天更多是风格选择 |
| 3.12 如何写出这种函数 | 先写长而乱的，然后**照着矫枉过正的方向反复切分** | 拆函数是手艺人动作，靠练不靠想 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：一个典型的「过长、混杂抽象层级」函数（对照书中 FitNesse 案例那种体量）。

```java
// 教学示意，不参与构建：反例 —— 抽象层级混杂 + 副作用 + 长函数
public void setupTeardownIncluderAndHandleResponses(String pathname, int width,
                                                     int depth, boolean before,
                                                     boolean after, String page,
                                                     String title, String[] args) {
    Response response = new Response();
    PageData pageData = pageData(pathname);
    String relativePath = getRelativePath(pathname);
    ...
    if (before) { includeSetupPages(pageData, relativePath, title); }
    else if (after) { includeTeardownPages(...); }
    else if (include) { ... }
    ...
    if (args[0].equals("shadow")) { ... }
    response.setContent(pageData.getWikiSource());
    handlePage(...);
}
```

拆开之后的结构（正例骨架）：

```java
// 教学示意，不参与构建：正例 —— 按抽象层级拆成「指令 + 询问」分离的一组小函数
public Response handle(String pathname) {
    PageData pageData = loadPage(pathname);       // 读取
    appendSurroundingPages(pageData);             // 组装（副作用集中在这）
    Response response = buildResponse(pageData);  // 构造
    return response;
}

private void appendSurroundingPages(PageData pageData) {
    if (pageData.shouldIncludeSetup())  pageData.append(setupPageArgs(pageData));
    if (pageData.shouldIncludeTeardown()) pageData.append(teardownPageArgs(pageData));
}
```

示例二：参数与「只做一件事」（3.2 / 3.6）。

```python
# 教学示意，不参与构建：反例 —— 布尔参数把一件事变成两件
def render_page(pathname, before, after, include):
    ...

# 正例：调用点自解释，函数的职责也变单一
render_page("Wiki/WikiSpaces", setup=True, teardown=False)
render_page("Wiki/WikiSpaces", teardown=True)   # 读者一眼看出两种语义
```

示例三：抽离 try/catch（3.9.1）——本章最被认可、也最容易照做的一条。

```java
// 教学示意，不参与构建：反例 —— 主流程被 try/catch 打断
public void sendInvite(String email) {
    try {
        Invite invite = new Invite(email);
        invite.send();
    } catch (Exception e) {
        log.error("failed: " + e.getMessage());
    }
}

// 正例：把「可能出错的部分」隔离成一个函数，主流程只剩意图
public void sendInvite(String email) {
    Invite invite = createInvite(email);
    invite.send();
}

private Invite createInvite(String email) {
    try {
        return new Invite(email);
    } catch (Exception e) {
        log.error("failed to create invite: " + email, e);
        throw new InviteFailedException(e);
    }
}
```

示例四：指令与询问分离（3.8）。

| 反例（既查询又修改） | 正例 |
| --- | --- |
| `if (set.contains("x")) set.add("x")` | `boolean added = set.add("x"); if (added) {...}` |
| `if (user.loggedIn()) logout(user)` | `if (user.ensureLoggedIn()) logout(user)` |

一个可执行的「函数长度」纪律（可直接进 pre-commit）：

| 指标 | 阈值（建议） | 工具 |
| --- | --- | --- |
| 单个函数行数 | ≤ 30，硬上限 60 | `ruff` / `golangci-lint funlen` / `CodeQL` |
| 圈复杂度 | ≤ 10 | `sonar` / `radon`（Python）/ `cyclomatic` |
| 参数个数 | ≤ 3；≥ 4 要问「是否该收成参数对象」 | linter |
| 嵌套深度 | ≤ 3 | `CodeQL` / `pmd` |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **「20 行」被当成硬指标追求** | 为达标把函数硬切成十几个只调用一次的小函数，产生大量一层深的样板，读者反而要跳来跳去 | 以「一级阅读能否理解」为准绳；机器指标只做下限告警 |
| 2 | 🔧 **过度切分污染测试** | 每个 3 行函数都要一个测试，覆盖率数字好看但测试可读性变差（`09-单元测试.md` 会重复讨论） | 只对**有行为边界**的单元设测试，私有逻辑通过公开行为覆盖 |
| 3 | 🔧 **「无副作用」在带状态的代码里不可行** | 命令式/UI/初始化代码天然要改状态；强行拆出纯函数会让调用链变复杂 | 承认「副作用集中在一个明确的区域」，见 `07-错误处理.md` 与 `11-系统.md` |
| 4 | 🔧 **「一个函数一个 return」已过时** | Dijkstra 的红字针对的是无结构化语言（Fortran/BASIC 的 `goto`），今天多 return 明显更好读 | 不必追求单一出口，追求「控制流一眼看懂」 |
| 5 | 🔧 **示例全是 Java，缺少泛型之后的写法** | `Optional`、`record`、lambda 出现后，`null` 判断与参数对象的写法都变了（见 3.9.3 的 `Error.java` 讨论） | 参考现代语言的结果类型；Go/Rust 的 `Result` 更接近这里的意图 |
| 6 | 🔧 **AI 生成代码典型地违反本章** | LLM 常一次给出 80 行的长函数，且函数名带 `process`/`handle` 这类无信息量的词 | 把「提炼函数」列为 AI 输出的第一道机械检查项 |
