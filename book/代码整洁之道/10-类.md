# 第 10 章 类

> **一句话**：**类越大、越想做多件事，就越难维护**——一个类的名字里塞进「Manager」「Helper」「Processor」，通常就说明它的职责已经溢出了。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 10.1 类的组织 | 静态变量 → 实例变量 → 构造器 → 方法；公有常量先、私有变量后；同一方法只在一个抽象层 | 类的内部布局要像报纸：先读标题再读正文 |
| 10.2 类应该很小 | 作者给的经验值是「一个类的实例变量不该超过 5 个」，行数上限远低于文件上限 | 类的「小」比「行数」更重要，参考指标是**职责数** |
| 10.3 单一职责（SRP） | 每个类只对一个参与者负责 | 责任要能被「别人说得出它是干什么的」检验 |
| 10.4 内聚 | 类的方法操作同一个变量的程度；内聚越高越好 | 高内聚 ⟹ 该类的方法都在改它的同一批字段 |
| 10.5 保持内聚 | 把方法不断拆出去，直到类的内聚达到最高 | 拆到「没有方法在改动大部分字段」为止 |
| 10.6 类之间的协调与内部类 | 对象之间的协调关系应该清晰可见 | 别让类之间靠隐式约定协作（方法调用链要能被读出来） |
| 10.7 内部类 | 内部类应随附其外部类，别单独暴露 | 用内部类减少接口数量 |
| 10.8 小结 | 与函数同理：短、专、内聚 | 类与函数是同一套原则的两种容器 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：类的组织顺序（10.1）。

```java
// 教学示意，不参与构建：正例 —— 类的内容按「可见性 + 静态性」分层
public class Order {
    // 1. 静态变量
    private static final int MAX_LINES = 100;
    // 2. 实例变量（同类私有，暴露最少）
    private final String orderId;
    private final List<Line> lines;
    // 3. 构造器
    public Order(String orderId) { this.orderId = orderId; this.lines = new ArrayList<>(); }
    // 4. 方法：先公有后私有，公有方法里不出现低层细节
    public void addLine(Line line) { ... }
    private void requireCapacity() { ... }
}
```

示例二：内聚的反面（10.4）——一个类的方法只操作了一半字段。

```java
// 教学示意，不参与构建：反例 —— 一半方法在管 lines，一半在管 shipping，内聚低
public class Order {
    private List<Line> lines;
    private Address shipTo;
    private Money discount;

    public void addLine(Line line) { ... }        // 只碰 lines
    public void removeLine(Line line) { ... }     // 只碰 lines
    public void setShipTo(Address a) { ... }      // 只碰 shipTo
    public void setDiscount(Money m) { ... }      // 只碰 discount
}
```

修正：按「变化的理由」拆成 `OrderLines` / `Shipping` / `Discount` 三个类（或保留一个类但确认这三者确实同时变化）。

```python
# 教学示意，不参与构建：正例 —— 高内聚：方法都在改同一个聚合
@dataclass
class OrderLines:
    items: list[Line]

    def add(self, line: Line) -> None: ...
    def remove(self, line: Line) -> None: ...
    def total(self) -> Money: ...
```

示例三：判断一个类是否「太大」的实用尺度。

| 指标 | 说明 | 建议阈值 |
| --- | --- | --- |
| 实例变量个数 | 作者使用的核心尺度 | ≤ 5，超过通常意味着多个职责 |
| 「Changes for」测试 | 是否有一个参与者会因为不同的理由要求你改它 | 一个 |
| 方法之间的字段交集 | 类里任意两个方法是否操作同一批字段 | 交集大即高内聚 |
| 名称里的连接词 | 「And」「Manager」「Processor」「Util」 | 出现即警戒 |
| 文件行数 | 次要指标 | Java 中 100–200 行居多；C++ 头文件常超 |

示例四：重构前的顺序（与 `14-逐步改进.md`、`15-JUnit内幕与重构SerialDate.md` 呼应）。

1. 先让它跑起来（提取方法，不改行为）
2. 再改名字（让类自己说明职责）
3. 最后切分类（把「一起变化的字段」聚成新类）

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1994 | GoF 书里的「一个类只有一个动机」是 SRP 的模式化版本 |
| 1995 | SRP 由 Martin 在 OOPSLA 的 SOLID 讨论中明确命名 |
| 2000 | Martin 把它写进 *Agile Software Development*，成为「类设计」的第一条 |
| 2008 | 本章出版，「一个类 5 个字段」的经验值被社区反复引用与质疑 |
| 2002–2011 | 依赖注入容器普及（Guice 2007、Spring），「类不该自己 new 依赖」成为 class 设计的默认前提 |
| 2014 | Java 8 的 lambda 让「一个类只做一件事」经常变成「一个闭包」 |
| 2017 | *Clean Architecture* 把 SRP 从类推广到组件与跨函数团队 |
| 2019 | Java `record` 让「只是数据的类」合法化并变短，缓解了「类太大」问题 |
| 2020s | 函数式/数据导向设计（如 Rust 的 enum + struct）提供「不靠类」的组织方式 |
| 2023–2026 | AI 生成类代码容易产出「上帝类」；「拆类」成为 AI 评审最常提的一条建议 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **「5 个实例变量」当成硬指标** | 有些概念天然需要更多字段（如一个富聚合）；强行拆会造成跨对象协调成本 | 用「变化的理由」判断，字段数只作参考 |
| 2 | 🔧 **对「小类」的偏好与「类爆炸」相对** | 拆得太碎会产生几十个只被调用一次的类与包，导航成本上升 | 拆的判据是「新类是否有独立的生命周期与变化理由」 |
| 3 | 🔧 **SRP 缺少「变化的方向」这一层** | 「只负责一件事」的说法模糊：是负责一种职责，还是负责一类参与者？ | 用「这个改动由谁来提」检验（Conway 式问题） |
| 4 | 🔧 **示例语言是老 Java，缺少泛型/记录/依赖注入的现代写法** | 类里的构造器常被迫写 setter/依赖 new | 现代写法用构造器注入 + `record` + 不可变字段 |
| 5 | 🔧 **没讨论「包/模块」层面的职责** | 本章的结论止于类，但实践中的耦合常发生在模块之间 | 类内聚之外再看模块耦合（*Clean Architecture*） |
| 6 | 🔧 **AI 生成类代码放大上帝类问题** | LLM 常见的输出是一个 300 行的类，含 CRUD、校验、通知 | review 时优先检查生成类的字段数量与「名字里的连接词」 |
