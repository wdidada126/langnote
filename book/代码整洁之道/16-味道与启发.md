# 第 17 章 味道与启发（Smells and Heuristics）

> **一句话**：这一章是全书最像「作弊小抄」的部分——**把作者在多年审阅里用过的判断标准，按类别列成可查阅的条目表**，也是附录 C 交叉索引的那张总表。

---

## 本章地图

| 类别 | 覆盖条目（摘要） | 结论 |
| --- | --- | --- |
| 注释 | 违规注释（误导性的、多余的、位置的、被注释掉的代码）、TODO 规范 | 注释是必要的恶，务必同步 |
| 例程与实现 | 别用 Null 做参数、别返回 null、表达式要短、别写死一个错误的边界 | 实现与接口都不该误导读者 |
| 函数 | 别返回 null、别传 null、别写参数对象、方法的抽象层级要一致 | 与 `03-函数.md` 的条目一一对应 |
| 命名 | 方法名用动词、类名用名词、每个概念一个词、别用双关 | 与 `02-有意义的命名.md` 的条目一一对应 |
| 通用 smells | 重复代码、超长块、条件逻辑过多、死代码、**括号之外的「懒代码」** | 重复是最先要消灭的味道 |
| 测试 | 测试要快、测试要独立、断言要完整、别测私有方法、别写「只会通过」的测试 | 与 `09-单元测试.md` 的条目对应 |
| 边界 | 第三方 API 的包一层、别泄漏内部结构、**兼容性承诺** | 与 `08-边界.md` 对应 |
| 类 | 类要小、保持内聚、内部类要随附外部类 | 与 `10-类.md` 对应 |
| 架构 | 别过早引入框架、构造与使用的解耦、别让架构依赖框架 | 与 `11-系统.md` / `12-迭进.md` 对应 |
| 附录 A 并发编程 II | 并发相关的早期文章合集 | 并发补课材料（见 `13-并发编程.md`） |
| 附录 B | `org.jfree.date.SerialDate` 的完整代码 | 案例研究的代码附录 |
| 附录 C | 启发式的交叉索引 | 把条目映射回原书章节，便于检索 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：把「味道」变成可自动化检查的清单（本章条目的机器化版本）。

| 味道（本章条目） | 机器可检 | 工具 |
| --- | --- | --- |
| 重复代码（同一段逻辑出现两次） | 是 | CPD / duplication 检测、`codeql` |
| 超长函数 / 超长块 | 是 | `ruff` / `golangci-lint` / `CodeQL` |
| 条件逻辑过多（圈复杂度高） | 是 | `sonar` / `radon` |
| 死代码、被注释掉的代码 | 是 | `sonar` / `infer` |
| 返回 null / 传 null | 部分 | `infer` / Kotlin 编译器 |
| 命名不当 | 部分 | linter 命名规则、CodeQL |
| 测试独立性差（共享状态） | 否 | 需要人的判断 |
| 抽象层级混杂 | 否 | 需要人的判断 |

示例二：几条最常用、性价比最高的条目。

| 条目 | 反例 | 正例 |
| --- | --- | --- |
| 别返回 null | `User u = find(id); if (u == null) return;` | `requireUser(id)`（找不到就抛） |
| 别传 null | `query(name, null, date)` | `query(name, date)`（重载） |
| 重复代码 | 三处相同的校验逻辑 | 抽成一个校验函数或守卫对象 |
| 死代码 | 遗留的 `private void legacy()` 无人调用 | 直接删 |
| 懒代码（本章指「用注释和命名遮盖设计问题」） | `// 这里以后会改成...` + 奇怪的结构 | 现在就改结构 |

示例三：如何把这一章当成 checklist 用。

| 场景 | 用哪一节 |
| --- | --- |
| code review 时找切入点 | 先看「通用 smells」与「命名」两类 |
| 收到一份新代码要接手 | 先跑自动工具，再对照「类」「函数」条目 |
| 制定团队规范 | 从附录 C 的交叉索引里挑出可自动化的条目 |
| 准备重构 Plan | 按「注释 → 命名 → 函数 → 类 → 架构」的顺序排优先级 |

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1990s | 「code smell」一词在 Object Mentor 内部使用（Ward Cunningham 的 wiki 也有相关讨论） |
| 1994 | GoF 书里已出现「代价（Consequences）」式的条目化表述 |
| 1999 | Fowler，《Refactoring》的「坏味道（Bad Smells）」目录成为最流行的版本 |
| 2008 | 本章把 smells/heuristics 条表化，按类别分组；附录 C 提供交叉索引 |
| 2013 | *AntiPatterns*（Wake，2006）与本章条目互相印证 |
| 2016 | 静态分析工具开始直接以「 smell 名」命名告警 |
| 2019 | 《重构（第 2 版）》新增 smell 分类，条目进一步细化 |
| 2021 | 各类 linter 的 rule name 大量采用 smell 词汇，形成事实上的行业词表 |
| 2023–2026 | AI 评审按 smell 条目打分；条目本身成为 prompt 的一部份 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **把「味道」当成必须全部消除的缺陷** | 有些味道在特定上下文里是划算的（如性能热路径的重复） | 用「改动的代价 vs 收益」判断，别追求零味道 |
| 2 | 🔧 **条目表的 Java 中心倾向明显** | 某些条目（如「参数对象」「成员前缀」）在别的语言里语义不同 | 按语言生态选择对应工具与判据 |
| 3 | 🔧 **「懒代码」这一条目定义含糊** | 中文译名与原文对应不精确，容易误读 | 理解其含义为「用注释与命名掩盖设计问题」 |
| 4 | 🔧 **没有给出「何时忽略」的规则** | 一个 checklist 没有例外清单会变成教条 | 明确例外：热路径、协议兼容层、一次性脚本 |
| 5 | 🔧 **AI 时代条目成为新的「对齐税」** | LLM 会机械引用条目建议，产生大量无意义的改名/拆分 | 评审时区分「真问题」与「条目噪音」 |
| 6 | **缺少并发与性能这两类味道的条目** | 全书最明显的缺口之一：并发坏味道（锁范围、共享可变状态）无处可查 | 见 `13-并发编程.md` 的误区表，并读并发专书 |
