# 第 4 章 注释

> **一句话**：注释是**必要的恶**——代码能说话时不要写注释；注释存在的每一处，通常都意味着**代码本身说不清楚**。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 导言：注释的作用 | 注释能弥补代码表达力的不足（法律信息、意图、警告、TODO） | 注释永远不应该是「代码需要注释才能懂」的借口 |
| 注释的位置 | 法务信息、意图解释、警示、TODO（要写明「谁、要做什么」） | 挂在有问题的那段代码头上，别抄在文件头 |
| 好注释 | 解释意图、说明法律信息、给公共 API 写说明、解释「为什么这么做」 | 讲「为什么」，不讲「做了什么」 |
| 坏注释 | 多余的信息、误导性的注释、日志性注释、逐行注释、位置的标记注释（`// end if`）、被注释掉的代码、HTML 注释、改动历史 | 每删一次代码，都要同步删它的注释 |
| 注释与代码不同步 | 注释一旦撒谎，比没有注释更糟 | 维护成本随代码变化而累积 |
| 总结 | 写注释前先问：这段代码能不能靠改名/抽取自解释 | 想清楚「要不要写注释」和「怎么写」 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

反例一：把「做了什么」抄成注释（多余的注释）。

```java
// 教学示意，不参与构建：反例 —— 注释只是复述代码
public void subtract(int a, int b) {
    // 把 a 减去 b
    result = a - b;
}
```

正例：如果真需要说明，就应该说明「为什么是减法而不是加法」。

```java
// 教学示意，不参与构建：正例 —— 解释意图与约束
// 结算以「含税价」为基准做减法，故这里是扣减而不是相加（财务口径见 FR-217）
public void subtract(int a, int b) { ... }
```

反例二：把「为什么」写成「做了什么」（误导性注释）。

```java
// 教学示意，不参与构建：反例 —— 注释与代码已经不同步
// 处理完所有订单
public void flush() {
    // TODO(martin): 这里以后要加缓存
    buffer.clear();
}
```

反例三：坏注释的几种典型形态（对照本章该节逐条）。

| 坏注释类型 | 示例（示意） | 为什么坏 |
| --- | --- | --- |
| 多余信息 | `// 设置 user 的名字` 紧跟着 `user.setName(name)` | 与代码重复，代码一改就撒谎 |
| 日志性注释 | 在代码里堆一行行 `// 2020-03-01 改了 x` | 版本控制里已有 commit 记录 |
| 位置的标记注释 | `// end for` 贴在循环右括号上 | 应该靠缩进与结构消除 |
| 被注释掉的代码 | 20 行历史代码留在函数里 | 版本控制会替你留着 |
| 注释掉的函数签名 | `// public void process() {...}` | 同上 |
| HTML 注释 | 在 `.java`/`.cs` 文件里写 HTML 注释块 | 注释对象搞错了 |
| 只写「什么」不写「为什么」 | `// 调用支付网关` | 改名就能表达的事 |
| TODO 没有负责人 | `// TODO: 优化这里` | 没人知道该找谁、要做什么 |

正例一：把注释当作「公共 API 契约」——这是书中明确认可的一类。

```java
// 教学示意，不参与构建：好注释 —— 说明契约与边界条件
/**
 * 以指定汇率换算金额，四舍五入到分。
 *
 * @throws IllegalArgumentException 若汇率为非正数
 * @implSpec 实现必须保持幂等：相同输入重复调用结果一致
 */
public Money convert(Money amount, Rate rate) { ... }
```

正例二：注释只挂在「问题本身」上（本章「注释的位置」的落点）。

```java
// 教学示意，不参与构建：注释贴在它解释的那段代码旁边，而不是文件顶部
public boolean isEligible(User user) {
    // 这里故意用 String 比较而不是时间差：跨时区结算要求按「日」对齐
    return !"SUSPENDED".equals(user.getStatus());
}
```

一个可执行的注释纪律：

| 规则 | 检查方式 |
| --- | --- |
| 删除一段代码时，同时删掉它的注释 | PR diff 中注释行数与代码行数比例 |
| 注释里出现「已废弃的旧行为」时，直接写 TODO 并署名 | CodeQL 自定义规则 |
| 公共 API 必须有说明性注释，且说明出错条件 | 文档覆盖率 |
| 禁止逐行注释 | linter（如 `CommentSpacers`、自定义 CodeQL 查询） |

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1970s | 注释以「卡片式的代码说明」为主，注释里有大量编号和手册引用 |
| 1990s | JavaDoc 与「文档先行」文化兴起，`/** ... */` 从可选变成公共 API 惯例 |
| 1994 | GoF 书里的类图/协作图注记风格影响了对「注释即设计文档」的期待 |
| 2000 | 极限编程把「注释要少」写进克制的实践：能改名解决的就不写注释 |
| 2008 | 本章出版，明确「注释是必要的恶」，并逐条列出坏注释 |
| 2009 | 《重构》把「以注释换取可读性」的手法（如「引入解释性变量」）系统化 |
| 2011 | 中译本引入；此后中文团队对「TODO 要有负责人」讨论增多 |
| 2014 | 静态分析工具开始检测「注释掉的代码块」并告警 |
| 2020s | 类型系统（Java `record`、Kotlin data class、Rust 文档注释）把不少注释义务转交给语言 |
| 2023–2026 | 出现新的注释类别：**给 AI 的注释**（说明约束与不可误改的部分），以及「注释与生成说明文档」的分工 |

## 近年研究与工业界开源实践（2015–2026）

趋势：**注释正在被机器接管**——文档由 API 抽取工具与 LLM 生成，注释的真实价值上移到「为什么」层面；同时「注释掉的代码」成为各类 linter 的常规告警。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `github/codeql` | **10,122★** | 可写自定义查询识别「注释与代码不一致」「文档注释缺失」 |
| `sonarsource/sonarqube` | **11,024★** | 「注释掉的代码应删除」「公共 API 应有文档注释」都是默认规则 |
| `psf/black` | **41,851★** | 格式化不删注释，但让「注释与代码对齐」变得稳定 |
| `astral-sh/ruff` | **49,779★** | 自带文档字符串检查（D 系列 pydocstyle）与注释风格规则 |
| `qodo-ai/pr-agent` | **13,146★** | AI 评审中「注释过时的」是最常见的提醒之一 |
| `pre-commit/pre-commit` | **15,594★** | 提交前集中清理注释与格式 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **把「注释越少越好」读成「不要注释」** | 公共 API、并发约束、领域规则、合规信息都**必须有**注释 | 区分「复述型注释（删）」与「意图型注释（留）」两类清单 |
| 2 | 🔧 **TODO 的写法没有约束力** | 书中只写了「要包含让人看得懂的描述」，但没有要求负责人与时间 | 用 `TODO(name, date): 做什么` 的模板，并在看板上追踪 |
| 3 | 🔧 **对「注释掉的代码」的批评在今天更成立** | 版本控制成熟后，注释掉的死代码纯是噪音 | 直接删；把历史交给 git blame |
| 4 | 🔧 **没有讨论非 ASCII（中文）注释的排版与编码问题** | 中文团队常见乱码、字符集不一致、`@author` 用拼音造成的歧义 | 统一 UTF-8，注释语言与标识符语言分离 |
| 5 | 🔧 **AI 生成代码引入了新的注释类别** | LLM 喜欢写「解释它刚做的事」的复述型注释，正好是本章最反对的一类 | 规定「注释只写非显然约束」，并在 review 里删掉复述型注释 |
| 6 | **全书 JavaDoc 示例会被误当成必须写 JavaDoc** | 书中肯定了 API 注释的价值，但没说明哪些 API 值得写 | 建立「只有跨模块公共契约才写 JavaDoc」的边界 |

## 与其他章 / 其他书的联系

- 本章的「坏注释」与 `02-有意义的命名.md` 是同一枚硬币：**改名能说清的事，就不要写注释**；注释里解释「这个变量是什么」，说明该改名了。
- 与 `03-函数.md` 3.5「描述性名称」的依赖关系一致：先尝试改结构，再考虑写注释。
- 「注释与代码不同步」在 `01-整洁代码.md` 1.6 童子军军规处有执行机制。
- 跨书：*Clean Code* 的注释章节与《代码大全 2e》「注释」一节的结论**基本一致**（都强调解释意图、反对复述），可对照阅读；《重构》的「以意图取代注释」是本章的操作手法；GoF 的类说明样式见 `book/设计模式GoF/`。
- 语言侧：C++ 的头文件文档注释与 `book/C++代码整洁之道.md` 中的相关实践可对照。
