# 第 6 章 对象和数据结构

> **一句话**：对象与数据结构是**两种相反的设计取向**——对象把行为藏起来、暴露接口；数据结构把数据摊开、暴露字段；搞不清自己写的是哪一种，就等于两种都得不到。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 6.1 数据反模式（Data Class） | 只有字段 + getter/setter 的类：「数据类」 | 若只有数据没有行为，它其实是数据结构，别当对象用 |
| 6.2 对象与数据结构的差异 | 对象：暴露行为、隐藏数据（可用性优先）；数据结构：暴露数据、少行为（可变换性优先） | 先决定「这个东西是要被加新行为，还是要被加新类型」 |
| 6.3 得墨忒尔律（Law of Demeter） | 别和陌生人说话：只调用自己的方法、参数、它直接持有对象的成员 | 链式调用 `a.getB().getC().doIt()` 是耦合信号 |
| 6.4 数据传送对象（DTO） | 无行为的数据容器（如 `Address`、`Money`）：这是合法的数据结构 | 不要给 DTO 加业务逻辑，那就不叫 DTO |
| 6.5 活动记录（Active Record） | `Person.save()` / `findByName()` 这类「数据 + 部分行为」的混合体 | 混合体是最常见也最危险的一类 |
| 6.6 被动数据（Passive Data） | 只读、可由外部自由消费的数据记录（配置、事件、DTO） | 越接近被动数据，越要有明确的「只读边界」 |
| 6.7 小结与取舍 | 什么时候该用对象，什么时候该用数据结构 | 见下方「核心精讲」的判据 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：同一个业务概念，两种写法（6.2 的核心对照）。

```java
// 教学示意，不参与构建：数据结构取向 —— 数据摊开，行为在别处
public class UserData {
    public String name;
    public String email;
}

// 使用方需要自己去拼逻辑
if ("".equals(userData.name) || userData.name == null) { throw new IllegalStateException(); }
```

```java
// 教学示意，不参与构建：对象取向 —— 数据私有，行为内聚
public class User {
    private final String name;
    private final String email;

    public User(String name, String email) {
        validate(name);              // 校验是自己的事
        this.name = name;
        this.email = email;
    }

    public boolean canBeInvited() { return !name.isBlank(); }  // 行为跟着数据走
}
```

示例二：得墨忒尔律（6.3）的违反与修正。

```java
// 教学示意，不参与构建：反例 —— 一串链式调用，暴露了内部结构
public double getTax() {
    return order.getCustomer().getAddress().getCountry().getTaxRate();
}

// 正例一：向「知道该怎么做的对象」发消息（Tell, Don't Ask）
public double getTax() {
    return order.calculatedTax();
}

// 正例二：如果只是要用一个值，就把它一次性拿过来
public double getTax() {
    Country country = order.countryOfDelivery();
    return country.taxRate();
}
```

| 违反形式 | 症状 |
| --- | --- |
| 链式调用超过两位 | `a.getB().getC().doSomething()` 改结构时全线崩 |
| 调用方同时读写对方字段 | 双向耦合，无法单独测试 |
| 结构体嵌套 3 层以上 | 任何一层结构调整，所有调用点都要改 |

示例三：绕过得墨忒尔律的「合法例外」——DTO/被动数据（6.4 / 6.6）。

```python
# 教学示意，不参与构建：DTO 就是「允许被穿透」的数据结构
@dataclass
class Address:
    city: str
    zip_code: str

@dataclass
class Order:
    address: Address
    total_cents: int

# 这里允许直接取值，因为 Order 是数据结构的角色
fee = order.address.city == "SHANGHAI"
```

示例四：活动记录的坑（6.5）。

| 特征 | 后果 |
| --- | --- |
| 类里既有字段又有 `save()`/`find()`，还有业务方法 | 模型层、持久层、业务逻辑耦在一起 |
| 单元测试要跑数据库 | 测试变慢，无法独立验证业务规则 |
| 一行 SQL 改了，业务方法一起碎 | 改动面不可控 |

可执行的判据（选择对象还是数据结构）：

| 如果你…… | 选 |
| --- | --- |
| 经常要给它加**新的行为种类** | **对象**（多态扩展） |
| 经常要给它加**新的数据类型**（新增一种形状） | **数据结构 / 判别联合 / enum + switch** |
| 要跨系统传输、序列化 | **DTO（纯数据）** |
| 只是配置、参数、记录 | **被动数据** |

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `swiftlang/swift` | **70,401★** | `struct` 值语义 + `protocol` 让「数据为主、行为为辅」成为默认写法 |
| `openjdk/jdk` | **23,379★** | 阅读它可以看到「真实 JDK 里对象/数据结构的混合形态」 |
| `golang/go` | **138,994★** | 结构体 + 方法：Go 把「数据 + 行为」绑在一起但无继承，逼你选取向 |
| `astral-sh/ruff` | **49,779★** | 可检测「只有字段的类」这类坏味道（配合自定义规则） |
| `github/codeql` | **10,122★** | 可查询「超深链式调用」「对外暴露的可变字段」 |
| `qodo-ai/pr-agent` | **13,146★** | AI 评审中「这里该做 Tell, Don't Ask」是常见建议 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **把「得墨忒尔律」当成绝对禁令** | 严格按它写会退化成大量转发方法（`getB()` 只能由 `A` 调用），反而产生噪音代码 | 关注**耦合的后果**，而不是链条长度；一次取值可以接受 |
| 2 | 🔧 **把「数据类」一律打成坏味道** | Java 的 `record`、Python 的 dataclass、Go 的 struct 今天都是被鼓励的写法 | 区分「DTO/配置/记录」与「缺行为的实体」，前者正当 |
| 3 | 🔧 **对活动记录的批评虽然对，但没给出替代方案的层级** | 书里说不要写 `save()` 混进来，但没说 ORM Frameworks 该如何分层 | 分离持久层与领域模型（仓储模式），而不是删掉 `save()` |
| 4 | 🔧 **对「贫血领域模型」几乎无话** | 本章否定缺行为的数据类，但现实中「实体只剩数据、逻辑全在 service」是主流形态 | 参考 DDD 的「领域服务 vs 实体」分工，别简单二选一 |
| 5 | 🔧 **示例语言是 Java，缺少值对象/不可变的视角** | 没有讲「让字段 `final` / 不可变集合」这一层 | 结合 `record`、Rust 的 struct + 所有权阅读 |
| 6 | 🔧 **AI 生成代码放大了 6.1 的坏味道** | LLM 极易产出「一堆字段 + getter 的 Data Class」 | review 时优先处理这类生成代码，把行为内聚回去 |
