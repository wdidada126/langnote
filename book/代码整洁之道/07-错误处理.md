# 第 7 章 错误处理

> **一句话**：错误处理是**最容易把主流程搞乱的那一类代码**——把它从主流程里搬出去，业务代码才可能保持「读起来像在讲业务」。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 7.1 使用异常而非返回码 | 返回错误码会让主流程堆满 `if (err != null)` | 错误码需要被调用方逐一检查，异常把失败路径隔离成另一段代码 |
| 7.2 异常规则 | 抛异常而不是返回 `null`/错误码；给出有意义的消息；不要吞掉异常 | 异常本身要携带足够信息 |
| 7.3 抽离 try/catch | try/catch 块后面的代码不该与业务混在一起 | 把可能出错的一段包成一个函数 |
| 7.4 错误处理就是一件事 | 一个函数里若主要负责错误处理，那它就是一个独立的「职责」 | 让错误路径保持单一形态 |
| 7.5 不返回 null | 返回 `null` 会把「没有」变成一个必须到处检查的状态 | 用空对象、Optional/Result、或抛出异常 |
| 7.6 不传 null | 传 `null` 等于把「没有这个值」的信息塞进签名 | 用参数对象、重载、Optional 参数 |
| 7.7 异常与错误处理的策略 | 别把第三方异常往上抛（转译）、别丢掉原始异常、别用异常做流程控制 | 异常是「异常事件的通道」，不是返回值 |
| 7.8 小结 | 错误处理的规则本质上只有三条：别吞、别满、别到处判断 | 关键是让主流程干净 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：错误码 vs 异常（7.1）。

```python
# 教学示意，不参与构建：反例 —— 每个调用点都要自己记得检查
def create_user(name):
    code = validate(name)
    if code != 0:
        return None, code
    return User(name), 0

# 调用点：一旦遗漏检查，后续就静默出错
user, code = create_user("")
send_welcome(user)      # user 是 None，问题延后 30 行才炸

# 正例：异常把失败路径从主流程里拿掉
def create_user(name: str) -> User:
    if not name:
        raise InvalidUserNameError("name must not be empty")
    return User(name)

user = create_user("")   # 读者读到这里不需要知道它的失败形态
```

示例二：抽离 try/catch（7.3）——本章最可执行的一条。

```java
// 教学示意，不参与构建：反例 —— try/catch 打断主流程
public Money convert(Money money, Rate rate) {
    Money result = null;
    try {
        result = moneyService.exchange(money, rate);
    } catch (RateUnavailableException e) {
        result = lastKnownRate.apply(money);   // 降级逻辑塞在异常里
    }
    auditLog.record(result);
    return result;
}

// 正例：出错的部分自成一段，主流程只剩意图
public Money convert(Money money, Rate rate) {
    Money result = exchangeWithFallback(money, rate);
    auditLog.record(result);
    return result;
}

private Money exchangeWithFallback(Money money, Rate rate) {
    try {
        return moneyService.exchange(money, rate);
    } catch (RateUnavailableException e) {
        log.warn("rate unavailable, use last known", e);
        return lastKnownRate.apply(money);
    }
}
```

示例三：不返回 null（7.5）。

```java
// 教学示意，不参与构建：反例 —— null 让调用方到处设防
public User findUser(String id) {
    return users.get(id);          // 找不到就是 null
}
// 调用方
User user = findUser(id);
if (user == null) { throw new IllegalStateException("..." ); }

// 正例一：直接说明「找不到」
public User requireUser(String id) {
    User user = users.get(id);
    if (user == null) throw new NoSuchUserException(id);
    return user;
}

// 正例二：允许「没有」也是一种结果
public Optional<User> findUser(String id) { ... }

// 正例三：用「空对象」代替 null
public static final User EMPTY = new User("unknown", "unknown@example.com");
```

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| `Optional<>` / `Result<>` | 业务逻辑里「没有」是正常结果 | 链式调用需要小心展开 |
| 空对象（Null Object） | 值类型、只读场景 | 空对象行为要写全，否则又是隐藏分支 |
| 抛异常 | 「没有」是异常事件 | 异常不该用于常规分支控制 |
| `requireXxx` 断言式 | 内部一致性要求 | 契约写在文档里，编译器不检查 |

示例四：异常转译与不吞异常（7.7）。

```java
// 教学示意，不参与构建：反例 —— 丢了上下文，还吞了根因
catch (SQLException e) {
    throw new RuntimeException("数据库出错");
}

// 正例：保留根因与上下文
catch (SQLException e) {
    throw new OrderPersistFailedException(orderId, "persist failed", e);
}
```

一个可执行的错误边界清单：

| 层 | 建议 |
| --- | --- |
| 领域/业务层 | 抛**领域语言**的异常，不带 HTTP/SQL 细节 |
| 应用/服务层 | 转译第三方异常，保留根因；一个用例只设一个入口点 |
| 接口/适配层（controller） | 在边界上统一映射为响应码/状态码 |
| 基础设施 | 只抛基础设施异常，不要往上抛框架异常 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **「不传 null」的绝对化** | 弱类型语言里「没有这个值」是常见表达；强制 Optional 反而让 API 变啰嗦 | 语言有类型表达力时用类型；否则在函数文档里说明 |
| 2 | 🔧 **对受检/非受检 exception 之争回避了** | 书中只说「用异常」，但 Java 受检异常在设计系统时会引发连锁 `throws` 声明 | 现代 Java/Scala 侧更倾向运行时异常 + 边界映射 |
| 3 | 🔧 **没讲异常的性能成本** | try/catch 在某些语言里确有成本，热路径上的异常被滥用会拖慢系统 | 热路径用状态码/结果类型；异常只在异常路径 |
| 4 | 🔧 **没讲「异常栈与日志的关系」** | 大量项目用 `printStackTrace()` 掩盖异常 | 规定：异常必须落日志（含根因），不得静默吞掉 |
| 5 | 🔧 **AI 生成代码是「吞异常」的重灾区** | `catch (Exception e) {}` / `except: pass` 是最常见的一段 | 在 CI 里对空 catch 直接 fail，不靠 review |
| 6 | **Java 示例让 null-free 规则显得比实际更激进** | Java 没有 `Result`，作者的选择是合理的；但 Go/Rust 的写法是另一套 | 按语言选择对应形态：`Result` / `Option` / 多返回值 |

## 与其他章 / 其他书的联系

- 7.3 抽离 try/catch 与 `03-函数.md` 3.9.1 是同一条规则的两种表述，是全书写得最实的一条。
- 7.5 不返回 null 与 `06-对象和数据结构.md` 的 DTO/被动数据呼应：null 常常是「数据结构缺少表达力」的症状。
- 本章的错误边界与 `08-边界.md` 合并看：第三方 API 的错误应该在这里被**转译**成你自己的异常类型。
- 与 `09-单元测试.md` 的关系：异常路径必须有测试，测试就是「异常契约」的规格说明。
- 跨书：GoF 的 Null Object 模式给出 7.5 的标准解法（`book/设计模式GoF/`）；*Clean Architecture* 把「异常转译」推广为系统边界的通用做法。
- 并发场景下的错误处理见 `13-并发编程.md`（那里异常会被 swallowed 在不同线程），C++ 侧的写法见 `book/C++代码整洁之道.md`。
