# 第 14 章 逐步改进（Successive Refinement）

> **一句话**：把 `SerialDate`（jFreeChart 里的一个真实日期类）从「能跑」一步步变成「干净」——**本书唯一完整的案例研究**，也是理解「重构顺序」最好的一份现场记录。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 导言 | 待改造对象：`org.jfree.date.SerialDate`（Java 1.2 时代的一个日期实现） | 目标不是「删掉它」，而是让它可读、可改、可测 |
| 第一步 | 先**建立测试网**：写测试让它在现有行为下稳定（characterization test） | 没有测试的重构是赌博 |
| 第二步 | 重命名：把 `SerialDate` 及其方法改成领域语言的名字 | 命名是重构的第一刀，也是回报最高的一刀 |
| 第三步 | 提取变量与方法：把超长方法按抽象层级切开 | 与 `03-函数.md` 的手法完全一致 |
| 第四步 | 替换魔法数字与死代码 | 让代码自己说话 |
| 第五步 | 拆分类：`SerialDate` 同时管「日期表示」与「日期计算」两件事 | 见 `10-类.md` 的 SRP |
| 收尾 | 留下一个比原来**更小、更快、更好读**的版本，并保留原 API 以便逐步替换 | 逐步替换 = `12-迭进.md` 的绞杀者 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**
> 说明：本章用的是真实开源代码 `SerialDate`（jFreeChart），改造细节以中译本第 14 章为准；下面是从中译本步骤里抽象出的**通用动作序列**，不照抄源码。

示例一：先给旧代码上「保险」（第一步）。

```java
// 教学示意，不参与构建：characterization test —— 记录「现在」的行为，不管它是否合理
@Test
void serialDate_behavesAsTodayForKnownCases() {
    SerialDate d = SerialDate.createFromDayOfYear(1955, 2, 60);
    assertThat(d.getYear()).isEqualTo(1955);
    assertThat(d.getMonth()).isEqualTo(Calendar.FEBRUARY);
    assertThat(d.getDayOfMonth()).isEqualTo(9);
    // 对「不合理」的行为也记录在案，作为后续决策的依据，而不是默默改掉
    assertThat(d.toString()).isEqualTo("...");
}
```

> 这一步的要点：**先把行为钉住，再谈改进**。任何改动都必须在「同样的测试仍然全绿」的前提下进行。

示例二：按抽象层级切分（对应第二步之后的重构动作）。

```java
// 教学示意，不参与构建：反例 —— 一个方法里同时做「解析」与「计算」
public int calculate(List<String> rows) {
    int total = 0;
    for (String row : rows) {
        String[] parts = row.split(",");
        int qty = Integer.parseInt(parts[1]);
        int price = Integer.parseInt(parts[2]);
        if (qty > 0) { total += qty * price; }
    }
    return total;
}

// 正例：按抽象层级拆开（与第三章「每个函数一个抽象层级」一致）
public int totalOf(List<String> rows) {
    int total = 0;
    for (String row : rows) total += lineTotalOf(row);
    return total;
}

private int lineTotalOf(String row) {
    Quantity qty = quantityOf(row);
    return qty.isPositive() ? qty.value() * priceOf(row) : 0;
}
```

示例三：改进顺序的固定套路（可直接套用到自己的旧代码）。

| 顺序 | 动作 | 风险 |
| --- | --- | --- |
| 1 | 补测试（把所有已知行为钉住） | 无（只加不删） |
| 2 | 改名字（类、方法、常量） | 低 |
| 3 | 提取方法（按抽象层级切） | 中：需要测试守着 |
| 4 | 消除重复与魔法数字 | 中 |
| 5 | 拆分类 | 高：改动面最大，留到最后 |
| 6 | 删除死代码与过时 API | 低收益，但要确认调用点 |

示例四：改进前后的度量对照（本章想让你看到的差异）。

| 指标 | 改进前 | 改进后 |
| --- | --- | --- |
| 单个方法行数 | 数十行甚至上百行 | 个位数到十几行 |
| 魔法数字 | 大量（`2`、`60`、`0`） | 集中在常量区 |
| 抽象层级 | 混杂（解析、校验、计算混排） | 分层 |
| 测试覆盖 | 无 | 有（改进的前置条件） |
| 对外 API | 一个臃肿类 | 更小的类 + 原 API 保留 |

| 年份 | 事件 |

| 1999 | Fowler，《Refactoring》出版，为这类「安全小步」提供手法命名与目录 |
| 2001 | 中译《重构》出版，「提炼方法」等手法进入中文实践 |

| 2023–2026 | AI 辅助重构（自动加测试、自动改名）让本章第四步、第二步的成本大幅下降；但「补测试」这一步仍需人来判断 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **只演示「怎么改」，没演示「为什么先做这一步」** | 初学者常跳过「补测试」直接改名字，然后不敢合 | 把「先钉住行为」写进重构检查表的最前面 |
| 2 | 🔧 **案例里的断言写法已过时** | 中译本用的是 JUnit 4 的 `assertEquals`，今天项目多用 JUnit 5 的 `assertX` | 参考现代断言写法，别照抄老 API |
| 3 | 🔧 **没讲「改到一半怎么办」** | 改进是连续的，中途可能被打断、被别的分支合入 | 每步留出可提交的边界，改到一半时先提交到分支 |
| 4 | 🔧 **近乎理想化的演示** | 书中没有「改到一半发现原设计的概念就是错的」这种情形 | 承认有些类只能重写，而不是不断重构 |
| 5 | 🔧 **没解释原 API 如何逐步下线** | 改进后的类与旧 API 并存期间，两套代码都得维护 | 明确「谁负责兼容、何时下线」，参考绞杀者模式 |
| 6 | 🔧 **AI 让「改」变容易，但「判断该改什么」更难** | 生成一堆小重构建议，却没有优先级 | 先按技术债清单与热点排序，再让 AI 执行 |
