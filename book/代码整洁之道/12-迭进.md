# 第 12 章 迭进（Emergence）

> **一句话**：好的架构不是**设计出来的**，而是**从「每次都只做一点、并且做完就能用」的迭代里生长出来的**——所以关键不是「先画好大图」，而是「让每一步都是可上线的」。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 12.1 设计与架构 | 架构的第一价值是「支持决策（可维护、可开发、可运维、可部署）」：可维护、可开发、可运维 | 架构不是画图，是**改动的成本结构** |
| 12.2 「Metropolis」的故事 | 用盖大厦比喻：先想清楚整体，再动手；作者反驳说软件不能这么建 | 软件的「不确定性」决定了它必须增量演进 |
| 12.3 复杂度从哪里来 | 需求驱动的复杂度 vs 架构家带来的复杂度 | 别把「为了未来」设计的复杂度当功绩 |
| 12.4 BDUF（Big Design Up Front）的问题 | 一次性大设计在需求变更前就已过期 | 用 TDD 与迭代替代 BDUF |
| 12.5 绞杀者模式（Strangler Pattern） | 用新系统逐步「绞杀」旧系统，而不是一次性重写 | 增量迁移的标准姿势 |
| 12.6 持续集成 | 每次提交都构建、测试、反馈；这是「迭进」的技术基础 | CI 不是工具，是**反馈速度** |
| 12.7 TDD 是设计工具 | TDD 的价值不在测试，而在它逼出的「小步、可测、可拆」的设计 | 本章最重要的结论 |
| 12.8 增量与迭代 | 每一步都「可以发布」；把大功能拆成可上线的小步 | 发布节奏决定架构演进速度 |
| 12.9 小结 | 迭进 = 小步 + 反馈 + 每次都保持可用 | 与 `11-系统.md` 的构造/使用分离互为因果 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：把「大设计」拆成可发布的小步（12.5 / 12.8）。

| 一次性重写的做法 | 绞杀者模式的做法 |
| --- | --- |
| 立项、半年后搬迁完成 | 第一步：新系统在旁边先跑起来 |
| 一刀切切换，风险集中 | 第二步：用路由把一部分流量导到新系统 |
| 旧系统成为「不可触碰的遗产」 | 第三步：逐条业务能力搬过去，旧系统不断变瘦 |

```text
# 教学示意，不参与构建：绞杀者的三个阶段
阶段 1  新增 "/orders" 只写不读（影子流量 + 结果对比）
阶段 2  按客户/区域灰度切流，新旧双写
阶段 3  旧实现下线，新实现成唯一路径
```

示例二：复杂度预算（12.3）——哪些「为了未来」的钱不该花。

| 常见说法 | 事实 |
| --- | --- |
| 「以后可能要支持多租户」 | 现在就写租户过滤逻辑 = 未验证的复杂度 |
| 「以后要换数据库」 | 领域层不依赖具体实现即可，不必现在抽象出五层 |
| 「先把通用框架写好」 | 通用框架的维护成本远大于收益 |
| 「这样更优雅」 | 优雅不产出价值，能改才产出价值 |

示例三：TDD 如何产生设计（12.7）。

```python
# 教学示意，不参与构建：TDD 小步 —— 从「不能测」到「能测」到「更清楚的名字」
# 1) 先写一个最小测试（红）
def test_can_add_line():
    lines = OrderLines()
    lines.add(Line("SKU-1", 2))
    assert lines.count() == 1

# 2) 实现到刚好通过（绿）
# 3) 重构：把 add/count 的内部结构调顺（仍然是绿）
```

| TDD 步骤 | 对设计的挤压 |
| --- | --- |
| 测试跑不完的代码不可合并 | 强制小步 |
| 要测就得能注入依赖 | 强制 `11-系统.md` 的构造/使用分离 |
| 测试要快 | 强制无副作用（`03-函数.md` 3.7） |
| 测试要短好读 | 强制 `03-函数.md` 的短函数与小类（`10-类.md`） |

一个可执行的「迭进纪律」：

| 频率 | 动作 |
| --- | --- |
| 每次提交 | 全量构建 + 测试（10 分钟内） |
| 每天 | 至少一次可部署的构建 |
| 每次需求 | 拆成 ≤ 3 天的可上线小步 |
| 每两周 | 检视一次「架构上欠了什么债」，只还一笔 |

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1975 | Brooks，*The Mythical Man-Month*「没有银弹」——本章 12.2/12.3 的论证基础 |
| 2001 | 敏捷宣言发布；同年极限编程把「小步快跑」变成共识 |
| 2001 | 绞杀者模式（Strangler Fig）在 Fowler 的 *Refactoring* 中正式命名 |
| 2010 | Fowler 完善 Strangler Pattern 与「并行运行」等迁移模式 |
| 2012 | 持续集成的实践标准化（Martin Fowler 的 CI 文章在 2006 已定义） |
| 2014–2017 | DevOps 与《持续交付》（Humble & Farley，2010）让「每次都可发布」成为工程标准 |
| 2015 | 微服务与容器化让「绞杀者」实现成本大幅下降 |
| 2017 | *Clean Architecture* 出版，把「依赖方向」的规则形式化 |
| 2019 | 「演进式架构」（*Building Evolutionary Architectures*，2018）引入「架构 Fitness Function」 |
| 2023–2026 | AI 辅助重构让小步迁移更可行；「先生成、再收敛」成为新的迭进形态 |

## 近年研究与工业界开源实践（2015–2026）

趋势：**「可发布」的门槛被工具降到接近零**（CI/CD + 特性开关 + 渐进发布），这让「迭进」比 2008 年更容易做到；同时，架构治理又从「经验判断」转向「可度量的 Fitness Function」。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `pre-commit/pre-commit` | **15,594★** | 迭进的**速度上限**：提交前反馈越快，小步越可行 |
| `psf/black` | **41,851★** | 无人值守的一致性，让「每次都顺手改一点」不引发争论 |
| `github/codeql` | **10,122★** | Fitness Function 的实现载体：把架构规则写成可执行查询 |
| `sonarsource/sonarqube` | **11,024★** | 持续度量技术债，支撑「每两周还一笔」的节奏 |
| `golang/go` | **138,994★** | 语言自带工具链降低「先编译再决定」的成本 |
| `qodo-ai/pr-agent` | **13,146★** | AI 让「每次 PR 顺手清理」的边际成本下降 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **「BDUF 一律不好」过于绝对** | 对于合规、数据迁移、分布式事务这类**改起来代价极高**的领域，前期设计不可省 | 区分「易变的部分（代码）」与「难变的部分（协议、schema、法规）」 |
| 2 | 🔧 **几乎没有讲遗留系统的启动路径** | 本章假定新项目；现实中「从一堆坏代码开始迭进」才是常态 | 补读《Working Effectively with Legacy Code》；先用绞杀者模式 |
| 3 | 🔧 **对「持续集成」的描述停留在 2008 年** | 当时的 CI 是一台构建机；今天是流水线 + 灰度 + 特性开关 | 把「可发布」拆解为可验证的流水线阶段 |
| 4 | 🔧 **「绞杀者」缺少具体的路由/回退机制** | 只有概念，没有双写、对比、回退的实现细节 | 结合特性开关与影子流量实践 |
| 5 | 🔧 **AI 时代「小步」的定义变了** | 一次 AI 生成可能一次产出上千行，迭进的粒度需要重新定义 | 把 AI 输出切成「一个 PR 一个意图」，先过测试再合并 |
| 6 | **「TDD 是设计工具」被大量读成「TDD 是为了测试」** | 这是本章最容易被误读的一句 | 关注可测性带来的设计约束，而不是覆盖率数字 |
