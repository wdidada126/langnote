# 第 8 章 边界

> **一句话**：你的代码与第三方库/框架/旧接口之间有一条**契约边界**——边界上的代码要由**你**拥有，否则每次上游升级，你都要跟着重构。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 8.1 边界与测试 | 在边界处写测试（「学习测试 / Learning Test」），用测试来「实验」第三方 API | 先写测试理解 API，再把它包起来 |
| 8.2 学习与探索 | 拿一份 API 写几个小程序来验证行为；作者用 JUnit 写学习测试的过程 | 把「试探」变成自动化测试，而不是注释掉的实验代码 |
| 8.3 边界与代码结构 | 不要把第三方类型泄漏到你的模块里；写薄适配器 | 「你的代码」与「他们的代码」要能在文件中区分 |
| 8.4 不要跨越边界传递内部结构 | 别把你的领域对象直接塞给框架 API | 传值、传 DTO、传接口 |
| 8.5 边界的边界 | 边界分层：库边界、框架边界、系统边界 | 每跨一层，就要重新定义契约 |
| 8.6 不透明的边界 | 「保证向后兼容」的接口只会不断加参数、不删旧方法，最终变得难用 | 长期收益差，但往往是唯一可选项 |
| 8.7 小结 | 为边界写测试、把边界包起来、保持边界清晰 | 边界是「防御性设计」的第一现场 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：学习测试（8.1 / 8.2）——作者最有实践价值的一段。

```java
// 教学示意，不参与构建：用测试来理解第三方 API 的实际行为
// 我在探索 LegacyLib.calculate() 到底对边界值做什么
@Test
void legacyLib_behavesSurprisinglyOnEmptyInput() {
    assertThat(LegacyLib.calculate("")).isEqualTo(-1);   // 没人料到的行为
    assertThat(LegacyLib.calculate(null)).isEqualTo(0);  // 更没人料到：不抛异常
}
```

这些测试有两个作用：① 教读者这个 API 的真实行为；② 上游升级时，一眼看出行为**有没有变**（回归哨兵）。

示例二：把第三方 API 包成你自己的接口（8.3 / 8.4）。

```python
# 教学示意，不参与构建：反例 —— 第三方类型泄漏到业务代码里
def fetch_invoice(client_id: str) -> HttpClientResponse:   # 泄漏了库类型
    resp = third_party.get(f"/clients/{client_id}/invoice")
    return resp

# 正例：定义一个属于「我」的最小接口，把第三方隔离在边界文件里
class InvoiceGateway:
    def fetch(self, client_id: str) -> bytes: ...         # 我拥有的契约

class ThirdPartyInvoiceGateway(InvoiceGateway):           # 唯一的边界文件
    def fetch(self, client_id: str) -> bytes:
        resp = third_party.get(f"/clients/{client_id}/invoice")
        return resp.bytes_body()                          # 在这里做转译
```

示例三：边界处的错误转译（与 `07-错误处理.md` 合并看）。

| 层 | 职责 |
| --- | --- |
| 你的领域 | 抛自己的异常，不认识第三方异常类名 |
| 网关/适配器 | 在这里把第三方异常转成你的异常，**保留根因** |
| 接口出口 | 在这里把异常映射成状态码/错误码 |

示例四：边界的三种典型形态（8.5）。

| 边界 | 典型风险 | 防御手段 |
| --- | --- | --- |
| 库边界（JSON 库、日志库） | 升级改行为 | 学习测试 + 包裹 |
| 框架边界（Web 框架、ORM） | 侵入你的对象（注解、基类、生命周期回调） | 少用注解、避免继承框架类，用适配层 |
| 系统边界（HTTP/消息/DAO） | 格式变化、脏数据 | 校验在边界（DSL/JSON schema）+ DTO 转领域对象 |

一个可执行的边界清单：

- 每个外部依赖，代码里只应有**一个**文件知道它的具体类名（用 grep 验证）。
- 每个外部依赖，都要有「行为回归测试」。
- 边界文件之外，禁止出现第三方包名。
- 边界处的**输入一律假设为脏**：做校验，做归一化。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **「包起来」的成本被低估** | 为每个库都写一层适配器，会产生比原库还厚的代码（典型如 JSON 库适配层） | 只包**你真的不确定行为**的部分；稳定的纯函数库可以不包 |
| 2 | 🔧 **学习测试在 CI 里没有和普通测试同等待遇** | 学完 API 就把测试删掉，上游升级时完全无感 | 把学习测试保留在回归套件里，标注「upstream behavior」 |
| 3 | 🔧 **框架边界的讨论不足** | 本章主要讲库边界，对「框架侵入我的领域对象」（注解、基类、生命周期回调）着墨少 | 参考 Ports & Adapters / Clean Architecture 的框架层约定 |
| 4 | 🔧 **对「兼容性承诺」的批评过于乐观** | 现实中很多库不能因为你的抱怨就改 API；「不透明边界」常常是唯一可选项 | 「不透明」时改用适配层 + 契约测试，而非期待上游修 |
| 5 | 🔧 **没讲网络边界/脏数据校验** | 「边界」在今天也指 HTTP 输入、消息体、文件导入 | 在边界加 schema 校验与限流/超时/重试策略 |
| 6 | 🔧 **AI 生成的胶水代码让边界层失控** | 每个 LLM 调用都容易生成「直接 import 第三方类型」的代码 | 用 lint 规则禁止核心包 import 外部库，AI 输出也必须过 |
