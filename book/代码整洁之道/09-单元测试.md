# 第 9 章 单元测试

> **一句话**：测试代码是这个系统的**规格与护栏**——它必须与生产代码同样整洁，否则它撑不了三个月，之后就成了没人敢碰的噪音。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 9.1 TDD 三定律 | ① 在写产品代码前先写会失败的单元测试 ② 编译不过就别写产品代码 ③ 当前测试通过就重构 | 测试先行的目的不是「测」，而是**逼出设计** |
| 9.2 清洁测试的 Five Rules | ① 构建（Build）必要对象 ② 运行（Run）被测试代码 ③ 修改（Modify）状态并断言 | 三段式结构：Build–Operate–Check（即 Arrange-Act-Assert） |
| 9.3 单一的断言 | 一个测试只测一种行为 | 断言多不等于覆盖全 |
| 9.4  fast / idempotent / isolated | 测试要快、要可重复、要互相独立 | 慢测试与共享状态是测试腐化的头两条 |
| 9.5 可读的测试 | 用「五行内的测试」作为可执行的规格说明 | 把测试当代码文档写 |
| 9.6 一行为一行为地构造（Ockham） | 用最小对象构造测试（不用整体对象的全字段构造） | 别为测试造巨型 fixture |
| 9.7 概念与数据的分离 | 测试构造与断言使用两种不同的语言 | 构造用领域语言，断言用词表 |
| 9.8 测试的策略 | 每个测试类对应一个「重要的边界条件」；别为 getter/setter 写测试 | 测试密度跟着边界走 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

示例一：Arrange-Act-Assert（中译本里叫 Build–Operate–Check）。

```python
# 教学示意，不参与构建
def test_transfers_do_not_overdraft():
    # arrange：构造必要的对象（只造这一个测试用得上的）
    account = CheckingAccount(overdraft_limit=0)
    other = SavingsAccount(balance=100)

    # act：运行被测试的行为
    account.transfer(200, other)

    # assert：用「行为」断言，而不是用「字段值」断言
    assert account.balance == 0
    assert not account.is_overdrawn()
```

示例二：五个名字相似的测试方法，却不是重复代码（9.2 的核心论点——**测试的重复是可以接受的，语义的重复不接受**）。

```java
// 教学示意，不参与构建：每个测试只说一件事，彼此不共享判断逻辑
@Test void depositIncreasesBalance()      { ... }
@Test void depositRejectsNegative()       { ... }
@Test void withdrawAtLimitIsAllowed()     { ... }
@Test void withdrawOverLimitIsRejected()  { ... }
@Test void withdrawUpdatesLastOperation() { ... }
```

对照：如果两个测试共享一段「划线检查」的私有方法，那说明其中一条该删了——**测试之间不该互相解释**。

示例三：构造最小化（9.6 / 9.7）。

| 反例（巨型 fixture） | 正例（最小构造） |
| --- | --- |
| 每个测试都 `new Customer(name, id, address, tier, joinedAt, ...)` 12 个字段 | 测试只关心 `balance`，就只构造 `new Account(100)` |
| 测试之间共享一个大 fixture，改一个字段影响另一条测试 | 每条测试自备最小上下文（isolated） |
| 断言用 `assertEquals("2020-03-01", date.toString())` | 断言用 `assertDateIs(date, LocalDate.of(2020,3,1))`（依赖词表） |

示例四：不写哪些测试（9.8）。

| 不写测试的 | 要写测试的 |
| --- | --- |
| 空方法、getter/setter 这类无逻辑的存取 | 有分支、有边界、有异常路径的 |
| 纯配置常量 | 状态机、金额计算、权限规则、并发时序 |
| 框架的胶水代码（由框架自己的测试覆盖） | 你写的一切「跨模块契约」 |

一个可执行的测试纪律（可直接进 CI）：

| 检查项 | 阈值建议 |
| --- | --- |
| 单个测试方法行数 | ≤ 10（含注释） |
| 测试文件与生产文件之比 | 1:1 起步（TDD 的常见经验值，非硬指标） |
| 测试运行时间 | 单元层 < 10 分钟 |
| 断言可读性 | 一句断言一句说明 |
| 覆盖率 | 不追 100%，追「分支 + 异常路径」覆盖 |

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 1999 | Kent Beck 的 *Extreme Programming Explained* 让「测试先行」进入主流词汇 |
| 2002 | *TDD: By Example* 出版；同年 Cooke 开始把「测试金字塔」的形状在社区会议中讲开 |
| 2003 | Beck 与 Gamma 的 JUnit 直接影响本章的示例语言 |
| 2008 | 本章出版；「测试代码也是生产代码」成为共识 |
| 2009 | Mike Cohn 的 *Succeeding with Agile* 让测试金字塔广泛传播 |
| 2011 | 《Working Effectively with Legacy Code》补上「给没有测试的代码加测试」，《Clean Code》的默认前提由此外推 |
| 2014 | testify / RSpec / pytest 等各语言测试框架成熟，三段式结构被语言惯用法固化 |
| 2017 | Google 的「测试金字塔」以内部实践文档形式外流，成为讨论「测试分层」的通用参考 |
| 2020 | 「测试金字塔的失败形态」（雪崩形、甜筒形）（雪花、甜筒）成为讨论热点：分层被拆开又合并、比例失控 |
| 2022–2026 | 快照测试与「AI 生成测试」流行，带来新的可读性/维护性问题；金字塔的讨论从「比例」转向「谁拥有哪种测试」 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **把「一个测试一个断言」理解成极窄** | 严格到「只断言一个字段」会产生大量样板测试 | 语义上「一件事」即可，允许一次断言一组相关结果 |
| 2 | 🔧 **TDD 三定律被当成流程打卡** | 「先写红测试」在很多团队退化成「先写测试再写实现」的形式主义，甚至先补测试再一起提交 | TDD 的真价值在「逼出可测的设计」，关注点应在可测性上 |
| 3 | 🔧 **几乎没有讲「测试变慢 / 无法并行」的问题** | 共享数据库、固定时间、随机种子都会让测试不可重复 | 测试隔离依赖：固定时钟、每次新建 fixture、避免共享资源 |
| 4 | 🔧 **没有讲「测试的类型分层」** | 本章通篇是「单元测试」，对集成/E2E/契约测试的分工与取舍少有讨论 | 结合测试金字塔阅读，`12-迭进.md` 的持续集成一节也在讲这个 |
| 5 | 🔧 **AI 生成测试的典型问题书里没有** | LLM 爱写「跑通即结束」的弱断言、快照无限膨胀 | 建立「断言必须可解释」的 review 标准；限制快照体积 |
| 6 | **对遗留系统几乎无解** | 假设你已经有可测的代码结构，现实中多数团队面对的是无测试的老代码 | 补上《Working Effectively with Legacy Code》的缝隙测试技巧 |

## 与其他章 / 其他书的联系

- 9.1 的 TDD 三定律是 `01-整洁代码.md` 里「整洁 = 有测试」的执行手段，也是 `12-迭进.md` 的核心论据。
