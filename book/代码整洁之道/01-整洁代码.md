# 第 1 章 整洁代码

> **一句话**：代码存在的唯一理由是「被人读懂」，所以衡量代码的第一标准不是它有多聪明，而是**别人（尤其一年后的你自己）读它时，能不能一次读懂**。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 要有代码 | 「我们从来没想过要写这么多代码」，但代码终究不可避免 | 承认代码的存在成本，别指望「零代码」方案绕过复杂性 |
| 1.2 糟糕的代码 | 糟糕的代码能跑，但会让团队泥足深陷 | 运行正确 ≠ 干净；两者是不同的维度 |
| 1.3 混乱的代价 | 混乱让新增功能越来越贵（「瀑布式贬值」） | 每拖一天，改动成本指数级上升 |
| 1.3.1 华丽新设计 | 有人提议重写/换框架来「解决」混乱，但新设计同样会腐化 | 只有持续清理，没有一劳永逸的重构 |
| 1.3.2 态度 | 「等以后再说」是专业失职 | 程序员对自己的产出负有保养义务 |
| 1.3.3 迷题 | 混乱代码导致的调试/理解成本是可估算的 | 用「别人读这段代码要多久」来量化 |
| 1.3.4 整洁代码的艺术 | 整洁的代码是**测试通过、语义直白、没有重复、表达清晰、布局得当**的代码 | 整洁是「可读性」而非「优雅感」 |
| 1.3.5 什么是整洁代码 | 让读者能按作者的原意理解，而不是反过来猜 | 整洁是一种**社交责任** |
| 1.4 思想流派 | 作者承认自己的立场属于「写整洁代码的少数派」 | 规则是流派的产物，不是普世律令 |
| 1.5 我们是作者 | 程序员是作者，读者是 patrons（赞助人），读者时间最贵 | 为读者写作，就像作家为读者写作 |
| 1.6 童子军军规 | 营地离开时比来时干净；代码同理 | 每次改动顺手清理一小片，不必等「重构周」 |
| 1.7 前传与原则 | 引用 SOLID：单一职责、开闭、里氏替换、接口隔离、依赖倒置 | 本章是全书的原则索引 |
| 1.8 小结 | —— | 把整洁当成习惯，而不是项目 |
| 1.9 文献 | 引用的外部文献 | 见「经典论文与原始文献」 |

## 核心精讲

> **教学示意，不参与构建、不编译、不运行。**

本章几乎不写功能代码，写的是「态度」。真正能落地的是童子军军规，下面是一个把它写进工程流程的最小骨架（示意）：

```java
// 教学示意，不参与构建：童子军军规的工程化落地
// 与其写成口号，不如写成「每次提交必须回答的两个问题」

// 反例：一次性承诺「下次一定清理」
// TODO: 这里以后要重构一下（三个月后没人记得 TODO 是谁写的、想做什么）

// 正例：把清理拆成「看得见、可验收」的小步
public void processOrder(Order order) {
    validate(order);          // 1. 校验
    charge(order);            // 2. 扣款
    notify(order);            // 3. 通知
}

// 童子军军规的量化版本：每次 PR 只做「一次小清理」
// - 删掉一个死方法
// - 给一个含糊的方法改名
// - 拆掉一块重复逻辑
// 规则：清理量不超过本次业务改动量的 10%，否则另开 PR
```

一个判断标准，可以直接拿来做 code review 的问题清单：

| 症状 | 为什么它是「不整洁」 |
| --- | --- |
| 一段逻辑需要读三处才敢改 | 知识分散（duplication） |
| 改 A 功能却必须同时改 B 处的字符串 | 耦合未隔离 |
| 方法名和它做的事对不上 | 读者要猜（intention-revealing） |
| 修改需要连带修改 5 个文件的注释 | 注释与代码脱钩 |
| 满屏 `if (flag == 1)` 却没人知道 1 是什么 | 魔法数字（见 `02-有意义的命名.md`） |

## 近年研究与工业界开源实践（2015–2026）

趋势：把「整洁」从**个人品味**迁移到**流水线约束**。代码审查里关于格式与命名的争论，已被格式化器与 linter 接管；人类评审者的时间转向「正确性、边界、意图」。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `astral-sh/ruff` | **49,779★** | 一次跑完 lint + format，让「格式不整洁」不再需要人来判断 |
| `psf/black` | **41,851★** | 「不合作式」格式化器，直接消灭风格争论 |
| `pre-commit/pre-commit` | **15,594★** | 童子军军规最实用的落地形式：提交前自动清理 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 说明 | 修正建议 |
| --- | --- | --- | --- |
| 1 | 🔧 **「童子军军规」被当成免检牌** | 军规原意是「顺手清理」，实践中常被用来给**无关重构**开绿灯，一次 PR 塞进 300 行清理 | 限定「清理量 ≤ 本次业务改动 10%」，超出必须拆 PR |
| 2 | 🔧 **「整洁是社交责任」缺少可度量的落点** | 「让读者能读懂」无法被评审、无法被度量，容易退化为主观争执 | 用可自动化指标兜底：单函数长度、文件长度、重复率、覆盖率 |
| 3 | 🔧 **对「华丽新设计」的批判过头** | 作者认为重写不能解决问题，但现实中存在「技术栈必须迁移」的硬性约束（EOL 运行时、合规要求） | 重写该做时就做，但用绞杀者模式（见 `12-迭进.md`）降低风险 |
| 4 | **「我们是作者」的隐喻有排他性** | 隐喻暗示只有写代码的人负责；实际维护中存在大量只读不改的调用方与运维脚本 | 扩展为「所有让代码存在的人都是读者」 |
| 5 | 🔧 **整章没有任何并发/性能视角** | 「整洁」被默认为「慢一点没关系」；在热路径上，为了可读性做的抽象可能带来数量级开销 | 性能敏感处标注成本预算，见 `book/C++并发编程实战2/` |
| 6 | **AI 辅助编码后，「写」变便宜，「读」的分发变了** | Copilot 生成的风格不整齐、含大量样板，反而放大了「读成本」 | 把格式/命名规则交给工具强制（见上文 toolchain），人只看意图 |
