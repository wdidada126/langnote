## 核心概念速览（中英对照）

- **模板方法** — Template Method：骨架算法固定在基类的非虚函数里，可变步骤延迟到子类
- **骨架算法** — skeleton algorithm：流程顺序不可变的那部分（init→update→render→shutdown）
- **原始操作/步骤** — primitive operation：骨架调用的虚函数，子类填空处
- **钩子** — hook：有默认实现、覆写可选的步骤（本书重构路径里「空函数默认版」即是）
- **非虚接口** — NVI（non-virtual interface）：公开非虚、私有虚——防止子类破坏骨架
- **多态** — polymorphism：虚函数 + 继承 = 运行期按对象实际类型分派
- **控制反转** — inversion of control：「别调用我们，我们会调用你」（GoF 对 Template Method 的引语）
- **CRTP** — Curiously Recurring Template Pattern：编译期模板方法，static_cast 到派生类
- **策略模式** — Strategy：模板方法的「整块可换」兄弟（第 4 章，对照见下）
- **游戏主循环** — game loop：update/render 帧循环——本章的教学载体（2.1 案例主题按小节标题为逐步重构范例 ⚠️具体游戏细节未核实）

## 动机：从一个「复制粘贴的循环」开始

按已核实的小节标题，2.1 的走法是典型的「坏味道示范」：项目里有两三份结构相同的代码——
初始化、循环体、收尾，每个模块各自复制一遍，只在个别步骤上不同（例如不同玩法模块的
update 内容不同）。复制的代价在第三次出现时才显形：改流程要改 N 处，改漏一处就是线上事故。

重构阶梯（本书教学法的核心，可复演）：

1. 把重复的**流程骨架**抽成基类函数（run）；
2. 把差异的**步骤**抽成纯虚/虚函数（onUpdate/onRender/onInit/onShutDown）；
3. run 声明为非虚——骨架不可被覆写（NVI 思想）；
4. 有通用默认的步骤给空默认实现（钩子），子类只写自己的差异。

得到的结构就是 GoF 的 Template Method：**行为参数化**——基类定义算法家族的结构，
子类定义算法家族的步骤内容。

## 机制：结构 + 🔧代码（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
class GameLoop {
public:
    virtual ~GameLoop() = default;
    void run(int frames){                       // 模板方法：骨架固定在基类
        if (onInit()){ for (int i=0;i<frames;++i){ onUpdate(i); onRender(i); } onShutDown(); }
    }
protected:
    virtual bool onInit(){ return true; }        // 钩子
    virtual void onUpdate(int) = 0;
    virtual void onRender(int) = 0;
    virtual void onShutDown(){}
};
class DemoLoop final : public GameLoop {
public:
    bool onInit() override { std::cout << "init assets\n"; return true; }
    void onUpdate(int f) override { std::cout << "update " << f << "\n"; }
    void onRender(int f) override { if (f==1) std::cout << "render frame1\n"; }
};
```

运行输出（实测）：`init assets / update 0 / update 1 / render frame1`。
要点：**调用方向反转**——子类的代码从不被 main 直接调用，而是被基类骨架在正确时机回调；
这与「你调用库」的普通复用划清界限，也是框架（framework）与库（library）的分界定义。

## 权衡：模板方法的账本

| 收益 | 代价 |
| --- | --- |
| 流程只写一遍，改骨架 = 改一处 | 骨架被钉死：想换步骤**顺序**必须动基类（OCP 违背） |
| 子类只表达差异，代码量最小 | 每多一个子类多一套 vtable 间接调用（性能可忽略、认知成本高） |
| 钩子提供「可选项」，默认行为集中管理 | 步骤签名是基类定的契约，子类间互相「看不见」，难调试回调栈 |

**换序需求出现时该迁到哪**：把「整段可变流程」外置成对象 → Strategy（第 4 章）；
把「步骤集合」做成数据 → 命令队列（第 7 章）。三者的选择线：**流程顺序稳定 → Template Method；
顺序与内容都要换 → Strategy；顺序由运行期数据决定 → Command**。

## 相邻概念对比

| 对比项 | Template Method | Strategy | Factory Method |
| --- | --- | --- | --- |
| 变化点 | 算法的**步骤内容** | 算法**整体** | 实例化的**具体类** |
| 机制 | 继承 + 虚函数（白箱） | 组合 + 接口（黑箱） | 虚函数只管「造」这一件事 |
| 粒度 | 粗（框架级） | 细（可逐对象换） | 单点 |
| GoF 原话 | 「行为参数化」 | 「算法族可互换」 | 「延迟到子类」 |
| 本书位置 | 第 2 章 | 第 4 章（4.2 专讲 DIP） | 第 3 章 |

## 最新演进与工业实践

- **CRTP：编译期模板方法**（已实测 g++ 15.2）：

```cpp
template <class Derived> struct LoopCRTP {
    void run(int frames){
        self().onInit();
        for (int i=0;i<frames;++i) self().tick(i);
    }
    Derived& self(){ return static_cast<Derived&>(*this); }
};
struct Mini final : LoopCRTP<Mini> {
    void onInit(){}
    void tick(int i){ out += i; }
    int out = 0;
};   // Mini m; m.run(3); → out == 3，零虚表、可内联
```

- **C++20 之后**：concepts 可把 CRTP 的「契约」写明白（`requires Derived::tick` 之类），
  补上「忘写步骤就得到天书错误」的老坑；纵深见 [../C++20模板元编程.md](../C++20模板元编程.md)。
- **引擎里的活样本**：Unreal Engine 的 Actor 生命周期钩子（BeginPlay/Tick 等，公开文档）就是
  模板方法——引擎钉死帧循环骨架，游戏代码填钩子；Unity 的 MonoBehaviour 同理（托管语言侧对照，
  另见 [../spring5设计模式.md](../spring5设计模式.md) 里 Java 框架的模板方法用例）。
- **被吸收的程度**：主循环骨架至今没有语言设施能替代（顺序是语义本身），
  这是 Template Method 在 2026 年仍然每天被手写的原因之一。
