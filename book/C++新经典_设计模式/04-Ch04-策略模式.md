# 第 4 章：策略模式（含依赖倒置原则）

> 对应原书第 4 章（✅ 已核实目录：4.1 一个具体实现范例的逐步重构 / 4.2 依赖倒置原则）。
> 大纲形态：[../C++新经典_设计模式.md](../C++新经典_设计模式.md)；导航：[../C++系列·总索引.md](../C++系列·总索引.md)。

## 核心概念速览（中英对照）

- **策略** — Strategy：一族可互换算法的接口封装，算法与使用者解耦
- **算法族** — algorithm family：同一问题域内目标相同、做法不同的实现集合（追击/逃跑/巡逻）
- **上下文** — Context：持有策略引用并在恰当时机委派的结构（本书的「怪物 AI 宿主」位）
- **依赖倒置原则** — DIP（Dependency Inversion Principle）：高层不依赖低层具体类，二者依赖抽象；
  抽象不依赖细节，细节依赖抽象（4.2 专节，本书把它放在策略之后不是偶然）
- **开闭原则** — OCP（Open-Closed Principle）：对扩展开放、对修改关闭——策略是其最大股东
- **运行期切换** — runtime switching：换策略不换宿主对象，与编译期选型相对
- **std::function**：C++11 后「一个函数就是一个策略」的最小载体
- **lambda 捕获** — lambda capture：无状态策略连类都不用写
- **策略模板/政策类** — policy-based class：把策略升格为模板参数，编译期选型（Andrei Alexandrescu
  《Modern C++ Design》的遗产，中文圈常称「策略模式模板化」）
- **concepts 约束** — C++20 concepts：给编译期策略装上「接口契约」

## 动机：AI 分支地狱的逐步重构

4.1 的标题就是全书公式：**先给一段 if-else/switch 按怪物类型选行为的代码**，
逐步重构到策略。典型的坏味道演进（按小节主题教学化转述 ⚠️非原文）：

1. `switch (monsterType)` 把「行为」和「类型」焊死——新怪 = 改主循环；
2. 行为被提到虚函数 `move()`——好了一点，但行为仍然**跟类型绑定**，
   同一只怪「狂暴时直线冲、平时巡逻」换不了；
3. 把「怎么动」再抽出一个**独立对象**（Strategy），宿主只持引用——类型与行为解耦，
   行为可以运行期任意组合、单独测试、单独复用。

第 3 步即 GoF 定义：「定义一系列算法，把它们一个个封装起来，并且使它们可互相替换」。
4.2 用 DIP 收束：**宿主（高层）依赖抽象策略，而不是具体 AI 实现**——
策略模式是 DIP 最直白的成例，这就是本书把二者放同一章的原因。

## 机制：三层载体 🔧（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
struct MoveCtx { double x, y; };
using MoveStrategy = std::function<void(MoveCtx&)>;   // 载体一：函数
void chase(MoveCtx& c){ c.x += 1.0; }
void flee (MoveCtx& c){ c.x -= 1.0; }
void patrol(MoveCtx& c){ static int dir=1; c.x += dir; if (c.x>3 || c.x<-3) dir=-dir; }

// 载体二：std::function 容器，运行期随意换
std::vector<MoveStrategy> ss{chase, flee};

// 载体三：编译期策略 + C++20 concepts 契约
template <class T> concept MovePolicy = requires (MoveCtx& c) { { T::apply(c) }; };
struct Rage { static void apply(MoveCtx& c){ c.x += 2.0; c.y += 2.0; } };
template <MovePolicy P> struct Agent {
    void act(MoveCtx& c){ P::apply(c); }
};
```

实测输出（截取）：`mob0 x=1 / mob1 x=0 / patrol x=2 / agent policy x=2 y=2`。
结构要点：GoF 的「抽象基类 + N 个具体策略 + Context 持指针」三件套，
在现代 C++ 里按**状态多少**退化选择：

| 策略有内部状态吗 | 需要运行期换吗 | 最省载体 |
| --- | --- | --- |
| 无 | 否 | 直接函数/lambda |
| 无 | 是 | `std::function`（注意小对象优化边界） |
| 有 | 是 | 抽象基类 + 多态（GoF 原版） |
| 任意 | 否（类型可模板化） | 模板参数（policy）/concepts 约束 |

## 权衡：策略的账单藏在间接里

- 每个策略一次堆分配/虚调用，帧循环里成吨的怪会放大成本——数据导向设计倾向
  「把常选策略编成枚举 + 分支，或分桶批处理」而不是逐对象多态（游戏业真实取舍，
  参见 [../Rust游戏开发实战.md](../Rust游戏开发实战.md) 中 Bevy 系统的批处理思路）。
- 策略间接的**收益侧**：可单测（每个 AI 行为独立断言）、可热换（debug 按键切 AI）、
  可组合（巡逻+视野检查=两个策略叠加，接第 6 章装饰器）。
- 反模式：**一个策略类只有一个方法且只有一对实现**——那是 if-else 的化装，直接写分支。

## 相邻概念对比

| 对比项 | Strategy | Template Method | State | Decorator |
| --- | --- | --- | --- | --- |
| 换的是什么 | 整段算法 | 算法里的步骤 | 随状态换行为**类别** | 不换，逐层加料 |
| 结构 | 一模一样（接口+实现族） | 骨架 vs 填空 | 接口相同、语义不同 | 接口自我包裹 |
| 区分口诀 | 调用方**主动选**算法 | 骨架**回调**你 | 状态机**自动**迁移 | 层层**环绕**同一对象 |

State 与 Strategy 是同构结构的双生子（GoF 也明说）：区别在**谁决定切换**——
调用方决定 = 策略；对象内部状态迁移决定 = 状态（第 9 章正面处理，
对照 [../设计模式GoF/05-策略、状态、模板方法与访客.md](../设计模式GoF/05-策略、状态、模板方法与访客.md)）。

## 选型速查：这四种「看起来像策略」什么时候别用策略

1. **两三个分支、永不再加** → 直接 if/switch；封装成模式是负收益。
2. **行为与类型一一绑定且编译期可定** → 虚函数覆写或模板参数即可，无需独立策略对象。
3. **策略共享大量上下文数据** → 把数据做成 `MoveCtx` 这样的显式上下文（如本文件示例），
   否则策略对象之间会靠全局变量私联——模式的整洁性被掏空。
4. **策略其实是「状态」** → 去第 12 章；策略间彼此知道、由内部迁移，就已经是 State 的语义。

## 最新演进与工业实践

- **lambda 吃掉「策略抽象基类」**：无状态策略一个 `std::function`/模板参数即完事，
  2010 年前教程里的 `IStrategy` 三件套在 C++11 后主要留给**有状态**策略（[../Effective_Modern_C++.md](../Effective_Modern_C++.md)
  item 27-34 的闭包诸条是地基）。
- **concepts 给策略族立契约**：`template <MovePolicy P>` 把「策略必须长什么样」写进签名，
  误用在实例化点、错误信息可读——这是本书 C++11 版策略教程拿不到的新武器（C++20 落地；
  演进纵深 [../C++20设计模式/01-导论-模式体系与C++20惯用法.md](../C++20设计模式/01-导论-模式体系与C++20惯用法.md)）。
- **工业样本**：SDL2/SDL3 的渲染后端以「函数表 + 枚举」在运行期选择实现（公开头文件
  `SDL_renderer` 后端机制，公知形态）；各图形库把「可换行为」装进函数表是普遍做法。
  游戏引擎更常见的现实：AI 策略**数据化**（行为树/状态脚本，UE Behavior Tree、
  各类 GAS 方案，公开文档可查）——策略模式的对象被序列化成了 DSL，模式词汇仍然成立。
- **P2996 静态反射（C++26）**：反射可自动枚举/注册策略实现，「策略注册表」的样板
  （第 3 章 registry）会被元编程替代；方向已核实，逐条影响标 ⚠️推定。
