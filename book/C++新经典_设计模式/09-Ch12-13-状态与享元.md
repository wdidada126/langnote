## 核心概念速览（中英对照）

- **状态模式** — State：对象行为随内部状态改变而「换一套类」，状态各自封装转移规则
- **具体状态** — ConcreteState：一个状态一个类，`handle()` 里干活并**自己决定**下一站
- **环境类** — Context：持当前状态指针、把请求转派给状态对象（游戏角色的宿主位）
- **状态图/状态机** — statechart / FSM：状态+事件+转移+动作的形式化模型
- **状态即单件** — state-as-singleton：无状态的状态类每类型只需一个实例（12.3 的正题）
- **层次状态机** — HSM（hierarchical state machine）：状态可嵌套（攻击⊂战斗），State 模式的复杂化上限
- **享元** — Flyweight：大量细粒度对象 sharing 不变内核 + 外置可变态以省内存
- **内部态/外部态** — intrinsic / extrinsic state：可共享的（字形纹理）vs 每次调用传入的（坐标/字体号）
- **享元工厂/驻留池** — flyweight factory / interning pool：按值查重的登记处
- **驻留** — interning：字符串驻留、图标图集——享元在真实系统里的通称

## 动机一（状态）：12.1「状态转换范例」= if-else 状态机的爆炸

角色有 idle/running/stunned…，每个操作在不同状态下行为不同、且触发不同转移。
朴素写法是巨型 `switch(state)` 嵌 `switch(input)`：状态×事件矩阵散落在每个函数里，
加一个状态要全项目搜索改分支。State 模式的重构方向：**把「状态」做成一等对象**——
每个状态类封装「我在这个状态时怎么响应」+「我把我自己换成谁」；Context 只留一个指针。
GoF 的判定语：「允许对象在内部状态改变时改变它的行为，看起来好像修改了它的类」。

12.3「状态类的单件实现方式」是本章的 C++ 点睛：状态对象**没有每实例数据**
（数据都挂在 Context 上），因此每类型只需一个全局实例——转移时指针换指针，
零构造零析构，顺带躲开状态对象的拷贝/所有权地狱。这一节实际是第 6–7 章单件的一次反向应用。

## 动机二（享元）：13.1「典型的范例」

屏幕上几万个字符，每个字符若都持「字形位图 + 编码 + 字体 + 尺寸 + 坐标」，
内存和加载都爆。字形位图只与「字符本身」有关（内部态），与「在屏幕哪儿」无关（外部态）。
享元：**内部态集中共享，外部态调用时传入**——一个 `a` 只造一次，几万次 `draw(x,y)` 复用。

## 机制：🔧 variant 状态机 + 享元池（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
struct Idle    { std::string name() const { return "idle"; } };
struct Running { std::string name() const { return "running"; } };
struct Stunned { std::string name() const { return "stunned"; } };
using State = std::variant<Idle, Running, Stunned>;          // 封闭状态集，类型即文档
State next(const State& s){
    struct T {
        State operator()(Idle) const { return Running{}; }
        State operator()(const Running&) const { return Stunned{}; }
        State operator()(Stunned) const { return Idle{}; }
    };
    return std::visit(T{}, s);
}
class Glyph {                                                 // 享元：内部态=纹理
public:
    explicit Glyph(std::string t):texture_(std::move(t)){}
    void draw(int x) const { std::cout << texture_ << "@" << x << " "; }  // 外部态=x
private: std::string texture_;
};
// 享元工厂：pool[key] 查重，5 次请求 3 个实例
```

实测输出：`running -> stunned -> idle -> running -> stunned -> idle ->`（转移环）、
`a@0 b@1 a@2 c@3 a@4 / flyweight instances=3`。
GoF 版状态模式（抽象 State + 每状态一个类 + Context 持 `State*`）仍是运行期开放状态集的答案；
上面 `variant` 版是**编译期封闭**状态集的现代答案——两种形态的取舍见权衡。

## 权衡：三种状态实现的 cost curve

| 实现 | 加状态成本 | 加转移成本 | 运行成本 | 适用 |
| --- | --- | --- | --- | --- |
| switch/枚举 FSM | 改所有 switch | 改一处表 | 分支预测友好 | 状态少、性能热路径 |
| GoF State 类族 | 新类不改旧类（OCP） | 同类小改 | 虚调用+指针 | 状态多、行为重、需热换 |
| variant+visit | 改 variant + 所有 visitor | 改一处 | visit 分派（可内联） | 状态封闭、行为常加 |

- **开放轴翻转**（与 Visitor 同题）：State 类族对「加状态」开放、「加事件」封闭；
  variant 对「加行为（visitor）」开放、「加状态」封闭——选型先问哪个轴在长。
- **状态机内建的替代压力**：引擎普遍提供现成 FSM/HSM（UE StateTree、各类行为树，公开文档），
  「手写状态类」的需求萎缩到工具/协议解析等长尾。
- **享元**：现代显存/图集（texture atlas）+ 实例化渲染（GPU instancing）接过了「省内存」的旗——
  CPU 侧共享 + GPU 侧批处理是 2026 版「享元」；纯指针池若带来堆碎片与间接跳转，
  可能不如「按类型 SoA 全量展开」（ECS 思路，接上一章）。

## 相邻概念对比

- **State vs Strategy**（结构相同！）：Strategy 由**调用方**选、彼此不知情；
  State 由**状态对象自己**迁、知道邻居（第 4 文件已铺这条线）。
- **State vs 模板方法**：状态类内部也常用「骨架+填空」复用——组合使用不冲突。
- **Flyweight vs 单件**：单件=类型唯一；享元=**按值**多实例复用（一图池 N 用）。
- **Flyweight vs 缓存/代理（14 章）**：缓存是「算过的留着」，享元是「相同的合并」，
  实现都靠工厂池，语义轴不同（下一章正面处理代理）。

## 最新演进与工业实践

- **`std::variant` + `overload` 惯用法**已成 C++17+ 状态机事实标准写法（`if constexpr`/
  `visit` 均可内联优化；基线见 [../C++17完全指南.md](../C++17完全指南.md)、
  [../现代C++语言核心特性解析.md](../现代C++语言核心特性解析.md)）。
- **协程改写状态机**：游戏 AI 的「巡逻→追击→攻击」序列天然对应协程的
  `co_await`/`co_yield` 挂起点（C++20 已核实）——「显式状态对象」被「隐式挂起帧」替代，
  Unity coroutine 与 UE 协程宏是工业先例（公开文档）；姊妹册的协程观察在
  [../C++20设计模式/12-空对象与观察者.md](../C++20设计模式/12-空对象与观察者.md)。
- **字符串驻留即工业享元**：编译器/符号表/`std::string` SSO 之外，各家引擎的资源名
  `FName`（UE，公开文档）是「按值去重成指针」的教科书级享元实现。
- **反射的旁路**：P2996（C++26）让「状态→行为映射表」可在编译期从类型元数据生成，
  手写转移表的样板有压缩空间 ⚠️（方向核实，工具链成熟度未核实）。
