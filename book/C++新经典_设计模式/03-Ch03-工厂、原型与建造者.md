## 核心概念速览（中英对照）

- **简单工厂** — simple factory：一个函数按参数决定 new 哪个具体类（非 GoF 正典，本书计数的「+1」）
- **工厂方法** — Factory Method：把「造哪个类」的决策延迟给子类/回调
- **抽象工厂** — Abstract Factory：一个工厂产出「一族」相关产品（武器+防具必须成套）
- **产品等级结构/产品族** — product hierarchy / product family：抽象工厂的两条轴（同款多型号 = 等级；不同款 = 族）
- **原型** — Prototype：对象自己复制自己——`clone()` 虚接口（GoF 称 virtual constructor）
- **注册式工厂** — factory with registration：`map<string, function<unique_ptr<T>()>>` 数据驱动的产线
- **建造者** — Builder：分离复杂对象的构造过程与最终表示
- ** Director**：GoF 原版里驱动建造流程的角色（本书与多数现代书一样弱化了它）
- **流式接口** — fluent interface：`Builder& hp(int)` 返回自身实现链式调用
- **指示初始化** — designated initializer：C++20 `MonsterCfg{.hp=150, .mp=80}`，Builder 的免样板对手

## 动机：三个问题串成一条演化线

本章小节标题本身就是一条演化线（3.2.1「通过工厂方法模式演变到原型模式」）：

1. **问题一：main 里全是 if-else new**。刷怪代码按类型分支 `new Goblin()/new Orc()…`，
   加一种怪改一处主干。→ **简单工厂**把分支收进一个静态函数：调用方只依赖字符串/枚举。
   但工厂类仍认识所有产品——每加怪还是改工厂。
2. **问题二：工厂认识所有产品**。→ **工厂方法**把「new 哪个类」下放给每个子类工厂；
   再加**注册表**（map 名字→lambda），新增怪只在注册表登记，主干永不动。
3. **问题三：复制一个已配置好的对象**。工厂从零造；但关卡编辑器里往往是「拿这只精英怪再复制一只」。
   → **原型模式**：`clone()` 让对象自己会复制自己（含多态安全——基类指针也能造出正确子类）。
4. **问题四：对象参数太多**。角色有名字/血量/蓝量/职业/外观…望远镜式构造函数（telescoping
   constructors）参数表爆炸 → **建造者**分步装配，最后 `build()` 一次性验收。

## 机制：一锅五式 🔧（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
// —— 原型 + 注册式工厂（刷怪）——
struct Monster { virtual ~Monster()=default;
    virtual std::unique_ptr<Monster> clone() const = 0;
    virtual std::string name() const = 0; };
struct Goblin final : Monster {
    std::unique_ptr<Monster> clone() const override { return std::make_unique<Goblin>(*this); }
    std::string name() const override { return "goblin"; } };
struct Orc final : Monster {
    std::unique_ptr<Monster> clone() const override { return std::make_unique<Orc>(*this); }
    std::string name() const override { return "orc"; } };
std::map<std::string, std::function<std::unique_ptr<Monster>()>> registry{
    {"goblin", []{ return std::make_unique<Goblin>(); }},
    {"orc",    []{ return std::make_unique<Orc>();    }}};
std::unique_ptr<Monster> create(const std::string& k){ return registry.at(k)(); }

// —— 抽象工厂：装备必须成套 ——
struct Weapon { virtual ~Weapon()=default; virtual std::string desc() const = 0; };
struct Armor  { virtual ~Armor()=default;  virtual std::string desc() const = 0; };
struct IronWeapon final : Weapon { std::string desc() const override { return "iron sword"; } };
struct IronArmor  final : Armor  { std::string desc() const override { return "iron armor"; } };
struct LevelFactory { virtual ~LevelFactory()=default;
    virtual std::unique_ptr<Weapon> makeWeapon() const = 0;
    virtual std::unique_ptr<Armor>  makeArmor()  const = 0; };
struct IronFactory final : LevelFactory {
    std::unique_ptr<Weapon> makeWeapon() const override { return std::make_unique<IronWeapon>(); }
    std::unique_ptr<Armor>  makeArmor()  const override { return std::make_unique<IronArmor>();  } };

// —— 建造者：分步造角色 ——
class Character {
public:
    class Builder;
    std::string name; int hp = 100; int mp = 0;
    Character(std::string n, int h, int m):name(std::move(n)),hp(h),mp(m){}
};
class Character::Builder {
public:
    explicit Builder(std::string n){ c_.name = std::move(n); }
    Builder& hp(int v){ c_.hp = v; return *this; }
    Builder& mp(int v){ c_.mp = v; return *this; }
    Character build(){ return c_; }
private:
    Character c_{"",0,0};
};
```

实测输出：`goblin vs goblin`（clone 成功）、`iron sword + iron armor`（成套）、
`hero hp=150 mp=80`（链式建造）。要点三条：**所有权**统一 `unique_ptr`（造一个拿一个，
杜绝 GoF 原版的裸 new 泄漏）；**注册表**是工厂方法的现代平替（数据驱动代替继承树）；
**clone 的实现**就是拷贝构造（`make_unique<Goblin>(*this)`），深拷贝义务在成员上，
裸指针成员必须手写（见附录章 [14-Ch22-设计模式总结与附录.md](14-Ch22-设计模式总结与附录.md) 的拷贝语意）。

## 权衡：五式的失效边界

- 简单工厂：唯一「违反 OCP」的成员（加产品改 switch），但**最诚实**——产品少于 3 个、
  不开放扩展时它就是正解；这也是它没进 GoF 正典却活在日常代码里的原因。
- 工厂方法（继承派）：C++ 里子类工厂 + 虚函数三件套的文件成本，通常输给注册表方案；
  插件架构（运行时 DLL 造类）才需要它的正统形态（见 [../C++API设计/11-脚本绑定与插件扩展.md](../C++API设计/11-脚本绑定与插件扩展.md)）。
- 抽象工厂：只有当「产品族跨族禁止混搭」是真实需求时才值回票价（铁制武器+铁制防具）；
  否则用两个独立简单工厂即可，别为想象中的「换族」付税。
- 原型：`clone` 的深拷贝正确性是隐性负债（多态成员要逐层 clone）；
  值语义成员（vector/string/智能指针禁 copy 的对象）会让原型寸步难行——先问能不能用配置数据重建。
- 建造者：参数 ≥4 且组合多才有意义；两个参数的对象用 designated initializer 一行完事。

## 相邻概念对比：一张「决策推迟点」表

| 模式 | 推迟的决策 | 决策依据 | C++ 现代平替 |
| --- | --- | --- | --- |
| 简单工厂 | 造哪个类 | 运行期参数 | switch/表驱动函数 |
| 工厂方法 | 谁来造 | 子类身份 | 注册表 + `function` |
| 抽象工厂 | 造哪一族 | 工厂实例选择 | 配置驱动的工厂模板 |
| 原型 | 从零造还是复制 | 已有实例 | 拷贝构造 + 配置模板 |
| 建造者 | 何时算造完 | build() 显式触发 | designated init / 校验后 `expected` |

## 最新演进与工业实践

- **C++20 指示初始化**直接替代大半轻量 Builder：`Character{.name="hero", .hp=150, .mp=80}`，
  编译期顺序无关、缺项可见——但**没有终态校验**，校验需求强（必填项/互斥项）仍是 Builder 或
  step-builder（类型状态机，见 [../C++20设计模式/02-建造器模式.md](../C++20设计模式/02-建造器模式.md)）。
- **C++23 `std::expected`** 给工厂一条不抛异常的失败通道：`expected<unique_ptr<Monster>, Error>
  create(string_view)`——实测样例见 [14-Ch22-设计模式总结与附录.md](14-Ch22-设计模式总结与附录.md)。
- **UE 的注册式工厂**：Unreal 用反射宏（UCLASS + 生成代码）把类名→类的映射表自动化（公开文档），
  等价于本章注册表 + 工厂方法的全部样板，**代价是构建期代码生成器（UBT/UHT）**——
  2026 视角看是「反射吃掉工厂样板」的现役工业案例。
- **游戏数据驱动的现实**：现代管线里「怪」通常不是 C++ 子类而是数据行（配表/ScriptableObject/
  .uasset），工厂只造一种 `Monster` 通用实体 + 加载不同数据——本章 Goblin/Orc 继承树
  在工业界正被「单类 + 数据」方案取代（ECS 一章会正面处理，见
  [08-Ch10-11-迭代器与组合.md](08-Ch10-11-迭代器与组合.md)）。
