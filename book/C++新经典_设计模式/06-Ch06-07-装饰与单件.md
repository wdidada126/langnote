## 核心概念速览（中英对照）

- **装饰器** — Decorator：逐层包裹对象、透明地追加职责，比继承更灵活的「加料」机制
- **组件/具体组件** — Component / ConcreteComponent：被包裹的抽象与原料
- **包裹链** — wrapper chain：装饰器持有同接口内层引用，请求逐层穿过后各自加工
- **透明装饰** — transparent decorator：装饰前后接口不变（GoF 的严格版）；半透明装饰是务实变体
- **单件** — Singleton：全局唯一实例 + 统一访问点
- **Meyers 单件** — Meyers' Singleton：函数内局部 static 返回引用——懒初始化 + C++11 线程安全
- **饿汉式/懒汉式** — eager / lazy initialization：类加载期 vs 首次访问期建实例（7.3 节的中文经典二分）
- **双重检查锁** — double-checked locking（DCLP）：旧时代手搓线程安全懒初始化，7.2 节主题
- **凤凰单件** — phoenix singleton：析构后再次 instance() 重建的续命方案（7.4「内存释放问题」的工业答案之一）
- **魔僧** — Magic Statics：C++11 对函数局部 static 初始化的线程安全保证（DCLP 的历史终结者）

## 动机一（装饰）：6.1「问题的提出」——继承凑不出组合

游戏存档的朴素写法：`RawStream` 想加 base64？派生 `Base64Stream`；想再压缩？
再派生 `ZipBase64Stream`……**排列组合爆炸**——n 种料要 2^n 个类，且「先压缩后编码」
和「先编码后压缩」是两个不同的类（顺序即语义）。装饰模式的解法：
不用继承展开组合，用**包裹折叠组合**——每层装饰器只认识「一个 Stream + 一份自己的工艺」。

重构阶梯（按 6.1→6.2 主题教学化转述 ⚠️非原文）：
1. 抽出统一接口 `Stream`；
2. 装饰器实现同接口 + 持 `unique_ptr<Stream>` 内层；
3. 构造顺序=洋葱顺序：`Zip(Base64(Raw))`，运行输出 `zip(b64(raw(...)))`——实测见下。

## 机制一：装饰 🔧 + 单件 🔧（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
struct Stream { virtual ~Stream()=default; virtual std::string write(std::string data) = 0; };
struct RawStream final : Stream {
    std::string write(std::string d) override { return "raw(" + d + ")"; } };
struct Base64Decorator final : Stream {
    explicit Base64Decorator(std::unique_ptr<Stream> s):inner_(std::move(s)){}
    std::string write(std::string d) override { return "b64(" + inner_->write(std::move(d)) + ")"; }
    std::unique_ptr<Stream> inner_; };
struct ZipDecorator final : Stream {
    explicit ZipDecorator(std::unique_ptr<Stream> s):inner_(std::move(s)){}
    std::string write(std::string d) override { return "zip(" + inner_->write(std::move(d)) + ")"; }
    std::unique_ptr<Stream> inner_; };

class GameConfig final {                 // Meyers 单件：配置中心
public:
    GameConfig(const GameConfig&) = delete; GameConfig& operator=(const GameConfig&) = delete;
    static GameConfig& instance(){ static GameConfig inst; return inst; }
    std::string server{"cn-1"};
private: GameConfig() = default;
};
```

实测输出：`zip(b64(raw(savegame)))`、`server=cn-1`。装饰器侧的要点：**移动内层所有权**
（`unique_ptr` 进构造函数）让包裹链的生命周期自动正确——GoF 原版的裸指针 attach 在
C++11 后没有存在理由。单件侧的要点：`static GameConfig inst;` 一行同时解决
懒初始化、线程安全（magic statics）、退出时析构三件事——**7.2 的双检锁、7.3 的饿/懒之争、
7.4 的释放问题，在 C++11 后全部被这一行吸收**。

## 权衡二（单件）：原书三节问题的 2026 答案清单

| 原书小节（✅标题） | 当年的解法 | 现代答案 |
| --- | --- | --- |
| 7.2 多线程问题 | 双检锁/加锁懒初始化 | 函数局部 static（magic statics，C++11 起语言保证）；DCLP 只剩面试题价值 |
| 7.3 饿汉 vs 懒汉 | 饿汉简单但不懒；懒汉懒但线程麻烦 | Meyers 式两者兼得——之争语义消解 |
| 7.4 内存释放 | 手动 delete/退出钩子 | 静态存储期自动析构；需要「可重建」才上 phoenix；跨 TU 析构顺序仍是真坑（见附录章） |

单件剩下的真问题只有两个：**隐藏依赖**（函数签名不告诉你它碰了全局，单元测试互相污染——
对策是把单件当「组合根的穷人写法」，测试时改传引用/接口）；
**析构顺序**（A 单件析构后 B 单件还调 A=UB——对策是「永不真正析构」的 leaked singleton
或启动期依赖排序）。对单件的总批判见 [../设计模式GoF/06-模式的代价与反模式.md](../设计模式GoF/06-模式的代价与反模式.md)。

## 相邻概念对比

- **装饰 vs 继承扩展**：装饰=运行期、可拆、按层加料；继承=编译期钉死。
- **装饰 vs 适配器（15 章）**：装饰**保持**接口并加强，适配器**改变**接口并翻译——
  一个向内加肉，一个对外换装。
- **装饰 vs 职责链（19 章）**：同为「环绕链」，装饰逐层都干活，职责链找「一个愿意干活的」。
- **单件 vs 静态类**：静态类不可多态、不可延迟、不可换实现；单件是「有身份的实例」。
- **单件 vs 享元（13 章）**：都管「只有一个/很少个」，享元按**值**去重共享，单件按**类型**唯一。

## 最新演进与工业实践

- **ranges view 是 std 化装饰器**：`views::filter | views::transform` 逐层包裹惰性的
  `range adaptor`，与本章 `Zip(Base64(Raw))` 结构同构（C++20 已核实入标准）；
  迭代器管道不需要虚函数——装饰的**运行期多态半边**被模板吸收，留下半边（可换实现）。
  详见姊妹册论证：[../C++20设计模式/06-组合与装饰器.md](../C++20设计模式/06-组合与装饰器.md)。
- **中间件环绕链**：游戏服务器网关（如作者 Linux 卷的「包头+包体」处理链）常用
  `vector<function<Next&>>` 做洋葱中间件——装饰的家族变体（对照
  [../C++20设计模式/09-职责链与命令.md](../C++20设计模式/09-职责链与命令.md)）。
- **单件的工业地位**：UE 的子系统（GameInstanceSubsystem 等，公开文档）仍是单件家族——
  但都挂在「组合根」生命周期下统一管理；2026 工程共识：**全局状态显式化**
  （服务定位器/依赖注入）比散落 `instance()` 可审计。库内 API 层论证：
  [../C++API设计/03-单例与工厂.md](../C++API设计/03-单例与工厂.md)。
- **并发纵深**：双检锁在 C++11 内存模型下的正确性讨论、`call_once` 路线，
  见 [../C++并发编程实战2/00-总览与阅读地图.md](../C++并发编程实战2/00-总览与阅读地图.md)。

## 两个易混点澄清

- **装饰 vs 「继承并重写几个方法」**：后者接口没变但构造期钉死，且基类改一个函数签名
  全体派生遭殃（脆弱基类问题）；装饰每层只依赖**抽象接口**，可测试、可拆链。
- **单件 vs 「一个全局变量」**：单件给出的是**受控访问点 + 构造时机 + 唯一性**三件事；
  全局变量三件皆无。判断某个单件是否该拆，就看这三件事它是否真的用到了——
  多数「顺手写的」单件三件都没用到，那就是个该被注入的对象。
