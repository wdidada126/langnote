## 核心概念速览（中英对照）

- **设计模式** — design pattern：特定语境下反复出现的问题及其解决方案的命名与文档化
- **模式语言** — pattern language：模式互相引用构成的网络（Alexander 建筑学 → GoF 的渊源）
- **抽象思维** — abstraction thinking：把「变化点」从「稳定点」剥离——本书 1.1.2 节的主题
- **重构** — refactoring：不改行为改结构；本书每个模式都从「一个具体实现范例的逐步重构」起步
- **面向对象的七大原则** — SOLID 等 OO 原则：模式是原则的成句答案
- **依赖倒置** — dependency inversion (DIP)：高层不依赖低层的具体构造，都依赖抽象
- **创建型/结构型/行为型** — creational / structural / behavioral：GoF 三大分类（本书 1.2.2 沿用）
- **模式的缺点** — drawbacks of patterns：过度设计、间接层成本、学习曲线（本书 1.1.4 专节，罕见地正面谈）
- **UML 类图** — UML class diagram：本书每章「引入模式」节配标准 OO 记号（原书小节标题多处含 UML 图）
- **编程环境** — development environment：本书基线是 Visual Studio + MinGW/g++ 一路（1.3 节口径）

## 动机：为什么「先讲思想再讲模式」

新手学模式的普遍病灶（1.1.3「学习设计模式普遍存在的问题」正是本书的靶子）：
**背代码**。把 23 个 UML 图背下来后，见到真实代码仍不知道哪块「在痒」。
本书的药方是把自己摆成「陪练」：每个模式先给一段能跑但坏味道的 C++ 代码，
一步步重构到模式结构，让读者**复演问题的出现**，而不是记忆答案。
这一教学法与 GoF 原书「案例-模式-案例」的教科书体（对照
[../设计模式GoF/01-引言与模式系统.md](../设计模式GoF/01-引言与模式系统.md)）不同，
更接近 Bob Nystrom《Game Programming Patterns》的问题驱动体例。

软件开发思想（1.2.1「大型项目的软件开发思想」）在作者语境里 = 作者做了二十多年
网络/游戏项目（见 [../C++新经典.md](../C++新经典.md) 作者介绍）后给出的分治总纲：
先切「会变的部分」与「不变的部分」，再谈用哪个模式命名这个切法。

## 机制：一个最小贯穿例——「战斗日志」的依赖倒置

模式的第一性原理可以用 20 行代码讲完：高层模块（战斗逻辑）不应钉死在低层实现
（控制台打印）上，中间垫一个纯虚接口。🔧 已实测 g++ 15.2（`-std=gnu++20`）：

```cpp
#include <iostream>
#include <string>
struct Logger { virtual ~Logger() = default; virtual void log(const std::string&) = 0; };
struct ConsoleLogger final : Logger {
    void log(const std::string& s) override { std::cout << "[console] " << s << "\n"; } };
struct Battle {
    explicit Battle(Logger& lg):lg_(lg){}
    void run(){ lg_.log("player attacks goblin"); }
    Logger& lg_;
};
int main(){ ConsoleLogger lg; Battle b{lg}; b.run(); }   // [console] player attacks goblin
```

要换「写文件」「发到战报服务器」，`Battle` 一行不改——这就是第 4 章策略、
第 11 章桥接、第 5 章观察者共同的母题：**找到那个「还要变」的轴，把它做成接口或模板参数**。
本书后面 24 个模式，本质都是这句的不同变体。

## 常见误区（本目录补写，供复演时对照）

1. **「模式=设计水平的证明」**：评审代码时以「你连策略模式都不用」开场是反模式；
   模式是沟通词汇不是勋章（本书 1.1.4「设计模式的缺点」正是此意 ⚠️按标题转述）。
2. **「学完 24 个就能写出好设计」**：模式回答「重复出现的问题用什么成句答案」，
   但**发现重复**才是难的部分——这需要 1.2.1 的「开发思想」打底。
3. **「UML 图画对就算懂」**：2.3 等章的 UML 节是记谱法；能不看图默写出可编译代码
   （本目录各章 🔧 样例）才算过手。
4. **把「简单工厂」当 GoF 正典**：它不在 23 式之内，本书把它计入 24 个是工程实用主义
   （见 [03-Ch03-工厂、原型与建造者.md](03-Ch03-工厂、原型与建造者.md) 的权衡节）。

## 模式的缺点：把 1.1.4 展开成可执行的自查表

| 代价 | 表现 | 解毒剂 |
| --- | --- | --- |
| 过度设计 | 三行 if 能解决的事套五个文件 | 「问题先于模式」：没痛感不上模式 |
| 间接层阅读成本 | debug 时跳七八层虚调用 | 保持「最简实现先行」的重构顺序 |
| 命名幻觉 | 知道是 Strategy 不等于知道该不该用 | 读 GoF 的 consequences 段而非 structure 段 |
| 时代错位 | 1994 年语言缺口已被 C++11/17/20 补上一部分 | 对照 [../C++20设计模式/01-导论-模式体系与C++20惯用法.md](../C++20设计模式/01-导论-模式体系与C++20惯用法.md) |
| 性能税 | 每帧热路径上的多态/堆分配 | 先测量；热路径用枚举分支/模板（各章权衡节有账） |

## 相邻概念对比：模式 vs 惯用法 vs 原则 vs 算法

- **惯用法（idiom）**：语言特有的小手法（RAII、CRTP、NVI），C++ 特有；模式是跨语言的。
- **原则（principle）**：OCP/DIP/SRP 是「宪法」，模式是「判例」。本书第 4 章用 DIP、第 10 章用 SRP
  专节讲这种承载关系。
- **算法（algorithm）**：算法解题（排序/寻路），模式解**结构**题。游戏里 A* 不是模式，
  「把 A* 做成可替换的 Strategy」才是模式。

## 最新演进与工业实践

- **2026 年的「模式还学不学」**：C++20 concepts、ranges、协程与 C++26 静态反射（P2996，已核实进入 C++26）
  持续「吸收」模式的样板部分，但吸收的是**实现**、不是**词汇**——团队沟通仍需「这里用命令队列」。
  与 [../Effective_Modern_C++.md](../Effective_Modern_C++.md) 的条目体互补：那本讲怎么写好 C++，
  本书讲怎么组织会变的 C++。
- **环境一节的历史局限**：1.3 节以 Visual Studio 为主（2022 年国内游戏公司主流 IDE，属实），
  本目录全部示例改在 **g++ 15.2 / `-std=gnu++20`** 下实测，读者无需 VS 也能复演。
- **教学法的工业印证**：《Game Programming Patterns》（Nystrom，公开免费在线版）同样每章
  「先给坏代码再重构」，是本书讲法在国际上的镜像；两本的模式交集约 14 个（游戏向筛选）。
