## 核心概念速览（中英对照）

- **备忘录** — Memento：在不破坏封装的前提下捕获对象状态，稍后恢复
- **发起人** — Originator：被存档的对象（游戏里的 Hero）
- **负责人/管理者** — Caretaker：保管备忘录、决定何时恢复（存档槽位管理器）
- **窄接口备忘录** — narrow interface memento：GoF 的 C++ 解法——恢复权限只给发起人
  （friend 或只读接口），外界只见「不透明存档块」
- **快照** — snapshot：值语义时代的备忘录——整个状态不可变拷贝一份就是备忘录
- **RAII 令牌** — RAII token / scope guard：离开作用域自动还原——「临时改、必回滚」的现代惯用法
- **职责链** — Chain of Responsibility：请求沿处理者链传递，直到有人处理或链尽
- **处理者** — ConcreteHandler：链上一环，「能办就办，办不了递给下家」
- **单纯 vs 非单纯职责链** — GoF 只定义了「单纯」；19.3 讨论的「非单纯」= 请求可被多环接力修改/
  环绕处理——即现代的**中间件/过滤器链**形态
- **涨薪审批** — raise approval：19.1 的贯穿范例（✅标题），组→经理→老板的审批权限链

## 动机一（备忘录）：存档点与「谁能读档」的权限问题

18.1 的范例主题按标题为「具体实现范例」（⚠️细节未核实），机制通用：游戏要在检查点存档、
死亡后恢复。最笨的做法是把 Hero 所有私有字段公开供外部序列化——**封装当场死亡**。
备忘录的契约：状态捕获由**发起人自己**完成（`snapshot()`），恢复也只接受**自己发的**备忘录
（`restore(const SaveState&)`）；负责人只保管、不解读——GoF 称之为「窄接口」原则。

## 动机二（职责链）：19.1「涨薪审批」= 不知道谁来处理的请求

审批人层级（组长/经理/老板）与「该找谁」是两类会变的知识。调用方硬编码金额分派=
每加一层审批改一遍主干。CoR：每个处理者只认识「我的额度上限」和「下家是谁」，
请求自动向上传导——**发送者与接收者解耦**，链结构即配置。

## 机制：🔧 值语义备忘录 + 审批链（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
struct SaveState { int level; int hp; std::string pos; };      // 备忘录：纯数据快照
class Hero {                                                   // 发起人
public:
    Hero(int l, int h, std::string p):level_(l),hp_(h),pos_(std::move(p)){}
    SaveState snapshot() const { return {level_, hp_, pos_}; }
    void restore(const SaveState& s){ level_=s.level; hp_=s.hp; pos_=s.pos; }
    void fight(){ hp_ -= 10; pos_ += "+fight"; }
private: int level_, hp_; std::string pos_;
};

class Handler {                                                // 职责链抽象处理者
public:
    virtual ~Handler() = default;
    void setNext(Handler* n){ next_ = n; }
    virtual void handle(int amount) = 0;
protected: Handler* next_{nullptr};
};
class Leader final : public Handler { public: void handle(int a) override {
    if (a <= 1000) std::cout << "leader approves " << a << "\n";
    else if (next_) next_->handle(a); } };
class Manager final : public Handler { public: void handle(int a) override {
    if (a <= 5000) std::cout << "manager approves " << a << "\n";
    else if (next_) next_->handle(a); } };
class Boss final : public Handler { public: void handle(int a) override {
    std::cout << (a <= 20000 ? "boss approves " : "all rejected ") << a << "\n"; } };
```

实测输出：`lv1 hp90 village+fight` → `lv1 hp100 village`（恢复成功）、
`leader approves 800 / manager approves 3000 / all rejected 99999`（链自然传导到底）。
现代 C++ 对 GoF 原版「memento 类要防外部访问」的修正：在**值语义 + const**语言里，
「防解读」不再是模式义务（`SaveState` 谁都能看，但没人**该**改），真正的封装线移到
「恢复只能用发起人发的数据」——用类型（`Hero::SaveState` 嵌套类）表达即可。

## 权衡

- **备忘录的拷贝成本**：状态大时快照=全量拷贝；工程分层：
  小对象走值拷贝（如上）、大结构走**持久化层**（序列化到磁盘/DB，内存态只留版本号）、
  热路径走 COW（写时复制）或 diff（只记变化量——编辑器 undo tree 的实现）。
- **undo 的两种世界观**：命令模式（第 7 文件）用「逆操作」做逻辑可逆，
  备忘录用「状态拷贝」做物理可逆——逆操作省内存但要求每操作可逆且顺序无环，
  拷贝白痴友好但吃内存；编辑器工业界常见混合（增量快照）。
- **CoR 的账**：链太长=延迟不可控；调试要回答「请求死在哪一环」。
  19.3「非单纯职责链」的环绕式（每环都能预处理+后处理）是中间件正解，
  但**环的语义不再是「试到我为止」**——两种链的混用是常见事故源，命名时应分开
  （`handler_chain` vs `pipeline`）。
- **RAII 是单对象备忘录的对手**：`{ auto save = cfg.patch(x); ... }` 出域自动还原——
  「临时修改+必回滚」场景（测试夹具、编辑器预览）用 RAII 令牌比手动 restore 更 C++
  （谱系同第 12 文件 06 装饰对 DCLP 的降维打击逻辑）。

## 相邻概念对比

| 对比 | Memento | Command(undo) | State | CoR |
| --- | --- | --- | --- | --- |
| 管的轴 | 状态的时间旅行 | 请求的对象化 | 行为随状态切换 | 请求找处理者 |
| 结构伙伴 | 常与命令搭档（undo 数据面） | 逆命令对 | 无关 | 与装饰/中介/状态都同构（持下家≈持状态） |
| 失效判据 | 状态可重建（配置驱动）时不必存 | 操作不可逆时退化快照 | —— | 发送者早知道该找谁就别用链 |

## 最新演进与工业实践

- **std::span/字节快照**：大块状态的备忘录现代写法是直接 `vector<std::byte>` +
  `memcpy`-安全的 TriviallyCopyable 约束检查（`std::is_standard_layout_v &&
  std::is_trivially_copyable_v`，C++11 起 constexpr 谓词，已核实）——
  「可 memcpy 性」成为存档合法性的编译期门禁。
- **游戏持久化的主流形态**：存档 = 序列化对象（`nlohmann::json`/protobuf 等，公知库），
  Memento 的「恢复」被反序列化接管；模式词汇仍成立：**序列化接口=发起人的 snapshot()**。
- **中间件链吃掉「非单纯 CoR」**：HTTP 服务器（Kestrel/Cascade 等）、asio strand、
  游戏网关的收包处理链（作者 Linux 卷的「包头+包体+业务分派」同款结构，见
  [../C++新经典.md](../C++新经典.md)）全是 pipeline 化职责链——
  Nesteruk 册亦持此论（链接见下）。
- **`std::expected` 做链上失败语义**（C++23）：处理者返回 `expected<Result, Decline>`
  替代静默传递，链尽时错误信息可累积——实测最小版见 [14-Ch22-设计模式总结与附录.md](14-Ch22-设计模式总结与附录.md)。
