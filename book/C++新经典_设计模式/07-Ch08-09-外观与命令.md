## 核心概念速览（中英对照）

- **外观** — Facade：为子系统集合提供一个高层统一入口，降低使用方与子系统的耦合
- **子系统** — subsystem：被隐藏复杂度的一组类（图形/音频/网络…）
- **门面与适配器之辨** — Facade 简化接口（一个→一套），Adapter 翻译接口（一个→另一个）
- **命令** — Command：把「一次请求」对象化——含方法名、接收者、参数、时序
- **接收者** — Receiver：真正干活的对象（扣预算的金币系统）
- **调用者** — Invoker：持有命令、决定何时 `execute()` 的中转（撤销栈/输入映射/网络队列）
- **撤销/重做** — undo/redo：命令对象化的第一红利
- **宏命令** — macro command：一串命令打包成一个命令（组合模式在行为轴的应用）
- **请求队列** — request queue：命令可序列化/跨线程投递——游戏「输入→逻辑帧」解耦的底座
- **配置读取门面** — config facade：8.1「配置相关的范例」的主题位（小节标题已核实，细节 ⚠️未核实）

## 动机一（外观）：8.1「一个配置相关的范例」

启动游戏要按正确顺序碰一串子系统：读配置文件 → 初始化图形 → 起音频 → 连网络，
每个调用方（main、热重启模块、关卡切换）都抄一遍这四步——**散弹式修改**：子系统加一步，
所有调用方都要中枪。外观的答案：给子系统群装一个**唯一正门** `GameEngine::boot()`，
调用方从此只见门、不见屋。

外观的两个纪律（很多中文书不讲）：
1. **别让外观变成万能中间人**——它只做「编排」，不存业务状态，否则退化成上帝对象；
2. **允许高级用户绕过门面**（GoF：想深控时可直接用子系统）——门面对友军不设防。

## 机制：🔧 外观 + 命令（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
class Graphics { public: void init(){} };
class Audio    { public: void init(){} };
class Network  { public: void init(){} };
class GameEngine {                                 // 外观：唯一正门
public:
    void boot(){ gfx.init(); aud.init(); net.init(); std::cout << "engine boot ok\n"; }
private: Graphics gfx; Audio aud; Network net;
};

class Command { public: virtual ~Command()=default;
    virtual void execute()=0; virtual void undo()=0; };
class BuildTower final : public Command {          // 具体命令：绑接收者+参数
public:
    BuildTower(int& budget, int cost):budget_(budget),cost_(cost){}
    void execute() override { budget_ -= cost_; }
    void undo() override { budget_ += cost_; }
private: int& budget_; int cost_;
};
struct Invoker {                                   // 调用者：历史栈
    void run(std::unique_ptr<Command> c){ c->execute(); hist_.push_back(std::move(c)); }
    bool undoLast(){ if (hist_.empty()) return false;
                     hist_.back()->undo(); hist_.pop_back(); return true; }
    std::vector<std::unique_ptr<Command>> hist_;
};
```

实测输出：`engine boot ok / gold=30 / after undo gold=70`（连造 30+40 两座塔后撤销最后一笔）。
命令侧的结构洞察：**「调用」本身成了数据**——于是可以被存储（历史栈）、排队（延迟帧）、
传输（网络帧同步）、记录（操作日志）、参数化（按键映射表）。9.3「命令模式用途研究」
展开的正是这份红利清单；9.3.1「增加对象使用时的独立性」即把接收者与命令解耦
（命令不再直接引用具体对象，而经服务定位/ID 查找回接收者——回放与联机场景的前提）。

## 权衡

- **外观的代价**：多一层薄壳（几乎零成本）；真风险是**边界腐蚀**——子系统间又互相直连、
  只有外部走门面，外观沦为「第四个子系统」。解法：命名纪律（*Manager/Facade 只在装配层出现）。
- **命令的代价**：一个小动作三个类（命令/接收者/调用者）——GoF 承认其对象数量膨胀。
  C++11 后轻量替代：`std::function` 存进栈（无 undo 需求时一行搞定）；
  需要 undo 时「命令对象 + 快照」或「备忘录」混搭。
- **undo 的正确性债务**：execute/undo 必须严格互逆——含随机数、时间、浮点的命令难可逆，
  工业解法常退化为「整状态快照」（备忘录路线，见第 12 文件）。

## 最新演进与工业实践

- **协程吃掉「延迟执行」半边**：命令队列的经典用途（把动作推迟到下一逻辑帧）在现代引擎里
  常写成协程挂起 `co_await next_frame()`（C++20 协程已核实入标准）——动作还保留「可挂起」语义，
  但不再需要显式对象化排队；UE 的 Blueprint 异步节点、Unity coroutine 是托管侧先行者（公开文档）。
  拉取式的「帧队列」另一面见 [../C++20设计模式/09-职责链与命令.md](../C++20设计模式/09-职责链与命令.md)
  与 [../C++20设计模式/10-解释器与迭代器.md](../C++20设计模式/10-解释器与迭代器.md)。
- **命令模式的新战场是网络**：帧同步/状态同步 RTS、MMO 技能系统仍把玩家输入序列化成
  命令流（lockstep 确定性执行）——这恰是 9.3.1「独立性」改造的动机（接收者用 ID 而非指针，
  命令才可序列化）。作者背景（《冒险之路》全球同服，见 [../C++新经典.md](../C++新经典.md) 作者介绍）
  与这条工业线吻合 ⚠️（书中是否展开联机案例未核实）。
- **事件溯源（event sourcing）**：「命令流即真相」的数据库化——命令模式的分布式放大，
  概念谱系见 [../微服务架构设计模式.md](../微服务架构设计模式.md)（saga/命令在另一尺度）。
- **外观的工业名场面**：几乎所有图形 API 的封装层都是门面（SDL 之于平台后端、
  C++23 `std::print` 之于 printf/format）；库边界治理对照 [../C++API设计/04-代理门面与观察者.md](../C++API设计/04-代理门面与观察者.md)。

## 复演提示：两个模式各一条最小路径

- **外观**：先列出调用方重复的「步骤序列」→ 原样搬进一个类的成员函数 → 私有化成员
  子系统、只公开编排函数。全程不许出现业务逻辑，出现了就说明门面开始腐化。
- **命令**：找到「一个动作」（建塔、合成、移动单位）→ 把动作的名字、参数、接收者
  打包成对象 → 把这个对象存进容器（历史/队列/映射表）→ 在容器另一端调用它。
  能存能传，模式就成立了；undo 是可选升级，不是入场券。
