## 核心概念速览（中英对照）

- **桥接** — Bridge：把**抽象侧**与**实现侧**拆成两棵树，用组合（委托）而非继承连接，独立演化
- **正交维度** — orthogonal dimensions：两个各自会独立变化的轴（渲染 API × 场景功能）
- **子类爆炸** — subclass explosion：M 个抽象 × N 个实现 = M×N 个类——16.1 的靶子（乘法降加法）
- **委托** — delegation：对象把活儿转交给持有的另一个对象——16.2 标题的前半句
- **句柄/体** — handle/body：Bridge 的 C++ 近亲惯用法（对外瘦句柄，对内胖实现）
- **跨平台编译期选择**：Bridge 在系统编程的通称——后端抽象 + 可换实现库
- **中介者** — Mediator：把对象间的**网状**直连改成经中心节点的**星形**转发
- **colleague（同事）** — 参与协作的各对象（聊天室的各玩家）
- **上帝对象** — god object：中介者的堕落形态——所有业务逻辑淤积在中心（最大风险）
- **事件总线** — event bus：中介者的匿名化/广播化变体（引擎常用，接第 5 章观察者）

## 动机一（桥接）：16.1「继承导致子类数量爆炸」

教科书场景（与本章标题严格对应）：图形×颜色、消息×格式、**渲染功能×后端 API**。
以继承硬凑两维：`OpenGLCircle`、`VulkanCircle`、`OpenGLSquare`…两维各加一个，类数相乘。
16.2 的解法一句话：**把「是什么」（抽象）与「用什么做」（实现）解耦**——
Circle 不再派生出每 API 一份，而是持有一个 `RenderAPI*`；两棵树各自独立扩展，
类数从 M×N 降到 M+N。这是 GoF「优先组合而非继承」最见效的一例。

## 动机二（中介者）：17.1 网状依赖的不可维护性

聊天室/大厅/经济系统里，每个对象都认识其他对象（或至少广播给所有人），
A 改协议要问 BCD 谁在听——N×N 依赖。中介者把「谁该通知谁」的**知识**收拢到一个对象：
同事只对中介说话，中介决定转发（星形）。游戏工业的放大形态：战局协调器、
EEAO（event-driven actor object）调度——以及一切「大厅 Manager」。

## 机制：🔧 桥接 + 中介者（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
class RenderAPI { public: virtual ~RenderAPI()=default;
    virtual std::string draw(const std::string& scene) const = 0; };
class OpenGL final : public RenderAPI {
public: std::string draw(const std::string& s) const override { return "GL:" + s; } };
class Vulkan final : public RenderAPI {
public: std::string draw(const std::string& s) const override { return "VK:" + s; } };
class Scene {                                           // 抽象侧：不关心用哪个 API
public:
    explicit Scene(std::unique_ptr<RenderAPI> api):api_(std::move(api)){}
    std::string render(const std::string& s) const { return api_->draw(s); }
private: std::unique_ptr<RenderAPI> api_;
};

class Room;
class Player {                                          // colleague：只认识 Room
public:
    explicit Player(std::string name):name_(std::move(name)){}
    void setRoom(Room* r){ room_ = r; }
    void send(const std::string& msg) const;
    std::string name() const { return name_; }
private: std::string name_; Room* room_{nullptr};
};
class Room {                                            // 中介者：星形中心
public:
    void join(Player* p){ members_.push_back(p); p->setRoom(this); }
    void relay(const Player* from, const std::string& msg){
        for (auto* m : members_) if (m != from)
            std::cout << m->name() << "<-" << from->name() << ": " << msg << "\n";
    }
private: std::vector<Player*> members_;
};
void Player::send(const std::string& msg) const { if (room_) room_->relay(this, msg); }
```

实测输出：`GL:main`（换 Vulkan 只动构造一行）、`B<-A: gg / C<-A: gg`（A 不认识 C）。
桥接侧的要点：**抽象侧持有实现侧的独占所有权**（`unique_ptr` 注入），运行期可换、
可 mock（测试注入假 API）；中介者侧的要点：转发的**策略**（谁能收、收几次）
是业务规则，集中即权力，也集中了风险——见权衡。

## 权衡

- **桥接是架构级决策**：一旦两棵树拆开就再也回不去「简单」；用早了白白多一层间接。
  判据：**两维是否真的都会独立变化**——只有一维动，另一维写死即可（YAGNI）。
- **Bridge vs Pimpl**：Pimpl（[../C++API设计/02-不透明指针与Pimpl.md](../C++API设计/02-不透明指针与Pimpl.md)）
  只拆**一个类**的接口/实现（编译防火墙，ABI 目的）；Bridge 拆**一族抽象/一族实现**
  （演化目的）。形态同源，意图不同——中文书常混，本目录分开记账。
- **中介者的账**：星形消灭了网状，但中心成为**单点复杂性**——
  「Mediator 写到 3000 行就是上帝对象」是行业共识警告；
  解毒剂：中介只做路由不做规则，规则留在同事或外置数据（配表/脚本）。
  17.1「基本概念」小节若放到今天，应加一句：中介+观察者的混合（事件总线）
  把「谁转发」也数据化了。

## 相邻概念对比

| 对比 | Bridge | Adapter | Mediator | Observer |
| --- | --- | --- | --- | --- |
| 轴 | 抽象×实现两树 | 一次性翻译 | N 对象经中心 | 1 对象广播 N |
| 接口谁变 | 两侧各自自由 | 客户端目标接口 | 同事间不再互识 | 订阅者实现接口 |
| 何时不用 | 只有一维在变 | 翻译一次就完 | 关系本就简单 | ——（另见第 5 章） |
| 本书相邻章 | 16 | 15 | 17 | 5 |

## 最新演进与工业实践

- **图形 API 抽象即行业级 Bridge**：SDL 的渲染后端、bgfx 的 renderer 架构（公开仓库）
  把「D3D/Vulkan/Metal/GL」做成可换实现树——16.1「功能×API 爆炸」的全行业解法；
  跨平台 C 库的标准解法（`dllexport`/后端表，另见 [../C++API设计/07-C++用法与符号导出.md](../C++API设计/07-C++用法与符号导出.md)）。
- **`std::function`/模板参数做编译期桥接**：抽象侧模板化 `Scene<RenderAPI>` 可把虚调用
  换成静态分派（零开销），代价是二进制膨胀与不可运行期换——策略章同款取舍。
- **中介者的工业形态**：UE 的 GameMode/GameState（一局比赛的规则中心，公开文档）就是正统
  Mediator；分布式放大版是消息代理（broker）与 saga 编排——谱系见
  [../微服务架构设计模式.md](../微服务架构设计模式.md)。
- **反射/代码生成**：中介路由表（事件类型→处理者）是注册样板高发区，
  P2996（C++26，已核实存在）可自动枚举处理者生成路由 ⚠️生态未核实。
