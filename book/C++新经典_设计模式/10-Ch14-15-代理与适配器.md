## 核心概念速览（中英对照）

- **代理** — Proxy：与被代理对象同接口、**控制访问**的替身（不是翻译接口）
- **虚代理/懒代理** — virtual proxy：昂贵对象按需才真正创建（贴图的 4K 数据别提前进内存）
- **缓存/缓冲代理** — caching proxy：把重复请求的结果留下（14.3.2 的专例小节）
- **守卫代理** — protecting/guard proxy：访问前鉴权（服务端权限中间层的原型）
- **远程代理** — remote proxy：本地替身代打网络（RPC stub 的学名）
- **写时复制代理** — copy-on-write proxy：值语义的共享-分叉魔术（历史 string 实现）
- **智能指针** — smart pointer：C++ 把「代理」语言化的最成功样本（unique/shared/weak）
- **适配器** — Adapter：把一个类的接口翻译成客户端期待的**另一个**接口
- **对象适配器** — object adapter：组合内层被适配者（现代默认）
- **类适配器** — class adapter：公开继承内层 + 覆写（15.3 专节；多继承语境，代价见权衡）
- **双向适配器** — two-way adapter：同一适配器同时服务两个方向的互译

## 动机一（代理）：boss.png 不该在加载界面就进显存

14.1 的「基本概念和范例」指向资源管理痛点：场景引用几百张贴图，真用到的只有当前视野的几张。
代理的答案：给每张贴图先立一个**只带文件名的同接口替身**，`pixels()` 第一次被调用时
才真正 load——调用方代码完全不知道真假（同接口是关键纪律，否则就不是代理）。
14.3.1 再把这个机制推广成应用场合清单：远程、虚拟、缓存、守卫、防火墙（copy-on-write）——
一张「为什么要隔一层」的 taxonomy，这是本书比 GoF 原版更实用的部分。

## 动机二（适配器）：第三方音频库不肯改接口

买来的/遗留的库只有 `playWav(path)`，引擎统一接口是 `AudioPlayer::play(path)`。
被适配者不可改、客户端不想动 → 中间加翻译层。适配器的判定语：**接口变了，语义没变**
（对比装饰：接口不变语义变——第 6–7 章埋的对偶线在此收拢）。

## 机制：🔧 虚代理 + 对象适配器（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
class Texture { public: virtual ~Texture()=default; virtual std::string pixels() const = 0; };
class RealTexture final : public Texture {                    // 真身：构造即昂贵
public:
    explicit RealTexture(std::string name):name_(std::move(name)){ std::cout << "[load " << name_ << "] "; }
    std::string pixels() const override { return name_ + "(4K data)"; }
private: std::string name_;
};
class TextureProxy final : public Texture {                   // 替身：先记账后开饭
public:
    explicit TextureProxy(std::string name):name_(std::move(name)){}
    std::string pixels() const override {
        if (!real_) real_ = std::make_unique<RealTexture>(name_);
        return real_->pixels();
    }
private: std::string name_; mutable std::unique_ptr<RealTexture> real_;
};

struct LegacyAudioPlayer {                                    // 不可改的第三方
    void playWav(const std::string& path){ std::cout << "legacy wav: " << path << "\n"; }
};
struct AudioPlayer { virtual ~AudioPlayer()=default; virtual void play(const std::string& path) = 0; };
struct LegacyAudioAdapter final : AudioPlayer {               // 对象适配器：组合内层
    explicit LegacyAudioAdapter(std::shared_ptr<LegacyAudioPlayer> p):p_(std::move(p)){}
    void play(const std::string& path) override { p_->playWav(path); }
private: std::shared_ptr<LegacyAudioPlayer> p_;
};
```

实测输出：`declared, not loaded` → 首次 `pixels()` 才出现 `[load boss.png] boss.png(4K data)`；
`legacy wav: bgm.wav`。两个结构学：代理用 `mutable unique_ptr` 把「懒建」封在 const 接口后；
适配器只做**名字/参数搬运**，绝不顺手加逻辑（加了就该拆成适配+装饰两层）。

## 权衡

- **代理的账**：一次虚调用+判空（便宜）；真正的坑是**身份分裂**——`&proxy != &real`，
  凡按指针比较大小的代码都会踩雷（GoF 警告，游戏引擎里靠「句柄/ID 比较」纪律规避）。
- **智能指针吃掉的那半边**：`shared_ptr` 天然是引用计数代理、`enable_shared_from_this`
  是弱身份代理——2026 年再手写「引用计数代理类」属于重复造轮；仍要手写的只剩
  虚代理/远程代理/守卫代理三类（API 边界层论证见 [../C++API设计/04-代理门面与观察者.md](../C++API设计/04-代理门面与观察者.md)）。
- **类适配器（15.3）的账**：公开继承把实现细节变接口、不可覆换内层、逼多继承——
  现代共识「优先对象适配器」；本书专列一节讲它，价值在读懂旧框架源码（如老式
  MFC/遗留库胶水层）时认得出。
- **适配器与过度包装**：三层适配追一个接口漂移时，正解是**回到源头统一接口**
  （或上第 11 章桥接做长期隔离）。

## 相邻概念对比：隔层模式四兄弟

| 模式 | 接口 | 语义 | 一句话 |
| --- | --- | --- | --- |
| 代理 Proxy | **不变** | 不变，但**控制访问**时机/权限 | 「我替你把门」 |
| 装饰 Decorator | **不变** | **增强** | 「我给你加料」 |
| 适配器 Adapter | **改变** | 不变 | 「我帮你翻译」 |
| 桥接 Bridge | 抽象/实现**两棵树** | 分离演化 | 「我给你拆墙」（16 章） |

## 最新演进与工业实践

- **`std::function` 即多态代理**：可调用对象的类型擦除代理（小对象优化内置）；
  远程代理的现代工业形态是 RPC/序列化框架（gRPC 等，公知）手写者寥寥。
- **资源懒加载被引擎资产系统接管**：UE 异步加载（AssetManager/软对象引用，公开文档）、
  各引擎 addressables 体系——虚代理的「按需」从「首次访问时同步 load」进化为
  「调度器提前一帧异步 load」，**模式语义在、实现换人**。
- **WASM/JS 绑定层是适配器流水线**：emscripten val、nbind（库内相关：
  [../C++API设计/11-脚本绑定与插件扩展.md](../C++API设计/11-脚本绑定与插件扩展.md)）
  在类型系统间逐向翻译——15.4「扩展运用」的当代放大版。
- **P2996 反射（C++26）对适配器的影响**：字段级接口翻译（结构体↔JSON/协议）可由元数据
  自动生成，手写「映射适配器」大幅缩水 ⚠️（生成器生态成熟度未核实）。

## 句柄/ID 与代理：游戏引擎的「替身」变体

引擎资源管理里更常见的不是本文件的类代理，而是 **handle 代理**：客户端拿 32 位句柄
（index+generation），运行时查表换真实指针——句柄即「可失效、可跨进程表达、可重定位」
的替身。它与虚代理在同一张权衡表的两端：句柄赢在**可失效与紧凑**，虚代理赢在
**调用透明**（接口不变）。写引擎代码时的判据：对象可能被卸载/搬移 → 句柄；
只是构造昂贵、接口稳定 → 虚代理。本文件 `TextureProxy` 换成
`expected<Texture&, LoadError>` 返回即同时吸收了第 14 文件总结章讲的错误通道——
模式组合在真实代码里向来如此发生。
