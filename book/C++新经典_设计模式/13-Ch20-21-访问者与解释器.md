## 核心概念速览（中英对照）

- **访问者** — Visitor：把「对元素结构的操作」外置成对象，遍历中不污染元素类
- **双分派** — double dispatch：`element.accept(visitor)` 内 `visitor.visit(*this)`——
  两次虚调用联袂确定 (元素类型 × 操作) 的矩阵单元
- **accept/visit 协议** — GoF 双方法握手：元素负责「我是谁」，访问者负责「对你做什么」
- **元素结构** — object structure：被遍历的对象集合/树（常由组合模式提供，第 8 文件）
- **开放/封闭轴** — open/closed axis：Visitor 对「加操作」开放（新 Visitor 类）、
  对「加元素」封闭（新元素要改所有 Visitor）——模式选型的总坐标系
- **多分派** — multimethod：N 维运行期分派，双分派是其 N=2 特例（C++ 无原生支持）
- **解释器** — Interpreter：为小语言定义文法→语法树→求值器的模式（21.3 机器人运动控制例：
  指令字符串解释执行，✅小节标题）
- **语法树** — AST：解释器的骨架——GoF 明说 Interpreter 是 Composite 的语言应用
- **终结符/非终结符表达式** — terminal / nonterminal expression：叶子与树枝两类 AST 节点
- **DSL** — domain-specific language：解释器模式的现代通称（技能脚本/配置小语言）
- **`std::variant` + `std::visit`**：封闭类型集上的编译期「访问者」——2026 视角的对照组

## 动机：20.1「一个具体范例的逐渐演化」

场景母题（按小节标题与模式本义教学化转述 ⚠️非原文）：对象结构稳定（元素类型很少变），
但**对其上的操作需求不断新增**（序列化、求值、渲染、统计…）。若把操作写成元素类的虚函数，
每加操作要打开所有元素类——散布式修改。Visitor 的答案：**操作住进访问者，元素只负责
「被访问」**；新增操作 = 新增一个 Visitor 类，元素类一字不动。

21 章解释器的动机则是另一个极端：**文法本身是需求**——策划要写「前进、左转、重复N次」
这类小指令（21.3 机器人运动控制），硬编码 if-else 解析每加指令改主干；把每条文法规则
做成一个表达式类，树 = 指令的组合，求值 = 遍历——**语言问题被翻译成结构问题**。

## 机制：🔧 三种活体（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
// 1) GoF 双分派访问者
class Visitor { public: virtual ~Visitor()=default;
    virtual int visit(const Number&) = 0; virtual int visit(const Add&) = 0; };
class Expr { public: virtual ~Expr()=default; virtual int accept(Visitor&) const = 0; };
struct Number final : Expr { explicit Number(int v):v_(v){}
    int value() const { return v_; }
    int accept(Visitor& v) const override { return v.visit(*this); } private: int v_; };
struct Add final : Expr { Add(std::unique_ptr<Expr> l, std::unique_ptr<Expr> r)
        :l_(std::move(l)),r_(std::move(r)){}
    int accept(Visitor& v) const override { return v.visit(*this); }
    const Expr& left() const { return *l_; } const Expr& right() const { return *r_; }
    private: std::unique_ptr<Expr> l_, r_; };
struct Evaluator final : Visitor {
    int visit(const Number& n) override { return n.value(); }
    int visit(const Add& a) override { return a.left().accept(*this) + a.right().accept(*this); }
};

// 2) 封闭表达式集：variant + visit（现代形态）
struct Node {   // 结构体提供递归 indirection，variant 才能自引用
    std::variant<int, std::pair<std::shared_ptr<Node>, std::shared_ptr<Node>>> v;
};
int eval(const Node& n){
    return std::visit([](const auto& x) -> int {
        using T = std::decay_t<decltype(x)>;
        if constexpr (std::is_same_v<T, int>) return x;
        else return eval(*x.first) + eval(*x.second);
    }, n.v);
}

// 3) 机器人小语言：字符指令流解释执行（21.3 主题的最小可复演版）
void runProgram(const std::string& prog, int& x){
    for (char c : prog){ if (c=='L') --x; else if (c=='R') ++x; }
}
```

实测输出：`sum=12`（GoF 版）、`vsum=10`（variant 版）、`robot x=1`（RRLRL → +1）。
双分派的机械本质值得点破：第一次虚调用按**元素实际类型**选中 `accept`，
第二次按**访问者静态类型**（`*this` 在 Visitor 基类视角）选中重载 `visit`——
两次单分派拼出一个「按 (类型, 类型) 查表」的假象。

## 权衡：开放/封闭轴的总清算

| 需求形状 | 正解 |
| --- | --- |
| 元素类型稳定，操作常加 | GoF Visitor（或 variant 上自由加 visitor 函数对象） |
| 操作稳定，元素常加 | 别用 Visitor——虚函数/`if constexpr` 链更省事 |
| 两者都常加 | 谁都救不了你——上代码生成或反射 |
| 类型集编译期封闭 | variant+visit：零虚表、可内联、漏分支编译期报错 |

- 双分派的隐性成本：`accept` 反向依赖 Visitor 前向声明（循环依赖管理）、
  元素被钉死「接待所有访客」的接口（20.3「深入理解」的处理对象）。
- 解释器的成本：手写词法/语法到一定规模必然转向**生成器**（lex/yacc、PEG、解析器组合子）
  或**数据驱动**（行为树编辑器）——GoF 自己在动机部分承认该模式「适合简单文法」。

## 相邻概念对比

- **Visitor vs Strategy**：Visitor 是「对一族**类型**各做一点事」（分派在类型矩阵），
  Strategy 是「对一件事换一种做法」（分派在算法选择）。
- **Visitor vs Interpreter**：解释器= 组合(结构) + 访问者(操作) 的成品装配——
  GoF 行为型三兄弟（23 章 Template/24 章 Visitor 在 Nesteruk 册合并，同此判断）。
- **variant+visit vs 双分派**：开放轴翻转——variant 加类型要改 variant 定义（封闭），
  加操作只写一个泛型 lambda（开放）；GoF 版恰好相反。选模式=选你在长哪个轴。

## 最新演进与工业实践

- **模式匹配仍未进标准**：`std::overload` 构造（P2662）与 pattern matching（P2391 等）
  截至 2026 未纳入 C++23 ⚠️（勿当标准设施引用）；`visit` + 泛型 lambda/手写 overload
  集合体已是事实惯用法（本文件实测代码即手写 `T` 仿函数版）。
- **编译器工业样本（LLVM，公开源码）**：指令遍历用**手写 switch + 表生成器（TableGen）**
  而非 Visitor 类族——同题（操作×类型矩阵）在超大规模下选择了代码生成路线，
  是「Visitor 的代价」最强注脚；clang 的 RecursiveASTVisitor 则是 Visitor 的正名之作（公开文档）。
- **P2996 静态反射（已核实纳入 C++26）**：对「枚举所有成员/派生类并施加操作」这类
  Visitor 主用途，反射可在编译期直接展开——注册表、序列化、AST 遍历三大本土应用场景
  的样板被釜底抽薪；「Visitor 是否会被反射整体替代」在 2026 年仍是开放问题（标 ⚠️推定）。
- **游戏脚本的现实**：21 章解释器的工业答案通常不是 C++ 内嵌类树，而是**外挂 Lua/Python
  虚拟机**（sol2、pybind11 等，公知库）——模式语义（解释一小语言）不变，实现外包给现成
  解释器；绑定层设计见 [../C++API设计/11-脚本绑定与插件扩展.md](../C++API设计/11-脚本绑定与插件扩展.md)。
