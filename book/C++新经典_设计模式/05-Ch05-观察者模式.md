## 核心概念速览（中英对照）

- **观察者** — Observer：状态变化时被自动通知的对象（订阅者）
- **目标/主题** — Subject：维护观察者名单、负责广播的枢纽（发布者）
- **发布-订阅** — publish-subscribe：Observer 的工程统称（注意与消息中间件的 Pub/Sub 组件有别）
- **拉模型/推模型** — pull / push model：通知里带不带数据（GoF 两种契约）
- **耦合度** — coupling：Subject 只认识「接口」不认识「具体人」——DIP 的又一次落地
- **悬垂订阅** — dangling subscription：观察者先于通知死亡，回调打到垃圾内存——Observer 的头号工程坑
- **令牌退订** — token-based unsubscription：用句柄/weak_ptr 管理订阅生命周期
- **信号与槽** — signals and slots：Qt 对 Observer 的类型安全封装（ moc 生成样板）
- **事件总线** — event bus / event channel：全局中介化 Observer，游戏引擎常见（见第 11 章中介者关联）
- **脏标记** — dirty flag：拉模型时代「通知=说一声变了」的配套手法

## 动机：5.1「遍历问题导致的低效率」

已核实的小节标题给出本书的引入路径：先有一段**轮询式**代码——宿主反复遍历一堆对象
问「你好了吗/你变了吗」，既浪费（每帧全量扫描）又僵化（要问的对象列表写死在循环里）。
问题实质是**依赖方向反了**：应该是「有事你告诉我」，不是「我每帧猜你有事」。

重构阶梯（按 5.1→5.2 的主题教学化转述 ⚠️非原文）：

1. 把「谁关心什么」登记成名单（观察者列表）；
2. 把「询问」翻转为「广播」：状态迁移点调用 `notify()`，遍历名单逐个回调；
3. 名单元素从具体类型升为抽象接口（或 `std::function`）——新增订阅者零改动宿主。

这就是 GoF 的 Observer：「定义对象间一对多的依赖，当一个对象改变状态时，它的所有依赖者
都会收到通知并自动更新」。游戏里它无处不在：成就系统监听击杀、音效监听状态切换、
UI 监听血量、战报服务监听战斗事件——本书以游戏案例贯穿的章节中，本章是最「结构性」的一个。

## 机制：现代最小实现 🔧（已实测 g++ 15.2，`-std=gnu++20`）

```cpp
struct Event { std::string type; int value; };
class Signal {
public:
    using Slot = std::function<void(const Event&)>;
    struct Token { virtual ~Token() = default; };
    std::shared_ptr<Token> connect(Slot s){
        auto t = std::make_shared<Token>();
        slots_.push_back({std::weak_ptr<Token>(t), std::move(s)});
        return t;
    }
    void fire(const Event& e){
        for (auto it = slots_.begin(); it != slots_.end(); )
            if (auto sp = it->first.lock()) { it->second(e); ++it; }
            else it = slots_.erase(it);          // 令牌亡则订阅自动清除
    }
private:
    std::vector<std::pair<std::weak_ptr<Token>, Slot>> slots_;
};
```

实测：`fxTok` 所在作用域结束后，第二次 `fire` 只打印 `score +5`——订阅者生命周期
由 `weak_ptr` 令牌自动管理。对比 GoF 原版三件套（抽象 Subject + 抽象 Observer + attach/detach），
现代 C++ 的三个替换：**类继承 → 函数对象**（少一层类型）、**手动 detach → 令牌自动失效**
（消灭头号事故源）、**裸 Event 参数 → 结构化事件体**（推模型）。

## 权衡：通知的账本

- **重入问题**：回调里再 `fire` 同一信号（成就触发新事件）会迭代器失效/无限递归——
  工业实现要么队列化（延迟广播），要么加广播深度锁。
- **顺序无保证**：名单顺序是实现细节，别依赖「UI 先更新音效后更新」。
- **一次事件全体遍历**：热路径（每帧每个粒子）用 Observer 是性能自杀——
  高频信号该合帧或直接函数调用；Observer 的甜区是**低频、多订阅者**（游戏事件、配置变更）。
- **测试红利**：断言「事件发生过」比断言「内部状态」稳得多，这是引擎内建事件系统的动机之一。

## 最新演进与工业实践

- **Qt 信号槽**（公开文档）：类型安全的 Observer 工业封装，编译期校验签名；
  代价是需要 moc 预处理器生成样板——「语言缺反射，框架来凑」的经典注脚。
- **UE 的 Delegate/EventDispatcher**（公开文档）与 FMOD/各类中间件的回调总线同理，
  游戏引擎事实上把 Observer 做成了**语言扩展**。
- **C++20 协程对 Observer 的翻转**：拉模型用 generator（C++23 `std::generator`，已核实入标准）
  可以把「每帧问一遍」写成 `co_yield` 惰性流——遍历与通知的边界变糊；
  Nesteruk 册对此有专章论证（[../C++20设计模式/12-空对象与观察者.md](../C++20设计模式/12-空对象与观察者.md)）。
- **std::expected/异常不是 Observer**：错误传播常被错用全局事件总线包装，
  2026 实践共识是「错误走 expected/result 通道，业务信号走事件通道」，两线分开。
- **反射（P2996，C++26）**：连接信号槽的字符串/宏样板可被元编程替代——方向核实，具体生态 ⚠️推定。

## 复演清单：从 5.1 到本文件代码的五步

1. 写出轮询版：宿主每帧问一遍每个订阅者（先体会痛）；
2. 反转方向：订阅者注册回调，状态迁移点统一 `fire`；
3. 消类型：抽象基类 Observer → `std::function`（少一层继承，多一分灵活）；
4. 补生命周期：裸函数指针时代的 detach 义务 → weak_ptr 令牌（本文件实现）；
5. 补重入/顺序：需要时把 `fire` 改成延迟队列广播。

每步都能单独编译单独跑——这正是本书「逐步重构」教学法在观察者可复演版本，
也是本目录对每一章代码的共同要求。
