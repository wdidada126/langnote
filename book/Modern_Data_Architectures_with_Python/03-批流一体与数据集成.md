# 03 · 批流一体与数据集成

> ⚠️ 主题重构章（原书目录不可得，见 [00-总览与阅读地图.md](00-总览与阅读地图.md) §2）。
> 本章处理 02 章留下的两个硬问题：**删除捕获**与**迟到数据**，并把"批流一体"从口号
> 拆成可执行的语义契约。流引擎（Flink/Spark Streaming/Kafka）本机不可实测，
> 全部 ⚠️ 转述；凡 🔧 只限 DuckDB/SQLite 侧可验证的语义类比。

## 1. 先把"批流一体"翻译成契约语言

批流一体（one dataset, one code path）的实质不是"用流引擎跑批"，而是三条契约：

1. **同一套变换逻辑**批与流共用（消灭 Lambda 的双实现漂移，01 章 §3）；
2. **同一套正确性定义**：以事件时间（event time）而非处理时间（processing time）
   为坐标系，窗口语义可重放（⚠️ Flink watermark 语义转述）；
3. **同一套一致性出口**：最终落地是幂等 upsert（02 章 🔧E1 的 MERGE 正是它的批侧化身）。

- 🔧 可本机验证的类比：DuckDB 里同一张 `ods_orders`，既接受微批 MERGE（02 章），
  也接受"带更正的迟到批"再 MERGE 一次——ON 键不变则终态收敛。
  流式引擎的 exactly-once sink 本质就是这条：把"重放安全"做成幂等写。
- ⚠️ 边界：真正的低延迟流状态（CEP、大窗口 join、乱序缓冲）超出本机两引擎能力，
  不外推；本册只主张"**微批重放**是流语义的廉价近似，适用于分钟级 SLA"。

## 2. CDC：删除与更正的正规来源

- 三种主流形态（⚠️ 全部转述，无一手实测）：
  1. **查询式**：时间戳轮询（=02 章水位线），看不见物删；
  2. **日志式**：解析 binlog/WAL（Debezium/WAL2JSON 家族），全事件（insert/update/delete）
     且有序，代价是要贴着数据库跑；
  3. **出箱式（outbox）**：应用把变更事件写进业务库的同事务表，管道消费 outbox。
     微服务拆分后的事实标准（⚠️ 转述工程共识）。
- 🔧 可验证的一半：SQLite 的 WAL 文件**确实**是追加式变更日志，`journal_mode=WAL` 下
  写操作先落 WAL——与 PG binlog 同构（机制类比，标非本书引擎行为）。本册不假装
  解析了 WAL，但工程要点可以本机演示：**outbox 表与业务表同事务写入**在 SQLite 的
  默认事务隔离下是一个 BEGIN/COMMIT 内两条 INSERT 的事——廉价到没有理由不用。
- CDC 事件进仓的标准姿势是"变更表 + 快照合并"：变更流按主键折叠（last-write-wins）
  刷成当前态快照，即 07 章表格式的 merge-tree 语义；本册 🔧E1 的 delta→MERGE 是
  它的最小可行版（无删除位；删除位加一列 `op` 后语义即补全）。

## 3. 迟到数据与回看窗口的工程配平

- 迟到分级：
  - **可容忍**：水位线查询故意回看 N 天（02 章回看窗口），MERGE 幂等吸收；
  - **不可容忍**：触发更正事件（CDC update 流），同样被 MERGE 吸收；
  - **灾难级**：源系统改了历史事实但**不更新 updated_ts**——任何增量口径都失明，
    唯一解是周期全量对账（🔧E3 的行数+指纹双比对即对账的最小形态）。
- 窗口聚合的迟到语义（┠ 转述流引擎）：allowed lateness/侧输出流等机制在微批世界
  的对应物="重算受影响窗口分区 + 原子替换"。DuckDB 侧 🔧 类比：
  `CREATE OR REPLACE` 目标分区表再 ATTACH 换出，等价于 overwrite-partition。

## 4. 集成的拓扑：点对点、总线还是湖仓

| 拓扑 | 形态 | 腐化模式 | 本册立场 |
| --- | --- | --- | --- |
| 点对点 | 每对系统一条管道 | N² 管道、无人认领 | 禁止新增 |
| 总线 | Kafka 企业事件总线 | topic 沼泽、schema 无政府 | ⚠️ 转述其治理成本 |
| 湖仓中枢 | 所有集成先入湖、再分叉消费 | 湖变"唯一真相"后变更即广播 | 07 章主选 |
| 联邦查询 | ATTACH 直连异构源不搬数 | 源侧耦合、性能不可承诺 | 🔧E5 限定小数据集 |

- 结论：**搬数进湖（带 CDC 事件语义）+ 湖上分叉**是 2024–2026 的主流折中；
  联邦直连只用于维表/查询期拼接，不用于事实数据长期依赖（源会改、会下线）。
- 与 Data Mesh 的接缝：集成拓扑的选择决定"域边界"画在哪——总线式集成天然反网格
  （耦合 topic 格式），湖仓式集成允许域各取所需。对读
  [../Data_Mesh/07-逻辑架构.md](../Data_Mesh/07-逻辑架构.md)（其逻辑架构三分面：
  domain-aligned / autonomous / platform-supported 与上表拓扑一一相关）。

## 5. Python 侧的集成件清单（务实版）

- **连接器**：pyodbc/官方 DBAPI 族、`duckdb.connect` + sqlite_scanner（🔧E1 ✅
  https://duckdb.org/docs/stable/extensions/overview ）；
- **帧与 Arrow**：pandas 仍是胶水事实标准，Arrow 是跨引擎零拷贝的"集成中间货币"
  （DuckDB↔pandas↔pyarrow 三角本机可用，标类比）；
- **契约校验**：ingest 前后各一次行数/指纹检查（05 章），失败即 quarantine 表；
- **编排接口**：管道函数暴露 (run, dry_run, since) 三元签名，任何编排器可包
  （02 章 §5 分离原则的 API 化）。

## 6. 自检问答（读毕应有答案）

1. "批流一体"的三条契约分别是什么？哪条能在本册 🔧 里演示？
   （同一逻辑/事件时间/幂等出口；第三条由 E1 的 MERGE 重放安全演示）
2. 查询式、日志式、outbox 三种 CDC 形态各自的"看不见什么"？
   （轮询看不见物删与时钟外真相；日志式依赖数据库权限与保留窗口；
   outbox 依赖应用纪律——忘了写 outbox 的事务=静默丢失）
3. 为什么"源改了历史但不更新 updated_ts"是全量对账的存在理由？
   （任何基于时间戳/键的增量口径对该事件族数学失明，指纹比对是唯一解）
4. 湖仓中枢与总线的本质区别一句话？（前者以不可变快照序列为真相、消费者拉取解耦；
   后者以 topic 为真相、格式耦合在传输层）
5. 🔧E1/E5 的 ATTACH 联邦为什么限定"小数据集"？（源侧无快照隔离保证、无性能承诺，
   事实数据长期依赖=把可用性外包给别人的库文件）
6. outbox 为何要"同事务"而不是"事后补发"？（跨事务=双写裂缝：业务成功事件丢失
   或反之，正是集成正确性最难修的一类事故）

## 核心概念速览（中英对照）

1. **批流一体** — Batch-stream unification：一套逻辑、事件时间坐标、幂等出口的三条契约。
2. **事件时间** — Event time：以数据自带时间戳为坐标系，重放不改语义（⚠️ 流引擎语境转述）。
3. **处理时间** — Processing time：以到达时刻为准，微批世界最常见的近似。
4. **CDC** — Change Data Capture：捕获 insert/update/delete 全事件的摄取方式。
5. **Outbox 模式** — Transactional outbox：业务写与事件写同事务，集成正规化的廉价方案。
6. **Last-write-wins** — LWW：按主键以最新事件折叠变更流成当前态。
7. **回看窗口** — Lateness window：增量查询故意多扫 N 天吸收迟到。
8. **全量对账** — Full reconciliation：指纹+行数双比对，抓"不更新时间戳的历史篡改"。
9. **Quarantine 表** — Quarantine：坏批次旁路存放，不阻塞好数据（04 章闸门配套）。
10. **集成拓扑** — Integration topology：点对点/总线/湖仓中枢/联邦四形态及其腐化模式。
11. **overwrite-partition** — 分区原子替换：重算受影响窗口后整体换出的幂等写。
12. **Arrow 中间货币** — Arrow as interchange：跨引擎零拷贝的列式内存交换格式。

## 最新演进与工业实践

- **Debezium Server / Debezium Connect** 仍是日志式 CDC 的开源主干（⚠️ 转述：本册无
  Kafka 环境，未实测）；其官方文档 debezium.io 写作本领域权威入口（本册引用前未能
  完成 curl 核验，按规范标 ⚠️ 不作内容依据，仅指路）。
- **DuckDB 的增量读取面**：sqlite_scanner 支持按 ATTACH 文件查询（🔧E1 实证），但
  "读 WAL 变更流"并非其设计目标——社区有 issue 讨论、未见稳定特性（⚠️ 转述，不引
  issue 号以免编造）。
- **微批重放作为工业默认**：分钟级 Airflow/ dags + upsert 的"穷人版流"在中小团队
  长期占优（⚠️ 转述工程共识）；其成立前提恰是本册 🔧E1 验证的幂等 MERGE 语义。
- **流式表格式**：Iceberg 的 merge-tree 引擎与增量读取（delete files 合并）把 CDC
  事件落湖标准化，✅ https://iceberg.apache.org/spec/ （2026-10-01 curl 200，
  07 章展开）；这是"批流契约"终于同构的地方——湖上批读与流读共用同一快照序列。
- **与本册谱系的关系**：流式原理深挖归论文线 [../../db/db.md](../../db/db.md) 与
  分布式册；本册贡献的是**消费者视角**：湖仓怎样把流的承诺翻译为可重放的表。
