## 1. 表格式解决的是什么问题（30 秒版）

- 裸 Parquet 湖的三大缺：无 ACID（半写可见）、无 schema 演进契约、无快照/时间旅行。
- 表格式=在对象存储文件之上加一层**元数据协议**：快照序列、manifest 清单、
  schema/分区演进史。Iceberg 的元数据树（table metadata → snapshot → manifest list →
  manifest → data files）✅ https://iceberg.apache.org/spec/ （00 已 curl 200）。
- 三家谱系（深入各归各册）：
  - **Iceberg**：引擎中立+规范最严格，本项目 [../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md](../Architecting_an_Apache_Iceberg_Lakehouse/00-总览与阅读地图.md)；
  - **Hudi**：upsert/增量摄取原生强项，见 [../Apache_Hudi_Definitive_Guide/00-总览与阅读地图.md](../Apache_Hudi_Definitive_Guide/00-总览与阅读地图.md)；
  - **Delta**：Databricks 生态默认，✅ https://delta.io/ 、社区中立化进展 ⚠️ 转述。
- 本册不重复三家的写路径细节；讲**消费者视角**：读快照、追增量、查元数据三件事在
  Python 里长什么样。

## 3. 读快照与追增量：消费者的两个基本动作

- **读快照**：给定 snapshot id 读一致性数据——时间旅行的工程用处不是审计员把玩，
  而是**管道重放的定位器**：02 章"从任意时刻重建"承诺要落到"从第 N 个快照重建"。
- **追增量**：查"两个快照间变化的数据文件"（Iceberg 增量读、Hudi 的 timeline/incremental
  query、Delta 的 change data feed，⚠️ 三家特性名转述）。这是 03 章 CDC 的湖仓正规形态：
  湖内增量取代源端轮询。
- 🔧 单机替身（语义对照实验，标类比非本书引擎行为）：本册 E3 的**追加式历史目录**
  （catalog 每次采集一行快照）在 SQLite 里复现了"元数据即快照序列"的内核——
  `SELECT * FROM catalog WHERE tbl='ods_orders' ORDER BY collected_at` 就是穷人版
  time travel。真实表格式的差别在于数据文件级清单与谓词下推，规模差几个数量级。

## 4. schema 演进：表格式如何接住 05 章的漂移

- Iceberg 的 schema 演进是**受控操作**（加列/改名以元数据变更表达，不动数据文件，
  ⚠️ 转述规范细节；✅ spec 页可达同上）。
- 与 🔧E3 的衔接：采集器检出指纹漂移后，湖仓世界的正确响应序列=
  漂移事件 → 对照表格式演进历史（元数据 diff）→ 判定"已批准的演进 vs 事故"——
  批准与否的数据源正是 05 章目录里的运营元数据。**闭环在此合龙**。
- 反例警告：Hive 式 ALTER 改 SerDe 而不改文件=新旧数据同表异格式的世纪坑
  （⚠️ 转述社区血泪共识）；表格式存在的理由之一就是让演进可审计。

## 6. 辨析三问 + 自检问答（读毕应有答案）

**辨析一：表格式 vs 目录服务。** Iceberg 规范管"表在存储上长什么样"（元数据树+
数据文件布局），catalog 管"表名到元数据树的注册查找"（REST/Hive/Glue 后端）。
两者常被产品营销混谈；工程上分清才懂"换 catalog 不动数据、换表格式动一切"。

**辨析二：快照 vs 备份。** 快照是元数据指针级零拷贝历史态（时间旅行的基础），
备份是数据文件复制（恢复成本的来源）。把"有 Iceberg"当"有备份"是年度常见事故前提
（快照被 expire 吃掉后无家可归，⚠️ 转述社区教训）。

**辨析三：ACID 表上的 ACID 库。** 表格式给单表事务；跨表原子性（orders+payments
同增同减）湖仓世界普遍**不提供**——那是数据库的地盘，别拿湖仓硬装。

**自检问答：**
1. 管道重放为什么需要 snapshot id 而不是日期？（同日多次提交、时钟漂移、
   回填数据都使墙钟不可靠；快照序列才是因果序）
2. E3 的"穷人版时间旅行"缺表格式三件中哪两件？（数据文件级清单+谓词下推；
   只有元数据行序列）
3. schema 演进与 ALTER 的本质区别？（演进改的是**契约的表达与兼容策略**并留审计，
   ALTER 只改当下 DDL——§4 反例即裸 ALTER 的世纪坑）

## 核心概念速览（中英对照）

1. **开放表格式** — Open table format：对象存储文件之上的元数据协议（Iceberg/Delta/Hudi）。
2. **快照** — Snapshot：表在某时刻的完整一致性状态，时间旅行的锚点。
3. **manifest** — 清单文件：快照到数据文件的中间索引层（Iceberg 元数据树节点）。
4. **时间旅行** — Time travel：按 snapshot/版本号读历史状态。
5. **增量读** — Incremental read：两快照间变化集的读取，CDC 的湖仓正规形态。
6. **变更数据流** — Change Data Feed：Delta 系特性名，湖内输出行级变更（⚠️ 转述）。
7. **schema 演进** — Schema evolution：以元数据操作表达的列增删改名，不动数据文件。
8. **catalog** — 表目录服务：Iceberg 的表注册层（REST/Hive/Glue 等后端，⚠️ 转述）。
9. **谓词下推** — Predicate pushdown：靠清单统计跳过无关文件，湖仓扫描成本的闸门。
10. **pyiceberg** — Iceberg 纯 Python 客户端：湖仓进入 Python 一等公民的标志件（⚠️ 细节转述）。
11. **compaction** — 文件合并：小文件治理的例行维护动作（他册纵深）。
12. **穷人版时间旅行** — 🔧 类比：追加式目录快照序列在 SQLite 内的最小复现（E3 延伸）。
