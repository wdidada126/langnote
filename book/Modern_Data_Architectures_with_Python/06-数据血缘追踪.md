## 1. 血缘的三种采集时机

| 时机 | 手段 | 精度 | 代表 |
| --- | --- | --- | --- |
| 静态（跑前） | SQL 解析器抽读写表 | 表级，列级可行但贵 | sqlglot、SQLGlot-based 工具 |
| 运行时（跑中） | 引擎钩子发事件 | 表/列级+执行上下文 | OpenLineage 集成（Airflow/Spark/dbt） |
| 平台内生（跑后） | 作业日志/游标反推 | 依平台 | Unity Catalog、DataHub 血缘 |

- 工程常识：**静态解析能覆盖 80% 的需求且零侵入**——本册 🔧E4 走这条路；
  运行时事件流是企业规模的正解（04 治理册的平台面）。
- 粒度阶梯：表级→列级→值级（cell-level）。列级解析要处理 `SELECT *` 展开、CTE、
  函数封装；值级基本只在论文里活（⚠️ 转述；本册连列级都只做表级演示，不装）。

## 2. 🔧E4 实测：解析 → 边表 → 递归追溯

方法（`experiments.py`，sqlglot 30.19.0 ✅ https://sqlglot.com/ ）：

1. 四步管道 SQL（ods_orders → stg_orders → mart_cust → mart_report，最后一步 JOIN
   质量章的 raw 帧），逐步 `parse_one(sql, dialect="duckdb")`，
   取 `find_all(exp.Table)` 的表名集合，扣除写入目标得源集。
2. **实测边表**（5 条，原样输出）：
   `[('orders','ods_orders'), ('ods_orders','stg_orders'), ('stg_orders','mart_cust'),
     ('mart_cust','mart_report'), ('raw','mart_report')]`
   ——注意第一条：`src.main.orders` 被解析为表名 `orders`（catalog.schema 被丢弃），
   跨源血缘要保留全限定名则需自取 `table.catalog/db` 属性拼接（诚实登记：本演示
   未做，多源同名表会有歧义，这是**手撕血缘 vs 平台血缘的第一个分水岭**）。
3. **上游闭包查询**（SQLite 递归 CTE，✅ https://sqlite.org/lang_with.html curl 200）：

```sql
WITH RECURSIVE anc(t, depth) AS (
  SELECT 'mart_report', 0
  UNION ALL
  SELECT l.src, a.depth+1 FROM lineage l JOIN anc a ON l.dst = a.t)
SELECT t, min(depth) FROM anc GROUP BY t HAVING t <> 'mart_report' ORDER BY 2;
```

   **实测输出**：`mart_cust(1), raw(1), stg_orders(2), ods_orders(3), orders(4)`——
   mart_report 的全部祖先按层级排序，含质量章旁路进来的 raw（**跨章血缘自发闭合**，
   这正是"架构即数据"的红利：04/05/06 三章的表在一张边图里互相可见）。
4. 踩坑登记（真实调试记录）：首版查询写 `SELECT DISTINCT t, min(depth)` 忘 `GROUP BY`，
   SQLite 把它当全表聚合只返回 1 行——**递归 CTE + 聚合的组合是血缘查询的手误高发区**，
   修复后加 `HAVING` 排除自身。

## 3. 边表模型的扩展位（从玩具到有用的距离）

- 加列不改模型：`(src, dst)` → `(src, dst, kind, pipeline_id, sql_hash, ts)`；
  `kind ∈ {table, column, job}` 一列即可支撑粒度升级。
- `sql_hash` 关联 05 章指纹：SQL 变了而边没重解析=血缘过期，可做陈旧度检查。
- 下游追溯=反向递归（`WHERE src=t`）：影响分析（"改这列会炸哪些报表"）与其
  只是方向之差；对读 [../The_Enterprise_Data_Catalog_2e/05-血缘分析与影响分析.md](../The_Enterprise_Data_Catalog_2e/05-血缘分析与影响分析.md)。
- 环检测：递归 CTE 遇环会指数爆，实用解=depth 上限或物化路径集合去重（登记为
  本演示未做的已知限制）。

## 4. 平台与规范对照

- **OpenLineage**（✅ https://openlineage.io/ ）：run/job/dataset + facets 的事件
  模型；本册边表≈其 dataset 级 lineage 的物化投影。采用面：Airflow/Dagster/Spark/
  dbt 官方或社区集成持续加密（⚠️ 转述；版本矩阵未逐条核实）。
- **dbt**：manifest.json 内生全图血缘，商业版 Data Lineage 页面化（✅ 入口
  https://docs.getdbt.com/ ，专页未验不引深链）。dbt 血缘的便宜来自声明式模型
  （ref() 即边），对读 [../Analytics_Engineering_with_SQL_and_dbt/00-总览与阅读地图.md](../Analytics_Engineering_with_SQL_and_dbt/00-总览与阅读地图.md)。
- **Unity Catalog**：查询期自动捕获列级血缘、零配置（⚠️ 平台侧转述），深度见
  [../Data_Governance_with_Unity_Catalog/04-数据发现与血缘追踪.md](../Data_Governance_with_Unity_Catalog/04-数据发现与血缘追踪.md)；
  与 E4 对照点：UC 是运行时引擎内生，E4 是静态外挂——前者省事、后者省基础设施，
  也天然错过运行时上下文（参数、实际分区）。
- **湖仓侧**：Iceberg 的 snapshot/operation 元数据使"哪个作业写了哪个快照"可查
  （07 章；✅ https://iceberg.apache.org/spec/ ），表格式内生的血缘是 2024–2026 的
  新共识：**血缘下沉到存储层，上层工具只读不猜**。

## 5. 血缘的三个正确用法（与一个滥用）

1. **影响分析**：变更前查下游闭包，通知 owner（05 章目录联动）；
2. **事故定位**：坏数字顺边表上浮找污染源（E4 的 raw 边即示例：报表脏了先查质量旁路）；
3. **合规取证**：个人数据流经哪些资产（治理线 06/08 章接口，对读
   [../Understanding_Data_Governance/08-合规与隐私.md](../Understanding_Data_Governance/08-合规与隐私.md)）。
4. 滥用=**血缘装饰品**：画了大图没人查——边表必须被管道（fail-fast）、事故（定位）、
   治理（取证）三条线至少一条**程序化消费**，否则退化为 05 章批判过的"维基百科"。

   与运行时事件互补非替代）

   取 name 单字段；升级=拼 catalog||db||name 三段键）
3. 递归 CTE 的环从哪来、如何拦？（互相引用的视图/物化循环；depth 上限或路径集去重）
4. 血缘陈旧度与质量规则怎么联动？（sql_hash 变→边表应重解析→比对差异出新边，

## 核心概念速览（中英对照）

1. **血缘** — Data lineage：数据资产间的派生依赖关系，常建模为 DAG。
2. **边表** — Edge table：(src,dst) 二元组列表，血缘的最小存储形态（🔧E4）。
3. **静态解析抽线** — Static lineage extraction：SQL 文本→读写表集，零侵入（🔧E4 sqlglot）。
4. **运行时事件血缘** — Runtime lineage：作业执行时上报的 run/dataset 事件（OpenLineage）。
5. **递归 CTE** — WITH RECURSIVE：沿边表迭代求上游/下游闭包的查询原语（🔧E4 实测）。
6. **上游闭包** — Ancestry closure：某资产的全部祖先+层级（🔧E4 输出 5 节点）。
7. **影响分析** — Impact analysis：反向递归，变更前的下游爆炸半径评估。
8. **列级血缘** — Column-level lineage：边细化到列，需展开 SELECT * 与 CTE（阶梯第二档）。
9. **全限定名歧义** — Qualified-name ambiguity：跨源同名表在朴素解析下的撞名风险（🔧E4 登记坑）。
10. **血缘陈旧度** — Lineage staleness：sql_hash 变而边未重解析的漂移态。
11. **manifest 血缘** — dbt manifest lineage：声明式 ref 关系免费生成的全图。
12. **查询期捕获** — Query-time capture：引擎执行计划内生血缘（Unity Catalog 式，⚠️）。
