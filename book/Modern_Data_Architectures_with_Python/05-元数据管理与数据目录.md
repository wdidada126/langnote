# 05 · 元数据管理与数据目录

> ⚠️ 主题重构章（原书目录不可得，见 [00-总览与阅读地图.md](00-总览与阅读地图.md) §2）。
> 🔧 实验组 E3 本章落地：双引擎（DuckDB+SQLite）元数据采集 → SQLite 目录表 →
> 列集指纹 → schema 漂移检出。制度面归治理线；本章是"目录的最小可行体"。

## 1. 元数据的三分法与它们的存储命运

- **技术元数据**：表/列/类型/行数/存储位置——可全自动采集（🔧E3 采的就是它）；
- **运营元数据**：谁跑的、何时跑、耗时、水位线、质量分数——管道副产品，必须落表；
- **业务元数据**：中文名、口径定义、owner、术语表——**只能人写**，工具只能提供
  编辑界面与变更流程。
- 目录（catalog）的工程定义：上述三类的**统一可查询索引**，实体粒度=表/列/资产。
  对读 [../The_Enterprise_Data_Catalog_2e/02-元数据模型与目录架构.md](../The_Enterprise_Data_Catalog_2e/02-元数据模型与目录架构.md)
  （其元数据模型章讲企业级实体关系设计，本章给单机版三张表的对照）。

## 2. 🔧E3 实测：采集器、指纹与漂移

方法（`experiments.py`）：

1. **采集器 `snap(conn, eng)`**：DuckDB 走
   `information_schema.tables/columns`（限定 `table_catalog=current_database()`
   ——踩坑登记：ATTACH 的 SQLite 源也在 information_schema 里混入 `main` schema，
   不过滤目录会把源表当本仓表采集，首跑即中招）；SQLite 走
   `PRAGMA table_info` + `sqlite_master`。
2. **指纹**：对表的（列名,类型）有序 JSON 做 SHA-256 截 12 位；同时记录 `count(*)`。
3. **目录落库**：`meta.db` 中 `catalog(eng, tbl, cols, nrows, fingerprint, collected_at)`，
   一次采集=一行带时间戳的快照——**历史目录免费得到**（追加式，可查"任何时刻的 schema"）。
   实测：首采 2 实体（duckdb.ods_orders=100,000 行 / sqlite.orders=100,000 行）。
4. **漂移检测**：`ALTER TABLE ods_orders ADD COLUMN region` 后再采一次，比对指纹 →
   检出 `['ods_orders']`，新列集 `[id, cust, amount, updated_ts, region]`。
   ALTER 语义差异登记：SQLite 加列同样支持（✅ https://sqlite.org/lang_altertable.html ，
   curl 200），但改型/删列需重建表——指纹比对对两引擎同构可用，**迁移脚本必须分引擎生成**。

## 3. 目录的三种消费姿势（按查询距离排）

1. **人搜**（找数据）：`SELECT * FROM catalog WHERE tbl LIKE '%order%'` ——🔧E3 的
   目录表 5 行 SQL 就够；企业级搜索/评分/协作面见
   [../The_Enterprise_Data_Catalog_2e/04-元数据检索与发现.md](../The_Enterprise_Data_Catalog_2e/04-元数据检索与发现.md)。
2. **程序读**（自动化）：管道启动前读目录校验上游指纹，漂移即 fail-fast（🔧E3 的
   直接用法）；04 章"新增列未配规则"的 finding 也从这里出。
3. **治理用**（审计与政策）：owner 覆盖率先聚合后上报——对读
   [../Understanding_Data_Governance/05-元数据管理与数据目录.md](../Understanding_Data_Governance/05-元数据管理与数据目录.md)
   （治理侧对目录组织的角色/流程要求）。

## 5. 主动元数据：目录从"维基百科"变"神经中枢"

- 被动目录=人看；主动元数据=被管道/质量/血缘**消费**的元数据（01 章 §5 反身性的延伸）。
- 本册的最小主动环：catalog 行变化 → 触发规则重审（04）→ 血缘边重解析（06）→
  下游订阅通知（08 的数据产品契约）。四个环节在 🔧E3/E4 都有可跑原型。
- Fabric 谱系把"主动元数据+知识图谱"上升为架构本体（对读
  [../Principles_of_Data_Fabric/00-总览与阅读地图.md](../Principles_of_Data_Fabric/00-总览与阅读地图.md)、
  [../Data_Fabric_Architectures/00-总览与阅读地图.md](../Data_Fabric_Architectures/00-总览与阅读地图.md)）；
  本册代码视角的翻译：**fabric 的"主动"落地为 catalog 表上的触发器 + 订阅边表**，
  机制不神秘，规模化才难。

## 6. 🔧E3 目录三表 DDL 全量（可抄）

```sql
-- meta.db：技术+运营元数据主表（追加式历史目录）
CREATE TABLE catalog(
  eng TEXT,                    -- 'duckdb' | 'sqlite' | 'federated'
  tbl TEXT,
  cols TEXT,                   -- JSON 有序列集 [(name,type)...]
  nrows INTEGER,
  fingerprint TEXT,            -- sha256(cols)[:12]
  collected_at TEXT DEFAULT (datetime('now'))
);
-- 边表（06 章血缘，同库）
CREATE TABLE lineage(src TEXT, dst TEXT);
-- 质量结果表（04 章，同库）
CREATE TABLE quality_results(rule TEXT, target TEXT, passed, value, ts TEXT);
```

- 三表一库即"目录+血缘+质量"的最小物理载体；**同库**是刻意的：一次事务里
  原子写下三类记录，避免跨库的时序不一致（治理数据自己先要有一致性）。
- owner 列刻意留给业务元数据（§1 第三类），加列走 §4 的漂移流程而不是偷偷改表——
  本册的元数据表结构变更同样受自家纪律约束（不动点问题的自示范）。

## 核心概念速览（中英对照）

1. **技术元数据** — Technical metadata：表/列/类型/行数，可全自动采集（🔧E3）。
2. **运营元数据** — Operational metadata：执行历史、水位线、质量分数等管道副产品。
3. **业务元数据** — Business metadata：口径/owner/术语，唯一只能人写的一类。
4. **数据目录** — Data catalog：三类元数据的统一可查询索引。
5. **information_schema** — 标准元数据视图：SQL 采集器入口（🔧E3 用，含 ATTACH 混入坑）。
6. **PRAGMA table_info** — SQLite 元数据方言：无 information_schema 时的采集路径（🔧E3）。
7. **schema 指纹** — Schema fingerprint：列集+类型哈希，比对即漂移检出（🔧E3）。
8. **追加式历史目录** — Append-only catalog：每次采集一行快照，免费获得任意时刻 schema。
9. **fail-fast 校验** — Fail-fast on drift：管道启动前查指纹，漂移即中止。
10. **三级命名空间** — Three-level namespace：Unity Catalog 的 catalog.schema.object 结构（⚠️ 平台侧）。
11. **主动元数据** — Active metadata：被自动化系统消费的元数据，fabric 架构的燃料。
12. **采集器（connector）** — Collector：面向异构源的元数据抽取插件（开源目录群核心件）。
