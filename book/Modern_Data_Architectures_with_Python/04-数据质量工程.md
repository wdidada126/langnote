## 1. 质量维度的可断言化

行业惯用六维（完整性/准确性/一致性/及时性/唯一性/有效性，⚠️ 转述 DAMA 系口径）。
工程上它们必须降解为**可断言的 SQL 谓词**，否则只是墙上的海报：

| 维度 | 断言形态（🔧E2 实测过的写法） | 示例 |
| --- | --- | --- |
| 完整性 | 空值率 ≤ 阈值 | `count(*) FILTER (WHERE email IS NULL)/count(*)` |
| 唯一性 | 键去重相等 | `count(*) = count(DISTINCT id)` |
| 有效性 | 值域/正则 | `count(*) FILTER (WHERE age NOT BETWEEN 18 AND 90)` |
| 一致性 | 跨表引用 | `ANTI JOIN` 找不到父即违约 |
| 及时性 | 水位线滞后 | `max(updated_ts)` 与 now 的差 |

## 2. 🔧E2 实测：20 行 SQL 规则引擎

方法（`experiments.py`，seed=42）：构造 20,200 行脏帧（pandas 注入 1% 空 email、
约 2% 越界 age、复制头部 200 行制造重复），`d.register("raw", df)` 注册进 DuckDB，
规则以「名字→单值 SQL」字典执行，全部结果落 JSON。

实测输出（原样）：
- `email_null_rate = 0.01`（注入 1% → 检出 1%，精确）；
- `id_uniq = false`（200 行重复被布尔断言捕获）；
- 越界 age 行数 = **404**（注入比例含随机重叠，检出以 SQL 计数为准——诚实登记：
  注入脚本按 `i%50` 标记 400 个 200 岁 + 重复行带来 4 个额外命中）；
- ANTI JOIN 引用完整性演示返回 0（演示构造使所有 cust 可配；规则本身语义已在
  脚本中验证可执行，该 0 是**数据属性**而非规则失效，登记以免误读）。

结论：规则引擎的内核就是「SELECT 单值的 SQL + 阈值比较 + 结果入库」三步；
Great Expectations 们提供的增量是**版本化的期望库、数据文档与校验历史**
（✅ https://docs.greatexpectations.io/docs/ ，2026-10-01 curl -sIL 200），
而非什么不可替代的算法。

## 3. 两种强制力：事前约束 vs 事后断言

- **SQLite CHECK（🔧 硬拦截实证）**：`CREATE TABLE t(id, age CHECK(age BETWEEN 18 AND 90))`
  后插入 age=200 → `IntegrityError: CHECK constraint failed`，**写入即失败、无脏行落盘**。
  这是数据库层的质量"宪法"；代价是只适用于自己拥有 schema 的新表，管不了外部源。
- **事后断言（规则引擎）**：面向摄取流，脏数据**先落 ODS 再检出**，可保留证据
  （quarantine 表）、可统计趋势（09 章）；代价是错误已经存在过。
- 工程配平：**目标层用约束、来源层用断言**；约束管"我生成的数据"，断言管"别人给我的数据"。
- ⚠️ DuckDB 亦支持 CHECK/PRIMARY KEY（本机可验），但批量摄取路径常为绕过校验走
  CTAS——"约束在装载路径上是否生效"要按引擎行为逐一测，本册只对 SQLite 的
  IntegrityError 行为做 🔧 断言。

## 4. 质量分数、阻断与告警的三档语义

- **阻断档**（blocker）：键重复/必填塌方 → 停管道，坏批次进 quarantine，人来看；
- **告警档**（warning）：空值率超阈值 → 放行 + 通知数据 owner（治理线的责任接口）；
- **观察档**（info）：分布漂移、新鲜度滞后 → 只记录，供周报与趋势。
- 分数化：`score = Σ(通过规则×权重)/Σ权重`，挂到 05 章目录表的表级实体上——
  **质量结果本身就是运营元数据**，这一句是 09 章闭环的铰链。
- 反模式：把全部规则设成阻断（管道天天红→无人看红）；阻断位只留给
  "下游会算错钱"的规则。对读
  [../Data_Observability_for_Data_Engineering/00-总览与阅读地图.md](../Data_Observability_for_Data_Engineering/00-总览与阅读地图.md)
  （其"五支柱"把 freshness/schema/volume 与本章三类断言一一映射）。

## 5. 规则即测试：把质量挪进 CI

- 规则库与管道代码同仓、同 review、同版本；
- **种子数据测试**：规则本身要用"已知脏/已知净"的小 fixture 回归（🔧E2 的
  注入-检出配对即该测试的现场版：注入 1% → 检出 0.01 才算规则没写错）；
- schema 变更触发规则重审：加列不改规则=规则库腐烂的开始（05 章漂移检测输出
  应把"新增列未配规则"列为一种 finding）；
- dbt 对照：`dbt test` 把断言声明进 YAML 并从 manifest 生成 SQL——声明式与本册
  命令式（🔧E2 手写 SQL）等价物互译，深度对读
  [../Unlocking_dbt/00-总览与阅读地图.md](../Unlocking_dbt/00-总览与阅读地图.md)。

## 6. 规则样例库（可直接抄进 🔧E2 的 rules 字典）

```sql
-- 完整性（阻断档）：必填塌方
SELECT count(*) FILTER (WHERE key_col IS NULL) = 0 FROM t;
-- 唯一性（阻断档）
SELECT count(*) = count(DISTINCT key_col) FROM t;
-- 值域（告警档）：占比式
SELECT count(*) FILTER (WHERE amt < 0) / count(*) <= 0.001 FROM t;
-- 引用完整性（告警档）：孤儿计数
SELECT count(*) FROM t LEFT JOIN dim d ON t.dim_id = d.id WHERE d.id IS NULL;
-- 新鲜度（阻断档）：水位线滞后分钟
SELECT datediff('minute', max(updated_ts), now()) <= 60 FROM t;
-- 体量哨兵（观察档）：行数环比突变
SELECT abs(count(*) - {prev_n}) / {prev_n} <= 0.2 FROM t;
-- 一致性（告警档）：聚合对账
SELECT abs((SELECT sum(amt) FROM t) - (SELECT sum(amt) FROM upstream)) < 0.01;
```

- 七条覆盖 §1 表格的五类断言；`{prev_n}` 类占位由 05 章目录的历史行注入——
  再次演示"质量结果与元数据互为表里"（09 章闭环的微观样本）。
- 每配一条规则自问：误报时谁来关？关错时谁背？答不出就先配成观察档。

## 核心概念速览（中英对照）

1. **质量六维** — Quality dimensions：完整/准确/一致/及时/唯一/有效，须降解为 SQL 断言。
2. **空值率断言** — Null-rate assertion：`FILTER (WHERE col IS NULL)` 占比对阈值（🔧E2）。
3. **唯一性断言** — Uniqueness assertion：`count(*)=count(DISTINCT key)`（🔧E2 检出 false）。
4. **CHECK 约束** — Column/table CHECK：写入即校验的数据库层硬拦截（🔧E2 IntegrityError 实证）。
5. **规则引擎** — Rule engine：名字→单值 SQL→阈值→结果入库的三步循环（🔧E2）。
6. **Quarantine** — 隔离表：被阻断批次的旁路存放，保留证据不阻塞好数据。
7. **阻断/告警/观察** — Blocker/Warning/Info：规则命中后的三档处置语义。
8. **质量分数** — Quality score：加权通过率，作为运营元数据挂到目录实体。
9. **期望库** — Expectation suite：GX 式版本化的规则集合与校验历史（✅ docs.greatexpectations.io）。
10. **规则回归测试** — Rule CI：规则本身用脏/净 fixture 验证"规则没写错"。
11. **新鲜度** — Freshness：max(事件时间)与 now 之差，及时性维度的可计算形态。
12. **声明式 vs 命令式断言** — Declarative vs imperative checks：dbt YAML 与手写 SQL 两种载体。
