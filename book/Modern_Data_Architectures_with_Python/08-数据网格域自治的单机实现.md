## 2. 🔧E5 实测：域自治 + 联邦组装

方法（`experiments.py`）：

1. 三域各建一个独立 DuckDB 文件并自造数据：
   domain_a.db→orders(100,000 行)、domain_b.db→shipments(50,000)、domain_c.db→payments(30,000)；
   **每域一个进程内连接建库后即 close**——生命周期互不依赖（自治的第一证明：
   没有共享 schema、没有中央写入者）。
2. 联邦层（第四个空连接）：`ATTACH 'domain_a.db' AS da; ... AS db; ... AS dc;`
   然后每域暴露一个 `CREATE VIEW`（orders/shipments/payments）——联邦层的
   **发布面**，域改内部实现、视图契约不变（数据产品"接口与实现分离"的文件版）。
3. 跨域查询：`SELECT count(*) FROM orders o JOIN payments pm ON o.id%30000=pm.id`
   **实测 rows=100,000**，三个物理隔离的库在一次 SQL 内完成联接。

```sql
ATTACH 'domain_a.db' AS da;  -- 域 A 加入联邦视野，不复制数据
CREATE VIEW orders AS SELECT * FROM da.main.orders;  -- 产品契约面
```

4. 治理挂接（把 E5 连回 E3/E4）：联邦视图注册进 05 章 catalog（eng='federated'），
   视图定义 SQL 交给 06 章解析器——**跨域血缘自动出现在边表**（da.main.orders 的
   限定名歧义问题即 E4 登记坑的联邦版，边界声明：手撕原型只到这一步）。

## 3. 数据产品契约：从口号到三张表

- 产品契约的可执行最小集：①schema+语义文档（05 章 catalog 行+业务元数据列）；
  ②质量 SLA（04 章规则结果按域聚合）；③新鲜度承诺（水位线滞后指标，02/04 章）。
  三件全部落表后，"消费方是否被兑现契约"=SQL 可断言——这就是

  所列可供性的工程基座。
- 对读治理面：契约的**违约处理**（谁仲裁、如何下架）归治理线（
  [../Understanding_Data_Governance/03-数据所有权与管理者职责.md](../Understanding_Data_Governance/03-数据所有权与管理者职责.md)）；
- 反模式：把"每个微服务配个库"当域自治——E5 的域边界画在**业务语义**
  （订单/物流/支付），不是技术进程；机械拆库得到的是新的沼泽（⚠️ 转述 Mesh 册警告）。

## 4. 平台之问：E5 离"自助平台"还差什么

- 差**多租户与供给自动化**：脚本手工建三域 vs 平台按申请生成域+配额+凭证；
- 差**计算面分离**：E5 联邦查询跑在单进程，真实平台是各域自带算力；
- 差**策略执行点**：ATTACH 即全权可见——没有行/列级授权层（Unity Catalog 式
  强制面见 [../Data_Governance_with_Unity_Catalog/03-访问控制与特权管理.md](../Data_Governance_with_Unity_Catalog/03-访问控制与特权管理.md)，⚠️ 平台行为转述）；
- 不差什么：**组合性证明**已成立（§2.3 一行 JOIN 跨三库）。
- 结论：E5 的价值=把 Mesh 论文里"逻辑集中治理、物理域内自治"一句话变成可 `ls`
  的六个文件；往上每一层都是工程预算问题，不是概念问题。

## 核心概念速览（中英对照）

1. **域自治** — Domain autonomy：域对数据全生命周期负责，存储/算力不共享（🔧E5 独立文件库）。
2. **数据产品** — Data product：对外提供契约化可消费面的域资产（🔧E5 联邦视图）。
3. **联邦组装** — Federated composition：不复制数据、经 ATTACH/视图跨域查询（🔧E5 实测）。
4. **发布面/契约面** — Publishing interface：域内部实现与对外视图解耦（🔧E5 CREATE VIEW）。
5. **可供性** — Affordability/affordances：产品对消费方的可用性承诺（Data_Mesh 册原语）。
6. **产品契约三件套** — Contract trio：schema+质量 SLA+新鲜度，全部可 SQL 断言。
7. **违约仲裁** — Breach arbitration：契约未兑现时的治理流程（治理线职责面）。
8. **ATTACH** — 库联接：DuckDB 把外部库文件挂进本会话命名的机制（E5 联邦原语）。
9. **策略执行点** — PEP：授权决定被强制执行的位置，E5 已知缺失项。
10. **语义边界** — Semantic boundary：域按业务含义而非服务进程切分（§3 反模式）。
11. **自助平台** — Self-serve platform：域的生成/供给/计费自动化层（§4 差距清单）。
12. **数据即产品 vs 数据即文件** — Product vs dump：有无契约与 owner 的分界。
