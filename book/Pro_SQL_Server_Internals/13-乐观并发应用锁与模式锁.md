## 核心精讲（转述 + ⚠️）

### 14 字节换来什么
书把行版本化拆成两问（转述 ⚠️）：谁写（事务戳）、下一版是谁（版本指针），外加单位序号支持同一事务内多改。开销三笔：行宽（8060 上限被蚕食、页行数下降）、版本生成 IO（tempdb）、清理保留线。**开关在库级**（READ_COMMITTED_SNAPSHOT / ALLOW_SNAPSHOT_ISOLATION），对已开表无差别生效——书中提醒这是"全库手术"不是"逐表调料" ⚠️。

### RCSI 与 SNAPSHOT 的语义分水岭
- RCSI：每条语句一个快照点。副作用：同一事务内两条语句可能看到不同世界（非幂等的"先查后改"在 RCSI 下仍可能踩到更新的已提交版本——书中用库存扣减例 ⚠️）。
- SNAPSHOT：事务级一致视图 + 提交时"我读过的行被别人改了吗"检测。写写冲突直接回滚牺牲者；它不防"幻读进谓词集"的更新路径（书中给出的经典坑：SNAPSHOT 事务看不到快照后新插入的行，因此"不存在则插入"要靠唯一约束兜底 ⚠️）。
- 迁移成本（书中清单 ⚠️）：动态 SQL/游标兼容、tempdb 容量重估、SNAPSHOT 要求连接会话显式 SET。

### 版本存储的垃圾回收
版本链只能被"清理线程在无人需要时"删（转述 ⚠️）：保留线=min(最早活动事务的快照点)。一个忘记提交的 SNAPSHOT 事务或开着长备份（镜像/日志备份期间的"日志重用等待"联动）会让版本膨胀、tempdb 撑爆；书中给出的排查看法：sys.dm_tran_active_transactions + version_store 相关 DMV 找最老事务。RCSI 下未结束事务同样拖清理，但通常只有"跨快照点"的事务才疼。

### 应用锁：把锁管理器当协调器用
第 22 章（4 页，主题块 ⚠️）：sp_getapplock 在 (资源名, 锁模式, 期限 SESSION/TRANSACTION, 超时, 允许者) 上拿一把"引擎不理解的资源"锁。书给的三类用例：单飞任务（防作业双跑）、业务对象序列号生成、跨表复合操作的互斥。要点：锁随事务释放最安全；资源名基数要有限（每行一个名=把锁内存当字典烧 ⚠️）。

### 模式锁与在线运维
SCH-S 在查询编译期获取、执行结束释放（书中机制 ⚠️）；SCH-M 是 DDL 的门票，且**不兼容一切**。于是经典事故：长查询持 SCH-S → ALTER 排队持 SCH-M → 后续所有新查询排在 ALTER 后面集体挂起。第 23 章的解药阶梯：① 低优先级锁（2014：MAX_DURATION=0 或数分钟，ABORT_AFTER_WAIT=SELF/BLOCKERS）；② 调度窗口+kill 阻塞者脚本（书的时代做法 ⚠️）；③ 在线索引操作减少持 SCH-M 的时长（仅收尾一小瞬 ⚠️ 转述）。锁分区一节交代的是锁分析器内部分片（同表不同 HOBT/区间落在不同分析器分区，降低调度器串行点），属"理解现象"层知识 ⚠️。

### RCSI 迁移检查单（21 章"全库手术"论的操作化 ⚠️）
书中把库级开关定位为基础设施手术而非逐表调料（转述 ⚠️），落地四步盘点：① 清点 JOIN 型/自连接 UPDATE-DELETE——行版本化下写路径要生成版本，放大成本先估；② 清点"借 S 锁副作用做互斥"的老代码（先 SELECT FOR SHARE 再改的土办法）——S 消失后这些代码裸奔，改法是从 UPDATE 原子进入或显式事务+重试；③ tempdb 容量与隔离评估（版本存footprint 随更新率涨）；④ 建立"最老活动事务/快照年龄"监控——它就是保留线的闹钟 ⚠️。

### 应用锁三种正确姿势与一种滥用（22 章用例展开 ⚠️）
书中三类用例按机制展开（转述 ⚠️）：单飞互斥——作业启动先在"任务 ID 资源名"上拿 SESSION 级锁+超时，防多实例双跑；业务序列号——先锁"计数器根"再取值递增，TRANSACTION 期限随提交自动放行，避免跳号空洞；跨表复合互斥——把多表操作映射到"聚合根"单一资源名上，用一把粗粒度逻辑锁替代多条行锁的排序难题，死锁环直接构造不出来。滥用形态：资源名按行/按用户无限增长——锁管理器被当字典用，内存与排队双双退化；正解永远是**有限、可枚举的资源名集合** ⚠️。

## 本章结论速记

- 乐观=用 14 字节+tempdb 买"读不挡写"。
- RCSI 治阻塞，SNAPSHOT 给一致视图，两者都不治写写冲突。
- SI 防丢更新不防"快照后新行"：upsert 交给唯一约束兜底。
- 低优先级锁只救 DDL 拿 SCH-M，不救 DML 死锁。
- 应用锁资源名要有限可枚举，否则锁管理器被当字典烧。
- 长事务是版本存储的债主：监控最老事务=监控 tempdb。
- 应用锁=给业务资源上引擎队列，替代轮询与自旋。
- SCH-M 事故链=长查询→DDL→全员；低优先级锁是官方解法。

## 工程模式与常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "开 RCSI 就没有阻塞了" | 写写仍 X 锁互斥；只是 S 锁消失 ⚠️ |
| "SNAPSHOT=可重复读" | 冲突检测语义（回滚牺牲者）比 SQL 标准 RR 强，但看不到新行导致 upsert 坑 ⚠️ |
| "版本存储在用户库" | 默认 tempdb（2019+ 持久化内存可选 ⚠️ 后时代）；容量规划算它一份 |
| "applock 可以随便命名" | 名字基数×持锁时长=锁内存与排队；用有限枚举资源名 ⚠️ |
| "ALTER 卡住就先 kill 查询" | 正解是低优先级锁+超时+重试；裸 kill 丢业务（书中脚本亦如此定位 ⚠️） |
| "事务里带用户交互无所谓" | 24 章头号禁令：连接/锁/版本三债同挂 ⚠️ |
| "RCSI 之后 UPDATE 里的读也不加锁" | 被修改行的读取仍走写路径+版本生成；"乐观"指的是别的读者，不是自己 ⚠️ |
| "SNAPSHOT 下的 SELECT 不占资源" | 它仍占 worker、沿版本链回溯、并把保留线拉老——最老快照的头号来源 ⚠️ |
| "applock 拿了不显式释放也安全" | SESSION 期限的锁活到连接关闭；连接池里=下一个借到该连接的请求莫名排队 ⚠️ |
| "在线重建索引就不怕 SCH-M" | 在线操作只在开始/收尾两瞬拿模式锁，窗口里长查询照样能挂起它（接 23 章 ⚠️） |

## 机制链条

```
UPDATE row ──▶ 旧版本 {戳, 指针, 序号} 拷入版本存储(tempdb)
新读者(RCSI) ──▶ 按语句快照点沿版本链回溯 ──不再等待 X 锁
清理线程 ──▶ 保留线 = 最早活动快照 ──▶ 链尾可删
长事务 ──▶ 保留线冻结 ──▶ 版本链膨胀 ──▶ tempdb 告警
```

## 核心概念速览（中英对照）

1. **行版本化** — Row Versioning：把旧版本搬去版本存储的乐观基座。
2. **14 字节行尾** — Row Versioning Pointer：事务戳+版本指针+单位序号。
3. **版本存储** — Version Store：tempdb 中的版本链仓库。
4. **RCSI** — READ_COMMITTED_SNAPSHOT：语句级快照的读已提交。
5. **SNAPSHOT 隔离** — 事务级快照 + 提交冲突检测。
6. **丢失更新** — Lost Update：SNAPSHOT 检测出的写写冲突（3960）。
7. **保留线** — Oldest Active Transaction：决定版本何时可清。
8. **应用锁** — Application Lock：sp_getapplock 命名的逻辑资源锁。
9. **SCH-M / SCH-S** — 模式修改/稳定锁：DDL 门票与查询影子。
10. **锁分区** — Lock Partitioning：锁分析器内部分片降争用。
11. **低优先级锁** — Low-Priority Locks：WAIT_AT_LOW_PRIORITY 协商式拿锁。
12. **ABORT_AFTER_WAIT** — NONE / SELF / BLOCKERS 三态退出策略。
13. **事务策略** — Transaction Strategy：短、顺、批、乐观四原则。
14. **版本链长** — Version Chain Length：读旧行要回溯的指针跳数，行版本化退化的隐性指标（书以现象描述 ⚠️）。
15. **单飞互斥** — Single-flight Lock：应用锁经典用法——防作业/初始化双跑。

## 最新演进与工业实践

- **RCSI 事实默认化**：Azure SQL DB 出厂开启；本地版仍默认关，但微软与社区的"新库先评估 RCSI"已成共识（[事务与内存优化表](https://learn.microsoft.com/en-us/sql/relational-databases/in-memory-oltp/transactions-with-memory-optimized-tables) ✅ 同域页；RCSI 专页未在本包验证清单，方向性描述 ⚠️）。
- **2022+ 的在线 DDL 面**：低优先级锁扩展到更多 ALTER 形态、RESUMABLE 索引操作让"建索引被锁打断"可断点续传（条目名以官方 2022/2025 发布页为准，本包仅验证两页存在：[2022](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2022) ✅ / [2025](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025) ✅）。
- **ADR 兜底长事务**：事务本地恢复+乐观快照保留改进，"一个未提交事务拖垮版本清理"的痛在开启 ADR 后显著缓解（[ADR](https://learn.microsoft.com/en-us/sql/relational-databases/accelerated-database-recovery-concepts) ✅）。
- **tempdb 进内存**：持久化内存（Intel Optane 路线，2019 起）可把版本存储放到 PMEM——硬件线 2024+ 收缩，机制思路保留 ⚠️（趋势性描述）。
- **工业实践**：高并发 OLTP 库"RCSI+应用锁单飞+低优先级在线 DDL+最老事务告警"四件套是 2024–2026 各大 runbook 的稳定组合；本章四章内容正好各供一件 ⚠️（模式性描述）。
- **官方语法页补齐（二轮核验）**：sp_getapplock/sp_releaseapplock 的参数面（资源名/模式/SESSION 与 TRANSACTION 期限/超时）现行文本见 [sp_getapplock](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql) ✅（curl 200，2026-09）。
- **隔离级别总表**：RCSI/SNAPSHOT/SERIALIZABLE 的现行官方语义页已核验：[SET TRANSACTION ISOLATION LEVEL](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql) ✅（二轮 curl 200）——上文"RCSI 专页未验证"的口径由该总表页部分补上（专页本身仍未直引 ⚠️）。
- **ADR 之后再读版本存**：开启 ADR 后"最老事务冻结清理"的压力面被事务本地恢复重构，保留线监控指标要随之改写（复用已验证页 [ADR 概念](https://learn.microsoft.com/en-us/sql/relational-databases/accelerated-database-recovery-concepts) ✅；机制细节 ⚠️ 以官方为准）。
