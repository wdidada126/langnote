| Much Ado About Data Row Size | 物理行 ≠ 内存行：内存中每列另有开销（作者给出"每行每列若干字节"的估算式，具体数字 ⚠️ 转述待核验） | 缓冲池被宽行挤爆是常见隐性故障 ⚠️ |

## 核心精讲（转述 + ⚠️）

### 页与行的物理布局
书的讲法：一个 8KB 页去掉 96 字节页头（具体开销数字 ⚠️ 转述），单行最大 8060；行以固定长前部 + 可变长尾部 + 中间偏移数组（var-len offset array）编码。堆表的槽数组还承担"删除后空间复用"的登记职责。对照其他引擎：这与 InnoDB 的 compact 行格式（NULL 位图 + 变长列表 + 记录头 5 字节）是同一问题的不同解法——见 [../MySQL技术内幕_InnoDB存储引擎2.md](../MySQL技术内幕_InnoDB存储引擎2.md)。

### 溢出与 LOB 树
书中区分三代：`text/ntext/image`（旧式，10 字节指针 + textmap 页）、`varchar(max)/varbinary(max)`（LOB 树，16 字节指针内嵌 PAGE_ID/时间戳/16 位递增数）、row-overflow（仍在表数据流中，但走独立页链）。作者反复强调：**LOB 指针列本身占行内空间**，把大对象放得离查询列越远，行内越紧凑 ⚠️。

### 分配映射与 IAM 扫描
GAM/SGAM/PFS 三页族管理"区/页"两级分配；表通过 IAM 链知道自己在用哪些区，所以**堆表 IAM 扫描天然无序**——这是第 2 章"堆 vs 聚集索引"的第一个伏笔。作者给出的排障钩子：分配映射页上的 `PAGELATCH_EX`（2:1:1、2:1:3 等）热点是 tempdb 并发问题根因，为第 12/27 章埋线 ⚠️。

### 行大小：物理 vs 内存
本章标题党但实用：内存中每列有额外描述开销、行还有状态字节数组，宽行把缓冲池"内存账"打爆后，表现为读同一张表越来越慢 ⚠️。工程含义：别把"能放下"当"放得下"，行内字节数要按内存放大系数估 ⚠️。

### ALTER TABLE 的两种代价（转述 ⚠️）
- **元数据级**：加可空列、加带常量 DEFAULT 的 NOT NULL 列——只改 schema，不重写行；旧行读取时按"缺失列=默认值"合成 ⚠️。
- **重写级**：改列类型（如 int→bigint）、改列为 NOT NULL（原可空）等需要触碰每一行；书里用演示说明"在线性"取决于版本（企业版 ONLINE 索引路径可缓解 ⚠️）。
- 教学示意（不参与构建）：`ALTER TABLE T ADD c VARCHAR(50) NULL;` 之后 `DBCC PAGE` 观察旧行不变——这是本书第 1 章经典验证路径的**描述**，非实测 ⚠️。

## 本章结论速记

- 一切性能讨论从"页"开始：8KB、8060、区、分配图页——后 34 章反复回到这套物理模型。
- 堆表没有"顺序"这回事：槽数组与 IAM 决定你看到的一切扫描行为 ⚠️。
- `SELECT *` 的代价不是列多，而是**页多**（溢出页/LOB 页被拖入）⚠️。
- 行在内存里比在磁盘上"胖"，缓冲池按内存行记账 ⚠️。
- 加列多数免费，改列多数昂贵 ⚠️。

## 工程模式与常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "一行只能 8060 字节，放不下就报错" | 可变长列会自动进 ROW_OVERFLOW 页；报错的是固定长列总和超限 ⚠️ |
| "SELECT * 方便" | 把溢出页/LOB 页全拖进缓冲池；页分裂统计、内存 grants 都会失真 ⚠️ |
| "文件组 = 性能开关" | 文件组只是分配边界；跨组并行读要多个文件+多盘才有意义 ⚠️ |
| "日志也属于文件组" | 日志不属于任何文件组；备份/恢复粒度差异的根源 ⚠️ |
| "加列要重写全表" | 多数加列是元数据操作（NULL 填充）；把 NOT NULL DEFAULT 常量加列也做成元数据 ⚠️ |
| "删除行会立刻归还空间给操作系统" | 页内空间进空闲槽位复用；整页空了也仍属该表（IAM 位图），要靠收缩/重建才易手 ⚠️ |
| "text/ntext 还能新建" | 微软官方已标 deprecated，新项目用 (max) 类型（[create-table 文档](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-table-transact-sql) ✅） |

## 延伸转述：书中判断力小题（转述 + ⚠️，非原书逐字）

1. **问**：一张空表为什么占 0 页？
   **答**：页按需分配（IAM/分配图语境，书中机制 ⚠️）——空表没有页就没有 I/O，TRUNCATE 后才"归零重来"。
2. **问**：为什么删除大量行后 `sp_spaceused` 显示"已用空间"不降？
   **答**：空页仍归该对象（IAM 位图不放手），空间在对象内部复用；归还需要 DELETE 后整页空置+收缩/重建 ⚠️。
3. **问**：一张 3 列各 3000 字符的 varchar 表能建吗？
   **答**：能——超长可变长列进 ROW_OVERFLOW 页，行内存 24 字节指针；但每次读全三列=三条页链 ⚠️。
4. **问**：页分裂为什么"各留一半"而不是"挪一行"？
   **答**：为未来顺序插入预留同页空间，摊薄分裂频率；随机键下这半页预留变成空的碎片 ⚠️（第 5 章主题）。
5. **问**：DBCC CHECKDB 报的页损坏和分配图有什么关系？
   **答**：一致性检查沿 IAM/PFS/GAM 交叉验证归属（书中提及 ⚠️ 细节未展开）；分配链断裂表现为"页丢失/泄漏"。
6. **问**：为什么书中演示爱用 `DBCC PAGE` 的打印模式 1/2/3？
   **答**：0 看结构、1 看行十六进制、2 看槽数组、3 综合——本章一切"页上现实"的观察入口 ⚠️（描述性，非实测）。
7. **问**：文件自动生长和页分配是同一件事吗？
   **答**：不是。生长是文件级扩容（可能瞬间完成取决于零初始化策略 ⚠️），分配是把页挂进对象 IAM；两者混淆是容量规划常见错。
8. **问**：一页能放多少行由什么决定？
   **答**：min(8060, 页可用空间/内存行宽)，且固定列与可变列头部另有开销——"行宽账"要按内存放大系数算 ⚠️。

## 核心概念速览（中英对照）

1. **页** — Page：SQL Server 最小 I/O 与分配单位，8KB。
2. **槽数组** — Slot Array：页尾记录每行起始偏移的数组，行逻辑序与物理序由此解耦。
3. **行溢出** — Row-Overflow：可变长列超出 8060 后迁入独立 ROW_OVERFLOW 页。
4. **LOB 树** — LOB Tree：max/(n)text/image 的页链（+时间戳指针）结构。
5. **区** — Extent：8 个连续页；分统一区（uniform）与混合区（mixed）。
6. **PFS 页** — Page Free Space：每 8088 页描述"空闲空间/是否已分配/页类型"。
7. **GAM/SGAM** — Global/Shared Allocation Map：标记统一区/混合区归属。
8. **IAM** — Index Allocation Map：一张表/分区拥有哪些区的位图链。
9. **页分裂** — Page Split：插入放不下时把页一分为二、各留一半。
10. **内存行大小** — In-Memory Row Size：行在缓冲池中比磁盘更大（每列开销）。
11. **最大行宽** — Max Row Size：一行 8060 字节的硬上限。
12. **IAM 扫描** — IAM Scan：堆表全表扫按分配图而非页号序。
13. **表重建** — Table Rebuild：ALTER 部分列类型改变引发的物理重写。

## 最新演进与工业实践

- **BLOB 默认 in-row（版本延续）**：`large value types out of row = 0` 自 2012 起为默认，本章机制至今成立；Azure SQL 与 SQL Server 2019/2022/2025 无本质变化（[create-table 官方文档](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-table-transact-sql) ✅ 200，行为细节 ⚠️ 转述）。
- **JSON 取代部分 XML/LOB 场景**：2022/2025 的 JSON 支持（JSON 类型/索引仍按 LOB 存储）让"半结构化列"回到行内思路 ⚠️，参见 [SQL Server 2022 新特性](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2022) ✅。
- **Azure SQL Hyperscale 的对位**：页仍存在，但数据页持久化到远程存储 + 日志服务（Log Service）独立于计算节点；本地 SSD 做读缓存——"页/区/分配图"的心智模型可用，"盘上布局"不再可观测（[Hyperscale 架构](https://learn.microsoft.com/en-us/azure/azure-sql/database/hyperscale-architecture) ✅）。
- **工业实践**：宽表拆垂直表、避免 `SELECT *`、把大对象放独立表按主键取，仍是 2024–2026 的 OLTP schema 评审硬条目（通用工程共识；量化收益 ⚠️ 无实测）。
