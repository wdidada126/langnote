## 核心精讲（转述 + ⚠️）

### 优化器的两步半流程
书把优化拆成（转述 ⚠️）：**简化**（代数重写：去冗余、常量化、外连接退化判定）→ **按访问路径枚举备选**（每个候选=树×索引×JOIN 序的组合）→ **自底向上代价回填**（依赖统计与"每 CPU/每 IO"内部常数）。关键工程含义：备选生成受启发式剪枝（书中转述"不会穷举"），所以**给索引=给备选**；坏统计=坏价格=坏选择。

### 火山模型的成本账
Pull 式 next() 一行一调：CPU 账按行×算子深度算（书中解释 NLV 低内存但高 CPU 的由来 ⚠️）；哈希/排序先阻塞全部输入再吐（breakers：阻塞算子=内存授予+tempdb spill 风险，接 03 授予）；无 breakers 算子（NL join、流聚合）适合 OLTP 流式。列存批模式（接 18）正是对火山模型的"每批 900 行"改造 ⚠️——书中以此解释列存为何快。

### 提示的等级与副作用
书按侵入度排提示（转述 ⚠️）：USE PLAN（最重，全计划注入）→ 语句级 JOIN/MERGE 提示 → 表级 INDEX/FORCESEEK → FAST N（只改优化努力不改结构）。共同副作用：**数据分布变了提示不自动变**——提示是"冻结的判断"。FORCESEEK+索引键匹配失败会直接无计划可执行；NOEXPAND 才让优化器看见索引视图本体（接 07）⚠️。

### 计划缓存的命中判定与参数嗅探
缓存键是"清洗文本+环境位"（转述 ⚠️）：注释/大小写不敏感但 ANSI 选项/数据库/全名敏感。参数嗅探（26 章 7 页）：存储过程首次执行按实参生成计划→形状类查询（同表不同谓词）互相"串味"。书的解药谱按侵入度：① 语句级 OPTION(RECOMPILE)（小查询最省心，编译成本换计划贴合）；② OPTION(OPTIMIZE FOR UNKNOWN/值)；③ 延迟编译局部变量（书中称"最笨也最可靠"）⚠️。判断"是不是嗅探病"的指纹：同一过程、不同参数、plan 里 estimated vs actual rows 差数量级（书给 DMV 取证 SQL 骨架 ⚠️）。

### Ad-hoc 与自动参数化
未参数化字面量的风暴：书中演示优化即配置（optimize for ad hoc workloads）只存存根、第二次形状命中才存计划；自动参数化只救"简单"语句（书中形态图 ⚠️）。工程结论：应用侧永远参数化，别赌引擎替你救 ⚠️。

### 计划强制的治理阶梯（书中"提示/指南"路线与后时代合流 ⚠️）
书里给提示注入排了三档姿势（转述 ⚠️）：先在语句级用 OPTION 验证（跟查询走、随代码回滚，最容易退役）；再进 plan guide（与代码解耦、DBA 侧部署，适合不能改的第三方 SQL）；USE PLAN 全计划注入只作急救。当代治理把第四档交给 Query Store：按运行时统计挑"已知良好计划"再 force plan，与 SQL 文本解耦。纪律一脉相承——**每个强制计划都要写明退役条件**（统计修好了？索引补上了？CE 版本回退了？），否则它就是下一代考古者的谜题 ⚠️。

## 本章结论速记

- 计划是统计的价格投影：先治统计再怪优化器。
- 每个强制计划都要写好退役条件，提示不是传家宝。
- 火山模型：行级 CPU 账 + 阻塞算子的内存/tempdb 账。
- 三 JOIN 各吃前提：小集+索引→NL，双序→Merge，双无序→Hash。
- 提示=冻结的判断，进计划指南前先想清楚谁来退役它。
- 缓存命中靠文本与环境一致；嗅探靠 RECOMPILE/OPTIMIZE FOR 管理。
- 字面量风暴用"优化即配置"止血，根治在应用侧参数化。

## 工程模式与常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "计划慢是优化器笨" | 多数是统计/索引缺位下"合理但错"的选择；先看估计 vs 实际 ⚠️ |
| "RECOMPILE 太贵不敢用" | 书给门槛感：编译成本<<坏计划成本时就是正解；高频小查询慎全句 RECOMPILE ⚠️ |
| "参数嗅探=坏东西" | 它本是复用红利；病在"多形共享一计划"，按分布拆形或用提示 ⚠️ |
| "开优化即配置就不用参数化" | 存根只省内存，第二次仍付编译；应用侧仍应绑参 ⚠️ |
| "USE PLAN 万能" | 指纹对不上直接报错；属急救不属运维 ⚠️ |
| "并行度调高=更快" | 每 DOP 一份内存授予与协调成本；OLTP 单查询并行常亏（书中 CXPACKET 案例 ⚠️ 接 15） |
| "估计≈实际就没问题" | 单算子偏差小而 JOIN 序基数积错仍选坏形态；书按"驱动行数"逐层再核 ⚠️ |
| "自动参数化能兜住所有字面量" | 失败参数化形态直接不救：每次全量编译+单次使用计划，缓存被字面量海淹没（书中实验口径 ⚠️） |
| "存储过程里拼动态 SQL 才能自适应" | 动态 SQL 确实绕开嗅探，但代价是缓存复用面+注入面；先走 RECOMPILE/OPTIMIZE FOR 阶梯再考虑它 ⚠️ |

## 核心概念速览（中英对照）

1. **基数估算** — Cardinality Estimation：优化器的价格引擎。
2. **备选计划** — Candidate Plan：剪枝后参与比价的方案集。
3. **火山模型** — Volcano/Iterator Model：next() 拉行执行范式。
4. **阻塞算子** — Blocking Operator：先吃光输入才吐（Sort/Hash）。
5. **内存授予** — Memory Grant：哈希/排序预批的内存配额。
6. **Spool** — 中间结果暂存算子（行/表/窗口）。
7. **分区交换** — Partition Exchange：并行计划的协调边。
8. **提示** — Hints：INDEX/FORCE ORDER/JOIN/FORCESEEK/NOEXPAND/FAST N。
9. **计划缓存** — Plan Cache：指纹化存取编译成果。
10. **参数嗅探** — Parameter Sniffing：首参塑形共享计划。
11. **RECOMPILE/OPTIMIZE FOR** — 语句级反嗅探双件套。
12. **优化即配置** — optimize for ad hoc workloads：存根止血。
13. **自动参数化** — Auto-Parameterization：简单/失败两档。
14. **计划指南** — Plan Guide：不改代码的提示注入。
15. **已知良好计划** — Known-Good Plan：Query Store 时代按运行时统计挑选、可强制回挂的历史计划 ⚠️（后时代对位）。

## 最新演进与工业实践

- **CE 版本漂移治理**：2014 CE 之后每大版都可能换（130/140/160），官方以数据库兼容级别钉住 CE；2022 起 CE 160 默认，"升级先锁兼容级再灰度"成为标准剧本（[IQP](https://learn.microsoft.com/en-us/sql/relational-databases/performance/intelligent-query-processing) ✅、[2022 新特性](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2022) ✅）。
- **智能查询处理（IQP）家族**：表变量延迟编译、批处理模式内存授予反馈（BMOQG）、交错执行、标量 UDF 内联——本章"授予估算失真"与"UDF 黑名单"两大痛点被逐项接管（[IQP](https://learn.microsoft.com/en-us/sql/relational-databases/performance/intelligent-query-processing) ✅；逐项 GA 版本 ⚠️ 以该页矩阵为准）。
- **Query Store 取代手工取证**：26 章的 DMV 排查套件整体升级为计划回归检测+强制（force plan）+自动调优的图形化底座（[Query Store](https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store) ✅）。
- **自动索引**：2022 Automatic Tuning/Automatic Indexing 在受控负载上自动生成/验证/回滚索引，嗅探与坏索引的运维面开始无人化（[自动索引压缩](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/automatic-index-compaction) ✅ 同域；Automatic Tuning 总览见 Azure 页 ✅：[automatic-tuning-overview](https://learn.microsoft.com/en-us/azure/azure-sql/database/automatic-tuning-overview)）。
- **编译成本的当代账单**：云原生按量计费下 ad-hoc 风暴既烧 CPU 也烧钱，参数化从"最佳实践"升格为"成本红线" ⚠️（趋势性描述）。
- **提示官方总表（二轮核验）**：本章"提示等级论"的现行语法与弃用注记见 [Hints](https://learn.microsoft.com/en-us/sql/t-sql/queries/hints-transact-sql) ✅（curl 200，2026-09）；书中表级/查询级/语句级三分法与官方分页一致。
