## 核心精讲（转述 + ⚠️）

### 索引视图的准入与代价
准入清单（转述 ⚠️）：视图与表都 SCHEMABOUND、必须先建唯一聚簇索引、基表 DML 在同事务内同步维护视图；不支持外连接等形态（版本限制 ⚠️）。收益场景：读多写少 + 固定聚合（典型 DW 汇总层）；OLTP 高频表上代价可能超过收益——书中用 INSERT 放大演示 ⚠️。企业版才自动查询匹配（view matching，优化器把对基表的查询重定向到视图；其他版本要 NOEXPAND ⚠️ 版本口径以 editions 页为准）。

### 标量 UDF 的性能陷阱（2014 语境）
本章与 26/14 章形成三角：谓词里的标量 UDF → 优化器视为不透明黑盒 → 每行调用 + 行模式执行 → 并行计划被压制。书的处方（转述）：能用 iTVF 不用标量；能用计算列（PERSISTED，接 04）不用函数；万不得已用"逐行 SQL"外置到应用。这是本书流传最广的经验条之一 ⚠️。

### 多语句 TVF 的估算灾难
固定估算 1 行 → 上游算子内存授予/Join 选型全错 → 大结果集时"先排序再错着排"。书中对比同查询换 iTVF 后的计划翻转 ⚠️。2019+ 的"表变量延迟编译 + 内联"部分化解，见"最新演进"。

### 分区视图与分区表的分工
分区视图跨库/跨服务器仍可（15 章的分区表不能跨实例）；单机场景基本让位于分区表 + CCI（18 文件）。join elimination 依赖 CHECK 约束——这也是"约束有优化器魔法"少见的正面案例 ⚠️。

### 可更新性的形状判定（转述 ⚠️）
"单基表、无聚合/DISTINCT/GROUP BY/计算列参与目标列"的视图可直接 INSERT/UPDATE/DELETE；多表视图要写活必须借 INSTEAD OF 触发器（接 06），此时视图成为"接口"而非"窗口"。书的提醒：DAL 把可写视图当表用时，触发器的集合语义与错误传播路径要一并评审 ⚠️。

### 函数选型的决策树（书中线索重构 ⚠️）
需要"表返回值"：参数化过滤→iTVF；确需多步暂存→临时表+存储过程（接 08/11），别用多语句 TVF 返回大结果；需要"标量派生值"：确定性表达式→PERSISTED 计算列（接 04）；复杂逻辑→iTVF 包装或应用层；只剩"必须标量且含流程控制"才接受标量 UDF，并预算它在 2014 的逐行代价 ⚠️。

## 本章结论速记

- 视图默认是文本级内联；索引视图是唯一真物化。
- 写少的聚合查询适合索引视图；高频表慎入。
- UDF 优先级：iTVF > 计算列 > 存储过程逻辑 > 标量 UDF（2014 语境）。
- 多语句 TVF 的"1 行谎言"是计划雪崩常见起点。
- 分区视图没有消失，它搬到了跨实例分片层。
- 函数形态的选择=优化器可见性的选择：内联即自由 ⚠️。

## 工程模式与常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "视图有性能损耗" | 普通视图零开销（等价内联）；损耗来自复杂嵌套干扰改写 ⚠️ |
| "索引视图随便建" | 严格准入 + 基表写放大；DW/报表库才常态划算 ⚠️ |
| "TVF 返回表总没问题" | 多语句形态估算失真；优先 iTVF ⚠️ |
| "标量 UDF 只是稍慢" | 并行压制 + 阻塞式逐行，可放大数十倍（书演示 ⚠️ 非实测口径） |
| "分区视图过时了" | 跨服务器分片仍无替代 ⚠️ |
| "视图嵌套越深越抽象" | 内联后计划复杂度随层数膨胀，报价与改写都可能失真（书中多层视图反例 ⚠️） |
| "函数缓存了结果就快" | 标量 UDF 的结果缓存（后时代特性）2014 不存在；当时唯一安全牌是内联形态 ⚠️ |

## 机制链条

```
视图引用 ──▶ 编译期内联展开 ──▶ 谓词下推/连接消除（受 CHECK/约束驱动）
索引视图 ──▶ 物化：基表每次 DML 同步维护（同事务）──▶ 读收益×写账单
分区视图 ──▶ 成员 CHECK ──▶ 约束证明裁剪成员表（join elimination）
标量 UDF ──▶ 黑盒：逐行调用、阻断并行、遮挡估算
iTVF    ──▶ 白盒：并入主查询，享受全部改写红利（书的首选 ⚠️）
```

## 延伸转述：书中判断力小题（转述 + ⚠️，非原书逐字）

1. **问**：普通视图会被"物化"吗？
   **答**：永不；它只是查询定义，每次引用都展开 ⚠️。
2. **问**：索引视图为什么强制唯一聚簇索引打头？
   **答**：给物化行集一个稳定定位器（二级索引依赖它）——与基表同一套 B+ 树逻辑（接 02 ⚠️）。
3. **问**：非企业版能用索引视图吗？
   **答**：能建能查，但优化器不自动匹配（需 NOEXPAND 显式指向）——书中反复强调的版次分水岭 ⚠️。
4. **问**：为什么索引视图要求 SCHEMABOUND？
   **答**：物化定义与基表结构必须锁死，否则基表 ALTER 会让物化失去意义 ⚠️。
5. **问**：标量 UDF 在 WHERE 里为何特别毒？
   **答**：每候选行一次调用且优化器无法下推进索引——Seek 变 Scan×行数 ⚠️。
6. **问**：多语句 TVF 何时可接受？
   **答**：小结果、会话内、逻辑复用场景；大结果集交给临时表+过程（书中路线 ⚠️）。
7. **问**：iTVF 能替代参数化视图的所有场景吗？
   **答**：读方向几乎能；写方向需 INSTEAD OF（可写性规则对函数不适用 ⚠️）。
8. **问**：视图上能建全文/列存索引吗？
   **答**：本章时代的限制清单在书里逐项过（列存直接建视图不支持，需基表列存/物化后查 ⚠️ 以官方为准）。
9. **问**：分区视图的成员表能异构（不同服务器）吗？
   **答**：能——这正是分区表给不了的跨实例形态；代价是分布式查询与两阶段提交账 ⚠️。
10. **问**：如何验证视图被内联了？
    **答**：看计划对象名与算子——视图名消失、基表现身即内联；NOEXPAND 场景例外（书给读计划手法 ⚠️）。
11. **问**：UDF 里能 TRY/CATCH 吗？
    **答**：当时函数对错误处理/副作用的限制严（清单 ⚠️ 以官方 CREATE FUNCTION 约束为准），这也是"薄函数"的理由之一。

## 核心概念速览（中英对照）

1. **普通视图** — Regular View：查询定义的内联宏。
2. **索引视图** — Indexed View：物化 + 唯一聚簇索引的持久结果集。
3. **架构绑定** — Schema Binding：依赖锁定，物化前提。
4. **视图匹配** — View Matching：优化器把基表查询重定向到视图（企业版 ⚠️）。
5. **NOEXPAND** — 提示：强制把分区视图当物化表用。
6. **分区视图** — Partitioned View：CHECK 划界的 UNION ALL 成员表。
7. **连接消除** — Join Elimination：按约束裁掉无关连接。
8. **可更新视图** — Updatable View：可直写的单基表形状。
9. **标量 UDF** — Scalar UDF：返回单值函数；2014 不可内联。
10. **多语句 TVF** — Multi-Statement TVF：BEGIN…INSERT…RETURN 表函数，估算=1 行。
11. **内联表值函数** — Inline TVF：参数化视图形态，首选 UDF。
12. **UDF 并行压制** — Parallelism suppression：标量函数导致单线程执行 ⚠️。
13. **结果缓存** — UDF Result Caching：后时代特性，本章当时不存在。
14. **谓词下推** — Predicate Pushdown：内联视图/函数的改写红利。
15. **两阶段提交** — DTC/2PC：跨服务器分区视图的隐性账单 ⚠️。

## 最新演进与工业实践

- **标量 UDF 内联（SQL Server 2019+）**：T-SQL 标量函数终于可内联进计划（带限制），本章"头号性能杀手"标签部分失效；逐表达式/逐对象开关（`DISALLOW_RESULT_CACHING`、TF 6578 等，细节 ⚠️ 以官方为准）（[IQP](https://learn.microsoft.com/en-us/sql/relational-databases/performance/intelligent-query-processing) ✅）。
- **表变量延迟编译 + TVF 内联家族**：2019 IQP 覆盖多语句 TVF 的真实行数反馈；2022 起 Query Store 可自动回滚差计划——本章三大陷阱都有了云/引擎侧的自动解毒路径（[What's new 2022](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2022) ✅）。
- **索引视图的后继**：时态表、物化视图语义在 Azure（Synapse/Fabric 的物化聚合）延续；SQL Server 本体的索引视图能力稳定 ⚠️（Fabric 细节不在本目录断言范围）。
- **工程实践（2024–2026）**：报表层预聚合首选"列存 + 物化视图语义"，索引视图退居存量；新系统里 UDF 的职责大量由视图/iTVF/应用层承担（共识性描述 ⚠️ 无量化）。
