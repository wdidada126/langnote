## 核心精讲（转述 + ⚠️）

### 分区函数/方案的机械模型
转述书中演示 ⚠️：`CREATE PARTITION FUNCTION pf (datetime) AS RANGE RIGHT FOR VALUES (...)` 把值域切成 N+1 段；`CREATE PARTITION SCHEME ps AS PARTITION pf ALL TO (fg1..fgN)` 把段映射到文件组。表的聚集索引键含分区列后，每个"分区"是一棵独立 B+ 树小森林——扫描带谓词时优化器做**分区消除**（只碰命中分区）。关键约束：一个表只能有一个分区依据列，且该列必须进聚集索引键与所有唯一约束键 ⚠️。

### SWITCH 为何"秒级"
`ALTER TABLE ... SWITCH PARTITION n TO empty_table` 只改页上的元数据指针，不搬数据（书中机制 ⚠️）。前提苛刻：两表结构完全同构、索引对齐、目标为空、且切换瞬间持有 SCH-M 锁——任何长查询都能让 SWITCH 排队并阻塞后面一切。书的实战建议：把 SWITCH 放进短事务、先在 staging 表做完索引/约束校验再切 ⚠️。

### 统计信息：分区的阿喀琉斯之踵
书中（以 2012/2014 行为口径 ⚠️）指出：分区表的统计默认只扫部分分区采样（"stats sample 14%" 之类的推导例子），热点新分区可能没进直方图；`UPDATE STATISTICS WITH FULLSCAN` 又太贵。后来的"持久采样率重算"（2016 自动更新按持久采样）与增量统计是分水岭——本书写作时增量统计仅限部分场景且书中持保留态度 ⚠️。

### 索引对齐与异种索引
对齐（aligned）=分区表的每个索引按同一方案切分，才能 SWITCH。书中演示"每分区不同压缩"（冷分区 PAGE 压缩、热分区无压缩，接 04）：一旦压缩不同，索引仍对齐（压缩不进对齐判据 ⚠️ 书中口径），但要单独对分区做 ALTER INDEX REBUILD 并指定目标文件组。SPLIT/MERGE 在有对齐索引时需重建/迁移数据以维持边界——这是滑动窗口最痛的一拍（书中给了 `ALTER TABLE SPLIT RANGE` 会搬数据的警告 ⚠️）。

### 分区视图与前朝今世
分区视图机制（成员表 CHECK + UNION ALL）在 SQL Server 2016 起被官方标注为"仍将支持但不改进"的遗留面（⚠️ 以官方文档口径为准）。书里仍花 8 页讲它，因为当时（2014）它是唯一能做跨服务器异构分区的路线；"表+视图混用"（每分区一表）恰恰预告了后来 Hyperscale/分片中间件的做法 ⚠️。

### 分区消除成立的四条证据（书中口径 ⚠️）
优化期分区消除看四件事（转述 ⚠️）：① 谓词是否直接落在分区键上且为可比较形态；② 边界判定的确定性——非确定函数（GETDATE 类）与变量参与比较时，消除可能推迟甚至失效（书中以表达式形态举例 ⚠️）；③ 消除发生在编译期（静态，字面量/参数可判）还是执行期（动态，如分区键来自另一表的连接列）；④ 索引是否对齐——对齐时算子是"N 棵小树各自 Seek"，失配则回退成大表扫描。判读方法：看计划里 Partition ID 属性/运行时分区数，这是"分区确实带来性能收益"的唯一硬证据 ⚠️。

## 本章结论速记

- 分区的第一收益是可管理性：SWITCH 秒级装载/清除。
- 分区键是宪法：选错列=全表重建。
- 对齐则自由，失配则寸步难行（SWITCH/SPLIT 全赖对齐）。
- 统计按分区失真，是性能侧最大暗雷。
- 消除要读运行时分区证据，不看愿望。
- 冷端先 SWITCH OUT 腾空再 MERGE，边界操作才不会搬数据。
- 分层存储（tiered storage）=分区+文件组+压缩的组合拳。
- 滑动窗口五步：SPLIT→LOAD→SWITCH OUT→MERGE→PURGE。

## 工程模式与常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "分区天然加速查询" | 谓词不带分区键=扫所有分区更慢；消除靠优化器证据不靠愿望 ⚠️ |
| "百万行小表也分区" | 每分区一套页结构/统计开销；书中门槛感：至少亿级且有日期切分键 ⚠️ |
| "SWITCH 随时可做" | 需 SCH-M、目标空表、完全同构；长事务可让它挂起全站 | 
| "SPLIT RANGE 是元数据操作" | 若新边界落进已有数据区间且表有对齐索引，会触发现实数据迁移，长锁 ⚠️ |
| "分区表统计自动准" | 采样可能错过热分区；要看 stats_histogram 的分区覆盖（书中排查法 ⚠️） |
| "分区列有索引就自动消除" | 非确定表达式、变量与 join 推导谓词会把消除压到执行期甚至全扫；看计划运行时分区数才作数 ⚠️ |
| "MERGE RANGE 随时能收边界" | 被合并分区带数据时须物理合并（移行+大事务日志+长锁）；滑动窗口正解是冷端先 SWITCH OUT 腾空再 MERGE ⚠️ |
| "SPLIT 的边界值随便补一个" | 边界切进已有数据区间=现实迁移；新分区永远从"空边界预留段"里长出来才是零搬家 ⚠️ |
| "分层存储和镜像随便搭" | 文件组级还原/部分可用性在镜像与旧式 Log Ship 下受限（转述 ⚠️） |

## 机制链条

```
分区函数 pf（边界值序列）
      │ 绑定
分区方案 ps（边界→文件组）
      │ 聚集索引键含分区列
分区表 = N 棵小 B+ 树 + 1 份逻辑元数据
      │ 索引全部对齐
SWITCH IN / SWITCH OUT（元数据级搬家）
      │ SPLIT/MERGE 维持窗口
滑动窗口：新数据进热端、老数据滑出冷端→压缩→归档→删除
      │ 全程要求：切换两表同构 + 索引对齐 + SCH-M 窗口
统计与消除：分区键谓词定边界 → 运行时分区数=收益证据
```

## 核心概念速览（中英对照）

1. **分区函数** — Partition Function：定义边界值的值域切割。
2. **分区方案** — Partition Scheme：边界段到文件组的映射。
3. **分区消除** — Partition Elimination：优化器裁掉不命中分区。
4. **切换** — SWITCH PARTITION：分区↔表间元数据级整体搬迁。
5. **对齐** — Aligned：索引与基表共用同一分区方案。
6. **每分区表** — Per-partition Table：分区视图混合形态。
7. **分层存储** — Tiered Storage：热冷数据按介质分层。
8. **滑动窗口** — Sliding Window：SPLIT/LOAD/SWITCH/MERGE 循环。
9. **边界右含** — RANGE RIGHT：边界值归属右侧分区。
10. **SPLIT/MERGE RANGE** — 增加/合并边界的两操作。
11. **分区键** — Partitioning Column：行归属的切分依据列。
12. **异构索引** — Unaligned Index：破坏 SWITCH 的索引形态。
13. **增量统计** — Incremental Statistics：按分区维护统计（后时代解药）。
14. **静态/动态消除** — Static/Dynamic Elimination：编译期 vs 执行期的分区裁剪。
15. **部分可用性** — Partial Availability：文件组级在线/离线与片块还原的 HA 接口面。

## 最新演进与工业实践

- **官方口径未变但地位变化**：分区仍是企业版/开发版特性（部分版次受限，标准版曾有 1GB 分区限制 ⚠️ 以官方[分区表和索引](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) ✅ 与版次页为准）。
- **增量统计成熟**：2017+/2019 的 `ALTER TABLE ... UPDATE STATISTICS ... WITH INCREMENTAL` 让热分区统计可控，补上本章最大暗雷（[统计信息](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics) ✅）。
- **自动收缩/自动索引**：2022 Automatic Indexing 与自动页取消（decommission）针对的是索引维护面，未接管分区生命周期（[2022 新特性](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2022) ✅）。
- **Azure SQL Hyperscale 换了维度**：存储计算分离（page server + log stream + 可加读节点），"搬冷数据到便宜盘"的需求被分层存储与按需复制替代——分区从性能工具退回管理工具（[Hyperscale 架构](https://learn.microsoft.com/en-us/azure/azure-sql/database/hyperscale-architecture) ✅）。
- **2025 的对位**：RESILIENT 统计/IQP 继续补采样与估算侧；分区本身无大改（[2025 新特性](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025) ✅）。
- **工业实践**：时序/日志类大表普遍"分区表 + 每分区 PAGE 压缩 + 滑动窗口 + SWITCH OUT 归档到对象存储"；书中五步舞仍是各大厂 runbook 的原型 ⚠️（模式性描述）。
- **官方语法页补齐（二轮核验）**：`UPDATE STATISTICS ... WITH INCREMENTAL / PERSISTED_SAMPLE_RATE`（引入版本 ⚠️ 以该页版本注记为准）的现行参数面见 [UPDATE STATISTICS](https://learn.microsoft.com/en-us/sql/t-sql/statements/update-statistics-transact-sql) ✅（curl 200，2026-09）——本章"统计阿喀琉斯之踵"的官方解药文本。
- **专页缺口声明（二轮）**：官方"滑动窗口实现指南"专页本轮 curl 实测 404，疑路径改版——滑动窗口口径继续以书 338–340 页结构 + [分区表和索引](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) ✅ 总页转述为准，勿引二手博客 ⚠️。
- **Hyperscale/托管实例的对位**：分区切换与 SPLIT/MERGE 在云上仍可用，但"文件组分层搬冷数据"的维度被共享存储架构弱化——把本章 runbook 移植上云前先核对存储形态 ⚠️（描述性论断，架构页见上节 Hyperscale 链接 ✅）。
