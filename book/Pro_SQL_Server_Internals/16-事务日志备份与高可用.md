## 核心精讲（转述 + ⚠️）

### WAL 与检查点的节拍
书中把日志讲成"唯一真相流"（转述 ⚠️）：每次修改产生日志记录→提交只需日志段落盘（组提交）；脏页由检查点按预算异步刷；崩溃后从"上次检查点"起 REDO、再 UNDO 未提交。关键机制账：日志连续写+页随机写——所以日志盘要顺序吞吐、数据盘要随机 IOPS。ARIES 谱系（同事务 ID/页 LSN/WAL）在 [../../db/ARIES.md](../../db/ARIES.md) 有原理层笔记，可对照本章的 SQL Server 工程化实现 ⚠️。

### VLF：环形日志的碎片学
日志文件内部切成 VLF，写入按环推进；截断只能发生在"非活跃 VLF"（转述 ⚠️）。AUTO_GROWTH 次数多→VLF 碎→备份读全文件时 IO 放大、日志清除慢（经典 42023/42024 语境 ⚠️ 书以现象+DBCC LOGINFO 计数演示）。书的处方：初始大小按峰值日写量一步到位、固定增长率、事后整形 ⚠️。

### 备份链的算术
一条可时间点恢复的链=全备+若干差异+连续日志（转述 ⚠️）。恢复时长账=各集还原时间+日志重放时间（前滚+回滚）；书给"全备周末夜+差异每夜+日志每 5–15 分钟"的模板并强调**差异基是全备**——漏日志会让链断、STOPAT 失败。片块恢复（piecemeal）把账拆到文件组：热组几分钟回，冷组小时级跟进 ⚠️（接 10 分层存储）。

### HA 选型：故障域决定技术
书第 31 章的核心是一张"故障域×技术"矩阵（转述 ⚠️）：
- 单机硬件/OS → FCI（共享盘，不防逻辑错误/页损坏）；
- 数据中心级、要可读副本 → AG（同步提交本地=零丢失，异步跨区=可能丢 ⚠️ 边界条件书有明确警告）；
- 库级热备、旧版本兼容 → Mirroring（书如实标"微软宣布弃用路线" ⚠️ 2014 口径，后来确实退役）；
- 粗粒度 DR/低成本 → Log Shipping；读写分担/过滤分发 → Replication（书提醒复制不保证原子切换 ⚠️）。
叠加约束：分层存储+文件组部分在线与镜像不兼容（镜像不支持文件组级还原 ⚠️ 接 10），AG 才接住了这套组合。

### 延迟持久化的取舍
2014 新增 WAIT_AT_DURABILITY(DELAYED)：提交不强制刷日志、按时限组批（默认约 1 秒 ⚠️ 书载口径）。崩溃丢"最近一批已提交"——书中定位：可重放的事件流/遥测写入，绝不用于金融账务；并提示与 AG 同步提交叠加时语义要重推 ⚠️。

### 恢复模型只回答一个问题（29 章收口 ⚠️）
模型选择其实只问"日志保留到哪"（转述 ⚠️）：SIMPLE=保到上次检查点；BULK_LOGGED=再叠加最小日志操作的模糊窗口；FULL=保到上次日志备份、支撑时间点链。常见误读是"SIMPLE 不能备份"——能备份，只是丢时间点维度；书把三档模型对位三种 RPO 等级：先定业务可接受丢多少，再选模型，最后才谈备份链密度——顺序反了就是仪式化运维 ⚠️。

## 本章结论速记

- 日志是真相流：WAL+检查点+恢复模型三件套撑起 ACID 与备份。
- 灾备第一步：先抢尾日志（tail-log backup），再谈还原。
- VLF 碎=全局慢；日志容量要规划。
- 备份链是 RPO/RTO 的数学解，不是仪式。
- HA 技术按故障域选：整机（FCI）/库（AG、Mirror、LS）/数据（复制）。
- 同步提交≠万能零丢失；延迟持久化=可调 D。

## 工程模式与常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "差异备份基是上次差异" | 基=最近全备；差异集随全备后数据页变化累积变大 ⚠️ |
| "日志备份失败=重启就好" | log_reuse_wait_desc 指认原因在先；盲目截断毁链 ⚠️ |
| "FCI 保护数据不出错" | 共享盘上的页损坏照单全收；要配 CHECKSUM/页修复（书载 ⚠️） |
| "AG 同步=跨地域零丢失" | 同步提交把提交延迟绑给对方往返；跨区异步才现实但可能丢 ⚠️ |
| "自动生长开着省事" | 生产日志/数据文件靠自动生长=VLF 碎片+突发写放大（书中运维律 ⚠️） |
| "备份完就安全" | 书强调还原演练与 RESTORE VERIFYONLY/CHECKSUM；没测过的备份=愿望 ⚠️ |
| "尾日志备份是可选动作" | 灾备场景不抢尾日志=最后一段已提交交易永久丢失；书把它列为恢复流程第一步 ⚠️ |
| "BULK_LOGGED 常开提效" | 最小日志操作之后接日志备份会强制文件组离线（书中 2012/2014 行为警告 ⚠️）；只在装载窗口临时切、切回再备份 |

## 机制链条

```
修改 ──▶ 日志记录（连续写）──提交──▶ 日志段落盘（组提交/可延迟 ⚠️）
检查点 ──▶ 脏页落数据文件（随机写）──▶ 截断点前移（受备份链约束）
崩溃 ──▶ REDO(自上次检查点沿日志) ──▶ UNDO(未提交) ──▶ 在线
备份 ──▶ 全/差/日志链 ──▶ 接力 RESTORE WITH RECOVERY/STOPAT ──▶ 时间点机器
HA  ──▶ 日志流复制（Mirror/AG/LS）+ 客户端重连（FCI 名/IP 漂移）
```

## 核心概念速览（中英对照）

1. **预写日志** — WAL：先日志后数据页的提交纪律。
2. **检查点** — Checkpoint：脏页刷盘+恢复起点前移。
3. **VLF** — Virtual Log File：日志文件内部环形段。
4. **日志重用等待** — log_reuse_wait_desc：截断被谁卡住的答案。
5. **恢复模型** — Recovery Model：SIMPLE/BULK_LOGGED/FULL。
6. **延迟持久化** — Delayed Durability：D 可调的组批提交。
7. **差异基** — Differential Base：最近一次全备。
8. **时间点恢复** — Point-in-Time Restore：日志接力+STOPAT。
9. **STANDBY 还原** — 带回滚文件的只读接力副本。
10. **片块恢复** — Piecemeal Restore：文件组级部分还原。
11. **FCI** — 故障转移集群实例：共享盘整机高可用。
12. **数据库镜像** — Mirroring：库级日志流热备（弃用路线 ⚠️）。
13. **AlwaysOn AG** — 可用性组：多库同步+可读副本+组级故障转移。
14. **日志传送** — Log Shipping：计划任务式的粗粒度 DR。
15. **RPO/RTO** — 丢多少/停多久：策略双轴。

## 最新演进与工业实践

- **日志侧**：ADR（2019+）把"回滚+截断"变成后台秒级操作，长事务不再锁死日志增长叙事（[ADR 概念](https://learn.microsoft.com/en-us/sql/relational-databases/accelerated-database-recovery-concepts) ✅）；VLF 管理仍是你自己的事（[日志架构与管理指南](https://learn.microsoft.com/en-us/sql/relational-databases/logs/sql-server-transaction-log-architecture-and-management-guide) ✅）。
- **备份侧**：备份到 URL 已成为标准通道（SMB/blob + 加密 + 不可变存储配合 [Ledger](https://learn.microsoft.com/en-us/sql/relational-databases/security/ledger/ledger-overview) ✅ 的防篡改思路对抗勒索）；"Managed Backup to Azure"演化为 Azure 备份/托管实例自动备份体系（[备份到 URL](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/sql-server-backup-to-url) ✅）。
