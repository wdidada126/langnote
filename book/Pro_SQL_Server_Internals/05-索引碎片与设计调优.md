## 核心精讲（转述 + ⚠️）

### 碎片的因果链（第 5 章主线）
随机键 INSERT → 目标页满 → 一分为二（第 1 章机制）→ 兄弟页散落不同区 → 范围扫描从"顺序读"退化为"跳读"；同时页内空洞让行数/页下降、缓冲池命中率下降。书中反复强调：**OLTP 小范围读对碎片不敏感（定位靠树），敏感的是大范围扫描与备份压缩比** ⚠️。

### 维护决策矩阵（转述）
碎片率高但页数少→不动；小表→重建便宜；大表→REORGANIZE 常态化 + 定期 REBUILD；重建时机避开备份/高峰；2012+ 的分区级重建可把成本切开 ⚠️。ONLINE= 只在企业版（书中版本口径 ⚠️ 以 editions 页为准）。

### 聚簇键的两难与三把钥匙（第 6 章主线）
顺序键（IDENTITY/SEQUENCE）消灭分裂但把插入压到一个热页 → 高并发下 PAGELATCH 热点（与 12/27 章的等待分析闭环）；随机键消灭热点但制造碎片。书的处方（转述 ⚠️）：
- 用 SEQUENCE + CACHE 拿高吞吐且大体递增；
- 用取模/哈希分片键或表分区把热点摊到多叶；
- GUID 必须上则用 NEWSEQUENTIALID/有序 GUID（版本 4 时序前缀等）；
- 或干脆把宽/随机键放非聚簇、聚簇给顺序代理键。

### usage_stats 的正确读法（转述 ⚠️）
`user_updates` 高而 `user_seeks+user_lookups` 低=候选删除；但注意：完整性约束（FK/PK）的索引、归档/查询不 frequent 的报表索引、重启后视图清零，都是"数据会骗人"的场景。

## 本章结论速记

- 碎片是键选择的果，维护策略只能治标。
- FILLFACTOR 是把未来分裂预付掉；REORGANIZE 是事后归拢。
- 聚簇键三原则再加一条：并发热点分布。
- SEQUENCE.CACHE、分区、哈希前缀是打散热页的三板斧。
- 索引合并（consolidation）优先于新增：先清理再补位。

## 工程模式与常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "碎片>10% 就重建" | 小索引重建无感、大索引重建昂贵；先看大小与扫描占比 ⚠️ |
| "GUID 主键必须打散" | 顺序型 GUID（NEWSEQUENTIALID/UUIDv7 思路）与代理聚簇键都可选 ⚠️ |
| "IDENTITY 一定无碎片" | 高并发下它是热页争用之源，非顺序读反而受牵连 ⚠️ |
| "重建索引统计必然新" | 重建按采样重算键统计，且非键列统计不动（接 03）⚠️ |
| "usage_stats 直接删零使用索引" | 重启清零/特殊负载误判，需先跑过完整业务周期 ⚠️ |

## 核心概念速览（中英对照）

1. **内部碎片** — Internal Fragmentation：页内空洞、填充率低。
2. **外部碎片** — External Fragmentation：逻辑序与物理序偏离。
3. **区碎片** — Extent Fragmentation：单表区混用/交错。
4. **填充因子** — FILLFACTOR：建索引时叶页预留的空隙。
5. **PAD_INDEX** — Pad Index：把 FILLFACTOR 扩到中间层叶之外页。
6. **重新组织** — REORGANIZE：叶级轻量归拢，在线低噪。
7. **重新生成** — REBUILD：整树重插，可换 FILLFACTOR/压缩/分区。
8. **物理统计视图** — sys.dm_db_index_physical_stats：三种采样模式的碎片度量。
9. **序列缓存** — SEQUENCE CACHE：批量预取号段、跳号换吞吐。
10. **顺序 GUID** — NEWSEQUENTIALID：主机递增的唯一标识默认。
11. **使用统计** — Index Usage Stats：seeks/scans/lookups/updates 记账。
12. **索引合并** — Index Consolidation：以宽并窄、去重键序。
13. **热页争用** — Hot Page Contention：顺序键末叶的 PAGELATCH 集中。

## 最新演进与工业实践

- **自动索引管理落地**：Azure SQL Database 的自动调优可自动创建/验证/删除索引并有强制计划回滚；SQL Server 2022 起本地版提供 Auto Index Management（默认模式/观察模式），把本章人工巡检半自动化（[Automatic tuning](https://learn.microsoft.com/en-us/sql/relational-databases/automatic-tuning/automatic-tuning) ✅；本地版支持范围逐代差异 ⚠️ 以官方页为准）。
- **GUID 生态更新**：UUID v7（时间前缀有序 GUID）成为应用侧主流（2024 起广泛流行）；SQL Server 2025 的 `NEWSQLID()`（有序 GUID 生成器）官方收录于 2025 新特性页（[2025 新特性](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025) ✅ 条目名逐字 ⚠️ 转述）。
- **列存分流**：DW 场景的"碎片维护"演变为列存的段合并/rebuild（[自动索引压缩/列存维护](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/automatic-index-compaction) ✅），本章行存方法论适用面收窄到 OLTP。
- **Hyperscale**：远程存储 + 页缓存弱化了"物理序"的读惩罚，但写热页问题依旧在计算本地 ⚠️（[Hyperscale 架构](https://learn.microsoft.com/en-us/azure/azure-sql/database/hyperscale-architecture) ✅）。
