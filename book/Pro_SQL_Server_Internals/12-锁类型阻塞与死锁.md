## 核心精讲（转述 + ⚠️）

### 锁的队列模型与转换等待
书中反复强调：SQL Server 锁是**每个资源一个转换器队列**（转换分析器 ⚠️ 转述）。请求（新拥有者）与转换（S→X 升级）共享兼容矩阵，但**转换等待会挡住后面的兼容请求**——这正是"读挡读"死锁的温床：两个事务都持 S 等 X，后来者哪怕只要 S 也排队。理解这点，19 章三个"非经典"死锁模式全部成立 ⚠️。

### 阻塞链与"头阻塞者"
18 章的方法论（转述 ⚠️）：阻塞是链不是点；dm_exec_requests 的 blocking_session_id 递归向上，**头的特征是自己不在等锁而在等 CPU/IO/网络**（或干脆在客户端思考）。取证包三件：头的当前语句+计划（sql_handle/plan_handle）、头的会话属性（登录/主机/程序）、等待资源类型（LCK_M_* 名里含请求模式与资源）。书警告：只看"谁被挡"会误罚受害者 ⚠️。

### 死锁四模式的共同解药
四个官方模式的机制差异大，但书的处方收敛到三条（转述 ⚠️）：① 把"读+改"合并进同一原子入口（UPDATE 起手或 RCSI 下读不走 S）；② 同一临界资源集合按固定顺序访问（如按主键升序逐行）；③ 缩小锁面（索引化谓词、短事务、批大小控制）。重试策略放最后：捕获 1205、指数退避、幂等设计 ⚠️。

### 锁升级的经济学
锁内存超过锁内部分配阈值（书以 ~5000 + 内存压力条件 ⚠️）时，引擎尝试把细粒度锁折叠为表级：折叠失败（如已有 IX 冲突）则本轮放弃、继续攒。1211 关自动升级→海量行锁可能撑爆锁内存报 1204；1224 按会话内存阈值关闭→粒度更细但风险同向放大。书的时代结论（2014）：优先用**分批 DML**（TOP N 循环删改）从源头避免升级，跟踪标志只作止血 ⚠️。

### 死锁图（graph）的三段读法（19 章取证法转述 ⚠️）
死锁清单分三段读（转述 ⚠️）：resource-list 给"争什么"（对象名、锁模式、KEY/RID 的 hash 值）；owner-list 给"谁持什么、等什么"——重点看 held 与 requested 交错成环的那两条边；victim 标记只回答"谁退"，断案要回到输入 SQL：牺牲者语句+幸存者语句**四条并排**，顺序问题通常一眼可见。书反复强调：只看 victim 等于只看病人不看病原——两个当事事务都是设计责任方 ⚠️。

### 阻塞取证的三件套与一条铁律（18 章方法论收口 ⚠️）
实时抓头目时三样必取（转述 ⚠️）：① 头的当前语句与计划（sql_handle/plan_handle，未缓存时 DBCC INPUTBUFFER 补）；② 头的会话画像（login/host/program/status——"sleeping with open transaction"是 DAL 经典罪证）；③ 等待者的 LCK_M_* 模式与资源映射（对象/索引/键值回落到具体行）。事后路线靠阻塞处理程序与 XE 锁事件（接 15）。铁律：**先装摄像头再谈调参**——没有取证通道的系统，阻塞事故只能靠猜 ⚠️。

## 本章结论速记

- 锁是带转换队列的资源门：转换等待会挡兼容请求。
- 排查阻塞先找头，头往往在等客户端。
- 死锁断案先并排四条语句，victim 只是症状。
- 死锁四模式三个源于"读先占、改后到"或顺序乱。
- graph 清单 + victim 标记是死锁断案的原始证据。
- 锁升级是内存折衷；正解永远是拆批次、缩事务、上索引。

## 工程模式与常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "S 锁不挡 S，怎么会读读死锁" | 转换等待队列把后来 S 者挡成环的一部分 ⚠️ |
| "死锁是引擎 bug" | 四模式全是应用访问序+计划质量共同决定；引擎只是裁判 ⚠️ |
| "sp_who2 足够排阻塞" | 它给不出转换等待与资源；书用 DMV+系统过程表 join 还原链 ⚠️ |
| "锁升级是 bug，要 1211 关掉" | 关掉后锁内存失控可 1204；先批量化再谈开关 ⚠️ |
| "NOLOCK 治阻塞" | 脏读+引擎可走分配单元顺序（书中引 2012 后行为警告 ⚠️ 转述），等于换事故类型 |
| "DEADLOCK_PRIORITY 让对手牺牲" | 定的是自己当牺牲者的意愿；全员 HIGH=死锁照样发生只是没人退 ⚠️ |
| "WITH (NOLOCK) 是排查标配" | 书把提示归入"冻结的判断"一类（接 25 章）；脏读只是换一种事故形态，且引擎可走非常规扫描顺序 ⚠️ |
| "kill 头目就完事" | 头若在大批 DML 中段，kill 触发回滚可能比等它跑完更贵；先看语句与预估回滚成本再决定 ⚠️ |
| "锁内存爆了重启解决" | 1204/升级风暴的根因在语句形态（未批量化、缺索引）；重启只是清账，病灶照旧 ⚠️ |

## 机制链条

```
请求锁 ──▶ 资源转换队列 ──兼容?──▶ 授予
              │不兼容
              ▼
        等待（LCK_M_XX）──对方也等我──▶ 环 ──▶ 监视器 6s 周期检环 ──▶ 选牺牲者 1205
              │
     细粒度锁攒到 ~5000+ ──▶ 升级评估 ──可行──▶ 折叠为表锁（短暂 ST_ 缓冲态 ⚠️）
              │不可行
              ▼ 下轮再试 / 内存压力 ──▶ 1204
死锁成环 ──▶ 监视器选 victim（回滚代价最小 ⚠️）──▶ 1205 ──▶ 客户端重试环
头目画像 = 不等锁而等 CPU/IO/客户端 ──▶ 取证三件套（语句+计划/会话/资源）
```

## 核心概念速览（中英对照）

1. **锁模式** — Lock Mode：S/U/X/IS/IX/Sch-M/Sch-S/BU 的请求语义。
2. **转换等待** — Conversion Wait：已持低模式等升高的排队，挡兼容者。
3. **锁粒度** — Lock Granularity：RID/KEY/PAGE/HOBT/TABLE 的碰撞面。
4. **KEY 范围锁** — Key-Range Lock：SERIALIZABLE 下防幻读的区间语义。
5. **头阻塞者** — Head Blocker：链条顶端不等锁的那个会话。
6. **阻塞链** — Blocking Chain：blocking_session_id 递归串。
7. **牺牲者** — Deadlock Victim：1205 被选中的事务（代价最小者 ⚠️）。
8. **DEADLOCK_PRIORITY** — 会话级"愿不愿意当牺牲者"参数。
9. **锁升级** — Lock Escalation：细粒度聚合为表级锁的内存折衷。
10. **lock_escalation 选项** — TABLE / TABLE, ALLOW LOCK / ALLOW BLOCK。
11. **跟踪标志 1211/1224** — 停自动升级的两把双刃剑 ⚠️。
12. **锁内存** — Lock Memory：不受 max server memory 约束的角落。
13. **重试退避** — Retry with Backoff：1205/1204 的客户端兜底。
14. **回滚代价** — Rollback Cost：victim 选择与"kill 前必估"的同一把尺（书以行为描述 ⚠️）。
15. **阻塞处理程序** — Blocking Process Capture：事后取证的引擎内置触发器通道（书载 ⚠️）。
