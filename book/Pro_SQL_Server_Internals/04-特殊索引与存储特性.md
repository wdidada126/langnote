## 本章地图

| 官方小节（✅） | 转述要点 | 一句话结论 |
| --- | --- | --- |
| Indexes with Included Columns | INCLUDE 列只进叶节点、不进键：键窄、叶宽；免回表且比把列全放进键更省；限制（不能用于聚簇/旧版筛选组合等 ⚠️） | 覆盖的正确姿势是 INCLUDE 不是加键 ⚠️ |
| Filtered Indexes | 带 WHERE 谓词的部分索引：更小更快、统计自动伴随（filter statistics）；需查询谓词可被蕴含才可用；默认参数（ARITHABORT 等 SET 选项）不匹配会让计划用不上它 | 用索引体积赌数据倾斜 ⚠️ |
| Filtered Statistics | 无索引列也可建带谓词的统计：为倾斜分布补直方图精度 | 统计也能"切片" ⚠️ |
| Calculated Columns | 持久化（PERSISTED）计算列可入索引；非持久化列每次重算；确定性要求 | 用一次写开销换索引可能 ⚠️ |
| Data Compression — Row / Page / Performance | ROW：变长压缩+固定长变长化+列描述符；PAGE：前缀压缩+字典+列式编码（ROW 为前置）；收益=页少 I/O 少，代价=CPU、缓冲池效应、临时表不继承（书中演示 ⚠️） | 压缩是拿 CPU 换 I/O 与内存 ⚠️ |
| Sparse Columns | NULL 不占列空间、非 NULL 多 4 字节开销；配合 COLUMN_SET 视图式聚合列；限制（类型/索引方式 ⚠️） | 稀疏列=EAV 的引擎内建化 ⚠️ |

## 核心精讲（转述 + ⚠️）

### INCLUDE 的树几何
键列参与排序与查找，INCLUDE 列只在叶出现——所以 INCLUDE 列不能帮忙过滤，但能消灭 Key Lookup。书中对比三方案（宽键 / 键+INCLUDE / 回表）在插入成本与读放大上的差异：INCLUDE 的中间层最窄、叶变宽 ⚠️。

### 筛选索引的谓词蕴含
优化器只有证明"查询谓词 ⊆ 索引谓词"才敢用筛选索引：`WHERE Status='Active'` 的查询遇到 `WHERE Status='Active' OR Status IS NULL` 之类不蕴含形态直接弃用；参数化后谓词更不可证——这是书里"看起来能提速实际用不上"的高频陷阱 ⚠️。另：连接/存储过程的 SET ARITHABORT 默认值不一致会静默失效（书中给排查手法 ⚠️）。

### 数据压缩的三本账
1. I/O 账：页少→逻辑读少→备份/日志（页镜像）都小；
2. CPU 账：读写两端解压压页成本；
3. 缓冲池账：同容量缓存的行数放大。
书中用统计/执行计划演示"压缩改变了 I/O 敏感算子的报价"，并提醒 tempdb 里排序默认不继承源表压缩 ⚠️。PAGE 压缩对列式重复值特别有效（与第 18 文件/列存章形成"页内列式"的呼应）。

### 稀疏列与 COLUMN_SET
稀疏列把"该属性为 NULL"的成本降为零、把"该属性有值"的成本抬 4 字节；COLUMN_SET 提供"伪宽列"查询体验。书给的限制（不能进筛选索引/CHECK 限制/类型约束等细节 ⚠️ 转述待核验）。工程上它输给了后来的 JSON——见"最新演进"。

## 本章结论速记

- 覆盖=INCLUDE，倾斜=筛选，函数列=PERSISTED，重分布=过滤统计，宽 NULL=稀疏列。
- 五种"特殊"全部在赌同一件事：你对工作负载的分布先验比默认引擎更懂 ⚠️。
- 压缩不改查询语义，但改成本结构：先量 CPU 余量再全面铺开。

## 工程模式与常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "INCLUDE 越多越覆盖" | 叶变宽放大每页行数损失与更新成本；覆盖高选择率列即可 ⚠️ |
| "筛选索引一定更小更快" | 查询谓词不满足蕴含时优化器根本不用它 ⚠️ |
| "压缩总赚" | CPU 饱和系统上压缩可能净亏；读为主的系统更受益 ⚠️ |
| "PAGE 可直接开" | PAGE 压缩内含 ROW，必须整链理解；且部分数据类型不参与 ⚠️ |
| "计算列索引随便建" | 非确定性函数（GETDATE 等）不可索引；持久化换空间 ⚠️ |
| "稀疏列=省空间万能" | 非 NULL 反而更贵；适合"绝大多数为 NULL"的场景 ⚠️ |

## 核心概念速览（中英对照）

1. **包含列** — Included Column：只存于索引叶、不参与排序键的覆盖列。
2. **筛选索引** — Filtered Index：带 WHERE 谓词的部分索引。
3. **谓词蕴含** — Predicate Implication：查询谓词被索引谓词逻辑包含。
4. **过滤统计** — Filtered Statistics：带谓词的列统计。
5. **计算列** — Computed/Calculated Column：表达式物化列，PERSISTED 可选。
6. **确定性函数** — Deterministic Function：同输入同输出，索引可用前提。
7. **ROW 压缩** — Row-level Compression：变长编码+固定长变长化。
8. **PAGE 压缩** — Page Compression：前缀+字典+列式编码，叠在 ROW 上。
9. **前缀压缩** — Prefix Compression：列内公共前缀提取。
10. **字典压缩** — Dictionary Compression：列内重复值入字典。
11. **稀疏列** — Sparse Column：NULL 零成本的可选列形态。
12. **COLUMN_SET** — Column Set：稀疏列的聚合伪列访问。

## 最新演进与工业实践

- **JSON 取代稀疏列/EAV**：SQL Server 2016+ 的 JSON（含计算列+索引拼装"影子列"）在 2022/2025 持续加码（JSON 索引、原生 JSON 类型计划），本书的"特殊列"工具箱整体迁移到 JSON 路线（[2022 新特性](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2022) ✅；[2025 新特性](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025) ✅）。
- **列存把压缩做成默认**：第 18 文件的 CCI 本质是"全表页内列式压缩 + 批处理"，本章 PAGE 压缩在行存侧的定位被列存分流（[Columnstore overview](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/columnstore-indexes-overview) ✅）。
- **压缩形态演进**：行存压缩保持企业版专属；列存侧另提供归档压缩（本书 35 章）与 2019+ 的元数据/统计改进，口径以官方页为准（[数据压缩官方文档](https://learn.microsoft.com/en-us/sql/relational-databases/data-compression/data-compression) ✅）。
- **自动索引调优（Automatic tuning）**：Azure/SQL 2022+ 可自动创建/删除索引与强制计划，本章"先验赌注"被云侧自动化部分接管（[Automatic tuning](https://learn.microsoft.com/en-us/sql/relational-databases/automatic-tuning/automatic-tuning) ✅；SQL Server 侧支持范围 ⚠️ 以官方页逐条为准）。
- **工业实践（2024–2026）**：INCLUDE+筛选索引仍是热点查询的常规武器；PAGE 压缩在 DW/staging 常态化，OLTP 侧按 CPU 余量决策（通用共识，量化 ⚠️）。
