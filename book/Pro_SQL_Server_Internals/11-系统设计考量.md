## 核心精讲（转述 + ⚠️）

### 连接的经济学
书中把连接成本拆三档（转述 ⚠️）：新建连接（握手+登录+环境初始化，毫秒级、且挤占调度线程）、池中取出（近乎免费）、连接被长事务占用（隐性成本：事务挂着→锁/版本存留、池实际容量缩水）。工程推论：DAL 里"用时开、用完还"优于长持有；ORM 的 Unit-of-Work 若跨用户思考时间持连接，是最常见的反模式 ⚠️。

### 存储过程路线的真实红利
书列四点（转述 ⚠️）：① 计划稳定（参数化+缓存，接 14）；② 权限可以只授 EXECUTE 不授表；③ 服务端改实现不动客户端（演进解耦）；④ 网络往返聚合（一次调用替多条语句）。代价：调试工具链弱、版本管理要靠部署脚本、逻辑双头（应用+DB）。2014 年的社区氛围已经"重应用轻过程"，本书的立场是克制地折中：接口收进过程，业务留在应用 ⚠️。

### EF6 解剖的可持续教训（机制层面今天仍成立 ⚠️）
1. **N+1**：延迟加载列表外键→每对象一查询；对策：显式 Include/批 join。
2. **IN 列表膨胀**：`Where(x => ids.Contains(x.Id))` 翻译为变长字面量列表，计划缓存按长度分桶——书中给出的解法（TVP/临时表 join）在 2024+ 仍是官方推荐路线 ⚠️。
3. **逐行 DML**：SaveChanges 的变更集翻译成一条语句一行——大批量时日志量、往返、锁全部劣化；书中建议绕过 ORM 走 SqlBulkCopy+暂存表+INSERT...SELECT/MERGE ⚠️。
4. **参数化但不同文**：LINQ 组合差异→文本差异→计划不复用（接 14 的 ad-hoc 缓存一节）⚠️。

### 乐观并发的实现谱系
书中演示三种并发令牌（转述 ⚠️）：时间戳列（rowversion，引擎自动递增）、版本号列（应用自增）、全字段比对（ORM 默认，宽行时 SQL 冗长）。推荐 rowversion：8 字节、免应用维护、索引不沾。冲突处理循环：读→改→提交→令牌不符→重读合并→限次重试。悲观锁（UPDLOCK/HOLDLOCK 读升级）只在"冲突概率高且业务不可丢"的窄场景保留 ⚠️。

### 数据访问的四种往返形态（书中案例框架收拢 ⚠️）
DAL 的成本=往返次数×每次代价，书中 EF6 案例可归成四种形态（转述 ⚠️）：单行单查询（ORM 默认，往返与日志双贵）、单行多查询（N+1，网络 RTT 放大延迟）、多行单查询（批量/TVP/MERGE，正路）、多轮交互（事务跨用户思考时间，最差）。工程推论是**先合并往返、再优化语句**——多数 ORM 病症落在前两种形态，解药（批量化、预加载 join）是结构改写而非语句调优 ⚠️。

## 本章结论速记

- DAL 选型是耦合度与性能的联合决策，没有免费抽象。
- 连接是池租约：短借短还，别跨思考时间。
- 往返模型是 DAL 的第一账单：先合并往返再谈语句。
- 存储过程=接口+权限+计划三合一，但不是业务逻辑坟场。
- ORM 的四宗罪（N+1、IN 膨胀、逐行 DML、文本抖动）都有标准解药。
- 乐观并发默认选 rowversion 令牌。

## 工程模式与常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "ORM 已优化，不用看生成 SQL" | 书中反复用 Profiler 验 SQL；不看的团队为 N+1 付双倍账 ⚠️ |
| "连接池大就能治慢" | 池只挪等待位置；根因常在事务时长与查询本身 ⚠️ |
| "存储过程=把业务搬进 DB" | 过程内长逻辑放大锁窗口与调试成本；书的原则：薄过程 ⚠️ |
| "IN 列表和 TVP 差不多" | 每长度一计划、优化器逐值估算；TVP 一次计划+真实统计 join ⚠️ |
| "EF 的 SaveChanges 是原子业务事务" | 默认每语句自治；只有收口时包事务才是——书中演示边界坑 ⚠️ |
| "乐观并发=不处理冲突" | 令牌只是检测；重试/合并策略才是设计 ⚠️ |
| "查询慢先加索引" | 先按往返形态归因：N+1/逐行是结构病，砍往返次数常胜过任何索引与提示 ⚠️ |
| "rowversion 可当业务版本号用" | 它只表达"行被动过"，不表达"内容变了/谁改的"；业务版本应另设列（书中令牌语义 ⚠️） |
| "池化后不用管连接串抖动" | 池按连接串全等分桶——串里多一个属性差异就是新池；书中演示串抖动导致的"隐性缩容" ⚠️ |

## 核心概念速览（中英对照）

1. **数据访问层** — DAL：应用与数据库之间的接口收敛层。
2. **连接池** — Connection Pooling：ADO.NET 按连接串复用物理连接。
3. **N+1 查询** — 一列表+逐行取详情：ORM 头号性能反模式。
4. **IN 列表** — IN List：集合展成变长字面量，计划缓存按形分桶。
5. **表值参数** — TVP：集合参数的引擎内正规形态。
6. **乐观并发** — Optimistic Concurrency：冲突检测+重试，不持长锁。
7. **行版本令牌** — Rowversion/Timestamp：引擎自增 8 字节并发令牌。
8. **并发令牌** — Concurrency Token：参与"比对即检测"的列。
9. **存储过程接口** — Stored Procedure Facade：EXECUTE 权限面+计划稳定+演进解耦。
10. **变更集** — Change Set / Unit of Work：ORM 攒到 SaveChanges 的写集合。
11. **批量装载** — Bulk Load：SqlBulkCopy/暂存表绕开逐行 DML。
12. **计划复用** — Plan Reuse：文本一致才谈得上缓存红利。
13. **往返模型** — Round-trip Model：DAL 成本=往返次数×每次代价。
14. **单飞互斥** — Single-flight：应用锁防作业/初始化双跑（接原书第 22 章，见本目录 13 文件）。

## 最新演进与工业实践

- **EF6 → EF Core**：EF6 止步于 .NET Framework 维护线，新地面是 EF Core（含 EF Core 8/9/10 对 SQL Server 的持续适配 ⚠️ 版本号以微软发布页为准）；本章四大问题的机制依旧，解药部分内置化（如 `Contains` 的参数化/值类型列表翻译改进、ExecuteUpdate/ExecuteDelete 批写通道）⚠️。
- **upsert 的正统化**：本章"装载后合入"的 MERGE 有竞态名声（书中亦警告 ⚠️）；2023+ 官方主推 `INSERT ... VALUES ... ON CONFLICT DO UPDATE`（upsert 语法，2024/2025 预览—GA 节奏以官方为准）与 TVP+MERGE 批式路线（[MERGE](https://learn.microsoft.com/en-us/sql/t-sql/statements/merge-transact-sql) ✅、[2025 新特性](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025) ✅）。
- ** temporality 新工具**：系统版本表（temporal tables, 2016+）把"审计/历史"从 DAL 下沉进引擎（概称 ⚠️，特性页未在本包验证清单内故不直链）。
- **云侧 DAL 形态**：Azure SQL 上官方自动调优（自动索引+强制计划）部分接管了本章"计划抖动"问题；Hyperscale 让容量与读扩展不再靠应用分库（[Azure 自动调优](https://learn.microsoft.com/en-us/azure/azure-sql/database/automatic-tuning-overview) ✅、[Hyperscale](https://learn.microsoft.com/en-us/azure/azure-sql/database/hyperscale-architecture) ✅）。
- **连接管理新账**：无服务器（serverless）计费模式下，冷启动让"连接=租约"变成"连接=唤醒开关"，短连接策略需重估 ⚠️（[单库弹性扩缩](https://learn.microsoft.com/en-us/azure/azure-sql/database/single-database-scale?view=azuresql) ✅）。
- 作者后续同题演讲/博文可作旁证：[aboutsqlserver.com](https://aboutsqlserver.com/) ✅。
- **补上 temporality 条目的官方直链（二轮核验）**：系统版本表总页现经 curl 200 验证——[temporal tables](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables) ✅；"历史/审计下沉进引擎"自此有了权威文本，上文"不直链"的保留口径可解除（原句保留作取证时间戳）。
