# 03 · 摄取存储处理与访问四属性

> 章口径声明：对应 2e 考察点③"Key data lake attributes, including ingestion, storage, processing,
> and access"（✅ K10plus 520 逐字）。四属性各成一小节；实现细节凡涉 Hadoop/云产品者一律 ⚠️ 转述官方文档，
> 机制概念用 🔧 本机实验作类比（非本书平台行为）。

## 一、Ingestion（摄取）⚠️

- 原则：**原始数据只摄取一次、保真入 raw 区**；转换推迟到下游（与 01 章 2.2 的 schema 推迟同源）。
- 时代形态（2016–2018）：批量文件落 HDFS/对象存储为主，Flume/Kafka 类管道为辅；1e 的"blog postings、
  product reviews"例证说明摄取对象已含**半结构/非结构**（✅ 简介逐字）。
- 摄取登记四元组（重构）：来源系统、批次水位、格式与压缩、责任人——缺任一项则 raw 区半年后不可读。
- 当下云对照：S3/GCS 事件驱动入湖、托管摄取服务（⚠️ URL 见 00 第五节）。

## 二、Storage（存储）⚠️ + 🔧 尺寸账

- 本书立场：存储层追求**廉价、可水平扩、多副本耐久**，格式选择服从"读写解耦"——写侧要吞吐（列式/压缩），
  读侧要裁剪（分区/谓词下推）。
- 时代格式：Text/CSV→Avro/ORC/Parquet 迁移期；2e 语境下 Hadoop 仍占主场。

🔧 实验 E4（同表三格式落盘尺寸，DuckDB 1.5.5 实测）：

```text
E4 sizes: {'gold.parquet': 335, 'gold.csv': 15, 'gold.json': 25}
```

读数（诚实版）：小表上 **Parquet 反而更大**（335B vs CSV 15B）——列式格式的回本条件是行数×列宽摊薄
元数据与压缩字典。引用"列式更省"必须带规模前提，这是本机实验对宣传话术的一次祛魅。**非本书平台行为**。

## 三、Processing（处理）与分区裁剪 ⚠️ + 🔧

- 处理层的选型问题（2e 语境的"deployment options"细分）：常驻集群 vs 按需拉起；批（Spark）与
  交互式 SQL（Presto 类）并存是当时常态（⚠️ 通识转述）。
- 裁剪机制三件套：分区目录约定（hive-style）、文件级 min/max 统计、谓词下推到扫描算子。

🔧 实验 E2（hive 分区视图 + 物理计划，DuckDB 实测逐字）：

```text
E2 hive view: [(1, 10.5, 2024), (3, 7.0, 2024), (4, 3.0, 2024)]
E2 plan has PARQUET_SCAN: False
E2 plan filter lines: ['│            year           │', '│      Filters: amt>5.0     │']
```

读数：`read_parquet(..., hive_partitioning=true)` 把目录名 `year=2024` 升格为**虚拟列**；`Filters: amt>5.0`
出现在计划中说明谓词已压到扫描侧。注意第一行如实记录：本机 DuckDB 计划的扫描算子名不叫 PARQUET_SCAN
（算子命名随引擎版本变化）——**裁剪看 Filters 行，不看算子名**，这是做平台评审时的防错姿势。**非本书行为**。

## 四、Access（访问）：读时定形的红利 ⚠️ + 🔧

- 访问层设计目标（考察点⑥的前半，此处讲机制）：**让"我不知道未来怎么问"成为常态问题**——
  目录先行、查询弹性、消费者自持口径。
- 权限模型归 04/05 章（治理面），本节只谈"读得到"。

🔧 实验 E5（JSON 文档直读，DuckDB 实测）：

```text
E5 duckdb read_json_auto: [(20.5, 3)]
```

读数：无 DDL、无导入作业，`read_json_auto` 直接出表——与 01 章 E1 的 CSV 推断合并看，即"访问层零建表"
的本地样本；代价是每次读都推断（生产上需目录缓存 schema，呼应 04 章）。

## 五、写时定形的对照税 🔧（E4b，SQLite 3.45.3 实测）

```text
E4b sqlite typed-load rows: 4 (4,)
```

读数：SQLite 路线要求**先** `CREATE TABLE t(ord INT, amt REAL, note TEXT)`，再逐行转型 INSERT；空串
`amt=''` 需手工判 None（脚本内 try/else 计数）。4 行全过是**写了适配代码**的结果——这就是 01 章
"暂存区模式提前裁剪 schema"之弊的机器证词：摄取时定型 = 每次新消费者/新字段都要回源重做 ETL。**非本书行为**。

## 六、四属性的互相牵制（本章小结）⚠️

| 属性 | 索取 | 偿付 |
| --- | --- | --- |
| 摄取 | 保真、只一次 | 存储膨胀、脏数据入库 |
| 存储 | 廉价、耐久 | 列式/分区复杂度后移 |
| 处理 | 吞吐与裁剪 | 分区键要预判查询模式 |
| 访问 | 弹性自助 | 目录与 schema 登记必须兜底 |

- 一句话：**湖的四属性不是并列清单，而是同一笔"schema 债务"在四处的分期偿还表。**
- 阅读纵深：表格式如何统一四属性，看 [../Engineering_Lakehouses_with_Open_Table_Formats/00-总览与阅读地图.md](../Engineering_Lakehouses_with_Open_Table_Formats/00-总览与阅读地图.md)；
  upsert 化摄取看 [../Apache_Hudi_Definitive_Guide/00-总览与阅读地图.md](../Apache_Hudi_Definitive_Guide/00-总览与阅读地图.md)。

## 七、摄取登记四元组样单与闸口速查（重构交付件）⚠️

| 登记项 | 最小字段 | 检查动作 |
| --- | --- | --- |
| 来源 | 系统名 + 责任人 + 业务含义一句话 | 抽查看板：字段空即退单 |
| 批次水位 | 起止时间戳 / 增量游标 | 断供报警：水位停滞超 2 周期 |
| 格式压缩 | CSV/JSON/Parquet/ORC + codec | 对账：登记格式 vs 文件魔数 |
| 质量闸口 | 非空率、类型符合率、行数环比 | 晋级处生效（05 章 prep 步） |

- 闸口分层（重构）：**入册闸**（登记完整性）→ **晋级闸**（数据质量）→ **上桌闸**（供应就绪度）；
  三闸都发生在管理带，不要求改动数据带任何字节——"治理不拖慢湖"（2e 简介原句意译）的流程学解释。
- 与 02 章 registry 表的关系：上表就是 registry 的列扩展模板；先四元组后扩展，避免"目录一次到位"幻觉。
- 常见腐化三态（评审速查）：登记在但路径漂移（对账失配）；闸口在但只拦新批（存量带病）；
  格式登记与实际压缩编码不符（读侧侥幸成功，换引擎即爆）——三态各对应六节检查法一条。

## 核心概念速览（中英对照）

| 中文 | 英文 | 一句话 |
| --- | --- | --- |
| 四属性 | key data lake attributes | 考察点③：摄取/存储/处理/访问 |
| 保真摄取 | raw-faithful ingestion | 只摄取一次、不做提前的口径裁剪 |
| 列式格式 | columnar format (Parquet/ORC/Avro) | 规模前提才回本（🔧 E4 尺寸账） |
| 分区裁剪 | partition pruning | 目录即虚拟列（🔧 E2 hive-style） |
| 谓词下推 | predicate pushdown | Filters 行进扫描算子侧（🔧 E2） |
| 读时定形 | schema-on-read | 直读推断零建表（🔧 E5）vs 写时定形税（🔧 E4b） |

## 最新演进与工业实践

- 四属性话语的 2020s 继承：对象存储（S3/GCS）成为存储答案的事实标准；**开放表格式**把"分区+统计+谓词"
  从引擎私有升格为表级公共协议（Iceberg/Delta/Hudi 三册在盘，链见六节）。
- 摄取层演进主线：批量文件落湖 → CDC/流式入湖（Hudi 的 upsert、Paimon 的流式 changelog，
  [../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md](../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md)）。
- 云上托管对照：AWS Glue/S3 Tables、GCP Dataproc/BigLake 把四属性做成托管件（⚠️ URL 见 00 第五节，
  内容转述未实测）。
- 工业提醒：本册"廉价存储"论在 2026 的对应风险是**湖上僵尸分区与未压缩中间态**造成的成本反噬，
  生命周期治理（04 章议题）已升格为 FinOps 常设项 ⚠️。
