## 本章地图

本章是全书的问题陈述章，负责回答三个问题：**我们到底要解决什么（集群与状态机）**、**什么叫达成一致（共识的定义与四个辨析）**、**什么情况下不可能或代价极高（拜占庭故障）**。

```
单机
 └→ 主从/读写分离（单点写，容量与可用性瓶颈）
     └→ 分片集群（容量解决，但每片仍单点）
         └→ 多副本集群（可用性解决，但副本间要「对同一件事达成一致」）  ← 共识的地盘
```

- **1.2 集群与状态机**：把「一堆机器」抽象成**一个确定性状态机**的多个副本——这是「复制状态机（Replicated State Machine, RSM）」模型，也是后续所有算法共同的建模前提：只要**初始状态相同 + 输入序列相同 + 状态转移函数确定**，各副本终态必然相同。于是「一致性」被规约为「**对输入序列的第 n 项达成共识**」。
- **1.3 共识简介**：共识 ≠ 一致性，共识 ≠ 副本同步，共识 ≠ 集群成员管理；本章用「与集群 / 与副本 / 与一致性」三个辨析把它们切开。
- **1.4 拜占庭故障**：把故障模型从「崩溃-停止（crash-stop）」升级到「任意行为（Byzantine）」，并带来**阈值从 `f < n/2` 收紧到 `f < n/3`** 的关键结论——这是全书唯一一次讨论非崩溃故障，也是本章最需要 2026 补丁的地方。

## 核心精讲

### 1.1 分布式架构的演进：为什么「达成一致」会变成核心问题

| 阶段 | 形态 | 解决的问题 | 暴露的新问题 |
| --- | --- | --- | --- |
| 单机 | 单库单应用 | 简单、强一致 | 容量与可用性瓶颈 |
| 主从 / 读写分离 | 一写多读 | 提升读容量 | 主库单点；异步复制丢数据 |
| 分片 | 按 key 拆分到多节点 | 提升写容量 | 跨片事务；单分片仍单点 |
| 多副本集群 | 每片多个副本 | 提升可用性 | **副本之间要就「第 n 条是什么」达成一致** ← 共识 |
| 多 region / 多活 | 跨地域部署 | 降低延迟、容灾 | 延迟放大，Leader 位置与读路径成为关键 |

演进的每一步都在「**用更多的机器换某个指标**」，而每引入一份副本，就多了一份「**谁说了算**」的问题。共识算法解决的正是这个最终问题。

### 1.2.1 分布式与集群：两个常被混用的词

- **分布式**：把**一件大任务拆成多个子任务**，分给不同节点协同完成（强调分工）；
- **集群**：把**同一份服务部署多份**，对外像一个整体（强调冗余）。
- 一个系统可以同时是两者：分布式数据库既是「分片（分布式）」又是「多副本（集群）」。共识只负责**后者中的副本间定序**。

### 1.2.2 容错能力：阈值是怎么算出来的

设副本数 $n$，允许故障数 $f$，quorum（法定人数）大小为 $q$：

- **安全性要求**：任意两个 quorum 必须相交 → $2q > n$；
- **可用性要求**：即使 $f$ 个节点故障，仍能凑出一个 quorum → $q \le n - f$；
- 联立得 $n > 2f$，即 **$n = 2f + 1$、$q = f + 1$**（崩溃故障下的经典结论）。

| 故障模型 | 最小节点数 | 典型算法 |
| --- | --- | --- |
| 崩溃-停止（crash-stop / crash-recovery） | $2f+1$ | Paxos、Raft、ZAB |
| 拜占庭（任意行为，含说谎/串谋） | $3f+1$ | PBFT、HotStuff、Tendermint |

> 🔧 **$3f+1$ 是「口头消息 + 无签名」下的结果**；使用数字签名（authenticated Byzantine）时消息不能被伪造转发，但仍需 $n \ge 3f+1$ 才能保证在异步/部分同步下既安全又活跃（PBFT 即此配置）。

### 1.2.3 状态机：共识的落点

状态机是一个三元组：状态集合 $S$、输入集合 $I$、确定性转移函数 $\delta: S \times I \to S$。
多副本要保持一致，只要保证**每条副本看到的输入序列完全相同**。以下为**教学示意，不参与构建**：

```text
// 教学示意：复制状态机的骨架（不参与构建、不编译、不运行）
class ReplicatedStateMachine:
    state      = INITIAL      // 所有副本的初值必须一致
    log        = []           // 已达成共识的输入序列（第 n 项 = log[n]）
    appliedIdx = 0

    // 共识层：把 client 请求变成一个「被批准的日志项」
    // 本章只定义接口；第 4 章（Paxos）/ 第 6 章（Raft）给出实现
    fn consensusPropose(cmd) -> index:
        index = consensus.append(cmd)     // 若冲突/换主，此处可能失败并重试
        return index

    fn applyLoop():
        while appliedIdx < consensus.commitIndex:
            appliedIdx += 1
            cmd  = log[appliedIdx]
            state = delta(state, cmd)     // 确定性转移：不允许读本地时间/随机数
```

关键在于 **`delta` 必须确定性**：读系统时钟、读本地随机数、读未同步的本地状态，都会让「同样的输入序列」产出不同终态，共识做得再对也没用。

### 1.3 共识的定义与四个辨析

**共识（consensus）** 的四个性质（这是学界通行定义，本书口径一致）：

| 性质 | 含义 |
| --- | --- |
| 终止性（Termination / Liveness） | 每个正确节点最终都会决定某个值 |
| 一致性（Agreement / Safety） | 所有正确节点决定的值相同 |
| 有效性（Validity） | 被决定的值一定是某个节点提议过的值 |
| 完整性（Integrity，部分定义含） | 每个节点最多决定一次 |

### 1.3.5 共识算法的发展历程（一张时间轴）

| 年代 | 事件 | 意义 |
| --- | --- | --- |
| 1978 | Gray《Notes on Database Operating Systems》 | 2PC 成型（原子提交，见 [03](03-2PC与3PC分布式事务.md)） |
| 1982 | 拜占庭将军问题（TOPLAS） | 故障模型升级 |
| 1985 | FLP（JACM） | 划出异步下界（见 [12](12-FLP不可能定理.md)） |
| 1988 | Viewstamped Replication（PODC） | 主副本复制的早期方案 |
| 1988 | 部分同步模型（JACM） | 给出工程可行的理论出口 |
| 1996 | 故障检测器（JACM） | 选主的理论依据 |
| 1998 / 2001 | Paxos（TOCS）/ Paxos Made Simple | 共识从理论走向工程 |
| 2006 / 2010 | Chubby（OSDI）/ ZooKeeper（ATC） | 协调服务范式；ZAB |
| 2013 / 2014 | EPaxos（SOSP）/ Raft（ATC） | 去中心化探索；可理解性重构 |

四个辨析（对应 1.3.2–1.3.4）：

1. **共识与集群**：集群是**物理组织形态**，共识是集群内部**达成一致的逻辑手段**；有集群不等于有共识（如主从异步复制的集群就没有共识）。
2. **共识与副本**：副本是**数据的多份存放**，共识决定的是**副本上的操作序列**；没有共识的副本同步，只能给出「最终一致」而非线性一致。
3. **共识与一致性**：一致性是**客户端能观察到的可见性/顺序保证**（线性一致性、顺序一致性、因果一致性……），共识是**服务端用来产出全序的手段**。共识是实现线性一致性的常用工具，但不是唯一工具，也不是一致性本身。
4. **发展历程**（1.3.5）：从 2PC 的原子提交，到 FLP 划出异步下界，到 Lamport 的 Paxos，再到为可理解性重构的 Raft、为主备广播定制的 ZAB，以及为降低延迟/去中心化探索的 Fast Paxos、EPaxos——本书第 2–4 篇即按此线索展开。

### 1.4 拜占庭故障

- **背景**：Lamport、Shostak、Pease 的「拜占庭将军问题」（ACM TOPLAS 1982）：节点可能**宕机、说谎、选择性转发、串谋**，且消息可能被篡改/伪造。
- **解的存在性**：口头消息（无签名）下，容错上界是 $f < n/3$；$n=3,f=1$ 时无解——这是「三将军问题」的经典不可能结论。
- **解决路线（1.4.2）**：
  - **PBFT**（Castro & Liskov，OSDI 1999）：部分同步下 $3f+1$ 节点、三阶段（pre-prepare / prepare / commit）、主视图切换；
  - **PoW 型**（比特币，2008）：把「谁有资格出块」变成算力竞赛，用经济成本替代身份准入，容错上界转为「算力占比 < 50%」；
  - **PoS 型**：用质押资产替代算力，配 finality gadget 提供确定性。

> ⚠️ **本章须说明**：大纲只给出「1.4.1 背景知识 / 1.4.2 解决方案」两个小节名，**未给出正文**。
> 上面列出的三条路线是**该主题公认的公认知识**，**不能据此断言本书 1.4.2 具体讲了哪一条**——未能核实原文，存疑。

## 版本演进

- **1980s–1990s**：问题被形式化（FLP 1985、拜占庭将军 1982），共识被证明「异步下无确定性解」；
- **1998–2001**：Lamport 的 Paxos 正式发表（TOCS 1998）与通俗重述（Paxos Made Simple 2001），共识从理论走向工程；
- **2006–2013**：Chubby（OSDI 2006）、ZooKeeper（ATC 2010）、Raft（ATC 2014）把「可理解的共识」变成中间件标配；
- **2023（本书）**：以中文教材口径把 Paxos/ZAB/Raft + Paxos 变种 + FLP 串成一条线，并配 PhxPaxos / SOFAJRaft 源码解析；这是本书相对早期中文材料的**增量**（源码与算法模拟），但理论边界仍停在 1990s 的结论上；
- **2026 视角**：共识已分化为两条主线——**崩溃容错（CFT）的 Multi-Raft 工程化**（TiKV/CockroachDB/etcd）与**拜占庭容错（BFT）在区块链与联盟链的复兴**（HotStuff/LibraBFT 一脉）。

## 近年研究与工业界开源实践（2015–2026）

> star 数均为 2026-09 用 `gh api repos/OWNER/REPO --jq '.stargazers_count'` 实测。

- **崩溃容错主线（CFT）**
  - `etcd-io/etcd`（**52,310★**）：Kubernetes 的元数据存储，etcd v3 用 Raft 做共识，是「Raft 事实上成为标准」的最大推手；核心实现见 `etcd-io/raft`（**1,128★**，已拆为独立库）。
  - `hashicorp/raft`（**9,136★**）：Consul/Nomad 使用的 Go Raft 库，与 etcd 的 Raft 在快照、读路径、成员变更策略上取舍不同（详见 [07-Raft.md](07-Raft.md)）。
  - `tikv/tikv`（**16,878★**）与 `pingcap/tidb`（**40,590★**）：TiKV 用 **Multi-Raft**（按 Region 分组，每组一个 Raft group）+ PD 调度，是「共识规模化」的代表实现。
  - `cockroachdb/cockroach`（**32,508★**）：同样 Multi-Raft，并把 Raft 与**分布式事务、HLC 时钟**深度耦合。
- **协调服务主线**：`apache/zookeeper`（**12,811★**）——ZAB 的参考实现（详见 [06-ZAB与ZooKeeper.md](06-ZAB与ZooKeeper.md)）。
- **拜占庭/联盟链主线**：`hyperledger/fabric`（**16,732★**）——Fabric 的排序服务自 v1.4.1 起提供基于 **Raft**（etcd/raft 库）的 CFT 排序，说明**联盟链场景也大量退回 CFT**（参与方身份已知时不需要 BFT）。
- **一致性验证**：`jepsen-io/jepsen`（**7,504★**）——Jepsen 用故障注入实测各系统宣称的一致性，是本章「共识 vs 一致性」论断的校验工具（结论见各章「近年实践」段）。
- **近年研究**：
  - **HotStuff**（Yin et al., PODC 2019）把 BFT 做成「链式 + 线性视图切换」，成为 Libra/Diem 一脉的基础；
  - **以太坊共识切换**：2022-09-15「The Merge」后以太坊主网由 PoW 转为 **PoS**，共识为 **Gasper = LMD-GHOST（分叉选择）+ Casper FFG（最终性）**（详见下方 🔧）；
  - **Flexible Paxos**（Howard, Malkhi, Spiegelman, OPODIS 2016）指出「所有 quorum 两两相交」是过强的要求，只需 Phase-1 与 Phase-2 quorum 相交，从而打开了 quorum 配置的设计空间。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「多副本 = 有共识」 | 异步主从复制的集群没有共识，只有「尽力而为」的复制；换主时可能丢已确认写入 |
| 2 | 「共识 = 一致性」 | 共识是**手段**（产出全序），一致性是**可观察保证**（线性/顺序/因果…）；两者是不同层次 |
| 3 | 「RSM 只要日志一致就行」 | 还要求 `delta` **确定性**：读本地时钟/随机数/未同步状态会破坏终态一致 |
| 4 | 「3 节点能容忍 1 个拜占庭节点」 | 不能。$n=3,f=1$ 在口头消息模型下**无解**；BFT 需 $3f+1$（即 4 节点才容 1） |
| 5 | 「拜占庭容错一定更好」 | BFT 代价是消息复杂度与节点数；若参与方身份可控（企业内网/联盟链），CFT（Raft）通常更划算 |
| 6 | 🔧 本书第 1 章若以「PoW = 拜占庭共识的主流解」收尾，则已过时 | **以太坊已于 2022-09-15 完成 The Merge，主网共识从 PoW 切换为 PoS（Gasper：LMD-GHOST + Casper FFG）**，PoW 不再是公链共识的默认答案；本书 2023 年出版，正文未能反映这一切换 |
| 7 | 🔧 本书未给出 BFT 的工程化现状 | 2026 年 BFT 的落地主要在许可链/联盟链与部分公链：HotStuff/LibraBFT 一脉提供线性视图切换，工程代价远低于 PBFT 的 view change；这块本书未覆盖，需用 HotStuff 论文与 [../分布式算法/08-拜占庭与容错共识.md](../分布式算法/08-拜占庭与容错共识.md) 补 |
| 8 | 🔧 本书未给出国产系统的共识选型对照 | 补一条对照（公开资料口径）：**OceanBase** 以 Multi-Paxos 为副本一致性核心，**PolarDB**（PolarDB-X / PolarDB 存储层）相关设计使用 ParallelRaft 一类的并行共识（见 [08-Raft工程实践与SOFAJRaft.md](08-Raft工程实践与SOFAJRaft.md)），**TiDB/TiKV** 用 Multi-Raft + PD。三者都不是「单点 Raft」，而是**分组/并行化的共识**；选型差异主要来自分片粒度与存储形态，而非算法本身 |
