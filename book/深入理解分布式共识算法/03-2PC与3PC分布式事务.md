# 第 3 章 2PC、3PC——分布式事务的解决方案

> 覆盖原书第 3 章（第 2 篇「常见分布式共识算法原理与实战」，P18–46）。
> 小节照抄大纲：3.1 二阶段提交协议（简述 / 故障恢复 / 优缺点 / 空回滚和防悬挂）；
> 3.2 三阶段提交协议（简述 / 故障恢复 / 优缺点）；3.3 二阶段提交协议在 Seata 中的应用（AT 模式 / 事务管理者 / 资源管理者 / 事务协调者）；3.4 本章小结。

## 本章地图

本章是全书第 2 篇的第一章，位置很微妙：**它讲的其实不是共识，而是原子提交（Atomic Commit）**。本书把它放在共识篇里，是因为两者在工程中常常相邻出现（跨分片事务 = 每组内部共识 + 组间原子提交）。

```
原子提交（本章）：让「一组参与者的本地事务」要么全提交、要么全回滚
      ▲                                   ▲
      │ 协调者单点 → 阻塞                  │ 用共识复制协调者 → 不阻塞
      │                                   │
   经典 2PC / 3PC                     Paxos Commit / Raft + 2PC（Spanner 一脉）
```

- **3.1 2PC**：Prepare（投票）+ Commit/Rollback（决议）两阶段；故障恢复靠**日志**；优点是简单、缺点是**协调者单点阻塞**与**保守的锁持有**。
- **3.1.4 空回滚与防悬挂**：这两个问题在术语上属于 **TCC（Try-Confirm-Cancel）** 框架（本书把它放在 2PC 小节下，因为有 Seata 铺垫）；核心是「**Cancel 可能在 Try 未执行时到达**」与「**Try 可能在 Cancel 之后才到达**」。
- **3.2 3PC**：在 2PC 中间插入 **PreCommit**，让参与者在提交前先「知道别人也同意了」，从而消除阻塞——但**只在无分区的同步模型下成立**。
- **3.3 Seata**：把 2PC 落到工程框架：TM（事务管理者）/ RM（资源管理者）/ TC（事务协调者）三角色 + **AT 模式**（自动生成 undo log，业务无侵入）。

## 核心精讲

### 3.1.1 2PC 的两阶段

| 阶段 | 协调者（Coordinator / TC） | 参与者（Participant / RM） |
| --- | --- | --- |
| Phase 1 投票 | 写 `begin` 日志 → 广播 `Prepare` → 等待 | 尝试执行本地事务、**写 undo/redo 日志并落盘**、锁住资源 → 回 `Yes`/`No` |
| Phase 2 决议 | 全 Yes → 写 `commit` 日志 → 广播 `Commit`；否则写 `abort` → 广播 `Rollback` | 按指令提交/回滚 → 回 `Ack` |

```text
// 教学示意：2PC 骨架（不参与构建、不编译、不运行）
fn coordinator(txn, participants):
    log.write(BEGIN, txn)                       // 关键：先落日志再发消息
    votes = []
    for p in participants: votes.append(p.prepare(txn))
    if all(v == YES for v in votes):
        log.write(COMMIT, txn)                  // 决议点：写了这条日志之后，结果不可变
        for p in participants: p.commit(txn)
    else:
        log.write(ABORT, txn)
        for p in participants: p.rollback(txn)
    log.write(END, txn)

fn participant_on_prepare(txn):
    // 必须把「能做/不能做」持久化后再回答，否则宕机恢复后不知道自己投过什么
    if tryExecute(txn):  log.write(PREPARED, txn); return YES
    else:                log.write(ABORTED,  txn); return NO
```

**决议点（commit point）** 是理解 2PC 的关键：**协调者把 `commit` 日志落盘的那一刻起，事务结果就已确定**，之后无论谁宕机，恢复后都必须把它做完。参与者同理：投出 `Yes` 后进入「未决（in-doubt）」状态，必须等协调者告诉它结果。

### 3.1.2 故障恢复：三种情形

| 故障 | 处理 |
| --- | --- |
| 参与者在投票前宕机 | 协调者超时按 `No` 处理 → 全局回滚（最简单） |
| 协调者在发决议前宕机 | 参与者处于未决状态 → **只能等协调者恢复**（阻塞） |
| 协调者/参与者在决议后宕机 | 重启后**按本地日志重放**：已写 `commit` 就继续提交，未写就回滚，并对未回 Ack 的节点重发 |

> **2PC 的阻塞性正是上表第二行**：协调者单点 + 参与者未决 = 资源锁长期持有。这也是「2PC 不是共识」的根本原因——共识要求**即使参与者故障也能推进**，2PC 做不到。

### 3.1.4 空回滚与防悬挂

- **空回滚（Empty Rollback）**：协调者调用参与者的 `Cancel`，但该参与者的 `Try` 还**没有执行**（可能请求丢失/超时）。若参与者如实「回滚」，可能把不属于本次事务的数据改动掉，或误报成功。
  - 解：参与者在 `Cancel` 时**先检查是否有对应的 Try 记录**（全局事务 ID + 分支事务 ID），没有就**记录一条空回滚标记并直接返回成功**。
- **防悬挂（Anti-hanging / 悬挂防护）**：`Cancel` 已经执行完，迟到的 `Try` 才到达。若不拦，会在已取消的事务上又锁住资源，且再也无人来 Confirm/Cancel → 资源悬挂。
  - 解：`Try` 执行前**先查空回滚标记**，命中则拒绝执行。
- 两者共同的工程前提：**一张「分支事务状态表」**，且状态写入与业务操作在同一个本地事务里。

> ⚠️ 大纲把这两个问题放在 3.1（二阶段提交）之下；术语上它们更常见于 **TCC** 与 Seata 的语境。本笔记按大纲位置保留，但标注其真实出处，避免读者误以为「经典 2PC 论文里就有空回滚」。

### 3.2 3PC：用 PreCommit 换不阻塞

```text
CanCommit   : 协调者问「能做吗？」（不锁资源、不写 undo）→ 参与者回 Yes/No
PreCommit   : 全 Yes → 协调者发 PreCommit，参与者写 prepared 日志、锁资源 → 回 Ack
DoCommit    : 协调者收到足够 Ack → 发 DoCommit，参与者真正提交
```

关键差异：**参与者在 PreCommit 之后超时未收到 DoCommit 时，可以「默认提交」**——因为所有参与者都已 Ack 过 PreCommit，大家都同意了。这消除了「等协调者」的阻塞。

> 🔧 **但这个「默认提交」在网络分区下会出错**：若协调者因未收齐 Ack 而决定 Abort，同时网络分区让部分参与者收不到 Abort 并按超时默认提交 → **一边提交一边回滚，数据不一致**。
> 3PC 的不阻塞性是建立在「**超时 = 节点故障**」这一同步假设上的；真实网络里超时也可能是分区，因此**工业界几乎不使用 3PC**。

| 维度 | 2PC | 3PC |
| --- | --- | --- |
| 阶段 | Prepare → Commit/Rollback | CanCommit → PreCommit → DoCommit |
| 阻塞性 | **阻塞**（协调者宕机时参与者悬挂） | 不阻塞（参与者超时可默认提交） |
| 资源锁 | Phase 1 起持有，直到决议 | PreCommit 起持有（准备阶段不锁资源） |
| 分区下的正确性 | 安全但不可用 | ❌ **可能一边提交一边回滚** |
| 消息数 | 2 轮 | 3 轮 |
| 工业使用 | 广泛（XA、Seata、数据库分布式事务） | **几乎不用** |

### 3.3 Seata 中的 2PC（AT 模式）

| 角色 | 全称 | 职责 |
| --- | --- | --- |
| TM | Transaction Manager（事务管理者） | 定义全局事务边界：`@GlobalTransactional` 开启/提交/回滚 |
| RM | Resource Manager（资源管理者） | 管理分支事务：注册分支、上报状态、按 TC 指令提交/回滚 |
| TC | Transaction Coordinator（事务协调者） | 独立服务：维护全局事务与分支事务状态、驱动 2PC、持全局锁 |

**AT 模式的执行方式**（业务无侵入）：

1. **一阶段**：RM 拦截业务 SQL → 解析出前后镜像 → 在**同一个本地事务**里写业务数据 + `undo_log`（前后镜像）→ 本地直接提交，并向 TC 注册分支、申请**全局写锁**；
2. **二阶段-提交**：TC 只做**异步删除 `undo_log` 与释放全局锁**（因为一阶段已经本地提交了）；
3. **二阶段-回滚**：TC 下发回滚 → RM 用 `undo_log` 里的后镜像**校验当前值**（防止脏写），再用前镜像回滚 → 删 `undo_log`、放锁。

```text
// 教学示意：AT 模式一阶段的数据写入（不参与构建、不编译、不运行）
BEGIN LOCAL TX;
   UPDATE account SET balance = balance - 100 WHERE id = 1;   // 业务 SQL
   INSERT INTO undo_log(branch_id, xid, before_image, after_image, ...);
   -- 全局锁： seizure of row key 由 RM 向 TC 申请，写在 TC 侧（或 lock_table）
COMMIT LOCAL TX;              // 本地已提交！全局事务此时「未决」
```

> AT 模式的**隔离性来自全局写锁**，不是来自共识；TC 本身的高可用（避免 2PC 的协调者单点）要靠 TC 集群 + 存储层的高可用方案，这也是 Seata 部署中的重点（🔧 见「常见误区」）。

**Seata 的四种模式对照**（本书 3.3 只展开 AT，其余列出以便定位）：

| 模式 | 侵入性 | 一致性 | 适用 |
| --- | --- | --- | --- |
| **AT** | 无侵入（自动生成 `undo_log`） | 靠全局写锁；读隔离由 `undo_log` 兜底 | 关系库、业务不愿改代码 |
| **TCC** | 高（要写 Try/Confirm/Cancel 三个方法） | 强（业务自定义补偿） | 非关系库、跨服务、需要精细控制 |
| **Saga** | 中（写正向 + 补偿服务） | 最终一致（无隔离） | 长事务、跨组织流程 |
| **XA** | 低（依赖数据库 XA 接口） | 强（标准 2PC） | 数据库原生支持 XA 且能接受阻塞 |

## 版本演进

- **1970s–1980s**：原子提交协议成型（Gray 1978 的《Notes on Database Operating Systems》给出 2PC 的经典表述；Skeen 1981 的 SIGMOD 论文给出非阻塞提交协议与「3PC 在何种条件下可行」的分析）；X/Open DTP 的 **XA** 规范把它固化成接口；
- **1990s**：ARIES 一族把本地恢复与 2PC 的 prepared 日志衔接起来，成为商用数据库的标准配置；
- **2004–2006**：Gray & Lamport《Consensus on Transaction Commit》给出 **Paxos Commit**——把协调者的决议用 Paxos 复制，2PC 的阻塞问题被彻底解决（代价是多一轮通信）；
- **2010s**：Percolator（OSDI 2010）把 2PC 搬到**客户端**（客户端做协调者 + 主键锁），Spanner（OSDI 2012）用 **Paxos + 2PC** 提供外部一致性的跨分片事务，Calvin（SIGMOD 2012）用「先定序再执行」绕开分布式提交的不确定性；
- **2019–2023（本书）**：Seata 一类的**中文开源事务框架**成为 2PC 在业务系统里的主流落地形态，AT 模式让「改一个注解就有分布式事务」成为现实——本书的价值在于把这个工程形态讲透了；
- **2026 视角**：生产系统的通行做法是**分层**——分片内部用 Raft/Multi-Paxos 保证副本一致，跨分片用 2PC（或 Percolator 式客户端 2PC），并把协调者状态也放进共识组；**没人直接用教科书 3PC**。

## 近年研究与工业界开源实践（2015–2026）

> star 数均为 2026-09 用 `gh api repos/OWNER/REPO --jq '.stargazers_count'` 实测。

- `apache/incubator-seata`（**26,012★**）：本章 3.3 的主角，阿里开源、现为 Apache 孵化项目。支持 **AT / TCC / Saga / XA** 四种模式；AT 模式的 `undo_log` 与全局锁实现是其最大特色，也是最容易踩坑的地方（脏写校验、全局锁竞争、TC 高可用）。
- `pingcap/tidb`（**40,590★**）：TiDB 的事务走 **Percolator 模型**（客户端 2PC + 主键锁），每条 Raft 组内部用 Raft 复制；这是「共识 + 原子提交」分层的开源样本。TiDB 5.0 起默认**悲观事务**，与 Percolator 原论文的乐观假设已有差异。
- `cockroachdb/cockroach`（**32,508★**）：同样采用「Raft 组 + 分布式事务」，但用 **HLC + 写意图（write intent）+ 并行提交（parallel commits）** 来压缩提交延迟，属于 2PC 的现代改良。
- `jepsen-io/jepsen`（**7,504★**）：用于检验事务框架宣称的隔离级别与原子性；对分布式事务类系统的典型发现是**默认隔离级别弱于宣称**、以及**客户端重试/超时语义**造成的偏差。
- **近年研究**：确定性数据库（Calvin 一脉及其后续 Aria/Bohm 等）通过「先定序、再执行」把 2PC 的协调开销从关键路径上移除；**并行提交/异步提交**（如 CockroachDB 的 parallel commits）把「事务是否已提交」变成一个可判定状态，避免未决事务长时间悬挂。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「2PC 是共识算法」 | 2PC 解决的是**原子提交**：协调者单点，协调者宕机则参与者阻塞；共识要求「即使 $f$ 个节点故障仍能推进」 |
| 2 | 「3PC 解决了 2PC 的问题，所以更先进」 | 3PC 的「超时默认提交」在**网络分区**下会导致一边提交一边回滚；工业界几乎不用（🔧） |
| 3 | 「空回滚是 2PC 的经典问题」 | 它属于 **TCC/Seata 框架**语境（Cancel 与 Try 的到达顺序问题）；经典 2PC 论文里没有这个术语（大纲把它放在 3.1.4，本笔记保留位置但标注出处） |
| 4 | 「Seata AT 模式的二阶段提交 = 数据库 COMMIT」 | AT 一阶段**已本地提交**，二阶段提交只是删 `undo_log` + 放全局锁；回滚才是真正做事的一步 |
| 5 | 「AT 模式的隔离性由数据库保证」 | 由 **TC 的全局写锁**保证；跨全局事务的写写冲突依赖它，锁竞争与死锁是运维重点 |
| 6 | 🔧 本书未给出「用共识消除协调者单点」的方案 | 补：**Paxos Commit**（Gray & Lamport, TOCS 2006）——把 2PC 的决议交给一个 Paxos 组复制，参与者向整个组询问结果，从而去掉协调者单点。这是本章唯一的「正统共识」入口，也是 Spanner 一脉（Paxos + 2PC）的理论依据 |
| 7 | 🔧 本书未给出 2PC 与共识的分层关系 | 补：生产系统的标准分层是「**组内 Raft/Multi-Paxos 复制 + 组间 2PC**」（TiDB/Percolator、Spanner、CockroachDB 皆然）。本书把 2PC 与共识并列，容易让读者以为二者是替代关系，实际是**相邻关系** |
| 8 | 🔧 TC 单点问题被低估 | Seata 的 TC 若单机部署，就完整继承了 2PC 的协调者单点；生产必须配置 TC 集群 + 高可用存储（db/redis 模式），并评估 TC 不可用期间的全局锁悬挂风险 |
| 9 | 🔧 本书未讨论 Saga 与补偿 | 长事务场景（跨服务、人工环节）通常不用 2PC，而用 **Saga**（正向服务 + 补偿服务）；2PC 的锁持有时间在跨服务场景下不可接受。这是本章选型视角的缺口 |
