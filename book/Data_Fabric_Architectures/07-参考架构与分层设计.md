## 7.1 参考架构的七层模型（学术重构）

⚠️ 本目录基于公共知识重构的七层参考架构，非本书原文：

| 层 | 名称 | 功能 | 对应前文章节 |
|---|---|---|---|
| L1 | 数据源适配层 | 连接器/协议适配/认证 | 04 章物理层 |
| L2 | 元数据采集层 | 三类元数据自动采集 | 03 章 |
| L3 | 知识图谱/语义层 | 实体归一/图谱/语义映射 | 03/04 章 |
| L4 | 策略/标签本体层 | 治理策略的形式化定义 | 08 章 |
| L5 | 编排/回路层 | DAG 状态机 + 主动元数据 | 05/06 章 |
| L6 | 消费/交付面 | API/BI/ML 消费接口 | 04 章消费侧 |
| L7 | 可观测/审计层 | 全链路追踪/合规审计 | 08 章 |

学术判断 ⚠️：七层模型的价值不在分层本身（任何架构都分层），而在**层间契约的形式化**——每层的输入/输出接口必须精确定义，否则层间耦合导致整体不可替换。

## 7.2 层间契约的形式化

设层 i 的接口为 I_i = (In_i, Out_i, Contract_i)：
- In_i：输入数据/事件类型
- Out_i：输出数据/事件类型
- Contract_i：不变量约束（类型/延迟/一致性）

**关键约束**：
1. **层间解耦**：L_i 只依赖 L_{i-1} 的 Out，不依赖其内部实现
2. **契约可替换**：满足 Contract_i 的任何实现可替换 L_i
3. **向上透明**：L_i 的变更不影响 L_{i+1}（只要 Contract_i 不变）

学术类比 ⚠️：这与软件工程中的**依赖倒置原则**（DIP）和**端口-适配器架构**（Hexagonal Architecture）同构——fabric 参考架构本质是把企业级数据系统视为一个大型端口-适配器系统。

## 7.3 🔧 G7（新增）：分层架构的最小可运行演示

场景：用 SQLite + Python 模拟 L1-L3 三层的最小 fabric。

```python
import sqlite3

# L1: 数据源适配（两个独立 SQLite 库）
src1 = sqlite3.connect(':memory:')
src1.execute("CREATE TABLE raw_orders(id INT, cust TEXT, amt REAL)")
src1.execute("INSERT INTO raw_orders VALUES (1,'Alice',100),(2,'Bob',200)")

src2 = sqlite3.connect(':memory:')
src2.execute("CREATE TABLE raw_customers(id INT, name TEXT, tier TEXT)")
src2.execute("INSERT INTO raw_customers VALUES (1,'Alice','gold'),(2,'Bob','silver')")

# L2: 元数据采集（模拟：记录表/列/行数）
meta = sqlite3.connect(':memory:')
meta.execute("CREATE TABLE catalog(src TEXT, tbl TEXT, cols TEXT, rows INT)")
meta.execute("INSERT INTO catalog VALUES ('src1','raw_orders','id,cust,amt',2)")
meta.execute("INSERT INTO catalog VALUES ('src2','raw_customers','id,name,tier',2)")

# L3: 语义层（模拟：跨源查询——cust↔name 映射）
result = src1.execute("SELECT cust, amt FROM raw_orders").fetchall()
customers = src2.execute("SELECT name, tier FROM raw_customers").fetchall()
# 应用层 JOIN（类比 DV 引擎的查询改写）
enriched = [(r[0], r[1], next((c[1] for c in customers if c[0]==r[0]), 'unknown')) for r in result]
print(f"enriched: {enriched}")
# enriched: [('Alice', 100.0, 'gold'), ('Bob', 200.0, 'silver')]
# ⚠️ 非本书引擎行为，Python+SQLite 分层演示
```

学术读数：三层分离的关键收益——L3 的语义映射（cust↔name）变更不影响 L1 的物理结构，只要 L2 的 catalog 保持更新。

## 7.4 连接器层的工业化现状

| 连接器类型 | 成熟度 | 代表 | 学术挑战 |
|---|---|---|---|
| 关系数据库 | 高 | JDBC/ODBC | 方言翻译的完备性 |
| 文档存储 | 中 | MongoDB/BSON 适配器 | 嵌套结构的扁平化 |
| 图存储 | 低 | Neo4j Bolt 适配器 | 图→表的投影信息损失 |
| 消息队列 | 中 | Kafka/ Pulsar 连接器 | 流式语义的批量化处理 |
| API/SaaS | 低-中 | REST/GraphQL 适配器 | Schema 漂移的自动检测 |

学术判断 ⚠️：连接器层的**长尾问题**是 fabric 实施的主要工程量——前 5 个连接器覆盖 80% 数据量，后 50 个连接器覆盖剩余 20% 但吃掉 60% 工期。

## 7.5 参考架构的部署拓扑

| 拓扑 | 描述 | 适用场景 |
|---|---|---|
| 集中式 | L1-L7 全部中央部署 | 单云/单数据中心 |
| 联邦式 | L1-L2 分布，L3-L7 集中 | 多源异构、语义集中 |
| 混合式 | L1-L3 分布，L4-L7 集中 | 大规模多云 |

学术判断 ⚠️：fabric 的"集中 vs 分布"选择与 mesh 的"领域自治"形成张力（09 章）——参考架构的拓扑选择本质是**组织权力结构的技术映射**。

## 7.8 Conway 定律与架构分层

学术上，架构分层与组织结构存在**同构关系**（Conway 定律） ⚠️：
- 每层对应一个团队：源层→数据工程团队，语义层→元数据团队，编排层→平台团队，治理层→合规团队，消费层→分析团队 ⚠️
- 层间接口 = 团队间 API ⚠️
- 架构复杂度 = 组织复杂度的映射 ⚠️

## 7.9 学术争议与开放问题

**争议：参考架构是否需要形式化验证？**

当前分层参考架构仅给出**描述性分层**，缺乏**形式化约束**——无法自动验证一个具体实现是否满足分层约束（如"是否存在 L1 直连 L5 的违规路径？"）。

- **正方** ⚠️：应引入架构一致性检查工具（类似类型检查器），自动验证层间依赖合规性。
- **反方** ⚠️：过度形式化会降低架构灵活性——实际部署中跨层优化不可避免。
- **开放问题**：分层约束的**可判定子集**是什么？即，哪些约束可以在多项式时间内自动验证？
