## 10.1 LLM 对 fabric 的三重影响

学术判断 ⚠️：LLM 从三个层面改变 fabric 的约束条件：

| 层面 | 影响 | 形式化 |
|---|---|---|
| 元数据生产 | LLM 辅助打标/血缘推断/本体演化 | coverage(B) ↑ 从 30% → 70%+（⚠️ 推定） |
| 消费面 | 自然语言查询 → 语义层压力增大 | Q 空间从 SQL/BI → NL query |
| 架构本身 | 向量存储/嵌入成为新的数据源类型 | S 集合扩展：S' = S ∪ {向量库} |

学术推论 ⚠️：LLM 解决了 fabric 的**最大瓶颈**（03 章 B 元数据覆盖率），同时引入了**新约束**（向量语义的精确性低于关系语义——嵌入相似度 ≠ 逻辑等价）。

## 10.2 向量存储作为 fabric 的新源类型

学术形式化 ⚠️：设向量存储为 V = {(e_i, v_i)}，其中 e_i = 实体，v_i = 嵌入向量。

- 查询：q(V, v_q) = {e_i | sim(v_i, v_q) > θ}
- 与关系查询的区别：结果是**概率性的**（sim > θ），非确定性的（WHERE clause）

**架构挑战**：
1. 向量语义与关系语义的**统一语义层**如何定义？（04 章的多模型推广）
2. 嵌入模型的版本化：换模型 → 全量重嵌入 → 语义漂移
3. 向量检索的**可解释性**：sim > θ 的结果无法给出逻辑解释

## 10.3 🔧 G10（新增）：LLM 辅助元数据打标的下限演示

场景：用 Python 模拟 LLM 辅助给数据集打业务标签——对比人工打标的覆盖率。

```python
import sqlite3

# 模拟：100 个数据集，人工已标 30 个，LLM 辅助标剩余 70 个
datasets = [{"id": i, "name": f"dataset_{i}", "human_label": None} for i in range(100)]
# 人工打标（30%）
for d in datasets[:30]:
    d["human_label"] = "sales" if d["id"] % 3 == 0 else "finance"

# LLM 辅助打标（模拟：基于名称模式匹配）
for d in datasets[30:]:
    if "sale" in d["name"] or d["id"] % 3 == 0:
        d["llm_label"] = "sales"
    else:
        d["llm_label"] = "finance"

# 覆盖率计算
labeled = sum(1 for d in datasets if d["human_label"] or d.get("llm_label"))
print(f"coverage: {labeled}/100 = {labeled}%")
# coverage: 100/100 = 100%
# ⚠️ 非本书引擎行为，Python 模拟 LLM 辅助打标
```

学术读数：LLM 辅助打标的**覆盖率**可从 30% → 100%，但**准确率**需要人工抽检——这是主动元数据 v3（6.6）的核心工程。

## 10.5 RAG 与 fabric 的架构接口

学术重构 ⚠️：RAG（检索增强生成）在 fabric 架构中的位置：

| RAG 组件 | fabric 对应层 | 接口 |
|---|---|---|
| 文档切分/嵌入 | L1 源适配（新源类型） | 嵌入管线连接器 |
| 向量存储 | L1 源适配（V 集合） | 向量库连接器 |
| 检索 | L3 语义层（向量查询） | 统一语义层的向量扩展 |
| 上下文组装 | L5 编排（检索→生成管道） | 编排引擎的新任务类型 |
| 生成 | L6 消费面（NL 输出） | 新消费接口 |

学术推论 ⚠️：RAG 不是 fabric 的"新功能"，而是 fabric 已有能力在**新消费模式**下的实例化——fabric 的元数据驱动/逻辑优先/自动化闭环在 RAG 管线中同样适用。

## 10.8 反问三则

1. "LLM 能否替代 fabric？"——不能。LLM 解决消费面的自然语言接口，但 fabric 解决的是**元数据驱动的自动化集成**——两者在不同层。
2. "fabric 在 AI 时代会更重要还是更不重要？"——更重要。AI 消费端（特征/嵌入/RAG）需要跨源**就近组装**，fabric 的语义层正是为此设计。
3. "学术专著能跟上 AI 的演进速度吗？"——学术的义务不是追热点，而是给出**可证伪的形式化**——即使具体技术变化，形式化框架的有效期更长。

## 10.9 AI 时代 fabric 演进的阶段模型（学术补充）

| 阶段 | AI 角色 | fabric 自动化等级 | 学术对应 |
|---|---|---|---|
| L0 辅助增强 | AI 作为工具（打标/搜索） | 人工驱动 | 信息检索 ⚠️ |
| L1 部分自主 | AI 作为代理（管道生成/质量修复） | 半自动 | 自动编程 ⚠️ |
| L2 协作共生 | AI 作为架构协作者（拓扑建议） | 条件自动 | 人机协作 ⚠️ |
| L3 自组织生态 | AI 作为架构本身 | 全自动 | 自组织系统 ⚠️ |

> **学术命题** ⚠️：当前工业实践处于 L0→L1 过渡期；学术研究的终极目标是 L3——但 L3 需要**可证明最优**的架构决策，这要求 fabric 的形式化理论先于 AI 优化理论成熟。

## 10.11 学术争议与开放问题

**争议：AI 驱动的架构决策是否可审计？**

- **正方** ⚠️：可解释 AI（XAI）技术可追溯决策路径——元数据变更→推荐→执行的链路可审计。
- **反方** ⚠️：深度神经网络的决策本质不可解释——只能审计**输入**（元数据）和**约束**（策略），不能审计**决策过程**。
- **本目录立场** ⚠️：至少保证决策的**输入上下文**和**约束条件**可记录（02 章铁律 3：闭环必须可观测），即使决策过程本身不可解释。

## 10.9 🔧 G11（新增）：向量语义 vs 关系语义的精确性对比（DuckDB 类比）

场景：模拟同一查询在关系语义（确定性）和向量语义（概率性）下的结果差异。

```python
import duckdb
# 关系语义：确定性查询
rel_result = duckdb.sql("""
    SELECT * FROM (VALUES ('Alice','sales'), ('Bob','finance'), ('Carol','sales'))
    t(name, dept) WHERE dept = 'sales'
""").fetchall()
# 向量语义：概率性查询（模拟嵌入相似度）
import random
vector_data = [('Alice', 0.92), ('Bob', 0.31), ('Carol', 0.88), ('Dave', 0.75)]
vec_result = [(name, sim) for name, sim in vector_data if sim > 0.7]
print(f"rel={len(rel_result)} rows (exact), vec={len(vec_result)} rows (probabilistic)")
# rel=2 rows (exact), vec=3 rows (probabilistic)（⚠️ 非本书引擎行为，DuckDB+Python 向量模拟）
```

学术读数：向量语义的**召回率更高但精确度更低**——sim > θ 的结果包含语义近似但不等价的条目。这是 10.2 架构挑战 1 的实证：统一语义层必须处理**概率性结果与确定性结果的混合**。
