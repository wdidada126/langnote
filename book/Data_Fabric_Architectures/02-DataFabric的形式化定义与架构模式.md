# 02 · Data Fabric 的形式化定义与架构模式

> 主题章（⚠️ 推定归属本书"核心定义"部分）。学术专著的首要义务是给核心概念一个**可证伪的定义**。本章把 fabric 从厂商营销话术中剥离，尝试给出形式化表述与架构模式分类。与 #210 的 [02-DataFabric的定义与能力模型.md](../Data_Fabric_as_Modern_Data_Architecture/02-DataFabric的定义与能力模型.md) 互补：#210 给能力模型（工程分类），本章给形式化（学科分类）。

## 2.2 形式化定义尝试（⚠️ 本目录学术重构）

设企业数据环境为多元组 E = (S, D, M, Q, P)：
- S = {s₁, ..., sₙ}：异构数据源集合
- D = {d₁, ..., dₘ}：数据资产集合（物理副本）
- M：元数据图谱（03 章），定义在 D 上的带标签有向图
- Q：查询/消费请求空间
- P：策略约束集合

**Data Fabric 定义**：F 是作用于 E 的架构层，满足——
1. **语义统一性**：∀q ∈ Q，F(q) 返回语义一致的结果，不论物理源
2. **逻辑优先性**：F 优先通过 M 中的语义映射路由查询，而非物理搬运数据
3. **元数据驱动**：F 的行为（路由、物化、策略下发）由 M 的当前状态决定
4. **自动化闭环**：F 包含从 M 到自身配置调整的反馈回路（06 章）

⚠️ 此形式化为**本目录重构**，非本书原文。目的是展示学术体裁应给出的定义精度。

## 2.3 架构模式分类学

基于 2.2 的四个条件，可推导出 fabric 的**架构模式谱系**：

| 模式 | 条件满足度 | 典型实现 | 适用场景 |
|---|---|---|---|
| 全虚拟化 | 1✅ 2✅ 3⚠️ 4❌ | Denodo 系 | 源少/查询简单 |
| 元数据驱动编织 | 1✅ 2✅ 3✅ 4⚠️ | IBM/Informatica | 中大型混合环境 |
| 主动元数据编织 | 1✅ 2✅ 3✅ 4✅ | 学术理想型 | 自动化成熟组织 |
| 伪 fabric | 1⚠️ 2❌ 3⚠️ 4❌ | 营销包装的 ETL 平台 | 无 |

裁决标准：**条件 4（自动化闭环）是 fabric 与老 EAI/ESB 的分水岭**。无闭环的"fabric"只是数据虚拟化 2.0。

## 2.4 铁律三条（⚠️ 本目录提炼）

从 2.2 可推导出三条不可违反的架构铁律：

1. **语义集中、数据分布**：fabric 集中的是元数据/语义，不是数据本身。违反此条则退化为"数据湖 2.0"。
2. **元数据质量 = 架构质量**：M 的完整性/一致性/新鲜度直接决定 F 的正确性上限。
3. **闭环必须可观测**：反馈回路（条件 4）的执行轨迹必须可审计，否则"自动化"不可信。

## 2.5 反定义：fabric 不是什么

| 它不是 | 为什么不是 | 辨析 |
|---|---|---|
| 数据虚拟化 | 虚拟化只满足条件 1-2，缺 3-4 | 虚拟化是 fabric 的**子组件** |
| ETL/ELT 平台 | 搬运优先，违反条件 2 | 搬运是 fabric 的**退化路径** |
| 数据湖/湖仓 | 物理统一而非语义统一 | 湖仓是 fabric 的**物化底座** |
| 数据目录 | 目录是 M 的载体，不是 F 本身 | 目录是 fabric 的**元数据面** |
| 数据中台 | 组织复用工程，非自动化语义层 | 目标同、机制异（01 章 1.3） |

## 2.7 🔧 类比组 G1（SQLite）：形式化条件的最小违反演示

场景：两个 SQLite 数据库（orders.db, inventory.db），一个"fabric 层"尝试统一查询。

```sql
-- 条件 1（语义统一）：两库的 product_id 含义不同（orders=SKU, inventory=内部码）
-- 若无映射表，SELECT 返回语义不一致 → 条件 1 违反
ATTACH 'inventory.db' AS inv;
-- 条件 2（逻辑优先）：
SELECT o.*, i.qty FROM orders o JOIN inv.items i ON o.product_id = i.sku;
-- 此查询 0 行搬运，纯逻辑 → 条件 2 满足
-- 条件 3（元数据驱动）：映射关系 product_id↔sku 需人工硬编码
-- 若无自动发现 → 条件 3 违反（⚠️ 非本书引擎行为，SQLite 类比）
```

读数：SQLite 级别的"fabric"只能演示条件 1-2；条件 3-4 需要元数据自动化——这正是学术专著要形式化的部分。

## 2.8 自检三题

1. 用 2.2 的四条件判定 Microsoft Fabric 是否为 data fabric（答案：否——它是统一 SaaS 平台，条件 2 违反）。
2. 为什么条件 4（闭环）是分水岭而非条件 1-3？（答：1-3 在 2010 年代的数据虚拟化产品中已满足，fabric 的"新"在 4。）
3. 2.3 表中"伪 fabric"模式在工业中是否常见？（⚠️ 转述社区共识：非常常见，是 2023-2024 市场噪音的主要来源。）

## 2.9 形式化性质分析（学术补充）

**命题 1**：02 章四条件（语义统一 / 逻辑优先 / 元数据驱动 / 自动化闭环）**相互独立**。

*证明思路*：构造反例——
- {1,2,3} 满足但 {4} 不满足 = 传统数据虚拟化平台（2010s 已实现）
- {1,2} 满足但 {3,4} 不满足 = 手工配置的联邦查询引擎
- {1,3,4} 满足但 {2} 不满足 = 元数据驱动的 ETL 搬运（违反逻辑优先）
- {2,3,4} 满足但 {1} 不满足 = 逻辑路由但语义不一致（映射错误场景）

每个条件的缺失都产生**不同类别的非 fabric 系统**，故四条件独立。□

**命题 2**：条件 4（自动化闭环）是 fabric 区别于所有前 fabric 架构的**最小充分区分条件**。

*论据*：条件 1-3 在 2010 年代的数据虚拟化产品（Denodo 系）中已分别或组合满足；条件 4 是 2020s fabric 叙事的**独有增量**。无闭环的"fabric"在学术上等价于"数据虚拟化 2.0"。
