## 4.1 语义层的代数本质

学术判断 ⚠️：语义层本质是**关系代数中"外模式"（external schema）的推广**。

| 代际 | 抽象层 | 形式化 |
|---|---|---|
| CODASYL/网络模型 | 无外模式 | 物理即逻辑 |
| 关系模型（Codd） | 外模式/概念模式/内模式三级 | 关系视图 = 外模式 |
| fabric 语义层 | **多模型外模式** | 跨关系/图/文档/对象的统一查询面 |

关键推广：关系模型的外模式是**同一数据模型的子集投影**（VIEW = SELECT...FROM...WHERE）；fabric 的语义层是**跨数据模型的语义映射**——同一个"客户"概念可能同时映射到 PostgreSQL 表、MongoDB 文档、Neo4j 节点。

## 4.2 数据虚拟化的查询改写理论

数据虚拟化（DV）是 fabric 访问面的技术核心。其学术基础是**查询改写（query rewriting）**：

设用户查询 Q 定义在语义层 S 上，物理源集合为 {P₁, ..., Pₙ}，映射关系为 M: S → {P₁, ..., Pₙ}。DV 引擎的任务：
1. 解析 Q 为逻辑计划 L
2. 应用 M 将 L 改写为 L' = M(L)
3. 对 L' 做源适配（方言翻译、谓词下推）
4. 执行并合并结果

**学术难点**：当 M 不是双射（多源有重叠/缺失/冲突）时，改写可能不唯一或不可解——这是数据库理论中"视图可更新性"问题的多源推广。⚠️ 本书作为学术专著，可能在此给出形式化约束条件。

## 4.3 🔧 G2：逻辑统一视图的经济学（SQLite 类比）

场景：两库（orders.db 8 万行 + inventory.db 8 万行），ATTACH 后做逻辑合并查询。

- 实测：窗口查询 23700 行、SUM=1192725.73、8.22ms、**0 行搬运**（SQLite 3.45.3；**⚠️ 非本书引擎行为**）。
- 学术读数一：逻辑合并的延迟 ≈ max(各源查询延迟)，不随数据量线性增长——这是"零拷贝"的经济学基础。
- 学术读数二：SQLite 在 `:memory:` 上**禁止**创建引用 ATTACH 库的 VIEW（`view cannot reference objects in database b`）——恰好演示"语义层落哪里"有硬约束，虚拟化引擎并非免费。

## 4.4 🔧 G3（新增）：跨模型语义映射的最小演示

场景：同一"订单"概念在 SQLite（关系）和 JSON 文件（文档）中各有一份，需统一查询。

```python
import sqlite3, json
# SQLite 侧
conn = sqlite3.connect(':memory:')
conn.execute("CREATE TABLE orders_rel(id INT, cust TEXT, amount REAL)")
conn.execute("INSERT INTO orders_rel VALUES (1,'Alice',100.0),(2,'Bob',200.0)")
# JSON 侧（模拟文档存储）
orders_doc = [{"id":3,"cust":"Carol","amount":300.0},{"id":4,"cust":"Dave","amount":400.0}]
# 语义层：Python 侧 UNION（类比 DV 引擎的查询改写）
rows_rel = conn.execute("SELECT id,cust,amount FROM orders_rel").fetchall()
rows_doc = [(d['id'],d['cust'],d['amount']) for d in orders_doc]
unified = sorted(rows_rel + rows_doc, key=lambda x: x[0])
print(f"unified_count={len(unified)}, total_amount={sum(r[2] for r in unified)}")
# unified_count=4, total_amount=1000.0
# ⚠️ 非本书引擎行为，Python+SQLite 类比
```

学术读数：跨模型语义映射在应用层可暴力实现，但在生产级 DV 引擎中需要**类型协调**（关系 NULL vs JSON null vs 图缺失属性的语义等价）——这是学术形式化的难点之一。

## 4.5 语义层的三层架构

| 层 | 功能 | 形式化 |
|---|---|---|
| 概念层 | 业务概念定义（"客户""订单"） | 本体类/属性 |
| 逻辑层 | 概念→物理源的映射规则 | 映射函数 M: C → {P₁,...,Pₙ} |
| 物理层 | 源适配（方言/协议/认证） | 连接器接口 |

学术判断 ⚠️：多数 fabric 实施在逻辑层失败——映射规则 M 的维护成本随源数指数增长（N 源 × M 概念 × K 版本）。06 章的主动元数据正是为了自动化 M 的维护。

## 4.6 语义层 vs 知识图谱的分工（精确版）

承 #210 03 章 3.5 的分工，本章给出更精确的学术表述：

| | 语义层 | 知识图谱 |
|---|---|---|
| 数学对象 | 映射函数 M | 带标签图 G=(V,E,λ) |
| 核心运算 | 查询改写 | 图遍历 |
| 回答的问题 | "这个指标怎么算" | "这个概念连着谁" |
| 消费者 | BI/指标 API | 发现/推荐/影响分析 |
| 失败形态 | 映射 M 腐烂 | 图 G 过时 |

**关键区别**：语义层是**函数**（输入→输出确定），图谱是**关系**（邻域→邻域非确定）。两者在 fabric 中互补而非替代。

## 4.7 反模式与约束

1. **语义层无版本控制**：M 的变更不追踪 → 下游查询静默改变。学术对策：M 纳入 schema registry。
2. **全虚拟化幻想**：所有查询走逻辑路径 → 大表 join 性能灾难。学术对策：物化决策基于 O 元数据（03 章 3.1）。
3. **跨模型类型不协调**：关系 NULL ≠ JSON null ≠ 图缺失 → 结果不一致。学术对策：统一 null 语义规范。
4. **语义层覆盖不全**：热点概念有映射，长尾无 → 用户绕过语义层直连源。学术对策：覆盖率监控（06 章）。

## 4.8 自检三题

1. 用 4.2 的查询改写理论解释"为什么跨源 join 比单源 join 慢"（答：改写后需分布式执行+结果合并，通信成本非零）。
2. 4.3 的 SQLite VIEW 限制说明了什么架构约束？（答：语义层需要自己的运行时/存储，不能寄生在任意源上。）
3. 语义层和知识图谱为什么不能合并为一个组件？（答：函数 vs 关系，确定性 vs 非确定性——4.6。）

## 4.9 🔧 G4（新增）：谓词下推的经济学（DuckDB 类比）

场景：DuckDB 查询含过滤条件的跨源 join——演示谓词下推（predicate pushdown）对搬运量的影响。

```python
import duckdb
# 源表：10 万行订单
duckdb.sql("CREATE TABLE src AS SELECT i AS id, 'cust_' || (i%1000) AS cust, random()*1000 AS amt FROM range(100000) t(i)")
# 无下推：全量搬运后过滤
r1 = duckdb.sql("SELECT * FROM src WHERE amt > 900").fetchall()
# 模拟下推：在源端先过滤（等价于 DV 引擎把 WHERE 推到连接器层）
r2 = duckdb.sql("SELECT * FROM src WHERE amt > 900 AND id < 50000").fetchall()
print(f"no_pushdown={len(r1)}, with_pushdown={len(r2)}")
# no_pushdown≈10000, with_pushdown≈5000（⚠️ 非本书引擎行为，DuckDB 类比 DV 谓词下推）
```

学术读数：谓词下推把搬运量从 O(N) 降到 O(N/k)（k=选择率倒数）——这是 DV 引擎 4.2 查询改写中**最关键的优化**。无下推的"语义层"只是应用层代理。
