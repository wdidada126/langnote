## 核心精讲

### 1. 逻辑 vs 物理：一张决策表

| 需求 | 选择 | 理由 |
| --- | --- | --- |
| 版本迁移/单表救回 | pg_dump | 跨版本、对象级粒度 |
| 整机灾难恢复基线 | basebackup + WAL 归档 | 速度、字节级一致 |
| 任意时间点（PITR） | 物理路线 | 逻辑备份无 WAL 概念 |
| 集群级全局对象 | pg_dumpall -g | 角色/表空间定义不在单库里 |

文档转述 ⚠️：

```bash
pg_dump -Fd -j 4 -Z gzip:6 -f /backup/appdir appdb     # 目录格式+并行+压缩
pg_restore -j 4 -d appnew /backup/appdir
pg_dump --table=public.orders -Fc appdb > orders.dump  # 单表
```

### 2. 物理基线 + 归档闭环（PITR 三件套）

```bash
pg_basebackup -h host -D /backup/base -Ft -z -Xs -P -c fast
```

```ini
archive_mode = on
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'
archive_timeout = 300        # 低峰期也保证 WAL 流不断档
```

- PITR（PG12+ 新恢复体系）：备机/新目录解包 base + archive → 放 `recovery.signal` →
  `recovery_target_time = '2024-06-01 10:30:00'` → 启动自动恢复并 promote。
- `pg_create_restore_point('deploy_v2')`：给"发布前"打锚点，出事直接恢复至锚点，比人肉记时间可靠。

### 3. 丢表恢复的实战路线（Ch11 名食谱）

1. **别慌**：确认误操作时间 T 与影响对象；停业务写入（或评估锁影响）。
2. 拉起**并行恢复实例**（另一台机器，basebackup+archive 恢复到 T-1s），`pg_dump --table` 抽回目标表。
3. 主库侧只回灌需要的对象——全库 PITR 会丢 T 之后所有数据。
- 预防三件套：`log_statement='ddl'`、权限收紧（呼应 [03-安全与权限.md](03-安全与权限.md)）、延迟备库
  （`recovery_min_apply_delay`，专治误 DROP）。

### 4. 备份提速与增量思想（Ch11）

- `-j` 并行 dump（表级粒度）、`-Z` 并行压缩；basebackup 走复制协议流式传输，`max_bundle_size` 打包小文件为后话。
- **增量备份**：原生 pg_basebackup 只有全量；业界方案 pgBackRest（diff/incremental + 保留策略 + 并行）已成事实标准。
- WAL 压缩（PG15 起 `wal_compression=lz4/zstd` 选项）——归档量与网络压力直接受益（转述 ⚠️，PG16 可用）。

### 5. 验证纪律：恢复演练自动化（Ch11）

```bash
pg_verifybackup /backup/base          # 校验 basebackup 完整性
pg_restore -l app.dump                # 目录/清单可读性
```

- 制度口径：任何备份策略必须回答三问——最近一次成功**恢复**是什么时候？RTO 实测多少分钟？单表级恢复可行吗？
- CI 做法：每周定时"自动恢复到临时实例 + 跑断言查询（pgTAP）+ 销毁"，把备份从"文件"变成"服务"。

## 常见坑与判读

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 恢复报 `requested recovery start point ... before oldest WAL` | 基线太旧/归档断链 | 重做 basebackup；修 archive_command |
| basebackup 后 WAL 疯狂堆积 | 废弃复制槽钉住 WAL | 检查 `pg_replication_slots`，删孤儿槽 |
| dump 后 restore 角色缺失 | 忘记 pg_dumpall -g | 全局对象单独版本化管理 |
| archive_command 一直失败但服务正常 | 归档失败静默积压 | `pg_stat_archiver` 建告警（failed_count） |

## 核心概念速览（中英对照）

- **基础备份** — base backup：物理恢复的字节基线，pg_basebackup 产物。
- **连续归档** — continuous archiving / WAL archiving：把 WAL 持续外送以支持 PITR。
- **时间点恢复** — PITR：恢复到归档覆盖的任意时刻。
- **恢复信号** — recovery.signal：PG12+ 以文件驱动的恢复模式开关。
- **恢复锚点** — restore point：命名的恢复目标，发布/变更打点用。
- **逻辑转储** — logical dump：pg_dump 对象级 SQL/二进制转储，跨版本可移植。
- **目录格式** — directory format：pg_dump 可并行的分片输出格式。
- **延迟备库** — recovery_min_apply_delay：给误操作留反悔窗口的从库。
- **备份校验** — pg_verifybackup：恢复前验证归档完整性。
- **增量备份** — incremental/differential backup：pgBackRest 类工具补齐的能力。
- **RPO/RTO** — 可容忍丢数据量/恢复耗时：备份策略的验收指标。

## 最新演进与工业实践

- **pgBackRest**（✅ https://github.com/pgbackrest/pgbackrest ，2026-09 实测 4408★、活跃）：
  全量/增量/差异 + 对象存储 + 并行 + expire 保留策略，PG16–18 时代企业标配；README 明确支持 PG 12 及以上全部版本。
- **pg_combinebackup**（社区增量合并工具，2024 年末发布）：基于标签文件与 manifest 实现原生 basebackup 的
  增量合并恢复（转述 ⚠️：本环境未能验证其仓库链接，以官方发行公告口径为准）。
- **pg_dump/pg_upgrade 联动（✅ 发行说明）**：PG17 的 `pg_upgrade` 保留逻辑槽/订阅状态、PG18 保留优化器统计
  ——升级与备份路线图的耦合越来越紧。
- **归档目标**：`archive_mode = always | on | remote_local`（PG16 语义）+ 对象存储直写（S3/GCS via 工具）
  取代 NFS cp 的 `archive_command` 是 2024–2026 主流；云厂商内建 PITR 即"basebackup+归档"的产品化（通识转述）。
- **恢复即测试**：用 `pg_restore_point` + 容器化秒级克隆做"任意时间点沙箱"验证，配合 pgTAP
  （https://github.com/theory/pgtap ，✅ 可达）断言，成为头部团队 SOP。
