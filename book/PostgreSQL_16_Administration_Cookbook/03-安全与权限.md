## 核心精讲

### 1. 角色不是账号（Ch6）

文档转述 ⚠️：

```sql
CREATE ROLE app_ro LOGIN PASSWORD 'x';        -- LOGIN 属性：能登录的才叫"账号"
CREATE ROLE reporter NOLOGIN;                 -- 权限包：纯角色
GRANT reporter TO app_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA reporting TO reporter;
ALTER DEFAULT PRIVILEGES IN SCHEMA reporting GRANT SELECT ON TABLES TO reporter;
```

- 两个必须分清的正交属性：`LOGIN` 与 `SUPERUSER/ROLE 成员`。给"权限包角色"加 LOGIN 是最常见的越权起点。
- `pg_hba.conf` 里可按用户/库正则匹配（✅ PG16 发行说明：用户与库名支持正则条目），把"谁能从哪连"从库内搬到网络边界。
- `REVOKE` 不级联到成员角色，写治理脚本时配合 `DROP OWNED BY` 处理残留对象权限。

### 2. 密码与认证演进线（Ch6）

- `password_encryption = scram-sha-256`（PG14 起默认）：md5 仅为兼容保留；本书口径是"存量 md5 哈希必须轮换"。
- PG16 相关（✅ 发行说明）：`scram_iterations` GUC 可调迭代次数（强度 vs 登录延迟）；libpq 新增
  `require_auth` 连接选项——客户端可以声明"只接受哪些认证方法"，防降级攻击。
- 外部认证：LDAP（`ldapbind`）、Kerberos（GSSAPI）、证书（`clientcert=verify-full`）；
  PG18（✅ 发行说明）OAuth 2.0 认证进入核心——本书时代的"外部认证系统"食谱正在被内置化。

### 3. 传输加密与连接治理（Ch6）

```text
# pg_hba.conf：只允许 TLS，且证书校验到 CA
hostssl all all 0.0.0.0/0 scram-sha-256
postgresql.conf：ssl = on; ssl_ca_file; ssl_min_protocol_version = TLSv1.2
```

- `hostssl` 前缀 + 客户端证书（`verify-full`）+ 口令双因子，是本书"强安全"三层拼图的标准答案。

### 4. 最小权限与 RLS（Ch6）

- 对象权限粒度：SCHEMA USAGE → TABLE 增删改查 → **列级**（`GRANT INSERT (col)`）→ 行级（RLS 策略）。
- RLS 要点：`FORCE ROW LEVEL SECURITY` 连表主也受策略约束；策略用 `USING`（可见）与 `WITH CHECK`（可写）两个谓词；
  性能上策略谓词会进扫描——大表务必给策略列建索引。

### 5. 审计的三档做法（Ch6）

| 档 | 手段 | 覆盖面 | 代价 |
| --- | --- | --- | --- |
| 轻 | `log_connections/log_disconnections` | 谁何时连 | 日志量 |
| 中 | 事件触发器（DDL 审计） | 结构变更 | 只能 server 端 DDL |
| 重 | pgAudit 扩展 | 按类别记 SELECT/DDL/DML 细节 | 高日志量+需预加载 |

文档转述 ⚠️：`shared_preload_libraries='pgaudit'` 后 `SET pgaudit.log = 'ddl,read';`。

### 6. 权限全景：治理必查的三条 SQL（Ch6）

文档转述 ⚠️（依据 PostgreSQL 官方监控视图一节）：

```sql
SELECT r.rolname, r.rolsuper,
       ARRAY(SELECT b.rolname FROM pg_auth_members m
             JOIN pg_roles b ON m.roleid = b.oid WHERE m.member = r.oid) AS member_of
FROM pg_roles r;                                          -- ① 角色继承树：防越权链条
SELECT has_table_privilege('app_ro', 'reporting.sales', 'SELECT');  -- ② 单点真值：查"为什么看不了"
SELECT grantee, table_schema, table_name, privilege_type
FROM information_schema.role_table_grants
WHERE table_schema = 'reporting';                         -- ③ 对象级清单：审计季盘点
```

- 三条各管一事：①看成员关系是否被"角色套角色"绕开最小权限；②`has_*_privilege` 系列函数返回的是
  含继承与默认权限之后的最终真值，是排错首选；③`information_schema` 视图给的是当前库的显式授权面。
- 注意口径：`role_table_grants` 只反映**当前数据库**，列级权限在 `role_column_grants`——
  治理脚本要按 `psql -l` 遍历各库分别聚合，单库快照不等于全实例快照。

## 常见坑与判读

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 用户能登录却看不了表 | 缺 SCHEMA USAGE（PG15 起 public 架构默认不再人人可建） | 授 `USAGE ON SCHEMA` + 默认权限 |
| RLS "没生效" | 表主绕过 / 未 FORCE | `ALTER TABLE ... FORCE ROW LEVEL SECURITY` |
| 改完 hba 不生效 | 只 reload 没确认语法 | `SELECT pg_reload_conf()` 后看 `pg_hba_file_rules` 的 error 列 |
| 密码升 scram 后旧应用连不上 | 存量 md5 哈希未轮换 | 重设一次 `ALTER ROLE ... PASSWORD` 触发哈希升级 |
| 连接池/老驱动 SASL 握手失败 | 池端只实现 md5 流程或版本过旧 | 升级连接池与 libpq 客户端，再轮换哈希 |
| "删了角色却还有权限" | 对象归属与授权残留挂在已删角色名下 | 先 `REASSIGN OWNED BY` 再 `DROP OWNED BY` |

## 核心概念速览（中英对照）

- **LOGIN 属性** — login attribute：角色可否作为会话入口，与权限包概念正交。
- **默认权限** — ALTER DEFAULT PRIVILEGES：对未来新建对象生效的授权规则。
- **行级安全** — Row Level Security (RLS)：按策略谓词过滤可见行。
- **策略谓词** — USING / WITH CHECK：RLS 的读过滤与写校验两半。
- **SCRAM** — SCRAM-SHA-256：盐化迭代哈希，PG 现代口令默认。
- **scram_iterations** — SCRAM 迭代次数：PG16 GUC，强度与延迟旋钮。
- **require_auth** — libpq 连接选项：客户端声明可接受的认证方法，防降级。
- **证书双向认证** — clientcert=verify-full：CN 与用户名一致才算通过。
- **事件触发器** — event trigger：DDL 级审计钩子。
- **pgAudit** — 细粒度审计扩展：按 READ/WRITE/DDL 等类别记录。
- **DROP OWNED BY** — 权限清理：删除角色名下对象与授权残留。

## 最新演进与工业实践

- **PG16（✅）**：`scram_iterations`、libpq `require_auth`、pg_hba 用户/库正则匹配。
- **PG17（✅ 发行说明）**：`sslnegotiation=immediate`（TLS 快握手，省往返）；SCRAM 认证失败不再泄露"用户是否存在"类时序信息（小幅加固）。
- **PG18（✅ 发行说明）**：OAuth 认证入核心；`OLD/NEW` 增强 RETURNING 也服务于审计型写法。
- **pgAudit**：官方仓库 https://github.com/pgaudit/pgaudit （✅ 已验证可达）——企业合规
  （SOX/等保）场景事实标准，版本跟进 PG 主线到 18。
- **最小权限工程化**：2024–2026 趋势是把授权治理写进迁移脚本（Flyway/Liquibase）+ CI 里用
  `information_schema`/`acis` 快照对比做"权限漂移"检测——与本书 Ch7 的可重复脚本思想同源（转述 ⚠️）。
- **密钥与口令管理**：Vault/KMS 注入 `PGPASSFILE` 替代硬编码连接串已是行业默认做法（通识转述）。
