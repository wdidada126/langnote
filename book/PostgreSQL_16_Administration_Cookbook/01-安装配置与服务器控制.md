## 核心精讲

### 1. 安装的三条路与一个观念（Ch1，⚠️ 小节推定）

- **发行包**（apt/yum、PGDG 仓库）：二进制带调试符号少、升级省心，生产主流；`initdb` 后数据目录默认属主 `postgres`，
  权限必须 `0700`——PG 拒绝为世界可读的数据目录。
- **源码**：`configure && make && make install`；DBA 装源码的主要动机是获得 `pg_config` 一致的开发头文件与自定义编译开关。
- **容器**：官方镜像 `postgres:16` 把数据目录放卷；本书强调容器适合开发/评估，生产上要小心 WAL 刷盘与卷语义。
- 连接排错的标准链路：**网络可达 → `listen_addresses` 含地址 → `pg_hba.conf` 有放行条目 → 认证通过**。
  90% 的"连不上"卡在第 3 步，报错分别是 `no pg_hba.conf entry` 与 `password authentication failed`。

### 2. 版本、时长与"这台机器到底是谁"（Ch2）

文档转述 ⚠️：

```sql
SELECT version();                          -- 精确小版本，如 PostgreSQL 16.x on x86_64-pc-linux-gnu
SELECT pg_postmaster_start_time(), now() - pg_postmaster_start_time() AS uptime;
SHOW config_file; SHOW data_directory; SHOW hba_file; SHOW log_directory;
SELECT oid, datname FROM pg_database;     -- 系统标识符 = 集群身份证（pg_control 里）
```

- 系统标识符（system identifier）决定备份/备库归属：错配 WAL 直接拒绝恢复——这是 Ch11 校验备份的第一道闸。
- 行数**没有**精确免费午餐：`reltuples`（autovacuum 维护的估算）快而不准；`COUNT(*)` 全扫准而贵，两者都要会选。

### 3. 参数四级覆盖模型（Ch3）

`pg_settings.source` 字段如实回答"这个值是谁设的"：`default / configuration file / override / database / user / session`。
优先级：会话 > 角色 > 库 > `postgresql.conf`/`ALTER SYSTEM`(=`postgresql.auto.conf`) > 编译默认。

文档转述 ⚠️：

```sql
ALTER SYSTEM SET work_mem = '16MB';   -- 写入 postgresql.auto.conf，reload 生效（视参数）
ALTER DATABASE app SET statement_timeout = '30s';
ALTER ROLE reporting SET work_mem = '256MB';
SELECT name, setting, source, context FROM pg_settings WHERE name = 'work_mem';
```

- `context` 列是本书式的关键知识点：`internal`（改了也没用）、`postmaster`（必须重启）、`sighup`（reload 即可）、
  `superuser-backend`/`backend`（新会话生效）、`superuser`/`user`（可随时 SET）。选错生效方式就选错了变更窗口。
- 判读纪律：`postgresql.auto.conf` 的值会**静默覆盖** `postgresql.conf`，排查参数"不生效"先看它。

### 4. 扩展：把 PG 变成乐高（Ch3）

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;  -- 配合 shared_preload_libraries，需重启
SELECT * FROM pg_available_extensions WHERE installed_version IS NULL;
ALTER EXTENSION pg_stat_statements UPDATE;           -- 小版本升级路径
```

- 需要预加载的扩展（如 `pg_stat_statements`）必须先写进 `shared_preload_libraries` 再重启，然后才能 `CREATE EXTENSION`。

### 5. 服务器控制与连接池（Ch4）

- `pg_ctl` 三种停法：`smart`（等所有客户端断开，可能永远等不完）、`fast`（回滚事务+断连，默认选择）、
  `immediate`(不做干净关闭，恢复时重放 WAL——仅救援用)。
- 资源治理工具箱：`max_connections`（每连接一个后端进程，连接数是内存账）、`superuser_reserved_connections`、
  `idle_in_transaction_session_timeout`（杀掉挂起事务，防 WAL/vacuum 被拖住）、`statement_timeout`、
  `idle_session_timeout`（PG14+ 空闲会话直接断）。
- **PgBouncer 三模式**：`session`（最保守）、`transaction`（默认推荐，池化率最高）、`statement`。
  要点：`transaction` 模式下会话级状态（`SET`、advisory lock、temp table）不可靠；PG16 侧配合
  `server_reset_query_always` 等语义，客户端连接串避免依赖 `search_path` 中途切换。

## 常见坑与判读

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 改 `postgresql.conf` 参数不生效 | `postgresql.auto.conf` 同名参数覆盖 | `RESET` 或 `ALTER SYSTEM RESET`；查 `pg_settings.source` |
| `FATAL: sorry, too many clients` | 连接风暴，池缺失 | 上 PgBouncer + 降 `max_connections` + 预留超级用户 |
| reload 后参数没变 | 参数 `context=postmaster` | 安排重启窗口；或 `pg_ctl restart` |
| 备库起了但"不认识"主库 | 系统标识符/WAL 时间线错配 | 核对 `pg_controldata` 的 Database system identifier |

## 核心概念速览（中英对照）

- **数据目录** — data directory / $PGDATA：集群全部文件根，权限 0700 是硬约束。
- **系统标识符** — system identifier：pg_control 内集群唯一 ID，备份/复制匹配凭证。
- **预加载库** — shared_preload_libraries：服务器启动即加载的扩展，需重启。
- **参数上下文** — GUC context：internal/postmaster/sighup/backend/user 决定生效方式。
- **自动配置文件** — postgresql.auto.conf：`ALTER SYSTEM` 落盘处，覆盖主配置。
- **pg_hba 主机认证表** — host-based authentication：连接放行的四元组（用户/库/地址/方法）。
- **优雅停机** — smart/fast shutdown：fast 为默认生产选择，immediate 仅救援。
- **连接池模式** — session/transaction pooling：PgBouncer 池化粒度，后者牺牲会话语义。
- **保留连接** — superuser_reserved_connections：给管理员留的逃生通道。
- **空闲事务超时** — idle_in_transaction_session_timeout：防挂起事务拖住 WAL 回收与 vacuum。
- **系统目录** — system catalogs（pg_class 等）：数据库自描述的元数据表。
- **reltuples 估算** — planner statistics estimate：autovacuum 维护的行数近似值。

## 最新演进与工业实践

- **PG17（2024-09）**：新内存上下文体系大幅降低服务器与 VACUUM 内存抖动（官方发行说明 ✅）；`sslnegotiation=immediate`
  省一个 TLS 往返；发行说明见 https://www.postgresql.org/docs/release/17.0/ （✅ 已验证可达）。
- **PG18（2025-09）**：异步 I/O 子系统（`io_method = worker | io_uring | sync`，Linux io_uring 可用）改变顺序扫描/
  位图堆扫描/vacuum 的 I/O 形态（✅ 文档：https://www.postgresql.org/docs/current/runtime-config-resource.html ）；
  OAuth 认证进核心（影响 Ch6 认证的演进判断）；`uuidv7()` 时间有序 UUID 成为默认建键新宠。
- **PG16 自带的管理改进**（✅ 发行说明）：`pg_stat_io` 每后端类型 I/O 统计、逻辑复制可从备库发布、
  vacuum 冻结性能提升、`BUFFER_USAGE_LIMIT` 限制 vacuum 对共享缓冲区的冲刷。
- **容器与安装现状**：官方镜像 `docker.io/library/postgres` 之外，云原生部署的主流已经是
  CloudNativePG（https://github.com/cloudnative-pg/cloudnative-pg ，2026-09 实测 9363★、持续活跃），
  原书 Ch12 也点名它；pgAudit/pgBadger 等生态扩展在 PG17/18 均已跟上（pgbadger：https://github.com/darold/pgbadger ✅）。
- **连接池**：PgBouncer 官方仓库 https://github.com/pgbouncer/pgbouncer （✅ 可达）；2024 起 1.23+ 增加
  `max_prepared_statement_count` 等与服务器端 prepared statement 的兼容改进（转述 ⚠️）。
- **监控面板**：本节"摸清一台服务器"类查询已被 pgwatch 3.x（https://github.com/cybertec-postgresql/pgwatch ，
  886★）模板化；pgwatch2（https://github.com/cybertec-postgresql/pgwatch2 ，1839★）仍在但社区重心已移向 3.x。
