## 核心精讲

### 1. 流复制的三条铁律（Ch12）

1. `wal_level=replica`（逻辑复制要 `logical`）且 `max_replication_slots/max_wal_senders` ≥ 实际+预留；
2. 备库基线必须来自**同一次** basebackup 的 WAL 起点——跨备份拼时间线必翻车；
3. 复制槽钉住 WAL：任何槽废弃 = 主库 `pg_wal` 无上限膨胀（呼应 [06-备份与恢复.md](06-备份与恢复.md) 的坑表）。

文档转述 ⚠️：

```bash
pg_basebackup -h primary -D /data -R -Xs -P -C
# 备库自动写 postgresql.auto.conf: primary_conninfo / primary_slot_name
```

```sql
SELECT application_name, state, sync_state, write_lag, flush_lag, replay_lag
FROM pg_stat_replication;          -- PG10+ 的 lag 列是延迟告警的原料
SELECT * FROM pg_replication_slots; -- 看 wal_status=lost 的槽
```

- **PG16 关键增强（✅ 发行说明）**：可以**直接从备库发布逻辑复制**（standby 作为 publisher）——
  把抽取压力从主库挪走；订阅端**大事务并行应用**、**初始同步二进制格式**（配 `binary` 订阅）。

### 2. 同步复制五档语义（Ch12）

`synchronous_commit` 由弱到强：`off → local → remote_write → remote_flush → remote_apply`。
`remote_apply` 才给"备库可读一致性"，代价是每次提交多一个 RTT——本书反复用 RPO/RTO/RTO 三角解释该权衡。

### 3. 逻辑复制：零停机升级的主干道

```sql
CREATE PUBLICATION pub_all FOR ALL TABLES;
CREATE SUBSCRIPTION sub1 CONNECTION 'host=old dbname=app' PUBLICATION pub_all
  WITH (create_slot=false, enabled=false, connect=false, binary=true, streaming=parallel);
```

- 用途：跨大版本在线迁移（先订阅旧版、追平、切流量）、双向同步（慎用）、部分表同步。
- 限制清单：序列不同步（需手工 `setval`）、DDL 不复制、TRUNCATE 需 PG11+ 且显式开启、无两阶段提交（PG14 起
  2PC 发布支持，转述 ⚠️ 细节）、大初始同步对主库压力（PG16 起可从备库发布缓解）。

### 4. HA：Patroni 与 Kubernetes 路线（Ch12）

| 方案 | 模型 | 关键机制 | 适用 |
| --- | --- | --- | --- |
| Patroni | DCS(etcd/Consul/K8s)+REST API | 基于复制槽+时间线的自动选主 | 裸机/VM 事实标准 |
| repmgr | CLI+监视 | 手动/半自动切换 | 轻量传统部署 |
| CloudNativePG | K8s Operator | 声明式 cluster/instance set，原生备份到 S3 | 云原生（本书正文点名） |

- 反脑裂三件套：仲裁（quorum）、STONITH/旧主自杀、时间线（timeline）单调递增。
- 本书时代（2023）K8s 运行 PG 已是生产选项：CloudNativePG 提供 `pg_basebackup` 式在线扩容副本与
  `backup` CRD（对接对象存储归档），与 Ch11 体系同构。

### 5. 升级：小版本与大版本（Ch12）

- 小版本（16.x→16.y）：修 bug/安全，滚动升级——备库先行，`pg_ctl restart -m fast`，主库最后换；无需 dump。
- 大版本：`pg_upgrade --check` → 跑升级 → `delete_old_cluster.sh`。
  **PG17（✅ 发行说明）**：`pg_upgrade` 保留逻辑复制槽与订阅状态（升级不再断复制链路）；
  **PG18（✅）**：`pg_upgrade` 保留优化器统计。
- 零停机大版本路线：新集群逻辑订阅 → 双写窗口 → 切流量 → 拆旧。16→18 跳版亦走此路。

## 常见坑与判读

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 磁盘被 WAL 吃满 | 废弃/失活复制槽 | 删孤儿槽，监控 `wal_status=unreserved/lost` |
| 切换后应用连错主 | 无 VIP/DNS/代理层 | 上 Patroni 的 REST 端点或 Pgbouncer 动态后端 |
| 逻辑订阅卡住 | 序列/约束不满足、冲突 | `pg_stat_subscription`、订阅表约束预建 |
| pg_upgrade 检查报 incompatible | 旧集群含被弃特性（如 tablespace 布局变化） | 按 `--check` 清单先手工清理 |

## 核心概念速览（中英对照）

- **流复制** — streaming replication：WAL 字节流物理复制，备库只读。
- **逻辑复制** — logical replication：行级发布/订阅，解码 WAL 为变更事件。
- **复制槽** — replication slot：服务端记录发送位点、防 WAL 过早回收。
- **时间线** — timeline：故障切换后分支编号，防旧主回写。
- **同步提交档位** — synchronous_commit levels：remote_apply 给读一致，remote_write 保 RPO=0。
- **发布/订阅** — publication/subscription：逻辑复制的两端对象。
- **备库发布** — publish from standby：PG16 新能力，抽数据不再压主库。
- **故障切换** — failover / 自动选主 — leader election：Patroni/DCS 的核心职责。
- **脑裂** — split-brain：双主共写，靠仲裁+STONITH+时间线防御。
- **小/大版本升级** — minor vs major upgrade：换二进制 vs 数据字典/磁盘格式迁移。
- **pg_upgrade** — 就地大版本升级工具：--check 预演、链路保留（17/18 增强）。
- **CloudNativePG** — K8s Operator：声明式集群、在线复制副本、对象存储备份。

## 最新演进与工业实践

- **PG16（✅ 实抓发行说明）**：备库逻辑发布、大事务并行应用、初始同步 binary 格式；逻辑两阶段提交改进。
- **PG17（✅）**：`pg_createsubscriber`——把**物理备库就地转成逻辑订阅者**（官方发行说明），小版本维护与大版本
  迁移路径合一；`pg_upgrade` 保留逻辑槽/订阅状态。
- **PG18（✅）**：`pg_upgrade` 保留优化器统计；AIO 子系统间接改善备库回放与 vacuum 的 I/O 形态（官方口径为顺扫/
  vacuum 等，备库回放收益属合理外推 ⚠️）。
- **Patroni**（✅ https://github.com/patroni/patroni ，2026-09 实测 8746★、当日仍在提交）：DCS 支持 etcd/Consul/ZooKeeper/
  Kubernetes，配 `pgBackRest` 钩子成"选主+备份"标准组合（社区常见栈：Patroni + HAProxy + PgBouncer + pgBackRest）。
- **repmgr**（✅ https://github.com/EnterpriseDB/repmgr ）适合保守的传统部署；云原生线 CloudNativePG
  （✅ https://github.com/cloudnative-pg/cloudnative-pg ，9363★）2026 年已成 K8s PG 的默认答案，本书"TPA/CloudNativePG"
  食谱的方向被完全验证。
- **大版本升级现状**：18 是当前稳定线、19 已进 beta（postgresql.org 新闻页实抓 ✅ 19-beta-4）；企业普遍以
  "16 → 18" 经 pg_upgrade 或逻辑复制跳版，配合本目录 [06-备份与恢复.md](06-备份与恢复.md) 的演练纪律。
