## 核心精讲

### 1. 一张视图看全活动（Ch8）

文档转述 ⚠️：

```sql
SELECT pid, usename, application_name, state, wait_event_type, wait_event,
       now() - xact_start AS xact_age, left(query, 60) AS q
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND state <> 'idle'
ORDER BY xact_age DESC;
```

- `state`：active/idle/idle in transaction（最危险态，拖住 vacuum 与 WAL）；
  `wait_event_type='Lock'/'IO'/'Client'` 给出"在等什么"的第一手证据。
- 锁等待链定位：`pg_locks` 自连接找 `granted=false` 行的阻塞者——本书与 Ch10 锁食谱共用该查询。

### 2. pg_stat_* 三兄弟与 pg_stat_io（Ch8，✅ PG16 新增 pg_stat_io）

- 累计视图会被重启清零：做趋势要么持久化到采集器（pgwatch/PMAs），要么用 `pg_stat_reset()` 纪律化基线。
- `pg_stat_user_tables.n_dead_tup`、`last_autovacuum`、`autovacuum_count` 是维护决策的三块仪表盘。
- `pg_stat_io`（PG16，✅ 发行说明）按后端类型×IO 操作×对象统计 hits/read/write/dirty/temp——定位"谁在做 IO"第一次可用。
- `pg_stat_statements`：`SELECT` 前需先 `shared_preload_libraries` 并重启；`mean_exec_time` 排序即慢 SQL Top-N。

### 3. 日志到日报的闭环（Ch8）

```text
logging_collector = on; log_destination = 'csvlog'
log_min_duration_statement = 1000     # 秒级以上全记
log_line_prefix = '%m [%p] %q%u@%d '   # 时间/进程/用户/库，pgBadger 解析友好
```

- 慢查询归因口径：`duration` 高但 `rows` 少 → 扫描问题；`shared_blks_read` 高 → IO；`plans`/`calls` 比 → 计划缓存。
- pgBadger 吃 csvlog 出交互式日报，正是 Ch8 食谱"每日汇总报告"的工业对应物。

### 4. autovacuum：从阈值到节奏（Ch9）

触发公式（死元组）：`n_dead_tup > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × 表大小`。

```sql
ALTER TABLE events SET (autovacuum_vacuum_scale_factor = 0.02);   -- 大表用绝对阈值思维
```

- PG16 改进（✅ 发行说明）：autovacuum 更及时响应成本延迟设置变化；`VACUUM ... PROCESS_MAIN=off` 只清 TOAST；
  vacuum 冻结路径性能提升；`BUFFER_USAGE_LIMIT`/`vacuum_buffer_usage_limit` 限制 vacuum 冲刷共享缓冲区的占比。
- 反模式：把 autovacuum 关成"每晚跑批"——高并发表死元组日积月累，膨胀与索引膨胀不可逆。

### 5. 冻结与 wraparound（Ch9）

```sql
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC LIMIT 5;
SELECT relname, age(relfrozenxid) AS xid_age FROM pg_class
WHERE relkind='r' ORDER BY xid_age DESC LIMIT 10;
```

- `autovacuum_freeze_max_age`（默认 2 亿）触发强制 vacuum；手工兜底：`VACUUM (FREEZE, ANALYZE)`。
- 告警链路：日志里 `WARNING: oldest xmin is far in the future` / 备份工具里 `minimum recovery target` 类 xid 报错，
  第一时间查上面两个 age。

### 6. 膨胀与索引维护（Ch9）

- 表膨胀判据：`pgstattuple` 的 `free_percent` 长期 > 30–40% 且 `dead_tuple_percent` 高。
- 回收三选一：autovacuum 调密（慢）、`VACUUM FULL`（锁表、空间翻倍）、`pg_repack`（在线重建，事实标准）。
- `REINDEX INDEX CONCURRENTLY`（PG12+）在线重建索引不挡写；临时表/系统目录索引不适用。
- 冗余索引：同列前缀重复索引与 `idx_scan = 0` 的未用索引，先 `DROP INDEX CONCURRENTLY` 观察再归档。

## 常见坑与判读

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| n_dead_tup 高但 last_autovacuum 是 NULL | 未提交事务钉住 horizon | 找 idle in transaction 会话杀掉 |
| vacuum 跑了表还是大 | 长事务/复制槽保留旧页 | `pg_replication_slots.xmin`；释放废弃槽 |
| 日志文件暴涨 | statement all + 细粒度 | 只记 duration 阈值以上 + 错警级别 |
| pg_stat_statements 计数全 0 | 视图未授权/重启清零 | 授权 + 用监控器做差分 |

## 核心概念速览（中英对照）

- **活动视图** — pg_stat_activity：每后端一行的实时全景。
- **等待事件** — wait_event：Lock/IO/Client/LWLock 四大类，PG 版"在等什么"。
- **IO 统计视图** — pg_stat_io：PG16 新增，按后端×操作×对象细分 IO。
- **语句统计** — pg_stat_statements：需预加载的归一化 SQL 统计扩展。
- **死元组** — dead tuple：MVCC 遗留不可见行，vacuum 的回收对象。
- **冻结点** — relfrozenxid/datfrozenxid：免回卷的页级水位。
- **回卷保护** — anti-wraparound vacuum：接近 xid 极限时的强制清理。
- **表膨胀** — bloat：死元组+长事务钉住旧元组致体量虚高。
- **在线重建** — REINDEX CONCURRENTLY / pg_repack：不锁写的空间回收路径。
- **成本延迟** — cost-based vacuum delay：以睡眠换前台 IO 份额。
- **BUFFER_USAGE_LIMIT** — PG16 vacuum 共享缓冲占用上限，防"清库即换血"。
- **日志采集器** — logging_collector/csvlog：pgBadger 类报表的原料。

## 最新演进与工业实践

- **PG16（✅ 发行说明实抓）**：`pg_stat_io`；vacuum 冻结提速；`BUFFER_USAGE_LIMIT` 与 `vacuum_buffer_usage_limit`；
  `VACUUM PROCESS_MAIN=off` 仅清 TOAST；autovacuum 对延迟参数响应更勤。
- **PG17（✅）**：VACUUM 全新内存管理（峰值内存与碎片大幅下降）；顺序读流式 IO 提速。
- **PG18（✅）**：异步 I/O 子系统（`io_method = worker|io_uring|sync`）使顺扫/位图堆扫/vacuum 的 IO 管道化，
  Linux io_uring 路径收益最明显；B-tree 层级扫描计数等新观测点（详见 https://www.postgresql.org/docs/release/18.0/ ）。
- **开源监控现状（2026-09 实测 GitHub）**：pgwatch 3.x https://github.com/cybertec-postgresql/pgwatch （886★，活跃）
  为 pgwatch2 https://github.com/cybertec-postgresql/pgwatch2 （1839★）的 Go 重写继任；
  Prometheus 路线 postgres_exporter https://github.com/prometheus-community/postgres_exporter （✅ 可达）。
  pgBadger https://github.com/darold/pgbadger （✅ 可达）仍是日志日报标准件。
- **工业实践**：大厂普遍"监控平台 + 自动限流"两条线：autovacuum 密度假设 + 在线回收（pg_repack/逻辑复制重建）替代
  锁表 FULL；复制槽废弃导致的 WAL 堆积是 2024–2026 多起公开事故的共同根因（通识转述 ⚠️）。
