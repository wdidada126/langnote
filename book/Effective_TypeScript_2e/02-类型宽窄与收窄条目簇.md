## 本簇条目地图（⚠️ 凭记忆条旨，非逐字）

- **条旨1**｜分清「拓宽/收窄/断言」三种类型变化：赋值推断会拓宽字面量，断言是单向谎言通道。
- **条旨2**｜用字面量类型精化声明；`as const` 冻结推断宽度（但不冻结值——见 🔧）。
- **条旨3**｜收窄首选判别式联合（`kind` 字段 + `switch`），运行时也是真 JS。
- **条旨4**｜`in`/`instanceof`/类型谓词函数的选型顺位：能结构化判别就不手写谓词 ⚠️。
- **条旨5**｜类型断言 `as` 是最后手段，`!` 非空断言更是；两者都不生成检查。
- **条旨6**｜留意收窄失效位：可变量被闭包捕获、跨函数边界、回调内控制流分析断链 ⚠️。
- **条旨7**｜对象解构/数组解构与收窄的配合（判别式在解构后可丢，`const` 拷贝保收窄）⚠️。

## 跨语言裁决

**裁决1｜TS 的收窄 ≈ Kotlin 智能转换（[../Effective_Kotlin/02-变量与表达式.md](../Effective_Kotlin/02-变量与表达式.md) Item ⚠️13），但失效的代价方向相反。**
EK 教义：smart cast 失效时「改结构而不是硬 cast」。TS 同构——控制流分析、`var`/可变捕获同样断链 ⚠️；
但断裂后的「硬 cast」即 `as`/`!` 在 TS 是**免检通道**而非运行时赌注：Java 的 cast 有 checkcast
兜底（错转抛 ClassCastException 当场定位），TS 的断言把错误**推迟到离谎言最远的解引用点**。
公理落点：Runtime vs Type System 专题推论2「断言=向编译器撒谎，运行时不产生转换不产生检查」。
实测 E8：`const maybe: string | null = null; maybe!.length` → 运行时 TypeError
`Cannot read properties of null (reading 'length')`，exit=1 ✅——`!` 删除后连痕迹都不剩。

**裁决2｜判别式联合的 `kind` 字段 = 把类型信息编码进值（公理推论3），Java/Kotlin 无此必要。**
EJ 时代用类型层次 + `instanceof`（EJ 告诫少用 ⚠️ 推定），因为运行时类型对象真实存在；
TS 里 `instanceof` 只对「真有 class 的 JS 值」有效，接口/别名一律不可探测——所以 TS 规范
把判别式提到选型第一顺位，`in` 探测的也是**属性存在性**而非类型。实测 E5：类型谓词
`x is Dog` 擦除后就是普通布尔函数（`fn.length = 1`，✅），谓词的「可信度」全押在作者实现上。

## 🔧 成对反例

坏味道（断言链 + 把 `as const` 当运行时契约）：
```ts
const cfg = { host: "api", port: 80 } as const;
(cfg as { port: number }).port = 8080;   // 运行时畅通无阻（本会话原样实测）
```
实测 E4：改写成功，`cfg.port === 8080`，`Object.isFrozen(cfg) === false` ✅——
`as const`/`Readonly` 纯类型层，「不可变」要运行时兑现得手写 `Object.freeze`。
修正（收窄正路）：
```ts
type Cfg = { kind: "remote"; host: string; port: number } | { kind: "local" };
function describe(c: Cfg): string {
  switch (c.kind) {                    // 判别式：编译期收窄 + 运行时真分支
    case "remote": return `${c.host}:${c.port}`;
    case "local": return "local";
  }
}
```
