## 本簇条目地图（⚠️ 凭记忆条旨，非逐字）

- **条旨1**｜`strict` 不是一个开关而是一个**家族**：noImplicitAny、strictNullChecks 等各自独立生效，逐项理解再逐项开。
- **条旨2**｜新项目从 strict 全量起步；老项目按「strictNullChecks 优先」顺序增量补课 ⚠️。
- **条旨3**｜避免 `any` 的另一杠杆在配置侧：`noImplicitAny` 让隐式 any 当场红。
- **条旨4**｜理解产码语法与纯类型语法的分界：`enum`/参数属性/装饰器**会生成 JS**，`type/interface/satisfies/as const` 纯擦除（公理档推论4）。
- **条旨5**｜d.ts 声明与实现漂移是第三方库事故位；`skipLibCheck` 是用检查预算换编译速度的决策 ⚠️。
- **条旨6**｜模块解析/`import`/`exports`、ESM-CJS 双轨配置 ⚠️ 2e 应有专条，编号不写死。
- **条旨7**｜tsconfig 也是代码：纳入版本库、CI 里 `tsc --noEmit` 常驻（公理推论1：CI 无 tsc=裸奔）。

## 跨语言裁决

**裁决1｜「配置=安全边界」是 TS 独有的重罪名。**
Java/Kotlin 的编译器入口唯一（javac/gradle-kotlin 插件），类型检查**默认且不可关闭**；
EJ 工程条（⚠️ 本仓无 Effective Java 档）无须谈「怎么让编译器跑起来」。TS 的运行时可以完全绕开
类型层——node 直接 strip-types 跑 `.ts`，校验全押在「你是否另外请出了 tsc」。故簇 01 的
「unknown 更安全」在工程带兑现为：**tsconfig 的 strict 家族选型决定整个代码库的类型预算汇率**。
公理落点：Runtime vs Type System 专题推论1。

**裁决2｜「产码语法边界」由本簇实测钉死——Kotlin `inline/reified` 是逃逸擦除，TS 的逃逸是 enum 类。**
Kotlin 靠内联把类型参数带进运行时（专题档对照表：✅ 列 EK 书档口径）；TS 的对应物是
`enum`/参数属性/装饰器这类**违背纯擦除的产码语法**——也正是擦除工具链的雷区。实测 E1/E2：
`enum Color { Red }` 与 `constructor(private readonly x: number)` 均被 strip-only 模式**拒跑**，
`SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]`（原文分别为 "TypeScript enum is not
supported in strip-only mode" / "TypeScript parameter property is not supported in
strip-only mode"），exit=1 ✅——专题档「strip-types 拒跑 enum 即界碑 ⚠️ 待补实测」**本簇销账**。

## 🔧 成对反例

坏味道（把产码语法当擦除语法，押进 strip-types/新工具链）：
```ts
enum Color { Red, Green }                       // E1 实测：node strip-only 直接 SyntaxError ✅
class P { constructor(private readonly x: number) {} }  // E2 实测：同样拒跑 ✅
```
修正（编码进值，保持纯擦除可迁移面）：
```ts
const Color = { Red: 0, Green: 1 } as const;    // 簇 02 E4 提醒：运行时不冻结，另配 freeze 才硬
type Color = (typeof Color)[keyof typeof Color];
class P { readonly x: number; constructor(x: number) { this.x = x; } }  // 手写等价，处处可擦
```
另：CI 无 `tsc --noEmit` 的仓库＝把全部类型预算记在编辑器红波浪线的口头账上（公理推论1 ⚠️ 书目共识口径）。
