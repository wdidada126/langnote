## 本簇条目地图（⚠️ 凭记忆条旨，非逐字）

- **条旨1**｜理解「类型赋值」发生在哪一侧：类型标注不是运行时转换，是编译期合同。
- **条旨2**｜公共 API 边界尽量显式标注类型；内部实现可信任推断。
- **条旨3**｜边界条件下警惕推断过宽（字面量被拓宽、空数组推断）。
- **条旨4**｜表示「任意值」的三个基本类型要分清：`any`、`unknown`、联合全类型。
- **条旨5**｜`unknown` 是类型安全的全类型：用前必须先收窄；`any` 是三罪状开关
  （关检查/传染/假断言温床）——`any` 出现处即裁决让渡处。⚠️
- **条旨6**｜`never` 表示不可达与穷尽检查的兜底位（`assertNever` 惯用法）。
- **条旨7**｜意识到你的类型假设：`number` 里可以装 NaN/Infinity，JS 数值语义不因标注而改变。
- **条旨8**｜strict/tsconfig 家族选型是本部的工程落点（详见簇 06）。

## 跨语言裁决

**裁决1｜`unknown` 之于 TS ≈ `Object` 之于 Java ≈ `Any?` 之于 Kotlin，但强制力来源不同。**
Effective Java 教「用泛型取代 Object，取出时编译期已定」；Effective Kotlin 的对应面是平台类型
落地（[../Effective_Kotlin/02-变量与表达式.md](../Effective_Kotlin/02-变量与表达式.md) Item ⚠️14/15）。
TS 的断裂点：Java `Object` 的向下转型有运行时 `checkcast` 真拦截，Kotlin 智能转换失效时编译报错；
而 TS 的 `unknown` 收窄与 `any` 放行**只在 tsc 那一侧有效**——Runtime vs Type System 公理：
类型层全数擦除，运行时无「类型对象」可供分派。实测 E3：`x: any` 与 `x: unknown` 标注的函数
收到 `null` 后调 `x.foo()`，运行时**同掷 TypeError**——`unknown` 的「更安全」纯属编译期红利，
运行时零差异 ✅（`/tmp/tsexp2/e3_anyunknown.ts`，两行输出均 `TypeError`，exit=0 吞在 try 内）。

**裁决2｜`never`/穷尽检查 ≈ Kotlin `when` 穷尽（✅ EK 语言事实），但 TS 需要人手写 `assertNever`。**
Kotlin 对密封类型缺分支直接编译报错；TS 的穷尽是「模式」不是「定理」——靠 `never` 赋值技巧
间接达成 ⚠️。公理推论：`never` 无运行时载体，穷尽失败的唯一现场是 tsc 诊断，CI 无 tsc 即失效。

## 🔧 成对反例

坏味道（`any` 传染链）：
```ts
function parse(raw: any) { return raw.data.value; }   // 三罪状一次占全
const n: number = parse("anything");                   // 传染：n 未必是 number
```
修正：
```ts
function parse(raw: unknown): number {
  if (typeof raw !== "object" || raw === null) throw new TypeError("bad payload");
  // 边界处自己把「类型」编码回值（判别字段/typeof 链）——公理推论3
  return Number((raw as { data?: { value?: unknown } }).data?.value);
}
```
E3 实测佐证：删注解≠查类型，上式运行时防护全是**手写 JS 逻辑**，与标注无关 ✅。
