## 核心概念速览（中英对照）

- **对象的内存足迹** — object footprint / `sizeof` 对象：对象=非静态数据成员（+padding+可能的 vptr）的紧凑打包，**不含成员函数**
- **空类的大小** — size of empty class：C++ 里空对象至少 1 字节（保证不同对象不同地址）
- **静态数据成员** — static data member：住在类的作用域、不住在对象里——不参与 sizeof
- **空基类优化** — empty base optimization (EBO)：可为空的基类（或特定位置的空成员）不占对象空间
- **`[[no_unique_address]]`**（C++20）：普通空成员也可 0 字节的合法声明，P0848R3（wg21 实测 302）
- **虚表指针** — vptr：一旦类多态，对象开头多出表指针，64 位下 +8 字节
- **填充** — padding：成员间/尾部为满足对齐要求插入的空隙——sizeof 常大于「成员之和」
- **标准布局** — standard-layout type（C++11）：子对象偏移可预测的那一类布局良民， offsetof/互操作的前提

## 动机：「对象里到底装了什么」是对象模型的第一问

面试高频题「sizeof 一个空类是几？」之所以成立，是因为它一刀切开两种心智模型：
**词法模型**（对象装着它的所有声明）vs **布局模型**（对象只是数据成员的紧凑编码，函数、静态成员
统统在外面）。本书第 2 章用 VS 内存窗口 + sizeof 打这场认知仗；后面 03–06 章全部建立在这个结论上：
对象 = **非静态数据成员序列 + 编译器悄悄插入的隐藏成员（vptr 等）**。

## 机制一：sizeof 实验矩阵 🔧已实测（g++ 15.2 -std=gnu++98 与 gnu++23 输出逐项相同）

```cpp
struct Empty{};                       // 空类
struct A   { char c; int i; char d; }; // 声明序「不友好」
struct AA  { char c; int i; };         // 重排对照
struct B   { int x; Empty e; };        // 空成员在尾部
struct V   { virtual void f(); };      // 只有一个「什么都不放的」虚函数
```

| 表达式 | 实测值 | 解释 |
| --- | --- | --- |
| `sizeof(Empty)` | 1 | C++ 规定对象非零大小（不同实例不同地址）；C 的 `{}` 结构体才允许 0 |
| `sizeof(A)` | 12 | c@0，i@4（对齐 4 把 c 顶开），d@8，尾部补到 4 的倍数 |
| `sizeof(AA)` | 8 | 少一个 char，padding 结构全变——sizeof 不是成员尺寸加法 |
| `sizeof(B)` | 8 | win32 ABI 下尾部空成员仍占 1 再对齐到 8（见「机制三」的 ABI 陷阱） |
| `sizeof(V)` | 8 | **虚函数不声明任何数据，却让对象 +8**：隐藏 vptr |

静态成员对照（🔧已实测）：`struct S{ static int n; int a; static int f(); }` → `sizeof(S)==4`，
与只写 `int a;` 完全一致——静态成员/静态函数全部在场外（`S::n` 是全局变量级别的符号）。
成员函数也一样：01 章的 `nm` 里 `_ZN3BoxIiE4showEv` 是**段里的代码**，不在对象里。
这是「词法模型」的第一记败笔：**对象空间只由（含隐藏的）数据决定**。

## 机制二：vptr 的账怎么算

`V` 的 8 字节不是「每个虚函数 8 字节」——虚函数再多也不加对象大小；
每类一张 vtable 在 `.rdata`（01 章 `_ZTV7Derived` 实测），对象里只多**一个**表指针。
推论：给类加第 1 个虚函数，对象尺寸跳变；加第 100 个虚函数，对象尺寸不动、vtable 变长。
这条曲线形状（阶跃后平坦）是判断「某抽象是否真的引入了多态」的廉价探针——
05 章会看到数据侧同款：加虚函数还可能改变成员偏移的朝向（vptr 抢偏移 0）。

## 机制三：EBO 与 ABI 陷阱 🔧已实测

```cpp
struct First{ Empty e; int x; };  // 空类作首成员：win32 实测 sizeof=8
struct Last { int x; Empty e; };  // 空类作尾成员：实测 sizeof=8
struct NUA  { int x; [[no_unique_address]] Empty e; }; // -std=gnu++23 实测 sizeof=4
```

- 经典 EBO 只在「空**基类**」处是硬收益（`struct D : Empty{ int x; }` 里 Empty 不占地盘）；
  作为**普通成员**时空类通常至少占 1 字节（首尾更保守），所以 First/Last 都没省。
- C++20 `[[no_unique_address]]` 把收益合法化到普通成员：实测 8→4。这是 2020 年教材基本没讲的补位
  （标准库 allocator/handle 打包、`std::tuple` 实现侧收益最大）。
- 同一份代码，**win32(MSVC 风味) 与 ELF(Itanium) 的数字可以不同**：空成员处置是 ABI 条件支持项。
  本表全部标注「实测于 g++ 15.2 win32」；Linux ELF 对照未在本机实测 ⚠️。

## 机制四：sizeof 的第二消费者——数组 stride 与对象身份

- **数组 = sizeof 的重复演奏**：`Empty arr[3]` 实测 `sizeof(arr)==3`、元素步幅 1——空类数组里的对象**真的隔 1 字节**，
  `&arr[0] != &arr[1]` 的身份承诺就是靠这 1 字节的「呼吸孔」兑现的；一旦启用 02 篇机制三的
  `[[no_unique_address]]`/EBO 把某成员压成 0，数组步幅随之改变——序列化与 mmap 场景里这是事故源。
- **跨语言对照锚**：Java/C# 的 `new Empty()` 也非 0（对象头+对齐，通常 8~16B），C（C23 前）的
  空 struct 大小是实现定义——「对象至少 1 字节」是 C++ 独有的**明确**承诺；理解这条差异，
  才知道 FFI 边界上「谁负责补 1 字节」。
- **对象地址稳定性**：成员布局编译期定死 ⇒ `&obj + offsetof` 恒等成立（标准布局类）——
  这是 05 篇 `offsetof` 断言、序列化「按字段读写」全部成立的前提。

## 权衡：1 字节的空类与「占位」哲学

空类占 1 字节看似浪费，换来的是 `&a != &b` 的对象身份承诺；而 EBO 把「基类位置」的 1 字节赎回。
代价：一旦启用 EBO，空基类与首个非空成员**共享地址**，`offsetof` 语义、
「成员地址单调」的直觉要重新核对——这就是标准把「非空成员不得与 EBO 基类同址」写进布局规则的缘由。
工程判断：想 0 字节打包就显式用 `[[no_unique_address]]`/基类化，**别赌 ABI 默认行为**。

## 相邻概念对比

- **C struct vs C++ class 的对象空间**：C 只算字段；C++ 可能偷偷插 vptr——`reinterpret_cast` 互转只对
  标准布局/POD 语境有规则可依（对照 [../C语言接口与实现.md](../C语言接口与实现.md) 的「对象即字节块」）。
- **sizeof 与对齐后的「可用尺寸」**：容器按 sizeof 排兵，缓存行按 alignof 对齐——两本账在 05 章合流。
- **Lippman 的「no_init 模型 vs vptr 模型」**：原典 [../深度探索C++对象模型/01-关于对象.md](../深度探索C++对象模型/01-关于对象.md)
  把「非虚类不付 vptr 账」（vptr 模型）与「一律付」（no_init 模型）作为设计空间对照——本书按 MSVC 现实直接给数。

## 最新演进与工业实践

- **C++11 → 23 的语言层增量**（教材停在 98/11）：
  - 标准布局/ trivial 类体系（C++11，`<type_traits>`）——「对象=字节块」何时合法的标准答案；
  - `[[no_unique_address]]`（C++20，P0848R3）——EBO 从基类特权变成成员的显式选项；
  - `std::bit_cast`（C++20）——合法化「对象字节当别的类型看」的最后兜道；
  - C++23 `std::start_lifetime_as`—— memcpy 出对象后正式「激活」生命期。
- **工业代码对应**：`std::function`/`std::tuple`/allocator-aware 容器实现大量吃 EBO；
  folly `cuda::pinned_vector` 等按 over-aligned 打包对象（衔接 05）。判据：
  「你的空 tag/策略类是成员还是基类」决定 sizeof，review 时可拿本表数字当尺。
