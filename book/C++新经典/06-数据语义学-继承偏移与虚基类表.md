## 核心概念速览（中英对照）

- **子对象顺次拼接** — subobject concatenation：派生类布局 = 各基类子对象 + 自身成员 +（可能的）虚基类区
- **继承偏移** — base offset：基类子对象在派生类里的起点；静态继承编译期常数（04 篇实测 +16），虚继承运行期才知道
- **虚基类** — virtual base class：菱形里保证「同一个」共享基类子对象的声明方式
- **vbase 偏移表项** — vbase offset（Itanium）：对象内存里存的「到我身上各虚基类的距离」，虚基寻址的间接层
- **虚表指针槽（vcall slot）** — vcall offset：虚基类里的虚函数，覆写归属随最终类型而变，表上再挂一层偏移槽 ⚠️ Itanium 口径
- **构造责任上收** — most-derived initializes virtual bases：虚基类构造只由最终派生类发起——中间类初始化列表里的 `B(...)` 被忽略（08 篇有实验）
- **共享与唯一地址** — shared subobject & unique address：全对象内虚基类只一份、且排在非虚部分之后（Itanium 惯例），代价是访问多一跳
- **经典活样本** — the `std::ios` diamond：`ios_base←(ios←istream/ostream)←fstream`，标准库里唯一长期量产的虚继承

## 动机：把 04 篇的「编译期加法」难题恶化成「运行期查表」

静态 MI 里 `p2` 的 +16 是常数，因为 D 的布局在编译期全知。虚继承的诉求恰好相反：
**共享基类 B 的位置必须等「谁是最终派生类」定了才知道**——`V1` 单独实例化时 B 紧跟人后，
放进 `D : V1, V2` 时 B 被挤到最后。布局从「常数」降级为「随最终类型浮动」，
于是对象里必须携带一张「我身上的虚基类各在哪」的偏移表。这就是虚基类一切成本之源。

## 机制一：菱形布局实测——数字与构造秩序 🔧已实测（g++ 15.2 win32，`-std=gnu++23 -O0`）

```cpp
struct B { int x; virtual void f(){} B():x(1){ printf("B ctor\n"); } };
struct V1 : virtual B{ int y; V1():y(2){ printf("V1 ctor\n"); } };
struct V2 : virtual B{ int z; V2():z(3){ printf("V2 ctor\n"); } };
struct D : V1, V2 { int w; };
```

实测输出：

```text
sizeof B=16  V1=32  V2=32  D=48
构造顺序：B ctor → V1 ctor → V2 ctor     // B 最先、由 D 代发
(char*)(B*)&d - (char*)&d = 32           // B 子对象浮在 D 尾部
```

读数：
1. **V1 变胖**（32 vs 静态继承同构体的 16~24）：除了 vptr，还要随身带「到 B 的距离」元数据；
   win32/MSVC 风味实现的具体字段排布与 ELF/Itanium 数字不同 ⚠️（本机未复测 ELF），**结构性结论一致**：
   每个持有虚基的类多一撮隐藏成员。
2. **B@32 在尾**：D 的「自有部分」（V1 区+V2 区）先铺，共享的 B 垫后——正因如此，
   **任何**中间类都不能假定 B 的偏移，寻址必须查对象自带的偏移表：
   `b = this + *(__ptrdiff *)(this - delta + vbase_offset_slot)` 级别的两段间接（Itanium ABI 文档口径 ⚠️）。
3. **构造顺序=B 先行**：V1、V2 的初始化列表即便写了 `B(...)` 也不生效，D 负责（本例用默认构造看不出来；
   带参版本实验放 08 篇同题）。语义学一句话：**虚基类是「全对象唯一公民」，户口落在最终派生类。**

## 机制二：访问成本清单与「值不值」判定

| 操作 | 静态继承 | 虚继承 |
| --- | --- | --- |
| 读 `B::x`（经 V1*/V2*） | `mov [this+off]`，off 编译期 | load vbase-offset 再 `mov`——多一次 dependent load |
| `sizeof` | 编译期常数 | 编译期仍可知（对象自身布局定），但**偏移是运行期数据** |
| 构造 | 各级初始化列表各管各 | 中间级忽略、最终级统管 |
| 指针比较/转换 | 常数调整 | 经偏移表的动态调整 |

所以「只是为了解决二义/共享」而虚继承是双重亏本买卖：既付布局税又付寻址税，还引入构造职责的
反直觉。真正需要它的只有两类场景：**菱形中确实要单一共享实例**（ios 家族；组件聚合根）与
**接口混入体系里的公共状态**（COM 聚合的 C++ 表达；很多框架的 `Object` 基）。工程惯例与 04 篇合流：
**大多数风格指南把虚继承列为默认禁用、特批使用**。

## 机制三：标准库的活体解剖——`fstream` 为什么长成那样

`std::basic_filebuf` 一侧：`istream/ostream` 虚继承 `ios`（实为 `basic_ios<char>` 继承
`ios_base`——精确层级各实现有差异 ⚠️）。收益：`fstream` 里 `cin` 与 `cout` 那两套
格式化状态（`fill/padding/事件`）**只有一份** `ios_base`——一次 `width()` 设置同时作用于读写两侧。
这是「共享」语义正当性的教科书证明，也解释了为什么**只有**流家族用虚继承：
它恰好是「用户会抱怨两份状态」的那种菱形。层级与惯用法展开见
[../C++标准库/09-正则表达式与IO流.md](../C++标准库/09-正则表达式与IO流.md)。

## 机制四：值不值的决策树（工程用法收口）

```text
需要共享一个基类子对象？
├─ 否 → 根本别虚继承：限定名/using（04 篇二义）或组合（成员化）
└─ 是 → 共享的「身份」必须是语言级继承关系吗？
    ├─ 否（只是状态共享）→ shared_ptr/显式引用 + 转发接口
    │      （可测试、可 mock、布局零税；现代默认）
    └─ 是（子对象本身必须是一个 B）→ virtual B，并接受：
           每持有一次 vbase 的类 +偏移元数据；B 成员访问 +1 段 load；
           构造职责上收（最终派生类代发）；抽象类不能直接实例化的连锁约束
```

三个落地判据（复盘用）：① `sizeof` 对比试验——把 `virtual` 去掉重测，差值就是「身份税」的字节数
（本目录实测 D 48 vs 静态菱形同构体显著更小）；② 反汇编里数 B 成员的 load 链（机制一表头）；
③ 检查所有最终派生类是否**都**正确初始化了 B——构造上收意味着**漏网即默认构造**，
这是虚继承 bug 的高发面（08 篇次序规则的推论）。

## 权衡与相邻概念对比

- **虚继承 vs 名字限定（04 篇二义）**：多数「二义」其实只需要限定名或用组合消灭——虚继承解决的是
  *身份唯一性*，从来不是为语法糖开的药方。
- **vbase offset vs thunk（04 篇）**：同为「多一层间接」，thunk 修 this 偏移（代码侧），
  vbase offset 定位子对象（数据侧）；前者编译期可完全消化（MSVC），后者每次访问都在。
- **本书 vs Lippman**：原典用 cfront 的「虚拟表区间+虚拟指针」模型推演（
  [../深度探索C++对象模型/03-Data语意学.md](../深度探索C++对象模型/03-Data语意学.md)），
  与 Itanium 的「对象内偏移表」模型结论同、路径异——两版对照能防止把某代 ABI 当永恒真理。

## 最新演进与工业实践

- **语言层零新特性但口径有微调**：C++11 起 `=delete`/final 让「禁止被虚继承/禁止某构造路径」可表达；
  C++20 聚合初始化允许直接初始化虚基类子对象（`D d{{}, {}, .w=4}` 语法收紧 ⚠️ 细节以标准文本为准）——
  构造职责上收的语法糖更顺了。
- **并发语境的成本再估**：vbase 的 dependent load 打乱编译器对「对象内独立字段可并行读」的推断，
  虚基类上的原子成员更容易成为争用点——`std::atomic` 布局惯例见
  [../C++并发编程实战2/05-Cpp内存模型与原子操作.md](../C++并发编程实战2/05-Cpp内存模型与原子操作.md)。
- **工业现状**：新设计里菱形共享更多用**显式持有**（`shared_ptr<B>` 成员 + 转发）替代虚继承——
  布局税换成一次堆间接与生命周期协商，换来接口可测试性（对照
  [../Effective_Modern_C++/04-智能指针.md](../Effective_Modern_C++/04-智能指针.md) 与
  [../C++20设计模式/05-适配器与桥接.md](../C++20设计模式/05-适配器与桥接.md) 的桥接路线）；
  仍存活的虚继承样本几乎只剩流家族与少数框架基类（COM 聚合走的是 C 层 vtable 协议，非 C++ 语法层）。
- **论文索引**：菱形布局的学术讨论集中在 JVM 接口方法表（itable）查找的同类问题语境，
  与 C++ vbase-offset 属同题不同解——按 04 篇所引 Java devirtualization 研究目录检索即可，
  不冒充 C++ 专门文献 ⚠️。
