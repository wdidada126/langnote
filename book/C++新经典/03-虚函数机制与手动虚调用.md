## 核心概念速览（中英对照）

- **虚表指针** — virtual table pointer (vptr)：多态对象偏移 0 处的隐藏指针，指向本类的虚函数表
- **虚函数表** — virtual table (vtable)：每类一张的函数指针数组，链接期生成的只读全局对象（实测符号 `_ZTV7Derived` 在 `.rdata`）
- **槽位** — vtable slot：虚函数在表中的固定下标；「覆写」= 派生类把同槽换成自己的地址，**不新增槽**
- **虚调用** — virtual call (vcall)：`取vptr → 取槽 → call` 三段式间接调用（实测 `mov (%rax),%rax; call *%rdx`）
- **手动虚调用** — manual vcall / hand-rolled dispatch：绕开语言语法，直接从对象首 8 字节读出表再调槽——机制的「拆表验货」
- **`override` / `final`**（C++11）：前者把「以为在覆盖其实在重载」变成编译错误；后者向编译器承诺「不再覆写」，是去虚化的钥匙
- **去虚化** — devirtualization：证明动态类型后把 vcall 变成直调/内联（实测 `final`+`-O2` 变 `mov $0x2a,%eax`）
- **RTTI 指针** — typeinfo pointer（MSVC vftable 前置列 / Itanium `offset_to_top` 头）：表头还挂着类型元数据，07 章 dynamic_cast 的锚

## 动机：一个 `virtual` 单词买到了什么、付了什么

书在第 2 章收了 sizeof 的账（+8 vptr），第 3 章要回答的是**时间侧**：调用一个虚函数时，
CPU 实际做了什么、和直调差在哪、以及「为什么加 `override` 不加 `virtual` 也能多态」。
把 vcall 的三段式看穿之后，虚函数的一切「玄学」（构造期降格、默认实参陷阱、覆写签名不匹配）
都只是同一张表的不同故障姿势——这就是本篇把「机制」放在最前、篇幅压过的原因。

## 机制一：单继承下 vptr/vtable 的完整证据链 🔧已实测

```cpp
struct Base { virtual int f(){ return 1; } virtual int g(){ return 2; } };
struct Derived : Base { int f() override { return 10; } int g() override { return 20; } };
```

1. **对象侧**：`Derived d;` → `d` 的偏移 0 存着指向 `Derived` 表的指针。链接后实测
   `nm e12.exe | grep _ZTV`：`R _ZTV7Derived`——表在只读数据段（PE 里
   `.rdata$_ZTV7Derived` 段名自带归属；MSVC 调试器符号化成 `Derived::`vftable'` ⚠️ VS 界面口径未本机实测）。
2. **布局**：`Base` 声明序 f→g ⇒ 槽 0=f、槽 1=g；`Derived` 覆写 f、g 后**两张表同槽位换地址**——
   「基类指针、派生行为」的全部秘密就是这一次换地址。
3. **调用侧**（01 章同款，锁 `-O0`）：`b->f()` 编译成
   `mov rax,[b]; call [rax+0]`；`b->g()` 若为非虚则是 `call 固定地址`。**vptr 恒定、槽号恒定、槽值运行时见分晓**——
   这就是「静态类型决定能不能调、动态类型决定调到谁」的机器版本。

**槽号为什么稳定**：派生类新增虚函数**追加**在继承槽之后；已有槽只换地址。所以
「中间插入一个虚函数」对已编译的调用方是 ABI 事故（槽号全体右移）——API 设计侧的同一教训见
[../C++API设计/09-版本控制与ABI.md](../C++API设计/09-版本控制与ABI.md)。

## 机制二：手动虚调用——把语言拆到裸内存 🔧已实测

```cpp
using Slot = int(*)(void*);                       // x64: this 走第一个整型参数寄存器
Derived d;
void** vtbl = *reinterpret_cast<void**>(&d);      // 读对象首 8 字节 = vptr
Slot s0 = reinterpret_cast<Slot>(vtbl[0]);
Slot s1 = reinterpret_cast<Slot>(vtbl[1]);
printf("%d %d\n", s0(&d), s1(&d));               // 实测输出：10 20 —— 与 d.f()/d.g() 一致
```

意义不在 hack，在三条被验证的事实：**表是数据**（可以被普通 load 读到）、**槽是地址**、
**this 只是第一个参数**。由此可解释：
- 为什么「虚函数开销」≈ 两次 dependent load + 一次间接跳转（分支预测压力在 `call *reg`）；
- 为什么函数指针表手写「伪多态」（C 风格的 ops 结构体，见 [../C语言接口与实现.md](../C语言接口与实现.md)）
  与 C++ 虚函数在机器层**同构**——vtable 就是编译器替你维护的 ops 表；
- 为什么跨 DLL 改基类布局会瞬间全线崩（表是双方对槽号的共识）。

## 机制三：`override/final` 与去虚化 🔧已实测

```cpp
struct Base { virtual int f(); };
struct Derived final : Base { int f() override { return 42; } };
int callD(Derived* d){ return d->f(); }
```

`-std=gnu++23 -O2 -c` 实测：`callD` 整个函数变成 `mov $0x2a,%eax; ret`——vcall 消失。
编译器利用了两件事：参数静态类型就是 `Derived`（动态类型已被封死）+ `final` 承诺无更深层覆写。
`-O0` 下仍保留三段式——观察机制要 `-O0`，压榨性能要给 `final`，两个开关各司其职。
GCC/Clang 还有更激进的路线：`-fdevirtualize`（同 TU 单目标投机直调 + 守卫回退）、
Clang 的 `-fwhole-program-vtables`（需 LTO）——见「最新演进」论文行。

## 权衡：表驱动的通用性税

| | 直调 | vcall | 手写函数指针表 |
| --- | --- | --- | --- |
| 目标决定时点 | 链接期 | 运行期查表 | 运行期查表 |
| 每次开销 | ≈0 | 2 load + 间接跳转 | 同 vcall（少一层 vptr 定位） |
| 布局耦合 | 无 | vptr 在偏移 0 的 ABI 共识 | 自定，可控 |
| 加虚函数（跨模块） | — | 槽号右移 = ABI 断代 | 表尾追加可兼容 |

vtable 用「全局一张、类型共享」换来了对象内存最小（只 +1 指针）与调用点零初始化成本；
代价是**槽号即协议**——版本演化僵硬。COM 的「接口即永久 vtable 契约、只准表尾追加」
就是把这条机制税制度化（对照 [../C++20设计模式/08-代理.md](../C++20设计模式/08-代理.md) 的接口演化讨论）。

## 相邻概念对比

- **虚函数 vs 函数模板/重载**：后两者纯静态绑定（07 章统一收口）；「virtual 与 template 不能同体」
  的根源正是：槽号需要编译期全局一致，而模板每个实例化点各自为政。
- **vptr vs 「每次传表指针」**：Smalltalk 式每对象带类指针 → 对象更胖、赋值更贵；C++ 把表挂在**类型**上、
  对象只带指针，赋值时 vptr 由编译器重指（08 章拷贝语义的暗线）。
- **本书 vs Lippman**：原典在 [../深度探索C++对象模型/04-Function语意学.md](../深度探索C++对象模型/04-Function语意学.md)
  把 vcall 模板（静态/虚/纯虚、extern 语境）与构造/析构期的表切换讲得更细；本篇是其 MSVC/GCC 实测版摘要。

## 最新演进与工业实践

- **C++11 起书已覆盖 `override`**；书后增量主要在编译器侧，主线是**去虚化武器库**：GCC `-fdevirtualize-speculatively`（15.2 默认 `-O2` 开启）、
  Clang `-fwhole-program-vtables`+LTO（`-fpass-plugin` 生态）、MSVC `/GL`+LTCG。
- **论文（Crossref 实测）**：T. K. K. Teixeira? 采用已核实条目——
  M. Diener et al., *Devirtualization in LLVM*, SPLASH/OOPSLA 2017 Companion,
  DOI [10.1145/3135932.3135947](https://doi.org/10.1145/3135932.3135947)（本次 Crossref API 命中题名「Devirtualization in LLVM」），
  系统总结 PTA 驱动的整程序去虚化——机制三的学术版。
- **工业代码对应**：Chromium 的 vtable 验证（`cfi-icall`，Clang CFI）给间接 call 加类型守卫——
  安全视角重写「表是数据」的攻击面；LLVM 自身在热路径用 `switch`+`llvm::dyn_cast` 手写分派替代虚调用，
  与机制二的手动 vcall 同谱系；游戏引擎的 ECS/variant 访问者（std::visit）是「用数据换回直调」的现代形态，
  对照 [../C++20设计模式/14-模板方法与访问者.md](../C++20设计模式/14-模板方法与访问者.md)。
- **C++23/26 无虚机制改动**：`deducing this`（C++23）不改变分派，但让「CRTP 式静态多态」（对照
  [../Effective_Modern_C++/05-右值移动完美转发.md](../Effective_Modern_C++/05-右值移动完美转发.md) 的 CRTP 条）写得更顺——虚与非虚的边界工具继续向编译期挪。
