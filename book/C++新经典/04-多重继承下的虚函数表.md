## 核心概念速览（中英对照）

- **多重继承** — multiple inheritance (MI)：一个类直接继承两个以上基类，对象内并排多个基类子对象
- **主基类/首子对象** — primary base / first subobject：占偏移 0、与派生类共享首 vptr 的那个基类
- **次 vptr** — secondary vptr：非首基类子对象自带的表指针——多态对象从「一个 vptr」变成「一串」
- **指针调整** — pointer adjustment：向上转型到非首基类时，`static_cast` 编译期给 this 加常数偏移（实测 +16）
- **thunk** — thunk：Itanium ABI 中 vtable 槽指向的桩：先调整 this 再跳真身（MSVC 不用 thunk，改用**每表同槽放已调整地址** ⚠️ 文档口径）
- **名字歧义** — ambiguous name lookup：两个基类各有一个 `f` 时，`d.f()` 编译失败，需限定或 using 声明
- **接口-实现分离的 MI 用法** — interface mixins / pure interfaces：只继承无数据纯虚类的「安全 MI 子集」（Java/C# 接口的 C++ 原型）

## 动机：单继承的「一个 vptr」神话在哪碎裂

03 章模型（对象头一个 vptr、一张表）是**单继承特例**。一旦 MI，问题立刻具体化：
`S2* p = &d;` 之后 `p->f()` 要调到 `D::f`——可是 `p` 指着的子对象在偏移 16，
若首 vptr 仍指向 `D` 的大表，`D::f` 收到的 this 却是**错位的**。MI 章的全部机制
（多 vptr、槽内换地址、thunk）都在修补这一个矛盾：**一份实现，多个 this 视角**。

## 机制一：MI 布局与指针调整 🔧已实测

```cpp
struct S1{ virtual ~S1(){} int a; };
struct S2{ virtual ~S2(){} int b; };
struct D : S1, S2 { int c; };
```

实测（g++ 15.2 win32，`-std=gnu++23 -O0`）：

```text
sizeof S1=16  S2=16  D=32
(char*)p1-(char*)&d = 0     // S1* 视角：原位
(char*)p2-(char*)&d = 16    // S2* 视角：指针被 +16 —— 「调整」发生在转换，不在调用
```

要点：
1. **布局=子对象顺次拼接**：`D` 内 S1@0（vptr+a+pad）、S2@16（vptr+b+pad）、c@32 后。
   每个带虚函数的基类子对象各带一个 vptr（次 vptr）。
2. **向上转型是代码不是数据**：`S2* p=&d;` 编译成 `lea rax,[d+16]`——静态可算，零运行时查表。
3. **每基类一张表，同一逻辑函数在不同表里槽地址不同**：`D` 的 S1 表里放 `D::f` 本体
   （this 天然对）；S2 表里放「先 -16 再跳 `D::f`」的处理版本——GCC/Itanium 用 thunk 桩实现，
   MSVC 直接生成一份调整过的入口地址 ⚠️（ABI 差异，本机未逐家复测）。
4. **代价清单**：对象变大（32 vs 单继承的 16）、每多一个多态基类多 8 字节 vptr、
   构造要装多个表指针、析构经 `p1->~S1()` 也能正确走到 `D` 的析构（实测可运行；调整发生在上行转换）。

## 机制二：歧义与名字查找——MI 的编译期面

```cpp
struct B1{ void f(); }; struct B2{ void f(); };
struct D2 : B1, B2 { };
// D2 d; d.f();        // ❌ 编译错误：request for member 'f' is ambiguous
D2 d; d.B1::f();       // ✅ 限定名
struct Fix : B1, B2 { using B1::f; };  // ✅ 声明「取 B1 版」，歧义消解即分辨率选择
```

机制：名字查找在派生类作用域并列铺开所有基类作用域，**平局即错**（不是重载决议——两者不同层，
参见 07 章「静态面」）。工程含义：MI 的重名冲突是**静默演化事故**——某个基类新加一个名字，
可能让所有同时继承它的派生类集体编译失败。这也是「优先组合、慎用 MI」教条的形式化理由之一。

## 机制三：一个函数体，两张表——覆写的「一式两份」🔧已实测

```cpp
struct S1{ virtual void vf(){ printf("S1::vf\n"); } int a; };
struct S2{ virtual void vf(){ printf("S2::vf\n"); } int b; };
struct D : S1, S2 { void vf(){ printf("D::vf\n"); } int c; };  // 只写了一份 vf
```

实测：`p1->vf(); p2->vf();` 输出两行 `D::vf`——**一个实现体被登记进两张表**（S1 表与 S2 表
各占一槽）。这暴露 MI 的语义空白：S1 与 S2 各自声明了 `vf`，D 的一份 `vf` 同时覆写**两个**
互不相干的虚接口；如果两个基类语义本不同，「一覆双得」就是隐患。标准给的解法：

- **命名介入（virtual inheritance + 纯虚）**：让菱形汇聚到共享基（06 篇的账）；
- **显式限定调用**：`d.S1::vf()` 走静态通道，绕开表；
- **工程侧**：多数风格指南直接禁止「多基类同名虚函数」——机制空白无法靠语法缝合。

观察法：`objdump -d e4_mi2.exe | grep -c 'call   \*'` 实测间接 call 计数 37（含 CRT/异常路径），
其中两次属于 `p1/p2->vf`——想精确定位就 `-O0` 单 TU 编译 `.o` 再反汇编（01 篇方法卡的用法）。

## 权衡：什么时候 MI 是对的

| 场景 | 判定 | 理由 |
| --- | --- | --- |
| 多「纯接口」混合（无数据、全纯虚） | ✅ 常用 | 每接口一张表、实现侧集中；Java/C# 接口即此 |
| 接口 + 实现基类混用 | ⚠️ 三思 | 主基类规则（只有一个基类能占「共享 vptr」名额）开始生效，布局耦合加重 |
| 菱形（共享基类） | ❌→06 篇 | 不用 virtual 继承会复制两份基类子对象；用了则见虚基类账 |
| 只是想要代码复用 | ❌ | 组合/CRTP/`std::variant` 访问者的现代替代，见下「最新演进」 |

Lippman 原典的「主基类」概念（[../深度探索C++对象模型/03-Data语意学.md](../深度探索C++对象模型/03-Data语意学.md) §子对象拼装）
指出：只有**第一个**无虚函数的基类能把自己的 vptr 让给派生类共享；MI 里一旦多个基类多态，
「共享」不存在、全副武装各自带表——正是机制一测出的形态。

## 相邻概念对比

- **MI vs 接口实现（COM/JNI）**：外部接口的 vtable 都被规定成「单一继承链的表」——COM 的每个
  interface 独立单继承自 IUnknown，**禁止接口间 MI**，就是为了绕开本篇的复杂度；
  对照 [../C++20设计模式/08-代理.md](../C++20设计模式/08-代理.md) 与 03 篇的「槽号即协议」。
- **MI vs `std::tuple` 式打包**：把「多基类」换成「多成员 + EBO」，this 错位问题消失（02 篇 EBO），
  泛型库（如 Boost.Hana、策略类打包）近年整体朝这一侧迁移。
- **调整发生在转换 vs 发生在调用**：MSVC/Itanium 都选「转换时调整 +（Itanium）调用时 thunk」的组合；
  没有「运行时找偏移」的查表——那是虚基类才需要的东西（06 篇）。

## 最新演进与工业实践

- **语言层**：C++11→23 对 MI 布局**零改动**——这是本篇数字十年不过时的原因；改动都在周边：
  C++11 的 `=delete` 可显式关掉不想要的基类接口、C++17 折叠表达式让「多 mixin」模板化更顺。
- **工业现状**：Google C++ Style 明确限制 MI（只许「无状态接口类 + 至多一个具体基类」）；
  Qt 的旧式「`QObject` + 其他具体类」MI 写法在新代码中多被组合 + d-pointer 取代 ⚠️（趋势性描述，未逐版核实）；
  Windows ATL/WTL、COM 及 `windows-rs` 的 C++ 投影仍在量产使用「多纯接口 MI」——它们的 vtable
  布局合规就是本篇模型。开源侧的通用 review 手法：用 sizeof 反推 vptr 个数，即可发现「意外多态化」。
- **延伸阅读**：thunk 与 vcall 模板的 ABI 级展开在
  [../深度探索C++对象模型/08-专题-现代编译器视角Itanium与MSVC.md](../深度探索C++对象模型/08-专题-现代编译器视角Itanium与MSVC.md)；
  Java 侧对照研究（invokeinterface 的 itable 查找 vs C++ 槽号直取）：DOI
  [10.1145/354222.353191](https://doi.org/10.1145/354222.353191)（*A study of devirtualization techniques for a Java
  Just-In-Time compiler*，Crossref 实测命中题名——注意其语境是 JVM，非 C++）。
