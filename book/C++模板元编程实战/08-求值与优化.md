# 第 8 章 求值与优化——表达式树的执行机器与全书收口

> 原书第 8 章（P233–259）与后记。
> 目录口径见 [../C++模板元编程实战.md](../C++模板元编程实战.md)。总览见 [00-总览与阅读地图.md](00-总览与阅读地图.md)。

前七章把"模型"编译成了类型；本章处理最后一块拼图：**表达式树到底何时、
在哪、算几次**。MetaNN 的求值子系统（`evaluate/` 目录，实测含 eval_plan/eval_pool/
eval_handle/eval_buffer/eval_group/eval_unit 六个设施工件）把"注册-计划-缓冲-句柄"
拆开，在其上叠三级优化：避免重复计算（缓存）、同类计算合并（OperSeq）、
多运算协同优化（§8.3.3）。本章也是全书"元编程×编译期计算"叙事的技术终点。

## 核心概念速览（中英对照）

- **运算的层次结构** — operation hierarchy：表达式套表达式形成的树，求值须自底向上（§8.1.1）
- **求值注册** — evaluation registration：表达式对象经 `EvalRegister` 把自身挂进求值体系（第 5 章接口）
- **求值计划** — eval plan（实测 `eval_plan.h`）：为一次求值生成的执行安排，可复用
- **求值缓冲/句柄** — eval buffer / eval handle：结果存放处与轻量引用；handle 可判"已求值"
- **求值池** — eval pool（实测 `cpu/trival_eval_pool.h`）：按类型回收/复用中间缓冲区
- **求值组** — eval group：同型求值的批量归组（同类合并的执行端）
- **避免重复计算** — common subexpression reuse：结构相等的表达式共享已算结果（§8.3.1，靠第 5 章 `operator==`）
- **同类计算合并** — same-kind merging：同标签不同操作数的运算合为一组内核调用（§8.3.2）
- **多运算协同优化** — multi-operation cooperation：跨表达式的全局安排（§8.3.3，全书最复杂小节）
- **主体/非主体类型求值** — primary vs non-primary eval path：数据类自带求值接口 vs 表达式类走注册（§8.2）
- **自动微分（前向模式）** — forward-mode AD / dual numbers：对偶数算术携带导数的求导法（本节实测复现，作为对照系）

## 动机：ET 的账单要在求值端付清

表达式模板把计算推迟，就必然有一个"兑现时刻"。天真兑现（赋值点递归算树）
浪费了静态架构的全部红利：同一子表达式在正向/反向里出现两次就重算两遍、
五个同型 sigmoid 调五遍内核、缓冲区随用随弃。MetaNN 的答案是**把求值本身
也当作可编译期安排的图问题**：类型层已知表达式结构（OperSeq/标签比较），
那么"何时算、算几次、放哪里"也能在类型层安排。这正是全书主题的最终陈述——
**模板技术贯穿一个真实框架的每一个子系统**。

## 机制精讲

### 8.1 求值模型与模块划分

§8.1.2 的模块图（对照实测文件）：`EvalUnit`（一次求值的执行体，CPU 特化，
第 5 章 sigmoid 里见过）、`EvalHandle<T>`（引用某个将算/已算的 T）、
`EvalBuffer`（handle 背后的存储+已算标志）、`EvalPlan`（把"注册过的表达式"
编成可执行计划）、`EvalPool`（设备侧资源池，trival_eval_pool=CPU 平凡实现）、
`EvalGroup`（归组器）。注册链在 `operators/operators.h`（实测）可见：`UnaryOp::EvalRegister`
检查 `m_evalBuf.IsEvaluated()`，未算则沿 `OperSeq_<TOpTag>` 序列取表头，
`THead::template EvalRegister<TTail>(m_evalBuf, m_data)` ——**编译期算子序列
驱动运行期注册顺序**，第 1 章"递归即循环"的最后一次、也是最华丽的一次出场。

### 8.2 基本求值逻辑

- **主体类型**（数据类）：自带求值接口——它已"在内存里"，注册即命中缓冲（§8.2.1）。
- **非主体基本类型**（ZeroMatrix 等特殊矩阵）：不占存储，求值=按形状生成（§8.2.2）。
- **运算模板**：走注册链（§8.2.3）；**DynamicData 与求值**（§8.2.4）是异步接口
  的落地点——`DynamicData.Get()` 触发 plan 执行、返回已物化引用。
  第 6 章"编译期↔运行期关口"在这里装上了收费闸机。

### 8.3 三级优化（机制转述）

1. **避免重复计算**（§8.3.1）：表达式对象可 `==`（第 5 章），命中缓冲=直接取 handle。
   反向传播大量复用正向激活，收益最大的正是训练场景。
2. **同类计算合并**（§8.3.2）：OperSeq 把同标签运算串成序列，注册期归入同一
   EvalGroup，一次内核遍历处理多组操作数（批量化"调用"而非批量化"数据"）。
3. **多运算协同优化**（§8.3.3）：跨表达式的全局重排/融合，书中篇幅最大、
   机制最重；⚠️ 本笔记未获得足以逐行复述的公开实现摘要，此处按节题与
   代码骨架（eval_plan 接口）转述其意图：**在类型层可见的全图信息上做类似
   编译器的调度优化**。读者以原书为准。

## 权衡

求值子系统自身有成本：注册/句柄/计划对**一次性小计算**是净亏（比 eager 更慢）；
复杂度也最集中（§8.3.3 的元函数是全库最难读部分）。作者的取舍是：MetaNN 面向
反复训练迭代的场景，摊销成立。这与 CPU 分支预测、JIT 的"warm-up 税"同属一个论证结构。

## 相邻概念对比

- MetaNN 求值 vs Eigen 的"赋值即求值"：Eigen 不做全局计划，融合只到单表达式止；
  MetaNN 把优化半径扩到跨表达式（类型层全图可见是其本钱）。
- EvalPool 缓冲复用 vs PyTorch caching allocator：同为"按尺寸/类型回收显存/内存"，
  一个服务表达式中间量，一个服务张量生命周期——问题同构，层次不同。
- 编译期求值调度 vs CUDA Graph：CUDA Graph 录制内核序列重放，MetaNN 用类型推导
  生成计划——都是"把决定从运行期拿走"，一个靠观察，一个靠静态类型。

## 最新演进与工业实践

- **🔧 已实测 g++ 15.2 的编译期自动微分对照实验**（`-std=gnu++23`，对偶数 Dual）：

```cpp
// 🔧 核心片段（已实测 g++ 15.2；完整程序含泰勒级数版 sin/exp）
template <class T> struct Dual {
  T v, d;                                            // (值, 对选定变量的导数)
  constexpr Dual operator*(const Dual& o) const
      { return {v*o.v, v*o.d + d*o.v}; }             // 乘积法则内置
  friend constexpr Dual exp(const Dual& x)
      { auto e = constexpr_exp(x.v); return {e, x.d*e}; };  // 链式法则内置
};
constexpr auto s = sigmoid<double>(Dual<double>{2.0, 1.0});
static_assert(s.v > 0.88 && s.v < 0.89);             // sigmoid(2)≈0.8808
static_assert(s.d > 0.10 && s.d < 0.11);             // sigmoid'(2)≈0.1050 —— 编译期断言通过
```

  实测输出：`sigmoid(2)=0.880797, sigmoid'(2)=0.104994`；
  `g(x)=sin(3x-1)+x²` 在 `x=0.5` 处 `g'=3.632748`，**导数值经 `static_assert` 在编译期断言成立**，
  与中心差分数值解 3.632748 一致。链式法则内嵌进每个 `constexpr` 重载——
  这就是"前向模式 AD 可以完全发生在编译期"的最小证据；MetaNN 反向模式导数
  （`SigmoidDerivative` 等手写运算）若能如此由编译期生成，可免去手写伴随。
  注意：libstdc++ 15 尚无 constexpr `<cmath>`（P1383 属 C++26，[wg21.link/P1383](https://wg21.link/P1383)
  实测 302），示例自带泰勒级数版 sin/exp——这是"现代演进"反哺书中技法的实例。
- **源到源 AD（Enzyme，[github.com/EnzymeAD/Enzyme](https://github.com/EnzymeAD/Enzyme) 实测存在）**
  与 **trace+函数变换（JAX `jax.grad/jax.vjp`）**是 2026 年消除"手写导数运算"的两条工业路线；
  Baydin 综述（第 3 章引文口径）四分类里，MetaNN 停在"operator overload + 手工伴随"，
  演进方向由这两家代表。
- **P2300 std::execution**（[wg21.link/P2300](https://wg21.link/P2300)，实测 302，
  已进 C++26）：sender/receiver 的"连接即建图、start 才执行"与 EvalRegister/plan 模型
  同构；若今天重写 MetaNN 求值端，P2300 就是现成的调度协议——本书的异步求值可读作其雏形。
- **torch.compile 的 Inductor**做 kernel fusion（点态合并）+ CSE（公共子表达式消除）——
  §8.3.1/8.3.2 的工业同名物；差别仅在 MetaNN 在模板实例化期完成、Inductor 在 JIT 编译期完成。
- **折叠/if constexpr 对求值端的影响有限**：本章瓶颈在"计划与缓存"，属架构不属语法；
  C++23 `if consteval`（P1938，实测 302）倒是允许同一函数在编译期/运行期走两条求值路——
  概念上是 EvalPlan"两世界分派"的语言化回响。⚠️ 仅作类比，非原书内容。
