# 第 5 章 运算与表达式模板——全书技术心脏

> 原书第 5 章（P119–147）。目录口径见 [../C++模板元编程实战.md](../C++模板元编程实战.md)。
> 总览见 [00-总览与阅读地图.md](00-总览与阅读地图.md)。

**表达式模板（expression templates, ET）是本书标题里"元编程实战"的最大单体**：
`A + B * C` 不再产生两个 N×N 临时矩阵，而是构造一个**类型即表达式树**的对象，
求值被推迟到赋值边界、且第 8 章还要求值子系统对它做融合与缓存。
本章同时展示 MetaNN 的运算框架：类别标签×变参萃取×特化分派的三件套。

## 核心概念速览（中英对照）

- **表达式模板** — expression templates (ET)：用模板参数递归编码运算树、把求值推迟给上下文的惯用法（Veldhuizen，C++ Report 1995 提出，谱系见下）
- **延迟求值** — lazy evaluation：表达式只建树不计算，物化发生在求值/赋值点
- **临时对象消除** — temporary elision：ET 的第一动机，省掉中间 N×N 存储与多次内存遍历
- **运算标签** — operator tags：`UnaryOpTags::Sigmoid`、`BinaryOpTags::Add` 等空类（实测 `operators/facilities/tags.h`）
- **运算类别** — operation category：按参数元数分类一元/二元/三元（§5.3），标签命名空间三组
- **OperOrganizer** — 运算组织者：按运算类别特化的基类，负责维度一致性检查（实测 `facilities/organizer.h`）
- **OperCateCal** — 类别推算元函数：由运算标签+操作数类型推算**结果**属于哪个 CategoryTags（实测 `category_cal.h`）
- **OperSeq** — 运算序列：为求值注册的优化把"同类运算"排成序列（实测 `oper_seq.h`，第 8 章主用）
- **EvalRegister** — 求值注册：表达式对象把自身登记进求值缓冲，返回 handle（实测 `operators/operators.h`）
- **折叠运算** — collapse（§5.6.4）：沿某维归约（求和类），矩阵→向量的降维算子
- **插值** — interpolate：三元运算示例，按系数混合两个矩阵（§5.7.3）

## 动机：naive 运算符重载的三重浪费

矩阵库最朴素的 `Matrix operator+(const Matrix&, const Matrix&)` 在 `A+B+C` 上：
造临时矩阵 T1（分配 N² 个 double + 写一遍）、算 A+B（读两遍写一遍）、再算 T1+C
（读两遍写一遍）——5 次 N² 内存遍历 + 1 次分配。矩阵运算的时间几乎全是**内存带宽**
（arithmetic intensity 低），临时物化的代价直接体现在墙钟上。ET 的解法：
`operator+` 返回的不是 Matrix 而是 `Expr<Add, Matrix, Matrix>`——一个**只含引用/子表达式**
的轻量类型；`A+(B+C)` 最终得到嵌套三层的表达式类型，一次遍历逐元素算完。
→ 这就是第 1 章"类型即数据"的完全体：**表达式树长在类型里**。

## 机制精讲

### 5.1–5.2 ET 与 MetaNN 的运算模板设计

§5.1 是 ET 通史简介（Veldhuizen 1995 → Blitz++ → Eigen 谱系）；§5.2 的"Add 模板的问题"是本章
最有教学价值的小节：朴素地为每个运算写一个自由函数+类，会立刻遇到——
参数可以是**任何数据类型**（Matrix/Batch/表达式/特殊矩阵），结果类别要**推算**
（标量×标量=标量，矩阵×矩阵逐元素=矩阵），维度要**校验**。
MetaNN 的答案是把"每个运算"拆成三样东西：**运算标签（身份）+ 特征萃取（traits）
+ 框架类模板（UnaryOp/BinaryOp）**。

### 5.4 五个辅助模板（框架的五根柱子）

实测源码可对应（`MetaNN/operators/facilities/`）：

| 书中名（§5.4） | 文件 | 机制 |
| --- | --- | --- |
| `OperElementType_`/`OperDeviceType_` | traits.h | 从操作数类型萃取元素类型/设备，决定结果"护照" |
| `OperXXX_` 系列 | traits.h | 各种运算侧特征的小元函数集合 |
| `OperCateCal` | category_cal.h | 运算标签+操作数类别 → 结果类别（查表式特化） |
| `OperOrganizer` | organizer.h | 按结果类别特化：Matrix 版存 RowNum/ColNum 并 assert SameDim |
| `OperSeq` | oper_seq.h | 给每类运算挂"可合并序列"，供第 8 章同类计算合并 |

`OperOrganizer` 的 SameDim 是变参递归（第 1 章循环技巧的实战），三元运算自动获得
三维检查——**检查逻辑写一次，元数与类别组合全免费**。

### 5.5–5.6 框架与实现示例

`UnaryOp` 的骨架（据实测 `operators/operators.h` 转述）：

```cpp
// 🔧 机制转述（结构取自公开仓库 operators/operators.h，做了删减）
template <typename TOpTag, typename TData>
class UnaryOp : public OperOrganizer<TOpTag, OperCateCal<TOpTag, TData>> {
public:
    using ElementType = typename OperElementType_<TOpTag, TData>::type;
    using DeviceType  = typename OperDeviceType_<TOpTag, TData>::type;
    bool operator==(const UnaryOp& v) const { return m_data == v.m_data; } // 结构相等！
    auto EvalRegister() const { /* 经 OperSeq_ 链把自身注册进求值缓冲 */ }
};
```

注意两个细节：①`operator==` 让表达式对象可**比较结构相等**——第 8 章"避免重复计算"
的缓存命中判断靠它；②`EvalRegister` 沿 `OperSeq_<TOpTag>::type` 序列头尾展开
（`SeqHead/SeqTail`），这是"运算注册求值"的统一入口。一个具体运算（§5.6.1 Sigmoid）
= 标签 + 一个偏特化类声明 + `EvalUnit` 里按 CategoryTags×DeviceTags 的求值实现
（实测 `sigmoid.h` 的 EvalUnit 特化直接 `LowerAccess` 拿裸指针循环——运算核心零抽象开销）。
§5.6.2 Add（二元）、§5.6.3 转置（改视图不改数据）、§5.6.4 折叠（降维）各展示一类难点。

## 权衡（§5.8"折衷与局限性"——原书最清醒的两页）

- 表达式对象含**引用**：`auto e = A + B;` 悬垂风险（临时数被表达式引用）——ET 的经典脚枪，
  Eigen 文档专章警告，MetaNN 也不例外 ⚠️（原书措辞未逐字核对，问题本身属机制固有）。
- 建树改变**求值语义**：赋值前不计算、地址取模可能变慢（对象里有内嵌子表达式）。
- 编译期成本：每棵表达式树都是类型，模板实例数量与表达式复杂度成正比。
- **与"运算多态"的冲突**：无法把 `A+B` 与 `f(A,B)` 塞进同一虚接口（类型各异且非多态）。

## 相邻概念对比

- **ET vs 代理模板（proxy-based）**：fmt 从 ET 路线转向代理模板（`format_string` 编译期
  解析 + 运行期值代理），换取可读错误与模块化编译——同一"延迟"动机、两种载荷策略。
- **ET vs `std::mdspan` 的 layout mapping**：mdspan 延迟的是**索引映射**不是算术，
  它声明式、可组合、不建树，专治"形状/步长"这一维——与 ET 互补而非竞争。
- 与 [../C++模板元编程/09-DSEL与表达式模板.md](../C++模板元编程/09-DSEL与表达式模板.md)（Abrahams 史前 MPL 的 ET 章）对读：那章给语法考古，本章给工业动机（带宽）与工程框架（五柱子）。

## 最新演进与工业实践

- **🔧 已实测 g++ 15.2 的迷你 ET 计时**（`-std=gnu++23 -O2`，1024×1024 double，`A+B*C`，
  5 次迭代取墙钟，仓库外临时目录）：
  - eager（每次运算物化临时矩阵）：**30.2 ms / 29.2 ms**（两轮）
  - ET（建 `BinExpr<Add,MatView,BinExpr<Mul,…>>` 树一次求值）：**15.5 ms / 20.3 ms**（两轮）
  - 结果一致（maxdiff=0）。**约 1.5–1.9× 加速**，与"少一趟内存遍历+省一次 N² 分配"
  的账吻合；差距没到数量级是因为 eager 版被返回值优化/移动救回一些，且现代 O3 对
  朴素循环也有向量化。测不出数量级差距也是结论：**ET 的收益是带宽账，不是算法魔法**。
- **Eigen** 至今以 ET 为引擎（`CwiseBinaryOp` 树）并配表达式级访问者；其官方文档的
  "Expression templates" 与 "Lazy evaluation" 两章是本章最好的现代伴读 ⚠️（URL 本次未实测）。
- **Blaze/xtensor/xsimd**（xtensor、xsimd 仓库实测存在）：xtensor 用 ET+广播 traits，
  xtensor/xsimd 把 SIMD 宽度编进类型——与"设备标签"同一思路的向量化维度延伸。
- **std::execution 视角**：`EvalRegister` 是"把计算登记给调度器"的 2018 手写版，
  与 P2300 sender/receiver（[P2300](https://wg21.link/P2300)，实测 302）的
  "描述即延迟、订阅才执行"语义同构——可作为给面试官讲 ET 的现代翻译。
- **编译器自动微分对照**：MetaNN 每个运算手写着 `XxxDerivative`（实测 tags 表里的
  `SigmoidDerivative/TanhDerivative`），Enzyme 一类源到源 AD 用 IR 变换自动生成——
  手工伴随是 ET 路线的成本，编译器求导是后来者的红利（第 3 章已铺）。
