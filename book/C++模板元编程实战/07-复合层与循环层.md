# 第 7 章 复合层与循环层——编译期拓扑与递归网络

> 原书第 7 章（P185–232），全书分量最重的实现章。目录口径见 [../C++模板元编程实战.md](../C++模板元编程实战.md)。
> 总览见 [00-总览与阅读地图.md](00-总览与阅读地图.md)。

复合层=**用类型写出来的计算图**：`LinearLayer` 的全部结构知识——两个子层、
三条连接——以模板参数的形态固化在 `ComposeTopology` 里（实测源码见下），
拓扑排序、子层实例化、policy 继承修正全在编译期完成；循环层 RecurrentLayer
则在这套静态骨架上加入"跨时间步共享一组子层"的 RNN 语义，以 GRU 为例落地。

## 核心概念速览（中英对照）

- **复合层** — composite layer：持有一组子层并按描述连接的层（层模式的层版）
- **结构描述语法** — topology description：`SubLayer<名,实现>` + `In/OutConnect` 谓词的模板 DSL（§7.1.2）
- **子层标签** — sublayer tag（`Sublayerof<LinearLayer>::Weight`）：以宿主层参数化的嵌套空类，保证唯一命名
- **内部连接** — InternalConnect：子层输出→另一子层输入的边；InConnect/OutConnect 连边界
- **ComposeTopology** — 拓扑编译单元：合法性检查+拓扑排序+子层类型表（§7.3）
- **拓扑排序** — topological sort：给 DAG 定执行序；书中用 Kahn 式"反复取零入度"的递归元函数实现
- **实例化爆炸防护**：§1.3.4 警告在本章兑现——拓扑元函数若逐步复制长列表会爆编译
- **ComposeKernel** — 复合内核：按拓扑结果驱动正向/反向的执行机器（§7.4）
- **梯度收集** — gradient gathering：复合层把输出端梯度按连接路由回各子层（§7.4.6）
- **policy 继承与修正** — policy inheritance/change：外层策略默认下沉、按子层覆写（`change_policy.h` 实测）
- **GRU** — gated recurrent unit：门控循环单元（Chung et al. 2014 论证其与 LSTM 等效更简）
- **循环层** — recurrent layer：沿时间步复用同一组子层参数（§7.6.2）

## 动机：手写一个 5 层 MLP 会有多少胶水

第 6 章的层各自为战。拼 `input→Weight→Bias→Sigmoid→output` 若手工做：
每层构造参数、正向调用序、反向**逆序**调用序、梯度在分叉点的汇聚、policy 下发……
全是 O(层数²) 的琐碎且机械的代码。机械=可自动生成=**可以用类型表达**。
作者的方案：把网络结构写成**模板参数的偏序理论问题**，编译期解出执行序——
运行期不再有"图遍历"，只有按编译期序表的顺序调用。

## 机制精讲

### 7.1 结构描述 DSL（实测语法）

`LinearLayer` 的真实定义（实测仓库 `layers/compose/linear_layer.h`，删注释）：

```cpp
// 🔧 摘自 MetaNN-book 分支（2019，Makefile 可编译），语法与书中 §7.1 一致
template <> struct Sublayerof<LinearLayer> { struct Weight; struct Bias; };
using Topology = ComposeTopology<
    SubLayer<WeightSublayer, WeightLayer>,      // 子层声明：标签+实现类型
    SubLayer<BiasSublayer,  BiasLayer>,
    InConnect<LayerIO, WeightSublayer, LayerIO>,               // 外输入→Weight
    InternalConnect<WeightSublayer, LayerIO, BiasSublayer, LayerIO>, // Weight→Bias
    OutConnect<BiasSublayer, LayerIO, LayerIO>>;               // Bias→外输出
template <typename TPolicies>
class LinearLayer : public ComposeKernel<LayerIO, LayerIO, TPolicies, Topology> { ... };
```

要点：①连接谓词描述的是**端口对端口**（子层的 I/O 都是第 6 章 LayerIO 通用结构）；
②子层标签从 `Sublayerof<宿主>` 取，不同宿主的同名子层也是不同类型（可无限嵌套复合层）；
③构造时 `.template Set<WeightSublayer>(name, in, out)` 用异类词典风格的具名参数
装配子层——第 2 章技术第三次兑现。

### 7.2 policy 继承与修正

外层 `TPolicies` 默认对全部子层生效（继承，§7.2.1）；`Change_Policy<子层标签, 新策略, 容器>`
式元函数（实测 `policies/change_policy.h`）为特定子层替换策略（§7.2.2），
Select_Policy 按标签命中。机制与第 2 章 PolicySelector 同源，只是查找键从"策略特征"
换成"子层标签"——**policy 系统即字典系统的第二次复用**。

### 7.3 ComposeTopology：五步编译期流水线

§7.3.3–7.3.7 的步骤（机制转述；实现细节按公开仓库可核部分写）：

1. **子句分类**：把 `ComposeTopology<Args...>` 的变参拆成 SubLayer 表与连接表（模式匹配）。
2. **合法性检查**：每个子层可达、无重复定义——失败表现为特化缺失的编译错误，
   **结构错在编译期死**正是全章卖点。
3. **拓扑排序**：递归元函数反复找"零入度"节点移入结果表；实现刻意避免
   "每步复制整个剩余表"的朴素写法（实例化爆炸防线，第 1 章警告的工程化）。
4. **子层实例化元函数**：按排序后的标签序列生成子层的成员类型表。
5. 输出给 ComposeKernel 的仅是**类型级的序表**——运行期零解析。

### 7.4–7.6 ComposeKernel 与循环层

ComposeKernel（§7.4）持有子层 tuple（按标签索引），正向=按拓扑序逐个调子层正向
（§7.4.5），反向=**逆拓扑序**收集梯度（§7.4.6 的梯度收集与分叉汇聚）。
§7.5 给出完整复合层示例（MLP 级）。循环层部分（§7.6）：GRUStep 本身是复合层
（输入门/重置门/候选的 Linear+Sigmoid/Tanh 拓扑，实测 `recurrent/gru_step.h`），
RecurrentLayer 把同一 GRUStep 沿时间展开复用，外部喂 Array 批序列（实测
`recurrent/recurrent_layer.h`，测试目录有 `test_gru.h/test_gru_2.h`）。

## 权衡

- **编译期图的代价**：改结构=重编译；一次实例化的模板深度（拓扑排序+子层展开）
  让编译时间随层数增长——作者明说这类框架适合"结构相对固定、求性能/求静态保证"的场景。
- **嵌套深度与编译器上限**：百层网络会把递归元函数推到 `-ftemplate-depth` 边缘；
  MetaNN 未解决（研究原型），工业静态图方案（如早期 CNTK 的 ComputeDevice 或
  ONNX 编译栈）改用"IR+外部编译器"绕开。
- **对比运行期图**：torch 的 `nn.Sequential` 一行等价，但每个 forward 都遍历模块列表。

## 相邻概念对比

- 结构描述 DSL vs [../C++20设计模式/](../C++20设计模式/) 的组合模式：同构（Composite），差别在 MetaNN 的连接是**被编译期检查的偏序公理**而非运行期指针。
- 拓扑排序元函数 vs Boost.Graph 的 `topological_sort`：一个是类型层的递归实例化，一个是运行期 BFS——算法同名，成本模型完全不同。
- GRUStep/RecurrentLayer vs cuDNN 融合 GRU kernel：静态路线把展开编译进类型，运行期路线把展开压进定制 kernel；殊途同"消除 Python 层循环"。

## 最新演进与工业实践

- **"编译期已知全图"的当代主流化**：`torch.compile`（TorchDynamo 字节码捕获→
  AOTAutograd 导出**前向+反向整图**→Inductor 生成代码，pytorch 仓库实测存在）说明
  "反向传播顺序在编译期决定"不再需要手写模板——tracer/编译器接管了 ComposeTopology 的工作。
  MetaNN 的路线在 2018 年是少数派，今天的表述是 "graph capture + grad mode"。
- **ONNX/静态图 IR**：ONNX 的 GraphProto 用 protobuf（运行期）承载第 7 章用类型承载的
  信息，再交给 ONNX Runtime/TensorRT 编译——证明两种载荷（类型 vs IR）都能做合法性检查与拓扑排序，
  区别在错误发现的时点与工具链生态。⚠️ ONNX 规范细节本次未逐文核对。
- **constexpr 解析器的新中间态**：现代 C++（如 nanobind/Eigen 的编译期字符串解析、
  fmt 的 `format_string`）展示"在 constexpr 函数里解析描述文本"的第三条路：
  既非模板元编程组合子句，也非运行期图——**constexpr 解释器**做拓扑检查，
  错误信息可控（if consteval [P1938](https://wg21.link/P1938)，实测 302，C++23）。
- **GRU 的当下**：GRU 未变，变的是序列建模主角（Transformer）；用本书框架语言表达，
  Attention 需要"三元运算+掩码广播"，MetaNN 的 Interpolate 型三元框架可扩展到它——
  这是留给读者的思维练习（本笔记观点，非原书内容）。
