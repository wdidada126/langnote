## 1. 一句话模型：血缘是 DAG，查询是可达性

血缘图 `G=(V, E)`：顶点=资产（表/列/作业/看板/策略），边=变换或依赖（`src → dst` 读作
"dst 依赖于 src"）。于是目录里的全部血缘产品面都化归为图查询：

| 产品话术 | 图论语义 |
|---|---|
| 下游影响分析（改这列谁会坏） | 正向可达集 + 到每个点的距离（爆炸半径/跳数） |
| 上游溯源（这数从哪来） | 反向可达集 |
| 血缘路径展示 | 两点间任意/最短路径 |
| 断链检测 | 弱连通分量分析、悬空边 |
| 循环告警（不该有） | 环检测（DAG 违例） |

## 2. 🔧 演示：11 条边上的递归 CTE 可达性

建 11 条边的玩具血缘（2 源系统 → staging → 数仓 → mart → BI/ML + 一条策略文档边），用
SQL 标准递归 CTE（✅ 语法依据 https://www.sqlite.org/lang_with.html curl 200）做带环保护的遍历：

```sql
WITH RECURSIVE reach(node, depth, path) AS (
  SELECT :seed, 0, :seed
  UNION ALL
  SELECT e.dst, r.depth+1, r.path || ' > ' || e.dst
  FROM edge e JOIN reach r ON e.src = r.node
  WHERE instr(r.path, e.dst) = 0            -- 路径防环：走过就不再走
)
SELECT MIN(depth), node FROM reach GROUP BY node ORDER BY depth, node;
```

**本机实测输出（SQLite 3.45.3，一次运行）**：

```text
impact of crm_source:
 (0,crm_source) (1,stg_customers) (1,stg_orders) (2,dw_dim_customer) (2,dw_fact_orders)
 (3,mart_customer_360) (3,mart_finance_recon) (4,bi_cohort_dashboard) (4,ml_churn_model)
reachable(excl seed): 8   max depth: 4   elapsed ≈ 289µs
upstream of bi_cohort_dashboard:
 {bi_cohort_dashboard, crm_source, dw_dim_customer, dw_fact_orders, erp_source,
  gdpr_policy, mart_customer_360, stg_customers, stg_orders}
exactly-2-hop downstream of dw_fact_orders: {bi_cohort_dashboard, ml_churn_model}
```

读数（全部可从输出复核）：
- `crm_source` 变更 → 8 个下游资产在爆炸半径内，最深 4 跳；**同一 seed 的正/反向查询是同一
  段 SQL 翻转 JOIN 方向**（`e.src=r.node` ↔ `e.dst=r.node`）——产品里两个按钮、内核里一行代码。
- `upstream(bi_cohort_dashboard)` 把 `erp_source`（经 stg_orders 两跳）和 `gdpr_policy`（策略文档
  边，`WHERE` 子句之外的"治理血缘"）一并捞出：演示了"血缘图混装多类边"时可达性照样工作，
  但**产品必须按边类型过滤展示**，否则看板会被政策文档吓到（演示作者注 ⚠️ 观点）。
- `depth=2` 的"恰好两跳"过滤 = 影响分级（P0 直接消费方 / P1 间接 / P2 远端）的最小机制。
- 289µs/11 边无性能含义；有含义的是**复杂度形态**：可达性 O(|E|) 级、路径枚举可指数爆炸——
  这就是各产品血缘 API 只给"半径 N"而不给"全路径列表"的原因（⚠️ 转述的普遍限制与此对齐）。

**类比边界声明**：真实目录的血缘是**带版本、带时间窗、带权限**的图（边有 observed_at/effective
区间，点有 ACL），纯 SQL 可达性演示刻意省略这三轴；跨引擎分布式遍历（如按层拉取+客户端合并）
的工程问题亦不在演示范围。

## 3. 表级/列级/作业级：血缘的三种粒度（⚠️ 转述 + 学术线 ✅）

- **表级**：OpenLineage 事件的 `inputs/outputs` 天然给出（✅ 规范 https://openlineage.io/docs/ ）；
  成本最低、信息量也最低——"fact_orders 依赖 stg_orders"救不了改列事故。
- **列级**：需要引擎内表达式追踪（Spark facet）或 SQL 解析器。学术侧 2025 仍有新系统：
  LineageX（ICDE 2025，✅ DOI 10.1109/icde65448.2025.00363 过 Crossref 200）、
  SQL 血缘抽取综述（✅ DOI 10.63345/jqst.v2i1.170 过 Crossref 200）——UDF/动态 SQL/聚合是
  三大断头点（⚠️ 两文献共识转述）。
- **作业级（job-centric）**：把"任务"也画成节点（`表 → 作业 → 表`），权限与 SLA 挂在作业上；
  DataHub 的血缘 UI 即此形态（⚠️ 转述；仓库 ✅ https://github.com/datahub-project/datahub ）。

## 4. 血缘的生命周期：边是观测出来的，会过期

- 边带 `last_observed_at`：三个月没人跑过的"血缘边"应降权/淡显——**血缘是频率图不是拓扑图**
  （重构观点 ⚠️，与运营元数据合流的自然推论）。
- 多源冲突：解析器说 A→B、事件说 A→C，谁当真？工程惯例：观测>解析>人工登记逐层覆盖（⚠️ 转述）。
- 删除同步：源端作业下线后边的清算（对读 `03`§2 tombstone 论点）。

## 5. 影响分析的产品化：从图算法到通知链

真实事故流（⚠️ 转述的行业通用剧本）：schema 变更 → 目录查正向可达集（半径 3）→ 按
所有者聚合 → 变更事件推给下游 owner（Slack/邮件/webhook）→ 下游确认或阻断。目录在这里的
角色是**路由表**：图给出"该通知谁"，主动元数据（`07`）给出"何时自动做"。没有血缘图时这一串
全靠人肉转发群消息——这是目录 ROI 论证里最硬的一条（原书立场无法核实 ⚠️，论点本身公开可见）。

## 核心概念速览（中英对照）

- **数据血缘** — Data Lineage：资产间变换/依赖关系的历史记录；图模型下即有向（理应无环）图。
- **可达性分析** — Reachability：影响=正向可达集、溯源=反向可达集；血缘产品面的数学公分母（🔧 演示核心）。
- **递归 CTE** — Recursive CTE：`WITH RECURSIVE` 不动点迭代写图遍历，SQL 标准武器（✅ sqlite.org/lang_with.html）。
- **路径防环** — Cycle Guard：`instr(path, dst)=0` 沿路径去重，兼容脏数据成环时的遍历终止。
- **爆炸半径** — Blast Radius：变更后受影响下游集合及其跳数分布，变更分级依据（🔧 8 资产/深 4 跳）。
- **列级血缘** — Column-Level Lineage：表达式粒度的边映射，UDF/动态 SQL 处易断头（✅ ICDE 2025 线）。
- **作业中心视图** — Job-Centric Lineage：`表→作业→表` 三段边，权限与 SLA 的挂载点。
- **频率图** — Frequency-Weighted Graph：边带 last_observed/热度，血缘展示按活跃度淡化的形态。
- **证据优先级** — Observation > Parse > Manual：多源血缘冲突时的覆盖次序（⚠️ 工程惯例）。
- **影响通知路由** — Impact Routing：可达集→按 owner 聚合→推送，目录作为事故流的路由表。
- **策略边** — Governance Edge：合规文档→资产的非变换边，与血缘同图存放、按类型过滤展示。
