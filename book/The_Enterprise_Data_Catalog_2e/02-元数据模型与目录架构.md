## 1. 实体模型：目录的"表结构"

任何目录的核心数据结构都退化为三元组式的图：

```
(Entity, Aspect, Value)      例：(dw.fact_orders,  "ownership", {owner: "team-billing"})
(Relationship, Type, Entity) 例：(stg_orders, "upstream_of", dw.fact_orders)
```

- **实体 urn 命名**：`urn:li:dataset:(urn:li:dataPlatform:snowflake,db.schema.tbl,PROD)` 形态
  （DataHub 模型，⚠️ 转述其开源文档口径）——平台+环境+路径三段式，解决"同名不同源"。
- **切面（aspect）模型**：实体的每类元数据是独立可版本化的切面（schema、ownership、stats、
  glossaryTerms…），增量更新互不干扰。对读 [../湖仓架构大规模数据平台的设计和实现/04-数据目录.md](../湖仓架构大规模数据平台的设计和实现/04-数据目录.md)
  （✅ 盘上）的"元数据分面"论述。
- **关系即边**：血缘/术语/文档链接全部是图中的边，因此"一个实体页"= 一次邻域查询的物化。
  这条设计使 `05` 章的可达性演示成为目录内核的自然推论。
- OpenMetadata 的取舍（⚠️ 转述；仓库 ✅ https://github.com/open-metadata/OpenMetadata curl 200）：
  少图多 JSON 列、类型化实体优先——两条路线（通用图 vs 类型化文档）之争相当于
  数据库界"关系 vs 文档"的目录版重演（对照 [../Database_Internals/00-总览与阅读地图.md](../Database_Internals/00-总览与阅读地图.md) ✅ 盘上）。

## 2. 四层参考架构

| 层 | 职责 | 典型选型 | 坑（⚠️ 工程转述） |
|---|---|---|---|
| ① 采集 Ingestion | pull 扫描 / push 事件 | 调度器+连接器；OpenLineage/WHL 事件 | 全量重扫打爆源库 information_schema |
| ② 存储 Store | 实体/切面/边的持久化 | MySQL/PG + ES +（图或边表） | 把 ES 当唯一真相源（文档型检索不可回灌） |
| ③ 索引 Index | 倒排+向量+facet | Elasticsearch/OpenSearch | 元数据高频变更下的索引风暴 |
| ④ 服务 API/UI | 检索、实体页、血缘 DAG、策略钩子 | GraphQL/REST + React | 无批量血缘接口 → 前端 N+1 遍历 |

四层分离的用意：**每层可独立替换**（⚠️ 该书立场的可核实旁证：DataHub 2021–2022 把存储从
ElasticSearch+MySQL 演进到 Kafka-as-database 的 MSE（Metrics/Stream Envelope），四层结构未动，
⚠️ 转述；仓库 ✅ https://github.com/datahub-project/datahub curl 200）。

## 3. Pull（扫描）vs Push（上报）：采集拓扑的根本分野

- **Pull**：目录定时 `DESCRIBE`/`information_schema` 全量拉。优点零侵入；缺点只有 schema、
  无"何时被谁怎么用"，且对源库有扫描税。
- **Push**：执行引擎在执行现场发事件（运行完成、输入输出集、列映射）。OpenLineage 规范是
  当下事实标准（✅ 文档实查 https://openlineage.io/docs/ curl 200）：`RunEvent{run, job,
  inputs[], outputs[], provenance}` 的 JSON 信封，Spark/Airflow/dbt 有官方集成（⚠️ 各集成
  成熟度转述）。
- **判据**：技术 schema 可 pull；血缘/使用画像**必须** push（pull 侧解析 SQL 只能得近似，
  见 `05`/`03`）。混合式（pull 兜底 + push 增强 + 冲突时 push 优先）是 2024–2026 的主流形态（⚠️ 转述）。

## 4. 元数据的"新鲜度"与版本化

- 元数据本身是有 TTL 的缓存：表随时被 alter/drop，目录页面上的 schema 与真实仓库之间的
  偏差（metadata drift）决定信任度——**给每条切面带上采集时间戳并显示**是最低成本信任建设（⚠️ 实践口径）。
- 切面级版本化 → 元数据的时间旅行（"上周三这张表的描述是什么"），支撑审计与回滚。
  这一需求与湖仓表格式的快照语义同构（对照 [../Apache_Iceberg活用入門/02-元数据三层结构.md](../Apache_Iceberg活用入門/02-元数据三层结构.md) ✅ 盘上——
  表级元数据树的三件套：metadata 文件→快照→manifest）。

## 5. 身份（identity）：目录里最难的一厘米

同一张物理表在「HMS 名 / Iceberg 全限定名 / dbt unique_id / BI 数据源别名 / S3 路径」里有五张脸。
**实体消歧（entity resolution）做得好坏，直接决定血缘图是连通图还是一堆碎片**（⚠️ 工程转述，
各家目录 issue 区的长期高频主题）。可核实的收敛方向：以 Iceberg REST Catalog（✅ 协议文档
https://iceberg.apache.org/docs/latest/ curl 200）的 `namespace.table` 为跨引擎锚点，其余名字
映射为别名切面——这是"catalog 协议升格为身份源"的路线，Polaris/Lakehouse 一代产品都走这条
（机制章：`06` + [../Apache_Iceberg活用入門/07-Catalog生态.md](../Apache_Iceberg活用入門/07-Catalog生态.md)）。

## 6. 一个反面教材：数据字典时代的模型错误（⚠️ 重构性讨论）

2000 年代元数据库（含 Inmon 式仓库元数据库）常见的失败模式：把元数据建模成**自由文本登记表**
（备注列装下一切），无法机器消费 → 治理政策落不了地。CIF 线的反思对读
[../Building_the_Data_Warehouse/12-高级话题与企业信息工厂.md](../Building_the_Data_Warehouse/12-高级话题与企业信息工厂.md)（✅ 盘上）。
目录时代的教训同构：**字段化、类型化、可 API 化**是元数据能被治理的前提；
「先有可查询的模型，后有可执行的治理」。

## 6b. 模型质量四指标（架构验收面，⚠️ 重构方法论）

1. **完备（completeness）**：核心资产是否五件套齐（名/描述/owner/schema/血缘边）？
   按实体域统计，不按全局均值（均值会被长尾灌水表稀释）。
2. **新鲜（freshness）**：切面 `observed_at` 的分布 P95 是否小于源系统变更周期？
3. **稳定（stability）**：源端改名/迁移时实体 ID 不变率——ID 一改，全部历史切面与边变孤儿，
   这是检验 `urn` 设计成熟度的唯一硬题。
4. **可扩（extensibility）**：新增一类实体（如"指标"）需要改内核还是只加注册表？
   DataHub 的 entity registry 与 OpenMetadata 的 schema 化实体是两条答案（⚠️ 转述，仓库
   存在性 ✅ 见 00§9 URL 表）。

四指标同时是 `07` 里"主动元数据"可自动化的前提：不可度量的模型谈不上触发策略。

## 7. 建模练习：给"指标"建一个实体（本章小结演示）

指标（metric）是最常被拒绝进目录的公民：它没有物理存储。正确姿势（⚠️ 转述口径，与 dbt
semantic layer 等公开模型一致）：指标=（定义切面：表达式/维度/过滤）+（血缘边：指标→上游数据集）
+（消费边：指标→看板）。指标入图后，"改一列影响哪些指标"与"改一表影响哪些看板"变成同一种
可达性查询（`05` 演示直接复用）。

## 核心概念速览（中英对照）

- **实体/切面模型** — Entity-Aspect Model：资产为实体、每类元数据为可独立版本化的切面（DataHub 系范式）。
- **URN** — Uniform Resource Name：资产全局唯一名，平台+环境+路径三段式，消歧第一道防线。
- **四层架构** — Four-plane Architecture：采集/存储/索引/服务的可替换分层，目录产品的通用骨架。
- **pull vs push 采集** — Scan vs Event Reporting：schema 可扫描、血缘与使用必须上报的分野判据。
- **OpenLineage** — OpenLineage：以 RunEvent JSON 信封为标准的事实血缘事件规范（openlineage.io ✅）。
- **元数据漂移** — Metadata Drift：目录内容与真实仓库的偏差；靠新鲜度戳与增量事件压制。
- **实体消歧** — Entity Resolution：同一物理资产多源异名的合并，决定血缘图的连通性。
- **元数据时间旅行** — Metadata Versioning：切面级历史保留，支撑审计回滚；与 Iceberg 快照语义同构。
- **图 vs 文档路线** — Graph vs Typed-document：目录内核的两条存储路线，对应泛关系/文档数据库之争。
- **指标实体化** — Metrics as First-class Assets：把无存储的指标以定义+边入图，使影响分析统一。
- **自由文本字典** — Free-text Dictionary：反模式原型；不可查询的元数据等于不可治理的元数据。

## 最新演进与工业实践

- **实体模型的标准化尝试（2022–2026）**：DataHub 的 Entity Registry（用户自定义实体类型）、
  OpenMetadata 的 entity schema（JSON Schema 化）、以及开放目录联盟推的互认模型（⚠️ 转述，
  未获可 200 一手页）三股力，方向都是"别锁死在 dataset+dashboard 十几种类型上"。
  仓库均已实查 ✅：https://github.com/datahub-project/datahub 、https://github.com/open-metadata/OpenMetadata 。
- **Iceberg REST Catalog 成为"机器面目录协议"赢家（2024–2026）**：Nessie/Polaris/Lakekeeper/Unity
  的 REST 端点相继兼容该协议（✅ 协议文档 https://iceberg.apache.org/docs/latest/ curl 200；
  https://projectnessie.org/ curl 200；Polaris 仓库 curl 200）。身份锚点之争（§5）实质是
  "谁当 REST 服务端"之争。
- **元数据后端的轻量化**：小团队 2024–2026 实践出现"PG + pgvector + 物化视图"替代
  ES+图库的极简目录栈（⚠️ 转述自社区部署帖；本目录 `04` 的 🔧 演示即此类思路的玩具版）。
- **引擎侧对位**：DuckDB 直接 ATTACH 外部 catalog（含 Iceberg REST）做"查询即元数据消费"
  （✅ 实测记录在盘 [../DuckDB_Up_and_Running/09-云端DuckDB与MotherDuck.md](../DuckDB_Up_and_Running/09-云端DuckDB与MotherDuck.md)，
  其 iceberg 扩展"可装不可查"的口径沿用），提示四层里的"服务层"未必需要独立进程。
