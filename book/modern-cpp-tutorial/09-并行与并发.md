## 一、动机：多线程从系统 API 升格为语言设施

C++98 时代 C++ 标准对"线程"零感知，跨平台多线程 = pthread/Win32 两套 API 各写一遍。C++11 借 LLVM/Boost 的提案底稿把线程模型一次性写进语言与标准库：`std::thread` 管生死、`std::mutex` 管临界区、`std::future` 管结果回传、`std::condition_variable` 管会合、`std::atomic` 与六种内存顺序管无锁世界的契约。原书第 7 章是全book篇幅最长、密度最高的一章：7.1–7.4 是"设施巡礼"，7.5 是"语义地基"——前四节的每个 API 都建立在内存模型之上，也正因此 7.5 开头的 `volatile` 假安全例是全书最重要的反例。

## 二、机制：五层设施逐个拆

**§7.1 并行基础**：`std::thread t(fn, args...)` 构造即启动（没有"先建后跑"状态机）；`join()` 等死、`detach()` 放飞（放飞后所有按引用捕获的栈对象即刻悬垂——原书示例特意用 `std::map` 演示线程参数**按值拷贝**进新线程，想传引用必须 `std::ref`，这是 C++ 线程 API 最反直觉的一处）。`std::this_thread::yield()`、`hardware_concurrency()` 提供调度与拓扑信息。

**§7.2 互斥量与临界区**：`std::mutex` 三操作 `lock/unlock/try_lock`；裸用配对极易失衡（异常路径），RAII 包装两级——`std::lock_guard`（构造锁析构放，无灵活度）与 `std::unique_lock`（可延迟上锁 `defer_lock`、可手动 `lock/unlock`、可转移所有权，是条件变量的唯一合法搭档）。双锁死锁的标准解法：`std::lock(m1, m2)` 一次锁俩（内部避免循环等待）+ `std::adopt_lock` 交给两个 guard 接管；C++17 的 `std::scoped_lock` 把这招打包成一个对象。原书还点了 `recursive_mutex`（"能不用就不用"的同类）。

**§7.3 期物**：`std::future` 是一次结果的异步信箱——`get()` 阻塞取（且只能取一次），`valid()`/`wait()` 辅助。三条产线：`std::promise`（手动 set_value，可跨线程转交）、`std::packaged_task`（把可调用对象包成任务，执行即填 future——原书用它演示与线程池的接口）、`std::async`（最省事的发射-收取）。`std::future` 析构的坑：`std::async(launch::async, ...)` 返回的 future 析构会**阻塞等任务结束**，"发射后不管"要手动转存。

**§7.4 条件变量**：生产者-消费者完整例（原书给出 `std::queue`+`condition_variable` 的 30 行骨架）。铁律三条：等待必须配 `unique_lock`；必须用**谓词版** `cv.wait(lk, pred)` 挡虚假唤醒（spurious wakeup）与竞态窗口；`notify` 前后 predicate 的修改要么在锁内要么对原子可见。`wait_for` 加超时防死等。

**§7.5 原子操作与内存模型**：开场反例——`volatile int flag` 双线程读 a 写 a：`volatile` 只禁编译器优化，**不建立线程间 happens-before**，`b` 的输出不可预判，是数据竞争 UB。随后 `std::atomic`：`load/store/exchange/fetch_add/compare_exchange_*`；`is_lock_free()` 探测是否真无锁。一致性模型：顺序一致性（seq_cst 默认，"像有一个全局时钟"）最贵；削弱版四档 relaxed/release-acquire/acquire-release/consume（原书按"释放-获取模型/释放-消费模型"讲依赖链例子：`memory_order_consume` 保护数据依赖，release-store + consume-load 才能安全解引用指针链）。`compare_exchange_weak` 允许虚假失败（某些 LL/SC 平台），strong 不虚假但可能在循环里更亏。

### 🔧 实测 a：atomic 计数与"假锁免费"探测（g++ 15.2，`-std=c++11 -pthread`）

```cpp
std::atomic<int> counter{0};
std::thread t1([&] { counter.fetch_add(1); });
std::thread t2([&] { counter++; counter += 1; });
t1.join(); t2.join();
struct A { float x; int y; long long z; };   // 16 字节聚合
std::atomic<A> a;
```

已实测 g++ 15.2：输出

```text
counter = 3
atomic<A>.is_lock_free = false, sizeof(A) = 16, alignof(A) = 8
```

两次递增+一次 fetch_add 精确等于 3——原子性实锤。第二行同时打脸"atomic 一定无锁"：16 字节聚合在本机 x86-64 上退化为内部自旋锁实现。链接期实测必须 `-pthread` 且 **`-latomic` 要放在源文件之后**（MinGW 链接顺序敏感，否则 `undefined reference to __atomic_is_lock_free`）。

### 🔧 实测 b：volatile 假安全（预期：能编译能跑，但答案是 UB）

```cpp
int a = 0; volatile int flag = 0;
std::thread t1([&] { while (flag != 1); std::printf("b = %d\n", a); });
std::thread t2([&] { a = 5; flag = 1; });
```

已实测 g++ 15.2 编译运行"正常"（本机常输出 `b = 5`）——这恰是原书要警示的：**能跑出对的答案的 UB 才是毒最深的 UB**；换 -O2、换 ARM 弱内存序平台、换编译器版本，`b = 0` 或永久挂起都合法。原书该例的正确修复正是 `std::atomic` + release/acquire。

## 三、权衡与陷阱

- `std::thread` 析构时既未 join 也未 detach → `std::terminate()`。RAII 包装（自写 join_guard 或 C++20 `std::jthread`）是工程必选项——原书写作用户时代还没有 jthread。
- 条件变量+bool 手写 = 每次都要重新发明；C++20 的 `latch/barrier/semaphore` 把三大同步模式降为 API（见下文演进）。
- 内存顺序的工业现实：99% 代码用默认 seq_cst 或"发布用 release/读取用 acquire"两板斧；relaxed 只属于引用计数增减这类"无同步意图的原子记账"。原书把 consume 讲得很美，但**实践中 consume 已被证明无法高效实现**——社区最终在 C++26 删除它（见演进节），读时要把例子里的 consume 直接替换成 acquire。
- 双锁 `std::lock` 方案 vs 锁序纪律：前者免疫死锁但多一次全局协商；高频路径还是"固定加锁顺序 + scoped_lock"为主。
- 原书两处文字勘误（2026-06 仍未修）：7.5 开头 "**有限**考虑 compare_exchange_weak" 应为"优先"；"削弱原子操作在**进程间**的同步条件"等三处"进程间"应为"线程间"（std::atomic 同步的是线程）。引用时须自行更正（见 00 勘误台账）。

## 四、与相邻概念对比

| 设施 | 解决什么 | 什么时候不够 |
|---|---|---|
| mutex+guard | 临界区互斥 | 需要"等条件"时（配 cv） |
| unique_lock | 可延迟/可转移的锁 | 不可复制（转移走语义即弃锁） |
| condition_variable | 会合/等待事件 | 谓词写错=伪唤醒地狱 |
| future/promise | 一次结果回传 | 多结果/流式（要队列或 C++20 execution） |
| atomic | 无锁记账 | 多变量一致性仍需锁或 careful fencing |
| volatile | **不解决并发** | 仅 MMIO/信号处理 |

## 核心概念速览（中英对照）

- **临界区** — critical section：多共享资源互斥访问的代码段
- **数据竞争** — data race：无同步的并发读写，UB 的法律源头
- **锁保护包装** — lock_guard / unique_lock：mutex 的 RAII 外衣
- **期物** — std::future / promise / packaged_task：异步结果的单格信箱
- **虚假唤醒** — spurious wakeup：wait 无 notify 也返回，故须谓词循环
- **顺序一致性** — sequential consistency：seq_cst 的"全局时钟"幻觉承诺
- **释放-获取语义** — release/acquire：发布点与订阅点的同步配对
- **释放-消费语义** — release/consume：依赖链版 acquire（实践已判死刑）
- **比较交换** — compare_exchange_weak/strong：CAS 原语，weak 容许虚假失败
- **无锁性探测** — is_lock_free：atomic 是否真用硬件原子指令

## 最新演进与工业实践

- **C++17 增量**：`std::scoped_lock`（多锁 RAII 一步到位）、`std::hardware_destructive_interference_size`（缓存行对齐）。原书 7.2 的 std::lock+adopt_lock 三步舞在 C++17 后应改写为 `std::scoped_lock lk(m1, m2);` 一行。
- **C++20 对位（P1135R6 已实测 wg21 302）**：`std::jthread`（自动 join + stop_token 协作取消）、`std::latch`/`std::barrier`（一次性/可复用会合计数）、`std::counting_semaphore`（以上三件同属 P1135R6）、`std::atomic<std::shared_ptr>`（自由函数原子访问族 C++20 弃用后的替换者）。教程只写到 C++11 设施层，这五件套是"第 7 章的现代读法"。
- **consume 之死（C++26，P2787R3 谱系，wg21 链接已验证）**：编译器无法正确追踪依赖链，主流实现全部把 consume 当 acquire 处理——标准最终将其从内存顺序枚举中移除；原书 7.5 的 consume 例子里它仍是一等公民，属"教材与标准时间差"的活标本。
- **工业现状**：内存模型章节的事实参照已是 cppreference 的 memory model 系列与 Boehm/Holzmann 著作；本笔记体系里 `../Effective_Modern_C++/07-并发API.md`（Meyers 条款 35–40："优先任务而非线程""default 的 async 由实现决定"）与 `../c++之旅3/10-并发.md`（第 10 章从 C++20/23 视角重讲并行）分别覆盖"决策指南"与"新版全貌"，教程原书提供的是最小可用的 API 骨架。
- **线性一致性理论锚点**：并发正确性的语义地基出自 Herlihy & Wing《Linearizability: A Correctness Condition for Concurrent Objects》（ACM TOPLAS 1990，DOI `10.1145/78969.78972`，已实测 api.crossref.org 返回该记录）——原书 7.5"像有一个全局时钟"的直观说法即其通俗投影。
