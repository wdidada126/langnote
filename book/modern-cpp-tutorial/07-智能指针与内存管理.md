## 一、动机：把 delete 的所有权写进类型里

裸指针只回答"东西在哪"，不回答"谁负责埋"。C++98 时代的三大失血点——异常路径跳过 delete、多所有者互相推诿、拷贝语义说不清——全部源于所有权只是注释里的君子协定。智能指针的答案是**所有权即类型**：`unique_ptr` 说"只有我"，`shared_ptr` 说"我们按引用计数轮流"，`weak_ptr` 说"我只看不占"。三者共享同一个 RAII 地基：资源的生命周期绑定栈对象的生命周期，析构函数是唯一 release 通道，异常栈展开也照常调用。原书把这章放在容器之后、并发之前，正合适：它消费第 3 章的移动语义（`unique_ptr` 只有移动没有拷贝），又为第 7 章"多线程下的 shared_ptr 哪些操作线程安全"埋下伏笔。

## 二、机制：三种指针的内部控制结构

**§5.1 引用计数账本**：计数是"多少个 shared_ptr 指向我"，不是"多少个指针"——裸拷贝指针对象、weak_ptr 都不入账。引用计数的两大原罪：原子操作开销（多线程下每 incref/decref 都是原子 RMW）与**循环引用**（两个对象互指，计数永不归零）。

**§5.2 shared_ptr（共享）**：控制块（strong/weak 计数 + 删除器 + 分配器）与对象本体可以两次 `new`（`shared_ptr<T>(new T)`）或一次（`make_shared<T>`，推荐：省一次分配、且避免 C++17 前函数实参求值交错导致的泄漏窗口）。`use_count()` 返回"共享该资源的 shared_ptr 个数"。裸指针隐式转 shared_ptr 是灾难入口（双重控制块）；同一资源两个独立控制块 = double free。`shared_ptr<T[]>`（C++17）让数组也终于有共享语义，`operator[]` 直接可用。

**§5.3 unique_ptr（独享）**：`unique_ptr<T, D>` 默认删除器 `delete`，零开销抽象——尺寸就是一个裸指针，比较/解引用直接内联，**不写自定义删除器就和裸指针一样快**。三板斧：`release()`（放弃所有权返回裸指针，危险）、`reset()`（析构当前接管新资源）、`get()`（只借看）。函数返回 `unique_ptr` 是工厂模式的现代形态（配合 C++17 强制复制消除，prvalue 直建目标，见 05 篇）。自定义删除器改变类型：`unique_ptr<FILE, decltype(&fclose)>` 的 size 是 16 字节（指针+函数指针），无捕获 lambda 做删除器可回到 8 字节——原书用 `decltype` 声明的坑（lambda 类型只能 `std::function` 或 decltype 两种写法）讲删除器的类型代价。
**std::make_unique 是 C++14 才补上的**：原书标注了这个尴尬（C++11 首发竟遗漏），异常安全的 `f(make_unique<A>(), make_unique<B>())` 论述依赖它。

**§5.4 weak_ptr（观察者）**：不增加 strong 计数，访问前必须 `lock()` 提升为 shared_ptr（资源可能已亡），`expired()` 只作提示（check-then-use 之间有竞态）。三大正规用途：破环（父指针用 weak）、缓存句柄、观察者模式的"目标可能先死"。`shared_from_this()` 依赖内部 enable_shared_from_this 弱计数，对象不是 shared 管理时调用即 UB/C++17 起 bad_weak_ptr。

### 🔧 实测：make_unique 档位 + 环泄漏 + weak 语义（g++ 15.2）

```cpp
auto p = std::make_unique<int>(42);            // C++14 起才有
struct Ring { std::shared_ptr<Ring> next; ~Ring() { std::puts("~Ring destroyed"); } };
{
    auto a = std::make_shared<Ring>();
    auto b = std::make_shared<Ring>();
    a->next = b; b->next = a;                  // 强引用环
}
// 作用域结束：若没打印 ~Ring destroyed，即证明泄漏
auto x = std::make_shared<int>(7);
std::weak_ptr<int> w = x;
bool lock_ok = w.lock() != nullptr;
x.reset();
```

已实测 g++ 15.2：`-std=c++11` 编译失败——`error: 'make_unique' is not a member of 'std'`；`-std=c++14` 通过，运行输出：

```text
*p = 42
use_count a = 2
(上面若未出现 ~Ring destroyed，即证明环泄漏)
weak sees use_count = 1, lock() ok = 1
after reset: expired = 1, lock() = nullptr
```

三个关键点全部实锤：**环内两个对象析构函数都没跑**（输出里没有 `~Ring destroyed`，教科书级泄漏复现）；weak 的 lock 提升期间计数升到 1；`x.reset()` 后 `expired=1`、`lock()` 返回 nullptr——weak 不续命。另注意 `use_count` 打印值受同一语句内求值顺序影响，实测代码把 `w.lock()` 提前求值才得到稳定的 `= 1`，这是原书没有提醒的细节。

## 三、权衡与陷阱

- **选择瀑布**：默认裸值/容器；需要堆+独享 → `unique_ptr`；确需共享所有权 → `shared_ptr`；shared 场景里所有"回指/观察" → `weak_ptr`。原书立场与业界一致：shared 是"我承认设计里有多主人"的坦白书，不是默认选项。
- `shared_ptr` 拷贝便宜（只 ++原子计数）但**赋值/析构贵**（可能触发 delete）；跨线程传 `shared_ptr` 副本安全，但**同一 shared_ptr 对象的并发读写不安全**——C++20 起 `std::atomic_load/store(shared_ptr*)` 自由函数族被标记弃用方向，替代方案是 `std::atomic<std::shared_ptr>`（C++20）。
- 派生类转基类 + `shared_ptr<Derived>` 直接交给 `shared_ptr<Base>` 拥有是合法的所有权移交，但 `enable_shared_from_this` 在构造期未初始化，构造函数里调 `shared_from_this()` 是经典 UB。
- 自定义删除器捕获了悬垂引用/生命周期不足的对象是 `unique_ptr` 的隐雷；`shared_ptr` 别名构造（aliasing constructor）能救一部分（子对象视图延长父对象寿命）。
- 教程未展开但值得记住：`make_shared` 的控制块与对象同块内存，**weak_ptr 未清零时会推迟整块内存释放**（对象析构了但内存不还）——持有大量 weak 且对象巨大时的经典权衡。

## 四、与相邻概念对比

| 维度 | 裸指针 | unique_ptr | shared_ptr | weak_ptr |
|---|---|---|---|---|
| 拥有资源 | 不定 | 独享 | 共享（计数） | 不拥有 |
| 尺寸 | 8B | 8B（默认删除器） | 16B（对象+控制块两指针） | 16B |
| 拷贝 | 随意（歧义） | 禁止 | 计数+1 | 计数不变 |
| 异常安全 | 需手动 | RAII | RAII | 需 lock 提升 |
| 典型场景 | C API 边界 | 工厂/成员 | 缓存/DAG 汇点 | 环的另一半/观察者 |

## 核心概念速览（中英对照）

- **RAII** — Resource Acquisition Is Initialization：资源寿命绑定对象寿命
- **引用计数** — reference counting：shared 的所有权账本，原子维护
- **控制块** — control block：strong/weak 计数+删除器，shared 的后台账房
- **独享指针** — std::unique_ptr：只移动不拷贝的零开销所有权
- **共享指针** — std::shared_ptr：计数归零即释放的共享所有权
- **弱指针** — std::weak_ptr：不增计数、需 lock 提升的观察者
- **自定义删除器** — custom deleter：把 free/fclose/UNLOCK 塞进类型系统
- **make_shared/make_unique** — 单次分配工厂函数（make_unique 迟至 C++14）
- **循环引用** — cyclic reference：shared 互指的计数死锁，weak 解环
- **shared_from_this** — enable_shared_from_this 的自愈取共享句柄

## 最新演进与工业实践

- **档位补全**：`std::make_unique`（C++14）、`std::shared_ptr<T[]>`（C++17）、`std::atomic<std::shared_ptr>`/`atomic<std::weak_ptr>`（C++20，P0718 谱系）、`std::atomic_ref`（C++20）。原书 5.2 遗留的"C++11 没有 make_unique"在今天的最低支持面上基本不再是问题（C++14 是当下工业地板）。
- **弃用与删除时间线**：`auto_ptr` 在 C++11 即被弃用（原书 5.2 有注），**C++17 正式移除**——任何还在写 `auto_ptr` 的代码库等于在 C++17 门前自焚；Herb Sutter 后来反复引用的"auto_ptr 被遗忘"故事（标准委员会差点让 unique_ptr 也步其后尘）是这一节最好的历史注脚。shared_ptr 的自由函数原子访问族在 C++20 标记弃用。
- **社区重估**：2020 后工业圈对 shared_ptr 的态度明显转向克制——Chromium（raw_ptr+Ownership 注解模型）、Rust（借用检查）代表了两个替代方向：用外部分析器或语言机制取代运行时引用计数。std::pmr arena（6 篇）+ 裸指针 + 生命周期约定的组合在低延迟场景抢走一部分原本 shared 的地盘。
