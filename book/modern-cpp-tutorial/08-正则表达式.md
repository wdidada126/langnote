## 一、动机：从"每次都要请 Boost 出山"到语言级支持

正则匹配在工业代码里承担三大任务——检验、替换、抽取（原书 6.1 开篇三需求），后台服务判 URL 是最高频场景。但 C++98/03 标准库里没有正则，事实标准是 Boost.Regex；TR1 曾把它收进扩展命名空间试水，**C++11 才正式把 `<regex>` 纳入标准库**（原书 6.2 强调"从语言级上提供了标准的支持，不再依赖第三方"）。这一章表面讲 API，实际讲两件事：正则语法的最小可读集（6.1 的两张表），以及 std::regex 的匹配对象模型（`std::regex` / `std::regex_match` / `std::smatch` 三件套）。值得补一句历史：`<regex>` 是 C++11 里唯一"由单一作者扛进标准"的大型库件——Tim Shen 当年以学生身份完成 libstdc++ 实现，这段掌故解释了它后来十年停滞的另一面：标准件有了，维护者却散了。

## 二、机制：两张表 + 一条匹配流水线

**§6.1 特殊字符表**（原书逐条）：`$` 串尾；`()` 子表达式分组；`*` 零或多次；`+` 一或多次；`.` 除 `\n` 外任意单字符；`[` 中括号表达式开始；`?` 零或一次/非贪婪标记；`\` 转义与前向引用；`^` 串首（方括号内表取反）；`{` 限定符开始；`|` 选择。**限定符表**：`*`≡`{0,}`、`+`≡`{1,}`、`?`≡`{0,1}`、`{n}`/`{n,}`/`{n,m}`；原书特别提醒 `{n,m}` 逗号两边不能有空格。这三张表覆盖 ECMAScript 语法子集即可读懂绝大多数表达式——std::regex 的**默认语法就是 ECMAScript**（`regex_constants::ecmascript`），另有 basic/extended/awk/grep/egrep 等语法旗标可选。

**§6.2 对象模型**：模式串装进 `std::regex`（`basic_regex` 别名），匹配动作分两个入口——`regex_match` 要求**整串**吻合，`regex_search` 只要**子串**命中（原书正文以 match 为例，search 在同族 API 里同形）。要抓子匹配就传 `std::smatch`（`match_results<string::const_iterator>` 别名）：`m[0]` 是全匹配、`m[1]` 起是括号组——与书的例子严格对应：`[a-z]+\.txt` 匹配文件名集合，`([a-z]+)\.txt` 抽出 base 名。**C++ 字符串二次转义**是原书花括号强调的第一坑：正则里的 `\.` 在字符串字面量里必须写 `\\.`（C++11 原始字面量 `R"(...)"` 是它的解药，见下方实测 b）。

API 家族完整一圈还有三件（原书点到为止，此处补全）：`regex_replace` 用 `$1 $2` 回填括号组做格式化替换；`regex_iterator`/`sregex_iterator` 把"扫完全串所有命中"变成迭代器区间，可直接喂 `std::distance`/`std::copy`/ranges；`regex_token_iterator` 则按"选哪些组"出 token（传 `-1` 即输出组间未命中的补集，是切分器的正则形态）。旗标位：`icase` 大小写不敏感、`nosubs` 丢弃子匹配换速度、`optimize` 请求构造期多干活换匹配期加速、`multiline` 让 `^$` 匹配行界——它们是 `basic_regex` 构造函数第二参数，语义是"建议"而非"保证"（实测 b 见 libstdc++ 对 optimize 的诚实响应）。

### 🔧 实测：复现原书 6.2 全部输出（g++ 15.2）

```cpp
std::string fnames[] = {"foo.txt", "bar.txt", "test", "a0.txt", "AAA.txt"};
std::regex txt_regex("[a-z]+\\.txt");
for (const auto& fname : fnames)
    std::cout << fname << ": " << std::regex_match(fname, txt_regex) << std::endl;
std::regex base_regex("([a-z]+)\\.txt");
std::smatch base_match;   // 命中后 base_match[1] 即括号组
```

已实测 g++ 15.2（`-std=c++11` 起即可编译），输出与原书代码块**逐字一致**：

```text
foo.txt: 1
bar.txt: 1
test: 0
a0.txt: 0
AAA.txt: 0
sub-match[0]: foo.txt
foo.txt sub-match[1]: foo
sub-match[0]: bar.txt
bar.txt sub-match[1]: bar
```

`test: 0`（无 .txt 后缀）、`a0.txt: 0`（数字不在 `[a-z]+` 内）、`AAA.txt: 0`（默认大小写敏感）三个否定样本正好把语义钉死。

### 🔧 实测 b：match/search 分水岭 + iterator 全家桶 + icase/optimize 旗标（g++ 15.2，-std=c++11）

```cpp
std::string s = "call 010-1234 or 020-5678 today";
std::regex phone(R"((\d{3})-(\d{4}))");                 // 原始字面量，免二次转义
auto begin = std::sregex_iterator(s.begin(), s.end(), phone);
std::string repl = std::regex_replace(s, phone, "($1) $2");
std::regex ci("[a-z]+\\.txt", std::regex_constants::icase);
std::regex opt("[0-9]+", std::regex_constants::optimize);
```

已实测 g++ 15.2（`-std=c++11 -O2 -Wall -Wextra` 零警告通过），输出：

```text
match=0 search=1 (整串 vs 子串)
iterator 扫出 2 个号码: [010-1234] [020-5678]
replace -> call (010) 1234 or (020) 5678 today
AAA.txt icase match=1
escaped==raw for foo.txt: 1
optimize ok=1
```

六条各钉一件事：**同一模式同一串，match=0 而 search=1**——"整串 vs 子串"一字之差就是验证与抽取的分水岭（原书 6.2 只演示 match，工单里一半的正则 bug 是拿 match 干 search 的活）；`sregex_iterator` 区间 + `std::distance` 两行扫出全部号码，`[0]` 取的是每个命中全串；`regex_replace` 的 `$1 $2` 回填把 `010-1234` 重排成 `(010) 1234`——注意替换串用的是 `$` 不是反斜杠，与模式侧 `\1` 语法分家，这是 std::regex 冷门接口里误用率最高的一处；`icase` 把原书的 `AAA.txt: 0` 翻成 1，证明默认样本的 0 来自大小写而非语法失配；**`R"((\d{3})-(\d{4}))"` 与逐字双写转义的模式对同一输入给出完全相同结果**（escaped==raw=1），从 C++11 起正则就该住进原始字面量，`\\\\` 地狱是历史包袱；`optimize` 旗标在 libstdc++ 上构造成功且匹配正确——但注意它是 `std::regex_constants::optimize` 的"建议"语义，GCC 实现是否真的多做预处理不作承诺，基准测试是唯一裁判（本机直觉：libstdc++ 对该旗标的处理长期近似忽略，热路径优化别指望旗标，指望 RE2）。

## 三、权衡与陷阱

- **性能是 std::regex 的原罪**：GCC 的 `<regex>` 是模板递归回溯机，编译产物大、运行时慢，教科书级反例是长非匹配串拖出指数级回溯。原书"进一步阅读的参考资料"直接挂了**库作者 Tim Shen 本人**在知乎《如何评价 GCC 的 C++11 正则表达式？》的回答——这是全书最硬核的一条参考文献：作者都不护短。生产环境热路径请用 RE2（DFA、线性时间保证、不支持回溯引用）或 Boost.Regex。
- **灾难回溯的最小复现形态**：`"(a+)+b"` 对 `"aaaaaaaaaaaaaaaaaaaaac"`（21 个 a 收尾 c）——指数级回溯，std::regex/Boost.Regex/PCRE 全部中招，RE2 因无回溯而免疫。凡是"模式来自用户输入"或"输入长度不受信"的场合，问题不是慢而是**可用性问题**（单请求打满一个核）。工程三件套：输入长度上限、超时/步数预算（std::regex 没有此项，又一个换 RE2 的理由）、模式白名单。
- **编译期成本也是成本**：`<regex>` 头本身拖慢 TU 编译，函数里现构 `std::regex` 会把同一模板在多个 TU 反复实例化——`extern template`（03 篇）救不回多少，真正止血的还是"模式对象提到循环外/静态存储期"与 RE2 的前缀编译。
- `regex_match` vs `regex_search` 选错是新手第一大坑：验证整串用 match，日志里捞字段用 search；书例的 URL 需求实际多为 search 场景。
- `std::smatch` 内部持有指向原串的迭代器：**原 `std::string` 析构/修改后 smatch 即悬垂**——这一点原书未展开，属于必须自知的隐藏契约。同理 `m[1].str()` 之外的直接 `string_view` 化（C++17 写法）同样依附原串，生命周期纪律一致。
- 把模式串声明为 `const std::regex` 循环外复用：regex 构造昂贵，函数体内每次现构是常见性能反模式；但 static 初始化非线程安全问题 C++11 后已解决。
- 6.1 的表是 ECMAScript 语义：`\d\w\s`、后向断言等未列出的语法书里没有，读外部正则教程时注意方言差异；且 ECMAScript 子集里 `(?=...)` 前瞻在 std::regex 可用而 `(?<=...)` 后顾不可移植，`\p{Unicode}` 属性类根本没有——从 PCRE/JS 迁移时按"减法"检查语法表。
- 窄/宽两套并行：`std::regex`（char）之外还有 `std::wregex` 与 `wsmatch`/`wcmatch` 家族，UTF-8 文本用窄版时**一切字符类都按字节工作**——`[一-龥]` 这类"按码点"的写法在 std::regex 里根本不成立；locale 敏感类（`[[:alpha:]]`、`\w` 在宽模式下）随 `std::locale` 变化，跨平台结果漂移的常见根源在此。文本若涉及 Unicode 分段/规范化，正解不是正则而是 ICU/utf8cpp，13 篇 `<text>` 展望也是这个缺口的一部分。
- `optimize`/`nosubs` 等旗标是**建议语义**：🔧 实测 b 只验证了"带旗标能构造、结果正确"，没有验证"实现真的执行了建议"——把正确性寄托在可选优化旗标上是危险契约；而 `icase` 属语义旗标（结果会变），可信。两类旗标要分开对待。

## 四、与相邻概念对比

| 方案 | 标准地位 | 时间复杂度 | 回退能力 | 适用 |
|---|---|---|---|---|
| `std::regex` | C++11 标准库 | 回溯，可指数 | 有（后向引用） | 一般校验/抽取 |
| Boost.Regex | 第三方事实标准 | 回溯 | 有+更多语法 | std 不够用时 |
| Google RE2 | 第三方 | DFA 线性保证 | **无**回溯引用 | 不可信输入/热路径 |
| C 库 `regcomp`/`regexec` | POSIX | 回溯（实现相关） | 有（`\1`） | 已有 C 边界/极小依赖 |
| 手写状态机 | — | 线性 | 自定义 | 极致性能 |

与相邻的"非正则"对手也对比一句：`std::string::find`/`find_first_of` 家族胜任"固定子串/字符集"两级需求且快一个数量级——只有真的需要"模式"（重复、选择、分组）才该请 regex 出场；C++23 起 `ranges` 的 `search`/`find_if` 子区间算法进一步蚕食"手写扫描+判断"的旧正则用例。

## 核心概念速览（中英对照）

- **正则表达式** — regular expression：描述字符串集合的匹配模式
- **特殊字符/元字符** — special characters：`$ () * + . [ ? \ ^ { |` 的语法核心
- **限定符** — quantifiers：`* + ? {n} {n,} {n,m}` 重复次数控制
- **整串匹配** — std::regex_match：全串吻合才为真
- **子串搜索** — std::regex_search：任一子串命中即为真
- **匹配结果** — std::smatch / match_results：`[0]` 全匹配、`[1..]` 括号组
- **全量扫描迭代器** — std::sregex_iterator：把所有命中变成迭代器区间
- **格式化替换** — std::regex_replace：`$1 $2` 回填括号组（替换侧用 `$` 不用 `\`）
- **语法旗标** — syntax_options：icase/nosubs/optimize/multiline，语义旗标与建议旗标有别
- **宽字符系族** — wregex/wcmatch/wsmatch：同一模板对 `wchar_t` 复用，`std::wregex` 受 locale 影响
- **原始字面量** — raw string literal：`R"(...)"`，正则模式的反斜杠解药（C++11）
- **ECMAScript 语法** — 默认方言，TR1 时代 Boost 语法的标准化子集
- **二次转义** — C++ 字符串层 + 正则层的双重反斜杠（`\\.`）
- **回溯爆炸** — catastrophic backtracking：NFA 回溯机的指数级失败模式

## 最新演进与工业实践

- **C++20/23/26 对位**：`<regex>` 本体在 C++20/23 **几乎原地踏步**（仅常量与小修），这本身就是社区信号——标准正则的性能债没人还；🔧 实测补充证据：`-std=gnu++26` 下 `<regex>` 照常编译（无弃用无升级），而 C++26 新文本设施 `<text>`（text_encoding：文本编码/校对/敏感处理，非正则替代）在 libstdc++ 15.2 上连 `__cpp_lib_text_encoding` 特性宏都未定义（本笔记 `-std=gnu++26` 探测输出 `no_text`），MSVC STL 则已先行落地——2026 年谈 std::text 主要还是 MSVC 平台的事。提案号本笔记复核不过关故不标注（网传编号常与 *Linear Algebra Library* 等论文撞号）。`std::format`/ranges 分流了一部分"抽取+重组"场景。
- **为什么标准不动 `<regex>`**：接口层没有共识痛点——match/search/replace/iterator 四件套形状被公认合理；实现层的债（回溯机、无超时预算、无 DFA 模式）修起来要么改变复杂度契约、要么引入实现自由度争议，委员会 2019 后的精力整体转向 ranges/format/coroutine/反射，regex 沦为"能用但没人爱"的标准件。SG16（ Unicode 建议组）把文本处理的力气花在了 char8_t/编码与 `<text>` 上，也没有回头碰正则。指望标准版"RE2 化"（线性时间保证选项）在本十年不现实。
- **三大实现近况**：libstdc++ 的部分在 GCC 4.9（2014）由 Tim Shen 重写为单遍 NFA，此后十年未再动架构，大表达式模板实例化爆炸照旧；MSVC STL 走 Plauger 血统的回溯机，长期以功能完整（含 `//` 换行语法等旗标齐全）著称；libc++ 的实现则因正确性 bug 数量多而被 Apple 平台开发者诟病——三家谁都没有 RE2 式的自动机。结论与 2015 年无异：**std::regex 用于教学与低频校验，热路径另请高明**。
- **工业选型现状**：高并发网关/反垃圾一律 RE2 或 hyperscanning（Rust regex crate 的自动机路线），std::regex 在安全边界上因无时间保证被视为 DoS 面。glibc/LLVM 的 sanitizer 之外，clang-tidy 也没有针对灾难回溯的 lint——工程上靠"模式白名单+输入长度上限"土办法。Boost.Regex 在 2026 年仍被 John Maddock 积极维护（作者同时是 std::regex 语法协调人），它与 RE2 的选型分界线就一条：**要不要回溯引用/后向断言**——要则 Boost，不要则 RE2 买线性时间保证；abseil 则干脆不提供正则（推荐外接 RE2），这一"故意缺席"本身就是 Google 系对 std::regex 的投票。
- **社区重估**：教程第 6 章的"三需求+两张表+一个例"结构被验证是恰当地位——它教的不是正则学，是 std::regex 的 API 形状；真正的使用建议在书外（Tim Shen 回答、RE2 文档）才能拿全。本目录内 `../C++标准库/09-正则表达式与IO流.md`（`C++标准库`笔记的正则章）从实现层（NFA/DFA、policy 设计）补掉了本教程未讲的 machinery，两篇互为横轴。
