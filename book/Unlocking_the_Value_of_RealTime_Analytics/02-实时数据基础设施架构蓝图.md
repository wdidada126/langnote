# 02 实时数据基础设施架构蓝图

> ⚠️ 重构章：对应原书约 3–5 个推定小节域（副题承诺的"架构"主体）。本章是全书技术浓度
> 最高处：把商业叙事（01 章）落成五段式基础设施蓝图。凡"原书是否如此分层"均标 ⚠️ 推定。

## 1. 五段蓝图总览（⚠️ 重构骨架）

```
[数据源] --CDC/事件--> [入湖/总线] --订阅--> [流处理] --> [RTA 存储] --> [服务/应用]
   业务库/IoT/日志      Kafka 系           Flink/Spark SS    列存/物化视图    看板/特征/API
```

| 段 | 职责 | 新鲜度贡献（延迟预算项） | 失败姿态 |
|---|---|---|---|
| 源 | 产生变更事实 | 采集器轮询间隔（秒–分） | 丢变更=静默失真 |
| 总线 | 缓冲+重放+解耦 | 落盘确认+复制（毫秒级） | 分区倾斜=局部延迟 |
| 处理 | 清洗/关联/聚合 | 算子链+状态访问（毫秒–秒） | 反压=新鲜度雪崩 |
| 存储 | 服务就绪的物化 | 提交可见性（毫秒–分钟） | 可见性语义错=决策错 |
| 服务 | 决策消费 | 查询+缓存失效（毫秒） | 缓存陈旧=最后一公里失效 |

关键叙事：端到端延迟是五段之和，**任何一段都可能吃掉全部预算**——这是 01 章"可承诺延迟"
的结构依据。

## 2. 源与入站：CDC 是"实时"的第一杠杆

- ⚠️ 转述（重构）：多数企业的存量现实是"业务库即事实源"，实时化的第一步不是上流处理，
  而是把"库表变更"变成"事件流"（CDC：变更数据捕获）。轮询式 CDC（按更新时间戳扫表）把
  新鲜度下限钉死在轮询周期；日志式 CDC（读事务日志）可下沉到亚秒。
- 技术对位：日志式捕获之所以快，是因为事务日志本就是数据库对外可见性的第一现场——
  🔧 E1（见 03 章）里 SQLite WAL 的"提交即可被新读事务看见"演示的正是这一可见性边界。
- 治理钩子：源端表结构变更（schema drift）是实时管道头号事故源，对位
  [Modern Data Architectures with Python 总览](../Modern_Data_Architectures_with_Python/00-总览与阅读地图.md)
  的数据质量/血缘章（波7 在盘）。

## 3. 总线与处理：Lambda→Kappa 的叙事简化

- ⚠️ 转述（重构）：本书作为价值册，对 2016 年前后的 Lambda（批流双路合并）vs Kappa
  （一切皆流+重放）之争只做实用主义裁决：**双路一致性维护成本高，能用"流 + 可重放总线 +
  定期批校正"混合就不要纯双路**。
- 2024–2026 技术对位：这场争论在工程上已被"批流一体"收敛——Flink 官方架构文档
  （https://flink.apache.org/what-is-flink/flink-architecture/ ✅ curl 200）把批视为流的
  特例；Databricks 结构化流（https://docs.databricks.com/aws/en/structured-streaming/ ✅ 200）
  同向。系列正典在 [Streaming Systems 总览](../Streaming_Systems/00-总览与阅读地图.md)
  （流表二元性/水位线的严格定义处）与 [Streaming Databases 总览](../Streaming_Databases/00-总览与阅读地图.md)。
- 本册站位：蓝图层只关心"该段占用多少延迟预算、坏了怎样"，不展开算子语义。

## 4. RTA 存储层：为"决策就绪"而生的物化

- ⚠️ 转述（重构）：服务层存储的选型判据被归约为三问——并发查询画像（看板 vs 点查）、
  新鲜度档位（01 章分层）、更新模式（追加 vs 撤销/更正）。列式 OLAP、KV 服务存储、
  物化视图引擎各占一角。
- 增量物化是"运营级"档位的性价比之王：用预聚合换查询延迟。🔧 E3（03 章）量化了
  全量重算 vs 增量 MERGE 的 28.9× 差距。
- 时点正确性（point-in-time correctness）：实时特征/风控关联要求"以决策时刻可见的数据
  做决策"，而非用最新值回看历史——这是 ASOF 语义的商用价值所在。

## 5. 🔧 实测（E4）：为时点正确性付费多少

- 环境：DuckDB Python 1.5.5，**非本书平台行为**，仅量化"时点连接 vs 最新值连接"的成本差。
- 方法：20 万条订单流 `ASOF JOIN` 5.8 万条按小时快照的用户余额表
  （`ON o.uid=b.uid AND o.ordered>=b.as_of_ts`），对照同一数据取"最新快照"后的普通等值连接。
- 读数：ASOF 时点连接 ≈ **41.0ms**（110,947 行命中）；最新快照普通连接 ≈ **3.1ms**。
  正确性溢价 ≈ **13×**，但绝对值仍是毫秒级——**"时点正确"在今天已是买得起的保险**。
- 对位结论：01 章"行动级"用例（风控/特征）应默认启用时点语义；用最新值回测会系统性
  高估模型效果（数据泄漏的架构根源之一）。

## 6. 服务层与最后一公里

- ⚠️ 转述（重构）：管道再快，若看板缓存 5 分钟、API 网关缓存 10 分钟，端到端新鲜度就是
  缓存值——**SLO 必须度量到消费者，而非到存储写入**。
- 技术对位：缓存失效/推送式订阅（SSE/WebSocket）与 03 章可见性实验（E1）同构：
  "写入完成"≠"读者可见"，中间隔着事务快照、缓存、复制延迟三层语义。
- 与 fabric 对位：统一访问语义（谁在何时以何新鲜度消费了哪份数据）由主动元数据登记，
  见 [Data Fabric Architectures 总览](../Data_Fabric_Architectures/00-总览与阅读地图.md)
  与其 06 章方向的延伸（本目录不代读，仅登记挂点）。

## 7. 蓝图自查清单（架构评审用，⚠️ 重构）

1. 每个用例是否标注了新鲜度档位与端到端延迟预算分解（五段各占多少）？
2. 源端 CDC 是轮询还是日志式？轮询间隔是否 < 档位预算的 1/3？
3. 总线是否保留足够重放窗口以支持"批校正"路径？
4. 处理层反压与状态后端的可观测指标是否接入 SLO 告警？
5. 存储层物化是全量重算还是增量？刷新周期与档位是否匹配（对位 🔧 E3）？
6. 需要时点语义的关联是否用 ASOF 类算子（对位 🔧 E4），还是误用最新值？
7. 服务层缓存 TTL 是否被计入端到端度量？
8. schema drift 是否有契约测试与自动血缘通知（对位波7 册）？

## 8. 本章要点回顾

1. 五段蓝图（源/总线/处理/存储/服务）各占延迟预算一段，端到端 SLO 是求和问题。
2. CDC 模式（轮询 vs 日志）决定新鲜度下限，是实时化第一杠杆。
3. Lambda/Kappa 之争在价值册里被降维为"混合+定期校正"的务实解。
4. RTA 存储三判据：查询画像、新鲜度档位、更新模式。
5. 增量物化用预聚合换延迟，运营级档位性价比最高（🔧 E3）。
6. 时点正确性溢价有限（🔧 E4 ≈13×），行动级用例应默认启用。
7. 最后一公里缓存是新鲜度黑洞，SLO 要度量到消费者。
8. 蓝图的治理面（drift/血缘/元数据）与波6/波7 册共享挂点。

## 核心概念速览（中英对照）

1. **五段蓝图** — Five-stage Blueprint：源→总线→处理→存储→服务的实时管道分层法。
2. **延迟预算分解** — Latency Budget Breakdown：把端到端 SLO 摊派到各段的工程动作。
3. **变更数据捕获** — CDC (Change Data Capture)：把库表变更转为事件流的入站技术。
4. **轮询式 CDC** — Polling-based CDC：按时间戳扫表的捕获方式，新鲜度受轮询周期钳制。
5. **日志式 CDC** — Log-based CDC：读事务日志的捕获方式，可达亚秒新鲜度。
6. **可重放总线** — Replayable Bus：保留历史供批校正/重建的缓冲层（Kafka 系）。
7. **Lambda 架构** — Lambda Architecture：批流双路+合并视图的 2011–2017 主流范式。
8. **Kappa 架构** — Kappa Architecture：一切皆流+重放的单路范式及其工程化修正。
9. **增量物化视图** — Incremental Materialized View：以 delta 合并代替全量重算的预聚合。
10. **时点正确性** — Point-in-time Correctness：以决策时刻可见数据为输入的语义要求。
11. **ASOF 连接** — ASOF Join：按时间最近性而非等值做关联的时点连接算子。
12. **最后一公里陈旧** — Last-mile Staleness：服务层缓存吞掉管道新鲜度的失效模式。
