# 03 内存结构调优 — Oracle Performance Tuning, 2e（精读重构）

> ⚠️ 主题重组口径（[00-总览与阅读地图.md](00-总览与阅读地图.md) §3/§8）。SGA 三池 + PGA 的 9i/10g 参数模型与病理学，
> 全部 ⚠️ 转述 + 文档锚 ✅；中文机理深版本在盘上《Oracle编程艺术》，本章是其"调优视角剪影"。

## 1. SGA 地图（本册时代的版式 ⚠️）

```
SGA
├── Buffer Cache（db_block_buffers × db_block_size → 9i 手工 / db_cache_size → 共享池化）
├── Shared Pool = Library Cache（游标/解析） + Dictionary Cache（行字典）
├── Large Pool（并行/ RMAN/ XAT 的"第二块内存"，无闩设计）
├── Java Pool / Streams Pool（10g 起随组件而生）
└── Log Buffer（redo 环形，见 04 章）
```

- 10g **ASMM**（`SGA_TARGET`）把池间边界交给内核动态搬，`*_TARGET` 变下限、advisory 视图（`V$DB_CACHE_ADVICE`、`V$SHARED_POOL_ADVICE`、`V$PGA_TARGET_ADVICE`）变"如果重分配会怎样"的模拟器 ⚠️。本册 2e 通说=双代并讲（⚠️ 推定）。
- 与 `02` 章的耦合：缓存不够 → `db file scattered/sequential read` 涨；共享池不够 → 硬解析排队 → `latch: shared pool`/`library cache` 涨。**内存调优的输出永远是等待账本的变化**，不是命中率数字。

## 2. Buffer Cache：命中率之后的正确学问（⚠️ 通说）

1. **多块池**：`db_nk_cache_size`（2k–32k）允许表空间块尺寸异构；每池独立 LRU，参数错配会让某池"饿死"——10g 时代高频事故 ⚠️。
2. **缓存钉与链**：热点块挂在 buffer chain 上，高并发同块读 → `cache buffers chains` 子闩风暴；对策从"降 PCTFREE/散列热块"到 10g 的 `_db_gh_*` 系列演进 ⚠️（机理正典在 [../Oracle编程艺术：深入理解数据库体系结构（第3版）.md](../Oracle编程艺术：深入理解数据库体系结构（第3版）.md)）。
3. **keep/recycle 池**：小对象钉住（keep）、大表扫描不污染（recycle）——`ALTER TABLE ... STORAGE (BUFFER_POOL KEEP)` ⚠️；10g 后 advisory 与 smart scan 让它退化为例行技巧。
4. **`db_cache_advice` 的正确读法** ⚠️：它模拟"若池为 E 大小，物理读多少"，只答"缩小有没有悬崖"，不答"增大值不值"。

### 🔧 类比 D1/D2：缓存不住 vs 缓存得住的差距在"回不回表"（SQLite，非 Oracle）

20 万行、`a` 列 20 个取值、`pad` 40 字节的表上（`demo_out.txt`）：

- 覆盖查询 `SELECT id,a ... WHERE a=5`（计划：`SEARCH big USING COVERING INDEX ix_big_a`）——1 万行全在索引页里拿到：**5.063 ms**。
- 同谓词回表 `SELECT * ...`（`SEARCH big USING INDEX` + 回查行）：**22.096 ms**（约 4.4 倍）。

对应 Oracle 账本：回表 = 每次多一个 `db file sequential read` 等待；"索引覆盖消灭单块读"在两个引擎里是同一个物理故事。缓冲池"装不装得下热集"SQLite 不模拟（无 LRU 等待面），该层只能 ⚠️ 转述。

## 3. Shared Pool：解析的内存战场（⚠️ 通说；SQL 面全展开在 `06`）

- 两块居民地：**Library Cache**（游标共享单元：SQL 文本→解析树→计划的三级句柄）与 **Dictionary Cache**（对象/列/权限元数据）。
- 病理三连 ⚠️：尺寸小 → 老化驱逐 → 再解析 → `latch: shared pool`/`library cache` + CPU 烧在解析；碎片化 → `ORA-04031`；未用绑定变量 → 版本爆炸（同文本千个游标），`V$SQL_SHARED_CURSOR` 的前代是 `V$LIBRARYCACHE` 命中率崩塌。
- 9i/10g 缓解阀：`cursor_sharing`（EXACT/FORCE/SIMILAR——SIMILAR 的直方图判定坑 ⚠️）、`session_cached_cursors`（会话侧软链接）、10g `session_state_caches` 等组件级细池（11g 起库缓存闩被 mutex 全面替换 ⚠️）。
- 度量习惯：抓"可解析比例"（每次执行新增版本数）比抓命中率更接近病灶——同判见 TOP 2e 解析章（✅ [../Troubleshooting_Oracle_Performance_2e/12-解析.md](../Troubleshooting_Oracle_Performance_2e/12-解析.md)）。

## 4. Large Pool / Java Pool / Streams Pool（⚠️ 一句话档案）

| 池 | 居民 | 饥饿症状 |
|---|---|---|
| Large Pool | 并行从属消息缓冲、RMAN 通道、XAT | 溢出抢 shared pool → 04031 |
| Java Pool | JVM 会话驻留 | Java 存储过程报 ORA-29558 类 |
| Streams Pool | 10g Streams 队列/捕获进程 | AQ 延迟升高 ⚠️ |

（10g 新组件、2e 时代正好赶上首版，通说会有一章半的篇幅 ⚠️ 推定。）

## 5. PGA：从排序区到工作区自动化（⚠️ 通说）

- 9i 手工时代参数群（`sort_area_size`/`sort_area_retained_size`/`hash_area_size` 等）→ 9i 起 `WORKAREA_SIZE_POLICY=AUTO` + `PGA_AGGREGATE_TARGET`：全实例工作区总预算 + 每操作按"期望最优/期望"两模式分配 ⚠️。
- 饥饿病理 ⚠️：排序溢盘（`direct path read/write (temp)`、`sort merges` 涨）、哈希连接分区化（一行变两次扫，10g `one pass/two passes` 统计）；`V$PGA_TARGET_ADVICE` 给"加到 E 时估算过盘量降多少"。
- 10g 专属：并行从属真实内存 `parallel_adaptive_multi_user`、`PGA_AGGREGATE_LIMIT` 是 12.2 才补的失控之锁（⚠️ 本册未及，演进节记录）。

## 6. 结构→等待→参数三步决策表（⚠️ 方法论收口）

| 症状（02 章账本） | 结构假设 | 当年动作 | 今天是否仍有效 |
|---|---|---|---|
| 物理读头部高、advisory 有悬崖 | buffer 饥饿 | 调大 DB_CACHE_SIZE/`SGA_TARGET` | 思路在，云 DB 多自动 ⚠️ |
| 共享池闩 + 解析 CPU 高 | 无绑定变量/池小 | 绑定变量 > `cursor_sharing` > 扩池 | ✅ 优先级至今不变 |
| temp 过盘、HJ 两 pass | PGA 饥饿 | 调大 PGA_AGGREGATE_TARGET | 同上 |
| 04031 反复 | 组件碎片/池边界 | 显式分池（ASMM off） | 罕见化 ⚠️ |

## 6.1 补充：参数 × 等待事件交叉表（⚠️ 通说重组；本册"结构派"的资产负债表）

| 等待头部 | 嫌疑参数 | 佐证视图 | 先查什么 |
|---|---|---|---|
| `db file scattered/sequential read` | `DB_CACHE_SIZE`/`SGA_TARGET` | `V$DB_CACHE_ADVICE` | advisory 有无悬崖、统计是否骗人（`06`） |
| `latch: cache buffers chains` | 子闩哈希数（隐藏参） | `V$LATCH_CHILDREN` | 先找热块再谈闩（`05`） |
| `latch: shared pool`/`library cache` | `SHARED_POOL_SIZE`/`CURSOR_SHARING` | `V$LIBRARYCACHE`、`V$SQL_SHARED_CURSOR` | 解析风暴优先于扩池 |
| `free buffer waits` | `DB_WRITER_PROCESSES` | `V$SYSSTAT` dirty | 写盘瓶颈归 `04` |
| `PGA 相关`（过盘/`direct path read temp`） | `PGA_AGGREGATE_TARGET` | `V$PGA_TARGET_ADVICE`、`V$SQL_WORKAREA` | 先抓肇事 SQL（排序/哈希） |
| ORA-04031 | 组件边界/`SGA_TARGET` | alert+`V$SGASTAT` | 大分配请求方（Java/Streams?） |

使用纪律 ⚠️：此表的正确读法是"**等待 → 假设 → 证据 → 动作**"，不是"等待 → 改参数"；每一格都要求先有第二列视图的量化证据。

## 6.2 共享池解剖图（⚠️ 通说教学版）

```
Shared Pool
├── Library Cache
│    └── Cursor（父句柄=文本+统计；子句柄=权限+计划+会话私有）×N 版本 ← 版本爆炸点
├── Dictionary Cache（行字典：对象/列/权限/段头）
├── 队列结构（LRU 链 + pin 计数；"老化=从 LRU 端驱逐未 pin 项"）
└── SQLArea/其他内存结构（并行消息缓冲的溢出落点 ← large pool 缺席时）
```

- 版本爆炸的账 ⚠️：每子游标约占固定头 + 私有 SQLA；千版本同文本 = 共享池被一种 SQL 吃光——`V$SQL` 的 `VERSION_COUNT` 列是这一病的验血单。
- 度量三件套 ⚠️：`V$LIBRARYCACHE`（RELOADS/HIT 比看趋势）、`V$SGASTAT` 的 `library cache`/`sql area` 占用、`V$SYSSTAT` 的 `parse count (hard)`。**硬解析率 = hard/total，比任何命中率都诚实。**

## 6.3 一个 2006 年真实感案例（⚠️ 合成教学案，非原书案例）

症状：白天每小时 `latch: shared pool` 上万、CPU 60% 在实例内。查：`VERSION_COUNT` 榜首为 ORM 生成的字面量 IN 列表 SQL（同模板 800 版本）。处置序列：①紧急 `CURSOR_SHARING=FORCE`（止血，出现执行劣化即回退）；②中期改应用启用绑定参数（真正的解）；③长期共享池扩容仅做缓冲。账本回收：硬解析率 45%→2%，`logons` 无关。教训 ⚠️：**共享池病九成是解析病，扩池是给漏水的桶换大桶。**

## 6.4 一页记忆卡（⚠️ 结构派自测题）

1. `free buffer waits` 归哪口？——DBWn 写不动（`04`），不是"缓存太小"的专属症状。
2. 扩共享池什么病能治、什么病治不了？——治容量饥饿；治不了版本爆炸（那是解析病，`06`）。
3. advisory 视图的共同假设？——"其他条件不变"；负载本身会变，悬崖段可信、缓坡段勿当真 ⚠️。
4. KEEP 池三条件？——对象小、访问频、被大扫冲刷——缺一即负收益 ⚠️。
5. mutex 时代后还要读本章吗？——要：饥饿的因果链不变，只是"闩"字换成了"版本/桶"字（演进节）。

## 核心概念速览（中英对照）

- **SGA** — System Global Area：实例共享内存区（缓存/共享池/大池…）。
- **缓冲缓存** — Buffer Cache：数据块的内存副本集合，LRU+pin 管理。
- **ASMM** — Automatic Shared Memory Management：10g `SGA_TARGET` 自动池配比。
- **advisory 视图** — Advisory Views：`V$*_ADVICE` 假设性重分配模拟器。
- **缓存链闩** — cache buffers chains Latch：热点块链的并发保护争用 ⚠️。
- **KEEP/RECYCLE 池** — Buffer Pools：热钉与防污染的双池策略 ⚠️。
- **库缓存/字典缓存** — Library/Dictionary Cache：shared pool 两大居民地。
- **ORA-04031** — 共享池分配失败：碎片/饥饿的终症 ⚠️。
- **工作区** — Work Area：排序/哈希/合并的 PGA 内存单元（`WORKAREA_SIZE_POLICY`）。
- **过盘** — Optimal/One-pass Execution：工作区超内存溢写临时段 ⚠️。

## 最新演进与工业实践

- **文档锚 ✅（2026-09-28 curl 200）**：内存架构与调优在 Tuning Guide 19/26 版主链（https://docs.oracle.com/en/database/oracle/oracle-database/26/tgdba/index.html ）；参考手册参数族（`SGA_TARGET`/`PGA_AGGREGATE_TARGET*`）两版均在册 ⚠️（未逐参数校验）。
- **代际变迁** ⚠️：11g 库缓存闩 → **mutex**（版本计数细粒度）、AMM（`MEMORY_TARGET`）后又推荐 AM 手动/HugePages；12c 多租户下 SGA 按 CDB 共享、PDB 有内存限额；19c `PGA_AGGREGATE_LIMIT` 默认化；**23ai/26ai**：内存顾问与 ADI 常态化，`INMEMORY` 列存池（12c 起）成为"第三块缓存"——本册的三池地图今天是它的历史底座。
- **工业实践**：自建 OLTP 主流停在 19c 参数面（大 SGA + HugePages + AM），云迁移后池配比问题基本交给自治层（✅ Autonomous 文档根 https://docs.oracle.com/en/cloud/paas/autonomous-database/index.html ，细节 ⚠️）；跨引擎类比：MySQL InnoDB buffer pool 单调一池（无共享池概念）、PG 无实例级缓存池（借 OS page cache）——互见 [../高性能mysql.md](../高性能mysql.md)、[../PostgreSQL_10_High_Performance_3e/00-总览与阅读地图.md](../PostgreSQL_10_High_Performance_3e/00-总览与阅读地图.md)。
- **读法建议**：本章参数清单按"过期"处理；不过期的是"**饥饿会伪装成等待、等待要先归因到池**"的诊断语法，与 TOP 2e 实时分析章合读性价比最高（✅ [../Troubleshooting_Oracle_Performance_2e/04-不可复现问题的实时分析.md](../Troubleshooting_Oracle_Performance_2e/04-不可复现问题的实时分析.md)）。
