# 02 等待事件与响应时间分析 — Oracle Performance Tuning, 2e（精读重构）

> ⚠️ 主题重组口径（[00-总览与阅读地图.md](00-总览与阅读地图.md) §3/§8）。本章是全书"仪表盘"章：
> Oracle 行为全部 ⚠️ 转述 + 官方文档 ✅ 锚；🔧 为 SQLite 等待计时类比（非 Oracle 行为）。

## 1. 等待接口：把"慢"拆成"在等什么"

- 原理 ⚠️：实例中每个会话的墙钟时间被插桩拆成**命名等待事件 + 非空闲 CPU/服务时间**；`V$SESSION_EVENT` 给会话累计、`V$SYSTEM_EVENT` 给实例累计（TIME_WAITED/COUNT/DB_TIME 列族）。
- **空闲/非空闲二分**是关键纪律 ⚠️：`SQL*Net message from client` 这类"等客户端敲键盘"的事件不计入调优账本；9i/10g 靠 `V$EVENT_NAME` 与文档清单人工划分，10g 起 wait class 把这件事制度化。
- 服务时间/等待分解 = 队列论口径：响应时间 = 队列时间 + 服务时间，等待事件命名基本对应"资源种类"（IO/锁/闩/网络/提交）。
- 官方现行锚 ✅：等待事件与性能视图在 Tuning Guide（26 版根页 https://docs.oracle.com/en/database/oracle/oracle-database/26/tgdba/index.html ，2026-09-28 curl 200）设独立章节；参考手册 `V$` 视图族同名健在 ⚠️。

## 2. 10g 时代的"头条等待事件"名录（⚠️ 通说转述）

| 事件 | 资源域 | 一句话病理解释 |
|---|---|---|
| `db file sequential read` | 单块物理读 | 索引回取/链式追块；次数比耗时更值得看 |
| `db file scattered read` | 多块物理读 | 全表扫描的 IO 证据 |
| `direct path read` | 绕过缓存直读 | 大排序/全扫并行/临时段 |
| `log file sync` | 提交 | 客户端感知提交慢的第一现场 |
| `log file parallel write` | LGWR | redo 盘慢，拖累上一行 |
| `enq: TX - row lock contention` | 行锁 | 业务锁语义问题，见 `05` |
| `latch: cache buffers chains` | 子闩 | 热点块并发钉读，见 `03/05` |
| `buffer busy waits` | 块状态 | 单块读风暴/段头竞争 |
| `CPU time`（非事件） | 服务时间 | 一切等待之外的账，占比高=好消息或坏 SQL |

- 读法纪律 ⚠️：先按 DB_TIME 占比排序 → 对头部事件问三句（谁在等？等什么资源？该资源哪来的压力？）→ 落到 `03–06` 章的结构域。TOP 2e 把这套读法工程化为实时/事后双路线（✅ 实证于 [../Troubleshooting_Oracle_Performance_2e/04-不可复现问题的实时分析.md](../Troubleshooting_Oracle_Performance_2e/04-不可复现问题的实时分析.md)、[../Troubleshooting_Oracle_Performance_2e/05-不可复现问题的事后分析.md](../Troubleshooting_Oracle_Performance_2e/05-不可复现问题的事后分析.md)）。

## 3. 会话画像与"响应时间原子"

- 单会话跟踪 ⚠️：`ALTER SESSION SET EVENTS '10046 trace name context forever, level 8/12'` 产出逐调用等待明细，tkprof 聚合——本册时代（2006）该组合已是标准武器；10046 至今未死，26 文档仍列 SQL Trace 为主诊断手段（✅ 同一 guide 根 + [../Troubleshooting_Oracle_Performance_2e/03-可复现问题的分析.md](../Troubleshooting_Oracle_Performance_2e/03-可复现问题的分析.md) 同款实证）。
- "总响应时间 = Σ 各等待"这条守恒式是全部剖析工具的世界观；剖析器输出的 self/propagated 两层计时即其递归化 ⚠️。

### 🔧 类比演示 D4：响应时间分解（SQLite 3.45.3，非 Oracle 行为）

本机 `demo.py`（产物 `D:\develops\tmp\dbwave_w5_orapt\demo_out.txt`）对 20 万行表跑三类操作并计时求和：

| "等待分项"（类比名） | 耗时 | 占比 |
|---|---|---|
| FULLSCAN-类比（`WHERE a IS NULL OR a<>-1` 全扫） | 10.26 ms | 40.7% |
| INDEX-类比（`a=7` 走 `ix_big_a`） | 0.555 ms | 2.2% |
| WRITE+UNDO-类比（UPDATE 3 万行后 ROLLBACK） | 14.369 ms | 57.1% |
| **Σ = 总账** | **25.185 ms** | 100% |

验证的是**方法论结构**：总时间可完全摊到命名分项上、头部两项吃掉 98%——这正是"先治最大等待"的算术依据；Oracle 的差别只在分项由内核自动命名并跨会话聚合 ⚠️。

## 4. 采样 vs 累计：当时的两个时间分辨率

- **累计面**：`V$SYSTEM_EVENT` 自实例启动累计——会被历史稀释，看增量（两次快照差）才反映"现在"，这正是 Statspack snap 对的动机 ⚠️（`08` 章）。
- **瞬时面**：`V$SESSION` join `V$SESSION_WAIT` 轮询采样——土法 ASH。10g 的 **ASH**（Active Session History，每秒采样活动会话、内存环形缓冲、10:1 沉淀进 AWR）把土法官方化 ⚠️；本册成书时 ASH 刚出生，通说不深（⚠️ 推定）。
- **事后面**：AWR 把采样/累计双料持久化 + ADDM 自动因果推断——2006 年新事物，本册以 Statspack 为主的口径到 2010s 全面让位 ⚠️（对 TOP 2e §6 同款判断，✅ 盘上已验）。

## 5. 等待事件之外必须留的三个问题（⚠️ 通说）

1. 等待覆盖不了"已发生但采样丢失"的尖峰 → 需要历史仓库（Statspack/AWR）。
2. 事件名是结果不是原因（`log file sync` 慢的根因可能在网络确认与 fsync 策略）→ 需要 OS 层仪表交叉（`vmstat/iostat`，见 `04`）。
3. 应用侧时间（连接获取、驱动往返）不在实例账本里 → 端到端剖析需要应用插桩，TOP 2e 的 Instrumentation 节把这点写进方法论（✅ [../Troubleshooting_Oracle_Performance_2e/02-关键概念.md](../Troubleshooting_Oracle_Performance_2e/02-关键概念.md)）。

## 5.1 补充：五个高频事件的"第二层问题"（⚠️ 通说追问链）

1. `db file sequential read` 高——**先问次数再问平均时延**：次数高=访问路径病（索引回表风暴/链行追块，接 `06`）；时延高=IO 栈病（接 `04`）。同名单事件两个科室。
2. `db file scattered read` 高——全表扫描不一定有罪：小表高频扫=缓存候选（keep 池/统计正确化），大表低频扫=正常报表；看**每扫描块的复用率**。
3. `log file sync` 高——拆三层：LGWR 本身慢（`log file parallel write` 对照）→ 盘；组提交未生效（提交节拍病，应用侧，接 `07`）→ 代码；网络确认（远程 standby 同步模式）→ 架构。
4. `enq: TX` 高——等待对象列（`V$SESSION` 的 ROW_WAIT 系）定位行 → 画持锁链 → 90% 场景结论是"改事务"不是"调数据库" ⚠️。
5. `latch: cache buffers chains` 高——找热点块（`X$BH`/`V$LATCH_PARENT` 系定位）→ 多为索引最左列热点或序列合并块 → 结构手术（反向键索引/散列，接 `05/06`）⚠️ 时代配方。

## 5.2 采样窗口与"尖峰丢失"的土法对策（⚠️ 通说）

- 10 秒轮询双查询法：`V$SESSION` join `V$SESSION_WAIT` 高频截屏，拼"事件×次数"直方——个人版 ASH；
- 事件守恒检查：采样期总时长应≈Σ事件时长，缺口=采样丢失/空闲混入；
- 与 Statspack 差值法（`08` 章）互为"显微镜/望远镜"。

## 5.3 一张"等待事件→结构域→动作"速查（⚠️ 重组）

| 事件头部 | 归域 | 首选视图 | 动作章 |
|---|---|---|---|
| db file scattered read | IO/统计 | `V$SQL` 按 reads | `04`+`06` |
| buffer busy waits | 并发/段 | `X$BH`(难) | `05` |
| latch: shared pool | 内存/解析 | `V$LATCH`+`V$SQLAREA` | `03`+`06` |

| enq: TX | 锁 | `V$LOCK` | `05` |

## 5.4 等待事件分析的五个高频误读（⚠️ 通说纠偏）

1. **按等待次数排序**：`SQL*Net more data from client` 次数可高达百万而无害——排序键应是"总时间占比"，次数只做形态参考。
2. **拿启动累计当"现在"**：实例跑三个月的 `V$SYSTEM_EVENT` 稀释一切新变化——永远用快照差（`08` 章）。
3. **给空闲事件开处方**：先对照空闲名单（`SQL*Net message from client`、`client init`、各类 job/slave idle）再立项 ⚠️。
4. **单事件宿命论**："看到 enq 就加索引"之类跳过持锁链取证——锁病的第一证据是 `V$LOCK` 关系图不是事件名。
5. **忽略无等待之慢**：CPU time 占比高 = 实例内计算（坏计划/解析/硬绑定 PL/SQL 循环），"没在等"恰恰是最大的病灶信号（`06` 章）。

（本节与 `01` 章 §6 误区呼应：等待模型是**账本语法**，不是**答案**；答案永远在"事件→结构域→机制"的下一跳。TOP 2e 用 2014 年的双轨（有/无诊断包）写法把"下一跳"制度化 ✅，本册提供其 2006 年的词汇表。）

## 5.5 等待事件诊断的三个"第一入口"（⚠️ 通说归纳）

1. **实例全局看占比**：`V$SYSTEM_EVENT` 快照差按 `TIME_WAITED` 降序 → TOP 5 事件锁定资源域（IO/锁/提交/缓存），决定本轮调优主战场。
2. **会话级看现场**：`V$SESSION` join `V$SESSION_WAIT` 抓活动会话当前事件 + 等待参数（P1/P2/P3 解码为文件号/块号/行标识），从"实例噪声"落到"具体对象"。
3. **调用级看明细**：10046 level 12 trace + tkprof 给出逐 SQL 的等待分项与绑定值，是"为什么这条 SQL 慢"的最终答案来源（与 `03` 章共享池解析诊断共用同一把 trace 刀）。

## 核心概念速览（中英对照）

- **等待接口** — Wait Interface：会话时间按命名等待事件插桩拆分的内核机制 ⚠️。
- **等待事件** — Wait Event：一次"等待某资源"的具名记录（如 `db file sequential read`）。
- **等待类** — Wait Class：10g 起事件按资源域归类（User I/O/Concurrency/…）⚠️。
- **空闲等待** — Idle Event：非工作负载所致（等客户端等），应从账本剔除 ⚠️。
- **DB_TIME** — Database Time：会话处于"数据库工作"状态的时间总量，AWR 报告的分母 ⚠️。
- **10046 事件** — SQL Trace Event 10046：会话级逐调用等待/绑定值跟踪，level 12 全量 ⚠️。
- **tkprof** — TKPROF：把 trace 文件聚合成按 SQL 汇总报告的分析工具 ⚠️。
- **ASH** — Active Session History：10g 每秒活动会话采样环形缓冲 ⚠️。
- **快照差** — Snapshot Delta：两次累计视图取差得"当下"画像的方法 ⚠️。
- **直接路径读** — Direct Path Read：绕过缓冲缓存的段级直读，伴随 `direct path read` ⚠️。

## 最新演进与工业实践

- **文档锚 ✅（2026-09-28 curl 200）**：等待与诊断现行权威=Tuning Guide 26 版根页 https://docs.oracle.com/en/database/oracle/oracle-database/26/tgdba/index.html 与 19 版 https://docs.oracle.com/en/database/oracle/oracle-database/19/tgdba/index.html ；本目录只引 guide 级根页（精确小节页易 404，#23 先例纪律）。
- **等待模型的 2026 现状** ⚠️ 转述：AWR/ASH 骨架未变且强化——ASH 全保真上云成 **ASH Analytics**（OCI 独立产品）、AWR 可推送 Hub 做跨库分析；10046/SQL Trace 谱系仍在文档主链（[../Troubleshooting_Oracle_Performance_2e/03-可复现问题的分析.md](../Troubleshooting_Oracle_Performance_2e/03-可复现问题的分析.md) 同款结论）。
- **许可格局变化**：Diagnostics Pack（AWR/ASH 访问许可）在 Autonomous/FREE 环境内不再单独计费 ⚠️；本地 19c/23ai 企业版仍按选件授权——"没有 Diagnostics Pack 怎么办"的老问题（TOP 2e ✅ Ch4/Ch5 双轨写法）在自治环境消失，在自建库仍真实。
- **跨引擎标配化**：MySQL `events_waits_summary_global_by_event_name` ≈ `V$SYSTEM_EVENT`、PG `pg_stat_activity.wait_event` ≈ `V$SESSION_WAIT`、SQL Server `sys.dm_os_wait_stats` ≈ 实例累计面 ⚠️ 类比；互见 [../高性能mysql.md](../高性能mysql.md)、[../PostgreSQL_10_High_Performance_3e/00-总览与阅读地图.md](../PostgreSQL_10_High_Performance_3e/00-总览与阅读地图.md)。
- **工业实践**：现代 SRE 把"USE/RED 方法 + 采样火焰图"叠加在等待模型上（eBPF 全栈剖析）；Oracle 侧对位物是 ASH Analytics 与 Enterprise Manager 的诊断簇 ⚠️。本册 2006 章面今天的正确用法：读懂事件名词源，工具面直接学 26ai 文档。
