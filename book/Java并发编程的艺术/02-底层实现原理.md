# 第 2 章 Java并发机制的底层实现原理（原书第 2 版 pp.16-58）

> **本书最硬核、最具独有价值的章节**：从 CPU 缓存一致性讲到 `volatile` 的 `lock` 前缀汇编，再到 `synchronized` 在字节码/JVM/CPU 三层的实现。这是其他 Java 并发书普遍略过的底层。

## 一、本章地图

| 主题 | 关键结论 |
| --- | --- |
| `volatile` 的 CPU 语义 | 编译期插 `lock` 前缀指令 → **MESI 缓存锁定/总线锁** + 内存屏障 |
| `synchronized` 三层实现 | 字节码 `monitorenter/exit` → JVM `ObjectMonitor` → 操作系统 `mutex` |
| 锁升级 | 偏向锁 → 轻量级锁 → 重量级锁（**偏向锁 JDK 15+ 已移除**） |
| 原子操作 | CAS（CPU `cmpxchg`）+ 缓存一致性协议（MESI/MESIF/MOESI） |

## 二、核心精讲

### 2.1 `volatile` 的底层（CPU 视角）
- 可见性：写 `volatile` 变量时，JIT 插入 **`lock` 前缀指令**（x86 上如 `lock addl $0, (%rsp)` 作为内存屏障），该指令**锁定总线/缓存行**，强制把写立即刷回主存并令其他 CPU 的该缓存行失效（MESI 协议 `Invalid` 状态）。
- 禁止重排序：该 `lock` 指令同时是**全屏障**（x86 上天然有 StoreLoad 语义），阻止 `volatile` 写之前的读写被重排到写之后（及对称方向）。
- 不保证原子：`volatile++` 仍是 读-改-写 三步，非原子（需 `AtomicInteger`/CAS）。
- 验证：`javap -c` 看 `volatile` 字段读写是否带 `flags: ACC_VOLATILE`；JOL/汇编看 `lock` 前缀。

### 2.2 `synchronized` 的三层实现
1. **字节码层**：`monitorenter` / `monitorexit`（同步块）；同步方法用 `ACC_SYNCHRONIZED` 标志。
2. **JVM 层**：每个 Java 对象头（Mark Word）含**锁状态**；进入同步时操作 `ObjectMonitor`（C++ 结构，含 `_owner`/`_EntryList`/`_WaitSet`）。
3. **OS 层**：重量级锁最终落到 **操作系统互斥量（`pthread_mutex`/`WaitForSingleObject`）**，涉及**用户态→内核态切换 + 线程挂起/唤醒**（贵）。

### 2.3 锁升级（🔧 修正）
- 经典路径：**偏向锁**（无竞争时把线程 ID 存 Mark Word，零开销）→ **轻量级锁**（CAS 抢 Mark Word，自旋）→ **重量级锁**（OS mutex，线程挂起）。
- 自适应自旋：JVM 按历史记录决定自旋次数，避免无意义空转。
- 锁消除 / 锁粗化：JIT 判定"锁对象不会逃逸"就直接去掉锁；连续加锁合并成一把。
- 🔧 **重大修正**：**偏向锁在 JDK 15 起被废弃并移除（JEP 374）**。现代 HotSpot 直接走"轻量级锁 + 自适应自旋 + 锁消除/粗化"，不再有偏向态。原书"默认走偏向锁"的叙述对 JDK 15+ **已过时**。

### 2.4 原子操作与缓存一致性
- 硬件原子原语：`cmpxchg`（x86）、`ldrex/strex`（ARM LL/SC）。
- **MESI 协议**：多核间通过缓存行状态（Modified/Exclusive/Shared/Invalid）保证一致性；`lock` 前缀本质是"获取该缓存行的独占权并写回"。
- 变体：Intel **MESIF**、AMD **MOESI**——影响跨核同步的微观性能。

## 三、版本演进

- **JDK 1.0–1.4**：`synchronized` 直接是重量级（每次都 OS mutex）→ 贵。
- **JDK 6 (2009)**：偏向/轻量级锁 + 自旋 + 消除/粗化 → 性能追平 `ReentrantLock`。
- **JDK 9 (2017)**：`VarHandle` 提供 plain/opaque/acquire/release/volatile 五档语义，可精确控制"要不要 `lock` 前缀级屏障"。
- **JDK 15 (2020)**：偏向锁移除（JEP 374）——维护偏向锁的代价在现代多核上已大于收益。
- **JDK 21+**：虚拟线程下持有 `synchronized` 会**pin 平台线程**（JDK 24 起多数场景已解），`ReentrantLock`/`StampedLock` 更适配。

## 四、经典论文 / 原始文献

- **Sewell et al., "x86-TSO: A Rigorous and Usable Programmer's Model for x86 Multiprocessors" (CACM 2010)**——x86 强内存模型的严格定义，解释为何 x86 下某些重排"看不到"。
- **Alglave, Maranget, Tautschnig, "Herding Cats: Modelling, Simulation, Testing, and Data-mining for Weak Memory" (TOPLAS 2014)**——ARM/POWER 弱内存的形式化，与 x86 对照。
- **Intel® 64 and IA-32 Architectures SDM, Ch. 8 "Memory Ordering"**——`lock` 前缀与 `cmpxchg` 的权威硬件手册。
- **Manson-Pugh-Adve (POPL 2005)**——JMM 形式化，给 `volatile` 语义定调。

## 六、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "`volatile` 保证原子" | 只保证可见+单变量读写原子；`i++` 非原子 |
| 2 | "`synchronized` 默认走偏向锁" | 🔧 JDK 15+ 偏向锁已移除，直接轻量级 |
| 3 | "锁总是很慢" | JDK 6 后轻量级/自旋/消除使其很快；无竞争时接近无锁 |
| 4 | "`volatile` 写不进内存" | 实际有 `lock` 前缀刷缓存行；代价在屏障而非写本身 |
| 5 | "MESI 让所有核瞬间一致" | 有传播延迟；`lock` 前缀的屏障才是"可见性"保证 |
| 6 | 虚拟线程里照用 `synchronized` | 会 pin 平台线程；改 `ReentrantLock`/`VarHandle`（JDK 24 起多数已修复） |
