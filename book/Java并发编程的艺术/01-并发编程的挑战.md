# 第 1 章 并发编程的挑战（原书第 2 版 pp.1-15）

> 本书开篇：并发不是"更快"的免费午餐，三大代价——上下文切换、死锁、资源限制。

## 一、本章地图

| 主题 | 关键结论 |
| --- | --- |
| 上下文切换 | 线程切换要保存/恢复寄存器与程序计数器（μs 级）；**过多线程反而更慢** |
| 减少上下文切换 | 无锁并发、CAS、最少线程、协程（虚拟线程） |
| 死锁 | 四个必要条件；避免 = 破坏其一（定序 / 超时 / 一次性申请） |
| 资源限制 | "多开线程"受 CPU 核数、内存、带宽、数据库连接池硬约束 |
| 资源限制解决方案 | 集群（多机）、池化（连接/线程）、改用异步 I/O |

## 二、核心精讲

### 2.1 上下文切换（Context Switch）
- 即使是单核，也靠时间片轮转"看起来"并行；切走时要保存线程上下文（PC、寄存器、栈指针），切回时恢复。
- **代价**：每次切换 ~1–数 μs，且污染 CPU 缓存（TLB、L1/L2 失效）→ 真正的"隐性税"。
- 衡量：`vmstat`/`pidstat -w` 看 `cs`（context switch）数；`async-profiler -e cpu` 看"是否大量时间花在内核切换而非业务"。

### 2.2 减少上下文切换的四条路
1. **无锁并发**：用 CAS / 无锁结构（ConcurrentLinkedQueue、LongAdder）避免争用导致的切换。
2. **CAS**：自旋重试替代挂起（高争用下需注意自旋开销，见第 7 章）。
3. **最少线程**：只配"刚好够"的工作线程（第 9 章线程池参数）。
4. **协程/虚拟线程**（JDK 21+）：**海量轻量任务由少量平台线程承载**，把"用户态调度"从 OS 手里拿回 JVM，切换成本极低。

### 2.3 死锁（与《实战》第 10 章互补）
- 四必要条件：**互斥、占有且等待、不可剥夺、循环等待**。
- 避免：① **锁顺序化**（全局定序，破坏循环等待）；② **超时 `tryLock`**（破坏"占有且等待"）；③ **一次性申请全部资源**。
- 诊断：`jstack`/`jcmd Thread.print` 能自动报告 Java 级 monitor 死锁。

### 2.4 资源限制
- 并发程序的吞吐上限由**最短板的资源**决定：CPU 核数、内存带宽、下游 DB 连接数、网络带宽。
- 例：CPU 密集任务开 1000 线程 ≠ 快 1000 倍，反而因切换崩；DB 连接池只有 20，开 200 线程也只是排队。
- 解法：**纵向池化**（连接池/线程池）+ **横向集群**（加机器）+ **异步化**（不阻塞等下游）。

## 三、版本演进

- **成书（JDK 7/8）**：协程思路停留在"Actor（Akka）/Green Thread"学术层；减少切换靠无锁 + 最少线程。
- **JDK 21 (2023)**：**虚拟线程（LEP 444）**让"海量轻量任务"真正落地——一请求一线程重新可行，且上下文切换成本从"OS 级 μs"降到"JVM 用户态 ns"量级。本书第 1 版叙述的"少用线程"被部分颠覆：不是"少用"，而是"用虚拟线程这种便宜的"。

## 四、经典论文 / 原始文献

- **JSR 133 / Manson-Pugh-Adve (POPL 2005)**——并发可见性的形式化（本章死锁/可见性讨论的理论底座）。
- **Ousterhout, "Why Threads Are A Bad Idea (for most purposes)" (1996)**——事件循环 vs 线程论战的一方（虚拟线程是"鱼与熊掌"的现代解法）。
- **von Behren et al., "Why Events Are A Bad Idea (for high-concurrency servers)" (2003)**——对上篇的反驳：线程模型在并发服务器上更优（虚拟线程印证此观点）。
- **Loom 项目文档 (JEP 444/425)**——虚拟线程设计。

## 六、常见误区 / 本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "线程越多越快" | 受上下文切换 + 资源限制；Amdahl 约束（《实战》11 章） |
| 2 | "死锁只能重启" | 用 `jstack` 定位 + 定序/超时预防 |
| 3 | "无锁一定减少切换" | 高争用下 CAS 自旋烧 CPU；需配合退避/分段 |
| 4 | "少用线程 = 性能" | JDK 21+ 虚拟线程让"多用便宜线程"可行，约束变成"平台线程/下游资源" |
| 5 | "加机器就能无限扩" | 受内存/带宽/DB 连接硬上限；要配合池化与异步 |
