## 一句话主题

第 3 章回答「我到底有什么数据、要搬什么进来」——一份数据资产盘点方法论；第 4 章回答「这玩意每月烧多少钱、怎么不失控」——2020 年 BigQuery 双计费模型的账本读法。两章合起来是立项（见 [01-入住BigQuery与仓库项目启动.md](01-入住BigQuery与仓库项目启动.md)）之后的第一笔尽调。

## Ch.3 All My Data：数据资产盘点

### 3.1 源系统普查（重构）

- 盘点四问：**数据在哪**（OLTP 库/SaaS/日志/文件/第三方）、**谁拥有**（业务 owner，治理章回收）、**多大规模多快变**（行数×字节×变更频率）、**给谁用**（消费者→报表优先级）；
- 结构谱系：强结构化（关系表）→半结构化（JSON/日志/CSV 带歧义）→非结构化（文档/图片，2020 年 BigQuery 只能存 GCS 指针，⚠️ 演进见文末）；
- 作者强调「先盘后搬」：清单外的表不要进仓库——范围失控是仓库项目失败头号原因（呼应 Ch.2 章程裁剪）。

### 3.2 装载模式预判（为 Ch.5/6 铺路）

- 决策树：新鲜度要求 ≤ 分钟 → 流式（Ch.6）；小时/天级 → 批量（Ch.5）；两者都要 → 批量补历史 + 流式追增量，以 MERGE/窗口收敛去重（Ch.8 养护节处理迟到数据）；
- 每源标注：主键/幂等键（防重）、水位字段（增量拉取游标）、敏感级别（Ch.14 策略标签的前置）；
- GCS 作为落地中转：BigQuery 装载天然以 GCS/Drive/Fusion 为源，盘点时把导出文件格式统一为 CSV/JSON/Parquet/Avro（⚠️ 转述，✅ 装载文档 https://docs.cloud.google.cn/bigquery/docs/loading-data-cloud-storage-csv 镜像 200）。

### 3.3 Schema 映射与质量基线（重构）

- 源 schema → 仓库 schema 的最小变形原则：改名/加 `loaded_at` 审计列/嵌套化（STRUCT 数组替代星型过度展开——BigQuery 嵌套列是其与经典 Kimball 建模的最大分歧，Ch.13 展开，方法论对位见 [../Building_the_Data_Warehouse/00-总览与阅读地图.md](../Building_the_Data_Warehouse/00-总览与阅读地图.md)）；
- 质量基线三板斧：行数对账（源 vs 仓）、空值率快照、关键指标抽样复核；Ch.5 装载后自动跑对账 SQL，是作者「仓库养护」理念的第一块砖。

## Ch.4 Managing BigQuery Costs：2020 账本读法

### 4.1 计费三向量（⚠️ 转述 2020 口径，数字仅作量级示意）

1. **查询·按需（on-demand）**：按扫描字节计费（2020 公开价约 $5/TB，前 1TB/月免费；本波无法核价历史页，具体单价标 ⚠️）；
2. **查询·包年（flat-rate）**：按槽位档位承诺（500 槽起步），扫描量与账单脱钩、并发受槽位约束；演进见 ✅ https://docs.cloud.google.cn/bigquery/docs/slots（镜像 200）；
3. **存储**：按字节-月计费；连续 6 个月未修改的表自动享受长期折扣（time-based 分层，无需人工归档）——✅ https://docs.cloud.google.cn/bigquery/docs/storage_overview（镜像 200）。

### 4.2 扫描量的四个旋钮（本章技术核心，重构）

- **列裁剪**：`SELECT *` 是账单加速器；只取所需列，列存引擎按列读取；
- **分区表**：日期分区 + `WHERE _PARTITIONTIME/分区列` 谓词下推，历史查询只扫目标窗口——✅ https://docs.cloud.google.cn/bigquery/docs/partitioned-tables（镜像 200）；
- **聚类表**：分区内按高选择性列（如客户 ID）排序聚簇，min/max 剪枝跳过数据块——✅ https://docs.cloud.google.cn/bigquery/docs/clustered-tables（镜像 200）；
- **结果缓存与物化视图**：24 小时结果缓存（按需下免扫描费）；物化视图对重复聚合直接省重算——✅ https://docs.cloud.google.cn/bigquery/docs/materialized-views-intro（镜像 200）。

### 4.3 事前-事中-事后三道闸（重构）

| 阶段 | 手段 | 2020 落点 |
| --- | --- | --- |
| 事前 | dry-run 估扫描字节、SQL 审查清单 | `bq query --dry_run` 返回 estimatedBytesProcessed |
| 事中 | 项目级配额、监控告警 | Cloud Monitoring 指标 + Billing Budget 告警（Ch.12 观测铺路） |
| 事后 | 账单归因、慢查询复盘 | INFORMATION_SCHEMA.JOBS 视图按标签/用户/表聚合字节数（⚠️ 2020 为 region 级信息模式，后演进为 region 前缀函数） |

- 标签归因：任务打 `labels=[('team','finance')]`，账单按标签拆——FinOps 雏形，2024–2026 已成行业标准（见文末）。

## 🔧 概念类比（非 BigQuery 平台行为）

DuckDB 1.5.5 本机实测「聚簇/有序性对扫描量的剪枝效应」——同一 Parquet 文件（400 万行×8 列，约 300MB，row group=12 万），仅 user_id 列的物理序不同：

```
E1 rand:   size=296MB row_groups=34 统计命中rg=34 query=9.3ms  rows=1
E1 sorted: size=310MB row_groups=34 统计命中rg=1  query=5.4ms  rows=1
```

- 乱序时按 user_id 点查需触碰全部 34 个 row group；按 user_id 排序后（≈BigQuery CLUSTER BY 的效果类比）min/max 统计把命中压到 1 个——**这就是聚类表省扫描费的机理**：剪枝依据是块级统计，聚错列=白付扫描费。⚠️ BigQuery 内部存储格式非公开 Parquet，块粒度/剪枝算法与其不同，本组仅类比「物理序→剪枝→账单」因果链。方法：`parquet_metadata()` 读列统计 + `time.perf_counter()` 计时，脚本 `D:\develops\tmp\dbwave_w8_bqdw\experiment.py`。
- 计费心智类比（承接 [01-入住BigQuery与仓库项目启动.md](01-入住BigQuery与仓库项目启动.md) 的 E3）：扫描量=账单字节数，DuckDB 侧可再验——`SELECT count(*) FROM parquet_metadata` 的 `total_uncompressed_size` 列即「若按字节计费的假想账单面」。

## 附：成本实验台与烧钱榜（自拟教学示意，⚠️ 非原书内容）

- **dry-run 实验**（示意命令，实机以当期 CLI 为准 ⚠️）：

```bash
bq query --dry_run --use_legacy_sql=false \
  'SELECT COUNT(*) FROM `proj.ds.events` WHERE created_at > "2020-01-01"'
# 返回 estimatedBytesProcessed —— 这就是账单预告单
```

- 同一条查询的三版对照实验设计（读者可在免费额度内自做）：`SELECT *` 全列版 / 只取两列版 / 加分区谓词版——记录三个 estimatedBytesProcessed 比值，亲手复现「4.2 四旋钮」的数量级差异；

## 核心概念速览（中英对照）

- **数据资产盘点** — Data Inventory：装载前对源系统的位置/所有权/规模/消费者的全量登记。
- **幂等键** — Idempotency Key：重复装载不产生重复行的业务键，流式 insertId 与批量重载的共同基础。
- **水位线** — Watermark：增量抽取的高水位游标字段（时间戳/自增 ID）。
- **按需计费** — On-Demand Pricing：按查询扫描字节付费，无承诺、波动大。
- **包年/承诺** — Flat-Rate：按月承诺槽位包干算力，扫描量与账单解耦。
- **槽位** — Slot：BigQuery 并发算力单位；承诺模式的计量对象。
- **长期存储折扣** — Long-Term Storage Discount：表 6 个月未修改自动降存储单价的分层机制。
- **列裁剪** — Column Pruning：列式存储只读查询涉及列，SELECT * 的反模式即源于此。
- **分区** — Partitioning：按时间列将表切成可跳过的块，历史查询的扫描量闸门。
- **聚簇** — Clustering：分区内按高选择性列排序，借助块级 min/max 剪枝。
- **结果缓存** — Results Cache：短期内相同查询直接返回既有结果、免再扫描。
- **试运行** — Dry Run：不执行仅估算扫描字节的查询预检。
- **成本归因标签** — Cost Allocation Labels：任务级标签把账单拆到团队/项目的记账维度。

## 最新演进与工业实践

- **计费模型换代（2023–2024）**：BigQuery Editions（Essential/Standard/Enterprise）+ 性能档位（Standard/Premium/Enterprise）成为新默认叙事，flat-rate/on-demand 二元被「容量 + 特性」矩阵取代；⚠️ 对应文档页（canonical `cloud.google.com/bigquery/docs/editions`）本波镜像实测 404、直连不可达（000），只作转述。槽位与预留的基础概念仍 ✅：https://docs.cloud.google.cn/bigquery/docs/slots、https://docs.cloud.google.cn/bigquery/docs/reservations-intro（均镜像 200）。
- **流式计费补丁（2024）**：默认流式配额（per-project 行速率限制）与 Storage Write API 统一了流式入口，写侧成本首次可与读侧同盘核算——✅ https://docs.cloud.google.cn/bigquery/docs/write-api（镜像 200）；2020 年 Ch.4 尚无此维度。
- **FinOps 工业化（2024–2026）**：大仓普遍以「账单标签 + INFORMATION_SCHEMA.JOBS + 成本异常检测」构成月度成本评审闭环；查询预算护栏（per-query bytes cap）进入平台原生能力；数据产品团队把「每千次报表扫描字节」列为工程 KPI。⚠️ 行业综述无单一权威 URL，以 Google Cloud FinOps 指南与产品文档转述为准。
