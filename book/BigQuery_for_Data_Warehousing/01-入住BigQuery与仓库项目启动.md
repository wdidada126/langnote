## 本章在本书中的位置

原书开篇两章解决「要不要搬、怎么立项」的问题：第 1 章把读者从自建数仓的心智模型迁移到 Google 全托管模型，第 2 章给出数仓项目本身的启动方法（干系人、章程、预算）。这两章几乎没有 SQL，是作者 Mark Mucchetti 全管理视角的定调章——本书骨架是「工程项目叙事」而非「API 参考」，这一点与同目录的 [../Google_BigQuery_TDG/00-总览与阅读地图.md](../Google_BigQuery_TDG/00-总览与阅读地图.md)（技术参考向）形成互补分工。

## Ch.1 Settling into BigQuery：从自建到托管的心智迁移

### 1.1 BigQuery 是什么（⚠️ 转述 + ✅ 文档）

- 全托管、无服务器的列式数据仓库：用户不管理集群、不分片、不设节点数；容量与并发由平台侧槽位（slot）体系承接。概览见 ✅ https://docs.cloud.google.cn/bigquery/docs/introduction（镜像 200 实测）。
- 存储与计算解耦：底层数据落在 Google 分布式文件系统上，计算层按查询临时拉起。存储侧机制转述见 ✅ https://docs.cloud.google.cn/bigquery/docs/storage_overview。
- 访问入口四件套：Web Console / `bq` 命令行 / REST API / 各语言客户端库；本书后续章节（Ch.10 调度、Ch.22 SDK）围绕这四者展开。

### 1.2 资源层级模型（2020 语境，⚠️ 转述）

- `组织 → 项目 → 数据集 → 表/视图`：数据集是权限与地理位置的锚点，表是计费与生命周期管理的基本单元。
- 与自建仓库的对位迁移：`实例≈项目`、`schema≈dataset`、权限模型从 GRANT 语句迁移到 IAM + 数据集访问规则双轨（详见 Ch.14 治理，本文件 08 号章文件）。
- 位置约束：数据驻留在选定区域，跨区联合查询在 2020 尚属早期能力（BigQuery Omni 是其后演进，见文末演进节）。

### 1.3 「入住」的行为清单（作者叙事要点的重构）

1. 用免费额度（每月 1TB 查询扫描 + 10GB 存储，⚠️ 2020 口径，其后已调整）先跑通最小闭环；
2. 把 GCP 项目结构与计费账户理清（财务导出、标签）——这是 Ch.4 成本管理的前置；
3. 确认网络与 IAM 身份体系（服务账号 vs. 个人账号），对应 Ch.22 的 Cloud SDK/认证铺垫；
4. 心态条款：**不要把 Hadoop/本地数仓的运维习惯平移过来**——没有节点要调、没有副本要管，要学的是「用量治理」。

## Ch.2 Starting Your Warehouse Project：立项方法学

### 2.1 数仓 vs. 数据集市 vs. 报表库（重构）

- 作者采用宽口径「数据仓库」= 面向分析的集中存储 + 治理 + 多消费者，而非仅 BI 报表后端；
- 与经典方法论的接榫：本节实际是 Inmon/Kimball 论战在云托管语境下的轻量重述，盘上对位见 [../Building_the_Data_Warehouse/00-总览与阅读地图.md](../Building_the_Data_Warehouse/00-总览与阅读地图.md)（Kimball 线）。
- 立项判据（重构自叙事）：数据源数量 × 消费者数量 × 合规要求三者任一超阈值才值得平台化，否则一个脚本 + 电子表格即可。

### 2.2 干系人与角色矩阵（重构）

- 三类核心角色：**数据工程**（装载/管道，对应 Ch.5–7）、**分析消费者**（查询/报表，对应 Ch.9、16–18）、**治理与财务**（成本、权限、生命周期，对应 Ch.4、14、15）。
- 作者的管理背景（30 年技术团队负责人，Springer 作者简介 ✅）使本节偏「组织设计」而非「技术选型」，这是本书区别于两本 O'Reilly BigQuery 册的底色。

### 2.3 项目章程与预算骨架（重构）

- 章程要素：目标、范围边界、数据源清单、成功度量、风险与退出条件；原书 Ch.23 给出一页 Sample Project Charter 模板（见 11 号章文件）。
- 预算双轨：按需（per-TB 扫描计费）起步 vs. 包年槽位承诺的拐点估算——2020 年时点作者建议年查询量稳定超过某阈值再谈 flat-rate，此结论已被 BigQuery Editions（2023）重构，见文末。
- 立项常见反模式（重构）：以「先存进来再说」立项而无消费者承诺；把流式当默认而非按需（Ch.6 的流式摄入有隐性成本）。

## 1.4 托管 vs. 自建：差异清单（⚠️ 转述口径的整理）

| 维度 | 自建列存仓库（2020 前主流） | BigQuery 托管模型 |
| --- | --- | --- |
| 容量规划 | 节点数/分片键/副本数人工定 | 槽位自动分配，容量弹性由平台兜底 |
| 索引 | DBA 建索引并维护 | 无用户索引；列裁剪+分区+聚类替代（Ch.13） |
| 升级/补丁 | 停机窗口工程 | 平台滚动升级，用户无感 |
| 计费心智 | 折旧+许可+人力 | 扫描量/槽位小时+存储字节三向量 |
| 故障域 | 磁盘/节点级 runbook | 区域级 SLA，行级一致性由平台保证 |
| 治理抓手 | 权限+审计日志 | IAM+信息模式视图+系统日志导出（Ch.12/14） |

- 表中「扫描量/槽位小时/存储字节」即 Ch.4 成本三角，立项期只要拿到这三条曲线就能做预算，比自建 TCO 模型简单一个量级——这是作者推荐小团队先按需起步的核心理由。
- 「无用户索引」常被传统 DBA 误读为性能失控：实际是优化责任从人转移到数据布局（分区表/聚类表）与写法（列裁剪），对位阅读 [../Snowflake_The_Definitive_Guide/00-总览与阅读地图.md](../Snowflake_The_Definitive_Guide/00-总览与阅读地图.md) 中微分区一节可见云仓共性。

## 2.4 立项风险登记册（重构自作者叙事线）

1. **成本失控风险**：按需模式下一条全表 JOIN 可产生数百美元账单——缓解：查询 dry-run（`bq query --dry_run`）估字节数入审批，呼应 Ch.4；
2. **技能错配风险**：团队会 SQL 不等于会云仓 SQL（Standard SQL 方言、嵌套列 REPEATED/STRUCT 是大石，Ch.13 展开）；
3. **供应商锁定风险**：管道代码绑定 GCP 服务（Dataflow/ PubSub）；缓解：转换层保持 ANSI 可移植、原始数据保留 Parquet 于 GCS——作者此立场在 Ch.5/7 再现；
4. **治理缺位风险**：先建表后补权限导致 IAM 补丁化，Ch.14 主张项目级策略先行；
5. **范围蔓延风险**：把机器学习、实时大屏全塞进一期——作者以章程一页纸裁剪（Ch.23 模板，见 [11-结论附录与项目章程.md](11-结论附录与项目章程.md)）。

## 🔧 概念类比（非 BigQuery 平台行为）

本机不可连 BigQuery，立项阶段的「扫描量级估算」用 SQLite 类比演示（临时件 `D:\develops\tmp\dbwave_w8_bqdw\experiment.py`）：

```
E3 db大小=15MB(4000x4096B) 无索引: ['SCAN ledger'] 24.9ms
E3 覆盖索引: ['SEARCH ledger USING COVERING INDEX ix_cover (account=?)'] 0.1ms 结果一致=True
```

- 30 万行 ledger 表：全表扫与覆盖索引的触达字节差一个数量级——类比「同一业务问题，查询写法的扫描量可差百倍」，立项估预算必须先估扫描剖面而非先问单价。⚠️ BigQuery 无用户可选索引，此差异由列裁剪/分区/聚类自动达成（Ch.13 展开），本组仅类比「扫描量=账单」这一计费心智。

## 核心概念速览（中英对照）

- **数据仓库** — Data Warehouse：面向分析主题的集中式存储层，与 OLTP 库分离，服务多类数据消费者。
- **托管服务** — Managed Service：平台方承担容量、可用性、升级与备份的运营模式，用户以用量换取免运维。
- **无服务器** — Serverless：无预置集群概念，计算按查询临时分配、按量计费。
- **槽位** — Slot：BigQuery 算力计量单位；按需与承诺模式的共同度量衡。
- **资源层级** — Resource Hierarchy：组织→项目→数据集→表的管理树，权限与驻留的载体。
- **IAM** — Identity and Access Management：GCP 统一身份与角色授权体系，叠加数据集访问规则使用。
- **项目章程** — Project Charter：一页纸立项合同，定义目标、范围、干系人、成功度量与风险。
- **干系人矩阵** — Stakeholder Matrix：按影响力×利益排布的项目角色分析工具。
- **免费额度** — Free Tier：每月一定扫描/存储额度内不产生费用的入门计费设计。
- **扫描剖面** — Scan Profile：查询实际触达的字节轮廓，按需计费预算的第一估算量。
- **数据集市** — Data Mart：面向单一部门的仓库切片，立项时与平台化仓库的边界要先行裁定。
- **驻留区域** — Data Location：数据集绑定的地理区域，合规与延迟的先决约束。

## 最新演进与工业实践

- **托管模型演进（2020→2026）**：BigQuery Editions（Essential/Standard/Enterprise）与性能档位（Standard/Premium/Enterprise，2023–2024 陆续 GA）取代 2020 年「flat-rate 三档」叙事；⚠️ 对应文档页在中国侧镜像 `docs.cloud.google.cn/bigquery/docs/editions` 本波实测 404（canonical cloud.google.com 域本环境 000 不可达），故本节仅作转述不给 ✅ 链。立项预算话术从「按扫描 vs. 包年槽位」变为「容量+特性组合选型」。
- **入住路径不变项**：资源层级（组织→项目→数据集→表）、IAM 叠加数据集访问规则、四件套入口（Console/bq/REST/客户端库）到 2026 仍成立，✅ 概览文档 https://docs.cloud.google.cn/bigquery/docs/introduction（本波镜像 200 实测）。
- **多中心与湖仓**：BigQuery Omni（多云查询）与 Lakehouse on BigQuery（2024 起 GA）扩展了「数据驻留」二元假设；本项目盘上湖仓线见 [../Data_Lakehouse_in_Action/00-总览与阅读地图.md](../Data_Lakehouse_in_Action/00-总览与阅读地图.md)。⚠️ 官方页本环境不可直连（cloud.google.com 全线超时实测记录），机制描述以镜像文档为准。
- **工业实践口径**：2024–2026 数仓立项普遍引入 FinOps 职能（成本归属标签、预算告警、季度容量复审），作者「章程先行」的方法论与之吻合；dbt/分析工程团队把「消费者承诺」落为 model 所有权清单，见 [../Analytics_Engineering_with_SQL_and_dbt/00-总览与阅读地图.md](../Analytics_Engineering_with_SQL_and_dbt/00-总览与阅读地图.md)。
