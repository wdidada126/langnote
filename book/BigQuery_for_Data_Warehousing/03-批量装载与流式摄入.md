## Ch.5 Loading Data into the Warehouse：批量装载工程

### 5.1 装载路径总览（⚠️ 2020 转述）

- **标准路径**：源系统导出 → GCS 对象（可 gzip）→ load job → 目标表。✅ 文档 https://docs.cloud.google.cn/bigquery/docs/loading-data-cloud-storage-csv；
- 支持格式：CSV、JSON（换行分隔 NDJSON 才能装载多行）、Avro（schema 自动继承）、Parquet、ORC；CSV 是「最大公约数」也是「歧义之王」（引号/编码/日期格式三件套必显式声明）；
- 入口三选一：Console 向导、`bq load`、`jobs.insert` API——批量装载走 **job** 而非直接 API 调用，异步、可轮询、可重试，这是与 Ch.6 流式的根本分野；
- 直连特例：Cloud SQL 备份桶直读、Google Sheets 临时表、BigQuery JDBC 连接器从关系库抽取（2020 时点属预览，⚠️）；外部数据联邦（External Data / Federation）让 CSV/Sheets/JDBC 可「不装先查」，作者态度：**联邦是试吃不是主食**，正式消费仍要落表。

### 5.2 作业参数与容错（本章操作核心，重构）

- `writeDisposition`：WRITE_TRUNCATE（快照重载首选）/ WRITE_APPEND（增量追加）/ WRITE_EMPTY；`createDisposition` 控制目标表自动建；
- 坏记录三道闸：`max_bad_records` 容忍度、跳过 vs. 整体失败、坏记录落表（后两种语义随版本演进，⚠️ 2020 以整体失败+人工排查为主）；
- schema 演化之痛：CSV 无 schema 携带能力，列序错位=静默脏数据——作者建议 **显式 schema JSON 文件入库管理**（Git 化的 DDL 是 Ch.15 变更管理的前奏），或优先用自描述格式 Avro/Parquet；
- 分区落位：装载时 `--time_partitioning_type=DAY` + 分区装饰器（partition decorator）`table$20200101` 精确覆写单日——历史修正只重写受影响分区，不动全表；
- 对账收尾：每个 load job 后跑 `源计数 vs 目标计数` 的断言 SQL（Ch.3 质量基线落地），失败则告警并保留 GCS 原件（GCS 生命周期规则设 7–30 天缓冲，⚠️）。

### 5.3 节奏设计（重构）

- 全量快照 vs. 增量抽取的取舍：小维表快照（幂等简单）、大事实表增量+水位、既大又乱的两段式（夜间批量补历史 + 高频小批追近段）；
- 「装载窗口」是被低估的产品约束：下游报表 8 点上班，装载链路 SLA 就要含导出/传输/作业三段预算——作者的项目管理经验在此章显形（与 Ch.10 调度呼应，见 [06-作业调度与无服务器函数.md](06-作业调度与无服务器函数.md)）。

## Ch.6 Streaming Data into the Warehouse：流式摄入语义

### 6.1 insertAll 直写（2020 主线，⚠️ 转述）

- `tabledata.insertall` JSON RPC：行级直写、立即可查（秒级可见）、**不另收查询扫描费**——流式入口本身 2015 年起免费，成本体现在下游查询与存储；
- 限额（2020 口径，⚠️ 数字以官方配额页为准）：单行约 1MB、单表/项目每秒行速率有默认配额，超限即 403/429——**客户端必须指数退避重试**；
- 幂等窗口：`insertId` 去重仅保证约 5 分钟内重发不重（best-effort，非 exactly-once）；作者给的重兜底方案：**业务键 + 下游 MERGE 去重**（技术预演 Ch.8/9，见 [05-仓库养护与查询开发.md](05-仓库养护与查询开发.md)）；
- 流的落位：流式行进入分区表的「当日分区」；高频微批写会推迟长期存储折扣的生效——流式不是免费的，账单在 6 个月后才显形（接 Ch.4 成本三角）。

### 6.2 管道选型三层（重构）

1. **裸 insertAll**：量小、格式简单、可接受至少一次——应用直埋或云函数代理（Ch.11）；
2. **Pub/Sub 缓冲 + 订阅推送 BigQuery**（2020 属新能力，⚠️ 预览转 GA 过程）：解耦生产速率、schema 自动建档——✅ https://docs.cloud.google.cn/pubsub/docs/overview；
3. **Kafka/自产流 → Dataflow 清洗 → BigQuery**：需要窗口聚合/侧输出/乱序处理时上重型武器——✅ https://docs.cloud.google.cn/bigquery/docs/streaming-data-into-bigquery 与 Dataflow 专章 [04-Dataflow托管管道.md](04-Dataflow托管管道.md)。

- 选型判据（作者口径重构）：**先问消费者要不要秒级**；多数报表天级足够，把流式当默认是给账单加戏——此立场与 Ch.4 一脉相承。
- CDC 补一句：关系库变更流（Debezium 类）在 2020 需自建 Kafka 链路；托管服务（Datastream）当时刚露面（✅ https://docs.cloud.google.cn/datastream/docs/overview 镜像 200，2020 预览），演进见文末。

## 🔧 概念类比（非 BigQuery 平台行为）

DuckDB 1.5.5 实测「分区裁剪=按装饰器只碰目标块」的因果（8 个 hive 分区 Parquet 文件，各 50 万行）：

```
E2 全分区(8文件)=5ms res=1998000000 | WHERE part=3=5ms res=249750000 裁剪后≈1/8 文件(盘上文件数=8)
```

- `WHERE part=3` 使聚合结果恰为全量的 1/8（249750000=1998000000/8），证明引擎只读了目标分区文件——类比 BigQuery 分区装饰器/分区谓词「单日重写、按窗扫描」的行为。⚠️ 小数据下两侧时延无差（5ms≈5ms），裁剪的收益在 TB 级才在时延与账单上显形，本组类比**语义正确性**（谓词→文件子集→结果子集）而非性能倍率。方法：`read_parquet('.../*.parquet', hive_partitioning=1)` + 结果对分验证。
- 承接 [02-数据盘点与成本管控.md](02-数据盘点与成本管控.md) 的 E1（聚类剪枝）：分区是「文件级跳过」、聚簇是「块级跳过」，两级剪枝叠加才是云仓扫描账单的控制阀。

## 附：装载与流式配方卡（自拟教学示意，⚠️ 非原书内容、非 BigQuery 实测）

- **批量装载配方**（示意 CLI，实机参数以当期 `bq help` 为准 ⚠️）：

```bash
# 快照重载单日分区：幂等三步
gsutil cp export_20200101.csv.gz gs://stage/proj/orders/
bq load --source_format=CSV --write_disposition=WRITE_TRUNCATE \
  --time_partitioning_field=order_date \
  proj.ds.orders\$20200101 \
  gs://stage/proj/orders/export_20200101.csv.gz \
  schema_orders.json
# 对账断言（Ch.3 基线落地）
bq query 'SELECT
  (SELECT COUNT(*) FROM `proj.stg.orders_raw`) = (SELECT COUNT(*) FROM `proj.ds.orders` WHERE _PARTITIONTIME="2020-01-01")'
```

- **流式 insertAll 最小语义卡**（转述 ⚠️）：单次请求体上限约 100MB/千行级批量、行内 `insertId` 短窗去重、成功响应≠落库可见（秒级最终一致）、403/429=配额信号必须退避——客户端伪码：

```python
rows = [{"insertId": r["event_id"], "json": r} for r in batch]
try: errors = client.insert_rows_json(table, rows, retry_ids=True)
except TooManyRequests: sleep_backoff(); resend()   # 指数退避是义务
```

- 迟到/乱序双兜底配方（Ch.8 预演）：`MERGE 目标 USING 去重视图 ON 业务键 WHEN 新到时间戳更大 THEN 覆盖`——配 Ch.6 的 last-write-wins 读视图，流式表即可安全重放；
- **装载方式决策表**（重构）：

| 场景 | 首选 | 备胎 |
| --- | --- | --- |
| 维表全量小 | 快照 WRITE_TRUNCATE | 外部表直查 |
| 事实大表日增 | 分区装饰器增量 | Dataflow 批量写 |
| 应用事件分钟级 | PubSub→BQ 订阅 | insertAll 直写 |
| CDC 行级变更 | （2020）Debezium+管道 / （2026）Datastream | 时间戳轮询 |

## 核心概念速览（中英对照）

- **装载作业** — Load Job：异步的批量导入对象，可轮询、可重试、带写入处置策略。
- **写入处置** — Write Disposition：WRITE_TRUNCATE/APPEND/EMPTY 三种目标表落位语义。
- **分区装饰器** — Partition Decorator：`table$YYYYMMDD` 形式定位单日分区的读写语法。
- **外部表联邦** — Table Federation：不复制数据直接查询 GCS/Sheets/JDBC 源的映射表。
- **坏记录** — Bad Record：解析失败的输入行；装载容错围绕其容忍度与去向设计。
- **NDJSON** — Newline-Delimited JSON：每行一个 JSON 对象的流式可切分格式，BigQuery JSON 装载的实际要求。
- **insertAll** — Streaming Insert：行级 JSON 直写 API，秒级可见、免扫描费、至少一次。
- **insertId** — Insert ID：流式行幂等键，仅在短窗口内提供去重尽力而为。
- **水位字段** — Watermark：增量批量抽取的高游标，与 insertId 同为防重防漏抓手。
- **流式配额** — Streaming Quota：行速率/字节速率默认限额，超限退避重试是义务而非选项。
- **Pub/Sub 推送订阅** — Push Subscription：以消息队列缓冲后投递 BigQuery 的解耦摄入路径。
- **CDC** — Change Data Capture：捕获源库行级变更的流，Debezium/Datastream 为两代实现。

## 最新演进与工业实践

- **摄入入口收敛（2023–2026）**：Storage Write API 于 2023-08 GA，成为流式写入的统一主干（append 流/批量写/BidiStream 三形态），传统 insertAll 退居兼容位——✅ https://docs.cloud.google.cn/bigquery/docs/write-api（镜像 200）；2024-11 起默认流式配额收紧并提供 per-project 豁免申请，2020 年「流式随便写」的口径已失效（⚠️ 转述）。
- **托管 CDC 成熟**：Datastream 2021 GA，MySQL/Postgres/Oracle → BigQuery 全托管流式复制，作者 2020 年手搭 Debezium+Kafka 的章节场景今天首先是 Datastream/DS 替代题——✅ https://docs.cloud.google.cn/datastream/docs/overview。
- **Kafka 直连**：Pub/Sub Lite Schema Registry 与 Kafka BQ 连接器生态补齐「第三条路」；BigQuery 侧 JSON 列原生类型（2022 GA）终结了「半结构化必先展开成列」的装载前置工序（⚠️ 转述，官方页本环境不可达）。
- **工业实践**：2024–2026 主流链路是 Dataflow Gen2/托管管道 + 分区表 + Storage Write API 的组合；「流式=账单延迟显形」（微批破坏长期折扣）被各云仓 FinOps 指南引用为通识。本册 Ch.5/6 的幂等-可重放-对账三角在 dbt 语境重写为 CI 数据合约，见 [../Analytics_Engineering_with_SQL_and_dbt/00-总览与阅读地图.md](../Analytics_Engineering_with_SQL_and_dbt/00-总览与阅读地图.md)。
