## 5.2 MapR Streams 的定位（⚠️ 转述本书描述）

书中描述的 MapR Streams 有四个卖点：

1. **Kafka API 兼容**：现有 Kafka 客户端代码可直接对接，迁移成本低。
2. **构建在统一存储之上**：与 MapR FS / MapR Database 共享同一分布式存储层，
   不需要为日志单独规划磁盘与副本容量。
3. **平台级多租户与安全**：以"票证（ticket）+ 挂载路径"式模型提供命名空间与访问控制，
   声称无需 ZooKeeper。
4. **广域复制（mirrors）**：平台内置跨集群/跨数据中心复制能力，服务于第 7 章的地理分布式主题。

## 5.3 核心架构分歧：复制日志 vs 共享存储

这是本章最有技术含量的一点，值得单独展开——**它比"选哪个产品"重要得多**。

| 维度 | Kafka 路线 | 共享存储路线（MapR 式） |
| --- | --- | --- |
| 数据放置 | 每副本各存一份完整日志（副本 = 独立磁盘） | 日志存于共享分布式存储，副本由存储层保证 |
| 磁盘放大 | 副本数 F → 存储 ×F | 存储层内部纠删/复制，应用侧只算一份 |
| broker 角色 | 有状态：既是计算又是存储 | 计算可更无状态，存储下沉 |
| 扩容 | 需分区迁移（数据搬运） | 理论上存储与计算可各自扩 |
| 故障恢复 | 副本切换 + 可能需重新同步 | 依赖存储层恢复语义 |
| 尾部延迟 | 副本不齐会拖慢写入 | 取决于共享存储的一致性代价 |

**2026 年的验证**：这张表描述的分歧不但没有消失，反而成了此后十年流平台演进的主线——
Kafka 的**分层存储（tiered storage）**、以及各云厂商"存算分离流服务"，
走的正是"把日志从 broker 本地盘搬走"这条路，也就是本书第 5 章主张的方向。
**读第 5 章的正确姿势是：把它当作"存算分离日志"的早期案例研究。**

## 5.4 平台选型的通用框架（本目录对第 5 章的重写）

把 2016 年的两个候选换成今天的任意候选，问题清单不变：

1. **兼容性与退出成本**：是否兼容开放协议？若供应商消失，客户端与运维知识能否复用？
2. **运维负担归属**：谁负责分区再均衡、副本不齐、磁盘水位、保留策略调优？
   自建 = 你负责；云托管 = 供应商负责但价格曲线不同。
3. **有序性与吞吐的真实上限**：单分区吞吐、可支撑分区数、再均衡停顿。
4. **保留与重放窗口**：能存多久？重放三年前的数据要付多少钱？
5. **跨地域能力**：是内建镜像，还是需要应用层双写或第三方复制工具？
6. **模式治理**：注册表是平台自带还是需要外部组件？
7. **可观测性**：消费者滞后、ISR 收缩、副本落后是否有开箱指标？
8. **语义能力**：幂等生产、事务、以及"精确一次生效"的落地路径是否完整？

### 🔧 D5 实测：日志压实的规模效应（概念类比，**非本书平台行为**）

压实是 5.2/5.3 都绕不开的能力（它决定"同一份逻辑状态要占多少磁盘"）。
用 DuckDB 1.5.5 量化：

```sql
-- 200 万条追加事件，只有 2000 个不同 key
CREATE TABLE lg AS SELECT i AS off, 'k'||(i % 2000) AS k, i AS v FROM range(0,2000000) t(i);
SELECT k, v FROM (
  SELECT k, v, row_number() OVER (PARTITION BY k ORDER BY off DESC) rn FROM lg
) WHERE rn = 1;
```

| 指标 | 实测值 |
| --- | --- |
| 原始日志行数 | 2,000,000 |
| 压实后行数 | 2,000 |
| **压缩比** | **1000×** |
| 压实计算耗时 | 0.03 s |
| 追加 1 条墓碑（`v = NULL`）后压实结果中值为 NULL 的 key 数 | 1 |

**结论**：压实把"存储与事件量成正比"变成"存储与状态基数成正比"——
这正是 5.3 表中"磁盘放大"一行的定量含义。墓碑实验验证了 02 章 2.4 的说法：
删除在日志里是一次**追加**，而不是移除。
**限度声明**：DuckDB 的 `row_number()` 是一次性批算，真实日志压实是**后台增量段合并**，
两者时间/空间曲线完全不同；本实验只类比"压实后的逻辑形态与规模"，**不类比压实的过程与代价**。
脚本：`D:\develops\tmp\dbwave_w8_starch\exp.py`（结果存 `results.json`）。

## 核心概念速览（中英对照）

- **Kafka 兼容** — Kafka-compatible API：以相同协议/客户端接口提供流服务，降低迁移与锁定成本。
- **统一存储层** — Converged/shared storage：日志、对象文件与宽表共享同一分布式存储底座。
- **副本磁盘放大** — Replication storage amplification：F 副本导致应用侧存储量 ×F 的代价。
- **存算分离** — Disaggregated storage & compute：把日志存储从 broker 本地盘下沉到共享/对象存储。
- **分层存储** — Tiered storage：热段留本地、冷段下沉廉价存储，以解耦重放窗口与磁盘成本。
- **广域复制** — Wide-area replication / mirrors：跨集群或跨数据中心异步复制日志的能力。
- **票证鉴权** — Ticket-based auth：以平台签发的凭据而非 ZooKeeper ACL 做访问控制的模型。
- **多租户命名空间** — Multi-tenant namespace：在同一集群内按路径/租户隔离主题与配额。
- **日志压实** — Log compaction：按 key 保最新值，使存储与状态基数而非事件量成正比。
- **墓碑** — Tombstone：以空值表达删除的追加型记录，删除在日志中不是移除。
- **退出成本** — Exit cost：更换流平台时客户端、运维知识与数据迁移的总代价。
- **再均衡停顿** — Rebalance pause：消费者组成员变化期间分区不可消费的窗口。
- **ISR 收缩** — ISR shrink：同步副本数下降，是持久性风险与写延迟上升的先导信号。
