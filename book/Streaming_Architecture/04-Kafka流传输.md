## 4.1 为什么是 Kafka：把 02 章的公理落到实现

02 章给出日志的四条公理（只追加 / 有序 / 可重放 / 多订阅）。本章的任务是看 Kafka
**用哪些具体机制**满足它们，以及为此付出了什么代价。

| 公理 | Kafka 机制 | 代价 |
| --- | --- | --- |
| 只追加 | 分区日志段（segment）文件顺序追加，永不原地改写 | 更新/删除只能靠压实策略近似 |
| 有序 | 分区内 64 位偏移量单调 | 全局有序要求单分区 → 并行度上限 |
| 可重放 | 消费者持有偏移量，可任意 seek | 需要足够长的保留期与磁盘 |
| 多订阅 | 每消费者组独立记录自己的偏移量 | 组数多时元数据与监控成本上升 |

## 4.2 主题 / 分区 / 偏移量：三个必须一次讲清的概念

- **主题（topic）**：逻辑分类，是生产者与消费者的命名契约。
- **分区（partition）**：物理并行单元；一个主题是 N 个分区的集合，**分区才是日志**。
  因此"主题的有序性"这个说法本身是错的——只有分区有序。
- **偏移量（offset）**：记录在**单个分区内**的位置。它不是全局序号，
  跨分区的偏移量互相不可比。任何"按偏移量做跨分区去重"的想法都是 bug 源。

**分区数决策**（02 章 2.5 的延续）：分区数决定消费并行度上界，且变更会破坏 key→分区 映射。
本章给出的经验法则是**按目标吞吐 / 单分区吞吐上界估算，再乘 2–3 倍余量**，
但强调这是 ⚠️ 与集群规格强相关的经验值，不可移植。

## 4.3 为什么顺序追加能撑起高吞吐

本章对 Kafka 性能的解释集中在三点（均为 ⚠️ 转述官方文档所述机制）：

1. **顺序 I/O**：磁盘顺序写的吞吐远高于随机写；把随机写变成顺序写是日志的根本红利。
2. **零拷贝**：数据从页缓存直达网卡，绕过用户态复制（sendfile 路径）。
3. **批处理与压缩在客户端做**：生产者把多条记录攒成一个批次再发送，
   摊薄了每次网络往返与 fsync 的固定开销。

**关键推论**：Kafka 的吞吐上限通常不在磁盘，而在**网络与分区数**；
这也解释了为什么"分区太少"是最常见的性能瓶颈。

## 4.4 复制与持久性：ISR 模型

Kafka 不用分布式共识协议复制每条消息，而用 **ISR（in-sync replica，同步副本集合）**：

- 每个分区有 1 个 leader 处理读写，F 个 follower 拉取日志。
- **只有 ISR 内的副本**才有资格被选为新 leader。
- `acks=all` + `min.insync.replicas ≥ 2` + 副本数 ≥ 3 是"已提交"语义的常见配置组合（⚠️ 转述）。
- **未进入 ISR 的副本**会被踢出，落后太多的 follower 需重新同步。

这里有一个本章着重强调的取舍：**ISR 牺牲了"任意副本可读"的灵活性，
换来了写入路径上不需要多数派投票的延迟优势。**

## 4.5 投递语义：at-most / at-least / exactly-once

本章把语义问题拆成"谁负责"：

| 语义 | 生产者 | 消费者 | 结果 |
| --- | --- | --- | --- |
| 最多一次 at-most-once | 发完即忘 | 先提交偏移量再处理 | 崩溃即丢，永不重复 |
| 至少一次 at-least-once | 确认后再报成功 | 处理完再提交偏移量 | 崩溃即重复，永不丢 |
| 精确一次 exactly-once | 幂等/事务 | 偏移量与输出同事务提交 | 语义等价于"恰好生效一次" |

**本章的核心洞见（也是全章最该记住的一句）**：
"精确一次"这个说法本身是误导性的——**网络里不可能保证一次一次地送达**。
可实现的是"**至少一次投递 + 幂等生效**"，效果等价于精确一次。
因此工程问题从"如何不重复发送"转成了"如何让重复无害"。

### 🔧 D3 实测：幂等重放达成"精确一次生效"（概念类比，**非本书平台行为**）

用 SQLite 3.45.3 验证"重复无害"这条路。构造 `src(p, off, k, amt)` 2 万条事件，
聚合表 `agg(k, total, applied_off)`，消费时按 (分区, 偏移量) 做水位去重：

```sql
INSERT INTO agg(k,total,applied_off) VALUES(?,?,?)
ON CONFLICT(k) DO UPDATE
  SET total = total + excluded.total, applied_off = excluded.applied_off
WHERE agg.applied_off IS NULL OR agg.applied_off < excluded.applied_off;
```

故意重叠重放（先消费 off∈[0,20000)，再消费 off∈[10000,30000)）：

| 方案 | 与真值的最大相对误差 |
| --- | --- |
| 朴素累加（无去重） | **0.384173**（重叠区间被双计，最高偏差 38%） |
| 偏移量水位去重 | **0.0**（完全一致） |

耗时 0.09 s。脚本：`D:\develops\tmp\dbwave_w8_starch\exp.py`（输出存 `results.json`）。
**限度声明**：这里用"单调偏移量"实现幂等，只在**同 key 的偏移量单调**时成立；
真实 Kafka 的多分区、乱序、跨 key 聚合场景需要事务或两阶段提交，
D3 类比的是"幂等消费"这一半，**不涉及 broker 侧实现**。
盘上对位（真实语义）：[../Streaming_Systems/05-精确一次与副作用.md](../Streaming_Systems/05-精确一次与副作用.md)、
[../Introduction_to_Apache_Flink/03-状态容错与恰好一次语义.md](../Introduction_to_Apache_Flink/03-状态容错与恰好一次语义.md)。

## 4.6 消费者组与再均衡

- **消费者组**是 Kafka 的负载均衡单位：组内每个分区只被一个消费者持有。
- 消费者数 > 分区数时，多出的消费者**空转**（这是最常见的容量误解）。
- 组成员变化触发**再均衡（rebalance）**：期间分区被回收再分配，
  再均衡停顿是流式作业延迟毛刺的主要来源之一（⚠️ 转述官方文档所述机制）。

**工程建议（本章原意的操作化）**：把再均衡频率当作容量指标看——
如果频繁再均衡，通常是消费者处理超时被判定死亡，而不是集群问题。

## 4.7 保留与压实：让日志同时充当表和流

- **时间/容量保留**：老段被整段删除 → 满足分析型高吞吐场景，重放窗口有限。
- **日志压实**：对每个 key 保留最新值，删除用墓碑表达 → 让主题成为"表的持久形态"。
  压实主题的语义就是 02 章的 KTable。

压实对存储规模的量级影响见 [05-MapR-Streams与平台选型.md](05-MapR-Streams与平台选型.md) 的 🔧 D5。

## 4.8 本章的"什么时候 Kafka 不够用"

作者在本章末尾（按其论证脉络）留下三个边界，2026 年看格外准确：

1. **Kafka 不做计算**：它是日志 + 分发。任何带状态的聚合、连接、窗口，
   要么用其自带轻量库，要么交给外部引擎——本书 05–06 章正是这么处理的。
2. **低延迟点查不是它的强项**：日志结构对"按 key 取最新值"需要额外的物化层。
3. **重放窗口 = 保留期**：若业务要重算三年，就得存三年（或把历史外移到湖仓）。

## 核心概念速览（中英对照）

- **主题** — Topic：生产者与消费者共享的逻辑命名契约，由若干分区组成。
- **分区** — Partition：物理日志与并行单元；有序性、复制、偏移量都以分区为单位定义。
- **偏移量** — Offset：记录在单分区内的 64 位位置，跨分区不可比。
- **日志段** — Segment：分区日志在磁盘上的切分文件单位，保留与压实以段为操作粒度。
- **ISR** — In-Sync Replicas：与 leader 保持同步、有选举资格的副本集合。
- **acks=all** — 全 ISR 确认：消息被 ISR 全部接收才算提交，是持久性配置的一端。
- **min.insync.replicas** — 最小同步副本数：低于该值时 leader 拒绝写入的保护阈值。
- **零拷贝** — Zero-copy：数据由页缓存直达网卡、绕过用户态复制的传输路径。
- **客户端批量压缩** — Client-side batching：生产端攒批后一次发送以摊薄固定开销。
- **消费者组** — Consumer group：组内分区独占、组间各自全量消费的负载均衡单位。
- **再均衡** — Rebalance：组成员变化导致分区重新分配的过程，伴随停顿与延迟毛刺。
- **at-least-once** — 至少一次：不丢但可能重复的投递保证，工程上的默认选择。
- **幂等消费** — Idempotent consumption：重复应用同一事件不改变结果，使"至少一次"等效"精确一次"。
- **日志压实** — Log compaction：按 key 保留最新值并留墓碑，使主题表达表的当前状态。
- **重放窗口** — Replay window：由保留策略决定的、可重新消费的历史长度。
