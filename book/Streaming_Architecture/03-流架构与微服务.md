## 3.1 本章的问题意识

微服务在 2015–2016 年已经从"要不要拆"进到"拆完怎么连"的阶段困境。本章的诊断是：
**绝大多数微服务失败不是拆得不对，而是连得不对**——一旦服务被拆成几十个，
它们之间的连接方式就决定了系统的可用性、可演进性与可观测性上限。
作者的答案是：**用流（日志）作为服务间唯一的数据交换介质。**

## 3.2 点对点集成的三重塌方

本章把 RPC/REST 直连的失败模式归为三类，逐条给出流式替代：

| 失败模式 | 机制 | 流式替代 |
| --- | --- | --- |
| **可用性耦合** | A 同步调 B，B 挂则 A 挂；调用链越长，联合可用度越低 | A 只写日志（本地追加即返回），B 上线后自行追赶 |
| **耦合的演进** | B 改接口/加字段需协调所有调用方 | 模式演进发生在日志上，旧消费者按自己认识的字段读 |
| **n² 集成面** | 每新增服务需与相关服务各建一条链路 + 各写一套重试 | 新服务只需订阅它关心的主题，链路数线性 |

**可用性耦合**是本章最有力的论证：若有向调用链上每环可用度 99.5%，
串 5 环就只剩约 97.5%——**微服务把"局部可用度"这个工程指标变成了"端到端可用度"这个产品指标**。
解耦（异步 + 日志持久）是唯一能打断这条乘法链的手段。

## 3.3 "共享数据库"是微服务的反模式，日志是它的解药

本章明确批评一种常见妥协：服务各自拆分了代码，却**共享同一个数据库**（用外键互相引用）。
后果是数据库成为隐性的强耦合点，任何 schema 变更都要全组织协调。

作者提出的替代模式：

```
服务 A（拥有自己的库） --写事件--> [日志/主题: a.orders] --订阅--> 服务 B（拥有自己的库）
                                                              --订阅--> 分析
                                                              --订阅--> 审计
```

要点：
1. 每个服务**只写自己的日志**，只读别人的日志；
2. 服务本地库与"写日志"之间必须有一致性协议（outbox / 事务性写出）；
3. 由此得到的性质：**数据库级隔离 + 数据级最终一致 + 零点对点调用**。

## 3.4 事件驱动的三个层次

本章隐含地把"事件驱动"分层，读时应区分（否则会把 C1 当成 C3 来实现）：

- **C1 事件通知（event notification）**：只说"某事发生了"，消费者需回查服务取详情。
  实现最省，但把可用性耦合又请了回来（回查即调用）。
- **C2 事件携带状态变化（event-carried state transfer）**：消息自带足够数据，消费者无需回查。
  本章明确推荐这一层，它是解耦与性能的最佳折中。
- **C3 事件溯源（event sourcing）**：领域对象的状态**只**由事件序列决定，命令被事件取代。
  最强也最重；本章的态度是"值得了解，但别作为第一站"。

**C2 是本章真正的技术主张**：它要求模式设计者把"下游需要知道的"写进事件，
这是对组织内契约治理能力的考验，也是 3.5 存在的原因。

## 3.5 模式（schema）治理：本章被低估的部分

一旦日志成为骨干，**事件模式就成了组织级的公共 API**。本章列出必须显式回答的问题：

1. **兼容性方向**：新增可选字段是向后兼容（旧读者忽略）还是向前兼容（新读者能读旧数据）？
   两者要求不同，实践中常需同时满足。
2. **序列化格式**：JSON 灵活但无强约束；二进制（Avro/Protobuf 一类）紧凑且可演进，
   但需要模式注册表这一新基础设施。⚠️ 本书时代 MapR/Kafka 生态对此尚无统一定论。
3. **模式注册表的所有权**：谁批准一次事件模式变更？这是组织问题，不是技术问题。
4. **删除字段怎么办**：注册表能挡住"改类型"，挡不住"语义漂移"——
   字段还在但含义变了，只能靠命名规范与文档。

## 3.6 流式骨干对可观测性的馈赠

本章一个常被忽略的论点：**当日志是唯一集成介质时，系统拓扑变得可枚举**。

- 主题清单 = 服务依赖清单（机器可读，可画出真实拓扑图）。
- 每主题的消费者滞后（当前偏移量 − 消费者偏移量）= 端到端延迟的直接指标，
  不需要在应用代码里埋点。
- 日志本身就是审计凭证：谁在何时以什么状态看到了什么，可重放复现。

## 3.7 本章与 2016 年主流叙事的分歧

2016 年前后"微服务"讨论的主流是**容器编排 + API 网关 + 服务网格**，
即关注"请求怎么路由"。本章刻意站在另一侧：**关注"数据怎么流动"**。
这个分歧后来被证明很关键——服务网格解决了 3.2 表格的第一行（重试/熔断/超时下沉到边车），
但对第二、三行（演进耦合、n² 集成面）无能为力，因为它们本质是**数据契约问题**而非**网络问题**。

## 3.8 落地检查表（本目录对本章的操作化重写）

1. 能否列出所有跨服务调用中，**响应时间不影响用户**的那些？它们应改为事件。
2. 每个服务是否有**自己独占的库**？若否，先解决这个再谈事件。
3. 每个"写库 + 发事件"的路径是否有 outbox 或等价保证？（无则会在崩溃时丢事件）
4. 事件是否达到 C2（自带状态）？若仍在回查，说明模式设计不足。
5. 是否存在模式注册表与变更审批流程？若否，第 6 个月起会出现静默破坏性变更。
6. 是否有"消费者滞后"的统一看板？若无，你无法在事故中判断影响面。

## 核心概念速览（中英对照）

- **可用性耦合** — Availability coupling：同步调用把被调方的故障按乘法传导给调用方。
- **端到端可用度** — End-to-end availability：链路上各环节可用度的乘积，微服务时代的真实产品指标。
- **事件骨干** — Event backbone：以服务间唯一数据交换介质形态存在的日志层。
- **n² 集成面** — n² integration surface：点对点集成下链路数随服务数平方增长。
- **每服务一库** — Database per service：服务独占其数据库，禁止跨服务外键引用。
- **outbox 模式** — Outbox pattern：在同一事务内把待发消息写入本地表，再由中继投递，保证原子性。
- **事件通知** — Event notification（C1）：只告知发生、需回查详情的事件层次。
- **事件携带状态转移** — Event-carried state transfer（C2）：消息自带下游所需数据，免回查。
- **事件溯源** — Event sourcing（C3）：状态完全由事件序列推导的持久化范式。
- **模式兼容性** — Schema compatibility：向后兼容（新代码读旧数据）与向前兼容（旧代码读新数据）两个方向。
- **模式注册表** — Schema registry：集中存放并校验事件模式、把关变更兼容性的基础设施。
- **语义漂移** — Semantic drift：字段名与类型未变但业务含义改变，工具无法检测的破坏性变更。
- **消费者滞后** — Consumer lag：主题当前偏移量与消费者偏移量之差，端到端延迟的直接度量。
- **服务网格** — Service mesh：把重试/熔断/可观测下沉到边车的网络层方案，不解决数据契约耦合。

## 最新演进与工业实践

**（1）本章的诊断在 2026 年成为共识，解法被重新分配**

"同步调用链导致可用性耦合"已是教科书内容。变化在于**解法分层**：
网络层的容错交给服务网格，业务层的解耦交给事件，数据层的同步交给 CDC。
本章把三者统一归给"流平台"，2026 年的实践把它们拆开了。

**（2）CDC 抢走了本章一部分地盘**

本章 3.3 的"服务 A 写事件给 B"，今天很多团队实际做法是：**A 只写自己的库，
Debezium 一类的 CDC 工具把 binlog 变成事件**。好处是应用零改造、不会漏发；
代价是事件形态退化为"表的物理变更"而非"领域事件"，需要额外的语义层收口。
这正是 [../Streaming_Databases/08-零ETL与近零ETL.md](../Streaming_Databases/08-零ETL与近零ETL.md)
讨论的主线，也是本书十年后最需要补写的一节。

**（3）模式治理已经产品化**

Kafka 生态的 Schema Registry、以及跨平台通用的 schema 约定（Avro/Protobuf/JSON Schema）
在 2020 年后成为默认配置。⚠️ 本会话未逐一核验各注册表当前版本行为，
仅登记方向；平台侧文档入口：<https://kafka.apache.org/documentation/>（✅ 200）。

**（4）"事件驱动微服务"的当代开源栈**

- 传输：Apache Kafka（✅ 官方文档 <https://kafka.apache.org/documentation/>）
- 编排层：⚠️ 各工作流引擎对"长事务 + 补偿"的支持差异较大，未在本会话核验
- 观测：消费者滞后指标 + 分布式追踪联动，2026 年已是可观测平台的标配项

**（5）本章的持久价值**

即便你完全不建 Kafka 集群，3.8 检查表的第 2、3、5 条（独占库、outbox、模式变更审批）
在任何"多服务共享数据"的系统里都成立。**这三条是本章脱离"流平台"语境后仍然有效的部分。**
若要继续追问"那到底要不要独立流平台"，请读
[../Streaming_Databases/07-混合数据系统的兴起.md](../Streaming_Databases/07-混合数据系统的兴起.md)
