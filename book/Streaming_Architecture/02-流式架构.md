## 2.1 一句话主张

**把系统中一切"发生过的东西"写成一条只追加、不可变、可寻址、可重放的日志，
让所有下游（服务、分析、模型、审计）都成为这条日志的消费者。**
这就是本书标题里的 "Streaming Architecture" 的全部含义——它先是一种**数据组织方式**，
其次才是一种**计算方式**。

## 2.2 日志（log）作为第一抽象

作者把日志的四条性质列为公理，后面所有工程结论都可由它们推出：

| 性质 | 含义 | 直接后果 |
| --- | --- | --- |
| 只追加（append-only） | 已写记录不被改写、不被删除（逻辑上） | 天然不可变审计凭证；写入路径无锁竞争 |
| 有序（ordered） | 分区内每条记录有单调偏移量（offset） | 消费者可用"偏移量"表达进度，断点续传平凡 |
| 可重放（replayable） | 任意消费者可从任意偏移量重新读 | 新消费者上线零回填工程；bug 修复后可重算 |
| 多订阅（publish/subscribe） | 一份数据、N 个独立消费进度 | 解耦：生产者不知道也不关心谁在消费 |

**关键洞察**：关系数据库的 WAL（预写日志）早就具备这四条性质，但从未被当作
**面向用户的接口**暴露出来。流平台的革命性不在技术新颖，而在**把内部日志提升为公共 API**。

## 2.3 流与表的对偶（stream ⇄ table）

本章给出本书最常被引用的一对概念：

- **流（stream）**：一系列**变更**（change），每条记录表达"发生了什么"。
- **表（table）**：流在某时刻的**快照**（snapshot），表达"现在是什么"。

二者互为对偶，可双向转换：

```
表 ← 折叠(fold/聚合) 流      # 把变更序列物化为当前状态
流 → 物化(materialize) 表
表 → 差分(diff/changelog) 流 # 两个快照相减得到变更序列（方向相反！）
```

这个对偶的工程价值：**同一份数据，事件驱动的消费者读"流视图"，点查/报表消费者读"表视图"，
两者由平台保证一致，不需要应用自己维护双写。**

### 🔧 D2 实测：快照差分推导 changelog（概念类比，**非本书平台行为**）

用 DuckDB 1.5.5 演示"表 → 流"这一方向，并验证它与真实 Kafka 的方向恰好相反：

```sql
CREATE TABLE s_old(k INTEGER, v DOUBLE);  -- (1,10)(2,20)(3,30)(4,40)
CREATE TABLE s_new(k INTEGER, v DOUBLE);  -- (1,10)(2,25)(4,40)(5,50)
-- insert
SELECT k,v FROM s_new WHERE k NOT IN (SELECT k FROM s_old);   -- → (5,50)
-- delete
SELECT k,v FROM s_old WHERE k NOT IN (SELECT k FROM s_new);   -- → (3,30)
-- update
SELECT n.k, o.v, n.v FROM s_new n JOIN s_old o USING(k) WHERE n.v<>o.v;  -- → (2,20→25)
```

实测结果：1 条 insert、1 条 delete、1 条 update，与人工核对完全一致。
**结论与限度**：差分需要**同时持有两个全量快照**，代价随表大小线性增长；
而 Kafka 的 KTable 是**反方向**——由 changelog 流压实物化出表，代价与变更量成正比、
与表大小无关。这正是"为什么需要专门的流平台而不是定时快照"的量化理由。

补充实验（ASOF JOIN 类比"按事件时间取版本"）：对一张 5 key × 5 版本的历史表做
`ASOF JOIN ... ON h.ver_ts <= q.qts`，查询 `(k=3, t=125)` 得到 `ver_ts=120, v=302`，
查询 `(k=4, t=100)` 得到 `ver_ts=100, v=400`——即"任意时间点的表视图"可以廉价地
从版本化日志中重建。这与 2.4 的"时间旅行"能力同源。

## 2.4 "时间旅行"与保留策略

因为日志保留了历史，系统获得两项免费能力：

1. **时间旅行查询**：任意 past 时刻的状态可由日志重放（或由压实表的版本列）重建。
2. **消费者追赶（catch-up）**：慢消费者不会阻塞生产者，只是偏移量落后；
   只要它落在保留窗口内，就能自行补齐。

由此引出**保留策略是架构决策而非运维细节**：

| 策略 | 语义 | 适用 |
| --- | --- | --- |
| 按时间保留（如 7 天） | 超出窗口的历史不可重放 | 事件量大、回填需求弱 |
| 按容量保留 | 保留最近 N 字节/条 | 成本刚性预算 |
| 日志压实（compaction） | 每 key 只保留最新值 + 墓碑 | "表"语义的流，状态后端 |
| 无限保留 | 日志即权威数据源 | 把日志当 system of record |

（压实与墓碑的量化效果见 [05-MapR-Streams与平台选型.md](05-MapR-Streams与平台选型.md) 的 🔧 D5。）

## 2.5 分区：并行度与有序性的唯一权衡点

日志必须切分成**分区（partition）**才能获得横向写入能力，但代价是：

- **分区内有序**，分区间**不保证全局有序**。
- 分区键的选择 = 业务实体选择。以 `user_id` 分区，则同一用户的事件有序、
  跨用户无序——多数应用要的正是这个粒度。
- **分区数一旦确定就难以更改**：改分区数会破坏"同 key 同分区"的映射，
  从而破坏依赖该映射的聚合状态。这是本章点名的**不可逆架构决策**之一。

## 2.6 与 Lambda / Kappa 的关系（本章的立场）

本章在讨论架构选型时把当时流行的两种范式摆出来：

- **Lambda**：批层（全量、准确、慢）+ 速度层（增量、近似、快）+ 服务层（合并视图）。
  优点是准确与实时兼得；缺点是**同一逻辑写两遍**、双份运维、双份 bug 面。
- **Kappa**：只留流一条路，需要"批"时就把日志重放一遍。
  优点是实现唯一；代价是**重放窗口受日志保留期约束**，且长历史重放耗时。

本书的立场可以概括为：**Lambda 的"双实现"是抽象缺失的补丁**。
一旦平台支持"同一算子图、有界/无界两种输入"（见 01 章 1.4），
批只是"重放日志的一段"，Lambda 的批层就退化为流层的一个特例。

## 2.7 流式架构不是什么（本章的负面界定）

作者用相当篇幅排除三个常见误解：

1. **不是消息队列**：MQ 的语义是"消费即销毁 + 点对点/竞争消费者"，
   日志的语义是"消费不销毁 + 多订阅各自进度"。把日志当 MQ 用会丢掉重放能力。
2. **不是 ESB**：ESB 的中心是**转换与路由**（智能管道），流平台的中心是**存储与分发**
   （笨管道 + 聪明端点）。前者把逻辑藏进基础设施导致不可测试，后者把逻辑留在消费者。
3. **不是"必须换掉数据库"**：日志负责"发生了什么"，事务库负责"当前允许什么"；
   二者是互补角色，不是替代关系。

## 核心概念速览（中英对照）

- **日志** — Log：只追加、有序、可重放、多订阅的记录序列，本书架构的第一抽象。
- **偏移量** — Offset：记录在分区内的单调位置，消费者用它表达进度并实现断点续传。
- **只追加** — Append-only：已提交记录不被改写；修正以"新记录"表达而非原地更新。
- **流表对偶** — Stream-table duality：流是变更序列、表是某时刻快照，二者可互相转换。
- **changelog** — Change log：由表状态变化导出的 insert/update/delete 事件序列。
- **物化视图** — Materialized view：由流持续折叠得到的表视图，查询时不再需要计算。
- **日志压实** — Log compaction：每 key 仅保留最新值加墓碑，使日志长度与状态量而非事件量成正比。
- **墓碑记录** — Tombstone：值为 null 的压实记录，用于把"删除"表达进日志。
- **保留策略** — Retention policy：决定日志可重放窗口的架构级参数，不是运维细节。
- **时间旅行** — Time travel：由日志重放或版本列重建任意历史时刻状态的能力。
- **分区** — Partition：日志的并行单元；分区内有序、分区间无序，且数量难以变更。
- **分区键** — Partition key：决定同一实体事件是否落入同一分区的业务字段选择。
- **Lambda 架构** — Lambda architecture：批层+速度层+服务层的双实现范式，本书的主要批评对象。
- **Kappa 架构** — Kappa architecture：只保留流一条路径、以重放替代批处理的范式。
- **笨管道聪明端点** — Dumb pipe, smart endpoints：转换逻辑留在消费者而非基础设施的设计取向。

## 最新演进与工业实践

**（1）流表对偶已成主流引擎的地基概念**

2026 年 Apache Flink 的 Table API/SQL 与 Kafka Streams 的 KStream/KTable DSL 都把 2.3 的
对偶写进了公开 API 命名。Flink 稳定版文档：<https://nightlies.apache.org/flink/flink-docs-stable/>
（✅ 200）。Kafka 官方文档的流处理与语义章节：<https://kafka.apache.org/documentation/>（✅ 200）。

**（2）"物化视图"从流平台外溢回数据库**

本章 2.3 的"表视图"能力，2024–2026 年出现两条分叉路线：
① 继续在流平台上做（Flink + Kafka + 状态后端）；
② 回到数据库内做增量物化视图（Streaming Databases 一派）。
第二条路正是 [../Streaming_Databases/04-物化视图.md](../Streaming_Databases/04-物化视图.md) 的主题，
也是本书出版十年后对流式架构最实质的修正：**很多团队发现他们要的是"始终新鲜的表"，
而不是"一个事件驱动架构"。**

**（3）湖仓把"日志"降级为表格式的一个属性**

Iceberg / Paimon 一类表格式用"快照 + 增量读"实现了 2.3/2.4 的大部分能力（时间旅行、增量消费、
模式演进），且不要求团队自建 Kafka 运维。盘上对位：
[../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md](../Apache_Paimon_Streaming_Lakehouse/00-总览与阅读地图.md)
