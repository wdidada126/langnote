## 1.1 本章要回答的问题

作者在第 1 章不做任何技术展开，而是先解决一个"立项辩护"问题：**为什么一家公司要把"流"
提升为架构的一等公民（first-class citizen），而不是继续把实时当作批处理的补丁？**
这一章的论证方式是"历史 + 痛点 + 反事实"，而不是"性能数字"。理解这一点，
才能理解为什么本书后面五章都在谈架构形态而非 API 细节。

## 1.2 数据处理的历史分期（本章主论证线）

书中把企业数据处理切成几个阶段，每一阶段的"主导抽象"不同：

| 阶段 | 主导抽象 | 数据形态 | 典型延迟 | 决策类型 |
| --- | --- | --- | --- | --- |
| 记录系统（system of record） | 表 / 主键 | 当前状态快照 | 事务级（毫秒） | 操作型 |
| 数据仓库 | 星型模型 / 维度 | 定期装载的历史切片 | 小时—天（T+1） | 描述型分析 |
| 大数据批处理 | 分布式文件系统 + 全量作业 | 不可变全量副本 | 小时 | 离线建模、报表 |
| 微批流（micro-batch） | 小批次的全量作业 | 短窗口切片 | 秒—分钟 | 近实时分析 |
| **流式架构（本书主张）** | **不可变日志 / 事件流** | **事件本身** | **毫秒—秒** | **在线决策、自适应** |

关键论断：**"延迟不是线性的改进，而是决策种类的跃迁。"** 当延迟从"天"降到"分钟"，
你只是把报表做快了；当延迟降到"事件发生的那一刻"，你才第一次有可能在**同一笔交易内**
改变结果（拦截欺诈、调整推荐、触发熔断）。这是"批 → 流"不可跨越的语义鸿沟，
也是本章为全书立论的地基。

## 1.3 微批是"披着流的皮做批"

本章对微批（把流切成 5 秒、1 分钟的小批次再跑批作业）持明确的批评态度，理由有三层：

1. **语义层**：微批的"当前状态"永远是批次边界的快照，不是事件到达瞬间的状态。
   对"必须在事件内做决定"的用例（风控授权路径），批次边界本身就是不可接受的延迟。
2. **运维层**：微批系统里，"批作业调度器 + 流式接收器 + 结果缓存"三套组件各自有
   独立的失败模型与延迟预算，端到端 SLA 由最弱一环决定。
3. **成本层**：为了压低批次间隔而无限加密批次，会让每批的固定开销（作业启动、
   元数据协商、结果落盘）占比升高——延迟降到某个点后，成本呈超线性上升。

## 1.4 "流是常态，批是特例"

本章最具纲领性的一句话可以概括为：**把批看作"一段有限长、已经全部到达的流"，
而不是把流看作"很多段小批"。** 这个视角反转带来三个直接后果：

- **同一套代码**：批与流是同一算子图的两种输入模式，不必维护两套逻辑（这正是
  Lambda 架构要付的"双实现税"）。
- **可重放性成为默认**：既然批只是"有限的流"，那么任何历史数据都能以流的形态重新喂进
  同一套处理逻辑——重放（replay）从"特殊运维动作"降级为"常规操作"。
- **状态与时间成为一等概念**：一旦承认事件可能乱序到达，就必须显式谈论
  "事件时间 vs 到达时间"与"水位线"。本书把这条留给了后续章节与同期文献。

> **系列互链**：这条"反转视角"在盘上有两个更严格的表述：
> [../Streaming_Systems/06-流和表.md](../Streaming_Systems/06-流和表.md)（流/表对偶的形式化）
> 与 [../Streaming_Databases/01-流式基础.md](../Streaming_Databases/01-流式基础.md)
> （从数据库侧看同一命题）。本书的独特点是：它把这条反转当作**架构**主张而非**语义**主张。

## 1.5 什么用例值得上流（本章的判据清单）

本章给出的判据不是"数据量大不大"，而是"决策是否随时间失效"：

1. **决策窗口 = 事件窗口**：授权、欺诈拦截、动态定价、告警抑制。错过即无价值。
2. **状态需要持续演化**：用户画像、模型在线更新、会话状态。批只能给"昨天的我"。
3. **多消费者解耦**：同一份事件要被风控、推荐、审计、数仓各自消费。
   用点对点集成会退化为 `n²` 条链路（此论点在第 3 章展开）。
4. **跨地域/跨系统的一致性传播**：只有"带时间戳的事件日志"能同时充当
   集成介质与审计凭证（此论点在第 7 章展开）。

反之，本章也明确列出不该用流的场景：纯历史归档分析、无实时诉求的 ETL、
以及"团队尚无能力处理乱序与状态"的情形——**引入流的运维复杂度必须有对价**。

## 核心概念速览（中英对照）

- **流式架构** — Streaming Architecture：以不可变事件流为系统主导抽象的架构风格，而非把事件流当作批处理的补充。
- **一等公民** — First-class citizen：指"流"在平台层拥有与表/文件同等的持久化、寻址与治理能力。
- **微批** — Micro-batch：把流切成固定小批次后用批引擎反复处理；延迟受批次边界与作业固定开销双重约束。
- **事件时间** — Event time：事件在真实世界发生的时间，区别于进入系统的时间（到达时间）。
- **延迟跃迁** — Latency regime shift：延迟降到事件窗口内时，可做的决策种类发生质变而非量变。
- **批是特例** — Batch as a special case of stream：把批理解为"有限长且已全部到达的流"的视角反转。
- **重放** — Replay：把历史事件按序重新灌入同一套处理逻辑，用于修 bug、回填与模型再训。
- **决策窗口** — Decision window：某类业务决策在事件发生后仍然有效的时长，是"是否上流"的核心判据。
- **点对点集成** — Point-to-point integration：服务两两直连的集成方式，规模上呈 n² 链路增长。
- **事件骨干** — Event backbone：以流平台作为系统间唯一集成介质的拓扑形态（第 3 章主题）。
- **速度层** — Speed layer：Lambda 术语，指对近期数据做近似实时处理的层，本书对其"近似"二字持保留。
- **系统记录** — System of record：拥有权威当前状态的事务型系统，与"事件日志"角色互补。
- **运维复杂度对价** — Operational trade-off：引入流式带来的状态/乱序/回放复杂度必须有业务收益匹配。
- **T+1** — Day-plus-one：批处理时代仓库装载节奏，指数据可用滞后一个自然日。

## 最新演进与工业实践

**（1）2016 → 2026：本章"动机论证"的哪些部分已经过时**

本章的动机在 2026 年已基本"胜利"，因此它的说服力反而下降——实时化不再是需要辩护的选项，
而是默认预期。需要更新的是**对手变了**：2016 年的对手是"微批 + Lambda 双实现"，
2026 年的对手变成"湖仓 + 变更数据捕获（CDC）+ 查询侧加速"这条更廉价的路径。

**（2）"流是常态，批是特例"已成为工业共识**

Apache Flink 的 DataStream / Table API 与 Apache Spark Structured Streaming 都采用了
"批流同一 API、批是有界流"的设计，正是本章纲领的实现。Flink 官方文档（稳定版）
对流/批统一与时间模型的表述见：<https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/time/>
（✅ 本会话 `curl -L` 返回 200）。Flink 架构总览见
<https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/flink-architecture/>（✅ 200）。

**（3）判据清单 1.5 在 2026 年的对应物**

- 判据 1（决策窗口 = 事件窗口）→ 今天的"实时风控 / 授权链路内决策"，工业上多以
  Flink + Kafka 或流式数据库承载；本书第 6 章是该判据的最早系统教材之一。
- 判据 2（状态持续演化）→ 在线特征（online feature store）与在线学习，
  2020 年后由 Feast 等开源项目标准化（⚠️ 项目细节未在本会话核验，仅登记方向）。
- 判据 3（多消费者解耦）→ 事件驱动架构（EDA）与 schema 注册表治理。
- 判据 4（跨地域传播）→ 本目录 07 章主题，2026 年由 Kafka MirrorMaker 2 /
  跨集群复制与 CRDT 存算分离方案承接（⚠️ 具体版本能力需查官方文档）。
