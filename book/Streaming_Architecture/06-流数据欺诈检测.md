## 6.1 为什么欺诈检测是流架构的"试金石"

欺诈检测同时具备 01 章 1.5 判据清单的全部四条，因此作者选它作为唯一深入案例并非偶然：

1. **决策窗口 = 事件窗口**：授权请求在几百毫秒内要给出放行/拒绝，事后发现毫无价值。
2. **状态持续演化**：欺诈手法每周变化，模型必须随数据漂移而更新。
3. **多消费者**：同一笔交易事件同时供风控、合规审计、营销画像、模型训练消费。
4. **跨地域**：收单行、发卡行、商户、风控中心常在不同区域（→ 第 7 章）。

**方法论价值**：如果一个架构在这四条下仍能工作，它在别的用例上大概率也能工作。

## 6.2 批式风控的结构性缺陷

本章先立一个对照面。批式（T+1 跑模型出名单）风控的三个不可修复缺陷：

| 缺陷 | 机制 | 后果 |
| --- | --- | --- |
| 决策已发生 | 模型输出晚于交易 | 只能事后追损，无法拦截 |
| 上下文丢失 | 授权路径上的实时特征（设备、地理位置、行为节奏）无法回填 | 特征分布与线上不一致 |
| 反馈延迟 | 欺诈标签需数周人工确认 | 模型更新周期被标签而非算法限制 |

**关键概念：训练-服务偏斜（training/serving skew）**。离线用批特征训练、
线上用实时特征打分，两条特征计算路径若不完全一致，模型效果会静默劣化。
本章给出的解法不是"更仔细地同步两套代码"，而是**只写一套特征计算逻辑，
批与流都从同一份事件日志重放得到**——这是 01 章"批是流的特例"在 ML 上的兑现。

### 🔧 D1 实测：追加式日志的确定性重放（概念类比，**非本书平台行为**）

"同一份历史事件重放两次必须得到完全相同的特征序列"是 6.2 方案的必要条件。
用 SQLite 3.45.3 建一张 20 万行的只追加事件表并验证：

```sql
CREATE TABLE log(offset INTEGER PRIMARY KEY AUTOINCREMENT,
                 p INTEGER, k TEXT, v REAL, ts INTEGER);
-- executemany 批量追加 200,000 行
SELECT count(*), min(offset), max(offset) FROM log;   -- 200000 | 1 | 200000
SELECT offset,k,v FROM log WHERE offset BETWEEN 1000 AND 1999 ORDER BY offset;  -- 重放两次比对
```

| 实测项 | 结果 |
| --- | --- |
| 20 万条追加写入耗时 | **0.35 s** |
| 同偏移量区间重放两次是否逐行一致 | **是（deterministic = true）** |
| 数据库层是否禁止 UPDATE 已提交记录 | **否**（可改写 → 不可变性是应用约定，非引擎保证） |
| 模拟按偏移量截断保留（删除 offset<50000）后剩余行数 | 150,001 |

**这张表里最有价值的是第三行**：关系库不会阻止你改写历史，因此
"训练数据不可变"必须靠**只追加的写入纪律 + 保留策略**来保证，
而不是靠"用了日志"这个事实。许多自称事件驱动的系统在这里悄悄失守——
用 `UPDATE` 修正历史标签，于是同一份训练集在不同时刻重放得到不同结果。
**限度声明**：SQLite 无分区、无消费者偏移量、无段文件，本实验只类比
"追加写 + 按位置重放"这一最小语义片段，不涉及任何 Kafka/MapR 行为。
脚本：`D:\develops\tmp\dbwave_w8_starch\exp.py`（结果存 `results.json`）。

## 6.3 流式模型必须回答的四个问题

本章把"把 ML 搬到流上"拆成四个工程问题，这个分解至今仍是标准表述：

1. **特征从哪来**：单事件特征（金额、商户类别）廉价；
   **聚合特征**（该卡近 1 小时异地交易笔数、该设备关联账户数）需要状态。
   → 状态规模 = 实体基数 × 窗口长度，这是风控系统的真实成本中心。
2. **标签何时到**：欺诈标签滞后数周。这意味着训练永远是"用旧上下文配新标签"，
   必须把特征快照随事件一起持久化（否则窗口状态早已被覆盖，无法重建训练样本）。
3. **模型如何更新**：增量更新（在线学习）vs 定期全量重训。
   前者响应快但易被异常期带偏；后者稳但滞后。**混合方案**（在线打分 + 离线重训 +
   影子模型对比）是工业主流。
4. **如何处置**：分数不是决策。真实系统是"分层策略 + 模型"——
   硬规则（黑名单、限额）在前，模型在中，人工审核在后。

## 6.4 概念漂移与模型的"半衰期"

本章强调：**欺诈模型的效果衰减不是 bug 而是对抗性系统的常态**。
攻击者会针对你的决策边界调整行为，因此：

- 模型性能指标必须按**时间分桶**观察，全局 AUC 会掩盖近期劣化。
- 需要"探索预算"：留出一小部分流量用于试探策略之外的行为，
  否则你只能观测到自己策略已过滤掉的那部分数据（**反馈闭环导致的样本选择偏倚**）。
- 特征分布监控（PSI 一类）应比模型指标更早告警。

## 6.5 从"流上打分"到"流上训练"

本章更进一步的主张：**把模型训练本身也看作流作业**。

- 训练样本流 = 特征快照流 ⋈ 标签流（**时间上的连接**，不是键上的连接）。
  这个连接的复杂度在于：标签到达时要能找到**当时**的特征快照，
  因此特征快照必须保留到标签平均到达时间之后。
- 评估也应在流上做：滚动窗口回测（walk-forward），
  禁止用未来信息预测过去（**时间泄漏**）。
- 模型版本应与事件偏移量绑定：记录"这条决策由哪个模型、在哪个偏移量上做出"，
  否则事后无法复现，也无法归因损失。

## 6.6 本章给架构师的三条硬结论

1. **风控是"状态密集"型流作业**：容量规划应按状态大小而非事件吞吐做，
   这与日志类主题的规划逻辑完全不同。
2. **特征计算路径必须唯一**：任何"离线一套 SQL、线上一套代码"的安排都会在
   半年内产生难以归因的效果差异（6.2 的偏斜）。
3. **不可变事件日志是 ML 治理的前提**：可复现性、审计、监管取证都建立在
   D1 验证过的那条最小语义上——**历史不被改写**。

## 核心概念速览（中英对照）

- **决策窗口** — Decision window：交易授权场景下分数仍有业务价值的极短时长。
- **训练-服务偏斜** — Training/serving skew：离线与在线两条特征计算路径不一致导致的静默效果劣化。
- **聚合特征** — Aggregate feature：需要跨事件累积状态才能算出的特征，风控的成本中心。
- **标签滞后** — Label delay：真实欺诈结果远晚于交易到达，决定特征快照的保留时长。
- **特征快照** — Feature snapshot：随事件持久化的当时特征值，用于事后重建训练样本。
- **在线学习** — Online learning：随事件增量更新模型参数，响应快但易被异常期带偏。
- **影子模型** — Shadow model：与主模型并行打分但不影响决策，用于安全评估新模型。
- **概念漂移** — Concept drift：输入或标签分布随时间变化，使模型效果按半衰期衰减。
- **对抗性系统** — Adversarial system：被预测对象会主动适应决策边界，欺诈检测的本质属性。
- **样本选择偏倚** — Sample selection bias：只观测到未被自身策略过滤的样本，导致反馈闭环失真。
- **时间连接** — Temporal join：按"标签到达时回溯当时特征"的条件连接，流式训练的核心算子。
- **时间泄漏** — Leakage：训练或评估中使用了预测时点尚不可得的信息。
- **滚动回测** — Walk-forward validation：按时间推进窗口重复"训练—预测"以模拟真实部署。
- **PSI** — Population Stability Index：特征分布相对基线的偏移度量，通常早于模型指标告警。
- **模型版本绑定** — Model-version pinning：把做出决策的模型版本与事件偏移量一并记录以支持复现。

## 最新演进与工业实践

**（1）本章的"特征路径唯一"主张已产品化为特征平台**

2019 年后，"离线/在线特征一致性"从架构原则变成独立基础设施（feature store 一类开源项目）。
其核心正是 6.2–6.5 的组合：统一定义、批流双写、point-in-time 正确性、在线低延迟读。
⚠️ 本会话未核验具体开源项目的当前版本行为，仅登记方向；
盘上对位：[../Streaming_Databases/03-实时数据服务.md](../Streaming_Databases/03-实时数据服务.md)。

**（2）"流上训练"的现实分工**

工业主流仍是**在线打分 + 离线重训**：流平台负责特征与决策，
训练保留在批引擎上（因为全量重训需要遍历长历史与全局交叉验证）。
这与本书 6.5 的激进主张相比是折中——**Kappa 式"训练也是流"在 ML 侧尚未成为默认**。

**（3）LLM 时代的风控变化（2024–2026）**

- 生成式模型使合成身份、文案与行为模式更难用规则覆盖，
  推动特征从"结构化统计"向"嵌入表示"扩展，进而要求流侧支持向量检索。
  盘上对位：向量库侧的检索语义见 [../Streaming_Databases/09-流式平面.md](../Streaming_Databases/09-流式平面.md)
  与系列中的向量书目（见 00 互链表）。
- 决策链路引入"模型 + 规则 + 人审"三层之外，出现"用大模型做解释与复核"的新层，
  但**授权路径内延迟预算未变**，因此大模型多在异步侧。
