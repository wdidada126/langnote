# 07 多重继承与类概念的精炼

> 对应原版 **第二部分第 12 章（多重继承）与第 13 章（类概念的精炼）**。
> 第 12 章是全书技术密度最高的"设计档案"：菱形布局、虚基类、this 调整、iostream 之战；
> 第 13 章把"类"从语法特征磨成语义契约（const 成员函数、静态成员、嵌套类、句柄类）。
> ⚠️ 小节归属未逐条核实，按主题重写。

## 核心概念速览（中英对照）

- **多重继承** — multiple inheritance（MI）：一个类同时继承多个具体基类；C++ 与 Java 路线分野的原点。
- **菱形问题** — diamond problem：两条路径共享底座时，成员归属与构造责任必须先回答"共享吗"。
- **虚基类** — virtual base class：声明"全图只留一份"的共享底座；代价是布局间接寻址与构造次序特例。
- **this 调整 / 调整块** — `this` adjustment / thunks：指向第二基类的指针要加偏移才能当派生类用——编译器在调用边界补这笔账。
- **主基类复用 vptr** — primary base 策略：单继承链上共享虚表指针槽位的实现选择（✅ Itanium ABI 文档化的定式）。
- **slicing** — 切片：按值拷贝派生类只留基类部分——"继承 + 值语义"的固有裂缝。
- **具体继承 vs 接口继承** — implementation vs interface inheritance：第 13 章给出的使用纪律（public 继承留给抽象基类）。
- **const 成员函数** — const member functions：逻辑常量性与位级常量性的第一次分裂（`mutable` 的前夜）。
- **句柄类** — handle classes：引用计数壳包住不可复制的核——"库能走多远，语言就跟多远"的样本。
- **嵌套类与友元** — nested classes & friendship：把"类概念"扩展为协作类型的可见性管理。
- **CRTP** — curiously recurring template pattern：不用虚表的"接口继承"替代形态（90s 命名 ⚠️ 词源，思想在类精炼语境下早熟）。
- **虚拟性之辩** — "virtuality considered harmful"论战：Herb Sutter 1999 年前后的文章把第 13 章纪律推向公共讨论（⚠️ 发表处引用请自行核对）。

## 本章地图

| 决策点 | 否决的备选 | 胜出的设计 | 长期代价 |
| --- | --- | --- | --- |
| 要不要 MI | 只许单继承 + 接口库（Java 早期路线） | 允许 MI，但"共享与否"必须显式（virtual） | 布局复杂、滥用案例多、教学负担 |
| 虚基类实现 | 每对象指针表（间接、GC 友好） | 偏移信息内嵌 + 最终派生类统一构造 | 与"布局即契约"的张力；ABI 细节多年不统一 |
| 第二基类成员访问 | 要求程序员手写偏移 | 隐式 `this` 调整（thunk/调用点修正） | 成员指针胖化、跨 ABI 复杂度显形（`05` 章） |
| 继承默认性 | 默认 virtual（Smalltalk 梦） | 默认非虚；virtual 显式 | "忘写 virtual"的教育成本永久化 |

## MI 线：问题空间与备选全景

- Simula 只有单继承；Clu 允许多实现绑定但禁子类型；Ada 的派生形式受限；
  Objective-C 走单继承 + 类别运行时——1980 年代末没有任何"值语义 + MI"的先例可抄。
- 需求真实存在：GUI 工具库（既"是可窗口部件"又"是可序列化对象"）与流库是两大推手。
- D&E 的切分：**实现复用该用组合（成员），子类型关系才用 public 继承**；
  菱形共享用 `virtual` 基类表达——把"要不要共享"从布局问题升格为语义宣告。
- 零开销原则的 MI 版：不用 MI 的人不付虚基类间接寻址的钱（主基类零偏移优化保留）；
  用的人不输手写（thunk 等价于手工偏移代码）。

**机制档案——虚基类布局（第 12 章招牌内容，大意转述）**：

- 非虚基类：成员按"基类优先"线性铺开；指向第二基类的指针到派生类指针的转换 = 编译期常量偏移。
- 虚基类：对象尾部放共享副本，各路径存"到副本的可达距离"；
  由此产生两条特例规则——虚基构造**先于**非虚基执行、且由**最终派生类**负责调用
  （绕开"每条路径各构造一次"的悖论）。
- vptr 策略：主基类与派生类复用槽位，其余基类独立 vptr——
  "成员函数指针在 MI 下可能变胖"的布局根因（✅ 各 ABI 文档可复核）。

🔧 菱形骨架（教学示意，不参与构建）：

```cpp
struct Shape   { virtual double area() const = 0; };   // 抽象接口角色
struct Colored { virtual void paint() {} };            // 正交能力
struct Icon final : Shape, Colored {                   // 非虚菱形：两份独立底座
    double area() const override { return 16.0; }
};
void by_shape(Shape& s);
void go(Icon& i) { by_shape(i); }   // 从 Colored 起点进来的调用要 this 调整——编译器在边界埋账
```

## 类概念精炼线（第 13 章）：把"类"磨成契约

同一时期，"什么才算一个类"被逐条钉死（本章的"语言哲学"部分）：

- **构造即不变式**：对象一旦可见即处于合法状态——析构/拷贝/赋值的义务由此派生（Rule of Three 的前夜）；
- **const 成员函数**：承诺"读不打扰"；逻辑常量性（对外行为）与位级常量性（内存镜像）的分裂，
  最终由 `mutable` 承认缓存/引用计数的合法地位（✅ C++98/03 补全）；
- **static 成员**：终结"类级数据借道友元塞文件静态"的时代；类内声明 + 类外定义的仪式为 ODR 服务（`10` 章）；
- **嵌套类/友元**：为句柄类、迭代器、代理等协作惯用法供给可见性管理；
- **抽象基类与纯虚**：接口角色的语法化——"有 vptr 但无实例"的类型定位。

Herb Sutter 后来"虚拟性只在接口"的论战（⚠️ 出处核对）不是新思想，
是把第 13 章的纪律推向公共共识；而值语义阵营（`unique_ptr` 不可复制、禁止切片的设计）
是其 2011 年后的工程化续篇。

## 著名案例：iostream 之战——MI 公众形象的分水岭

1990 年代初的老 iostream 层次（`ios` 虚基 + `istream`/`ostream` 分别继承 + `iostream` 菱形聚合）
把虚基类间接寻址、构造次序特例与链接复杂度一次性推给全体用户；
性能阵营（以 `printf` 拥趸与嵌入式用户为主）借题发挥"MI 有害"。
转折点：Stepanov/Jacobo 的"新流"提案以 `ios_base` + 模板解耦重写层次、
**放弃以继承为中心的组织方式**（✅ 事件骨架与两位提案人；月份细节 ⚠️）。
D&E 第 12 章对这场争论的直接回应（大意）：语言提供 MI ≠ 鼓励用 MI 建模一切；
把"机制可用性"与"建模正确性"分开，是 `02` 章规则 4 的最著名判例。
后果：此后 C++ 的主叙事变为"接口/实现分离靠抽象基类 + 组合"；
Go 的"少谈继承"是隔代回响（⚠️ 影响链不断言，仅作对照）。

## 最新演进与工业实践

- **值语义对 slicing 的反击**：`= delete` 拷贝（C++11 ✅）、`final` 标注（C++11 ✅）、
  CRTP 静态多态——三条路都是"继承 + 值"裂缝的工程化绕桥。
- **多态构造的补课**：C++20 起智能指针工厂齐套（make_unique C++14 ✅）；
  C++23 `deducing this`（✅ ISO 锚点）让基类工厂/CRTP 写法第一次免除模板仪式；
  cloning 惯用法仍靠约定——D&E 当年未解决项至今半开放。
- **concepts 改写"能力复用"**：`Colored` 式正交能力在 C++20 后优先用 concept + 自由函数建模
  （ranges 全面避开深继承 ✅ range-v3 文档），MI 的战场收缩到运行时插件/组件类层次。
- **工业界**：Google C++ Style/Chromium 约定"至多一个具体基类、其余纯接口、接口不持有数据"——
  D&E 纪律的条款化；COM 与 Qt 对象模型是 MI 布局复杂性长期共存的两个活体样本
  （qobject_cast 替代 dynamic_cast 的动机可作案例研究 ⚠️ 细节）。

## 常见误区

- 误区：「虚基类是防重名的语法糖」。它是**布局与构造责任的重新分配**——
  不理解"最终派生类统一构造"就上虚基类，等于持有未爆弹。
- 误区：「private 继承不算继承」。它是实现继承的合法载体（空基优化 EBO 的工具 ✅ 惯用法，
  常用于 allocator/compressor 压缩），第 13 章的 public/private 划界是语义宣告不是能力开关。
- 误区：「Java 弃 MI 证明 C++ 错了」。两边解决同一问题（能力正交复用）：
  C++ 选机制、Java 选约定（接口无实现 + 组合）——`02` 章"给手段不下道德判断"的对照实验，各有账单。
