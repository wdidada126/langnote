# 04 库与未来可能性

> 对应原版 **第一部分第 8 章（库）与第 9 章（展望）**。
> 第 8 章讲"C++ 用户实际靠哪些库活着"（C 标准库、iostream、工具类、数值与并发的生态扫描），
> 第 9 章是 1994 年写的"未来十年愿望清单"——今天读来是全书最好的一道**历史对答题**。
> ⚠️ 两章小节结构未逐条核实，按主题重写。

## 核心概念速览（中英对照）

- **语言与库的分界** — language/library boundary：机制进语言、策略进库——D&E 反复使用的切分刀（`02` 章规则 5 的执行机构）。
- **C 库继承** — inheritance of the C library：`<stdio.h>`/`<stdlib.h>` 是 C++ 出生自带的嫁妆，也是兼容性枷锁的一半。
- **流** — iostream：C++ 第一个"OO 味"的标准库；老流层次（虚继承菱形）是 `07` 章 MI 案例的主角。
- **流的两大职责** — formatting vs device abstraction：格式层设计过重（locale facet 虚函数舞蹈），设备层（`streambuf`）反而长寿。
- **容器/算法/迭代器** — containers, algorithms, iterators：Stepanov 三件套，1994 年进入标准草案（HP Labs 提案 ✅ 通行记载）。
- **具名流 vs 泛型组件** — streams vs generic components：同一问题（I/O 与序列抽象）的两代答案，胜负手是组合性。
- **国际化工具类** — internationalization：money/date/collate 的 facet 设计——"库层吸收语言教训"的例子。
- **数值与并发库** — numeric & concurrent libraries：D&E 时代只有第三方方案；标准并发到 C++11 才补上（✅ ISO 锚点）。
- **库孵化语言** — libraries as language probes：先在库/扩展里验证再进语言——C++ 演化的主通道（`12` 章全览）。
- **TR/TS 通道** — Technical Report / Specification：C++03 后新增的"库快速车道"（TR1 2005/07、随机数 TR、正则 TR ✅ 通行记载）。
- **附录的预言** — the 1994 wish list：GC 接口、模板参数约束、并发标准化、模块化编译、更安全转换……
- **std 前缀的生态位** — 标准库作为"最大的第三方库"：与 boost/abseil/folly 的共生竞争关系。

## 问题空间：薄库时代的三条出路

库生态薄 → 用户各写各的 vector/string/stream → 不可互操作。备选：

- **A. 语言钦定一套容器/字符串**（Java/.NET 路线）：互操作最强，
  但把赌注押在一次设计上，且容器进关键字意味着所有用户为所有假设付费（违反 `02` 章规则 2）——否决；
- **B. iostream 一统 I/O 与格式化**：当时正在进行；后来被证明格式层设计过重，
  在性能敏感场景全面失守（printf/sprintf/自定义格式化长存 ⚠️ 措辞）；
- **C. 泛型组件库路线**（STL，写作当年正发生）：容器 + 算法 + 迭代器以模板表达，
  互操作靠概念约束而非继承；第 9 章对它期待与保留并存（性能承诺取决于编译器内联质量——这一担忧
  在 2000s 后被优化器兑现）。

**取舍准则（库侧的三条）**：

1. 库快于语言演化（不动语法/ABI），所以新抽象先在库里试——`08` 章 range-v3 逻辑的源头；
2. 但**跨 ABI 与生命周期的约定**（所有权、错误处理、分配策略）迟早要语言级表达——
   智能指针、异常 RAII、allocator 的"语言化补票"皆由此来；
3. 库的设计错误比语言错误便宜一个数量级（可换实现、可并存）——
   这解释了委员会为何乐意让库先背锅（iostream → 新流的整段历史即证据）。

## 著名案例：第 9 章愿望清单的"对答案"环节

🔧 1994 年的愿望 → 实际落地（标准锚点按 ISO 版次核实）：

```text
模板参数约束（"concepts 前身"）   → C++20 concepts（机制回看 08 章）✅
垃圾回收的标准化接口              → 从未进标准；2026-09 时点仍无（C++26 有安全/hardening 方向 ⚠️）
并发与任务的标准模型              → C++11 线程/内存模型 ✅；协程 C++20 ✅；执行器（C++26 方向 ⚠️）
模块化的编译单元                  → C++20 modules ✅（载体论文 P1103R3，open-std.org 实测 200）
更安全的强制转换                  → named casts（C++98 ✅）+ constexpr 家族细分场景（见 06 章）
数值/并行通用库                   → C++17 parallel STL ✅；数学常数 C++20 ✅；linalg（C++26 方向 ⚠️）
字符串一等公民化                  → 未进关键字；basic_string 持续加厚 + string_view（C++17 ✅）
国际化/日期时间库                 → chrono 大扩展（C++20 ✅ 日历/时区，Hinnant 库孵化语言的样本）
```

这张对照表是全书"演化的不可预测性"最佳教材：**方向大多猜对，机制载体几乎全换**——
GC 之争转化为所有权语言化（unique_ptr），export 梦转化为 modules，
异常规范梦碎转化为 concepts/noexcept 两种新形态的约束表达。

## 最新演进与工业实践

- **库先行的常态化（2015–2025）**：fmt → `std::format`（C++20 ✅）；
  range-v3 → ranges（C++20 ✅）；GSL span → `std::span`（C++20 ✅）；
  tl::expected 等三家竞争 → `std::expected`（C++23 ✅）——第 8 章的"孵化"论成为标准流程。
- **TR 通道的现代变体与教训**：并行 TS（2015）→ parallel STL（C++17）但执行器模型在 C++20 被拆支架、
  改走 sender-receiver（C++26 方向 ⚠️）；网络 TS（2018）至今未入正式标准——
  孵化成功率的诚实统计：**约一半库在 TS 阶段死亡或变形**。
- **影子标准库的当代形态**：abseil（`absl::optional/variant/string_view` 先于/快于 std ✅ 公开文档）、
  folly（`Folly Expected/Dynamic`）、bloomberg bde——与 D&E 时代"第三方流库 vs iostream"结构同型；
  差异在于如今各家都写"到 std 的对齐策略"，反向确认了标准库的锚点地位。
- **包管理缺位**：第 9 章没预料到的是"最后一公里"（依赖与分发）问题——
  至今无标准包管理器（vcpkg/Conan 并立 ✅ 现状），"库即语言"的推论"包即语言"落空。
- **WG21 制度化回应**：LEWG 的设立（`03` 章）等于承认"库是标准的一半"——
  委员会工作重心从语法转向 API 设计评审是 2010s 后最大变化。

## 常见误区

- 误区：「iostream 是失败的」。它在格式化 I/O 上输了，但在同步控制与设备契约（`streambuf`）上长寿；
  `std::print` 与流互操作（✅ cppreference 可核）说明分层重估后仍有资产。
- 误区：「STL 进标准是委员会的胜利」。恰相反，它是**库通道绕开语言内耗**的案例——
  若当年容器进关键字，评审战会拖垮整个 C++98 时间表（`08` 章续谈模板阻力）。
- 误区：「标准库薄 = 语言落后」。核心克制是 `02` 章规则的兑现；真正的教训是
  **孵化通道必须制度化**（TR/TS/LEWG 皆由此生），民间 boost 时代靠个人英雄主义不可持续。
- 误区：「愿望清单落空 = 作者失准」。第 9 章落空的不是判断力而是载体选择——
  把"猜对方向"与"猜对机制"分开记分，才是读预测文本的正确姿势。

## 第 8 章库清单的读法（1994 年货架盘点，大意转述）

- **C 继承层**：`<stdio.h>`、`<stdlib.h>`、`<math.h>`——人人会用、人人嫌弃其类型不安全；
  它们的错误处理（返回码 + `errno`）与 C++ 异常体系的张力是 `09` 章双轨制的远因；
- **标准初生层**：iostream（格式 + 设备双职责的纠缠在此埋下）、工具类（`complex`、比特集等零星居民）；
- **第三方事实标准层**：数值计算（各厂商 BLAS/LAPACK 封装）、GUI 工具包（以类层次展示 MI 需求与灾难，`07` 章）、
  并发任务库（线程原语各家自造，`11` 章标准缺位期的众生相）；
- **刚进草案的新客**：STL 容器/算法/迭代器 + string——第 8 章的篇幅分配本身就说明作者的重视方向。

读法建议：把这份清单当"1994 年的依赖树"，逐条问"今天谁活着、被谁替代、走的是语言化还是库化路线"——
本目录 `12` 章的档案法在库史上一样好用。
