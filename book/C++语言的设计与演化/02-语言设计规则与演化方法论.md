# 02 语言设计规则与演化方法论

> 对应原版 **第一部分第 4 章（C++ 语言设计规则）** 及书末附录 A 的设计规则清单。
> 这是全书被引用最多的一章：把 D&E 前史（`01` 章）里"做事的直觉"提炼成"可执行的规则"。
> ⚠️ 附录 A 的规则条目编号与逐字措辞未核实，本文一律为**意译转述**，不伪造引文。

## 核心概念速览（中英对照）

- **零开销原则** — zero-overhead principle：不用者不付费；用者应不输手写——D&E 给出经典表述的第一版。
- **面向抽象的语言** — support abstraction, not built-ins：给自定义类型与内建类型同等的语法权利。
- **不强制使用** — don't force anyone to use anything：任何机制（含 OOP 机制）都不得是必经之路。
- **给定问题而非语法糖** — provide mechanisms for the problem：语言解决"怎么表达"，不裁决"该不该用"。
- **渐进式披露** — progressive disclosure：新手可只用子集，专家不被子集限制（"一个语言，多层使用"）。
- **兼容性优先** — compatibility with C：合法 C 程序应尽量仍是合法 C++，破坏须有强理由并逐个记档。
- **可移植性即静态性** — portability through static checking：编译期能抓的错误不留给运行时。
- **演化而非革命** — evolution in place：每版是超集；坏决策公开承认并用新机制温和替换（"deprecate, don't remove"）。
- **两套多态正交论** — overloading 处理"不同类型同名操作"，virtual 处理"同一抽象不同实现"，混用即灾难。
- **不给人虚假安全感** — no false sense of security：语言不假装拦住所有错误（裸指针、`union`、转换皆放行但要可审计）。
- **手册即宪法临时文本** — ARM as interim reference：标准化前，注释参考手册承担规则书角色（`03` 章）。
- **设计规则档案** — design rules catalogue（附录 A）：每条规则挂适用/违反案例，供未来决策举证引用。

## 问题空间：接力改造需要成文宪法

一门被多人接力改造的语言，如果没有成文规则，每个补丁都会重燃旧仗。
1980 年代末可选的治理方式：

- "独裁设计者"（Stroustrup 一人裁决）：可持续到有委员会之前，但不可扩展、不可问责；
- "委员会共识 + 无规则"：1990 年后的 ANSI/ISO 现实——D&E 写规则正是想给委员会一面镜子；
- "形式化先行"（定义 + 证明）：Ada 路线；D&E 明确不走——静态语义可以事后补齐，
  但"零开销"必须设计时兑现，先证明再实现会错过硬件窗口。

## 规则条文的骨架（均为大意转述，⚠️ 非原文措辞）

1. C++ 首先服务"必须同时搞定抽象与机器"的程序员，其次才是教学与美学；
2. 每个机制回答两问：不用它的人付什么费？用它的人比手写慢多少？——答不出即出局；
3. 用户自定义类型必须获得内建类型的全套权利（传值、运算符、作用域、常量性、重载）；
4. 不为"唯一正确用法"下道德判断：多重继承、goto、`union`、转换都在列——语言给手段，团队做决定；
5. 新机制必须能被旧机制的纪律保护：异常依赖析构、RTTI 依赖 virtual、模板依赖重载决议；
6. 与 C 的兼容是一票否决级默认，但**逐条可诉讼**——每次破坏都记进档案说明理由；
7. 静态检查优先：能在编译期表达的约束（类型、名字、常量性）不留给运行期约定；
8. 演化路径对坏决策诚实：公开承认、提供替代、让旧写法自然退役——删除是最后选项。

## 取舍准则的应用示例（本目录各章的"预言"）

- 规则 2 → 否决默认虚函数（`07` 章）、否决表驱动之外的每函数异常管理费（`09` 章）；
- 规则 3 → 运算符重载与转换函数（`06` 章）、模板对"自定义类型一等公民"的极端延伸（`08` 章）；
- 规则 6 → `03` 章标准化史里"要不要 RTTI"的拉锯方式：可以进，但必须零开销化实现；
- 规则 8 → `export`（`08` 章）与异常规范（`09` 章）的相反命运：一个拖十年才删、一个十年内删——
  说明"删除成本"由生态规模决定，不由规则文本决定。

🔧 规则落地的最小标本——"默认 virtual"之争的完整否决过程（教学示意）：

```cpp
struct B { virtual void f(); void g(); };
struct D : B {
    void f() override;      // C++11：忘写 virtual 但签名匹配 → override 编译期兜底
    // void g() override;   // 编译错误：B::g 非虚——静态检查兑现规则 7
};
// 否决案：若当年默认 virtual ——
//   1) 每个含成员函数的类都要 vptr，sizeof 契约与 C 布局兼容破产（违反规则 6）；
//   2) 每次调用间接跳转 + 内联失效（违反规则 2）；
//   3) slicing 依然存在（值语义问题不因默认虚消失）。
```

**演化方式的示范**：C++11 没有改默认值（那会革命化），而是加 `override` 把"忘写虚"降级为
可编译期检查的错误——规则 7 + 规则 8 的教科书式联合作战。

## 后果：规则的推论清单（C++ 诸"丑"的辩护状）

- 没有默认虚函数、`==` 不自动生成、GC 缺席、头文件文本包含、`explicit` 要手写——
  全部是规则推论，不是设计者没看见；
- 反面清单（规则执行失败项）：`export`（`08` 章）、动态异常规范（`09` 章）、
  老 iostream 层次（`07` 章）——规则能挡坏默认，挡不住"好意但未验证生态"的特性；
- 元教训：**规则系统防不住"未经生态检验的委员会善意"**——这是 D&E 之后三十年最稳定的历史观察。

## 最新演进与工业实践

- **规则的当代再生产**：WG21 提案模板事实上要求"问题→备选→取舍→兼容性"四段论，
  与本章章法同构；C++ Core Guidelines（[../C++CoreGuidelines解析.md](../C++CoreGuidelines解析.md)）
  是"设计规则"面向用户的 2010 年代翻版（Stroustrup + Sutter 主编，✅ GitHub isocpp/CppCoreGuidelines 存在）。
- **零开销与安全的拉锯（2020s 新风向）**：C++23/26 周期的安全议题（边界检查、lifetime profile、
  hardening 方向）在试探"规则 2 能否升级"：主流答案是 **opt-in 的 profile/工具层**而非默认付费
  （⚠️ 具体提案名与状态请以 WG21 会议记录为准，本笔记不复述未核实的 P 号）。
- **"deprecate, don't remove" 的松动**：C++17 移除动态异常规范与 `register`（✅ ISO 锚点）——
  委员会开始接受"付兼容性代价换语义一致"，这是与 D&E 时代最重要的气质差异（对照 `09` 章）。
- **工业界**：abseil/folly 的基线管理文档（abseil LTS 标签与 "live at head" 策略、folly 对
  C++17/20 的滚动跟进 ✅ 两库公开文档）是规则 8 的生态镜像：破坏性变更以"代际 + 迁移工具"方式分期兑付。

## 常见误区

- 误区：「零开销 = C++ 很快」。它是对**未用机制**的承诺；滥用 `std::function`、深虚链照样贵——
  "用了的不能比手写差"这半句才约束这一侧。
- 误区：「设计规则是法律」。它们是**举证责任分配**：违反不禁止，但要给全委员会一个交代。
- 误区：「有了规则就不会有坏特性」。见上方反面清单；规则的作用是让坏特性**死得可查**。
- 误区：「方法论只适用于语言」。D&E 式"档案化决策"同样是平台团队 API 演化的模板——
  对照 [../C++API设计.md](../C++API设计.md) 与 Lakos 的物理演化章节。
