# 09 异常处理的设计之争

> 对应原版 **第二部分第 16 章（异常处理）**。这是 D&E 中"争论史"写得最坦率的一章：
> 异常从 1980 年代末被激烈抵制（"开销！滥用！"），到 Release 2.0/3.0 的实现，
> 再到标准化时的妥协产物（异常规范）——作者把问题空间、备选与否决理由全部留档。
> ⚠️ 小节归属未逐条核实，按主题重写。

## 核心概念速览（中英对照）

- **异常处理** — exception handling（EH）：错误路径与正常路径在语法与执行流上分离的机制。
- **栈展开** — stack unwinding：throw 后按逆构造序调用局部对象析构，直到匹配 catch——"展开即析构"是 C++ EH 与值语义的接榫点。
- **RAII** — resource acquisition is initialization：D&E 时代定名的惯用法——资源寿命绑定对象寿命；异常安全的地基（没有它，EH 在 C++ 寸步难行）。
- **析构即 finally** — destructors-as-finally：C++ 不需要 `finally` 关键字的论证——清理职责唯一化为析构（D&E 论点的通行概括 ⚠️ 非逐字）。
- **terminate 策略** — `std::terminate`：未捕获异常的失败姿态（默认 abort）；vs 自动重启/自动 GC 的备选。
- **异常规范** — exception specifications（`void f() throw(A,B)`）：C++98 加入的事后约束；违约走 `unexpected` 复杂度黑洞 → C++11 弃用、**C++17 移除**（✅ ISO 锚点）。
- **noexcept** — C++11 的替代契约：编译期可判的"不抛承诺"，并参与优化与库决策（✅ ISO 锚点）。
- **零成本展开** — zero-cost/table-driven EH：表驱动元数据（DWARF `.eh_frame`/Windows `.pdata`）让"不抛时函数序言无管理费"；vs SjLj 每函数落点税（✅ 主流编译器现状）。
- **异常安全等级** — basic/strong/nothrow guarantee：D&E 之后成形的术语层（Cargill、Abrahams 等推动 ⚠️ 措辞）——对语言机制的二次工程化。
- **错误码 vs 异常** — error codes vs exceptions：可忽略性（返回码可被无视）与强制性（异常必须处理或继续传播）的取舍主线。

## 本章地图

| 决策 | 备选 | C++ 选择与理由 |
| --- | --- | --- |
| 要不要 EH | 不要（C 派）/ try+GC 兜底（Java 式）/ 有但析构不保证 | 要，且**展开必须走析构**——清理语义唯一化 |
| 未捕获怎么办 | 自动回收/重启进程/崩溃 | `std::terminate`：语言不做资源兜底，进程层负责 |
| 性能承诺 | 每函数设管理费的实现 | "不用者不付费" → 倒逼表驱动实现成为主流 |
| 错误类型 | 整数码 / 仅类层次 / 任意对象 | 可抛任意可拷贝对象；实践中多态异常类 + `what()`（✅ C++98 体系） |

## 问题空间：构造函数没有地方挂错误码

D&E 第 16 章的问题陈述（大意）：

- 构造函数**没有返回值可查**——"创建失败"要么抛异常、要么进两阶段初始化（`init()` 方法 + 合法/半成品双状态，一个永久侵蚀"构造即不变式"的民间补丁）；
- const 成员与引用成员**必须在初始化列表完成**，失败路径同样无路可走；
- 资源（锁、句柄、内存）在任意提前退出点上都要可清理——返回码方案让每个调用点手写梯子。

**备选全景**：

- A. 约定 + 返回码 + `setjmp/longjmp`：跳转**跳过析构**——在带析构语义的语言里等于制造泄漏机器，否决；
- B. Ada 式受控类型 + 异常：抽象正确，但其运行时（任务/GC）搬不进 C 的世界（`01` 章）；
- C. Java 将选的"默认 GC 兜底"：回收让"清理不全"的代价变小——C++ 没有这个后盾（`11` 章 GC 之争的镜像）；
- D. **异常 + 析构驱动的展开 + RAII 纪律**：胜出。
  关键洞察：把"清理"职责全数交给析构函数，于是**析构就是 finally**——
  不需要新语法，语言已有一块专职清理的构件。

## 著名争论留档：三阵线、一个失败品

**1. 性能阵线**。1980s–90s"支持异常但人人喊贵"：早期实现给每个函数加 try 包裹（设置落点），
即使从不抛也付管理费——直接违反零开销原则。工程答案是**表驱动 EH**：
正常路径不插入运行时指令，展开信息存于静态表、仅在真抛时查表回放。
代价换了口袋：代码段增大（元数据）、以及 JIT/动态生成代码环境需要登记元数据
（Go 1.21 恢复 C 栈穿越、Python 3.11 表驱动 EH 等邻国事件是其 2020s 回声 ⚠️ 各自成说不展开）。

**2. 规范阵线（`throw(A,B)` 的失败）**。意图"接口承诺可静态检查"，现实：

- 检查发生在运行期（违约 → `unexpected` → 多半 terminate）——静态收益为零；
- 与泛型天然冲突：模板函数无法列举用户类型可能抛出的全部异常——组合性毒瘤；
- 拖累优化：编译器不敢把"可能违约"的函数内联进承诺路径。
一个特性同时输掉 `02` 章规则 2 与规则 7 → C++17 移除（✅）。
替代品 `noexcept`（C++11 ✅）把承诺改为**可编译期判定、违约即 terminate、无中间机制**——极简方案的胜利。

**3. 哲学阵线**。异常是"常规控制流"还是"灾难通道"？
生态最终纪律：预期内失败走 `error_code`/`optional`，异常留给真异常（构造失败、不变式崩塌、
资源耗尽）——`std::expected`（C++23 ✅）即给前一半场景补的标准语法。

🔧 异常安全等级工作示意（教学代码，不参与构建）：

```cpp
void strong_push(std::vector<Widget>& v, const Widget& w) {
    Widget copy = w;      // 先做"可能失败且不留副作用"的一步
    v.push_back(copy);    // vector 自身保证：要么成功要么原样（strong guarantee 的地基）
}
void basic_example(std::vector<Widget>& v, const Widget& w) {
    v.push_back(w);       // 若 w 的拷贝构造中途抛出：不变量保持、元素数或已+1（basic guarantee）
}
// 析构 noexcept 化（C++11 起默认 noexcept ✅）：展开期析构再抛 = terminate——清理通道不容二次灾难
```

## 后果与后续史

- **RAII 从惯用法升为语法依赖**：`std::lock_guard`（C++11 ✅）→ `scoped_lock`（C++17 ✅）——
  锁、句柄、文件全面对象化；"谁在异常路径上活着"成为 C++ API 设计的默认问题。
- **移动语义与 EH 的重新定价**（C++11 ✅）：`vector` 扩容只在移动构造 `noexcept`（或可回退拷贝）时用它——
  `move_if_noexcept` 是"异常安全经济学"直接写进标准库利率的著名案例（✅ cppreference 条目存在）。
- **异常规范的移除路径**：`throw()` 空规范被 `noexcept` 取代保留至今（✅ C++11 起推荐），
  其余动态规范 C++17 除名——D&E 时代"设计外生长"的正式尸体处理，二十年周期。

## 最新演进与工业实践

- **禁异常阵营的制度化**：Google/Chromium/多数游戏主机 SDK 关异常（`-fno-exceptions`）但 **RAII 照用**——
  "不用 EH、坚持析构纪律"成为与 D&E 预言并行的第二主流；LLVM `Error/Expected`、abseil/folly 状态类型
  是返回码阵营的现代库化（✅ 各家公开文档）。
- **协程对异常传播的适配**：协程帧内未捕获异常的 terminate 时机、跨帧传播语义在 C++20/23 持续细化
  （⚠️ 细节以 WG21 状态与实现文档为准）。
- **安全视角**：异常路径的清理次序仍是内存/健壮性议题常客；C++ Core Guidelines 的
  R.*（recovery/error）条款集（✅ isocpp GitHub 存在）可视为对第 16 章的 2010s 批注。
- **运行时画像**：真抛的毫秒级成本（展开 + 符号化）让"异常只走冷路径"成为性能工程的通识；
  `-fno-exceptions` 的二进制收益测量与代价（库混链、第三方强制）是工业评审常见议题（✅ 实践通识）。

## 常见误区

- 误区：「异常很贵所以别用」。成本剖面是不抛近零、抛极贵——贵的是"用异常当循环"，不是"用异常"。
- 误区：「析构抛异常会触发回滚」。相反：展开期析构再抛 → terminate（✅ 标准行为）——析构默认 `noexcept` 正为此设。
- 误区：「`noexcept` 只是文档」。它是优化输入与库决策依据（`vector` 扩容选移动与否直接读它）——写错契约有性能/行为双重后果。

## 一场争论的三个生命周期阶段（本章的元教训）

1. **机制期（1987–1993）**：要不要异常？——以"构造失败无处报错 + 析构即 finally"定案；
   这一阶段赢了的是**表达力**（错误终于有了不污染返回值语法的通道）；
2. **契约期（1994–2011）**：怎么约束抛什么？——动态规范试验失败、`noexcept` 极简重建；
   这一阶段学费换来的认知：**契约必须编译期可判定、违约后果必须单一**；
3. **分区期（2011–今）**：哪些错误根本不该走异常？——expected/optional/error_code 与异常划界，
   sanitizer 与冷路径画像成为新的公共语言；这一阶段仍在进行（⚠️ 结论开放）。

三阶段恰好对应语言演化的通用形态："先给机制、再给契约、最后划地盘"——
`12` 章将看到模板（机制 → 概念契约 → ranges 地盘）与编译单元（include 机制 → export 失败 → modules 地盘）
走过同样的三段路。
