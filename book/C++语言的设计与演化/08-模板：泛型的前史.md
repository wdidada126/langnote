# 08 模板：泛型的前史

> 对应原版 **第二部分第 15 章（模板）**。D&E 写这一章时（1994），STL 刚进草案、
> 模板的编译模型争论正烈——所以它是名副其实的"泛型**前史**"：机制已定，文化未定。
> 本章按《抽象机制分册》读：通用编程的历史备选、实例化模型之争、约束之争、以及 `export` 之死。
> ⚠️ 小节归属未逐条核实，按主题重写。

## 核心概念速览（中英对照）

- **模板** — templates：以类型为参数的类/函数生成机制；C++ 泛型的核心语法。
- **通用编程** — generic programming：Stepanov 路线——算法抽象于容器之上，靠概念而非继承连接（第 15 章与之正式握手）。
- **实例化** — instantiation：模板到具体代码的展开；时机（隐式/显式）与场所（头文件/仓库）构成编译模型之争。
- **包含模型** — inclusion model：实例化要求定义可见 → 模板定义住头文件；简单但放大编译时间与宏污染（`10` 章）。
- **分离编译/仓库模型** — separate compilation with a template repository：`export` 关键字的野心与失败（✅ C++11 移除）。
- **具体化** — concretization：ARM 时代对 specialization 的旧称；显式全特化/偏特化的历史词根。
- **模板实参推导** — argument deduction：调用点免写 `<T>` 的搜索引擎；与重载决议的合流是复杂度之源（`06` 章）。
- **两阶段名字查找** — two-phase name lookup：非依赖名定义时查、依赖名实例化时查——1990s 末至 2000s 初决议的定案（✅ 标准文本早定，实现 2010s 才补齐）。
- **SFINAE** — substitution failure is not an error：推导失败从"报错"降级为"出局候选"——元编程的许可证（术语出处 ⚠️ Vandevoorde 90s 著述）。
- **模板模板参数** — template template parameters：把"模板当参数"；C++17 补齐使用裂缝（✅ ISO 锚点）。
- **概念** — concepts：对模板参数的语法/语义约束；"检查过早 vs 过晚"之争的 C++20 终点站。
- **鸭子类型的静态版** — duck typing at compile time：模板默认不检查接口——便利与诊断灾难同源。

## 问题空间：类型安全容器复用的四种历史答案

- 宏模板（`#define` 生成类型）：无类型检查、无作用域、错误信息天书——C++ 模板正是为替代它而生（`10` 章预处理器批判的正面）；
- `void*` + 约定：一次实现、处处不安全（`const` 丢失、拷贝语义无从表达）；
- 继承基容器（Smalltalk/早期 Java 集合）：向堆指针付费、切片/装箱两难——值语义语言特有的痛（`05` 章）；
- Ada 泛型包：编译期重编译式泛型 + 实例化形参检查——D&E 第 15 章的主要对标与部分借鉴对象（约束思想的前身）。

**设计决策的三条准则（大意转述）**：

1. 模板必须**不牺牲内联与布局控制**——生成代码等价手写（零开销原则在泛型上的应用）；
2. 模板参数**默认不做接口检查**：编译期只保证"能编译"、不保证"该概念"——
   代价（诊断灾难、约束缺失）直到 C++20 concepts 才收回；这是本章与 `02` 章呼应的最大悬案；
3. 实例化模型取"包含模型 + 可选显式实例化"：链接期靠弱符号合并去重——
   平台不承担"仓库"这种新基础设施的运维责任（与 Ada 路线分野的务实理由）。

## 著名案例：`export` 之死——"委员会通过但生态拒绝"的标本

`export` 承诺"模板定义可藏进实现文件，编译器经仓库复用实例化"。失败因果链：

- 需求侧错位：真正想要它的是编译时间焦虑，但它省的是"源代码可见性"而非编译工作本身；
- 实现生态分裂：EDG/Borland 做过，主流厂商未跟进（`03` 章 vendor dynamics 的裁决时刻）；
- 语义黑洞：跨 TU 的实例化复用与增量编译/调试信息模型冲突不断；
- 文化反噬：模板元编程兴起后，"编译期计算需要定义可见"成为**反需求**（`12` 章 constexpr 谱线的伏笔）。

结局：C++11 移除 `export`（✅ ISO 锚点）。D&E 亲述的教训在 2000s 完整应验：
**语言机制的可行性 ≈ 语义 × 实现生态 × 库用法，三者乘积，缺一即零。**

🔧 同一泛型需求的三代写法（教学示意，不参与构建）：

```cpp
// 1994：朴素模板——误用在实例化深处报一百行错
template <class T> T my_max(T a, T b) { return b < a ? a : b; }

// 2003–2017：SFINAE 手写约束（报错仍晦涩；traits 全家桶时代）
template <class T>
typename std::enable_if<std::is_integral<T>::value, T>::type
my_max2(T a, T b) { return b < a ? a : b; }

// C++20：概念——当年"检查时机之争"的终局写法 ✅ std::integral 为标准概念
std::integral auto my_max3(std::integral auto a, std::integral auto b) {
    return b < a ? a : b;
}
```

## 机制补遗：两阶段查找为什么重要

- 阶段一（定义时）：非依赖名照常解析——抓拼写错、让编辑器/工具能在不实例化的情况下理解代码；
- 阶段二（实例化时）：依赖名（挂 T 的）才查找——此时 ADL（`10` 章）接管用户类型的关联函数（`swap`、`begin`）。
它同时兑现了 `02` 章规则 7（静态检查优先）与规则 5（与既有查找体系可组合），
但 1990s 多数编译器为"兼容性便利"长期违规（在定义处全查/在实例化处全查两个极端游走），
2002 年前后的 DR 拉锯与 GCC/EDG 的合规竞赛才把文本变成现实——
**语言标准与实现生态的十年时差标本**（`03` 章滞后带的延续）。

## 最新演进与工业实践

- **概念的正名全过程**：Dos Reis & Stroustrup 给出形式规格（POPL 2006 论文，
  DOI 实测：<https://doi.org/10.1145/1111037.1111064>）→ C++0x 草案收录 →
  2009 年前后被移出（语义欠账 ⚠️ 措辞从简）→ concepts-lite TS（2015–2017 ✅ 发布为 ISO TS）→
  **C++20 concepts 进标准**（✅ ISO 锚点）。
  判决式总结：**晚检查保留为默认，早检查降为可选层**——D&E 之争以"两个都要"收场。
- **ranges 是概念的第二大客户**：range-v3（Niebler 等）→ C++20 ranges（✅）；
  约束让诊断可读性第一次成为可验收的工程指标。
- **modules 接住 export 未竟之事**：C++20 modules（✅；载体论文 P1103R3 open-std.org 实测 200）
  用"语义分区 + 头单元"解决编译放大，而非"实例化仓库"——同一问题换轴解答（`10` 章续谈）。
- **constexpr 收编元编程**：MPL 时代（`../C++模板元编程.md` ✅ 库史实）的 traits/整数序列仪式，
  如今大半由 `if constexpr`（C++17 ✅）、`consteval`（C++20 ✅）与变参折叠（C++17 ✅）承担——
  模板的"图灵完备副作用"被驯化为受控的编译期执行语言。
- **工业实践**：概念红利按编译器代际发放——GCC 10+/Clang 10+/MSVC 16.8+ 才有可用 concepts（✅ 公开支持矩阵，
  精确版本线 ⚠️ 使用时复核）；abseil 的 `ABSL_OPTION_USE_STD_...` 系列把"C++17/20 择路"做成构建开关，
  是库层消化泛型新机制的标准姿势。

## 常见误区

- 误区：「模板 = 参数化类型」。模板还是编译期程序（实例化即求值）——1990s 末元编程的"发现"
  是语言副作用，D&E 写作时无人预见；concepts 因此不只是语法糖，而是给类型系统补的欠账。
- 误区：「concepts 取代了 SFINAE」。`requires` 改善表达与诊断，底层候选淘汰语义仍是 SFINAE；
  存量 trait 库继续服役是理性选择而非落后。
- 误区：「两阶段查找是 C++20 新规」。C++98/03 文本早已定案——见上节"时差标本"。
