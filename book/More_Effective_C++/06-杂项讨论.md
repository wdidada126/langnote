# 第 6 部分 杂项讨论（Miscellany，Item 32–35）

> 对应英文原版 Part "Miscellany"（条目英文名已核实自 Addison-Wesley/InformIT 官方目录页）：
> Item 32 Program in the future tense；Item 33 Make non-leaf classes abstract；
> Item 34 Understand how to combine C++ and C in the same program；Item 35 Become a student of the language。
> 四条共同的气质是"元建议"：不针对某个语法特性，而针对**演化、复用边界与学习方式**。
> 中文部分名「杂项讨论」沿用单文件大纲 [../More%20Effective%20C++.md](../More%20Effective%20C++.md) 的叫法。

## 核心概念速览（中英对照）

- **面向未来编程** — program in the future tense：假设需求会变，把"改一处不震全身"当作设计目标。
- **编译依赖最小化** — minimize compilation dependencies：用前置声明 + handle-body（pimpl）把"实现变更"挡在头文件之外。
- **非成员非友元函数** — non-member non-friend functions：不增加耦合面却完成同样工作，封装性反而更好。
- **静态初始化顺序不定** — static initialization order fiasco：跨编译单元的全局对象初始化顺序无定义。
- **非尾端类** — non-leaf class：继承树中间节点；书中主张中间节点应为抽象类。
- **语言混编** — mixing C and C++：链接名（name mangling/`extern "C"`）、对象布局假设、异常边界、堆配对四道关卡。
- **语言学徒** — student of the language：把标准文本、期刊与委员会动态当作日常读物学习习惯。

## 动机：1996 年的焦虑——标准将至、C 永生、语言会长大

这部分写于 C++98 定案前夜，Meyers 的三个担忧全部押中了历史：
类库要跨版本演化（Item 32）、继承体系是软件产品线（Item 33）、C++ 必须与 C 长期共存（Item 34）、
以及"本书之外还有标准"（Item 35）。四条评论是他在书末给读者的"十年后仍然有效"的那部分。

## 机制精讲

### Item 32：三个"为变化留余量"的具体手段

1. **编译依赖最小化**：客户代码只依赖接口所在的头；把易变成员挪进实现类，本体只持一个指针
   （handle-body / pimpl——Item 28 技术的正式应用）。收益不是"看起来整洁"，而是
   **重编译图**从"一人改、全村编译"缩到实现文件自编译。
2. **优先非成员非友元**：能用公开接口完成的功能就别做成成员——成员函数访问 private 数据的
   **特权面**越大，将来数据表示改动波及的函数越多。Sutter 的 "Minimize Encapsulation"
   （《Exceptional C++》第 71 条语境）把这条推成了教科书原则 ⚠️ 章号未逐字核实。
3. **别赌静态初始化顺序**：跨编译单元的命名空间级对象构造顺序无定义，`extern` 一个 T 的
   全局构造等于埋雷。解法：把全局换成"函数内局部静态"（Meyers Singleton 的原型），
   初始化时置于首次使用点。

🔧 三个手段的最小骨架（教学示意，未实测）：

```cpp
// (1) pimpl：头文件里只剩一个指针，Widget 的实现改动不再触发客户重编译
class Widget {
    struct Impl;                       // 前置声明
    std::unique_ptr<Impl> pimpl_;      // 或裸指针 + Item 28 的手工句柄
public:
    Widget();  ~Widget();              // 析构/构造的定义必须在 .cpp（Impl 完整可见处）
    void draw();
};
// (2) 非成员非友元：能只用公开接口完成的功能不做成员
void serialize(const Widget& w, std::ostream& os);   // 改 Widget 表示时它无特权、也无需改
// (3) 局部静态：初始化顺序=首次使用顺序，跨 TU 安全（C++11 起还线程安全）
Logger& logger() { static Logger instance; return instance; }
```

### Item 33：中间节点抽象化——防的是"拿错类型当值类型"

论证链：具体非尾端类（concrete non-leaf）鼓励三类事故——按值传基类（切片，
[03-异常.md](03-异常.md) 里 catch-by-value 的孪生问题）、数组多态（Item 3 的算术必然）、
以及"在中间节点上继续扩展时无人拥有销毁协议"。三条治疗：

1. 把中间节点拆成"抽象接口 + 唯一具体叶"；
2. 中间节点**必须携带实现**（如共同数据成员）时，把它模板化：模板实例天生各过各的，
   不会被塞进同一棵虚函数继承树——书中在此语境下触及了模板复用与继承复用的互换性，
   并与 CRTP（curiously recurring template pattern，术语出自 Coplien，1995）思想相接
   ⚠️ 原书是否逐字使用 CRTP 一词未核实，系统性展开见
   [08-补编-从MEC++到Loki定制技法谱系.md](08-补编-从MEC++到Loki定制技法谱系.md)；
3. 若两者都难，至少把析构设 protected 非虚并禁止按值——但这已违背多态使用惯例。

**相邻概念对比**：Item 33 与 Item 24（多态成本）是一体两面——24 教你算钱，33 教你
"钱该花在树的哪一层"。接口层（抽象）越浅、实现层（具体）越靠叶，误用面越小。

### Item 34：C/C++ 混编的四道关卡

1. **链接名**：C++ 有 mangling，C 没有；互相引用必须 `extern "C"` 包住**声明与定义两侧**。
   变量另加 `extern "C"` 语义限制（不能同名重载）。
2. **布局与传值**：C 标准对"空结构体""成员对齐""位域"的允许集与 C++ 类不同；
   带构造函数/非平凡成员的类跨语言边界按值传递在 C++98 是未定义行为（POD 假设被破坏）。
   安全协议：跨界只传 **C-ABI 兼容的 POD 或指针**。
3. **堆配对**：`new` 与 `malloc` 两套分配器不共享账本——谁分配谁释放；动态库场景还要
   防"跨 CRT/跨堆"（Windows 各 DLL 链接自己的 CRT 时释放对方内存即崩）。
4. **异常边界**：异常不得穿越不含展开信息的 C 帧（历史上直接 `terminate`，且 C 帧内的
   资源没人替你释放）；C 回调进 C++ 代码时，回调顶端必须 try/catch 包到 C 世界。

🔧 一份"混编海关申报单"式的正确姿势（教学示意，未实测）：

```cpp
// ===== 共享头文件（C/C++ 双兼容）=====
#ifdef __cplusplus
extern "C" {
#endif
typedef struct Engine engine_t;            // 不透明句柄：C 侧只见指针
engine_t* engine_create(const char* conf); // 分配在 C++ 侧完成，C 侧永不 new/malloc
void      engine_destroy(engine_t*);       // 谁 alloc 谁 free：配对函数收编堆边界
int       engine_run(engine_t*, char** err); // 错误以返回码+出参字符串穿越边界，异常不外逃
#ifdef __cplusplus
}
#endif
```

这个骨架把四道关卡一次关死：链接名（extern "C"）、布局（不透明指针不传结构体值）、
堆（配对函数）、异常（错误码过界）。今天所有主流 C++ 库（fmt、SQLite 包装、LLVM-C）
对外 ABI 都是它的变体。

### Item 35：成为语言学徒

书中最"虚"也最实用的一条：读标准（当年是 CD 草案，今天是 ISO/IEC 14882）、
追踪期刊与会议（C++ Report 与 C Users Journal 后来都停刊了 ⚠️ 停刊年份未核实）、
读编译器扩展文档、跟踪委员会提案。Meyers 自己的《Effective Modern C++》
（[../Effective_Modern_C++.md](../Effective_Modern_C++.md)）就是这条的示范作业：
同一作者在 18 年后用同样的方法重学了一遍语言。

## 权衡与相邻概念对比

- **pimpl（Item 32） vs 虚接口基类（Item 33）**：都切断"改动→重编译/误用"传播链；
  pimpl 切编译期依赖，抽象基切类型误用。大规模项目常要同时用——前者管头文件，后者管继承树。
- **混编边界（Item 34） vs 纯 C API 设计**：Reddy 的 C API 设计原则（不透明句柄、版本结构体）
  是 Item 34 的现代工程化，见 [../C++API设计.md](../C++API设计.md)。

## 最新演进与工业实践

- **Modules（C++20）正面回答了 Item 32**：`import` 取代 `#include` 后，编译依赖与文本依赖
  解耦，pimpl 退守为"ABI 稳定"专用手段（插件系统、C 边界）。但模块化迁移成本使 pimpl
  在工业界仍不可替代——Lakos 的物理设计框架是共同背景，见 [../大规模c++程序设计.md](../大规模c++程序设计.md)。
- **`final`（C++11）给 Item 33 一个语法开关**：不打算被继承的类标 `final`，"非尾端必须抽象"
  从纪律变成可检查声明；C++20 `[[noreturn]]`/属性生态同属"意图入语言"路线。
- **静态初始化顺序（Item 32）的后续工具**：C++11 线程安全局部静态（magic statics）、
  C++20 `constinit`（强制常量初始化，把运行期初始化顺序问题变成编译错误）、
  C++26 拟推进的 `^this`/静态反思设施继续蚕食这一类问题 ⚠️ 个别条目进展以 WG21 官网为准。
- **Item 34 长成了"FFI 学科"**：系统语言互操作（C++26 `import std` 时代的 extern "C" 不变）、
  `std::span`/`std::string_view` 作为零拷贝跨界视图（C++17/20），以及 Rust `extern "C"`
  对同一问题的重新发明——可参考 [../Rust权威指南.md](../Rust权威指南.md) 的 FFI 章节语境 ⚠️ 未逐字核对。
- **Item 35 的当代资源**：cppreference（<https://en.cppreference.com>）、ISO C++ FAQ
  （<https://isocpp.org/faq>，同样出自 Meyers 之手）、Compiler Explorer、WG21 论文库
  （<https://www.open-std.org/jtc1/sc22/wg21/docs/papers/>）、`/std:c++latest` 与
  `__cpp` feature-test 宏（C++20 标准化）把"追语言"变成了可查询的工程动作。
