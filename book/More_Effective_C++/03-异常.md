# 第 3 部分 异常（Exceptions，Item 9–15）

> 对应英文原版 Part "Exceptions"（条目英文名已核实自 Addison-Wesley/InformIT 官方目录页）：
> Item 9 Use destructors to prevent resource leaks；Item 10 Prevent resource leaks in constructors；
> Item 11 Prevent exceptions from leaving destructors；
> Item 12 Understand how throwing an exception differs from passing a parameter or calling a virtual function；
> Item 13 Catch exceptions by reference；Item 14 Use exception specifications judiciously；
> Item 15 Understand the costs of exception handling。
> 本章是全书与今天关系最紧张的一部分：七条里有一条（异常规格）**整个机制已被标准删除**，
> 其余六条反而成了现代 C++ 的地基——RAII 这个术语本身即经本书 Item 9 风行开来
> （"Resource Acquisition Is Initialization" 一词的确切最早出处 ⚠️ 未核实，多归于 C++ 社区/Stroustrup）。

## 核心概念速览（中英对照）

- **RAII** — Resource Acquisition Is Initialization：资源生命周期绑定到栈对象生命周期，析构即释放。
- **句柄类** — handle class：包裹裸资源（指针/描述符）的小类，构造取得、析构归还。
- **构造期泄漏** — leaks in constructors：成员构造函数抛出时，"半构造对象"的析构不会运行，只有**已完成构造的成员**会被析构。
- **析构函数不外抛** — exceptions never leave destructors：析构中异常逃逸 → `std::terminate`。
- **交换式提交** — swap-based commit-or-rollback：先在副本上做危险操作，全部成功后一次不抛的 `swap` 提交——强异常保证的手工原型。
- **落地缓冲** — thrown object storage：抛出对象不在抛点栈帧存活，而是被拷贝到展开路径上调用方的 landing pad。
- **切片捕获** — slicing on catch by value：`catch (Base)` 会把派生类异常切成基类切片对象，且 `throw;` 重抛的是切片副本。
- **异常规格** — exception specification：`void f() throw(A,B)`；违约走 `unexpected` → 默认 `terminate`；C++11 弃用、C++17 移除。
- **零成本异常模型** — zero-cost/table-driven exception handling：try 块不注册任何东西，靠编译期生成的展开表在抛出时查表 unwind。
- **基本保证 / 强保证** — basic / strong guarantee：抛出后无泄漏且对象处于合法状态 / 操作要么完成要么完全回滚（"提交或回滚"）。

## 动机：异常把"错误路径"变成主流路径，资源管理必须换范式

1996 年的论战背景：大量 C++ 代码因"怕泄漏"而拒绝异常。Meyers 的回应是把问题拆开——
泄漏不是异常造成的，是**裸资源 + 手工释放**造成的；异常只是把原本就存在的错误路径
暴露成显式控制流。七个条目连起来是一条完整论证链：
**用析构管资源（9）→ 构造里也要用对象管资源（10）→ 析构自身要闭嘴（11）→
理解抛出的拷贝语义才能救场（12/13）→ 别用异常规格自我设限（14）→ 算清真实的成本（15）**。

## 机制精讲

### Item 9/10：RAII 与它的构造期边界

- Item 9：每个资源配一个句柄类，"取得即初始化、离开即释放"；书中示例形态是 `std::auto_ptr`
  包 `new` 出来的对象（该类型 C++11 弃用、C++17 移除，见演进节）。
- Item 10 的机制核心是**构造/析构的对偶性**：构造函数体还没执行完，该对象的析构函数就
  **永远不会被调用**；已完成的直接成员与基类子对象则会被正常析构。于是
  `A(const X& x, const Y& y) : px(new X(x)), py(new Y(y)) {}` 在 `new Y` 抛出时泄漏 `px`
  ——因为 `A` 尚未构造完成，而 `px` 是裸指针、没有析构。解法只有一种方向：
  **把每个危险资源都放进一个"能自己析构"的成员**（句柄/智能指针），让对偶性替你收尾。
  顺序技巧（重排初始化列表让后一个先分配）只治两资源的病，多资源时必须上对象。

### Item 11：析构函数为什么不许抛——以及怎么"吞"

机制：栈展开过程中若又一个析构抛异常，运行时无法同时展开两层，直接 `terminate()`。
两条出路：**吞掉并记录**（析构里 `try { close(); } catch (const auto&) { log; }`）；
或把可失败操作**拆到显式函数**（`commit()`/`close()` 由调用者处理错误，析构只做"若未显式
提交则按回滚处理"）。Item 11 同时给出"交换式提交"：更新操作在副本上完成，最后用
**永不抛出的 `swap`** 把结果换进 `*this`——异常安全策略的雏形。C++11 起析构默认
`noexcept`（语言把你的疏忽变成硬约束，见演进节）；标准库容器的元素析构要求 noexcept。

### Item 12：抛出 ≠ 传值 ≠ 虚调用——三个拷贝时机

| 操作 | 拷贝发生在 | 拷贝物活在 | 动态类型 |
| --- | --- | --- | --- |
| 按值传参 | 调用点，进函数前 | 被调函数形参 | 参数声明类型（切片） |
| 抛出异常 | throw 表达式处 | **展开路径上为 handler 预备的缓冲区**，穿越栈帧不死 | 保留对象原始动态类型 |
| 构造/析构期虚调用 | 无拷贝 | — | **锁定在正在构造/析构的类**：vtable 指针按构造顺序逐层设置 |

第三行是关键推论：构造/析构函数里调虚函数不会派发到派生/基类版本——与异常无关，但 Meyers
放在此处对比"对象生命期不同阶段类型视图不同"。抛出对象的"拷贝后长寿"也解释了两件事：
`throw` 局部变量是合法的（先拷贝进缓冲区再析构原对象）；而 `throw` 一个指针后按值 catch
原类型是指针语义的陷阱。

### Item 13：按引用捕获

- `catch (by value)` 三宗罪：切片（丢动态类型与成员）、`throw;` 重抛的是**切片后的副本**、
  拷贝构造若抛异常直接 `terminate`（处理异常期间不许再抛）。
- `catch (T& e)`：不切片，但会**改掉原始对象**，且无法捕获右值临时；
- `catch (const T& e)`：书中与今天的一致推荐。捕获顺序"派生先、基类后"（同重载决议无关，纯运行时顺序匹配）。

### Item 14：异常规格——用运行期灾难换虚假安全感

机制：`void f() throw(Bad1,Bad2)` 不在编译期证明任何东西，而是在违约时调用
`std::unexpected`，默认 `terminate`。它还有两个结构性缺陷：（1）**泛型代码不可写**——
`template <class T> void g(T x) throw(??? )` 无法转发 T 可能抛的类型集合；
（2）它把"异常类型集合"当作接口契约，诱使调用方做类型嗅探而不是做状态恢复。
Meyers 的著名结论：**异常规格既不增强也不减弱程序安全性，只是增加僵硬**。
唯一相对可用的形式是 `throw()`（承诺不抛），它的精神后代就是 `noexcept`。

### Item 15：成本账

1996 年常见实现是「构造/销毁登记 + 运行时表」（MSVC 早期 /EHa），try 块有真实入场费；
书中给出的方向（表驱动、抛出慢）今天已是主流实现：**Itanium ABI 的 DWARF CFI + LSDA 表、
Windows x64 的 .pdata/.xdata 表**——正常路径零开销，抛出时才查表展开。
成本转移到三处：（1）代码/只读数据体积增大，cache 与加载变贵；（2）展开表妨碍某些优化
（如跨调用帧的对象放置决策）；（3）throw 路径本身远慢于返回码。嵌入式 `-fno-exceptions`
语境（LLVM 即禁用异常）里，错误码/`std::expected`/`llvm::Error` 是答案——
这恰好证明 Item 14 的精神：**契约要写在类型里，不要写在规格里**。

## 权衡与相邻概念对比

- **异常 vs 返回码**：异常强迫处理（编译警告意义上）、可穿越多层调用；返回码可被忽略但零展开成本。80-20 法则在错误处理同样适用：罕见路径用异常、预期内失败用值类型。
- **RAII vs finally**：finally 是"推迟到块结束"的过程式补偿；RAII 把补偿时刻绑到对象寿命，组合性与可继承性更好（Java/C# 社区转 C++ 的常见误区）。
- **强保证 vs 基本保证**：强保证 ≈ 交换式提交，代价是一次完整副本/移动；基本保证只要求"合法且可继续"。

## 最新演进与工业实践

- **`noexcept`（C++11）接管了异常规格的正面语义**：编译期可检查（`noexcept(expr)` 是常量表达式）、
  运行期违约直接 terminate 而无 unexpected 层；**C++17 彻底移除动态异常规格**
  （[P0003 "Removing Dynamic Exception Specifications"，2016](https://wg21.link/p0003)，提案号已实测可达）。
- **noexcept 的性能含金量**：`std::vector` 增长只有在移动构造 `noexcept` 时才用移动（否则退回拷贝）；
  迭代器/分配器契约大量依赖它——Item 14 若写于今天，标题该改成"用 noexcept 而非规格"。
  类型系统中的 noexcept 统一（函数指针/成员函数指针）见
  [P0012 "Improving the usability of noexcept function specifications"，2016](https://wg21.link/p0012)。
- **析构默认 `noexcept`（C++11）**：Item 11 从"建议"升级为"语言默认"；显式 `noexcept(false)` 是逃生舱，几乎不该按。
- **保证词源**：`basic guarantee` / `strong guarantee`（及 no-throw guarantee）作为标准术语出自
  David Abrahams 的泛型库异常安全论文（2000 年前后）与 Sutter《Exceptional C++》(2000) 的推动；
  本书 1996 年的表述是"commit-or-rollback 风格"策略 ⚠️（词源细节未逐字核实）。
- **`std::uncaught_exception` 的消亡**：Item 相关年代用来判断"是否在展开中"（析构里决定吞还是抛）；
  该函数 C++17 弃用、C++20 移除（cppreference），替身 `std::uncaught_exceptions()`（C++17）返回计数，
  Sutter 用它实现过 `finally` 型作用域守卫。fmt 库与 Folly 的 `SCOPE_EXIT` 是工业级替身。
- **`std::expected<T, E>`（C++23，[P2540](https://wg21.link/p2540)）**：把"可预期的失败"编进返回类型，
  与异常（不可预期失败）形成明确分工——Meyers 两难权衡的现代第三答案；Abseil 的 StatusOr 早已是 Google 全码库标准。
- 相关书目：异常安全与现代契约实践的系统叙述见 [../Effective_Modern_C++.md](../Effective_Modern_C++.md)；
  Sutter 的专题书不在本库索引内，不建链（避免死链）。
