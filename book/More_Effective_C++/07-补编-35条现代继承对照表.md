# 补编 A：35 条现代继承对照表（1996 → C++26）

> 本文件**不是原书章节**，是本目录的补编（体例参照
> [../Stream_Processing_with_Apache_Flink/](../Stream_Processing_with_Apache_Flink/00-总览与阅读地图.md)
> 的"补编"做法）：把 35 条逐一对照到 C++11/14/17/20/23/26 之后的现状，
> 标注 **存活 / 更新 / 退役** 三种命运。判定标准：结论今天是否仍应照做（存活）、
> 结论方向对但手段换了（更新）、机制已从标准或实践中消失（退役）。

## 核心概念速览（中英对照）

- **条款命运** — item lifecycle：技术建议也有保质期，判断其存活/更新/退役是精读旧书的全部意义。
- **语言级执法** — language enforcement：旧"惯例"被新语法/类型系统接管（如 `=delete`、`final`、`noexcept`）。
- **库级收编** — library absorption：手写工艺被标准库组件取代（智能指针、variant、optional）。
- **提案锚点** — proposal anchor：以 WG21 提案号为知识点的最小可核实引用单位。

## 统计与读法

- 35 条中：**纯退役** 3 条（14、28、29 的机制本体）；**更新/被收编** 约 15 条；
  **原文照做仍成立** 约 17 条——比例本身即是"本书值得精读"的量化回答。
- 表中所有提案号均经 `https://wg21.link/<编号>` 实测可达（2026-09 验证）；
  个别提案的**最终采纳轮次**未逐条核对，标注以 [wg21.link](https://wg21.link) 跳转结果为准。

## 最新演进与工业实践

- 本补编整张表就是"书后演进"的总账，另点名三个工业信号：Google 全码库以 Abseil + StatusOr
  落地 Item 10/15 的现代答案（<https://abseil.io/tips/>）；LLVM 禁异常、以 `llvm::Error`/
  Expected 实践"可预期失败走值类型"；fmt 以 `FMT_COMPILE_STRING` 类编译期检查实践
  Item 19/20 的"零临时对象"极限形态（<https://github.com/fmtlib/fmt>）。
- 判定"存活"的条款建议进代码评审清单，判定"更新/退役"的条款建议进技术债看板。

## 一张"命运分布"的读法建议

- **只信半截的风险**：退役条款（14/28/29）恰恰是本书论证最精彩的——留着读"为什么错"，
  比背"现在是什么"更能防住新场景里复活的老坑（比如无锁引用计数、跨 DLL 的 auto_ptr 变体）。
- **存活条款（1/3/7/9/11/13/16–24 的骨架部分）值得逐条摘抄进代码评审清单**；
  更新条款建议按"新手段能否让旧代码编译报警"排序落实（`=delete`/`noexcept`/`final`
  属于第一天就能上的，PMR/expected 属于下一季度迁移的）。
- 与 [../Effective_Modern_C++.md](../Effective_Modern_C++.md) 的 42 条对读时，
  以本表为"从 1996 出发"的正向索引、EMC++ 为"从 2014 出发"的反向索引，两向夹逼同一知识点。
