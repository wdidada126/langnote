# 06 安全模型

> Polaris 的安全模型是其区别于其他 Catalog 实现的核心特性之一。
> 本章拆解 Principal / PrincipalRole / CatalogRole 三层 RBAC 与 OAuth2 认证机制。

## 6.1 安全模型概览

### 6.1.1 三层 RBAC 架构

```text
┌──────────────────────────────────────────────────┐
│  Principal（用户/服务账号）                        │
│  alice │ bob │ spark-service │ flink-ingestion    │
├──────────────────────────────────────────────────┤
│  PrincipalRole（全局角色）                         │
│  data-engineer │ data-scientist │ admin           │
├──────────────────────────────────────────────────┤
│  CatalogRole（Catalog 内角色）                     │
│  reader │ writer │ schema-admin │ table-creator   │
├──────────────────────────────────────────────────┤
│  权限（Privileges）                                │
│  TABLE_READ_DATA │ TABLE_WRITE_DATA │             │
│  NAMESPACE_CREATE │ CATALOG_MANAGE_ACCESS │ ...   │
└──────────────────────────────────────────────────┘
```

## 6.2 Principal（身份）

### 6.2.1 定义

Principal 是 Polaris 中的身份实体，可以是：
- **人类用户**：通过 OAuth2/OIDC 认证。
- **服务账号**：Spark/Flink/Trino 等引擎的自动化身份。

### 6.2.2 创建 Principal

```bash
# ⚠️ 文档转述，未实际执行
curl -X POST http://localhost:8181/api/management/v1/principals \
  -H "Content-Type: application/json" \
  -d '{
    "principal": {
      "name": "alice",
      "credentials": {
        "type": "credential",
        "clientId": "alice-client-id",
        "clientSecret": "alice-client-secret"
      }
    }
  }'
```

> 🔧 类比：Polaris 的 Principal 类似 SQLite 的用户概念，但 SQLite 是文件级权限，Polaris 可细化到 namespace/表级。⚠️ 非本书引擎行为。

## 6.3 PrincipalRole（全局角色）

### 6.3.1 定义

PrincipalRole 是分配给 Principal 的角色集合。一个 Principal 可以有多个 PrincipalRole。

### 6.3.2 分配关系

```text
alice ──→ data-engineer ──→ (在 catalog_A 中是 writer)
                          ──→ (在 catalog_B 中是 reader)
bob   ──→ data-scientist ──→ (在 catalog_A 中是 reader)
```

### 6.3.3 创建与分配

```bash
# 创建 PrincipalRole
curl -X POST http://localhost:8181/api/management/v1/principal-roles \
  -d '{"principalRole": {"name": "data-engineer"}}'

# 将 PrincipalRole 分配给 Principal
curl -X PUT http://localhost:8181/api/management/v1/principals/alice/principal-roles/data-engineer
```

## 6.4 CatalogRole（Catalog 内角色）

### 6.4.1 定义

CatalogRole 定义了在特定 Catalog 内的权限集合。
同一个 PrincipalRole 在不同 Catalog 中可以映射到不同的 CatalogRole。

### 6.4.2 权限粒度

CatalogRole 可以拥有的权限（Privileges）：

| 权限 | 作用域 | 说明 |
| --- | --- | --- |
| `CATALOG_MANAGE_ACCESS` | Catalog | 管理 Catalog 的访问控制 |
| `CATALOG_MANAGE_CONTENT` | Catalog | 管理 Catalog 的内容 |
| `NAMESPACE_CREATE` | Namespace | 创建命名空间 |
| `NAMESPACE_DROP` | Namespace | 删除命名空间 |
| `NAMESPACE_READ_PROPERTIES` | Namespace | 读取命名空间属性 |
| `TABLE_CREATE` | Table | 创建表 |
| `TABLE_DROP` | Table | 删除表 |
| `TABLE_READ_DATA` | Table | 读取表数据 |
| `TABLE_WRITE_DATA` | Table | 写入表数据 |
| `TABLE_READ_PROPERTIES` | Table | 读取表属性 |

> 🔧 类比：Polaris 的权限粒度类似 PostgreSQL 的 GRANT 系统，但 SQLite 只有文件级权限。权限通过角色链（Principal→PrincipalRole→CatalogRole）间接分配。⚠️ 非本书引擎行为。

### 6.4.3 创建 CatalogRole 并授权

```bash
# 在 catalog_A 中创建 CatalogRole
curl -X POST http://localhost:8181/api/management/v1/catalogs/catalog_A/catalog-roles \
  -d '{"catalogRole": {"name": "writer"}}'

# 授予 TABLE_WRITE_DATA 权限
curl -X POST http://localhost:8181/api/management/v1/catalogs/catalog_A/catalog-roles/writer/grants \
  -d '{
    "grant": {
      "type": "privilege",
      "privilege": "TABLE_WRITE_DATA",
      "resource": {"type": "catalog"}
    }
  }'

# 将 CatalogRole 分配给 PrincipalRole
curl -X PUT http://localhost:8181/api/management/v1/catalogs/catalog_A/catalog-roles/writer/principal-roles/data-engineer
```

## 6.5 OAuth2 认证流程

### 6.5.1 令牌获取与使用

```text
引擎 → POST /api/catalog/v1/oauth/tokens (client_id + client_secret + scope)
     ← 200 OK (access_token=<jwt>, expires_in=3600)
引擎 → GET /api/catalog/v1/my_catalog/namespaces (Authorization: Bearer <jwt>)
     ← 200 OK / 403 Forbidden
```

引擎在令牌过期前重新获取。Polaris 不维护会话状态——每个请求独立验证令牌。

## 6.6 安全模型与企业的映射

| 企业概念 | Polaris 映射 |
| --- | --- |
| 员工 | Principal |
| 部门/团队 | PrincipalRole |
| 项目权限 | CatalogRole |
| 具体操作权限 | Privilege |
| SSO 登录 | OIDC Provider → Principal |

## 6.8 本章小结

- 三层 RBAC：Principal → PrincipalRole → CatalogRole → Privilege。
- OAuth2 认证：client_credentials 获取令牌，Bearer token 访问 API。
- 权限粒度可细化到 namespace/表级。

## 核心概念速览（中英对照）

| 中文 | English | 一句话 |
| --- | --- | --- |
| 身份 | Principal | 用户或服务账号 |
| 全局角色 | PrincipalRole | 分配给 Principal 的角色集合 |
| Catalog 角色 | CatalogRole | Catalog 内的权限集合 |
| 权限 | Privilege | 具体操作权限（读/写/创建/删除） |
| 令牌 | Access Token | OAuth2 认证的短期凭证 |
| 最小权限 | Least Privilege | 只授予完成工作所需的最小权限 |

## 最新演进与工业实践

- **2024-2025**：Polaris 的 RBAC 模型逐步稳定 ⚠️（以官方文档为准）。
- **工业趋势**：企业级部署通常对接 OIDC 提供商（Okta/Azure AD/GCP IAM），而非使用内置 client_id/client_secret。
- **⚠️**：列级权限在 REST catalog 规范中尚未标准化，Polaris 当前支持到表级。
- **参考**：安全配置以 `polaris.apache.org` 官方文档为准。
