# 09 运维与治理

> 从开发环境到生产环境，Polaris 需要监控、审计、快照管理与合规。
> 本章覆盖运维实践与治理策略。

## 9.1 运维架构

### 9.1.1 生产部署架构

```text
┌──────────────────────────────────────────────────────────┐
│  负载均衡器（ALB/NLB）                                    │
├──────────────────────────────────────────────────────────┤
│  Polaris Server 集群（K8s Pod × N）                      │
│  ┌────────┐ ┌────────┐ ┌────────┐                       │
│  │ Pod 1  │ │ Pod 2  │ │ Pod 3  │  ← 无状态，可水平扩展  │
│  └────────┘ └────────┘ └────────┘                       │
├──────────────────────────────────────────────────────────┤
│  元数据存储（PostgreSQL 主从 + 自动故障转移）              │
├──────────────────────────────────────────────────────────┤
│  对象存储（S3/GCS/ADLS，跨区域复制）                      │
├──────────────────────────────────────────────────────────┤
│  监控/日志                                                │
│  Prometheus + Grafana │ ELK/Loki │ AlertManager          │
└──────────────────────────────────────────────────────────┘
```

### 9.1.2 无状态设计

Polaris Server 本身是无状态的——所有状态在 PostgreSQL（元数据）和对象存储（数据）中。
这意味着：
- ✅ 可水平扩展：增加 Pod 即可提升吞吐量。
- ✅ 滚动更新无停机：逐个替换 Pod。
- ⚠️ PostgreSQL 是单点——需要主从复制与自动故障转移。

## 9.2 监控

### 9.2.1 关键指标

| 指标类别 | 指标 | 说明 |
| --- | --- | --- |
| 请求延迟 | `polaris_request_duration_seconds` | REST API 请求延迟分布 |
| 请求计数 | `polaris_request_total` | 按端点/状态码统计 |
| 错误率 | `polaris_error_total` | 4xx/5xx 错误计数 |
| 活跃连接 | `polaris_active_connections` | 当前活跃引擎连接数 |
| 元数据操作 | `polaris_metadata_operations_total` | 表创建/删除/更新计数 |
| 认证失败 | `polaris_auth_failure_total` | OAuth2 认证失败计数 |

### 9.2.2 Prometheus 配置

```yaml
# ⚠️ 文档转述
scrape_configs:
  - job_name: 'polaris'
    metrics_path: '/metrics'
    static_configs:
      - targets: ['polaris-0:8182', 'polaris-1:8182', 'polaris-2:8182']
```

### 9.2.3 告警规则

```yaml
# ⚠️ 文档转述
groups:
  - name: polaris-alerts
    rules:
      - alert: HighErrorRate
        expr: rate(polaris_error_total[5m]) > 0.05
        for: 5m
        labels:
          severity: warning
      - alert: HighLatency
        expr: histogram_quantile(0.99, polaris_request_duration_seconds) > 5
        for: 5m
        labels:
          severity: critical
```

> 🔧 **类比**：Polaris 的监控类似监控 SQLite 的 `PRAGMA stats`——
> 但 SQLite 是单机嵌入式，监控靠进程级指标；
> Polaris 是远程服务，需要 HTTP 端点暴露 Prometheus 指标。
> 🔧 差异：SQLite 无监控端点；Polaris 的管理端口（8182）暴露 /metrics。
> ⚠️ 非本书引擎行为。

## 9.3 审计

### 9.3.1 审计日志

Polaris 记录所有管理操作和 API 请求的审计日志：

| 字段 | 说明 |
| --- | --- |
| `timestamp` | 操作时间 |
| `principal` | 执行操作的 Principal |
| `action` | 操作类型（CREATE_TABLE / DROP_TABLE / GRANT 等） |
| `resource` | 操作的资源（catalog/namespace/table） |
| `result` | 操作结果（SUCCESS / FAILURE） |
| `source_ip` | 请求来源 IP |

### 9.3.2 审计日志输出

| 输出目标 | 说明 |
| --- | --- |
| 文件 | 本地日志文件（需配合日志收集） |
| stdout | 容器标准输出（K8s 环境） |
| 外部系统 | 通过日志框架对接 Splunk/Datadog/ELK |

### 9.3.3 合规需求

| 合规框架 | 审计要求 | Polaris 支持 |
| --- | --- | --- |
| SOC 2 | 操作审计追踪 | ✅ 审计日志 |
| GDPR | 数据访问记录 | ⚠️ 需配合引擎层日志 |
| HIPAA | 完整审计链 | ⚠️ 需配合存储层日志 |

## 9.4 快照管理

### 9.4.1 Iceberg 快照的生命周期

Iceberg 表每次写入都创建新快照——快照不会自动清理。
如果不管理，元数据会无限膨胀。

### 9.4.2 快照过期策略

```sql
CALL polaris.analytics.expire_snapshots(
    table => 'events', older_than => TIMESTAMP '2025-01-01 00:00:00', retain_last => 10);
```

### 9.4.3 孤儿文件清理

```sql
CALL polaris.analytics.remove_orphan_files(
    table => 'events', older_than => TIMESTAMP '2025-01-01 00:00:00');
```

> 🔧 类比：类似 SQLite 的 `VACUUM`。差异：SQLite 整理单文件碎片；Iceberg 清理分布式对象存储上的文件。⚠️ 非本书引擎行为。

## 9.5 生产环境检查清单

| 类别 | 检查项 |
| --- | --- |
| 部署 | PostgreSQL 主从 / 对象存储跨区域复制 / Server ≥2 副本 / LB 健康检查 / TLS |
| 安全 | OAuth2/OIDC / 独立 Principal 凭证 / RBAC 最小权限 / allowedLocations / 审计日志 |
| 监控 | Prometheus 指标 / Grafana 仪表盘 / 告警规则 / 日志收集 |
| 运维 | 快照过期策略 / 孤儿文件清理 / 备份策略 / 灾难恢复演练 |

## 9.6 常见运维故障速查

| 故障 | 症状 | 排查方向 |
| --- | --- | --- |
| 连接池耗尽 | 503 + 连接数攀升 | 引擎侧未关闭 Session；配置连接池上限 |
| 元数据延迟飙升 | P99 >1s | PostgreSQL 慢查询 / 对象存储慢 / GC 暂停 |
| 快照膨胀 | 查询规划变慢 | 执行快照过期 + 孤儿文件清理 |

> 🔧 类比：类似排查 SQLite 的 `SQLITE_BUSY`——但 SQLite 是单机锁等待，
> Polaris 是分布式链路上的任意一环变慢。⚠️ 非本书引擎行为。
