# 10 未来展望

> Polaris 的终局不仅是"一个更好的 Catalog"——它指向开放数据生态的基础设施层。
> 本章展望 AI 资产目录、开放标准演进与 Polaris 在湖仓生态中的长期位置。

## 10.1 AI 资产目录

### 10.1.1 从表到 AI 资产

传统 Catalog 管理的是"表"——结构化数据的元数据。
但 AI/ML 工作流需要管理的资产远不止表：

| 资产类型 | 说明 | 当前状态 |
| --- | --- | --- |
| 训练数据集 | Iceberg 表作为训练数据 | ✅ 已支持 |
| 特征存储 | 特征工程的中间结果 | ⚠️ 探索中 |
| 模型注册 | ML 模型的版本管理 | ⚠️ 非 Polaris 当前范围 |
| Prompt 模板 | LLM 的 prompt 版本管理 | 🔧 概念阶段 |
| 评估结果 | 模型评估指标与数据集 | ⚠️ 探索中 |

### 10.1.2 Polaris 在 AI 资产目录中的角色

Polaris 的核心价值——**标准化的元数据管理**——可以扩展到 AI 资产：

```text
┌──────────────────────────────────────────────┐
│  AI 工作流                                    │
│  数据准备 → 特征工程 → 训练 → 评估 → 部署    │
├──────────────────────────────────────────────┤
│  AI 资产目录（Polaris 扩展？）                 │
│  训练数据 │ 特征 │ 模型 │ Prompt │ 评估结果   │
├──────────────────────────────────────────────┤
│  数据目录（Polaris 当前）                      │
│  Iceberg 表 │ 视图 │ 命名空间                 │
└──────────────────────────────────────────────┘
```

> ⚠️ AI 资产目录的具体形态尚未确定——以上为基于 Polaris 架构方向的推断。

## 10.2 开放标准演进

### 10.2.1 Iceberg 规范的演进

Iceberg 表格式本身在持续演进：
- **Iceberg v3**：行级更新性能优化、默认值支持。
- **View Spec**：视图标准化——Polaris 已支持。
- **Materialized View**：物化视图规范在讨论中。

### 10.2.2 REST Catalog 规范的演进

REST Catalog 规范也在迭代：
- **OAuth2 扩展**：更灵活的令牌交换机制。
- **异步操作**：大表的创建/删除可能耗时较长，异步端点在讨论中。
- **事件通知**：表变更事件推送（webhook/kafka）在探索中。

### 10.2.3 跨格式标准化

当前 REST catalog 规范是 Iceberg 特有的。未来可能：
- Paimon 探索 REST catalog 兼容 ⚠️（社区讨论中）。
- Hudi 探索 REST catalog 兼容 ⚠️（社区讨论中）。
- 统一的"湖仓 Catalog 规范"可能出现 ⚠️（纯推测）。

> 与 [Engineering_Lakehouses_with_Open_Table_Formats/](../Engineering_Lakehouses_with_Open_Table_Formats/)
> 的三格式横评呼应——如果 REST catalog 成为跨格式标准，Polaris 的价值将进一步放大。

## 10.3 联邦的深化

### 10.3.1 从 Catalog 联邦到数据联邦

当前 Polaris 的联邦是 Catalog 级——联邦的是"元数据"。
未来可能扩展到数据级：

| 层级 | 当前 | 未来可能 |
| --- | --- | --- |
| 元数据联邦 | ✅ 已支持 | 深化 |
| 查询联邦 | ❌ 需引擎配合 | ⚠️ 探索中 |
| 数据复制 | ❌ 不支持 | ⚠️ 概念阶段 |
| 跨域事务 | ❌ 不支持 | 🔧 纯理论阶段 |

### 10.3.2 数据 Mesh 的技术支撑

Polaris 联邦是数据 Mesh 架构的技术支撑之一：
- 每个域（Domain）拥有自己的 Catalog。
- Polaris 提供跨域的统一访问入口。
- 域的自治通过 Catalog 级权限隔离实现。

> 详见 [Data_Fabric_and_Data_Mesh_with_AI/](../Data_Fabric_and_Data_Mesh_with_AI/) 的 Mesh 架构讨论。

## 本章速查卡

- 一句话：Polaris 的愿景是从数据 catalog 扩展为 AI 资产统一目录。
- 三层可移植：开放格式（数据）+ 开放规范（元数据）+ 开源实现（治理）。
- Catalog 标准之争：Polaris（Apache 开源）vs Unity Catalog（Linux Foundation）vs 商业托管。
- AI 资产目录：模型/特征/数据集——愿景而非现状。
- 🔧 类比：DuckDB 只管关系数据；Polaris 要管数据 + AI 全资产。
- 过关标准：能说出三层可移植 + 四条演进方向。

## 10.7 从现有 Catalog 迁移到 Polaris

### 10.7.1 迁移路径概述

企业从商业 Catalog（如 AWS Glue / Hive Metastore）迁移到 Polaris 的典型路径：

| 阶段 | 操作 | 风险 |
| --- | --- | --- |
| 评估 | 盘点现有 Catalog 的表/视图/权限数量 | 低 |
| 并行运行 | Polaris 与旧 Catalog 同时运行，逐步迁移工作负载 | 中 |
| 切换 | 将引擎配置指向 Polaris REST 端点 | 中-高 |
| 清理 | 下线旧 Catalog | 低 |

### 10.7.2 关键注意事项

- **元数据导出**：从 Hive/Glue 导出表定义，转换为 Iceberg 表元数据。
- **凭证映射**：旧系统的权限模型需重新映射到 Polaris 三层 RBAC。
- **回滚计划**：并行运行期间保留回退能力——切换后至少观察一个完整 ETL 周期。
- **⚠️**：迁移工具仍在社区讨论中，目前以手动 + 脚本为主。

> 🔧 类比：类似从 SQLite 迁移到 PostgreSQL——数据格式不变，
> 但连接方式、权限模型、并发模型都需要调整。⚠️ 非本书引擎行为。

## 10.8 本章速查卡补充

- **迁移三步走**：评估 → 并行 → 切换。
- **核心风险**：权限映射不完整、回滚计划缺失。
