# 08 外部目录与联邦

> Polaris 不仅管理自己的表——它还能将外部 Catalog "挂载"到统一入口。
> 本章覆盖联邦的设计动机、实现机制与典型场景。

## 8.1 为什么需要联邦

### 8.1.1 现实世界的 Catalog 碎片化

企业通常有多个 Catalog（AWS Glue / Unity / Hive Metastore），每个引擎需分别配置 → 元数据孤岛、权限分散、运维复杂。

### 8.1.2 联邦的解决方案

Polaris 联邦 = 将多个外部 Catalog 注册到 Polaris，通过统一的 REST 端点访问。

```text
Spark ──┐
Flink ──┤
Trino ──┼── Polaris REST API ──┬── Internal Catalog (Polaris 管理)
                               ├── AWS Glue (联邦)
                               ├── Nessie (联邦)
                               └── Gravitino (联邦)
```

> 与 [Data_Fabric_and_Data_Mesh_with_AI/](../Data_Fabric_and_Data_Mesh_with_AI/) 的关系：
> 那里讲数据联邦/Mesh 的理念与架构，本章讲 Polaris 作为联邦技术实现的具体机制。

## 8.2 联邦的架构设计

### 8.2.1 联邦 Catalog 的类型

| 类型 | 说明 | 示例 |
| --- | --- | --- |
| Internal | Polaris 自身管理 | Polaris 创建的 Iceberg 表 |
| External | 联邦的外部 Catalog | Glue、Nessie、Gravitino 等 |

### 8.2.2 联邦的数据流

```text
引擎 → Polaris REST API
         │
         ├─ 如果是 Internal Catalog → Polaris 直接处理
         │
         └─ 如果是 External Catalog → Polaris 代理请求到外部 Catalog
                                        │
                                        ├─ Glue → AWS Glue API
                                        ├─ Nessie → Nessie REST API
                                        └─ ...
```

### 8.2.3 透明代理

联邦的关键设计：**引擎不需要知道 Catalog 是 Internal 还是 External**。
Polaris 作为透明代理，统一处理请求路由。

> 🔧 **类比**：类似 DuckDB 的 `ATTACH` 多个数据库——
> 用户通过统一接口访问不同数据库，不需要知道数据实际存在哪里。
> 🔧 差异：DuckDB 的 ATTACH 是本地文件级；Polaris 联邦是远程 HTTP 服务级。
> ⚠️ 非本书引擎行为。

## 8.4 联邦的安全考量

### 8.4.1 凭证传递

联邦场景下，Polaris 需要管理外部 Catalog 的访问凭证：

| 模式 | 说明 |
| --- | --- |
| 静态凭证 | Polaris 存储外部 Catalog 的长期凭证 |
| 凭证交换 | Polaris 用自身凭证换取外部 Catalog 的临时凭证 |
| 直通凭证 | 引擎的凭证直接传递给外部 Catalog |

### 8.4.2 权限映射

联邦 Catalog 的权限需要映射：
- Polaris 的 CatalogRole 权限 → 外部 Catalog 的实际权限。
- 如果外部 Catalog 有不同的权限模型，Polaris 需要翻译。

> 🔧 **类比**：类似 SQLite 的 `ATTACH` 多个数据库时，每个数据库有自己的用户权限——
> 你需要确保当前用户对 ATTACH 的数据库也有访问权。
> 🔧 差异：Polaris 联邦是远程服务级，权限映射更复杂。
> ⚠️ 非本书引擎行为。

## 8.5 联邦的典型场景

### 8.5.1 场景一：并购整合

公司 A 使用 Glue，公司 B 使用 Nessie。并购后：
- 通过 Polaris 联邦两个 Catalog，无需迁移数据。
- 引擎通过 Polaris 统一查询两个 Catalog 的表。

### 8.5.2 场景二：多云架构

- 生产在 AWS（Glue），灾备在 GCP（BigQuery Metastore）。
- Polaris 联邦两个 Catalog，提供统一访问入口。

### 8.5.3 场景三：渐进式迁移

- 从 Hive Metastore 逐步迁移到 Polaris。
- 过渡期通过联邦同时访问 HMS 和 Polaris 中的表。

## 8.6 联邦的限制与注意事项

| 限制 | 说明 |
| --- | --- |
| 跨 Catalog 查询 | Polaris 联邦不提供跨 Catalog 的 JOIN——需要引擎侧联邦 |
| 权限一致性 | 不同 Catalog 的权限模型可能不一致 |
| 性能开销 | 代理请求增加一跳延迟 |
| 特性兼容 | 外部 Catalog 可能不支持所有 Iceberg 特性 |

> ⚠️ 联邦能力仍在快速迭代中，具体支持的外部 Catalog 类型以官方文档为准。

## 核心概念速览（中英对照）

| 中文 | English | 一句话 |
| --- | --- | --- |
| 联邦 | Federation | 通过统一入口访问多个外部 Catalog |
| 外部 Catalog | External Catalog | 非 Polaris 管理的 Catalog |
| 透明代理 | Transparent Proxy | 引擎无需知道 Catalog 是 Internal 还是 External |
| 凭证传递 | Credential Propagation | 联邦场景下的访问凭证管理 |
| 权限映射 | Permission Mapping | 不同 Catalog 权限模型的翻译 |
| 跨 Catalog 查询 | Cross-Catalog Query | 需要引擎侧联邦支持 |
