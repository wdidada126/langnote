## 核心精讲

### 1.1 拜占庭将军问题：故障模型的分水岭

问题陈述（Lamport/Shostak/Pease 1982）：n 位将军围城，其中 f 位是叛徒。所有忠诚将军必须**采取同一行动**（同进攻或同撤退），且少数叛徒不能让忠诚将军做出错误决定。

关键区分：

- **崩溃故障（crash fault, CFT）**：节点要么正常响应，要么停摆。**不会说谎**。
  Paxos / Raft / ZAB 都属于这一类。
- **拜占庭故障（Byzantine fault, BFT）**：节点可以**任意行为**——对不同节点说不同的话、伪造消息、串谋、选择性沉默。
  PBFT / PoW 属于这一类。

> 本书用「苏秦的困境」与「二忠一叛难题」做类比（1.1.1 / 1.1.2），
> 这是**教学性比喻**，本节不做复述，只保留可形式化的结论。

### 1.2 口信消息型：为什么是 3f+1

口信消息（oral message）假设：消息本身可被传递，但**叛徒可以改写转发的内容**，忠诚者无法证明「谁说了什么」。

直觉反例（三将军、一叛徒，即 n=3, f=1）：

```
教学示意，不参与构建
场景：将军 A(忠诚, 发起) / B(忠诚) / C(叛徒)
A 发「进攻」给 B、C
C 收到后转发给 B 说「A 说的是撤退」   <- 叛徒篡改
B 看到：A 说进攻，C 说 A 说撤退
-> B 无法区分「A 是叛徒」还是「C 是叛徒」
-> 无解。这就是 n=3 扛不住 f=1，必须 n >= 3f+1 = 4
```

递归算法 `OM(m)`（m 为叛徒数上界）：指挥官发给 n−1 个副官，每个副官再对收到的值递归执行 `OM(m−1)`，
最后取多数。**消息复杂度是 O(n^(m+1))**，这也是它只具理论意义的原因。
结论定理：口信消息下，当且仅当 **n ≥ 3f+1**（且连通）时可达拜占庭一致。

### 1.3 签名消息型：用密码学换掉人数要求

签名消息（signed message）增加三条假设：

1. 忠诚将军的签名**不可伪造**，且任何改动可被检测；
2. 任何人都能**验证**签名真伪；
3. 只有签名者本人能产生自己的签名。

算法 `SM(m)` 的核心变化：副官收到消息后**不再重新签名转发原文**，而是把「收到的签名链」原样传递。
于是叛徒无法在中间篡改（改了就验签失败），只能选择**沉默**——而沉默可被识别为「不表态」，用默认值兜底。

| 消息类型 | 人数下界 | 直观代价 |
| --- | --- | --- |
| 口信消息 | n ≥ 3f+1 | 需要更多机器；消息量随 m 指数爆炸 |
| 签名消息 | n ≥ f+2（f 个叛徒时） | 需要 PKI/签名体系，计算与密钥管理成本 |

> 本书 1.3 节标题写作「如何解决 n>(3f+1) 的限制」，指向的就是签名消息这条路径。

### 1.4 选 CFT 还是 BFT：成本差一个数量级

```
教学示意，不参与构建
func pickFaultModel(env):
    if 节点由单一可信组织运维（内网、有鉴权、有审计）:
        return CFT   // Paxos / Raft / ZAB：2f+1 副本，两阶段
    if 节点由互不信任的多方运维（联盟链、公网、客户端可提交任意请求）:
        return BFT   // PBFT / PoW：3f+1 副本，三阶段 + 视图更换
    if 业务能容忍「先写着、之后修」:
        return 最终一致  // Gossip + Quorum NWR，不需要共识
```

工程判断（2026 视角补充，非本书原文）：

- **绝大多数企业内网系统不需要 BFT**。理由不是「不会出故障」，而是「故障不会表现为主动说谎」——
  磁盘静默损坏、内存位翻转这类问题靠**校验和 + 端到端验证**解决，比上 BFT 便宜得多。
- BFT 的真实成本不只是机器数：PBFT 的消息复杂度是 O(n²)，n 到几十就明显吃力。

### 2.1 CAP：被误用最多的定理

三个指标（本书 2.1.1）：

- **C 一致性**：这里指**线性一致性（linearizability）**——读操作必须看到最近一次已完成的写。
- **A 可用性**：每个**非故障节点**收到的请求都必须返回非错误响应（不要求是最新的）。
- **P 分区容错**：网络分区（消息丢失/延迟）发生时系统仍能继续运行。

不可能三角（Gilbert & Lynch 2002 的形式化结论）：异步网络中，**无法同时保证 C、A、P**。

最常见的误读是把 CAP 当成「三选二」的静态配置。正确读法：

```
教学示意，不参与构建
// CAP 真正的命题
if 网络正常(无分区):
    系统可以同时满足 C 和 A
else:  // 分区已发生，必须选一边
    CP: 少数派分区拒绝服务（保 C，牺牲 A）
    AP: 两边都继续服务（保 A，牺牲 C，之后做冲突合并）
// P 不是可选项：公网/跨机房网络一定会分区
```

### 2.2 ACID：CAP 的「酸」

- **原子性（Atomicity）**：事务要么全做，要么全不做 —— 靠 undo log 回滚。
- **一致性（Consistency）**：事务前后满足应用定义的**不变式**（invariant），这是**应用层**语义，不是数据库替你保证的。
- **隔离性（Isolation）**：并发事务互不干扰 —— 靠锁或 MVCC。
- **持久性（Durability）**：提交后即使崩溃也不丢 —— 靠 redo log 落盘。

分布式下原子性的两种主流实现（本书 2.2）：

1. **二阶段提交（2PC）**：协调者先 `prepare`（各参与者写 redo/undo 并答复），再 `commit`。
   致命弱点：**协调者宕机时参与者阻塞**（必须持有锁等待，无法单方面决定）。
2. **TCC（Try-Confirm-Cancel）**：把两阶段搬到**业务层**——`Try` 做资源预留，`Confirm` 确认，`Cancel` 释放。
   代价是每个业务都要写三段代码，且必须保证幂等、空回滚、防悬挂。

### 2.3 BASE：CAP 的「碱」

- **Basically Available（基本可用）**：允许降级——本书 2.3.1 给出「4 板斧」：
  **流量削峰、延迟响应、体验降级、过载保护**。
- **Soft state（软状态）**：允许副本之间存在**中间态**，不要求时刻一致。
- **Eventual consistency（最终一致性）**：若不再有新写入，副本最终会收敛到一致。

BASE 落地的技术栈其实就是本书后半本的内容：**Gossip 反熵**（第 7 章）+ **Quorum NWR**（第 8 章）。

## 版本演进

- **1982**：Lamport/Shostak/Pease 提出拜占庭将军问题，给出口信与签名两种解法与下界。
- **1978–1993**：Gray 在《Notes on Database Operating Systems》中系统化了 2PC 与日志；
  X/Open 于 1991 前后发布 **XA 规范**（本书第 9 章的正式出处）。
- **2000**：Eric Brewer 在 PODC 提出 CAP 猜想（当时是 conjecture，不是 theorem）。
- **2002**：Gilbert & Lynch 给出形式化证明，CAP 成为定理。**注意：他们证明的是「异步网络 + 消息丢失」下的不可兼得**，
  与很多人以为的「任何时候三选二」不是一回事。
- **2007**：Pat Helland 在 CIDR 发表《Life beyond Distributed Transactions: an Apostate's Opinion》，
  给出 TCC 的思想源头（本书第 10 章的正式出处）。
- **2008**：Dan Pritchett 在 ACM Queue 发表《BASE: An Acid Alternative》，BASE 一词由此流行。
- **2022（本书）**：把上述四套理论打包成「选型的 PH 试纸」——用酸碱比喻 C/A 取舍，是本书最鲜明的教学法。
- **2026 视角**：CAP 的调料包已经不够用了。工业界更常用 **PACELC**（无分区时也要在延迟 L 与一致性 C 之间取舍），
  以及把一致性表述为**可调节的会话保证**（读己之写、单调读、有界陈旧度）。这些本书均未涉及。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：CAP 的形式化被进一步细化——2017 年前后关于「CAP 中的 A 到底指什么」的争议催生了
  **可调节一致性（tunable consistency）**与 **HAT（Highly Available Transactions，Bailis et al. VLDB 2014）**的系统化研究：
  「高可用」与「可串行化」并非完全对立，读己之写/单调读等会话保证可在 AP 系统里实现。
- **工业界开源**（star 数 2026-09 `gh api` 实测）：
  - `apache/zookeeper`（**12811★**）：CP 协调服务的经典实现，第 6 章主角。
  - `etcd-io/etcd`（**52310★**）：CP 的 KV 存储，K8s 的事实标准元数据存储。
  - `hashicorp/consul`（**30085★**）：服务发现与配置，Raft 强一致 + 健康检查的组合。
  - `kubernetes/kubernetes`（**128012★**）：把「CP 元数据存储（etcd）+ AP 的边缘组件」组合成一个系统的最大样本。
  - `pingcap/tidb`（**40590★**）/ `cockroachdb/cockroach`（**32508★**）：在分布式事务上给出**可串行化**的 CP 答案，
    是「ACID 阵营」2026 年的代表性工程。
  - `apache/incubator-seata`（**26012★**）：TCC/AT/Saga 模式的事务框架，本书第 10 章 TCC 的工业化落地形态。
- **Jepsen 实测**（`jepsen-io/jepsen`，**7504★**）：Kyle Kingsbury 自 2013 年持续发布的一致性测试报告，
  是「厂商宣称的 C 到底成不成立」的**唯一公开裁判**。2026 年读本书第 2 章时，应把 Jepsen 报告当作 CAP 的实证补充。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「CAP 是三选二，我选了 CA」 | 不存在 CA 系统：**P 不可放弃**。真实取舍只在分区发生时选 C 还是 A |
| 2 | 「口信消息和签名消息的要求一样」 | 口信需 n ≥ 3f+1；签名可降到 f+2，代价是 PKI 与验签成本 |
| 3 | 「拜占庭容错就是防黑客」 | BFT 防的是**任意行为节点**（含 bug、静默损坏、串谋），不是通用安全方案；它不解决鉴权与加密 |
| 4 | 「ACID 的 C 和 CAP 的 C 是同一个 C」 | 不是：ACID 的 C 是**应用不变式**，CAP 的 C 是**线性一致性**。同名不同义，是最常见的混淆 |
| 5 | 「2PC 就是分布式事务的全部」 | 2PC 只解决**原子提交**，不解决隔离性；分布式可串行化还需要并发控制配合 |
| 6 | 🔧 2026 补丁：本书未提 FLP | 本书第 1 章讲了「能不能一致」，但**没讲异步模型下「必然终止」的不可能性**（FLP, JACM 1985）。没有 FLP，就无法解释为什么 Paxos/Raft 必须引入超时与 Leader。建议与 [../分布式算法/03-FLP与不可能性.md](../分布式算法/03-FLP与不可能性.md) 同读 |
| 7 | 🔧 2026 补丁：CAP 缺少 PACELC 维度 | 无分区时系统仍需在**延迟**与**一致性**间取舍（如是否走 Read Index、是否等多数派）。本书 2.1 只讲分区时，读者容易误以为「不分區就免费得到强一致」 |
| 8 | 🔧 2026 补丁：BFT 选型建议需补一句 | 本书 1.4 给出 BFT/CFT 选择标准，但 2026 年还应补：**联盟链与公网场景**才有必要 BFT；企业内网用 CFT + 校验和 + 端到端验证更划算。联盟链落地见 `hyperledger/fabric`（16732★） |
