# 第 5 章 一致哈希算法

> 覆盖原书：第 5 章「一致哈希算法」。
> 5.1 使用哈希算法有什么问题、5.2 如何使用一致哈希算法实现哈希寻址、5.3 小结。
> 章题中的「分群」用法见本书副标题式表述「如何分群，突破集群的『领导者』限制」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 哈希算法的问题 | `hash(key) % N` 的扩容灾难 | N 变化时**几乎所有 key 都要重映射**，缓存全失效、数据全迁移 |
| 5.2 一致哈希 | 哈希环、虚拟节点、顺时针查找 | 节点伸缩时只迁移 **1/N 左右**的 key，其余不动 |
| 5.3 小结 | 一致哈希的定位 | 它解决的是**寻址（数据放哪）**问题，**不是一致性（副本一致）**问题 |

## 核心精讲

### 5.1 取模哈希为什么不可伸缩

```
教学示意，不参与构建
// 朴素做法
node = nodes[ hash(key) % len(nodes) ]
// 从 3 台扩到 4 台时：
//   key 的落点 = hash(key) % 3  ->  hash(key) % 4
//   绝大多数 key 的余数都变了 -> 近乎全量迁移
// 后果：
//   1. 缓存：命中率瞬间归零 -> 数据库被打爆（经典「缓存雪崩」）
//   2. 存储：需要在短时间内搬走大部分数据，网络与磁盘都扛不住
```

**量化对比**（N 个节点扩到 N+1）：

| 方案 | 需要迁移的 key 比例 | 4→5 台时的迁移量 |
| --- | --- | --- |
| `hash(key) % N` | ≈ N/(N+1)（近乎全量） | ≈ 80% |
| 一致哈希（无虚拟节点） | ≈ 1/(N+1) | ≈ 20% |
| 一致哈希（带虚拟节点） | ≈ 1/(N+1)，且分布更均匀 | ≈ 20% |

### 5.2 哈希环与虚拟节点

```
教学示意，不参与构建
// 1) 构造哈希环：把 0 ~ 2^32-1 看成一个首尾相接的环
// 2) 把「节点」映射到环上：hash(nodeIP) -> 环上一个位置
// 3) 把「key」映射到环上：hash(key) -> 环上一个位置
// 4) 从 key 的位置顺时针走，遇到的第一个节点就是它的归属

func locate(key, ring[]):
    h = hash(key)
    i = lower_bound(ring, h)          // 第一个 >= h 的节点位置
    if i == len(ring): i = 0          // 环绕
    return ring[i].node

// 虚拟节点：每个物理节点映射成 K 个环上位置
for node in nodes:
    for k in 0..K-1:
        ring.insert( hash(node + "#" + k) -> node )
// K 通常取 100~200：让不同节点在环上「切」到的弧长更接近
```

**虚拟节点解决的两个问题**：

1. **数据倾斜**：物理节点少时，环上弧长差异大，可能某台机器扛 60% 的 key。虚拟节点做「统计平均」。
2. **扩容再平衡**：新增节点时，它的 K 个虚拟点从多个已有节点那里各接手一小段，
   迁移量自然摊薄，而且**可以从多台机器并行拉取**。

> 本书 5.2 强调「哈希寻址」，并把它与「突破集群领导者限制」联系起来：
> 一致哈希让**每个 key 都有确定的归属节点**，因此可以把一个大集群按 key 切成若干「群」，
> 每群各自解决自己的一致性问题——这正是后续 Multi-Raft / 分片系统共用的思路。

### 5.2 补充：副本与偏好列表（一致哈希如何与副本策略衔接）

```
教学示意，不参与构建
// 一致哈希不只用来找「一个」节点，也用来找「N 个」副本
// 做法：从 key 的位置顺时针走，取前 N 个**不同的物理节点**
func preferenceList(key, ring, N):
    out = []; seen = set()
    i = lower_bound(ring, hash(key))
    while len(out) < N and len(seen) < len(allNodes):
        node = ring[i].node
        if node not in seen: out.append(node); seen.add(node)
        i = (i + 1) % len(ring)
    return out          // 这就是 Dynamo 的 preference list
// 有了它，第 8 章 Quorum NWR 才知道该往哪 N 个节点写
```

> 这是本书第 5 章与第 8 章之间**没有明说但确实存在的衔接**：
> 第 5 章解决「数据放哪 N 个节点」，第 8 章解决「这 N 个节点里写几个、读几个」。

### 5.2 补充：扩容期间的读路径（迁移没做完时读什么）

```
教学示意，不参与构建
// 场景：节点 D 加入环，A 的一部分区间要迁给 D，正在搬
// 客户端来读：
//   (a) 直连存储：客户端算错位置 -> 读到「未迁移」的旧节点 -> 拿到旧值或 miss
//   (b) 代理层/协调层：代理持有最新环视图 -> 重定向到正确节点 -> 正确
//   (c) 双写 + 双读：迁移期间同时写两边，读时取最新 -> 正确但代价高
// 2026 年的主流做法是 (b)：把环视图交给代理/协调服务（etcd/Consul）托管
//   而不是让每个客户端各自算环
```

这一节解释了为什么「扩容只迁 1/N」这一漂亮结论在企业里并不总是成立——
**迁移期间的读正确性**是另一件事，一致哈希本身不管。

### 5.3 一致哈希「不」解决什么

这是本章最容易被忽视的一点，也是全书的术语陷阱：

| 概念 | 中文都叫「一致」 | 英文 | 解决的问题 |
| --- | --- | --- | --- |
| **一致哈希** | Consistent Hashing | Consistent **Hashing** | 数据**放在哪**（寻址/分片） |
| **一致性** | Consistency（线性一致/最终一致） | Consistency | 副本之间**看到什么**（副本状态） |
| **共识** | Consensus | Consensus | 多个节点**对第 n 条指令达成同一决定** |

认清这三者的区别，才能理解为什么本书第 5 章（一致哈希）与第 8 章（Quorum NWR）是两个完全不同的话题。

## 版本演进

- **1997**：Karger 等人在 STOC 发表《Consistent Hashing and Random Trees》，
  原始场景是**缓解 Web 缓存热点（hot spots）**——与今天「分布式存储分片」的语境并不完全相同。
- **2007**：Amazon Dynamo（SOSP 2007）把「一致哈希 + 虚拟节点 + 偏好列表（preference list）」组合起来，
  形成可伸缩的 KV 存储模板；此后 Cassandra、Riak 沿用。
- **2010s**：出现**有界负载一致哈希**（Consistent Hashing with Bounded Loads，Google 2017 年公开其 `h2o`/Maglev 相关实践），
  解决「即使有虚拟节点也可能有热点」的问题。
- **2022（本书）**：第 5 章篇幅很短（3 节），定位是「够用即可」，重点放在哈希寻址与「分群」这一思想上。
- **2026 视角**：
  - 一致性哈希在 2026 年仍是**缓存与无状态分片**的首选（Redis 客户端分片、CDN 节点选择、网关路由）；
  - 但**有状态存储几乎不再直接用裸哈希环**，而是用 **range 分片 + 集中调度**（TiKV 的 Region + PD、Spanner 的 tablet、CockroachDB 的 Range）——
    因为 range 分片能做**按负载的细粒度再平衡**，而哈希环做不了「只搬热点区间」；
  - **Rendezvous Hashing（Highest Random Weight, HRW）**在很多新系统里取代了一致哈希：
    不需要环结构，对每个 key 计算 `hash(key, node)` 取最大者，天然支持权重与「副本列表」。
  - 云原生场景下，寻址常常被**上移到代理层/协调层**（如 Vitess、Proxy、K8s Service），应用层不再自己算哈希。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：
  - **有界负载一致哈希**（Bounded-load consistent hashing）被形式化：在容量约束下把负载控制在平均值的 (1+ε) 倍内，Google 与 Vimeo 都有公开实现；
  - **Jump Consistent Hash**（Lamping & Veach, 2014）：无需存储环、O(log N) 计算、分布近乎完美，**无虚拟节点**——
    在只需要「bucket 编号」而不需要「副本列表」的场景里已大量取代哈希环；
  - **一致性哈希与共识的组合**：分片后每个分片（群）内部再跑 Raft 组，即 **Multi-Raft**，这是 2018 年后的主流。
- **工业界开源**（star 数 2026-09 `gh api` 实测）：
  - `redis/redis`（**76485★**）：Redis Cluster 用的是**哈希槽（16384 slots）**而非严格意义的一致哈希环——
    这是一个常被搞混的点：槽位方案是「固定槽数 + 槽到节点的映射可变」，迁移粒度是槽。
  - `apache/zookeeper`（**12811★**）：其一致性由 ZAB 保证，与一致哈希无关；放在一起看有助于区分本章 5.3 的三个「一致」。
  - `tikv/tikv`（**16878★**）：**range 分片 + PD 调度**，是 2026 年主流分片方案的代表（不是哈希环）。
  - `pingcap/tidb`（**40590★**）：在 TiKV 分片之上提供 SQL，可观察「分片 → 事务 → 共识」三层如何叠起来。
  - `apache/rocketmq`（**22621★**）：消息队列的队列分配与消费者负载均衡里也能看到一致性哈希/轮询策略的选择。
- **Jepsen 实测**（`jepsen-io/jepsen`，**7504★**）：对 Cassandra/Riak 等一致哈希系统的报告显示，
  **分片方案本身不产生一致性错误**，但它们暴露的「会话保证缺失」「读修复时序问题」值得读本章时对照。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「一致哈希保证副本一致」 | 完全无关。它只解决**寻址**，副本一致性靠共识或 Quorum（本书第 8 章） |
| 2 | 「有了一致哈希就不用虚拟节点」 | 节点少时倾斜严重；虚拟节点是标配而非优化 |
| 3 | 「Redis Cluster 用的一致性哈希」 | Redis Cluster 用的是 **16384 个哈希槽**，迁移粒度是槽，不是环 |
| 4 | 「扩容时迁 1/N 就万事大吉」 | 迁移期间**读会落到旧节点**造成 miss/陈旧读；需要双写、重定向或代理层配合 |
| 5 | 🔧 2026 补丁：缺 Rendezvous / Jump Hash | 本书只讲哈希环。2026 年新系统里 **Jump Consistent Hash**（2014）与 **Rendezvous Hashing**（1998）因无环结构、支持权重与副本列表而被大量采用，建议补读 |
| 6 | 🔧 2026 补丁：有状态存储已转向 range 分片 | 哈希环无法「只搬热点区间」。TiKV/CockroachDB/Spanner 都用 **range 分片 + 集中调度器**（PD / Range 分裂合并）。本章的「分群」思想是对的，但落地形态在 2026 年已换代 |
| 7 | 🔧 2026 补丁：热点（hot key）问题本书未展开 | 一致哈希解决的是「均匀分布」，**解决不了单个 key 成为热点**（如爆款商品）。工程解法是本地缓存、key 加随机后缀打散、读副本扩展。这与哈希算法本身无关，但常被误以为是哈希环能解决的 |
| 8 | 🔧 2026 补丁：云原生下寻址被上移 | 2026 年多数业务不再自己算哈希，而是交给**代理层 / 服务网格 / 协调服务**（Vitess、Proxy、K8s Service + etcd）。本书 5.2 的「自己算环」在真实系统里已较少见 |
