## 核心概念速览（中英对照）

- **只读/可变双面孔** — read-only vs mutable collection interfaces：✅ `List`/`Set`/`Map` 只读，`MutableList` 等增写；✅ 二者非两个容器，是同一容器的两种能力视图。
- **协变导致的假只读** — covariant escape：✅ `List` 协变（`out E`），`MutableList` 可当 `List` 传，但 ✅ `as MutableList` 强转回去依然能改——只读类型是护栏不是锁。
- **序列** — `Sequence`：拉式惰性流水线，✅ 多步链合并遍历、免中间集合。
- **解构声明** — destructuring declaration：`val (a, b) = x`，✅ 依赖 `componentN()` 约定；列表按位置、Map Entry 给 (K, V)。
- **中间集合** — intermediate collection：链式集合操作每步新建 List 的隐性成本，Sequence/`groupByTo` 等的存在理由。

## 条目清单（⚠️ 编号推定，本部 10 条）

### Item ⚠️21｜参数收只读、返回给只读、字段留可变（Prefer read-only collection types）

🔧 坏味道：
```kotlin
fun report(items: ArrayList<String>, scores: HashMap<String, Int>): MutableList<Double> { ... }
```
🔧 修正：
```kotlin
fun report(items: List<String>, scores: Map<String, Int>): List<Double> { ... }
```
理由：✅ Kotlin 集合类型分层是语言级设计：`List` 无 `add`，✅ 且协变（`List<String>`
可是 `List<Any>`）而 `MutableList` 不变。签名用具体可变类（`ArrayList`）既绑死实现，
又邀请调用方在你背后改数据；只读类型把"我消费不改写"写进契约。内部真需要改，
用 `toMutableList()` 在函数边界拷一次——成本明码标价。
对照：Java 的 `Collections.unmodifiableList` 是运行期包装（改了抛异常）；C++ 对应
`const std::vector<T>&` 形参+返回 `const&` 或值——Kotlin 的只读接口≈C++ 的 const
引用参数教义，但 ✅ 没有 C++ 那种 const_cast 后门式的体面谴责，只有硬强转。

### Item ⚠️22｜暴露集合属性时，别让别名漏进可变深渊（Don't leak mutable internals）

🔧 坏味道：
```kotlin
class Playlist {
    val songs: MutableList<String> = mutableListOf()   // val ≠ 不可变内容！
}
playlist.songs.add("hack")   // ✅ 编译通过：val 只锁引用，不锁内容
```
🔧 修正：
```kotlin
class Playlist {
    private val _songs = mutableListOf<String>()
    val songs: List<String> get() = _songs              // 同一对象的只读视图
}
```
理由：✅ `val` 修饰的是绑定不是对象——`val MutableList` 是新手最贵的一个误区。
私有可变 backing + 公开只读 getter 是标准防御；但 ✅ 视图不是拷贝，
`(playlist.songs as MutableList).add(...)` 仍能得手——对外 API 若要硬隔离，
返回 `toList()` 快照或 ✅ JDK 的 `Collections.unmodifiableList` 语义再包一层。
选哪档取决于"防误用"还是"防恶意"。
对照：Java 同一坑（`final List` + `Collections.unmodifiableList` 可被强转回原引用）；
C++ 用返回 `const T&`/值拷贝从类型上封死，代价是没有 Kotlin 这种"同一对象换张脸"
的零拷贝视图选项。

### Item ⚠️23｜多步流水线用 Sequence，一步过滤用集合操作（Use Sequence for long pipelines）

🔧 坏味道：
```kotlin
val top = lines
    .map { it.trim() }          // 新建 List，全量
    .filter { it.isNotEmpty() } // 又新建 List
    .map { it.length }          // 又新建 + 装箱
    .sorted()                   // 又新建
    .take(10)
```
🔧 修正：
```kotlin
val top = lines.asSequence()
    .map { it.trim() }
    .filter { it.isNotEmpty() }
    .map { it.length }
    .sorted()
    .take(10)
    .toList()
```
理由：✅ 集合操作每步物化一个中间 List（O(链长×n) 的分配+GC 压力）；✅ `Sequence`
把每元素的多步转换融合成一次推进，`take(10)` 还能提前短路（✅ sorted 例外，
必须吞尽再吐——这是 Sequence 也救不了的排序本质）。链只有 1-2 步时集合版更直读，
别教条化。
对照：Java Stream 是"默认惰性、终点操作落地"，✅ 且可 `.parallelStream()`——Kotlin
Sequence 单线程拉式，更像 C++20 ranges 的 `views`（惰性组合、按需推进，见本仓
[../C++20模板元编程/09-范围库.md](../C++20模板元编程/09-范围库.md)）而非 Java Stream。

### Item ⚠️24｜groupBy/associateBy 替掉手写聚合循环（Use grouping operations）

🔧 坏味道：
```kotlin
val byDept = mutableMapOf<String, MutableList<Employee>>()
for (e in employees) {
    val list = byDept[e.dept]
    if (list == null) byDept[e.dept] = mutableListOf(e)
    else list.add(e)
}
```
🔧 修正：
```kotlin
val byDept = employees.groupBy { it.dept }
val index = employees.associateBy { it.id }            // 键唯一场景
val count = employees.groupingBy { it.dept }.eachCount()
```
理由：✅ `groupBy/associateWith/groupingBy...eachCount` 是标准库对这些固定模式的
命名——手写版不但啰嗦，还常伴随"HashMap 容量没预估、循环内重复算 key"之类
性能小坑。聚合意图（分桶/建索引/计数）用名字直陈，grep "groupBy" 能找到全部
分桶点。
对照：Java 8 `Collectors.groupingBy` 同旨但签名冗长（类型推断帮了 Kotlin）；
C++ 无内建对应物，手写 `unordered_map<string, vector<...>>` 循环是日常，
ranges-v3 的 `group_by` 才补上一点。

### Item ⚠️25｜解构用得上名字才用；Pair 超过两个就升级 data class（Destructure meaningfully）

🔧 坏味道：
```kotlin
fun parse(input: String): Triple<String, Int, Boolean> = ...
val t = parse(line)
if (t.second > 0 && t.third) send(t.first)
```
🔧 修正：
```kotlin
data class Parsed(val head: String, val offset: Int, val ok: Boolean)
fun parse(input: String): Parsed = ...
val (head, offset, ok) = parse(line)
if (offset > 0 && ok) send(head)
```
理由：✅ 解构依赖 `componentN()` 约定（data class 与 Pair/Triple 自带；✅ List 解构
按位置且多余元素会越界、Map Entry 解构天然二元）。`Triple` 的位置语义只活在
文档口头承诺里，参数换序编译器不响；升级 data class 后位置错误变成名字错误，
而解构写法保留可读性。单点使用不配命名类型——Pair 的适用区是"临时、两处、
用完即弃"。
对照：Java 没有语言级解构（record + 手动访问器是最近亲）；C++ 的结构化绑定
`auto [a, b] = p;` 对 `std::tuple` 同样按位置裸奔，C++ 社区"tuple 超过 3 个成员
就该换 struct"的裁决与这条完全一致。

### Item ⚠️26｜别拿 indices+下标遍历当作唯一姿势（Iterate idiomatically）

🔧 坏味道：
```kotlin
for (i in 0..list.size - 1) {
    println(list[i])
}
if (list.size % 2 == 0) ...
```
🔧 修正：
```kotlin
for (x in list) println(x)
for ((index, x) in list.withIndex()) ...
for (i in list.indices) ...        // 确实要下标时
if (list.size.isEven()) ...        // 或 list.size % 2 == 0
```
理由：✅ `until`/`indices`/`withIndex` 是为这类手搓边界准备的惯用语；
`0..size-1` 在 size=0 时 ✅ 恰好安全（`..(-1)` 为空区间）但读者要现场证明这件事——
惯用语省的是**读者的证明义务**。对 `LinkedList` 等随机访问昂贵实现，✅ 索引遍历
退化 O(n²) 而迭代器 O(n)：类型只写 `List` 时索引循环是埋雷。
对照：Java 的 `for (int i = 0; i < list.size(); i++)` 同样被 Effective Java
（Item ⚠️推定：for-each 优先）批评；C++ 的 `vec[i]` vs 迭代器是存在千年的
"随机访问成本"分歧，Kotlin 用接口分层把分歧藏进类型。

### Item ⚠️27｜空结果是 emptyList()/emptySequence()，不是 null（Never return null collections）

🔧 坏味道：
```kotlin
fun findTags(post: Post): List<String>? =
    if (post.tags.isEmpty()) null else post.tags
val tags = findTags(p) ?: emptyList()   // 调用方被迫复读"不可能为空"
```
🔧 修正：
```kotlin
fun findTags(post: Post): List<String> = post.tags
val tags = findTags(p)
```
理由："没有结果"对集合而言是一个合法集合值（✅ 空 List 支持全部只读操作、
`forEach` 零次、`sum` 归零），null 反而把"可空传染"塞进签名（见 02 部
Item ⚠️15）。✅ 标准库 `emptyList<Nothing>()` 是单例零成本。需要区分"没查"和
"查了没有"时，那个语义应由**另一个通道**表达（sealed 结果/异常），不该让
null 越权兼职。
对照：Effective Java Item ⚠️推定"返回空集合而非 null"原教旨同款；Java 9+ 的
`List.of()` 也走不可变空单例；C++ 返回空容器是出厂直觉，nullptr 从不伪装成容器。

### Item ⚠️28｜加/删元素：+ 是语义糖，+= 对可变集合是陷阱（Know + and += on collections）

🔧 坏味道：
```kotlin
val set = mutableSetOf("a")
set + "b"                 // ❌ 静默无效：产生新 Set 被丢弃
val list = mutableListOf(1)
list += 2                 // ✅ 有效，但 ✅ 它编译成 list.add(2)（原地）还是 new + 重赋？读者要查
```
🔧 修正：
```kotlin
val set = mutableSetOf("a")
set.add("b")              // 可变集合：明写原地
val readOnlyPlus = setOf("a") + "b"   // 只读集合：明写生成新集合
```
理由：✅ `+` 在 `List`/`Set`/`Map` 上有完整重载（元素与集合两种右侧）；✅ `+=` 对
可变集合的 `plusAssign` 走原地 `add`/`addAll`，对只读接收者走 `plus` 产生新值后
重赋——同一符号两种内存行为。混用导致"写了没生效"（丢弃新集合）或"以为没生效
其实改了"。按接收者能力二选一，别混。
对照：Java 无运算符重载，`list.add(x)` / `Stream.concat` 两条路泾渭分明；
C++ 的 `push_back` vs 返回新 vector（`+=` 对 `std::vector` 是拼接语义）同样靠
类型各自定义，教训一致：运算符的内存语义必须在接收者类型上唯一。

### Item ⚠️29｜重复操作同一集合前，先物化/转类型止损（Avoid repeated traversals and containment checks）

🔧 坏味道：
```kotlin
val winners = users.filter { it.active }.sortedBy { it.score }.take(10)
val losers  = users.filter { it.active }.sortedByDescending { it.score }.drop(10)
if (winners.contains(name)) ...          // winners 是 List：O(n) 查找
```
🔧 修正：
```kotlin
val ranked = users.asSequence()
    .filter { it.active }
    .sortedBy { it.score }               // 一次排序
val (winners, losers) = ranked.chunked(10).let { ... } // 按真实分页需求切
val winnerSet = winners.toSet()          // 反复 contains → Set
```
理由：✅ `filter+sorted+take` 每步都全量过一遍数据，两次链=两倍遍历；共享前缀
应物化一次。✅ `List.contains` 是 O(n)，反复查询模式标准库明言应转 `Set`
（`toSet()`/`toMutableSet()`）。这类条目本质是"看清每个操作的复杂度再组合"——
Kotlin 不隐藏成本，只给惯用名。
对照：Java Stream 里 `collect` 后复用是同款纪律；C++ 的"先 `std::sort` 一次、
再 `binary_search`/`unordered_set`"是算法竞赛与工程共同的肌肉记忆——
复杂度意识跨语言通用，语言只提供语法糖不提供免费的 O(1)。

### Item ⚠️30｜Map 的默认值三件套：getOrDefault / getOrPut / computeIfAbsent 的 Kotlin 选法（Avoid mutable default patterns）

🔧 坏味道：
```kotlin
val counts = mutableMapOf<String, Int>()
for (w in words) {
    val c = counts[w]
    if (c == null) counts[w] = 1 else counts[w] = c + 1
}
```
🔧 修正：
```kotlin
val counts = words.groupingBy { it }.eachCount()          // 纯统计场景
// 需要增量累积时：
counts.getOrPut(w) { 0 }.let { counts[w] = it + 1 }       // 或
counts.merge(w, 1) { a, b -> a + b }                       // ✅ 平台 API 可用时
```
理由：✅ `getOrPut` 是标准库扩展（键缺失时求值默认并放入），✅ 与 Java 的
`computeIfAbsent` 方向一致但注意差异：`getOrPut` 的默认值**总被求值**（惰性版是
`getOrPut` 无、用 `computeIfAbsent` 才有）。手写 null 分支是 Java 肌肉记忆在
Kotlin 里的无谓搬运。
对照：Java `merge/computeIfAbsent` 一族 API 面大且易误用（`computeIfAbsent` 重入
修改是著名死锁/IAE 坑）；✅ Kotlin 的 `getOrPut` 简单但无原子性保证——多线程计数
请直接上 `ConcurrentHashMap`/LongAdder，见 [07 部](07-并发与协程.md)。

## 核心概念中英对照表

| 中文 | 英文 | 一句定义 |
| --- | --- | --- |
| 只读集合接口 | read-only collection interface | `List/Set/Map`：无增删方法，协变 `out E`。 |
| 可变集合接口 | mutable collection interface | `MutableList` 等：增写方法，不变。 |
| 假只读/别名泄漏 | mutable leak via alias | `val MutableList` 或强转回可变：val 只锁引用。 |
| 序列 | Sequence | 拉式惰性流水线，融合多步、免中间集合。 |
| 中间集合 | intermediate collection | 集合链式每步物化 List 的成本来源。 |
| 解构声明 | destructuring declaration | `val (a,b)=x`，依 `componentN()` 约定。 |
| 分组/关联 | grouping / associating | `groupBy/associateBy/groupingBy().eachCount()` 模式库。 |
| withIndex / indices | 带下标遍历 / 下标区间 | 替代手搓 `0..size-1` 的惯用访问器。 |
| plusAssign 歧义 | `+=` dual semantics | 可变接收者原地 add、只读接收者生成新值。 |
| getOrPut | 缺失即放默认 | 类似 computeIfAbsent 但默认值急切求值。 |
