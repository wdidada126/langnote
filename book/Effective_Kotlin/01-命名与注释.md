## 核心概念速览（中英对照）

- **命名约定** — naming convention：Kotlin 官方风格（camelCase 函数/变量、PascalCase 类型、SCREAMING_SNAKE 常量），✅ 编译器不强制，靠约定与 linter。
- **匈牙利命名反模式** — anti-Hungarian notation：名字里编入类型信息（`strName`、`listItems`），Kotlin 类型推断使类型信息免费，✅ 名字重复类型即冗余。
- **KDoc** — Kotlin documentation：`/** */` 文档注释，✅ 支持 `@param/@return/@see` 与 Markdown，IDE 渲染。
- **解释"为什么"而非"是什么"** — comment intent：注释的第一职能是记录决策动机，代码本身陈述行为。✅ 这是通行工程共识，非逐字引书 ⚠️。
- **魔法数** — magic number/constant：字面量直接嵌在逻辑里；对策是提命名常量。
- **代码即文档边界** — self-documenting limit：好命名压不出业务动机与坑，KDoc/注释仍有不可替代位。

## 条目清单（⚠️ 编号推定，本部 10 条）

### Item ⚠️1｜选择表意的名字（Choose meaningful names）

🔧 坏味道：
```kotlin
fun f(l: List<User>, d: Double): List<User> {
    val r = l.filter { it.a > d }
    return r
}
```
🔧 修正：
```kotlin
fun findUsersWithOverdueBalance(
    users: List<User>,
    threshold: Double,
): List<User> = users.filter { it.overdueAmount > threshold }
```
理由：名字是调用方唯一的"离线文档"。`f/l/d/r` 把理解成本全部转嫁给读代码的人；
表意名（动词短语描述做什么、名词描述是什么）让函数签名本身构成需求陈述。
长度应与作用域成正比——一行 lambda 里 `it` 足够，公开 API 参数名要能进文档。
对照：Java 老手同样讲 meaningful names，但 Kotlin 的默认参数+具名实参让长名字
（`findUsersWithOverdueBalance(threshold = 100.0)`）读起来比 Java 重载更顺口。

### Item ⚠️2｜名字里不要编入类型（Don't include types in names）

🔧 坏味道：
```kotlin
val strTitle: String = ...
val userList: List<User> = ...
fun getAgeInt(): Int = ...
```
🔧 修正：
```kotlin
val title: String = ...
val users: List<User> = ...
fun getAge(): Int = ...
```
理由：✅ IDE/类型推断/编译器随叫随到地回答"x 是什么类型"，名字里再抄一份就是双份
维护——类型一改名字就撒谎。名字的边际信息应该是**语义**（`pendingUsers` 比 `userList`
多说"未处理"），不是类型。复数表达集合（`users`），`toX/toY` 表达转换，类型信息归类型。
对照：Java 里 `users` vs `userList` 至少提示了声明类型；Kotlin 泛型推断+`val` 局部
推断后这层信息彻底免费，匈牙利残余更应清除。C++ 的 `i_ptr`/`sp_` 前缀同理是弱类型
时代的遗产。

### Item ⚠️3｜按语义选命名风格（Follow Kotlin naming conventions）

🔧 坏味道：
```kotlin
val MAX_User_Count = 10          // 半吊子常量大写
fun FindUsers() { }              // 函数用 PascalCase
class user_account { }           // 类用 snake_case
```
🔧 修正：
```kotlin
const val MAX_USER_COUNT = 10    // 编译期常量：SCREAMING_SNAKE
fun findUsers() { }              // 函数/属性：camelCase
class UserAccount { }            // 类型：PascalCase
```
理由：✅ Kotlin 官方约定：类型 PascalCase；函数/绑定/对象 camelCase；编译期常量
SCREAMING_SNAKE_CASE；类型参数单大写字母。✅ 注意 Kotlin 里只有 `const val`（顶层或
object/companion 中的编译期常量）才惯例全大写，普通 `val` 即使"事实不可变"也用
camelCase——这是与 Java `static final` 约定的真实分歧点。混用风格会让读者每个标识符
都要停下来问"这是常量还是变量？是类还是函数调用？"
对照：Java 的 `static final` 一律大写近似"所有常量"；Kotlin 区分 `const val`（编译期
内联）与运行期 `val`，命名风格跟着这个区分走。

### Item ⚠️4｜用命名参数换取可读性，但别滥用（Use named arguments）

🔧 坏味道：
```kotlin
thread(name, 1000, true, false)   // true/false 是什么？
```
🔧 修正：
```kotlin
thread(name, timeout = 1000, daemon = true, verbose = false)
// 或更好的出路：把布尔参数换成分层 API
thread(name).withTimeout(1000).asDaemon()
```
理由：✅ Kotlin 支持具名实参（`name = value`），位置歧义（连续同类型参数、布尔旗标）
当场消解。但具名参数是止痛药不是药：整串参数全具名往往说明函数吃太多配置，
应拆类型或用 DSL。布尔旗参（boolean flag）本身是坏味道——调用点看不出分支语义。
对照：Java 无具名实参，靠 Builder 模式与静态工厂方法名（`Executors.newSingleThreadExecutor`）
达到同效；Kotlin 默认参数+具名实参基本淘汰了一大半 Java Builder。

### Item ⚠️5｜单字母只留给类型参数与 lambda 参数（Name type parameters meaningfully in public APIs）

🔧 坏味道：
```kotlin
fun <T> process(t: T): List<T>            // 公开 API 上泛参数毫无信息
val sorted = users.sortedBy { u -> u.age } // 每个 lambda 都显式起名单参数
```
🔧 修正：
```kotlin
fun <Element> List<Element>.distinctCount(): Int  // 语义可点破时起名
fun <T> memoize(crossinline block: () -> T): () -> T // 惯例 T/R/U 完全可接受
val sorted = users.sortedBy { it.age }             // 单参数惯用隐式 it
```
理由：✅ Kotlin 标准库自己就用 `T/R/U`（`let` 返回 `R`、`Map<K,V>`），单字母在
**通用函数式签名**里是行业普通话，不算坏味道。真正该起名的是有领域含义的型参
（`<Key, Value>` 自研 Map、`<Input, Output>` 转换器）和超过两层嵌套、`it` 会被遮蔽的
lambda 参数（✅ 嵌套 lambda 里外层 `it` 不可见，必须显式命名或外层改用命名形参）。
对照：Java 泛型擦除后 `<T>` 只是文档级提示；C++ 模板参数 `template <typename T>` 同理，
但概念化之后（C++20 concepts，本仓 [../C++20模板元编程/06-概念和约束.md](../C++20模板元编程/06-概念和约束.md)）
约束名承担了"型参语义"，Kotlin 则靠上界 `<T : Comparable<T>>`。

### Item ⚠️6｜注释解释"为什么"，代码陈述"做什么"（Comments should explain why）

🔧 坏味道：
```kotlin
i++                 // i 加 1
// 找到第一个过期用户
val u = users.first { it.expired }
```
🔧 修正：
```kotlin
// 每个用户只计一次重试，++ 放在发送后而非循环头：
// 循环体外还有一次补发路径共享这个计数（见 retryLater）
retries++
```
理由：复述语法的注释（`i++ // i 加 1`）是纯熵：代码改了它不改就是谎言，改了它就得
同步维护两处——零信息、负价值。注释唯一不可替代的输出是**动机、约束、坑、决策记录**
（为什么不用并行流、为什么这里故意容忍竞态）。命名与表达式结构能表达"做什么"，
表达不了"为什么这样才安全/这样才快"。
对照：Effective Java 同款条目（Item 69/70 附近 ⚠️ 记忆推定）；C++ 模板元编程社区的习惯
是把"为什么"写进 static_assert 的消息里，Kotlin 没有运行期前的等价物，靠注释。

### Item ⚠️7｜KDoc 只写公开 API，且别与命名互相抵消（Document APIs with KDoc）

🔧 坏味道：
```kotlin
/**
 * getUser
 * @param id id
 * @return user
 */
fun getUser(id: Long): User? = repo.findById(id)
```
🔧 修正：
```kotlin
/**
 * 按主键读取用户。
 * 返回 null 表示不存在或已注销（软删）——调用方需区分时先 [hardExists]。
 * 注意：本函数走读副本，主从延迟内可能读到旧值。
 */
fun getUser(id: Long): User? = repo.findById(id)
```
理由：✅ KDoc 会渲染进 IDE quick doc 与 Dokka 产物，是公开 API 的契约面。参数名、
返回值类型 KDoc 已经知道，抄写无增益；契约里 KDoc 才说得出的是：null 的语义、异常、
线程/延迟假设、废弃路径（`@Deprecated` 优先，✅ 它带编译期告警而 KDoc 文字不带）。
内部私有实现不配 KDoc——那是注释（为什么）的领地，不是文档（契约）的领地。
对照：Java Javadoc 承担"生成文档+契约"双职；`@deprecated` 标签在 Java 早期也只是文字，
Java 9+ 才有 `@Deprecated` 注解级 forRemoval，Kotlin 的 `@Deprecated(level, ReplaceWith)`
一步到位可机读。

### Item ⚠️8｜消灭魔法数与隐式常量（Avoid magic numbers）

🔧 坏味道：
```kotlin
if (seconds > 3600 && code != 401 && !ip.startsWith("10.")) block()
```
🔧 修正：
```kotlin
private const val ONE_HOUR_SECONDS = 60 * 60
private const val UNAUTHORIZED = 401
private val PRIVATE_NET_PREFIXES = listOf("10.", "192.168.")

if (seconds > ONE_HOUR_SECONDS && code != UNAUTHORIZED &&
    PRIVATE_NET_PREFIXES.none { ip.startsWith(it) }
) block()
```
理由：裸字面量把"业务规则"藏进"符号形状"——`3600` 是一小时还是超时预算？`401` 出现
两次改一处漏一处。✅ `const val` 是编译期常量（顶层/object/companion 中，基本类型与
String），会被内联，零成本；带语义类型的常量（时长、金额）更进一步用 value class
（见 [04 部](04-类与接口.md) Item ⚠️）。命名常量同时是天然的注释锚点与搜索锚点。
对照：Java 的 `static final int` 编译期常量同样被内联（✅ 常量内联是 JLS 规定），
C++ 的 `constexpr` 同构——三家都懂，差别只在 Kotlin 里连"文件级私有常量"都不必先造个
`Utils` 类，顶层 `private const val` 即可。

### Item ⚠️9｜注释也要"随代码删除而删除"，过期注释比没有更毒（Keep comments up to date）

🔧 坏味道（代码重构后遗留）：
```kotlin
// TODO: 下一版换成缓存后这里要加锁  （三年后：缓存早已上线，锁语义已改）
fun load(id: Long) = dao.get(id)
```
🔧 修正：
```kotlin
// 2026-02 起 cache-aside 上线，本函数依赖缓存层的 singleflight，勿在此加锁
fun load(id: Long) = dao.get(id)
```
理由：✅ 注释随源码同版本演进，Git 历史不会替注释保鲜——错误注释是主动误导，
比无注释更糟（读者信任它才看它）。`TODO/FIXME` 必须带任务号或责任人，否则等价于
许愿。能进 issue/任务系统的不要进注释，注释只留"读这段代码的人当下必须知道的事"。
对照：Java 社区同样有 stale Javadoc 病；C++ 头文件注释与实现分离时腐烂更快，
Kotlin 单文件属性/实现同处，腐烂面小一些但一样会烂。

### Item ⚠️10｜行宽与代码宽度：换行也是格式契约（Keep lines short）

🔧 坏味道：
```kotlin
val price = items.filter { it.active }.map { it.discounted(unit) }.sumOfBigDecimal() * taxRate(taxRegion, customerTier(today()))
```
🔧 修正：
```kotlin
val activeItems = items.filter { it.active }
val netAmount = activeItems.sumOf { it.discounted(unit) }
val price = netAmount * taxRate(taxRegion, customerTier(today()))
```
理由：✅ IntelliJ/ktlint/detekt 默认行宽 100-120；一屏看不全的链式表达式把"数据流"
压成"字符串汤"。每行一个概念、给中间结果起名字，等于免费获得断点与日志位——
命名的中间值是 Kotlin 里最便宜的调试设施（✅ 链上每步可单独 `let { println(it); it }`
而不破坏表达式）。
对照：Java Stream 链的"折行玄学"（`.map` 顶格还是缩进）在 Kotlin 里用命名中间量替代；
C++ 长模板表达式（`std::enable_if_t<std::is_invocable_v<...>>`）同样是"一行装不下就
先拆别名"的同一工程直觉。

## 核心概念中英对照表

| 中文 | 英文 | 一句定义 |
| --- | --- | --- |
| 命名约定 | naming convention | 社区共识风格：类型 PascalCase，函数/变量 camelCase，常量 SCREAMING_SNAKE。 |
| 具名参数 | named arguments | 调用点写 `name = value` 消歧，✅ Kotlin 原生支持。 |
| 编译期常量 | compile-time constant (`const val`) | 顶层/object 内基本类型+String 的 `val`，编译期内联。 |
| 文档注释 | KDoc | `/** */` 契约文档，渲染进 IDE/Dokka，只写公开 API。 |
| 废弃标记 | `@Deprecated` / ReplaceWith | 机读弃用契约，带编译期告警，优于注释文字。 |
| 魔法数 | magic number | 无语义裸字面量；对策为命名常量。 |
| 类型参数命名 | type parameter naming | 通用型参用 T/R/U/K/V，领域型参应具名。 |
| 隐式 lambda 参数 | implicit parameter `it` | 单参 lambda 默认名；嵌套时外层被遮蔽。 |
| 过期注释 | stale comment | 与代码脱钩的注释，主动误导源。 |
| 表意命名 | meaningful naming | 名字承载语义而非类型；长度随作用域增长。 |
