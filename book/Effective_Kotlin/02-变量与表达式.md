## 核心概念速览（中英对照）

- **不可变性优先** — prefer immutability：`val` 默认、`var` 例外；状态越少推理面越小。
- **智能转换** — smart cast：✅ 编译器在控制流内自动收窄可空/公共子类型，无需手写 cast。
- **可变委托** — mutable delegation（`by lazy`、属性委托）：初始化时机与存储策略外置。
- **平台类型** — platform type（`T!`）：✅ Kotlin 与无注解 Java 互操作的边界区，空安全不被编译器担保。
- **表达式优先** — expression-oriented style：`if`/`when`/`try` 皆有值（✅ Kotlin 中它们是表达式），减少语句级中间变量。

## 条目清单（⚠️ 编号推定，本部 10 条）

### Item ⚠️11｜默认写 val，把 var 当需要辩护的例外（Reduce mutability）

🔧 坏味道：
```kotlin
var total = 0.0
for (i in items) {
    if (i.active) total += i.price
}
```
🔧 修正：
```kotlin
val total = items.filter { it.active }.sumOf { it.price }
```
理由：✅ `val` 只承诺引用不可变（内容是否不可变另论），但它消除了"这个变量后面会不会
被偷偷改掉"的跟踪成本。`var`+循环体的每一次赋值都是给读者埋的一次状态断言。
"先 val，改不动再升 var"是把不可变当默认、可变当例外的最小操作方式；
函数式管道（filter/sumOf）顺手消灭了累加器这个最常见的 var。
对照：Java 老手知 `final` 局部变量同款收益，但 Java 里 `final` 是仪式、Kotlin 里 `val`
是默认语法位——`var` 得主动敲出来，心理摩擦本身就是一种 linter。C++ 的 `const auto`
教义（Herb Sutter "Concision"）完全同构。

### Item ⚠️12｜声明尽量靠近使用处，最小化作用域（Declare as late as possible）

🔧 坏味道：
```kotlin
fun handle(req: Request): Response {
    val user = userService.get(req.userId)
    val config = loadConfig()          // 60 行后才用
    val token = issueToken(user)       // 中途可能整个提前 return
    ...
}
```
🔧 修正：
```kotlin
fun handle(req: Request): Response {
    val user = userService.get(req.userId)
    if (req.isProbe()) return NO_CONTENT
    val config = loadConfig()          // 临近使用、且在提前退出之后
    val token = issueToken(user)
    ...
}
```
理由：作用域=理解成本×生命周期。✅ 声明即初始化（Kotlin 无 Java 式"先声明后赋值"
的确定赋值分析负担——`val` 必须初始化，✅ 编译器直接强制），把"取了但没用上"和
"提前 return 后白算"两类浪费消灭在结构里。靠近使用处还让命名中间量（见 01 部
Item ⚠️10）与断点一一对应。
对照：Java 8+ 的 `var` 局部推断才让"声明贴近使用"在 Java 里稍微不蠢（此前类型名太长
人们倾向堆在函数头）；C++ 同样有"declare at first use"教义，但 C++ 的初始化顺序
与 UB 纠缠更深。

### Item ⚠️13｜懂智能转换的边界，失效时改结构而不是硬 cast（Smart casts and their limits）

🔧 坏味道（智能转换失效的三种典型，🔧 待实测报错文案）：
```kotlin
var name: String? = readName()
if (name != null) {
    name = readName()          // 二次赋值
    println(name.length)       // 仍需 ?. 或 !!，智能转换被收回
}

val list = ArrayList<String>()
if (list is MutableList<*>) { }   // 永远真，白写的检查；且智能转换无意义

val s: String? = getMaybe()
if (s is String) {
    anotherVar = s               // OK：局部不可见可空转换
}
```
🔧 修正：
```kotlin
val name = readName() ?: return      // 早退后 name 是 String，全程智能转换
println(name.length)

val s: String? = getMaybe()
if (s != null) use(s)                // val/确定非空路径：编译器自动收窄
```
理由：✅ 智能转换的前提是编译器能证明"检查到使用之间值没变"：局部 `val`、非空检查
之后满足；✅ `var`（跨模块或本类之外可改的属性、可被闭包改的捕获变量）、
带自定义 getter 的属性会失效。失效时先重构结构（早退、拷贝进局部 `val`），
而不是反射弧性地贴 `!!` 或 `as String`——那把编译期证明降级成口头保证。
对照：C++ 没有等价机制，`dynamic_cast` 每次都要手写并检查 nullptr；Java 的模式匹配
`if (o instanceof String s)`（JEP 395）是"限定作用域自动转换"，比 Kotlin 智能转换弱
（仅限该 instanceof 块内、不追踪 var 变化），Kotlin 的控制流收窄覆盖面更大。

### Item ⚠️14｜平台类型进入代码前先"落地"为明确的 T 或 T?（Handle platform types explicitly）

🔧 坏味道：
```kotlin
val name = javaUser.getName()   // String! 直接流入业务逻辑
println(name.length)            // 编译通过；Java 侧返回 null 时运行期 NPE
```
🔧 修正：
```kotlin
val name: String? = javaUser.getName()
println(name?.length ?: 0)
// 或在边界处收窄并当场失败，把爆炸半径钉在互操作行上
val name: String = javaUser.getName() ?: error("Java getName() returned null")
```
理由：✅ 无空注解的 Java 返回值是平台类型 `T!`——编译器不强制检查、也不承诺安全，
NPE 会延迟到离雷区很远的地方炸。在互操作**边界行**就把它落成 `T` 或 `T?`（带显式类型
标注），是把"哪层负责空安全"写死在结构上；给 Java 库源码/依赖加
`org.jetbrains.annotations.@Nullable/@NotNull` 是根治路径（✅ 编译器识别注解）。
对照：C++ interop 没有"编译器半信半疑"的中间态——extern "C" 进来的一切类型直接信任，
空指针检查全靠人肉纪律，Java 平台的 `T!` 反而是 Kotlin 给的额外提示层。

### Item ⚠️15｜可空是传染的：别为省一个 if 让整个签名变 T?（Don't introduce nullability needlessly）

🔧 坏味道：
```kotlin
fun findUser(id: Long): User? = db.get(id)
fun greet(id: Long): String? = "Hi " + findUser(id)?.name   // 被迫可空
```
🔧 修正：
```kotlin
fun requireUser(id: Long): User = db.get(id) ?: throw NoSuchElementException("no user $id")
fun findUserOrNull(id: Long): User? = db.get(id)   // 可空语义真需要时才单独提供
fun greet(id: Long): String = "Hi " + requireUser(id).name
```
理由：✅ `T?` 会迫使每个下游调用点处理 null，把"这里可能没有"扩散成签名层面的流行病。
函数应选**自己语义的真实版本**：业务上"必有"就用 `requireX` 早抛（异常路径）；
"可能没有且调用方要分情况"才给 `findXOrNull`。两个入口分别命名，可空性成为文档而
非意外。
对照：Java 用 `Optional` 做同类区分（`find` 返回 `Optional<User>`），✅ 代价是 Optional
本身可 null 的著名坑（Stuart Marks 专文）；C++23 的 `std::expected<T, E>` 走的是
"要么值要么错"第三条路，语义上比 `T?`+异常都更诚实。

### Item ⚠️16｜elvis 与早退组合，把空检查从嵌套 if 里解放出来（Use elvis with return/throw）

🔧 坏味道：
```kotlin
fun pay(order: Order) {
    val acc = order.account
    if (acc != null) {
        if (acc.balance >= order.amount) {
            acc.charge(order.amount)
        } else {
            throw NotEnoughFunds()
        }
    } else {
        throw NoAccount()
    }
}
```
🔧 修正：
```kotlin
fun pay(order: Order) {
    val acc = order.account ?: throw NoAccount()
    if (acc.balance < order.amount) throw NotEnoughFunds()
    acc.charge(order.amount)
}
```
理由：✅ `a ?: b` 中 b 可以是 throw/return（右侧表达式短路整个函数），这让"异常即
退出路径"写成一行、主流程零缩进（guard clause 风格）。嵌套 if 把 happy path 推到
最里层，diff 时一行改动抖三层缩进；早退把每条失败规则拍平成平行的一行。
对照：Java 同样讲 guard clause（Effective Java 同款口味），但没有 elvis——
`Objects.requireNonNull(acc, ...)` 抛的是 NPE 族而非领域异常，表达力差一档；
C++ 里对应习惯是 `if (!acc) throw ...;` 前置检查链。

### Item ⚠️17｜区分 lateinit / by lazy / 可空，别用 lateinit 当可空的替代品（Choose the right initialization tool）

🔧 坏味道：
```kotlin
class Svc {
    lateinit var conn: Connection   // "应该初始化好了吧" 全靠运气
    fun handle() { conn.send() }    // 忘了初始化 → 运行期 UninitializedPropertyAccessException
}
```
🔧 修正：
```kotlin
class Svc(deps: Deps) {
    val conn: Connection by lazy { deps.factory.open() } // 首次访问才建，之后缓存
    // 或：构造注入，根本不存在"中间态"
}
```
理由：✅ `lateinit` 只适用于非空 var、不能用于可空类型与基本类型（语义上它用 null
存储但禁止你看见 null）、访问未初始化即抛专属异常——适合框架反射注入场景；
✅ `by lazy` 适合"昂贵、可能永远用不到、线程安全默认"的延迟初始化；
✅ 可空 `T?` 适合"确实可能没有"的领域事实。三者各回答一个不同的问题，用错就是
把编译期问题搬进运行期。
对照：Java 靠构造器+final 字段把"无中间态"做成默认纪律（Effective Java Item ⚠️推定：
考虑静态工厂）；Spring 字段注入 `@Autowired` 的 lateinit 化在 Kotlin 里至少还有
编译期可读的失败信息，Java 里是裸 NPE。C++ 没有反射注入文化，对应物是
`std::optional` 成员 vs 构造期强制。

### Item ⚠️18｜if/when 是表达式：用返回值替代"先声明 var 再分支赋值"（Favor expression-oriented style）

🔧 坏味道：
```kotlin
var label: String
if (score > 90) label = "A"
else if (score > 60) label = "B"
else label = "C"
```
🔧 修正：
```kotlin
val label = when {
    score > 90 -> "A"
    score > 60 -> "B"
    else       -> "C"
}
```
理由：✅ `if`/`when`/`try` 在 Kotlin 里是表达式，分支合流点必然完成初始化
（✅ 漏一个分支编译报"when must be exhaustive"，对密封类型是免费的规则完整性检查）。
`val`+`when` 把"每个 label 必有值"从人肉断言变成编译器定理；Java 的三元链和
switch 赋值（✅ Java 14+ 才有 switch 表达式）在 Kotlin 是出厂设置。
对照：C++ 没有 if 表达式，只有三目 `?:` 链与 IIFE（lambda 立即调用）硬凑——
Kotlin 的 `run { ... }` 当块表达式用与之同构；Java 老手需补一课：这里没有
fallthrough 这个坑（✅ `->` 不贯穿）。

### Item ⚠️19｜字符串模板优先，复杂插值降级为普通语句（Use string templates）

🔧 坏味道：
```kotlin
val msg = "Hello " + name + ", your order " + orderId + " ships in " + days + " days"
```
🔧 修正：
```kotlin
val msg = "Hello $name, your order $orderId ships in $days days"
val total = "Total: ${order.amount * rate}"   // 表达式插值用花括号
```
理由：✅ `$x` 插值简单名、`${expr}` 插值表达式，可读性对齐文案本身；拼接版把标点、
空格、转义拆进字符串边界里，多语言迁移时模板还能整体当资源看。过度花哨的插值
（模板里套 lambda）才是反模式——那时抽出来。
对照：Java 字符串 `+` 编译后本来就是 StringBuilder/`makeConcat`（✅ JDK9+ 的
StringConcatFactory），"模板更省"是可读性收益不是性能收益；C++20 的 `std::format`
（`format("Hello {}", name)`）是同类动机，但格式串与实参分离，类型安全靠编译检查
而非作用域可见性。

### Item ⚠️20｜别造"只有一个值的包装流程"：链上每个中间量都该挣得自己的名字（Avoid pointless temporaries）

🔧 坏味道：
```kotlin
val tmp = users.map { it.name }
val sortedTmp = tmp.sorted()
val result = sortedTmp.take(10)
return result.joinToString()
```
🔧 修正：
```kotlin
return users.map { it.name }
    .sorted()
    .take(10)
    .joinToString()
```
理由：Item ⚠️12/13 教我们把值提出来命名；本条管住反向：**纯搬运**的中间量
（只为"下一步要用"而存在、不新增语义）是变量声明通胀。判据是"名字是否传达
读流水线读不出的信息"——`netAmount` 有信息（汇总额）、`tmp` 没有。链式 vs 展开
没有教条：调试期展开、稳定后收成表达式体，命名裁决跟着信息量走。
对照：Java Stream 链几乎强迫你单表达式（局部变量反而啰嗦）；C++ 范围库（本仓
[../C++20模板元编程/09-范围库.md](../C++20模板元编程/09-范围库.md)）`views | transform | take`
的管道语法是同一审美，只是 Kotlin 用点号不用竖线。

## 核心概念中英对照表

| 中文 | 英文 | 一句定义 |
| --- | --- | --- |
| 不可变引用 | immutable reference (`val`) | 绑定不可重赋，不担保被指对象不可变。 |
| 智能转换 | smart cast | 控制流分析在证明值未变后自动收窄类型。 |
| 平台类型 | platform type (`T!`) | 无注解 Java 值的 Kotlin 表示，空安全不担保。 |
| Elvis 运算符 | elvis operator (`?:`) | 左侧为 null 时取右侧，右侧可为 throw/return。 |
| 守卫子句 | guard clause | 失败条件一行早退，主流程不嵌套。 |
| 延迟初始化 | `lateinit` / `by lazy` | 前者非空 var 框架注入，后者首次访问求值并缓存。 |
| 表达式体 | expression body | 函数/分支直接以表达式为值，免 `return` 样板。 |
| 穷尽检查 | exhaustiveness check | `when` 对密封类型/Boolean 缺分支编译报错。 |
| 字符串模板 | string template | `$name`/`${expr}` 内嵌插值。 |
| 中间量通胀 | temporary inflation | 无语义增值的临时变量，流水线可读性之敌。 |
