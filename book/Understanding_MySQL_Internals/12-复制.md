# 第 12 章 复制（Replication ⚠️ 英文章题反构）

> 原书章：第 12 章（中文正版目录实抓：「复制」）。二级小节**全部实抓**：概述 / 基于语句与基于行 / 双线程从服务器 / 多主服务器 / SQL 命令 / 二进制日志格式 / 自定义复制实用程序。
> 语境基线：4.1/5.0——**SBR 为默认、从库只有 IO + SQL 两个线程、位置靠 binlog 文件名 + 偏移**（GTID 与并行复制都还没出生）。
> 旁证：中文旧笔记残留的模块清单里就有「主复制服务器模块 / 从复制服务器模块」两项（✅ 见 [../深入理解MySQL核心技术.md](../深入理解MySQL核心技术.md)），与本章结构吻合。

## 12.1 本章地图

| 节 | 内容 | 2007 年口径的结论 |
| --- | --- | --- |
| 概述 | 主库写 binlog，从库拉取并重放；异步、最终一致 | 复制是「日志重放系统」，不是「数据同步系统」 |
| SBR vs RBR | 语句格式紧凑但可不确定；行格式安全但体积大（5.1 才完善） | 本章第一次把「复制正确性」摆上台面 |
| 双线程从库 | IO 线程写 relay log，SQL 线程串行重放 | 重放单线程 = 延迟不可控的根因 |
| 多主 | 环形互指、`auto_increment_increment/offset` 错开自增 | 冲突不发生 ≠ 冲突被解决 |
| SQL 命令 | `SHOW MASTER STATUS` / `CHANGE MASTER TO` / `START SLAVE` 一族 | 位置型（file+pos）运维语言 |
| binlog 格式 | 事件流：公共头 + 事件体；`mysqlbinlog` 可读 | 事件类型表是排障字典 |
| 自定义实用程序 | 用客户端库/UDF 自己消费 binlog 或注入复制事件 | 「把 binlog 当数据流」的最早官方许可 |

## 12.2 概述与机制骨架（历史语境）

- **三件事的定义**：主库把「改变数据的语句/行变更」按事务顺序写进二进制日志；从库的 **IO 线程**伪装成一个特殊客户端（`COM_REGISTER_SLAVE` + `COM_DUMP`）把日志流抄进 relay log；从库的 **SQL 线程**把 relay log 里的内容重放成本地事务。本章全部讨论都建立在这三件事上，见 [04-客户端与服务器通信.md](04-客户端与服务器通信.md) 的协议视角。
- **位置而非身份**：5.0 的复制进度就是 `(binlog 文件名, 偏移)`。它带来两个今天的运维常识级痛点：主库切换要人工换算坐标、多主/级联时坐标会「同名不同内容」——GTID 就是为消灭这两个痛点而生（5.6+，⚠️ 版本点转述；现代页 https://dev.mysql.com/doc/refman/8.4/en/replication-gtids.html ）。
- **异步与崩溃安全的耦合**：`sync_binlog`、`innodb_flush_log_at_trx_commit` 的「双 1」话题，本质就是第 11 章那套早期两阶段的落地参数（见 [11-事务.md](11-事务.md) 11.5）：redo 与 binlog 谁先落盘决定崩溃后从库会不会收到主库其实没提交的事务。
- **表锁与复制格式的隐藏连线（本轮实测细节）**：8.4 `include/thr_lock.h` 注释写明 `TL_READ_DEFAULT` 在 `open_tables()` 会「**依二进制日志格式**」变成 `TL_READ` 或 `TL_READ_NO_INSERT`（✅ 实测文件）。也就是说 SBR/混合模式会改变 Server 层的锁类型——书中把「基于语句与基于行」当格式问题讲，今天可补一句：**它同时是并发与正确性问题**。

## 12.3 基于语句 vs 基于行 vs 混合（本章的思想含量所在）

| 维度 | SBR（语句，书中默认） | RBR（行） | MIXED |
| --- | --- | --- | --- |
| 日志内容 | 原始 SQL 文本 | 变更前后行镜像 | 默认 SBR，遇不安全语句自动切 RBR |
| 体积 | 小 | 大（尤其宽表 UPDATE） | 折中 |
| 不确定性风险 | `NOW()`/`RAND()`/无 `ORDER BY` 的 `LIMIT`/未定义顺序聚合 → 主从可能不同结果 | 低（位置仍需主键/唯一定位） | 低 |
| 可审计性 | 高（能直接看懂做了什么） | 需工具翻译事件 | 高 |
| 断言 | 书中还讲到「语句格式让从库可以复用优化器」 | 5.0/5.1 过渡期实现细节 ⚠️ | — |
- **本章最值得记住的判读法**：不确定性强弱 = 「重放结果是否只取决于数据状态而不取决于执行环境」。这个判据从 2007 用到今天，也是所有 CDC/审计系统「为什么偏爱行格式」的原始理由。现代格式定义（ROW/STATEMENT/MIXED）见 ✅ https://dev.mysql.com/doc/refman/8.4/en/replication-formats.html 。

## 12.4 双线程从库：为什么延迟无法避免

- **两个线程的分工**：IO 线程只做「抄日志 + 落 relay log + 更新 `Master_*_Pos`」，几乎不是瓶颈；SQL 线程把并行产生的写事务**串行**重放——主库 8 个核压出来的吞吐，从库 1 个线程去追，延迟是数学必然。
- **当年的缓解手段**：把从库硬件配强、拆多从库分摊读、减少大事务（因为大事务在 SQL 线程里也是原子的）、`slave_skip_errors` 之类「跳过」手段（今天官方明确反对 ⚠️ 转述）。
- **后来的答案**：并行复制（MTS，按库/按组提交顺序/按 WRITESET 依赖追踪三种粒度演进），从「双线程」变成「一 IO + N 工作线程 + 协调」；现代口径见 ✅ https://dev.mysql.com/doc/refman/8.4/en/replication-threads.html 与 https://dev.mysql.com/doc/refman/8.4/en/replication-threads-monitor-worker.html 。
- **单线程的另一面**：SQL 线程同时也是「复制正确性的守门人」——它保证按主库提交顺序应用，这正是今天所有延迟/一致性 SLA 谈判的起点。

## 12.5 多主服务器（书中口径）

- **典型拓扑**：A→B、B→A 环形（或多环），每台都开 `log-slave-updates` 才谈得上级联。
- **自增避让**：`auto_increment_increment` 与 `auto_increment_offset` 错开每台机器的自增序列，这是书中给出的「多主不撞主键」的标准手法（今天仍是多主/双活配置里的默认动作 ⚠️ 转述）。
- **真正没解决的问题**：同一条记录在两台机器上同时被改——MySQL 不检测、不仲裁，**后写的覆盖先写的**（除非业务自己加版本列）。多主把「冲突概率」压低了，把「冲突解决」留给了应用。这个判断在 2007 与 2026 都成立；今天的自动冲突处理走组复制（✅ https://dev.mysql.com/doc/refman/8.4/en/group-replication.html ），已不是本章意义上的「多主复制」。

## 12.6 SQL 命令与二进制日志格式（事件流）

- **书中时代的命令族**（历史语境，今天拼写已换代）：`SHOW MASTER STATUS`、`SHOW SLAVE HOSTS`、`SHOW SLAVE STATUS`、`CHANGE MASTER TO MASTER_LOG_FILE=…, MASTER_LOG_POS=…`、`START/STOP SLAVE`、`RESET MASTER`、`SET sql_log_bin=0`。
  - 现代拼写换代（`SOURCE`/`REPLICA` 术语族）自 8.0.22 引入、旧名进入弃用轨道 ⚠️（本轮未逐条抓 release notes 页），可核验入口：✅ https://dev.mysql.com/doc/refman/8.4/en/replication-administration.html 。
- **binlog 是事件流而不是文本文件**：每个事件＝公共头（时间戳、事件类型、从库长度、位置、标志等定长前缀）+ 事件体；文件中还有格式描述事件（FDE）等控制事件。书中「二进制日志格式」小节的读法今天仍有效：**先认事件类型，再谈排障**。
- **工具与参数**：`mysqlbinlog` 是官方读日志工具（✅ https://dev.mysql.com/doc/refman/8.4/en/mysqlbinlog.html ）；`binlog_row_image`、`binlog_format`、`expire_logs_days`/`binlog_expire_logs_seconds`、`sync_binlog`、`max_binlog_size` 属本章参数族（现代参数页 ✅ https://dev.mysql.com/doc/refman/8.4/en/replication-options-binary-log.html ）。
- **checksum 的分代差（⚠️ 转述）**：5.0 时代的 binlog 无事件校验和（本目录不写具体引入版本，除非另有实抓）；今天 `binlog_checksum` 默认启用，跨版本读日志要显式处理。

## 12.7 自定义复制实用程序（本章的尾巴，也是最有前瞻的一节）

- **书里教的事**：把 binlog 当可解析的数据流——用客户端库连上去请求日志转储、自己解析事件、或注册 UDF/写工具来做「复制的旁路消费者」。2007 年这是「自己写同步工具」的小众玩法。
- **这条路的今天**：它就是 CDC（Change Data Capture）产业的原点。主流开源实现是 Debezium（✅ https://github.com/debezium/debezium ）一类基于 binlog 事件解析的连接器；MySQL 官方侧也给了 Clone/组复制/`performance_schema` 复制表等标准化设施（⚠️ 未逐一抓页，入口在 12.6 的 administration 页）。
- **判读方式**：任何「MySQL→外部系统」的实时链路，都要回答本章的三问：①读 statement 还是 row 事件？②坐标用 file+pos 还是 GTID？③崩溃后从哪里续读且幂等？——这三问在书中已有雏形。

## 12.9 常见误区与修正

| 误区 | 修正 |
| --- | --- |
| 「主从延迟是网络问题」 | 常见根因是 SQL 线程串行重放 + 主库大事务；先分层定位再谈网络（12.4） |
| 「多主=高可用」 | 多主只是双写拓扑；冲突仲裁与自动故障切换要靠检测/仲裁层（组复制）或应用设计 |
| 「binlog 就是 SQL 日志」 | 它是**事件流**，行格式下根本没有 SQL 文本；工具解析事件而非读语句 |
| 「有复制就有备份」 | 复制不做保留策略与一致性快照，本书也无备份专章（见 [00-总览与阅读地图.md](00-总览与阅读地图.md) 的勘误节）；备份体系在 [../高性能mysql.md](../高性能mysql.md) 一侧 |

## 核心概念速览（中英对照）

1. **二进制日志** — binary log：Server 层按提交顺序记录变更的事件流文件。
2. **中继日志** — relay log：从库 IO 线程落盘、SQL 线程消费的本地日志。
3. **IO 线程 / SQL 线程** — replication threads：双线程从库的两个角色（抄日志 / 重放）。
4. **基于语句的复制** — SBR：日志里存 SQL 文本，重放即再执行一次。
5. **基于行的复制** — RBR：日志里存前后行镜像，与执行环境无关。
6. **混合模式** — MIXED：默认 SBR、遇不确定语句自动切 RBR。
7. **不确定性** — nondeterminism：同输入不同结果使主从可能不一致的语句属性。
8. **复制坐标** — replication position：`(binlog 文件, 偏移)`，5.0 的进度表示。
9. **GTID** — global transaction identifier：全局事务号，取代坐标定位（书后时代）。
10. **环形多主** — circular multi-master：互为主从的拓扑，靠自增步长避让冲突。
11. **事件公共头** — common event header：每个 binlog 事件的定长前缀。
12. **格式描述事件** — format description event：日志开头的自描述事件，工具解析的起点。
13. **半同步** — semi-sync：至少一个从库确认收到日志才返回提交（书后时代）。
14. **并行复制** — parallel replication / MTS：多工作线程按依赖重放（书后时代）。
15. **自定义复制实用程序** — custom replication utility：把 binlog 当数据流消费的工具（CDC 前身）。

- **未能核验项（保持 ⚠️）**：RBR 成为默认、GTID/并行复制/WRITESET 引入的确切小版本点、binlog 校验和与加密的引入版本、旧复制术语的移除版本——本轮未逐条抓 release notes，凡涉及具体版本号的句子一律标 ⚠️ 或写成「书后时代」。
- **2024–2026 工业实践**：①**默认姿势已换代**——RBR + GTID + 并行复制 + 半同步/组复制，本章的「双线程 + file/pos」只出现在遗留系统里，读它的能力＝接手老系统的能力；②**拓扑判断标准**：异步（吞吐优先）→ 半同步（少丢数据）→ 组复制/多数派（自动故障切换 + 冲突检测），三级阶梯与本章 12.5 的「多主不仲裁」形成对照；③**CDC 成为标配**：把 binlog 当数据流消费（Debezium ✅ https://github.com/debezium/debezium ）已比「读 binlog 排障」更常用，本章 12.7 是这条产业线的文献起点；④**连接层配套**：复制本质上占连接与线程资源，池化与代理（ProxySQL ✅ https://github.com/sysown/proxysql ）时代要为主从链路预留容量（呼应 [06-基于线程的请求处理.md](06-基于线程的请求处理.md)）。
