## 7.2 双对象模型：handler 与 handlerton

- **一句话分工**：`handlerton` 是「引擎这个人」，`handler` 是「他手里拿着的那张表的工具」。Server 层在打开一张表时，先按 `.frm`/表定义确定引擎，再从该引擎的 handlerton 上的工厂函数要一个 handler 实例，此后 `TABLE->file` 就是这个实例。
- **官方示例里的工厂**（ha_csv-5.1.cc，✅ 逐字读过）：`handlerton csv_hton = { MYSQL_HANDLERTON_INTERFACE_VERSION, csv_hton_name, SHOW_OPTION_YES, csv_hton_comment, DB_TYPE_BLACKHOLE_DB, …, csv_create_handler, … }`，`csv_create_handler(TABLE_SHARE *table) { return new ha_csv(table); }`，构造函数 `ha_csv(TABLE_SHARE *t) : handler(&csv_hton, t) {}`——**handlerton 指针在基类构造时交出去**，这就是两对象的绑定点。
- **能力声明位置不同层**：表级能力走 `table_flags()`（示例里 `return HA_NOT_EXACT_COUNT;` 明确告诉优化器「别拿 records 当 COUNT(*) 的答案」），索引级能力走 `index_flags()`（示例 `return 0;`，即「我没有键」），引擎级能力走 handlerton 的 flags（示例 `HTON_CAN_RECREATE | HTON_ALTER_CANNOT_CREATE`）。三层标志是 Server 层「按引擎降级功能」的实现根据（呼应 [01-MySQL历史与架构.md](01-MySQL历史与架构.md) 的能力位图）。
- **引擎「是不是事务型」不由 handler 决定**，而由 handlerton 上的 `commit/rollback/prepare/recover/savepoint` 函数槽是否非空决定（第 11 章展开）。示例引擎把这些槽**全部填 NULL**——这恰好是书中「非事务引擎长什么样」的最佳教具。
- **教学引擎谱系的命名提醒**：官方示例叫 `ha_csv`（引擎名 `OREILLY_CSV`），MySQL 真正的 CSV 引擎源码文件是 `storage/csv/ha_tina.cc`（社区流传「tina 取自 Monty 女儿之名」⚠️ 未见官方出处）。两者同构，本目录一律以能实测的两份代码为准，不把「ha_tina 是书中引擎」当事实写。

## 7.3 只读引擎必须实现的方法（按官方示例逐条）

| 方法（5.1 示例签名） | 谁在什么时候调 | 示例里的做法 |
| --- | --- | --- |
| `open(name, mode, test_if_locked)` | 表被打开（可能来自表缓存） | `thr_lock_init` + `thr_lock_data_init`、`my_malloc(CSV_INFO)`、`fn_format(..., ".csv", ...)`、`my_open`，游标 `pos=0` |
| `close()` | 表关闭 | `thr_lock_delete`、`my_close`、`my_free` |
| `rnd_init(scan)` | 全表扫描开始前 | 头文件里内联：`pos=0; records=0; return 0;` |
| `rnd_next(buf)` | 扫描每一行 | 先 `ha_statistic_increment(&SSV::ha_read_rnd_next_count)`，再 `fetch_line(buf)`，成功则 `records++` |
| `rnd_pos(buf, set_pos)` | filesort 之后按位置回读 | `pos = my_get_ptr(set_pos, ref_length)` 后 `fetch_line(buf)` |
| `position(record)` | 记下当前行位置 | `my_store_ptr(ref, ref_length, pos)`（`ref_length` 决定位置编码宽度） |
| `info(flags)` | 每次要统计量时 | **把 `records` 抬到至少 2**，防止优化器认为「最多一行」；其余展示量置 0 |
| `external_lock(thd, lock_type)` | 表锁管理器加完锁后的引擎侧钩子 | `return 0`（示例无需文件锁，MyISAM 才需要） |
| `store_lock(thd, to, lock_type)` | 语句规划阶段收集本表要加的锁 | 把 `&lock` 挂到返回链上（详见 [08-并发访问与锁定.md](08-并发访问与锁定.md)） |
| `create(name, form, info)` | DDL 建表 | 示例里 `return 0`（.csv 文件由人放到 datadir） |
| `bas_ext()` | 引擎的文件扩展名清单 | `return csv_ext;`（`{".csv", 0}`） |
| `table_flags()` / `index_flags()` | 能力询问 | `HA_NOT_EXACT_COUNT` / `0` |

- **`fetch_line()` 才是本章的真正教材**：示例用 512 字节块 `my_pread` 逐字节状态机解析 CSV（引号内不认逗号/换行、`\\` 转义、`""` 表字面双引号），每遇字段边界就 `(*field)->store(field_buf.ptr(), field_buf.length(), system_charset_info)`——**字段对象自己负责把文本变成内存里的行**，行末再 `memset(buf, 0, table->s->null_bytes)` 清 NULL 位图、未出现的字段 `set_default()`。读完这段，「Server 层的记录缓冲到底是谁填的」这个问题就永久解决了。
- 错误返回的约定：`HA_ERR_END_OF_FILE` 表示扫完（示例里读块失败或读到 0 字节都归一为此码），其它 `HA_ERR_*` 上抛由 Server 层映射成 SQL 错误。**引擎不许对调用方抛 C++ 异常**（示例通篇返回整数码）。

## 7.4 三方对读：4.1 → 5.1 → 8.4 的接口漂移（实测）

| 位置 | 4.1 示例 | 5.1 示例 | 8.4 `ha_tina.cc` | 漂移含义 |
| --- | --- | --- | --- | --- |
| 引擎注册 | 无 handlerton，改树编译 | `handlerton csv_hton={…}` + `mysql_declare_plugin(oreilly_csv)` | `st_mysql_storage_engine csv_storage_engine={MYSQL_HANDLERTON_INTERFACE_VERSION}` + `tina_init_func` 里逐字段赋值 | 位置初始化 → 声明式插件 → 回调内赋值（字段太多不敢按位排） |
| 工厂签名 | — | `csv_create_handler(TABLE_SHARE*)` | `tina_create_handler(handlerton*, TABLE_SHARE*, bool, MEM_ROOT*)` | hton 与内存分配器进入构造路径 |
| 建表 | — | `create(name, TABLE *form, HA_CREATE_INFO*)` | `create(name, TABLE*, HA_CREATE_INFO*, dd::Table*)` | 数据字典对象穿透到引擎 |
| 打开表 | `open(name, mode, test_if_locked)` | 同左 | `open(name, int, uint open_options, const dd::Table*)` | 同上；`.frm` 时代结束 |
| 扩展名 | `bas_ext()` | `bas_ext() const` | `tina_hton->file_extensions` | 从 handler 虚函数上移到 hton |
| 统计计数 | `statistic_increment(ha_read_rnd_next_count, &LOCK_status)` | `ha_statistic_increment(&SSV::ha_read_rnd_next_count)` | `ha_statistic_increment(&System_status_var::ha_read_rnd_next_count)` | **全局计数 + mutex → 会话级计数**（正是第 6 章「组锁」路线的落地样本） |
| NULL 位图 | `table->null_bytes` | `table->s->null_bytes` | 走 `TABLE_SHARE` | TABLE 与 TABLE_SHARE 职责切分 |
| 指针存取 | `ha_get_ptr` | `my_get_ptr` | `my_get_ptr` | 工具库命名归一 |
| 能力标志 | — | `HTON_CAN_RECREATE \| HTON_ALTER_CANNOT_CREATE` | `HTON_CAN_RECREATE \| HTON_SUPPORT_LOG_TABLES \| HTON_NO_PARTITION` | `HTON_ALTER_CANNOT_CREATE` 在 8.4 CSV 里已不见（✅ grep 计数 0） |
| 新增钩子 | — | — | `rm_tmp_tables`、`is_supported_system_table`、`check_if_incompatible_data` | 临时表治理与 DD/系统表白名单 |

- **同一份 `store_lock()` 从 2007 活到今天**：4.1 示例、5.1 示例与 8.4 `ha_tina.cc` 的函数体在语义上逐字同构（`if (lock_type != TL_IGNORE && lock.type == TL_UNLOCK) lock.type = lock_type; *to++ = &lock;`）。这是本目录判断「哪段书的内容仍是有效知识」的样板：**接口骨架长寿，签名与注册方式短命**。

### 代码摘录（逐字取自 `ha_csv-5.1.cc`，✅ 官方示例，O'Reilly 允许引用示例代码）

```c
handlerton csv_hton= {
  MYSQL_HANDLERTON_INTERFACE_VERSION,
  csv_hton_name,                 /* "OREILLY_CSV" */
  SHOW_OPTION_YES,               /* SHOW ENGINES 里可见 */
  csv_hton_comment,
  DB_TYPE_BLACKHOLE_DB,          /* 示例偷懒复用了 BLACKHOLE 的类型枚举 */
  ...
  0,       /* savepoint size. */
  NULL,    /* savepoint */  NULL,    /* rollback to savepoint */
  NULL,    /* commit */     NULL,    /* rollback */   NULL, /* prepare */
  NULL,    /* recover */    NULL,    /* commit_by_xid */
  ...
  csv_create_handler,            /* Create a new handler */
  ...
  HTON_CAN_RECREATE | HTON_ALTER_CANNOT_CREATE,
  NULL,    /* binlog_func */  NULL, /* binlog_log_query */
};
```

- 读这段的最佳方式是**把它当第 11 章的反面教材**：事务槽整排 NULL、`binlog_*` 也 NULL、`savepoint size` 为 0——Server 层据此判定「此引擎不参与事务、不参与两阶段」。书中「非事务引擎如何声明」这件事，官方代码一句话不用写就演示完了。
- `DB_TYPE_BLACKHOLE_DB` 是示例的取巧处：不新增 `enum db_type` 就能跑，代价是 `SHOW TABLE STATUS`/`ENGINE=` 的类型识别要另靠 `table_type()`（示例头文件里 `return "OREILLY_CSV";`）。今天写引擎必须老老实实注册自己的 `db_type`。

## 7.5 「向 MySQL 添加定制存储引擎」的当年流程（历史语境）

1. 复制示例的 `.h/.cc`，按书中「目录布局」放进 `sql/`（4.1）或 `storage/<name>/`（5.1）。
2. 在 4.1 路线里要改服务器侧的引擎注册表与构建文件，重新编译整个 mysqld；在 5.1 路线里改为提供 `.so` + `mysql_declare_plugin` 块，`INSTALL PLUGIN` 装载。
3. 实现必要 handler 方法（见 7.3 清单）；在 handlerton 上声明能力与事务槽（若无事务则留 NULL）。
4. 用 `CREATE TABLE ... ENGINE=OREILLY_CSV`（示例引擎名）验证 Server 层能路由到你；用 `SHOW ENGINES` 看 `Support` 列。
5. 调试路径回到第 2 章：断点打在 `open`/`rnd_next`/`store_lock`，盯 `TABLE::file`、`ref`、`records`。

## 7.7 常见误区与修正

| 误区 | 修正 |
| --- | --- |
| 「handler 就是存储引擎」 | handler 是**每表一个**的会话句柄；引擎级单例是 handlerton |
| 「不实现 `write_row` 会编译失败」 | 不会——基类有默认实现返回「不支持」；只读引擎正是靠这点只写读路径 |
| 「`records` 就是真实行数」 | 示例专门在 `info()` 里把 `records` 抬到 ≥2 并用 `HA_NOT_EXACT_COUNT` 拒绝被当作 COUNT(*) 答案 |
| 「按示例代码可直接编译 8.x 引擎」 | 签名与注册方式已换代（见 7.4），可复用的只有方法职责划分 |

## 7.8 三问三答（本章高频疑问卡）

- **Q1：为什么 MySQL 能把接口维持近二十年不换掉？**
  A：因为换的是「注册与签名」，不换「职责划分」：打开/关闭、两种扫描（顺序与按位置）、索引读写、加锁钩子、统计量上报这五组语义从 4.1 到 8.4 都在，只是每次加一批可选钩子。
- **Q2：官方示例为什么要同时给 4.1 和 5.1 两份源码？**
  A：等于公开了一份「接口 diff」。把两份文件对照读（本目录 7.4 表就是这么来的），比任何文字描述都直观地说明插件化那次改动有多大。
- **Q3：今天还值得自己写引擎吗？**
  A：作为训练极值得（8.4 的 CSV/BLACKHOLE 代码量都很小，且官方示例仍在库里）；作为产品要想清楚 DD、分区、事务、复制四件事都得跟，成本远高于 2007。

## 核心概念速览（中英对照）

1. **handler 类** — handler：每表一个的引擎句柄，Server 层与存储后端的唯一通道。
2. **handlerton** — handlerton：引擎级单例描述表，含名字、能力标志、事务槽、工厂函数。
3. **工厂函数** — create handler：handlerton 上负责 new 出 handler 实例的回调。
4. **顺序扫描** — record scan：`rnd_init`/`rnd_next`/`rnd_pos`/`position` 组成的游标协议。
5. **位置引用** — ref / ref_length：把「行在哪」编码成可排序可回放定长字节。
6. **能力标志** — table flags / index flags：`HA_NOT_EXACT_COUNT` 等按表/按索引声明引擎自我限制的位标志。
7. **NULL 位图** — null bitmap：记录缓冲开头的空值标记区（`table->s->null_bytes`）。
8. **字段自解码** — Field::store：由 Field 对象把原始字节写进记录缓冲的正确偏移。
9. **外部锁钩子** — external_lock：表锁加完后引擎侧的补充动作。
10. **锁登记** — store_lock：语句规划期把本表的锁需求交给表锁管理器。
11. **教学引擎** — teaching engine：官方示例 `ha_csv` 与真实 CSV 引擎 `ha_tina` 的同构样本。
12. **插件式引擎** — pluggable storage engine（5.1 起）：以 `mysql_declare_plugin` 注册的引擎。
13. **接口漂移** — API drift：同语义方法在不同大版本里的签名与注册方式变化。
14. **数据字典钩子** — dd::Table 参数：8.0 起进入 handler 的元信息入口。

## 最新演进与工业实践

- **接口现状（转述 + 实测文件）**：8.4 的 `sql/handler.h` 与 `storage/csv/ha_tina.cc` 均实测可达，可核验本章 7.4 每一格：https://github.com/mysql/mysql-server/blob/8.4/sql/handler.h 、https://github.com/mysql/mysql-server/blob/8.4/storage/csv/ha_tina.cc 、https://raw.githubusercontent.com/mysql/mysql-server/8.4/storage/csv/ha_tina.cc 。官方引擎文档索引：https://dev.mysql.com/doc/refman/8.4/en/storage-engines.html 。
- **8.x 引擎必答题清单（相对本书新增的四个方向）**：事务性数据字典集成（https://dev.mysql.com/doc/refman/8.4/en/data-dictionary.html ）、原子 DDL（https://dev.mysql.com/doc/refman/8.4/en/atomic-ddl.html ）、分区兼容（https://dev.mysql.com/doc/refman/8.4/en/partitioning.html ）、并行扫描与迭代器执行器（`sql/iterators/`，8.4 有 `hash_join_iterator.h` 等 ✅ 实测 200）。
- **今天仍活着的非 InnoDB 引擎**（8.4 文档实测 200 为据）：MEMORY（https://dev.mysql.com/doc/refman/8.4/en/memory-storage-engine.html ）、MyISAM（https://dev.mysql.com/doc/refman/8.4/en/myisam-storage-engine.html ）、CSV/Archive/Federated/MERGE 各有专页（同域 `archive-`/`federated-`/`merge-`）。这比「InnoDB 一统」的通俗说法更准确：**接口仍然多路，只是默认只剩一路**。
- **工业实践提示**：写新引擎在 2026 年主要发生在三类场景——云厂商自研后端、AI/向量与列式存取适配层、归档与外部数据联邦。评估时先把 handler 的 DD/分区/事务/复制四件事列成清单，缺一项就要在 Server 层降级对应功能；这与本章「能力位图决定降级面」的结论完全一致。
- **练手路径**：O'Reilly 官方示例镜像（https://github.com/dev2sec/Understanding-MySQL-Internals ）里的 `ha_csv-5.1.*` 是最小可读样本；进阶直接读 8.4 的 `storage/csv/` 与 `storage/blackhole/`，两者的 handler 实现规模都适合通读。
