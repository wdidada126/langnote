## 4.2 核心精讲（历史语境）

- **极简主义的胜利**：经典 MySQL 协议没有会话恢复、没有流控、没有多路复用——一条连接同一时刻只做一件事（半双工）。书中把「包→命令→响应」的机械循环讲得极清楚，这恰是理解后来一切补丁（压缩、SSL、预编译、二进制结果集）为何长成那样形状的原点。
- **包格式的三个设计点**（书中原样展开）：长度字段限 16MB（大对象要开 `max_allowed_packet` 的口子）；序号字段用于分包与丢包检测；payload 首字节是命令/状态字。今天抓包看 MySQL，这三点仍是第一课。
- **4.1 认证握手的历史地位**：4.1 把 mSQL 时代的明文风险问题正式解决（`SHA1(password) XOR` 方案，即 mysql_native_password 的前身形态），书中「验证握手」小节就是这次变更的第一手描述。注意：该方案后来又被 8.0.4 起的 caching_sha2_password（SHA256 + 快速缓存路径）取代——书中内容进入「历史语境」。
- **能力协商**：capability flags 一个 32 位字段挤满了扩展（压缩、SSL、预编译、结果集元数据……），客户端与服务器取交集。这套「加法哲学」一直延续到 8.x 的扩展能力位（如查询属性、会话状态跟踪）。
- 教学示意（不参与构建）：一条 `SELECT` 的完整线上生命 = 握手 → COM_QUERY 包 → 列定义包 ×N → 行包 ×M → EOF；今天用任意抓包工具仍可复现该形状（转述）。

## 4.6 三问三答（本章高频疑问卡）

- **Q1：为什么说 MySQL 协议是「半双工」？今天改变了吗？**
  A：同一连接上请求-响应严格交替，无 pipeline、无并发帧。8.x 社区版仍如此；多语句仅省往返不改全双工。改变并发模型要靠「多连接」或代理层——这正是 ProxySQL/连接池繁荣的协议学原因。
- **Q2：预编译语句（prepared）安全吗？**
  A：协议层把 SQL 模板与参数分帧传输、内核分开处理，注入面显著小于字符串拼接；书中只给了 COM_STMT_* 骨架，今天应理解为「默认正确用法」。
- **Q3：想继续深挖协议读什么？**
  A：看 mysql-server 主干 `include/mysql/` 协议头与官方 Internals 文档（本网络对官方文档站 403 ⚠️，GitHub 源码树 ✅ 可达可核验）。

## 4.7 字节级精讲：包头、分包与序号（本轮复测已可直取官方协议参考）

> 口径说明：本章 4.6 Q3 保留首轮「官方文档站 403 ⚠️」的记录不改；**本轮复测**官方《MySQL Source Code Documentation》协议参考已可达，以下事实逐条取自该参考并给链接（✅ 实测 200）。

- **包的构成**（✅ https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_basic_packets.html ）：

```
Payload
  int<3>  payload_length   // 头部 4 字节之外的字节数
  int<1>  sequence_id
  string<var> payload
Example: 01 00 00 00 01   → length=1, sequence_id=0x00, payload=0x01
```

- **16MB 的确切语义（最常被写错的一行）**：payload ≥ 2²⁴−1 时长度字段填 `ff ff ff`，剩余部分继续发后续包，**直到某个包的 payload 小于 2²⁴−1**；官方给的例子是「正好 16 777 215 字节」要发成 `ff ff ff 00 …` + `00 00 00 01`（一个零长度包）。自研客户端/代理少发这个空包就会得到「包不完整」。
- **序号语义**：官方原文——sequence-id 每包递增、**可以回绕**、从 0 开始、**在命令阶段（Command Phase）新命令开始时重置为 0**。因此认证阶段一条流水、每条命令一条流水；服务端发现序号不连续即断链（`Packets out of order` 类错误的来源）。
- **实现锚点**：该页在定义下列出 See also：`my_net_write()`、`net_write_command()`、`net_write_buff()`、`my_net_read()`、`net_send_ok()`——正是第 3 章 NET 抽象的函数族；书时代这些实现位于 `sql/net_serv.cc`（✅ 5.7 树该路径实测 200；8.0/8.4 该路径已重组 ⚠️ 未能定位新文件）。
- **命令包的最小形态**（转述 ⚠️，命令枚举页本轮未逐条抓到）：payload 首字节是命令字（`COM_*` 族），`COM_QUERY` 之后直接跟 SQL 文本、不额外加终止符——「一个字节驱动整个内核」就是这一句。可核验入口：✅ https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_command_phase.html 。

## 4.8 OK / ERR 两种响应的字节骨架（实测）

- **OK 包**（✅ https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_basic_ok_packet.html ）：`header 0x00`（或 `0xFE`，见下）+ `lenenc affected_rows` + `lenenc last_insert_id`，随后按能力位分支——有 `CLIENT_PROTOCOL_41` 时是 `int<2> status_flags` + `int<2> warnings`；有 `CLIENT_SESSION_TRACK` 时再跟会话状态信息。
  - 官方给的完整例子：`07 00 00 02 00 00 00 02 00 00 00` —— 头 4 字节是「长度 7 / 序号 02」，payload 解出「0 受影响行、last_insert_id=0、status_flags=0x0002（AUTOCOMMIT 开）、0 warnings」。
  - **一个漂亮的判读规则（官方原文）**：`OK: header=0 且包长 ≥7`；`EOF: header=0xFE 且包长 <8`——**同一种帧靠长度区分语义**，这是本书「EOF 包」段落今天最容易踩的兼容坑。
  - 5.7.5 起 OK 包也被用来表示 EOF、EOF 包进入弃用；老客户端不发 `CLIENT_DEPRECATE_EOF` 就仍收 EOF——这段是本章「加法哲学/能力协商」最真实的样本。
- **ERR 包**（✅ https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_basic_err_packet.html ）：`0xFF` + `int<2> error_code` + （若 `CLIENT_PROTOCOL_41`）`'#'` 标记 + 5 字节 SQLSTATE + 文本；官方例子 `17 00 00 01 ff 48 04 23 48 59 30 30 30 4e 6f 20 74 61 62 6c 65 73 20 75 73 65 64` 解出「errno 0x0448、SQLSTATE HY000、`No tables used`」。错误文本长度受 `MYSQL_ERRMSG_SIZE` 限制（官方页原话）。

## 4.9 会话状态跟踪：本书时代没有、今天必需的一层

- 官方协议参考在 OK 包之后定义了 **Session State Information**：一串 `(int<1> type, lenenc data)` 块；`SESSION_TRACK_SYSTEM_VARIABLES` 的 data 又是「lenenc 变量名 + lenenc 变量值」。
- 给的实例（✅ 同上 OK 页）：执行 `SET autocommit = OFF` 后随的跟踪块含 `0a 61 75 74 6f 63 6f 6d 6d 69 74 03 4f 46 46`，即长度 0x0a 的 `autocommit` 与长度 0x03 的 `OFF`。
- **为什么和读者有关**：连接池/代理把「连接」抽象成可换的物理链路后，客户端无法再靠「这条连接一直是我的」来推断变量与事务状态；服务器把状态变更随响应回传，池化才能安全复用连接。这正是本章「能力协商」路线在 8.x 的最新延长线（呼应 [05-配置变量.md](05-配置变量.md) 的作用域规则）。

## 核心概念速览（中英对照）

1. **半双工协议** — half-duplex protocol：连接上请求与响应严格交替的模型。
2. **包（packet）** — packet：3 字节长度 + 1 字节序号 + payload 的传输单元。
3. **序号字节** — sequence id：分包重组与乱序检测的连接级计数器。
4. **能力位协商** — capability flags：连接建立时客户端/服务器取交集的扩展位。
5. **验证握手** — authentication handshake：盐值交换 + 散列应答的登录流程。
6. **mysql_native_password** — 经典 SHA1 认证插件（8.4 起默认停用）。
7. **caching_sha2_password** — 8.0.4 起默认认证插件（SHA256+服务端缓存）。
8. **命令字** — command byte：payload 首字节，COM_* 家族总称。
9. **预编译协议** — prepared statement protocol：COM_STMT_PREPARE/EXECUTE 二进制往返。
10. **结果集元数据** — column definition packets：列定义包族，描述字段类型字符集。
11. **EOF 包** — EOF packet：结果集边界帧（8.0 被弃用式替代）。
12. **压缩协议** — compressed protocol：整包 zlib 压缩的可选层（弃用方向 ⚠️）。
13. **VIO** — virtual I/O：TCP/Unix socket/SSL 的统一传输壳。

## 最新演进与工业实践

- **认证演进（转述）**：8.0.4 起默认 caching_sha2_password；8.4 默认停用 mysql_native_password（升级必查项）。官方文档域 dev.mysql.com 对本网络 403 ⚠️，结论以社区共识 + 源码树核验（✅ https://github.com/mysql/mysql-server ，`plugin/auth/` 与 `include/mysql/` 协议头）。
- **协议扩展的近况**：8.0.23 引入查询属性（query attributes）、会话状态跟踪（基线 5.7）持续服务连接池与代理；EOF 弃用帧成为解析器兼容清单常客（转述 ⚠️ 官方链接不可达）。
- **生态观察**：代理层（ProxySQL 等）与云托管把「连接」升级为可池化资源；协议半双工模型的扩容答案仍是「多连接」，本书第 4 章 + 第 6 章一起构成理解连接池配置的底层语言。
- **工业排障**：`max_allowed_packet` 仍是导入大 BLOB/大事务报错的第一嫌疑人（书中 16MB 包上限的现代回声）；抓包分析入门即本章包格式三件套。
- **同目录延伸**：认证插件的加载框架见 [../MySQL运维内参.md](../MySQL运维内参.md)（现代运维视角）；协议与复制帧关系见 [12-复制.md](12-复制.md)。
