# 第 11 章 事务（Transactions ⚠️ 英文章题反构）

> 原书章：第 11 章（中文正版目录实抓：「事务」）。二级小节**全部实抓**：事务存储引擎实现概述 / 实现处理器子类 / 定义 handlerton / 使用查询高速缓存 / 使用复制二进制日志 / 避免死锁。
> 语境基线：4.1/5.0——事务能力完全由存储引擎提供，Server 层只做「登记 + 编排」；查询缓存仍是内核模块；binlog 参与的早期两阶段刚成型。

## 11.2 核心精讲（历史语境）：能力在引擎，编排在 Server

- **「MySQL 有自己的事务吗」——2007 年的正确回答是：没有，只有事务编排器。** Server 层的 `Transaction_ctx`（当年挂在 THD 上）保存的是「当前语句/事务里出现过哪些 handlerton」的数组；`COMMIT` 时挨个调用它们的 `commit()`。单引擎时看起来像「MySQL 有事务」，多引擎混用时你就看见了编排层的真实面目。
- **`external_lock()` 是事务的起点**（呼应 [08-并发访问与锁定.md](08-并发访问与锁定.md)）：Server 层拿到表锁后告诉引擎「F_UNLCK / F_TO_INITIAL / F_WRLCK」这类意图，InnoDB 在这里判断「是不是本事务第一次接触这张表」，若是则登记自己的事务对象进 THD。示例引擎直接 `return 0`——**非事务引擎就是「什么都不做」**。
- **语句级 vs 事务级**： autocommit 下每条语句是一个事务，Server 层在语句结束时调 `ha_commit_trans()`；显式 `BEGIN` 后引擎需跨语句保持状态，这就是为什么 handler 实例在事务期间不能被随便关掉（书中「实现处理器子类」一节的动机）。
- **保存点（SAVEPOINT）是纯引擎能力**：Server 层维护名字到 `savepoint` 结构的映射，实际语义（回滚到什么状态）由 handlerton 的 `savepoint/set/rollback/release` 三/四个槽实现；`savepoint size` 声明引擎需要多少每事务内存。示例里为 `0`（✅ 实测：`0, /* savepoint size. */`）。

## 11.3 定义 handlerton：把「是否事务型」写成代码（实测摘录）

`ha_csv-5.1.cc` 的 `handlerton csv_hton` 里与本章有关的部分（✅ 逐字）：

```c
  0,       /* slot */
  0,       /* savepoint size. */
  NULL,    /* close_connection */
  NULL,    /* savepoint */
  NULL,    /* rollback to savepoint */
  NULL,    /* release savepoint */
  NULL,    /* commit */
  NULL,    /* rollback */
  NULL,    /* prepare */
  NULL,    /* recover */
  NULL,    /* commit_by_xid */
  NULL,    /* rollback_by_xid */
  ...
  HTON_CAN_RECREATE | HTON_ALTER_CANNOT_CREATE,
  NULL,    /* binlog_func */
  NULL,    /* binlog_log_query */
```

- **四组槽位对应四种能力**：①`commit/rollback/prepare` = 本地事务与 XA 准备；②`commit_by_xid/rollback_by_xid/recover` = **崩溃后按 XID 收尾**（XA/恢复路径，`recover` 让 Server 在启动时问引擎「你手里有哪些悬挂事务」）；③`savepoint*` = 保存点；④`binlog_func/binlog_log_query` = 引擎与二进制日志的协作钩子。
- **`recover`/`*_by_xid` 这一组最值得记住**：它是「引擎崩溃恢复」在接口上的可见部分。InnoDB 靠 redo 自己恢复，但仍需向 Server 报告悬挂的 XA 事务；非事务引擎全部留空。对照 [../mysql/19-redo日志.md](../mysql/19-redo日志.md)、[../mysql/20-undo日志.md](../mysql/20-undo日志.md) 看现代实现，接口层与算法层的分工一目了然。
- **`flags` 是能力合同**：`HTON_CAN_RECREATE`（`CREATE TABLE IF NOT EXISTS` 可以走「删了重建」捷径）、`HTON_ALTER_CANNOT_CREATE`（5.1 示例用；✅ 8.4 `ha_tina.cc` 里已无此标志，改为 `HTON_SUPPORT_LOG_TABLES | HTON_NO_PARTITION`）、以及后来决定事务可见性的 `HTON_SUPPORTS_ATOMIC_DDL` 一族（8.0）。

## 11.4 使用查询高速缓存（本书时代，今天整节作废）

- **当年机制**：查询缓存按「SQL 文本 → 结果集」缓存，任何会改变某张表内容的语句都要让相关缓存项失效。引擎侧的义务是**如实上报**「我改了哪些表」，以及维护能让 Server 判断「这张表有没有被写过」的版本信息；书中把这件事放在事务章，是因为失效时机与语句提交点强相关。
- **为什么当年值得做**：读多写少的 Web 负载命中率高，且对引擎透明（第 1 章「Server 层做通用优化」路线的代表作）。
- **今天的状态（勘误纪律）**：查询缓存在 5.7.20 起弃用、**8.0 起整体移除**。本轮实测两条硬证据：①8.4 文档域 `https://dev.mysql.com/doc/refman/8.4/en/query-cache.html` 返回 **404**（专页消失）；②源码树 `sql/query_cache.h` 在 8.4 blob 返回 **404**（实现文件消失）。**本节内容请当计算机考古读**，替代路线是应用层缓存 + 连接池 + 复制读扩展。

## 11.5 使用复制二进制日志：早期两阶段

- **朴素事实**：InnoDB 的行改动在引擎日志里，而复制/恢复用的是 Server 层的 binlog——**两份日志必须达成一致**，否则从库可能重放「主库其实没提交」的变更。
- **书中时代的解法（内部 XA 的雏形）**：写事务时先在引擎里 `prepare`（ redo 落盘、事务标记为 prepared），再把该事务的 binlog 缓存刷入文件并 fsync，最后 `commit`；崩溃恢复时 Server 用 `recover()` 收集引擎里的 prepared 事务清单，与 binlog 里的事务边界比对：binlog 里有完整提交事件的就补提交、没有的就回滚。这正是今天「binlog 与 redo 的两阶段提交 + 组提交」的早期形态。
- **代价与收益**：多一次引擎层 fsync 的代价换来「主从一致」这个复制系统的命根子。现代演进（组提交、`binlog_group_commit_sync`、半同步、并行复制）在 repo 内的现代口径见 [../mysql/X2-日志系统专题.md](../mysql/X2-日志系统专题.md) 与 [12-复制.md](12-复制.md)。
- **接口钩子的位置**：binlog 相关能力在 handlerton 上（见 11.3 的 `binlog_*` 槽），而不是 handler——**「是否与复制日志协作」是引擎级决定**。

## 11.6 避免死锁：两层不同的答案

| 层 | 策略 | 本章语境 |
| --- | --- | --- |
| Server 层表锁 | **预防**：一条语句的所有锁通过 `thr_multi_lock()` 一次拿全 | 见 [08-并发访问与锁定.md](08-并发访问与锁定.md) 8.5 |
| InnoDB 行锁 | **检测**：维护等待图，发现环后回滚牺牲者 | 书中只带过，深水区属 [../MySQL技术内幕_InnoDB存储引擎2.md](../MySQL技术内幕_InnoDB存储引擎2.md) 与 [../mysql/22-锁.md](../mysql/22-锁.md) |
| 用户可做的 | 固定加锁顺序、短事务、一致索引访问顺序、必要时提高隔离级别换更少的间隙锁 | 转述 ⚠️（本机无实例可实测） |

- 书中「避免死锁」小节的价值在于把「为什么 MySQL 表锁不报死锁却会长时间等待」讲透：**没有等待图，所以没有死锁可报**；今天的 `innodb_deadlock_detect`、`innodb_lock_wait_timeout` 属于另一层。

## 11.8 常见误区与修正

| 误区 | 修正 |
| --- | --- |
| 「MySQL 的事务是 Server 层实现的」 | Server 层只做编排与日志协调；ACID 四性全在引擎（本书正是为澄清此事而写） |
| 「没有 binlog 就没有复制」 | 反过来更准：binlog 与引擎日志的一致性才是复制正确性的前提（11.5） |
| 「表锁会报死锁」 | 表锁只排队、不检测；看到 `Deadlock found` 应立刻定位到 InnoDB |
| 「XA 只是给外部事务管理器用的」 | 8.0 的内部 XA（binlog↔redo）是每台单机实例都在用的机制，哪怕用户从不写 `XA START` |

## 11.9 三问三答（本章高频疑问卡）

- **Q1：为什么事务槽在 handlerton 而不是 handler？**
  A：事务是**引擎级**承诺（一个引擎一个事务管理器），而 handler 是**表级**句柄；Server 层提交时要遍历「本事务涉及的引擎」，所以函数指针必须挂在引擎单例上。
- **Q2：`commit_by_xid`/`recover` 什么时候真的被用到？**
  A：崩溃恢复期与 XA 场景——Server 启动时问每个事务型引擎「你有哪些已 prepare 未 commit 的事务」，再拿 binlog 决定补提交或回滚。示例引擎把这两槽留 NULL，即「我没有悬挂状态」。
- **Q3：这一章哪部分今天还值得花时间？**
  A：11.2（能力在引擎）、11.3（槽位含义）、11.5（两阶段的动机）三块仍是理解 8.x 事务的地基；查询缓存一节直接跳过。

## 核心概念速览（中英对照）

1. **事务编排** — transaction coordination：Server 层收集涉及引擎并按序提交/回滚的职责。
2. **事务上下文** — Transaction_ctx：THD 上「本事务涉及哪些引擎」的登记表。
3. **提交槽** — commit / rollback：handlerton 上的引擎级提交与回滚回调。
4. **准备槽** — prepare（XA）：两阶段提交的第一阶段入口。
5. **按 XID 收尾** — commit_by_xid / rollback_by_xid：崩溃后据 XID 补提交或回滚。
6. **恢复询问** — recover：启动时让引擎上报悬挂事务清单。
7. **保存点** — savepoint：事务内的可回滚锚点，纯引擎能力。
8. **每表句柄复用** — handler lifetime：事务期间 handler 实例不可随意关闭。
9. **外部锁登记** — external_lock：表锁到手后引擎判断是否开启事务上下文。
10. **能力标志** — HTON_* flags：`HTON_CAN_RECREATE`、（8.0）`HTON_SUPPORTS_ATOMIC_DDL` 等合同条款。
11. **早期两阶段** — prepare → binlog flush → commit：binlog 与引擎日志的一致性协议雏形。
12. **组提交** — group commit：多事务共享一次 binlog fsync 的现代优化。
13. **死锁预防 vs 检测** — prevention / detection：表锁一次拿全 vs InnoDB 等待图。
14. **查询缓存** — query cache：需引擎配合失效的内核模块（8.0 已删）。
