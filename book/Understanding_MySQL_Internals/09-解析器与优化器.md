# 第 9 章 解析器与优化器（The Parser and Optimizer ⚠️ 英文章题反构）

> 原书章：第 9 章（中文正版目录实抓：「解析器和优化器」）。二级小节实抓：解析器 / 优化器。
> 语境基线：4.1/5.0 的 `LEX` + `JOIN` 世界——**Selinger 式代价骨架 + 5.0 新加的子查询处理**，还没有派生表合并、没有 hash join、没有直方图。
> 本章取证升级：官方示例 `ha_csv-4.1.cc` 末尾附了一段**作者自己写的计划转储代码**（`dump_explain()`/`dump_join()`/`dump_join_tab()`，✅ 逐字读过），它把「解析产物与优化产物长什么样」用真实字段名摊开了；本文件按它反推本章的对象链路，另以 8.4 主干文件存在性作现代对照。

## 9.1 本章地图

| 节 | 内容 | 2007 年口径的结论 |
| --- | --- | --- |
| 解析器 | bison 语法（`sql/sql_yacc.yy`）→ `LEX` 结构 + `Item` 表达式树；语句类型分派 | 解析只「记录意图」，不做决策 |
| 优化器 | 表序枚举 + 每表访问方法选择 + 代价估算（`records`、键分布） | 保守代价模型：宁可多读几行，不敢赌统计量 |
| 子查询（5.0 新特性） | 多条执行路线（物化 / EXISTS 化 / 标量 / 派生表 …）⚠️ 具体枚举命名未实抓 | 子查询第一次成为「优化器要选型的东西」 |
| 连接算法 | nested loop 为主，`join_buffer` 撑起 block nested loop（BNL） | 缓冲换随机 I/O，是当时唯一的大规模改机 |

## 9.2 三段式：文本 → LEX/Item → JOIN（用官方示例代码锚定）

官方示例 4.1 版结尾的转储函数（✅ 逐字，作者原意为「在 gdb 里看一眼当前语句的计划」）：

```c
#include "sql_select.h"

void dump_join_tab(JOIN_TAB* jt)
{
  fprintf(stderr,"table=%s\n", jt->table->real_name);
  fprintf(stderr,"access method = %s\n", join_type_str[jt->type]);
}

void dump_explain()
{
  THD* thd = current_thd;
  LEX* lex = thd->lex;
  Item *where = lex->select_lex.where;
  JOIN* join  = lex->select_lex.join;
  ...
}
```

这十几行是本章最好的教具，因为它把四层对象的归属一次说清：

1. **`current_thd`**：一切都挂在连接上下文上（呼应 [03-核心类结构与变量.md](03-核心类结构与变量.md)）。
2. **`thd->lex`（`LEX`）**：解析产物总入口，`select_lex` 是当前查询块（5.0 用 `SELECT_LEX`/`SELECT_LEX_UNIT` 链表表达 UNION 与嵌套）。
3. **`select_lex->where`（`Item`）**：条件表达式树——**解析器造树，不化简**。
4. **`select_lex->join`（`JOIN`）**：优化产物；`join->join_tab[i]` 是第 i 张表的计划项，`JOIN_TAB::type` 是访问方法枚举，`join_type_str[]` 是它的字符串名（就是 `EXPLAIN` 里 `type` 列的值域）。
- 换句话说：**`EXPLAIN` 输出的每一列，在 5.0 的代码里都有一个字段与之对应**。书中「优化器」小节的实质就是把这张映射表讲一遍。

## 9.3 解析器精讲（历史语境）

- **语法文件至今同名**：`sql/sql_yacc.yy` 在 8.4 树里仍是 SQL 语法主文件（✅ 实测 200：https://github.com/mysql/mysql-server/blob/8.4/sql/sql_yacc.yy ）——本书教「改语法要先动 yacc 文件」这件事没有过期，过期的是语法内容（窗口函数、CTE、JSON 表函数、`CHANGE REPLICATION SOURCE TO` 等新语法都是后来加进去的）。
- **解析阶段做的三件事**：建 `LEX`/`SELECT_LEX` 骨架、把表达式翻译成 `Item` 树、把表名/列名以 `TABLE_LIST`/`Item_field` 形式登记。**权限检查与表打开在解析之后**（`mysql_parse` → `execute_sqlcom_select` → `open_tables_for_query`），所以「一条语句能跑」的顺序是：语法过关 → 对象存在 + MDL/权限过关 → 优化 → 执行（2007 年没有 MDL，见 [08-并发访问与锁定.md](08-并发访问与锁定.md)）。
- **词法与字符集**：解析器必须懂 `collation`，标识符合法性按字符集判定；`/*!50100 ... */` 这类版本注释是当年「一份脚本跨版本」的手段（今天仍在用）。
- **多语句与命令分派**：一个包里的多条语句按顺序解析执行；命令字进入 `dispatch_command` 的分支见 [04-客户端与服务器通信.md](04-客户端与服务器通信.md) 与 [06-基于线程的请求处理.md](06-基于线程的请求处理.md)。

## 9.4 优化器精讲：5.0 的决策面

| 决策 | 书中时代的做法 | 依赖的信息 |
| --- | --- | --- |
| 表序 | 从可能的连接顺序里搜索，配合索引可用性剪枝（枚举规模受限，不是全排列 DP） | 各表可用键、`records` |
| 每表访问方法 | `const`/`system`、`eq_ref`、`ref`、`range`、`index`、`ALL` 一类阶梯（`join_type_str[]` 即其字符串表） | 键存在性、等值条件、键选择性粗估 |
| 是否用索引 | 主要看「有没有可用的等值/范围条件 + 键前缀」 | 无直方图，粗粒度 |
| 临时表/文件排序 | 分组排序需求触发，代价按经验而非实测 | `sortlength`、行宽估计 |
| 子查询 | 见 9.5 | 5.0 新增 |

- **代价模型的保守性是本书最值得记住的一点**。示例引擎里那段注释（✅ 逐字大意：「优化器绝不能以为表少于两行，否则它以为只需读一行；我们不知道行数，所以永远至少报 2」）就是这条保守性的现场证据：Server 层**要求**引擎在 `info()` 里给「不至于让优化器走偏」的下限（见 [07-存储引擎接口.md](07-存储引擎接口.md)）。当年没有列统计、没有直方图，代价计算只能用 `records` 和键的粗估，于是「优化器不敢赌」成为设计底色。
- 理论坐标：Selinger & Chamberlin 等的访问路径选择框架（System R 谱系）是这一代优化器的公共祖先——*Access path selection in a relational database management system*, SIGMOD 1979，DOI ✅ 200 校验：https://api.crossref.org/works/10.1145/582095.582099 。本书讲的正是这条路线在 MySQL 里的「缩水实现」。

## 9.5 5.0 子查询：五类处理路线（⚠️ 命名口径待核验）

中文版目录里本节属「优化器」之下，书中把 5.0 的子查询实现列为多策略并存。**本目录能给的是机制清单，但「官方五条策略的确切命名」未能实抓（O'Reilly 正文不可达），整节按 ⚠️ 推定登记**：

1. **半连接 / IN→EXISTS 改写**：把 `WHERE a IN (subquery)` 视作相关存在性判断，避免物化。
2. **物化（materialization）**：把子查询结果落成临时表再探测；书中强调「唯一化 + 位图」这一形态（5.0 的实现特征 ⚠️）。
3. **EXISTS 策略**：相关子查询按外层每行执行一次（今天仍是兜底路线，性能最差）。
4. **标量子查询**：结果单值，可在常量上下文中求值。
5. **派生表 / FROM 位置查询**：物化为临时表并与外层连接。
- 判读方式（今天可复现）：`EXPLAIN` 里 `SUBQUERY`/`MATERIALIZED`/`DEPENDENT SUBQUERY` 一类 `select_type` 就是这几条路线留下的可见痕迹；现代改写策略见官方「Subquery Optimization」页（✅ 实测 200：https://dev.mysql.com/doc/refman/8.4/en/subquery-optimization.html ）。

## 9.6 BNL：本书时代的「连接加速器」

- **动机**：nested loop 内表按 join 键逐行随机访问，最坏是「外表行数 × 内表随机 I/O」。5.0 引入 `join_buffer`：把外表若干行攒进缓冲，内表扫描一遍时批量匹配——**用顺序扫描换随机访问**。
- **适用面**：只在「内表没有可用索引」时生效；这也是书中提醒「加对索引比指望 BNL 更有效」的原因。
- **今天**：8.4 文档有「Hash Join Optimization」专页（✅ https://dev.mysql.com/doc/refman/8.4/en/hash-joins.html ），且**已无 block-nested-loop 专页**（✅ 同域 `block-nested-join.html` 实测 404）——BNL 被 hash join 取代这一节替换关系，从官方文档结构上能直接看出；`hash_join_iterator.h` 在 8.4 源码树实测存在（✅ https://github.com/mysql/mysql-server/blob/8.4/sql/iterators/hash_join_iterator.h ）。连接算法的现代口径另见 https://dev.mysql.com/doc/refman/8.4/en/nested-join-optimization.html 。

## 9.8 常见误区与修正

| 误区 | 修正 |
| --- | --- |
| 「书中优化器=教科书 Selinger 实现」 | 只借了代价化的思想；表序是受限搜索而非完整 DP，统计量粗到只有 `records` 级别 |
| 「解析器负责优化」 | 解析只造树；一切选型发生在优化阶段，二者之间还有对象打开与权限检查 |
| 「BNL 是 MySQL 独有的发明」 | 它是 block nested loop 这一通用算法的实现，MySQL 的卖点是把它接进 `join_buffer`；今天同位置换成 hash join |
| 「`type` 列的取值是文档里的字符串」 | 顺序相反：代码里是 `JOIN_TAB::type` 枚举 + `join_type_str[]` 名字表，`EXPLAIN` 只是打印它 |

## 9.9 三问三答（本章高频疑问卡）

- **Q1：为什么 5.0 要专门给子查询写一节？**
  A：因为 MySQL 4.1 才支持子查询、5.0 才给它多种执行路线——这是本书写作时**最新、最不稳定**的一块内核。也解释了为什么今天读这一节最容易「背错年代」。
- **Q2：书里为什么不讲代价模型细节？**

## 核心概念速览（中英对照）

1. **解析器** — parser：把 SQL 文本变成 `LEX`/`Item` 结构的语法层。
2. **LEX** — parse descriptor：解析产物总入口，挂在 THD 上。
3. **查询块** — SELECT_LEX / unit：单个 SELECT 及其嵌套/UNION 组织。
4. **Item 树** — expression tree：条件与列的表达式表示，不做求值决策。
5. **TABLE_LIST** — range table：语句涉及的表及其别名登记。
6. **JOIN** — join descriptor：优化产物，含表序、访问方法、临时表决策。
7. **JOIN_TAB** — per-table plan node：第 i 张表的计划项，`type` 即访问方法。
8. **访问方法阶梯** — join type：`system/const/eq_ref/ref/range/index/ALL` 一档档。
9. **代价估算** — cost estimation：以 `records` 与键粗估为主的选型。
10. **半连接** — semijoin：`IN` 子查询的等价改写路线。
11. **物化** — materialization：把子查询结果落成临时表。
12. **派生表** — derived table：FROM 位置子查询，物化或合并。
13. **块嵌套循环** — block nested loop (BNL)：join buffer 攒外表行、顺序扫内表（今已被 hash join 取代）。
14. **文件排序** — filesort：需要额外排序时的临时结构（8.0 起称「sort file / 迭代器排序」）。
15. **保守优化器** — conservative optimizer：统计薄所以不赌代价的时代特征。
