# 第 8 章 并发访问与锁定（Concurrent Access and Locking ⚠️ 英文章题反构）

> 原书章：第 8 章（中文正版目录实抓：「并发访问与锁定」）。二级小节实抓：**表锁管理器**（全章就这一节，但它是 5.0 Server 层并发控制的全部家当）。
> 语境基线：4.1/5.0——**Server 层只有表级锁，且尚无 MDL（元数据锁，5.5 才引入）**。
> 本章取证升级：`include/thr_lock.h` 与 `mysys/thr_lock.cc` 的 8.4 版本实测可达（✅ https://raw.githubusercontent.com/mysql/mysql-server/8.4/include/thr_lock.h 、https://raw.githubusercontent.com/mysql/mysql-server/8.4/mysys/thr_lock.cc ），书里讲的这台「表锁机器」今天还在库里跑；结构体字段与优先级表按下文照其原文登记。

## 8.1 本章地图

| 节 | 内容 | 2007 年口径的结论 |
| --- | --- | --- |
| 表锁管理器 | `THR_LOCK`（每表一实例）+ `THR_LOCK_DATA`（每线程每表一实例）+ 四条队列的授予算法 | 表锁是 Server 层唯一的跨引擎并发手段 |
| 锁类型阶梯 | `TL_READ*`/`TL_WRITE*` 十余种类型按优先级排列，同优先级 FIFO | 写优先是默认策略，靠 `max_write_lock_count` 防读饥饿 |
| 与 handler 的咬合 | `store_lock()` 收集需求 → `thr_multi_lock()` 一次性加锁 → `external_lock()` 通知引擎 | 「一次拿全所有锁」是死锁 avoidance 的设计前提 |
| 引擎内部锁 | MyISAM 的行数/自增值靠锁状态回调同步；InnoDB 自己管行锁 | Server 层不管引擎内部并发 |

## 8.2 2007 年的三层锁观（先把层次钉死）

1. **Server 层表锁**（本章主角，`mysys/thr_lock.*`）：解决「同一张表上多个线程读写怎么排队」，对 MyISAM/MEMORY/CSV/ARCHIVE 这类引擎就是**唯一**的并发控制。
2. **引擎内部锁**：InnoDB 的行锁/间隙锁/闩锁在它自己的模块里，Server 层看不见；MyISAM 只在文件层面做点补充。
3. **全局 mutex 群**：保护统计量、缓存、配置等共享状态（见 [06-基于线程的请求处理.md](06-基于线程的请求处理.md) 的「分组加锁」）。

- **当年最大的空洞是第「0」层**：没有任何机制防止「一条 SELECT 正在读表结构时，另一条 ALTER 把表换掉」。书中讲表锁管理器时那种「够用就好」的语气，正是 5.0 时代的真实状态；这个洞由 5.5 的 MDL 补上（✅ https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html ）。读本章必须把「表锁」与「元数据锁」严格分开，否则会把两代机制混成一锅。

## 8.3 THR_LOCK：一台机器的零件表（实测字段）

- **`THR_LOCK`（每表一个）**：一个 `mysql_mutex_t` + 四条链表——`read_wait`、`read`、`write_wait`、`write`；再加两个计数：`write_lock_count`（写锁授予次数，读到锁时清零）与 `read_no_write_count`；最后是一组状态回调 `get_status/copy_status/update_status/restore_status/check_status`。
  - 那组回调不是装饰：MyISAM 用它把「表行数」「下一个自增值」这类**必须与锁同生共死**的量在加锁时取、在放锁前写回（`update_status`/`restore_status` 注释即「Before release of write/read」）。理解了这点，就理解了为什么 MyISAM 的 `COUNT(*)` 免扫描优化能保持正确。
- **`THR_LOCK_DATA`（每线程每表一个）**：`owner`（`THR_LOCK_INFO`，内含 `thread_id` 与挂起用的 `mysql_cond_t *suspend`）、`type`（本次要什么锁）、`next/prev`（串在四条队列之一上）、`status_param`，以及 8.4 里新增的 `struct PSI_table *m_psi`——**performance_schema 的表 I/O 计时就挂在这颗钉子上**（现代残影，书时代没有）。
- **返回值族**：`THR_LOCK_SUCCESS / THR_LOCK_ABORTED / THR_LOCK_WAIT_TIMEOUT / THR_LOCK_DEADLOCK`。注意最后两个：表锁管理器**能报超时**（`lock_wait_timeout` 的前身思路），而「DEADLOCK」在这里主要是**被上层（InnoDB）借用**的返回码语义，Server 层表锁自己并不做等待图检测。

## 8.4 锁类型与优先级阶梯（照 8.4 源码文件头注释登记，✅）

`mysys/thr_lock.cc` 开头的官方注释给出的类型表（书中 5.0 口径与此基本一致）：

| 类型 | 语义（源码注释原意） |
| --- | --- |
| `TL_READ` | 低优先级读 |
| `TL_READ_WITH_SHARED_LOCKS` | 带共享锁的读 |
| `TL_READ_HIGH_PRIORITY` | 高优先级读 |
| `TL_READ_NO_INSERT` | 读时不允许并发插入 |
| `TL_WRITE_ALLOW_WRITE` | 允许其它写者并存的写 |
| `TL_WRITE_CONCURRENT_INSERT` | 可与 SELECT 混用的插入；允许低优先级锁抢过 |
| `TL_WRITE_LOW_PRIORITY` | 低优先级写 |
| `TL_WRITE` | 高优先级写 |
| `TL_WRITE_ONLY` | 高优先级写，且**让所有新锁请求直接报错** |

- **优先级排列**（同一注释）：`WRITE_ALLOW_WRITE, WRITE_CONCURRENT_INSERT, WRITE_LOW_PRIORITY, READ, WRITE, READ_HIGH_PRIORITY, WRITE_ONLY`；**同优先级 FIFO**。
- 书里反复强调的两条推论：①默认写优先，长写队列会把读饿死 → 用 `max_write_lock_count`（8.4 源码仍是这个全局量 ✅）在写够 N 次后把读提为高优先级；②`TL_WRITE_ONLY` 是 `FLUSH TABLES WITH READ LOCK` 这类全局动作的实现手段，也是当年备份流程「卡住一切」的技术原因（备份体系本身不在本书，见 [../高性能mysql.md](../高性能mysql.md)）。
- **一个跨章细节**：8.4 头文件对 `TL_READ_DEFAULT` 的注释写着「只在解析阶段使用；`open_tables()` 会按**二进制日志格式**把它变成 `TL_READ` 或 `TL_READ_NO_INSERT`」。也就是说，binlog 是 statement 还是 row，直接决定表锁的类型——这是第 12 章复制与本章锁体系的接线处，书中未展开，本目录在此登记。

## 8.5 请求—授予—等待的机械过程（历史语境 + 结构自证）

1. 语句规划阶段，Server 层为每个用到的表调用 `handler::store_lock()`，把该引擎要求的 `THR_LOCK_DATA` 收进一条数组（示例引擎：只有当 `lock.type == TL_UNLOCK` 时才把请求类型写进去，否则保留已升级的高类型）。
2. 数组交给 `thr_multi_lock(data, count, thd_info, timeout)` **一次全部请求**——官方注释写得很直白：*"Every thread must acquire all locks it needs through thr_multi_lock() to avoid dead-locks"*。**一次拿全**才是 2007 年 MySQL 的死锁预防策略，不是检测策略。
3. 拿不到就进对应 `*_wait` 队列，在自己的 `mysql_cond_t` 上挂起；授予方在释放时按优先级扫描等待队列，唤醒可授予者（`data->cond` 置空表示已被授予）。
4. 每把锁授成后调 `get_status`；写锁释放前调 `update_status`，读锁释放前可能调 `check_status`/`restore_status`（MyISAM 用它维护行数与自增）。
5. 全部锁到手后才对每个 handler 调 `external_lock(thd, lock_type)`：这是**引擎侧事务/文件锁的起点**（示例引擎直接 `return 0`，InnoDB 在此登记事务上下文，见 [11-事务.md](11-事务.md)）。

## 8.6 与旧译笔记的对位（中文读者常问的三点）

- 旧笔记把这一章的疑问集中在「MyISAM 有统一的接口？」——答案是：**统一的不是锁，是钩子**。Server 层只规定「你要在 `store_lock` 里交出锁需求、在 `external_lock` 里做你自己的工作」，至于内部怎么并发（表锁 / 行锁 / 无锁）完全由引擎自决。
- 「表锁管理器」四个字在中文版里容易被读成「管所有锁的管理器」，实际只管**表级**；行级并发在 5.0 时代是 InnoDB 的私事。
- 旧笔记残记的模块清单（服务器初始化 / 连接管理器 / 线程管理器 / 解析器 / 优化器 / 表管理器 / 抽象存储引擎接口 / 日志记录模块 …，✅ 见 [../深入理解MySQL核心技术.md](../深入理解MySQL核心技术.md)）里的「表管理器」正对应本章与第 7 章的交界面。

## 8.7 「历史语境」清单

| 书中描述（4.1/5.0） | 今天（8.4/9.x） | 证据 |
| --- | --- | --- |
| Server 层表锁是并发控制主战场 | InnoDB 行锁/间隙锁 + MVCC 才是主战场；表锁只服务 MyISAM/MEMORY/CSV 与 `LOCK TABLES` | ✅ https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html |
| 没有元数据锁，DDL 与 DML 靠表锁粗糙互斥 | MDL（5.5 起）保护表定义，`performance_schema.metadata_locks` 可观测 | ✅ https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html 、https://dev.mysql.com/doc/refman/8.4/en/performance-schema-metadata-locks-table.html |
| `TL_WRITE_DELAYED`（INSERT DELAYED 用）存在于类型表 | 8.4 的 `enum thr_lock_type` 已无该值（✅ 实测枚举清单无 `TL_WRITE_DELAYED`）；INSERT DELAYED 已退出 | 版本点 ⚠️ 转述（官方 release notes 域未逐一抓取） |
| 写饥饿靠 `max_write_lock_count` 经验调参 | 机制仍在（全局量未消失 ✅），但 OLTP 负载下讨论重心换成 InnoDB 锁等待/超时与死锁日志 | ✅ https://dev.mysql.com/doc/refman/8.4/en/internal-locking.html |
| 并发插入是 MyISAM 的特色能力 | 概念仍在文档里，且成为 InnoDB 改变行格式（8.0.17+「no gap for recs at end」）时的历史参照 | ✅ https://dev.mysql.com/doc/refman/8.4/en/concurrent-inserts.html |

## 8.8 常见误区与修正

| 误区 | 修正 |
| --- | --- |
| 「MySQL 从来不做死锁检测」 | Server 层表锁走「一次拿全」的**预防**路线；InnoDB 在引擎内做等待图**检测**并回滚牺牲者——两层不能混 |
| 「表锁管理器是历史化石、8.0 已删」 | 没删：`mysys/thr_lock.cc` 与 `include/thr_lock.h` 在 8.4 树中实测存在，CSV/MyISAM 仍靠它 |
| 「读多写少就不用管锁」 | 默认写优先 + 长写队列在 2007 与今天都是 MyISAM 卡死的经典成因 |
| 「`external_lock` 里的 lock_type 是行锁参数」 | 它是表级意图的枚举，被用来决定引擎是否开启/结束事务上下文 |

## 8.9 三问三答（本章高频疑问卡）

- **Q1：书中这章为什么只有「表锁管理器」一节？**
  A：因为 5.0 的 Server 层并发控制就这么多：MDL 没出生、GTID 没出生、InnoDB 还是外挂。这一节的价值不是内容量，而是**它是所有 MySQL 锁叙事的起点**。
- **Q2：`thr_multi_lock` 的「一次拿全」在 8.x 还成立吗？**
  A：成立——Server 层的语句加锁路径仍是先 `store_lock` 收集再一次性授锁，只是其上加了 MDL 层做结构保护；两层顺序是「先 MDL 后表锁」，反序会造成锁序倒置（转述 ⚠️ 未逐行核验 8.4 的 `open_tables` 路径）。
- **Q3：今天排查「谁锁住了我的表」应该用什么？**
  A：先分层定位：结构层看 `performance_schema.metadata_locks`；引擎层看 InnoDB 锁与事务视图；只有当表是 MyISAM/MEMORY/CSV 时才回到本章这台机器的语义（`processlist` 的 "Waiting for table level lock" 一类状态，转述 ⚠️）。

## 核心概念速览（中英对照）

1. **表锁管理器** — table lock manager：`mysys/thr_lock` 提供的表级读写锁排队机器。
2. **主锁** — THR_LOCK：每表一个的锁对象，持有四条队列与一把 mutex。
3. **锁实例** — THR_LOCK_DATA：每线程每表一个的锁请求登记项。
4. **等待队列** — read_wait / write_wait：拿不到锁时挂起等待的链表。
5. **持有队列** — read / write：已授予锁的有序链表。
6. **一次拿全** — multi lock acquisition：`thr_multi_lock` 的死锁预防策略。
7. **优先级阶梯** — lock priority order：从 `TL_WRITE_ALLOW_WRITE` 到 `TL_WRITE_ONLY` 的排序。
8. **并发插入** — concurrent insert：`TL_WRITE_CONCURRENT_INSERT` 允许读插混行的能力。
9. **写饥饿防护** — max_write_lock_count：写够若干次后提升读优先级的全局量。
10. **状态回调** — get/copy/update/restore/check status：把 MyISAM 行数与自增值绑进锁生命周期。
11. **表级锁等待** — table-level lock wait：`Waiting for table level lock` 一类状态的历史来源。
12. **元数据锁** — MDL：5.5 起保护表结构的层（本书时代缺位）。
13. **无等待图** — no deadlock detection：Server 层表锁只预防、不检测。

- **理论回看**：本章描述的「表级读写锁 + 优先级 + 一次拿全」在严格性上只保证互斥正确，不涉及冲突可串行化证明；需要形式化定义时参考上面给出的 Papadimitriou（DOI 已 200 校验）。
