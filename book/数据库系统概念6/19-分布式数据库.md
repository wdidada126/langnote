# 第 19 章 分布式数据库

> **本章地图**：分布式数据存储（**复制**与**分片**）→ **分布式事务**（本地/全局事务、系统故障与介质故障、两阶段提交 2PC 及其故障处理、三阶段提交）→ **分布式并发控制**（单一锁管理器 / 多协调者 / 主副本 / 多数协议 / 分布式死锁）→ **可用性**（主备、多副本、Quorum、读修复、CAP）→ **分布式查询处理**（半连接、代价模型、数据本地性）→ **异构与联邦数据库、中间件** → 目录系统（LDAP）。

## 二、核心精讲

### 19.1 数据分布：复制与分片
- **复制（replication）**：提高可用性与读吞吐；**分片（fragmentation / sharding）**：水平分片（按行，常用哈希或范围）与垂直分片（按列）。
- 复制的三种更新传播：**同步（强一致，延迟高）、异步（最终一致，有丢失窗口）、半同步**。
- **主副本（primary copy）**：每数据项指定一个主副本负责加锁 → 大幅简化分布式并发控制。
- 🔧 现代术语对照：分片 = **shard / tablet / region**（TiDB Region、HBase Region、Bigtable tablet）；复制 = **Raft/Paxos group** 的成员集合。教科书讲的「replication + fragmentation」在今天被统一抽象为 **range partition + Raft group + 自动 rebalance**。

### 19.2 分布式事务与两阶段提交（2PC）
1. **阶段一（Prepare / Voting）**：协调者向所有参与者发 `PREPARE`；参与者写 undo/redo 日志并回复 `YES/NO`。
2. **阶段二（Commit / Abort）**：全 YES → 写 `commit` 日志后发 `COMMIT`；否则 `ABORT`。
- 🔧 **2PC 是阻塞协议**：协调者在阶段二崩溃且参与者已投 YES 时，参与者无法确定结果，只能**阻塞等待协调者恢复**（in-doubt 事务，会一直持有锁）。这是 2PC 最大的工程痛点。
- 解法：**3PC**（引入 pre-commit，减少阻塞窗口，但网络分区下仍可能不一致，工业界不用）、**Paxos Commit / Raft 复制协调者**（Gray & Lamport, TODS 2006）、TiDB 的 **Percolator 模型**（把提交状态存在数据本身，协调者无状态，可用任意节点接管）。
- 故障处理：**参与者写 prepare log 之前崩溃** → 协调者 abort；**之后崩溃** → 恢复后按协调者决定；**协调者崩溃** → 参与者按日志中的协调者决定或等待 / 咨询其他参与者（cooperative termination protocol）。

### 19.3 分布式并发控制
- 方案谱系：
  1. **单一锁管理器**（集中式，简单但有热点与单点）；
  2. **多协调者 / 多数协议（majority protocol）**：加锁需获**多数副本**同意（> n/2），避免单点；
  3. **主副本协议**：锁只向主副本申请；
  4. **分布式时间戳 / 全局快照**（HLC、TrueTime）。
- **分布式死锁**：局部等待图无法发现跨节点环 → 需要**全局等待图**（集中式检测）或**分布式死锁探测**（TiDB 的 deadlock detector 在 TiKV 上做全局环搜索）、或超时兜底。
- 🔧 **分布式可串行化 + 复制一致性**是两件事：前者由 2PL/MVCC 保证，后者由共识算法保证；**Spanner 用 TrueTime + 2PC + Paxos 同时做到外部一致性**（OSDI 2012）。

### 19.4 可用性与一致性
- **Quorum 协议**：N 副本，读需 R 个、写需 W 个，$R + W > N$ 保证读能见到最新写；再配合**版本号 / 向量时钟**解决并发写冲突。
- **读修复（read repair）**、**反熵（anti-entropy）**、**hintedd handoff**（Dynamo 三件套，SOSP 2007）。
- **CAP / PACELC**：见第 17 章。🔧 工程现实：绝大多数系统选择 **CP（Raft 强一致）+ 高可用的自动选主**，或 **AP（最终一致）+ 冲突解决（CRDT / LWW）**。

### 19.5 分布式查询处理
- 关键优化：**减少网络传输**。
  - **半连接（semijoin）**：先把 A 的 join key 投影发到 B 站点，过滤 B 后再传回 → 显著降低传输量（分布式 join 的核心技术，在 Impala/Presto 中即 **dynamic filter / runtime filter**）。
  - **数据本地性（locality）**：把计算调度到数据所在节点（MapReduce/HDFS 的经典原则）。
- 代价模型：$总代价 = CPU + I/O + 传输量 \times 网络代价$，网络项通常权重最高。
- 🔧 现代对应：**runtime filter**（Impala, CIDR 2013）、**bloom filter 下推**、**colocate join**（同分布键免 shuffle）。

### 19.6 异构分布式数据库 / 联邦数据库
- **联邦数据库（federated DDBS）**：各局部 DB 保持自治，通过 **wrapper / mediator**（TSIMMIS、Garlic）统一访问。
- **多数据库系统 / 中间件**：ODBC/JDBC、分库分表中间件（ShardingSphere、MyCat、Vitess）。
- 🔧 现代形态：**数据湖 + 联邦查询**（Trino / Presto 多 connector、Apache Calcite 的联邦优化、Data Virtualization）；**HTAP 与湖仓一体（Lakehouse，Delta Lake/Iceberg/Hudi）**。

### 19.7 目录系统（LDAP）
- **目录（directory）**：以读为主、层次化命名（DIT）、属性-值对的数据存储；协议 **LDAP**（轻量目录访问协议），源自 X.500（DAP）。
- 🔧 现实：LDAP/Active Directory 仍是企业身份基础设施；但教科书对目录系统的篇幅在今天已属历史背景，可略读，重点理解「**读多写少 + 层次命名空间 + 弱事务**」这一特殊场景。

## 四、近年研究与工业界开源实践

- **近年研究**：**确定性事务**（Calvin, SIGMOD 2012；Aria, VLDB 2020）消除分布式 2PC 的协调开销；**Geo-distributed 事务**（Spanner、CockroachDB、以及 *SLOG*, VLDB 2019 的确定性重排序）；**Serializable 的分布式实现**（CockroachDB 的 parallel commits、write intent）；**HLC vs TrueTime** 的时钟方案对比。
- **工业界开源**（star 数 2026-09 实测）：
  - `pingcap/tidb`（≈40.6k★）：Percolator + Raft（TiKV），Region 自动分裂/合并与 rebalance，是「教科书分片+复制」的完整工业实现。
  - `cockroachdb/cockroach`（≈32.5k★）：Range + Raft + HLC + **parallel commits**，分布式串行化的最佳实践。
  - `vitessio/vitess`（≈21.4k★）：MySQL 分片中间件，对应本章「多数据库中间件」。
  - `apache/shardingsphere`（≈20.8k★）：分库分表 + 分布式事务（XA / Seata 型），Java 生态代表。
  - `apache/calcite`（≈5.2k★）：联邦查询优化器框架，是理解「异构分布式查询」的最佳源码。
  - `trinodb/trino`、`apache/iceberg`（≈9.3k★）：数据湖联邦查询与湖仓格式。
  - `etcd-io/etcd`（≈48k★）：Raft 最小实现，读 `raft/` 包可直接对照共识算法。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "2PC 保证原子性且不会卡住" | 协调者崩溃导致**阻塞**；需复制协调者或无状态提交（Percolator） |
| 2 | "多数派协议只是容错技巧" | 它同时是**并发控制**（加锁需多数同意）与一致性基础 |
| 3 | "分布式死锁能被单节点检测" | 需全局等待图或分布式探测器 |
| 4 | "最终一致就是不管一致性" | 需要明确的**冲突解决**策略（LWW / CRDT / 应用层合并） |
| 5 | "分片后加机器一定线性扩展" | 热点分片、跨片事务与 rebalance 开销会破坏线性 |
| 6 | 🔧 本书缺口 | 未覆盖 **Percolator / Spanner / Calvin 之后（2010+）的 NewSQL 浪潮**、**Raft/KV 分离架构**、**湖仓一体与联邦查询**；LDAP 部分可视为历史材料 |
