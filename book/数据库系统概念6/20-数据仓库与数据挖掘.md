# 第 20 章 数据仓库与数据挖掘

> **本章地图**：为什么需要数据仓库（OLTP vs OLAP 分离）→ **多维数据模型**（事实表 / 维表 / 度量）→ **星型 / 雪花 / 事实星座** → **OLAP 操作**（roll-up / drill-down / slice / dice / pivot）→ **数据立方体（cube）** 与物化 → 数据仓库设计与实现（ETL、列存、位图索引、物化视图）→ **数据挖掘**（分类、回归、聚类、关联规则、异常检测）→ 现代湖仓与向量检索。

## 二、核心精讲

### 20.1 OLTP vs OLAP
| 维度 | OLTP | OLAP |
| --- | --- | --- |
| 访问模式 | 点查询、短事务、随机写 | 大范围扫描、聚合、批量导入 |
| 数据 | 当前、规范化（3NF） | 历史、反规范化（维度模型） |
| 优化目标 | 事务吞吐、行级锁 | 扫描吞吐、压缩、列裁剪 |
| 存储 | 行存 + B+ 树 | **列存** + 稀疏索引 / zone map |

- 🔧 **列存的三大优势**：① **只读需要的列**（I/O 减少一个数量级）；② **同列同质 → 压缩率高**（字典编码、RLE、Delta、Frame-of-Reference）；③ **向量化友好**（定长数组 → SIMD）。

### 20.2 多维数据模型与模式
- **事实表**（业务度量：销售额、数量）+ **维表**（时间、商品、地区、客户）。
- **星型模式**：一个事实表 + 多个扁平维表（最常用）。
- **雪花模式**：维表进一步规范化（省 I/O，join 更多）。
- **事实星座**（galaxy）：多个事实表共享维表。
- 🔧 现代反趋势：**宽表/大平表**（ClickHouse 的 `MergeTree` 单大宽表、Dremel 的嵌套列存）比星型 join 更快；**维度退化（degenerate dimension）** 与 **OLAP 的 join 消除**（用预聚合 + 字典编码替代）成为常态。

### 20.3 OLAP 操作与数据立方体
- **上卷 roll-up**（由细到粗，如 日→月）、**下钻 drill-down**（粗到细）、**切片 slice**（某维取单值）、**切块 dice**（多维取值）、**旋转 pivot / rotate**。
- **数据立方体（Data Cube）**：所有维度组合的聚合预计算（Gray et al., *Data Cube: A Relational Aggregation Operator Generalizing Group-By, Cross-Tab, and Sub-Totals*, ICDE 1996 —— 对应 SQL 的 `CUBE` / `ROLLUP` / `GROUPING SETS`，见第 5 章高级 SQL）。
- **物化视图选择**：立方体格（cube lattice）中选择性价比最高的视图集合（贪心算法）；维护策略：**增量维护** / **延迟维护** / **重建**。

### 20.4 数据仓库实现技术
- **ETL / ELT**：抽取-转换-加载；现代多为 **ELT**（先入湖，再用 SQL 转换，dbt 是代表）。
- **列式存储**：C-Store（VLDB 2005）→ Vertica；**Parquet / ORC** 成为湖上事实标准（嵌套列存源自 Dremel, VLDB 2010）。
- **位图索引（bitmap index）**：低基数列的利器，支持高效 AND/OR（第 11 章）；Druid / Pinot / ClickHouse 的 `roaring bitmap` 是其现代形态。
- **预聚合与 Rollup 表**：ClickHouse `AggregatingMergeTree`、Druid rollup、StarRocks 的物化视图自动改写。
- 🔧 **分层架构**：ODS → DWD → DWS → ADS（阿里/国内大厂通用数仓分层），与维度建模（Kimball）理论互为补充。

### 20.5 数据挖掘
- **分类**（决策树 CART/C4.5、朴素贝叶斯、SVM、神经网络）——监督学习。
- **回归**（线性/逻辑回归）。
- **聚类**（k-means、DBSCAN、层次聚类）——无监督。
- **关联规则**（Apriori, Agrawal & Srikant VLDB 1994；FP-Growth, 2000）——购物篮分析；评价指标 support / confidence / lift。
- **异常检测**、**文本挖掘**、**推荐**（协同过滤）。
- 🔧 现代视角：教科书把数据挖掘作为数据库的一个章节；**2015 年后这条线独立成机器学习/数据科学学科**，数据库侧留下的接口是 **in-database ML**（MADlib、BigQuery ML、SQLFlow、PostgresML）与 **特征平台（Feast）**。

## 四、近年研究与工业界开源实践

- **近年研究**：**湖仓一体（Lakehouse）**（Delta Lake / Iceberg / Hudi 在对象存储上提供 ACID 与 time travel）；**向量化 + 编译执行的 OLAP**（Velox、DuckDB）；**学习式查询优化与物化视图推荐**（云厂商的自动 MV 推荐）；**Data Mesh / 数据契约**（组织层面的范式转移）；**LLM 时代的向量检索与 RAG**（pgvector、Milvus）。
- **工业界开源**（star 数 2026-09 实测）：
  - `clickhouse/clickhouse`（≈50.1k★）：列存 OLAP 的现实标杆，可直接对照 C-Store 的 projection / 压缩 / 稀疏索引设计。
  - `duckdb/duckdb`（≈41.7k★）：嵌入式列存 + 向量化，支持直接查 Parquet/Iceberg，是「个人数仓」首选。
  - `apache/spark`（≈44.0k★）/`apache/hive`（≈6.0k★）：Hadoop 生态的批处理与 SQL 层。
  - `apache/iceberg`（≈9.3k★）/ `delta-io/delta` / `apache/hudi`：湖仓表格式三强（隐藏分区、schema 演进、time travel）。
  - `apache/doris` / `StarRocks` / `apache/druid`：MPP 分析型数据库的现代形态（向量化 + 物化视图自动改写 + 实时摄入）。
  - `apache/madlib`、`postgresml/postgresml`：in-database ML，对应本书数据挖掘章节的现代落地。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "数据仓库就是把 OLTP 库复制一份" | 需建模（维度模型）、分层、历史快照（缓慢变化维 SCD） |
| 2 | "雪花模式比星型更好（更省空间）" | 星型更易理解、join 更少，通常**性能更好** |
| 3 | "立方体要预计算所有组合" | 组合爆炸（2^n），必须**选择**物化（lattice + 贪心） |
| 4 | "数据挖掘 = SQL 聚合" | 分类/聚类/关联规则是独立算法体系，数据库只是宿主 |
| 5 | 🔧 本书以 2000 年代视角写 | 需补充 **列存（C-Store/Dremel/Parquet）、湖仓一体、云数仓（Snowflake/BigQuery）、实时数仓（Flink + Doris）、向量检索** |
