# 第 16 章 恢复系统

> **本章地图**：故障分类（事务故障 / 系统崩溃 / 介质故障）→ 存储层次（易失 / 非易失 / **稳定存储**）→ 基于日志的恢复（**undo log** 与 **redo log**）→ **先写日志 WAL 规则** → 检查点（静止检查点 → **模糊检查点**）→ **ARIES 算法**（LSN/pageLSN/recLSN/PrevLSN、CLR、脏页表 DPT、事务表、分析/重做/回滚三阶段）→ 缓冲区管理（**steal / no-steal × force / no-force** 四象限）→ 非易失内存与远程备份系统。

## 二、核心精讲

### 16.1 故障分类与恢复目标
| 故障 | 表现 | 恢复手段 |
| --- | --- | --- |
| **事务故障**（逻辑错误、死锁 victim） | 单个事务中止 | undo 回滚该事务 |
| **系统崩溃**（掉电、内核 panic） | 内存内容全丢，磁盘数据页可能处于中间态 | **WAL + ARIES**（redo 已提交、undo 未提交） |
| **介质故障**（磁盘损坏） | 磁盘数据丢失 | 备份 + 归档日志 + **PITR（时间点恢复）** |

- 🔧 现代工程关注点：教科书默认「稳定存储不会同时坏」，现实中**同城双活 / 三副本 / 跨地域备份**（RPO/RTO）才是可用性主线；介质故障的概率远高于教科书的想象。

### 16.2 存储层次与稳定存储
- 易失（内存 / CPU cache）→ 非易失（磁盘 / SSD）→ **稳定存储**（理论抽象：永不丢失；工程上用 **多副本 + 校验 + 备份** 逼近）。
- 🔧 SSD 时代的新问题：**掉电时的 partial write**（页只写一半），因此文件系统与数据库都要处理 **原子写 / full-page write**（PostgreSQL 的 `full_page_writes` 正是为应对「页面撕裂 torn page」）。

### 16.3 日志与 WAL 规则
- 日志记录类型：`<T, start>`、`<T, X, V1, V2>`（更新：旧值 V1 / 新值 V2）、`<T, commit>`、`<T, abort>`。
- **undo log 规则（先写日志，后写数据）**：输出修改到磁盘前，必须先把 `<T, X, V1, V2>` 落到稳定存储；提交时 `<commit>` 落盘后才能告知用户成功。
- **redo log 规则**：提交时先强制把 **所有日志记录（含新值）** 写到稳定存储，**再**写数据页（数据页可延迟落盘）。
- **WAL（Write-Ahead Logging）核心定理**：
  1. undo 信息必须在数据页落盘**之前**写日志（保证能回滚）；
  2. redo 信息必须在事务提交**之前**写日志（保证提交不丢）。
- 🔧 **undo log 与 redo log 的工程分工**：MySQL InnoDB 用 **redo log（物理逻辑，ib_logfile）+ undo log（逻辑，回滚段）**；PostgreSQL 只有一份 WAL（物理）+ 堆内旧版本；Oracle 是 redo + undo 表空间。不要以为「undo log 是文件、redo log 也是文件」就等价。

### 16.4 检查点
- **静止检查点（ quiescent checkpoint）**：暂停所有事务 → 把脏页全部刷盘 → 写 `<checkpoint>` 日志 → 恢复。代价：写停顿。
- **模糊检查点（fuzzy checkpoint）**：只记录「此刻活跃事务列表 + 脏页列表」，后台异步刷脏 —— 🔧 商用系统全部采用（InnoDB 的 `master thread` 异步刷脏 + sharp checkpoint 只在正常关闭时做）。
- 🔧 崩溃恢复起点：从**最后一个完成的检查点**开始扫描（InnoDB 还会用 checkpoint 的双 slot 防止检查点本身写坏）。

### 16.5 ARIES 算法（本章的皇冠）
> Mohan et al., *ARIES: A Transaction Recovery Method Supporting Fine-Granularity Locking and Partial Rollbacks Using Write-Ahead Logging*, ACM TODS 1992。

三个核心原则：
1. **Write-ahead logging**（先写日志）；
2. **Repeating history during redo**（重做时**重复历史**：不管事务是否已提交，把崩溃前做过的所有更新原样再做一遍，把数据库恢复到崩溃瞬间的状态）；
3. **Logging changes during undo**（回滚也要记日志：**CLR，Compensation Log Record**），保证回滚本身可重入、不重复执行。

关键数据结构：
- **LSN（Log Sequence Number）**：日志全局单调递增偏移；每个页面头记录 **pageLSN**（最后修改该页的日志 LSN）；缓冲池中记录每个脏页首次变脏的 **recLSN**。
- 每条日志含 **PrevLSN**（同一事务上一条日志），形成**单事务的反向链表** → undo 时按 PrevLSN 回溯。
- **脏页表（DPT）**：脏页 id → recLSN；**事务表（Xact Table）**：活跃事务 → 最后 LSN、状态。

三阶段恢复：
1. **分析（Analysis）**：从最近 checkpoint 正向扫描到日志末尾，重建 DPT 与事务表，确定 redo 起点（DPT 中最小的 recLSN）与 undo 集合（崩溃时活跃事务）。
2. **重做（Redo）**：从 redo 起点正向扫描，对每条 update 记录：若 `LSN > pageLSN`（该页尚未包含此修改）且该页在 DPT 中，则重放。**物理日志 + pageLSN 比较 → 天然幂等**，重复历史安全。
3. **回滚（Undo）**：对活跃事务按 **PrevLSN 反向** 回滚，每步写 CLR（CLR 永不重复执行，因为它记录的是「已完成补偿」）。

- 🔧 理解 ARIES 的两句话：**redo 是「向前把数据库恢复到崩溃点」**，**undo 是「向后撤销未提交事务」**；两者不交叉，因为 redo 阶段已经把状态补齐了。
- 🔧 工程印证：InnoDB 的恢复由 `recv_recovery_from_checkpoint_start()` 驱动（分析 + redo），undo 交由后台 `trx_rollback_or_clean_recovered`；WAL 的 LSN 语义与 ARIES 完全一致。

### 16.6 缓冲区管理四象限
|  | **no-force**（提交不必刷脏页） | **force**（提交必须刷脏页） |
| --- | --- | --- |
| **steal**（允许未提交事务的脏页落盘） | ✅ **steal + no-force：ARIES / 所有主流数据库** | steal + force（少） |
| **no-steal**（未提交页不许落盘） | no-steal + no-force（如某些内存库） | no-steal + force（最笨，恢复最简单） |

- 🔧 **steal + no-force 是最难的组合**（为什么需要 undo？因为 steal 可能让脏数据落盘；为什么需要 redo？因为 no-force 让已提交数据可能没落盘），但它换来最小 I/O 和最高并发 —— 这正是 ARIES 存在的意义。

### 16.7 远程备份与高可用
- 主站点 → 备份站点传输日志；备份站点持续 redo；主站失效后接管（需处理「主站已提交但日志未送达」的**数据丢失窗口**）。
- 三种模式：**同步（零丢失、高延迟）/ 异步（有丢失窗口）/ 半同步**（MySQL semi-sync 即折中）。
- 🔧 现代替代方案：**Raft/Paxos 复制状态机**（TiDB / CockroachDB / etcd 的日志复制本质就是「分布式 WAL」），比传统 log shipping 更强的自动选主与一致性保证。

## 四、近年研究与工业界开源实践

- **近年研究**：**非易失内存（NVM / PMem）上的日志精简**（如 *Write-Behind Logging*, VLDB 2016，Soules 等提出用 flush 顺序代替 redo）；**PMem 事务内存**；**确定性数据库的恢复**（Calvin 只需重放输入，无需 redo 日志）；**逻辑复制与 CDC 合并进 WAL**（Debezium 依托 PG/MySQL 的逻辑解码）。
- **工业界开源**（star 数 2026-09 实测）：
  - `postgresql/postgres`（≈17k★）：WAL + full-page write + 归档 → PITR；`pg_waldump` 可直接查看 WAL 内容，是学习 ARIES 的最佳开源样板。
  - `mysql/mysql-server`：redo（`log0log.cc`）+ undo 回滚段（`trx0undo.cc`）；`innodb_flush_log_at_trx_commit=1` 就是 WAL 规则的开关（设为 2 会在崩溃时丢最后一秒事务）。
  - `facebook/rocksdb`（≈32.1k★）：LSM 树的 WAL + MANIFEST；LSM 场景下 WAL 更像「memtable 的 redo」，compaction 后即可回收。
  - `etcd-io/etcd`（≈48k★）：Raft 日志 + WAL + snapshot，是「分布式 WAL + 快照压缩」的教科书实例。
  - `wiredtiger` / `mongodb/mongo`（≈28.6k★）：WiredTiger 的 WAL + 检查点实现同样遵循 ARIES 三原则。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "提交成功 = 数据页已写盘" | no-force：提交只需 **redo log** 落盘，数据页可延迟刷 |
| 2 | "undo log 和 redo log 都是日志，作用差不多" | undo 保证原子性（回滚/构造旧版本），redo 保证持久性（重放），方向相反 |
| 3 | "检查点会把所有脏页刷盘" | 现代数据库用**模糊检查点**，只记元数据，不强制刷盘 |
| 4 | "redo 只重做已提交事务" | ARIES **重复历史**：所有更新都 redo，未提交事务随后由 undo 撤销 |
| 5 | "回滚不需要记日志" | 必须写 **CLR**，否则回滚中途再崩溃无法判断补偿是否已完成 |
| 6 | "commit 后立刻断电也不会丢" | 取决于 `flush_log_at_trx_commit` / `synchronous_commit` 配置，异步提交会丢 |
| 7 | 🔧 本书缺口 | 未讲 **SSD torn page / full_page_writes**、**NVM 上的恢复**、**Raft/Paxos 作为分布式 WAL**、**备份与 PITR 的工程流程** |
