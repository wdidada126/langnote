# 第 26 章 高级事务处理

> **本章地图**：**事务处理监控器（TP monitor）** → **事务性工作流**（workflow 与 ACID 的冲突）→ **高性能事务系统**（瓶颈在哪、H-Store/VoltDB、确定性执行）→ **主内存数据库** → **实时事务系统**（截止时间与优先级调度）→ **长事务**（**Saga / 补偿事务 / 嵌套事务 / savepoint**）→ **弱一致性等级**（degree 0–3、游标稳定性、可用副本）→ 现代形态：**消息队列事务 + 分布式事务框架（Seata/Temporal）**。

## 二、核心精讲

### 26.1 事务处理监控器（TP Monitor）
- 历史产品：**CICS**（IBM，1968 起）、**Tuxedo**（AT&T → BEA → Oracle）、**Encina**、**Top End**。
- 核心功能：① **事务路由与负载均衡**；② **跨多个资源管理器的事务协调**（**XA 接口 / 两阶段提交**，X/Open DTP 模型：AP-TM-RM 三角色）；③ **进程/线程池管理**（避免每个请求 fork 进程）；④ **持久消息队列**（把请求入队，保证不丢）；⑤ **恢复与重启**。
- 🔧 现代继承者：**Java EE 的 JTA/JTS + 应用服务器（WebLogic/JBoss）**、**消息中间件的事务消息**（RocketMQ 事务消息、Kafka 的 `exactly-once` 事务生产者）、**分布式事务框架**（Seata AT/TCC/Saga、DTM、Narayana）。理解 XA 是读这些框架源码的前提。

### 26.2 事务性工作流
- **工作流**：由多个**活动（activity）**组成的长期、多步骤业务过程（订单→支付→库存→物流→开票）。
- 与传统事务的冲突：工作流**跨越数小时/数天**、包含**人工审批**与**外部系统**（不可回滚），无法用单事务的 ACID 包裹（锁不能持有这么久）。
- 解法谱系：
  1. **Saga**（Garcia-Molina & Salem, SIGMOD 1987）：长事务拆成若干子事务 $T_1..T_n$，每个配一个**补偿事务** $C_i$；失败时逆序执行补偿（**语义原子性**而非原子性，中间状态对外可见）。
  2. **嵌套事务（nested transaction）**（Moss, 1981）：子事务可独立回滚，父事务决定最终提交；Open Nested Transaction 允许子事务提前释放锁并暴露结果（配合补偿）。
  3. **多版本 + 私有工作区**：每个活动在自己的工作区修改，最终合并（版本冲突需人工解决）。
  4. **状态机 / 事件驱动编排**：**Temporal / Cadence**（工作流即代码，持久化执行历史）、**Camunda/Zeebe**（BPMN）、**AWS Step Functions**、**Netflix Conductor**。
- 🔧 **Saga 的关键工程细节**：补偿必须是**幂等的**、**可交换的**（commutative，否则逆序补偿不正确）；前向恢复（重试）优于后向恢复；**隔离性缺失**要靠**语义锁**（`pending` 状态字段）或 **reservation 模式**弥补。

### 26.3 高性能事务系统：瓶颈何在
Stonebraker 等人的测量（*The End of an Architectural Era*, VLDB 2007）指出传统 OLTP 数据库的时间去向：
- **缓冲池管理**、**闩（latch）争用**、**锁管理**、**日志（fsync + 写入）**、**B 树维护** —— 真正用于「有用工作」的比例很低。
- 优化方向：
  - **共享一切的单线程分区**（H-Store / VoltDB）：数据按分区划分，每个分区单线程执行 → **完全去掉并发控制与闩**；跨分区事务需要全局协调（代价高 → 靠分区键设计规避）。
  - **确定性执行**（**Calvin**, SIGMOD 2012）：先就事务顺序达成一致（sequencer 层），再确定性执行 → 无分布式 2PC 协调，跨分区事务也高效。
  - **日志优化**：**group commit**（合并 fsync，MySQL 的 `binlog_group_commit`）、**early lock release**（提前释放锁，VLDB 2010）、**Aurora 的日志即数据库**（消除双写）。
  - **无锁结构**：内存索引（skip list / Bw-tree, ICDE 2013；**Masstree**, EuroSys 2012）。

### 26.4 主内存数据库
- 代表：**TimesTen**（Oracle）、**Altibase**、**H-Store/VoltDB**、**SAP HANA**（列存为主）、**Hekaton**（SQL Server In-Memory OLTP，VLDB 2013：buckets + lock-free + MVCC + OCC）、**Redis**。
- 关键认知：🔧 **内存数据库仍需 WAL 与检查点**（内存掉电即失），瓶颈从磁盘 I/O 转移到 **日志 fsync、网络与内存带宽**；**持久内存（PMem / CXL）**进一步模糊内存与存储的边界。

### 26.5 实时事务系统
- 截止期分类：**硬（hard，超时即灾难，如飞控）/ 软（soft，超时价值衰减）/ 固（firm，超时作废）**。
- 优先级调度：**EDF（最早截止期优先）**、**优先级继承**解决**优先级反转**（低优先级持锁阻塞高优先级）。
- 🔧 现实中「实时数据库」更多是**嵌入式/工业/金融撮合**场景（KDB+、TimesTen、自研内存撮合引擎），通用数据库很少提供硬实时保证。

### 26.6 长事务与弱一致性等级
- **长事务问题**：锁持有时间长（严重降低并发）、失败回滚代价大、日志巨大、长时间占用连接。
- **弱一致性等级（Gray 1976 的 degree 0–3）**：
  | 等级 | 含义 | 现代对应 |
  | --- | --- | --- |
  | Degree 0 | 不覆盖未提交数据（无脏写） | 最低要求 |
  | Degree 1 | + 无脏写丢失 |  |
  | Degree 2 | + 无脏读 | **Read Committed** |
  | **Degree 3** | + 可重复读、无幻读 | **Serializable**（≈ 严格 2PL） |
  - **游标稳定性（cursor stability）**：DB2 的默认级别，只保证**当前游标行**不加长锁（介于 degree 2 与 3 之间）。
  - **可用副本（available copies）算法**、**epsilon-serializability**（允许有限不一致）、**N 版本副本**。
- 🔧 现代视角：这些等级被 ANSI SQL 的四个隔离级别与 SI/SSI 取代（见第 14、15 章）；「弱一致性换取可用性」的思想在分布式系统中演化为**最终一致 + CRDT + 因果一致**。

## 四、近年研究与工业界开源实践

- **近年研究**：**确定性数据库的复兴**（Aria, VLDB 2020；**SLOG**, VLDB 2019；**Detock**）；**存算分离下的事务提交**（PolarDB Serverless、Aurora）；**eBPF 定位事务延迟归因**；**Saga 的形式化隔离语义**（*Highly Available Transactions*, VLDB 2014 与 *The Homeostasis Protocol*）。
- **工业界开源**（star 数 2026-09 实测）：
  - `seata/seata`（≈26.0k★）：AT（基于 undo log 的反向补偿，本质是自动 Saga）/ TCC / Saga / XA 四种模式，**本章最直接的开源对照物**。
  - `temporalio/temporal`、`uber/cadence`（≈9k★ 量级）：工作流即代码（持久化执行历史），对应 26.2 的事务性工作流。
  - `apache/rocketmq`（≈22k★）与 `apache/kafka`（≈33.8k★）：事务消息与 exactly-once，对应 TP monitor 的持久队列功能。
  - `apache/doris`（≈16.0k★）、`voltdb`（已转闭源/归档）、`redis/redis`（≈76.5k★）：内存/高性能 OLAP 与内存存储。
  - `HdrHistogram/HdrHistogram`：尾延迟测量，是任何事务系统性能工程的必备工具。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "Saga 等价于分布式事务" | Saga 只提供**最终一致**（中间状态可见），且要求**补偿幂等** |
| 2 | "工作流可以用一个 ACID 事务包住" | 长周期 + 外部系统使锁与回滚不可行；必须拆分 + 补偿 |
| 3 | "内存数据库不需要日志" | 需要 WAL + checkpoint + 复制；只是瓶颈转移 |
| 4 | "XA/2PC 能解决微服务的跨库事务" | 可用性代价高、锁持有时间长；微服务更常用 **Saga + 幂等 + 去重表** |
| 5 | "提高并发度就能提高吞吐" | 闩与日志 fsync 会形成拐点；反而需**分区单线程**或确定性执行 |
| 6 | 🔧 本书缺口 | 未覆盖 **2010–2025 的确定性事务、Saga 的工业实现（Temporal/Seata）、消息事务、Serverless 事务**；TP monitor 一节的 CICS/Tuxedo 内容可作历史背景理解 |
