# 第 17 章 数据库系统体系结构

> **本章地图**：集中式系统 → 客户-服务器系统（两层和三层）→ **并行数据库**（共享内存 / 共享磁盘 / 无共享）→ **分布式数据库**（本地自治、分片、复制、CAP）→ 云数据库与 Serverless → 现代「存算分离」与 HTAP。本章是第 18、19 章的总纲。

## 二、核心精讲

### 17.1 集中式系统
- 单机上运行全部功能（早期大型机）。优点：实现简单；缺点：**纵向扩展有天花板**，单点故障。
- 🔧 现实：今天一台 x86 服务器（数百核 + TB 内存 + NVMe）已能承担过去大型机的负载，「单机优先」在 2020 年代重新成为主流哲学（SQLite/DuckDB 的复兴、SingleStore 的单机性能宣传）。

### 17.2 客户-服务器系统
- **两层架构**：客户端应用（含业务逻辑）直连数据库 → 胖客户端，维护成本高。
- **三层架构**：表现层（浏览器/App）→ 应用服务器（业务逻辑、连接池）→ 数据库。**中间件**承担连接池、缓存、读写分离路由。
- 🔧 工程要点：**连接池**（HikariCP）在应用侧而非数据库侧；**连接风暴**是三层架构最典型的容量问题（PG 的 `max_connections` 硬限制催生 pgbouncer；MySQL 用 thread pool 插件）。

### 17.3 并行数据库：三种体系结构
| 架构 | 特征 | 代表 | 评价 |
| --- | --- | --- | --- |
| **共享内存（shared-memory）** | 多 CPU 共享同一内存与磁盘 | 单机多核、PostgreSQL 并行查询 | 最易实现，受内存带宽与 NUMA 限制 |
| **共享磁盘（shared-disk）** | 多节点共享存储，各自独立内存 | Oracle RAC、早期 DB2 pureScale | 需分布式锁管理（DLM）与缓存一致性 |
| **无共享（shared-nothing）** | 节点各自 CPU/内存/磁盘，靠网络协调 | Teradata、Greenplum、ClickHouse、TiDB | **扩展性最好**，是分布式数仓的事实标准 |

- 🔧 关键结论：**shared-nothing 是唯一具备近线性扩展能力的架构**，代价是需要数据重分布（reshuffle）与分布式事务。

### 17.4 分布式数据库
- 目标：**本地自治**（节点可独立管理）+ **不依赖中心站点** + **持续运行** + **位置独立性** + **分片独立性** + **复制独立性** + **分布式查询/事务** + **硬件/OS/网络/DBMS 异构**。
- **分布式事务**：两阶段提交（2PC，协调者 + 参与者，prepare/commit 两轮）、三阶段提交（3PC 解决协调者单点阻塞，但网络分区下仍不安全）。
- **CAP**：分区容错 P 是网络前提；发生分区时只能在 **一致性 C** 与 **可用性 A** 之间取舍。🔧 **CAP 常被误读**：无分区时系统可同时满足 C 与 A；真正落地要看 **PACELC 定理**（Else：延迟 L 与一致性 C 的权衡）。
- **一致性模型谱系**：线性一致（linearizable）> 顺序一致 > 因果一致 > 最终一致；弱一致系统常用 **Quorum（R + W > N）** 与 **读修复**。

### 17.5 云数据库与 Serverless
- IaaS（托管实例 RDS）→ PaaS（托管服务）→ **存算分离**（Aurora「日志即数据库」、PolarDB、Snowflake）→ **Serverless / 自动弹性**（Aurora Serverless v2、Neon、PlanetScale）。
- 🔧 Aurora 的核心洞见：**跨网络写 6 副本的 redo 页很贵，只传 redo log 流**；把恢复逻辑下沉到存储层 —— 这是「数据库即日志」思想的最成功商业实践（SIGMOD 2017 论文）。

### 17.6 现代延伸：HTAP 与多模
- **HTAP**：同一系统同时服务 OLTP 与 OLAP（TiDB 的 TiFlash 列存副本、SingleStore、Oracle Database In-Memory）。
- **多模 / 统一引擎**：文档、KV、图、向量（PostgreSQL 的 pgvector、MongoDB Atlas Vector Search）。

## 四、近年研究与工业界开源实践

- **近年研究**：**存算分离的弹性**（Neon 的 Pageserver 架构，VLDB 2022 系统论文）；**Serverless 数据仓库的冷热分层**；**disaggregated memory / RDMA 池化**（PolarDB Serverless、Google AlloyDB）；**HTAP 的资源隔离与一致性**（ByteHTAP, VLDB 2022）。
- **工业界开源**（star 数 2026-09 实测）：
  - `pingcap/tidb`（≈40.6k★）：shared-nothing + HTAP（TiKV 行存 + TiFlash 列存，Raft Learner 异步复制），国产分布式数据库代表。
  - `cockroachdb/cockroach`（≈32.5k★）：Raft 分片 + 串行化分布式事务，纯 shared-nothing 的「Spanner 开源实现」。
  - `clickhouse/clickhouse`（≈50.1k★）：shared-nothing 列存的极致实践，MPP 分析型。
  - `duckdb/duckdb`（≈41.7k★）：**嵌入式分析**反向路线（进程内 OLAP），证明「单机优先」仍在复兴。
  - `apache/hadoop`（≈15.7k★）/ `apache/spark`（≈44.0k★）/ `apache/hive`（≈6.0k★）：大数据侧的 shared-nothing 生态（HDFS 存储 + 计算引擎解耦，本质是 shared-disk 与 shared-nothing 的混合）。
  - `etcd-io/etcd`（≈48k★）：Raft 共识 + 分布式配置，理解分布式一致性的最小可运行样例。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "分布式一定比单机快" | 跨节点网络与分布式事务开销巨大；**能单机就不要分布式** |
| 2 | "CAP 三选二" | P 是网络属性不可选；真正取舍在 **C vs A**（分区时）与 **L vs C**（平时，PACELC） |
| 3 | "2PC 是无懈可击的原子提交" | 协调者崩溃会导致参与者**阻塞**（in-doubt 事务），需 Paxos/Raft 复制协调者 |
| 4 | "共享磁盘天然高可用" | 需分布式锁管理与缓存融合协议（cache fusion），实现难度极高 |
| 5 | 🔧 本书缺口 | 第 6 版成书于 2010 年前后，**几乎未涉及云原生存算分离（Aurora/Snowflake）、Serverless、HTAP、NewSQL（Spanner/Cockroach/TiDB）、多模与向量检索** —— 需补读 2015 年后的系统论文 |
