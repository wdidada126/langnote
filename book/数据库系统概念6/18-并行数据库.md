# 第 18 章 并行数据库

> **本章地图**：**I/O 并行**（分区：轮转 / 哈希 / 范围；偏斜 skew 处理）→ **查询间并行**（并发执行多个查询，提升吞吐）→ **查询内并行**（**操作符内并行** intra-operation 与 **操作符间并行** inter-operation，流水线 vs. 物化）→ **并行排序**（范围分区排序 + 归并）→ **并行连接**（分片-复制、并行 hash join、并行嵌套循环、非对称分片）→ **并行度（DOP）选择**与代价模型。

## 二、核心精讲

### 18.1 I/O 并行：数据分区
| 策略 | 规则 | 适用 | 风险 |
| --- | --- | --- | --- |
| **轮转（round-robin）** | 第 i 条到第 i mod n 个磁盘 | 顺序全表扫描 | 点查询要读全部磁盘 |
| **哈希分区** | 对分区属性哈希 | 点查询、等值连接 | **数据偏斜**（热点 key） |
| **范围分区** | 按值域区间 | 范围扫描、非等值连接 | **值分布不均**导致偏斜 |

- 🔧 偏斜处理工程手段：**虚拟桶（virtual bucket / consistent hashing）**、**按高频 key 单独拆分**、**统计直方图预分区**、Spark 的 **AQE（Adaptive Query Execution）动态合并倾斜分区**（SPARK-9850 起）。
- **分区属性选择**：应基于查询负载中的高频 join/过滤键；选错则几乎所有查询都需要重分布。

### 18.2 查询间并行（inter-query parallelism）
- 多个查询/事务并发执行 → 提高**吞吐**，不降低**单查询延迟**。
- 🔧 受制于**锁与闩（latch）争用**：并发度超过某点后吞吐反而下降（PostgreSQL / MySQL 在 64–128 并发后常见的吞吐拐点，催生连接池限流与 thread pool）。

### 18.3 查询内并行（intra-query parallelism）
- **操作符内并行**：同一操作符（如一次扫描、一次排序）在多个数据分区上并行执行 —— 依赖数据已分区。
- **操作符间并行**：不同操作符并行（**流水线并行** pipeline：消费者边消费边生产；**独立并行**：无依赖的操作符同时跑）。
- 流水线 vs 物化：
  - 流水线省 I/O，但生产者可能被消费者阻塞（需**流水线缓冲区 / flow control**）；
  - 物化（materialize）写中间结果，便于重新执行与并行度切换。
- 🔧 现代执行引擎的两种范式：
  1. **火山模型（Volcano / iterator）**——教科书默认，行式 `next()` 调用，虚函数调用开销大；
  2. **向量化 / 批量执行（vectorized execution）**——MonetDB/X100（CIDR 2005）提出，一次处理一批（vector），ClickHouse、DuckDB、Velox 均采用；**编译执行（codegen）**——Hyper（Neumann, VLDB 2011）把查询编译成机器码。

### 18.4 并行排序
- **范围分区排序**：先按排序键范围把数据分到各节点/线程 → 各分区本地排序 → 归并（n 路归并，并行前缀技术可加速）。
- 🔧 工程：PostgreSQL 的 `Gather Merge`、ClickHouse 的 `PartialSorting + MergeSorting`、Spark 的 sort-based shuffle（替代早期的 hash shuffle，SPARK-20499 后成为默认）。

### 18.5 并行连接
| 算法 | 思路 | 适用 |
| --- | --- | --- |
| **分片-复制连接（partitioned / fragment-and-replicate）** | 把两个关系按 join key 分区，各分区本地 join | 等值连接，两表都已分区 |
| **并行哈希连接** | 各分区内建哈希表探测；或用**非对称分片**（小表广播到所有节点 = **broadcast join**，大表保持分区） | 大小表差异大时 broadcast 最优 |
| **并行嵌套循环** | 分块驱动表，逐块与内表并行比对 | 非等值 / 小表 |

- 🔧 **broadcast hash join vs. shuffle hash join** 是 Spark / Flink / TiDB 优化器的核心决策（依据统计信息中的表大小与 `autoBroadcastJoinThreshold`）。

### 18.6 并行度与代价模型修正
- 并行查询代价 ≈ $\frac{\text{串行代价}}{\text{并行度}} + \text{协调开销} + \text{重分布开销}$。
- 🔧 并行度并非越大越好：受 CPU 核数、内存（哈希表内存放大）、**数据重分布网络带宽**三重限制；超配会导致 spill 到磁盘或 OOM。
- 🔧 NUMA 与跨 socket 内存访问：PostgreSQL 在 NUMA 机器上高并行度性能退化是已知问题（社区长期讨论），ClickHouse 通过 `numa` 绑定与本地内存池缓解。

## 四、近年研究与工业界开源实践

- **近年研究**：**morsel-driven 调度**（细粒度任务窃取，SIGMOD 2014 后成为内存数据库标配）；**向量化 + 编译融合（Velox / Substrait / Arrow DataFusion）**；**存算分离下的 shuffle 优化**（push-based shuffle，Spark SPARK-30602）；**GPU 加速 join/sort**（HeavyDB、cuDF）；**学习式代价模型用于并行度选择**。
- **工业界开源**（star 数 2026-09 实测）：
  - `clickhouse/clickhouse`（≈50.1k★）：向量化 + 多核并行的极致工程，`max_threads`、SIMD、`ParallelHashJoin` 均可对照本章概念。
  - `duckdb/duckdb`（≈41.7k★）：进程内向量化 + 多线程 pipeline（`TaskScheduler` 的 morsel 派发），代码量小、最适合逐行对照教科书算法。
  - `apache/spark`（≈44.0k★）：AQE 动态倾斜处理、broadcast/shuffle join 选择、codegen（WholeStageCodegen）。
  - `apache/flink`（≈26.4k★）：流批一体的并行执行模型（operator chain、slot sharing）。
  - `facebookincubator/velox`：Meta/Intel 开源的统一向量化执行引擎，被 Presto/Spark/Gluten 接入，代表 2020 年代执行引擎的收敛方向。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "并行度设成 CPU 核数的倍数就好" | 受内存与网络限制；哈希表内存放大常导致 spill/OOM |
| 2 | "哈希分区一定均匀" | **热点 key 会致命偏斜**，需直方图/盐化（salting）/AQE 动态拆分 |
| 3 | "流水线总是优于物化" | 阻塞操作符（sort、hash build）会截断流水线；且物化有利于重新执行 |
| 4 | "并行只关乎 CPU" | 并行数据库中 **I/O 与网络（重分布）** 才是主要瓶颈 |
| 5 | 🔧 本书以火山模型 + shared-nothing 磁盘库为主 | 需补充 **向量化执行、编译执行、morsel 调度、NUMA 感知**；这些是 2005–2014 年的范式转变，第 6 版尚未充分反映 |
