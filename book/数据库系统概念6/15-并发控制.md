# 第 15 章 并发控制

> **本章地图**：锁的基本概念（共享锁 S / 排他锁 X）→ **两阶段封锁协议 2PL**（增长/收缩阶段、严格 2PL、强严格 2PL）→ 锁管理器实现（锁表、锁转换、锁升级、死锁预防与检测）→ **多粒度封锁与意向锁**（IS/IX/SIX）→ 基于图的协议（树协议）→ **时间戳排序协议**（Thomas 写规则）→ **有效性检查协议**（乐观并发控制，读/验证/写三阶段）→ **多版本机制 MVCC / 快照隔离** → MVCC + 2PL 的混合（MySQL InnoDB）→ 幻读与谓词锁 / 间隙锁 / next-key lock → 插入删除操作与删除 phantom。

## 二、核心精讲

### 15.1 锁与两阶段封锁
- **共享锁（S）/ 排他锁（X）相容矩阵**：S-S 相容，其余不相容。
- **2PL 定理**：若所有事务都遵守两阶段封锁（先只加锁、释放第一个锁之后不再申请新锁），则调度**一定冲突可串行化**。
  - 🔧 证明要点：以「第一个释放锁」时刻为界，把事务分成增长阶段与收缩阶段，按「获得最后一个锁的顺序」构造前驱图，可证无环。
- **严格 2PL（strict 2PL）**：排他锁**直到提交/中止才释放** → 避免级联回滚（脏读导致的连锁 abort）。
- **强严格 2PL（rigorous 2PL）**：**所有**锁（含 S 锁）都在提交时释放 → 商用数据库主流（InnoDB / SQL Server / DB2 默认即此类），因为实现简单且可直接配合 WAL。
- 🔧 **2PL 只保证冲突可串行化，不保证无死锁**，也不保证「可恢复调度」——所以必须叠加严格性。

### 15.2 封锁的实现：锁管理器
- **锁表**：以数据项（或页 / 行 / 表）为 key 的哈希表，链表记录请求队列与授予情况。
- **锁转换（lock conversion）**：S → X 升级（放队列前面优先，否则易死锁）；X → S 降级（放队列尾部）。
- **锁升级（lock escalation）**：当某事务持有的行锁数量超过阈值，把它升级为**表锁**以节省内存 —— SQL Server、DB2 均如此；🔧 这是「并发度突然下降」的经典原因（一次大批量 UPDATE 把整表锁住）。
- **死锁处理**
  - **预防**：① 一次性申请全部锁（简单但并发低）；② **排序**（按固定次序加锁）；③ **时间戳法 wait-die / wound-wait**（老等新 / 老抢新，保证无环）；④ **超时 + 重试**。
  - **检测与恢复**：维护 **wait-for 图**（等待图），周期性检测环；选择**牺牲者**（victim）回滚 —— InnoDB 的选择策略是「回滚 undo log 记录数最少的事务」（即代价最小，而非最年轻）。
  - 🔧 现代系统更常用**锁等待超时（innodb_lock_wait_timeout，默认 50s）+ 等待图检测**双管齐下。

### 15.3 多粒度封锁与意向锁
- 粒度层次：数据库 → 表（关系）→ 页 → 行（元组）。
- **意向锁**：要在下层加 S 锁，必须先在上层加 **IS**；要加 X 锁，先加 **IX**；**SIX** = S + IX（整表读 + 部分行写）。
  - 相容矩阵要点：IX 与 IX 相容（不同行可同时写），IX 与 S 不相容，SIX 与 IS 相容、与 IX/SIX/S 不相容。
- 🔧 意向锁的本质：**让上层不必扫描全部下层锁表就能判断冲突**，是教科书里少有讲透但工程上极常见的设计（InnoDB 的 `IS`/`IX` 即此）。

### 15.4 基于图的协议（树协议）
- 前提：数据项构成有向无环图（常为树），加锁必须**自顶向下**，且只有持有父节点锁才能加子节点锁；可随时解锁，但解锁后不能再加锁。
- 性质：**保证冲突可串行化 + 无死锁**，且并发度高于 2PL（因为可以更早解锁）。
- 🔧 缺点：事务可能被迫锁住并不访问的祖先节点。实际系统很少直接用，但**B+ 树索引的 latch crabbing（蟹行）**就是这一思想的产物。

### 15.5 时间戳排序协议（Timestamp Ordering, TO）
- 每个事务 $T_i$ 有唯一时间戳 $TS(T_i)$（进入系统时刻或全局单调计数器）。
- 读：$TS(T_i) < WTS(Q)$ → 读到的是「未来」写 → **回滚重启**；否则允许并执行 $RTS(Q) = \max(RTS, TS)$。
- 写：$TS(T_i) < RTS(Q)$ → 有「未来」事务已读过旧值 → 回滚；$TS(T_i) < WTS(Q)$ → 写已被覆盖 → **Thomas 写规则：忽略该写（而非回滚）**，这是 Thomas 写规则带来的改进（在视图可串行化下仍正确，但不再是冲突可串行化）。
- 🔧 优点：无死锁；缺点：长事务频繁重启（starvation）、需要给事务分配新时间戳、**不可恢复**（除非配合 commit 排序）。商用单点数据库几乎不用纯 TO，但 **CockroachDB 用混合逻辑时钟 HLC 做 SI 的快照时间戳**，思想同源。

### 15.6 有效性检查协议（乐观并发控制 OCC）
- 三阶段：**读阶段**（读数据到私有副本，写进临时变量）→ **有效性检查阶段**（分配时间戳，校验）→ **写阶段**（写入数据库）。
- 校验规则：对 $T_i$（时间戳小于已验证事务集）：
  1. 若 $T_j$ 已提交且在 $T_i$ 读阶段之后仍可能写 → 冲突；
  2. 检查 $T_i$ 读集与 $T_j$ 写集是否相交且 $T_j$ 在 $T_i$ 开始前未完成写阶段。
- 🔧 OCC 在**低冲突**（读多写少、短事务）场景下吞吐远高于 2PL；但在高冲突下「重启风暴」致命。现代落地：**FoundationDB、CockroachDB 的高冲突写意图、内存数据库 Hekaton、F1**。

### 15.7 多版本并发控制（MVCC）与快照隔离
- 三种多版本协议：**多版本时间戳排序（MVTO）**、**多版本两阶段封锁（MV2PL）**、**快照隔离（Snapshot Isolation, SI）**。
- **快照隔离**：读事务看到**事务开始时刻的已提交快照（Start Timestamp）**，写事务用 **first-committer-wins** 规则（若两事务写同一项且并发，后提交者中止）。
- 性质：SI **不是可串行化**——经典反例 **写偏斜（write skew）**：两个事务各自读同一集合后写不相交项，导致约束被破坏（如「至少一名医生值班」两人同时请假）。
- 解法：**SSI（可串行化快照隔离）**——Cahill 等人在 PostgreSQL 9.1 实现，通过跟踪 `rw-conflict`（读写依赖）环检测并中止。
- 🔧 版本存储：InnoDB 用 **undo log 回滚段构造旧版本**（版本链放在回滚段，不在主索引），PostgreSQL 用 **堆内多元组 + HOT 更新**，Oracle 用 undo 表空间。版本 GC：InnoDB 的 purge 线程受 **历史链表** 与最老活跃事务（ReadView）限制 → 长事务导致 undo 膨胀与 purge 滞后（线上常见故障）。

### 15.8 MVCC + 2PL 的混合（MySQL InnoDB 实际做法）
- **快照读（consistent read，`SELECT`）走 MVCC，无锁；当前读（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）走 2PL + 行锁**。
- 行锁三种：**Record Lock**（记录锁）、**Gap Lock**（间隙锁，锁索引记录之间的区间）、**Next-Key Lock**（记录 + 间隙，左开右闭区间）——正是靠 next-key lock 在 **RR** 级别消除了幻读（这也解释了为什么 InnoDB 的 RR 比标准定义的 RR 更强）。
- 🔧 退化为表锁的陷阱：若 `UPDATE` 的谓词**未走索引**（全表扫描），InnoDB 会给扫描过的所有行加锁（甚至全表），并发直接崩塌 —— 生产事故高发点。

### 15.9 幻读、插入与删除
- 幻读（phantom）：同一事务两次范围查询，另一事务**插入**了满足条件的新行。
- 解法谱系：**谓词锁（predicate lock，精确但代价高）→ 索引区间锁 / 间隙锁（近似但高效）→ 物化冲突（materialize conflict，"phantom 表"技巧）**。
- 🔧 删除操作的处理：删除一条记录后，其间隙的锁合并，可能导致锁区间扩大；`-infinity / +infinity` 伪记录用于锁住边界。

## 四、近年研究与工业界开源实践

- **近年研究**：**确定性数据库**（Calvin, SIGMOD 2012 / 拓展到 FaunaDB；以及 **Bohm**、**Aria**, VLDB 2020）——先定序再执行，彻底消除分布式两阶段提交中的并发不确定性；**OCC 在存算分离与 RDMA 场景的复兴**（如 **Sundial**, CIDR 2021 / VLDB 2022，用逻辑租约降低重启率）；**Hekaton**（SQL Server 内存 OLTP，VLDB 2013 论文）把 MVCC + OCC 做到内存级吞吐。
- **工业界开源**（star 数 2026-09 实测）：
  - `postgresql/postgres`（≈17k★）唯一在开源关系库里实现 **SSI** 的系统，源码见 `src/backend/storage/lmgr/predicate.c`。
  - `pingcap/tidb`（≈40.6k★）：Percolator 模型（Google，OSDI 2010）的开源实现，客户端两阶段提交 + 乐观事务（后加悲观事务模式）；TiDB 5.0 起默认**悲观事务 + 分布式死锁检测**。
  - `cockroachdb/cockroach`（≈32.5k★）：**HLC 混合逻辑时钟 + 串行化快照**，写意图（write intent）机制对应 OCC/TO 的融合。
  - `facebook/mysql-5.6`、`mysql/mysql-server`：InnoDB 锁实现见 `storage/innobase/lock/lock0lock.cc`（`lock_rec_lock`、`lock_rec_insert_check_and_lock` 即间隙锁判定入口）。
  - FoundationDB（apple/foundationdb）：纯 OCC + 确定性模拟测试，是「教科书 OCC 真正在 production 跑」的最好样本。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "2PL 就能避免死锁" | 2PL 只保证冲突可串行化；死锁靠预防/检测独立解决 |
| 2 | "遵守 2PL 就是严格 2PL" | 严格 2PL 要求 X 锁到提交才放；普通 2PL 会级联回滚 |
| 3 | "SI 就是可串行化" | SI 允许写偏斜；需 SSI 或显式加锁（`FOR UPDATE`） |
| 4 | "MVCC 读不加锁，所以不会阻塞写" | 快照读不阻塞，但**当前读**（DML / `FOR UPDATE`）仍走 2PL |
| 5 | "RR 一定有幻读" | 标准 RR 有，但 **InnoDB RR 因 next-key lock 无幻读**；PG 的 RR（SI）也无幻读但可能写偏斜 |
| 6 | "意向锁是给行加的" | 意向锁加在**上层粒度**（表级），用于快速判断下层冲突 |
| 7 | "死锁只能靠超时发现" | InnoDB / PG 均有基于等待图的主动检测，超时是兜底 |
| 8 | 🔧 本书未覆盖 | **分布式并发控制**（2PC 期间的锁持有、Percolator 的 primary lock、TrueTime / HLC 外部一致性）、**确定性并发控制**、**SI 在只读副本上的 staleness 语义** |
