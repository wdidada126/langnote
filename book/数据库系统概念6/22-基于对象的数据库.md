# 第 22 章 基于对象的数据库

> **本章地图**：关系模型的**阻抗失配（impedance mismatch）** → **复杂数据类型**（结构化类型、集合构造器 array/multiset、嵌套关系）→ **继承**（类型继承与表继承）→ **对象标识（OID / 引用）** vs 外键 → **持久化编程语言**（ODMG、OQL、JDO / JPA）→ **对象-关系（ORDBMS）与 SQL:1999 结构化类型** → 与关系模型的权衡 → 现代结局：**ORM + JSON/文档数据库**胜出，纯 OODBMS 退场。

## 二、核心精讲

### 22.1 动机：阻抗失配
- 面向对象语言中的**对象图**（引用、继承、集合、多态）与关系模型中的**平表 + 外键**之间存在表示差异，需要大量样板代码做映射。
- 两条技术路线：
  1. **OODBMS**（纯对象数据库，GemStone、ObjectStore、Versant）——让数据库直接存对象，消除映射；
  2. **ORDBMS / ORM**——在关系模型里加对象特性（SQL:1999 结构化类型），或在应用层加映射框架（Hibernate）。
- 🔧 历史结论：**OODBMS 在商业上失败**（Stonebraker 等对此有大量争论，《Object-Relational DBMSs: The Next Great Wave》, 1996 是 ORDBMS 阵营的宣言）。原因：SQL 生态与查询能力的网络效应太强，而「对象导航」在集合查询面前并无优势；**SQL 标准吸收了对象特性（结构化类型、继承、方法），对象数据库的核心卖点被消化掉了**。

### 22.2 复杂数据类型与类型构造器
- **结构化类型（structured / row type）**：`CREATE TYPE Address AS (street VARCHAR, city VARCHAR)`，可作列类型、可嵌套。
- **集合构造器**：`array`（有序、可重复）、`multiset`（无序、可重复）、`set`（无序、去重）、嵌套关系（表值列）。
- **大对象 LOB**：CLOB / BLOB —— 数据库里存文档、图片、音视频（🔧 现代实践：大文件放对象存储 S3，只在库里存 URL/元数据）。
- 🔧 现代等价物：**PostgreSQL 的 `jsonb`、复合类型、数组、hstore**；**MySQL 的 JSON 类型** —— 教科书讲的「结构化类型」在今天几乎都以 **JSON 半结构化** 的形式落地，而非 SQL:1999 的 `CREATE TYPE`。

### 22.3 继承
- **类型继承**：`CREATE TYPE Student UNDER Person`（继承属性并可添加）；**表继承**：子表继承父表的列（PostgreSQL 的 `INHERITS`）。
- 继承带来的语义难题：**约束与外键如何随继承传播**（PostgreSQL 的继承与外键约束长期不兼容，是文档明确警告的坑）、**多重继承**下的冲突消解。
- 🔧 工程实现：ORM 中常见三种继承映射 —— **单表（single table，靠 discriminator 列）**、**每类一表（joined）**、**每具体类一表（table-per-concrete-class）**；JPA 的 `@Inheritance` 注解即这三种策略，与数据库层继承是两套东西。

### 22.4 对象标识与引用
- **对象标识 OID**：系统生成、与值无关、永久不变（即使对象被删除也不复用）→ 支持**对象共享**与**环状结构**，区别于关系模型的「值标识（主键）」。
- **引用（reference / `REF`）**：SQL:1999 的 `REF(type)` 列 + `DEREF` 操作，可 `deref` 出对象。
- 🔧 权衡：OID 便于表示图/网状结构，但破坏了关系模型的**数据独立性**（程序依赖物理标识），也让「值相等 vs 标识相等」的语义变复杂。现代做法：**主键（业务无关 UUID / 雪花 ID）承担 OID 角色，外键承担引用角色**；图数据库（Neo4j）才真正用物理指针式关系（`relationship`）。

### 22.5 持久化编程语言与 OQL
- **持久化语言**：把语言的持久化能力扩展为数据库（OPAL/GemStone、Java 的 **JDO** 与其后继 **JPA/Hibernate**、C++ 的 ODMG 绑定）。
- **OQL（Object Query Language，ODMG 标准）**：语法类似 SQL 但返回对象/集合，支持路径表达式（`p.address.city`）与导航。
- 🔧 现代对照：**JPA Criteria / JPQL、Hibernate HQL** 就是 OQL 的直系后代；而 **LINQ（.NET）** 与 **Python SQLAlchemy / Django ORM** 也属同类思想。教科书里的 OQL 本身已死，但其思想活在所有 ORM 里。

### 22.6 对象-关系DBMS（ORDBMS）
- 关系模型 + 用户定义类型（UDT）+ 用户定义函数（UDF）+ 继承 → **PostgreSQL、Illustra、Informix Universal Server、Oracle 8 的对象选项**。
- 🔧 **PostgreSQL 是 ORDBMS 血脉的直接继承者**（POSTQUEL → Postgres 的 ADT 与继承设计来自 Stonebraker 的 Postgres 项目），其 `CREATE TYPE`、`CREATE OPERATOR`、`CREATE FUNCTION`（可用 C/PLpgSQL/PLPython 编写）、表继承、扩展机制（PostGIS 就是用 UDT + 索引扩展实现的）都是本章概念的活样板。

## 四、近年研究与工业界开源实践

- **近年研究**：**文档/半结构化模型的理论化**（JSON Schema、MongoDB 的 schema 演进研究）；**图模型的统一**（GQL 标准，ISO/IEC 39075，2024 年发布，把图查询标准化）；**对象模型的回归**（Figma/Autodesk 等场景下 CRDT + 本地对象存储的 "local-first" 软件，SIGMOD 2022 相关讨论）；**LLM 时代的语义数据模型**。
- **工业界开源**（star 数 2026-09 实测）：
  - `mongodb/mongo`（≈28.6k★）：文档数据库，是「对象/嵌套结构直接入库」路线最成功的商业化产物（BSON 文档 ≈ 嵌套对象）。
  - `hibernate/hibernate-orm` / `mybatis/mybatis-3`（≈20.4k★）：阻抗失配的**应用层**主流解法；第 8 章（E-R）与本章是 ORM 的理论基石。
  - `postgresql/postgres`（≈17k★）：ORDBMS 活化石，`CREATE TYPE`、`INHERITS`、UDF 一应俱全。
  - `neo4j/neo4j`（≈17.3k★）：图数据库，用「关系即一等公民」解决对象模型的导航需求。
  - `prisma/prisma`、`sqlalchemy/sqlalchemy`：现代 ORM/查询构建器，OQL 思想的当代形态。

## 五、常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "对象数据库取代关系数据库才是先进的" | 历史上 OODBMS 商业失败；关系模型 + **JSON 类型 + ORM** 消化了其需求 |
| 2 | "OID 比主键更自然，应该用" | OID 破坏数据独立性；现代用 **UUID/雪花 ID 作代理主键** |
| 3 | "嵌套集合比 join 更快，所以嵌套表更好" | 嵌套在非规范化读场景下快，但更新异常与约束维护困难 |
| 4 | "表继承是建模继承关系的首选" | ORM 层通常用 **单表 + discriminator**；数据库表继承会带来约束/分区的复杂语义 |
| 5 | 🔧 本书定位 | 第 6 版保留本章主要出于模型谱系完整性；**工程上应把精力转向 JSON/文档模型、ORM 映射策略与图模型（GQL）** |
