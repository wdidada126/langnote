# 第 5 章 从线程通信来窥探并发中的条件等待机制

> 等待/通知：`Object.wait()`/`notify()`/`notifyAll()`（基于 Monitor）、`Condition.await()`/`signal()`（基于 AQS 条件队列）、`park`/`unpark`（`Unsafe`/`LockSupport`）。本书揭秘「为什么 wait 必须在 synchronized 里 + while 循环」。详见黄文海 5 章、之美 10 章。

## 一、核心精讲

### 2.1 🔧 wait 必须在同步块 + while 循环
- `wait()` 释放锁并等，醒来需重新竞争锁；用 `if` 可能因「虚假唤醒/多等待者」漏判（🔧 永远 `while(条件) wait()`，不用 `if`；`notifyAll` 优于 `notify` 避免信号丢失）。

### 2.2 Condition vs wait/notify
- 一个 `ReentrantLock` 可建多个 `Condition`（多等待集），精准 `signal` 特定条件（🔧 `Object.wait` 只有一个等待集，`notifyAll` 唤醒全部低效）；AQS 下 Condition 用独立条件队列。

### 2.3 LockSupport.park/unpark
- `Unsafe.park` 底层，许可式（先 unpark 再 park 也不阻塞）（🔧 `LockSupport` 是 AQS/线程池等待基础；虚拟线程的 `park` 是卸载而非阻塞 carrier）。

## 三、常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | "if 配 wait" | 必 while，防虚假唤醒 |
| 2 | "notify 够用" | 多等待者用 notifyAll |
| 3 | "wait 不在同步块" | 抛 IllegalMonitorState |
| 4 | "一个锁一个条件" | Lock 可多 Condition |
