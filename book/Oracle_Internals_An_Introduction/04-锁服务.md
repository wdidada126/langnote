## 4.0 本章导读

锁服务回答的是"两个事务同时要同一件事，谁先谁后、怎么排队、堵死怎么办"。本章顺序：与闩锁的分界（4.1）、模式矩阵与 TM/TX 两族（4.2）、阻塞与死锁（4.3）、两组 SQLite 对照实测（4.4）、调优世界观（4.5）。

## 4.1 锁与闩锁的分界（回链 03 章）

⚠️ 转述（概念轴）：闩锁保护**机制**（内存结构改写瞬间），锁保护**语义**（这行数据在事务意义上归谁、以什么强度）。三条硬差异：

1. **持有长度**：闩锁微秒级（[03-闩锁服务.md](03-闩锁服务.md)）；锁可跨越整个事务（秒→小时）。
2. **排队形态**：闩锁是 spin/sleep 竞速；锁是**入队**（enqueue 一词来源）——按到达序与模式兼容性排队，锁资源对象化、可命名、可查询。
3. **可见性**：锁有用户可见的申请面（`LOCK TABLE`）与释放语义（COMMIT/ROLLBACK），闩锁完全内核私有。

一个共同底座（⚠️ 转述）：两者最终都落在"内核里的串行化请求"，8i 时代都进同族等待记账——这正是本书把 Locks 与 Latches 分章并列、06 章再合并观测的原因。

## 4.2 锁模式矩阵与两族锁

⚠️ 转述（v$lock 口径，LMODE/REQUEST 数字模式与现行文档一致）：

- 模式阶：**Null(NL) &lt; Row Share(RS/SS) &lt; Row Exclusive(RX/SRX) &lt; Share(S) &lt; Share Row Exclusive(SRU/SSX) &lt; Exclusive(X)**；下位之间大多兼容（这正是"行级锁下并发 DML 不打架"的机制面），S 与 RX 互斥（表级读锁挡住他人 DML）。
- **TM（表锁）**：任何 DML 自动申请，模式 RX——它不锁内容，只声明"我正在改这张表"，防住并发的破坏性 DDL。
- **TX（事务锁）**：行级锁的化身——首个改某行的事务把该行的 TX 锁挂在 ITL/块上；他人改同行 ⇒ 排在该事务后面。`enq: TX - row lock contention`（后代表述 ⚠️）是 OLTP 最常见的锁等待，其真因通常是**设计**（热点行计数、序列模拟表）而非引擎。
- 其他族（DX/DF/DD 等 ⚠️ 名词转述）：字典锁定、直接路径、表空间脱机配合等，本书时代点到为止。
- 读表口诀（⚠️）：`v$lock` 一行 = 一个（会话×锁资源）持有或请求；`LMODE>0` 是持有、`REQUEST>0` 是排队；`BLOCK=1` 意味着"我这个持有正挡着别人"。
- 模式速写（⚠️ 记忆锚）：SELECT 不加锁（靠读一致性）、INSERT/UPDATE/DELETE=表 RX+行 TX、`LOCK TABLE ... IN SHARE MODE`=S、`EXCLUSIVE`=X——四档覆盖 8i 日常全部锁语义。

## 4.3 死锁与阻塞（8i 现实）

⚠️ 转述：

- **阻塞（blocking）**：A 等 B 的锁——不是错误，是排队；`v$lock` 的 `BLOCK=1` 列标出堵路者。
- **死锁（deadlock）**：环状等待。Oracle 选择**检测并报错牺牲一方**（ORA-00060 + 跟踪文件含环详情与"最近 SQL"），而非全量预防或让超时先占——与 SQL Server 的锁优先级/超时、PostgreSQL 的等待环检测属同一问题的不同工程答案（⚠️ 对照转述，未逐一验证对方文档）。
- 8i 的痛：没有 ASH ⇒ 抓"谁堵谁"只能轮询 `v$session` 或手工联查 `v$lock` 的 ID1/ID2——[06-内部视图观测与调优.md](06-内部视图观测与调优.md) 重构这套手艺；现代版本 `v$session.blocking_session_final`/`DBA_BLOCKERS` 已把它产品化（⚠️ 后视）。
- 死锁的第一处方永远是应用：**统一资源获取顺序**（先表 A 后表 B 的纪律），而不是调引擎。

## 4.4 🔧 类比实测（非 Oracle）：SQLite 的三种"锁面"对照锁服务

**G4 共享缓存的表级读写锁矩阵**🔧（✅ 代理实抓文档 [https://sqlite.org/sharedcache.html](https://sqlite.org/sharedcache.html)，官方注明该模式已不推荐——类比样本恰证其局限）：

```python
# 两个连接共享缓存：file:test.db?cache=shared
A: BEGIN; INSERT INTO t VALUES (1)   # 未提交
B: UPDATE t SET x=2  -> OperationalError: 'database table is locked'
B: SELECT count(*) FROM t -> OperationalError: 'database table is locked: t'
```

- 读法：SQLite 共享缓存的锁是**表粒度**，且**读也被未提交写挡住**——直接报错、不入队、不等待。对照 Oracle：行粒度 TX 锁 + 排队语义 + 读者绝不等待。**三点差异恰好是 enqueue 服务的三项价值**：粒度细（并发高）、能排队（公平）、读者走 undo 快照（不被写者阻塞）。（⚠️ 类比；实测为本机 sqlite 3.45.3，脚本 `D:\develops\tmp\dbwave_w7_oraint\exp_sqlite.py`。）

**G5 WAL 模式下的读写并存**🔧：写事务开着不提交，读者照样看到旧值：

```
journal_mode=wal; 写者 BEGIN IMMEDIATE+INSERT（未提交），WAL=12 KiB
读者 SELECT → 1 行（旧快照）；写者 COMMIT 后 → 2 行
```

- 读法：SQLite 用 WAL 文件版本化实现"读者读前镜像"——Oracle 用 undo 段实现同一语义，且不需要文件级版本共存（⚠️ 机制差异转述）。**"读者从不被写者阻塞"在两引擎里分别是 WAL 帧版本链与块级一致性读的结果**——00 定位表所说"锁服务与读一致性是一对孪生"的实证版。
- 复跑要点：读者与写者分连接；SQLite 默认回滚日志模式下读者会被写者挡（journal 存在即挡读写），**只有 WAL 才复现 G5**——这本身说明"读一致性是需要架构投资的"。

## 4.5 锁调优的世界观（重构）

⚠️ 转述通行原则（机制在本书、方法在姊妹册）：

1. **短事务是锁服务的免费午餐**：TX 锁随 COMMIT 释放——持锁时间≈事务长度；隔离级别与语句级一致性的现代口径见 [../Troubleshooting_Oracle_Performance_2e/02-关键概念.md](../Troubleshooting_Oracle_Performance_2e/02-关键概念.md)（✅ 在盘姊妹章文件）。
2. **热点行是设计缺陷**：计数表/模拟序列 ⇒ 哈希分片或去计数化；锁等待的处方几乎总在应用侧。
3. **不要拿闩锁的药治锁的病**：latch free 调并发结构（[03-闩锁服务.md](03-闩锁服务.md)），enqueue 调事务边界——02/03/04 三章的"事件→服务→处方"对照在 [06-内部视图观测与调优.md](06-内部视图观测与调优.md) 汇总。
4. **DDL 是重锁客户**：`Share/Exclusive` 级申请撞上长事务 ⇒ 大表维护窗口被一行未提交拖死（⚠️ 转述；`SKIP LOCKED`/`NOWAIT` 是后 10 年的解法 ⚠️）。
5. **与安全的邻接线**：权限模型决定谁能申请对象锁，锁语义与授权语义正交——与波内兄弟 [#61 Oracle_Security](../Oracle_Security/00-总览与阅读地图.md)（✅ 已落盘；00 §2 ISBN 辨析对手册）的分界：那册讲"谁能锁"，本册讲"锁怎么运行"。

## 4.6 自查问题

1. 两个并发 UPDATE 同一表不同行，各自申请什么模式？为何不互相等待？（RX 兼容；TX 行不同）
2. `v$lock` 里 BLOCK=1 的一行说明什么角色？（持有者正挡人，堵路者）
3. 🔧 G4 里读者为何也被挡，而 Oracle 读者不会？（表粒度+无 undo 快照路径）
4. 死锁报错后，Oracle 让谁承担损失、依据是什么？（回滚牺牲方的当前语句 ⚠️，非整个事务的通行误解）

自查答题要点（⚠️ 口径）：

1. 各申请 RX（TM 兼容）+ 不同行的 TX——行不同则资源不同，不冲突；
2. "我这个持有者正在挡人"——排队者身份看 REQUEST，堵路身份看 BLOCK；
3. 共享缓存表粒度且无快照路径，读者只能撞锁（🔧 G4 实测原文）；
4. 牺牲的是**当前语句**的回滚（默认行为），整句重做由应用决定——ORA-00060 跟踪文件给环与双方 SQL（⚠️）。

## 核心概念速览（中英对照）

- **入队锁** — Enqueue：按模式兼容性排队的对象级锁申请，锁服务的机制本体。
- **锁模式矩阵** — Lock Mode Compatibility Matrix：NL/RS/RX/S/SRX/X 之间的相容表。
- **TM 锁** — Table Lock (TM)：DML 自动申请的 RX 表锁，防并发 DDL，不锁内容。
- **TX 锁** — Transaction Lock (TX)：行级归属锁，首个改写者的事务持有。
- **行锁争用** — Row Lock Contention：多会话争同一行的 TX 锁排队（`enq: TX` 类等待）。
- **阻塞者** — Blocking Session：持锁致他人排队的会话（v$lock BLOCK 列）。
- **死锁** — Deadlock：环状等待；Oracle 检测后牺牲一方（ORA-00060，⚠️ 转述）。
- **表粒度锁** — Table-Level Lock（🔧 G4）：SQLite 共享缓存的粗粒度形态，读写同挡。
- **快照读** — Snapshot Read（🔧 G5）：读者不等待写者、读旧版本的语义（WAL/undo 各自达成）。
- **ITL** — Interested Transaction List：块内事务槽，行锁的驻地点（⚠️ 转述）。
- **锁与闩锁分界** — Lock vs Latch：语义序列化 vs 机制互斥，持有量级与排队形态全不同。
- **NOWAIT/SKIP LOCKED** — Non-blocking Lock Requests：跳过等待的访问形态（11g/12c 后语汇 ⚠️）。
