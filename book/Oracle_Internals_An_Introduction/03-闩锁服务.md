# 03 · 闩锁服务（Latches：SGA 的轻量串行化）

> ⚠️ 主题重构口径（原书 TOC 不可达，[00-总览与阅读地图.md](00-总览与阅读地图.md) §3）；精读重构，非原书文本。Oracle 不可本机实测，全部 Oracle 行为为 ⚠️ 转述；🔧 块为**非 Oracle、非本书内容**的 SQLite 类比实测。副题第二元素 "Latches"（✅ 书名自题）。

## 3.0 本章导读

闩锁是本书辨识度最高的主题：它是"数据库内核自己的锁"——不为业务服务，只为共享内存结构的改写瞬间服务。本章依次给：定义与分界（3.1）、两段式获取算法（3.2）、8i 著名闩锁族（3.3）、本机类比实测（3.4）、以及争用读法（3.5）。

## 3.1 闩锁是什么、保护什么

⚠️ 转述（机制通识）：

- **Latch（闩锁）**＝保护 SGA 内一段**易变共享结构**（自由块链表、LRU 链、哈希桶链、共享池堆区）的**轻量互斥原语**。与锁（[04-锁服务.md](04-锁服务.md)）的区别速记：

| 维度 | Latch 闩锁 | Lock 锁（enqueue） |
|---|---|---|
| 保护对象 | 内存结构（链表/哈希桶） | 数据库对象语义（行/表/事务进度） |
| 持有者 | 一个会话进程，**获取后可能 sleeping**（后成风险话题 ⚠️） | 显式持有、有队列入队语义 |
| 请求方式 | 自旋→挂起的两段式，极短持有 | 排队等模式转换，可长期持有 |
| 失败形态 | 拿不到 ⇒ 记 `latch free` 等待或立即放弃 | 拿不到 ⇒ enqueue 等待，死锁有检测 |
| 用户语义 | 不可申请/释放，内核自动管理 | DDL/DML 隐式 + LOCK TABLE 显式 |

- **获取即争用面**：8i 时代闩锁无子闩锁（children 9i 才引入，⚠️），一个 `cache buffers chains` 闩锁护着成段哈希桶——热点块 = 热点闩锁，这是 8i 高并发 OLTP 的头号结构性瓶颈（⚠️ 转述，社区共识）。
- 数量级感受（⚠️ 转述）：一次闩锁获取在"无人争用"时约微秒级；一旦进入 sleep 路径则毫秒到秒级——**同一原语的两条路径相差三个数量级**，这就是"闩锁要防挂起"的算术理由。

## 3.2 两段式获取：spin 然后 sleep（本册心脏）

⚠️ 转述获取算法骨架：

```
try get(nowait):
    原子测试并置位闩锁字；成功 → 记录 get
for i in 1..spin_count:            # 阶段一：自旋
    CPU 重试；每次不成则退避（sched_yield/短睡）
if 拿到: 记 miss-then-hit          # 阶段二：入等待
    否则 → 挂入等待者链，置睡眠，记一次 sleep
被持有者唤醒 → 重试；超时(time-out) → 再自旋若干轮后继续等
```

- 计数语义（`v$latch` 列，⚠️ 至今文档化 ✅ URL 文末）：`GETS` 总获取、`MISSES` 首试不成、`SLEEPS` 进入挂起的次数。**gets 高不是病，misses/gets 与 sleeps/misses 的比值才是**——前者衡量自旋救回率，后者衡量真正让出 CPU 的代价。
- `spin_count` 参数的哲学：自旋用 CPU 换延迟，挂起用上下文切换换 CPU——闩锁调优的万年公式是"让自旋恰好接住争用的短尾"。8i 调 spin_count 是危险手工活（⚠️），现代版本由内核算法自适应（⚠️ 后视）。
- 等待面：会话停在 `latch free`（或细分具名 `latch: shared pool` 等）事件上，p1/p2 给闩锁地址/编号——回链 [02-等待服务.md](02-等待服务.md) 的"参数才能定位"。
- 立即闩锁（immediate latches，⚠️ 转述）：redo allocation 类"绝不排队"的闩锁用 `IMMEDIATE_GETS/IMMEDIATE_MISSES` 单独记账，拿不到就走——04 章"no-wait"世界的机制版。

## 3.3 8i 著名闩锁族（重构清单，⚠️ 转述）

| 闩锁 | 护着什么 | 典型风暴场景 |
|---|---|---|
| shared pool | 空闲内存/库缓存堆分配 | 非共享 SQL 泛滥、硬解析风暴 |
| library cache | 游标句柄链 | 海量一次性 SQL（OLTP 反模式） |
| cache buffers chains | 缓冲哈希桶链 | 热点索引叶块/索引根块 |
| cache buffers lru chain | LRU 链 | 高并发块老化/摘除（后由子链+touch counter 缓解 ⚠️） |
| redo allocation | 日志缓冲区分配游标 | 提交风暴、log buffer 过小 |
| redo copy / posting | 写进程唤醒链表 | 大批量修改的落盘排队 |
| messages/write queue | LGWR/DBWR 唤醒队列 | 后台进程响应慢 |

- 与解析的因果：shared pool/library cache 闩锁风暴几乎总是**硬解析率**问题——机制在 [05-内存与共享池.md](05-内存与共享池.md)（内存服务），症状在 [02-等待服务.md](02-等待服务.md)（等待），处方在 [../Troubleshooting_Oracle_Performance_2e/12-解析.md](../Troubleshooting_Oracle_Performance_2e/12-解析.md)（✅ 在盘姊妹章文件）。
- CBOF 侧写：优化器线不碰闩锁，但 [../Cost_Based_Oracle_Fundamentals/14-10053跟踪文件.md](../Cost_Based_Oracle_Fundamentals/14-10053跟踪文件.md)（✅ 在盘姊妹章文件）揭示：每次硬解析要在优化器里做大量"读共享结构"的动作——那是闩锁持有期的主要租户之一（⚠️ 类比推断，两册口径互补）。

## 3.4 🔧 类比实测（非 Oracle）

**G2b 复用——自旋/挂起的形态学**：`busy_timeout=5000` 的写请求在被持锁 150 ms 的对手面前**阻塞 167 ms 后成功**（[02-等待服务.md](02-等待服务.md) 实测）：这是"miss → sleep → wake → get"的单次样本；`busy_timeout=0` 的 22.0 ms 快速失败则是"try get 不成即弃"。⚠️ 注意：SQLite 的等待发生在**文件锁层**（无用户态 spin 可见段），比 Oracle 两段式少了自旋段——类比只到"等待/放弃二象"为止。

**G3 临界区与"可跳过的后台合并"——checkpoint 实测**🔧（脚本 `D:\develops\tmp\dbwave_w7_oraint\exp_sqlite.py`）：

```
写入 3000 行（WAL=1351 KiB）后：
PRAGMA wal_checkpoint(PASSIVE)  → (0, 336, 336)，WAL 文件 1351 KiB 不变
PRAGMA wal_checkpoint(TRUNCATE) → (0, 0, 0)，WAL 归 0 KiB
```

- 读法：PASSIVE＝"有空才做、被人占着就少做"——返回三元组 (busy, log, checkpointed) 首位是**忙标志**：0 表示本轮没被挡；这正是闩锁"try get 不成就走"精神的化身。TRUNCATE＝强行推进直到日志回绕（对应 Oracle "DBWR 写完脏块 ⇒ 日志复用点前移"的语义，⚠️ 类比）。
- 官方文档口径（✅ 代理实抓 [https://sqlite.org/wal.html](https://sqlite.org/wal.html)）：WAL 检查点把前缀帧复制回库文件并重置 WAL——**读者快照会限制可复制前缀**（G3b 实测见 [06-内部视图观测与调优.md](06-内部视图观测与调优.md)：持快照读者时 PASSIVE (0,170,0)，WAL 684 KiB 原封不动）。

## 3.5 争用读法与处方边界

⚠️ 转述的通行读法（本书时代）：

1. `v$latch` 差分：`misses/gets` 与 `sleeps/misses` 双比值定位"在争的闩锁"。
2. 具名事件细分（后期版本）：`latch: xxx` 直接指名——8i 多为 `latch free`，需回 `v$latch.name` 查号（⚠️）。
3. 处方分层：热点块 → 分散访问（reverse key 索引/序列 cache/集群因子话题归优化器线 [../Cost_Based_Oracle_Fundamentals/05-聚簇因子.md](../Cost_Based_Oracle_Fundamentals/05-聚簇因子.md) ✅ 在盘姊妹章文件）；解析风暴 → 共享游标；提交风暴 → 事务合并（⚠️ 转述，现代多不再手调 spin_count）。
4. 何时别看闩锁：CPU 空闲、等待以 enqueue/I/O 为主时——那是 [04-锁服务.md](04-锁服务.md)/存储层的事。
5. 度量陷阱：`v$latch` 计数器跨重启清零、快照法必须成对记录时间基线（⚠️ 转述，06 章纪律 2 的前置）。

## 核心概念速览（中英对照）

- **闩锁** — Latch：SGA 内易变结构的轻量互斥原语。
- **自旋** — Spin：拿不到时在 CPU 上重试等待，赌持有者瞬间释放。
- **挂起等待** — Sleep on Waiters：自旋未果后让出 CPU、入等待链被唤醒的形态。
- **spin_count** — Spin Count：自旋重试上限参数，CPU 与延迟互换的旋钮（⚠️ 8i 手工调）。
- **GETS/MISSES/SLEEPS** — Latch Statistics：获取总数/首试不成数/进入睡眠数，v$latch 三柱主账。
- **立即闩锁** — Immediate Latch：绝不排队、拿不到即走的闩锁族，IMMEDIATE_* 单独记账（⚠️ 转述）。
- **子闩锁** — Child Latches：9i 起把热点父闩锁分片为多子闩锁以降争用（⚠️ 后视演进）。
- **cache buffers chains** — Buffer Hash Latch：护缓冲哈希桶的闩锁，热点块风暴源（⚠️ 转述）。
- **shared pool 闩锁** — Shared Pool Latch：护库缓存堆分配的闩锁，硬解析风暴的靶面（⚠️ 转述）。
- **no-wait 获取** — Immediate Get：不成就立即放弃的获取模式（🔧 G2a 类比）。
- **忙标志** — Busy Flag（🔧 G3 返回组首位）：临界区被占、本轮只做了部分工作。
- **日志复用点** — Redo Reuse Point：checkpoint 推进后可覆盖重写 redo 的位置（⚠️ 转述；SQLite WAL 截断类比）。
- **持有期租户** — Hold-time Tenant：闩锁被占用期间在做的具体工作（解析/拷贝/链扫），处方按租户开。
