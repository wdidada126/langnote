# 02 · 等待服务（Waits：等待接口与事件模型）

> ⚠️ 主题重构口径（原书 TOC 不可达，[00-总览与阅读地图.md](00-总览与阅读地图.md) §3）；本章为精读重构，非原书文本。Oracle 不可本机实测，全部 Oracle 行为为 ⚠️ 转述；🔧 块为**非 Oracle、非本书内容**的 SQLite 类比实测。对应副题第一元素 "Waits"（✅ 书名自题）。

## 2.0 本章导读

等待服务是四服务中最"面向用户"的一个：它不解决问题，它**把问题说成话**。本章先给等待接口的定义与微观过程（2.1–2.2），再给 8i 的事件族速记（2.3），然后用本机 SQLite 把"等待的两种命运"测给你看（2.4），最后收在"从等待读到处方"的三步法（2.5）。

## 2.1 等待接口：把"不跑"变成数据

⚠️ 转述（机制通识，与现行文档口径一致）：

- 会话的时间只有两种形态：**在 CPU 上执行**，或**在等待某件事**。等待接口（Wait Interface，7.3 引入、8.0/8i 成型为核心诊断面）把后者以**具名事件**记录：一次等待 = 事件名 + 3 个参数（p1/p2/p3）+ 时长 + 状态。
- 8i 的观测面：`v$session_wait`（每会话**当前/最近一次**等待，瞬时视图）；配合 `v$session`、`v$system_event`（实例累计）、`v$event_name`（事件目录，⚠️ 8i 后期具备）。
- 事件分类的世界观：**空闲（idle）等待不消耗 DB Time**——SQL*Net message from client、rdbms ipc message 这类"等活儿上门"要从总时长里剔除；非空闲等待之和≈数据库时间，这是后来时间模型方法论的公理（→ [../Troubleshooting_Oracle_Performance_2e/00-总览与阅读地图.md](../Troubleshooting_Oracle_Performance_2e/00-总览与阅读地图.md)，其 [../Troubleshooting_Oracle_Performance_2e/02-关键概念.md](../Troubleshooting_Oracle_Performance_2e/02-关键概念.md) 把这条公理仪器化了）。

## 2.2 一次等待的微观过程

⚠️ 转述（机制模型）：进程要做的事无法立即完成（要读盘、要闩锁、要另一进程的服务、要客户端回包）⇒ 在内核里：

1. 记录入等待（事件号 + p1/p2/p3，语义由事件定义：文件号/块号、闩锁地址、对象 id…）；
2. **注册**到该资源的等待链（若资源支持等待队列）；
3. 挂起（OS 级 sleep/poll），被唤醒后累计实际等待时长；
4. 结束记录：超时（time-out 后再试）或拿到资源继续；`STATE` 列留下 WAITED LONG/SHORT 的足迹。

三个要点：
- **同一事件名可来自完全不同的栈**（如 `buffer busy waits` 在 8i 指缓冲块正处于读入/修改态）——必须看 p1/p2/p3 才能定位到文件/块/原因。
- **瞬时视图会骗人**：轮询 `v$session_wait` 的采样间隔决定你能不能抓到短等待——8i 没有 ASH，短而频繁的争用只体现在 `v$latch`/`v$sysstat` 的累计增量里（方法论 → [06-内部视图观测与调优.md](06-内部视图观测与调优.md)）。
- **等待 ≠ 病**：等待是症状清单不是病因；闩锁等待的病因在并发访问模式（[03-闩锁服务.md](03-闩锁服务.md)），锁等待的病因在事务设计（[04-锁服务.md](04-锁服务.md)）。

## 2.4 🔧 类比实测 G2：等待的两种命运——即时失败 vs 挂起-唤醒（非 Oracle）

SQLite 的锁冲突处理是等待接口最干净的显微镜：同一操作，只改 `busy_timeout`，观察到的"等待行为"完全不同。🔧 实测（Python 3.13.2 / sqlite 3.45.3，Windows AMD64；脚本 `D:\develops\tmp\dbwave_w7_oraint\exp_sqlite.py`，读数存 `exp_results.txt`）：

- **G2a 不自旋不挂起**：连接 A 持 `BEGIN EXCLUSIVE`，连接 B `busy_timeout=0` 立刻写 → **22.0 ms 内抛 `database is locked`**（含调用开销，无等待）。→ 类比 Oracle 的"立即放弃获取"（no-wait 语义）：把等待成本转成错误处理成本。
- **G2b 引擎内部挂起-唤醒**：A 持锁 150 ms 后提交，B `busy_timeout=5000` → 语句**阻塞 167 ms 后成功**，无任何用户态重试代码。→ 这就是等待接口记录的形态：调用方"注册→睡→被唤醒→继续"，耗时 ≈ 持有时长 + 唤醒延迟。
- **官方语义对照**（✅ 代理实抓 [https://sqlite.org/c3ref/busy_timeout.html](https://sqlite.org/c3ref/busy_timeout.html)）：busy_timeout 的缺省处理器**累计休眠指定毫秒**，不足则继续等，到限返回 SQLITE_BUSY——"超时是累计的休眠预算"与 Oracle 闩锁的 spin→sleep 时间预算同构（⚠️ 类比）。
- 复跑要点：持有方与等待方必须**分连接**且持有方先确认已拿锁（实验用 Event 同步），否则测出的是竞态噪声而非等待形态；读数存 `exp_results.txt`（busy 22.0 ms / 167 ms 两组）。
- 边界诚实声明：SQLite 冲突返回错误码、由接口层决定等不等；Oracle 的等待是内核内建且有事件记账——**形态类比，不是实现等同**。
- 观测面差（⚠️）：Oracle 每次等待留下 EVENT+P1..P3+TIMED 的记账行，SQLite 只给你"最终成没成"；本目录用 167−150≈17 ms 的唤醒延迟差**示意**记账存在，不据此推算任何 Oracle 时长。

## 2.5 从等待到调优的读法（重构方法论雏形）

⚠️ 转述（通行方法，三步）：

1. **会话维度**：连续采样 `v$session_wait`，把非空闲等待聚成直方图——"这 5 分钟它主要在等什么"；单次采样只能证明"这一瞬"。
2. **实例维度**：`v$system_event` 两次快照差分 ÷ 间隔 = 每秒事件率；对照 `v$sysstat` 的 CPU time——等待占大头则调并发/内存（→ [05-内存与共享池.md](05-内存与共享池.md)），CPU 占大头则是执行效率（→ [../Cost_Based_Oracle_Fundamentals/00-总览与阅读地图.md](../Cost_Based_Oracle_Fundamentals/00-总览与阅读地图.md)：优化器决定的行路径才是 CPU 账本）。
3. **语义维度**：p1/p2/p3 解读表——同一事件在不同参数下处方完全不同（buffer busy waits 指向"装配中"vs"当前态"，闩锁地址不同指向不同闩锁）。
4. **频次×时长二维**：`平均等待时长 = 总时长/次数` 高 ⇒ 单次慢（I/O 层）；次数高均值低 ⇒ 微争用风暴（闩锁层）——两维分开看是 8i 手工时代的"土版 ASH"。
5. **等待链思维**：一个会话的等待常常指向另一个会话的行为（提交/未提交/解析风暴）——等待表读的是"关系"不是"孤立数字"（→ [06-内部视图观测与调优.md](06-内部视图观测与调优.md) 联查图）。

## 2.6 自查问题（读完应能回答）

1. 为什么 `SQL*Net message from client` 的 3 小时不说明系统有问题？（空闲剔除原则）
2. `latch free` 与 `latch: shared pool` 的观测含义差在哪？（具名化程度；机制见 [03-闩锁服务.md](03-闩锁服务.md)）
3. 🔧 实验中 167 ms 与 22.0 ms 分别对应等待世界的哪种命运？（挂起-唤醒 vs 即败）
4. 8i 抓不到 1 ms 的短等待，该用哪个数据面兜底？（累计增量差分——见 [06-内部视图观测与调优.md](06-内部视图观测与调优.md)）

自查答题要点（⚠️ 口径）：

1. 空闲事件原则——客户端思考时间不是数据库的账；
2. 具名闩锁直接给病根，`latch free` 还需查号回 `v$latch.name`（03 章 3.5）；
3. 167 ms＝注册-挂起-唤醒闭环（G2b），22.0 ms＝即败转错误（G2a）；
4. `v$system_event`/`v$latch` 的两次快照差分是短等待的唯一存证。

## 2.7 本章要点回看

- 等待接口把"会话为什么不在 CPU 上"变成具名、带参、带时长的一等数据（✅ 书名自题主题）。
- 空闲/非空闲的切分是 DB Time 世界观的起点，现代时间模型（Antognini）是它的直系后代。
- 瞬时视图 + 采样 = 8i 的全部；理解这一点，才理解 ASH 为何是革命。
- 🔧 证据：同一写冲突，busy_timeout=0 ⇒ 22.0 ms 报错；busy_timeout=5000 ⇒ 167 ms 后成功——等待的两种命运可在本机复现（非 Oracle）。

## 核心概念速览（中英对照）

- **等待接口** — Wait Interface：以具名事件记录会话非 CPU 时间的内核机制。
- **等待事件** — Wait Event：一次非 CPU 停留的命名，如 db file sequential read。
- **p1/p2/p3** — Wait Parameters：事件的三个参数槽，语义随事件而定义。
- **空闲等待** — Idle Wait：不计入 DB Time 的"等活上门"类事件。
- **DB Time** — Database Time：非空闲等待 + CPU 时间之和，时间模型的核心量（⚠️ 后视口径转述）。
- **瞬时视图** — Point-in-Time View（v$session_wait）：只显示当前/最近一次等待，需采样成时间线。
- **挂起-唤醒** — Sleep/Wake：等待者注册到资源队列后被挂起、被释放者唤醒（🔧 G2b 形态）。
- **超时预算** — Timeout Budget：busy_timeout/闩锁等待上限，累计休眠式的等待成本封顶。
- **no-wait 语义** — Immediate Failure：拿不到即报错、不进入等待（🔧 G2a）。
- **事件率差分** — Delta Rate：两次 v$system_event 快照差分求每秒率，8i 的"伪采样"。
- **STATE 列** — Wait State：WAITING/WAITED SHORT TIME/WAITED LONG TIME 的足迹语义（⚠️ 转述）。
- **症状非病因** — Symptom vs Cause：等待是症状；闩锁/锁/内存的设计才是病因。
