# 05 · 内存服务（SGA、缓冲池与共享池内部）

> ⚠️ 主题重构口径（原书 TOC 不可达，[00-总览与阅读地图.md](00-总览与阅读地图.md) §3）；精读重构，非原书文本。Oracle 不可本机实测，全部 Oracle 行为为 ⚠️ 转述；🔧 块为**非 Oracle、非本书内容**的 SQLite 类比实测。副题第四元素 "Memory"（✅ 书名自题）。

## 5.0 本章导读

内存服务是三件事的交汇：块住在哪（缓冲池）、SQL 的解析产物住在哪（共享池）、它们被改被读时归谁管（闩锁与 pin）。本章先给 SGA 服务地图（5.1），再进缓冲池状态机（5.2）与库缓存句柄/锁/pin 三级生命（5.3），然后用两组本机实验把"页缓存收益的边界"和"日志持久性的代价"测出来（5.4）。

## 5.1 SGA 的服务地图（8i 口径，⚠️ 转述）

SGA（System Global Area）＝实例启动时按参数圈出的共享内存（8i 手工配比时代：`db_block_buffers`×块大小、`shared_pool_size` 一锤定音，`db_cache_size` 自动段尚在雏形 ⚠️）。四大服务在此驻留：

| 区 | 结构 | 受谁保护（回链 [03-闩锁服务.md](03-闩锁服务.md)） |
|---|---|---|
| 数据库缓冲池 | 块副本哈希表 + LRU 链 + 脏链 | cache buffers chains / lru chain 闩锁 |
| 共享池 | 库缓存（句柄/游标/pin）+ 数据字典缓存 | shared pool / library cache 闩锁 |
| 重做日志缓冲 | 循环写日志字节区（KGGLCR? 结构名 ⚠️ 不展开） | redo allocation / copy 闩锁 |
| 其他 | 锁/闩锁定义数组、大池（8i 起）、Java 池等 | 各自 |

- 读法：**每次 I/O 与解析都走"闩锁→结构→释放"的小事务**——缓冲读的"latch→hash→find→pin→unlock→copy out"路径就是本册全部机制的合奏面（⚠️ 转述模型）。
- 与入门册的关系：波内 [#44 Oracle_Essentials_5e](../Oracle_Essentials_5e/00-总览与阅读地图.md)（✅ 已落盘）讲"SGA 有哪几块"，本册讲"每块内部怎么动"——同一张地图的缩放级差。
- 后台进程一句话分工（⚠️ 转述够用口径）：DBWR 管脏块落盘（5.2 脏链的搬运工）、LGWR 管日志先到（5.4 G7 的对应物）、服务器进程是这些结构的闩锁客户——本册不发进程详解，只标它们的接口点。
- 度量提醒：8i 时代靠 `v$sysstat` 的"consistent gets/logical reads"估命中率，本目录 05 章 G6 的负结果正是对"命中率=性能"口号的当代警示（⚠️ 类比校准，非 Oracle 结论）。

## 5.2 缓冲池内部：块的状态机与 LRU

⚠️ 转述：

- 块副本驻留态：free（可重用）→ read（正从盘装配，他人读会同撞 `buffer busy waits`）→ dirty（已改未落盘，挂脏链等 DBWR）→ 回 free；当前会话正在改的称 current。
- **LRU**（半随机/touch counter 是 9i 的改进，8i 为朴素 LRU ⚠️）：全表扫描会沿 LRU 把热块挤出——8i 时代对策是 keep/recycle 池与直接路径读（⚠️ 转述），Steve Adams 后来对缓冲争用的公开分析正是从这套结构出发（⚠️ 谱系）。
- 读一致性（backout）：读者撞见"当前块值比自己快照新"⇒ 用 undo 在私有缓冲里**回退**出旧镜像——[04-锁服务.md](04-锁服务.md) "读者不等待"的实现面；pin 计数保护块在此过程中不被老化。
- 脏块与检查点：DBWR 按检查点队列批推脏块、LGWR 保日志先行——`log file sync`（用户侧提交等待）与 `log file parallel write`（LGWR 侧写等待）是同一枚硬币两面（⚠️ 转述，06 章症状表收录）。

## 5.3 共享池与库缓存：句柄、游标与 pin

⚠️ 转述（本书时代的核心难点，也是其"Memory"章的招牌）：

- 一条 SQL 的共享内存生命：**句柄（handle，锁名对象语义）→ 库缓存锁（library cache lock）→ 库缓存 pin（护住可执行体）**——注意：这里的 lock/pin 是**共享池内的命名序列化对象**，借用 [04-锁服务.md](04-锁服务.md) 的词汇却不是 enqueue 服务本体——pin＝"正在使用，禁止淘汰/改写"，句柄与游标各挂计数。
- 硬解析全程：shared pool 闩锁下分配内存、语法/语义/优化（→ [../Cost_Based_Oracle_Fundamentals/00-总览与阅读地图.md](../Cost_Based_Oracle_Fundamentals/00-总览与阅读地图.md)：优化器是租这段持有期的租户）、生成游标、置入库缓存；软解析只走 pin 路径。
- **风暴因果闭环**：非参数化 SQL ⇒ 句柄/pin 数量爆炸 ⇒ shared pool 闩锁争用（[03-闩锁服务.md](03-闩锁服务.md)）+ `latch: shared pool`/`library cache` 等待（[02-等待服务.md](02-等待服务.md)）+ 游标老化/碎片 ⇒ 解析时间失控——TOP2e 的 [../Troubleshooting_Oracle_Performance_2e/12-解析.md](../Troubleshooting_Oracle_Performance_2e/12-解析.md)（✅ 在盘姊妹章文件）给的是现代完整处方，本册给的是它的机制地基。
- 图钉的另一面：pin 住的块/对象不可淘汰——"钉住计数"是内存服务与淘汰策略之间的仲裁人（⚠️ 转述；副题 Memory 的落点）。
- 观测面预告：`v$librarycache` 的 pin-hits/misses、`v$rowcache` 字典命中、`v$sgastat` 的自由空间——三个都是"事后累计"，与 06 章的瞬时联查互补（⚠️）。
- 8i 参数速记（⚠️ 转述，名与语义按社区通行资料）：`db_block_buffers`（缓冲池页数）、`db_block_size`（页大小）、`shared_pool_size`（共享池字节数）、`log_buffer`（日志缓冲字节数）、`db_keep_cache_size`/`db_recycle_cache_size`（8i 新引入的多池 ⚠️）——配比即架构，本册机制章的"地图边界"。

## 5.4 🔧 类比实测 G6/G7（非 Oracle）

**G6 页缓存与 mmap：缓冲池"命中即免系统调用"效应的可测版**🔧（24,064 KiB 库、30,000 行 BLOB 全表扫描；脚本 `D:\develops\tmp\dbwave_w7_oraint\exp_sqlite.py`）：

```
PRAGMA cache_size=-500     （~0.5 MB 内部页缓存）冷扫描   16.2 ms
PRAGMA cache_size=-20000   （~20 MB）                     22.8 ms / 21.1 ms（两次）
PRAGMA mmap_size=268435456 （256 MB 内存映射）后          13.8 ms
```

- **诚实的负结果**：内部页缓存从 0.5 MB 放大到 20 MB **没有变快**（16.2→22.8 ms）——24 MB 的库早被 OS 文件缓存接住，SQLite 内部缓存只剩记账成本；而 mmap 略优（13.8 ms）体现"省一次用户态拷贝"。→ 对照 Oracle：SGA 缓冲池的收益发生在**OS 缓存不可依赖**的多实例/大工作集场景；"命中率提升必更快"在单机小库上是伪命题——本实验正是该警告的机测样本（00 §7 登记的负结果）。
- Oracle 侧的"mmap≈直接映射、省闩锁拷贝路径"对应物（keep 池/直接路径读）一律 ⚠️ 转述，不外推数字。

**G7 日志持久性的两种代价**🔧（300 条单行插入同事务提交的端到端耗时）：

```
journal_mode=DELETE synchronous=FULL(2)  → 2.9 ms
journal_mode=WAL    synchronous=FULL(2)  → 1.0 ms
journal_mode=WAL    synchronous=NORMAL(1)→ 0.6 ms
```

- 读法：回滚日志模式每次提交付"建日志→同步→删除"的 fsync 税；WAL 用追加帧+按需检查点摊薄它——对应 Oracle "redo 恒写、undo 按需"与"LGWR 组提交摊薄 log file sync"的结构（⚠️ 类比转述）；数字仅刻画 SQLite 本机形态，**不构成任何 Oracle 比例**。

## 5.5 自查问题

1. 为什么 8i 全表扫描会"伤"缓冲池，9i 之后用什么机制缓解？（朴素 LRU vs touch counter/半随机 ⚠️）
2. backout 出来的块放哪，为什么它不阻塞写者？（私有缓冲；undo 构造快照）
3. library cache pin 与 latch 的分工一句话？（pin 保内容存活，latch 保改写瞬间）
4. 🔧 G6 的负结果对"调大缓存必提速"的调优口号意味着什么？（工作集小于 OS 缓存时内部收益边际≈0）

自查答题要点（⚠️ 口径）：

1. 朴素 LRU 让一次性扫描污染热点——9i 起 touch counter/半随机插入缓解；
2. backout 在**私有（会话级）缓冲**构造快照，不碰共享块副本，故与写者互不干扰；
3. latch 保"改写那一步"（微秒），pin 保"整个使用期"（语句级/调用级）——粒度与时长两级不同；
4. G6：16.2 ms（0.5 MB）已接近 22.8/21.1 ms（20 MB）——OS 缓存兜底时，引擎缓存只加记账（🔧 实测，非 Oracle）。

## 5.6 本章要点回看

- SGA＝四服务驻留地；每次读块/解析都在闩锁持有期内完成小动作（⚠️ 转述）。
- 缓冲池：块状态机 + LRU + backout 一致性读；共享池：句柄→锁→pin 三级生命，pin 计数仲裁淘汰（⚠️ 转述）。
- 风暴闭环横跨 02/03/05 三章：硬解析是病根，等待与闩锁是症状，pin/句柄是病理。
- 日志侧账本：redo 结构 + LGWR 组提交决定 `log file sync` 形态——它是"提交频率 × 存储延迟"的乘积，不是单纯磁盘问题（⚠️ 转述）。
- 🔧：页缓存放大未必提速（16.2→22.8 ms 负结果如实）、mmap 13.8 ms、DELETE 2.9 ms vs WAL 1.0/0.6 ms——全部标非 Oracle。

## 核心概念速览（中英对照）

- **SGA** — System Global Area：实例共享内存区，四大内部服务的驻留地。
- **缓冲池** — Buffer Cache：块副本哈希表+LRU 链的 SGA 分区（8i 手工配比时代 ⚠️）。
- **buffer busy waits** — Wait Event：撞见正被装配/改写/回退的块副本（⚠️ 转述）。
- **backout/一致性读** — Read Consistency via Undo：读者私有区用 undo 回退出块旧镜像。
- **脏链/检查点队列** — Dirty Queue / Checkpoint Queue：等待 DBWR 落盘的块挂链（⚠️）。
- **共享池** — Shared Pool：库缓存+字典缓存所在 SGA 分区。
- **句柄** — Handle：库缓存条目的锁名句柄对象。
- **pin / 钉住计数** — Pin / Pin Count：使用中对象免淘汰的引用计数与加锁动作。
- **硬解析/软解析** — Hard/Soft Parse：是否重走分配+优化全路径。
- **页缓存** — Page Cache（🔧 G6）：SQLite 内部按 cache_size 计费的页驻留层。
- **内存映射 I/O** — mmap（🔧 G6）：把库文件映射进地址空间省拷贝的读取形态。
- **log file sync** — Commit 等待：用户会话等 LGWR 确认日志落盘的等待事件（⚠️ 转述）。
- **keep/recycle 池** — 多缓冲池形态：8i 起把特定对象的驻留策略显式化（⚠️ 转述）。

- **文档级锚点**（✅ 本机验证，302→200）：等待/闩锁两大视图的 23ai 参考页 [https://docs.oracle.com/en/database/oracle/oracle-database/23/refrn/V-SESSION_WAIT.html](https://docs.oracle.com/en/database/oracle/oracle-database/23/refrn/V-SESSION_WAIT.html)、[https://docs.oracle.com/en/database/oracle/oracle-database/23/refrn/V-LATCH.html](https://docs.oracle.com/en/database/oracle/oracle-database/23/refrn/V-LATCH.html)——库缓存争用仍以二者为主要观测面。

- **工业实践**（⚠️ 转述）：缓冲池旁路需求（大数据扫描不污染缓存）现代由 Exadata Smart Scan/内存数据库形态承接；单机世界的同题答案即本实验的 mmap/OS 缓存分工——"引擎内缓存与 OS 缓存谁主导"，小数据集上永远是后者（G6 实证）。
- **学术对照**：LRU 缺陷（扫描污染）的学界代餐 LRU-K/2Q/Adaptive 置换族见论文线 [../../db/db.md](../../db/db.md)；Hekaton 的"全内存+无闩锁分区索引"是本册两大服务（闩锁+缓冲）的整体颠覆样本（⚠️ 转述）。
