# 13 复制（第 18 章 复制）

> **本章地图**：复制的动机（性能/可用性/容错）与一致性增强的代价 → **组通信**（组成员服务、视图、可靠+有序组播作为复制底座、视图同步组播）→ **容错服务**：被动（主备）复制与主动复制（状态机方法）、两种模型的正确性条件与恢复 → **高可用服务**：gossip 架构（读一写全部 ROWA 的局限）、quorum 共识族（读/写法定人数、加权 quorum、目录式 quorum）、gossip 传播与删除标记 → **事务复制**：主副本事务、用 quorum 共识的事务、gossip 架构中运行事务、2PC 与复制的组合。

## 本章地图

复制把一份数据放在多台机器上，立刻面对「**性能、可用性、容错**」三收益与「**一致性代价**」的交换。本章给出四种坐标：按**组通信**（消息送达与顺序）、按**容错服务模型**（主备 vs 状态机）、按**高可用算法**（gossip/quorum）、按**事务**（复制与并发控制+提交协议的交织）。它是 10-协调与协定.md 共识理论的应用层，也是现代存储系统（Raft 组、CRDT、Kafka ISR）的概念母体。

## 核心精讲

> 以下伪代码、表格均为**教学示意，不参与构建**。

### 组通信与视图

- **组成员服务**维护**视图（view）**：当前被系统认同的成员名单；成员崩溃/加入触发视图变更，交付给应用时保证**视图同步**（virtual synchrony 的核心承诺：所有 correct 成员在同一视图内看到同一组消息）。
- 副本协议建立在组播语义上：被动复制要 FIFO + 全序（对状态更新），主动复制要**全序**（状态机要求所有副本以相同顺序执行相同命令）。
- 🔧 视图变更本身就是一次「成员共识」——组通信与共识互为因果，这是复制系统绕不开的鸡生蛋问题（第 5 版用「故障检测器假设」绕过，现代系统用 Raft 成员变更单日志条目解决）。

### 18.2 容错服务：被动与主动复制

- **被动复制（primary-backup）**：primary 接收请求、执行、把状态更新组播给 backup；primary 崩溃由组内选举接管。
  - 「备份不足够新」的窗口靠**全序 + view-synchronous** 组播收窄；事件「备份状态落后 ≤ 一个消息」是工程常态（同步/半同步/异步复制的连续谱）。
  - **正确性条件**：若 primary 在发出更新前崩溃 → 请求未完成，客户端重试；若已发出 → 备份接管后继续——二者以「更新是否进入全序」为界，不重不漏。
- **主动复制（active/state machine）**：所有副本执行同一命令序列；前提是命令执行**确定性**（无本地时钟、无随机数、无并发读取歧义）。
  - 客户端故障也可以吸收：请求经全序组播后，副本各自执行，崩溃的客户端重发请求被幂等过滤（请求标识符去重）。
- 🔧 两者现代对应：Raft（被动：leader 执行 + 日志复制 + 提交点）与确定性数据库（主动：先定序后执行，Calvin）；Kafka 的 ISR 是「半同步被动复制」的流式版本。

### 18.3 高可用服务与 quorum

- **读一写全部（ROWA）**：读任意副本、写全部副本——读快写慢，且任一副本不可用即写不可用。

  | 方案 | 读副本数 R | 写副本数 W | 特点 |
  | --- | --- | --- | --- |
  | ROWA | 1 | N | 读快；一坏全停写 |
  | 多数派 quorum | ⌈(N+1)/2⌉ | ⌈(N+1)/2⌉ | R+W>N，读写相交 |
  | 加权 quorum | 按 weight | 按 weight | 副本能力不等时用（Gifford） |
  | 目录式 quorum | 1（读目录指向的新副本） | 目录 + 若干 | 读延迟低，目录是热点 |

- **多数派 quorum（Gifford, 1979）**：写 W 个、读 R 个，要求 **R + W > N** 保证读写集相交；最常用 N=3, W=2, R=2。
- **gossip（epidemic）传播**：副本随机交换更新，O(log N) 轮收敛；三种交换方式——push（副本主动推自己新知识）、pull（拉对方新知识）、push-pull（双向合并），pull 在收敛后期反而更高效。
- **删除标记（deletion markers/tombstones）**必不可少，否则「删除」会被旧副本复活；墓碑自身要有 GC 策略（Cassandra 的 gc_grace_seconds 即此）。
- 🔧 quorum 的隐藏成本：读到的可能是**旧版本**，需要版本向量/时间戳判定新鲜度；这直接催生了 Dynamo 的 sloppy quorum + 向量时钟协调（SOSP 2007）。

### 18.4 事务复制

- 主副本事务：全部操作走 primary（多副本数据库的默认选择）。
- quorum 事务：事务对每个数据项按 quorum 读/写，与并发控制正交叠加；两阶段提交与 quorum 组合时，提交本身也要 quorum 决议。
- gossip 架构中运行事务（Ladin et al., 1992）：前端协调器收集读集版本信息，向副本组提交「带版本预期的更新」；分区时允许本地执行、恢复时合并——事务语义只对「读集版本仍有效」的更新成立。
- 🔧 2PC + 复制的组合难题：提交协议本身也要复制（协调者不能单点）——这一难点的现代答案就是把 2PC 的协调者状态放进 Paxos/Raft 组（Spanner/TiDB/CockroachDB 一律如此，见 12-分布式事务.md）。

### 算法走查（教学示意，不参与构建）

**走查 1：反熵（anti-entropy）的三种交换**

```text
每 Δ 时间, 副本 R 随机选一个对端 Q:
  push:   发送「我比你新」的更新摘要 → Q 应用
  pull:   询问 Q「你有什么我没有的」 → R 应用
  push-pull: 双向交换差集
摘要构造: 版本向量 / 哈希默克尔树（范围摘要, Dynamo/Cassandra 用于快速定位差异）
```

- 收敛速度 O(log N)：每轮随机配对使「已知该更新的副本数」期望翻倍。
- 🔧 Merkle 树摘要让「找差异」从 O(数据量) 降到 O(log 数据量)，是现代反熵实现的标配。

**走查 2：被动复制的接管判定**

```text
primary P, backup B, 组播全序 G:
  客户端请求 r → P 执行 → 更新 u(r) 进入全序 G
  B 侧按 G 依次应用更新
  P 崩溃 → 组触发视图变更 → B 成为新 primary
  判定:
    u(r) 已进入 G → B 会应用它 → 对客户端「已完成」
    u(r) 未进入 G → B 没有它 → 客户端重试（幂等性由请求标识符保证）
```

- 「是否进入全序」是唯一的事实分界线——这是半同步复制 acks=all 的教科书形态。

**走查 3：quorum 配置的可用性算术**

- N=5, R=2, W=3：任两 quorum 相交 ≥ 1；写容错 = N − W = 2 个副本可坏，读容错 = R 侧同理；
- 特例 N=3, R=1, W=3（ROWA）：写容错 0；N=3, R=3, W=1（只读副本镜像）：读容错 0；
- 🔧 R、W 都是可调的可用性/一致性旋钮：读多写少把 R 调小（可用性）但必须 W > N − R 保持相交。

### 自测问答（教学自用）

- **Q：主动复制要不要「读也要全序」？** 要。若副本 A 读到命令序 5 的状态、副本 B 执行到序 7 才响应读，同一客户端会看到时间倒流——读也必须走同一全序（或绑定到已完成序号的快照）。
- **Q：quorum 能替代共识吗？** 能解决「单对象读写」的可用副本问题，但跨对象事务、日志复制需要更弱的门限语义时就不够——共识 = quorum + 顺序 + 一致恢复，三件事缺一不可。
- **Q：gossip 为什么用随机对端而不是固定拓扑？** 随机配对让故障与拓扑变化不影响收敛路径（流行病学的「均匀混合」假设）；固定拓扑某关键节点失效即断链。
- **Q：视图同步组播在成员变更瞬间丢消息吗？** 协议保证不丢：旧视图消息要么全部交付后才切视图，要么全部作废——「消息边界即视图边界」，这是 ISIS 对复制最大的贡献。
- **Q：事务复制里「只复制更新还是复制整个事务」？** 现代主流复制**逻辑更新（事务序日志）**而非页/行物理差异：既保持事务原子性，又允许副本独立做并发控制（应用日志）——MySQL binlog/PG logical replication 均如此。

### 工程易错清单

- 同步/半同步/异步不是三档开关，是「备份确认语义」的连续谱：acks 配置改一档，RPO/吞吐全部重估。
- 只读副本的一致性要显式声明（bounded staleness / causal / snapshot）：监控里加「副本延迟分布」而不是只看均值。
- 墓碑 GC 期限必须 > 最长故障修复时间：GC 提前会把「还没同步到的删除」复活。
- 成员变更期间复制协议的多数派定义会变化（新旧配置）：Raft 的 joint consensus / 单步变更就是为此存在，不要自己发明「先切配置再补消息」。
- 副本放置要按**故障域**（机架/可用区）打散：3 副本同机架等于 1 副本。
- gossip 频率与消息大小的乘积是稳态开销：节点数扩大 10 倍要重新调参，不是「天然可扩展到无限」。

## 近年研究与工业界开源实践（2015–2026）

- **Raft 成为复制的事实标准**（ATC 2014）：leader-based 被动复制的可读化；ZAB（ZooKeeper）、Viewstamped Replication 同族。
- **Multi-Raft 分组**：一个集群跑成千上万个 Raft 组，按 region/-range 分数据（TiKV、CockroachDB），把「组通信 + quorum」颗粒度做细以兼顾吞吐与局部故障域。
- **CRDT（Conflict-free Replicated Data Types）**（Shapiro et al., 2011）：gossip 复制 + 可交换合并 = 无协调最终一致；离线优先应用（协同编辑、移动端数据库）的主流选择。
- **工业界开源**（star 数 2026-09 实测）：
  - `etcd-io/etcd`（52310★）：Raft 参考实现；`pingcap/tidb`（40588★）：Multi-Raft + Region 调度；`cockroachdb/cockroach`（32498★）：Raft + 多版本副本。
  - `apache/kafka`（33839★）：ISR（in-sync replicas）+ acks=all 是「半同步被动复制」的流数据版。
  - `apache/cassandra`（10103★）：Dynamo 血统的 quorum + 墓碑 + 提示移交（hinted handoff）。
  - `hashicorp/consul`（30082★）：LAN/WAN 两层 gossip 做成员与健康信息传播——gossip 理论最直接的产品化。
  - `apache/incubator-seata`（26012★）与 `temporalio/temporal`（23295★）：事务复制语义向补偿/工作流的延伸（对照 12-分布式事务.md）。
- **研究侧**：跨区域复制的延迟预算建模、副本一致性「分级」（Strict Serializability vs Snapshot vs Bounded Staleness）的工业定标（Cosmos DB 的 five levels）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「三副本写两副本读一就强一致」 | quorum 只保证读写相交；旧值判定、删除复活、跨项事务仍需版本与协调机制 |
| 2 | 「gossip 最终一致 = 事务安全」 | gossip 路径只适合宽松语义；事务级保证要回到 quorum/共识 + 并发控制 |
| 3 | 「主动复制只要组播全序就行」 | 还要求执行**确定性**；非确定性副作用（时钟/随机数/外部 IO）必须剥离或定序 |
| 4 | 「墓碑可以随手清」 | 墓碑 GC 早于最慢副本追平 → 删除复活；GC 期限由最大故障时长决定 |
| 5 | 🔧 本书未覆盖 | Raft 的日志匹配与提交不变量、Multi-Raft 与 Region 调度、CRDT 形式化、Dynamo 系 sloppy quorum、复制下的隔离级别分级（Homeostasis Protocol） |
| 6 | 「复制数量越多越可靠」 | N 越大写 quorum 成本越高；可靠性的正确标的是故障域独立性（机架/可用区） |
