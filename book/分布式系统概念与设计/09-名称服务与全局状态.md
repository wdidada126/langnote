# 09 名称服务与全局状态（第 13 章 名字服务 + 第 14 章 时间和全局状态）

> **本章地图**：命名的基础（名字、属性、解析）→ 名称服务与名称空间（合并/分区/别名/挂载）→ DNS 案例研究（层次结构、zone、资源记录、迭代/递归解析、缓存与负载分担）→ 目录服务（X.500/LDAP、按属性检索）→ **物理时钟**（偏差与漂移、Cristian 算法、Berkeley 算法、NTP）→ **逻辑时间与时钟**（先于发生关系 happens-before、Lamport 时钟、全序组播）→ **向量时钟** → **全局状态**（一致性割集、Chandy–Lamport 快照算法、分布式调试与死锁检测）。

## 本章地图

第 13 章回答「**名字如何找到对象**」：名称服务把可读名字解析为属性/地址，DNS 是互联网上最成功的名称服务实例。第 14 章回答「**分布式系统里「现在」和「当时全部」是什么**」：物理时钟同步永远有误差，于是用逻辑时钟刻画因果关系；而要观察系统全局，就必须靠快照算法在不停止系统的情况下捕获一个**一致的全局状态**。两章合起来是后续协调（15 章）、复制（18 章）算法的时序与状态地基：没有统一的「顺序」与「状态」概念，共识、事务、副本管理都无从谈起。

## 核心精讲

> 以下伪代码、表格与例子均为**教学示意，不参与构建**。

### 13.x 名称服务的要素

- **名字空间（name space）**：由结点（node）构成的标签图，叶结点持有对象引用或属性，目录结点只持有到其他结点的映射。
- **解析（resolution）**：给定路径名 `/etc/hosts` 或 `www.example.com`，逐级查表。两种协作方式：
  - **迭代导航（iterative navigation）**：客户端逐级向每个名称服务器问「下一个该问谁」（DNS 常用）；
  - **递归导航（recursive navigation）**：服务器代为向下查询，代价是服务器负载与缓存复杂度。
- **别名与多视图**：同一对象多个名字（邮件域 vs 主机域）；**挂载（mounting）**（如 NFS 挂载点）把别的名称空间嫁接进来；**泛播（anycast）**式解析让同一名字解析到就近副本。
- **DNS 关键设计**：
  - 层次域名树 + **zone**（管理授权单元，主/从服务器间 zone transfer）；
  - 资源记录（RR）五元组：

    | 字段 | 含义 | 例子 |
    | --- | --- | --- |
    | Domain Name | 被解析的名字 | `www.example.com` |
    | TTL | 缓存有效期 | `86400` |
    | Class | 协议族 | `IN` |
    | Type | 记录类型 | A / NS / CNAME / SOA / MX |
    | Value | 记录值 | `93.184.216.34` |

  - **缓存 + TTL**：解析器缓存答案，TTL 是一致性与负载的旋钮；
  - 负载分担：同一域名配多个 A 记录，DNS 轮询即最早的「服务发现 + 负载均衡」。
- **名字解析的安全面**：缓存投毒（Kaminsky 攻击）与 DNSSEC 的响应签名——名字「指错对象」等价于安全被攻破，这是命名与安全的交界。
- **目录服务**：不止按名字查，还能按**属性**查（X.500 / LDAP 的 `(&(objectClass=person)(mail=*@x.org))` 式检索）。🔧 现代 Kubernetes 的 Service/DNS（`svc.namespace.cluster.local`）、Consul 的服务目录，都是「名称服务 + 属性检索」的直系后代。

### 14.1 物理时钟同步

- 时钟偏差（skew）与漂移率（drift）：石英钟有 ppm 级漂移，节点间若长期不对准，事件排序会失真，必须定期校准。
- **Cristian 算法（1989）**：向时间服务器发请求，用往返时间 RTT 估计误差界，`T = T_server + RTT/2`，可容忍 ±RTT/2 内的不确定度。
- **Berkeley 算法**：master 轮询所有机器取平均，主动「拉平」而不是对准外部时间（内一致性而非外一致性）；对慢钟放宽拉快、对快钟缓拉慢。
- **NTP**：分层 stratum 结构，三种同步模式：

  | 模式 | 适用 | 特点 |
  | --- | --- | --- |
  | 组播 | 局域网 | 精度最低、开销最小 |
  | 客户端/服务器（过程调用式） | 常规同步 | 多次采样统计滤波 |
  | 对称（peer 对等） | 服务器互备 | 双向交换，精度最高 |

- 🔧 数据库场景的教训：时间不可信是分布式事务的大敌——Google 的解法不是「同步得更好」而是「给时间配上**误差界**」（见 TrueTime）。

### 14.2 逻辑时钟与因果

- **先于发生关系（happens-before, →）**：同进程内程序序 + 消息发送先于接收，是跨进程因果的传递闭包。并发（a∥b）= 互不因果。
- **Lamport 时钟（1978）**：每进程计数器，发消息时 +1 并携带，收到时 `C = max(C, C_msg) + 1`。它保证：a → b 则 C(a) < C(b)；但**反向不成立**（时钟值小不代表因果在前）。
- **全序组播**：Lamport 时钟 + 进程 ID 决胜，保证所有进程以相同顺序看到同一组消息——副本状态机（replicated state machine）的地基。
- **向量时钟**：每进程维护 `[c1..cN]`，收到消息做逐分量 max 后自增分量。可判**双向因果**：`V(a) < V(b)` 当且仅当 a → b；不可比 ⇔ 并发。

  例子（三进程 P1..P3，教学示意）：P1 发 m1（V=[1,0,0]），P2 收后自增（V=[1,1,0]）再发 m2；若 P3 只见过 m2 未见过 m1，其时钟无法小于 m2 的向量——「谁没见过谁」一目了然。🔧 代价是 O(N) 消息头——这正是 Dynamo/Cassandra 用「部分向量 + 客户端协调」的折衷来源。

### 14.3 全局状态与快照

- 为什么难：没有同步的全局时钟，也做不到「同一瞬间」停机拍快照。
- **一致性割集（consistent cut）**：割集若包含一条消息的接收事件却不包含其发送事件，即为**不一致**（会出现「凭空消失的消息」）。
- **Chandy–Lamport 快照算法（1985）**：前提是 **FIFO 信道**。发起者记录自己状态并向所有出边发 **marker**；某进程首次收到 marker 时记录自身状态并停止入边记录、对所有出边发 marker；在收到某入边 marker 之前，把该入边上到达的消息记为「信道状态」。算法的两个不变量：
  1. 所有进程的状态都取自**同一割集**（marker 起到「切」的作用）；
  2. 每条信道的记录内容与进程状态相容（不会出现「无中生有的消息」）。
- 用途：**分布式死锁检测**（wait-for 图的快照里找环）、终止检测、检查点（配合日志回滚恢复）、监控（Prometheus 式「拉取快照再聚合」即是它的工程弱化版）。
- 🔧 分布式调试的本质困难：所观察的谓词分**短暂（transient）/ 稳定（stable）**之别——「死锁」是稳定的，「某变量瞬时超限」不是，后者必须靠向量时钟回放因果史，或用**可能/必然（possibly/necessarily）模态**刻画。

### 算法走查（教学示意，不参与构建）

**走查 1：一次 `www.example.com` 的迭代解析**

1. 客户端本地解析器缓存未命中 → 向本地 DNS 服务器（运营商或公司 resolver）发起查询；
2. 本地服务器缓存未命中 → 问根服务器，得到 `.com` 顶级域 NS 记录（含 glue A 记录）；
3. 问 `.com` 服务器，得到 `example.com` 的 NS（权威服务器地址）；
4. 问 `example.com` 权威服务器，得到 `www` 的 A 记录；
5. 本地服务器按各记录 TTL 写入缓存，返回客户端；
6. 后续同域查询直接吃缓存，TTL 到期重新解析——「缓存命中/回源」的比例就是 DNS 的抗压能力来源。

安全注脚：每一步都信任上一步返回的 NS/A 值，因此需要响应校验（DNSSEC 签名链）或随机化端口/事务 ID 提高投毒难度。

**走查 2：Lamport 时钟（单进程逻辑）**

```text
C 初始为 0
本地事件:   C ← C + 1
发送消息 m: C ← C + 1; 随 m 携带 C
接收消息 m: C ← max(C, C_m) + 1
```

性质：若 a → b（因果在前），则 C(a) < C(b)。反例（教学示意）：两进程各自本地事件都得到 C=5，但彼此毫无因果——数字相等/更小都不能推出并发。

**走查 3：Chandy–Lamport 快照（三进程例）**

- 初始：P1 发起快照，记录自身状态 S1，向 P2、P3 的出边发 marker；
- P2 首次收到（来自 P1 的）marker：记录自身状态 S2，标记 P1→P2 信道记录开始；此后来自 P1 的消息先入「信道缓冲」而非应用；
- P2 对自己的出边（P2→P1、P2→P3）发 marker；
- P2 收到 P1→P2 信道上的第二个 marker（即 P1 出边的 marker 到达 P2）？不——P1→P2 的记录在 P2 收到 P1 的 marker 时刻开启、P2 收到 P1 后续 marker（若有）或算法结束前关闭，期间到达的消息即信道状态；
- 汇总 {S1, S2, S3, 各信道缓冲} = 一致的全局状态：不含「只有接收没有发送」的幽灵消息。

前提重申：信道必须 **FIFO**，否则 marker 与普通消息乱序，割集失效。非 FIFO 场景要改用带序号的变体（Lai–Yang 等）。

### 快照与死锁检测的组合

- 在快照上构建全局 wait-for 图：进程状态里带上「正在等谁」；
- 在快照图中找环 = 真实死锁（快照一致性保证环内信息自洽，排除「边消失」的假死锁）；
- 这是 09-名称服务与全局状态.md 与 12-分布式事务.md「分布式死锁」一节的方法学接口：**死锁检测 = 状态捕获 + 图算法**，两个子问题分别解耦。

### 自测问答（教学自用）

- **Q：为什么「缓存 + TTL」能让 DNS 扛住全球流量？** 缓存把权威服务器流量按 TTL 指数级摊薄到各级 resolver；TTL 同时是名字变更传播延迟的上界——它是「一致性与可用性」的一根显式旋钮，读者可用 CAP 语言复述之。
- **Q：Berkeley 算法与 Cristian 算法的目标差在哪？** 前者只追求「内部互相一致」（可整体偏移），后者追求「对准外部权威」。NTP 是两者的合体：对外对准 stratum 上游，对内分层拉平。
- **Q：Lamport 时钟给不出并发判定，为什么还无处不在？** 因为大多数系统只需要**因果一致地定序**（日志、锁请求、事务时间戳的单调性），不需要知道「谁和谁并发」；判定并发的需求（冲突协调）才被迫升级到向量时钟。
- **Q：快照算法为什么必须 FIFO？非 FIFO 怎么办？** marker 的语义是「此后到达的消息属于信道状态」，乱序则语义崩塌；Lai–Yang 变体给消息打序号代替 marker，代价是带外约定。
- **Q：「可能（possibly）」与「必然（necessarily）」观测的区别？** possibly = 存在一个一致割集使谓词为真（调试时值得报警）；necessarily = 所有一致割集都为真（可作为系统不变量）。分布式监控产品的「告警去抖」本质是在两者之间选档。

### 工程易错清单

- 事件顺序的三个层面别混：**物理发生序（不可观测）→ 因果序（happens-before）→ 全序（人为约定）**；工程系统里引用「先后」时先问一句是哪一层。
- NTP 跳变 vs 渐变：chrony 默认缓调（slew），硬跳（step）会破坏「时间单调」假设——数据库/交易系统必须禁 step 或配 HLC 兜底。
- 向量时钟只回答「见过没有」，不回答「谁的值更新」；「更新」必须由应用语义（last-writer-wins 规则等）另行定义。
- 快照算法记录的是「状态」不是「真相」：它给出的割集可能从未在物理时间上整体存在过——但它**逻辑上自洽**，这对死锁/终止判定已经足够。
- TTL 不是可靠性手段：缓存过期≠服务恢复；健康检查与 TTL 要分开配置。
- LDAP 注入与 DNS 通配符滥用是命名系统的常见攻击面：属性检索的输入要转义，泛播/通配符记录要按「最小授权」管理。
- 监控聚合顺序：多节点日志按「各节点本地时间戳」排序是错的；按 Lamport/向量时钟或统一授时源重排，才能看到因果。

## 近年研究与工业界开源实践（2015–2026）

- **TrueTime（Spanner, OSDI 2012 / TODS 2017）**：GPS + 原子钟给每次时间读数返回**区间 [earliest, latest]**，事务等待区间尽头换来外部一致性——把「物理时钟不可靠」变成「可计算的不确定度」。
- **混合逻辑时钟 HLC**（Kulkarni et al., 2014）：物理墙上限 + Lamport 逻辑增量的合成，被 CockroachDB、YugabyteDB 采用；🔧 HLC 既满足 Lamport 单调性又「读起来像墙钟」，解决了纯逻辑时钟难以做 GC/调试的问题。
- **Clock-SI**（Duffy et al., 2013）：分区部署下用本地时钟直接做快照隔离的时间戳来源，证明「不必全网同步也能 SI」。
- **数据中心精密授时**：PTP（IEEE 1588）+ 白金设备进入公有云（AWS Time Sync 提供 PTP 接口），亚微秒同步让 TrueTime 类设计走出 Google；内核态 NTP 逐步被 chrony/PTP 硬件时间戳取代。
- **工业界开源**（star 数 2026-09 实测）：
  - `cockroachdb/cockroach`（32498★）：HLC 作为事务时间戳，快照读按因果一致（见 11-事务与并发控制.md）。
  - `etcd-io/etcd`（52310★）：名称/配置存储 + MVCC 版本号，可视为「逻辑时钟即版本」的实用化。
  - `apple/foundationdb`（16730★）：全局序由确定性模拟 + 版本号授予服务保证，本质是集中式 Lamport 时钟的工程极致。
  - `hashicorp/consul`（30082★）：服务目录（名称服务 + 健康检查属性检索）的事实标准之一。
  - Kubernetes（`kubernetes/kubernetes`，127994★）：CoreDNS 完成集群内名称解析，对应本书 13 章「名称服务 + 缓存」模型的现代镜像。
  - NTP 的现代实现 `chrony`（仓库 star 未核验）： Linux 发行版默认 NTP 客户端/服务端。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Lamport 时钟能判断并发」 | 它只能保序不能判并发；判并发必须用向量时钟 |
| 2 | 「NTP 同步后物理时间可当全序用」 | 公网毫秒级误差远超局域网事务间隔；才需要 TrueTime/HLC |
| 3 | 「快照算法要求停止系统」 | Chandy–Lamport 正是**不停机**捕获一致状态的算法，但要求 FIFO 信道 |
| 4 | 「DNS 缓存 TTL 越长越好」 | TTL 是负载与故障切换速度的权衡；现代服务发现常用极短 TTL + 主动健康检查 |
| 5 | 「向量时钟免费」 | 消息头随节点数线性增长；大规模系统用部分向量/版本号折衷，牺牲部分并发判定能力 |
| 6 | 🔧 本书未覆盖 | TrueTime 的实现细节与等待区间证明、HLC 的 GC 界、CRDT 中向量时钟的收敛应用、时钟同步攻击面（NTP 攻击、时钟回拨对 TLS/事务的影响） |
