# 第 1 章 分布式系统的特征

> **覆盖原书**：中译第 5 版第 1 章「分布式系统的特征」（案例研究：万维网）。
> **本章地图**：什么是分布式系统 → 资源共享与开放性 → WWW 案例（HTML/URL/HTTP/可伸缩性）→
> 构造挑战七项（异构性、开放性、安全性、可伸缩性、故障处理、并发性、透明性）→ 八种透明性细分 →
> 普适计算与 Web 的演进背景。

## 本章地图

- 原书开章立论：**分布式系统是「位于联网计算机上的组件，仅通过消息传递来通信并协调动作的系统」**。
  这一定义刻意不提共享内存、不提节点对等与否——对等的（对等系统）与不对等的（客户-服务器）都涵盖。
- 全章围绕两条线展开：一条是**动机线**（资源共享 → WWW 成为最大规模的分布式系统案例），
  一条是**挑战线**（七项挑战，后面每一章都在回应其中一两项）。
- 大纲摘录中出现的「刀片服务器（blade server）」「QoS」「CORBA」均出自本章背景小节：
  刀片服务器是构建数据中心级可伸缩硬件的形态之一；QoS 是第 3/20 章的前引；CORBA 是第 5/8 章的前引。

## 核心精讲（教学示意，不参与构建）

### 1.1 资源共享与开放性
- **资源**：硬件（打印机、存储）、软件（文件、数据库）、数据与服务，凡是能被多个用户/程序使用的都算。
- **开放性（openness）**的关键是**发布关键接口**并基于一致的通信机制：新服务可以增量加入、
  多个厂商可以提供异构实现。反过来，接口发布也带来「统一 vs 竞争」的标准化博弈——
  IETF（互联网协议）与 OMG（CORBA）是两个典型组织。
- 🔧 中间件（middleware）的定义在本章给出：屏蔽底层网络、硬件、操作系统与编程语言差异，
  为应用提供一致计算模型（RPC、远程事件、远程 SQL 访问、分布式事务等）的软件层。
  虚拟机（Java 虚拟机）是「代码到处运行」的另一种路径。

### 1.2 案例：万维网
- 三个基础发明（照抄原书口径）：**HTML**（超文本标记语言）、**URL**（统一资源定位器）、
  **有容错与可伸缩性的客户端-服务器体系**（浏览器 + Web 服务器 + HTTP）。
- WWW 为什么成为最大的分布式系统？逐条对上七项挑战：
  - **异构性**：浏览器掩盖了服务器端操作系统/硬件差异；HTTP 是通用协议。
  - **可伸缩性**：服务器可复制、可分而治之（按 URL 分层级代理/缓存）。
  - **透明性**：用户看到的是「一个页面」，资源实际在何处、被谁缓存不可见。
  - **故障处理**：链接失效/服务器宕机只表现为局部错误，系统整体继续运行。
- 🔧 动态内容（CGI，原书时代称 CGI，今天对应服务端渲染/Serverless 函数）与 HTTP 的
  无状态性是本章埋下的两个伏笔：无状态让复制与缓存变容易，但让「会话」需要应用层自行实现。

### 1.3 七项构造挑战（前半视角的浓缩版）

| --- | --- | --- |
| 异构性 | 网络、硬件、OS、编程语言、开发者实现的差异 | Ch3（网络）、Ch5/8（中间件）、Ch7（OS） |
| 开放性 | 关键接口发布、可增量扩展 | Ch5/8（接口与互操作） |
| 安全性 | 机密性、完整性、可用性 | Ch11（安全性，本目录 07 文件） |

### 1.4 八种透明性（原文照抄口径）
1. **访问透明性**：用相同操作访问本地与远程资源；
2. **位置透明性**：无需知道资源物理/网络位置；
3. **并发透明性**：多进程并发使用共享资源互不干扰；
4. **复制透明性**：多副本的存在对使用者不可见；
5. **故障透明性**：屏蔽故障，任务在软硬件故障下仍能完成；
6. **移动透明性**：资源与客户在系统内移动不受影响；
7. **性能透明性**：负载变化时系统可重配置以提升性能；
8. **伸缩透明性**：系统与应用可扩展而不改变系统结构与应用算法。

### 1.5 判定练习：一个系统「透明」到了什么程度
用三个日常场景做透明性自检（原书案例思路的教学重述）：
- **手机电话簿**：联系人换了号码，你仍拨「张三」——这是**位置/移动透明性**（号码簿服务
  屏蔽了映射），但若对方漫游断线，你听到的是忙音而非「无法到达」——**故障透明性失败**。
- **云盘同步目录**：本地目录与云端对象存储同步，你感知不到副本存在（**复制透明性**）；
  但断网后写入冲突需要人工解决——**并发透明性破损**，冲突暴露给了用户。
- **网页登录态**：会话在多台服务器间迁移，用户无感（**位置/复制透明性**）；
  但会话过期被踢回登录页，等于把「状态在服务端哪台机器」的细节反向暴露——
  工程上靠粘性会话或共享会话存储（Redis）修补。
- 结论：透明性不是布尔值，而是**逐性质逐场景的权衡表**；设计时应显式列出「我承诺哪些透明、
  在什么条件下失效、失效时用户看到什么」。

### 1.6b 七项挑战的自检问题清单（读后续章时反复回看）
1. 异构性：这个机制假设了哪些平台/网络/语言特性？
2. 开放性：新加入的厂商能否只凭接口文档实现一个兼容节点？
3. 安全性：谁可以加入？消息被窃听/伪造会怎样？
4. 可伸缩性：节点数 ×100 时，哪个组件最先饱和？
5. 故障处理：任一组件崩溃后，系统返回什么、丢什么、重试什么？
6. 并发性：两个请求同时命中同一资源，谁赢？
7. 透明性：哪些细节对用户可见，哪些被刻意隐藏、隐藏的代价是什么？
- 用法建议：每读完本目录一个章节文件，回填这张清单——它是全书的主线索引。

### 1.6 从七项挑战到当代设计模式（映射速查）
| 挑战 | 原书时代的答案 | 当代工程答案（2015–2026） |
| --- | --- | --- |
| 异构性 | 中间件（CORBA/Java） | 容器 + 编排（K8s）、protobuf/OpenAPI 契约 |
| 开放性 | 发布接口、标准组织 | API 网关 + OpenAPI/CRD 生态、可插拔 CNI/CSI |
| 安全性 | 加密、认证协议 | 零信任、mTLS、OIDC（见本目录 07 文件） |
| 可伸缩性 | 复制服务器、缓存 | 水平自动扩缩、分片（sharding）、CDN |
| 故障处理 | 重传、冗余 | 混沌工程、SLO/错误预算、重试 + 熔断 + 幂等 |
| 并发性 | 信号量、锁 | 分布式锁（租约）、乐观并发、消息队列削峰 |
| 透明性 | 八种透明性框架 | sidecar 注入、声明式 API、「透明」下沉到基础设施 |
- 🔧 读法建议：把左列当「问题清单」，中列当「1980–2010 的经典解」，右列当「面试/生产答案」；
  原书各章给的是中列，本目录各章的 🔧 节补右列。

### 1.7 可伸缩性四子问题展开（原书口径逐条细化）
| 子问题 | 表现 | 经典案例 |
| --- | --- | --- |
| 控制物理资源开销 | 用户增加时成本应接近线性而非陡增 | 服务复制的数据结构开销 |
| 控制性能损失 | 规模扩大后延迟不应失控 | 集中式服务器的网络瓶颈 |
| 防止软件资源用尽 | 固定长度标识符/表会被耗尽 | 32 位 IPv4 地址枯竭（正是 IPv6 的动机）、16 位端口号 |
| 避免性能瓶颈 | 数据结构或算法在规模临界点退化 | 集中式单点（后续靠分区/复制化解） |
- 🔧 读法：原书此表写于 2000 年代初，但「资源用尽」一类至今反复发生（IPv4、
  早期 32 位时间戳、短 URL 码空间）；可伸缩性设计的第一课是**估算标识符与状态的空间上限**。

### 1.8 开放性的两个层次（补充）
- **接口开放**（发布规范）：任何人可实现客户端/服务器——IETF 的 RFC 传统；
- **实现开放**（开源实现可用）：标准 + 参考实现一起构成事实标准——Linux/Apache 时代之后，
  「开源即开放」成为默认预期，原书写作时这一点尚未成为共识。
- 两者缺一不可：只有接口开放会导致「规范兼容但实现不兼容」（CORBA 的教训，
  见本目录 05 文件 🔧 节）。

## 近年研究与工业界开源实践（2015–2026）

- **「七项挑战」的现代表述**已迁移进云原生词汇表：可伸缩性 → 弹性（autoscaling）、
  故障处理 → 混沌工程与 SLO、透明性 → sidecar/service mesh 的「透明注入」。
- 开源实践（star 数 2026-09 `gh api` 实测）：
  - `kubernetes/kubernetes`：把「声明式资源 + 控制器」做成事实上的分布式系统公共底座，
    其 API 开放性正是原书「开放性」挑战的当代答案（star 未核验——本次实测命令未包含该库，
    需要时补查）。
  - `torvalds/linux`（250162★）：异构性最底层的抹平者；本章提到的「操作系统异构」在今天
    由容器（namespace/cgroup）进一步抽象。
- 🔧 微服务运动把本章挑战从「教科书问题」变成「每家公司的面试题」：服务发现（位置透明）、
  重试与幂等（故障透明）、限流（并发/可伸缩）分别对应一项挑战的工程解。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「分布式系统 = 多台机器 + 网络」 | 原书定义的核心是**仅靠消息传递协调**，共享内存多处理器不算 |
| 2 | 「透明性越高越好」 | 见 Waldo 论文：故障与延迟在本地/远程间有本质差异，完全伪装透明反而有害（局部 vs 全局故障语义） |
| 3 | 「可伸缩性只是加机器」 | 原书列出四个子问题：控制物理资源开销、控制性能损失、防止软件资源用尽、避免性能瓶颈——第 4 项（如 32 位地址空间、表结构上限）最易被忽略 |
| 4 | 🔧 本书未覆盖 | 云与虚拟化仅作背景提及；以今天视角应补：多租户隔离、按量计费、区域/可用区故障域——这些已成为「可伸缩性」挑战的当代形态 |
| 5 | 🔧 大纲摘录遗留问题 | 摘录中「分布式系统故障模型？？哪里介绍了」——答案在第 2 章（omission/arbitrary/timing 三类）与第 15 章，本目录 02 文件详解 |
| 6 | 「分布式系统都是服务器集群」 | 对等系统（原书第 10 章）与移动/泛在计算（第 19 章）都是一第一等的分布式系统，节点可以是对等端或传感器 |
| 7 | 「中间件 = 一个具体产品」 | 中间件是**分层抽象**：RPC 框架、消息队列、对象请求代理、服务网格都扮演中间件角色，判断标准是「是否屏蔽了网络与平台差异」 |
