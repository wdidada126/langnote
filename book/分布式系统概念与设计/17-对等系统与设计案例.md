# 17 对等系统与设计案例（第 10 章 对等系统 + 第 21 章 分布式系统设计：Google 实例研究）

> **本章地图**：P2P 的定义与三大动机（资源共享/规模/匿名与自治）→ 历史三幕：Napster（集中目录）→ Gnutella（全泛滥查询）→ **结构化 P2P**（DHT：Chord 一致性哈希环、Pastry/Tapestry 前缀路由、Kademlia 异或度量）→ 应用案例（BitTorrent 文件分发、Squirrel/OceanStore/Ivy、P2P 多媒体）→ **Ch21 设计案例**：Google 基础设施全景（GFS 分布式文件系统、MapReduce 计算、Bigtable 结构化存储、Chubby 分布式锁服务）与「简单务实的设计取舍」。

## 本章地图

两章合读是一条「**从对称到不对称**」的设计光谱：P2P 用**完全对称**的节点换来极限规模与无单点；Google 案例用**精心设计的不对称**（单 master、专用存储）换来可控的复杂度。DHT 的路由与 quorum/共识共享同一套概率与多数派直觉；GFS/Bigtable 则示范了本书前 18 章的全部机制（复制、一致性、锁、提交）如何被取舍成一个能跑全球业务的整体。中译第 5 版章题：「对等系统」（第 10 章）与「分布式系统设计：Google 实例研究」（第 21 章）。

## 核心精讲

> 以下伪代码、表格均为**教学示意，不参与构建**。

### 10.1 P2P 的中间件问题

- P2P 系统的中间件职责：**成员管理**（动态加入退出）+ **资源定位**（在 N 个对等点上找对象）。
- 三代定位方案：
  1. **集中目录**（Napster）：查找 O(1)，但服务器是单点与法律靶子；
  2. **泛滥查询**（Gnutella）：无结构，洪泛 O(N) 消息，靠 TTL 截断，不可扩展；
  3. **结构化 DHT**：按 key 哈希放到「负责该 key 的节点」，查找 O(log N) 跳。

### 10.2 DHT 的四种代表设计

| 设计 | 路由度量 | 表结构 | 查找代价 | 工程现状 |
| --- | --- | --- | --- | --- |
| Chord | 环形哈希 | 后继 + finger 表（2^i 距离） | O(log N) | 教学经典 |
| Pastry | 数字前缀 | 前缀路由表 + 邻近集 | O(log N) | 兼顾物理邻近 |
| Tapestry | 数字前缀 | Plaxton 树 | O(log N) | 静态对象定位 |
| Kademlia | **XOR 距离** | k-bucket 树 | O(log N) | BitTorrent/以太坊在用 |

- **Chord 细节**：节点与 key 同映到 m 位哈希环；查找沿 finger 表折半（每次至少缩短一半距离）；节点加入/退出只影响环上局部指针；**后继列表（successor list）**——每个节点记录 r 个后继，节点失效概率独立时，环不破裂的概率随 r 指数上升。
- **Kademlia**：以**异或（XOR）**距离为度量，查找路径天然重叠（每次迭代候选集部分共享），工程上抗 churn 表现最好——BitTorrent 主流 DHT 与以太坊节点发现（discv5）都用它或其后代。
- 副本放置：同一 key 的副本按环上后继邻域放置；多副本查找与 quorum 读（13-复制.md）可叠加。

### 10.3 应用案例

- **BitTorrent**：文件分块、**稀有块优先**（rarest first）+ **互惠传输**（tit-for-tat，choking 算法）激励共享；Tracker → DHT 演化（去中心化发现）。
- **Squirrel / OceanStore / Ivy**（书中案例）：P2P Web 缓存、P2P 存储对象与 P2P 文件系统——把 DHT 当「分布式哈希数据库」用，再叠加一致性/缓存层。
- P2P 多媒体：直播/点播的应用层组播树（对应 15-分布式多媒体系统.md 的组播需求）。
- Skype 早期（第 1 版目录案例）：超级节点层次——「纯 P2P」在 NAT/性能现实下的妥协。

### 21.x Google 案例研究（第 21 章）

- **GFS（SOSP 2003）**：单 master（元数据在内存）+ chunkserver（64MB chunk，3 副本，**租约 + 主副本定序**）；为「追加为主」的负载优化，接受**重复记录与不一致副本**，由上层（MapReduce）过滤——「放宽一致性换简单与吞吐」的教科书级示范。
- **MapReduce（OSDI 2004）**：以 GFS 的数据本地性为前提的批处理编程模型；master 调度、worker 执行、Combiner/Partitioner 定制；容错靠「重跑而非回滚」（幂等的 map/reduce）。
- **Bigtable（OSDI 2006）**：稀疏、分布式、持久化多维有序表；tablet 按 range 切分，元数据三级（root/META/用户表），Chubby 提供锁与 tablet 位置根；SSTable + MemTable 的 LSM 风格读写。
- **Chubby（OSDI 2006）**：Paxos 组 + 租约的分布式锁/小文件服务——**第 15 章共识理论在 Google 的落地形态**，也是 ZooKeeper/etcd 的直系祖先；客户端用会话（session/lease）维持与 master 的关系。
- 🔧 案例的教学价值：四件套分别是「文件系统、批计算、KV 存储、协调服务」，每个都做了激进的**负载特化取舍**（GFS 单点、Bigtable 无跨行事务、Chubby 集中式锁）——设计案例教的不是「正确答案」而是「取舍得起」。

### 算法走查（教学示意，不参与构建）

**走查 1：Chord 查找（m=6 位环，节点 8 找 key 54）**

```text
finger 表: 节点 n 维护 finger[i] = 在环上找 (n + 2^i) 的后继
查找 54（由节点 8 发起）:
  8 的 finger 中不超过 54 的最大者 = 42 → 跳到 42
  42 的 finger 中不超过 54 的最大者 = 51 → 跳到 51
  51 的后继 = 54 → 54 负责 key 54
每次跳转距离至少减半 → O(log N) 跳
```

- 节点加入：新节点 n 插入 → 通知其前后继更新指针与 finger；副本/区间所有权随之局部转移。
- 🔧 后继列表 r 的意义：r 个连续后继全失效的概率 p^r（p 为单点失效率），r=O(log N) 即可把环断裂概率压到可忽略。

**走查 2：MapReduce WordCount（书中案例的最小复述）**

```text
map(k1, v1):        // v1 为文档文本
  for word in tokenize(v1): emit(word, 1)
reduce(word, [1,1,...,1]):
  emit(word, sum)
master:
  分配 map 任务（优先分配到持有所需文件块副本的 worker —— 数据本地性）
  map 输出按 partition 函数分给 R 个 reduce 任务
  worker 失败 → 重跑该任务（map/reduce 幂等, 无需回滚）
```

**走查 3：Bigtable 读路径**

1. 客户端向 Chubby 查询 tablets 位置根（root tablet）；
2. 沿 METADATA 表定位目标 tablet 所在的 tabletserver；
3. 读 = MemTable（活跃）+ SSTable（磁盘，可能多层合并）合并视图，Bloom filter 挡掉无关 SSTable；
4. 写 = 写 WAL + 更新 MemTable；compaction 后台合并 SSTable。
- 分布式锁（Chubby）、有序存储（tablet）、副本（GFS 底层）三层各司其职——按章拼装的教科书式架构。

### 自测问答（教学自用）

- **Q：DHT 把 key 均匀哈希，会不会毁掉局部性？** 会——同一网站的多个对象散到全网。补救：Squirrel 用「整站到单节点」的粒度缓存，Kademlia 用 k-bucket 按物理邻近排序候选；局部性与负载均衡是 DHT 的第一对矛盾。
- **Q：BitTorrent 的 tit-for-tat 为什么有效？** 激励按「实测吞吐」结算（上传多者获对等下载），伪造身份无法作弊（换 ID 就重新排队），博弈论上形成合作均衡——机制设计而非加密强度保证了系统存活。
- **Q：GFS 的「记录追加可能重复」为什么可接受？** 上游（MapReduce）按 chunk 内偏移 + 校验和去重；任务本身幂等——把去重责任上移到唯一知道语义的层，是「端到端原则」的经典应用。
- **Q：Chubby 为什么是「锁 + 小文件」而不是纯锁服务？** 会话/租约语义需要「可读写的元数据」（锁文件内容放 ACL、持有者信息）；客户端还拿它存「谁是主」的小配置——一个 Paxos 组顺便解决三个问题（锁、选举、配置）。
- **Q：Google 案例里哪个决策最难「抄」？** 单 master GFS 的元数据全内存：它依赖「chunk 数 ÷ 内存」的定量预算与可接受的恢复时长——抄架构不抄容量数学，是读案例章最常见的事故来源。

## 近年研究与工业界开源实践（2015–2026）

- **对等的当代形态**：
  - **IPFS**（`ipfs/kubo`，17142★，协议层 `libp2p/go-libp2p`，6882★）：内容寻址 + DHT 定位 + bitswap 交换，Kademlia 的现代完整实现；Filecoin 以存储市场补经济激励。
  - **区块链即 P2P 的遗产**：`bitcoin/bitcoin`（90250★）的 gossip + 工作量证明、`ethereum/go-ethereum`（51370★）的 discv5（Kademlia 后代）——共识/广播/定位全部沿用 P2P 语汇，只是「激励」升级为一等公民。
  - `webtorrent/webtorrent`（31420★）：浏览器内 BitTorrent（WebRTC 数据通道），P2P 多媒体案例的当代样本。
- **Google 案例的开源化**（star 数 2026-09 实测）：几乎每一件都有开源对应物——GFS → HDFS（`apache/hadoop`，15670★）；Bigtable → HBase（`apache/hbase`，5560★）/ Cassandra（`apache/cassandra`，10103★）；Chubby → ZooKeeper（`apache/zookeeper`，12811★）/ etcd（`etcd-io/etcd`，52310★）；MapReduce → Spark/Flink；Borg → Kubernetes（`kubernetes/kubernetes`，127994★，Ch21 之后的发展，书中未收）。LevelDB（`google/leveldb`，39446★）即 Bigtable SSTable 的单机化抽屉。
- **研究侧**：DHT 路由与「信息中心网络（ICN）」、去中心化存储的纠删码副本策略、对等网络的经济机制设计（mechanism design）持续活跃。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「P2P = 盗版文件共享」 | P2P 是架构属性（对称节点 + 无中央协调），内容分发/CDN/区块链都是其合法形态 |
| 2 | 「DHT 查找 O(log N) 所以处处最优」 | 泛滥查询在**局部性**与实现简单性上反而常胜；现实中多数系统是 DHT 与集中索引的混合 |
| 3 | 「GFS 是「更好的文件系统」」 | 它是**为追加负载特化**的文件系统，一致性模型弱于 POSIX；照抄会踩坑 |
| 4 | 「Chubby 是锁服务器所以要实现完整锁语义」 | Burrows 论文明确：客户端用**租约 + 会话**语义，不做精细锁；照 POSIX 锁使用会失效 |
| 5 | 🔧 本书未覆盖 | Raft 取代 Chubby 式自研共识成为默认、CRDT 与对等协同、区块链共识（PoS、HotStuff 系）的算法演进、IPFS/内容寻址体系 |
| 6 | 「MapReduce 仍是主流计算模型」 | 已被 Spark/Flink 的内存/流式模型取代；但「数据本地性 + 幂等重跑」的容错哲学被完整继承 |
