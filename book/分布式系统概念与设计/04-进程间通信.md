# 第 4 章 进程间通信

> **覆盖原书**：中译第 5 版第 4 章「进程间通信」。
> **本章地图**：互联网协议族的编程接口 → **Socket 数据报（UDP）**与**流（TCP）**编程 →
> 默多克的组播与 IP 组播（可靠组播问题）→ 外部数据表示与 marshalling（XDR/序列化）→
> 客户-服务器通信设计（阻塞/非阻塞、超时、心跳）→ 案例概览：MPI 与 Skype（摘录线索）。

## 本章地图

- 第 3 章讲协议「是什么」，本章讲进程「怎么用」：Socket API 是本书所有后续机制
  （RPC/RMI、组通信、文件系统 RPC）的公共底座。
- 大纲摘录关键词核对：**CORBA 与 MPI** 出现在本章（摘录把 CORBA 挂在第 4 章，实际其
  体系详解在第 8 章；MPI 在本章「进程组通信/并行编程」讨论中）；**Skype** 在原书是
  对等覆盖网络案例（第 10 章），摘录将其记在第 4 章，本目录在 05/10 文件归位。
- 组播（组通信）在本章以 **IP 组播与可靠组播协议**形式首次出现——它是第 6 章「间接通信」
  与第 15 章「组播与协定」的前奏。

## 核心精讲（教学示意，不参与构建）

### 4.1 Socket：统一的进程间通信接口
- Socket = 通信端点（IP 地址 + 端口号）+ 协议选择（UDP/TCP）+ 本地 OS 缓冲与队列。
- **数据报 Socket（UDP）**：
  - 语义：独立报文、不可靠、可乱序、有最大长度限制（受 MTU 与 64KB 上限）；
  - 适合：请求-响应（一次请求一次响应，超时重发）、状态广播、DNS。
- **流 Socket（TCP）**：
  - 语义：可靠有序字节流、连接生命周期（三次握手/四次挥手）、流控（滑动窗口）、拥塞控制；
  - 适合：长会话、大文件、需要按序消费的场景。
- 🔧 与第 3 章呼应：TCP 的「可靠」只是把丢包遮蔽成延迟，应用仍要处理**连接失效**
  （对端崩溃表现为 read 返回 0 或超时，而非明确故障报告）——故障语义弱是 Socket 抽象的固有代价。

```java
// 教学示意，不参与构建：UDP 请求-响应骨架（Java 风格）
DatagramSocket s = new DatagramSocket();
byte[] buf = reqBytes;
DatagramPacket p = new DatagramPacket(buf, buf.length, serverAddr, port);
s.send(p);
s.setSoTimeout(2000);                 // 客户端超时：异步系统中唯一可用的故障检测手段
s.receive(p);                         // 超时后按「至少一次」语义决定重发与否
```

### 4.2 组播与可靠组播
- **IP 组播**：一对多投递，路由器负责复制（IGMP 加入组、组播地址范围 224.0.0.0–239.255.255.255）；
  Java 里 `MulticastSocket` 直接可用。
- **可靠组播**：IP 组播本身不可靠（丢包/无成员管理）；需要协议补足有序性与成员视图一致性——
  原书指出这正是第 15 章「组播与协定」（ISIS 一脉）的入口。
- 🔧 2026 修正：IP 组播在公网**从未大规模部署**（运营商不开放）；今天的「组播」由应用层实现：
  CDN、pub/sub 消息系统、WebRTC 的 SFU 转发。原书第 6 章「间接通信」的出版-订阅正是替代形态。

### 4.3 外部数据表示与 marshalling
- 问题：字节序（大端/小端）、结构对齐、指针/对象引用不可跨机传递。
- 三条路线（原书口径）：**CORBA CDR**（第 8 章）、**Java 序列化**（自描述、类型随流）、
  **XML/JSON 文本编码**（互操作性与可读性优先）。
- 🔧 2026 修正：文本编码时代被 **protobuf/FlatBuffers/Avro** 等二进制 IDL 取代（强 schema、
  前后兼容、体积小）；JSON 只在「人对数据可读」时保留。Java 原生序列化因反序列化漏洞
  （ gadget chain ）已被普遍视为反模式。

### 4.4 客户-服务器通信设计要点
- **阻塞/非阻塞/超时**：`setSoTimeout` 是异步模型下唯一的本地故障检测；
- **至少一次 / 至多一次**语义：重发带来重复请求风险 → 幂等设计（第 5 章 RPC 语义延续）；
- **心跳与保活**：长连接用应用层心跳探测对端（TCP keepalive 周期过长且不可控）。

### 4.5 工作例题：一次 UDP 请求的生命周期与三种坏结果（教学重述）
- 正常路径：`send` 报文进入内核发送缓冲 → IP 路由 → 对端网卡收包 → 内核放入接收队列 →
  对端 `receive` 取走。
- 三种坏结果与应对：
  1. **报文丢失**：发送方永远不知道 → 超时重发（at-least-once）或放弃（maybe）；
  2. **报文重复**（重发后原报文又到达）：requestId 去重（at-most-once）；
  3. **对端崩溃**：表现为持续超时，无法与「网络分区」区分 → 心跳与故障检测（第 15 章）。
- 结论：**Socket API 不提供故障语义，语义是调用方协议设计出来的**——这正是第 5 章 RPC
  框架存在的理由。

### 4.6 组播的排序级别（可靠组播速查）
| 级别 | 保证 | 实现要点 | 典型用途 |
| --- | --- | --- | --- |
| 尽力而为 | 无 | IP 组播裸用 | 音视频（应用自容错） |
| FIFO | 同一发送者按序 | 每源序号 | 状态复制 |
| 因果（causal） | 因果链按序 | 向量时钟戳 | 协作系统 |
| 全序（total） | 所有接收者一致的全序 | 定序器/共识 | 复制状态机（第 15/18 章接续） |
- 原书在本章只给 IP 组播机制；四级排序的形式化在第 15 章（协调和协定，后半目录）——
  ISIS 虚拟同步组通信是「排序 + 视图」的经典综合。

### 4.7 案例注记：MPI 与 Skype（摘录关键词归位）
- **MPI**（摘录原文「跨语言的通讯协议，用于编写并行计算机，支持点对点和广播」口径照抄）：
  面向**并行计算**的消息传递标准，进程组 + 集合通信（广播/归约/散播）是它的灵魂；
  与本书第 4 章的关系是「同一抽象域的 HPC 特化」，顺序与容错假设与互联网分布式系统不同
  （MPI 假设进程故障即作业失败，不做部分容错）。
- **Skype**（摘录「Skype 一个覆盖网络的例子；Skype 体系结构是公开的」）：原书把 Skype 作为
  P2P 覆盖网络案例讲授（第 10 章语境）；其「超级节点中继」结构是 NAT 穿越与对等路由的
  经典教材，也是第 3 章 NAT 问题的应用兑现。早期协议未公开文档化，「结构公开」的说法
  来自原书时代的社区逆向研究，🔧 现代阅读建议以「覆盖网络设计思想」取材，勿引用其具体协议细节。

### 4.8 Socket 编程常见坑位速查（工程补充，教学示意）
| 坑 | 现象 | 对策 |
| --- | --- | --- |
| 半开连接 | 对端断电无 FIN，read 永久阻塞 | 应用层心跳 + 空闲超时 |
| Nagle 与延迟确认互锁 | 小包写延迟几百毫秒 | `TCP_NODELAY`（或合并写） |
| 消息边界丢失 | TCP 流被拆/粘包 | 定长/分隔符/长度前缀成帧 |
| 接收缓冲堆积 | 慢消费者拖垮服务线程 | 背压/流控（credit 机制） |
| TIME_WAIT 风暴 | 主动关闭方端口耗尽 | 连接池/长连接 |
| 大小端错乱 | 跨平台解析错值 | 网络字节序或自描述编码 |
- 读法：原书讲「API 语义」，这一张表是语义在工程里的落点；每个坑都能追溯到
  4.4 节的某条设计要点。

### 4.9 TCP 连接建立与关闭时序速查（教学重述）
- **三次握手**：SYN（c→s, seq=x）→ SYN+ACK（s→c, seq=y, ack=x+1）→ ACK（c→s, ack=y+1）；
  意义：双方各确认「我发你能收、你发我能收」两个方向可用。
- **四次挥手**：FIN → ACK → FIN → ACK；主动关闭方进入 TIME_WAIT（2×MSL）——
  等待「迷路的旧报文自然死亡」，防止旧连接数据污染新连接。
- 与分布式语义的连接点：
  1. 握手保证**两个方向独立可达**——半开（一端认为已连、另一端已弃）正是异步故障的具象；
  2. TIME_WAIT 是「协议层面的重放保护」，与应用层 requestId 去重（5.4 节）思想同源；
  3. 🔧 QUIC 用连接 ID 取代四元组并把握手与 TLS 合并（1-RTT），上面三点全部重构——
     但「双向可达确认 + 旧报文失效」两个本质需求没变。

## 近年研究与工业界开源实践（2015–2026）

- **QUIC 生态**：`cloudflare/quiche`（12609★，2026-09 `gh api` 实测）；nginx（31731★）与
  各主流浏览器/服务端已默认支持 HTTP/3。

  使单机百万级并发连接的「事件循环 + 零拷贝」成为常规配置。
- **组播的现代替身**：Kafka/RocketMQ 等发布-订阅系统（见

  在应用层重建了「一对多有序投递」，且把持久化纳入语义——这是 IP 组播与 JMS 时代的
  混合体演进。
- 🔧 MPI 并未消亡而是退守 HPC/AI 集群：NCCL 等集合通信库在 GPU 训练中延续 MPI 语义。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「TCP 可靠，所以不会丢数据」 | 可靠指**已确认数据**的有序交付；未 flush、对端崩溃、内核缓冲未落盘的数据照样丢失 |
| 2 | 「UDP 一用就丢包，还是 TCP 稳」 | 丢包源于拥塞而非协议；QUIC 正是「UDP 上的可靠传输」反例——可靠性与协议层次无关，与实现有关 |
| 3 | 「IP 组播是组通信的标准答案」 | 公网不可用；生产系统一律应用层组播（pub/sub、SFU、CDN） |
| 4 | 「Java 序列化 = 通用 marshalling」 | 仅限 Java 同源系统；跨语言与安全角度都应选 IDL（protobuf 等） |
| 5 | 🔧 本书未覆盖 | QUIC 多路复用与连接迁移、io_uring、eBPF、WebSocket（浏览器长连接事实标准，2011 RFC 6455，晚于多数原版章节的写作） |
| 6 | 🔧 摘录归位说明 | 摘录把「CORBA」「Skype」记在第 4 章名下：CORBA 体系详解在原书第 8 章（本目录 05 文件），Skype 是第 10 章对等案例（后半目录） |
