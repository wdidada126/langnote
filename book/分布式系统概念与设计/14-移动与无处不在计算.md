# 14 移动与无处不在计算（第 19 章 移动和无处不在计算）

> **本章地图**：无处不在计算的愿景（Weiser）→ 无处不在系统对分布式系统的三重挑战（易失性连接、低带宽/间歇网络、设备异构与能量约束）→ **发现服务**（发现协议四要素：注册/查找/匹配/租赁；案例：Jini 发现、UPnP、蓝牙 SDP）→ **易失性关联下的操作**（disassociation 感知、访问低带宽网络的适配、hotspot 场景）→ **易失性 IPC 与数据共享**（面向间歇连接的组播/发布订阅、离线操作与冲突协调）→ 与物理世界集成（智能空间、上下文感知、能量管理）。

## 本章地图

移动设备会频繁断连、重连、换网络（volatility），传统「服务器常在、连接稳定」的分布式假设全部失效。本章的主题词是**易失性（volatility）**：服务要用**发现协议**动态找（而非静态配置），通信要容忍**断续**（而非假设消息必达），数据要支持**离线工作 + 事后合并**（而非假设随时在线）。它的许多思想（发布订阅、租赁、离线优先、上下文感知）在今天 IoT 与边缘计算里全面复活。

## 核心精讲

> 以下伪代码、表格均为**教学示意，不参与构建**。

### 无处不在系统的约束清单

- **易失性连接**：设备在关联/解除关联之间反复切换；连接是「事件」而非「状态」。
- **带宽与延迟不对称**：蜂窝/无线链路慢且贵，常需要**数据适配**（过滤、降级、缓存预取）。
- **能量与计算受限**：通信比本地计算耗电高一个数量级以上——「能本地做的别传网络」。
- **异构与匿名协作**：陌生设备临时协作，没有管理员预配置——这正是发现服务存在的理由。
- **上下文感知**：位置、邻近、设备状态参与计算（智能空间：环境里的服务随人的移动而重组）。

### 发现服务（Discovery）

- 四要素模型：**注册**（服务上线宣告）、**查找**（客户端查询）、**匹配**（类型/属性匹配）、**租赁（lease）**——注册信息带租期，到时自动失效，解决「服务悄悄消失」的垃圾回收问题。
- 案例（书中口径）对比：

  | 系统 | 注册方式 | 查找方式 | 特色 |
  | --- | --- | --- | --- |
  | Jini lookup | 服务上传代理对象 | 按 Java 类型查找 | 代理对象下载到客户端执行（代码移动！） |
  | UPnP | SSDP 组播宣告 | HTTP 查询 XML 描述 | 设备/服务双层 XML 模型，SOAP 控制 |
  | 蓝牙 SDP | 连接即注册 | 按服务类/属性查询 | 近距离极简，无租赁概念 |

- 🔧 现代对应：mDNS/DNS-SD（Bonjour、`_http._tcp.local`）、Kubernetes 的服务 DNS + 健康检查、Consul 的服务目录——「租赁」演化成 TTL/心跳，「按类型查找」演化成标签选择器。
- 案例延伸（书中提及）：**Cooltown**（HP 实验室）——把「实体物件」用 URL/信标数字化，发现服务延伸到物理世界；这是 IoT「数字孪生」思想的先声。

### 易失性通信

- 组播与发布订阅对移动场景友好：发送者不维护接收者名单，断连设备回来后可从持久化队列/日志**补齐**（利用 10-协调与协定.md 的可靠组播与 13-复制.md 的日志思路）。
- **离线操作 + 冲突协调**：离线期间本地更新，重连时按版本向量（09-名称服务与全局状态.md）比较、自动合并或人工协调——Dynamo/CRDT 的离线优先应用正是这条线的延长线。
- **访问低带宽网络**：代理/网关做协议转换与内容过滤（图片降采样、字段裁剪）；缓存与预取按「再连接成本」调度。
- 🔧 教科书时代用「代理（proxy/gateway）」做协议与带宽适配；今天对应物是边缘节点与 CDN 边缘函数。

### 与物理世界集成（书中「物理集成」主题）

- **智能空间（smart space）**：房间级的服务组合随人员进出动态重建；安全模型从「固定边界」变为「临时信任」。
- **能量管理**：通信调度（批量收发、监听休眠占空比）成为协议设计目标——IoT 时代 BLE/802.15.4 的 sleepy end device 全套继承。
- 🔧 位置隐私：上下文感知收集轨迹，匿名化与最小化收集原则在书中已有前瞻讨论。

### 算法走查（教学示意，不参与构建）

**走查 1：发现协议生命周期（以租赁为核心）**

```text
服务 S 上线:
  向发现服务注册 (类型, 属性, 地址, lease=300s)
  每 300s 前刷新租约（心跳）
客户端 C:
  查询 (类型 = 打印机, 属性: 双面) → 得到匹配项列表
  选中一项, 直接与 S 通信（不经发现服务）
S 崩溃:
  不刷新 → 租约到期 → 发现服务自动注销
  客户端侧: 通信失败后重新查询（发现结果永远可能过期）
```

- 租约时长的权衡：太短 → 心跳风暴与误注销；太长 → 幽灵服务滞留。Kubernetes 的 lease 对象（默认续约窗口数十秒）是同一权衡的当代取值参考。

**走查 2：离线合并（版本向量比较）**

```text
离线期间: 设备 A 修改记录 r → 本地版本 r@A:[2,0]
设备 B 同时修改 r         → 本地版本 r@B:[0,2]
重连时交换版本向量:
  [2,0] 与 [0,2] 互不支配 → 并发修改 → 冲突
  策略: 数据类型可交换（计数器 add）→ 自动合并
        文本（协同编辑）→ CRDT 合并算法
        业务语义（如状态机）→ 弹窗人工协调
合并后: r@[2,2] 双方收敛
```

- 与 13-复制.md 的 gossip 合并、09-名称服务与全局状态.md 的向量时钟判定是同一套机制的三次出场。

**走查 3：mDNS/DNS-SD 发现一条记录**

```text
组播查询: _airplay._tcp.local PTR?
应答: PTR _airplay._tcp.local → 客厅电视._airplay._tcp.local
      SRV 客厅电视... → 192.168.1.7:7000
      TXT 客厅电视... → (设备能力键值对)
```

- 组播范围限于链路本地（TTL=1 跳），用 DNS 语法复用缓存/轮询语义——「发现服务四要素」的现代极简实现。

### 自测问答（教学自用）

- **Q：发现协议为什么要「租赁」而不是「心跳注销」？** 设备可能断电/走远而无法主动注销——租约把「失效判定」的权利交给发现服务一侧，故障时自动回收；心跳只是续租手段。
- **Q：UPnP 用组播宣告，为什么大网络里不可扩展？** SSDP 的 NOTIFY/SEARCH 在二层泛洪，设备数×搜索频率线性放大组播流量；mDNS 同理限制在链路本地——规模化的发现必须换成目录服务（单播查询 + 缓存）。
- **Q：离线优先应用的「会话保证」指什么？** Terry 的 session guarantees（read-your-writes、monotonic reads 等）：在同一个客户端会话内，即使后端是最终一致副本，也保证看不见「自己刚写完又被回滚」的时间倒流——实现只需要客户端携带最新版本号向量。
- **Q：能量约束如何影响协议设计？** 把「随时可通信」改成「批量 + 占空比」：MQTT keepalive 周期、BLE connection interval 本质都是让射频休眠；协议层的每次重试风暴都是电池杀手。
- **Q：Jini「下载代理对象」的安全问题是什么？** 客户端执行不可信代码——移动代码模型在今天的对应物（浏览器 JS、OTA 插件）用沙箱/签名解决，Jini 时代的答案（类加载校验）已不足够。

### 工程易错清单

- 「在线/离线」是信号不是布尔量：弱网（2G 级延迟）比断连更常见也更伤协议，重试策略要按延迟分档。
- 发现服务的查询结果必须带过期时间戳：缓存「刚才找到的服务」超过租约期就是事故来源。
- 推送通道（长连接）在移动 OS 上不可假设常驻：后台限制会杀连接，消息必须经服务端排队补投。
- 离线期间的本地时钟不可信（用户可改）：离线数据的「时间顺序」要用逻辑时钟/版本号，不要用设备墙钟排序。
- IoT 固件更新与配置下发要走「断点续传 + 签名」：易失网络里大文件传输按普通 TCP 传必失败。
- 隐私合规从协议层做起：发现广播里的字段（设备名/序列号）会泄露用户身份，BLE/Matter 均引入了地址随机化。

## 近年研究与工业界开源实践（2015–2026）

- **IoT 协议栈定型**：MQTT（发布订阅 + QoS 等级，完美对应「易失性通信」）、CoAP（UDP + 可观察资源）取代 UPnP/SOAP 成为物联网主流；标准化由 OASIS/IETF 推进。
- **离线优先与 CRDT**：本地先行、异步合并的移动数据库（自动合并的 CRDT 实现）成为移动端标配思路。
- **发现与配对标准化**：Apple 的 Bonjour/mDNS、Google Fast Pair、Matter/Thread（智能家居，基于 mDNS + 证书配对）——发现服务从「找打印服务」进化为「安全设备入网」。
- **边缘计算**：云-边协同把「代理/网关适配」思想放大为架构层级；低延迟与数据主权双驱动。
- **工业界开源**（star 数 2026-09 实测）：
  - `eclipse-mosquitto/mosquitto`（11221★）：轻量 MQTT broker，易失性通信的教学级实现样本。
  - `emqx/emqx`（16756★）：大规模 MQTT 集群（百万级连接）。
  - `nats-io/nats-server`（20771★）：发布订阅 + 请求回复的极简消息系统，移动/边缘场景常用。
  - Kubernetes（`kubernetes/kubernetes`，127994★）：边缘发行版（K3s 等）把发现、租赁（lease）、健康检查按本书模型规模化。
- **研究侧**：移动边缘计算（MEC）的任务卸载决策、联邦学习在设备侧的通信约束、5G 网络切片对 QoS 分级的下沉。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「移动性只是网络慢一点」 | 本质是**易失性**：会话、缓存、注册信息都必须按「随时消失」设计 |
| 2 | 「发现服务靠广播就行」 | 广播在电池与规模上不可持续；租赁 + 单播查询 + 缓存目录才是常态 |
| 3 | 「离线合并是文件系统专利（Coda）」 | CRDT 与向量时钟把离线合并推广到任意数据类型 |
| 4 | 「UPnP/SOAP 是现代 IoT 的样子」 | 🔧 已被 MQTT/CoAP + JSON/CBOR 取代；书中 SOAP 控制消息一节按历史阅读 |
| 5 | 「本章与后端工程无关」 | 服务发现（DNS/Consul）、心跳租赁（K8s lease）、断线重连（Kafka 消费者 rebalance）全是本章思想的常驻后端形态 |
| 6 | 「断连重连后数据自然是新的」 | 必须显式做会话保证（read-your-writes 等）或版本比较，否则静默回退 |
