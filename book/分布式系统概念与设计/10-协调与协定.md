# 10 协调与协定（第 15 章 协调和协定）

> **本章地图**：可靠的组通信（基本组播/可靠组播、FIFO/因果/全序三种有序性、IP 组播之上的可靠性补齐）→ **虚拟同步**与 ISIS（视图变更与消息交付的一致性）→ **拜占庭将军问题**（口头消息 vs 签名消息、3m+1 门限、交互一致性）→ 失败检测器（Completeness/Accuracy 两轴、四种强度）→ **分布式互斥与选举**（中心协调者、令牌环、Lamport 时间戳算法；环选举、霸道算法 bully）→ **共识问题**与 **FLP 不可能定理** → **Paxos**（角色、两阶段、多数派相交）及其工程形态。

## 本章地图

本章是全书「算法密度」最高的一章：一组副本要就「消息顺序」「谁当主」「下一个值是什么」达成**协定（agreement）**，而失败与网络分区让这不可能轻易做到。可靠组播解决「大家都要收到」，有序组播解决「按同样顺序收到」，拜占庭协议解决「有人撒谎也能定」，共识与 Paxos 解决「异步+崩溃也能定」。它是 13-复制.md 全部副本协议的理论内核，也是理解 etcd/ZooKeeper/Kafka 等一切「协调服务」的概念字典。

## 核心精讲

> 以下伪代码与例子均为**教学示意，不参与构建**。

### 组播的可靠性与有序性

- **可靠性定义**：correct 进程组播的消息，所有 correct 进程终将收到（对崩溃容错：崩溃者的消息也要尽力送达）。
- **三种有序性**（从弱到强）：
  1. **FIFO**：同一发送者的消息按发送序送达；
  2. **因果序**：若 send(m1) → send(m2)，所有进程先 m1 后 m2；
  3. **全序（total order）**：所有 correct 进程以**相同顺序**收到所有消息（不管与发送序是否一致）。
- 🔧 关键直觉：全序 ≠ FIFO ≠ 因果，三种性质两两独立；状态机复制需要的是「FIFO + 全序」。
- IP 组播只提供「尽力而为」：可靠组播靠**否定确认（NACK）+ 补发**补齐丢失，有序性靠保留缓冲区 + 延迟交付（hold-back queue）实现。
- 实现套路：
  1. **定序者（sequencer）**：中心进程给消息编号，简单但定序者本身要容错；
  2. **ISIS 风格否决式**：提案式全序——进程收到消息先广播提议位置，冲突时协商，延迟到无冲突才交付；
  3. **经共识对每批消息定序**：现代主流（Raft 日志即全序）。

### 虚拟同步（ISIS，1987）

- **组成员服务**维护**视图（view）**：当前被系统认同的成员名单；成员崩溃/加入触发视图变更。
- 核心承诺：消息交付与视图变更**同步**——所有 correct 成员都在**同一个视图内**看到同一组消息，不会有成员「换了视图还收到旧视图消息」造成分叉。
- 🔧 历史地位： ISIS 是「组通信即中间件」的起点；虚拟同步的现代继承者包括 Kafka 消费组的 rebalance、Raft 的配置变更（成员变更日志条目）。

### 拜占庭与失败模型升级

- **拜占庭将军（Lamport–Shostak–Pease, 1982）**：m 个叛徒存在时，n ≥ **3m + 1** 个将军才能用**口头消息**达成一致；带签名可把门限降为 n ≥ m + 2。
- 协议形态：OM(m)（口头消息，递归广播 n−1 轮）与 SM(m)（签名消息，一轮即可）。
- 🔧 意义：它把「失败模型」从 crash 扩展到 arbitrary（任意/恶意），奠定了后来 BFT 系统（PBFT、区块链共识）的问题定义；n ≥ 3m+1 的直觉是「2m+1 个诚实的多数必须压过 m 个叛徒加 m 个观察错误」。

### 失败检测器与互斥/选举

- **Chandra–Toueg 失败检测器**两轴四档：

  | 检测器 | 完备性 | 准确性 |
  | --- | --- | --- |
  | Perfect（P） | 不漏报 | 不误报 |
  | Eventually Perfect（◇P） | 最终不漏报 | 最终不误报 |
  | Strong（S） | 不漏报 | 允许成对误报 |
  | Eventually Strong（◇S） | 最终不漏报 | 最终有限误报 |

  异步系统中完美检测器不可实现，但 **◇P**+ 超时重试足以把 Paxos 带入「工程可行」区间。
- **分布式互斥**三件套：
  1. 中心协调者（2 条消息/次，单点）；
  2. 令牌环（轮转，延迟 O(N)，令牌丢失难检测）；
  3. Lamport 时间戳算法：请求广播带时间戳，收齐 N−1 个更高优先级应答才进入临界区，消息数 O(3(N−1))。
- **选举算法**：环选举（消息数 O(N²) 量级）、**霸道算法 bully**（最大 ID 获胜，故障恢复时接管，消息数 O(N²)）。
- 🔧 现实中多数系统直接用租约 + Raft 选主取代教科书选举——但超时风暴（false leader，两主并存窗口）问题仍是 bully 思想要面对的。

### 共识与 Paxos

- **共识问题**：n 个进程，各自 propose，最终 agree 于同一个值，且该值是某人提议的。与拜占庭协定、可靠组播可互相归约（共识 → 拜占庭协定；全序组播可用共识实现）。
- **FLP 不可能定理（Fischer–Lynch–Paterson, 1985）**：异步系统 + 哪怕一个崩溃 + 确定性共识，不存在保证终止的算法。出路：加失败检测器、加随机化、加部分同步假设。
- **Paxos（Lamport, 1998/2001）**：三类角色（proposer/acceptor/learner），两阶段：
  1. **prepare(n)**：多数派 acceptor 承诺不再接受编号 < n 的提议，并返回已接受的最大编号提议；
  2. **accept(n, v)**：v 取 prepare 阶段看到的最高编号已接受值（否则可用自己的），多数派接受后学习。
- 🔧 正确性支柱是**多数派相交**：两个 quorum 至少共享一个 acceptor，保证承诺与已接受值的继承链；这也是后续 Quorum 复制（13-复制.md）的同一数学。
- 工程形态对比：

  | 形态 | 要点 | 代表 |
  | --- | --- | --- |
  | Multi-Paxos | 稳定 leader 跳过 prepare | Chubby |
  | Raft | term + 日志复制 + 选主一体，可读性重构 | etcd、TiKV |
  | Viewstamped Replication | 视图变更与复制一体 | 1988 原始/2012 v2 |
  | ZAB | 原子广播 + 崩溃恢复两态 | ZooKeeper |

### 算法走查（教学示意，不参与构建）

**走查 1：全序组播的 hold-back 队列（ISIS 风格简化版）**

```text
收到消息 m:
  放入 hold-back 队列，广播「我建议 m 排在第 i 位」的提案
收集所有成员对 m 的提案:
  若存在顺序冲突（两个进程对同一对消息给出相反相对次序）:
    按提议者 ID 决胜，重新广播修正提案
  否则: 采纳为最终次序
交付规则:
  队首消息若已获得全组一致的最终次序且前面无待交付消息 → 交付
```

要点：消息「收到」与「交付」分离；一致性代价是每条消息一轮额外通信——这就是为什么工程上更愿意用「先共识后交付」（Raft 日志）而非「先收后议」。

**走查 2：Paxos acceptor 状态机**

```text
状态: promised_n（已承诺的最大编号）, accepted_n, accepted_v

收到 prepare(n):
  若 n > promised_n: promised_n ← n; 回复 (promised, accepted_n, accepted_v)
  否则: 拒绝（回复当前 promised_n）

收到 accept(n, v):
  若 n >= promised_n: promised_n ← n; accepted_n ← n; accepted_v ← v; 回复 accepted
  否则: 拒绝
```

不变量：acceptor **绝不**接受编号小于已承诺值的提议——这一条加上「proposer 必须继承 prepare 中看到的最高已接受值」，就排除了「两个值同时被选定」。

**走查 3：bully 选举例**

- 节点 1..5，ID 越大优先级越高；节点 5（主）崩溃，节点 3 最先发现：
  1. 节点 3 向 4、5 发 ELECTION；4、5 无响应（5 死了，4 假设死了/超时）；
  2. 节点 4 回复 I AM ALIVE（4 > 3），节点 3 退让；
  3. 节点 4 向 5 发 ELECTION，无响应 → 4 自立为主，广播 COORDINATOR；
  4. 节点 1、2 确认。若中途节点 5 复活，它向所有人发 ELECTION，群龙无主的更小 ID 全部退让——「复活即夺权」正是 bully 之名的由来，也是不稳定窗口的来源。
- 🔧 消息复杂度 O(N²) 与夺权抖动，是现代系统改用租约 + Raft 选主的直接动因。

### 共识问题的归约网络

- 共识 → 全序组播：把「选定的值」当作每轮要交付的批次（日志条目），共识序即交付序；
- 全序组播 → 共识：对「下一批消息集合」达成一致即可实现全序；
- 共识 → 拜占庭协定：把共识结果再广播校验（拜占庭条件下共识协议本身要换 BFT 变体）；
- 记忆口诀：**这三种协定在崩溃模型下互相等价，难度谱系由失败模型（crash → 拜占庭）与时间假设（同步 → 异步）决定**。

### 自测问答（教学自用）

- **Q：为什么说「可靠组播 + 全序」就能实现状态机复制？** 状态机复制只要求「所有副本以相同顺序执行相同命令」——可靠组播保证命令不丢，全序保证顺序一致；剩下唯一要处理的是视图变更与副本加入时的追赶。
- **Q：FLP 之后 Paxos 为什么是安全的？** FLP 排除的是「保证终止」；Paxos 的 prepare/accept 两阶段只承诺**安全性**（不选定两个值），活性（最终选定）交给部分同步假设——超时后换更高编号重试，理论上有「活锁」可能，实践中概率可忽略。
- **Q：拜占庭 3m+1 门限的直觉？** 要在 m 个叛徒下安全，诚实多数必须 ≥ m+1 且总数 − 诚实多数 ≥ 2m（叛徒 + 因信息滞后而「装错」的诚实节点各占 m），解得 n ≥ 3m+1；签名让诚实节点不「装错」，门限才降。
- **Q：◇P 检测器「最终正确」为什么够用？** 因为共识的活性只需要「最终存在一个稳定期，期间检测器不误报且 suspect 集合足够大」；稳定期之外可以随意犯错。
- **Q：Kafka 没有共识协议为什么近似全序？** 它把「共识」退化成「ISR 多数 ack + 单 leader 顺序写 + high watermark 截断」，在承认 leader 切换期间不可用的情况下，用更简单的协议换取吞吐——理解这一点就理解了「共识」与「复制日志」的关系。

### 工程易错清单

- 「全序」不等于「因果序」也不等于「FIFO」：测试全序组播时要专测「与发送序不同」的用例，而不是只测顺序号。
- 失败检测器的超时值没有「正确值」：它是误报率（多余切主）与漏报率（故障发现延迟）的权衡曲线，要按业务 SLA 定标并压测。
- Paxos 编号（proposal number）必须全组唯一且递增：用「轮次 + 节点 ID」拼接；两台节点用同一编号会互相抵消承诺。
- 选举成功 ≠ 安全接管：新主必须先确认「旧主的在途消息是否已交付」（租约到期 + 日志追赶），否则出现双主脑裂。
- 组成员变更和消息定序要用同一个日志（Raft 的做法）；两个独立机制（定序用 A、成员用 B）会在变更瞬间产生「谁是谁的人」的歧义。
- 拜占庭模型下「重试」本身可能被攻击者利用（重放）：消息必须带会话/轮次唯一号。
- 共识服务的吞吐不是免费的：每条日志一次多数派往返，把「不需要共识的操作」（只读租约读、本地读）识别出来旁路，是性能优化的第一课。

## 近年研究与工业界开源实践（2015–2026）

- **Raft 的胜利**（Ongaro & Ousterhout, USENIX ATC 2014）：以可理解性为设计目标，成为新系统的默认共识选择；Raft 共识层库遍地开花。
- **Multi-Raft 与分区并行**：TiKV、CockroachDB 把数千个 Raft 组跑在同一进程池上（见 13-复制.md）。
- **共识的再优化**：EPaxos（SOSP 2013，无 leader、命令相关时才冲突处理）、Flexible Paxos（放宽 quorum 相交条件）、Vertical Paxos；拜占庭方向 PBFT → HotStuff（PODC 2019 三阶段链式 BFT，成为区块链 BFT 共识骨架）。
- **Jepsen 实证**（`jepsen-io/jepsen`，7505★）：对 ZooKeeper、etcd、consul 等的分布式黑盒测试反复发现「声称线性一致实则否则」的问题——教科书协定性质必须靠实证验证而非声明。
- **工业界开源**（star 数 2026-09 实测）：
  - `etcd-io/etcd`（52310★）：Raft 参考实现，Kubernetes 的大脑。
  - `apache/zookeeper`（12811★）：ZAB 协议（类 Paxos 的原子广播），本书「全序组播 + 主备」思想的活化石。
  - `hashicorp/consul`（30082★）：Raft + LAN/WAN gossip，把「组通信」做成产品。
  - `pingcap/tidb`（40588★）：TiKV 内嵌 Multi-Raft，教学上最适合读的工业级共识代码之一。
  - `apache/kafka`（33839★）：以 ISR + 高水位（high watermark）实现「非拜占庭近似全序」的日志复制，是理解「共识工程折衷」的另一入口。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「全序组播可由 Lamport 时钟直接得到」 | 教科书方案需要知道「所有 N 个进程的消息都到齐」的终止判定；工程上由共识/定序者完成 |
| 2 | 「拜占庭容错就是共识」 | 拜占庭协定在同步+签名下可解；异步+拜占庭+随机化是另一谱系，门限不同（n ≥ 3m+1） |
| 3 | 「FLP 说明共识做不了」 | FLP 只排除「确定性 + 保证终止」；部分同步（超时）与随机化两条路都绕开了它 |
| 4 | 「Paxos = 一轮投票」 | prepare/accept 两阶段缺一不可；多数派相交与「继承已接受值」是安全性的全部来源 |
| 5 | 「互斥算法现成可用」 | 教科书互斥消息成本 O(N)；现代实现要么单点 Raft 组，要么租约，绝不用分布式令牌环 |
| 6 | 🔧 本书未覆盖 | Raft 的选主与日志匹配不变量、Viewstamped Replication v2、EPaxos/Flexible Paxos、HotStuff 与 BFT 链；ISIS 只作历史背景，虚拟同步的现代继承者是成员变更 + 日志复制 |
