# 15 分布式多媒体系统（第 20 章 分布式多媒体系统）

> **本章地图**：多媒体数据的特征（数据量大、实时性、时间连续性、多数据流同步）→ **QoS（服务质量）**：参数化（带宽/延迟/抖动/丢失率）、协商与降级协商 → **资源管理**：准入控制、CPU/内存/网络的资源保留（RSVP 思想）与处理器/磁盘调度 → **流适配**：过滤（filtering）、可伸缩编码、按带宽降级 → 应用层组播与实时传输（RTP/RTCP、RTSP）→ 案例研究：Tiger 视频文件服务器（条带化 + 调度 + 容错）。

## 本章地图

多媒体流（音/视频）与「尽力而为」的数据传输天然冲突：它需要**有界的延迟与抖动**、容忍**少量丢失**、追求**带宽自适应**。本章给出 QoS 的形式化（把「流畅」翻译成可协商的参数）、资源管理的机制（保留/准入/调度），以及流适配的工程手段；第 5 版以 Tiger 视频文件服务器作收束案例。RDMA 网络与 WebRTC 时代，这套「QoS 语言」仍是流媒体与实时通信系统的骨架。

## 核心精讲

> 以下伪代码、表格均为**教学示意，不参与构建**。

### 多媒体数据的特征

- **大而实时**：原始视频（无压缩）每秒可达数百 Mbps；端到端延迟超过 ~150ms 对话即明显不适（ITU-T G.114 语境）。
- **时间依赖**：媒体元素有「内在时间线」；多流之间需要**同步**（唇音同步 lip-sync，音视频偏差一般要求 < ~80ms 级）。
- **容错观不同**：丢帧可以接受（可容忍丢失），重传反而有害（迟到 = 无用）——与 TCP 的可靠有序传输目标相反。
- 数据流的元信息（采样率、帧率、压缩格式）本身要随流传输——「流描述」也是协议的一部分。

### QoS 管理三件事

- **参数化**：QoS 用四元组描述，典型目标档位：

  | 参数 | 低档（语音通话可接受） | 高档（点播影院级） |
  | --- | --- | --- |
  | 带宽 | ~30 kbps（压缩语音） | 数 Mbps（高清视频） |
  | 端到端延迟 | < 150 ms | 秒级即可 |
  | 抖动 | < 几十 ms（缓冲吸收） | 秒级缓冲无所谓 |
  | 丢失率 | 可容忍少量（PLC 补偿） | 近零（重传可用） |

- **协商（negotiation）**：应用 → 系统 → 网络逐层申报与讨价还价；可能被**降级协商（renegotiation）**，如网络拥塞时从 30fps 降到 15fps。
- **准入控制（admission control）**：新流能否接受取决于「已有流的保留是否会被破坏」——类似数据库的锁冲突检测，只是对象换成资源预算。

### 资源管理与调度

- **保留（reservation）**：网络层 RSVP（接收端驱动的资源保留协议，RFC 2205 一族）沿路径保留带宽；端系统保留 CPU/内存/磁盘带宽。
- **处理器调度**：媒体线程需要**实时调度**（速率单调 RM/最早截止期优先 EDF）而非分时轮转；书中强调「调度算法必须支持每流 CPU 份额保证」。
- **流适配（adaptation）**：**过滤（filtering）**——在网络中间节点丢弃高分辨率增强层（需编码配合分层）；发送端根据 RTCP 反馈（丢包率/抖动）动态调码率。
- 🔧 教科书的设计（中间节点有感知地丢数据）要求网络「聪明」；互联网选择了另一条路——**端到端自适应**（应用层自适应码率，见下 2026 视角），IntServ/RSVP 全网保留最终只在专网存活。

### 实时传输协议层

- **RTP（RFC 3550）**：时间戳 + 序列号 + 载荷类型，跑在 UDP 上；**RTCP** 传接收质量反馈（发送者据此适配）。
- **RTSP**：流控制（播放/暂停/快进），与 RTP 数据通道分离。
- 组播分发：本书写作时依赖 IP 组播；其后被**应用层组播**（CDN 分发树、P2P 流）取代。

### 案例研究：Tiger 视频文件服务器（第 5 版收束案例）

- 面向「点播影院」负载：大量并发点播少量热门影片。
- **条带化（striping）**：每部影片按时间片（block）轮转切到多块磁盘/多个节点；播放时各盘轮流供块，单盘只承担 1/N 的持续读带宽。
- **调度**：按「轮（round）」组织读盘与发送；新流只在轮边界插入，错过本轮等下一轮——把「实时调度」简化为「班车时刻表」。
- **容错**：奇偶校验块（类 RAID5）跨节点分布，单盘失效用其余块重建播放流。
- 🔧 设计哲学与 GFS 同款：负载特化（恒定码率、顺序读）换来极简机制——案例教学的价值在「特化」二字。

### 算法走查（教学示意，不参与构建）

**走查 1：RTP 头的关键字段**

| 字段 | 作用 | 接收端用法 |
| --- | --- | --- |
| sequence number | 包序 | 检测丢包（序号空洞）、乱序重排 |
| timestamp | 采样时刻 | 抖动计算、流间同步（与 RTCP SR 关联） |
| payload type | 编码格式 | 动态切换编码（适配的信号通道） |
| SSRC | 流标识 | 多流复用/换源检测 |

- 接收端用序号 + 时间戳估计网络状态 → 经 RTCP 接收者报告（fraction lost、jitter）反馈发送端 → 发送端调码率——闭环三步。

**走查 2：Tiger 式「班车」调度**

```text
影片 F 按播放时长切成等长块, 轮转条带分布到磁盘 D1..Dk
一轮（round）= 播放一帧块的时间 T
每轮开始: 每个活跃流读一块（只从自己当前负责的盘）
轮末: 网络发送本轮数据
新流加入: 只在轮边界插入, 第一轮先取齐「缓冲前置量」
单盘失效: 该盘承担的块由奇偶校验盘 + 其余盘重建（容忍 1 盘失效）
```

- 关键简化：所有流等速（CBR）→ 调度退化为排班表，无需优先级抢占——「负载特化」换来机制极简的范本。

**走查 3：端到端自适应码率（ABR）**

```text
播放器维护:
  带宽估计 E（滑动平均最近分片下载速率）
  缓冲水位 B（秒）
选择下一分片码率:
  E 高 & B 高 → 升档; E 低或 B 低 → 降档（宁可画质降，不可卡顿）
  切换在「分片边界」进行 → 无需中间网络节点配合
```

- 对比书中的「网络内过滤」：ABR 把智能从网络搬回端系统，牺牲一点收敛速度换取全网可部署——IntServ 与端到端哲学之争的胜负手。

### 自测问答（教学自用）

- **Q：为什么 RTP 建在 UDP 上而不是 TCP？** 重传的旧帧已无价值、队头延迟致命；RTP 用序号让「丢包」变成显式信息（FEC/PLC 用它补偿），时间戳让「何时播放」与「何时到达」解耦——面向实时，宁丢勿迟。
- **Q：准入控制和拥塞控制是一回事吗？** 不是。准入控制在**新流进入时**拒绝（静态容量判定），拥塞控制在**运行中**适应（动态反馈）；互联网只做后者，所以实时应用必须自带自适应。
- **Q：唇音同步为什么不需要全网统一时钟？** 只需两条流共享同一 RTP 时间轴（同一 SSRC 系或 RTCP SR 关联），接收端对齐相对偏移即可——绝对钟差是常数项，可消去。
- **Q：Tiger 案例的「等下一轮」会引入多少延迟？** 最坏一个整轮时间 T（典型亚秒级），换来了零抢占、零优先级反转的确定性调度——延迟上界可计算是媒体服务器的第一设计目标。
- **Q：分层编码（可伸缩视频）为什么在当年没火、现在又活了？** 当年网络中间节点不做「智能丢层」，端到端 ABR 不需要分层；如今 WebRTC SVC/AV1 分层又成主流——因为 SFU（转发服务器）扮演了当年「过滤路由器」的角色，只是它部署在应用层。

### 工程易错清单

- 抖动缓冲是自适应的：固定大缓冲保平滑但加延迟（交互场景不可接受），固定小缓冲省延迟但频繁欠载——现代播放器动态调整，别写死。
- 时间戳单位错误是 RTP 实现第一 bug 源（视频 90kHz、音频 48kHz 各不相同）：跨流同步前先统一换算。
- 「丢包率低」不等于「体验好」：关键帧丢失的连锁（直到下个 I 帧）比均匀丢包伤害大得多，FEC/关键帧保护要按帧类型分配。
- 直播延迟的分层预算：采集→编码→打包→传输→缓冲→解码，每段都有下限；宣传「亚秒延迟」的产品先问它砍了哪段缓冲。
- 服务器端转码是「资源保留」的现代形态：GPU 池按流预留，超卖就会抖动——准入控制思想没过时，只是对象换了。
- 多媒体流量做拥塞退让（ responding to ECN/loss）是互联网礼仪：不退让的自适应流会挤压自己与他人。

## 近年研究与工业界开源实践（2015–2026）

- **WebRTC**（W3C/IETF，2011–2021 定型）：RTP 思想 + 拥塞控制（GCC/transport-cc）+ SDP 协商的浏览器标准，实时通信民主化；QUIC（HTTP/3 底座）把「UDP + 应用层控制」哲学推广到通用传输。
- **自适应码率（ABR）**：HLS/DASH 把「过滤」改造成「多码率切片 + 客户端择优」；ABR 算法（BBA、Pensieve/强化学习）成为研究热点。
- **工业界开源**（star 数 2026-09 实测）：
  - `FFmpeg/FFmpeg`（64518★）：编解码/转码事实标准，资源管理与分层编码的底层引擎。
  - `videojs/video.js`（39899★）、`livekit/livekit`（21115★）：播放器与 WebRTC SFU，对应本书「流适配 + QoS 反馈」的现代栈。
  - `GStreamer/gstreamer`（3324★）：管线式多媒体框架，最接近书中「过滤/适配」组件模型的开源实现。
  - `webtorrent/webtorrent`（31420★）：浏览器内 P2P 流媒体——应用层组播的当代标本（另见 17-对等系统与设计案例.md）。
- **研究侧**：低延迟直播协议（SRT/LL-HLS）的延迟-抖动折衷、边缘转码与按需性价比、生成式视频的传输与缓存新问题。
