## 核心精讲（教学示意，不参与构建）

### 12.1 设计挑战
- 透明性（访问/位置/移动）、性能（缓存命中与一致性折中）、可伸缩性（服务器负载、
  网络瓶颈）、容错（服务器崩溃后的语义）、一致性（多客户端并发读写同一文件）。

### 12.2 案例：Sun NFS
- **架构**：VFS（虚拟文件系统）本地层 + v-node 抽象 + NFS 客户端模块 + RPC 到远程文件服务
  （mount 协议挂载根目录 → 文件句柄 file handle 引用远程文件/目录）。
- **NFS v2/v3 协议**（Flat file service + lookup 过程，原书逐过程讲解）：
  - **无状态服务器**：每个请求自包含（文件句柄 + 偏移），服务器不保存会话——崩溃后
    客户端重试即可，实现简单、可伸缩性好；
  - **幂等操作**：多数过程可安全重发；**at-least-once + 幂等 = 崩溃透明**，
    是第 5 章「调用语义」的最佳落地样本；
  - **缓存一致性弱点**：客户端缓存块 + 属性缓存（acregmax/acdirmax，默认 3–60s），
    只保证「有限时间的陈旧」——**会话语义近似而非强一致**；服务器缓存写回（v3 异步写）。
- **NFS v4**：转向**有状态**（委托 delegation、锁与租约、复合过程、强一致方向移动、
  集成安全 ACL），回答了 v2/v3 的一致性与安全批评。
- 🔧 原始论文：Sandberg et al. 1985（见下表）——「简单协议 + 幂等 + 无状态」三件套
  至今是 RPC 服务设计的教科书答案。

### 12.3 案例：AFS（Andrew File System）
- **设计目标**：可伸缩性优先（原书案例面向 Carnegie Mellon 校园网全校师生）。
- **核心机制**：
  - **整文件缓存**：文件（或 chunk）整体复制到客户端磁盘，重复访问走本地；
  - **回调承诺（callback promise）**：服务器记录「哪些客户持有有效缓存」，文件变更时
    主动回调作废——**回调失效而非每次校验**，把读路径的网络开销降到接近零；
  - **会话语义**：读旧值/写提交后可见，介于 NFS 的弱缓存一致与真正的强一致之间。
- **可伸缩性论证**（原书数据分析）：负载测量显示典型文件访问呈强局部性
  （绝大多数访问命中本地缓存），服务器瓶颈在「打开/关闭」而非读写——整文件缓存把
  服务器负载从「每块 IO」降为「每会话」，这是 AFS 扩到数千节点的根本原因。
- **后续**：Coda（AFS 后继，加入离线操作与服务器复制，AVSG/VSG 概念）——复制章（后半
  目录）的经典案例。

### 12.4 复制与最新设计（原书展望节 + 摘录 DSM 线索）
- 原书「最新设计」以 GFS 类架构开头：**元数据与数据分离、单一主节点、chunk 复制、
  弱一致性以换吞吐**——为第 21 章 Google 案例伏笔。
- DSM（分布式共享内存）：以「共享地址空间假象」呈现分布式内存，一致性与页错误是核心问题；
  摘录关键词「DSM/持久对象存储」即此，原书在第 5 版将其压缩，细节可循英文版独立章。

### 12.5 NFS 协议过程速查（v2/v3 核心，照原书分类）
| 过程 | 作用 | 幂等? |
| --- | --- | --- |
| lookup(dirfh, name) | 目录句柄 + 文件名 → 文件句柄+属性 | 是 |
| create/mkdir/remove/rmdir | 目录项操作 | 是（语义幂等） |
| read(fh, offset, count) / write(...) | 按偏移读写 | 是（偏移显式） |
| getattr / setattr | 属性读写 | 是 |
| 其他（rename 等） | 个别非幂等（如 rename 到已存在目标） | 视情况 |
- 要点：**除「打开文件的状态类操作」外，几乎所有过程显式带偏移/句柄**，这使重发安全、
  服务器可无状态——AFS 作者评价 NFS 的成功一半来自「协议设计克制」。
- 🔧 v4 的变化即「有状态化」：open/close、委托（delegation）、锁租约，全部以**服务器状态**
  换语义强度——故障恢复从「重发就行」变成「状态回收协议」（grace period）。

### 12.6 NFS vs AFS 一致性/性能对照（教学重述）
| 维度 | NFS v2/v3 | AFS |
| --- | --- | --- |
| 缓存单位 | 块（8KB 级） | 整文件（或大 chunk） |
| 一致性 | 属性缓存超时（秒级陈旧） | 回调失效（会话语义） |
| 读路径 | 每块都可能上网络（缓存过期后） | 命中即本地磁盘 |
| 写路径 | 直写/异步写回服务器 | 关闭时整文件回传 |
| 故障模型 | 服务器崩溃透明（无状态+重试） | 回调记录丢失需全量重建 |
| 可伸缩性瓶颈 | 服务器每块 IO | 回调记录与并发写同一文件 |
- 🔧 记忆锚点：NFS 把一致性当作**性能税**（缓存时间短点就一致点），AFS 把性能当作
  **一致性妥协的回报**（会话内自由，关闭时结算）——云盘同步（Dropbox/OneDrive）是 AFS
  直系后裔，NAS/NFSv4 是 NFS 直系后裔。

### 12.7 工作例题：AFS 回调失效的时间线（教学重述）
1. 客户 C1 打开文件 f → 服务器发回整文件 + 回调承诺，C1 缓存；
2. C1 反复读 f：全部本地命中（零网络）；
3. 客户 C2 修改 f 并关闭 → 服务器向所有持回调者（C1）发失效消息，作废其缓存；
4. C1 下次读 f：缓存已作废 → 重新从服务器取新版本。
- 失效消息丢失（网络分区）怎么办：C1 重连时**主动向服务器验证回调是否仍有效**
  （重连即全量验证）——这就是「回调协议」的容错条款，也是 AFS 实现复杂度集中点。

## 近年研究与工业界开源实践（2015–2026）

- `apache/hadoop`（15670★）：HDFS，GFS 的开源实现；社区重心已迁出，
  但「NameNode/EditLog/SecondaryNN」仍是元数据高可用的反面教材库。
- `ceph/ceph`（17073★）：CRUSH 算法去除中心元数据服务器，CephFS 提供 POSIX 语义。
- `juicedata/juicefs`（14469★）：云原生 POSIX FS（Redis 等元数据引擎 + S3 数据层），
  是「AFS 整文件缓存思想 + 对象存储」的当代合成体。

### 12.8 复制与容错的文件系统视角（Coda 概要 + 与后半目录的桥）
- **Coda**（AFS 后继）的三个关键词：
  1. **VSG/AVSG**（卷的可用服务器组）：逻辑上「全部副本」vs 当前可达副本集合；
  2. **乐观复制**：分区期间允许读写 AVSG 副本，重连后按 COPS 冲突规则协调
     （文件级/目录级版本向量）——冲突可能需人工合并；
  3. **客户端持久缓存**：断连操作（disconnected operation）=「把 AFS 的会话语义推到极限」。
- 与第 18 章（复制，后半目录 [13-复制.md](13-复制.md)）的关系：文件系统用**版本向量 +
  应用级合并**简化了通用复制问题；通用化的「主动/被动复制、quorum」在那章展开。
- 🔧 2026 映射：Git 的分支/合并、CRDT 协同编辑、云盘冲突副本（「-冲突」文件）都是
  Coda 乐观复制思想的变体——「离线优先」从未过时，只是换了载体。

### 12.9 选型速查：什么时候用什么（2026 工程视角）
| 场景 | 适配方案 | 理由 |
| --- | --- | --- |
| 企业共享挂载（Office 文档等） | NFSv4.2 / SMB / 云 NFS | POSIX 语义 + 权限模型成熟 |
| 数据湖/AI 训练数据 | 对象存储（S3） + 缓存层 | 吞吐与成本，容忍最终一致 |
| 云上容器持久卷 | CephFS / JuiceFS / 云盘 | POSIX + 横向扩展 |
| 超大规模内部存储 | Colossus 类（自研） | 元数据分布式化、快速恢复 |
- 读法：原书两个案例给出「极点」，现实选型在极点连线上按**一致性需求 × 元数据规模 × 成本**
  定位。

## 版本演进
- 🔧 **NFS 依然活着**：NFSv4.2 与云 NFS 服务（EFS/Filestore）承接企业挂载场景；
  教学顺序建议「先 NFS（协议极简）→ AFS（一致性工程）→ GFS（规模极简）→ 对象存储（语义重构）」。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「NFS 不缓存所以没有一致性问题」 | NFS 有客户端缓存（属性+数据），只是没有强一致协议；acregmax 时间内可见陈旧数据 |
| 2 | 「AFS 回调 = 分布式缓存失效协议可无限扩展」 | 服务器要维护回调记录，断连（分区）期间回调不可达 → 重连时的缓存验证是 AFS 复杂度来源 |
| 3 | 「无状态服务器一定更好」 | 无状态换来崩溃透明与简单性，代价是一致性弱、锁/委托难以支持——NFS v4 反向修正即为证明 |
| 4 | 「GFS 适合通用文件系统场景」 | GFS 假设大文件、顺序读写、追加为主、应用容忍异常重复记录；这些假设迁移失败正是 MapReduce 时代后对象存储崛起的原因之一 |
| 5 | 🔧 本书未覆盖 | Colossus、HDFS Federation 与 RBF、对象存储（S3/MinIO）、JuiceFS/CephFS、纠删码替代三副本 |
| 6 | 🔧 版次注记 | 摘录中「DSM」在英文版第 5 版为独立章，中译版并入本章展望；后半助手任务清单的「分布式共享内存」对应此章 |
| 7 | 「缓存一致性可以靠时间戳 TTL 做到正确」 | TTL 只能界定**最大陈旧窗口**，不提供写后读保证；需要更强保证时要么回调（AFS）、要么租约+版本号（v4 委托）、要么应用层妥协 |
