# 12 分布式事务（第 17 章 分布式事务）

> **本章地图**：扁平分布式事务与嵌套分布式事务的界面 → **两阶段提交协议 2PC**（vote-request / vote / commit / abort 四类消息、协调者与参与者状态机、不确定期、双方的超时路径）→ 协议性能与**通信/日志/只读事务优化** → **三阶段提交 3PC**（pre-commit、Skeen 模型、分区不安全）→ 网络分区下的抉择（原子性 vs 可用性）→ **分布式死锁**（全局 wait-for 图、路径推送/边追逐检测）→ **TP Monitor 与事务上下文**（X/Open DTP、XA 接口）。

## 本章地图

第 11 章解决了「并发正确」，本章解决「**要么都做、要么都不做**」：一个事务的操作分散在多台服务器上，任何一台崩溃、任何一条线路中断，都不能造成「部分提交」。2PC 用一轮投票 + 一轮决定完成这件事，代价是**不确定期**（uncertain period）里参与者的锁要一直持有。3PC 试图消除协调者单点阻塞，代价是更多轮次且在分区下不安全。TP Monitor 则是把这些协议做成中间件的工业形态。中译本第 17 章还包含**分布式死锁**一节——多台服务器各自的 wait-for 图拼不出全局环，需要专门的检测协议。

## 核心精讲

> 以下伪代码、状态表均为**教学示意，不参与构建**。

### 扁平与嵌套分布式事务

- **扁平**：客户端的事务请求经 RPC 打到多台服务器，任一服务器可成为协调者（通常是第一个被访问者或专门协调服务）。
- **嵌套**：子事务本身又是分布式事务；子事务的提交要靠其内部 2PC，父事务靠子事务结果决定——层层叠加，恢复语义复杂（本书以模型介绍为主，工程落地极少）。
- 🔧 嵌套分布式事务的现代遗存：Temporal/Cadence 的工作流树（活动即子事务，持久化执行历史）；跨服务的 Saga 树形编排。

### 17.2 两阶段提交（2PC）

- 阶段一（voting）：协调者发 **vote-request**；每个参与者执行到「可以单方面 abort」的边界（写盘 prepare 记录），回 **vote-commit** 或 **vote-abort**。
- 阶段二（decision）：**全票 commit** → 协调者写 commit 记录、广播 **commit**；任一 abort → 广播 **abort**。
- 参与者状态机（教学示意）：

  | 阶段 | 收到 vote-request | 投 commit 后 | 收到 commit/abort |
  | --- | --- | --- | --- |
  | 动作 | 写 prepare 记录、投票 | 进入 **uncertain** | 写终态记录、释放锁、执行提交/中止 |

- **超时路径**：
  - 协调者在 voting 阶段超时 → 直接单方面 abort（此时没人投过票，安全）；
  - 参与者在 uncertain 期超时 → **不能自作主张**，只能向其他参与者「询问决定」（cooperative termination protocol）；若协调者与所有参与者同时失联，参与者**阻塞**。
- 🔧 教科书最值得记住的一句：**2PC 的提交阶段协议越少越好，因为每个协议消息都在延长锁持有时间**。书中给出两个优化：
  1. 只读事务不进入投票（协调者知道它无写集，直接不要求其表决、不期待其 ack）；
  2. 「一票否决即先行中止」：任一参与者投 abort，协调者可立即广播 abort 而不必等齐（early abort）；
  3. prepare 记录与 undo/redo 日志合并写盘，减少一轮 fsync。
- **为什么投票不能省**：任何参与者在不知道「别人投了什么」时单方面提交，就可能在别人中止时违反原子性——「两阶段」的最小性。

### 17.3 三阶段提交（3PC）

- Skeen（1981）：在 vote 与 commit 之间插入 **pre-commit** 阶段；所有参与者先确认「大家都准备提交」再执行提交。三态：abort → pre-commit → commit。
- 好处：参与者在 pre-commit 后即使协调者崩溃，也能凭其他参与者状态**推断出决定**（不再无限阻塞）——只要还能联系到任一参与者。
- 代价：多一轮消息；**网络分区下不安全**（分属两侧的参与者可能各自推进到不同状态）。🔧 现代实践几乎不用 3PC：分区概率与后果都被接受为「用 Paxos 组复制协调者状态」的理由，而不是用 3PC。

### 分区与一致性的取舍

- 分区时若坚持原子性：跨区事务必须中止 → 可用性受损；若允许各自提交：违反单副本一致性。这是 CAP 在事务协议上的具体显形。
- 🔧 教科书立场（保原子性优先）在 2005–2012 被两股潮流修正：**Google Percolator**（接受短暂不一致换可用性）与 **Paxos 组替代协调者单点**（阻塞消失因为协调者不单点）。

### 分布式死锁

- 各服务器只持有局部 wait-for 图：环可能**跨服务器**存在，局部检测永远看不见。
- 两类经典检测协议：
  - **路径推送（path-pushing）**：服务器周期性把局部 wait-for 图推给所有可能相关的服务器，收方合并后再找环；
  - **边追逐（edge-chasing）**：沿等待边转发探针（probe），探针回到发起者即证明有环；用 Lamport 时间戳可判「真实死锁」与「假死锁」（过期信息）。
- 🔧 工程现实：全局死锁检测的通信成本高，主流分布式数据库用「锁等待超时 + 中心化死锁检测器」（如 TiDB 的全局死锁检测服务）或干脆按时间戳预防。

### TP Monitor 与事务上下文

- X/Open DTP 模型：AP（应用程序）—TM（事务管理器）—RM（资源管理器），**XA 接口**把 prepare/commit 以标准方式插进 RM。
- TP Monitor（CICS、Tuxedo 一脉）的职责：事务路由、连接/线程池、持久队列、负载均衡。
- 🔧 现代继承者：JTA/JTS、消息队列的事务消息（RocketMQ 半消息）、微服务分布式事务框架（Seata/Dtm）与编排工作流（Temporal）——协议内核仍是 2PC 或其补偿变体。

### 算法走查（教学示意，不参与构建）

**走查 1：2PC 双方状态机**

```text
协调者 Co:
  发 vote-request 给所有参与者 → 等待
  超时（voting 期内）        → 写 abort 记录, 广播 abort
  收齐: 全 commit            → 写 commit 记录, 广播 commit
       至少一个 abort        → 写 abort 记录, 广播 abort（可早停）

参与者 P:
  收 vote-request → 执行到临界点, 写 prepare 记录（含 undo/redo）
    投 commit → 进入 uncertain, 等待决定
    投 abort  → 本地中止, 结束
  等待决定超时（uncertain 期）:
    → 进入 cooperative termination: 询问其他参与者
      有人知道决定 → 采纳
      全都失联     → 阻塞（这是 2PC 的原罪）
```

- 走查要点：**prepare 记录落盘发生在投票之前**——投票即承诺，承诺的前提是「无论之后谁崩溃，我都能按决定完成或回滚」。
- 消息/日志次数：2 次消息轮 + 3 次（协调者决策、参与者终态）关键 fsync——工程上各种「省一次 fsync」的优化都围绕这条基线。

**走查 2：3PC 为什么分区不安全（反例）**

- 参与者 A、B 都到了 pre-commit；A 与协调者同区，B 被隔离；
- 协调者崩溃；A 侧推断「可以 commit」继续提交；B 侧联系不上任何人且已过 pre-commit——若 B 侧同时有旧信息认为「可能要 abort」，两侧分道扬镳，原子性破坏。
- 3PC 只在「崩溃但不分区」的假设下非阻塞——这个假设在真实网络里不成立，故被 Paxos 复制协调者取代。

**走查 3：边追逐死锁检测**

```text
服务器 Si 上: 事务 T1 等待 T2 持有的锁 → 局部边 T1 → T2
若 T2 的锁由远端事务持有: 向该服务器转发探针 (发起者=T1, 途经=T2, 目标=T2 所在服务器)
目标服务器上: 探针到达时若 T2 正在等待 T3:
  记录「T1 经 T2 等待 T3」
  若 T3 == T1 → 探针回到发起者 → 宣告死锁
  否则继续转发
用 Lamport 时间戳挑选牺牲者: 沿途记录时间戳, 回环中时间戳最小（最老）者被中止
```

- 假死锁来源：探针途经的服务器状态过期（等待关系已解除）——用时间戳过滤「旧边」，或等下一轮探测确认。

### 自测问答（教学自用）

- **Q：参与者在 uncertain 期为什么不干脆「回滚」？** 它可能已被记录为「投了 commit」且协调者已广播 commit 给其他参与者——单方面回滚违反原子性；uncertain 的本质是「自己的票已经可能改变世界，却不知道世界最终选了哪边」。
- **Q：为什么「投 abort 可以立即广播」而「投 commit 不行」？** abort 是一票否决（安全），commit 必须全票（一个迟到的 abort 消息可能还在路上）——单调性不对称造就了 2PC 的消息优化空间只在 abort 方向。
- **Q：只读事务怎么「逃过」2PC？** 它无写集，投不投票都不影响别人；协调者直接不等它——省一轮消息与一次锁释放延迟，是书上给的最实用优化。
- **Q：分布式死锁检测为什么会有「假死锁」？** 探针走网络有延迟，等待关系可能在探针途中消失；解法是给探针/边打时间戳，只认「发起时间晚于边建立」的路径，或等下一轮探测复核。
- **Q：Seata 的 AT 模式和 XA 差在哪？** XA 在数据库内核里锁住资源直到全局决定；AT 在应用层拦截 SQL、记录前后镜像（undo log），全局锁只锁「写冲突判定」，提交即放锁、失败靠反向补偿——用一致性窗口换吞吐。

## 版本演进

- 第 1–3 版：2PC/3PC 与并发控制同章；第 3 版起独立成「分布式事务」章。

### 工程易错清单

- prepare 记录必须**先落盘再投票**：顺序颠倒等于承诺了一张空头支票——这是 2PC 实现里最致命也最常见的 bug。
- 悬挂事务要有后台清理：参与者长期 uncertain 时，需要运维手段（人工查协调者日志/强制决定工具），不能只靠协议。
- 2PC 与锁的持有时间直接耦合：事务里放慢操作（外部 HTTP 调用）在 prepare 之前是事故高发区。
- 3PC 的「非阻塞」只在崩溃模型下成立：任何分区/消息乱序测试都要跑一遍，证明自己没有误用 3PC。
- 死锁检测的探针要限流：热点锁 + 高并发会让探针指数扩散，必须带 TTL 与去重。
- 事务消息的「回查」逻辑必须幂等且可重入：回查时本地事务可能尚未落库，判定要基于状态机而非「查一次就信」。

## 近年研究与工业界开源实践（2015–2026）

- **Percolator**（Google, OSDI 2010）：Bigtable 上的快照隔离 + 主锁（primary lock） + 失效通知，2PC 的「无协调者常驻」形态；TiDB 的乐观事务是它的开源实现（`pingcap/tidb`，40588★）。
- **Spanner 的 TrueTime 两阶段提交**：2PC + Paxos 组复制 + 等待时间区间尽头，实现外部一致性——「2PC 不可用」的教条被「协调者本身是 Paxos 组」打破；对照 [book/分布式数据库入门进阶与实战/06-事务基础与分布式事务.md](../分布式数据库入门进阶与实战/06-事务基础与分布式事务.md)。
- **确定性数据库**：Calvin（SIGMOD 2012）先把事务定序再执行，免去提交协议的协调；Aria/SLOG 延续该思路。
- **微服务时代的 2PC 变体**（star 数 2026-09 实测）：
  - `apache/incubator-seata`（26012★）：AT 模式把 2PC 外观与 undo log 反向补偿结合，TCC/Saga/XA 多模式并存——「XA 太重」与「最终一致要补偿」两派分歧的活标本。
  - `dtm-labs/dtm`（10923★）：语言无关的 Saga/TCC/两阶段消息编排。
  - `apache/rocketmq`（22620★）：事务半消息 = 「本地事务 + 定时回查」的 2PC 语义投影。
  - `temporalio/temporal`（23295★）：把嵌套事务语义改写为持久化工作流，是本章嵌套事务模型的现代翻版。
- **Jepsen 类测试**（`jepsen-io/jepsen`，7505★）多次揭示：声称实现严格可串行化的分布式事务系统，在分区/时钟异常下实际更弱——提交协议的「安全声明」需要黑盒验证。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「2PC 保证高可用」 | 2PC 保证原子性不保证可用性：协调者与参与者同时失联时 uncertain 参与者阻塞 |
| 2 | 「3PC 是 2PC 的严格改进」 | 3PC 消除阻塞但引入分区不安全；工业界用「Paxos 复制协调者」而非 3PC |
| 3 | 「XA 即 2PC 的全部」 | XA 只是接口规范；实现质量（prepare 落盘、悬挂事务处理）决定生死 |
| 4 | 🔧 分布式死锁检测可以无脑开 | 全局检测通信成本高、且有过期信息假死锁；主流是超时 + 中心检测器，或时间戳预防 |
| 5 | 「分布式事务 = 2PC 一种解法」 | 🔧 现代谱系还有 Percolator 主锁、Saga/TCC 补偿、确定性定序（Calvin）、消息最终一致（事务消息），本书均未覆盖 |
| 6 | 「TP Monitor 已过时」 | 其职责（路由、池化、持久队列、事务上下文传播）被 Service Mesh + MQ + 工作流引擎瓜分继承 |
