## 核心精讲（教学示意，不参与构建）

### 5.1 RPC 的设计问题（第 5 章主体）
- **请求-响应协议**：doOperation / getRequest / sendReply 三元组；消息结构含
  requestId 与远程引用；超时 + 重发策略决定调用语义。
- **调用语义（invocation semantics）**：
  | 语义 | 实现方式 | 后果 |
  | --- | --- | --- |
  | Maybe | 单发不重发 | 丢消息即丢调用，适合可容忍的统计类应用 |
  | At-least-once | 超时重发 | 可能重复执行 → 需要幂等操作 |
  | At-most-once | 重发 + 去重（requestId 过滤） | 不重复但可能失败 |
  | Exactly-once | at-most-once + 服务器重传应答 | 理想语义，成本最高 |
- **参数传递**：值传递靠 marshalling；引用参数无法直接传（远程地址空间不同）→
  改为「传值」或「回调」；对象参数在 RMI 中变为**传远程引用**或**序列化拷贝**。
- **透明性的代价**：Waldo 论文的警告——本地调用失败是「编译期/逻辑错误」，远程调用失败是
  「运行时/环境错误」，两者不应伪装成同一种东西；RMI 在异常体系中显式区分
  （如 `RemoteException` 强制声明）。
- 🔧 与摘录「RMI vs RPC」对照：一句话——RPC 面向过程与 IDL，RMI 面向对象（远程接口、
  引用传递、分布式 GC），其余（stub 生成、编解码、故障处理）同构。

### 5.2 分布式对象与 Java RMI（第 8 章主体）
- **分布式对象模型**：远程对象持有者 + 远程接口（`java.rmi.Remote`）+ 远程引用；
  stub/skeleton 负责编解码（第 5 版已用动态代理，skeleton 可省）。
- **分布式垃圾回收**：服务器为每个远程对象维护引用者集合（租约 lease），
  客户续租、断线到期回收——「分布式 GC = 引用计数 + 租约超时」，不会精确，只求不泄漏。
- **绑定为工厂模式**：RMI Registry 只是名字 → 远程引用的查找表，真正的引导问题
  （第一个引用怎么拿）由外部机制解决（第 13 章名字服务同理）。

```java
// 教学示意，不参与构建：Java RMI 三件套骨架
public interface Shape extends Remote {           // 远程接口
    int getVersion() throws RemoteException;
}
public class ShapeImpl extends UnicastRemoteObject implements Shape {
    public int getVersion() { return 1; }         // 被自动导出为远程对象
}
// 客户端：Registry 查引用 → stub 代理 → 方法调用经 marshalling → TCP 传输
```

- **CORBA 概要**（摘录关键词）：OMG 的对象请求代理（ORB）体系——IDL 定义接口、
  CDR 编码、GIOP/IIOP 协议、POA 对象适配器、对象引用可序列化（IOR）；
  组件模型（CCM/CORBA Component Model）在其上扩展。CORBA 的历史教训：
  接口标准化先行但实现互操作困难，最终被 Web 服务与 gRPC 取代（见下文 🔧）。

### 5.3 远程事件
- 事件通知的分布式化：事件服务（第三方的 add/remove listener + notify）vs
  观察者直连；涉及订阅者的可达性（订阅方在 NAT 后、宕机后通知失效）问题——
  完整解法是第 6 章的发布-订阅系统（06 文件）。

### 5.4 工作例题：请求-应答协议的消息结构与重发决策（教学重述）
- 请求消息最小字段：`type(request/reply)`、`requestId`（客户唯一递增）、
  `remoteRef`（远程对象引用）、`operationId`、参数 marshalling 结果。
- 重发决策树（客户侧）：
  ```
  超时 → 已重发超过上限? 是: 报错给应用
                否: 操作幂等? 是: 直接重发(at-least-once)
                             否: 服务端支持 requestId 去重? 是: 重发(at-most-once)
                                                          否: 报「不确定」错误(Waldo 警告)
  ```
- 服务端去重实现：按客户标识 + requestId 保留最近应答表（LRU），重复请求直接重放旧应答——
  这张小表就是「exactly-once 效果」的全部成本。
- 🔧 与 gRPC 映射：requestId → gRPC stream id；「不确定」错误 →
  `UNAVAILABLE`（可重试）vs `DEADLINE_EXCEEDED` 的语义区分。

### 5.5 工作例题：Java RMI 的分布式 GC 什么时候会误伤（教学重述）
- 机制回顾：客户端持有远程引用需定期**租约续期**；服务端租约到期即回收远程对象。
- 误伤场景：客户端 GC 暂停（stop-the-world）超过租约期 → 服务端回收 → 客户端续租时收到
  `NoSuchObjectException`。工程对策：租约远大于 GC 暂停上限 + 客户端对失效引用**重新
  lookup 重建**（而非崩溃）；反方向（泄漏）则靠客户端正常退出时显式 `unreferenced`。
- 引申：所有「租约式」机制（NFSv4 委托、分布式锁、ZooKeeper 会话、Kerberos 票据）
  共享同一权衡——**租约短了误回收，长了泄漏/权限悬挂**。这是本书贯穿性的设计母题之一。

### 5.6 CORBA 服务清单速查（第 8 章补充）
| 服务 | 用途 | 当代对应物 |
| --- | --- | --- |
| Naming | 名字 → 对象引用 | DNS/Consul/Nacos |
| Trading | 按属性查找（黄页） | 服务目录/服务发现 |
| Events | 事件通道（推/拉） | pub/sub、Kafka |
| Transactions | 对象事务（OTS） | XA/Seata |
| Concurrency | 对象锁 | 分布式锁服务 |
- 🔧 读法：CORBA 的失败不在服务清单（思路全对），而在「语言级对象总线」的互操作成本；
  gRPC 的胜利是把这套服务**拆还给基础设施**，而非重造。

### 5.7 参数与对象传递的四种去向（第 5/8 章综合，教学重述）
| 参数类型 | 跨网络时的处理 | 语义 |
| --- | --- | --- |
| 基本类型/结构 | marshalling 拷贝 | 值传递 |
| 远程对象引用 | 传引用（stub） | 引用传递，调用回远程 |
| 本地可序列化对象 | 序列化拷贝 | 值传递（副本独立演化） |
| 本地不可序列化对象（句柄/线程等） | 编译/运行时报错 | 不支持——边界暴露 |
- 教学要点：**同一类型系统里的「值/引用」二分在网络上变成四分**；
  设计远程接口时第一条纪律就是明确每个参数走哪一列——这正是 protobuf 把
  消息（值）与引用（resource name / URI）显式分开的原因。

### 5.8 远程调用故障对用户的可见性（综合例题）
- 场景：电商下单调用库存服务扣减，超时未收到应答。库存扣了没有？三种可能：
  1. 请求未到达——库存未扣，可安全重试；
  2. 请求到达并扣减，应答丢失——**已扣，重试会重复扣**；
  3. 请求到达，服务端执行中崩溃——**状态不确定**。
- 教科书答案：不猜。用幂等键（订单号）让重试收敛到唯一结果，或改用事务性消息/两阶段提交
  （第 17 章，后半目录）。这道题是「调用语义 → 分布式事务」的桥，建议与
  [../分布式数据库入门进阶与实战/06-事务基础与分布式事务.md](../分布式数据库入门进阶与实战/06-事务基础与分布式事务.md) 对读。

## 版本演进

- 第 3/4 版：CORBA 为绝对主角（整章案例）；第 5 版把 CORBA 压缩为「组件模型概要」，
  Java RMI 案例扩充，并新增 Web 服务接口的对比性引言（第 9 章展开）。
- 🔧 2026 视角（本章变化最大的一章）：
  1. **gRPC + protobuf 事实上取代 CORBA/Java RMI**：HTTP/2 多路复用、protobuf IDL、
     四种流式调用；跨语言由代码生成而非对象总线实现。
  2. **Dubbo**（摘录关键词）：国内主流 RPC 框架，从「接口代理 + 注册中心（如 Nacos/Apollo
     管配置）」演化为兼容 gRPC 协议的多协议体系——摘录「ip 地址写死 Apollo 可以解决」
     正是注册中心/配置中心消灭硬编码地址的经验，其理论原型是原书第 13 章名字服务。
  3. **eBPF/gRPC 场景下的服务网格**：远程调用的路由、重试、熔断从 SDK 下沉到 sidecar/eBPF，
     「透明性」从语言机制变成基础设施机制。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「RPC 做到完全透明就成功了」 | 恰当目标：**语法透明 + 语义显式**；故障必须以异常形式暴露给调用者 |
| 2 | 「at-least-once 重发即可保证送达」 | 重发造成重复执行，非幂等操作（转账、下单）会出错；需去重或幂等设计 |
| 3 | 「分布式 GC 可以做到和本地一样准」 | 租约机制本质是「超时即回收」，宁可误回收（由应用捕获失效引用重建）也不泄漏 |
| 4 | 「CORBA 失败因为太复杂」 | 部分成立；更根本的是实现互操作差、治理失败，且 Web 时代接口契约转向文本/IDL 生成 |
| 5 | 🔧 本书未覆盖 | gRPC/protobuf、流式调用（server/client/bidi streaming）、服务网格 mTLS、OpenAPI 契约 |
| 6 | 🔧 摘录批注归位 | 「Dubbo/Apollo/Grpc」为摘录者现代批注：理论原型分别对应原书第 13 章（名字服务）与本章（远程调用设计） |
