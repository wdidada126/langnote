## 核心概念速览（中英对照）

- **任务与线程** — task / thread：任务是"要做的事"，线程是"做事的工人"，一一对应是最低配
- **detached thread** — 分离线程：无 join 责任，活到 main 结束即被枪毙——危险糖
- **参数传递进线程** — passing arguments：新线程可能活得比实参久，**拷贝或 shared_ptr 是默认答案**
- **packaged 通信族** — future / promise / packaged_task：一条"结果的管道"
- **async 惰性任务** — std::async：不手写线程的 launch 策略包装，配合 future 取结果
- **互斥与锁 RAII** — mutex / lock_guard：用作用域（第 1 章）管锁的生命周期（第 3 章 RAII 再演）
- **数据竞争=UB** — data race：非原子且至少一写，C++ 内存模型直接判死刑
- **原子量** — atomic：无锁的最小同步粒，但"原子≠事务"，组合仍需锁
- **condition_variable** — 条件变量：`wait(lk, pred)`——谓词防丢失唤醒的教范
- **latch / barrier（预告）** — 倒计数闩/会合栅：并发 TS v2 的计数与轮次同步（§15.6 露出）
- **shared_mutex** — 读写锁：读多写少的正规解，2nd 仅提名
- **生产者-消费者队列** — 任务通信：§15.7 的示例=用 mutex+condvar 手写线程池的胚胎

## 动机：11 页讲"为什么标准库要自带线程"

§15.1 开门见山：**并发是语言问题而非库问题**——内存模型、原子性、线程的创建/汇合
必须有跨编译器的统一语义，否则每个库各写一套平台胶水。Stroustrup 的叙事把并发
定位为"资源管理的极端形态"：线程与锁都是资源，RAII 是唯一的安全带。
全章不教"怎么并发"（那是专册的事），教**标准 API 的最小心智地图**。

## 机制：三种任务形态 + 两种通信

1. **thread 直连**（§15.2–15.4）：构造即启动；join/detach 二选一否则 terminate。
   传参铁律："引用要命"——`thread t(ref(x))` 或 `[&]` 捕获局部是悬垂制造机；
   导学建议**默认拷贝**或 `shared_ptr`（对照第 13 章所有权）。
2. **future/promise 管道**（§15.7.1）：生产者 `set_value`（含异常传播！
   set_exception 由抛出隐式完成）、消费者 `get`（一次性）。
   `packaged_task` 把可调用对象装进管道，`async()` 再包一层"要不要真开线程"的策略。
3. **共享数据的两档**（§15.5）：mutex+lock_guard（组合不变式）与 atomic（单变量）。
   "别用 atomic 模拟锁，也别用锁包裹一切"是本节的天平。
4. **等待事件**（§15.6）：condition_variable 的标准形态是
   `cv.wait(lk, []{return ready;});`——谓词版免疫 spurious wakeup 与丢失唤醒；
   2nd 顺带预告 barrier/latch（Concurrency TS v2，即 C++20 转正件）。

🔧 实测（g++ 15.2，c++17/c++20 双档，**c++20 下运行 PASS**）：
- `std::atomic<int>::wait/notify_one`（3e/TS 转正件的本地直证）：c++17 **拒绝**、
  c++20 **编译+运行通过**。
- `std::jthread` + `stop_token`（3e §18.5.4"停止 thread"新增件的预告位）：c++17 无此类型、
  c++20 通过并正确停止（本机需 `-static`，动态链接受限于 libwinpthread 路径，⚠️ 环境噪音非语言结论）。

## 课堂问答（自读后对答案）

1. **问：** `thread t(f, x)` 与 `thread t(f, std::ref(x))` 的安全边界差在哪？
   **答：** 前者把 x **拷贝**进线程内部存储，线程生命周期与 x 解耦；后者只传引用，
   若 x 先于线程销毁即悬垂——所以 `ref` 只配 join 到底、且 x 活得更久的场景（导学建议默认拷贝）。
2. **问：** 为什么 `future::get()` 说"一次性"？要多个消费者怎么办？
   **答：** `get` 取走共享状态里的值（void 也算"取走就绪态"），二次 get 对同一状态是 UB/逻辑错误；
   多消费者要么 `shared_future`（可复制、各自 get），要么上层自己加锁广播。
3. **问：** `async(launch::async, f)` 和直接 `thread(f)` 何时选前者？
   **答：** 当你只关心"结果什么时候好"而不关心"几个工人"时——async 允许实现推迟到 `get()`
   才执行、允许复用线程，把调度权交还库；需要亲手控制线程（亲和性/生命周期）才下沉到 thread。
4. **问：** `atomic<int>` 计数器能代替 mutex 保护的计数器吗？
   **答：** 单变量自增可以（`++` 即 RMW，无撕裂）；一旦"计数与其他状态要**一起**变"
   （组合不变式），原子给不了事务性——那必须锁。"原子≠事务"是本节天平的支点。
5. **问：** `cv.wait(lk, pred)` 的谓词版为什么是必须的而不是便利的？
   **答：** 裸 `wait` 会遭遇虚假唤醒（spurious wakeup）与丢失唤醒（通知发生在等待前）；
   带谓词版=醒来后重查条件、不满足继续睡——把正确性从"通知时序玄学"拉回"条件事实"。

## 最新演进与工业实践

- **第 3 版（C++20）改了什么**：本章升第 18 章，增量最密：§18.3.1 锁家族补
  `scoped_lock/lock_guard 的 CTAD`；§18.3.2 原子量提及 **atomic_ref/wait**；
  新增 **§18.5.4 停止 thread（jthread/stop_token）** 与 **§18.6 协程**
  （generator/协作式多任务 §18.6.1）——2nd 整页都没碰的两座山。
- **C++23/26 又推进了什么**：C++23 小修（`std::execution` 之外的 latches 修订）；
  大动作是 **senders/receivers（P2300R10《`std::execution`》，
  [wg21.link/p2300](https://wg21.link/p2300) 本会话实测可跳转、标题核实为 `std::execution`）**
  面向 C++26 的任务图抽象——coroutine 之上的组合层；
  协程侧 C++23 以 LWG 修复为主（`std::generator` 是 Ranges TS 支流，VS 2022/GCC 14+，
  ⚠️ 未逐档核实）。
- **实现史节点**：coroutine 核心语言 GCC 10/Clang 5 起（TS）——2nd 写作时点（2018）
  恰在合并前夜，故书中零覆盖，这条"缺席"本身就是版本时间线的证据。
