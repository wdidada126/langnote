## 核心概念速览（中英对照）

- **概念** — concept：对模板参数的具名布尔约束，`requires` 表达式的集合
- **约束表达式** — requires expression：`requires(T a, T b){ a+b; }` 语法化"我用到你什么"
- **标准库概念** — standard library concepts：`std::integral`、`std::sortable` 等公共词汇
- **subsumption（蕴含）** — subsumption：约束之间的逻辑蕴含，用于重载择优
- **收缩/推导** — narrowing / constraint-based deduction：概念让错误在"门口"发生
- **泛型编程** — generic programming：以概念而非类层次组织的编程范式（§7.3 的立场承 Stepanov 一脉，引语未逐字核 ⚠️）
- **算法即抽象** — algorithm as abstraction：导学引用"泛型=发现算法共性"的立场
- **可变参数模板进阶** — variadic templates：折叠、转发、`(void)...` 惯用法退场
- **表达式折叠** — fold expression：`(args + ...)` 四型折叠替代递归展开
- **完美转发** — perfect forwarding：`std::forward<T>(u)` 保值类别与 const 穿参
- **模板编译模型** — template compilation model：包含模型（头里定义）+显式实例化 vs 分离编译
- **错误信息经济学** — error message economics：概念的第一 KPI 是把 500 行报错压成 3 行

## 机制：concepts 解决的三件事

1. **早报错**：无约束模板把错误拖到实例化点（常常在标准库内部）；
   `template<Addable T>` 在调用点直接指出"int 满足，X 不满足，差一个 operator+"。
2. **文档即类型**：`requires` 子句就是参数化接口文档，且会随代码重构自动更新——
   对比注释里的"要求 T 有 operator+"。
3. **重载择优**：`std::integral auto` 版与通用版并存时，**更被蕴含（subsumed 之逆）的约束
   胜出**——这是 concepts 区别于 `enable_if` 的地方：择优逻辑进语言，不进库作者玄学。

🔧 实测（g++ 15.2）：`template<typename T> concept Addable = requires(T a,T b){a+b;};` +
`static_assert(std::integral<int>);` 在 c++17 **拒绝**（concept 关键字不存在）、
c++20/c++23 **通过**；缩写形式 `int twice(int auto v){...}` 在本机三档**全部报错**
（`two or more data types in declaration`）——**GCC 对"约束型 auto 形参"的解析落后于
Clang**（Clang 接受，⚠️ 未本机验证），而朴素 `auto v`（无约束）仅 c++20 起接受、
gnu++17 只给扩展警告。同一特性三种待遇，是"概念语法落地不均"的活标本。

§7.4 变参进阶给出两条硬干货：折叠表达式的四种形态（一元右折叠最常见），
以及 `f(std::forward<Args>(args)...)` 转发链——§7.4.2 与第 13 章 `make_unique` 场景闭环。
§7.5 模板编译模型坦白"包含模型=把实例化外包给每个 TU"，这是编译时间病的根，
药方分别是显式实例化（库作者用）与 modules（语言用）——链回第 3 章。

## 课堂问答（自读后对答案）

1. **问：** concept 和 `static_assert(requires...)` 都能拦错，差在哪？
   **答：** static_assert 是"事后验尸"（已在实例化内部炸开）；concept 参与**重载决议与
   推导**——不满足的候选直接出局，编译器给出"哪个约束没满足"的门禁级报错，还能写
   "两个都可行时选更受约束者"。
2. **问：** 为什么 `std::sortable` 这类标准概念对调试 `std::sort` 报错帮助最大？
   **答：** 因为它把"要 CopyConstructible + `operator<`/comp"的隐性合同变成命名实体，
   报错第一行就引用概念名；C++17 时代要自己读 200 行实例化回溯。
3. **问：** 折叠表达式 `(args + ... + init)` 与 `(... + args)` 等价吗？
   **答：** 语法类别不同（一元左/右折叠、二元折叠）；对可结合运算结果相同，
   **对 `-`/除法这类不满足结合律的运算，折叠方向直接决定结果**——变参工具函数的经典 off-by-one。
4. **问：** "模板=编译期虚函数"这个类比哪句对、哪句错？
   **答：** 对：都参数化"类型/行为"。错：虚函数一次分派一张表，模板 N 个实参 N 份代码；
   虚函数运行期可扩展，模板要求类型当场可见——所以 concepts 补的是**接口显式化**，
   不是"给模板加 vtable"。
5. **问：** `std::integral auto v` 与 `auto v` 的报错时机差在哪？
   **答：** 前者在**调用点**判"约束满不满足"（不满足=无匹配候选），后者先接受任何类型、
   错误拖进函数体实例化处——这正是"门口报错 vs 屋内爆炸"的两种 UX。
6. **问：** 为什么导学要专门讲"模板编译模型"而不只讲语法？
   **答：** 因为**包含模型=把实例化外包给每个 TU**，这是编译时间病与"模板定义必须在头里"
   两条约定的共同根源；讲清模型，读者才懂 modules/concepts 分别在哪一层开药。

## 权衡：概念、SFINAE 与 tag dispatch 的同题三面

- `enable_if`（§13.9.3 露真身）：库层面的约束，可读性差但 C++11 就能用；
- tag dispatch（§6 遗留惯用法）：以重载分派，运行不了"报错也要管"的场景；
- concepts：语言级，报错最好、可被推导系统理解。
三版把这层对比写成 §8.2.6"类型与概念"；本册则在 §7.2.3"合法代码"里先给直觉。
