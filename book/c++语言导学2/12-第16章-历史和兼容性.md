## 核心概念速览（中英对照）

- **C with Classes** — "带类的 C"（1979–83）：C++ 的史前形态，类的雏形+带类型名的 cfront
- **cfront** — C++ 到 C 的转译器：早期实现即前端，兼容基因的成因
- **大事年表** — chronology：1979 命名、1985 TC++PL 出版、1998 C++98、2011 现代转折、
  2017/2020 节奏化
- **兼容性铁律** — backward compatibility：Stroustrup 的第一设计约束，"增量演化"的根
- **零开销抽象** — zero-overhead principle：不用者不付费，用了者不比手写差
- **子集/兄弟论** — C and C++ as siblings：C 不是 C++ 的子集（§16.3.1 的纠正）
- **兼容性差异点** — incompatibilities：字符集、整型提升、原型检查、柔性数组、
  `restrict`/VLA 等 C99 件不入 C++
- **extern "C"** — 链接名协商：两族互操作的桥
- **特性演化清单** — feature evolution：C++11/14/17 语言与库的双轨表（§16.2）
- **已弃用清单** — deprecated：动态异常规范、`auto` 作存储类说明符等
- **标准流程** — ISO C++ process：CD→IS、TS 支线，"每三年一版"的社会工程
- **风格与标准** — standards and style：语言标准管语义，风格管人——§16.1.4 的分界

## 动机：作者写史，是为了给"克制"辩护

终章的存在本身就是 Stroustrup 的论点：**不理解的语法怪癖会教你错误的风格**。
§16.1 用"历史如何约束设计"解释为什么 C++ 不用垃圾回收、为什么宏还在、为什么
异常可关。对读者，这一章是前面 15 章的"考古层"：每条建议背后都躺着一个
年代事件。单文件笔记在此留下的 "`= == 的区别？`" 疑问其实也是历史问题——
C 的赋值即表达式传统，16.3.2 的兼容性差异清单里就有它。

## 机制：三张清单读法

1. **§16.1.1 年表**：记住四个节拍点即可——1998（标准化还债）、2003（修 bug）、
   **2011（语言重做：移动/lambda/auto，从"更好的 C"转向"现代抽象语言"）**、
   2014/17/20（三年一版的快车道）。
2. **§16.2 特性演化**：语言/库分栏是本章的精髓——`constexpr`（语言）与
   `string_view`（库）不同轨；读任何"新特性"文章先问进的是哪一轨、哪个版本。
3. **§16.3 C/C++**：**"C 是 C++ 的非严格子集"是流传最广的错误**——
   柔性数组、复合字面量、VLA 在 C 合法在 C++ 非法；整型提升规则分叉；
   C++ 的类型检查更严。互操作的正路是 extern "C" + 一套共享 ABI 的"哑接口"。

## 权衡：弃用而非删除

§16.2.7 列出的动态异常规范（`throw()`）、`register`、自动变量等命运——
**C++ 拆东西的刀法：先 deprecated（标准书面警告），隔一代才移除**，
因为兼容性铁律只对"有活代码的痛"让路。对照第 3 版：`register`/动态异常规范
在 3e §19.2.9"移除或弃用"里已进"移除"堆——2nd→3e 之间正好跨过那条界线。

🔧 实测（g++ 15.2 三档）：用编译器给本章"实物标本"——
`void f() throw(int) {}` 动态异常规范在 **c++17 与 gnu++17 皆硬报错**
（`ISO C++17 does not allow dynamic exception specifications`，连 GNU 扩展模式也不放行
——"移除级"弃用的标本）；`register int r=1;` 在 c++17 只给警告
（`does not allow 'register'`）仍可编译——**同为"标准不再允许"，移除的彻底度也分档**。
这比任何表格都直观：§16.2.7 的"已弃用"清单，就是这类代码在编译器里逐年升级的病历。

## 课堂问答（自读后对答案）

1. **问：** 为什么 C++ 宁可留着宏、留着指针算数，也不"一步到位"换掉它们？
   **答：** 兼容性铁律：数十亿行存量代码是资产也是人质——**增量演化**要求每步可回头；
   替代件（constexpr/智能指针）以"新增+共存"方式进场，旧件先 deprecated 再隔代移除。
2. **问：** `throw(int)` 动态异常规范为什么死得比 `register` 彻底？
   **答：** 实测本册：g++ 15.2 下 `throw(int)` 在 c++17 与 gnu++17 均**硬报错**，
   `register` 只给警告。根因是前者与移动/泛型的异常传播组合语义坏到不可修复（且运行期检查
   付不起零开销），后者只是语法化石、不伤害别人——弃用烈度跟着**危害**走，不跟着资历走。
3. **问：** "C 是 C++ 的子集"错在哪？给三个具体反例。
   **答：** C 合法而 C++ 非法：柔性数组（`struct S { int n; int a[]; }`）、复合字面量、VLA；
   另有整型提升规则分叉、字符字面量类型不同——互操作正路是 extern "C"+哑接口，不是拿 C++ 编 C 码。
4. **问：** 为什么语言特性和库组件要分两轨记忆？
   **答：** 生效条件不同：语言特性卡在**编译器+标准档**（`-std=`），库件还卡在**标准库实现版本**
   （本册 `std::print` 连 c++23 都缺的现场教材）；报障时先问"哪一轨、哪年进的"，能省一半时间。

## 最新演进与工业实践

- **第 3 版（C++20）改了什么**：升第 19 章，新增 §19.1.6 "C++ 模型"（资源管理/
  RAII/泛型的三支柱总结——2nd 散落全书的暗线转正），§19.2.4/19.2.8 补
  **C++20 语言与库特性两栏**（concepts/ranges/coroutines/modules/spaceship 入表），
  §19.2.9 改名"移除或弃用的特性"；参考文献更新到 HOPL-IV（2020）。
- **C++23/26 又推进了什么**：C++23 已定档（deducing this 进编译器扩展、ranges 补全、
  `if consteval`——本会话实测 g++ 15.2 `if consteval` c++23 通过/c++20 拒绝）；
  C++26 的模块补票（P2633/P2465 线）、执行器（P2300）、合约（P2900）
  在 4th 版（若出版）才会入正片——2nd/3rd 版的时间胶囊到此封顶。
- **工业实践**：企业基线远慢于标准（Google/Chromium 2020s 才全量 C++17→20，
  ⚠️ 凭公开博客印象）；"用什么标准"是 ABI 与人才市场决策而非技术决策——
  这正是本章给架构师的真正礼物。
