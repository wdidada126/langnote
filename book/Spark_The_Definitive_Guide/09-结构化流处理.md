## Ch 20 核心：Structured Streaming

### 设计理念

✅ **Structured Streaming = 将流数据当作"无界表"处理**
- 流数据被视为不断追加行的输入表（Input Table）
- 使用与批处理相同的 DataFrame API 和 Catalyst 优化器
- 默认微批模型（Micro-Batch）；Spark 2.3+ 支持 Continuous Processing

### 基本模型

```python
# 读取流数据
streamingDF = spark.readStream \
    .format("rate") \
    .option("rowsPerSecond", "10") \
    .load()

# 使用 DataFrame API 处理 (与批处理语法相同!)
resultDF = streamingDF \
    .withWatermark("timestamp", "10 seconds") \
    .groupBy(window("timestamp", "5 seconds")) \
    .count()

# 输出结果
query = resultDF.writeStream \
    .outputMode("update") \
    .format("console") \
    .start()

query.awaitTermination()
```

### 三种输出模式 (Output Mode)

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| `append` | 只输出新行 | 无聚合的简单过滤/投影 |
| `complete` | 每次输出完整结果表 | 有聚合的场景（需全量状态） |
| `update` | 只输出变化的行 | 有聚合但只需增量更新 |

### 事件时间与水线 (Event-Time & Watermark)

✅ **事件时间**：数据本身携带的时间戳（区别于处理时间）
✅ **Watermark**：定义"迟到数据的容忍度"，超过水线的旧数据将被丢弃

```python
# 设置 10 秒水线
df.withWatermark("event_time", "10 seconds") \
  .groupBy(window("event_time", "5 minutes")) \
  .count()
```

⚠️ Watermark 是延迟与完整性之间的权衡：设太短会丢数据，设太长增加状态存储。

### 触发器 (Trigger)

| 触发器 | 说明 |
|--------|------|
| `ProcessingTime("5 seconds")` | 每 5 秒一个微批（默认） |
| `ProcessingTime("0 seconds")` | 尽快处理（无间隔） |
| `Once()` | 只处理一次当前可用数据 |
| `AvailableNow()` | 3.3+ 一次性处理所有可用数据 |
| `Continuous("1 second")` | 持续处理模式（低延迟，功能受限） |

### 流 Join

✅ 流-流 Join（Spark 3.2+）：两个流之间可基于时间窗口 Join
✅ 流-静态 Join：流与静态 DataFrame Join

## Ch 21 核心：流数据源与接收器

### 内置数据源

| 数据源 | readStream | writeStream | 说明 |
|--------|-----------|-------------|------|
| `rate` | ✅ | ❌ | 测试用，每秒生成 N 行 |
| `text` | ✅ | ✅ | 文件流（监控目录） |
| `parquet/json/csv` | ✅ | ✅ | 文件流 |
| `kafka` | ✅ | ✅ | Kafka 消费/生产 |
| `socket` | ✅ | ❌ | 测试用 |
| `memory` | ❌ | ✅ | 输出到内存表（调试用） |

### Kafka 集成

```python
# 读取 Kafka
kafkaDF = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "host:9092") \
    .option("subscribe", "topic_name") \
    .load()

# 写入 Kafka
query = resultDF.selectExpr("CAST(key AS STRING)", "CAST(value AS STRING)") \
    .writeStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "host:9092") \
    .option("topic", "output_topic") \
    .start()
```

### 容错与 Exactly-Once

✅ **WAL (Write-Ahead Log)**：记录微批的偏移量，故障恢复时从上次位置继续
✅ **Source 支持**：Kafka / 文件系统 支持 exactly-once
⚠️ Sink 端 exactly-once 取决于 Sink 是否支持幂等写入

### 监控

```python
query.status          # 当前状态
query.lastProgress    # 最近一个微批的进度
query.recentProgress  # 最近多个微批的进度
query.awaitTermination()
query.stop()
```

## 🔧 DuckDB / SQLite 类比

> 以下类比均为辅助理解，**非本书引擎行为**。

🔧 **类比 1：流式 DataFrame ≈ DuckDB 无直接等价 / SQLite 无直接等价**
- Spark Structured Streaming 将流视为无界表
- DuckDB/SQLite 是批处理引擎，无原生流处理能力
- Flink 的 Table API 与 Spark Structured Streaming 更相似 · ⚠️ 非本书引擎行为

🔧 **类比 2：Watermark ≈ 无直接等价**
- Spark Watermark 管理迟到数据的概念
- DuckDB/SQLite 无此概念（批处理不需要）
- Flink 也有 Watermark 机制 · ⚠️ 非本书引擎行为

🔧 **类比 3：文件监控目录 ≈ DuckDB 的 watch 模式（实验性）/ SQLite 无**
- Spark `readStream.format("text").load("dir/")` 监控目录新文件
- DuckDB 无原生文件监控（需外部轮询）
- 概念类似 `tail -f` 但针对文件目录 · ⚠️ 非本书引擎行为

🔧 **类比 4：流 Join ≈ 无直接等价**
- Spark 支持流-流 Join（基于事件时间窗口）
- DuckDB/SQLite 无流 Join 概念
- Flink 的 Temporal Join 是类似功能 · ⚠️ 非本书引擎行为

## 最新演进与工业实践

**Structured Streaming 的演进（书后发展）：**

| 演进 | 版本 | 影响 |
|------|------|------|
| Continuous Processing | 2.3 | 低延迟持续处理（功能受限） |
| 流-流 Join | 3.2 | 两个流之间可 Join |
| `AvailableNow` 触发器 | 3.3 | 一次性处理所有可用数据后停止 |
| 状态存储增强 | 3.x | RocksDB 状态后端（大规模状态） |
| 异步处理 | 4.x 规划 | 异步 I/O 提升吞吐量 |

> 来源: spark.apache.org ✅

**工业实践（2026）：**
- Structured Streaming 在实时数仓中广泛应用（CDC → Kafka → Spark → Delta）
- 高吞吐场景仍倾向 Flink（更低延迟、更成熟的状态管理）
- 流批对照: [Introduction_to_Apache_Flink](../Introduction_to_Apache_Flink/02-时间四要素：事件时间乱序水位线与窗口.md) 深入对比了 Flink 的时间语义
- RocksDB 状态后端在大规模流处理中越来越重要
