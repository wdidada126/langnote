第9章的核心思想是：数据库管理系统对用户提交的SQL查询语句，并不会直接执行，而是会进行一系列复杂的“加工”和“优化”，目的是用最高效、成本最低的方式得到正确结果。这个过程主要分为两大类：

1.  代数优化（逻辑优化）：基于关系代数规则，对查询语句本身的逻辑结构进行等价变换。
2.  物理优化（执行计划优化）：为优化后的逻辑查询选择最有效的物理操作（如使用哪个索引、采用哪种连接算法）。

1. 代数优化（9.3 节）在 MySQL 5.7 中的体现

代数优化的原则是等价变换，即改变查询的执行顺序，但不改变最终结果。MySQL 的优化器会自动完成这些操作。

常见规则及 MySQL 5.7 示例：

a) 选择操作尽早执行
•   思想：尽早过滤掉不相关的数据，减少后续操作（如连接）的数据量。

•   MySQL 示例：
    -- 原始写法（不一定高效）
    SELECT * FROM employee e 
    JOIN department d ON e.dept_id = d.id 
    WHERE e.salary > 10000;

    -- 优化器会将其等价变换为：
    -- 1. 先执行 SELECT * FROM employee WHERE salary > 10000 (得到一个结果集t1)
    -- 2. 再将 t1 与 department 表进行连接
    
    你可以通过 EXPLAIN 命令查看执行计划，会发现对 employee 表的访问（WHERE salary > 10000）是先执行的。

b) 投影操作尽早执行
•   思想：只取出需要的列，减少中间结果的数据大小。

•   MySQL 示例：
    -- 不好的习惯
    SELECT * FROM ... JOIN ... WHERE ...

    -- 好的写法，也是优化器会尽力去做的
    SELECT e.name, d.dept_name FROM employee e 
    JOIN department d ON e.dept_id = d.id;
    
    即使你写了 SELECT *，优化器在内部处理时也可能只传递必要的列ID。

c) 子查询优化（这是 MySQL 5.7 的重点）
•   思想：子查询（特别是相关子查询）的执行方式通常很像嵌套循环，性能很差。优化器会尝试将其“扁平化”为更高效的连接操作。

•   MySQL 示例：
    -- 使用子查询
    SELECT name FROM employee 
    WHERE dept_id IN (SELECT id FROM department WHERE location = 'Beijing');

    -- 在 MySQL 5.7 及以后版本，优化器通常会将其重写为半连接（Semi-join）
    -- 类似于：
    -- SELECT e.name FROM employee e 
    -- SEMI JOIN department d ON (e.dept_id = d.id AND d.location = 'Beijing')
    
    注意：在 MySQL 5.6 及更早版本中，子查询性能可能很差，需要手动改为 JOIN。MySQL 5.7 对半连接的优化已经非常成熟。使用 EXPLAIN 查看时，如果看到 select_type 为 MATERIALIZED 或 DEPENDENT SUBQUERY 变为 SIMPLE，就说明优化生效了。

2. 物理优化（9.4 节）在 MySQL 5.7 中的体现
物理优化是为逻辑查询计划选择具体实现算法和访问路径。MySQL 优化器基于成本模型（Cost Model）进行选择，它会估算不同执行计划的 I/O、CPU 和内存成本。

核心决策点及 MySQL 5.7 示例：
a) 选择访问路径（单表）
•   问题：是直接全表扫描（Table Scan），还是使用索引？
•   MySQL 决策依据：优化器根据表的统计信息（如 cardinality，即索引列不同值的数量）来估算条件过滤掉的数据比例。

•   示例：
    SELECT * FROM employee WHERE last_name = 'Smith';
    ◦   如果 last_name 字段上没有索引，只能全表扫描。
    ◦   如果有索引 idx_last_name，优化器会判断：叫 ‘Smith’ 的人多不多？如果只占表的很小一部分（例如<10%），则使用索引扫描。如果‘Smith’非常多（比如占了50%），则可能认为全表扫描成本更低，因为省去了回表（如果索引不是覆盖索引）的随机I/O开销。

b) 选择连接算法（多表）
这是物理优化的重中之重。MySQL 5.7 主要支持以下连接算法：

1.  嵌套循环连接（Nested-Loop Join, NLJ）
    ◦   算法：驱动表（外表）的每一行，都与内表的所有行进行匹配。
    ◦   适用场景：这是 MySQL 的基本算法。当内表有高效索引（通常是连接条件的索引）时，性能非常好。
    ◦   EXPLAIN 输出：在 Extra 字段中不会有特殊提示。type 字段显示了内表的访问方式（如 eq_ref 表示通过主键或唯一索引查找，效率高）。

2.  基于块的嵌套循环连接（Block Nested-Loop Join, BNLJ）
    ◦   算法：当内表没有可用索引时，NLJ 性能极差（O(m*n)）。BNLJ 进行了优化：将驱动表的多行读入一个连接缓冲区（join_buffer），然后批量与内表进行比对，减少了内表的扫描次数。
    ◦   适用场景：内表无索引可用时的备用方案。如果表很大，join_buffer_size 设置过小，性能依然很差。
    ◦   EXPLAIN 输出：在 Extra 字段中会显示 Using join buffer (Block Nested Loop)。

3.  哈希连接（Hash Join）
    ◦   重要提示：MySQL 5.7 不支持真正的哈希连接！ 这是 MySQL 8.0 才引入的重大优化。在 MySQL 5.7 中，对于无索引的等值连接，你只能看到 BNLJ。这也是从 5.7 升级到 8.0 能带来巨大性能提升的一个重要原因。

如何查看 MySQL 5.7 的优化结果？

使用 EXPLAIN 命令是观察优化器决策的最佳工具。
EXPLAIN FORMAT=JSON 
SELECT e.name, d.dept_name 
FROM employee e 
JOIN department d ON e.dept_id = d.id 
WHERE e.salary > 10000;


•   EXPLAIN 输出中的关键字段：
    ◦   type：访问类型，如 ALL（全表扫描）、index（索引扫描）、range（范围扫描）、ref/eq_ref（索引等值查找）。性能从低到高。
    ◦   key：优化器决定使用的索引。
    ◦   rows：预估需要检查的行数。
    ◦   Extra：额外信息，如 Using where（在存储引擎层后过滤）、Using index（覆盖索引）、Using temporary（使用临时表）、Using filesort（需要额外排序）、Using join buffer（使用BNLJ算法）。

总结

对于 MySQL 5.7：
•   代数优化：优化器已经相当智能，会自动进行子查询转换、条件化简等。你的任务是尽量写出语义清晰的SQL。
•   物理优化：核心在于创建合理的索引，为优化器提供高效的访问路径。同时，要理解 BNLJ 是它在处理无索引连接时的唯一选择，需要注意其性能瓶颈。
•   与教材的差异：教材讲的是通用理论，而具体数据库实现会有差异。例如，MySQL 5.7 缺乏哈希连接和并行查询等高级特性，但这些在 Oracle、PostgreSQL 或 MySQL 8.0+ 中是存在的。

理解这些底层原理，能帮助你更好地设计表结构、索引，并解读 EXPLAIN 结果，从而进行高效的 SQL 调优。

并发控制的主要技术包括封锁（Locking）、时间戳（Timestamp）、乐观控制法（Optimistic Concurrency Control）和多版本并发控制（Multiversion Concurrency Control，MVCC）。见11.8。
封锁（Locking）：封锁是最基本的并发控制技术之一，它通过在数据对象上加锁来防止多个事务同时访问或修改同一数据对象。封锁可以分为共享锁和排他锁，共享锁允许多个事务同时读取同一数据对象，而排他锁则只允许一个事务独占数据对象。
时间戳（Timestamp）：时间戳是一种基于时间的并发控制技术，它给每个事务分配一个唯一的时间戳，并根据时间戳的顺序来决定事务的执行顺序。如果一个事务的时间戳早于另一个事务，则它必须等待另一个事务完成后才能执行。
乐观控制法（Optimistic Concurrency Control）：乐观控制法是一种基于事务之间不冲突的假设的并发控制技术。它允许多个事务同时访问和修改同一数据对象，但在提交事务时进行检查，如果发现冲突则进行回滚或重试。
多版本并发控制（Multiversion Concurrency Control，MVCC）：MVCC是一种基于多版本的并发控制技术，它允许多个版本的数据对象共存，并为每个事务分配一个唯一的时间戳。事务只能访问与自己时间戳相匹配的数据版本，从而避免了数据冲突。MVCC广泛应用于现代数据库系统中，如PostgreSQL和Oracle等。
这些并发控制技术各有优缺点，适用于不同的应用场景。选择合适的并发控制技术可以提高数据库的性能和并发处理能力。

MySQL、PostgreSQL（PGSQL）、Oracle和DB2等关系型数据库都使用封锁（Locking）技术来实现并发控制。
在MySQL中，封锁技术主要通过在数据表或数据行上加锁来实现。MySQL支持共享锁和排他锁，共享锁允许多个事务同时读取同一数据对象，而排他锁则只允许一个事务独占数据对象。MySQL还提供了一些锁定级别和锁定策略，例如表级锁、行级锁和页面锁等，以便更好地适应不同的应用场景。
在PostgreSQL中，封锁技术也是通过在数据对象上加锁来实现的。PostgreSQL支持多种类型的锁，包括共享锁、排他锁、意向锁等，以满足不同的并发控制需求。此外，PostgreSQL还提供了一些高级特性，例如死锁检测和处理、可重复读隔离级别等，以提高并发处理的性能和可靠性。
在Oracle中，封锁技术同样是重要的并发控制机制之一。Oracle支持多种类型的锁，包括表级锁、行级锁、分区锁等，以满足不同的并发控制需求。此外，Oracle还提供了一些高级特性，例如自动锁定管理、锁定升级和降级等，以提高并发处理的性能和可靠性。
在DB2中，封锁技术同样是重要的并发控制机制之一。DB2支持多种类型的锁，包括表级锁、行级锁、页面锁等，以满足不同的并发控制需求。此外，DB2还提供了一些高级特性，例如死锁检测和处理、可重复读隔离级别等，以提高并发处理的性能和可靠性。
总的来说，这些关系型数据库都使用封锁技术来实现并发控制，并根据不同的应用场景提供了多种类型的锁和一些高级特性来提高并发处理的性能和可靠性。

排他锁（Exclusive Lock，简称X锁）和共享锁（Shared Lock，简称S锁）是数据库中常用的两种锁类型，用于实现并发控制和事务隔离。
排他锁（X锁）：排他锁是一种独占锁，一旦一个事务获取了某个数据对象的排他锁，其他事务就不能再获取该数据对象的任何类型的锁，包括共享锁和排他锁。也就是说，其他事务无法读取或修改该数据对象，直到获取排他锁的事务释放了该锁。排他锁主要用于保证数据的一致性和完整性，例如在更新或删除数据时需要获取排他锁以防止其他事务同时修改同一数据对象。
共享锁（S锁）：共享锁是一种共享锁，多个事务可以同时获取同一个数据对象的共享锁，但是只能读取该数据对象，不能修改。也就是说，如果一个事务获取了某个数据对象的共享锁，其他事务也可以获取该数据对象的共享锁，但不能获取排他锁。共享锁主要用于提高并发性能，例如在查询数据时可以使用共享锁，允许多个事务同时读取同一数据对象。
需要注意的是，如果一个事务想要获取某个数据对象的排他锁，但是该数据对象已经被其他事务获取了共享锁，那么该事务必须等待其他事务释放共享锁后才能获取排他锁。同样地，如果一个事务想要获取某个数据对象的共享锁，但是该数据对象已经被其他事务获取了排他锁，那么该事务必须等待其他事务释放排他锁后才能获取共享锁。这就是锁的兼容性规则。
总之，排他锁和共享锁是数据库中常用的两种锁类型，用于实现并发控制和事务隔离。排他锁主要用于保证数据的一致性和完整性，而共享锁主要用于提高并发性能。在设计和优化数据库应用时，需要根据具体的应用场景选择合适的锁类型来平衡并发性能和数据一致性。

确切的控制由封锁的类型决定。基本的封锁类型有两种:排他锁(excusivelocks，简称X锁)和共享锁(sharelocks，简称S锁)。
排他锁又称为写锁。若事务T对数据对象A加上X锁，则只允许T读取和修改A，其他任何事务都不能再对A加任何类型的锁，直到T释放A上的锁为止。这就保证了其他事务在T释放A上的锁之前不能再读取和修改A。
共享锁又称为读锁。若事务T对数据对象A加上S锁，则事务T可以读A但不能修改A，其他事务只能再对A加S锁，而不能加X锁，直到T释放A上的S锁为止。这就保证了其他事务可以读A，但在T释放A上的S锁之前不能对A做任何修改。

在运用X锁和S锁这两种基本封锁对数据对象加锁时，还需要约定一些规则。例如，何时申请X锁或S锁、持锁时间、何时释放等。这些规则称为封锁协议(locking protocol)。

##### 11.6 两段锁协议 2 Pharse Lock
注意跟2PC
2 Phase Commit两阶段提交 区别开来
两段锁协议（2PL，Two-Phase Locking）和两阶段提交协议（2PC，Two-Phase Commit）都是分布式系统中的协议，但是它们的目的和应用场景是不同的。
两段锁协议是一种用于数据库并发控制的协议，它的核心思想是将事务的执行过程分为两个阶段：增长阶段和收缩阶段。在增长阶段，事务可以获得新的锁，但不能释放已有的锁；在收缩阶段，事务可以释放已有的锁，但不能获得新的锁。通过两个阶段的划分，两段锁协议可以避免死锁和饥饿等问题，保证并发控制的正确性和高效性。
两阶段提交协议是一种用于分布式事务处理的协议，它的核心思想是将事务的提交过程分为两个阶段：准备阶段和提交阶段。在准备阶段，协调者询问所有参与者是否准备好提交事务，参与者根据自己的状态给出答复；在提交阶段，协调者根据参与者的答复来决定是否提交事务。通过两个阶段的划分，两阶段提交协议可以保证分布式事务的一致性和原子性。
需要注意的是，虽然两段锁协议和两阶段提交协议都是分布式系统中的协议，但是它们的目的和应用场景是不同的。两段锁协议主要用于数据库的并发控制，而两阶段提交协议主要用于分布式事务处理。此外，它们的实现方式和锁的类型也不同，两段锁协议主要使用封锁技术，而两阶段提交协议则不涉及具体的锁类型。

PostgreSQL：PostgreSQL是一种流行的开源关系型数据库，它使用两段锁协议来实现并发控制。PostgreSQL提供了多种类型的锁，包括共享锁、排他锁、意向锁等，以满足不同的并发控制需求。
MySQL：MySQL也是一种流行的开源关系型数据库，它同样使用两段锁协议来实现并发控制。MySQL提供了表级锁和行级锁等多种类型的锁，以及不同的锁定策略和隔离级别，以便更好地适应不同的应用场景。
Apache Cassandra：Apache Cassandra是一种高性能的开源NoSQL数据库，它使用乐观并发控制和轻量级的锁定机制来实现高并发和高性能。虽然Cassandra不严格遵循两段锁协议，但它使用了一种类似的机制来实现并发控制。

以下是一个简单的 Linux C++ 实现两段锁协议（2PL）的示例：
```cpp
#include <iostream>  
#include <thread>  
#include <mutex>  
#include <condition_variable>  
  
using namespace std;  
  
// 共享资源  
int shared_resource = 0;  
  
// 互斥锁和条件变量  
mutex mtx;  
condition_variable cv;  
  
// 事务的状态  
enum TransactionState {  
    READY, // 事务准备就绪  
    WAITING, // 事务正在等待锁  
    COMMITTING, // 事务正在提交  
    ABORTED, // 事务被中止  
    COMMITTED // 事务已提交  
};  
  
// 事务的结构体  
struct Transaction {  
    int id; // 事务的ID  
    TransactionState state; // 事务的状态  
    mutex mtx; // 事务的互斥锁  
    condition_variable cv; // 事务的条件变量  
};  
  
// 获取共享资源的值  
int get_shared_resource() {  
    lock_guard<mutex> lock(mtx);  
    return shared_resource;  
}  
  
// 设置共享资源的值  
void set_shared_resource(int value) {  
    lock_guard<mutex> lock(mtx);  
    shared_resource = value;  
}  
  
// 事务开始执行  
void transaction_start(Transaction& trans) {  
    trans.state = READY;  
    trans.cv.notify_all();  
}  
  
// 事务尝试获取锁  
void transaction_try_lock(Transaction& trans) {  
    unique_lock<mutex> lock(trans.mtx);  
    trans.state = WAITING;  
    trans.cv.wait(lock, [&] { return trans.state == READY; });  
}  
  
// 事务释放锁  
void transaction_release_lock(Transaction& trans) {  
    unique_lock<mutex> lock(trans.mtx);  
    trans.state = COMMITTING;  
    trans.cv.notify_all();  
}  
  
// 事务提交  
void transaction_commit(Transaction& trans) {  
    unique_lock<mutex> lock(trans.mtx);  
    trans.state = COMMITTED;  
    trans.cv.notify_all();  
}  
  
// 事务中止  
void transaction_abort(Transaction& trans) {  
    unique_lock<mutex> lock(trans.mtx);  
    trans.state = ABORTED;  
    trans.cv.notify_all();  
}  
  
// 执行事务的函数  
void execute_transaction(int id) {  
    Transaction trans = { id, READY, mutex(), condition_variable() };  
    transaction_start(trans);  
    transaction_try_lock(trans);  
    // 在这里执行具体的操作，例如读取或修改共享资源的值等  
    set_shared_resource(get_shared_resource() + 1);  
    transaction_release_lock(trans);  
    transaction_commit(trans);  
}  
  
int main() {  
    // 创建多个线程执行事务  
    thread t1(execute_transaction, 1);  
    thread t2(execute_transaction, 2);  
    thread t3(execute_transaction, 3);  
    // 等待所有线程执行完毕  
    t1.join();  
    t2.join();  
    t3.join();  
    // 输出共享资源的值  
    cout << "Shared resource: " << get_shared_resource() << endl;  
    return 0;  
}
```

##### 11.8 其他并发控制机制
并发控制的方法除了封锁技术外还有时间戳方法、乐观控制法和多版本并发控制等。

TiDB 的并发控制

TiDB 的并发控制模型深受 Google Spanner 和 Percolator 论文的影响，其核心是 MVCC + 乐观事务（OCC）模型，并在新版本中加强了对悲观锁的支持。

1.  MVCC（核心机制）：
    ◦   TiDB 中的所有数据行都会包含多个版本，每个版本都有一个唯一的开始时间戳和结束时间戳（由全局授时中心分配）。

    ◦   读操作（如 SELECT）：默认在快照隔离（Snapshot Isolation, SI） 级别下运行。读操作会获取一个开始时间戳，然后读取在这个时间戳之前已经提交的最新数据版本。这保证了读操作永远不会被阻塞，也实现了非阻塞的读-写并发。

2.  分布式事务模型（决定写冲突的处理方式）：
    ◦   乐观事务模型（传统/默认）：

        ▪   阶段一（预提交）：事务在执行过程中，会将修改缓存在私有空间，不冲突的写操作可以并行执行。这是典型的OCC“读阶段”。
        
        ▪   阶段二（提交）：在提交时，事务会从全局授时中心获取一个唯一时间戳作为提交版本号。然后进行冲突检测（主要是检查写入键的版本是否发生变化），如果没有冲突，则将所有修改一次性原子地提交（写入公共存储）。如果冲突，则事务回滚。
        
        ▪   特点：在低冲突场景下吞吐量高，但在高冲突场景下（如多个事务修改同一行）回滚率高，性能下降明显。

    ◦   悲观事务模型（当前推荐和生产主流）：

        ▪   为了更好兼容 MySQL 生态和应对高冲突场景，TiDB 引入了悲观锁。
        
        ▪   执行过程：类似于传统数据库，在执行 UPDATE、DELETE 等语句时，会尝试获取对应行的排他锁。如果锁被其他事务持有，则当前事务会等待。
        
        ▪   提交：仍然使用两阶段提交，但冲突检测在获取锁时已经完成，大大降低了提交阶段的回滚概率。
        
        ▪   特点：行为更接近 MySQL InnoDB，减少了提交时的意外失败，更适合高冲突的OLTP场景。

OceanBase 的并发控制

OceanBase 同样以 MVCC 为基础，但其设计哲学更强调在分布式架构下实现极致的 OLTP 性能和高可用性。它的并发控制模型与 TiDB 有显著区别，更倾向于悲观锁优先。

1.  MVCC（核心机制）：
    ◦   与 TiDB 类似，OceanBase 也为每个数据行维护多个版本，每个版本带有时间戳信息。

    ◦   读操作同样基于快照隔离，读取特定时间戳下的数据一致性快照，实现读写不阻塞。

2.  分布式事务与锁管理：
    ◦   基于两阶段提交（2PC）和悲观锁：

        ▪   OceanBase 在处理分布式事务时，默认采用悲观锁机制。当一个事务需要修改数据时，它会立即向该数据所在的分片（Tablet）的 Leader 节点申请锁。
        
        ▪   锁是实时管理和持有的。这避免了像 TiDB 早期乐观模型那样在提交时才发现冲突。
        
        ▪   整个分布式事务的提交过程严格遵循两阶段提交协议，由事务管理器（Coordinator）协调所有参与者（Participants）共同完成提交或回滚。
        
        ▪   为了优化性能，OceanBase 实现了“单分区事务优化”，即如果事务只涉及一个分区，则可以走一阶段提交，极大降低延迟。

3.  全局时间戳服务（GTS）：
    ◦   OceanBase 使用一个高可用的、全局单调递增的时间戳服务（早期版本由RootService统一分配，后续版本有优化），为所有事务分配唯一且连续的时间戳。这有助于保证全局一致的快照和事务顺序，是实现强一致性的关键。

核心区别总结

特性 TiDB OceanBase

默认事务模型 从乐观转向悲观（目前生产环境推荐使用悲观事务） 悲观事务模型为主，锁实时获取。

冲突解决时机 乐观模型下：在事务提交时检测冲突，可能回滚。<br>悲观模型下：在DML语句执行时加锁等待。 在DML语句执行时立即加锁，避免提交时冲突。

设计侧重点 更侧重于高吞吐的混合负载（HTAP），其乐观模型适合写入量大但冲突相对较少的场景。 更侧重于低延迟、高并发的OLTP场景，其悲观模型适合对响应时间敏感、冲突较多的传统交易业务。

时间戳获取 通过 Placement Driver (PD) 组件提供全局授时。 通过全局时间戳服务（GTS）提供强一致的时间戳。

结论：
两者都是世界级的分布式数据库，它们都基于 MVCC 来提供高效的读并发和一致性快照。主要区别在于处理写冲突的哲学：
•   TiDB 提供了更灵活的选择（乐观或悲观），其架构更适合云原生和大规模扩展。

•   OceanBase 从一开始就为高并发、低延迟的金融级OLTP场景设计，其悲观锁和强一致性时间戳方案更注重稳定性和可预测性。

选择哪一种取决于你的具体业务场景（冲突概率、对延迟和吞吐量的要求等）。
