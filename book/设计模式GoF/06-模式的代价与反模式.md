# 第 6 章 模式的代价与反模式

> **一句话**：模式是**有代价的解决方案**，不是**无代价的装饰**——一个模式的「效果（Consequences）」段写完后就应立刻问一句：现在我们真的需要它吗？

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 模式的真实代价 | 间接层、类数目、理解成本、文档债务 | 原书自己写过：模式会「增加对象的数目」、「增加系统生成的复杂性」 |
| 过度设计与模式滥用 | YAGNI、提前抽象、为三个类套 Composite | 判据：加需求时是否必须改它 |
| 上帝对象与 Mediator | God Class、God Module、God 库 | 耦合没有消除，只是转移到了中间人身上 |
| 模式与语言的能力差异 | 语言自带 enum/lambda/struct/ranges 后，部分模式退化成噪音 | 语言能力变化时，模式清单会自动变短 |
| 经典反模式清单 | Golden Hammer、Shotgun Surgery、Cargo Cult、Magic Container | 反模式是「成功执行但错误选择」的模式 |
| 模式审查怎么做 | 记录动机、代价、退场条件 | 把「引入一个模式」当成需要理由的决策 |

## 核心精讲

### 1. 原书自己列出的代价（Consequences）

不是我们事后苛责，原书每一章的「Consequences」里就有这些条目：

| 模式的代价类型 | 原书里的具体例子 |
| --- | --- |
| **增加间接层** | Abstract Factory 引入的「产品族 × 产品等级」类矩阵；Proxy 的转发开销 |
| **牺牲可替换性/可测性** | Singleton 让依赖变成全局；Template Method 让子类无法独立于父类理解 |
| **增加状态与生命周期复杂度** | Prototype 的克隆语义；Memento 的快照管理；State 的迁移合法性 |
| **降低可预测性** | Observer 的更新顺序不确定；Chain of Responsibility 不保证被处理 |
| **阻碍重构** | Adapter 让旧接口长期存在；Flyweight 让外在状态散落在调用侧 |

> **读法提示**：把「代价」当作**退场条件（exit condition）**来写，即「什么情况下应该拆掉它」——这是本章最重要的操作建议。

### 2. 过度设计的三个典型场景

```cpp
// 教学示意，不参与构建、不编译、不运行
// 场景 A：只有一个实现的 Strategy —— 接口 + 两个类，其中一个只是空壳
struct Discount { virtual int apply(int price) const = 0; };
struct NoneDiscount : Discount { int apply(int p) const override { return p; } };
// 真正需要的是：int finalPrice(int p);   // 函数即可，不必抽象

// 场景 B：三个类的 Composite，没有递归语义
// 场景 C：为「未来可能要扩展」先把 Facade、Adapter、Registry、Factory 全写上
```

判据只有一条：**「新增一个需求时，这个模式会被改吗？」** 答案是否，就是噪音。

### 3. 上帝对象（God Object）与 Mediator 的失败模式

```cpp
// 教学示意，不参与构建、不编译、不运行
class ApplicationMediator {           // 典型的「协调一切」上帝对象
public:
    void onUserLogin(const User& u)      { authService_.login(u); audit_.log(u); notify_.to(u); mail_.send(u); }
    void onOrderPlaced(const Order& o)   { /* ... 又是一串协调 */ }
    void onPaymentDone(const Pay& p)     { /* ... 再一串 */ }
private:
    AuthService authService_; AuditLog audit_; NotifyService notify_; Mailer mail_;
    // 所有业务规则最终都写进这里，因为它「什么都知道」
};
```

**为什么这是反模式**：耦合没有消失，只是从「对象之间的横向引用」转移成了「Mediator 对一切的纵向掌握」。副作用：Mediator 无法只测一个用例；任何新交互都要改 Mediator（ shotgun surgery）；多人并行开发必然冲突集中。

**更好的切法**：事件发布-订阅（耦合方向明确、可异步）、职责下沉到领域服务（Mediator 只做编排不做规则）、或显式状态/策略分解。

### 4. 模式与语言能力：某些模式会退化成噪音

| 语言能力出现后 | 被替代的模式 | 退化后的代码 |
| --- | --- | --- |
| 一等函数 / lambda | **Command**、Strategy（一次性场景） | `auto job = [&]{ ... };` |
| 静态语言自带枚举与判别联合 | **State**（简单状态）、**Visitor** | `std::variant<A,B,C>` + `std::visit` |
| 值类型 / record / 不可变结构体 | **Builder**（字段少时）、**Memento**（不可变快照） | `Point{1, 2}` |
| 标准算法与 Ranges / Stream | **Iterator**（手写迭代器类） | `std::ranges::for_each(coll, f)` |
| 语言级智能指针 | **Proxy** 的「智能引用」 | `std::shared_ptr<T>` |
| 字符串常量池 / 结构体与类字面量复用 | **Flyweight**（语言内部已做） | 字面量即共享 |
| 闭包 + 泛型（Rust trait / C++ concepts） | **Decorator**（轻量包装） | `Box<dyn Fn()>` 或管道组合 |
| 注解与 AOP / 中间件管道 | **Decorator**（横切职责） | `app.use(logger); app.use(auth);` |

> 关键洞察：**模式的必要性取决于语言的表达力**。1994 年 C++ 没有 lambda、没有 Ranges、没有智能指针，所以那些样板是必要的；2026 年的语言把它们都内建了。**如果一段代码能用一个语言特性写完，它就不再是模式，只是代码。**

### 5. 经典反模式（Antipatterns）

| 反模式 | 含义 | 与模式的关系 |
| --- | --- | --- |
| **Golden Hammer**（锤子万能） | 「我们有一把锤子，所以所有东西都是钉子」——所有问题都用同一个模式解 | 模式的流行导致的选择偏误 |
| **Pattern Abuse / 模式滥用** | 为用模式而用模式，导致接口数量爆炸 | 回避了「先问变化点」的步骤 |
| **Cargo Cult**（教条式） | 抄模式的结构，不理解其情境与力量 | 形式正确、语义缺失 |
| **God Class / God Module** | 一个类知道并执行一切 | Facade/Mediator 用错时的必然产物 |
| **Shotgun Surgery**（霰弹式修改） | 一个需求要改十几个类 | Composite/Adapter/Factory 用错时的症状 |
| **Magic Container / 容器即上帝** | DI 容器里塞进一切，配置层比业务层还厚 | 创建型模式被容器的滥用 |
| **Abstract Factory Obesity** | 只有一个实现却建了整族工厂 | 提前抽象 |

## 版本演进

| 维度 | 1994 | 2010s | 2020s（今天） |
| --- | --- | --- | --- |
| 主流批评 | 模式数量太少、不成体系 | **模式被过度使用**（"patterns are being overused" 的争论） | **模式被语言与框架吃掉**，讨论转向「模式何时不必出现」 |
| 典型症状 | 缺词汇、缺复用 | 为三个类套 Composite；满仓库的 `*Factory`/`*Adapter` | 满仓库的 `*Builder`/`*Visitor` 样板，被 record/sealed 取代 |
| 治理手段 | 靠书籍与培训 | Code Review 里的「模式适用性问题」 | 架构决策记录（ADR）+ 模式审查 + 静态架构检查（依赖规则） |
| 与原则的关系 | 模式与 SOLID 尚在并行 | SOLID + DI 成为模式的前置秩序 | 「先满足 SOLID 与可读性，模式是结果的命名而非手段」 |

> 一句话概括三十年：**从「缺模式」到「模式滥用」再到「模式被语言吸收」**。今天读 GoF 的正确姿势是把它当**设计词汇与代价清单**，而不是模板库。

## 近年研究与工业界开源实践（2015–2026）

**趋势**：反模式的讨论重心从「某个项目用错了模式」转向「**架构为什么会朝着上帝对象与配置地狱演化**」，以及「**语言特性如何把模式变成噪音**」。工程上的应对是三件事：（1）用**架构决策记录（ADR）**把「引入模式的动机与退场条件」写下来；（2）用**静态依赖规则**（模块依赖检查）阻止 Shotgun Surgery 与 God Module；（3）用**语言新特性**重写样板层，使模式回到「真正的决策」。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `rust-lang/rust` | **119,149★** | Rust 的所有权与 trait 让「上帝对象」难以无约束生长；组合优先的语言文化直接抑制 God Class |
| `microsoft/TypeScript` | **111,192★** | 类型系统能提前捕获「接口 × 实现」矩阵的错误；判别联合压缩 Visitor 样板 |
| `spring-projects/spring-framework` | **60,260★** | 同时是「DI 容器解开耦合」与「Magic Container」反模式的现场，是观察两者边界的最佳样本 |
| `google/googletest` | **39,581★** | 测试里的「为 mock 而抽象接口」是过度设计的常见入口，也是治理经验最丰富的地方 |
| `facebook/folly` | **30,545★** | 用少量高复用原语（Function、Future、Singleton）替代大量一次性抽象，是反模式治理的正面范例 |
| `openjdk/jdk` | **23,379★** | 标准库演进史本身就是「模式被语言能力替代」的记录（`Observer` 被 `Function` 挤压） |
| `dotnet/runtime` | **18,298★** | `record`/`init` 与 `required` 成员在语言层削减 Builder 与工厂 |

## 常见误区与本书需修正之处

| 误区 | 现象 | 修正 |
| --- | --- | --- |
| 🔧 **只读「意图」，跳过「代价」** | 以为模式只有好处；结果上线后出现预期外的耦合与调试困难 | 把代价段当成必读，并写成退场条件（什么情况该拆掉它） |
| 🔧 **1994 的实现被当成最佳实践照抄** | 抄原书裸指针、手写引用计数的代码，今天毫无必要地变长 | 用智能指针/值语义/ranges 重写；样板压缩后再判断模式是否还成立 |
| 🔧 **对继承依赖过度宽容** | 需要新行为就加一个子类，继承树越深越难改 | 优先组合与函数参数化；CRTP、`std::function`、泛型策略 |
| 🔧 **Facade/Mediator 变上帝对象而无人发现** | 协调类吸收全部业务规则，导致所有变更集中在单点 |  mediator 只做编排、规则下沉；用依赖规则检查限制协调类的宽度 |
| 🔧 **把「用了设计模式」当成果汇报** | 简历与评审里只报模式名，不报解决的问题与代价 | 陈述「变化的点是什么、因此选择了哪个模式、放弃了什么」 |
| 🔧 **DI 容器被当成万能解药** | bean 数量远超真实组件数，配置层比业务层厚 | 只在装配边界用容器；把「值对象」留在容器外 |
| 🔧 **lambda 出现后仍手写 Command 类** | 只为一行逻辑建类，文件数暴涨 | 用 `std::function`/`Runnable`；需要撤销/重做/序列化时才保留类 |
| 🔧 **缺少模式审查环节** | 模式一旦引入便永久保留，即使需求早已消失 | 引入时记录 ADR，评审时问「这个变化点还在吗？」 |
