# 第 7 章 并发与协同模式对照（GoF 之外）

> **一句话**：GoF 的 23 个模式都假设「只有一个线程在跑」——本章补上真正用错 GoF 模式的重灾区：**并发语境下的模式**，以及它们与 POSIX/Java 并发库的对照。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| GoF 在并发下会变成什么 | Observer / Singleton / Iterator / Facade 的并发变体 | 单点思考「通知顺序、可见性、锁序、反注册」 |
| Active Object 主动对象 | 用「方法请求队列 + 调度线程」把方法调用变成异步 | 本质是 Command + Proxy 的组合，但不在 23 个之内 |
| Half-Sync / Half-Async | 同步层与异步层之间用「队列 + 观察者」桥接 | 原书 Ch4 讨论过，POSA 与 ACE 系统化 |
| Reactor / Proactor | 事件多路复用与完成通知两种 I/O 模型 | 现代事件循环（epoll/kqueue/io_uring、Node、Netty）的前身 |
| Thread-per-Request 与事件循环 | 两种并发风格的取舍 | GoF 全都没有覆盖；今天的选择是被运行时决定的 |
| 常见误用 | 在 Handler/Observer 里加锁、用 Singleton 做全局可变状态、Iterator 遍历时修改 | 这些正是「GoF 模式 + 并发」出事故的三个高频点 |

## 核心精讲

### 1. GoF 模式在并发语境下的四个变形

| GoF 模式 | 并发下的问题 | 并发版改法 |
| --- | --- | --- |
| **Observer（#19）** | 通知顺序不确定；观察者异常中断整轮；观察者未注销导致泄漏；同步通知造成惊群 | 改成「投递到事件队列 + 单一消费者串行处理」；或用响应式流的背压；用 `std::weak_ptr` 避免泄漏 |
| **Singleton（#5）** | 双重检查锁的亚语义问题；跨模块初始化顺序；析构竞态 | Meyers 单例 / `call_once` / 依赖注入的 scope；进程内唯一不等于「全局可变」 |
| **Iterator（#16）** | 遍历期间容器被修改；失效语义未定义；跨线程共享迭代器 | 快照迭代或 fail-fast；用不可变数据结构；用范围类型自带的所有权语义 |
| **Facade（#10）** | 门面把子系统内部实现透传出去，locking 散落到各子系统 | 门面成为「单一锁的边界」并明确记录在接口文档里，或不暴露内部句柄 |

```java
// 教学示意，不参与构建、不编译、不运行
// 观察者模式在并发下的最小正确形态：投递 + 单线程消费
class EventBus {
    private final LinkedBlockingQueue<Runnable> queue = new LinkedBlockingQueue<>();
    private final ExecutorService workers = Executors.newSingleThreadExecutor();

    public void post(Runnable event) { queue.add(event); }   // 发布者不直接调用观察者
    public void start() {
        while (true) {
            Runnable e;
            try { e = queue.take(); } catch (InterruptedException ex) { return; }
            workers.execute(e);                                // 消费串行化，顺序确定
        }
    }
}
```

### 2. Active Object 主动对象（不在 GoF 23 个之内）

**意图**：将**方法调用与方法执行解耦**，使调用方立即返回、执行发生在自己的线程上，从而**自然地实现并发**。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 组成：Proxy（外壳，方法放入队列）+ MethodRequest 队列 + Scheduler 线程 + Servant（真正执行者）
class ActiveObject {                       // 代理：调用方看到的是同步语义
public:
    void fireAndForget(int cmd) { enqueue([this, cmd]{ servant_.handle(cmd); }); }
    int futureResult()          { return result_.get(); }   // future 承载结果
private:
    void enqueue(std::function<void()> task);               // 任务队列（Command 模式）
    Servant servant_;                                       // 执行者
    ResultFuture result_;                                   // 结果通道
};
```

**与 GoF 的关系**：它是 **Command（#14）+ Proxy（#12）+ Future** 的组合，但它出现在 POSA（1996）与 ACE 里，**不在 GoF 的 23 个之内**。区别在于：GoF 关注「结构如何解耦」，Active Object 额外关注「**执行发生在哪个线程、生命周期归谁、异常如何传播**」。

### 3. Half-Sync / Half-Async 半同步/半异步

**意图**：在**同步编程的简易性与异步编程的高吞吐**之间取平衡：上层用同步方式写代码（便于推理），下层的 I/O 事件由异步机制驱动，两层之间用一个**队列 + 观察者**桥接。

```text
  同步层（业务代码，阻塞式调用）
        │   ↑ 用队列 + 通知把结果送回
   ┌────┴───────────────────────────┐
   │   队列（Queue）：跨层的唯一边界   │   ← 这里是 Half-Sync/Half-Async 的核心
   └────┬───────────────────────────┘
        │   ↓ 事件由异步循环（Reactor）驱动
  异步层（事件多路复用：epoll/kqueue）
```

原书 Ch1 曾讨论过类似思想（「同步与异步的混合」），POSA 与 ACE 把它系统化；今天它已内建进运行时（Node.js、Netty、Spring 的 WebFlux 与 Servlet 混合部署形态）。

### 4. Reactor 与 Proactor

| 维度 | Reactor | Proactor |
| --- | --- | --- |
| 通知含义 | 「**有事件可读/可写**」，需要应用自己发起读/写 | 「**读/写已完成**」，数据已在用户缓冲区 |
| 典型实现 | select/poll/epoll + 回调 | Windows IOCP、Linux io_uring（完成式语义的一部分） |
| 与 GoF 的关系 | 与 **Observer（#19）** 同构：事件源多播给处理器 | 与 **Async Command** 同构：请求 + 完成回调 |
| 今天的对应物 | 事件循环、Netty、Tokio、libuv | `io_uring` 的完成队列、Windows 异步 I/O |

```cpp
// 教学示意，不参与构建、不编译、不运行
// Reactor 骨架：一个事件循环 + 一组「事件处理器」（Chain of Responsibility 的味道）
while (not done) {
    int n = epoll_wait(ep, events, max, timeout);      // 多路复用等待
    for (i = 0; i < n; ++i) {
        Handler* h = static_cast<Handler*>(events[i].data.ptr);   // 分发
        h->handle_event(events[i].events);                        // 处理
    }
}
```

### 5. 并发编程里最常见的三个 GoF 误用

| 误用 | 后果 | 修正 |
| --- | --- | --- |
| 在 Observer/Handler 回调里加锁，而锁序与事件顺序相反 | **死锁** | 回调内不加锁，改为投递；锁只保护数据，不保护回调 |
| 用 Singleton 承载全局可变状态 | 并行测试互踩、热重载失效、多租户不可能 | 进程内唯一资源（连接/配置）可以单例；**可变业务状态绝不放单例** |
| 遍历共享容器时用 Iterator 并同时修改 | 未定义行为或崩溃 | 先快照，或用带原子性的遍历；C++ 里用带版本号的容器或不可变结构 |

## 版本演进

| 阶段 | 代表 | 对模式的影响 |
| --- | --- | --- |
| 1994 GoF | 无并发模式，全部假设顺序执行 | 这是最大的结构性缺口 |
| 1996 POSA / ACE | Active Object、Half-Sync/Half-Async、Reactor、Proactor、Guarded Suspension、 Balking 等进入模式家族 | 并发模式从「经验技巧」变成「有命名的设计」 |
| 2000s | Java `synchronized`/`Concurrent`、.NET TPL 之前时代的手写线程池 | 模式实现从「手写队列」变成「用标准库」 |
| 2011–2020 | C++11 线程内存模型、`std::async`、`jthread`/`stop_token`；Java 19 虚拟线程预览 | 手写 Active Object 被「线程池 + future」取代；虚拟线程让 Thread-per-Request 重新便宜 |
| 2015–2026 | 事件循环（Node/Netty/Tokio）、io_uring、`std::jthread`、`ExecutorService` 生态、结构化并发 | Reactor 成为默认运行时；Command/Observer 在并发侧被「任务 + 回调 + 背压」取代 |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：（1）**Reactor 被运行时内建**，应用层不再手写事件分发；（2）**虚拟线程/纤程让 Thread-per-Request 回潮**，Active Object 的实现价值下降；（3）**观察者被响应式流与队列化事件取代**，因为「通知顺序」在并发下始终是不可推理的；（4）GoF 并发语境的最大教训沉淀为一句话：**并发设计的核心约束不是结构，而是「谁在哪个线程上、什么时刻可见、异常去哪里」**。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `rust-lang/rust` | **119,149★** | tokio 运行时是 Reactor + Active Object 的现代范本；所有权让「跨线程共享」在编译期受限 |
| `swiftlang/swift` | **70,401★** | 结构化并发（async/await、Task group、child task 取消）把「生命周期」变成语言机制 |
| `facebook/folly` | **30,545★** | `folly::Executor`、`EventBase`、异步链；C++ 侧并发模式的工业级实现集合 |
| `openjdk/jdk` | **23,379★** | `java.util.concurrent`（Executors、CompletableFuture、Phaser）把 Active Object 的组件全部库化 |
| `dotnet/runtime` | **18,298★** | `Channel<T>` / `SemaphoreSlim` / async 流；Half-Sync/Half-Async 的现成件 |
| `google/googletest` | **39,581★** | 并发测试最难；「测试里发现单例污染」几乎每个项目都会遇到 |
| `boostorg/boost` | **8,581★** | `boost::asio` 是 Proactor/Reactor 的 C++ 事实标准实现 |
| `microsoft/TypeScript` | **111,192★** | Node 生态的事件循环 + libuv，是 Reactor 普及最广的证据 |

## 常见误区与本书需修正之处

| 误区 | 现象 | 修正 |
| --- | --- | --- |
| 🔧 **把 GoF 当并发设计指南** | 以为 23 个模式覆盖并发解法 | 并发模式在 POSA/ACE 里，见本章与 `book/C++并发编程实战2/` |
| 🔧 **在 Observer/Handler 回调里加锁** | 事件顺序与锁序相反导致偶发死锁 | 回调只做投递与记录，业务在有锁的保护区里执行 |
| 🔧 **用 Singleton 承载可变业务状态** | 并行测试互相污染、热重载失效 | 单例只用于「进程内唯一资源」；可变状态走注入 |
| 🔧 **Iterator 遍历时修改集合** | 未定义行为、崩溃或漏元素 | 快照遍历 / fail-fast 语义 / 不可变集合；修改走统一入口 |
| 🔧 **手写一个「Active Object」框架** | 自己造线程池，缺取消与异常传播 | 用 `std::jthread`+`stop_token`、`ExecutorService`、`tokio::spawn` |
| 🔧 **假设观察者通知是同步且有序的** | 依赖注册顺序的行为，在高并发下偶发失败 | 明确「顺序不保证」；需要顺序就串行化到单线程消费者 |
| 🔧 **把 Reactor 当成「高级 Observer」而不看它的边界** | 回调网络里异常与取消无处可去 | 明确错误传播通道与取消语义（这也是现代运行时的核心设计点） |
| 🔧 **1994 假设「没有线程」的代码直接搬到多线程** | GoF 结构不假想并发，天然可能不安全 | 加并发安全约束到模式的「不变式」里：不可变数据优先 |
