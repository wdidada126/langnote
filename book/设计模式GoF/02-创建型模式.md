# 第 2 章 创建型模式（Abstract Factory / Builder / Factory Method / Prototype / Singleton）

> **一句话**：创建型模式的共同命题是「**把 new 的那一刻放到可替换的地方**」——而 1994 年用类继承、2026 年用依赖注入容器，两者的代价完全不同。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Abstract Factory（#1） | 产品族的创建与使用的解耦 | 类数量按「族 × 等级」增长；只有一种实现时不值得用 |
| Builder（#2） | 构造流程与最终表示分离 | 最适合「必填/可选字段多且可校验」的不可变对象 |
| Factory Method（#3） | 创建动作交给子类决定 | 框架里最常见的扩展点；也是 Abstract Factory 的常见实现方式 |
| Prototype（#4） | 用克隆代替构造 | 初始化成本高时收益最大；核心风险是深拷贝语义 |
| Singleton（#5） | 唯一实例 + 全局访问点 | 代价：破坏可测试性与可替换性；今天更该被 DI 的 scope 或模块级变量取代 |
| 与 DI 容器的关系 | 容器吸收了工厂的「组装」职责 | 手写工厂的绝大部分价值已被容器完成，剩下的才是设计决策 |
| Singleton 的批判 | 隐藏依赖、并行初始化、测试污染 | 需要唯一性时优先「进程内唯一资源 + 显式注入」 |

## 核心精讲

### 1. Abstract Factory（抽象工厂，#1）

**意图**：提供一个创建**一系列相关或相互依赖**对象的接口，而无需指定它们的具体类。

```cpp
// 教学示意，不参与构建、不编译、不运行
// Abstract Factory 的最小骨架（C++ 风格）
struct Button { virtual void paint() const = 0; virtual ~Button() = default; };
struct TextBox  { virtual void render() const = 0; virtual ~TextBox() = default; };

struct GUIFactory {                       // 抽象工厂
    virtual ~GUIFactory() = default;
    virtual Button* createButton()  = 0;  // 每个产品等级一个工厂方法
    virtual TextBox* createTextBox() = 0;
};

struct WinFactory : GUIFactory {
    Button* createButton() override  { return new WinButton(); }
    TextBox* createTextBox() override { return new WinTextBox(); }
};
struct MacFactory : GUIFactory { /* ... */ };

void render(const GUIFactory& f) {        // 客户只依赖抽象工厂
    Button* b = f.createButton();
    b->paint();
    delete b;                             // 1994 的写法：客户负责销毁
}
```

**类图（文字版）**：`Client ──> AbstractFactory`（抽象），`WinFactory / MacFactory `实现之，两类产品 `AbstractProductA/B` 由工厂方法返回，产品族必须**同源**（同工厂产出的按钮与文本框风格配套）。

**代价**：每新增一个产品族，要改**每一个**具体工厂类（这是著名的「**违反开闭原则的横向扩展**」）。解决思路有多个：用 DI 容器按配置注册实现、用「工厂方法链 + 反射/注册表」、或用泛型把工厂参数化。

### 2. Builder（建造者，#2）

**意图**：将一个复杂对象的**构造过程与它的表示分离**，使得同样的构造过程可以创建不同的表示。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 传统 Builder：分步构造，最后一次性 build
class HttpRequest {
public:
    class Builder {
        std::string method_, url_;
        bool secure_ = false;
    public:
        Builder& method(std::string m) { method_ = std::move(m); return *this; }
        Builder& url(std::string u)    { url_    = std::move(u); return *this; }
        Builder& secure(bool s)        { secure_ = s; return *this; }
        HttpRequest build() const {           // 把「构造约束」集中在这里
            if (method_.empty()) throw std::invalid_argument("method required");
            return HttpRequest{method_, url_, secure_};
        }
    };
private:
    HttpRequest(std::string m, std::string u, bool s) : method_(std::move(m)), url_(std::move(u)), secure_(s) {}
};
// 用法：HttpRequest::Builder{}.method("GET").url("/").secure(false).build();
```

**适用场景**：参数 5 个以上、其中有必填项、希望对象**构造后不可变**、或构造流程本身要说清楚（「先校验半径再建圆」）。

### 3. Factory Method（工厂方法，#3）

**意图**：定义一个用于创建对象的接口，让**子类决定实例化哪一个类**；Factory Method 使一个类的实例化延迟到子类。

```cpp
// 教学示意，不参与构建、不编译、不运行
struct Document { virtual void open() = 0; virtual ~Document() = default; };
struct SpreadSheet : Document { void open() override { /* ... */ } };

struct Application {                       // 框架侧：模板方法里调用工厂方法
    virtual Document* createDocument() = 0;   // 工厂方法（扩展点）
    void newDocument() {
        Document* d = createDocument();        // 由子类决定造什么
        d->open();
        delete d;
    }
    virtual ~Application() = default;
};
struct MyApp : Application { Document* createDocument() override { return new SpreadSheet(); } };
```

### 4. Prototype（原型，#4）

**意图**：用**原型实例指定要创建的对象种类，并通过拷贝这个原型来创建新对象**。

```cpp
// 教学示意，不参与构建、不编译、不运行
struct Prototype {
    virtual ~Prototype() = default;
    virtual Prototype* clone() const = 0;      // 关键：克隆接口
};

struct PriceTag : Prototype {
    std::string sku;
    int cents = 0;
    PriceTag* clone() const override { return new PriceTag(*this); }  // 复制构造即原型
};
```

**要点**：
- 适合「构造成本高（要查库/要重算/要建连接）」，且新对象与已有对象只差少量字段。
- **风险**：浅拷贝会共享子对象，导致「改了副本、动了原件」；原型注册表（按 key 取原型）需要保证注册表里的原型是「干净样本」。

### 5. Singleton（单例，#5）——原书写法与现代写法对照

原书的实现提示（C++ 侧）主要讨论：如何防止多个实例（私有构造、静态方法返回引用）、如何在程序结束时正确销毁（**"Meyers singleton" 在书里以「用嵌套类的局部静态」的形式出现**），以及多线程环境下避免重复初始化。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 写法 A：Meyers 单例（C++11 起推荐：线程安全由语言保证，无显式锁）
class Logger {
public:
    static Logger& instance() {
        static Logger inst;      // C++11 起：局部静态变量的初始化是线程安全的
        return inst;
    }
    void log(const std::string& msg) { /* ... */ }
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
private:
    Logger() = default;
};

// 写法 B：双重检查锁（1994 的经典写法，今天没有理由再用）
class LegacySingleton {
public:
    static LegacySingleton* instance() {
        if (!p) {                       // 检查 1
            std::lock_guard<std::mutex> g(m);
            if (!p) { p = new LegacySingleton(); }  // 检查 2
        }
        return p;
    }
private:
    static LegacySingleton* p;
    static std::mutex m;
};
```

**Singleton 被现代实践批判的四条理由**：

| 理由 | 说明 |
| --- | --- |
| **隐藏依赖** | 调用方看不出它依赖一个全局状态；换环境（测试、多租户）就失效 |
| **破坏可测试性** | 多线程并行跑测试时状态互相污染；要重置单例只能加「仅供测试」的 reset 方法（这是反模式） |
| **并行初始化** | 多个单例之间存在初始化顺序依赖时，会退化成「静态初始化顺序不确定」的老问题 |
| **现代替代** | 需要「唯一」时：C++ 用「进程内唯一 + 显式注入」，Java 用 DI 容器的 scope（singleton / session / request），Rust 用 `OnceLock`/`LazyLock` 或 `static` 与 `Send + Sync` 契约 |

## 版本演进

| 模式 | 1994（C++ 98 / Smalltalk） | C++11/17/20 | Java 8/17 |
| --- | --- | --- | --- |
| Abstract Factory | 裸指针工厂 + 具体类矩阵 | 智能指针返回 + 工厂模板化；`std::unique_ptr<T>` 明确所有权 | 泛型 `Supplier<T>`、Spring 的 `BeanFactory` |
| Builder | 手写 Builder 类 | C++20 起可用**指定初始化 + 聚合初始化**大幅削减 Builder；`std::optional`/`expected` 表达可空与失败 | Java 16+ `record` + compact constructor 让不可变对象几乎不需要 Builder |
| Factory Method | 每个产品一个子类 | 把「工厂方法」换成函数对象/模板参数：模板参数即「创建策略」 | `IntFunction<T>`、`Supplier<T>`、SPI（`java.util.ServiceLoader`） |
| Prototype | 手写 `clone()` + 注册表 | 复制构造 + `std::variant` 更安全；复制语义由编译器保证 | `Cloneable` 已基本被视为设计缺陷（克隆绕过构造函数） |
| Singleton | 双重检查锁 / 静态指针 | **Meyers 单例**（推荐）；C++20 的 `std::once_flag`/`call_once` 更规范 | Java 5 起用 Enum 单例（防反序列化与反射攻击）；现代用框架 scope 或 `static final` 字段 |

> 一句话总结演进方向：**创建型模式的价值，从「怎么 new」转移到了「谁负责把依赖组装起来」**。1994 年这个问题没有好的答案，所以每一处都要手写工厂；今天大部分答案由 DI 容器和语言静态初始化提供。

## 近年研究与工业界开源实践（2015–2026）

**趋势**：创建型模式在主流工程里「退居幕后」——DI 容器成为事实上的 Abstract Factory + Factory Method；手写工厂的剩余价值集中在「跨语言边界」「带生命周期的复杂装配」「测试替身的运行时替换」。同时，语言级单例机制（Rust 的 `static`/`OnceLock`、Java 的 `record` + 容器 scope）让「唯一性」变成配置问题而不是设计问题。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `spring-projects/spring-framework` | **60,260★** | 工业级创建型模式实现：`BeanFactory` = Factory Method + Abstract Factory；`scope` 取代手写 Singleton |
| `google/guice` | **12,731★** | 轻量 DI 框架，直接把「手写工厂」压缩成一行注解；是「Singleton 应被注入取代」的主流论据 |
| `facebook/folly` | **30,545★** | `folly::Singleton` / `Lazy` 带销毁顺序保证；C++ 侧对「单例与程序生命周期」的工程化答案 |
| `openjdk/jdk` | **23,379★** | `java.util.ServiceLoader` 的 SPI 机制是 Factory Method 的官方范式；`Optional`/`record` 影响 Builder 的写法 |
| `dotnet/runtime` | **18,298★** | `IServiceCollection`/`IServiceProvider` 与 `Lazy<T>`；微软 DI 容器把作用域与释放语义标准化 |
| `rust-lang/rust` | **119,149★** | `std::sync::OnceLock` / `LazyLock` 提供语言级延迟初始化，同时保证 `Send + Sync` 契约 |
| `google/googletest` | **39,581★** | 测试里最常见的「单例污染」现场；Test Double 的替换策略几乎等同于「手动 DI」 |

## 常见误区与本书需修正之处

| 误区 | 现象 | 修正 |
| --- | --- | --- |
| 🔧 **Singleton 写成「防止被 new」就算数** | 只锁了构造，忽略初始化顺序、销毁顺序、多模块重复初始化 | C++11 用 Meyers 单例或 `call_once`；有跨模块初始化依赖时改用「延迟到首次访问」的显式初始化函数 |
| 🔧 **Singleton 破坏测试性** | 为跑并行测试给单例加 `resetForTest()`，正式代码里出现测试专用开关 | 把唯一性交给注入：`Logger&` 构造函数注入；确需全局时用容器 scope |
| 🔧 无「扩展需求」仍用 Abstract Factory | 只有一个产品族的实现，却有两个工厂类 | 先用 Factory Method 或直接 `std::function`；扩展点出现后再升级为 Abstract Factory（见 `book/重构*` 的做法） |
| 🔧 **1994 的裸指针实现被照抄** | `createButton()` 返回裸指针，调用处漏 `delete` 造成泄漏 | C++ 用智能指针明确所有权语义；Java 用 `Supplier<T>` / Spring bean |
| 🔧 **Prototype 用浅拷贝** | 副本与原型共享子对象，改副本影响原型 | 明确「深拷贝/共享」的语义并在克隆方法注释里写死；或干脆不用克隆，改用「复制构造 + 字段覆写」 |
| 🔧 **Builder 过度膨胀** | 每加一个字段就改 Builder 类，Builder 比 Product 还长 | 字段少用可变构造参数；字段多用 `record`/聚合初始化；只在「有多步约束」时才完整 Builder |
| 🔧 **把 DI 容器当万能** | 所有类都变成 bean，config 类里填八层配置 | 容器解决「对象装配」，不解决「对象内部设计」；组件数量与循环依赖是需要治理的信号 |
| **工厂方法被当成 new 的包装** | `new Foo()` 外面套一层 `createFoo()` | 只有当「创建哪一族产品」本身是可扩展点时才成立；否则那只是增加调用栈 |
