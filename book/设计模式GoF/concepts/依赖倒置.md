# 专篇：依赖倒置（Dependency Inversion）

> **一句话**：GoF 的创建型模式解决「谁来创建」，依赖倒置（DIP）解决「谁来定方向」——**方向定错了，Singleton 和手写工厂就成了必然**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| DIP 的两条规则 | 高层策略不依赖低层细节；细节依赖抽象 | 抽象的「所有权」必须归高层 |
| 与 GoF 创建型模式的对应 | Singleton/Factory 的失败大多是 DIP 违反 | 唯一性交给容器，方向交给注入 |
| 控制的三种形态 | 构造注入 / 属性注入 / 服务定位器（定位器是伪装成 DI 的服务） | 构造函数注入最利于可测试性 |
| 在模式层面的结果 | State/Strategy/Observer 的抽象归谁 | 抽象不是「接口集合」，是「高层意图」 |
| 常见误用与修正 | 为注入而注入：容器里全是组件、值对象也变成 bean | 只在装配边界使用容器 |

## 核心精讲

### 1. DIP 的两条规则

1. **高电平策略不应依赖于低层细节**。低层细节应当依赖于高电平策略（反过来也成立）。
2. **抽象不应依赖于实现细节**。细节应依赖于抽象。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 违反 DIP：高层策略（OrderService）依赖了具体细节（MySQLOrderRepository）
class OrderService {
public:
    void place(const Order& o) { mysqlRepo_.save(o); }     // 硬依赖具体类
private:
    MySQLOrderRepository mysqlRepo_;                        // 「创建」与「方向」双双绑定
};

// 遵守 DIP：抽象由高层定义，低层实现它，创建交给外部
class OrderRepository {                                     // 抽象归高层
public:
    virtual ~OrderRepository() = default;
    virtual void save(const Order&) = 0;
};
class MySQLOrderRepository : public OrderRepository { void save(const Order& o) override { /* ... */ } };

class OrderService {                                        // 高层只依赖抽象
public:
    explicit OrderService(std::shared_ptr<OrderRepository> repo) : repo_(std::move(repo)) {}
    void place(const Order& o) { repo_->save(o); }
private:
    std::shared_ptr<OrderRepository> repo_;                 // 实现由外部注入
};
```

### 2. DIP 与 GoF 创建型模式的因果关系

| GoF 模式 | 若方向反了会怎样 | 按 DIP 的正确做法 |
| --- | --- | --- |
| **Singleton（#5）** | 全局单例被当成「配置服务」，谁都能改它 → 测试无法隔离 | 唯一性作为**生命周期属性**由容器提供（scope），依赖通过构造注入 |
| **Factory Method（#3）** | 框架提供 `createDocument()`，子类却依赖框架细节 → 框架被反向依赖 | 抽象由**使用方**（高层）定义，框架只实现它 |
| **Abstract Factory（#1）** | 产品族的具体类被硬编码进工厂，策略层被迫依赖具体类 | 产品族抽象与容器配置同处高层 |
| **Builder（#2）** | Builder 持有具体类型的复杂初始化逻辑，成了上帝构造者 | 初始化逻辑属于「装配边界」，而不是业务类 |

### 3. 控制的三种形态（以及为什么其中一种是伪 DI）

| 形态 | 写法 | 评价 |
| --- | --- | --- |
| **构造函数注入** | `OrderService(std::shared_ptr<OrderRepository>)` | 依赖**显式可见**、易于测试、顺序确定；首选 |
| **属性/设值注入** | `svc.repo = repo;` | 适合可选依赖；会让对象在「未注入」状态下存在 |
| **服务定位器（Service Locator）** | `ServiceLocator::resolve<OrderRepository>()` | **伪装成 DI 的反模式**：依赖被隐藏，测试要改全局配置；只有跨语言边界（遗留系统/插件宿主）才勉强可用 |

```java
// 教学示意，不参与构建、不编译、不运行
// 服务定位器：看起来是解耦，实际上依赖被藏进了全局
class Locator {
    private static final Map<Class<?>, Object> REGISTRY = new HashMap<>();
    @SuppressWarnings("unchecked")
    static <T> T get(Class<T> type) { return (T) REGISTRY.get(type); }
}
// 问题：调用方（OrderService）对 OrderRepository 的依赖在类里完全看不出来，
//      测试时必须先改全局注册表 —— 这正是 Singleton 被批判的原因之一。
```

### 4. DIP 在行为型模式里的表现

- **Strategy（#21）**：抽象（策略接口）必须由**使用算法的客户**定义，而不是由算法提供者定义。经典的「接口放置错误」就是把 `ZipCompression` 放进 `Compression` 的接口里。
- **State（#20）**：状态接口的定义者是「上下文」，而不是各个状态类。
- **Observer（#19）**：主题与观察者的共同抽象（事件模型）属于**高层**，否则观察者会被迫依赖主题的细节类型。
- **Template Method（#22）**：这是 DIP 的**反例**——模板方法恰恰要求低层去依赖高层的骨架，因此它总是与依赖倒置原则冲突。这就是为什么现代框架更倾向「函数参数化 + 组合」而不是模板方法。

### 5. 常见误用

| 误用 | 现象 | 修正 |
| --- | --- | --- |
| 为注入而注入 | 每个类都加一个接口，接口比实现还多 | 只在有**两个以上实现或需要测试替身**时抽象 |
| 值对象也进容器 | `Money`、`Point` 变成 bean，配置层比业务层厚 | 值对象用普通构造/`record`，留在容器外 |
| 抽象放在低层包里 | 「领域接口」定义在数据库包内，高层被迫降依赖方向 | 抽象（接口）与实现分离到不同包，接口归高层 |
| 用服务定位器冒充 DI | 代码里充满 `Locator.get()`，测试靠改全局 | 改用构造函数注入；跨宿主边界才考虑定位器 |
| 把 DIP 当成「所有依赖都要注入」 | 连日志、时钟都要注入又造一个 wrapper | 判断依据是「是否需要替换/是否需要测试替身」 |

## 版本演进

| 阶段 | 主流做法 |
| --- | --- |
| 1994（GoF 语境） | 依赖方向靠「工厂 + 继承」硬扛；Singleton 与手写的 Factory 是唯一务实选择 |
| 2002（SOLID 成型） | DIP 被列为第五原则；「依赖应通过抽象」成为设计评审条目 |
| 2007–2010（Java 企业栈） | 重量级容器（EJB/J2EE）与轻量容器（Guice/Spring）成熟，构造函数注入普及 |
| 2014 之后 | **构造函数注入**成为事实标准（C++/Java/Kotlin/Rust 皆然）；服务位置器退居边缘 |
| 2020 年代 | 编译期 DI（Kotlin Koin、Rust 的 `Dependency` 宏/显式传参）减少运行时反射惩罚；「纯函数 + 显式参数」进一步压缩容器需求 |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：（1）**构造函数注入成为跨语言共识**，服务定位器被主流实践视为反模式；（2）**容器职责收缩**——只做装配，不做业务，值对象与本领域对象留在容器外；（3）**编译期/显式 DI 兴起**（Kotlin、Rust、Go 的显式传参），减少反射与运行时代理；（4）**「纯函数优先 + 显式依赖」**让最内层的代码几乎不需要容器。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `spring-projects/spring-framework` | **60,260★** | DIP 的工业化实践：构造函数注入、组件扫描、scope（取代手写 Singleton） |
| `google/guice` | **12,731★** | 轻量 DI，注解驱动的构造函数注入，是「Singleton 应被注入取代」的经典论据 |
| `facebook/folly` | **30,545★** | C++ 侧「显式依赖 + 少量原语」的代表：不使用运行时容器，而用组合与注入 |
| `rust-lang/rust` | **119,149★** | 依赖通过函数参数与 struct 字段显式表达，编译期确定，无运行时容器 |
| `dotnet/runtime` | **18,298★** | `IServiceCollection` 与 `ActivatorUtilities` 把装配语义标准化 |
| `openjdk/jdk` | **23,379★** | SPI（`ServiceLoader`）是「抽象由调用方定义、实现可在运行时替换」的标准范式 |
| `microsoft/TypeScript` | **111,192★** | 构造函数注入在 JS 生态常见（NestJS/TSyringe），类型系统让契约可检查 |

## 常见误区与本笔记需修正之处

| 误区 | 现象 | 修正 |
| --- | --- | --- |
| 🔧 **Singleton 被当作「最简单」的依赖管理** | 全局单例承载可变状态，并行测试互相污染 | 唯一性用容器 scope 表达，状态通过构造注入 |
| 🔧 **服务定位器冒充 DI** | 依赖藏在 `Locator.get()` 里，测试改全局配置 | 改构造函数注入；定位器仅用于宿主/插件边界 |
| 🔧 **接口被「抽象化」到无法表达意图** | 接口方法集合巨细无遗，实现方被迫实现无关方法 | 抽象只保留高层需要的行为 |
| 🔧 **为测试而抽象** | 每个类都配一个 `IFoo`，只为 mock 一个纯函数 | 纯函数直接测；只有有状态且有替换需求才抽象 |
| 🔧 **把 DIP 与 Template Method 混为一谈** | 用模板方法实现依赖倒置，结果子类依赖父类细节 | 依赖方向要倒置时，改用组合与注入；模板方法不适合倒置 |
| 🔧 **容器变成全局配置文件** | 配置层比业务层厚，编译无法发现装配错误 | 容器只在装配边界；值对象与本领域对象留在容器外 |
