# 专篇：观察者与响应式（Observer ⟶ Reactive Streams）

> **一句话**：GoF 的 Observer（#19）是「同步通知的多播」，响应式流是它的**带背压的异步版本**——差别不在名字，而在「谁决定流速」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Observer 的四个隐藏契约 | 顺序不确定、异常会中断、忘记反注册、同步造成惊群 | 这四条不是 bug，是原书 Consequences 段写下的代价 |
| 推模型 vs 拉模型 | 主题推数据 / 观察者自己拉 | 数据小且观察者都关心 ⟶ 推；数据大或可能不关心 ⟶ 拉 |
| 响应式流的三要素 | `Publisher`/`Subscriber`/`Subscription` + backpressure | 把「通知速率」变成可协商的契约 |
| 冷热 Observable | Cold 每次重播 / Hot 共享实时流 | 选择错误会直接造成事件丢失或重复消费 |
| 与 Event Sourcing 的关系 | 备忘录（#18）与事件日志 | 事件溯源是 Observer 的时间维度扩展 |
| 常见误用 | 订阅里加锁、跨线程订阅、忘记退订 | 与 `07-并发与协同模式对照.md` 的三条高频事故一致 |

## 核心精讲

### 1. Observer（#19）的四个隐藏契约（原书写明过的代价）

| 契约问题 | 原书的说法 | 症状 |
| --- | --- | --- |
| **更新顺序不确定** | 观察者注册顺序不等于通知顺序 | 两个观察者互相依赖时偶发失败 |
| **不保证被处理** | 若没有观察者，通知静默结束 | 事件被吞掉，无日志无告警 |
| **异常会中断整轮通知** | 一个观察者抛错，后续不再被通知 | 局部错误变成全局故障 |
| **观察者生命周期** | 忘记 `detach` 时非 GC 语言会泄漏 | 主题持有观察者，整棵对象树无法释放 |

```cpp
// 教学示意，不参与构建、不编译、不运行
// 一个「只投递、不直接调用」的 Observer，解决上面的四契约问题
class EventBus {
public:
    using Handler = std::function<void(const Event&)>;
    Subscription subscribe(Handler h);        // 返回句柄，析构即退订（RAII）
    void publish(const Event& e) {
        for (auto& h : handlers_) {
            try { h(e); } catch (const std::exception& ex) { errors_(ex); }   // 逐个隔离
        }
    }
private:
    std::vector<Handler> handlers_;           // 简化示意；生产实现需考虑订阅期间被修改
};
```

### 2. 推模型与拉模型

```text
推模型（Push）：主题 → 观察者    "我变了，这是数据"
   - 优点：观察者不用关心如何取，接口窄
   - 适合：数据小、观察者都关心同一份完整数据（UI 绑定最常见）

拉模型（Pull）：主题 → 观察者 → 主题 "我变了，我自己来取"
   - 优点：观察者可以只取需要的字段（省带宽/省计算）
   - 适合：数据量大、观察者可能只关心子集（数据库物化视图、缓存失效）
```

原书倾向于**推模型**（"推一个默认实现，拉一个更灵活的实现"），但工程上真正的分界是：
**「主题是否知道观察者需要多少？」** 不知道就别推太多。

### 3. 响应式流：把「通知速率」变成契约

```java
// 教学示意，不参与构建、不编译、不运行
// Reactive Streams 的最小契约（Java 生态接口形态）
interface Publisher<T> {
    void subscribe(Subscriber<? super T> s);
}
interface Subscriber<T> {
    void onSubscribe(Subscription s);        // 拿到「流速控制权」
    void onNext(T item);                      // 收到一项
    void onError(Throwable t);                // 出错终止
    void onComplete();                        // 正常终止
}
interface Subscription {
    void request(long n);                     // 背压：我要 n 个
    void cancel();                            // 我不要了
}
```

**为什么背压是决定性的**：GoF 的 Observer 假设通知无限快、处理无限快；一旦生产者远快于消费者，同步通知就会把整个调用栈拖垮（惊群 + 堆积）。响应式流把「谁慢谁说了算」写成协议，`request(n)` 就是这条协议的核心。

### 4. 冷 Observable vs 热 Observable

| 维度 | Cold（冷流） | Hot（热流） |
| --- | --- | --- |
| 订阅时 | 每次订阅**重新产生**数据 | 订阅时订阅已存在的流，可能错过之前发生的数据 |
| 示例 | 文件读取、数据库查询、HTTP 请求 | 鼠标事件、Socket 数据、UI 事件 |
| 风险 | 多次订阅 = 多次副作用 | 错过事件（必须处理连接窗口/重放缓存） |
| 工程选择 | 需要「可重放、可测试」数据时用 Cold | 需要「实时、共享」时用 Hot |

### 5. 与 Memento（#18）/ 事件溯源的关系

- GoF 的 **Memento（#18）**保存的是「**状态快照**」，用于回到过去。
- **事件溯源（Event Sourcing）**保存的是「**事件序列**」，通过重放重建状态。
- 二者是同一个问题的两个方向：**要恢复状态时，你是存「结果」还是存「过程」？**
  - 快照：恢复快，但丢失过程，无法解释「怎么变成这样」。
  - 事件日志：可解释、可审计、可重放，但恢复需要重放全部或做快照+增量。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 快照 + 事件日志的混合：定期快照 + 增量事件，即典型工程折中
struct Snapshot { std::vector<Event> events; };      // Memento 的形态
std::vector<Snapshot> snapshots;                      // 周期性快照
std::deque<Event>    pending;                         // 快照之间的增量事件
```

## 版本演进

| 阶段 | 形态 |
| --- | --- |
| 1994 | GoF：手写的 `attach/detach/notify` + 观察者接口 |
| 2000s | JMS、消息中间件；观察者被「消息总线」制度化 |
| 2007–2010 | .NET `IObservable<T>`/`IObserver<T>` 落地（Rx.NET 的前身） |
| 2013–2015 | **Reactive Streams 规范**发布，RxJava/RxJS/Project Reactor 陆续实现；`request(n)` 成为标准 |
| 2017 | Reactive Streams 规范定稿；Java 9 的 `java.util.concurrent.Flow` 纳入 JDK |
| 2019 起 | Reactor/RxJava 3 的普及；UI 层大量改用「数据流 + 声明式绑定」 |
| 2020 年代 | 协程/异步流（`Flow<T>`、Kotlin `SharedFlow`）把冷热的语义重新拉回语言层；响应式管道进入主流 UI 与后端 |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：（1）**背压成为默认契约**，异步管道取代同步通知；（2）**冷热语义被语言化**（Kotlin `Flow`、`SharedFlow`、Swift `AsyncSequence`、Rust 的 channel + `select!`）；（3）**事件总线泛滥被视为反模式**——导致可追踪性下降，工程上转向「显式领域事件 + 明确订阅清单」；（4）**测试**成为观察者实现的主要难点：确定性顺序、重试、幂等。

## 常见误区与本笔记需修正之处

| 误区 | 现象 | 修正 |
| --- | --- | --- |
| 🔧 **依赖注册顺序决定通知顺序** | 「我先注册 A 所以 A 先跑」，在并发与重订阅下失效 | 明确顺序不保证；需要顺序就串行化到单线程消费者 |
| 🔧 **订阅里加锁导致死锁** | 主题持有锁时通知，观察者又去拿另一个锁 | 回调只投递，处理在有锁的保护区里 |
| 🔧 **忘记退订** | 短生命周期观察者被长生命周期主题持有，内存泄漏 | RAII 句柄（析构自动退订）或弱引用订阅 |
| 🔧 **一个订阅者抛异常中断整轮通知** | 局部错误扩散 | 逐个 try/catch 隔离，错误送专门的错误通道 |
| 🔧 **同步通知造成惊群** | 高频事件下所有观察者一起变慢，最终压垮调用栈 | 引入背压/批量/合流，降低通知频率 |
| 🔧 **所有通信都走事件总线** | 调试链路极长、"谁改了我的状态"无法回答 | 只在领域边界用事件；查询用直接调用，保持可追踪 |
| 🔧 **把 Memento 与事件溯源混淆** | 快照无限增长，或重放成本不可控 | 定期快照 + 增量事件；明确审计需求 |
