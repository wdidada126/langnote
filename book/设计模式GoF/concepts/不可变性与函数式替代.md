# 专篇：不可变性与函数式替代

> **一句话**：GoF 的很多模式是在「状态可变」的世界里为了防止混乱而生的——**先让状态不可变，有些模式就不需要了**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 为什么 1994 年必须可变 | 没有 lambda、没有值类型标准库、并发靠锁 | 可变是默认，模式就是补丁 |
| 不可变对象的收益与代价 | 可推理、可共享、可测试；代价是对象多、构造复杂 | 变的是「复制成本」，不是「复制本身」 |
| 被不可变性替代的模式 | State、Memento、Strategy、Flyweight、Builder 的一部分 | 有需求就进，无需求就不造 |
| 持久化数据结构 | 结构共享让「不可变 + 复制」变便宜 | C++ 的 `std::string` SSO/COW、Rust 的 `Rc`、HashMap 的持久化实现 |
| 函数式组合替代部分模式 | 管道、折叠、偏函数、类型状态 | 命令链 ⟶ 表达式 |
| 常见误用 | 为不可变而不可变，性能崩塌；可变性藏在同一份数据的公开字段里 | 明确「不可变边界」放在哪儿 |

## 核心精讲

### 1. 为什么 1994 年可变是默认

- 对象创建成本高（无值语义、无移动语义、无标准容器语义），**原地修改比复制便宜**。
- 并发模型靠锁与共享内存，共享可变状态是常态。
- 语言上没有「不可变列表」这类标准件，所以 GoF 提供了 **Flyweight（#11）** 来共享、**Memento（#18）** 来保存、**Prototype（#4）** 来复制。

### 2. 不可变对象的收益与代价

```cpp
// 教学示意，不参与构建、不编译、不运行
// 可变版本：原地改，一次只有一个对象，但状态历史无处可查
struct MoneyMutable {
    double amount = 0;
    void add(double d) { amount += d; }        // 改了别人手里的副本看不见
};

// 不可变版本：每次「修改」都产生新值，旧值自动存活
struct Money {
    double amount;
    Money(double a) : amount(a) {}
    Money plus(double d) const { return Money(amount + d); }   // 返回新值
};
// Money m{100}; auto m2 = m.plus(5);   // m 仍是 100，m2 是 105
```

| 收益 | 代价 |
| --- | --- |
| 推理简单：值不随时间变化 | 每次「更新」都要分配新对象 |
| 天然线程安全（只要发布安全） | GC/分配压力上升（高频更新场景明显） |
| 可缓存、可共享、可重放 | 构造复杂字段多时需要 Builder 或工厂辅助 |
| 测试容易：不需要重置共享状态 | 大对象整体复制代价高（需要持久化数据结构缓解） |

### 3. 被不可变性替代的模式

| 模式 | 在可变世界里的用途 | 不可变世界的替代 |
| --- | --- | --- |
| **State（#20）** | 用状态对象切换行为 | 用类型状态或纯函数：`enum` 状态 + 纯函数分派；非法状态无法构造 |
| **Memento（#18）** | 保存内部状态以便回滚 | 不可变快照本身就是历史（持久化数据结构的版本链） |
| **Strategy（#21）/ Command（#14）** | 用对象承载可替换行为 | 函数对象/闭包，`std::function` 一行 |
| **Flyweight（#11）** | 共享细粒度对象省内存 | 值语义与常量池让共享变成默认（字符串字面量即共享） |
| **Builder（#2）** | 分步构造复杂对象 | 少字段用聚合/`record` 初始化；多步约束仍然需要 Builder |
| **Observer（#19）** | 状态变化时通知观察者 | 数据流/响应式管道；或干脆用「值 + 派生计算」 |
| **Singleton（#5）** | 持有全局可变配置 | 不可变配置一次性构建，注入到各处 |

```java
// 教学示意，不参与构建、不编译、不运行
// State 的不可变替代：数据 + 纯函数，而不是「状态对象决定行为」
record Order(int items, boolean paid) {
    boolean canShip() { return paid && items > 0; }   // 行为跟着数据走，无状态切换
}
// 需要「行为随状态变化」时，用穷尽匹配的纯函数比状态类层次更便宜：
static String label(Order o) {
    return switch (o) {
        case Order(int i, boolean p) when p && i > 0 -> "shipping";
        case Order(int i, boolean p) when i > 0     -> "awaiting payment";
        case Order(int i, boolean p)                -> "empty";
    };
}
```

### 4. 持久化数据结构：让「不可变 + 复制」变便宜

- **结构共享**：更新一棵树只重建被改的那条路径，其余节点与旧版本共享。
- C++/Java 里：`std::string` 的短串优化与写时复制（COW）是语言级的小持久化结构；`immutable.js`/PCollections 是 Map/List 的持久化实现。
- Rust 里：`Rc<T>`/`Arc<T>` 的克隆即浅拷贝 + 引用计数，天然是「共享的不可变图」。

### 5. 函数式组合替代命令链

```python
# 教学示意，不参与构建、不编译、不运行
# 命令式：一条条的语句，状态被逐步修改
result = []
for row in rows:
    if row.active:
        result.append(row.total() * 0.9)

# 函数式：命令链变成一次表达式，没有中间状态
result = [row.total() * 0.9 for row in rows if row.active]
discount = lambda r: r.total() * 0.9        # 这就是 Strategy 的一行版
```

这类替代的适用边界：变换是**无副作用的数据流**时最香；一旦需要「事务、重试、异步、可撤销」，就要回到显式的命令对象与显式状态机。

### 6. 不可变边界应该放在哪儿

| 建议 | 说明 |
| --- | --- |
| 领域层的**值对象** | 金额、日期、坐标、标识符：一律不可变 |
| 跨线程共享的数据 | 不可变 + 安全发布 = 免锁 |
| 高频写入的运行时状态 | 不必强求不可变；用锁或专用并发容器 |
| 组件的公开字段 | 一旦公开可变字段，等于把内部可变性泄漏给调用方（GoF 时代常见） |

## 版本演进

| 阶段 | 与不可变性的关系 |
| --- | --- |
| 1994 | 可变是默认；Flyweight/Memento/Prototype 是它的成本 |
| 2000s | Java 的 `String` 不可变、C# 的 `readonly`；函数式语言（Haskell/Scala）把不可变作为默认 |
| 2014+ | **C++11 的移动语义**：「复制的成本」被大幅降低；`const` 成为默认推导方向 |
| 2016+ | **Kotlin `val` / Java `record` / Rust 所有权的不可变默认**：不可变从「风格」变成「语言默认值」 |
| 2020s | 持久化数据结构与「值语义优先」成为主流库的设计约束；不可变让并发模式大幅简化（无锁读取路径） |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：（1）**不可变成为语言默认值**——Kotlin `val`、Java `record`、Rust 所有权、C++ 移动语义，让「不可变」不再是风格选择；（2）**并发代码里不可变的收益最明显**——读取路径无锁、可见性问题消失；（3）**持久化数据结构进入主流库**（不可变 Map/List、结构共享）；（4）反方向的代价也清楚：把「高频运行时状态」也强制不可变，会导致对象分配暴增，此时可变 + 所有权/锁更合适。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `rust-lang/rust` | **119,149★** | 所有权与 独占可变借用 `&mut'：不可变共享与可变独占由类型系统区分 |
| `microsoft/TypeScript` | **111,192★** | `readonly`、`as const`、判别联合让不可变在 JS 静态类型层可表达 |
| `swiftlang/swift` | **70,401★** | `let` 默认、值类型（struct/enum）语义、写时复制（COW） |
| `spring-projects/spring-framework` | **60,260★** | 不可变配置对象（`@ConfigurationProperties` 绑定）与不可变 bean 的边界 |

| `dotnet/runtime` | **18,298★** | `record`、`init` 访问器、`required` 成员、`ImmutableArray<T>` |

## 常见误区与本笔记需修正之处

| 误区 | 现象 | 修正 |
| --- | --- | --- |
| 🔧 **为不可变而不可变** | 高频运行态也走「产生新对象」，分配暴增 | 值对象不可变；高频运行态用可变 + 锁/并发容器 |
| 🔧 **可变性从公开字段泄漏** | 内部不可变，却暴露可变集合引用 | 返回不可变快照或只读视图（`List.copyOf`/`const` 视图） |
| 🔧 **Builder 当成不可变的唯一路径** | 少字段也写一套 Builder | 聚合初始化/`record` 即可；Builder 留给多步约束 |
| 🔧 **Flyweight 必要性被高估** | 对象不多也做享元池，得到复杂度而非性能 | 只在字符、小对象、字面量共享等真正受益处做 |
| 🔧 **Memento 快照无限增长** | 每次操作存全量快照，内存线性上涨 | 差分快照 + 定期全量，或改事件日志 |
| 🔧 **把无副作用等同于不可变** | 参数被偷偷改，I/O 里藏可变全局 | 边界输入后转成不可变值，副作用显式化 |
| 🔧 **1994 的可变假设被照搬** | 手写引用计数与裸 `delete` 的原型/享元实现 | 用值语义与智能指针，把「能否修改」交给类型系统 |
