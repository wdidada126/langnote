# 第 4 章 行为型模式（Chain of Responsibility / Command / Interpreter / Iterator / Mediator / Memento / Observer）

> **一句话**：行为型模式的共同对象是「**职责分配与消息流向**」——它们决定了「事件从哪来、谁响应、响应完之后谁接着干」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Chain of Responsibility（#13） | 请求沿链传递，直到有人处理 | 现代形态就是中间件/过滤器管道；必须保证有兜底 |
| Command（#14） | 把请求封装成对象（支持撤销、排队、宏） | lambda 之后退化成一行；真需求是撤销/重做/日志 |
| Interpreter（#15） | 解释一门语言的句子 | 只适合 DSL；通用语言要用 parser generator |
| Iterator（#16） | 顺序遍历聚合而不暴露内部结构 | Ranges / Stream / 迭代器协议已经把它语言化 |
| Mediator（#17） | 用中介封装对象间交互 | 上帝对象的重灾区；可用事件总线替代直接引用 |
| Memento（#18） | 保存并恢复对象内部状态 | 快照可能很贵；要警惕不可序列化字段 |
| Observer（#19） | 主题变化时通知观察者 | 现代形态是响应式流与事件总线；要注意反注册与异常隔离 |

## 核心精讲

### 1. Chain of Responsibility 职责链（#13）

**意图**：让多个对象都有机会处理请求，从而解除「发送者」与「接收者」的耦合；请求沿链传递，直到某个对象处理它。

```cpp
// 教学示意，不参与构建、不编译、不运行
class Handler {
public:
    virtual ~Handler() = default;
    virtual bool handle(const Request& req) = 0;     // 返回 true 表示「我处理了」
    void setNext(std::shared_ptr<Handler> n) { next_ = std::move(n); }
protected:
    std::shared_ptr<Handler> next_;
    bool tryNext(const Request& req) {                 // 链上的传递逻辑
        return next_ && next_->handle(req);
    }
};

class AuthHandler : public Handler {
    bool handle(const Request& r) override {
        if (!r.authenticated) return true;   // 拦截
        return tryNext(r);                    // 放行给下一个
    }
};
// 组装：auth -> rateLimit -> validate -> log ；末端必须有「兜底处理」否则请求静默丢失
```

**推模型 vs 拉模型**：原书区分「纯职责链」（中断即结束）与「管道」（每个节点都可能加工请求再交给下一个）。现代中间件（ASP.NET `HttpContext` 可改写响应）属于后者。

### 2. Command 命令（#14）

**意图**：将一个请求封装为一个对象，从而可用不同的请求、队列或日志参数化客户端；并支持**撤销/重做**。

```cpp
// 教学示意，不参与构建、不编译、不运行
struct Command {
    virtual ~Command() = default;
    virtual void execute() = 0;
    virtual void undo()   = 0;
};

class MoveCommand : public Command {         // 命令 = 动作 + 接收者
public:
    MoveCommand(Grid& g, int from, int to) : grid_(g), from_(from), to_(to) {}
    void execute() override { grid_.move(from_, to_); }
    void undo()   override { grid_.move(to_, from_); }
private:
    Grid& grid_;
    int from_, to_;
};

// 调用记录栈即可实现撤销/重做
std::vector<std::unique_ptr<Command>> history;
```

**现代写法**：C++ 里 `std::function<void()>` 加一个 lambda 就是一次性的命令；Java 里 `Runnable` / `Consumer<T>` 直接替代；需要「可序列化的工作单元 / 分布式事务日志」时才值得一个完整的命令类。

### 3. Interpreter 解释器（#15）

**意图**：给定一门语言，定义它的**文法**表示，并定义一个解释器，使用该表示来解释语言中的句子。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 一个最小的布尔表达式解释器
struct Expr { virtual ~Expr() = default; virtual bool eval() const = 0; };
struct AndExpr : Expr {
    bool eval() const override { return lhs_->eval() && rhs_->eval(); }
    std::unique_ptr<Expr> lhs_, rhs_;
};
struct NotExpr : Expr {
    bool eval() const override { return !sub_->eval(); }
    std::unique_ptr<Expr> sub_;
};
struct LitExpr : Expr {
    explicit LitExpr(bool v) : v_(v) {}
    bool eval() const override { return v_; }
    bool v_;
};
// 真正的工程做法：用 parser generator（ANTLR/Coco/Yacc）生成 AST 与 visitor，
// 而不是手写递归下降再手写一遍 eval —— Interpreter 模式只在 DSL 场景成立。
```

**适用边界**：四类文法——正则、算术表达式、配置 DSL、查询语言。对一门「通用语言」（C++/Java 本身），应该去写编译器而不是解释器模式。

### 4. Iterator 迭代器（#16）

**意图**：提供一种方法顺序访问一个聚合对象中的**各个元素**，而又**不暴露该对象的内部表示**。

```cpp
// 教学示意，不参与构建、不编译、不运行
template <typename T>
class Range {
public:
    struct iterator {
        T* p;                                   // 简单指针实现的迭代器
        T& operator*()  const { return *p; }
        iterator& operator++() { ++p; return *this; }
        bool operator!=(const iterator& o) const { return p != o.p; }
        bool operator==(const iterator& o) const { return p == o.p; }
    };
    explicit Range(T* b, T* e) : begin_(b), end_(e) {}
    iterator begin() const { return iterator{begin_}; }
    iterator end()   const { return iterator{end_}; }
private:
    const T* begin_; const T* end_;
};
```

- 原书区分「内部迭代器」（`forEach`，控制流在聚合内）与「外部迭代器」（客户拿着走，支持多游标、可比较位置）。
- **需要注意**：随机访问容器用索引更快；并发修改需要 fail-fast 或快照语义；C++20 Ranges、Java Stream、Python 的迭代协议、JavaScript 的 `Symbol.iterator` 都把「手写迭代器类」变成了例外。

### 5. Mediator 中介者（#17）

**意图**：定义一个中介对象来**封装一系列对象之间的交互**，使对象之间不需要显式地互相引用，从而降低耦合，且可独立地改变交互方式。

```cpp
// 教学示意，不参与构建、不编译、不运行
class ChatRoom;                                   // 中介者
class Person {
public:
    void send(const std::string& msg) { room_->broadcast(*this, msg); }  // 不再直接引用其它 Person
    explicit ChatRoomMediator(ChatRoom* r);
private:
    ChatRoom* room_;
};

class ChatRoom {                                  // 中介者集中了所有交互规则
public:
    void broadcast(const Person& p, const std::string& msg) {
        for (auto& other : people_) other.receive(p.name(), msg);
    }
private:
    std::vector<Person*> people_;
};
```

**代价是最致命的**：所有「对象交互规则」集中到 Mediator 里，它立刻成为 `GodClass`。原书自己也承认「中介者可能会变得庞大难以维护」——这就是「模式反模式」里点名的第一条。

### 6. Memento 备忘录（#18）

**意图**：**在不破坏封装性的前提下**，捕获一个对象的内部状态，并在该对象之外保存这个状态，这样以后就可将该对象**恢复到原先保存的状态**。

```cpp
// 教学示意，不参与构建、不编译、不运行
class Editor;                                     // 发起人
class Memento {                                   // 窄接口：只有 Caretaker 能读写
public:
    virtual ~Memento() = default;
private:
    friend class Editor;                          // 用友元（C++）表达「封装不被破坏」
    explicit Memento(std::string state) : state_(std::move(state)) {}
    std::string state_;
};

class Editor {
public:
    std::unique_ptr<Memento> save() { return std::make_unique<Memento>(buffer_); }
    void restore(const Memento& m) { buffer_ = /* 从 m 读回 */; }
private:
    std::string buffer_;                          // 内部状态
};
```

**要点**：快照要**不可变**且**可序列化**；含线程、连接、文件句柄的对象不能整体快照，需要拆出「可保存的状态」与「运行时资源」。

### 7. Observer 观察者（#19）

**意图**：定义对象间的一种**一对多**的依赖关系，当一个对象的状态发生变化时，所有依赖于它的对象都得到通知并被自动更新。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 推模型：主题把「足够完整的数据」推给观察者（原书 favour 的方向）
class Subject {
public:
    void attach(std::shared_ptr<Observer> o) { observers_.push_back(std::move(o)); }
    void detach(const std::shared_ptr<Observer>& o) { /* 按身份移除 */ }
    void notify() { for (auto& o : observers_) o->update(state_); }
protected:
    int state_ = 0;
private:
    std::vector<std::shared_ptr<Observer>> observers_;
};
class Observer {
public:
    virtual ~Observer() = default;
    virtual void update(int state) = 0;
};

// 拉模型：主题只发通知，观察者自己来取数据（适合数据量大、观察者可能不关心全部）
// void notify();  // 主题只说「我变了」，观察者调用 subject.getState()
```

**原书指出的具体问题**：（a）意外的更新（级联通知难以控制）；（b）更新顺序不确定；（c）一个观察者出错会破坏后续通知；（d）**内存泄漏**——观察者忘记 `detach` 时，非 GC 语言里主题持有观察者导致整棵对象树无法释放；（e）同步通知容易造成「惊群」性能问题。

## 版本演进

| 模式 | 1994 | C++11/17/20 | Java 8/17 / 现代 |
| --- | --- | --- | --- |
| Chain of Responsibility | if/else 或 switch 的巨型链 | `std::function<bool(Request)>` 组成的管道；`std::vector` 顺序执行 | Servlet filter、ASP.NET middleware、gRPC interceptor |
| Command | 每个命令一个类 | `std::function<void()>` + lambda；命令栈即 undo/redo | `Runnable`/`Consumer<T>`；.Command 在 UI 与任务队列里仍常见 |
| Interpreter | 递归下降 + 表达式树 | 用 `std::variant` + `std::visit` 表达 AST；或用 Expression Templates 编译成函数对象 | JavaCC/ANTLR 生成 tree-walking interpreter；`ScriptEngine` |
| Iterator | 手写 Iterator 接口 + 具体迭代器类 | **C++20 Ranges**：`begin()/end()` + concepts + 管道操作符 | Java Stream（内部迭代）、`Iterable`、Python 迭代器协议 |
| Mediator | 一个 `Mediator` 接口 + 具体中介 | 事件总线 / `std::shared_ptr` 解耦 + 观察者；或状态图（boost::msm） | Spring `ApplicationEventPublisher`、消息总线 |
| Memento | 手写快照类 + 友元/包可见性 | `std::optional<T>` 快照 + 不可变值；差分快照节省内存 | 序列化快照（Java 序列化/`record`）；事件溯源（Event Sourcing） |
| Observer | 手写 attach/detach/notify | `std::shared_ptr` 弱引用避免泄漏；也可 `observe_on` 语义化 | `Observable`（Java 9 起标记过时）⟶ **Reactive Streams**（`Publisher`/`Subscriber`，带 backpressure） |

> 一句话总结：**行为型模式是 lambda 与响应式范式冲击最大的一类**。Command、Strategy、Observer 在 2014 年之后大面积退化成闭包与订阅；**剩下的真实需求**是「可撤销」「有背压」「要跨进程」。

## 近年研究与工业界开源实践（2015–2026）

**趋势**：（1）**观察者被响应式流水线替换**——`Publisher/Subscriber` 规范 + backpressure，让「通知风暴」变成流量控制问题；（2）**职责链被中间件管道制度化**——每个 Web 框架都有成熟的 filter 链，程序员不再手写；（3）**Iterator 被标准算法库与 Ranges 彻底覆盖**；（4）剩下的痛点集中在「Observers 在分布式环境下的顺序与幂等」以及「Mediator 的边界如何切分」。

| --- | --- | --- |
| `facebook/react` | **250,713★** | React 的 state 订阅机制是 Observer 的极简现代形态（订阅 + 差异比较 + 批量更新） |
| `rust-lang/rust` | **119,149★** | `tokio` 生态的事件循环与 `trait Observer`，把「通知」变成类型安全的通道 |

## 常见误区与本书需修正之处

| 误区 | 现象 | 修正 |
| --- | --- | --- |
| 🔧 **只用 Command 却不需要撤销/排队** | 为一个按钮动作建 5 个命令类 | 用 lambda / `std::function`；只有「可序列化、可重放、可撤销」才需要一个类 |
| 🔧 **Mediator 变成上帝对象** | 中介者类吸收了全部业务规则，「协调」和「业务逻辑」混在一起 | 让 Mediator 只做编排，规则放状态/策略；或改用事件发布-订阅，让耦合方向明确 |
| 🔧 **Observer 通知顺序不确定导致 bug** | 两个观察者互相依赖更新顺序，偶发失败 | 要么按优先级显式排序，要么让观察者无顺序依赖（幂等）；不要靠「注册顺序」赌行为 |
| 🔧 **观察者忘记反注册导致内存泄漏** | 长生命周期主题持有短生命周期观察者（C++ 尤其明显） | 用 `std::weak_ptr` 持有观察者；或生命周期对齐（观察者退出即自动解绑） |
| 🔧 **一个观察者抛异常中断整轮通知** | 通知循环里某个订阅者崩溃，其余订阅者收不到事件 | 逐个 try/catch 隔离，并把异常记进错误通道；或改用「投递 + 异步消费」 |
| 🔧 **手写 Iterator 类** | 只为了 `for` 一次遍历却写了完整迭代器接口 | 用标准算法/范围 for；需要自定义遍历先考虑生成器（Python generator、C++20 协程） |
| 🔧 **用 Interpreter 实现一门通用语言** | 手写递归下降 + 手写求值，缺类型系统缺报错定位 | 用 parser generator + visitor；DSL 才适合 Interpreter 模式 |
| 🔧 **1994 年的同步通知假设** | 原书假定 notify 是同步、无背压 | 现代实现要显式处理背压（Reactive Streams、`stop_token`/`CancellationToken`、批量与合流） |
