# 第 1 章 引言与模式系统

> **一句话**：原书 Ch1 回答「设计为什么这么难、模式是什么」；Ch2 回答「模式怎么写、怎么分类、彼此是什么关系」——这两章决定了后面 23 个模式该怎么读。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 面向对象编程的「四要素」 | 抽象、封装、多态、继承 | 继承是本书 23 个模式里 **Template Method / Bridge / State / Visitor** 的地基，也是它最大的包袱 |
| 1.2 设计为什么会「不那么优雅」 | 依赖绑定过紧、过于特定于领域、修改的副作用、层次划分不当 | 模式的动机来自「复用与演化的矛盾」，不是来自「代码不够漂亮」 |
| 1.3 什么是设计模式 | 一组「命名、抽象、可用于多种情境的解决方案」 | 模式的四要素：名称、问题、解决方案、效果（后果） |
| 1.4 模式的分类学 | 创建型 / 结构型 / 行为型（按「变化点」划分） | 分类的依据是**让什么保持稳定**：创建型稳定「造什么」，结构型稳定「怎么拼」，行为型稳定「怎么协作」 |
| 1.5 模式与框架（Framework）的区别 | 模式是设计决策，框架是可复用的半成品程序 | 框架调用你的代码（ inversion of control），模式只是被记录和命名的决策 |
| 1.6 如何写一个模式 | 动机、适用性、结构、参与者、协作、效果、实现、代码示例、已知应用 | 本书每个模式的 9 段式描述是后来的 UML + 设计文档的模板 |
| 1.7 模式之间的关系 | 依赖、相似、互补、冲突、因果 | 例如 Abstract Factory 常用 Factory Method 实现；Facade 与 Mediator 都是「中间人」但职责不同 |
| 1.8 本书的取舍 | 只收录「面向对象机制」相关的模式，不做架构模式、不做并发模式 | 这是本书最大的限定条件（见 `00` 第 4 节） |

## 核心精讲

### 1. 模式的四个要素（原书对「模式」的定义）

原书给模式的判断标准可以压缩成四问，用来判断「你发现的那个结构算不算一个模式」：

| 要素 | 要回答的问题 | 反例（不算模式的东西） |
| --- | --- | --- |
| **名称** | 它叫什么？ | 一个只在单个文件里出现的私有函数 |
| **问题** | 在什么情境下、什么力量在起作用？ | 「代码有点乱」 |
| **解决方案** | 这个情境下达到平衡的结构与协作关系 | 一堆具体类 |
| **效果** | 用它换来什么、又付出了什么？ | 只有好处没有代价的口号 |

> 「效果（Consequences）」是原书写得最诚实的一节。原书 1.1 节的著名论断大意是：**你无法一步到达好的设计**，必须**迭代地修改系统**，同时保持「已完成的劳动成果的形态」——这就是模式存在的理由。

### 2. 面向对象的基本要素，以及它们的代价

原书用一句话概括面向对象设计的困难，翻成今天的话：**「把职责分给谁」决定了「改一处要动几处」**。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 说明：原书 1.1 节的「四要素」最小可运行骨架（C++ 风格，非任何标准）

// 抽象与封装：把「形状」的变化点封闭在派生类里
struct Drawing {                     // 一个最简单的「被稳定下来的 abstraction」
    virtual ~Drawing() = default;
    virtual int area() const = 0;    // 稳定的操作接口
};

struct Square final : Drawing {
    int side = 0;
    int area() const override { return side * side; }
};

// 继承带来的「紧耦合」：改 Draw() 的实现要回到基类
struct Box {
    virtual void draw() { /* 具体绘制写死在这里 */ }
    virtual ~Box() = default;
};
```

**原书对继承的态度是双面的**：它既是 Template Method / State / Bridge 的实现手段，也是「难以改变依赖于具体实现的操作」的根源。原书 1.1 节给出的建议是：**优先用对象组合（composition）而非类继承来取得效果的实现（"favor composition over inheritance"）**——这句话后来被广为引用，很多读者却是从 *Design Patterns* 里第一次读到的。

### 3. 模式 vs 框架：控制反转的方向

| 维度 | 设计模式 | 框架（Framework） |
| --- | --- | --- |
| 形态 | 一段设计决策、一个被命名的结构 | 一个可运行的半成品程序（Eclipse、JUnit、Spring、.NET） |
| 复用方式 | 你按模式写代码 | 你填框架留出的扩展点 |
| 控制流 | 你的代码调用你的代码 | **框架调用你的代码**（`protected virtual` / `template` / 回调） |
| 粒度 | 类级、文件级 | 应用级、模块级 |
| 关系 | 模式常被**内建**在框架里（JUnit 用了 Template Method 与 Command，Servlet 用了 Adapter/Decorator，Spring 用了 Factory Method 与 Proxy） | 框架是模式的容器与示范 |

> 一个很好的自检问题：**你想引用的是一个模式，还是一个框架？** 如果只是为了让代码「看起来专业」而给三个类套上 Composite 的接口，那是把模式用成了形状。

### 4. 模式的分类学：按「变化点」划分

```java
// 教学示意，不参与构建、不编译、不运行
// 用一行代码定位「这是哪一类模式」
// 1) 创建型：new 的那一刻需要被替换/被延迟/被共享
//    AbstractFactory / Builder / FactoryMethod / Prototype / Singleton
// 2) 结构型：对象之间的「拼装方式」需要被替换
//    Adapter / Bridge / Composite / Decorator / Facade / Flyweight / Proxy
// 3) 行为型：对象之间「谁跟谁说话、谁先说」需要被替换
//    ChainOfResponsibility / Command / Interpreter / Iterator / Mediator
//    Memento / Observer / State / Strategy / TemplateMethod / Visitor
```

分类的**判据不是「模式有多高级」，而是「你打算稳定住哪一个变化点」**：

- 想让「产品种类」变化 ⟶ 创建型（Abstract Factory / Factory Method / Prototype）
- 想让「组合方式」变化 ⟶ 结构型（Bridge / Decorator / Proxy）
- 想让「算法与职责的分配」变化 ⟶ 行为型（Strategy / State / Command / Chain of Responsibility）

### 5. 模式之间的关系图（文字版）

```
                    Abstract Factory ──(常用 Factory Method 实现)──> Factory Method
                             │
                             └──(产品族配套)──> 保证 ProductA/B 同源
                    Singleton ◄──(常)── Prototype   // 原型注册表 + 唯一实例
                    Composite ◄──(常)── Decorator   // 都要求「组件接口一致」
                    Observer  ◄──(常)── Command     // 通知时把命令对象当载荷投递
                    Mediator  ✕ Facade               // 都是中间人：Mediator 协调交互，Facade 简化接口
                    State     ══ Template Method     // 都靠继承/多态改变行为，State 是运行期切换，TM 是编译期确定
                    Visitor   ✕ Composite            // Visitor 对操作开放、对元素封闭；Composite 反之
```

**冲突（Conflicting）**的一对典型例子：Facade 想隐藏子系统，而 Observer 想让子系统向外广播——需要决定「广播出去的信息是否被 Facade 过滤」。

### 6. 原书 9 段式模式模板

原书每个模式都按同样的骨架描述，读久了就能「扫一眼目录知道全篇结构」：

| 段落 | 内容 |
| --- | --- |
| Intent 意图 | 一句话说清它做什么 |
| Motivaion 动机 | 一个真实场景，通常是「某处发生了变化」（（原书段落名 Motivation） |
| Applicability 适用性 | 什么时候用它（原书给的是一系列「适用性」列表） |
| Structure 结构 | 类图（UML 之前用 OMT 图） |
| Participants 参与者 | 每个类的职责 |
| Collaborations 协作 | 谁调用谁 |
| Consequences 效果 | **代价**（原书最值得读的部分） |
| Implementation 实现 | 语言相关的实现提示、策略（如「用 C++ 实现 Singleton 要注意 delete 的顺序」） |
| Known Uses 已知应用 | 真实系统里谁用过（Smalltalk 的 Model-View 框架是主要例证） |

## 版本演进

| 维度 | 1994（原书） | 现代写法 |
| --- | --- | --- |
| 描述工具 | **OMT** 类图（Grady Booch 的方法学）+ 文字模板 | UML / PlantUML / Mermaid 类图；模式描述模板被 wiki 化 |
| C++ 侧 | 裸指针、`delete`、无标准容器语义、无智能指针 | 智能指针、`std::variant`、`concept`、`std::span`；很多模式实现从「几十行类层次」缩到「十几行」 |
| Java 侧 | 1994 年 Java 尚未发布 | 泛型、`default` 方法、`record`、`sealed interface`；模板文件基本被框架吃掉 |
| 分类学 | 三分法（创建/结构/行为） | 三分法仍是主流词汇，但社区补充了「并发模式」「架构模式」「企业集成模式」「反模式」等维度 |
| 「模式 vs 框架」 | 1994 年框架概念刚普及 | 今天的「框架」≈ GoF 模式 + DI 容器 + 运行时；**很多 GoF 模式被框架内置** |
| 模式写作 | 手写 OMT 图 | 生成式：PlaneDraw/PlantUML 从代码生成类图，与模式的「结构」段落自动对应 |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：2015 年之后，「新模式」的产出明显放缓，研究与工程讨论的重心从「发明模式」转向「**模式何时不该出现**」以及「**语言/框架如何吃掉模式**」。同时，模式作为**沟通词汇**的生命力反而更强了（Code Review、面试、UML 书里）。三条主线：

1. **类型系统与语言特性持续吞掉模式样板**：Rust 的 trait + 所有权、Java 的 record/sealed、C++ 的 Ranges 与 Concepts，都让若干模式退化成一行语言构造。
2. **DI 容器与模块化运行时接管创建型模式**：Singleton 被 DI 的 scope（singleton/request/transient）取代，Factory 被容器注入取代。
3. **模式审查（pattern review）进入架构治理**：把「引入一个模式」当成一个需要理由与代价记录的决策，而不是默认选择。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `rust-lang/rust` | **119,149★** | 语言层面的替代方案：trait 对象、enum 分派让 Strategy/State 省掉一整层继承 |
| `microsoft/TypeScript` | **111,192★** | 结构化类型 + `readonly` 让 Flyweight/不可变设计写法变轻；record 与 sealed 家族的参照 |
| `swiftlang/swift` | **70,401★** | `protocol` + `any`/`some` + `Result`  Builder，`mirror` 让部分 Builder/Adapter 样板消失 |
| `spring-projects/spring-framework` | **60,260★** | 现代版的创建型模式集合：BeanFactory 即 Factory Method + Abstract Factory 的工业化实现 |
| `google/googletest` | **39,581★** | xUnit 家族本身就是 Template Method（测试骨架固定、步骤留给子类）与 Command 的实例 |
| `facebook/folly` | **30,545★** | C++ 工业库：`folly::Singleton` 是 Meyers 单例的工程化、带 Destroy 保证的版本 |
| `openjdk/jdk` | **23,379★** | 标准库里的模式标本：`java.util.Iterator`（Iterator）、`javax.servlet.Filter`（Chain of Responsibility）、`Executor`（Command） |

## 常见误区与本书需修正之处

| 误区 | 现象 | 修正 |
| --- | --- | --- |
| 🔧 **把模式当成目标** | 「为了用设计模式而重构」，三个类硬套 Composite | 模式的判据是「有没有一个真实的变化点」；没有变化点的模式是纯噪音 |
| 🔧 **忽略「效果（Consequences）」段** | 只读「意图/适用性」，跳过「代价」，以为模式只有好处 | 原书自己写了代价（如 Observer 的更新顺序不确定、Flyweight 的 extrinsic 状态易错）；代价段才是模式的核心内容 |
| 🔧 **混淆模式与框架** | 把「引用了某个库」说成「用了某模式」 | 模式是设计决策，框架是可运行半成品；库中内建模式不等于你的代码用了模式 |
| 🔧 **分类学被当成圣经** | 争论某个模式「应该算行为型还是结构型」 | 三分法是 1994 年的标签，重点是「稳定哪个变化点」；标签差异不影响设计正确性 |
| 🔧 **模式模板变成文档负担** | 每个类都写「意图/动机/适用性」9 段注释 | 9 段式是为书写书；工程代码里只保留不可省略的部分（不变式、生命周期、线程安全性） |
| 🔧 **继承被当作默认手段** | 需要新行为就加一个子类 | 原书自己说「优先组合而非继承」；优先考虑 `std::function`/lambda、策略表、数据驱动 |
| 🔧 **1994 的 C++ 写法被直接照搬** | 抄原书裸指针 `delete` 的代码到今天 | 智能指针、移动语义、`std::variant` 之后，很多实现骨架可以直接收缩；见各章「版本演进」 |
| **把模式名当黑话** | 讨论「上 Facade 吧」但没人知道要收窄什么接口 | 模式名是沟通的**压缩工具**，使用前必须说清「要稳定住的变化点」与「代价」 |

## 与其他章 / 其他书的联系

- 本目录：`00-总览与阅读地图.md`（分类总表在此）⟶ 本文件是它的展开；学完必须对 `06-模式的代价与反模式.md` 建立警惕（模式的动机段落很像反模式的动机段落）。
- `book/架构整洁之道*`：本文件的「模式与框架」区别，在架构层升维成「框架与架构的边界」；Clean Architecture 的 **依赖倒置规则**可与 `concepts/依赖倒置.md` 合读。
- `book/代码整洁之道*`：模式的「效果」段落要和「代码可读性」对齐——结构优雅但类名冗长、注释仪式化的代码，等于模式症状。
- `book/重构*`：原书没写「如何安全地把老代码改成模式结构」，`book/重构*` 补的就是这一步（引入模式前先消除重复、命名方法变量）。
- `book/C++并发编程实战2/`：本文件的「框架」概念在并发语境下变成「并发框架与执行器」，而 GoF 完全没有并发视角（见 `07-并发与协同模式对照.md`）。
- `book/计算机程序的构造和解释（原书第2版）/`：SICP 的「消息传递与面向对象」一节是 GoF 之前 20 年的面向对象设计思想；本文件的「模式间关系」在 SICP 的「数据导向程序设计」里有更早的形态。
