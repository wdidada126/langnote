# 第 3 章 结构型模式（Adapter / Bridge / Composite / Decorator / Facade / Flyweight / Proxy）

> **一句话**：结构型模式是「**用组合代替继承来扩展能力**」的七个具体答案——它们全部依赖同一个前提：接口稳定、实现可变。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Adapter（#6） | 接口翻译（对象适配器 / 类适配器） | 改接口不改动原类；但适配到一定程度就应重构原类 |
| Bridge（#7） | 抽象与实现分离（二维扩展） | 代价是两个继承层次；只有一维变化时是过度设计 |
| Composite（#8） | 树形组合，组合与叶子同接口 | 透明式 Composite 会污染接口；应偏向「安全式」 |
| Decorator（#9） | 动态附加职责 | 叠加顺序决定语义；类爆炸时可改用中间件/函数装饰器 |
| Facade（#10） | 为子系统提供简化门面 | 最容易演变成上帝对象，需要明确的子系统边界 |
| Flyweight（#11） | 共享细粒度对象（内在/外在状态） | 外在状态必须外部维护；内在状态必须不可变 |
| Proxy（#12） | 用替身控制访问（虚拟/保护/远程/智能引用） | `std::unique_ptr` 与语言级智能指针是最常见的「智能引用」 |

## 核心精讲

### 1. Adapter 适配器（#6）

**意图**：将一个**类的接口**转换成客户期望的另一个接口，使得原本接口不兼容的类可以协同工作。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 对象适配器：继承目标接口、持有被适配者（更常用）
class ThirdPartySdk {                  // 第三方：接口是 legacyFoo()
public:
    void legacyFoo() { /* ... */ }
};

class ITarget {                       // 客户期望的接口
public:
    virtual ~ITarget() = default;
    virtual std::string request() const = 0;
};

class Adapter : public ITarget {      // 对象适配器
public:
    explicit Adapter(ThirdPartySdk sdk) : sdk_(std::move(sdk)) {}
    std::string request() const override { return "adapter: " + sdk_.legacyFoo(); }
private:
    ThirdPartySdk sdk_;                // 组合而非继承
};
```

- **类适配器**（多重继承，`class Adapter : public Target, public Adaptee`）在 C++ 里可行，在 Java 单继承下不可用。
- **与 Facade 的区别**：Adapter 改的是**单类的接口语义**；Facade 改的是**子系统的边界**。

### 2. Bridge 桥接（#7）

**意图**：将**抽象部分与实现部分分离**，使它们可以**独立地变化**。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 两个正交维度：抽象（Shape） × 实现（Renderer）
class Renderer {
public:
    virtual ~Renderer() = default;
    virtual void renderCircle(float r) const = 0;
};

class Shape {                          // 抽象层持有实现的抽象引用（「桥」）
public:
    explicit Shape(const Renderer& r) : r_(r) {}
    virtual ~Shape() = default;
    virtual void draw() const = 0;
protected:
    const Renderer& r_;
};

class Circle : public Shape {
public:
    using Shape::Shape;
    void draw() const override { r_.renderCircle(radius); }
    float radius = 1.0f;
};

class VectorRenderer : public Renderer { void renderCircle(float r) const override { /* ... */ } };
class RasterRenderer : public Renderer { void renderCircle(float r) const override { /* ... */ } };
```

> 现实中的 Bridge：C++ 标准库 `std::basic_ios` ↔ `std::basic_streambuf`；JDBC 的 `Driver` 与 `Connection`。

### 3. Composite 组合（#8）

**意图**：将对象组合成**树形结构**以表示「部分-整体」层次；使得用户对**单个对象和组合对象的使用具有一致性**。

```cpp
// 教学示意，不参与构建、不编译、不运行
struct Component {
    virtual ~Component() = default;
    virtual int price() const = 0;
    virtual void add(std::unique_ptr<Component>) {
        throw std::logic_error("leaf cannot add children");   // 透明式 Composite 的代价
    }
};

struct Leaf : Component {
    int price() const override { return 10; }
    // add 继承自 Component，抛异常
};

struct Bundle : Component {           // 组合节点
    std::vector<std::unique_ptr<Component>> children;
    int price() const override {
        int sum = 0;
        for (auto& c : children) sum += c->price();
        return sum;
    }
    void add(std::unique_ptr<Component> c) override { children.push_back(std::move(c)); }
};
```

- **透明式**：叶子节点也继承 `add/remove`（客户可以无脑调用，但叶子会抛异常）⟶ 接口被污染。
- **安全式**：只在 Composite 上暴露 `add/remove`，代价是客户端要判断类型（在静态类型语言里更常用）。
- 现代替代：价值不大的树可以改用「树形 `std::variant` + 递归 `std::visit`」。

### 4. Decorator 装饰（#9）

**意图**：**动态地**给一个对象**添加一些额外的职责**；就扩展功能而言，比生成子类更为灵活。

```cpp
// 教学示意，不参与构建、不编译、不运行
struct Stream {
    virtual ~Stream() = default;
    virtual void write(const std::string& data) = 0;
};

struct FileStream : Stream {
    void write(const std::string& data) override { /* 写文件 */ }
};

struct Decorator : Stream {           // 装饰基类：透明地转发
protected:
    explicit Decorator(std::shared_ptr<Stream> s) : inner_(std::move(s)) {}
    void write(const std::string& data) override { inner_->write(data); }
    std::shared_ptr<Stream> inner_;
};

struct EncryptStream : Decorator {    // 具体装饰：前置职责
    using Decorator::Decorator;
    void write(const std::string& data) override {
        inner_->write(encrypt(data));
    }
};
// 组合：std::make_shared<FileStream>() 套三层 Encrypt/Compress/Buffer
```

**顺序决定语义**：`encrypt(compress(x))` 与 `compress(encrypt(x))` 结果不同，这是 Decorator 的主要认知负担。

### 5. Facade 外观（#10）

**意图**：为子系统中的一组接口提供一个**一致的界面**，定义一个高层接口，让子系统更易使用。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 把「下单」的跨模块调用收进一个门面，客户端不必再逐个调用
class OrderFacade {
public:
    void placeOrder(const Order& o) {
        inventory_.reserve(o.items);          // 库存子系统
        payment_.charge(o.total);             // 支付子系统
        mailing_.sendConfirm(o.email);        // 通知子系统
    }
private:
    InventoryService inventory_;
    PaymentService   payment_;
    MailingService   mailing_;
};
```

> **是否用了 Facade 的自检**：子系统有明确的包/模块边界，且「绕过门面直接调用子系统」不应发生。若绕过门面的调用很多，那门面就是多余的间接层，或者子系统边界划错了。

### 6. Flyweight 享元（#11）

**意图**：运用**共享**技术有效地支持**大量细粒度对象**。

```cpp
// 教学示意，不参与构建、不编译、不运行
// 内在状态（可共享、不变）在外，外在状态（上下文相关）在调用侧
struct Glyph {                                   // 享元：只含内在状态
    char code;
    const Font* font;                            // 不可变、可共享
};

class GlyphFactory {                             // 享元工厂：用 Map 复用
public:
    const Glyph* getGlyph(char c, const Font& f) {
        Key key{c, &f};
        if (auto it = pool_.find(key); it != pool_.end()) return it->second;
        return pool_.emplace(key, new Glyph{c, &f}).first->second;
    }
private:
    struct Key { char code; const Font* font; bool operator<(const Key& o) const; };
    std::map<Key, Glyph*> pool_;
};

void drawText(const GlyphFactory& f, const std::string& s, const Point& origin) {
    for (char c : s) {                           // 外在状态 origin 由调用侧提供
        const Glyph* g = f.getGlyph(c, defaultFont());
        draw(g, origin);                         // 位置是「外在状态」，不是享元的一部分
    }
}
```

**铁律**：内在状态必须在共享期间**完全不可变**，否则会立刻出现「改一个字形、所有位置都变」的 bug。

### 7. Proxy 代理（#12）

**意图**：为其他对象提供一种**代理以控制对它的访问**。

| 代理种类 | 作用 |
| --- | --- |
| 虚拟代理（Virtual） | 延迟创建开销大的真实对象（懒加载） |
| 保护代理（Protection） | 按权限决定是否放行 |
| 智能引用（Smart Reference） | 额外动作：引用计数、加锁、写时复制 |
| 远程代理（Remote） | 代表另一个地址空间的对象（RPC stub、ORM 懒加载） |

```cpp
// 教学示意，不参与构建、不编译、不运行
// 虚拟代理 + 保护代理的最小实现
class Image {
public:
    virtual void draw() = 0;
    virtual ~Image() = default;
};

class RealImage : public Image {
public:
    void draw() override { loadFromDisk(); /* ... */ }   // 构造时并不加载
private:
    void loadFromDisk();
};

class ImageProxy : public Image {               // 代理：控制真实对象的生命周期
public:
    void draw() override {
        if (!real_) real_ = std::make_unique<RealImage>();  // 懒加载
        real_->draw();
    }
private:
    std::unique_ptr<RealImage> real_;
};
```

## 版本演进

| 模式 | 1994 | C++11/17/20 | Java 8/17 |
| --- | --- | --- | --- |
| Adapter | 多重继承式类适配器（Java 不可用） | 智能指针 + 组合；模板可生成「通用适配器」 | 函数式接口 + 适配器方法、`Map<K,V>` 适配到 `Function` |
| Bridge | 两个继承树 + 裸指针 | 持有 `std::shared_ptr<Impl>`；`std::variant` 可把「实现」变成值域 | 接口 + 实现类树；`record` 让「值 + 实现」更轻 |
| Composite | 透明式（叶子继承 `Add`） | 倾向「安全式」；`std::variant<Leaf, Bundle>` + `std::visit` 消除虚函数表 | `Default` 接口方法抛异常；`record` + sealed 接口做「递归树」 |
| Decorator | 每个装饰一个类 | C++20 ranges/管道（`|` 组合）、`std::function` 链；AOP 与中间件替代 | 静态代理/动态代理（`InvocationHandler`）、Spring AOP、装饰器方法 |
| Facade | 子系统类集合 + 门面 | 门面 + 依赖注入；`std::facade` 无标准，靠模块边界 | Spring 的 `Facade` 服务门面、SDK 包装层 |
| Flyweight | 手写 `FlyweightFactory` 与 `Flyweight` 接口 | `std::unordered_map` 缓存 + 不可变值；`std::string` 的 SSO/共享即语言级享元 | `String` 常量池、`enum` 单例池、`record` 天然不可变 |
| Proxy | 手写智能指针 / 远程 stub | **`std::unique_ptr`/`shared_ptr` 本身就是语言级的「智能引用」**；`std::optional` 做「可能不存在」 | `java.lang.reflect.Proxy`、`ByteBuddy`/CGLIB；虚拟代理被懒加载框架内置 |

> 演进中最重要的一条：**Proxy 的「智能引用」在 C++ 里已经由标准智能指针承担**，1994 年那几十行的 `SmartPointer` 不再需要自己写；**Decorator 的「动态附加职责」在 Java 里被 AOP 与中间件管道承担**；**Flyweight 的「共享字符串」在语言里已经内置**。

## 近年研究与工业界开源实践（2015–2026）

**趋势**：结构型模式在**语言层被大量吸收**（智能指针吃掉 Proxy、ranges 吃掉部分 Decorator、字符串常量池吃掉 Flyweight），在**框架层被制度化**（AOP/中间件吃掉 Decorator、ORM 懒加载吃掉虚拟代理）。剩下的活儿集中在「跨系统集成」与「控制访问边界」，也就是 Adapter 与 Facade 的真实战场。

| --- | --- | --- |

## 常见误区与本书需修正之处

| 误区 | 现象 | 修正 |
| --- | --- | --- |
| 🔧 **透明式 Composite 污染接口** | 叶子节点也暴露 `add()`，调用处靠 `try/catch` 处理 | 改用安全式（只在父节点暴露）；或用 `std::variant`/sealed 接口表达「非叶子」约束 |
| 🔧 **Facade 演变成上帝对象** | 门面类上千行，绕过它直接调子系统的调用四处都是 | 门面只做「编排」，不做业务；把子系统拆到包边界，并规定「同包可绕过、跨包不可绕过」 |
| 🔧 **只有一维变化还上 Bridge** | 一个继承树硬拆成两个，类数量翻倍 | 用组合 + 函数/策略；两个维度都真正独立演化时才上 Bridge |
| 🔧 **Flyweight 的内含状态可变** | 共享对象里放了位置/时间戳等外在状态 | 严格区分内在/外在状态：内在状态构造后不可变，外在状态由调用侧传入 |
| 🔧 **手写智能引用（Proxy 的 1994 写法）** | 自己写 `RefCountedPtr`，漏掉异常安全与拷贝语义 | 直接用 `std::shared_ptr`/`unique_ptr`；需要「写时复制/加锁」语义时明确它是新类型而非代理 |
| 🔧 **Decorator 类爆炸** | 3 个特性 × 4 种组合 = 十几个装饰类，且顺序靠命名区分 | 改用数据驱动的特性列表 + 中间件管道（ASP.NET middleware、Express/Koa 中间件、gRPC interceptor） |
| 🔧 **Adapter 被用来掩盖长期技术债** | 每接一个旧系统就加一层 Adapter，永不重构 | 给 Adapter 设「到期条件」：能被替换为一层薄封装就不算 Adapter，考虑直接重构原接口 |
| 🔧 **1994 的裸指针所有权约定被照抄** | 工厂返回裸指针、调用处零散 `delete` | 明确所有权（谁 `delete`、谁持有），或全部改用智能指针/值语义 |
