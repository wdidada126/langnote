# 第 5 章 策略、状态、模板方法与访客（Strategy / State / Template Method / Visitor）

> **一句话**：这四个模式全部是「**用多态把变化的行为抽出成可替换的对象**」——差别只在「行为由谁来选择、何时切换，以及往后加东西更便宜的是操作还是元素」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Strategy 策略（#21） | 算法族可互换，客户可独立选择 | 接口要够窄；关键是「选择发生在哪里」 |
| State 状态（#20） | 对象内部状态改变时改变其行为 | 运行期可切换的状态机；迁移合法性要显式检查 |
| Template Method 模板方法（#22） | 算法骨架固定，可变步骤留给子类 | 「依赖继承」的反模式源头；非虚也可以（CRTP） |
| Visitor 访问者（#23） | 把操作封装到访问者里，便于新增操作 | 对操作开放、对元素封闭；新增元素类型很痛苦 |
| 四者的横向比较 | 选择时机、扩展方向、封装代价 | 一句话定位：Strategy 换算法，State 换行为，TM 换步骤，Visitor 换操作 |

## 核心精讲

### 1. Strategy 策略（#21）

**意图**：定义一系列**算法**，把它们**逐个封装**起来，并且使它们可以**互相替换**；使得算法可以独立于使用它的客户而变化。

```cpp
// 教学示意，不参与构建、不编译、不运行
class CompressionStrategy {           // 策略接口：越窄越好
public:
    virtual ~CompressionStrategy() = default;
    virtual void compress(std::ostream& in, std::ostream& out) = 0;
};

class ZipStrategy   : public CompressionStrategy { void compress(...) override { /* zip  */ } };
class Lz4Strategy   : public CompressionStrategy { void compress(...) override { /* lz4  */ } };

class Packer {                        // 使用策略的客户：只依赖接口
public:
    void setStrategy(std::shared_ptr<CompressionStrategy> s) { s_ = std::move(s); }
    void run(std::istream& in, std::ostream& out) { s_->compress(in, out); }
private:
    std::shared_ptr<CompressionStrategy> s_;
};
// 现代写法：把 setStrategy 换成构造注入或参数化，甚至直接 std::function
```

**要点**：
- 策略接口要**足够窄**（只暴露真正会变的那部分），否则各策略都无法互换。
- **选择点在哪**：如果选择是固定规则（如「大文件用 lz4」），直接放进客户构造函数；如果选择本身是运行时数据，才值得一个 Strategy + 工厂。

### 2. State 状态（#20）

**意图**：允许一个对象在其**内部状态改变时改变它的行为**，这个对象看起来像改变了它的类。

```cpp
// 教学示意，不参与构建、不编译、不运行
class Machine;                                   // 上下文（Context）

class State {                                    // 状态接口
public:
    virtual ~State() = default;
    virtual void insertCoin(Machine& m) = 0;     // 每个状态响应同一组事件
    virtual void eject(Machine& m)       = 0;
    virtual void dispense(Machine& m)    = 0;
};

class NoCoinState : public State {               // 具体状态：行为不同
public:
    void insertCoin(Machine& m) override { m.setState(std::make_shared<HasCoinState>()); }
    void eject(Machine&) override        { /* 无操作 */ }
    void dispense(Machine&) override     { /* 无操作 */ }
};

class Machine {
public:
    void setState(std::shared_ptr<State> s) { state_ = std::move(s); }   // 运行期切换
    void insertCoin() { state_->insertCoin(*this); }
private:
    std::shared_ptr<State> state_ = std::make_shared<NoCoinState>();
};
```

**与 Strategy 的三个区别**：（a）State 的对象持有一个**对 Context 的引用**，可以请求切换状态；（b）State 的切换是**运行期由行为本身触发**的；（c）State 关心的是「状态合法迁移」，Strategy 不关心。

### 3. Template Method 模板方法（#22）

**意图**：定义一个操作中的**算法的骨架**，将**一些步骤延迟到子类**中；使得子类可以不改变算法的结构即可重定义算法的某些特定步骤。

```cpp
// 教学示意，不参与构建、不编译、不运行
class DataImport {                      // 模板方法：算法骨架固定，步骤可变
public:
    void run() {                        // 非虚：保证骨架不可被绕过
        connect();
        read();                         // 可变步骤
        transform();                    // 可变步骤
        persist();
        notify();                       // 可变步骤
    }
    virtual ~DataImport() = default;
protected:
    virtual void read()      = 0;
    virtual void transform() = 0;
    virtual void persist()   = 0;
    virtual void notify() {}
private:
    void connect() { /* 固定 */ }
};

class CsvImport : public DataImport {   // 子类只填步骤
    void read() override { /* 读 CSV */ }
    void transform() override { /* 映射 */ }
    void persist() override { /* 落库 */ }
};
```

**原书指出的两条代价**（至今成立）：
1. **控制反转的「不完整」**：模板方法提供的 hooks 太少，子类往往需要覆写多个方法，或者干脆覆写一个新方法，导致「模板方法不再是模板方法」。
2. **继承的脆弱性**：如果实现依赖超类的具体实现细节，子类一改就破坏超类算法；原书提醒「要清楚地文档化哪些是protected、哪些允许覆写」。

```cpp
// 不变式写法：把可变步骤放到参数里，而不是放到子类里（避免继承）
template <typename Derived>
void runImport(const Derived& impl) {    // CRTP：静态模板方法
    impl.connect();
    impl.read();  impl.transform();
    impl.persist();
}
```

### 4. Visitor 访问者（#23）

**意图**：表示一个**作用于某对象结构中各元素的操作**。它使你可以在**不改变各元素的类的前提下**定义作用于这些元素的新操作。

```cpp
// 教学示意，不参与构建、不编译、不运行
struct Element { virtual ~Element() = default; virtual void accept(class Visitor&) = 0; };

struct PlusNode  : Element { void accept(Visitor& v) override; int value; };
struct MinusNode : Element { void accept(Visitor& v) override; int value; };

struct Visitor {                        // 对每种元素一个 visit 重载
    virtual void visit(PlusNode&)  = 0;
    virtual void visit(MinusNode&) = 0;
    virtual ~Visitor() = default;
};

// 计算求值：一个访问者
struct CalcVisitor : Visitor {
    void visit(PlusNode& n) override  { sum += n.value; }
    void visit(MinusNode& n) override { sum -= n.value; }
    int sum = 0;
};

void PlusNode::accept(Visitor& v)  { v.visit(*this); }   // 元素回调访问者（二次分派）
void MinusNode::accept(Visitor& v) { v.visit(*this); }
```

**收益与代价**：
- 收益：新增**操作**（求值、打印、序列化、类型检查）时，只加一个 Visitor，不必动元素类。
- 代价：**新增元素类型必须改每一个 Visitor**。所以 Visitor 是「对操作开放、对元素封闭」；如果一个元素层级很少变、操作很多，Visitor 才划算。
- 现代替代：C++17 的 `std::variant` + `std::visit`（编译期分派，无需 `accept`），Java 17 的 `sealed interface` + `switch` 模式匹配（同样编译期穷尽检查）。

### 5. 四者的横向对照

| 维度 | Strategy | State | Template Method | Visitor |
| --- | --- | --- | --- | --- |
| 稳定什么 | 算法族 | 迁移规则 | 算法骨架 | 操作集合 |
| 变化什么 | 具体算法 | 内部状态 | 可变步骤 | 元素类型 |
| 选择时机 | 客户构造/配置时 | 运行期，由行为触发 | 编译期（继承结构） | 使用方传入访问者 |
| 扩展方向 | 加算法 | 加状态 | 加子类（不推荐扩张） | 加操作容易、加元素困难 |
| 耦合方式 | 组合（优先） | 组合 + Context 引用 | **继承** | 元素持有 accept，双分派 |
| 典型误伤 | 只有一种实现 | 状态逻辑还写在 if 里 | 子类数百个、骨架失守 | 元素类被迫暴露内部字段 |

## 版本演进

| 模式 | 1994 | C++11/17/20 | Java 8/17 |
| --- | --- | --- | --- |
| Strategy | 抽象基类 + 具体策略子类 | `std::function` / lambda 最常用；或模板参数静态多态 | `IntFunction`/`Function<T,R>` + 方法引用；Spring `Strategy` 注入 |
| State | 每个状态一个类 + Context 切换 | 状态类改为状态枚举 + 表驱动状态机；`std::variant<StateT...>` | 枚举 + `switch`（Java 17 增强 `switch`）；状态机库如 `spring-statemachine` |
| Template Method | `protected virtual` 钩子 | 优先改为**函数参数化**：把步骤变成 `std::function`；CRTP 做静态版 | `default` 接口方法；函数式写法用 `Consumer` 列表 |
| Visitor | `accept` + 双分派 | **`std::variant` + `std::visit`**（编译期分派，无虚开销） | `sealed interface` + `switch` 模式匹配（穷尽检查）；或 `record` 配合 `when` 分支 |
| 共同趋势 | 依赖继承与虚函数 | 继承 ⟶ 组合/lambda/泛型（「组合优于继承」的落地） | 多态分派被**模式匹配**部分替代 |

> 语言能力变化的净效果：**Strategy 与 Command 退化成 lambda，Visitor 被 `variant`/`sealed` 部分替代，Template Method 被函数参数化替代，State 被状态机库与枚举表替代**。真正还站在前排的，是「操作易变 vs 元素稳定」那一类场景（编译器的 pass）。

## 近年研究与工业界开源实践（2015–2026）

**趋势**：（1）**Visitor 类模式被代数数据类型替代**——Rust enum + match、C++ `std::variant` + `std::visit`、Java 17 `sealed interface` + switch 模式匹配，都在编译期做穷尽检查，比双分派更便宜也更安全；（2）**Strategy 进入函数式与配置化**——策略变成数据（表 + 闭包），并可由配置文件或运行时规则引擎驱动；（3）**Template Method 减少使用**——"prefer composition over inheritance" 与函数参数化让继承层级不必要地增长；（4）状态机从手写进入库化（有限状态机、状态图与状态机建模工具）。

| 仓库 | star（实测） | 说明 |
| --- | --- | --- |
| `rust-lang/rust` | **119,149★** | enum + match 穷尽检查是 Visitor 的类型安全替代品；trait 对象让 Strategy 无虚函数负担 |
| `microsoft/TypeScript` | **111,192★** | 判别联合（discriminated union）与 `switch` 穷尽检查；`strict` 模式下的联合类型即轻量 ADT |

## 常见误区与本书需修正之处

| 误区 | 现象 | 修正 |
| --- | --- | --- |
| 🔧 **只有一种实现还上 Strategy** | 一个接口两个类，其中一个是空壳 | 先用函数参数/枚举分支；等第二个真实实现出现再抽 Strategy（YAGNI） |
| 🔧 **Template Method 引发继承脆弱性** | 子类依赖父类私有实现细节，父类一改子类全崩 | 把可变点通过参数/组合注入；必须继承时用 CRTP 或 `final` 保护骨架 |
| 🔧 **Visitor 破坏元素封装** | 元素被迫提供 `getChildren()`/`getLeft()` 等访问器，访问者直接读内部字段 | 让元素自己暴露语义化方法而非结构访问器；或用 `variant` 替代双分派 |
| 🔧 **Visitor 用于只有一个操作的场景** | 一个操作却要一个 Visitor 接口加 5 个实现类 | 直接用多态分派或 `std::visit`；Visitor 的价值在于「操作多、元素少」 |
| 🔧 **State 与 if-else 的边界不清** | 既有状态类又残留一堆 `if (state == X)` | 状态迁移表化，禁用跨状态判断；否则两个真相来源互相打架 |
| 🔧 **Strategy 接口过宽** | 策略之间无法实现（各需要不同上下文方法） | 把上下文拆窄，或让策略只接受「已抽取的最小输入」 |
| 🔧 **1994 的虚函数双分派开销被忽略** | 热路径上 Visitor 因虚调用与缓存不友好而变慢 | 改用 `variant`/枚举 + 编译期分派；或把访问者做成可内联的小函数 |
| 🔧 **把 State 当成"状态数据"而非"状态行为"** | 状态类里只有字段没有行为，行为全在 Context 的 switch 里 | 行为必须住在状态类里；Context 只做委托与迁移合法性校验 |
