# 10 测试与验证（Ch10: Testing and Validation）

> 章题与编号取证 ⚠️ 推定（终版前 9 章 ✅ 实抓止于 Going Beyond Scala；本章按 2e 草案第 8 章"测试和验证"对位推定为终版第 10 章，章题取草案英译通行形）。节级结构依草案 ✅ 实抓：单元测试（一般 Spark 单测、模拟 RDD）/ 获取测试数据（生成大数据集、抽样）/ ScalaCheck 属性检查 / 集成测试 / 性能验证（Spark 计数器、相关项目）/ 作业验证。⚠️ 终版或有调整。

## 0. 本章主线

调优的隐藏前提：**你得能证明"改完还对"和"真的变快了"**。没有这两条证明，前面九章的一切优化都只是"看起来变快了"。本章把 Spark 测试拆成四层，每一层都有"分布式带来的特殊难点"：

```
        ┌───────────────┐
        │  性能验证      │  计数器/事件日志：证明"真的变快"
        ├───────────────┤
        │  集成测试      │  外部系统往返：证明"写得出去读得回来"
        ├───────────────┤
        │  作业/属性测试  │  不变量断言：证明"任意输入都对"
        ├───────────────┤
        │  单元/函数测试  │  local[*] 或纯函数：证明"这块逻辑对"
        └───────────────┘
```

## 10.1 单元测试的两条路（草案 8.1 ✅）

- 真引擎路线：local[*] 单机全线程跑真转换——快（秒级启动）、可信（真语义），但**单机线程模型照不出分布式 bug**（分区边界、序列化往返在 local 模式下形状不同——序列化税只有 cluster 才交）。⚠️＋ https://spark.apache.org/docs/latest/rdd-programming-guide.html ✅（local 模式条目）
- 纯函数路线：把 lambda 的业务核心抽成不依赖 Spark 类型的纯函数，"测函数不测框架"——判读：这是 DataFrame 时代的主流姿势，转换逻辑下沉为可单测的 UDF/表达式，Spark 侧只测装配。⚠️
- 模拟 RDD（草案 8.1.2）：以 RDD 接口造替身（mock），验证调用形状与装配逻辑——判读：该手法随 DataFrame/SQL 主流化而**贬值**：计划即断言，`explain()` 输出的物理计划可直接 diff 比对，替身反而遮蔽了优化器的真实行为。⚠️
- 🔧 概念锚回 [05-DataFrame与SparkSQL](05-DataFrame与SparkSQL.md) 的 E6：DuckDB/SQLite 里"同一条查询在 ANALYZE 前后计划翻面（ia→ib，39.9ms→0.0ms）"证明**物理计划是行为的可读契约**——把"计划 diff"当回归断言，是性能测试的静态面（**类比非 Spark**）。

## 10.2 测试数据：大与偏都要造得出（草案 8.2 ✅）

- 生成大数据集（合成派）：编程分布造规模与形状——uniform 测吞吐基线、Poisson 测一般倾斜、**Zipf 测病态倾斜**（热键长尾的天然发生器）；官方 random data 算子族为工具位。⚠️＋ https://spark.apache.org/docs/latest/rdd-programming-guide.html ✅
- 抽样（真实派）：从生产数据切片——分层抽样保比例、reservoir 抽样的单遍等概率；判读要点：**抽样测得出功能 bug，测不出倾斜 bug**（抽样抹平了尾部），两类夹具要并存。
- 关键工程纪律：**倾斜不是异常值是设计参数**——E5 类热键分布（30% 单键）应出现在测试夹具里，而不是事故现场才第一次遇见（回看 [06-Join优化](06-Join优化.md)）。
- 夹具尺寸三档：毫秒级（逻辑正确性，每次提交跑）/ 分钟级（形状回归，每日跑）/ 生产规模抽样（性能验证，发版前跑）——档位错配是"测试永远绿、上线就爆炸"的主因。⚠️

## 10.3 属性测试与 ScalaCheck（草案 8.3 ✅）

- 思想：不逐例断言，断言"不变量对生成器产出的所有样本成立"——反例由框架自动缩小（shrink）到最小可复现形。
- Spark 契合点：分布式算子的正确性天然是属性形——
  - shuffle 前后记录数守恒；
  - partitionBy 后同 key 必同分区；
  - reduceByKey 与"先全量收集再本地折叠"结果相等（**预聚合的正确性定义**，接 [08-键值对数据与Shuffle](08-键值对数据与Shuffle.md)）；
  - join 结果行数介于上下界之间（inner ⊆ 左侧、匹配率可核对）。⚠️
- 局限诚实记：属性测试管"语义等价/守恒"，管不了"性能不退化"——后者是 10.5 的职责；也管不了外部系统契约。
- 判读：语言中立时代该思想以 pytest＋hypothesis（Python 侧）延续，思路等价、生成器生态更大。⚠️

## 10.4 集成测试与作业验证（草案 8.4/8.6 ✅）

- 集成层：外部系统（Kafka/湖仓表/对象存储）用容器化实例或 dry-run catalog 隔离；核心动作是**往返闭环**——写出后必须读回断言（schema 漂移、类型精度、时区、NULL 语义都在往返处露馅；回看 ../Use_Iceberg_with_Spark/03-数据读写与MERGE-INTO.md）。
- 作业验证（调度成功≠数据正确）：给每个出口加三类断言——
  1. 行数/基数带（与上游对账或历史均值 ±σ）；
  2. 聚合值哨兵（关键指标的今日值 vs 昨日值，突变告警）；
  3. 新鲜度（数据到达时间预算内）。
  此为数据质量工程口径，与 ../bigdata/12-数据质量与工程实践.md 互证。⚠️
- 环境差分：集成测试的失败常来自"测试环境与生产不同构"——分区数、并行度、序列化器配置应进夹具清单而非默认值碰运气。⚠️

## 10.5 性能验证（草案 8.5 ✅，本章压轴）

- 计数器法：Spark 累加器与事件日志采集三族指标——**shuffle bytes（写/读）、spill 记录数与字节、task 时长分布（p50/p95/max）**；优化前后同夹具对照，**先定义指标再动手优化**。⚠️＋ https://spark.apache.org/docs/latest/configuration.html ✅（eventLog 与 accumulator 参数族）
- 方法论母版：E1/E5/E6 的共同纪律=同一数据、同一查询、只动一个变量、报具体差值——无对照不谈收益。🔧（类比非 Spark）
  - E1：DuckDB 12M 行聚合，内存上限 120MB＋temp_directory 触发 spill 文件、0.77s vs 4GB 不 spill 0.89s——**spill 不是灾难是阶梯**，证明"改内存参数=改执行形状"可被测量；
  - E5：热键拆分在单机的负收益——**"优化有效"必须被测出来而不是被相信**。
- 回归三对照（可比对象的选择）：上一版代码（改对了没）/ 上一版引擎（升级安全吗，接 [03-Spark升级与迁移](03-Spark升级与迁移.md)）/ 上一批数据（漂移感知）——各测一个维度，缺一即盲区。
- "性能验证相关项目"（草案 8.5.2）：基准与回归框架的历史名录——到 2026 判读为 CI 化：以固定硬件跑 TPC-DS 子集做版本/改动双回归（趋势观察 ⚠️；本轮未对该节所涉项目逐一验链，不点名不引链）。

## 10.6 误区清单

| # | 误区 | 正解 | 出处 |

| 1 | local[*] 全绿即可上线 | local 照不出序列化/分区边界类分布式 bug | 10.1 |

## 10.9 验证先行的先后序（全书收束纪律）

- 任何优化动手前，先取四项绿灯：函数断言／计数守恒／计划快照／指标基线；优化动手后，同四项复跑＋基线对照。⚠️
- "验证先行"反对的三种免费幻觉：应该变快了、hint 生效了、默认值没变——每种都对应本章一个测量项。⚠️＋ https://spark.apache.org/docs/latest/configuration.html ✅（eventLog/accumulator 族）

## 10.10 要点回显

- 四层金字塔各挡一类事故：单元挡逻辑错、属性挡不变量破坏、集成挡外部契约漂移、性能挡收益幻觉——跳层即留盲区。
- 三件套（行数/计划/账单）是本章的最低部署形态，也是 03 章方法学的自动化对象。
- 测试夹具里的 Zipf 是廉价的倾斜演习；生产里的 Zipf 是昂贵的倾斜事故——夹具设计就是风险预算分配。

## 核心概念速览（中英对照）

- **local[*] 模式** — 单机全线程测试集群：功能验证的默认沙盒，分布式形状的盲区制造机。
- **计划断言** — Plan assertion：以物理计划文本为回归比对对象，SQL 时代的"单元测试"。
- **数据夹具** — Test fixture data：按分布设计（含倾斜）的可复现输入集。
- **Zipf 生成器** — 倾斜合成器：长尾热键的可控来源。
- **属性测试** — Property-based testing：对生成样本断言不变量，分布式正确性的天然语形。
- **反例缩小** — Shrinking：属性测试把失败样本自动最小化的机制。
- **计数器验证** — Counter-based validation：以累加器/事件日志指标证明执行形状。
- **事件日志** — Event log：作业历史的可离线回放证据链。
- **往返闭环** — Round-trip integration：写出后以读回验证外部系统契约。
- **性能回归** — Performance regression：指标基线对照下退化的变更，CI 门禁对象。
- **新鲜度断言** — Freshness assertion：数据到达时间纳入出口校验。
- **三对照基线** — Code/engine/data baselines：回归可比对象的三个维度。
