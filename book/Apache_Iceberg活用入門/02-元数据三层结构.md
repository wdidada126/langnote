# 第 2 章 元数据三层结构：table metadata / snapshot / manifest list / manifest file

> ⚠️ 章题为**推定**（示意日文名：メタデータの構造），原书真实目录未核实，见 [00-总览与阅读地图.md](00-总览与阅读地图.md)。
> 本章逐字段内容全部依据官方 [Table Specification](https://iceberg.apache.org/spec/)（写作时核对 `format/spec.md`），是全书理解成本最高、回报最大的一章。

## 本章地图

> 一句话：**表状态 = 一棵四层文件树：table metadata（根，JSON）→ snapshot（快照）→ manifest list（快照的文件清单目录，Avro）→ manifest file（某分片内数据/删除文件的索引，Avro）→ data/delete files。每一层只引用下一层，提交 = 原子换根。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 2.1 全景图 | 四层结构 + 指针如何串起一次读取 | 从 catalog 到 parquet 只需 4 跳 |
| 2.2 table metadata 文件 | JSON 根文件的全部关键字段 | 表的历史本身也是元数据 |
| 2.3 snapshot | snapshot-id/parent/sequence-number/summary | 快照 = 某时刻 manifest list 的引用 |
| 2.4 manifest list | 每个 manifest 的元信息与聚合统计 | 规划阶段读它，不读 manifest |
| 2.5 manifest file | manifest_entry：status/snapshot_id/序列号/data_file | 文件级「账目」所在，含列级 min/max |
| 2.6 一次写入的文件账 | INSERT/COMPACT 各新增/改了哪些文件 | 只有根指针换了一次 |
| 2.7 元数据表 | snapshots/history/manifests/files/partitions | 用 SQL 看穿这棵树 |
| 2.8 命名与保留 | vNNN 编号、version-hint、删除边界 | expire 之后旧层才可删 |

## 核心精讲

> **教学示意，不参与构建。** 字段名以 spec 原文（英文）为准；示例 JSON/Avro 片段为手工缩写。

### 2.1 全景：一次 `SELECT` 顺指针走四跳

```text
catalog（HMS/Glue/REST）
  └─ 表当前位置 → metadata/00123-xxx.gz        ① table metadata（JSON，根）
       ├─ schemas[]、partition-specs[]、current-snapshot-id = 58504441…
       └─ snapshots[]
            └─ snapshot 58504441
                 └─ manifest-list → metadata/snap-58504441-….avro   ② manifest list
                      ├─ manifest_entry m1 (partition_spec_id=0, 覆盖 dt∈[1/1,1/15])
                      ├─ manifest_entry m2 …                         （每行=一个 manifest + 聚合统计）
                      └─ …
                           └─ metadata/0a1b2c-d0.m0.avro            ③ manifest file
                                ├─ DataFile f1: 分区值、行数、字节数、每列 min/max
                                ├─ DataFile f2 …                     
                                └─ DeleteFile d1（v2：position delete 等）
                                     └─ data/dt=…/00000-0.parquet   ④ 数据/删除文件
```

规划阶段引擎只做 ①②（+按谓词粗剪枝后打开少量③）：这就是 1.1 说「规划与表大小解耦」的原因。

### 2.2 table metadata 文件：表的「宪法」

gzip 压缩的 JSON，路径形如 `metadata/00007-<uuid>.metadata.json`（部分实现缩写为 `vNNNNN`）。关键字段分组（spec §Table Metadata）：

| 组 | 字段 | 说明 |
| --- | --- | --- |
| 身份 | `format-version` | 1/2/3，表能力定版（第 1.5 节） |
| | `table-uuid` | 表的全球唯一 ID，随表迁移不变；行级血缘/加密引用它 |
| | `location` | 表根路径 |
| 演化库 | `schemas[]` + `current-schema-id` | **全部历史 schema**，每个字段有稳定 `field-id`（第 4 章） |
| | `partition-specs[]` + `default-spec-id` | **全部历史分区规范**，各有 `spec-id`（第 3 章） |
| | `last-partition-id` / `last-column-id` | 分配器水位，保证 ID 永不复用 |
| 排序 | `sort-orders[]` + `default-sort-order-id` | 排序规范也是可演化的列表 |
| 快照 | `snapshots[]` | 全部快照对象（§2.3）；`current-snapshot-id` 指向当前 |
| | `refs` | 命名引用：`main` 分支 + 用户分支/标签，带 snapshot-id 与保留策略 |
| | `snapshot-log[]` / `metadata-log[]` | 「何时发生了什么提交」「何时换过哪些根文件」两条审计流水 |
| 序列 | `last-sequence-number` | 全局单调提交序号水位（v2 起，§2.3/第 5、6 章） |
| 血缘 | `next-row-id`（v3） | row lineage 的行号分配器 |
| 杂项 | `properties` | `write.parquet.compression-codec`、保留策略等 |

要点：**历史（schema/spec/snapshot/log）全部内嵌在根文件里**，所以「表自描述」；换根文件即换整个表状态，这正是原子提交的载体（第 6 章）。

### 2.3 snapshot：某一刻的文件清单引用

spec §Snapshots 的字段：

```json
{
  "snapshot-id": 3021787114022113362,
  "parent-snapshot-id": 9877665,
  "sequence-number": 21,          // v2：该快照中新增文件/删除文件的「年龄」
  "timestamp-ms": 1623303900000,
  "operation": "append",           // v2 枚举：append/replace/overwrite/delete
  "manifest-list": "snap-3021….avro",
  "schema-id": "3",
  "first-row-id": 1000,            // v3 row lineage
  "added-rows": 10000              // v3
}
```

- **快照链 = 树**：`parent-snapshot-id` 串出祖先链；分支/tag 让链变成树（`refs`）。
- `operation` 四枚举值得展开：`append`（只加文件）、`overwrite`（**快照替换**语义：从当前快照继承的既有文件被标记 existing、新集合替换旧集合，常见于 `INSERT OVERWRITE`）、`delete`（只加删除文件，行级删除的 MoR 形态）、`replace`（维护型替换：rewrite_data_files 用，语义上「内容不变、布局变了」，第 8 章）。
- `summary`（`operation-parameters` + changes）：`added-data-files`、`deleted-data-files`、`added-delete-files`、`equated-delete-files` 等，是审计「这次提交干了什么」的第一现场。

### 2.4 manifest list（snapshot summary file）：Avro，一次快照一个

每行是一个 `manifest_file` 记录（spec §Manifest List）：

| 字段 | 用途 |
| --- | --- |
| `manifest_path`、`manifest_length` | 指向哪个 manifest 文件 |
| `partition_spec_id` | 该 manifest 属于**哪个分区规范**——多 spec 共存的物理证据（第 3 章） |
| `content` | 0=data / 1=deletes（v2：删除文件单独成 manifest，`content=1`） |
| `sequence_number` | 该 manifest 内**所有条目共有的数据序列号**（v2） |
| `min_sequence_number` | 条目里最小的序列号——判断「老文件是否也可能被本 manifest 的删除影响」，避免不必要的打开（v2） |
| `added_snapshot_id` | 哪个快照加入的 |
| `added/existing/deleted_files_count`、`added_rows_count/...` | 聚合计数，规划期免开 manifest |
| `partitions[]` | **对 manifest 内所有分区值的列级聚合**：每个分区字段有 `contains_null`、`contains_nan`、`lower_bounds`、`upper_bounds` —— 剪掉整个 manifest 的依据就在这 |

`min_sequence_number` 是 v2 精妙点之一：没有它，规划器必须打开所有 manifest 才能判定删除适用范围；有了它，「纯老账本」可整体跳过。

### 2.5 manifest file：文件级账本 + 列级统计

Avro 文件，header 里带 `schema`、`schema-id`、`partition-spec(-id)`、`format-version`、`content`。每条记录是一个 `manifest_entry`：

```text
manifest_entry {
  status: EXISTING(0) | ADDED(1) | DELETED(2)
  snapshot_id        -- 最后改变该条目的快照
  sequence_number    -- v2：数据的年龄（EXISTING 条目在 manifest 重写时继承，不重写数据）
  file_sequence_number
  data_file {
    content: 0=data | 1=position-deletes | 2=equality-deletes | 3=deletion-vector-files(v3)
    file_path, file_format(PARQUET/ORC/AVRO/METADATA/PUFFIN),
    partition(row: 按所属 spec 的 transform 计算出的分区值),
    record_count, file_size_in_bytes,
    column_sizes/value_counts/null_value_counts/nan_count（按字段 ID 键控）,
    lower_bounds/upper_bounds（按字段 ID 键控的截断统计）,
    key_metadata/split_offsets/sort_order_id,
    equality_ids（equality delete 适用列）, first_row_id(v3),
    content_offset/content_size_in_bytes（v3 deletion vector 在 Puffin 内的定位）
  }
}
```

三个细节：
1. **分区值是物化的**：`partition` 是「按当时 spec 算出的元组」，不靠目录名反推——隐藏分区（第 3 章）成立的前提。
2. **统计按 field-id 键控**：改名/重排不影响剪枝正确性（第 4 章成立的前提）。
3. `ADDED/EXISTING/DELETED` 让 manifest 兼任「增量视图」：增量读、`files` 元数据表、changelog 都由 status+snapshot_id 过滤而来。

### 2.6 一次写入的文件账（教学示意）

| 操作 | 新增文件 | 根指针 |
| --- | --- | --- |
| `INSERT INTO`（append） | 新 data files ×N、含 ADDED 条目的新 manifest ×1+、新 manifest list ×1、新 metadata JSON ×1 | 换 1 次 |
| `DELETE`（MoR, v2） | 新 position-delete files、新删除 manifest(content=1)、新 manifest list、新 metadata | 换 1 次 |
| `UPDATE`（CoW） | 重写后的 data files + 对应新 manifest；被替换文件在 entry 上标 DELETED（或落入新 manifest 的既有集合）、新 list、新 metadata | 换 1 次 |
| `rewrite_data_files` | 合并后的新 data files + replace 快照 + 新 list/metadata；旧文件仅失去引用，不立即删 | 换 1 次 |
| `ALTER TABLE ... ADD COLUMN` | **只有新 metadata JSON**（schema 演化不动数据，第 4 章） | 换 1 次 |

不变的规律：**任何提交 = 新增若干不可变文件 + 一次原子换根**。旧文件全部原地保留，所以回滚 O(1)，所以维护的本质是「失去引用后何时可删」（第 8 章）。

### 2.7 元数据表：把树摊平成 SQL（教学示意，以 Spark 为例）

```sql
SELECT * FROM prod.db.orders.snapshots;        -- 快照链：id/parent/operation/timestamp/summary
SELECT * FROM prod.db.orders.metadata_log_entries; -- 根文件流水（可查到已 expire 的旧版本记录）
SELECT * FROM prod.db.orders.manifests;        -- 当前快照的 manifest list 展开
SELECT content, file_path, record_count FROM prod.db.orders.files
  WHERE deleted = false;                       -- 全部 DataFile 条目 + 统计
SELECT * FROM prod.db.orders.partitions;       -- 按 spec+分区聚合：行数/文件数/spec_id
SELECT * FROM prod.db.orders.history;          -- 曾为 current 的时刻
CALL system.set_current_snapshot('prod.db.orders', 3021787114022113362);  -- 回滚（第 6/8 章）
```

排障心法：**「表不对」先看 `snapshots` 的 summary，「表变慢」先看 `manifests`/`partitions` 的数量分布**——后者直接暴露 manifest 碎片化与小文件问题（第 8 章重写判据）。

### 2.8 命名、缓存提示与保留边界

- 根文件按 `vNNNNN`/序号命名；Hadoop catalog 用 `metadata/version-hint.text` 指示当前号，其他 catalog 以 catalog 记录的路径为准——所以**别手写指针**，一切经 `TableOperations`（第 6 章）。
- metadata 文件自含 `snapshot-log`/`metadata-log`，客户端只需缓存根文件。
- 保留边界：一个文件/manifest/manifest list/metadata JSON 可删除，当且仅当**没有任何仍在保留期内的快照（含 refs 指向的分支/tag）引用它**。`expire_snapshots` 就是在推进这条边界（第 8 章）。

## 版本演进与兼容性

- v1 没有 `sequence-number`、没有 delete manifest、manifest list 理论上可选——因此 v1 表上「文件的年龄」不可靠，第 5 章的删除正确性整套机制在 v2 才成立。
- v2 强制 manifest list + 序列号；v3 在此之上加 `first-row-id`/`added-rows`（快照级与文件级行号，供 row lineage 与增量系统消费）与 Puffin 删除向量。
- 发行版动态：1.5+ 元数据压缩/缓存改进、`clean_expired_metadata`（expire 时顺带删旧根文件）；🔧 新版规划器持续优化「少开 manifest」（如按分区字段的删除向量下推）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「manifest 就是文件名的清单」 | manifest 携带行数列级统计与分区元组，是**规划器的索引**，不是 ls 输出 |
| 「快照存在 catalog 里」 | 快照在 metadata JSON 与对象存储文件里；catalog 只存一个根指针 |
| 「DELETED 条目=文件已删」 | 条目是**元数据账**；物理删除要等 expire + 保留窗口（§2.8） |
| 「metadata-log 和 snapshot-log 一样」 | 前者记录根文件替换历史，后者记录快照纳入历史；回滚后 snapshot-log 不动、metadata-log 增加 |
| 「读表时要读 Parquet footer 拿 schema」 | schema 在根文件；footer 只为列裁剪/解码，统计剪枝已在 manifest 层完成 |
| 「表慢 = 查询引擎问题」 | 大半是树胖了：manifest 数量爆炸/碎小。查 `manifests` 再决定 rewrite（第 8 章） |
