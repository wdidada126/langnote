# 第 5 章 行级删除与更新：delete files（v1/v2/v3）

> ⚠️ 章题为**推定**（示意日文名：行レベルの削除と更新——.delete files），原书真实目录未核实，见 [00-总览与阅读地图.md](00-总览与阅读地图.md)。
> 依据：spec §Delete Files / §Sequence Numbers / §Deletion Vectors（v3）与官方 `docs/spark-writes.md` 的 MERGE 说明（概念层已核对）。

## 本章地图

> 一句话：**Iceberg 不改写数据文件来删行——它写「哪些行作废」的旁证文件（delete files），读的时候现场应用；序列号决定哪张「作废清单」管哪个数据文件。这就是 v2 的 merge-on-read。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 为什么行级修改难 | 对象存储不可变、文件粒度提交 | 只能「加文件」，不能「改文件」 |
| 5.2 CoW vs MoR | 重写整文件 vs 记删除账 | 改得少选 MoR，读得多选 CoW |
| 5.3 position delete | (文件, 行号) 对 | 最通用，v2 基础 |
| 5.4 equality delete | (列值=谓词) 删除 | CDC/upsert 利器，代价在读侧 |
| 5.5 序列号匹配规则 | delete 只作用于更老的数据文件 | 正确性的核心不变式 |
| 5.6 deletion vector（v3） | Puffin 里的位图 | 读侧 O(1)，取代 position delete |
| 5.7 UPDATE/DELETE/MERGE 怎么落 | 各语句生成的文件组合 | 一次语句可产生多类 manifest |
| 5.8 读放大与维护 | delete 文件堆积的代价 | rewrite_position_delete_files/CoW 化 |

## 核心精讲

> **教学示意，不参与构建。** 下列文件结构为规范字段的简化示意。

### 5.1 不可变存储上的「删除」

数据文件（Parquet）写完即不可变；Iceberg 的提交模型也只加文件（§2.6）。于是「删 1 行」只有两条路：

- **Copy-on-Write（CoW）**：重写包含该行的整个文件（其余行原样带过去），新文件替换旧文件（entry 标 DELETED）。v1/v2 都支持，语义简单：快照里的文件集合永远「物理即逻辑」。
- **Merge-on-Read（MoR）**：不动数据文件，写一个**删除文件**记录「谁作废了」，读者合并两者。v2 引入；代价转嫁给每一次读。

### 5.2–5.4 三种删除文件

| 类型 | 载体 | 内容 | 生成场景 | 读取代价 |
| --- | --- | --- | --- | --- |
| **position delete** | v1 风格：DataFile（content=1，Parquet/ORC/Avro），列 `file_path, pos[, row]`；v3 偏好 deletion vector | 被删行的**物理位置** | MoR DELETE/UPDATE 的默认形态 | 按文件分组应用位点集合，便宜 |
| **equality delete** | DataFile（content=2），带 `equality_ids` 声明键列，值为空或存旧值 | 「`id=5 AND c='x'` 的行全删」这种**谓词** | CDC/upsert（写侧不知旧行在哪个文件） | 每个数据文件的每行都要做键匹配，最贵 |
| **deletion vector**（v3） | **Puffin 文件**（`file_format=PUFFIN`），条目用 `content_offset/content_size_in_bytes` 指向内嵌 Roaring 位图 | 目标数据文件的行号位图 | MoR 删除的 v3 形态 | 一次读取位图，O(1) 判定；**取代 position delete** |

补充两点规范细节：
- 删除文件**也有分区值**（按所属 spec 计算）——匹配只在同分区内进行（§5.5）；
- equality delete 的「旧值是否存写」：v2 允许只存键列；若存了旧值可进一步用 `lower/upper_bounds` 剪掉不可能的数据文件（`equated-delete-files` 统计在 summary 里，§2.3）。

### 5.5 序列号：删除的「时间有效域」（spec §Sequence Numbers）

v2 给**提交**编号：快照与其中新增文件共享 `sequence-number`（= 提交时的 `last-sequence-number + 1`）。删除文件的适用规则因此可以只靠年龄表达：

```text
delete 文件 D（seq=7, partition=dt=2024-01-02, spec=0）
  适用 ⟺ 数据文件 F.partition == D.partition
        且 F 的 data sequence number < 7        （v2 规则：严格小于）
```

- **为什么不能等于**：同一提交里既新增数据又发删除是病态（删刚写的行应该直接别写）；「严格小于」把「同提交内新增的文件不受本次删除影响」钉死，避免顺序歧义；
- **manifest 重写怎么保住年龄**：rewrite_data_files 合并老文件时，新文件的 `sequence_number` **继承**自旧文件（`use-starting-sequence-number`/继承语义，§2.5 的 EXISTING 条目同理）——否则「更老的文件」判定会失效，删除范围错乱；
- **retry 为什么便宜**：提交冲突重试时，只需把新写的 delete manifest 重新盖到新的基快照上、按新 seq 重标；数据文件不动（第 6 章）。
- 跨分区匹配被禁止（partition 元组必须相等）；因此 `UPDATE` 若把行的分区值改了，实现上必然拆成「老文件上 position delete + 新分区新文件」（CoW 风格处理移动，MoR 只能删旧写新）。

v1 没有序列号，删除能力整体缺席（v1 只有 overwrite 级别的操作），这就是「行级修改=v2 起」的规范根源。

### 5.6 deletion vector（v3）

position delete 的本质问题：**读侧要为每个数据文件合并一堆 (pos) 记录**，文件数×delete 数的交叉在大规模 MoR 下炸裂。v3 改为：每个数据文件配一张 Roaring 位图，存进共享的 Puffin 文件：

```text
manifest entry: DataFile 00001.parquet
             + 同一 entry 引用 Puffin 文件内该文件的 DV（offset/size）
读: 扫到 00001.parquet → 取 DV → 行号在位图里即跳过
```

- 1:1 关联（一个数据文件一份 DV），规划期即可判定，无「按分区+年龄扫描候选 delete」的过程；
- `content=3`（deletion-vector-file）与旧 position delete 可共存过渡；
- 维护过程 `rewrite_position_delete_files`（§5.8/第 8 章）与 v3 的「DV compaction」是同一治理方向的两代方案。
- 🔧 Puffin 规范（`format/puffin-spec.md`）还承载列统计/表达式统计（`compute_table_stats`/`compute_partition_stats` 过程写入的就是它）。

### 5.7 语句 → 文件映射（教学示意，Spark 方言）

```sql
-- MoR 删除：产出 delete manifest（content=1），数据文件不动
DELETE FROM orders WHERE id = 5;                    -- 引擎选择 CoW/MoR（见下）

-- MERGE upsert（CDC 入湖的典型写法）
MERGE INTO target t USING changes s ON t.id = s.id
WHEN MATCHED AND s.op = 'd' THEN DELETE
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

-- CoW 化：SQL 会话级切换（Spark）
SET spark.sql.iceberg.handle-timestamp-without-timezone = false; -- 无关，示例略
-- 实际开关是表属性：
ALTER TABLE orders SET TBLPROPERTIES ('write.update.mode'='copy-on-write',
                                      'write.delete.mode'='copy-on-write',
                                      'write.merge.mode'='copy-on-write');
```

一次 MoR `UPDATE` 的产出：新 position-delete 文件（旧行位点）+ 新数据文件（改后的行）+ 新快照（operation=overwrite? 不，MoR 更新常记 `delete`+`overwrite` 混合视图，以 summary 为准）。**结论：读 `snapshots.summary` 就能反推引擎实际执行了什么。**

等式：`write.delete.mode` ∈ {copy-on-write, merge-on-read}；更新/合并同理。Spark 默认 CoW（v2 前唯一选项），Flink/Trino 默认与可选项各不相同——以第 9 章各引擎文档核对为准。

### 5.8 MoR 的债：读放大与治理

delete 文件不会自己消失。读路径要为每个命中的 DataFile 应用所有「适用的」delete（§5.5 的候选集），于是：

- 规划变慢（更多 delete manifest 打开）、扫描变慢（每行判删除）；
- 治理手段：① `rewrite_data_files(remove-dangling-deletes=true)` 把带删除的数据文件 CoW 物化；② `rewrite_position_delete_files` 合并/清理 delete 文件；③ v3 表启用 `write.format.default=parquet` 之外的 `deletion-vector.enabled=true` 与 `delete.target.file-size-bytes` 等 DV 写路径属性 🔧（DV 模式成为一等公民，第 8 章的维护编排会带上它们）；
- 判据参考（官方文档量级建议）：行级修改频繁且**读多**→尽快 CoW 物化；写多读少（CDC 暂存层）→MoR + 定期 compaction 是甜点区。

## 版本演进与兼容性

| 版本 | 行级能力 |
| --- | --- |
| v1 | 无 delete files；UPDATE/DELETE 只能靠 overwrite 全文件重写 |
| v2 | position + equality delete、序列号、delete manifest（content=1/2） |
| v3 | deletion vector（Puffin）、DV 优先的写路径、row lineage 配合 DV 追踪 |

- 引擎侧：读 v2 MoR 表的引擎必须支持删除合并（老 Trino/Presto、老 Athena 分代支持不一致）；**同表混用 CoW/MoR 写入方**时，所有读者都必须能处理 delete——「一个引擎不支持」= 数据静默少删，属兼容性红线。
- 1.6+：Spark `add_files`→v2 迁移、维护过程对 delete 文件的持续优化；🔧 1.9/1.11 线：DV 写路径、partial-progress rewrite。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「DELETE 删了文件」 | 只新增了删除账本；物理清理要等 compaction/expire |
| 「MoR 一定比 CoW 快」 | 写侧快、**每次读都付利息**；读频高即成负资产 |
| 「equality delete 和 position delete 等价」 | 前者按值匹配、可作用于「将来才出现」的兼容新文件规则更严（仅对 seq 更小文件生效），后者按位点、必须知道目标文件 |
| 「upsert 用 DELETE+INSERT 两条就行」 | 并发下不原子；用 MERGE（单提交）或 Flink upsert 模式（第 9 章） |
| 「delete 文件多了影响元数据」 | 不仅影响元数据大小，主要影响**每个数据文件的合并成本**与规划剪枝 |
| 「v3 DV 出现后 position delete 作废」 | 兼容期内可共存；迁移策略见官方版本说明（此处不展开实现细节） |
