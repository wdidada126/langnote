# 第 8 章 表维护操作：compaction、快照过期与孤儿文件

## 本章地图

> 一句话：**Iceberg 的「快」是把成本后置换来的——小文件、manifest 碎片、删除账本、旧快照都在悄悄堆积；维护四件套（rewrite_data_files / rewrite_manifests / expire_snapshots / remove_orphan_files）就是把利息定期结清的调度学。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 8.1 为什么会变慢 | 文件数/元数据树/删除账本三条债 | 维护=对着 `manifests`/`files` 元数据表做体检 |
| 8.2 rewrite_data_files | 小文件合并、排序、策略与参数 | binpack/sort/zorder；partial-progress 可长驻 |
| 8.3 rewrite_manifests | manifest 碎片化治理 | 规划慢于扫描时的第一嫌疑 |
| 8.4 expire_snapshots | 保留窗口与时间旅行的对账 | 窗口 ≥ 最长读+回滚需求，含 refs |
| 8.5 remove_orphan_files | 危险的双刃剑 | dry-run + 窗口必须大于一切写入周期 |
| 8.6 过程全景 | rollback/branch/cherrypick/migrate 等 | 按「管理/维护/迁移」三类记忆 |

## 核心精讲

> **教学示意，不参与构建。** `CALL` 语法核对自官方文档示例，未在集群执行。

### 8.1 三条债的体检 SQL（Spark）

```sql
SELECT * FROM t.files WHERE deleted = false;      -- 文件数、平均大小（<100MB 亮红灯）
SELECT content, count(*) FROM t.manifests GROUP BY content; -- manifest 数与 data/delete 拆分
SELECT * FROM t.partitions;                        -- 每分区文件数、所跨 spec
SELECT * FROM t.snapshots ORDER BY committed_at;   -- 快照频率与体量（流式表一小时几百个）
```

- **数据文件债**：流式/微批写入 → 碎文件 → 规划与打开开销爆炸；
- **元数据债**：每次提交新增 manifest；高频提交+过期滞后 → manifest list 巨大、规划器打开成本上升 → `rewrite_manifests`；
- **删除债**：MoR delete files 堆积（§5.8），读每行都要查账。

### 8.2 rewrite_data_files（binpack / sort）

```sql
-- binpack：合并到 ~512MB，可按分区裁剪范围
CALL sys.rewrite_data_files('db.t', where => 'dt >= "2025-01-01"',
      options => map('target-file-size-bytes','536870912','max-file-groups-to-parallelize','4'));
-- sort：借重写顺手建立排序（配合 §3.7 的 sort order 收益）
CALL sys.rewrite_data_files('db.t', strategy => 'sort', sort_order => 'write_order');
CALL sys.rewrite_data_files('db.t', strategy => 'sort', sort_order => 'zorder(c1,c2)');
```

参数与语义要点（spark-procedures 文档核对）：`strategy` ∈ {null→binpack, `sort`(含 zorder/hilbert/按表 write order)}；`options` 常见 `target-file-size-bytes`、`max-file-size-bytes`/`min`、`delete-file-enabled`(dangling deletes)、**`partial-progress.enabled`**（长任务分段提交，每段一个 replace 快照——被中断可保留已完成部分）、`use-starting-sequence-number`（false 时新文件带提交时刻序列号，影响 §5.5 的删除匹配！默认与引擎版本相关，动它前先读 reliability 文档）、`remove-dangling-deletes`。
- 产出快照 `operation=replace`（§2.3）：语义「内容不变、布局变」；
- **与 CDC/流读的关系**：rewrite 不改数据内容，但会**合并文件、改变位置**——从某快照做增量读的消费方要么容忍 replace 快照（官方结构：增量读以快照序列呈现，append 才产生可消费变更），要么把消费窗口对齐到 rewrite 边界；这是「维护作业与流管道打架」的根因；
- v2+：rewrite 顺带把适用的 delete 物化掉（CoW 化），治删除债。

### 8.3 rewrite_manifests

manifest 数量爆炸（典型：Flink 分钟级 checkpoint × 多分区）会让每次规划读巨大的 manifest list。`CALL sys.rewrite_manifests('db.t')` 把当前快照的 manifest 重新打包（参数 `use_caching`；新版支持 `sort_by` 整理分区维度）。零数据重写、一个元数据提交（第 6 章），属于「规划慢但扫描不慢」时的对症药。判据：`manifests` 表行数 ≫ 合理分区数（经验值：单快照数千条以上且查询规划以秒计时）。

### 8.4 expire_snapshots：唯一真正删数据的日常

```sql
CALL system.expire_snapshots('db.sample', TIMESTAMP '2025-06-30 00:00:00', 100);
-- 命名参数版：
CALL sys.expire_snapshots(table => 'db.t', older_than => TIMESTAMP '...',
     retain_last => 7, max_concurrent_deletes => 4, clean_expired_metadata => true);
```

- 语义：删除 `older_than` 之前（且超出 `retain_last` 保底）的快照及其**不再被任何保留快照/refs 引用**的文件；参数（已核对）：`retain_last`、`max_concurrent_deletes`、`stream_results`、`snapshot_ids`、`clean_expired_metadata`（连旧 metadata 文件一起清）。
- **安全窗口三问**（maintenance 文档的明示警告）：
  1. 最长运行中的读/回滚回溯要多远？长查询固定基快照，其引用文件不能先删；
  2. 时间旅行/审计合规要求保多久？（分支/tag 也算 refs，§7.5）
  3. 失败重试的下游作业最多会回看几个快照？
- 顺序纪律：**先 rewrite（生成 replace/新快照），后 expire**；反了会把「刚被合并掉的旧文件」提前变成可删；再后才是 orphan 清理。
- 频率：高频提交（流式）的表不 expire = 元数据树无界生长、对象存储账单无界生长。

### 8.5 remove_orphan_files：最危险的过程

孤儿来源：① 提交前就失败的写作业留下的文件；② 外部引擎绕过元数据直接往表目录写；③ 维护/迁移中断。`expire` 不碰「从未被引用」的对象，所以需要专门扫描：

```sql
CALL sys.remove_orphan_files('db.t', older_than => TIMESTAMP '...', dry_run => true);
-- 参数（已核对）：older_than, location, dry_run, file_list_view, prefix_mismatch_mode
```

- 原理 = 列目录（LIST 全表前缀）− 元数据引用集，**差集即孤儿候选**；
- 三条铁律：**dry-run 先跑**；`older_than` 必须大于「任何可能仍在进行的写入周期」（候选写入但尚未提交的文件就是「未来会被引用」的文件！官方警告保留阈值覆盖全部写入周期）；跨实现路径表述差异（§/斜杠、大小写、多前缀）用 `prefix_mismatch_mode` 处理或干脆把外部文件排除出表目录；
- 成本警告：S3 LIST 按请求计费，TB 级表一次全扫的清单开销可观——用清单报告（S3 Inventory）+ `file_list_view` 喂给它。

### 8.6 过程全景（spark-procedures 清单归类记忆）

| 类 | 过程（节选） | 用途一句话 |
| --- | --- | --- |
| 管理 | `rollback_to_snapshot` / `rollback_to_timestamp` / `set_current_snapshot` / `delete_orphan_files`(别名) / `register_table` | 回滚与指针管理（§7.5、§2.7） |
| 维护 | `rewrite_data_files`、`rewrite_manifests`、`rewrite_position_delete_files`、`expire_snapshots`、`remove_orphan_files`、`rewrite_table_metadata`（压缩根文件：合并历史 schema/spec 条目、瘦身 metadata JSON）、`rewrite_table_path`（跨集群复制的路径改写） | 本章主体 |
| 迁移/摄取 | `add_files`（把外部 Hive 目录文件登记进已有 Iceberg 表）、`migrate`（Hive 表原地转换，可 `drop_backup`）、`snapshot`（保留原表的可重复摄取） | 第 9 章 Hive 迁移线 |
| 血缘/分析 | `ancestors_of`、`create_changelog_view`（net_changes/identifier_columns）、`compute_table_stats`/`compute_partition_stats`（写 Puffin）、`cherrypick_snapshot`、`publish_changes`、`fast_forward` | WAP 与增量消费 |

### 8.7 编排：把四件套变成制度

```text
建议节奏（教学示意思路，按业务对表逐一校准）：
 流式/微批表   rewrite_data_files 每 1–6h(partial-progress) + rewrite_manifests 每日
              expire_snapshots 每日（窗口=时间旅行需求 ∪ 最长读 ∪ refs）
 批 UPSERT 表  CoW 化或每日 rewrite_position_delete_files + 每周 expire
 全表         remove_orphan_files 每月（dry-run 先行；避开大写入窗口）
```

- 🔧 **Table Maintenance Service**（1.5+ 的 Spark 扩展）：以作业形式**连续调度** rewrite（自带 partial-progress 分段提交），替代手写 cron + 超时中断的脆弱方案；
- 并发约束：同一张表 rewrite 与 expire 不并行（互为危险基线，§6.6）；多表可并行但要共享 catalog 限流预算（§7.2 Glue）；
- 观测：metrics 报告（`added_data_files_result.bytes_...` 等）与维护日志入湖自监控——「维护是否跟上写入」= 快照年龄分位 & 平均文件大小趋势。

## 版本演进与兼容性

- 过程名迁移：早期 `delete_orphan_files` → 统一为 `remove_orphan_files`（旧名保留别名）；`rewrite_manifests` 1.2 起稳定；`rewrite_position_delete_files`（v2 删除文件 compaction）1.4+；`rewrite_table_metadata`/`rewrite_table_path` 1.5+；🔧 v3 DV 的维护并入 rewrite 路径。
- Flink 维护入口不同（actions/flink-runtime 的 `rewrite_aborted_sequence_number_snapshots`、compact action 等，形态与 Spark 过程不通用）；Trino/Dremio 等把部分维护能力做成 `call` 但参数面小——跨引擎表统一用 Spark 过程跑维护是主流做法。
- `expire` 的元数据清理随版本增强：`clean_expired_metadata`、`stream_results`（大表流式删，防 driver OOM）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「不维护也没事，反正查询也能跑」 | 三条债（§8.1）以查询延迟和 LIST 账单的形式收息；快照表就是病历 |
| 「expire 会删掉正在被长查询用的文件」 | 有保留窗口才安全：窗口设短了真会（maintenance 明言长回溯查询需保留版本）——事故源于拍脑袋窗口 |
| 「orphan 清理是普通垃圾回收，随手跑」 | 它是本目录唯一**可能删活数据**的过程：窗口与 dry-run 是红线（§8.5） |
| 「rewrite 会改变数据」 | replace 快照：内容不变；但**文件身份/位置全变**，流读消费方要懂（§8.2） |
| 「compaction 越频繁越好」 | 频繁 rewrite = 频繁 churn 文件、抵消上游增量；按平均文件大小与查询 P95 定频 |
| 「manifest 多了没关系」 | 规划器逐 manifest 打开比较 bounds；数与大小都进规划延迟（§2.4 的聚合统计救不了无限碎片） |
