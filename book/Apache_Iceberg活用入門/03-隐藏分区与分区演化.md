## 本章地图

> 一句话：**Hive 把「怎么分区」烧进目录名；Iceberg 把它抽象成一组可对列求值的 transform，查询用列谓词、引擎自动翻译成分区谓词——于是改分区策略只是追加一条新 spec，老数据不动。**

| 3.2 transform 家族 | identity/bucket/truncate/年月日时/void | 每种都有确定的哈希与截断语义 |
| 3.3 分区元组与剪枝 | manifest 存物化分区值 + 列统计 | 谓词→分区谓词的推导是双向的 |

| 3.5 ALTER 语法 | add/drop/replace partition field | 元数据 O(1) |
| 3.6 设计怎么选 | day+bucket 起步、宽窄权衡 | 分区是「剪枝 + 并行度」的杠杆 |

## 核心精讲

> **教学示意，不参与构建。** SQL 语法核对自官方 spark-ddl 文档，未在本机集群执行。

### 3.1 隐藏分区（hidden partitioning / 隠れパーティショニング）

Hive 分区是**字符串约定**：`WHERE dt = '2024-01-01'` 能剪枝，`WHERE ts >= '2024-01-01'`（ts 是 timestamp 列）完全不能——因为分区键 `dt` 与列 `ts` 是两个东西，翻译靠人。

Iceberg 的分区规范声明的是**对源列的函数**：`PARTITIONED BY (days(ts))`。于是：

- 写入端：引擎按 `day(ts)` 算出分区值（epoch 天数，**整数，不是字符串**）写进 manifest 的 `data_file.partition`；
- 查询端：规划器把列谓词 `ts >= :d` 按同一 transform 推导出分区谓词 `day(ts) >= day(:d)`，据此剪 manifest 条目/文件。

用户查询里**根本不需要知道分区存在**——这就是「隐藏」：分区布局是物理细节，逻辑计划只谈列。附带红利：类型安全（写错分区值不再「静默丢数据」）、谓词不漏（`>=`、`BETWEEN` 都能推导）。

### 3.2 transform 家族（spec §Partition Transforms）

| transform | 语义（规范定义） | 典型用法与注意 |
| --- | --- | --- |
| `identity` | 原样取列值（含 null→null 分区） | 低基数枚举列；高基数会炸碎分区 |
| `bucket[N]` | 对列的**规范化字节串**做 32 位 MurmurHash3，再取模：`to_int(hash(x)) mod N` | 打散热点；**N 变了=不同 spec**；float NaN 有专列处理 |
| `truncate[W]` | 定宽截断：字符串前 W 字符；整数 `x - (x mod W)`（负数向 -∞） | 粗粒度前缀/区间分桶；IP、邮编 |
| `year` / `month` / `day` / `hour` | 时间→epoch 年/月/日/时（整数天数可负） | 事件时间列的标配；`date` 走 day |
| `void` | 常量 null | 保留列名但不再参与分区（演化时「占位」） |

规范强制 transform 的**跨实现一致性**（同一值在任何语言实现算出同一分区）——这是多引擎写同一张表不裂成两套目录的前提。分区值在元数据中按源列类型编码（§2.5），`lower_bounds` 截断到规范规定的字节数。

**多列分区字段**：🔧 新版规范为 `partition_field` 引入 `source-ids[]`，支持如 `truncate(4, col_a, col_b)` 的组合 transform（较新实现才支持，跨引擎读写前先核对版本）。

### 3.3 剪枝的两级漏斗

```text
查询: WHERE ts BETWEEN :a AND :b AND category = 'x'
① manifest 级: spec 里 category=identity → 直接比对分区元组;
              无 ts 相关分区 → 落到列统计 lower/upper_bounds(ts) 判定
② 文件级: data_file 的 bounds(ts), 命中文件才进扫描计划
```

要点：**transform 参与剪枝，列统计兜底不参与的列**。所以「隐藏分区」不等于「不用统计」——2.5 的按 field-id 键控 bounds 与剪枝是同一套推导引擎的两条腿。分区列建议**低基数 + 每分区目标 ~128MB–1GB**（官方 guidance），过大剪枝粗、过小元数据爆炸（第 8 章的 manifest 压力）。

### 3.4 分区演化（partition evolution / パーティション進化）

Iceberg 区别于三剑客其他两家、也区别于 Hive 的最强能力之一（spec §Evolution）：

- 改分区 = 在 `partition-specs[]` 里**追加一条新 spec**（新 `spec-id`），并把 `default-spec-id` 指向它；
- 老文件的 manifest entry 仍按**自己写入时的 spec** 解释（manifest header 携带 `partition-spec(-id)`，见 §2.5），新文件按新 spec；
- **没有任何数据重写、没有回填任务、没有双写窗口**；
- 规划器面对混合 spec 的表：按各文件所属 spec 分别推导分区谓词，再并集结果。

等价定义的 spec 必须复用现有 `spec-id`（规范禁止注册语义相同的重复 spec）。`days(ts)` 与 `day(ts)`（REPLACE 场景，§3.5）属同义，不分裂。

**演化何时需要**：数据量与查询模式一起长大。经典路径（对应原书大概会讲的故事）：

```text
起步: (day(ts))                → 每天几个文件
量涨: (day(ts), bucket(16,id))  → 并发写入者互相压不到同一批文件
热点: (day(ts), identity(region), bucket(32,id))
```

以及反向：`bucket(16)` → `bucket(512)` 时**旧桶不变**，新文件用新桶数——这就是把「分桶数」从承诺变成建议。

### 3.5 ALTER 语法（教学示意，Spark 方言，已核对官方示例）

```sql
ALTER TABLE prod.db.sample ADD PARTITION FIELD catalog;             -- 追加 identity
ALTER TABLE prod.db.sample ADD PARTITION FIELD bucket(16, id);
ALTER TABLE prod.db.sample DROP PARTITION FIELD truncate(4, data);
ALTER TABLE prod.db.sample REPLACE PARTITION FIELD ts_day WITH day(ts); -- 换名/等价重写，不算破坏性
ALTER TABLE prod.db.sample ADD PARTITION FIELD years(ts) WITH NAME 'ts_year'; -- 🔧 给分区字段命名
```

- `ADD/DROP/REPLACE` 都只产生新的 spec + 换 `default-spec-id`，一次普通提交（第 6 章）。
- 验证演化生效：`SELECT * FROM t.partitions` 会看到同一表里多个 `spec_id` 的行；老分区字段在新写入的文件上消失。
- Flink/Trino 语法各异（Trino 是 `ALTER TABLE ... ADD PARTITION FIELD` 类似风格，Flink 1.x 部分操作仍要走 Spark/Java API——**第 9 章的多引擎核对表**）。

### 3.6 设计取舍清单

1. **时间列选事件时间还是摄取时间**：分区是物化的值，改不动历史——选错列的代价由演化兜底，但混合 spec 会让 `partitions` 元数据表读起来费劲。
2. **bucket 数不是承诺**：但要保证**同批写入者用同一 spec**（否则并行小文件翻倍）。
3. **identity 高基数陷阱**：一个 user_id 一个分区 → manifest entry 爆炸，规划器变慢（第 8 章 `rewrite_manifests` 治标，设计治本）。
4. **null/边界**：各 transform 对 null、负数、NaN 的行为规范已定，跨引擎不应有差异；遇差异按引擎 bug 处理，别改表设计绕。
5. **剪枝有效性可测**：用 `SELECT * FROM t.files` 估算谓词能剪掉多少 `file_size_in_bytes`（官方 performance 文档的推荐手法）。

### 3.7 分区不是排序：sort order 的互补位

分区决定「文件怎么分组」，`sort-orders` 决定「文件内行怎么排」。`rewrite_data_files(sort_by => 'ts, id')`（第 8 章）重写文件内容但不改 spec、不改语义；排序提升 bounds 剪枝的命中率（文件内 ts 连续 → 每文件 min/max 区间变窄 → 剪掉的更多）。「先分区演化、后排序 compaction」是治理大表的常规两步。表级默认 `WRITE ORDERED BY (ts)` 建表即可声明（Spark 语法），bucket 亦可用于排序规范（与分区 transform 共享哈希定义）。

## 版本演进与兼容性

- 分区演化自 0.7/2019 即有，是 Iceberg 的招牌；v1 表就支持多 spec。
- 🔧 1.4+：分区字段命名（`WITH NAME`）、更完整的 transform 描述符；新版：多列 transform（source-ids）；v3 表 `void` 与新增字段的 null 分区行为不变。
- 兼容性关注：老实现/老引擎（如旧版 Presto、未升级的 Hive ODPS 类连接器）可能不支持多 spec 表的读取；跨引擎表演化前先跑一遍各引擎的最小读测试。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「隐藏分区=没有分区」 | 布局照常存在且物化在 manifest，只是查询面不可见也不需要可见 |
| 「DROP PARTITION FIELD 会删老数据/老目录」 | 只影响**新写入**用的 spec；老文件继续按老 spec 解释 |
| 「改分区后要跑迁移任务」 | 不需要；Iceberg 无「迁移窗口」概念（对比 Hive 改分区的重写） |
| 「分区越多剪枝越好」 | 碎分区→小文件+manifest 膨胀，规划变慢；剪枝目标 128MB+ /分区，其余交给排序与 ZOrder 类聚簇 |
| 「bucket(16) 和 bucket(17) 数据会串」 | 它们是不同 spec，各写各的文件，互不冲突；只是同表内并存 |
| 「WHERE dt='2024-01-01' 还能用」 | 分区不再以目录/列的形式存在，硬编码分区谓词的旧查询要改成对源列的谓词 |
