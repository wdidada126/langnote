## 核心概念速览（中英对照）

| 中文 | 英文 | 一句话定义 |
|---|---|---|
| 状态 | state | 对象字段在程序生命周期内的取值历史；可变=允许原地改写 |
| 状态变更 | (state) mutation | `x = x + 1` 式的原地改写——01 档 effect 的头号来源 |
| 不可变数据 | immutable data | 一经构造不再改写；"修改"= 构造新值（`val` + `data class`） |
| 受控变更 | controlled mutation | Saumont 关键立场：变更不被禁止，被**圈进可审计的边界** |
| 持久化/共享结构 | persistent data structure | 旧版本与新版本共存且共享大部分存储（List 的 cons 节点） |
| 拷贝更新 | copy-on-write update（`copy()`） | Kotlin data class 的"以新替旧"惯用法；深改痛点见 06 档 Lenses |
| 引用透明对偶 | transparency under immutability | 纯函数+不可变数据 ⇒ 任意表达式可缓存/并行/重放 |

## 复演：渐进重构叙事（本档演进链）

Saumont 的招牌例子族之一是"银行账户"（⚠️ 情节复演，非逐字引书）——
从裸可变对象改到"变更被关进笼子"：

**第 0 态——裸可变**（坏在：任何方法、任何调用方都能改余额，历史不可追溯）：

```kotlin
class Account0(var balance: Double = 0.0) {
    fun deposit(a: Double) { balance += a }
    fun withdraw(a: Double) { if (a <= balance) balance -= a else throw RuntimeException("nsf") }
}
```

三个病灶同时发作：并发下 `+=` 非原子；`throw` 违反 03 档纪律；单元测试必须"先跑一遍才知道状态"。

**第 1 态——全量不可变**（消灭的 effect：原地改写；异常顺手换 Either）：

```kotlin
data class Account1(val ownerId: String, val balance: Double = 0.0) {
    fun deposit(a: Double): Account1 = copy(balance = balance + a)
    fun withdraw(a: Double): Either<Error, Account1> =
        if (a in 0.0..balance) Right(copy(balance = balance - a))
        else Left(InsufficientFunds(a, balance))
}
// 每个"版本"都是值：可断言、可回放、可并行——账户历史 = 值序列
```

**第 2 态——变更并未消失，只是搬家**（现实需求：一个 update 函数里连续存取三次）：

```kotlin
fun process(a: Account1, ops: List<Double>): Account1 =
    ops.fold(a) { acc, o -> if (o >= 0) acc.deposit(o) else acc.withdraw(-o).orThrow() }
// 局部"可变量" acc 仍在，但它是**参数线程**（threaded state）：
// 每次迭代显式携带、不可被外部看见——变更被降维成数据流
```

**第 3 态——受控变更的合法形态**（Saumont 的妥协位）：性能热点确需原地改时，
用私有构造器+只暴露变换方法，把 mutation 圈在类内部一处：

```kotlin
class Account3 private constructor(private val balance: Double) {          // 字段 val！
    constructor() : this(0.0)
    fun deposit(a: Double) = Account3(balance + a)                          // 返回新实例
    companion object { fun of(b: Double): Account3 = Account3(b) }          // 入口即校验点
}
// "变更控制"字面义：能改的构造路径只有一条，审计面 = 一处
```

## Java / C++ 对照

- **Java**：`final` 字段+无 setter 只是"浅不可变"——`final List` 内容照改；真不可变需
  防御拷贝或 `Collections.unmodifiable*` 包装。record（Java 16，2021，晚于本书）= `data class`
  的迟到直系；对比之下 Kotlin 的 `data class.copy()` 是语言级标配。
- **C++**：`const` 修饰**访问路径**不修饰**对象**——`const T&` 可绑到非 const 原物；
  真正不可变要 `constexpr`+构造后无别名改写，且拷贝语义默认深复制（`copy` 的心智负担更重）。
  RAII/移动语义让 C++ 的"版本化更新"倾向复用缓冲，与持久化结构的共享哲学相反。
- **Kotlin**：`val` 只锁引用不锁内容（`val list = mutableListOf()` 照样能 add）——
  与 Java `final` 同款陷阱；持久化 List（`::` cons）在 stdlib 缺席，Arrow 等库补位 ⚠️。

## 权衡

- **优点**：可推理性（值=快照）、天然并行安全、历史即数据（事件溯源的微型预览）。
- **缺点**：结构共享缺失时深树更新 O(n) 拷贝；`copy` 只到一层（痛点与解药 → 06 档 Lenses）；
  垃圾回收压力。
- **本仓预设立场**（⚠️ 读后裁决）：Saumont 的"控制而非禁止"比原教旨 immutability
  更适合 JVM——记账在签名与边界，不在信仰。
