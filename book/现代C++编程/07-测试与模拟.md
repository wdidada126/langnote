## 核心概念速览（中英对照）

- **单元测试** — unit test：以「可命名的最小行为」为粒度的自动化验证，C++ 无语言级 xUnit，全靠库
- **测试夹具** — test fixture：为同组用例重复准备/销毁环境（GoogleTest 的 `TEST_F` 类）
- **判据/断言宏** — assertions / matchers：`EXPECT_*` 继续执行、`ASSERT_*` 即刻返回——失败语义的两种
- **测试替身谱系** — test doubles：dummy/stub/spy/mock/fake 五分法，只有 mock 断言「交互」
- **模拟框架** — mocking framework：GoogleMock（与 GTest 同仓）、Trompeloeil、FakeIt（运行时反射式）等
- **依赖注入** — dependency injection：协作对象经构造/参数传入而非内部 new，多态接口（`03` 章）是其载体
- **接缝** — seam：被测代码里「可替换点」的名字；测试可行性=接缝密度
- **制动服务例** — brake service example：以传感器/执行器接口为注入点的教学标本（10.2）
- **头-only 测试库** — header-only test lib：Catch2 单头文件/自注册用例，与 GTest 主框架流对照
- **死亡测试** — death test：`EXPECT_DEATH(stmt, "regex")` 在子进程里验证「该崩就崩」，`assert`/`terminate` 语义的验收工具
- **参数化/类型化测试** — value/typed tests：同一逻辑扫枚举值或扫类型列表，模板与测试宏的合流点（`04` 章回收）
- **表达式分解** — expression decomposition：Catch2 宏把 `REQUIRE(a == b)` 两侧求值成可读报告，断言宏的两副面孔
- **伪实现** — fake：如内存版 DAO，行为真实但换存储——比 mock 便宜、比真库快的中间选项（Martin Fowler 替身谱系）
- **消毒器协同** — sanitizers：ASan/UBSan/TSan 与单测同跑是工业 CI 默认组合，「测试通过」≠「无未定义行为」

## 1. 动机：为什么测试章压轴第二部分开头

第一部分讲完语言，原书立刻用第 10 章回答「写出来的东西怎么证明是对的」——这是全书教学结构上最像工程书的一笔：第 10 章的判据（接缝、注入、替身）会贯穿此后每一章的库选择（智能指针→所有权可断言、Asio→定时器可虚拟时钟）。10.2 的汽车制动服务例子刻意选在**硬件依赖**场景：不注入替身就无法测试，逼出「接口先行」的设计反思。

## 2. 机制：框架解剖与 mock 的工作方式

**GoogleTest 骨架。** `TEST(Suite, Case)` 宏自注册进全局用例表，`main` 里的 `RUN_ALL_TESTS()` 驱动；`EXPECT_EQ/THROW/DOUBLE_EQ` 展开为带源位置信息的断言对象（`05` 章语句作用域 + 本处宏元编程的双重应用）。死亡测试（`EXPECT_DEATH`）、参数化与类型化测试族覆盖「断言×夹具×枚举」的组合需求。

**GoogleMock 的机制。** `MOCK_METHOD(void, applyBrake, (int level), (override))` 生成带「期望表」的替身：`EXPECT_CALL(mock, applyBrake(3)).Times(2).WillOnce(...)`——成员函数在编译期被改写成记录交互的通用转发器（变参模板+宏，`04`/`06` 章的工业级示范）。**行为验证（交互断言）而非状态断言**，是 mock 与 stub 的分水岭。

**Catch2/Test-Do-That 光谱。** Catch2 用表达式分解宏把断言两侧求值展开成可读报告；doctest 是它的轻量分支；Trompeloeil 以「纯 C++ 宏」实现 mock 而少一分预处理器黑魔法（本会话未验证其现状 ⚠️ 只作方向引用）。选择判据：CI 依赖管理（header-only 友好度）、断言语法可读性、mock 表达力。

**测试与生命周期。** 10.4 隐含的关键工程点：替身所有权（值成员 vs `unique_ptr`+注入）、异步代码的时序断言（`13` 章 Asio 处需要「手动推进时钟」类接缝）——这些把测试章与第 4/11 章焊在一起。

## 3. 权衡：接缝密度就是设计税

- **mock 一切 vs 真值优先**：过度 mock 让测试「与实现同碎」——Google 系指南的口径：优先真依赖+快 I/O（`std::filesystem::temp_directory_path`，`11` 章），接口只给真正的替换需求留。
- **宏框架 vs 语言设施**：GTest/GMock 的宏魔法与 C++20 反射前景（P2996 线，同库笔记已核为 Reflection for C++26）形成对照——反射若落地，MOCK_METHOD 这类代码生成物可能半标准化。
- **`assert` 不是测试**：`NDEBUG` 下 `assert` 整体消失（第 21 章程序支持设施回收此坑），且断言失败=进程终止，与测试框架的「记录并继续」语义不同物种。

## 4. 相邻概念对比

| 概念 A | 概念 B | 分界线 |
| --- | --- | --- |
| stub（返回值桩） | mock（交互期望） | 只喂输入 vs 还断言「被怎样调用」；能用状态断言就别上交互断言 |
| GTest 主框架 | Catch2 自注册 | `main` 控制权与构建集成方式的流派差；单文件引入难度差 |
| `EXPECT_*` | `ASSERT_*` | 记录失败继续 vs 立即 return（GTest 家族语义） |
| 运行时反射式 FakeIt | 编译期 MOCK_METHOD | 运行时方法拦截（平台限制、慢）vs 类型安全的代码生成 |
| 单元测试 | 属性测试/集成测试 | 定点例 vs 随机空间 vs 边界缝合——本章只教第一层 |

## 典型误区与修正视角

| 误区 | 症状 | 修正视角 |
| --- | --- | --- |
| 「`assert` 就是单元测试」 | Release 构建里验证集体蒸发 | `NDEBUG` 整体删除 + 失败即终止进程；测试框架的语义是「记录并继续」（本章 🔧 微型框架即演示这一半区） |
| 「mock 越多越安全」 | 重构实现时测试全红、行为没变 | 交互断言把**实现细节**钉进测试；能状态断言就不交互断言，接缝只为真替换需求留 |
| 「`TEST` 顺序可以指望」 | 用例间共享静态状态偶发失败 | 两大框架都支持乱序/过滤运行（GTest `--gtest_shuffle`、Catch2 `--order rand`）；用例必须可独跑 |
| 「GMock 的 NiceMock 是默认姿势」 | 噪音期望全靠 Nice 压掉 | 默认 `NaggyMock` 报警是有原因的：先弄清越界调用来自哪，再决定 `Nice`/`Strict` |
| 「替身所有权交给框架」 | mock 生命周期与注入点错配悬垂 | 所有权走 `08` 章三选一（值/`unique_ptr` 独占/`shared_ptr` 共享）；`EXPECT_CALL` 只描述行为不管寿命 |
| 「异步代码靠 sleep 测」 | CI 上偶发红、本地绿 | 需要「手动推进时钟/任务泵」接缝（`13` 章 Asio `io_context` 恰好可停可跑），真实等待是测试反模式 |
| 「测试框架选定就永远不换」 | 迁移成本逐年堆积 | 判据三件套：CI 依赖管理难度、断言可读性、mock 表达力——GTest↔Catch2 的「header-only 便利」神话两边都有账（Catch2 v3 已转库形态） |

## 🔧 实测对照：手写微型测试框架 vs `std::source_location` 加持（已实测 g++ 15.2）

10.1 的教学起点是「不用框架也能测」——2026 年给手写断言加位置信息不再需要 `__FILE__` 宏戏法：

```cpp
#include <cstdio>
#include <source_location>
struct Assert {
    int passed = 0, failed = 0;
    void check(bool cond, const char* what,
               std::source_location loc = std::source_location::current()) {
        if (cond) { ++passed; }
        else { ++failed; std::printf("FAIL %s @%s:%d\n", what, loc.file_name(), loc.line()); }
    }
    ~Assert() { std::printf("passed=%d failed=%d\n", passed, failed); }
};
bool braked(bool sensor) { return !sensor; }
int main() {
    Assert a;
    a.check(braked(false), "no sensor -> not braked");
    a.check(!braked(true),  "sensor -> braked");
    a.check(braked(true),   "deliberate wrong expectation");
}
```

- `-std=gnu++20` 真实输出：`FAIL deliberate wrong expectation @s07.cpp:16` ＋ `passed=2 failed=1`（默认实参在**调用点**捕获 `source_location::current()`，行号精确到失败调用行）。
- `-std=gnu++17`：编译失败——`<source_location>` 是 C++20 库件（其语言-库衔接采用稿主题 *Source location* ⚠️ 本会话未逐字核提案号）。
- 这就是 GoogleTest 宏给你东西的最小无宏实现：把这份 20 行框架与 10.2 例子的判据接起来，「为什么还要框架」的答案自然浮现（用例发现、参数化、死亡测试、断言表达式分解——宏省不掉的部分）。

## 最新演进与工业实践

- **C++20 对测试库的三件补给**：`source_location`（上实测）、三路比较让 `EXPECT_EQ` 级断言对自定义类型免写比较（`05` 章 `<=>`）、`[[likely]]`/`[[assume]]` 与 sanitizer 编译选项协同（[`google/sanitizers`](https://github.com/google/sanitizers)：ASan/UBSan/TSan 与 CI 组合已是工业默认；本项目平台注脚：MSVC `/fsanitize=address` 可出报告、MinGW 无 libasan，见 [`../C++代码调试的艺术.md`](../C++代码调试的艺术.md) 实测记载）。
- **工业仓库**：[`google/googletest`](https://github.com/google/googletest)（GTest+GMock 同仓）、[`catchorg/Catch2`](https://github.com/catchorg/Catch2)（v3 起转库形态——「header-only 永远便利」也需修正 ⚠️ 版本细节以官方文档为准）、[`doctest/doctest`](https://github.com/doctest/doctest)（编译速度优先的分支）、[`boostorg/ut`](https://github.com/boostorg/ut)（Boost 生态内的极简反射风格测试件）。
- **练习/拓展接点**：10.x 的制动服务练习在 2026 年的升级点：把传感器接口注入改写成 `std::function<void(int)>` 回调版（`06` 章账单：可测性提升 vs 间接调用），再用 concepts 把「任何满足 BrakeService 概念的替身」免继承接入——接口注入与概念约束的正面对撞实验。
