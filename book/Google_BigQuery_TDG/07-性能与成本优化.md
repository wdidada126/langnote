## 核心精讲

### 1. "按字节计费"——成本函数的第一性原理（⚠️ 转述）

BigQuery 按需模式：每查询扫描的字节数 × 单价 = 费用。**未裁剪的 SELECT \*** 是最直接的烧钱姿势。
配套仓库 `07_perf/cost_estimate.sh`（✅ 实抓）演示 dry run 估字节：

```bash
# 配套仓库原例（✅）：dry run 估算查询扫描量
bq query --dry_run --format=prettyjson "SELECT * FROM \`bigquery-public-data\`.new_york_citibike.citibike_trips"
# 输出含 totalBytesProcessed 字段 → 换算美元
```

⚠️ 官方口径：1 TB 扫描 ≈ $5（按需价，以现文档为准）；首 1 TB/月免费。
这意味着**分区裁剪省的不是时间——是钱**（与 Snowflake credits 模型形成对照，
[../Snowflake_The_Definitive_Guide/08-账户成本管理.md](../Snowflake_The_Definitive_Guide/08-账户成本管理.md)）。

### 2. 分区裁剪：第一杠杆（⚠️ 转述 + ✅ URL）

分区表按日期/时间列或整数区间切块（06 章已述机制）；查询 WHERE 命中分区键→只扫对应块。
⚠️ 关键约束：
- 分区键必须是 DATE/TIMESTAMP/INT64（整数区间 2023+ ⚠️）；
- 每表最多 4000 个分区（⚠️ 官方 quotas 页）；
- 对 `_PARTITIONDATE` / `_PARTITIONTIME` 伪列的过滤必须用常量表达式（不能是子查询结果 ⚠️）。

配套 `hurricanes.sql`（✅ 配套仓库实抓）以地理+时间双维过滤示范裁剪组合拳。

### 3. 聚簇：分区内的二级剪刀（⚠️ 转述）

聚簇按 ≤N 列物理排序存储→匹配谓词时块级统计（min/max）跳过非匹配块。
⚠️ 注意：
- 聚簇**不替代**分区——二者叠加使用；
- 聚簇列选择应匹配高频过滤/JOIN 键；
- 聚簇表在 INSERT/UPDATE 时有额外排序成本（⚠️ 写入变慢换读取变快）。

🔧 **DuckDB 1.5.5 类比（非 BigQuery 行为）**：DuckDB 无聚簇概念，但 hive 分区 parquet 的裁剪行为
可类比（06 章 T9 实验已实测）。核心定律一致：**裁剪省扫描，碎文件吃收益**。

### 4. 近似函数：用误差换钱（⚠️ 转述）

03 章已列 `APPROX_COUNT_DISTINCT`/`APPROX_QUANTILES`；本章的消费视角：
- 精确 `COUNT(DISTINCT x)` 在 10 亿行上可能扫全量→$50；
- `APPROX_COUNT_DISTINCT(x)` 用 HyperLogLog 草图→扫描量相同但计算量骤降（⚠️ 计算成本 vs 扫描成本区分）；
- `TABLESAMPLE SYSTEM(10 PERCENT)` 在探索阶段直接砍 90% 扫描字节。

### 5. 物化视图与结果缓存（⚠️ 转述）

| 机制 | 命中条件 | 计费 |
| --- | --- | --- |
| 结果缓存 | 完全相同 SQL + 底表未变 + 窗口内（⚠️ ~24h） | 免费（0 字节） |
| 物化视图 | 查询匹配预计算定义 + 刷新周期内 | 按 MV 大小扫描（远小于原表） |

⚠️ 结果缓存**不保证**命中——任何 DML/DDL/流式写入都使缓存失效。
物化视图的刷新有成本（按刷新时扫描字节计），需权衡"刷新频率 vs 数据新鲜度 vs 查询频率"。

### 6. 槽位管理与 editions（⚠️ 转述 + ✅ 官方 slots 页）

2026 的槽位叙事已演化为 editions 体系：

| edition | 槽位模型 | 适用 |
| --- | --- | --- |
| Standard | 按需自动分配，无预留 | 探索/低频 |
| Enterprise | 可预留槽位 + 容量承诺折扣 | 生产负载 |
| Enterprise Plus | 自动扩缩 + 更高隔离 | 大规模/SLA 敏感 |

⚠️ fluid scaling（2026-06 GA ✅）：预留槽位秒级计费、无最小时长——这是原书 2019 时代"按月承诺"的重大松绑。
对读 Snowflake 仓库秒级启停 [../Snowflake_The_Definitive_Guide/02-架构与虚拟仓库.md](../Snowflake_The_Definitive_Guide/02-架构与虚拟仓库.md)。

### 7. BI Engine：看板 SLA 的兜底层（⚠️ 转述）

BI Engine 把热点数据/预计算结果放入内存→亚秒级响应。
⚠️ 成本独立计费（GB/月内存）；适用场景：Looker/Data Studio 看板、高频重复查询。
05 章"应用侧模式清单"中"用 BI Engine 兜住看板 SLA"即指此。

## 常见误区（⚠️ 转述 + 🔧 实测校准）

| 误区 | 事实 |
| --- | --- |
| SELECT * 只是"多拉几列" | 每多一列 = 多扫一列的字节 = 多花钱（列存的代价面） |
| 分区越多越好 | 碎分区→文件碎片→打开成本吃掉裁剪收益（🔧 06 章 T9 精神） |
| 缓存一定命中 | DML/流式写入即失效；窗口以官方文档为准 |
| 槽位 = vCPU | slot 是并行度抽象单位，不承诺 CPU 等价（⚠️ slots 页） |
| 近似函数省扫描字节 | 近似函数省**计算量**，扫描字节不变（但耗时/槽位占用下降） |
| dry run 收费 | dry run 免费——是预算第一工具（✅ cost_estimate.sh） |

## 最新演进与工业实践

- **editions 体系定型（2024-2026 ✅ 版本说明实抓）**：Standard/Enterprise/Enterprise Plus 三级取代原书时代的"按需/预留"二分；
  fluid scaling 2026-06-03 GA 使预留槽位可秒级自动扩缩——成本弹性大幅跃升。
- **Iceberg 托管表的成本面（2026-07 GA ✅）**：开放格式进入托管执行面→"自带格式 vs 托管格式"的成本权衡
  成为新课题（✅ docs.cloud.google.com/bigquery/docs/iceberg-tables）。
- **查询洞察仪表盘**：控制台内置查询日志分析（✅ 版本说明 2026 条目），把"哪些查询烧钱"从 INFORMATION_SCHEMA 手工 SQL
  升级为开箱即用的可视化面板。
- **工业实践**：生产环境常见分层——交互查询走 Standard edition（按需）；批管道走 Enterprise 预留（承诺折扣）；
  看板走 BI Engine（内存兜底）。对读 Snowflake 同题
  [../Snowflake_The_Definitive_Guide/09-查询性能分析与优化.md](../Snowflake_The_Definitive_Guide/09-查询性能分析与优化.md)。
- **方言趋同的省钱启示（🔧）**：DuckDB 1.5.5 的 `EXCLUDE` 列剔除（02 章实测）在 BQ 侧对应 `SELECT * EXCEPT`——
  二者都是"只扫需要的列"的列存纪律；语言不同，经济动机一致。
