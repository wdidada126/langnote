# 第 4–5 章 架构分解与基于组件的分解模式

> 覆盖原书第 4 章（代码库能分解吗 / 基于组件的分解 / 战术分叉 / Sysops Squad：走上分解之路）
> 与第 5 章（识别和调整组件、收集公共领域组件、扁平化组件、明确组件依赖项、
> 构建组件领域、构建领域服务、总结）。
> 这两章是本书「分而治之」部分的操作手册：第 2–3 章回答「要不要拆」，
> 这里回答「从哪里下刀、按什么顺序切」。

## 本章地图

> 一句话：**先问「代码库能不能分」（分不了就别谈服务化），再选一条分解路径
> （基于组件 / 战术分叉），最后用六种组件模式把切出来的东西整理成可治理的形态。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 4.1 代码库能分解吗 | 先评估代码库本身的可分解性 | 耦合缠成一团的库，**先重构再拆**，否则只是把混乱分布式化 |
| 4.2 基于组件的分解 | 找出组件边界，按边界切 | 组件是分解的基本单位，服务只是组件的一种部署形态 |
| 4.3 战术分叉 | 复制单体后各自删不需要的部分 | 用「删除」代替「设计」，快速暴露真实的耦合点 |
| 5.1 识别和调整组件 | 找出候选组件并调整边界 | 边界的第一版几乎总是错的，要迭代 |
| 5.2 收集公共领域组件 | 把被多处复用的领域逻辑收拢 | 复用的领域逻辑要不要成为服务，是独立决策 |
| 5.3 扁平化组件 | 去掉不必要的层级 | 层级是耦合的藏身处 |
| 5.4 明确组件依赖项 | 把隐式依赖变成显式契约 | 依赖可见，才谈得上治理 |
| 5.5 构建组件领域 | 按领域聚合组件 | 领域边界 > 技术层级 |
| 5.6 构建领域服务 | 把领域组件升级为独立服务 | 服务化的最后一步，也是代价最高的一步 |

## 核心精讲

> **教学示意，不参与构建。** 以下检查表、分叉流程与依赖图均为教学性重述。

### 3.1 第 4.1 节：先问「代码库能分解吗」

```text
分解前的体检清单（教学示意）：
  □ 有没有清晰的模块/包结构？还是所有代码都能互相 import？
  □ 有没有共享的可变全局状态？（它是分解的头号杀手）
  □ 数据访问层是否集中？还是到处散落 SQL？
  □ 领域逻辑与基础设施逻辑是否混在一起？
  □ 有没有基本的测试保护？（没有测试就重构 = 赌博）
  □ 构建是否可增量？一次全量构建会拖垮分解节奏

判定（教学示意）：
  体检大部分不过 → 先做**模块化重构**（在单体内建立边界），不要急着拆服务；
  体检基本通过 → 可以进入基于组件的分解。
```

这条顺序是本章最重要的实务建议：**分布式化不会消灭耦合，只会让耦合变贵**。
先在单体内把边界做实，是 2023 年之后业界反思的核心结论之一（见「版本演进」）。

### 3.2 第 4.2 节：基于组件的分解

```text
组件（component）：系统的一个物理/部署/可替换的构成单位，
                  有明确定义的接口与依赖。
分解步骤（教学示意）：
  ① 识别候选组件：按业务能力/领域概念/变更频率分组；
  ② 画依赖图：谁依赖谁，有没有环；
  ③ 消除环：提取公共部分或反转依赖；
  ④ 定义接口：组件之间只通过接口通信；
  ⑤ 决定部署形态：同一进程内的模块？还是独立服务？——这是**两个决策**。
```

关键点：**「划分组件」与「部署成服务」是两个独立决策**。
很多团队把它们合成一个决策，结果是被迫接受分布式的全部代价。

### 3.3 第 4.3 节：战术分叉（tactical forking）

```text
战术分叉的流程（教学示意）：
  ① 把单体代码库整体复制 N 份（每份对应一个目标服务）；
  ② 在每一份里**删除**不属于该服务的代码；
  ③ 编译——编译不过的地方，就是真实的耦合点；
  ④ 逐个处理这些耦合点：要么抽出公共组件，要么改成显式接口调用；
  ⑤ 反复迭代，直到每份都能独立编译。

为什么有效：
  「设计边界」是猜测，「删除代码」是实证。
  编译器会告诉你真实依赖是什么，比架构研讨会可靠。
代价：
  短期代码重复、合并困难、需要严格的时间盒（不能长期多份并行）。
```

### 3.4 第 5 章的六种组件分解模式

```text
① 识别和调整组件模式（5.1）
   先把候选组件找出来（靠变更频率、业务能力、数据归属），再迭代调整边界。
   第一版边界几乎必然要改——把它当作假设，不要当作结论。

② 收集公共领域组件模式（5.2）
   把被多处用到的领域逻辑（如「计算折扣」「校验资质」）收集起来。
   ⚠ 收集 ≠ 服务化：先成为库，再决定要不要成为服务（见第 8 章复用模式）。

③ 扁平化组件模式（5.3）
   去掉「为了分层而分层」的中间层。层级越多，依赖越难看清，重构越痛。

④ 明确组件依赖项模式（5.4）
   把隐式依赖（反射、全局状态、共享库表）变成显式接口/契约。
   依赖不可见 → 无法治理 → 无法自动化检查。

⑤ 构建组件领域模式（5.5）
   按业务领域聚合组件，而不是按技术层（controller/service/dao）聚合。

⑥ 构建领域服务模式（5.6）
   把某个领域的组件升级为独立部署的服务——代价最高的一步，
   换来独立伸缩、独立发布与团队自治。
```

### 3.5 示意：一张分解顺序图（教学示意）

```text
阶段 0  体检：代码库可分解吗？——不过关就先做模块化重构
阶段 1  识别组件 + 画依赖图 + 消环
阶段 2  明确依赖项（接口化），把隐式耦合显性化
阶段 3  按领域聚合组件，扁平化层级
阶段 4  收集公共领域组件（先做成库）
阶段 5  只对「驱动因素成立」的领域做服务化（第 3 章的驱动因素）
阶段 6  为服务化付出的代价买单：数据所有权（第 6、9 章）、
        分布式事务（第 12 章）、契约（第 13 章）
```

## 版本演进

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| 拆分的默认答案 | 微服务仍是现代化目标 | **模块化单体**重新成为默认起点：先在单体内做实边界，确有驱动因素再服务化 |
| 分解依据 | 限界上下文（DDD）+ 变更频率 | DDD 术语的普遍使用有所退潮，但「按变更频率与数据归属划分」这一实质保留下来 |
| 战术分叉 | 作为一种激进但有效的手段 | 仍有效；但更常见的是**渐进式绞杀**（strangler fig）与「先模块后服务」的组合 |
| 依赖治理 | 靠评审与架构图 | 静态依赖分析进 CI；依赖图可由构建系统与可观测性自动产出 |
| 重构的执行 | 人工 | AI 编码助手显著降低了机械重构（改名、提接口、搬包）的成本，但**边界判断仍属人** |
| 分解的验收 | 主观 | 用适应度函数验收：依赖方向、禁止跨模块直连、层级规则等可自动检查 |

## 近年研究与工业界开源实践（2015–2026）

- **「先模块后服务」成为主流建议**：2023 年之后，业界反思过度拆分的公开讨论增多，
  主流做法是先在单体内用模块边界、依赖规则与独立的 schema 做实切分，
  再用本章的分解模式逐步外移。这与本书第 4–5 章的顺序一致，只是**更强调停在阶段 3 也可以**。
- **静态依赖治理工具化**：`TNG/ArchUnit` star = **3843**（2026-09 `gh api` 实测），
  可把「明确组件依赖项」「禁止跨领域依赖」写成 CI 里的可执行检查（见 [01](01-权衡分析的语言-ADR与适应度函数.md)）。
- **AI 编码助手降低机械重构成本**：搬包、提接口、消环这类机械工作被大幅加速；
  但「哪些代码属于同一业务变化单元」仍需人来判定——这正是本章 5.1 的核心。
- **绞杀者模式仍是主力迁移路径**：配合网关/代理逐步切流，降低一次性重写风险。
- **依赖可视化**：构建系统与分布式追踪可自动产出依赖图，
  让本章 5.4「明确依赖项」从人工梳理变成可自动生成的事实。
- 本目录所有代码为教学示意、不参与构建；star 均为 2026-09 `gh api` 实测，查不到写「star 未核验」。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「先拆服务，边界以后再调」 | 分布式化让边界**更难调**（跨网络、跨契约、跨数据）；先在单体内做实 |
| 2 | 「战术分叉 = 长期维护多份代码」 | 它是**发现耦合**的短期手段，必须有严格时间盒 |
| 3 | 「按技术层分组件」 | 按业务变化单元与数据归属分（Parnas 1972） |
| 4 | 「公共逻辑一收集就做成服务」 | 收集 ≠ 服务化；先做库，服务化会引入新的运维与可用性代价（第 8 章） |
| 5 | 「依赖图画完就完事」 | 依赖必须**显式且可检查**，否则图很快失真 |
| 6 | 「拆完就解耦了」 | 共享数据、共享库、同步强依赖都会把量子重新焊回去（第 2 章） |
| 7 | 🔧 「微服务是分解的终点」 | 2023 年后的实践更强调：停在模块边界也是一种**合格终点** |
| 8 | 🔧 「DDD 术语是分解的必要条件」 | 术语热度有起伏，实质（变更频率 + 数据归属）不变；别为术语而术语 |
| 9 | 🔧 「AI 能自动完成分解」 | 机械重构可以，边界判断不行；边界错了，生成越快偏得越远 |
| 10 | 🔧 「分解不需要验收标准」 | 用适应度函数验收（依赖方向、层级、禁止跨领域直连），否则边界会被慢慢磨掉 |

## 思考题

1. 用 3.1 的体检清单给你们的单体打分：有几项不过？每项不过要付什么代价？
2. 画一张真实的组件依赖图（用构建工具或追踪数据导出，不要靠记忆），找出所有环。
3. 试一次「战术分叉」的桌面推演：如果复制后删掉某领域，编译会挂在哪些地方？
4. 你们的公共领域逻辑现在是库还是服务？按第 8 章的复用阶梯，它该在哪一档？
5. 挑一个已拆分的服务，回看它当初的驱动因素：今天还成立吗？不成立的话有回退路径吗？
