## 本章地图

> 一句话：**先量清楚现在的耦合（架构量子），再决定要不要模块化（驱动因素）——
> 顺序反了，就会变成为了拆而拆。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 架构量子（Ch2） | 可独立部署的最小单位，含其功能内聚与耦合关系 | 量子越大 → 部署单元越大 → 可伸缩性与可部署性越受限 |
| 识别耦合（Ch2） | 静态耦合（结构连线）与动态耦合（运行期通信） | 两种耦合要分开看，合起来才决定「能不能独立部署」 |
| Sysops Squad：理解量子（Ch2） | 在案例上数出量子 | 先把现状画出来，再谈目标 |
| 模块化的驱动因素（Ch3） | 为什么值得模块化：可维护、可测试、可部署、可扩展、自治 | 模块化是**手段**，驱动因素才是目的 |
| Sysops Squad：创建业务案例（Ch3） | 把驱动因素翻成业务语言 | 架构改进要能写成业务案例，否则拿不到资源 |

## 核心精讲

> **教学示意，不参与构建。** 以下量子清单与打分表均为教学性重述。

### 2.1 什么是架构量子

```text
架构量子（architecture quantum）：
  可独立部署的**最小单位**——它不仅包含代码，还包含这个部署单元要正常工作
  所依赖的一切（尤其是它的数据/schema 与运行期通信伙伴）。

为什么需要这个概念：
  「服务数」会骗人——两个服务共用一个数据库、或者一个服务同步调用另一个才能完成业务，
  那么它们**在架构上其实是一个量子**：改一个就得一起测、一起发。

数法（教学示意）：
  quantum = { 部署单元 U, U 独占或强依赖的数据 D, U 运行期同步依赖的伙伴集合 S }
  若 A 与 B 共享同一个 D，或 A 同步强依赖 B 才能完成业务 → A、B 属于同一量子。
```

### 2.2 静态耦合 vs 动态耦合

```text
静态耦合（static coupling）：结构上「怎么连在一起」——
  依赖方向、共享库、共享 schema、共享契约、共享基础设施。
  → 决定了**改一处会牵连到谁**，以及能不能单独构建/部署。

动态耦合（dynamic coupling）：运行期「怎么说话」——
  同步调用（阻塞、级联失败、共同承担可用性）vs 异步消息（解耦但引入最终一致）。
  → 决定了**运行时故障怎么传播**，以及可用性如何组合。

合起来的读法：
  静态耦合低 + 动态耦合低 → 真正独立的量子（可独立部署、独立失败）
  静态耦合低 + 动态耦合高 → 部署自由，但可用性被绑在一起（同步调用链）
  静态耦合高 + 动态耦合低 → 能各自跑，但改代码/改 schema 要一起改（共享库/共享库表）
  静态耦合高 + 动态耦合高 → 分布式单体（最坏组合）
```

最后一行是本章最有杀伤力的判断：**把单体拆成多个服务却共享数据库、同步强依赖，
得到的不是微服务，而是「分布式单体」**——比单体更差的形态。

### 2.3 模块化的驱动因素（Ch3）

```text
模块化的目的不是「看起来清爽」，而是换取下面这些可度量的收益：
  可维护性（maintainability）  变更的影响范围可控，理解成本可局部化
  可测试性（testability）      模块边界可 mock/隔离，测试更快更稳
  可部署性（deployability）    可以单独发布，发布窗口与风险面变小
  可扩展性（scalability）      热点模块可独立扩容
  可用性 / 故障隔离            一个模块故障不拖垮全部（容错边界）
  团队自治（Conway 定律）      模块边界与团队边界对齐，减少跨团队协调

反过来的代价（必须一起列）：
  分布式带来的网络不可靠、最终一致、跨模块事务、运维与可观测性成本。

打分示意（教学示意，非实测）：
                单体内模块化    拆分为独立服务
  可维护性          ★★★★            ★★★
  可测试性          ★★★★            ★★
  可部署性          ★★              ★★★★
  可扩展性          ★★              ★★★★
  可用性/隔离       ★★              ★★★★
  事务与一致性      ★★★★            ★（需 Saga/最终一致）
  运维成本          ★★★★            ★
```

### 2.4 从驱动因素到业务案例（Ch3）

```text
架构师常犯的错误：拿技术语言去要资源。
正确做法是把驱动因素翻译成业务能感知的量：
  可部署性 → 发布频率、上线前置时间（lead time）、变更失败率
  可用性   → 停机时长、受影响的用户/订单数
  可扩展性 → 大促期间的扩容成本与响应时间
  团队自治 → 跨团队等待时间、需求交付周期

业务案例模板（教学示意）：
  「现在：X 变更需要 N 个团队协同，平均前置时间 T，故障影响面 S。
    目标：把领域 A 模块化，使 80% 的变更只需 1 个团队，前置时间降到 T/3。
    代价：新增分布式事务处理与可观测性投入，预计 M 人月。」
→ 这段落进 [01](01-权衡分析的语言-ADR与适应度函数.md) 的 ADR「上下文」段。
```

## 版本演进

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| 拆分风向 | 微服务仍是默认现代化路径，本书在教「怎么拆得对」 | **明显退潮**：业界普遍反思过度拆分，「模块化单体（modular monolith）」重新成为主流默认起点 |
| 拆分的依据 | 限界上下文（DDD）+ 驱动因素 | 同上，但新增一条强约束：**先问能不能在单体内把模块边界做实**，做不到再拆 |
| 静态耦合的治理 | 代码评审 + 经验 | 静态依赖分析进 CI（见 [01](01-权衡分析的语言-ADR与适应度函数.md) 的适应度函数） |
| 动态耦合的治理 | 靠架构图与文档 | 可观测性（调用链/依赖拓扑）可自动生成真实依赖图，文档不再是唯一依据 |
| 康威定律的用法 | 按团队结构拆 | 反向使用：先用团队结构约束**可接受的最大拆分数**，避免拆出无人维护的服务 |
| AI 编码助手 | 未涉及 | 生成代码的速度让「边界」更容易被侵蚀，因此静态耦合检查的重要性上升 |

## 近年研究与工业界开源实践（2015–2026）

- **「回到模块化单体」的回潮**：2023 年之后，业界对过度拆分的反思进入主流，
  常见建议是「先在单体内把模块边界、依赖方向、数据所有权做实，确有收益再拆」——
  这与本章「先量量子、再谈模块化」的顺序完全一致，只是结论更保守。
  相关讨论散见于公开演讲与工程博客（*本目录不引用未署名二手结论的具体数字*）。
- **静态耦合治理工具化**：以 Java 生态的架构约束测试为代表，
  实测 `TNG/ArchUnit` star = **3843**（2026-09 `gh api` 实测），
  可将本章 2.3 的「依赖方向」约束写成可执行的适应度函数。
- **真实依赖拓扑来自可观测性**：分布式追踪（OpenTelemetry 一脉）能自动产出真实调用图，
  使「动态耦合」从架构师的判断变成可导出的客观数据。
- **交付度量成为业务案例的标准语言**：前置时间、变更失败率等指标让本章 2.4 的
  「把驱动因素翻译成业务语言」有了通用口径（见 *Accelerate*）。
- **AI 编码助手的副作用**：代码产出成本下降，边界更容易被无意破坏；
  自动化静态检查因此从「加分项」变成「必需品」。
- 本目录所有代码为教学示意、不参与构建；star 均为 2026-09 `gh api` 实测。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「服务数 = 解耦程度」 | 共享库表或同步强依赖的两个服务是**同一个量子**；数服务没意义，数量子 |
| 2 | 「拆了就能独立部署」 | 独立部署的前提是静态耦合与动态耦合**同时**低 |
| 3 | 「静态耦合低就够了」 | 同步调用链把可用性绑在一起：动态耦合高时故障会级联 |
| 4 | 「模块化 = 拆服务」 | 模块化是**手段**；在单体内做模块化同样能拿到可维护性与可测试性 |
| 5 | 「按技术层分模块」 | Parnas 1972 的经典结论：按**易变性/业务变化**分，不按技术职责分 |
| 6 | 「架构改进不用说业务语言」 | 🔧 拿不到资源的架构改进等于没做；驱动因素必须翻译成可度量的业务量 |
| 7 | 🔧 「微服务是现代化的终点」 | 2023 年后反思成为主流：拆分的**驱动因素**不成立时，模块化单体更划算 |
| 8 | 🔧 「康威定律意味着按现团队结构拆」 | 反向用更稳：先看团队能长期维护几个服务，用它约束拆分上限 |
| 9 | 🔧 「架构图就是依赖真相」 | 应以可观测性导出的真实调用关系为准；文档常滞后 |
| 10 | 🔧 「AI 生成的代码不会破坏边界」 | 恰恰相反：生成越快、越需要自动化的边界检查（适应度函数） |

## 思考题

1. 画出你们系统的架构量子图：哪些「服务」其实属于同一个量子？共享了什么？
2. 分别列三条静态耦合与三条动态耦合，指出哪一条最阻碍独立部署。
3. 用本章 2.3 的驱动因素表给「拆 / 不拆」打分，并写出可被业务理解的三句话。
4. 用康威定律反推：以你们团队规模，长期能维护多少个可独立部署单元？现在超了吗？
5. 找一处「为了拆而拆」的模块：它当初的驱动因素是什么？今天还成立吗？
