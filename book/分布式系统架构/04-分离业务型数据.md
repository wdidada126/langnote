> 代码的耦合可以重构，数据的耦合一旦形成，迁移与回滚都极其昂贵。

## 本章地图

> 一句话：**数据分解的驱动因素与代码分解并不相同——
> 数据的真正约束是「谁会一起变、谁能容忍不一致、谁能承担迁移成本」；
> 而数据库类型一旦选错，换的代价远高于换服务框架。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 6.1 数据分解的驱动因素 | 为什么要拆数据：变更隔离、伸缩、故障隔离、团队自治、合规 | 驱动因素不成立就不要拆数据——共享库表也有它的价值 |
| 6.2 分解单体数据 | 怎么拆：先找数据归属，再断开关联，再处理跨库查询 | 外键与跨库 join 的消失是最大的行为变化 |
| 6.3 数据库类型的选择 | 关系/键值/文档/宽列/图/时序等多态持久化 | 选型的依据不是流行度，而是**访问模式 + 一致性 + 规模** |
| 6.4 Sysops Squad：多维数据库 | 案例：一个系统里出现多种数据库 | 多态持久化是常态，代价是运维与心智负担 |

## 核心精讲

> **教学示意，不参与构建。** 以下 SQL/DDL 与选型矩阵均为教学性重述，不参与任何构建或迁移。

### 4.1 数据分解的驱动因素

```text
与代码分解不同，数据分解的驱动因素更偏「状态」本身：
  变更隔离     某类数据的 schema 变更不应牵动其他领域
  独立伸缩     热点数据的读写压力不应拖累全库
  故障隔离     一个领域的数据故障不应让整个系统不可用
  团队自治     数据归属清晰，团队才能独立演进
  合规与属地   数据主权、留存期限、审计要求可能强制物理隔离
  性能特征差异  OLTP 与 OLAP、点查与全表扫描，混在一库里会互相拖累

反面的代价（必须同时列）：
  跨库 join 消失 → 需在应用层拼装或引入读模型；
  跨库事务消失 → 需 Saga/最终一致（第 9、12 章）；
  数据一致性从「数据库保证」变成「应用保证」；
  运维复杂度与成本上升（多套备份、监控、升级）。
```

### 4.2 分解单体数据：三步走

```text
步骤一：确定数据归属（谁拥有这张表）
  判据：哪个业务能力**写**它最多？它随哪个领域一起变？哪个团队为它负责？
  ⚠ 读得多不算拥有——读可以通过接口/读模型解决，写才是归属。

步骤二：断开关联（外键、跨库 join、共享序列）
  教学示意（不参与构建）：
    -- 分解前
    ALTER TABLE orders ADD CONSTRAINT fk_customer
      FOREIGN KEY (customer_id) REFERENCES customers(id);

    -- 分解后：外键消失，改为
    --   ① 应用层校验（调用客户服务的存在性接口），或
    --   ② 接受「引用完整性最终成立」（异步核对/对账任务）
    -- 并且跨库 join 改为：
    --   SELECT ... FROM orders WHERE customer_id IN (:ids);  -- 两次查询 + 应用层拼装

步骤三：处理跨库查询与报表
  常见做法（各有代价）：
    · 应用层拼装（简单，但 N+1 与内存风险）
    · 读模型/物化视图（快，但有同步延迟）
    · 数据领域模式（见第 10 章）
    · 分析侧汇总（见第 14 章数据网格）
```

### 4.3 数据库类型的选择：按访问模式选，不按流行度选

```text
选型维度（教学示意）：
  ① 访问模式    点查 / 范围扫 / 聚合 / 图遍历 / 全文 / 向量相似
  ② 一致性要求  强一致（跨行事务）还是可接受最终一致
  ③ 数据形态    强 schema 还是半结构；是否需要 JOIN
  ④ 规模        单机能扛还是要分片；写入吞吐与数据量的量级
  ⑤ 运维能力    团队能否运维第二种数据库（这是最常被忽略的一条）

常见映射（教学示意，非实测）：
  关系型       强 schema、事务、复杂查询、中小规模   → 默认选择
  键值         简单点查、超高吞吐、缓存             → 会话、计数器、缓存
  文档         半结构、读多写少、单实体聚合         → 内容、配置、用户档案
  宽列         海量写、按主键/分区查、可调一致性     → 时序、消息、宽表
  图           多跳关系查询                         → 关系网络、权限、推荐
  时序/列存    时间序列与聚合分析                   → 监控、指标
  向量         相似检索                             → 语义检索、RAG 场景
  搜索引擎     全文与相关性                         → 站内检索
```

### 4.4 多维数据库（polyglot persistence）的真实代价

```text
「一个系统多种数据库」听起来美好，代价清单必须提前列：
  · 每多一种库 = 多一套备份/恢复/监控/升级/容量规划；
  · 跨库的数据一致性没有数据库兜底，必须靠应用层或平台层；
  · 团队技能被稀释：能调优 A 库的人不一定能调优 B 库；
  · 故障排查路径变长：一次慢查询可能横跨三种存储。

本书务实立场（按标题与结构推断，*原文措辞未能核实*）：
  多态持久化是**结果**不是**目标**——只有当驱动因素明确成立时才引入第二种数据库。
```

## 版本演进

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| 数据库类型版图 | 关系 / KV / 文档 / 宽列 / 图 / 时序 | 新增**向量数据库**成为常见选型（语义检索与 RAG 场景驱动） |
| 分布式 SQL | 已成熟但仍在教育市场 | NewSQL/分布式 SQL 成为「既要有关系语义又要横向扩展」的默认答案之一 |
| HTAP | 处于宣传期 | 混合负载（事务 + 分析）有了更多成熟选项，但**是否真省一层**仍取决于负载特征 |
| 托管化 | 已普及 | 托管数据库成为默认；「能不能运维第二种数据库」的问题变成「付不付得起托管费」 |
| 数据分解的依据 | 限界上下文 + 驱动因素 | 同上，并新增**数据主权/合规**这一硬约束（属地化与留存要求） |
| 迁移工具 | 主要靠自研 | CDC（变更数据捕获）成为标准能力，使双写/回切/灰度迁移更容易 |

## 近年研究与工业界开源实践（2015–2026）

- **向量数据库进入常规选型**：语义检索与检索增强生成（RAG）场景推动向量检索成为一类独立存储。
  实测 star（2026-09 `gh api`）：`milvus-io/milvus` = **46255**、`qdrant/qdrant` = **34835**。
  它们把本章 4.3 的选型表从「六种」扩到「七种以上」。
- **宽列存储仍是海量写的主力**：`apache/cassandra` star = **10102**（2026-09 `gh api` 实测），
  可调一致性档位使其成为「接受最终一致」场景的经典选择。
- **CDC 成为分解与迁移的标准工具**：变更数据捕获让「双写 + 校验 + 切换」成为可控流程，
  显著降低了本章 4.2 的迁移风险。
- **托管化改变了运维约束**：本章 4.3 的第⑤条（团队能否运维第二种数据库）
  在今天更多转化为成本与供应商锁定问题，而不是纯技术能力问题。
- **合规成为硬约束**：数据主权、属地化与留存期限常常**直接决定**能不能合库，
  优先级高于技术选型。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「数据跟着服务一起拆就行」 | 数据归属要单独判断：**写**得多的一方拥有它，读得多不算 |
| 2 | 「外键可以留在应用层」 | 应用层只能在**写入时校验**，无法阻止事后删除；需异步对账兜底 |
| 3 | 「跨库 join 用应用层拼装就好」 | 要注意 N+1、内存与分页语义；高频场景应改用读模型或数据领域模式 |
| 4 | 「多一种数据库很酷」 | 每多一种库 = 多一套全生命周期运维；驱动因素不成立就不该加 |
| 5 | 「选最流行的那个」 | 选型的依据是访问模式 + 一致性 + 规模 + **运维能力** |
| 6 | 「拆完数据一致性由数据库保证」 | 数据库的保证止步于单库；跨库一致性改由应用/平台承担（第 9、12 章） |
| 7 | 🔧 「选型表到此为止」 | 2023 年之后**向量数据库**成为常见第七类；选型表要更新 |
| 8 | 🔧 「分布式 SQL 能解决一切」 | 它解决「关系语义 + 横向扩展」，不解决跨领域的数据归属与团队边界 |
| 9 | 🔧 「合规可以上线后再补」 | 数据主权与留存要求是**物理约束**，常常决定架构而非被架构决定 |
| 10 | 🔧 「迁移不需要回退路径」 | 数据迁移必须有可回切设计（双写 + 对账 + 灰度），否则失败即事故 |

## 思考题

1. 列出你们的核心表，逐张写出「拥有它的业务能力」——有没有哪张表找不到明确的拥有者？
2. 找一处跨库 join，给出三种替代方案的代价（应用层拼装 / 读模型 / 数据领域）。
3. 你们的第二种数据库是为什么引入的？驱动因素今天还成立吗？
4. 如果明天下发一条数据属地化要求，哪些数据必须物理隔离？你的架构能支持吗？
5. 设计一次数据迁移的双写与回切方案：对账指标是什么？什么条件下切换？
