# 第 10 章 分布式数据访问

> 覆盖原书第 10 章（服务间通信模式 / 列 schema 复制模式 / 复制缓存模式 /
> 数据领域模式 / Sysops Squad：工单分配的数据访问）。
> 上一章讲的是「数据归谁」，本章讲的是**「别人要用你的数据怎么办」**——
> 这是服务化之后每天都会遇到的现实问题。

## 本章地图

> 一句话：**服务拆开之后，「拿别人的数据」变成了架构问题：
> 你可以每次去问（通信）、复制几列到本地（列 schema 复制）、放缓存（复制缓存）、
> 或者把数据按领域归拢成一个可消费的数据领域。四种办法都在换「延迟 vs 陈旧 vs 耦合」。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 10.1 服务间通信模式 | 同步请求/响应 vs 异步消息/事件 | 同步拿最新数据但耦合可用性；异步解耦但引入陈旧与一致性窗口 |
| 10.2 列 schema 复制模式 | 把对方表的部分列复制到本地库 | 读本地、快；代价是副本陈旧 + schema 漂移 |
| 10.3 复制缓存模式 | 用共享/分布式缓存承载复制数据 | 极快；代价是缓存一致性、容量与雪崩风险 |
| 10.4 数据领域模式 | 按领域提供数据（含读模型/视图） | 语义清晰、可被多消费方共享；代价是要维护一个额外的数据产品 |
| 10.5 Sysops Squad 案例 | 工单分配的数据访问 | 同一系统里不同场景可以选不同模式 |

## 核心精讲

> **教学示意，不参与构建。** 以下模式描述与伪代码均为教学性重述。

### 8.1 服务间通信模式：同步 vs 异步

```text
同步（请求/响应，如 HTTP/gRPC）
  + 拿到的是**当下**的值；语义直观；错误处理在调用栈里
  - 调用方可用性 × 被调方可用性（第 2 章动态耦合）
  - 尾部延迟叠加：一次请求串 N 次调用，p99 会被放大
  - 级联故障：需要超时、熔断、舱壁、降级

异步（消息/事件）
  + 解耦可用性：被调方短暂不可用不影响调用方
  + 天然支持一对多广播与重放
  - 数据是**过去的**：一致性窗口客观存在
  - 需要幂等消费、顺序语义、重试与死信处理

示意（教学示意，不参与构建）：
  // 同步：读当下
  customer = customerService.getById(id);        // 失败 → 本次请求失败

  // 异步：读本地副本，由事件维护
  customer = localCustomerReadModel.get(id);     // 可能为 N 毫秒前的状态
```

### 8.2 列 schema 复制模式

```text
做法：把另一个服务拥有的表中的**少数几列**复制到自己的库里（不是整表）。
  例：工单服务只复制客户表的 (id, name, level) 三列，不复制地址、联系方式等。

为什么只复制几列：
  · 复制越少，schema 漂移与同步压力越小；
  · 复制的是「读所需」，不是「整张表」——这是它与「共享数据库」的分界线。

优点：本地 join、本地查询、无网络调用、性能好。
代价：
  · 副本陈旧（有界陈旧，要明确能容忍多久）；
  · 源端 schema 变更要能传播（需要契约与兼容策略，见第 13 章）；
  · 复制链路本身要可观测、可对账。
⚠ 只复制**读**，绝不能把复制来的列当 writable——那样就滑向共同所有权（第 9 章）。
```

### 8.3 复制缓存模式

```text
做法：把高频读取的数据放进共享/分布式缓存（内存态），各服务从缓存读。

优点：延迟极低；减轻源库压力；对读多写少的数据性价比最高。
代价：
  · 一致性：缓存与源库之间必然有窗口（失效策略决定窗口大小）；
  · 失效风暴与缓存雪崩：需要 TTL 抖动、熔断、空值占位；
  · 容量与成本：内存比磁盘贵，且需要容量规划与逐出策略；
  · 故障域：缓存集群本身成为关键依赖（缓存挂了源库能否扛住？）。

三种常见失效策略（教学示意）：
  write-through  写时同步更新缓存（一致性好，写延迟上升）
  write-behind   写时异步更新（写快，但崩溃窗口可能丢更新）
  cache-aside    读时回填、写时失效（最常用；要处理并发回填与穿透）
```

### 8.4 数据领域模式

```text
做法：把某个业务领域的数据以**可消费的形态**对外提供（读模型/视图/数据产品），
      而不是让消费方各自去复制或拼装。

与「列 schema 复制」的区别：
  复制模式 = 消费方各自复制自己需要的列（分散、可能不一致）
  数据领域 = 由数据拥有方提供一个**语义明确**的数据视图（集中、可治理）

优点：
  · 语义单一来源：口径一致（同一个「活跃用户」定义只有一个地方实现）；
  · 可被多个消费方共享，避免 N 份复制漂移；
  · 便于加访问控制与审计。
代价：
  · 需要有人维护这个数据产品（拥有者、SLA、演进）；
  · 又一层数据延迟（物化/刷新的时间）；
  · 若设计不当，会退化为「一个新的共享数据库」（反模式）。
```

### 8.5 四模式对照（教学示意）

```text
                延迟   陈旧程度   对源可用性依赖   实现成本   适用
同步通信         中      无          高（强）        低        强一致必需、低频调用
列 schema 复制   低      中          低              中        高频读、只读少量列
复制缓存         最低    中～高      中              中        读多写少、可容忍陈旧
数据领域         低      中          低              高        多方共享同一口径的数据
```

### 8.6 选择的顺序（教学示意）

```text
① 先问：能不能接受陈旧？
   不能 → 同步通信（并接受可用性耦合）
   能   → 继续
② 再问：有几个消费方需要同一口径？
   只有自己 → 列 schema 复制（按需复制少量列）
   多个方   → 数据领域（统一口径，避免 N 份漂移）
③ 再问：读压力是否集中在少数热点？
   是 → 叠加复制缓存（并设计好失效与兜底）
④ 无论选哪个：都要有**对账**与「陈旧程度」的可观测指标。
```

## 版本演进

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| 事件/消息平台 | Kafka 已是事实标准 | Kafka / Pulsar 双雄并立；托管化使运维门槛大幅下降 |
| 变更传播 | 主要靠应用发事件 | **CDC（变更数据捕获）** 成为复制类模式的标准实现方式：直接从库日志取变更 |
| 读模型 | 手工维护 | 物化视图、流式处理与增量计算使读模型成为平台能力 |
| 数据领域的组织形态 | 作为模式出现 | 与第 14 章的**数据网格**合流：数据即产品、领域拥有、平台提供底座 |
| API 层的聚合 | BFF / API 网关 | BFF 与聚合层普遍化；同时 GraphQL 一类技术在部分场景替代多次同步调用 |
| AI 编码助手 | 未涉及 | 生成「直接查别人库」的代码很容易，因此复制/领域模式的**边界约束**更需要被自动化检查 |

## 近年研究与工业界开源实践（2015–2026）

- **事件平台成为数据访问的基础设施**：实测 star（2026-09 `gh api`）：
  `apache/kafka` = **33848**、`apache/pulsar` = **15338**。
  二者支撑了本章 8.2/8.4 的复制与事件驱动读模型。
- **CDC 让「复制模式」变简单**：直接从数据库日志捕获变更，
  免去「双写」的原子性难题，也使复制链路可回放、可对账。
- **读模型平台化**：流式处理与增量物化让「数据领域」从手工视图变成可声明的产物，
  消费方拿到的不再是裸表，而是有语义的数据产品。
- **缓存仍是第一手段但需治理**：复制缓存的收益极高，
  代价集中在失效策略、雪崩防护与容量规划；多数事故源于「没有失效兜底」。
- **AI 编码助手的边界风险**：最容易被生成出来的错误代码就是「直接连接别人的库」；
  因此「谁可写哪张表」必须有可执行的检查（见 [01](01-权衡分析的语言-ADR与适应度函数.md)）。
- 本目录所有代码为教学示意、不参与构建；star 均为 2026-09 `gh api` 实测。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「同步调用最省事，全用它」 | 同步会把**可用性相乘**、把 p99 相加；高频路径要考虑异步或复制 |
| 2 | 「复制来的列也可以写」 | 复制只能读；一旦写入就变成共同所有权（第 9 章），代价高一个量级 |
| 3 | 「缓存能解决一切读压力」 | 缓存带来陈旧、雪崩与容量问题；必须有失效兜底与源库可承载的验证 |
| 4 | 「复制整张表更方便」 | 只复制所需列——复制面越小，schema 漂移与同步成本越低 |
| 5 | 「数据领域 = 共享数据库」 | 数据领域是**由拥有方提供的语义视图**；共享库表是反模式，两者形似而神不同 |
| 6 | 「异步就没有一致性问题」 | 异步只是把一致性问题**延后**：需要幂等、顺序、对账 |
| 7 | 🔧 「复制链路不需要对账」 | 任何复制/缓存都要有对账与陈旧度指标，否则偏差会静默累积 |
| 8 | 🔧 「陈旧程度不用量化」 | 应写成有界陈旧指标（多久、多少条、影响哪个功能） |
| 9 | 🔧 「CDC 只是运维工具」 | 它是本章复制类模式的实现底座，应纳入架构决策而非事后补丁 |
| 10 | 🔧 「AI 生成的代码会遵守数据边界」 | 不会；边界必须显式声明并可被自动检查 |

## 思考题

1. 挑一个高频的跨服务读，按 8.6 的顺序走一遍：你该选哪种模式？为什么？
2. 你们的复制链路有没有对账？多久跑一次？不一致时能自动修复吗？
3. 缓存失效策略是哪一种？如果缓存集群整体不可用，源库能扛住吗（做过演练吗）？
4. 找一个「复制了整张表」的地方：能不能只复制几列？schema 漂移时怎么发现？
5. 「数据领域」在你们系统里存在吗？如果有，它的拥有者与 SLA 是谁？
