# 第 7 章 服务粒度

> 覆盖原书第 7 章（粒度分解因素 / 粒度集成因素 / 找到正确的平衡 /
> Sysops Squad：工单分配粒度 / Sysops Squad：客户注册粒度）。
> 本章是全书最「可操作」的一章：它把「拆多细」这个玄学问题，
> 变成**两栏因素的对拉**——一栏催你拆小，一栏催你别拆。

## 本章地图

> 一句话：**粒度没有正确答案，只有两股力量的平衡点：
> 分解因素（disintegrators）催你把服务拆小，集成因素（integrators）把你拉回大块**。

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 7.1 粒度分解因素 | 促使拆小的因素 | 变化频率不同、伸缩需求不同、故障隔离、安全边界、自治团队 |
| 7.2 粒度集成因素 | 促使别拆的因素 | 跨服务事务、数据依赖、工作流与编排、共享代码与库 |
| 7.3 找到正确的平衡 | 两栏对照后做决策 | 平衡点随业务演进而变，粒度需要**周期性复核** |
| 7.4/7.5 Sysops Squad 案例 | 工单分配粒度、客户注册粒度 | 两个案例演示「同一个系统里可以有不同粒度」 |

## 核心精讲

> **教学示意，不参与构建。** 以下因素表与打分法为教学性重述。

### 5.1 分解因素（为什么想拆小）

```text
① 变更频率不同（code volatility）
   稳定部分与高频变化部分混在一起 → 每次发布都要全量回归。
   拆开后，稳定部分几乎不发，变化部分可快速迭代。

② 伸缩需求不同（scalability / throughput）
   一个系统里只有少数功能是热点。整体扩容 = 为冷代码买单。
   拆开后，热点可独立扩容。

③ 故障隔离（fault tolerance）
   关键路径与非关键路径同一进程 → 非关键功能 OOM 会拖垮关键功能。
   拆开后，故障域被限制。

④ 安全与权限边界
   不同数据有不同的访问敏感度与合规要求；独立部署便于施加不同的访问控制。

⑤ 团队自治（Conway 定律）
   多个团队改同一代码库 → 协调成本与合并冲突。
   边界与团队边界对齐后，团队可独立交付。

⑥ 可扩展性 / 可替换性（extensibility）
   希望某块能力能被独立替换或新增实现。
```

### 5.2 集成因素（为什么别再拆了）

```text
① 跨服务事务（database transactions）
   一个业务操作要跨多个服务改数据 → 失去单库事务，
   必须上 Saga/补偿/最终一致（第 12 章）。
   这是最强的「别拆」信号。

② 数据依赖（data relationship / shared data）
   两个服务强依赖同一张表 → 它们其实属于同一个架构量子（第 2 章）。
   强行拆开只会得到分布式单体。

③ 工作流与编排（workflow / choreography）
   一个业务流程横跨多步 → 要么引入编排器，要么改用事件协作（第 11 章）。
   每一步拆分都会增加流程的可观测与排错成本。

④ 共享代码与库（shared code / libraries）
   领域逻辑被多处共用 → 做成库还是服务，是独立决策（第 8 章）。

⑤ 契约与版本（contract coupling）
   每次拆分都会新增对外契约（第 13 章），契约越多，演进越受约束。

⑥ 运维与认知负担
   每多一个可部署单元，就多一套监控、告警、发布、值班认知。
```

### 5.3 两栏对照法（教学示意）

```text
做法：把候选边界的两栏因素列出来，**不求和、不加权平均**——
      因为两类因素不可比（一个是收益，一个是代价）。

示例（教学示意，非实测）：
  候选：把「工单分配」从工单服务里拆出来
  分解因素                      集成因素
    变更频率不同（★★★）          跨服务事务（★★：分配结果要写回工单）
    伸缩需求不同（★★★★）         数据依赖（★★★：共用工单表）
    故障隔离（★★★）              工作流（★★★：分配是流程的一环）
    团队自治（★★）               契约（★★：新增一个分配接口）
  判定：伸缩与故障隔离的理由强，但数据依赖是硬伤
      → 正确顺序是「先拆数据归属（第 6 章），再拆服务」，
        而不是先拆服务再想数据怎么办。
```

### 5.4 一个系统里可以有不同粒度

```text
本书两个案例（工单分配粒度、客户注册粒度）传达的要点：
  粒度不是全局常量，而是**每个边界各自决策**的结果。
  同一个系统里，有的领域适合粗（强事务、数据耦合紧），
  有的领域适合细（高频变化、热点、可最终一致）。
→ 追求「统一粒度」是错的；追求「每个边界都有理由」才是对的。
```

### 5.5 粒度的复核机制

```text
粒度一旦确定，会随业务漂移。建议（教学示意）：
  · 每次重大业务变更时，回看相关边界的两栏因素是否仍成立；
  · 用可观测数据校验分解理由：
      「因伸缩而拆」→ 看扩容成本是否真降了；
      「因变更频率而拆」→ 看发布频率与回归范围是否真改善了；
  · 把结论写进 ADR（supersede 旧的那篇），见 [01](01-权衡分析的语言-ADR与适应度函数.md)。
```

## 版本演进

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| 拆细的风向 | 微服务是现代化默认路径 | **收敛**：过度拆分的反思成为主流，粒度整体有变粗的趋势 |
| 拆分的默认起点 | 问「能拆多细」 | 问「能不能不拆」——先在单体内做实模块边界 |
| 「先拆服务、后拆数据」的代价 | 已被本书指出 | 2023 年之后有公开工程案例因过度拆分而**回退**到更粗粒度，成为反思的标志性事件 |
| 团队的约束 |  Conway 定律用于对齐 | 更常被反向使用：团队规模决定**可长期维护的服务数上限** |
| 度量 | 主要靠经验与代码量 | 交付度量（前置时间、变更失败率）与可观测数据成为复核依据 |
| AI 编码助手 | 未涉及 | 新增服务与契约的边际成本下降 → 更需要人为设定「服务数上限」这类约束 |

## 近年研究与工业界开源实践（2015–2026）

- **粒度的整体收敛**：2023 年之后，过度拆分的反思进入主流，
  「模块化单体」重新成为默认起点；本章的两栏对照法恰好可用于**论证回退**——
  当集成因素（尤其是跨服务事务与数据依赖）压过分解因素时，合并是正确的。
- **公开案例的示范效应**：有大型服务把分布式组件合并回更粗粒度并公开说明成本下降，
  使「回退」从忌讳变成可讨论的选项。（*本目录不引用未经核实的数字*。）
- **交付度量成为复核依据**：前置时间、变更失败率、发布频率让本章 5.5 的复核从主观变客观。
- **自动化检查支撑粗粒度**：模块边界可以用静态依赖检查保证（见
  [01](01-权衡分析的语言-ADR与适应度函数.md)），因此**单体内也能拿到很多拆分收益**——
  这削弱了「必须拆成服务」的理由。
- **AI 编码助手带来的新约束**：新增服务与契约的成本下降，
  团队需要显式设定「服务数上限」「契约数量上限」这类适应度函数，防止无意识膨胀。
- 本目录所有代码为教学示意、不参与构建；star 均为 2026-09 `gh api` 实测。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「服务越小越好」 | 小服务的代价在集成侧：事务、数据、工作流、契约都要付钱 |
| 2 | 「粒度应该全系统统一」 | 粒度是**每个边界各自决策**的结果（本书两个案例的要点） |
| 3 | 「按技术层定粒度」 | 按业务变化单元与数据归属定 |
| 4 | 「先拆服务，数据以后再说」 | 数据依赖是最强的**反向**信号；先拆数据归属再拆服务 |
| 5 | 「拆完就不用管了」 | 粒度会随业务漂移，需要周期性复核并更新 ADR |
| 6 | 「两栏因素可以加权求和」 | 收益与代价不可通约；应逐条说明理由，而非算总分 |
| 7 | 🔧 「微服务是唯一现代化路径」 | 2023 年后反思成为主流；停在模块化单体也是合格答案 |
| 8 | 🔧 「回退等于承认失败」 | 有公开案例把过度拆分回退并获益；回退是正常的架构演进 |
| 9 | 🔧 「团队结构决定一切」 | 反向用更稳：用团队长期维护能力**约束**服务数量上限 |
| 10 | 🔧 「AI 生成服务很便宜，多拆无妨」 | 契约与认知负担才是长期成本；需要显式的数量类适应度函数 |

## 思考题

1. 挑一个你们的服务，列出它的两栏因素：哪一条分解理由最强？哪一条集成代价最痛？
2. 有没有哪个服务是「拆了之后又发现数据赖在一起」的？按本书的顺序应该先做什么？
3. 用可观测数据复核一次拆分理由：说好的伸缩收益/故障隔离，真的实现了吗？
4. 以你们团队规模，长期能维护多少个可部署单元？现在超了吗？超出的话怎么收？
5. 写一个「服务数量上限」类的适应度函数：触发条件与处置方式是什么？
