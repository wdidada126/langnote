## 本章地图

> 一句话：**数据所有权是服务边界的实质；所有权一旦分散，
> 单库事务就消失了，你必须在「分布式事务」与「最终一致性」之间做选择。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 9.1 分配数据所有权 | 按业务能力/变更责任分配归属 | 归属不清的服务拆分一定失败 |
| 9.2 单一所有权 | 一份数据只由一个服务写 | 最干净：无冲突、无协调 |
| 9.3 公共所有权 | 一份数据被多方**读**、一方写（或只读副本） | 读可以给，写不能给 |
| 9.4 共同所有权 | 多方都能写同一份数据 | 最贵：需要协调或冲突解决 |
| 9.5 所有权总结 | 三档对照 | 能用单一/公共就别用共同 |
| 9.6 分布式事务 | 跨服务原子性的选项与代价 | 2PC 阻塞、Saga 补偿——都是代价，不是免费午餐 |
| 9.7 最终一致性模式 | 放弃原子性后的收敛手段 | 对账、重试、事件同步、读修复 |
| 9.8 Sysops Squad 案例 | 工单处理的数据所有权 | 同一系统里可以同时存在三档所有权 |

## 核心精讲

> **教学示意，不参与构建。** 以下场景与伪代码均为教学性重述。

### 7.1 三档所有权（教学归纳）

```text
① 单一所有权（single ownership）
   一份数据只有一个服务能写；其他服务需要就调接口。
   + 无写冲突、无协调成本、schema 可独立演进
   - 所有写都要走网络（延迟 + 可用性依赖）

② 公共所有权（common ownership）
   一份数据被多个服务**读**（可能通过副本/缓存/只读视图），写仍归一方。
   + 读性能与可用性改善（本地副本）
   - 副本有延迟 → 读到陈旧数据；需要明确「能容忍多陈旧」（第 10 章）
   ⚠ 若读方也开始写，就滑向第③档

③ 共同所有权（joint/shared ownership）
   多个服务都能写同一份数据。
   + 有时是业务现实（多方都会改订单状态）
   - 最贵：要么引入分布式事务（9.6），要么接受冲突与最终一致（9.7）
   ⚠ 这是最强的「架构量子没切开」信号（第 2 章）
```

判断口诀（教学示意）：**写权归一，读权可放，共享写权是最后手段。**

### 7.2 分布式事务：两条路都不便宜

```text
路一：分布式事务（追求原子性）
  2PC（两阶段提交）
    流程：投票阶段（各参与者写 WAL 并投票）→ 决策阶段（提交/回滚）。
    + 跨服务原子性由协议保证
    - 阻塞：协调者或参与者在提交期间失败会阻塞，直到节点恢复；
    - 写 N-of-N：对尾部延迟敏感；
    - CAP 视角：2PC 是 CA，**不分区容错**——协调者挂了无法安全提升新协调者。
  Saga（见第 12 章）
    把长事务拆成一串本地事务，失败时**反向补偿**。
    + 不阻塞、每步都是本地事务
    - 没有隔离性：中间状态对其他事务可见（需要语义对策：预留、加锁、语义锁等）
    - 补偿必须**幂等**且可能失败（需要重试与人工兜底）

路二：最终一致性（放弃原子性）
  用事件/消息在各服务间传播变更，接受短暂不一致。
  + 吞吐与可用性最好
  - 一致性语义变成应用责任：需要幂等、去重、对账与补偿。
```

### 7.3 最终一致性模式（9.7）

```text
① 事件驱动同步
   写方在本地事务里提交数据，并发出事件（配合事务性发件箱保证不丢）。
   读方消费事件更新自己的副本/读模型。
   ⚠ 关键：事件与数据必须在**同一个本地事务**里被记录，否则会丢事件。

② 重试与幂等
   消费端可能重复收到事件 → 所有处理必须幂等（幂等键、去重表、版本号）。

③ 对账与基线修复（reconciliation）
   异步比对各副本/各服务的状态，发现不一致就修复。
   这是最终一致的**最后保险**：任何模式下都值得有一条对账链路。

④ 读修复（read repair）
   读时发现副本陈旧，顺手修正（与 dsforfun 第 5 章 Dynamo 的做法同源）。

⑤ 有界陈旧（bounded staleness）
   把「能容忍多旧」写成可度量的指标，而不是含糊地说「最终一致」。
```

### 7.4 示意：一次跨服务下单（教学示意）

```text
服务：订单（拥有订单表）、库存（拥有库存表）、支付（拥有支付记录）

方案 A（2PC）
  begin → 订单预写 → 库存预扣 → 支付预扣 → 全部 OK → commit
  ✗ 任一参与者慢/挂 → 整条链路阻塞，锁持有时间 = 最慢参与者

方案 B（Saga，编排式）
  1 创建订单（本地事务）→ 2 扣库存（本地事务）→ 3 扣支付（本地事务）
  若 3 失败 → 补偿：回滚库存、取消订单
  ✗ 步骤 2 与 3 之间，其他服务能看到「已扣库存但没支付」的中间状态

方案 C（事件 + 最终一致）
  1 创建订单并发出 OrderCreated（本地事务）
  2 库存服务消费 → 扣库存 → 发 StockReserved
  3 支付服务消费 → 扣款 → 发 PaymentDone
  4 订单服务消费 → 置为已确认；任一步失败 → 发补偿事件/超时取消
  ✗ 一致性窗口存在；需要幂等 + 超时 + 对账
```

### 7.5 与所有权档位的对应

```text
若能把数据归属设计成 单一/公共所有权 → 多数场景根本不需要分布式事务；
只有落在 共同所有权 上的那部分，才必须在 9.6 与 9.7 之间二选一。
→ 这就是为什么本章把「所有权」放在「事务」之前讲：
   **先削掉对分布式事务的需求，再谈用哪种分布式事务。**
```

## 版本演进

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| 分布式事务的默认选择 | 本书以权衡框架呈现（Saga 为主） | 编排式 Saga 因工作流引擎成熟而更可行（见 [09](09-管理分布式工作流.md)、[10](10-事务Saga.md)） |
| 事件与数据的一致性 | 需要读者自行设计 | **事务性发件箱（transactional outbox）+ CDC** 成为标准解法 |
| 一致性档位 | 「最终一致」居多 | 「有界陈旧」与可调一致性档位更常见，把「多旧」变成可度量参数 |
| 对账 | 作为兜底建议 | 被视为**必备**能力（异步比对 + 自动/人工修复），并进入运维看板 |
| 数据所有权的表达 | 架构图与文档 | 用数据目录/契约登记表达，并可被自动化检查（谁有权写哪张表） |
| AI 编码助手 | 未涉及 | 生成跨服务调用更容易，但**所有权边界**必须显式声明，否则生成代码会直接跨库写 |

## 近年研究与工业界开源实践（2015–2026）

- **事务性发件箱 + CDC 成为事实标准**：把「业务数据」与「待发事件」写进同一本地事务，
  再用变更数据捕获把事件可靠地投递出去——这解决了本章 7.3① 的关键难点（事件不能丢）。
- **工作流引擎让编排式 Saga 变得便宜**：实测 star（2026-09 `gh api`）：
  `temporalio/temporal` = **23303**、`netflix/conductor` = **12751**、
  `camunda/camunda` = **4296**（另有历史仓库 `camunda/camunda-bpm-platform` = **4269**；
  ⚠ `camunda/camunda7` 经 `gh api` 实测返回 **404**，本目录不采用该仓库名）。
- **消息与事件平台是最终一致的底座**：`apache/kafka` star = **33848**、
  `apache/pulsar` star = **15338**（2026-09 `gh api` 实测）。
- **对账进入常态化运维**：跨服务一致性不再只靠协议保证，
  而靠「异步比对 + 基线修复」兜底，并把不一致量作为可观测指标。
- **所有权的可执行化**：数据目录与访问控制策略让「谁有权写哪张表」可被检查，
  把本章 7.1 的分配结果变成可执行的约束。
- 本目录所有代码为教学示意、不参与构建；star 均为 2026-09 `gh api` 实测，查不到写「star 未核验」。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「服务拆开了，数据所有权自然清楚」 | 所有权必须**显式分配**；归属不清的拆分会退化为分布式单体 |
| 2 | 「读得多就拥有这份数据」 | **写**才是归属；读可以通过接口/副本解决 |
| 3 | 「公共所有权 = 双方都能写」 | 公共是「多方读、一方写」；双方都写是共同所有权，代价高一个量级 |
| 4 | 「2PC 能保证跨服务原子性，用就是了」 | 2PC 阻塞、N-of-N、且**不分区容错**；它是 CA 不是 CP |
| 5 | 「Saga 就是分布式事务的免费替代」 | Saga 没有隔离性：中间状态可见，需要语义对策；补偿还需幂等 |
| 6 | 「最终一致 = 不用管一致性」 | 必须配幂等、去重、超时与**对账**；对账是所有方案的最后保险 |
| 7 | 🔧 「事件发出去就行了」 | 事件必须与业务数据同属一个本地事务（事务性发件箱），否则会静默丢事件 |
| 8 | 🔧 「一致性窗口不需要量化」 | 应写成有界陈旧指标（PBS 一脉），否则「最终」没有意义 |
| 9 | 🔧 「协调者单点无所谓」 | 协调者是新的故障域；把协调者状态放进高可用存储/共识组是现代做法 |
| 10 | 🔧 「AI 生成代码会自己尊重所有权」 | 不会。所有权必须显式声明并可被检查，否则生成的代码会直接跨库写 |

## 思考题

1. 列出你们的核心数据，逐项标注所有权档位；有几个落在「共同所有权」上？能降级吗？
2. 挑一个跨服务写操作，分别用 2PC、Saga、事件+最终一致三种方案设计，列出各自的失败模式。
3. 你们的事件是怎么发出去的？与业务数据在同一事务里吗？不是的话，丢事件怎么发现？
4. 「一致性窗口」在你们系统里是多少？怎么度量？谁在看这个指标？
5. 挑一条对账链路：它多久跑一次？发现不一致后是自动修复还是人工？升级路径是什么？
