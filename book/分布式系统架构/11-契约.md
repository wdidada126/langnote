# 第 13 章 契约（严格 / 宽松、邮戳耦合）

> 覆盖原书第 13 章（严格契约与宽松契约 / 微服务中的契约 / 邮戳耦合 /
> Sysops Squad：管理工单契约）。
> 本章回答的是「服务之间究竟拿什么说话」：**契约的松紧决定了演进的自由度**——
> 越严格越安全但越难改，越宽松越好改但要自己承担兼容性风险。

## 本章地图

> 一句话：**契约是服务之间唯一的正式约定；严格契约把类型与结构钉死（安全但僵硬），
> 宽松契约只约定「你需要的那部分」（灵活但需自律），而邮戳耦合是最该被抓出来的隐性契约。**

## 核心精讲

> **教学示意，不参与构建。** 以下 schema 片段与对照表均为教学性重述。

### 11.1 严格契约 vs 宽松契约

```text
严格契约（strict contract）
  服务端严格定义并校验字段名、类型、必填性、取值范围；
  收到不符合约定的请求直接拒绝（400/422）。
  + 安全：错误在边界被拦住，不会渗进业务逻辑
  + 可演进性强的一半： breaking change 更容易被检测到
  - 僵硬：加一个可选字段也要走一遍发布流程
  - 客户端升级压力：服务端加严校验，老客户端可能立刻失败

宽松契约（loose contract）
  只约定「消费方真正需要的字段」，忽略未知字段；
  容忍对方多给、少给、多版本共存（如 tolerant reader 风格）。
  + 灵活：双方可以不同步发布
  + 演进友好：加字段对老消费方无感
  - 风险自担：字段被悄悄移除/改名时，消费方只能自己发现
  - 需要契约测试兜底（不能只靠「应该没问题」）

示意（教学示意，不参与构建）：
  // 严格：类型与必填都声明，未知字段拒绝
  schema Order { id: UUID, amount: Decimal, currency: Enum, status: Enum }  // 未知字段 → 报错
  // 宽松：只读取需要的字段，忽略其他
  order.id      = payload["id"]      // 只取所需
  order.amount  = payload["amount"]  // 其余字段忽略
```

选型判据（教学示意）：

```text
组织内、同步发布可控、强类型栈   → 偏严格（把错误挡在边界）
跨组织、版本长期共存、发布不同步 → 偏宽松 + 契约测试
```

### 11.2 微服务中的契约：为什么它比库 API 贵得多

```text
库 API 的调用方在同一个进程里 → 改签名，编译器会告诉你所有调用点。
服务契约的调用方在**别的部署单元**里 → 你无法编译别人的代码。

后果：
  ① 契约一旦发布就是**对外承诺**：删字段、改类型、收紧校验都是 breaking change；
  ② 需要版本策略（URL 版本、内容协商、字段级兼容）；
  ③ 需要兼容性规则：只加不改、只松不紧、新增字段有默认值；
  ④ 需要**契约测试**（consumer-driven contract）：由消费方声明期望，提供方验证；
  ⑤ 需要弃用流程：公告期 → 双写/双支持 → 摘除。
```

### 11.3 邮戳耦合（stamp coupling）

```text
定义（结构化设计一脉的经典耦合类型之一）：
  把一整个复合数据结构（对象/记录）传给对方，
  而对方**只用到其中的少数字段**。

为什么危险：
  · 表面上是「一个参数」，实际上依赖了整个结构 → 隐性依赖；
  · 结构里任何字段的变化都会传导到消费方（编译/序列化/校验层面）；
  · 最难被发现：看函数签名看不出来，要看实现才知道只用了两个字段。

识别方法（教学示意）：
  ① 静态分析：传入的结构有 N 个字段，实现里只读了 M 个（M << N）→ 可疑；
  ② 变更影响分析：改一个字段，有多少「其实不用它」的服务被迫重新发布？

修正：
  · 传**真正需要的字段**（转向数据耦合）；
  · 或者为不同消费方定义各自的视图/读模型（第 10 章的数据领域模式）。
```

### 11.4 契约与耦合等级（教学示意）

```text
内容耦合（最差）  直接改对方内部状态/越过接口
公共耦合          共享全局数据/共享库表
控制耦合          通过参数控制对方内部流程分支
邮戳耦合          传整个结构却只用几个字段        ← 本章重点要抓的
数据耦合（最好）  只传所需的、最小的必要数据
```

### 11.5 契约演进清单（教学示意）

```text
□ 新增字段：给默认值/可选；老消费方不受影响（安全）
□ 删除字段：先标记 deprecated → 公告 → 观察调用 → 再摘除（不安全）
□ 改类型/收紧校验：视为 breaking change，需要版本并存
□ 改语义：（同名字段含义变了）最危险，应换字段名
□ 每次变更：跑契约测试 + 兼容性检查（CI 门禁）
□ 有弃用台账：谁在用旧版本、什么时候摘
```

## 版本演进

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| 契约描述 | OpenAPI / Protobuf 为主 | 同左，且**契约即代码**：schema 进仓库、进 CI、自动生成客户端 |
| 兼容性检查 | 多靠人工评审 | 兼容性规则可由工具在 CI 中自动校验（加字段安全、删字段阻断） |
| 契约测试 | consumer-driven contract（CDC）实践已成熟 | 更普及，并常与 schema registry 联动 |
| schema 治理 | 分散在各服务 | **schema 注册中心**成为事件/消息架构的标配（集中管理与兼容性策略） |
| 邮戳耦合的识别 | 靠代码评审 | 可用静态分析与字段级使用统计辅助发现 |
| AI 编码助手 | 未涉及 | 契约与客户端代码可被自动生成 → 兼容性检查与弃用台账更重要（否则生成即分裂） |

## 近年研究与工业界开源实践（2015–2026）

- **契约描述与代码生成**（实测 star，2026-09 `gh api`）：
  `protocolbuffers/protobuf` = **72067**、`OAI/OpenAPI-Specification` = **31242**。
  二者分别是强类型二进制契约与 HTTP API 契约的事实标准，
  支撑本章 11.1 的「契约即代码」实践。
- **schema 注册中心成为事件架构标配**：在消息/事件平台中集中登记 schema
  并施加兼容性策略（向前/向后兼容），使「删字段」这类破坏性变更在**发布前**被拦住。
  相关平台实测：`apache/kafka` = **33848**、`apache/pulsar` = **15338**。
- **契约测试（CDC）普及**：由消费方声明期望、提供方在 CI 中验证，
  把「应该没问题」变成可执行门禁。
- **兼容性检查自动化**：加字段（有默认值）自动通过，删字段/改类型自动阻断，
  直接对应本章 11.5 的演进清单。
- **AI 编码助手的影响**：客户端与契约可被快速生成，
  因此**兼容性策略与弃用台账**必须由工具保证，否则版本分裂会迅速失控。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「严格契约更专业，一律用严格」 | 跨组织/版本长期共存时，严格会让每次演进都变成协调事件 |
| 2 | 「宽松契约就是不管」 | 宽松要配**契约测试**；没有测试的宽松等于裸奔 |
| 3 | 「传整个对象只是图省事」 | 那就是邮戳耦合：隐性依赖整个结构，改字段会波及无关服务 |
| 4 | 「加字段是安全的」 | 加**必填**字段对老消费方是破坏性的；加可选/有默认值的才安全 |
| 5 | 「改字段语义不算 breaking change」 | 同名改义是最危险的变更；应换字段名 |
| 6 | 「契约文档写完就完事」 | 契约要进 CI：兼容性检查 + 契约测试 + 弃用台账 |
| 7 | 🔧 「schema 治理可以以后再说」 | 事件架构下 schema 就是契约；没有注册中心与兼容策略，演进必然失控 |
| 8 | 🔧 「自动生成客户端就不需要契约评审」 | 生成只是降低接入成本；兼容性判断与弃用节奏仍需人来定 |
| 9 | 🔧 「内部服务可以随意改」 | 内部服务也有多个消费方；「内部」不等于「无契约」 |
| 10 | 🔧 「邮戳耦合只看签名看不出来，就没法治理」 | 可用静态分析与字段级影响分析；也可通过为消费方提供专属读模型来规避 |

## 思考题

1. 列出你们最重要的三份契约，标注它们是严格还是宽松，并说明为什么这么选。
2. 找一处邮戳耦合：传入的结构有多少字段？实际用了几个？改成传最小集会牵动什么？
3. 你们的兼容性检查在哪里跑？删一个字段会发生什么（有人拦吗）？
4. 有没有「同名改义」的历史遗留？它现在还能被安全理解吗？
5. 弃用台账在哪里？谁在跟踪旧版本的剩余调用方？
