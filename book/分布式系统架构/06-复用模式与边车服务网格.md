## 本章地图

> 一句话：**复用是一条从轻到重的阶梯：代码复制 → 共享库 → 共享服务 → 边车/服务网格；
> 每上一档，复用性变强，但耦合、运维与故障域也一起变大。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 8.1 代码复制 | 直接复制一份 | 最松的耦合，但一致性靠人；适合**还没到复用时机**的东西 |
| 8.2 共享库 | 打成库，各服务引入 | 复用与性能俱佳，但**版本治理**是新成本，且绑定技术栈 |
| 8.3 共享服务 | 做成独立服务调用 | 跨语言、可独立发版；代价是新的故障域与网络开销 |
| 8.4 边车和服务网格 | 把横切逻辑放到进程旁的代理 | 业务代码零侵入、策略统一；代价是运维复杂度与排错链路变长 |
| 8.6 代码复用何时带来价值 | 复用的判据 | 复用不是美德，**被验证过的共性**才值得复用 |

## 核心精讲

> **教学示意，不参与构建。** 以下对比表与配置片段均为教学性重述。

### 6.1 复用阶梯：四档的代价对照

```text
                耦合    跨语言   独立发版   运维成本   适用
代码复制         最低    是       是         低        尚未稳定的共性、极小的片段
共享库           中      否（绑栈）否（随应用发）中     稳定且同栈的通用逻辑
共享服务         较高    是       是         高        跨栈、且需独立演进的能力
边车/服务网格     高（平台级）是   是（平台侧）最高     横切的基础设施逻辑（通信、安全、可观测）
```

关键观察：**越往上，「复用」越像「依赖」**。共享库的版本冲突、共享服务的可用性依赖、
服务网格的运维复杂度——这些都是复用的账单，只是开票时间不同。

### 6.2 代码复制：被低估的选项

```text
「复制」通常是被当作坏味道的，但本章把它列为正式选项（按标题与结构推断）：
  + 零耦合：改自己的副本不影响别人
  + 零治理成本：不需要版本协调
  - 一致性靠人：一处修 bug，别处可能漏

适用判据（教学示意）：
  · 这段逻辑是否**已经被验证为共性**？（还不确定 → 先复制，别急着抽）
  · 变更频率高不高？（高 → 复制的同步成本会失控）
  · 复制份数会不会失控？（超过 2–3 份就该考虑上档）
```

这与「Rule of Three」（第三次重复才抽象）的经验规则一致：
**过早抽象比重复更贵**，因为错误的抽象会同时约束所有使用方。

### 6.3 共享库：最常见的档位，代价在版本

```text
优点：无网络开销、无新故障域、调试简单、性能好。
代价：
  · 技术栈绑定（Java 的库给不了 Go 服务用）；
  · 版本治理：升级需要所有使用方配合（菱形依赖、不兼容升级）；
  · 泄漏风险：库里塞进业务逻辑后，它就不再是「基础设施」，而是隐式契约。
判据（教学示意）：
  逻辑稳定 + 同栈 + 无独立发版需求 → 共享库是性价比最高的档位。
```

### 6.4 共享服务：跨栈的代价是新的故障域

```text
优点：跨语言；可独立发版与扩容；逻辑有单一事实来源。
代价：
  · 新增一个**必须高可用**的依赖——它的可用性会乘进调用方的可用性（第 2 章动态耦合）；
  · 网络开销与尾部延迟（每多一跳，p99 就多一份风险）；
  · 契约演进成本（第 13 章）。
判据（教学示意）：
  只有当「跨栈」或「必须独立演进」成立时，才值得从库升到服务。
```

### 6.5 边车与服务网格：把横切逻辑移出业务进程

```text
边车（sidecar）：把一个服务的横切能力（服务发现、熔断、重试、mTLS、遥测）
  放进与它同生命周期的独立进程/容器里，业务进程只关心业务。

服务网格（service mesh）：所有边车 + 统一的控制面。
  数据面（data plane）   每个服务旁的代理，负责实际的流量处理与遥测上报
  控制面（control plane）统一下发策略、证书、路由与限流配置

收益：
  · 业务代码零侵入：横切能力可由平台团队统一升级；
  · 策略一致：mTLS、重试、超时、限流在所有服务上同构；
  · 可观测性统一：调用链与指标不再依赖各服务自觉埋点。
代价：
  · 运维复杂度显著上升（又一个必须懂的系统）；
  · 排错链路变长（业务 → 边车 → 网络 → 对端边车 → 对端业务）；
  · 资源开销（每实例多一个代理进程）。
```

### 6.6 复用何时带来价值（8.6）

```text
复用不自带价值。有价值的复用至少要满足（教学示意）：
  ① 共性已被验证：至少 2–3 个真实使用方，且用法一致；
  ② 变更频率可预期：不会每周变，否则所有使用方都被拖着走；
  ③ 有明确的拥有者与演进流程：谁改、怎么发、怎么弃用；
  ④ 复用带来的收益 > 治理与耦合成本。
反例：为了「统一」把所有小工具抽成一个 common 包，
      结果任何小改动都要全量回归——这就是复用的负收益。
```

### 6.7 示意：给一段逻辑选档（教学示意）

```text
场景 A：金额格式化（15 行，各服务都在用，很少变）
  → 共享库（稳定、同栈、无独立发版需求）
场景 B：用户身份校验（跨 Java/Go 两种栈，安全策略需统一更新）
  → 共享服务 或 边车（安全策略要能独立、强制地升级）
场景 C：服务间调用的重试/超时/熔断策略（所有服务都需要，且要统一）
  → 服务网格（典型的横切关注点）
场景 D：某个领域规则（只有两个服务用，需求还在变）
  → 先复制，等稳定后再抽（过早抽象更贵）
```

## 版本演进

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| 服务网格形态 | 边车（sidecar）为绝对主流 | 出现**无边车（sidecar-less / ambient）**形态，把代理能力下移到节点层，降低每实例开销 |
| 网格的采纳 | 热度高但落地门槛也高 | 趋于理性：中小规模常选择「库 + 网关」而非完整网格 |
| 平台工程 | 概念形成期 | 横切能力被打包成平台默认能力（内置模板 + 流水线），业务团队无需自行接入网格 |
| 横切逻辑的下沉 | 靠边车 | 出现内核层（eBPF 一类）方案，把可观测与网络策略进一步下沉 |
| 安全 | 本章无独立安全章 | 零信任与 mTLS 成为网格的核心卖点之一，身份认证/授权下沉到基础设施 |
| AI 编码助手 | 未涉及 | 业务代码生成更快，横切逻辑更应**由平台统一提供**，避免各服务各写一套 |

## 近年研究与工业界开源实践（2015–2026）

实测 star（2026-09 `gh api`）：

- `envoyproxy/envoy` star = **28995** —— 服务网格数据面的事实标准代理之一；
- `istio/istio` star = **38408** —— 最知名的服务网格实现，提供控制面与策略下发；
- `linkerd/linkerd2` star = **11499** —— 另一条更轻量的网格路线。

趋势与实践：

- **从边车走向「编排下沉」**：网格能力从「每个 Pod 一个代理」向节点级/平台级收敛，
  以降低资源开销与运维复杂度；同时与平台工程的默认模板结合，
  让业务团队「不感知网格」也能拿到 mTLS 与遥测。
- **理性的采纳尺度**：网格的收益随服务数与跨语言程度上升；
  小规模系统往往用「库 + 网关 + 统一 SDK」更划算——这正呼应本章 6.6「复用何时带来价值」。
- **安全与合规成为主要驱动力**：统一 mTLS、身份认证与访问策略，
  是许多组织引入网格的第一理由（也弥补了本书没有独立安全章的缺口）。
- **AI 编码助手的间接影响**：业务代码生成速度提升后，
  横切逻辑若不由平台统一提供，就会出现「每个服务各写一套重试/超时/埋点」的分裂。
- 本目录所有代码为教学示意、不参与构建；star 均为 2026-09 `gh api` 实测，查不到写「star 未核验」。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「复用总是好的」 | 复用自带耦合与治理成本；本章 8.6 专门问「何时带来价值」 |
| 2 | 「复制代码一定是坏味道」 | 在共性未验证前，复制比错误抽象便宜 |
| 3 | 「共享库没有运行时代价」 | 版本治理、技术栈绑定、菱形依赖都是真实成本 |
| 4 | 「做成服务就更解耦」 | 共享服务引入了新的**同步依赖与故障域**（第 2 章动态耦合） |
| 5 | 「上了服务网格就不用管重试超时」 | 策略统一了，但**语义**（哪些操作可重试、幂等性）仍在业务侧 |
| 6 | 「网格是免费的性能」 | 每实例多一跳与多一个进程；资源与延迟都有实测代价 |
| 7 | 🔧 「只有边车一种网格形态」 | 2023 年后出现无边车/节点级形态，选型时应比较开销与运维复杂度 |
| 8 | 🔧 「小团队也该上网格」 | 收益随规模上升；小规模用库 + 网关往往更划算 |
| 9 | 🔧 「本书覆盖了安全」 | 中文版**没有独立安全章**；零信任/mTLS 等实践主要通过网格落地，需另找资料 |
| 10 | 🔧 「横切逻辑可以交给 AI 各服务各写一遍」 | 恰恰相反：越容易生成，越需要由平台统一提供，否则分裂不可控 |

## 思考题

1. 挑一段你们「共享」的公共代码，判断它在阶梯上该在哪一档？现在放错了吗？
2. 有没有一个 common 包正在变成隐式契约？它的拥有者与弃用流程是什么？
3. 你们的横切能力（重试/超时/熔断/埋点）现在是哪个档位？各服务是否写了自己的一套？
4. 以你们的服务数与语言栈数量，引入服务网格的收益能否盖过运维成本？给出量化理由。
5. 写一个「禁止在业务代码内实现重试策略」的适应度函数：怎么检出？违规怎么办？
