# 第 1 章 权衡分析的语言：ADR 与适应度函数（没有最佳实践会怎么样）

> 覆盖原书第 1 章（何为「难点」/ 永不过时的软件架构建议 / 数据在架构中的重要性 /
> 架构决策记录 / 架构适应度函数 / 架构与设计：保持定义简单 / 引入 Sysops Squad 的传奇故事）。
> 本章是全书的方法总纲：后面 14 章都在反复使用这里的两个工具——
> **ADR（记录决策）** 与 **适应度函数（把约束变成可执行的检查）**。

## 本章地图

> 一句话：**分布式架构里没有最佳实践，只有权衡；既然没有正确答案，
> 那就要把「为什么这么选」写成 ADR，把「不能坏到什么程度」写成可执行的适应度函数。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 何为「难点」 | 有取舍、无最佳实践的问题域 | 难点的标志是「没有放之四海皆准的答案」 |
| 永不过时的软件架构建议 | 少数几条长期成立的原则 | 原则要少而硬，其余交给上下文 |
| 数据在架构中的重要性 | 数据往往比代码更难搬 | 拆服务的真正难点在数据，不在代码 |
| 架构决策记录（ADR） | 把决策与上下文、后果一起记录 | 决策的可追溯性比正确性更可管理 |
| 架构适应度函数 | 把架构特征变成可衡量的检查 | 不能衡量的架构特征，等于不存在 |
| 架构与设计：保持定义简单 | 区分架构（难改的）与设计（易改的） | 这个区分决定了什么该进 ADR |
| 引入 Sysops Squad | 贯穿全书的虚构案例 | 全书所有权衡都在同一案例上演示 |

## 核心精讲

> **教学示意，不参与构建。** 以下 ADR 模板、适应度函数伪代码与权衡矩阵均为教学性重述。

### 1.1 「难点」的定义：为什么没有最佳实践

```text
普通问题：有已知的好答案，照做即可（用什么序列化、怎么写单元测试）。
难点（hard part）：
  ① 没有一个放之四海皆准的答案；
  ② 每个选项都有真实代价，且代价落在不同的维度上；
  ③ 代价的支付方（团队/业务/运维）往往不是做决定的人。

分布式架构几乎全是难点：
  服务拆多细？数据谁拥有？事务怎么保证？工作流谁来编排？契约多严格？
→ 因此本书的方法不是「给你答案」，而是「给你一套把权衡说清楚、记下来、能在事后被检验的方法」。
```

### 1.2 ADR：把决策变成可追溯的资产

ADR（Architecture Decision Record，架构决策记录）的经典格式来自 Michael Nygard 2011 年的文章
（*Documenting Architecture Decisions*），核心是「轻到没人会偷懒不写」：

```text
# 标题：<编号>. <一句话决策>

## 状态（Status）
proposed / accepted / deprecated / superseded by <编号>

## 上下文（Context）
我们面对的事实与约束：业务目标、规模、团队结构、现有系统、时间盒。
（只写事实，不写情绪。）

## 决策（Decision）
我们决定做什么。用主动语态一句话说清。

## 后果（Consequences）
好后果 / 坏后果 / 中性后果，以及**我们接受**的代价。
（写下「我们愿意为此付出什么」——这才是 ADR 的价值所在。）
```

工程要点：

- **ADR 是「不可变的记录」**：决定变了就新写一篇并标记 superseded，不要回头改旧文；
- **ADR 放在代码库里**：与代码同评审、同版本化，才有机会被后人看到；
- **ADR 的读者是未来的自己**：写「当时为什么」，而不是「现在对不对」。

### 1.3 适应度函数：把架构特征变成可执行的检查

适应度函数（fitness function）这一术语出自《Building Evolutionary Architectures》
（Ford、Parsons、Kua，O'Reilly 2017），本书把它作为架构治理的核心工具：

```text
适应度函数 = 对某个架构特征（可伸缩性、耦合度、可测试性……）的客观、可执行的度量。

分类（沿该书的分类维度）：
  Atomic（原子）   只测一个维度，如「服务间不得跨库直连」
  Holistic（整体） 同时测多个维度，如「部署频率 + 变更失败率的组合门槛」
  Triggered（触发式） 在特定事件时运行，如 CI 流水线里的依赖检查
  Continual（持续式） 常驻运行，如生产环境的延迟/错误率监控
  Static（静态）    静态分析结果，如循环依赖检测
  Dynamic（动态）   运行期行为，如压力测试下的 p99 延迟
```

示意（教学示意，不参与构建）：

```yaml
# fitness-functions.yaml —— 教学示意，不参与构建
- id: FF-001
  name: 禁止跨服务直接访问他人数据库
  kind: static, triggered, atomic
  check: |
    扫描所有服务的连接配置；
    若某服务的数据库账号属于另一个服务的 schema → 失败。
  on_violation: block_merge

- id: FF-002
  name: 领域层不得依赖基础设施层
  kind: static, triggered, atomic
  check: |
    静态依赖分析：domain.* 不得 import infrastructure.*
  on_violation: block_merge

- id: FF-003
  name: 关键路径 p99 延迟预算
  kind: dynamic, continual, holistic
  check: |
    生产采样窗口 5min；p99(checkout) <= 300ms 且 错误率 <= 0.1%
  on_violation: alert_and_open_adr_review
```

### 1.4 权衡矩阵：把「纠结」外化

本书用 Sysops Squad（一个虚构的运维外包团队）贯穿全书，每个决策都用
**「选项 × 架构特征」的矩阵**打分，而不是靠直觉：

```text
示例矩阵（教学示意，数字仅示意评分高低，非实测）：

决策：工单分配服务是否单独拆分
                 可伸缩性  可用性  性能  可部署性  可测试性  数据完整性  成本
方案 A 拆成独立服务   ★★★★   ★★★    ★★    ★★★★    ★★★     ★（需 Saga） ★★
方案 B 留在单体模块   ★★      ★★★★  ★★★★  ★★       ★★★★    ★★★★       ★★★★
方案 C 拆但共享数据库 ★★★     ★★★    ★★★   ★★★      ★★       ★★★        ★★★

读法：
  ① 先列**架构特征**，再列方案——列不出特征就说明需求没聊清楚；
  ② 每个格子都要能说出「为什么」，说不出就回去量；
  ③ 选完把这张表贴进 ADR 的「后果」段。
```

### 1.5 架构与设计：保持定义简单

```text
本书的一个务实立场（标题即为「保持定义简单」）：
  架构 ≈ 难以改变、改变代价高的那些结构决策；
  设计 ≈ 相对容易改变的实现层决策。
→ 只有「难改的」才值得写 ADR、才值得配适应度函数；
  把什么都当架构，治理成本会把团队拖垮。
```

### 1.6 数据才是难点（本章承上启下的一句）

```text
本章明确把「数据在架构中的重要性」单独提出来：
  代码可以重写、可以并行演进、可以用版本兼容；
  数据是唯一状态，搬起来最贵、回滚最难、跨服务共享的代价最高。
→ 所以本书第一部分以「分」为主，但真正的硬骨头在第 6 章（分离业务型数据）、
  第 9 章（数据所有权）、第 10 章（分布式数据访问）、第 12 章（Saga）。
```

## 版本演进

原书英文版 2021、中文版 2023。本章的方法本身没变，但**工具与执行方式**在 2023–2026 变化明显：

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| ADR 的载体 | Markdown 文件放仓库里（Nygard 格式） | 同左，但普遍**工具化**（模板校验、索引页自动生成、与 RFC/设计文档流程合并）；实践中也常与团队既有文档流程统一 |
| 适应度函数的执行 | 主要是 CI 里的静态检查 + 监控告警 | 与平台工程（platform engineering）合并：架构约束下沉为**默认可复用的流水线与策略** |
| 架构治理 | 靠人评审 | 自动化治理 + 人工评审双轨；违规可自动阻断合并 |
| 决策的输入 | 人工调研与经验 | **AI 编码助手**参与方案生成与代码骨架产出，人的工作重心转向「定义约束与验收」 |
| 「架构 vs 设计」的边界 | 靠经验划 | 用适应度函数显式标出「哪些改动必须通过哪道检查」，边界因此可执行 |

## 近年研究与工业界开源实践（2015–2026）

- **ADR 实践已成标配**：以 Nygard 格式为事实标准，并出现多种工具化索引与模板仓库。
  实测 `joelparkerhenderson/architecture-decision-record` star = **17026**（2026-09 `gh api` 实测）——
  它是该实践最广为引用的模板/资料汇集仓库。
- **适应度函数的自动化落地**：以静态依赖/分层约束检查为代表的自动化架构治理在 Java 生态最成熟，
  实测 `TNG/ArchUnit` star = **3843**（2026-09 `gh api` 实测）——
  可把本书 1.3 的「静态、触发式、原子」类适应度函数直接写成单元测试。
- **AI 编码助手改变决策成本**：方案原型的产出成本大幅下降，
  于是**「把约束写清楚」的价值上升**——适应度函数正好承担这个角色：
  人负责定义「什么不允许」，机器负责生成与检查。
- **平台工程把治理前置**：组织把架构约束做成默认流水线与模板，
  使本书「适应度函数」从「架构师的工具」变成「平台的能力」。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「找个最佳实践照做就行」 | 本书的前提就是**没有最佳实践**；能做的最好事情是把权衡说清楚并记下来 |
| 2 | 「ADR = 会议纪要」 | ADR 记的是**决策 + 上下文 + 接受的代价**；纪要记过程，ADR 记结论 |
| 3 | 「决策变了就改 ADR」 | 应新增一篇并标记 superseded，保留历史链条，否则失去追溯价值 |
| 4 | 「架构特征列出来就能治理」 | 不能度量 = 不能治理；必须落成适应度函数（可执行检查） |
| 5 | 「适应度函数越多越好」 | 每个函数都有维护成本；只给**难改的架构决策**配，别把设计层也拉进来（本书 1.5） |
| 6 | 「数据是拆完服务之后再处理的事」 | 🔧 本书明确把数据放在方法总纲里：数据才是拆分的真正约束（1.6） |
| 7 | 🔧 「AI 编码助手会替你做架构决策」 | 它降低的是**方案产出**成本，不是**约束定义**成本；约束不清时，生成越快偏差越大 |
| 8 | 🔧 「自动化治理可以替代架构评审」 | 适应度函数只能检查**已形式化**的部分；价值判断（业务权衡）仍需人 |
| 9 | 🔧 「适应度函数一次写完就一劳永逸」 | 架构演进后需复核；失效或过严的函数本身就是技术债 |

## 思考题

1. 挑一个你们最近做的架构决策，按本章 1.2 的模板补写 ADR：补不上「上下文」说明什么？
2. 列出你们最重要的三个架构特征，各写一个可执行的适应度函数（标明 atomic/holistic 与 triggered/continual）。
3. 找出你们代码库里一条**没有被任何检查保护**的架构约束，说明它过去是否失守过。
4. 「架构 vs 设计」：你们团队的分界在哪？这个分界是否反映在评审与 CI 上？
5. AI 编码助手参与开发后，你们哪些约束必须**先于代码**存在？把它们写成适应度函数。
