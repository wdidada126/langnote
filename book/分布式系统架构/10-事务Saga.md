# 第 12 章 事务 Saga

> 覆盖原书第 12 章（事务 Saga 的 8 种模式 / 状态管理与最终一致性 / 管理 Saga 的手段 /
> Sysops Squad：原子性事务和补偿更新）。
> 本章是第 9 章「分布式事务」的落地篇，也是第 11 章编排/编舞之争的具体战场：
> **Saga 把一个长事务拆成一串本地事务，代价是失去隔离性。**

## 本章地图

> 一句话：**Saga 用「每步都是本地事务 + 失败时反向补偿」换取不阻塞的原子性；
> 它的全部难点不在正向流程，而在补偿的幂等性与中间状态的可见性。**

## 核心精讲

> **教学示意，不参与构建。** 以下伪代码与对策清单均为教学性重述。

### 10.1 Saga 的基本模型

```text
Saga（Garcia-Molina & Salem, SIGMOD 1987）：
  长事务 T 拆成 T1, T2, ..., Tn（每个都是**本地事务**）；
  每个 Ti 配一个补偿 Ci（语义上的撤销，不是物理回滚）；
  正向执行 T1..Tn；若 Tj 失败，则反向执行 C(j-1)..C1。

与 2PC 的对比：
                2PC                Saga
  原子性        协议保证（阻塞）     最终保证（靠补偿）
  隔离性        有（锁保持到提交）   **没有**（中间状态可见）
  阻塞          会（协调者/参与者失败）  不会
  适用          短事务、少参与方    长流程、跨服务
```

### 10.2 八种形态（教学归纳，非本书原始命名）

```text
① 史诗型（步骤过多、流程过长）
   一个 Saga 包了十几步 → 补偿链与排错都失控。
   对策：按子域拆成多个短 Saga，用事件衔接。

② 乒乓型（服务间反复来回）
   A 调 B，B 又调 A…… → 循环依赖、调用链不可理喻。
   对策：把流程控制权收拢到编排器，服务之间不再互相驱动。

③ 童话型（假设不会失败）
   只写正向流程，没有补偿、没有超时 → 生产上迟早出事。
   对策：为每一步显式定义补偿与超时策略（哪怕是「人工介入」）。

④ 时间旅行型（想撤回已被读到的状态）
   试图「回滚」一个已经被其他事务读到的中间状态 → 物理上做不到。
   对策：接受不可回滚，改为**前向修复**（继续推进到一致状态）或用语义锁避免被读到。

⑤ 幻想型（设计与现实脱节）
   按理想网络与理想依赖设计 → 一上生产就崩。
   对策：在设计与评审阶段显式注入失败场景（超时、重复、乱序、部分成功）。

⑥ 恐怖型（补偿本身会失败）
   补偿操作不幂等、或补偿也会失败且无兜底 → 不一致永久化。
   对策：补偿必须**可重入**；失败要有重试上限 + 人工工单兜底。

⑦ 并行型（分支并行执行）
   多个分支同时推进以缩短总时长 → 需要同步点与部分成功的处理。
   对策：明确汇合点语义（全部成功/可容忍部分失败），并为每个分支准备补偿。

⑧ 短篇集型（多个独立子流程）
   若干彼此独立的短流程组合 → 容易与「史诗型」混淆。
   对策：能独立的就真独立（各自一个 Saga），不要用一条长链把它们串起来。
```

### 10.3 隔离性：Saga 最难的一课

```text
Saga 没有隔离性 → 中间状态对其他事务可见。经典异常：
  · 脏读（读到 Saga 未完成的中间状态）
  · 丢失更新（两个 Saga 同时改同一条记录）
  · 不可重复读 / 幻读（Saga 执行期间数据被别的 Saga 改了）

常见对策（教学归纳，见 Richardson《Microservices Patterns》一脉的归纳）：
  语义锁（semantic lock）     在记录上标记「处理中」，阻止其他 Saga 改（或提示稍后）
  交换式更新（commutative）   把更新设计成可交换的（加减/集合并），顺序无关
  悲观视图（pessimistic view）先标记再操作，让其他 Saga 提前感知风险并中止/排队
  重读值（reread value）      提交前重读一次，若被改过则中止并重试
  版本文件（version file）    记录已执行的操作序列，用于检测冲突
  按值传（by value）          请求中携带读数，服务端据此判断数据是否已被改
```

### 10.4 补偿的设计要点

```text
① 补偿必须幂等
   同一个补偿可能被重放多次（重试、消息重投）。
   做法：幂等键 / 去重表 / 状态机校验（只从「已预留」补偿一次）。

② 补偿不等于反向调用
   例：「扣库存」的补偿是「归还库存」，但业务上可能还需要
        取消预留记录、发通知、更新读模型——补偿是一个**业务动作**。

③ 补偿也可能失败
   必须有重试上限 + 人工兜底（工单/告警）。
   「补偿失败」是最终一致的死结，不能只写日志了事。

④ 补偿的顺序与时间
   反向补偿按执行过的步骤倒序；
   超时未完成的步骤要先**确定其最终状态**（查询/对账）再决定补偿还是继续。

示意（教学示意，不参与构建）：
  on StepFailed(stepIndex, error):
      for i in reversed(completedSteps):
          retry_with_backoff(compensate(i), max=3)
          if still_failed:
              open_manual_ticket(i)      # 人工兜底，绝不能静默
```

### 10.5 状态管理

```text
Saga 的状态必须**持久化**（否则进程崩溃就丢失上下文）：
  · 记录：Saga 实例 ID、当前步骤、已完成步骤、各步参数与幂等键；
  · 状态推进要幂等（重复消息不能把状态推错）；
  · 需要超时与调度（等待异步响应、定时重试）；
  · 需要可查询（「这一单卡在哪一步」）。

这正是第 11 章「编排器/工作流引擎要持久化状态」的原因——
现代工作流引擎把这四件事做成了内建能力。
```

## 版本演进

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| Saga 的实现方式 | 多为自研（状态表 + 消息 + 定时任务） | 工作流引擎内建持久化执行、重试、补偿与可视化（见第 11 章实测 star） |
| 编排 vs 编舞 | 争论中 | 关键长流程普遍回摆到**编排式 Saga**，因为补偿与状态管理更可控 |
| 幂等与去重 | 靠团队自觉 | 框架层提供幂等键、去重与可重入语义 |
| 可观测 | 自建 | 流程实例视图 + 追踪成为标配，「卡在哪一步」可直接查询 |
| 补偿的兜底 | 常缺失 | 人工工单/告警被纳入流程定义，作为一等公民 |
| AI 编码助手 | 未涉及 | 正向流程很容易被生成，但**补偿与幂等**仍需人工设计与评审 |

## 近年研究与工业界开源实践（2015–2026）

- **工作流引擎成为 Saga 的载体**（实测 star，2026-09 `gh api`）：
  `temporalio/temporal` = **23303**、`netflix/conductor` = **12751**、
  `camunda/camunda` = **4296**（历史仓库 `camunda/camunda-bpm-platform` = **4269**）。
  它们把本章 10.5 的四件事（持久化、超时/重试、可查询、可视化）内建。
- **消息/事件平台是协作式 Saga 的底座**：
  `apache/kafka` = **33848**、`apache/pulsar` = **15338**（2026-09 `gh api` 实测）。
- **幂等成为框架能力**：幂等键、去重表与可重入语义普遍由框架或库提供，
  不必每个团队各自实现——但**语义上的幂等**（什么是同一次操作）仍需业务定义。
- **补偿的兜底被制度化**：补偿失败必须落到人工工单/告警，
  并被纳入流程定义与演练，而不是「写个 log」。
- **AI 编码助手的边界**：正向步骤可被快速生成；
  **补偿、幂等与隔离对策**是必须人工设计的部分，也是评审的重点。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Saga = 分布式事务」 | Saga **没有隔离性**；它保证的是「最终一致」而非「原子可见」 |
| 2 | 「补偿 = 反向调用」 | 补偿是**业务动作**（可能含通知、读模型更新），且必须幂等 |
| 3 | 「补偿一定会成功」 | 补偿也会失败；必须有重试上限 + 人工兜底 |
| 4 | 「重试就够了」 | 重试要求幂等；否则重复执行会造成重复扣款一类事故 |
| 5 | 「中间状态没人会看到」 | 没有隔离性 → 一定会被看到；需要语义锁/重读值一类对策 |
| 6 | 「Saga 不需要持久化状态」 | 状态丢失 = 补偿无依据；持久化是硬要求 |
| 7 | 🔧 「八种模式都要用上」 | 其中多数是**需要避免的形态**；本目录已标注该节命名未能核对原文 |
| 8 | 🔧 「Saga 要自己实现状态机」 | 2026 年应先评估成熟工作流引擎 |
| 9 | 🔧 「协作式 Saga 一定更解耦」 | 它把补偿责任分散到各参与方，遗漏风险更高（第 11 章） |
| 10 | 🔧 「AI 能生成完整 Saga」 | 它能生成正向步骤；补偿与幂等仍需人工设计，是评审重点 |

## 思考题

1. 挑一个你们的 Saga，数一数它有几步：超过多少步就该拆？补偿链有多长？
2. 它的每一步补偿都幂等吗？请给出幂等键的设计与去重机制。
3. 中间状态会被其他服务读到吗？你们用的是哪一种隔离对策？代价是什么？
4. 补偿失败时发生什么？有没有人工兜底？这条路径做过演练吗？
5. 如果把这套 Saga 迁到工作流引擎上，哪些代码可以删掉？哪些必须保留？
