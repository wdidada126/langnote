# 第 11 章 管理分布式工作流（编排 vs 编舞）

> 覆盖原书第 11 章（集中编排式通信 / 分散协作式通信 / 权衡集中编排与分散协作 /
> Sysops Squad：工作流管理）。
> 本章是全书争论最激烈的一章，也是 2023–2026 实践变化最大的一章：
> 本书写作时「编舞（choreography）」正流行，而随后**工作流引擎重新崛起**，
> 把「编排（orchestration）」的性价比大幅抬高。

## 本章地图

> 一句话：**跨服务的业务流程要么由一个中心指挥（编排），要么由各方按事件自行其是（编舞）；
> 前者换来可控与可观测，后者换来解耦与自治——代价是另一侧的账单。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 11.1 集中编排式通信 | 一个编排器驱动所有步骤 | 流程可见、错误集中处理；但编排器成为新的耦合点与故障域 |
| 11.2 分散协作式通信 | 各方订阅事件自行推进 | 高度解耦、易扩展；但流程隐式、难观测、难排错 |
| 11.3 权衡集中编排与分散协作 | 六个维度的对照 | 关键判据是**错误处理的复杂度**与**流程是否需要被看见** |
| 11.4 Sysops Squad 案例 | 工作流管理 | 同一系统里两种风格可以混用 |

## 核心精讲

> **教学示意，不参与构建。** 以下流程伪代码与对照表均为教学性重述。

### 9.1 集中编排（orchestration）

```text
结构：有一个编排器（orchestrator）负责驱动流程：
  调用服务 A → 等待结果 → 调用服务 B → 失败则触发补偿 → 记录状态。

示意（教学示意，不参与构建）：
  orchestrator.run("create-order"):
      orderId  = order.create(ctx)          // 步骤 1
      try:
          stock.reserve(orderId, items)     // 步骤 2
          payment.charge(orderId, amount)   // 步骤 3
          order.confirm(orderId)            // 步骤 4
      except StepFailed as e:
          compensate(e.completedSteps)      // 反向补偿（第 12 章 Saga）

优点：
  · 流程显式可见：一张图/一份定义就是整个业务；
  · 错误处理集中：超时、重试、补偿都在一处；
  · 可观测与可回放：状态在哪一步一目了然；
  · 易于测试：可以在编排器层模拟各步失败。
代价：
  · 编排器成为**新的耦合点**与故障域（需要高可用与持久化状态）；
  · 编排器里容易长出业务逻辑（要警惕变成「上帝服务」）。
```

### 9.2 分散协作（choreography）

```text
结构：没有中心。各方通过事件/消息自行推进：
  订单服务发 OrderCreated → 库存服务消费后发 StockReserved
  → 支付服务消费后发 PaymentCharged → 订单服务消费后置为已确认。

优点：
  · 高度解耦：加一个新参与方只需订阅事件，不改现有服务；
  · 无中心故障域；
  · 与事件驱动架构天然契合，吞吐好。
代价：
  · 流程**隐式**：没有人能一眼看出整个流程长什么样；
  · 排错困难：一个订单卡住了，要翻多个服务的事件日志；
  · 补偿分散：每一步失败都要有人负责发补偿事件；
  · 循环依赖与事件风暴风险。
```

### 9.3 六维权衡表（教学示意）

```text
维度              编排（集中）              编舞（分散）
耦合               高（都知道编排器）        低（只知道事件）
流程可见性         显式、集中                隐式、分散
错误处理           集中、易设计              分散、易遗漏
可观测/排错        容易（有流程状态）        困难（需跨服务追踪）
扩展新参与方       要改编排器                只订阅事件（低成本）
故障域             编排器是新的关键依赖      无中心依赖
测试               易（可在编排层注入故障）  较难（需端到端）
典型适用           长流程、有补偿、强审计    简单广播、可最终一致
```

### 9.4 关键判据：错误处理的复杂度

```text
本书的权衡最终落在「出错时怎么办」：
  · 步骤多、有补偿、需要人工介入/超时重试 → 编排更省事；
  · 步骤少、无补偿、可幂等重试 → 编舞更省事。

一个实用判据（教学示意）：
  如果流程需要「**回滚已经做过的事**」，就优先考虑编排；
  因为补偿的顺序、幂等与状态管理集中在编排器里最可控。
```

### 9.5 混用：最常见也最现实

```text
真实系统几乎都是混合的：
  · 主流程（下单、退款）用编排——需要可见性与补偿；
  · 通知类、派生类（发送通知、更新索引、刷新读模型）用编舞——无需回滚；
  · 领域内用编舞，跨领域的关键流程用编排。
→ 本书的立场是「权衡」而非「选边」；把每种流程按上表的维度过一遍即可。
```

## 版本演进

这是本书最需要 2026 补丁的一章。原书写作时社区风向偏向编舞，随后发生了一次明显的回摆：

| 议题 | 原书时期（2021–2023） | 2026 现状 |
| --- | --- | --- |
| 编排 vs 编舞的风向 | 编舞（事件驱动）更受推崇 | **编排回摆**：工作流引擎成熟后，编排的运维与开发成本大幅下降 |
| 编排器的实现 | 多为自研（状态机 + 定时 + 消息） | 成熟的开源/托管工作流引擎成为默认选项（持久化状态、重试、补偿、可视化内建） |
| 长流程的可靠性 | 靠自研保证 | 引擎提供持久化执行、超时、重试策略与可回放，长流程不再是高危区 |
| 可观测性 | 需自建 | 引擎自带流程实例视图，直接回答「这一单卡在哪一步」 |
| 编排下沉 | — | 编排/重试/补偿能力被平台化，业务团队声明流程即可 |
| AI 相关 | 未涉及 | **AI 智能体（agent）编排**成为新的工作流形态：多步调用工具、需要可重试与可回放 |

## 近年研究与工业界开源实践（2015–2026）

- **工作流引擎的崛起**（实测 star，2026-09 `gh api`）：
  - `temporalio/temporal` star = **23303** —— 以「持久化执行」为核心的工作流引擎，
    把重试、超时、补偿与长流程状态管理做成内建能力；
  - `netflix/conductor` star = **12751** —— 面向微服务编排的引擎；
  - `camunda/camunda` star = **4296**（历史仓库 `camunda/camunda-bpm-platform` star = **4269**）；
    ⚠ `camunda/camunda7` 经 `gh api` 实测返回 **404**，本目录不采用该仓库名。
- **实践结论的回摆**：社区里「编舞 vs 编排」的争论在 2023 年后趋于务实——
  关键长流程普遍回到编排（因为有引擎兜底），而通知/派生类仍走编舞。
- **编排下沉为平台能力**：重试、超时、补偿、可视化由平台统一提供，
  业务团队只声明流程与步骤语义，这与第 8 章「横切能力下沉」是同一趋势。
- **流程挖掘（process mining）**：从事件日志还原真实流程，
  部分缓解了编舞「流程隐式」的缺点——也说明编舞并非不可观测，只是成本更高。
- **AI 智能体编排**：多步工具调用需要可重试、可回放与状态持久化，
  工作流引擎成为承载这类流程的常见底座，使本章的权衡在 2026 年多了一类新用例。
- 本目录所有代码为教学示意、不参与构建；star 均为 2026-09 `gh api` 实测，查不到写「star 未核验」。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「编舞更先进，编排过时」 | 二者是权衡；2023 年后编排因引擎成熟而回摆 |
| 2 | 「编排器会成为瓶颈所以不能用」 | 编排器只负责**协调**不承载业务数据；配合持久化与水平扩展可管理 |
| 3 | 「编舞没有单点所以更可靠」 | 可靠性转移到了「每个参与方都要正确处理补偿」，遗漏更难发现 |
| 4 | 「事件链条就是流程文档」 | 链条分散在各服务里；需要额外的流程视图或流程挖掘才能看见全貌 |
| 5 | 「编排器里可以写业务规则」 | 会退化为上帝服务；编排器只管**顺序与错误**，规则归领域服务 |
| 6 | 「所有流程都用一种风格」 | 混用最现实：主流程编排、通知类编舞 |
| 7 | 🔧 「编排必须自研状态机」 | 2026 年应先看成熟工作流引擎（Temporal/Camunda/Conductor 等） |
| 8 | 🔧 「长流程不可靠是必然」 | 持久化执行 + 幂等 + 可回放可以把长流程做成常规工程 |
| 9 | 🔧 「补偿就是反向调用」 | 补偿必须幂等、可重入、可能需要人工兜底；见 [10-事务Saga.md](10-事务Saga.md) |
| 10 | 🔧 「AI 智能体的多步调用不需要编排」 | 恰恰最需要：可重试、可回放、可观测，正是工作流引擎的强项 |

## 思考题

1. 挑一个你们的跨服务流程，按 9.3 的六维表打分：它更适合编排还是编舞？
2. 该流程需要「回滚已做过的事」吗？如果需要，补偿的顺序与幂等怎么保证？
3. 你们现在有几种自研的「流程状态机」？它们能不能被成熟工作流引擎替代？
4. 编舞的流程里，一个订单卡住了你怎么查？需要多久？能否用流程挖掘改善？
5. 如果要把一个 AI 多步流程做成可靠服务，你会用哪种工作流能力？为什么？
