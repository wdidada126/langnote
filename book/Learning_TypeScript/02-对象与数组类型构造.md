## 核心机制

- **对象类型=形状描述，不是类**：`type Point = { x: number; y: number }` 说的只是
  「有这两个属性」。✅ 实测：`{ x:0, y:0, z:99 } as Point` 运行时 `Object.keys` 得
  `[ 'x', 'y', 'z' ]`——多余属性活得好好的，「多余属性检查」纯粹是**字面量直赋瞬间**的
  编译期规则，过一道手就失效。
- **属性修饰全在类型层**：`?`（可选）、`readonly` 只约束编译器。✅ 实测：可选属性
  `o.a` 读作 `undefined` 且 `'a' in o === false`——所谓「可选」运行时就是「键不存在」，
  无任何标记留存。
- **数组是普通 JS 数组**：`number[]`/`Array<number>` 只是泛型写法差异（Ⅳ 段再会）；
  元组 `[number, string]` 运行时与数组同形（✅ 旁证：专题档实验 A 里 `f.length` 等反射
  事实不因类型注解改变）。✅ 实测：`nums.push("sneaked in" as never)` 后
  `number[]` 打印 `[ 1, 'sneaked in' ]`，length=2。
- **与名义类型系对照**：Java 里 `Point` 是类，实例带着 Class 元数据，`instanceof` 有运行时
  真身；Kotlin `data class Point` 还白送 `equals/hashCode/copy`。TS 的对象类型三者皆无：
  **形状相同即同一类型，相等性要自己造**（专题档推论 5）。Java 读者的心智要把「定义形状」
  从「造一个类」重写成「登记一条编译期检查规则」。

## 批判读法

- 入口书用大量生活化例子（书本/唱片目录之类 ⚠️ 印象）教形状写法，但对「字面量直赋才有
  多余属性检查」这条反直觉规则的例外面着墨少——建议自建记忆判词：**EPC 是新鲜度检查不是
  结构检查**。⚠️ 口径归纳。
- `Record`/索引签名在本段可能一闪而过，真正威力在 Type-Level TS 谱系才展开，此处只需
  认字不必深究。⚠️。
- 数组 vs 元组的取舍（何时该用元组建构返回值）在原书偏保守，工程圈对「二元组返回值」的
  可读性争议更大，读到别处谱系再校正。⚠️。

## 🔧 微实验

- 🔧（未实测）EPC 绕过矩阵：`const p: Point = { ...literal }`（报错）vs 先赋中间变量再转

## 中英对照表

| 中文 | 英文 | 一句定义 |
| --- | --- | --- |
| 对象字面量类型 | object literal type | 用 `{ a: T }` 语法直接描述形状，无对应运行时构造 ✅。 |
| 多余属性检查 | excess property check (EPC) | 仅字面量直赋瞬间触发的编译期规则 ✅运行时不拦。 |
| 可选属性 | optional property | `a?: T`；运行时即「键可不存在」✅实测。 |
| 只读属性 | readonly property | 编译器禁写；`Object.freeze` 才是运行时真墙 ⚠️未实测。 |
| 元组 | tuple | 定长+按位类型的数组写法；运行时就是普通数组 ⚠️推断面。 |
| 索引签名 | index signature | `[key: string]: T` 形状级「字典」，Record 的底层。 |
| 类型别名 | type alias | `type X = ...` 给形状起名；纯编译期，零痕迹 ✅。 |
