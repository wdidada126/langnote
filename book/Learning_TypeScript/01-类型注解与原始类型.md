## 核心机制

- **注解是期望，不是断言**：`let count: number = 1` 里的 `number` 是写给编译器的契约，
  运行时不存在任何守护。✅ 实测：把 string 赋进 `number` 变量，strip-types 照跑不误——
  `after unguarded reassign: a string living in a number slot typeof: string`。
- **原始类型直接继承 JS 的地形**：`string/number/boolean/null/undefined/bigint/symbol`，
  TS 不改写运行时。✅ 实测：`typeof NaN = "number"`、`typeof null = "object"`、
  `Number.isNaN(NaN) = true`——JS 老坑原样带进 TS，类型层反而给你补救面（字面量类型、
  类型收窄），但补救全在编译期。
- **推断优先于书写**：`const x = "a"` 推成字面量类型 `"a"`，`let x = "a"` 推成 `string`——
  这条「let 加宽、const 锁死」规则是全书后续收窄/判别联合的地基。⚠️ 书内口径凭记忆。
- **与名义类型系的对照（本系列第一处思维切换）**：Java 的 `int i = 1; i = "s"` 被 JLS 在
  赋值点用运行时类型体系拦下且 `i` 的槽位永远刻着 `int`；Kotlin 同理，`val`/`var` 的类型
  活在字节码签名里。TS 的注解在 ✅ 实验 A（专题档）中证明运行时零痕迹——**声明不创建约束，
  声明只是给检查器看的说明书**。Java/C++ 读者的旧直觉「声明=分配了类型的形状」必须降级为
  「声明=登记了一条编译期期望」。

## 批判读法

- 本书对 `any` 的危害只温和提醒（入口书定位使然）；从 Effective TypeScript 谱系回看，
  `any` 是「局部关闭类型检查」而非「一种类型」，读 Ⅰ 段时就该自建这条判词。⚠️ 口径归纳。
- `unknown` 与 `any` 的差别在入口书着墨少，但它是后续收窄语法的入口钥匙，建议读到
  Ⅲ 段回头补一遍。⚠️。
- 字面量类型（literal types）在本段出现但动机后置（为判别联合服务），第一遍读会觉得
  「为什么 number 还不够」——这是结构安排，不是你的问题。⚠️ 印象。

## 中英对照表

| 中文 | 英文 | 一句定义 |
| --- | --- | --- |
| 类型注解 | type annotation | `: T` 形式的编译期期望，运行时零痕迹 ✅。 |
| 原始类型 | primitive type | JS 的 string/number/boolean 等不可再分的值类型。 |
| 字面量类型 | literal type | `"a"`/`42` 这类把具体值当类型，收窄与判别的原料。 |
| 类型推断 | type inference | 不写注解时由初值定类型；const 锁字面量、let 加宽 ⚠️。 |
| 断言 | type assertion | `as T`：向编译器撒谎，运行时不转换不检查 ✅机理。 |
| 擦除 | erasure | 类型层语法编译期全数剥除；TS 系零留存。 |
| 逃逸舱 | escape hatch | `any`/`as`/`@ts-ignore` 三件套，检查的人为豁免口。 |

⚠️ 欠账：逐字章名与节次目录；`any`/`unknown` 相关条目在原书的确切位置；tsc 报错矩阵未实测。
