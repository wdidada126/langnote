# 第 11 章 系统原则与发行包制作 / 第 12 章 发行包升级

> **一句话**：第 11 章把一堆"能开多少 ETS 表、能不能启动就加载模块、心跳断了怎么办"的系统级旋钮摊开给你，第 12 章教你**在不换进程状态的前提下换掉整个系统的代码**——这两章是 OTP 区别于其他运行时的地方。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 系统原则与限制 | ETS 表数上限、进程数上限、code path、加载模式 | 限制不是"用来卡你的"，是**容量规划的边界** |
| 嵌入式 vs 交互式 | embedded（启动时加载全部模块）vs interactive（按需加载） | 生产必须 embedded：模块缺失就崩，而不是等到第一次调用 |
| `rel` 文件与 `systools` | `.rel` 声明应用与运行时版本 → 自包含目录 | release = 虚拟机 + 应用 + 代码，**自带故障域边界** |
| `rebar3` 与 `relx` | 社区构建工具 | `rebar3 release` 是今天的标准做法 |
| `heart` 看门狗 | 心跳与自定义脚本、升级判定 | `heart` 是"节点级 supervisor"，脚本决定"重启还是换机" |
| 代码加载与热升级 | 换 `.beam`、旧代码保留期 | 热升级的前提是**进程状态与代码解耦** |
| 应用升级脚本（`appup`） | 模块级升级指令 | 只换自己写的模块时 `appup` 足够 |
| 发行包升级（`relup`）与 release handler | 应用 + **运行时**一起升级 | `relup` 是"连虚拟机一起换"的唯一途径 |
| 分布式环境下的升级 | 节点间版本不一致的窗口 | 滚动升级的旧节点可能不兼容新代码 |
| 数据库 schema 变更 | 结构变更与升级脚本 | **最难的部分永远在数据结构，不在代码** |

## 核心精讲

> 以下片段均为**教学示意代码，不参与编译、不参与任何构建**。

```erlang
%% ---- 1) 系统限制与运行时信息：容量规划的输入 ----
%% 常见旋钮（命令行或 vm.args）：
%%   +P 65536                 %% 最大进程数
%%   +E 256                   %% 最大 ETS 表数（历史问题：表太多会拖慢 name lookup）
%%   -kernel sync_threads_qlen 4096
%%   -kernel inet_dist_use_interface {192,168,1,10}

erlang:system_info(procs).        %% 当前进程数
erlang:system_info(ets_limit).    %% ETS 表相关上限
erlang:system_info(schedulers).   %% 在线调度器数

%% ---- 2) rel 文件：声明"这 releases 由哪些东西组成" ----
%% my_release.rel
%%   {release, {"my_release", "1.0.0"}, {erts, "26.2.5"},
%%    [{kernel, "10.2.3"},
%%     [stdlib, "6.0.1"],
%%     [sasl,       "4.0.1"],
%%     [crypto,     "5.2.1"],
%%     [ssl,        "12.1.2"],
%%     [my_app,     "1.0.0"]]}.

%% systools 用它生成自包含目录；今天多数团队直接用：
%%   rebar3 release
%%   rebar3 tar
```

```erlang
%% ---- 3) heart：节点级看门狗 ----
%% 启动时加 -heart，并配置 heart 脚本
%% heart 定期发心跳；连续未应答 → 触发脚本
%%   脚本里决定：只重启 Erlang（heart -shutdown ...）还是整机重启
%%   heart 默认会读 heart.beam 所在目录的 heart 可执行/脚本
%% 关键：**脚本要能看历史重启次数**，否则会陷入"无限重启循环"

%% ---- 4) 热代码升级的最小形态 ----
%% 旧版本进程手里握着 {module, old_vsn} 的函数引用 → OTP 保留旧代码直到进程消亡
%% 所以升级的正确姿势是：
%%   (a) 新代码模块先加载
%%   (b) 把进程状态**迁移**到新格式（code_change/3）
%%   (c) 让旧进程自然消亡（监督树重启 → 跑到 init/1 的初始状态）

%% appup 指令示例（只换自己模块时的常用写法）
%%   {VsnOld, VsnNew,
%%    [{add_module,  my_mod},
%%     [{delete_module, my_old_mod}, {module, my_mod}]}]}

%% relup 中负责"停旧簇/跑指令/起新簇"的那一段（语义上的三段）
%%   {apply, {application, stop,  [my_app]}}   %% 停
%%   {apply, {my_app_mod, up, ["1.0.0", "1.0.1"]}}  %% 升
%%   {apply, {application, start, [my_app]}}   %% 起
```

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| OTP 18/19（2014–2015） | 原书基线：`systools` 与 `relx` 仍是发行包主力工具 |
| OTP 21（2017） | `rebar3 release` 的标准化让 `relx` 退居二线；容器化开始进入部署流程 |
| OTP 22（2018） | `rebar3` 3.0 时代，release 与 `hex` 依赖树更紧密 |
| OTP 24（2020） | JIT 默认启用后 release 的体积与启动时间权衡需要重新测量 |
| **OTP 26（2022）** | **`erts_internal` 大量函数与调用被移除（潜在不兼容）**——依赖私有 API 的 release 升级会踩坑；**JIT 默认加 `-fno-omit-frame-pointer`，`perf` 等工具能抓到 BEAM 进程栈**；`argparse` 模块出现 |
| OTP 27+（2023–2026） | release 与容器镜像/编排（k8s 的 readiness/liveness）结合进一步深化；`heart` 多模式时间（`multi_time_warp` 在 OTP 26 默认开启）影响升级窗口内的时间语义 |

## 近年研究与工业界开源实践（2015–2026）

趋势：**热代码升级从"日常操作"退化为"紧急手段"**。2015 年之后，团队更倾向于"进程短命 + 监督树重启 + 滚动发布"，把 `appup`/`relup` 留给"确实不能停"的子系统。同时构建与交付方式从目录/ tar 变成容器镜像，"release" 的边界被 k8s 的 Deployment 接管。

## 常见误区与本书需修正之处

| 现象 | 说明 | 现状 / 修正 |
| --- | --- | --- |
| 🔧 **把 ETS 表数上限（`+E`）当成性能旋钮** | 表太多会拖慢**进程注册表与名称查找**这类全局结构，不只是内存 | 按功能聚合表；不要为每个请求建表 |
| 🔧 **生产用 interactive 模式** | 交互式按需加载会导致"某个模块第一次被调用时才炸" | 生产必须 embedded：启动即加载，缺模块立刻失败 |
| 🔧 **升级后没有跑过一次完整回滚演练** | `appup`/`relup` 的指令只在真实走一遍时才暴露问题 | 上线前在预发跑一次"升→降→再升"；失败路径（`prePurge`/`postPurge`）也要测 |
| 🔧 **滚动升级期间节点版本不一致** | 旧节点调用新节点的 `{nodedown, Node}` 与新协议会互相不认识 | 保证新旧版本**双向兼容**（协议里带版本号 + 兼容分支），或从"可容忍旧节点"的一侧开始升级 |
| 🔧 **`heart` 陷入无限重启循环** | 心跳失败就重启，重启又失败，节点永远起不来 | heart 脚本要能读历史重启次数，超出阈值就换整机/摘流量 |
| **schema 变更写进 `appup` 就算完成** | 数据结构的历史数据不会自动迁移 | 用补偿任务逐步迁移；必要时双写（详见 `09-` 的"数据共享"） |
| 🔧 **`erts_internal` 的私有调用在 OTP 26 后失效** | 自 OTP 24 起预告、OTP 26 大量移除 | 依赖它的库必须升级；业务代码不要依赖 erts 内部接口 |
| 🔧 **release 与容器镜像"两套事实"** | `rebar3 release` 的产物与 Dockerfile 安装的 OTP 版本不一致 | 一个工具链出产物；镜像里只放运行时与配置 |

## 与其他章 / 其他书的联系

- 前序：`07-` 的 application 在这里被打包成可部署、可升级的整体。
- 后续：`09-` 让这个整体跨节点运行，`10-` 负责运维与监控。
- 与 `book/多处理器编程的艺术2/`：艺术版没有任何"升级"概念，因为共享内存状态升级比消息传递更难；这正是**消息传递路线的一项隐藏红利**——进程状态随进程消亡，升级时往往只需重置。
- 与 `book/C++并发编程实战2/`：C++ 侧没有热升级，升级必须重启；这也是 Erlang 在高可用场景下的结构性优势。
- 与 `book/Java并发编程之美/`：Java 侧热部署（如 Spring Boot 重启 Context）是"伪热升级"，与 `relup` 的可控指令相比仍显粗糙。
