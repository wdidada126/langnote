# 第 9 章 应用程序与第 10 章 特殊进程与自定义行为

> **一句话**：第 9 章讲"**OTP 运行时如何找到并拉起你的进程**"（`.app` 文件 + application controller），第 10 章讲"**反过来：你如何自己实现一套 behaviour**"——前者是接入，后者是理解一切 OTP 抽象的钥匙。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 应用程序如何运行 | application controller、boot 序列、`.app` 清单 | 应用是**依赖 + 顶层 supervisor** 的打包单位 |
| 应用结构 | `vsn`、`applications`、`mod`、`.app` 文件字段 | `applications` 声明依赖顺序；漏了依赖会在 boot 时炸 |
| 回调模块 | `-module(my_app). -behaviour(application)` | `start/2` 返回 `OkPid` 才叫"启动成功" |
| 应用程序与代码升级 | 应用是升级的最小单元 | 升级一个应用 = 换一批模块 + 跑升级脚本 |
| 特殊进程的设计规则 | 为什么有些进程可以直接进监督树 | 特殊进程 = 手写但遵守协议的进程 |
| 手写一遍 `gen_server` | 从 `proc_lib` 到消息循环到 `sys` 兼容 | **读懂 behaviour 的最好方式是照着抄一遍** |
| 事件处理与运行时/代码集成 | 特殊进程如何参与 trace 与系统消息 | 漏掉系统消息转发 = 与 OTP 生态脱钩 |
| 自定义行为的取舍 | 什么时候不该自己写 behaviour | 用标准 behaviour 的收益远大于抽象自由度 |

## 核心精讲

> 以下片段均为**教学示意代码，不参与编译、不参与任何构建**。

```erlang
%% ---- 1) application 回调：返回值决定"启动成功"的语义 ----
-module(my_app).
-behaviour(application).
-export([start/2, stop/2]).

start(_StartType, StartArgs) ->
    case my_top_sup:start_link(StartArgs) of
        {ok, Pid}      -> {ok, Pid};            %% 顶层 supervisor 的 pid
        {error, Reason}-> {error, Reason};      %% application controller 据此判定失败
        ignore         -> ignore
    end.

stop(_Reason, _State) -> ok.                    %% 有 start 就该有 stop
```

`.app` 清单的关键字段（"应用如何被找到"）：

```erlang
%% my_app.app
{application, my_app,
 [{description, "my service"},
  {vsn, "1.0.0"},
  {registered, [my_top_sup]},
  {mod, {my_app, []}},                         %% application callback
  {applications, [kernel, stdlib, sasl]},      %% **依赖声明，决定启动顺序**
  {env, [{port, 8080}]},
  {modules, [my_app, my_top_sup, my_worker]}]}.
```

```erlang
%% ---- 2) 特殊进程：手写但遵守"协议" ----
%% 规则 1：用 proc_lib 启动（这样父进程/监督者才知道它起来了没）
%% 规则 2：trap_exit（需要接收退出信号时）
%% 规则 3：把系统消息交给 sys / proc_lib 处理
%% 规则 4：任何模式下都不做"不可恢复"的动作（否则重启无意义）

-module(my_special).
-export([start_link/0, init/1]).

start_link() ->
    proc_lib:start_link(?MODULE, init, [self()], [{compiler_trace, true}]).

init(Parent) ->
    process_flag(trap_exit, true),
    proc_lib:init_ack({ok, self()}),            %% 告诉"父进程"：我起来了
    loop(Parent, #{}, []).

loop(Parent, State, Msgs) ->
    receive
        {From, Tag, Req} -> handle_call(From, Tag, Req, State);
        {'EXIT', P, R}   -> handle_exit(P, R, State);
        {system, From, Req} ->
            sys:handle_system_msg(Req, From, none, none, State, ?MODULE),
            loop(Parent, State, Msgs);
        Other -> loop(Parent, State, [Other | Msgs])
    end.

%% 若没有这一行，`sys:get_state/1` 之类的调试手段全部失效
handle_system_msg(Msg, From, Parent, Name, State, Mod) ->
    sys:handle_system_msg(Msg, From, Parent, Name, State, Mod).
```

```erlang
%% ---- 3) 自定义 behaviour：把"骨架"抽象出来 ----
-module(my_counter).
-export([behaviour_info/1]).                     %% OTP 21+ 用 -behaviour + callbacks 属性，但仍兼容旧式

behaviour_info(callbacks) ->
    [{init, 1}, {handle_count, 2}, {terminate, 2}];
behaviour_info(_) -> undefined.
```

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| OTP 18/19（2014–2015） | 原书基线：`.app` 字段、`application` 启动语义、手写 behaviour 的旧式 `behaviour_info/1` |
| OTP 21（2017） | `-behaviour`/`-callback` 属性成熟；同一进程的回调类型可以更精确（`-callback` + `-optional_callbacks`） |
| OTP 24（2020） | `proc_lib` 与 `gen_server:call` 改用进程别名；启动期的失败暴露更早 |
| **OTP 26（2022）** | **`proc_lib:start*` 在子进程失败时变为同步失败**；要求失败路径显式调用 `proc_lib:init_fail/2,3` 或干脆退出；`erts_internal` 大量移除，手写进程的私有内部 API 需要重新自查 |
| OTP 27+（2023–2026） | `application` 与容器化/集群编排（如 `libcluster`）的组合成为主流形态 |

## 近年研究与工业界开源实践（2015–2026）

趋势：应用的**打包方式**在 2015 年之后经历了"rel → OTP release → 容器镜像"的转变；`rebar3` 的 release 仍然可用，但生产里更常见的是"一个 release 一个容器 + 外部编排负责重启"。同时 **"自定义 behaviour" 的需求下降**——社区更倾向用 `gen_statem` 与干脆不用行为，因为抽象成本难以摊销。

| 仓库 | star | 说明 |
| --- | --- | --- |
| `erlang/otp` | **12337★** | `application`、`proc_lib`、`sys` 的实现；`init_fail/2,3` 的出处 |
| `erlang/rebar3` | **1819★** | `rebar3 release` 把 application 编成可部署单元 |

## 常见误区与本书需修正之处

| 现象 | 说明 | 现状 / 修正 |
| --- | --- | --- |
| 🔧 **`proc_lib:start*` 的启动失败语义变了** | OTP 26 起它在子进程失败时是**同步失败**，且要求失败路径显式 `init_fail/2,3` 或直接退出 | 手写特殊进程（含测试里的 `proc_lib` 用法）需要检查失败分支 |
| 🔧 **忘了 `proc_lib:init_ack/1`** | 父进程会一直等，直到超时或崩溃 | 启动路径上成功与失败两侧都要有明确反馈 |
| 🔧 **手写进程不转发系统消息** | 一旦漏掉 `{system, From, Req}`，`sys`/`dbg`/`Observer` 全都失效 | 明确调用 `sys:handle_system_msg/6`；原书只在末尾一句话带过 |
| 🔧 **`.app` 里的 `applications` 写不全** | 依赖顺序错了，boot 时才炸；容器化后更常见（镜像里少了 SASL 等应用） | 依赖列表按实际使用复核；release 与容器镜像要一致 |
| **`start/2` 返回 `{ok, Pid}` 才成功** | 常见误读：返回 `ok` 会被当成别的语义 | 返回 `{ok, Pid}`；失败返回 `{error, Reason}`，想跳过返回 `ignore` |
| 🔧 **自定义 behaviour 变成万金油** | 抽象成本难以摊销，且回调签名会随业务演化漂移 | 优先标准 behaviour；确需自定义时限定回调集合并用 `-optional_callbacks` |
| **把"特殊进程"当成"绕过 OTP 的捷径"** | 不遵守协议的特殊进程是运维黑洞 | 特殊进程的唯一价值是"标准 behaviour 做不到"的情况（如需要精细控制启动时序） |
| 🔧 **`behaviour_info/1` 的旧式写法** | OTP 21+ 推荐 `-callback` 属性；旧式仍在但不再是主流 | 新代码用 `-behaviour` + `-callback` |

## 与其他章 / 其他书的联系

- 前序：`06-` 的顶层 supervisor 需要被"谁启动"——就是本章的 application。
- 后续：`08-` 把 application 打包成发行包并升级。
- 与 `book/多处理器编程的艺术2/`：艺术版 Ch6 讲"通用构造"（把任意并发对象用共识实现）；**自定义 behaviour 是运行时层面的通用构造**，区别在于它复用的是 BEAM 的进程语义而非内存语义。
- 与 `book/C++并发编程实战2/`：C++ 里"骨架 + 回调"要用模板或虚函数手写，`std::function` 是常见替代；Erlang 把它做成语言级约定。
- 与 `book/Java并发编程之美/`：Java 的 SPI / ServiceLoader 在"接入方式"层面与 application 相似，但缺少"依赖顺序 + 生命周期"的强制约束。
