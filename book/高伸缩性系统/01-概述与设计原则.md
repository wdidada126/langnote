# 第 1 章 概述与设计原则

> **一句话**：第 1 章先把"伸缩"这个词从直觉里拆出来（并发 ≠ 并行，伸缩 ≠ 更快），再给出 OTP 的四层拼图（语言、工具库、行为抽象、设计原则），最后把"让失败成为常态"写进设计要求。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 定义问题 | 并发（concurrency）与并行（parallelism）的区别；伸缩的定义；Amdahl / Gustafson / 贝尔定律 | 并发是**结构属性**（谁和谁同时存在），并行是**执行属性**（同一时刻几条指令在跑）；伸缩是"**加资源后吞吐/延迟是否可预期地变化**"，而不是"变快了" |
| OTP | 什么算 OTP：语言 + 运行时 + 库 + 设计原则 | OTP 不是一堆库，而是**一套把并发、崩溃、升级都规范化了的工程约定** |
| Erlang | 进程抽象、不可变数据、表达式即一切 | 进程是**成本极低**的并发单元；数据不可变是消息传递安全的地基 |
| 工具和库 | `rebar3`、`hex`、`Observer`、`appmon`、`debugger` 等 | 生态工具决定"能不能在生产上活着"，作者用整本书讲如何用它 |
| 系统设计原则 | 失败即正常（let it crash）、进程隔离、接口优先、按领域切进程 | **设计原则比 API 更重要**；OTP 的价值在于它逼你把原则写进结构 |
| Erlang 节点 | `node`、`.app`、节点即可部署单元 | 一个节点 = 一个独立的故障域与升级单元 |
| 分布式、基础设施、多核 | 网络必然不可靠、多核与调度器 | "网络分区是常态"是后面 13–15 章的前置结论 |

## 核心精讲

> 以下片段均为**教学示意代码，不参与编译、不参与任何构建**。

```erlang
%% 并发与并行的区别：同一份工作，两种写法
%% 左：并行 —— 一次只做一个（同一进程，非尾递归，会撑爆栈）
%% 右：并发 —— 多个独立活动体，结构上是"同时存在"的
parallel([]              -> 0;
parallel([H | T])       -> H + parallel(T).          %% 不能并行，顺序依赖

concurrent(N) ->
    Parent = self(),
   lists:foreach(fun (I) ->
                      spawn(fun () -> Parent ! {done, I, I * I} end)
                  end, lists:seq(1, N)).              %% 结构上的并发
```

伸缩判据的最小模型（Amdahl 的串行分数 $s$，核心数 $n$）：

$$S(n) = \frac{1}{s + (1 - s)/n}$$

```erlang
%% Amdahl 上限：串行部分 s 决定天花板
amdahl_limit(SerialFraction) -> 1 / SerialFraction.   %% n -> ∞ 时

%% Gustafson 视角：问题规模随 n 增长，串行分数不变
gustafson(N, SerialFraction) -> N - (N - 1) * SerialFraction.
```

OTP 的四层拼图，用一行"启动整棵应用树"来说明"库 + 行为 + 原则"是怎么合起来的：

```erlang
%% application controller 按 .app 声明的依赖顺序启动顶层 supervisor
%% 开发者代码只写两样东西：一个 top-level supervisor 的 spec，一个回调模块
-module(my_app).
-behaviour(application).
-export([start/2, stop/2]).

start(_StartType, _StartArgs) ->
    my_top_sup:start_link().                          %% 其余交给 OTP
```

"失败即正常"在工程上の最小表达——**不要写 `try/catch` 去保住一个已经不该活着的进程**：

```erlang
%% 反例：在函数里吞掉异常，进程活着但状态已经坏了
%% 正解：让它崩，交给 supervisor 重启（见 06-监督者与容错策略.md）
```

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| OTP 18/19（2014–2015，本书基线） | `application` 与 `release` 的基础形态固定；`appmon` 曾用于观察监督树 |
| OTP 21（2017） | 调度器 SMP 默认开启——"多核就得考虑分布"这件事不再靠参数切换 |
| OTP 24（2020） | BeamAsm JIT 默认启用，"换更强的机器就更快"这条垂直伸缩假设获得一波红利 |
| OTP 26（2022） | 本地 pid/port 标识符有效位 28 → 60 位，**理论上不再节点内复用**；`proc_lib:start*` 失败时同步失败，启动期语义更"确定" |
| OTP 27–29（2023–2026） | `maybe_expr` 默认启用、Dialyzer 增量模式；作者写"设计原则"时用到的工具链进一步轻量化 |

## 近年研究与工业界开源实践（2015–2026）

## 常见误区与本书需修正之处

| 现象 | 说明 | 现状 / 修正 |
| --- | --- | --- |
| 🔧 **"并发即并行"的旧解** | 第 1 章把并发描述为"多个独立活动体"，容易被初学者读成"多核并行" | 补充：BEAM 是**单进程多线程**的运行时（scheduler 线程 + 进程），并发 ≠ 并行；并行要靠多核调度或跨节点 |
| 🔧 **Amdahl 的适用边界** | 书中引用 Amdahl 时暗示"串行部分固定" | 按 Gustafson 与 Ahmad 的批评：在伸缩场景下串行分数常随规模变化，应同时给出两条曲线 |
| 🔧 **"垂直伸缩最简单"的经验值** | 2016 年的机器与今天差距很大，JIT 与内存带宽改变了成本曲线 | 补充：OTP 24 起 JIT 默认开启，单节点吞吐提升明显；但"换大机器"仍不解决单点故障，最终仍要回到水平伸缩（`10-` 章） |
| **把 OTP 当成四个独立部件** | 读者常跳过"设计原则"直接抄 `gen_server` | 原则是本书真正的骨架，见 `06-` 章；`behaviour` 只是它的固化形态 |
| **把"节点"当成"机器"** | `node` 与物理机不是一回事，一个容器/容器组里可能跑多个节点 | 补充：容器化后节点更轻，但 `net_kernel` 的分区与重启代价没有变小 |
| **忽视"网络必然失败"这条前置结论** | 第 1 章点到即止 | 展开在 `09-` 与 `10-` 章 |

## 与其他章 / 其他书的联系

- 前序：**本书开篇**；后续 `02-` 讲进程与消息传递，`06-` 讲失败即正常的落地形态。
- 与 `book/多处理器编程的艺术2/`：**艺术版 Ch1 的 Amdahl/Gustafson 讨论与本章同宗**，但艺术版用"共享内存上的并行效率"立论，本书用"消息传递上的系统结构"立论——这正是**消息传递 vs 共享内存**这条主线的两个端点。
- 与 `book/C++并发编程实战2/`：后者第 8 章讲 Amdahl 与并行算法，与本章公式同源；差异在于 C++ 侧要**显式**把并行压进共享地址空间。
- 与 `book/Java并发编程之美/`：Java 侧第 1 章讲线程与状态机，可对照"为什么 Java 需要线程池兜住线程成本，而 Erlang 不需要"。
