# 第 13 章 分布式架构与第 14 章 永不停止的系统

> **一句话**：第 13 章把节点连起来并回答"服务该怎样被拆开"，第 14 章回答更狠的问题——**当分区、丢包、时钟漂移都是常态时，你的系统凭什么还在使用者的感知里"活着"**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 节点类型与家族 | 前端节点 / 后端节点、节点家族与命名 | 先按"职责"切节点，再按"负载"切进程 |
| 联网与分布式 Erlang | `net_kernel`、EPMD、消息透明发送 | 分布式 Erlang 让"加个节点"变得容易，也让"误用"变得更容易 |
| 套接字与 SSL | `gen_tcp`/`ssl`、证书与 TLS 1.3 | 真正的安全边界在**传输层与身份**，不在消息格式 |
| 面向服务与微服务架构 | SOA 与微服务在 OTP 里的落法 | 一个节点就是一个服务的最小实现 |
| 点对点与接口 | P2P 拓扑、接口设计 | 拓扑决定故障传播路径；接口决定耦合度 |
| 可用性、容错、弹性、可靠性 | 四个词被混用，需要严格区分 | **可用性** = 是否可服务；**容错** = 失败时不扩散；**弹性** = 退化到能用；**可靠性** = 长时间不出错 |
| 数据共享 | mnesia/EETS/ETS 与"谁拥有数据" | 没有归属的数据必然在分区时产生分歧 |
| 一致性与可用性的权衡 | CAP/PACELC 与工程取舍 | 权衡不是"选 CAP 里的 P"，而是"在分区时选哪边" |
| 系统与运维的联动 | 分区后的自愈与人工介入 | "永不停止"是设计出来的，不是运维出来的 |

## 核心精讲

> 以下片段均为**教学示意代码，不参与编译、不参与任何构建**。

```erlang
%% ---- 1) 跨节点调用的两副面孔 ----
%% 同一条消息，本地与远程写法一致 —— 这正是危险所在
Pid ! {request, self(), body}.                 %% 本地 / 远程一致
rpc:call(Node, mod, fun, [Arg]).               %% 明确远程（OTP 23+ 用 erpc 更好）
erpc:call(Node, mod, fun, [Arg]).              %% 能区分返回值 / 抛出 / 错误

%% OTP 23+：分布式 spawn 更快；erpc 替代 rpc（区分异常与错误，性能更好）
SpawnRef = spawn_monitor(Node, fun work/0).

%% ---- 2) 分区期间的一致性取舍（最小状态机）----
%% 两个分区各自接受写入 → 需要一个"冲突解决"层
%% 常见做法：最后写入胜出（LWW）+ 显式冲突日志，而不是假装没分歧
write_with_conflict(Key, Val, TS) ->
    case read(Key) of
        {ok, #{ts := OldTS, val := OldVal}} when OldTS > TS ->
            {conflict, OldVal, Val};          %% 记录分歧，而不是静默覆盖
        _ -> store(Key, #{ts => TS, val => Val})
    end.

%% ---- 3) 共享状态的所有权 ----
%% 反例：多个节点都读写同一张 public ETS 表 → 分区后无法仲裁
%% 正解：数据只由"该节点的 owning process"写入，其他节点走消息
call_owner(Node, Key, NewVal) ->
    RPC = rpc_call(Node, key_server, write, [Key, NewVal]),
    RPC.
```

四个"ility"的判定口径（本章最重要的一张对照）：

```erlang
%% 可用性   Available：此刻能不能响应（外部视角）
%% 容错     Fault tolerance：失败被限制在局部（内部视角）
%% 弹性     Graceful degradation：资源耗尽时退化到"少做一点"，而不是全崩
%% 可靠性   Reliability：在**长期连续运行**中不退化（内存/句柄/堆泄漏都算破功）
%% 四者的关系：可靠性是其余三者的时间积分 —— 跑得越久，差异才暴露
```

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| OTP 18/19（2014–2015） | 原书基线：EPMD 是节点名解析的必需项；分布式 Erlang 的默认形态 |
| OTP 21（2017） | 调度器 SMP 默认开启，跨节点与本机性能差距的**衡量方式**改变 |
| OTP 23（2019） | **可以不依赖 EPMD 跑分布式**（`-dist_listen false`、`-erl_epmd_port`）；`erpc` 模块引入；`pg` 上位替代 `pg2` |
| OTP 24（2020） | 分布式 TLS 握手可并发；TLS 1.3 进入默认支持列表 |
| OTP 25（2021） | 默认使用新的外部项格式与新链接协议（OTP 23.3 起引入），节点间兼容性门槛提高 |
| **OTP 26（2022）** | **V4 node container types 与新链接协议成为必需**；本地 pid/port 标识符有效位 28→60 位（节点内不再复用，分区/重连后更不易撞车） |
| OTP 27+（2023–2026） | 节点自动发现与编排（DNS / k8s）成为主流，Erlang 分布式更多被包在 Service Mesh 之后 |

## 近年研究与工业界开源实践（2015–2026）

趋势：2015 年之后 Erlang 分布式的**部署形态彻底改变**——节点从"机房里的固定机器"变成"容器编排下的动态实例"，这让"节点名稳定性"与"成员管理"成为新的痛点；同时网格（mesh）级 mTLS 让 TLS 开销重新进入视野，OTP 24 起的并发 TLS 握手正是对症改进。一致性方面，工业界的共识是**在业务层做分歧解决**，而不是在存储层追求强一致。

## 常见误区与本书需修正之处

| 现象 | 说明 | 现状 / 修正 |
| --- | --- | --- |
| 🔧 **把"分布式 Erlang"当成"分布式透明"** | 原书讲的是"消息写法一致"，但网络失败会**以消息形式**出现，而不是异常 | 处处要考虑分区：`{nodedown, Node}`、`noproc`、超时；显式 `erpc` 优于隐式 `!` 跨节点 |
| 🔧 **CAP 被念成"三选二"** | 真正的取舍发生在**分区期间**（CA/P 之外的东西），并且还有"非分区时选延迟还是一致性"这一维（PACELC） | 用 Abadi 的 PACELC 重写本节结论 |
| 🔧 **"共享 ETS 表"被当成分布式存储** | `public` 表只在**本节点**可见；跨节点访问只能走进程 | 跨节点数据必须有 owner 进程与明确的冲突解决策略 |
| 🔧 **分区期间写入静默覆盖** | 两个分区各写各的，恢复后无法判断谁对 | 显式记录冲突（带时间戳/版本），或采用 `pause_minority`/`quorum` 之类的自愈策略 |
| 🔧 **节点名在容器里变得不可靠** | IP 变化 → 节点名变化 → 旧进程引用失效 | 用稳定的短名/域名 + 自动发现；OTP 23+ 可以不依赖 EPMD；节点名不要写死 |
| **把 SOA/微服务当成万能解药** | 微服务把进程边界推到网络边界，代价是延迟与故障放大 | 先在**一个节点内**切好进程与职责边界，再决定是否拆服务 |
| 🔧 **"永不停止"被理解为"永不重启"** | 恰恰相反：它要求可以随便重启（进程短命、无状态化） | 与 `06-` 的短生命期进程策略配套；重启是常规操作而不是事故 |
| 🔧 **TLS 只在"需要时"才关注** | 内网服务网格全面 mTLS 后，TLS 握手成为分布式延迟的主要来源之一 | 复用连接、开启 TLS 1.3（OTP 23+ 默认）、必要时做握手并发（OTP 24+） |

## 与其他章 / 其他书的联系

- 前序：`08-` 的 release 在这里被部署到多个节点上。
- 后续：`10-` 把伸缩与监控接上，是本章"弹性"的落地。
- 与 `book/多处理器编程的艺术2/`：艺术版 Ch5 讲共识数、Ch16 讲调度与工作分配；**共识（Raft/Paxos）与 Erlang 的"重启成初始状态"是两条完全不同的容错路线**——前者坚持数据一致，后者接受状态重置。
- 与 `book/C++并发编程实战2/`：C++ 侧没有"进程崩溃"这一层，崩溃往往是**进程级信号或内存破坏**；Erlang 把崩溃收敛成可管理的事件。
- 与 `book/Java并发编程之美/`：Java 侧常用"心跳 + 重试 + 幂等"对抗网络不确定性；Erlang 侧把这些做成 monitor 与监督树的默认行为。
