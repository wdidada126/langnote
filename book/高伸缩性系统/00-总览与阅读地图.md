# 《高伸缩性系统：Erlang/OTP 大型分布式容错设计》总览与阅读地图

> **一句话**：这是一本**站在核心设计者视角**讲 Erlang/OTP 的书——它不教你 `spawn/3` 怎么写，而是讲清楚「为什么 OTP 的行为（behaviour）长这样、监督树怎么分层、失败即正常（let it crash）如何变成一条工程纪律」，并给出伸缩、容错、不停机升级的完整取舍清单。

**大纲版在此**：`book/高伸缩性系统.md`（含完整中译目录；若该单文件不存在，则本目录是**唯一形态**。无论哪种情况，本目录都是**深度重写版**，与大纲版（如果存在）并存互链）。

## 3. 版本演进时间轴（本书成书 ⟶ 2026）

本书 2016 年成书、2018 年中译出版，对应的 OTP 是 18/19/20；到 2026 年已经走过 11 个大版本。下表只列**与本书主题直接相关**的演进（star / 版本行均为 2026-09 实测）。

| 年份 | OTP | 与本书相关的关键变化 |
| --- | --- | --- |
| 2014-04 | **18** | 本书成书时的基线；`erts` 调度器为对称多核（SMP）默认开启前的年代 |
| 2016-06 | **20** | `erts` 进程与端口的内存使用优化、`erlang:system_info` 补充；本书中译本对应世代 |
| 2017-06 | **21** | **从 OTP 21 起调度器默认 SMP 开启**（`+S` 参数的意义被弱化）；`erts` 引入 `erts_internal`，把内部能力显式暴露给内核应用 |
| 2018-06 | **22** | `write_concurrency` 对 `ordered_set` **首次生效**（此前无效）；`decentralized_counters` 首次为 `ordered_set` 提供 |
| 2019-06 | **23** | ETS 的 `insert/delete` 并发可扩展性覆盖全部表类型，`decentralized_counters` 默认随 `write_concurrency`；**移除 `scheduler_poll` 与 async I/O 的 dtrace/LTTng 探针**；新增 `erpc`（替代 `rpc`，分布式 spawn 更快）；`pg` 模块上位 |
| 2020-05 | **24** | **BeamAsm JIT 默认启用**；**选择性接收（selective receive）优化应用得更频繁**（`recv_opt_info`）；进程别名（EEP 53）；**supervisor 支持 significant children 与 `auto_shutdown`**（EEP 56）；24.2 起 dirty scheduler 的 allocator 可用 `+Mdai` 单独开启 |
| 2021-05 | **25** | ETS 的 `write_concurrency` 新增 **`auto`** 选项（约等于"自动决定要不要加锁拆分"）；`erts` 默认 `async` 写路径的观测手段进一步收缩 |
| 2022-05 | **26** | **选择性接收优化扩展到「reference 由别的函数返回」的场景**，`gen_server:send_request/3` 与 `wait_response/2` 因此大幅提速；`proc_lib:start*` 在子进程失败时变为**同步失败**；新增 `call_memory` trace；**`erts_internal` 大量函数与调用被移除**（潜在不兼容）；本地 pid/port 标识符的有效位从 28 位扩到 60 位 |
| 2023–2026 | **27 / 28 / 29** | 27 起 `maybe_expr` 默认启用；`dialyzer --incremental`、JIT 类型优化持续推进；调度器与 JIT 的改进使得本书中「靠 `+S` 和进程数量堆吞吐」的经验值需要重新标定 |

> 一句话总结：**本书讲的"设计原则"依然成立，但"性能经验值"部分已经过期**——ETS 的 `write_concurrency`、选择性接收优化、`supervisor` 的 `auto_shutdown`、`proc_lib` 的同步失败，都是 2018 年之后补上的新答案。每一章的「版本演进 + 常见误区」小节正是为补齐这些而写。

## 4. 与并发类书籍的分工

| 书 | 主线 | 与本书记什么 |
| --- | --- | --- |
| 本书 `book/高伸缩性系统/` | **消息传递 + 运行时治理** | 进程设计、监督树、行为抽象、不停机升级、容量与监控 |
| `book/多处理器编程的艺术2/` | **共享内存 + 正确性理论** | 线性一致性、共识数、MCS/CLH 队列锁、内存回收；用 Java 伪码。**两者正好是"消息传递 vs 共享内存"这条主线的两端** |
| `book/C++并发编程实战2/` | **语言与工程：标准库线程的正确用法** | `std::thread` / 内存序 / 无锁结构；关注"怎么把并发写对、写快" |
| `book/Java并发编程之美/` | **Java 线程与 JDK 实现** | 线程状态、线程池、锁与 AQS 源码实现 |

- 本目录与 `多处理器编程的艺术2` 的分工：**艺术版回答「并发算法为什么这样设计」（正确性、进展条件、共识下界），本书回答「一个 7×24 小时运行的系统该怎么组织进程与失败」（可运维性、伸缩、升级）**。想给本书的"失败即正常"找一个形式化地基，去看艺术版 Ch3（可线性化）与 Ch5（共识数）。
- 与 `C++并发编程实战2` 的分工：后者讲**同一进程内**如何共享数据不翻车；本书讲**进程之间**如何不翻车。锁与无锁是"把并发压进一个地址空间"的手段，而 Erlang 干脆不给共享内存——**这不是更聪明，而是把两个世界的问题换了一个层面解决，代价是消息拷贝与调度开销**。
- 与 `Java并发编程之美` 的分工：Java 侧需要**显式池化**线程（线程池、虚拟线程 JEP 444 之后有所缓解）；Erlang 侧进程极廉价，池化这件事被运行时隐藏了，代价是**你更容易不小心把进程当成"免费资源"滥用**（见 `03`、`06` 的误区小节）。

## 5. 本书刻意规避 / 未覆盖的缺口（2026 视角）

- **没有独立的性能章**：ETS/mnesia 选型、binary 内存、调度器 tuning 分散在 Ch2/Ch5/Ch15，缺少一张统一的性能检查清单。
- **没有独立的测试章**：`common_test` 只作为 `rebar3` 的一个子命令被顺带提及；属性测试（PropEr / QuickCheck）没有系统展开。
- **没有分布式数据库的实现细节**：本书讲"如何使用 mnesia / 如何设计数据共享"，但**不涉及 Riak/Redis/Cassandra 内部**；要补请看 `book/Design Data-intensive Applications.md` 与本目录 `09-` 的延伸。
- **没有跨语言互操作细节**：Ports（Erlang ↔ OS 进程）、NIF（C/ Rust ↔ BEAM）只触及"存在性"，没有 C++ 侧 ABI、异常穿越、回调线程模型（dirty NIF scheduler）的深度讨论。
- **没有 NIF 与调度器阻塞的工程规范**：OTP 24 之后 dirty scheduler 的 allocator 与"NIF 里做阻塞 IO"那条老建议（42 秒规则）值得单独成文。
- **没有可观测性的现代栈**：本书的"监控"止于 `fprof`/`eprof`/`Observer`/SASL；2015 年之后的 OpenTelemetry、`prometheus` exporter、`recon` 一类工具未被覆盖。
- **没有形式化验证**：`eqWAlizer`、`gradualizer`、以及基于 `sys_fsm` 的模型检验不在书内。

## 7. 跨语言对照表

| Erlang/OTP（本书） | Java | Go | Rust |
| --- | --- | --- | --- |
| `spawn/3`、进程（每进程独立堆、调度由 erts 抢占式完成） | `java.lang.Thread`（1:1 内核线程；**虚拟线程 JEP 444** 之后才接近"廉价"） | `go func()`，goroutine（用户态协程，M:N，GC 感知栈增长） | `std::thread`（OwnedThread/ScopedThread）；异步侧用 `tokio::task::spawn` |
| 进程间**只**通过消息传递（`!` / `receive`） | `wait/notify`、`CompletableFuture`、`Channel`（第三方） | **channel**（`chan` / `select`），语言级消息传递 | `mpsc::channel`；`tokio::sync` 系列 |
| `receive ... after` 超时 | `LockSupport.parkNanos` / `Future.get(timeout)` | `select` + `time.After` | `tokio::time::timeout` |
| `link`/`monitor` 与"崩溃即传播" | 无直接对等物（靠 `Thread.UncaughtExceptionHandler` + 自定义兜底） | 无直接对等物（`panic` 不跨 goroutine 传播） | `panic = abort`（通常不跨任务恢复） |
| `supervisor` + `max_restarts` 重启策略 | 无对等物（靠 `ExecutorService` + 自研重启器） | 无对等物（靠 `supervise` 类库） | 无对等物（靠 `tokio::spawn` 的失败即终止） |
| ETS（共享内存表、锁/计数器可调） | `ConcurrentHashMap`（分段/桶级 CAS） | 无内置；`sync.Map` 或自建 | 无内置；`dashmap` 等三方 |
| `persistent_term` | 接近静态字段 + 不可变读 | 接近包级 `var` | 接近 `OnceLock<T>` |
| BEAM 抢占式调度 + reduced reduction | JVM 安全点 + 线程时间片 | Go 抢占式调度（信号/async preemption） | tokio 工作窃取 + 协作调度 |
| 热代码升级（`.beam` 换模块） | 热替换基本没有（OSGI 只是近似） | 无 | 无 |
| OTP `release` 与 `appup` 升级 | 无 | 无 | 无 |

> **主线提醒**：Java/Go/C++ 世界里"共享内存 + 锁"是默认答案，Erlang 把这条主线**换掉**了；而 Rust 用所有权把共享进一步压缩到 `Arc`/`Mutex`，Go 用 channel 把消息传递做成一等公民——**三者的分歧点，正是本书反复强调"消息传递改变设计方式"的地方**。
