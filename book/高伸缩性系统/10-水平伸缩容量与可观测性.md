# 第 15 章 水平规模伸缩 / 第 16 章 监视与抢救性支持

> **一句话**：第 15 章把"加机器"变成一条可测的曲线（容量规划、瓶颈定位、背压），第 16 章补上最后一环——**当系统已经处于过载或故障状态时，如何主动降级而不是继续硬撑**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 水平伸缩 vs 垂直伸缩 | 加节点 vs 加资源 | 水平伸缩的代价是"一致性 + 会话 + 运维复杂度"，垂直伸缩的代价是"单点" |
| 容量规划 | 峰值倍率、增长曲线、资源余量 | 规划的输入不是 CPU，而是**瓶颈资源**（CPU / 内存 / 队列 / DB 连接） |
| 容量测试 | 压测方法与"测到什么为止" | 压测要测到**饱和点之后**，否则看不到拐点 |
| 平衡你的系统（负载均衡） | 轮询、最少连接、一致性哈希 | 负载均衡解决"谁去干"，不解决"干不过来" |
| 找寻瓶颈 | 逐层测量、Amdahl 的串行分数 | 先证明"瓶颈在别处"，再动手优化 |
| 系统蓝图 | 把吞吐/延迟/资源画成一张图 | 蓝图是容量讨论的共同语言 |
| 负载调节与背压 | 排队、丢弃、限流 | **背压是"系统对上游说不"的权利**，没有背压的系统会在上游侧崩 |
| 监视 / 日志 / 指标 / 警报 | 三层可观测性 | 指标用于告警，日志用于归因，追踪用于跨节点串联 |
| 抢救性支持（preemptive support） | 熔断、降级、feature flag | 主动"少提供服务"好过被动"什么都提供的烂服务" |

## 核心精讲

> 以下片段均为**教学示意代码，不参与编译、不参与任何构建**。

```erlang
%% ---- 1) 背压：用"超时 + 拒绝"向上传播压力 ----
%% 不做限流时，上游会一直灌，直到进程邮箱无界增长 → 内存爆
handle_request(From, Req) ->
    case queue:len(Pending) of
        N when N > 1000 -> %% 反压：明确拒绝，让上游自己减速
            From ! {error, overloaded};
        _ -> enqueue(From, Req)
    end.

%% 用 receive after 做"排队等待时间与是否值得等"的判据
wait_for_slot(Queue) ->
    receive
        {slot, Token} -> Token
    after 200 -> timeout
    end.

%% ---- 2) 熔断：下游持续失败就先别打了 ----
%% OTP 生态里的经典实现是 fuse 库（本章"抢救性支持"的具体形态）
%%   状态机：ok → blown（熔断）→ 冷却后 half-open（半开试探）
%%   触发条件通常是"连续 N 次失败"或"错误率超阈值"
%%   熔断期间请求**快速失败**，而不是继续占着超时与线程

%% ---- 3) 三层可观测性的最小落法 ----
%% 指标：telemetry 事件 → 聚合 → 告警（写少读多）
%% 日志：结构化（key-value），带 request_id 便于串联
%% 追踪：一次请求的跨节点 span（见本章"经典文献"里的 Dapper）

%% 指标埋点的骨架（示意）
telemetry:execute([my_app, http, request], #{count => 1},
                  #{duration => DurMs}, #{node => node()}).
```

排队论视角下的容量判据（用于"找瓶颈"一节）：

```erlang
%% 利用率 ρ = λ / μ；M/M/1 下 ρ → 1 时排队延迟急剧放大（Kleinrock）
%% 经验结论：**把系统跑到 70% 利用率，队列延迟就已经很危险了**
%% Little's law：并发数 L = λ × W（到达率 × 平均停留时间）
%%   → 想降并发，只能降 W（要么让它更快，要么让它少做）
utilization(Throughput, ServiceRate) -> Throughput / ServiceRate.
```

```erlang
%% ---- 4) 找瓶颈的顺序（工程清单）----
%%   1. 先确认瓶颈**不在**应用层：看调度器使用率、看 GC 时间占比
%%   2. 再看是否有全局串行点：单个 gen_server 撑全部请求（见 03-）
%%   3. 再看外部依赖：DB / 缓存 / 下游服务的连接池是否打满
%%   4. 最后才轮到"优化算法"
```

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| OTP 18/19（2014–2015） | 原书基线：`fprof`/`eprof`/`Observer` 是主要观测工具 |
| OTP 20（2016） | `erts` 的内存与调度改进，让"垂直伸缩"在本书成书年代仍然划算 |
| OTP 21（2017） | **调度器 SMP 默认开启**：一个节点的并行度终于默认生效 |
| OTP 22（2018） | `write_concurrency` 对 `ordered_set` 生效；ETS 不再是"必然的串行点" |
| OTP 24（2020） | JIT 默认开启 + 选择性接收优化更频繁 → 单节点吞吐提升，水平伸缩的压力曲线整体下移 |
| OTP 25（2021） | ETS `write_concurrency` 的 `auto` 选项：共享表的并发代价交给运行时判断 |
| **OTP 26（2022）** | **选择性接收优化扩展到"reference 由其他函数返回"的场景**，请求—响应类服务的延迟与吞吐量显著改善；JIT 默认带 `-fno-omit-frame-pointer`，`perf` 可直接抓 BEAM 进程栈 |
| OTP 27+（2023–2026） | `telemetry` 成为事实标准；OpenTelemetry 让"跨语言追踪"落地，Erlang 节点被纳入统一 APM |

## 常见误区与本书需修正之处

| 现象 | 说明 | 现状 / 修正 |
| --- | --- | --- |
| 🔧 **只压到"不报错"就收工** | 容量测试的价值在**拐点之后**： saturation 点、过载后吞吐是升还是崩 | 一直压到吞吐开始下降；记录拐点对应的资源水位作为告警阈值 |
| 🔧 **把队列长度当唯一告警指标** | 队列增长是结果，原因可能是下游慢、GC 停顿或全局串行点（见 `03-`） | 告警应该指向**原因**：调度器使用率、GC 时间、下游 P99、连接池占用 |
| 🔧 **没有背压就"自动扩容"** | 上游无止境地灌，扩容只是把崩溃推后，且可能引发雪崩扩容 | 先做限流/熔断/优先级队列，再谈扩容；扩容要有上限与冷却 |
| 🔧 **熔断阈值写死** | 固定阈值在负载波动时会误跳闸或永不跳闸 | 用错误率 + 连续失败数 + 冷却时间三要素；半开状态必须真的试探 |
| 🔧 **"抢救性支持"被理解成"加监控"** | 它指的是**主动降级**：宁可少做业务，也不让系统整体雪崩 | 需要预先设计降级路径（简化功能 / 缓存兜底 / 快速失败），并做好开关 |
| 🔧 **垂直伸缩仍然被当成默认答案** | 2016 年的经验值在 JIT 与 ETS 优化之后需要重新标定；但垂直伸缩依然解决不了单点故障 | 决策顺序：先消除单点 → 再考虑水平伸缩 → 最后才考虑换更大的机器 |
| **负载测试在生产网络里做** | 结果不可复现，且会打垮真实用户 | 独立网络/流量影子；或压测流量带标记并旁路 |
| 🔧 **只记录指标不记录"为什么"** | 指标告诉你"慢了"，日志才告诉你"慢在哪一步" | request_id 贯穿三者；指标用增量、日志用结构化 key-value |
