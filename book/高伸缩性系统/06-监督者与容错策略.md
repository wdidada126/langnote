# 第 8 章 监督者

> **一句话**：第 8 章是全书的核心——监督树把"崩溃"变成**一个可以被配置的参数**（重启策略），而 `max_restarts` 这条规则既是容错的基础，也是**重启风暴**的根源。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 监督树 | 树形结构、父监管子、子不监管孙的父 | 树的**深度**决定故障域的大小；越平的树越难定位 |
| OTP  supervisors | `one_for_one` / `one_for_all` / `rest_for_one` | 三种策略对应三种"故障域"定义：局部、整体、有序 |
| supervisor behaviour | `init/1` 返回 `ChildSpec` 列表 | 行为本身就是一个特殊的"永不崩溃的 worker" |
| 启动 supervisor / 规格 | `start_link`、`SupFlags`、`ChildSpec` 字段逐项 | `intensity`/`period` 是**防风暴闹钟**，不是"多重启几次" |
| 动态子节点 | `supervisor:start_child/2`、`terminate_child/2`、`restart_child/2` | 动态分支让监督树能反映真实负载，但**动态部分没有重启记忆** |
| 非 OTP 合规进程 | 手写 `proc_lib` 让普通进程挂进树 | 挂进树要付出"符合 `proc_lib` 协议"的代价 |
| 可伸缩性与短生命期进程 | 请求级进程（per-request process） | 进程短命是**优点**，让状态随进程自然消亡 |
| 同步启动以保证确定性 | `proc_lib` 顺序启动 | 顺序启动换来可预测的启动结果，代价是启动变慢 |
| 测试你的监督策略 | 主动杀进程、观察重启次数 | **没被测试过的策略等于没写** |
| 比较：与手写 try/catch | "失败即正常" vs 防御式编程 | 前者把复杂度交给运行时，后者把复杂度留在业务里 |

## 核心精讲

> 以下片段均为**教学示意代码，不参与编译、不参与任何构建**。

```erlang
%% ---- 1) 三种重启策略的语义差别 ----
%% one_for_one：一个子进程死了只重启它（最常用）
%% one_for_all ：任何一个死了，全部停掉再全部起（故障域=整棵子分支）
%% rest_for_one：死了它 + 它后面启动的兄弟（用于"启动次序有依赖"的场景）

SupFlags = #{strategy => one_for_one,
             intensity => 5,          %% 60 秒内重启超过 5 次 → supervisor 自己放弃
             period => 60},

%% ChildSpec 的四个关键字段：id、start、restart 判定、shutdown、type、modules
Child = #{id       => worker,
          start    => {worker, start_link, []},
          restart  => permanent,      %% permanent/transient/temporary
          shutdown => 5000,           %% 超过此时长就 kill（用 0 或 brutal_kill）
          type     => worker,
          modules  => [worker]},

%% ---- 2) 一个"故意做错"的 worker：崩溃即恢复 ----
worker_loop(State) ->
    receive
        {work, Req}  -> worker_loop(State),   %% 记住：真正的活儿要交给别的进程
        stop         -> ok
    end.

%% 失败即正常的最小形态
%%   不需要 try/catch、不需要回滚、不需要"保持数据一致"
%%   让进程崩 → supervisor 重启 → 状态从 init/1 重置
```

重启风暴的最小复现与它的解法：

```erlang
%% 场景：worker 启动后立即崩溃（配置错误/依赖缺失）
%%   T0  supervisor 重启 worker #1 → 失败
%%   T1  supervisor 重启 worker #2 → 失败
%%   ... intensity 用尽 → **supervisor 自己也终止** → 整棵子树消失
%% 这是生产上最常见的"配置改错 → 全节点进程集体消失"的根因

%% 修法 1：给启动加重试上限之外的**退避**（在 dynamic child 侧自己实现）
%% 修法 2：把 intensity 调高只能延后问题，要修的是"启动即失败"的原因
%% 修法 3：把可失败的依赖（外部服务、配置、磁盘）放到 worker 启动之后
```

动态子节点与它的盲区：

```erlang
%% 动态起一个请求级进程：代价低、状态随进程消亡
{ok, Pid} = supervisor:start_child(pool_sup, [Request]),

%% 盲区：start_child 起的进程**不会**被计入 intensity，
%% 也不会被自动管理重启次数；它死了就是死了
%% 想要"动态 + 有重启策略"，就自己维护一层 supervisor
```

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| OTP 18/19（2014–2015） | 原书基线：`permanent`/`transient`/`temporary` 三态与 intensity/period 已定型 |
| OTP 21（2017） | 调度器 SMP 默认开启；`supervisor` 的启动性能受益 |
| **OTP 24（2020）** | **supervisor 支持 EEP 56：significant children 与 `auto_shutdown`**——子节点若声明"失败不重要"，supervisor 可以在它继续存活时自行降级 |
| OTP 24.2（2021） | 代码清理请求数被限制为调度器数的 2 倍（关键进程时代的响应性） |
| OTP 26（2022） | `proc_lib:start*` 在子进程失败时变为**同步失败**，启动期"错误配置导致重启风暴"的暴露更早 |
| OTP 27+（2023–2026） | 监督树工具（`recon`、`Observer` 的 applications 视图）与 `auto_shutdown` 的配合更成熟 |

## 近年研究与工业界开源实践（2015–2026）

趋势：监督策略的**工程重点从"重启什么"转向"何时不需要重启"**。OTP 24 的 `auto_shutdown` 把"子节点自己判断还要不要存在"变成可能的选项；同时社区普遍采用了"启动时即快速失败（fail fast）+ 外部看门狗（`heart`）+ 进程级降级"的组合，而不是把 `intensity` 调大。

## 常见误区与本书需修正之处

| 现象 | 说明 | 现状 / 修正 |
| --- | --- | --- |
| 🔧 **"intensity 调大 = 更容错"** | intensity 用尽时 **supervisor 自己终止**，整棵子树消失——这是重启风暴的终局 | 优先修"启动即失败"的根因；确需重试要有退避；`auto_shutdown`（OTP 24+）可作为补充 |
| 🔧 **启动风暴：50 个子进程同时重启** | 一次配置错误让所有子节点同时失败，节点瞬间进入"重启风暴" | 依赖外部服务的 worker 改成"启动后异步连接 / 连接失败不崩"；启动顺序与 `proc_lib` 同步启动配合 |
| 🔧 **`restart => permanent` 一律用** | `permanent` 会**无限**重启 transient 场景下的失败进程；`temporary` 才代表"死了就算了" | 按业务语义选：需要可用性 → permanent；一次性任务/缓存 → temporary |
| 🔧 **`shutdown => 5000` 就够了？** | 长回调里的 server 不会在 5 秒内停下来，最终被 `kill`；`terminate/2` 不保证执行 | 关键资源（文件、socket）用 `terminate/2` 之外的方式保证；需要立刻停就 `0` / `brutal_kill` |
| **动态子进程没有 intensity 保护** | `supervisor:start_child` 起的进程不计入重启次数，失控调用会把节点打满 | 动态部分自带限流，或用一个 dedicated 的 dynamic supervisor 兜住 |
| **把 supervisor 当"万能父进程"** | supervisor 只做启动与重启，不做负载均衡、不做健康检查 | 健康检查与流量调度属于业务层（见 `10-`） |
| 🔧 **没有测试过的监督策略** | 原书最后一节明确要求测试，但工程上常常跳过 | 用 `rebar3 ct` 写"杀掉 N 次子进程，断言节点仍然活着"的回归用例 |
| **"非 OTP 合规进程"随手 spawn** | 不遵守 `proc_lib` 协议的进程挂进树后，supervisor 无法判断启动成功 | 用 `proc_lib:start_link` 或明确用普通 `spawn` 不挂树 |

## 与其他章 / 其他书的联系

- 前序：`03-` 提供了可监督的进程，`05-` 提供了状态化进程。
- 后续：`07-` 把节点按照 application 组织，`08-` 用发行包承载整棵树，`09-` 让树跨节点存活。
- 与 `book/多处理器编程的艺术2/`：艺术版 Ch5 讲共识下界（多个进程如何就一个值达成一致）；**监督树不做共识，它做"代价最小的一致"：直接把进程重启成初始状态**——这是消息传递路线给出的另一条答案。
- 与 `book/C++并发编程实战2/`：C++ 侧靠 RAII + 异常安全保证资源正确释放；Erlang 侧靠**进程死亡释放一切**，代价是状态需要重置。
- 与 `book/Java并发编程之美/`：Java 的线程池需要"任务失败后如何恢复"的显式策略（如 `ThreadPoolExecutor.CallerRunsPolicy`）；Erlang 把它写成 `max_restarts` 这个数字。
