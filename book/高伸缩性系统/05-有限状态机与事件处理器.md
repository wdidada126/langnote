# 第 6 章 有限状态机与第 7 章 事件处理器

> **一句话**：第 6 章用一台**咖啡机**和一个**电话控制器**说明"状态机是并发系统的骨架"，第 7 章用 `gen_event` 说明"事件流是可以被插拔替换的架构层"——两者合起来就是 OTP 里"状态"与"可观测性"的两条主线。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 有限状态机 the Erlang way | 状态 + 事件 → 副作用 | 状态是数据，转移是函数；不需要专门的 FSM 语言 |
| 咖啡机 FSM / 硬件 stub / 通用 FSM | `coffee_machine` 与模拟硬件 | 硬件 stub 让 FSM 可测试：**把外部世界抽象成消息** |
| 启动 FSM / 发送事件 / 终止 | `gen_fsm:start_link`、事件是一等消息 | FSM 进程**同时**处理事件、超时与系统消息 |
| 电话控制器（命令式版本） | 手写状态机的灾祸 | 没有行为约束的状态机 = 意大利面 |
| 事件 / 通用事件管理器与处理器 | `gen_event` 的 manager/handler 双层结构 | handler 可动态增删，这是它最大的价值也是最大的风险 |
| 启停 manager / 增删 handler / 同步与异步事件 | `add_handler/2,3`、`sync_notify/1`、`notify/1` | 异步事件不保证顺序、不保证送达；同步事件会把延迟转嫁给发送者 |
| 取数据 / 错误处理与非法返回值 | handler 返回值约定 | handler 抛异常会**杀掉整个 manager**，不是只杀 handler |
| 替换 handler / SASL 告警处理器 | `swap_handler`、`alarm_handler` | SASL 报告是 OTP 默认装的"崩溃报告"，但线上要换成自己的上报 |
| 通信顺序进程视角（对照） | 事件顺序与时钟 | 事件处理器里"看起来并行"的事件其实有隐含顺序 |

## 核心精讲

> 以下片段均为**教学示意代码，不参与编译、不参与任何构建**。

```erlang
%% ---- 1) 有限状态机：状态作为数据，转移作为消息 ----
-module(coffee).
-behaviour(gen_statem).                      %% 书中写 gen_fsm；OTP 19 起建议 gen_statem
-export([start_link/0, insert_coin/0, brew/0]).
-export([init/1, callback_mode/0, terminate/3]).

start_link() -> gen_statem:start_link({local, coffee}, coffee, [], []).
insert_coin() -> gen_statem:cast(coffee, {coin, 1}).
brew()        -> gen_statem:call(coffee, brew).

init([]) -> {ok, idle, #{credits => 0}}.

callback_mode() -> [state_functions, state_enter].

%% 状态函数：每个状态就是一个 receive 循环；**注意没有兜底分支**
idle(enter, _Old, Data) ->
    {keep_state, Data};
idle({call, From}, {brew, _}, #{credits := C} = D) when C >= 2 ->
    {keep_state, D, [{reply, From, ok}, next_state, brewing, D#{credits => 0}]};
idle(cast, {coin, V}, #{credits := C} = D) ->
    {keep_state, D#{credits => C + V}};
%% 反例：状态函数里漏掉 pattern 时，事件不会丢，但会被"永不处理"地卡住

idle(Any, _From, _Data) -> {keep_state, #{}, [{reply, _From, {error, Any}}]}.
```

```erlang
%% ---- 2) 事件处理器：manager 与 handler 的关系 ----
gen_event:add_handler(alarm_mgr, my_alert_h, []).
gen_event:notify(alarm_mgr, {cpu_hot, node()}).
gen_event:sync_notify(alarm_mgr, {mem_watermark, node()}).   %% 等 handler 处理完
gen_event:swap_handler(alarm_mgr, my_alert_h, my_alert_h2, []).

%% handler 的两种返回值：ok 表示"我处理了"，{error, Term} 表示"我不处理"
handle_event({cpu_hot, Node}, State) -> {ok, State};
handle_event({mem_watermark, _Node}, _State) -> {ok, State}.

%% ⚠ handler 里抛异常 → manager 进程终止，**所有** handler 一起没了
handle_event(Bad, State) -> error(bad_event), {ok, State}.    %% 不要这样
```

```erlang
%% ---- 3) 硬件 stub：把不可测的世界变成消息 ----
%% 真实硬件换成 stub 进程，FSM 的测试就不依赖物理设备
-behaviour(gen_event).
-module(hw_stub).
-export([init/1, handle_event/2, terminate/2]).

init([]) -> {ok, #{}}.
handle_event({button, X}, S) -> {ok, S#{button => X}};
handle_event(_, S)            -> {ok, S}.
terminate(_, _)               -> ok.
```

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| OTP 19（2014） | **`gen_fsm` 被标记 deprecated，官方推荐 `gen_statem`**（此后 FSM 的标准写法改变） |
| OTP 21（2017） | `gen_statem` 的 `state_enter` 调用与 `postpone` 等能力完善，成为事实标准 |
| OTP 22（2018） | map 与 JIT 侧的改进让"状态用 map 保存"的写法明显更便宜 |
| OTP 24（2020） | **编译器/JIT 对"全字面量键的 map"生成更好代码**；`recv_opt_info` 让选择性接收优化可见 |
| **OTP 26（2022）** | **选择性接收优化扩展到"reference 由其他函数返回"的场景**，状态机里"按请求标记分派"的路径显著变快；map 内部原子键顺序变化，`maps:iterator/2` 提供确定性遍历 |
| OTP 27+（2023–2026） | `gen_statem` 继续稳定；事件侧的标准做法进一步向 `telemetry` 与 OpenTelemetry 迁移 |

## 近年研究与工业界开源实践（2015–2026）

趋势：状态机在语言层的地位上升（显式状态 + 显式事件比隐式回调更好推理），但**事件处理器在架构层的地位下降**——`gen_event` 的"运行时插拔 handler"被证明在大型系统里难以推理，工业界改用了三种替代：① 编译期确定的事件订阅表；② 官方 `telemetry` 事件 + 外部采集；③ 外部消息总线（Kafka/NATS）。

| 仓库 | star | 说明 |
| --- | --- | --- |
| `erlang/otp` | **12337★** | `gen_statem`（取代 `gen_fsm`）与 `gen_event`/SASL 的实现 |
| `elixir-lang/elixir` | **26677★** | `GenStateMachine` 与 `GenEvent` 的精神续作 |
| `nats-io/nats-server` | **20768★** | 事件总线的当代形态，`gen_event` 的典型替代者 |
| `rabbitmq/rabbitmq-server` | **13876★** | 队列事件与统计走 `telemetry`，不靠可插拔 handler |
| `tokio-rs/tokio` | **33232★** | 对照：`select!` + 状态字段手写状态机，无行为抽象 |
| `openjdk/jdk` | **23379★** | 对照：`StateMachine` 无内建，FSM 靠框架（如 Akka）补全 |

## 常见误区与本书需修正之处

| 现象 | 说明 | 现状 / 修正 |
| --- | --- | --- |
| 🔧 **`gen_fsm` 已过时** | 原书示范的是 `gen_fsm`，它在 OTP 19 起 deprecated | 新代码用 `gen_statem`：`callback_mode`、状态函数、`state_enter` |
| 🔧 **状态函数的"漏 pattern"** | 状态函数里没有匹配分支时，事件**既不处理也不报错**，表现为"系统卡住" | 每个状态函数给一条兜底分支，或在 `gen_statem` 里用 `postpone` 显式延后 |
| 🔧 **handler 抛异常杀掉整个 manager** | `gen_event` 的语义是：handler 出错 → manager 终止 → 所有 handler 失效 | handler 内部一律 try/catch，或把"处理"与"投递"分离 |
| 🔧 **把 `gen_event` 当架构层用** | 原书对"可插拔 handler"的强调在真实系统里会变成不可推理的动态依赖 | 改为编译期确定的订阅表 + `telemetry`；需要外部总线就用 Kafka/NATS |
| 🔧 **`sync_notify` 的延迟转嫁** | 同步事件让发送者被最慢的 handler 拖住，热点 handler 会形成隐性串行点 | 默认用异步 `notify`；同步只在必要时用于"投递已确认"语义 |
| **事件顺序被假设** | 异步事件不保证跨 handler 的顺序 | 状态里带序号或时间戳，必要时用 `sync_notify` |
| 🔧 **咖啡机示例里的硬件假设** | 硬件 stub 与真实驱动的差异会被跳过，导致"测试通过、上线翻车" | 驱动层与协议层解耦，stub 只替换协议，不替换驱动语义 |

## 与其他章 / 其他书的联系

- 前序：`03-` 的 `gen_server` 是"只有一个状态"的行为，本章是它的状态化版本。
- 后续：`06-` 监督 FSM 进程，`09-` 跨节点分发事件。
- 与 `book/多处理器编程的艺术2/`：艺术版 Ch3 讲可线性化（状态机的语义正确性），本章讲状态的**工程实现**；`gen_statem` 的事件顺序问题本质是线性一致性问题。
- 与 `book/C++并发编程实战2/`：C++ 侧用状态字段 + 显式转移函数手写 FSM，风险是转移期间加锁；Erlang 侧状态转移是消息驱动的**天然串行**，代价是不共享状态。
- 与 `book/Java并发编程之美/`：Java 的 `synchronized` + 状态变量需要小心可见性；Erlang 的消息传递把可见性问题变成了**交接顺序问题**。
