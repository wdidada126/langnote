# 第 3 章 行为模式与通用型服务器（gen_server）

> **一句话**：行为（behaviour）不是语法糖，而是**把"进程骨架"从"业务逻辑"里抽出来后留下的那道缝**；`gen_server` 则是这道缝最窄的那一个——本章所有"超时、死锁、未处理消息"的坑都发生在缝里。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 进程的骨架 / 设计模式 | 从 N 个相似进程里抽出共同骨架 | 骨架 = 启动、循环、收消息、终止；业务 = 状态与处理 |
| 回调模块 | `-behaviour(gen_server)` 与 `-export([...])` 的约定 | 约定优先于实现：回调写错，进程直接崩，而不是悄悄跑歪 |
| 抽取出通用的行为模式 | 手写一遍骨架，再发现"所有 server 都一样" | 通用行为是**被重复了 N 次之后才存在的**，不是设计出来的 |
| 启动 server / client 函数 / server 循环 | `start_link` → `init/1` → loop | `start_link` 把进程挂进监督树，`init/1` 失败则启动失败 |
| 通用服务器 / 消息传递：冰山之下 | `gen_server` 内部把 `{From, Tag, Request}` 塞进消息体 | 回调收到的消息**带请求标记**，客户端才能对上号 |
| 同步式消息传递 | `gen_server:call` 与默认 5000 ms 超时 | 超时是**调用者侧**的，服务端没有超时 |
| 异步式 / 其他消息 / 未处理的消息 | `cast`、`handle_info` | 没有兜底 pattern 时，未匹配消息**留在邮箱里堆积** |
| 同步客户端 / 终止 | 阻塞 vs 非阻塞、清理 | `terminate/2` 只在"礼貌停止"时被调用，`kill` 时不保证 |
| Call 超时 / 死锁 / 通用服务器超时 | 三种超时发生在三个不同位置 | **最容易忽视的是服务端"没有超时"** |
| 休眠行为 / Going global / 链接行为 | `hibernate`、`{global, Name}`、`{via, ...}` | 休眠省内存但会触发两次 GC；`via` 是把注册逻辑外置的正解 |

## 核心精讲

> 以下片段均为**教学示意代码，不参与编译、不参与任何构建**。

```erlang
%% ---- 1) 手写一遍"通用服务器"：行为模式的诞生过程 ----
%% 先写业务进程的骨架，发现骨架与业务无关
start_link(Args) -> proc_lib:start_link(?MODULE, init, [Args], []).
init(Args) ->
    process_flag(trap_exit, true),
    loop(Args, #{count => 0}).
loop(State, Data) ->
    receive
        {call, From, Tag, get}  -> From ! {Tag, maps:get(count, Data)},
                                   loop(State, Data);
        {call, From, Tag, inc}  -> From ! {Tag, ok},
                                   loop(State, Data#{count => maps:get(count,Data)+1});
        {'EXIT', _Pid, _R}      -> ok;                 %% 不 trap_exit 就会被杀
        Other                   -> io:format("drop ~p~n", [Other])
    end.
%% 抽出通用骨架后剩下的就是：init/1、handle_call/3、handle_cast/2

%% ---- 2) 正解：gen_server 的最小形态 ----
-module(counter).
-behaviour(gen_server).
-export([start_link/0, bump/0, peek/0]).

start_link() -> gen_server:start_link({local, ?MODULE}, ?MODULE, 0, []).

bump()  -> gen_server:call(?MODULE, bump).
peek()  -> gen_server:call(?MODULE, peek).

init(Init) -> {ok, Init}.

handle_call(bump, _From, N) -> {reply, N + 1, N + 1};
handle_call(peek, _From, N) -> {reply, N, N}.

%% handle_info 里若没有兜底，任何意外消息都会在邮箱里堆积
handle_info(Other, State) ->
    io:format("unexpected: ~p~n", [Other]),
    {noreply, State}.
```

`gen_server:call` 的三处超时陷阱：

```erlang
%% 陷阱 A：默认 5000 ms。慢一点就崩调用者，但服务器**根本不知道**
%%         OTP 24 之前：迟到的回复仍会进调用者邮箱，变成"垃圾消息"
%%         OTP 24 起：gen_server:call 使用进程别名（EEP 53），迟到回复不再被接收
_ = gen_server:call(counter, peek, 5000).

%% 陷阱 B：服务端 handle_call **没有超时**。一个慢回调会阻塞整个 server，
%%         所有并发请求排在同一条进程里——这是"死进程堆积"最常见的来源
handle_call(heavy, _From, S) ->
    Reply = do_heavy_that_takes_minutes(),
    {reply, Reply, S}.                     %% 期间所有 call 都在等

%% 陷阱 C：两个 server 互相 call = 必然死锁；最容易发生在"链接行为"与
%%         {global, Name} 场景里，日志打印一下就发现调用路径成环了
%% 死锁最小模型：
%%   A ! {call, B, tag, ping}, B ! {call, A, tag, pong}  %% 双方都在等对方回复
```

注册与全局名字的原语（"Going global" 的实质）：

```erlang
%% 本地注册：靠进程存活即名字存在
gen_server:start({local, counter}, counter, 0, []).

%% 跨节点注册：{global, Name} 靠 pg 语义保持唯一；{via, M, N} 把注册表换成
%% 别的实现（例如用 ETS 自己实现的注册表），代价是要自己处理分割后的名字冲突
gen_server:start({global, counter}, counter, 0, []).
gen_server:start({via, my_reg, counter}, counter, 0, []).
```

休眠（hibernate）与它的代价：

```erlang
%% 长时间空闲的 server 可以用 hibernate 归还堆内存
handle_call(idle, _From, S) -> {reply, ok, S, hibernate}.

%% 但 hibernate 进出各触发至少一次 GC；**别在每次调用之间用它**
%%   —— 对繁忙 server 是净损失（gen_server 文档明确提醒）
```

## 版本演进

| 版本 | 与本章相关的变化 |
| --- | --- |
| OTP 21（2017） | `{via, Module, Name}` 注册机制成熟，`pg`（分布式进程组）替代 `pg2` 成为命名与分组的新基座 |
| OTP 22（2018） | `write_concurrency` 对 `ordered_set` 生效；`gen_server` 侧为异步请求配对（`send_request/3` + `wait_response/2`）铺路 |
| OTP 23（2019） | `check_response/2`（自 23.0 起）支持手动轮询式取回复；`pg` 落地；分布式 spawn 性能改善 |
| **OTP 24（2020）** | **`gen_server:call` 改用进程别名（EEP 53）→ 超时后的迟到回复不再污染调用者邮箱**；选择性接收优化应用更频繁；supervisor 支持 `auto_shutdown` |
| OTP 25（2021） | ETS `write_concurrency` 的 `auto` 选项 |
| **OTP 26（2022）** | **选择性接收优化扩展到"reference 由其他函数返回"的场景**，`send_request/3` / `wait_response/2` 因此显著提速；`proc_lib:start*` 在启动失败时同步失败 |
| OTP 27+（2023–2026） | `handle_continue` 等回调语义稳定；Dialyzer 增量模式让"回调返回值写错"更早被发现 |

## 近年研究与工业界开源实践（2015–2026）

趋势：OTP 的行为体系在 2020 年之后**从"加抽象"转向"把已有抽象做快"**。`gen_server` 本身没有新行为被加入标准库，但它的**请求—响应路径被反复优化**（进程别名、选择性接收）、被 OTP 26 的 JIT 与调度器改动进一步加速；同时社区大量迁移到 `gen_statem`（原书写作时 `gen_fsm` 更常见），`handle_common_reply` 一类手工状态机正在被取代。

## 常见误区与本书需修正之处

| 现象 | 说明 | 现状 / 修正 |
| --- | --- | --- |
| 🔧 **以为 `gen_server:call` 超时 = 服务端放弃** | 超时只是**调用者等不下去**，服务端仍在跑，稍后把回复发到调用者邮箱 | 服务端要做真正的业务超时（`Timeout` 字段 + `handle_info` 取消）；OTP 24 起进程别名让迟到回复不再污染邮箱 |
| 🔧 **`handle_call` 里的慢回调导致"死进程堆积"** | 一个 `gen_server` 进程是**串行**的，任何长回调都会让所有并发请求排队；客户端侧先超时崩掉，服务端仍在慢慢处理 | 长任务要么交给专门的 worker 进程并通过 monitor 追踪，要么拆成多个 server；真要实现"可放弃"需要服务端取消语义 |
| 🔧 **没有兜底 pattern 的 `handle_info`** | 未匹配消息**不会丢**，而是留在邮箱；一旦 server 长期不处理，邮箱会无界增长 | 补一条兜底分支（丢弃并记日志），并给关键流程加 `receive after` 清理 |
| **死锁只在"互 call"时出现** | 误读：真正的死锁还包括"自己 call 自己"（`calling_self`）、以及 `gen_server:call` 时进程被 `kill` 后仍挂在 receive |
| **把 `terminate/2` 当可靠清理点** | `kill` / 崩溃时它不会被调用，状态与文件句柄可能不落盘 | 关键状态交给外部存储或 ETS/disk_log，别把希望寄托在 `terminate/2` |
| 🔧 **把 `hibernate` 用在繁忙 server 上** | 进出 hibernate 各触发至少一次 GC | 只对明显空闲的 server 用；繁忙路径保持常驻 |
| **用 `cast` 保证送达** | `cast` 在服务端进程不存在时**静默丢失** | 需要确认就走 `call` 或显式 monitor |
| 🔧 **`{global, Name}` 被当成分割保护** | 名字唯一性靠分布式进程组维持，**网络分区期间不保证唯一** | 分区后的名字冲突要在应用层处理（`via` + 自研仲裁） |

## 与其他章 / 其他书的联系

- 本章是 `02-` 的封装化，也是 `06-` 的输入——行为写好后才谈得上"挂进监督树"。
- 与 `book/多处理器编程的艺术2/`：艺术版 Ch3 关心"并发对象的可线性化"，`gen_server` 的 `handle_call` 序列正是**串行化**执行点；艺术版 Ch2 的互斥与本章"靠单进程串行消除锁"是同一件事的两面。
- 与 `book/C++并发编程实战2/`：C++ 里同样的"串行点"要显式用互斥量保护（`std::mutex` + 条件变量），Erlang 把它变成**进程拓扑**；这是消息传递 vs 共享内存的主线分歧。
- 与 `book/Java并发编程之美/`：Java 的线程池 + `BlockingQueue` 承担排队职责，Erlang 的邮箱承担，但前者需要显式调参、后者由 erts 调度。
