# 《Type-Level TypeScript》分章笔记 03 · 映射类型

> 第Ⅲ段「映射类型：键重排、修饰符增删、同态映射」（⚠️ 段名凭 [00-总览与阅读地图.md](00-总览与阅读地图.md) 骨架表机制清单记忆，非原书目录逐字）。一句话定位：**类型层的 for-in**——02 档给了分支，本档给遍历；`Partial/Pick/Omit` 全家都是它的 instantiated 成品。

## 核心机制

### 1. 同态映射：`[K in keyof T]` 是「带结构继承的遍历」
```ts
type Clone<T> = { [K in keyof T]: T[K] };
```
遍历源类型的键集**且原样继承修饰符**（可选 `?`、只读 `readonly`）——这就是「同态 homomorphic」的特权身份：只有形如 `in keyof T` 的映射才享受，换成独立键集（如 `in "a" | "b"`）就退化成普通匿名对象。推论：数组/元组被同态映射时保持数组形状（`Clone<[1, "a"]>` 仍是元组）而不是变成 `{0|1: ...}` 的记录。**体操第一定律：想保住原类型的骨架，就必须写同态形。**

### 2. 修饰符增删：`-?` / `-readonly` 是「负号算子」
```ts
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
type MyRequired<T> = { [K in keyof T]-?: T[K] };
```
`readonly`/`?` 在映射体内是**可加减的代数对象**：写 `?` 加可选、`-?` 去可选。`MyRequired` 的 `T[K]` 还需接 04 档预告的非空断言工具 `NonNullable`（`T[K] extends null | undefined` 面）才彻底，此为本档留给 05 组合拳的活扣。工程边界先钉：**`-?` 不会让值真的存在**，运行时字段照旧可缺（擦除公理，见专题档）。

### 3. 键重排 `as` 子句：映射的第二引擎（4.1 引入 ⚠️ 版本归属社区口径）
```ts
type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };
type OmitX<T> = { [K in keyof T as K extends "x" ? never : K]: T[K] };
```
`as` 干两件事：**改名**（配模板字面量，4.x 前只能靠交叉类型硬拼）与**滤键**（映射到 `never` 的键被删除——Omit 的原生写法）。`Capitalize` 只吃字符串，故 `string & K` 收窄；K 若是 symbol/number 键会被条件滤掉——这是典型坑面，书中练习站常见答案即此形态 ⚠️ 以原文为准。

### 4. 映射 × 条件 × 递归三器合奏：`DeepReadonly` 样板
```ts
type DeepReadonly<T> = T extends Function ? T
  : T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T;
```
条件负责**逃逸口**（函数不拆、原子不拆），映射负责遍历，递归负责纵深——三段机制在此汇齐。逃逸口的次序就是正确性：函数也是 object，把 `T extends object` 放前面会把整个闭包类型拆成 `{call: ...}` 面目全非，本号最经典的失分点。

### 5. 视图再造：键值互换与展平
`type Invert<T extends Record<string, string>> = { [K in keyof T as T[K]]: K }` 与 `PrefixKeys<T, P extends string> = { [K in keyof T as `${P}${string & K}`]: T[K] }`——API 层「给响应体全体加前缀/取反查表」这类需求能被压成一行映射。这是映射类型在本书里最「有用」的一面，也是后两档（字面量、递归）的展示台。

## C++ 对偶裁定

| TS 机制 | C++20 对应物 | 裁定 |
|---|---|---|
| `add_pointer` 型 trait 变换族 | 同态映射本体：输入类型→输出类型、骨架保持 | **强对偶**，对读 [../C++20模板元编程/05-类型特征和条件编译.md](../C++20模板元编程/05-类型特征和条件编译.md) |
| `readonly/?` 修饰符加减 | 类型特征对 cv/引用限定的剥除与重组（`remove_const_t` 等） | 形对神异：C++ 限定符是类型原子的组成部分，TS 修饰符是对象类型的可重写元数据 |
| `in keyof T` 遍历成员名 | **无对偶**（成员名不可反射；trait 只能按已知名字逐个适配） | 差集档 ★：TS 能「遍历你不知道的键」，C++ 做不到 |
| `as` 键重排 | 无对偶（P2996 静态反射若过才可写） | 差集档，时代差主证 |
| 元组同态保形 | `std::apply`/index_sequence 造 `std::tuple<Ts*...>`（03 章模式） | 部分：C++ 靠下标序列模拟遍历，名字维度仍缺 |

总裁定：第Ⅲ段一半（修饰符/变换框架）与 C++ traits 同峰可互链 [../C++20模板元编程/07-模式和惯用法.md](../C++20模板元编程/07-模式和惯用法.md) 的类型列表惯用法，另一半（**键名即数据**）是 TS 独占——这正是 00 档预告「Ⅳ 段起重点差集」的前哨。

## 批判读法

- **hover 即天书**：`DeepReadonly<S>` 展开后是嵌套未求值的映射表达式，编辑器折叠显示 `{readonly [K in keyof ...]}`；调试期看不到「具体形状」是映射类型的头号可读性代价，比条件链更甚。
- **实例化数 = 键 × 键 × 深度**：深对象上的深映射（DeepReadonly 嵌 50 键对象）按乘法烧实例化预算，与 05 档深度上限同一条账；「一行代码、千次实例化」是本号真实成本模型。
- 工程止损线：`readonly` 两层封顶、键重排模板串嵌套两层封顶是常见 review 约定 ⚠️（社区经验，非书载）；更深的需求应走 schema-first（`zod` 式「值即类型源」，擦除公理的工程解，见专题档戒律 3）。
