# 第7章 单个服务的基本结构 — 从一连接一线程到 one thread one loop

> 对应原书第 7 章（§7.1–7.12，原书第 515–586 页）。目录经豆瓣条目 35491437 核实 ✅。
> 全书架构正题：以一个带网络通信组件的高性能服务如何搭骨架为主线，
> 走过 thread-per-connection → Reactor → one loop per thread → 分层网络库 → 定时器/缓冲 → 经典结构全景。
> 03/04/06 三章的全部零件在这一章组装。

## 核心概念速览（中英对照）

- **一连接一线程** — thread-per-connection：最直白模型，并发上限被线程栈内存与调度开销锁死（7.3）
- **反应器模式** — Reactor：就绪通知 + 分发回调的事件驱动模式（EPoll 的 LT 是天然 Reactor 基座，7.4）
- **前摄器模式** — Proactor：完成通知 + 结果分发（IOCP 是原生实现；书中以 IOCP 为例对照讲解）
- **一线程一循环** — one thread one loop：每线程内单事件循环、循环内无锁、跨线程走队列投递（7.5）
- **唤醒机制** — wakeup：向 loop 线程投递任务的安全唤醒——`eventfd`/`pipe` + 套接字自连（书取后者路线，7.5.3）
- **定时器** — timer：超时扫描设施；最小堆（O(logN)）、时间轮（O(1) 摊还）、有序容器三流派（7.9）
- **时间缓存** — cached time：一次 `gettimeofday` 服务一整轮事件处理，避免每秒数万 syscall（7.9.4）
- **接收/发送缓冲区** — receive/send buffer：连接级用户态缓冲——解决"读不如愿/写不凑手"（7.7）
- **高水位背压** — high watermark：对端不收导致发送缓冲堆满时的处置策略（7.7.3）
- **Channel/Connection/Session 分层** — 网络库三层：fd 事件↔连接对象↔协议语义的解耦（7.8）
- **侵入式结构** — intrusive data structure：节点自带链接域，定时器/环形队列零额外分配（7.11）
- **`listenfd` 非阻塞** — accept 风暴下的循环保护（7.12.1）
- **惊群** — thundering herd：多 accept 线程/多 loop 争一 listenfd 的唤醒浪费与 `SO_REUSEPORT` 解法（7.12.2 语境）
- **事件循环饥饿** — loop starvation：一个 handler 阻塞/长算拖垮整个 loop 上所有连接（7.10 的议题）

## 动机：C10K 是结构问题，不是调参问题

7.1.1 给出高效框架三原则（书意转述）：**不浪费线程在等待上、不在共享状态上锁来锁去、
系统调用批量化**。thread-per-connection 三条全违——每连接一个线程阻塞在 recv（等待浪费）、
全局连接表加锁（锁竞争）、线程风暴 syscall（上下文切换）。Chen 的 C10K 论文
（[The C10K problem, Dan Kegel](https://www.kegel.com/c10k.html)，已核实可达）列出的十种死法，
解药全部收敛到同一句：**把"并发"从线程维度搬到事件维度**。

## 机制：本章六块拼图

### 7.2–7.4 结构演化三部曲

原始阻塞服务器（accept→read 循环，串行处理）→ fork/线程化（并发但重）→
**Reactor**：`epoll_wait` 收就绪事件 → 按 fd 找到 handler → 回调执行；回调必须**短**。
书对 Reactor/Proactor 的界定（7.4）沿用经典论文口径：Reactor 通知"你**可以**读写"（注册者自己做 IO），
Proactor 通知"IO **已完成**，数据在你的 buffer 里"（内核代做，IOCP 独此一家）。
Linux 上 io_uring 把 Proactor 补齐（见演进节）。

### 7.5 one thread one loop（本章心脏）

结构：loop 线程持有 epollfd + 就绪数组 + **每循环一次时间缓存**（7.9.4）+ 定时器堆 +
**任务队列**。跨线程投递 `run_in_loop(fn)`：入队 + 唤醒。唤醒机制书选的是**socketpair/自连 loopback**
（7.5.3 给了 Windows loopback 兼容版），Linux 现代默认 `eventfd`。
铁律与推论：
- loop 内一切状态无锁（单线程访问就是同步）——fd 的 handler、连接对象、定时器回调全在 owner loop 里跑；
- 跨 loop 交互 = 消息投递，永不加锁共享对象；
- **7.6：同一 socket 的收发只允许一个 owner 线程碰**——EPOLLONESHOT（4.14.4）是"把一条连接派给线程池"
  时的补偿方案，与 one-loop-per-thread 二选一；
- 7.5.6 效率账：唤醒成本一次 syscall、任务队列只在入队瞬间持锁（03 章 t01 的实测数据 2.7M 任务/s 即该模式上限的量级感）。

### 7.7 缓冲区与高水位（背压的网络层版本）

recv：内核缓冲→用户 recv buffer→**切出完整消息**才回调（6.3 编解码器的宿主）；
send：小写先堆 send buffer，loop 内攒够大块一次 writev（4.15 在此兑现；ET 模式配合"可写时才写"）。
7.7.3 服务端狂发、对端不收：发送缓冲无上限=内存炸，有上限=必须表态——丢弃/断连/阻塞回调线程/通知上层
（高水位回调），**没有"都不选"这个选项**。这就是现代"backpressure"议题的 2021 中文表述。

### 7.8 网络库分层与 7.12 经典结构

Channel(fd 事件读写位+回调) ← Socket(包装 fd+收发缓冲) ← Connection(状态机+编解码) ← Session(协议语义)
← Service；7.8.3 给出连接→loop 的两种映射（按 fd hash / 首连分派+迁移）。
7.12 全景图：main 线程起 Service，acceptor 独占 loop（listenfd 非阻塞的理由 7.12.1：
backlog 打满时 accept 返回 EAGAIN 而不是挂住循环）、N 个 IO loop 各持连接、
业务线程池（7.10 的"要不要单独开线程"结论：**算得快的进 loop、算得慢/会阻塞的进池**——
与 03 章线程池 vs 协程分界一致）。7.12.3 性能瓶颈清单：syscall 数、拷贝次数、锁、定时器精度、内存碎片。

### 7.9–7.11 定时器与侵入式结构

- 最小堆（`std::priority_queue`，7.9.2）：插入/弹出 O(logN)，每轮只看堆顶，配 cached time——Redis/muduo 路线；
- 时间轮（7.9.3 思路源头）：槽=滴答、插入 O(1)、到期扫描 O(1) 摊还，代价是精度=tick、远期超时需 lap 圈数或层级轮；
- 7.11 侵入式：节点内嵌 `next/lower` 指针——定时器堆里"回调对象自身携带链表域"，插入零分配、
  取消 O(1)（直接摘链），是 Linux 内核 timer_list 与 muduo TimerQueue 的共同选择。

**实测**（`t03_timingwheel.cpp`，g++ 15.2）：500,000 个定时器、到期时刻均匀落在 1–4096ms、
1024 槽×1ms tick 时间轮 vs `std::priority_queue` 最小堆，含插入全程计时：
**wheel 42 ms vs heap 181 ms（4.3×）**，两者触发的定时器数量一致（500000）。
注意这是"大时钟跨度+海量并发定时器"下轮扫描摊还优势的教学演示；
小 N、低触发率场景 heap 因常数更小常反超——7.9.3 的"性能优化"本质就是"别为低频定时器付扫描税"。⚠️ 单轮实现，未处理跨 epoch 溢出。

## 权衡与边界

| 模型 | 线程数 | 延迟 | 吞吐上限来源 | 复杂度 |
| --- | --- | --- | --- | --- |
| 线程/连接 | N | 最低（阻塞唤醒） | ~千级（栈+调度） | 最低 |
| Reactor 单 loop | 2–3 | syscall 排队 | 单核 epoll | 中 |
| Reactor M loop（本章） | 核数级 | loop 内无锁 | 线性到核数 | 中高 |
| 线程池 + EPOLLONESHOT | 核数级 | 迁移缓存局部性差 | 单连接被单事件限速 | 高 |
| Proactor/IOCP | 池 | 内核代 IO | 包/批大小 | 高（平台锁死） |

## 相邻概念对比

- **Reactor vs Proactor**：就绪 vs 完成；同步 IO 复用 vs 异步 IO 复用。跨平台库把两者都映射进同一事件循环抽象（asio 的 service 层）。
- **one loop per thread vs share-everything**：前者共享代码/不共享数据，后者线程池+全局锁；书 7.5+7.8.3 已含前者全部要素，后者在 2026 年的代言是 seastar（下文）。
- **run_in_loop vs 锁保护对象**：7.6 的"不要多线程用同一 socket"在对象层等价于"别在多线程访问同一 Session"——把对象钉在 loop 上，用消息说话。

## 内存池补记 🔧（7.12.3 内存碎片的解药之一）

`t04_mempool.cpp`（g++ 15.2）：2,000,000 次 32B `new/delete` 对固定档 free-list 池
（chunk 批量向 OS 申领、释放只挂 freelist）：**55,120 µs vs 21 µs（≈2600×）**——
教学值（池无跨尺寸档/无归还 OS 逻辑，真实 tcmalloc 要付 thread-local cache 与转移成本），
但量级正确地解释了"为什么 glibc malloc 之上还要一层 tcmalloc/jemalloc"（09 章日志与 08 章 Redis
`zmalloc` 均依赖此结论）。tcmalloc 一手资料：gperftools 仓库 [google/gperftools](https://github.com/google/gperftools)（检索核实）；
jemalloc 论文（USENIX ATC'10）为正式出版物。⚠️ Windows MSVC CRT 堆行为不同，未做跨分配器对照实测。
