# 第4章 网络编程重难点解析 — socket、select/poll/epoll 与非阻塞语义

> 对应原书第 4 章（§4.1–4.17，原书第 282–396 页）。目录经豆瓣条目 35491437 核实 ✅。
> 全书技术密度最高的一章：以 Linux  sockets 为主线、Windows winsock 为副线，
> 4.6（阻塞/非阻塞）与 4.14（epoll）两节合计逾 60 页，是 07 章服务结构的直接输入。
> ⚠️ 实测边界声明：epoll/io_uring 属 Linux 内核设施，**本机（Windows）不可实测**，
> 机制按内核 man 手册与公开文档转述；select/非阻塞 socket 的 Windows 语义（winsock）部分可实测（本章仅书证转述，未新做实验）。

## 核心概念速览（中英对照）

- **套接字** — socket：内核网络协议栈的文件描述符句柄（Windows 上是 UINT_PTR 型 SOCKET）
- **I/O 多路复用** — I/O multiplexing：单线程用 select/poll/epoll 同时等待多个 fd 就绪
- **水平触发/边沿触发** — Level Triggered (LT) / Edge Triggered (ET)：epoll 每次报告"仍就绪" vs 只在"状态翻转"时报
- **`EPOLLONESHOT`** — 一次性触发标志：事件触发后自动摘除，多线程安全分发连接的开关，4.14.4
- **非阻塞套接字** — non-blocking socket：`O_NONBLOCK`/`ioctlsocket(FIONBIO)`；读写不就绪即返回 `EWOULDBLOCK`/`WSAEWOULDBLOCK`
- **部分写** — partial write：非阻塞 send 可能只吞走半截缓冲区，循环续写是义务不是选项
- **`TCP_NODELAY`** — 禁用 Nagle：小包即时发送，RPC 型协议的延迟旋钮
- **`FIONREAD`/`ioctl`** — 查询接收缓冲可读字节数：4.10 的"偷看内核缓冲"技巧
- **`EINTR`** — 被信号打断的错误码：所有 Linux 慢系统调用的必修伪错误，4.11
- **`SIGPIPE`** — 对端已关闭仍写 → 默认杀进程：服务端必须 `SIG_IGN` 或 `MSG_NOSIGNAL`，4.12
- **散布/聚集 I/O** — scatter/gather I/O（`readv`/`writev`）：一次系统调用跨多个用户态缓冲，4.15
- **字节序** — host/network byte order（`htonl/ntohl/htons/ntohs`）：线上协议大端制的强制统一，4.16
- **域名解析** — `getaddrinfo`/`gethostbyname`：协议无关的地址解析入口，4.17（阻塞调用，藏在线程池/异步解析的动机）
- **完成端口** — I/O Completion Port, IOCP：Windows 的异步通知式复用模型（本章 epoll 的对照物）

## 动机：socket API 的"坑位地图"比 API 本身大

书的写法是**按踩坑频率排大小节**：为什么 send 只发了一半？（4.6）为什么 read 返回 -1 还 errno=EINTR？（4.11）
为什么对端拔网线后写操作把进程杀了？（4.12）为什么 connect 卡 3 分钟？（4.8）——每个"为什么"对应
服务端事故库里的一个条目。跨平台库设计（4.3）则把两平台差异列成清单：SOCKET 类型、`closesocket` vs `close`、
`WSAGetLastError` vs `errno`、select 第一参数在 Windows 被忽略、`WSAEWOULDBLOCK≡EWOULDBLOCK` 的映射。

## 机制：三个必懂的层次

### 4.5/4.13/4.14 select → poll → epoll 的演化逻辑

- `select(fd_set)`：每次全量上传 fd 集合，内核 O(N) 扫描，位图容量 FD_SETSIZE=1024，返回后还要用户态再扫一遍找就绪者——**三次 O(N)** 是淘汰它的理由。
- `poll(pollfd[])`：数组替位图（解除 1024 限制、in/out 分离），但仍是每次全量传入 + O(N) 扫描 + 找就绪 O(N)。
- `epoll`（4.14）：`epoll_create` 内核侧红黑树登记 + 就绪链表；`epoll_ctl` 增量修改注册（O(logN)）；
  `epoll_wait` 只返回就绪数组（O(就绪数)）——把 O(N) 从热路径上摘掉。
- **LT vs ET（4.14.3，本章最重要的设计决策）**：LT 下 fd 只要有剩余数据就一直报告——编程简单但
  一次事件可能只处理一块数据，反复唤醒；ET 只在"不可读→可读"翻转时报——必须一次循环 read 到 `EAGAIN`，
  否则剩余数据**永远等不到下一个边沿**（配合 4.10 的 FIONREAD 决定读节奏）。
  书的"busy 分布"含义（本目录转述）：LT 的唤醒次数与"数据到达批次"同频；ET 的唤醒次数与
  "连接空闲→忙碌翻转"同频，高吞吐长连接下 ET 的 syscall 数显著更少，但**任何一个忘记读干净的 handler
  都是静默的延迟炸弹**——muduo/Redis 默认 LT（见 08 章），Nginx 用 ET，是两派工业代表。
- `EPOLLONESHOT`（4.14.4）：多线程 event loop 池中防止同一连接被两工人并发处理——事件触发即失效，
  处理完 `epoll_ctl(MOD)` 重新武装。与 7.6"不要多线程共用一个 socket"是同一问题的两种答案。

### 4.6–4.10 非阻塞语义全景（书用同一对示例程序跑遍矩阵）

非阻塞读写返回值矩阵（4.6.3 原表复述）：send 返回 (0, 部分, -1+EAGAIN, -1+真错误)；recv 返回
(>0, 0=对端正常关闭 FIN, -1+EAGAIN, -1+真错误)。四个配套细节：
- 发送 0 字节（4.7）**不发包但探测对端是否已关**（recv 返回 0 的镜像语义在写侧的实现）；
- connect 非阻塞化（4.8）：立即 `EINPROGRESS`，可写事件到达时 `getsockopt(SO_ERROR)` 取三次握手结果——
  超时可控的异步连接标准配方；书进一步给了"连接时顺便接收第一组数据"（4.9）：SYN 队列里带数据的技巧（Linux `TCP_FASTOPEN` 的前身式讨论 ⚠️ 书未展开 TFO）。
- 「服务端发数据对端不收」（4.10 引出、7.7.3 展开）：发送缓冲堆满 → 写侧必须限流，这是背压议题的源头。

### 4.15–4.17 收尾三件

`readv/writev`（4.15）把"头部+body"两缓冲一次 syscall 写出（06 章协议的天然搭档，配合 `writev` 还能避免粘包拷贝）；
字节序（4.16）说明 htons 族与 memcpy 序列化（禁止强转指针读结构，对齐+字节序双坑——为 6.6 埋线）；
`getaddrinfo`（4.17）给出协议无关解析 + 强调其**内部可能同步 DNS 阻塞**——现代实现（c-ares、getaddrinfo_a）见下文。

### 4.3/4.4 跨平台与 bind 的细节雷（书用小节多而短，合并复述）

- **4.3 族**：`socket` 返回类型 `int` vs `SOCKET`（Windows 无效值是 `INVALID_SOCKET` 而 Linux 是 `-1`——
  跨平台库判错函数必须封一层）；`closesocket` 不保证立即发 FIN（linger 语义）；
  select 第一参数 nfds 在 Windows 被忽略（传 0 也能跑——移植陷阱的经典案例，4.3.6）；
  错误码表 Windows/POSIX 双轨映射（`WSAENOTCONN≡ENOTCONN`，4.3.7）。
- **4.4 bind**：绑定 `0.0.0.0`（全接口）vs 具体 IP vs `127.0.0.1`（回环独占）的部署差异；
  端口选择：`bind(0)` 让内核发临时端口 + `getsockname` 回读（监控端口随机化用得上）；
  `SO_REUSEADDR`（Linux 允许 TIME_WAIT 端口重启服务）与 `SO_REUSEPORT`（4.14 语境下的多 accept 负载均衡，书在 7.12 惊群处兑现）。

### ET 模式标准读写循环（🔧 骨架，4.14.3 书意转述+现代库惯例）

```c
// Linux 语义，本机（Windows）不可实测 ⚠️——以下为 ET 纪律的最小骨架
// 注册：EPOLLIN|EPOLLET|EPOLLOUT(按需)；fd 必须非阻塞（ET 不配非阻塞=死锁式读挂）
for (;;) {
    n = epoll_wait(epfd, evs, MAXEV, timeout_ms);
    for (i = 0; i < n; ++i) {
        if (evs[i].events & EPOLLIN) {
            for (;;) {                       // 读干为止：ET 的"义务"所在
                r = read(fd, buf, sizeof buf);
                if (r > 0)  on_data(buf, r);           // 继续循环，不 break
                else if (r == 0) { close_conn(fd); break; }   // 对端 FIN
                else if (errno == EAGAIN) break;              // 读干净，等下一个边沿
                else { close_conn(fd); break; }               // 真错误
            }
        }
        if (evs[i].events & EPOLLOUT) { /* 循环 writev 到 EAGAIN，剩余留发送缓冲 */ }
    }
}
```

LT 版只删"内层 for(;;)"——一次事件读一块，内核还会再报。ET 的全部事故都藏在
"on_data 抛异常/提前 return 导致没读到 EAGAIN"这一句里，这就是 08 章 Redis 选 LT 的源码级注脚。

## 权衡与边界

- **select/poll vs epoll vs IOCP**：前两者跨平台（Windows 的 select 连非 TCP fd 都支持有限）；
  epoll 是 Linux 就绪通知式；IOCP 是 Windows 完成通知式（"何时可读" vs "读写已完成"）——
  跨平台库（boost::asio/ACE）要把抽象抹到"事件循环+每 fd 处理器"，两套原生模型必须分别映射，书 7.8 的分层由此而来。
- **ET vs LT**：ET 省唤醒、涨事故面（漏读饿死、与 epoll_ctl(MOD) 的成本互抵）；LT 容错、高吞吐下多几次
  无谓唤醒。选择依据是 handler 纪律能否审计——工业主流（Redis/muduo）宁要 LT 的确定性。
- **阻塞 vs 非阻塞 socket（4.6.4）**：阻塞码在专用工作线程里仍可接受（业务线程模型）；
  任何 event loop 里的 fd 必须非阻塞；listenfd 必须非阻塞（7.12.1 理由：惊群下 accept 竞争会挂住 loop）。

## 相邻概念对比

| 维度 | select | poll | epoll | IOCP |
| --- | --- | --- | --- | --- |
| fd 上限 | 1024 位图 | 无（内存） | 无 | 无 |
| 每次成本 | O(N)×3 | O(N)×2 | O(就绪) | 内核代管 |
| 触发语义 | 水平 | 水平 | LT/ET 可选 | 完成通知 |
| 线程模型适配 | 每线程一副本 | 同左 | 树可共享 | 天然多线程 |
| 平台 | 跨（含 Win） | 跨 | Linux | Windows |

## 最新演进与工业实践

- **io_uring（2019 起，Linux 5.1+）**：把"就绪通知"升级为"提交队列/完成队列共享环"——
  `io_uring_submit` 批量提交 SQE、CQE 收割完成，网络收发本身可异步化（`accept/recv/send` opcode），
  epoll 循环可被整体替换；`IOSQE_POLL` 类还能"猜就绪则免中断"。一手文档：内核手册页
  [io_uring(7) @ man7](https://man7.org/linux/man-pages/man7/io_uring.7.html)（已核实可达）、
  用户态库 [axboe/liburing](https://github.com/axboe/liburing)（作者 Jens Axboe；本机 GitHub 直连被策略拦截 ⚠️，
  经检索与 man-pages 交叉确认存在且活跃）。⚠️ Windows 无对应物（IOCP 是其精神近亲），**本机不可实测**。
- **TCP Fast Open（RFC 7413）**：4.9 "连接时带第一组数据"的标准化后代，SYN 即可携带 payload。
- **异步 DNS**：`getaddrinfo_a`/c-ares 把 4.17 的阻塞点挪出事件循环；glibc 的 NSS 缓存陷阱（nscd/systemd-resolved）是现代部署常识。
- **现代开源对照**：libevent/libuv（三平台复用抽象，epoll+EVFSTAT+IOCP 的后端拼装）、
  boost::asio 的 reactor/proactor 双概念（其 io_context 在 Windows 后端即 IOCP）；
  seastar 用"每核一个 epoll loop + DPDK/posix 双栈"把 4.14 的 ET 纪律发挥到极致（见 07 章）。

## 本章小结

4.14 的三句总结（书意转述）：epoll 把"监视成本"从每次调用摊销到每次注册；ET 把"读干净"变成程序员的义务；
LT 把这个义务还给内核——**理解谁欠谁，比记住参数位重要**。
