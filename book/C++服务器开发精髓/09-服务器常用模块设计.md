# 第9章 服务器开发中的常用模块设计 — 重连、心跳、日志、错误码与监控

> 对应原书第 9 章（§9.1–9.5，原书第 681–752 页）。目录经豆瓣条目 35491437 核实 ✅。
> 收尾章：前八章造出"能跑的服务"，本章补"能活很久的服务"四件套——
> 断线重连、心跳保活、日志系统、错误码体系，外加监控端口。全章是运维视角的设计清单，
> 9.3 日志一节独占近半篇幅（9.3.1–9.3.10），是本章与 07 章缓冲区设计之后第二处"深水区"。

## 核心概念速览（中英对照）

- **断线自动重连** — auto reconnect with backoff：指数退避+抖动（jitter）的重连策略，9.1
- **TCP keepalive** — `SO_KEEPALIVE`（75s/9 次/75s 默认）：内核层探活，对端掉电/半开连接的兜底，9.2.1
- **应用层心跳** — application heartbeat：带内保活报文，兼探"进程活着但卡死"，9.2.2
- **带业务数据的心跳** — piggybacked heartbeat：有数据时不再发空心跳（省流量），9.2.4
- **心跳代理修正** — heartbeat keep-alive through proxy：NAT/LB 空闲超时倒逼的最小心跳频率，9.2.3
- **异步日志** — asynchronous logging：前端格式化+入队，后端线程批量落盘，9.3.2
- **背压** — backpressure：日志队列满时"丢/堵/降"三选一的生产-消费表态，9.3.2 语境
- **日志分级与滚动** — log level / rotation：DEBUG–FATAL 等级、按大小/日期切文件（9.3.2/9.3.6）
- **集中式/分布式日志** — centralized logging（ELK 类）：多机日志汇聚检索，9.3.7
- **数据包日志** — packet dump log：hexdump 级协议取证日志，9.3.3（与 5.8 tcpdump 分工：应用内 vs 线缆上）
- **性能日志** — performance/timing log：关键路径耗时打点，9.3.5（当代演进=tracing）
- **错误码系统** — error code design：分段/分层的机读错误契约，与 HTTP 状态码分类学同宗，9.4
- **监控端口** — admin/monitor port：独立于业务端口的只读自省接口（stats/健康检查/动态开关），9.5
- **日志递进缩减** — log level ramp-down：开发期 DEBUG 上产线 INFO 的治理节奏，9.3.10

## 动机：长命服务的四个慢性病

TCP 连接的"死亡"是静默的（9.2 开篇：对端拔线/进程假死，本端 read 永远等不到 FIN）；
日志慢会拖垮热路径（同步 fprintf 的 fsync 尖刺）、错误码乱会毁掉排障（9.4）、
没有自省接口则线上不可治理（9.5）。四件都不是"性能"问题而是**可运维性**问题——
作者把第 9 章排在源码分析之后，正是"先会造，再会养"的次序。

## 机制：四件套逐个拆

### 9.1–9.2 重连与心跳（一对必须同时设计的机制）

重连（9.1）的要点：区分"主动关/被动断"、退避重试（书给 1s→2s→4s→封顶+随机抖动的经典序列——
防重连风暴 thundering herd 的客户端侧版本）、**重连后状态重建**（鉴权、订阅、序列号续传——
协议要预留 resume 语义，06 章协议设计的隐藏考题）。
心跳三层（9.2）：内核 keepalive（零代码但只到 TCP 层，且默认参数下首包 75 s）、
应用心跳（间隔 = min(链路空闲超时)/2 类经验律；超时阈值 = N 个 RTT + 容忍，书给参数表）、
带数据即心跳（9.2.4，省掉 9.2.5 担心的移动端流量税）。9.2.3 点破一个现代常识：
**移动网络 NAT/中间 LB 会静默杀空闲流**，心跳是替网络拓扑交的税；9.2.6/9.2.7 则把心跳日志降噪
（每 N 次心跳打一条，否则日志被保活包淹没——9.3.10 缩减策略的先声）。

### 9.3 日志系统（本章心脏）

9.3.2 的技术实现拆解，书的路子正是"前端-队列-后端"三段：
1. **前端**：调用点只做格式化进内存缓冲（等级过滤在锁外做，级别判断短路）；
2. **队列**：环形/阻塞队列解耦"产生速度"与"磁盘速度"——**异步日志的全部风险都在这一段的满/空策略上**；
3. **后端**：独立线程批量 write + 周期性 fsync（掉电丢多少日志=缓冲深度+sync 策略），
   滚动/压缩/按类型分文件（9.3.6）。
其余各节是"日志内容治理"：包日志 hexdump（9.3.3，注意敏感字段脱敏，与 9.3.9 呼应）、
性能日志打点（9.3.5）、业务字段规范（9.3.7：traceid/uid 可检索性——集中式日志的先决条件）、
敏感信息红线（9.3.9）、递进缩减（9.3.10）。

**实测**（`t07_asynclog.cpp`，g++ 15.2，win32 线程模型）：4 生产者 × 25,000 行 →
有界环形队列（8192 槽，mutex+双 condvar）→ 单落盘线程攒批（≤256KB/batch）fwrite。
**100,000 行全部落盘、零丢弃，耗时 22.2 ms ≈ 4.5M 行/秒**；背压策略演示了"丢+计数"分支
（注释中同步给出"阻塞等待"分支的写法——两种背压形态各一行代码的差距，但**丢日志要计数可观测**是 9.3 的立场）。
过程中栽进 9.3/7.7 联合考过的两个真坑（后述实测记录）。

### 9.4 错误码系统

书的核心主张：错误码是**给机器读的 API**（人读文案走日志）。设计点：
全局唯一注册表（禁"各模块自撞"）、分段（`模块段|类别|明细` 位域式）或分层（HTTP 状态码分类学的私有化，
1xx 可重试/4xx 调用方错/5xx 服务方错——6.11 SMTP 的三段式在这里兑现）、
**可重试性必须编码进码本身**（9.4.2 实践表：网络层错误→退避重试、业务错误→不重试）。

### 9.5 监控端口

与业务端口隔离的只读接口：`stats`（累计计数器快照）、健康检查（liveness/readiness 二分的 2021 年中文雏形）、
动态开关（日志级别热调/采样率）；书强调**鉴权与最小暴露**（监控端口被扫是常见事故）。

## 权衡与边界

- **心跳频率三角**：更短=更快发现死链、更省 NAT 税、更耗电/耗流量——9.2.5 的移动端视角即三方博弈，
  没有银弹只有参数表。
- **异步日志队列**：无界=OOM 风险、有界+丢=可能丢关键错误行、有界+堵=把磁盘尖刺传染业务线程。
  书与实测给出的折中：**默认丢（计数+告警）、错误级别可越队直写、或分级双队列**（普通异步/严重同步）。
- **同步刷盘的幻觉**：`fsync` 只保证"交给内核"，掉电场景要 NVMe FUA/PMEM 才闭环——9.3.2 的"崩溃丢几条"讨论在云盘时代更复杂 ⚠️（云厂商刷盘语义各异，书未展开）。
- **错误码 vs 异常**：跨进程边界（网络协议）必用码；进程内模块边界按 1.x RAII 哲学异常可用——
  书的"错误码面向机器、日志面向人"在两种载体上同时成立。

## 相邻概念对比

| 手段 | 检出什么 | 检出时延 | 成本 |
| --- | --- | --- | --- |
| TCP keepalive | 内核层死链 | 分钟级（默认参） | 零代码 |
| 应用心跳 | 进程卡死/假活 | 秒级（可调） | 流量+代码 |
| 读写错误（EPIPE/recv0） | 已发生的断 | 即时 | 无 |
| 监控端口探活 | 整机可用性 | 平台拉取周期 | 平台依赖 |

日志 vs tcpdump（9.3.3 包日志）：前者懂应用语义（traceid 串因果）但只看得到自己；
后者看得见全链路争辩但无业务上下文——**包日志是两者间的翻译层**（5.8 与 9.3 合读）。

## 最新演进与工业实践

- **结构化日志统治**：字段化（JSON/key=value）+ 集中检索（Loki/ClickHouse/ES）取代自由文本；
  C++ 侧 spdlog（同步/异步双模、按 size/daily 滚动，[github.com/gabime/spdlog](https://github.com/gabime/spdlog)，
  检索核实）与 glog 是 9.3.2 的现成实现——spdlog 的异步线程池模式与本章实测 t07 结构同构。
- **tracing 三件套**（metrics/logs/traces）：9.3.5 性能日志的当代形态是 OpenTelemetry——
  traceparent 头跨服务传播（HTTP/W3C Trace Context 标准），"日志里带 traceid"（9.3.7 主张）已是平台内建。
- **心跳的替代与消亡**：HTTP/2 与 gRPC 用 PING 帧/Ping 流做 keepalive（`keepalive_time/timeout` 参数与
  9.2 经验律一字不差，gRPC keepalive 文档为现行规范）；QUIC 把空闲超时会话复活内建进传输层；
  长连接网关（Envoy）的 `idle_timeout/stream_idle_timeout` 是"9.2.3 代理场景"的平台化。
- **错误码的标准位**：`std::errc`/`std::error_code`（C++11，标准库层；本目录 [../C++标准库/10-国际化数值并发与分配器.md](../C++标准库/10-国际化数值并发与分配器.md) 有专节）

## 实测记录 🔧

- `t07_asynclog.cpp`（g++ 15.2）：结论见上文——**100,000 行 / 22.2 ms / 零丢弃 / 文件字节数校验一致**。
- 过程中复现并修复两个"教科书级"队列 bug：① 消费者索引忘取模（环形缓冲越界，UB 挂死）；
  ② 尾指针取模回绕而头指针单调递增 → "队满"判定永久失效（丢日志分支被误触发、消费停滞）。
  教训通用：**ring buffer 的 head/tail 要么都单调（推荐，判满=head-tail==cap）、要么都取模（判满需留空槽）**——
  混用即事故，正是 9.3/7.7 所防的那类"静默错误"。
- keepalive/监控端口属 Linux socket 选项与服务端设施，Windows 本机可配 `SO_KEEPALIVE`+`tcpkeepalive`（winsock）
  但默认参数验证依赖真实断链场景，未实测 ⚠️。
