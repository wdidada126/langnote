# 第6章 网络通信协议设计 — 粘包、TLV、压缩与 HTTP/WebSocket

> 对应原书第 6 章（§6.1–6.12，原书第 422–514 页）。目录经豆瓣条目 35491437 核实 ✅。
> 全书"设计观"最重的一章：从 TCP 字节流本质出发，一路推到自定义二进制协议（TLV）、
> 整型压缩、XML/JSON、HTTP、SMTP/POP3、WebSocket 的完整光谱——作者团队自研 IM/推送协议的实战沉淀（6.9 自定义协议示例是全章落点）。

## 核心概念速览（中英对照）

- **粘包/拆包** — message batching / fragmentation：TCP 是无消息边界的字节流，应用层必须自带"包从哪开始到哪结束"的编码
- **TLV** — Type-Length-Value：字段带类型与长度的自描述编码，协议演化的最小充分机制
- **整型压缩** — integer compression（varint/LEB128）：小值少占字节的可变长编码
- **ZigZag 编码** — signed→unsigned 映射：让小负数也获得短 varint（protobuf sint 族）
- **包分片** — chunking/fragmentation：payload 超单包上限时的切片-重组协议（6.7）
- **字节对齐** — byte alignment：跨平台结构体直传的第一颗雷（与 4.16 大小端并列）
- **定长字段** — explicit field width：协议里用 `int32_t` 而非 `int`/`long`（6.6.2）
- **keep-alive/长连接** — HTTP persistent connection：6.10.6，连接复用对握手风暴的缓解
- **chunked 编码** — HTTP chunked transfer：6.10.3，"长度未知也能流式"的分块编码（与 TLV 同构）
- **WebSocket 握手/帧** — upgrade handshake + masked frame：把 TCP 全双工字节流套上"消息语义"（6.12）
- **permessage-deflate** — WebSocket 帧压缩扩展（6.12.3）
- **RESTful** — 资源化 URL + 方法语义的 HTTP 使用约定（6.10.8 以 Java Spring MVC 为镜）
- **协议版本位** — protocol version field：6.6.5 自动升级功能的前提

## 动机：不设计协议，就会被 TCP 设计你

6.1 的立论一句话：**TCP 保证字节流有序可靠，但从不保证"消息边界"**——发两次 `send("AAA")`、
`send("BBB")`，对端 recv 完全可能一次收到 `AAABBB`（粘包）或 `AA`/`ABBB`（拆包）。
所以**边界责任在应用层**：要么带内定界（长度/分隔符）、要么带外分道（每消息一连接）。
本章后续所有小节都是这个命题的展开。

## 机制：四组核心

### 6.2–6.4 从 struct 到 TLV 的演化台阶

书给出的演化序列（6.4.1）——每一级都在解决上一级的痛点：

1. **裸 struct 直传**：最快，但字节对齐、大小端、字段增删全把协议焊死在编译器布局上（6.6.1/6.6.4 两大雷：
   `#pragma pack` 治标、`memcpy+ntohl` 手写治标中）；
2. **定长头 + 定长体**（`magic|version|len|body`）：解决边界（len 字段）与最低限度演化（version）；
3. **定长头 + 变长体**：加一条消息一种格式，格式爆炸；
4. **TLV**：字段级自描述——**未知 Type 可跳过**（旧端读新协议不死）、可选字段零成本、Type 空间即字段命名空间；
   代价是解析要遍历（无索引）、Length 校验是安全生命线（恶意 length → 缓冲区事故）。
   6.4.3 顺带给出协议设计工具（IDL 代码生成）的位置，自然引出 protobuf 类工具的必要性。
   解析框架（6.3）书里是"状态机 + 环形缓冲：读够头部拿 len、读够 len 回调、剩余留buffer"——
   即 muduo `LengthBasedCodec` 同款（07 章 7.6/7.7 的接口侧）。

### 6.5 整型压缩：把"数字大小≠数字宽度"讲透

定宽 int32 存 1 也占 4 字节。varint：每字节低 7 位存值、最高位续接标志（ASCII 值 1 字节、
65535 三字节）。**实测**（`t05_varint.cpp`，g++ 15.2）：{0,1,127,128,300,2^20,2^40,2^64-1}
编解码往返全部 OK；8 样本合计 64B 定宽 → 26B varint（2.46×）；ZigZag 修正后 zz(-1)=1
（小负数不再膨胀为 10 字节——protobuf `sint32/64` 的机制）。同一编码在 HTTP/2 HPACK 整数、
protobuf varint、LEB128（ELF DWARF）中各自独立出现——**一个 40 年老招统治所有现代二进制协议**。

### 6.7–6.10 分片、文本协议与 HTTP

- 包分片（6.7）：消息 > 单包上限（网络 MTU、服务端 max_body、内存保护）时的分片头
  （`total|index|flag`）与重组超时；强调**分片与粘包是同一枚硬币**——都是"边界与尺寸"管理。
- XML/JSON（6.8）：文本协议账本——人可读/通用解析器 vs 体积膨胀 3–10 倍 + 解析 CPU；
  书的结论不是"binary 好"，而是**按运维人群与量级选型**，这是 6.8 最有价值的立场。
- HTTP（6.10）：请求/响应文本格式、GET/POST 语义、chunked（分块编码即 TLV 变体）、
  长连接与 `Connection: keep-alive`（6.10.6，与 9.2 心跳共章议题）、libcurl（6.10.7）、
  RESTful 与 Spring MVC 对照（6.10.8——中文服务器书里少见的跨栈视野）。

### 6.11–6.12 邮件协议与 WebSocket 精读

- SMTP 对话（421/250 状态码三段式）与 POP3（UIDL 去重）：作者拿它们当"文本协议设计史"讲——
  状态码分类学（1xx–5xx）直接启发 9.4 错误码系统设计；
- WebSocket（6.12）：HTTP Upgrade 握手（`Sec-WebSocket-Key/Accept` 的 SHA1 魔术串）、
  帧格式（FIN/opcode/payload len 7/16/64 三档——变长整数第三次现身、客户端→服务端必须掩码防代理缓存投毒）、
  扩展协商（permessage-deflate）；6.12.4–6.12.5 给出装包解包与握手解析代码，是全章把"自定义协议"方法论
  在真实标准协议上验收的习题。

### 6.9 自定义协议示例拆解：把前面所有小节缝成一个帧（🔧 结构骨架，书意转述）

6.9 给出的示例协议是全章方法论的验收件，帧布局（位域示意，均网络字节序 + 显式定宽，6.6.2/6.6.4 落地）：

```
+--------+--------+--------+--------+----------------------------------+
| magic  |version |  flags  | cmdtype |  body_len (varint, 6.5)        |  ← 定长头 + 变长长度
+--------+--------+--------+--------+----------------------------------+
|                        body: TLV 序列 (0..N 个 Type, 6.4)             |  ← 字段级演化空间
+---------------------------------------------------------------------+
|                        可选 payload: 压缩后的业务包 (6.7 分片时带     |
|                        total/index/flag 三个 TLV 前置字段)            |
+---------------------------------------------------------------------+
```

要点复盘：magic+version 管"是不是我们的协议/能不能演进"（6.6.5 自动升级的前提）；
flags 留压缩/分片/加密位（每位的含义永久占坑——发布前写注册表，9.4 错误码注册表的镜像纪律）；
body_len 用 varint 而非定长 4 字节（6.5 实测 2.46× 的直观收益）；TLV 体允许旧端跳过未知 Type；
echo/心跳消息（cmdtype 里的两个特殊值）与 9.2 直接对接。**一个好的自定义协议=本章每小节各贡献一个字段。**

## 权衡与边界

- **分隔符 vs 定长 vs 长度前缀**：分隔符协议（行协议/SMTP 式）可读但值内转义税重；
  定长浪费但零解析；长度前缀是工程默认——三者与 6.3/6.4 台阶一一对应。
- **ID/TLV vs schema（protobuf）**：TLV 自描述换来"无 schema 也能跳过未知字段"，
  protobuf 用 schema + tag 号换取强类型与更高密度；两者的演化承诺相同：**加字段不破坏旧端、未知 tag 保留/跳过**。
- **文本 vs 二进制不是信仰问题**：内部高频 RPC 用二进制、对外公开 API 用 JSON/HTTP——6.8 的"场景选型"与
  6.10.8 REST 并存即是答案。

## 相邻概念对比

- **HTTP chunked vs 自定义长度前缀**：同一机制的文本化（hex 长度行）与二进制化（定宽/ varint 长度）两副面孔。
- **WebSocket vs 长连接+心跳（9.2）**：WS 是"浏览器里的 TCP"——消息边界+双向+穿透 HTTP 基建；
  原生 app 端自研协议在边界问题上要做 WS 已经替你做的全部功课。
- **分片（6.7） vs IP 分片**：应用层分片可控可重组超时，IP 分片丢一片全丢——高性能协议栈宁可用 MTU 探测也不赌 IP 分片。

## 最新演进与工业实践

- **HTTP/2（RFC 7540）与 HPACK**：二进制分帧层（帧头 `length(24b)|type|flags|streamId(31b)`）就是 6.4 定长头+变长体的工业化；
  HPACK 整数编码是 varint 的逐位同款；多路复用把"连接级边界"下沉到"流级边界"。
- **HTTP/3/QUIC（RFC 9000）**：把重传/流控搬进用户态 UDP——"粘包问题"被釜底抽薪（每 stream 天然消息通道）；
  代价：自建拥塞控制（见 CS144 的 TCP 状态机 → QUIC 对照阅读）。
- **protobuf/flatbuffers**：protobuf（varint+tag，Google 系全栈）；flatbuffers（零拷贝访问、游戏/嵌入式高频选型）——
  两者是 6.4.3 "协议设计工具"的终局形态。
- **现代开源对照**：drogon（内置 JSON/自定义控制器，WebSocket 客户端/服务端一体，本机 xmake 包缓存中即有 v1.9.3）；
  brpc 的 baidu_std 协议（定长头+protobuf body 的教科书实现，[apache/brpc](https://github.com/apache/brpc) 仓库；本机直连抓取被策略拦截 ⚠️ 按检索核实存在）。
