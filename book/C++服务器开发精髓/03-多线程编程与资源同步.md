# 第3章 多线程编程与资源同步 — 从 OS 原语到线程池与协程

> 对应原书第 3 章（§3.1–3.13，原书第 159–281 页）。目录经豆瓣条目 35491437 核实 ✅。
> 全书分量最重的一章：Linux（pthread）/Windows（API）/C++11（std）三套线程设施并排讲，
> 并以 3.12 线程池、3.13 纤程/协程收口——这一章是 07 章服务结构的直接地基。

## 核心概念速览（中英对照）

- **线程** — thread：进程内共享地址空间的调度单位；一个进程多任务
- **线程局部存储** — Thread Local Storage, TLS（`__declspec(thread)`/`__thread`/`thread_local`）：每线程一份的变量副本
- **互斥量/临界区** — mutex / critical section：同一时刻只有一个持有者的独占锁
- **信号量** — semaphore：计数许可，P/V（wait/post）操作，可跨进程（命名）
- **条件变量** — condition variable：与互斥量配合的"等待谓词为真"唤醒机制，必须配 while/带谓词 wait 防虚假唤醒
- **读写锁** — readers-writer lock / rwlock：多读单写；`std::shared_mutex`（C++17）
- **原子操作** — atomic operation（`Interlocked*`/`__sync_*`/`std::atomic`）：硬件 LOCK 前缀指令封装的不可分割读改写
- **数据竞争** — data race：两个线程无同步地访问同一内存且至少一写——未定义行为
- **死锁/活锁** — deadlock / livelock：循环等待锁 vs 互相谦让不休眠；3.9.4/3.9.5
- **纤程** — fiber：用户态可挂起的执行流，调度权完全在程序手里（Windows FIBER）
- **协程** — coroutine：可 yield/resume 的轻量执行流；书中指 Lua 风格协作式协程
- **线程池** — thread pool：固定工人 + 任务队列，把"每任务一线程"换成"每任务一入队"
- **环形队列** — ring buffer / circular queue：定长数组 + 头尾游标的生产者-消费者缓冲，3.12.2
- **`scheduler-locking`** — 调试期线程调度冻结：见 02 章实测

## 动机：服务器为什么绕不开"多线程 + 同步"

长连接服务的时间开销大头是 IO，但**业务计算、定时器、日志落盘、多核扩展**都必须把线程用起来；
线程一多，共享可变状态就是原罪。书给出的路径是教科书级的三步：先用 OS 原语（3.5/3.6）建立
"机制直觉"，再收敛到 C++11 标准封装（3.7），最后落到两条工程总成——3.12 线程池与 3.13 协程。
值得注意的写法：每个话题都 Linux/Windows 双轨（如 3.4.2 专门讲 `InterlockedIncrement`），
这在国产服务器书里少见，也和作者长期做跨平台框架的背景一致。

## 机制：四组关键细节

### 3.1–3.3 线程本体（概念层最容易答错的三题）

- **主线程 return ≠ 进程立即终止**，但 `exit()/ReturnFromMain` 会让所有支线程立刻消亡——栈对象不析构、RAII 失效（呼应 1.1）；线程函数 return/`pthread_exit` 只结束自己。
- **某线程崩溃 = 整个进程崩溃**（Linux 信号默认动作杀进程；Windows SEH 未捕获同样终止进程），所以"崩一个线程再拉起一个"的设想在**进程内**不成立，要靠多进程（07 章 master-worker 结构的理由之一）。
- **join 语义**：不 join 也不 detach 的 std::thread 析构直接 terminate——书 3.2.3 用 Linux/Windows 双例说明回收资源义务。

### 3.4 原子操作：从"为什么 `i++` 不安全"开始

机制链：`i++` 编译为 load-add-store 三步（书 3.4.1 逐指令拆）→ 平台提供带锁总线指令：Linux `lock incl`/`__sync_fetch_and_add`，Windows `InterlockedIncrement`（3.4.2）→
C++11 `std::atomic<int>` 统一封装并补上内存序（3.4.3，`memory_order_*` 的深水区本书点到为止，见互链）。
**实测**（g++ 15.2，win32 线程模型）：8 线程 × 100 万自增——`std::atomic` 恒得 8,000,000；
裸 `int` 两次运行分别得 1,790,810 / 1,956,861，竞争规模肉眼可见（`t02_lockfree.cpp`）。

### 3.5–3.7 三套同步原语对表（本章主干）

| 功能 | Linux | Windows | C++11/17 | 机制注脚 |
| --- | --- | --- | --- | --- |
| 互斥 | `pthread_mutex_t` | CRITICAL_SECTION | `std::mutex` | Windows 临界区仅本进程、且自旋后挂起（用户态→内核态两级） |
| 计数许可 | `sem_t`/System V | Semaphore 内核对象 | `std::counting_semaphore`(C++20) | 命名信号量是老的跨进程 IPC 通道 |
| 等待-唤醒 | condvar | Event（auto/manual） | `std::condition_variable` | 书 3.6.3 把 Event 讲成"Windows 的条件变量"，语义对应 manual-reset≈notify_all |
| 读写 | rwlock | SRWLock | `std::shared_mutex` | 写优先策略是实现定义，防写者饥饿不可依赖 |
| 跨进程共享 | 共享内存+futex | 命名内核对象 + `CreateShared`（3.6.8） | —— | C++ 标准无跨进程同步 |

`std::condition_variable` 的三个必讲坑书都覆盖了：**必须配 predicate 的 wait**（丢唤醒/虚假唤醒）、
**wait 期间才释放锁**（唤醒-检查-挂起必须原子，2 章实测的丢唤醒事故即源于此类边界）、
**notify 放锁内还是锁外**（性能与优先反转的权衡）。

### 3.9 锁经验（全章最短也最可执行）

减少次数（批量取任务而不是取一个加一次）、明确范围（作用域锁 `lock_guard` 自动边界）、
缩小粒度（分片锁）、防死锁（锁序全局化 / `std::scoped_lock` 多锁原子获取 / 超时退让）、
防活锁（退避加随机）。3.10 TLS 三平台对照 + 3.11 C 库非线程安全函数清单（`strtok/localtime/gmtime`→
`_r` 族）是"扫雷表"性质的附录。

### 3.12–3.13 线程池与纤程/协程

线程池设计（3.12.1）：工人循环 `wait → 取任务 → 锁外执行`（书强调执行必须在锁外，否则任务间串行化）；
环形队列（3.12.2）给出定长无 malloc 的生产者-消费者缓冲；消息中间件（3.12.3）把同一抽象抬到进程间。
3.13 纤程（Windows API `CreateFiber/SwitchToFiber`）与协程（Lua `coroutine.create/resume/yield`）
并讲——作者立场是"协程 = 把调度权收回用户态的线程"，这是 07 章 one loop per thread 的伏笔。

## 权衡与边界（本目录实测支撑）

- **线程池 vs 协程调度**：线程池以"任务排队"换线程数可控，但任务阻塞（如同步 IO）会占死工人；
  协程以"挂起换 CPU"解决等待密集任务，但**一次阻塞调用毒化整个载体线程**，且调试栈碎片化。
  经验分界：CPU 密集→线程池；IO 密集等待→事件循环+协程；混合→双池隔离（07 章 7.10 同一命题）。
- **锁 vs 无锁**：无锁的收益只在高竞争+低优先延迟场景；`t02` 同时演示了 Treiber 栈的 ABA 隐患
  ——pop 的 CAS 成功不代表 `old->next` 仍存活，书中路线是 tagged pointer（地址+计数器）或
  hazard pointer/epoch 回收。一手来源：Dmitry Vyukov《Efficient ABA Prevention》《Non-intrusive mpmc queue》
  ——**个人博客/非正式出版物**，原站 1024cores.net 已停服，可经 web.archive.org 检索快照 ⚠️（GitHub 直连被网络策略拦截，未能逐条验证原链）。
- **实测结果（`t01_threadpool.cpp`）**：4 工人 + mutex/cv 队列，200,000 个微任务 74 ms 消费完（≈2.7M 任务/s，std::function 堆分配含在内），
  证明"锁只在取任务瞬间"的朴素线程池在毫秒级任务下不构成瓶颈；任务再小一级（纯自增）则队列锁竞争开始主导，该换批量窃取。
- **一次自埋雷的诚实记录**：初版 submit 循环用 `[&]` 捕获循环变量 i——工人执行时 i 已推进，
  sum 得到 20,000,633,018 ≠ 19,999,900,000；改 `[&, v = i]` 后正确。**任务闭包必须按值捕获参数**，
  这是 3.3"类对象指针作为线程参数"惯用法的 lambda 时代变体。

## 相邻概念对比

- **mutex vs 自旋锁**：临界区 > 一次上下文切换代价（µs 级）才值得自旋；Linux futex 已是"用户态自旋+内核挂起"混合体。
- **semaphore vs condvar**：前者计数许可（天然做限流器），后者表达"状态谓词"；用信号量模拟条件变量易丢事件。
- **thread_local vs 锁分片**：TLS 是"消灭共享"路线，聚合后再合并（如每线程统计计数）；与 07 章 7.6"每连接单线程"同哲学。
- **fiber vs coroutine vs std::thread**：调度主体（OS/程序）、切换成本（内核态/用户态/零——编译器展平）、抢占性三点全不同；C++20 协程属于第三类（无栈、编译器生成状态机）。

## 最新演进与工业实践

- **C++20/23 并发包**：`std::jthread`（自动 join + `stop_token` 协作取消）、`std::latch/barrier`、
  `std::counting_semaphore`、`std::atomic_ref`；`std::execution`（P2300，[wg21.link/p2300](https://wg21.link/p2300) 可查）把"线程池+任务图"标准化为 sender/receiver——3.12 的未来形态。
- **C++20 协程落地网络库**：folly::coro（[facebook/folly](https://github.com/facebook/folly) repo 内 folly/coro）、
  boost::asio 的 `co_spawn/co_await`（官方文档 [boost.org/asio overview](https://www.boost.org/doc/libs/release/doc/html/boost_asio/overview/core/spawn.html)）、
  cppcoro（已被 folly 收编取代）；**07 章的反应堆回调地狱在 2026 年的标准解法就是协程化 reactor**——书里 3.13 的手搓 fiber 直觉被语言级特性兑现。
- **无锁设施标准化**：`std::atomic` 的 `wait/notify_one`（C++20）让 condvar 部分退休；folly 的 `AtomicHashMap`、
  moodycamel::ConcurrentQueue 是 Vyukov 思想的开源直系后代。
- **工业线程池**：folly `CPUThreadPoolExecutor`/`IOThreadPoolExecutor` 双池分工＝书 3.12+7.10 结论的库化；
  Java 式 virtual threads 在 C++ 生态的对应物是 libunwind+协程调度器（如 msvc 的 PPL task 或自研 scheduler）。
- **Windows 侧对照**：IOCP 本身是"内核线程池 + 完成端口"（7 章展开）；`SRWLock`/`SleepConditionVariableCS` 与 pthread 一一对应；本书实测（PATH/DLL 混载事故，见 02 章）说明 **win32 线程模型 MinGW 的 cv 语义可依赖，前提是不混链两套运行时**。

## 本章小结

同步原语是三套方言讲同一件事：**让"等待-检查-转移"成为原子动作**；
线程池与协程则是同一枚硬币的两面——都在回答"任务数 ≫ 内核可承受线程数时怎么办"。
