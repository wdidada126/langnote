# 07 · 应用：语义搜索、RAG 与混合检索（Applications）

> 覆盖本目录主题结构第 7 章（⚠️ 主题构造，见 [00-总览与阅读地图.md](00-总览与阅读地图.md)）。本书副标题的落点是 "to Applications"：向量数据库的价值最终在检索应用里兑现。本章 🔧 用玩具数据集把最容易被低估的工程语义——**元数据过滤与 KNN 的组合方式**——的召回代价量出来。

## 内容规格（小节地图，⚠️ 推定）

- **语义搜索**：query→embed→KNN→top-k；查询改写、HyDE（用假设文档向量检索）、多查询融合。
- **RAG 管道**：文档→切块（chunking 策略=召回率的第一杠杆）→嵌入→入库；问→embed→检索→拼提示→LLM。向量库在此是"非参数化记忆"。
- **混合检索（hybrid search）**：BM25 词面命中 + 向量语义命中，RRF（倒数排名融合）合并——2024–2026 生产默认答案；ES/OpenSearch/各专用库都已内置。
- **元数据过滤**：租户隔离、时间窗、权限标签与 KNN 的组合语义（本章实测主角）。
- **重排（rerank）**：ANN 粗召回 top-50~100 后交叉编码器精排——两阶段检索的标准形态。
- **多模态与场景**：图片/音频以图搜图、推荐召回（embedding-based retrieval）、去重（近重复检测）。

## 核心技术清单

- pre-filter / post-filter / filtered-HNSW 三策略（见实测）。
- RRF 公式：`score = Σ 1/(60 + rank_i)`——免调参融合的事实标准（⚠️ 通行做法转述）。
- chunk 重叠、按语义边界切分、父子块（small-to-big）检索。
- ACL/行级安全与向量检索的组合：过滤必须进索引内部才可信（06 章产品对比点）。
- 缓存层：query 嵌入缓存、结果缓存（设计数据密集型应用里的标准武器在此复用）。

## 🔧 实测：过滤 × KNN 的三种姿势与召回代价（玩具实现，非生产引擎行为）

数据同 01 章（10,000×64、60 簇、带 `cluster` 元数据）；过滤条件 `cluster=7`（命中 167/10000=1.7%）；"过滤后真值"=先过滤再对子集全量暴力；查询 100 条；脚本 `exp_g.py` F 段。

1. **post-filter（全库 KNN 取 top-k 再扔不合格）**：top-10 直出后过滤 → recall@10=**0.017**——几乎全灭（1.7% 选择率下 top-10 平均只剩 0.17 个幸存者）。
2. **overfetch（放大 k 再滤）**：top-100 → **0.162**；top-500 → **0.779**——想靠"多取点"救 post-filter，k 要放大 50 倍才勉强及格，成本随之线性涨；且选择率更低时彻底失效（数学上无上限保证）。
3. **pre-filter（先过滤、再对幸存者暴力）**：recall=**1.000，0.7 ms/q**（子集只有 167 条）——小选择率下最便宜且精确；但过滤后剩 500 万条时 pre-filter 就退回全库暴力问题。
4. **结论（玩具但方向正确）**：过滤越狠→pre-filter 越优；过滤越松→"索引内带过滤"（06 章 Qdrant/Milvus 的 filtered HNSW）才是稳态方案；post-filter+拍脑袋 overfetch 是事故配方。

## 易错点与陷阱

- **RAG 答错先查检索**：多数"幻觉"实为召回缺失——先用 ground truth 段落是否在 top-k 里定位（08 章 recall 口径），再怪生成器。
- **chunk 与嵌入模型互锁**：换切块策略≈换语料，需全量重灌（02 章版本管理同款坑）。
- **混合融合前不统一分数量纲**：BM25 分数无界、cosine 有界——直接加权求和会一边倒，用 RRF 按名次融合。
- **权限过滤放应用层**：先取回再在代码里扔=数据已出库，多租户场景是合规事故；过滤必须进存储/索引层（实测 4 的治理面）。
- **rerank 位置**：ANN 参数（ef/nprobe）没给足候选时，重排救不回未召回的内容——两阶段各自调参。

## 2026 视角补注

- **Agentic 检索**：2025 后 RAG 演进为 agent 多轮检索（查询分解、迭代检索、图+向量并用），向量库角色从"一次 top-k"变成"工具"（定性 ⚠️）。
- **混合检索原生化**：ES 8.x knn+RRF、Milvus 2.4+ 混合检索（稀疏向量 BM25/SPLADE 与稠密一把抓）、pgvector+tsvector 手工混合（⚠️ 各官方文档转述；仓库 ✅ 见 01 章演进节）。
- **edge 化**：SQLite/DuckDB 级本地向量（sqlite-vec、LanceDB）把本章应用带进端侧 RAG——与 06 章"嵌入式向量库"线呼应（sqlite-vec：asg017 出品，⚠️ 本机 HEAD 超时未验成；LanceDB 仓库 ✅ 200 已验，见 01 章）。

## RAG 排障分层表（症状→定位层→本章工具）

| 症状 | 第一定位层 | 工具/数字锚 |
| --- | --- | --- |
| 答案完全跑题 | 检索没召回依据段 | 对"标准答案所在文档"查 rank（recall@k 口径，08 章） |
| 答案半对半错 | 召回了但淹没在噪声里 | k 与 chunk 大小、rerank 位次（重排=位次手术） |
| 权限内容泄漏 | 过滤发生在应用层 | pre-filter 进索引（实测 3 的 1.000 姿势） |
| 新文档查不到 | 段未索引化/副本落后 | 写入可见性参数（06 章一致性光谱） |
| 长文档查碎句 | 切块无语义边界 | 父子块/small-to-big 回窗 |
| 同问不同答 | 查询嵌入前缀错配 | 02 章"读写共用预处理器"纪律 |
- 使用法：从上到下二分——先证明"依据段在不在 top-k"，再谈生成侧一切玄学。

## 混合与多阶段的预算分配（把召回率当总预算花）

- 词面腿（BM25）与语义腿（向量）覆盖的错误类型互补：拼写/专名/精确数字走词面，改写/跨语言/概念走语义——两腿 top-50 融合后 rerank，是"同样的延迟预算买到更大有效召回"的标准配方（⚠️ 通行实践）。
- 预算顺序建议：chunk 策略 > 召回参数（ef/nprobe/overfetch）> rerank 模型 > 生成提示工程——越上游杠杆越大，本册实测（0.017→0.779 的 overfetch 曲线）就是"召回参数这一档"的价格标签。
- 多查询/迭代检索（agent 化）本质是"把一次大预算换成 N 次小预算"：总 recall 可升，但延迟与成本乘 N——08 章方法学按总工作点结算。

## 数字台账（本章 🔧 值与出处）

| 数字 | 含义 | 出处 |
| --- | --- | --- |
| 167/10,000=1.7% | 过滤选择率（cluster=7） | `exp_g.py` F |
| 0.017 / 0.162 / 0.779 | post-filter top10/100/500 的 recall@10 | F1 |
| 1.000 @0.7 ms | pre-filter+子集暴力（167 条） | F2 |
- 外推提示（算术）：选择率 p 时 post-filter 期望幸存=k'×p 个——要 10 个幸存者需 k'≈10/p，p=1.7% 时即 ≈590，与实测 500 档 0.779 相符（模型-实验对表）。
- 再进一步（留给你的复玩）：把过滤条件换成"双字段与"（cluster=7 AND id%2=0，选择率 ≈0.85%），F1 三档应整体再 halve 上下——post-filter 的损失按选择率乘法叠加，这就是生产要求"组合过滤进索引"的定量理由。
- 口径备注：F 段与 08 章 G 表同进程产出（out_g3.txt），0.6/0.7 ms/q 两值之差即运行间抖动，玩具规模下 ≤15% 属正常带宽。

## Agent 时代"检索即工具"的三形态（06 章产品观的调用侧镜像）

- **top-k 工具**：把向量库包成 `search(query, k, filter)` 给 LLM 调用——最常见也最容易被滥用（k 由模型随口给）；防御=参数白名单+结果数上限。
- **迭代检索**：分解子问题→多轮 top-k→证据池去重合并——08 章工作点结算按"总延迟/总召回"计，不再是单次曲线。
- **图+向量双工具**：向量库找入口实体、图库沿关系扩展上下文（Neo4j 挂点）——两代相似检索（词面/几何）之外第三条腿"结构"。
- 对过滤语义的影响：agent 生成的 filter 表达式质量不稳定，pre/post 姿势要能在计划层切换（07 章实测就是切换的成本表）；生产上给 agent 的过滤器先过"选择率预估"再定策略。

## 缓存与成本的最后一公里（检索层之上的经济学）

- **查询嵌入缓存**：同一 query 反复嵌入在会话式应用里命中率可观——缓存键=预处理器版本+原文，两要素缺一即坐标系事故（02 章纪律）。
- **结果缓存的失效域**：文档更新、权限变更、过滤选择率变化都会使 top-k 缓存过期——失效粒度必须与"最严过滤维度"对齐（租户级而非全局）。
- **重排的账单**：cross-encoder 精排每候选一次前向，50 候选≈检索本身数倍成本——用 08 章"总工作点"结算，别只看质量增益。
- **冷热分层**：热租户常驻内存索引、冷租户磁盘/对象存储档（DiskANN/LanceDB 形态）——"一套库两种物理计划"是 2025 后托管产品的主流成本曲线（⚠️ 定性转述）。

## 核心概念速览（中英对照）

- **语义搜索** — Semantic search：按嵌入相似度返回内容。
- **RAG** — 检索增强生成：外部检索喂给 LLM 的管道。
- **切块** — Chunking：文档到检索单元的划分策略。
- **混合检索** — Hybrid search：词面(BM25)×语义(向量)融合。
- **RRF** — Reciprocal Rank Fusion：按名次融合，免量纲。
- **重排** — Reranking：交叉编码器对粗召回精排。
- **预过滤/后过滤** — Pre-/post-filter：过滤发生在 KNN 前/后。
- **过度取回** — Overfetch：放大 k 以补偿过滤损失。
- **HyDE** — 假设文档嵌入：用生成文本的向量检索真实文本。
- **稀疏向量** — Sparse vector：词面权重的向量形态（SPLADE/BM25 式）。

## 最新演进与工业实践

- **过滤即一等公民**：Qdrant（faceted filter 进 HNSW 遍历）、Weaviate（倒排+向量混合引擎）、Milvus（标量过滤+分区裁剪）都把本章实测 4 的"稳态方案"写进卖点（⚠️ 文档转述；代码仓库 ✅ 200 已验，链接见 01 章演进节）。
- **SQL 阵营的追赶**：SQL Server 2025 与 Oracle 23ai 的向量检索都是"WHERE + ORDER BY distance + LIMIT"的原生 SQL 形态，过滤语义天然正确（⚠️ 微软/甲骨文文档转述；Oracle 页 ✅ 200 已验）。
- **评测新形态**：RAG 端到端评测框架（RAGAS 等）与向量检索指标（08 章）分层配合——检索 recall 是 RAG 质量的下界（定性 ⚠️）。
