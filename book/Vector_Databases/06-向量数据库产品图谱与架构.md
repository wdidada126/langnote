# 06 · 向量数据库产品图谱与架构（Products & Internals）

> 覆盖本目录主题结构第 6 章（⚠️ 主题构造，见 [00-总览与阅读地图.md](00-总览与阅读地图.md)）。本章把市面产品摆进两张表：横向"专用引擎 vs 库内向量 vs 嵌入式"，纵向"写入路径→段/索引→查询路径→过滤→分片副本"的通用架构骨架。🔧 用 DuckDB 1.5.5 当"能整机拆开的向量数据库标本"。

## 内容规格（小节地图，⚠️ 推定）

- **专用向量数据库**：Pinecone（全托管/服务端）、Weaviate、Qdrant、Milvus（分布式重器）、Zilliz Cloud、Vespa、 turbopuffer（对象存储分层新锐，2024）——卖点是"向量为一等公民"的完整数据库能力。
- **通用数据库内向量**：PostgreSQL+pgvector、Oracle 23ai `VECTOR`、SQL Server 2025/Azure SQL `VECTOR`、Elasticsearch/OpenSearch `dense_vector`、ClickHouse、SingleStore、TiDB、Cassandra 5.x 向量演进（与兄弟册 #92 的挂点）。
- **嵌入式/库形态**：Chroma、LanceDB、sqlite-vec、DuckDB vss、hnswlib/faiss/annoy/scann（索引库，不是数据库）。
- **架构五件套**：①WAL/持久化 ②growing→sealed 段模型（LSM 血统：写入先进内存小段，后台建索引归并）③索引层（04/05 章算法的产品化）④标量过滤子系统（倒排+bitmap，07 章实测语义）⑤分片/副本/scatter-gather。
- **一致性光谱**：向量索引天然是"最终一致的近似结构"——写入可见性、副本 staleness、删除墓碑的可见语义各产品参数不同（本章给辨析框架，具体参数 ⚠️ 文档转述）。

## 核心技术清单

- 段的形态：raw vectors（精确重排/暴力兜底）+ 压缩码（量化）+ 图/倒排索引 + 标量索引四件套同段共存。
- 多租户：collection/namespace/partition 三级隔离——Milvus partition key、Pinecone namespace、Qdrant payload partition 同一思想（⚠️ 文档转述）。
- 内存模型：HNSW 全内存 → DiskANN 磁盘图 → 对象存储分层（turbopuffer/LanceDB）是"成本每 GB 递减、延迟每跳递增"的三代选择。
- 存算分离：查询节点无状态、索引在共享存储——2024 后 Pinecone Serverless/Zilliz 的官方叙事（⚠️ 转述）。
- "向量索引是缓存"论：任何索引坏了都能靠 raw 暴力重建——持久化只保证 raw，索引文件可丢可重算（工程心态）。

## 🔧 实测：DuckDB——拆给你看的"库内向量"最小标本（1.5.5；引擎真实行为，数据玩具）

1. **零扩展形态**：`FLOAT[]/DOUBLE[]` 列 + `list_cosine_similarity/list_distance` 即"无索引向量数据库"：万级单查 warm **10.2 ms**、参数化循环 58.7 ms/q（01 章同源，重跑稳定）——小体量 RAG 的完全体，无额外依赖。
2. **扩展形态**：`INSTALL vss` 一行装成（commit b833341 ✅）；HNSW 索引 1.68 s 建成、3.78 ms/q recall@10=0.908（05 章实测二）——同一引擎"暴力/索引"两档共存，正是很多产品的真实分层。
3. **类型契约**：vss 只吃 `FLOAT[N]` 定长数组，`DOUBLE[64]` 建索引直接 Binder Error——列式引擎把"维度是 schema 一部分"写得明明白白（对比专用库 collection 级 dimension 固定，同款约束）。
4. **SQL 组合语义**：过滤+KNN 就是一条 `WHERE ... ORDER BY distance LIMIT k`（07 章三种姿势在单一引擎内由优化器/执行器决定，不存在跨层协议问题）——"库内向量"最大的架构红利。
5. **边界感**：DuckDB 无并发写服务、无副本分片——标本能教学架构，不能替代 06 章产品；各产品官方文档链接见本章演进节（✅ 均已 200 验链）。

## 易错点与陷阱

- **"都是 ANN 引擎，随便换"**：段模型/更新语义/过滤一致性/租户隔离才是选型差异，recall-QPS 只是入场券（08 章评测学）。
- **写入放大盲区**：每段都重建索引（尤其图类）——高频写场景要按"日增×重建成本"估 TCO，而不是看 benchmark 的只读曲线。
- **删除的正确性**：墓碑不清理，recall 分母漂（07 章过滤叠加后更难查）；compaction 策略是产品差异点不是实现细节。
- **副本间索引版本差**：不同副本图结构不同→同一查询返回不同 top-k 是正常现象（近似性×多副本），业务不能假设"全局确定序"。
- **把 ES 当"顺便"选**：文本+向量混合确实顺手，但大 d 高召回场景其 HNSW 参数面/量化深度与专用库仍有差距（定性 ⚠️，用 08 章方法自测）。

## 2026 视角补注

- **版本事实（2024–2026，均 ⚠️ 转述自官方页，链接 ✅ 200）**：pgvector 0.8（halfvec 2000 维索引上限/量化路线）；Milvus 2.5（JSON 列、函数、快照）；Qdrant 1.x 高速迭代（ByteVec/edge 版）；ES 8.x→9.x 引入 bbq（Better Binary Quantization）默认档；LanceDB 被 Spark/多模态生态频繁集成；Neo4j 5.11+ 向量索引 GA；Cassandra 侧 vector 数据类型与向量检索能力经 JIRA CASSANDRA-19181 起步（✅ https://issues.apache.org/jira/browse/CASSANDRA-19181 200 已验，细节以官方文档为准）。
- **SQL 标准化**：ISO SQL:2023 未纳入向量类型；"事实标准"由厂商方言分头推进（Oracle VECTOR、T-SQL VECTOR、PG 扩展型）——标准跟踪建议看 JTC1/SC32 动态（定性 ⚠️，未取到可核验的"SQL 向量入标"官方提案链接，如实存疑）。
- **合并与并购潮**：向量初创 2024–2025 密集并入大厂数据库（Zilliz/MongoDB/Clickhouse 等动作）——产品图谱是流动的，读本书格局要配 08 章的自测方法（定性 ⚠️）。

## 选型决策树（把本章三张形态表串成一条问句链）

1. **数据在哪，向量就尽量在哪**：主数据已在 PG/ES/Oracle 且向量是附属列→库内路线（pgvector/ES knn/厂商 VECTOR 类型），过滤与权限复用既有模型（07 章 pre-filter 免费获得）。
2. **查询形态是"纯语义 top-k+重排"且规模过亿**→专用引擎（Qdrant/Milvus/Weaviate/Pinecone），吃它段模型+分片+量化的规模红利。
3. **单机/端侧/无服务**→嵌入式（DuckDB vss/LanceDB/sqlite-vec/Chroma）：本册 🔧 已示范万级完全够用（3.8 ms@0.908），十万级开始看建索引与内存曲线。
4. **写读比高（流式特征/会话记忆）**→优先看段模型与 compaction 的可观测性（Milvus 系/Qdrant），避开"每次写入触发图重建"的隐藏成本。
5. **以上都满足时比运维**：备份恢复、版本升级、多租户配额、计费模型——"检索性能差异"通常在第三轮 POCl 里才浮出水面，而"运维差异"第一轮就咬人。
- 反模式提醒：拿公开榜单当选型结论=拿别人工作点调自己参数（08 章"曲线而非点"的选型侧镜像）。

## 采购验收三问（附本目录可复用的数字锚）

- **"过滤正确性给我看"**：现场跑带 WHERE 的 top-k，要求对方解释 pre/post/图内过滤策略——07 章实测 3 档（0.017/0.162/0.779）是提问用的标尺。
- **"删除后再测召回"**：删 10% 数据重跑 recall@10，观察墓碑堆积曲线——不接受"这要等 compaction"作为唯一回答。
- **"重建预算多少"**：杀掉索引只留 raw，量全量重建时长=你的真实 RTO——06 章"索引即缓存"论的落地题。

## 产品一句话人设（背下来就能听懂选型会议）

- Pinecone="云上的它"：全托管、serverless、你不碰任何索引参数也几乎不翻车（贵在其价）。
- Milvus="集群的重器"：段/分片/流式组件最全，运维面也最宽；Zilliz 是其云投影。
- Qdrant="工程洁癖的 Rust 单体"：过滤进图遍历做得最干脆，中小集群体感最好。
- Weaviate="语义全家桶"：倒排+向量+模块（rerank/generative）一体，schema 心智最重。
- ES/OpenSearch="顺手的那个"：文本检索主业+向量副业，混合检索场景常赢在"少一个系统"。
- pgvector="SQL 世界公民"：一切以事务与 JOIN 为前提的团队默认解。
- LanceDB/sqlite-vec/DuckDB vss="端侧三件套"：文件即数据库，评测与实验的自由度之王（本册标本=DuckDB）。
- 人设会过时，架构五件套不会——用本节反推 06 章表格，两遍记牢。

## "向量列"的数据库概念小史（为什么 2025 年的爆发其实不突然）

- 1990s：图像检索社区在对象-关系库里塞 `float4[]` 变长数组做特征列（PostgreSQL 数组祖上就是干这个的，✅ PG 数组为内置类型的常识）——有列无索引，全表暴力。
- 2000s–2010s：倒排/位图索引进入通用库，相似检索留在专门系统（Lucene 系做词面、SIFT/PHOG 工具链做视觉）——"库内向量"的第一段空窗。
- 2016–2020：HNSW/DiskANN 让 ANN 工程化，faiss 让算法库化；分析型引擎开始内建数组函数（DuckDB 列式+SIMD 的 `list_*` 家族即此期产物，✅ 06 章标本实测）。
- 2021–2023：pgvector 把"类型+运算符+索引"三件套补成 SQL 生态正典；ES 8 把 knn 塞进查询 DSL。
- 2024–2026：大厂数据库原生 `VECTOR` 类型（Oracle 23ai/SQL Server 2025）——六十年的"扩展列"叙事终于转正。
- 启示：每次"向量进库"都不是新需求，是**索引技术追平存储抽象**的一次会师——本册 04/05 章就是这次会师的技术现场。

## 核心概念速览（中英对照）

- **专用向量数据库** — Purpose-built vector DB：向量为一等公民的全功能引擎。
- **库内向量** — In-database vectors：既有数据库以类型+索引+SQL 承载向量。
- **嵌入式向量** — Embedded/local-first：进程内文件形态，无独立服务。
- **段模型** — Segment (growing/sealed)：写入小段→后台索引化的 LSM 式生命周期。
- **命名空间** — Namespace/partition：多租户与租户内裁剪的隔离单元。
- **scatter-gather** — 分片扇出再归并 top-k（08 章召回分解）。
- **存算分离** — Disaggregated storage/compute：对象存储+无状态查询层。
- **写入可见性** — Consistency of inserts：新向量何时可被近邻查询命中。
- **墓碑与 compaction** — Tombstone/compaction：删除的延迟清算。
- **TCO 分层** — RAM/SSD/对象存储三档：成本-延迟主轴。
