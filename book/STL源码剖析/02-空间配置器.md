# 第 2 章 空间配置器（Allocators）

> 覆盖原书第 2 章：标准配置器接口、SGI 两级配置 `__malloc_alloc_template` / `__default_alloc_template`、
> 内存池（free-lists）、`construct()`、`destroy()`、`uninitialized_fill/fill_n/copy`、
> （书末附录形态的）标准接口 `<memory>`/`<defalloc>` 双轨。
> 本章回答一个成本问题：**为什么 tiny allocation 不能直接甩给 malloc。**
> 源码引用自可达镜像 [karottc/sgi-stl](https://github.com/karottc/sgi-stl)（行文以 `stl_alloc.h:行号` 标注，
> 均已打开核对）；对侯捷原书仅为机制转述，不伪造逐字原文。

## 核心概念速览（中英对照）

- **空间配置器** — allocator：把「配置/释放」抽象成模板参数的间接层，容器与内存来源解耦。
- **一级配置** — first-level `__malloc_alloc_template`（`stl_alloc.h:109`）：薄封装 malloc/free/realloc，返回 0 时进 OOM 处理循环。
- **二级配置** — second-level `__default_alloc_template`（`stl_alloc.h:289`）：≤128 字节的小额请求由自管内存池承接。
- **free-lists** — 16 条空闲单链表：以 8 字节为间距档（8/16/…/128），节点用 `union _Obj { _Obj* link; char data[1]; }` 自存储链表指针。
- **round_up** — `_S_round_up(bytes)`（`stl_alloc.h:300`）：`(n+7) & ~7`，把请求并入上对齐档位。
- **chunk_alloc** — `_S_chunk_alloc(size, nobjs)`（`stl_alloc.h:429`）：从内存池余量切块；余量不足则向堆再批发一大块。
- **20 个起卖** — refill 默认 `nobjs = 20`（`stl_alloc.h:499`）：一次 chunk 尽量多备同档对象，摊薄配置成本。
- **空间换时间** — `_S_heap_size` 只增不减：已配置的堆内存原则上不归还操作系统，进程生命周期内循环再用。
- **分配与构造分离** — `construct()`：placement new 在裸内存上调构造函数；`destroy()` 显式调析构，二者是配置器的「第二拍」。
- **未初始化内存算法** — `uninitialized_copy/fill/fill_n`：在有 allocator 时用 `construct`，无 allocator 时退化为 `copy/fill`。
- **OOM 钩子** — `__malloc_alloc_oom_handler`（`stl_alloc.h:125,154`）：malloc 失败后循环「handler→再试」，全失败则抛 `bad_alloc`。

## 动机：malloc 的三个不划算

1. **小额频繁**：每次 `new int`/链表节点/红黑树节点都是几十字节，malloc 要加锁、找空闲块、
   写块头（glibc 每块另有 8–16 字节簿记），常数开销常大于请求本身。
2. **外部碎片**：频繁混合尺寸的申请释放把堆打碎，长跑服务内存水位只涨不跌。
3. **类型盲**：malloc 不懂 C++ 对象——分配和构造是两件事，异常安全（分配成功但构造抛异常）
   需要「未初始化内存」这一层显式建模。

SGI 的答案：**大块交给 malloc（它见多识广），小块自己管（档位固定、行为可预测）**，
再给对象生命周期补上 construct/destroy 这一层。

## 机制：两级配置的完整回路

### 1. 分流点：128 字节

```cpp
// stl_alloc.h（节选转述，:348-373）
static void* allocate(size_t __n) {
  if (__n > (size_t) _MAX_BYTES)            // _MAX_BYTES = 128 (:283)
    __ret = malloc_alloc::allocate(__n);    // 一级：直连 malloc
  else {
    _Obj** __my_free_list = _S_free_list + _S_freelist_index(__n);  // 定位档位
    _Obj* __result = *__my_free_list;
    if (__result == 0)
      __ret = _S_refill(_S_round_up(__n));  // 该档空了：补货
    else {                                  // 命中：摘下头节点
      *__my_free_list = __result->_M_free_list_link;
      __ret = __result;
    }
  }
  return __ret;
}
```

档位常数：`_ALIGN = 8`、`_MAX_BYTES = 128`、`_NFREELISTS = 16`（`stl_alloc.h:283-285`，
已实测该镜像如此；⚠️ 原书不同印次对 NF 的图示偶有出入，以源码为准）。

### 2. refill 与 chunk_alloc：批发逻辑

```text
refill(size)                     # 免费档已空，去内存池进货
  nobjs = 20                     # 想拿 20 个
  chunk = chunk_alloc(size, nobjs)   # nobjs 可能被就地改小
  把 chunk 串成 nobjs-1 个节点的链表挂回 free_list[size]
  第 1 个节点交给调用者

chunk_alloc(size, nobjs):        # stl_alloc.h:429
  total = size * nobjs
  left  = end_free - start_free  # 内存池余量
  if left >= total:       切 total，皆大欢喜
  elif left >= size:      nobjs 减到能切几个切几个
  else:                        # 余量连一个都给不起
    want = 2*total + round_up(heap_size >> 4)   # :447-448 加征「过往红利」
    若 left > 0：这块残料挂进它尺寸所属的 free_list（废物利用，:451-457）
    p = malloc(want)
    若 p == 0：翻遍所有档位找一条非空 free_list，
               劫走其头节点当新池（size→128 逐档扫描，:463-477）
               仍一无所获 → 交给一级 malloc_alloc（可能抛 bad_alloc）
    否则 heap_size += want；新池 [p, p+want) 就位，重试 chunk_alloc
```

三处设计各有防御对象：
- **`heap_size >> 4` 加征**：本次要多要一点，让后续批发更少撞上「池将空」路径——摊平抖动；
- **残料入档**：旧池剩 7 字节给不起 16 字节档？挂到 8 字节档，永不浪费；
- **劫走其他档**：内存碎片化的兜底——所有档位的存货都是「已经付过钱」的。

### 3. 归还方向：deallocate 只进池、不出池

`deallocate(p, n)`：>128 直接 `free`；≤128 则 `round_up` 定位档位、把头节点插回链表（`stl_alloc.h:530+`）。
**内存从 free-list 回到池、从池回到 OS 的路不存在**——这就是「宁可空间换时间」的账单：
换走的是 RSS 单调性，换来的是小对象路径上零系统调用。多线程版本用
`__NODE_ALLOCATOR_LOCK` 粗粒度锁（`stl_alloc.h:340-342` 的 RAII `_Lock`），
这也是后世「每线程池」（jemalloc tcache、mimalloc page）绕开的瓶颈。

### 4. 第二拍：construct / destroy / uninitialized 三兄弟

`stl_construct.h`（124 行）里 `_Construct/_Destroy` 做两件事：placement new 起对象；
析构时以 `__type_id(T)` 是否等于 `__true_type` 判断「是否有平凡析构」，POD 直接跳过析构调用。
`stl_uninitialized.h` 的同名算法带 allocator 参数时用 `Alloc::construct`，否则用 `std::copy`——
**异常安全协议**：`uninitialized_fill_n(first, n, value)` 若在构造第 k 个时抛出，
负责把前 k-1 个 destroy 干净再上抛。vector/deque 的扩容全部踩在这层上（见 04 篇）。

## 权衡

| 维度 | 只用 malloc | SGI 两级 | 每线程现代池（jemalloc/mimalloc） |
| --- | --- | --- | --- |
| 小对象延迟 | 系统级簿记 + 锁 | 一次数组寻址 + 摘链 | 无锁 tcache 命中 |
| 外部碎片 | 依赖分配器 | 按档归化，档内零碎片 | 按档 + region |
| 内存归还 | 及时（trim） | **基本不还** | 分级归还 |
| 多线程 | 内建竞争处理 | 全局粗锁（可关） | 线程私有缓存 |
| 与异常协议配合 | 无 | construct 层显式建模 | —（语言层同 SGI） |

128B/8B 两个魔数是 90 年代末的调参：对齐收益（指针复用、CPU cache line 未成气候）
与档位数量 × 每档存货的 RSS 膨胀之间的折中。⚠️ 书中是否给过基准数据未核实。

## 相邻概念对比

- **`alloc` vs 标准 `allocator<T>`**：SGI 同时有旧式无类型 `alloc::allocate(n)`（本文件主角）
  与符合标准的模板 `allocator<T>`（`<memory>` 转发给同一个二级池）；书称「双轨并存」。
- **`pthread_alloc`**：镜像仓库有 `pthread_alloc.h`——按堆栈式线程共享的 lock-free 池，书末讨论的「专科生」，未成为主流。
- **内存池 vs arena**：两级配置是**按尺寸分档的池**；arena/单调缓冲（C++17 `pmr::monotonic_buffer_resource`）
  是**按生命周期整块释放**——后者才是现代高性能服务更常用的形态（07 篇实测）。
- **与《提高 C++ 性能的编程技术》互证**：Bulka/Mayhew 的 placement new 惯用法与本层完全同源，见
  [../提高C++性能的编程技术.md](../提高C++性能的编程技术.md)。

## 最新演进与工业实践

- **std::allocator 接口收缩（本机实测）**：g++ 15.2 下，`allocate(n, hint)` 与 `alloc.construct(...)`
  在 `-std=gnu++17` 可编译、在 `-std=gnu++23` 直接编译失败（`bits/allocator.h` 中成员已移除）——
  **C++20 起 hint 版 allocate 与 construct/destroy 从 std::allocator 消失**（已实测 g++ 15.2；
  ⚠️ 对应提案编号未逐一核实，不在此引用）。定制内存策略的正规入口收敛为
  `allocator_traits` + 自定义类型，或干脆用 pmr。
- **P0522R0（2016，已并入 C++17）**：《Matching of template template-arguments excludes compatible
  templates》——让「多一个模板参数的 allocator」能匹配 `template<class T, class Alloc=...> class C` 型参数，
  直接受益者是 `polymorphic_allocator` 与嵌套容器。open-std 原文实测可达：
  [p0522r0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2016/p0522r0.html)；
  后续遗留问题由 [P3310R5（2024）](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2024/p3310r5.html) 处理（标题实测核实）。
- **pmr 接手「运行期选池」**：C++17 `std::pmr::memory_resource` 把 SGI「编译期换 allocator 模板参数」
  升级为「运行期换资源对象」，`synchronized_pool_resource` 就是两级 free-list 的标准化身
  （线程安全、带归还策略）。见 [../C++标准库.md](../C++标准库.md) 相关章节与本目录 07 篇（含实测）。
- **工业分配器谱系**：SGI 的档位思想在 [jemalloc](https://github.com/jemalloc/jemalloc)（tcache + size class）、
  [mimalloc](https://github.com/microsoft/mimalloc)（page + 自由链表）里原样复活；区别只在
  「每线程私有 + 会把整页还给 OS」。读本书第 2 章等于读它们的祖父代码。
- **可观测性**：libstdc++ 编译期 `-fno-new-constructors`、`__default_alloc_template` 早已不存在于标准接口，
  但 glibc malloc 的 `mallopt(M_ARENA_MAX)`/碎片调参仍是本书问题的现代运维版。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 二级配置器是 C++ 标准的一部分 | 标准从未规定分档池；那是 SGI 实现自由，现代三家实现都直接薄接 `::operator new` |
| 2 | free-list 节点有专门的 next 字段开销 | `union _Obj` 借用空闲块自己的首 8 字节存指针，空闲时是链、在用是数据 |
| 3 | `deallocate` 会 free 小块内存 | 小块只回 free-list，池永不缩水；进程 RSS 高水位是设计使然 |
| 4 | allocator 只管 malloc | 还管构造/析构协议（construct/destroy/uninitialized_*），异常安全在此层兜底 |
| 5 | 自定义 allocator 今天仍是大杀器 | 状态化 allocator 的传递地狱使 pmr/全局钩子（mimalloc new-delete override）更常用（07 篇）|
