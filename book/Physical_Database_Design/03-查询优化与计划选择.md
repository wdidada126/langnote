# 第 3 章 · 查询优化与计划选择（Query Optimization and Plan Selection）

> 精读重构，非原书文本。页 31–51。元数据与取证见 [00-总览与阅读地图.md](./00-总览与阅读地图.md)。

## 本章定位

物理设计与优化器之间因果链的正面阐述：**物理设计的产物（索引/视图/聚簇/分区）构成优化器可选的"计划空间"，优化器按代价在空间中选一个计划**。要预测设计的效果，必须先理解计划怎么选。这一章是第 4/5/9/12 章的地基——不会读计划的设计师不会选索引。

## 精读重构要点

### 3.1 计划空间（plan space）与"菜单"隐喻

- 优化器枚举的逻辑计划 = 算子组合（访问路径 × 连接顺序 × 连接算法 × 聚合策略）；物理设计**不指定计划，只收窄菜单**。
- 本章关键概念 **menu effect**：加一个索引等于给菜单加一道菜——优化器按代价点菜，**可能点你不想让它点的**。设计者真正要评估的不是"这个索引能不能被用"，而是"加了之后所有查询重新选菜，整体代价是否下降"（为第 9 章相互依赖问题作引）。

### 3.2 访问路径的代价分解

DB2 风格的分解（重建该章记号）：

- **INDEX_ONLY**：只扫索引，不回表——最便宜；
- **INDEX_AND_FETCH**：索引给 RID → 回表取行；FETCH 项 ≈ 回表页数 = 命中行数 / (每页行数 × 聚簇因子)。聚簇比（clustering ratio）把"索引选择性"与"物理布局"缝在一起——这是第 7/8 章分区/聚簇的代价入口；
- **TABLESCAN**：顺序读全表 + 过滤谓词；
- **IUF（Index Using Fetch）与 prefetch**：范围/等值索引扫描后按 RID 预取页；预取把随机 I/O 摊薄成"顺序-ish"。

### 3.3 统计是代价模型的燃料

- COLCARD（列基数/NDV）、CARDF（表基数）、NGROUPS（分组基数）、LOWKEY/HIGHKEY、直方图/FREQCOUNTS——优化器估这些数来打分。
- 本章埋下的坑：**统计错 → 计划错**，而统计来自第 10 章的"计数与抽样"（见 [08-相互依赖问题与计数抽样.md](./08-相互依赖问题与计数抽样.md)）——物理设计评估（what-if）要求**与真机同源**的统计，否则推荐的索引在真机上表现不同。

### 3.4 连接方法的选择逻辑（重建）

- **NL 嵌套循环**（内表用索引 → NLIX 变体）：外层小、内层索引命中且等值键 → 首选；
- **merge join**：输入已按连接键有序（聚簇索引/分区键正好对齐时可免排序——设计含义：聚簇可"顺路"服务连接）；
- **hash join**：大表无有序性、等值连接、内存够 build 侧——OLAP 默认主力；
- 设计启示：物理设计通过**提供有序性**（聚簇、索引键序、分区键对齐）改变 join 方法选择，这往往比"让某个谓词走索引"的收益更大（呼应第 14 章星型连接）。

### 3.5 物化视图作为"计划改写"

- 视图匹配（view matching）：查询是某物化视图的子集时，优化器改读视图（aggregation 视图还需 group-by 列对齐）。视图是计划空间里的"预制菜"——第 5 章专讲选它（见 [05-物化视图选择.md](./05-物化视图选择.md)）。

### 3.6 本章结论式立场

优化器是"给定物理环境的代价最小化器"；**设计师的控制变量是物理环境而非 SQL 本身**。同一条 SQL，改索引=改菜单、改分区=改分布代价、聚簇=改 FETCH 代价——这三根杠杆贯穿全书后半。

## 阅读提示（2026 视角）

## 典型场景重构（示例，数字非原书 ⚠️）

- 场景 A（menu effect 翻车案）：为 Q1 建索引 I，Q2 原本走 hash join 良好，I 出现后 Q2 优化器选中 NLIX、内表被逐行访问而变慢 10 倍——**单查询视角的"好索引"在全局视角可以是坏设计**；处置：第 4 章评估必须含"受影响查询全集"；
- 场景 B（统计撒谎案）：列实际只有 10 个值、统计按默认猜 1000 个值 → 优化器认为谓词选择率 0.1% 选索引 → 实际命中 90% 行、FETCH 雪崩。RUNSTATS 补直方图后计划自动翻正——设计前先看统计质量（第 10 章）；
- 场景 C（有序性套利）：大表按连接键聚簇后，merge join 免排序直接归并——**不建新索引也省了整本排序账**，这是"物理布局→计划形状"最优雅的案例。

## 常见误读

- 把优化器当黑箱只赌结果：本章要求能**手推计划**——推不出就解释不了设计收益；
- 认为"加了索引查询就一定变快"：索引改变菜单，点菜的是优化器——评估单位是查询全集而非单条 SQL；
- 把视图匹配当玄学：subsumption 本质是谓词包含 + 聚合可分解两个判定（5.1 展开），可教可测。

## 核心概念速览（中英对照）

- **计划空间** — Plan Space：给定物理环境下优化器可枚举的全部执行计划集合
- **菜单效应** — Menu Effect：新索引改变可选计划集合进而可能改变既有查询的选择
- **INDEX_ONLY** — Index-Only Scan：仅索引层即可完成，无需回表
- **INDEX_AND_FETCH** — Index-with-Fetch：索引给 RID 后按页回表取行
- **聚簇比** — Clustering Ratio：索引命中行的页局部性度量，FETCH 代价的核心因子
- **COLCARD/CARDF** — Column/Table Cardinality：列基数/表基数，DB2 统计与代价输入
- **NGROUPS** — Number of Groups：GROUP BY 组数估计，视图匹配打分用
- **NLIX** — Nested Loop with Index：嵌套循环内表走索引的连接形态
- **Sort-Merge Join** — Sort-Merge Join：双侧按连接键有序后归并；有序性可由聚簇顺路提供
- **Hash Join** — Hash Join：build/probe 两侧的分区式连接，OLAP 默认主力
- **视图匹配** — View Matching：查询可被物化视图完全覆盖时的计划改写
- **预取** — Prefetch：按索引 RID 序列成页预读，摊薄随机 FETCH
- **统计同源性** — Statistics Consistency：what-if 评估须用与真机同源的统计，否则推荐失真

## 最新演进与工业实践

- **代价模型的新十年**：学习式基数估计（MSCN/Normalizing Flows 系）与传统直方图并存于研究原型（Lero、Postgres 扩展 pg_cardinality 类），生产默认仍是直方图+采样 ⚠️ 转述；计划稳定性工具（Oracle SPM、SQL Server Query Store/Plan Forcing、PG pg_hint_plan）已成一线标配 ⚠️ 转述。
- **自动索引的"菜单感知"**：Oracle 19c+ Auto Indexing 用"不可见索引 + 负载回归期"实测新菜单对真实 SQL 集合的影响后再转正（入口文档 https://docs.oracle.com/en/database/oracle/oracle-database/ ，✅ 可达，机制细节 ⚠️ 转述）；DB2 autonomic indexing 同路线（https://www.ibm.com/docs/en/db2 ，✅ 可达）。这正是本章"评估整体而非单索引"警告的工业实现。
- **explain 生态**：从 EXPLAIN 走向 EXPLAIN ANALYZE + 计划可视化（PEV2 系、VTune 式算子火焰图）；PG 官方文档 https://www.postgresql.org/docs/18/sql-createindex.html 与 EXPLAIN 页为索引型态对照表提供了权威口径 ✅。
- 与 repo 论文线衔接：what-if 与自动设计器学术源头见 [../../db/db.md](../../db/db.md)（Chaudhuri et al., AutoAdmin "what-if" index analysis utility, SIGMOD 1998, DOI 10.1145/276304.276337，✅ Crossref 200 校验）。
