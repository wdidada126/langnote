# 第 12 章 · 自动化物理数据库设计（Automated Physical Database Design）

> 精读重构，非原书文本。页 223–264，全书篇幅最重的方法章之一。元数据与取证见 [00-总览与阅读地图.md](./00-总览与阅读地图.md)。

## 本章定位

把 02–11 各章的方法装进一台机器：**自动设计器（design advisor / tuner）**。三位作者正是这条研究线（IBM AutoAdmin 谱系）的当事人，本章因此带一手内幕：工业实现长什么样、评估底座怎么搭、以及**它哪里不行**。

## 精读重构要点

### 12.1 自动设计器的五层架构（重建）

1. **负载采集层**：查询缓存/监视表（SQL 全集或采样 + 频次权重），对应第 1 章输入清单与第 10 章抽样纪律；
2. **候选生成层**：索引候选（第 4 章 4.1 流水线）+ 视图候选（第 5 章 5.2 分组格）+ 分区/聚簇候选（第 6–8 章规则）——本章的增量是**多结构联合候选空间**；
3. **评估层（what-if）**：虚拟索引/视图 + 优化器钩子 + 统计合成（第 4 章 4.4 三件套；学术底座 AutoAdmin "what-if" index analysis utility, SIGMOD 1998, DOI 10.1145/276304.276337 ✅）；
4. **选择层**：带空间/维护预算的贪心，配第 9 章互依赖局部修正（合并、增删实验）；
5. **解释与执行层**：推荐报告（每个结构的净收益归因）、灰度激活（不可见索引观察期）、回滚通道。

### 12.2 设计器"必须知道"的物理常识（本章干货）

- **预算账户制**：空间、维护写、备份窗口三类预算同时约束——超预算时贪心的截断顺序决定推荐质量；
- **视图-索引联合选择**：同一预算内先视图后索引会互相顶替（第 9 章），必须同轮竞争；
- **候选剪枝的工程艺术**：全枚举组合爆炸，靠启发式剪（键长上限、每表索引数上限、视图深度上限）——剪枝规则本身就是领域知识的编码；
- **评估一致性**：所有候选用同一负载权重、同一统计快照、同一评估种子（第 10 章纪律的机器化）。

### 12.3 已知局限（作者自陈，重建）

- **负载非静态**：设计器为"历史负载"优化，业务漂移使推荐过期——需要周期性重跑，而重跑又受统计/计划扰动干扰；
- **计划扰动不可完全建模**：what-if 估计的是"新菜单上的最优"，真实优化器可能选到次优（menu effect 的另一面）；
- **写负载低估**：OLTP 表上的索引维护代价在批量窗口外看不全；
- **建议≠命令**：解释层必须让人能驳回——工业失败案例多来自"全自动采纳 + 无人审计"。⚠️ 本章中的具体产品数字（Design Advisor 加速比等）未能核实，不录。

### 12.4 与 DB2 产品的对应

- DB2 Design Advisor（原 Visual Explan）覆盖索引/MQO/分区推荐；autonomic 方向（自调优内存、STMM）试图把设计器常驻化——本章把这些产品当作方法学注脚来写。同书另一作者线的 RUNSTATS/统计自动化在第 10 章。

## 阅读提示（2026 视角)

本章五层架构 = 今天每个"索引推荐/AI 调优"产品的解剖图，包括 LLM 调优助手：**评估层是否真跑了 what-if，还是只做了规则匹配**——检验任何一个"自动索引"产品仍用这五层逐层发问。

## 主线结构图（重构）


## 本章论证链

1. 手工流程（4/5/9 章）在负载规模下不可持续 → 自动化不是奢侈品是必需品；
2. 自动化的咽喉是 **what-if**：不物化就能评估，才可能在可枚举时间内试完候选；
3. what-if 的可信度 = 统计同源性 × 优化器钩子完整度——缺一即"垃圾进垃圾出"；
4. 选择层必须带互依赖修正，否则机器只会更快地犯贪心的错（第 9 章的警告在此兑现）；
5. 最后两层（解释/灰度）决定生死：工业上失败的设计器几乎都败在"无归因、无观察期"，而非算法；
6. 局限清单（12.3）是本章最诚实也最长寿的部分——每一项都是后来 self-driving 研究的立项书。

## 典型场景重构（示例，数字非原书 ⚠️）

- 场景 A（设计器正确姿势）：季度重跑设计器 → 报告"建议合并 5 个窄索引为 2 个宽索引、新增 1 个视图、删除 8 个月未用索引"→ 灰度激活 + 30 天观察期 → 全量采纳——**审计式自治**，人始终在环；
- 场景 B（翻车姿势）：全自动采纳 + 负载月切 → 新负载计划集漂移、旧自动索引变成写侧纯负债 → 空间爆 + 装载超时——12.3"负载漂移 + 无人审计"的组合事故；
- 场景 C（评估底座缺失）：某顾问工具无真实优化器钩子，用规则打分冒充 what-if，推荐"永远加索引从不建议删"——12.1 五层检验法可直接判生死。

## 常见误读

- 把设计器当"开箱即用性能机"：它是方法学的机器化，方法学错了机器放大错误；
- 以为自动化=去工程师：自动化后工程师的工作从"做决定"变为"设预算、审归因、管漂移"——12.2 的账户制知识反而更值钱；
- 低估解释层：净收益归因是设计与运维的接口合同，没有它的设计器在合规场景直接不可用。

## 核心概念速览（中英对照）

- **自动设计器** — Physical Design Advisor/Tuner：候选→评估→选择→推荐的全自动设计工具
- **多结构联合空间** — Joint Structure Space：索引/视图/分区/聚簇在同一候选与预算内竞争
- **what-if 评估** — What-if Analysis：虚拟结构 + 优化器钩子 + 统计合成的免物化评估
- **虚拟索引** — Hypothetical/Virtual Index：不占盘、仅供评估登记的索引假象
- **预算截断** — Budget Cutoff：空间/维护/窗口三预算下贪心的停止规则
- **净收益归因** — Benefit Attribution：推荐报告中每结构对每查询的收益解释
- **观察期激活** — Staged Adoption：不可见索引/影子视图先观察后转正
- **负载权重** — Workload Weighting：按频次/代价给 SQL 集合加权
- **周期性重跑** — Periodic Re-evaluation：对抗负载漂移的设计器运维方式
- **剪枝启发式** — Candidate Pruning Heuristics：键长/索引数/视图深度上限等知识编码
- **无人审计风险** — Blind Adoption：全自动采纳导致计划扰动累积的失败模式
- **STMM** — Self-Tuning Memory Manager：DB2 常驻式自调优（设计器产品形态之一）

## 最新演进与工业实践

- **商业自治化（本章机器的 2026 形态）**：
  - DB2 autonomic indexing：自调优内存中的索引顾问持续创建/丢弃实验索引并统计收益（IBM Docs 入口 https://www.ibm.com/docs/en/db2 ✅ 可达；行为细节 ⚠️ 转述）；
  - Oracle Autonomous Database / Auto Indexing：19c 起全自动索引生命周期（创建→不可见观察→转正/回滚），文档入口 https://docs.oracle.com/en/database/oracle/oracle-database/ ✅ 可达，机制 ⚠️ 转述；
  - SQL Server DTA → Azure SQL 智能性能（自动索引管理，带回归检测）⚠️ 转述。
- **开源等价物**：HypoPG + pg_index_advisor 手工拼出 12.1 的 2/3/4 层（仓库 `HypoPG/hypopg`、`bigblan/pg_index_advisor`，GitHub 直连本机不可达 ⚠️ 按名引用）；MySQL Shell 表分析工具 + `sys.schema_unused_indexes` 走"审计式"而非"推荐式"路线 ⚠️ 转述。
- **自驱动数据库研究线**：12.3 的"负载漂移 + 计划扰动不可建模"两项局限正是 self-driving DBMS 的当代议题——工作负载预测（Query-based Workload Forecasting for Self-Driving DBMS, SIGMOD 2018, DOI 10.1145/3183713.3196908 ✅）与其后继 MB2（SIGMOD 2021, DOI 10.1145/3448016.3457276 ✅，Crossref 200 校验）把评估层从静态 what-if 升级为行为模型；
- **LLM 调优助手（2024–2026）**：各云厂商推出对话式索引/查询顾问；按 12.1 五层检验，多数只有第 1/5 层（读缓存 + 给建议），缺真实评估层——本章 12.3 的"建议≠命令"在 LLM 时代加倍适用。
