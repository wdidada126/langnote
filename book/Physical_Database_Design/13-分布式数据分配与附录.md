> 精读重构，非原书文本。原书第 16 章页 357–370、附录 A 页 371–374、附录 B 页 375–378，及尾部材料（Glossary 379–389 / Bibliography 391–409 / Index 411–425），按"离主题最远的收束材料"合并（映射见 [00-总览与阅读地图.md](./00-总览与阅读地图.md)）。

## 本章定位

全书收尾：把物理设计从单机/单集群推广到**多站点**（第 16 章），再用两页附录补上"一笔简易账"（A：性能模型）与一个 2007 年商战话题（B：DB2 HADR vs Oracle Data Guard 灾备）。方法论含量不高，但 16 章是分布式的"分配决策学"，今天读湖仓多区域复制仍有用。

## 精读重构要点

### 16B.1 分片、复制与分配（第 16 章）

- **分片（fragmentation）**：水平（按谓词切行，范围分区跨站推广）、垂直（按列组切表）、混合；分片正确性 = 完备（可重构全表）+ 最小（不重复）；
- **复制（replication）**：全复制/部分复制；一致性模式（同步/准同步/异步，更新冲突策略：主站点、时间戳、业务规则）；
- **分配（allocation）决策**：对每个分片决定放哪些站点——本章的代价模型是"每站点读写频度 × 本地/远程访问单价 + 复制维护流量"；
- 经典直觉规则（重建）：
  - 数据**读多写少 + 跨站读** ⇒ 向读站点复制；
  - **写集中、读分散** ⇒ 分片留在写站 + 读走远程，或物化视图补读热点；
  - **事务跨分片** ⇒ 尽量按事务边界分片（本地化事务 = 共享无度 co-location 的跨站版）；
- 与第 6 章的衔接：shared-nothing 是"站点内并行切分"，本章是"站点间业务切分"；两章共用"倾斜/局部性/重分布"三词汇。

### 16B.2 附录 A：简单数据库性能模型（页 371–374）

- 全章四页的"一笔账"公式骨架（重建）：响应时间 ≈ 队列等待 + Σ(服务时间 × 请求次数)；请求次数由五本账（第 11 章，见 [09-查询执行计划与物理设计.md](./09-查询执行计划与物理设计.md)）给出，服务时间由 I/O 单价（第 13 章，见 [11-逼近硬件本质.md](./11-逼近硬件本质.md)）给出；
- 用途不是精确预测，而是**数量级比较与瓶颈定位**：任何物理设计建议都应能在模型里指出"省的是哪一项"——把全书方法钉在一个可计算骨架上；
- 局限：排队非线性、缓冲池命中率动态——作者自知，故仅用于相对比较。

### 16B.3 附录 B：DB2 HADR vs Oracle Data Guard（页 375–378）

- 两页对比卡（重建维度）：日志传输（网络同步/异步 vs REDO apply）、备库可读性（快照备库 vs 物理备库 Active DataGuard 时代前形态）、故障切换时间目标、一致性等级与数据丢失窗口（RPO/RTO 表达）；
- 2007 年语境：HADR 是 DB2 对抗 Oracle 的灾备卖点；今天两产品仍是各自阵营标配，**对比维度原样可用**——它是"灾备也是一种物理设计"的注脚（备份窗口、恢复语义在第 7 章范围分区已埋线）。

## 本章论证链

1. 站点间布局是第 6 章"布局三问"的放大版：切给谁（分片）、要不要多份（复制）、每份放哪（放置）；
2. 分配代价里**通信单价**权重远高于盘单价 → 局部性压倒一切，分片键应顺着事务边界而不是表结构；
3. 复制引入一致性光谱（同步→异步）——性能与数据丢失窗口是一枚硬币两面；
4. 附录 A 把全书折算成四行公式：设计建议必须能指认"省的是哪一项"，否则不可辩护；
5. 附录 B 示范了"灾备即物理设计"：备份窗口、RPO/RTO、备库可用性都是布局决策——呼应第 7 章分区级备份与第 13 章日志传输。

## 典型场景重构（示例，数字非原书 ⚠️）

- 场景 A（复制判定）：欧、亚两站点共读一张产品目录（日读万次、月写一次）→ 全复制 + 夜间同步刷新；若换成购物车表（高频写 + 站点内读）→ 分片留本站、零复制——同两句话把 16B.1 两条规则都用上了；
- 场景 B（模型比较法）：候选方案 1"加索引"预估把 FETCH 项从 900 次/查询砍到 40；方案 2"改分区"把扫描项从 12000 页砍到 800 页——附录 A 的意义是**让两种收益可比**，而不算出精确毫秒；
- 场景 C（灾备选型）：金融主站要求 RPO=0 → 同步日志传输 + 自动切换 + 仲裁；分析备站只要求 RTO 天级 → 异步 + 快照恢复——附录 B 的三维度（传输模式/切换时间/备库可读）至今仍是云 DR 检查单骨架。

## 常见误读

- 跳过第 16 章"反正不上多站点"：同一模型直接适用湖仓跨区域复制与读副本放置（2026 的主场景）；
- 把附录 A 当玩具：它是全书**可辩护性**的底线工具——任何设计建议应能在模型里自证；
- 把附录 B 当过时广告：HADR/Data Guard 仍是两阵营现役主力，对比维度比 2007 年多数博客写得更克制准确。

## 核心概念速览（中英对照）

- **水平分片** — Horizontal Fragmentation：按谓词条件把行集切给不同站点
- **垂直分片** — Vertical Fragmentation：按列组切分（与第 15 章拆分同一手法的多站版）
- **分片完备性** — Fragmentation Completeness/Minimality：可重构 + 不重复的正确性条件
- **数据复制** — Replication：同片多站冗余存放及其一致性模式
- **冲突解决** — Update Conflict Resolution：多写主场景的仲裁规则
- **分配决策** — Data Allocation：分片×站点的放置矩阵选择问题
- **局部性原则** — Locality Principle：按事务/读写热点站点摆放以最小化远程访问
- **简单性能模型** — Simple Performance Model：响应时间=等待+Σ(服务时间×次数) 的数量级骨架
- **RPO/RTO** — Recovery Point/Time Objective：灾备的两个不可回避指标
- **HADR** — High Availability Disaster Recovery：DB2 日志传输备库方案
- **Data Guard** — Oracle Data Guard：REDO 应用备库方案
- **快照备库** — Snapshot Standby：备库临时可读写再回放的切换形态
