# 第 1 章 · 物理数据库设计导论（Introduction to Physical Database Design）

> 精读重构，非原书文本。页 1–13。元数据与取证见 [00-总览与阅读地图.md](./00-总览与阅读地图.md)。

## 本章定位

全书的"总目录页"：定义物理设计在数据库工程流水线中的位置（逻辑模型定稿之后、上线与调优循环之中），并给出贯穿全书的分析框架——**负载 → 访问计划 → 存储布局 → 空间/时延/维护代价的权衡**。作者三人均为 IBM 背景，本书视角天生带 DB2 打痕，但概念工具是引擎中立的。

## 精读重构要点

### 1.1 逻辑设计 vs 物理设计

- 逻辑设计回答"实体、关系、范式"；物理设计回答"**同样的逻辑模式，怎样在磁盘上摆放才能又快又省**"：索引（键与类型）、物化视图/汇总表、分区与分布（数据切给谁）、聚簇（行在页/块里的顺序）、反范式化（冗余换连接）、存储参数与 I/O 配置。
- 关键立场：物理设计**不改变 SQL 语义**，只改变代价。这也是它与"改写 SQL"（见 ../SQL优化核心思想.md）的分界线。

### 1.2 例程负载与非例程负载

- 书名原版副题的关键词是 **non-routine applications**：OLTP 点查/短事务这类"例程负载"，引擎默认 B+ 树 + 范式化几乎自动够用；本书火力集中在**非例程负载**——决策支持（DSS）、数据仓库、批量夜间作业、高并发混合负载。
- 非例程负载的特征：扫描量大、连接层数深、聚合分组重、负载随报表周期波动——于是聚簇、位图索引、物化视图、范围分区这些"重型武器"才进入设计空间（后续章逐一展开：02/05/06/07 对应文件）。

### 1.3 物理设计的输入清单

重建该章强调的四类输入：

1. **负载画像**：SQL 全集（或采样），谓词列、连接列、分组列、排序列的出现频度；
2. **数据画像**：表基数、列相异值数（NDV）、值分布（直方图/频率计数）——这正是第 10 章"计数与抽样"（见 [08-相互依赖问题与计数抽样.md](./08-相互依赖问题与计数抽样.md)）服务的需求；
3. **硬件画像**：CPU/内存/磁盘通道，缓冲池大小（第 13 章 Down to the Metal，见 [11-逼近硬件本质.md](./11-逼近硬件本质.md)）；
4. **约束**：空间预算、写放大预算（维护代价）、备份恢复窗口（范围分区的一大卖点是分区级备份）。

### 1.4 决策与迭代环

- 物理设计不是一次性动作：设计 → 上线 → 负载漂移 → 重评。作者把"自动设计器"（第 12 章，见 [10-自动化物理数据库设计.md](./10-自动化物理数据库设计.md)）定位为把这个环自动化，而非取消工程师的判断——因为**相互依赖问题**（第 9 章，见 [08-相互依赖问题与计数抽样.md](./08-相互依赖问题与计数抽样.md)）使得"逐个索引单独评估"系统性给出错误答案。
- 核心公式化的直觉：任何物理设计决策的收益 = Σ(受影响查询的计划改善) − Σ(写入维护代价 + 空间代价 + 优化器误选风险)。全书各章都是这个式子在具体决策类型上的展开。

### 1.5 术语纪律

- 该章给出全书术语基线：access plan（访问计划）、clustering ratio（聚簇比，页 197–221 深入，见 [09-查询执行计划与物理设计.md](./09-查询执行计划与物理设计.md)）、RID、I/O service time、what-if 评估等；后续章不再重复定义。术语表集中在 Glossary（页 379–389，见 [13-分布式数据分配与附录.md](./13-分布式数据分配与附录.md)）。

## 阅读提示（2026 视角怎么读它）

云原生与湖仓时代，本章"输入清单"里最难自动化的反而是**负载画像**：SQL 全集在 SaaS 里往往比 2007 年更难采集（多租户、ORM 生成）。1.2 节"例程/非例程"之分正被 HTAP 与湖仓混合负载模糊——读时把每个决策都问一遍"在存算分离下还成立吗"。

## 本章论证链

1. 物理设计改变代价不改变语义 → 所以必须**量化评估**，不能靠口诀；
2. 量化评估需要负载/数据/硬件三画像 → 画像本身要花钱采集 → **抽样与计数**成为一等公民（第 10 章）；
3. 决策彼此牵连 → 逐结构单独评估系统性错误 → **互依赖**必须建模或绕开（第 9 章）；
4. 人肉做 1–3 太贵 → 把方法装进**自动设计器**（第 12 章）；
5. 所有账最后折算成 I/O/CPU/内存单价 → **Down to the Metal**（第 13 章）；
6. 副题限定战场：**非例程负载**才值得全套武器（第 14 章数仓是主场）。

## 典型场景重构（示例，数字非原书 ⚠️）

- 场景 A（OLTP 例程负载）：点查+短事务，B+ 树主键 + 两三个二级索引，无视图无分区——本章立场：此时**克制**是正确设计，任何多余结构都是纯负债；
- 场景 B（夜间 ETL + 白天报表）：白天查询与夜间装载**共享同一预算账户**——装载窗口的维护开销可能让"白天的收益"在总账上为负，必须按 24 小时周期评估（为 12 文件"装载窗口即第一约束"埋线）；
- 场景 C（混合负载）：同一集群跑批与查询竞争缓冲池/带宽——布局决策（分区粒度、块大小）要按**最差并发时刻**定，而非平均时刻。

## 常见误读

- 把物理设计当"上线前最后一道工序"：它是贯穿生命周期的环（1.4）；
- 把本书当 DB2 手册读：载体是 DB2，**方法框架引擎中立**，各章都给了跨引擎映射（见各文件"最新演进"节）；
- 把"非例程负载"读成"小众负载"：2026 年分析/混合负载已是多数系统的主体负载，本书的问题意识反而更中心。

## 核心概念速览（中英对照）

- **物理数据库设计** — Physical Database Design：在不改变逻辑语义前提下决定索引/分区/聚簇/视图/存储布局的过程
- **例程负载** — Routine Workload：OLTP 式点查短事务，默认物理结构即可胜任
- **非例程负载** — Non-Routine Workload：DSS/数仓/批量作业，物理设计收益显著的主战场
- **访问计划** — Access Plan：优化器为一条 SQL 选定的算子与访问路径组合
- **聚簇比** — Clustering Ratio：一次按索引取回的行命中同一页/块的密度，决定 FETCH 代价
- **设计输入四画像** — Workload/Data/Hardware/Constraint Profiles：物理设计决策的输入
- **维护代价** — Maintenance Cost：写路径上更新索引/视图/统计的分摊代价
- **写放大** — Write Amplification：一次逻辑写引发的物理层重复写（日志/索引/副本）
- **负载漂移** — Workload Drift：上线后 SQL 分布随业务变化导致原设计失效
- **迭代设计环** — Iterative Design Loop：设计→上线→监测→重评的工程循环
- **空间预算** — Space Budget：索引/视图/副本占盘与备份窗口约束
- **设计决策公式** — Benefit = Gain − Maintenance − Risk：全书统一的权衡框架

## 最新演进与工业实践

**到 2024–2026，本章框架的"自动化"走向已定局**：

- **自治化设计环**：DB2 的 autonomic indexing（自调优内存中的索引顾问，自动创建/丢弃实验索引）仍是商业库中血统最正的"物理设计闭环"，官方文档见 IBM Docs（https://www.ibm.com/docs/en/db2 ，✅ curl 验证可达，具体版本行为 ⚠️ 转述）；Oracle Autonomous Database（19c 起 Auto Indexing，索引的创建/不可见/删除由引擎代管，文档入口 https://docs.oracle.com/en/database/oracle/oracle-database/ ，✅ 可达；细则 ⚠️ 转述）。
- **负载画像的新瓶颈**：APM/查询指纹（performance_schema、pg_stat_statements）成为工业界采集"SQL 全集"的事实标准——本章 1.3 的画像输入在现代平台里是**自动喂给**索引顾问的。
- **湖仓改写"物理设计"边界**：Iceberg/Delta 表格式把分区、排序、小文件合并变成**表维护操作**（见 [../Apache_Iceberg活用入門/03-隐藏分区与分区演化.md](../Apache_Iceberg活用入門/03-隐藏分区与分区演化.md) 与 [../Apache_Iceberg活用入門/08-表维护操作.md](../Apache_Iceberg活用入門/08-表维护操作.md)；分区规范 https://iceberg.apache.org/docs/latest/partitioning/ ，✅ 可达），"设计→漂移→重评"环第一次可以由表维护作业全自动执行（自动 compact / rewrite）。
- **HTAP 对 1.2 节的冲击**：例行/非例行负载的分界在 Doris/StarRocks/ClickHouse 混合负载实践中趋于消失，物理设计选择退化为"分区键 + 排序键 + 物化视图"三件套 ⚠️ 转述。
- 与本节相关的 repo 互链：反范式化的当代形态（宽表/打平）见 [../大数据SQL优化.md](../大数据SQL优化.md)。
