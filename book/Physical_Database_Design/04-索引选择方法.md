# 第 4 章 · 索引选择方法（Selecting Indexes）

> 精读重构，非原书文本。页 53–70。元数据与取证见 [00-总览与阅读地图.md](./00-总览与阅读地图.md)。

## 本章定位

全书操作核心之一：给定负载与空间预算，**选哪几个索引**。方法框架（候选生成 → 单独评分 → 贪心组合 → 相互依赖修正）就是后来所有 Design Advisor / Auto Indexing 的教科书原型。与 [../数据库索引设计与优化.md](../数据库索引设计与优化.md) 互为中英镜像，本章补的是"算法过程"。

## 精读重构要点

### 4.1 三步流水线

1. **候选索引生成（candidate generation）**：从负载 SQL 逐条抽取"索引可服务列"——谓词列、连接列、GROUP BY 列、ORDER BY 列；把这些列按可行顺序拼成复合键候选，遵守启发式约束：
   - 等值谓词列放前、范围列随后、排序列对齐尾部；
   - 键列数上限（max key columns）与键宽上限（受页大小/索引开销约束）；
   - 一张表候选索引数上限（写放大约束）。
2. **单索引收益评估**：对每条 SQL，比较"只用该索引"与"基线计划（无新索引）"的代价差；需要第 3 章的 what-if 与统计输入（见 [03-查询优化与计划选择.md](./03-查询优化与计划选择.md)）。
3. **贪心组合（greedy selection）**：每轮选"对当前剩余负载总收益最大"的候选加入集合，受空间预算截断——直到预算耗尽或收益低于阈值。

### 4.2 为什么贪心够用又不够用

- 够用的场景：负载中查询彼此独立、索引服务面重叠少；
- 不够用的根源（本章末伏笔，第 9 章全面展开，见 [08-相互依赖问题与计数抽样.md](./08-相互依赖问题与计数抽样.md)）：
  - **收益不可加**：索引 A 单独对查询 Q 无效、与 B 组合后 Q 才走覆盖路径；
  - **互相顶替**：宽索引可顶替多个窄索引，贪心先收了窄的、预算被占；
  - **计划扰动**：新索引使别的查询选到更差计划（menu effect）。
- 作者的务实态度：贪心 + 事后"互依赖检查"（对被选集合做局部增删/合并实验）比完全搜索更工程可行；完全搜索是组合爆炸（索引选择是 NP 难，学术源头：Index Selection in Relational Databases, Foundations of Data Organization, 1987, DOI 10.1007/978-1-4613-1881-1_41，✅ Crossref 200 校验）。

### 4.3 索引型态的特殊选择规则（重建）

- **聚簇索引只有一个**：列选择标准从"哪条查询受益"升维为"哪类扫描是表的主访问形态"；插入热点（递增键）与页面碎片化的权衡是长期运维矛盾；
- **位图 vs B+ 树**：更新频度是分水岭——位图索引在重写负载下表征恶化（锁粒度）；
- **覆盖索引的宽度纪律**：INCLUDE 越多，写放大越大——预算应按"每个额外列每行的字节"折算；
- **MDC/块索引场景**：多低基数维度列分析型表——直接跳到第 8 章 MDC（见 [07-多维聚簇MDC.md](./07-多维聚簇MDC.md)），别用 N 个单列 B+ 树硬扛。

### 4.4 what-if 的工程底座

- 本章把 what-if 定义为三件套：虚拟索引（不物化、只登记于统计/目录的假索引）+ 优化器钩子（评估含虚拟索引的计划）+ 统计合成（估算虚拟索引的 COLCARD/聚簇比）。缺任何一件，第 12 章自动设计器就无法工作（见 [10-自动化物理数据库设计.md](./10-自动化物理数据库设计.md)）；what-if 学术源头：AutoAdmin "what-if" index analysis utility, SIGMOD 1998, DOI 10.1145/276304.276337 ✅。
- ⚠️ 该章具体实验数字（候选缩减率等）未能从公开资料核实，不录。

### 4.5 从推荐到上线的闭环纪律

- 设计器给的是"净收益"建议：要求把空间、维护、备份窗口折进同一账户；
- 灰度上线：先建**不可见/未激活索引**观察，再全量——这是 DB2/Oracle 共同实践路线，本章已给出雏形。

## 典型场景重构（示例，数字非原书 ⚠️）

- 场景 A（列序题）：谓词 `status=? AND ts>? ORDER BY ts`——正确键序 `(status, ts)`：等值在前、范围殿后，且顺带免排序；`(ts, status)` 退化为纯范围索引；
- 场景 B（预算题）：50GB 预算、候选 12 个索引——贪心先收 3 个高收益窄索引，第 10 个候选（宽覆盖索引，可顶替前三个）被预算截断；**事后合并检查**（9.2）把三个窄的并成一个宽的，净收益反升——这就是"贪心够用又不够用"的标准剧本；
- 场景 C（写侧否决）：候选在 OLTP 热表收益显著，但表日均更新 2000 万次、索引含 5 个高频写列——维护账压过收益，**否决**；同表在数仓副本上则值得（12 文件的装载窗口视角）。

## 常见误读

- 把"能用索引"当"该建索引"：本章的核心是**值不值**，能用只是入场券；
- 忽略候选生成的上限纪律：max key/每表索引数上限不是保守，是把写放大与计划扰动写进规则；
- 以为设计器输出即终稿：没有 4.5 的灰度观察期，设计器只是高级猜測机。

## 核心概念速览（中英对照）

- **候选索引生成** — Candidate Index Generation：从负载谓词/连接/分组/排序列枚举可行复合键
- **最左前缀** — Leftmost Prefix：复合键可用前缀约束，候选生成的第一规则
- **最大键列数** — Max Key Columns：键列/宽度上限，控制索引开销与写放大
- **贪心选择** — Greedy Selection：逐轮取边际收益最大候选的组合算法
- **收益不可加** — Non-additive Benefit：两索引组合才触发覆盖路径等超可加效应
- **索引顶替** — Index Subsumption：宽索引可替代窄索引，贪心过早占预算的风险源
- **空间预算** — Space Budget：索引总占盘与备份窗口的硬约束
- **虚拟索引** — What-if / Hypothetical Index：不物化仅登记、供优化器评估的假索引
- **优化器钩子** — Optimizer Hook：what-if 评估读取计划代价的接口
- **净收益** — Net Benefit：推荐分数 = 查询收益 − 维护 − 空间 − 扰动风险
- **不可见索引** — Invisible/Experimental Index：先建后验、观察期后转正的灰度机制
- **位图写退化** — Bitmap Write Degradation：高更新负载下位图索引的锁粒度恶化

## 最新演进与工业实践

- **开源三件套（2024–2026 现状）**：PostgreSQL 侧 **HypoPG**（GitHub 仓库 `HypoPG/hypopg`，提供本章 4.4 的虚拟索引 + `hypopg_explain`）与 **pg_index_advisor**（仓库 `bigblan/pg_index_advisor`，基于 pg_stat_statements 采样 + HypoPG 评估的推荐器）——两仓库 URL 本机直连不可达（GitHub 屏蔽），⚠️ 按仓库名引用；MySQL 侧 Shell `util.analyzeTableStatistics`/`analyzeTable` 与 `table_status` 提供索引使用度体检 ⚠️ 转述；SQL Server Database Engine Tuning Advisor（DTA）仍是本章流水线的产品化，微软已将其能力向云端（Azure SQL Intelligent Performance）迁移 ⚠️ 转述。
- **商业自治化**：DB2 11.5 autonomic indexing 与 Oracle 19c+ Auto Indexing（文档入口见前章，✅ URL 可达）；共同路线：虚拟/不可见索引 + 负载回归 + 自动转正或回收——即 4.5 的机器化。
- **学术延续**：学习型索引（SIGMOD 2018, DOI 10.1145/3183713.3196909 ✅）与自驱动数据库的工作负载预测（Query-based Workload Forecasting for Self-Driving DBMS, SIGMOD 2018, DOI 10.1145/3183713.3196908 ✅）分别处理"键怎么选结构"与"负载漂移怎么预测"——本章贪心框架仍是两者的评估底座。
- 湖仓侧的新等价物：Databricks/Snowflake 的自动 clustering / liquid clustering 把"聚簇选择"自动化，而"二级索引选择"在扫描型引擎中整体退场（Iceberg 无索引，只有分区 + 排序 + 元数据剪枝；见 [../Apache_Iceberg活用入門/03-隐藏分区与分区演化.md](../Apache_Iceberg活用入門/03-隐藏分区与分区演化.md)）。
