# 第 5 章 · 物化视图选择（Selecting Materialized Views）

> 精读重构，非原书文本。页 71–96。元数据与取证见 [00-总览与阅读地图.md](./00-总览与阅读地图.md)。

## 本章定位

索引线之外的第二条"预制结构"线：物化视图（DB2 语境叫 MQT / materialized query table，其他库称 summary table / aggregate view）。本章回答三件事——**什么样的视图值得物化、怎么判断查询能被视图回答、刷新代价怎么进账户**。是全书与数据仓库工程距离最近的一章。

## 精读重构要点

### 5.1 视图能回答查询吗：匹配（subsumption）判定

- 谓词匹配：查询谓词 ⊆ 视图谓词（查询是视图的"子集行"）；
- 投影匹配：查询输出列在视图键或可再聚合列中；
- GROUP BY 对齐：查询分组列 = 视图分组列（或其子集，可二次上卷）；
- 聚合可分解性：SUM/COUNT/MIN/MAX/AVG（AVG 需存 SUM 与 COUNT 双列）可上卷；COUNT(DISTINCT) **不可**从更细视图推出——除非视图直接物化了该 distinct 层级（重要设计规则，重建）。

### 5.2 视图选择流水线

与第 4 章同构但候选空间更爆炸（视图 = 连接子图 × 分组集 × 聚合集）：

1. 从负载抽取公共"连接骨架 + 分组形状"作候选视图；
2. what-if 评估"走视图 vs 走底表"的代价差（视图匹配器要在评估里跑一遍）；
3. 贪心 + 预算（空间 + 刷新窗口）；
4. **视图-索引耦合**：视图本身也要索引（分组键索引），且底表索引与视图互为顶替——这是第 9 章相互依赖问题的最难变体（见 [08-相互依赖问题与计数抽样.md](./08-相互依赖问题与计数抽样.md)）。

### 5.3 刷新：代价的真正大头（重建）

- 完全刷新：简单、窗口大、夜间批可行；
- 增量刷新：依赖 change capture（DB2 的注册表/mutation staging table，其他库的 CDC/流），对不可逆聚合（MIN/MAX 删除侧、DISTINCT）需存明细或回底表补偿；
- **刷新调度是物理设计的一部分**：视图链（视图上再建视图）形成依赖 DAG，刷新顺序 = 拓扑序；链越深，新鲜度与窗口越难保证；
- 新鲜度（freshness）与可用性折进用户 SLA：OLAP 用户容忍 T+1， Operational 报表可能要求分钟级——决定增量/完全的选择。

### 5.4 星型连接视图特例

- 本章把"星型连接 + 分组"视图作为最重要候选类单独处理：事实表 × 维表的分组聚集是 DSS 负载的 80% 形状；视图按维度层级组织（date/day、dept/region）；
- 上卷关系：细视图可回答粗查询——视图集设计成**层级包络**（rollup lattice）而非任意散点，是工程上可控的关键（呼应第 14 章，见 [12-数据仓库OLAP与反范式化.md](./12-数据仓库OLAP与反范式化.md)）。

### 5.5 维护代价账户

每次底表变更 → 视图维护写 + 可能级联上卷 + 统计重收集；视图越多，DML 尖峰越深（bulk load 期间的视图维护开销可主导 ETL 窗口）。作者立场：**视图的收益评估必须用"变更负载加权"**——白天低写入但夜间 ETL 巨大时，视图可能让窗口翻倍（为第 14 章 warehouse 场景铺垫）。

## 阅读提示（2026 视角）

本章的"视图选择"如今拆成了两条产品线：库内（Oracle real-time MQC、PG 增量物化视图、Doris/StarRocks 异步物化视图）与库外（指标层/dbt metrics/Cube 预聚合）。**匹配判定与上卷可分解性**这两块硬知识在两条线里都原样适用——2026 年做"指标口径一致性"的人本质上在做 5.1 的事。

## 主线结构图（重构）

```
 负载(分组形状聚类) ──► 候选视图(连接骨架×分组格×聚合集)
                              │ 匹配判定: 谓词⊆/列覆盖/聚合可分解
                              ▼
                     what-if: 走视图 vs 走底表
                              │ 视图自身索引也进候选
                              ▼
        刷新账(增量CDC/完全重算/链式拓扑序) ──► 贪心+预算(空间+窗口+新鲜度)
```

## 本章论证链

1. 视图=预制结果，收益来自"重复付费的连接+聚合"被一次付清；
2. 收益兑现的前提是**匹配**（5.1），匹配失败视图就只是又一张表；
3. 匹配失败的主因是不可分解聚合与分组错位 → 视图集要铺在**分组格**上有包络关系；
4. 视图不是免费的：刷新账与底表索引/视图互相顶替 → 必须与索引同预算池联合选择（9 章）；
5. 刷新窗口与新鲜度把视图选择从"查询问题"变成**运维排程问题**——数仓 T+1 与 operational 分钟级走两条完全不同的技术路线。

## 典型场景重构（示例，数字非原书 ⚠️）

- 场景 A（该建）：日报表 `SUM(amount) GROUP BY date, region` 每天被 200 次不同切片重复计算——物化后切片查询读小表，明细扫描账清零；AVG 另存 SUM/COUNT 双列以可上卷；
- 场景 B（不该建）：同一形状每周只跑一次、且底表日增千万行——刷新账 > 收益，视图沦为"夜间炸弹"；
- 场景 C（DISTINCT 陷阱）：视图按 (date,region) 物化 `COUNT(DISTINCT user)`，运营按 (date,channel) 问同样指标——**上卷推不出**，必须为该切片单独物化或下沉明细；这是 5.1 不可分解规则最常被违反的现场。

## 常见误读

- 把物化视图当"存储过程化的缓存"：没有匹配判定与刷新纪律，它就是最危险的冗余（悄悄变旧）；
- 只评估查询收益不排刷新拓扑：视图链越深，夜间窗口雪崩概率越高（5.3）；
- 忽略视图上的索引：视图选中后仍需服务切片谓词——视图不是终点结构。

## 核心概念速览（中英对照）

- **物化视图 / MQT** — Materialized View / Materialized Query Table：查询结果物理落表、可被优化器透明改写命中的预制结构
- **视图匹配** — View Matching / Subsumption：判定查询能否由视图行集+可再聚合列回答
- **上卷** — Rollup：从细分组向粗分组的二次聚合，AVG 需 SUM/COUNT 双列支撑
- **可分解聚合** — Decomposable Aggregate：SUM/COUNT/MIN/MAX 可由部分结果合成
- **不可分解聚合** — Non-decomposable Aggregate：COUNT(DISTINCT) 等不能由细视图推出的形态
- **分组格** — Group-by Lattice：分组集按上卷关系构成的格，视图集应铺在格上
- **增量刷新** — Incremental Refresh：只处理变更部分（CDC/mutation staging）维护视图
- **完全刷新** — Complete Refresh：全量重算，简单但窗口大
- **变更捕获** — Change Data Capture (CDC)：为增量维护提供变更流的机制
- **视图链** — View-on-View Chain：物化视图叠物化视图形成的依赖 DAG 与拓扑刷新序
- **新鲜度** — Freshness / Materialization Latency：视图与底表的时差，需折入 SLA
- **星型视图** — Star-join View：事实×维度分组聚合视图，DSS 负载主形状
- **写放大主导** — Maintenance-dominated Window：ETL 批量写入时视图维护反超查询收益的场景

## 最新演进与工业实践

- **PostgreSQL**：`REFRESH MATERIALIZED VIEW CONCURRENTLY`（9.4 起）解决刷新期间可用性；增量物化视图是社区二十年圣杯——PG 18 世代引入 `INCREMENTAL` 刷新形态的提案与实现讨论活跃，**具体版本行为 ⚠️ 待核验**（未能从 postgresql.org 实抓 release note 原文，本笔记不作定论）；工业上更常见的是 pg_ivm 扩展路线 ⚠️ 转述。
- **实时物化（商业库）**：Oracle 12c+ Real-Time Materialized Views（查询自动合并底表增量，文档入口 https://docs.oracle.com/en/database/oracle/oracle-database/ ✅ 可达，机制 ⚠️ 转述）；DB2 MQT + refresh 调度同路线（https://www.ibm.com/docs/en/db2 ✅）。
- **分析引擎的"视图选择"产品化**：Apache Doris / StarRocks 的异步物化视图支持多表 join + 自动分区对齐 + 透明改写，基本是 5.1/5.2 流水线在 OLAP 引擎里的内建版 ⚠️ 转述；Flink 1.20+ 的 Materialized Table 把"视图选择"推进到流式物化层 ⚠️ 转述。
- **湖仓路线**：Iceberg/Delta 不做库内视图，用"聚合表 + 表维护作业"等价（rollup 作业 DAG 即 5.3 的依赖拓扑）；语义层（dbt Metrics/Cube）把 5.4 的格结构搬到了 SQL 之外的服务层——匹配判定变 simple 为"查询计划 vs 语义层聚合定义"，工程问题没变 ⚠️ 转述。
- 学术线衔接：视图维护与查询改写的经典综述可在 [../../db/db.md](../../db/db.md) 的论文索引中按"materialized view maintenance"线索追。
