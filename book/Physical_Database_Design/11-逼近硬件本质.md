# 第 13 章 · 逼近硬件本质（Down to the Metal）

> 精读重构，非原书文本。页 265–315，全书最长的一章（50 页）。元数据与取证见 [00-总览与阅读地图.md](./00-总览与阅读地图.md)。

## 本章定位

物理设计的"地基章"：前面所有结构（索引/分区/聚簇/视图）的代价最终都要折算成**磁盘 I/O、内存与 CPU 的物理账**。本章把 DBA 从"结构选择"拽到"存储栈"：缓冲池、预取、裸设备、日志写路径、RAID、条带化。2026 年重读，它是"数据库性能 = I/O 系统性能"论断的年代标本，框架仍有效，具体参数已换代。

## 精读重构要点

### 13.1 一次读请求的旅程

- 逻辑页 → 缓冲池查找 → 未命中则 I/O 请求 → 文件系统/裸设备 → 磁盘队列 → DMA 搬运 → 页入池；
- 设计者关心的旋钮：缓冲池大小与数量（多缓冲池按表/分区隔离）、页替换策略（LRU 族 + pin/keep 防污染）、池钉与异步读。

### 13.2 读路径优化三件套

- **顺序预取（sequential/list prefetch）**：按 RID 序列（聚簇好时）或容器内页序批量预读——FETCH 账（第 11 章，见 [09-查询执行计划与物理设计.md](./09-查询执行计划与物理设计.md)）的物理实现；预取深度过大 → 缓冲池污染，过小 → I/O 延迟串行化；
- **异步 I/O / 多线程读**：把机械寻道的延迟藏进并行；DB2 的 readahead 与各库 prefetch 参数；
- **DMA 与内核旁路**：OS bypass（裸设备/AIO）在 2007 是为绕开页缓存双重缓冲与上下文切换；今天同类动机换名字叫 SPDK/用户态驱动 ⚠️ 转述。

### 13.3 写路径与日志（本章的"金属"部分）

- **提交代价**：commit = 日志落盘（组提交、log block 大小、日志盘的独占性——日志与数据混盘时寻道互噬）；
- **检查点/flush 策略**：脏页批量回写与前台读的带宽竞争；
- **RAID 选择账**：RAID 1/10（写 2×、随机好）vs RAID 5（写放大 4 读 2 写、重建窗口风险）——OLTP 日志盘、数据盘、临时盘各自的布局规则；
- **条带与对齐**：extent/chunk 跨盘条带化拉满通道数，2007 年 DB2 容器/表空间布局即为此设计；条带大小与典型 I/O 大小（页/块）错配 → 单请求多盘应答的浪费。

### 13.4 存储栈全景与设计检查单（重建）

- 从"盘"到"库"：disk → adapter/channel → (SAN) → OS FS/raw → DB container → tablespace → page/block；每层的并发上限与排队论直觉（附录 A 的简单性能模型在此使用，见 [13-分布式数据分配与附录.md](./13-分布式数据分配与附录.md)）；
- 检查单式结论：**日志独占快盘 → 数据条带匹配预取粒度 → 缓冲池按负载分池 → 临时/排序空间独立**——四步是本章全部工程浓缩。

### 13.5 与结构章的因果闭环

- 分区/聚簇的收益上限 = 本章的 I/O 单价表：预取把"顺序读多页"变便宜 → 聚簇/块剪枝的相对优势扩大；随机小读便宜化（SSD）会**削弱**聚簇收益但**增强**索引点查——本章给出的这层"单价敏感性分析"是全书最超前的方法论点。

## 阅读提示（2026 视角）

把"磁盘"换成"NVMe SSD / 对象存储"重读 13.2/13.3：随机读延迟 ≈ 100µs 时预取不再是第一优化；而**日志带宽与 fsync 延迟**仍是性能命门；SAN 换成分布式存储后，"独占日志盘"变成"选 IOPS 型云盘/实例存储"。方法可迁移，参数表要重抄。

## 主线结构图（重构）

```
 SQL请求 → [缓冲池] ─命中→ 返回页
              │未命中
              ▼
     预取器(list/seq) → I/O 请求 → [OS: FS|裸设备|AIO]
                                        ▼
                              [RAID/条带: 0/1/5/10]
                                        ▼
                     盘队列 ←— 数据盘 | 日志盘 | 临时盘 分离布局
     写路径: commit → 日志落盘(组提交) → 检查点 → 脏页批量回写
```

## 本章论证链

1. 上层一切结构的收益，最终按 I/O/CPU/内存单价结算（13.5）；
2. 读路径三板斧：缓冲池（少读）→ 预取（读得顺）→ 异步/旁路（读得快）；
3. 写路径的命门是**日志落盘延迟**——组提交、块大小、日志盘独占性，直接决定事务吞吐上限；
4. RAID/条带决定"单价表"形状：RAID 10 买随机性能、RAID 5 买空间但付写放大与重建风险——按数据热度和可容忍损失分级布局；
5. 结论不是"背参数"，而是学会**问单价**：任何结构决策先问"在盘/内存/CPU 当前单价下，省的是哪本账、赚不赚"。

## 典型场景重构（示例，数字非原书 ⚠️）

- 场景 A（日志与数据混盘）：commit 风暴与报表扫描抢同一批盘臂 → 延迟长尾互相放大；拆分日志独占少量快盘后双方都稳定——"日志盘独占"是本章检查单第一步；
- 场景 B（预取过度）：深度预取使全表扫描变快 3 倍，却把在线库缓冲池洗成冷池 → 按查询类型分池（在线池/批处理池）+ 批查询走 MRU 防污染；
- 场景 C（条带错配）：chunk 64KB 而页 16KB → 一次页读跨 4 盘应答、通道利用率虚高——条带单位与典型 I/O 单位要对齐或成整数倍关系。

## 常见误读

- 当 SSD 性能手册读：本章的**排队与预算思维**（每层并发上限、请求数×服务时间）在 NVMe/对象存储时代毫不过时（🔧 说明：本章主题本机不可测，全部 ⚠️ 转述）；
- 把"裸设备"当教条：2007 年绕 FS 的动机今天由 AIO/io_uring/Direct-IO+原子写分担——读动机不读结论；
- 忽视"四步检查单"的顺序性：日志→数据→分池→临时空间，顺序错了等于没做。

## 核心概念速览（中英对照）

- **缓冲池** — Buffer Pool：页级内存缓存，大小/分池/pin 是设计变量
- **页钉与保留** — Pin/Keep：热页防驱逐的提示手段
- **顺序/列表预取** — Sequential/List Prefetch：按页序或 RID 序列批量预读
- **缓冲池污染** — Buffer Pool Pollution：大批扫描挤驱逐热页
- **异步 I/O** — Asynchronous I/O：提交与等待分离以并行寻道
- **DMA** — Direct Memory Access：外设直写内存减轻 CPU 搬运
- **裸设备 / OS 旁路** — Raw Device / OS Bypass：绕开双重页缓存与 FS 开销
- **提交日志序** — Write-Ahead Logging / Commit Cost：commit = 日志落盘的强制序
- **组提交** — Group Commit：合并多事务日志 I/O
- **RAID 10 vs 5** — RAID Trade-off：写放大/随机性能/重建风险的布局选择
- **条带化** — Striping：数据跨盘分段并行应答，chunk 需匹配 I/O 粒度
- **表空间/容器布局** — Tablespace/Container Layout：DB 侧对物理盘的映射单元
- **单价敏感性** — Cost-Tolerance Analysis：结构收益随硬件单价表变化的二阶分析

## 最新演进与工业实践

- **NVMe/NVMe-oF/SPDK（2024–2026 主流）**：本机队列深度 + 用户态轮询取代"裸设备+多线程读"；内核旁路线由 SPDK（GitHub `spdk/spdk`，直连不可达 ⚠️ 按名引用）与 io_uring 延续——13.2 的"藏延迟"目标不变，手段换代；
- **PMEM 的兴起与退场**：Intel Optane PMEM（2019–2021）曾让"日志=内存+电池"的 13.3 设想落地（PG/Redis 的 AOF-dax 实验），2021 年 Optane 产品线终止——本章读来像"未竟之路"的注脚 ⚠️ 转述；
- **CXL 内存分层（2024–2026）**：CXL 2.0/3.x 交换内存让"缓冲池分冷热层"重回架构议题（Meta/三星的数据库分层实践，AWS/Google 的 TPU/GPU 主机内存池化）——13.1 的"页在池里"正演化为"页在层级里" ⚠️ 转述，无本机制品可实测；
- **云盘参数化**：EBS io2/本地 NVMe 实例存储 vs 对象存储 + 缓存层（Aurora、Snowflake、Iceberg on S3）——"日志独占快盘"变成" WAL 走专用低延迟服务"（Aurora 六副本日志即此思路的极端版）⚠️ 转述；
- **LSM 对写路径的接管**：RocksDB/LevelDB 及 ZenFS（把 LSM 直接下到 SSD 固件的尝试）延续本章"写放大预算"的讨论，只是主语从 RAID 变成闪存通道 ⚠️ 转述，见 [../Database_Internals/07-日志结构存储.md](../Database_Internals/07-日志结构存储.md)；
- 🔧 说明：本章主题（裸设备/RAID/SAN）本机不可实测，全部为转述 + ⚠️；页级机制的替身实验可用 DuckDB 在普通文件系统上验证"有序布局剪枝"收益（见 [07-多维聚簇MDC.md](./07-多维聚簇MDC.md) 🔧 节）。
