# 第 6–7 章 · 分区：共享无度与范围分区（Shared-nothing Partitioning; Range Partitioning）

> 精读重构，非原书文本。原书第 6 章页 97–123、第 7 章页 125–142，按规范合并为一文件（映射表见 [00-总览与阅读地图.md](./00-总览与阅读地图.md)）。

## 本章定位

把"数据摆放"拆成两个正交问题：**跨节点怎么切**（shared-nothing 分区/哈希分布，第 6 章）与**单节点内怎么按值域切**（范围分区，第 7 章）。2007 年这是 DB2 EEE/DPF 与 Oracle 分区视图的主战场；2026 年这套词汇整体复活为湖仓的 partition spec + 分布键。

## 精读重构要点

### 6A.1 共享无度分区（第 6 章）

- 模型：N 个节点，无共享磁盘，数据按**哈希分布键**切成片段散到各节点，各节点自带 CPU/内存/盘，并行度 = 节点数——DB2 DPF / Oracle RAC(非共享存储路线)/ Greenplum 同谱系。
- 设计变量：
  - **分布键选择**：高频连接键优先（co-location join：同键数据同节点，本地完成大连接，免 repartition 网络传输）；
  - **倾斜（skew）**：哈希键 NDV 低或值热点 → 某节点过载；纠偏靠重键、加盐、或复合键；
  - **两阶段聚合**：GROUP BY 键 ≠ 分布键时的 partial agg → redistribute → final agg；
  - **repartition/broadcast**：连接键不对齐时的两种代价形态（广播小表 vs 重分布大表）。
- 与物理设计其他杠杆的接口：每个节点内部仍然有索引/聚簇/范围分区问题——第 6 章管"宏观布局"，第 7/8 章管"微观布局"。

### 6A.2 范围分区（第 7 章）

- 模型：按分区键（几乎总是时间列/日期列）把一张逻辑表切成若干物理分区，每分区独立容器/表空间：`VALUES LESS THAN` 边界。
- 核心收益（按本章论证顺序重建）：
  1. **分区剪枝（partition pruning）**：谓词 `date BETWEEN ...` 直接排除整个分区——比任何索引都便宜的扫描削减；
  2. **滚动数据生命周期**：新分区 staged load → 交换进（exchange/attach partition）、老分区 detach → 归档/删除，ETL 窗口从"删一年数据"变成"摘一个分区"；
  3. **分区级备份/恢复**：备份窗口按热度分级；
  4. **物理结构异构**：老分区压缩/少索引、热分区多索引——同一逻辑表不同物理策略。
- 维护成本与陷阱：
  - 全局索引 vs 局部索引（local index）：范围分区表上每个分区各建索引，跨分区扫描要做 index union；全局索引保唯一性但分区维护时重建代价大；
  - 分区边界变更（rebalance/split）昂贵——设计时按**数据保留期**定粒度（按天还是按月分区）是一次性不可逆决策；
  - 剪枝依赖谓词是**字面常量/可推断**：`date = CURRENT_DATE - 5` 在运行期剪枝（DB2 当年特性）、函数包裹分区键则剪枝失效。
- 与聚簇的对比（为第 8 章铺垫）：范围分区是"按一维切块 + 运维语义"，MDC 是"按多维切块 + 查询语义"（见 [07-多维聚簇MDC.md](./07-多维聚簇MDC.md)）。

### 6A.3 两种分区的组合拳

- 大表典型三层：节点间哈希分布（宏观并行）→ 节点内范围分区（生命周期）→ 分区内 MDC/聚簇索引（微观局部性）。本章给出的这句"布局三问"（切给谁 / 怎么滚 / 怎么挨着）就是全书物理设计总纲的操作化。

## 本章论证链

1. 并行度来自"数据切给谁"→ 分布键=连接键/分组键的交集最大化（6A.1）；
2. 分布键选择错误的代价以**每次大连接重复 shuffle** 的形式长期付利息；
3. 单节点内，"按值域切 + 谓词带值域"是扫描削减最便宜的杠杆 → 范围分区（6A.2）；
4. 范围的边界与粒度是**准不可逆决策**——运维语义（滚动/备份）全押在它上；
5. 于是 2007 年最疼的"改分区=重灌数据"，正是 2026 年 Iceberg partition evolution 要解决的问题——本章的痛点是湖仓的卖点。

## 典型场景重构（示例，数字非原书 ⚠️）

- 场景 A（co-location 套利）：订单表按 `customer_id` 哈希分布、客户表同键分布 → 订单-客户连接全本地；若运营报表总按 `region` 聚合，region 又不在分布键里 → 每次全量重分布——分布键永远在"主连接"与"主聚合"之间做取舍；
- 场景 B（剪枝失效案）：报表 SQL 写成 `WHERE EXTRACT(MONTH FROM ts)=3`——函数包裹分区键，整年数据都读；改写为 `ts BETWEEN` 区间后剪枝恢复——**分区键上保持裸列谓词**是纪律（Iceberg hidden partitioning 用 transform 在元数据层解了这个围）；
- 场景 C（归档流水线）：按月分区，`DROP PARTITION` 归档 24 个月前的数据、每天 exchange 新分区入——备份窗口按热度分级（热分区日备、温周备、冷不备）——运维收益全部兑现的样板。

## 常见误读

- 把 shared-nothing 分区当"索引的一种"：它是**布局与并行**问题，服务的是扫描与连接账；
- 忽视全局索引的分区维护耦合：范围分区表上加全局唯一索引 = 分区运维（drop/split）时重建风暴的预约单；
- 以为剪枝总是自动发生：谓词形态、统计新鲜度、分区元数据三者齐备才剪得动（🔧 乱序表不剪枝的对照见 07 文件实测节）。

## 核心概念速览（中英对照）

- **共享无度分区** — Shared-nothing Partitioning：数据按分布键哈希散到无共享磁盘的多节点，并行度随节点扩展
- **分布键** — Distribution Key：决定行落点的哈希键，选择标准是高频连接/分组键
- **数据倾斜** — Skew：分布热点导致节点过载，纠偏靠重键/加盐/复合键
- **同址连接** — Co-location Join：连接键 = 分布键时连接在数据所在节点本地完成
- **重分布 / 广播** — Repartition / Broadcast：连接键不对齐时的两种 shuffle 代价形态
- **范围分区** — Range Partitioning：按分区键值域把逻辑表切成物理分区的切分方式
- **分区剪枝** — Partition Pruning：谓词值域与分区边界比较后整分区排除
- **局部索引** — Local Index：每分区独立建的索引，跨分区扫描需合并
- **全局索引** — Global Index：跨分区统一键空间的索引，唯一性载体、维护昂贵
- **滚动生命周期** — Rolling Data Lifecycle：staged 新分区交换入、老分区摘除归档的 ETL 模式
- **分区边界** — Partition Boundary：LESS THAN 值集合；定粒度即定不可逆运维决策
- **布局三问** — Who/How-roll/How-adjacent：切给谁、怎么滚、怎么挨着的三层设计纲

## 最新演进与工业实践

- **声明式分区的十年演进**：PostgreSQL 10（2017）引入声明式分区，11–17 逐步补齐剪枝、分区级统计、外键与全局索引限制放宽；官方手册分区章 https://www.postgresql.org/docs/current/ddl-partitioning.html （✅ curl 验证可达）——第 7 章的剪枝/滚动生命周期两收益在 PG 里对应 pruning + `DROP PARTITION`/detach 归档。
- **湖仓复活"逻辑分区"**：Apache Iceberg 的 hidden partitioning + partition evolution（规范 https://iceberg.apache.org/spec/ 与分区文档 https://iceberg.apache.org/docs/latest/partitioning/ ，✅ 均可达）解决本章两个 2007 年痛点：**边界不可改**（evolution 允许换分区表达式而不动数据）与**函数包裹键导致剪枝失效**（谓词在元数据层解析 transform，如 `days(ts)`）。repo 深读见 [../Apache_Iceberg活用入門/03-隐藏分区与分区演化.md](../Apache_Iceberg活用入門/03-隐藏分区与分区演化.md)。
- **商业库分区现状**：Oracle 19c 区间分区/自动分区（interval/auto-list）、按分区运维（move/drop online）仍是分区卖点（文档入口 https://docs.oracle.com/en/database/oracle/oracle-database/ ✅，细则 ⚠️ 转述）；DB2 范围分区 + MDC 并存（https://www.ibm.com/docs/en/db2 ✅）。
- **Shared-nothing 的后继形态**：MPP（Snowflake/BigQuery/Redshift/Greenplum/Doris）把 6A.1 的哈希分布与两阶段聚合全部内化；Snowflake 更以 micro-partition 自动化取消"分布键"这一用户决策——分布键的倾斜管理变成引擎的自动 reclustering 问题 ⚠️ 转述。
