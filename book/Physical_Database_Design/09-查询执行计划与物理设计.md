# 第 11 章 · 查询执行计划与物理设计（Query Execution Plans and Physical Design）

> 精读重构，非原书文本。页 197–221。元数据与取证见 [00-总览与阅读地图.md](./00-总览与阅读地图.md)。

## 本章定位

第 3 章的"算账深化"：把访问计划拆到**算子级 I/O 与 CPU 记账**，让设计者能回答"这个索引/聚簇/分区到底省了哪笔钱"。本章是 01–08 各章的代价汇合点——FETCH、扫描、连接、聚合、排序五本账，物理设计的杠杆都落在其中某一本上。

## 精读重构要点

### 11.1 计划代价的五本账（DB2 记号风格重建）

- **扫描账**：表容器页数 × 顺序读单价；分区/MDC 剪枝（见 [06-分区·共享无度与范围分区.md](./06-分区·共享无度与范围分区.md)、[07-多维聚簇MDC.md](./07-多维聚簇MDC.md)）直接砍这本账；
- **索引账**：B+ 树下降页数（树高，常 2–4）+ 叶子层范围页数；
- **FETCH 账（本章主角）**：索引给 RID → 取数据页。理想聚簇下命中行数/每页行数 = 页请求数；聚簇衰减后近似每行一页——这本账解释了**为什么同样的索引，聚簇表上快一个量级**。DB2 用 CLUSTERRATIO/统计中的顺序性度量入模型；预取（顺序预读 RID 序列的页）把随机读摊薄，但缓冲池被预取污染的风险见第 13 章（[11-逼近硬件本质.md](./11-逼近硬件本质.md)）；
- **连接账**：NLIX 外层行数 × 内层下降；hash 的 build/probe 页读写 + 内存不足溢出多次分区；merge 的排序账（外部排序趟数 = f(内存, 数据量)）——聚簇/分区键对齐可**消掉整个排序账**；
- **排序/聚合账**：ORDER BY 与索引键序匹配则零成本；GROUP BY 走 hash 或预排序，视图命中则两本全免（见 [05-物化视图选择.md](./05-物化视图选择.md)）。

### 11.2 设计杠杆 → 账本的映射表（本章核心贡献，重建）

| 设计动作 | 主要省的账 | 主要新增的账 |
|---|---|---|
| 选择性二级索引 | 扫描账（变索引账） | 索引账+FETCH 账（若聚簇差） |
| 覆盖索引 | FETCH 账清零 | 索引账变宽、写放大 |
| 聚簇索引/表组织 | FETCH 账摊薄 | 插入热点、页分裂 |
| 范围分区/块剪枝 | 扫描账按值域砍 | 元数据、边界维护 |
| 物化视图 | 连接+聚合+扫描三本 | 刷新与一致性 |
| 分布键对齐 | 连接账去 repartition | 倾斜、重分布一次性 |

- 这张表把全书决策统一成"**省哪本、添哪本、在什么负载形态下净赚**"——第 4/9 章的贪心评分实际就是在算这张表的差分。

### 11.3 计划形状对物理设计的反向要求

- hash join 溢出多趟时，加内存或建"让内侧变小"的索引（半连接谓词下推）；
- NLIX 依赖内侧索引存在——设计器评估 NLIX 收益时必须确认内侧索引**在预算内可建**；
- 分区表上的聚合两阶段化：分组键含分区键时局部聚合可直接上报（无 repartition）——**分区键也是聚合布局键**；
- 并行化形态（intra-partition 流水线/inter-partition 分段）改变每本账的单价，共享无度并行见第 6 章。

### 11.4 用计划反推负载画像

- 本章给出实操流程：抓生产计划缓存 → 按账本分解每个计划的成本构成 → 找出"被同一本账卡住的一组查询" → 对应杠杆一次服务一组（而非逐查询加索引）——这是 9.1 互依赖思想的工程化：以**账本聚类**代替以**查询聚类**做设计。

## 阅读提示（2026 视角）

列存与向量化让"扫描账"的单价暴跌（压缩+SIMD），FETCH 账在湖仓里变成"文件账"（小文件=高元数据税）；账本框架不变，单价表要换成 2026 版：**随机页读 ≈ 冷对象存储 GET**，聚簇收益模型随之重算。

## 🔧 本机实测（SQLite 3.45.3，账本视角）

方法：30 万行表上 `SELECT b FROM t WHERE a BETWEEN x AND y`（命中约 1 万行），非覆盖索引（索引账+FETCH 账）vs 覆盖索引（索引账，FETCH 清零），20 次均值 5.520ms vs 4.716ms（🟢 约 15%）。
- 解读：收益偏小是因为 SQLite 表窄行、页命中率高（数据本就"近似聚簇"，每页装 ~75 行）——**FETCH 账的收益上限 = 聚簇差 × 行宽**，负载形态决定杠杆大小，正是本章 11.2 表的含义。
- 对照 [02-索引基础技术.md](./02-索引基础技术.md) 的 EXPLAIN 计划文本（COVERING INDEX 标注）。

## 本章论证链

1. 物理设计的效果**只能通过计划翻译**成性能——设计者必须会读账；
2. 五本账各有"单价"（第 13 章 I/O 栈、CPU、内存），各有"砍法"（各结构章）；
3. 11.2 映射表是本章的心脏：每个结构动作 → 省哪本/添哪本 → 负载形态下净赚与否；
4. 反向因果同样成立：想要的计划形状（NLIX、免排序 merge、本地聚合）会**规定你必须提供什么结构**——设计即"为理想计划备料"；
5. 实操收口（11.4）：从生产计划缓存出发按账聚类，比从单条 SQL 出发加索引，结构性地少建冗余。

## 典型场景重构（示例，数字非原书 ⚠️）

- 场景 A（聚簇比翻盘）：`status` 等值索引命中 5% 行：聚簇比 0.9 时回表≈表页数 ×5%；聚簇比 0.05 时几乎每行一随机页——同一索引两计划差一个量级；解法不是换索引而是把该列请进 MDC/聚簇维度（07 文件）；
- 场景 B（预取污染）：批量报表用 list prefetch 把 8GB 冷数据灌进缓冲池，在线交易热页被逐出、延迟毛刺——预取深度是全局参数，要按"最坏并发时刻"定（第 1 章场景 C 的再现，第 13 章展开）；
- 场景 C（分区键即聚合键）：月报表 `GROUP BY region` 且数据按 region 范围分区——各分区局部聚合直出，无重分布；换成 `GROUP BY city` 就要全量重分布——分区/分布键的选择同时是聚合布局的选择。

## 常见误读

- 把本章当 EXPLAIN 教程：EXPLAIN 是工具，**账本分解**才是方法；
- 只优化"最慢 SQL"：五本账视角下，慢 SQL 往往只是同一本账被重复付费的最显性一笔；
- 忽略"反向要求"（11.3）：设计器推荐 NLIX 收益却不建内侧索引=推荐失效——计划与结构要联立求解。

## 核心概念速览（中英对照）

- **五本账** — Cost Accounts：扫描/索引/FETCH/连接/排序聚合的代价分解框架
- **FETCH 账** — Fetch Cost：按 RID 回表取页的代价，聚簇比决定其大小
- **CLUSTERRATIO** — Clustering Ratio：DB2 聚簇质量统计量，FETCH 账的模型因子
- **预取** — Prefetch / Sequential List Prefetch：RID 序列页预读，摊薄随机读
- **缓冲池污染** — Buffer Pool Pollution：大预取把热页挤出内存的副作用
- **NLIX** — Nested-Loop with Index：内侧索引支撑的嵌套循环，依赖内侧索引可建
- **Hash 溢出** — Hash Spill：build 侧超内存后多趟分区读写
- **外部排序** — External Sort：内存不足时的归并趟数代价
- **免排序** — Sort Avoidance：索引键序/分区对齐直接消掉排序账
- **半连接下推** — Semi-join Pushdown：先小集合过滤大表内侧，让 NLIX 划算
- **分组键对齐** — Group-by/Partition-key Alignment：分组含分区键时局部聚合免上报
- **账本聚类** — Account-based Grouping：按"卡同一本账"聚类查询做设计，替代逐查询加索引

## 最新演进与工业实践

- **计划缓存/账本工具成熟**：Oracle SQL Plan Monitoring、SQL Server Query Store（计划回归检测）、MySQL `performance_schema.events_statements_*` + EXPLAIN ANALYZE（PG 自 9.2 起，手册 https://www.postgresql.org/docs/18/sql-createindex.html 同域 ✅）——11.4 的"抓计划→分账→聚类"从手工脚本变成内建服务 ⚠️ 转述。
- **向量化/列存改单价**：ClickHouse/DuckDB 把扫描账压到"压缩块解压 + SIMD 过滤"，索引账在分析引擎普遍让位于 zonemap 剪枝（🔧 见 [07-多维聚簇MDC.md](./07-多维聚簇MDC.md)）；但"行存 OLTP 的 FETCH 账"在 HTAP 行存侧原样保留 ⚠️ 转述。
- **云原生的 FETCH 变体**：Aurora/Snowflake/Iceberg 上回表 = 对象存储 GET，"聚簇"升级为"文件内排序 + 文件间布局（sort/liquid clustering）"——11.2 映射表逐条可平移（Iceberg sort order：https://iceberg.apache.org/spec/ ✅）。
- 与自动设计器：账本分解是第 12 章设计器评分函数的可解释内核（见 [10-自动化物理数据库设计.md](./10-自动化物理数据库设计.md)）。
