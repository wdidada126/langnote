# 第 5 章　性能调优

> 原书第 5 章是**实战性最强、且方法论在 2026 年仍然成立**的一章：它给出了一套
> 「先找瓶颈（CPU/文件IO/网络IO/内存/程序慢）→ 再对症下药（JVM调优/程序调优）」的闭环。
> 这套**自上而下定位瓶颈**的思路，今天依然是性能工程的常识。会变的是**工具与开关**：
> 本书用 `top/jstat/jmap/jstack` 手工捞，今天有 JFR/async-profiler/Prometheus 持续采样；
> 本书调的是 Serial/Parallel/CMS，今天默认 G1、可选 ZGC/Shenandoah。
> 读这章要**把方法论留下，把工具链与 GC 参数更新到 2026**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 寻找性能瓶颈 | 分 CPU/文件IO/网络IO/内存四类消耗分析 + 程序执行慢的原因归类 | **先量化瓶颈在哪一类资源，再动手**，避免盲调 |
| 5.1.1 CPU消耗分析 | us/sy/id/wa/hi/si 各态含义；热点方法 | CPU 高先看是用户态（算法/循环）还是系统态（系统调用/锁） |
| 5.1.2 文件IO消耗分析 | iowait、读写吞吐 | IO 瓶颈靠缓存/批量/异步解 |
| 5.1.3 网络IO消耗分析 | 带宽、连接数、丢包 | 网络瓶颈靠连接复用/压缩/批量 |
| 5.1.4 内存消耗分析 | 堆内/堆外、GC 压力 | 内存瓶颈看是泄漏、碎片还是分配过快 |
| 5.1.5 程序执行慢原因分析 | 资源未瓶颈却慢：锁竞争/外部依赖慢/GC 停顿 | 「慢」≠「资源满」，要分层查 |
| 5.2 调优 | JVM 调优 + 程序调优 + 资源未满但慢的专项 | 调优是**迭代**：假设→测量→改→再测量 |
| 5.2.1 JVM调优 | 堆大小、收集器选择、GC 参数 | 目标定「吞吐/停顿」再选收集器 |
| 5.2.2 程序调优 | 算法、锁、IO、对象创建、字符串 | 程序层优化收益常大于 JVM 参数 |
| 5.2.3 资源消耗不多但程序执行慢 | 锁/外部依赖/GC/伪共享等隐性成本 | 这一节是本书最被低估的洞察 |

## 核心精讲

（以下为教学性梳理；所有片段均**教学示意，不参与构建**，绝不编译/运行。）

### 5.1 先定位，再调优：四类资源 + 一个反直觉

```text
# 教学示意，不参与构建：排查顺序（自上而下）
1. 看整体: top / htop / vmstat  -> 哪类资源吃紧?
   CPU 高?  IO 高?  内存涨?  网络满?
2. 按类下钻:
   CPU  -> us 高=业务算法 ; sy 高=系统调用/锁 ; 用 profiler 找热点方法
   IO  -> iostat/iotop 找读写热点 -> 缓存/批量/异步
   网络 -> netstat/ss 看连接/重传 -> 复用/压缩
   内存 -> jstat 看 GC ; jmap 看对象 -> 泄漏/碎片
3. 反直觉: 资源都没满但慢 -> 锁竞争 / 外部依赖RT高 / GC STW / 伪共享
```

- **CPU 各态**（本书 5.1.1 的经典表）：`us` 用户态（你的代码）、`sy` 系统态（内核/系统调用）、
  `id` 空闲、`wa` IO 等待、`hi/si` 硬/软中断。us 高通常意味着算法/循环热点；sy 高常是
  **锁竞争导致频繁上下文切换**或大量系统调用。
- **「资源没满却慢」**（本书 5.1.5 / 5.2.3 的精华）：最常被忽略——
  锁竞争（线程在等锁而非在跑）、外部依赖 RT（DB/下游慢）、GC 停顿（STW 卡住所有线程）、
  伪共享（多核缓存行互相 invalidate）。

### 5.2 JVM 调优的目标先行

```text
# 教学示意，不参与构建：GC 调优先定目标
目标A: 高吞吐   -> Parallel / G1 (吞吐优先)
目标B: 低延迟   -> G1 (可设 MaxGCPauseMillis) / ZGC / Shenandoah (亚毫秒)
目标C: 小内存   -> Serial / 小堆 G1
调优变量: -Xms/-Xmx (堆) , 新生代比 , 收集器 , 停顿目标
```

> [04-分布式应用与SunJDK类库.md](04-分布式应用与SunJDK类库.md)（5.2.2 程序调优常改的是 4.1/4.2 的误用）。

## 版本演进

- **本书无第二版**；本节写 2010 年口径 → 2026 年视角的变化。
- **工具链换代**：本书的 `top/jstat/jmap/jstack/VisualVM` 仍是基础，但 2026 年首选
  **JFR + JMC（低开销持续采样）、async-profiler（火焰图）、Arthas（线上不停机诊断）、
  Prometheus + Grafana（跨实例聚合）**。单靠反复 `jmap -dump` 已不够。
- **GC 参数全换**：本书的 Serial/Parallel/CMS 调优经验，今天映射到
  **G1（默认）/ ZGC / Shenandoah**；CMS 已移除（JDK 14），调优从「调各种比例」变为
  「设停顿目标 + 给够内存」。
- **容器化带来的新变量**：本书假设物理机；2026 年 JVM 跑在容器里，必须开容器感知
  （JDK 8u191+ 默认开），并按 cgroup 限额设堆，否则 OOMKilled。
- **可观测性补位**：本书「程序慢」靠经验猜；今天用 **OpenTelemetry 分布式追踪**直接看到
  慢在哪一个 span（方法/下游调用），5.1.5 的「外部依赖慢」被精确量化。
- **程序调优新手段**：`CompletableFuture` 异步化、虚拟线程（JDK 21）解轻量并发、
  向量化/SIMD（Project Panama）、GraalVM 原生镜像降启动与内存。

## 近年研究与工业界开源实践（2015–2026）

- **诊断工具开源**：`async-profiler`（火焰图事实标准）、Arthas（`alibaba/arthas`，线上诊断）、
  `apache/kafka` 等项目的性能实践文档。JFR 已开源并内置 OpenJDK。
- **云原生可观测**：**Prometheus + Grafana + OpenTelemetry** 成为 2026 性能工程的标配，
  直接把本书 5.1 的「四类消耗」做成持续 dashboard 与告警。
- **GC 工程化**：G1/ZGC/Shenandoah 在各 JDK 发行版（Temurin、Dragonwell、Kona、Zing）落地；
  ZGC 在阿里/腾讯内部支撑超低延迟交易系统（公开案例可查，具体数字以厂商披露为准）。
- **APM 产品**：Pinpoint、SkyWalking（`apache/skywalking`，虽未单独查 star，属真实项目）、
  Elastic APM 等把 5.1.5「外部依赖慢」做成可视化调用链。
- **压测工具**：`wrk`/`hey`/`jmeter`（Apache JMeter，真实项目）配合 5.2 调优闭环。

> 说明：star 数未在本题集中核实的部分（如 skywalking、jmeter），本目录**未杜撰数字**，仅标注项目真实存在。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「性能不行就加机器/加内存」 | 先定位瓶颈类型；资源没满却慢时加机器无效（见 5.1.5） |
| 2 | 「JVM 调优就是调 -Xmx」 | 收集器与停顿目标同样关键；且 G1/ZGC 已大幅降低手动调参需求 |
| 3 | 「CPU 100% 一定是算法烂」 | 可能是 sy 态的锁竞争/上下文切换，先看 us/sy 占比 |
| 4 | 「内存涨就是泄漏」 | 也可能是分配过快/GC 跟不上/堆外（Netty 的 direct buffer）未控 |
| 5 | 「资源都没满就不慢」 | 锁竞争、外部依赖 RT、GC STW、伪共享都会让程序慢（5.2.3） |
| 6 | 🔧 5.1 工具链过时 | 2026 必补 JFR/async-profiler/Arthas/Prometheus；单靠 jmap/jstack 不够 |
| 7 | 🔧 5.2.1 GC 参数全换 | CMS 已移除；今天 G1 默认、ZGC/Shenandoah 可选，调优范式变了 |
| 8 | 🔧 5.1/5.2 缺容器化变量 | 容器里必须容器感知 + 按 cgroup 设堆，否则 OOMKilled |
| 9 | 🔧 5.1.5 缺分布式追踪 | 2026 用 OpenTelemetry 直接定位「外部依赖慢」的 span，本书靠猜 |
| 10 | 🔧 5.2.2 缺现代程序优化 | 异步化（CompletableFuture）、虚拟线程、原生镜像等本书未及 |
