# 第 6 章　构建高可用的系统

> 原书第 6 章进入**实践篇的架构目标**：高可用（系统尽量不挂、挂了也能快速恢复）。
> 它的核心论断朴素但永恒——**「避免单点」是第一步（负载均衡 + 热备），
> 然后「减少故障、及时发现、快速处理」**。这套三段式在 2026 年依然成立，
> 只是实现从「手写主备 + 心跳」变成了「Kubernetes 多副本 + 健康检查 + 自愈 + 多可用区」。
> Service Mesh 的熔断/限流/重试进一步把「提高应用自身可用性」下沉到基础设施。
> 读这章要**保留三段式心智，更新为高可用架构的云原生实现**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 6.1 避免系统中出现单点 | 负载均衡技术（软硬件/四七层）、热备（主备切换） | **消除单点是高可用的前提**；任何组件都要有冗余 |
| 6.1.1 负载均衡技术 | DNS/HTTP/LVS/Nginx、轮询/加权/最小连接、会话保持 | 把流量分摊到多实例，同时隐含「去单点」 |
| 6.1.2 热备 | 主备、心跳检测、VIP 漂移/切换 | 单点宕机时备机接管，RTO 取决于切换速度 |
| 6.2 提高应用自身的可用性 | 避免故障、及时发现故障、及时处理故障、应对访问/数据量上涨 | 单点消除后，靠「预防-发现-恢复」三件套兜底 |
| 6.2.1 尽可能地避免故障 | 灰度发布、限流、降级、压测 | 最好的处理是不发生 |
| 6.2.2 及时发现故障 | 监控、健康检查、告警 | 看不见的故障最致命 |
| 6.2.3 及时处理故障 | 自动切换/重启、故障隔离、预案 | 处理要快且可自动化 |
| 6.2.4 访问量及数据量上涨的应对 | 扩容、缓存、拆分 | 容量规划是高可用的延伸 |

## 核心精讲

（以下为教学性梳理；所有片段均**教学示意，不参与构建**，绝不编译/运行。）

### 6.1 去单点：负载均衡 + 热备

```text
# 教学示意，不参与构建：去单点的两种基本手段
A) 负载均衡(横向复制, 多活):
   流量 -> [LB] -> App1 / App2 / App3   (任一挂, LB 摘除, 服务不中断)
B) 热备(主备, 一主一备):
   App(主) <--心跳--> App(备) ; 主挂 -> VIP/流量切到备 (RTO=切换耗时)
差别: A 多实例同时服务(利用率高); B 备机闲(浪费但简单)
```

- **负载均衡的层次**（本书 6.1.1）：DNS（粗粒度、TTL 慢）、四层（LVS/IP，快、无应用感知）、
  七层（Nginx/网关，可按 URL/会话路由）。**会话保持**保证同一用户落到同一实例，但有损于水平伸缩。
- **热备的关键**是**心跳 + 切换决策**：误判（脑裂）会让两台都以为自己是主。本书时代靠 VIP 漂移；
  今天 K8s 的 readiness/liveness 探针 + 控制器天然解决。

### 6.2 提高应用自身可用性：预防-发现-恢复

```text
# 教学示意，不参与构建：三段式
预防: 灰度/金丝雀发布, 限流(令牌桶/漏桶), 降级(非核心功能关掉), 全链路压测
发现: 指标(CPU/QPS/错误率) + 日志 + 链路追踪 -> 告警(阈值/异常检测)
恢复: 自动重启/切流, 故障域隔离, 预案演练(混沌工程)
```

> 读这一章时请对照 [07-构建可伸缩的系统.md](07-构建可伸缩的系统.md)（6.2.4 的容量上涨正是第 7 章伸缩的动机）、

## 版本演进

- **本书无第二版**；本节写 2010 年口径 → 2026 年视角的变化。
- **去单点由 K8s 原生承载**：本书手写的「负载均衡 + 热备 + 心跳」被
  **Deployment 多副本 + Service（集群内 LB）+ 多可用区 + 探针自愈**取代；
  外部流量由 Ingress/API 网关（Spring Cloud Gateway、Kong、APISIX）承接。
- **熔断/限流/重试下沉到 Service Mesh**：Istio（`istio/istio` 38408★）+
  Envoy（`envoyproxy/envoy` 28995★）以 sidecar 提供这些能力，应用零改造
  （对应本书 6.2.1 的限流/降级、1.2 的调用容错）。
- **注册发现保证「实例列表实时正确」**：本书的「热备切换」依赖手写心跳；
  今天 `alibaba/nacos` 33419★ / `apache/zookeeper` 12811★ 提供健康检查 + 自动摘流。
- **可观测性支撑「及时发现」**：本书 6.2.2 的监控告警，今天由
  Prometheus + Grafana + OpenTelemetry + Alertmanager 实现；混沌工程（Chaos Mesh 等）主动验证「能恢复」。
- **多活与单元化**：本书是「同城主备」；2026 年头部系统是「异地多活 / 单元化路由」，
  把 6.1 的去单点做到城市级（RPO≈0、RTO 秒级）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「加了负载均衡就高可用了」 | 后端/数据库/缓存/依赖服务都可能是单点，需逐层去单点 |
| 2 | 「热备一定能无缝切换」 | 切换有 RTO；脑裂/VIP 漂移失败会双主或全断，需演练 |
| 3 | 「高可用=不挂」 | 目标是「少挂+快恢复」；RTO/RPO 才是量化指标 |
| 4 | 「监控装了就发现故障」 | 无告警阈值/无链路，等于没看；需可观测三支柱(指标/日志/追踪) |
| 5 | 「限流降级是可选的」 | 它是 6.2.1「避免故障」的核心；没有则雪崩 |
| 6 | 🔧 6.1 仍停留在手写主备/心跳 | 2026 去单点由 K8s 多副本+探针+多可用区原生承担 |
| 7 | 🔧 6.2.1 缺 Service Mesh 降级/熔断 | Istio/Envoy 把容错下沉基础设施，应用零改造 |
| 8 | 🔧 6.2.2 缺现代可观测性 | 2026 用 Prometheus/OTel/告警，混沌工程主动验证恢复 |
| 9 | 🔧 6.1 缺「城市级多活/单元化」 | 本书是同城主备；2026 头部做到异地多活，RPO≈0 |
