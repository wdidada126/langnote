# 第 7 章　构建可伸缩的系统

> 原书第 7 章是实践篇的**最后一章、也是全书的落点**：可伸缩（系统能随业务增长平滑扩容）。
> 它把伸缩拆成**垂直伸缩（升单机配置）**与**水平伸缩（加机器/拆系统）**两条路，
> 并对「高访问量 / 大数据量 / 提升计算能力」逐一给策略。
> 这套二分法在 2026 年依然成立，但**水平伸缩的执行者已从「手写分库分表 + 加 Web 节点」
> 变成「Kubernetes HPA 自动扩缩 + 存算分离 + 分片中间件」**。
> 读这章要**保留「垂直 vs 水平」的框架，更新为云原生的弹性伸缩实现**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 7.1 垂直伸缩 | 提升单机能力：更强的 CPU/内存/磁盘、加缓存、升级算法 | **垂直有天花板**（单机物理上限、成本非线性），是「先顶一阵」的快招 |
| 7.1.1 支撑高访问量 | 升配置、本地缓存、连接池优化 | 垂直缓解读压力，但不解决写/存储瓶颈 |
| 7.1.2 支撑大数据量 | 更大内存/磁盘、压缩、索引优化 | 数据量超单机容量时必须转向水平 |
| 7.1.3 提升计算能力 | 更多核、并行化、JVM/GC 调优 | 受阿姆达尔定律约束，并行有收益上限 |
| 7.2 水平伸缩 | 加机器/拆系统：无状态层扩容、数据分片、读写分离、异步化 | **水平近乎无限伸缩**，但带来分布式复杂度 |
| 7.2.1 支撑高访问量 | 无状态 Web/服务多实例 + 负载均衡 | 无状态是水平伸缩的前提（见第 6 章去单点） |
| 7.2.2 支撑大数据量 | 数据库分库分表、分布式存储、冷热分离 | 数据超单机必须分片，引入一致性/路由成本 |
| 7.2.3 提升计算能力 | 任务并行/MapReduce、分布式计算框架 | 计算任务切分多机执行 |

## 核心精讲

（以下为教学性梳理；所有片段均**教学示意，不参与构建**，绝不编译/运行。）

### 7.1 vs 7.2：先垂直、后水平，但终归要水平

```text
# 教学示意，不参与构建：伸缩路线决策树
流量/数据上涨
  |
  |-- 单机还有余量? --> 垂直伸缩(升配/缓存/调优)  --快但到顶
  |
  |-- 单机到顶? --> 水平伸缩:
        无状态层 -> 加实例 + LB (最简单, 见 6.1)
        存储层   -> 分库分表 / 分布式存储 (引入路由+一致性)
        计算层   -> 任务分片 / MapReduce
```

- **垂直伸缩的上限**：受单机物理容量、成本非线性（顶配机器单价远超中配）、
  **阿姆达尔定律**（并行化收益受串行比例限制）三重约束。它是「先顶一阵」的快招，不能当终局。
- **水平伸缩的前提是「无状态」**：有状态实例无法直接加副本（状态怎么同步？）。
  本书 6.2 的去单点 + 7.2 的水平伸缩共同要求：**把状态外移到缓存/数据库/共享存储**。
- **数据分片的代价**（本书 7.2.2 的隐含成本）：分库分表后，**跨分片事务、全局索引、扩容再平衡**
  全部变难——这正是今天分片中间件（ShardingSphere）与分布式数据库要解决的（见「与其他书的联系」）。

### 7.2.3 计算能力的水平化：从多线程到 MapReduce

```text
# 教学示意，不参与构建：单机并行 -> 多机并行
单机: 线程池把大任务切成子任务并行 (受核数/内存限)
多机: 任务调度框架把子任务分发到 N 台机器 (Hadoop/Spark/Flink 思路)
      -> 容错(任务失败重跑) + 数据本地性 +  shuffle 是分布式计算的核心难题
```

> 读这一章时请对照 [06-构建高可用的系统.md](06-构建高可用的系统.md)（水平伸缩的多实例即 6.1 去单点）与
> [04-分布式应用与SunJDK类库.md](04-分布式应用与SunJDK类库.md)（7.2.3 并行依赖 4.2 的线程池/并发工具）。

## 版本演进

- **本书无第二版**；本节写 2010 年口径 → 2026 年视角的变化。
- **水平伸缩由 K8s 自动化**：本书手写的「加 Web 节点 + 配 LB」被
  **Deployment + HPA（基于 CPU/QPS/自定义指标自动扩缩）+ Cluster Autoscaler** 取代；
  弹性从「人审批」变为「秒级自动」。
- **存储层分片的中间件化**：本书 7.2.2 的「手动分库分表」今天由
  **ShardingSphere、Vitess（YouTube 开源的 MySQL 分片）、TiDB（分布式数据库）**承载，
  自动路由 + 弹性扩容，免去手写分片逻辑。
- **存算分离**：本书「大数据量」靠堆单机磁盘；2026 年对象存储（S3/OSS/MinIO）+
  计算节点无状态化，让存储与计算各自伸缩（见 [../湖仓架构大规模数据平台的设计和实现] 相关笔记）。
- **Serverless / 函数计算**：极致水平伸缩形态——按请求量从 0 到 N 瞬时扩缩，
  把 7.2 的「水平伸缩」推到「无需关心实例」的极端。
- **分布式计算框架成熟**：本书 7.2.3 的「任务并行」今天由 Spark/Flink/Ray 标准化；
  Flink 的流批一体取代早期 MapReduce 思路。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「加机器就能无限伸缩」 | 有状态/单点/数据耦合会卡住水平伸缩；先无状态化、外移状态 |
| 2 | 「垂直伸缩能解决一切」 | 受单机物理上限、成本非线性、阿姆达尔定律三重约束 |
| 3 | 「分库分表一劳永逸」 | 引入跨片事务、全局索引、扩容再平衡难题；今天交给中间件/分布式DB |
| 4 | 「伸缩只是运维的事」 | 架构必须「为伸缩而设计」（无状态、数据分片、异步） |
| 5 | 🔧 7.2 仍是手写加节点/分表 | 2026 由 K8s HPA 自动扩缩 + ShardingSphere/Vitess/TiDB 承载 |
| 6 | 🔧 7.1/7.2 缺「存算分离」 | 对象存储+无状态计算让存储/计算各自伸缩，本书只有堆单机磁盘 |
| 7 | 🔧 7.2.3 缺现代计算框架 | Spark/Flink/Ray 标准化分布式计算，本书只有概念性并行 |
| 8 | 🔧 7.2 缺 Serverless/函数计算 | 极致水平伸缩：按请求 0→N 瞬时扩缩，本书未及 |
| 9 | 🔧 7.2 缺「容器化弹性」 | 弹性伸缩在 2026 是声明式指标驱动，而非人工加节点 |
