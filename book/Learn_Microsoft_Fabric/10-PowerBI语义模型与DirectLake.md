## 2. 三种连接模式辨析（⚠️ 转述）

| 模式 | 数据在哪 | 刷新语义 | 适用 |
|---|---|---|---|
| Import | 模型内列存副本 | 定时全量/增量刷新 | 中小规模、快查询 |
| DirectQuery | 留在源库 | 查询时穿透 | 实时强约束/超大表 |
| Direct Lake | 就在 OneLake 表 | **免导入**，读时直用 | Fabric 仓/湖表主场 |

- Direct Lake 要点（⚠️ 转述）：语义模型不复制数据，报表引擎直接读湖/仓的列存文件；
  大模型 + 高频访问场景下绕开「刷新窗口税」；限制面（源表类型、计算列代价）以当日页为准。
- 官方 URL 本轮仅验到 semantic-models 域页 200；Direct Lake 专页现行路径未定位——
  引用写 ⚠️ 并建议读者当日搜「Direct Lake」核实（诚实登记，波 5 册同样发现旧链 404）。

## 3. 🔧 本机类比：Direct Lake ≈ 免导入直读（非 Fabric 行为）

```text
E4 直读新增数据文件实验（DuckDB 1.5.5，2026-10-02 实测）：
  基表 ev.parquet（1,000,000 行）+ 新落盘 append.parquet（100,000 行）
  read_parquet(['ev.parquet','append.parquet']) 直查：1,100,000 行，墙钟 1.8ms
  ——新文件**不经任何导入步骤**即可被查询命中（OS 缓存热态）
迁移直觉：Direct Lake 的「数据落地=即刻可分析」正是把「导入/刷新」从关键路径上摘掉；
  代价结构从「导入窗口」转移到「每次查询的扫描成本」（对照 05 章 E5 列存数量级）。
（类比声明：Fabric 语义模型的 VertiPaq/缓存/并发机制与 DuckDB 无实现对应，平台行为不可本机实测 ⚠️）
```

## 8. 模式选择决策树（重构表）

- 数据已在 Fabric 仓/湖且查询面广？→ Direct Lake 优先，小参考表混布 Import；
- 源不在 Fabric 且不能落地？→ DirectQuery（接受源端墙钟）；
- 规模小、口径复杂、要极致交互？→ Import（付刷新税）；
- 犹豫时：按「刷新窗口是否业务硬约束」一票裁决（⚠️ 重构决策句）。

## 9. 教学 FAQ（重构问答位，⚠️ 非原书）

- **问：Direct Lake 下计算列还香吗？** 答：计算列把成本从刷新移到每次查询（对照 🔧 E4/E5
  代价转移直觉）；重口径尽量上移 SQL/建模层（⚠️ 转述+判读）。
- **问：语义模型和仓库视图谁定义指标？** 答：同一指标只允许一个家——DAX 度量留交互口径、
  SQL 留物化口径，冲突时以治理登记为准（11 章联动）。
- **问：老 PBI 报表怎么进来？** 答：工作区原生存在；升级重点在模式重设与容量绑定，
  不是重建报表（⚠️ 转述，细则当日核）。

## 最新演进与工业实践

- 趋势线（⚠️ 转述）：微软把报表语义层的叙事从「导入性能学」推向「湖仓直读学」——Direct Lake
  及其对外部表/ Iceberg 源的扩面是 2024–2026 BI-Fabric 交汇的主增量；本册不断言「Import 已死」
  之类口号，规模/并发/治理仍是三因子权衡（✅ whats-new 页 2026-10-02 验 200）。
- 工业实践：大客场景常见组合=仓表 Direct Lake 主力 + 小参考表 Import 混布；「先治模型清单，
  再谈 AI 辅助报表」是顾问共识路径（⚠️ 转述）；DP-600 考点画像：三模式取舍题与
  模型权限继承题（⚠️ 推定）。
