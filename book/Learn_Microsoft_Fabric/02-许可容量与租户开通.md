## 2. 许可分级骨架（⚠️ 转述官方 licenses 页）

| 层级 | 面向 | 关键限制 | 典型用途 |
|---|---|---|---|
| 免费 Fabric 试用容量 | 个人学习 | 限时限容（F 级试用） | 本书式教学实验 |
| Power BI 免费档 | 个人探索 | 不能发布共享 | 试语义模型 |
| Power BI Pro/Premium Per User | 协作 | 容量门槛触发 Fabric 全功能受限 | 中小团队 |
| Fabric 专用容量（F SKU） | 企业 | 按 CU 数分档，从低档到千 CU 级 | 生产工作负载 |
| 预留/按月计费 Azure 订阅挂载 | 成本治理 | 承诺期换折扣 | 稳态大租户 |

- 核心机制：**容量（Capacity）= CU 池**；所有 item 的操作折算成 CU 消耗进同一池子——
  数仓查询、笔记本运行、刷新、报表渲染同池竞价（⚠️ 转述）。
- 「试用容量可自建、免 Azure 订阅」是学习路径的第一钥匙（⚠️ 转述；✅ 门户枢纽 <https://learn.microsoft.com/en-us/fabric/>）。

## 3. 租户开通与管理员动作面（⚠️ 转述）

- 开通链：Entra ID 租户 → 管理员门户（admin portal）→ 开产品门（是否允许用户自助试用）→
  用户建工作区（✅ 域名入口 <https://learn.microsoft.com/en-us/fabric/>，管理页具体路径本轮未逐一验链，⚠️ 登记缺口）。
- 租户级开关决定一切：是否允许外部来宾、是否允许跨租户分发、是否强制工作区绑定容量——
  「先问租户设置再问性能」是排障第一课（⚠️ 转述）。
- 工作区 ↔ 容量映射：一个容量可挂多工作区；容量间可做**故障隔离**（把生产与探索分池），
  这是成本与稳定性的第一个架构决策（⚠️ 推定本书会强调）。

## 4. CU 消耗的结构直觉（🔧 本机类比，非 Fabric 行为）

- Fabric 的 CU 可粗略理解为「并行供给单位」：查询耗时 ≈ 数据量 ÷ 并行度。本机 DuckDB 线程弹性
  实验演示同一聚合在 1 线程 vs 8 线程的差异（脚本 `D:\develops\tmp\dbwave_w9_learnf\`）：

```text
E6 3,000,000 行分组聚合：threads=1 → 71.2ms；threads=8 → 20.0ms；加速比 3.57x
（DuckDB 1.5.5，本机实测 2026-10-02；**非 Fabric/Fabric CU 平台行为**，仅作「并行供给摊薄墙钟」类比）
```

- 结论迁移（⚠️ 类比推论）：加 CU 不改变总工作量，只摊薄墙钟；小数据集加速比受并行开销侵蚀
  （本机 8 线程只有 3.57× 而非 8×）——对应「容量买大不等于所有 item 都变快」。

## 5. 成本工程清单（⚠️ 转述 + 推定体裁）

- 观测三件套：容量指标页（CU 秒级曲线）、工作区消耗归因、查询级计量——先归因再优化（⚠️ 转述）。
- 常见烧钱点（⚠️ 转述社区共识）：高频刷新（语义模型每小时全量重导入）、笔记本常驻大会话、
  镜像初始全量同步、跨容量搬迁数据。
- 控费动作（⚠️ 转述）：刷新节流与增量优先、会话池参数收紧、镜像用增量、按环境分容量并
  设置容量仪表板告警（Fabric 管理员门户能力，具体页面本轮 ⚠️ 未逐条验链）。
- 与云仓对照（盘上实链）：Redshift 的并发槽位、Snowflake 的 credit 仓库尺寸——三种供给模型
  在 [../Amazon_Redshift_TDG/00-总览与阅读地图.md](../Amazon_Redshift_TDG/00-总览与阅读地图.md)、
  [../Snowflake_The_Definitive_Guide/00-总览与阅读地图.md](../Snowflake_The_Definitive_Guide/00-总览与阅读地图.md) 各自有专章；

## 6. 许可选择的决策问答（⚠️ 重构案例位）

1. 只有 3 人做 POC？→ 自助试用容量，不碰采购（⚠️ 转述）。
2. 已有 Power BI Pro 全员？→ 起步用共享容量，把重负载 item 识别出来再决定是否升专用 F 容量（⚠️ 转述）。
3. 7×24 报表服务 + 批量管道混跑？→ 专用容量 + 环境分离 + CU 告警三件套（⚠️ 推定）。
4. 合规要求数据不出地区？→ 先看租户区域与容量区域绑定规则（⚠️ 转述，细则当日页核实）。

## 8. 开通演练脚本（教学体裁推定位，⚠️ 推定本书含此类 Runbook）

1. 用组织账号登录门户 → 自助申领试用容量（免 Azure 订阅）（⚠️ 转述）。
2. 建两个工作区：`lab-dev`（实验）与 `lab-prod`（结课项目），记录各自 item 清单。
3. 在管理员门户截图「租户设置」中你关心的 5 个开关：外部共享、来宾邀请、试用许可、
   默认容量绑定、审计日志保留（⚠️ 转述，页面名当日核实）。
4. 运行一次最小管道 + 一次笔记本会话，回到容量指标页观察 CU 曲线形状：是「尖峰」还是「平台」？
   尖峰=即席查询型，平台=常驻刷新型——这个直觉决定升配方向（⚠️ 推定练习设计）。
5. 把第 4 步的观察写成「消耗归因备忘录」模板（工作区→item→动作三级下钻）——即 02 章的结课物。

- 检查点：若你的账号看不到管理员门户，说明角色不够——这是**设计如此**（SaaS 权限分层），
  不是故障（⚠️ 转述）。

## 核心概念速览（中英对照）

| 中文 | 英文 | 一句话 |
|---|---|---|
| 容量单位 | Capacity Unit (CU) | 跨工作负载共享的计费/供给单位 |
| 专用容量 | dedicated capacity (F SKU) | 企业生产用的独立 CU 池 |
| 试用容量 | trial capacity | 自助、限时、教学向 |
| 管理员门户 | admin portal | 租户级开关与容量管理的唯一入口 |
| 消耗归因 | capacity metrics attribution | 把 CU 曲线拆到工作区/item |
| 增量刷新 | incremental refresh | 控费第一杠杆 |
| 产品门 | product gate | 允许/禁止用户自助开通的租户开关 |
| 环境分离 | environment separation | 用容量边界做故障与成本隔离 |
