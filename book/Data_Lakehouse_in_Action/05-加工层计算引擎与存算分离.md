## 2. 存算分离经济学（§1）

```
传统 MPP 数仓                    湖仓存算分离
┌───────────────┐               ┌─────────┐   ┌─────────┐
│ 计算+存储绑定 │               │ 弹性计算 │ ← │ 对象存储│  ← 独立扩容
│ 扩容=整体翻倍 │               │ 按需起停 │   │ 按GB·月 │
└───────────────┘               └─────────┘   └─────────┘
 闲置为账单买单                  闲置≈0（停机），重算不搬数据
```

- 代价面：网络成为新的"内存总线"，扫描性能取决于 §3 的布局纪律与元数据裁剪质量
  ——存算分离把"要不要买大机器"变成"会不会排文件"。
- ✅ Azure 语境总口径（Synapse= 数据集成+多引擎+安全治理的伞形服务）：
  <https://learn.microsoft.com/en-us/azure/synapse-analytics/overview-what-is>。

## 4. 🔧 实测组四：行组统计裁剪依赖数据布局（DuckDB 1.5.5）

**方法**：4,000,000 行 (id, h) 表写出同一 Parquet（ROW_GROUP_SIZE 122880 ⇒ 66 行组，
`parquet_metadata()` 计数验证），两种物理序：按 id 排序 vs 按 hash 打乱。
同一谓词 `WHERE id BETWEEN 1000 AND 1999`（命中 1,000 行，0.025% 选择率）：

| 文件布局 | best-of-5 耗时 | 命中校验 |
| --- | --- | --- |
| 按 id 有序 | **0.0040 s** | count=min=1000 ✓ |
| 按无关列打乱 | **0.0111 s** | 同左 ✓ |
| 比值 | **×2.8** | 同数据同格式同谓词，唯一变量=布局 |

- 前置组（同实验族）：单文件 66 行组、全扫 0.0100s → 高选择率点查 0.0048s——
  证实**行组 min/max 统计被用作跳过依据**；但乱序时统计区间全体重叠、信息量归零。
- 判读：**谓词下推不是引擎的恩赐，是布局的函数**——这解释了工业界为何把
  Z-ORDER/Liquid Clustering/`sort` 写策略当作湖仓第一性能手段（§7 链接处有实操版）。
- 错位声明：姊妹目录 #195 册 🔧 为分位数语义类比、DLUR 为 sqlite 版本表——本组
  （布局×行组裁剪）为新增证据，不与前册重复。

## 6. 作业形态与文件节拍（§5）

```
新鲜度需求 ↑            提交节拍 ↓           文件数 ↑
批(T+1)      ── 每日一次大提交 ──   大文件✓
微批(5-15min) ─ 检查点即提交 ─      中文件
流(秒级)     ── 高频小提交 ──      小文件✗ → 必须配 compaction（04 §6 🔧 的税）
```

- 设计恒等式：**新鲜度目标 − 提交开销 = 系统真实吞吐上限**；把 03 章 exactly-once
  三段与本章节拍放在一起，才构成完整的"摄入-加工"账。
- 对位：Paimon LSM 路线用"写优化换读税"（→ 09 章书系链接
  [../Apache_Paimon_Streaming_Lakehouse/02-核心数据结构LSM树与主键表.md](../Apache_Paimon_Streaming_Lakehouse/02-核心数据结构LSM树与主键表.md)），

## 8. 常见误区

| 误区 | 修正 |
| --- | --- |
| "存算分离=性能免费" | 网络顶掉了本地盘红利，性能改由布局纪律决定（§4 🔧） |
| "谓词下推开了就快" | 布局乱序时下推信息量归零，×2.8 差距即证据（§4） |
| "一个湖只配一个引擎" | 多引擎路由是范式本意；单引擎绑定=新的厂商锁定（§5） |
| "流式总比批先进" | 秒级新鲜度的账单是 compaction 与冲突处理（§6），批仍是很多场景正解 |
| "自动扩缩容解决成本问题" | 无归集标签时只解决弹性不解决问责（§7） |
| "Spark 参数调优=湖仓调优" | 文件数/布局/统计的存储侧旋钮优先于 executor 内存旋钮（§4→§6 链） |

## 核心概念速览（中英对照）

- **存算分离** — Disaggregated Storage & Compute：计算与存储独立扩缩的架构（§1）。
- **计算引擎** — Compute Engine：Spark/Flink/Trino/SQL 端点等湖上执行器。
- **行组统计** — Row-Group Statistics：min/max 等摘要，谓词下推的情报源。
- **数据布局** — Data Layout/Clustering：物理排序与聚簇，裁剪收益的先决条件（🔧 §4）。
- **Z-ORDER / Liquid Clustering** — 多维聚簇技术：以写放大换读裁剪（§4 判读）。
- **微批** — Micro-Batch：流批折中形态，提交节拍=文件节拍。
- **检查点** — Checkpoint：流作业故障恢复位点，与湖提交原子对齐是难点（§6）。
- **引擎路由** — Engine Routing：按负载把查询派给合适引擎（§5）。
- **成本归集** — Cost Attribution：按团队/作业标签拆分账单（§7）。
- **并发风暴** — Concurrency Storm：交互小查询与批扫描互踩（§7）。
