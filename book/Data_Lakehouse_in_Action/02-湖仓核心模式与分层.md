## 3. 事务层：ACID 从哪来（§2）

- **对象存储提供的原语极弱**：整文件 PUT 原子、无 append、无 rename 原子性保证（ADLS
  的 rename 目录语义是"逐文件 copy"陷阱 ⚠️ 通识）。
  ✅ ADLS 分层命名空间与 POSIX 语义边界：
  <https://learn.microsoft.com/en-us/azure/storage/blobs/data-lake-storage-introduction>。
- **表格式的三件套**：
  1. **快照清单**（snapshot/manifest/commit-log）：一次提交 = 追加一个"当前文件全集视图"；
  2. **提交协议**：靠"条件写/日志序号抢占"实现串行化（Delta `_delta_log` 条件 PUT、
     Iceberg catalog 原子换 metadata 指针——机制各异，语义同构）✅ 各家文档口径；
  3. **文件不可变 + 写时复制**：UPDATE = 写新文件 + 清单里替换旧文件引用，旧文件留给
     时间旅行，过期由清理任务回收（VACUUM/expire_snapshots → 11 章）。
- 纵深互链：[../Delta_Lake_Up_and_Running/02-事务日志与提交协议.md](../Delta_Lake_Up_and_Running/02-事务日志与提交协议.md)
  的 sqlite 手写迷你版本表给出提交协议的最小复现；本章 🔧 则站在**真引擎**一侧看
  "快照隔离到底多强"。

## 4. 🔧 实测组一：快照可见性与写冲突（DuckDB 1.5.5，Python 客户端，文件库 mvcc.db）

**方法**：两个独立连接 a/b 指向同一 DuckDB 文件库，交叉开启事务、读、写、提交，
记录可见性与冲突行为（脚本与输出存 `D:\develops\tmp\dbwave_w6_dlai\exp6.log / exp8.log`）。

| # | 场景 | 实测结果 | 湖仓语义对位（⚠️ 类比，非本书引擎行为） |
| --- | --- | --- | --- |
| 1 | a 在途事务读 → b 提交 UPDATE 后 a 再读同一行 | a 读到 **`new`**（对方新值可见） | DuckDB 默认为**语句级快照**；Delta/Iceberg 的读固定在查询起始快照，不会中途换——"事务级快照"反而更强 |
| 2 | b 已 DELETE 未提交 → a 读表 | a 见 **2 行**（删除不可见） | 双方都不脏读：对应表格式的 READ COMMITTED 隔离 ✅ 文档口径 |
| 3 | b 提交删除 k=2 → a 的在途事务 UPDATE 同一行 → a 提交 | a 提交**成功**，终态 `[(1,'orig')]`（更新落在已被删行上，静默消失） | **丢失更新**在此不被拦截；Delta 默认可串行化冲突检测会在提交时报错回滚 ⚠️ 文档口径——单机嵌入式与分布式乐观并发在此分道 |
| 4 | 写写不重叠（a 插入新键、b 删他键） | 双双提交，无冲突 | 行级冲突粒度，与表格式"读集/写集相交才算冲突"同型 |

**三点判读**：
1. "有 ACID"三个字背后是三种独立承诺——**原子提交**（场景 2 的不可见性）、
   **快照一致性**（场景 1 暴露其档位差异）、**冲突检测**（场景 3 暴露其缺席代价）；
   选型时逐项问，不要打包接受。
2. 场景 1/3 的差异**不是 DuckDB 缺陷**，而是嵌入式单写者引擎与共享存储多引擎并发
   （本书语境：Spark+Synapse+BI 同读一湖）根本不在同一威胁模型里——这正是湖仓需要
   表格式的理由。
3. 把本组实验的"冲突静默消失"放大到生产，就是 06 章治理要拦的"双写者踩踏"事故。

## 5. 数据分层：Bronze/Silver/Gold（§4，⚠️ 推定按 medallion 通用口径重构）

| 层 | 内容 | 变换 | 典型消费者 |
| --- | --- | --- | --- |
| Bronze（原始） | 源系统原样落地，含坏数据 | 只加技术元数据（到达时间、批次） | 排障、重放 |
| Silver（清洗） | 去重、类型对齐、轻度集成 | 质量规则 + schema 约束生效 | 数据工程 / ML 特征 |
| Gold（服务） | 面向主题的聚合/宽表 | 维度建模或集市化 | BI、数据科学、应用 API |

- 关键工程决策是**每层物化还是视图**：层层的物理副本 = 存储翻倍 + 一致性窗口；
  纯视图 = 读放大。实务按"复用度×重算成本"决定（→ 04 章小文件实测的读放大证据）。
- 对位盘上：Databricks medallion 官方口径 ✅ <https://learn.microsoft.com/en-us/azure/databricks/lakehouse/>；
  Delta 专著纵深 [../Delta_Lake_Definitive_Guide/08-湖仓架构-Medallion.md](../Delta_Lake_Definitive_Guide/08-湖仓架构-Medallion.md)。

## 6. 与 Inmon 三层瀑布对位（§5）

| medallion | Inmon 三层（[../The_Data_Lakehouse/04-大容量存储器与数据湖仓.md](../The_Data_Lakehouse/04-大容量存储器与数据湖仓.md)） | 分歧点 |
| --- | --- | --- |
| Bronze | 原始数据层 raw | 基本同义 |
| Silver | 近生产数据 near-production | Inmon 强调"集成后才可复用"；medallion 对集成的强制较弱 |
| Gold | 生产数据 production | Inmon 要求与仓库模型同等级别的集成纪律 |
| （无） | 数据砂仓 sandpit | Databricks 生态用 workspace/notebook 承担，不入数据层 |

**判读**：两套语言描述同一风险——"越靠近消费者，越需要 schema 与集成纪律"。
Menon（⚠️ 推定立场）取 Databricks 谱系；Inmon 视为自家理论的湖化延伸。目录版读者
应两本对读：[../The_Data_Lakehouse/12-对照章-Inmon理论与开放表格式实现.md](../The_Data_Lakehouse/12-对照章-Inmon理论与开放表格式实现.md)。

## 7. 开放接口是命门（§6）

- 表格式规范公开（Iceberg spec ✅ <https://iceberg.apache.org/spec/>；Delta protocol 公开 ⚠️）
  ⇒ 引擎可替换 ⇒ 数据资产寿命 > 任何单一引擎的商务周期。
- 反例警惕：本书 2022 年语境里"湖仓"常被与 Databricks 捆绑销售；Menon 的对策是把
  六动词生命周期与具体产品解耦（⚠️ 推定），2024 后 Iceberg 成为跨厂商公约数（→ 11 章）。

## 8. 常见误区

| 误区 | 修正 |
| --- | --- |
| "表格式给了快照隔离就是事务级" | 档位不同：查询级/语句级/事务级要实测（§4 场景 1） |
| "写写冲突一定会被引擎拦下" | 只有提交时冲突检测在位才拦得住（§4 场景 3：丢失更新静默通过） |
| "分层=每层都物化一份" | 视图/物化按复用×重算成本决策（§5） |
| "用哪个表格式不重要，反正都 ACID" | 协议细节（冲突定义、清理语义、多引擎支持）差异巨大（→ 12 本湖仓书系地图） |
| "时间旅行免费" | 旧文件要留存才谈得上旅行，与清理策略对冲（→ 04/11 章） |

## 核心概念速览（中英对照）

- **参考架构五积木** — Storage / Table format / Governance / Compute / Serving：湖仓解剖的标准切法（⚠️ 本书口径重构）。
- **原子提交** — Atomic Commit：全部可见或全部不可见的版本切换。
- **条件写** — Conditional Put：对象存储上实现串行化的关键原语 ✅ 文档口径。
- **快照隔离** — Snapshot Isolation：读固定于一个版本；DuckDB 实测显示语句级与事务级有别（🔧 §4）。
- **丢失更新** — Lost Update：并发下后写覆盖先写的经典异常（🔧 §4 场景 3）。
- **写时复制** — Copy-on-Write：UPDATE=写新文件+改清单，不改原文件。
- **medallion 分层** — Bronze/Silver/Gold：原始/清洗/服务（⚠️ 推定）。
- **信息供应链瀑布** — Inmon raw/near-production/production：与 medallion 对位的另一套纪律语言。
- **引擎中立性** — Engine Neutrality：开放表格式规范支撑的多引擎可替换性。
- **数据砂仓** — Data Sandpit：Inmon 体系中专给数据科学的自由区（§6 表）。
