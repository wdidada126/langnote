## 2. 对象存储：便宜带来的四宗罪（§1）

1. **List 慢且贵**：按前缀分页列举，桶内百万文件时"看看有什么"本身成为成本——
   表格式的清单文件（manifest/checkpoint）正是在赎这笔罪（→ 02 章）。
2. **无原子 rename**：目录"移动"=逐对象拷贝；Hive 时代 `ALTER TABLE ADD PARTITION`
   的原子性幻想在此破产。
3. **最终一致性（历史包袱）**：S3 2020-12 起已强一致 ⚠️ 通识，但本书 2022 语境仍反复
   强调"先元数据后可见"的写入次序。
4. **请求费**：GET/LIST 按次计费 ⇒ 小文件问题在云上直接是账单问题（§5 🔧 的货币化版）。

## 3. ADLS Gen2 速览（§2，✅ 官方页 2026-09 抓 200）

- 定位：Blob 对象存储 + **分层命名空间（HDFS 兼容 POSIX 元数据）**，目录rename/ACL
  获得近似文件系统语义：
  <https://learn.microsoft.com/en-us/azure/storage/blobs/data-lake-storage-introduction>。
- 安全接口（RBAC + POSIX ACL 双层，→ 07 章）：
  <https://learn.microsoft.com/en-us/azure/storage/blobs/data-lake-storage-access-control>。
- ⚠️ 转述：即便有 POSIX 层，**表格式仍不依赖目录 rename 做提交**（各家协议都收敛到
  条件写/元数据指针），所以 ADLS 的 HDFS 兼容主要服务互操作，不是 ACID 地基。

## 4. Parquet：列式格式为什么是默认答案（§3）

```
Row Group（默认~128MB/百万行级）
 ├─ Column Chunk × N列   ←每列独立压缩编码
 │    └─ Page            ←最小解压单元
 └─ Footer: schema + 每列每row-group的 min/max 统计  ←谓词下推的情报源
```

- 垂切 → 列裁剪只读所需列；统计 → **行组级**谓词跳过；编码(RLE/字典) → 压缩率。
  ✅ 官方文档：<https://duckdb.org/docs/stable/data/parquet/overview.html>。
- 本书时代之争（Parquet vs ORC vs Delta 默认）已以 Parquet 全胜收场（→ 11 章对账）；
  盘上格式内幕纵深：[../bigdata/09-存储与文件格式.md](../bigdata/09-存储与文件格式.md)、
  [../DuckDB_in_Action/10-大数据集性能考量.md](../DuckDB_in_Action/10-大数据集性能考量.md)。

## 5. 🔧 实测组二：hive 分区裁剪的量化（DuckDB 1.5.5）

**方法**：2,000,000 行合成表（id/x/pad 三列，pad 60 字符），按 `dt = 2023-01-01 + id%365`
`PARTITION_BY dt` 写出 365 个日期分区（COPY 自动分片 ⇒ 共 **1,887 个 parquet 文件**），
以 `read_parquet('p2/*/*.parquet', hive_partitioning=1)` 对比全扫 vs 单日谓词：

| 指标 | 全分区扫 | `WHERE dt='2023-07-04'` | 说明 |
| --- | --- | --- | --- |
| 耗时（best of 3） | 0.116 s | 0.040 s | ≈ **×2.9**（本机 SSD 热缓存，比值偏保守） |
| profile 扫描文件数 | 1,887 | **5**（"Total Files Read: 5"） | EXPLAIN ANALYZE 直接给出裁剪铁证 |
| 返回行数 | 2,000,000 | 5,479 | 与 2M/365 理论值吻合（校验通过） |

**判读**：分区裁剪的收益上限=谓词选择率；比值没到 365 倍，是因为 DuckDB 并行列扫把
"打开不匹配文件"的固定开销摊薄了——在对象存储上这个固定开销是**每文件一次 GET+一次
元数据读**，按次计费且高延迟，裁剪收益会远大于本地盘（⚠️ 推理，方向与云厂商成本
指南一致）。分区键选错（与谓词无关）时收益归零——见 §7 误区 1。

## 6. 🔧 实测组三：小文件税（DuckDB 1.5.5）

**方法**：200,000 行数据，两种物化：A=200 个 1,000 行小文件；B=1 个 200,000 行文件。
同一查询 `SELECT count(*), sum(id)`（best of 3）：

| 形态 | 耗时 | 结果校验 |
| --- | --- | --- |
| A：200 files | 0.0228 s | (200000, 19999900000) ✓ |
| B：1 file | 0.0043 s | 同左 ✓ |
| **比值** | **×5.3** | 行数相同 ⇒ 差异全部来自文件级开销 |

- 20 万行在本地盘已付出 5 倍代价；小文件成本 = 每文件的 open/footer-read/统计合并，
  与行数无关 ⇒ 文件越碎税越重。流式摄入高频提交（03 章 §4）+ 高并行度写出是两大
  制造机；compaction（OPTIMIZE/rewrite_data_files）是还税手段 →
  [../Architecting_an_Apache_Iceberg_Lakehouse/10-湖仓维护.md](../Architecting_an_Apache_Iceberg_Lakehouse/10-湖仓维护.md)。
- 🔧E5 与姊妹目录错位的说明：#148 册的迷你清单实验演示的是 expire/orphan **语义**，
  本组量的是**读延迟税**，互不重复。

## 7. 分区策略：从 Hive 目录到隐藏分区（§6）

- 传统：路径即分区（`dt=2023-07-04/part-0.parquet`），谓词命中路径才裁剪（§5 实测所用）。
  痛点：粒度写死，查询方式一变就得重刷目录。
- Iceberg **隐藏分区**：分区表达式记在元数据里（`days(ts)`），查询按表达式匹配裁剪，
  且**分区演进**（evolve partition spec）只改元数据不动老数据 ✅
  <https://iceberg.apache.org/docs/latest/>。纵深互链：
  [../Use_Iceberg_with_Spark/05-演化与隐藏分区.md](../Use_Iceberg_with_Spark/05-演化与隐藏分区.md)、
  [../Engineering_Lakehouses_with_Open_Table_Formats/07-Schema与分区演化.md](../Engineering_Lakehouses_with_Open_Table_Formats/07-Schema与分区演化.md)。
- 替代方案：分区不动、数据内**聚簇**（Z-ORDER/Liquid）换读性能——DLUR 的 OPTIMIZE 章：
  [../Delta_Lake_Up_and_Running/04-时间旅行与表维护.md](../Delta_Lake_Up_and_Running/04-时间旅行与表维护.md)。
  布局对读路径的放大效应，本目录在 05 章用 🔧 实测组四给出"有序 vs 乱序同谓词 ×2.8"证据。
- 选择口诀：**高选择率等值谓词列做分区；基数爆炸列拒绝分区（小文件自伤）；
  时间列用隐藏分区或聚簇，别用天级目录赌查询模式**。

## 8. 常见误区

| 误区 | 修正 |
| --- | --- |
| "分区键随便选，反正能裁" | 裁剪只对**命中谓词**的分区表达式生效；与谓词无关=零收益还交小文件税（§5/§7） |
| "对象存储和盘语义一样" | List 成本、GET 计费、rename 非原子三罪各不同（§1） |
| "Parquet 快是因为压缩好" | 三大件是列裁剪+行组统计+编码，压缩只是搭头（§4） |
| "ADLS 有 POSIX 就能当 HDFS 用" | 提交协议不依赖 rename；POSIX 层主要为互操作与权限（§3 ⚠️） |
| "小文件只影响 List" | 本地实测无 List 场景也已 ×5.3（§6），云上叠加请求费更狠 |
| "加了分区=查询自动快" | 全表扫谓词不命中分区列时，分区反而因碎片化更慢（§6 变体） |

## 核心概念速览（中英对照）

- **对象存储** — Object Store：S3/ADLS 类扁平 KV 化海量存储；湖仓的地基。
- **分层命名空间** — Hierarchical Namespace：ADLS Gen2 的 HDFS 兼容元数据层 ✅。
- **列式格式** — Columnar Format：Parquet/ORC，按列切块存放与编码。
- **行组** — Row Group：Parquet 内统计与跳过的粒度单元。
- **谓词下推** — Predicate Pushdown：用 footer 统计在读侧跳过数据块（→ 05 章 🔧）。
- **分区裁剪** — Partition Pruning：按谓词只扫命中分区（🔧 §5：5/1887 文件）。
- **小文件税** — Small-file Tax：每文件固定开销随文件数线性叠加（🔧 §6：×5.3）。
- **隐藏分区** — Hidden Partitioning：分区表达式入元数据，查询按其匹配裁剪 ✅ Iceberg。
- **分区演进** — Partition Evolving：改分区方案不动历史数据 ✅ Iceberg。
- **compaction** — 压实：小文件合并成读友好大文件（§7 → 维护册）。

## 最新演进与工业实践

- **布局智能化收敛**：从"人选分区键"到引擎自动聚簇（Delta Liquid Clustering、
  Iceberg 家族 rewrite 策略、各云仓 auto-clustering）；本书 2022 的分区章节在今天
  多数场景已被"少手工分区+托管聚簇"替代 ⚠️ 转述。
- **Vortex/下一代列式格式的探索**：社区对 Parquet 解冻成本的迭代研究持续 ✅
  见各官方仓库动态（iceberg/parquet 生态 <https://iceberg.apache.org/docs/latest/> 关联页）；
  2026 年生产主流仍是 Parquet，本书格式结论未过期。
- **对象存储侧演进**：S3 条件写/清单 V2、ADLS Gen2 软删除与不可变存储等原语增强，
  直接改善了表格式提交协议与合规保留的实现成本 ⚠️ 转述（→ 11 章）。
- **本机可复现口径**：§5/§6 两组数字全部产生于 DuckDB 1.5.5 + 单文件 parquet，
