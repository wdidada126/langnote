## 2. 四段史前史（§1）

```
 1980s-90s          2000s               2010s                2020s
┌──────────┐    ┌───────────┐     ┌────────────┐      ┌──────────────┐
│ 操作型DB │ →  │ 数据仓库  │  →  │  数据湖    │   →  │   数据湖仓   │
│ OLTP/报表│    │ 维度建模  │     │ Hadoop/S3  │      │ 湖的存储 +   │
│ 单一真相 │    │ 星型/雪花 │     │ schema-on- │      │ 仓的ACID/治理│
└──────────┘    └───────────┘     │ read,自由  │      └──────────────┘
     ↑服务报表   ↑服务分析        └────────────┘
                                    ↑服务数据科学家
```

- **操作型数据库**：为事务服务，分析负载一上大屏就拖垮生产库 → 催生"把数据搬出去分析"。
- **数据仓库（数仓）**：Kimball 维度建模 / Inmon CIF 两条路线，主题导向、集成、非易失、随时间变化
  （W-H-Inmon 四特征 ⚠️ 通识转述）。代价：schema 前置、模型变更慢、只装结构化数据。
  对位盘上：[../The_Data_Lakehouse/00-总览与阅读地图.md](../The_Data_Lakehouse/00-总览与阅读地图.md)
  （Inmon 本人把"仓库的集成纪律"带进湖的立场，详见第 4 节）。
- **数据湖**：廉价对象存储 + "先存后想"（schema-on-read）。Hadoop 时代三件套
  HDFS/Hive/HBase，云时代换成 S3/ADLS + 托管 Hive。问题：文件即真相、无 ACID、
  "数据沼泽"——盘上对位 [../bigdata/09-存储与文件格式.md](../bigdata/09-存储与文件格式.md)。
- **湖仓（Lakehouse）**：在湖的对象存储之上加一层**开放表格式**（元数据 + 事务协议 +
  列式文件格式），让 BI 与 ML 直接、一致、可信地读同一份数据。
  ✅ 官方定义口径：Databricks 术语页 <https://www.databricks.com/glossary/data-lakehouse>；
  ✅ Azure 侧同义口径 <https://learn.microsoft.com/en-us/azure/databricks/lakehouse/>。

## 3. 旧模式的结构性痛点（§2）

| 痛点 | 表现 | 湖仓的解法（本书口径 ⚠️） |
| --- | --- | --- |
| 双系统并存 | 湖存原始、仓存建模，两套集群两套技能 | 一份数据两种负载（data science + SQL）✅ glossary 口径 |
| 副本链条 | 源→湖→暂存→仓→集市，每跳一次拷贝 | 分层但**不搬数据**：Bronze/Silver/Gold 同存储介质 |
| 数据沼泽 | 无 ACID、无约束、脏读半写文件 | 表格式提供快照隔离/回滚（→ 02 章 🔧） |
| BI 被排除在湖外 | 报表工具无法直连 Hive 表 | 引擎无关开放接口：Parquet + 元数据规范 |
| 治理与安全割裂 | 仓有 RBAC，湖只有目录权限 | 统一 catalog + 行/列级策略（→ 06/07 章） |
| TCO 失控 | 仓内存全量明细，按压缩行计费 | 明细留湖（对象存储价），仓层只留高价值聚合 |

**Menon 的问题设定（据封底/简介 ✅ 原文照录）**："Propose a new scalable data
architecture paradigm, Data Lakehouse, that addresses the limitations of current
data architecture patterns"——注意他的主语是 **paradigm（范式）**：本书通篇把湖仓
当作**架构模式**来讲（如何摄入、存储、加工、治理、服务、防护），而不是教某一个表格式。
这是它和盘上 Iceberg/Delta/Hudi/Paimon 各"表格式专著"的根本分工差异（→ 00 章书系地图）。

## 4. 四股驱动力（§3，⚠️ 重构自简介 "the drivers"）

1. **云与对象存储成熟**：S3/ADLS 把 PB 级存储的价格打下来，"湖"第一次比"仓的磁盘组"便宜；
   ✅ ADLS Gen2 = 对象存储 + 分层命名空间 POSIX 语义
   <https://learn.microsoft.com/en-us/azure/storage/blobs/data-lake-storage-introduction>。
2. **AI/ML 负载爆发**：特征工程要读原始明细，重灌数仓一轮=几周；数据科学栈（Python/Spark）
   天然长在湖上。对位：[../Advanced_Analytics_with_Spark_2e/00-总览与阅读地图.md](../Advanced_Analytics_with_Spark_2e/00-总览与阅读地图.md)（湖上 ML 负载的教科书样本）。
3. **实时化压力**：批式 T+1 报表 → 分钟级运营决策，流式入湖需求（→ 03 章）。
   对位：[../Introduction_to_Apache_Flink/00-总览与阅读地图.md](../Introduction_to_Apache_Flink/00-总览与阅读地图.md)。
4. **治理合规收紧**：GDPR 时代的访问审计、数据主体删除，湖的"裸文件"状态不可审计。
   对位：[../Data_Governance_Elsevier/00-总览与阅读地图.md](../Data_Governance_Elsevier/00-总览与阅读地图.md)。

## 6. 常见误区

| 误区 | 修正 |
| --- | --- |
| "湖仓 = Databricks 产品" | 湖仓是架构范式；Snowflake/Dremio/纯 Iceberg 栈都是同范式实现（→ 11 章对账） |
| "上了湖仓就有治理" | 治理是独立一层（catalog+策略），表格式只给 ACID 与版本，不给权限（→ 06/07 章） |
| "旧模式已过时，全推倒重来" | Menon 简介明示要理解 "patterns used in the past"：湖仓吸收仓的纪律、湖的自由，多数企业以共存/迁移收场（⚠️ 推定立场） |
| "湖仓消灭 ETL" | 分层建模反而更需要管道纪律（→ 03 章） |
| "数据湖够用了，何必加元数据" | 裸湖上做 UPDATE/回滚/隔离都要手工造轮子——02 章 🔧 演示给出最小语义代价 |

## 核心概念速览（中英对照）

- **数据仓库** — Data Warehouse：面向主题、集成、非易失、随时间变化的分析型存储（Inmon 四特征）。
- **数据湖** — Data Lake：以原始格式廉价存储多形态数据、读时定 schema 的存储库。
- **数据沼泽** — Data Swamp：缺元数据/治理而不可信的湖。
- **湖仓一体** — Data Lakehouse：对象存储 + 开放表格式，让 BI/ML 直同一份可信数据 ✅ glossary 口径。
- **架构范式** — Architectural Paradigm：本书对湖仓的定位——模式而非产品。
- **读时模式** — Schema-on-Read：写入不设约束、查询时解释结构。
- **medallion/分层** — Bronze/Silver/Gold：原始/清洗/服务三层（⚠️ 术语推定引入）。
- **驱动力** — Drivers：云、AI/ML、实时、合规四股（§4）。
- **信息供应链** — Information Supply Chain：Inmon 语境的湖仓前身理论（对位 §5）。
- **TCO** — Total Cost of Ownership：存储分层定价 + 双系统人力成本的综合账。
