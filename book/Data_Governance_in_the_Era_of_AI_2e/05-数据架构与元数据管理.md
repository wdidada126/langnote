## 一、AI 时代的数据架构演进

### 1.1 从数仓到 Lakehouse

| 架构世代 | 代表 | 特征 | 治理挑战 |
|---|---|---|---|
| 传统数仓 | Oracle/SQL Server | Schema-on-write, ETL | 集中治理，相对简单 |
| 数据湖 | S3/ADLS + Spark | Schema-on-read, ELT | 数据沼泽风险 |
| Lakehouse | Databricks/Fabric | 湖+仓融合 | 需统一治理层 |
| 数据编织 | 逻辑层+物理层 | 联邦式访问 | 元数据驱动治理 |
| 数据网格 | 领域自治 | 去中心化 | 联邦治理 + 互操作 |

### 1.2 AI 对架构的新需求 ⚠️ 转述

- **特征存储**（Feature Store）：ML 特征的注册、版本、共享

## 二、元数据管理在 AI 治理中的核心地位

⚠️ 转述

### 2.1 三类元数据

| 类型 | 描述 | AI 场景示例 |
|---|---|---|
| 技术元数据 | Schema、类型、存储位置 | 训练表列定义、模型输入格式 |
| 业务元数据 | 业务含义、所有者、标签 | 特征业务描述、模型用途 |
| 运营元数据 | 执行日志、血缘、性能 | 训练作业日志、推理延迟 |

### 2.2 AI 特有的元数据需求 ⚠️ 转述

传统元数据管理不覆盖：
- **模型卡片**（Model Card）：模型描述、训练数据摘要、性能指标
- **数据表**（Datasheet）：数据集来源、用途、偏见评估
- **特征血缘**：从原始数据到模型特征的完整转换链
- **推理谱系**：输入数据→模型版本→输出结果的可追溯链

## 三、数据血缘（Data Lineage）

⚠️ 转述

### 3.1 血缘的层次

| 层次 | 粒度 | 用途 |
|---|---|---|
| 表级血缘 | 表→表 | 影响分析、ETL 依赖 |
| 列级血缘 | 列→列 | 字段级影响分析 |
| 特征级血缘 | 原始列→特征 | AI 模型可解释性 |
| 模型级血缘 | 数据集→模型→决策 | 合规审计 |

### 3.2 AI 治理对血缘的特殊要求 ⚠️ 转述

1. **端到端可追溯**：从原始数据到模型决策的完整链路
2. **版本感知**：血缘需记录数据/模型的版本变化
3. **双向追踪**：正向（数据→决策）+ 反向（决策→数据）
4. **实时血缘**：流式场景需近实时血缘更新

→ 数据血缘基础详见 [Understanding_Data_Governance Ch06](../Understanding_Data_Governance/06-数据血缘.md) ⚠️ 互链

- 模型使用的所有训练数据集列表
- 每个数据集的来源、许可证、质量指标
- 模型的预训练基础、微调数据来源
- 第三方库与依赖项清单

## 五、🔧 本地演示：DuckDB 数据血缘追踪

> ⚠️ 非本书引擎/平台行为。以下演示使用 DuckDB 类比列级血缘追踪。

```python
import duckdb

con = duckdb.connect()

# 创建简化的血缘追踪表
con.execute('''
CREATE TABLE column_lineage (
    source_table TEXT,
    source_column TEXT,
    target_table TEXT,
    target_column TEXT,
    transform_type TEXT,
    model_id TEXT
);
''')

con.execute('''
INSERT INTO column_lineage VALUES
    ('raw_users', 'age', 'features', 'age_bucket', 'binning', 'fraud-det-v2'),
    ('raw_users', 'income', 'features', 'income_log', 'log_transform', 'fraud-det-v2'),
    ('raw_transactions', 'amount', 'features', 'avg_amount_30d', 'aggregation', 'fraud-det-v2'),
    ('raw_transactions', 'merchant_id', 'features', 'merchant_risk', 'encoding', 'fraud-det-v2'),
    ('features', 'age_bucket', 'model_input', 'feat_0', 'identity', 'fraud-det-v2'),
    ('features', 'income_log', 'model_input', 'feat_1', 'identity', 'fraud-det-v2');
''')

# 反向追踪：给定模型输入特征，追溯到原始数据列
result = con.execute('''
WITH RECURSIVE trace_back AS (
    -- 起点：模型输入特征
    SELECT target_table, target_column, source_table, source_column, transform_type, 1 AS depth
    FROM column_lineage
    WHERE target_table = 'model_input' AND model_id = 'fraud-det-v2'
    UNION ALL
    -- 递归：继续向上追溯
    SELECT cl.source_table, cl.source_column, cl.target_table, cl.target_column, cl.transform_type, tb.depth + 1
    FROM column_lineage cl
    JOIN trace_back tb ON cl.target_table = tb.source_table AND cl.target_column = tb.source_column
    WHERE tb.depth < 5
)
SELECT DISTINCT source_table, source_column, transform_type, depth
FROM trace_back
WHERE source_table LIKE 'raw_%'
ORDER BY source_column;
''').fetchall()

print("fraud-det-v2 特征血缘（反向追溯到原始数据）：")
for r in result:
    print(f"  {r[0]}.{r[1]} → [{r[2]}] (深度:{r[3]})")

con.close()
# 输出:
# fraud-det-v2 特征血缘（反向追溯到原始数据）：
#   raw_transactions.amount → [aggregation] (深度:2)
#   raw_transactions.merchant_id → [encoding] (深度:2)
#   raw_users.age → [binning] (深度:2)
#   raw_users.income → [log_transform] (深度:2)
```

🔧 以上为本地 DuckDB 演示（使用递归 CTE 实现血缘追踪），⚠️ 非本书引擎/平台行为。
