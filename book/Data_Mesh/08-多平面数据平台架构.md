# 第 10 章 The Multiplane Data Platform Architecture（多平面数据平台架构）

> 机工中译第 10 章。小节 ✅ 实抓：Designing a Journey-Driven Platform / The Data Product Developer Journey / The Data Product Consumer Journey / Recap。本章把第 4 章的平台主张落成结构图：平台=多平面 + 两条用户旅程。

## 1. 核心命题：平台按用户旅程切平面，不按技术栈切

传统数据平台按技术分层（存储层/计算层/调度层），结果是没人对"端到端交付一个数据产品"负责。她改按**旅程**驱动设计：平台的能力组织必须镜像两类用户的真实工作流——**数据产品开发者**与**数据产品消费者**。这是"平台即产品"（第 4 章）方法论在本章的具体执行。

## 2. The Data Product Developer Journey（开发者之旅）✅ 小节名，环节 ⚠️ 转述

她描绘产品开发者（域团队工程师）的完整生命周期旅程，平台需在每一环节提供自助能力：
1. **设计**：产品画布（契约先行：用例、接口、SLA 声明）；
2. **脚手架/创建**：模板生成含质量/观测/安全默认值的产品骨架；
3. **开发**：本地与沙箱环境、数据样本、契约测试工具；
4. **部署**：CI/CD 管线、不可变发布、多环境提升；
5. **运行**：托管编排与计算放置（第 9 章嵌入式计算的落点）、SLI 观测；
6. **退役**：下线通知、依赖清理、存档。
- 关键设计原则：**每个旅程环节都有"铺平的路"**（golden path），偏离正路需自担成本——用开发者体验实现第 5 章的多态政策落地。
- 编排环节的机制级参照（⚠️ Dagster 转述未实测）：其软件定义资产（`@asset`）+ 物化（materialize）+ 检查（asset checks）+ 分区回刷几乎逐条对应"创建-部署-运行-质量"旅程；但注意 Dagster 是**单团队视角**的编排器，mesh 要求的是**多团队联邦**的编排契约——跨团队资产依赖需靠接口声明而非代码 import，这正是本书"架构量子独立性"的编排学翻译。选型评估可用 DuckDB 做本地最小复现（🔧 见 [10-数据产品设计-提供消费转换.md](10-数据产品设计-提供消费转换.md) 的契约演示），Dagster 本体本环境未安装。

## 3. The Data Product Consumer Journey（消费者之旅）

与第 3 章五步旅程（发现/理解/信任/探索/组合）对齐，本章补充**平台侧供给**：
- 发现 → 产品目录/市场是平面接口，索引由平台横切收集（不靠人工登记）；
- 理解/信任 → 契约、血缘、质量指标内嵌目录页；
- 探索 → 即席查询沙箱与样本，零审批起步、按敏感级升档；
- 组合 → 多接口形态（SQL/文件/流/API）可达，组合失败时反馈直通提供方 backlog。
- 她强调消费者旅程的度量（转化漏斗：搜索→查看→试用→订阅→复用）是平台与产品双重 KPI——第 7 章"价值/投资比"的操作化。

## 4. 平面结构（⚠️ 按本章与第 9 章雏形重构）

| 平面 | 职责 | 类比 |
|---|---|---|
| 应用平面 Application | 面向消费者的界面（BI/Notebook/市场/开发台） | SaaS 前端 |
| 编排平面 Orchestration | 跨产品的依赖图、SLA 编排、政策关卡 | K8s 控制面 |
| 数据平面计算 Data-plane Compute | 产品级工作负载引擎（批/流/交互） | 容器运行时 |
| 基础设施平面 Infrastructure | 多云资源供给与网络/身份基座 | IaaS/云 |
- 平面间以声明式接口解耦，政策/观测/元数据为横切（crosscutting）注入——该结构后来在 DataHub/OpenMetadata 等开源目录的架构叙事中能看到弱化回声（⚠️ 观察转述）。
- 批判：四平面边界在中小组织里常被一个平台团队兼任，**平面分离的成本随规模阈值出现**——书未给出该阈值，是"mesh 何时不值得"讨论的空白之一（2024–2026 退潮批评常引此点）。

## 开发者体验度量建议（平台运营面 ⚠️ 引申，非书内逐条）

- 时间轴：idea→首个沙箱结果、首次生产发布、契约变更上线的 lead time；
- 阻力面：偏离黄金路径率、工单率（本应自助却人肉）、模板 fork 率（平台不适配信号）；
- 信任面：发布回滚率、SLA 达成可视化覆盖率；
- 网络面：单产品平均消费方数、跨域组合次数（复用进化的北极星）。
与第 4 章 12 项自助清单配对使用：清单测"有没有"，度量测"好不好用"——两者都缺时平台会静默退化为文档站（书内 §4 失败模式的量化监控）。

## 常见疑问（FAQ）

**Q1：两条旅程谁先设计？**
A：开发者旅程（供给侧先通），消费者旅程随后补发现/探索；反过来会建成"有目录无产品"的橱窗——与 15.3 试点次序同构。
**Q2：平台要不要支持全部六种消费接口形态？**
A：按当期产品契约分布裁剪；抽象层留扩展位即可，全量实现是过度平台化（§4 批评"接管一切"的变体）。
**Q3：编排平面与 Airflow/Dagster 这类工具边界在哪？**
A：工具是单点实现；本章的编排平面还要**跨团队依赖契约化 + 政策关卡宿主**两件平台外属性——只有编排器不等于有编排平面（⚠️ Dagster 转述见 §2 注）。
**Q4：四平面要不要四个团队？**
A：不必；平面是关注点非组织单元。小组织一个平台团队分模块兼任，规模化后再裂变（书未处理，属合理延伸 ⚠️）。
**Q5：目录是不是可以外购？**
A：目录的"索引与界面"可购，"元数据发射义务+关卡政策"不可购——外购目录+自建发射规范是唯一可持续组合（行业实践共识 ⚠️）。
**Q6：本章和第 4 章到底谁读谁？**
A：顺序读第 4（为什么建），精读本章（建成什么样）；两章合并阅读约 40 页，冗余主要在"平台即产品"的动机复述——赶时间可只读本文件 §2–§4 三表。

## 核心概念速览（中英对照）

- **旅程驱动平台设计** — Journey-driven Platform Design：以开发者/消费者工作流组织结构，替代技术栈分层。
- **产品画布** — Data Product Canvas：契约先行的产品设计工件。
- **开发者之旅** — Developer Journey：设计-脚手架-开发-部署-运行-退役六环。
- **消费者之旅** — Consumer Journey：发现-理解-信任-探索-组合五环（第 3 章定义、本章平台化）。
- **黄金路径** — Golden Path / Paved Road：默认合规且阻力最小的开发通道。
- **应用平面** — Application Plane：消费者与开发者的界面层。
- **编排平面** — Orchestration Plane：跨产品依赖与关卡的协调层。
- **数据平面计算** — Data-plane Compute：产品自带的引擎工作负载。
- **横切关注点** — Crosscutting Concerns：身份、政策、观测、元数据的全平面注入。
- **消费漏斗度量** — Consumption Funnel：目录转化的平台级 KPI。
- **联邦编排契约** — Federated Orchestration Contract：跨团队依赖以声明接口而非代码耦合表达。
- **规模阈值问题** — Scale Threshold Critique：平面分离成本收益拐点（书未量化的空白）。

## 最新演进与工业实践

- **资产导向编排扩散（2023–2026）**：Dagster（assets）、dlt、Airflow 的 Dataset 抽象相继把"编排对象=数据资产/产品"变为主流默认，本章"以产品为单元编排"的判断已被工具链验证（⚠️ 文档转述，各库行为未本机实测）。
- **目录与关卡商品化**：Unity Catalog（含 Glossary/Tags/Lineage 与开放 Iceberg REST）、Snowflake Horizon、OpenMetadata/DataHub 家族在承接"发现平面 + 政策关卡"；2024 后 catalog 之争实质是谁成为多平面平台的控制面（⚠️ 竞争转述；云仓类一律不作实测声明）。
- **平台工程的组织吸收**：IDP 团队（Backstage 等）把"开发者之旅"做成门户模板产品，数据产品旅程成为其垂直场景模板——本章方法论溢出到通用平台工程（⚠️ 观察转述）。
- **2025–2026 现状口径**："data platform as a product" 已是行业通用语，其概念股权可追溯至本书第 4+10 章；但实践中平台收敛为"湖仓 + 目录 + 契约 CI"三件套，四平面完整自建者仍属少数（与"原则拆件落地"一致，见 [01-DataMesh速览.md](01-DataMesh速览.md) 演进节）。
- 反向对照：编排平面的中心化风险（谁拥有编排面谁实质上复辟中心化）是与 [大数据之路](../大数据之路.md) 中台架构共享的结构性问题，两系笔记互读时留意。
