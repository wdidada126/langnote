# 第 9 章 The Logical Architecture（逻辑架构）

> Part III 首章，机工中译第 9 章。小节 ✅ 实抓：Domain-Oriented Analytical Data Sharing Interfaces / Data Product as an Architecture Quantum / The Multiplane Data Platform / Embedded Compute Strategies（中文版 9.4「嵌入式计算策略」）/ Recap。本章是全书架构重心：把四原则翻译成一个逻辑参考架构。

## 1. 本章定位：逻辑架构 ≠ 参考实现

Dehghani 刻意给的是**逻辑架构**（各关注点如何解耦、接口长什么样），拒绝给物理蓝图（"用什么云产品"），并声明物理形态因组织/成本/合规而异。这与她 2020 文的逻辑架构图一脉相承（✅ 该文含同一图：四原则各推出一个逻辑视图——domain-oriented data and compute / data product as the architectural quantum / multi-plane data platform / computational policies embedded in the mesh）。

## 2. Domain-Oriented Analytical Data Sharing Interfaces（领域导向的共享接口）

- 核心句：**接口先于实现**。域与域之间只通过声明式数据共享接口相遇（批数据集、流主题、API、文件……多种形态并存），不存在"直连别域的库"这种隐式耦合。
- 三类接口参与方：提供方（承诺契约）/ 消费方（声明假设）/ 平台（保证契约可被机器验证与执行）。
- 反直觉点：共享接口**不要求**先有全局统一语义模型——她反对"先企业级本体再共享"的传统路线（这是与经典数据治理/主数据管理的正面决裂），改为"接口级兼容性 + 组合时局部适配"（适配以消费者驱动的转换产品承担，呼应第 2 章防腐层）。
- 与本系列互文：接口即契约的演化理论见 [设计数据密集型应用](../设计数据密集型应用/04-编码与演化.md)（4 章：模式演化/兼容性，集中式 schema 治理的微观替代方案）；接口协议（Iceberg/Parquet/REST 等）的物理选型见 [Practical_Lakehouse_Architecture](../Practical_Lakehouse_Architecture/03-存储湖仓架构的核心.md)。

## 3. Data Product as an Architecture Quantum（数据产品=架构量子）——本章原创概念

- "量子"借自物理：**不可再分的最小独立单元**。数据产品是数据域中可独立部署、独立运行、独立演化、可组合的最小单元——比"表"大（表无契约无团队）、比"域平台"小（平台不是交付物）。
- 她的量子三特征（⚠️ 按论述重构）：**独立性**（生命周期自治，运行时自包含）、**边界性**（ports/adapters 界定，内部实现对外不可见）、**组合性**（量子互联形成 mesh，价值在网络组合处涌现）。
- 数据产品类型学在本节定型：
  1. **source-aligned**（源对齐：域的第一方产品）；
  2. **standard / consumer-aligned**（标准/消费者对齐：跨域聚合适配）；
  3. **analytical / experimental**（分析/实验型：为特定用例派生）。
  这套三分被 #200《Implementing Data Mesh》系实现文献扩成九类类型学（⚠️ 待其落盘核对），本书版本只给这三类——辨析：引用"数据产品 N 分类"时先核对出处是本三分类还是他书扩编。
- 架构量子概念是本书对工程词汇表最独特的输出；2023 后社区批评也集中于此：**什么算"独立"没有判定标准**，粒度可无限细分导致产品目录爆炸。

## 4. The Multiplane Data Platform（多平面数据平台：雏形）

- 本章给出平台分层雏形（第 10 章全展开）：应用平面（消费者工具与产品界面）、编排平面（跨产品的工作流与依赖）、基础设施平面（资源供给）、**数据平面计算**（产品自带的转换与服务逻辑）。
- 关键纪律：**关注点分离即治理面**——策略注入在各平面交界的"关卡"（gate）上，而非产品内部代码里（直通第 5 章计算治理与第 14 章观测）。

## 5. Embedded Compute Strategies（嵌入式计算策略）

- 反"中央计算集群包打天下"：计算随数据产品走（产品自带批/流/交互引擎选型），中央平台只提供联邦式的**计算能力目录与放置策略**（按成本/延迟/合规把工件调度到合适引擎）。
- 与 [The_Data_Lakehouse](../The_Data_Lakehouse/00-总览与阅读地图.md) 的"引擎中立、表为中心"论调互补：lakehouse 使"计算随数据走"在物理上可行（开放表格式 + 多引擎），mesh 在其上规定"选择权归域"。

## 架构量子判定表（操作化 ⚠️ 由 §3 三特征归纳）

| 判定问题 | 是→ | 否→ |
|---|---|---|
| 能否独立部署（不协调他方发布）？ | 候选量子 | 只是组件（并入父产品） |
| 有独立契约与版本线？ | 候选量子 | 物化视图/索引（非产品） |
| 有 owner 团队与预算？ | 量子成立 | 伪量子（资源而非产品） |
| 能被他域独立发现消费？ | 量子成立 | 内部实现细节 |
| 粒度：删掉它，网络组合面是否缩小？ | 保留 | 合并候选 |
五问过三即"表级产品化"风险，过五即"域级巨石"风险——粒度辩论的可执行版本。

## 常见疑问（FAQ）

**Q1：逻辑架构图能直接当采购需求书吗？**
A：不能。接口形态（批/流/API）与平面划分可映射到产品类目，但"量子/关卡"无对应 SKU；把 mesh 当采购清单是本领域最常见误用。
**Q2：接口与契约什么关系？**
A：接口是形（怎么取），契约是诺（取到算什么承诺）；同接口可挂不同契约（同一 SQL 端点不同 SLA），第 3 章契约要素表是其展开。
**Q3："架构量子"有没有物理学之外的先例？**
A：微服务文献的"最小可部署单元"与 Actor 模型消息隔离是近亲；她加了**组合性**（量子互联成网络）以别于服务拆分。
**Q4：嵌入式计算会不会成本失控？**
A：会——所以 §5 强调中央"计算能力目录 + 放置策略"与第 16 章成本归因；失控的 N 个小集群是 mesh 变体的常见死法（实践共识 ⚠️）。
**Q5：四平面与 OSI 分层什么关系？**
A：无关系。OSI 是通信协议栈，四平面是**责任/关注点**切分（旅程 × 关卡宿主），类比止于"正交分层"一词。
**Q6："量子"和"微服务"到底差在哪？**
A：微服务的单元是**进程**（请求-响应），量子的单元是**资产+契约+团队责任**（数据可长期静止仍是产品，进程停而数据承诺仍在）；把量子当"数据的微服务"会丢掉组合性与生命周期面——这是本书架构学最易被读丢的一格。
**Q7：接口不统一（批/流/API 并存）消费者怎么编程？**
A：不要求统一接口，要求统一的**契约描述语言**（目录层元模型）——消费者按承诺检索、按接口适配；统一描述而非统一传输，正是"边界标准化、实现多元"的落地（与 2024-12《Designing data products》的接口表同构 ✅）。

## 核心概念速览（中英对照）

- **逻辑架构** — Logical Architecture：关注点解耦与接口定义蓝图，不指定物理技术。
- **架构量子** — Architecture Quantum：数据域中不可再分的独立可部署单元=数据产品。
- **数据共享接口** — Data Sharing Interface：域间唯一合法相遇面（批/流/API 多形态）。
- **源对齐产品** — Source-aligned Data Product：产生域持有的第一方权威数据产品。
- **标准/消费者对齐产品** — Standard / Consumer-aligned Data Product：跨域聚合与适配产品。
- **防腐层** — Anti-Corruption Layer：消费侧语义隔离模式（DDD 移植）。
- **计算随数据走** — Embedded Compute：产品自带引擎选型权，中央仅供给与放置。
- **多平面平台** — Multiplane Platform：应用/编排/基础设施/数据计算四平面雏形。
- **关卡式治理** — Gate-based Governance：策略注入平面交界而非产品内部。
- **组合性** — Composability：价值在接口互联网络处涌现的设计前提。
- **粒度失控** — Granularity Failure：量子定义欠精确引发的目录爆炸（后发批评）。
- **全局本体路线批判** — Against Global Ontology First：接口兼容替代企业级统一模型。

## 最新演进与工业实践

- **粒度问题的工程答案（2023–2026）**：实践中以"用例簇 + 可部署性"双约束定粒度，数据产品规模从几十到几百之间是存活样本常见区间（⚠️ 社区经验转述，无统计口径）。
- **架构量子与"数据产品即软件构件"**：2024 后出现以 Terraform/Helm 式打包分发数据产品的实践（产品含 infra 定义 + 契约 + 代码 + 元数据），与本书"接口先于实现"契合（⚠️ 生态转述；概念对表 IDP 见 [04-自助数据平台原则.md](04-自助数据平台原则.md)）。
- **逻辑架构的官方后继文本**：martinfowler.com《Designing data products》（2024-12-10，✅ https://martinfowler.com/articles/designing-data-products.html ）把本章"接口"层推进到字段级设计清单，可视为本书第 9+11–14 章的合并更新版。
- **平台对撞**（2024–2026）：Lakehouse/warehouse 双巨头路线（Databricks Unity Catalog vs Snowflake Horizon）在争"目录与治理关卡"的宿主层——恰是本章"平面交界关卡"的商品化战场（⚠️ 竞争格局转述，云仓不可本机实测，不做行为断言）。
