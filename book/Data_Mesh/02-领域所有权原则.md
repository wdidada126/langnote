# 第 2 章 Principle of Domain Ownership（领域所有权原则）

> 机工中译第 2 章。小节 ✅ 实抓：A Brief Background on Domain-Driven Design / Applying DDD's Strategic Design to Data / Domain Data Archetypes / Transition to Domain Ownership / Recap。

## 1. 原则陈述与位置

四原则中的第一原则：**数据的所有权归产生它的业务领域**（source-aligned domain），而非中央数据团队。本章用三节铺垫（DDD 简史 → 战略设计迁移到数据 → 领域数据的原型分类），一节落地（如何过渡）。理解本章的钥匙是：这不是"技术重构指南"，而是**责任再分配的政治经济学**——把"数据是谁的活"这个问题重新回答。

## 2. DDD 速览（本节按原书思路重构 ⚠️ 转述）

- 战术 DDD（实体/值对象/聚合）不是本章重点；重点是 Eric Evans 的**战略设计**：subdomain（核心域/支撑域/通用域）、bounded context（语义边界，同一个"customer"词在不同上下文可以不同义）、context mapping（上下文之间的合作关系：共享内核、防腐层、客户-供应商等）。
- Dehghani 的迁移命题：**分析型数据世界同样存在语义边界**。营销中心与风控中心的"交易"字段同名不同义，强行进一个全局模型就产生她所说的"语义债务"。bounded context 提供切分所有权的成熟语言。
- 与本系列的连接：微服务拆分逻辑在 [设计数据密集型应用](../设计数据密集型应用/00-总览与阅读地图.md) 的语境是分区/复制的分布式机制；mesh 把"拆分"的动因从性能改为**认知负荷与责任**——同一手法，不同目的。

## 3. Applying DDD's Strategic Design to Data

- **领域识别**：以业务能力（capability）而非数据对象划分域；域再分 subdomain，核心域优先建设数据产品。
- **数据子域类型**（⚠️ 转述其分类法）：领域可拥有 *source-aligned*（源对齐，域既是数据产生者也是第一责任人）与 *consumer-aligned*（消费者对齐，为下游用例组合跨域数据）两种角色——前者是所有权主体，后者是网络中的组合节点。
- **Context Map 数据化**：域间数据关系沿用 context mapping 词汇：共享内核（跨域基础数据产品）、防腐层（消费他域数据时做语义转换的适配产品）、开放主机服务（以标准接口发布数据产品）。这套词汇后来被 #200 那类实现书吸收为"数据产品依赖图"（⚠️ 待其落盘核对）。
- **谁承担所有权**：域内的"数据产品团队"（跨职能：域专家 + 数据工程师 + 分析师/ML 工程师），而非外包给数据平台的托管服务。

## 4. Domain Data Archetypes（领域数据原型）✅ 目录实抓

本节给出按业务域的数据分类原型（⚠️ 细节转述）：
1. **Passive domain（被动域）**：只消费、不产出独立数据产品；
2. **Active domain（主动域）**：产出数据产品但互操作有限；
3. **Structured / Product-driven domain（结构化/产品驱动域）**：按产品方法系统化生产互操作数据产品。
进阶路线 passive → active → product-driven 被用于第 15 章成熟度评估。另按数据来源分 **source-aligned / aggregator（consumer-aligned）/ legacy-aligned** 三类数据产品——即第 9 章"架构量子"讨论的产品类型学的前身。注意：这套三分与 Kimball 总线架构中"业务过程总线矩阵"解决的问题（跨过程一致性）不同轴：Kimball 按过程建事实模型，mesh 按**所有权**切责任——与 [The_Data_Lakehouse](../The_Data_Lakehouse/00-总览与阅读地图.md) 及 Inmon [#169《Building the Data Warehouse》](../Building_the_Data_Warehouse/00-总览与阅读地图.md)（已落盘，波尾闭环）对照读，正是"建模轴 vs 组织轴"的分水岭。

## 5. Transition to Domain Ownership（过渡）

- 原书反对"一次性组织重组式"切换，主张以**试点域**（选核心域 + 有痛感用例 + 有域专家愿意接）先跑通所有权闭环，再复制。
- 过渡清单（⚠️ 重构）：为域建数据能力（人/技能/激励）→ 划数据边界 → 从"帮中心团队供数"改为"为自己域的数据产品负责"→ 中心团队转型为平台与赋能角色。
- 康威定律的工程含义：先改团队职责边界，架构边界才会跟上；"只改工具不改组织"被她列为伪 mesh 的第一大形态。
- 现实摩擦（书承认 + 社区验证）：多数公司**找不到**愿意且能够持有数据产品的域团队——数据工程人才密度远低于软件工程师，这正是 2024–2026 批评"下放变弃养"的根源，见本章末"最新演进"。

## 6. 概念辨析

- 领域所有权 ≠ 数据不出域：她明确要求分析型数据要可被网络内发现与组合，所有权指**责任**不是**领土封锁**。
- 领域所有权 ≠ 部门数据孤岛（silo）的正当化：孤岛是无契约的私有数据；域所有权是以产品契约向全组织暴露数据，语义上相反。批评者认为实践中二者难以肉眼区分，这条防线完全依赖第 5 章治理与第 3 章产品契约的兑现。

## Context Mapping 模式在数据域的移植表（⚠️ 按 DDD 原典 + 本章论述重构）

| DDD 上下文关系 | 数据域对应做法 | 何时用 |
|---|---|---|
| Partnership | 两域共担一个跨域用例的契约演进节奏 | 核心业务联动（如订单×库存） |
| Shared Kernel | 跨域共享的基础参考数据产品（双方变更需同步发布） | 主键/编码规范/组织维度 |
| Customer-Supplier | 上游域按下游承诺排期供数 | 强依赖、可协商 |
| Conformist | 下游无条件接受上游契约（无议价能力） | 监管数据、外部源 |
| Anti-Corruption Layer（ACL） | 消费者对齐产品承担语义翻译，隔离上游模型 | 上游模型不适配分析用例时的默认解 |
| Open Host Service | 域以标准多形态接口公开数据产品 | 想被广泛复用的核心域 |
本表帮助把第 9 章"接口先于实现"落到关系类型学：mesh 只要求**每条依赖被显式归类**，不要求统一模式。

## 所有权判定的操作问题清单（⚠️ 由本章+第 15 章评估框架归纳）

1. 该数据的**业务事实**由哪个域的决策改变？（谁改流程谁拥有）
2. 语义争议（同名异义/同义异名）由谁裁决并记录？
3. schema 演进的破坏成本由谁承担？契约变更的沟通义务在谁？
4. 质量事故的消费方影响由谁值班响应？
5. 退役决策（停止供数）由谁批准、给多长窗口？
6. 成本账单（存储/计算）归到谁的预算？
6 条中任何一条回答不出，该域就还没准备好接所有权——此即 15.1 "是否采用"判据在单产品尺度的应用。

## 常见疑问（FAQ）

**Q1：领域所有权会不会造成数据孤岛复辟？**
A：书内答案：契约 + 默认可发现性把"私有"变"公开责任"（§6）；批评者答案：实践中界限靠治理兑现，治理弱则孤岛化——两说并存，见 [05-联邦计算治理原则.md](05-联邦计算治理原则.md) 演进节。

**Q2：小域没有数据工程能力怎么办？**
A：书内主张平台摊薄 + 使能团队过渡；2024–2026 的主流修补是"托管式自治"（见"最新演进"），原教旨视之为复辟。

**Q3：域边界划错了多可怕？**
A：与微服务同病：边界错误以契约破坏为代价缓慢修正；共享语义锚点（第 13 章）与产品退役机制是两条纠错通道。DDD 战略设计功底的欠缺会被放大。

**Q4：源系统和数据产品团队冲突时谁让步？**
A：本书立场：分析型数据产品是源域团队职责的**扩展**，不是对源系统团队（运营侧）的接管；operational 与 analytical 两套接口在 2020 原文双平面论中已分（✅）。

**Q5：和主数据管理（MDM）什么关系？**
A：不建全局主数据，而用"共享内核型参考数据产品"局部替代——这是与经典治理谱系最大的分歧点之一（对照 [数据架构之道](../数据架构之道.md) 的 MDM 处理）。

## 核心概念速览（中英对照）

- **领域所有权** — Domain Ownership / Domain-oriented Decentralized Data Ownership：数据责任归产生域。
- **有界上下文** — Bounded Context：DDD 语义边界概念，mesh 切分数据所有权的基本刀法。
- **子域** — Subdomain：核心域/支撑域/通用域；决定数据产品建设优先级。
- **上下文映射** — Context Map：域间协作模式词汇（共享内核/防腐层/开放主机服务）移植到数据域。
- **源对齐数据产品** — Source-aligned Data Product：由产生数据的域持有的第一方产品。
- **消费者对齐数据产品** — Consumer-aligned Data Product：为下游用例聚合跨域数据的产品。
- **遗留对齐** — Legacy-aligned：为未现代化系统包装出的过渡产品。
- **被动/主动/产品驱动域** — Passive / Active / Product-driven Domain：域的数据成熟度原型。
- **认知负荷** — Cognitive Load：以团队可承受知识半径定域大小，源自 Team Topologies 语境。
- **数据语义债务** — Semantic Debt：全局单模型压制多语义造成的错位累积。
- **伪 mesh** — Pseudo Mesh：只切分不产品化、或只上工具不改组织名的假改造。
- **试点域** — Pilot Domain：所有权过渡的最小验证单元。
- **康威定律** — Conway's Law：组织结构决定系统结构的迁移依据。

## 最新演进与工业实践

- **Team Topologies 合流**：本书出版后，"enabling team / platform team 三角"与 mesh 角色模型的融合成为落地标配（Manuel Pais 即为本书作序推荐人之一，✅ 影印版页推荐语实抓）；2024 年后平台工程基金会（PPF）的 Platform Engineering 叙事吸收了这一角色表（⚠️ 转述）。
- **所有权退潮实证（2024–2026）**：多起公开复盘（企业数据会议演讲与博客，⚠️ 无稳定 DOI 文献）报告"域团队数据能力缺口"是 mesh 停滞首因；主流修正方案是**托管式自治**（managed autonomy）：中央数据工程虚拟团队代行生产，责任账本仍记在域——被原教旨批评为"新中心化"。此辩论即集中式 vs 去中心化对话的当代形态，与 [Building_the_Data_Warehouse](../Building_the_Data_Warehouse/00-总览与阅读地图.md)（Inmon #169，同波已落盘）笔记中"中央架构 vs 领域演进"之争同构。
- **Iceberg 多写者现实**（2024–2026）：开放表格式成熟后，"多域共写一张表"从不可能变为需治理的常规（catalog 层分支/冲突管理），给"源对齐产品"提供了此前缺失的技术底座（与 [Apache_Iceberg活用入門](../Apache_Iceberg活用入門/)、[Delta_Lake_Definitive_Guide](../Delta_Lake_Definitive_Guide/) 目录版可互查；本行仅登记为系列内互链候选，落盘自检确认目标存在）。
- **中文语境**：《Data Mesh 权威指南》（机工 2023）流通后，"数据领域负责制"常见于国内数据资产入表与数据要素讨论，但多与 mesh 原义脱钩成管理口号（⚠️ 观察性转述）。
