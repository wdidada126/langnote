# 第 14 章 头文件

> **本章地图**：`include/` 目录树（`linux/`、`asm-i386/`、`sys/`、`std/`）与 `-I` 搜索顺序 → 「内联函数 + 宏」是 0.11 实现小体积的唯一手段（`static inline`、`extern inline`）→ `asm-i386/system.h` / `io.h` 的裸汇编入口 → 与 glibc 头文件的冲突与「两套 libc」的处理。核心结论：0.11 头文件是**编译器扩展的集大成者**（`__attribute__`、内联汇编、结构体打包、手工展开循环），它解释了为什么这本书要单独用一章来讲「看起来只是声明」的文件。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |

| 14.2 数据结构集中声明 | `sched.h`、`fs.h`、`mm.h`、`kernel.h` 定义全部核心结构体 | 头文件即「内核的架构决策文档」 |

## 核心精讲

> 以下均为**教学示意，不代表可编译运行**。

### 14.1 `include/` 目录树与 `-I` 顺序

```text
include/
├── linux/          内核核心定义
│   ├── config.h    （由编译期生成，包含 CPU 类型等宏）
│   ├── sched.h     struct task_struct / init_task
│   ├── fs.h        struct m_inode / buffer_head / dir_entry
│   ├── mm.h        mm_segment_t
│   ├── kernel.h    内核信息、printk 原型
│   ├── errno.h     -EACCES / -ENOENT ...
│   ├── tty.h       struct tty_struct
│   ├── time.h      struct timeval / timezone
│   └── ...
├── asm-i386/       平台相关（编译内核时用 -I 指向它）
│   ├── system.h    cli/sti/lgdt/ltr/... 全是裸指令或 inline asm
│   ├── io.h        outb/inb/inl/outl
│   ├── segment.h   TI_SEG / SEGMENT 描述符选择器
│   └── linker.h    连接器脚本符号（_text/_etext/_end）
├── sys/            wait.h / stat.h / types.h / resource.h
└── std/            stddef.h / stdarg.h / defines.h ...
```

- 编译内核时 `Makefile` 用 `-Iinclude -Iinclude/linux -Iinclude/asm` 之类的顺序，把 `asm/` 解析到 `asm-i386/`；这已经具备现代内核 **`scripts/headers` + UAPI 过滤** 的雏形。
- 🔧 现代内核把头文件分成三层：
  - `include/uapi/`（或 `*_uapi/*.h`）——**用户空间可见**的内核接口，只能包含纯 C 声明与常量；
  - `include/`（内核内部）——可以包含结构体、内联函数、宏；
  - `include/net/`、`include/drm/`、`include/linux/` 等子系统私有头。
  - 由 `scripts/headers-install.sh` 负责把 `uapi` 子集安装到 `usr/include`，并对「内核私有的宏泄漏给用户」做检查（`header-test` 工具）。

### 14.2 内联函数：0.11 的「轻量库」

```c
/* include/linux/kernel.h（0.11 形态的示意）—— 教学示意，不代表可编译运行 */
#define asmlinkage __attribute__((regparm(0)))
#define NORETURN __attribute__((noreturn))
#define _PACKED __attribute__((packed))
#define _ALIGNED(a) __attribute__((aligned(a)))
#define __inline extern inline
#define ALIGN(x,a)  (((x) + (a) - 1) & ~((a) - 1))

static inline void * ALIGNED(16) foo(void) { ... }
```

关键点：

- `asmlinkage`（`regparm(0)`）让**系统调用进出不传寄存器参数**——这是 x86 32 位 ABI 的历史包袱，今天内核里是 `asmlinkage` + `#include <asm/syscall.h>`。
- `_PACKED` 用 `__attribute__((packed))` 消除结构体填充，让 `dir_entry` 之类**必须精确对应盘上布局**的结构与磁盘字节对齐。
- 🔧 现代的对应物：`__packed`、`__aligned()`、`__cacheline_aligned_in_smp`、`__always_inline`、`noinline`。

### 14.3 平台相关的裸汇编（`system.h` / `io.h`）

```c
/* include/asm-i386/io.h —— 教学示意，不代表可编译运行 */
#define outb(value, port) \
__asm__ ("outb %%al, %%port"::"a" (_value), "d" (_port))

static inline unsigned char inb(unsigned short _port)
{
    unsigned char _v;
    __asm__ volatile ("inb %%dx, %%al":"=a" (_v):"d" (_port));
    return _v;
}
```

```c
/* include/asm-i386/system.h —— 教学示意，不代表可编译运行 */
#define cli() __asm__ ("cli")
#define sti() __asm__ ("sti")
#define iret() __asm__ ("iret")
#define nop() __asm__ ("nop")

static inline void ltr(unsigned short _sel) { ... }
static inline void lgdt(void *_gdt) { ... }
static inline void flush_tlb(void) { ... }
static inline void return_from_sys_call(unsigned long _eax)
{ __asm__("cmpl $0, %%esp ...") }
```

- 这些头文件实际上就是**内核最小的「机器描述」**；换一个架构（arm、riscv）只要换 `asm-<arch>/` 这一层，`linux/` 下的头几乎不动。
- `return_from_sys_call` 是内联汇编里最著名的一段：它在返回用户态之前检查 `need_resched`，顺手做任务切换。
- 🔧 现代内核把这类代码集中到 `arch/x86/include/asm/`，并且大量使用 `uaccess` 说明符、屏障 macro（`barrier()`、`smp_rmb()`）、以及 `asm("" ::: "memory")` 的形式化约束。

### 14.4 常量、位域与 `__attribute__((aligned))`

```c
/* include/linux/config.h（0.11 由编译生成）—— 教学示意，不代表可编译运行 */
#define NR_OPEN 20
#define NR_INODE 32
#define NR_FILE 64
#define NR_SUPER 8
#define NR_TASK 64
#define NR_REQUEST 32
```

- 「调参」原本靠 `Makefile` 的 `EXTRAVERSION`/`CPPFLAGS` 或配置头文件，今天变成 **Kconfig** 里的 `int` 类型选项，功能等价但可验证。
- 🔧 现代对照：`CONFIG_NR_OPEN`、`CONFIG_NR_FILES`、`CONFIG_NR_CPUS`、`CONFIG_HZ`，以及 `NR_CPUS` 与 `CONFIG_MAXSMP` 的关系。

### 14.5 编译期断言与「头文件的现代职责」

```c
/* 教学示意，不代表可编译运行 —— 现代内核风格 */
#define __BUILD_BUG_ON_ZERO(e) ((int)(sizeof(struct { int:-!!(e);; })))
#define BUILD_BUG_ON(cond) __BUILD_BUG_ON_ZERO(cond)

/* UAPI 头里最常见的写法（真实存在于 include/uapi/linux/types.h） */
typedef struct { __u32 counter; } atomic_t;   /* 不能用锁、不能用 copy_to_user */

/* 常见标注（现代 kernel.h / compiler.h） */
#define __init      __section(.init.text)
#define __exit      __section(.exit.text)
#define __must_check __attribute__((warn_unused_result))
#define __maybe_unused __attribute__((unused))
#define __force     __attribute__((force))
```

- `BUILD_BUG_ON` 把「结构体与盘上格式不一致」这类错误从**运行期异常**提前到**编译期报错**，这是头文件职责的质变。
- 🔧 现代编译器标注全集见 `include/linux/compiler*.h`：`__always_inline`、`__noinline`、`__must_check`、`__maybe_unused`、`__attribute__((format(printf,1,2)))` 等；判断编译器能力则靠 `include/linux/compiler-gcc.h` / `compiler-clang.h` 里的 `__has_attribute()` 与版本宏。

### 14.6 与 glibc 的关系

- 内核**不使用 glibc 的头文件**，自己实现了 `memcpy`/`strcpy`/`sprintf` 等（见 `15-库文件.md`）。
- 但 `include/string.h` 里用 `static inline` 定义了 `memcpy`，如果链接用户的程序就会出现「同一个符号两套定义」——0.11 的 `tools/build.c` 与 `Makefile` 就是在这条边界上做取舍。
- 🔧 现代内核里这些「.userspace 也能看到的函数」被明确区分：`include/linux/string.h`（内核实现）、`include/uapi/...`（用户可见常量），而 `scripts/headerdevcheck` 负责拦截泄漏。

## 版本演进

| 时间 | 事件 |
| --- | --- |
| 1991–1994 | 0.11：`include/` 只有 4 个子树，靠 `-I` 顺序切换平台头 |
| 1996 前后 | 2.0：头文件随源码树一起发展；`include/asm-generic/` 开始出现，减少重复 |
| 2003 | `include/linux/autoconf.h` 由 Kbuild 生成，`linux/config.h` 的包含关系定型 |
| 2008 前后 | **UAPI 分离**正式化：`include/uapi/` 让用户空间只依赖稳定的内核接口子集 |
| 2008 | `BUILD_BUG_ON` 普及；`compiler.h` 统一封装 `likely/unlikely`、`__force` 等标注 |
| 2010–2014 | `checkpatch` 与 `sparse` 成为合并流程的常驻门槛；`coccinelle` 用于批量语义改写 |
| 2015–2026 | `include/linux/compiler*.h` 全面接受 GCC/Clang 差异；`include/linux/minmax.h`、`err.h`、`bits.h` 等小工具头被拆分出来；`Documentation/process/coding-style.rst` 成为事实标准 |

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：头文件层面的工作集中在 **减少编译时间**（`-Wno-...`、前向声明、`include/linux/head.h` 拆分）、**提高类型安全**（`sparse` 的 `address-space` 标注、`__user/__kernel` 区分）、**自动生成 uapi 文档**（`kernel-doc` 从注释生成 ABI 文档），以及 **Rust 与 C 头文件互操作**（`bindgen` 生成 `bindings_generated.rs`）。
- **工业界开源**（star 数 2026-09 实测）：
  - `torvalds/linux`（≈**250k★**）：头文件的权威来源，`include/uapi/` 与 `include/linux/compiler*.h` 是必读；`Documentation/process/` 里有 style 与补丁规范。
  - `llvm/llvm-project`（≈**40.7k★**）：Clang 对 `__attribute__` 与 `__has_attribute` 的实现，内核的 `compiler-clang.h` 依赖它。
  - `gcc-mirror/gcc`（≈**11.3k★**）：GCC 扩展（`__attribute__`、`asm goto`）的定义者，本书所有内联汇编语法都源自 GCC。
  - `torvalds/linux` 之外的对照：`kernel.org` 的 `scripts/` 目录（由 `torvalds/linux` 仓库提供）里的 `header_install`、`checkpatch.pl`、`sparse` 配置。

## 常见误区与本书需修正之处

| # | 误区 / 本书局限 | 2026 年的修正与补充 |
| --- | --- | --- |
| 1 | 「头文件只是声明，没有逻辑」 | 0.11 的 `system.h`/`io.h` 里全是可执行代码；现代头文件甚至包含**编译期断言** |
| 2 | 「平台头靠 `-I` 顺序就够了」 | 🔧 现在用 `include/asm-generic/` + `scripts/headers` 做**统一的 UAPI 导出**，避免「每个架构一份 uapi」 |
| 3 | 「`static inline` 是为了快」 | 0.11 里它同时是「**不用 libc 的实现手段**」；今天 `static always_inline` 更多是控制代码生成 |
| 4 | 「量大小由 config.h 手动改」 | 🔧 由 Kconfig 生成 `autoconf.h`，并提供 `menuconfig` 界面与依赖校验 |
| 5 | 「结构体 packing 用 `#pragma pack`」 | 🔧 内核明确**不用** `#pragma once` 与 `#pragma pack`，只用 `__attribute__((packed))`，保证 GCC/Clang 行为一致 |
| 6 | 「头文件里的宏随便写」 | 🔧 有编码规范：`BUILD_BUG_ON` 类型检查、`checkpatch` 限制行宽与命名、`sparse` 检查地址空间 |
| 7 | 「用户态程序可以直接包含内核头」 | 🔧 必须只包含 `include/uapi/` 子集；否则会出现 ABI 不一致与宏泄漏（历史上多次出错） |
| 8 | 「只支持 GCC」 | 🔧 内核同时支持 Clang（`-Werror` 特化、`compiler-clang.h`），且逐步接受 rustc 参与编译 |
