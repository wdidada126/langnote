# 第 16 章 建造工具

> **本章地图**：顶层 `Makefile` 的 `CFLAGS`/`LDFLAGS`/`HEADS` 变量 → 各子目录 `Makefile` 的「按目录递归编译」→ `boot/` 的 16 位汇编（`as86`/`ld86` 与 `bootsect.s`/`setup.s`/`head.s`）→ **`tools/build.c` 把 bootsect+setup+system 拼成 Image** → 内核自带的 `Documentation/` 说明文档。核心结论：0.11 的建造体系是「**一个普通 Makefile + 一个 600 行的 C 小程序**」，它几乎没有任何抽象，却完整描述了「引导扇区 + 实模式代码 + 保护模式内核」三段式镜像的构建方法——现代 Kbuild 只是把它系统化。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 16.1 顶层 `Makefile` | `CFLAGS`、`LDFLAGS`、`HEADS`、`ALL`、目标 `Image`/`zImage`/`clean` | 纯手工变量驱动，无配置系统 |
| 16.2 子目录 `Makefile` | `kernel/`、`fs/`、`mm/`、`drivers/block/` 等的 `OBJS` | 每个文件一个 `.o`，手工列全（**没有通配符**） |

| 16.5 `Makefile` 里的架构移植 | `ARCH`、`CROSS_COMPILE`、`linux/config.h` | 交叉编译的雏形（0.11 时代还只有一部分支持） |

## 核心精讲

> 以下均为**教学示意，不代表可编译运行**。

### 16.1 顶层 `Makefile` 的骨架

```make
# Makefile（0.11 形态的简化示意）—— 教学示意，不代表可编译运行
ARCH := i386

AS      = as
LD      = ld
CC      = $(CC) -m386
CFLAGS  = -Wall -Wstrict-prototypes -O2 -fomit-frame-pointer
LDFLAGS = -e init -Ttext 0

BOOTCON  = cron
ALL      = Image
HEADS    = boot/head.o init/main.o kernel/kernel.o
         fs/mfs/genfs.o fs/fs.o
         mm/mm.o
         kernel/blk_drv/blk_drv.o kernel/chr_drv/chr_drv.o

Image: Image-1 Image-2 Image-3
	cat Image-1 Image-2 Image-3 > Image
	rm -f Image-1 Image-2 Image-3

Image-1: boot/bootsect.o
	$(LD) $(LDFLAGS) -s -o Image-1 $<

Image-2: boot/setup.o
	$(LD) $(LDFLAGS) -s -o Image-2 $<

Image-3: head.o init/main.o ...
	$(LD) $(LDFLAGS) -s -o Image-3 ...
```

- `LDFLAGS = -e init -Ttext 0`：把内核入口符号定为 `init`，**全部代码逻辑地址从 0 开始**（运行时靠 `boot/head.s` 里的段重定位与页表把 0 映射到物理内存）。
- 用 `cat` 把三个目标拼起来，是「镜像大小固定 3 段」的朴素做法。
- 🔧 现代内核把 `cat` 换成 `objcopy + ld` 的精确段布局（`vmlinux.lds.S`），并生成 `vmlinux`、`bzImage`、`vmlinux.bin`、`.map`、符号表等一整套产物。

### 16.2 子目录 `Makefile`：文件清单要手写

```make
# kernel/Makefile（0.11 形态的简化示意）—— 教学示意，不代表可编译运行
OBJS = sched.o sys_call.o fork.o panic.o printk.o vsprintf.o
       oops.o kpanic.o sched_idle.o int_handler.o mktime.o
       traps.o math_emulate.o

kernel.o: $(OBJS)
	$(LD) -r -o kernel.o $(OBJS)
```

- `ld -r`（relocatable link）把一组 `.o` 合并成一个「可再链接的目标文件」，是当年组织内核子模块的唯一手段。
- 🔧 现代内核：`scripts/Makefile.build` 递归收集 `obj-y`/`obj-m` 列表，`vmlinux-linker` 阶段由 `vmlinux.lds.S` 精确控制每个 section 的落位；且支持 `ld --gc-sections` 抛弃未使用代码。

### 16.3 `boot/` 的 16 位装配（`as86`/`ld86`）

```make
# boot/Makefile（0.11 形态）—— 教学示意，不代表可编译运行
AS86FLAGS = -30 -0 -a
LDFLAGS86 = -0

boot/bootsect.o: boot/bootsect.s
	as86 $(AS86FLAGS) -o boot/bootsect.o boot/bootsect.s

boot/setup.o: boot/setup.s
	as86 $(AS86FLAGS) -o boot/setup.o boot/setup.s
```

- `as86`（bin86 包）负责 **16 位实模式**汇编；GAS 的 `.code16` 要到很晚才成熟。
- 三段的分工：
  - `bootsect.s`：MBR 处，把自身与 `setup`、`system` 从软盘读到内存，然后 `jmpi go, SETUPSEG`；
  - `setup.s`：关闭中断、设置临时的 GDT、进保护模式、临场重定位段寄存器；
  - `head.s`：设置 IDT/GDT、开启分页、检测 8259、跳到 `main()`。
- 🔧 现代启动链：UEFI（或 kexec）→ `arch/x86/boot/header.S`/`eboot.S` → 解压 `zImage`（`arch/x86/boot/compressed/`）→ `head_64.S` 进入 64 位 → `start_kernel()`。工具换成 `gcc`/`ld`/`objcopy`，bootloader 换成 GRUB/systemd-boot。

### 16.4 `tools/build.c`：把三段拼成 Image

```c
/* tools/build.c（简化示意）—— 教学示意，不代表可编译运行 */
int main(int argc, char **argv)
{
    ...
    /* 1) 读入口 Makefile 段偏移 */
    /* 2) 依次把 4 个模块按指定偏移拷贝进一块大内存 */
    if (bufp - buf != 0) { ... }
    /* 3) 在头部填上扇区数、根设备号等参数 */
    buf[0x1fe] = ...;   /* 引导签名 0x55 0xAA */
    ...
    write(1, buf, sizeof buf);   /* 写到 stdout，重定向成 Image */
}
```

- 这正是「为什么第 17 章的实验能直接 `dd if=Image of=/dev/fd0`」的原因：**Image 是一个 1.44MB 的软盘镜像**，`tools/build.c` 负责把所有内容按固定布局填好。
- 它也是 GNU/Linux 早期「构建工具也是个 C 程序」的经典案例（对比 `makepkg`、`baobab` 的早期形态）。
- 🔧 现代对应物：`scripts/build`（Kbuild 里的构建辅助程序）、`scripts/pack-cpio.c`（initramfs 打包）、`scripts/objtool`（运行时验证内核代码与 `.o` 的 ELF 结构一致性，`check_obj` 阶段）。

### 16.5 配置：`linux/config.h` 与 `include/linux/autoconf.h`

- 0.11 的配置来自 `Makefile` 里的宏（`CONFIG_*`）与手工编辑的 `include/linux/config.h`。
- 🔧 现代：`Kconfig` 文件 + `scripts/kconfig/`（提供 `menuconfig`/`nconfig`/`defconfig`/`oldconfig`），生成 `.config` 与 `include/generated/autoconf.h`；`scripts/headers` 负责把 `uapi` 头文件安装到 `usr/include`。

### 16.6 系统化的现代建造体系

| 构件 | 作用 | 0.11 的对应 |
| --- | --- | --- |
| Kbuild（`Makefile` + `scripts/Makefile.build`） | 递归编译 | 每个子目录手写的 `Makefile` |
| Kconfig / `menuconfig` | 内核功能配置 | `include/linux/config.h` 手工维护 |
| `scripts/` 工具（objtool、pack-cpio、headers、firmware） | 构建期辅助程序 | `tools/build.c` |
| dtc（设备树编译器） | 把 `.dts` 编译成 `.dtb` | 无 |
| BPF 的 LLVM 后端 | 用户态把 BPF C 编译成 eBPF 字节码，由内核验证并 JIT | 无 |
| KUnit / selftest | 构建期可选纳入测试 | 无 |
| Rust（`Documentation/rust/`） | 内核中允许 Rust 编写的组件 | 无 |

## 版本演进

| 时间 | 事件 |
| --- | --- |
| 1991–1994 | 0.11：手写 Makefile + `as86`/`ld86` + `tools/build.c` |
| 1995 | `Makefile` 引入 `CONFIG_*` 与内核配置概念 |
| 1996–2000 | 2.0/2.2：顶层 Makefile 支持 `ARCH`/`CROSS_COMPILE`，开始支持 Alpha/Sparc |
| 2000 | Kconfig 出现（源自 `tconfig`，2000 年由 Roman Zykov / 后由 Al Viro 重写为 `scripts/kconfig`） |
| 2002 前后 | **Kbuild 2.5 重构**：`scripts/Makefile.build` 机制确立，Makefile 降到「只描述对象」 |
| 2005 | 2.6.11 起 `make mrproper/oldconfig`、模块构建体系成熟 |
| 2010 前后 | `scripts/headers` 与 UAPI 安装分离；`Kconfig` 拆分为 source 树布局 |
| 2015 前后 | `dtc` 进入内核 `scripts/`，设备树成为 ARM/RISC-V 的标准描述 |
| 2018 | 内核构建转向 `sparse`/`checkpatch` 常态、`objtool` 强制化（防止运行时投机执行） |
| 2021 | KUnit 进入主线；`make rustavailable` 等新目标出现 |
| 2022 | **Rust for Linux**：Rust 支持合并进程开启（6.1 起 `CONFIG_RUST`），`rustc` + `bindgen` 进入构建链 |
| 2023–2026 | 构建系统逐步引入 `Rust` 与 C 混合链接；`rustfmt` 检查纳入 CI；`make report` 等可观测性工具出现 |

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：构建系统的研究/工程工作集中在 **增量构建正确性**、**可复现构建（REPRODUCIBLE_BUILDS）**、**交叉编译与容器化工具链**、**编译期合规性检查（`objtool`、`sparse`、`rustfmt+clippy`）**，以及 **大型 Cohort 项目的构建并行度（make -j）与内存占用**。
- **工业界开源**（star 数 2026-09 实测）：
  - `torvalds/linux`（≈**250k★**）：构建系统本身就在仓库里——`Makefile`、`scripts/Makefile.*`、`Kconfig`、`scripts/`、`Documentation/kbuild/`、`Documentation/rust/`。
  - `Rust-for-Linux/linux`（≈**4.4k★**，Miguel Ojeda 维护的内核 Rust 支持分支仓库）：“Rust for Linux” 的官方实验场，是理解 16 章 16.7 节的最佳现场。
  - `gcc-mirror/gcc`（≈**11.3k★**）与 `llvm/llvm-project`（≈**40.7k★**）：内核 2024–2025 起逐步支持 Rust 与 Clang 组合编译，两者都是必需工具链。
  - `u-boot/u-boot`（≈**5.3k★**）：现代 bootloader 的构建范式，也是 `tools/build.c` 那条「镜像生成」链路的后代。
  - `devicetree-org/devicetree-specification`（≈**1.1k★**）：设备树规范，构建链里的 `dtc` 编译对象。
  - `tianocore/edk2`（≈**6.3k★**）：UEFI 固件的构建体系，与 GRUB/systemd-boot 一起构成现代的「0 段启动」。

## 常见误区与本书需修正之处

| # | 误区 / 本书局限 | 2026 年的修正与补充 |
| --- | --- | --- |
| 1 | 「内核就是 `make` 一下」 | 现代内核构建前需要 `make defconfig/menuconfig`，构建中会跑 `objtool`、`genheaders`、`dtc`、VMLINUX 符号表等十余个生成步骤 |
| 2 | 「一个 Makefile 就能描述整个内核」 | 🔧 现代是 `Kbuild` + `Kconfig` + `scripts/` 的三层体系，Makefile 只描述「谁依赖谁」 |
| 3 | 「16 位代码由 GAS 处理」 | 0.11 用专门的 `as86`/`ld86`（bin86）；今天由 GAS 的 `.code16gcc` 与专用 `.inc` 处理，ARM/RISC-V 早已无此问题 |
| 4 | 「镜像布局由 `cat` 决定」 | 🔧 由 `vmlinux.lds.S` 精确定义 section 布局；`initramfs` 由 `scripts/pack-cpio` 打包 |
| 5 | 「交叉编译就是把 CC 换成 `i386-elf-gcc`」 | 🔧 现代交叉编译需要 `ARCH=<arch> CROSS_COMPILE=<prefix>-`，还要区分 `hostprogs`、`target`、`as-needed` 三类目标 |
| 6 | 「内核只用 C 写」 | 🔧 6.1 起 **Rust** 可以编写内核模块/驱动（`Rust-for-Linux`），并有 `rustfmt`/`clippy` 检查 |
| 7 | 「设备树不重要」 | 🔧 ARM/RISC-V 上设备树是**必须的**，由构建期的 `dtc` 编译 `.dts` → `.dtb` |
| 8 | 「构建一次就够了」 | 🔧 有 `mrproper`、`olddefconfig`、`savedefconfig`、`rebuild` 等完整生命周期；CI 里还要跑 `sparse`、`checkpatch`、`smatch` |
