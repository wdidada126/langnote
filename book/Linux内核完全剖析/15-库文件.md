# 第 15 章 库文件

> **本章地图**：`lib/string.c`（`mem_copy`/`str_compare`/`str_chr` 等 C 运行时基础函数）→ `lib/malloc.c`（`kmalloc`/`kfree` 的 **chunk 头 + 按尺寸分档 freelist**）→ `lib/stdio.c`（用户态可用的简易 stdio）→ `lib/vsprintf.c` / `lib/sprintf.c`（格式化输出，把「数字转字符串」手写到底）→ `lib/dir.c`/`lib/readdir.c`/`lib/ctype.c` 等零散工具。核心结论：0.11 自带了一份**最小 C 运行时**，它既是内核的一部分，也是用户态程序的 libc 替代品——理解它，才能理解「为什么这本书专门用一章讲几个 `for` 循环」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 15.1 为什么内核自带库 | 不使用 glibc；内核与用户程序各有一份实现 | 同一份 `string.c` 被两次编译进不同的镜像 |
| 15.2 `lib/string.c` | `mem_copy`、`mem_compare`、`str_len`、`str_cmp`、`str_chr`、`str_rchr` | 逐字节手写、无 MMX/SSE、无对齐优化 |
| 15.3 `lib/malloc.c` | `kmalloc(size)`：`struct task_struct` 风格的 chunk 头 + 尺寸分档 + 空闲链表 | **相同大小的程序块用 bit 位链接**，`kfree` 直接回收 |
| 15.4 `kfree` 与碎片 | 只回收自身大小档位，不合并相邻块 | 与今天 SLUB/SLUB 的「对象合并」思路不同 |
| 15.5 `lib/stdio.c` | `getchar`/`putchar`/`gets`/`puts`/`printf` 的用户态简易版 | 与 glibc 的 `stdio` 同名，冲突来源 |
| 15.6 `lib/vsprintf.c` | 数字转字符串、宽度/填充/进制格式化的手写实现 | `printk` 与 `printf` 共用同一套格式化引擎 |
| 15.7 `lib/ctype.c`、`lib/dir.c`、`lib/readdir.c` | 字符分类、目录项遍历辅助 | 一些小而全的工具函数 |
| 15.8 现代 `lib/` | `memdup`、`bitmap`、`xarray`、`scatterlist`、`kunit`、`lib/crypto` | 🔧 从「字符串与分配」扩展到**通用数据结构与算法层** |

## 核心精讲

> 以下均为**教学示意，不代表可编译运行**。

### 15.1 两份 C 运行时：内核与用户程序

```text
内核侧： kernel/printk.c 引用 lib/string.c 的 mem_copy / mem_compare ...
用户侧： 用户的测试程序（在 0.11 上跑的）也需要 memcpy/strlen
```

- 前者编译进 `Image`（链接时已解析），后者由 `tools/build.c` 决定要不要把 `lib/string.o` 打进用户程序。
- 这个「双实现」在这本书第 17 章的实验里会造成**符号重复定义**的困惑——这正是理解内核与 libc 边界的入口。

### 15.2 `lib/string.c`：手写的基础函数

```c
/* lib/string.c —— 教学示意，不代表可编译运行 */
#define __NO_-MM_ 0

int mem_compare(unsigned char *s1, unsigned char *s2, unsigned int n)
{
    while (n--) {
        if (*s1++ != *s2++) {
            return 1;
        }
    } else
        return 0;
    return 0;
}

void *mem_copy(void *to, const void *from, unsigned int count)
{
    unsigned char *p1 = to;
    const unsigned char *p2 = from;
    while (count--) *p1++ = *p2++;
    return to;
}
```

- 一眼就能看出两个问题：**没有 `const` 的返回值语义**（早期内核常量越来越多）、**没有重叠拷贝保护**（`memcpy` vs `memmove` 的区别在这一版里被忽略）。
- `str_chr`（找字符）、`str_rchr`（反向找）、`str_len`、`str_cmp` 也都是逐字节循环。
- 🔧 现代内核：`lib/string.c` 加入了 `memchr_inv`、`strnlen_chk`、`string.h` 里的 `__builtin_memcpy` 内联；用户态侧用编译器内建的 `memcpy`。批量字符处理由 `lib/string_helpers.c` 承担，而真正的向量化在 `arch/*/lib/string*.c`（x86 的 SSE2/AVX2 版本）。

### 15.3 `lib/malloc.c`：分档分配器

```c
/* lib/malloc.c —— 教学示意，不代表可编译运行 */
struct task_struct {
    /* 注意：0.11 的 malloc 复用了 task_struct 这个结构体名，
       它作为 chunk 头使用（前 16 字节），因为内核里没别的空闲链表结构 */
    ...
};

struct task_struct *malloc(unsigned int size)
{
    unsigned int i;
    struct task_struct *prev, *curr, *new;

    if (size > MAX_MEMORY_SIZE) return NULL;
    if (size < MINMALLOC) size = MINMALLOC;
    if (!(i = (size + BYTE_ALIGNMENT - 1) / BYTE_ALIGNMENT))
        i = 1;
    /* 找到对应的尺寸档位（0 = 32, 1 = 64, ... 或大块） */
    prev = NULL;
    if (!(curr = free_lists[i])) {        /* 该档位无空闲块 → 建一个 */
        ...
        new = get_free_page(GFP_KERNEL);  /* 从分页里拿一页 */
        if (!new) return NULL;
        free_lists[i] = new;              /* 变成该档位的链表头 */
        free_lists[i]->rlimit = (i - 1) * 32;
        free_lists[i]->state = curr = (struct task_struct *)((char *)new + PAGE_SIZE * curr->rlimit);
        ...
    }
    ...
    return curr;
}
```

架构要点（很多人第一次读会以为在 stdlib）：

1. chunk 头直接**复用内核 `struct task_struct` 的前若干个字段**，因为内核里再没人比它更好用，且省空间；
2. **按尺寸分档**（32/64/…/2048 字节，超出则单独特分配），每档一条 `free_lists[i]` 空闲链表；
3. 分配时从对应档位的链表头取，**链表节点就是对象本身**（`next` 字段）。
4. 分配不到就从 `get_free_page()` 再要一整页。

```c
void free_skb(...);
void kfree_skbmem(void *_ptr, int size) { ... }

void kfree_skbmem(void *_ptr, int size)
{
    struct task_struct *curr, *next, *prev;
    int i;
    ...
    /* 把该块插回 free_lists[对应档位] */
}
```

- `kfree` 用「**传入的 size 决定档位**」来定位链表——这一点非常容易踩坑：**同一个指针必须带着正确的 size 去释放**，这与现代分配器的「从指针反推 chunk 头」完全不同。
- 🔧 现代内核：`kmalloc()` 走 SLUB（每 `kmem_cache` 有 per-cpu `freelist`），**不需要 size 参数**也能释放（`kfree(p)`），因为它从 `virt_to_head_page(p)` 反推；`kmalloc` 由 `include/linux/slab.h` → `kmem_cache_alloc`。
- 用户态分配器的经典对照：`ptmalloc`（glibc，arena + tcache）、`jemalloc`（per-thread arena + size class）、`mimalloc`（large page abstraction）。

### 15.4 用户态 stdio 与格式化输出

```c
/* lib/stdio.c / lib/sprintf.c —— 教学示意，不代表可编译运行 */
int getchar(void) { ... }
int putchar(int c) { ... }
int printf(const char *fmt, ...)
{
    va_list args;
    int written;
    va_start(args, fmt);
    written = sprintf(mybuf, fmt, args);
    ...
    va_end(args);
    return written;
}
/* vsprintf：把数字按进制转成字符串，处理前导零、宽度、符号 */
if (*fmt == '0' && (*(fmt + 1) == 'x' || *(fmt + 1) == 'X')) { ... }
```

- 0.11 的 `printf` 没有缓冲区、没有行缓冲、没有 `FILE*` 抽象，直接 `putchar` 写 TTY；
- `vsprintf` 的实现里能看到「**从右向左填充 buffer**」的经典技巧（先算好字符串的起始位置），这是那个年代手写格式化输出的标准做法。
- 🔧 现代内核：`lib/vsprintf.c` 仍在（供 `printk` 使用），但用户态 `printf` 由 glibc 实现：`vfprintf` 的查找表 + 数字转字符串走 `__printf_buffer_*`（SIMD 加速）与 `__printf_fp_l` 的精确浮点格式化（glibc 的 `printf_fp` 使用 MP 运算保证正确舍入）。

### 15.5 年表与同一问题的两种答案

| 主题 | 0.11 | 2026 年的现代形态 |
| --- | --- | --- |
| 复制/比较 | `lib/string.c` 逐字节 | 编译器内建 + `arch/x86/lib/string_64.c` 的 AVX2 版本；`memremap` 处理 I/O 内存 |
| 分配 | `lib/malloc.c` 分档链表 | SLUB（`mm/slub.c`）、SLOB、`kmem_cache`、per-cpu 池；用户态 glibc/jemalloc |
| 格式化 | `lib/vsprintf.c`（vsnprintf 的雏形） | `lib/vsprintf.c` 仍在，内核新增 `snprintf`/`sysfs_emit` 等安全封装 |
| 字符串助手 | 无 | `lib/string_helpers.c`：`string_get_size`、`sysfs_emit`、`strscpy` 等安全封装 |

## 版本演进

| 时间 | 事件 |
| --- | --- |
| 1991–1994 | 0.11：`lib/` 只包含 `string/malloc/sprintf/vsprintf/stdio/dir/readdir/ctype/args/unistd` |
| 1996 前后 | 2.0：`lib/string.c` 增加 `strnlen` 等；`mm/kmalloc.c` 从 `kernel/` 迁出 |
| 2005–2008 | SLUB 默认化；`kmalloc` 的 `GFP` 标志体系成熟 |
| 2010 | `lib/bitmap.c`、`lib/radix-tree.c` 迁出子系统；`lib/list_sort.c` 用于 `rbtree` 迁移 |
| 2015 | `lib/xarray.c`（内核 3.9 起）替代部分 radix tree 用法 |
| 2018 | `scatterlist` 泛型化（`lib/scatterlist.c`），支撑 DMA、加密与 NVMe |
| 2021 | **KUnit**（`lib/kunit/`、`lib/tests/`）进入主线，库函数终于有了单元测试框架 |
| 2023 | `lib/string_helpers.c` 支持 `sysfs_emit_at`、`strscpy` 全面替换 `strcpy` 类不安全函数 |

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：分配器研究方向集中在 **NUMA 感知分配**、**低延迟路径**（无锁/差分分配）、**可复现性与确定性**、**安全（线性化与元数据混淆攻击）**，以及 **非确定性内存回收（RCU）**；字符串层则集中在 **SIMD 加速**与**越界检测的编译期支撑**。
- **工业界开源**（star 数 2026-09 实测）：
  - `torvalds/linux`（≈**250k★**）：`lib/string.c`、`lib/vsprintf.c`、`lib/string_helpers.c`、`lib/scatterlist.c`、`lib/xarray.c`、`lib/tests/` 都在 `lib/`，是本章的现代直系后代。
  - `jemalloc/jemalloc`（≈**11.2k★**）：per-thread arena + size class，是「size 分档」思路的工业化版本，Firefox/MySQL 默认使用它。
  - `llvm/llvm-project`（≈**40.7k★**）：`__builtin_memcpy` 与 `-D_FORTIFY_SOURCE` 的编译期检查，正好补上 0.11 缺失的边界检查。
  - `gcc-mirror/gcc`（≈**11.3k★**）：`-Wstringop-overflow` 一类警告让不安全拷贝在编译期被拦下。
  - `openzfs/zfs`（≈**12.5k★**）：ARC 与 slab 混合的缓存/分配策略，是「库级算法」被做进生产系统的另一个样本。

## 常见误区与本书需修正之处

| # | 误区 / 本书局限 | 2026 年的修正与补充 |
| --- | --- | --- |
| 1 | 「`lib/malloc.c` 就是内核的 malloc」 | 它是**简化版分档分配器**，与现代 SLUB 在「如何定位 size」「如何合并空闲块」上完全相反 |
| 2 | 「`kfree` 不用传 size，因为内核知道」 | 恰恰相反：0.11 的 `kfree(p, size)` **必须**带 size，否则找不到该回收的链表 |
| 3 | 「`memcpy` 不重叠是 glibc 的严谨要求」 | 0.11 的 `mem_copy` 没有区分 `memcpy`/`memmove`，重叠行为未定义 |
| 4 | 「`lib/` 里的东西已经没人用了」 | 🔧 `lib/vsprintf.c`、`lib/string.c` 仍在内核关键路径上；`lib/` 已经扩到 bitmap、radix tree、xarray、scatterlist、zstd、KUnit |
| 5 | 「分配只发生在启动早期」 | 🔧 运行时仍有大量分配：`mempool`、`kobject` 生命周期、`debugfs`、模块加载、网络 skbuff；FIPS/加密库也在 `lib/crypto/` |
| 6 | 「库函数没有测试」 | 🔧 `lib/tests/` 有 KUnit 测试（如 `lib/tests/string_kunit.c`、`lib/tests/hexdump_kunit.c`） |
| 7 | 「用户态库与内核库是同一套」 | 🔧 内核**绝不**链接 glibc；`CONFIG_LIBSCHED` 之类选项控制是否使用内核库函数（不再依赖 lib/ 的旧路径） |
