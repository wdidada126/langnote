# 第 9 章 块设备驱动程序

> **本章地图**：块设备文件层 `blk_dev.c`（`blk_dev[]` 请求数组与策略函数指针）→ 请求提交与合并 `ll_rw_blk.c`（`make_request` / `try_merge`）→ 电梯重排 `elevator.c` → 具体驱动 `hd.c`（IDE 硬盘）与 `floppy.c` → IDE 寄存器编程 `hd_out` → 读容量与分区 `get_hd`。核心结论：0.11 的块层是**全局静态请求数组的单队列模型**，没有 per-device 队列、没有请求优先级、没有 barriers/fua，这些限制决定了后面所有「现代块层」的设计动机。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 9.1 `blk_dev.c` | `blk_dev[NR_REQUEST]` 请求数组 + 每设备策略函数 `blk_dev_struct` | 请求池**静态预分配 32 个**（`NR_REQUEST`），耗尽即失败 |
| 9.2 `ll_rw_blk.c` | `MAKE_REQUEST` 策略函数、`try_read_merge`/`try_write_merge`、扇区对齐 | 一次 `ll_rw_block` 可展开成若干 request；**合并只在同一 buffer head 链上做** |
| 9.3 `ll_rw_blk.c` 主流程 | `make_request()`：分区检查 → 校验扇区 → 缓冲区锁 → 合并/插入 → `do_request` | 「先看缓冲区、再看队列」的两阶段模型，是 page cache 之前的时代写法 |
| 9.4 `elevator.c` | 电梯式（elevator）重排：向上/向下扫描 | 只减少寻道，**不做带宽公平**，也不感知 deadline |
| 9.5 `hd.c` | IDE 硬盘：`hd_info`、`hd_registers`、`hd_out()`、命令与状态寄存器 | 驱动**直接 I/O 端口编程**，轮询完成（`ide_intr` 尚未启用中断驱动） |
| 9.6 `hd.c` 分区与容量 | `get_hd()`、CHS→LBA、`hd_ioctl` | 0.11 只支持 **16 个分区**（4 主 + 扩展链），IDE 控制器数量固定 |
| 9.7 `floppy.c` | 软驱：`FDC` 端口、`DOR`/状态机、`bad_flp` | 软盘 DMA + 中断，属于「经典的、但已死掉的」设备模型 🔧 |
| 9.8 缓冲区层的接口 | `fs/buffer.c` 与块层的边界 | `bread`/`breada` 是块层上方唯一入口，缓冲缓存与请求队列**强耦合** |

## 核心精讲

> 以下均为**教学示意，不代表可编译运行**。0.11 的块层与今天内核的 `struct request_queue` 完全同名不同义，切勿按字面照抄到现代内核。

### 9.1 块设备文件层（`blk_dev.c`）：静态请求数组

0.11 没有「每个设备一个队列」，而是**所有块设备共用一张请求表**：

```c
/* fs/blk_dev.c —— 教学示意，不代表可编译运行 */
#define NR_REQUEST 32

struct request {
    int dev;              /* -1 = 空闲槽位 */
    int cmd;              /* READ / WRITE */
    int errors;
    unsigned long sector; /* 起始扇区（设备绝对扇区） */
    int nr_sectors;       /* 总扇区数 */
    int hard_sectors;     /* 已传送扇区 */
    unsigned long buffer; /* 数据缓冲区线性地址 */
    unsigned long bh;     /* 第一个 buffer head 的指针 */
    unsigned long bhtail; /* 最后一个 buffer head */
    struct request *next; /* 链接下一个请求（电梯重排用） */
};

struct blk_dev_struct {
    void (*request_fn)(void);   /* 该设备的策略/请求函数 */
    struct request *current_request;
};

extern struct blk_dev_struct blk_dev[NR_BLK_DEV]; /* IDE/ floppy/... */
```

关键结论：

- 请求槽位**静态分配且总数固定**（32）。系统里持续有 I/O 时，`NR_REQUEST` 耗尽会让新请求**直接返回失败**（`make_request` 找不到空槽就 `-EAGAIN`），这是 0.11 吞吐量上限的硬瓶颈。
- 「策略函数」`request_fn` 是**每设备一个函数指针**，现代内核里这个概念被拆成了 `make_request`（ colocating 策略）+ `submit_bio` + 调度器三层。

### 9.2 请求合并（`ll_rw_blk.c`）

`try_merge()` 的三条规则读起来很晦涩，但本质只有三条：

```c
/* fs/ll_rw_blk.c —— 教学示意，不代表可编译运行 */
static int try_merge(int major, int minor, struct request *req, int cmd,
                     struct buffer_head *bh)
{
    struct request *prev;

    if (req->dev < 0)          /* 找空槽 */
        return 1;
    /* 一）同设备、同命令、物理连续、且是这个 buffer head 的处理对象 */
    if (req->dev == dev && req->cmd == cmd && bh->b_blocknr == req->sector) {
        /* 二）缓冲区不是异步写且未被提交（b_dirt==0，即「干净」可重入） */
        if (!(bh->b_state & BH_Async) && (bh->b_state & BH_Dirty) == 0) {
            req->bh = bh;                 /* 挂进 request 的 bh 链 */
            bh->b_req = cmd;
            bh->b_next = NULL;
            req->bhtail = bh;
            req->nr_sectors += count;
            return 1;
        }
    }
    /* 三）否则只能往前一个 request 合并（request 内部也是 bh 链） */
    ...
}
```

- 合并的粒度是 **buffer head（512 字节）**，不是页、也不是「任意相邻请求」，所以「顺序大 I/O」在 0.11 里多半合成不了大请求。
- `BH_Async` 标志的存在，说明缓冲区有「已交给块层、正在飞行」的状态位——**这就是现代内核 `struct bio` 里的 `BIO_IO_OWned` / `btiovec` 的前身**。

### 9.3 请求提交主流程（`make_request`）

```c
/* fs/ll_rw_blk.c —— 教学示意，不代表可编译运行 */
void make_request(int major, int minor, struct buffer_head *bh)
{
    int cmd = bh->b_state & BH_Dirty ? WRITE : READ;
    ...
repeat:
    req = get_request(major, minor);      /* 从 blk_dev[major]. 静态池取槽 */
    if (!req) return;                     /* 队列满：直接放弃（不休眠！） */
    ...
    if (req->cmd == cmd && ... )          /* try_merge 成功则提前返回 */
        goto ok;
    add_request(major, req);              /* 按电梯顺序插入队列 */
    do_request(major);                    /* 立刻尝试下发 */
ok:
    lock_buffer(bh);
}
```

三个值得记住的工程事实：

1. `make_request` **在中断/原子上下文中也可能被调用**（早期 `bread` 路径），所以它不能阻塞等待空槽；
2. 因此「队列满」的唯一行为是**丢弃这次 I/O**，上层靠 `b_state & BH_Launder` 重试或 upper layer 报错；
3. 🔧 现代内核的做法截然相反：`blk_mq` 会**在调度器层排队并限流（blk-mq 的 `TAG` 机制）**，队列满时阻塞提交者而不是丢请求。

### 9.4 电梯算法（`elevator.c`）

0.11 的电梯只有两个方向：` elevator 上扫 / 下扫`，遇到队列两端的请求就换方向。它解决的是「减少寻道」，但不是「公平」。

```c
/* fs/elevator.c —— 教学示意，不代表可编译运行 */
static void电梯插入(struct request *req, struct request *next)
{
    /* 规则：先找「方向一致的最近请求」；
            若请求在磁道两端之外，则反向插入 */
    if (req->sector < rq->sector) {          /* 新请求在内侧 */
        while (rq->next && rq->next->cmd == rw &&
               req->sector < rq->next->sector)
            rq = rq->next;
    } else {                                 /* 外侧 */
        while (rq->next && rq->next->cmd == rw &&
               req->sector > rq->next->sector)
            rq = rq->next;
    }
    ...
}
```

- 同一磁道上的请求按扇区号排序，天然做了一次合并；
- 但没有 deadline 概念：一个持续请求本设备的后台进程，可以让一个前台的读请求**永远等下去**（经典的「I/O 饥饿」）。

### 9.5 IDE 驱动的寄存器编程（`hd.c` 的 `hd_out`）

0.11 的 IDE 驱动是教科书级的裸端口操作，但依赖 x86 的 `outl` 可写 I/O 端口这一历史便利：

```c
/* drivers/blocks/hd.c —— 教学示意，不代表可编译运行 */
static void hd_out(unsigned int drive, unsigned int nsect, unsigned int sect,
                   unsigned int head, unsigned int cyl, unsigned int cmd)
{
    /* 手工拼装 LBA 或 CHS 参数，逐个写到控制器寄存器 */
    outb(0x00, HD_CMD);                       /* 先停掉可能的中断 */
    ...
    outb(sect, HD_CURRENT);                   /* 扇区号（0.11 用 CHS/LBA 混合） */
    outb((cyl << 8) | cyl_low, HD_DATA);      /*  cylinder 低字节 */
    ...
    outb(cmd, HD_CMD);                        /* 0x20 = READ, 0x30 = WRITE */
}
```

- 每一步都靠 `inb(HD_STATUS)` 轮询 `HD_DRQ`（数据请求）与 `HD_ERR`；
- 0.11 里 IDE 中断处理 `IDE_interrupt` 已经存在，但真正的**多命令流水线（tagged queuing）**要等到 2.6 的 `libata`。
- 🔧 现代 SATA/AHCI/NVMe 驱动：全部走 **DMA 描述符环 + MSI 中断 + NCQ 深队列**，CPU 不再逐个轮询端口。NVMe 更直接：`SQ/CQ` 环形队列，最多 64K 命令槽（IOQ 深度），多个 I/O 队列（per-CPU / per-IOQ）并行。

### 9.6 扇区级视角：0.11 的设备抽象只有「扇区号」

```c
/* include/linux/fs.h（0.11）—— 教学示意，不代表可编译运行 */
struct hd_struct {
    unsigned long start_sect;
    unsigned long nr_sects;
};
```

一切上层（inode 位图、缓冲区、mknod）都把设备当成「**连续的扇区数组 + 分区表**」，这是 0.11 能跑在 16MB 内存上的关键简化，也是它无法承载现代设备特性的根源（例如不支持非 512B 物理扇区、不支持 discard/TRIM、不支持分区对齐提示）。

## 版本演进

| 时间 | 内核版本 | 事件 |
| --- | --- | --- |
| 1991–1994 | 0.11 时代 | 静态 `blk_dev[]` 请求池 + 电梯 + 轮询 IDE；代码总量小到能用一本书逐行讲完 |
| 1999–2002 | 2.3/2.4 | 引入 `ELIA`（电梯 I/O 算法）作为可替换调度器，机制上有了「策略可插拔」的雏形 |
| 2003–2007 | 2.6 | **deadline** 调度器（2003）加入过期时间防止饥饿；**CFQ**（2007 起默认）引入「按进程/按 cgroup 公平」；blk layer 支持 barriers、FUA 与 `Request Queue` 参数（`queue_max_sectors` 等） |
| 2010–2013 | 2.6.30 / 3.9 | **blk-mq（multiqueue）** 由 Jens Axboe 于 2013 年合并（3.13），废掉全局单队列，改为**per-CPU 软件队列 + per-device 硬件队列 + tag 集合** |
| 2013–2016 | 3.13 / 4.x | bfq/noop/deadline 全部适配 blk-mq；`blk-mq` 成为默认路径 |
| 2020 前后 | 5.x | NVMe 默认走 blk-mq；多队列调度器（`mq-deadline`、`kyber`、`bfq`）成熟 |
| 2023 | 5.x / 6.x | **io_uring 成为主流异步 I/O 接口**（5.1 引入，2023 年大量数据库/存储栈切换到 io_uring + HOU 模式）；`zoned block device`（ZBD）承诺接口完善 |

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**： blk-mq 时期的研究集中在 **多队列与 NUMA 亲和**、**多路径 I/O（MPATH）**、**存储分类（device classification）**与**延迟敏感调度（Kyber、EEVDF）**；**Zoned Block Devices / ZBD 与 ZAC-WD** 让「顺序写入约束」进入标准；**io_uring 的绑核与批量提交**（如 HOU：io_uring 直接走 O_DIRECT 到块层，绕过 page cache）在 2023–2025 年被数据库与存储系统广泛采纳。
- **工业界开源**（star 数 2026-09 实测）：
  - `torvalds/linux`（≈**250k★**）：块层实现在 `block/`，调度器在 `block/bfq-iosched.c`、`block/mq-deadline.c`、`block/kyber-sched.c`；NVMe 驱动在 `drivers/nvme/`。
  - `axboe/liburing`（≈**3.8k★**，io_uring 的用户态库，**原 `axboe/io_uring` 已更名迁移到这里**）：`io_uring_setup/enter/register` 的封装，是学习 io_uring 最好的起点。
  - `qemu/qemu`（≈**13.8k★**）：实验环境的默认模拟器，`-drive if=none,id=...` 与 `virtio-blk` 让 0.11 也能挂虚拟盘。
  - `buildroot/buildroot`（≈**3.7k★**）：为实验做最小 rootfs 的标准工具。
  - `iovisor/bcc`（≈**22.7k★**）：用 eBPF 跟踪块层（`block:block_rq_issue` / `block:block_rq_complete`）来「给 0.11 装上遥测」，是替代老实验的测量手段。

## 常见误区与本书需修正之处

| # | 误区 / 本书局限 | 2026 年的修正与补充 |
| --- | --- | --- |
| 1 | 「块层就是一条全局请求队列」 | 🔧 现代块层是 **blk-mq 的多队列**：软队列（per-CPU `ctx`）+ 硬队列（per-device `hwq`）+ tag 管理，队列满时阻塞而非丢请求 |
| 2 | 「电梯算法就是现代的 I/O 调度」 | 🔧 电梯只有寻道优化、无公平、无过期。现代默认 **mq-deadline**（有读优先 + 过期）与 **BFQ**（按权重公平、支持 cgroup 层级） |
| 3 | 「I/O 请求大小由内核决定」 | 🔧 内核会**按设备能力裁剪**（`queue_max_sectors` / `max_segment_size` / `max_write_zeroes`），并且支持 **barriers、FUA、discard、WRITE_ZEROES、ZBD 的 zone append** |
| 4 | 「只认 512 字节扇区」 | 🔧 4Kn（4096 字节物理扇区）设备已成主流；NVMe 的 LBA 与元数据分离、`END-to-END Data Protection` 都是新层次 |
| 5 | 「异步 I/O 只能用 libaio」 | 🔧 现代异步 I/O 首选 **io_uring**（内核 5.1 引入，2023 后成为主流），`O_DIRECT` + HOU 模式下少一次内存拷贝 |
| 6 | 本章 `hd_out` 的端口轮询写法 | 🔧 现代驱动不轮询端口：DMA 描述符 + MSI-X 中断 + NCQ，CPU 只在队列满时才介入 |
| 7 | 「块设备驱动 = 硬盘驱动」 | 🔧 现在的块设备还包括 **virtio-blk、loop 设备、dm（device-mapper）、md（软 RAID）、zram（压缩内存盘）**，0.11 完全没有这些层次 |
