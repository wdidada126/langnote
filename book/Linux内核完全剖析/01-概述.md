# 第 1 章 概述

> **本章地图**：UNIX 的诞生（1969，贝尔实验室）→ MINIX（1987，Andrew Tanenbaum，教学用微内核）→ GNU 计划（1983–1991，Richard Stallman，自由软件运动）→ POSIX 标准（IEEE 1003.1，1988/1990）→ Linux 的诞生（1991-08-25，Linus Torvalds 在 comp.os.minix 发帖）→ 版本变迁与命名争论 → 早期贡献者 → 内容综述（全书的「读法」说明）。
>
> 一句话结论：**这一章决定你用什么心态读后面 16 章**。Linux 的「内核」只是一堆 C 与汇编，它的历史源流决定了它为什么长成这样：UNIX 的接口哲学、MINIX 的教学取向、GNU 的工具链、POSIX 的契约。

## 核心精讲

### 1.1.5 从一封公开信开始

1991 年 8 月 25 日，Linus Torvalds 发表在 `comp.os.minix` 上的帖子（常被引为「Linux 的诞生」）：

```
Hello everybody out there using minix ...
I'm doing a (free) operating system (just a hobby, won't be big and
professional) for the 386 AT.
```

> 🔧 **补充事实**：这封帖子原文长期存疑，诸多转述版本措辞不一；可追溯的权威来源是存档站 `https://www.kernel.org/`、`freshmeat` 早期转载与 Torvalds 本人 Later 的澄清贴。引用时建议标注「公开信（1991-08-25，comp.os.minix 帖，转述版）」。

### 1.1.4 POSIX 为什么重要

POSIX 的意义不是「标准化」，而是**契约化**：内核只承诺一组可移植的接口，用户程序只依赖这组接口。

```c
/* 教学示意，不代表可编译运行：POSIX 的最小 fork/exec/wait 骨架 */
#include <unistd.h>
#include <sys/wait.h>

/* 关注点：返回值 -1 表示失败，0 表示子进程，正数表示已回收的子进程 pid */
pid_t pid = fork();          /* 创建进程：UNIX 的「万物皆 fork」入口 */
if (pid < 0) { /* 失败 */ }
else if (pid == 0) {
    execv("/bin/ls", argv);  /* 用新程序替换当前进程映像 */
    _exit(127);              /* execv 成功不返回；失败必须显式退出 */
} else {
    waitpid(pid, &status, 0);/* 阻塞等待子进程，回收僵尸 */
}
```

> 结论：`fork/exec/wait` 三件套 + 「一切皆文件」是后面 `08-内核代码.md` 里 `sys_fork`/`sys_execve`/`sys_wait4` 的**存在理由**。

### 1.1.2 MINIX 与「可讲解性」的取舍

MINIX 是本书选择 0.11/0.12 的真正背景：Tanenbaum 的书配了一个约 1 万行的教学内核，让人「读完就能跑」。Linux 0.x 与之对照：

| 维度 | MINIX（1987） | Linux 0.11（1991） |
| --- | --- | --- |
| 内核形态 | 微内核：进程/文件/设备服务在用户态 | 单体内核：全部在内核态 |
| 代码规模 | 约 1.2 万行 | 约 1 万行 |
| 教学友好度 | 高（模块边界清晰） | 中（全局耦合但整体可跑） |
| 真实用途 | 教学 | 真实开发（当时的 PC 级服务器） |

> 结论：本书选 Linux 0.x 而不是 MINIX，是「**要一个真实且能跑的整体**」，而不是「要一个边界最清晰的结构」。这决定了后面章节的阅读方式——必须顺着代码流走，而不是顺着模块边界走。

### 1.1.8 早期贡献者名单（为什么名单重要）

0.x 时代的贡献者集中在少数人身上：

| 人物 | 贡献 |
| --- | --- |
| Linus Torvalds | 内核主体、版本策略 |
| Andrew Tanenbaum | MINIX 与学术影响 |
| Hendrik Starostin | 早期工具与部分代码 |
| Ingo Molnar | 🔧 2.6 的 O(1) 调度器、后来的 CFS 与 futex 相关工作 |
| Linus Walleij、Peter Zijlstra 等 | 🔧 当代调度器与驱动维护者 |

> 说明：0.x 的具体贡献者名单在各版本 CREDITS/CHANGELOG 中不一致，此处只列**可确证**的人物与贡献方向，不作完整枚举。

> 结论：**Linux 的历史不是「一个人 + 社区」，而是「一条连续的技术接力」**。本书覆盖的 0.x 只是一条起跑线。

### 1.1.5/1.1.6 为什么「先小后大」：0.11 与现代内核的体量对比

| 指标 | Linux 0.11（1992） | Linux 6.x（2026，≈） |
| --- | --- | --- |
| 源码行数 | 约 1 万行 | 4000 万行以上 |
| 顶层目录 | 9 个 | 20 余个 |
| 支持的体系结构 | 1（i386） | 30+（含 arm64、riscv64、loongarch…） |
| 单文件最大复杂度 | `sched.c` 约 300 行 | `sched/fair.c` 数千行 |
| 编译时长 | 分钟级（手工 `cat` 成 Image） | 小时级（Kbuild + 模块化） |
| 阅读方式 | 可以逐行读 | 只能按子系统读 |

> **结论**：把 0.11 当作「体量缩微模型」来读，它的价值不是「过时」，而是「**可整体内化**」。这也是本书至今仍被反复推荐的原因。

## 近年研究与工业界开源实践（2015–2026）

- **内核版本节奏本身成了研究对象**：`torvalds/linux`（**250112★**，2026-09-25 实测）保持约 9–10 周一版；LWN 的「CPU scheduler」与「Memory management」专题是跟踪主线最有效的渠道。
- **Min 内核作为教学基准位仍在**：`mit-pdos/xv6-public`（**9646★**）和 `mit-pdos/xv6-riscv`（**10516★**）是「另一个 0.x 同代教学内核」，与本书 0.11 可以按文件逐行对照（各自的 `proc.c`、`vm.c`、`bio.c` 与本书 `08`/`12` 同名）。
- **社区对「到底该读哪版内核」的共识**：先看小内核建立心智模型，再看 `Documentation/` 与子系统设计。本书正好对应第一段。
- **中文读者的现代延伸**：`dreamportdev/Osdev-Notes`（**1158★**）、`Minep/lunaix-os`（**525★**）等仓库是用现代工具链重走「从 bootsect 到 fork」这条路。

## 常见误区与本书需修正之处

| # | 说法/写法 | 修正与补充 |
| --- | --- | --- |
| 1 | 「Linux 是 Linus 一个人写的」 | Torvalds 只写了内核主体；glibc、gcc、coreutils 来自 GNU，文件系统/驱动来自全球贡献者 |
| 2 | 「MINIX 是 Linux 的前身」 | 二者是**同代并发**关系：Tanenbaum 的 MINIX 影响了思路，但 Linux 直接依赖的硬件与群体是另一套；真正的「前身」是 UNIX |
| 3 | 「1991 年那封公开信的措辞」 | 转述版本措辞不统一，引用应标注为「转述版 / 存疑」 |
| 4 | 🔧 「版本变迁到 2.6 就够了吧」 | 2.6 之后还有 3.x/4.x/5.x/6.x；CFS（2.6.23）、eBPF（3.12）、io_uring（5.1）都在其后 |
| 5 | 🔧 「本书只讲历史，不影响今天」 | 0.11 的 `fork` 语义、文件 inode 模型、`sys_*` 编号方式延续至今，读它等于读主线内核的「祖先代码」 |
| 6 | 🔧 「没有 GNU 也一样能玩」 | 没有自由工具链就没有可编译的内核；这也是 GNU 计划至今的价值 |
| 7 | 🔧 「读完 0.11 就等于懂 Linux」 | 懂的是「1992 年的 Linux」；进程/内存/调度/网络的具体实现都已换过数轮 |
| 8 | 🔧 「Linux 与 UNIX 没区别」 | 差异在内核形态（单体 vs 分层）、GPL 与社区治理、以及对 x86 的深度绑定 |
| 9 | 🔧 缺少的现代材料 | 建议补：*The Linux Kernel Documentation*（kernel.org/doc）、LWN.net、以及各子系统的维护者 tree（如 `torvalds/linux-next`） |
| 10 | 🔧 「MINIX 的微内核更先进，Linux 该走那条路」 | 微内核的理论优势 1987 年就成立，但 IPC 成本与工程复杂度让 Linux 选择了单体内核；今天的折中是模块 + 用户态服务 |
