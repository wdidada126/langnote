1. 从作业图到部署图：为什么流作业的「并行度形状」决定一切。

## 核心精讲

### 1. 三张图：逻辑图 → 执行图 → 部署图

- StreamGraph（API 翻译出的算子 DAG）→ JobGraph（算子链化后）→ ExecutionGraph（并行 subtask 展开 +
  slot 分配计划）。✅ 术语以官方架构页为准（URL 见头部）。
- 「规模化」的第一性：**状态按 key 分区、计算按 channel 流水**——同一张图在不同并行度下是不同成本结构。
- 🔧 单机类比（DuckDB 1.5.5，非 Flink 行为）：02 章 D1 的 12 桶聚合若改按 `user_id, bucket` 双键分组，
  计划形态从 12 段变 600 段——**key 基数放大 = shuffle 面放大**，与 Flink keyBy 后并行度分配同构的
  「先分区再聚合」逻辑；真实引擎的差别（网络混洗、credit-based 流控）本模拟完全不含。

### 2. slot 共享：让一张图吃满一池资源

- TaskManager 提供 N 个 slot；不同作业的 subtask **可同 TM 混装**（slot sharing 默认开）——
  均匀化资源、避免「重算子独占、轻算子饿死」。✅ 架构页/部署文档通识，⚠️ 参数名不在此抄写。
- 资源不均衡的解法阶梯 ⚠️ 转述：算子链拆分 → 细粒度资源（individual task slot）→ 异构部署。

### 3. 反压：延迟的上界由最慢算子定

- 机制：下游缓冲耗尽 → credit 通知上游减速 → 逐级上溯到源（源降速 = 消费滞后 = 端到端延迟变大）。
- 运维读数：反压颜色图 + busy 率 + checkpoint 对齐时长三者联读，定位瓶颈算子。✅ 官方 metrics/checkpoint
  页含对齐时长指标（`.../docs/ops/state/checkpoints/` 实测 200）。
- 与 02/03 章的闭环：**反压拖慢 watermark 推进**（源滞后 → 各分区 max_et 拉开 → 木桶更斜）；
  **反压拖垮 checkpoint**（对齐期间缓冲膨胀）。这是「at scale」三个字的运维学真身。⚠️ 转述，
  调优实操：[../Stream_Processing_with_Apache_Flink/10-运维监控与调优.md](../Stream_Processing_with_Apache_Flink/10-运维监控与调优.md)。

### 4. 生命周期：savepoint 是流作业的「git」

- 四场景（✅ savepoints 页通识）：**升级换版、改并行度/拓扑、A/B 或回滚、跨集群迁移**。
- `stop-with-savepoint`：带终态快照的优雅停机，替代「先 cancel 再祈祷」。⚠️ 转述 CLI 形态。
- 🔧 类比 D5（SQLite 在线备份，非 Flink）：200,000 行状态一致性拷贝 **9 ms**——「快照便宜、恢复更便宜」
  的直觉有单机数字托底；但真实 savepoint 的贵处在**跨版本状态兼容**（uid 对位/序列化器演进），
  单机文件复制完全不触及这一层 ⚠️（官方 savepoints 页 "State Schema Evolution"）。
- 部署形态演进（2022 书基线 → 2026）⚠️ 转述：YARN/standalone 为主 → **Kubernetes Operator 化**
  （session/per-job/application 三模式），application mode「一图一集群」成生产推荐。

### 5. 容量规划三步算术（概念向，不抄参数）

1. **吞吐 → 并行度**：峰值事件率 ÷ 单 subtask 稳态处理能力（用压测的每核事件数，而非官方宣称值 ⚠️）；
   取整再留 30% 余量给倾斜与追赶（checkpoint 失败后的重放洪峰，03 章）。
2. **状态 → 内存/磁盘选型**：活跃 key 数 × 平均状态体积——GB 级内存后端可谈；TB 级必上 RocksDB，
   且把「状态大小增长曲线」当容量报表看（TTL 未配 = 曲线只升不降）。⚠️ 转述。
3. **恢复 → 存储带宽**：savepoint/checkpoint 落对象存储时，快照体积 ÷ 读写带宽 = 恢复时间下界；
   增量快照与 Fast Restore 改的就是这个除式（03 章 §5）。🔧 类比 D5 的 9 ms/200k 行只是「本地」下界，
   跨网络两个数量级起步 ⚠️（**非 Flink 行为**，纯结构类比）。

### 6. 调度与网络：规模化下的两处隐性成本

- **shuffle 分区策略**：keyBy 的 hash 决定倾斜面；rebalance/forward/rescale 各自改变状态形状
  （姊妹册 05 章有逐算子对照表 ✅ 已验名链接见其目录）。
- **credit-based 流控**：接收缓冲通告代替盲目发送——高延迟网络（跨 AZ）下缓冲/并行度配比不当，
  吞吐上不去不是 CPU 问题 ⚠️ 转述。
- **机架感知**：万节点级把随机 shuffle 变局部 shuffle 的调度维度。⚠️ 概念登记，细节不展开。

### 7. 运维 checklist（概念向收敛，不抄参数）

1. checkpoint 是否**按时完成**（间隔 vs 完成时长的余量）？
2. watermark 滞后是否稳定（突发扩大 = 源倾斜或反压前兆）？
3. 状态大小增长曲线是否有拐点（TTL 是否配了——无 TTL 的状态是定时炸弹）？
4. 升级演练：savepoint 恢复 + 输出 diff 是否在 CI 里自动化？
5. 迟到数据率（side output 计数）是否逼近业务容错预算（02 章 🔧 lag 表的工业版）？

### 8. 部署形态三问（2022 书时代 → 2026 现状）

| 问题 | Session | Per-Job（⚠️ 已淡出） | Application（现行推荐 ⚠️ 通说） |
| --- | --- | --- | --- |
| 集群谁拥有 | 常驻共享 | 每作业一集群 | 每作业一集群、主流程在集群内 |
| 适合 | 短小交互/开发 | 隔离要求高的旧实践 | 生产长驻作业 |
| 客户端职责 | 提交即失联风险 | 提交端翻译图（瓶颈） | 仅触发，镜像即环境 |

- 要点 ⚠️ 转述：镜像化（作业+依赖自包含）让 03/05 章的 savepoint 升级剧本真正可 CI 化——
  「作业版本 = 镜像 + savepoint 指针」的最小闭环。
- 盘上工程对照：[../Stream_Processing_with_Apache_Flink/09-集群部署与配置.md](../Stream_Processing_with_Apache_Flink/09-集群部署与配置.md)（2022 书时代形态更全）。

## 常见误区

1. 「并行度越大越好」——key 基数低时纯增 shuffle 与状态碎片；先问数据形状再定并行度。
2. 「反压 = 网络慢」——多数根因在算子（状态访问/RocksDB 写放大/外部 sink 阻塞）⚠️。
3. 「savepoint 万能回滚」——拓扑大改时 uid 不对位即「静默丢状态」，需显式 `--force` 决策 + 对账 ⚠️。
4. 「测试集群跑通 = 生产能跑」——规模改变定性（长尾延迟、倾斜、快照体积），入门书标题里的 at scale 指的就是这个。
5. 「K8s 上不用管 checkpoint 存储」——快照落对象存储的**带宽与一致性**是新瓶颈位 ⚠️ 转述。

## 核心概念速览（中英对照）

- **作业图三态** — StreamGraph/JobGraph/ExecutionGraph：逻辑→链化→物理部署的三级投影。✅
- **算子链化** — operator chaining：相邻一对一算子合并成一个任务，省序列化与调度。✅
- **槽位共享** — slot sharing：subtask 混装同 TM，均匀用资源。✅
- **反压** — backpressure：下游缓冲耗尽逐级减速的现象与信号。✅
- **credit-based 流控** — credit-based flow control：接收方通告可收缓冲量，替代定时轮询。⚠️
- **停止带保存点** — stop-and-ignore/savepoint 家族之 stop-with-savepoint：优雅停机留可恢复点。⚠️ 转述
- **增量扩缩容** — rescaling：改并行度从 savepoint 重分派 keyed state。✅
- **TTL 状态过期** — state TTL：给状态设寿命，防无界增长。⚠️
- **指标三件套** — busy / backpressured / checkpoint alignment：定位瓶颈的标准读数。✅
- **watermark 滞后** — watermark lag：进度停滞的观测探针（倾斜/反压前兆）。
- **应用模式** — application mode：以作业为部署单元的 K8s 形态 ⚠️ 转述。
- **机架/网络感知** — network-aware scheduling：大规模下 shuffle 局部性的调度维度。⚠️
