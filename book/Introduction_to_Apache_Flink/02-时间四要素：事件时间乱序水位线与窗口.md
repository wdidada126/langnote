## 本章地图

1. 三种时间：事件时间 / 摄入时间 / 处理时间——先选时钟再谈正确性。
2. 乱序是常态：网络分区、重试、移动端缓存都会带来「迟到的过去」。
3. Watermark：用「不再更老」的猜测替代「已齐」的证明。
4. 窗口 = 对无限流的有限切分；触发、允许迟到、丢弃三开关。

## 核心精讲

### 1. 三种时间（三种「何时算完成」的答案）

| 时间 | 定义 | 优点 | 代价 |
| --- | --- | --- | --- |
| 事件时间 event time | 事件发生时刻（数据自带） | 结果可复现、乱序可控 | 必须猜「到齐」→ watermark |
| 摄入时间 ingestion time | 进入 Flink 的时刻 | 免除 watermark 生成 | 丢源头延迟信息 ⚠️（新版本已弱化该独立类型） |
| 处理时间 processing time | 算子执行时刻 | 最快、零机制成本 | 重跑不可复现，窗口随机器速度漂移 |

✅ 概念清单以官方页为准：`https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/time/`（实测 200）。
🔧 批式类比（SQLite 3.45.3，`demo.py`）：对同一张 5 万行事件表，用 `max(ts)` 一次性「定角」耗时 **2.1 ms**——
批的世界角=真时间，**不存在迟到问题**；这条数字是给「为什么批不需要 watermark」的锚。

### 2. 乱序的形式化：一条流 = 一个不断改口的证词

- 定义乱序度 p95：事件时间与到达时间之差的分布尾部。
- 关键不变量：**任何 watermark 只能覆盖「已见过的事件时间」**，对「未来的过去」（源头时钟偏差导致的
  et > now）永远无效。⚠️ 转述（该坑在 [../Stream_Processing_with_Apache_Flink/06-时间与窗口算子.md](../Stream_Processing_with_Apache_Flink/06-时间与窗口算子.md) 有工程处置）。

### 3. Watermark = 「我猜 event time 不再低于 W」

- 生成：每个并行源/分区维护 max_seen_et，算子取**所有输入的最小值**合并（木桶原理）。✅ 官方
  stateful-stream-processing 概念页对「多输入取 min」有明确表述（URL 见 00 第五节）。
- 触发规则：窗口 `[s, e)` 在 `W ≥ e` 时首次触发——即「承诺 e 之前的数据（在允许迟到 p95 内）到完了」。

### 🔧 类比实测 D2：lag 扫描——watermark 松紧是延迟/正确率的旋钮（**非 Flink 行为**）

纯 Python 到达顺序模拟（seed=155；50,000 事件铺 1 小时；3.05% 注入真迟到，迟到 600–900 s；正常传输抖动 ≤5 s；
规则 `W = max_seen_et − lag`，事件 `et < W` 记为迟到）。`demo_out.txt` 实测：

| lag | 判迟到数（率） | 其中误伤正常 | 真迟到命中 |
| --- | --- | --- | --- |
| 0 s | 36,733（73.5%） | 35,207 | 1,526 |
| 60 s | 1,526（3.05%） | 0 | 1,526 |
| 300 s | 1,526（3.05%） | 0 | 1,526 |
| 900 s | 0（0.0%） | 0 | 1,526 全容忍（窗口输出推迟 ~15 min） |

- 读数 🔧：lag=0（严格 max_seen）在抖动 ≤5 s 的流上误伤 70%——**watermark 必须容忍乱序**；
  lag 越过抖动上界后误伤归零；lag 逼近真迟到分布上界则改判「容忍重发 late 数据」。
- 这正是官方 watermark + allowedLateness + 清理策略三件套要联合调的旋钮（✅ concepts/time 与
  release-1.17 windows 页 `https://nightlies.apache.org/flink/flink-docs-release-1.17/docs/dev/datastream/operators/windows/`）。
- 非 Flink 声明：单机单线程循环，无并行算子图、无 idle source 处理（真实 Flink 里空闲分区会**卡住**
  watermark 合并，需要 idle timeout——本模拟不体现，⚠️ 转述，工程处置见姊妹册 06 章）。

### 4. 窗口：对无限流的有限切分

- 滚动 Tumbling / 滑动 Sliding / 会话 Session / 全局 Global。✅ 分类为官方 windows 页通识。
- 🔧 类比实测 D1（DuckDB 1.5.5）：`SELECT floor(epoch(ev_ts-base)/300)::INT bucket, count(*) FROM clicks
  GROUP BY 1`——100,000 行、1 小时跨度的随机点击流按 5 分钟「滚动桶」聚合，得 **12 个桶、5.9 ms**
  （首三桶 [8442, 8289, 8416]）。**批式时间桶 = 一次性算完的滚动窗口**；Flink 的区别在于桶随 watermark
  逐个「关门结账」，且迟到数据可对已关之门二次开账。
- 触发≠丢弃：Flink 窗口「首次触发后进入迟到收集态」，allowedLateness 内**修正重发**（非撤回，是再发一版），
  超期按清理策略丢弃。⚠️ 转述自官方 release-1.17 windows 页表述。

### 5. 水位线生成的工程细节（概念层够用即可）

- **周期 vs  punctuated**：默认按固定周期扫描分区 max_et 发 watermark（周期性）；punctatable 流
  （自带进度标记，如 binlog 位点）可按事件即时发。✅ windows/time 官方页通识，⚠️ 术语细节不展开。
- **单调性责任在算子**：Flink 保证合并后单调不回退；**生成器**若乱序取 max 出错，语义不兜底。
- **时钟偏差预算**：源头 NTP 偏差进入乱序分布——p95 乱序应含偏差项，否则 watermark 系统性偏紧
  （🔧 D2 表 lag=0 行的工业放大版）。

## 常见误区

1. 「watermark 单调就行」——跨并行度不取 min 会把迟到数据放行（🔧 lag=0 行是反例的另一面）。
2. 「允许迟到=不丢数据」——超窗口的迟到照样丢，除非侧输出兜住（姊妹册 14 补编：侧输出用法）。
3. 「处理时间够快就准」——快 ≠ 正确：重跑结果变了就是错了（1.3 节表）。
4. 「ingestion time 折中最好」——⚠️ 新版本它已并入 event time 自动生成路线，别再当第三类时间选型。
5. 「窗口只在流上有」——批的 date_trunc/TUMBLE 是同构语义（🔧 D1 即证），差别在**触发时机与增量修正**。

## 核心概念速览（中英对照）

- **事件时间** — event time：数据自带的发生时刻；可复现计算的唯一可靠锚（✅ concepts/time）。
- **处理时间** — processing time：算子执行时钟；零成本但不可复现。
- **摄入时间** — ingestion time：入界时刻；⚠️ 新版本中已弱化为独立配置。
- **乱序** — out-of-orderness：到达序 ≠ 事件时间序；用 p95 乱序度量水位线滞后。
- **水位线** — watermark：`max_seen − lag` 的进度猜测，窗口触发与迟到判定的准绳（✅）。
- **空闲源** — idle source：无数据的并行分区位住 watermark 合并，需 idle 标记 ⚠️ 转述。
- **滚动窗口** — tumbling window：无重叠定长桶（🔧 D1 的批式同构体）。
- **滑动窗口** — sliding window：定长可重叠，一条数据进 N 个桶。
- **会话窗口** — session window：按不活动间隙切分，无固定长。
- **窗口触发** — window trigger：watermark 越界/处理时间/自定义三种触发器。
- **允许迟到** — allowed lateness：关门后的二次开账宽限期；期间修正重发。
- **迟到侧输出** — late data side output：超期数据的旁路收容，不再进主聚合。
- **窗口关闭/清理** — window cleanup：宽限期满后状态清除，防状态泄漏。
