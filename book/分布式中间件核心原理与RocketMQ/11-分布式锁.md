## 核心精讲

（以下为教学性梳理，代码均**教学示意，不参与构建**。）分布式锁核心是「**互斥 + 防死锁（自动释放）+ 谁加谁解**」。

### 11.1 为什么需要分布式锁

- 单机 `synchronized`/`ReentrantLock` 只管一个 JVM 内的线程；
- 多实例部署下，多个进程同时改同一资源（如库存扣减）会超卖 → 需要**跨进程的互斥**。

### 11.2 Zookeeper 实现（教学示意）

```java
// 教学示意，不参与构建：Curator 分布式锁
InterProcessMutex lock = new InterProcessMutex(client, "/locks/stock");
try {
    lock.acquire();          // 创建临时顺序节点，最小序号者获锁
    deductStock();           // 临界区
} finally {
    lock.release();          // 释放（断开会话临时节点自动删，防死锁）
}
```

> ZK 锁靠「**临时顺序节点**」：会话断开临时节点自动消失，天然防死锁；watch 机制通知下一个等待者。

### 11.3 Redis 实现（教学示意）

```java
// 教学示意，不参与构建：Redisson 分布式锁（带看门狗自动续期）
RLock lock = redissonClient.getLock("stock-lock");
try {
    lock.lock();             // SET NX + 看门狗定时续期
    deductStock();
} finally {
    lock.unlock();           // 校验持有者再删，防误删他人锁
}
```

> Redis 锁核心是 **`SET key value NX PX` 原子加锁 + 唯一 value 防误删 + 看门狗续期**；
> 早期「SETNX + 过期时间」非原子易出竞态，Redisson 已封装好。

## 版本演进

- **本书基于 Zookeeper 临时节点锁 + Redis SET NX / Redisson**，是 2023 年主流两种实现。
- **🔧 2026 视角：RedLock 争议**。Redis 作者与分布式系统学者（如 Martin Kleppmann）对
  **RedLock（多实例 Redis 锁）** 的安全性有公开争论——基于时钟假设在多机房/网络分区下不严谨，
  2026 年**不建议把 RedLock 用于强一致互斥**，更推荐「单实例 Redisson + 租约」或 ZK/etcd 看门狗锁。
- **🔧 2026 视角：etcd 租约锁**。云原生下 **etcd（Lease + 租约）** 成为 K8s 生态内的现代锁底座，
  与 ZK 思路类似但更云原生。
- **🔧 2026 视角：锁的替代**。很多场景可用「数据库乐观锁（版本号/ CAS 更新）」或「消息队列串行化」
  替代分布式锁，降低外部依赖（呼应第 8 章顺序消息的串行化思路）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「分布式锁能 100% 互斥」 | 依赖正确性假设（时钟/网络），需明确边界，必要时用 ZK/etcd |
| 2 | 「锁住就安全」 | 须防死锁（自动释放）、防误删他人锁（唯一 value） |
| 3 | 「SETNX 就够」 | 非原子设过期易竞态，应用 Redisson 封装 |
| 4 | 🔧 本书未提 RedLock 争议 | 2026 不应把 RedLock 用于强一致互斥，优先 Redisson 单实例/看门狗或 ZK/etcd |
| 5 | 🔧 本书未提 etcd 锁 | 2026 云原生场景可用 etcd Lease 锁 |
| 6 | 🔧 本书未讲锁的替代 | 乐观锁 / 消息串行化（第 8 章顺序消息）常可替代硬锁 |
