## 核心精讲

（以下为教学性梳理，代码均**教学示意，不参与构建**。）本章是 RocketMQ 最「值钱」的一章——生产级可靠性。

### 8.1 消息丢失的三处风险（教学示意）

```text
# 教学示意，不参与构建：丢消息链路
① 生产者→Broker：网络抖动/无重试 → 发送丢
② Broker 存储：异步刷盘 + 宕机 → 落盘前丢
③ 消费者：自动 ACK + 处理崩 → 处理前丢
```

### 8.2 事务消息（half 机制）

RocketMQ 事务消息用「**half 消息 + 回查**」保证「本地数据库事务」与「发消息」的原子性：

1. 发 **half 消息**（对消费者不可见）到 Broker；
2. 执行本地事务（如扣库存、建订单）；
3. 根据本地事务结果 **Commit**（half 变可见）或 **Rollback**（丢弃 half）；
4. 若 Broker 长时间未收到确认，会**回查**生产者本地事务状态。

```java
// 教学示意，不参与构建：事务消息
TransactionSendResult r = producer.sendMessageInTransaction(
    new Message("order-topic", orderJson.getBytes()), order);
// 实现 TransactionListener：executeLocalTransaction / checkLocalTransaction
```

### 8.3 零丢失方案

| 环节 | 措施 |
| --- | --- |
| 发送端 | 同步发送 + 重试（或事务消息） |
| Broker | **同步刷盘** + 主从同步双写/Dledger |
| 消费端 | **手动 ACK**，处理成功再提交 offset |

> 代价：延迟升高、吞吐下降。零丢失是「业务强一致」场景的取舍，非默认。

### 8.4 重复消费与乱序

- **重复消费**：网络重试、rebalance、消费超时都会重投 → 消费端必须**幂等**（去重表/唯一键）。
- **乱序**：跨 queue 天然无序；要保证顺序需**同一业务键发同一 queue（分区有序）**，消费端串行消费该 queue。
- **重试/延时/死信**：消费失败自动重试（按延迟级别），最终进 **死信队列（DLQ）** 人工处理。

### 8.5 四种高级特性（教学示意）

```java
// 教学示意，不参与构建：顺序 / 过滤 / 延时
producer.send(msg, (mqs, m, arg) -> mqs.get(m.getKeys().hashCode() % mqs.size()), key); // 顺序：同 key 同 queue
msg.putUserProperty("age", "18");                 // SQL92 过滤（需开启）
msg.setDelayTimeLevel(3);                          // 延时消息（固定延迟级别）
```

## 版本演进

- **本书基于 RocketMQ 4.x 的事务消息/half 机制、同步刷盘、重试/延时/死信、顺序/过滤**。
- **🔧 2026 视角：事务消息的边界**。事务消息解决「发消息 + 本地事务」原子性，但
  **跨多个下游的「分布式事务」仍建议用第 10 章 Seata / 可靠消息最终一致**，事务消息不是万能。
- **🔧 2026 视角：5.x 定时/延时消息增强**。5.x 支持**任意精度延时（Timer Message）**，不再局限于
  固定延迟级别（8.5.4 的延时消息在 5.x 下能力更强）。
- **🔧 2026 视角：幂等与去重**。2026 年强调「消费幂等」是架构第一原则，常配合数据库唯一约束或
  Redis 去重表，原书 8.4 已讲重复但未上升到「设计必做」高度。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「消息发出就成功」 | 需确认发送结果 + Broker 落盘 + 消费确认 |
| 2 | 「消息不会重复」 | 重试/rebalance 必重投，消费端必须幂等 |
| 3 | 「事务消息 = 分布式事务」 | 只保证「本地事务+发消息」原子，多下游仍需 Seata/最终一致 |
| 4 | 「同步刷盘一定零丢失」 | 还需发送重试 + 消费手动 ACK，三者齐备才零丢失 |
| 5 | 🔧 本书延时消息限于固定级别 | 2026 5.x 支持任意精度延时（Timer Message） |
| 6 | 🔧 本书幂等讲得轻 | 2026 应把「消费幂等」列为架构必做项 |
