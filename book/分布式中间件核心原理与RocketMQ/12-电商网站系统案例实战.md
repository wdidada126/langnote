### 12.3 下单 + RocketMQ 失败补偿（教学示意）

```java
// 教学示意，不参与构建：下单后发消息，消费端失败重试/进死信（呼应第 8 章）
@Transactional
public void createOrder(Order o) {
    orderMapper.insert(o);
    rocketMQTemplate.send("order.created", o);   // 本地事务+事务消息保证原子（8.2）
}

@RocketMQMessageListener(topic="order.created", consumerGroup="stock-cg")
public void onOrder(Order o) {
    try { stockClient.deduct(o); }               // 失败按 8.4 重试，最终进死信人工处理
    catch (Exception e) { throw new RuntimeException(e); }  // 触发重试
}
```

### 12.4 支付回调经 MQ 解耦（教学示意）

```java
// 教学示意，不参与构建：支付网关回调写消息，业务侧异步消费
@PostMapping("/pay/notify")
public String notify(PayCallback cb) {
    rocketMQTemplate.send("pay.callback", cb);   // 同步返回成功，业务异步处理
    return "success";
}
// 消费侧：更新支付单状态、触发发货等
```

## 版本演进

- **本书基于 Spring Cloud Alibaba（Nacos + Dubbo + Gateway）+ RocketMQ + Seata + Redis 的 2023 年主流栈**。
- **🔧 2026 视角：栈的微调**。Nacos/Dubbo/Sentinel/Gateway 仍是 Alibaba 套件主流；
  但 2026 年更强调 **可观测性（SkyWalking/Prometheus）** 与 **容器化部署（第 3 章）** 作为项目必配，
  原书 12.2 偏功能栈、轻运维可观测。
- **🔧 2026 视角：RocketMQ 5.x 接入**。若用 5.x，下单/支付解耦应走 **Proxy/gRPC 或 PopConsumer**，
  客户端接入方式比 4.x 更现代（见第 4、7 章）。
- **🔧 2026 视角：支付与一致性**。支付链路强一致可结合 **Seata TCC** 或「事务消息 + 对账」，
  不能只靠「发了消息就完事」，需补对账与幂等（第 8、10、11 章）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「下单直接同步调库存/积分」 | 应异步化 + 补偿（MQ），避免慢路径拖垮下单 |
| 2 | 「支付回调处理了就行」 | 回调须先 ACK 再异步处理，处理失败靠重试/死信 |
| 3 | 「项目 = 堆组件」 | 组件要按业务边界组装，且必备幂等/对账/可观测 |
| 4 | 🔧 本书偏功能栈轻运维 | 2026 必补可观测（SkyWalking/Prometheus）与容器化 |
| 5 | 🔧 本书未提 5.x 接入 | 2026 下单/支付解耦可走 Proxy/PopConsumer |
| 6 | 🔧 本书支付一致性讲得浅 | 2026 应补 Seata TCC / 对账 / 幂等 |
