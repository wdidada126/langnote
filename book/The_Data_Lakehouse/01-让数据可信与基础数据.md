# 01 让数据可信与基础数据（原书第 1–3 章）

> 对应真实目录：第 1 章 让数据可信 / 第 2 章 基础数据 / 第 3 章 如何避免不良数据。
> ⚠️ 章题来自豆瓣著录的真实目录；**章内小节划分与论述细节为依据 Inmon 公开著述（《数据仓库》系列、白皮书与博客）的重建**，非书中原文。凡"书中说"均指这一重建脉络与 Inmon 一贯立场的合取，不作为引文。

## 核心概念速览（中英对照）

- **数据湖仓** — data lakehouse：本书主题；Inmon 定义为"湖的存储 + 仓的纪律"的分层数据环境（详见 04 章）
- **数据仓库** — data warehouse：Inmon 毕生主张的集成、面向主题、时变、非易失的数据集合
- **数据湖** — data lake：无架构治理的原始堆放地，Inmon 眼中的"不良数据放大器"
- **数据可信** — trustworthy data：能对每个数字回答"从哪来、怎么变、可否重做"的属性
- **基础数据** — primitive / atomic data：最低粒度、未按任何用途加工过的事实数据
- **最低层次粒度** — lowest level of granularity：Inmon 仓库设计铁律：存最细，聚合可事后生成
- **跳板/缓冲区** — staging area：ETL 第一站，清洗与类型统一的隔离带
- **数据质量** — data quality：在 Inmon 体系中是架构属性（可回溯、可重做），不是口号
- **不良数据** — bad data：错误、重复、口径不一、无法溯源的数据的合称
- **信息供应链** — information supply chain：数据从源到消费者的流水线式组织方式（详见 08 章）

## 核心精讲

### 1. Inmon 的第一性主张：可信是"造"出来的，不是"洗"出来的

```
源系统A ─┐                      ┌─→ 报表(生产层)
源系统B ─┼→ staging → 集成/清洗 →┼─→ ML(近生产层)
源系统C ─┘   (唯一质检口)         └─→ 探索(砂仓)
```
（教学示意，不参与构建）

Inmon 对数据质量的理解和他对数据仓库的定义同源：**集成发生在写入路径（schema-on-write）上，一次集成、处处复用**。数据湖的诱惑恰恰相反——"先存下来，用的时候再说"。第 1 章（⚠️ 重建）大概率把这两条路线摆在一起：前者每次消费便宜、首次写入贵；后者首次写入便宜、每次消费贵且互相不一致。湖仓（04 章）就是他要的第三条路：**原始层照单全收（学湖的便宜），近生产/生产层严格集成（守仓的纪律）**。

### 2. 基础数据：粒度即期权

"基础数据"（第 2 章章题，英文语境对应 primitive data）是 Inmon 从 1992 年一路讲到晚年的概念：

- 定义：不带任何报表立场、记录业务事件最小事实的数据；
- 理由：**上层用途是未来的函数，粒度是当下的承诺**。存了原子级，任何聚合都是可重算的冗余；只存聚合，则未来新需求不可满足；
- 在湖仓语境下的新变化 ⚠️：原始层（raw）事实上替仓库承担了"永久保存最细数据"的角色，基础数据的概念从"仓库表"迁移到"近生产层的标准化细粒度事实"。这是 Inmon 晚年自我修订最明显的一处（对照他早年"湖里的数据没有架构就没有价值"的强硬说法）。

### 3. 如何避免不良数据：把质检做成供应链工序

第 3 章（⚠️ 重建）的路径应是"防治结合，以防为主"：

1. **唯一入口**：所有数据进供应链必须过 staging——类型统一、去重、参照完整性校验、码值映射。出口可以有 N 个，入口只能有一个；
2. **例外队列（quarantine）** ⚠️：不合格记录不静默丢弃，进隔离区挂账、有人认领——"丢数据比丢数据更贵"；
3. **可重做性**：任何一条生产层数字要能从原始层重放算出（这是 04 章原始层不可变设计的动机之一）；
4. **时间一致性**：源系统时钟、抽取时刻、装载口径三件事分开管理；Inmon 一贯强调仓库记录"事件事务时间 + 系统装载时间"双时间戳。

### 4. 为什么这三章要连着读

1 → 2 → 3 是一个论证三段论：大目标是**可信**（第 1 章）；可信的载体是**最细粒度的基础数据**（第 2 章）；可信的敌人是**不良数据**，防治手段是**架构+工序**（第 3 章）。后文第 4–9 章（数据类型→抽象→存储）回答"这套纪律搬到湖上要付什么工程代价"，第 10 章之后回答"值不值"。

### 5. 关键论断速记（⚠️ 依 Inmon 一贯立场重建，非书中原文）

可作为读书时对照原文的"预言清单"——若原书措辞与此不同，以原书为准并回来修订本节：

- 可信不是道德口号，是**工程可判定属性**：给定一个数字，能机械地回答"从哪来、怎么来、能否重做"；
- 粒度承诺在先、用途在后：**你不知道未来谁会要数据，但你知道他一定嫌粗**；
- 派生数据可以是缓存，不能是唯一出处（single source of truth 必须在基础数据上）；
- 集成点越少越可控：每多一个"入口"，质量事故的概率乘性增长；
- 湖仓对第 1–3 章的改动是**扩大原料仓**（raw 永久全存），而不是放松质检站（staging/集成的职责原样保留）；
- 不良数据的成本结构：一次错误 < 长期信任折价——所以可信要按"资产保值"立项。

### 6. 可信三要素的操作化检查单（教学工具 ⚠️）

把 1.2 的三要素变成可对任何"湖仓"系统打分的清单：

| 检查项 | 追问 | 不及格信号 |
| --- | --- | --- |
| 可溯源 | 报表数字能否点到近生产表、再点到 raw 对象？ | 血缘停在"某脚本产出" |
| 可重做 | 删除任一中间层，能否仅凭 raw+代码重建？ | 中间层含"手工修正"不可再生 |
| 口径一致 | 同名指标是否全企业单一出处？ | 各部门各自 SELECT 聚合 |
| 例外可见 | 被拒记录有账可查、有人认领吗？ | 无效行被静默过滤 |
| 双时间 | 事件事务时间与装载时间是否分开记录？ | 只有一个"更新时间" |
| 幂等 | 同输入重跑 N 次结果是否一致？ | 重跑产生重复/漂移 |

这张表后文反复使用：04 章检验三层瀑布、08 章检验集成工序、12 章对照表格式各自兑现了哪几行。

## Inmon 说法 vs 工程现实

| Inmon（⚠️ 重建立场） | 工程现实（已核实来源） |
| --- | --- |
| 唯一入口 staging 做质检 | 开放表格式时代，入口质检仍成立，但"staging"常实现为 bronze→silver 的 pipeline（见 [../Delta_Lake_Definitive_Guide/08-湖仓架构-Medallion.md](../Delta_Lake_Definitive_Guide/08-湖仓架构-Medallion.md)） |
| 基础数据存最细粒度 | 实现侧要防"细粒度小文件灾难"：compaction 是 Inmon 理论里不存在的工序（见 [../Engineering_Lakehouses_with_Open_Table_Formats/08-Compaction与表维护.md](../Engineering_Lakehouses_with_Open_Table_Formats/08-Compaction与表维护.md)） |
| 可重做=从原始层重放 | Delta time travel / Iceberg 快照回滚解决的是"表内重放"，跨层重放仍需业务自己保证幂等 ⚠️ |
| 不良数据靠架构防治 | 现代实践另加数据契约（data contract）与质量监控（如 Great Expectations 类工具），书中是否提及未核实 ⚠️ 🔧 |

## 常见误区

| 误区 | Reality |
| --- | --- |
| "数据湖也能可信，只要加个 catalog" | Inmon：catalog 只是描述，可信来自**写入路径上的集成工序**（08、11 章展开） |
| "基础数据 = 原始数据" | 基础数据已经过清洗集成；raw 是源样。混淆两者会把脏数据当资产 |
| "存了明细就不需要聚合层" | 明细解决"能不能算"，聚合解决"快不快、口径稳不稳"；生产层仍要有组织的派生 |
| "质量项目是阶段性的" | Inmon 视质量为供应链常设工序，一次性清洗在无架构环境下必然回潮 |
| "先建湖仓产品，可信自然有了" | 顺序颠倒：可信来自第 1–3 章的架构与工序，产品只是载体（04 章） |
| "细节数据没人用，纯成本" | 用没用到是期权行权问题；存不存是行权资格问题（06 章价值账） |
| "Inmon 反对数据湖所以本书是负面的" | 本书恰恰是收编之作：原始层保留湖的全部低成本与不可变优势 |
