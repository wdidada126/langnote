# 02 数据类型与数据抽象（原书第 4–5 章）

> 对应真实目录：第 4 章 不同类型的数据 / 第 5 章 数据抽象。
> ⚠️ 章题来自豆瓣著录的真实目录；**章内小节划分与论述细节为依据 Inmon 公开著述的重建**，非书中原文。

## 核心概念速览（中英对照）

- **数据类型** — types of data：Inmon 按"数据的原生形态"划分的类别，本书的展开单位（第 6–8 章各占一类）
- **结构化数据** — structured data：可用关系表与先行 schema 完整表达的数据
- **文本数据** — text data：自然语言书写、语义内嵌于字符串的数据
- **模拟数据** — analog data：连续物理量经采样/数字化得到的数据（物联网侧）
- **数据抽象** — data abstraction：让消费者不必感知数据的物理层次、格式与位置的分层遮蔽机制
- **层次抽象** — layering abstraction：raw/近生产/生产三层本身构成一种抽象台阶 ⚠️
- **格式无关性** — format independence：同一逻辑数据可落 Parquet/ORC/Avro 而消费者不觉察
- **架构（schema）与模式** — schema：对数据结构与约束的描述；Inmon 主张集成层的 schema 先行
- **引用数据/码表** — reference data：解释数据所需的值域与代码集合，跨类型数据的公共胶水
- **信息供应链** — information supply chain：不同类型数据汇入的同一条加工流水线（08 章）
- **模式与实例** — schema vs instance：类型层描述结构（schema），数据层承载事实（实例）——抽象把两者分开管理
- **口径** — measure definition / conformance：同一事实在不同消费者间保持一致的语义约定，抽象升档的伴随产物

## 核心精讲

### 1. 类型分类学是目录结构，也是架构承诺

原书目录里第 6–8 章（结构化、文本、模拟/IoT）并列在"数据类型与抽象"（第 4–5 章）之后——这个安排本身就是论点（⚠️ 重建解读）：**湖仓架构必须为每一类原生数据给出显式的入库通道**，而不是像通用数据湖那样"什么都是对象文件"。

```
        结构化(业务库/事务)   文本(文档/邮件)   模拟/IoT(传感器)
              │                    │                  │
              ▼                    ▼                  ▼
        [通道A: 抽取/CDC]    [通道B: 解析→实体抽取]  [通道C: 流式落地]
              └────────────────────┼──────────────────┘
                                   ▼
                     统一的 raw 层 → 近生产层 → 生产层
```
（教学示意，不参与构建；三条通道的具体名字为 ⚠️ 推定）

- **结构化数据**：Inmon 的老本行，直接进入集成供应链，schema 先行；
- **文本数据**：他的立场历来鲜明——**文本本身不进供应链，解析出的结构化事实才进**（原文保留在 raw 层供重解析）；这与"扔进湖里让 LLM 自己读"的 2020 年代主流做法正面冲突 🔧，是 03 章重点对撞点；
- **模拟/IoT 数据**：特征是价值密度极低、体量极大。Inmon 的处方（⚠️ 推定）：raw 层廉价全存，近生产层按事件模型化（时序事实表思路），生产层只存高价值聚合。

### 2. 数据抽象：Inmon 借用的其实是软件工程概念

第 5 章章题"数据抽象"在数据类图书中少见。⚠️ 重建其论证：

1. 抽象 = **接口与实现分离**。湖仓的消费者接口是"某层的某张表/某个目录条目"，实现是"对象存储上的一堆文件 + 表格式元数据"；
2. 三层瀑布是**抽象层级的实体化**：raw 层近乎无抽象（源系统的镜像），近生产层抽象掉源系统差异，生产层再抽象掉分析实现细节、只留业务概念；
3. 推论：**任何"跳过中间层直接读低抽象层"的行为都在消耗可信度**——这就是 04 章"瀑布禁令"的抽象论基础；
4. 与 OOP 的类比 ⚠️：schema 即接口签名，数据集成即多态实现统一，catalog 即接口注册表（这三条对应关系是本笔记的教学类比，非书中论述）。

### 3. 抽象层次与消费者匹配（预告第 12 章）

第 12 章章题"数据需要的层次"与本章构成"机制—需求"的对子：抽象提供台阶，层次需求决定谁站在哪级台阶上。报表站生产层、ML 特征站近生产层、数据考古站 raw 层——各得其所，且**不允许为便利而降层直读**（例外走砂仓流程，07 章）。

### 4. 分类学的裂缝（诚实记录）

- Inmon 的三分类对**半结构化**（JSON、XML、嵌套日志）归属含糊 ⚠️：按形态近文本，按消费方式近结构化。书中如何处理未核实；2026 年的工程答案通常是"表格式的 nested type + schema evolution"（见 [../Apache_Iceberg活用入門/04-Schema演化.md](../Apache_Iceberg活用入門/04-Schema演化.md)）；
- 对**向量数据/embedding** 这类 2023 年后的新原生类型，成书时点（原版年份未核实 ⚠️）大概率未覆盖 🔧，但它是"湖仓是 AI 基石"副标题下最实际的缺口。

### 5. 抽象失效的四种形态（⚠️ 教学归纳，用于自查）

第 5 章若把抽象讲透，反面清单应该长这样（本笔记归纳，供对照原书）：

| 失效形态 | 症状 | 违反的抽象原则 |
| --- | --- | --- |
| 泄漏（leak） | 消费者被告知"这列只在 2021 年前的分区里有" | 抽象应隐藏实现细节 |
| 旁路（bypass） | 报表直连 raw 文件路径 | 台阶塌陷（04 章瀑布禁令） |
| 分裂（fork） | 同一逻辑表有两套 schema 各自演化 | schema 即合同，合同不能有两份 |
| 腐化（rot） | 文档说一套、系统跑一套 | 接口与实现失同步（→ 11 章目录治理） |

### 6. 术语辨析：抽象 ≠ 聚合 ≠ 脱敏 ≠ 建模 ⚠️

Inmon 的"数据抽象"极易与相邻概念混淆，先划清边界（辨析为本笔记贡献）：

- **抽象 vs 聚合**：聚合是粒度变换（明细→汇总），抽象是**认知负担的转移**——生产层既聚合又抽象，近生产层只抽象不聚合；
- **抽象 vs 脱敏**：脱敏改变内容以保护隐私，属安全侧工序；抽象不改变语义内容，只改变"你需要知道多少"；
- **抽象 vs 建模**：建模选择"用什么结构表达业务"（3NF/维度），抽象决定"结构暴露给谁看几层"——一个谈表达，一个谈可见性；
- **抽象 vs 虚拟化**：视图是虚拟抽象（读时展开），分层表是物理抽象（写时固化）；湖仓三层是物理抽象为主——因为 Inmon 要的是**可审计的加工记录**，虚拟层不留加工痕迹。

## 常见误区

| 误区 | Reality |
| --- | --- |
| "数据抽象=逻辑建模" | Inmon 此处指**分层遮蔽**，逻辑建模只是其中一环；混淆会低估 raw 层的存在意义 |
| "类型不重要，湖都能装" | 能装≠能供货：三类数据的价值密度、时效、schema 演化速率完全不同，共用一条无差别管道必然在某一类上翻车 |
| "半结构化没有 schema 所以是自由的" | 半结构化只是把 schema 检查推迟给消费端；在近生产层仍需显式化（03 章细化） |
| "抽象越高越好" | 对探索性消费者，高抽象层丢信息；这就是近生产/raw 层作为合法抽象档位存在的理由（07 章） |
| "分类是学术游戏" | 分类=架构承诺：每类给不给通道、走哪条通道，直接决定该类数据可不可信 |
| "统一格式（Parquet）就消除了类型差异" | 容器统一≠语义统一：IoT 乱序与合同条款的坑不在文件后缀里 |
| "多几层抽象总没坏处" | 每层都有维护与延迟成本；Inmon 的三层是给"承诺等级"定价，不是层数崇拜 |
