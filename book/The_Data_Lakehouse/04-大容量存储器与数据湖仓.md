# 04 大容量存储器与数据湖仓（原书第 9 章）

> 对应真实目录：第 9 章 大容量存储器与数据湖仓。
> 定位：**全书理论枢纽**。前 8 章的铺垫（可信、类型、抽象）在此收拢成一个架构，后 9 章的应用（集成、分析、目录）由此展开。
> ⚠️ 章题来自豆瓣著录的真实目录；**三层瀑布、ODS、砂仓等具体机制是依据 Inmon 公开著述（其博客与白皮书中的 lakehouse 架构论述）重建**，章节编号与措辞非书中原文。

## 核心概念速览（中英对照）

- **数据湖仓** — data lakehouse：本书核心概念；Inmon 版定义为"大容量廉价存储 + 分层集成纪律"的数据环境
- **大容量存储** — big storage：对象存储/云廉价磁盘，使"原始数据永久全存"首次在成本上可行
- **原始数据** — raw data：源系统/文件原样落地、不可变的第一层，一切重做的证据底座
- **近生产数据** — near-production data：已清洗集成、可被分析/ML 消费但未冻结的中间层
- **生产数据** — production data：经架构约束冻结、面向报表/API/SLA 的最高可信层
- **数据瀑布** — data waterfall：数据只能 raw→近生产→生产单向流动、禁止绕层倒灌的流控原则 ⚠️
- **数据仓库** — data warehouse：生产数据在传统架构中的物理载体；Inmon 视湖仓为其在湖上的延续
- **数据湖** — data lake：只有 raw 层、缺上层纪律的形态——Inmon 认为湖仓是对湖的"补完"而非"替代性否定"
- **操作型数据存储** — ODS / Operational Data Store：面向近期运营的集成层；⚠️ 任务书作"ODSO"，Inmon 通写 ODS
- **架构内建** — architecture-driven：湖仓与湖的分水岭：有无强制的层次与集成约定

## 核心精讲

### 1. 一张主图：Inmon 三层瀑布

```
  ┌─────────────────────────────────────────────┐
  │  生产层 production data                        │  ← 报表/API/SLA，口径冻结，最高可信
  ├─────────────────────────────────────────────┤
  │  近生产层 near-production data                 │  ← 清洗+集成+建模；ML 特征、分析取数
  ├─────────────────────────────────────────────┤
  │  原始层 raw data（不可变、只追加、永久保留）      │  ← 源系统镜像；重做的证据底座
  └─────────────────────────────────────────────┘
        ▲              ▲              ▲
     结构化源        文本源         IoT/模拟源   （03 章三通道在此汇入 raw）
   —— 数据瀑布：只允许 下→上 逐级加工，禁止跨层直读/倒灌 ——
（教学示意，不参与构建；层名为常规英文回译 ⚠️）
```

这张图是 Inmon 把 30 年仓库思想"移植到湖上"的产物，三个设计选择环环相扣：

- **raw 不可变 + 永久**：因为便宜存储才付得起；因为要"可重做"（01 章）所以必须留；
- **近生产层是主角**：所有集成、清洗、类型对齐、参照对齐都在这里发生——**这就是 Inmon 的 staging/仓库集成层在湖上的化身**；
- **生产层是承诺**：对业务口径与 SLA 的冻结，等价于旧日"发布报表所依据的那份数"。

### 2. 定义之争：湖仓是架构，不是产品

第 9 章（⚠️ 重建）几乎必然要处理一个混乱：市面上"湖仓"要么是 Databricks 式（表格式 + 统一引擎），要么是云厂商 PaaS 名。**Inmon 的定义学是功能性的**：一个数据环境算不算湖仓，取决于它是否具备上图的层次与集成纪律，而不取决于它用了 Delta 还是 Iceberg、跑在哪家云上。由此得出他著名的口吻：**"没有架构的湖仓只是一个更贵的数据湖。"**（⚠️ 这句是按其一贯立场复述的示意，非引文）

### 3. 数据瀑布：把"可信"写成流向纪律

瀑布（data waterfall）概念承接他的信息供应链（08 章）：

- **单向性**：加工产物可回指其输入（沿 raw→近生产→生产的正向血缘），杜绝"生产层数字被下游手工改回湖"的倒灌；
- **禁跨层直读**：报表不应 SELECT 裸 raw——那是 02 章"抽象台阶"的兑现；例外走砂仓（9.5）；
- **可重放**：任一层可从其下层重建；这是"可重做"三要素的架构表达。
- ⚠️ 注意：Inmon 的"瀑布"与软件工程贬义的"瀑布模型"无关，他是正面使用这个比喻的（流水线的级间约束），阅读时别带先入评价。

### 4. ODS 与数据砂仓的归位 ⚠️

- **ODS（操作型数据存储）**：Inmon 体系里的老牌组件——面向近期、运营视角、集成度低于仓库。湖仓语境下（⚠️ 推定）它落在 raw 与近生产之间偏运营侧，服务"当天/近实时"的操作型查询，与生产层的"分析口径"分工不同；
- **数据砂仓（data sandpit）**：给数据科学家/分析师的"自由玩数区"。关键约束：**砂仓允许降层取数（可读 raw/近生产），但产出要进生产必须回到正规瀑布重新加工**——自由探索与口径冻结被这道墙分开。砂仓与 05 章"数据工程"、09 章"分析"直接相关。

### 5. 三方辨析：同一堆磁盘，三种灵魂

| 维度 | 数据湖 | 云数仓 | Inmon 湖仓 |
| --- | --- | --- | --- |
| 存储 | 廉价对象存储 | 专用/托管 | 廉价对象存储 |
| schema | on-read（读时） | on-write（写时） | **分层：raw 无、上层 on-write** |
| 集成 | 无强制 | 装载时强制 | **近生产层强制** |
| 可信度 | 消费者自担 | 平台保证 | 架构（瀑布+层）保证 |
| 主要风险 | 变数据沼泽 | 成本/锁定 | 落地复杂、需真做集成 |

### 6. 对 AI/ML 的呼应（副标题"bedrock"）⚠️

三层模型给 ML 的价值（⚠️ 重建）：raw 提供**训练数据考古权**（模型要重训时能取回当初的原始分布）、近生产提供**特征**、生产提供**上线后监控基线**。副标题把湖仓抬到"AI/ML 与 data mesh 基石"的高度，其论据正是这一层供给关系（11 章收尾 mesh 侧）。

### 7. 三层设计的三个不变量（⚠️ 教学提炼）

无论用什么产品实现，Inmon 式湖仓的三层必须同时满足以下三条才算成立——这是本笔记给 04 章的"验收标准"：

1. **证据不变量**：上层任一数据可追溯到下层输入（无血缘的层视为不存在）；
2. **方向不变量**：加工只沿 raw→近生产→生产发生（倒灌与跨层直读都是架构违规）；
3. **重建不变量**：任一层可仅由其下层+代码完整重建（重建不了=该层混入了不可再生的私货）。

三条各对应一种腐败形态：断链、旁路、夹带。治理动作即围绕这三处做文章。

| Inmon（⚠️ 重建立场） | 工程现实（已核实来源） |
| --- | --- |
| 三层是逻辑架构，与实现无关 | 落地时"层"通常=表格式上的表/命名空间；Medallion bronze/silver/gold 与其三层近乎同构（[../Delta_Lake_Definitive_Guide/08-湖仓架构-Medallion.md](../Delta_Lake_Definitive_Guide/08-湖仓架构-Medallion.md)） |

## 常见误区

| 误区 | Reality |
| --- | --- |
| "买了带表格式的湖就是湖仓" | Inmon：缺分层集成纪律与流向约束，只是"有事务的湖" |
| "raw 层既然不可变，就不用管质量" | raw 的正确性由"忠实镜像源系统"定义；质量在近生产层治理 |
| "生产层=旧的数仓，是多余的历史包袱" | 生产层承担口径冻结与 SLA，是"可信"承诺的落点，非包袱 |
| "瀑布=过时的瀑布开发" | 此处指数据级间单向流动，与软件开发过程模型无关，取其"质检流水线"义 |
| "砂仓破坏纪律，应禁止" | Inmon 给砂仓留了合法出口：可读低层，但产出回归生产须重走瀑布 |
