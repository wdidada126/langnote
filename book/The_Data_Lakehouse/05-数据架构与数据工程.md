# 05 数据架构与数据工程（原书第 10 章）

> 对应真实目录：第 10 章 数据架构与数据工程。
> ⚠️ 章题来自豆瓣著录的真实目录；**章内小节与论述为依据 Inmon 公开著述的重建**，非书中原文。标注 🔧 处为按 2026 年工程现状补充。

## 核心概念速览（中英对照）

- **数据架构** — data architecture：规定数据如何在各层间流动、存储、演化的总体设计，区别于单个库表的物理设计
- **数据工程** — data engineering：沿信息供应链把数据从低层加工到高层的施工活动与岗位
- **架构 vs 设计** — architecture vs design：Inmon 的一贯区分——架构定"层与流向"，设计定"某张表怎么建"
- **信息供应链** — information supply chain：数据架构的骨架，04 章三层瀑布的组织化表达
- **跳板** — staging：数据工程的第一道工序所在，架构上对应 raw→近生产的转换闸口
- **物理数据库设计** — physical database design：被 Inmon 明确排除在"架构"之外的下游活动
- **数据建模** — data modeling：把集成后的数据组织成主题/维度结构，主要发生在近生产层
- **管道** — pipeline：数据工程交付物的实现单元 ⚠️ Inmon 少用此词但含义对应供应链工序
- **元数据驱动** — metadata-driven：以元数据（而非硬编码）驱动集成与血缘 🔧
- **架构治理** — architecture governance：确保各工程活动不破坏瀑布与分层约束的机制

## 核心精讲

### 1. 数据架构的第一定义：层与流向

Inmon 谈"架构"有强烈的个人烙印（⚠️ 重建）：**架构 = 数据在组织里的宏观流动结构**，不是某个系统的技术方案。在他眼里，一个企业哪怕换了三次技术栈，只要"源系统→集成→仓库→集市"的流向没变，架构就没变。落到本书，就是 04 章的三层瀑布——所以第 10 章（在结构上紧跟第 9 章）的任务是把那张图**从"数据视图"翻译成"职责视图"**：谁来保证流向不被破坏、谁来施工。

### 2. 架构 ≠ 物理设计：一条被反复强调的红线

| 数据架构管的事 | 物理设计管的事 |
| --- | --- |
| 有几层、层间允许什么流动 | 一张表用哪种文件/分区/索引 |
| 集成在哪发生、口径在哪冻结 | 主键、分区键、聚簇键怎么选 |
| 数据保留多久（raw 永久？归档？） | 冷热分层、生命周期具体阈值 |
| 跨源业务键如何对齐 | 某个 JOIN 如何加速 🔧 |

Inmon 的批评对象（⚠️ 推定延续他一贯火力）：把"架构师"和"某某数据库专家"混为一谈——工具厂商语境里的 architecture 常退化为 product selection。湖仓尤其容易中招：买了表格式≠有了数据架构（呼应 04 章"湖仓不是产品"）。

### 3. 数据工程：架构的动词形式

数据工程（data engineering）在 Inmon 笔下不是 2015 年后才被发明的新岗位，而是他一直说的"沿着信息供应链施工的人"。⚠️ 重建其工序划分与三层对齐：

```
数据工程工序（供应链视角）      对应层/瀑布
  抽取/接入 (extract/ingest)      源 → raw
  落地封存 (land & freeze)        raw（不可变）
  清洗/转换 (cleanse/transform)   raw → 近生产
  集成/建模 (integrate/model)     近生产
  口径发布 (publish)              近生产 → 生产
  监控/重做 (monitor/replay)      贯穿（可信保障）
```
（教学示意，不参与构建；工序名为常规英文回译 ⚠️）

- 与 🔧 现代管道工程（Airflow/dbt/Flink）的差别：Inmon 视角强调**每道工序都服务同一套分层约束**，而非"把数据搬过去就行"；工具可换，瀑布位不变。
- staging（01 章）在这里升格为架构组件：它是"源 → 近生产"之间的隔离带，把源系统的变化性挡在集成层之外。

### 4. 工程、建模、管理的三角 ⚠️

Inmon 会把三者分清（⚠️ 重建）：

- **数据建模**决定近生产/生产层的结构（主题、维度、粒度），是"工程要照着做的设计图"；
- **数据工程**把建模与集成规则落成可运行、可重做的加工链；
- **数据管理/治理**（→ 11 章数据目录）定口径与规则。
- 反模式：让工程在 ETL 代码里"顺手"决定业务口径——口径应显式建模、可审计（这也是他反对"降层直读"的组织学理由）。

三角色的责任落点（⚠️ 教学归纳）：

| 角色 | 对哪层负责 | 交付物 | 越界信号 |
| --- | --- | --- | --- |
| 数据架构师 | 层与流向本身 | 瀑布图、集成点、保留策略 | 陷入选型争论、不过问口径 |
| 数据建模师 | 近生产/生产结构 | 主题模型、粒度声明、口径定义 | 模型被工程"顺手"改动 |
| 数据工程师 | 工序实现 | 可重放、幂等的管道 | 代码里长出业务规则 |

### 5. 湖仓时代的新命题（⚠️ 重建，可能超出原书表述）

04 章三层进入工程日常后，架构/工程多出几件事：

1. **不可变 raw 的工程约束**：不能 UPDATE，只能追加 + 表格式时间旅行——重做从"改数据"变成"重放管道"；
2. **多引擎读写同一层**：Spark 写、Flink 流写、Trino 查——工程要保证提交不互踩（→ 12 章：表格式的 ACID 就是干这个的）；
3. **成本进入架构决策**：raw 永久保留的可行性依赖存储/请求费模型（🔧 见 [../湖仓架构大规模数据平台的设计和实现/03-存储湖仓架构的核心.md](../湖仓架构大规模数据平台的设计和实现/03-存储湖仓架构的核心.md)）；
4. **元数据驱动 🔧**：层间转换规则、血缘、质量断言尽量用元数据表达，使重做与审计机械化。

### 6. 架构反模式（⚠️ 教学归纳）

- **点对点蜘蛛网**：绕过分层直接 N×N 互连，集成无法复用、无法审计；
- **降层直读**：报表直连 raw——抽象台阶塌陷（02 章）；
- **ETL 藏口径**：业务定义埋在脚本里，改一处口径要全链路考古；
- **砂仓转正**：探索产物未走瀑布就接生产——04 章砂仓墙被拆。

## Inmon 说法 vs 工程现实

| Inmon（⚠️ 重建立场） | 工程现实（已核实来源） |
| --- | --- |
| 架构=层与流向，稳定 | 现代"数据架构"常被理解成技术栈选型；Inmon 定义更窄更深，二者对话时需先对齐词义 |
| 数据工程=供应链施工 | 落地为可编排、可观测的 pipeline；调度/血缘/重放是显式工程件（[../Apache_Hudi_Definitive_Guide/08-基于HudiStreamer构建数据湖仓.md](../Apache_Hudi_Definitive_Guide/08-基于HudiStreamer构建数据湖仓.md)） |
| 多引擎并发靠约定 | 真正解决靠表格式乐观并发（[../Engineering_Lakehouses_with_Open_Table_Formats/06-事务与并发写.md](../Engineering_Lakehouses_with_Open_Table_Formats/06-事务与并发写.md)）；Inmon 理论层不覆盖该机制 |
| 架构治理保瀑布 | 实现侧靠 catalog + 权限 + 血缘 + CI 校验，是治理产品而非架构自带（[../湖仓架构大规模数据平台的设计和实现/06-湖仓架构中的数据与AI治理和安全.md](../湖仓架构大规模数据平台的设计和实现/06-湖仓架构中的数据与AI治理和安全.md)） |

## 常见误区

| 误区 | Reality |
| --- | --- |
| "选了湖仓产品就有了数据架构" | 产品给的是能力，架构是"层与流向"的约束，仍要自己立 |
| "数据工程就是写 ETL 脚本" | Inmon 语境：工程工序服务于分层与可信，脚本只是载体 |
| "架构师=最懂数据库调优的人" | 物理设计是架构的下游；把二者等同会导致架构被工具牵着走 |
| "口径写在 ETL 里更省事" | 短期省事、长期不可审计；口径应显式建模并可从生产层回溯 |
