# 10 软数据与描述性数据（原书第 15–16 章）

> 对应真实目录：第 15 章 软数据 / 第 16 章 描述性数据。
> ⚠️ 章题来自豆瓣著录的真实目录；**"软数据""描述性数据"在 Inmon 著作中含义固定但外延宽，本章小节与两处定义为依据其公开著述 + 常规数据管理术语的重建**，非书中原文；细分口径未核实，全章带 ⚠️。

## 核心概念速览（中英对照）

- **软数据** — soft data：邮件、通话记录、合同、社交内容、备注等承载业务语境但形态松散的数据，Inmon 长期用此词指代"难以量化却富含语义"的那一类
- **描述性数据** — descriptive data：关于数据的数据——元数据、参考数据、码表、命名与口径说明 ⚠️（细分未核实）
- **元数据** — metadata：描述数据的内容、来源、结构、血缘的数据（与 11 章数据目录直接相关）
- **参考数据** — reference data：解释业务数据所需的值域与代码集合（码表、状态字典），02 章已出现
- **硬数据** — hard data：与软数据对举，指结构规整、可直接量化的事务型数据（术语常规回译 ⚠️）
- **语境/语义** — context / semantics：软数据的核心价值——同一事实在不同语境下含义不同
- **数据画像** — data profiling：对软/低结构数据摸清结构、分布、质量的先期工序 🔧
- **业务术语表** — business glossary：描述性数据的人读面，口径对齐的载体
- **血缘** — lineage：数据从源到消费者的可追溯路径（描述性数据的关键一类）
- **置信度** — confidence：软数据抽取结果的可信程度标注（03 章文本通道的延续）
- **主数据管理** — master data management（MDM）：组织级主数据/参考数据的维护与分发机制，描述性数据的运营形态 ⚠️ 术语按常规
- **数据保鲜/腐烂** — data rot：描述性数据与真实系统脱节的过程——第 6 节自查单要拦截的头号敌人

## 核心精讲

### 1. 软数据：Inmon 给"定性信息"留的位置（第 15 章 ⚠️）

"soft data"是 Inmon 偏爱多年的术语。在他的用法里（⚠️ 重建），软数据**不等于**技术上所有非结构化大数据，而特指**含有业务判断与语境、但难以直接塞进事实表**的那类：客户经理备注、工单往来邮件、质检员描述、合同条款、投诉原文。它们的价值在于——**很多决策的真实依据其实是软数据，只是过去没法存、没法算**。

湖仓对软数据的意义（⚠️ 推定，接第 9 章）：便宜存储 + 灵活 schema 让"先存原文、后补结构化"首次可行——这正是 03 章文本通道"raw 封存原文、近生产落解析产物"的两步法在软数据上的复用。区别在软数据更强调**语境不可丢**：解析成结构化的同时要留指针回原文，否则"为什么这么判断"的证据链断裂。

处理路径（⚠️ 教学化）：

```
软数据原件(邮件/备注/合同) → raw 层(原文+语境元数据封存)
   → 抽取(实体/情感/意图/关键字段, 带置信度) → 近生产层(结构化事实+回指原文指针)
   → 生产层(可签字的派生指标, 如投诉根因分布)
```
（教学示意，不参与构建）

### 2. 描述性数据：让集成"知道什么算对"（第 16 章 ⚠️）

第 16 章紧接软数据，主题转向"关于数据的数据"。⚠️ 依 Inmon 一贯用法，描述性数据大致覆盖三类（细分口径未核实）：

- **元数据（metadata）**：结构、来源、血缘、时效——"这条数据从哪来、怎么来的"；
- **参考数据（reference data）**：码表、值域、状态字典、组织/产品主数据——"这个代码/术语是什么意思"；
- **业务口径/术语（glossary）**：指标定义、计算规则——"收入到底怎么算"（05、08 章反复出现的"口径显式化"）。

为什么单列一章（⚠️ 按其理论）：**描述性数据是信息供应链的"质量标准与标签"**。第 8 章集成之所以能判定"对齐/没对齐"，全靠参考数据与口径这些描述性数据在先。没有可信的描述性数据，三层瀑布就退化成"三层不知道自己在干嘛的拷贝"。

### 3. 两章的隐秘连接：软数据最难被描述 ⚠️

Inmon 把 15、16 相邻放置（⚠️ 推解读）暗含一个张力：**软数据的语义是模糊的，而描述性数据要求语义确定**。当"客户情绪=负面"这类抽取结果要登记进目录、纳入参考数据体系时，置信度、版本、口径都要被描述——这是软数据对治理能力出的难题，直接把话题推向第 17 章数据目录。

### 4. 描述性数据自身要治理 ⚠️

一个 Inmon 式提醒：码表/术语表失修是**口径漂移的源头**。源系统偷偷加了一个状态码、字典没更新，近生产层集成就会静默错配。所以描述性数据不是"文档写完放着"，而是随供应链持续校验的活工件（🔧 现代做法：参考数据管理 MDM + 变更评审 + schema/值域 drift 检测）。

### 5. 软数据登记最小字段集（⚠️ 教学清单）

软数据进目录（11 章）时至少要比硬数据多登记这些字段——因为它的语义是抽取出来的、会出错的：

| 字段 | 为什么必需 |
| --- | --- |
| 原文指针 + 原文哈希 | 证据链闭合；原文被改可发现 |
| 抽取器标识与版本 | 换模型后圈定受影响产物 |
| 置信度/复核标记 | 让下游按可信度分级使用 |
| 语境标签（渠道/文体/时域） | 同一抽取器在不同语境精度不同 |
| 人工抽检结果 | 置信度是自称的，抽检是他称的 |

### 6. 描述性数据三分法自查单（⚠️ 教学）

对应 16.1 的三类，每类一个致命追问：

- **元数据**：血缘是自动采集还是手工维护？（手工血缘必腐烂——17 章目录的可信度问题在此埋下）
- **参考数据**：码值新增/废弃有没有变更流程与生效日期？（无日期=历史数据无法正确重释）
- **业务口径**：口径定义与其生产层实现（SQL/模型）是否绑定并可 diff？（定义与实现脱节是"口径漂移"的工程学定义）

三类共同构成 08 章集成"知道什么算对"的依据；任何一类缺位，信息供应链就在盲运行。

### 7. 与 AI 语料管理的历史性交汇 🔧（超出原书范围）

2023 年后"语料/数据集卡片（datasheet/dataset card）"运动实质上是在给软数据补描述性数据登记规范——字段清单与第 5 节高度神似（来源、版本、抽取方式、抽检）。可以视为 Inmon 第 15–16 章思想在 LLM 时代的再发现：**语料不可描述，即不可审计**。原书是否触及此关联未核实 ⚠️。

## 常见误区

| 误区 | Reality |
| --- | --- |
| "软数据=不结构化=不重要，先不管" | 很多决策的真实依据是软数据；Inmon 给它专门章节正名 |
| "描述性数据就是技术元数据" | 还含参考数据与业务口径——三者缺一，集成无从判对错 |
| "把邮件直接当事实表用" | 必须先抽结构化事实且保留回指原文的指针，否则证据链断 |
| "码表/术语表建一次就够用" | 描述性数据失修=口径漂移源头，需持续治理 |
| "置信度是模型内部指标，与治理无关" | 登记并抽检置信度，软数据才敢进近生产层（第 5 节） |
| "参考数据和主数据是一回事" | 参考数据是值域/码表、主数据是核心业务实体；两者都是描述性数据但治理节奏不同 ⚠️ 辨析为本笔记补充 |
