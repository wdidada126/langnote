# 08 数据湖仓中的数据集成（原书第 13 章）

> 对应真实目录：第 13 章 数据湖仓中的数据集成。
> 定位：信息供应链的"工艺章节"——raw→近生产→生产之间每一次搬运如何做到可信。
> ⚠️ 章题来自豆瓣著录的真实目录；**章内机制（集成类型、瀑布工序、例外处理）为依据 Inmon 公开著述的重建**，非书中原文。🔧 处为本笔记补充的现代实现件。

## 核心概念速览（中英对照）

- **数据集成** — data integration：把多源数据在业务键、口径、粒度、时间四个维度对齐的过程，Inmon 体系的中心工序
- **信息供应链** — information supply chain：集成活动的组织形态——像实业供应链一样有入库质检、加工工序、出货标准
- **瀑布式数据流** — waterfall（data flow）：集成沿层逐级发生、每级只对下一级负责（04 章流向纪律的工艺版）
- **跳板/缓冲区** — staging：入库质检站：清洗、类型统一、码值映射都在此完成（01 章组件的工艺化）
- **实体解析/同一化** — entity resolution：判定"不同源里的同一个人/账户/设备"的集成难题 ⚠️ 术语回译
- **参照数据对齐** — reference data conformance：跨源码表/值域映射，口径一致的前提
- **全量 vs 增量** — full load vs incremental：两种装载节奏，湖仓时代增量（CDC）地位上升 ⚠️/🔧
- **例外队列** — exception/quarantine queue：不合格记录的挂账区，集成工序的"不良品隔离带"
- **可重放** — replayability：集成失败或被质疑时可从 raw 重跑复现——不可变 raw 存在的工艺理由
- **数据版本化** — data versioning：每次集成的输入/输出都有版本对应 🔧 表格式时间旅行给了实现

## 核心精讲

### 1. 集成为什么独占一章

第 9 章给骨架（三层），第 12 章给需求（层次），第 13 章（本章）回答**肌肉怎么动**：数据如何从低层被可信地搬到高层。Inmon 的一贯论断（⚠️ 重建）：**"集成"是仓库/湖仓区别于归档、缓存、数据集市的本质属性**——没有集成纪律的"湖仓"只是带目录的文件系统。

### 2. 信息供应链：一个贯穿 Inmon 职业生涯的比喻

```
实业供应链                    信息供应链（湖仓版）
  原材料入库      ──→          raw 层落地封存（只追加、不修改）
  来料质检        ──→          staging：清洗/去重/类型统一/参照映射
  加工装配        ──→          近生产层：实体解析、口径对齐、建模
  成品检验+出厂    ──→          生产层：口径冻结、SLA 承诺、发布
  批次追溯        ──→          血缘 + 可重放（raw→生产全链路）
  不良品隔离区     ──→          例外队列（挂账、认领、返工）
```
（教学示意，不参与构建）

比喻的要害在**可追责**：每道工序有输入输出、有质检标准、有不良品处置流程——"数据集成"因此从"写脚本"升格为"运营一条流水线"。

### 3. 四类集成难题（⚠️ 按其理论归纳）

1. **键（identity）**：同一业务实体在不同源有不同标识 → 实体解析/主数据映射；IoT 场景里是"设备台账即主数据"（03 章）；
2. **口径（conformance）**："收入""活跃"跨部门定义不同 → 参照数据对齐 + 在集成层强制单一口径（05 章"口径不藏在 ETL 里"）；
3. **粒度（granularity）**：源 A 记到订单行、源 B 记到订单头 → 统一到最细可行粒度再聚合——基础数据原则（01 章）的工艺版；
4. **时间（temporal）**：抽取时刻、业务发生时刻、口径生效时刻三者错位 → 双时间戳、SCD 类技术。🔧 实现细节见 [../Delta_Lake_Definitive_Guide/10-设计模式-CDC与SCD.md](../Delta_Lake_Definitive_Guide/10-设计模式-CDC与SCD.md)。

### 4. 瀑布工序：箭头上的工程

- **raw→近生产**：解码/解析（03 章三通道各自的前置工序）+ staging 质检 → 输出清洗后的原子事实；
- **近生产→生产**：口径物化（指标/聚合/集市投影）+ 发布评审；
- **每个箭头都要求**：幂等（重跑同输入得同输出）、可重放（raw 不变）、可审计（版本与血缘对应 🔧）；
- ⚠️ 诚实标注：原书是否给出幂等/重放的具体机制未知（Inmon 通常停在原则层）——机制由表格式与编排系统提供，见 12 章对照。

### 5. 增量/CDC：节奏变了，质检口没变

Inmon 的仓库年代以批为主（夜间窗口）；湖仓时代流式与 CDC 成为默认 ⚠️/🔧。他的原则在增量下如何自洽（⚠️ 重建推演）：

- 瀑布的**级**不变：CDC 流也要先落 raw（变更日志原样封存），再进近生产；
- 变化的是**驻留时间**：从 T+1 到分钟级——"新鲜"不能以跳过质检为代价（现实中"入湖即清洗"的直写模式恰是 Inmon 会批评的绕开 staging）；
- raw 保留 CDC 日志使"从任意检查点重放"成为可能——🔧 对应 Hudi/Delta 的增量查询与流式增量摄取（[../Apache_Hudi_Definitive_Guide/10-构建端到端的湖仓解决方案.md](../Apache_Hudi_Definitive_Guide/10-构建端到端的湖仓解决方案.md)）。

### 6. 失败模式清单 ⚠️（教学归纳）

| 失败模式 | 症状 | Inmon 式解药 |
| --- | --- | --- |
| 静默丢数 | 对不上账、无人知晓 | 例外队列 + 条数/金额守恒校验 |
| 口径漂移 | 同名指标多版本并存 | 口径在集成层冻结，生产层单一出处 |
| 倒灌 | 下游修正值手写回低层 | 瀑布单向性 + 修正走上游重放 |
| 砂仓转正 | 实验表直接接报表 | 回归瀑布重加工（07 章单向阀） |
| 绕层集成 | 报表直连源库/湖 | 权限与血缘把直读显性化并收费 |

### 7. 集成成熟度分级（⚠️ 教学量规，非书中内容）

给"信息供应链"一个可自评的阶梯，用于判断自己的湖仓离 Inmon 标准还差几级：

| 级别 | 特征 | 典型症状 |
| --- | --- | --- |
| L0 直连 | 消费者各连各的源 | 口径以人头计 |
| L1 集中堆放 | 有统一 raw 层，无加工纪律 | "贵而无值的湖"（04 章批评的对象） |
| L2 单点清洗 | 有 staging，但只有部分流经 | 旁路数据与正规数据互不认识 |
| L3 全链供应链 | 一切生产数据必经 raw→staging→近生产→生产；例外队列运转 | 达到 Inmon 及格线 |
| L4 可重放机械化和 | 血缘/版本/幂等使重做与审计是常规操作而非英雄行为 | 可信成为默认属性 |

多数自称湖仓的系统停在 L1–L2：**有层的形状，没有层的约束**。第 13 章的工艺清单正是 L2→L3 的搬迁手册（⚠️ 本笔记的定位类比）。

## 常见误区

| 误区 | Reality |
| --- | --- |
| "ELT 时代 ETL 已死，先入仓再转换" | Inmon：转换位置可谈，**质检口与级间约束不可省**；ELT 只是把 T 挪进近生产层做 |
| "集成=工具选型（跑 Airflow 还是 DataX）" | 集成是语义工程（键/口径/粒度/时间），工具只是载体 |
| "有了 CDC 就可以取消 staging" | CDC 改变的是节奏；staging 的职责（隔离源变化）由 raw+近生产层继续承担 |
| "上游脏了先凑合用，回头再修" | 无例外队列的"回头再修"=口径漂移的制度化 |
