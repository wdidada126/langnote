# 11 数据目录与架构演化（原书第 17–18 章）

> 对应真实目录：第 17 章 数据目录 / 第 18 章 数据架构的演化（末章）。
> ⚠️ 章题来自豆瓣著录的真实目录；**章内论述为依据 Inmon 公开著述（含其对 catalog、演化式架构、data mesh 的一贯评论）的重建**，非书中原文。第 18 章与副标题"data mesh"的关系为 ⚠️ 推定。

## 核心概念速览（中英对照）

- **数据目录** — data catalog：登记各层数据资产、结构、口径、血缘与所有者（owner）的索引系统——湖仓的"地图"
- **元数据仓库** — metadata repository：Inmon 老牌概念：目录的存储底座，集中管理描述性数据（16 章）
- **血缘** — lineage：数据元素间的加工依赖链，瀑布可审计性的记录形态
- **影响分析** — impact analysis：改一处源/口径会波及哪些下游——目录的核心查询
- **架构演化** — evolution of data architecture：Inmon 名命题：架构是"渐进生长"（grow incrementally）出来的，不是一次设计到位
- **分而治之/增量交付** — piecemeal growth：一次只建一个主题域，边用边长——他与 Kimball 少数一致的方法论之一
- **数据网格** — data mesh：组织级的领域自治+数据产品化；副标题将其与湖仓并置，Inmon 立场是"mesh 需要湖仓做底座" ⚠️
- **数据产品** — data product：mesh 的交付单元；在 Inmon 视角≈生产层某主题的正式对外供数 ⚠️ 映射为笔记推定
- **联邦治理** — federated governance：mesh 的治理模式，与 Inmon 中央供应链存在张力 ⚠️
- **发现性** — discoverability：消费者找到"对的层的对的数据"的能力——目录的 KPI
- **语义层** — semantic layer：把口径定义集中托管、供工具消费的服务层，目录的业务面延伸 🔧
- **领域所有权** — domain ownership：mesh 术语：数据产品归业务领域负责；Inmon 式目录同样要求每层资产有 owner ⚠️

## 核心精讲

### 1. 数据目录：三层瀑布的索引面（第 17 章 ⚠️）

Inmon 谈目录从来不是"工具推荐"，而是**架构必件套件**（⚠️ 重建）：

- 04 章的瀑布承诺"任一生产出数可回溯到原始"——兑现这个承诺的**登记簿**就是目录（血缘的持久化）；
- 07 章的消费者矩阵要生效——消费者**得先能找到**自己该用的层和表——发现性（discoverability）；
- 16 章的描述性数据（口径/码表/元数据）——目录是其**系统化存储与服务接口**。

一句话定位：**目录不生产可信，目录让可信可查询**。反之，没有供应链的集成纪律，目录只是给数据沼泽配一份精美索引——这是他对"catalog 万能治理派"的惯常批评 ⚠️。

🔧 现代延伸（原书大概率未展开）：目录正从"人读的字典"变成"机读的控制系统"——元数据驱动权限（行列级）、质量断言、生命周期策略（raw 保留/归档），见 [../湖仓架构大规模数据平台的设计和实现/04-数据目录.md](../湖仓架构大规模数据平台的设计和实现/04-数据目录.md) 与 [../Engineering_Lakehouses_with_Open_Table_Formats/09-Catalog与互操作.md](../Engineering_Lakehouses_with_Open_Table_Formats/09-Catalog与互操作.md)（catalog 同时是表格式的提交协议参与者——Inmon 的"目录"概念不覆盖这层机器语义，属理论与实现的重要分叉，12 章对照）。

### 2. 架构演化：Inmon 的方法论遗嘱（第 18 章 ⚠️）

末章标题"数据架构的演化"承载他最一贯的主张：**大架构是长出来的，不是憋出来的**（piecemeal / incremental growth，从《数据仓库》第一版讲到湖仓）：

- **按主题域增量**：一次集成一两个域（客户、交易……），跑通端到端可信链，再滚动扩展——反对"大爆炸式全量建模"；
- **架构不变量与实现变量的分离**：层与流向（04）是常量；存储、引擎、格式是变量——演化的是变量；
- **存量迁移路径** ⚠️（推定为其对企业的实际建议）：有仓库的企业不必推倒——把仓库的"集成层/发布层"语义平移到近生产/生产层，把被存储成本压制没存的最细数据补到 raw；没有仓库的企业则直接从瀑布建起。

### 3. 回收副标题：湖仓、AI/ML 与 data mesh 的三层关系 ⚠️

副标题（AI、ML 与 data mesh 的基石）在末章收尾（⚠️ 推定其论证结构）：

1. **对 AI/ML**：09 章已证——三层供数+可复现性是 ML 工程的地基（"bedrock"一词的确切含义）；
2. **对 data mesh**：mesh 主张领域自治、数据产品、联邦治理——Inmon 式解读是：**每个领域产品内部仍要跑一条迷你瀑布**（raw→近生产→生产），否则"产品"只是把沼泽切成小块；mesh 提供的是**组织拓扑**，湖仓提供的是**每个节点的架构标准件**——二者正交，可叠放；
3. **诚实的张力 ⚠️**：中央信息供应链 vs 联邦治理存在真实的理念冲突（谁定义跨域口径？实体解析谁负责？）。本书如何处理未见原文可考——建议对读时带着这两个问题，别默认 Inmon 已给出答案。

### 4. 目录最小登记集（⚠️ 教学清单，按层裁剪）

"登记什么"是目录章最可操作的部分。给一个按 04 章三层裁剪的最小集：

| 层 | 必登记项 | 选登记项 |
| --- | --- | --- |
| raw | 源系统、落地时间、不可变声明、保留策略、owner | 源端变更频率、合规标签 |
| 近生产 | 输入血缘（指向上游表/对象）、清洗规则版本、粒度声明、口径草案状态 | 质量断言结果、更新 SLA |
| 生产 | 冻结口径定义+实现 diff、发布评审记录、SLA、消费方清单 | 关联术语表条目、成本标签 |

判断目录合格与否的试金石仍是 01 章三要素：**给定生产层一项资产，能否沿登记信息机械地走回 raw**——能，目录就是可信的地图；不能，它只是资产清单。

### 5. 增量演化的节奏设计（⚠️ 推演）

"按主题域滚动"要落成节奏才不流于口号（教学推演，非书中方案）：

- 每个增量交付单元 = **一个主题域 × 完整三层贯通**（禁止"先把全域 raw 铺完再说"的横切式推进——那会长期停在 L1 堆放态，见 08 章成熟度表）；
- 每域以"端到端可重放演练成功"为完工定义（DoD）；
- 口径评审随域滚动、不集中憋大招；描述性数据（10 章）与目录登记（17 章）作为每域交付的一部分**随层落地**，不留"治理二期"欠账。

## 常见误区

| 误区 | Reality |
| --- | --- |
| "先上目录再谈架构，治理从索引开始" | Inmon：无供应链的目录是沼泽索引；顺序应是瀑布先行、目录随层登记 |
| "架构演化=没有架构，走哪算哪" | 演化针对实现变量；层与流向是不变量——增量≠机会主义 |
| "data mesh 取代了 Inmon 式架构" | mesh 管组织切分，湖仓管节点内架构；层级不同，不构成替代 |
| "血缘画一次存档就行" | 血缘是活的：每次管道变更都要同步登记，否则影响分析误导 |
| "登记越全越好，恨不得把每个值都入库" | 目录过载会无人维护；按第 4 节最小集分层裁剪 |
| "演化=等完美蓝图再动工" | Inmon 反蓝图主义：端到端打通一个域，胜过全域 PPT 架构 |
| "目录有了 AI 搜索，就不需要血缘登记" | 搜索解决"找得到"，血缘解决"信得过"——两者不可替代（17.3） |
