# 《Tackling TypeScript》段笔记 05 · 常见疑难反例集

> ⚠️ 段名凭记忆与站体例拟（骨架 Ⅴ：`this`、类字段初始化、结构化陷阱 ✅ 主题带出自 00 档，定位=「为什么 TS 不报错」反例集、擦除代价案例库）。本笔记把本会话与专题档实测整合成案例表：每条=「类型全绿但运行出错」的一个机制根因。

## 一、核心机制：反例的共同根源只有一条公理

**类型层不参与运行时**（一句话公理 ✅）。故「类型对但运行错」仅两种成因：**主动撒谎**（as/any/`!.` 骗过编译器）与**被动被骗**（结构兼容过宽/声明库失真，编译器没被骗但信息本就错）。Java/C++/Kotlin 读者的默认直觉「编译过了≈运行时至少有兜底」在此**整条失效**：Java 强转有 checkcast 真拦截、数组协变有 ArrayStoreException（⚠️ 专题档 Java 列书目口径）、Kotlin private 是编译+字节码双墙——TS 对应位置全部为空。

## 二、案例总表（实测列：✅=本会话 node v22.14 --experimental-strip-types 真跑）

| # | 案例 | 最小复现 | 运行时真相 | 实测 | 对照语言差异点 |
|---|---|---|---|---|---|
| 1 | **`as` 撒谎** | `const s = 42 as unknown as string` | `s.length`=undefined，`s.toUpperCase()` TypeError——断言零转换零检查 | ✅ aslie.ts | Java 强转运行时 checkcast 拦（⚠️ 书目）；语义断裂最大处（专题戒律 2） |
| 2 | **`any` 传染** | `JSON.parse→any→赋给 number 注解→toFixed` | 崩于 `toFixed is not a function`，`typeof n==="string"` | ✅ any_json.ts | Kotlin 无 any；Java Object 下转需显式检；any=官方闭嘴出口 |
| 3 | **`private` 无墙** | `class A { private s=42 }`；`Object.keys(new A())`、`(v as any).s` | keys 含 `s`、as any 直读；JS `#hard` 才隐身 | ✅ priv.ts（+专题实验 A ✅） | Java private 反射可捅但字节码有墙；Kotlin private 真墙；TS private=编译期礼貌 |
| 4 | **`enum` 运行时怪形** | `enum Color { Red }` | strip-only **SyntaxError 拒跑** ✅；transform 直跑出**双向映射对象** `{"0":"Red","Red":0}`——类型层语法竟造了个真值对象，反向映射是误用温床（键污染/数字反查） | ✅ enm.ts（销专题戒律 4 ⚠️） | Java enum 是真类（有方法有身份）；Kotlin enum class 同；TS enum=历史包袱，现代口径联合字面量替 |
| 5 | **数组协变裸奔** | `Dog[]` 经 `as unknown as unknown[]` 塞字符串→`.map(d=>d.breed.toUpperCase())` | 数组照收 `["…","not a dog"]`，崩在成员访问 | ✅ covar.ts | Java 数组协变**运行时抛 ArrayStoreException**（⚠️ 书目口径）——同名机制 TS 无兜底，协变+擦除双重放行 |
| 6 | **非空断言 `!.`** | `document.getElementById("x")!.style` | 元素不存在时读 null 属性崩；`!` 只是对编译器的一次口头保证 | 🔧 待补（运行时面可测，本波未跑） | Kotlin `!!` 同款语义但 Kotlin 有 null 传播族可选；`!.` 无任何运行时形态 |
| 7 | **结构兼容过宽（被动被骗）** | 形状恰配的错对象赋给目标类型；@types 声明与实现错位 | 编译器无从区分「碰巧同形」——无标称身份即无防御 | ⚠️ 类型报错面不可测（无独立 tsc） | Java/C++ 名义类型天然免疫；Kotlin 接口按名义实现免疫 |
| 8 | **`this`/类字段初始化** | 回调脱离 receiver 后 `this` 丢失；字段声明与赋值的阶段差 | `this` 是 JS 运行时的动态绑定，类型注解管不了调用方式 | ⚠️ 00 档 ✅ 主题带在册，细则未直证 | Kotlin/Java this 词法稳定；此坑是「JS 语义×TS 注解」的杂交带 |

前 5 条满足「至少 5 个」配额且全部 ✅ 实测；6–8 为登记在案的待扩展位（诚实标注，不冒充已验）。

## 三、批判读法
- 反例集的读法应倒置 01 章裁决：**每条=四论点兑现的一个具体漏洞**——#1/#2/#6 漏在论点 #3（重构网拦谎言），#3/#4 漏在 #4（意图无强制），#5 漏在 #1（捕获面止于形状），#7 是 #2 文档性的暗面（文档会说谎）。
- 「类型全绿」的心理安慰在 TS 里比 JVM 语言**更便宜也更危险**：Java 编译过≈类型系统+运行时双保险，TS 编译过≈只有你写的类型在对你自己负责。反例集的正确用法是把每条换算成 lint/评审规则（no-any 棘轮、禁 `!.`、少 `as` 多守卫——⚠️ 工程推论非书目）。
- 与专题档互校：案例 3/5 的「实测」直接复用专题实验 A 的口径与脚本位（/tmp/tsexp → 本会话 /tmp/tsexp2），两档合读即「公理→戒律→案例」三级链条。
- 表内 #4 enum 是唯一的**双向反例**：既可能「以为有运行时保护其实没有」（注解类），也可能「以为纯类型其实产了码」（enum/装饰器）——擦除叙事不是「运行时什么都没有」，而是「运行时有的必须逐条点名」，点名清单即专题戒律 4。
- 案例 8（this/类字段）提醒本段的真正书名味：Rauschmayer 的疑难章大头是 **JS 语义疑难穿 TS 外衣** ⚠️ 凭记忆与 00 档主题带（this、类字段初始化在册）——「类型对但运行错」只是其反例谱系的一支，另一支是「类型帮不上忙」，本集以 A 支为主、B 支登记待扩。
