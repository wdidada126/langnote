# 《Tackling TypeScript》段笔记 03 · 进阶类型与建模

> ⚠️ 段名凭记忆与站体例拟（骨架 Ⅲ：联合、交叉、字面量、泛型、收窄 ✅ 出自 00 档，高价值点=判别联合建模章）。对照策略按 00 档：语法面与 Programming TS 重叠速查，本笔记只取「建模哲学」增量。

## 一、核心机制：五件套的建模语义（面向 Java/C++/Kotlin 对照）

读法前提：五件套没有一个会在运行时留下形状（公理 ✅），它们改写的只是**你能对数据提出的可检查问题的集合**——以下每条同时给出「表达力增益」与「擦除后的信任缺口」两面。

- **联合类型 `A | B`**：类型即集合的并（[00-总览与阅读地图.md](../Type_Level_TypeScript/00-总览与阅读地图.md) 的类型=集合观在此落地）。对照：Java 表达「A 或 B」要 sealed interface + 两个实现（JEP 360 线 ✅ 该档口径），Kotlin 要 sealed class——**TS 一行直达**，代价是消费端收窄责任全在程序员。
- **判别联合（discriminated union）**：本段王牌。`{ kind: "circle", r } | { kind: "square", s }` 的 `kind` 标签=**手工编码进值的运行时反射**——专题戒律 3「类型信息只能编码进值」的正面教材。对照表：
  | 机制 | Java | Kotlin | TS |
  |---|---|---|---|
  | 和类型表达 | sealed interface+record | sealed class+data class | 判别联合一行 |
  | 分支穷尽检查 | switch 模式匹配（⚠️ 版本线依 JDK21 档口径） | `when` 穷尽 sealed | switch + `never` 兜底 |
  | 运行时身份留存 | class 元数据全在 | class 在、泛型擦除 | **零留存**（专题对照表 ✅）——标签必须是数据字段，类型层帮不了忙 |
  推论：判别联合只对「你亲手造的数据」成立；JSON.parse 进来的对象不会自带守约的 `kind`（05 章反例位）。
- **交叉类型 `A & B`**：属性合并的组合子，**不是继承**——对照 C++ 多继承/Kotlin 接口默认实现的「行为复用」语义，`&` 只谈形状不谈行为；函数类型参与交叉重载是陷阱带 ⚠️ 记忆口径。专题实验 A ✅：`Shape & Named` 注解后 `f.length` 仍为 1——交叉在运行时不存在。
- **字面量类型与 `as const`**：`42`、`"red"` 作为类型=值级别的意图表达，纯类型层 ✅（擦除公理推论）。**替代 enum 的现代口径**：`const enum` 之外，联合字面量 `'a'|'b' + as const 对象` 零产码——而 `enum` 是会产码的少数派（本会话实测 ✅：transform-types 下 enum 变双向映射真对象，详见 04/05）。
- **泛型**：名字绑形状，约束走结构路线（`T extends { id: string }`）；对照 Java 桥方法留痕、Kotlin `reified T` 借内联逃逸擦除、C++ 模板单态化生成真代码（✅ 专题四语言表后三列为书目口径）——**TS 无任何 `instanceof T` 可能**，运行时要类型身份只能把构造器/标签当值传递。
- **收窄 `narrowing`**：`typeof`/`in`/`instanceof`/`x is T` 谓词——本质是编译期流分析对 02 章「真实运算符」的借道；编译后谓词函数=普通 boolean 函数。`satisfies` 与 `as const` 纯类型层、`enum` 产码——混合带即专题戒律 4 的地雷位。

## 二、批判读法
- 建模上限=结构类型的上限：无真标称（brand 类型靠命名约定 hack ⚠️）、无高阶类型；两个形状全同的「金额」和「秒数」类型互兼容——**意图表达（01 章论点 #4）在基础带之后仍无强制**。
- 判别联合对 Kotlin 读者是「when+sealed」的熟悉形状，但信任方向相反：Kotlin 编译器保证 sealed 子类集合封闭，TS 只保证**你写进类型的**分支穷尽——外部数据源永远在集合外。
- 「类型即集合」让 `never`=空集、单元类型=单点集成为可推理代数——本段读法建议配合 Type_Level TS 的运算视角，Rauschmayer 处理 ⚠️ 凭记忆（以示例驱动为主）。
- 泛型一节对 C++ 读者的反向警戒：TS 泛型**不生成代码**（对照单态化 ✅ 专题表），它只是检查期的形状变量——把「模板实例化性能/代码膨胀」话题整体搬进 TS 讨论是范畴错误；但也别指望 `T` 在运行时帮你做任何分派。
- 收窄的「编译期幻觉」测试法：每个收窄结论自问「这段 if 删掉后运行时行为有区别吗」——多数时候没有（守卫的运行时腿属于 02 章运算符清单），有区别的只有 `typeof/in/instanceof` 那几条真检查。

## 三、🔧 微实验（本会话 node v22.14 --experimental-strip-types 真跑）
- 引用专题实验 A ✅：判别联合 `Shape` + 交叉注解 `Shape & Named` 的函数 `f.length=1`——联合/交叉全数擦除，形状是纯编译期话语。
- `enm.ts` ✅（对照条目）：联合字面量写法零产码可直跑；`enum` 在 strip-only 模式直接 SyntaxError 拒跑——「类型层语法多数不产码、enum 例外」的界碑实测（销专题戒律 4 的 ⚠️）。
- `guard.ts` ✅（02 章复用）：`"kind" in u` 收窄的运行时腿是 JS 原生 `in`——收窄机制=「编译期分析 × 运行时真运算符」的合体，缺后者前者无从校验外部数据。
- `any_json.ts` ✅（建模侧读法）：判别联合防线在 `JSON.parse` 出口处即被架空——`raw` 是 any，`kind` 是否存在编译器不追问；**建模章的全部信任假设止于你亲手 `new`/字面量构造的数据**，外部数据须 schema-first 重造类型（专题戒律 3 的反面实证）。
- 🔧 待补（专题第五节原文照录）：判别联合运行时收窄 vs `as` 强转的 crash 位点对照；`never` 穷尽兜底的报错面需 tsc ⚠️。
