## 核心概念速览（中英对照）

- **分离编译** — separate compilation：翻译单元（TU）模型，头文件是"人肉依赖声明"。
- **模块** — modules（C++20）：编译一次的语义单元，`export module`/`import`，终结文本包含。
- **主模块接口单元** — primary module interface：`.ixx`/`M.cpp` 中带 `export` 的部分，模块的"合同面"。
- **命名空间别名** — namespace alias：`namespace fs = std::filesystem;`，大规模工程减压阀。
- **按值返回/移动** — return by value + move：返回局部对象，C++17 保证复制消除（guaranteed copy elision）。
- **结构化绑定** — structured bindings：`auto [x, y] = p;` 拆 tuple/pair/聚合成员。
- **模板参数推导指引** — deduction guide：告诉 CTAD 如何从构造实参推出类模板参数。
- **异常** — exceptions：throw/catch + 栈展开，把"错误路径"从"正常路径"剥离。
- **不变式** — invariant：类维护"构造后恒真"的谓词；构造函数失败唯一出口是异常。
- **错误码** — `std::error_code`：跨边界（尤其 ABI/线程/进程）的可移植错误值。
- **断言** — `assert`/`static_assert`/`Expects`：运行期自检、编译期自检、契约前/后置条件。
- **不抛出** — `noexcept`：既是承诺也是优化提示（移动、析构、vector 扩容依赖它）。

## 设计视角：动机 → 机制 → 权衡 → 相邻对比

**动机：头文件为什么必须死？**（书之大意）`#include` 是文本粘贴：同一份声明被解析 N 次、宏污染全局、
包含顺序决定成败、编译时间随依赖平方增长。Stroustrup 把 modules 讲得非常克制——机制三句话：
`export module Math;` 声明接口，`export` 标记对外可见实体，`import Math;` 拿到的是**已编译的语义**而非文本。
权衡他也直说：现有代码不会一夜迁移，所以模块与头文件可共存（头可以包成头单元 header unit）。
这段的深读入口是 [../C++语言的设计与演化/10-名字空间与C预处理器.md](../C++语言的设计与演化/10-名字空间与C预处理器.md)：
当年 namespaces 赢下 module 提案的论点，与 2015-2019 modules 复活的设计妥协，是同一场辩论的两个半场。

**机制：值语义统治接口。** 3.4 的核心信息不是语法，而是**选择压力**：
输入参数按值（可移动类型）或 `const&`+显式 `std::move`；输出用返回值不用出参——
因为 C++17 起"返回局部对象零开销"是保证而非编译器优化（guaranteed copy elision），
而出参强制调用方默认构造再赋值。结构化绑定与 CTAD 是同一哲学的人体工学：
让"类型显然"的地方不必再写类型。相邻对比：Go 的多返回值靠元组语法，Rust 靠元组类型，
C++ 用 tuple+绑定把它们缝进已有语法——导览书展示的是"缝合的痕迹"（`get<>` vs 解构）。

**机制：一张"参数怎么传"速查（3.4 的口径整理）。** 导览书把结论散在正文里，本表按节归拢（书之大意）：

| 意图 | 写法 | 理由 |
| --- | --- | --- |
| 输入，廉价类型（int/指针/小聚合） | 按值 | 拷贝成本低于引用间接层 |
| 输入，可移动/可能需要副本 | 按值 + 需要时 `std::move` | 一次接口适配两种调用方 |
| 输入，大且只用不改 | `const T&` | 免拷贝；可空则 `const T*` |
| 输出 | 返回值 | C++17 保证零额外拷贝；出参强制默认构造 |
| 输入输出 | `T&` | 明示"会被改" |
| 调用方备好的缓冲区 | `span<char>` | 有长度的"输出参数"，回到输入语义 |

**机制：异常的地盘论。**（4.2-4.3）书的立场历来清晰：**构造失败只能 throw**（没有返回值可写），
而"可预期的失败"（找不到文件、解析失败）不该用异常。这正是 4.4"替代方式"的伏笔：
返回值 + `error_code`（低频、跨边界）与"永不失败"设计（重试/兜底值）。
零开销原则的精确表述在这里出现：不 throw 时不付费——但"不付费"指代码路径而非二进制体积，
异常表（DWARF/SEH）常驻，这是嵌入式 `-fno-exceptions` 阵营仍有存在感的根因（工业实践节展开）。
4.5 把 `Expects()/Ensures()`（GSL 风格契约）与 assert 并列：**断言是"你欠我的"，异常是"世界欠你的"**
（书之大意：违反不变式=程序员的 bug，外部错误=环境的行为）。

**权衡：noexcept 的双刃。** 声明 `noexcept` 让 move/析构进入快路径（vector 扩容敢搬不敢拷），
但违约即 `std::terminate`——比异常更糟的是"没有出口"。书给出的默认策略（4.5.3）：
普通函数不加；移动操作与析构加；接口层用条件 noexcept（`noexcept(expr)`）。

## 最新演进与工业实践（第 3 版止于 C++20，本节补 C++23/26）

- **`std::expected<T, E>` 定稿（C++23，P0323R12 ✅wg21.link 302 + open-std 索引标题 "std::expected"）**：
  4.4 节"error_code 与 optional 都不解渴"的直接答案——值类型携带"成功值或错误值"，无异常开销。
  组合子 `and_then/or_else/transform` 来自 **P2505R5 "Monadic Functions for std::expected"**（✅标题实测）。
  🔧 本机实测（MinGW g++ 15.2，`-std=gnu++23` 编译运行通过；`-std=c++20` 下 `std::expected` 硬错误不存在）：

  ```cpp
  std::expected<int, std::string> divide(int a, int b);
  auto r = divide(10, 2)
             .transform([](int x) { return x + 1; })
             .and_then([](int x) { return divide(x, 0); });   // 失败沿链传播
  // 输出: ok=0 err=div by zero fallback=-1
  ```
  工业侧：Boost.Outcome 是 expected 的"近亲上游"（作者同圈层）；LLVM 自研 `llvm::Expected<T>`/Error
  多年，std::expected 统一了这类方言的时间点正落在 C++23（各库迁移现状 ⚠️ 未逐一核实，方向为"新代码用 std"）。
- **契约（contracts）进 C++26**：P2900 系列（"Contracts for C++"，R9→R14 多轮修订 ✅wg21.link 302 实测，
  媒体多源报道其进入 C++26 定稿 ⚠️ 本目录未核 ISO 最终文档）。它把 4.3/4.5 的 Expects/Ensures
  从库宏升格为语言构造（语义：违约动作可配置，从 abort 到 UB 分层）。
- **`static_assert` 用户自定义消息（C++23，P2741R3 ✅标题 "user-generated static_assert messages"）**：
  `static_assert(sizeof(T)==8, "T must be 8 bytes", fmt::format(...))` ——编译期报错体验对齐编译期计算。
- **modules 的 2026 落地现状**：GCC 自 14/15 支持 `-std=c++20` 模块（编译自身库尚不含官方 `import std;`），
  CMake ≥3.28 有 `CXX_MODULES` 语言支持；MSVC STL 提供官方 `import std;` 头模块。书附录 A 的判断
  （"用你的实现提供的东西"）至今不过时；深读见 [11 章](11-历史兼容性与std模块附录.md)。
- **Google style 阵营**：abseil/folly 历史上禁异常/慎用异常（folly 提供 `fbthrift` 异常穿透层；
  abseil `StatusOr` 与 expected 语义同构且早已存在 ⚠️ 版本细节未核）——读本章时把 expected 想象成
  "标准化 StatusOr"最贴近工业直觉。

## 常见误区

1. "模块=更快的头文件"：modules 首先改的是**语义模型**（可见性由 export 决定而非包含顺序），
   编译加速是副产品；把宏依赖重的旧头直接包成模块会撞 ODR 与宏导出限制（`export` 不了宏）。
2. `std::move` 当"转左为右"的咒语：3.4 的口径是"对局部变量 return 不要写 move（挡住 NRVO）"，
   这是 Meyers 的 EC++ item 与本书互文的点（[../Effective_Modern_C++/05-右值移动完美转发.md](../Effective_Modern_C++/05-右值移动完美转发.md)）。
3. 拿异常做跨 ABI/跨插件边界：vtable、noexcept 帧、CRT 堆不一致都可能让 catch 接不住——
   书 4.4 推荐边界用 error_code，C++23 之后边界上多了一个 expected（值类型可穿 ABI）。
4. `assert(f(x()))` 里带副作用：NDEBUG 下表达式整个消失，"release 才出的诡 bug"常客（4.5.1 点名）。
5. 把 `export` 当"注释掉即可隐藏"：模块可见性由 `export` 决定，接口单元里漏写 export 的实体
   import 方根本看不见——与头文件"写了声明就能用"的直觉相反（3.2.2）。
6. 结构化绑定当万能解包：`auto [a,b]` 对 tuple/pair 走 `get<>`、对聚合走公有成员访问，私有成员
   不可绑、数组要写全个数（3.4）；跨 ABI 场景它只是语法糖，不产生任何布局保证。
7. `noexcept` 上加复杂表达式：`noexcept(f())` 里的 `f` 若是未定义/有副作用调用可能直接编译错误，
   惯用法是 `noexcept(noexcept(f()))`——双层含义见 [04 章](04-模板与概念和泛型编程.md)条件 noexcept 回收。
