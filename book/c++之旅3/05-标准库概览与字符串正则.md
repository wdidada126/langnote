## 核心概念速览（中英对照）

- **标准库组件** — standard-library components：容器/算法/字符串/IO/并发等"不依赖运行时"的官方零件箱。
- **std 命名空间** — `std::`：全部标准实体的家；书中立场：库内自由函数调用会经 ADL，别裸 `using namespace std;`。
- **ranges 子命名空间** — `std::ranges::` / `std::views::`：C++20 起范围化重排的算法家谱（9.3.2）。
- **头文件 ↔ 模块映射** — headers vs modules：9.3.4 给出"哪个头提供哪个组件"的导览表（过渡期真相）。
- **短字符串优化** — SSO：`std::string` 把 ≤15 字节左右存进对象本体，小串零堆分配。
- **字符串视图** — `std::string_view`：`{const char*, size_t}` 对，不拥有字符、O(1) 传参。
- **悬垂视图** — dangling view：视图生命周期必须覆盖其指向的缓冲——string_view 第一杀手。
- **正则原语** — regex grammar（ECMAScript 方言）：`\\d+`、`(a|b)*`、`[[:alpha:]]` 类 POSIX 混合。
- **正则三件套** — `regex_match`（全匹配）/ `regex_search`（找子串）/ `sregex_iterator`（遍历全部）。
- **捕获组** — capture groups：`smatch m; m[1]` 子表达式回填。
- **u8string** — C++20 `std::u8string` + `char8_t`：把 UTF-8 从"char 里装字节"升格为类型（书中一笔带过）。

## 设计视角：动机 → 机制 → 权衡 → 相邻对比

**动机：为什么标准库"薄"？**（书之大意）ISO 只承诺"跨平台可移植的最小公共集"，
GUI/网络/线程池/序列化永远在标准外——这是 C++ 生态"库即语言扩展"的成因（Boost、abseil、folly 的存在理由）。
Stroustrup 的告诫很具体：先查标准库，再查长期稳定的行业库（他点名 GSL、FFI 类），最后才自造。
9.3.3/9.3.4 的过渡期视角值得划重点：**同一组件可能同时有头文件、模块、std 模块三种到达路径**，
本书附录 A 专讲这个（见 [11 章](11-历史兼容性与std模块附录.md)）。

**机制：string 的"贵"与 string_view 的"赖"。** 10.2.1 揭 SSO：小串零分配、大串一次分配+拷贝；
`operator+` 链式拼接在 C++11 移动语义后不再每步建临时对象（10.2 明确此点——这是"移动语义改变日常代码"的标本）。
string_view（10.3）把"只读文本参数"成本压到两个字，且接受 `const char*`、string、字面量三方；
代价：它不保证 `\0` 结尾、且**不续命**——经典事故 `std::string_view v = std::string("tmp") + "x";` 悬垂。
书的处方：view 只用于"从输入到处理"的短窗口；跨语句持有请回到拥有者。
相邻对比：Rust `&str` 由借用检查器保证不悬垂；C++ 靠程序员纪律——这是"无 GC 语言的共同税"。
🔧 实测口径：本机 g++ 15.2 `-std=gnu++20` 编译运行书中风格例子（构造/拼接/find/substr）无碍；
另用 `std::format`（见最新节）复现"数字进文本"的现代管道通过。

**编辑整理：string 相关操作的成本速查（归拢 10.2/10.3 口径，非原表）。**

| 意图 | 首选写法 | 成本注记 |
| --- | --- | --- |
| 只读文本参数 | `std::string_view` | 两字（指针+长度），零分配；不保证 `\0` 结尾 |
| 可变字符串 | `std::string`（返回时按值+move） | SSO 内零分配；热点 `reserve` 后再拼 |
| 数字 ↔ 文本 | `to_chars`/`from_chars`；格式化用 `format` | `to_string` 每次分配，热路径慎用 |
| 切分/替换 | `find`+`substr`，或 ranges `split/join` | 上 regex 是最后的最后手段 |
| 拼接 | `+=`/`append`（先 `reserve`） | C++11 移动后 `operator+` 链不再逐步建临时对象 |

**机制：regex 的定位是"够用就好"。** 10.4 选 ECMAScript 语法为默认方言（JS 兼容、生态最大），
给出 match/search/迭代三档用法与邮箱小例子。导览书不讳言两大痛点（书之大意）：
① 语法细节（POSIX 类名、ECMAScript 扩展）文档化不足，cppreference 成了实际权威；
② 主流实现**慢**（尤其 MSVC 首次构造、冷路径分配）。设计视角：regex 被刻意做成"库而非语言特性"，
所以它随时可以被更快的库替换（RE2 系线性时间自动机是工业默认之一 ⚠️ 各家采用现状未逐一核）。
书中邮箱例子的教训不在那一串模式怎么写（模式原文请以书为准 ⚠️），而在**POSIX 字符类 `[:w:]` 与
ECMAScript 转义混排的语法缝合处**——默认方言选 ECMAScript 正是为了蹭 JS 生态的认知度。
🔧 三件套最小骨架（编辑整理示例，g++ 15.2 `-std=gnu++20` 编译运行通过）：

```cpp
static const std::regex pat{R"(\d+-\d+)"};         // ① 模式编译贵：提出来只编一次
std::smatch m;
if (std::regex_search(text, m, pat)) { /* 用 m[0] */ }   // ② 找子串/捕获组
for (std::sregex_iterator i{text.begin(), text.end(), pat}, e; i != e; ++i)
  ;                                               // ③ 遍历所有命中
```

**权衡：为什么标准库没有"更好的 JSON/HTTP/异步 I/O"。** 9 章组件表 vs 现实需求缺口的张力，
正是 WG21 "先网络 TS/执行 TS，再谈合并"的路线注脚（std::execution 见 [10 章](10-并发.md)）。
读本章时把"缺什么"当成练习：你会发现每个缺口在本目录"C++23/26 补位节"都有新答案。

## 最新演进与工业实践（第 3 版止于 C++20，本节补 C++23/26）

- **`std::print`（C++23，P2093R14 "Formatted output" ✅）**：基于 `std::format`（C++20，P2286/P2418 线，
  具体号 ⚠️ 未采）的直写通道：`std::print("{} -> {:.2f}\n", s, x)`，无 `<<` 语法噪音、格式串**编译期校验**。
  🔧 本机实测：MinGW g++ 15.2 下 `<print>` **编译通过但链接失败**（`undefined reference to std::__open_terminal /
  std::__write_to_terminal`——MinGW 运行时缺口 ⚠️），而 `<format>` 完全可用——诚实记录：
  在该工具链用 `std::format` + `puts/fprintf` 兜底；Linux（UCRT 无此问题）或换 libc++/较新 msvc 运行时无碍。
- **C++23 文本小补**：`std::bytes`（字节序列定域名，本环境 ❌ 未实现，见 [00](00-总览与阅读地图.md) 实测表）
  → C++26 改名 `std::text_encoding` 处理编码标识（定稿号 P2772 ⚠️ 未核到标题，仅述方向）。
- **ranges 对 string 的重写**：`std::views::split`/`join`/`transform` 让"切词/替换"脱离 regex（书 14 章口径）；
  `ranges::to`（C++23）终结收集样板（实测见 [07 章](07-容器与算法.md)）。
- **C++26 观察项（只述方向）**：用户自定义类型的 format 扩展、缓冲输出 `printbuf`（见 [06 章](06-输入输出与文件系统.md)）
  仍在 SG 讨论 ⚠️ 未采到可靠定稿号；UTF-8 工具（std::utf8 系提案）亦未进标准——10 章"文本处理自己动手"的现状短期不变。
- **regex 的工业边缘化**：性能敏感路径普遍换 RE2/srell/pcre2；abseil 至今无 regex 组件（用 RE2 是常见搭配 ⚠️ 转述）；
  C++26 对 regex 无大动作——本章的"导览+提醒去外面找快的"结论 2026 年仍然成立。
- **GCC/Clang 支持矩阵**：`std::format` GCC 13+ 完备（本机 15.2 实测 ✅）；
  `std::print` GCC 14+（本机编译 ✅/链接受 MinGW 运行时限制 ❌，如上述）。

## 常见误区

1. `string_view` 当 `string` 的"更快版本"存起来：它是视图不是值——成员函数返回、容器元素、跨 await 都是雷（10.3 点名）。
2. 拼接用 `s1 + s2 + s3` 担心性能：移动+SSO 下多数场景够用；热点再上 `absl::StrCat`/`fmt::format`/`string::append`  reserve。
3. regex 匹配整行忘记锚定：`regex_match` 全串、`regex_search` 子串——把 search 当 match 用是安全漏洞素材（校验场景）。
4. 以为 `char8_t`/`u8string` 做了转换：C++20 只是**类型化**，编码转换仍在库外（std::utf8 系提案未进标准 ⚠️）。
5. `std::regex` 放循环里构造：模式编译贵到离谱（实现相关），至少 `static const` 提出来（书 10.4 未明说，cppreference 实测众所周知）。
6. 拿 `string_view.data()` 当 C 字符串传给 `fopen` 类 API：view 不保证 `\0` 结尾（substr 结果尤其）——
   需要 NUL 就落回 `string`，或先断言来源是字面量（10.3 的告诫）。
7. 把"regex 慢"推广到"所有模式匹配都该手写"：`from_chars` 解析数字、`views::split` 切分隔符都比正则快一个量级，
   但语义复杂（回溯、替换、命名组）时仍需正经引擎——按 10.4 的分层选工具。
8. 以为 `std::format` 与 `printf` 格式串通用：`{:d}/{:.2f}` 是新语法，`%s` 不认；且格式串非字面量时
   编译期校验退化为运行期 `format_error`（🔧 本机 t08 实测输出 `argc=1 bytes-avail=0`，format 通路正常）。
