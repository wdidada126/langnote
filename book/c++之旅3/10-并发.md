## 核心概念速览（中英对照）

- **任务与线程** — task vs thread：任务=要算的东西，线程=执行任务的资源；async 把选择权交给实现。
- **数据竞争** — data race：两线程无序访问同位置且至少一写=未定义行为，C++ 内存模型的头号公敌。
- **互斥与锁** — `mutex/lock_guard/scoped_lock`：RAII 锁包装；`scoped_lock`（C++17）多锁防死锁。
- **原子量** — `std::atomic<T>` + 内存序：无锁同步的最小公倍器（默认 seq_cst，放松需论证）。
- **条件变量** — `condition_variable(_until)`：等待"事件"而非忙等；**必须配谓词**防虚假唤醒。
- **future/promise** — 一次性结果通道：生产者写 promise，消费者 `get()`（异常沿通道传播）。
- **packaged_task / async** — 把可调用对象挂上 future；`async` 懒执行 vs `thread` 急执行。
- **jthread / stop_token / stop_source**（C++20）— 可协作停止、自动 join 的线程：本书新增节的正主。
- **协程** — coroutine：`co_await/co_yield/co_return` 可挂起函数；标准只给**机制**（promise_type 协议）不给调度器。
- **awaitable/awaiter** —  Awaiter 三问：`await_ready/await_suspend/await_resume`。
- **协作式多任务** — cooperative multitasking：单线程事件循环 + 协程切换（书中 echo_server 例）。
- **无栈协程** — stackless coroutine：帧由编译器堆分配，挂起即返回——与有栈纤程（ucontext/boost.fiber）相对。

## 设计视角：动机 → 机制 → 权衡 → 相邻对比

**动机：为什么标准并发从线程起步而不是任务池？**（18.1）硬件趋势（核数增长、单核频率停滞）+
"什么都不给则人人自造轮子"的标准化逻辑。C++11 先给线程/原子/mutex 这三件"最小公倍器"，
更高层（工作窃取调度器、任务图）留给库——本书 18.2 对比 thread 与 async 的用意即示范
"同一抽象层级可以有急/懒两种实现"。Stroustrup 明确说：裸 thread 是并发界的裸 new，
日常该用带所有权语义的高层件——这句话的终点就是 C++20 的 jthread。

**机制：停止三兄弟修了 20 年的坑。** `thread` 不 join 即 terminate、detach 后无法取消、
用户手写 `atomic<bool> done` 各造各的轮子。`stop_token`（18.5.4）把"请求停止"标准化：
`jthread` 自带 stop_source，析构时 request_stop + join 一气呵成；任务侧以 stop_token 轮询或注册回调。
权衡（书未展开，cppreference 有）：停止是**协作式**的——不检查 token 的代码永远不会停；
且 token 轮询点选择本身就是设计。📋 三兄弟分工（编辑整理）：`stop_source`=发停止请求的一方
（`jthread` 隐式自带一个）、`stop_token`=随线程函数参数送达的"感知器"、`stop_callback`=为"正在等"
的代码准备的唤醒钩子（条件变量/睡眠中的任务靠它跳出）。🔧 本机实测（g++ 15.2 `-std=gnu++20 -static` 编译运行通过）：
jthread + `request_stop()` + 循环内 `stop_requested()` 检查的取消模式，输出停止计数。

**机制：协程="可挂起函数"的机制层。** 18.6 的教学路径极其克制：先给 `get_char_async` 微型 awaitable，
再手搓 promise_type，最后用协程重写 echo_server 协作调度——全程**不用任何库协程类型**。
设计视角（书之大意，反复强调）：协程语义（谁恢复、何时恢复、结果放哪）因场景（IO/生成器/任务图）
天差地别，标准库若钦定一种会重蹈 `std::execution` 未至前的混乱，故 P0912 系只冻结**协议**：
`initial_suspend/final_suspend/await_transform` 钩子 + Awaiter 三问。代价：学习者必须先懂协议才能读任何
协程库（asio/cppcoro/boost.asio awaitable 各家 promise 选型不同）；收益：所有库在同一机械层上对话。
深读：[../C++20设计模式/06-组合与装饰器.md](../C++20设计模式/06-组合与装饰器.md) 处理不了这层——
请去 [../C++新经典.md](../C++新经典.md) 与 cppreference 协程页（本库暂无协程专著目录 ⚠️）。

**权衡：锁 vs 原子 vs 无等待的消息传递。** 18.3/18.4 给的决策树（书之大意）：
先问"能否不共享"（按任务切分）→ 共享低频用 mutex（简单即正确）→ 高频单字用 atomic →
"无锁数据结构"是专家领域（本书一页都不给实现，诚实推给专著——本库即
[../C++并发编程实战2/07-无锁数据结构.md](../C++并发编程实战2/07-无锁数据结构.md)）。
内存序六档只列概念不展开，"默认 seq_cst，放松前先画 happens-before 图"是全章的潜台词。

**相邻对比：** 与 Go（CSP"通过通信共享内存"、runtime 调度器全包）、Rust（类型系统编译期灭掉 data race）
相比，C++ 选择"提供全部原语，纪律靠人和工具"（TSan 是事实标配 ⚠️ 书未提，属工程现实）——
这也是本章"建议"节全部指向"能高层则高层"的原因。

## 最新演进与工业实践（第 3 版止于 C++20，本节补 C++23/26）

- **`std::execution`（senders/receivers，C++26，P2300R10 ✅标题 "`std::execution"`，wg21.link 302 实测）**：
  18.5 "future 不够用"的正式终局——异步任务组合子（`when_all/schedule/let_value/…`）、
  执行器（scheduler/executor）一等公民、与并行算法（[07 章](07-容器与算法.md) 13.6 执行策略）合流。
  参考实现 **stdexec**（NVIDIA/Apple 出品，GitHub 活跃）已可在 C++20 编译器试用 ⚠️ 版本矩阵未逐一核。
  future/promise 的历史地位：一次性、不可组合、无 backpressure——读 P2300 动机节是最佳补课。
- **hazard pointers（C++26）**：无锁容器"何时能安全 delete"的 20 年老大难（18.3 无锁节的暗坑）
  标准答案在途——P1121R2/R3 接口提案 → P2530 "Why Hazard Pointers should be in C++26"（✅标题实测），
  2024 年扩展族 P3135/P3427；媒体多源称已入 C++26 定稿 ⚠️ 本目录未核 ISO 终文，GCC 15 未实现（实测无）。
  现行工业替代：folly `HazPtrTable`、`boost.lockfree` 各显神通。
- **协程的库层补齐（C++23/26）**：`std::generator`（P2502R2 ✅，[08 章](08-范围与指针容器.md) 实测）
  是协程进标准库的**第一个**消费者；awaitable 的 `co_await std::optional`（P2945? ⚠️ 不写号）方向讨论中。
  调度器（execution）与协程的胶水即 P2300 的 `schedule` 原语——18.6 手写 echo_server 的"最终形态"。
- **厂商/编译器现状**：GCC 10 起 jthread、GCC 10-14 协程渐进（clang 全实现最早）；本机 GCC 15.2
  对本章语法全支持（jthread/协程微型例均编译通过 ✅）；cppcoro（Lewis Baker）与 Boost.Asio 2.x
  （awaitable 操作器全家桶）是 2026 年生产协程的主流门面 ⚠️ 版本表述从新。
- **观测面**：`std::stacktrace`（C++23，号 ⚠️ 未采）给死锁/竞态事后取证补了标准件；
  sanitizer（TSan/ASan）与 Thread Sanitizer 报告解读见 [../C++代码调试的艺术.md](../C++代码调试的艺术.md)
  与 [../C++并发编程实战2/11-多线程应用的测试和除错.md](../C++并发编程实战2/11-多线程应用的测试和除错.md)。

## 常见误区

1. `detach()` 当"后台任务"惯用法：失去所有生命周期控制——jthread/async+future 才是标准姿势（18.5.4 的存在理由）。
2. `condvar.wait(lk)` 不带谓词：虚假唤醒（spurious wakeup）是合法行为，裸 wait 必错（18.4 演示 predicate 重载）。
3. 原子量当"无锁线程安全对象"：`atomic<struct>` 仍是单字操作，多字段一致性需要别的（锁/版本号/RCU/hazard）。
4. 协程=异步自动发生：忘记写 `co_await` 的函数就是普通函数；协程帧里存引用悬垂（string_view 同债，见 [05 章](05-标准库概览与字符串正则.md)）。
5. `future.get()` 里异常"丢了"：它被 rethrow 到 get() 点——忽略 future 的 async 任务，错误会静默蒸发（18.5.3 暗坑）。
6. 用 `volatile` 做线程同步：它只保证"不被优化掉"，不保证任何顺序/可见性——书 18.3.2 点名，atomic 才是正门。
7. 协程帧里跨 `co_await` 持有 `lock_guard`：挂起点后可能在**另一个线程**恢复，锁的获取/释放异线程=UB——
   临界区要收窄到不跨挂起点（cppcoro 的 `scoped_async_lock` 就是为此造的类型）。
8. `stop_callback` 在循环里反复注册：每次都可能分配共享状态；轮询型任务用 `stop_requested()` 即可，
   只有"会阻塞很久"的等待点才值得挂回调（18.5.4 的两种姿势）。
9. 把 `async` 当"保证开新线程"：实现可延迟到 `get()` 时同线程执行——想强制并发只能 `std::thread`，
   想拿回错误传播就必须消费 future（18.5.3 的两句坦白）。
