## 核心精讲

（以下伪代码与示意图均为**教学示意，不参与构建**。）

### 12.1 单机配置与启动

- 最小配置项（笔记口径，具体参数以官方文档为准）：
  - `tickTime`：ZK 的最小时间单位（心跳与超时计算的基础）；
  - `dataDir`：快照与事务日志目录；
  - `clientPort`：客户端连接端口。
- 🔧 工程提醒：**事务日志与快照应放在不同磁盘**——事务日志是顺序追加写，
  与快照（随机写）或与其他服务争抢 IO 会显著抬高延迟，这是 ZK 运维的经典建议。

### 12.2 数据模型（本章的骨架）

#### 12.2.1 时间语义

- ZK 内部用两类「时间」来定序：
  - **`zxid`（ZooKeeper Transaction ID）**：全局单调递增的 64 位事务 ID，
    高 32 位是 **epoch**（leader 任期），低 32 位是任期内的计数器。
    🔧 **epoch 的作用正是防止旧 leader 复辟后产生冲突决定**（呼应 [04](04-共识与Paxos-Raft.md) 的 term）。
  - **版本号**：每个 znode 有 `version`（数据版本）、`cversion`（子节点版本）、`aversion`（ACL 版本）。
    写操作可携带期望版本号实现 **CAS**（`-1` 表示不检查）。

#### 12.2.2–12.2.3 树状模型与 znode 状态

- 命名空间是一棵**树**（类似文件系统路径：`/services/order/instance-0001`），
  每个节点称 **znode**，既存数据也存子节点。
- **znode 的 stat 结构**（常用字段）：
  | 字段 | 含义 |
  | --- | --- |
  | `czxid` / `mzxid` | 创建时 / 最后一次修改时的 zxid |
  | `ctime` / `mtime` | 创建 / 最后修改的毫秒时间戳 |
  | `version` / `cversion` / `aversion` | 数据版本 / 子节点版本 / ACL 版本 |
  | `ephemeralOwner` | 若为临时节点，记录持有它的 **session id**；持久节点为 0 |
  | `dataLength` | 数据字节数（🔧 受 12.2.5 限额约束） |
  | `numChildren` | 子节点数量 |
  | `pzxid` | 最后一次子节点变更的 zxid |

#### 12.2.4 znode 的可选特性（四类经典 + 两类新增）

| 类型 | 特性 | 典型用途 |
| --- | --- | --- |
| **持久节点**（PERSISTENT） | 显式删除才消失 | 配置、服务目录 |
| **临时节点**（EPHEMERAL） | **会话结束即自动删除** | 服务实例注册、存活探测、锁 |
| **持久顺序节点**（PERSISTENT_SEQUENTIAL） | 名称自动追加单调递增序号 | 分布式队列、全局命名 |
| **临时顺序节点**（EPHEMERAL_SEQUENTIAL） | 临时 + 自增序号 | **分布式锁**（12.8.4）、选主 |
| 🔧 **容器节点**（CONTAINER，3.5+） | 最后一个子节点被删后会被异步删除 | 分组目录的自动清理 |
| 🔧 **TTL 节点**（3.5+，需开启） | 超时未修改且无子节点则删除 | 有限期的注册项 |

#### 12.2.5–12.2.6 限额与权限

- **限额**：单个 znode 的数据大小有上限（**默认 1 MB**，由 `jute.maxbuffer` 控制）。
  🔧 这条限制决定了 ZK 的适用边界：**它只存元数据，绝不存业务数据**。
  更关键的是——**这个上限是「任何节点的数据 + 其所有子节点列表」的序列化大小**，
  「一个父节点下挂十万个子节点」会直接失败，这是生产常见事故。
- **权限（ACL）**：`scheme:id:permission` 三元组；
  常用 scheme 有 `world`（anyone）、`auth`、`digest`（用户名密码）、`ip`、🔧`sasl`（Kerberos）；
  permission 为 `CREATE/READ/WRITE/DELETE/ADMIN` 的组合。
  🔧 ACL 是**继承的**——父节点的权限约束子节点，且 ACL 本身修改受 `aversion` 保护。

### 12.4 监听器（Watcher）：ZK 最有魅力的机制

- **三个特性**（12.4.1）：
  1. **一次性（one-shot）**：触发一次即失效，想持续监听必须**重新注册**（最常见的踩坑点）；
  2. **异步通知**：事件由服务端异步推送，客户端在回调中处理；
  3. **轻量**：通知里**只有事件类型与路径，不带数据**——客户端需自行再读一次（于是读到的是**最新值**，可能已不是触发时刻的值）。
- **事件类型**（12.4.2）：`NodeCreated`、`NodeDeleted`、`NodeDataChanged`、`NodeChildrenChanged`；
  另有连接态事件（`None` 类型下 `SyncConnected` / `Expired` / `Disconnected`）。
- 🔧 两条使用纪律：
  1. **Watcher 不保证你看到每一次变更**（一次性 + 通知丢失窗口）→ 需要可靠感知时应**轮询 + 版本号比对**；
  2. **羊群效应（herd effect）**：一个节点变化唤醒成千上万个 watcher → 锁实现必须用**顺序节点 + 只监听前驱**（见 12.8.4 与示意代码）。

### 12.5 连接与会话（Session）

- **会话是 ZK 的第一类公民**：临时节点的生命周期、Watcher 的生命周期都**绑定在会话上**。
- **会话状态**：`CONNECTING → CONNECTED（ASSOCIATED）→ ... → CLOSED/EXPIRED`。
- **服务器切换**（12.5.2）：客户端连接串里给出多个服务器地址，断连时自动切换；
  🔧 切换过程中**会话 ID 与密码不变**，因此临时节点不会被误删——这是 ZK 能容忍单机故障的关键。
- **会话过期（EXPIRED）**：超过 `sessionTimeout` 未与集群联系 → 服务端判定过期 →
  **删除该会话的所有临时节点**、失效所有 Watcher。客户端必须**重新建立会话并重做注册**（不能假设状态还在）。
- 🔧 工程陷阱：**会话过期是"服务端判定"的，客户端不一定立刻知道**。
  客户端在 `EXPIRED` 之前可能已经"以为自己还活着"并继续操作 → 会产生「我以为锁还在」的错误。
  这也是 [06-分布式锁.md](06-分布式锁.md) 强调 fencing token 的原因。

### 12.6 集群模式与一致性实现

- **角色**：Leader（处理写与事务提议）、Follower（参与投票、可处理读）、🔧 Observer（不投票，只扩展读能力）。
- **ZAB 协议**（12.6.2）的两个阶段：
  1. **崩溃恢复 / 选主（Discovery & Synchronization）**：选出 Leader 并确保其拥有**最完整的历史**（最大 zxid）；
  2. **原子广播（Broadcast）**：Leader 把写请求作为事务提案广播，获**多数派**确认后提交，
     按 zxid 顺序应用到各节点的状态机——这与 [04](04-共识与Paxos-Raft.md) 的状态机复制是同一个骨架。
- **12.6.3 一致性级别讨论**（本章最关键、也最容易被读漏的一节）：

| 保证 | ZK 是否提供 | 说明 |
| --- | --- | --- |
| **顺序一致性（Sequential Consistency）** | ✅ | 所有客户端看到**同一个**更新顺序（按 zxid） |
| **单一系统映像** | ✅ | 客户端无论连哪个服务器，看到的服务视图一致（会话迁移时会拒绝连到落后于自己的服务器） |
| **FIFO 客户端顺序** | ✅ | 同一客户端的请求按其发送顺序被执行 |
| **原子性** | ✅ | 更新要么全成功要么全失败，无部分应用 |
| **线性一致性（读）** | ⚠️ **默认不是** | 客户端可能连到**落后**的 Follower，读到旧值；调用 **`sync()` 后再读**才接近线性读 |
| **持久性**（已提交数据在多数派存活下不丢） | ✅ | 依赖多数派持久化 |

- 🔧 一句话总结本节：**ZK 的写是线性一致的（都过 Leader + 多数派），读默认是顺序一致的（可能陈旧）**。
  要强读就 `sync()`——代价是一次与 Leader 的同步往返。
  2026 年 etcd 的做法更显式：`ReadIndex` 与 `Lease Read`，把这件事变成 API 上的选择。

### 12.8 应用场景（把原语拼成能力）

| 场景（原书小节） | 用哪些原语 | 要点 |
| --- | --- | --- |
| **节点命名**（12.8.1） | **顺序节点** | 用自增序号生成全局唯一、可读、有序的名字（`/tasks/task-0000000001`） |
| **服务发现**（12.8.2） | **临时节点** + **Watcher** | 实例注册为临时节点，会话断开自动摘除；消费者监听子节点变化 |
| **应用配置**（12.8.3） | **持久节点** + **Watcher** | 配置写入 znode，客户端监听变更并热更新（注意 Watcher 一次性，要重注册） |
| **分布式锁**（12.8.4） | **临时顺序节点** + 监听前驱 | 序号最小者得锁；其余只监听**前一个**节点（避免羊群效应）；会话过期自动释放 |

### 第 13 章 再论分布式系统（总结篇）

- **13.1 分布式与一致性**：全书收束到一个判断——
  **分布式系统之所以难，是因为它把"一致性"从一个默认事实变成了一个需要设计、需要付费的目标**；
  理论篇给「一致性的定义与边界」，实践篇给「在边界内如何做事」，工程篇给「把共识做成组件」。
- **13.2 本书脉络**（13.2.1–13.2.3）：三篇不是并列，而是**同一条因果链的三个截面**：
  - 理论篇回答「**什么做不到、什么做得到**」（一致性 / 共识 / CAP-BASE）；
  - 实践篇回答「**做不到时怎么保证业务正确**」（锁 / 事务 / 调用 / 保护 / 幂等）；
  - 工程篇回答「**把这些能力做成可复用组件**」（消息中间件 / 协调中间件）。
- 🔧 13.3 的「展望」写于 2022 年；站在 2026 年回看，值得补记的四条现实：
  **Kubernetes 成为分布式 OS**、**服务网格接管客户端治理**、**CDC+流处理取代双写**、
  **OpenTelemetry 统一可观测性**——这四条不改变本书的结论，但改变了结论的**落地方式**。

### 教学示意：顺序节点分布式锁（含羊群效应优化）

```python
# 教学示意：ZK 分布式锁（只监听前驱）；不参与构建，不运行。
def acquire_lock(zk, lock_path):
    my = zk.create(f"{lock_path}/lock-", ephemeral=True, sequential=True)
    while True:
        children = sorted(zk.get_children(lock_path))     # 按序号排序
        if my.endswith(children[0]):
            return my                                      # 序号最小 → 获得锁
        predecessor = children[children.index(basename(my)) - 1]
        # ★ 只监听前驱（而不是监听父节点）→ 避免羊群效应
        released = zk.wait_for_delete(f"{lock_path}/{predecessor}")
        if not released:
            continue                                       # Watcher 一次性，需重新注册

def release_lock(zk, my):
    zk.delete(my)       # 删除即释放；进程崩溃时由会话过期自动清理（临时节点）
```

```python
# 教学示意：读路径的两种选择（对应 12.6.3）；不参与构建，不运行。
def read(zk, path, strong):
    if strong:
        zk.sync(path)                 # 与 Leader 同步（ReadIndex 的 ZK 版本）
    return zk.get_data(path)          # 弱读可能连到落后 Follower → 陈旧值
```

## 版本演进

- **版本情况**：本书第 1 版（2022-01）；**第 2 版未核实到，标注「待核验」**。以下记录 ZK 与其生态的演进。
- **ZK 的三个阶段**：
  1. **2006–2008（前身）**：Google Chubby（OSDI 2006）证明「锁服务 + 名字服务」是分布式系统的刚需；
     ZAB 的早期表述见 Reed & Junqueira 的 LADIS 2008 短文；
  2. **2010–2011（成型）**：ZooKeeper 论文（ATC 2010）与 ZAB 论文（DSN 2011）发表，ZK 成为 Hadoop/HBase/Kafka 生态的默认协调者；
  3. **2015–2026（被替代与去依赖）**：etcd 随 Kubernetes 崛起成为云原生生态的默认协调存储；
     Kafka 用 KRaft 移除 ZK 依赖；配置类需求迁往 Nacos/Apollo 等专用配置中心。
- 🔧 **2022 → 2026 最重要的三条**：
  1. **KRaft**：`apache/kafka` 自 3.3 起提供生产可用的 KRaft，4.0 起不再依赖 ZooKeeper——
     「协调组件内置化」取代「外部 ZK」成为新标准；
  2. **etcd 成为 K8s 生态的默认答案**：`etcd-io/etcd`（≈52.3k★，2026-09 实测）提供
     lease、watch、事务（CAS）、`ReadIndex` 线性读，接口设计比 ZK 更贴近现代应用；
  3. **ZK 自身的演进**：支持容器节点与 TTL 节点、管理服务器（AdminServer）、动态重配置等；
     但**新项目默认不再首选 ZK**。

## 近年研究与工业界开源实践（2015–2026）

- **协调组件（star 均为 2026-09 `gh api` 实测）**：
  - `apache/zookeeper`（≈12.8k★）：仍是 Hadoop/HBase 等生态的协调者，运维经验丰富、稳定；
  - `apache/curator`（≈3.2k★）：ZK 的 Java 客户端框架，封装了锁（`InterProcessMutex`）、
    选举（`LeaderSelector`）、服务发现等**配方（recipes）**，是 12.8 各场景的开箱即用版；
  - `etcd-io/etcd`（≈52.3k★）：K8s 的存储底座；**lease + watch + txn(CAS) + ReadIndex 线性读**
    是 2026 年协调类需求的默认接口形态。
- 🔧 **KRaft：迁离 ZooKeeper 的标志性事件**：
  - `apache/kafka`（≈33.8k★）自 3.3 起 KRaft 生产可用、4.0 起移除 ZK 依赖；
  - 意义：2015 年的标准答案是「用外部 ZK 做协调」，2026 年的标准答案是「**内置 Raft**」；
  - 这一变化不影响本章原理的价值（ZAB/会话/Watcher 仍是必修），但改变选型结论。
- **配置与服务发现的专用化**：
  - `alibaba/nacos`（≈33.4k★）：注册中心 + 配置中心一体化，AP/CP 可切换；
  - `hashicorp/consul`（≈30.1k★）：服务发现 + 健康检查 + KV；
  - 趋势：**配置**从 ZK 迁往专用配置中心（更强的 UI、灰度、历史版本、推送），
    **协调**（锁/选主）迁往 etcd 或内置 Raft。
- **Multi-Raft 与协调的规模化**：`tikv/tikv`（≈16.9k★）等用 Multi-Raft 把「一组共识」扩展到「成千上万组」，
  是本章 12.6 单组 ZAB 的规模化延伸（见 [04](04-共识与Paxos-Raft.md)）。
- **可验证性**：`jepsen-io/jepsen`（≈7.5k★）曾对 ZooKeeper 的一致性做过公开测试，
  推动了社区对「默认读是否线性一致」这一问题的清晰表述（与 12.6.3 直接相关）。

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「ZooKeeper 是线性一致的」 | **写**过 Leader + 多数派，是线性一致的；**读**默认可能连到落后的 Follower → 陈旧值；需 `sync()` 才接近线性读（12.6.3） |
| 2 | 「Watcher 会持续推送」 | **一次性**触发，触发后必须重新注册；且通知不带数据，需自行再读 |
| 3 | 「Watcher 不会漏事件」 | 一次性 + 注册窗口，中途的变更可能收不到；关键状态应靠**版本号比对或轮询**兜底 |
| 4 | 「临时节点在客户端断开时立刻消失」 | 要等**会话过期**（`sessionTimeout`）才删除；客户端在此期间可能误以为自己还持有锁 |
| 5 | 「ZK 可以当数据库存业务数据」 | 单节点数据上限默认 1 MB，且**含子节点列表**的序列化大小；ZK 只存**元数据与协调状态** |
| 6 | 「锁实现里监听父节点就够了」 | 会产生**羊群效应**（一次变更唤醒全部等待者）；正确做法是**顺序节点 + 只监听前驱** |
| 7 | 「ZK 挂了就没法服务发现了」 | 客户端通常有本地缓存；但缓存会陈旧——这正是 [05](05-CAP与BASE定理.md) 的取舍，需明确可接受窗口 |
| 8 | 🔧 本书需 2026 补丁 | 12.6.3 的「一致性级别」应补 **etcd 的 ReadIndex / Lease Read** 作为对照：它把「读是否线性」变成显式 API 选择，比 `sync()` 更清晰 |
| 9 | 🔧 本书需 2026 补丁 | 本章未提 **KRaft 与「去 ZooKeeper 化」**：Kafka 4.0 起不再依赖 ZK，新项目默认不再首选 ZK 做协调 |
| 10 | 🔧 本书需 2026 补丁 | 12.8.3「应用配置」应补**专用配置中心**（Nacos/Apollo 等）作为当代替代：灰度、历史版本、推送能力远超 ZK |
| 11 | 🔧 本书需 2026 补丁 | 本章未提 **Kubernetes 生态用 etcd**：云原生场景下「协调存储」的默认答案是 etcd，ZK 主要留存于 Hadoop 系生态 |
| 12 | 🔧 本书需 2026 补丁 | 第 13 章的展望应补四条 2026 现实：**K8s 作为分布式 OS、服务网格接管治理、CDC+流处理取代双写、OpenTelemetry 统一可观测性** |
