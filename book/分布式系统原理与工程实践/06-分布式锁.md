# 第 5 章 分布式锁（实践篇开篇）

> **本章地图**：为什么需要分布式锁（5.1）→ 三个特性（**全局性 / 唯一性 / 遵从性**，5.2）→ 设计要点（5.3）
> → 四种实现（**逻辑 / 唯一性索引 / 唯一性校验 / 一致性**，5.4）→ 应用场景（5.5）。

## 本章地图

- 位置：实践篇第 5 章，是「理论篇 → 实践篇」的第一站。
  - 第 2–4 章给了「一致性 / 共识 / CAP-BASE」三件理论武器；
  - 第 5 章立刻用它们解决一个最具体的问题：**多个节点如何互斥地访问同一份资源**。
- 主线：
  1. 单机锁（`synchronized` / `mutex`）只在**进程内**有效，跨进程跨机器就失效；
  2. 于是需要一个**所有节点都认可的权威**来授予锁（这就是「全局性」）；
  3. 谁来做这个权威、权威本身怎么容错，决定了四种实现方式的强弱；
  4. 越强的实现越依赖共识组件（第 3 章），这正好把理论篇和实践篇缝在一起。
- 🔧 本章是全书最需要「2026 补丁」的实践章之一：
  分布式锁在 2026 年的工程共识是「**能用乐观并发控制就别用锁；必须用时一定要 fencing token + 租约**」，
  而 Redlock 这类纯客户端算法自 2016 年起就有公开的、未平息的正确性争议。

## 核心精讲

（以下伪代码与示意图均为**教学示意，不参与构建**。）

### 5.1 产生背景：单机锁为什么不够

| 场景 | 单机锁 | 分布式场景下的失败 |
| --- | --- | --- |
| 进程内多线程 | `mutex` / `synchronized` | 有效（同一地址空间） |
| 同机多进程 | 文件锁 / 共享内存信号量 | 有效（同一内核） |
| **跨机多进程** | 无计可施 | 需要**外部权威**来仲裁「谁持有锁」 |

- 典型需求：定时任务只跑一次、库存扣减串行化、防止重复下单、主从切换时的脑裂防护。
- 🔧 关键认知：**分布式锁保护的通常不是「代码段」，而是「外部资源」**（数据库行、文件、下游接口）。
  这一点决定了后面「fencing token」为什么是必须的——因为暂停（GC STW、网络抖动）会让「锁还有效」这个信念失效。

### 5.2 三个特性（本书的分类很实用）

| 特性 | 含义 | 工程含义 |
| --- | --- | --- |
| **全局性**（5.2.1） | 锁的状态对所有参与者**可见且一致** | 不能各节点各存一份「我以为谁持有锁」；必须有一个大家都能查到的地方 |
| **唯一性**（5.2.2） | 同一时刻**至多一个**持有者 | 这是互斥的定义；实现上通常靠「原子地创建一条不存在的记录」 |
| **遵从性**（5.2.3） | 所有参与者都**自觉遵守**锁协议 | 🔧 分布式锁的软肋：**它只是约定，不是强制**。绕过锁直接改数据的代码，锁拦不住 |

- 🔧 「遵从性」这一条是本书写得很好的地方，值得展开：
  分布式锁**不是**内存屏障，它没有硬件强制力。因此：
  1. 要么**所有写路径**都先取锁（工程上极难保证，尤其是历史代码与运维脚本）；
  2. 要么**让被保护的资源自己能拒绝**（fencing token / 版本号 CAS）——这才是可靠做法。

### 5.3 设计要点（本书给出的是一份很实用的检查清单）

- **加锁与解锁必须是同一把钥匙**：释放时校验持有者标识（UUID / 会话 ID），否则会误删别人的锁；
- **必须有过期时间**：持有者崩溃后锁要能自动释放，否则资源永久不可用；
- **加锁与设过期时间必须原子**：先 `SETNX` 再 `EXPIRE` 中间崩溃 → 永久锁；
- **释放必须原子**：用 Lua 脚本或 CAS 保证「校验 + 删除」一步完成；
- **锁的粒度**：锁太粗 → 并发度归零；锁太细 → 锁数量爆炸与死锁；
- **可重入与自动续期**：长任务需要看门狗（watchdog）续期，但续期本身也可能失败；
- **获取失败的处理**：阻塞等待 / 快速失败 / 自旋重试 + 退避。

### 5.4 四种实现（本书最有价值的一节）

| 实现 | 权威来自 | 唯一性由谁保证 | 容错性 | 典型适用 |
| --- | --- | --- | --- | --- |
| **逻辑分布式锁**（5.4.1） | 应用自己的约定/配置（如按 ID 哈希决定「谁有资格」） | 逻辑规则 | 🔧 **不真正互斥**，只是避免争抢 | 分片任务调度（每个实例只处理自己那一片） |
| **唯一性索引分布式锁**（5.4.2） | 数据库的**唯一索引** | 数据库约束 | 依赖数据库高可用 | 已有数据库、并发量不高、希望零新组件 |
| **唯一性校验分布式锁**（5.4.3） | Redis 等 KV 的 `SET key value NX PX ttl` | 单命令原子性 + TTL | 依赖 Redis 高可用（主从异步复制有窗口） | 高并发、允许偶发失效的「防重」场景 |
| **一致性分布式锁**（5.4.4） | **共识组件**（ZooKeeper / etcd / Consul） | 共识日志 + 会话/租约 | 最强（多数派可用才可用） | 金融、库存、主节点选举等关键场景 |

- 🔧 逐一说明：
  - **逻辑锁**本质上**不是锁**，而是「**不争抢**」的设计（把互斥问题消解掉）。它往往是最好的方案——
    如果业务能改造成「每个实例只处理自己的分片」，就根本不需要锁。
  - **唯一性索引锁**：实现极简（插入一条唯一记录即加锁，删除即解锁），
    但要处理「持有者崩溃留下垃圾记录」→ 必须带过期时间或由超时清理任务兜底。
  - **唯一性校验锁**（Redis 类）：单命令原子 + TTL，性能好；
    但**主从异步复制**意味着主节点加锁成功后宕机、从节点尚未同步 → 可能出现**两把锁**。
    Redlock（向多个独立 Redis 实例加锁、多数派成功才算拿到）试图修补，但自 2016 年起有公开的批评（见文献表）。
  - **一致性锁**：把锁状态交给共识组件，配合**临时节点 / 租约**（会话断开即自动释放），
    这是唯一能同时满足「唯一性 + 崩溃自动释放」的方案；代价是每次加锁都要走一次共识（毫秒级）。

### 5.5 应用场景（速查）

| 场景 | 推荐强度 | 说明 |
| --- | --- | --- |
| 定时任务防重复执行 | 逻辑锁 或 唯一性索引锁 | 宁可跳过一次也不要双跑；用分片逻辑最省事 |
| 防止重复下单 / 幂等去重 | 唯一性索引（业务唯一键） | 用**业务唯一键**比用锁更自然，见 [10](10-幂等接口.md) |
| 库存扣减 | 一致性锁 或 **CAS 乐观扣减** | 高并发下应优先用 `UPDATE ... WHERE stock >= n` 的原子更新，而不是加锁 |
| 主节点选举 / 脑裂防护 | 一致性锁（租约） | 必须带 fencing token，见下 |
| 缓存击穿防护 | 唯一性校验锁（短 TTL） | 偶发失效可接受 |

### 教学示意：Redis 锁 + fencing token

```lua
-- 教学示意：Redis 加锁与解锁（Lua 保证原子）；不参与构建，不执行。
-- 加锁：SET lock_key <uuid> NX PX 30000     （NX = 仅不存在时，PX = 毫秒过期）
-- 解锁：校验 uuid 再删，必须用 Lua 保证「比较 + 删除」原子
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0    -- 不是自己的锁，绝不能删
end
```

```python
# 教学示意：为什么需要 fencing token；不参与构建，不运行。
class Resource:
    def __init__(self): self.last_token = 0
    def write(self, token, value):
        if token < self.last_token:
            raise StaleLock("锁已过期，拒绝这次写入")   # ★ 资源侧自卫
        self.last_token = token
        self.value = value

# 时间线：
#   t0: 客户端 A 获得锁（token=33），随后发生 GC STW / 网络卡顿
#   t1: 锁 TTL 到期，客户端 B 获得锁（token=34）并写入
#   t2: A 恢复，仍以为自己持有锁，发起写入（token=33）
#   → 没有 fencing：B 的写入被 A 覆盖，且 A 毫不知情
#   → 有 fencing：资源侧记住 last_token=34，拒绝 token=33
```

```text
# 教学示意：四种实现的「权威强度」阶梯（文本图，不参与构建）

逻辑锁        无权威（靠不争抢）        → 成本 0，强度 0
唯一性索引锁  数据库约束即权威          → 成本低，强度中（依赖 DB 高可用）
唯一性校验锁  KV 单命令原子即权威        → 成本低，强度中（复制异步有窗口）
一致性锁      共识日志即权威            → 成本高（每次共识 RTT），强度高
                                        ↑ 越往上越接近「唯一性」的真正含义
```

## 版本演进

- **版本情况**：本书第 1 版（2022-01）；**第 2 版未核实到，标注「待核验」**。以下记录分布式锁实践的演进。
- **三个阶段**：
  1. **1978–1989（理论）**：Lamport 的逻辑时钟与全序化（CACM 1978）让「按序裁决请求」成为可能；
     Ricart-Agrawala（CACM 1981）给出教科书级互斥算法；**租约**（Gray & Cheriton, SOSP 1989）引入「有期限的授权」，
     把「崩溃不释放」这个死结变成可解问题；
  2. **2006–2010（组件化）**：Chubby（OSDI 2006）与 ZooKeeper（ATC 2010）把分布式锁做成**服务**，
     应用不再自己实现协议，只需「创建临时节点 / 创建租约」；
  3. **2016–2026（反思与收敛）**：Kleppmann 对 Redlock 的公开批评（2016）与 antirez 的回应，
     让「**锁必须配 fencing token**」成为行业共识；etcd 的 lease + 事务（CAS）成为 K8s 生态的默认做法；
     「能用乐观并发就别用锁」重新成为首选。
- 🔧 **2022 → 2026**：
  - 共识组件的锁接口进一步标准化（etcd 的 `lease` + `txn`，K8s 的 `coordination.k8s.io/Lease`）；
  - 云原生场景下「分布式锁」大量被**平台能力**替代（K8s 的 leader election、Job 的 `parallelism`、Operator 的单实例约束）。

## 近年研究与工业界开源实践（2015–2026）

- **共识组件做锁（star 均为 2026-09 `gh api` 实测）**：
  - `etcd-io/etcd`（≈52.3k★）：**lease + txn（CAS）** 是 K8s 生态的标准锁/选主做法；
    `concurrency` 包封装了 Session、Mutex、Election；
  - `apache/zookeeper`（≈12.8k★）+ `apache/curator`（≈3.2k★）：Curator 的 `InterProcessMutex`
    把「顺序临时节点 + Watcher」封装成可重入锁，并处理了羊群效应（见 [12](12-ZooKeeper详解与再论分布式系统.md)）；
  - `hashicorp/consul`（≈30.1k★）：session + KV 锁，AP 倾向下更强调 TTL 兜底。
- **KV / 缓存侧实现**：
  - `redisson/redisson`（≈24.4k★）：Redis 分布式锁的 Java 事实标准，带 watchdog 自动续期、可重入、红锁实现；
  - `redis/redis`（≈76.5k★）：`SET key val NX PX ms` 是本章 5.4.3 的原始命令；Redlock 属其官方推荐之一（有争议）；
  - `hazelcast/hazelcast`（≈6.6k★）等内存数据网格也提供分布式锁，但同样受复制模型影响。
- 🔧 **2026 视角：能不用锁就别用锁**：
  - 数据库侧：`UPDATE ... SET stock = stock - n WHERE id = ? AND stock >= n` 是**原子条件更新**，
    用乐观并发把「互斥」下推给存储引擎，吞吐远高于加锁；
  - 消息侧：把同一 key 的请求路由到同一分区（Kafka 的 key 分区）顺序处理，用**分区有序**替代互斥；
  - 平台侧：Kubernetes 的 Lease API 与 leader election 已经把「单实例」做成平台能力，无需自己实现锁。
- **争议的现状**：Redlock 的正确性讨论（2016 起）至今没有定论；
  社区主流建议是**关键场景不用纯 Redis 锁，改用共识组件**（etcd/ZK），并把 fencing token 写进资源侧。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「分布式锁能像内存锁一样保护临界区」 | 它只保护**约定**；绕过锁的写路径锁拦不住（本书 5.2.3「遵从性」已指出） |
| 2 | 「加了过期时间就安全了」 | 过期只解决「崩溃不释放」，却引入「持有者还在但锁已过期」→ 需要 fencing token 让资源侧自卫 |
| 3 | 「`SETNX` 后再 `EXPIRE` 就行」 | 两步之间崩溃 → 永久锁；必须**单命令** `SET key val NX PX ttl` |
| 4 | 「解锁直接 `DEL` 就行」 | 必须校验持有者标识并原子执行，否则会删掉别人刚获得的锁 |
| 5 | 「锁有 TTL 就不需要考虑 GC STW」 | STW 可能超过 TTL；资源侧没有 fencing 时，过期持有者的写入会静默覆盖新持有者的写入 |
| 6 | 「分布式锁能解决分布式事务」 | 锁只做互斥，不提供原子提交；跨资源一致性要事务或 Saga（[07](07-分布式事务.md)） |
| 7 | 「逻辑锁也是锁」 | 它靠「不争抢」消解互斥，成本低但**不提供真正的互斥保证**；场景不匹配会出双跑 |
| 8 | 🔧 本书需 2026 补丁 | 5.4.3/5.4.4 应显式引入 **fencing token**（或版本号 CAS）：这是 2016 年后关于分布式锁最重要的行业共识 |
| 9 | 🔧 本书需 2026 补丁 | 应补 **Redlock 争议**：Redlock 自 2016 年起存在公开的正确性质疑，关键场景建议改用共识组件 |
| 10 | 🔧 本书需 2026 补丁 | 应补 **平台化替代**：K8s Lease / leader election、按 key 分区顺序消费、数据库条件更新——很多场景下「不需要分布式锁」才是正解 |
| 11 | 🔧 本书需 2026 补丁 | 「锁的客户端一致性职责」（重试、超时、时钟）已部分下沉到服务网格，但**锁本身的语义不会因此变强**，不要混淆 |
