# 第 6 章 分布式事务（实践篇）

> → 应用内多数据库事务方案（6.4）→ 单体应用间事务方案（6.5：**化为本地事务 / 化为应用内多数据库事务 / TCC /
> 本地异步消息机制 / 异步消息中心机制**）→ 近似事务（6.6）。

## 本章地图

- 位置：实践篇第 6 章，紧接第 5 章（锁）。第 5 章解决**互斥**，第 6 章解决**原子性**。
- 主线：
  1. 先把「分布式事务」按**边界**分类（这是本书最有特色的一节）；
  2. 对每一类给出「**降级**」方案——注意关键词是降级，不是「实现分布式事务」；
  3. 全书实践篇的方法论在这里定型：**先想办法把分布式事务降级成本地事务，降不掉再谈协议**。
- 🔧 这个思路与本章文献表里 Helland 2007 那篇著名论文（*Life beyond Distributed Transactions*）一脉相承：
  工业界的共识从来不是「如何做好分布式事务」，而是「**如何避免它**」。
- 🔧 与理论篇的接缝：[03](03-两阶段提交与三阶段提交.md) 讲清了 2PC 的代价，
  本章的 TCC、本地异步消息、异步消息中心三节，本质上都是「绕开 2PC」的工程答案。

## 核心精讲

（以下伪代码与示意图均为**教学示意，不参与构建**。）

### 6.1 本地事务与分布式事务

| 维度 | 本地事务 | 分布式事务 |
| --- | --- | --- |
| 参与者 | 一个数据库（一个资源管理器） | 多个数据库 / 多个服务 / 多个系统 |
| 原子性保障 | 数据库的 WAL + 锁/MVCC | 需要额外的提交协议或补偿机制 |
| 典型成本 | 微秒~毫秒级 | 毫秒~秒级（多轮协调 + 长锁持有） |
| 失败模式 | 回滚即可 | 部分提交、未决、补偿失败 |

- 🔧 判断标准很朴素：**原子性是由谁提供的**。
  只要原子性仍由**单个数据库的本地事务**提供，就不算真正的分布式事务——
  本章 6.5.1「化为本地事务」正是利用这一点把问题消解掉。

### 6.2–6.3 按「边界」给分布式事务分类（本书特色）

> 以下四类之名照抄本书 6.2 的小节标题（6.2.1–6.2.4）。
> 各类在书中的**精确界定与举例未能逐条核实原文**，表格中的「跨越什么边界 / 典型场景」是依据小节标题给出的**笔记口径判读**，
> 供阅读时定位用，不冒充原文定义。

| 类别（原书小节标题） | 跨越的边界（笔记判读） | 典型场景 | 难度 |
| --- | --- | --- | --- |
| **应用内多数据库事务**（6.2.1） | 同一应用进程内，跨越**多个数据库实例** | 分库分表后一次业务改两个库 | 低：可用 XA / 2PC，参与者都是数据库 |
| **单体应用间事务**（6.2.2） | 跨越**多个单体应用**（各自有自己的库） | 订单系统 ↔ 库存系统 | 中：需要跨进程的协调或补偿 |
| **分布式系统内事务**（6.2.3） | 同一个分布式系统内部，跨**多个服务/分片** | 微服务内部一次链路改多处 | 中高：节点多、故障面大 |
| **分布式系统间事务**（6.2.4） | 跨越**不同的组织/系统边界** | 跨公司对接、支付清算 | 高：无法要求对方配合做 Prepare，只能靠对账与补偿 |

- 🔧 这条分类轴的价值在于：**它把「技术难度」翻译成「你能在多大程度上要求对方配合」**。
  - 参与者都是自己可控的数据库 → 可以上 2PC/XA；
  - 参与者是别人的系统 → 对方不会为你实现 Prepare 接口，只能靠**消息 + 幂等 + 对账**。
- **6.3 类别总结**的核心结论（笔记口径）：**边界越靠外，「协议式」方案越失效，「消息 + 补偿 + 对账」越成为唯一解**。

### 6.4 应用内多数据库事务方案

- 首选：**XA / 2PC**（[03](03-两阶段提交与三阶段提交.md)），由数据库原生支持；
- 备选：**化为本地事务**——把跨库操作重排，使每个库内的操作各自成为一个本地事务，靠业务顺序与补偿衔接；
- 实用优化：
  - **按同一维度分片**（把相关的行放到同一个库），让跨库变单库；
  - **把最关键的写放在最后一个库**，前面的失败用补偿回滚；
  - 🔧 现代分片中间件（如 `apache/shardingsphere`，≈20.8k★，2026-09 实测）提供 XA/BASE（Saga）两种模式的显式选择，
    正是本书这一节的开源对照物。

### 6.5 单体应用间事务方案（本章的重头戏）

| 方案（原书小节） | 核心思路 | 一致性强度 | 代价 |
| --- | --- | --- | --- |
| **化为本地事务**（6.5.1） | 重新划分数据与职责，让一次业务只落在一个库里 | 强（本地事务） | 需要**业务与数据模型改造**，常常是最划算的方案 |
| **化为应用内多数据库事务**（6.5.2） | 把跨应用调用改成「一个应用直接访问多个库」，再用 XA/2PC | 强（2PC） | 破坏了应用边界（耦合回退）；2PC 的阻塞与锁代价 |
| **TCC**（6.5.3） | Try（预留资源）/ Confirm（确认）/ Cancel（释放预留）三阶段，由业务代码实现 | 最终一致（有预留隔离） | 每个参与者都要写三段代码；Confirm/Cancel 必须幂等 |
| **本地异步消息机制**（6.5.4） | 本地事务里同时写业务数据与「待发送的消息表」（Outbox），后台任务投递 | 最终一致 | 需要额外表 + 投递任务 + 消费端幂等 |
| **异步消息中心机制**（6.5.5） | 引入独立消息中间件做事务消息（半消息 / 事务消息 + 回查） | 最终一致 | 依赖 MQ 的事务消息能力；仍需消费端幂等与对账 |

- 🔧 **TCC 的三个动作**（Helland 2007 提出 Tentative/Confirm/Cancel，中文社区常称 Try/Confirm/Cancel）：
  - **Try**：**预留**资源（冻结库存、预扣额度），不产生最终效果；
  - **Confirm**：确认执行，把预留转成最终结果（必须幂等，且理论上不应失败）；
  - **Cancel**：释放预留（必须幂等）。
  - 与 2PC 的本质差别：**TCC 在业务层预留，2PC 在资源层加锁**。
    因此 TCC 的锁粒度更粗但**锁持有时间由业务控制**，且不依赖数据库的 Prepare 接口——这是它能跨系统工作的原因。
- 🔧 **本地异步消息机制（Outbox）** 是本章最值得记住的工程模式：
  1. 在同一个本地事务里写「业务数据」和「Outbox 表一条消息」；
  2. 后台线程轮询 Outbox 投递到 MQ，成功后标记已发送；
  3. 消费端**必须幂等**（[10](10-幂等接口.md)），因为投递是至少一次的。
  它把「数据库 + MQ 的原子性」问题，降级为「**单机事务 + 至少一次投递 + 消费端幂等**」——
  2026 年这一模式常进一步升级为 **CDC**（见近年段）。

### 6.6 近似事务

- 「近似事务」指**不追求严格原子性，只追求业务可接受的结果**的方案族：
  最大努力通知、定时对账与冲正、补偿重试、人工兜底。
- 🔧 它不是「偷懒」，而是**分布式事务的最终形态**：
  当边界跨到外部系统（6.2.4）时，对账与冲正是**唯一**可靠的手段。
  成熟系统的标配是「自动补偿 + 定时对账 + 差异告警 + 人工介入通道」四件套。

### 教学示意：TCC 与 Outbox

```python
# 教学示意：TCC 的三个动作（库存服务）；不参与构建，不运行。
class InventoryService:
    def try_reserve(self, order_id, sku, n):
        # 幂等：同一 order_id 重复调用只预留一次
        if self.reservations.exists(order_id): return "already"
        self.db.execute("UPDATE stock SET frozen = frozen + %s, avail = avail - %s "
                        "WHERE sku = %s AND avail >= %s", (n, n, sku, n))
        self.reservations.insert(order_id, sku, n)   # ★ 预留记录，用于 Confirm/Cancel 去重

    def confirm(self, order_id, sku, n):
        if not self.reservations.exists(order_id): return "noop"   # 幂等
        self.db.execute("UPDATE stock SET frozen = frozen - %s WHERE sku = %s", (n, sku))
        self.reservations.mark_done(order_id)

    def cancel(self, order_id, sku, n):
        if not self.reservations.exists(order_id): return "noop"   # 幂等
        self.db.execute("UPDATE stock SET frozen = frozen - %s, avail = avail + %s "
                        "WHERE sku = %s", (n, sku, n))
        self.reservations.mark_done(order_id)
```

## 版本演进

- **版本情况**：本书第 1 版（2022-01）；**第 2 版未核实到，标注「待核验」**。以下记录分布式事务方案的演进。
- **四个阶段**：
  1. **1978–1987（协议时代）**：2PC（Gray 1978）、R* 的工程优化（TODS 1986）、
     Sagas（Garcia-Molina & Salem, SIGMOD 1987）给出长事务的补偿解法；
  2. **2005–2007（反思时代）**：Helland 的 CIDR 2005（内外数据之分）与 CIDR 2007（*Life beyond Distributed Transactions*）
     明确了「避免分布式事务」的工业立场，并给出 Tentative/Confirm/Cancel（TCC）的活动模型；
  3. **2010–2012（强一致复兴）**：Percolator（OSDI 2010）、Spanner（OSDI 2012）、F1（VLDB 2012）
     证明「全球规模的强一致事务」在工程上可行，代价是专用硬件时钟与共识复制；
  4. **2015–2026（事件驱动时代）**：事件溯源、Outbox、CDC、流处理与工作流引擎（Saga 编排）成为主流，
     「补偿」从手写代码变成平台能力。
- 🔧 **2022 → 2026**：
  - **CDC + 流处理取代双写**成为默认范式：不再在业务代码里同时写库与写 MQ，
    而是只写库、由 CDC 捕获变更、由流处理投递（详见近年段）；
  - **Saga 编排（orchestration）**借助工作流引擎复兴（`temporalio/temporal` 一类），
    把「补偿逻辑写在哪」这个问题交给基础设施；
  - **Multi-Raft + 并行提交**让「真·分布式事务」的延迟降到可商用区间，缩小了「绕开事务」的必要性。

## 近年研究与工业界开源实践（2015–2026）

- **事务框架（star 均为 2026-09 `gh api` 实测）**：
  - `seata/seata`（≈26.0k★）：**AT / TCC / Saga / XA** 四模式并存，是本书本章最完整的开源对照物；
  - `dtm-labs/dtm`（≈10.9k★）：跨语言事务管理器，支持 Saga、TCC、XA、二阶段消息；
  - `temporalio/temporal`（≈23.3k★）：持久化工作流，把 Saga 的**编排**变成普通代码（补偿失败可重试、可观测）。
- **强一致分布式数据库的当代形态**：
  - `pingcap/tidb`（≈40.6k★）：Percolator 系，乐观/悲观事务 + 分布式死锁检测，Multi-Raft 支撑分片；
  - `cockroachdb/cockroach`（≈32.5k★）：HLC + 串行化快照 + 并行提交，把 2PC 延迟压低。
- 🔧 **CDC + 流处理取代双写（2026 年最值得记住的一条）**：
  - `debezium/debezium`（≈13.2k★）：捕获数据库变更日志（binlog/WAL）成为事件流；
  - `apache/flink-cdc`（≈6.5k★）：把 CDC 直接接进流处理作业；
  - 组合拳：**单机事务（写库 + Outbox）→ CDC 捕获 → 至少一次投递 → 消费端幂等**，
    把本章 6.5.4 的手写投递任务升级为平台能力；
  - 它同时也消灭了「双写不一致」这一类生产事故——因为根本不再有双写。
- **事务消息**：`apache/rocketmq`（≈22.6k★）的事务消息（半消息 + 事务回查）是本书 6.5.5「异步消息中心机制」的工业实现；
  `apache/kafka`（≈33.8k★）则通过幂等生产者 + 事务 API 提供 exactly-once 的流处理语义。
- **分片中间件**：`apache/shardingsphere`（≈20.8k★）把 XA 与 BASE（Saga）做成可切换配置，
  直观展示了本章「按边界选方案」的思想如何落到框架里。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「TCC 就是业务版的 2PC」 | 2PC 在**资源层加锁**，TCC 在**业务层预留**；TCC 不依赖参与者的 Prepare 接口，因此能跨系统 |
| 2 | 「Saga 就是分布式事务」 | Saga 只保证「最终一致」：**没有隔离性**，中间状态对外可见，需要业务容忍或额外封锁 |
| 3 | 「用了事务消息就不用做幂等」 | 事务消息保证「消息与本地事务一致地发出」，**不保证只消费一次**；消费端幂等仍必需 |
| 4 | 「Outbox 是多此一举，直接双写就行」 | 双写在「写库成功、发消息失败」时永久不一致；Outbox 用本地事务把二者绑死 |
| 5 | 「TCC 的 Confirm 不会失败」 | 只是**应该**不失败（前置资源已预留）；网络故障仍可能失败，必须可重试且幂等 |
| 6 | 「分布式事务一定比本地事务慢很多，所以永远别用」 | 现代 Multi-Raft + 并行提交已把开销压到可接受；是否使用取决于**业务能否接受最终一致** |
| 7 | 「补偿能把错误改回原样」 | 补偿是**业务上的反向操作**（退款≠撤销），不是回滚；已被外部观察到的影响无法撤回 |
| 8 | 🔧 本书需 2026 补丁 | 6.5.4 的「本地异步消息机制」应升级为 **Outbox + CDC**：手写一个轮询投递任务在 2026 年已被平台化方案取代 |
| 9 | 🔧 本书需 2026 补丁 | 本章未覆盖 **Saga 的编排 vs 协同（orchestration vs choreography）** 与**工作流引擎**：这是长事务补偿在 2026 年的主流承载方式 |
| 10 | 🔧 本书需 2026 补丁 | 本章未覆盖 **CDC + 流处理取代双写** 的整体范式，也未覆盖 **确定性事务**（Calvin 系）这条「先定序再执行」的路线 |
| 11 | 🔧 本书需 2026 补丁 | 6.2 的四类划分很有价值，但缺一条当代常用判据：**参与者是否受你控制**（能否要求它实现 Prepare/预留接口），这直接决定只能走消息+对账 |
