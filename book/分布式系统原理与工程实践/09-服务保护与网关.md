# 第 8 章 服务保护与网关（实践篇）

> **本章地图**：服务保护的理论依据（8.1.1）→ **隔离**（8.1.2）→ **限流**（8.1.3）→ **降级**（8.1.4）
> → **熔断**（8.1.5）→ **恢复**（8.1.6）→ 服务网关的产生背景、功能与结构（8.2）。

## 本章地图

- 位置：实践篇第 8 章，紧接第 7 章（服务发现与调用）。
  第 7 章解决「**找得到、调得通**」，第 8 章解决「**对方不稳时我怎么活**」。
- 主线（五个手段是一条递进的防线）：
  1. **隔离**：先把故障**限制在局部**（舱壁/线程池/信号量）；
  2. **限流**：从**入口**控制进入系统的量（令牌桶/漏桶/滑动窗口）；
  3. **降级**：量太大或依赖不可用时，**牺牲非核心**（返回兜底值、关闭功能）；
  4. **熔断**：依赖已经坏了，**干脆别调**（快速失败，给对方恢复时间）；
  5. **恢复**：验证对方是否恢复，**半开探测**逐步放量。
- 🔧 本章与 [05-CAP与BASE定理.md](05-CAP与BASE定理.md) 的对应关系很直接：
  **BASE 的「基本可用（Basically Available）」就是这五个手段的具体实现**。
- 🔧 2026 补丁：本章的五个手段依然成立，但实现方式变了——
  **自适应并发限制**（不再靠人填固定阈值）、**服务网格统一治理**、**混沌工程验证有效性**、
  **OpenTelemetry 提供判断依据**，这四件事是 2022 年之后最重要的补充。

### 8.1.1 理论依据（笔记判读，未逐条核实原文）

- 本章 8.1.1 给出的「理论依据」，按小节标题与后续五节的展开方式判断，
  其作用是说明**「为什么过载必须主动拒绝，而不是排队硬扛」**。
  常见的支撑理论是排队论的基本关系 **利特尔法则（Little's Law）**：`L = λ · W`
  （系统中平均请求数 = 到达率 × 平均停留时间）。
- 🔧 由此得到工程上最重要的一条推论：
  - 当到达率 λ 接近服务速率上限时，**排队长度与响应时间呈非线性（趋于发散）增长**；
  - **排队本身会消耗内存与连接**，排队越久，能服务的请求越少 → 恶性循环；
  - 因此**在系统过载时，主动拒绝（快速失败）比排队等待更能保住吞吐**。
- 这条推论是本章后面所有手段的共同理论基础：**宁可拒绝一部分，也不要让全部变慢**。
- ⚠️ 说明：以上为**笔记口径的判读**，本书 8.1.1 的具体论证（是否使用利特尔法则、是否引用排队论公式）
  **未能核实原文**，标注为「未能核实原文，存疑」，不冒充原书观点。

### 8.1.2 隔离（Bulkhead）

| 隔离方式 | 做法 | 代价 | 适用 |
| --- | --- | --- | --- |
| **线程池隔离** | 每个依赖一个独立线程池，池满即拒绝 | 线程上下文切换开销；池数量多时内存压力大 | 依赖响应时间差异大、需要超时控制 |
| **信号量隔离** | 每个依赖一个计数信号量，达到上限即拒绝 | 无排队/无超时（调用在业务线程内执行） | 高频、低延迟、内部调用 |
| **物理/集群隔离** | 重要业务独占机器或独占集群 | 成本高 | 核心链路、多租户隔离 |
| **数据隔离** | 分库分表、按租户分片 | 跨片操作复杂 | 防止一个租户拖垮全局 |

- 🔧 隔离的本质：**把「共享资源」切成互不相干的份额**，使一个依赖的故障不会耗尽全局资源。
  这也是为什么它排在五个手段的第一位——**不隔离的话，其他手段都无从谈起**。

### 8.1.3 限流（Rate Limiting）

| 算法 | 机制 | 特点 |
| --- | --- | --- |
| **固定窗口计数** | 每个时间窗内计数，超限拒绝 | 简单；**窗口边界可能放过 2 倍流量**（临界突刺） |
| **滑动窗口** | 把窗口切成小格，按格加权统计 | 平滑；内存与实现成本略高 |
| **漏桶（Leaky Bucket）** | 请求入桶，桶以固定速率出水 | **强制匀速**，无法应对合理突发 |
| **令牌桶（Token Bucket）** | 以固定速率生成令牌，请求取令牌 | **允许突发**（桶内积攒的令牌），工程上最常用 |
| **并发数限制** | 限制同时在处理的请求数 | 与延迟直接相关，比 QPS 更贴近系统容量 |

- 🔧 **限流位置的三层**（推荐层层设置）：
  1. **网关/接入层**：挡住总量与 obvious 的异常流量；
  2. **服务间调用（客户端侧）**：保护自己不被下游拖垮，也防止打爆下游；
  3. **资源层（线程池、连接池、数据库连接数）**：最后一道硬边界。
- 🔧 **限流依据什么指标**：QPS 是最常见的，但**并发数与「系统负载指标」更靠谱**——
  固定 QPS 阈值在系统变慢时会失准（响应变慢 → 实际并发翻倍 → 雪崩）。
  这正是 2026 年「**自适应并发限制**」要解决的问题（见近年段）。

### 8.1.4 降级（Degradation）

- 定义：**在系统压力过大或依赖不可用时，主动关闭/简化非核心功能，保证核心链路可用**。
- 常见降级手段：
  - 返回**兜底数据**（缓存旧值、默认推荐列表、静态页）；
  - 关闭**非核心功能**（评论、推荐、积分、营销）；
  - **异步化**（把同步写改为写日志后异步处理）；
  - **读降级**（从主库读改从从库读；从强一致读改最终一致读）。
- 🔧 降级的前提是**分级**：必须事先明确「核心链路」与「可牺牲项」，
  否则故障发生时只能临时拍脑袋——**降级预案要在平时演练，而不是在故障时设计**。

### 8.1.5 熔断（Circuit Breaker）

```text
# 教学示意：熔断器三态机（文本图，不参与构建）

       [CLOSED 关闭] ── 连续失败达到阈值 ──▶ [OPEN 打开]
            ▲                                      │
            │                                      │ 快速失败（不再调用下游）
            │                                      ▼
            │                             [HALF-OPEN 半开]
            └──── 探测成功并达到阈值 ◀──── 放行少量探测请求
                        │
                        └── 探测失败 ──▶ 回到 OPEN（重新计时）
```

- 三态含义：
  - **CLOSED**：正常放行，统计失败率/慢调用率；
  - **OPEN**：直接返回错误或走降级逻辑，**不再调用下游**（给下游恢复时间）；
  - **HALF-OPEN**：放行少量探测请求，成功则关闭熔断，失败则重新打开。
- 🔧 熔断与降级的关系：**熔断是触发条件，降级是 fallback 动作**。
  只熔断不降级 = 用户直接看到错误页；只降级不熔断 = 每次仍要等超时才知道失败。两者应成对配置。

### 8.1.6 恢复（Recovery）

- 恢复要解决的是「**什么时候可以重新放量**」：
  - **半开探测**（8.1.5 的 HALF-OPEN）是最常见的机制；
  - **逐步放量**：不要从 0 直接到 100%，按固定比例或指数方式恢复（防二次打垮）；
  - **重置统计窗口**：恢复后要清空失败计数，否则旧数据会立刻再次触发熔断。
- 🔧 最难的一条：**下游恢复时往往是最脆弱的时刻**（缓存冷、连接池空、JIT 未热），
  一次性放量极易造成「恢复 → 立刻再崩」的**亚稳态故障**（metastable failure，见文献表）。

### 8.2 服务网关

- **产生背景**（8.2.1）：服务数量增长后，每个服务各自实现鉴权、限流、日志、协议转换，
  既重复又难以统一治理 → 抽出一个**统一入口**。
- **功能**（8.2.2）：
  路由与负载均衡、鉴权与鉴权下发、限流与熔断、协议转换（HTTP↔gRPC、REST↔内部协议）、
  请求/响应改写、灰度与流量镜像、日志与追踪埋点、跨域与 TLS 终结。
- **结构**（8.2.3）：通常是「**控制面 + 数据面**」——
  控制面管配置与下发，数据面（Nginx/Envoy/APISIX/Kong）负责实际转发。
- 🔧 2026 视角：网关与**服务网格**的边界在收敛：
  「南北向流量（外部进入）」归 API 网关，「东西向流量（服务间）」归网格，两者**共用同一套策略语言与遥测**。

### 教学示意：令牌桶与熔断器

```python
# 教学示意：令牌桶限流器；不参与构建，不运行。
import time
class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate, self.capacity = rate, capacity   # rate: 令牌/秒
        self.tokens, self.last = capacity, time.time()
    def allow(self, n=1):
        now = time.time()
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= n:
            self.tokens -= n
            return True                              # 允许（可突发直到桶空）
        return False                                 # 拒绝（快速失败，不排队）
```

```python
# 教学示意：熔断器三态；不参与构建，不运行。
class CircuitBreaker:
    def __init__(self, fail_threshold, reset_timeout):
        self.state, self.fails = "CLOSED", 0
        self.fail_threshold, self.reset_timeout = fail_threshold, reset_timeout
        self.opened_at = None

    def call(self, fn, fallback):
        if self.state == "OPEN":
            if time.time() - self.opened_at < self.reset_timeout:
                return fallback()                    # 快速失败 + 降级
            self.state = "HALF-OPEN"; self.fails = 0
        try:
            r = fn()
            if self.state == "HALF-OPEN":
                self.state = "CLOSED"; self.fails = 0   # 探测成功 → 关闭
            return r
        except Exception:
            self.fails += 1
            if self.fails >= self.fail_threshold:
                self.state, self.opened_at = "OPEN", time.time()
            return fallback()
```

## 版本演进

- **版本情况**：本书第 1 版（2022-01）；**第 2 版未核实到，标注「待核验」**。以下记录本章主题的演进。
- **三个代际**：
  1. **1993–2007（理论与方法）**：网络侧的随机早期检测 RED（Floyd & Jacobson, ToN 1993）
     确立「过载要主动丢弃」的思想；Nygard《Release It!》（2007）把**舱壁（Bulkhead）**与
     **熔断器（Circuit Breaker）**作为模式固定下来；
  2. **2011–2018（库化）**：Netflix Hystrix（2011 起）把隔离/熔断/降级做成一个库；
     Google SRE 书（2016）系统化了「过载处理与优雅降级」；Dean & Barroso《The Tail at Scale》（CACM 2013）
     给出对冲请求（hedged requests）等长尾治理手段；
  3. **2018–2026（自适应与平台化）**：Netflix 提出**自适应并发限制**（梯度算法，2018，技术博文），
     Envoy 将其实现为自适应并发过滤器；治理下沉到服务网格；**混沌工程**成为检验手段；
     OSDI 2022 的《Metastable Failures in the Wild》系统刻画了「恢复即再崩」这类反直觉故障。
- 🔧 **2022 → 2026 的四条补丁**：
  1. **从固定阈值到自适应**：QPS 阈值在系统变慢时失效，改为按延迟反馈动态调整并发上限；
  2. **从应用库到基础设施**：重试/超时/熔断下沉到 sidecar（承接 [08](08-服务发现与调用.md)）；
  3. **从「相信配置」到「混沌验证」**：限流熔断是否真的生效，靠故障注入演练证明；
  4. **从各自埋点到 OpenTelemetry**：判断该不该限流、该熔断谁，依赖统一的 trace/metrics。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「限流和熔断是一回事」 | 限流**控进入的量**（防自己被打爆）；熔断**断掉对坏依赖的调用**（防被下游拖垮） |
| 2 | 「熔断了就是降级了」 | 熔断是**触发条件**，降级是 **fallback 动作**；只熔断不降级 = 用户直面错误 |
| 3 | 「线程池隔离最安全，全都用线程池」 | 线程池有切换开销与内存成本；高频低延迟的内部调用更适合**信号量隔离** |
| 4 | 「限流阈值设成压测峰值即可」 | 系统变慢时 QPS 不变而并发翻倍；应以**并发数/延迟反馈**为准，或用自适应限流 |
| 5 | 「过载时排队比拒绝更友好」 | 排队会吃掉连接与内存并放大延迟，最终**全部超时**；主动拒绝才能保住有效吞吐 |
| 6 | 「熔断恢复后可以立刻全量放量」 | 恢复瞬间下游最脆弱（缓存冷、连接池空），应**半开探测 + 逐步放量** |
| 7 | 「网关上限流就够了」 | 网关只挡南北向；服务间（东西向）的**重试风暴与扇出放大**必须在调用侧治理 |
| 8 | 🔧 本书需 2026 补丁 | 本章阈值是**静态配置**；2026 主流做法是**自适应并发限制**（按延迟反馈动态调整） |
| 9 | 🔧 本书需 2026 补丁 | 本章未覆盖**混沌工程**：保护策略必须靠故障注入演练证明有效，而不是靠评审通过 |
| 10 | 🔧 本书需 2026 补丁 | 本章未覆盖 **OpenTelemetry 统一可观测性**：没有统一 trace/metrics，就无法判断该限谁、该熔断谁 |
| 11 | 🔧 本书需 2026 补丁 | 8.2 网关与**服务网格**的职责边界在 2026 年已收敛为「南北向网关 + 东西向网格 + 共享策略与遥测」，应补入 |
