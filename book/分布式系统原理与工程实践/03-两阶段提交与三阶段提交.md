## 核心精讲

（以下伪代码与状态机均为**教学示意，不参与构建**。）

### 2.4.1 2PC 的角色与两个阶段

- **两个角色**：
  - **协调者（Coordinator）**：通常由发起事务的应用/事务管理器担任，持有全局事务 ID，负责收集投票并下达最终决定；
  - **参与者（Participant）**：各个资源管理节点（数据库分片、消息队列、远程服务），各自在本地执行并**先不提交**。
- **两个阶段**：

| 阶段 | 协调者动作 | 参与者动作 | 落盘要求 |
| --- | --- | --- | --- |
| **阶段一：投票（Prepare / Voting）** | 向所有参与者发 `PREPARE` | 执行本地操作、写 undo/redo 日志、**锁住相关资源**，回复 `YES`（准备好）或 `NO` | 参与者必须先把「准备」这一事实**持久化**，否则崩溃后无法回答 |
| **阶段二：提交（Commit / Abort）** | 全票 YES → 写 `COMMIT` 记录并广播 `COMMIT`；否则广播 `ABORT` | 按指令提交或回滚，释放锁，回复 `ACK` | 协调者必须先写决定再广播，否则崩溃后参与者无从得知结果 |

### 2.4.2 为什么 2PC 能被论证为「线性一致」

- 论证的关键在于：**提交点是一个全局唯一的瞬间**。
  - 所有参与者都在 `PREPARE` 后处于「未决（in-doubt）」状态，对外不可见；
  - 协调者一旦写下 `COMMIT` 记录，事务的**生效点**就唯一确定了；
  - 此后任何读到的数据都包含这次写，之前的都不包含 → 满足 [02](02-一致性的概念与强弱.md) 里线性一致性的定义。
- 🔧 要补充两点本书未必展开的细节：
  1. **锁的持有期**：为保证多对象事务的原子可见，参与者的锁必须**持有到第二阶段结束**。
     这才是 2PC 性能差的根因——不是多发了两条消息，而是**把锁持有时间拉长到了两轮 RTT**。
  2. **未决状态需要人工/协议兜底**：协调者崩溃后，参与者手上那些「已 PREPARE 但未收到决定」的事务，
     只能**阻塞等待**协调者恢复，或者按预设策略（presumed abort / presumed commit）处理。

### 2.4.3 2PC 的优劣

| 优点 | 缺点 |
| --- | --- |
| 语义强：**原子提交**，参与者看到「全做或全不做」 | **同步阻塞**：参与者在 Prepare 后必须持锁等待，吞吐受最慢节点拖累 |
| 实现简单，是 XA 规范与绝大多数数据库的标准能力 | **协调者单点**：协调者在阶段二崩溃 → 参与者永久未决（除非有高可用协调者） |
| 与本地事务无缝衔接（参与者就是本地事务） | **无容错性**：协调者 + 某参与者同时崩溃，剩余节点无法自行决定（这正是它「不是共识」的理由） |
| — | **锁争用放大**：跨节点事务把锁范围从单机扩大到跨节点，死锁与超时概率上升 |

### 2.5.1 3PC：加一个「预提交」

- 思路：在 2PC 的两阶段之间插入 **PreCommit**，让参与者在「还不知道最终结果」时也能**自行推进**。

| 阶段 | 内容 | 参与者的超时默认动作 |
| --- | --- | --- |
| **CanCommit** | 协调者询问「能不能做」，参与者只做可行性检查，**不写日志不持锁** | 超时 → 自行中止 |
| **PreCommit** | 协调者写预提交记录并广播；参与者写 undo/redo 日志并回复 ACK | 超时（未等到 DoCommit）→ **默认提交** |
| **DoCommit** | 协调者收到全部 ACK → 广播 `COMMIT` | 超时 → 提交（因为已 PreCommit，说明大家都同意了） |

- 🔧 3PC 消除阻塞的机理：
  参与者一旦进入 PreCommit 状态，就知道「**所有人都投了 YES**」这个事实；
  因此即使协调者之后失联，参与者也可以**安全地默认提交**——不会再有人投 NO。
  2PC 里没有这个中间状态，所以参与者在 Prepare 后**不敢自行决定**。

### 2.5.2 3PC 的真实边界（本章最重要的一句修正）

- **3PC 只在「崩溃故障（crash failure）」模型下解决了阻塞**。
- **在网络分区（network partition）模型下，3PC 仍然会产生不一致**：
  分区发生时，一边因超时默认提交，另一边可能收到 `ABORT` 或仍在不确定的分支，两边做出相反决定。
- 这背后是不可绕过的理论：**FLP 不可能结果**（Fischer, Lynch, Paterson, JACM 1985）说明
  **异步系统下只要有一个进程可能失败，就不存在既安全又总能终止的确定性共识算法**；
  3PC 的「超时默认提交」本质上是**用「可能不一致」换了「不阻塞」**——它并没能绕开 FLP。
- 🔧 结论：
  **2PC 的阻塞问题，正确解法不是 3PC，而是把提交协议建立在共识之上**（如 Gray & Lamport 的 Paxos Commit：
  让每个参与者的决定本身由一个 Paxos/Raft 组复制，协调者也成为一个可容错的复制状态机）。
  这也是 Spanner、TiDB、CockroachDB 等现代分布式数据库的做法。

### 教学示意：2PC 的状态机与故障注入点

```python
# 教学示意：最小 2PC 协调者 / 参与者；不参与构建，不运行。
class Coordinator:
    def commit(self, txn, participants):
        votes = []
        for p in participants:
            votes.append(p.prepare(txn))      # ① 网络超时？② 参与者崩溃？
        if all(v is YES for v in votes):
            self.log.write("COMMIT", txn)     # ③ 写决定——必须先落盘再广播
            for p in participants:
                p.do_commit(txn)              # ④ 广播中途协调者崩溃 → 参与者未决
        else:
            self.log.write("ABORT", txn)
            for p in participants:
                p.do_abort(txn)

class Participant:
    def prepare(self, txn):
        self.local_execute(txn)               # 执行但不提交
        self.wal.write("PREPARED", txn)       # ⑤ 崩溃后可恢复的关键记录
        self.lock(txn.keys)                   # ⑥ 锁持有到阶段二结束 ← 性能杀手
        return YES
    def do_commit(self, txn):
        self.wal.write("COMMIT", txn); self.unlock(txn.keys)
    def recover(self):                        # 重启后：向协调者查询未决事务
        for t in self.wal.in_doubt():
            ask_coordinator(t)                # ⑦ 协调者若不可恢复 → 永久阻塞
```

```text
# 教学示意：2PC 与 3PC 的超时行为对照（文本图，不参与构建）

2PC： Prepare 之后参与者处于 in-doubt
       → 协调者失联：只能等待（阻塞），不敢自行决定
       → 因此：协调者必须高可用化（Raft 复制）才能真正可用

3PC： CanCommit → PreCommit → DoCommit
       → PreCommit 之后失联：默认提交（不阻塞）
       → 代价：分区时可能出现「一边提交、一边中止」的决定分歧
       → 因此：3PC 只解决崩溃故障下的阻塞，不解决分区下的不一致
```

## 版本演进

- **版本情况**：本书第 1 版（2022-01）；**第 2 版未核实到，标注「待核验」**。以下记录协议本身的演进脉络。
- **协议演进四步**：
  1. **1976–1978（原型）**：Lampson & Sturgis 的崩溃恢复技术报告、Gray 的《Notes on Data Base Operating Systems》
     给出了两段式原子提交的基本形态；
  2. **1981–1986（系统化）**：Skeen 在 SIGMOD 1981 提出非阻塞提交协议（3PC 的源头）；
     R* 系统在 TODS 1986 系统化了 presumed abort / presumed commit 等优化，让 2PC 真正可用于产品；
  3. **1991（标准化）**：X/Open 发布 **XA** 规范，2PC 成为数据库与中间件的通用接口；
  4. **2006–2012（共识化）**：Gray & Lamport 的《Consensus on Transaction Commit》（TODS 2006）把 2PC 的协调者
     换成 Paxos 组；Spanner（OSDI 2012）与 Percolator（OSDI 2010）把这套思想做成全球规模的工程现实。
- 🔧 **2022 → 2026**：
  - 3PC 在工程上**几乎没有被部署**（本书 2.5.2 的优劣分析已经说明了原因）；
  - 真正流行的是「**2PC 的共识化**」与「**绕开 2PC**」两条路：
    前者是 Paxos Commit / Raft 复制的协调者，后者是 TCC、Saga、Outbox + CDC（见 [07](07-分布式事务.md)）。

## 近年研究与工业界开源实践（2015–2026）

- 🔧 **2PC 的共识化（协调者不再单点）**：
  - `pingcap/tidb`（≈40.6k★，2026-09 `gh api` 实测）：Percolator 模型的开源实现，
    客户端充当协调者，写意图（write intent）与 primary lock 承担原子性；
  - `cockroachdb/cockroach`（≈32.5k★，实测）：并行提交（parallel commits）把 2PC 的「事务记录」状态原子切换，
    把提交延迟从两轮降到一轮，是 Gray & Lamport 思路的新一代工程化；
  - `etcd-io/etcd`（≈52.3k★，实测）：虽不是数据库，但它展示了「协调者 = Raft 复制状态机」的通用形态。
- **XA / 事务中间件的当代形态**：
  - `seata/seata`（≈26.0k★，实测）：AT / TCC / Saga / XA 四种模式并存的分布式事务框架，是本书第 6 章的开源对照物；
  - `dtm-labs/dtm`（≈10.9k★，实测）：跨语言分布式事务管理器，原生支持 Saga / TCC / XA / 二阶段消息；
  - `temporalio/temporal`（≈23.3k★，实测）：用「持久化工作流」承载长事务补偿，把 Saga 的编排问题变成代码问题。
- 🔧 **CDC + 流处理取代双写（2026 年最值得记住的一条工程补丁）**：
  - 传统做法：业务代码里同时写数据库和消息队列（双写），需要 2PC 或 XA 才能保证原子；
  - 2026 年主流做法：**Outbox 表 + CDC 捕获 + 流处理投递**——只写一次数据库，由 CDC 把变更变成事件；
  - `debezium/debezium`（≈13.2k★，实测）与 `apache/flink-cdc`（≈6.5k★，实测）是这一模式的标准件；
  - 它把「分布式事务」降级为「单机事务 + 至少一次投递 + 消费端幂等」，
    正是本书第 6 章（[07](07-分布式事务.md)）与第 9 章（[10](10-幂等接口.md)）的组合拳。
- **确定性提交的研究线**：确定性数据库（Calvin, SIGMOD 2012；Bohm / Aria, VLDB 2020）先定序再执行，
  从根本上省掉提交阶段的协调——是 2PC 的另一条绕开路线。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「2PC 是共识算法」 | 不是。共识要求**任何多数派存活即可自行决定**；2PC 中协调者崩溃即阻塞。2PC 是**原子提交协议** |
| 2 | 「3PC 解决了 2PC 的阻塞，所以更先进」 | 3PC 只在**崩溃故障**下解决阻塞；**网络分区**下会出现「一边提交、一边中止」的不一致，因此生产几乎不部署 3PC |
| 3 | 「2PC 慢是因为多发了两条消息」 | 根因是**锁持有时间**被拉长到两轮 RTT + 协调者落盘，消息数只是表象 |
| 4 | 「协调者写不写日志无所谓」 | 协调者必须**先落盘决定再广播**；否则崩溃恢复后无法回答参与者的查询，产生永久未决事务 |
| 5 | 「XA 事务能保证跨库强一致」 | XA 只定义接口；保证强度取决于各参与者的隔离级别与协调者实现，且同样有阻塞问题 |
| 6 | 「用了消息队列就不用管原子性了」 | 消息投递与数据库写入之间仍有原子性问题，需要 Outbox/CDC 或事务消息（见 [07](07-分布式事务.md)） |
| 7 | 🔧 本书需 2026 补丁 | 2.4.2 若把 2PC 论证为「线性一致」，应补一句：**这是针对提交点而言**；跨对象事务的**可串行化**还需隔离级别配合，二者不是一回事 |
| 8 | 🔧 本书需 2026 补丁 | 本章未覆盖 **Paxos Commit / 共识化协调者**：这是 2PC 阻塞问题的正解，也是 Spanner/TiDB/CockroachDB 的实际做法 |
| 9 | 🔧 本书需 2026 补丁 | 本章未覆盖 **CDC + 流处理取代双写**：2026 年最常见的「绕开 2PC」工程范式 |
| 10 | 🔧 本书需 2026 补丁 | 本章未提 **HLC / TrueTime**：分布式提交要给事务定全局提交时间戳时（外部一致性），答案在这两者，而不在 2PC 本身 |
