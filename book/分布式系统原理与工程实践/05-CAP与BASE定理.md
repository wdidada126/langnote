## 核心精讲

### 4.1.1 CAP 定理的精确表述

- **流行表述**（本书 4.1 大概率采用）：分布式系统无法同时满足**一致性 C**、**可用性 A**、**分区容错性 P**，最多三者取二。
- **精确表述**（Gilbert & Lynch 2002，把直觉变成定理）：
  - **C**：这里指**线性一致性**（见 [02](02-一致性的概念与强弱.md)）——每次读都能看到最近一次已完成的写；
  - **A**：每个**非故障节点**收到的请求都必须在**有限时间内**返回**非错误**响应（不允许无限等待、不允许拒绝）；
  - **P**：网络允许**丢失任意多的消息**（即分区可以发生）；
  - **定理**：在**异步网络模型**下，不可能实现一个既保证线性一致、又保证（分区期间）完全可用的**原子读写寄存器**。
- 🔧 三个必须说清的点：
  1. **P 不是可选项**。分区是网络属性，不是设计选择；你能选的只有「分区发生时**牺牲 C 还是牺牲 A**」。
     所以「CA 系统」在存在网络的分布式系统里**不存在**（单机数据库才是 CA）。
  2. **C 与 A 的取舍是「分区期间」的取舍**。没有分区时，系统完全可以同时给出 C 和 A——
     这正是 2026 年 Spanner / TiDB / CockroachDB 宣称「既一致又高可用」并不矛盾的原因。
  3. **取舍是细粒度的**。同一系统可以对不同数据、不同操作做不同选择（有的键强一致，有的键最终一致）；
     「这个系统是 CP 还是 AP」是过度简化。

### 4.1.2 示例与理解：分区发生时发生了什么

```text
# 教学示意：分区下的两条路（文本图，不参与构建）

      客户端写 x=1  ──▶ 分区 A 侧副本
                              │
                   网络分区（A 侧与 B 侧失联）
                              │
       ┌──────────────────────┴──────────────────────┐
       ▼                                             ▼
  【选 CP】B 侧拒绝服务（不可用）              【选 AP】B 侧继续用旧值应答
   → 保住了「读到的一定是新的」                 → 保住了「永远有响应」
   → 代价：部分客户端拿不到响应                 → 代价：读到 x 的旧值（不一致）
   → 分区恢复后直接继续                         → 分区恢复后需要做冲突解决/收敛
```

- 典型归类（工程口径，非定理结论）：
  | 系统 | 常见归类 | 说明 |
  | --- | --- | --- |
  | ZooKeeper / etcd | **CP** | Leader 失去多数派即停止服务（详见 [12](12-ZooKeeper详解与再论分布式系统.md)） |
  | Eureka | **AP** | 注册信息以「最终一致 + 客户端缓存」为准，宁可给旧列表也不拒绝 |
  | Cassandra（默认） | **AP**（可调） | 一致性级别可调，QUORUM 下向 CP 靠拢 |
  | Spanner / TiDB / CockroachDB | **CP**（同时追求高可用） | 用共识 + 硬件时钟把不可用的窗口压得极小 |
  | 单机 RDBMS | **CA** | 无网络分区可发生（P 不适用），因此能同时 C 与 A |

### 4.2 从 CAP 到 BASE：承认代价之后的工程姿态

- CAP 说「分区时你必须放弃一个」；
  由于**放弃 A 很难被业务接受**（用户宁可看到旧数据也不想看到报错页），
  工程上普遍选择**放弃（强）C** → 于是需要一套描述「放弃之后怎么办」的语言，这就是 **BASE**。
- 🔧 由此可以理解本书 4.2 的论证方向：
  **CAP 是「做不到什么」的定理，BASE 是「做不到之后怎么活」的工程原则**；
  两者不是并列的定理，而是「约束 → 应对策略」的关系。这也是本章编排在理论篇末尾的原因——
  它同时是理论篇的结论和实践篇的序言。

### 4.3 BASE 的含义与应用

| 字母 | 全称 | 含义 | 工程对应 |
| --- | --- | --- | --- |
| **B** | Basically Available（基本可用） | 允许**降级可用**：响应时间变长、部分功能关闭，但**不整体不可用** | 限流、降级、熔断（本书第 8 章） |
| **S** | Soft state（软状态） | 允许系统存在**中间状态**，且该状态无需外部输入也会自行变化 | 异步复制、缓存、未决事务 |
| **E** | Eventual consistency（最终一致性） | 停止写入后，经过有限时间所有副本**收敛** | 反熵、读修复、CRDT、重试 |

- **BASE 与 ACID 的关系**：常被称为「**反 ACID**」，但更准确的说法是**对 ACID 的放宽与后置**：
  ACID 追求「每一步都正确」，BASE 追求「最终结果正确，过程允许不一致」。
- 🔧 应用时的三条落地经验：
  1. **先问业务能不能接受最终一致**：余额、库存、配额这类有不变式的场景通常不能，必须强一致或加锁；
  2. **能接受的话，把收敛时间变成可承诺的指标**（「99% 在 200ms 内收敛」），否则「最终」没有工程意义；
  3. **用幂等 + 重试兜住过程的不一致**（本书第 9 章），这是 BASE 落地最常被漏掉的一环。

### 教学示意：一个可调一致性的写入路径

```python
# 教学示意：同一份数据，按 CAP/BASE 取舍选择写入策略；不参与构建，不运行。
class KVStore:
    def put(self, key, value, mode):
        replicas = self.replicas_for(key)
        if mode == "CP":
            ok = self.quorum_write(replicas, key, value)   # W > N/2
            if not ok:
                raise Unavailable("宁可不可用，也不写入可能被回滚的值")
            return "strong"
        if mode == "AP":
            self.write_local(replicas[0], key, value)
            self.async_replicate(replicas[1:])             # 后台反熵
            return "eventual（可能暂时不一致，稍后收敛）"

    def get(self, key, mode):
        if mode == "CP":
            return self.read_with_readindex(key)           # 走 leader / ReadIndex
        return self.read_any_replica(key)                  # 可能读到旧值
```

```text
# 教学示意：PACELC（本书未覆盖，2026 补丁）
# 分区发生时：在 A 与 C 之间取舍（Else 之前的 PA/PC）
# 正常运行时：在 L（延迟）与 C（一致性）之间取舍（EL/EC）

           有分区？
          /      \
        是        否
     PA/PC      EL/EC
  （可用 vs 一致） （延迟 vs 一致）

例：Dynamo/Cassandra 默认 PA/EL；Spanner 为 PC/EC（但用硬件把代价压小）
```

## 版本演进

- **版本情况**：本书第 1 版（2022-01）；**第 2 版未核实到，标注「待核验」**。以下记录 CAP/BASE 的讨论演进。
- **CAP 讨论的三个阶段**：
  1. **1999–2000（提出）**：Fox & Brewer 先用 **Harvest/Yield** 刻画「部分结果 + 高可用」；
     Brewer 在 PODC 2000 的 keynote 摘要中提出 CAP 猜想；
  2. **2002（证明与澄清）**：Gilbert & Lynch 给出形式化证明，把 C 明确为**线性一致性**，
     也由此暴露了「三选二」说法的粗糙；
  3. **2012–至今（反思与细化）**：Brewer 本人在《CAP Twelve Years Later》（IEEE Computer 2012）中强调
     「分区极少发生，正常运行时的一致性与延迟取舍才是设计主战场」；
     Abadi 同年提出 **PACELC**，把「分区时」与「平时」两段取舍写进同一个框架。
- 🔧 **2022 → 2026**：
  - 「我们是 CP 还是 AP」这种整系统标签在架构评审中已基本被 **per-operation / per-key 的 PACELC 描述**取代；
  - 「强一致 = 慢」的直觉被打破：共识 + RDMA/NVMe + 硬件时钟让强一致的绝对延迟进入可用区间，
    真正的取舍重新回到**延迟预算**而非「可用性」；
  - BASE 中的「E」有了更强的技术内涵：**CRDT** 让「最终一致」不再是「最后写入者获胜」，而是**可证明收敛**。

## 近年研究与工业界开源实践（2015–2026）

- 🔧 **PACELC 成为选型语言**（star 均为 2026-09 `gh api` 实测）：
  - `apache/cassandra`（≈10.1k★）：可调一致性级别（ONE/QUORUM/ALL）几乎就是 PACELC 的旋钮；
  - `redis/redis`（≈76.5k★）：异步复制取 `PA/EL`，`WAIT` 与 `WAIT` 之外的读写分离策略则向 `PC/EC` 靠；
  - `etcd-io/etcd`（≈52.3k★）、`apache/zookeeper`（≈12.8k★）：明确的 `PC` 路线（无多数派即不可用）。
- **注册中心的 CP/AP 之争（本书第 7 章的直接案例）**：
  - `Netflix/eureka`（≈12.7k★）：AP 注册中心代表，宁可返回过期实例列表；
  - `alibaba/nacos`（≈33.4k★）：同时支持 AP（Distro 协议）与 CP（Raft）两种模式，可按服务切换；
  - `hashicorp/consul`（≈30.1k★）：CP 倾向 + 客户端缓存兜底。
- 🔧 **CRDT 让 BASE 的「E」变强**：
  - `automerge/automerge`（≈6.6k★）、`yjs/yjs`（≈22.8k★）把无协调收敛做成可用库，
    协同编辑、离线优先应用不再需要「最后写入者获胜」这种粗糙策略。
- **强一致系统的可用性工程**：`cockroachdb/cockroach`（≈32.5k★）与 `pingcap/tidb`（≈40.6k★）
  在共识 + 自动故障转移下宣称多 9 的可用性，说明 4.1 的取舍在实践中是**延迟预算问题**而非「能否服务」问题。
- **验证工具**：`jepsen-io/jepsen`（≈7.5k★）公开测出过若干系统在分区下「声称 CP 却返回旧读」的问题，
  提醒我们：**CAP 分类是声称，需要测试证明**。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「CAP 是三选二，我可以选 CA」 | 分区不可选择（P 是网络属性）；有网络的系统只能在**分区期间**于 C 与 A 之间取舍，CA 只存在于单机 |
| 2 | 「CAP 说不能同时 C 和 A」 | 定理说的是**分区期间**；无分区时系统完全可以既一致又可用 |
| 3 | 「一个系统整体是 CP 或 AP」 | 取舍是**按操作、按数据项**做的；同一系统常同时提供强一致读与最终一致读 |
| 4 | 「BASE 是 CAP 之外的另一个定理」 | CAP 是**不可能定理**；BASE 是**工程原则**（基本可用 / 软状态 / 最终一致），二者是「约束 → 对策」关系 |
| 5 | 「最终一致 = 数据会永久不一致」 | 只承诺**收敛**；配合读修复、反熵、版本向量或 CRDT，不一致性窗口可被量化 |
| 6 | 「软状态就是脏数据」 | 软状态指「允许存在会自行演化的中间状态」，是设计上的让步，不是缺陷 |
| 7 | 🔧 本书需 2026 补丁 | 本章未引入 **PACELC**：绝大多数系统的真实取舍发生在**无分区时的延迟 vs 一致性**，只有 PACELC 能描述 |
| 8 | 🔧 本书需 2026 补丁 | 本章未覆盖 **CRDT**：BASE 的「E」在 2026 年已经有可证明收敛的数据结构支撑，而非仅靠「最后写入者获胜」 |
| 9 | 🔧 本书需 2026 补丁 | 本章未提**一致性声明需要验证**：Jepsen 等方法论把「我们符合 CAP 的哪一侧」变成可证伪的工程声明 |
| 10 | 🔧 本书需 2026 补丁 | 「CP 系统不可用时客户端完全无助」应补：现代客户端用**本地缓存 + 陈旧读 + 快速失败**组合，把不可用窗口的体验损失降到最低 |
