# 第 1 章 分布式概述（理论篇开篇）

> **本章地图**：什么是分布式系统 → 应用形态怎么一步步演进（**单体 → 集群 → 狭义分布式 → 微服务**）
> → 定义、一致性与节点 → 优势与问题 → 引出后面三章要解决的「一致性 / 共识 / 约束」。

## 本章地图

- 位置：理论篇第 1 章，是全书的**问题提出章**。
  - 1.2 用四种应用形态给出「为什么需要分布式」的历史动机；
  - 1.3 给出分布式系统的定义，并把「分布式一致性问题」作为全书主线抛出；
  - 1.4/1.5 做成本收益对账，1.5 列出的每一条问题都对应后面某一章的解法。
- 主线（读的时候按这条线抓）：
  1. **形态演进**：单体 → 集群 → 狭义分布式 → 微服务，是「拆分粒度」不断变细的过程；
  2. **节点**：拆分之后，原来的一次进程内调用变成了跨节点调用；
  3. **一致性问题**：跨节点之后，「看到的数据是不是同一份」第一次成为问题（本章只提出，第 2 章展开）；
  4. **代价**：优势与问题成对出现，全书其实都是在为 1.5 的问题清单买单。
- 🔧 本章是全书最适合补 2026 视角的一章：2022 年之后，Kubernetes 事实上成了「分布式操作系统」，
  服务网格接管了大量原本写在客户端 SDK 里的分布式职责，微服务的热度也让位于「模块化单体 / 宏服务」的反思。

## 核心精讲

（以下伪代码与示意图均为**教学示意，不参与构建**。）

### 1.1 概述：为什么会有「分布式系统」这门课

- 单机性能有上限（CPU、内存、磁盘、网络带宽任一到顶），而业务规模无上限；
- 单机的**可用性**也有上限：一台机器挂了就是全站挂了；
- 于是把「一台更强的机器」换成「一批普通的机器 + 一套协作规则」——这套协作规则就是分布式系统的全部内容。
- 🔧 一句话概括分布式系统的本质：**用不可靠的部件组装出可靠的服务**；
  所有算法、协议、中间件都在回答同一个问题：**在部件会坏、网络会丢、时钟会漂的前提下，如何让外界看起来像一台机器**。

### 1.2 应用的演进历程（本书的分类法是本章最大的特色）

| 形态 | 部署单位 | 拆分粒度 | 典型协作方式 | 主要解决的问题 | 新引入的问题 |
| --- | --- | --- | --- | --- | --- |
| **单体应用** | 一个进程（一个包） | 不拆分 | 进程内函数调用 | 开发部署简单、事务是本地事务 | 改一处要全量发布；局部热点要整体扩容 |
| **集群应用** | 同一份程序的多份副本 | 不拆分，只复制 | 负载均衡 + 共享存储/共享会话 | 吞吐与可用性（副本冗余） | 会话/状态共享；缓存一致性 |
| **狭义分布式应用** | 多个不同的子系统 | 按子系统（模块）拆 | RPC / 消息队列 | 不同模块独立伸缩、独立演进 | 跨节点调用失败、跨节点数据一致 |
| **微服务应用** | 大量小服务 | 按业务能力再细分 | 服务注册发现 + 网关 + 熔断限流 | 团队自治、独立发布、细粒度伸缩 | 运维复杂度爆炸；链路长、排障难；分布式事务 |

- 🔧 本书把「集群」与「狭义分布式」明确分开，是很值得肯定的处理：
  **集群 = 复制（同一份程序多份）**，**分布式 = 拆分（不同的部分各做各的）**。
  日常口语里把这两件事都叫「分布式」，是后面许多误解的源头。
- 演进的真实驱动力不是「技术先进」，而是**组织结构与发布频率**：
  当多个团队要独立发布同一份代码时，单体必然成为瓶颈——这是康威定律在工程上的直接体现。

### 1.3 分布式系统的定义、一致性问题与节点

- **定义**（教科书口径，三种常见表述）：
  - Tanenbaum / van Steen：分布式系统是「一组独立的计算机，对用户表现为一个单一连贯的系统」；
  - Coulouris 等：分布式系统是「联网计算机上的硬件或软件组件仅通过消息传递来通信与协调动作的系统」；
  - 广为流传的 Lamport 幽默表述：*「分布式系统就是这样一种系统：一台你根本不知道它存在的计算机出了故障，
    就可能导致你自己的计算机不可用。」*（该表述常被教材引用，具体原始出处见本章文献表，本章不把它当严格定义用。）
- **分布式一致性问题**（1.3.2，本章只提出）：
  同一份数据有多个副本 / 同一次业务跨越多个节点时，各节点「看到的状态」可能不一致。
  🔧 注意这里的「一致性」和数据库中的 ACID 一致性不是一回事——这正是第 2 章 2.1 要澄清的第一件事。
- **分布式应用中的节点**（1.3.3）：
  - 按**是否有本地状态**划分是最有用的切法：
    - **无状态节点**：可随意增删副本，扩缩容最容易（本书第 8 章的限流、熔断主要作用于这类节点的入口）；
    - **有状态节点**：扩缩容要迁移数据，一致性、副本、选主全都由此而来（第 2–4 章的理论全部服务于它）。
  - 🔧 工程口诀：**先把状态赶出去，剩下的就都是可以随便加机器的部分**。
    这也是为什么生产上把会话放 Redis、把文件放对象存储、把状态交给数据库。

### 1.4 优势与 1.5 问题（成对记忆）

| 优势 | 对应的代价（问题） | 本书在哪一章给出解法 |
| --- | --- | --- |
| 性能可水平扩展 | 跨节点协调开销；网络延迟不可忽略 | 第 7 章（调用）、第 8 章（治理） |
| 可用性高（冗余） | 副本之间的数据不一致 | 第 2 章（一致性） |
| 可独立演进、独立发布 | 版本兼容、接口契约、幂等 | 第 9 章（幂等接口） |
| 资源隔离 | 局部故障扩散（雪崩） | 第 8 章（隔离/熔断/降级） |
| 团队自治 | 全局可见性差、排障难 | 第 8 章网关、本目录近年段的可观测性补丁 |

### 读本章的三条收获

1. **会描述形态**：能用「复制 vs 拆分」说清集群与分布式的差别，不再混用两个词；
2. **会定位问题**：看到「服务越来越多」时，能立刻指出新增的是哪一类问题（调用失败 / 一致 / 排障 / 发布）；
3. **会预判代价**：知道任何一次拆分都在把「编译期耦合」换成「运行期耦合」，因此契约、幂等、可观测性必须同步补上。

### 教学示意：把「单体 → 分布式」的代价显性化

```python
# 教学示意：同一段业务逻辑，在单体与分布式下的失败点数量对比。
# 不参与构建，不运行。

# —— 形态 1：单体 ——
def transfer_in_monolith(db, a, b, amount):
    with db.transaction():          # 本地事务：要么全成功，要么全回滚
        db.decr(a, amount)
        db.incr(b, amount)
    # 失败点：只有 db 一个。

# —— 形态 2：狭义分布式（账户服务 / 记账服务 两个节点）——
def transfer_in_distributed(acct, ledger, a, b, amount):
    ok1 = acct.decr(a, amount)      # ① 网络可能超时（不知道有没有真的扣了）
    ok2 = ledger.incr(b, amount)    # ② 可能成功也可能失败
    if not (ok1 and ok2):
        acct.compensate(a, amount)  # ③ 补偿本身也可能失败
        ledger.compensate(b, amount)
    # 失败点：3 个远程调用 + 各自的部分失败语义。
    # 重试 ① 会造成重复扣款 → 幂等（第 9 章）；
    # 让 ①② 原子 → 分布式事务（第 6 章）或共识（第 3 章）；
    # 选谁做「权威」→ 锁（第 5 章）或选主（第 3 章）。
```

```text
# 教学示意：四种形态的部署拓扑（文本图，不参与构建）

单体:        [ App ]──[ DB ]
集群:        [LB]─┬─[ App ]─┐
                  ├─[ App ]─┼─[ DB ]   （程序复制，状态仍在共享存储）
                  └─[ App ]─┘
狭义分布式:  [ App-A ]──RPC──[ App-B ]──MQ──[ App-C ]   （按模块拆）
微服务:      [GW]─┬─[svc-1]─┬─[registry]   ┌─[svc-2]
                  └─[svc-3]─┘             └─[svc-4]──[config]
                          （服务数十上百个，配套发现/配置/网关/治理）
```

## 版本演进

- **版本情况**：本书为 2022-01 电子工业出版社第 1 版；**本次检索未核实到第 2 版或改版重印记录，标注「待核验」**。
  因此本段不写「版次差异」，改为记录本书成稿之后（2022 → 2026）本章主题在业界的演进。
- **2022 → 2026 的三处变化**：
  1. **Kubernetes 成为事实上的分布式操作系统**：
     调度、扩缩容、健康检查、服务发现（Service/CoreDNS）、配置（ConfigMap/Secret）、滚动发布
     统统下沉到平台层。本书第 1 章描述的「应用形态演进」仍在，但**演进的落地方式**变了——
     今天几乎没有人从裸机开始搭集群，而是先有 K8s 再有应用。
  2. **微服务的热度回落**，「模块化单体 / 宏服务」重新被讨论：
     Amazon、Google 等公开分享过「微服务拆分过细导致成本与延迟失控」的反思材料；
     拆分决策重新回到「团队边界与发布频率」，而不是「越细越好」。
  3. **服务网格把客户端职责搬到基础设施**：重试、超时、熔断、mTLS、可观测性从 SDK 移到 sidecar，
     本书第 7–8 章讲的许多「应用要自己做的事」，2026 年有相当一部分由网格代劳（详见 [08](08-服务发现与调用.md)）。

## 近年研究与工业界开源实践（2015–2026）

- 🔧 **Kubernetes 作为事实上的分布式 OS**：
  - `kubernetes/kubernetes`（≈128.0k★，2026-09 `gh api` 实测）——调度、服务发现、滚动发布、声明式自愈；
  - 学术侧：`Burns et al.` 的 Borg/Omega/K8s 三代总结（CACM 2016）与 EuroSys 2015 的 Borg 论文；
  - 影响：本书 1.2 的「集群应用」在今天几乎等价于「K8s 上跑多个 Pod + Service」。
- **微服务框架**：
  - `apache/dubbo`（≈41.6k★，实测）：Java 系 RPC + 服务治理一体化；
  - `go-micro/go-micro`（≈23.1k★，实测）：Go 系微服务框架（近年活跃度下降，仅作形态参考）；
  - `grpc/grpc`（≈45.3k★，实测）：跨语言 RPC 事实标准，第 7 章「远程过程调用」的当代默认实现。
- **服务网格（承接本书 1.2 的微服务形态）**：
  - `istio/istio`（≈38.4k★，实测）、`envoyproxy/envoy`（≈29.0k★，实测）；
  - 把重试/超时/熔断/mTLS/追踪从应用 SDK 下沉到数据面，是「微服务之后的第二次基础设施化」。
- **模块化单体的反思（2023–2026）**：
  - 多家大型互联网公司公开分享过「把过度拆分的微服务合并回去」的实践（公开演讲与工程博客，非同行评审论文）；
  - 结论与本书 1.5「分布式应用的问题」一致，只是 2026 年业界更愿意用**拆分成本**来反向约束拆分决策。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「微服务就是分布式系统」 | 微服务只是**拆分粒度最细**的一种分布式形态；集群、狭义分布式同样属于分布式系统 |
| 2 | 「集群和分布式是一回事」 | 集群 = **复制**（同一份程序多份）；分布式 = **拆分**（不同部分各司其职）；本书 1.2 已明确分开，值得记住 |
| 3 | 「分布式一定更快」 | 分布式换来的是**可伸缩上限**与**可用性**，单次请求延迟通常变长（多一跳网络 + 序列化） |
| 4 | 「把单体拆开就解耦了」 | 拆分只把**编译期耦合**换成**运行期耦合**；契约、版本、幂等、可观测性必须同步补上 |
| 5 | 「无状态服务就没有一致性问题」 | 无状态服务本身没有，但它读写的**有状态依赖**（DB/缓存/MQ）有，问题只是被转移了 |
| 6 | 🔧 本书需 2026 补丁 | 本书按「单体→集群→狭义分布式→微服务」单向演进叙述；2026 视角应补一句：**演进不是单向的**，模块化单体与宏服务是合法的回头路 |
| 7 | 🔧 本书需 2026 补丁 | 本章未涉及 **Kubernetes**：今天「集群应用」的默认载体是 K8s，服务发现/配置/发布/自愈都由平台提供，读本章时应自行叠加这一层 |
| 8 | 🔧 本书需 2026 补丁 | 本章 1.5 未列「可观测性与排障成本」：跨节点链路追踪（OpenTelemetry）已成为分布式系统的**必备件**而非可选项，详见 [09](09-服务保护与网关.md) |
