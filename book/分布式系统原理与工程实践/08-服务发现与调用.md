# 第 7 章 服务发现与调用（实践篇）

> **本章地图**：分布式带来的问题（7.1）→ 服务发现的三种模型（**反向代理 / 注册中心 / 服务网格**，7.2）
> → 三模型比较（7.2.5）→ 服务调用：**基于接口的调用 vs 远程过程调用 RPC**（7.3）。

## 本章地图

- 位置：实践篇第 7 章。第 5 章（锁）解决互斥、第 6 章（事务）解决原子性，第 7 章解决**寻址与通信**。
- 主线：
  1. 服务被拆开之后，「**对方在哪台机器上**」第一次变成动态信息（实例会扩缩、会迁移、会挂）；
  2. 于是需要一套「**谁在哪、还能不能用**」的权威来源——这就是服务发现；
  3. 三种模型的差别，本质是「**这份权威放在哪一层**」：集中代理 / 注册中心 + 客户端 / sidecar 代理；
  4. 找到对方之后还要决定「怎么调」：接口调用（面向契约）还是 RPC（面向方法）。
- 🔧 本章是全书与实践贴合最紧的一章，也因此最需要 2026 补丁：
  Kubernetes 的 Service + CoreDNS 已成为默认的服务发现形态，
  **服务网格把重试、超时、熔断、mTLS、追踪从客户端 SDK 接管到 sidecar**，
  本章讲的「应用要自己做的事」，有相当一部分在 2026 年由基础设施代劳。

## 核心精讲

（以下伪代码与示意图均为**教学示意，不参与构建**。）

### 7.1 分布式带来的问题（为什么「写死 IP」不行了）

| 问题 | 单体/集群时代 | 分布式/微服务时代 | 带来的需求 |
| --- | --- | --- | --- |
| 实例数量 | 固定、少 | 动态、多（弹性伸缩） | **服务注册与健康检查** |
| 实例位置 | 固定 IP | 容器漂移、IP 变化 | **按名寻址**（而不是按 IP） |
| 实例状态 | 人工确认 | 随时可能半死不活 | **健康检查 + 摘除** |
| 调用方式 | 进程内函数 | 跨网络调用 | **序列化 + 协议 + 失败语义** |
| 配置变更 | 改文件重启 | 需热更新 | **配置中心 + 推送/监听** |

### 7.2 三种服务发现模型（本书最实用的一节）

| 模型 | 权威在哪 | 调用路径 | 客户端要做的事 | 优点 | 缺点 |
| --- | --- | --- | --- | --- | --- |
| **反向代理模型**（7.2.2） | 一个集中代理（Nginx / LVS / API 网关） | 客户端 → 代理 → 实例 | 几乎不用改，调代理即可 | 对客户端零侵入；集中治理、集中鉴权 | 代理是**单点与瓶颈**；多一跳延迟；代理自身要高可用 |
| **注册中心模型**（7.2.3） | 独立注册中心（ZK / etcd / Nacos / Consul / Eureka） | 客户端查注册中心拿实例列表 → **直连**实例 | 集成 SDK：注册、心跳、订阅、负载均衡 | 少一跳（直连）；扩展性好 | 客户端有侵入（语言绑定）；注册中心一致性级别影响可用性 |
| **服务网格模型**（7.2.4） | 控制面（Istio 等）+ 每个实例的 sidecar（Envoy） | 客户端 → 本地 sidecar → 对端 sidecar → 实例 | **几乎零侵入**（应用只连 localhost） | 治理能力统一、语言无关、可灰度可观测 | 运维复杂度高；sidecar 带来延迟与资源开销；排障链路长 |

- **7.2.1 服务发现模型中的角色**（三个抽象）：
  - **服务提供者（Provider）**：启动时注册、运行中上报健康状态、下线时注销；
  - **服务消费者（Consumer）**：查询或订阅实例列表，做负载均衡与故障重试；
  - **服务注册中心（Registry）**：持有「服务名 → 实例列表」的映射，并负责健康检查与变更通知。
- 🔧 三者的关键设计抉择是**推送 vs 拉取**：
  - 推送（Watcher/长轮询）：变更及时，但注册中心要维持大量长连接（ZooKeeper Watcher、Nacos 推送）；
  - 拉取（定时轮询 + 客户端缓存）：压力小、注册中心可弱一致，但变更有延迟（Eureka 的典型做法）。
- 🔧 **注册中心该选 CP 还是 AP**（与 [05](05-CAP与BASE定理.md) 直接相关）：
  - 注册中心短暂不一致的后果通常是「调到一台已下线的实例」→ 由**客户端重试/熔断**兜住，损失可控；
  - 因此 AP 倾向（Eureka、Nacos 的 Distro 模式）在实践中完全可行，且可用性更好；
  - 但**分布式锁、选主、配置强一致下发**这类场景必须 CP（ZooKeeper/etcd/Consul）。
  - 结论：**注册中心本身不必强一致，但「实例是否健康」的判断要尽量本地化与快速**。

### 7.2.5 三种模型的比较（速查）

| 维度 | 反向代理 | 注册中心 | 服务网格 |
| --- | --- | --- | --- |
| 客户端侵入 | 无 | 高（SDK） | 低（sidecar） |
| 延迟 | 多一跳（集中） | 直连（最优） | 两跳本地 sidecar（可接受） |
| 语言无关 | 是 | 取决于 SDK 覆盖 | 是 |
| 治理能力 | 集中在代理 | 分散在 SDK（版本难统一） | 集中在控制面（统一） |
| 运维复杂度 | 低 | 中 | 高 |
| 典型产品 | Nginx / Kong / APISIX | ZooKeeper / etcd / Nacos / Consul / Eureka | Istio + Envoy / Linkerd |

### 7.3 服务调用：基于接口的调用 vs RPC

| 维度 | **基于接口的调用**（7.3.2） | **远程过程调用 RPC**（7.3.3） |
| --- | --- | --- |
| 抽象 | 「调用一个**服务接口**」（HTTP + JSON/REST 风格） | 「调用一个**远端方法**」（像本地函数一样） |
| 契约 | URL + 方法 + 报文格式（OpenAPI 等） | IDL（`.proto` / `.thrift`）+ 生成 stub |
| 耦合 | 松（只要报文对得上） | 紧（stub 版本要匹配） |
| 可读性/调试 | 高（人可读） | 低（需工具） |
| 性能 | 一般（文本协议） | 高（二进制编码 + 长连接多路复用） |
| 适用 | 对外 API、跨组织集成 | 内部高频调用 |

- **RPC 的五要素**（工程视角）：
  1. **IDL 与代码生成**（`.proto` → stub）；
  2. **序列化/反序列化**（protobuf、Thrift、Hessian、JSON）；
  3. **通信协议与连接复用**（HTTP/2 多路复用、自定义 TCP 帧）；
  4. **寻址与负载均衡**（服务发现 + 客户端 LB 策略：轮询、最少连接、一致性哈希、就近路由）；
  5. **失败语义与治理**（超时、重试、熔断、降级）——🔧 2026 年这一项大量下沉到服务网格。
- 🔧 **RPC 的第一原则是「它不像本地调用」**：
  本地调用只有「成功/抛异常」两种结果，RPC 还有第三种：**超时（不知道有没有成功）**。
  这第三种结果正是 [10-幂等接口.md](10-幂等接口.md) 存在的理由。

### 教学示意：注册 + 发现 + 调用

```python
# 教学示意：注册中心模型的最小闭环；不参与构建，不运行。
class Registry:
    def __init__(self): self.services = {}          # name -> {instance_id: (addr, expire_at)}
    def register(self, name, inst_id, addr, ttl):   # 提供者：注册 + 续约
        self.services.setdefault(name, {})[inst_id] = (addr, now() + ttl)
    def heartbeat(self, name, inst_id, ttl):
        if (name, inst_id) in self._flat(): self.register(name, inst_id, _addr_of(), ttl)
    def deregister(self, name, inst_id):
        self.services.get(name, {}).pop(inst_id, None)
    def sweep(self):                                 # 健康检查兜底：清掉过期实例
        for name, insts in self.services.items():
            for iid, (addr, exp) in list(insts.items()):
                if exp < now(): insts.pop(iid)
    def lookup(self, name): return list(self.services.get(name, {}).values())

class Consumer:
    def call(self, name, method, args):
        peers = self.registry.lookup(name)           # 可本地缓存（AP 注册中心的典型做法）
        if not peers: raise NoInstance(name)
        peer = self.lb.pick(peers)                   # 客户端负载均衡
        return self.rpc.invoke(peer, method, args, timeout=..., retry=...)
```

## 版本演进

- **版本情况**：本书第 1 版（2022-01）；**第 2 版未核实到，标注「待核验」**。以下记录本章主题的演进。
- **四个阶段**：
  1. **1981–1984（RPC 诞生）**：Nelson 的博士论文（CMU 1981）与 Birrell & Nelson（ACM TOCS 1984）
     确立「像调函数一样调远端」的抽象与失败语义讨论；
  2. **1990s–2000s（集中代理时代）**：硬件/软件负载均衡 + 反向代理（本书 7.2.2），
     一致性哈希（Karger 等, STOC 1997）成为路由层的基石；
  3. **2010–2016（注册中心 + 编排层）**：ZooKeeper（ATC 2010）、Eureka/Consul 等成为标配；
     Borg（EuroSys 2015）与 K8s（CACM 2016）把「命名 + 负载均衡」下沉到平台；
  4. **2016–2026（服务网格时代）**：Envoy/Istio 用 xDS 把路由、重试、熔断、mTLS 变成**数据面配置**，
     客户端 SDK 的职责大幅收缩。
- 🔧 **2022 → 2026**：
  - **Kubernetes 成为默认的服务发现层**：`Service` + `Endpoints/EndpointSlice` + `CoreDNS`
     提供「按名寻址 + 负载分发」，很多团队不再单独部署注册中心；
  - **服务网格从「要不要上」变成「上了之后怎么瘦身」**：Ambient mesh / sidecarless 方向兴起，
     说明网格的价值被认可、但其资源开销被反思；
  - **gRPC 成为内部调用默认协议**，HTTP/2（RFC 9113）多路复用 + protobuf 成为事实标准。

## 近年研究与工业界开源实践（2015–2026）

- **注册中心 / 配置中心（star 均为 2026-09 `gh api` 实测）**：
  - `alibaba/nacos`（≈33.4k★）：AP（Distro）与 CP（Raft）双模式，注册中心 + 配置中心一体；
  - `hashicorp/consul`（≈30.1k★）：服务发现 + 健康检查 + KV，CP 倾向 + DNS 接口；
  - `etcd-io/etcd`（≈52.3k★）：K8s 的存储底座，也是强一致服务发现的默认选择；
  - `Netflix/eureka`（≈12.7k★）：AP 注册中心的历史标杆（已进入维护态，主要作形态参考）；
  - `polarismesh/polaris`（≈2.6k★）、`sofastack/sofa-registry`（≈0.66k★）：国产注册中心的其他形态。
- **RPC 框架**：
  - `grpc/grpc`（≈45.3k★）：跨语言 RPC 事实标准（HTTP/2 + protobuf）；
  - `apache/dubbo`（≈41.6k★）：Java 系 RPC + 服务治理一体化，含多种负载均衡与路由策略。
- 🔧 **服务网格（接管客户端一致性职责）**：
  - `istio/istio`（≈38.4k★）+ `envoyproxy/envoy`（≈29.0k★）：控制面 + 数据面，
    把**超时、重试、熔断、mTLS、追踪**从应用 SDK 下沉为 xDS 配置；
  - 这一步对本书 7.3 的意义重大：本章描述的「客户端要做的事」，
    2026 年由 sidecar 统一完成，**应用代码回归业务本身**；
  - 新兴的 sidecarless / ambient mesh 方向在降低资源开销，说明该架构仍在演进。
- **K8s 作为事实上的分布式 OS**：
  - `kubernetes/kubernetes`（≈128.0k★）+ `coredns/coredns`（≈14.3k★）：
    Service/CoreDNS 提供默认寻址，滚动发布与自愈由控制器完成；
  - 影响：本章 7.2 的三种模型在云原生场景下常常是「**平台提供基础（Service），网格提供治理（Istio）**」的组合。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「注册中心必须强一致」 | 注册信息短暂陈旧的后果可由**客户端重试/熔断**兜住；AP 注册中心完全可行（但锁/选主场景必须 CP） |
| 2 | 「服务发现 = 负载均衡」 | 发现回答「有哪些实例、是否健康」；负载均衡回答「选哪一个」；两者可分离 |
| 3 | 「RPC 就是把本地调用搬到远端」 | RPC 有第三种结果：**超时**（不知道是否成功）；重试必须配幂等（[10](10-幂等接口.md)） |
| 4 | 「反向代理多一跳所以一定更慢」 | 集中代理减少了客户端的连接数与重试风暴，在高扇出场景下**总体**可能更快 |
| 5 | 「上了服务网格就不用管重试和超时」 | 网格只是把策略**集中配置**；不合理的值（如无退避的重试）会放大故障，仍需人来判断 |
| 6 | 「健康检查通过了实例就一定可用」 | 健康检查通常是**进程级/端口级**；依赖的下游挂了、线程池打满等「半死」状态检查不出来 |
| 7 | 🔧 本书需 2026 补丁 | 本章未覆盖 **Kubernetes Service + CoreDNS**：2026 年大多数团队的服务发现首先由平台提供，注册中心是「平台之上再加一层」 |
| 8 | 🔧 本书需 2026 补丁 | 7.3 未覆盖 **服务网格接管客户端一致性职责**：重试/超时/熔断/mTLS 已下沉为数据面配置，应用 SDK 大幅瘦身 |
| 9 | 🔧 本书需 2026 补丁 | 本章未覆盖 **可观测性的一体化**：服务调用必须输出 trace/metrics/logs（OpenTelemetry），否则跨节点排障无从下手 |
| 10 | 🔧 本书需 2026 补丁 | 本章未讨论 **就近路由与单元化**（多活/容灾场景下按单元收敛流量），这是 2026 年大规模服务调用的必备话题 |
