## 核心精讲

### 9.1 概述：幂等为什么是分布式的刚需

- **幂等的直观定义**：同一个操作**执行一次与执行多次**，对系统状态的影响**相同**。
- 必须幂等的三个地方（本书实践篇的三条线索在此汇合）：
  | 来源 | 为什么会重复 | 相关章节 |
  | --- | --- | --- |
  | 网络超时重试 | 不知道上一次是否成功 → 只能重试 | [08](08-服务发现与调用.md) |
  | 消息重复投递 | MQ 是「至少一次」语义 | [11](11-分布式中间件与RabbitMQ.md) |
  | 补偿/回滚重试 | TCC 的 Confirm/Cancel 可能重发 | [07](07-分布式事务.md) |
- 🔧 一句话：**在分布式系统里，「恰好一次」是奢望，「至少一次 + 幂等」才是工程答案**。

### 9.2 代数视角：幺元、零元与幂等

> 术语（通用代数定义，与离散数学教材一致）：
> 设集合 `S` 上有二元运算 `⊙`。

| 概念 | 定义 | 直觉 |
| --- | --- | --- |
| **幺元（单位元）e** | 对任意 `a ∈ S`，`e ⊙ a = a ⊙ e = a` | 「做了等于没做」的那个元素 |
| **零元（零元素）θ** | 对任意 `a ∈ S`，`θ ⊙ a = a ⊙ θ = θ` | 「一旦出现就吞掉一切」的那个元素 |
| **幂等元 a** | `a ⊙ a = a` | 「对自己再作用一次，结果不变」 |
| **幂等运算** | 若 `S` 中每个元素都幂等，称运算 ⊙ 是幂等的 | 整个运算天然支持重复 |

- 🔧 为什么这三个概念能用来做接口设计：
  把「**多次调用**」看成「**同一个元素与自己做运算**」，
  那么「重复无害」就等价于「这个元素（或这个运算）是幂等的」。
  于是**幂等化**有了两条明确的路径：
  1. **幺元化**：让「第二次及以后的调用」退化成**幺元**（做了等于没做）；
  2. **零元化**：让某个状态成为**零元**（出现之后，后续调用全被吞掉，结果恒定）。

### 9.3 函数视角：复合与幂等

- **函数的幂等**：`f ∘ f = f`（先做一次再做一次 = 只做一次）。
- **复合函数的幂等**：若 `h = g ∘ f`，则
  `h ∘ h = g ∘ f ∘ g ∘ f`——**一般不等于 `h`**。
  🔧 这正是工程事故的高发点：**两个各自幂等的步骤复合起来未必幂等**。
  例：`f = "读取余额"`（幂等），`g = "余额 +100"`（**非**幂等，是增量运算）→ `g ∘ f` 不幂等。
- 由此得到 9.4 的第三种手法：**运算的幂等化**——把「增量运算」改造成「赋值运算」。

### 9.4 复合函数幂等化的三种手法（本章的方法论核心）

| 手法（原书小节） | 代数含义 | 工程做法 | 例子 |
| --- | --- | --- | --- |
| **函数的幺元化**（9.4.1） | 让重复调用作用在「已达成」的状态上时，等价于**乘以幺元** | 调用前先判断「目标状态是否已是期望状态」，是则直接返回成功 | `PUT /user/1 {name:"A"}` 重复调用结果一致 |
| **函数的零元化**（9.4.2） | 让某个终态成为**零元**，吞掉后续所有操作 | 进入终态后，任何变更请求都返回固定结果（或固定错误），不再改变状态 | 订单「已完成」后任何修改请求都返回终态 |
| **运算的幂等化**（9.4.3） | 把不满足 `a ⊙ a = a` 的运算换成满足的 | 把**增量运算**（`x += n`）改成**赋值运算**（`x = target`）；把「自增 ID」改成「业务唯一键」 | `SET balance = 100`（幂等）替代 `balance += 100`（非幂等） |

- 🔧 三者合起来就是一句话：**要么让重复调用无事可做（幺元），要么让状态封死（零元），
  要么把运算本身改成可重复的（赋值代替累加）**。

### 9.5–9.6 接口的幺元化与零元化

- **接口的幺元化（9.5）**：
  - 设计接口时优先选择**「设置成 X」**而不是**「增加 X」**的语义（PUT 优于 PATCH 累加）；
  - 删除接口对**不存在的资源**应返回成功（删除不存在的 = 结果已达成）；
  - 创建接口接受**客户端提供的业务唯一键**（而不是服务端自增），重复创建返回已存在的资源。
- **接口的零元化（9.6）**：
  - 明确业务的**终态**（已完成、已取消、已退款）；
  - 终态之后的所有写操作返回**同一个结果**（幂等的成功或明确的冲突错误），不再产生副作用；
  - 🔧 典型落地是**状态机 + 状态校验**：`UPDATE ... WHERE status = 'INIT'`，
    已被改过则影响行数为 0 → 直接返回当前状态。

### 9.7 调用的幂等化：四种工程手段（本章最实用的一节）

| 手段（原书小节） | 做法 | 适用 | 注意 |
| --- | --- | --- | --- |
| **判断插入数据**（9.7.1） | 用唯一索引/主键兜住重复插入；撞唯一键即视为已成功 | 创建类接口、防重复下单 | 唯一键必须是**业务唯一键**（如 `order_no`），不能是自增 ID |
| **判断删除数据**（9.7.2） | 删除前先判断是否存在；不存在时按成功处理 | 删除类接口 | 注意「删除后又创建」的场景要能区分 |
| **判断数据版本**（9.7.3） | 乐观锁 `version` / CAS / 状态机条件更新 | 更新类接口、余额与库存 | 版本号必须随请求携带，服务端比较后再写 |
| **拦截重试调用**（9.7.4） | 请求携带**幂等键（idempotency key）**，服务端用去重表拦截重复 | 通用兜底，尤其适合「不知道是否成功」的重试 | 去重记录必须与业务操作**在同一事务**里写，否则拦截不住 |

- 🔧 **幂等键（idempotency key）的最小正确实现**（这是 9.7.4 的关键，也是生产最容易写错的地方）：
  1. 客户端为**同一业务意图**生成唯一键（如 `request_id`），重试时**必须复用同一个键**；
  2. 服务端在处理前先查去重表：
     - 无记录 → 插入去重记录（状态 `PROCESSING`）**并与业务写入放同一事务**；
     - 有记录且已完成 → 直接返回上次的结果（**缓存结果**，不要重复执行）；
     - 有记录且处理中 → 返回「处理中」，让客户端稍后查询（避免并发重复执行）。
  3. 去重记录要有**过期策略**，但不能早于可能的重试窗口。

### 教学示意：幂等键去重的正确写法

```sql
-- 教学示意：去重表与业务表同库同事务；不参与构建，不执行。
CREATE TABLE idempotency (
  idempotency_key VARCHAR(64) PRIMARY KEY,
  state           VARCHAR(16) NOT NULL,   -- PROCESSING / DONE / FAILED
  result          JSON,                   -- 缓存的响应，便于重试直接返回
  created_at      TIMESTAMP NOT NULL
);
```

```python
# 教学示意：带幂等键的接口处理流程；不参与构建，不运行。
def create_order(request):
    key = request.headers["Idempotency-Key"]       # 客户端生成，重试时复用
    with db.transaction():                          # ★ 关键：去重与业务同事务
        row = db.select_one("SELECT * FROM idempotency WHERE key = ? FOR UPDATE", key)
        if row:
            if row.state == "DONE":  return row.result          # 直接返回上次结果
            if row.state == "PROCESSING": raise InProgress(key) # 让客户端稍后查
            if row.state == "FAILED": db.update(key, state="PROCESSING", result=None)
        else:
            db.insert("idempotency", key, state="PROCESSING")

        order_id = db.insert("orders", request.payload)   # 业务唯一键也在同一事务
        result = {"order_id": order_id}

        db.update("idempotency", key, state="DONE", result=result)
    return result
    # 事务回滚 → 去重记录一并消失 → 客户端重试会重新执行（安全）
```

```python
# 教学示意：运算的幂等化——把增量改成赋值；不参与构建，不运行。
# 非幂等（重试两次就多加一次）：
#   UPDATE account SET balance = balance + 100 WHERE id = 1;
# 幂等（携带目标值或幂等键，重复执行结果不变）：
#   UPDATE account SET balance = 900 WHERE id = 1 AND version = 7;
# 幂等（CAS / 状态机，重复执行第二次影响行数为 0）：
#   UPDATE orders SET status = 'PAID' WHERE id = ? AND status = 'INIT';
```

```text
# 教学示意：HTTP 方法的幂等性（RFC 语义，非实现保证）
# 安全（无副作用）：GET / HEAD / OPTIONS / TRACE
# 幂等：GET / HEAD / PUT / DELETE / OPTIONS / TRACE
# 非幂等：POST（语义上「创建/提交」）→ 需要幂等键或业务唯一键来补
# ★ 注意：RFC 给的是「方法语义的要求」，不是「实现的保证」；
#   服务端实现得不好，PUT 也可能不幂等。
```

## 版本演进

- **版本情况**：本书第 1 版（2022-01）；**第 2 版未核实到，标注「待核验」**。以下记录幂等实践的演进。
- **三个阶段**：
  1. **1983–1996（语义层）**：ACID（Haerder & Reuter 1983）让单机事务天然幂等地处理重试；
     HTTP/1.1（RFC 2616，1999；后由 RFC 7231 §4.2.2 与 **RFC 9110 §9.2.2** 更新）
     在协议层规定了「安全方法」与「幂等方法」的**语义要求**；
  2. **2010s（工程层）**：支付与电商场景把「**幂等键**」变成 API 设计惯例
     （Stripe 等支付网关公开其幂等键方案）；消息队列转向「至少一次投递 + 消费端幂等」；
  3. **2013–2026（平台层）**：流处理把「恰好一次」做成平台能力——
     Flink 的异步屏障快照（Carbone 等，2015/2017）、Kafka 的幂等生产者与事务（KIP-98），
     把幂等从「接口设计纪律」升级为「**端到端语义**」。
- 🔧 **2022 → 2026**：
  - 「至少一次投递 + 幂等消费」已与 **Outbox + CDC** 绑定成一套标准范式（见 [07](07-分布式事务.md)）；
  - **exactly-once 被重新定义为端到端属性**：源端可重放 + 处理端 checkpoint + **sink 幂等或事务写入**，
    三者缺一不可——单说「我的流处理引擎是 exactly-once」是不够的；
  - 幂等键进入 API 设计规范（不少团队的 API 规范要求写接口必须支持幂等键）。

## 近年研究与工业界开源实践（2015–2026）

- **流处理与消息侧（star 均为 2026-09 `gh api` 实测）**：
  - `apache/flink`（≈26.4k★）：checkpoint + 两阶段提交 sink，端到端 exactly-once 的代表；
  - `apache/kafka`（≈33.8k★）：幂等生产者（PID + 序列号去重）+ 事务 API（KIP-98）；
  - `apache/rocketmq`（≈22.6k★）：事务消息 + 消费端去重；
  - `apache/pulsar`（≈15.3k★）：提供幂等生产者与事务消息。
- 🔧 **Outbox + CDC + 幂等消费的标准范式**：
  - `debezium/debezium`（≈13.2k★）与 `apache/flink-cdc`（≈6.5k★）把「数据库变更」变成可重放事件流；
  - 组合拳：**本地事务（业务 + Outbox）→ CDC 捕获 → 至少一次投递 → 幂等消费**；
  - 它与本章 9.7.4 的关系：幂等键从「HTTP 头」扩展到「**事件 ID / (topic, partition, offset) 组合**」。
- **幂等键的基础设施**：
  - `redis/redis`（≈76.5k★）：`SET key val NX PX ttl` 常用于短期幂等键去重，
    但要注意「去重与业务写入不同源」时的原子性问题——**最可靠的做法仍是与业务同事务**。
- **支付/API 领域惯例**：把幂等键写进公开 API 的做法已被广泛采用（Stripe 等支付网关公开文档可查），
  是本章 9.7.4 最好的外部佐证。
- **可观测性**：幂等去重命中率应作为**指标**暴露——命中率异常升高往往意味着上游在疯狂重试（故障前兆）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「GET 天然幂等，我只用 GET 就行」 | RFC 给的是**语义要求**不是实现保证；GET 里写数据库的接口照样不幂等 |
| 2 | 「加了唯一索引就幂等了」 | 唯一索引只挡住**重复插入**；更新类操作（累加、状态流转）仍需版本号或幂等键 |
| 3 | 「两个幂等的步骤复合起来也幂等」 | 不成立（9.3）：`g ∘ f` 一般不满足 `h ∘ h = h`；这是复合调用最容易踩的坑 |
| 4 | 「MQ 保证不重复投递，就不用做幂等」 | 「恰好一次投递」在分布式下做不到或有巨大代价；标准语义是**至少一次 + 消费端幂等** |
| 5 | 「幂等键每次重试都重新生成」 | 重试必须**复用同一个键**，否则等于没做幂等 |
| 6 | 「去重表单独写就行」 | 去重记录与业务写入必须**同一事务**；否则「业务成功、去重记录回滚」会把幂等变成漏拦 |
| 7 | 「幂等 = 返回成功」 | 幂等要求**状态影响相同**；对已终态的请求返回「冲突/已完成」也是幂等的（零元化） |
| 8 | 🔧 本书需 2026 补丁 | 本章未把幂等放进**端到端 exactly-once** 的框架：源可重放 + 处理 checkpoint + sink 幂等/事务写入，三者缺一不可 |
| 9 | 🔧 本书需 2026 补丁 | 本章未覆盖 **Outbox + CDC** 场景下的幂等键形态（事件 ID / 位点），这是 2026 年最常见的幂等场景之一 |
| 10 | 🔧 本书需 2026 补丁 | 本章未提**幂等去重命中率应作为监控指标**：它是上游重试风暴的早期信号，应接入 OpenTelemetry/Prometheus |
| 11 | 🔧 本书需 2026 补丁 | 9.7.4 的并发处理（同一键的并发重试）应补「**处理中**」这一中间态：否则并发重试会同时穿透去重 |
