# 12 三向比较与基础特性其他优化

> 对应原书 **第24章 三向比较（C++20）· 第34章 基础特性的其他优化（C++11～C++20，含 34.12 模块）**
> 导航：[系列索引](../C++系列·总索引.md) ｜ [单文件笔记](../现代C++语言核心特性解析.md) ｜ [00 总览](00-总览与阅读地图.md)

## 核心概念速览（中英对照）

- **太空船运算符** — spaceship operator（`<=>`）：一次比较返回三向结果
- **比较类别类型** — ordering types：strong/weak/partial_ordering 三档保真度
- **合成比较** — defaulted comparison：`operator<=> = default` 按成员字典序生成
- **重写约束** — rewritten candidates：仅定义 `<=>` 时 `==/!=/</<=/>/>=` 六式齐发
- **按值默认比较** — defaulted comparison on value categories（C++20 细则，34.4）
- **std::launder** — 指针漂白：同地址新对象让编译器"认账"（C++17，34.2）
- **保证的返回值优化** — RVO/NRVO 与 PRVO：34.3，机制详见文件 04
- **按值推导 new 数组** — `new U[]{...}`（C++20，34.5）
- **伪析构调用** — pseudo-destructor call：`p->int::~int()` 结束对象生命周期（C++20，34.8）
- **destructor(2) operator delete** — C++20 带析构提示的删除函数（34.7）
- **模块** — modules（import/导出，34.12）

## 动机

比较运算是 C++ 最大的样板产地：每个类型六件套 + 全序/偏序语义靠人肉维持一致
（`<` 写了 `>` 忘写、`==` 与 hash 打架）。C++20 把"我声明一个比较，编译器补全其余"
做成语言设施。34 章则是本书的"碎屑抽屉"：显式转换运算符、launder、按值推导 new、
伪析构——每个都是某类底层代码（placement 生命周期管理/小语言实现）的刚需，
外加模块这个"大碎屑"。

## 机制（编译器视角）

- **`<=> = default` 是编译器模板**：对成员**声明序字典序**逐对比较，短路返回；
  生成物是 `operator<=>` + **合成六个重写候选**（`==` 另可独立 default——C++20 起
  `==` 不再从 `<=>` 自动派生布尔，而是"若没写则用 `<=>==0` 重写"，两者并存时 `==` 优先）。
  实测：只 default 了 `<=>` 的 `V`，`x<y / x!=y / x>=y` 全部工作。
- **三档 ordering 是"比较能否区分等价与相等"的类型编码**：
  `strong_ordering`（可替换，如 int）、`weak_ordering`（等价≠相等，如忽略大小写字符串）、
  `partial_ordering`（有不可比存在，如 float+NaN）。编译器在 `<=>` 返回类型上做
  概念检查（`three_way_comparable`），选错档位=语义说谎，静态检查救不了你。
- **float 的 `<=>`**：`std::partial_ordering`，且 NaN 使 `unordered` 合法；
  `-0.0==0.0` 但 `<=>` 给 equal——IEEE 语义完整保留（编译器用符号位+大小三分决策树）。
- **`std::launder` 的存在理由**：编译器基于"指针相等 ⇒ 同一对象"做别名/常量优化；
  placement new 在同地址换对象后，旧指针按 TBAA/object model 仍指向"旧对象幽灵"，
  launder 是向编译器**宣告对象已换新**的 intrinsic（GCC 实现为 `__builtin_launder`，
  优化层禁止穿透）。典型触发：`const` 成员/基类子对象原地替换 + union 活跃成员切换
  （与文件 08 手工协议呼应）。
- **34.7 在 `operator delete` 里析构对象（destroying delete）**：C++20 新增
  `void operator delete(void*, std::destroying_delete_t)`——delete 表达式**不再**由编译器
  调析构，而是把对象指针（可转型）交给你的 delete 函数自己处置：小对象内存池/
  自定义 vtable 调度语言的运行时从此不需要 hack delete 调用点。
- **34.8 伪析构调用**：`p->T::~T()` 语法早已存在但仅限"对象可访问"语境；C++20 允许
  用 typedef/typename 名结束任意对象生命周期（实现 variant/alignas 缓冲时不用写
  具体类型的 ~ 调用壳）。
- **模块（34.12）**一句话机制：`export module m;` 编译产生 **BMI（模块接口文件）**，
  下游 `import m;` 读入的是**已语义分析的 AST 序列化**而非文本——预处理/头文件守卫/
  文本包含模型整个被替换；宏默认不进模块。支持度本机实测：

  ```text
  g++ -std=gnu++20 -fmodules 模块接口 → error: 'module' does not name a type
  g++ -std=gnu++23 -fmodules 模块接口 → 编译通过
  ```

  GCC 15 的完整 modules 链路（named module + BMI 目录）在本机**未做端到端多文件实测** ⚠️，
  此处只留语法层取证；Clang/MSVC 的模块成熟度高于 GCC 是 2021-2026 共识（谨慎措辞）。

## 权衡

- `<=>` 合成的是**字典序**：成员顺序变化即比较语义变化——把"成员声明序"当成 ABI
  一样对待；不想全暴露就手写 `==` + 子集比较。
- 默认比较会把**所有成员**卷入， Padding/缓存字段/版本字段要显式排除
  （惯用法：`std::tuple` 化参与比较的子集）。
- `std::launder` 是**性能换正确性**的窄口：到处launder 等于关掉一类优化；
  只在对象替换边界用。
- destroying delete 要求**所有**该类的 new/delete 成对自定义，否则重载集合混乱；
  框架级才值得。

## 相邻概念对比

| 需求 | C++17 手工方案 | C++20 语言方案 |
| --- | --- | --- |
| 六件套比较 | 手写/宏生成 | `operator<=> = default` |
| 类内不变量校验 | assert/静态检查 | `==` 独立 default（允许"等价但不同"时手写） |
| 原地换对象后用旧指针 | UB 边缘游走 | `std::launder` |
| delete 时自定义析构路径 | 类型擦除 hack | destroying delete |
| 编译防火墙 | Pimpl | 模块 BMI（文件 02 链接性话题的续篇） |

## 🔧 实测样例（已实测 g++ 15.2，-std=gnu++20）

```cpp
#include <cstdio>
#include <compare>
struct Base{ virtual bool eq(const Base&) const; virtual ~Base() = default; };
struct Der : Base{ bool eq(long) const override; };        // 故意写歪签名
struct V{ int a, b; std::strong_ordering operator<=>(const V&) const = default; };
int main(){ V x{1,2}, y{1,3};
  printf("x<y=%d x!=y=%d x>=y=%d\n", x<y, x!=y, x>=y); }   // == != < > <= >= 全部合成
```

`override` 签名漂移的实测诊断（同 TU 编译）：

```text
error: 'bool Der::eq(long int) const' marked 'override', but does not override
```

修复为 `eq(const Base&) const override { return true; }` 后运行：

```text
x<y=1 x!=y=1 x>=y=0
```

**只写了一个 `<=>`，`!=` 与 `>=` 都工作**——六个重写候选的取证。
aligned new/`std::construct_at` 实测（-std=gnu++20，归 13 文件话题但此处联动）：
`aligned new addr%64=0 sizeof(CacheLine)=64` / `construct_at=9`；
同程序里 `std::start_lifetime_as` 实测**未被 libstdc++ 15 提供**
（`error: 'start_lifetime_as' is not a member of 'std'`）——launder 家族的语言层
（P0593R6，实测 302）与库层进度差活例。

## 最新演进与工业实践

- **C++23：`std::expected`（P2505R5 monadic，实测 302 为配套 monads 提案）**把"错误即
  值"接进比较/解包生态；`<=>` 的余波是 `std::compare_three_way` 进入算法（
  `ranges::binary_search` 等默认比较器换代）。
- **按值默认比较（34.4）的坑位回顾**：C++20 初版 `<=>` 对基类切片比较的行为修订
  （LWG 3683? 编号 ⚠️ 未实测不引）——工业教训：default `<=>` 的类型有基类时写测试。
- **模块工业现状**：MSVC 是 C++20 modules 最激进实现（`/std:c++20`+IFC），
  CMake 3.23+ 的 `FILE_SET CXX_MODULES` 把跨编译器模块构建拉进正轨；
  abseil/folly 截至本笔记未全量迁移（观望 + `-fmodule` 实验），
  range-v3/std::ranges 生态则吃"头文件+宏"旧账最狠（⚠️ 表述为趋势判断，未逐一取证）。
- **`import std;`**（P1699 实测 404 → **不引用提案号**；机制已随 C++23 的
  标准库模块分发生效，GCC/Clang/MSVC 于 2024-2026 相继可用，措辞保守）。
- **[[assume]]（C++26，P2811 实测 302，标题机读失败 ⚠️）**与 destroying delete 同属
  "给优化器下指令"路线：Godbolt 上 `[[assume(x>0)]]` 消除分支的样例是当代
  低延迟库（folly::fibers? 不逐引）常用手段。
