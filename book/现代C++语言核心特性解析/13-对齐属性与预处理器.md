## 核心概念速览（中英对照）

- **数据对齐** — data alignment：对象地址必须是其对齐要求的倍数（平台/向量指令根因）
- **alignof** — alignment-of 运算符：查询类型的对齐要求
- **alignas** — alignment 说明符：请求类型/变量的新对齐（可超过默认=超对齐）
- **超对齐类型** — over-aligned type：`alignas(64)` 类，C++17 起 new/delete 携带对齐
- **属性语法** — attribute syntax：`[[...]]` 标准属性 vs `__attribute__((...))`/`__declspec(...)` 厂商属性
- **[[nodiscard]]** — 弃返回值警告属性（C++17；C++20 可标注类型）
- **[[maybe_unused]] / [[deprecated]] / [[fallthrough]] / [[noreturn]]** — 诊断类标准属性
- **[[carries_dependency]]** — 内存模型提示属性（C++11，实现采纳度低）
- **[[likely]] / [[unlikely]]** — 分支预测提示（C++20）
- **[[no_unique_address]]** — 成员空优化属性 EBO（C++20）
- **__has_include** — 预处理包含探测（C++17）
- **特性测试宏** — feature-test macros：`__cpp_lib_*`/`__cpp_impl_*`（C++17 `<version>`）
- **__VA_OPT__** — 变参宏分隔符控制（C++20）

## 动机

三章是"**与编译器和构建环境谈判的正式语法**"：
- 对齐：`__attribute__((aligned))`/`#pragma pack` 方言横行的性能关键区（缓存行、SIMD）
  需要标准武器；
- 属性：GCC/MSVC 各自的 `__attribute__`/`__declspec` 不可移植，且旧扩展语法
  `[[attribute]]`（如 `int [[x]]`）难解析——C++11 统一 `[[...]]` 并收编首批标准属性；
- 预处理器：库要探测"有没有 `<optional>`/编译器到了哪一代"，`__has_include` 与
  特性测试宏把 `#ifdef` 玄学变成可查询事实。

## 机制（编译器视角）

- **对齐在布局层生效**：`struct Packed{ char a; int b; }` 实测
  `alignof=4 sizeof=8`——GCC 按成员对齐插入 padding（a 后垫 3）；
  `alignas(64) CacheLine` 实测 `sizeof=64 alignof=64`，且 `::operator new(size,
  std::align_val_t{64})` 返回地址 `%64==0`（🔧 实测）——C++17 起 aligned new 家族
  带 `std::align_val_t` 重载，超对齐类型的**析构删除函数也必须收对齐参数**否则链接错配。
  Windows/MinGW 的历史坑：MSVC 的 malloc 只保证 16，MinGW 走 msvcrt 时超对齐需
  `_aligned_malloc` 桥（本目录只陈述本机实测通过，不再外推 ⚠️）。
- **`[[no_unique_address]]` 的实现**：编译器把空类型成员的 EBO 从"基类特权"扩展到
  "任意成员"，实测 `sizeof(Layout1)=8`（空成员占 1 导致填充）vs
  `sizeof(Layout2)=4`（属性生效）。它与匿名 union 位域手法相比是**类型安全版**；
  限制：对非空成员退化回普通占位；与 `[[gnu::no_unique_address]]`（更早 GCC 扩展）同义。
- **属性是"带命名空间的标注"**：标准属性在 `std` 命名空间，`using namespace std;` 后
  可写 `[[nodiscard]]`；厂商属性必须带 `gnu::`/`msvc::` 前缀（本书 31.4 的 using 打开
  技巧）。编译器对**未知属性**的处理是"警告但继续"（与宏的静默吞噬对比，这是属性
  优于宏的核心论据——拼错 `__has_features` 无声，拼错属性有警告）。
- **诊断类属性的 lower 位置**：
  `[[nodiscard]]` 挂在 `FunctionDecl`，调用点 `Sema::CheckForDiscardedAttributes`
  报 `-Wunused-result`（实测原文：`ignoring return value of 'int important()',
  declared with attribute 'nodiscard'`）；
  `[[likely]]` 进 GCC 的预测 pass（profile/预测初始化），与 `__builtin_expect` 同槽；
  `[[noreturn]]` 让调用点之后的代码成为可达性死区（控制流图收尾，未初始化警告随之改变）；
  `[[fallthrough]]` 抑制空 case 警告——纯 Sema 标记位。
- **`carries_dependency` 的标准与现实**：意图是给 release/acquire 链去掉栅栏，
  三家实现均未采纳优化（P0768? ⚠️ 不引号；按共识陈述）——**标准属性≠有效属性**的标本。
- **`__VA_OPT__`（C++20）**：`__VA_OPT__(,)` 在变参为空时整体消失，终结
  `##__VA_ARGS__` 扩展逗号粘贴 hack；实测无参/有参两形态都正确（`no-args line` /
  `two args: 7 abseil`）。
- **特性测试宏矩阵**：`<version>` 头是"实现自述表"——`__cpp_if_constexpr`、
  `__cpp_lib_expected` 之类；库条件编译（abseil 的 ABSL_HAVE_STD_OPTIONAL）靠它，
  但**各实现的宏值更新滞后于实际支持**是行业通病（链"编译器≠标准库"三层支持观，文件 01）。

## 权衡

- 超对齐改变 `sizeof`/new 路径：混用 aligned/unaligned `operator delete` 是 UB；
  类型一旦 `alignas` 就把自己交出去给对齐规则（放进旧容器/placement 时三查）。
- `[[no_unique_address]]` 让 EBO 进成员，但取地址语义变微妙（成员可能与后续成员
  同地址）——**不要对"可空优化成员"取指针比较**；`std::tuple` 靠它瘦身但 debug 模式下
  常禁用（实现开关）。
- 属性 vs 宏的选型：属性有语法检查/无展开冲突，但**不能条件编译**（`[[maybe_unused]]`
  配 `#if` 仍是宏的世界）；`__has_include` 探测头文件存在**不探测符号存在**——
  特性测试宏才是符号级真相，三者构成"探测深度阶梯"。

## 相邻概念对比

| 探测手段 | 粒度 | 例子 | 失败模式 |
| --- | --- | --- | --- |
| `#ifdef` 编译器宏 | 工具链 | `__GNUC__` | 版本≠特性 |
| `__has_include` | 文件 | `<version>` | 文件在≠实现全 |
| 特性测试宏 | 特性 | `__cpp_lib_expected>=...` | 更新滞后 |
| concepts/SFINAE（文件 16） | 表达式 | `requires std::range<R>` | 编译期才可用 |

## 🔧 实测样例（已实测 g++ 15.2，-std=gnu++20/-std=gnu++11）

对齐与 EBO（gnu++20）：

```cpp
#include <cstdio>
struct Padded{ alignas(64) char line; char data[7]; };
struct Packed{ char a; int b; };
struct Empty{};
struct Layout1{ Empty e; int v; };
struct Layout2{ [[no_unique_address]] Empty e; int v; };
enum E16 : unsigned short { a };
int main(){
  printf("alignof(Padded)=%zu sizeof(Packed)=%zu alignof(Packed)=%zu alignof(E16)=%zu\n",
     alignof(Padded), sizeof(Packed), alignof(Packed), alignof(E16));
  printf("sizeof(Layout1)=%zu sizeof(Layout2)=%zu\n", sizeof(Layout1), sizeof(Layout2));
}
```
实测输出：

```text
alignof(Padded)=64 sizeof(Packed)=8 alignof(Packed)=4 alignof(E16)=2
sizeof(Layout1)=8 sizeof(Layout2)=4
```

aligned new + construct_at + __VA_OPT__（gnu++20）：

```text
no-args line
two args: 7 abseil
aligned new addr%64=0 sizeof(CacheLine)=64
construct_at=9
```

`[[nodiscard]]` 警告实测（gnu++17 -Wall）：

```text
warning: ignoring return value of 'int important()', declared with attribute 'nodiscard' [-Wunused-result]
```

`__has_include(<version>)` 分支实测通过（样例包含后使用 `__cpp_impl_destroying_delete`
探测，gnu++20 下宏可见）。

## 最新演进与工业实践

- **C++23/26 属性续作**：`[[assume]]`（C++26，P2811 实测 302，标题机读未成功 ⚠️——
  优化器契约属性）；P2552R3 **"On the ignorability of standard attributes"（实测 302）**
  ——把"可忽略属性"（ignore-and-continue 语义）标准化，未知属性不再各厂行为不一；
  `[[nodiscard(...)]]` 带理由消息（C++23）补上"为什么别丢返回值"。
- **工业设施对照**：folly 的 `FOLLY_ASSUME`/`FOLLY_INLINE` 宏家族是属性标准化前的
  等价层；abseil 的 `ABSL Attributes` 文档（`ABSL_ATTRIBUTE_*`）同样是被 `[[...]]`
  收编的桥接层；mimalloc/Intel oneAPI 等用 `alignas(64)`+`[[no_unique_address]]`
  做缓存行对齐与空优化成员（⚠️ 项目细节未逐一读源码，模式性描述）。
- **`std::assume_aligned`（C++20，P0600 系[[nodiscard]] 库化提案实测 302）**：
  指针"我保证已对齐"的库层版本，与语言层属性互补。
- **预处理器继续被边缘化**：modules（文件 12）+ 特性测试宏 + concepts 三件套之后，
  `#if` 手工探测在新增代码里的份额持续萎缩——CMake `configure_file`/`compile_feature`
  层承担更多探测职责（工程趋势判断）。
