# 第 3 章 编程范式总览 与 第 4 章 结构化编程

> **一句话**：结构化编程的全部遗产只有一条可执行的约束——**不要用 goto**；而这条约束之所以重要，是因为它让「一段程序能否被推理」成为架构的地基。

## 核心精讲

**教学示意，不参与构建、不编译、不运行。**

三个范式的本质是「对跳转/赋值的不同约束」——这是本书里非常好用的一张对照表：

| 范式 | 被约束的东西 | 架构上的意义 |
| --- | --- | --- |
| 结构化编程 | 直接跳转（goto） | 让控制流可以**分层推理**：一个函数只有一个出口，好测 |
| 面向对象编程 | 间接跳转（函数调用点） | 让「调用哪个实现」可以在运行时决定 → **依赖反转的技术基础** |
| 函数式编程 | 赋值（可变状态） | 让「有没有被改过」这个问题消失 → 单测与并发都变简单 |

Ch4 的「功能性降解拆分」用同一个例子讲两遍（示意，非真实源码）：

```java
// 反例：控制流与逻辑纠缠，无法单独验证排序部分
// （示意：goto 风格的控制流，无法把"排序"单独抽出来推理）
void process(List<Order> orders) {
    // ... 一堆穿插的分支
}
```

```java
// 正例：把不可变部分（纯函数）和可验证部分（外壳）分开
static List<Row> sortedRows(List<Row> rows) {        // 纯：只依赖输入
    return rows.stream().sorted(Comparator.comparing(Row::id)).toList();
}

List<Row> handle(List<Row> rows) {                   // 外壳：负责 IO、异常、事务
    List<Row> clean = rows.stream().filter(r -> r.valid()).toList();
    return sortedRows(clean);
}
```

> 本书的关键论断是：**「顺序结构 + 单入口单出口」不只是代码风格，它决定了你能否把一段逻辑从系统里抠出来单独测试**；而「能单独测」正是架构边界存在的前提。

## 版本演进

| 时期 | 事件 | 与本章的关系 |
| --- | --- | --- |
| 1968 | Dijkstra，《Go To Statement Considered Harmful》（Comm. ACM） | Ch4 的第一性来源，也是结构化编程的起点 |
| 1968 | Conway，《How Do Committees Invent?》（Datamation） | 与结构化同年的另一条线索：结构由人产生（见第 9 章） |
| 1972 | Wirth，《Program = Data Structures + Algorithms》（CACM） | 「程序 = 算法 + 数据结构」的经典表述，Ch3 用它当靶子 |
| 1980s | 结构化编程成为工业规范（可自顶向下设计、流程图） | Ch4「科学来救场」的语境 |
| 2000s | 单元测试框架成熟，测试取代形式化证明成为主流验证手段 | Ch4「形式化证明没有发生」的现实版答案 |
| 2017 | 本书出版，把结构化编程降级为「三条约束之一」 | 范式不再神圣，只按「约束了什么」来评估 |
| 2020 年代 | 函数式思想（不可变数据结构、纯函数、事件溯源）在主流语言里被普遍吸收 | Ch6 的内容成为默认实践，Ch3 的「三选一」说法进一步淡化 |
| 2020 年代 | AI 生成代码大量产出嵌套分支与控制流，Ch4 的可推理性重回刚需 | 测试与静态分析成为 AI 时代的主要防线 |

| 仓库 | star（2026-09-25 `gh api` 实测） | 说明 |
| --- | --- | --- |
| `rust-lang/rust` | **119150** | 所有权与不可变默认（`mut` 显式声明）把 Ch6 的不可变性变成编译器义务 |

## 常见误区与本书需修正之处

| 误区 | 表现 | 修正 |
| --- | --- | --- |
| 🔧 把「三个范式」当成教科书式的分类去背 | 争论「我这是不是函数式」 | 只问一句：**这段代码的依赖与状态谁在控制** |
| 认为「goto 有害」在 2026 年已过时 | 用异常、事件、回调绕开控制流，等价物比 goto 更糟 | 异常与回调都是**改名的 goto**；同样要受结构化约束 |
| 把「不可变性」当成必须全面不可变 | 全函数式改写业务系统，性能与心智成本双输 | Ch6 的建议是**隔离可变性**：边界处收口，内部按需可变 |
| 🔧 「面向 XX 编程」的营销说法 | 团队口号换了一轮又一轮 | 范式只是约束集合，架构决策不依赖哪个范式 |
| Ch4 的「可推导性」被读成「我们能证明程序」 | 花时间做不可行的形式化 | 承认证明做不到，改用**可组合 + 可测试 + 静态分析**三件套 |
| 认为结构化编程只属于 1970 年代 | — | 它现在仍然决定了「一段逻辑能否被单独抠出来测」 |
