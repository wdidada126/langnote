# 第 14 章 组件耦合

> **一句话**：组件的规矩只有两条——**别成环**（ACD），以及**别让不稳定的东西被稳定的东西依赖**（SDP），而 SAP（稳定抽象原则）把二者合起来说：**越稳定的组件，抽象程度应该越高**。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Ch14 无依赖环原则（ACD） | 组件依赖图必须无环 | 环会让「发布顺序」与「理解顺序」双双失控 |
| Ch14 自上而下的设计 | 环是怎么被「事后补救」引入的 | 常见手法是回调/事件/`util` 包绕开依赖方向 |
| Ch14 稳定依赖原则（SDP） | 依赖方向要指向稳定方向 | 让「变更较少」的组件挡在前面 |
| Ch14 稳定抽象原则（SAP） | 稳定组件必须足够抽象 | 防止「稳定组件」变成「没人敢碰的死代码」 |
| Ch14 组件耦合张力图 | 稳定性 vs 抽象度 | 稳定的组件很可能是具体的 → 危险区 |
| Ch14 本章小结 | 三个原则是一条曲线的三个投影 | 用度量的方式谈架构，而不是靠口味 |

## 核心精讲

**教学示意，不参与构建、不编译、不运行。**

**稳定性度量**：某组件 i 的不稳定度 `I = 传入依赖数 / (传入 + 传出依赖数)`，`I=0` 最稳定，`I=1` 最不稳定。

```text
     抽象度 A
         ^
         |                  理想线 A = 1 - I
         |                  *
         |                *     <- 稳定且抽象（好）
         |              *
         |            *
         |          *
         |        *
         |     *           <- 稳定且具体（危险：没人敢改）
         |   *
         | *             <- 不稳定且抽象（等于没抽象）
         +------------------------------------> 不稳定度 I
         O（0,0）左上角 = 稳定；右上角 = 不稳定
```

**四条可执行的规则**（示意写法，落地按语言选工具）：

```text
# 1) 无依赖环：C4 层（Components）不得反依赖 C3
# 2) 稳定依赖：稳定组件（I≈0）不得依赖不稳定组件
# 3) 稳定抽象：稳定组件里抽象类型的比例要够高
# 4) 单向指向：domain 包不得出现对 web/infra 包的 import
```

**最常见的「伪解环」套路**（这些写法能过编译，但仍然制造环）：

| 手法 | 表面效果 | 真实后果 |
| --- | --- | --- |
| 把共享逻辑放进 `util` / `common` | 消除了 import 方向 | `util` 被所有组件依赖 → 事实上不可发布 |
| 用事件（Event）互相通知 | 「不直接调用了」 | 事件契约散落各处，跨组件一致性失控 |
| 用回调反转调用 | 依赖图看起来无环 | 控制流变成图，读者无法自上而下推理 |
| 组件 A「继承」组件 B 的实现 | 复用了代码 | 具体实现进入继承链，LSP 破裂（见 `05-LSP与ISP.md`） |

## 常见误区与本书需修正之处

| 误区 | 表现 | 修正 |
| --- | --- | --- |
| 🔧 把「无环」当成可以牺牲架构正确性的逃生口 | 用事件/回调/`util` 强行拆环，代价是控制流不可读 | 先解决真正的依赖方向；环的结构性修复优于绕路 |
| 认为 SAP 要求「稳定组件必须抽象」是普适 | 让所有稳定模块都为扩展留口 | 只对**预期长期存在**的组件要求抽象；一次性组件不在此列 |
| 把「稳定性」理解为人少改动 | 用「没人改」当稳定性证据 | 用依赖计数（I 值）衡量稳定性，而不是主观印象 |
| 组件内也强制无环 | 为了拆一个内部环把类拆到七八个文件 | 环只在组件间才算代价（Ch12–13 的组件定义） |
| 🔧 SDP 被读成「依赖越少越稳定」 | 刻意制造「没人依赖的核心包」 | 稳定 = 依赖它的人多；不要为了指标制造假稳定 |
| 认为架构规则靠文档维持 | README 里画了依赖图，半年后没人看 | 用 CI 规则机器化（ArchUnit / dependency-cruiser / Bazel） |
