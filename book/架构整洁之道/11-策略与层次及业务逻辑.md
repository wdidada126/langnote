# 第 19 章 策略与层次 与 第 20 章 业务逻辑

> **一句话**：本章把「依赖方向」做了一次定量的刻度——策略离圆心越远越具体、**层次（Level）就是「离中心的步数」**；而业务逻辑的形状（实体 vs 用例 vs DTO）决定了这条刻度能不能落地。

## 核心精讲

**教学示意，不参与构建、不编译、不运行。**

**「层次」的量化理解**：层次不是「第几层目录」，而是**这条依赖跳了几步才能到达业务规则**。

```text
   Level 0（最内，最稳定、最贵）   —— 业务实体：Order、Money
        |
   Level 1                        —— 用例：PlaceOrder（依赖实体）
        |
   Level 2                        —— 接口适配器：Controller / Presenter
        |
   Level 3（最外，最易变、最便宜）  —— 框架与驱动：Hibernate、Jackson、Servlet
```

**业务逻辑的三段式**（Ch20 的形状图）：

| 角色 | 回答什么问题 | 是否认识框架 | 变化原因 |
| --- | --- | --- | --- |
| 业务实体 Business Entity | 「什么是对的」（不变式、规则） | 不认识 | 领域语言变化（很少） |
| 用例 Use Case | 「要做什么」（编排、流程） | 不认识 | 需求编排变化（中等） |
| 请求/响应模型 DTO | 「长什么样」（传输格式） | 认识外层格式 | 协议/UI 变化（频繁） |

```java
// ---------- Business Entity（最内，不认识任何框架） ----------
public final class Order {
    private final OrderId id;
    private final Money total;
    private final List<OrderLine> lines;

    public static Order place(CustomerId cid, List<OrderLine> lines, Money discount) {
        Money sum = lines.stream().map(OrderLine::price).reduce(Money.ZERO, Money::plus);
        if (sum.lessThan(discount)) throw new IllegalStateException("discount too large");
        return new Order(OrderId.newId(), cid, lines, sum.minus(discount));
    }
    public Money total() { return total; }
}
```

```java
// ---------- Use Case（只依赖自己定义的抽象与 DTO） ----------
public final class PlaceOrder {
    private final OrderRepository repo;
    public PlaceOrder(OrderRepository repo) { this.repo = repo; }

    public PlaceOrderResponse execute(PlaceOrderRequest req) {
        Order o = Order.place(req.customerId(), req.lines(), req.discount());   // 规则
        repo.save(o);                                                           // 抽象
        return new PlaceOrderResponse(o.id(), o.total());                       // DTO
    }
}
```

## 近年研究与工业界开源实践（2015–2026）

## 常见误区与本书需修正之处

| 误区 | 表现 | 修正 |
| --- | --- | --- |
| 🔧 把「用例」当成「业务的全部」 | 用例里写满规则，实体只剩 getter/setter | 不变式归聚合（实体），用例只做编排 |
| 🔧 用例层返回领域对象，让外层直接消费 | Presenter 直接读 `Order.getLines()` | 用例返回 DTO，Presenter 只认 DTO（Ch23） |
| 把事务边界画在用例外的注解上却不知其意 | `@Transactional` 一刀切，长事务频发 | 事务边界属于用例层设计的一部分，不是框架配置 |
| 「层次」被当成目录层级 | `level1/`、`level2/` 命名 | 层次 = 依赖距离（离业务规则几步） |
| 实体被当成「数据类」用 | 实体里只有字段与 getter，规则散到 Service | 规则属于实体；Service 只编排 |
| 认为 DTO 只是「为了方便」 | 领域对象直接序列化，字段随 UI 变化 | DTO 是边界契约，专门维护（Ch17） |
| 事务与规则混写导致难以测试 | 单测必须起数据库 | 规则与事务分离：实体与用例可纯内存测试 |
