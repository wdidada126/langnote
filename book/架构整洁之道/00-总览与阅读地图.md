# 《架构整洁之道》总览与阅读地图

> **一句话**：这本书真正要回答的不是「怎么分层」，而是「哪些决定必须留在系统最里面、哪些决定可以外包给框架」——判据只有一个：依赖方向，以及「留住改与不选的权利」的成本。
> 原书 *Clean Architecture: A Craftsman's Guide to Software Structure and Design*, Robert C. Martin, Prentice Hall 2017-09, ISBN 9780134494166, 432 页。
> 中译本：Robert C. Martin 著，**孙宇聪** 译，**电子工业出版社 2018-09**，**ISBN 9787121347962**（ISBN 经出版社书目页与百度百科词条交叉核实为 978-7-121-34796-2），定价 99.00 元，324 页，6 部分 34 章 + 附录 A「架构设计考古」。

## 3. 依赖方向与分层总览（同心圆）

### 3.1 同心圆 ASCII 图

源码依赖的方向一律**指向圆心**（" inward"）；跨层调用（调用发生在运行时）则**由外向内**，内层永不 outer 回调外层。

```
   +---------------------------------------------------------------+
   |  Frameworks & Drivers       框架与驱动层（最外、最易改）        |
   |  Web/UI、数据库、框架、Main 组件、外部脚本与工具                 |
   +-------------------------------+---------------------------------+
                                   |  依赖方向：向内（inward）
                                   v
   +---------------------------------------------------------------+
   |  Interface Adapters        接口适配器层                        |
   |  Controllers / Presenters / Gateways / DTO / 数据映射器         |
   +-------------------------------+---------------------------------+
                                   |  依赖方向：向内
                                   v
   +---------------------------------------------------------------+
   |  Use Cases                 用例层                              |
   |  Interactor / 业务用例 / 输入出 DTO / 事务边界                   |
   +-------------------------------+---------------------------------+
                                   |  依赖方向：向内
                                   v
   +---------------------------------------------------------------+
   |  Entities                  实体层（最内、最稳定）                |
   |  企业级业务规则 / 领域对象 / 与框架、DB、UI 完全无关             |
   +---------------------------------------------------------------+

   对应运行时调用：外层 -> 内层
     HTTP 请求 -> Controller -> UseCase(Interactor) -> Entity
     DB 读取   -> Gateway    -> UseCase            -> Entity
```

### 3.2 各层职责表

| 层 | 英文 | 谁负责 | 允许的依赖 | 该层放什么技术 | 常见误用 |
| --- | --- | --- | --- | --- | --- |
| 实体层 | Entities | 企业级业务规则 | 只允许依赖同层甚至无依赖 | 领域对象、不变式、值对象 | 把 JPA 注解打在实体上，让最内圈被 ORM 绑死 |
| 用例层 | Use Cases | 应用级业务规则（一个用例一件事） | 向内依赖实体层；**向外只依赖接口** | Interactor、输入/输出 DTO、事务脚本 | 用例里直接写 SQL，或用例之间互相依赖 |
| 接口适配器层 | Interface Adapters | 把外层数据格式转成用例能懂的形状 | 向内依赖用例层接口，向外依赖框架 | Controller、Presenter、Gateway、Repository 实现 | 把业务逻辑写进 Controller/Presenter |
| 框架与驱动 | Frameworks & Drivers | 具体的数据库、Web 服务、框架、Main | 被内层依赖其接口 | Spring/Hibernate/MySQL/React/Main | 把「框架最佳实践」当成架构决策 |

### 3.3 依赖方向的四条硬规则

| 规则 | 含义 | 违反后果 |
| --- | --- | --- |
| 源码依赖向内 | `import` / `use` 只能指向内层包 | 内层一改，外层跟着全量重编译 |
| 内不识外 | 内层**不得 import** 外层任何东西 | 业务规则被 Web 框架类型污染，单测必须起容器 |
| 外可识内 | 外层可以依赖内层的接口，用实现注入 | 无 — 这正是要保留的机制 |
| 跨边界只传 DTO | 边界两侧只传简单数据结构，不传领域对象 | 领域对象被序列化策略牵着走 |

## 5. 本书刻意规避 / 未覆盖的缺口

| 缺口 | 说明 | 补到哪里 |
| --- | --- | --- |
| **并发架构** | 全书没有任何一章讨论线程、事件循环、异步边界如何进入分层结构；Ch29「整洁的嵌入式架构」只处理目标硬件瓶颈 | `book/代码整洁之道*`、`book/Java并发编程*` 系列；本目录 14 章「常见误区」列出该缺口 |

| **数据建模与数据库选型的具体权衡** | Ch30 只论证「关系型数据库是可替换的实现细节」，不给索引、事务隔离级别、存储引擎、多模数据库的取舍标准 | `book/数据库系统概念6/`、`book/MySQL技术内幕（第5版）.md` |

## 6. 实验工具链：架构守护

> star 均为 **2026-09-25 用 `gh api repos/OWNER/REPO --jq '.stargazers_count'` 实测**。

| 工具 | 用途 | 典型规则示例 | star（实测） |
| --- | --- | --- | --- |
| `TNG/ArchUnit` | Java 字节码级架构守护，失败即构建失败 | `noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat().resideInAnyPackage("..web..")` | **3843** |
| `sverweij/dependency-cruiser` | JS/TS 依赖图检查，适合前端与 Node 服务 | `{"name": "no-domain-to-web", "from": {"path": "^src/domain"}, "to": {"pathNot": "^src/web"}}` | **7218** |

| `rust-lang/rust` | Rust 的 `mod`/`crate` 提供真正的私有性，可以用 `pub(crate)` + 手动 lint 守护分层 | clippy 自定义 lint 检查 `domain` 模块不得 `use crate::web` | **119150** |
| `spring-projects/spring-framework` / `spring-projects/spring-boot` | 本书 Ch32 的对象：框架是「单向婚姻」，但也是实践里最容易抄起 refactor 的参照物 | — | **60260 / 81497** |

| `pytest-dev/pytest` | Ch28 的落点：把「测试系统」当成一等组件，用测试专用 API 降低端到端成本 | 分层 fixture、`--test-arch` 时跳过集成测试 | **14534** |

> 手工实验建议（**教学性质，不参与任何构建**）：拿一个小项目，分别用 ArchUnit（Java）、dependency-cruiser（TS）、`go list -deps`（Go）、`cargo` 的模块私有性（Rust）跑同一条规则「`domain` 不得依赖 `web`/`infra`」，对比四种语言下「边界」是靠编译器保证、靠构建工具保证、还是只靠人自觉。
