# 第 5 章 面向对象编程 与 第 6 章 函数式编程

> **一句话**：OOP 真正买到的是「用多态把依赖方向反转过来」的能力，FP 真正买到的是「把可变性关进笼子」的能力——两者都不是为了「更优雅」，而是为了「更贵的选择被推迟」。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Ch5 封装 | 把数据与操作绑在一起 | 封装让「信息隐藏」可落地，是组件化的前提 |
| Ch5 继承 | 子类替代父类 | 继承是强耦合，用错代价极高（LSP 的靶子） |
| Ch5 多态 | 用间接调用替代条件分支 | **多态 = 架构层的依赖反转开关** |
| Ch5 本章小结 | OOP 的三要素不是「必须全用」 | 关键是能控制「调用哪个实现」 |
| Ch6 整数平方 | 一个 `square` 函数的三种写法 | 从命令式到声明式的光谱 |
| Ch6 不可变性与软件架构 | 不可变带来的推理便利 | 不可变让「谁改了它」不再是架构问题 |
| Ch6 可变性的隔离 | 把可变部分圈起来 | 实践中更可行的是「隔离」而非「消灭」 |
| Ch6 事件溯源 | 不存状态，存事件 | 用「可重放的历史」换取可审计与可回滚 |
| Ch6 本章小结 | FP 是第三种约束 | 与结构化、OOP 并列，取长于「无副作用」 |

## 核心精讲

**教学示意，不参与构建、不编译、不运行。**

**Ch5 的核心：用同一批数据结构，让调用方不依赖具体实现。**

```java
// Entities / 领域对象：不认识框架
public interface CandidateClock { long today(); }         // 抽象，向内

// 外层提供实现：向外
public class SystemClock implements CandidateClock {
    public long today() { return System.currentTimeMillis() / 86400000L; }
}
```

```java
// 反例：条件分支写死实现，等价于"依赖方向已定死"
public BigDecimal fee(Money amount) {
    if ("CN".equals(country)) { ... } else if ("US".equals(country)) { ... }
}
```

```java
// 正例：多态把"选哪个实现"变成运行时决定，新增国家不改旧代码（OCP 的技术基础）
public interface FeePolicy { BigDecimal apply(Money amount); }
public class Countries {
    private final Map<String, FeePolicy> policies = new HashMap<>();
    public void register(String code, FeePolicy p) { policies.put(code, p); }
}
```

**Ch6 的核心：可变性的隔离，而不是消灭。**

```java
// 反例：可变状态散落在整条调用链，测试必须按顺序跑
// （示意：任何一步都能被别的用例改脏）

// 正例方向：值对象不可变，可变点收口在一个明确的地方
public final class Money {
    private final long cents;
    public Money(long cents) { this.cents = cents; }
    public Money plus(Money other) { return new Money(this.cents + other.cents); }
}
```

> 注意 Ch6 与 Ch30 的呼应：**事件溯源把「当前状态」降级为「可重算的投影」**，这既是构架上的可选项，也是把数据库放回「实现细节」位置的技术手段之一。

## 近年研究与工业界开源实践（2015–2026）

趋势：**「OOP vs FP」之争结束，取而代之的是「可变性预算」的分配**；同时 Rust 的成功把「谁拥有可变性」变成编译器问题。本书 Ch5–6 提出的心理模型，正在被语言机制直接实现。

| 仓库 | star（2026-09-25 `gh api` 实测） | 说明 |

| `golang/go` | **138994** | Go 没有类与继承，隐式接口让「多态」更轻；但编译期没有不可变性支持 |

## 常见误区与本书需修正之处

| 误区 | 表现 | 修正 |
| --- | --- | --- |
| 🔧 把「必须全用封装、继承、多态」当教条 | 为用而用，为每个类造一个接口 | 只保留**要用多态反转依赖**的地方；其余直接具体类 |
| 认为「不用继承」就是现代做法 | 完全弃用继承后大量重复 | 组合优于继承 ≠ 不用继承；本书 Ch9 给出 LSP 的判定标准 |
| 把「不可变性」理解成「一切都不许变」 | 全函数式改写业务系统 | 采用 Ch6 的「隔离」策略：边界收口 + 值对象不可变 |
| 🔧 「函数式」被当作性能错误的选择 | 为纯函数牺牲数量级性能 | 先问热路径；在热路径上使用记忆化/不可变结构，在冷路径上保留可变 |
| 认为事件溯源可以无脑采用 | 事件回放慢、快照复杂、查询侧要另建读模型 | 仅在审计/追溯需求强的地方采用（Ch6 自己说的是「可选项」） |
| Ch5 的「多态」被当成银弹 | 所有分支都改写成策略类 | 分支本身不是问题，**硬编码的实现选择**才是问题 |
