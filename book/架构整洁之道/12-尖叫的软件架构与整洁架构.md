# 第 21 章 尖叫的软件架构 与 第 22 章 整洁架构

> **一句话**：如果软件在「尖叫」——目录一打开就大声说出它的业务用途，而不是大声宣告 `Spring`/`Hibernate`/`React`——那么它的架构就是干净的；而整洁架构的全部内容，就是把同心圆画对并让依赖方向无一例外地指向圆心。

## 核心精讲

**教学示意，不参与构建、不编译、不运行。**

**「尖叫」的对照**：同样是电商系统，两种目录写法传递的信息完全不同。

```text
# 不尖叫：看目录就知道技术栈，看不出业务
src/main/java/com/example/app/
    service/     UserService.java
    controller/  UserController.java
    repository/  UserRepository.java
    config/      ApplicationConfig.java
    entity/      UserEntity.java

# 尖叫（同一系统的另一种组织）：目录第一眼就是业务
src/main/java/com/example/
    order/       <- 订单：这个系统是在做订单
    catalog/     <- 商品
    checkout/
    support/     <- 技术支持层（Ch34 的按层/按功能/按组件封装）
```

**四层与依赖方向（本书 Ch22 的正式版本）**：

| 层 | 负责 | 是否认识框架 | 依赖方向 |
| --- | --- | --- | --- |
| Entities | 企业级业务规则 | 完全不认识 | 只向内（自身） |
| Use Cases | 应用级业务规则 | 不认识（只认识自己定义的抽象与 DTO） | 向内 |
| Interface Adapters | Controller/Presenter/Gateway/Mapper | 认识框架，但只做转换 | 向内（依赖用例接口） |
| Frameworks & Drivers | DB、Web、框架、Main | — | 被依赖（在外围） |

```java
// ---------- Entities（最内） ----------
public final class Money { private final long cents; /* 不变式与运算 */ }

// ---------- Use Cases（向内只依赖抽象） ----------
public interface PaymentGateway {                  // 归内层所有
    Result<PaymentId> charge(Money amount, AccountId id);
}

public final class ChargeOrder {
    private final PaymentGateway gateway;
    public ChargeOrder(PaymentGateway g) { this.gateway = g; }
    public ChargeResponse execute(ChargeRequest r) {
        Result<PaymentId> res = gateway.charge(r.amount(), r.accountId());
        return new ChargeResponse(res.value());
    }
}

// ---------- Interface Adapters（外层，做转换） ----------
@RestController                                   // 框架注解只出现在这里
final class ChargeController {
    private final ChargeOrder useCase;
    ChargeController(ChargeOrder u) { this.useCase = u; }
    @PostMapping("/charge") ChargeResponseDto post(@RequestBody ChargeDto dto) { ... }
}

// ---------- Frameworks & Drivers（最外，实现内层接口） ----------
final class StripeGateway implements PaymentGateway { /* HTTP + SDK 细节 */ }
```

**依赖关系规则的违反检查**（示意，不参与构建）：

```text
  违反 1：domain 包里出现了 @Entity / import org.springframework
  违反 2：use case 里 new 了具体 Repository 实现
  违反 3：entity 直接被 Controller 返回给 JSON 序列化
  违反 4：具体实现的包名比抽象更"内"（把实现放进了内核目录）
```

## 版本演进

| 时期 | 事件 | 与本章的关系 |
| --- | --- | --- |
| 2005–2006 | Cockburn，Hexagonal Architecture（Ports & Adapters） | 「内/外」语言的来源 |
| 2008 | Palermo，Onion Architecture | 同心圆的最早版本 |
| 2012 | 本书写作期，作者把自己 2002 年的实践重新组织 | 从「原则」走向「架构」 |
| 2017-09 | **Clean Architecture 出版**：依赖关系规则正式成文 | 本章即书名的落点 |
| 2017–2018 | Java 9 JPMS、Spring Boot 2 同期 | 语言级模块与框架级约定并行演进 |
| 2018-09 | 中译本：把 Clean Architecture 译作「整洁架构」 | 「整洁架构」成为中文社区常用词 |
| 2018–2021 | 「整洁架构很贵」的公开批评（样板代码、DTO 膨胀、单测成本） | 见 `13`、`15` 章与本章「常见误区」 |
| 2020 年代 | 变体大量出现：Lightweight/Explicit Architecture、Modular Monolith、Hexagonal+DDD 合流 | 都是对本章的微调：改动同心圆的位置，不改依赖方向 |
| 2020 年代 | 「模块化单体」复兴：用模块边界获得整洁架构的部分好处，不承担分布式成本 | 对本章代价的现实回应 |
| 2024–2026 | AI 辅助编程普及，架构规则进入 lint/生成模板 | 依赖方向再次被当作硬约束（CI 必过） |

## 近年研究与工业界开源实践（2015–2026）

趋势：**整洁架构的「四层」在 2020 年代被反复精简**——工业界普遍接受「依赖方向」，拒绝「固定四层」；同时，把四层约束变成 CI 必过规则的做法被广泛采用。

| 仓库 | star（2026-09-25 `gh api` 实测） | 说明 |
| --- | --- | --- |
| `TNG/ArchUnit` | **3843** | 校验依赖方向的主流工具，规则即「依赖关系规则」的代码化 |
| `sverweij/dependency-cruiser` | **7218** | 前端/Node 侧同样可校验同心圆边界 |
| `bazelbuild/bazel` | **25880** | 用构建图把「外层不得被内层引用」变成编译错误 |
| `spring-projects/spring-boot` | **81497** | 反过来最容易被直接抄成「注解到处飞的整洁架构」 |
| `golang/go` | **138994** | Go 下最简形态：`internal/` + `cmd/` 即可表达四层 |
| `rust-lang/rust` | **119150** | 模块私有性让最内层天然不暴露框架类型 |

## 常见误区与本书需修正之处

| 误区 | 表现 | 修正 |
| --- | --- | --- |
| 🔧 「整洁架构」被当成固定模板照抄 | 四层、六个包、DTO 全上，小项目也一堆样板 | 记住依赖方向即可；层数按项目规模增减 |
| 🔧 所有依赖都指向内部，导致最内圈负债 | 实体里为 `Clock`、`Logger` 建接口；内核包依赖一堆抽象 | 只对有真实替换动机的边界加抽象（Ch11 已提示） |
| 「框架是工具」被读成「完全不用框架」 | 拒绝 ORM、手写 SQL，自己造轮子 | 框架照用，但用它的方式是把框架放外层、按端口适配 |
| 把 Entities 理解成「DB 表对应的类」 | Entity 带 `@Entity` 注解，被 ORM 绑死 | Entities 是业务规则载体，映射可以放在外层 |
| 「尖叫」被当成目录整洁度的审美问题 | 追求目录漂亮，但依赖仍然横穿 | 尖叫的本质是**依赖方向正确**，目录只是可见的结果 |
| 以为四层与 DDD 的聚合边界冲突 | 实体被多个用例随意共享 | 用聚合收口不变式，用例通过聚合接口协作 |
| 认为只要分了层就自动可测 | 单测仍要起 Spring 上下文 | 可测性来自「内层不认识框架」，不是来自目录名字 |
| 🔧 对数据库与 Web 的「细节论」在真实项目里造成反复重造 | 每个项目重做一次「换 ORM」的痛 | 先用小范围试点验证可替换性，再决定是否投资抽象 |
