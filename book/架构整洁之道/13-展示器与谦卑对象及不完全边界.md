# 第 23 章 展示器和谦卑对象 与 第 24 章 不完全边界

> **一句话**：本章是全书的「省钱章」——谦卑对象说明「哪些代码必须 dumb 到可以自动测」，而不完全边界承认「把边界一次画完是贵的」，并给出只画一半的三种办法。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Ch23 谦卑对象模式 | 边界上有两种代码：难测的逻辑与 dumb 的搬运 | 把逻辑与搬运分开，让机器测前者 |
| Ch23 展示器与视图 | View 应该 dumb，Presenter 承载逻辑 | 逻辑放 Presenter 而不是模板/CSS |
| Ch23 测试与架构 | 端到端测试的规模是可闻见的架构代价 | 边界内少一个端到端测试，架构就赚一次 |
| Ch23 数据库网关 | ORM 是适配器，不是业务 | 业务只依赖网关接口 |
| Ch23 数据映射器 | 领域对象与存储模型的转换放在边界上 | 不要让 ORM 直接吃领域对象 |
| Ch23 服务监听器 | 入站消息也是一类适配器 | 与 Controller 同构 |
| Ch24 省掉最后一步 | 不必一次画到「无懈可击」 | 边界可以留缺口 |
| Ch24 单向边界 | 内层不必然要反向 tell 外层 | 单向调用降低复杂度 |
| Ch24 门户模式 | 用少量「门户类」做受控的跨边界 | 折中的经典解法 |
| Ch24 本章小结 | 边界是频谱，不是开关 | 按成本选择画多深 |

## 核心精讲

**教学示意，不参与构建、不编译、不运行。**

**谦卑对象（Humble Object）**：把「要推理的逻辑」和「不用推理的搬运」分开。

```java
// 反例：逻辑写在渲染代码里，测它必须起浏览器
// （示意：模板里塞满了条件判断）

// 正例方向：逻辑在 Presenter（可纯单测），视图只负责显示
public final class OrderPresenter {
    private final Clock clock;                       // 可注入 → 时间可测试
    public String present(OrderView v) {
        return v.buyer().name() + " 于 " + clock.today() + " 下单，共 "
                 + v.lines() + " 件";              // 纯逻辑，无 IO
    }
}
```

**数据库网关 + 数据映射器（Ch23 的架构含义）**：

```java
// 内层定义端口：返回领域对象，不返回行数据
public interface OrderGateway {
    Order find(OrderId id);
    void save(Order order);
}

// 外层实现：ORM 实体 -> 领域对象的映射只在这里
final class JpaOrderGateway implements OrderGateway {
    public Order find(OrderId id) {
        OrderRow row = em.find(OrderRow.class, id.value());
        return row == null ? null : Order.reconstitute(row.toSnapshot());   // 映射
    }
    public void save(Order order) { /* Row 组装与 persist */ }
}
```

**不完全边界的三种省法（Ch24）**：

| 做法 | 做法解释 | 适用 |
| --- | --- | --- |
| 省掉最后一步 | 先只做「依赖方向正确」，暂不做双向通知 | 起步阶段 |
| 单向边界 | 内层只调外层一次（如写事件），不做回调 | 不需要反向下达命令时 |
| 门户模式（Facade/Port） | 放几个大一点的门面类，集中跨边界调用 | 不想为每处调用都写接口 |

> 这是本书最实用的一章之一：**它给了「不做的正当理由」**。很多团队把 Ch22 的同心圆做成全双工、全 DTO、全事件，成本骤增；Ch24 明确说边界可以是频谱上的任何一点。

## 近年研究与工业界开源实践（2015–2026）

趋势：**测试成本成为边界设计的硬约束**。团队不再问「要不要端到端测试」，而是问「这条边界上放几个端到端测试最省钱」；同时，契约测试与测试替身让「外层可替换」这件事不必再用重集成来验证。

| 仓库 | star（2026-09-25 `gh api` 实测） | 说明 |
| --- | --- | --- |
| `pytest-dev/pytest` | **14534** | 分层测试与 fixture 是 Ch23「把逻辑挤到可测处」的工程化 |
| `TNG/ArchUnit` | **3843** | 校验「映射器只在外层」「网关接口在内层」 |
| `sverweij/dependency-cruiser` | **7218** | 前端可同样约束「视图不得直接引用数据层」（谦卑对象思想） |

## 常见误区与本书需修正之处

| 误区 | 表现 | 修正 |
| --- | --- | --- |
| 🔧 「所有依赖都指向内部」被推到极致 | 内核为 `Clock`、`Logger`、`Money` 全建接口，代码量翻倍 | 只对真会被替换的依赖做抽象（Ch11、Ch22 已提示） |
| 把 Presenter 写成第二个业务层 | Presenter 里又做校验又做计算 | Presenter 只做「领域数据 → 视图模型」的转换与格式化 |
| 认为端到端测试越少越好 | 完全删掉集成测试，只留单测 | 本书 Ch28 主张的是**合理的规模**，不是零 |
| 数据映射器被当成「无用的一层」 | 直接用 ORM 实体当领域对象 | 生命周期与不变式一旦要求纯净，映射器就值得 |
| 🔧 把「不完全边界」读成「不用完成」 | 半途而废的边界成为长期债 | 边界可以分阶段完成，但每阶段都必须是**可用且自洽**的 |
| 门户模式被滥用成万能胶水 | 所有跨边界都走几个大 Facade | 门面只承担受控的少数入口，不当成隐藏依赖的黑洞 |
| 服务监听器与控制器混为一谈 | 同一份业务代码被复制成两套入口 | 两者是同构的适配器，可共用用例层 |
| 「谦卑对象」被理解成「不要逻辑」 | 视图模板里塞满 `if` | 是把逻辑放到**可测**的地方，而不是删掉逻辑 |
