# 第 12 章 组件 与 第 13 章 组件聚合

> **一句话**：组件是「一起发布、一起版本化」的粒度，而聚合原则（REP/CCP/CRP）回答一个现实问题：**把哪些类放进同一个包，能让「被迫一起改」的次数最少**。

## 核心精讲

**教学示意，不参与构建、不编译、不运行。**

**三条聚合原则的取舍关系**（这张表是 Ch13 的核心，也是评审时的发言提纲）：

| 原则 | 想解决的问题 | 代价 |
| --- | --- | --- |
| REP 复用/发布等同 | 复用单元必须是版本单元 | 版本化成本高，小组件被迫冒烟测试 |
| CCP 共同闭包 | 同一原因的变更发生在同一处 | 包变大，跨模块的改动变多 |
| CRP 共同复用 | 复用时不会顺带拖进多余依赖 | 包被拆得很碎，发布次数暴涨 |

```text
            REP
             ^
            /|\
           / | \
          /  |  \        desired
         /   |   \      properties
        /    |    \
       /     |     \
      v      |      v
   CCP ------+------ CRP
   （任意两点之间都要做取舍）
```

**用「变更原因」而不是「技术分层」来划组件**（示意目录结构）：

```text
# 反例：按技术层次切组件（Controller/Service/Dao 三层，改一个需求要跨三处）
src/
  web/  OrderController.java
  service/ OrderService.java
  dao/ OrderDao.java

# 正例方向：按"变更原因"（业务能力）切组件，内部的层次由组件自己负责
src/
  order/          # 订单能力：需求一变，这里也变
    api/          # 对外接口（Ch11 的抽象）
    internal/     # 实现细节，不对外可见
  payment/
  shipping/
```

> 这一段是本书在中文社区争议最大的地方之一：**「按业务切包」与「按层次切包」谁是默认？」** 本书的答案是前者（组件内再分层），而 many 传统企业项目沿用后者。取舍的关键变量是「团队规模 × 变更频率」。

## 版本演进

| 时期 | 事件 | 与本章的关系 |
| --- | --- | --- |
| 1971 | Parnas，《On the Criteria To Be Used in Decomposing Systems into Modules》（CACM） | 模块化与信息隐藏的奠基，Ch12 历史叙事的终点 |
| 1990s | Punycom / DLL / JAR / WAR 的演进 | Ch12「组件发展史」的原始素材 |
| 2002 | P of EAA（Martin） | 组件被明确等同于「可发布的一层」 |
| 2003 | Evans，DDD | 限界上下文与「组件」在 2020 年代合流 |
| 2013 | Akroyd & Essembler 关于 Java 9 模块化的早期讨论 | 通向 JPMS |
| 2017 | 本书 Ch12–13：把 REP/CCP/CRP 与「组件边界」绑定 | 包组织第一次有了成文原则 |
| 2017–2018 | Java 9 的 JPMS 正式可用（`module-info.java`） | 语言级组件：验证「包可见性 ≠ 架构边界」 |
| 2018 | Go modules（`go.mod`） | 组件 = 一个仓库模块；`package` 只有目录级可见性 |
| 2019 | Rust modules + crates.io | `mod`/`pub(crate)` 提供真正私有性，组件粒度更细 |
| 2020 年代 | monorepo + Bazel 成为大厂标配 | 组件边界由构建系统强制执行；`visibility` 成为架构语言 |
| 2020 年代 | 「按功能封装」在前端（feature folder）与后端同时流行 | CCP 优先于 CRP 的现实例证 |

## 近年研究与工业界开源实践（2015–2026）

趋势：**「包」不再是唯一的组件**。语言模块（JPMS）、模块仓库（Go/Rust）、构建图（Bazel）、前端 feature folder 各自提供了不同强度的边界；同时 monorepo 把「一起发布」变成默认，CCP 的权重上升，CRP 的权重下降。

| 仓库 | star（2026-09-25 `gh api` 实测） | 说明 |
| --- | --- | --- |
| `bazelbuild/bazel` | **25880** | 用 `deps` + `visibility` 强制组件边界，把 Ch13 的取舍写成编译错误 |
| `golang/go` | **138994** | Go module 是发布单元；`package` 只在目录级可见，跨目录私有性需要 `internal/` 约定 |
| `rust-lang/rust` | **119150** | `mod` + `pub(crate)` + crate 提供语言级封装，天然支持「按功能封装」 |
| `TNG/ArchUnit` | **3843** | 在 JPMS 之前，用字节码规则补足 Java 包可见性的不足 |
| `sverweij/dependency-cruiser` | **7218** | JS/TS 用配置文件强制「功能目录之间不得互相依赖」 |

```text
# 用 Bazel 表达「order 组件不得依赖 payment 组件」的代码示意（教学示意，不参与构建）
# //src/order/BUILD
# java_library(
#     name = "order",
#     srcs = glob(["*.java"]),
#     deps = [":order_api"],          # 只允许依赖自己的 api，禁止 @//src/payment
#     visibility = ["//src:__subpackages__"],
# )
```

## 常见误区与本书需修正之处

| 误区 | 表现 | 修正 |
| --- | --- | --- |
| 🔧 把「所有依赖都指向内部」照搬为「所有类都在一个组件里」 | 组件内无边界，改一处动全量 | 组件内仍要有 api/internal 的边界，甚至双层组件 |
| 🔧 按技术层次切包，却期待获得组件的好处 | 三层一通到底，改一个需求跨三处 | 按变更原因（业务能力）切包，层次退到组件内部（`00` 的总览 3.3 节） |
| 追求「完全无环」而把包拆到几百个 | 发布数量爆炸、跨包调用横飞 | 环只在**组件之间**才痛；组件内部允许环（Ch14 会区分） |
| 为 CRP 反复拆分公共包 | `common-utils`、`core-common` 成为依赖黑洞 | CRP 只对真正共享的组件生效；其余走内部包 |
| 认为 REP 要求「每个组件都独立发布」 | 小组件被迫做全套版本管理 | 单体里 REP 可以退化为「共享包一旦发布，全量回归」 |
| 🔧 JPMS 的 `module-info` 被当成架构边界 | 模块图很美，反射与 classpath 混乱依旧 | 语言模块只解决可见性，不解决依赖方向，仍需 ArchUnit 之类的规则 |
