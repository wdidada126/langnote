# 第 1 章 设计与架构究竟是什么 与 第 2 章 两个价值维度

> **一句话**：本章是全书的「第一性原理」——架构不是把系统切成漂亮的盒子，而是**把「贵」的决定往后拖、往里放**，判据是「开发、部署、运行、维护」四个视角下的人力成本。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Ch1 目标是什么 | 「什么是架构」的四种问法：系统 vs 应用、软件架构 vs 架构 | 架构的定义被归约为「那些不易改变、改起来很贵的决定」 |
| Ch1 案例分析 | 用「工资系统」「库存系统」的例子说明「设计」与「架构」无法一刀切 | 有些决定是架构（跨组件、跨部署），有些只是设计（类内部） |
| Ch1 本章小结 | 架构 = 系统里最重要的部分 | 「最重要的」= 最贵的、最难改的、最难回滚的 |
| Ch2 行为价值 | 让系统「按需求跑起来」 | 如果速度是唯一目标，最优解经常是没有架构 |
| Ch2 架构价值 | 让系统「好改、好测、好部署」 | 架构的价值在于 **OES**：可维护性、可测试性、可部署性 |
| Ch2 哪个价值维度更重要 | 艾森豪威尔矩阵：重要 vs 紧急 | 「紧急但不重要」会挤掉「不紧急但重要」的架构工作 |
| Ch2 为好的软件架构而持续斗争 | 组织层面的对抗 | 架构工作必须被明确排进日程，否则永远输给 deadline |

## 核心精讲

**教学示意，不参与构建、不编译、不运行。**

全书的因果链可以写成一句可以放进 code review 检查表的话：

```text
   架构（依赖方向、边界）
        |
        v
   保持「可选项」（没做的决定）
        |
        v
   改起来便宜  ->  人力成本低  ->  满足需求（行为价值）
```

用一句代码层的判词来对照（Java 语法示意）：

```java
// 反例：行为价值至上，架构价值为零
// 业务逻辑直接长在框架与数据访问里，最"贵"的决定被最早做出
@Service                     // <- 框架决定
public class OrderService {
    @Autowired JdbcTemplate jdbc;   // <- 存储决定
    public void place(Order o) {
        jdbc.update("insert into orders ...");   // <- 业务规则 == SQL
    }
}
```

```java
// 正例方向：最贵（最难改）的决定向内，最容易替换的实现向外
// Entities：企业级业务规则，不认识任何框架
public class Order {
    private final Money total;
    public Order(Money total) { this.total = total; }
}

// Use Cases：应用级规则，只依赖抽象
public interface OrderRepository { void save(Order o); }
```

> 关键区别不是「分层好不好」，而是：**上面第一个例子里，「订单等于一段 SQL」这个决定被永久固化了**；第二个例子里，它只是一个可以在 `Main` 组件里换掉的实现。

**四个视角的成本表**（本书 Ch15 展开，Ch1 先埋下）：

| 视角 | 关注点 | 架构失误在这里的表现 |
| --- | --- | --- |
| 开发 Development | 多快能把新需求写完 | 改动跨 5 个包、single test 必须起整个容器 |
| 部署 Deployment | 发布一次要多久、会不会互相牵连 | 一个模块上线，另一个模块被迫回滚 |
| 运行 Operation | 稳态性能与可观测性 | 加一个字段要改表、要改 ORM 映射、要改缓存 key |
| 维护 Maintenance | 三年后还有没有人敢动 | 只有写它的人才敢改，文档等于作者回忆录 |

## 版本演进

| 时期 | 说法 | 变化 |
| --- | --- | --- |
| 2002（P of EAA） | 「架构」≈ 分层方案（三层、Domain Model、Data Mapper） | 讨论集中在**有哪些模式可选** |
| 2017（本书） | 架构 = **依赖方向** + **保持可选项** | 从「选模式」转向「选哪些决定不做」 |
| 2018 中译本 | 同上 | 中文读者最常引用的一句：软件架构是「shapes 系统生死攸关的部分」 |
| 2020 年代批评之一 | 「保持可选项」被读成「一切都要可替换」，于是 DTO、接口、工厂泛滥 | 修正方向：**只对会真换的东西做抽象**，其余直接写死 |
| 2020 年代批评之二 | AI 辅助编程让「骨架代码」生成成本骤降，但生成的骨架天然贴合框架与 ORM | 结论反而回归本书：架构决定必须由人先做，AI 只能填实现 |

## 近年研究与工业界开源实践（2015–2026）

趋势判断：**「架构」这个词在 2020 年代的工业界重心从「分层」滑向「可验证性」**——架构不再靠文档与评审维持，而是由构建系统、CI 规则、静态分析机器检查。本书 Ch1 所主张的「重要但不紧急」正在被工具化为「紧急且自动」。

| 仓库 | star（2026-09-25 `gh api` 实测） | 说明 |
| --- | --- | --- |
| `TNG/ArchUnit` | **3843** | 把 Ch1 的判据写成编译期规则；Maven/Gradle 插件让「架构价值」进入 CI |
| `sverweij/dependency-cruiser` | **7218** | 前端与 Node 侧的做法：用一个 JSON 规则文件描述「哪些目录不能依赖哪些目录」 |
| `bazelbuild/bazel` | **25880** | 用 `deps`/`visibility` 把 Ch1 的「贵决定」固化进构建图 |
| `spring-projects/spring-boot` | **81497** | Ch1 批评的典型场景：约定优于配置极速出活，但默认结构把业务塞进 `@Service` |

> 手工实验（**教学示意，不参与构建**）：把下面这条 ArchUnit 规则加到任何项目，Ch1 的「架构价值」立刻从口号变成红灯：
> `noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat().resideInAnyPackage("..web..", "..infra..")`

## 常见误区与本书需修正之处

| 误区 | 表现 | 修正 |
| --- | --- | --- |
| 🔧 「架构 = 所有依赖都指向内部」被当成铁律 | 连 `Log`、`Money`、`Result` 都要建内部接口 | 只对**真的会换**的边界做抽象；抽象数量应与「预期变更次数」成正比 |
| 把 Ch1 的定义读成「架构就是拓扑图」 | 画的图很漂亮，改代码照样跨层 | 用可执行的规则（ArchUnit / dependency-cruiser）替代图 |
| 「行为价值优先」被当成不做架构的借口 | 原型阶段直接写死，两年后无法维护 | 用艾森豪威尔矩阵承认张力：不是不做架构，而是**把架构决定排进「重要不紧急」** |
| 认为 Ch2 的 OES 指标可以量化 | 试图给出「可维护性 = X」的公式 | OES 是**方向性的**判据（好不好测、好不好部署），不是精确指标 |
| 🔧 「重要但不紧急」在真实组织里永远排不进日程 | 直到第一次线上事故 | 用 CI 里的架构规则把架构约束从「人的自律」变成「机器强制」 |
| 用 Ch1 的「系统生死攸关部分」给过度设计背书 | 三个人的项目上四层 + 事件总线 | 先问：这个系统三年后还会存在吗？会换 ORM 吗？ |
