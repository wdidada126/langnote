# 第 27 章 服务：宏观与微观、第 29–34 章（嵌入式、实现细节、案例分析、拾遗）

> **一句话**：本册的最后一半在讲同一件事的两面——**服务是一种边界，而数据库、Web、框架都只是「细节」**；真正难的是把这两句话用在有真实数据、真实并发、真实迁移压力的系统里。

## 核心精讲

**教学示意，不参与构建、不编译、不运行。**

**「横跨型变更」的成本示意（Ch27 的核心论断）**：

```text
   需求：给订单加一个优惠券字段

   单体（含边界）：1 个包内改 3 处，一次发布
   微服务（边界错）：订单、支付、库存、风控、通知 5 个服务各改一次
                    + 5 次发布 + 跨服务数据一致性 + 回归成本
   -> 结论：服务数量不是越多越好；边界应与「一个团队能独立交付」对齐
```

**框架是「单向婚姻」（Ch32）的态度表**：

| 框架给你的 | 框架拿走的 |
| --- | --- |
| 开发速度、约定、生态 | 部分结构决策权、升级自由度、某些替换可能 |
| 校验与自动配置 | 测试速度（若测试需要启容器） |
| 成熟的最佳实践 | 与框架版本绑定的长期成本 |

**三种封装方式（Ch34 收尾清单）**：

| 方式 | 划分依据 | 优点 | 适用 |
| --- | --- | --- | --- |
| 按层封装 | 技术层次（ui/application/domain/infra） | 传统、直观 | 小型系统、团队分层 |
| 按功能封装 | 业务能力（order/checkout） | 变更集中、团队自治 | 主流中大型系统 |
| 按组件封装 | 完整业务组件（含自己的 api + 实现） | 边界最硬 | 需强隔离的平台/插件化系统 |

**「具体实现细节中的陷阱」（Ch34）的几条**（示意）：

```text
   1. 在领域层写 SQL / 加 @Transactional
   2. 让领域对象直接实现框架接口（implements Serializable / org.hibernate.*）
   3. 把 DDL 变更当成「小改动」（跨服务 schema 耦合）
   4. 用全局工具类（util）当成共享层
   5. 在业务代码里 new 出框架对象（DateTimeFormatter、ObjectMapper）
```

## 近年研究与工业界开源实践（2015–2026）

趋势：**服务边界的「强度」重新被定价**。微服务退潮、模块化单体回归，同时事件驱动与 CQRS 成为标配；而本书 Ch30–32 的「细节论」在数据与框架层面正在被工具化——迁移工具、schema 演进、ORM 抽象让「可替换」成为现实任务，而不是口头承诺。

| 仓库 | star（2026-09-25 `gh api` 实测） | 说明 |
| --- | --- | --- |
| `spring-projects/spring-framework` | **60260** | Ch32 的对象：框架决定结构；也是「单向婚姻」的最大实例 |

## 常见误区与本书需修正之处

| 误区 | 表现 | 修正 |
| --- | --- | --- |
| 🔧 把「数据库只是实现细节」当免责声明 | 团队从不做 schema 演进设计，换数据库从未试点 | 「细节」指的是**代码依赖方向**，不是「可以不做数据设计」；迁移成本才是真实约束 |
| 🔧 把「Web 是实现细节」理解为「不用管 Web」 | 前端与协议决策失控扩散 | 边界仍要设：协议契约、前端团队自治、BFF 都是需要设计的决定 |
| 🔧 每个限界上下文都切一个服务 | 分布式单体、跨服务事务、需求横跨五项 | 从弱边界开始：模块化单体 + 事件，必要时才升服务（Ch27「运送猫咪的难题」） |
| 「服务边界解决了扩展问题」 | 服务切分基于数据表而非业务能力 | 按业务能力与团队边界切（Ch27「对象化是救星」） |
| 框架只能「单向婚姻」被理解成「不用框架」 | 拒绝 Spring/React，自造基础设施 | 用框架，但把框架放在外层、结构决策留在自己手里（Ch32 给了具体方案） |
| Ch29 嵌入式只讲硬件瓶颈 | 只关心「跑得起来」 | 也应该关心：交付节奏、OTA、设备端测试策略 |
| 把 Ch34 的封装清单当可选项随便挑 | 三种混用，包结构混乱 | 一种为主、其余为辅；同一系统里至少统一一种 |
| 🔧 「具体实现细节中的陷阱」在 AI 辅助编程下放大 | 生成代码默认贴合框架与 ORM，陷阱自动产生 | 用生成模板与 CI 架构规则约束（见 `00` 第 6 节工具链） |
| 认为单体与微服务在架构上等价 | 只改部署形态 | 差异在一致性、发布协调、运维复杂度（见 `book/设计数据密集型应用.md`） |
