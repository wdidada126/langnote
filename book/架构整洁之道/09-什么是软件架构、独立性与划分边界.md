# 第 15–18 章 什么是软件架构、独立性与划分边界

> **一句话**：架构的定义被压缩成一句可操作的话——**最大化「还没做的决定」的数量**；而独立性的四个维度（开发、部署、运行、保持选项）就是这句话的检查表，边界则是把这句话翻译成代码的那支笔。

## 核心精讲

**教学示意，不参与构建、不编译、不运行。**

### 一、「保持可选项」的可视化（Ch15）

架构决策往往是树状分叉，好的架构让你在分叉口把选择权留久一点：

```text
   需求 A（今天必做）
        |
        +-- 决定 1： ORM 用 Hibernate        <- 贵、难改、应尽早但可选
        +-- 决定 2： REST over HTTP          <- 贵、难改、可推迟
        +-- 决定 3： 单体部署                 <- 贵、难改、可推迟
        +-- 决定 4： 类名叫 Order            <- 便宜、立刻做

   好的架构：让 1/2/3 在 Ch26 的 Main 组件里才被拍板，业务代码不知道
   差的架构：1/2/3 早在 @Entity 与 @RestController 注解里就已经拍死了
```

**四个独立性的检查表**（可直接用于评审）：

| 维度 | 问自己 | 架构失误的信号 |
| --- | --- | --- |
| 开发独立性 | 一个新需求需要几个人理解几层代码？ | 改一个字段名要打开 6 个文件 |
| 部署独立性 | 我的改动要不要和别人一起发布？ | 一个模块上线，另一个模块被迫回滚 |
| 运行独立性 | 我能不能换掉实现而不影响别的服务？ | 换 ORM 等于重写业务层 |
| 保持可选项 | 我现在做的决定，三年后还能改吗？ | 决定被写进了框架注解/DDL/协议里 |

### 二、边界的三个强度等级（Ch18）

| 强度 | 形态 | 例子 | 通信代价 | 适用于 |
| --- | --- | --- | --- | --- |
| 弱 | 同一个包/模块内的目录 | `order/` 与 `payment/` 两个包 | 无（函数调用） | 大多数系统起步阶段 |
| 中 | 本地进程 / 独立部署单元（jar、容器） | 支付服务独立部署 | 序列化 + 网络 | 明确会拆散的部分 |
| 强 | 远程服务 / 消息队列 | 订单 → 库存（gRPC/Kafka） | 网络 + 一致性风险 | 需要独立组织与发布的 |

### 三、跨边界的数据形状（Ch17 + Ch20 呼应）

```java
// 反例：领域对象直接抛到边界外，它的序列化策略决定了你的协议
public Order createOrder(Order o) { ... }         // 领域类型泄漏到 Controller

// 正例方向：边界两侧各用自己的数据结构
public record CreateOrderRequest(String sku, int qty) {}                 // 外层（HTTP JSON）
public record CreateOrderResponse(UUID orderId, BigDecimal total) {}
```

```java
// UseCase 的输入输出：只依赖自己定义的 DTO（示意，Ch20 展开）
public interface CreateOrderUseCase {
    CreateOrderResponse execute(CreateOrderRequest request);
}
```

### 四、插件式架构的最小骨架（Ch17）

```text
   core/          <- 内核：业务规则 + 用例，不含任何框架
   plugins/
     db/          <- 数据库是插件
     web/         <- Web 框架是插件
     auth/        <- 鉴权是插件
   Main           <- 装配：决定装哪些插件（Ch26）
```

> 一个容易被忽略的约束：**边界两侧的「语言」必须一致，否则边界会退化成序列化层**。领域对象里加了 `private LocalDateTime createdAt`，边界就被时间格式绑架了。

## 常见误区与本书需修正之处

| 误区 | 表现 | 修正 |
| --- | --- | --- |
| 🔧 把「保持可选项」当成「什么都别决定」 | 两个月的项目不做任何命名决策 | 便宜的决定立刻做；贵的决定才需要「保持选项」 |
| 🔧 「单体没有独立性」被当成定论 | 单体被制度性歧视 | 四个维度可以分别满足；单体缺失的通常是**部署/组织**独立性 |
| 把「重复」一律当作坏味道 | 为避免共享而复制代码却被评审驳回 | 当重复换来了解耦与并行开发时，重复是划算的 |
| 🔧 把「边界」一次性画满 | 一开始就分出十几个服务/模块 | 本书自己就说不全画：先内核 + 必要的插件边界 |
| 🔧 服务边界与组件边界被默认等同 | 一个限界上下文被切成 5 个微服务 | 只有**组织边界**才值得升级为服务边界 |
| 🔧 「数据库与 Web 是细节」在真实项目里反复翻车 | 团队每换一次 ORM 就重写一遍业务 | 细节论要配上「明确的替换预算」：小范围试点再全面替换 |
| 认为「插件式架构」必须有插件系统 | 自己造一套 DI 容器与插件协议 | 90% 的情况只需要一个 `Main` 装配点 + 接口 |
| 跨边界直接传递领域对象 | 协议字段随领域对象演进、双方强耦合 | 边界两侧各用 DTO（Ch20 的请求/响应模型） |
| 把线程/协程当成边界 | 用线程池划分模块 | Ch18 明确：线程是内部实现细节，不是边界 |
| 边界画在「技术层次」上 | web/service/dao 三层贯通 | 按业务能力画，层次退到组件内部（`07-组件与组件聚合.md`） |
