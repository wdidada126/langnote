## 核心精讲

### 2.1 分层与「透明通信的代价」
原书用 OSI 与 TCP/IP 两套分层讲封装：应用想发一句话，经过表示/会话/传输/网络/链路层层加头。
Tanenbaum 强调的是分层的**管理收益与性能损失**这对矛盾——这个矛盾在 2026 年以
「内核旁路（RDMA、DPDK、eBPF）」的形式复活：层次太多时，人们会把层压扁。

原书对两套分层模型的对照可压缩成一张表：

| OSI 层 | TCP/IP 对应 | 原书关注点 | 2026 年状态 |
| --- | --- | --- | --- |
| 1–2 物理/链路 | 链路层 | Ethernet/令牌环之争 | Ethernet 完胜；令牌环只剩考题 |
| 3 网络 | 网络层（IP） | ATM vs IP 之争 🔧 | IP 完胜；QUIC 在其上重构传输 |
| 4 传输 | TCP/UDP | 可靠传输、流控 | TCP/UDP 仍是底座；QUIC 用户态化 |
| 5–7 会话/表示/应用 | 应用层 | XDR/ASN.1 编码 🔧 | Protobuf/JSON/FlatBuffers |

**分层史的教训**：原书 2.2 节花整节讲 ATM，本目录只留一句结论——
技术上精致（定长信元、面向连接、QoS）、工程上失败的范式案例。
「最先进的方案赢了还是最兼容的方案赢了」，ATM 用整个身家给出答案。

### 2.3 客户—服务器模式
- **连接导向还是无连接**：请求/应答天然成对，无连接（UDP 式）即可支撑多数 LAN 场景；
  原书还讨论了给请求/应答包设计协议字段（程序号、版本号、过程号）——这正是 Sun RPC 的包格式。
- **寻址**：广播定位（LAN 内）、定时器+缓存、以及目录服务三种。
- **阻塞性**：同步/异步、发送阻塞/接收阻塞的组合矩阵；原书结论是大多数系统用阻塞式 send/recv。

「客户—服务器模式」在原书里还有一个常被考的细节：**服务器有状态还是无状态**。

| 属性 | 无状态服务器 | 有状态服务器 |
| --- | --- | --- |
| 故障恢复 | 客户端重发即可 | 需恢复会话状态 |
| 请求自包含 | 是（每请求带全信息） | 否（依赖服务器记忆） |
| 性能 | 重复传递上下文 | 可缓存会话 |
| 典型 | 早期 NFS 设想、HTTP | DCE、数据库连接 |

NFS 的故事（无状态设想被回调缓存等需求拖成「事实上有状态」，直到 NFSv4 承认这一点）
是 [06-一致性复制与容错.md](06-一致性复制与容错.md) 第 5 节的好例子；HTTP/1.0 无连接、
HTTP/1.1 持久连接、HTTP/2 多路复用的演化，则是同一权衡在 Web 协议上的重演。

### 2.4 远程过程调用（全章核心）
把「调用远程函数」做得像本地函数一样，是本书乃至整个 1990 年代分布式系统的核心叙事。
五个组件：客户端过程、客户端 stub、RPC 运行时、服务器 stub、服务器过程。

1. 客户端调用 stub → stub **封送（marshal）**参数。
2. 运行时把消息发给服务器 stub → 解封 → 真正调用服务器过程 → 结果原路返回。

三个必须诚实面对的难点（原书都讲了）：

- **参数传递**：指针怎么办？拷贝-恢复、仅支持值传递、或引用参数一律不准（Sun RPC 的选择）。
- **异构编码**：不同字节序/字长 → 外部数据表示 XDR（Sun RPC）或 ASN.1（OSI/DCE）。
- **失败语义**：本地调用「不执行/执行一次」二选一，RPC 却可能出现**执行了但结果丢失**——
  于是有至少一次（at-least-once，要求操作幂等）、至多一次（at-most-once，可能拒绝重发）、
  恰好一次（无法完美实现，只能组合出近似）。

RPC 与本地调用还有两个常被忽视的差别，原书均有交代：

- **透明性的边界**：stub 能隐藏「参数怎么走」，藏不住「延迟多大、会否超时」。
  设计接口时就应该意识到远程调用是**贵**的——粗粒度接口（一次传一批）优于细粒度接口
  （逐字段调用）。这条对 2026 年写 gRPC/REST 接口同样有效。
- **绑定（binding）问题**：客户端第一次调用前，怎么知道「READ_FILE_PROG 这个程序号
  在哪台主机的哪个端口」？答案是 port mapper / 目录服务——与
  [04-命名.md](04-命名.md) 的定位四法直接接轨。

```c
/* 教学示意，不参与构建：Sun RPC 风格的接口定义（.x 文件语法）。
   体现「接口先于实现」与 XDR 编码的约定，本目录不编译任何 RPC。 */

program READ_FILE_PROG {
    version READ_FILE_VERS {
        string READ(string) = 1;    /* 过程号 = 1，版本号防漂移 */
    }
} = 999001;                          /* 程序号：服务器上定位到哪个服务 */
```

### 2.5 组通信
一对多通信是客户—服务器模式的自然推广：**闭组**（只有成员可发）与**开组**；
**可靠组播**要保证所有成员都收到；**原子组播**进一步要求要么全体按序收到、要么全不收——
这是 [06-一致性复制与容错.md](06-一致性复制与容错.md) 复制协议的通信基石。

组通信的「序」有强弱之分，原书的讨论可以整理成一张序谱：

| 序 | 保证 | 典型实现思路 |
| --- | --- | --- |
| FIFO 序 | 同一发送者的消息按发送序到达 | 发送方带序号 |
| 因果序 | 因果相关的消息全体同序 | 消息携带依赖向量 |
| 全序（完全有序） | 所有成员看到相同的总序 | 定序者（sequencer）或共识 |
| 原子组播 = 可靠 + 全序 | 要么全体按同序收到、要么全不 | ISIS 虚拟同步 |

这张谱在 2026 年有一个几乎逐字对应的工程版本：Kafka 的分区有序（FIFO）、
消息携带因果引用、以及「要不要引入定序者」的取舍讨论——概念没换名字，换了实现载体。

组通信还有一个原书点到、2026 年极其重要的概念：**组成员管理（group membership）**。
「组里现在有谁」本身就是分布式状态，成员视图不一致会导致严重的系统级 bug：
一台机器以为自己已退出组、别人还在给它发消息——历史上 ISIS/Amoeba/Transis
都在这里摔过跤。2026 年的答案是把「成员视图」交给共识系统（etcd 里的 lease、
K8s 节点心跳），**不再让通信协议自己猜成员**——这是本章思想被吸收得最彻底的一处。

## 版本演进

| 时期 | 通信主流 | 关键变化 |
| --- | --- | --- |
| 1985–1995（原书） | Sun RPC、XDR、OSI/ATM 讨论 | RPC 把过程调用抽象搬上网；ATM 曾被寄予 LAN/ WAN 统一厚望 |
| 1995–2005 | CORBA/DCOM/Java RMI（对象中间件）、SOAP/XML | 编码从二进制 XDR 走向文本化；接口定义语言(IDL) 泛滥 |
| 2005–2015 | Thrift/Protobuf + HTTP、消息队列（RabbitMQ/Kafka） | RPC 与消息分离：请求应答归 RPC，事件流归队列 |
| 2015–2026 | gRPC（HTTP/2 + Protobuf）、QUIC、消息总线云服务 | 多路复用与流控解决队头阻塞；幂等重试成为库默认能力 |

**一条贯穿的暗线：编码格式的「二进制 ⇄ 文本」钟摆。**
XDR（二进制、紧凑）→ CORBA CDR（二进制、复杂）→ XML/SOAP（文本、啰嗦）→
JSON（文本、简单）→ Protobuf/FlatBuffers（二进制、带回紧凑与 schema）。
每换一次方向，都会出现「新格式解决了旧格式的问题、又引入了新问题」的循环——
读原书 2.4 节的 XDR 时记住：**它不是过时的细节，而是钟摆的第一个完整摆幅**。

## 近年研究与工业界开源实践（2015–2026）

- **gRPC 一统 RPC 江山**：`grpc/grpc`（45342★，2026-09-26 实测）复刻了原书全套概念——
  Protobuf 扮演 XDR/IDL，HTTP/2 扮演传输层，拦截器链扮演 stub 生成器的运行时部分；
  原书「失败语义」讨论变成了 gRPC 重试策略 + 幂等令牌（idempotency key）的工程标配。
- **消息队列的组通信遗产**：Kafka 的消费者组与 ISR 复制、NATS 的 at-least-once 语义，
  都是 2.5 节可靠组播思想的商品化形态；「原子组播」则由共识系统（etcd，52310★）替代——
  大家发现与其做组播协议，不如直接做共识。
- **内核旁路与分层压缩**：RDMA、QUIC（把传输+安全+拥塞控制合一）、用户态网络栈，
  逐一回应 2.1 节「分层开销」问题；数据中心 RPC 延迟已从毫秒级进入微秒级。
- **Cap'n Proto / FlatBuffers** 一类零拷贝编码（Cap'n Proto 主仓不在 GitHub 本次核验范围，star 未核验）
  把「封送」这个 1984 年的概念又优化了一轮。
- **可观测性入栈**：分布式追踪（OpenTelemetry 生态）把「一次 RPC 经过了谁、每跳多慢」
  变成一等公民数据——原书时代的 RPC 调试靠打印，今天的调用链是生产系统标配；
  这也是「透明通信」叙事 2026 年的补集：通信透明了，**可观测性必须不透明**。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「RPC 可以完全像本地调用」 | 失败语义永远不同：超时的调用可能已在远端执行；必须设计幂等性 |
| 2 | 「封送只是把结构体拷进缓冲区」 | 异构环境还有字节序、对齐、字符串编码（XDR/Protobuf 的存在意义） |
| 3 | 「组播=广播给所有人」 | 可靠/原子组播有严格的全体一致要求，普通多播不保证 |
| 4 | 🔧 **2.2 ATM 网络整节作废** | 2026 年读法：把 ATM 当「面向连接网络为何输给 IP」的案例研究即可 |
| 5 | 🔧 **XDR/ASN.1 已边缘化** | 现在的主流是 Protobuf/FlatBuffers/JSON Schema；但要理解它们解决的问题与 XDR 完全同源 |
| 6 | 🔧 **「恰好一次不可能」的表述要现代化** | 现代答案是「恰好一次效果」：幂等写 + 事务性确认（Kafka 事务、云厂商 idempotency API） |
| 7 | 「阻塞性只是 API 细节」 | 阻塞模型决定服务器并发结构：阻塞 RPC → 每连接一线程；非阻塞/异步 → 事件循环，见 [03-进程与线程.md](03-进程与线程.md) 4.1 |
| 8 | 「面向连接比无连接高级」 | 请求/应答语义用无连接（或轻连接）即可；连接的成本在握手与状态，HTTP/2、QUIC 的取舍都在这条线上 |
