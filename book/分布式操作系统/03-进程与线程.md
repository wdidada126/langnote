## 核心精讲

### 4.1 线程（原书讲得极详细的一节）
- **动机**：RPC 客户端在等待应答时还能发第二个请求；RPC 服务器能用多线程并行服务多个客户——
  Tanenbaum 用「三客户并发 RPC」图说明线程在分布式场景的必要性。
- **用户级线程 vs 内核级线程**：用户级快（切换不进内核）、但一个阻塞系统调用拖死整包；
  内核级切换贵、却能用多核。原书给出的**调度器激活（scheduler activations）**方案
  （upcall 通知用户态）是 1991 年的经典设计。
- **线程包要素**：创建/销毁/等待/yield；原书给了一个用定时信号驱动用户级线程包的示例。

用户级与内核级线程的取舍，可以整理成一张对读表（读 4.1 时建议左右栏对照记忆）：

| 维度 | 用户级线程 | 内核级线程 |
| --- | --- | --- |
| 切换成本 | 几条指令，不进内核 | 陷入内核，保存/恢复全套上下文 |
| 阻塞系统调用 | 整个进程（该包内全部线程）被拖住 | 只阻塞该线程 |
| 多核利用 | 困难（一个内核调度单位） | 天然并行 |
| 实现方 | 库（runtime） | 内核 |
| 调度权 | 用户态自定（快但可能饿死内核资源） | 内核统一（公平但切换贵） |
| 2026 年形态 | Go/Java 虚拟线程（有内核协作改良） | pthreads（1:1） |

原书成书时 N:1（纯用户级）还是主流；2026 年的主流是 1:1（服务器 Java/C++）与
改良 M:N（协程 runtime）并存——scheduler activations 的「内核通知用户态」思想
正是改良 M:N 的理论底座。

```c
/* 教学示意，不参与构建：分布式 RPC 服务器的线程化骨架（概念版）。
   重点不是这段代码，而是「每个请求一个线程」与「线程池」的取舍，
   它在 2026 年演变为每连接一个协程（Go/async runtime）。 */

void *worker(void *arg) {
    for (;;) {
        Request *req = queue_pop();      /* 从共享队列取请求 */
        Response *rsp = remote_call(req); /* 出网等待期间线程让出 */
        deliver(rsp);
    }
}

int main(void) {
    for (int i = 0; i < POOL_SIZE; i++)
        thread_create(worker, NULL);     /* 线程池：预先创建，避免反复 fork */
    accept_loop();
}
```

### 4.2 系统模型：三种资源观
| 模型 | 设想 | 1995 年评价 | 2026 年回声 |
| --- | --- | --- | --- |
| 工作站模型 | 每人一台空闲时段可借用的工作站 | 主流 | 空闲桌面算力如今意义有限，但「把任务调度到空闲节点」思想延续在集群调度 |
| 处理器池模型 | 集中一柜子计算服务器，用户终端只做交互 | Tanenbaum 倾向于此 | **Kubernetes 就是处理器池模型的完全体**：Pod 即池中租借的算力单元 |
| 混合模型 | 个人机 + 池 | 折中 | 实际云厂商形态：个人开发机/Notebook + 弹性算力池 |

### 4.3 处理机分配（本章与今日联系最紧的一节）
- 前提概念：**负载图**（系统平均负载）、**迁移性**（可迁移/不可迁移计算）、
  **发送 vs 接收**（有人闲得发慌主动出手 vs 有人忙不过来求助）。
- 四类算法（原书命名）：图论确定性算法、集中式启发式、层次式算法、投标（bid）算法。
- 通病：**不稳定性**——互相甩任务的振荡；以及决策所需的集中式状态本身是单点。

四类算法在原书基础上可补一句现代判读：

| 原书算法 | 思路 | 2026 年判读 |
| --- | --- | --- |
| 图论确定性算法 | 把任务集建模成图，最小化通信/执行代价 | 静态假设太强；对应今天的离线装箱/排程问题 |
| 集中式启发式 | 中央节点收集负载，轮流分配 | 与 K8s 单调度器架构惊人相似（但 K8s 靠乐观并发与失败重试解决单点） |
| 层次式 | 分层汇总负载、逐层决策 | 对应 multi-cluster / 分级调度（K8s Federation、YARN 层次队列） |
| 投标算法 | 各节点对任务报价，价低者得 | 市场化调度：后来的 Spot 定价、深度学习集群竞价实验 |

四类算法共享的失败模式也值得记录：**信息越新鲜，决策越振荡**。
原书指出的不稳定性（两台中等负载机器互相甩任务）在 2026 年的自动扩缩容里
原样重演（HPA 抖动、缩容风暴），工程解也同构——加滞后（hysteresis）、
加冷却期、加最小变更步长。

### 4.4 调度中的工程细节
原书列举的启发式：选最闲的接收者、负载低于阈值才发送、迁移「新创建的任务」而非运行中的
（迁移成本与缓存效应——这个洞察在 2026 年的调度器亲和性、Pod anti-affinity 里一模一样）。

原书还区分了**发送者主动（sender-initiated）**与**接收者主动（receiver-initiated）**
两类策略，这组对照在 2026 年有精确的对应物：

| 策略 | 原书描述 | 现代对应 |
| --- | --- | --- |
| 发送者主动 | 忙节点主动外移任务 | 抢占式调度、Spot 抢占、驱逐（eviction） |
| 接收者主动 | 闲节点拉取任务 | work stealing（Go scheduler、ForkJoinPool）、pull 模式消息队列 |
| 对称 | 双方都动 | 混合负载下最稳健，但参数最难调 |

### 4.1 补充：线程与 RPC 的组合模式（原书的经典配图逻辑）
原书用三张图讲「线程如何救活分布式服务」，其逻辑可以文字化为三种服务器形态：

| 服务器形态 | 结构 | 问题/收益 |
| --- | --- | --- |
| 单线程 RPC 服务器 | 一次只服务一个请求 | 服务器 CPU 大量空转等网络 |
| 每请求一线程 | 请求来即建线程 | 并发高，但线程爆炸（内存/切换） |
| 线程池 + 队列 | 固定线程消费请求队列 | 1995 年的最优解，也是 2026 年协程调度器的骨架 |

三种形态的演化线一直延伸到 [09-从分布式OS到现代云OS.md](09-从分布式OS到现代云OS.md)
的 Serverless：「请求本身获得执行资源」——相当于把「每请求一线程」推进到
「每请求一台（虚拟）机器」，粒度变了，结构逻辑没变。

## 版本演进

| 时期 | 并发/调度形态 | 关键变化 |
| --- | --- | --- |
| 1985–1995（原书） | 用户级线程包 + condor 类空闲工作站借用 | N:1 与 N:M 线程争论；处理器分配靠启发式 |
| 1995–2005 | 内核级 1:1 线程普及（Linux pthreads）、集群批处理（LSF/PBS） | 多核未至，服务器并发靠进程池 |
| 2005–2015 | 多核爆发；C10K → 事件循环/协程；虚拟机资源调度 | 调度问题搬进 hypervisor 与数据中心 OS |
| 2015–2026 | 容器 + 编排调度器（K8s/Nomad）；Go/async 轻量并发 | 处理器池模型彻底胜利：请求算力如同原书「租一台池中机器」 |

**版本演进的另一条暗线：进程定义的变化。**
| 时期 | 「进程」包含什么 | 备注 |
| --- | --- | --- |
| 1995（原书） | 地址空间 + 线程 + 资源句柄 | Mach 的任务/线程切分 |
| 2013（Docker 元年） | 进程 + 镜像 + cgroup 限额 + 命名空间隔离 | 容器把「资源边界」写进了进程定义 |
| 2015–2026 | Pod（多容器共享网络/存储的调度单位） | 调度单位从进程升级为「进程组」 |

读原书 4.2 节「系统模型」时用这条暗线对照：Amoeba 的进程描述符 ≈ 镜像 + PodSpec 的原型。

## 近年研究与工业界开源实践（2015–2026）

- **Kubernetes 调度器 = 4.3 节的产业化**：`kubernetes/kubernetes`（127994★，2026-09-26 实测）的
  调度循环（过滤 + 打分 + 绑定）就是「接收启发式 + 打分」的正规化；Bin packing、拓扑扩散/聚合
  对应原书「最闲接收者」与「就近迁移」的启发式。另一派 `hashicorp/nomad`（16974★）用同样的
  问题域证明 4.3 节没有过时，只是换了 API。
- **协程复兴**：Go runtime（GMP 模型）与 Java 虚拟线程（Loom）把「用户级线程 + 内核协作」重新做对——
  本质是 scheduler activations 的改良版；「每请求一线程」在 2026 年以每请求一协程回归。
- **调度器激活的现代回声**：io_uring、epoll 事件模型 + async runtime，是「内核通知用户态」思想的
  连续演化；原书 4.1 的争论（线程 vs 事件）如今是「协程 vs 事件回调」之争。
- **实时分布式**：车规级实时通信（TSN）与 ROS 2 的 executor 调度，是 4.6 节在机器人/汽车场景的落地。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「用户级线程必然比内核级快」 | 阻塞系统调用会让整包线程卡死；现代方案是 1:1 或改良的 M:N（协程） |
| 2 | 「负载迁移总是划算」 | 迁移运行中任务有缓存/状态成本；原书即建议迁移新任务——协程调度同理（避免频繁抢占） |
| 3 | 「处理机分配是 OS 内核的事」 | 2026 年它在编排层（K8s）与用户态 runtime 里；内核只管单机 |
| 4 | 🔧 **Condor 类空闲工作站借用已式微** | 同类思想活在抢占式 Spot 实例/竞价算力与 HPC 批调度里 |
| 5 | 🔧 **线程包 API 过时** | pthreads 仍是底座，但业务层普遍写协程/异步；读 4.1 时应对照 Go runtime 模型 |
| 6 | 🔧 **处理器分配算法可忽略细节** | 图论/投标算法可作为思想史阅读；2026 年面试与工程主流是 K8s 调度框架与 bin-packing 策略 |
| 7 | 「实时系统就是快」 | 4.6 节的核心是**可预测/有界**而非快；错过截止期等于错的系统里，「平均快」毫无意义 |
| 8 | 「容错在 4.5 一节讲完了」 | 4.5 只是引入故障分类与冗余概念；完整协议（复制、提交、协定）在 [06-一致性复制与容错.md](06-一致性复制与容错.md) |
