## 核心精讲

### 1.1 定义与「单一系统映像」
Tanenbaum 的经典定义：分布式系统是**一组独立的计算机，但对用户来说就像一台单一的连贯计算机**。
拆开是两半：机器独立（自治、各自可能崩溃）+ 呈现统一（用户不用知道哪些东西在哪台机器上）。
后半句即「单一系统映像（SSI）」，是 1990 年代 Amoeba 一类系统毕生追求、而 2026 年由容器编排以另一种方式近似实现的目标（见 [09-从分布式OS到现代云OS.md](09-从分布式OS到现代云OS.md)）。

### 1.2 四个目标
- **资源可访问性**：打印机、文件、计算能力可以被网络内任何节点使用。
- **透明性**：访问/位置/迁移/复制/并发/故障六个维度上，「分布」对用户不可见。
  Tanenbaum 给出的透明性分类至今仍是教科书标准表述。
- **开放性**：按公开接口规范实现即可接入（原书举例即 Sun NFS / OSF DCE 的接口）。
- **可扩展性**：用户和机器翻几倍，系统不该散架——原书就指出 DNS 层次命名、
  「避免集中式组件、集中式表、集中式算法」是三条可扩展性戒律。

### 1.3 硬件概念（原书的分类树）
- 多处理机（共享内存）：总线型、交换型（Omega 交叉开关）。
- 多计算机（消息传递）：MPP（同构、专有互连）、**COW（Cluster of Workstations）**——
  异构、商品化以太网互连。Tanenbaum 在 1995 年就下注 COW 会赢，事后看完全正确。
- 🔧 2026 年对照：COW 的现代形态就是普通服务器集群 + 万兆/RDMA 互连；
  「多处理机」一极则以多核 CPU + NUMA 的形式活在单机内。

原书的分类树可以横向对照到今天的每一层硬件：

| 原书分类 | 耦合程度 | 1995 年实例 | 2026 年实例 |
| --- | --- | --- | --- |
| 多处理机·总线 | 紧（共享内存总线） | 双 CPU 工作站 | 单片多核 SoC |
| 多处理机·交换 | 紧（交叉开关/NUMA） | 大型 SMP 服务器 | NUMA 机架、CXL 内存扩展 |
| 多计算机·MPP | 松（专有互连） | nCUBE/Intel Paragon | HPC 集群 + InfiniBand（GPU 训练） |
| 多计算机·COW | 最松（商品网） | 工作站 + 以太网 | 云数据中心 + 以太网/RDMA |

「耦合越紧、通信越像函数调用；耦合越松、通信越像协议设计」——这句话是
第 2 章（RPC）与第 6 章（DSM）分野的硬件根源。

### 1.4 软件三分法（本书的坐标系）
| 类型 | 有无统一系统映像 | 典型例子 | 用户感知 |
| --- | --- | --- | --- |
| NOS（网络操作系统） | 无，每机各自登录、显式指定主机 | 早期 Unix + TCP/IP | 「我用的是机器 A 上的文件」 |
| 中间件 | 部分（服务层面统一，OS 之下不管） | NFS、DCE | 服务统一，底层仍暴露 |
| DOS（分布式操作系统） | 有，一个 OS 管全部机器 | Amoeba、Mach/Chorus 尝试 | 单一登录、统一进程/文件命名 |

原书立场：**真正的 DOS 尚未成功，中间件是当前（1995）的折中**。这句话到 2026 年依然成立——
只是「中间件」换了个名字叫 Kubernetes（[09](09-从分布式OS到现代云OS.md)）。

### 1.2 的标准表：六类透明性（全书反复引用，值得背下来）

| 透明性 | 隐藏什么 | 典型例子 | 实现代价 |
| --- | --- | --- | --- |
| 访问透明 | 数据表示、操作方式的差异 | 本地文件与 NFS 挂载点同 API | 协议适配层 |
| 位置透明 | 资源在哪台机器 | Amoeba 权能不暴露服务器地址 | 定位服务（见 [04-命名.md](04-命名.md)） |
| 迁移透明 | 资源搬家了 | 转发指针、home 位置 | 解引用开销 |
| 复制透明 | 有几个副本 | 主备复制对读方不可见 | 一致性协议（见 [06-一致性复制与容错.md](06-一致性复制与容错.md)） |
| 并发透明 | 别人也在用 | 事务隔离 | 并发控制（见 [05-同步.md](05-同步.md)） |
| 故障透明 | 某个副本挂了 | 重试 + 冗余 | 掩盖故障会损害可观测性——这是 2026 年的主流反思 |

### 1.5 设计问题的展开：为什么「集中式」是原罪
原书 1.5 节把设计问题拆成五组，其中最贯穿全书的一条是**伸缩性与集中式的矛盾**：

1. 集中式**组件**：一台中央文件服务器——单点瓶颈 + 单点故障。
2. 集中式**表**：一张中央命名表——访问路径随规模线性恶化。
3. 集中式**算法**：按固定顺序收集全体状态再决策——任何一台失联都阻塞全局。

三条戒律的对策分别是：复制与分片（第 6 章）、层次命名（DNS/第 7 章权能）、
局部化决策（第 3 章选举与第 5 章共识）。「避免集中」不是教条，而是把集中式
**换成可容错的集中式**（如共识组）——这正是 2026 年 etcd/Raft 的世界观。

### 1.2 的另一面：四个目标互相打架
原书没有明说、但值得补上的一层：这些目标是**互相冲突**的——

| 冲突对 | 冲突点 | 原书的隐性取舍 | 2026 年的显性取舍 |
| --- | --- | --- | --- |
| 透明性 vs 性能 | 每层透明都加一次间接 | 隐性接受（工作站快） | 明码标价：sidecar/代理延迟记入预算 |
| 透明性 vs 可观测性 | 故障透明掩盖真实状态 | 未展开 | 「诚实暴露失败」成为 SRE 原则 |
| 开放性 vs 性能 | 通用协议慢于专用协议 | 未展开 | gRPC 通用 + RDMA 专用的双栈 |
| 可扩展性 vs 一致性 | 越大越难同步 | 第 6 章才触及 | CAP 进入产品文档 |

读第 1 章时建立「目标是有代价的」直觉，后面每一章的协议都能理解成
「为某个透明性付出的账单」。

### 1.4 的补充：中间件的三层结构
原书给中间件画的位置图值得记住：应用代码 → **中间件**（提供统一接口：RPC、消息、命名、事务）
→ 各机器各自的本地 OS → 网络。中间件不接管内核，却提供分布式 OS 的全部「服务面」。
DCE（原书第 10 章）是 1995 年该结构的代表；REST/gRPC API 网关、服务网格是 2026 年
同一张图的翻版。

```c
/* 教学示意，不参与构建：用一张图区分「共享内存」与「消息传递」编程模型的差异。
   同样的「计数器加一」，两种硬件模型下的正确写法完全不同。 */

/* 多处理机（共享内存）：靠锁保原子 */
pthread_mutex_lock(&mu);
counter = counter + 1;          /* 复合操作，需互斥 */
pthread_mutex_unlock(&mu);

/* 多计算机（消息传递）：靠复制与共识保一致 */
send(leader, INC);              /* 请示协调者 */
recv(leader, NEWVAL);           /* 接受全局序的值 */
counter = NEWVAL;
```

## 版本演进

| 时期 | 硬件 | 软件范式 | 关键变化 |
| --- | --- | --- | --- |
| 1985–1995（原书背景） | 工作站 + 10 Mbps 以太网；MPP 与 COW 并存 | NOS → 中间件 → 真正 DOS 的探索（Amoeba/Mach/Chorus/DCE） | 「做一台机器一样的大电脑」是显式目标 |
| 1995–2005 | 集群普及，机架式 x86 | 中间件全面胜利：NFS/AFS、CORBA、J2EE | 研究界承认 SSI 难产；RPC/对象中间件当道 |
| 2005–2015 | 虚拟化 + 云（AWS 2006） | 分布式文件系统（GFS/HDFS）、MapReduce | 数据中心即计算机；分布式重写一切 |
| 2015–2026 | 超大规模数据中心 + 万兆/RDMA | 容器编排、服务网格、Serverless | Kubernetes 承担「分布式 OS」的角色（见 [09](09-从分布式OS到现代云OS.md)） |

## 近年研究与工业界开源实践（2015–2026）

- **「数据中心即计算机」**：从 Google 的 warehouse-scale computing（Barroso 等，Morgan Claypool 系列论文）到今天的
  AI 集群调度，1.3 节 COW/处理器池的争论以 GPU 集群调度的形式重演——Kubernetes、Slurm、
  自研调度器都在回答原书 4.3 节的同一个问题（谁把任务放到哪台机器）。
- **中间件进化为编排层**：`kubernetes/kubernetes`（127994★，2026-09-26 实测）已成为事实上的
  「集群操作系统」外壳；其声明式 API 与原书「单一连贯系统」的初衷是同一枚硬币的两面。
- **透明性概念的回潮**：服务网格（如 Istio）宣称把流量管理/加密/重试做成「对应用透明」，
  这正是原书 1.2 节六类透明性的工程化尝试，也继承了「透明性代价」的老争论。
- **开放性的新载体**：OCI 镜像规范（`opencontainers/runc`，13459★）是 1.2 节「开放性」的现代成功案例——
  接口标准化后，谁实现镜像谁就能接入整个生态。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「分布式系统 = 多台机器联网」 | 关键在统一映像/统一服务，NOS 联网不算 |
| 2 | 「透明性越高越好」 | 透明性有代价：故障透明会掩盖真实状态，可观测性要求「诚实暴露」部分失败（见 06 章） |
| 3 | 「分布式 OS 和网络 OS 是一回事」 | 原书 1.4 的三分法专门用于区分两者 |
| 4 | 🔧 **ATM 网络、MPP 的篇幅已无用** | 2026 年应直接读以太网/RDMA 与商品化集群；MPP 内容仅存历史价值 |
| 5 | 🔧 **「真正的 DOS 尚未出现」的结论要更新** | Kubernetes 生态近似实现了当年 DOS 的目标（统一调度/命名/服务发现），但它是用户态编排层而非内核——范式从「内核里做」迁移到「内核之上做」 |
| 6 | 🔧 **可扩展性数字过时** | 原书讨论「成千上万台」已属激进；今天百万级 Pod 的调度需要分片（Kubernetes multi-cluster、调度器分片） |
| 7 | 「开放性就是有标准文档」 | 开放性的有效判据是**多方可独立实现并互操作**；OCI/DNS 过关，很多「开放 API」只过关一半 |
| 8 | 「COW（集群）与云计算是两回事」 | 同一硬件形态的两次命名：1995 年叫 COW，2006 年后叫云；差别在计费与 API，不在架构 |
