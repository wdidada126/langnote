## 核心精讲

### 1 范式为什么「输了」（三重绞杀）
1. **硬件经济学反转**：Amoeba 假设「工作站夜里空闲，算力昂贵要共享」；1990 年代后期
   CPU 指数降价 + 带宽暴涨，每台机器自带全量 OS 成为最便宜的选择。「处理器池」败给
   「人人有 CPU」——直到 2006 年云计算把算力重新集中，池模型换名「实例租用」复活。
2. **兼容性引力**：Amoeba/Mach/Chorus 都要回答「能跑我的 Unix 程序吗」。仿真兼容层
   是成本黑洞，而 Linux 免费提供了 100% 兼容的「网络操作系统 + 中间件」组合。
   DCE 路线（内核之上做分布式）从此成为默认。
3. **性能论战定音**：L4 证明微内核 IPC 可以快，但「快」已不足以对抗生态——
   结论：微内核退守安全关键（车载/航空/验证），通用计算归于宏内核。

这三重绞杀可以提炼成一句判词，方便与 [01](01-分布式系统引论.md) 的目标清单对读：
**分布式 OS 输掉的不是技术，是「换掉单机内核」这个前提本身**——
当 Linux 免费且够快时，一切分布式能力都被迫搬到内核之外，
而搬运过程恰恰催生了比内核更繁荣的上层生态（DCE → K8s）。

### 3 Kubernetes 作为「事实上的分布式 OS」（本目录最重的对照表）

| Amoeba/Mach 时代的概念 | Kubernetes 世界的对应 | 说明 |
| --- | --- | --- |
| 处理器池中创建进程 | Pod 被调度到节点 | `kube-scheduler` 即原书 4.3 处理机分配的工业化 |
| 权能（访问凭证） | ServiceAccount Token / RBAC | 「名字+权限」合一的现代形态（无单向函数校验，改为签名令牌） |
| 目录服务器 | etcd（`etcd-io/etcd`，52310★）+ API Server | 共识承担了原书 3 章时钟/互斥/选举的全部职责 |
| 服务定位（广播/目录） | Service + CoreDNS | 「服务名 → 虚拟 IP → 端点」，[04-命名.md](04-命名.md) 目录服务路线 |
| 进程描述符 | PodSpec / OCI 镜像 | 声明式；`opencontainers/runc`（13459★）是「创建进程」的新原语 |
| FLIP 组播 | Service/Ingress + 消息系统 | 未直接复刻；组通信让位给「共识 + 队列」 |
| Unix 仿真层 | 容器即兼容层 | Linux ABI 就是新一代的「Amoeba Unix 仿真」——但这次兼容层赢了 |

一句话：**Kubernetes 不是把 OS 内核搬上网，而是把 OS 的「系统调用面」重新发明为声明式 API**。
原书 1.2 节的「单一连贯系统映像」以「集群状态 = API 对象」的形态部分兑现。

对照表要加上一行「差异」才算诚实——三个不能一一对应的点：

| Amoeba 概念 | K8s 对应 | 无法对应的差异 |
| --- | --- | --- |
| 统一进程命名空间 | Pod 各自独立 PID 空间 | K8s 放弃了「全局进程表」，靠 Service 名而非 PID 引用工作 |
| 权能自动传递 | RBAC 显式授权 | 没有自动的「权能随消息携带」，授权是静态配置 |
| 处理器池动态迁移 | Pod 基本不迁移 | 失败即重建（新身份），迁移透明性被「重启透明性」替代 |

### 4 新的单一系统映像候选（2026）
- **Serverless**：函数即进程单位，平台隐藏机器——透明性比 Amoeba 更彻底（连 Pod 都看不见），
  代价是可控性（当年的透明性之争重演）。
- **WebAssembly / WASI**：`bytecodealliance/wasmtime`（18657★）、`wasmerio/wasmer`（21089★）；
  WASI 给「跨机器可移植的系统接口」一个无 POSIX 包袱的候选——原书 4.6/7 章的
  「轻量进程 + 能力化安全」思想在 WASM 的 capability-based 导入模型里重生。
- **microVM 与沙箱**：`firecracker-microvm/firecracker`（36955★）、`google/gvisor`（19420★）——
  「进程的安全边界」重新成为热点，这正是 Mach 端口权能当年解决的同一问题。
- **sidecar / 服务网格**：把通信透明性做成基础设施注入——原书 2 章组通信 + 6 章复制的
  「中间件化」完成时。
- **单系统映像的「残余阵地」**：全闪存分布式存储的统一命名空间、AI 集群的统一调度视图、
  多集群服务网格——SSI 没有以「一台大电脑」出现，而是按领域零星落地；
  每落地一处，都会重新吵一遍原书 1.5 节的老问题（透明性 vs 可观测性）。

这四个候选的成熟度差异值得一表：

| 候选 | 成熟度 | 最大的未解问题 |
| --- | --- | --- |
| Serverless | 生产成熟 | 冷启动与状态管理 |
| WASM/WASI | 服务端上升期 | 系统接口完备度（线程/异步/网络） |
| microVM | 生产成熟 | 密度与启动速度的再平衡 |
| 服务网格 | 生产成熟但争议中 | 复杂度是否超过收益 |

### 5 如果 Tanenbaum 写第三版（2026 视角清单）
- 第 2 章删 ATM，改 QUIC/gRPC/RDMA；
- 第 3 章加 TrueTime/HLC、Raft、租约；
- 第 4 章处理器分配改写为容器调度与 GPU 集群调度；
- 第 5 章文件系统改对象存储与纠删码；
- 第 6 章 DSM 保留一致性模型，实例换 Redis/内存网格；
- 实例研究换四章为两章：Kubernetes 与 Spanner/etcd。

再加两章 1995 年还不存在的主题：

| 新章 | 内容 | 对应原书概念 |
| --- | --- | --- |
| 可观测性 | 指标/日志/追踪、eBPF | 「故障透明」的另一半：诚实暴露而非掩盖 |
| 安全与零信任 | mTLS、身份、最小权限 | 权能思想的服务化重生 |

## 版本演进

> 本表是全目录时间线的「总纲」——各章版本演进表都是本表某一段的放大。

| 时期 | 「分布式 OS」叙事的主人 | 关键变化 |
| --- | --- | --- |
| 1985–1995（原书） | 内核研究者（Amoeba/Mach/Chorus/DCE） | 在内核里做分布式 |
| 1995–2005 | 中间件厂商（CORBA/J2EE/DCE 后继） | 在内核上做分布式 |
| 2005–2015 | 云平台与大数据栈（GFS/MapReduce/Hadoop） | 在机房尺度重做一切 |
| 2015–2026 | 编排与平台工程（K8s/Serverless/WASM） | 用声明式 API 重构「分布式 OS 的系统调用面」 |

**判读这条演进线时最容易犯的错**：把「范式输赢」理解成「技术输赢」。
其实每一阶段胜出的技术（TCP/IP、Linux、容器）都是**上一阶段的普通参与者**，
赢的是位置与生态位，不是论文里的最优设计。DCE 的 RPC 设计不如 Amoeba 的 FLIP 精致，
但它跑在现成 Unix 上——2026 年做技术选型时，这条历史规律仍是第一参考。

## 近年研究与工业界开源实践（2015–2026）

- **编排层的「OS 化」持续加深**：`kubernetes/kubernetes`（127994★，2026-09-26 实测）社区把
  「设备插件」（GPU/FPGA 调度）、资源模型、准入控制（admission control）做成内核级钩子——
  对比原书第 4 章，2026 年连「外设」都进入了分布式 OS 的抽象。
- **平台工程与「内部开发者平台」**：把集群包装成产品交付，等于把 1.2 节「用户感知统一映像」
  从技术目标变成组织目标。
- **AI 集群成为新的调度主战场**：GPU 拓扑感知调度、成组（gang）调度、检查点搬迁——
  原书第 4 章的「处理机分配」在 2026 年最贵的算力（训练集群）上重演，
  且当年「迁移新任务」的洞察依然是对的（迁移已调度的训练任务代价极高）。
- **WASI 的推进**：wasi-nn、wasi-threads 等提案让 WASM 逐步具备「进程」的全部要素；
  capability-based 的导入模型被业界视为比传统 POSIX 更安全的系统接口方向。
- **边缘与广延**：K3s/KubeEdge 类项目把集群 OS 的边界推到车间与卫星——
  原书 4.6 实时分布式的核心关切（可预测性）在边缘场景重新升温。
