# 数据建模与关系处理（原书 Ch7）

> ⚠️ 主题重构：Ch7 代码 `data_modeling` 含 nested/join/denormalize 三组完整示例——ETF 分红数据（dividend）的三种建模方案对比，是本章精华。

## 1. ES 中的关系问题

ES 是文档存储——不支持 SQL JOIN。关系建模 = **用存储结构换查询能力**的取舍谱系。

书中 ETF 场景：一个 ETF（fund）对应多条 dividend（分红记录）——一对多关系三种建模策略：

| 策略 | 数据模型 | 查询 | 更新代价 | 存储代价 |
|---|---|---|---|---|
| Denormalize | 分红数组嵌入 ETF 文档 | 快（单文档命中） | 高（更新整文档） | 中（冗余） |
| Nested | 分红作为隐藏子文档 | 精确（nested query + agg） | 中（重写子文档） | 中（独立 Lucene 文档） |
| Parent-Child (join) | ETF 为父，dividend 为子 | 灵活（has_child/has_parent） | 低（独立更新） | 高（join 字段 + 路由约束） |

## 2. Object 数组的"串味"问题

```json
{
  "name": "SPY",
  "dividends": [
    {"date": "2018-01-15", "amount": 1.2},
    {"date": "2018-06-20", "amount": 1.5}
  ]
}
```

ES 将 object 数组**扁平化**为列式倒排：
- `dividends.date = [2018-01-15, 2018-06-20]`
- `dividends.amount = [1.2, 1.5]`

查询 `{"date":"2018-01-15", "amount":1.5}` 会**误命中**——因为 date 和 amount 的配对关系已丢失。

→ 解决：**Nested 类型**——每个子对象独立索引为隐藏文档，保持字段配对。

## 3. Nested 建模

```json
// cf_etf_dividend_nested_mappings.json 核心 ⚠️ 转述
{
  "mappings": {
    "properties": {
      "name": { "type": "keyword" },
      "dividends": {
        "type": "nested",
        "properties": {
          "date": { "type": "date" },
          "amount": { "type": "float" }
        }
      }
    }
  }
}
```

- nested 文档是隐藏 Lucene 文档——查询需 `nested` query 包装
- 聚合需 `nested` bucket 包装（见 [06-聚合框架.md](06-聚合框架.md)）
- 更新代价：改一个 nested 子文档 = 重写整个父文档

官方文档：https://www.elastic.co/guide/en/elasticsearch/reference/7.17/search-aggregations-bucket-nested-aggregation.html ✅ 200

## 4. Parent-Child (Join Field) 建模

```json
// cf_etf_dividend_join_mappings.json 核心 ⚠️ 转述
{
  "mappings": {
    "properties": {
      "relation": {
        "type": "join",
        "relations": { "fund": "dividend" }
      }
    }
  }
}
```

- 父文档：`{"relation": "fund"}`
- 子文档：`{"relation": {"name": "dividend", "parent": "SPY"}}`
- 查询：`has_child`（找有匹配子文档的父）、`has_parent`（找匹配父文档的子）
- 关键约束：父与子必须在**同一主分片**——routing 由父 ID 决定
- 代价：子文档更新不影响父（低代价），但查询有 ~10x 开销

## 5. 反规范化（Denormalize）

书中 `cf_etf_dividend_denormalize_bulk.json`：每条 dividend 独立文档 + 冗余 ETF 字段。
- 优势：独立更新、简单查询
- 劣势：存储冗余、ETF 信息变更需更新所有 dividend 副本

## 7. 建模决策树（书中 ETF 数据集贯穿）

1. 数据量大 + 频繁读 + 极少更新子对象 → **Denormalize**
2. 需要保持字段配对语义（date-amount、author-date） → **Nested**
3. 子文档频繁独立更新（增删改）+ 不需要父子联合排序 → **Parent-Child**
4. 关系复杂（多对多） → ES 不擅长——**应用侧 JOIN 或换图数据库**（见 [../Neo4j_The_Definitive_Guide/00-总览与阅读地图.md](../Neo4j_The_Definitive_Guide/00-总览与阅读地图.md)）

## 8. 本章要点

- ES 关系建模 = 三角取舍（读写/一致性/存储）——无银弹
- Object 数组扁平化是经典陷阱——nested 解决此问题
- Parent-child 的 routing 约束（父与子同分片）是运维难点
- TDG [../Elasticsearch_The_Definitive_Guide/02-高级搜索与查询DSL.md](../Elasticsearch_The_Definitive_Guide/02-高级搜索与查询DSL.md) 的 nested/parent-child 是 1.x 时代口径，本章为 7.0 实操版

## 核心概念速览（中英对照）

1. **反规范化** — Denormalization：将关联数据冗余存储到单文档，减少查询复杂度
2. **嵌套类型** — Nested Type：ES 中子对象独立索引为隐藏文档，保持字段配对语义
3. **Join 字段** — Join Field：ES 7.0 中 parent-child 关系的 mapping 声明方式
4. **has_child / has_parent** — 跨层级查询：从父查子（has_child）、从子查父（has_parent）
5. **Routing 约束** — 父子文档路由到同一分片，routing = parent ID
6. **对象串味** — Object Field Flattening：object 数组扁平化导致字段配对关系丢失
7. **文档模型** — Document Model：ES 以半结构化 JSON 文档为存储单元
8. **应用侧 JOIN** — 在客户端/应用层手动拼接关联数据（ES 无 JOIN）
9. **重写代价** — 更新 nested 子文档需重写整个父文档（Lucene 段不可变）
10. **数据冗余** — Denormalize 引入的存储成本——一致性由应用维护

## 最新演进与工业实践

- **ES 9.x**：parent-child 仍有 `has_child`/`has_parent`，但 Elastic 官方文档建议**优先考虑 denormalize**（性能更优）。`join` 字段类型保留——无新关系建模机制
- **Elasticsearch 8.x 新选项**：`flattened` 字段类型（https://www.elastic.co/docs/... ⚠️ 路径未验证）——将任意 JSON 对象索引为 keyword 集合，避免 dynamic mapping 爆炸——不解决关系问题但解决"未知结构"场景
- **工业实践**：搜索引擎场景（电商/日志/可观测性）绝大多数用 denormalize + 单宽表；nested 用于"必须精确匹配子对象字段对"场景（合同条款、药品成分）；parent-child 在"子文档频繁独立更新且需反向查询父"场景存活
- **跨模型对比**：关系型数据库靠 JOIN 引擎处理关系；图数据库靠遍历引擎（Neo4j 等）；ES 的取舍本质是"用存储结构替代计算"——DDIA [../设计数据密集型应用/00-总览与阅读地图.md](../设计数据密集型应用/00-总览与阅读地图.md) Ch7 给出更一般化的视角
- **本册贡献**：书中 ETF 三方案对比是 ES 建模教学中最清晰的实操示例之一——社区笔记常引用
