# 06 · 概念与代码膨胀：模板的两大慢性病（对应原书第 10–11 章）

> 原书位置：第 10 章「专用名词——概念」（P180–191）/ 第 11 章「代码膨胀」（P192–208）。
> 单文件大纲：[../深入实践C++模板编程.md](../深入实践C++模板编程.md)。

## 核心概念速览（中英对照）

- **模板的先天不足** — templates lack requirements：形参只说「是个类型」，没说「能做什么」
- **概念** — concept：对模板参数的显式需求规格（语法、语义、公理）
- **ConceptGCC** — Berman/Sutton 的概念扩展编译器：语法含 `concept typename X { reqs }` + `concept_map`，已随标准投票失败而退役
- **概念映射** — concept map：把「类型 T 满足概念 C」显式登记进程序——C++20 改走结构化推断，此机制死亡
- **概念检查** — concept check：手工把需求写进模板体的惯用法（`BOOST_CONCEPT_ASSERT`、检查宏）
- **典型概念** — canonical concepts：Assignable/CopyConstructible/… STL 命名需求文档化的产物
- **SFINAE** — Substitution Failure Is Not An Error：重载集中「替换失败≠错误」的静默淘汰机制
- **检测惯用法** — detection idiom（`void_t`, C++17）：`is_detected` 式「问表达式是否合法」的库工具
- **源代码膨胀** — source bloat：为每种类型手写代理/包装类的复制粘贴地狱（11.1 代理类困境）
- **目标代码膨胀** — object-code bloat：每个实例化各生成一份机器码；成因在「类型无关部分也随类型重编」
- **基类抽取** — base-class extraction：把与 T 无关的成员/函数下沉到**非模板基类**，全类型共享一份码

## 动机：一次报错为什么像考古

书中第 10 章的立论（机制转述）：`sort(my_weird_list.begin(), my_weird_list.end())`
的失败要穿过七八层模板实例化栈才在深处爆出「没有 operator<」，诊断里全是
`__normal_iterator<...>` 与 STL 内部签名。**错误出现的位置离错误原因的距离**是模板
系统的原罪。概念运动的三个时代正好在此分野：

1. **提案时代（本书成书时点）**：ConceptGCC 给语法 `concept typename C { requires ... }`，
   使用方写 `concept_map std::list<E> : Container { }`——显式登记、编译器早查。
   2006 年 ISO 投票未过，路线死亡。
2. **模拟时代**：Boost.ConceptCheck、书中 10.4 的「概念检查宏」——用普通模板
   + 成员指称技巧（取 `&T::operator=` 的地址证明可赋值）在实例化时早报错。
3. **实现时代（C++20）**：concepts 语法归来，但**没有 concept_map**——满足与否由
   编译器对 requires 表达式做结构化推断，公理性要求（"排序后有序"）回归文档。

## 机制：SFINAE 如何参与重载，概念如何改写诊断

**SFINAE 的行为层定义**：重载决议为每个候选函数模板做「把推导出的实参代回签名」的
替换；任何一步失败（如 `enable_if<false>::type` 无 type 成员）只把该候选**从重载集中
静默移除**；全体移除后才报「no matching function」。关键细节：替换只看**立即上下文的
签名部分**，函数体里的错误仍是硬错误（深栈考古照旧）——这就是为什么 2013 年要靠
`enable_if` 把需求全部搬进签名。

```cpp
// 🔧 已实测 g++ 15.2 -std=gnu++17：SFINAE 时代的报错（真实截取）
template <class T, class = typename std::enable_if<std::is_integral<T>::value>::type>
T halve(T v) { return v / 2; }
halve(3.5);
// error: no matching function for call to 'halve(double)'
// note: candidate: 'template<class T, class> T halve(T)'
// note: template argument deduction/substitution failed:
// error: no type named 'type' in 'struct std::enable_if<false, void>'
```

```cpp
// 🔧 已实测 g++ 15.2 -std=gnu++20：concepts 的报错（真实截取）
template <std::integral T> T halve_modern(T v) { return v / 2; }
halve_modern(3.5);
// error: no matching function for call to 'halve_modern(double)'
// note: constraints not satisfied
// note: the expression 'is_integral_v<_Tp> [with _Tp = double]' evaluated to 'false'
```

同文件里自定义概念的实测诊断（requires 表达式版）更锋利：

```cpp
// 🔧 已实测 g++ 15.2 -std=gnu++20（d2_concept_err.cpp 截取）
template <class T> concept HasFoo = requires(T t) { t.foo(); };
NoFoo n{}; callFoo(n);
// note: the required expression 't.foo()' is invalid   ← 直接点名缺哪个成员
// note: set '-fconcepts-diagnostics-depth=' to at least 2 for more detail
```

对比结论到编译器行为层面：概念是**签名级需求的语法化**——把当年必须塞进
`enable_if` 的东西移到可诊断、可组合（`&&`/`||` subsumption）、可复用的位置；
淘汰候选的机制仍是重载决议，但淘汰理由被保留进诊断。**经典文献口径**（Bancila 书
亦同此论，见 [../C++20模板元编程.md](../C++20模板元编程.md)）：concepts 取代的
不是 SFINAE 机制而是 `enable_if` 惯用法；纯检测类需求（"有没有 `foo` 成员"）
当年用 decltype-SFINAE，今天用 requires 表达式，一字一义。

**代码膨胀（第 11 章）**两条战线（机制转述）：

- 源代码膨胀：代理类/访问器为每类型手写一份——书中顺手对比 D 语言的模板混入
  （template mixin）作解，属时代趣谈；今天的解法即概念+约束模板（一份代码通吃）。
- 目标代码膨胀：`stack<array<int,100>>` 与 `stack<array<double,100>>` 里，
  push/pop 的**指针体操部分逐字节相同**却各编一份。治理三板斧：
  ① **基类抽取**——类型无关逻辑进非模板基类（书中 11.2.3「改进代码」实测口径：
  把成员函数体里不依赖 T 的部分搬进 `stack_common`）；② **显式实例化白名单** +
  `extern template`（N1987，已实测可达）让热点实例只编一次；③ **类型擦除**——
  `std::function<void(int)>` 一份码服务所有可调用物，用一次间接调用换实例数量。

## 权衡：早报错 vs 泛得开

概念检查太早会误杀「中间态类型」——迭代器流水线里常有人先造出半成品再补成员；
C++20 标准库概念普遍只要求**最终使用点**成立，且刻意保持 weakly-semantic
（`std::regular` 带公理但编译器不验公理）。膨胀治理同样有对价：`extern template`
牺牲「任何类型即取即用」换编译/链接时间；类型擦除牺牲内联与堆分配换代码量。
**选边依据只有一个：测**（体积、编译秒数、调用热区）。

## 最新演进与工业实践

- **标准库概念入库（C++20, P0898R3 "Standard Library Concepts"，wg21.link 实测可达；
  前身为 Concepts TS 工作稿 N4674，实测可达）**：`<concepts>` 提供 `same_as/integral/
  invocable/...`；`<ranges>` 的迭代器/范围概念族见 [05 章](05-迭代器与算法.md)。
- **库缺概念问题**：仍有标准组件停留在「文档要求」层（如分配器的全部要求直到
  C++20 才获得 `std::allocator` 概念背书），而 `std::atomic` 不可拷贝这类
  「概念可满足性反直觉」也在库工作组持续修——本书 10 章的清单今天大半可由编译器代验。
- **检测惯用法转正**：C++17 `void_t` + `std::experimental::is_detected`（库 TS 血统，
  ⚠️ 是否进 C++26 未核实），是「concept_map 死亡后」检测需求的轻量正解。
- **fmt 的膨胀治理实证**：`FMT_SHARED`/非 header-only 模式下核心解析器全部
  `extern template` 化进 libfmt.so——11 章三板斧的第②板在现代旗舰库里的落地
  （github.com/fmtlib/fmt，`fmt/base.h`）。folly 的 `Function`/`Conv` 则是类型擦除板。
- **诊断工程的日常**：`-fconcepts-diagnostics-depth=2`（GCC）与 clang 的
  `-fconcepts-diagnostics-format=elfv2` 风格输出，是 2026 年读概念报错的标配——
  「考古式模板报错」已是可调参数而非宿命。
