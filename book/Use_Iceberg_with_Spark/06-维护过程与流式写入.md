## 核心精讲

> 以下 SQL/代码均为**教学示意，不参与构建**；`CALL` 语法需要 02 章的 extensions 已开启。

### 6.1 为什么 Iceberg 也需要「后台运维」

写路径的每次提交都追加元数据（manifest）与数据文件；读路径按当前快照展开文件清单。
于是债务自动累积：

- **小文件**：高频小批量写 → 成千上万 KB 级 Parquet → 读侧 task 数爆炸；
- **元数据膨胀**：manifest 条目过多 → Spark 作业「Planning 阶段」就比 Flink 慢（04 章 `manifests` 表可诊断）；
- **过期快照与孤儿文件**：旅行窗口的对价是存储成本；失败作业可能遗留无引用文件。

Spark-Iceberg 的解法是**把维护做成可调用的过程**（`CALL catalog.system.<proc>`），本质仍是 Spark 作业，
天然分布式、可被 Airflow/DolphinScheduler 编排。

### 6.2 rewrite_data_files

```sql
-- 教学示意 A：binpack（默认策略），目标 512MB
CALL wh.system.rewrite_data_files(
  table => 'demo.orders',
  strategy => 'binpack',
  options => map('target-file-size-bytes', '536870912',
                 'min-input-files', '5')
);

-- 教学示意 B：sort 重写，顺便为点查建聚簇顺序
CALL wh.system.rewrite_data_files(
  table => 'demo.orders',
  strategy => 'sort',
  sort_by => 'customer,ts',
  where => 'ts >= "2025-01-01"'            -- 只整理近段热数据
);
```

- MoR 表的 delete 文件在此过程中被物化消化（等价于 Delta 的 VACUUM+OPTIMIZE 合体）。
- 默认按**分区**分组重写，绝不跨分区搬行（避免破坏分区隔离）；这正是 5.4 所说的「统一新旧
  分区规格」的手段：先 `REPLACE PARTITION FIELD`，再全表 sort/binpack。
- 并发注意：重写与业务写会提交冲突；新版提供分布式/增量变体与 `partial-progress.enabled`
  （允许重写部分结果先提交，⚠️ 具体参数名随版本，以 spark-procedures 文档为准）。

### 6.3 rewrite_manifests

```sql
-- 教学示意：合并碎片化 manifest（Java API 对应 rewriteIf(小文件阈值)）
CALL wh.system.rewrite_manifests('demo.orders', false);   -- 第二参 check_compatibility
```

症状：查询 planning 分钟级、`SELECT count(*) FROM tbl.manifests` 四位数。频率远低于 6.2。

### 6.4 expire_snapshots 与 remove_orphan_files

```sql
-- 教学示意：过期 7 天前的快照（物理删除其独占文件）——旅行窗口在这里被收割
CALL wh.system.expire_snapshots(table => 'demo.orders', older_than => TIMESTAMP '2025-09-01 00:00:00', retain_last => 5);

-- 注意：expire 不隐式处理分支/标签；被分支钉住的快照不过期（Iceberg 1.4+ 语义）

-- 教学示意：清理 3 天前无引用的孤儿文件（失败作业残留）
CALL wh.system.remove_orphan_files(table => 'demo.orders', older_than => TIMESTAMP '2025-09-22 00:00:00');
```

两个都是**删除语义**：误配 expire 会废掉回滚与增量读；orphan 清理的 `older_than` 必须晚于
最长作业时长（默认 3 天口径即为此），否则可能删掉进行中作业的暂存文件。
命名核对：现行过程名 `remove_orphan_files`；旧版文档/API 称 `delete_orphan_files`
（maintenance.md 的 Java/Actions API 仍写作 `deleteOrphanFiles`），同一功能两代名字。

### 6.5 流式读

```scala
// 教学示意：从当前快照开始持续消费增量（micro-batch 发现新快照）
spark.readStream
  .format("iceberg")
  .option("streaming", "true")
  .option("monitoring-interval", "5 minutes")       // 周期性检查新快照
  .option("streaming-max-files-per-micro-batch", "1000")  // 新版节流键名（旧版为 maxFilesPerTrigger，见版本节）
  .load("wh.demo.events")
```

- 默认**只消费 append**；上游若产生行级删除，快照会令流作业报错，除非开启删除向量/
  delete 消费选项（如 `streaming-delete-enabled`，⚠️ 名称与适用版本以当前文档为准）。
- 静态读历史区间：`read.streams` 风格的一次性消费或直接用 4.5 的 DataFrame 增量选项。

### 6.6 流式写

```scala
// 教学示意：聚合结果每分钟一个快照落表
aggDF.writeStream
  .format("iceberg")
  .option("checkpointLocation", "s3://bucket/ckpt/events_agg")
  .trigger(org.apache.spark.sql.streaming.Trigger.ProcessingTime("1 minute"))
  .toTable("wh.demo.events_agg")
```

限制清单（官方文档口径）：

- 输出模式仅 **append / complete**（官方文档口径）；`Update` 不支持；
  **Continuous 触发器不支持**——连续执行无法对接「提交即快照」的原子协议。
- 每个 micro-batch = 一次快照提交 → exactly-once 的根基是 catalog CAS；checkpoint 丢失
  等于重来，表不会脏。
- 流式写**不做行级 upsert**；需要 upsert 的实时链路用「流落地暂存表 + 微批 MERGE」两段式（03 章 3.5）。
- 高频小批 = 小文件制造机：与 6.2 的 compaction 排班联动是必然。

### 6.7 维护排班表（教学建议，非官方 SLA）

| 过程 | 频率示例 | 前置/依赖 |
| --- | --- | --- |
| `rewrite_data_files` | 每 1–6 小时，按分区窗口增量做 | 业务低峰；避开同分区并发 MERGE |
| `rewrite_manifests` | 每天/每周 | planning 慢才做 |
| `expire_snapshots` | 每天 | 旅行窗口与增量读消费位点先核对 |
| `remove_orphan_files` | 每周 | 仅在有作业失败残留证据时提频 |

顺序心法：**先整理（rewrite）再过期（expire）**，孤儿清理永远最后。

## 版本与兼容性

- 过程框架（`system` 命名空间 + `CALL`）依赖 Spark procedures（Spark 3.1+）与 Iceberg extensions。
- 流式读的节流选项经历改名：`maxFilesPerTrigger` → `streaming-max-files-per-trigger` →
  当前文档口径 `streaming-max-files-per-micro-batch`（另见 02 章风格的 catalog 级配置）。
  跨版本迁移旧流作业务必逐键核对。
- `rewrite_data_files` 的 zorder/聚类变体（`sorted_by`、Spark 聚簇表 `WRITE USING CLUSTERED BY`）
  属 1.8+/Spark 4 时代新面，⚠️ 本目录未逐项核实其稳定状态。
- v3 deletion vector 表的维护路径与 v2 MoR 不同（以 spec 与 release notes 为准）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「Iceberg 自动 compaction」 | 规范只保证读不受碎片影响；合并文件是引擎侧过程，要自己排班 |
| expire_snapshots 当 VACUUM 随手跑 | 它决定旅行/回滚/增量读的有效窗口；先与下游消费位点对齐 |
| remove_orphan_files 越勤越好 | 误删进行中作业的暂存文件=数据损坏；`older_than` 是安全阀不是格式参数 |
| 流式写开 `Trigger.AvailableNow` 就支持 upsert | 触发器与写入语义无关；Iceberg 流写只有 append 系 |
| 「checkpoint 没了会丢数据」 | 丢的是消费进度；表侧每批都是完整快照，重放即可（幂等性由源保证） |
| CALL 报 `Unsupported statement` | 忘开 `spark.sql.extensions`（02 章 2.3），过程全部由 extensions 注册 |
