## 核心精讲

> 以下 SQL 均为**教学示意，不参与构建**。

### 5.1 隐藏分区：机制与 transform 清单

建表时声明的不是「分区列」，而是**分区表达式**：

```sql
-- 教学示意
CREATE TABLE wh.demo.events (
  event_id BIGINT, user_id BIGINT, event_type STRING, payload STRING, ts TIMESTAMP
) USING iceberg
PARTITIONED BY (days(ts), bucket(16, user_id));
```

物理布局由 Iceberg 决定（目录名如 `ts_day=2025-01-01/user_id_bucket=7/`），但**用户与查询不可见**。
支持的 transforms：

| 类别 | transform | 例 |
| --- | --- | --- |
| 恒等 | `identity` | `identity(region)` |
| 时间 | `years/months/days/hours` | `days(ts)` |
| 有界 | `bucket(N, col)`、`truncate(W, col)` | `bucket(16, id)`、`truncate(4, zip)` |
| 特殊 | `void` | 分区值置空（配合演化保留旧文件归属用） |

剪枝原理：查询规划时 Iceberg 把谓词沿 transform **反构**成分区范围。`WHERE ts >= '2025-01-01 10:30'`
会被重写为「对 `ts_day >= 2025-01-01` 的分区保留，且对 `ts_day = 2025-01-01` 的分区内文件按真实
stats 继续过滤」——用户不需要知道 `days(ts)` 的存在。这是元数据层的表达式改写，
与 Catalyst 靠 `dt` 列名做静态裁剪有本质区别（对照 [../bigdata/04-SparkSQL与结构化数据.md](../bigdata/04-SparkSQL与结构化数据.md) 的分区裁剪节）。

### 5.2 隐藏分区如何免除 Spark 原生分区痛点

| Spark 原生分区痛点（1.1 回顾） | Iceberg 的答案 |
| --- | --- |
| 查询必须记得 `WHERE dt='...'`，忘写=全表扫 | 写 `WHERE ts >= ...` 即可，剪枝由 transform 反构自动完成 |
| 按天粒度定死；小时级需求要加列重刷 | 分区演化（5.4）一条 `REPLACE PARTITION FIELD` |
| 冗余派生列 `dt` 污染 schema 与下游 | 表里根本没有 `dt` 列 |
| 多分区键组合目录爆炸、无统计 | `partitions` 元数据表聚合每分区统计（04 章 4.4） |
| 补数 = 手工搬目录 + `MSCK REPAIR` 类操作 | 提交即注册，目录布局对所有人透明 |

### 5.3 Schema evolution 的 Spark 表现

Iceberg 用**列 ID**（不是名字、不是位置）标识列，因此任何改名/重排都不触碰数据文件
（官方文档原话：schema 更新是元数据变更，无需重写数据文件）。

```sql
-- 教学示意：全部 O(1) 元数据操作
ALTER TABLE wh.demo.events ADD COLUMN severity INT AFTER event_type;
ALTER TABLE wh.demo.events ADD COLUMN source STRING FIRST;
ALTER TABLE wh.demo.events RENAME COLUMN event_type TO kind;
ALTER TABLE wh.demo.events DROP COLUMN payload;
ALTER TABLE wh.demo.events UPDATE SET user_id TYPE BIGINT;   -- 见下方提升白名单
```

**允许的类型提升**（不转码、只改解释）：

- `int → bigint`；`float → double`；`decimal(p1,s1) → decimal(p2,s2)`（p2>p1 且 s2=s1）。
- `string ↔ binary`（UTF-8 表示下无损）。
- 其他一律禁止：`bigint → int`、`string → int`、改精度缩位等都要走「加新列 + backfill + 删旧列」。

**Spark 读写侧的表现**：

- 读：旧文件缺的新列按 null 填充；改名后的列自动按 ID 对回——不会像 Hive 那样错位。
- 写：V2 写路径按**列名**解析（`INSERT ... UPDATE SET *`、`writeTo().append()` 都是 name-based），
  DataFrame 里出现表中不存在的列默认报错；「写入时自动加列」（write-time schema evolution）是较新的
  特性，开关与行为随版本变化较大（⚠️ 未逐版核实，使用前查所用版本的 spark-writes 文档）。

### 5.4 Partition evolution

真实故事线：先按天分区跑半年，BI 要求小时粒度。Hive 表只能全量重写；Iceberg：

```sql
-- 教学示意：天 → 小时
ALTER TABLE wh.demo.events REPLACE PARTITION FIELD days(ts) WITH hours(ts);

-- 加一维：桶分区也保留事件类型维度
ALTER TABLE wh.demo.events REPLACE PARTITION FIELD days(ts) WITH days(ts), identity(kind);

-- 撤销演化（扩回去）
ALTER TABLE wh.demo.events EXPAND PARTITION FIELD bucket(16, user_id);
```

关键语义（官方口径）：

- **元数据操作，不回填**：老文件保留自己的旧分区规格（spec-id 记录在文件元数据里），新写入用新规格。
- 剪枝**永远正确**：查询 `ts` 谓词时，规划器按各文件的 spec 分别反构——days 文件按天范围、
  hours 文件按小时范围。这就是「隐藏」二字的含金量：布局异质，接口同构。
- 代价：新旧规格并存期间，单个分区的文件可能散在多种目录形态；想要统一物理布局
  才需要 `rewrite_data_files` 主动重排（06 章）。

### 5.5 演化与读写的耦合点

- **并发写者 + schema 变更**：提交冲突会因「基线快照过期」触发重试；长时间运行的批任务
  与 `ALTER TABLE` 赛跑时，重试可能撞上「列被改名」——V2 提交按列 ID 校验，一般能自动收敛，
  但**下游 DataFrame 的 select 列名要同步更新**，这是唯一需要人管的部分。
- **分区列参与 schema 演化的限制**：identity 分区的列改名安全（按 ID），但**不建议**对参与
  分区的列做 DROP/类型变更后再演化分区——规划器表达式反构会失去依据。
- **多引擎**：Iceberg schema/分区演化的元数据对 Flink/Trino 同义；Spark 侧改完不需要通知别人，
  这正是 catalog 独立于引擎的收益（02 章 2.4）。

## 版本与兼容性

- `AFTER/FIRST`、RENAME、类型提升在 Spark 3.1 + Iceberg 0.11+ 时代即完整；本能力是 Iceberg 最早期的卖点。
- `REPLACE PARTITION FIELD` 语法自 Spark 3.1；`EXPAND PARTITION FIELD` 稍晚。
- 删除列上的「字段 ID 回收」：Iceberg 不回收 ID（防止旧文件语义漂移），规范级决定。
- Spark 4.x 的 V2 write with schema changes（写侧自动加列）规范仍在演进，生产使用前按所用版本
  的 release notes 复核（⚠️ 本目录未逐版核实该开关名）。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「改名/重排要重写 Parquet」 | 列 ID 解析，纯元数据；这正是与 Hive SerDe 模式的分水岭 |
| 「分区演化会搬迁历史数据」 | 不会；新旧 spec 共存，剪枝各自反构。搬迁是另一件事（compaction 带 `where`） |
| 「有了隐藏分区不需要看 EXPLAIN」 | 谓词不落在分区 transform 上（如对 `ts` 用函数包裹 `date_format(ts)`）剪枝照样失效 |
| 「UPDATE SET user_id TYPE INT 也行」 | 提升有白名单；降级/跨域必须加列+回填三步走 |
| 演化后直接 `SELECT dt` | 表里从来就没有 `dt` 列；目录名是 Iceberg 私有布局，别拿去写查询 |
| 「DROP COLUMN 会释放存储」 | 文件里列还在，直到该文件被重写/过期；存储账单看 `all_data_files` |
