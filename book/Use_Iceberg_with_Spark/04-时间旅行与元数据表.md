## 核心精讲

> 以下 SQL 均为**教学示意，不参与构建**。

### 4.1 快照模型回顾

Iceberg 表根元数据 `v<N>.metadata.json` 里维护：当前快照指针 + 快照历史。每次 INSERT/MERGE/ALTER
产生一个新快照，指向一份完整的 manifest list。所谓时间旅行，就是**把查询计划的文件清单
换成历史快照的清单**——数据文件从未动过，变的只是解析入口。这解释了它为什么零成本、跨引擎一致。

### 4.2 全表时间旅行

```sql
-- 按快照 ID（官方文档示例形态）
SELECT * FROM wh.demo.orders VERSION AS OF 10963874102873;

-- 按提交时间
SELECT * FROM wh.demo.orders TIMESTAMP AS OF '2025-01-31 23:59:00';

-- 等价通用语法（带分支时更常见）
SELECT * FROM wh.demo.orders FOR SYSTEM_VERSION AS OF 10963874102873;
```

快照 ID 哪里来？下一条的元数据表。

### 4.3 分支与标签旅行

Iceberg ≥1.4 引入 Git 式分支/标签（需要 02 章 extensions）：

```sql
-- 教学示意
CALL wh.system.create_branch('demo.orders', 'audit-branch', snapshot_id => 10963874102873);
CALL wh.system.create_tag('demo.orders', 'v2025-q1', snapshot_id => 10963874102873);

SELECT * FROM wh.demo.orders VERSION AS OF 'audit-branch';   -- 分支当「版本名」查
SELECT * FROM wh.demo.orders VERSION AS OF 'v2025-q1';       -- 标签常用于季度口径固化
```

### 4.4 元数据表全家福

| 元数据表 | 内容 | 典型用途 |
| --- | --- | --- |
| `tbl.history` | 快照变更序列（version, timestamp, operation, is_current） | 找事故时间点、旅行锚点 |
| `tbl.snapshots` | 全部快照（id, parent_id, sequence, summary 含增删行数/文件数） | 旅行 ID 来源、写入体量监控 |
| `tbl.manifests` | 当前快照的 manifest 文件清单（分区范围、序列号） | 元数据膨胀诊断 |
| `tbl.files` | 当前快照的数据文件明细（record_count、大小、分区值、content 类型：含 data/delete 文件） | 小文件与倾斜盘点 |
| `tbl.partitions` | 按分区规格聚合的统计（行数、大小） | 「哪个分区在疯长」一页看清 |
| `all_data_files` / `all_delete_files` / `all_manifests` / `all_entries` | **跨所有快照**的同构视图 | 存储账单、孤儿分析、清理前评估 |

```sql
-- 教学示意：最近 5 次提交都干了什么
SELECT snapshot_id, parent_id, timestamp_of_snapshot, operation,
       summary['added-data-files'] AS added, summary['deleted-data-files'] AS deleted
FROM wh.demo.orders.snapshots ORDER BY snapshot_id DESC LIMIT 5;

-- 元数据表本身也可以时间旅行
SELECT * FROM wh.demo.orders.manifests TIMESTAMP AS OF '2025-09-20 08:00:00';
SELECT * FROM wh.demo.orders.partitions VERSION AS OF 10963874102873;
```

### 4.5 增量读取（读两个快照之间的变更）

官方文档明确：**Spark SQL 语法不支持增量读取**，走 DataFrameReader 选项（核对自 spark-queries.md）：

```scala
// 教学示意：读取 start（不含）到 end（含）之间新增的数据
spark.read
  .format("iceberg")
  .option("start-snapshot-id", "10963874102873")   // exclusive
  .option("end-snapshot-id", "63874143573109")     // inclusive
  .load("wh.demo.orders")                          // 也可 load 表名（catalog 已配置时）
```

限制与提醒（文档原话口径）：

- 目前增量读只取 **append 操作**产生的数据；对 replace/overwrite/delete 类快照不支持——
  所以它适合「上游保证纯追加」的镜像表拉取，不是通用 CDC 方案（通用方案用 03 章 MERGE）。
- 新版还提供 `start-tag`/`end-tag`、`included-snapshot-ids` 等选项（以当前版本文档为准）。
- 区间内快照若被 `expire_snapshots` 过期，增量读直接失败——旅行窗口是这里的硬前提。

### 4.6 回滚与恢复

```sql
-- 把表的当前指针切回旧快照（元数据操作，秒级；不删任何文件）
CALL wh.system.rollback_to_snapshot('demo.orders', 10963874102873);

-- 或直接改属性
ALTER TABLE wh.demo.orders SET TBLPROPERTIES 'current-snapshot-id' = 10963874102873;

-- 延长旅行窗口：控制历史过期（单位：天）
ALTER TABLE wh.demo.orders SET TBLPROPERTIES 'history-expire-days' = 30;
```

**回滚 ≠ 找回文件**：若目标快照之后跑过 `expire_snapshots`，被物理清除的文件回滚也救不回。
旅行窗口是运维承诺（见 06 章 expire 策略），不是规范保证。

### 4.7 实战场景

- **误删恢复**：`DELETE` 误伤 → `history` 定位事故前快照 → `rollback_to_snapshot` →
  用 `INSERT INTO 现表 SELECT * FROM 旧快照 WHERE 缺失条件` 精补。
- **A/B 对数**：口径改造前后，`VERSION AS OF 'v2025-q1'` 与当前表各跑一遍聚合，差异可归因。
- **审计取证**：`snapshots.summary` + `all_data_files` 可回答「何时提交、动了哪些分区文件」；
  「谁」需要作业侧在快照 summary 里自定义打点（`SET` 作业标签/写入参数，命名空间自定义）。

## 版本与兼容性

- 基础 `VERSION/TIMESTAMP AS OF`：Spark 侧 DataSource V2 标准语法 + Iceberg 支持已久；
  **分支名旅行、`FOR SYSTEM_VERSION`** 依赖 `IcebergSparkSessionExtensions`。
- 分支/标签：Iceberg 1.4（2023）起进入主干。
- 增量读取语法经历过 `START ... END ...` → `BETWEEN` 措辞统一，跨旧版脚本要复核。
- `history-expire-days`、`write.metadata.delete-after-commit.enabled` 等属性名稳定，但
  expire 相关行为在 1.6+ 有增强（如 `remove_orphan_files` 与 expire 的协同），细节以当前文档为准。

## 常见误区

| 误区 | 事实 |
| --- | --- |
| 「时间旅行不需要 extensions」 | 基础形态不需要，但分支旅行/部分增强语法需要；报「Unsupported statement」先查 02 章配置 |
| 「旅行窗口 = 无限」 | 快照被 expire 后不可旅行；窗口长短由 `history-expire-days`/调度决定 |
| 把 `tbl.files` 当全量文件账 | 它只列**当前快照**；跨快照要用 `all_data_files` 并自行去重 |
| `rollback_to_snapshot` 后再也不 expire 旧快照 | 回滚只动指针，不影响 GC 策略；二者独立调度 |
| 用时间旅行做长期备份 | 快照链在同一个 catalog/存储体系内；跨region 灾备靠复制（如策略性 backup，非本能力） |
| 以为 TIMESTAMP AS OF 精确到行 | 它定位的是「该时刻最新的已提交快照」，粒度=提交 |
