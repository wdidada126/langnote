# 08 Backup, Recovery, and Moving Data（备份、恢复与数据迁移）

> 原书第 8 章章名 ✅ Crossref 实抓；小节结构为推定重构 ⚠️（⚠️ 全章文档转述，无实机演练）。
> 基线 Cassandra 3.x；文件布局与工具名以同期官方文档域为参照。

## 题纲

Cassandra 的备份哲学从 05 章"不可变 SSTable+hard link 快照"推出：**备份=给数据目录拍
一致性快照+管好 commitlog，恢复=把文件放回去再让环认账**。本章三块：快照/恢复剧本、
sstable 工具族、跨集群搬运（sstableloader/COPY/跨 DC 迁移）。

## 1. 快照（snapshot）

```bash
nodetool -h n1 snapshot --tag before_schema_change -ks app -cf events
# 落到 <data_dir>/<ks>/<tbl>/snapshots/before_schema_change/
```

- 本质：flush memtable → 对 SSTable **hard link**，几乎零空间/零拷贝；不备份 commitlog
  （快照点后的写不在内，见 §3）。
- 运维纪律：快照目录**不能长期留着**（锁住旧文件阻碍压缩回收）；
  外拷用 `rsync/tar`，回收后 `nodetool clearsnapshot`。
- 一致性语义：跨副本无全局一致点——快照是**每节点视角**的备份，恢复按"节点"为单位（§2）。

## 2. 单机恢复剧本（⚠️ 转述的标准流程）

1. 停节点；清干净数据目录（或换新机走 replace，03 章）。
2. 快照文件回放到 `<data_dir>/<ks>/<tbl>/`（权限/属主核对）。
3. 决定 commitlog 是否回放：全留（回放）或全弃（丢快照点后增量）。
4. 启动 → `nodetool describecluster/status` → 对该节点跑一次 **repair**（防环上分歧固化）。
- 恢复后必查：schema 版本一致、hinted handoff 队列、该节点负载与邻居对齐（10 章指标）。

## 3. commitlog 与"增量"

- commitlog 是本地恢复材料（05 章），不是复制介质：**跨节点回放不支持**——
  别指望 binlog 式 PITR；3.x 的"增量备份"≈定时快照+（如启用）commitlog 归档
  （commitlog_archiving.properties，主要服务 CDC 消费 ⚠️ 通述）。
- PITR 的正解在应用侧：双写窗口/TTL 重放/把重放责任交给幂等建模（04 章 upsert 特性在这里兑现）。

## 4. sstable 工具族（手改文件的"合法异端"）

| 工具 | 用途 | 运维注记 |
|---|---|---|
| `sstableloader` | 把 SSTable 经 CQL 协议 bulk 载入集群 | 按 RF 现算路由，跨版本/跨集群搬数据主力 |
| `nodetool scrub` | 重写损坏 SSTable、可跳损坏分区 | 数据"腐化"急救（`-s` 跳过模式 ⚠️ 通述） |
| `nodetool verify` | 文件级校验（防篡改/防坏盘） | 报警→verify→scrub 链 |
| `nodetool rebuild_index` | 索引重建（2i 损坏/搬文件后） | 与快照恢复常配套 |
| `sstableupgrade` | major 升级后重写旧格式 SSTable | 3.x→4.x 路线的必做收尾 |
| `sstablesplit` / `sstablerewrite` | 大文件切分 / 按新 snitch 重写 | 运维手术刀，动前先快照 |

- 共同纪律：**任何直接摆弄数据目录的动作都先快照、后 repair**（§2 剧本的镜像使用）。

## 5. 跨集群/跨 DC 搬数据

- 小批量：cqlsh COPY（02 章量级红线）。
- 大批量：源集群快照 → sstableloader 到目标（可异环、异 RF；走 9042，吃目标写预算，11 章流控）。
- TB 级：Spark bulk output 直产 SSTable（07 章）再 loader 进环。
- DC 级迁移/下线：加新 DC→`rebuild`→应用双写切流→老 DC 逐节点 decommission（03 章剧本组合 ⚠️ 转述）。
- 多租户/拆表合并类需求：Cassandra 没有 `INSERT INTO ... SELECT` 跨表拷贝——一切靠导出-重塑-装载。

## 6. 灾难恢复分级（本章的"预案"落点）

| 级别 | 场景 | 手段 | RPO 直觉 ⚠️ |
|---|---|---|---|
| L1 | 单节点坏盘 | replace + 邻副本自动补齐 | ~0（RF 内冗余） |
| L2 | 误删表/行 | 快照恢复单节点+replace 语义+repair | 快照间隔 |
| L3 | 整 DC 毁 | 另一 DC 承接流量（03 章多 DC 是本预案的前提） | ~0（若 EACH_QUORUM） |
| L4 | 全环逻辑腐化（坏 schema/坏发布） | 全体快照回滚=最昂贵剧本：逐节点回+版本 pin | 快照间隔 |

## 7. 备份/搬运命令卡（⚠️ 转述）

```bash
# 快照三件套
nodetool snapshot -ks app --tag d1
ls /var/lib/cassandra/data/app/events-*/snapshots/d1
nodetool clearsnapshot --tag d1
# 恢复前置：停服→文件归位→权限→启动→repair（§2 剧本的命令行形态）
rsync -aH snapshots/d1/ /var/lib/cassandra/data/app/events-<id>/   # ⚠️ 细节以文档为准
# 工具族速记
sstableloader -d n1,n2 /path/to/sstables          # 跨环装载（9042，流控见 11 章）
nodetool scrub app events                         # 腐化急救
nodetool rebuild_index app events                 # 2i 对齐手术
sstableupgrade <ks> <tbl>                         # major 升级收尾（4.0+ 语境见文末）
# cqlsh 小搬运
COPY app.events FROM 'e.csv' WITH DELIMITER=',' AND HEADER=TRUE;   # 万行红线（02 章）
```

## 核心概念速览（中英对照）

- **snapshot (nodetool)** — 快照：flush 后 hard link SSTable 的节点级一致点。
- **hard link** — 硬链接：零拷贝备份的实现底座。
- **clearsnapshot** — 清快照：回收旧链接，防压缩回收被锁。
- **commitlog replay** — 提交日志回放：本地崩溃恢复材料，非跨节点增量通道。
- **commitlog archiving** — 提交日志归档：面向 CDC 消费者的旁路流。
- **sstableloader** — 批量装载器：经原生协议按 RF 重路由导入 SSTable。
- **scrub** — 数据清洗：重写损坏文件，可选跳过损坏分区。
- **verify** — 校验：文件完整性体检，腐化告警后的第一查。
- **rebuild_index** — 索引重建：2i 与数据漂移后的对齐手术。
- **sstableupgrade** — 格式升级：major 版本后重写历史 SSTable。
- **PITR** — 时间点恢复：Cassandra 无原生全局 PITR，靠幂等建模与预案弥补。
- **replace semantics** — 顶替语义：恢复即换身份，token 遗产接管（03 章）。
- **DC failover** — 数据中心切换：备份的最高形态是多 DC 冗余而非冷文件。

## 最新演进与工业实践

- **增量快照转正（⚠️ 通述）**：4.0+ 的"增量快照"（保留上次快照以来新 SSTable 拷贝语义）
  进入文档体系，5.0 文档树含 Backups 专页（✅ 导航实抓）——本书"定时全快照"的 RPO 焦虑部分缓解。
- **CDC v2（✅ 5.0 文档树 CDC 专页在档）**：change data capture 的 4.x/5.0 重设计把
  commitlog 变成可消费的变更流（写 cdc_raw/、消费者外部提交位点），
  是 Cassandra 向"类 binlog 下游"的正式让步——但 PITR 仍需自建（速览条目的边界不变）。
- **格式代际红线（✅ NEWS.txt 实抓）**："Cassandra 4.0 removed support for any pre-3.0 format"——
  2.x 时代的历史 SSTable 无法直升 4.x/5.x；3.x→4.x 的 sstableupgrade 是迁移合同的一部分。
- **对象存储备份生态**：2026 年工业实践常见"快照→S3 兼容存储+按 DC 编排"的外部工具化
  （如各托管平台/开源备份工具）⚠️ 具体工具名与能力未逐一实证，仅给趋势口径。
