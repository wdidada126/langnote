# 第 22 章 开发者测试

> **一句话**：开发者测试的全部价值在于「把正确性检查从最后一道工序挪到每一步」——它是对作者自己的代码最便宜的第一道防线。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 22.1 开发者测试在软件质量中的角色 | 测试人员 vs 开发者的分工；测试不是「别人负责的收尾」 | 大部分缺陷在开发者测试阶段被发现，且成本最低 |
| 22.2 推荐的测试方法 | 单元测试、集成测试、回归测试、系统测试、验收测试 | 五类互补：各自回答不同的失败问题 |
| 22.2 补充：测试驱动开发（TDD）与测试优先 | 先写失败测试再实现 | 第 2 版对它只有简介；它后来成为主流 |
| 22.3 测试技巧锦囊 | 数据界定、等价类划分、边界测试、猜测猜测再猜测、覆盖导向 | 生成测试用例的系统方法 |
| 22.4 典型错误 | 过多测试非功能行为、测试冗余、不可测的代码 | 「测试什么」比「测多少」重要 |
| 22.5 测试支持工具 | 断言、测试框架、mock、覆盖率、UI 工具 | 工具降低测试成本，但不能制造可测性 |
| 22.6 改善测试过程 | 保留测试记录、回归测试制度化 | 回归测试套件是长期资产 |
| 22.7 保留测试记录 | 缺陷记录与测试记录 | 数据驱动的过程改进 |

## 核心精讲

五类测试的分工（教学示意，不参与构建）：

```text
[伪代码] 测试类别与「它能回答的问题」
类别          对象            回答的问题                失败时的现象
------------ ----------------|-------------------------|------------------
单元测试      单个单元/类      「这个单元对不对」        单点失败，定位快
集成测试      若干单元的协作   「它们接起来对不对」        连接处数据不匹配
回归测试      已修复的缺陷     「有没有旧病复发」          已知场景的失败
系统测试      整个系统         「端到端行为对不对」        跨层/跨服务的失败
验收测试      用户需求         「交付的东西是不是要的」     需求漂移
```

> **教学示意，不参与构建、不编译、不运行。**

黑盒测试的两个经典手法（教学示意，不参与构建）：

```text
[伪代码] 生成测试用例的系统方法
1 数据界定 + 等价类划分
   输入域划分为若干等价类；每个类取代表值 + 边界值
   例：输入 1~100 的整数 -> {0, 1, 2, 99, 100, 101} 即可覆盖主要风险
2 猜测-测试-再猜测（error guessing）
   基于经验列出「这里最容易错什么」，直接写针对该点的用例
   常见猜测点：空集合、单元素、极大/极小、重复键、并发、时区、负数
3 覆盖导向
   语句覆盖 << 分支覆盖 < 条件覆盖 < 路径覆盖
   实用折中：分支覆盖 + 对关键分支做条件覆盖
```

> **教学示意，不参与构建、不编译、不运行。**

可测性的反面（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：不可测——依赖全局状态、依赖真实时钟、副作用混在查询里
class Report {
    double total() {
        return db.queryAll().stream()          // 依赖全局 db
            .filter(x -> today().after(x.date()))  // 依赖系统时钟
            .mapToDouble(x -> x.amount)
            .sum();
    }
}

// 正例：依赖显式化，测试可以直接构造输入
class Report {
    private final Clock clock;                  // 时间可注入
    Report(Clock clock) { this.clock = clock; }
    double total(Collection<Record> rows) {     // 数据可构造，无全局依赖
        return rows.stream()
            .filter(r -> clock.instant().isAfter(r.date()))
            .mapToDouble(Record::amount).sum();
    }
}
```

> **教学示意，不参与构建。**

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 把覆盖率当成质量目标 | 覆盖率证明跑过，不证明断言正确 | 用突变测试 / 断言强度作为补充指标 |
| 2 | 测试「所有可能的输入」 | 不可能也不必要 | 等价类 + 边界 + 错误猜测 |
| 3 | 测完就不管，测试随代码腐化 | 未通过时随手改成跳过，套件就废了 | 未通过的测试必须当天修好，或立即删除 |
| 4 | 为「可测」而给每个类加注入点 | 过度设计 | 只在真正的耦合点解耦（时钟、随机源、外部 IO） |
| 🔧 | 第 2 章/第 22 章对「测试优先」只有简介 | 2004 年 TDD 刚起步，书里未体系展开 | 结合 Beck 的 TDD 与「红—绿—重构」节奏理解；把「先写失败测试」作为默认习惯 |
| 🔧 | 第 2 版的测试技术锦囊偏手工推理 | 现代有大量支持工具（property-based testing、fuzzing） | 补充：属性测试用「性质」替代「样例」；fuzzing 专攻崩溃类缺陷 |
| 🔧 | 第 2 版假设测试由开发者写完就完成 | AI 生成代码后可以「反向用测试检查模型的假设」 | 补充：把「这段生成代码的前提假设」写成断言，是 AI 时代最有效的测试用法 |

# 第 23 章 调试

> **一句话**：调试的前 90% 时间花在「定位」而不是「修正」——修正只需一行，定位需要一套与心理偏见对抗的方法。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 23.1 调试概述 | 调试是「假说—检验」循环；调试中的心理因素 | 调试是科学方法的小规模应用，因此要对抗直觉 |
| 23.2 寻找缺陷 | 假设优先、二分法、仪器化、重现 | 定位缺陷的顺序决定调试时长 |
| 23.3 修正缺陷 | 修正前先复现、一次改一处、检查是否同源 | 「修好了」不等于「修对了」 |
| 23.4 调试中的心理因素 | 确认偏误、归因错误、对旧代码的假设 | 心理因素是调试失败的主因，不是技术 |
| 23.5 调试工具 | 日志、断点、监视、内存/性能剖析、运行时可视化 | 工具选择取决于你处在「哪一步不确定」 |

## 核心精讲

调试的假说—检验循环（教学示意，不参与构建）：

```text
[伪代码] 调试的标准循环（每一步都要留下可复核的记录）
1 稳定重现：把「偶尔失败」变成「必然失败」（否则无法验证修复）
2 定位数据入口：最近一次改动 / 最上层怀疑点
3 形成假说：某某输入 + 某某路径 -> 某某状态错误
4 设计检验：这个假说若成立，一定还会在别处露出痕迹（副作用预测）
5 检验：只做能区分「这个假说 vs 其他假说」的实验
6 修正：改一处，且保证修正后所有原有测试仍通过
7 复盘：为什么当初会写出这个缺陷？能否用一条检查拦住？
```

> **教学示意，不参与构建、不编译、不运行。**

定位策略的选择（教学示意，不参与构建）：

```text
[伪代码] 定位缺陷时最常见的三种策略
(a) 从「最近的改动」倒推    成本最低，但只在「缺陷由改动引入」时有效
(b) 从「症状」二分搜索      通用，但要求你能构造稳定的中间状态（可观测/可插桩）
(c) 从「领域原理」正向推导  适合「看起来不可能」的缺陷；需要领域知识
原则：先用 (a)，无效立刻切 (b)；不要在同一个方向上重复三次同样失败的假设
```

> **教学示意，不参与构建、不编译、不运行。**

修正缺陷的纪律（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：修正时顺手「重构」了周围代码，于是新旧行为混在一起，回归无法归因
if (amount > 0) { deposit(amount); }      // 修 bug 时又改了参数顺序

// 正例：一次只改一件事；把可观察行为的变化与其他变化分离
if (amount > 0) { deposit(amount); }      // 只改判断条件，其余保持原状
// 结构调整（参数顺序、抽取）放在独立的提交里
```

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 直接改症状试图「让它跑起来」 | 常见缺陷有多个症状，改一处会在别处爆 | 先定位到根因，一次只改一处 |
| 2 | 相信「这段代码一直是对的」 | 作者的记忆和注释都不可靠 | 用可观测性（日志/断点）验证，而不是回忆 |
| 3 | 反复试同一个改法三次以上 | 说明假说不成立，应该换策略 | 强制切换到二分/正向推导 |
| 4 | 修 bug 时顺手重构 | 让回归无法归因 | 分离「修行为」与「改结构」两个提交 |
| 🔧 | 第 2 版对「调试是科学方法」的表述缺少与认知科学的连接 | 23.4 点到为止 | 补充：显式对抗确认偏误——每次实验前写下「我期望看到什么痕迹」 |
| 🔧 | 第 2 版的工具列表偏向 2004 年的单机调试 | 分布式、异步、AI 代码的新症状无法靠断点解决 | 补充：可观测性（结构化日志 + 追踪）优先于断点；AI 生成代码要先「质疑前提」再调试 |
| 🔧 | 第 2 版把并发调试几乎略过 | 2020 年代并发缺陷占比不低 | 补充：竞争条件检测（TSan 类工具）应作为并发代码的常规手段 |
