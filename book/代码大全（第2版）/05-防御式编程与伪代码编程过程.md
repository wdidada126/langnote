# 第 8 章 防御式编程

> **一句话**：防御式编程的全部意义在于把「错误的传播」截在边界上——让错误在数据进入的地方就变成本地事件，而不是系统级的意外。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 8.1 保护程序免受无效输入影响 | 「垃圾进，垃圾出」；输入校验的三种时机（接口/数据/文件） | 校验点越少越好，且必须**在所有**入口 |
| 8.2 断言 | 断言 vs 错误处理的区别、`assert` 的代价与收益 | 断言用于「绝不该发生」，错误处理用于「可能发生」 |
| 8.3 错误处理技术 | 返回中立值、换掉输入、用异常、断言分诊、处理坏数据的启发式 | 选错处理机制会让调用方被迫吞掉错误 |
| 8.4 异常 | 何时该抛、异常与「错误返回值」的成本对比、构造函数的坑 | 异常让代码更整洁，但也让调用方的正确性更难推理 |
| 8.5 隔离程序 | 用分类器把接口与实现隔开、把错误限制在最小区域 | 「一个类里的错误处理量 = 抽象泄漏的程度」 |

## 核心精讲

错误处理的五种手段及其适用域（教学示意，不参与构建）：

```text
[伪代码] 错误/异常的处理谱系

手段                 | 用于            | 对调用方的成本 | 可推理性
--------------------|---------------|---------------|---------
返回中立值(0/空/null)| 可恢复的常规失败 | 低            | 高
换掉输入(修正它)      | 可自动纠正的数据 | 低            | 高
返回错误码/Result     | 需要显式处理     | 中（易被忽略） | 中
抛出异常             | 程序无法继续     | 中（可能漏捕获）| 低（需看文档）
断言                 | 违反「不可能」   | 无            | 高（开发期）
```

> **教学示意，不参与构建、不编译、不运行。**

断言与异常的分诊示例（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
import java.util.Objects;

final class Grid {
    private final int width, height;
    private final int[] cells;

    Grid(int width, int height, int[] cells) {
        // 断言用于「调用方不该传」——是契约违反，不是数据错误
        assert width > 0 && height > 0 : "尺寸必须为正";
        // 异常用于「外部输入可能不合法」——是可恢复/可上报的事件
        Objects.requireNonNull(cells, "cells");
        if (cells.length != width * height) {
            throw new IllegalArgumentException("cells 长度与尺寸不匹配");
        }
        this.width = width; this.height = height; this.cells = cells;
    }

    int at(int x, int y) {
        if (x < 0 || y < 0 || x >= width || y >= height) {   // 边界校验
            throw new IndexOutOfBoundsException("x=" + x + " y=" + y);
        }
        return cells[y * width + x];
    }
}
```

> **教学示意，不参与构建。**

「隔离区」的形状——把错误处理密度降到最低：

```text
[伪代码] 用分类器隔离外部世界
外部世界(不可信) -> [Validator/Classifier] -> 内部(可信, 有契约) -> 业务 -> 出口
                     ^ 所有校验集中在这里，内部代码无需重复检查
收益：内部代码没有 try/catch 噪音；校验规则只有一处可改；安全性可审计
```

> **教学示意，不参与构建、不编译、不运行。**

## 近年研究与工业界开源实践（2015–2026）

趋势：**「错误必须被看见」从纪律变成类型**。非异常错误类型（`Optional`、`Result`、C++23 的 `std::expected`，Rust 的 `Result`）把「不处理错误」变成编译错误，这直接补强了 8.3/8.4 的弱点——因为 2004 年最大的问题是「错误码被静默忽略」。同时，schema-first 的接口设计把输入校验左移到契约层。

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 每个函数内部都做一遍输入校验 | 重复校验制造噪音与不一致 | 校验只在边界做一次（8.5 分类器） |
| 2 | 用断言处理「可能发生」的错误 | 断言在生产环境常被关闭，会静默放行 | 断言只用于契约违反；可恢复错误用异常或.Result |
| 3 | 构造函数里做可能失败的事 | 对象半构造后进入不一致状态（第 2 版已警告） | 构造只做赋值，失败逻辑放到初始化/工厂方法 |
| 4 | 把「抛异常」当成免费的干净错误处理 | 异常使控制流难以静态追踪 | 同一项目内统一策略，并在文档中声明函数是否抛异常 |
| 🔧 | 第 2 版 2004 年时「被忽略的错误码」不是主要问题 | 2020 年代 `Optional`/`Result`/`std::expected` 让它变成类型错误 | 补充：优先使用「必须显式处理的错误类型」，而不是靠人记得检查 |
| 🔧 | 对断言的成本/收益分析基于 2004 年的 CPU 假设 | 断言在部分语言里已可被编译器优化掉 | 补充：生产构建应保留 invariant 断言，或改用契约测试 |
| 🔧 | 未预见到 AI 生成代码更容易「跳过校验」 | 模型倾向于生成 Happy Path | 把「边界校验」明确列入 AI 代码审查清单的第一项 |
| 🔧 | 过度强调「防御」会被读作「到处加检查」 | 防御的成本被低估 | 区分「可信内部」与「不可信边界」，只在边界加厚 |

# 第 9 章 伪代码编程过程

> **一句话**：伪代码编程过程是把「设计」翻译成「代码」的**带护栏的推进法**——每一步都留下可核对的中间物，避免从想法直接跳到细节导致的返工。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 9.1 伪代码编程过程的步骤 | 分四步：确定用哪种伪代码、构思整体方案、为每个子程序写伪代码、编码 | 核心是「自上而下、一次只解决一类细节」 |
| 9.2 伪代码的写法 | 类似真实代码但忽略语言细节；用简洁的语句描述操作 | 伪代码是设计的表达，不是注释的草稿 |
| 9.3 逐步精化的例子 | 从高层到低层，每步只填一类细节（接口→数据→算法→异常） | 「一次只遇到一类复杂度」是它的真正价值 |
| 9.4 个体差异 | 有人适合一次性写完，有人适合逐步精化 | 没有普适的最佳方式，但逐步精化更可教学 |
| 9.5 与重构的关系 | 伪代码过程本身就是「重做一遍」的受控版本 | 它把重构的最大风险（改结构不改行为）提前化解 |

## 核心精讲

四步推进法的状态机（教学示意，不参与构建）：

```text
[伪代码] 伪代码 → 代码 的推进

Step 1  确定写法：决定用什么伪代码风格（缩进/伪关键字），全程保持一致
Step 2  构思方案：写下「子程序做什么、公开接口长什么样」，不碰内部
Step 3  写伪代码：对每个子程序写「做什么」级别的语句，用缩进表示控制流
Step 4  编码：逐块把伪代码替换成真实代码，每完成一块就跑一次

关键约束：Step 4 里「一次只填一类细节」——
        先签名与接口，再数据结构，再算法，最后错误处理
```

> **教学示意，不参与构建、不编译、不运行。**

逐步精化的示例：从一句说明到实现（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 目标：「把订单里已支付但未发货的条目挑出来，按金额降序返回」

// Step 3 的伪代码（先只表达意图，不表达语言细节）
//   result = empty list
//   for each item in order.items:
//       if item.paid and not item.shipped:
//           result.add(item)
//   sort result by amount descending
//   return result

// Step 4 的第一次落地：接口与结构骨架先就位，算法留空
Record OrderItem(Money amount, boolean paid, boolean shipped, Sku sku) {}
List<OrderItem> unpaidShipped(Order order) {
    List<OrderItem> selected = new ArrayList<>();
    for (OrderItem it : order.items()) {
        if (it.paid() && !it.shipped()) {   // 下一步才细化谓词来源
            selected.add(it);
        }
    }
    selected.sort(Comparator.comparing(OrderItem::amount).reversed());
    return selected;
}
```

> **教学示意，不参与构建。**

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 把伪代码当「注释的草稿」 | 那样它就退化成事后补写的无用文档 | 伪代码是设计的表达，在编码之前完成 |
| 2 | 一次性把所有细节都填完再跑 | 违背逐步精化的初衷 | 每块填完即验证，控制「一次遇到的复杂度种类」 |
| 3 | 认为伪代码过程慢 | 它的成本在前期，收益在返工减少 | 用「缺陷在后期发现的成本」折算它的 ROI |
| 4 | 用一套伪代码风格混写所有子程序 | 风格不一致会让伪代码失去可核对性 | 全项目统一伪代码写法 |
| 🔧 | 第 2 版未把「测试优先」与逐步精化明确衔接（2004 年两股潮流刚交汇） | 今天它们本应是同一个节奏 | 补充：每精化一块，先写它的失败测试再实现 |
| 🔧 | 对个体差异的处理偏温和，未给出选择依据 | 教学场景下「逐步精化」几乎总是更优 | 补充：新手用逐步精化，老手按问题规模选择一次性写法 |
| 🔧 | AI 辅助编码下伪代码过程的「中间物」定义失效 | 生成代码跳过了显式中间步骤 | 把「意图说明 + 边界情形清单」作为新的中间物，生成后逐条核对 |
