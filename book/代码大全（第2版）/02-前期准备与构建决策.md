# 第 3 章 谋定而后动：前期准备

> **一句话**：前期准备不是「先写需求文档再写代码」这种仪式，而是**在动手之前把三类不确定性尽量收敛成可判定的形式**——问题是什么、要做什么、怎么做。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 3.1 前期准备的重要性 | 准备不周的诱因、序列式与迭代式的取舍 | 迭代不等于不准备；迭代把准备变成「可回归的准备」 |
| 3.2 确定软件类型 | 三类软件： personnel（人员问题）、commercial（商业）、system/mission-critical（系统/任务关键） | 不同类型的软件在准备深度上完全不同，用错模板会浪费一半预算 |
| 3.3 定义问题的先决条件 | 问题定义 vs 需求分析的区别 | 问题定义关注「为什么」，需求关注「有什么」 |
| 3.4 需求的先决条件 | 为什么要有正式需求、稳定需求的神话、构建期间如何处理变更 | 需求变更不是异常，是常态；关键是建立变更的代价感知 |
| 3.5 架构的先决条件 | 架构的典型组成部分 | 架构不是本书主题，但它是构造阶段的「上游约束」 |
| 3.6 花费的时间 | 准备应占用的时间比例 | 迭代式项目准备时间占比低，但**准备次数多** |

## 核心精讲

三类软件的差异，直接决定准备深度（教学示意，不参与构建）：

```text
[伪代码] 软件类型 → 准备深度矩阵

类型                | 需求变更容忍 | 必须 formal 的需求 | 架构必须先定 | 典型准备占比
-------------------|--------------|-------------------|--------------|--------------
personnel(人员系统) | 高           | 否                 | 否           | 低
commercial(商业系统)| 中           | 部分               | 部分         | 中
system/mission-crit.| 低           | 是                 | 是           | 高

推论：对 personnel 类系统做重型准备，是纯粹的浪费
推论：对 mission-critical 类系统做轻量准备，是事故的前置条件
```

> **教学示意，不参与构建、不编译、不运行。**

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 把迭代理解成「准备可以省略」 | 迭代把准备碎片化，但不消除准备 | 每个迭代开始前的验收口径必须明确 |
| 2 | 追求「稳定的需求」当作目标 | 作者本人就否定这个神话 | 转而追求「变更可评估、可排序、可拒绝」 |

| 🔧 | 未涉及需求的可执行化与 API 契约优先（OpenAPI/gRPC） | 2004 年时这些还不是通用实践 | 补充：接口契约先于实现编码，能显著降低 3.3/3.4 的不确定性 |

# 第 4 章 关键的构建决策

> **一句话**：语言选错、约定不成文、实践不挑，这三件事一旦定错，后面每一章的技巧都会被抵消掉一部分。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 4.1 选择编程语言 | 语言特性如何限制表达力；语言决定「你必须写多少样板」 | 换语言的代价远高于学好一门语言；但不要用语言当借口 |
| 4.2 编程约定 | 编码约定、注释约定、文件组织 | 约定不能是「美观偏好」，必须解决可预测性问题 |
| 4.3 技术浪潮中的位置 | 「深入一种语言去编程」、波浪式技术演进 | 判断你所在语言的阶段，决定「要不要等下一代」 |
| 4.4 选择重要的构建实践 | 挑出对你的项目真正有效的少量实践，而不是全盘照搬 | 列出的实践清单是本书的浓缩版；关键是少而狠 |

## 核心精讲

「重要的构建实践」清单（本章最可直接照抄的交付物，本节以要点形式给出）：

```text
[伪代码] 关键构建实践清单（按收益/成本排序）
1. 前期准备：定义问题、商定需求、定架构轮廓
2. 设计：用 ADT/类的层次做设计，保持信息隐藏
3. 编码：命名精确、控制结构简化、注释解释「为什么」
4. 个人实践：先写测试（测试优先）、小步重构
5. 协作：结对或评审、每日构建
6. 质量注入：静态分析 + 单元测试 + 回归
7. 调整：先测量再优化（Ch25）

选择原则：不要一次引入全部。挑 4~6 项，坚持到变成肌肉记忆。
```

> **教学示意，不参与构建、不编译、不运行。**

语言选择对表达力的约束（教学示意）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 同一个意图在不同语言下的「样板成本」差异：
// Java 需要显式接口 + 实现；Python/JS 可能一行；
// C++ 需要区分头文件声明与定义、注意值/引用/指针语义。
// 本节不比较优劣，只说明：语言决定了你必须人为处理哪些复杂度。

interface Price { int cents(); }
record Money(int cents) implements Price { }   // 现代 Java 的紧凑写法
```

> **教学示意，不参与构建。**

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 「语言的选择无关紧要，重要的是程序员」 | 部分对，但语言确实决定你必须显式处理哪些复杂度 | 区分「语言限制表达力」与「语言限制错误率」两件事 |
| 2 | 把编码约定当成风格指南 | 好约定解决「可预测性」，不是美观 | 检验：一个新人能否**预测**别人代码的格式？ |
| 3 | 一次全量引入所有构建实践 | 作者明确警告过「实践过敏」 | 按 4~6 项小步引入，逐项固化 |
| 🔧 | 第 2 版的「技术浪潮位置」模型只覆盖 2004 年前的波浪 | 云原生、AI 是两道新的浪 | 补充判断维度：生态成熟度、可招聘性、审查友好度 |
| 🔧 | 对编程约定的期望值偏理想化（假设团队会遵守） | 2004 年靠自觉，AI 时代靠工具 | 把「约定」拆成「人自觉遵守」与「工具强制」两层，前者只留真规范 |
| 🔧 | 未预见到 AI 辅助编码会改变约定重心 | 生成代码风格不稳定，更易漂移 | 约定重心应从「格式」转到「语义与边界」：公开契约、错误处理、空值口径 |
