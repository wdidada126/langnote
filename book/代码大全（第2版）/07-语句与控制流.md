# 第 14 章 组织直线型代码

> **一句话**：直线型代码的顺序不是随机的——把「有依赖关系的语句挨在一起、把无依赖的语句排成可读的序列」，是最低成本的可读性改善。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 14.1 直线型代码的顺序 | 按依赖排序；顺序本身承载信息（如 C 的 IIFE） | 排序规则明确：依赖在前、相似在一起 |
| 14.2 把顺序问题变成词组 | 用「词汇化」表达语句块（如 Python 的 with） | 顺序若能压缩成一个概念，就压缩 |
| 14.3 直线型代码举例 | 几何函数、矩阵运算等 | 顺序错误是静默 bug 的主要来源 |
| 14.4 与子程序的关系 | 直线型代码的「最小完整语句集」 | 直线型代码应有明确边界，便于抽取为子程序 |

## 核心精讲

排序规则（教学示意，不参与构建）：

```text
[伪代码] 直线型代码的排序三原则
原则 1：按「谁依赖谁」排序 —— 被依赖的在前
原则 2：按「相似/同族」分组 —— 让一行能带出下一行
原则 3：把「执行顺序」与「数据顺序」区分开
        混乱的表现：int a = b * c;  // 与后续语句无依赖，却被要求排在特定位置
收益：把「必须按这个顺序做」编码进结构，而不是靠注释说明
```

> **教学示意，不参与构建、不编译、不运行。**

依赖顺序示例（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：顺序是任意的，靠注释「说明」为什么必须先算 avail
int avail = max - used;   // 注释：必须在 used 之前
int used = sum(items);

// 正例：直接让顺序体现依赖，注释降级为解释「为什么」
int used  = sum(items);          // 先算用量
int avail = max - used;          // 再算余量（依赖显式）
```

# 第 15 章 使用条件语句

> **一句话**：条件语句本身不是问题，**隐藏分支**才是——`if` 里做的所有事，调用方都要自己在脑子里重放一遍。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 15.1 if 语句 | 编码风格（先处理正常路径、if-else-if 链、case 语句） | 先写「简单的正常路径」，复杂分支放在后面 |
| 15.2 case 语句 | 按序排列 case、穷尽覆盖、避免落入下一个 case | case 的穷尽性要靠编译器检查 |
| 15.3 真/假判断 | 隐式布尔测试 vs 显式比较 | 显式比较能防拼写错误（如 if (a = b)） |
| 15.4 简化条件表达式 | 布尔变量替代深嵌套、用 Decision Table | 用「中间布尔量」把 4 层嵌套降到 1 层 |

## 核心精讲

嵌套降层（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：四层嵌套，读者必须记住前面的所有条件
if (order != null) {
    if (order.customer() != null) {
        if (order.customer().isActive()) {
            if (order.amount().isPositive()) { return true; }
        }
    }
}
return false;

// 正例：用「正向条件的中间量」把嵌套压平，读起来像 bullets
record Order(Customer customer, Money amount) {}
boolean canPlace(Order order) {
    return order.customer() != null
        && order.customer().isActive()
        && order.amount().isPositive();
}
```

> **教学示意，不参与构建。**

真/假判断与「隐藏分支」（教学示意，不参与构建）：

```text
[伪代码] 隐藏分支的四种形态
1. if (x) { ... }  // 若 x 是「表达式的一部分」而非独立事实，调用方需要自己推导
2. 短路求值里的副作用：if (flag && (line = read()) != null)
3. 三元/短路中的赋值：value = flag ? compute() : compute()   // 重复调用
4. 默认参数实现的隐式分支（Ch13.5）
对策：把条件拆成「有名字的事实」，用中间布尔量表达
```

# 第 16 章 控制循环

> **一句话**：循环是「会重复阅读的一行」——所以循环体本身越短，循环的名次就越容易读懂。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 16.1 循环的种类 | for/while/repeat-until/foreach | foreach 最不容易出错，for 最灵活 |
| 16.2 循环和迭代器的选择 | 何时用迭代器（如 C++ 的 iterator、Java 的 Iterable） | 让语言承担遍历，减少索引错误 |
| 16.3 控制循环的编码风格 | 括号、缩进、空语句、end-condition 表达 | 风格要点不多，关键一致 |
| 16.4 循环退出条件 | 尽量少的退出条件、统一退出顺序、把 end-condition 写正 | 一个循环多个出口 = 读者要记多处 |
| 16.5 循环体内的工作 | 尽量短、内嵌块、缩进 | 长循环体 = 该抽子程序 |
| 16.6 边界与下标 | 下标上下界写法、边界自检 | 边界错误是最经典的缺陷类型 |

## 核心精讲

循环体长度的判据（教学示意，不参与构建）：

```text
[伪代码] 循环的「一行定律」
好循环：循环体短的像句子 —— 集合上的一次变换
坏循环：循环体长到必须滚动屏幕 —— 它其实是一个「带索引的状态机」

判断步骤：
1. 循环体超过 5 行 -> 抽出「这一轮做什么」为子程序
2. 需要维护多个下标同步前进 -> 换成 zip/迭代器/查找表
3. 需要提前退出且有多种退出条件 -> 统一到一个退出点或改卫语句
4. 循环内含分支嵌套 -> 分支单独抽成谓词函数
```

> **教学示意，不参与构建、不编译、不运行。**

下标与边界（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：下标写出错、边界差一、循环里做太多事
for (int i = 0; i <= xs.length; i++) {      // <= 越界
    if (xs[i] > threshold) { sum += xs[i]; }
}

// 正例：用语言/库提供的遍历，边界由实现保证
int sum = 0;
for (int x : xs) {                          // 无下标，无边界
    if (x > threshold) { sum += x; }
}
```

> **教学示意，不参与构建。**

# 第 17 章 不常见的控制结构

> **一句话**：剩下的那些控制结构——递归、goto、短路、惰性求值——都不是「不能用」，而是「必须证明你真的需要它」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 17.1 递归 | 无限递归与栈溢出、递归的替代（迭代/队列） | 递归让某些问题自然，但让它有界是责任 |
| 17.2 goto 的害处 | 从 Dijkstra 到现代语言 | 「goto 的合法用途」比「goto 有害」的信息量小 |
| 17.3 短路求值 | 短路的收益与副作用风险 | 短路中不要放副作用 |
| 17.4 延迟表达式（lazy evaluation） | 惰性求值、懒汉初始化 | 惰性换来的性能，要用正确性来付 |
| 17.5 其他 | 异常处理作为控制流、协程与生成器 | 把异常当控制流会破坏可推理性 |

## 核心精讲

递归的「有界性证明」（教学示意，不参与构建）：

```text
[伪代码] 递归 vs 迭代的选择
选递归当且仅当：
  (a) 问题的定义天然递归（树/图/分治），且
  (b) 有明确的规模递减，且
  (c) 深度可控（不会因为数据形态而爆栈）

递归的代价：栈空间 + 隐含的「调用顺序」作为状态
对策：深度不确定时改用「队列 + while」的显式迭代（Trampoline）
```

> **教学示意，不参与构建、不编译、不运行。**

递归的迭代改写（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 递归形式：结构清晰，但深度受栈限制
static int sumTree(TreeNode n) {
    if (n == null) return 0;
    return n.value() + sumTree(n.left()) + sumTree(n.right());
}

// 迭代形式：用显式栈，深度不再受调用栈限制
static int sumTreeIterative(TreeNode root) {
    int sum = 0; Deque<TreeNode> stack = new ArrayDeque<>();
    stack.push(root);
    while (!stack.isEmpty()) {
        TreeNode n = stack.pop();
        if (n == null) continue;
        sum += n.value();
        stack.push(n.right()); stack.push(n.left());
    }
    return sum;
}
```

> **教学示意，不参与构建。**

goto 与异常作为控制流（教学示意，不参与构建）：

```text
[伪代码] 「非结构化」控制流的当代表述
goto            -> goto 已基本消失，但「跨函数跳转」以异常的形式复活
异常作控制流     -> 好处是跳过中间步骤；坏处是调用方无法静态看到控制流
对策（现代）：

  - 用「可返回的错误值」表达预期内的分支，异常只留真正的意外
```

# 第 18 章 表驱动法

> **一句话**：把「一串 if/else」变成「一张表 + 一次查表」，是这本书里投入产出比最高的招数之一。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 18.1 表驱动法的概念 | 逻辑复杂 → 查表 | 表是「数据与逻辑的分界线」 |
| 18.2 表驱动法的策略 | 直接拷贝、索引表、阶梯技术、查询表 | 按「键的取值方式」选策略 |
| 18.3 表的例子 | 错误处理表、测试用例表、业务规则表 | 新增一种情形只需加一行 |
| 18.4 表驱动法的好处 | 逻辑集中、易扩展、易测试 | 表本身也是测试资产 |

## 核心精讲

四种表的策略（教学示意，不参与构建）：

```text
[伪代码] 表驱动法的四种形态
1 直接拷贝(记载在案的表)：键 -> 值，一次查表得结果
2 索引表：键存在一张索引里，指向真正的处理表（处理表可以分块/分批）
3 阶梯技术(范围查表)：按区间分段，每段有上限值，适合「百分位/费率」
4 查询表：键 -> 某个行为（函数指针/枚举映射）

选择：键是离散小集合 -> 1/2；键是连续区间 -> 3；键要映射到动作 -> 4
```

> **教学示意，不参与构建、不编译、不运行。**

查表替 if 链（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：加一种错误类型要改 if 链；忘记改某处就是不一致
String message(int code) {
    if (code == 1) return "参数错误";
    if (code == 2) return "权限不足";
    if (code == 3) return "超时";
    return "未知错误";
}

// 正例：表驱动 —— 新增类型只需加一行，且可穷尽校验
enum ErrCode { BAD_PARAM, FORBIDDEN, TIMEOUT }
enum HttpStatus { BAD_REQUEST, FORBIDDEN, SERVICE_UNAVAILABLE }
record ErrorSpec(HttpStatus status, String msg) { }
Map<ErrCode, ErrorSpec> TABLE = Map.of(
    ErrCode.BAD_PARAM,    new ErrorSpec(HttpStatus.BAD_REQUEST, "参数错误"),
    ErrCode.FORBIDDEN,    new ErrorSpec(HttpStatus.FORBIDDEN,  "权限不足"),
    ErrCode.TIMEOUT,      new ErrorSpec(HttpStatus.SERVICE_UNAVAILABLE, "超时")
);
ErrorSpec describe(ErrCode code) {
    return TABLE.getOrDefault(code, new ErrorSpec(HttpStatus.INTERNAL_SERVER_ERROR, "未知错误"));
}
```

> **教学示意，不参与构建。**

阶梯技术（教学示意，不参与构建）：

```text
[伪代码] 阶梯技术：把「区间 -> 系数」变成一次查找
上限数组   [  0,  100,  500, 1000,  5000 ]   // 阶梯点
系数数组   [ 1.0, 0.9,  0.7,  0.5,  0.3  ]
思路：找到第一个「上限 >= 需求」的下标，取该下标处的系数
收益：新增一档只需在两个数组里各加一个元素，不改逻辑
```

# 第 19 章 常规控制问题

> **一句话**：控制流本身写对之后，剩下的敌人是「复杂度」——嵌套、布尔表达式、状态组合，它们决定你能否一眼看清一段代码。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 19.1 布尔表达式 | 用 true/false 而非 0/1、括号明确结合、用中间量减少判断、尽量用正逻辑 | 布尔表达式的可读性来自「命名 + 括号」 |
| 19.2 空语句 | 分号陷阱与空语句块 | 空语句几乎总是笔误 |
| 19.3 驯服危险的深层嵌套 | 用卫语句、立即返回、if-then-else 中的 then 且留 else、拆分、抽子程序 | 「少一层嵌套」优先于「少一行代码」 |
| 19.4 结构化编程 | 顺序、选择、重复三结构 | 三结构足够表达一切，因此嵌套是有成本的 |
| 19.5 控制结构与复杂度 | 复杂度 = 判断点的数量与分布 | 复杂度可测量，因此可管理 |

## 核心精讲

复杂度的度量与降层（教学示意，不参与构建）：

```text
[伪代码] 复杂度 ≈ 一条路径上有多少个「必须正确」的决策点
判断点：if / while / for / case / 三元 / && / || / catch
复杂度区间：
  1~3   可一眼看懂，无需拆分
  4~7   需要作者在脑子里记一层上下文（建议拆）
  8+    必须拆分；否则测试无法覆盖关键组合
```

> **教学示意，不参与构建、不编译、不运行。**

```java
// 教学示意代码，不参与构建、不编译、不运行
```

