# 第 20 章 软件质量概述

> **一句话**：质量不是「最后检查一遍」，而是**每种技术对应一类缺陷、且只对应一类**——先想清楚你要防哪种缺陷，再挑技术。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 20.1 软件质量的特性 | 11 类外部特性 + 内部特性：速度、平台、并发、健壮性、可测试性、可维护性、可移植性、可复用性、可读性、可修改性、可移植性…… | 质量目标之间的冲突是常态，取舍必须显式 |
| 20.2 改善软件质量的技术 | 低层技术（语言/命名/注释）与高层技术（评审/测试/度量） | 高层技术检测到低层技术无法发现的缺陷 |
| 20.3 不同质量保障技术的相对效能 | 各类技术的「能检出的缺陷类型」与「成本」 | 本章最实用的一节：选型表 |
| 20.4 什么时候进行质量保证工作 | 每个阶段注入的质量 | 「越早注入越便宜」，但高层技术必须独立存在 |
| 20.5 软件质量的一般原则 | 质量是首先目标、明确缺点、控制复杂度、保持一致性 | 质量优先于进度；质量是过程属性不是阶段属性 |

## 近年研究与工业界开源实践（2015–2026）

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 把质量当成「测试阶段」的事 | 测试只能发现缺陷，注入点在前头 | 质量是构造期的属性 |
| 2 | 用覆盖率作为质量指标 | 覆盖率证明「跑过」，不证明「断言了对」 | 用突变测试 / 断言强度评价测试质量 |
| 3 | 一旦进度紧急就砍质量技术 | 这几乎必然导致后续返工 | 砍的是「非默认」的技术，保留最核心的几项 |
| 4 | 追求「质量特性的全面高」 | 质量特性互相冲突 | 显式取舍并记录决策（ADR） |
| 🔧 | 第 2 版的效能矩阵缺少「突变测试」「AI 生成代码审查」两行 | 2004 年不存在这些技术 | 补充：突变测试补覆盖率之弱；AI 审查补评审之「常规缺陷」层 |
| 🔧 | 对「越早注入越便宜」的定量描述（1:10:100）是经验法则 | 被反复引用但缺少严格实验支撑 | 引用时标注为经验法则，用自家数据重新标定 |
| 🔧 | 第 2 版默认质量技术作用于「人写的代码」 | AI 生成代码的质量分布不同 | 补充：AI 产出需「更高密度的断言 + 更密的评审」，并单独度量其缺陷率 |

# 第 21 章 协同构建

> **一句话**：协同构建不是「多个人写同一份代码」，而是**用第二双眼睛抵消第一双眼睛看不到的问题**——所以它的收益高度依赖于协作方式，而不是人数。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 21.1 协同开发实践概要 | 协同的好处（文化/质量/进度/乐趣）与代价（沟通成本/一致性风险） | 协同不能替代标准化，它补充标准化 |
| 21.2 结对编程 | 两种角色（驾驶/领航）、收益、代价、适用条件 | 作者的结论偏乐观；现实中的证据比书里弱 |
| 21.3 正式检查 | 代码评审（Code Review）的分工与流程 | 正式检查擅长发现「设计层」缺陷 |
| 21.4 其他类型的协同开发实践 | 评审会议、程序走查、结对、轮换作者 | 轮换作者是最被低估的一条 |
| 21.5 协同构建技术的比较 | 各类技术的强度/成本对照 | 结论：交叉检查的强度与成本基本成正比 |

## 核心精讲

协同方式的强度—成本谱（教学示意，不参与构建）：

```text
[伪代码] 交叉检查方式的强度 vs 成本
方式            强度（检出率）   成本（相对）  擅长层次
-------------- ---------------- ------------ ----------
结对编程        高                高          逻辑+设计
正式评审/走查    高                中高        设计+需求
pair 轮换/内联评审 中高            中          上下文一致
在线评审(PR)     中                低          可读性+一致性
提交前钩子       中低              极低        风格+明显缺陷
自动化测试       专精              低(每运行)   回归与边界
```

> **教学示意，不参与构建、不编译、不运行。**

结对的两种角色与轮换节奏（教学示意，不参与构建）：

```text
[伪代码] 结对的两种角色
驾驶者 Driver：控制键盘，写实现，做局部决策
领航者 Navigator：主动审查，思考全局与下一步，记录待办

关键纪律：
- 角色必须定期轮换（否则领航者会退化成「看屏幕的人」）
- 领航者不打字，但必须持续读——这是结对与「一个人写另一个人看」的分界线
- 结对最适合「不确定的任务」；对机械性任务，两个人都知道答案 = 双倍成本
```

> **教学示意，不参与构建、不编译、不运行。**

「第二双眼睛」为什么有效（教学示意，不参与构建）：

```text
[伪代码] 协同构建的作用机理
1 认知多样性：作者的盲区不是能力问题，是「写的时候无法同时看到」
2 生产者在场：发现问题的那个人马上就能改，无需等下一轮
3 社会压力：代码会被同伴看到，显著降低「随手提交」的概率
4 知识分散：结对/轮换让系统知识不集中在一个人身上（bus factor）
```

> **教学示意，不参与构建、不编译、不运行。**

## 近年研究与工业界开源实践（2015–2026）

趋势：**结对编程被「异步化 + 自动化」分解**。机械部分由 linter/AI 承担，评审部分由在线 PR + 自动化检查承担，剩下的「高不确定性决策」才需要真人对结对。同时，「代码所有权共享」（trunk-based、short-lived branches）成为协同默认，减少了「作者唯一」的风险。

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 把结对当成「两个人同时写代码」 | 角色不清会让领航退化成看客 | 明确角色并定期轮换 |
| 2 | 认为结对必然提升质量与周期 | 作者的结论偏乐观，实证证据不一致 | 在高不确定性任务上采用，机械任务用自动化替代 |
| 3 | 认为评审只是「找 bug」 | 评审的主要价值在设计与意图层 | 评审清单里显式包含「这处抽象对不对」 |
| 4 | 多人协同即可替代标准化 | 协同发现的是「作者看不见的」，编码规范仍需统一 | 规范 + 自动化是前提，协同是补充 |
| 🔧 | 第 2 版对 pair programming 的收益证据评价**偏乐观** | 书里把质量提升与周期缩短列为常态结论；2015 年后的经验研究对其在规模化环境下的普适性提出质疑，推行阻力与人员匹配问题被低估 | 采用时应限定条件：任务不确定性高、两人能力相当、有轮换纪律；否则优先用「在线评审 + 自动化」 |
| 🔧 | 第 2 版写作于 PR 式在线评审之前，缺少「异步协同」的讨论 | 2004 年评审主要是正式走查 | 补充：异步评审（PR）成本更低、覆盖更广，但需要明确的审核清单与「小改动」纪律 |
| 🔧 | 未预见到 AI 辅助编码会替代 pair 的一部分工作 | Copilot 能即时给出建议 | 保留「领航」角色（审意图、看全局），把「驾驶」部分交给模型 |
