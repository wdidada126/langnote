# 第 10 章 变量使用中的常规问题

> **一句话**：变量的大部分问题不是「用错了」，而是「没声明清楚」——声明位置、作用域、存活期、绑定方式，这四件事决定你能不能可靠地推理一段代码。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 10.1 变量声明 | 声明位置、声明与定义的差别、初始化 | 「先声明后使用」不是形式主义，它是编译器的检查前提 |
| 10.2 变量的_register 与存活期 | 作用域、存活期、绑定与赋值 | 存活期越短，出错时需要的上下文就越少 |
| 10.3 变量的类型 | 显式类型与隐式类型的取舍 | 隐式类型方便但减少信息；现代语言普遍折中 |
| 10.4 类型和变量声明的坑 | 类型转换、类型降低、隐式转换的危险 | 「能自动转换的类型系统」会替你制造 bug |
| 10.5 变量命名 | 见 Ch11 | 本章只讲结构性约束（长度、作用域对应） |

## 核心精讲

作用域与「最小覆盖原则」（教学示意，不参与构建）：

```text
[伪代码] 变量的存活期 → 推理成本

全局变量  : 任何地方都能读改写 | 需要读全部代码才能确定它为何是这个值
模块级变量 : 需要在模块内读全部代码
局部变量  : 只需读所在子程序
循环变量  : 只需读所在循环
常量      : 只需读声明处

原则：把变量的作用域尽量推向「最小可用范围」
推论 1：变量的声明位置越靠近使用点，越不容易成为「遗留状态」
推论 2：能改成常量的地方就别让它可变（Ch6/Ch8 的不可变方向）
```

> **教学示意，不参与构建、不编译、不运行。**

初始化与「未定义行为」的防线（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：声明与初始化分离，中间存在「半就绪」窗口
int total;                 // 此刻 total 处于未定义状态
total = compute();         // 若 compute() 抛异常，后续依赖 total 的代码将读到脏值

// 正例：声明即初始化，不存在半就绪窗口
final int total = computeOrZero();   // final 让「赋值之后不可再改」成为事实

// 另一类经典问题：== 与 = 的混淆、浮点比较
boolean eq(double a, double b) { return Math.abs(a - b) < 1e-9; }  // 不要用 ==
```

> **教学示意，不参与构建。**

类型系统的「隐式转换」陷阱（教学示意，不参与构建）：

```text
[伪代码] 隐式转换的常见事故面
- 有符号/无符号混算：负数被当成巨大正数
- 整数溢出：不抛异常，而是绕回（Java 里可用 Math.addExact 检测）
- float 累加：累积误差（Ch25 的「脂肪和糖浆」里就有这类）
- 布尔→整数：0/1 巧合可用，掩盖逻辑错误
结论：语言能自动转换，不代表应该自动转换
```

> **教学示意，不参与构建、不编译、不运行。**

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 追求「变量声明得越早越好」（老式风格） | 过早声明扩大存活期，制造遗留状态 | 尽量靠近使用点声明 |
| 2 | 认为类型越弱越灵活 | 弱类型的灵活性由运行期 bug 支付 | 关键位置用强类型表达不变式 |
| 3 | 依赖隐式类型转换省事 | 隐式转换是「静默的语义变更」 | 关键边界显式转换并断言结果范围 |
| 4 | 把「魔法数字」一律替换成常量 | 有些魔法数字是真实的数据（如数组下标），替换反而制造噪音 | 判断标准：这个数字表达的是**语义**还是**数值**？ |
| 🔧 | 第 2 版对「魔法数字」的过度规范化倾向 | 第 2 版把「任何硬编码数值都应命名常量」写成近似规则，后文被认为过严 | 修正：只对**语义性硬编码**（配置阈值、业务常量）命名；对算法内部的下标/循环边界保持字面量 |
| 🔧 | 10.4 的类型讨论基于 2004 年的语言状态 | 泛型、类型推断、非空类型已经重塑了这个议题 | 补充：类型推断用于实现细节，公开 API 保留显式类型 |
| 🔧 | 对变量「命名长度」的建议（20 字符左右）被误读为硬性上限 | 名字长度应与作用域成正比：作用域越大，名字越要具体 | 用它替代固定长度，而不是固定长度 |

# 第 11 章 变量名称的威力

> **一句话**：名字是程序员最主要的工具，不是装饰——一段代码里 90% 的信息量，通常压在它出现的那几个标识符上。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 11.1 变量名的长度 | 名字长度与作用域成正比；20 字符左右为参考 | 短名字只适合短作用域 |
| 11.2 名字中的限定词 | 限定词（total、max、count）放前还是放后 | 约定唯一，且优先「total 在前 + 类型在后」等稳定模式 |
| 11.3 名字对语句可读性的影响 | 好名字让语句接近自然语言 | 判断标准：删掉名字，语句还能读吗？ |
| 11.4 变量名记法 | 匈牙利记法、前缀/后缀、下划线、大小写 | 记法应服务于「编译器看不到的信息」 |
| 11.5 命名要点 | 避免误导、命名要与类型一致、用具体而非抽象 | 最贵的一类错误是「名字对但语义错」 |
| 11.6 常量与枚举的命名 | 全大写 + 下划线（C 系）或类型前缀（Java 系） | 常量名表达「这是什么」，不是「它是什么类型」 |

## 核心精讲

命名检查清单（教学示意，不参与构建）：

```text
[伪代码] 命名自查（Yes 表示合格）
□ 名字能完整表达「是什么」，而不仅是「像什么」
□ 循环变量 i/j/k 只在极短作用域内使用；超过一层嵌套就改名
□ 名字不重复类型信息（listOrder 而不是 orderList 的反向误读要小心）
□ 名字不误导（别用 userCount 表示「可能未初始化」）
□ 名字与它的实际类型一致（别把 HashMap 叫 xxxList）
□ 限定词放前：totalRevenue、maxRetries
□ 常量名表达语义：MAX_UPLOAD_BYTES（而不是 BUFSIZE）
□ 同一个概念在整个项目里有同一个名字（别一会儿 row 一会儿 record）
```

> **教学示意，不参与构建、不编译、不运行。**

匈牙利记法今天还剩什么（教学示意，不参与构建）：

```text
[伪代码] 匈牙利记法的历史收益 vs 现代等价物
历史收益（2004 年以前）：IDE 无智能补全时，用前缀表达「类型/作用域/状态」
    -> szName（以 NUL 结尾的字符串）、lpszName（长指针字符串）
现代等价物：类型系统 + IDE 补全 + 静态分析接管了类型信息

结论：保留「语义属性」前缀，其余交给编译器
```

# 第 12 章 基本数据类型

> **一句话**：基本数据类型本身不是问题，「在基本类型之上手工造出的语义」才是问题——一旦你用 int 表达金额，你就已经写下了一种货币。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 12.1 使用数据类型的策略 | 用类型表达语义、用类表达概念 | 能用类型说清的，别写在注释里 |
| 12.2 浮点数的注意事项 | 精度、比较、累加误差 | 货币金额不要用二进制浮点；比较用容差 |
| 12.3 整数的注意事项 | 溢出、无符号、除零 | 溢出是静默的，需要显式运算或范围断言 |
| 12.4 字符与字符串 | 编码、字符串比较、不可变字符串 | 字符串是「最被低估的类型」 |
| 12.5 布尔与枚举 | 枚举替代「魔法数字」、位标志 | 枚举比布尔更可扩展 |
| 12.6 数组与字典 | 稀疏数据的表达、矩阵、记录 | 选错容器会造出复杂度 |

## 核心精讲

把语义装进类型（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：用裸类型承载语义，于是合法性规则散落各处
double price;                 // 单位是元还是分？能否为负？
if (price > 0) { /* 每层调用都要重复这个判断 */ }

// 正例：类型承载语义，合法性规则只说一次
record Money(long cents) {        // 内部用整数分，避免浮点误差
    public static Money ofYuan(double yuan) { ... }
    public Money plus(Money other) { requireNonNegative(); ... }
}
record UserId(String value) {     // 顺便让「空字符串不是合法 UserId」成为构造事实
    public static UserId of(String v) {
        if (v == null || v.isBlank()) throw new IllegalArgumentException("UserId 不能为空");
        return new UserId(v);
    }
}
```

浮点与整数的坑（教学示意，不参与构建）：

```text
[伪代码] 数值陷阱与对策
陷阱                 | 对策
--------------------|------------------------------------
0.1 + 0.2 != 0.3    | 货币用整数分/最小单位；一般比较用绝对/相对容差
整数溢出静默绕回     | 使用 checked 运算；范围在构造时断言
除以零不抛异常       | 显式检查分母，或用可选类型表达「不可能为零」

字符编码混淆         | 统一 UTF-8；比较前显式 normalize
```

枚举优于布尔与魔法数字（教学示意代码，不参与构建、不编译、不运行）：


## 核心精讲

别名问题：指针/引用最贵的一段（教学示意，不参与构建）：

```text
[伪代码] 别名的三种形态与代价
1. 两个变量指向同一对象（引用语义）
   -> 修改通过任一名字发生，调用方无法预判被改的是什么
2. 对象里存着别人的引用（成员别名）
   -> 该对象的「状态」不再只由自己决定
3. 返回内部引用/指针（escaping）
   -> 调用方可以改变对象的私有状态，封装失效

对策（现代）：不可变数据 + 值语义 + 所有权（Rust）/ 深度拷贝
             在边界处做「防御性拷贝」而不是到处加注释
```

> **教学示意，不参与构建、不编译、不运行。**

相等性与拷贝（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：可变对象 + 值相等 = 最经典的 bug 温床
class Money {                     // 用了/equals 但可变
    public int cents;
    // 于是 map.get(money) 依赖传入时的快照，更新 cents 后永远取不到
}

// 正例：不可变值对象 -> 相等性稳定，可安全作为键/集合元素
record Money(int cents) { }       // 值相等 + 不可变
record Point(int x, int y) { }    // 值语义，hashCode 由语言提供
```

> **教学示意，不参与构建。**

变参与默认参数（教学示意，不参与构建）：

```text
[伪代码] 变参 / 默认参数的代价
变参函数：
  优点：调用方读起来自然
  缺点：绕过静态类型；参数个数/顺序错误只在运行期暴露
  替代：重载 + builder + 显式参数对象

默认参数：
  优点：减少重载数量
  缺点：调用点看不出「哪些参数是默认给的」；默认值散落在函数定义处
  替代：把默认实现写进调用方（一处可比、易搜）
```
