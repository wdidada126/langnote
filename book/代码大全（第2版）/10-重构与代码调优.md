# 第 24 章 重构

> **一句话**：重构的前提不是「有重构工具」，而是**有能把行为锁住的机制**——所以重构之所以在 2004 年之后才普及，是因为自动化测试先普及了。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 24.1 软件演化的类型 | 四种演化：journey（旅程）、evolution（演进）、servolution（服务演化）、immortal（不朽） | 区分「演化类型」决定你要不要重构、要重构到什么程度 |
| 24.2 重构简介 | 重构的定义（不改变外部行为、改善内部结构）、可重构与不可重构的代码 | 判断能否安全重构，看的是有没有行为锁 |
| 24.3 特定的重构 | 提炼子程序、内联、移动、替换算法、以查询替代临时变量等 | 手法目录由 Fowler 系统化，本章给判断 |
| 24.4 安全的重构 | 先有测试、小步、按序；测试失败时立刻回退 | 「重构的关键是纪律，不是手法」 |
| 24.5 重构策略 | 何时重构（!"when you see a bad smell"）、有多少重构够、重构与开发的比例 | 常见比例约 10%–20% 的代码时间用于重构 |

## 核心精讲

重构的前提条件（教学示意，不参与构建）：

```text
[伪代码] 可重构性检查（Yes 才能动手）
□ 有充分的自动化测试：改之前能跑，改之后能证明没变
□ 重构是「一小步」：每步都保持行为一致（不可观察的状态变化也要单向）
□ 能快速回滚：git 历史 + 短分支 + CI
□ 有明确目标：这次重构是为了「改起来更便宜」，不是为了「看起来更漂亮」
□ 不影响交付：重构不在发布窗口进行

结论：如果没有测试，重构只能叫「重写」，风险量级完全不同
```

> **教学示意，不参与构建、不编译、不运行。**

重构示例：把「条件 + 分支」重构成「表 + 策略」（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// Before：三个分支，每加一种券类型就要改这里
double discount(Order o) {
    if (o.coupon() == Coupon.FREE_SHIPPING) return 10.0;
    if (o.coupon() == Coupon.HALF_PRICE)    return o.total() / 2;
    if (o.coupon() == Coupon.TEN_OFF)       return Math.min(10.0, o.total() * 0.1);
    return 0.0;
}

// After：把「分支」变成「可替换的部件」，新增类型无需改这里
interface DiscountPolicy { double apply(Order o); }
record FreeShipping() implements DiscountPolicy { public double apply(Order o) { return 10.0; } }
record HalfPrice()    implements DiscountPolicy { public double apply(Order o) { return o.total() / 2; } }
record TenOff()       implements DiscountPolicy { public double apply(Order o) { return Math.min(10.0, o.total()*0.1); } }

static double discount(Order o, DiscountPolicy p) { return p.apply(o); }
// 行为保持不变：同样的输入仍有同样的输出 —— 这是「安全」的唯一判据
```

> **教学示意，不参与构建。**

重构与开发的节奏（教学示意，不参与构建）：

```text
[伪代码] 「重构周期」的现实比例
开发新功能  70%
重构（为下一个功能铺路） 20%
删除无用代码 10%

判断何时重构：
- 你要改一个「改起来很痛」的地方  -> 先重构，再改（痛感即信号）
- 看到一个坏味道但马上要交付    -> 记 TODO，不要顺手大改
- 重构进行到一半被人打断        -> 立刻提交，保证 HEAD 始终可发布
```

> **教学示意，不参与构建、不编译、不运行。**

# 第 25 章 代码调整策略

> **一句话**：代码调整的第一课不是「怎么改快」，而是「**先测量**」——在没有数据之前做任何优化，都是在优化一个你想象中的问题。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 25.1 性能概述 | 性能与经济学：时间/空间/开发成本三者权衡 | 性能是权衡，不是目标本身 |
| 25.2 代码调整简介 | 调整的前提：正确的程序 + 测量 | 「先让它对，再让它快」 |
| 25.3 脂肪和糖浆 | 把「脂肪」砍掉（算法与策略），而不是削「糖浆」（微优化） | 本章最重要的隐喻 |
| 25.4 性能测量 | 基准测试、 profiler、噪声控制 | 测量本身有误差，不要拿单次数值下结论 |
| 25.5 反复调整 | 小步测量—调整—回归 | 回归测试是性能工作的同伴 |
| 25.6 代码调整方法总结 | 一套有序的调整流程 | 脂肪优先，糖浆最后 |

## 核心精讲

「脂肪与糖浆」原则（教学示意，不参与构建）：

```text
[伪代码] 脂肪 vs 糖浆
脂肪：算法选择、数据结构、策略层、不必要的抽象、多余的拷贝
      -> 去掉它能带来数量级提升；代价是实现复杂度和时间
糖浆：内层循环里的微小运算、位运算、展开、避免函数调用
      -> 去掉它只有百分之几；代价是可读性

原则：先砍脂肪，再刮糖浆
反例：在内层循环里做糖浆优化，而外层算法是 O(n^2)
结论：优化的顺序决定了一生能拿到的收益上限
```

> **教学示意，不参与构建、不编译、不运行。**

调整流程（教学示意，不参与构建）：

```text
[伪代码] 「先对再快」的五个步骤
1 让程序正确：有测试保证行为不变
2 测量：找出真正的热点（profiler 而不是直觉）
3 判断「这是脂肪还是糖浆」：热量高的部位优先
4 改一处 + 再测：单变量实验，否则你不知道是哪一处起了作用
5 回归验证：功能测试 + 性能基准一起跑
禁忌：一次堆上五个改动，然后说「变快了」——你无法归因
```

> **教学示意，不参与构建、不编译、不运行。**

一个「先测后改」的骨架（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 关键：先有基准，才有「优化」这个词
interface Throughput { double opsPerSecond(int n); }

final class Bench {
    static double measure(Throughput t, int n) {
        long t0 = System.nanoTime();
        double ops = t.opsPerSecond(n);        // 返回处理量，避免 JIT 优化掉空调用
        long t1 = System.nanoTime();
        return ops / Math.max(1e-9, (t1 - t0) / 1e9);
    }
}
// 之后每次调整都重跑这个基准，并同时跑功能回归测试
```

> **教学示意，不参与构建。**

## 核心精讲

循环调整的可读性代价（教学示意，不参与构建）：

```text
[伪代码] 常见的循环调整手法与其「可读性账单」
手法                收益          可读性代价
-------------------|-------------|------------------
边界不变量外提      小~中         低（可用注释/提取）
最小化循环内工作    中            低~中
合并/展开循环       小~中         高（应变式推导困难）
用更强索引/指针算术 中（旧机器上）  高
结论：第一优先看算法；第二优先看数据布局；循环展开了就别回去了
```

数据变换：视图 vs 拷贝（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：为「避免修改」而每处都做深拷贝 —— 空间与时间双输，且语义混乱
List<Order> safe = new ArrayList<>(orders);       // 拷贝
for (Order o : safe) { ... }

// 正例：先决定「我要的是视图还是快照」，并在类型/命名上表达出来
List<Order> snapshot = List.copyOf(orders);       // 明确的不可变快照
// 或用只读视图 + 明确的修改入口
Stream<Order> view = orders.stream().filter(...); // 惰性视图
```

「抽象值不值」（教学示意，不参与构建）：

```text
[伪代码] 抽象的收益 vs 代价（26.7 的核心问题）
收益：复用、易改、可推理
代价：多一层间接、多一层类型、初始化成本、调试时多跳一次

判断顺序：
1 这处抽象会被复用三次以上吗？ 否 -> 先写直白版本（Rule of Three）
2 改这里的成本会因此下降吗？  否 -> 抽象只是在美化
3 抽象引入了哪些「必须同时正确维护」的约定？把它们记下来
```

> **教学示意，不参与构建、不编译、不运行。**

## 版本演进

| 维度 | 第 1 版（1993） | 第 2 版（2004） | 2015–2026 |
| --- | --- | --- | --- |
| 微优化条目 | 很多 | 减少 | 大部分被编译器吸收，不再需要手写 |
| 数据布局 | 少 | 略提 | 成为主要收益点（缓存行、对界、列式布局） |
| 内联/展开 | 手工 | 手工 | 编译器自动完成，手工展开基本无益 |
| 低阶语言重写 | 常见手段 | 保留 | 少见；被「换一种更高效的实现/换算法」替代 |
| AI 编码 | 无 | 无 | 生成代码仍会复制这些旧习惯（层层展开、指针算术） |

## 近年研究与工业界开源实践（2015–2026）

趋势：性能工作从「指令层」上移到「**数据布局 + 并行 + 分配**」。分配器开销、缓存行填充、避免不必要的拷贝与装箱，构成今天绝大多数「优化」的实际内容；同时，性能回归被纳入 CI，防止「快了 3% 但可读性腰斩」的交易无法被质疑。

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 照着 26.x 的手法列表逐条套用 | 多数手法在现代编译器下无益 | 只当目录，逐个实测 |
| 2 | 展开循环/内联以求「快」 | 可能导致指令缓存与可维护性问题 | 交给编译器 |
| 3 | 用低阶语言重写作为常规手段 | 代价是失去类型与生态保护 | 只在测量证明必要时使用 |
| 4 | 忽略抽象的成本（26.7 的真正问题） | 过度抽象同样是性能与可读性负债 | 按 Rule of Three 决定抽象时机 |
| 🔧 | 第 2 版的调整技术里，微优化占主要篇幅 | 2020 年代的编译器使其中大部分作废 | 把重心放在算法、数据布局、分配与并行 |
| 🔧 | 第 2 版缺少「性能必须可回归」的概念 | 性能退化往往在重构后悄悄发生 | 补充：把性能基准纳入 CI 门禁，防止不可见的退化 |
| 🔧 | 对「用低阶语言重写」的代价论述不足 | 真正的代价是人才、生态与错误的代价 | 补充：重写前先量化「到底能拿多少」，通常远低于预期 |
