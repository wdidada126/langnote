# 第 6 章 可以工作的类

> **一句话**：类不是「把一堆相关函数塞在一起」的容器，而是**一组被接口边界保护起来的秘密**——你只能看见接口，看不见里面的易变区。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 6.1 类的基础：抽象数据类型（ADT） | 数据的「表示」与「操作」的绑定；ADT 是类的心智模型 | 先有 ADT 再有类；ADT 让你能脱离语言讨论设计 |
| 6.2 良好的类接口 | 接口与实现的分离、Accessor/Mutator 的最小化、避免公开成员 | 好接口是「窄」的：做不到的比做得到的更重要 |
| 6.3 设计和实现问题 | 类职责单一、继承与组合的选择、构造函数、内存与生命周期 | 「先写组合再想继承」；构造函数只做能一致完成的事 |
| 6.4 创建类的理由 | 16 条创建类的正当理由 | 反过来的清单同样重要：**不该创建**的理由（仅为分组、仅为数据 holders） |
| 6.5 语言特定问题 | 各类语言的可见性、friend、嵌套类、析构等 | 语言决定「你必须显式处理哪些复杂度」 |
| 6.6 超越类：包 | 包/命名空间、包的接口、包的层次 | 包是「第二层信息隐藏」，常被忽略 |

## 核心精讲

判断一个类该不该存在（教学示意，不参与构建）：

```text
[伪代码] 创建类的 16 条正当理由（正向）
1 建模现实对象  2 建模虚拟对象  3 降低复杂度     4 隔离复杂度
5 隐藏实现细节  6 限制作用域   7 提升可测试性   8 隔离一处的变更
9 隐藏全局数据  10 封装单一职责 11 让接口与实现解耦 12 便于复用
13 便于替换实现 14 简化与外部系统的交互 15 为一块逻辑命名 16 便于并发隔离

[反向清单] 不该创建类的理由 —— 本书最实用的一页
X 仅为把几个函数放在一起      X 仅为存几个字段（data holder 无行为）
X 仅为对应一个数据库表        X 仅为「看起来更面向对象」
X 仅为让文件不至于太长        X 仅为继承树里占个位置
```

> **教学示意，不参与构建、不编译、不运行。**

接口窄化的示例（教学示意代码，不参与构建、不编译、不运行）：

```java
// 反例：接口宽，暴露了所有可能的操作，等于承诺了所有实现
interface BadAccount {
    void open(); void close(); void deposit(BigDecimal amt);
    void withdraw(BigDecimal amt); BigDecimal getBalance();
    void setOverdraftLimit(BigDecimal lim); boolean isFrozen();
    void freeze(); void unfreeze();   // 大部分调用方永远用不到
}

// 正例：接口窄，且「操作」按调用方视角组织
interface Account {
    TxResult deposit(Money amt);
    TxResult withdraw(Money amt);
    Money balance();
}
// 冻结、透支额度等作为独立策略对象，而不是 Account 的方法
```

> **教学示意，不参与构建。**

构造函数的「只做一致的事」原则，以及组合优于继承：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 组合优先：把「易变的实现」变成可替换的部件，而不是继承层次的一支
final class ReportRenderer {
    private final TemplateEngine engine;   // 构造时注入，而不是继承某个 RendererBase
    private final Clock clock;             // 便于测试，便于替换
    ReportRenderer(TemplateEngine engine, Clock clock) {
        this.engine = Objects.requireNonNull(engine, "engine"); // Ch8 防御式编程
        this.clock  = Objects.requireNonNull(clock, "clock");
    }
    String render(Context ctx) { return engine.apply(ctx, clock.now()); }
}
```

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 用「文件里有多少函数」判断类的大小 | 类大小的正确指标是**认知负荷与变更半径** | 用 change radius 与接口宽度替代行数 |
| 2 | 数据类（纯字段容器）被当成合法的类 | 无行为的 data holder 只是命名良好的结构体 | 若没有行为，就让它显式地成为结构体/record，别伪装成类 |
| 3 | 用继承复用代码 | 继承复用会同时复用其契约与脆弱性 | 先组合；确需多态时用 Strategy/Bridge |
| 4 | 为「以后可能用到」预留接口方法 | 这是过度设计最常见的形式之一 | YAGNI：接口只含已存在的需求 |
| 🔧 | 第 2 版把「创建新类」作为默认动作，很少提醒「先考虑不新建」 | AI 辅助编码时代这个问题被放大 | 补充：先问「能不能用一个函数/一个 record 解决」 |
| 🔧 | 6.5「语言特定问题」覆盖的是 2004 年的语言状态 | 泛型、sealed 类型、模块系统已改变可见性讨论 | 补充：可见性应表达「哪些秘密要藏」，而不是「语言允许哪些修饰符」 |
| 🔧 | 对包/模块的接口讨论不足，默认包只是目录 | 2020 年代「模块边界」是主要的复用与依赖边界 | 补充：包级接口（导出的符号面）比类接口更容易失控 |

# 第 7 章 高质量的子程序

> **一句话**：子程序是「控制流与数据流的汇合点」——一个子程序做一件事，做到可以一句话说清，它的名字就是它的全部文档。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 7.1 创建子程序的正当理由 | 16 条理由（降低复杂度、避免重复、隐藏顺序、隐藏指针操作等） | 与 Ch6 同样需要「反理由」清单 |
| 7.2 子程序级别的设计 | 至少一个入口一个出口、goto 的去向、耦合最小化、长度 | 子程序内部的结构化，决定了外部接口的可靠性 |
| 7.3 好的子程序名称 | 动词+对象、长度约 20 字符、返回值命名、避免使用无意义的动词 | 名称精确性可量化：一个名字能说出它做了什么 |
| 7.4 一个子程序应该有多长 | 建议「一个屏幕内」；长子程序的症状 | 长度不是罪，长度是症状——症状它做了太多事 |
| 7.5 如何使用子程序参数 | 参数数量（建议 ≤ 7）、顺序、对象/基本类型的选择、可选参数 | 参数是最强的耦合点；用「隐藏参数」替代可选参数 |
| 7.6 函数使用中的特别注意事项 | 返回值处理、被零除、类型转换、布尔表达式求值 | 函数与子程序的分工：一个「动作」，一个「谓词」 |
| 7.7 宏子程序和内联子程序 | 宏的陷阱、内联的代价 | 宏是「文本替换」不是「函数调用」，必须彻底规避 |

## 核心精讲

子程序质量的判定清单（教学示意，不参与构建）：

```text
[伪代码] 子程序体检（每条 Yes 表示合格）
□ 名称是动词短语，且能回答「做什么」
□ 只做一件事，且名字能覆盖它（不能只覆盖一半）
□ 有明确的前置条件，且被断言检查（Ch8）
□ 参数数量 ≤ 7，且没有「可选参数填 null」这种情形
□ 只有一个返回点，或用一致的提前返回策略
□ 没有修改传入的对象（除非它就是为此而来）
□ 没有隐藏的输入（时间、全局状态、随机数）
□ 长度低于一屏，若超出则说明它在做多件事
```

> **教学示意，不参与构建、不编译、不运行。**

参数处理的正反面（教学示意代码，不参与构建、不编译、不运行）：

```java
// 反例：布尔标志参数 = 这个子程序至少有两套行为
void render(boolean isCacheEnabled, boolean shouldValidate) { /* 4 种组合 */ }

// 正例：拆成语义明确的函数，调用方读起来就是文档
void renderCached();
void renderAndValidate();
// 或用枚举显式表达三态，避免布尔参数堆叠
enum RenderMode { CACHED, VALIDATED, PLAIN }
void render(RenderMode mode);
```

> **教学示意，不参与构建。**

宏 vs 函数的对比（教学示意，不参与构建）：

```text
[伪代码] 宏的三宗罪（2004 年讲得对，2026 年仍然对）
1. 宏是文本替换：参数类型错误不会被编译器发现
2. 宏会意外多次求值：#define SQUARE(x) ((x)*(x)) 传入 i++ 会 ++ 两次
3. 宏没有作用域：调试栈里看不到名字，出错在预处理之后的位置
结论：模板/内联函数/constexpr 应当取代宏；需要宏的场合只有
      「条件编译」与「字符串化」这类真正的预处理能力
```

> **教学示意，不参与构建、不编译、不运行。**

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 以「行数」作为子程序质量的指标 | 行数是症状指标不是原因 | 用单一职责与认知复杂度替代 |
| 2 | 用布尔参数表达可选行为 | 实际上是两套函数的合成 | 拆函数或用枚举/策略 |
| 3 | 认为提前返回（early return）破坏结构化 | 现代实践普遍接受「一致地提前返回」 | 关键是一致性，而不是只有一个出口 |
| 4 | 以为宏的问题只是「丑」 | 宏是文本替换，会意外多次求值 | 用函数/模板/constexpr 替代 |
| 🔧 | 第 2 版默认「一个子程序至少有一个入口一个出口」的严格解释 | 早期结构化编程遗产在现代实践中被放宽 | 修正为「允许提前返回，但全项目一致」 |
| 🔧 | 对「隐藏输入」（时间、全局状态、随机）的讨论分散 | 这是 2020 年代纯函数运动的核心议题 | 补充：显式传入时钟/随机数源，比在参数清单里塞参数更好 |
| 🔧 | 未考虑 AI 生成代码的函数划分习惯 | 模型倾向于生成长函数与宽接口 | 评审时优先要求「拆分长函数」，并把参数清单作为审查项 |
