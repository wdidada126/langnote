# 第 27 章 程序规模对构建的影响

> **一句话**：规模不改变错误的种类，但**改变错误的分布**——小项目里均匀分布的缺陷，在大项目里会集中到少数模块。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 27.1 交流和规模 | 沟通路径随人数呈组合增长、概念完整性的维持成本 | 规模的第一代价是沟通，不是性能 |
| 27.2 项目规模的范围 | 从个人脚本到百万行系统的量级梯度 | 用规模分层决定管理策略与工具 |
| 27.3 规模对错误的影响 | 缺陷密度与规模的关系；缺陷集中在少数模块 | 修复一处会引入新的缺陷（bug-fix bug） |
| 27.4 规模对生产率的影响 | 规模越大，人均产出越低 | 最重要的定量结论之一 |
| 27.5 规模对开发活动的影响 | 测试/调试占比随规模上升 | 规模越大，前期准备与集成越值得投入 |

# 第 28 章 管理构建

> **一句话**：管理层的重点是「让程序员能写出好代码的环境」——而不是监督他们写代码写得够快。

## 核心精讲

度的类别与「反游戏化」（教学示意，不参与构建）：

```text
[伪代码] 度量类别与风险
类别        指标示例                      被游戏化的方式
-----------|-------------------------------------------
规模        LOC、文件数                   写更长的代码
缺陷        缺陷数、缺陷密度              藏缺陷 / 不报 minor
进度        完成的故事点                  拆分故事以凑数
质量        覆盖率、CR 数                  写无断言测试 / 刷 CR 次数

对策：每个指标配一个「反向指标」或上下文指标
   LOC -> 配变更失败率
   覆盖率 -> 配突变测试分数
   缺陷数 -> 配「修复后 30 天内复发率」
```

压力与质量的关系（教学示意，不参与构建）：

```text
[伪代码] 进度压力的传导路径
进度压力上升
  -> 跳过评审 / 跳过测试 / 提前提交
  -> 缺陷注入上升、剔除率下降
  -> 测试期缺陷暴增，需要更多修复时间
  -> 进度进一步落后，压力进一步上升   （正反馈环）
破解：在环路中切断一处 —— 通常是「拒绝无测试的提交」这一条硬规则
```

工程示意：构建进度的「期望值驱动」（教学示意，不参与构建）：

```text
[伪代码] 「改一下日期就当完成了」的失败模式
  真实进度：0.6
  管理预期：1.0  （把日期从 8/31 改到 9/15，假装多出两周）
  实际结果：9/15 交付的是「按 0.6 进度做的东西」，需求缺口被隐藏
  后果：测试阶段才发现缺口，进度再次落后，且信任受损
  对策：用「可运行的产物」而非「日期」来度量进度
```

# 第 29 章 集成

> **一句话**：集成方式比集成频率更重要——把集成从「一次大爆炸」变成「每次提交一次」，是这十几年工程效率最大的单项改进。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 29.1 整合方式的重要性 | 大爆炸式 vs 增量式 | 集成策略决定「发现冲突与缺陷的时间」 |
| 29.2 整合频率 | 阶段式 vs 增量式（每日/每小时） | 频率越高，冲突成本越低 |
| 29.3 增量整合的策略 | 自顶向下、自底向上、系统矩阵、频繁集成 | 三种策略各有适用场景 |
| 29.4 每日构建与冒烟测试 | 构建频率、冒烟测试、构建健康度 | 「构建必须始终可发布」是一条硬纪律 |

## 核心精讲

集成策略的对比（教学示意，不参与构建）：

```text
[伪代码] 集成策略
大爆炸式：大家都完成后一次性合并 -> 冲突集中、缺陷定位困难、进度风险大
自顶向下：先集成上层，底层用桩（stub）-> 早期可见系统形状，桩的实现会返工
自底向上：先集成底层，上层用桩 -> 底层扎实，上层接口可能被迫妥协
系统矩阵：并行地在多个层次上做增量 -> 最实用，但需要严格的任务切分
频繁集成：每次提交都构建并跑冒烟测试 -> 成本最低、反馈最快

结论：选择「增量 + 频繁」；三种自顶/自底/矩阵用于组织工作而不是安排阶段
```

> **教学示意，不参与构建、不编译、不运行。**

每日构建的健康规则（教学示意，不参与构建）：

```text
[伪代码] 构建纪律（现代 CI 的原型）
1 构建必须始终可运行（broken build 当天修复）
2 构建包含：编译 + 静态分析 + 单元测试 + 冒烟测试
3 冒烟测试只测「核心路径能否跑通」，不做全覆盖
4 反馈在几分钟到几小时内，超过一天就失去意义
5 构建失败时，禁止「绕过测试并提交」，除非有明确的 hotfix 流程
```

> **教学示意，不参与构建、不编译、不运行。**

| 🔧 | 第 2 版的集成讨论假定集中式版本控制 | 分支/合并模型发生了根本变化 | 补充：分支策略与特性开关是集成策略的组成部分 |
| 🔧 | AI 辅助编码下的集成风险被低估 | 短时间内的批量提交会淹没人工评审 | 补充：对生成提交必须有自动化的「意图说明 + 校验」前置 |

# 第 30 章 编程工具

> **一句话**：工具的价值不在「功能多」，而在「把正确的做法变成不用思考的做法」——所以最好的工具是那些自动执行的。

## 本章地图

| 30.2 源代码工具 | 编辑器、重构工具、格式化器、静态分析、版本控制 | 本节是本章主干，也是本书最「时效性强」的部分 |

## 核心精讲

源代码工具的分层（教学示意，不参与构建）：

```text
[伪代码] 源代码工具栈（2026 年的实际形态）
层            代表                        作用
------------|----------------------------------
格式化器      black / gofmt / rustfmt      消灭风格争论
Linter        golangci-lint / clippy       消灭明显缺陷
静态分析      CodeQL / SonarQube           消灭模式化缺陷
类型检查      编译器                        消灭契约错误
测试          xUnit / 属性测试框架          消灭回归
覆盖率/突变   coverage / mutation          证明测试有效
CI 编排       GitHub Actions / pre-commit  把上述全部自动化
原则：越低层的工具越应该「不可协商」
```

> **教学示意，不参与构建、不编译、不运行。**

「打造自己的工具」（教学示意，不参与构建）：

```text
[伪代码] 何时自建工具
信号：你在同一类操作上花超过 30 分钟，且这类操作每周至少发生 3 次
反信号：为一次性的分析写 500 行脚本 -> 用一次性脚本，别建长期工具
原则：自建工具要能随代码一起提交、一起演进（否则 3 个月后没人敢动）
```

> **教学示意，不参与构建、不编译、不运行。**

工具选择的判断顺序（教学示意，不参与构建）：

```text
[伪代码] 引入新工具的顺序
1 这个工具能不能进 pre-commit / CI？ 不能 -> 慎重（会依赖人的自觉）
2 它的规则能不能「先只看不改」？    不能 -> 规则太激进，会引发对抗
3 它的输出能不能被追踪？            不能 -> 无法证明它有用
4 引入后，哪件事变「不用思考」了？  答不出 -> 它只是让流程变复杂
```

> **教学示意，不参与构建、不编译、不运行。**

## 近年研究与工业界开源实践（2015–2026）

趋势：**工具收敛与默认化**。格式化器把风格层争议彻底解决；lint 被聚合；pre-commit 统一入口；AI 辅助编码成为新增的一类「工具」并迅速成为默认。同时，工具治理出现新问题：工具规则过多会让开发者疲劳，因此「先只看不改」（warn-only）的滚入策略成为主流做法。

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 工具越多越好 | 规则疲劳会让所有工具失效 | 保持规则集精简，逐步滚入 |
| 2 | 一次性脚本当长期工具维护 | 无人敢动的脚本比没有更糟 | 能进版本库的才进版本库 |
| 3 | 依赖 IDE 的私人配置 | 换环境就失效 | 配置进版本控制（配置文件即资产） |
| 4 | 忽略「工具之间的串联」价值 | 单个工具好，串起来才有用 | 工具导向的环境（30.4） |
| 🔧 | 第 2 版的工具清单已高度过时 | 2004 年的编辑器与版本控制讨论不再有参考价值 | 只保留「分层与判断顺序」，替换具体工具名；具体工具见本文件的工具链表 |
| 🔧 | 第 2 版完全没有 AI 辅助编码类工具 | 它们现在是工程师最常用的工具 | 补充：把 AI 工具纳入同一套治理（可回滚、可审查、有记录） |
| 🔧 | 「工具梦想世界」一节偏浪漫 | 今天的差距主要是「治理」而非「能力」 | 补充：真正的瓶颈是规则治理、提示管理与审查负担 |
