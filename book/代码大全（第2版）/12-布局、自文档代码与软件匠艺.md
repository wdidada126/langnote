# 第 31 章 代码的布局和风格

> **一句话**：布局是「视觉语法」——统一布局的价值不在好看，而在让读者不必先解析格式、再理解内容。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 31.1 布局综述 | 布局服务于可读性；两种流派（自由 vs 统一） | 流派之争无意义，关键是「统一」 |
| 31.2 布局风格 | 换行、缩进、空格、括号位置、行宽 | 具体规则交给格式化器 |
| 31.3 布局的风格要素 | 统一、紧凑、一致、高效、可读（DISR） | 五项要素可用来评估任何风格 |
| 31.4 改善可读性的习惯做法 | 注释对齐、分节、控制行宽、不要滥用空格 | 「先统一，再优化」 |

## 核心精讲

布局风格要素（教学示意，不参与构建）：

```text
[伪代码] DISR 五项
D 统一(Unified)   : 同一结构在不同地方长得一样 -> 靠"预测"而非"阅读"
C 紧凑(Compact)   : 信息密度高 -> 一屏能看到更多
I 一致(Conistent) : 与团队/社区惯例一致 -> 新人的学习成本最低
R 可读(Readable)  : 眼睛不必做多余的工作（换行、对齐）
E 高效(Efficient) : 不浪费版面（别留大片空白）

注意：五个要素可能互相冲突（紧凑 vs 可读），需要一个明确的取舍顺序
实用顺序：统一 > 一致 > 可读 > 紧凑 > 高效
```

> **教学示意，不参与构建、不编译、不运行。**

风格规则的最终归宿（教学示意，不参与构建）：

```text
[伪代码] 风格规则的三层
第 1 层 格式化器强制（black / gofmt / rustfmt）：缩进、换行、括号、行宽
第 2 层 Linter 强制（golangci-lint / clippy）：命名、可见性、明显坏味道
第 3 层 评审与约定：语义层面的风格（早返回、卫语句、注释策略）

原则：能自动强制的，绝不写进文档；文档里只留「无法自动化的取舍」
```

> **教学示意，不参与构建、不编译、不运行。**

# 第 32 章 自文档代码

> **一句话**：注释的黄金法则是「**代码能说清的，别写注释**」——注释唯一该解释的是「为什么」，而不是「是什么」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 32.1 注释的必要性 | 注释是「意图的记录」，代码是「实现的记录」 | 两者缺一不可，但职责不同 |
| 32.2 好的注释与坏的注释 | 好的：解释意图/理由/约束/前置条件；坏的：复述代码/误解过时 | 判断标准：删掉它，读者会少知道什么？ |
| 32.3 注释策略 | 何时该注释、何时不该 | 「记下你当时知道、现在不知道的东西」 |
| 32.4 风格要素 | 注释的位置、对齐、简洁、避免装饰 | 风格次要，准确首要 |
| 32.5 说明数据类型 / 使代码自文档并使它更新 | 命名与结构的自文档力量；注释的维护义务 | 最好的注释是没有写下的注释 |

## 核心精讲

注释的判据（教学示意，不参与构建）：

```text
[伪代码] 注释三问
问 1：代码本身在说明「是什么」，注释重复它就删（冗余注释是负债）
问 2：注释在说明「为什么这么做」，而代码无法表达 -> 保留（价值高）
问 3：注释描述的是「没写进代码的约束/权衡/取舍」-> 保留（最有价值的一类）

典型「好注释」样本：
  // 为什么用整数分而不是 double：避免 0.1+0.2 的表示误差进入对账
  // 为什么这里没加缓存：并发下的一致性与收益不成比例，见 #1234
```

> **教学示意，不参与构建、不编译、不运行。**

让代码自文档（教学示意代码，不参与构建、不编译、不运行）：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例：注释在复述代码，且会过期
// 计算总数
int total = 0;
// 遍历数组
for (int i = 0; i < xs.length; i++) { total += xs[i]; }

// 正例：代码自文档，注释只剩「为什么」
// 用整数最小单位求和，避免浮点累积误差进入对账口径
long totalCents = 0L;
for (long x : amountsCents) { totalCents += x; }
```

> **教学示意，不参与构建。**

注释的更新义务（教学示意，不参与构建）：

```text
[伪代码] 注释腐化循环
改动代码 -> 忘了改注释 -> 注释变成「错误的说明」
                -> 读者因此做出错误假设 -> 新的缺陷
破解：
1 让注释靠近被描述的代码（否则改代码时看不见）
2 在评审清单里显式检查「注释是否与代码一致」
3 用工具标记「改动过的行，其上方注释需复核」（代码审查工具的部分能力）
```

> **教学示意，不参与构建、不编译、不运行。**

# 第 33 章 个人性格

> **一句话**：这一章是整个 900 页里最像「师傅带徒弟」的一章——它不教招式，教的是**态度决定下限、习惯决定上限**。

## 核心精讲

五个性格特征的可操作化（教学示意，不参与构建）：

```text
[伪代码] 五种性格特征 -> 可观察行为
谦逊 Humility
    -> 假定自己的前提可能有错；先检查假设再下结论
    -> 承认"我不知道这块为什么这样"
好奇心 Curiosity
    -> 遇到不懂的底层，花时间搞清；这些时间会在别处连本带利返回
独立思考 Intellectual Honesty
    -> 不听信权威与流行说法；对"大家都这么做"保持警惕
纪律 Discipline
    -> 约定先设后守；没有纪律的灵活等于混乱
创造 Creativity
    -> 对同一问题寻找多种方案；为"更好"留出余量
```

> **教学示意，不参与构建、不编译、不运行。**

常见的失败模式（教学示意，不参与构建）：

```text
[伪代码] 四种常见失败模式与破解
拖延 Procrastination        -> 用「最小可完成原子」破解：先写下第一步的具体动作
细节强迫 (over-precision)   -> 区分「必须先对」与「可以粗略」两件事
停滞 Stagnation             -> 每隔一段时间做一项超出舒适圈的小事
挫败 Frustration            -> 把大目标拆成「今天能验证的小 Cycle」
```

> **教学示意，不参与构建、不编译、不运行。**

经验的复利（教学示意，不参与构建）：

```text
[伪代码] 经验积累方式
1 记录：问题、当时的解法、为什么这样选
2 复盘：这次的缺陷源于哪一类「没被提前考虑」的情形
3 抽象：这次学到的东西能否写成一条可复用的规则（再写进检查清单）
4 传播：把规则交给工具（lint/CI）才算真正完成
```

# 第 34 章 关于软件匠艺

> **一句话**：匠艺的天职不是把代码写完，而是**对得起读你代码的下一代**——每一处「我这次赶时间」，都会以别人赶时间的代价还回去。

## 核心精讲

大泥球的形成（教学示意，不参与构建）：

```text
[伪代码] 大泥球的四个成因
1 缺少「整洁必须优先」的共识：每次赶时间都留下一处脏
2 缺少「变更的单一责任人」：谁都改，谁都不负责整体形状
3 缺少「局部优化的正反馈」：没人做过「重构一小块以利长期」的示范
4 缺少「可见的质量账本」：脏代码从不出现在任何报表上

破解：让「整洁」变成最低门槛（工具强制），让「重构」变成日常动作
```

> **教学示意，不参与构建、不编译、不运行。**

「何时止步」的判据（教学示意，不参与构建）：

```text
[伪代码] 停止优化的顺序
停手顺序（从先到后）：
1 正确性未保证时 -> 停止一切美化（先补测试）
2 可预测性已达成（同一输入同输出、无隐藏状态）-> 可做结构整理
3 结构已清晰 -> 只做能测量收益的调整
4 收益无法测量 -> 停止（此时它只是在改变癖好）
```

> **教学示意，不参与构建、不编译、不运行。**

职业自主权与「说不」（教学示意，不参与构建）：

```text
[伪代码] 面对冲突的四个姿态（从差到好）
1 沉默接受：留下技术债，日后由别人偿还
2 抱怨不从：情绪化，无产出
3 对抗拒绝：立场化，损害协作
4 提供选项：给出「三个方案 + 各自代价 + 我的推荐」
     -> 这是匠艺在组织中的通行语言
```

> **教学示意，不参与构建、不编译、不运行。**

## 近年研究与工业界开源实践（2015–2026）

趋势：匠艺从**个人德性**转向**组织可验证**。代码评审文化、架构决策记录、质量门禁、以及 AI 时代的审查规范，都在把「匠艺」变成可共享的标准。同时，新张力出现了：当生成代码足够「能用」，区分高手的差别就不再是谁写得快，而是**谁愿意为一段没人要求的整洁负责**。

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 把匠艺理解为「追求完美代码」 | 过度完美是浪费 | 34.6 给止步判据 |
| 2 | 认为匠艺只关乎个人 | 没有组织支持，个人无法坚持 | 用「提供选项」换取组织支持 |
| 3 | 把技术债当作道德问题来审判 | 会制造对立 | 把债登记、定价、排期 |
| 4 | 认为「大泥球」只出现在坏团队 | 它是渐进的、所有人都会贡献 | 用工具与责任划分防范 |
| 🔧 | 第 2 版的匠艺讨论预设「代码由人手写、作者即负责人」 | AI 生成代码让「责任」变模糊 | 补充：AI 协作下，责任不因「不是我写的」而消失；审查与收尾仍是人的职责 |
| 🔧 | 第 2 版对「何时止步」的讨论偏粗略 | 现代有更细的判据（可测量收益优先） | 用第 34 章的止步顺序作为落地版本 |
| 🔧 | 第 2 版未涉及「AI 产出也要被匠艺对待」 | 生成代码同样会变成大泥球的来源 | 补充：把 AI 产出纳入与人工代码同一套质量与重构标准 |
