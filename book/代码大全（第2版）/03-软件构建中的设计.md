# 第 5 章 软件构建中的设计

> **一句话**：设计的第一任务是**管理复杂度**，其他一切设计准则都是从这条推出来的工程后果。

| 节 | 内容 | 结论 |

## 核心精讲

理想设计特性的可度量版本（教学示意，不参与构建）：

```text
[伪代码] 设计质量 → 可观测代理指标

复杂度低          -> 单模块认知负荷可控；单元测试不需要读 10 个文件
ethics/接口小     -> 「接口 ≤ 7 个参数量级」；新调用方不需要读实现
耦合松            -> 改 A 不需要同步改 B 的签名
信息隐藏充分      -> 隐藏的是「易变区」（数据格式、算法、外部依赖）
易改区清晰        -> 需求变化有明确落点
抽象层次一致      -> 同一系统里没有「半个抽象」
可测试            -> 单测不需要全局 setup
```

> **教学示意，不参与构建、不编译、不运行。**

信息隐藏的分层示例——哪些东西**不该**出现在实现里：

```java
// 教学示意代码，不参与构建、不编译、不运行
// 反例（信息泄漏）：调用方需要知道「用户存在哪、怎么排序」
class WrongUserRepo {
    List<User> loadFromDb(String sql, int page, int size); // 泄漏了存储细节
}

// 正例（信息隐藏）：调用方只依赖「能拿到什么」
interface UserRepo {
    Optional<User> findById(UserId id);
    Page<User> page(int page, int size);   // 分页策略仍是实现细节
}
// 隐藏的易变区：底层是 SQL / NoSQL / gRPC / 内存 mock，调用方无感
```

> **教学示意，不参与构建。**

一个简单的「耦合度」探针，用来判断重构是否值得：

```java
// 教学示意代码，不参与构建、不编译、不运行
public final class CoupleProbe {
    // 计算修改一个类时需要同步触碰的类数量（近似「变更半径」）
    public static int changeRadius(Class<?> c) { /* 扫描其字段/方法签名引用 */ return 0; }
    // 经验阈值：> 5 通常意味着抽象层次不一致，进入重构候选
}
```

> **教学示意，不参与构建。**

## 版本演进

| 维度 | 第 1 版（1993） | 第 2 版（2004） | 2015–2026 |
| --- | --- | --- | --- |
| 主线 | 以「对象设计」为主 | 把**管理复杂度**明确为设计第一原理，层次从「模块」细化到「类与子程序」 | 复杂度管理被重述为「认知负荷」理论 |

| 现代补强 | — | — | 依赖注入容器、端口与适配器（六边形）成为「松散耦合」的主流实现；ADR 记录设计决策 |

## 近年研究与工业界开源实践（2015–2026）

趋势：复杂度管理从**人的自觉**转向**工具的可视化 + 结构的惯例化**。依赖图工具、静态分析里的「圈复杂度/认知复杂度」告警、ADR（架构决策记录）把设计决策显式化，让「设计是迭代过程」不再是借口。此外，AI 辅助编码让「设计先行」重新变重要：生成代码能把坏抽象原样放大，而好抽象能被快速复用。

| 仓库 | star | 说明 |
| --- | --- | --- |
| `github/codeql` | **10122** | 把「坏抽象」的坏味道写成可查询规则 |
| `sonarsource/sonarqube` | **11024** | 认知复杂度门禁，5.2 的量化版 |
| `golangci/golangci-lint` | **19398** | 结构约束（如禁止循环依赖）的自动检查 |
| `pre-commit/pre-commit` | **15594** | 设计约束的执行点 |

## 常见误区与本书需修正之处

| # | 误区 | 说明 | 修正 |
| --- | --- | --- | --- |
| 1 | 把设计的层次理解成「系统—子系统—模块—包—类—子程序」就完了 | 层次是**视角**不是分级；同一层可以从任一方向看 | 用「抽象是什么」定义层，而不是用大小 |
| 2 | 把启发式清单当规矩背 | 作者明确说启发式是「建议」 | 每条启发式配一个反例判断 |
| 3 | 以「设计是启发式」为借口无限设计 | 5.4 的回答是「做多少才够：到能写出通过测试的第一个实现就够」 | 用时间盒 + 原型 + 快速反馈定界 |
| 4 | 为了抽象而抽象（过度工程） | 第 2 版已警告继承滥用 | 先有第三处重复，再抽公共抽象（Rule of Three） |
| 🔧 | 第 2 版 2004 年的设计词汇缺少「依赖注入 / 端口与适配器 / 限界上下文」 | 它们是「松散耦合」在 2020 年代的成熟形态 | 补充：接口定义放在消费方而非实现方，是 2026 年的默认约定 |
| 🔧 | 对「设计是自然而然形成的」表述偏玄学 | 现代认知科学给出了解释与边界 | 用「设计产出可用假设—用测试/原型证伪」替代「自然涌现」的说法 |
| 🔧 | AI 辅助编码场景下，坏抽象会被生成代码放大 | 模型倾向于复现上下文中的模式 | 生成前先给抽象骨架；生成后把「抽象一致性」加入评审清单 |
