# 第 4 章　处理状态变化

> 原书第 4 章是把第 2 章「watch」真正用起来的章，也是**主从实战的开篇**。它用一个贯穿第 4–6 章的
> master-worker 示例，演示如何用 watch 在「任务出现 / 成员变化」时做出反应。这一章只讲
> 「正常路径下的状态变化处理」，故障留到第 5 章，陷阱留到第 6 章。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 注册监视点 | 在 `exists/getData/getChildren` 时传入 watch，分别在「创建/数据变/子列表变」时触发 | 不同读操作注册的 watch 捕获的事件类型不同，要选对 API |
| 事件类型与处理 | `NodeCreated / NodeDeleted / NodeDataChanged / NodeChildrenChanged` 的处理分支 | 收到事件后**必须重读状态并重注册 watch**，否则漏事件 |
| 主从示例：结构 | `/workers`、`/tasks`、`/assign`、`/status` 四棵子树及其语义 | 这一棵「黑板树」是整个实战的骨架 |
| 主从示例：主 | master watch `/workers` 与 `/tasks`，出现待办任务就派给某 worker（`/assign/worker-X/task-N`） | master 是「读事件 → 写派发」的反应式循环 |
| 主从示例：从 | worker watch 自己的 `/assign/worker-X`，收到任务就执行并写回 `/tasks/.../status` | worker 是「等派发 → 执行 → 写回」的循环 |
| 主从示例：客户端 | client 创建 `/tasks/task-N` 并 watch 其 `status` 子节点 | 任务结果通过「状态子节点 + watch」回传 |

## 核心精讲

（以下为教学性梳理，Java 片段均**教学示意，不参与构建**。）

### 4.1 选对 watch 的注册点

不同读操作能感知的变化不同，这是写对 watch 的前提：

| 注册 API | 能触发的事件 | 典型用途 |
| --- | --- | --- |
| `exists(path, watch)` | 节点被创建 / 被删 / 数据变 | 关注「某路径是否存在」（含还没创建时） |
| `getData(path, watch)` | 被删 / 数据变（**不含**子节点变） | 关注「这个节点的内容」 |
| `getChildren(path, watch)` | 子节点列表变（增/删；**不含**某子节点内容变） | 关注「组成员 / 任务清单」 |

> 常见坑：`getChildren` 的 watch **不会**因「某子节点的数据变了」而触发，只会因「子节点增删」触发。
> 要感知子节点内容，得分别对每个子节点 `getData(..., watch)`。

### 4.2 事件处理的标准闭环

```java
// 教学示意，不参与构建：收到事件后的标准动作
public void process(WatchedEvent e) {
    if (e.getType() == Event.EventType.NodeChildrenChanged) {
        // 1) 重新拉最新状态
        List<String> kids = zk.getChildren(watchedPath, true); // 2) 立即重注册 watch
        // 3) 对"新增/消失"的成员做差量处理
        reconcile(kids);
    }
}
```

- **三步缺一不可**：处理事件 → 重读最新 → 重注册 watch；
- 若只在 `process` 里做事却不重注册，下次变化就**收不到**了（第 2 章讲过 watch 一次性）。

### 4.3 主从示例的「黑板树」

```text
# 教学示意，不参与构建：master-worker 的 znode 布局
/workers
    /worker-1        (临时节点，worker 在线即存在)
    /worker-2
/tasks
    /task-00000001   (持久顺序节点，待办任务)
        /status      (子节点，存 RUNNING/DONE + 结果)
    /task-00000002
/assign
    /worker-1
        /task-00000001   (master 派给 worker-1 的任务)
    /worker-2
```

| 子树 | 写入者 | 监听者 | 语义 |
| --- | --- | --- | --- |
| `/workers` | worker（临时节点） | master | 组成员：谁在线 |
| `/tasks` | client | master | 待办任务清单 |
| `/assign/<worker>` | master | 对应 worker | 派发结果 |
| `/tasks/<id>/status` | worker | client | 任务进度/结果 |

### 4.4 master 的派发循环

```java
// 教学示意，不参与构建：master 反应式派发
// 1) master 监听 /tasks 与 /workers
zk.getChildren("/tasks", taskWatcher);
zk.getChildren("/workers", workerWatcher);

void onNewTask() {
    List<String> tasks = zk.getChildren("/tasks", true);     // 重注册
    List<String> workers = zk.getChildren("/workers", true);
    for (String t : tasks) {
        if (alreadyAssigned(t)) continue;
        String w = pickWorker(workers);                      // 选一个 worker
        zk.create("/assign/" + w + "/" + t, data, ..., PERSISTENT);
    }
}
```

- master **不在收到事件时抢着改**，而是「拉最新清单 → 做差量 → 派发」，避免并发重复派发；
- 真正生产里 master 还要防「同一任务派给两人」——靠「先 `exists(/assign/<w>/<t>)` 再 create，
  捕获 `NodeExistsException`」实现幂等（第 5–6 章展开）。

### 4.5 worker 的执行与回写

```java
// 教学示意，不参与构建：worker 侧
zk.getChildren("/assign/worker-1", assignWatcher);  // 等派发

void onAssigned() {
    for (String t : zk.getChildren("/assign/worker-1", true)) {
        byte[] spec = zk.getData("/tasks/" + t, false, null);   // 取任务内容
        byte[] result = run(spec);
        zk.create("/tasks/" + t + "/status", result, ..., PERSISTENT); // 写回结果
    }
}
```

> 注意回写的是 `status` **子节点**而非覆盖 `/tasks/<t>` 本身——这样 client 只需 watch `status`，
> 与「任务内容」和「任务进度」关注点分离。

## 版本演进

- **本书无第二版**；本节写 2013 年口径 → 2026 年视角的变化。
- **这套「watch + 差量重读」范式今天多由 Curator 的 `NodeCache / PathChildrenCache / TreeCache`
  接管**（第 8 章），手写 `process` 分流容易漏重注册，生产应优先用缓存封装。
- **etcd 的「持久监听 + MVCC Revision」让「错过事件」问题天然缓解**：客户端带 `watch(fromRev)`
  可续传，不必像 ZK 这样靠「读最新值」补；这是选型时 watch 模型的根本差异（见第 1、2 章）。
- **「任务队列」场景今天更常用专门 MQ（Kafka/Pulsar）**，ZK 队列只是教学级配方，真实高吞吐任务
  分发不建议用 ZK 顺序节点硬扛。

## 近年研究与工业界开源实践（2015–2026）

- **Curator 的 Cache 体系**：`apache/curator`（3173★）的 `NodeCache / PathChildrenCache / TreeCache`
  把「4.2 的三步闭环」封装成「本地缓存 + 自动重注册 + 事件回调」，是本章手写代码的生产替代。
- **etcd 的 watch + MVCC Revision**：`etcd-io/etcd`（52309★）支持带历史 revision 的监听续传，
  直接缓解 ZK「watch 一次性、易漏事件」的固有缺陷。
- **Kafka / Pulsar 接管任务流**：`apache/pulsar`（15339★）等消息系统把「任务分发」从 ZK 配方里
  解脱出来，说明第 4 章示例更适合「教学 + 轻量协调」而非「高吞吐队列」。
- **ZK 自身**：`apache/zookeeper`（12811★）的 watch 语义在 3.5+ 稳定，未做本质改动。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「收到事件就代表拿到了最新数据」 | 事件只说「变了」，**不含新值**，必须再读一次 |
| 2 | 「处理完事件 watch 自动续上」 | watch **一次性**，处理分支里必须重注册，否则漏后续事件 |
| 3 | 「getChildren 的 watch 能感知子节点内容变」 | 只感知子节点**增删**，内容变要各自 getData 注册 |
| 4 | 「master 收到事件立刻改就行」 | 并发下会重复派发；要「拉全量 + 幂等创建」做差量收敛 |
| 5 | 🔧 第 4 章未提 Curator Cache 封装 | 2026 年生产代码用 `NodeCache/PathChildrenCache` 替代手写 process 分流 |
| 6 | 🔧 未对比 etcd 持久 watch | ZK 一次性 watch 的漏事件问题在 etcd 靠 revision 续传天然解决，选型必读 |
| 7 | 🔧 未提示「ZK 队列仅教学级」 | 高吞吐任务分发应用 MQ，避免把 ZK 当通用队列压 |
