# 第 5 章　故障处理

> 原书第 5 章是主从实战的「抗压」章：第 4 章只跑了正常路径，这一章把**连接丢失、会话过期、
> 主/从/客户端崩溃**逐一砸进来，演示如何让你的协调逻辑在故障后正确恢复。这是全书最「工程」的一章——
> 它不教你新 API，而是教你怎么把第 3–4 章的 API 用得**在故障下仍然正确**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 连接丢失（ConnectionLoss） | 网络抖动 / server 切换导致 `ConnectionLossException` | 操作结果**未知**，必须靠 `exists`/幂等收敛，不能当失败 |
| 会话过期（SessionExpired） | 超时窗口内无心跳，server 清掉临时节点与会话 | 旧会话的一切（临时节点、watch）**全部作废**，必须重建 |
| 幂等设计 | 用「先 `exists` 再 `create`、捕获 `NodeExists`」「带版本 CAS」让重试安全 | 故障恢复的主旋律就是「可安全重试」 |
| 主故障与恢复 | master 崩溃后其临时节点消失，新 master 选出后要**重建派发状态** | 新主必须「重扫 /tasks 与 /assign 差量」而非盲目重派 |
| 从故障与恢复 | worker 崩溃后 `/workers/<id>` 临时节点消失，其未完成任务需由 master 重新派发 | 用「任务归属节点不存在 + 任务未完成」识别孤儿任务 |
| 客户端故障 | client 崩溃不影响任务执行，但需处理「会话消失 → watch 失效」 | client 重连后要**重新注册所有 watch** |
| 可恢复的异常分类 | 可重试（ConnectionLoss）/ 不可重试（SessionExpired）/ 需业务判断（NodeExists） | 异常分类决定「重试 / 重建 / 放弃」三种策略 |

## 核心精讲

（以下为教学性梳理，Java 片段均**教学示意，不参与构建**。）

### 5.1 连接丢失：结果未知，切勿当失败

```java
// 教学示意，不参与构建：ConnectionLoss 下的"探活收敛"
try {
    zk.create("/assign/w1/task-1", ..., PERSISTENT);
} catch (ConnectionLossException e) {
    // 不知道服务端到底建没建成功
    if (zk.exists("/assign/w1/task-1", false) != null) {
        return;            // 已建好，视为成功
    } else {
        zk.create("/assign/w1/task-1", ..., PERSISTENT); // 没建，重试
    }
}
```

- 核心原则：**连接丢失 ≠ 操作失败**。ZK 的写都走 leader 全序，服务端要么做了要么没做，
  客户端用 `exists` 探一下就知道了（呼应第 3 章伏笔）。
- 「探活 + 重试」本身要包在循环里，并设最大重试次数，避免无限重试。

### 5.2 会话过期：一切归零，必须重建

```java
// 教学示意，不参与构建：会话过期的处理
public void process(WatchedEvent e) {
    if (e.getState() == Event.KeeperState.Expired) {
        // 旧会话已死：临时节点、watch 全没了
        zk = new ZooKeeper(connectString, sessionTimeout, this); // 重建句柄
        reinitialize();   // 重建所有 watch、重新声明自己的临时节点
    }
}
```

- 会话过期后，**所有临时节点被删、所有 watch 失效**——这是 ZK 回收「失联成员」的机制，也是你
  必须「重建 + 重注册」的原因；
- 重建后不能假定旧状态还在，要重新走一遍「声明身份（建临时节点）+ 注册 watch」的初始化。

### 5.3 幂等：让任意一步都可安全重来

| 手段 | 做法 | 防什么 |
| --- | --- | --- |
| `exists` + `create` 捕获 `NodeExistsException` | 先查再建，建重了就当成功 | 重复派发同一任务 |
| 带版本 CAS（`setData(path, data, version)`） | 版本不符抛 `BadVersionException` | 覆盖别人刚写的进度 |
| 任务状态机（NEW→ASSIGNED→RUNNING→DONE） | 只对「当前态合法」的转移生效 | 已完成任务被重复执行 |

```java
// 教学示意，不参与构建：幂等派发
if (zk.exists("/assign/" + w + "/" + t, false) == null) {
    try { zk.create("/assign/" + w + "/" + t, ..., PERSISTENT); }
    catch (NodeExistsException ignore) { /* 别人刚建了，幂等忽略 */ }
}
```

### 5.4 主崩溃后，新主如何不「重复派发」

- master 用**临时节点** `/master` 声明身份（第 6 章选举会展开）；原主崩溃 → `/master` 消失 →
  新主当选；
- 新主上任第一件事**不是立刻重派所有任务**，而是：
  1. 扫 `/tasks` 得到全部任务；
  2. 扫 `/assign/*` 得到已派发的任务；
  3. **只派发「在 tasks 里、但 assign 里没有」的任务**；
- 这样即使旧主在崩溃前已派发但未写回，新主也不会重复派（因为 assign 里已有记录）。

### 5.5 worker 崩溃：孤儿任务回收

- worker 崩溃 → `/workers/<id>` 临时节点消失 → master 通过 watch 知道该成员下线；
- 但 `/assign/<id>/*` 是**持久**节点（派发记录），不会随 worker 消失；
- master 识别孤儿任务：「`/assign/<id>/<t>` 存在，但 `/workers/<id>` 不存在，且 `/tasks/<t>/status`
  未完成」→ 把该任务重新加入待派发池，派给还在线的 worker。

## 版本演进

- **本书无第二版**；本节写 2013 年口径 → 2026 年视角的变化。
- **Curator 的 `RetryPolicy` + `ConnectionStateListener` 已把 5.1–5.2 的「探活/重建」封装掉**
  （第 8 章）：生产代码一般只声明「连接状态变化时要做什么」，不必手写 `exists` 重试骨架。
- **会话过期的根因（GC 长暂停、网络分区）在云原生环境更常见**，2026 年更强调
  `sessionTimeout` 与 JVM GC / 容器调度超时的配合（见第 10 章调优）。
- **etcd 的 lease（租约）语义与 ZK 会话类似但更轻**，且 `Revision` 让「探活收敛」可用
  `txn` 原子判存，不必像 5.1 那样 round-trip 两次。

## 近年研究与工业界开源实践（2015–2026）

- **Curator 的 `RetryPolicy` / `ConnectionStateListener`**：`apache/curator`（3173★）把 5.1–5.2 的
  手写重试/重建变成声明式，是本章代码的生产替代。
- **etcd lease + txn**：`etcd-io/etcd`（52309★）用 `lease` 实现临时语义，`txn` 原子判存，
  把「探活收敛」的两步合并为一个原子操作，比 ZK 的 `exists+create` 更稳。
- **Kubernetes 用 etcd 的 lease 实现 Pod/节点健康检查**，是「会话/租约式成员管理」的大规模工业实现，
  与本章 worker 临时节点机制同构。
- **Jepsen 风格的故障注入测试**（2013 起）让「连接丢失/会话过期后是否仍一致」成为可证伪命题，
  是本书时代还没有的工程维度（呼应第 9 章内部正确性）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「ConnectionLoss 就是失败，直接报错」 | 结果未知，必须 `exists`/幂等收敛后再定论 |
| 2 | 「会话过期后旧 watch 还在」 | 会话过期 = 临时节点 + watch 全作废，必须重建句柄并重注册 |
| 3 | 「master 崩溃后新主重派所有任务」 | 会重复执行；要先差量（tasks 与 assign 比对）再补派 |
| 4 | 「worker 崩溃其任务自动回收」 | assign 是持久节点，孤儿任务要 master 主动识别并重新派发 |
| 5 | 🔧 第 5 章未提 Curator 的自动重试/重建 | 2026 年生产代码用 `RetryPolicy` + `ConnectionStateListener` 替代手写骨架 |
| 6 | 🔧 未对比 etcd lease+txn 的原子收敛 | etcd 用 `txn` 一步判存，比 ZK 的 exists+create 更简洁且少一次往返 |
| 7 | 🔧 未提「云原生下会话超时与 GC/调度超时的耦合」 | 容器环境长 GC/调度暂停更易触发过期，调优视角需补（见第 10 章） |
