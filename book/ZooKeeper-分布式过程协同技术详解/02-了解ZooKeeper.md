# 第 2 章　了解 ZooKeeper

> 原书第 2 章是把第 1 章的「黑板」具体化的章：黑板到底是什么结构（znode 树）、有哪些节点类型、
> 会话和监视点怎么工作、有哪些操作和保证。这是后面所有 API 与实战的**词汇表**，
> 读不懂这一章，第 3–8 章的示例代码会处处卡壳。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 数据模型 | znode 树（类文件路径的层次命名空间），每个 znode 存少量数据与元数据 | ZK 数据 = 一棵小数据量的树，不是关系表也不是 KV |
| znode 类型 | 持久（persistent）/ 临时（ephemeral）/ 顺序（sequential），可组合成持久顺序、临时顺序 | **临时节点随会话消失**是「组成员 / leader 选举」的基石；**顺序**提供全局有序序号 |
| 监视点（watch） | 对节点设一次性触发器，变化时被推送事件 | watch 是「变更通知」而非「数据订阅」，且只触发一次 |
| 会话（session） | 客户端与服务器间的 TCP 长连 + 心跳，超时则由服务端判定死亡 | 会话决定临时节点的生死，超时 ≠ 网络瞬断 |
| 操作 | create / delete / exists / getData / setData / getChildren / sync 等 | 操作分读（exists/getData/getChildren）与写（create/delete/setData）两类 |
| 保障（guarantees） | 顺序一致、原子性、单一系统映像、及时性（timeliness） | 这套保证是 ZK「协调内核」的承诺，也是配方可靠的前提 |
| ACL | 以 scheme:id:permission 描述访问控制 | ZK 的权限是**节点级**的，不等同于传输安全（详见第 10 章 TLS） |
| zkCli 实操 | 用 `zkCli.sh` 创建/读取/列举/设 watch，体会命令形态 | CLI 是验证概念最便宜的方式（本目录只引用，不启动） |

## 核心精讲

（以下为教学性梳理，命令行/伪代码均**教学示意，不参与构建**。）

### 2.1 数据模型：一棵小数据量的树

ZK 把协调状态组织成**层次化的命名空间**，路径像文件系统（`/app/workers/worker-1`），
但每个节点（znode）既能挂子节点也能自己存一小段数据（默认上限约 1 MB）。它**不是文件系统**——
没有「目录 vs 文件」之分，每个 znode 既是「目录」也是「文件」。

```text
# 教学示意，不参与构建：一棵典型的 znode 树
/
├── app
│   ├── config          (持久节点，存全局配置 JSON)
│   ├── workers
│   │   ├── worker-1    (临时节点，worker 在线则存在)
│   │   └── worker-2    (临时节点)
│   ├── tasks
│   │   ├── task-0001   (顺序节点，待分配任务)
│   │   └── task-0002
│   └── leader         (临时节点，当前主的身份)
```

### 2.2 znode 类型：临时节点与顺序节点是配方的命根

| 类型 | 行为 | 典型用途 |
| --- | --- | --- |
| 持久（persistent） | 显式删除才消失 | 配置、任务元数据 |
| 临时（ephemeral） | **会话结束即被删除** | 组成员（worker 心跳的等价物）、leader 节点 |
| 顺序（sequential） | 创建时追加单调递增序号 | 锁队列、FIFO 队列、选举的「先来后到」 |
| 持久顺序 / 临时顺序 | 上述组合 | 任务分配（task-0001…）、公平锁 |

> 关键点：**临时节点不依赖心跳轮询**，而是依赖会话——客户端崩了或网络断了直到会话超时，
> 服务器自动清理其临时节点，其余客户端通过 watch 立即看到「该成员已下线」。
> 这正是第 1 章「组成员」需求的服务端实现。

### 2.3 监视点（watch）：一次性的变更通知

客户端可以对 `exists / getData / getChildren` 设 watch。当对应节点变化（创建/删除/数据变/子列表变）
时，服务端推一个**事件**给客户端。要点：

- **只触发一次**：收到事件后要重新注册 watch，否则后续变化不再通知；
- **可能错过**：两次注册之间发生的变化，客户端靠「读最新状态」补偿，而非靠累积事件；
- **事件含类型**：`NodeCreated / NodeDeleted / NodeDataChanged / NodeChildrenChanged`。

```text
# 教学示意，不参与构建：watch 的一次性本质
client A:  getData("/config", watch=true) -> 得到值 v1
server  :  setData("/config", v2)
server  :  推 NodeDataChanged 给 A
A       :  收到事件，但此刻 watch 已失效
A       :  若想继续监听，必须再 getData(..., watch=true)
A       :  若 server 在 A 重注册前又 setData(v3)，A 不会收到 v2->v3 的单独事件，
          只能在下一次读时看到最新值 v3
```

### 2.4 会话（session）：临时节点的生死簿

- 客户端连上某台 server 建立会话，会话有**超时时间（sessionTimeout）**；
- 客户端周期性发心跳（ping）续命；若 server 在超时窗口内没收到任何心跳，
  判定会话过期，**清理该会话的所有临时节点**；
- 会话过期后，客户端会收到 `Expired` 状态，必须重建连接与所有 watch（第 5 章重点）。

### 2.5 保障（guarantees）：协调内核的承诺

原书明确列出四条核心保证，是后面所有配方正确性的来源：

1. **顺序一致（sequential consistency）**：客户端发起的更新按发送顺序被应用；
2. **原子性（atomicity）**：更新要么成功要么失败，无中间态；
3. **单一系统映像（single system image）**：客户端无论连到哪台 server，看到的都是同一份最新状态
   （leader 视角）；
4. **及时性 / 时效性（timeliness）**：客户端读取到的数据会在某个时间界（bounded）内是最新的。

> 严格说 ZK 的写是**线性一致**（经由 leader 的 zxid 全序），读在 follower 上是「单一系统映像 +
> 时效界」级别。这和第 9 章 Zab 的广播顺序直接相关。

## 版本演进

- **本书无第二版**；本节写 2013 年口径 → 2026 年视角的变化。
- **容器节点（container znode）与 TTL 节点是 3.5+ 新增**，原书只有持久/临时/顺序三类；
  容器节点在「父删子也删」的管理场景（如 Curator 的某些配方）很有用，第 2 章类型表需补。
- **节点数据上限从「硬 1 MB」变为可调**（`jute.maxbuffer`），但「协调小数据」的定位不变；
  把大 payload 塞进 ZK 仍是反模式。
- **ACL 仍非传输安全**：2013 年如此，2026 年仍如此——节点级 ACL 解决「谁能操作节点」，
  链路加密要等 SASL/TLS（第 10 章 3.5+ 才完整支持），二者别混为一谈。
- **ZK 3.5+ 的 AdminServer**：原先靠四字命令，后增加基于 HTTP 的管理面（见第 10 章）。

## 近年研究与工业界开源实践（2015–2026）

- **etcd 的 MVCC + 监听（watch 流）**：`etcd-io/etcd`（52309★）的 watch 是**持久事件流**而非一次性，
  且在服务端维护监听树——这与 ZK「一次一注册、可丢事件」形成鲜明对照，是选型时的关键差异
  （见第 1 章）。
- **Consul / Nacos 的 KV + 会话/健康检查**：`hashicorp/consul`（30087★）、`alibaba/nacos`（33419★）
  同样提供「节点树 + 会话/健康探针 + watch（或长轮询）」，在「服务注册发现」场景直接对标 ZK。
- **Curator 对节点类型的扩展封装**：`apache/curator`（3173★）把临时/顺序/容器节点的创建与
  自动清理包成 `PersistentEphemeralNode`、`Container` 等，降低第 2 章概念的心智负担（见第 8 章）。
- **ZK 自身 3.5+**：容器节点、TTL 节点、`jute.maxbuffer` 可调、AdminServer，是本章「类型与运维」
  在 2013 年之后的实际演进。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「watch 是持久订阅，能重放历史事件」 | watch **只触发一次**且可能丢事件；补偿靠「读最新值」，不能当事件总线 |
| 2 | 「临时节点靠心跳轮询维持」 | 临时节点靠**会话**，server 在超时窗口无心跳即清，客户端无需轮询 |
| 3 | 「ZK 是文件系统，能存大文件」 | 每 znode 只存小数据（默认 ~1 MB，且可调但定位不变），是协调元数据不是对象存储 |
| 4 | 「ACL 等于安全」 | ACL 是**节点级授权**，不含链路加密；传输安全靠 SASL/TLS（第 10 章） |
| 5 | 「读到 follower 就一定是最新」 | follower 读是「单一系统映像 + 时效界」，强一致需 `sync` 或读 leader；详见第 9 章 |
| 6 | 🔧 第 2 章类型表缺容器节点 / TTL 节点 | ZK 3.5+ 引入，现代配方常用，需补入类型表 |
| 7 | 🔧 未提示「watch 一次性」在客户端库里的封装差异 | Curator/etcd 客户端把重注册包成「持久监听」，易让人误以为 ZK 原生支持，需点明 |
