# 第 9 章　ZooKeeper 内部原理

> 原书第 9 章是从「使用者」跨到「理解者」的章：前面你只管 `create/getData`，这一章揭开
> 写请求是如何在**一组服务器之间保持一致**的——核心就是 **Zab（原子广播协议）**、**领导者选举**、
> **仲裁（quorum）**，以及背后的**日志 / 快照 / 内存树 / 序列化**。读懂这一章，前面的「顺序一致、
> 单一系统映像、会话」才落到实处。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 请求处理链 | 读由任意 server 直接回（内存）；写走 leader：PREP → PROPOSAL → ACK → COMMIT → 应用 | 读快（本地内存）、写慢（要多数派确认），这是 ZK 的性能画像 |
| 原子广播 Zab | 两阶段：恢复（选主+同步）→ 广播（正常提交）；保证事务按 leader 顺序全序交付 | Zab 是「主备复制 + 全序广播」，不是 Paxos 但同谱 |
| 领导者选举 | 按 `(zxid, sid)` 择优：事务越新优先，其次 id 大优先；获多数票者当选 | 选出的 leader 必含**所有已提交事务**，这是正确性的根 |
| 仲裁（quorum） | 写需 `n/2+1` 多数派 ACK；2n+1 容忍 n 失败 | 集群必须奇数台，脑裂时靠多数派不双活 |
| 事务日志与快照 | `FileTxnLog` 追加写事务；`FileSnap` 定期dump内存树；恢复时「快照 + 重放日志」 | 重启快、崩溃可恢复，且日志可针对性 fsync |
| 内存数据树 | 整棵 znode 树常驻内存（`DataTree`），这是 ZK「小数据、低延迟」的代价与来源 | 数据必须小，内存放得下；这也解释了 1 MB 上限的来由 |
| 序列化（jute） | 用 `.jute` 描述生成序列化代码，事务/请求/响应都走它 | 紧凑二进制，是跨 server 与落盘的格式基础 |

## 核心精讲

（以下为教学性梳理，伪代码/示意均**教学示意，不参与构建**。）

### 9.1 一个写请求的一生

```text
# 教学示意，不参与构建：写请求的 Zab 流程
Client -> Follower: create(/x)
Follower -> Leader: 转发写请求
Leader:  PREP   (生成 zxid = <epoch, counter>，做本地校验)
Leader:  PROPOSAL(zxid, 变更) -> 发给所有 follower
Follower: 落盘事务日志(可批量 fsync) -> 回 ACK
Leader:  收到多数派 ACK -> COMMIT(zxid)
Leader:  将变更应用到内存 DataTree
Leader -> Follower: COMMIT 通知
Follower: 应用变更到自己的 DataTree
Leader -> Client: 返回成功
```

- **读**不需要这个流程：任意 server 直接从内存 `DataTree` 返回（带第 2 章的「时效界」）；
- **写**必须过 leader 且拿到多数派 ACK，所以写延迟取决于「leader→follower 往返 + 日志 fsync」。

### 9.2 Zab：两个模式

| 模式 | 时机 | 做什么 |
| --- | --- | --- |
| 恢复模式（recovery） | 启动 / leader 崩溃 | 选主 + 新主与 follower 对齐「已提交事务」，保证不丢已提交 |
| 广播模式（broadcast） | 正常运行 | 对每笔事务走 9.1 的 PROPOSAL/ACK/COMMIT，保证全序 |

- Zab 的保证：**① 已提交的提案，新 leader 一定拥有；② 所有正常 server 按相同顺序看到事务**。
- 与 Paxos 区别：Zab 是**为「主备状态复制」定制**的广播协议（primary-backup），强调「顺序一致地
  把所有状态变更复制到副本」，而非通用的「对单个值达成共识」。

### 9.3 领导者选举：凭什么选它

```text
# 教学示意，不参与构建：选举的择优键
投票键 = (zxid, sid)
  zxid: 本机见过的最大事务 id（越高 = 数据越新）
  sid : 服务器 id（zxid 相同时用大 id 兜底）
规则: 每张票投"当前已知键最大者"；某候选获 多数派(>n/2) 票 -> 当选
```

- 因为按 `zxid` 择优，**新 leader 必然拥有所有已提交事务**，从而恢复模式结束后不丢已提交数据；
- 选举本身也走「多数派」——这正是 9.4 仲裁的体现，保证不会出现两个都被多数认可的 leader。

### 9.4 仲裁（quorum）与 2n+1

- 设集群 `N` 台，仲裁大小 `Q = floor(N/2) + 1`；
- 写需 `Q` 个 ACK 才提交 ⇒ 任意两个仲裁**必有交集** ⇒ 不会出现「两组各自提交」的双写；
- 容错数：`N=2f+1` 时最多容忍 `f` 台宕机（N=3 容 1，N=5 容 2）。**偶数台浪费**（4 台也只容 1）。

### 9.5 日志、快照与内存树

| 组件 | 角色 | 关键点 |
| --- | --- | --- |
| `DataTree`（内存） | 整棵 znode 树常驻内存 | 读快、必须小数据、是 1 MB 上限的根本原因 |
| `FileTxnLog` | 追加式事务日志，每条含 zxid | 顺序写 + 可批量 fsync，是持久性与顺序的来源 |
| `FileSnap` | 周期性把内存树 dump 成快照 | 重启时「加载最近快照 + 重放其后日志」比全量重放快 |

- 恢复流程：先找最新快照还原到某时刻状态，再**只重放快照之后的事务日志**，补齐到最新；
- 这解释了为什么 ZK 重启很快、且崩溃不丢已提交数据。

### 9.6 序列化：jute

- ZK 用自研的 **jute** 序列化（由 `.jute` 描述文件生成编解码代码），覆盖请求、响应、事务记录；
- 紧凑二进制，落盘日志和跨 server 传输都用它；这层决定了「线上 wire format」的稳定性。

## 版本演进

- **本书无第二版**；本节写 2013 年口径 → 2026 年视角的变化。
- **Zab 的「与 Paxos 等价 / 正确性证明」在学界后续有更多形式化工作**，但工业实现基本稳定；
  想深究应与 Raft 对照——2014 年 Raft 论文让「更易理解的共识」成为主流，第 9 章可作为
  「主备广播」视角的对照样本（见 [../深入理解分布式共识算法/00-总览与阅读地图.md](../深入理解分布式共识算法/00-总览与阅读地图.md)）。
- **ZK 3.5+ 的「动态重配置」**让集群成员变更不再需要停服改 `zoo.cfg` 重启，是运维层的重要演进
  （见第 10 章），其内部即 Zab 对「配置变更作为特殊事务」的支持。
- **存储与快照策略多年稳定**，但「日志与快照分离到不同盘（`dataLogDir`）」的调优建议至今有效
  （见第 10 章）。

## 近年研究与工业界开源实践（2015–2026）

- **etcd 用 Raft（非 Zab）**：`etcd-io/etcd`（52309★）的共识走 Raft，与 ZK 的 Zab 形成「同类目标
  两种协议」的经典对照；理解第 9 章 Zab 后，再读 Raft 会格外通透（见共识算法书）。
- **Consul / Nacos 同样基于 Raft**：`hashicorp/consul`（30087★）、`alibaba/nacos`（33419★），
  说明「协调服务内部用 Raft」已成主流，Zab 主要留守 ZK 自身。
- **BookKeeper / Pulsar 依赖 ZK 做元数据与协调**：`apache/bookkeeper`（2013★）、
  `apache/pulsar`（15339★）把 ZK 当作「元数据 + 选主」底座，是 ZK 内部机制（Zab/选举）的真实消费者。
- **Kafka KRaft 去除 ZK**：Kafka 自 3.3 起用自带 Raft（KRaft）替代 ZK，是「原依赖 ZK 内部协调、
  后自研共识」的工业样本，改写第 9 章「谁在用 Zab」的清单。
- **ZK 自身**：`apache/zookeeper`（12811★）3.8/3.9 线持续维护，Zab 内部实现稳定。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「ZK 是数据库，数据落盘才返回读」 | 整棵树在内存，读走内存、写才落日志；这正是小数据/低延迟定位 |
| 2 | 「任何 server 都能写」 | 写必须经 leader 提交（follower 转发），只有读可本地返回 |
| 3 | 「Zab = Paxos」 | Zab 是主备状态复制的**广播**协议，目标不同于「对单值达成共识」的 Paxos |
| 4 | 「偶数台集群也能容同样多的错」 | N=4 与 N=3 都只容 1 台，偶数浪费，应用 2n+1 |
| 5 | 「重启要从头重放全部日志」 | 先加载最近快照再重放其后日志，恢复很快 |
| 6 | 🔧 第 9 章未与 Raft 对照 | 2026 年共识主流是 Raft，读 Zab 时应把 Raft 当作对位物（见共识算法书） |
| 7 | 🔧 未提 3.5+ 动态重配置 | 集群成员变更已可在线进行，内部即「配置作为特殊事务」，需补 |
| 8 | 🔧 未提 KRaft 去 ZK | Kafka 自研 Raft 替代 ZK 共识，是「协调内部实现」的工业转向，需补 |
