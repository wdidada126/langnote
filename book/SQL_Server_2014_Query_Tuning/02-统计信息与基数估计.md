## 2.1 为什么基数估计是「一切下游决策之源」

优化器的成本模型单位是抽象代价，而每个算子的代价几乎都乘以其基数：
- 索引查找 vs 扫描：选择率决定 Seek 的回表税是否划算（05 章 G1 🔧 演示 124× 差距如何随选择率翻转）。
- 连接算法：小×大→嵌套循环，两大→哈希/合并（04 章）。
- 内存授予与并行度：按估计行数折算，估小了 spill 到磁盘，估大了白占资源。
- 自适应改写：如是否展开标量子查询、是否做 Distinct 聚合消除，都由基数判断触发。
结论句（调优第一定律）：**「计划坏，先查行数差」**——比较估算行与实际行的比值，是所有排障流程的第一步（03/12 章）。

## 2.2 统计信息的物理形态（转述 ⚠️）

每个统计对象覆盖一组列（表级自动统计或用户 CREATE STATISTICS，过滤统计可带 WHERE 谓词），内部三件套：
1. **头信息**：对象 ID、最后更新时间 rows_mod_ratio 类字段（2014 为行数阈值，2016+ 改为动态密度阈值）。
2. **密度向量**：前缀列组合的平均不重复度 1/∞distinct，服务多列等值组合与无前导列谓词。
3. **直方图**：≤201 个阶梯（RANGE_HI_KEY/相等计数/范围/平均选择率），服务单列的范围、点查与 TOP 估计。
DBCC SHOW_STATISTICS 三结果集分别对应三者；调优者至少会读「密度=1/键值数」和「直方图桶宽」。✅ statistics 页。
**采样本质**：统计基于 SAMPLE 子集构建，大表默认采样率极低 → 数据偏斜时桶外推误差大（工业上用 `WITH FULLSCAN`/`SAMPLE n PERCENT` 权衡更新成本 ⚠️）。

## 2.3 自动统计：创建与更新的阈值

- 自动创建：无统计可覆盖的谓词列首次查询即建（sys.auto_stats 可见）。
- 自动更新（2014 时代表达式）：表列修改计数 > 500 + 20%×行数 → 触发；对百万行大表意味着**一次更新窗口可积压 20 万行变化**，基数长期失真。
- 缓解手段 ⚠️ 转述：`ALTER TABLE ... REBUILD`/`UPDATE STATISTICS ... WITH FULLSCAN` 排班；追踪表对高频改动列放宽阈值或加过滤统计；`TEXT/Image` 大列不入统计的坑（旧版本）。
- 陷阱清单：
  - 统计只记录「分布」，不记录「列间相关」→ 多谓词按独立性假设相乘（2.5 🔧G5 演示误差谱）。
  - 临时表统计在各连接会话独立、可能陈旧；跨步骤大临时表应显式建统计或保持行数在预估域。
  - 列存另有持久化统计差异（10 章）。

## 2.4 2014 分水岭：新基数估计器（兼容级 120）

SQL Server 2014 在数据库 COMPATIBILITY_LEVEL=120 下启用源自 Azure SQL DB V12 的**新 CE**（✅ cardinality-estimation-sql-server 页）。模型差异要点（转述 ⚠️）：

| 场景 | 传统 CE（≤110） | 新 CE（≥120） |
|---|---|---|
| 等值无匹配 | 猜测密度或常数级修正 | 假设「不存在则 1 行」类简化 |
| 谓词相关性 | 全部独立相乘 | 引入部分相关性假设（重叠区间修正） |
| 不等式/范围 | 直方图桶严格外推 | 常量选择性先验（对越界值衰减） |
| BETWEEN | 两端同直方图 | 按等宽先验折减 |
| OR/IN 大列表 | Expensive-OR 保守 | 去重+选择率合成改良 |

- 数据库级开关：`LEGACY_CARDINALITY_ESTIMATION`（ Scoped CONFIGURATION，2016+ 才有细粒度回退；2014 当年只能整库兼容级回退 ⚠️）。
- 升级实操：兼容性测试时成对比较 110/120 的计划与耗时；「升级后变慢」的头号元凶即 CE 换代而非硬件（与 07 章计划漂移互证）。

## 2.5 🔧 本机类比：密度、直方图与估计误差谱（非本书引擎行为）

**实验 A（SQLite 3.45.3）**——统计对象里的「密度」长什么样：
```sql
-- t2(k1,k2) 50万行：k1∈{1,2} 且偏斜(470000:30000)，k2 均匀 1000 值
ANALYZE;  -- 生成 sqlite_stat1
SELECT * FROM sqlite_stat1;
-- ix3(k2): '500000 500'   -- 平均 500 行/键 → 密度≈1/1000
-- ix2(k1): '500000 250000'-- 平均 25 万行/键 → 对偏斜的 k1=2(实际3万) 是 8 倍高估
```
如实登记：本例 `WHERE k1=2 AND k2=5` 在 ANALYZE 前后计划都选了更优的 ix3——SQLite 默认启发已接近，**统计的可见产出是数字而非必然的计划翻转**；SQL Server 中直方图缺位时的密度兜底正是同一角色。

**实验 B（DuckDB 1.5.5）**——独立性假设的两端误差：
```
EXPLAIN 估计 vs 实测：
status='A' AND cust=1234   → 估计 ~89 行，实际 0 行（cust 与 status 完全相关，误差 ∞）
amount>1000                → 估计 ~100,000 行，实际 150,479 行（低估 33%）
amount>1000 AND status='A' → 估计 ~125,000 行，实际 37,626 行（高估 3.3 倍：乘性合成）
```
方法：range(500000) 造表，cust=i%5000、status=i%4、amount=(i*i%9973)/7，`EXPLAIN` 取 ~N rows 标注、`fetchone()` 取实际。三行数字构成「相关/越界/乘性」误差谱，与 2.4 表中新 CE 试图修正的场景一一对位。

## 2.6 调优者的统计工具箱（⚠️ 转述 + 示例形态）

- `CREATE STATISTICS s_orders_cust_ts ON orders(cust) WITH FULLSCAN, STATS_STREAM ...`——偏斜列全采样；过滤统计 `WHERE status='A'` 服务热点切片。
- `UPDATE STATISTICS ... WITH RESUME`（2014 无 RESUME，属后续演进；当年用 `NORECOMPUTE` 与作业分片 ⚠️）。
- 混合度量：对比 `DBCC SHOW_STATISTICS` 与实跑行数，把误差 >10× 的统计列入维护清单（12 章基线流程）。
- 多列相关性怀疑时：**拆谓词单独测行数**，用 `OPTION (RECOMPILE)` 现场观察，或直接建组合统计覆盖该工作负载切片。

## 核心概念速览（中英对照）

- **统计信息** — Statistics:列分布元数据（头/密度向量/直方图），优化器代价估计的燃料。
- **直方图** — Histogram:≤201 阶梯的分布近似，服务范围与点查选择率。
- **密度向量** — Density Vector:前缀列组合平均不重复度 1/distinct。
- **过滤统计** — Filtered Statistics:带 WHERE 的切片统计，对热点子集更细。
- **自动统计** — Auto Statistics / sys.auto_stats:优化器按需创建维护的统计。
- **采样率** — Sample Percent:统计构建读取的行比例，偏斜数据与大表的矛盾焦点。
- **基数估计器** — Cardinality Estimator (CE):估计行数的模型系统，2014 换代。
- **兼容级别 120** — Compatibility Level 120:启用新 CE 的数据库开关。
- **独立性假设** — Predicate Independence:多谓词选择率相乘的默认模型。
- **内存授予** — Memory Grant:按估计行数折算的执行内存，估错即 spill 或争用。
- **溢出到磁盘** — Spill:排序/哈希超出授予内存后的 tempdb 落盘。
- **选择率** — Selectivity:谓词保留行比例，CE 的基本计价单位。

## 最新演进与工业实践

- **2016→2022 CE 持续修正**：130/140/150/160 逐级都有基数行为变更（如 2019 起内联表变量参与估计），微软官方建议「每次提升兼容级都当一次引擎换代做回归」。✅ https://learn.microsoft.com/en-us/sql/relational-databases/performance/cardinality-estimation-sql-server
- **智能查询处理对统计盲区的兜底**：自适应连接（2017+）在执行期按实际行数改投 Hash/Merge；记忆化（2022）缓存行数以修正反复误估——相当于把 CE 的一部分搬到运行时。✅ intelligent-query-processing 页。
- **数据库作用域配置细粒度回退**：`ALTER DATABASE SCOPED CONFIGURATION SET LEGACY_CARDINALITY_ESTIMATION = ON`（2016+）与查询提示 `OPTION (LEGACY_CARDINALITY_ESTIMATION)`，比整库换兼容级温和得多。⚠️ 转述。
- **大表统计维护工业化**：Ola Hallengren 作业套件按索引/统计分策略刷新（抽样率与阈值可配）是社区事实标准；Azure SQL 自动调优中的「强制统计更新」检测即该痛点的云托管化。⚠️ 生态现状转述。
- **理论文献**：直方图等高桶 vs V-optimal 权衡可溯到 Pochampally et al.（⚠️ 未复核 DOI，仅给题录）；现代列存统计（持久化 vs 内存）与本时代差异见 10 章演进节。
