## 5.1 Seek 还是 Scan：一条成本不等式 ⚠️

非聚集索引查找的总账 = 索引层级页读（深度 ~3-4 页/Seek 首访）+ **匹配行数 × 回表随机页读**（Key Lookup，去重后按页摊）；扫描 = 表的顺序页读全量。调优判读规则：
- 回表行数少（选择性高）→ Seek 胜；行数大→随机 IO 乘法爆炸→Scan 反胜。
- 「优化器选了扫描」不等于索引无用：多数情形是它在正确执行上述不等式。
- 覆盖化（INCLUDE/键序包含）把回表项清零，是改写这条不等式的**唯一治本杠杆**——G1/G2 演示其量级。
- 索引上的 residual `WHERE`（Scan-with-predicate）仍要读全部索引页，只是比表窄：列存式「窄扫描」思路在行存的对应物。

## 5.2 🔧 实验 G1/G2：Seek 红利与覆盖红利（非本书引擎行为）

SQLite 3.45.3，orders 表 500,000 行（cust=i%5000、status=i%4、amount/ts 派生列）：
```
G1 无索引：SELECT COUNT(*) FROM orders WHERE cust=1234 AND status='A'
   计划 SCAN orders                    21.1 ms
   建 ix_orders_cust_status(cust,status) 后
   计划 SEARCH ... USING COVERING INDEX  0.2 ms   → ≈124× 
G2 覆盖 vs 回表：
   SELECT status ... WHERE cust=1234  → COVERING INDEX            0.1 ms
   SELECT amount ... WHERE cust=1234  → USING INDEX（需取表列）    0.8 ms   → ≈8×
```
- G1 对应 5.1 的不等式两侧；G2 的 8× 就是「回表项」的可测代价（SQLite 主键即 rowid，回表≈RID Lookup；SQL Server 非聚簇索引回基表为 Key Lookup，量纲同源、常数不同——**故标注非本书引擎**）。
- 迁移到 SQL Server 的读图法：实际计划里 Key Lookup 算子的行数以千计且父 Seek 行数大 → 上 INCLUDE 或调整键序（判读规则与 🔧 数字互证）。

## 5.3 SARGability 清单：谓词写法决定能否 Seek（⚠️ 转述+示例）

可 Seek（同列比较侧无函数包裹、类型匹配）：
- `col = @v`、`col > @v`、`BETWEEN`、前缀 `LIKE 'abc%'`、`IN (@a,@b)`（折成分段 Seek 或 Spool+Seek）。
- `col + 0 > 100` 这类**常量折叠**能救回；但 `YEAR(orderdate)=2014` 不能——改写为 `orderdate>=2014-01-01 AND <2015-01-01` 的**半开区间**是标准处方（06 章同款）。
必死写法（列侧函数/转换/隐式提升）：
- 列上任何函数/运算：`SUBSTR(code,1,3)=@c` → 持久化计算列+索引，或改写法。
- 隐式类型转换：`varchar` 列配 `nvarchar` 参数（优先级规则向 nvarchar 提升列）→ **ORM 参数类型钉死**是第一处方；计划 XML 里 CONVERT_IMPLICIT 警告即此（03 章）。
- `OR` 跨列：可能退化为 Expensive-OR（索引求并+位图）或全扫；拆 UNION ALL 让每支各自 Seek 是可控处方。
- 前缀通配 `LIKE '%x'`：本质无解，考虑全文/列存（10 章）或倒排思路（跨引擎对照 [../Fundamentals_of_Database_Indexing/00-总览与阅读地图.md](../Fundamentals_of_Database_Indexing/00-总览与阅读地图.md)）。

## 5.4 索引设计速则（与 Strate 卷对位的调优子集）

- 键序：等值列在前、范围列在后；排序消除需求可反向决定键序（ORDER BY 列进键，INCLUDE 补载荷）。
- INCLUDE：宽列、从不过滤只投影的列；换 8× 级回表税（🔧G2）。
- 窄索引税：每索引写放大+碎片（机制在 [../SQL_Server_2012_Internals/05-索引内部结构与管理.md](../SQL_Server_2012_Internals/05-索引内部结构与管理.md)，维护节奏在 [../Expert_Performance_Indexing_SQL_Server_2019/09-索引维护.md](../Expert_Performance_Indexing_SQL_Server_2019/09-索引维护.md)）——调优者只需一条决策线：**读路径红利 > 写放大成本才建**。
- 重复/重叠索引清理：`sys.dm_db_index_usage_stats` 的 user_seeks/scans/lookups 组合 + 键序前缀包含判据（工业巡检脚本化，12 章）。
- 索引视图（2000-2014 一贯）：预连接/预聚合，需 schema_binding+确定性函数+ANSI 选项钉死；企业版才可免费用自动匹配，标准版必须查询能直接引用 ⚠️ 版本约束。

## 5.5 分区与切换：大表访问路径的旁路 ⚠️

- 分区=同一逻辑表的多个物理单元；查询带分区键谓词才**分区消除**，否则全分区扫描——「建了分区不等于会消除」，读图看 `Partition ID`/Static/Dynamic 消除属性。
-  SWITCH 分区交换是分钟级加载/归档通道（对齐 [../Pro_SQL_Server_Internals/10-数据分区.md](../Pro_SQL_Server_Internals/10-数据分区.md)）；调优语境里它替代大 DELETE。
- 2014 标准版分区限制（1000 分区为企业版特性；分区数上限差异 ⚠️ 版本条款）。

## 5.8 访问路径工坊：九个「为什么不走我的索引」判词

1. 键序首列没被等值命中 → B-tree 定位从第一列起，缺前导=无 Seek 资格。
2. 列被函数/转换包裹 → 5.3 必死清单。
3. 谓词类型与参数不匹配 → CONVERT_IMPLICIT 上列侧（06 §6.5-1）。
4. 匹配行数占比过宽 → 5.1 不等式站扫描一边，是正确决策。
5. 统计骗人（偏斜）→ 02 直方图核对。
6. 缓存里挂着别时刻的坏计划 → 07 嗅探。
7. 分区键无谓词 → 5.5 消除失败。
8. 碎片/页密度极端恶化 Seek 成本 → 维护窗口复核（Strate 卷 09）。
9. 索引被 DISABLE/离线重建中 → 变更单核对。

## 5.10 一页口诀

> 前导定生死、等值先、范围后、排序列进键；
> 列裸类型配、SARG 才成立；

## 核心概念速览（中英对照）

- **索引查找** — Index Seek：B-tree 定位到匹配区间的访问路径。
- **索引扫描** — Index Scan：全量读索引/表页，窄索引扫描优于宽表扫描。
- **回表** — Key/RID Lookup：非聚簇命中后按行指针取基表列。
- **覆盖索引** — Covering Index：键+INCLUDE 含全部所需列，回表项归零。
- **SARGable** — 可搜索谓词性质：列侧无函数、类型匹配的等值/范围比较。
- **隐式转换** — Implicit Conversion：数据类型优先级改写列侧表达式，废 Seek。
- **Expensive-OR** — 优化器对跨列 OR 的索引合并策略（带行数保护）。
- **持久化计算列** — Persisted Computed Column：函数表达式的可索引替身。
- **分区消除** — Partition Elimination：分区键谓词裁剪物理分区。
- **ALTER TABLE SWITCH** — 分区交换：元数据级批量加载/归档通道。
- **索引视图** — Indexed View：schema-bound 物化连接/聚合。
- **写放大** — Write Amplification：每加一索引对写路径的乘法成本。
