## 1.0 管线图（转述口径的记忆锚）

```
批处理文本
   │ 解析器 parse
   ▼
语法树 ──绑定元数据──▶ 关系表达式树(Tree)
   │ 简化/规范化（重写规则·自顶向下+自底向上交替）
   ▼
规范化树 ──▶ 公共判据子树缓存 CCB
   │ 搜索（转换规则 × 实现算子，按表数分档）
   ▼
候选计划集 ──代价模型(统计信息驱动)──▶ 选定计划(执行树)
   │ 编译产物进计划缓存
   ▼
执行引擎（iterator 拉取 · 内存授予 · 并行调度）
```

## 1.1 一条查询的旅程：从批处理到行

SQL Server 的关系引擎把一条语句的生命周期切成「编译（optimization/compilation）」与「执行（execution）」两个世界，调优工作 90% 落在两者的接缝上：

1. **解析与绑定（parse & bind）**：T-SQL 批处理被分析器拆成语法树，关系引擎对照元数据绑定对象名、解析视图、展开星号、做名称限定。语义错误在此抛出，尚未涉及性能。
2. **规范化**：语法树被转换为关系代数式的内部表达式树（Tree），做平凡化重写：常量折叠、可结合算子下压、`NOT( NOT x )` 消去、将 `IN/EXISTS/OR/INTERSECT/EXCEPT` 尽量重写为连接。
3. **公共判据子树（CCB, Common Criteria Buffer）**：把候选方案中重复的子表达式送进公共判据缓存，对每个子树独立寻优并缓存其最优子计划的判据，避免组合爆炸下的重复估价。这是理解「为什么加一张表会让整条计划面目全非」的关键：子计划的最优性是上下文相关的，CCB 命中与否改变搜索路径。⚠️ 转述（Learn intelligent-query-processing 系列口径；名称按社区通译「公共判据/Common Criteria Buffer」，官方未给出统一中译）
4. **搜索与成本估计**：在规则（transformation）× 物理算子（implementation）张开的搜索空间里，用统计信息驱动的代价模型给候选计划打分，选最低者。
5. **执行**：执行引擎按数据流拉取模型（Volcano 式 iterator）逐算子驱动；此时真正决定性能的是行数、内存授予与 IO 形态——而它们全都建立在第 4 步的**基数估计**之上。本章的总论点：优化器是一个「猜测机器」，调优者的工作是让它的猜测接近现实。

## 1.2 搜索策略分档（经典 Books Online 口径 ⚠️）

经典文档对连接搜索空间的三档策略（转述自旧版 BOL「query optimization」条目，新版并入 Learn 性能文档族 ⚠️ 未逐字复核原页）：

| 参与连接的基表数 | 搜索策略 | 后果 |
|---|---|---|
| ≤9 表 | 穷举全部连接顺序与交换律组合 | 编译时间随表数阶乘式增长 |
| 10–16 表 | 限制为「最优若干」顺序的受限搜索 | 顺序质量开始让位于编译耗时 |
| >16 表 | 启发式贪心 | 优化器明确放弃全局搜索，计划质量高度依赖写法 |

工程含义：宽表星型/雪花模型多连接查询在 SQL Server 上「编译慢 + 计划未必最优」是结构性现象，不是 bug；对超复杂语句要考虑拆分、临时表物化以把每个子语句拉回穷举档（06 章展开）。临时表物化打断搜索空间的机制与 [../Pro_SQL_Server_Internals/14-查询优化执行与计划缓存.md](../Pro_SQL_Server_Internals/14-查询优化执行与计划缓存.md) 的「分而治之」讨论一致。

## 1.4 优化器不可见之手：三个贯穿全书的概念

1. **可行计划 ≠ 最优计划**：优化器只在「它能想到的」实现里选择；把某物理算子踢出搜索空间（如不满足合并连接的排序要求）与「该算子更贵」是两件事，读计划时要区分（03 章）。
2. **估计驱动执行**：内存授予、并行度、算子选择全部来自估计；基数错一处，级联放大（02 章 G5 🔧 类比演示估计误差谱）。
3. **搜索是有预算的**：优化是编译期行为，受成本阈值截断；参数嗅探使同一语句在不同时刻拥有不同预算与不同统计背景，因而「计划随机漂移」（07 章）。

## 1.5 版本语境：2014 在优化器谱系中的位置

- SQL Server 2005 引入现代优化器骨架；2008 增表值参数/日期类型；**2014 的核心变化是「新基数估计器」上线（数据库兼容级别 120 启用，源自 Windows Azure SQL Database V12 的选择性模型）**——对老 SQL Server 调优书的最大冲击即在此：大量「2008 时代经验」在 120 下失效（02 章专节）。✅ 依据 cardinality-estimation-sql-server 页。
- 后续演进到 2019/2022 的「智能查询处理」（自适应连接、延迟模式综合、表变量内联、记忆化）见各章末「最新演进」节；本书出版时（⚠️ 疑 2014）这些均不存在。

## 1.5a 规范化阶段常见的重写（示例为示意性 T-SQL，⚠️ 非原书代码）

- 常量折叠：`WHERE amount + 0 > 100` 先折叠为 `amount > 100` 再判可否走索引（折叠救回 SARGable，见 05 章）。
- `IN → Join`：`WHERE cust IN (SELECT id FROM vip)` 常被重写为半连接，再由 04 章的算子选择决定 NLAP/HSAP/MAJOIN。
- `OR → 合并/展开`：同列 OR 可能折为范围查找；异列 OR 触发 Expensive-OR 或转 UNION 模式（读实际计划时按次数看真实分支）。
- 标量聚集子查询 → 聚合连接：`(SELECT COUNT(*) FROM orders o WHERE o.cust=c.id)` 变 GROUP BY+LEFT JOIN，为后续哈希/流聚合铺路。
- 视图内联、CTE 展开：视图与公用表表达式没有独立物理身份，优化在展开后的树上进行。

## 1.5b 代价模型的成分（转述口径 ⚠️）

- I/O 成本：以页为单位，区分随机/顺序读，与缓冲区池命中率无直接建模关系（内存内容影响执行不影响估计）。
- CPU 成本：算子逐行处理成本与聚集调用成本叠加。
- 内存与并行：授予粒度、线程派发与交换（exchange/spool）的并行税——并行不是免费午餐，行少时优化器主动放弃并行。
- 等待成本：2014 系代价模型是「查询完成时间」代理而非资源账，锁与阻塞不进入编译期代价（这正是 11 章存在的理由）。

## 1.7 常见误区（各一条，防身用）

1. 「优化器挑了扫描说明索引没用」——错：估计行数大或键序不匹配时扫描更便宜，先看估计行数与实际的差。
2. 「加 WITH (NOLOCK) 提速是常规操作」——错：那是牺牲一致性换吞吐的脏读开关，属 11 章病理而非 01 章药方。
3. 「计划缓存命中=快」——只对编译部分成立；执行成本与命中与否无关。
4. 「重写规则是黑魔法不可预期」——大部分重写有固定形态，可用 03 章的实际计划反推（见各章反查表）。
5. 「并行度越高越好」——优化器的成本阈值与 max degree of parallelism 共同截断，OLTP 高并发下过度并行诱发调度税（12 章方法论）。
6. 「统计信息自动更新了就万事大吉」——自动更新阈值（老式 20%+500）在大表上滞后，是基数误估的头号来源（02 章）。

## 核心概念速览（中英对照）

- **查询处理器** — Query Processor：关系引擎中负责编译与执行查询的部件总称。
- **解析与绑定** — Parse & Bind：语法树构建与元数据名称解析阶段，错误在此抛出。
- **规范化** — Normalization/Simplification：常量折叠、谓词下压、IN/OR 转连接等代数重写。
- **公共判据子树** — Common Criteria Buffer (CCB)：候选子计划判据缓存，控制搜索空间组合爆炸。
- **转换规则** — Transformation Rule：等价重写规则，扩大可考虑的计划集合。
- **实现算子** — Implementation / Physical Operator：逻辑算子的物理落地（如 Join→NL/Hash/Merge）。
- **搜索空间** — Search Space：规则×实现张开的候选计划集合，按表数分档穷举或启发。
- **成本模型** — Cost Model：以 IO/CPU/内存/线程加权的目标函数，非真实时间。
- **基数估计** — Cardinality Estimation：优化器对每步输出行数的猜测，一切下游决策之源。
- **兼容级别** — Compatibility Level：数据库行为开关，120 起用新基数估计器。
- **Volcano 迭代器模型** — Volcano/Iterator Execution：算子按 open/next/close 拉取驱动的执行方式。
- **编译时间** — Compilation Time：优化本身的耗时，复杂语句可超过执行耗时。
- **表达式树** — Expression Tree (Tree)：解析绑定后的内部代数表示，规范化的作用对象。
- **谓词下压** — Predicate Pushdown：把过滤尽量移到数据源头，缩小上游算子输入。
- **半连接** — Semi Join：EXISTS/IN 语义的物理化形态，只回传真匹配行。
