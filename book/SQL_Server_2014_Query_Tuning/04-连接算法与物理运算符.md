## 4.1 三大连接算法的代价形态（调优判读版）

| 算法 | 输入要求 | 代价骨架 | 内存行为 | 典型翻转点 |
|---|---|---|---|---|
| 嵌套循环 NL (Inner/Fetch/Alias) | 无 | 外侧行数 × 内侧单次查找成本 | 近零 | 外侧估计行数「很小」时被选中；实际行数大 → 灾难呈乘法放大 |
| 合并连接 Merge (Inner/Outer/Full) | 双侧按键有序（索引序或 Sort） | 线性扫 + 排序税 | 低（可部分 spill） | 双侧大且已有序时最优；一侧无序时 Sort 成本决定生死 |
| 哈希连接 Hash (Build/Probe) | 无 | 建小侧哈希 + 扫大侧 | 建侧需授予内存 | 两大表无索引序的默认解；授予不足则递归 spill |

- 2014 的 Hash Match 同时承担聚合（Glob/Partial）；并行计划常见 Partial+Spin 的多阶段形态，读图别误认成两次连接（03 章）。
- 交叉连接/笛卡尔积出现在无连接谓词或优化器改写中间态，实际行数为两侧乘积=红灯（03 决策树）。

## 4.2 连接顺序：优化器怎么排、你怎么帮

- ≤9 表穷举顺序、>9 受限、>16 贪心（01 章 1.2 分档）。
- 外连接限制：`LEFT JOIN` 链可被自由重排的程度受「保留语义」约束；谓词位置（ON vs WHERE）决定外连接能否被简化为内连接——**这是写法层面影响连接树的第一开关**（06 章展开）。
- 半连接/反连接形态：EXISTS→Semi，NOT IN（可空列）→带 Assert 的 Anti，NOT EXISTS→Anti；NOT IN + 可空子查询列会被强制保守形态，索引选择随之改变 ⚠️。
- 辅助手段：多列键连接时先做基数裁剪（日期/租户过滤）比任何提示都稳；大表连接的「先聚合再连接」重写是最普适的顺序干预（等价性注意分组键唯一性）。

## 4.3 内存授予与 spill 的观测路径 ⚠️

- 授予按估计行数×行宽折算；估计错→授予错→spill 或争用，形成「基数错误→磁盘错误」的级联（02 章 G5 误差谱的现实版本）。
- 观测：实际计划的 `SpillToTempDb` 警告；`sys.dm_exec_query_memory_grants` 的 granted vs required；等待类型 `PAGEIOLATCH_*/PAGELATCH_*` 与 tempdb 争用（12 章等待视角）。
- 处方顺序：先修统计/参数化（治估计），再调 max grant/资源治理（治后果），最后才考虑改写（治形态）——与 08 章提示滥用红线一致。

## 4.4 排序消除与有序性传递（🔧G4 类比）

SQL Server 视「有序」为可消耗资产：聚簇索引前缀序可满足 ORDER BY/ORDER 需求，从而消灭 Sort 算子并让 Merge 免单。SQLite 3.45.3 的同款语义本机实证（**非本书引擎行为**）：
```
EXPLAIN QUERY PLAN SELECT id FROM orders ORDER BY id LIMIT 100;
  → SCAN orders                       （rowid 序即聚簇序，排序免费）
EXPLAIN QUERY PLAN SELECT id FROM orders ORDER BY amount LIMIT 100;
  → SCAN orders + USE TEMP B-TREE FOR ORDER BY   （= SQL Server 的 Sort 代价）
```
判读同构：见到 `Segment`/无 Sort 的窗口函数计划=有序性红利；见到 Segment 前的 Sort=索引没建对键序（05 章）。

## 4.5 跨引擎对位（与 MySQL 优化器章节的镜像表）

| 知识点 | SQL Server（本章） | MySQL 5.x（Understanding_MySQL_Internals/09） |
|---|---|---|
| 连接选择 | NL/Merge/Hash（2014 无 Hash 于内存储引擎，优化器可选） | 当年只有 NL 家族+索引驱动，BNL 兜底 |
| 顺序决策 | 成本模型穷举 | 贪婪+成本混合，顺序敏感于索引可用性 |
| 半连接 | EXISTS→Semi/索引探查 | 子查询物化或 semi-join 策略 |
| 计划可见性 | SHOWPLAN XML 全属性 | EXPLAIN 极简，后补 FORMAT=TREE（演进节） |
| 调优杠杆 | 统计+索引+提示+重写 | 索引+重写（当年无 CBO 级提示自由度） |

对照结论：同一句 SQL 在两引擎的「坏计划」成因高度同构（行数误估/有序性缺失），这也是 🔧 类比可跨引擎迁移的底气。

## 4.6 聚合与去重的物理形态 ⚠️

- Stream Aggregate：要求输入按分组键有序，常配 Segment 做部分聚合；并行下 Partial→Gather→Final 三段。
- Hash Aggregate：无序大分组，代价含建哈希+spill 风险。
-  Distinct 的选择性：`COUNT(DISTINCT)` 在 2012 前有「顺序+分段」改写史，2014 主要按基数决定；宽表大去重是内存授予重灾区。
- 窗口函数：ROW_NUMBER 族借排序消除实现，UDF 无果（Spool）；分页查询的 `OFFSET/FETCH`（2012+）计划形态=Sort+Top，索引序可整体免单（05 章实操）。

## 4.7 🔧 本机类比：连接形态的可见性（非本书引擎行为）

DuckDB 1.5.5（哈希连接节点直读）：
```
EXPLAIN SELECT count(*) FROM o JOIN (SELECT DISTINCT cust FROM o WHERE amount>500) s USING(cust)
物理计划骨架：UNGROUPED_AGGREGATE ← HASH_JOIN(Inner, ~8,804,366 rows) ← SEQ_SCAN(~500,000) / HASH_GROUP_BY(~100,000)
```
- `~8,804,366` 是**估计输出行数=对上游误差的乘性放大**的活标本：建侧/探侧估计各含误差，连接节点把误差相乘（对照 4.3 级联链条）。
- SQLite 无哈希连接（NL+索引为主），其 `SEARCH ... USING INDEX` 嵌套形态正是「外侧每行一次内侧 Seek」的 NL 教科书结构——50 万行 demo 中外侧若误小，成本立即乘爆（G1 数字的另一读法）。

## 4.9 算法工坊：七种「连不上/连得慢」的形态判读

- 想走 Merge 却先 Sort：连接键无索引序——05 键序处方（把连接键做成前导列）。
- Hash 建侧选了大表：外侧行数被低估（02/07），交换表序的提示只作归因实验（08）。
- NL 外侧 20 万行：估计 says 小、实际 says 大——比值诊断直达 02 §2.5 误差谱。
- 聚合后连接仍爆炸：连接键含分组粒度外的列，先聚后连不成立（4.2 重写注意）。
- 窗口函数慢在 Sort：PARTITION/ORDER 键序与索引错配（4.6，🔧G4 同理）。
- 半连接形态消失（EXISTS 变全扫连接）：子查询列可空性改变 Anti 形态（4.2）。
- 并行计划比单线程更慢：Exchange 税+倾斜分发（Repartition 键基数不足），MAXDOP 治理（12.5）。

> 有序是资产、授予是押金、tempdb 是当铺；

## 核心概念速览（中英对照）

- **嵌套循环连接** — Nested Loops Join:外行驱动内查找，吃「外侧小」的估计。
- **合并连接** — Merge Join:双有序线性合流，有序性红利最大化者。
- **哈希连接** — Hash Join:建小侧哈希探大侧，两大表默认解。
- **Build/Probe 侧** — 哈希连接构造侧与探测侧；错侧建大表=灾难。
- **半连接/反连接** — Semi/Anti Join:EXISTS/NOT EXISTS 的物理化。
- **有序性传递** — Order Preservation:索引序/Sort 输出被下游算子消耗的性质。
- **排序消除** — Sort Elimination:用有序输入替代 Sort 算子的优化。
- **内存授予** — Memory Grant:执行前按估计行数预扣的内存配额。
- **溢出** — Spill:授予不足时哈希/排序落 tempdb。
- **部分聚合** — Partial Aggregate:并行计划的本地预聚合阶段。
- **误差放大** — Cardinality Error Propagation:上游估计误差沿树相乘。
- **批量模式** — Batch Mode:列存引入的向量化执行形态（2014 限列存触发）。

## 最新演进与工业实践

- **自适应连接（2017+）**：执行期按实际行数在 NL↔Hash/Merge 间改投，直接封堵 4.1 的「外侧估计小」陷阱；默认关闭、需兼容级+查询存储环境。✅ intelligent-query-processing 页。
- **批量模式行存储（170+）**：行存扫描也能进批执行，Hash/聚合的 CPU 账整体重算——本表 4.6 的结论对现代版本要重新校准 ⚠️。
- **Serverless/Azure 的内存授予自动校正**：查询存储历史分位数反推授予，工业上「spill 即告警」进入自动治理。⚠️ 生态转述。
- **MySQL 对照演进**：8.0.18+ 引入 Hash Join、8.0.20 起 EXPLAIN FORMAT=TREE——4.5 表中「当年只有 NL」的不对称已反转收敛（[../Understanding_MySQL_Internals/09-解析器与优化器.md](../Understanding_MySQL_Internals/09-解析器与优化器.md)）。
- **DuckDB 作为分析侧参照系**：本目录 🔧 组的现代向量化引擎代表；工程界把「行式 vs 批式」的直觉训练交给 DuckDB 演示已成低成本惯例（本机 1.5.5，非本书引擎）。
