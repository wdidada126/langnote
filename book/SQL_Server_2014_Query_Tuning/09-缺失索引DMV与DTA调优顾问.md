## 9.1 缺失索引 DMV 族：优化器的「事后自白」⚠️ 转述

四视图分工：
- `sys.dm_db_missing_index_details`：哪张表、等值列（equality_columns）、不等值列（inequality_columns）、被渴望的 INCLUDE 列（included_columns）——即 05 §5.4 键序规则的机器生成端。
- `sys.dm_db_missing_index_groups`：把「组」关联到多条语句需求。
- `sys.dm_db_missing_index_group_stats`：user_seeks/user_scans、avg_*_cost、avg_user_impact（**编译器想建而没建的账本**）。
- `sys.dm_db_missing_index_columns`：函数式逐列查询入口。
判读纪律五条：
1. 只反映**考虑过而被拒**的访问路径，不反映写放大与维护成本——它天然鼓吹多建索引。
2. 无分区/视图/列存拓扑感；不评估碎片与排序消除链。
3. `avg_user_impact` 是百分比式抽象，不等于墙钟收益；结合 query_stats 的实际耗时加权。
4. equality>inequality 的顺序就是推荐键序；INCLUDE 列宽要过 05 §5.4 成本线。
5. 长期驻留不衰减（重启清零、无老化）→ 巡检要快照差分，别拿单帧当真理。

## 9.2 DTA：工作负载驱动的调优顾问 ⚠️ 转述

- 输入形态：SQL 文件/表、**缓存内容快照**（sys.dm_exec 族）、Profiler trace（当年）、查询存储（后续版本替代）。
- 调优模式：索引（聚集/非聚集/筛选/空间）、分区、**假设配置**（Hypothetical Indexes——tempdb 内不占真身的纸面索引，评估建议成本用，勿与生产索引混淆；清理有官方脚本口径）。
- 输出：事件级建议、定义脚本、**依赖报告**（建议间交互）、**报表（Server 侧成本/空间/时间三维）**、可配置「最多索引数/保留现有/估计空间上限」。
- 已知局限（社区共识+官方注记 ⚠️）：
  1. 按语句独立最优≠全局最优，建议集常互相重叠/冲突——要人工做前缀合并（05 §5.4 使用统计复核）。
  2. 看不到应用层写路径峰值与维护窗口；空间成本仅静态估计。
  3. 分区建议保守（对齐/ SWITCH 前提不检查业务装载通道）。
  4. 对「先改写法再谈索引」（06）零感知——DTA 永远在现有语句形态下给索引。
- 工业配方：DTA 跑**代表性负载窗口**（高峰切片+夜间批）→ 建议进「假设验证」→ 按 08 §8.4 归因四分法裁决 → 上线走 12 章基线回归。

## 9.3 从建议到索引的裁决流程（本章方法论主件）

```
missing_index 快照/DTA 建议
  → 去重：与现有索引做键序前缀比对（重叠即改 INCLUDE 或弃）
  → 成本线：写放大估计（表日写行数×索引数）、空间、维护窗口
  → 语义线：过滤索引候选（高频切片谓词）、列存候选（聚合扫描族）
  → 验证：假设索引/影子库 AB → 记录 P95 与计划形态变化
  → 上线+登记：纳入使用统计巡检（user_* 列）与 12 章基线
```
- 反面判据（删索引信号）：user_seeks+user_lookups 长期为 0 且非唯一约束载体；写放大显著——治理剧本同流程，「删」比「建」更需要变更管理 ⚠️。

## 9.4 其它「自动建议」的同族（时间盒：2014 生态）

- 索引视图建议：DMV 无此能力，靠工作负载手工识别（05 §5.4）；后续版本 DTA 亦未纳入——登记为工具空白。
- 统计缺口侧：02 章自动统计承担；「自动创建=自动够用」是误区（偏斜大表处方在 02 §2.6）。
- 内存侧：`DBCC MEMORYSTATUS`/目标/页生命周期属 12 章等待与压力线。
- 跨引擎对照：MySQL 无 DTA 同格物（其「索引推荐」散在外围工具）；PG 的 hypopg 扩展=假想索引评估的开源实现——DTA 思想在开源世界的对应物登记 ⚠️ 生态转述。

## 9.5 🔧 本机类比：从查询形态反推索引的极简模型（非本书引擎行为）

SQLite 3.45.3 上「手工 DTA」流程演示（orders 50 万行）：
```
负载语句（含 06/05 混合形态）：
  L1 SELECT ... WHERE cust=? AND status=?          → 键序 (cust,status) 等值在前
  L2 SELECT ... WHERE amount>? ORDER BY ts LIMIT ?  → 建议 (amount,ts)？→ 实际验证：
     建 ix(amount,ts) 后 EXPLAIN: SEARCH USING INDEX 且无 TEMP B-TREE（排序消除达成）
  L3 SELECT count(*) GROUP BY status               → 窄覆盖 (status) 即可
差分纪律：先跑「无索引基线 SCAN」，逐条加建议索引复测耗时与计划文本变化——
即 missing_index 的「想建→验证→裁决」闭环在零权限引擎上的等价练习。
```
方法：EXPLAIN QUERY PLAN 文本 diff + perf_counter；脚本在 tmp/dbwave_w5_sstune。**教学价值**：DTA 的全部黑话（equality/inequality/included）都能用这三条语句自证。

## 9.7 建议工坊：六个真实风格的裁决练习（⚠️ 构造例）

1. details 报 `equality=(cust), included=(amount,ts)`、group_stats impact 97%——但表已日写千万：过 9.3 成本线后改「窄化 INCLUDE 试验一周」。
2. 两条建议键序互为前缀：合并为一条+INCLUDE 差集（9.3 去重）。
3. impact 高但 user_seeks 累计低：语句本身低频，弃。
4. DTA 建议分区、装载通道无 SWITCH：治理不成熟，降级为「按日期过滤索引」观察项。
5. 建议索引视图而查询含非确定函数引用：schema 绑定前提不满足（05 §5.4），先改写法。
6. 假设索引收益巨大但上线后 P95 不动：瓶颈在等待（11）或授予（04）——回 12.2 分层。

## 核心概念速览（中英对照）

- **缺失索引 DMV** — Missing Index DMVs：优化器求而不得的访问路径账本。
- **equality_columns** — 等值谓词列，推荐键序的前段。
- **inequality_columns** — 范围谓词列，键序后段。
- **included_columns** — 渴望的覆盖列（免回表载荷）。
- **avg_user_impact** — 组统计中的抽象收益百分比，非墙钟承诺。
- **DTA** — Database Engine Tuning Advisor：工作负载→索引/分区/假设建议器。
- **假设索引** — Hypothetical Index：tempdb 纸面索引，评估专用需清理。
- **依赖报告** — Dependency Report：建议间交互披露。
- **调优配置文件** — Tuning Template：会话参数（上限/保留/空间帽）。
- **前缀重叠** — Prefix Overlap：建议与现有索引的键序包含关系。
- **写放大** — Write Amplification：索引数的隐性持续成本。
- **影子验证** — Shadow Validation：非生产环境 A/B 上线前演练。

## 最新演进与工业实践

- **DTA 的世纪黄昏**：微软已把调优顾问标记为「不再积极开发」并推荐迁移查询存储+自动调优路线（✅ DTA 页顶部注记口径；旧端点文档随改版漂移，00 §7 登记数条 404）——本目录保留 2014 时代的完整使用心智，现代读者按「云托管自动索引治理」理解其继任者。
- **查询存储即「负载分析器」**：按计划归族的工时统计替代 trace/缓存快照输入（✅ QS 页）；自动调优在其上做「建议→实施→回测→回滚」全自动闭环，缺失索引 DMV 的原始语义仍在其下运转 ⚠️ 转述。
- **开源对应物**：PG hypopg、MySQL 生态的 PT/Index Advisor 类工具；DuckDB 无索引但 `EXPLAIN` 估计可见性使其成为「索引直觉」教学替身（00 §5 立场）。
- **工业化建议治理**：把「建索引=变更」写进 CI（schema 迁移审查+使用统计复审窗口）在社区实践（如 Ola Hallengren 维护矩阵）中已是默认；建议的**生命周期**（引入-验证-复审-退役）比单点建议质量更决定索引库健康 ⚠️ 实践主张。
