## 3.1 三种计划的获取通道与语义差

| 通道 | 命令/界面 | 语义 | 代价 |
|---|---|---|---|
| 估算计划 | `SET SHOWPLAN_XML ON` / SSMS「显示估计的执行计划」 | **不执行查询**，只输出优化器选定计划 | 安全但缺实际行数/时间 |
| 实际计划 | `SET STATISTICS XML/PROFILE ON` / SSMS「包含实际执行计划」 | 执行并逐算子记录实际行数、次数、耗时 | 有观测税；并行时间按线程聚合会失真 |
| 服务器侧捕获 | 计划缓存 DMV（`sys.dm_exec_query_stats` + `sys.dm_exec_sql_plan`）、查询存储（2016+）、XEvents `query_post_execution_showplan` | 事后取证，生产环境正解 | 2014 当年只能走缓存/Profiler 残影 ⚠️ |

判读铁律：**估算计划用来理解「优化器怎么想」，实际计划用来发现「它哪里想错了」**——两者的 EstimatedRows vs ActualRows 比值就是 2.1 调优第一定律的操作化。

## 3.2 图形计划的运算符词典（高频 20 个 ⚠️ 转述）

- 访问类：Clustered/Index Scan（含 WHERE 谓词的扫描=残余过滤）、Index/Clustered Seek、Key Lookup、RID Lookup、Table Spool/Eager Spool（物化复用，常见于递归 CTE 展开与行版本化写 tempdb）、Lookup 的「隐藏成本」= 随机页读。
- 连接类：Nested Loops、Hash Match、Merge Join、Cross Join、Cartesian（行数爆炸红灯）。
- 聚合/排序类：Stream Aggregate、Hash Aggregate（2014 无此独立算子，聚合走 Hash Match(Glob)——到 2019 延迟模式综合才改名，判读年代差异注意 ⚠️）、Sort、Top/Top(N) Sort、Segment（排序消除的分段比较）。
- 改写类：Constant Scan、Table Value Function（内联与否一眼可辨）、Cast/Convert（**Convert 发生在列侧=索引失效信号**，05 章 SARGability）、UDX/UDF 行内展开、Assert（约束检查的隐性算子）、Compute Scalar。
- 并行类：Exchange (Repartition/Broadcast/Gather Streams)、Sort (Merge Interval)——并行计划总耗时≠算子耗时相加。
- 特殊：Spool (Lazy/ Eager)、Window Spool（ROW_NUMBER 族）、Filter（残余谓词）、Row Count Spool。

## 3.3 XML 计划：程序化取证的唯一正解

SHOWPLAN/STATISTICS XML 的关键属性（调优脚本按此过滤 ⚠️ 转述）：
- `RelOp/EstimateRows`、`ActualRows`（属性名 EstimatedRows/ActualRows；多次执行取最大或合计）、`EstimateIO/EstimateCPU`。
- `Warnings` 节点：NO_JOIN_INDEX、NO_INDEX、MISSING_INDEX（09 章）、ROWS_ESTIMATE_ERROR、CONVERT_IMPLICIT（隐式转换！回 05 章）。
- `RunTimeStats`：每个执行线程的 CPU/IO/查询时间——**并行下必须除线程数理解**。
- `StatementOptmLevel` 与 `StatementSubTreeCost`：FULL/SIMPLE 区分；子树成本对比找「大头」。
- 检索模式：`WHERE query_plan.exist('…RelOp[@PhysicalOp="Index Scan"]')=1` 类 XQuery 批量扫描缓存计划，把「哪些语句在做全表扫描」变成可查询的资产清单（12 章基线流程的输入）。

## 3.4 读图的决策树（本章主件）

```
拿到计划
 ├─ 先看第一个偏差：哪个算子 Estimated/Actual 比 >10×？
 │    ├─ 是访问算子 → 统计/CE 问题(02) 或 参数嗅探(07)
 │    └─ 是连接/聚合前 → 上游行数已错，回推最上游偏差算子
 ├─ 再看形态：
 │    ├─ Key/RID Lookup 行数大 → 覆盖化(05)
 │    ├─ Sort 吃 CPU 大 → 索引顺序消除(05) 或 max_dop 重排
 │    ├─ 意外的 NL on 大表 → 估计行数太小(回 02/07)
 │    └─ Spool + tempdb 写大 → 行版本化(11) 或 递归/去重模式
 └─ 最后看警告图标：隐式转换、缺失索引、外键无支撑索引的 Assert。
```

## 3.5 观测陷阱清单（⚠️ 转述为主）

1. STATISTICS PROFILE 的逐行文本与图形不等价，图形隐藏了重算子警告。
2. 实际计划自带执行开销：对 <50ms 的语句误差占比高，别拿单次观测做基线。
3. `SET STATISTICS TIME` 在并行计划里给出的是**跨线程累计 CPU**，与墙钟时间可差数倍。
4. SHOWPLAN_XML 不执行查询，因此参数嗅探发生在「缓存里那条真实计划」上——估计计划≠缓存计划（07 章核心区分）。
5. SSMS「执行计划」标签页渲染的是查询完成后的快照；长跑语句要看 live 监控（后续版本能力，2014 当年靠 Profiler ⚠️）。
6. 同一语句因数据库选项（如 AUTO_CREATE_STATISTICS 关闭）表现不同，读图前先记录环境。

## 3.6 🔧 本机类比：计划文本的「眼睛训练」（非本书引擎行为）

SQLite 3.45.3 的 `EXPLAIN QUERY PLAN` 把本章判读规则压成一行可验证的形态：
```
QUERY PLAN(05 章 G1 场景)：
  (3,0,0,'SCAN orders')                                  ← 全表扫描
  (3,0,0,'SEARCH orders USING COVERING INDEX ix…(cust=?)')← 查找+免回表
G4 排序消除对比：
  ORDER BY id     → SCAN（聚簇序免费）
  ORDER BY amount → SCAN + USE TEMP B-TREE FOR ORDER BY  ← 相当于 SQL Server 的 Sort 算子
```
DuckDB 1.5.5 的 `EXPLAIN` 直接在物理计划节点上打印 `~N rows` 估计（G5 的三行误差谱），相当于把 SQL Server 每个 RelOp 的 EstimatedRows 暴露出来——**「先找估计与实际的倍数差」这条规则在任意引擎的图形文本上都能练**，故作为 00 §5 🔧 组的读图教具。

## 3.8 读图工坊：十个高频图形病灶（一句话判词）

1. Index Scan + 大 ActualRows + 谓词里有函数 → 06 §6.1 写法塌方。
2. Key Lookup 挂在 Seek 后、行数千级 → 05 §5.2 覆盖化红利区。
3. Nested Loops 内侧每轮几十毫秒、外侧万行 → 外侧估计错（07 嗅探或 02 统计）。
4. Hash Match 带 SpillToTempDb → 授予错（04 §4.3），先修估计再谈内存。
5. Sort 占整树成本 50%+ → 有序性资产没用上（04 §4.4、05 键序）。
6. Eager Spool + tempdb 写 → 11.3 版本链或递归展开，查隔离选项。
7. 全计划与昨日同哈希不同形态 → 07 漂移，拉 query_hash 族谱。
8. Assert 频繁出现在写路径 → 外键/约束缺支撑索引（05.4 关联）。
9. 并行 Exchange 两侧行数悬殊 → Broadcast 侧真小则合理，否则上游误估。
10. 标量 UDF 函数宿主循环执行 N 次 → 6.5 第 2 条内联处方。

## 3.9 取证顺序口诀

> 先比值（估/实）、再看形（算法/序）、
> 后看账（IO/CPU/内存授予）、末看警（Warnings 节点）；
> 并行除线程、观测带税心；
> 估计计划读动机、实际计划读现实。

## 核心概念速览（中英对照）

- **估算执行计划** — Estimated Execution Plan:不执行查询的优化器输出。
- **实际执行计划** — Actual Execution Plan:带运行时行数/耗时的实录。
- **SHOWPLAN_XML** — 估计计划的 XML 会话开关。
- **STATISTICS PROFILE/BLOB** — 实际计划的文本/XML 两种旧新形态。
- **估计行数** — Estimated Rows (EstimateRows):优化器给每算子的输入/输出猜测。
- **警告节点** — Warnings:XML 中的 MISSING_INDEX/CONVERT_IMPLICIT 等病灶标记。
- **键查找/ RID 查找** — Key/RID Lookup:非聚集索引命中后回基表的随机 IO。
- **Spool** — Table/Eager/Row Count Spool:计划内物化复用或计数结构。
- **Exchange 流** — Repartition/Broadcast/Gather Streams:并行计划的数据搬运算子。
- **子树成本** — StatementSubTreeCost:XML 中可比的相对成本。
- **优化级别** — StatementOptmLevel:FULL/SIMPLE，反映是否被时间预算截断。
- **隐式转换** — Implicit Conversion:类型不匹配致列侧 CONVERT，索引杀手。

## 最新演进与工业实践

- **实时查询统计与计划观测内置化**：SSMS/Azure 的 Live Query Statistics 与查询存储的「按小时计划回归图」取代了本时代 Profiler 手抓。✅ https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store
- **执行模式推断**（2019+ 计划属性 `ExecutionMode=Row/Batch`）与批量模式行存储扫描（170+）让「行式 vs 批式」直接写在计划里，判读维度新增一行。⚠️ 转述。
- **工具生态**：plan 解析开源/商业件（如查询存储可视化、XQuery 批量扫描脚本库）已成 DBA 常规；工业实践趋势是**把读图规则代码化**进巡检（与 12 章基线合流）。
- **跨引擎对照**：MySQL `EXPLAIN FORMAT=JSON/TREE`（[../Understanding_MySQL_Internals/09-解析器与优化器.md](../Understanding_MySQL_Internals/09-解析器与优化器.md)）与 DuckDB `EXPLAIN ANALYZE` 的节点级实际行数已成开发者日常——SQL Server 系「读 XML 属性」的老功夫在新引擎上有更友好的等价物，招聘/协作语境下值得互相翻译。
