## 7.1 缓存键与复用条件（读病理先读解剖）

- 缓存对象按计划哈希/模板组织：语句文本（参数化后的模板）、所需 ANSI/排序规则/数据库上下文等共同构成**复用谓词**——任一不匹配即新编译（ORM 连接选项漂移=缓存翻倍的第一隐凶）。
- 三种 resident 形态：Ad-hoc（未参数化批）、Prepared（参数化模板）、Stored proc/function/trigger；`sys.dm_exec_cached_plans` 的 objtype/usecounts 是体检入口。
- 驱逐：内存压力（CMEMTHREAD/RESOURCE_SEMAPHORE 类 waits，12 章）按成本老化打分逐出；「缓存巨大但命中率低」=单用计划堆积，处方见 7.4。
- 优化发生在缓存**之外**（编译时刻），执行发生在缓存**之内**（复用时刻）——03 §3.5 第 4 条陷阱的机制版。

## 7.2 参数嗅探（Parameter Sniffing）正名

定义 ⚠️ 转述：编译/重编译时刻，优化器**用当时传入的参数实际值**做基数估计，并把这份计划挂给后续所有参数值复用。于是：
- 幸运嗅探：首值代表性强 → 全员受益。
- 不幸嗅探：首值偏斜（大客户/冷门日期）→ 后续全量值共用一把错误的尺子，行数/算法/授予全面错位（04 §4.3 级联）。
- 触发重编译的任一条件（统计更新、schema 版本变更、编译环境漂移）都会**重新抽签**——这就是「同一条 SQL 昨天快今天慢」的规范解释。
- 判读指纹：
  1. 实际计划首算子行数与缓存内计划估计严重不符（03 决策树）。
  2. `sys.dm_exec_query_stats` 中同一 query_hash 下多个 plan_handle、耗时双峰。
  3. 手动 `OPTION (RECOMPILE)` 后「立刻变好」——嗅探确认性实验（处方之一）。

## 7.3 处方谱系（从温和到烈药）

| 处方 | 动作 | 适用 | 代价 |
|---|---|---|---|
| `OPTION (RECOMPILE)` 查询级 | 每次执行现编现估 | 值分布极散的热点查询 | CPU 换稳定；语句短小可控 |
| `OPTION (OPTIMIZE FOR (@p=常量))` / `UNKNOWN` | 按指定值/统计密度估计 | 典型值明确 | 固化偏差风险 |
| 局部变量隔离 | `@local=@param` 后引用变量 | 让优化器回到密度估计（经典处方 ⚠️） | 失去真值红利 |
| `sp_executesql` 分支包装 | 按值域分支各持专属计划 | 多租户大小客户分流 | 代码复杂 |
| `OPTIMIZE FOR UNKNOWN`+过滤统计 | 密度兜底转精 | 切片稳定 | 维护统计 |
| 计划冻结（Plan Guide） | 缓存外强绑计划 | 升级救火 | 脆断，08 章 |
| 清除单计划 | `DBCC FREEPROCCACHE(plan_handle)` | 应急重抽签 | 瞬时编译风暴注意 |
- 数据库级 `PARAMETERIZATION FORCED/SIMPLE` 与自动参数化调优（后续版本）分界线读演进节。
- **Ad-hoc 膨胀治理**：`sp_configure 'optimize for ad hoc workloads'`（2008+）让单用批先存小存根再升全计划；配 `forced parameterization` 评估，SQL 全文审计先行（06 §6.2）。

## 7.4 缓存卫生体检脚本化（⚠️ 转述查询形态）

- Top-N 单用计划：`cached_plans` 过滤 objtype='Adhoc' AND usecounts=1，按大小排序 → 模板化整改清单。
- 同 query_hash 多计划：`query_stats` 分组计数 → 漂移监视器（配 12 章基线）。
- 缓存大小/外部：`sys.dm_os_memory_clerks` 的 MEMORYCLERK_SQLCACHE/STORE 分账（内存侧机制在边①目录）。
- 工作集健康度：usecounts 直方图——「长寿高复用」占比是 OLTP 缓存质量的北极星。

## 7.5 🔧 本机类比：计划复用的最小模型（非本书引擎行为）

SQLite 3.45.3 的 `sqlite3_prepare` 缓存与「文本变则重编」演示：
```
prep A: SELECT id FROM orders WHERE cust=?  → 复用同一 vm，二次 prepare 耗时 0.000x ms 级
prep B: SELECT id FROM orders WHERE cust = ?（空格变体）→ 文本规范化差异同样命中缓存（SQLite 按规范化键）
DuckDB prepared：EXECUTE 复用同计划对象，参数值变化不触发重优化
  → 即「计划与值解耦」的极简模型：SQL Server 的嗅探之所以存在，
    恰因为它**在编译期把值折进了估计**，比 DuckDB/SQLite 的解耦更激进也更脆弱。
```
教学要点：先见「无嗅探」的干净复用，才能理解 SQL Server「嗅探是特性不是 bug」的措辞（社区共识表述 ⚠️）。方法：python sqlite3/duckdb 双连接对比 prepare/execute 行为，脚本在 tmp/dbwave_w5_sstune。

## 7.6 与升级的战争：缓存层的版本断层 ⚠️

- 兼容级提升=全部计划失效重编（CE/重写规则换代，02 §2.4）→「升级后性能玄学」的 80% 在缓存层结算。
- 灰度配方：双数据库不同兼容级对跑同一参数矩阵；收集 query_hash 级 plan 分布；差异计划逐个走 7.3 处方而非整体回退。
- 参数嗅探的「云终局」：查询存储时代的自动计划纠正见演进节；2014 当年只有手工剧本（本章全部内容的时代框）。

## 7.8 漂移工坊：同一语句多副面孔的案卷分类

- 案卷一「每天 02:00 后变慢」：统计作业更新触发重编译、首值换人 → 02/07 联诊。
- 案卷二「应用重启后忽快忽慢」：连接选项漂移（ANSI nulls/隔离/ARITHABORT）致双份缓存 → 7.1 复用谓词。
- 案卷三「灰度新参数后劣化」：新客户大值被嗅进共享计划 → OPTIMIZE FOR/分支包装。
- 案卷四「索引重建当天劣化」：schema 版本变更引发全体重编、抽签不利 → 7.3 温和谱系。
- 案卷五「字面量 SQL 的 CPU 高」：ad-hoc 风暴，与单语句快慢无关 → 7.4 卫生线。
- 案卷六「同 hash 双计划双峰」：新旧模板共存（拼串改动）→ 全文指纹比对。

## 7.9 应急三斧复核（先诊断后抽签）

1. 确认现场有真实缓存计划可取（03 §3.1 通道三）。
2. `FREEPROCCACHE(plan_handle)` 定点清除前先存档 XML（结案证据）。
3. 清除后观察 5 分钟：若首值再犯，立刻转 7.3 常驻处方——抽签不是治疗。

## 核心概念速览（中英对照）

- **计划缓存** — Plan Cache：编译产物驻留区，按复用谓词命中。
- **参数嗅探** — Parameter Sniffing：编译期以实际参数值定估计。
- **Ad-hoc 计划** — Ad-hoc Plan：未参数化批的一次性缓存对象。
- **查询哈希** — query_hash/query_plan_hash：DMV 中语句/计划归族键。
- **重编译** — Recompilation：统计/架构/环境触发计划更新，嗅探重抽签。
- **USECOUNTS** — 计划复用计数，缓存卫生的体检指标。
- **optimize for ad hoc workloads** — 单用批存根优化服务器选项。
- **FREEPROCCACHE(plan_handle)** — 定点清除单计划的应急手段。
- **OPTIMIZE FOR** — 指定嗅探值或 UNKNOWN 的查询选项。
- **Plan Guide** — 模板/对象级计划冻结通道（08 章）。
- **CMEMTHREAD** — 缓存/内存对象争用等待类型族。
- **漂移** — Plan Drift：同语句跨时间换计划的工程统称。

## 最新演进与工业实践

- **查询存储+自动调优收编嗅探**：2016 起 QS 保留历史计划，「强制上次已知良好计划」是官方内建处方；Azure 自动调优直接自动执行；SQL Server 2022 起 QS 默认开。✅ https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store
- **IQP 对嗅探的软化解**：表变量延迟编译、参数化表变量嗅探（2022/160）、记忆化部分缓解重复编译——传统处方并未过时但适用面在缩。⚠️ 转述。
- **工业实践**：「双峰耗时+多 plan_handle」告警规则进巡检平台是 SaaS DBA 常规；升级兼容级配「计划回归门禁」（按 query_hash 比对 P95）成为迁移方法论——与波5在盘兄弟 Migrating_to_MariaDB（引擎迁移方法论同构题，按需对读）互为跨引擎参照。
- **应急手册地位**：`DBCC FREEPROCCACHE`/RECOMPILE 类「抽签型」手段在托管云（Azure SQL/Managed Instance）部分被禁用或代以强制计划 UI——自治方向是**把抽签变成可审计的决策**。⚠️ 生态转述。
