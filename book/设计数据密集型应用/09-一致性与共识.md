## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 一致性保证 | 一致性 ≠ ACID 的事务隔离，也不是 CAP 的 C | 它是「副本之上程序看到什么」的运行期承诺 |
| 线性一致性 | 最新值保证：读必然看到已完成的最近写（寄存器抽象） | 与可串行化不同：线性一致只谈单对象，且承诺实时序 |
| 顺序保证 | 因果序弱于线性一致；序列号/HLC 追加顺序保证 | 拿不到全局时钟，就用单点定序或逻辑序 |
| 共识问题与算法 | 全体节点对同一值达成一致且不可反悔 | FLP 证明纯异步无解 → 工程选择：超时（部分同步） |
| 单主复制与共识 | 共识 = 决定性的单主复制 + 疑似故障时的正确换主 | 手写「心跳选主」几乎必错；用成熟库 |
| etcd/ZooKeeper 与共识服务 | 线性一致 CAS、租约、watch；可作锁/配置/服务发现 | 共识服务给的是「小而硬」的原语，不是通用数据库 |
| 成员变更与容错 | 多数派存活才可用；f = 2n+1 容 n 故障 | 2PC 是「协调者挂了全体卡死」，共识不是——这是本质差别 |

## 核心精讲

### 9.1 线性一致性的读法

线性一致（linearizability）要求：一旦某写操作完成，**之后开始**的任何读都必须看到
该写（或更新的值）。等价理解：所有操作看起来都发生在「开始与结束之间的某个瞬间」，
且这个瞬间序与实时序一致。

```
教学示意（不参与构建）：
t1: x=0
写 W(x=1) 在 t3 完成
读 R 若开始于 t4 → 必须返回 1          ← 线性一致
读 R 若在 t3 前开始 → 可返回 0          ← 合法
```

工程含义：
- 需要 quorum 读 + 写前 quorum 检查（`w + r > n` 只是可能达标），或**经主**读。
- DNS、读多写少的缓存不需要线性一致，付不起延迟代价——**一致性按操作选**。
- 与**可串行化**正交：可串行化管多对象事务的等价性，线性一致管单对象的实时序；
  Spanner 的外部一致性、Calvin 的确定性定序追求两者叠加。

### 9.2 顺序保证的阶梯

| 保证 | 含义 | 代价 |
| --- | --- | --- |
| 线性一致 | 单对象 + 实时序 | 协调/延迟，主故障期间不可用 |
| 因果一致 | 有因果关系的操作全序，无因果的可分叉 | 无全局协调；需追踪因果（版本向量/HLC） |
| 最后写胜利 LWW | 按时间戳覆盖 | 丢弃并发写，静默丢数据 |

因果一致 + 单对象原子写可组合出很多场景需要的强度，且可用性更好——这是
CRDT 与本地优先应用的理论地基（第 12 章）。

### 9.3 共识：定义与不可绕过的代价

- **一致性协议**（agreement）：没有两个节点给出不同决定；**完整性**：只决定
  真正提议过的值；**有效性/终止性**：最终有决定。
- **FLP 不可能定理**（Fischer, Lynch, Paterson, JACM 1985）：纯异步、哪怕一个节点
  失效，也不存在必然终止的确定性共识。工程出路是**引入超时**（部分同步模型，
  Dwork–Lynch–Stockmeyer 1988）或**随机化**（Ben-Or 等）。
- **共识 ≠ 2PC**：2PC 在协调者崩溃时阻塞；共识算法用多数派换主继续运转。
  2PC 管的是「参与者都同意提交」，共识管的是「对唯一决定达成一致」——可以
  用共识实现容错的协调者（Gray & Lamport《Consensus on Transaction Commit》）。

### 9.4 Raft 的可读性红利

Raft（Ongaro & Ousterhout, USENIX ATC 2014）为可理解性而生，术语成为行业通用语：
Leader / Follower / Term / Log / Committed Index。教学示意（不参与构建）：

```text
选主：任期号 term 单调递增，获得多数派选票者成为 Leader
复制：Leader 按日志序追加 entry，跟随者确认到多数派即 commit
安全：投票时比较日志新旧，保证已提交的 entry 不会被未写入它的候选人覆盖
```

### 9.5 共识服务：etcd 与 ZooKeeper 的分工

- 共同点：线性一致读/写（多数派提交）、租约、CAS（compare-and-swap 式条件更新）、
  通知（watch）。
- ZooKeeper（ATC 2010）基于 Zab，贡献了「znode + ephemeral node + watcher」这套
  协调原语词汇表；Kafka 曾长期用其做元数据与控制器选举。
- etcd（核心在 `etcd-io/raft`）是 Kubernetes 的元数据基座；v3 API 提供
  `Txn`（原子 if-then-else）与 lease，作为锁与选主的底座。
- 它们都不适合当数据库：单组共识吞吐有限，适合放**少量、强一致、低频**的元数据。

### 9.6 用共识服务做锁：常见坑位

共识服务给了「小而硬」的原语，但**从原语到正确的锁**仍有几步要走：

- **锁过期与 GC 暂停**：lease 到期后持锁者可能仍在运行（第 8 章的暂停问题）。
  防御是 fencing token——etcd 的 `ModRevision`、ZooKeeper 的 `zxid/version`
  都可充当递增令牌，但**要求共享存储会检查它**，而很多下游根本不检查。
- **锁的粒度**：全局锁（吞吐瓶颈）vs 按资源加锁（需要一致的哈希/命名规则）。
- ** herd 效应**：watch 全量唤醒 → 惊群；应使用带前缀的排队式锁或 fair lock
  模式（ZooKeeper 顺序节点的经典用法）。
- 🔧 工程判断：如果业务能容忍双主的一瞬间（幂等、可对账），简单 lease 足够；
  如果不能容忍，别自己拼锁——把「需要互斥的状态」放进共识组本身
  （用 etcd `Txn` 直接条件写状态位），比「锁 + 存储检查令牌」少一层缝隙。

### 9.7 共识之外的替代物：什么时候可以不用

| 需求 | 更便宜的替代 | 为什么够 |
| --- | --- | --- |
| 服务发现/成员列表 | 带 TTL 的最终一致注册 | 过期条目自愈，短时不一致可容忍 |
| 配置分发 | 版本号 + 轮询/长轮询 | 旧配置短期存活无害 |
| 任务去重 | 数据库唯一约束 | 单库事务内可解 |
| 领导者选举 | **必须共识** | 双主不可容忍 |
| 定序/分配 ID | 单点或 epoch + 段 | 可容忍时比共识便宜得多 |

- 记住反向结论同样重要：**不要为了「分布式」三个字引入共识组**——
  共识组是一台「多数派活着的条件下永不阻塞」的强一致小机器，维护成本
  （成员变更、快照、磁盘 IO、监控）远高于它的 API 面积所暗示的复杂度。

### 9.8 成员变更与重启的真实成本

- 集群成员变更（加节点/换节点/缩容）是共识里最容易出错的部分：Raft 用
  单步变更或联合共识（joint consensus）保证变更过程中不会出现两个多数派。
- 运维红线（教学示意，不参与构建）：
  ```text
  5 节点 → 维护上限：同时只允许坏 2 个
  换节点：先加（扩到 6）→ 数据追平 → 再删（缩回 5）
  灾难恢复：强行重置成员前，先确认旧多数派真的不可能复活
  ```
- 「旧多数派复活」是数据脑裂的经典来源：备份拉起的集群带旧日志、旧
  epoch 回来继续写——fencing 与 epoch 校验必须在**所有**写路径上生效。

## 版本演进

- 1985：FLP 证明共识在纯异步下不可行——所有实用算法都是对它的回应。
- 1988：Dwork, Lynch, Stockmeyer《Consensus in the Presence of Partial Synchrony》
  证明部分同步下可行，为超时类算法正名。
- 1990：Herlihy & Wing《Linearizability: A Correctness Condition for Concurrent
  Objects》给出线性一致的形式化定义与验证工具。
- 1996：Chandra & Toueg 的不可靠故障检测器把「超时判死」理论化。
- 1998/2001：Paxos（Part-Time Parliament / Paxos Made Simple）；2007《Paxos Made
  Live》公布 Google Chubby 的工程化差距。
- 2010：ZooKeeper 论文；2012 Spanner（OSDI）用 TrueTime 给出外部一致性；
  2014 Raft（ATC 2014）与 Ongaro 的博士论文把共识变成可教学、可实现的事实标准。
- 2012：Calvin（SIGMOD 2012）展示「先定序后执行」的确定性路线。
- 第 2 版（2026）：Raft/etcd 生态与 Kubernetes 语境成为叙事主线，2PC 与共识的
  区分、成员变更（joint consensus）细节更充实。

## 近年研究与工业界开源实践（2015–2026）

- **Jepsen 系列实证**：对 etcd（v3.4 报告确认线性一致读成立，同时指出 watch 语义
  边界）、MongoDB（旧版本 causal consistency 与 "majority" 选项曾与文档不符）、
  CockroachDB（时钟前跳违反串行化的修复、以及早期「SERIALIZABLE」实为 snapshot
  语义的改名）的审计共同说明：**共识内核正确 ≠ 对外语义正确**，读路径、租约、
  时间戳都可能引入回归。
- **Anomalous Serializable 与写入偏斜**：分布式系统常以「交互检查」或
  SSI-in-distributed 形式追赶单机 SSI；社区持续讨论「应用层写偏斜容忍清单」
  是否比全量可串行化更划算（呼应第 7 章）。
- `etcd-io/etcd`（52.3k★）与 `etcd-io/raft`（1.1k★）：K8s 元数据底座 + 可复用
  Raft 库；`hashicorp/raft`（9.1k★）是另一份广泛嵌入（Consul/Nomad）的实现。
- `cockroachdb/cockroach`（32.5k★）：Multi-Raft + HLC + 串行化快照，把共识塞进
  事务层内外的代表作品。
- `apache/kafka`（33.8k★）：自 KIP-500 起用 Raft（KRaft）取代 ZooKeeper 做元数据
  管理，是「共识服务被内置化」的标志性迁移。
- `pingcap/tidb`（40.6k★）：TiKV 以 Multi-Raft 复制、PD 用内置 Raft 管理时间戳
  服务的高可用。

## 常见误区与本书需修正之处

| # | 误区 | 修正（🔧 为 2026 视角补充） |
| --- | --- | --- |
| 1 | 「有共识就有一致性，无需区分」 | 共识只是机制；对外语义（线性一致读、租约、watch）各服务差异大 |
| 2 | 「w+r>n 天然线性一致」 | 只在特定配置成立； sloppy quorum、并发读旧主都可能破坏 |
| 3 | 「2PC 和共识差不多」 | 2PC 阻塞式、无容错换主；共识可继续服务，二者解决的问题不同 |
| 4 | 「用自己的心跳+超时实现选主即可」 | 拜占庭将军的最简形态即能让自研选主产生双主；用成熟共识库 |
| 5 | 🔧 「共识内核通过 Jepsen 就万事大吉」 | Jepsen 屡次发现读路径/时钟/文档层面回归；每个版本都要重测 |
| 6 | 🔧 「ZooKeeper 已过时可以忽略」 | 大量存量系统仍在用；其协调原语词汇（znode/ephemeral/watch）仍是通用语 |
| 7 | 「共识集群越大越可靠」 | 多数派变大 → 延迟变高；3 节点容 1、5 节点容 2 是实用上限区间 |
| 8 | 「共识服务可以顺便当业务数据库」 | 元数据规模与吞吐错配；共识组塞大数据集会拖垮选举与复制 |
| 9 | 「线性一致读不要钱」 | 必须经主或 ReadIndex quorum 校验，延迟是实打实付出的；按操作选一致性 |
