# 第 2 章 数据模型与查询语言

> 原书第 2 章 *Data Models and Query Languages*。数据模型是软件最重要的抽象：
> 它决定「哪些问题好问、哪些问题难问」。本章按关系 → 文档 → 图的顺序对比三种模型，
> 并讨论声明式查询语言与 schema 的读写时序。

## 核心精讲

（以下为教学性梳理，示例 SQL/Cypher 均**教学示意，不参与构建**。）

### 2.1 三种模型的同源与分岔

- 关系模型（Codd 1970）之前，商业数据库以**层次模型**（IMS）与**网状模型**（CODASYL）
  为主：程序员手工导航指针，无连接运算。关系模型用**集合 + 谓词**替换导航，查询优化器
  决定执行路径——这是「模型即抽象」的第一课。
- **文档模型的历史回摆**：JSON 文档 ≈ 层次模型，但多了自描述与灵活 schema。选型判据：
  - 数据是**一对多树形**（简历、订单行项）→ 文档模型好：一次读取拿到全部，局部性高；
  - 数据有大量**多对多** → 关系模型好：文档模型里引用要多次查询，连接（join）支持弱；
  - 「文档 vs 关系」的真实分歧在**schema 假设**而非嵌套本身——关系库也能存 JSON，
    文档库也有引用，边界是渐变的。

### 2.2 归一化与局部性：一个例子看清取舍

```text
# 教学示意：简历数据的三种存法（不参与构建）
层次/文档式：{ 用户, [教育经历 x3], [职位 x2] }        → 一次读全，改一条经历要重写文档
关系式：     users | educations(user_id FK) | positions → 连接查询，任意维度聚合
```

- **归一化（normalization）**在文档语境下的代价：文档模型鼓励反归一化（把所属组织名
  冗余进简历文档），组织改名时要么全量更新所有文档，要么接受旧名（数据陈旧）。
  关系模型中这是 `JOIN organizations` 一次搞定的事。**反归一化的写放大 vs 连接的读放大**
  是跨模型的通用权衡。

### 2.3 schema 的读写时序

- **schema-on-write**（关系模型）：写入时强制 schema，类比编译期类型检查——写错即拒绝；
- **schema-on-read**（文档模型）：数据写入不检查，读取时才解释——类比运行时类型检查；
- 动态字段、异构行（不同时期不同结构）更适合 schema-on-read；跨应用共享数据、约束严格
  时，schema-on-read 的「灵活性」其实是把校验成本转嫁给了**所有读者**。
- 真实工程里两者常混合：核心交易表 schema-on-write，用户行为/配置类数据 schema-on-read；
  混合落地的载体正是关系库的 JSON 列（PostgreSQL JSONB、MySQL JSON）。

### 2.4 声明式查询：说 What 不说 How

```sql
-- 教学示意：声明式 vs 命令式
SELECT a.name, b.species
FROM animals AS a JOIN animals AS b ON a.parent = b.id
WHERE b.species = 'shark';   -- 只描述结果；执行顺序、索引选择交给优化器
```

- 命令式代码必须自带循环与次序，优化器无从下手；声明式语言可被系统重写为任意高效执行
  计划，也是「客户端/服务端并行化」与「向量化执行」的前提（→ 近年研究段）。
- **MapReduce 式查询**（CouchDB 视图等）是命令式与声明式之间的一档：写 map/reduce 函数
  （命令式），但调用方式与结果缓存是声明式框架管的（→ 第 10 章展开）。

### 2.5 图数据模型

- **属性图（property graph）**：顶点/边都带任意属性，边有向、可命名、顶点间允许多条边
  （如「A 资助 B」与「A 是 B 的员工」两条边并存）。
- **Cypher**（Neo4j 的查询语言，后标准化为 GQL 一脉）用 ASCII 画图：

```text
// 教学示意：Cypher 查询「在美国出生、现居欧洲的人」
(person) -[:BORN_IN]-> (:Location {name:'United States'}),
(person) -[:LIVES_IN]-> (:Location {name:'Europe'})
```

- 与关系库写递归 CTE（`WITH RECURSIVE`）相比，图查询把「沿边迭代直到满足条件」写成
  一阶形式；关系模型可以做到（固定深度循环或 CTE），但表达笨重——**差别不在能力，在
  遍历的人机工学**。
- **三元组存储 / SPARQL**：全库即「主语-谓语-宾语」集合；RDF 是其标准数据格式；SPARQL
  的查询形状与 SQL 相近但作用于图模式匹配。
- **Datalog**：`祖先(X, Y) :- 父母(X, Z), 祖先(Z, Y).` 这样的规则即递归定义的视图；
  Cascalog、Datomic 一脉的根，学术味浓但影响深远（递归查询、声明式规则引擎）。
- **图 vs 关系的选型**：关注点在「实体间的连接深度与变长路径查询」→ 图；关注点在
  「大规模集合运算与成熟工具链」→ 关系。同构数据（社交关注列表）用关系库也完全可行。

### 2.6 文档模型的局部性代价与收益

- 收益：一次 I/O 载入整文档，无需多次索引查找；更新局部把「多表事务」变「单文档原子
  替换」。
- 代价：应用若只需要文档中一个字段，也要整文档读写；大文档更新（如 100KB 文档改 10 字节）
  的写放大不可忽视；文档通常整体原子替换，跨文档事务要看引擎支持（MongoDB 4.0+ 支持多
  文档事务，但性能代价高）。

### 2.7 三种模型速查表

| 维度 | 关系模型 | 文档模型 | 图模型 |
| --- | --- | --- | --- |
| 最佳数据形状 | 表格化、多对多密集 | 一对多树形、自包含 | 变长路径、万物互联 |
| 局部性 | 行簇聚（InnoDB）或回表 | 整文档一次读 | 邻接表/索引自由遍历 |
| 连接 | 一等公民 | 弱（多次查询） | 边遍历（一等公民但方向不同） |
| schema 约束 | 写时强制 | 读时解释 | 通常松（属性自由） |
| 代表系统 | PostgreSQL、MySQL | MongoDB、Couchbase | Neo4j、Dgraph（star 未核验） |
| 典型失配场景 | 用关系库存深嵌套 JSON | 用文档库做报表聚合 | 用图库做大规模集合扫描 |

- 这张表是本章的「选型小抄」：三列都是被真实负载塑造的答案，**先看数据的形状与变更
  频率，再选模型**；反过来（先选模型再削足适履）是 NoSQL 年代最大的教训。

## 近年研究与工业界开源实践（2015–2026）

- **向量化执行与列式内存格式**：MonetDB/X100（VLDB 2005）开启的向量化思想已成 OLAP 引擎
  标配；**Apache Arrow**（`apache/arrow`，17158★，2026-09 实测）把「零拷贝列式内存 +
  跨语言」变成交换标准，向量化与进程间数据传输共用同一物理布局。🔧 本书第 1 版成文时
  Arrow 尚未出现（2016 年发布），第 2 版讨论向量化时应补此背景；嵌入式分析引擎 DuckDB
  （`duckdb/duckdb`，41712★）是「向量化 + 列存」进 OLAP 之外场景的代表。
- **湖仓格式与 schema 演化**：**Apache Iceberg**（`apache/iceberg`，9273★，2026-09 实测）、
  Delta Lake、Hudi 把 schema 演化做进表格式层（add/drop/重排/提升必填），与本章
  「schema-on-read/write」形成第三种形态：**schema-on-table-format**——写入快照校验，
  读取按快照回放任意历史 schema。仓库 `book/Apache_Iceberg活用入門/` 可对读。
- **向量数据库浪潮（2021–2026）**：pgvector（pgvector/pgvector，star 未核验）、Milvus
  （milvus-io/milvus，star 未核验）、Pinecone 等把「最近邻检索」变成一等查询能力；
  第 2 版方向性新增的 AI 负载正落于此。向量「模型」与本章的经典模型并列，是新的第三类
  「内容寻址」范式。
- **图数据库与图标准**：Neo4j（`neo4j/neo4j`，17259★，2026-09 实测）；**GQL**
  （ISO/IEC 39075:2024）成为继 SQL 之后第二个 ISO 标准数据库查询语言——第 1 版出版时
  此事未发生，值得补记；SQL:2023 标准也引入了属性图查询（SQL/PGQ），关系与图在标准层
  正式合流。
- **JSON 文档能力**：MongoDB（`mongodb/mongo`，28587★）与 PostgreSQL（`postgres/postgres`，
  22198★）的 JSONB 双雄，印证「文档与关系融合」的钟摆落点；MongoDB 5.0 起的时序集合
  （time series collections）进一步模糊「文档库只做 OLTP」的旧印象。
- **特化模型的持续增殖**：时序库（InfluxDB/TimescaleDB，star 未核验）、搜索（Elasticsearch，
  star 未核验）、宽列（Cassandra，10103★）——Stonebraker 2005「One size fits all 已死」
  的预言以「每个负载一种引擎」的方式全面兑现；代价是第 12 章（数据系统的未来）要回答
  的「怎么把它们拼回一个系统」。
- **查询语言的十年主线**：声明式全面胜利——SQL 在大数据生态（Spark SQL、Trino/Presto、
  Flink SQL）里反向收编了 NoSQL 的查询层；连图（GQL）与文档（JSON SQL 扩展）都以 SQL
  方言或姊妹标准的形式落地。本章「声明式 vs 命令式」的论证，十年后几乎不再有反例。
  🔧 第 1 版写作时 NoSQL 查询层还各自为政，这是最值得在重读时更新的时代背景。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「NoSQL = 不用建模」 | 恰恰相反：schema-on-read 把校验转嫁给读者；没有 schema 更要**纪律性建模** |
| 2 | 「文档数据库不支持多对多」 | 支持但别扭：引用需多次查询、连接支持弱；多对多密集时关系/图模型更合适 |
| 3 | 「关系模型是导航指针的低效版」 | 反了：关系模型把「怎么取数据」交给优化器，网状模型才是手工导航 |
| 4 | 「图数据库只是社交网络专用」 | 递归遍历、路径查询、变长关系是通用痛点；图模型是遍历的人机工学优化 |
| 5 | 「文档模型天然可扩展，关系模型天然不可扩展」 | 两者的可扩展性差异来自具体系统的设计选择（→ 第 5、6 章），不是模型本身属性 |
| 6 | 「反归一化是文档库的免费午餐」 | 反归一化把一致性维护成本转移到写路径；组织改名类问题不因换库而消失 |
| 7 | 「schema-on-read 就不用管 schema 了」 | 读取端终将汇聚出**事实上的 schema**；无显式 schema 只是延迟并放大了演化成本 |
| 8 | 「Cypher/SPARQL 是图数据库的私有能力」 | GQL 已 ISO 标准化、SQL/PGQ 进入 SQL 标准；图查询正在成为通用查询语言的一部分 |
| 9 | 🔧 本书第 1 版未覆盖 | **向量化与 Arrow 列式内存格式**；**GQL 标准化（ISO 2024）与 SQL/PGQ** |
| 9 | 🔧 本书第 1 版未覆盖 | **湖仓表格式（Iceberg/Delta/Hudi）的 schema 演化**：快照级 schema、读写兼容规则显式化 |
| 10 | 🔧 本书第 1 版未覆盖 | **向量数据模型与相似度查询**（第 2 版方向性新增） |
