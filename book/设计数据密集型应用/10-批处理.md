# DDIA 第 10 章 批处理

> 本章覆盖原书第三部分「衍生数据」第十章。视角切换：前九章关注在线服务的请求/响应，
> 本章关注**吞吐优先**的离线处理——Unix 管道 → MapReduce → 数据流引擎的演进史。
> 第 2 版将云对象存储上的现代批处理（Spark/Trino 类引擎、存算分离）纳入叙述。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 用 Unix 工具做批处理 | 管道串联小工具；日志文件作为通用接口 | 统一接口 + 组合 = 惊人的表达力，这是所有数据流系统的原型 |

## 核心精讲

（以下示意均为**教学示意，不参与构建**。）

### 10.1 Unix 管道：一切的原型

- 管道的三个设计红利：
  1. **统一接口**：文本行（今天演化为 JSON/Parquet 行）让任意程序可组合；
  2. **不写中间文件**：内存中流式传递，小数据集全程不出内存；
  3. **自动并行**：`sort` 内部就是外部归并排序，天然利用多核与磁盘。
- 与数据库的对照：数据库把「组合」交给 SQL 优化器，Unix 把它交给 shell。
  两条路线在分布式批处理中重新合流。
- 一个值得记住的细节：Unix 工具对**编码与格式**的假设（按行、按分隔符）
  使组合成为可能，也构成天花板——二进制与嵌套数据必须换武器。现代
  「列存 + schema registry」是同一问题在分布式尺度的重演（第 4 章编码
  与演化的知识在这里直接复用）。

### 10.2 MapReduce 的骨架

```text
教学示意（不参与构建）：
输入分片 → map(worker, 并行) → 按 key 分区/排序 → shuffle → reduce(worker) → 输出文件
容错：任务失败 → 在别的节点重跑（输入仍在新写好的文件里）→ 输出可重复生成
```

- 关键设计是**把状态放在不可变的输入文件里**，任务失败重算即可，不需要回滚——
  与在线服务「必须处理部分失效」形成鲜明对比（第 8 章的麻烦在这里被规避而非解决）。
- shuffle 是最大瓶颈：全量按 key 网络重分区 + 排序。

### 10.3 连接的三板斧

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| sort-merge join | 两输入按 join key 排序后归并 | 大表 × 大表（默认） |
| broadcast hash join | 小表广播到所有 reduce 节点建哈希表 | 小表可全内存 |
| partitioned hash join | 两表同 key 分区后各分区内哈希连接 | 数据倾斜缓解 |

- 数据倾斜（hot key）是分布式 join 的头号敌人：count-distinct 极端倾斜时
  需两阶段聚合（加盐打散再汇总）。
- 倾斜之外的第二杀手是 **OOM 式广播**：把「自以为小」的表广播出去，结果它
  有几百 GB。引擎的自动选择（Spark 的 `autoBroadcastJoinThreshold`）默认
  10MB 级别是有理由的；手工 hint 之前先 `count` + 看统计信息。
- 输出提交的原子性容易被忽略：MR/Spark 写目标表失败重跑时，若输出不幂等
  （追加而非覆盖、无分区级提交），会产生双份结果。成熟做法是写临时目录 +
  原子 rename/commit 协议，或交给表格式（Iceberg 的快照提交）管理。

### 10.4 从 MapReduce 到数据流引擎

- MR 的痛点：**每个作业把中间结果物化到 HDFS**；多步作业 = 多次全量落盘 + 作业
  调度延迟 + 手写 DAG 胶水代码。
- 演进链条（全部真实存在的系统/论文）：
  **Dryad（EuroSys 2007，微软）→ FlumeJava（PLDI 2010，Google）→ Spark（NSDI 2012）**。
  Spark 的贡献是把中间态改为**内存中的 RDD 血缘（lineage）**：失败不落盘重算，
  而是沿血缘重放窄依赖分区。
- 引擎接管了 MR 用户手写的职责：join 策略选择、分区布局、执行顺序——本质是
  「优化器回归」，与当年关系模型对网状模型的胜利同构。

### 10.5 图与迭代：Pregel

- BSP（bulk synchronous parallel）超级步模型：每轮所有顶点收消息、计算、发消息，
  直到无人再发消息。迭代算法（PageRank 类）在 MR 上每轮一个作业、全量落盘，
  Pregel 把顶点状态驻留内存、消息在超级步间流动。
- 开源对应物：Giraph（Hadoop 生态）、Spark GraphX；实践中更常用「SQL on Spark +
  轮次循环」凑合。

### 10.6 shuffle 的解剖：为什么它贵

- 一次 shuffle = **map 端分区写盘 + reduce 端拉取 + 按键排序/归并**。
  成本构成：网络全量传输一次、磁盘写读各一次、排序 O(n log n) 级别的 CPU。
- 工程杠杆：
  1. **尽早过滤/投影**（列裁剪、谓词下推）——少动数据永远是第一优化；
  2. **预分区 + 预排序**的输入（如按 join key 写出的湖表）可跳过 shuffle 阶段
     （Spark 的 bucket join、Iceberg 的分区演进都为它服务）；
  3. **广播小表**把 join 从 shuffle 降为 map 侧查找；
  4. 倾斜处理：加盐打散（两阶段聚合）、隔离热点 key 单独 join。
- 🔧 判断依据不是感觉：引擎的执行计划（Spark UI 的 shuffle read/write 量、
  Trino 的 EXPLAIN）会直接给出每步搬运的字节数——先看数字再优化。

### 10.7 容错哲学：批处理为什么「好做」

第 8 章列出的部分失效麻烦，在批处理里被**结构性规避**了：

| 在线服务 | 批处理 |
| --- | --- |
| 输入持续变化，无法重放 | 输入不可变文件，可反复读 |
| 一次请求失败必须快速反馈 | 任务失败可整块重跑 |
| 状态（会话/锁）跨请求存活 | 任务无共享状态，输出文件是唯一产物 |
| 部分失效立即影响用户 | 坏分区重算，用户只看到延迟 |

- 这解释了为什么批处理系统敢用「重算」这个暴力手段，而在线系统必须做
  WAL/共识这些精细活。反过来，**流处理就是被拉长成无界的批处理**，
  它不得不重新面对在线系统的麻烦——第 11 章的 checkpoint、exactly-once
  都是这个「回嫁妆」的过程。
- Spark 的血缘重算与 MR 的整任务重跑是同一哲学的两个精度档位：
  血缘把重算粒度从「作业」缩到「分区」。

### 10.8 SQL 的回归与「声明式下沉」

- MR 时代：执行计划由用户代码硬编码（map/reduce 怎么连是手写的）。
- Hive 把 SQL 编译成 MR 作业是转折点；Spark SQL / Presto（Trino）把优化器
  完整带回来：列裁剪、join 重排、谓词下推、CBO。
- 历史的押韵：关系模型当年在单机上击败网状模型（第 2 章），靠的正是
  「访问路径交给优化器」；分布式批处理的重演说明这不是巧合，而是
  **声明式接口在组合爆炸下的必然优势**。
- 🔧 2026 的默认写法：数据管道用 SQL/声明式框架（dbt、Spark SQL、Flink SQL）
  写逻辑，把物理执行交给引擎；手写 MR 级代码只剩极少数超特殊场景。
- **声明式下沉的边界**：优化器不是万能的——物理布局（分区/聚簇/排序）、
  文件大小与压缩格式仍需人工设计；「声明式」省的是逻辑组合，省不掉
  数据布局决策。

## 版本演进

- 1970s–80s：Unix 管道与工具哲学（Kernighan & Pike《The UNIX Programming
  Environment》是其总结）；「组合小工具解决大问题」。
- 2003/2004：GFS（SOSP 2003）与 MapReduce（OSDI 2004）把「容错的吞吐机器」产品化。
- 2006–2010：Hadoop 开源化（HDFS/MapReduce，源自 Nutch）；Hive（VLDB 2010 论文）
  把 SQL 编译为 MR 作业；Pig（SIGMOD 2008）提供数据流脚本语言。
- 2007–2012：Dryad → FlumeJava → Spark，批处理进入「引擎 + 内存中间态」时代。
- 2010：Dremel（VLDB 2010）展示列存 + 嵌套数据的交互式扫描，成为交互式
  OLAP 引擎（Presto/Trino、ClickHouse 一脉）的思想来源之一。
- 2016–2020：对象存储（S3/GCS/OSS）替代 HDFS 成为新「分布式文件系统」，
  存算分离；Trino/Spark on 对象存储 + 开放表格式（第 12 章衔接）成为默认。
- 第 2 版（2026）：批处理叙述以对象存储与现代引擎为默认背景，并给出与流处理
  （第 11 章）统一的取舍讨论。

## 近年研究与工业界开源实践（2015–2026）

- **对象存储上的批处理**：Hive Metastore → Glue/Unity Catalog 的元数据层演化；
  Iceberg/Delta/Hudi（第 12 章展开）让「表」重新成为批处理的一等公民。
- `apache/spark`（44.0k★，2026-09 实测）：事实上的批处理标准引擎；Spark Connect
  与向量化执行持续演进。
- `trinodb/trino`（13.3k★）与 `apache/druid`（14.1k★）：Dremel 思想的开源分支，
  MPP 交互式扫描的代表。
- `apache/hbase`（5.6k★）：Bigtable 思想的开源对应物，MR 时代常用的存储后端，
  如今多被湖仓替代——本身是架构变迁的活标本。
- `google/leveldb`（39.4k★）：与本章无直接关系，但 MapReduce 时代的次级索引与
  compaction 思想对理解第 3 章 LSM 基础有用。
- **与 Unix 管道的螺旋回归**：duckdb、jq、mlr 等「单机小工具」在 2020s 复兴，
  「能在一台机器上跑就别上集群」成为新的默认判断（本书第 1 版已有此提醒）。
- **引擎的工程取向**：向量化执行（按列批量算）与代码生成（把算子编译成
  机器码）是现代引擎吞吐的两把钥匙——Spark（Tungsten）、DuckDB、ClickHouse
  都在这条线上；它们解释了为什么「同一 SQL 换引擎快十倍」如此常见。

## 常见误区与本书需修正之处

| # | 误区 | 修正（🔧 为 2026 视角补充） |
| --- | --- | --- |
| 1 | 「MapReduce 已死，不用学」 | 它是所有数据流引擎的词汇表来源（shuffle/分区/血缘）；学概念不学使用 |
| 2 | 「批处理比流处理简单所以先学批」 | 批处理确实更可控，但两章应对照读：流是「没有边界的批」 |
| 3 | 「HDFS 是批处理的必要条件」 | 🔧 2026 默认是对象存储 + 开放表格式；HDFS 只是历史默认 |
| 4 | 「分布式 join 直接 join 就行」 | 数据倾斜与热点 key 是默认会发生的；先看 key 分布再定策略 |
| 5 | 「数据大了就一定需要集群」 | 🔧 duckdb/单机向量化引擎覆盖大多数企业数据集；先测量再上分布式 |
| 6 | 「中间结果落盘是浪费」 | 落盘是 MR 的容错策略而非失误；Spark 血缘重算在长流水线上也有成本 |
| 7 | 「join 两个大表平均用力」 | 倾斜 key 决定一切；先看 key 分布，热点单拎处理 |
| 8 | 「输出写完就等于成功」 | 幂等输出（覆盖写/原子重命名/带分区提交标记）才是重跑安全的前提 |
