# 第 4 章 编码与演化

> 原书第 4 章 *Encoding and Evolution*。数据格式在变，已落盘的数据不会自己变：
> 旧数据要能被新代码读（**向后兼容**），新数据要能被旧代码读（**向前兼容**）。
> 本章是 schema 演化与 RPC/消息兼容性的总纲。

## 核心精讲

（以下为教学性梳理，编码示例均**教学示意，不参与构建**。）

### 4.1 文本格式的坑

- JSON/XML/CSV 的通用问题：数字精度（JS 的 2^53 上限）、二进制串无法表示（Base64 膨胀
  33%）、CSV 的多义性（转义、分隔符、无 schema）。
- **JSON 的数字陷阱**是经典考点：大于 2^53 的整数（如 Twitter 的 tweet id）在 JavaScript
  端会静默失真——当时 Twitter 只好用字符串传 id。
- **语言内置编码**（Java `Serializable`、Python pickle、Ruby Marshal）的问题：绑定语言
  版本、安全问题（反序列化即代码执行）、性能差——跨进程边界一律禁用。

### 4.2 二进制编码的两条路线

- **带字段标签（Thrift / Protobuf）**：每个字段编号写进编码，未知编号跳过即可。
  - 兼容规则：**可加新字段（新编号）、可删字段，但绝不能复用旧编号**——改语义的编号
    复用是脏数据根源；新增字段标 `required` 要三思（会破坏旧写入端）。
  - 体积来源：字段名不进编码（进 schema），整数用变长编码（varint/zigzag），重复键值对
    消失。
- **不带字段标签（Avro）**：编码中只有字段值，顺序拼接；解释依赖**读/写两份 schema**
  对齐。
  - 落地方式：Avro 对象容器文件内嵌 writer schema；RPC 场景双方握手交换 schema；
    数据库场景用 **schema registry** 集中存版本。
  - 兼容规则在 registry 上配置：backward（新读旧）、forward（旧读新）、full 双向；
    字段改名靠**别名（aliases）**机制，类型扩大（int→long）按规则表处理。
  - Avro 的优势：紧凑、与动态语言亲和（无 codegen 也能读）、schema 本身也是数据（可演化）。

```text
# 教学示意：同一个记录的三种二进制体积对比（示意量级，非实测）
JSON（含字段名）      : ████████████████  ~100 单位
Protobuf/Thrift 压缩 : ███████           ~45 单位（字段编号 + 变长整数）
Avro（无标签）       : █████             ~30 单位（依赖外部 schema）
```

- **选型对照**：需要「字段可跳过、工具链广」→ Protobuf；需要「schema 即数据、Hadoop/
  湖仓生态原生」→ Avro；需要「零拷贝/零解码」→ FlatBuffers/Cap'n Proto/Arrow（→ 近年段）。

### 4.3 三条数据流通道

1. **通过数据库**：写 schema 旧、读代码新的时间差可达数月——「把数据重写回旧格式」几乎
   总是错的；存多份编码才是正解（→ 第 11 章 CDC 的重放思想）。档案类存储的兼容期甚至
   以十年计，这是 Avro「容器文件自带 schema」存在的理由。
2. **通过 RPC**：网络调用 ≠ 本地调用（超时、重试、部分失败、版本漂移）；gRPC 用
   Protobuf，Finagle/Thrift 一脉用 Thrift。REST 的「无 schema 自由」与 RPC 的「强契约」
   是光谱两端；**失败矩阵**是 RPC 设计的核心作业：
   ```text
   # 教学示意：一次 RPC 可能的结局（不参与构建）
   成功 | 超时（结果未知！）| 对端崩溃（结果未知）| 对端过载（退避重试 or 快速失败）
   ```
   「结果未知」意味着重试必须有幂等设计（→ 第 8、9 章）。
3. **通过消息传递**：broker 做缓冲，收发方解耦；一条消息可能被多个消费者处理（→ 第 11 章
   事件日志）；**delivery 语义**（至多一次/至少一次/恰好一次）在 broker 层面只有前两者是
   诚实的，「恰好一次」要靠端到端去重（→ 第 11 章）。
4. **Actor 框架**（Akka、Orleans、Erlang OTP）：消息与状态封装进单线程 actor，框架保证
   单 actor 内无并发——但**消息编码仍需跨版本兼容**，actor 内部无共享内存不等于没有演化
   问题。

### 4.4 兼容性规则速查表

| 变更类型 | Protobuf/Thrift | Avro |
| --- | --- | --- |
| 加新字段 | 可以（新编号；建议默认值语义） | 可以（读端用默认值；老 schema 读端需 forward 规则） |
| 删字段 | 可以（编号永不复用，可用 reserved 防复用） | 可以（读端跳过缺失字段） |
| 字段改名 | 可以（编号不变即可，名字只是文档） | 需要 aliases（读写对齐靠名字） |
| 类型扩大（int32→int64） | 有限兼容（varint 编码内可读，语义需自查） | 按类型推广规则表（int→long→float→double） |
| 复用旧编号 | **绝对禁止**（脏数据之源） | N/A（无编号，按名字对齐） |
| 单向 vs 双向 | 由使用方式决定 | registry 显式配置 backward/forward/full |

- 这张表是本章的「考前小抄」：两种路线的规则不同，但**底线相同——演化方向必须想清楚
  是「新读旧」还是「旧读新」，还是两者都要**。没想清楚的团队会在三个月后同时需要双向
  兼容，此时任何 schema 都救不了已经写入的脏数据。

### 4.5 三条通道的兼容性要求对比

| 通道 | 兼容期 | 典型灾难 | 工程对策 |
| --- | --- | --- | --- |
| 数据库 | 月～十年 | 旧格式翻新脚本破坏档案数据 | 存多版本编码；读时解释 |
| RPC | 部署窗口（分批上线） | 新旧服务版本握手失败 | 滚动发布期间双向兼容；IDL 入库做 CI 检查 |
| 消息 | 消费者升级前 | 老消费者读不懂新消息 | registry 兼容策略 + 死信队列兜底 |
| 档案/湖仓 | 十年计 | 历史重放（reprocessing）失败 | 容器文件自带 schema（Avro）/表格式快照（Iceberg） |

## 近年研究与工业界开源实践（2015–2026）

- **Protobuf 与 schema registry**：`protocolbuffers/protobuf`（72066★，2026-09 实测）是
  事实标准；Confluent Schema Registry（`confluentinc/schema-registry`，2464★，2026-09
  实测）让 Avro/Protobuf 的兼容策略成为 CI 检查项——「兼容性错误在构建期拦截」是本章
  思想工程化的最大进展。
- **gRPC 与服务契约**：`grpc/grpc`（45342★，2026-09 实测）以 Protobuf IDL + HTTP/2 把
  「跨语言强契约 RPC」变成云原生标配；OpenAPI/Swagger 是 REST 阵营对应的契约工程化。
- **零拷贝编码**：Cap'n Proto、FlatBuffers 把解码移出热路径（直接在缓冲区上访问字段），
  是「延迟敏感服务」的选项；**Apache Arrow**（17158★，2026-09 实测）把零拷贝思想推到
  数据分析生态（→ 第 2 章近年段），进程间大数据传输直接共享列式内存。
- **JSON 的工程化补丁**：JSON Schema 生态成熟；MessagePack/CBOR 一脉做「JSON 的紧凑
  版」；CBOR 在 IoT/COSE 标准体系内落地。
- **「JSON 系」二进制的定位**（教学示意对比，不参与构建）：MessagePack/CBOR 是「JSON
  的压缩重编码」——保留 JSON 数据模型的动态性，但没有 schema 就没有兼容规则；它们
  解决体积与解析速度，**不解决本章的主题（演化）**。把「用了二进制 JSON」当成「有了
  schema 管理」是最常见的自欺，两者正交。
- **湖仓 schema 演化**：Iceberg（9273★）/Delta/Hudi 把本章「前后向兼容」落到表格式层，
  兼容规则成为可配置、可校验的显式资产（仓库 `book/Apache_Iceberg活用入門/`、
  `book/Delta_Lake_Definitive_Guide/`、`book/Engineering_Lakehouses_with_Open_Table_
  Formats/` 可对读）。
- **Protobuf 的十年演进**：Protobuf「Editions」（2022 年起）把 proto2/proto3 的语法选项
  统一为可组合的 feature 体系，schema 语言本身也开始「按本书方法论演化」——兼容规则
  被显式版本化，而不是靠约定俗成。🔧 第 1 版只讲了 proto2/proto3 的字段规则。
- **多语言工程化**：Buf 一类 schema 工具链（lint/breaking check/registry，star 未核验）
  把「编号永不复用」这类纪律变成 CI 规则；gRPC 的生态让 Protobuf IDL 成为事实上的
  服务契约仓库。本章的教训十年间从「开发者自觉」变成「构建系统强制」。
- **数据格式的安全面**：反序列化漏洞（Java 序列化、pickle、不安全的 protobuf 解析路径）
  十年间多次成为重大攻击面——「不要在进程边界接受不可信编码」从性能建议升级为安全
  红线；schema 验证也属于零信任边界的一部分。🔧 第 1 版几乎没有安全视角，属必补内容。
- **演化速度的分层**（十年间形成的共识分层）：数据库内数据（年）→ 湖仓表（季度）→
  消息事件（周）→ 服务接口（天）。兼容策略应该随层选择，而不是一套规则打天下——
  接口可以 breaking review + 版本号并存，档案数据则永远只能加字段。这一分层恰好对应
  本章 4.3 三条通道的时间常数，读第 10、11 章（批/流重处理）时会再次遇到。
- **给第 2 版读者的提示**：本章的框架（格式 → 通道 → 兼容规则）在十年间没有过时，
  变化的是三个主角的座次——Protobuf 借 gRPC 登顶、Avro 退守湖仓与 Kafka 生态、Arrow
  成为新的第三极；读第 2 版时建议按这个座次表对照新版本的新增段落。

### 4.6 编码格式选型速查表

| 场景 | 首选 | 理由 |
| --- | --- | --- |
| 服务间 RPC 契约 | Protobuf（gRPC） | 工具链、生态、CI 检查成熟 |
| 数据湖/批处理文件 | Parquet（列）+ Avro（行） | 湖仓事实格式，schema 演化受表格式管理 |
| 消息系统负载 | Avro/Protobuf + registry | 消费者跨版本兼容是硬需求 |
| 前端/浏览器交换 | JSON | 无处不在的运行时支持 |
| 进程内/进程间大数据传输 | Arrow / FlatBuffers | 零拷贝，避免序列化税 |
| 配置文件 | YAML/TOML/JSON | 人类可读优先，体积不敏感 |

- 这张表同样是「默认项」而非「规定」：任何一格的前提都是负载与团队现实——但**先有
  默认再谈例外**，比每次从零争论省一个数量级的会议时间。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「JSON 人类可读，所以总是更好的选择」 | 可读性换来体积、精度与速度三重代价；服务内部契约优先二进制 schema |
| 2 | 「新增字段只要别删旧的就行」 | 需要**双向**兼容：新读端必须容忍旧数据缺字段（默认值），旧读端必须跳过新字段 |
| 3 | 「字段编号/枚举值复用一下没关系」 | 复用旧编号但改语义是最隐蔽的脏数据源；规则是「只加不改，编号永不复用」 |
| 4 | 「RPC 就是远程的函数调用」 | 超时、重试、部分失败、版本漂移使其本质是**分布式交互**；失败语义必须显式设计（→ 第 8 章） |
| 5 | 「Actor 框架内消息不用管编码」 | 跨版本 actor 之间消息仍需前后向兼容；框架只隔离内存，不隔离演化 |
| 6 | 「Avro 比 Protobuf 先进」 | 各有所长：Avro 紧凑且 schema 即数据，Protobuf 工具链与生态更广；选型看 channel（文件/RPC/消息） |
| 7 | 「数据库里的旧数据会在 schema 变更时自动翻新」 | 只在读时解释；物理旧格式可能留存数月甚至十年，「重写回旧格式」是把演化链焊死 |
| 8 | 「消息队列保证恰好一次」 | broker 层只有至多/至少一次；恰好一次要端到端幂等 + 事务（→ 第 11 章） |
| 9 | 「schema 先上线，代码后跟上就行」 | 部署顺序决定需要的兼容方向；滚动发布期间新旧版本并存，双向兼容是刚需而非加分项 |
| 10 | 🔧 本书第 1 版未覆盖 | **schema registry 的 CI 化兼容检查**、**Arrow/Cap'n Proto 零拷贝**、**湖仓表格式的 schema 演化规则** |
