# DDIA 第 7 章 事务

> 本章覆盖原书第二部分「分布式数据」第七章。事务是前两章（复制、分区）留下的补偿机制：
> 一旦数据被复制和分区，并发与部分失效就会打破简单的顺序假设，事务把这种复杂性打包成一套
> 可声明的保证。第 2 版（Kleppmann & Riccomini，O'Reilly 2026）对事务章做了重构并更新了
> 工业案例；本笔记按内容主题组织，小节措辞以正版目录为准，不逐条抄目录。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 事务的棘手概念 | ACID 四个字母的真实含义；BASE 是营销词而非保证 | A 是「可中止性」，C 是应用层不变量，只有 A、I、D 是数据库保证的 |

### 7.1 ACID 的精确化

- **原子性**：不是「并发」（那是隔离性），而是**可中止性**——事务中途出错，保证之前的写全部作废。这依赖 undo/redo 日志（单机实现见 MySQL 的 redo/undo 体系）。
- **隔离性**：并发事务互不干扰。教科书给出的最高级别是**可串行化**：并发执行的结果与某个串行顺序相同。
- **持久性**：提交后写入不丢。在分布式语境下，持久性还要问「副本落在几台机器、几个故障域」。
- **一致性（C）**：DDIA 明确指出 C 是**应用层属性**——不变量（如「借贷相等」）由应用维护，A/I/D 只是工具。把 C 当成数据库承诺是常见误读。
- **事务的棘手概念**一节还讨论了「单对象与多对象操作」的分野：没有事务时，
  多对象写可能在崩溃后留下半套状态，单对象写入也仍可能被并发读到中间值
  （非原子更新）——这是事务存在的最小理由，先于一切隔离级别。
- 🔧 补充视角：把「是否需要事务」误当成性能问题（关掉事务换吞吐）在
  微服务实践里屡见不鲜；更稳的问法是「我的不变量有哪些、由谁强制」——
  没有答案的系统不是不需要事务，而是把正确性交给了运气。

```sql
-- 教学示意：写偏斜的医院值班例子（不参与构建）
BEGIN;                                        -- T1 与 T2 并发
SELECT count(*) FROM doctors WHERE on_call    -- 两人都读到 2（快照隔离下都能过）
  WHERE shift = 'night';                      -- 各自认为"还有人在"
UPDATE doctors SET on_call = false WHERE id = <self>;  -- 写不相交的行 → 允许提交
COMMIT;                                       -- 结果：无人值班，不变量被破坏
```

### 7.2 隔离级别谱系

| 级别 | 防住的异常 | 仍存在的异常 | 典型代表 |
| --- | --- | --- | --- |
| Read Committed | 脏读、脏写 | 不可重复读、幻读、丢失更新 | PG/Oracle/InnoDB 默认 |
| Repeatable Read | + 不可重复读 | 幻读（标准定义）、写偏斜 | MySQL InnoDB RR（加 next-key lock 后更强） |
| 快照隔离（SI） | + 丢失更新（单事务多读的情形靠 first-committer-wins） | **写偏斜**、反常依赖 | PG 的 RR、Oracle、FoundationDB |
| 可串行化 | 全部 | — | 2PL（旧）、SSI（PG 9.1+）、串行执行（VoltDB） |

- 术语对照：SI 的实现要点是「快照读 + first-committer-wins 写冲突检测」——
  并发事务写了同一行时，**后提交者中止**，而不是等待或覆盖。
- 「反常依赖」（anomalous/(read-write) dependency）是 SSI 论文的词汇：事务读了
  一个值并据此行动，但它读到的是旧快照——SSI 检测的正是这种 `rw` 反依赖成环。
- 注意隔离级别是**实现可选项**而非必然：同一个「RR」标签在不同系统里语义
  相差甚远，永远以「防住了哪些异常」来沟通，而不是以级别名。

### 7.3 三条可串行化路线

1. **串行执行**：单线程顺序跑事务（H-Store/VoltDB 一脉）。前提是事务短、数据集放内存、
   吞吐靠分区并行。工程含义：跨分区事务要尽量避免，否则吞吐崩塌。
2. **两阶段封锁（2PL）**：读阻塞写、写阻塞读；配合谓词锁（或索引区间锁）才能覆盖幻读。
   缺点是死锁与并发度骤降。教科书细节见《数据库系统概念6》第 15 章。
3. **可串行化快照隔离（SSI）**：在快照隔离上加「乐观检测」——跟踪两类反依赖
   （先读到旧值后别的事务写入 `rw` 冲突），提交时检测环。核心洞察：
   **写偏斜必然形成 rw 依赖环**，检测环比预防锁便宜。

### 7.4 SSI 的三个实现要点（PostgreSQL 口径）

- 事务读写集的跟踪放在 SI 运行之上，**不额外加锁**，所以读多写少场景几乎零开销。
- 为控制误报，需要「SIREAD」影子谓词与**事务提交时间戳排序**：环上的边要区分
  「危险结构」（dangerous structure），只对可能形成环的组合中止。
- 代价是**失败后重试**：高冲突负载下重试风暴会吃掉乐观收益，这与 OCC 的老结论一致。

### 7.5 写偏斜的实际形态清单

写偏斜之所以难防，是因为它穿着「正常业务逻辑」的外衣。以下场景都是同一类
「读一批 → 各自决定 → 写不相交对象」的模式：

| 场景 | 不变量 | 被破坏的过程 |
| --- | --- | --- |
| 医生值班 | 至少一人在班 | 两人并发请假，都读到「还有别人」 |
| 会议室预订 | 同一时间段不重复 | 两个用户查空档后各自 INSERT（区间不相交但时间重叠） |
| 唯一用户名 | 用户名不重复 | 检查不存在后并发 INSERT（快照下都能过检查） |
| 双人游戏等结束 | 双方不能同时拿走 | 各自查「对方是否已拿走」 |
| 余额白名单 | 账户不许透支 | 各自读总额后扣不同账户 |

- 对策从弱到强：唯一约束/外键（数据库强制）→ `SELECT … FOR UPDATE`
  显式锁 → 物化冲突（把「区间」物化成一行再加锁）→ SSI。
- 🔧 工程默认建议：**凡是「检查-然后-写入」的代码，先问一句话——检查的谓词
  有没有被数据库强制？没有就必须升级隔离级别或显式加锁。**

### 7.6 隔离级别选择的决策树

```text
教学示意（不参与构建）：
是否存在跨对象的「读后写决定」？
├─ 无（单行更新、追加写）→ RC/SI 足够
├─ 有，且谓词可被约束表达（唯一键/外键/触发器）
│    → 用数据库约束，保持默认级别
├─ 有，且可用显式锁覆盖（行数少、入口集中）
│    → FOR UPDATE / 语义锁（状态字段）
└─ 有，且约束复杂（业务不变量、跨多行）
     → 可串行化（SSI 或串行执行），并设计好重试
```

- 重试设计三要素：**捕获特定错误码**（PG 的 `40001` serialization_failure）、
  **指数退避**、**副作用置于事务提交之后**（否则重试会重复发邮件）。
- 🔧 微服务语境补充：跨服务的不变量无法靠任何一个库的隔离级别保证——
  那是第 12 章「端到端正确性」与 Saga/补偿（见《数据库系统概念6》第 26 章）
  的领地。事务的边界画在哪个服务里，比隔离级别选什么更早决定成败。

### 7.7 与 MySQL InnoDB 的对照阅读要点

InnoDB 是「MVCC + 2PL 混合」的活教材，与本章纯 SI/SSI 叙述互补：

- 快照读（普通 `SELECT`）走 MVCC 版本链；当前读（DML、`FOR UPDATE`）走行锁，
  靠 next-key lock（记录 + 间隙）在 RR 级别消除幻读——所以 InnoDB 的 RR
  实际上强于标准定义，但**仍不防所有写偏斜**（间隙锁只在当前读生效）。
- 版本链挂在 undo log 上，purge 受最老活跃事务约束 → **长事务导致 undo 膨胀**
  是线上高发事故，等价于本章「快照太老」的警告。
- 细节推导（锁相容矩阵、wait-for 图、锁升级）不在本书范围，
  深读见《数据库系统概念6》第 15 章与 mysql 笔记。

## 版本演进

- 1983：Härder & Reuter 提出 ACID 缩写，把原子性定位为「all or nothing」。
- 1995：Berenson 等人《A Critique of ANSI SQL Isolation Levels》指出 SQL 标准隔离级别定义
  的漏洞，并首次系统命名**快照隔离**与写偏斜——本章大半概念源自该文。
- 2008：Cahill 的博士论文及 AJP 论文给出 SSI 的完整算法（serializable snapshot isolation），
  2011–2012 年由 Ports & Grittner 落地为 PostgreSQL 9.1。
- 2014 前后：Ports 等人《Highly Available Transactions》证明「无协调的隔离级别」上限，
  说明**可串行化必然需要跨节点协调**——这是第 2 版讨论分布式隔离的骨架。
- 2017：Amazon Aurora 论文（SIGMOD 2017）示范「日志即数据库」——事务持久性
  下沉到存储层，是第 2 版云原生事务叙事的技术伏笔。
- 第 2 版（2026）：云原生与托管数据库语境更新了案例（如 Aurora/Neon 类存算分离系统的
  事务语义），并把「事务到底承诺了什么」放在部分失效的视角下重述。
- 中文第二版《数据密集型应用系统设计》（中国电力出版社 2026-08）基于英文 2 版。

## 近年研究与工业界开源实践（2015–2026）

- **Jepsen 系列实证**：Jepsen 对 MongoDB（旧版本：默认 w=1 时丢失确认写）、etcd（多数
  集群下线性一致读达标，但 stale read 选项是明确弱化）、CockroachDB（早期版本曾把
  "SERIALIZABLE" 实际提供到 snapshot 语义，后改名并修正）的审计说明——**隔离级别是
  实测出来的，不是文档写出来的**。选型时应看最新的 Jepsen 报告而不只是版本号。
- **Anomalous Serializable 讨论**：社区近年常争论「应用其实不需要完整可串行化，只要堵住
  少数具体异常」。此路线的工程对应物是约束数据库（如 F1 的 Spanner 侧约束、CRDB 的
  check constraint）与显式 `SELECT … FOR UPDATE`；本书立场：能靠数据库就不靠约定。
- `postgresql/postgres`（22.2k★，2026-09 实测）：开源关系库中唯一原生 SSI，
  核心在 `src/backend/storage/lmgr/predicate.c`。
- `pingcap/tidb`（40.6k★）：Percolator 式乐观事务起步，5.0 起默认悲观事务 + 分布式
  死锁检测；隔离级别提供 SI 与 RC。
- `cockroachdb/cockroach`（32.5k★）：HLC 时间戳 + 串行化快照隔离，写意图机制。
- `apple/foundationdb`（16.7k★）：乐观并发控制（5ms read version / commit 冲突检测）
  在生产系统里的最好样本。

## 常见误区与本书需修正之处

| # | 误区 | 修正（🔧 为 2026 视角补充） |
| --- | --- | --- |
| 1 | 「ACID 的 C 是数据库保证的一致性」 | C 是应用层不变量；A/I/D 才是数据库承诺 |
| 2 | 「快照隔离 = 可串行化」 | SI 防不住写偏斜；需要 SSI 或显式锁 |
| 3 | 「REPEATABLE READ 都一样」 | 标准 RR 仍有幻读；PG 的 RR 是 SI；InnoDB RR 靠 next-key lock 更强 |
| 4 | 「事务失败重试一定安全」 | 重试前提是**副作用幂等**；带外部副作用（发邮件）的事务不能用裸重试 |
| 5 | 🔧 「隔离级别看文档就够了」 | Jepsen 多次发现文档与实测不符（MongoDB、CockroachDB 早期版本）；以实测审计为准 |
| 6 | 🔧 「单机语义可平移到分布式」 | 无跨节点协调的可串行化不存在（Highly Available Transactions 结论）；分布式可串行化必然付费 |
| 7 | 「检查过再写就安全」 | 检查与写入之间窗口正是不变量被破坏的地方；必须由约束/锁/SSI 收紧 |
| 8 | 「长事务只是慢一点」 | 长事务顶住 MVCC 版本链与锁；InnoDB undo 膨胀、PG 事务 ID 回卷都是其后果 |
| 9 | 「事务能包住外部副作用」 | 提交与副作用（邮件/HTTP）之间没有原子性；需 outbox 模式或幂等设计（第 12 章） |
