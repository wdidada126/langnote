## 核心精讲

（以下为教学性梳理，伪代码均**教学示意，不参与构建**。）

### 3.1 哈希索引：最笨也最诚实的起点

- 原型：**追加式日志文件 + 内存哈希表**（key → 文件内偏移），如 Bitcask 的做法。
  - 写：纯 append，顺序写磁盘，快；
  - 读：一次哈希查找 + 一次磁盘读；
  - 崩溃恢复：重放日志重建哈希表。
- 必须解决的两件事：
  1. **日志段压缩（compaction）**：同一 key 只保留最新值，按段合并去重；删除用墓碑标记；
  2. **部分写入的崩溃恢复**：校验和（checksum）逐条记录；append 到一半崩溃的记录要能被
     识别并丢弃（块边界 + 校验和是通行做法）。
- 天花板：键空间必须装进内存；区间查询（`WHERE key > a AND key < b`）无法高效——
  这正是 SSTable 出发的理由。**从哈希日志到 SSTable 的唯一改动是「段内按 key 排序」**，
  书中这段推导是全章最值得精读的部分。

### 3.2 SSTable 与 LSM-Tree：把「段」排好序

- **SSTable（Sorted String Table）**：每个段内 key 有序、可稀疏索引、可压缩。优势：
  合并段是**归并排序**（顺序 I/O）；区间查询快；稀疏索引省内存。
- 构造方式：写先入**内存表（memtable，常为红黑树/跳表）**，满了刷成 SSTable 文件；
  查询从新到旧查内存表与各级 SSTable；后台**合并压缩**回收空间。
- 这套结构即 **LSM-Tree（Log-Structured Merge-Tree，O'Neil et al. 1996）**；
  落地系统：LevelDB、RocksDB（Bigtable/HBase/Cassandra 的存储引擎同一血统）。
- **三种放大**（现代研究给本章补的度量语言）：
  - 写放大：同一字节被 compaction 反复重写的倍数；
  - 读放大：一次点查要查的层数/文件数（布隆过滤器可把它压回 1–2）；
  - 空间放大：同一 key 的多版本并存期（compaction 间隔越长越严重）。
- **compaction 策略家族**：leveled（分层，RocksDB/LevelDB 默认，读放大低、写放大高）、
  size-tiered（尺寸分层，Cassandra 传统策略，写放大低、空间放大高）、FIFO（时序场景）。
  策略选择就是三种放大之间的配比。
- **Bloom filter**：位数组 + k 个哈希函数，回答「肯定不存在/可能存在」；对 LSM 点查是
  生死线——没配布隆的 LSM 点查可能放大到全层扫描。误判率约 (1−e^(−kn/m))^k，n 为元素数、
  m 为位数（Bloom 1970）。

### 3.3 B-Tree：近乎四十年的正统

- 以**页（page，常 4KB，与磁盘块对齐）**为单位的磁盘寻址树；每个页引用子页，分支数即
  分支因子；二分查找在页内进行。树高 O(log 分支因子 N)，百万级键通常 3–4 层。
- 写新页前**预写日志（WAL）**保证崩溃安全；并发用**锁存器（latch）**保护树结构；页分裂
  （middle 处分裂、父页插入分隔键）是写放大与碎片的主要来源。
- 对比 LSM：B-Tree 一次写涉及 WAL + 页 + 可能的分裂（写放大存在但可控），读最多树高次
  寻址；LSM 写吞吐高、顺序 I/O 友好，但 compaction 会干扰前台延迟（**读写相互干扰**）。

| 维度 | LSM-Tree | B-Tree |
| --- | --- | --- |
| 写吞吐 | 高（顺序写 + 批量合并） | 中（WAL + 原位更新） |
| 读（点查） | 需查多层，靠布隆过滤器缓解 | 一次树高内完成 |
| 区间扫描 | 好（段内有序） | 好（叶子链） |
| 压缩比 | 好（后台重写可重编码） | 弱（碎片与空洞） |
| 前台延迟 | 受 compaction 干扰 | 更平稳 |

### 3.4 其他索引

- 二级索引：值 → 主键，本身可用 B-Tree 或 LSM 实现；**簇聚索引（clustered index）**把行
  存进索引叶子（InnoDB 主键即此），非簇聚则回表——「索引中存指针还是存数据」决定回表
  与否。
- 多列索引：连接索引（`last_name, first_name` 最左前缀）、多维索引（地理库 R-Tree 一脉，
  纬度/经度无单一排序）。
- 全文与模糊索引：倒排（term → 文档列表）+ 编辑距离（Levenshtein automaton、n-gram）；
  Lucene/Solr/Elasticsearch 是工程代表。

### 3.5 列式存储：分析型负载的答案

- OLAP 查询只碰 4–5 列中的 1–2 列，但行存必须整行读出——**列存把每列连续存放**，
  扫描 I/O 只覆盖所需列；压缩（位图编码、字典编码、游程编码）与向量化处理（一次算一列块）
  进一步把瓶颈从磁盘搬到**内存带宽**。
- 压缩与向量化相互成就：压缩后的列数据在 CPU 缓存里批量 SIMD 运算，是现代分析引擎
  （ClickHouse、DuckDB、Dremel/BigQuery）共同的设计基因。
- **物化聚合（materialized aggregates）**：数据立方体（data cube）等预计算，是空间换时间
  的保守设计；列存引擎普及后，即时聚合常已够快，物化视图退为补充。
- **星型/雪花模型**：OLAP 的事实表 + 维度表结构，是关系模型在分析场景的延续——列存引擎
  之上跑的仍是 SQL，这是本章与第 2 章（声明式查询）的呼应点。

### 3.6 事务型引擎速查：两组血统的真实样子

| 引擎 | 结构血统 | 代表用户/场景 | 一句话定位 |
| --- | --- | --- | --- |
| RocksDB | LSM（leveled） | TiKV、CockroachDB、Flink state | 嵌入式 LSM 事实标准 |
| LevelDB | LSM（Google 2011） | 教学/嵌入式原型 | RocksDB 的直系祖先 |
| Cassandra / HBase | LSM（Bigtable/Dynamo 血统） | 宽列工作负载 | 分布式 LSM 的两个分支 |
| InnoDB | B+ 树 + 堆/簇聚 | MySQL | WAL + 页式 B+ 树的单机正统 |
| PostgreSQL | 堆 + 非簇聚 B 树 | 通用 OLTP | MVCC 堆内多版本（版本清理是命门） |
| SQL Server / Oracle | B 树族 + 各自 WAL | 商业 OLTP | 本章「正统」在商业侧的延续 |

- 读这张表的正确姿势：**列「结构血统」决定性能形状（三种放大的分布），列「代表用户」
  决定你在哪里遇到它**。选型时两列都要看——很多「选型之争」其实是「把 RocksDB 的延迟
  形状套到了 InnoDB 的负载上」。

## 近年研究与工业界开源实践（2015–2026）

- **LSM vs B-Tree 的现代实证**：Luo & Carey《LSM-based Storage Techniques: A Survey》
  （VLDB Journal 2020）系统化 write/read/space 放大谱系；Sarkar、Athanassoulis 等的
  compaction 优化研究（SIGMOD 2022 前后的 LSMSuite 一系工作）把「分层自适应压缩」变成
  热点。🔧 本书第 1 版只给定性对比，现代结论是：**两者在总 I/O 量上差距比直觉小，差异
  主要在延迟方差与调优成本**。
- **工业界主流引擎的选型现实**：
  - RocksDB（`facebook/rocksdb`，32135★，2026-09 实测）：LSM 事实标准，TiKV/CockroachDB
    /Flink 的底座；ClickHouse（`ClickHouse/ClickHouse`，50077★）走 MergeTree 列存变体；
  - B-Tree/堆存储阵营：PostgreSQL（`postgres/postgres`，22198★）与 MySQL InnoDB
    （见 [../mysql/06-B树索引.md](../mysql/06-B树索引.md)）；
  - DuckDB（`duckdb/duckdb`，41712★）：向量化列存进嵌入式场景，是「列存外溢」的代表。
- **列存与湖仓**：Apache Parquet（`apache/parquet-java`，3083★，2026-09 实测）成为对象
  存储上的列存事实格式；Iceberg（9273★）在其上提供快照与 schema 管理（→ 第 2 章近年段）。
- **2025 年安全事件视角**：2025 年前后 RocksDB 及其客户端生态（如 Jedis 类 Java 客户端）
  出现过被广泛讨论的安全漏洞事件，推动存储引擎供应链审计——**具体 CVE 编号本次未核验，
  不列编号**，此处仅作为「嵌入式引擎被广泛复用 → 漏洞影响面放大」的教训记录。🔧 第 1 版
  完全没有供应链安全视角，属必补内容。
- **向量索引进入存储引擎**：HNSW/IVF 索引被主流引擎吸收（pgvector、Milvus、Elasticsearch
  的 dense vector），「索引结构」家族从 B-Tree/LSM/倒排扩到最近邻图索引——🔧 第 1 版
  「其他索引」一节值得按此扩充。
- **云盘与对象存储改写 I/O 假设**：本地 NVMe 的顺序/随机代价差（本章推导的根基）在
  网络块存储与对象存储上被重新定价——远端对象存储上的 LSM（一次 compaction = 大量
  PUT/GET）与传统本地盘的调优结论不能照搬；Aurora 类「日志即数据库」进一步把页写变成
  日志写（SIGMOD 2017，见第 6 章论文表）。🔧 第 1 版的 I/O 模型假设本地盘，第 2 版语境
  下这一假设需要明示。
- **「存储引擎即服务」的分层**：云计算把存储引擎藏进托管产品（DynamoDB、Bigtable
  托管版），用户只能通过延迟/吞吐 SLA 间接感知引擎血统——本章知识从「实现者知识」
  变成「选型者的解释框架」：看到 p99 尾部毛刺 → 先问是不是 LSM compaction；看到
  随机读放大 → 先问是不是布隆过滤器没配。
- **写入路径的十年收敛**：WAL + 内存表 + 后台合并的「追加写骨架」成为几乎所有写入
  密集系统的共同底盘（LSM、Kafka log、流状态存储、湖仓 delta 文件）——本章 3.1 节
  「最笨的哈希日志」其实是十年间最主流的设计基因，读第 10、11 章时请带着这个视角
  回看 3.1。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「LSM 写快读慢，B-Tree 反之，绝对成立」 | 是分布不是两分：LSM 区间扫描很快、B-Tree 写放大也不小；实际差异在延迟方差与调优成本 |
| 2 | 「compaction 是后台事，不影响前台」 | 大 compaction 与前台读写共享 I/O 与缓存，延迟毛刺（latency spike）是 LSM 生产事故高发点 |
| 3 | 「哈希索引、LSM、B-Tree 互斥」 | 同一库里并存很常见：InnoDB 主键 B+ 树 + change buffer；RocksDB 内部多层结构混合 |
| 4 | 「列存只对数仓有用」 | 向量数据库、时序库、湖仓格式（Parquet）全是列存血统；分析列存思想已外溢到一切只扫描负载 |
| 5 | 「布隆过滤器是 LSM 可选项」 | 在多层引擎上它是点查延迟的生死线；未配布隆的 LSM 点查可能放大到全层扫描 |
| 6 | 「簇聚索引存数据是 MySQL 的私货」 | 簇聚 vs 非簇聚是通用索引设计维度：InnoDB 主键簇聚、PostgreSQL 全部非簇聚（堆 + 索引） |
| 7 | 「WAL 只是崩溃恢复用」 | WAL 同时是复制日志（→ 第 5 章）、CDC 事件源（→ 第 11 章）与列存库的写入通道（→ Aurora 类架构） |
| 8 | 「 LSM 的 memtable 用什么数据结构无所谓」 | 跳表/红黑树/B+ 树的并发实现与内存回收直接决定写吞吐（→ 多处理器编程的跳表笔记） |
| 9 | 🔧 本书第 1 版未覆盖 | **LSM vs B-Tree 的现代实证结论**（VLDB Journal 2020 综述谱系）、自适应 compaction |
| 9 | 🔧 本书第 1 版未覆盖 | **对象存储上的表格式（Parquet/Iceberg）**；**嵌入式引擎供应链安全（2025 RocksDB/Jedis 类事件）** |
| 10 | 🔧 本书第 1 版未覆盖 | **向量索引（HNSW/IVF）进入通用存储引擎** |
