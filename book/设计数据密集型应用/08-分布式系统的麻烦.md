# DDIA 第 8 章 分布式系统的麻烦

> 本章覆盖原书第二部分第八章。它回答一个问题：为什么第 7 章的「真相来源」在多台机器上
> 不能再成立。核心是**部分失效（partial failure）**与**不确定性**：同一程序时灵时不灵，
> 故障定位无法收敛到单点。第 2 版把云环境下的失效统计与协作问题讲得更直白。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 故障与部分失效 | 单机从「全坏/全好」到分布式「一半坏一半好」；不可靠组件 | 部分失效 + 重试 = 结果不确定，这是分布式问题的根源 |
| 不可靠的网络 | 请求丢失/延迟/响应丢失无差别；超时与超时长度权衡 | 「请求发出但没回音」时无法区分丢包、对端崩溃还是网络分区 |
| 故障检测 | 心跳与租约 | 超时只能给出「可能死」的猜测，租约只是有限期的怀疑 |
| 不可靠的时钟 | 物理钟漂移、NTP、单调钟与墙上钟；时钟同步假设 | 时间戳不能当因果依据；墙上钟可能倒退 |
| 暂停与进程停顿 | GC 停顿、VM 迁移、时钟跳变让「持有租约的进程」暂时失能 | 进程不知道自己被暂停了；必须靠 fencing token 防御 |
| 知识、真相与谎言 | 节点只能基于本地观察行动 | 唯一「真相」是法定人数的观察结果，引出第 9 章 |

## 核心精讲

（以下图示与代码为**教学示意，不参与构建**。）

### 8.1 超时不是答案，只是问题换了个问法

- 网络只能传递「发出去了」，不保证「到达」、不保证「及时到达」、也不保证
  「对端处理了」。因此三种情形在客户端**无法区分**：
  1. 请求在网路上丢了；
  2. 对端活着但响应排队很久；
  3. 对端在处理请求途中崩溃。
- 若超时后**重试**，且请求非幂等（如转账），可能造成**重复副作用**——所以幂等性
  是任何重试机制的前置条件。
- 超时长 → 等待久但误判少；超时短 → 快速转移负载但可能「误杀」活节点并制造
  双主。本书建议用**测量到的响应延迟分布（如 99.9 分位）**推导超时，而不是拍脑袋。

### 8.2 时钟：两种钟，两种坑

- **墙上钟（time-of-day clock）**：受 NTP 调整，可能**跳变或倒退**；只适合给人看。
- **单调钟（monotonic clock）**：不倒退，只适合测时长；跨机器无意义。
- 即使 NTP 同步良好，也存在**毫秒级到分钟级**的偏差；闰秒等跳变让「本机时间戳
  排序」完全不可靠。
- 结论：**不能拿一个节点的物理时间戳判断跨节点的事件先后**。替代物是逻辑时钟
  （Lamport）与混合逻辑时钟 HLC（CockroachDB / YugabyteDB 采用）。
- 两类时钟的具体后果差异：墙上钟错 → 时间戳乱序、缓存 TTL 计算错误、证书
  校验异常；单调钟错（如 Cloudflare 案例中的内核补丁）→ 超时与测量失真。
  代码里要区分 API：`clock_gettime(CLOCK_REALTIME)` vs `CLOCK_MONOTONIC`，
  语言层同理（Go 的 `time.Now()` 含墙钟但 `Since` 用单调）。
- HLC 一句话原理：**物理时间做量尺、逻辑计数器破平局**——读起来像墙上钟，
  但保住了因果序，且不需要额外共识。

### 8.3 进程暂停与 fencing token

- 暂停来源：GC stop-the-world、VM 迁移/挂起、内核抢占、时钟跳变、`SIGSTOP`。
- 经典事故模型：进程 A 拿到租约后暂停；租约到期，协调者把租约给 B；A 恢复后
  **不知道自己已失效**，继续写共享存储 → 数据损坏。
- **fencing token**：协调者每次授权发一个**单调递增**的令牌；存储侧拒绝旧令牌的写。
  这要求存储本身能检测「过期令牌」——又把问题推给了有顺序保证的存储（第 9 章）。
- token 的来源要可靠：若由协调者随手生成，暂停/回滚后可能重复；正确做法是
  从共识组拿单调序号（etcd 的 revision、ZooKeeper 的 zxid，或 Spanner 式
  时间戳区间）——「防御令牌」自身也依赖第 9 章的定序能力，这是本章与
  下一章的因果接缝。

```
教学示意（不参与构建）：
A: 拿到 lease=33, 暂停 10s ……
B: lease 过期 → 拿到 lease=34 → 写入 OK
A: 恢复后带 33 写入 → 存储拒绝（34 已是最新）   ← fencing 生效的前提是存储会比对
```

### 8.4 「真相」由多数派定义

- 单个节点的观察（我活着、他死了、时间是 X）都可能错误。因此系统需要
  **quorum 多数派**来裁决（第 5 章读写仲裁的推广），以及**共识算法**来对关键决策
  达成一致（第 9 章）。
- 协作者（co-leader）问题：两个节点都自认是领导者。defusing 手段正是 fencing token
  + 共识产生的世代号。

- **不可靠的时钟**一节还引用了一个值得记住的工程格言（本书原意转述）：
  「闰秒不是一小时后再改就能解决的小事，它提醒我们墙上钟永远可能跳」。
  与之配套的设计纪律是：**任何跨机器的顺序判断，都不要写「比较两个节点的
  当前时间」这种代码**；需要排序就自己造序（单点发号、共识定序、HLC）。
- 网络分区期间的选择（拒绝服务 vs 提供可能过期的服务）没有标准答案，
  但必须是**显式决定**：写进代码与运维手册，而不是隐含在默认参数里——
  这正是 CAP/PACELC 讨论给工程实践的真正产出。

### 8.5 超时怎么定：从延迟分布推导

- 拍脑袋设超时的两种失败：设短了 → 误判活节点死亡，触发无谓的 failover 与
  双主风险；设长了 → 故障响应迟钝，请求方线程/连接被拖死。
- 本书建议的方法：持续测量请求往返时间分布，取**足够覆盖绝大多数样本的分位**
  （如 P99.9）加上余量作为超时。要点：
  1. 只看平均值没用——网络延迟是**长尾**的，尾部的方差远大于均值；
  2. GC 停顿与队列积压会让「对端活着但很慢」长期出现，超时必须容忍它；
  3. 超时是**动态预算**：负载变了分布就变了，固定值迟早失配。
- 故障检测器的理论口径（φ-accrual，Chandra & Toueg 一脉的工程化，Akka、
  Cassandra 采用）：不输出「死/活」，输出「以当前观测，对方已死的可能性」，
  让上层按业务自选阈值。

### 8.6 幂等性：不可靠网络下的第一课

- 重试的代价谱系：at-most-once（不重试，可能丢）→ at-least-once（重试，可能重）
  → exactly-once（端到端效果，代价高且范围有限，见第 11 章）。
- 幂等的实现手段（从弱到强）：
  1. 天然幂等的操作（`set k=v`、覆盖写）；
  2. **唯一请求 ID + 去重表**：把「处理过哪些请求」与业务写入放进同一事务；
  3. 条件写（CAS / 带版本号的更新）：重复请求因版本过期而失败；
  4. 业务层状态机：重复请求落在已完成状态上直接幂等返回。
- 🔧 实践口径：**分布式系统设计的第一问不是「怎么保证不重复」而是
  「重复了会怎样」**。先把副作用设计成幂等，重试机制才敢放心用。

### 8.7 故障的层级与爆炸半径

| 层级 | 例 | 典型表现 |
| --- | --- | --- |
| 进程 | 崩溃、OOM、死循环 | 单实例不可用 |
| 节点 | 宕机、内核 panic、时钟跳变 | 心跳丢失 |
| 网络 | 分区、丢包、长尾延迟 | 节点活着但「看不见」 |
| 机架/可用区 | 断电、光缆、空调 | 一组副本同时失联 |
| 控制面 | 配置中心、DNS、证书过期 | **所有**数据面节点同时失能 |

- 🔧 云时代的教训：**故障域设计要显式**——副本跨可用区只是及格线；
  真正的深坑是「共享依赖」（同一控制面、同一证书轮换、同一 NTP 源）把
  独立故障域耦合成单点。Jepsen/大厂事故复盘里反复出现「数据面冗余、
  控制面单点」的结构性错误。
- 容量冗余（N+2 而非 N+1）与**灰度隔离**（变更批次间留观察窗）是缓解
  级联失效的两个最便宜手段。
- 另一个经常被忽略的维度是**人**：变更窗口、误操作、回滚剧本缺失造成的
  故障占比不亚于技术故障。第 1 章讲的可靠性工程（混沌演练、故障注入、
  复盘文化）在本章背景下才显出必要性——演练的意义正是让「部分失效」
  在可控环境里先发生一遍。

### 8.8 Byzantine 一笔带过

- 区分**拜占庭故障**（节点说谎）与普通故障（节点崩溃但不撒谎）。数据中心内
  一般只防后者；拜占庭容错代价高，区块链语境才成为必需。本书只做概念界定。## 版本演进

- 1978：Lamport《Time, Clocks, and the Ordering of Events in a Distributed System》
  确立「用事件因果序而非物理钟」的思想——本章反物理钟论证的源头。
- 1989：Gray & Cheriton《Leases: An Efficient Fault-Tolerant Mechanism for
  Distributed File Cache Consistency》提出租约；本章指出的「租约 + 暂停」漏洞
  由后来的 fencing 实践（Chubby 论文中的 token）补全。
- 2010–2013：Jepsen 项目（Kyle Kingsbury）把「文档假设 vs 网络现实」的落差变成了
  可复现的实验报告，近年审计直接推动了多家数据库修复隔离与一致性缺陷。
- 2017-01：Cloudflare DNS 全球故障，原因链之一是 RHEL 内核为规避闰秒而加的
  钟倒退补丁（hrtimers）在特定负载下使 ` CLOCK_MONOTONIC` 出现负偏，leap smear
  假设失效——公开事后复盘可查，是「时钟不可信」的年度级案例。
- 第 2 版（2026）：云原生与托管服务的故障域叙述更新（可用区级失效、控制面
  故障、对象存储的最终一致语义变迁等），并强化了「不可靠时钟对事务与共识的影响」。

## 近年研究与工业界开源实践（2015–2026）

- **Jepsen 时钟陷阱**：审计中反复出现「依赖本机时间戳做排序」的缺陷（如某些
  Cassandra 版本读写冲突用时间戳裁决导致丢失写）。Jepsen 对 CockroachDB 的
  早期审计还发现「时钟瞬间前跳导致违反串行化」的案例，促成 CRDB 在不确定
  区间加入 wait-before-commit。结论：**时钟漂移是可串行化的隐形敌人**。
- **闰秒工程化**：闰秒 smear（Google、Amazon 在日终 24 小时内平滑加秒）成为云
  默认实践；Cloudflare 2017 事件则说明 smear 之外的内核路径仍可能炸。
  （2022 年起国际计量大会决议 2035 年前取消闰秒机制，工程界普遍欢迎。）
- `etcd-io/etcd`（52.3k★）：failover 与 lease 实现是学习「心跳 + 多数派」的
  标准素材；Jepsen 审计（v3.4 报告）确认线性一致读在多数派下成立。
- `hashicorp/raft`（9.1k★）与 `etcd-io/raft`（1.1k★）：把「不可靠网络上做出
  可靠决定」写成可读代码的两份参考实现。
- `nats-io/nats-server`（20.8k★）：轻量消息层对「最多一次/至少一次」语义的取舍
  示范——网络不可靠下没有免费语义。

## 常见误区与本书需修正之处

| # | 误区 | 修正（🔧 为 2026 视角补充） |
| --- | --- | --- |
| 1 | 「超时了节点一定死了」 | 只能得出「它没在期限内回应」；可能是慢、可能是网络分区 |
| 2 | 「NTP 同步了，时间戳就能排序事件」 | 毫秒级偏差 + 跳变即足够破坏因果判断；用逻辑钟/HLC |
| 3 | 「拿到租约就有权操作直到到期」 | 进程可能被暂停而不自知；必须有 fencing token 且存储会检查 |
| 4 | 「重试是免费的」 | 非幂等操作 + 重试 = 重复副作用；先设计幂等键 |
| 5 | 🔧 「云上网络是可靠的」 | 可用区级网络故障、控制面抖动都是常态故障模型；SLA 百分位要看 P99.9 |
| 6 | 🔧 「闰秒已经处理好了」 | smear 只覆盖部分路径；Cloudflare 2017 案例说明内核时钟源仍是隐患 |
| 7 | 「冗余副本越多越可靠」 | 共享依赖（控制面/DNS/证书/NTP）会耦合故障域；冗余要按故障域而非副本数设计 |
| 8 | 「心跳正常 = 节点健康」 | 心跳只证明进程能定时醒来；GC 长停顿、磁盘写满都可能心跳正常但业务不可用 |
