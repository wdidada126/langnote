# 第 1 章 可靠、可扩展与可维护的系统

> 原书 *Designing Data-Intensive Applications*（O'Reilly，第 2 版 2026）第 1 章
> *Reliable, Scalable, and Maintainable Systems*。全书的「需求章」：先定义三个形容词，
> 后面十一章都在回答怎么实现它们。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Thinking About Data Systems | 数据库/队列/缓存/索引等工具的组合；数据密集 ≠ 计算密集，瓶颈在数据量与复杂度 | 单一工具装不下需求时，问题变成「如何组合工具」 |
| Reliability | 硬件故障、软件错误、人为失误三类故障；fault / failure / 容错 | 系统应在**部分组件出错**时仍持续正确工作；容错是对特定故障类别而言 |
| Scalability | 如何描述负载（推特时间线案例）、性能（吞吐/延迟/百分位）、弹性扩展 | 先用参数描述负载，再回答「负载增长 ×10 时怎么办」；扩容无银弹 |
| Maintainability | 可运维性、简单性（管理本质复杂度）、可演化性 | 软件成本大头在维护期；三大设计目标分别针对运维、复杂度、变更 |

## 核心精讲

（以下为教学性梳理，代码与数值均为**教学示意，不参与构建**。）

### 1.1 可靠性：三类故障

- **故障（fault）≠ 失效（failure）**：fault 是组件偏离规约，failure 是整个系统停止提供服务。
  容错（fault-tolerance）指「预见 fault 并应对」，通常定义为对**某一类** fault 容错；
  「系统要能容忍 x 台机器同时挂」就是容错边界声明。
- **硬件故障（hardware faults）**：磁盘、内存、电网、网卡。单机假设下平均无故障时间（MTBF）
  是统计量；经典对策是冗余——磁盘 RAID、双电源、热备。云时代冗余单位从磁盘变成整台机器，
  虚拟机「随时可被宿主回收重启」是新的硬件故障常态。
- **软件错误（software errors）**：系统性 bug（闰秒、失控的资源消费者、依赖服务连锁故障）。
  特点是无随机性、错误关联传播，硬件冗余无效。对策：进程隔离、监控、自我检查、灰度发布、
  版本回滚。
- **人为失误（human errors）**：运维是最主要的故障来源（经典研究里 10–25% 的宕机由配置
  错误引起，具体数字随年代浮动，未核实原文精确值）。对策：
  1. 最小化犯错机会的 API（生产环境只留受控入口，其余走沙箱）；
  2. 沙箱环境试错 + 快速恢复（回滚、双写、快照）；
  3. 全方位遥测（错误率、延迟、流量、饱和度）；
  4. 流程演练：故障注入、值班复盘（Netflix 混沌工程的前身思想）。
- **不可靠性与期望的关系**：本书反复强调「可靠性是相对**期望**而言」——对营销系统，
  99.9% 足够；对支付系统，丢一笔都是事故。**先定义「正确」，才谈「容错」**。

### 1.2 可扩展性：先描述负载，再谈扩容

- 可扩展性不是形容词，是问句：「如果负载增长 N 倍，系统还能维持性能吗？」
  N 倍不是均匀放大：读多写少 → 加副本；写入洪峰 → 分区；复杂连接 → 预计算。
- **负载描述参数**：QPS、读写比、缓存命中率、同时在线用户数、单请求的扇出数。书中推特
  时间线案例：
  - 「拉模式」：读时聚合关注者的推文——读放大，热点用户的粉丝越多读越贵；
  - 「推模式」：发推时写入粉丝时间线缓存——写放大，粉丝 3000 万的大 V 单条推文写 3000 万次；
  - 现实是混合：普通用户推模式，大 V 拉模式兜底。**没有全局最优，只有负载形状决定的设计**。
- **性能度量**：吞吐（throughput）适合批处理；响应时间（response time）适合在线服务。
- **延迟百分位**：响应时间是分布不是数字。p50/p95/p99/p999；**尾部延迟（tail latency）**
  才影响慢的那个用户：
  - p50（中位数）≠「平均数」——平均数会被少数慢请求拉偏，与「用户实际体验的中等水准」
    相去甚远；
  - 报告百分位时请按**窗口聚合**（如每分钟），并区分客户端/服务端测量——服务端 p99 不含
    网络与排队，客户端 p99 才是用户视角；
  - 尾部放大（tail latency amplification）：一个页面请求扇出到多个后端，只要**一个**后端
    落在 p100 之外，整页变慢。100 次后端调用全快的概率随调用数指数下降。

  ```text
  # 教学示意：扇出后的尾部放大（不参与构建）
  单次调用 p99 慢的概率 = 1%
  一次页面 = 100 次后端调用
  P(至少一次慢) = 1 - 0.99^100 ≈ 63%   # 并行调用可压缩等待时间，但无法消除
  ```
- **扩展方法**：垂直（更强的机器）vs 水平（更多机器）。弹性（elastic）= 自动加节点分流；
  跨机分摊无状态服务容易，**有状态系统才是一切麻烦的来源**——这是第 5、6 章的引子。
- **架构与规模的匹配**：初创期用单体（买更强的机器更便宜），到了性能/组织瓶颈再拆——
  「为了百万用户提前设计微服务」与「撑到一亿用户还是单体」都是真实失败模式，可扩展性
  设计要跟着**当下负载形状**走，并保留演化空间。
- **描述负载的参数清单**（工程速查）：

| 参数 | 例子 | 为什么是它 |
| --- | --- | --- |
| QPS / 读写比 | 读 10k QPS，写 500 QPS | 决定读副本 vs 写分区 |
| 单请求扇出数 | 一次页面 20 个后端调用 | 决定尾部放大 |
| 数据增速 | 每天新增 50GB | 决定何时必须分区（→ 第 6 章） |
| 缓存命中率 | 95% | 决定真实后端负载 |
| 会话时长 / 连接数 | 百万长连接 | 决定网关与内存模型 |

- 填这张表的过程就是「可扩展性设计」的第一步：**负载参数变了，最优架构就变了**；
  同一套代码在两个负载形状下可能需要相反的设计。

### 1.3 可维护性：三种人、三个目标

- 软件生命周期成本大头在维护（修 bug、适配新平台、还技术债）。三个设计目标：
  1. **可运维性（operability）**：让运维团队轻松——监控、自动化、文档、避免绑定单一厂商；
  2. **简单性（simplicity）**：管理**本质复杂度**（essential complexity）与**偶然复杂度**
     （accidental complexity）；消除偶然复杂度的工具是**抽象**（好抽象藏起实现细节而不
     泄漏）；
  3. **可演化性（evolvability）**：需求会变；可演化性与数据模型、schema 的灵活性直接相关
     （→ 第 2、4 章），也与组织的敏捷/重构能力相关。
- **可维护性的现代度量尝试**：SLO 达成率、变更失败率、平均恢复时间（MTTR）、技术债
  清偿速度——这些都不是书里的原文，而是本书出版十年间工程界给「可维护性」找的抓手
  （→ 近年研究段）。

### 1.4 把三个目标变成可校验的合同

- 可靠性 → **SLO 合同**：对外承诺用 SLO 写下来，内部用错误预算管理兑现。
- 可扩展性 → **容量模型**：负载参数（QPS/读写比/数据增速）× 单位成本 → 扩容触发线。
- 可维护性 → **运维契约**：监控指标、runbook、回滚时限、变更窗口。

```text
# 教学示意：一个 SLO 的写法（不参与构建）
目标：读 API 的 p99 延迟 < 200ms，99.9% 的请求成功
窗口：滚动 30 天
预算：30 天窗口内允许 43.2 分钟的预算消耗（0.1% × 30 天）
动作：预算剩余 < 25% 时冻结非紧急发布
```

| 目标 | 量化载体 | 谁负责 | 失守时的动作 |
| --- | --- | --- | --- |
| 可靠性 | SLO / 错误预算 | SRE + 业务方 | 冻结发布、降级预案 |
| 可扩展性 | 容量模型 / 压测基线 | 平台团队 | 扩容、分区、降级写入 |
| 可维护性 | DORA 指标 / 技术债台账 | 全团队 | 专项重构窗口 |

- 这张表是本笔记对第 1 章的现代注脚：书里三个「形容词」，十年后都变成了可签收的
  「合同」——这也是读第 2 版时该带上的视角。

## 近年研究与工业界开源实践（2015–2026）

- **SRE 与错误预算**：Google《Site Reliability Engineering》（O'Reilly 2016，官网免费）把
  第 1 章的「可靠性」工程化——SLO/SLI/错误预算：预算耗尽就冻结发布，可靠性从「越多越好」
  变成「恰好达标即可」的显式权衡。这与本书「可靠性是相对期望而言」一脉相承：期望越高，
  预算越薄。🔧 第 1 版只有 SLO/SLA 的定义级讨论，错误预算机制是十年间最重要的补丁。
- **可维护性的度量尝试**：业界逐渐用 DORA 四指标（部署频率、变更前置时间、变更失败率、
  服务恢复时间）间接度量「可演化性」与「可运维性」；学术界则有 Moseley & Marks 之后对
  偶然复杂度的持续讨论（状态机抽象、声明式系统的倡导）。🔧 属第 1 版未覆盖的度量视角。
- **混沌工程自动化**：Netflix Chaos Monkey → Gremlin/Chaos Toolkit 一脉，把「人为失误与
  软件错误」的对策从流程演练升级为自动化实验；开源实现如 `chaos-mesh/chaos-mesh`
  （star 未核验）、Alibaba ChaosBlade（star 未核验）。故障注入平台让 1.1 节的对策第 4 条
  从「人工演练」变成 CI 里的一步。
- **尾部延迟工程化**：hedged request / request shrink-wrapping 进入主流 RPC 框架
  （gRPC，`grpc/grpc`，45342★，2026-09 实测，含 hedging 策略）；The Tail at Scale 的
  思想成为微服务扇出架构必修课。
- **云弹性**：Kubernetes（kubernetes/kubernetes，star 未核验）成为水平扩容事实标准；
  「无状态易扩、有状态难扩」依然是第 1 章论断，第 5–9 章即为有状态问题的展开；
  Serverless/FaaS 把「扩容」进一步推给平台，代价是冷启动与状态外置（→ 第 10、11 章）。
- **对象存储与托管服务**：十年间默认底座从「自管虚机 + 自建磁盘 RAID」变为「对象存储 +
  托管数据库 + 托管消息」，1.1 节的硬件故障一节在云语境下被重写为「可用区故障与配额
  限制」——第 2 版方向性修订正落于此。
- **可观测性标准化**：OpenTelemetry（star 未核验）把指标/日志/追踪的采集标准化，
  「全方位遥测」从各厂商私有方案变成开放协议；SLO 的计算与告警也随之工具化
  （SLO 生成器类项目，star 未核验）。没有遥测就没有 SLO，也没有第 1 章的一切对策。
- **AI 负载的容量观**：GPU 推理集群的「负载参数」新增了 token 吞吐、批量大小、KV 缓存
  占用——第 2 版方向性新增的 AI 负载，本质是把本章「先描述负载」的方法论用到新硬件上。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「可靠 = 数据有备份」 | 备份只覆盖硬件故障；软件错误与人为失误需要隔离、灰度、可回滚等设计 |
| 2 | 「看平均响应时间就够了」 | 响应时间是分布；p95/p99 之后的用户才是真实体验，扇出场景尾部还会放大 |
| 3 | 「可扩展性 = 加机器」 | 先用参数刻画负载；无状态层的水平扩展容易，有状态层是难点（→ 第 5、6 章） |
| 4 | 「SLA 越高越好」 | 可靠性有成本，现代实践用 SLO + 错误预算把「可靠性 vs 迭代速度」变成显式权衡 |
| 5 | 「容错 = 不会出错」 | 容错总是「对某类 fault 容错」；系统设计先声明容错的对象与边界 |
| 6 | 「服务端 p99 达标 = 用户体验达标」 | 服务端测量不含网络/重试/排队；体验指标要在客户端或入口层测 |
| 7 | 「提前按大厂架构设计就能省以后的迁移」 | 架构要匹配当下负载形状；过早拆分的偶然复杂度本身就是故障源 |
| 8 | 🔧 本书第 1 版未覆盖 | **错误预算作为可维护性/可靠性度量**、混沌工程自动化、DORA 类度量 |
| 9 | 🔧 本书第 1 版未覆盖 | **云托管服务对可运维性的重构**；**AI/向量负载的容量与弹性**（第 2 版方向性新增） |
