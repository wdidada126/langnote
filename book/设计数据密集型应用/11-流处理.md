# DDIA 第 11 章 流处理

> 本章覆盖原书第三部分第十一章。批处理（第 10 章）假设输入有界且早已存在；流处理
> 处理**无界、按到达顺序**的数据。本章是第 2 版改动较大的章节之一：CDC 主流化、
> 流批一体的现实进展与新的事件语义讨论都被纳入。

## 核心精讲

（以下代码为**教学示意，不参与构建**。）

### 11.1 消息系统与日志的分歧

- 传统消息代理（AMQP 风格）：确认即删除，消息的消费顺序与重放语义复杂。
- **日志型系统（Kafka，NetDB 2011 论文提出）**：分区内的追加日志 + 消费者 offset。
  - 重放：移动 offset 重新消费——这让「修 bug 后重跑管道」成为可能；
  - 分区 = 并行单元；**分区内有序**是唯一承诺；
  - 保留策略独立于消费，日志是**历史档案**而不仅是传输管道。
- 分区数是 Kafka 最难更改的配置之一（同一 key 的映射会变），规划时按
  目标吞吐 × 余量来定，而不是按当前流量。
- 消费组（consumer group）承担了「弹性」与「故障转移」：成员变化触发
  rebalance，分区重新分配；rebalance 期间消费暂停，频繁 rebalance 本身
  就是事故信号（消费者太慢被踢出 → 更慢 → 连环踢出）。

### 11.2 CDC：变更数据捕获

```text
教学示意（不参与构建）：
[OLTP 库] --binlog/WAL--> [Debezium 连接器] --> [Kafka topic per table]
                                                     |
                                          +----------+-----------+
                                          v                      v
                                    [物化视图/缓存]         [搜索索引/湖仓]
```

- CDC 的本质：把**主库的日志**当成事实源，衍生存储（索引、缓存、物化视图、
  湖仓表）全部成为日志的**消费者**——这正是第 12 章「分拆数据库」的机制基础。
- 落库回写纪律：CDC 消费者绝不应写回源库（除非带明确的数据流向标注），
  否则环形依赖会让「事实源」失去唯一性——派生写回事实层是 unbundled
  架构里最常见的自毁操作。
- 两种抽取位：**日志拉取（binlog/WAL）**优于**查询轮询（updated_at 扫表）**——
  前者不丢、有序、低侵入；后者有轮询间隙、需要时区与时钟纪律（第 8 章伏笔）。
- schema 演化是 CDC 的真正难点：上游 DDL 之后下游必须能解析新旧并存的事件
  （Avro + schema registry 的兼容性规则）。

### 11.3 时间与窗口

| 概念 | 含义 | 陷阱 |
| --- | --- | --- |
| 事件时间 | 事件发生时刻（数据自带时间戳） | 客户端时钟不可信（第 8 章） |
| 处理时间 | 算子看到事件的时刻 | 受背压/重启影响，不可作业务依据 |
| watermark | 「早于此的事件应已到齐」的进度线 | 定小了丢迟到数据，定大了延迟高 |

- 迟到事件策略：侧输出（dead letter）单独处理，或允许窗口更新并发出修正结果。
- 「The Dataflow Model」（VLDB 2015）把这些组合成统一框架：**what（结果）/ where
  （窗口）/ when（触发）/ how（修正累积）** 四个正交维度。
- 窗口种类速查：滚动（tumbling，固定切）、滑动（sliding，重叠）、会话
  （session，按活动间隙动态合并）。会话窗口的 merge 语义要求状态后端支持
  合并（Flink 的 keyed state merge），选型时注意。
- watermark 的工程口径：它是一个**承诺**（「承诺不会再收到早于此的数据」）
  而非事实——承诺错了就有丢数据的口子。理想来源是能给出单调、可控时间戳
  的上游（服务端打点、队列摄取时间），而不是客户端设备时钟。

### 11.4 交付语义的准确理解

- **at-most-once**：直接发，丢了不补——适合指标。
- **at-least-once**：确认 + 重试——必须配合**幂等消费**。
- **exactly-once**：Kafka 事务（producer transactional.id + coordinator）与 Flink
  的两阶段提交 sink（checkpoint barrier 对齐 + pre-commit/commit）是两条主流路径；
  二者都只保证「**从源到特定 sink 的端到端效果恰好一次**」，跳出了这个闭环
  （写到数据库、发 HTTP）就退回幂等 + 去重键。
- Flink 实现要点：checkpoint 用 Chandy-Lamport 异步快照思想（barrier 随流传播），
  状态恢复到一致切点；两阶段提交把「对下游可见」推迟到 checkpoint 完成之后。

### 11.5 日志与表：一枚硬币的两面

- 表是**某一时刻的快照**，日志是**变化的全程记录**；两者可互相导出：
  - 日志 → 表：从头重放所有变更（reducer 的 fold）；
  - 表 → 日志：CDC 把每次变更变成事件。
- 这就是「事件溯源」与「物化视图」的统一表述：**真相放日志，视图可重建**。
- 实践推论：
  1. 派生视图坏了 → 重放日志重建，不必担心「缓存不一致补丁越打越多」；
  2. 日志保留策略决定重建能力：`compact`（每 key 保留最新）适合表语义，
     时间保留适合事件史；
  3. schema 是日志的约束：兼容性规则（Avro registry 的 backward/forward）
     必须在上线流程里强制，否则重放历史会炸。

### 11.6 背压与限流：流的「拥塞控制」

- 消费速度 < 生产速度时，系统必须表态：
  1. **背压**（反压传播到源头减速，Flink 网络栈内建）；
  2. **缓冲堆积**（Kafka 天然把背压变成磁盘堆积，消费组延迟追赶）；
  3. **丢弃**（指标类流可接受）；
  4. **熔断/限流**（保护下游数据库类 sink）。
- Kafka 的设计选择值得咀嚼：它把「消费落后」合法化为 consumer lag（一个
  可观测、可告警的正常指标），而不是异常——这与消息队列「堆积即事故」的
  心智模型完全不同。
- 🔧 常见事故形态：流作业 join 大状态（流-表 join 的表无限增长）→ 状态
  后端撑爆 → checkpoint 超时 → 无限重启。**状态 TTL 与窗口清理策略**是
  流作业的必修配置，不是可选项。

### 11.7 状态管理与 checkpoint 的运维面

- 状态后端三选一：内存（快、易丢）、嵌入式 RocksDB（大状态标配，读写走
  序列化）、远端状态存储（弹性但延迟高）。
- checkpoint 间隔的权衡：间隔短 → 恢复快但持续开销大；间隔长 → 反之。
  两阶段提交 sink 下，**数据可见延迟 ≥ checkpoint 间隔**——这是吞吐换
  可见性，别用「exactly-once」去承诺实时性。
- 恢复实践：savepoint（手工快照）用于升级/迁移；**状态 schema 兼容性**
  是升级作业的最大风险点，与事件 schema 同等重要。
- 监控四件套（教学示意，不参与构建）：
  ```text
  consumer lag      —— 消费是否跟得上
  checkpoint 时长/成功率 —— 恢复能力是否在退化
  watermark 延迟    —— 业务可见性的真实口径
  状态大小          —— 有无 key 无限增长
  ```
  这四项分别对应本章的四个故障面：背压、容错、时间、状态——排障时
  按这个顺序看，多数流作业问题能在十分钟内定位到面。

## 版本演进

- 1985：Chandy & Lamport《Distributed Snapshots: Determining Global States of
  Distributed Systems》——所有流式容错的算法源头。
- 2011：Kafka 论文（NetDB'11 workshop）确立日志模型；2013 年 Jay Kreps 的
  《The Log: What every software engineer should know about…》（LinkedIn 工程
  博客长文）成为日志哲学的通行文本。
- 2013：MillWheel（Google，VLDB 2013）带来 watermark 与「exactly-once 状态计算」。
- 2014：Storm@Twitter（SIGMOD 2014）；2015：The Dataflow Model（VLDB 2015），
  Google Cloud Dataflow 的理论化。
- 2016–2020：Kafka Streams、Flink 成熟；Flink 1.4 引入两阶段提交 sink。
- 2020–2026：**CDC 主流化**——Debezium 生态、Flink CDC 把「连接器即 SQL 源表」；
  Kafka KRaft 去除 ZooKeeper；流批一体在 Flink/Paimon、Spark + Delta 上逐步落地
  但仍未消灭批处理；表格式（Iceberg 等）成为流写批读的交汇点。
- 第 2 版（2026）：新增「流处理是否值得」的权衡讨论与更多事件语义内容。

## 近年研究与工业界开源实践（2015–2026）

- **CDC 工具生态**：`debezium/debezium`（13.2k★）成为 Kafka 生态 CDC 事实标准；
  `apache/flink-cdc`（6.5k★）把整库同步做成 Flink 作业的声明式 YAML/SQL；
  各云厂商托管 CDC（DTS/Datastream 类）普遍基于日志位。
- **流批一体的现实进展**：`apache/flink`（26.4k★）提供统一 API，但社区实际形态
  更多是「Flink 写湖（Paimon/Iceberg）+ Spark/Trino 批读」的两段式；
  `apache/paimon`、`apache/fluss` 等新项目围绕「流的表化」仍在演进。
- `apache/kafka`（33.8k★）：KRaft 元数据自治（KIP-500 落地）、Kafka Streams 的
  exactly-once v2；`nats-io/nats-server`（20.8k★）与 `apache/pulsar`（15.3k★）
  提供不同取舍的日志/队列混合形态；`rabbitmq/rabbitmq-server`（13.9k★）代表
  传统代理路线仍在大量存量使用。
- `apache/beam`（8.7k★）：Dataflow 模型的可移植编程层，批流共用一套管道代码。
- **engine 层注意**：Jepsen 曾审计 Kafka Streams 与 Flink 的恢复语义，指出
  「exactly-once」宣传与某些外部 sink 组合下的实际效果存在差距——
  语义声明永远要与你的具体 sink 组合一起评估。

## 常见误区与本书需修正之处

| # | 误区 | 修正（🔧 为 2026 视角补充） |
| --- | --- | --- |
| 1 | 「Kafka 是数据库，可以当存储用」 | 它是可重放日志；无二级索引/事务查询，角色是管道与缓冲 |
| 2 | 「exactly-once 是消息层面的保证」 | 是端到端效果，依赖源 offset + 状态快照 + 事务 sink 的闭环 |
| 3 | 「watermark 定长即可」 | 应按观测到的事件时间延迟分布动态推导；静态超时最易出错 |
| 4 | 「CDC 用轮询实现就够了」 | 轮询有间隙与时钟依赖；日志位抽取才是第一选择 |
| 5 | 🔧 「上了流处理就要消灭批处理」 | 2026 的主流是流批共存：流供低延迟视图，湖仓批做重算与回填 |
| 6 | 🔧 「事件时间戳可以信任」 | 客户端时钟漂移/跳变（第 8 章）会污染窗口；服务端打点是更稳的默认 |
| 7 | 「消费落后是故障」 | Kafka 心智下 lag 是可观测的正常状态；要盯的是 lag 趋势与业务可见延迟 |
| 8 | 「状态不用管 TTL」 | 无界 key 空间的状态会无限增长；TTL/窗口清理是必配项 |
| 9 | 「exactly-once 等于零丢失零重复」 | 只在源-sink 闭环内成立；外部副作用仍需幂等键与对账 |
