# 第 5 章　去中心化的分布式数据库架构

> 原书第 5 章是架构篇的开篇，题目即「**去中心化**」：以分布式事务处理技术为主线，
> 从数据库架构角度拆出七个面——存储（5.1）、查询优化与并行执行（5.2）、高可用（5.3）、
> 事务（5.4）、可扩展（5.5）、强一致（5.6）、**解耦（5.7，即存算分离）**。
> 这一章把前四章的「原理」翻译成「架构该长什么样」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 分布式存储架构 | 数据分布（分片/副本）、存储引擎选择 | 分片决定扩展性，副本决定可用性，二者靠共识保持一致 |
| 5.2 分布式查询优化与并行执行架构 | 查询下推、并行算子、MPP | 分布式下「把计算挪到数据旁」比「拉数据」关键 |
| 5.3 高可用性架构 | 多副本、故障切换、quorum | 可用性来自冗余 + 自动选主（Raft/Paxos，见第 3 章） |
| 5.4 分布式事务架构 | 2PC/Percolator/Spanner 式事务的架构位置 | 事务跨分片，需全局协调（见第 4、7–9 章） |
| 5.5 可扩展性架构 | 弹性扩缩、再均衡 | 加节点要能「无停机」重分布数据 |
| 5.6 强一致性架构 | 共识 + 同步策略保证强一致 | 强一致 = 副本用共识保序 + 读写策略配合 |
| 5.7 解耦 | 计算与存储分离（存算分离） | 计算层与存储层独立扩缩，是云原生 DB 的底座 |

## 核心精讲

（以下为教学性梳理，伪代码/示意均**教学示意，不参与构建**。）

### 5.1–5.3 存储 / 查询 / 高可用

- **分布式存储（5.1）**：把数据按分片键（hash/range）切到多节点，每分片配多副本；副本一致性由第 3 章共识保证。
- **查询优化与并行执行（5.2）**：分布式 SQL 要「分片裁剪 + 下推 + 并行聚合」。MPP（大规模并行处理）让各节点本地算、再汇总共享结果。

```text
# 教学示意，不参与构建：分布式查询下推
SELECT sum(amount) FROM orders WHERE region='cn'
-> 各分片本地: SELECT sum(amount) ... WHERE region='cn'   (下推到数据旁)
-> 协调节点: 把各分片的部分和再 sum
# 比 "把全表拉到协调节点再算" 省几个数量级网络
```

- **高可用（5.3）**：N 副本中允许少数故障；选主（Leader election）由 Raft/Paxos 做，故障自动切。

### 5.4–5.6 事务 / 可扩展 / 强一致

- **分布式事务架构（5.4）**：事务协调者跨分片跑 2PC（或 Percolator/Spanner 模型）；架构上要把「协调」与「数据」解耦以免瓶颈。
- **可扩展（5.5）**：扩容 = 加节点 + 再均衡（rebalance）数据；关键是「再分片不中断服务」。
- **强一致（5.6）**：写需被多数派确认（quorum），读需读最新已提交版本——是第 2 章次序一致性在架构上的落地。

### 5.7 解耦（存算分离）

- **核心思想**：把「无状态的计算层」与「有状态的存储层」分开；存储层用对象存储/分布式存储持久化，计算层可弹性扩缩、按需启停。
- **收益**：计算扩缩不影响数据；存储层专注复制与持久；成本更优。是 Aurora、PolarDB、Snowflake 一脉的主流。

```text
# 教学示意，不参与构建：存算分离
计算节点(无状态, 可水平扩) --网络--> 共享存储/对象存储(多副本, 持久)
写: 计算节点写日志 -> 存储层落盘并多副本
读: 计算节点直接读存储层 (本地缓存加速)
```

## 版本演进

- **本书无第二版**；本节写 2021 年口径 → 2026 年视角的变化。
- **存算分离从「前沿」变「主流」（本书 5.7 已点出）**：2026 年 Aurora/PolarDB/Snowflake/Redshift 乃至 OceanBase 4.x 都走向存算分离/单机分布式一体化。本书判断前瞻。
- **Multi-Raft 成为可扩展 + 强一致的统一底盘**：每分片一 Raft 组，天然兼顾 5.5 与 5.6。🔧 本书 2021 对 Multi-Raft 着墨有限（见 [03-一致性问题的解法.md](03-一致性问题的解法.md)）。
- **云原生多活**：跨地域多活（active-active）取代「一地主、异地备」，是 5.3/5.6 在 2026 年的工程形态。🔧 本书未专述多活。
- **HTAP 在架构层的体现**：行列双存 + 资源组隔离，属 5.1/5.2 的扩展，详见 [06-新技术与分布式数据库架构.md](06-新技术与分布式数据库架构.md) 6.4。🔧

## 近年研究与工业界开源实践（2015–2026）

- **star 数（2026-09，`gh api` 实测）**：这些系统是「去中心化分布式架构」的落地：

| 项目 | 定位 | star |
| --- | --- | --- |
| `cockroachdb/cockroach` | 去中心化、Raft+HLC、存算一体（自管存储） | 32509 |
| `pingcap/tidb` | 计算(TiDB)-存储(TiKV) 分离架构，Multi-Raft | 40591 |
| `tikv/tikv` | 存算分离中的「存储层」(Multi-Raft KV) | 16878 |

| `apache/hbase` | 基于 HDFS 的列存、Region 分片 | 5560 |

- 🔧 **存算分离开源生态（2015–）**：从 Aurora 论文起，PolarDB、TiDB（TiFlash 列存旁路）、OceanBase 4.x 一体化均呼应 5.7；2026 年已成默认架构选项。
- **对象存储成为存储底座**：S3/对象存储 + 表格式（Iceberg/Delta/Hudi）让「存储层」标准化，与 5.7 解耦思想一致（见 [../湖仓架构大规模数据平台的设计和实现/00-总览与阅读地图.md](../湖仓架构大规模数据平台的设计和实现/00-总览与阅读地图.md)）。

## 常见误区与本书需修正之处

| 误区 | 事实 | 书目 |
| --- | --- | --- |
| 「分片就一定能无限扩展」 | 分片键选错会导致热点/跨分片事务激增，扩而不快 | 5.1 / 5.5 |
| 「多副本 = 高可用 = 强一致」 | 副本解决可用；强一致还要读写策略配合（quorum/同步） | 5.3 / 5.6 |
| 「存算分离一定慢」 | 网络成瓶颈是早期顾虑；日志即数据库/本地缓存已大幅缓解 | 5.7 |
| 🔧 本书 2021 对存算分离主流化估计偏保守 | 2026 年存算分离已是云原生 DB 标配，建议加重权重 | 5.7（🔧 补） |
| 🔧 本书未专述「跨地域多活」 | active-active 多活在 2026 年是金融级核心诉求 | 5.3 / 5.6（🔧 补） |
| 🔧 本书未把 Multi-Raft 作为可扩展+强一致的统一底盘 | 2026 年每分片一 Raft 组是主流实现 | 5.5 / 5.6（🔧 补，见第3章） |
