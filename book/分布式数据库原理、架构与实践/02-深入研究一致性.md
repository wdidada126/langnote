# 第 2 章　深入研究一致性

> 原书第 2 章是全书「一致性」主题的骨架：把一致性拆成四类——
> **结果一致性**（副本最终收敛到同一结果，含共识/拜占庭）、
> **次序一致性**（线性/顺序/因果/会话，关注事件顺序）、
> **分布式事务一致性**（单机事务 C 与分布式事务 C 的关系）、
> **架构一致性**（主备一致、去中心化一致）。
> 这一章给出一套「一致性分类学」，是读后续所有案例（Spanner/Percolator/CockroachDB）的字典。

## 核心精讲

（以下为教学性梳理，伪代码/示意均**教学示意，不参与构建**。）

### 2.2 结果一致性：共识与拜占庭

- **拜占庭将军问题（2.2.1）**：用「将军们通过信使达成一致进攻时机，其中可能有叛徒」形象化**共识（consensus）**——即使有故障/恶意节点，忠诚节点也要就同一命令达成一致。
- **结果一致性的应用（2.2.2）**：副本状态机复制（state machine replication）：只要所有副本以相同顺序执行相同命令，最终结果必一致。Paxos/Raft 解决的就是这个。

```text
# 教学示意，不参与构建：结果一致性的核心
目标: 多个副本对 "下一个要执行的命令是什么" 达成一致
手段: 共识协议 (Paxos / Raft) -> 形成一致的日志顺序
结果: 各副本重放同一日志 -> 状态最终相同 (结果一致)
```

### 2.3 次序一致性：四种「顺序」

- **线性一致性（2.3.1，Linearizability）**：最强。每个操作看起来在某一瞬时原子发生，且**若 opA 在真实时间上先于 opB 完成，则全局顺序中 A 必在 B 前**。等价于「单拷贝可串行、且符合真实时间」。
- **顺序一致性（2.3.2，Sequential）**：所有进程看到同一操作顺序，但该顺序**不必符合真实时间**，只要各进程自身程序序保持。
- **因果一致性（2.3.3，Causal）**：仅保持**有因果关系的事件**的顺序，并发事件可乱序。比顺序弱、比最终强。
- **会话一致性（2.3.4，Session）**：在「同一会话（连接）」内保证单调读/写，跨会话不保证。常用作最终一致系统的用户体验补丁。

```text
# 教学示意，不参与构建：四种次序的强弱（强 -> 弱）
线性一致 > 顺序一致 > 因果一致 > 会话一致(一种客户端视角的弱保证)
# 强一致是 "单系统" 错觉；越弱越能容忍分区/延迟
```

> 关键区别：**线性一致要求符合真实时间顺序**，顺序一致只要求「有个一致顺序」但不挂钩真实时间。这是 Spanner 用 TrueTime 换来的东西（见 [07-Spanner深度探索.md](07-Spanner深度探索.md)）。

### 2.4 分布式事务一致性：和「副本一致性」不是一回事

- **单机事务的一致性（2.4.1）**：ACID 的 C = 数据库始终满足**完整性约束**（主键唯一、外键、余额非负等）。它与「多副本是否一样」无关。
- **分布式事务的一致性（2.4.2）**：跨多个分片/参与者的事务，要么全提交要么全回滚，且隔离性要成立。
- **两者关系（2.4.3）**：副本一致性（第 2.2/2.3 类）解决「多个拷贝看到的数据是否一样」；事务一致性解决「一组操作是否满足完整性 + 隔离」。二者正交但**都影响用户看到的结果是否正确**——例如 2PC 提交后，若副本间是最终一致，仍可能读到旧值。

### 2.5 架构一致性：主备 vs 去中心化

- **主备一致性（2.5.1）**：一主多备，写走主、备异步/同步追——一致性取决于同步策略（强同步 = 牺牲可用/延迟）。
- **去中心化的分布式系统一致性（2.5.2）**：无单一主，靠共识在 peers 间达成一致（本书第 3 章 Paxos/Raft 的主战场，也是第二篇「去中心化架构」的题眼）。

## 版本演进

- **本书无第二版**；本节写 2021 年口径 → 2026 年视角的变化。
- **一致性谱系的工程化更清晰**：2026 年「线性/顺序/因果/会话/最终」五级已是默认心智模型；本书按四类（结果/次序/事务/架构）组织，建议读时把 2.3 的四级映射到这套通用谱系。
- **因果一致性的回归**：2026 年因果一致因「向量时钟 + 无协调读」在部分场景复兴（如 Bayou、COPS 一脉思想），本书 2.3.3 已点出，近年更受重视。
- 🔧 **本书成书时（2021）Raft 已是事实标准**，但书中对「Multi-Raft」着墨有限；2026 年 TiDB/CockroachDB/OceanBase 的 Multi-Raft 是结果一致性的主流工程形态，需补（见 [03-一致性问题的解法.md](03-一致性问题的解法.md) 与 [09-CockroachDB深度探索.md](09-CockroachDB深度探索.md)）。

## 常见误区与本书需修正之处

| 误区 | 事实 | 书目 |
| --- | --- | --- |
| 「一致性只有『一致/不一致』两种」 | 一致性是连续谱系：线性>顺序>因果>会话>最终 | 2.3 |
| 「线性一致 = 顺序一致」 | 线性一致额外要求「符合真实时间顺序」 | 2.3.1 / 2.3.2 |
| 「事务的 C 就是副本一致」 | 事务 C 是完整性约束，副本一致是多拷贝一致，二者正交 | 2.4.3 |
| 「最终一致一定会读到旧值，不可用」 | 最终一致配会话保证/有界陈旧可在多数业务可接受 | 2.3.4 / 2.5 |
| 「拜占庭问题只存在于加密货币」 | 它是共识的通用模型，容忍拜占庭需要 BFT 类协议 | 2.2.1 |
| 🔧 本书未把四类一致性映射到「通用强弱谱系」 | 2026 年普遍用「线性/顺序/因果/会话/最终」五级做统一框架，建议在 2.1 概览处补一张映射表 | 2.1（🔧 补框架） |
| 🔧 本书对因果一致性的近年工程复兴着墨少 | COPS/无协调因果读在 NewSQL 的取舍中权重上升，2026 年需补 | 2.3.3（🔧 延伸） |
