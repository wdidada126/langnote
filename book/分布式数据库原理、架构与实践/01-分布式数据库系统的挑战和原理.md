# 第 1 章　分布式数据库系统的挑战和原理

> 原书第 1 章是原理篇的引子：先罗列「设计一款分布式数据库要面对哪些挑战」，
> 再给出分布式设计的基本理论框架（CAP / PACELC / ACID-BASE），
> 最后落到「一致性的本质是什么」——偏序、全序、有序与并发。
> 这一章定调了全书：**一致性问题是分布式数据库的头号难题**。

## 核心精讲

（以下为教学性梳理，伪代码/示意均**教学示意，不参与构建**。）

### 1.1 挑战：分布式系统面临的问题 + 数据库面临的一致性问题

- **分布式系统面临的问题**（1.1.1）：节点故障、网络分区/延迟/乱序、消息丢失、时钟漂移、异构硬件。这些在单机世界里几乎不存在。
- **数据库面临的一致性问题**（1.1.2）：事务的 ACID（尤其 C 与 I）、副本间数据是否一致、读写是否看到「该看到」的版本。
- **分布式数据库系统面临的问题**（1.1.3）：把上面两组问题叠加——**在会出故障、会分区的网络上，还要保证事务的 ACID**。这正是本书全书要解的题。

> 本书的论断（内容提要原话）：「只要完美解决了一致性问题，那高可用分布式数据库的设计工作就完成了 80%。」这个结论可当**作者观点**记，不必当作不可置疑的公理。

### 1.2 分布式理论：CAP / PACELC / ACID-BASE

- **ACID（1.2.1）**：原子性、一致性、隔离性、持久性——单机事务的传统目标。
- **BASE（1.2.1）**：基本可用（Basically Available）、软状态（Soft state）、最终一致（Eventual consistency）——NoSQL 一脉的「退而求其次」哲学。
- **CAP（1.2.2）**：一致性（C）、可用性（A）、分区容忍（P）三者最多取二。**关键澄清**：分区（P）在网络系统中**不可避免**，所以真实取舍是「CP 还是 AP」，而不是「能不能三者全要」。

```text
# 教学示意，不参与构建：CAP 的真实取舍
正常网络:  可同时做到 C + A
发生分区:  必须选 -> CP（牺牲 A，拒绝可能不一致的写）
                  或 AP（牺牲 C，继续服务但可能读到旧值）
```

- **PACELC（1.2.3）**：在 CAP 之外补一个维度——**即便没有分区（E，else），也要在延迟（L）和一致性（C）之间取舍**。这是 CAP 的「新进展」，本书点名提到。

```text
# 教学示意，不参与构建：PACELC 的写法
如果 出现分区(P): 选 A 还是 C   (即 CAP)
否则(Else)      : 选 L(低延迟) 还是 C(强一致)
```

### 1.3 一致性的本质：偏序、全序、有序与并发

- **偏序与全序（1.3.1）**：happened-before 关系是一种**偏序**——并非任意两个事件都能比较先后；全序则是任意两个事件都能排出唯一先后。
- **有序与并发（1.3.2）**：两个事件若不能由偏序关系定先后，则**并发（concurrent）**。一致性的许多定义，本质就是「能否、以及如何把并发事件纳入一个合理的全序」。

```text
# 教学示意，不参与构建：偏序 vs 全序
事件 a -> b (a happened-before b): 可比较
事件 x, y 并发            : 偏序下不可比较，需额外机制(时钟/共识)才能排全序
```

- 本章的结论：第 2 章要细分「结果一致性 / 次序一致性 / 事务一致性 / 架构一致性」，第 3 章要用时钟与共识把偏序「升级」为可工程实现的全序。

## 版本演进

- **本书无第二版**；本节写 2021 年口径 → 2026 年视角的变化。
- **CAP 的教学口径微调**：2026 年更强调「P 不可避免，所以讨论的是 CP/AP + PACELC 的 L/C」，与本书 1.2.3 一致；但教学中常补充「一致性本身也有强弱谱系（线性/顺序/因果/最终）」，本书第 2 章才展开谱系。
- **一致性 80% 论**：2026 年看仍成立，但「解决一致性」不等于「解决一切」——可扩展性、运维、多租户、成本同样是工程核心。🔧 本书偏重一致性，读时勿把「一致性」当唯一维度。
- **新共识视角**：2021 年后，工业界对 CAP 的实际工程化更偏向「可调一致性（tunable consistency）」与「用共识换强一致但控制延迟（PACELC 的 L）」，与本书 1.2.3 方向一致。

## 近年研究与工业界开源实践（2015–2026）

- **star 数（2026-09，`gh api` 实测）**：本章偏理论，无直接对应单体开源；相关系统见后章。这里给出「一致性谱系」常被引用的工程实现系统的 star：

| 项目 | 定位 | star |
| --- | --- | --- |
| `cockroachdb/cockroach` | Spanner 精神继承者：Raft + HLC，强一致 | 32509 |
| `pingcap/tidb` | NewSQL：Multi-Raft + Percolator + TSO | 40591 |
| `oceanbase/oceanbase` | 国产原生分布式，Paxos 多副本 + TSO | 10291 |

- **可调一致性成为标配**：Cassandra / DynamoDB / Cosmos DB 均提供「一致性级别」开关（强/有界陈旧/最终），是 PACELC 的工程落地。
- **Jepsen 测试**：Kyle Kingsbury 的 Jepsen 系列（2015 起）持续曝光分布式数据库在分区/故障下的真实一致性行为，推动「声明的一致性」必须「可被验证」。
- 🔧 **线性一致性检查器普及**：Porcupine（Go）、Knossos（Clojure）让「声称线性一致」可被自动化证伪，是 2026 年做一致性实现的标配工具（本书成书时此类工具已存在但生态更成熟于其后）。

## 常见误区与本书需修正之处

| 误区 | 事实 | 书目 |
| --- | --- | --- |
| 「CAP 是说可以任选两个」 | P（分区容忍）在网络系统中不可避免，真实取舍是 CP 或 AP | 1.2.2 |
| 「ACID 与 BASE 是对立的，只能选一派」 | 它们是设计哲学光谱的两端，现代系统常在同一系统内按操作选不同级别（可调一致性） | 1.2.1 |
| 「一致性就是『数据一样』」 | 一致性有强弱谱系（线性/顺序/因果/会话/最终），「一样」只是其中最强的一种 | 1.3 / 第 2 章 |
| 「并发就是同时发生」 | 并发 = 偏序下不可比较先后，与是否物理同时无关 | 1.3.2 |
| 「解决了一致性就解决了一切」 | 一致性是核心但非全部，可扩展性/运维/成本同样关键 | 1.1（🔧 作者 80% 论需补偏） |
| 🔧 本书未给「一致性强弱谱系」的总览图 | 谱系在 2026 年是讨论一致性的前提；本书把谱系拆到第 2 章逐类讲，建议读前先建「线性>顺序>因果>会话>最终」的层级直觉 | 第 2 章 |
| 🔧 本书未提「可调一致性 / 逐操作一致性级别」 | 2026 年主流系统均支持按请求选一致性级别，是 PACELC 的直接工程化 | 1.2.3（🔧 工程延伸） |
