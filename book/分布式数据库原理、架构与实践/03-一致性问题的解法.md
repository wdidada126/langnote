# 第 3 章　一致性问题的解法

> 原书第 3 章是「解法篇」：前面两章把问题（一致性）讲透了，这一章给工具箱——
> 先讲**物理时钟不可靠**（3.1），再依次给出**逻辑时钟**（3.2）、**向量时钟**（3.3）、
> **混合逻辑时钟 HLC**（3.4），最后落到两大共识算法 **Paxos**（3.5）与 **Raft**（3.6）。
> 这一章是从「理论」到「工程」的桥：时钟解决「排序」，共识解决「就同一顺序达成一致」。

## 核心精讲

（以下为教学性梳理，伪代码/示意均**教学示意，不参与构建**。）

### 3.1–3.4 时钟三件套

- **物理时钟的问题（3.1）**：不同机器的墙上时钟有漂移，NTP 也只把误差收敛到毫秒级且可能跳变——**不能靠它定全局唯一顺序**。
- **逻辑时钟（3.2）**：Lamport 时钟给每个事件一个自增整数 `(counter, node_id)`，编码 happened-before。缺点：仅能判「a→b」，**无法区分「b 与 a 并发」还是「b 在 a 后」**。
- **向量时钟（3.3）**：每个节点维护一个向量 `[c1,c2,...]`，`V(a) < V(b)` 当且仅当每个分量都 ≤ 且至少一个 < ，此时可**判定因果先后**；不可比则并发。代价：向量长度 = 节点数。
- **混合逻辑时钟 HLC（3.4）**：`HLC = (physical_time, counter, node_id)`，在物理时间戳之上叠加逻辑计数，既「接近真实时间」（便于 TrueTime 类外部一致性），又能**在物理时间相等时靠逻辑计数排因果**。CockroachDB 即用它。

```text
# 教学示意，不参与构建：三种时钟的能力对比
逻辑时钟  : 能排 happened-before，不能判并发
向量时钟  : 能排因果 + 能判并发，O(节点数) 空间
HLC       : 接近真实时间 + 能排因果 + 定长，工程首选
```

### 3.5 Paxos

- **角色（3.5.2）**：Proposer（提议案）、Acceptor（批准）、Learner（学习结果）。
- **Basic Paxos（3.5.3）**：两阶段（Prepare/Promise → Accept/Accepted），保证「一旦某值被选定，后续提案必带该值」。只就**单个值**达成一致。
- **改进与扩展（3.5.4）**：Multi-Paxos（固定 Leader 把多轮 Basic Paxos 压成「选 Leader 后只发 Accept」）用于**复制日志**——这正是数据库副本一致的实现方式。

```text
# 教学示意，不参与构建：Multi-Paxos 复制日志
Leader 对每个日志槽 i 跑一轮 Paxos -> 所有副本的日志槽 i 值一致
=> 副本状态机重放同一日志 -> 结果一致 (对应第2章 2.2)
```

### 3.6 Raft

- **目标（3.6.1）**：与 Paxos 等价的能力，但**更易理解与实现**——把问题拆成 Leader 选举、日志复制、安全性三部分。
- **详解（3.6.2）**：任期（term）+ 心跳维持 Leader；写请求经 Leader 复制到多数派才提交；Leader 切换时靠「提交规则」防日志空洞。
- **与 Paxos 比较（3.6.3）**：Raft = Multi-Paxos 的「可理解重排版本」；工程上 Raft 因其清晰成为 2026 年主流（etcd、TiKV、Consul 都用 Raft）。

```text
# 教学示意，不参与构建：Raft 写流程
Client -> Leader: 写
Leader 追加日志 -> 发给 Follower
多数派 (quorum) 写入成功 -> Leader 提交 -> 回复 Client
```

## 版本演进

- **本书无第二版**；本节写 2021 年口径 → 2026 年视角的变化。
- **Raft 已是事实标准（本书 3.6 已体现）**：2026 年 Raft 系（etcd-io/etcd、tikv/tikv、hashicorp/consul）几乎垄断「需要共识的组件」；本书判断正确。
- **Multi-Raft 成为数据库主流**：单 Raft 组无法水平扩展，TiDB/TiKV、OceanBase、CockroachDB 都用 **Multi-Raft**（每个分片一个 Raft 组）。🔧 本书 2021 对 Multi-Raft 着墨有限，2026 年必须补。
- **HLC 普及**：CockroachDB/YugabyteDB 用 HLC 替代 TrueTime 的硬件依赖（见 [09-CockroachDB深度探索.md](09-CockroachDB深度探索.md)）。本书 3.4 已讲 HLC，方向正确。
- **TSO 路线并存**：OceanBase（GTS）、TiDB（PD）走「中心时间戳分配器」而非无中心 HLC。🔧 本书未把「TSO vs HLC」作为两大工程路线对比，建议补。

## 近年研究与工业界开源实践（2015–2026）

- **star 数（2026-09，`gh api` 实测）**：共识是这些系统的底座：

| 项目 | 定位 | star |
| --- | --- | --- |
| `cockroachdb/cockroach` | Raft + HLC，共识用于每个 Range | 32509 |
| `pingcap/tidb` | PD 提供 TSO；TiKV 用 Raft（Multi-Raft） | 40591 |
| `tikv/tikv` | 基于 Raft（Multi-Raft）的分布式 KV 存储 | 16878 |
| `oceanbase/oceanbase` | Paxos 多副本（Multi-Paxos 思想） | 10291 |

- **etcd-io/etcd**：Raft 的标杆实现（Go），是 Kubernetes 的元数据底座；其 raft 库被众多项目复用。
- **新共识变种（2015–）**：EPaxos / WPaxos（无序/分区共识，降低跨机房延迟）、Raft 的流水线/批处理优化（如 TiKV 的 batch+Raft）；🔧 本书 2021 未展开这些，属 2026 年延伸。
- **BFT 在工业界的回归**：区块链带火 BFT（Tendermint/COMETBFT），但在「可信机房内」数据库仍用 CFT（Crash Fault Tolerance）的 Raft/Paxos。

## 常见误区与本书需修正之处

| 误区 | 事实 | 书目 |
| --- | --- | --- |
| 「物理时钟够用，直接用 NTP 排序」 | NTP 有误差且会跳变，不能定全局唯一顺序 | 3.1 |
| 「逻辑时钟能判并发」 | 逻辑时钟只能编码 happened-before，无法区分并发与因果后 | 3.2.3 |
| 「Paxos 和 Raft 是两回事」 | Raft 等价于 Multi-Paxos 的可理解重排版 | 3.6.3 |
| 「Basic Paxos 就能当日志复制用」 | Basic Paxos 只定单值，日志复制要用 Multi-Paxos/Raft | 3.5.4 |
| 「HLC 就是物理时间」 | HLC 是物理时间 + 逻辑计数的混合，仍可判因果 | 3.4 |
| 🔧 本书对 Multi-Raft 着墨有限 | 2026 年水平扩展靠 Multi-Raft（每分片一 Raft 组），是分布式 DB 标配 | 3.6（🔧 工程延伸） |
| 🔧 本书未对比 TSO vs HLC 两条工程路线 | 通用系统要么中心 TSO（OB/TiDB-PD），要么无中心 HLC（CockroachDB）；这是 2026 年选型核心 | 3.4 / 3.6（🔧 补对比） |
| 🔧 本书未提 EPaxos/WPaxos 等无序共识 | 跨地域低延迟场景的无序共识在 2015 后成熟，属 2026 延伸 | 3.6（🔧 延伸） |
