## 五、🔧 本机类比实验总表（SQLite/DuckDB，**均非 SQL Server 行为**）

因 SQL Server 无法本机部署，以下 5 组实验只用于锚定「观测面」概念，引擎语义均不同，禁止当作 SQL Server 结论引用：

| 组 | 落点章节 | 实验 | 实测结果（本机 Python 3.13 / stdlib sqlite3 + duckdb） |
|---|---|---|---|
| T1 | 06 | `ANALYZE` 后 `sqlite_stat1` 出现行数统计（表级 `'t',NULL,'20000'`），配合索引后计划由 `SCAN t` 变 `SEARCH t USING INDEX ix_b` | 🔧 概念锚：统计信息驱动选择率判断（SQL Server 的直方图/头远比这复杂） |
| T2 | 09 | 连接 A `BEGIN EXCLUSIVE` 持锁，连接 B `PRAGMA busy_timeout=200` 下写同一库 | 🔧 B 等待约 659ms 后报 `database is locked`（SQLite 的 busy handler 按步长退避，超时精度是离散步进）；A 提交后 B 仅 2.8ms 完成——「阻塞即等待」的最小模型 |
| T3 | 10 | `set_trace_callback` 全程捕获语句文本 | 🔧 得到 CREATE/INSERT×5/SELECT 的流式痕迹——「轻量持续捕获」锚点；SQL Server 对应物是扩展事件（机制完全不同） |
| T4 | 05 | 3 万行表 `page_count`=1585；删 90% 后仍 1585 页、`freelist_count`=1385；`VACUUM` 后 160 页 | 🔧 「删数据≠缩文件、空间进空闲链」——对应索引膨胀/页复用概念（SQLite 无在线 REBUILD） |
| T5 | 02/07/08 | DuckDB `EXPLAIN ANALYZE` 输出带算子名的计划树（`PERFECT_HASH_GROUP_BY` 等）与逐算子 time/rows | 🔧 逐算子实测统计 ≈ SQL Server 实际执行计划 + `sys.dm_exec_query_stats` 的观测意图（语义不可平移） |

- **动态管理视图** — Dynamic Management Views (DMV)：引擎内状态的只读系统视图族（⚠️ 转述）
- **查询存储** — Query Store：计划与运行时统计的历史库（⚠️ 转述）
- **扩展事件** — Extended Events (XEvent)：轻量事件捕获框架（⚠️ 转述）
- **参数嗅探** — Parameter sniffing：编译期采样参数值导致计划不适配其他参数（⚠️ 转述）
- **索引碎片** — Index fragmentation：逻辑/物理页序偏离与页密度不足（⚠️ 转述）
- **基数估计** — Cardinality estimation (CE)：优化器对行数的预测，排错中多数「坏计划」的根因层（⚠️ 转述）
- **阻塞链** — Blocking chain：会话互相等待锁形成的有向链（⚠️ 转述）
- **SQLOS** — SQL Server Operating System 层：调度/内存/闩锁等 OS 抽象（⚠️ 转述，详见 #56 笔记）
- **参照数据** — Reference data：健康基线快照，故障时做差比对（⚠️ 转述）
- **busy handler** — SQLite busy_timeout：本机 🔧 类比用的阻塞等待机制，**非 SQL Server 行为**

## 最新演进与工业实践

到 2024–2026，本书方法论对应物的现状（各章文末展开，此处只给总图）：

1. **版本面**：SQL Server 2022→2025（docs 已现 `sql-server-ver17` 视图）延续本书主线：Query Store 成为默认排错台、智能查询处理（IQP）系列特性替代了当年手工 trace flag 的位置；官方排错文档持续以 DMV+XEvent 为骨架：[sys.dm_os_wait_stats](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-os-wait-stats-transact-sql)、[Query Store](https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store)、[扩展事件](https://learn.microsoft.com/en-us/sql/relational-databases/extended-events/extended-events/)（均 ✅ 2026-09 HEAD 200）。
2. **工具生态**：Brent Ozar 团队 [SQL Server First Responder Kit](https://github.com/BrentOzarULTD/SQL-Server-First-Responder-Kit) 与 Adam Machanic 的 [sp_WhoIsActive](https://github.com/amachanic/sp_whoisactive) 仍是最活跃的工业级排错脚本库（✅ HEAD 200），与本书「脚本化巡检」路线一致；Paul Randal 系检查面（DBCC CHECK 家族）仍是完整性兜底，见 Kalen Delaney/Paul Randal 生态的 [Pro SQL Server Internals](../Pro_SQL_Server_Internals/00-总览与阅读地图.md) 笔记。
3. **研究面**：「自动调优/自感知 DBMS」是本书主题的研究升级版：Eddies 自适应执行（Avnur 与 Hellerstein，SIGMOD 2000，[DOI:10.1145/342009.335420](https://api.crossref.org/works/10.1145/342009.335420) ✅）、SIGMOD 2018 负载预测自驾驶 DBMS（Ma 等，[DOI:10.1145/3183713.3196908](https://api.crossref.org/works/10.1145/3183713.3196908) ✅）、MB2 行为分解建模（Marcus 等，SIGMOD 2021，[DOI:10.1145/3448016.3457276](https://api.crossref.org/works/10.1145/3448016.3457276) ✅）。
4. **跨引擎对照**：等待/事件理念在其他引擎的等价物（PostgreSQL `pg_stat_activity`、SQLite `busy_timeout`、DuckDB 逐算子剖析）见本目录 🔧 类比总表；教科书层定义见 [数据库系统概念7](../数据库系统概念7.md)。
