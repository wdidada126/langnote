# 08 查询存储与计划回归排查（⚠️ 主题重构章）

> 章名非原书逐字章名（取证降级见 [00-总览与阅读地图](00-总览与阅读地图.md) 第二节）。本章重构 Query Store：它解决的观测缺口、数据模型、回归对拉工作流与强制计划。全部 **⚠️ 转述**；🔧 **非 SQL Server 行为**。

## 1. Query Store 补的是哪个洞

⚠️ 转述：第 07 章的 `dm_exec_query_stats` 有三个结构性缺口——重启即失、计划逐出即失、无「同查询历史多计划」的时间轴。Query Store（2016+ 引擎内建，SQL Server/Azure SQL 均可用）把 **查询→计划→运行时统计** 的三元组持久化到用户库内：`sys.query_store_query`（逻辑查询）、`sys.query_store_plan`（含 XML 与最后执行时间）、`sys.query_store_runtime_stats`（按区间的聚合时延/CPU/内存授予/临时表使用）。官方权威页 ✅ HEAD 200：https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store

关键配置语义 ⚠️ 转述：`WAIT_FOR_RESULTS`（默认且推荐）、数据清洗（flush 间隔/存储上限）、`OPERATOR_LEVEL_METRICS`（SS2022+ 开算子级统计——把第 02 章「估计 vs 实际」推进到「逐算子历史」）。

## 2. 回归（Plan Regression）的标准工作流

⚠️ 转述：「昨天快今天慢」的四步：

1. **定位查询**：top resources by duration/recent vs history（SSMS 报表或 T-SQL 对 `runtime_stats` 差分）；
2. **切计划**：同 `query_id` 下按 `plan_id` 与时间分桶——出现「计划 B 上线后均值时延台阶式上升」即回归；
3. **归因**：对比 A/B 计划 XML 差异（驱动表、连接类型、DOP、估计行数——回到 06/07 章上游）；
4. **处置**：`sp_query_store_force_plan(query_id, plan_id)` 止血 + 决定长期修（统计/索引/参数化）。
   反向操作 `sp_query_store_unforce_plan`；清盘用 `sp_query_store_flush_db`/`RemoveQueryStoreAllReports` 系（⚠️ 转述名称族，落地前查目标版本文档）。

## 3. 读数据的最小查询集（重构示例，⚠️ 转述语义）

```sql
SELECT qs.query_id, qp.plan_id, rs.runtime_stats_interval_id,
       rs.avg_duration, rs.max_duration, rs.count_executions
FROM sys.query_store_runtime_stats rs
JOIN sys.query_store_plan qp ON qp.plan_id = rs.plan_id
JOIN sys.query_store_query qs ON qs.query_id = qp.query_id
WHERE qs.query_sql_text LIKE N'%Orders%'
ORDER BY rs.last_execution_time DESC;
```

要点：区间表 `sys.query_store_runtime_stats_interval` 给时间轴；`execution_type` 区分正常/异常终止；强制计划后 `force_failure_count` 观察是否反复失效（=上游还没修好）。

## 4. 不只是回归：Query Store 的三种排错用法

⚠️ 转述：
1. **升级验收**：CU/大版本/兼容性级别切换前后，用 top 资源查询 + 计划变化对比清单做回归门禁（升级后第一件事，胜过事后救火）；
2. **长期趋势**：时延的周环比、执行次数结构变化，替代自造快照表的第 01 章参照数据；
3. **取证回溯**：事故窗口内「谁在那 10 分钟出现新计划」——把第 06/07 章的「再编译抖动」变成可查询历史。

## 5. 边界与陷阱（⚠️ 转述）

1. **默认未开启**（SQL Server 侧，Azure SQL 默认开）：没数据 ≠ 没事故——上线清单第一项 `ALTER DATABASE ... SET QUERY_STORE = ON`；
2. **写放大**：高频短查询+算子级统计的元数据开销，需用 interval/limit 控制；
3. **强制不是修复**：数据分布继续漂移后强制计划可能变新的坑；
4. **清理即历史断层**：存储上限触发的 auto-purge 会吃掉老区间，取证窗口有限（保留策略要写进治理文件）；
5. 跨库视图不同：Query Store 数据在**各用户库内**，实例级汇总需自建联合查询。

## 6. 🔧 类比实验（**非 SQL Server 行为**）

1. **逐算子实测对照** 🔧：DuckDB `EXPLAIN ANALYZE` 在本机对 20 万行聚合查询输出含 `PERFECT_HASH_GROUP_BY` 的算子树与逐算子 time/rows——相当于「开了算子级统计且只此一次」的 Query Store 断面；差异在**持久化与历史轴**：DuckDB 不存，Query Store 存。
2. **重启即失对照** 🔧：SQLite 无任何计划历史；跑 `EXPLAIN` 两次无法区分「计划变了吗」——用它体会 2016 之前 SQL Server 的观测真空（当年靠 `dm_exec_*` 抢救+快照表土法）。
3. **区间聚合类比** 🔧：把 SQLite 当「参照数据库」，用 Python 每分钟采一次 `PRAGMA page_count` 写时序表——手工复现 `runtime_stats_interval` 的思想（分桶+聚合+清洗），帮助理解 Query Store 的表设计而非其引擎语义。
4. **强制计划类比** 🔧：SQLite/DuckDB 无 plan forcing 原语；最接近的是 SQLite 索引提示 `INDEXED BY`——「把计划钉死，数据变了也不松手」的副作用（陈旧钉死）同构可感。

## 8. 检查清单（重构）

1. 所有关键库 `is_query_store_on=1` 巡检入作业；
2. 存储上限/清洗策略按「取证窗口 ≥ 一个业务周期」设定；
3. 升级演练：兼容性级别变更先在 Query Store 快照窗口内做 A/B；
4. 强制计划必须挂「到期复审」标签，防永久拐杖；
5. 定期导出 top 回归候选清单（时延台阶检测：均值±kσ 或分位跳变）；
6. 与扩展事件（10 章）分工：Query Store 管「计划与时延历史」，XEvent 管「锁/闩/错误事件流」。

## 9. 管理面与取证面速记（⚠️ 转述语义）

```sql
-- 启停与体检（列/选项名以目标版本文档为准）
ALTER DATABASE [AppDb] SET QUERY_STORE = ON (
    OPERATION_MODE = READ_WRITE,
    QUERY_CAPTURE_MODE = AUTO,             -- 智能过滤，低峰开销
    MAX_STORAGE_SIZE_MB = 2048,
    INTERVAL_LENGTH_MINUTES = 30,
    DATA_FLUSH_INTERVAL_SECONDS = 900,
    CLEANUP_POLICY = (STALE_QUERY_THRESHOLD_DAYS = 60)
);
SELECT name, is_query_store_on FROM sys.databases;   -- 实例巡检一行
```

- `QUERY_CAPTURE_MODE`：AUTO 依赖查询生命周期启发式，短查询海洋型负载建议显式 `ALL` 试点后回退评估；
- 强制的持久性：强制记录存于库内，随备份/AG 走——但故障切换到可读副本后强制不生效（副本只读，⚠️ 转述边界）；
- 多库汇总：各库 QS 独立，实例级「TOP 回归榜」需遍历 `sys.query_store_*` 的库间联合查询或集中采集（第 10 章仓库层）。

## 10. 场景演练（重构示例，⚠️ 非原书案例）

**场景 A｜「升级当天 15:10 起订单查询 8 倍慢」**
1. QS 按 `last_execution_time` 切 15:00 前后两窗：同 query_id 出现新 plan_id——教科书回归；
2. 对拉两计划 XML：驱动表互换+估计行数从 300 跳到 420 万（06 章 CE 病灶）；
3. 止血：force 旧计划；根因：升级重置了某列组统计采样——进 06 章处方；
4. 归档：本次「新计划出现」的检出 SQL 固化为升级门禁模板。

**场景 B｜「强制计划反复失效」**
1. `force_failure_count` 上升 = 被强制计划基线被删（索引变更/兼容性调整）；
2. 说明强制只是遮羞布：回归真实根因（缺索引？参数形态？）后解除强制；
3. 治理规则：每条 force 必须带工单号注释（自建登记表，QS 本身无注释字段 ⚠️ 转述）。

## 核心概念速览（中英对照）

- **查询存储** — Query Store：库内持久化的查询/计划/运行时三元组历史 ⚠️
- **query_id / plan_id** — 逻辑查询与计划的稳定标识：回归对拉的坐标 ⚠️
- **运行时统计区间** — runtime_stats_interval：时间分桶聚合单元 ⚠️
- **计划回归** — Plan regression：新计划导致性能台阶式劣化 ⚠️
- **强制计划** — Force plan：`sp_query_store_force_plan` 钉定执行方案 ⚠️
- **算子级统计** — Operator-level metrics：SS2022+ 的逐算子历史 ⚠️
- **WAIT_FOR_RESULTS** — 启用模式：首启用不阻塞在线负载的等待语义 ⚠️
- **auto-purge** — 自动清洗：超上限后的历史截断，取证窗口杀手 ⚠️
- **升级验收** — Upgrade validation：以 QS 历史做回归门禁的 DBA 流程 ⚠️
- **EXPLAIN ANALYZE** — DuckDB 🔧 一次性逐算子断面：无历史轴，**非 SQL Server 行为**
- **INDEXED BY** — SQLite 🔧 计划钉死类比：陈旧拐杖同构感，**非 SQL Server 行为**

## 最新演进与工业实践

1. **版本线（⚠️ 转述自官方）**：SQL Server 2022 引入算子级统计与更细资源维度；2025（`ver17`）方向为 Query Store 数据归档至 Azure（保留长历史、本地瘦身）——第 5 节「取证窗口」矛盾的产品化解法；官方页保持 [✅ HEAD 200](https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store)。
2. **Azure 托管化**：自动计划纠正（automatic plan correction）= Query Store + 自动 force/unforce 的云端默认策略；工业争议在「自动兜底掩盖根因」——本书「处置≠修复」原则正好回应。
3. **工具生态**：FRK 系（✅ [GitHub](https://github.com/BrentOzarULTD/SQL-Server-First-Responder-Kit)）与第三方 QS 报表器持续维护；Paul Randal 系博客长期供 QS 内部机制（异步 flush 线程）排错案例（⚠️ 转述）。
4. **研究同频**：自驾驶 DBMS 把「计划选择+回归检测」建模为学习问题——负载预测（Ma 等，SIGMOD 2018，[DOI:10.1145/3183713.3196908](https://api.crossref.org/works/10.1145/3183713.3196908) ✅）、MB2 配置行为建模（SIGMOD 2021，[DOI:10.1145/3448016.3457276](https://api.crossref.org/works/10.1145/3448016.3457276) ✅）；Query Store 的三元组历史正是这类模型缺的「训练数据」底座 ⚠️ 评注。
