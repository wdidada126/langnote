# 06 统计信息与基数估计（⚠️ 主题重构章）

> 章名非原书逐字章名（取证降级见 [00-总览与阅读地图](00-总览与阅读地图.md) 第二节）。本章重构「统计信息维护 + 低效查询的估计误差」主题：直方图/密度模型、自动统计的触发学、以及把坏计划归因到 CE 误差的读法。全部 **⚠️ 转述**；🔧 为本机 SQLite/DuckDB 实测，**非 SQL Server 行为**。

## 1. 统计信息在排错链中的位置

⚠️ 转述：优化器的一切成本比较都建立在「估计行数」上；估计由统计信息（每列/每统计对象：头部+直方图，基于采样）产生。**多数「坏计划」的第一因是行数估计错误**，而非索引缺失——这是本章作为第 07/08 章前置的理由。机制详版：[Pro SQL Server Internals/03-统计信息](../Pro_SQL_Server_Internals/03-统计信息.md)。

## 2. 观测面：怎么看「统计新不新鲜、够不够用」

⚠️ 转述（官方统计文档：https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics ✅ HEAD 200）：

- `sys.stats` / `sys.dm_db_stats_properties`：最后更新时间、`modification_counter`（自上次更新以来变更估计量）、采样行数与百分比；
- `DBCC SHOW_STATISTICS`：头部（行密度/步骤数）+ 直方图（≤201 步的 RANGE_HI_KEY/RANGE_ROWS/EQ_ROWS）；
- 计划层面：XML 中 `Guess`/`Cardinality` 与实际 `rowcount` 的对比（第 08 章实计划对拉的基础）。

**大表陷阱** ⚠️ 转述：自动更新的触发阈值历史上按「行数固定比例」设计，超大表要等海量变更才触发——2016 起跟踪标志 346/`TF 2371` 语义并入较新版本，改变触发曲线（陡峭化）；排错时看到「统计表 18 个月没更新但表每天变 2%」要立刻意识到采样滞后。

## 3. 直方图的读法：一个例子级说明

⚠️ 转述：直方图把值域切成 ≤201 步，每步记录高键值、步内行数、等于高键的行数。由此：

1. 谓词落在大步内 → 估计按步内均匀假设摊分（倾斜数据必错）；
2. 值不在直方图（新写入的热点值）→ 按密度/平均频率外推；
3. 相关列的组合谓词 → 独立性假设（`WHERE a=? AND b=?` 按密度相乘）——列组统计（filtered/column group stats）存在的理由。

「估计 10 行、实际 10 万行」的经典事故形态即上述 1+3 叠加：嵌套循环被选成驱动计划。

## 4. 维护动作与选择

⚠️ 转述：`UPDATE STATISTICS` 的 `WITH FULLSCAN / SAMPLE n PERCENT / RESAMPLE`；索引 REBUILD 附带更新其索引统计但**不覆盖筛选统计**（第 05 章关联盲区）。策略面共识：核心表固定周期 FULLSCAN 不现实时用「按修改量驱动」的更新作业；`_WA_` 前缀的系统统计（自动创建的单列统计）是依赖信号而非噪声（⚠️ 转述，Kalen Delaney 系经典解释）。

## 5. CE 的版本与补偿器

⚠️ 转述：旧/新基数估计器（LE/CE，以兼容性级别切换）对相关性与倾斜建模不同；SQL Server 2019+ 的 **IQP** 系列给 CE 误差上了运行时补偿：基数估计反馈（表变量）、内存授予反馈（第 04 章）、表变量延迟编译。排错含义：**同一查询在不同兼容性级别给出不同计划**是合法解释项——回归排查先核对兼容级别与数据库级 IQP 配置。

## 6. 🔧 本机类比实验（**非 SQL Server 行为**）

1. **T7 统计的形态** 🔧（SQLite）：20 万行表上 `status`（两值：19.9 万/1 千）与 `amt`（高基数）各建索引；`ANALYZE` 后 `sqlite_stat1` 得到：
   - `('orders','ix_amt','200000 200')`、`('orders','ix_status','200000 100000')`
   ——格式「总行数 + 每不同值平均重复数」即 SQLite 的密度模型（无直方图）。`ix_status` 的 avg 重复 100000 一眼可见选择性灾难。
2. **T1 统计→计划翻转** 🔧：无统计时 2 万行表按 `b=42` 计划 `SCAN`；建索引+`ANALYZE` 后翻为 `SEARCH ... USING INDEX ix_b`——「统计改变成本比较从而改变计划」的最小因果链（SQL Server 的直方图比这丰富得多，因果同构）。
3. **DuckDB 侧对照** 🔧：`ANALYZE` 后 `EXPLAIN ANALYZE` 的逐算子实测 rows 让「估计 vs 实际」可直接对拉——SQL Server 需实际执行计划（Ctrl+M）拿到的东西，DuckDB 一条命令给全。
4. **类比局限登记**：SQLite 无自动更新触发学、无直方图步、无 `modification_counter`——本章第 2/4 节的「新鲜度」维度只在 ⚠️ 转述层成立，本机无法复现。

## 8. 检查清单（重构）

1. 坏计划先做「估计 vs 实际」逐算子对拉，误差 >10× 的算子即 CE 病灶；
2. 查统计最后更新时间 + `modification_counter` 双指标，不单独看日期；
3. 大表：确认触发曲线（版本/跟踪标志）是否让更新「永远追不上」；
4. 筛选统计、列组统计是否覆盖高频谓词组合；
5. 回归类问题核对兼容性级别与 IQP 配置差异（第 08 章联动）；
6. 更新统计后仍劣化 → 转 `OPTION (RECOMPILE)`/查询存储强制等短期止血 + 回到设计层。

## 9. 三个现场场景（重构示例，⚠️ 非原书案例）

**场景 A｜「升级兼容级别后个别查询慢 40 倍」**
1. 新 CE 的相关性/约束推理模型改变 → 行数估计台阶式变化；
2. 抓新旧计划对拉估计 vs 实际（08 章实计划），确认误差量级方向；
3. 数据库级回退兼容性级别只是止血，正解按病灶选：列组统计/重写谓词/提示。

**场景 B｜「WHERE 含隐式转换，统计再新也没用」**
1. `nvarchar` 列配 `varchar` 常量 → 列侧 CONVERT 使 seek 不可能（机制在 #36/14 章表达式域）；
2. 统计视图一切正常，但估计退化为全表密度——先查 plan XML 里的 CONVERT 再查统计；
3. 治法：类型对齐（连接/驱动层），本章负责识别、应用层负责根除。

**场景 C｜「参数化视图/函数的统计盲区」**
1. 内联 TVF 的谓词估计会并入外层；多语句 UDF 按固定 1 行猜（⚠️ 转述经典行为，2019 表变量/批处理改进部分缓解）；
2. 误差被嵌套放大——把 UDF 展开成 JOIN 后重估；
3. CE 反馈类特性对 UDF 内部无效（⚠️ 转述），此类「估计 1 行实际 10 万行」计划须手工治理。

## 10. 采样学补充（⚠️ 转述）

- 采样率与直方图步界的随机性：同表两次 SAMPLE 10% 可得不同步界，谓词恰跨步界时估计抖；关键对象用 FULLSCAN 或固定 `RESAMPLE` 语义；
- 增量统计（incremental stats，分区级）依赖分区对齐，`ALTER TABLE SPLIT/MERGE PARTITION` 会使其失效——维护脚本必须联动重建（05 章联动）；
- 持久化：统计本体是表内对象，随备份迁移；但自动更新是**库选项**，环境漂移要巡检（`DATABASEPROPERTYEX(N'AppDb', N'IsAutoUpdateStatistics')`，⚠️ 转述），异步变体 `AUTO_UPDATE_STATISTICS_ASYNC` 另有一档「先旧计划后更新」的时序副作用。

**语句小抄**（重构，语义 ⚠️ 转述）：

```sql
-- 新鲜度与变更量（列名以目标版本官方文档为准）
SELECT OBJECT_NAME(s.object_id) AS obj, s.name,
       p.last_updated, p.modification_counter, p.rows, p.rows_sampled
FROM sys.stats s
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) p
WHERE p.last_updated < DATEADD(day, -14, SYSUTCDATETIME())
   OR p.modification_counter > p.rows * 0.10;

-- 定向更新（对谓词热点列，别全库无差别）
UPDATE STATISTICS dbo.Orders (STAT_OrderDate) WITH FULLSCAN;
```

**与 05 章的分工再申明**：索引 REBUILD 只带走其索引统计的更新义务，筛选统计/单列系统统计要独立巡检——「做了维护作业≠统计健康」是排错访谈里最常翻车的回答。

**估计误差的量化口径**（重构建议）：逐算子 `实际行数/估计行数` 取比值，>100× 为红级（直接决定连接类型错配）、10–100× 黄级（倾斜/步界问题）、反向 <0.01× 也要立案（低估导致授予不足与 spill）。该表填进第 01 章证据层级第二层以下的第一站。

## 核心概念速览（中英对照）

- **统计信息** — Statistics：列值分布的采样摘要（头部+直方图） ⚠️
- **直方图** — Histogram：≤201 步的值域切分与步内计数 ⚠️
- **密度** — Density / average key frequency：每不同值平均重复数 ⚠️（🔧 SQLite 仅有此项）
- **基数估计** — Cardinality Estimation (CE)：谓词/连接行数的预测 ⚠️
- **独立性假设** — Independence assumption：组合谓词按密度相乘的建模简化 ⚠️
- **自动创建/更新统计** — Auto-create/update stats：引擎自维机制及其触发学 ⚠️
- **modification_counter** — 变更计数：`dm_db_stats_properties` 的新鲜度原料 ⚠️
- **筛选统计** — Filtered statistics：谓词子集上的专属统计 ⚠️
- **TF 2371** — 跟踪标志：大表自动更新触发曲线的引擎级修正 ⚠️
- **基数估计反馈** — CE feedback：IQP 对表变量行数的运行时纠偏 ⚠️
- **sqlite_stat1** — SQLite 🔧 统计表：「行数+平均重复」极简密度模型，**非 SQL Server 行为**
- **估计 vs 实际** — Estimated vs actual rows：一切计划诊断的第一对照 ⚠️/🔧
