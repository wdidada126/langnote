# 01 故障排除方法论与体系结构基础（⚠️ 主题重构章）

> 章名非原书逐字章名（取证降级见 [00-总览与阅读地图](00-总览与阅读地图.md) 第二节）。本章重构「排错从哪开始」的总纲：SQL Server 体系结构分层、性能问题的资源视角、等待差值法与参照数据基线。凡引擎行为均为 **⚠️ 转述**（据微软官方文档与作者公开写作），未经本机验证。

## 1. 排错的对象是一个「排队系统」

⚠️ 转述：SQL Server 的 CPU 与并行度由 SQLOS 的调度器（scheduler）模型管理，请求在调度器上以「协作式」方式运行——一段自愿让出（yield）后重新排队。由此得到排错的第一性原理：**任何一次请求的墙钟时间 = 实际干活时间 + 各类等待时间 + 队列等待时间**。慢查询诊断不是找「哪条 SQL 慢」，而是回答「时间花在哪一类资源上」。

SQLOS 分层（详细内核面见 [SQL_Server_2012_Internals/01-体系结构与SQLOS](../SQL_Server_2012_Internals/01-体系结构与SQLOS.md)）：

- 宿主层：Windows/Linux 之上的 OS 抽象（调度、NUMA、内存节点）；
- SQLOS 层：调度器/任务、资源池、闩锁（latch）、异步 I/O；
- 引擎层：关系引擎（查询编译/执行）+ 存储引擎（缓冲池、日志）；
- 可观测层：DMV、等待统计、扩展事件、Query Store（本书后续各章的入口）。

## 2. 资源四象限：CPU / 内存 / I/O / 并发

⚠️ 转述：社区通行的分类法（等待类型即按此归类）把症状映射到四类资源：

| 资源 | 典型问题形态 | 本目录对应章 |
|---|---|---|
| CPU | 编译风暴、低效计划、并行过度、非yield 时间片 | 07 / 08 |
| 内存 | 缓冲池不足→物理读放大、查询内存授予（grant）等待 | 04 |
| I/O | 存储延迟、tempdb 争用、预读/日志写 | 03 |
| 并发 | 锁阻塞、死锁、闩争用 | 09 / 10 |

方法论要点：**先分类再深挖**。用一次等待统计快照（第 02 章）把问题钉进象限，能避免 80% 的「看见碎片就重建」式误诊。

## 3. 等待差值法：排错的「体温计」

⚠️ 转述：`sys.dm_os_wait_stats` 自实例启动累计，直接看绝对值会被历史噪声淹没。正确姿势是差值采样：

1. 采集快照 S1（过滤良性等待后按等待时间排序）；
2. 等待一个故障窗口（如 5 分钟）；
3. 采集 S2，做 S2−S1，得到窗口内真实消耗。

良性等待（用户端网络推送、睡眠、浏览器/锁获取类「等活干」的等待）不计入问题——社区脚本（sp_BlitzFirst、First Responder Kit）已内置过滤白名单（见第 10 章）。

🔧 **概念锚点（非 SQL Server 行为）**：等待差值法的本质是「对累计计数器做区间差分」，在任何引擎都成立。本机 SQLite 的最小类比是阻塞等待实验：连接 A `BEGIN EXCLUSIVE` 持锁后，连接 B 设 `PRAGMA busy_timeout=200` 再写库——实测 B 等待约 **659ms** 后抛出 `database is locked`（SQLite 的 busy handler 按离散步长退避，200ms 只是「至少」语义）；A 提交后再测 B 仅需 **2.8ms** 完成。「时间去哪了 = 干活 + 排队」在 SQLite 上表现为一次可复现的等待差。此为 SQLite 行为，SQL Server 的锁等待是会话级可观测的 `sys.dm_exec_requests.wait_type`，机制完全不同。

## 4. 参照数据（Reference Data）：没有基线就没有异常

⚠️ 转述：作者系社区（Paul Randal、Brent Ozar 等）反复强调的工程实践：故障现场不可复现是常态，必须在健康期持续留下「正常长什么样」：

- 每日/每小时的 DMV 快照（等待 top-N、CPU、IOPS、内存压力指标）；
- 计划与统计的元数据（Query Store 本身即是自动参照库，见第 08 章）；
- 容量趋势（文件增长、tempdb 版本化速率、日志生成率）。

落地清单（重构建议，非原书逐字）：
1. 选定采集器（FRK 存储过程定时作业 / 自定义 DMV 快照表 / XEvent）；
2. 定义保留期（原始 7–14 天、聚合 ≥1 年）；
3. 定义「告警即快照」动作：CPU 突增时自动抓 `dm_exec_requests` + 计划文本；
4. 季度演练：用历史快照盲测一次「上周三 14:00 为什么慢」。

## 5. 排错的证据层级

⚠️ 转述：证据强度从高到低——实际执行计划的算子级统计 > 等待统计 > 会话级 DMV 快照 > 计数器（perfmon）> 猜测。本目录各章的「检查清单」都按此排序组织。

1. **先证伪资源瓶颈**：CPU/IO/内存是否有饱和证据（第 02–04 章）；
2. **再定位负载贡献者**：按总耗时的 top SQL（第 07 章 `sys.dm_exec_query_stats` 类聚合，见 https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-exec-query-stats-transact-sql ）；
3. **然后计划级分析**：估计 vs 实际行数、回归对比（第 08 章）；
4. **最后才谈维护动作**：索引/统计操作（第 05、06 章），避免「无差别重建」。

## 7. 常见误区（重构归纳）

1. 用「平均值」看延迟：等待的长尾才是故障源，需按百分位/最大拆；
2. 把等价的等待类型混为一谈：`PAGEIOLATCH_SH`（读盘）与 `PAGELATCH_SH`（缓冲池页闩）指向完全不同的层；
3. 忽略 NUMA/资源池维度：等待会「看起来」在 CPU，实为调度器饱和（⚠️ 转述）；
4. 只盯慢 SQL：高频快 SQL 的总消耗常大于低频慢 SQL——先看聚合再看极值；
5. 无基线时上生产重启实例：清掉了唯一现场证据。

## 8. 演练推演：一张「报表变慢」工单（重构示例，⚠️ 非原书案例）

1. T0 采集：确认实例 72 小时无重启（否则先补参照数据缺口）；
2. 等待差值 5 分钟窗口：`PAGEIOLATCH_SH` 占 46%，`SOS_SCHEDULER_YIELD` 8%——主象限 I/O，CPU 次要；
3. 按第 01 节流程归因：I/O 象限内查 `dm_io_virtual_file_stats` 分文件差分——延迟集中在单一用户文件而非日志/tempdb；
4. 交叉验证缓冲池：逐出速率升高 + 该表对象缓冲池占用被大扫描驱逐 → 转第 04 章决策树；
5. 结论候选：某新上线报表做大范围扫描（第 05/08 章计划归因），而非「存储坏了」；
6. 处方次序：修查询/加覆盖索引 → 错峰 → 最后才谈扩内存/换盘；
7. 复盘动作：把该场景的等待形态截图归档进参照数据库（下次同形态 30 秒定位）。

**推演暴露的方法论要点**：同一现象（慢）经由「象限→文件→缓冲池→计划」的证据链会走向完全不同的处方——流程的价值在**排除错误处方**，不只在找到正确的那个。

## 9. 版本与平台面注记（⚠️ 转述）

- 本书覆盖世代：SQL Server 2016/2017/2019 及 Azure SQL 为主（主题重构理解，章内已按此处理 IQP/Query Store 的「可用性差异」）；
- Linux 版：DMV/等待/Query Store/XEvent 全量可用，差异在文件路径、权限模型与 perfmon 替代（`sp_server_diagnostics`/Prometheus 导出）；
- Azure SQL DB：无实例级 OS 视野，等待与 DMV 仍在，资源上限由 DTU/vCore 治理——方法论不变、观测入口换壳；
- 与 #56（2012 内核）笔记联读时注意：Query Store 是 2016 产物，2012 世代的「历史计划」只能靠快照表土法。

**三句话记住本章**：
1. 慢 = 干活 + 排队，先分清再开药；
2. 没有基线的现场是案发现场，有基线的现场才是监控截图；
3. 证据层级决定处方置信度——从实际计划往下排，从猜测往上拒。

## 核心概念速览（中英对照）

- **排错方法论** — Troubleshooting methodology：以资源分类+等待差值+证据层级组织诊断流程的总纲 ⚠️
- **等待差值法** — Wait stats delta：两次 `sys.dm_os_wait_stats` 快照差分定位窗口内消耗 ⚠️
- **SQLOS** — SQL Server Operating System：调度器/内存节点/闩锁的 OS 抽象层 ⚠️
- **协作式调度** — Cooperative scheduling：任务自愿让出调度器时间片的模型 ⚠️
- **良性等待** — Benign waits：不代表问题的等待类型（如待机睡眠类） ⚠️
- **参照数据** — Reference data：健康期持续采集的基线快照 ⚠️
- **资源四象限** — CPU / Memory / I/O / Concurrency：症状归类框架 ⚠️
- **证据层级** — Evidence hierarchy：实际计划>等待>会话快照>计数器>猜测 ⚠️
- **busy_timeout** — SQLite busy timeout：🔧 本机类比「排队等待」的开关，**非 SQL Server 行为**
- **database is locked** — SQLITE_BUSY：🔧 实测阻塞报错，仅锚定「阻塞即等待」概念
- **页闩 vs 磁盘闩** — PAGELATCH vs PAGEIOLATCH：内存页保护 vs 读盘等待的分界 ⚠️
- **资源池** — Resource pool / NUMA node：调度与内存配额的分维度 ⚠️
- **First Responder Kit** — FRK：社区采集器脚本包，参照数据的现成实现（见第 10 章）

## 最新演进与工业实践

1. **2024–2026 版本面**：微软持续扩充 SQL Server/Linux 版性能故障排除文档体系，排错入口仍以等待统计+DMV 为骨架：[sys.dm_os_wait_stats 官方页](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-os-wait-stats-transact-sql)（✅ HEAD 200）。SQL Server 2025（docs `ver17`）新增的查询归档（Query Store 归档到 Azure）把「参照数据」从脚本自觉变成产品能力 ⚠️ 转述。
2. **工具面**：Brent Ozar 团队 [SQL-Server-First-Responder-Kit](https://github.com/BrentOzarULTD/SQL-Server-First-Responder-Kit)（✅ 200）已成为「等待差值法+基线」的事实标准开源实现；Adam Machanic 的 [sp_WhoIsActive](https://github.com/amachanic/sp_whoisactive)（✅ 200）承担现场快照层。
3. **研究面**：把「排队系统」思路做到极致的是自适应执行研究：Eddies（Avnur、Hellerstein，SIGMOD 2000，[DOI:10.1145/342009.335420](https://api.crossref.org/works/10.1145/342009.335420) ✅）按运行时反馈逐算子调度；现代自驾驶方向见 SIGMOD 2018 负载预测（Ma 等，[DOI:10.1145/3183713.3196908](https://api.crossref.org/works/10.1145/3183713.3196908) ✅）。
4. **跨引擎现状**：同类「等待/活动视图」观测面在 PostgreSQL（`pg_stat_activity`、`pg_stat_statements`）、DuckDB（逐算子 `EXPLAIN ANALYZE`，🔧 本机 T5 实验）均已普及——方法论跨引擎成立，视图名不通用。
