# 02 动态管理视图与等待统计（⚠️ 主题重构章）

> 章名非原书逐字章名（取证降级见 [00-总览与阅读地图](00-总览与阅读地图.md) 第二节）。本章重构本书观测工具箱的核心：DMV 体系与等待统计的读法。SQL Server 不可本机实测，全部 **⚠️ 转述**自微软官方文档（DMV 列名与语义以官方页为准，已做 HEAD 200 校验）；🔧 类比实验**非 SQL Server 行为**。

## 1. DMV 是什么、不是什么

⚠️ 转述：动态管理视图（Dynamic Management Views）是引擎内部状态的只读系统视图族（`sys.dm_*`），按域分组：执行（`dm_exec_*`）、会话/请求（`dm_os_*`、`dm_exec_sessions/requests`）、数据库/对象（`dm_db_*`）、IO（`dm_io_*`）。三条纪律：

1. **权限面**：`VIEW SERVER STATE` 才能看实例级 DMV（⚠️ 转述）；
2. **易失性**：多数内容重启即失——「先导出再分析」是铁律（第 01 章参照数据）；
3. **版本差异**：列集合随版本/CU 变化，文档化脚本必须容错（社区脚本普遍用动态 SQL 探测列存在性）。

## 2. 等待统计主表与三件套读法

⚠️ 转述：主表为 `sys.dm_os_wait_stats`（官方列：`wait_type`、`waiting_tasks_count`、`wait_time_ms`、`max_wait_time_ms`、`signal_wait_time_ms`），官方页 https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-os-wait-stats-transact-sql （✅ HEAD 200）。读法三件套：

- **等待时间 vs 信号时间**：`wait_time_ms` 是资源就绪前的等待，`signal_wait_time_ms` 是资源就绪后等 CPU 派发的时间——信号占比高指向 CPU 压力/调度器饱和（⚠️ 转述）；
- **总量 vs 单次**：`wait_time_ms / waiting_tasks_count` 高而总量低 = 高频小等待（如闩争用形态）；总量高而单次均值低 = 海量正常等待（先分类再看）；
- **max 的陷阱**：`max_wait_time_ms` 只说明最惨一次，不代表典型——要差值+分位。

标准查询形态（转述社区通用模板，非原书逐字）：

```sql
SELECT wait_type, waiting_tasks_count,
       wait_time_ms, signal_wait_time_ms,
       CAST(100.0 * wait_time_ms / SUM(wait_time_ms) OVER() AS decimal(5,2)) AS pct
FROM sys.dm_os_wait_stats
WHERE wait_type NOT IN ( /* 良性等待过滤表，FRK 内置 */ )
ORDER BY wait_time_ms DESC;
```

## 3. 当前正在发生的事：requests 与 sessions

⚠️ 转述：`sys.dm_exec_requests`（官方页 ✅ HEAD 200）是「此刻」的表：每活跃请求一行，含 `session_id`、`status`、`command`、`wait_type`、`wait_time`、`blocking_session_id`、`plan_handle`、`statement_*` 偏移。它回答「现在谁在干什么、卡在哪」；`sys.dm_exec_sessions` 给登录/主机/客户端维度；`sys.dm_exec_connections` 给网络层。**三表以 session_id 串联**是全部现场排错脚本的骨架（第 09、10 章反复使用）。

## 4. 聚合历史：query stats 一族

⚠️ 转述：`sys.dm_exec_query_stats`（官方页 ✅ HEAD 200）按计划缓存项累计 `execution_count`、`total_worker_time`、`total_elapsed_time`、`total_physical_writes` 等——「历史上哪类 SQL 消耗最大」的来源；配合 `sys.dm_exec_sql_text(plan_handle 派生)` / `sys.dm_exec_query_plan` 取文本与 XML 计划。注意：缓存被逐出则统计消失，这也是第 08 章 Query Store 存在的理由。

## 5. 等待类型地图（按第 01 章四象限归位）

⚠️ 转述（类别学名以官方文档为准）：

| 象限 | 代表等待 | 一句话病理 |
|---|---|---|
| I/O | `PAGEIOLATCH_*`、`WRITELOG`、`IO_COMPLETION` | 缓冲池未命中需读盘/日志落盘慢 |
| 内存 | `RESOURCE_SEMAPHORE`、`MEMORY_ALLOCATION_EXT`、`CMEMTHREAD` | 授予/内存对象分配排队 |
| CPU | `SOS_SCHEDULER_YIELD` | 时间片让出后再排队（量>阈值时） |
| 并发 | `LCK_M_*`、`PAGELATCH_*`、`LATCH_EX` | 锁/闩串行化点 |
| 跨界 | `CXPACKET`/`CXCONSUMER` | 并行交换——既可能是并行等待也可能是并行供数 |

**`CXPACKET` 反直觉读法** ⚠️ 转述：高 `CXPACKET` 不等于「并行是错的」——并行线程在等对方供数时也在计时。先问「为什么需要并行」（行数/统计，第 06 章），再谈砍 DOP。

## 6. 🔧 类比实验组（**非 SQL Server 行为**，仅锚定概念）

1. **累计计数器差分** 🔧：等待统计≈对单调计数器做区间差分。本机 SQLite 无等待视图，但 DuckDB 的 `EXPLAIN ANALYZE` 输出实测计划树（本机实测：`SELECT cat,count(*) FROM f WHERE id>1000 GROUP BY cat` 得到含 `PERFECT_HASH_GROUP_BY` 的算子树并带逐算子 time/rows）——「用运行时数据而非猜测读执行」与 DMV 同一认识论，语义不可平移。
2. **会话级「此刻」视图类比** 🔧：SQLite 单写者模型下，用两连接复现「谁挡了谁」：A `BEGIN EXCLUSIVE` 持写锁，B 写同库——B 实测阻塞 ~659ms 后报 `database is locked`（`busy_timeout=200`）。SQL Server 中同一局面表现为 `dm_exec_requests.blocking_session_id` 指向 A，且 B 的等待类型是 `LCK_M_...`——本实验只给「阻塞可观测」的直觉。
3. **信号等待类比** 🔧：「资源就绪后等 CPU」在 SQLite/DuckDB 无对应物（无调度器 DMV 层），故本书该概念只用 ⚠️ 转述，不做类比——诚实登记类比边界。
4. **权限面类比** 🔧：SQLite 无 `VIEW SERVER STATE` 层级；最接近的是 DuckDB 只读模式限制系统表写入。仅说明「观测面也有权限面」这一通用设计。

## 8. 检查清单（重构）

1. 采集前确认是否重启过（`sys.dm_os_uptime` 类信息）；
2. 先过滤良性等待再看排名；
3. 对榜首等待回官方文档查「这个等待意味着什么资源」，不查「网上说怎么修」；
4. 差值窗口覆盖一次完整业务波峰；
5. 把 signal/wait 比例、调度器 `runnable_tasks`（⚠️ 转述自 `sys.dm_os_schedulers`）作为 CPU 象限的交叉验证；
6. 保存查询结果快照（含采集时间戳），进入第 01 章参照数据库。

## 9. 三个现场场景（重构示例，⚠️ 非原书案例）

**场景 A｜「夜间批处理后白天变慢」**
1. 差分窗口取「白天高峰」而非全天——夜间备份/作业把累计值污染殆尽；
2. 窗口榜首 `WRITELOG` + `IO_COMPLETION` → 提交形态问题（03 章），不是索引问题；
3. 若榜首是 `PAGELATCH_EX` 且集中在 tempdb → 版本存储/分配热点（03 章 4 节）。

**场景 B｜「CPU 90% 但没慢查询」**
1. signal 占比 >40% + `SOS_SCHEDULER_YIELD` 高 → 调度饱和；
2. 查 `dm_exec_query_stats` 的 `total_worker_time` 排行——通常指向编译风暴（07 章）或标量 UDF 逐行消耗；
3. 资源治理器/最大 DOP 是止痛，重写出编译循环才是治。

**场景 C｜「等待榜首是 ASYNC_NETWORK_IO」**
1. 语义：引擎算完了在等客户端收——**病灶在应用侧**（逐行读取、网格渲染）；
2. 数据库调优动作几乎全部无效，处方是客户端批量化/投影瘦身；
3. 这是「等待类型→资源」映射表中「非引擎资源」类的代表，登记进白名单外但单独归类。

## 10. 读数纪律补充（⚠️ 转述）

- `waiting_tasks_count` 与 `wait_time_ms` 联立看：前者是次数不是时长，海量短等待可能是正常态；
- 采样间隔内如有统计作业/索引维护/重启，窗口作废重采；
- 多 NUMA 实例把 `dm_os_schedulers` 的负载倾斜作为等待数据的前置检查；
- 把「榜首等待」写进工单时必须同时写采集时间窗与过滤表版本，否则同事无法复现你的结论。

## 核心概念速览（中英对照）

- **动态管理视图** — DMV (`sys.dm_*`)：引擎状态只读视图族 ⚠️
- **等待类型** — Wait type：等待归类的枚举键（`PAGEIOLATCH_SH`、`LCK_M_X` 等） ⚠️
- **信号等待** — Signal wait：资源就绪后等 CPU 派发的时间 ⚠️
- **良性等待** — Benign wait：不代表问题的等待，须过滤 ⚠️
- **差值采样** — Delta sampling：对累计 DMV 两次快照相减 ⚠️
- **dm_exec_requests** — 当前请求视图：此刻谁在等什么 ⚠️
- **dm_exec_query_stats** — 计划聚合统计：历史消耗排行 ⚠️
- **plan_handle** — 计划句柄：连接统计/文本/XML 的钥匙 ⚠️
- **CXPACKET** — 并行交换等待：读前须区分供数与饥饿 ⚠️
- **RESOURCE_SEMAPHORE** — 内存授予排队等待：查询内存不足信号 ⚠️
- **VIEW SERVER STATE** — 服务器状态查看权限：观测面权限门槛 ⚠️
- **EXPLAIN ANALYZE** — DuckDB 🔧 逐算子实测计划：观测同认识论，**非 SQL Server 行为**
- **database is locked** — SQLite 🔧 阻塞报错：阻塞可观测性锚点，**非 SQL Server 行为**

## 最新演进与工业实践

1. **官方文档面**（✅ HEAD 200）：等待统计与 requests/query stats 的权威列表持续在 learn.microsoft 维护：[sys.dm_os_wait_stats](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-os-wait-stats-transact-sql)、[sys.dm_exec_requests](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-exec-requests-transact-sql)、[sys.dm_exec_query_stats](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-exec-query-stats-transact-sql)。
2. **等待统计的工业化**：2024–2026 社区事实标准仍是 FRK 的 `sp_BlitzFirst`（实时等待诊断）与 [sp_WhoIsActive](https://github.com/amachanic/sp_whoisactive)（现场快照），两者均活跃维护（✅ HEAD 200）；Erin Stellato 等作者的性能主题持续再版/更新课程化。
3. **智能查询处理的影响** ⚠️ 转述：2019 起的 IQP 系列（批处理模式内存授予反馈、表变量延迟编译等）改变了部分等待形态的解读——`RESOURCE_SEMAPHORE` 类等待在反馈机制下可能自我修正，观察窗口要拉长。
4. **研究线**：等待/排队视角的自动化演进为负载感知调度与自驾驶 DBMS：MB2（Marcus 等，SIGMOD 2021，[DOI:10.1145/3448016.3457276](https://api.crossref.org/works/10.1145/3448016.3457276) ✅）用行为分解模型预测引擎配置效果——与本书「先分类再深挖」同构，只是把决策交给了模型。
