# 09 阻塞、死锁与并发故障排除（⚠️ 主题重构章）

> 章名非原书逐字章名（取证降级见 [00-总览与阅读地图](00-总览与阅读地图.md) 第二节）。本章重构「锁/阻塞/死锁」主题：锁与闩的分野、阻塞链取证、死锁图读法、隔离级别与行版本的代价。机制深版对照 [Pro SQL Server Internals/12](../Pro_SQL_Server_Internals/12-锁类型阻塞与死锁.md)。全部 **⚠️ 转述**；🔧 **非 SQL Server 行为**。

## 1. 先分清：锁等待 vs 闩等待

⚠️ 转述：

- **锁（lock）**：逻辑一致性原语，保护「数据内容」，等待表现为 `LCK_M_S/U/X/IX…`，可被死锁监视器选中牺牲者；
- **闩（latch）**：物理结构原语，保护「页/树节点」的瞬时修改，等待是 `PAGELATCH_*`/`PAGEIOLATCH_*`，**不进锁死锁检测**（闩序由引擎内部保证，第三方无法「造成」闩死锁 ⚠️ 转述）。

症状都叫「卡住」，处方完全不同：锁→改事务/索引/隔离；闩→热点页/分配结构/并行形态（03/04/05 章回流）。

## 2. 阻塞链取证：谁在堵、堵了谁

⚠️ 转述核心视图：`sys.dm_exec_requests.blocking_session_id`/`blocking_transaction_id`（官方页 ✅ HEAD 200：https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-exec-requests-transact-sql ）、`sys.dm_tran_locks`（持有/请求的锁资源明细）、`sys.dm_os_waiting_tasks`（跨请求的等待边）。现场要点：

1. **链头往往不是凶手**：链头是「正在慢慢干活的事务」——抓它的语句+计划+开始时间才知道为什么持锁久；
2. **head_blocker 与睡眠者**：链头会话 `status=sleeping` 且 `open_transaction_count>0` ——应用「开事务不提交」（连接池忘 rollback/异常分支漏提交）是工业头号形态，锁只是它的影子；
3. **粒度放大**：行锁升级为表锁（⚠️ 转述 `sys.dm_exe...p_lock_promotion` 统计视图族）常由缺索引的大范围 UPDATE 触发——修 WHERE 的选择性而非直接加跟踪标志压制。

工具层：Adam Machanic 的 sp_WhoIsActive（✅ [GitHub](https://github.com/amachanic/sp_whoisactive)）一条命令给出「阻塞树+命令文本+等待」——即本节全部 DMV 的脚本化封装（第 10 章）。

## 3. 死锁：读图三步

⚠️ 转述：死锁快照来自 system_health 会话的 `xml_deadlock_report`（第 10 章展开）或专用捕获。读图：

1. 两个 `process-list` 节点各自的输入语句、持有/请求模式；
2. `resource-list` 中互相环路锁对象（键/页/RID）；
3. `victim-list` 谁被牺牲（优先级/成本）。

经典病理与处方（⚠️ 转述）：**异序访问**→统一访问顺序；**范围锁重叠**（SERIALIZABLE 的 KEY-RANGE）→降隔离级别+行版本；**索引不同导致锁序不同**→对齐索引使两查询同路径；**批删除撞单行更新**→小批次+让路提示（`READPAST`/`NOWAIT` 场景化使用）。死锁是并发正确性的固有代价——目标是「低频+可自愈+有告警可查」，不是清零。

## 4. 隔离级别与行版本的隐性账单

⚠️ 转述：`READ_COMMITTED_SNAPSHOT`（RCSI）把读锁换成版本读——阻塞少了，但账挪到：tempdb 版本存储（第 03 章）+ 最长事务年龄 + `version_cleanup_rate`。排错时「开了快照隔离反而更慢」九成在这三处。`SNAPSHOT` 隔离另有更新冲突回滚（error 3960 族 ⚠️ 转述）。2022 的 resilient database（镜像/AG 故障切换与锁定语义增强 ⚠️ 转述）：属高可用面，本书主线仅在 03 章 tempdb 容量模型处呼应。

## 5. 预防性设计清单（⚠️ 转述+重构）

1. 事务最短化：把用户交互/网络调用挪出事务；
2. 索引覆盖写路径：让 UPDATE 精确锁到的行集=其语义行集；
3. 热点计数表改「多行分桶+聚合读」或队列化，避免单页 `PAGELATCH_EX` 串行（Dmitri Korotkevitch 公开写作中反复演示的热键模式 ⚠️ 转述）；
4. 锁超时与重试策略在应用层成文（`LOCK_TIMEOUT` 有值且被处理）；
5. 大批量操作错峰+分页提交。

## 6. 🔧 类比实验（**非 SQL Server 行为**）

1. **T2 阻塞链单跳** 🔧（本机 SQLite）：A `BEGIN EXCLUSIVE` 持写锁；B `PRAGMA busy_timeout=200` 下写→实测 **~659ms 后 `database is locked`**（busy handler 离散步进退避，超时是「至少」语义）；A 提交后 B **2.8ms** 完成。「链头在慢慢干活→尾端超时报错」的形态可见，但 SQLite 是库级独占锁——粒度远粗于 SQL Server 行锁，**不可平移**。
2. **死锁环类比** 🔧：SQLite 无锁管理器故无死锁；两进程文件锁互等属于 OS 层。用「两连接先各自 `BEGIN IMMEDIATE` 抢写权」只能复现**先到先得**而非环——反衬 SQL Server 死锁监视器的必要性来自锁粒度细到行/键。
3. **闩类比登记** 🔧：SQLite/DuckDB 无 latch 观测面——本章第 1 节的闩/锁分野纯 ⚠️ 转述，无锚点，诚实标注。
4. **版本存储类比** 🔧：SQLite WAL 模式下长读事务阻止 WAL 截断、WAL 文件膨胀（`PRAGMA journal_mode=WAL` 下可观察 -wal 体积随长读会话增长）——与「长事务钉住 tempdb 版本链」同构：清理被最慢消费者卡住。**语义不同，直觉同**。

## 9. 死锁病理分类台账（⚠️ 转述社区经验学）

| 病理 | 图面特征 | 处方 |
|---|---|---|
| 异序访问 | 两 proc 互等对方已持的表/对象 | 统一对象访问顺序（代码评审级） |
| 索引路径差异 | 同表两查询锁**不同键**（各走不同索引） | 对齐索引使二者同路径；或覆盖索引收敛 |
| 范围锁重叠 | SERIALIZABLE/RANGE 键锁互咬 | 降隔离+RCSI；缩小谓词范围 |
| 批撞单行 | 大批量 X 锁页/表撞 OL 点更 | 分页小批+`READPAST`（可跳过语义先评审） |
| 转换死锁（Convert） | 模式转换（U→X）互等，常见同页多更新 | 键散列/分区减密；重试策略兜底 |
| Schema 锁环 | `Sch-M` 撞长查询的 `Sch-S` | DDL 错峰+`LOCK_TIMEOUT`+`WAIT_AT_LOW_PRIORITY`（2014+ 联机操作选项 ⚠️ 转述） |

台账用法：按周统计各类占比，**治前两类**（设计问题，可根除）；后四类多数接受「低频+自愈+告警」的运行态——清零是伪目标。

## 10. 场景演练（重构示例，⚠️ 非原书案例）

**场景 A｜「每天 09:00 报表拖死 OLTP」**
1. sp_WhoIsActive 抓树：链头是 3 分钟大报表（`SELECT` 持 `S` 锁于聚簇索引范围）；
2. 库开了 RCSI 但报表在 `SNAPSHOT` 之外跑（默认 READ COMMITTED 仍拿共享锁）→ 会话级 `SET TRANSACTION ISOLATION LEVEL SNAPSHOT` 或确认 RCSI 覆盖；
3. 长期：报表走只读副本/延迟备份副本（#36/16 章高可用面）。

**场景 B｜「应用连接池耗尽但服务器空闲」**
1. 表象在应用，根因在阻塞：链尾全部 `LCK_M_...` 等待且链头睡眠持事务（第 2 节 head blocker）；
2. `login/domain` 维度聚合 `dm_exec_sessions` 定位肇事应用模块；
3. 处方在代码：事务边界+异常路径 rollback；DB 端 `LOCK_TIMEOUT` 只是止损阀。

**场景 C｜「死锁频发但都秒级自愈」**
1. 台账分类（第 9 节）显示 80% 是「索引路径差异」型：两条 UPDATE 各走各的非聚簇索引锁键；
2. 根除样本：给其中一条补齐索引使两者同路径——一周后该类清零；
3. 剩余「转换死锁」低频项：登记接受，应用统一重试一次。

**链尾视角补注**（⚠️ 转述）：
- 阻塞排序按「链深×被阻塞会话数」而非单链最长——受害者数量才是业务口径；
- 配了 XEvent `blocking_process_clustered` 阈值捕获（10 章）后可回放「谁堵了 5 秒以上」历史清单，与死锁台账分表管理。

## 核心概念速览（中英对照）

- **阻塞链** — Blocking chain：会话互等锁的有向链，链头常为「慢活者」 ⚠️
- **锁升级** — Lock escalation：行锁聚表锁的粒度跳变 ⚠️
- **head blocker** — 链头会话：睡眠持事务是头号工业形态 ⚠️
- **死锁图** — Deadlock graph/xml_deadlock_report：环路与牺牲者的取证文档 ⚠️
- **牺牲者** — Deadlock victim：优先级/成本判定后被回滚方 ⚠️
- **RCSI** — READ_COMMITTED_SNAPSHOT：读换版本、无读锁的库级开关 ⚠️
- **版本存储** — Version store：tempdb 中的行版本链，长事务钉住 ⚠️
- **PAGELATCH_EX 热点** — 热页闩争用：单页高并发写的串行化 ⚠️（🔧 无对应物）
- **latch vs lock** — 闩 vs 锁：物理结构 vs 逻辑一致性原语 ⚠️
- **READPAST/NOWAIT** — 让路提示：跳过被锁资源的选项族 ⚠️
- **busy_timeout / database is locked** — SQLite 🔧 阻塞等待与报错：单跳链直觉，**非 SQL Server 行为**
- **WAL 截断受阻** — SQLite 🔧 长读钉日志：版本清理同构直觉，**非 SQL Server 行为**

## 最新演进与工业实践

1. **捕获面现代化（⚠️ 转述）**：SQL Trace 时代的 `sp_lock`/`fn_get_sql` 组合彻底退役；现行为 XEvent `lock_acquired/blocking 系事件` + system_health 死锁图 + Query Store 并发画像三线并行（第 08/10 章）。
2. **工具现状**：[sp_WhoIsActive](https://github.com/amachanic/sp_whoisactive)（✅）与 [First Responder Kit](https://github.com/BrentOzarULTD/SQL-Server-First-Responder-Kit)（✅）仍是阻塞取证默认件；Erin Stellato 等社区作者持续维护死锁分析报表脚本（⚠️ 转述）。
3. **引擎侧** ⚠️ 转述：2019+ 对内存优化表使用乐观/闩结构差异、2022 RDE 对高可用读锁语义的改进，均要求排错时先确认对象类型与 HA 拓扑再套本章结论；2025 的 vector/JSON 新数据类型暂不改变锁模型主线。
4. **跨引擎 🔧**：PostgreSQL 的 `pg_stat_activity`+`deadlock_timeout` 观测、SQLite `busy_timeout` 实验（本机复现）——「阻塞=等待+可归因」成为各引擎通用语言；SQL Server 的行级锁+监视器复杂度仍是最高档（非 SQL Server 行为类比止于此）。
