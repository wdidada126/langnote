# 04 内存架构与内存压力排错（⚠️ 主题重构章）

> 章名非原书逐字章名（取证降级见 [00-总览与阅读地图](00-总览与阅读地图.md) 第二节）。本章重构「CPU/内存负载」主题中的内存半区：缓冲池、查询内存授予、内存压力信号及其在等待与 DMV 上的投影。全部 **⚠️ 转述**自微软文档与内核系教材；🔧 类比**非 SQL Server 行为**。

## 1. 三层内存格局（排错所需最小模型）

⚠️ 转述：
1. **进程层**：max server memory 上限下的整体提交；min server memory 保底；
2. **SQLOS 层**：内存节点（NUMA 对齐）、内存对象与 clerk type（`MEMORYCLERK_*`）记账；
3. **引擎层**：缓冲池（数据页缓存）+ 查询执行内存（排序/哈希授予）+ 计划缓存（Store 类）。

对应观测：`sys.dm_os_memory_clerks`（各 clerk 占用）、`sys.dm_os_process_memory`（总用量与页面生命周期）、`sys.dm_os_buffer_descriptors`（缓冲池里每页归属，可按库聚合出「谁 Cache 了多少」）（⚠️ 转述的视图族；列名以官方为准）。

## 2. 缓冲池与物理读的关系

⚠️ 转述：缓冲池命中率高→物理读少；「内存不足」在 SQL Server 上**很少表现为报错，而表现为 `PAGEIOLATCH_*` 等待上升**——OS 层可能毫无内存告警（引擎把 OS 可用内存吸干是设计行为）。排错动作：
1. 用 `sys.dm_os_buffer_descriptors` 分库/分对象看占用构成；
2. 对「理应常驻却反复被逐出」的热对象，检查大表全扫（把热页挤出）与备份/大批量作业的扫描策略（⚠️ 转述：资源治理或错峰比加内存常更对症）；
3. 需要更大缓冲池时，先核对 max server memory 是否被人为压低、或 OS 侧真有压力（与 DBA 协作的边界证据）。

扩展缓冲池（EBS，用 SSD 做二级缓存）已随新版弃用的教训 ⚠️ 转述：官方页 https://learn.microsoft.com/en-us/sql/database-engine/configure-windows/buffer-pool-extension （✅ HEAD 200，页面即标注不适用新版本）——历史上「上 EBS 救内存」的偏方在今天应解读为「扩 RAM 或治理扫描」。

## 3. PLE：从圣杯到降权

⚠️ 转述：Page Life Expectancy（缓冲页平均驻留秒数，`sys.dm_os_performance_counters` 中 Buffer Manager 对象）曾被当作内存健康第一指标。2019+ 社区共识（Brent Ozar 等持续撰文）：PLE 受扫描驱逐、NUMA 拆分、备份读等多因素扰动，**单一阈值（如 300 秒）判决已不可靠**——应与 free page/free list 扫描速率、`PAGEIOLATCH` 差分、逐出速率联立。这是本书方法论在 2024–2026 的重要校准点。

## 4. 查询内存授予（grant）与 RESOURCE_SEMAPHORE

⚠️ 转述：行模式查询执行前按估计行数申请内存授予；不足则排队等待 `RESOURCE_SEMAPHORE`，单查询可配 `RESOURCE_SEMAPHORE_QUERY_COMPILE`（编译内存）。两个高频病理：

1. **授予等待**：多数根因是**基数估计错误**（第 06 章）导致授予过大——修统计/修计划优于加内存；
2. **授予不足→spill**：排序/哈希落 tempdb（第 03 章关联），计划 XML 中显示 `NoFreeMem`/physical IO 出现在 Sort/Hash 算子（⚠️ 转述）。

**反馈机制的时代变化** ⚠️ 转述：2019 起 IQP 提供批处理模式内存授予反馈（Memory Grant Feedback），行模式下授予问题多被自动纠偏——排错时注意「等待统计里 semaphore 消失」可能不是治好了，是反馈在掩盖上游 CE 问题；Query Store 里的 spill 计数仍值得盯。

## 5. 计划缓存的内存面

⚠️ 转述：计划缓存是一个 Store（`CACHESTORE_SQLCP`/`OBJSTORE` 等 clerk）——单查询即弃（ad-hoc）风暴会把它撑满并驱逐别的组件；解法是 `optimize for ad hoc workloads` 与参数化（第 07 章），而不是无限加内存。检查：clerk 排名 + `sys.dm_exec_cached_plans` 按 usecounts=1 的占比（⚠️ 转述）。

## 6. 内存排错的决策树（重构）

```
PAGEIOLATCH 上升？
├─ 是 → 缓冲池被驱逐？（扫描作业/容量不足）→ 治理扫描 / 扩内存
│        └─ 否 → 存储本身慢（第 03 章）
└─ 否 → RESOURCE_SEMAPHORE？
         ├─ 是 → 授予异常者=CE 错误者（第 06/08 章）→ 修统计/修计划
         └─ 否 → clerk 异常者（Clerk 泄漏 vs 缓存膨胀）→ 组件级定位
                  └─ 都不显著 → 回到 CPU/并发象限（02/09）
```

🔧 **类比实验（非 SQL Server 行为）**：SQLite/DuckDB 均无缓冲池 DMV；最接近的直觉是 DuckDB 溢出行为——排序/哈希超 `memory_limit` 时落盘 temp 目录（`PRAGMA temp_directory`），可复现「授予不足→spill 变慢而非报错」的形态；SQLite 的 `PRAGMA cache_size` 调页数则演示「池大小→物理读次数」的关系。二者语义与 SQL Server 的授予模型不同，只作方向锚。

## 8. 检查清单（重构）

1. `sys.dm_os_memory_clerks` top-10 与历史基线比（差分，不做绝对值判决）；
2. PLE 与逐出/免费页速率联立，不单独报警；
3. semaphore 等待者→取其计划与估计/实际行数差（喂给第 06/08 章）；
4. tempdb spill 计数进入巡检表；
5. ad-hoc 占比>阈值时启用 `optimize for ad hoc workloads`（⚠️ 转述：配置项，需重启生效面很小）；
6. 云/容器化实例注意「容器内存上限≠max server memory」的换算（⚠️ 转述）。

## 9. 三个现场场景（重构示例，⚠️ 非原书案例）

**场景 A｜「加了 128G 内存，PAGEIOLATCH 没降」**
1. 检查 max server memory：默认上限会吸走新内存，缓冲池理应扩大——没变说明限制在别处（容器/cgroup、min/max 配置）；
2. 缓冲池扩大后命中率仍未升 → 工作负载本就以扫描为主（每查新页），加内存无效；
3. 回到 05/08 章做计划归因：内存处方必须等扫描治理之后评估。

**场景 B｜「RESOURCE_SEMAPHORE 高峰排队，查询全挂起」**
1. 抓 semaphore 等待者的 `task_memory_grants`：授予大小与 `wait_time` 排序（⚠️ 转述）；
2. 榜首多为「估计 10 行、实际 100 万行」的 CE 受害者（06 章）——授予被放大万倍；
3. 短期：对该语句 `MAX_GRANT_PERCENT` 限流；长期：修统计/改写，反馈机制（2019+）可能已自动纠正，先确认兼容性级别。

**场景 C｜「clerk 排名里 USERSTORE_SCHEMAMGR 异常膨胀」**
1. 模式缓存 store 膨胀常伴随海量单用计划/超宽 ad-hoc 负载（07 章缓存病理联动）；
2. 先排除内存泄漏判据：是否随负载周期涨落（组件记账 vs 真泄漏）；
3. 真异常样本收集后走微软支持路径——clerk 内部结构不是 DBA 侧可修对象（⚠️ 转述边界）。

## 10. 观测面补充（⚠️ 转述）

- `sys.dm_os_performance_counters` 里 Buffer Manager/Paging 等计数器实例与 NUMA 拆分（`_NODE01` 后缀）联读，否则均值掩盖单节点饥饿；
- 计划缓存驱逐与 QDS（Query Store）留档互补：内存压力会先牺牲缓存，QDS 是唯一幸存者（08 章）；
- 大页（lock pages in memory / AWE）在 Windows/Linux 的落地差异影响「内存被 OS 换出」类事故的形态；
- 内存排错的最后防线是**基线**：clerk 快照、PLE 曲线、授予等待计数都要有「上周正常时」可比。

**clerk 速查小表**（⚠️ 转述类别学，名称以 `sys.dm_os_memory_clerks` 实况为准）：

| clerk 族 | 住在这里的东西 | 异常时先想什么 |
|---|---|---|
| `MEMORYCLERK_SQLBUFFERPOOL` | 缓冲池本体 | 与 max server memory 配置对账 |
| `MEMORYCLERK_SQLQUERYCOMPILE` | 编译workspace | 编译风暴（07 章） |
| `MEMORYCLERK_SQLUTILITIES` | 备份/DBCC 缓冲 | 维护作业并发度 |
| `USERSTORE_OBJPERF/SCHEMAMGR` | 计划/元数据缓存 | ad-hoc 膨胀、对象数爆炸 |
| `MEMORYCLERK_SOSMEMMANAGER` | SQLOS 结构页 | 对象数/线程数异常增长 |

**读数纪律**：clerk 绝对值无意义（引擎按需扩张），只有「同窗差分+历史分位」两轴同时异常才立案；跨 NUMA 节点时先按 `memory_node_id` 拆开再看。

## 核心概念速览（中英对照）

- **缓冲池** — Buffer pool：8KB 页缓存，物理读总闸 ⚠️
- **内存 clerk** — Memory clerk：SQLOS 按组件记账的内存归属单元 ⚠️
- **max server memory** — 服务器内存上限：引擎自我克制线 ⚠️
- **PLE** — Page Life Expectancy：页平均驻留秒数，2019+ 已降权为参考项 ⚠️
- **授予等待** — RESOURCE_SEMAPHORE：执行内存排队信号 ⚠️
- **内存授予** — Memory grant：按估计行数预批的执行内存 ⚠️
- **spill** — 溢出：授予不足把排序/哈希写去 tempdb ⚠️
- **内存授予反馈** — Memory Grant Feedback：IQP 的批处理授予自纠偏 ⚠️
- **计划缓存** — Plan cache：Store 型内存区，ad-hoc 风暴的受害者 ⚠️
- **EBS** — Extended Buffer Pool：已弃用的 SSD 二级缓存偏方 ⚠️
- **cache_size / temp_directory** — SQLite/DuckDB 🔧 池大小与溢出目录：方向锚点，**非 SQL Server 行为**

## 最新演进与工业实践

1. **PLE 降权成为定论**：2024–2026 社区脚本（[First Responder Kit](https://github.com/BrentOzarULTD/SQL-Server-First-Responder-Kit) ✅ HEAD 200）的告警逻辑不再以 PLE 单指标触发内存告警——本书第 3 节的校准已工具化。
2. **IQP 覆盖扩大** ⚠️ 转述：SQL Server 2022→2025 的内存授予反馈扩展到部分行模式场景、并引入更细的授予诊断（`sys.dm_exec_query_memory_grants` 仍是底料）；排错时先确认兼容性级别，再解读等待形态。
3. **容器与云边界**：Azure SQL 托管实例/K8s 部署下内存配额换算进入 DBA 视野（⚠️ 转述自微软配置文档域）。
4. **🔧 类比现状**：DuckDB 的 `memory_limit`+spill 可观测性（`PRAGMA database_list`/temp 目录体积）为「授予-溢出」提供了本机可复现的极简版——仍**非 SQL Server 行为**。
