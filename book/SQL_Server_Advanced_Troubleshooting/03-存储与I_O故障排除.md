# 03 存储与 I/O 故障排除（⚠️ 主题重构章）

> 章名非原书逐字章名（取证降级见 [00-总览与阅读地图](00-总览与阅读地图.md) 第二节）。本章重构「磁盘子系统与存储调优」主题：I/O 栈如何反映到等待与 DMV、tempdb 争用、文件与自动增长的排错动作。全部 **⚠️ 转述**；🔧 实验**非 SQL Server 行为**。

## 1. SQL Server 的 I/O 栈（排错视角）

⚠️ 转述：读写请求自上而下经过：存储引擎（页粒度 8KB）→ 缓冲池（命中则不下盘）→ SQLOS 异步 I/O 层 → OS/驱动 → 存储阵列/云盘。排错要区分三种慢：

1. **逻辑读多**：计划/索引问题（第 05–08 章），盘不慢也慢；
2. **物理读多**：缓冲池装不下工作集（第 04 章）或冷启动/驱逐；
3. **每 IO 延迟高**：真存储问题——看 `sys.dm_io_virtual_file_stats` 的 stall/读写字节比（⚠️ 转述：`io_stall_read_ms` 等累计列，官方域文档）与等待 `PAGEIOLATCH_SH`（读盘）/`WRITELOG`（日志提交）。

三者的处方完全不同——这是第 01 章「先分类再深挖」在 I/O 象限的落地。

## 2. 日志 I/O：WRITELOG 与事务形态

⚠️ 转述：提交必须等日志落盘（WAL）。`WRITELOG` 高说明提交频率×日志量超过存储吞吐；对应动作在**工作负载侧**更有效：合并小事务、加大批次、检查日志文件所在盘是否与其他文件争带宽。日志与恢复机制的内核细节见 [SQL_Server_2012_Internals/03-日志与恢复](../SQL_Server_2012_Internals/03-日志与恢复.md)。

## 3. 文件组、自动增长与「预排错」

⚠️ 转述：数据文件自动增长是同步操作——增长瞬间的写请求被卡住，表现为等待尖峰。排错动作：

- 大表文件用**固定大小预配**，增长只作兜底且步长别用默认百分比；
- 监控文件用量趋势，容量告警先于症状；
- 同一逻辑库的多文件布局关注比例填充（proportional fill，⚠️ 转述：文件分配按空闲空间比例）——不均等文件尺寸会制造隐性热点。

## 4. tempdb：全实例共用的风暴眼

⚠️ 转述：tempdb 承载排序/哈希溢出、游标、行版本（快照隔离/`READ_COMMITTED_SNAPSHOT`）、临时表、在线操作中间状态。三大故障形态：

1. **页分配争用**：SGAM/PFS 闩（等待名含 `PAGELATCH_*`，对象为 tempdb 内页）——历史上以「每 CPU 核一个临时文件（≤8）」缓解（社区通行做法，⚠️ 转述；新版本内存优化 tempdb 元数据页后大幅弱化此规则）；
2. **版本存储膨胀**：长事务钉住版本链，`tempdb` 暴涨且清理线程（version store GC）无法推进——先找「谁开了长事务未提交」（第 09 章 `dm_tran_active_transactions` 域，⚠️ 转述）；
3. **磁盘配置问题**：tempdb 与用户库同盘同队列，用户 I/O 淹没排序溢出。

对应章内检查：tempdb 使用率、版本存储大小、最长未提交事务年龄（⚠️ 转述的三类查询）。

## 5. 读放大与预读

⚠️ 转述：顺序访问触发整 extents 预读；坏计划（大表全扫）会把预读变成 I/O 洪水——等待上可见 `PAGEIOLATCH_SH` 的 `waiting_tasks_count` 暴涨但行数消耗集中在个别查询。处方常在执行层不在存储层：回到第 05/08 章。

🔧 **概念锚（非 SQL Server 行为）**：「读放大」在 SQLite 上可直接测：本机创建 3 万行表（`page_count`=1585），删除 90% 行后文件仍是 **1585 页**、`freelist_count`=**1385**（空间进空闲链未归还 OS）；`VACUUM` 后降到 **160 页**。SQL Server 语义不同（页复用策略、无 VACUUM 同物），但「逻辑行数下降≠物理读压力下降」的直觉一致——这正是索引膨胀章（05）要处理的错配。

🔧 **另一锚点**：DuckDB 的 `EXPLAIN ANALYZE` 实测显示逐算子 rows——扫多少行是读放大的第一证据；SQL Server 对应物是实际执行计划的 row leaks（估计 vs 实际）。

## 6. 存储排错的度量学

⚠️ 转述：三个不可省的指标——IOPS、吞吐（MB/s）、**延迟（ms，且按分位）**。阵列级指标（perfmon/存储侧）与实例级指标（`dm_io_virtual_file_stats` 差分）要联立：实例看到某文件平均读延迟 80ms 而存储侧报 5ms，差异层（虚拟化/驱动/队列深度）才是病灶。

## 8. 检查清单（重构）

1. 按文件差分 `dm_io_virtual_file_stats`：读写延迟分表排名，找异常单文件；
2. `WRITELOG` 高→画提交速率曲线，不做「换更快的盘」的第一反应；
3. tempdb 暴涨→先查事务年龄与版本存储，再查磁盘；
4. 自动增长事件抓取（⚠️ 转述：默认跟踪/错误日志/扩展事件均可记）→ 对大文件改预配；
5. 全扫洪水→转第 05/08 章做计划归因；
6. 云盘（Azure 托管盘）注意分层限速：单文件 IOPS 上限会把「阵列很快」的直觉打掉（⚠️ 转述）。

## 9. 三个现场场景（重构示例，⚠️ 非原书案例）

**场景 A｜「扩容后更慢」**
1. 现象：加盘/换云盘层级后高峰期 `PAGEIOLATCH_SH` 反升；
2. 排查：按文件差分延迟排名——热点仍在旧文件（数据未重分布，文件组内比例填充偏置）；
3. 处方：把大表迁移/重建到新文件，而不是继续加盘。

**场景 B｜「tempdb 撑爆磁盘，业务全部报错」**
1. 顺序：先 `dm_tran_active_transactions` 找最长事务年龄（09 章联动），看版本存储占比；
2. 若是版本链：杀死/重启罪魁会话比清 tempdb 有效（⚠️ 转述：版本清理要等最老事务结束）；
3. 若是排序溢出/临时对象：抓当窗 top 计划的 spills（Query Store，08 章）归因到 SQL；
4. 事后：tempdb 预配多文件+独立卷（遗留习惯在新版本仍无害，作为卫生项保留）。

**场景 C｜「整点必卡 90 秒」**
1. 等待窗口固定 → 高度怀疑周期性作业：增长事件（错误日志/默认跟踪）、备份开始时刻、统计更新作业；
2. `WRITELOG`+`IO_COMPLETION` 同时尖峰 + 备份窗口重合 → 备份 I/O 治理（限速/错峰），不是数据库坏了；
3. 把尖峰时刻与变更日历对齐是存储排错的第六感，靠参照数据积累。

## 10. 机制注记与版本面（⚠️ 转述）

- 预读粒度：按顺序性判定整 extent 预取，坏扫描会把预读变成洪水（第 5 节）——Linux/云盘上 readahead 双层（OS+引擎）叠加曾致延迟误读，微软有专门 KB 讨论；
- 日志写模型：块提交（block commit）合并组提交，`WRITELOG` 的均值受提交**频率**影响大于**体积**——小事务风暴型病灶；
- `instant file initialization`（IFI）：数据文件增长免清零（权限面：`SE_MANAGE_VOLUME_NAME`），日志文件永远不享受——「增长卡 30 秒」在日志侧是常态，设计要预配；
- 云盘限速是 2024+ 新增变量：单盘 IOPS/吞吐上限使「实例 DMV 慢、存储监控快」的错位有了新解释层。

**I/O 归因四步联立表**（重构）：

| 层 | 观测 | 异常判据 |
|---|---|---|
| 引擎 | `PAGEIOLATCH`/`WRITELOG` 差分 | 窗口占比与均值延迟双高 |
| 实例 | `dm_io_virtual_file_stats` 分文件 | 单文件显著离群于同卷兄弟 |
| OS/虚拟化 | perfmon/`dm_os_process_memory` I/O 深度 | 队列持续堆积 |
| 存储 | 阵列/云盘侧延迟分位 | 与实例层错位→中间层病灶 |

**一句话纪律**：四表中「实例层异常而存储层正常」出现率最高——多数「存储慢」事故最后结案为「数据库自己读太多」（回到 05/07/08 章），存储排错的谦卑在于先怀疑自己。

## 核心概念速览（中英对照）

- **缓冲池命中** — Buffer pool hit：页已在内存则不下盘，物理读的总闸 ⚠️
- **PAGEIOLATCH_SH** — 读盘等待：缓冲池未命中等待页读入 ⚠️
- **WRITELOG** — 日志写等待：提交等待日志落盘 ⚠️
- **WAL** — Write-Ahead Logging：先写日志后写数据的恢复基石（教材层见数据库系统概念）
- **tempdb** — 系统工作库：排序/行版本/临时对象的共用池 ⚠️
- **PFS/SGAM 争用** — 分配页闩争用：tempdb 高频分配的串行点 ⚠️
- **版本存储** — Version store：快照隔离的行版本链，长事务致膨胀 ⚠️
- **自动增长** — Auto-growth：同步扩文件造成的等待尖峰 ⚠️
- **比例填充** — Proportional fill：多文件按空闲比例分配的规则 ⚠️
- **读放大** — Read amplification：逻辑需求 vs 物理读取的倍数错配（🔧 SQLite 页实验锚定）
- **io_stall** — I/O 停顿累计：`dm_io_virtual_file_stats` 的延迟原料 ⚠️
- **freelist** — SQLite 空闲页链：🔧 类比「删除≠归还」，**非 SQL Server 行为**
- **VACUUM** — SQLite 文件紧缩：🔧 实测 1585→160 页，仅膨胀概念锚点

## 最新演进与工业实践

1. **内存优化 tempdb**（SQL Server 2019 起，⚠️ 转述）：PFS 等元数据页进内存专属结构后，「多文件治争用」的旧教条权重显著下降；2022/2025 延续该机制，排错重点转向版本存储与容量治理。
2. **Azure 托管盘节奏控制**：2024–2026 云上排错的头号新变量是磁盘分层（Premium SSD v2/Ultra）的按需限速与突发信用——实例级延迟与存储级配额必须联立监控（⚠️ 转述自微软 I/O 节奏控制文档域）。
3. **观测面现状**：文件级 I/O 统计的官方参考持续维护（`sys.dm_io_virtual_file_stats` 所在 DMV 索引域，✅ 本书关联页已验证：[等待统计官方页](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-os-wait-stats-transact-sql)）。
4. **跨引擎对照 🔧**：SQLite `PRAGMA page_count/freelist_count` + `VACUUM` 的实测（1585→160 页）与 DuckDB 逐算子 rows 统计说明「物理/逻辑放大」是普适观测维度——SQL Server 工具名不同、结论不可平移（非 SQL Server 行为）。
