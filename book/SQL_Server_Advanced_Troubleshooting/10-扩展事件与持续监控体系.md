# 10 扩展事件与持续监控体系（⚠️ 主题重构章）

> 章名非原书逐字章名（取证降级见 [00-总览与阅读地图](00-总览与阅读地图.md) 第二节）。本章收束全书：扩展事件（XEvent）框架的排错用法、system_health 的默认取证价值，以及把前九章串成「持续监控体系」的工程化路径。全部 **⚠️ 转述**；🔧 **非 SQL Server 行为**。

## 1. 为什么是 XEvent：Profiler 的解剖学替代

⚠️ 转述：SQL Profiler/服务器端跟踪世代的核心缺陷是「以事件流为单位重格式输出」，开销高且安全事件缺位。扩展事件（2008 引入、2012 成熟）以**极低开销的异步事件引擎**取代之：会话（session）→ 事件（event）→ 动作（action，补充上下文）→ 目标（target：ring_buffer/file/event_file/stream）。官方总览 ✅ HEAD 200：https://learn.microsoft.com/en-us/sql/relational-databases/extended-events/extended-events/

排错纪律：
1. 谓词过滤（`WHERE duration > 5000`）在引擎侧完成，不要「全抓再客户端筛」；
2. `event_file` 轮转与体积上限必须显式设定（环回目标 ring_buffer 会悄悄覆盖旧数据）；
3. 生产会话清单进版本管理，事故现场先 `SELECT * FROM sys.server_event_sessions` 看别人留了什么。

## 3. system_health：引擎自带的案卷

⚠️ 转述：默认会话 `system_health` 常驻，环回目标含 `spid_registry`、`wait_info`（采样）、`errors` 记录（`sp_server_diagnostics` 组件健康）与 `event_file`（sql_server_process_events、`xml_deadlock_report`、`security_error_reported` 等）。排错价值：
1. 死锁历史的第一取证源（无需提前布置）；
2. `sp_server_diagnostics` 组件快照回答「引擎自己认为健康吗」；
3. 局限：环形缓冲短（分钟到小时级）、采样有偏——**不能替代第 01 章的自建参照数据**。

## 4. 持续监控体系：把本书合成一个闭环

重构的参考架构（⚠️ 转述+方法论综合）：

```
采集层：FRK 作业(sp_Blitz/sp_BlitzFirst/sp_BlitzCache/sp_BlitzIndex) + sp_WhoIsActive 定时
      + XEvent 定向捕获(死锁/阻塞/慢批) + Query Store(库内历史)
  ↓
存储层：集中仓库库(快照表/解析后的 XEvent 表)，保留期分级
  ↓
分析层：等待四象限看板 + 基线偏差告警(分位而非阈值常量)
  ↓
处置层：runbook(01-09 章检查清单的落地) + 变更后回归门禁(08 章升级验收)
```

Brent Ozar 团队 First Responder Kit（✅ https://github.com/BrentOzarULTD/SQL-Server-First-Responder-Kit ）与 Adam Machanic sp_WhoIsActive（✅ https://github.com/amachanic/sp_whoisactive ）即采集层的现成件；Dmitri Korotkevitch 在 expertsql 的长文系列（⚠️ 转述）与本书互为表里。

## 5. XQuery 读法：从 XML 里取字段

⚠️ 转述：event_file 目标经 `sys.fn_xe_file_target_read_file` 暴露为 XML，用 `.query()/.value()` 抽字段是社区脚本的通用形态：

```sql
SELECT x.e.value('@timestamp','datetime2') AS ts,
       x.e.value('(data[@name="database_id"]/value)[1]','int') AS db_id,
       x.e.query('.') AS evt
FROM (SELECT CAST(event_data AS xml) AS ed
      FROM sys.fn_xe_file_target_read_file(N'deadlock*.xel',NULL,NULL,NULL)) AS f
CROSS APPLY f.ed.nodes('/Event') AS x(e);
```

（示例为转述语义的重构写法，事件字段名以目标版本 schema `sys.dm_xe_object_columns` 为准 ⚠️。）

## 6. 🔧 类比实验（**非 SQL Server 行为**）

1. **T3 轻量持续捕获** 🔧（本机 SQLite）：`set_trace_callback` 挂载后全程记录语句文本，实测捕获 `CREATE TABLE z`、5×`INSERT`、`SELECT count` 的流式痕迹——「引擎内挂回调、谓词/格式化留给下游」的 XEvent 直觉；SQLite 的 trace 是同步 Python 回调，**开销模型与 XEvent 异步环形缓冲完全不同**。
2. **ring_buffer 覆盖类比** 🔧：用 `collections.deque(maxlen=N)` 模拟环回目标——写满即悄悄丢最旧，直观复现第 3 节「默认会话留不住昨天的证据」。
3. **集中仓库类比** 🔧（DuckDB）：把 T3 的语句流按分钟写 CSV，再用 DuckDB 一条 SQL 聚合出 top 语句——即「XEvent file → 解析表 → 看板」管道的单机最小版；DuckDB 扫文件聚合的实测速度说明解析层不再是瓶颈。
4. **DMV 权限/目录类比** 🔧：`sys.server_event_sessions` 类元数据查询在 SQLite 对应 `PRAGMA function_list` 式的自省命令——都体现「观测框架自身也要可观测」。

## 8. 检查清单（重构）

1. 生产实例默认三问：system_health 在跑吗？自建会话清单有版本管理吗？event_file 落在哪个盘、多大轮转？
2. 死锁/阻塞捕获先于慢查询捕获布置（成本低、取证价值高）；
3. `query_post_execution_showplan` 类重事件只允许窗口化启用；
4. 采集脚本每季度对目标版本做一次 schema 校验（事件/列更名风险，⚠️ 转述）；
5. 仓库层保留期 ≥ 审计需求，聚合层永不清；
6. 每次事故复盘输出「本次缺哪张网」→ 回补采集清单（第 01 章参照数据的迭代机制）。

## 10. 与云和第三方栈的边界（⚠️ 转述）

- Azure SQL DB：Query Store 内置报表+自动计划纠正承担了本表「每小时/每日」两行的一部分，但事件级捕获仍要自建 XEvent（`azure_sql_databases_*` 系遥测走诊断设置导出）；
- 托管实例（MI）：接近 VM 形态，FRK/sp_WhoIsActive 全兼容（Linux 内核面差异在 OS 指标层）；
- 第三方监测（Darwin/Redgate/SolarWinds 系）本质是「采集层换壳」：数据模型仍由 DMV/QS/XEvent 三源决定——本书方法论不因工具商而豁免；
- 反模式警示：把所有 XEvent 会话设成无限文件+无清理，三个月后自己制造第 03 章容量事故。

## 核心概念速览（中英对照）

- **扩展事件** — Extended Events (XEvent)：低开销异步事件捕获框架 ⚠️
- **会话/事件/动作/目标** — session/event/action/target：XEvent 四元组 ⚠️
- **ring_buffer / event_file** — 环回与文件目标：各有覆盖/膨胀权衡 ⚠️
- **system_health** — 默认健康会话：引擎自带的短周期案卷 ⚠️
- **sp_server_diagnostics** — 组件健康流：引擎自评通道 ⚠️
- **fn_xe_file_target_read_file** — 文件目标解析函数：XQuery 抽字段入口 ⚠️
- **谓词下推** — 引擎侧 filtering：XEvent 低开销的前提 ⚠️
- **FRK / sp_Blitz 系** — First Responder Kit：采集层工业现成件（✅ GitHub）
- **sp_WhoIsActive** — 现场快照脚本：阻塞/等待/计划一屏（✅ GitHub）
- **持续监控闭环** — collect→store→analyze→runbook：本章的体系学 ⚠️
- **set_trace_callback** — SQLite 🔧 语句级回调：XEvent 直觉锚点，**非 SQL Server 行为**
- **deque(maxlen)** — 🔧 环回目标模拟器：覆盖语义的最小复现
