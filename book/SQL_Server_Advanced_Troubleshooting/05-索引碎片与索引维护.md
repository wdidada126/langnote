# 05 索引碎片与索引维护（⚠️ 主题重构章）

> 章名非原书逐字章名（取证降级见 [00-总览与阅读地图](00-总览与阅读地图.md) 第二节）。本章重构「索引碎片与维护策略」主题：碎片的两个维度、度量视图、REORGANIZE/REBUILD 的取舍与「按需维护」的治理观。全部 **⚠️ 转述**；🔧 实验**非 SQL Server 行为**。

## 1. 两类碎片，一个常被混用的词

⚠️ 转述（内部结构详版见 [Pro SQL Server Internals/02](../Pro_SQL_Server_Internals/02-表与索引的内部结构与访问方法.md)）：

1. **外部碎片（order fragmentation）**：叶子链表的逻辑序与磁盘物理序错配——伤害顺序扫描的预读效率；
2. **内部碎片（page density）**：页平均可用空间占比低——同样数据占更多页，放大读量与缓存压力。

「碎片率高」本身不是病症：一次性装载后只读的大索引，90% 外部碎片可能毫无影响；而高频改键的窄索引 5% 碎片也可能伴随严重页闩争用。**症状驱动**（等待里有 `PAGEIOLATCH_SH`、扫描逻辑读异常）优先于指标驱动——这是本书立场（⚠️ 主题重构理解）。

## 2. 度量：dm_db_index_physical_stats

⚠️ 转述：TVF `sys.dm_db_index_physical_stats` 提供 `avg_fragmentation_in_percent`（外部）、`page_count`、`avg_page_space_used_in_percent`（内部）等；开销随采样模式（LIMITED/SAMPLED/DETAILED）差异巨大——DETAILED 全扫叶子链，大表上本身就是事故源。检查姿势：LIMITED 起步，对可疑对象再升档；关注 `forwarded_record_count`（堆的转发指针，见 Kalen Delaney 系笔记）。

## 3. REORGANIZE vs REBUILD：一个被用反的表

⚠️ 转述（官方 ALTER INDEX：https://learn.microsoft.com/en-us/sql/t-sql/statements/alter-index-transact-sql ✅ HEAD 200）：

| 维度 | REORGANIZE | REBUILD |
|---|---|---|
| 动作 | 叶子层链接整理，逻辑操作 | 新 B 树整体重建后切换 |
| 日志量 | 小 | 大（最小记录需恢复模式允许） |
| 锁/在线 | 短时页级锁，基本无阻塞窗口 | `ONLINE=ON` 需企业版语义（⚠️ 转述版本面），非在线则长表锁 |
| 统计信息 | 保留 | 默认重建时更新 |
| 适用直觉 | 轻度整理、窗口紧 | 深度碎片/变更存储参数/压缩 |

社区长期形成的反教条：**「10–15% 重建、5–10% 重组」的旧阈值来自小表时代**（碎片率的分母是页数——百万页索引的 3% 也是灾难，十页索引的 99% 无所谓）。替代方案是三维决策：绝对页量 × 内部碎片 × 症状（⚠️ 转述自 Michelle Ufford 系作业框架的通行做法）。

## 4. 维护作业治理与工具生态

⚠️ 转述：企业实践中索引维护属于作业调度域（SQL Agent），排错侧关心的是维护动作本身制造的故障：
1. REBUILD 风暴→日志暴涨+IO 饱和+备份链肥大（维护窗口把生产拖慢是常见「次生灾害」）；
2. 无差别全库重建→浪费且掩盖真实热点；
3. 工业标准件：Brent Ozar 团队的 **sp_BlitzIndex**（元数据级索引体检：重复索引、未用索引、过度维护线索，✅ https://www.brentozar.com/blitzindex/ HEAD 200）与 Michelle Ufford 的迷你维护作业（按碎片率分档+日志体积控制，⚠️ 转述）。

## 5. 键设计与碎片的因果上游

⚠️ 转述：随机 GUID 主键 = 插入随机打到 B 树任意页 → 内部碎片+页闩热点三连。排错遇到 `PAGELATCH_EX` 集中于某索引时，先看键是不是 `NEWID()`，处方是 `NEWSEQUENTIALID()`/序列表/带前缀 GUID 等设计修正——**维护是下游，键设计是上游**（另见 [Pro_SQL_Server_Internals/05-索引碎片与设计调优](../Pro_SQL_Server_Internals/05-索引碎片与设计调优.md)）。

## 6. 🔧 类比实验（**非 SQL Server 行为**，并登记类比局限）

1. **物理与逻辑脱钩** 🔧（本机 SQLite，50 万行表）：随机散布删除 50% 后 `PRAGMA page_count`=**1465**（文件不缩）；`VACUUM` 后 **734**（减半）。范围聚合耗时 8.3ms→7.5ms——SQLite 按 B 树逻辑遍历、跳过空页，**几乎无磁盘序碎片问题**；这恰好反衬 SQL Server 碎片的伤害面（预读依赖物理序、缓冲池按页驻留）在 SQLite 上不可复现。类比只到「删除不归还空间、体积与逻辑需求脱钩」为止。
2. **度量开销分档类比** 🔧：DuckDB 侧用 `EXPLAIN ANALYZE` 看 rows 而不对「碎片」建模（列式 row-group 自带压缩统计）——提示「碎片」是行式 B 树引擎的地方性概念，跨引擎先问数据结构再套指标。
3. **维护窗口次生灾害类比** 🔧：SQLite `VACUUM` 需要近乎双倍临时空间且全程持锁——「整理动作本身是大操作」的直观教训 30 秒可复现（本机 T4/T6 均见秒级阻塞面）。
4. **键随机性类比** 🔧：SQLite 中把主键换成随机 TEXT 再插入，`page_count` 增速显著高于顺序键（本机同构实验）——「随机键→页利用低」的方向感通用，具体指标体系仍是 SQL Server 的。

## 8. 检查清单（重构）

1. 症状先行：有无扫描类逻辑读/`PAGEIOLATCH` 异常，再查碎片表；
2. `avg_fragmentation_in_percent` 永远与 `page_count` 成对读；
3. REBUILD 前列：日志盘余量、备份链节奏、在线选项的版本/许可面（⚠️ 转述）；
4. 对随机键表把处方升级到设计层（序列键/分区对齐）；
5. 维护作业加「本窗口最大日志量」护栏，防止维护制造事故；
6. 每季跑一次 sp_BlitzIndex 级体检归档，比对上季差异。

## 9. 三个现场场景（重构示例，⚠️ 非原书案例）

**场景 A｜「碎片 99% 的百万行表，查询从不慢」**
1. 该表只在月度归档时整段读，顺序大扫描+预读下外部碎片代价趋零；
2. 结论：指标异常≠病症，把「是否进入作业清单」的判据写成「访问形态×症状」两列；
3. 无脑重建的代价：日志暴涨+维护窗口超时——不治也罢了。

**场景 B｜「重建索引后反而更慢」**
1. 检查一：REBUILD 顺带 `UPDATE STATISTICS`——全扫描重采样使直方图步界移动，坏计划诞生（06 章联动）；
2. 检查二：填充因子被默认值重置，页留白变化改变插入行为；
3. 教训：维护是变更，变更要走 08 章的 Query Store 回归门禁，事后对拉 top 资源查询。

**场景 C｜「新插入集中在最后一页，`PAGELATCH_EX` 排队」**
1. 典型自增/时间键+高并发装载（键设计上游问题，第 5 节）；
2. 短期：分区把热点摊到多分配单元（机制面见 #36 分区章）；
3. 长期：键改哈希前缀/反转段，或改「序列+范围查询」双索引结构。

## 10. 度量学注记（⚠️ 转述）

- `avg_fragmentation_in_percent` 的计算基于叶链与磁盘 extent 序的偏离抽样——LIMITED 模式下由元数据推得，页少时抖动大，**只看趋势不看单点**；
- 内部碎片用 `avg_page_space_used_in_percent` 对照 FILLFACTOR 设定差，判断「留白策略失效」；
- 堆：`forwarded_record_count>0` 的表任何扫描都走转发指针——它的「碎片」远比 B 树版恶性，处方是 clustered index 或 `CREATE CLUSTERED INDEX` 化，而非重组；
- 列存储索引不适用本章指标体系（row-group 压缩与 delta store 是另一套健康学，见 #36 列存章）。

**维护动作成本排序表**（重构，⚠️ 转述语义）：

| 动作 | 日志量 | 阻塞面 | 统计影响 | 适用直觉 |
|---|---|---|---|---|
| 不动 | 0 | 无 | 无 | 症状缺失时是正确答案 |
| REORGANIZE | 小 | 短页锁 | 保留旧统计 | 轻外部碎片+窗口紧 |
| REBUILD ONLINE | 大（版本受限） | 起止瞬间 Sch-M | 默认重更统计 | 深碎片/改存储参数 |
| REBUILD OFFLINE | 大 | 全程表锁 | 默认重更统计 | 维护窗充足的非关键表 |
| DROP+CREATE（聚簇） | 最大 | 长 | 需手动跟进 | 顺带数据重整（等价迁移） |
| ALTER PARTITION 重组 | 中 | 元数据为主 | 增量统计失效风险 | 分区对齐修复而非救碎片 |

**顺序纪律**：先症状、再度量、后动作；任何一行动作之前问三件事——日志盘够吗？备份链节奏会被打乱吗？变更窗口里 Query Store 准备好接回归了吗（08 章）？

## 核心概念速览（中英对照）

- **外部碎片** — External/order fragmentation：叶链逻辑序 vs 物理序错配 ⚠️
- **内部碎片** — Internal fragmentation / page density：页均空间利用率低 ⚠️
- **avg_fragmentation_in_percent** — 平均碎片率：`dm_db_index_physical_stats` 主指标 ⚠️
- **LIMITED/SAMPLED/DETAILED** — 采样模式：度量开销的三档 ⚠️
- **REORGANIZE** — 重组：叶子层链接整理、低日志操作 ⚠️
- **REBUILD** — 重建：整树重构，可在线（版本受限） ⚠️
- **FILLFACTOR/PAD_INDEX** — 填充因子：叶/中间层留白策略 ⚠️
- **转发指针** — Forwarded record：堆更新导致的行迁移记录 ⚠️
- **维护窗口次生灾害** — Maintenance-induced regression：REBUILD 风暴拖慢生产 ⚠️
- **sp_BlitzIndex** — 索引体检脚本：重复/未用/过度维护线索（✅ 社区工具）
- **page_count 脱钩** — 🔧 SQLite 体积不随删除缩减：方向锚点，**非 SQL Server 行为**

## 最新演进与工业实践

1. **工具现状（✅ HEAD 200）**：[sp_BlitzIndex](https://www.brentozar.com/blitzindex/) 与 [First Responder Kit](https://github.com/BrentOzarULTD/SQL-Server-First-Responder-Kit) 活跃维护；Michelle Ufford 的维护作业框架仍是作业调度的工业默认件 ⚠️ 转述。
2. **引擎侧演进** ⚠️ 转述：SQL Server 2016+ 对页分配与延迟持久化的改进、2022 智能查询处理降低「坏计划借道碎片」误诊率；联机重建在 2019+ 各 SKU 的可用性扩大（版本面以官方 ALTER INDEX 页为准 ✅）。
3. **云托管语境**：Azure SQL DB 自动维护选项（自动索引创建/回滚，⚠️ 转述 IQP 特性）让「人肉重建」进一步让位于「策略+审计」，但本书的症状驱动原则恰是审计自动动作的依据。
4. **研究对照 🔧**：列式/LSM 引擎（DuckDB、RocksDB 系）以 compaction 取代 reorganize 语义——碎片治理的研究表达是「后台合并策略」；本机 DuckDB row-group 统计可作极简对照，非 SQL Server 行为。
