# 07 计划缓存与参数嗅探（⚠️ 主题重构章）

> 章名非原书逐字章名（取证降级见 [00-总览与阅读地图](00-总览与阅读地图.md) 第二节）。本章重构「低效查询：编译、缓存与参数敏感性」主题：缓存命中模型、再编译风暴、参数嗅探的病理与工具箱。全部 **⚠️ 转述**；🔧 **非 SQL Server 行为**。

## 1. 计划缓存：为什么「第二次快第三次又慢了」

⚠️ 转述：查询编译昂贵，引擎按「查询指纹（签名）+ 环境（ANSI 设置等）」缓存计划。排错关心的三件事：

1. **命中率与编译压力**：`sys.dm_exec_query_stats`（✅ 官方页 HEAD 200）的 `compile_*` 与 execution 比值、SQL 编译器等待/worker 占比；
2. **逐出与重新编译**：统计更新、索引变更、`sp_recompile`、内存压力都会标记计划失效——`sys.dm_exec_procedure_stats` 的 `execution_count` 骤降+`cached_time` 重置是现场证据；
3. **缓存膨胀**：ad-hoc 文本微差异（注释/字面量/大小写）各占一坑——`optimize for ad hoc workloads` 先存压缩桩再存全计划（⚠️ 转述），`query parameterization`（简单/强制）是数据库级阀门。

## 2. 参数嗅探（Parameter Sniffing）的准确定义

⚠️ 转述：编译时用**首次传入的实参值**预测行数（第 06 章 CE），产出的计划被**所有后续参数值共用**。数据倾斜 + 多形态参数 = 灾难的充要条件：「大客户计划跑了小客户」与反向都常见。识别特征：

- 同一 proc 计划平均时延 bimodal（直方图双峰）；
- 手动 `EXEC p @x=慢值` 立刻变慢、`@x=快值` 变快，且 `SET STATISTICS XML ON` 见估计/实际行数与共享计划一致；
- Query Store 里同 query_id 出现多 plan_id 且时延分化（第 08 章工具）。

**反误诊**：参数嗅探≠万能筐——先确认不是统计陈旧/缺索引/回归（升级、兼容性级别变更）。

## 3. 工具箱：从止血到根治（⚠️ 转述的选项清单）

| 手段 | 语义 | 代价 |
|---|---|---|
| `OPTION (RECOMPILE)` | 每次执行现场编译，天然无共享 | CPU；高频小查询不适用 |
| `OPTIMIZE FOR (@p=典型值/UNKNOWN)` | 编译期钉值或用中性密度 | 需选对值 |
| 局部变量赋值 | 切断嗅探链（变量初值未知→密度估计） | 同 RECOMPILE 的计划盲区 |
| 查询存储强制计划 | 见 08 章 | 掩盖设计问题 |
| `OPTION (QUERYTRACEON 4137/9481…)` | 旧式旁路（⚠️ 现由 `USE HINT`/`QUERY_OPTIMIZER_COMPATIBILITY_LEVEL` 承接，官方 hints 页 https://learn.microsoft.com/en-us/sql/t-sql/queries/hints-transact-sql-query ✅ HEAD 200） | 文档化/合规风险 |

根治方向 ⚠️ 转述：拆分支（不同参数形态不同 SQL）、按形态给不同 proc、或让数据更「可估计」（列组统计、分区对齐）。

## 4. 再编译风暴的两种形态

⚠️ 转述：
1. **缓存抖动**：单查询巨型计划+内存压力→反复逐出反复编译——表现为编译 worker 时间占比高；处方在内存（04 章）与查询瘦身；
2. **参数即字面量**：应用未参数化（ORM 拼字面量）→ 每个值都是新指纹 → 缓存爆+逐出。看 `dm_exec_cached_plans` 中 `usecounts=1` 占比（第 04 章 5 节呼应）。这是**应用侧缺陷**，DB 端 `forced parameterization` 只是止痛。

## 5. 🔧 类比实验（**非 SQL Server 行为**）

1. **无缓存对照** 🔧：SQLite 每次 `sqlite3_prepare` 现场编译、计划仅属该语句对象——因此 SQLite **不存在参数嗅探**（绑参不进计划成本）。本机演示：同一 prepared 语句换绑定值，`EXPLAIN QUERY PLAN` 文本恒定。对比出 SQL Server 的关键设计张力：共享计划换编译成本，倾斜数据让共享变毒药。
2. **统计参与成本** 🔧（承接 06 章 T7）：SQLite 的 `sqlite_stat1` 只在 prepare 时刻影响计划——等价于「每次 RECOMPILE 的短生命周期缓存」，说明「计划复用 + 分布信息陈旧」的矛盾在最小引擎里也要面对，只是解法不同。
3. **DuckDB  prepared** 🔧：`PREPARE`+`EXECUTE` 复用计划，同样无嗅探病理——两引擎皆「每连接私有计划」，SQL Server 是「实例级共享」；类比只到「复用带来陈旧风险」为止。
4. **字面量爆炸类比** 🔧：SQLite 无实例缓存可炸；用「把 1 万条只差常量的 INSERT 文本各自 prepare」演示内存/编译开销的单调增长——方向感实验，**非 SQL Server 行为**。

## 7. 检查清单（重构）

1. 慢化对象先取 `dm_exec_query_stats` 的「均值时延分布」再取 top 实例；
2. 双峰=嗅探嫌疑 → 计划 XML 里 `ParameterList`/`ParameterCompiledValue` 与实传值对比（⚠️ 转述）；
3. ad-hoc 占比高 → 应用参数化改造优先于 DB 强制参数化；
4. 止血顺序：Query Store 强制（若可用）→ RECOMPILE/OPTIMIZE FOR 计划指南级方案；
5. 每次统计更新/索引变更后观察再编译曲线，区分「修好了」与「抖动中」；
6. 云化面：Azure SQL 的自动计划纠正（Automatic plan correction）即 Query Store 强制的托管化（⚠️ 转述，与 08 章合看）。

## 8. 场景演练（重构示例，⚠️ 非原书案例）

**场景 A｜「应用上线后偶发 3 秒慢，其余毫秒级」**
1. `dm_exec_query_stats` 均值掩盖双峰 → 取时延分桶直方图（社区脚本 sp_BlitzCache 的 top 视图同理）；
2. 抓计划 `ParameterCompiledValue` 与实参分布对撞：慢样本参数都是「历史数据稀疏段」；
3. 处方：`OPTIMIZE FOR UNKNOWN` 或按数据段拆 proc——RECOMPILE 因该 proc 每秒 400 次被否决（编译 CPU 代价）。

**场景 B｜「统计更新后存储过程突然快」**
1. 计划失效+重编译的合法解释项：新直方图改了嗅探基（06 章联动）；
2. 若随后又慢回去 → 再编译周期里混进了坏嗅探，转计划稳定性审计（同 query 多 plan 并存）；
3. 教训：统计/索引变更是**生产变更**，要挂变更日历。

**场景 C｜「临时表引发的连锁再编译」**
1. proc 内 `#t` 建后即用，首次执行按临时表实况编译，二次按缓存版本执行——经典 temp-table 嗅探变体（⚠️ 转述：`#t` 与表变量差异详见 #36/14 章）；
2. 稳定化：表变量+`OPTION (RECOMPILE)` 组合在中小规模下最可预测（⚠️ 转述社区经验学）。

## 9. 概念边界澄清（⚠️ 转述）

- 参数嗅探≠计划不稳定：前者是「一个计划服务多参数形态」的系统性偏置，后者掺统计变更/内存驱逐等噪声；
- 计划指南（Plan Guide）与 Query Store 强制的取舍：指南可随基线重编译但维护重，强制简单但会因计划失效（基线删除）而 `force_failure`（08 章）；
- 「编译在等待统计里不可见」是常见误读：编译消耗记在 worker time，表现为 `SOS_SCHEDULER_YIELD` 占比升而非独立等待类型。

**手段选择决策表**（重构，⚠️ 转述语义）：

| 局面 | 首选 | 理由 |
|---|---|---|
| proc 高频（>每秒数次）+ 偶发慢 | Query Store 强制 + 根因修复 | RECOMPILE 的编译税付不起 |
| proc 低频 + 参数形态分明 | 拆 proc/分支内独立语句 | 让每个计划只服务一种形态 |
| ad-hoc 报表类（本就一次一编译） | 无需防嗅探，直接调本次 | 无共享即无偏置 |
| 数据段漂移（历史表越来越斜） | `OPTIMIZE FOR` 定期重估或 `RECOMPILE` 计划指南 | 钉值会过期，指南可随基线重编译 |
| 无法改代码（供应商包） | 计划指南/QS 强制 + 变更台账 | 外部面只剩 DB 侧杠杆 |

**证伪清单**（宣称「修复了参数嗅探」之前）：
1. 修复后慢样本的参数值是否仍在分布内（别只测了好参数）；
2. 峰值窗口压测过编译 CPU 增量；
3. Query Store 里同 query_id 的计划多样性没有恶化成「每个参数一个新计划」；
4. 回归门禁（08 章）跑过一轮 top 资源对比。

## 核心概念速览（中英对照）

- **计划缓存** — Plan cache：按查询指纹+环境共享编译产物的机制 ⚠️
- **查询指纹** — Query hash / 签名：文本归一后的缓存键 ⚠️
- **参数嗅探** — Parameter sniffing：编译期采样实参致计划偏置 ⚠️
- **再编译** — Recompilation：失效标记后的重编译事件 ⚠️
- **RECOMPILE 提示** — OPTION (RECOMPILE)：每次现场编译的止血 ⚠️
- **OPTIMIZE FOR** — 参数值策略：钉典型值或 UNKNOWN ⚠️
- **ad-hoc 工作负载** — Ad-hoc：高变异字面量负载，缓存杀手 ⚠️
- **强制参数化** — Forced parameterization：DB 级字面量改写 ⚠️
- **USE HINT** — 提示化兼容开关：QUERYTRACEON 的文档化替代 ⚠️
- **usecounts=1 占比** — 一次性计划率：膨胀诊断指标 ⚠️
- **prepared statement** — SQLite/DuckDB 🔧 私有计划模型：无嗅探对照，**非 SQL Server 行为**

## 最新演进与工业实践

1. **官方文档（✅ HEAD 200）**：[sys.dm_exec_query_stats](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-exec-query-stats-transact-sql) 与 [查询提示页](https://learn.microsoft.com/en-us/sql/t-sql/queries/hints-transact-sql-query) 为当前权威；`QUERY_OPTIMIZER_COMPATIBILITY_LEVEL` 系提示已文档化——2024–2026 排错不再需要未公开的 trace flag。
2. **IQP 影响** ⚠️ 转述：表变量延迟编译等特性显著压缩了经典嗅探场景，但倾斜参数的行模式过程仍归本章工具治理；Azure SQL 的自动计划纠正把「强制计划」托管化，本书原则（先归因再强制）仍是审计准绳。
3. **社区工具**：Adam Machanic 的 [sp_WhoIsActive](https://github.com/amachanic/sp_whoisactive)（✅）现场抓「当前参数+所用计划」；FRK 的 `sp_BlitzCache`（✅ [仓库](https://github.com/BrentOzarULTD/SQL-Server-First-Responder-Kit)）自动标注嗅探嫌疑计划（参数敏感列+估算偏差启发式）。
4. **研究面**：计划共享的稳健性是经典课题——自适应执行（Eddies，[DOI:10.1145/342009.335420](https://api.crossref.org/works/10.1145/342009.335420) ✅）与多计划选择（plan pinning/robust plans 文献系）给出「不赌单计划」的理论路线；本机 SQLite/DuckDB 的私有计划模型是无共享端的对照锚（🔧 非 SQL Server 行为）。
