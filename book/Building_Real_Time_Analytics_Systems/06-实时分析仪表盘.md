# 06 构建实时分析仪表盘（Building Real-Time Analytics Dashboards）

> 书目 #157 第 6 章 ｜ 主题：仪表盘架构、Streamlit 是什么、配置、构建仪表盘。
> 精读重构（目录 ✅，展开 ⚠️），非原书文本；Streamlit 行为不实测，⚠️+官方文档。

## 本章任务

- 理解"消费面"的最小可用形态：为什么本册选 Streamlit 而不是 Grafana/BI 全家桶；
- 掌握仪表盘三层：数据连接（Pinot 查询客户端）→ 查询编排（每次刷新即查询）→ 渲染与自动刷新策略；
- 建立"仪表盘是实时系统的显微镜"意识：它是端到端新鲜度 SLO 的人肉探针。

## 6.1 仪表盘架构（Dashboard Architecture）

- 形态选择（本册）：**代码化仪表盘**（dashboard-as-code）而非拖拽 BI——版本可控、逻辑可测、与 Streams 应用同仓演进；
- 数据通路：`Streamlit 进程 → Pinot Broker (SQL) → 段` ，无缓存层时**每次交互=一次真实查询**——前端刷新节奏直接压在服务层 QPS 上；
- 两个新鲜度旋钮：自动刷新间隔（auto-refresh）与查询时间窗（rolling window 的宽度）——它们的乘积决定"看多新、花多贵"；
- 对照盘上：可视化的理论（编码/交互）不在本册，本册只讲"接上实时数据"的工程面；时序仪表盘近亲见 [../Time_Series_Databases/00-总览与阅读地图.md](../Time_Series_Databases/00-总览与阅读地图.md)。

## 6.2 什么是 Streamlit（What Is Streamlit）

- Python 脚本即应用：自上而下重跑模型（每次交互重执行脚本 ⚠️ 运行机制以官方 docs 为准：https://docs.streamlit.io/ ✅200）；
- 对本册的意义：**零前端**把"查询结果→折线/柱状/计数卡"糊出来，教学关注点保持在数据链路上；
- 组件心智：`st.query_params`（路由参数化切片）、`st.cache_data/ttl`（新鲜度缓存语义）、`st.empty/progress`（自刷布局）（⚠️ API 名以官方为准）。
- 代价登记：重跑模型+无并发服务化=演示利器、生产前端勉强（生产位由 Quarkus/真前端替换，见 09 章"更新订单服务"）。

## 6.3 配置（Configuration）

- 连接配置三件套：Pinot broker URL、表名/时间列名、凭据（⚠️ 书用环境变量或 config.toml，细节不转述）；
- 客户端选型：Pinot 官方 Python 客户端或 REST `/query/sql` 端点（⚠️ 包名以 docs.pinot.apache.org 为准 ✅200）；
- 时间窗参数化：把"最近 N 分钟"提到页面控件——仪表盘第一次具备"自助切片"原型；
- 本地起法心智：`pip install streamlit` 型单机进程 + `streamlit run app.py`（通用做法，非书照抄）。

## 6.4 构建仪表盘（Building the Dashboard）

目录级重构的构建序列（⚠️ 代码不转述）：

1. 查询封装函数：入参（时间窗、维度过滤）→ Pinot SQL → DataFrame；
2. 版面：顶部 KPI 卡（总单量/GMV）+ 主图（按分钟聚合的流式折线）+ 维度小图（品类/门店 Top-N）；
3. 自刷：脚本级 sleep/rerun 或组件 timer，观察"点亮的分钟柱"右移=新鲜度的肉眼证明；
4. 下钻：URL 参数携带切片 → 后续章节订单级页面（09 章）挂同一路由空间；
5. 反模式记录：把整页所有图各发一条全历史 SQL（应共享一次过滤+多聚合列，或预聚合层）——服务层 QPS 的头号杀手。

**端到端验收**（本章隐含里程碑）：注入一条测试订单 → 数秒内 KPI+1 → Kafka 滞后/段可见/前端刷新三段延迟各自可测——11 章生产监控的雏形。

## 🔧 概念补刀：查询成本随窗宽线性涨（类比，非本书引擎）

延续 E5 的算术（DuckDB 1.5.5，**非 Streamlit/Pinot**）：as-of 全扫聚合在 50 万行 Parquet 上 2.5~4.7ms，预聚合读取 0.3ms——把"刷新间隔×时间窗"想成两个独立预算：刷得勤但窗窄（点状态读）便宜；窗宽刷勤（大扫描）贵。仪表盘配置即这两个预算的分配（数据见 `D:\develops\tmp\dbwave_w8_brtas\results.txt`）。

## 核心概念速览（中英对照）

- **代码化仪表盘** — Dashboard as Code：以版本化脚本代替拖拽 BI 工件。
- **重跑模型** — Rerun-on-Interaction：Streamlit 每次交互重执行脚本的运行语义（⚠️）。
- **自动刷新** — Auto-Refresh：以轮询间隔换新鲜度的前端策略。
- **滚动窗口** — Rolling Window：查询时间范围随 now 前移的切片方式。
- **新鲜度探针** — Freshness Probe：仪表盘兼作端到端延迟的肉眼监控。
- **KPI 卡** — Metric Card：单值聚合的头部展示单元。
- **下钻参数** — Drill-down Params：URL 查询参数驱动的切片路由。
- **缓存 TTL** — Cache TTL：结果复用时长=新鲜度上限的开关（⚠️ API 名）。
- **查询风暴** — Query Storm：全图各发重查询打爆服务层的反模式。
- **时间预算×刷新预算** — Window vs Refresh Budget：两个独立成本旋钮。
- **零前端** — Zero Frontend-Code：以脚本快速糊出交互面的取舍。
- **端到端可见性** — End-to-End Visibility：注入→显示全链路延迟的可测性。

## 最新演进与工业实践

- Streamlit 现状：官方主线已引入原生定时刷新/状态管理能力（⚠️ 具体 API 演进未逐条实证），docs ✅ https://docs.streamlit.io/ （curl 200）；"自刷 sleep hack"已是历史写法。
- 仪表盘栈分化：内部运营盘（Streamlit/Grafana/Superset）vs 产品内嵌分析（Pinot+自研前端，本册 09 章方向）——user-facing analytics 的"盘"不再是运维工具而是产品件（呼应 #199 价值叙事，同波登记不链）。
- Grafana + Pinot 数据源插件、Superset 连 Pinot 等现成集成 ⚠️ 转述（官方 docs.pinot.apache.org ✅200 有连接器章节）。
- ClickHouse 生态的 Grafana/Superset 直连更流行，使"轻仪表盘+重 OLAP"组合更常见 ⚠️（https://clickhouse.com/docs ✅200）。
