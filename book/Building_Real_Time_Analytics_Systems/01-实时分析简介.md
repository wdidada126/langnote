## 本章任务

- 建立"事件流是事实记录的第一形态"的世界观；
- 给出实时分析的定义与"新鲜度即产品特性"的判断标准；

- 分清三类常被混淆的系统：事务系统（OLTP）、批数仓（OLAP-T+1）、实时分析（亚秒~分钟级新鲜度）。

## 1.1 什么是事件流（What Is an Event Stream）

- 事件（event）= "某时刻某事发生了"的不可变事实；事件流 = 按时间追加（append-only）的事件序列。
- 关键性质：只追加不修改（变化以新事件表达）、可重放（replayable）、天然带序（分区内有序）。
- 工程载体：Apache Kafka 的 topic/partition/offset 模型把"日志即数据库"（log as database）落到基础设施层。
- 对照：表（table）是"此刻状态"的快照投影；流（stream）是"状态如何变成此刻"的历史。二象性详见 [../Streaming_Systems/06-流和表.md](../Streaming_Systems/06-流和表.md)。

## 1.2 理解流数据（Understanding Stream Data）

- 流数据的四个工程属性：到达无序性（out-of-order）、时间语义（事件时间 vs 处理时间）、重复性（at-least-once）、无界性（unbounded）。
- 迟到与水位线（watermark）的处理哲学在 [../Streaming_Systems/03-水位线.md](../Streaming_Systems/03-水位线.md) 展开到理论级；本册从实用角度引用：先分类需求，再决定"允许多旧"。
- ⚠️ 书中以订单/配送事件为例展开模式设计，细节不逐条转述。

## 1.3 什么是实时分析（What Is Real-Time Analytics）

- 工作定义：数据产生后**秒级到分钟级**内可被聚合查询并驱动决策/展示，且查询模式以高并发点查+多维聚合为主。
- 与流处理（stream processing）的分界：流处理回答"怎么算"（transform/aggregate/join），实时分析回答"怎么被低延迟地查"（serving）。本册的独特立场：**实时分析的瓶颈通常在服务层，不在计算层**。
- 与运营分析（operational analytics）的重叠：⚠️ 兄弟册 #166 从 HTAP 视角处理同一地带，本册从事件侧处理。

## 1.4 实时分析的优势（Advantages）

1. 决策新鲜度：促销/风控/调度从 T+1 变为 T+0；
2. 面向用户的分析产品（user-facing analytics）：把"仪表盘"变成产品功能卖给终端用户；
3. 运营闭环：异常在发生窗口内被发现并自动响应；
4. 统一口径：流上定义的指标复用同一份事件真源（避免批流两套口径漂移）。

## 1.6 对实时分析应用程序进行分类（Classifying RTA Apps）

⚠️ 书中分类框架以"新鲜度要求 × 查询形态（追加只读 vs 状态更新）"为轴，本章重构其要点：

| 类别 | 新鲜度 | 写形态 | 典型 |
|---|---|---|---|
| A 追加型聚合 | 秒~分 | append-only | 点击流计数 |
| B 状态更新型 | 秒 | upsert | 订单状态大盘 |
| C 关联富化型 | 分 | join 流×流/流×表 | 富化后多维分析 |
| D 交互点查型 | 亚秒 | 高并发主键查 | 用户侧"我的订单分析" |

分类的价值：决定第 4~9 章"Kafka Streams 直查 or Pinot 服务层"的分叉；B/D 类是"为什么要服务层"的根因。

## 🔧 实测 E5：新鲜度换时延的第一性体验（非本书引擎行为）

用 DuckDB（Python 包 1.5.5，**非本书 Kafka/Pinot 引擎**）模拟"仪表盘每次刷新都重扫事件 vs 读预聚合状态"：

- 数据：50 万行事件表（key/事件时间/值），写为 Parquet（row group 121344）；
- 实验：as-of 时刻向前推进 12 个点，每点全扫过滤 `event_time <= t` 聚合；
- 结果：全扫聚合耗时 min 2.5ms / median 3.4ms / max 4.7ms；改读**预聚合状态表**同样问题仅 **0.30ms**，且各 as-of 点结果与增量维护一致（exact match: True）。
- 结论（概念级）：新鲜度维护（预聚合）把查询成本从 O(历史) 降到 O(状态)，这正是物化视图/服务层存在的算术理由；50 万行还小，历史到十亿级时该差距即"能不能做产品"的差距。脚本与输出：`D:\develops\tmp\dbwave_w8_brtas\exp.py / results.txt`。

## 核心概念速览（中英对照）

- **事件流** — Event Stream：按时间只追加、可重放的事实序列，实时分析的原料。
- **实时分析** — Real-Time Analytics：秒~分钟级新鲜度之上支撑高并发聚合查询的能力。
- **流表二象性** — Stream-Table Duality：流是表的变化史，表是流的折叠态。
- **事件时间** — Event Time：数据发生时刻而非到达时刻，正确性锚点。
- **处理时间** — Processing Time：系统时钟，实现低延迟但语义脆弱。
- **水位线** — Watermark：对"不再期待更早事件"的显式承诺，控迟到。
- **追加型分析** — Append-only Analytics：只增不改的聚合类实时需求。
- **状态更新型分析** — Upsert-driven Analytics：以键折叠最新值的状态类需求。
- **面向用户的分析** — User-Facing Analytics：把实时聚合查询作为终端用户产品功能。
- **服务层** — Serving Layer：为高并发低延迟查询优化的存储+计算层。
- **新鲜度** — Freshness：数据产生到可查的时间差，被当作 SLA 维度。
- **T+1 批分析** — Batch BI：隔天口径的传统数仓，与本册对象互补不互斥。
- **日志即数据库** — Log as Database：以不可变日志为第一存储形态的架构观。
- **单一事件真源** — Single Event Source of Truth：批流共用一套事件避免口径漂移。
