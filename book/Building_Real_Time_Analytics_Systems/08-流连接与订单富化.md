# 08 使用 Kafka Streams 连接流（Joining Streams with Kafka Streams）

> 书目 #157 第 8 章 ｜ 主题：用 Kafka Streams 富化订单数据、把订单项加入 Pinot、更新订单服务信息、刷新 Streamlit 仪表盘。
> 精读重构（目录 ✅，展开 ⚠️），非原书文本。

## 本章任务

- 掌握流式 join 的三种形态（流×表、表×表、流×流窗口 join）与各自的语义边界；
- 在 AATD 里落地"订单富化"：order/order line 事实流 × product 维表流 → 带商品名/价格的宽事实 → 进 Pinot；
- 认清 join 的隐藏账单：**状态驻留**（要留多久历史才能接上新到的另一半）。

## 8.1 使用 Kafka Streams 丰富订单数据（Enriching Order Data）

- 富化=enrichment：给事实流补维度列（商品名/单价/品类），使分析侧可多维切片；
- 形态一（本章主力）**流×表**（KStream×KTable）：订单流每条去查产品表当前态——语义=「处理时刻的维度视图」，实现=本地 KV 点查，O(1) 无窗口负担；
- 形态二 **流×流**（KStream×KStream）：如 order header × order line 按键互接——必须限定**时间窗口**（both sides 保留 window 时长 ⚠️ store 保留期概念），否则状态无限；乱序与迟到由 timestamp 语义处理（[../Streaming_Systems/09-流式连接.md](../Streaming_Systems/09-流式连接.md) 把三类 join 的语义矩阵推到理论级，本章是其工程实例）；
- 陷阱登记：
  - 维表更新竞态：产品改名瞬间，富化结果取决于"谁先到"——最终一致而非时点正确（要"事件时刻的维度"需走时态版本 join，书未及则通识登记 ⚠️）；
  - 一对多展开：header×line join 后事件数放大（一单 N 行=N 条富化事实），下游计量/去重要重审；
  - 分区对齐：join 双方必须同 key 同分区（republish/repartition 是常态步骤）。

## 8.2 将订单项添加到 Pinot（Adding Order Lines to Pinot）

- 富化后的 order line 宽事实经新的摄取管线进 Pinot 事实表（复用 05 章 streams ingestion，⚠️ topic/表名不转述）；
- 为什么带维度列进引擎而不是查询时 join：高 QPS 用户面把 join 推到写侧（预 join 宽表）是实时 OLAP 的常见定型——存储换查询时延，与 E3"有序换剪枝"同一哲学（空间/写时换读时）；
- 订单项落表后解锁的分析：品类销量、客单结构、Top-N 商品时变榜（03 表 C 类需求闭环）。

## 8.3 更新订单服务信息（Updating the Order Service）

- 订单服务（REST 面）从"只有 id 级明细"升级为"可回显富化后的订单商品行"；
- 链路：Streams 富化结果同时 tee 到服务侧 topic/状态，服务读本地（04 章模式）而非直查 Pinot——**读模型按访问形态分叉**（点查走 KV/服务缓存，聚合走 OLAP）；
- 这是 CQRS 的读侧多元物化，在 [../Streaming_Databases/07-混合数据系统的兴起.md](../Streaming_Databases/07-混合数据系统的兴起.md) 有谱系展开。

## 8.4 刷新 Streamlit 仪表盘（Refreshing the Streamlit Dashboard）

- 06 章仪表盘加"品类/商品"维度切片：新事实表+新查询封装，前端零结构变化——检验了 05 章"加维度组合不需要新拓扑"的承诺兑现；
- 刷新语义提醒：宽表数据到达有 join 窗延迟（双方到齐才出富化结果），仪表盘时间轴会出现"补画"现象——新鲜度 SLA 应按 join 形态分级承诺（01 分类框架的回声）。

## 🔧 概念对照（类比，非本书引擎行为）

DuckDB 1.5.5（**非 Kafka Streams**）演示"流×表=维表点查"与"流×流=窗口内等号配对"的算术差异：

- 流×表：`orders JOIN products ON key` 一次哈希 join 4M 内 3~10ms 级（E3 数据规模）——表侧全态在盘，无驻留成本；
- 流×流：E5 型 as-of 语义若写成双侧 `BETWEEN t-window AND t` 自 join，代价随窗口宽度线性膨胀；
- 结论（概念级）：**"表侧有全史则便宜；双侧皆片段则用窗口买确定性"**——正是 Streams 里 KTable join 免窗、KStream join 必窗的成本真相。脚本：`D:\develops\tmp\dbwave_w8_brtas\exp.py`。

## 核心概念速览（中英对照）

- **富化** — Enrichment：为事实流补齐维度列的写时加工。
- **流×表连接** — Stream-Table Join：一侧全态免窗的 O(1) 点查 join。
- **流×流连接** — Stream-Stream Join：双侧留窗的有状态配对，窗口=驻留账单。
- **连接窗口** — Join Window：两侧记录可被配对的时间跨度（⚠️ 概念通用）。
- **重分区** — Repartition：join 前把双方按同 key 同分区对齐。
- **事件放大** — Fan-out Multiplication：header×line 后事实条数倍增的计量问题。
- **预 join 宽表** — Pre-joined Wide Table：把 join 推到写侧换读侧 QPS。
- **补画现象** — Late Backfill on Chart：join 窗延迟致仪表盘时间轴回填。
- **读模型分叉** — Read Model Forking：点查与聚合各走物化形态。
- **CQRS 读侧** — CQRS Read Side：一份写流多份查询视图（谱系在 Streaming_Databases）。
- **维度竞态** — Dimension Race：维更新与事实到达的先后不定性。
- **新鲜度分级** — Tiered Freshness：join 形态决定的 SLA 分层承诺。
