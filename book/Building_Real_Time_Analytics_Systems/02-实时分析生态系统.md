# 02 实时分析生态系统（The Real-Time Analytics Ecosystem）

> 书目 #157 第 2 章 ｜ 主题：定义生态系统、经典流处理技术栈 vs 现代流处理技术栈。
> 精读重构（目录 ✅，展开 ⚠️），非原书文本。

## 本章任务

- 把全书组件放进一张"数据流向图"：源 → 总线（Kafka）→ 处理器 → 服务层 → 前端；
- 理解经典栈（Lambda 时代的批层+速度层）到现代栈（Kappa/事件驱动 + OLAP 服务层）的演化；
- 记住本章的批判性结论：**流处理器不是查询引擎**——这是第 5 章引入 Pinot 的伏笔；
- 为 🔧 E1（物化视图支持性）建立概念锚点。

## 2.1 定义实时分析生态系统（Defining the Ecosystem）

- 五面分层：采集面（CDC/埋点/网关）、总线面（Kafka/Pulsar）、计算面（Kafka Streams/Flink）、存储-服务面（Pinot/Druid/ClickHouse）、消费面（BI/嵌入式仪表盘/告警）。
- 每条边界都是契约：schema 注册表（Confluent Schema Registry ⚠️ 书中是否使用未实证）、时间语义约定、新鲜度 SLO。
- 生态位判断口径（本册立场）：一个组件要么持有状态（processor state store / OLAP 表），要么只搬运（broker/connector），不存在"既搬运又服务查询"的免费午餐。

## 2.2 经典流处理技术栈（Classic Stream Processing Stack）

- Lambda 架构叙事（与 #156 同一时代的语言）：批层保正确、速度层保新鲜、服务层合并视图；痛点=两套代码两份口径。
- 经典组件代际：Storm（低层原语）→ Spark Streaming（微批）→ Flink（原生流+水位线）。本册对 Flink 只作背景，主角选 Kafka Streams（理由见 4 章）。
- 经典栈的"仓板式"下游：Hadoop/Hive/Parquet 的 T+1 分析链路（存储格式细节见 [../bigdata/09-存储与文件格式.md](../bigdata/09-存储与文件格式.md)）。
- Kappa 修正：以可重放日志取代批层，"流是唯一真源"；理论纵深在 [../Streaming_Systems/10-大规模数据处理的演进.md](../Streaming_Systems/10-大规模数据处理的演进.md)。

## 2.3 现代流处理技术栈（Modern Stream Processing Stack）

- 画像（本册演示的形态）：**Kafka（总线）+ Kafka Streams（无服务器化处理器，跑在应用进程内）+ Pinot（实时 OLAP 服务层）+ Streamlit/Quarkus（消费面）**。
- 三个现代性特征：
  1. 处理逻辑应用化（library 而非 cluster，扩缩随应用实例）；
  2. 服务层回归"专用引擎"而非通用数仓（亚秒高并发）；
  3. 湖仓作为旁路冷路径（第 13 章主题，衔接 [../Data_Lakehouse_in_Action/00-总览与阅读地图.md](../Data_Lakehouse_in_Action/00-总览与阅读地图.md)）。
- 对照盘上：Flink 路线（重状态、独立集群、精确一次端到端）见 [../Stream_Processing_with_Apache_Flink/00-总览与阅读地图.md](../Stream_Processing_with_Apache_Flink/00-总览与阅读地图.md) 与 [../Introduction_to_Apache_Flink/00-总览与阅读地图.md](../Introduction_to_Apache_Flink/00-总览与阅读地图.md)；本册 Kafka Streams 路线是其"轻装侧"镜像。
- ⚠️ 各引擎具体行为（Pinot 的星树索引、Druid 的增量段、ClickHouse 的 MergeTree 合并）本册不实测，只给官方文档指认，详见各章"最新演进"节。

## 🔧 实测 E1：物化视图是什么的"在场证明"（非本书引擎行为）

"现代栈"里服务层的本质是**预计算的物化视图**。用 DuckDB（Python 包 1.5.5，**非本书 Pinot/ClickHouse 引擎**）探查概念边界：

- `CREATE MATERIALIZED VIEW mv AS ...` → **Parser Error: syntax error at or near "MATERIALIZED"**（DuckDB 1.5.5 无物化视图 DDL）；
- `CREATE VIEW v AS SELECT 42` → 成功，但普通视图是逻辑宏：每次查询全量展开重算，无预计算、无失效管理。
- 概念结论：市场分三层——无视图引擎（DuckDB 现状：靠管道/调度手工物化）、逻辑视图+查询改写（PostgreSQL 路线）、真物化+增量维护（Pinot/Oracle 路线）。本册服务层属第三层。物化视图的失效/一致性理论见 [../Streaming_Databases/04-物化视图.md](../Streaming_Databases/04-物化视图.md)（该册有 DBSP 理论线）。

## 本章工程判断清单

1. 团队没有专职数据工程 → Kafka Streams+服务层组合优先（运维面最小）；
2. 已有 Flink 平台 → 本册的"服务层思想"可直接移植（计算面换马不影响结论）；
3. 查询 P99 要求 <100ms 且 QPS>100 → 服务层是硬需求，不是可选项；
4. 只要 T+1 → 别上实时栈（新鲜度是成本，不是勋章）。

## 反方观点登记（保持判断力）

1. "Kafka 太重论"：Redis Streams/Pulsar/NATS 在中小场景更省——本册选 Kafka 因生态（CDC/连接器）不单因性能（⚠️ 书是否讨论未证）；
2. "服务层多余论"（云仓派）：Snowflake/BigQuery 持续缩短可见延迟，T+分钟场景可少一层——反驳点是**高并发用户面点查**的计价模型仍不适配（05.2 的账在云仓时代部分失效，诚实登记 ⚠️）；
3. "一栈到底论"（CK 派）：ClickHouse 全家桶覆盖 03-表+05-服务——宽表 upsert 与高并发点查的历史短板在收窄 ⚠️（以 https://clickhouse.com/docs 现状为准）。

## 核心概念速览（中英对照）

- **Lambda 架构** — Lambda Architecture：批层保准确+速度层保新鲜的二元结构，双码双口径是原罪。
- **Kappa 架构** — Kappa Architecture：以可重放日志统一批流，流是唯一真源。
- **服务层** — Serving Layer：面向终端查询的实时存储+计算层（Pinot 位）。
- **库式处理器** — Library-based Processor：Kafka Streams 形态，处理逻辑嵌应用进程。
- **集群式处理器** — Cluster-based Processor：Flink/Storm 形态，独立运行时与资源面。
- **物化视图** — Materialized View：预计算并持久化的查询结果，可增量维护。
- **逻辑视图** — Logical View：查询时展开的宏，无预计算（DuckDB 🔧 实证缺口语法）。
- **Schema 契约** — Schema Contract：组件边界上的模式治理约定。
- **新鲜度 SLO** — Freshness SLO：以数据年龄为承诺的服务等级维度。
- **专用 OLAP 引擎** — Purpose-built OLAP Engine：为实时聚合查询定制的引擎（对位通用数仓）。
- **旁路冷路径** — Cold Path via Lakehouse：实时层保留重历史与再计算的湖仓出口。
- **数据年龄** — Data Age / Lag：查询结果反映"多早以前"的事实。
- **运维面** — Operational Footprint：架构引入的部署/升级/值守成本总和。

## 最新演进与工业实践

- 2023→2026 栈位移：流式总线 Kafka 与实时 OLAP（Pinot/Druid/ClickHouse）进一步解耦，"处理层薄化、服务层厚化"与本册判断一致（⚠️ 趋势转述）。
- Kafka Streams 现状：随 Kafka 4.x 演进，docs ✅ https://kafka.apache.org/documentation/streams/ （curl 200）；状态存储仍 RocksDB 本地盘路线。
- Pinot 社区：第三/四代包含服务端实例弹性与租户隔离演进 ⚠️（未逐条实证），官方文档 https://docs.pinot.apache.org/ ✅200。
- ClickHouse 的实时分析抢位：半结构化解析 + 物化视图增量链使其可覆盖部分 Pinot 场景 ⚠️ 转述，官方 https://clickhouse.com/docs ✅200；盘上无 ClickHouse 单文件（00 §4.2 登记）。
