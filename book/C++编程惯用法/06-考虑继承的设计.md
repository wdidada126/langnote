## 核心概念速览（中英对照）

- **为继承而设计，否则禁用继承** — design and document for inheritance, or prohibit it：本卷时代已成型的设计军规
- **模板方法** — Template Method：算法骨架钉死在基类非虚函数里，步骤留虚钩子——1993 框架的心脏瓣膜
- **NVI（非虚接口）雏形** — Non-Virtual Interface idiom：public 一律非虚、virtual 一律受保护；
  正式定名归 Sutter 的 GotW 专栏（⚠️ 期号未核），机制雏形在本卷语境已齐
- **钩子** — hook（virtual hook）：受保护虚函数=派生类唯一合法定制点
- **开闭原则** — open-closed principle：对扩展开放、对修改关闭（Meyer 1988 提出，1993 框架文献的宪法）
- **里氏替换** — Liskov Substitution Principle：子类型必须可替换（Liskov 演讲 1987/论文 1994，
  ⚠️ 本卷成书窗口内该原则尚未成文发表——引用时勿安在本书头上）
- **不变式守护** — invariant guardianship：公开流程非虚 ⇒ 派生类无法绕过前置/后置检查
- **客户循环** — client of the hierarchy：派生类作者也是基类作者的客户——设计对象是"未来的陌生人"
- **框架 vs 类库** — framework vs class library：控制反转归框架；框架强迫你按它的形状思考（详见 08 复用章）

## 一、动机：继承是把双刃剑，本章教"剑鞘"

04/05 章讲机制，本章讲**纪律**：一旦类允许被公有继承，基类就背上了对"所有未来派生者"的承诺。
1993 年的综述给出的核心洞察可以压成一句：**虚函数是公开契约的履行点，不是定制点的邀请**——
把两者在语法上分开（public 非虚壳 + protected 虚钩），流程与不变式的守护权就永远留在基类手里。
这正是后来 Sutter 命名 NVI 时总结的结构；本卷的史料价值在于它在 1993 就以成型姿态出现，
比"设计模式"（1994 GoF）与 NVI 定名都早。

## 二、机制：壳-钩结构的语法效应（🔧 实测）

🔧 实测样本 04_nvi.cpp（g++ 15.2 -std=gnu++23 -O0 -Wall，完整实录）：

```cpp
class Process {
public:
    void run() { if (pre()) { doWork(); post(); } }   // 客户唯一入口：非虚，流程焊死
    virtual ~Process() = default;
protected:
    virtual bool pre() { return true; }
    virtual void doWork() = 0;
    virtual void post() { std::puts("post: default"); }
};
class Job : public Process {
protected:
    void doWork() override;  void post() override;
};
```

```text
doWork: real job
post: job-specific
doWork: real job
post: job-specific
```

- `j.run()` 与 `Process& p = j; p.run()` 都先入基类壳：派生者**无法**在流程前后塞私活（`pre/post` 是
  protected，客户代码摸不到）——当年注释里写"pre 之后才许改状态"的契约，从此有语法 enforcement。
- 1993 版写法与 Sutter 版 NVI 的差距只剩两点：钩子当年常留 public（靠文档要求别直调），
  以及拷贝语义未标配（后来推成 `protected` 拷贝 + public 虚 `clone`）。
- 机制根在对象模型：vptr 逐层切换 ⇒ 基类壳里调钩子打到派生实现（构造期除外——04 章已述）。

## 三、权衡

- **锁流程 vs 留逃生门**：NVI 把派生者限制在"填步骤"里；真需要重排流程的合法派生怎么办？
  当年答案：把它需要的不变式并入钩子契约。今天答案：要么你根本不该用继承（改组合/策略注入）。
- **每钩一虚的开销**：壳→钩两连跳（壳可内联、钩必虚）；非热路径无所谓，框架主循环里这是 NVI 的
  已知批评点——现代对策是对可证明的叶子类 `final` 让编译器去虚化。
- **文档负担没消失**：线程安全约定、钩子调用序（"post 可能在异常路径不被调"）仍要写——
  语言到今天也没把"类对派生者的契约"做成可检查类型（C++26 `reflection`/contracts 在途，⚠️ 前景不保证）。

## 四、相邻概念对比

| 手法 | 定制点位置 | 流程守护 | 失败模式 | 本章态度 |
| --- | --- | --- | --- | --- |
| 全 public 虚函数群 | 任意覆盖 | 无（客户可绕过直调钩子） | 覆盖即破不变式 | 否决 |
| 模板方法 + protected 钩 | 步骤 | 有 | 钩子契约文档化不足 | **推荐** |
| 策略注入（组合+函数对象） | 换整个部件 | 有（部件契约） | 类型集封闭 | 推荐（单方法接口优先；见 🔧 06 实测：`std::function` 32 字节免 ABC 树） |
| CRTP/policy | 编译期 | 编译期检查 | 报错可读性 | 推荐（封闭类型集） |
| `variant` + `visit` | 无派生 | 穷尽检查 | 加类型改所有访问者 | 封闭代数首选 |

## 最新演进与工业实践

- **NVI 的正式化与传播路径**：Sutter《Exceptional C++ / More Exceptional C++》的 "Virtuality"
  系列文章（⚠️ 具体期号与卷次未在此复核，按公开文章引用）把它命名为 NVI；C++ Core Guidelines
  **C.128 "当设计基类时，把虚函数设为 private"**（比 protected 更进一步：钩子由友元式非成员壳调用）与
  **C.129 "派生类不得重定义继承来的非虚函数"**（https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines ）
  ——本章纪律在准则层的两条落点，规则号已核实。
- **Google Style 的裁决**：其风格指南要求基类文档**逐函数**声明线程安全与可覆盖性约定
  （"文档化类的线程安全性/继承约定"），即准则 R/I 族条款；对当年"public 虚钩是否可直调"的争论，
  工业裁决是：公开面一律非虚，能 private 就 private。
- **fmt / abseil 样本**：fmt（https://github.com/fmtlib/fmt ）的 `buffer_appender`/格式化器体系几乎不用
  虚钩（编译期注入），abseil 的 `absl::Status`/`Cord` 类以"不可继承 + 值语义"为默认——
  两者代表本章论点的两种现代分流：**要么把定制点上移到类型参数，要么直接关掉继承**。
- **模式书的同题重写**：模板方法在模式谱系的 2020 年代形态见
  [../C++20设计模式/14-模板方法与访问者.md](../C++20设计模式/14-模板方法与访问者.md)；
  策略化分流见 [../C++20设计模式/13-状态与策略.md](../C++20设计模式/13-状态与策略.md)。

- **两条现代分支的实测注脚**：🔧 04_nvi 样本里客户只能通过 `run()` 进入流程（`pre` 编译期不可见）；
  而 🔧 06_callback 样本显示"单钩子"场景下整个 ABC 层可以被一个 `std::function` 参数替换——
  两条证据合起来就是本章的现代裁决：**钩子多于一个、且流程有不变式**时 NVI 仍是正解，
  否则请让位给闭包注入。

## 常见误区与自查

1. 把 NVI 念成"所有函数都要虚壳转发"——只锁**有不变式的流程入口**；平凡访问器无需双层。
2. 钩子设 protected 却让客户通过派生类公开继承再"顺手 public 化"（`public Base::pre;`）——
  纪律回到文档层，防弹衣被自己拆了。C.128 的 private 化正是为堵这条路。
3. "设计给继承"=多留 public 虚函数——恰恰相反：少而精的封闭钩子集才是好继承面。
4. 自查：翻出你库的某个 public 虚函数，回答"派生者覆盖它后基类哪些不变式失效"——
   答不出，就先把它收进非虚壳。
