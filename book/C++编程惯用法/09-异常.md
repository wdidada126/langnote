## 核心概念速览（中英对照）

- **异常安全（前史）** — exception safety（pre-history）：1993 的问题清单="抛出后资源漏不漏、对象碎不碎"，
  但"RAII/基本保证/强保证"词汇表还没发明（词源见下文演进节）
- **动态异常规范** — dynamic exception specification：`void f() throw(A,B);`——违约调 `unexpected()` 再
  terminate；运行期惩罚、零编译期承诺，本书时代的招牌歧途（🔧 实测其死刑执行日）
- ** terminate 悬崖** — terminate on violation：规范外抛出或 `throw;` 无在传异常时——直接终止；当年"异常策略"
  争论的核心恐惧源
- **展开期泄漏** — leak during unwinding：栈展开只调**已构造局部对象的析构**——裸 new + 后抛 = 漏；
  当年用 try/catch+手工清理对抗，即 RAII 的反面教材需求
- **析构不抛** — destructors must not throw：1993 已确立的军规（展开中二次抛出=terminate 的路径）
- **错误码 vs 异常** — error codes vs exceptions：贯穿全书年代的路线战争；今天的裁决是"分层并用"
- **零成本异常模型** — table-driven/zero-cost EH：正常路径零插桩、代价搬到二进制体积与抛出路径——
  当年"异常慢"论断的现代修正版
- **noexcept 时代** — the noexcept era（现代对照）：违约即终止、**编译期可查询**、参与重载与容器策略——
  与旧规范的"运行期打小报告"性格相反
- **异常被拒的工业带** — exception-free zones（现代对照）：Google/Chromium 等禁用异常形成另一支柱
  （错误码/`Status`/`expected`）

## 一、动机：新武器的心慌期

1993：异常处理刚随 ARM/早期编译器落地（cfront 3.0 带异常，但大量团队从未用过），
社区心慌集中在：性能（"每个 try 都插桩？"）、可维护性（"哪层 catch？"）、以及和 C 库/编译器
混编时的展开不可知。本章主题的综述姿态是典型的"技术恐慌期文献"：
问题意识全对（资源、语义、分层），给出的语言工具答案（throw 规范、catch-all 纪律、
手工清理模板）则大面积退役。**读它请配合 03 句柄章**：那才是当年对抗展开期泄漏的半支杠杆——
另一半（RAII 的系统化）要等 Meyers 1995/96 命名。

## 二、机制：旧规范为什么注定失败（🔧 实测双联）

**旧写法（1993 语境，🔧 示意）**：

```cpp
void deposit(double amt) throw(InsufficientFunds, Overflow); // 看起来=接口文档的机械化
```

三个致命机制事实，1993 年只看清了第一个：

1. **违约成本在运行期且无退路**：抛出列表外类型 → `unexpected()` → 默认 terminate。
   文档型断言被伪装成类型系统成员；泛型（调用者可能是模板）里根本无法写全列表——
   这两条足以判死刑。
2. **它不表达"不抛"的承诺强度**，而 noexcept 表达且**编译期可查**。
3. **它妨碍复用层次组合**：包装函数要"透传"下层异常就得重抄列表——维护假契约。

🔧 实测语言清算（02b，g++ 15.2）：

```text
$ g++ -std=gnu++98 -c 02b.cpp     → 编译通过（当年合法）
$ g++ -std=c++17  -c 02b.cpp
error: ISO C++17 does not allow dynamic exception specifications   ← P0003 移除（C++11 已弃用）
```

🔧 实测 noexcept 的现代性格（02，完整实录）：

```text
is_nothrow_move_constructible<MoveNoexcept>=1
is_nothrow_move_constructible<MoveMayThrow>=0
漏 noexcept: 搬移3个元素期间拷贝次数=3
caught: g
```

`vector` 扩容搬移元素时用 `move_if_noexcept`：**移动构造没标 noexcept 就整批退化为深拷贝**
（实测拷贝计数 3）。"异常声明"从运行期小报告进化成编译期策略输入——两代机制的性格差异，
这一个样本讲透。

## 三、权衡

- **抛出点 vs 返回点检查**：异常把"错误路径"从返回值走廊挪到旁路，正常代码干净，代价是
  控制流隐式——函数任何一行都可能离开；配套纪律（哪些错误值得抛、边界处转换）1993 没有答案，
  今天也没有统一答案（见演进节的"分层并用"）。
- **展开 vs 终止（`-fno-exceptions`）**：禁用异常确实省体积、稳定控制流——Google 系路线的技术根；
  但析构仍要 noexcept（C++11 起默认即是），1993 "析构别抛"军规被语言直接写死。
- **异常与对象生命周期**：本章与 02/03 章的真正交汇点——半构造对象与展开期析构的组合，
  在 RAII 出现前是纯粹的勇气测试。

## 四、相邻概念对比

| 机制 | 检查时机 | 违约后果 | 可组合性 | 命运 |
| --- | --- | --- | --- | --- |
| 错误码 | 调用点（可忘查） | 静默传播 | 高（C 通用） | 存活（边界层） |
| `throw(A,B)` | 运行期 | `unexpected`→terminate | 差（透传重抄） | C++17 移除 🔧 |
| `noexcept` | 编译期 | 违约直接 terminate | 参与容器/策略决策 🔧 | 现役 |
| `std::expected<T,E>` | 类型层 | 强制处理 | 高 | C++23 现役 |
| 资源清理 | 析构（RAII） | —— | 与前三正交 | 现役第一杠杆 |

## 最新演进与工业实践

- **规范史（提案号已核 wg21.link 通行说法）**：动态异常规范 C++98 原生 → C++11 弃用
  （`noexcept` 同期进场）→ **P0003R2 于 C++17 移除**。`noexcept` 语义/操作数见
  https://en.cppreference.com/w/cpp/language/noexcept_spec 。
- **异常安全词汇的真正出处（诚实标注）**："基本保证/强保证/无抛保证"分级出自 **David Abrahams**
  的系列文章与 Boost 实践（1999–2001 年代，⚠️ 具体篇目年份此处未逐一复核），
  **不是本卷（1993）的产物**——MEC++（1996）的 swap-and-swap 提交式与"落地缓冲"分析
  （[../More_Effective_C++/03-异常.md](../More_Effective_C++/03-异常.md)）才是中文世界最熟的同期系统化。
- **Google Style / abseil 的裁决**：Google 风格指南长期禁止在内部代码使用异常
  （https://google.github.io/styleguide/cppguide.html "Exceptions" 节），其工程答案=错误码的强类型化：
  `absl::Status`/`StatusOr`；Chromium 同源。这条"异常拒绝带"与 ISO 主流并行存在，
  正是本章当年"要不要用异常"争论的组织化终局。
- **`std::expected`（C++23，P0323 线）**：类型系统裁决"可能失败的函数"——可移动、可组合
  （and_then 单子链）、零展开成本；边界层转换（异常↔expected）成为新分层艺术。
- **零成本展开器现状**：Itanium `.eh_frame`/SEH 表驱动（正常路径无插桩）+ 抛出路径较慢 +
  二进制体积税——当年"异常慢"的三个成分各自有各自的答案（见
  [../深度探索C++对象模型/07-站在对象模型的尖端.md](../深度探索C++对象模型/07-站在对象模型的尖端.md)、
  [../C++并发编程实战2/00-总览与阅读地图.md](../C++并发编程实战2/00-总览与阅读地图.md) 同波次的现代叙述）。
- **GSL 接管**：不可恢复的契约违反（前置条件）→ `Gsl::Expects` 快速失败，与"可恢复错误→异常/expected"
  分层并用——1993 混合在一条"异常策略"横幅下的问题被拆成三个工具（https://github.com/microsoft/GSL ）。
- **fmt 侧证**：fmt 默认 `FMT_THROW`（异常型 `format_error`）但编译开关 `FMT_EXCEPTIONS=0`
  可切终止/错误码路线（⚠️ 选项名以当前版本文档为准）——一线库同时供两条路线的工业活样本。

## 常见误区与自查

1. 给新代码写 `throw(...)`——编译器直接拒绝（🔧 实测）；"文档化可抛类型"请用 `noexcept` + 注释 + 概念约束。
2. 移动构造"应该"隐式 noexcept——**不会**（🔧 实测退化拷贝=3）；显式写，或用 `std::is_nothrow_move_constructible_v` 做 CI 断言。
3. 析构里 try/catch 吞异常当"安全"——吞错与 terminate 二选一时，先问对象还允许存在吗；标准答案是析构 `noexcept`，
   错误路径外置。
4. 自查：把你代码库的一个热循环加 `try` 再测吞吐——体验"零成本"一词的准确含义（成本在哪一列）。
