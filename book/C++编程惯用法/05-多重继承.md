## 核心概念速览（中英对照）

- **多重继承** — multiple inheritance (MI)：一个派生类同时继承多个基——实现复用与接口合成的双刃剑
- **菱形继承** — diamond inheritance：两路共同祖先导致的二义与两份子对象问题，MI 的标志事故形
- **虚基类** — virtual base class：声明"这条路上共享唯一祖先子对象"；共享靠运行期间接层买
- **二义性** — ambiguity：两基类同名成员/隐式转换路径等长，编译期报、链接期不救
- **接口类** — interface class：纯虚 + 无状态的基类；MI 的安全子集（1993 已具雏形的裁决）
- **混入** — mixin（后起之名，当时以 "class parameter" 等词出现）：以 MI 附加正交小能力（可计数/可串接流）
- **vbptr/vbtable** — virtual base table（MSVC 术语；Itanium 用 vofflist）：运行期定位虚基子对象的间接账本
- **构造合并顺序** — construction order：虚基由**最终派生类**直接构造、先于一切——绕过中间层的惊喜源
- **this 调整** — this adjustment/thunk：跨路转换指针时的偏移修正——🔧 实测两路 `Base*` 不同址

## 一、动机：为什么 1993 值得一整章讲 MI

MI 在 ARM（1989）才正式成文，cfront 3.0 时代实现坑遍地；同时期的框架潮流（Application Framework、
多库拼装）又强烈渴望"一个类同时是 Streamable + Persistable + Observable"。
本卷单列 MI 章的动机即：**把新语言的锋利工具用法与禁区分开讲**——哪些 MI 是真需求
（接口合成），哪些是设计失误的美化（把实现依赖藏进继承），哪些布局后果（二义/切片/大小）
编译器根本不会替你兜底。这是 1993 年少见地"以机制而非宣传口径"谈 MI 的文本形态。

## 二、机制：钻石的两种摆法（🔧 实测全录）

🔧 实测样本 03_mi.cpp（g++ 15.2 -std=gnu++23 -O0 -Wall，完整实录）：

```text
sizeof(Base)=16 sizeof(L)=16 sizeof(R)=16 sizeof(Diamond)=40
sizeof(VL)=32 sizeof(VR)=32 sizeof(VD)=48
非虚钻石: 两份 Base 子对象? 两个 Base* 不同址=1 (L路=...f6a0 R路=...f6b0 &d=...f6a0)
虚钻石: 共享唯一 Base, 两路同址=1
虚基偏移(vbtable 间接层): 32 字节
```

读账：

1. **非虚钻石**：`Diamond` 里躺着**两份** `Base`（40 = 16+16+4w 的布局账），
   `static_cast<L*>(&d)` 与 `static_cast<R*>(&d)` 得到**不同地址**——`d` 的 `Base` 视图有两个，
   经谁调用虚函数就是两个对象的故事；`Base b(d);` 直接编译报错（哪一份？）。
2. **虚钻石**：`VD` 共享唯一 `Base` 子对象，两路指针同址——语义修复。但每个虚继承子对象从 16 涨到 32
   （多了到虚基的间接账本），`VD` 48 字节里还要容下偏移 32 处的虚基本体；
   对虚基成员的每次访问都要先查这层表（Itanium 经 vofflist / MSVC 经 vbptr→vbtable，两家的表见互链）。
3. **构造顺序**：`VD` 构造必须先直接构造共享的 `Base`（`VL/VR` 对 `Base` 的构造说明被跳过）——
   中间层"我以为我初始化了它"是经典心智坑。

## 二点五、案例讨论：虚基类的构造"被抢答"

```cpp
struct Base { int v; Base(int x=0) : v(x) {} };
struct VL : virtual Base { VL() : Base(1) {} };        // ① 这两处对 Base 的构造说明
struct VR : virtual Base { VR() : Base(2) {} };        // ② 在 VD 面前全部作废
struct VD : VL, VR { VD() : Base(3) {} };              // ③ 唯一说话的人
```

构造 `VD` 时 `Base::v == 3`——**最终派生类直接构造共享虚基，中间层被静默跳过**（Itanium/MSVC 一致）。
"静默"是本案的刀口：若 `VD` 忘了写③，则虚基走默认构造（`v==0`），中间层①②里明明写了、也编译通过的
初始化参数**一个都不执行**，且没有任何一行诊断。1993 年代该行为被反复列为"MI 章必须单开一节"的
头号理由；今天它仍是面试高频与真实事故源（虚基+带参构造+忘记最派生转发）。派生教训：**虚基类尽量
只有默认构造**，让"谁构造共享祖先"在结构上不可能出错。

## 三、权衡

- **虚基类税**：省掉一份子对象与二义，代价是每个相关对象 +16 字节量级的间接账本 + 每次访问多两跳 +
  构造语义变复杂。1993 至今的工程共识因此成形：**能不用虚基就不用；要共享祖先请改设计**
  （把共同状态往下推成组合，或把共同行为抽成接口）。
- **MI 的安全带**：接口类（纯虚、零状态）参与钻石**没有数据共享问题**——多份基指针只是同一 vptr
  的不同入口；"一个带实现的基 + 若干接口"是当年给出、至今有效的构型。
- **动态类型 vs 静态二义**：`dynamic_cast` 在 MI 格上找唯一最派生路径（歧义则回空指针）——
  RTTI 是 MI 时代补出来的和解机制（见深度探索 07 章），这个因果值得记住。

## 四、相邻概念对比

| 需求 | 1993 的 MI 解 | 现代更优解 |
| --- | --- | --- |
| 一个类多种"身份" | 多接口 MI | 仍 MI（接口类），或 concept 约束的自由函数族 |
| 复用多份实现 | 多实现 MI + 虚基 | 组合 + 委托（转发薄壳）；CRTP 堆叠 |
| 共享公共数据 | 虚基类 | 共享指针成员/依赖注入；虚基退居二线 |
| 类型可扩展拼装 | class parameter 思想 | 模板 policy 类（Loki 路线，MEC++ 补编有谱系） |
| 双分派 | 双继承树 visitor | `std::variant` + `visit`（编译期穷尽检查） |

## 最新演进与工业实践

- **语言没有淘汰 MI，只是圈养**：C++26 前无移除议题；`final`、`override`、`[[nodiscard]]` 降低
  MI 事故率；C++23 的 deducing-this 主要利好 CRTP 路线从而**减少**为复用而 MI 的动机（⚠️ 影响判断为综述口径）。
- **Google Style / abseil 的裁决**：Google 风格指南对 MI 的现行条款是"允许，但当多个基类同时携带
  实现时要极其谨慎，推荐只带一个实现基"（措辞按该指南"Multiple inheritance"节，引用前请复核原文）；
  Chromium 口径更紧。abseil 公共 API 中多继承罕见，身份合成让位于值类型 + 自由函数。
- **标准库的示范**：`std::istream` 单链 + `iostream` 虚继承 `std::ios_base` 家族（`ios` 为虚基）
  是标准库里唯一著名的虚基案例——教科书常引；而异常体系 `std::runtime_error` 等单链，说明"接口多身份"
  在库里也用**少层单继承**解决。对照 [../C++标准库/09-正则表达式与IO流.md](../C++标准库/09-正则表达式与IO流.md)。
- **布局账本的两家对照**：MSVC vbptr/vbtable 与 Itanium vofflist 的实测差异见
  [../深度探索C++对象模型/08-专题-现代编译器视角Itanium与MSVC.md](../深度探索C++对象模型/08-专题-现代编译器视角Itanium与MSVC.md)
  ——本目录实测在 g++（Itanium 风格）上做，换 MSVC 具体数字会变、机制结论不变。
- **经典文献（核实口径）**：Stroustrup 在 HOPL-II《The Evolution of C++》
  （http://www.stroustrup.com/hopl2.html）亲述 MI/虚基类进入语言的设计争论——
  比任何二手转述权威；本卷与之对读即得"设计意图 vs 工程用法"双拼。

## 常见误区与自查

1. "虚继承修好了钻石"——它修的是**语义**（唯一子对象），收的是**性能与复杂度**税；不是免费午餐。
2. 两个都带数据的基类做 MI 而不用虚基，常是"把依赖关系画成继承"的设计病——先问 is-a，再问 has-a。
3. `Base*` 两路不同址（🔧 实测）意味着把 `Base*` 当对象身份键（如放 set 去重）在多路体系下会分裂。
4. 自查：画出你项目里最深的继承树，数数其中几层真需要"实现继承"——1993 章末反思题的 2026 复刻版。
