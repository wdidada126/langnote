## 核心精讲

### 1. 机制卡片（✅ 直引官方页）
> 每个表的数据被切成 **micro-partitions（典型 50–500MB 未压缩）**，列式存放；每个分区为每列维护
> min/max 等统计，存于托管元数据层；**用户不定义也不维护分区键**——布局问题被平台"没收"了。
> —— https://docs.snowflake.com/en/user-guide/tables-clustering-micropartitions ✅200
> 表结构总览页 ✅ https://docs.snowflake.com/en/user-guide/tables-micro-partitions

推论（转述 ⚠️）：
- 裁剪（pruning）= 查询谓词与分区值域求交，交空即跳过；因此**过滤列与物理写入顺序的对齐度**
  就是性能的第一因（第 4 章聚簇是对它的持续修复）。
- DML 会重切分区：UPDATE/DELETE/MERGE 使局部有序性随时间**熵增** → 聚簇健康度会退化。
- 教科书镜像：分区/聚集索引的"布局即查询习惯"命题 →
  [../数据库系统概念6/10-存储和文件结构.md](../数据库系统概念6/10-存储和文件结构.md)、
  [../数据库系统概念6/11-索引与散列.md](../数据库系统概念6/11-索引与散列.md)。

### 2. 统计与自动 ANALYZE（转述 ⚠️）
列统计自动维护（`AUTO_ANALYZE` 参数可关 ⚠️），供优化器估卡；裁剪用值域、优化器用直方图，两套
消费者共享同一元数据。✅ https://docs.snowflake.com/en/user-guide/querying-top-k-pruning-optimization
（2026 文档已把 **Top-K pruning** 列为独立优化：`ORDER BY … LIMIT n` 场景用分区级界值直接跳。）

### 3. 装载顺序工程（转述 ⚠️ + 方法论）
```sql
-- 教学示意，非书中原文
COPY INTO orders FROM @stage/file.csv
  ... ;  -- 上游先按 (order_date) 排好，或
INSERT INTO orders SELECT * FROM staging ORDER BY order_date;  -- 装载即聚簇
```
进阶清单：谓词列画像（取高频过滤列组合）→ 装载 ORDER BY 对齐主组合 → 观察聚簇退化（第 4 章）→
决定是否上显式 CLUSTER BY。**能靠顺序解决的不要花钱聚簇**（转述 ⚠️）。

### 4. 小文件与合并（转述 ⚠️）
过碎的源文件/过小批次摄入 → 微分区装不满 → 值域变宽且数量爆炸 → 裁剪与元数据双侧受损。
官方装载最佳实践的"凑批"建议 ✅ https://docs.snowflake.com/en/user-guide/data-load-overview
（经索引 200 抓得）与第 8 章 Snowpipe 连续摄入的对读：连续性与文件尺寸的权衡主场。

### 5. 🔧 本地镜像实验（DuckDB 1.5.5，**非 Snowflake 行为**）
命题：物理有序度决定值域裁剪收益。方法：4,000,000 行合成表（`d_days∈[0,730)`），
同一数据分别以 **按 d_days 排序** 与 **全随机** 两种物理顺序写成 Parquet
（row_group_size=122880，≈33 个 row group≈"微分区"），跑同一 range 谓词
`WHERE d_days BETWEEN 100 AND 104`：
| 布局 | 用时（🔧实测） |
| --- | --- |
| 有序 | **5.7 ms** |
| 乱序 | **12.6 ms（2.2×）** |
机制读法：有序文件中命中 row group 的 min/max 高度重叠查询区间，其余被统计跳过；乱序文件每个
row group 值域都覆盖全区间 → 裁剪全灭、退化为全扫。`parquet_metadata()` 可人工检查每组 min/max
（实验脚本与结果 JSON：`D:\develops\tmp\dbwave_w4_advshk\experiments.py / experiments_result.json`）。
注意：Parquet row group ≠ micro-partition（尺寸、元数据归属、维护者都不同），此实验只类比
**"值域覆盖→裁剪失效"** 这一条因果链。

## 常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "没有分区概念所以不用管布局" | 布局以"装载顺序+聚簇键"的形式回来找你 |
| "微分区越小裁剪越准" | 过碎→元数据与打开开销反噬，50–500MB 是平台平衡点 |
| "UPDATE 不影响性能" | DML 破坏局部有序性，聚簇健康度随时间退化需监控 |
| "列统计是给 DBA 看的" | 优化器估卡与裁剪共用，AUTO_ANALYZE 关掉是伤敌八百 |
| "压缩只影响账单" | 压缩改变分区实体尺寸，间接影响裁剪粒度与 I/O |

## 核心概念速览（中英对照）

1. **微分区** — micro-partition：50–500MB 未压缩的自动列式存储单元，裁剪基本粒度。
2. **分区统计** — partition metadata：每分区每列 min/max 等值域，托管元数据层的货币。
3. **数据裁剪** — pruning：谓词×值域求交跳过无关分区；扫描量的第一决定因素。
4. **Top-K 裁剪** — Top-K pruning：为 ORDER BY+LIMIT 用分区界值直接跳的新式裁剪 ⚠️。
5. **装载顺序** — load ordering：COPY/INSERT 物理顺序=Day-1 聚簇质量。
6. **熵增退化** — clustering degradation：DML 破坏局部有序性，健康度随时间下降（转述 ⚠️）。
7. **小文件问题** — small-file problem：碎分区使裁剪与元数据双侧受损。
8. **列压缩** — columnar compression：微分区按列压缩；同一列同型数据红利最大。
9. **AUTO_ANALYZE** — 自动统计维护开关：优化器估卡的供给侧 ⚠️。
10. **row group**（🔧类比物）：Parquet 的物理分组，本实验借它镜像微分区的统计裁剪。
11. **值域覆盖** — overlapping ranges：乱序布局的病理学名词，裁剪失效的直接原因。
12. **SARGable 谓词** — 可参与裁剪的谓词形态：列上无函数、无隐式类型转换。
