## 核心精讲

### 1. 聚簇机制与键选择（转述 ⚠️）
> `CLUSTER BY (k1, k2…)` 声明后，平台自动增量重排（automatic reclustering），把表向"按键值域
> 分层不重叠"的理想态收敛；无需（也不应）人工 RECLUSTER——手动命令在文档中已标记 **Deprecated**。
> —— ✅ https://docs.snowflake.com/en/user-guide/tables-clustering-keys
> ✅ https://docs.snowflake.com/en/user-guide/tables-auto-reclustering
> ✅（弃用标记实证）https://docs.snowflake.com/en/user-guide/tables-clustering-manual
键选择方法论（书中惯用框架的重述 ⚠️）：
- 取**过滤谓词最高频的列**；等值列在前、范围列在后；
- 键列基数与查询组合数决定"理想态分区数"，**键不是越多越好**（组合爆炸→维护费↑）；
- 频繁更新/低选择率列慎入键（重排 churn 大）。

### 2. 健康度诊断（转述 ⚠️）
```sql
-- 教学示意，非书中原文
SELECT SYSTEM$CLUSTERING_INFORMATION('ORDERS','(order_date,region)');
SELECT SYSTEM$CLUSTERING_PERCENTAGE('ORDERS');   -- 整体命中一数值 ⚠️
```
✅ https://docs.snowflake.com/en/sql-reference/functions/system_clustering_information
读法：`total_partition_count` 相对理想值膨胀=重叠恶化；`stable/histogram_depth` 浅=重排跟不上；
诊断视图侧对应 `INFORMATION_SCHEMA` / ACCOUNT_USAGE 的 clustering 系历史视图（⚠️ 转述）。

### 3. 搜索优化服务（转述 ⚠️）
聚簇解决"范围大扫描"，**搜索优化解决"点查与包含查询"**：对声明列维护托管结构，
`WHERE col = ?`、`CONTAINS`、`LIKE '%x%'` 类谓词受益；存储按索引字节计费，DML 有维护费。
✅ https://docs.snowflake.com/en/user-guide/search-optimization-service
✅ https://docs.snowflake.com/en/user-guide/search-optimization/enabling
**JOIN 加速支线（2026 文档 ✅）**：为等值 JOIN 键启用搜索优化可显著减扫描——
✅ https://docs.snowflake.com/en/user-guide/search-optimization/join-queries （与第 5 章 JOIN 策略共振）。

### 4. 物化视图（转述 ⚠️）
预聚合+自动改写；基表 DML 同步维护（消耗 cloud services credits）。判定式：
`复用率 × 单次节省 > 维护成本` 才建；低复用即亏。
✅ https://docs.snowflake.com/en/user-guide/views-materialized
✅ https://docs.snowflake.com/en/sql-reference/sql/create-materialized-view
与"动态表"（增量编排管线，第 7 章）的分工：MV=优化器改写对象；动态表=声明式增量管道。

### 5. 🔧 本地镜像实验（DuckDB 1.5.5，**非 Snowflake 行为**）
命题："物理重排把范围查询从全扫变窄扫"。4,000,000 行同数据两表：`heap_shuf`（INSERT 时随机打散）
vs `heap_sorted`（按 d_days 有序），同一 `BETWEEN 100 AND 104` 查询各跑 5 次取均值：
| 表 | 均耗时（🔧） |
| --- | --- |
| 乱序 | **3.55 ms** |
| 有序 | **1.28 ms（≈2.8×快）** |
差异全部来自数据布局，SQL 一字未改——这就是"RECLUSTER 在花什么钱"的直觉版本。

## 常见误区

| 误区 | 事实（转述 ⚠️） |
| --- | --- |
| "建表时 ORDER BY 过了就不用聚簇" | DML 熵增会把有序性磨掉，聚簇是持续过程 |
| "聚簇键越多越保险" | 键组合爆炸+维护计费，选 2–3 个高价值列即可 |
| "手动 RECLUSTER 是日常操作" | 官方已弃用手动路线；自动聚簇是唯一正解 |
| "搜索优化=给表加索引" | 它只补点查/包含/JOIN 键场景，且按字节持续计费 |
| "物化视图多多益善" | 每个 MV 都在为全量 DML 交税 |

## 核心概念速览（中英对照）

1. **聚簇键** — clustering key：CLUSTER BY 声明的重排目标列组（有优先级）。
2. **自动聚簇** — automatic reclustering：平台持续增量重排服务，按 credit 计费。
3. **手动重聚簇** — manual RECLUSTER：已弃用（⚠️✅ docs 标 Deprecated）。
4. **聚簇信息** — SYSTEM$CLUSTERING_INFORMATION：深度/重叠/分区数诊断函数。
5. **聚簇百分比** — SYSTEM$CLUSTERING_PERCENTAGE：整体健康度一数值 ⚠️。
6. **搜索优化服务** — search optimization service：点查/包含/JOIN 键的托管加速结构。
7. **索引字节计费** — per-byte index billing：搜索优化的账单形态。
8. **物化视图** — materialized view：预聚合+自动改写对象，DML 侧交维护税。
9. **谓词组合** — predicate pattern：键选择的信息源（高频等值在前）。
10. **重排抖动** — reclustering churn：键含高频更新列时的病态。
11. **改写判定式** — 复用率×节省>维护成本（MV 决策方法论 ⚠️）。
12. **动态表对照** — dynamic table：声明式增量管道，与 MV 分工不同（第 7 章）。
