# 第 3 章 Data Vault 2.0 方法论（The Data Vault 2.0 Methodology）

> 目录取证：章题与 3.1/3.2/3.3 小节题 ✅ 实抓自 Elsevier 官方 TOC。正文为精读重构；「六大关键实践」名录系 Data Vault 2.0 公开标准的一致口径，⚠️ 书中逐条措辞未核对。

## 1. 为什么方法论是模型的一部分

Data Vault 2.0 区别于 1.0 的标志之一：**模型方法论自带交付方法论**。作者的主张（3.0 语境）：再好的散列模型，若项目按瀑布式两年一期交付，照样死在源系统变更与需求漂移上。因此 DV 2.0 = 三型建模 + SDLC 3.0 敏捷框架，二者不可拆。

SDLC 3.0 的生态位（本章的业界综述口径）：
- 1.0：瀑布（RUP 前置）；2.0：Scrum/XP 等敏捷框架（不管数据侧）；
- 3.0：面向数据密集型项目的敏捷混合框架——把 Scrum 的迭代、看板的工作流、DevOps 的自动化与「数据项目特有的发布单元（工作包）」缝合起来。DV 2.0 是首批把自身方法论明确挂在 SDLC 3.0 上的数据建模法。

## 2. 3.1 项目规划（✅）

- **按业务发布价值切片**，不按模型层次切片：迭代目标是「上线两个 Hub + 关联集市可视」这类可验证价值，而非「完成概念模型」。
- **KPI 驱动的范围治理**：每个发布绑定可度量的业务 KPI（装载时窗、覆盖源数、报表响应），用 KPI 决定下一刀切哪里。
- 规划工件：项目章程、发布路线图（以「功能包 = 一组源+一组三型+一批集市」为单位）、风险登记。
- 团队结构：作者按 SDLC 3.0 给出角色划分（发布团队/项目团队两层），⚠️ 具体角色表未逐条核。

## 3. 3.2 项目执行（✅）

六大关键实践（Six Key Practices，DV 2.0 标准与本章的骨干）：

1. **Defined Business Scope（定义业务范围）**——发布围绕业务价值而非技术里程碑；
2. **Project Team / Delivery Team（项目/交付双团队制）**——项目团队管治理与范围，交付团队按 sprint 产出；
3. **Sprint-based Iterative Delivery（冲刺迭代交付）**——2–4 周一个可部署增量；
4. **Work Packages（工作包）**——每个可部署单元（一个源实体组/一个集市切片）是独立工作包，自带模板与自动化，可并行、可复制；
5. **Communication and Collaboration（沟通协作）**——每日站会 + 以模型/血缘为共同语言；
6. **Best Practices / Lessons Learned（最佳实践与复盘沉淀）**——模式库与模板库随项目生长。

执行侧的工程含义：**工作包 + 模板化 = 自动化**。一个源系统的接入被压缩成「填映射清单 → 生成三型 DDL + 装载 SQL/包 → 跑质量断言」，这正是第 12 章自动化装载（SQLDBM 的 T-SQL 生成、VanDyke 的 SSIS 框架）在方法论层的动机。

## 4. 3.3 评审与改进（✅）

- 每个发布/迭代末尾的评审不只对业务演示，还对**架构指标**：装载时窗、并行度利用率、模型漂移成本（加一列要动几个工件）。
- 复盘产物直接回写模板库（第 N+1 个工作包比第 N 个更快），把「持续改进」变成可积累的资产。
- 与数据质量章（13）、元数据章（10）咬合：评审的输入就是 Metrics Vault/Error Mart 的客观数据。

## 5. 方法论中的三个「反瀑布」设计决策

1. **模型不做全量前置**：概念级词汇表（业务对象清单）先行，三型细节随工作包滚动设计——源没接就不建。
2. **不承诺「银弹时点」**：Raw Vault 允许同实体多源记录并存（same-as 后处理，第 5/13 章），把「清洗决策」从阻塞项降级为后续工作包。
3. **发布单元即回滚单元**：工作包粒度保证任一切片可独立重发。

## 5.6 一个示例迭代的日历（重构演示，航司域）

```text
Sprint N（两周）工作包「接入 OMS 客户」:
  d1-2  词汇表对齐: OMS 的 ACCOUNT 是不是我们的 CUSTOMER?（→ 先建 Hub 保真，裁决挂 backlog）
  d3-4  映射清单: 源列→卫星分组/哈希列集（模板生成器出 DDL 草案）
  d5-7  Stage+装载: 幂等批、Meta Mart 三计数、错误原因码字典增量
  d8-9  集市切片: 一个 PIT 视图 + 一张星型维（可演示的最小价值）
  d10   评审: KPI（新源时窗/行数对账）+ 复盘条目回写模板库
```

关键点：**「先保真、后裁决」体现在 d1-2**——模型层允许悬而未决的身份问题存在（same-as 待建），交付不被治理争论阻塞；这是 DV 方法论与瀑布式数据治理最实质的差别。

## 5.7 Kimball 生命周期方法论 vs SDLC 3.0（对照，供附节讨论用）

| 维度 | Kimball 生命周期（工具箱第 3 版附录口径，转述见 [../数据仓库工具箱3.md](../数据仓库工具箱3.md)） | DV 2.0 / SDLC 3.0 |
| --- | --- | --- |
| 单元 | 线框图（lineary）→ 维度模型 → ETL → 交付 | 工作包（源×三型×集市切片） |

## 5.10 术语锚点（本章易与它书混淆的词）

- 本书「方法论」=模型法+交付法合体；Kimball 书中 methodology 仅指交付法（生命周期），模型法叫维度建模——引用时注意所指层。
- 「敏捷」在 DV 语境专指 SDLC 3.0 的发布结构，不是泛指「快」。
- 「工作包」≠ WBS 任务：它是可部署工件束（代码+映射+测试+文档），验收=上线不是完成。

## 核心概念速览（中英对照）

- **SDLC 3.0** — SDLC 3.0 Framework：混合敏捷/看板/DevOps 的数据项目交付框架。
- **六大关键实践** — Six Key Practices：DV 2.0 方法论的操作支柱。
- **工作包** — Work Package：一个可独立部署的数据交付单元（源+模型+集市切片）。
- **发布团队/项目团队** — Delivery Team / Project Team：SDLC 3.0 双层团队结构。
- **冲刺** — Sprint：固定时长的迭代单元。
- **KPI 驱动** — KPI-driven Delivery：以业务指标度量每刀发布价值。
- **模板化** — Templating：工件（DDL/ETL/测试）以模板批量生成。
- **滚动建模** — Rolling/Iterative Modeling：拒绝全量前置设计，随工作包扩展模型。
- **复盘沉淀** — Lessons Learned Capture：经验回写为模板与模式库。
- **模型漂移成本** — Drift Cost：需求变更时模型侧要动的工件量，DV 的自度量指标。
- **并行工作包** — Parallel Work Packages：多团队互不阻塞地接入不同源。
- **业务价值切片** — Value-based Slicing：按可演示价值切分范围。
- **模式库** — Pattern Catalog：DV 模式（三型/PIT/Bridge 等）的组织内登记册。
- **交付节奏** — Release Cadence：发布/迭代的固定时间节拍。

## 最新演进与工业实践

- **Data Mesh 与 DV 2.0 的兼容性争论（本节为本目录重点专题）**：2019 年后 Zhamak Dehghani 的 Data Mesh 以「去中心化的域拥有数据产品」直接挑战「中心 EDW」前提，与 DV 2.0 的核心卖点（企业级单一集成骨干）正面冲突。2023–2026 社区实践的主流调停立场大致三种：① **Mesh 管组织与契约、Vault 管单域或共享骨干的建模**（域内数据产品内部可用三型，域间以可计算契约交换）；② **把 Raw/Business/Mart 三层改造成「平台提供的自助骨干」**——中心只保平台与散列/审计契约，模型工作下放到域团队（与第 3 章「工作包+模板化」精神一致，可视为 DV 方法论自身完成了 Mesh 化改造）；③ 认为两者不可调和（Mesh 阵营常把 Vault 归为「中央 bottlenecks 的化石」，DV 阵营则指 Mesh 无解决企业级一致性的手段）。⚠️ 以上为社区论战梳理（Data Vault 大会演讲、dbt/AutomateDV 社区讨论等公开材料），非原书内容——成书于 2015 年，早于 Mesh。
- **敏捷数据工程对「工作包」的继承**：dbt 的 model + test + docs 工件束天然即工作包；CI/CD（dbt Cloud CI、GitHub Actions）实现了第 3.2 节设想的「生成+断言+重发」闭环。
- **AI 辅助建模（2024–2026）**：Scalefree 已发布 datavault4dbt 的 AI agent skills 仓库（https://github.com/ScalefreeCOM/datavault4dbt-agent-skills ，2026-09 验证可达，收录于 2026-08），把「源→三型映射」的模板工作交给 agent——方法论中「模板积累=提速」的路线在 LLM 时代的延续。
- **VanDyke SSIS 框架现状** ⚠️ 待核验：当年与本章工作包理念配套的 VanDyke（SSIS Data Vault 自动化厂商，注意 vandyke.com 实为 VanDyke Software/SecureCRT，与 Data Vault 无关，2026-09 实测确认）未再查到活跃的 Data Vault 产品线，工业重心已迁移至 dbt 系（见 [12-装载DataVault.md](12-装载DataVault.md)）。
