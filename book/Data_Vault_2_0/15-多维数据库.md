# 第 15 章 多维数据库（Multidimensional Database）

> 目录取证：章题与 15.1 Accessing the Information Mart / 15.2 Creating Dimensions / 15.3 Creating Cubes / 15.4 Accessing the Cube ✅ 实抓自 Elsevier 官方 TOC。正文为精读重构；本章平台绑定 Microsoft SSAS 2015 形态，现状修正见文末——阅读时请把它当「立方体作为集市投影」的方法论文字，而非产品教程。

## 1. 本章在全书的坐标

信息集市的最后一类消费者：需要**预聚合、钻取层级、单元格回写（write-back）**的传统分析（财务预算、经营分析会）。作者的架构回答：多维数据库（MDD/Cube）**不是又一层真相，而是星型集市之上的缓存投影**——Vault 是全历史本体、星型是关系投影、立方体是聚合投影，三者派生链单向：`Vault → Mart → Cube`。

## 2. 15.1 访问信息集市（✅）

- 立方体的数据源=第 14 章物化星型（不是视图/不是 Vault——立方体构建需要稳定扫描面，⚠️ 书中是否允许直连 PIT 未核）；
- 本节同时讲「关系型访问」（ad hoc SQL/ODBC）与「多维访问」（MDX/客户端）两类消费者的不同喂法——同一份数字、两种协议。

## 3. 15.2–15.3 建维度、建立方体（✅，SSAS 语境）

以 SQL Server Analysis Services（多维模式）为演示平台（书中版本口径 ⚠️ 约 2012/2014 代）：

- **维度**：SSAS 维度←星型维表；层级（年-季-月）、属性、序属性对齐 Kimball 维度设计（第 7 章）；时态维度经 14.4 处理后进立方体即得「任意时点钻取」；
- **立方体**：度量组←事实表；聚合（aggregations）设计=按查询画像自动+手工调优；分区（processing mode：MOLAP/ROLAG/分区按时间滚动）对应装载窗口经济学；
- **非可加与桥接**：带 Bridge 的关系（分摊/层级）在立方体中的处理（many-to-many dimension）——第 6 章 Bridge 在立方体侧的镜像难点，⚠️ 书中处理深度未逐例核。

## 4. 15.4 访问立方体（✅）

- MDX 查询、Excel 数据透视表/Reporting Services 订阅——2015 年企业报表的末代主流形态；
- 本节真正可迁移的知识：**立方体接口三件套**（成员层级导航、聚合上下文、计算单元成员=KPI 表达式），换成 2026 年的语义层/OLAP 引擎名词仍一一对应。

## 5. 架构结论（本章要点化）

1. 立方体可整层重建（投影可弃），坏了从 Mart 重刷——与 14 章「集市可重算」同构，Vault 双层架构第三次兑现「重算红利」；
2. 立方体的历史深度不必等于 Vault 深度：预聚合按保留期分层（近 13 月 MOLAP、远期回落实表），成本模型清晰；
3. 口径唯一性靠派生链保证：任何单元格争议沿 `Cube→Mart→PIT→Satellite→Stage→源` 回溯（第 10 章 Meta Mart 是回溯地图）。

## 5.5 立方体设计走查（15.2/15.3 的操作骨架，重构示意）

以订票域（第 7/14 章星型）建 Cube：

1. **数据源绑定**：FACT_BOOKING+四张角色日期维（BOOK/FLY 两套外键=两个日期角色，立方体侧以 Role Dimension 或第二度量组表达——Kimball 老问题在 MDD 里的同解）；
2. **度量组**：订票金额（可加）、客户数（半可加→ DistinctCount 聚合设计，成本警告）；
3. **维度属性**：层级（年季月/组织树）、序属性（排序≠浏览序）、属性关系（防 M2M 爆炸）；
4. **聚合+分区**：按月分区、近 13 月 MOLAP 全聚合、远期 ROLAP 直落事实表（分区经济学）；
5. **处理策略**：增量 process（分区级）+ 全量重算兜底（投影可弃的兑现）；
6. **权限**：角色→维度成员筛选（14 章出口纪律在立方体的镜像）。

## 5.6 MDX 一例与「三件套」的现代转译（15.4）

```mdx
SELECT {[Measures].[Booking Amt]} ON 0,
  NON EMPTY [Customer Tier].[Tier].Members ON 1
FROM [BookingCube]
WHERE ([Date].[Month].&[2015-06], [Flight Route].[Route].&[SHA-PVG])
```

## 5.7 立方体层要不要保留的决策（本章的最终现代化，本目录判断 ⚠️）

- 留：财务合并报表（矩阵回写+审计）、超大历史跨期聚合的固定报表群；
- 弃：交互分析主力（列存/湖直查+语义层）、数据科学消费（PIT/视图直供）；
- 共同前提不变：**任何投影都能从 Vault 重算**——15 章在全书的真正贡献不是 SSAS 教程，而是「投影链单向性」的最后一块示范。

## 5.8 立方体容量与刷新速算（15.3 的经济学，重构示意）

```text
全聚合立方体 ≈ Π(维度基数_i) × 度量数 × 8B × 稀疏折减(0.1–0.3)   ← 维度爆炸第一禁令来源
分区增量处理成本 ∝ 当期分区行数（非全史）                        ← 按月分区的理由
行聚合(ROLAP)直查 ≈ 扫描事实行数 × 列宽  ← 列存引擎下常优于「小聚合集+高并发」的 MOLAP 拐点
```

三条经验：基数最大的维（客户）先聚合「层级+父级」两档而非全叉积；时间维度永远入聚合骨架；DistinctCount 类半可加度量单独降级处理（不可预聚合→近似算法或落回明细）。这些权衡与 2026 语义层「推荐物化」算法的目标函数同构（⚠️ 本目录类比）。

## 5.9 立方体章的三句遗产（即便弃用 MDD 也应带走的东西）

1. **投影链单向性**（Vault→Mart→Cube）是一切「缓存架构」的正解模板；
2. **分区=刷新成本的基本单位**——今天叫增量物化视图/分簇回填，概念同源；
3. **单元格争议回溯协议**（15.4→14.5→10 章）：任何数字都能答「你看到的是哪个宇宙」——这比任何具体技术都长寿。

## 5.10 若仍要维护 SSAS 资产（过渡期实操，⚠️ 现状口径）

1. 处理日志接入 Meta Mart（立方体也是投影，批账不例外）；
2. 度量定义抄送语义层登记册——未来迁移 DAX/MetricFlow 时口径资产不丢；
3. 分区策略与 14 章物化窗口对齐（同源同时刻刷新，杜绝「立方体新于集市」的时间倒挂）；
4. 新需求默认走「直查+语义层」，立方体只接回写/合规豁免类——自然日落（sunset）而非硬撤。

## 5.11 立方体→直查迁移的三步拆解（重构路线图，⚠️ 经验口径）

1. **度量对齐**：把立方体度量逐个翻译为 SQL 表达式并与历史聚合值对账（容差 0）——本质是给第 14 章物化表补一套「聚合等价测试」；
2. **消费分流**：固定报表→增量物化视图；交互分析→列存/湖直查；回写类→独立规划应用（勿塞回数仓）；
3. **日落治理**：立方体转只读一季后下线，处理日志与定义归档进元数据库（第 10 章自反性收尾——投影的遗产也要可审计）。

## 核心概念速览（中英对照）

- **多维数据库** — Multidimensional Database (MDD/Cube)：预聚合的多维存储。
- **联机分析处理** — OLAP：多维钻取/切片/旋转的分析范式。
- **MOLAP/ROLAP** — MOLAP/ROLAP：立方体存储模式谱系。
- **度量组** — Measure Group：立方体内一组共享粒度的度量。
- **聚合设计** — Aggregation Design：按查询画像预计算汇总。
- **分区** — Partition：立方体按时间等切块以增量处理。
- **多对多维度** — Many-to-Many Dimension：桥接结构在立方体中的表达。
- **钻取** — Drill-down/Drill-across：沿层级或跨事实深入。
- **MDX** — Multidimensional Expressions：立方体查询语言。
- **计算成员** — Calculated Member：立方体内的 KPI 表达式。
- **单元格回写** — Write-back：预算场景写回立方体。
- **投影可弃** — Disposable Projection：立方体可整体重灌的架构属性。
- **透视表** — PivotTable：Excel 端立方体消费者。
- **SSAS** — SQL Server Analysis Services：本章演示平台。

## 最新演进与工业实践

- **SSAS 的暮色**：微软火力转向 Fabric/Power BI 的 DirectLake 与 DAX 引擎，多维 SSAS 长期无大功能投入（⚠️ 生命周期官方声明未核，判断为社区共识）；本章「立方体=聚合投影」的定位论恰好适用于 PBI 导入模式/DirectLake。
- **语义层是新立方体**：dbt Semantic Layer、Cube（cube.dev）、AtScale、LookML 提供「度量定义+按需编译聚合」，取代手工建 Cube；15.2–15.4 的成员/层级/计算概念几乎原样映射到语义层的 dimension/measure 定义（对照阅读：[../数据仓库与OLAP实践教程.md](../数据仓库与OLAP实践教程.md) 的立方体理论仍适用，变的只是物化引擎）。
- **列存引擎接管 OLAP 本体**：ClickHouse/DuckDB/Druid/Pinot/StarRocks 让「秒级大宽表聚合」不再需要立方体层；Vault→直连列存/湖仓的 BI 路线在 2024–2026 已是中小规模默认（生态通述 ⚠️；DuckDB 侧本目录有 🔧 单机体验：14 章导出宽表查询在 20 万行毫秒级，聚合直查可行性的低配证据）。
- **Data Vault × 语义层的合流叙事**：厂商文章已把「DV 骨干+指标语义层出口」作为湖仓标准拓扑之一（例：https://coalesce.io/data-insights/data-vault-2-0-the-complete-implementation-guide/ ✅ 2026-09 可达，观点转述 ⚠️ 不作背书）。
