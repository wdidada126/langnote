# 第 4 章 Data Vault 2.0 核心建模：Hub / Link / Satellite（Data Vault 2.0 Modeling）

> 目录取证：章题与 4.1–4.5 小节题（含 Hub/Link/Satellite Definition 三个定义节）✅ 实抓自 Elsevier 官方 TOC。正文为精读重构；三型契约以 Data Vault 2.0 公开标准口径书写。

## 1. 4.1 建模导论 / 4.2 建模词汇（✅）

Data Vault 模型=**面向业务键的关系图 + 时态属性壳**。词汇表先立规矩：

- **业务键（Business Key, BK）**：源系统给出的标识（客户号、保单号）；Vault 不发明全局 ID，只**记录**源的 ID（同一实体的多源 ID 靠 same-as Link 关联，见第 5 章）。
- **散列键（Hash Key）**：`HK = hash(BK)`（2.0 标准另含「多代哈希」：对「源系统名+BK」哈希得 hash key of hash key，用于 same-as/角色派生，⚠️ 书中展开深度未核）。**永远在暂存层算好再进 Vault**；禁止用哈希值做语义推断。
- **时态元数据列（每张 Satellite/Link 必备）**：`r_timestamp/load_dts`（装载时刻）、`load_end_dts`（闭区间时刻，开集为哨兵值如 9999-12-31）、`record_source`（源系统/文件/表名）。第 11 章详述。
- **只追加（Append-Only）**：Vault 表没有 UPDATE/DELETE 的合法场景（纠错亦以新记录表达，见第 13 章）。

## 2. 4.3 Hub 定义（✅）

**一个业务键的登记表。**

| 契约 | 内容 |
| --- | --- |
| 列 | `hk_hub`（PK，BK 的哈希）、`bk_hub`（原样保留）、`load_dts`、`record_source` |
| 行数 | 每个**唯一 BK** 一行（多源同 BK 塌缩为一行）；不保存任何描述 |
| 写模式 | 只插新键；已有键的再到达**不更新**（连 load_dts 都不动，新事实交给 Satellite） |
| 禁止 | 存名称/状态等描述列；存指向其它 Hub 的键（那是 Link 的职责）；复合 Hub（一表两 BK——那是 Link） |

🔧 实测（DuckDB 1.5.5，本机脚本 `dbwave_datavault2`）：CRM 与 OMS 两源各含 `C1`（tier 分别为 VIP/GOLD），按 `INSERT ... SELECT DISTINCT md5(cust_id)` 装载后 **Hub 共 3 行、C1 仅 1 行**——多源塌缩即「Hub 是键的集合而非记录的集合」的直接证据。

## 3. 4.4 Link 定义（✅）

**Hub 之间的关系（事实间的业务联系），也是业务事件的骨架。**

| 契约 | 内容 |
| --- | --- |
| 列 | `hk_link`（成员 HK 复合哈希）、≥2 个成员 `hk_*`（允许自环/可空成员——可空表达「关系尚未知」而非伪造默认值）、`load_dts`、`record_source`、（**effectivity** 属性组：`eff_from`/`eff_to` 或 active 标志） |
| 语义 | 一次关系的发生/存在；基数：1:1、1:N、N:M 皆可，**N:M 的明细在 Link 不在 Bridge**（Bridge 是集市层的展开，第 6 章） |
| Effectivity | 当关系在「同一时点只允许一个有效目标」时（客户→当前经理），Link 携带效果性：新关系到达即闭旧行（🔧 实测：C1 会籍 CLUB_1→CLUB_2 换会，旧行 `eff_to=2015-06-30` 闭合，新行开至哨兵 9999-12-31，三行并存可查询任意时点的会籍） |
| 禁止 | 存度量/描述（进 Satellite of Link）；存 Hub 才有的键语义 |

- **Satellite of Link**（关系属性的时态壳，如「保单-理赔」关系的理赔金额修订史）与 **Link Satellite 上的计算**构成 Business Vault 的规则表达面。
- Same-as Link（同实体多源键互认）、Role-play 由 Hub 派生（第 5 章）。

## 4. 4.5 Satellite 定义（✅）

**挂在 Hub 或 Link 上的时态属性集——"描述" 的唯一归宿。**

| 契约 | 内容 |
| --- | --- |
| 列 | FK=`hk_hub/hk_link`、`load_dts`（PK 之一）、`load_end_dts`、`hashed_columns`(哈希差)、描述列组、`record_source` |
| 分组原则 | 按**变更频率+语义内聚**切分（地址、联系方式、风险等级各一颗；快变慢变不混住） |
| 写模式 | 仅当**哈希差变化**才追加新行；未变化直接过滤（🔧 实测见下） |
| 禁止 | 指向其它 Satellite 的外键；指向非本父键的列；描述列里再放业务键（那暗示缺一个 Hub/Link） |

🔧 hash-diff 去重实测（DuckDB）：同一批次重放 4 行源数据 → **新增 0 行**（哈希差全等被过滤）；仅 CRM 侧 `C1 tier VIP→PLAT` → 只追加 1 行，历史 `(2015-01-01,'VIP')、(2015-07-01,'PLAT')` 并存可查。附带发现一个真实工程坑：若同一装载批次里同一 HK 有**多个不同源的行**（C1/CRM 与 C1/OMS），哈希差去重必须**按 (hk, record_source) 各自比最新**，否则批内互相误伤——这解释了为什么 `record_source` 是 Satellite 契约列而非注释。

## 5. 三型之外：Reference 表与 Payload（本章口径）

- **Reference/Lookup 表**：允许出现在 Vault 的**唯一非规范化结构**（值域表，如币种/等级定义，带标准化的 same-as 映射），定义与用法在第 6.3 节展开。
- **Payload（载荷列/表）**：低建模价值的透传字段（一长串源端宽表列），不建三型、直接落暂存/原始载荷表随行存档；社区将其列为「可选型」，⚠️ 书中是否给独立定义未核（官方 TOC 无 Payload 小节）。
- **业务关系与业务事实的分界口诀**（本章总结口径）：能画成「名词-动词-名词」的 → Link；名词的属性 → Satellite；名词本身 → Hub。

## 6. 一个完整的最小样例（贯穿多章）

航司样例（源：CRM/OMS 客户、航班、订票）：

```text
Hub: H_CUSTOMER(hk_customer, bk_customer)   Hub: H_FLIGHT(hk_flight, bk_flight)
Link: L_BOOKING(hk_booking, hk_customer, hk_flight, load_dts, record_source)
Sat:  S_CUSTOMER_ATTR(hk_customer, load_dts, load_end_dts, hd, name, tier, record_source)
Ref:  R_SEAT_CLASS(class_code, class_desc_std)   ← Reference（唯一非3NF白名单）
```

装载推演见 [11-数据提取与哈希.md](11-数据提取与哈希.md)、[12-装载DataVault.md](12-装载DataVault.md)；时态查询结构见 [06-高级建模PIT与Bridge.md](06-高级建模PIT与Bridge.md)。

## 6.6 从零建模五步（把本章规则串成流程，重构演示）

以「保险：客户投保多张保单、保单多被保人」为例：

1. **圈名词**：客户/保单/产品/代理人 → 4 个 Hub；「投保」事件 → Link(customer, policy)；
2. **分属性**：客户（姓名地址=慢变卫星 A；风险评级=快变卫星 B）；保单（保额=随修订变化→保单卫星）；
3. **判关系**：被保人≠投保人 → Link 角色成员×2（同一 H_CUSTOMER 两槽位，Role Play）；
4. **定效果性**：「当前服务代理人」唯一 → Link 带 eff；「保单多被保人」同期可多 → 多活跃（关 eff，第 5 章）；
5. **留缺口**：源系统还没给的键 → 可空成员 + same-as backlog，**不造默认值**。

## 6.7 FAQ（本章高频疑问，本目录整理）

- **Q：Hub 为什么不能带属性？** 任何属性都可能变，而 Hub 的契约是「键永不再写」——属性进卫星才能既保键稳定又保历史。
- **Q：散列键撞了怎么办？** 概率见 11.2 生日界；工程答案是「HK 旁必留 BK 列」，冲突可检出可解释，且查询永不依赖「哈希=身份」的哲学承诺。
- **Q：为什么不直接用复合自然键 JOIN？** 多源复合键宽度不齐、类型漂移、NULL 语义混乱；哈希把 JOIN 列规范成定长单列——这是第 2 章并行装载的前提。
- **Q：三型会不会表太多？** 会。这是用「表数量」换「变更局部性」的显式交易（附节 §3 的成本讨论）。

## 核心概念速览（中英对照）

- **枢纽表** — Hub：单一业务键的登记表，不含描述。
- **链接表** — Link：Hub 间关系/事件的骨架，可带效果性。
- **卫星表** — Satellite：Hub/Link 的时态属性壳，仅哈希差变化才追加。
- **业务键** — Business Key：源系统给的标识，Vault 忠实记录不发明。
- **散列键** — Hash Key：BK 的哈希，装载并行化的基石。
- **多代哈希** — Multi-generation Hashing：哈希的哈希（源+BK 复合），同化多源键。
- **哈希差** — Hash Diff：描述列组的哈希，卫星变更检测器。
- **效果性** — Effectivity：关系「同时点唯一有效」的闭区间语义。
- **同址链接** — Same-as Link：同实体多源业务键的互认关系。
- **角色扮演** — Role Play：一个 Hub 按不同业务语义多视图使用（不建多表）。
- **记录来源** — Record Source：行出自哪个源系统/文件/表的标记列。
- **装载时刻** — Load Date/Load DTS：行进入 Vault 的时间戳。
- **载荷表** — Payload：透传低价值列的可选存档结构。
- **引用表** — Reference Table：值域/码表，Vault 内唯一非规范化豁免。
- **只追加** — Append-Only：无 UPDATE/DELETE 的写契约。
