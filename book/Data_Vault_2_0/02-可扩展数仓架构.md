# 第 2 章 可扩展数据仓库架构（Scalable Data Warehouse Architecture）

> 目录取证：章题与 2.1/2.2 小节题 ✅ 实抓自 Elsevier 官方 TOC。正文为精读重构。

## 1. 2.1 可扩展数仓架构的维度（✅）

作者把「可扩展」拆成三条正交的轴（本节以维度之名展开）：

1. **数据量可扩展（volume scalability）**：TB→PB 的线性增长能力。手段：分区/分布键、无共享（shared-nothing）MPP、近似的「只追加」写模式（避免 update 放大）。
2. **用户/并发可扩展（user scalability）**：读写互不阻塞。手段：读侧用集市/立方体/物化视图隔离，写侧装载窗口与查询窗口错开；append-only 天然减少锁冲突。
3. **功能/变更可扩展（functional scalability，即 adaptability）**：新增源、新增属性、新增业务关系不重构既有模型。手段：把「关系」与「描述」拆进不同型体（第 4 章三型），变更被局部化。

> 这三轴对应第 1 章的 Scalability/Agility/Adaptability 三角在**架构层**的投影。经典数仓失败的共同点：三条轴互相纠缠——为一个新字段重建事实表、为一次装载锁住全部查询。

架构上的通用武器清单（本节语境，⚠️ 逐条页码未核）：水平分区（partitioning）、垂直拆分（把宽表按访问频度拆薄）、并行装载（partition-by-partition 并发 upsert）、列式存储与 MPP 引擎（详见第 8 章）。Data Vault 的贡献在于**模型本身不阻止这些手段**：三型天然可按业务键哈希值做 hash 分布，Satellite 按时间做 range 分区，Link 可按 eff_from 分区。

## 2. 2.2 Data Vault 2.0 架构（✅）

全书的架构骨架图（用文字重画）：

```text
┌─ Sources (ERP/CRM/files/API/MQ) ─┐
│            │ 抽取(第11章)          │
│            ▼                      │
│        Staging Area（保真暂存 + 可选 Payload 列）
│            │ 装载(第12章, 并行/追加)  │
│            ▼                      │
│   ┌── Raw Data Vault ──┐  ┌─ Business Vault ─┐  ┌─ Information Marts(第7/14章) ─┐
│   │ Hub/Link/Satellite │→│ 规则Link、计算Sat │→│ 星型/雪花/PIT 直视图/立方体      │
│   │ Reference 表       │  │ 同化后的实体      │  │ 供 BI/报表/数据挖掘             │
│   └────────────────────┘  └──────────────────┘  └────────────────────────────────┘
│   ▲ 元数据/审计：load_dts、record_source、Meta/Metrics/Error Mart（第10章）贯穿 ─▲ │
└──────────────────────────────────────────────────────────────────────────────────┘
```

要点：

- **三层不是可选的**：Raw 保真（源系统说了什么）、Business 规则（企业怎么解释）、Mart 表达（用户怎么看）。层间只允许「向下引用键、向上供给数据」，禁止 Mart 反写 Vault——这是与「维度即仓库」的纯 Kimball 立场的根本分歧（见 [07-维度建模.md](07-维度建模.md) 与附节）。
- **并行装载的结构性前提**：Hub 只认业务键哈希、Satellite 只认哈希差，装载任何一张表都不需要「先查代理键再插入」的全局序列点，因此可以按表/按分区任意并行。这是 2.0 相对 1.0 在架构可扩展上的最大增量（代理键查表是 1.0 时代的吞吐天花板，⚠️ 书中对 1.0 瓶颈的具体量化未核）。
- **效果性（Effectivity）与时态**贯穿架构：Link 的 active/effective 区间 + Satellite 的有效区间，使「任意时点的架构快照」成为可查询对象（第 6 章 PIT 表）。
- 架构与平台解耦：本节给出的是逻辑拓扑，物理落位（单机 RDBMS、MPP、Azure）在第 8 章讨论——同一拓扑也适用于今天的 Snowflake/Databricks（见文末演进节）。

## 3. 三型 × 三轴的适配矩阵（2.1 的展开，重构口径）

| 架构手段 | 落在 Hub | 落在 Link | 落在 Satellite |
| --- | --- | --- | --- |
| 哈希分布（把行撒到节点） | hk 天然均匀 | hk_link 均匀 | 跟随父 hk 共置 |
| 时间范围分区 | 收益小（行数≈实体数） | eff_from 分区 | load_dts 分区（主战场） |
| 垂直拆分 | ——（本征已最薄） | 属性一律外迁卫星 | 按变更频率再细分 |
| 并行装载 | 键集合无重叠→全并行 | 等 Hub 完成（一层依赖） | 等父键，批内并行 |
| 读写隔离 | 点查少 | 中等 | 扫描多→列存化（第 8 章） |

结论：**卫星是扩展性问题的 80% 所在**——它最大、写得最勤、被 PIT 折叠后才是查询面。历史上大量「Vault 慢」案例实为卫星未按变更频率切分、又没做时间分区（工程常识口径 ⚠️ 非书中案例）。

## 5. 反模式：伪可扩展的三种形态（本章警示，重构）

1. **哈希键上再建大宽视图供 BI**：绕开集市层，把时态复杂度转嫁给报表工具（正解：14 章物化/虚拟化抉择）；
2. **所有卫星一张巨型表**（「我们抽象得很好」）：卫星的切分语义（内聚+变更频率）被抹掉，哈希差退化为全行比较；
3. **在 Raw Vault 建聚合事实**：违反保真契约，聚合一旦有 bug 无源可重算——聚合属于 Mart（第 14/15 章）。

## 核心概念速览（中英对照）

- **数据量可扩展** — Volume Scalability：随数据规模线性扩吞吐/存储的架构能力。
- **并发可扩展** — User Scalability：读写、多消费者互不阻塞的能力。
- **功能可扩展** — Functional Scalability / Adaptability：加源、加列、加关系不重构模型。
- **无共享架构** — Shared-Nothing (MPP)：各节点管自己分片的横向扩展范式。
- **水平分区** — Horizontal Partitioning：按行值域切分表（时间/哈希）。
- **垂直拆分** — Vertical Partitioning：按列簇拆薄热点宽表。
- **并行装载** — Parallel Loading：多进程/多线程并发写不同实体或分区。
- **原始层** — Raw Data Vault Layer：与源 1:1 保真的三型层。
- **业务层** — Business Data Vault Layer：业务规则与派生计算的同化层。
- **集市层** — Information Mart Layer：面向 BI 的表达层（星型/视图/立方体）。
- **代理键瓶颈** — Surrogate Key Lookup Bottleneck：1.0 时代串行查键对扩展的制约。
- **哈希分布** — Hash Distribution：按哈希键把行撒到节点的分布策略。
- **只追加写** — Append-Only：以追加代替更新的写模式，Vault/湖仓的共同底色。
- **贯穿元数据** — End-to-end Metadata：load_dts/record_source 等审计列随数据流动。
- **拓扑与平台解耦** — Platform-agnostic Topology：逻辑架构不绑定具体引擎。

## 最新演进与工业实践

- **同一拓扑落到湖仓**：Raw/Business/Mart 三层与 medallion（bronze/silver/gold）分层几乎逐层同构——Delta 官方口径的 medallion 架构见 [../Delta_Lake_Definitive_Guide/00-总览与阅读地图.md](../Delta_Lake_Definitive_Guide/00-总览与阅读地图.md)；社区常直接拿「Vault 三层 + Iceberg/Delta 底座」组合（如 ../Apache_Iceberg活用入門/00-总览与阅读地图.md 讨论的分层落地）。
- **Hudi 补齐「并行 upsert」短板**：书中「并行装载」在湖上需要表格式的事务写入支撑，Hudi 的 upsert/index/timeline 正是这一环（[../Apache_Hudi_Definitive_Guide/00-总览与阅读地图.md](../Apache_Hudi_Definitive_Guide/00-总览与阅读地图.md)）。
- **dbt 即「架构层」的执行器**：Raw/Business/Mart 三层在 dbt 项目里对应分层 model + selector/暴露控制（docs 的 +docs:show / 私有模型），AutomateDV/datavault4dbt 直接以宏库实现三层装载契约（见 [12-装载DataVault.md](12-装载DataVault.md) 演进节）。
- **弹性扩展的现实形态**：Snowflake 的虚拟仓隔离读写并发、Databricks 的 serverless 弹性，是 2.1 三轴在 2020 年代的商用答案；书中 2015 年的 Azure 答案（第 8 章）已换代，⚠️ 各家性能口径转述自厂商文档，未本机实测。
