# 第 1 章 数据仓库导论（Introduction to Data Warehousing）

> 目录取证：章题与 1.1–1.4 小节题 ✅ 实抓自 Elsevier 官方 TOC。正文为精读重构，非原书文本。

## 1. 本章要解决的问题

在引入 Data Vault 之前，作者先铺一张「数据仓库四十年地图」：数仓不是模型问题，而是**企业级信息交付架构**问题——为什么 1990 年代的经典方案（Inmon 的 CIFS/IDWK、Kimball 的维度总线）在生产扩张中纷纷失灵，才逼出了 Data Vault 这一骨干层。

## 2. 1.1 数据仓库史（✅ 小节实抓）

- 术语源头：1991 年前后 W. H. Inmon 提出「面向主题、集成、非易失、随时间变化的数据集合」四特征（该定义在 repo [../数据仓库工具箱3.md](../数据仓库工具箱3.md) 第 1 章亦有同一口径的转述）；同时期 R. Messerschmitt 等早期实践。
- 两条路线的分野：
  - **Inmon 路线**：自下而上，先建企业级 EDW（规范化），再派生数据集市。强调单一事实来源。
  - **Kimball 路线**：自上而下，直接以一致性维度+总线架构交付企业级星型。强调可交付速度。
- 1990s–2000s 的工程灾难清单（本章为 Data Vault 立论做的铺垫）：源系统频繁变更压垮 ETL、批窗口撑不住数据量增长、规范化 EDW 查询慢、维度 EDW 面对多源冲突束手无策、审计/合规要求全历史。
- ⚠️ 史实细节（作者点名的具体案例与年份）以原书为准，此处仅按公认史料重构。

## 3. 1.2 企业数据仓库环境（✅）

EDW 的真实运行环境三要素：

1. **异构源**：ERP/CRM/遗留大机/文件/日志，主键语义互相冲突（同一客户三套 ID）。
2. **业务不等待**：新增源系统、新增字段是常态，模型必须「加表不加灾」。
3. **多消费者**：报表、OLAP、数据挖掘、合规追溯对同一份数据提出不同时态视角的要求。

结论：EDW 层若要稳定，必须与「表达业务的维度模型」**解耦**——这是全书架构分工的起点（详见第 7、14 章与[附-Kimball与DataVault分工与混用.md](附-Kimball与DataVault分工与混用.md)）。

## 4. 1.3 Data Vault 2.0 导论（✅）

- Data Vault 由 Dan Linstedt 于 1990 年代末（业界通说 1999 年，一个保险精算项目）首创；第 1 代以「面向业务、可审计、可追溯的 3NF+时态骨干」成名。
- **2.0 的三个增量**（本章给出纲领，第 2/3 章展开）：
  1. **散列键（Hash Keys）**：用业务键的哈希替代代理键，消除装载前的序列查表瓶颈，支持并行 ETL；
  2. **哈希差（Hash Diff）**：卫星表用一行哈希判断属性集是否变化，变更检测 O(1) 化；
  3. **SDLC 3.0 方法论**：把敏捷交付框架（六大关键实践）写进模型方法论本体——模型方法第一次自带项目管理外壳。
- 核心理念三元组：**Scalability（可扩展）、Adaptability（可适应）、Agility（敏捷交付）**——分别对应架构、模型、方法论三个层面。
- 与 Inmon 关系的社区通说：Vault 常被定位为「对 Inmon CIFS 的现代化替代」，⚠️ 书中具体措辞未逐页核对。

## 5. 1.4 数据仓库架构总览（✅）

本章给出的分层（后续章节反复使用）：

```text
源系统 → Stage(暂存) → Raw Data Vault → Business Data Vault → Information Mart(维度/报表/立方体) → 消费者
                ↑ 元数据/Meta Mart 贯穿全链（第 10 章）
```

- Raw Vault：与源系统 1:1 保真的「事实的法庭记录」，永不清洗、永不删除；
- Business Vault：业务规则的落地层（规则 Link、计算卫星、同化后的桥接）；
- Information Mart：Kimball 式星型或任何 BI 需要的形状（第 7/14 章）。
- Payload（可选型）：把无建模价值但需随行的宽列直接「载荷」进暂存/原始表，避免为一次性的透传字段建三型（社区通用模式，⚠️ 书中着墨位置未核）。

## 6.6 三大经典痛点 → DV 2.0 的对策映射（本章论证骨架，重构）

1. **源系统变更风暴**（加列/换表/并购）→ 三型分离：新属性开新卫星，Hub/Link 不动（第 4/5 章兑现）；
2. **装载吞吐天花板**（代理键查表、单线程合并）→ 哈希键 + 保真 Stage + 按实体并行（第 11/12 章兑现）；
3. **历史口径丢失**（覆盖式更新、软删除）→ 卫星双时态 + 全追加 + Error/Correction 留痕（第 4/13 章兑现）。

> 每个痛点在 Kimball 体系里也有对应武器（维度重定义、增量聚合、SCD2），差别在于 Kimball 把解法放在**同一层**（星型），Vault 拆成**两层**——这是理解第 7/14 章分工论的钥匙。

## 6.7 FAQ（三问三答，本目录整理）

- **Q：Vault 是不是反对 Inmon？** 不是。它继承「EDW 应为集成/时态/稳定的企业层」这一 Inmon 命题，反对的是 CIFS 的具体建模教条（纯 3NF 宽连接、无散列契约）。
- **Q：为什么第 1 章就要读架构？** 因为 DV 的模型决策（卫星切分、可空链接）全是为第 2 章的扩展性目标服务的；脱离架构读三型会退化成「怪异 ER 图」。
- **Q：小数据、单源项目要不要上 Vault？** 本书立场偏企业级（688 页的对象就是 Scalable）；简单项目的成本收益判断见 [附-Kimball与DataVault分工与混用.md](附-Kimball与DataVault分工与混用.md) §3 决策表。

## 核心概念速览（中英对照）

- **企业数据仓库** — Enterprise Data Warehouse (EDW)：全企业单一集成、时态保存的数据资产层。
- **信息交付架构** — Corporate Information Factory (CIFS)：Inmon 提出的 EDW+集市+暂存的工厂式架构，Vault 的历史参照物。
- **数据骨干** — Data Backbone：位于源系统与集市之间、不随展示需求漂移的规范化+时态存储层。
- **散列键** — Hash Key：业务键经哈希得到的键值，替代代理键以消除查表串行点。
- **哈希差** — Hash Diff：属性集拼接哈希，用于卫星表变更检测。
- **原始数据金库** — Raw Data Vault：与源保真、只追加不修改的三型集合。
- **业务数据金库** — Business Data Vault：承载业务规则与计算的同化层。
- **信息集市** — Information Mart：面向分析消费者的维度/报表层（本书=星型集市）。
- **载荷表** — Payload：透传低价值宽列的可选结构。
- **可扩展/可适应/敏捷** — Scalability / Adaptability / Agility：DV 2.0 三角承诺。
- **源系统冲突** — Source System Conflict：同一业务对象多源不一致，EDW 常态难题。
- **批窗口** — Batch Window：ETL 必须在其中完成装载的时间约束，历史瓶颈之一。
- **审计追溯** — Auditability：任一时点答案可复现的能力，Vault 的立身卖点。
- **全历史** — Full History：不覆盖、不删除、以时态区间表达变化。

- **云数仓上的 Data Vault**：Snowflake 官方生态与第三方指南持续把 DV 2.0 作为参考架构（例：Coalesce 的《Data Vault 2.0: The Complete Snowflake Implementation Guide》，https://coalesce.io/data-insights/data-vault-2-0-the-complete-implementation-guide/ ，2026-09 验证可达）；书中第 8 章的 Azure 场景今天对应 Fabric/Synapse 一代。⚠️ 云厂商侧性能结论无法本机实测，均转述。
