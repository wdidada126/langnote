# 第 8 章 物理数据仓库设计（Physical Data Warehouse Design）

> 目录取证：章题与 8.1–8.6 小节题 ✅ 实抓自 Elsevier 官方 TOC（8.3 Microsoft Azure Cloud Computing Platform、8.5 Database Options 等）。正文为精读重构；书中平台细节属 2015 年快照，现状以「最新演进」节修正。

## 1. 8.1 数据库负载画像（✅）

物理设计从负载分类开始（本章口径，与通用教材一致）：

- **装载负载**：大批量追加（卫星/链接）、小批量点插（新 Hub 键）、周期性截断暂存——写主导、顺序 I/O 友好；
- **查询负载**：集市聚合（扫描+分组）、PIT 时点查找（点查+小范围扫描）、ETL 内查表（哈希键 JOIN）；
- **维护负载**：索引重建、统计更新、归档。

Vault 的负载画像结论：**天然 OLAP-友好偏扫描、天然 DWH-友好偏追加**，而 Vault 层的点查（"给我这个客户的全部历史"）又要求键列可索引——三种负载分层放置（Raw/Business 少索引、Mart 重索引/列存）是本章的布局主线（⚠️ 书中具体索引建议未逐条核）。

## 2. 8.2 开发/测试/生产环境分离（✅）

- 三环境+发布管道是方法论（第 3 章工作包）的物理承接：模型变更、ETL 包、映射配置全部随工作包晋级；
- 数据复制策略：生产全量→测试抽样→开发最小样（航司样例库，第 11.8 节），配元数据（第 10 章）保证「同模型多环境」一致性；
- 当年的 SSIS 项目部署/参数化困境书中多有实操，⚠️ 细节未核；其精神今天对应 dbt Cloud environments / CI 多目标 profile。

## 3. 8.3 Microsoft Azure 云平台（✅）——含 CDM 话题

2015 年视角的 Azure 数据栈（书中所写为快照）：SQL Azure（V1 时代 DW）、Azure Data Lake Store/Analytics 初生、ADFS/数据网关。作者演示「Vault 拓扑落 Azure」的弹性意义：装载高峰扩算力、查询时段错峰（当年 SQL DW 尚无自动弹性，⚠️ 书述以 TOC 语境推定）。

**CDM（Common Data Model）在两代故事中的位置**：

- 书中语境（⚠️ 推定位于 8.3 讨论生态时提及）：微软为数据湖定义的标准化模型+文件格式（table + model JSON），SQLDBM 等建模工具当时即宣布支持导出 CDM 格式；
- 现状（✅ 微软官方文档口径）：CDM 已演进为「数据分析实体标准 schema」，与 ADLS Gen2/Dataverse/Synapse 深度绑定，ADF/Synapse 内置 CDM 格式化读写：https://learn.microsoft.com/en-us/common-data-model/data-lake （2026-09 验证可达）；
- 概念辨析：CDM 的「公共数据模型」与 Vault 社区口中的 "common data model（企业共享核心业务模型）" 不是一回事——前者是**微软的格式/词表标准**，后者是 3NF 骨干的语义共享愿景（详见 [附-Kimball与DataVault分工与混用.md](附-Kimball与DataVault分工与混用.md) 词义框）。

## 4. 8.4 本地（On-Premise）物理架构 / 8.5 数据库选项（✅）

- 书中时代选项矩阵：SQL Server（+列存索引CCI/分区，2014/2016 前夜）、Oracle Exadata、APS/PDW、Hadoop 边缘场景；选型四问=容量曲线、并发画像、许可成本、团队技能（⚠️ 按章旨重构）。
- 对 Vault 特别相关：
  - **哈希键列宽**：128-bit MD5 → CHAR(32)/BINARY(16)；键宽换并行度是当年争论点（第 11.2  hashing 的下游决策）；
  - **列存 vs 行存**：卫星表列存化（扫描窄列聚合）、Hub 点查行存或堆表+哈希索引（⚠️ 书中具体建议未核，此为通行工程口径）；
  - **分区**：卫星按 load_dts range、链接按 effectivity 分区。
- 🔧 单机侧观察（DuckDB 1.5.5，列存引擎）：20 万卫星行装载微基准中「全列比较去重」与「哈希差去重」耗时同量级（0.08s vs 0.12s，重放均 0 新增），说明 hash diff 的成本收益强烈依赖引擎——向量化引擎里全列比较本已廉价，哈希差的价值更多在**跨异构引擎可移植的窄键契约**与行存储过程时代的比较开销规避。见 [12-装载DataVault.md](12-装载DataVault.md)。

## 5.6 键宽与容量速算（11.2 的物理账单，本目录整理）

```text
每行键开销： CHAR(32) hex ≈ 32B（未压缩） vs BINARY(16) ≈ 16B vs BIGINT 截断 ≈ 8B
卫星 50 亿行、三键引用 ⇒ 仅键列：hex 480GB / bin 240GB / 64bit 120GB（列存压缩前）
碰撞预算（生日近似）：128-bit 十亿级键 p≈10⁻¹⁷ 级；64-bit 亿级键 p 进入 10⁻² 区间需监控
```

结论不是「越小越好」，而是**位宽=风险×空间×JOIN 成本三方定价**；🔧 本机 DuckDB 观察：CHAR(32) hex 在列存下压缩极好（重复前缀/熵低），行存时代的「半宽焦虑」被压缩部分抹平（本目录微基准观察，量级结论，⚠️ 不具普适性）。

## 5.8 FAQ

- **Q：Vault 要不要外键约束？** 通行答案：不建（装载顺序+框架保证，12.1），审计需要时以元数据视图替代——省下的写放大正是扩展性来源；⚠️ 书中立场按此常识理解。
- **Q：卫星能建聚合索引/物化视图吗？** 能且应该谨慎——聚合属于 Mart 职责，骨干上的物化是「偷偷长出集市」，先问 14 章决策表。
- **Q：书中 Azure 一节今天还值得读吗？** 作为「云化论证」的结构（弹性/错峰/托管 ETL 三收益）仍成立，产品名全部过时；用本目录演进节+../The_Data_Lakehouse 补现状即可。

## 5.9 物理设计检查单（8.6 收口前，重构）

1. 三层各归其 schema/库/_catalog_，权限矩阵从 Mart 单向引用骨干；
2. 分区：卫星 load_dts range、链接 eff_from、事实交易日期——归档动作按分区 DROP 而非 DELETE（追加阵营的物理自律）；
3. 索引白名单：骨干只留 HK 聚簇/定位索引，其余「想加的索引」全部转成 14 章物化申请；
4. 统计信息在装载批末刷新（哈希键列直方图无用、依赖唯一性假设，优化器提示 ⚠️ 通用经验）；
5. 环境晋级物=映射清单+生成物，禁止手改 PROD DDL（8.2 铁律）；
6. 时区统一 UTC 存储、展示层本地化（11.3 load_dts 的孪生纪律）。

## 5.10 平台选项速览（8.5 的两代对照，⚠️ 现状为社区通识）

| 2015 书中选项 | 2026 常见落位 | Vault 适配点 |
| --- | --- | --- |
| SQL Server（+SSIS/SSAS） | Fabric/Synapse 系 | 生成器血统最顺（SQLDBM 老家） |
| Oracle/Exadata | 仍在金融存量 | 哈希键需 RAW(16) 列宽谈判 |
| APS/PDW | Synapse DW | 分布键=HK 天然契合 |

> 环境分离一句话：数据可以少，管道必须同构——四环境共用同一生成物与同一栅栏顺序。

## 核心概念速览（中英对照）

- **负载画像** — Workload Profiling：按装载/查询/维护分类度量 IO 模式。
- **环境分离** — Environment Separation：dev/test/prod 物理与流程隔离。
- **发布管道** — Deployment Pipeline：工件跨环境晋级通道。
- **通用数据模型(微软)** — Common Data Model (CDM)：数据湖标准 schema+文件格式。
- **弹性扩缩** — Elastic Scaling：云仓算力按时段伸缩。
- **列存索引** — Columnstore Index (CCI)：按列压缩与扫描加速的索引结构。
- **哈希键列宽** — Hash Key Width：128-bit vs 64-bit 键的空间/JOIN 权衡。
- **范围分区** — Range Partitioning：按时间值域切分（卫星/链接）。
- **文件组** — Filegroup：物理存储分片单元（SQL Server）。
- **MPP** — Massively Parallel Processing：无共享并行查询架构。
- **窄键契约** — Narrow-Key Contract：以定长哈希统一 JOIN 列的跨引擎约定。
- **schema 分层** — Schema Layering：raw/vault/marts 三层在库内的物理映射。

## 最新演进与工业实践

- **平台换代**：SQL Azure→**Snowflake/Databricks/Fabric/Synapse** 一代；书中「拓扑与平台解耦」的判断被验证——同一 Vault 三层在 Snowflake 上以独立虚拟仓跑装载/查询即 8.1 隔离的现代解（转述 ⚠️，不可本机实测）。
- **CDM 现状**（✅ 微软文档）：CDM folder/model 仍是 ADLS/Synapse/Fabric OneLake 的一等格式（https://learn.microsoft.com/en-us/common-data-model/data-lake ）；Iceberg 的强势（../Apache_Iceberg活用入門/00-总览与阅读地图.md）使「湖上表格式」竞争未尘埃落定。
- **SQLDBM 现状**（✅ 2026-09 官网实抓）：sqldbm.com 已转型为多云建模工作台（列示 Snowflake/Databricks/BigQuery/Synapse/Redshift/Fabric 支持），首页不再突出 Data Vault 生成（其 DV/Kimball 脚本生成能力为历史功能，现状深度 ⚠️ 待核）——作者 Olschkke 的工具与公司后来并入更宽的建模/Servicenow 系产品线（⚠️ 收购细节未核验，不展开）。
- **键宽新证据**：DuckDB/ClickHouse 等列存引擎对 BINARY(16) vs BIGINT 哈希键的 JOIN 性能差异与行存时代完全不同 🔧（见 12 章实测节延伸），2024 后社区出现「Vault 是否还需要哈希键」的再辩论（观点汇总 ⚠️，无权威定论）。
- **论文线**：列存/MPP 的底层依据（C-Store→Vertica、DSM 等）见 [../../db/db.md](../../db/db.md) 论文索引，可与此章选型讨论对读。
