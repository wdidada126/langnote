# 第 9 章 主数据管理（Master Data Management）

> 目录取证：章题与 9.1–9.9 小节题 ✅ 实抓自 Elsevier 官方 TOC（含 9.4 Operational vs Analytical MDM、9.9 Integrating MDS with the Data Vault and Operational Systems）。正文为精读重构；本章大量绑定 Microsoft MDS 产品形态，现状见文末。

## 1. 本章的问题域：谁是「客户」？

Vault 忠实记录多源冲突（第 5 章 same-as 只是把冲突**存档**），而「企业最终认哪个客户/产品/组织为准」是 MDM 的职责。作者把 MDM 请进架构而非放任集市层自治：黄金记录（golden record）**在上游生成、向 Vault 供数**，Vault 不生产黄金记录、只保真地携带其历史。

## 2. 9.1–9.3 定义、目标与驱动（✅）

- 主数据=被多业务过程共享的高价值实体数据（客户/产品/员工/地点/组织）。
- MDM 目标：单一可信视图（STV）、身份识别与合并（match & merge）、层级治理、变更审批流。
- 驱动因素（书中列举口径）：合规（反洗钱/KYC）、交叉销售、成本（重复客户=重复邮寄）、并购整合。
- 9.5/9.6 的两个「使能」视角：MDM 使能**受管的自助 BI**（维度有了权威口径才敢放权自助）与**全面质量管理**（TQM 语境）——MDM 不是独立项目而是集市质量的前置件，这与第 13 章数据质量互为表里。

## 3. 9.4 操作型 vs 分析型 MDM（✅）

| 维度 | 操作型 MDM（oMDM） | 分析型 MDM（aMDM） |
| --- | --- | --- |
| 消费者 | 前台应用（开户、下单） | 数仓/集市/报表 |
| 时延要求 | 实时/近实时 | 批量周期 |
| 冲突策略 | 覆盖式，取「权威源」 | 全历史并存+同化视图 |
| 身份状态 | 已裁决 | 可含未裁决（same-as 待确认） |

作者的关键论点：**数仓不要冒充 oMDM**——把合并决策做进 ETL 存储过程既无治理界面也无审计闭环；正确姿势是 aMDM 视角：接收 oMDM/人工治理产出的映射（黄金 ID ↔ 源 ID），以 same-as Link + 角色卫星的形式入 Vault，供集市消费并可回放任意时点的身份观。

## 4. 9.7–9.9 建模、导入与集成（✅，Microsoft MDS 语境）

本章实操围绕 **SQL Server Master Data Services (MDS)** 展开（书中示例，⚠️ 版本以书中为准未核，约 2014/2016 代）：

- 9.7 建模型：MDS 实体/层级/属性组定义（客户主模型带版本版本化）；
- 9.8 导入模型：staging 批量导入 + business rule 校验 + 版本提交（commit）产生批准态黄金数据；
- 9.9 **MDS↔Vault 集成模式**（本章技术核心）：
  1. MDS 的版本化变更视图→第 11 章作为一类源（11.10 即「Sourcing Master Data from MDS」小节 ✅ 实抓）抽取；
  2. 落 Vault 形态：黄金实体=新 Hub（H_CUSTOMER_MDM）或既有 Hub 的角色卫星；黄金↔源键映射=same-as Link（带 MDS 版本提交时刻的 effectivity）；层级=BOM/parent-child Link+集市 Bridge；
  3. 反向：挖掘/报表发现的候选重复经质量工单回到 MDS 裁决（第 13.9 匹配合并的出口）。

## 5. 与其他章的连线

- 9.9 的键映射直接消费第 5 章 same-as 语法；
- MDS 版本=第 10 章元数据的一部分（身份变更的审计链）;
- 「黄金记录变更」进集市后即第 7 章维度 SCD 事件与第 14 章维表重刷的触发器。

## 5.5 端到端时序：一条客户合并如何流到报表（9.9 操作化，重构）

```text
d0  MDS: 人工队列裁决 C1(CRM) ≡ 000C1(大机) → 版本 V2015Q3 提交
d1  提取(11.10): MDS 版本映射视图 → stage（带版本好与提交时刻）
d2  装载(12): L_SAMEAS_CUST 新行 (eff_from=d1提交时刻, record_source='MDS:V2015Q3')
d3  同化(13.10): V_CUST_IDENTITY 视图刷新 → 黄金代理值发布
d4  集市(14): DIM_CUSTOMER SCD2 归并两别名 → 报表客户数 -1（合并生效）
d5  审计(10/14.5): 用 PIT 复原 d0 前报表 → 仍是两客户（历史不被裁决改写）
```

要点：**裁决是事件不是改写**——d5 那行是 MDM 与数仓合谋对抗「历史被追溯性篡改」的证据链。

## 5.6 oMDM 集成三模式（9.9 的选型，重构）

| 模式 | 数据流 | 适用 | 风险 |
| --- | --- | --- | --- |
| 推送式 | MDS 变更即推源系统（总线/API） | 强操作型场景 | 数仓被实时化绑架（本书不荐） |
| 拉取式（书中主线） | 数仓按批拉 MDS 版本视图 | 分析型，批窗口宽松 | 版本间漂移需 load_dts 锚定 |
| 双写旁路 | 裁决同时写源与数仓 | 过渡期 | 一致性窗内两态并存 |

## 5.7 与第 5 章 same-as 的职责分界（易混点）

- **same-as Link**：存储层语法——「两个键等价（于某时段，依某出处）」；
- **MDM**：决策层流程——产生上述声明的治理机器（匹配规则、人工队列、审批、回退）；
- 推论：没有 MDM 也能用 same-as（人工 SQL 裁决+工单号当 record_source）；有 MDM 不接 Vault 则裁决无法时态回放——两半独立可缺，合体才完整。

## 5.8 FAQ

- **Q：MDM 项目失败率出名的高，本书方案依赖它吗？** 弱依赖：Vault 在「无 MDM」世界照样保真运行（两别名并存=受管的模糊）；MDM 到位后只是把裁决自动化。这是双层架构对「大 MDM 工程」的经典减压答。
- **Q：层级主数据（组织树）走 9 章还是 6 章？** 定义与审批走 MDM（9.7 建模型），事实与展开走 Vault Link+Bridge（6.2）；两边以版本号/same-as 式映射对齐。
- **Q：书中用 MDS，我用 Informatica/Senzing，本目录还适用吗？** 适用——5.5 时序里把 MDS 换成你的裁决引擎、版本提交换成其「黄金发布」事件即可，接口语义不变。

## 核心概念速览（中英对照）

- **主数据** — Master Data：跨业务共享的权威实体数据。
- **黄金记录** — Golden Record：多源合并后的可信单一视图。
- **操作型/分析型 MDM** — oMDM / aMDM：服务前台 vs 服务分析的两类 MDM。
- **单一可信视图** — Single Trusted View：MDM 的交付目标。
- **匹配与合并** — Match & Merge：身份识别裁决流程。
- **业务规则** — Business Rules（MDS）：版本提交前的校验条款。
- **版本提交** — Version Commit（MDS）：黄金状态生效+可回放的时点。
- **层级治理** — Hierarchy Governance：组织/BOM 树的管理。
- **同义链接承接** — Same-as Carry-over：黄金映射以 same-as Link 入 Vault。
- **KYC** — Know Your Customer：金融合规驱动的身份权威需求。
- **实体解析** — Entity Resolution：跨源识别同一现实对象。
- **身份图** — Identity Graph：实体-别名-关系的图式存储（现代 MDM 形态）。
- **受管自助** — Managed Self-Service：MDM 保障下的 BI 放权。
- **裁决后置** — Deferred Adjudication：先保真存档、后治理归一的 Vault 哲学。

## 最新演进与工业实践

- **Microsoft MDS 的黄昏**：MDS 作为 SQL Server 附带功能长期低投入演进；微软的官方接力是 **Microsoft Fabric/Customer Insights 的主数据与 Common Data Model（CDM，见第 8 章）+ Dataverse** 方向（⚠️ MDS 的正式生命周期终点声明未逐条核，仅提示读者「书中示例平台已过气」——SQL Server 2022 仍捆绑 MDS 的说法流传，未取官方确认 ⚠️）。
- **MDM SaaS/开源自建**：2020s 的替代谱系——SAP MDI/Informatica MDM 延续企业市场；开源侧 Semarchy xDM（社区版）、Senzing（实体解析引擎）、Theia/Palantir 系「ontology」产品把黄金记录升级为「对象层」。与 Vault 的接口形态不变：映射→same-as Link。谱系为社区通识整理（⚠️ 无单一权威出处）。
- **与数据编织/语义层的合流**：Snowflake Semantic View、dbt 语义层等把「权威实体口径」上浮为版本化指标定义，aMDM 的部分职能（口径仲裁）被语义层吸收（观点梳理 ⚠️）。
- **对照**：阿里 OneData 用「OneID」体系解同一题（ID-Mapping 图计算）——见 [../大数据之路.md](../大数据之路.md)；其「先保真入仓、ID 归一独立体系」与本章 Vault 哲学高度同构。
