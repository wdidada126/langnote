# 附：Kimball 维度建模 vs Data Vault 的分工与混用——Vault 作 EDW 层 + Kimball 作 DM 层

> 本文件为**专题节**（非原书章），聚焦本书区别于 repo 既有 Kimball 线笔记的架构主张，材料来源：本书官方 TOC 的 7/14 两章骨架 + 两派公开著作/社区实践对照。Kimball 原教旨细节请以 [../数据仓库工具箱3.md](../数据仓库工具箱3.md) 为准，本文件不转述其全书。

## 1. 两派的第一性问题不同

| | Kimball（《工具箱》第 3 版） | Data Vault 2.0（本书） |
| --- | --- | --- |
| 第一问 | 「用户要看什么？」→ 从业务过程出发建维度 | 「数据从哪来、如何永不丢失地存？」→ 从源系统契约出发建三型 |
| 交付单元 | 一个发布=若干总线矩阵格子（过程×维度） | 一个工作包=一组源实体×三型 +（可选）集市切片 |
| 真相层 | 一致性维度+企业星型本身就是 EDW | Raw/Business Vault 才是 EDW；星型是投影 |
| 变更观 | 需求驱动演进（维度生命周期） | 源与需求双驱动：骨干对源稳定、集市对需求敏捷 |
| 集成武器 | 总线矩阵+一致性维度（治理手段） | 三型契约+哈希键+same-as（结构手段） |
| 历史观 | 维度 SCD1/2/3、事实补写（选择保） | 全历史默认全保（卫星/链接时态） |

一句话：**Kimball 把建模押在“用”上，Data Vault 押在“存”上**。两派互相指责的靶子也因此不同——批 Kimball 者指「星型硬扛多源集成，ETL 变清洁工」；批 Vault 者指「三型层多一层成本，BI 端还得再建一遍星型」。本书第 7+14 章正是对后一指责的系统回答。

## 2. 本书的分工方案：双层混用（Vault = EDW，Kimball = DM）

这是本专题的核心，按书中三层拓扑给出职责切分：

### 2.1 职责表

| 关注点 | EDW 层（Raw+Business Vault） | DM 层（Information Mart，即 Kimball 地盘） |
| --- | --- | --- |
| 建模语言 | Hub/Link/Satellite/Reference/PIT/Bridge | 事实表/维表/总线矩阵/SCD |
| 键 | 散列键（不可变、跨源） | 代理键或沿用 HK（14.7 的取舍） |
| 多源冲突 | 同址存档+same-as 裁决（5.2/13.9） | 只见已裁决身份（13.10） |
| 历史 | 全保真双时态 | 按需 SCD 深度，可重算 |
| 变更吸收 | 新属性=新卫星（不动存量） | 新口径=新视图/新集市（不动骨干） |
| 消费者 | ETL/数据科学家/审计 | BI 用户/报表/自助分析 |
| 质量门 | G2/G3（13.4） | G4 出口裁剪 |

### 2.2 接口契约（14 章操作化）

1. 集市**只饮 Business Vault**（14.1）——DM 层禁止直连源或 Raw；
2. 一致性维度问题被结构化为「同一 HK/PIT 生成」——总线矩阵退化为「集市目录+口径登记」（第 10 章业务元数据）；
3. 维度口径变更=换切面（卫星组合/PIT 配置），骨干零改动——Kimball 再工程痛点的结构性解法；
4. 立方体/语义层是 DM 之上的第三投影（15 章），派生链单向 `Vault→Mart→Cube`。

### 2.3 Kimball 侧吸收了什么

反方向也成立，混用项目中 DM 层完全沿用 Kimball 4 步法（选过程→定粒度→选维度→定事实）、事实表三型、junk/role-play 维等全部武器——本书第 7 章本身就是一份浓缩 Kimball 教程（这正是它值得与 [../数据仓库工具箱3.md](../数据仓库工具箱3.md) 对读的原因）。**分工不是折中：每层用自己的完整方法论**。

## 3. 选型决策：什么时候需要 Vault 层？

社区多年实践沉淀的判断表（本目录梳理，非书中原表 ⚠️）：

| 信号 | 倾向 |
| --- | --- |
| 源系统 ≤2、语义稳定、交付压力为主 | 纯 Kimball 直接星型（工具箱路线足够） |
| 多源同实体冲突频繁（客户/产品多 ID 世界） | Vault 骨干 + same-as |
| 强审计/全历史/合规（金融、保险、医药） | Vault（卫星+PIT 是法务友好形态） |
| 高频源端 schema 变更、并购接入常态化 | Vault（加表不加灾） |
| 数据湖/流式为主、变换层薄 | 可跳过 Vault，medallion+维度直接走（见 §5） |
| 组织无 DW 团队、BI 即全部 | 纯 Kimball 或现代 dbt 项目即可 |

中文语境镜像案例：阿里 OneData（[../大数据之路.md](../大数据之路.md)）用「公共层=维度模型」顶替了 Vault 的位置——它同样处理多源冲突（ODS 保真+DWD 清洗），但裁决放在维度明细层而非独立 3NF 骨干。**OneID vs same-as Link** 是两套文化对同一问题的答案（对照本仓库两书可感）。

## 5. 2026 年的三方格局（演进观点，⚠️ 梳理性判断）

- **纯 Kimball + dbt**：中小数据量下星型直接建在湖仓 bronze/silver 上（medallion≈隐式骨干），Vault 层被「薄 silver」替代——「不需要独立 3NF 层」在简单场景确实成立；
- **Vault + dbt（AutomateDV/datavault4dbt）**：多源复杂组织的显式骨干路线，工具链成熟度（2026 实测：两库均活跃）已反超当年 SSIS 时代；
- **Mesh 化改造**：骨干概念域内化（每域自带 mini-vault），中心只留平台与契约（见 [03-DataVault20方法论.md](03-DataVault20方法论.md) 演进节的 Mesh 三方立场）。
- 混用常态：真实企业里「Vault 作 EDW + Kimball 作 DM」与「medallion+维度」经常**按域并存**——两派信徒共同反对的旧敌人（源系统直通报表）已死，争论焦点只剩「显式骨干层的成本是否值得」。

## 6. 常见混用错误清单（两派笔记互读后的负面知识）

1. 在 Raw Vault 里做清洗（违反 11 章保真契约）——等于把裁决埋进无人审计的角落；
2. 集市直接 JOIN 源系统（绕过 14.1 取材纪律）——口径分叉重新发明；
3. 用 Kimball 思维给 Hub 加描述列、用 Vault 思维给维表做全历史（双层职责互串）；
4. 在 DM 层重建 same-as（裁决必须在 Business Vault 完成一次）；
5. 把 Reference 表当 Hub 供（过度建模）或反之（该建 Hub 的实体降级为码表）；
6. 立方体/语义层里再造一层历史——投影只保留报表所需口径深度（15 章分区经济学的另一面）；
7. 忽略 CDM 词义冲突：微软 CDM（湖仓格式标准，见 [08-物理数仓设计.md](08-物理数仓设计.md)）≠ 建模人口中的 common data model（共享概念模型）≠ Dataverse CDM——三层文档里务必标注具体所指。

## 6.5 一个混用参考架构（重构示例，⚠️ 非书中原图/真实企业）

```text
                        ┌────────── DM 层（Kimball 地盘）──────────┐
ERP(CRM) ─┐  Stage+哈希 │ Raw+Business Vault        marts:        │  BI/自助
          ├─ 提取 ────► │  H/L/SAT + REF      ──►  DIM_*/FACT_*   ├─ 报表/语义层
电商平台 ─┘  (薄)       │  PIT/BRG 中间件        (SCD2 投影)      │
                        └──────────── EDW 层（Vault 地盘）────────┘
遗留大机 ──► 旁路：文件→Payload→同一 Stage 合同（源的脏活不污染骨干）
治理：总线矩阵→集市目录；口径→语义层定义；身份→MDM 引擎产出 same-as
```

角色分配一句话：**「源负责说、Stage 负责记、Vault 负责存得下说得清、Mart 负责答得快、语义层负责答得齐」**。

## 6.6 迁移路径：存量 Kimball 数仓要不要补 Vault 层？

按痛感分级（本目录整理，⚠️ 咨询口径）：

| 症状 | 处方 |
| --- | --- |
| 维表 ETL 里出现跨源 CASE WHEN 仲裁 | 该实体该有 Hub+same-as（裁决上浮 G3） |
| 一次源 schema 变更导致 3 个集市回归 | 卫星化该列（变更局部性回归测试） |
| 需要「任意时点重放监管报表」 | 补 PIT+保留源观察史（星型 SCD2 不够） |
| 并购季（新源接入>内部需求） | 骨干整体 Vault 化；存量星型先当「已物化集市」保留 |
| 以上皆无，单源、报表少 | **别迁移**——Vault 是规模药，不是维生素 |

迁移姿态通常是「新域走 Vault+Mart 双层、老域原地续命、交汇点在语义层」，一步到位的翻修在公开案例中属少数（行业通说 ⚠️）。

## 6.7 术语三角辨析表（写作/读文献防串台）

| 词面 | 所指 | 出处系 |
| --- | --- | --- |
| Common Data Model (CDM) | 微软数据湖标准 schema+文件格式（表+model JSON） | Azure/Synapse/Fabric 文档 ✅ |
| common data model（小写泛指） | 企业共享概念/核心业务模型（「统一词汇表的 3NF 骨干」愿景） | 建模社区/DAMA 语系 |
| Dataverse/CDM 实体 | Dynamics/Power Platform 应用实体库 | 微软应用侧 |
| Canonical Model | 集成架构里的规范消息模型（ESB 时代） | 集成语系 |

四者都在不同文献里缩写成 CDM——本书第 8 章语境取第一个（微软格式），Vault 社区文章偶用第二义，引用时务必注锚。

## 6.8 FAQ（管理层三连）

- **「多一层 Vault 是不是重复建设？」** 若你的集成复杂度≈0，是重复；否则它替换的是原来散落在「星型 ETL 存储过程+临时表+人肉对齐会」里的**隐性集成层**——成本转移，非新增（附 §1 表的第一性问题即此论证）。
- **「两派要不要站队？」** 本书给出的岗位答案：骨干工程师练 04–06/11–13 章，分析工程师练 07/14 章+Kimball 工具箱，两边在 PIT 与语义层接口处握手。
- **「选型写进架构决议怎么表述？」** 可直接引用 §3 决策表+§6.6 处方表作证据链（本目录口径，非书中原话）。

## 核心概念速览（中英对照）

- **双层架构** — Two-layer Architecture：Vault 骨干 + 维度表达的分层合同。
- **投影** — Projection：星型/立方体自骨干派生、可弃可重算。
- **取材纪律** — Mart Upstream Discipline：集市只饮 Business Vault。
- **总线矩阵** — Bus Matrix：Kimball 的一致性协调工件，双层中收缩为目录。
- **一致性维度** — Conformed Dimension：由同 HK/PIT 生成的共享维。
- **裁决一次** — Adjudicate Once：身份/值域决策只发生在 G3。
- **同义链接** — Same-as Link：多源键等价的骨干级表达。
- **OneID** — 阿里系等价物：图计算 ID 归一体系（对照案例）。
- **medallion** — Bronze/Silver/Gold：湖仓对分层的另一种命名。
- **薄 silver** — Thin Silver 路线：无显式 3NF 骨干的隐式集成层。
- **mini-vault** — 域内小骨干：Mesh 语境下的域级 Data Vault。
- **模型即代码** — Model-as-Code：模板/生成器驱动的建模工件形态。
- **CDM 词义三角** — CDM Ambiguity：微软格式标准/共享概念模型/Dataverse 三义并存。
- **成本-价值判断** — Backbone Cost-Benefit：显式骨干层是否值得的选型核心。
