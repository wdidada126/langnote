# 13 · 索引监控（Monitoring Indexes）

> 原书 Chapter 13 "Monitoring Indexes"，pp.461–514（✅ Crossref，DOI …_13）。54 页：
> 把索引变成有账本、有仪表、有裁决流程的运维对象。⚠️ 叙事重构，✅ 锚 Learn。

## 本章主线

监控三问：**谁在用（usage）、用得怎样（operational）、谁在等（waits/blocking 的索引
形态）**。本章给出采集面（DMV/扩展事件/查询存储）与裁决面（删除候选/新增候选的
证据链标准）的分层设计——第 08 章神话 1/7 的执法机构在这里。⚠️

## 13.1 使用率账本 ⚠️/✅ 概念

- `sys.dm_db_index_usage_stats` 四计数（user_seeks/scans/lookups/updates）+ 系统侧计数
  分列；四列各自讲不同的故事（高 scans+低 seeks=键序错配信号；lookups 高=覆盖不足
  信号；updates 高+reads 低=删除候选主证据）。
- 记账规则（工程三纪律 ⚠️）：重启清零（窗口须跨业务周期）、只记 user 侧有效访问、
  聚合键必须到 index 粒度而非表粒度。✅ DMV 体系官方文档域（本册不逐视图给 404 风险
  URL，以 Learn 检索为准 ⚠️）。
- 2019 增强：operational stats 家族补叶级 insert/update/delete 与页活动统计 ⚠️ 视图名
  转述——写税第一次有了"每索引写速率"的直接观测面。

## 13.2 缺失侧账本 ⚠️

- missing index DMV 四件套的读法：equality/inequality/include 列组建议 + 估计收益 +
  **unique scans 计数**（同一查询反复注册=噪声源）；与 §8.1-7 的批判条款配套使用：
  建议→按列组合并→对照现有索引前缀→再进第 11 章策略评审。
- 陷阱清单（重构 ⚠️）：收益估计不计维护成本；组合爆炸（N 个建议可能 2 条复合键通吃）；
  过滤索引场景不敏感。

## 13.3 运行时与等待面 ⚠️/✅

- 页闩锁类等待（PAGELATCH_*）热点定位 → 分配争用/热页画像（键单调或过随机两型，
  对位 §1.2/§2.2）；LCK_M_* 阻塞链的索引形态（锁升级行数阈值触发 ⚠️ 转述）。
- 扩展事件模板挂锁等待/慢语句，把"偶发 3 秒"变成可归因事件：✅
  https://learn.microsoft.com/en-us/sql/relational-databases/extended-events/extended-events
- 查询存储作为"计划回归雷达"：per-query 的 plans + runtimeStats，异常窗口自动浮现 ✅：
  https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store

## 13.4 裁决流程：删除候选与体积账 ⚠️ 重构

1. 候选池：窗口内 seeks+scans+lookups=0 且 updates>0；
2. 复核：重启窗口污染？月度批覆盖？外键/唯一约束/复制/全文键依赖（删不得的索引
   清单——全文键回指 §7.1）；
3. 体积与写税量化：page_count × 写速率 = 释放空间/节省税的上下界；
4. 处置：先 DISABLE（留结构可回滚）再 DROP（两段式）；变更走 §10.4 四步流程。
- "禁用代替删除"是本章给出的低风险执法样板 ⚠️（DISABLE 语义以 Learn ALTER INDEX 为准）。

## 13.5 监控的存储与采样设计 ⚠️

- DMV 快照作业化：分钟级采样→留存窗（7/30/90 天分级），重启检测=instance startup_time
  比对；快照表本身就是"索引监控的索引设计题"（时间键+聚合读 → §11 自指应用）。
- 阈值告警只留两类：计划回归（QS）与锁风暴；体积/使用率走周报裁决而非即时告警 ⚠️。

## 13.6 🔧 类比：观测面缺位时的最小自建（非 SS 行为）

环境：python sqlite3 3.45.3——SQLite 没有 usage_stats 同位物，本册演示"自造账本"：
以 `pragma_index_list('orders')` 出索引目录（含 partial 标志，S4 实测输出
`[('ix_partial', 1)]`）+ `sqlite_stat1` 出统计行，两张目录左连接即"体积-统计"最小
报表；**使用计数无处可取**——这正说明 SQL Server 的 13.1 账本是引擎红利，监控设计的
核心能力（窗口/聚合/裁决）在任何引擎都得自己搭，工具可换、纪律不变。

## 13.9 判读 FAQ

- **Q：零读索引直接删？**
  A：过 §13.4
- **Q：监控保留多久？**
  A：粒度换深度：分钟级 7 天、小时级 90 天、快照永久；裁决要能重放到决策当日。
- **Q：seek 多但很慢，索引没用吗？**
  A：看回表与余谓词：seek 命中 40 行却 lookup 数万次=覆盖缺口，索引没错、形态差一层。
- **Q：系统侧计数能忽略吗？**
  A：用户面裁决可低权重；备份/checkdb/复制流量归因时要回头看它——删错“无人用”索引多冤在系统计数。
- **Q：告警只留两类会不会漏？**
  A：漏的是慢病（体积/使用率漂移），本就用周报执法；告警留给急性事件，分工明确才是设计。
- **Q：XEvent 会拖慢生产吗？**
  A：轻量是其立身之本
- **Q：查询存储开不起（容量/版本）怎么办？**
  A：降级为定时 DMV 快照+计划缓存采集——QS 是便利件不是前提，账本思维优先于具体工具。
- **Q：锁升级怎么从监控面反推索引？**
  A：行锁堆积
- **Q：监控表自身的索引怎么治理？**
  A：自指演练：时间键+聚合读的样例（§13.5）恰好可走 §15 全套循环——吃自己狗粮。

监控章的产出不是报表而是“可辩护的判决”：每条增删记录都应扛得住九问的反诘。

## 核心概念速览（中英对照）

1. **user_seeks/scans/lookups/updates** — 使用率四计数：键序错配/覆盖不足/写税的三联表。
2. **取证窗口** — observation window：跨业务周期、避重启污染的统计采集时长。
3. **operational stats** — 操作统计：2019 叶级读写活动观测面 ⚠️。
4. **missing index 四件套** — 愿望清单族：新增候选的输入而非结论。
5. **unique scans 噪声** — 同查询反复注册的计数去重问题。
6. **删除候选池** — drop candidate pool：零读+有写+无结构依赖的索引集合。
7. **DISABLE 先行** — disable-then-drop：留回滚余地的两段式执法。
8. **PAGELATCH 热点** — latch hotspot：分配页/热叶页争用的等待面画像。
9. **锁升级** — lock escalation：行锁堆积转表锁、索引设计可干预的阈值事件 ⚠️。
10. **计划回归雷达** — regression radar：查询存储 per-query 计划/时长的漂移检测。
11. **快照作业化** — DMV snapshot jobs：分钟级采样+分级留存的监控存储设计。
12. **重启检测** — startup_time diff：账本窗口有效性的哨兵。
