# 06 · 内存优化表索引（Indexing Memory-Optimized Tables）

> 原书 Chapter 6 "Indexing Memory-Optimized Tables"，pp.197–211（✅ Crossref，DOI …_6）。
> In-Memory OLTP（Hekaton）表的索引世界观与磁盘表彻底分叉的一章。⚠️ 叙事重构，✅ 锚 Learn。

## 本章主线

内存优化表没有页、没有磁盘 B+ 树、行常驻内存——索引退化为**指针结构**（哈希表或
内存序树），且**必须**至少一个索引（无索引表不允许 durable 持久化形态的常规用法 ⚠️
版本口径）。本章讲三型选择、bucket_count 调参与"内存索引同样要度量"的工程纪律。⚠️

## 6.1 三型索引与必选约束 ⚠️/✅

- `PRIMARY KEY NONCLUSTERED HASH(N)` / `NONCLUSTERED INDEX (...)` / `NO_INDEX`
  （聚簇=存储形态，2019 的 memory-optimized 聚簇索引支持口径 ⚠️ 转述）；
  durable 表要求至少一个索引（CHECKPOINT 数据文件按索引顺序落盘 ⚠️）。
  ✅ 官方总览：https://learn.microsoft.com/en-us/sql/relational-databases/in-memory-oltp/overview-and-usage-scenarios
- 哈希：等值定位 O(1)，无区间/排序能力——`WHERE k=?` 之外全是它的盲区；
  非聚簇内存索引：支持范围/排序/等值，代价是写路径更长、行数上限口径不同 ⚠️。
- bucket_count 估算 ≈ 预期 distinct 键数/桶装载系数（旧版建议 1–2 倍，2019 有自适应
  bucket 再哈希演进 ⚠️ 转述）；估算过低→链化退化，过高→内存浪费，**两个方向都可观测**
  （`sys.dm_db_xtp_hash_index_stats` 的 chain_level 分布 ⚠️ 视图名以 Learn 为准）。

## 6.2 无回表世界与"每查询一索引" ⚠️

- 内存表行数据直接挂在索引条目旁（索引即行容器，聚簇情形）或行头指针（非聚簇）——
  磁盘语义的"覆盖索引消灭 key lookup"在此变形为"选对索引消灭链遍历"。⚠️
- 多谓词列的组合爆炸在内存表上更贵：每个访问模式几乎需要一个专属索引；官方对
  每表索引数上限有口径（999 ⚠️ 转述，以 Learn 限制页为准）。

## 6.3 何时用内存优化表 ⚠️ 重构论证

1. 热点小表 + 极高并发等值访问（会话状态、计数器、高速暂存）→ 哈希主键；
2. 范围/排序密集的表 → 非聚簇内存索引；
3. 装载后仅批量消费的缓冲表 → NO_INDEX（省结构、靠并行扫）；
4. 大表全内存化 → 成本/恢复时间未必划算，磁盘表+宽缓冲池常更稳妥。
- 本章与第 15 章方法论咬合：**先证明磁盘路径是瓶颈**，再进入内存表复杂度。⚠️

## 6.4 🔧 类比说明：DuckDB 纯内存引擎的旁证（非本书引擎行为）

环境：duckdb **1.5.5**（python），200k 行 orders 全程内存/本地文件混合：

```
EXPLAIN SELECT * FROM orders WHERE customer_id=777
→ SEQ_SCAN, Filters: customer_id=777, ~40 rows（无索引可用的全扫+过滤）
CREATE INDEX ix_d ON orders(customer_id) 成功，但再 EXPLAIN 仍为 SEQ_SCAN（D3 实测）
```

- 读数：DuckDB 对点查**默认不用二级索引**——在"数据在内存/列块连续"的世界里，顺序扫
  的带宽常常打赢指针追逐。这与 Hekaton"必须为访问模式配结构"的立场形成镜像：
  内存消除 I/O 等待后，**索引价值取决于定位模式而非存在性**，是第 08 章神话批判的
  引擎级回声。SQLite（S1）则相反：加索引立刻 SCAN→SEARCH。
- 该对比不映射 Hekaton 的哈希/内存树实现细节，仅作"索引收益随存储形态翻转"的结构
  类比，如实登记。

## 6.7 判读 FAQ

- **Q：内存表索引会落盘吗？**
  A：非持久结构（noschema-bound 语义外）索引不写盘：重启后哈希桶按数据重建，启动时长即索引重建税。⚠️
- **Q：hash 8192 桶不够怎么办？**
  A：升 bucket_count 走 ALTER（2019 口径 ⚠️）或等自适应重哈希；链长分布是唯一的体检单。
- **Q：一个查询两个等值列，哈希怎么配？**
  A：哈希索引只吃完整键等值——两列拼一个键或改用非聚簇内存索引；“部分键命中”在哈希里不存在。
- **Q：内存表需要碎片维护吗？**
  A：无页则无分裂
- **Q：Durable 与 MemoryOnly 对索引的影响？**
  A：durable 必须有索引（落盘按索引序），memory_only 可 NO_INDEX——先定持久化需求再定索引下限。
- **Q：行版本链有多长？快照开销？**
  A：无锁 MVCC 以行版本链实现，长事务=链膨胀；内存表调优的第二战场从索引移到事务时长。⚠️
- **Q：内存表能 join 磁盘表吗？**
  A：可以（跨引擎查询），但执行路径与统计边界不同——混合负载先用 §15 循环验证再定迁移清单。
- **Q：999 索引上限真会撞到吗？**
  A：正常设计不会；撞上限通常意味着 §6.2 的“每模式一索引”被滥用为“每列一索引”。
- **Q：2026 还新建内存表吗？**
  A：作为新项目入口需三思（官方热度与替代方案，见演进节 ⚠️）；存量迁移则本章仍是必读。

内存表把“I/O 焦虑”换成“结构焦虑”：索引从加速器变成访问模式的存在性声明。

## 核心概念速览（中英对照）

1. **In-Memory OLTP/Hekaton** — 内存优化引擎：行常驻内存、无闩锁设计的表引擎 ⚠️/✅。
2. **内存优化表** — memory-optimized table：`MEMORY_OPTIMIZED=ON` 的表对象。
3. **哈希索引（内存）** — hash index：bucket 数组+链，仅等值定位。
4. **bucket_count** — 桶数：哈希容量旋钮，链化与浪费的平衡点。
5. **自适应桶重哈希** — adaptive bucket rehash：运行期桶数演化能力 ⚠️ 版本口径。
6. **内存非聚簇索引** — nonclustered (memory-optimized) index：支持范围/排序的指针结构。
7. **NO_INDEX** — 无索引表：仅暂存/批量场景的免结构形态（durable 受限 ⚠️）。
8. **索引即容器** — index-as-container：聚簇内存表行直接依索引组织的语义 ⚠️。
9. **链长度分布** — chain length stats：哈希健康度的观测面（DMV 口径 ⚠️）。
10. **每模式一索引** — one-index-per-access-pattern：内存表组合爆炸的建索引策略 ⚠️。
11. **先证瓶颈** — prove-the-bottleneck：进入内存表复杂度前的测量门槛。
12. **SEQ_SCAN 胜利** — scan-beats-index：列存/内存带宽下点查索引失效的反直觉旁证 🔧。
