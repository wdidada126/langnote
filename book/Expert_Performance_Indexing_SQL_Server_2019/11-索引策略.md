# 11 · 索引策略（Indexing Strategies）

> 原书 Chapter 11 "Indexing Strategies"，pp.353–438（✅ Crossref，DOI …_11）。86 页的
> 全书重心：从"建哪条索引"上升到"用什么结构组合服务负载"。⚠️ 叙事重构。

## 本章主线

按**负载形态**分派的策略武器库：复合键设计、INCLUDE、过滤（部分）索引、计算列索引、
索引视图、列存储、大表分治。每条策略都是 §2 存储账本与 §3 统计语义的函数；策略的
反面（何时不用）与正面同等篇幅——本章是"条件化重写"心法（ch8）的设计室。⚠️

## 11.1 复合键设计法 ⚠️/✅ 概念

- 键序规则：等值谓词列在前（可定位）、区间/排序列居中、共享列在后；前导列选择性
  决定树的第一刀切得多细。✅ CREATE INDEX 语义：
  https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql
- "窄键+INCLUDE 宽列" vs "宽键" 的树高/扇出权衡（§2.2 算术）；等值列的组合顺序还应向
  **统计可估性**倾斜（复合统计对象配合，§3.4）。⚠️
- 冗余前缀治理：ix(a)、ix(a,b) 并存时删前者；前缀复用计划以键序表评审。⚠️

## 11.2 过滤（部分）索引 ⚠️/✅

- `WHERE` 筛选条件（谓词须包含式匹配，`RECOMPILE`/参数化交互是著名限制 ⚠️ 转述）：
  对"热点小切片"（status='OPEN' 仅占 2%）把索引体积/写税同步缩小到切片量级。
- 🔧 直证（非 SS 引擎行为，§11.5）：20 万行表上 `WHERE status='A'`（39 行）的部分索引
  仅 **1 页**，全量三列索引 1128 页——1128 倍体积差就是过滤索引的全部论据。
- 滥用防线：谓词值域漂移（'OPEN' 占比季节波动）让部分索引一夜失效；每年度重审筛选
  谓词的分布前提。⚠️

## 11.3 计算列与索引视图 ⚠️/✅ 概念

- 持久化计算列可索引：把表达式谓词（`YEAR(d)=2019` 反模式 ⚠️ SARGable 讨论移交 ch12）
  物化为可 seek 的列；非持久化列的"表达式索引"路线在 SQL Server 不存在（PG 侧可对照）。
- 索引视图（schema-bound、确定性要求、SET 选项前置 ⚠️ 转述）=预聚合的物化结构；
  标准版以下不享视图索引加速（版本口径 ⚠️），且基表 DML 需实时同步维护——聚合收益
  必须大于跨表写税。列存出现后（§11.4）索引视图的适用面收窄到"高并发小聚合"。

## 11.4 列存储索引 ⚠️/✅

- 非聚簇列存（段/组/字典压缩 + segment 消除）服务扫描聚合型负载；与行存同表并存=
  HTAP 的 2019 形态；聚集列存储表无传统 B+ 树聚簇键。✅ 总览：
  https://learn.microsoft.com/en-us/sql/relational-databases/indexes/columnstore-indexes-overview 、
  设计指引 https://learn.microsoft.com/en-us/sql/relational-databases/indexes/columnstore-indexes-design-guidance
- 决策线（重构 ⚠️）：查询以"宽扫描+聚合+高压缩受益列"为主 → 列存；点查/窄行 → B+ 树；
  两者混合负载 → 行存表+非聚簇列存镜像或分区裁切。

## 11.5 🔧 本机类比集（非本书引擎行为）

环境：python sqlite3 3.45.3 + CLI 3.50.6（dbstat），orders 200k：

```
键序敏感（S3）: ix(order_date,status): date=? AND status=? → COVERING 双列定位
                仅 status='C'          → SCAN ix_cov（前导不可定位,退化为全索引扫）
过滤索引（S4）: ix_partial(customer_id) WHERE status='A' → dbstat 1 页 vs ix_cov 1128 页
                谓词含 status='A' 的查询 → SEARCH/SCAN 直接选中 ix_partial（CLI 复测）

                INCLUDE 不进排序层, SQLite 无独立 INCLUDE 概念（差异如实登记）。
```

## 11.6 大表与归档策略 ⚠️ 转述

- 分区对齐索引（每分区一索引栈）把维护/裁剪降到分区粒度；SWITCH 前后索引栈的同构
  约束是运维高频坑 ⚠️（分区机制细节归 Pro SQL Server Internals 谱系）。
- 归档即删除：冷数据搬出主表优于给冷数据建索引（写税常在、读税归零的不对称）。

## 11.9 判读 FAQ

- **Q：列存会吃掉行存的多少流量？**
  A：只吃扫描/聚合型；点查、高选择性窄行仍归 B+ 树——负载分家后两武器各守疆界，不存在替代关系。
- **Q：过滤索引与表分区怎么选？**
  A：切片谓词单一且热→过滤索引；多维裁切+按时间装卸→分区；两者可叠（分区表上的分区级过滤索引要验证命中 ⚠️）。
- **Q：索引视图 vs 列存重叠吗？**
  A：聚合收益
- **Q：计算列索引能救多少非 SARG 写法？**
  A：表达式物化
- **Q：INCLUDE 与把列并入键尾差在哪？**
  A：键列参与排序
- **Q：热冷分表算索引策略吗？**
  A：算，且是上位解
- **Q：每表索引数的合理上限？**
  A：没有数，只有预算：§13.1 的 writes 乘子与体积账之和不超窗口与缓存容量即可。
- **Q：策略评审必问的三题？**
  A：服务哪个谓词形态/被谁替代（前缀依赖）/撤销条件与证据各是什么。
- **Q：列存的排序键怎么起手？**
  A：低基数

策略章的通病是“拿着结构找负载”；九问的共同解药是把每个武器先还原成一条负载陈述句。

## 核心概念速览（中英对照）

1. **键序规则** — key order design：等值先行、区间次之、共享殿后的复合键排列法。
2. **前导列选择性** — leading column selectivity：复合索引第一刀的数据切分效率。
3. **冗余前缀索引** — redundant prefix index：被更长键前缀覆盖的可删索引。
4. **过滤索引** — filtered index：带 WHERE 的切片索引，体积/写税随切片缩小。
5. **值域漂移** — predicate drift：筛选谓词分布随业务演化致部分索引失效的慢性病。
6. **持久化计算列** — persisted computed column：可索引的物化表达式列。
7. **索引视图** — indexed view：先物化后建唯一聚簇的视图，DML 实时同步税 ⚠️。
8. **列存储索引** — columnstore index：段式列压缩结构，扫描聚合型负载的形态解。
9. **行存列存并存** — hybrid row/column store：同表双结构服务混合负载。
10. **分区对齐** — aligned partitions：索引栈按分区同构切分，维护降至分区粒度。
11. **归档即删除** — archive-over-index：冷数据迁出优于冷数据建索引。
12. **HTAP（2019 形态）** — 行存+非聚簇列存的引擎内混合处理 ⚠️/✅。
