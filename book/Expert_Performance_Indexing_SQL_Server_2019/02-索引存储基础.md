# 02 · 索引存储基础（Index Storage Fundamentals）

> 原书 Chapter 2 "Index Storage Fundamentals"，pp.29–90（✅ Crossref，DOI …_2）。
> 本章是全书篇幅最大的存储章之一（62 页）。章内叙事 ⚠️ 重构；引擎事实以 Learn ✅ URL 锚定。

## 本章主线

索引决策的"物理账本"：页（8KB）如何装行、键宽如何换算成树高与页数、行定位符与转发
指针如何影响回表成本。作者把"先看存储、再谈性能"作为贯穿全书的方法论地基。⚠️

## 2.1 页与区间：SQL Server 的存储原子 ⚠️ 转述 + ✅ 概念

- 一切表/索引的分配单位是 8KB 页；页头 + 行数组 + 空闲区；区（extent）= 8 连续页。
  混合分配/统一分配（mixed/uniform allocation）控制小表碎片（GAM/Sgam/PFS 结构细节属
  Pro SQL Server Internals 谱系，本册按 ⚠️ 引用不展开）。
- 行大小上限与"宽列行外存储"：varchar(max)/xml/varbinary(max) 走 LOB 行外页，
  影响索引可用性（不能作键列的列类型限制）。✅ 类型口径见
  https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql ⚠️ 页内

## 2.2 键宽 → 树高 → I/O 的算术 ⚠️ 重构（核心论证链）

- 每层扇出 = 页大小 / (键宽 + 指针宽)：int(4B) 键的扇出远大于 uniqueidentifier(16B)。
- 4 字节键约可支撑百万行 3 层，16 字节 GUID 显著抬高树高与每层页缓存压力——这是
  本书反对"随手 GUID 聚簇"的算术根基。⚠️ 结论符合通行 B+ 树代价分析（理论侧对读
  [../Physical_Database_Design/02-索引基础技术.md]）。
- 二级索引的**隐藏成本**：每个非聚簇索引叶子都复制一份聚簇键作定位符——聚簇键越宽，
  全部二级索引同步膨胀（"选窄而稳的聚簇键"由此推出）。⚠️

## 2.3 堆、转发指针与 RID 不稳定 ⚠️ 转述

- Heap 上 UPDATE 变宽 → 行迁移到新页 → 原位置留 forwarding pointer → 非聚簇索引
  的 RID 不变但多一跳；行迁移（clustered）则是**键更新引发删除+插入**的树级联维护。
- 工程含义：高频变宽列的表慎用堆；高频更新的键列不要进聚簇键。⚠️

## 2.4 INCLUDE、键顺序与覆盖的存储代价 ⚠️ 转述

- INCLUDE 列只落叶子：树高不变、叶子变肥 → 索引总页数上升；键列参与排序：树高/扇出
  受影响。二者代价形态不同，选择依据 = 谓词形态 vs 输出列集合。
- "覆盖索引消灭回表"的边界：低选择性谓词下，扫肥叶子的成本可能反超窄键+回表。⚠️

## 2.5 填充因子与页内预留 ⚠️ 转述

- FILLFACTOR/PAD_INDEX 决定建树时叶子/中间层的预填空隙：面向键插入分布（递增 vs 随机）
  调参；填不满 = 空间换碎片延迟（与第 09 章维护闭环）。✅ 参数语义见
  https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql

## 2.6 数据压缩对索引页的影响 ⚠️ 转述

- ROW/PAGE 压缩（ Enterprise 功能定位随版本演变 ⚠️ ）降低索引页数 → 读 I/O 与缓存
   footprint 双降，代价是 CPU；对宽 INCLUDE 索引收益最大。具体功能层级版本口径 ⚠️。

## 2.7 🔧 本机类比：每对象页数直方图（非本书引擎行为）

环境：sqlite3 CLI **3.50.6**（编译入 dbstat 虚拟表；python 3.45.3 内核对未启用，如实记录），
demo.db 为 20 万行 orders + 4 个二级索引，`SELECT m.name, COUNT(*) FROM dbstat d, sqlite_master m
WHERE d.name=m.name AND m.type IN('table','index') GROUP BY m.name` 实测：

```
orders            1730 页   (heap-organized, rowid 表 ≈ 聚簇基表类比)
ix_cov            1128 页   (customer_id,status,total 三列键, 覆盖)
ix_date_status    1377 页   (含长日期列, 键更肥)
ix_orders_cust     581 页   (单 int 键 —— 最瘦)
ix_partial           1 页   (WHERE status='A' 部分索引, 仅装 39 行)
```

- 读数：同为二级索引，页数差 **1128 倍**——键宽/INCLUDE 宽度/行过滤直接改写存储账本，
  与 §2.2/§2.4 的叙事同构；SQLite 页为可变得页大小，SQL Server 恒 8KB，数值不可平移，
  **仅比值语义可比**。
- 覆盖索引另一侧证据（python 3.45.3）：`SELECT status,total FROM orders WHERE customer_id=?`
  → `SEARCH … USING COVERING INDEX ix_cov`，而多要一列 order_date 即退化回表。

## 核心概念速览（中英对照）

1. **页** — page：SQL Server 8KB 存储原子，行数组+行偏移结构。
2. **区** — extent：8 个连续页的统一分配单位。
3. **PFS 页** — page free space：登记每页空闲与归属的元数据页。
4. **转发指针** — forwarding pointer：堆行迁移后原槽留下的跳板指针。
5. **行迁移（键更新）** — row migration (key update)：聚簇键变更=删除+插入的级联维护。
6. **扇出** — fan-out：B+ 树每层可容纳的 (键,指针) 对数，由页大小/键宽决定。
7. **树高** — tree depth/b-level：定位一次需读的页数，键越宽树越高。
8. **INCLUDE 列** — non-key column：仅驻叶子、不参与排序分发的覆盖列。
9. **覆盖索引** — covering index：查询所有输出列均在索引内、免回表的索引。
10. **填充因子** — fillfactor：建树时叶内预留空隙百分比，延迟页分裂。
11. **数据压缩** — row/page compression：以 CPU 换页数的行内/页内编码。
12. **LOB 行外存储** — out-of-row LOB：大值类型移出数据页，影响索引可用性。
13. **dbstat** — dbstat：SQLite 页级观测虚拟表（🔧 本册类比工具，非 SS 组件）。

- 2019→2022→2025：8KB 页/行偏移结构未变；列存（xVelocity）持续吸收分析负载的"存储账本"
  话题：https://learn.microsoft.com/en-us/sql/relational-databases/indexes/columnstore-indexes-overview ✅、
  设计指引 https://learn.microsoft.com/en-us/sql/relational-databases/indexes/columnstore-indexes-design-guidance ✅
- 工业实践：云托管（Azure SQL DB/Managed Instance）下压缩与分配治理多为默认/自动，
  本书式的页级手工推理价值集中在**索引键宽决策**与**回表成本预判**两个不变量上。⚠️ 判断
- 实测路线更新：本机可用 docker/SQLite 双轨验证页语义；SQL Server Linux 容器可跑真实
  dbstat 对位物（sys.dm_db_database_page_allocations）：
  https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-overview ✅（本册按纪律未安装未跑，⚠️）
- 跨引擎：DuckDB 以 row group + zone map 取代"窄页+树高"叙事（第 14 章 🔧 D1/D2 对照），
  列存世界里键宽对读路径的影响权重与 B+ 树世界完全不同。
