# 14 · 索引分析（Index Analysis）

> 原书 Chapter 14 "Index Analysis"，pp.515–594（✅ Crossref，DOI …_14）。80 页、全书最长：
> 执行计划的逐算子判读与"从计划倒推索引决策"的案例方法。⚠️ 叙事重构。

## 本章主线

计划是索引决策的**尸检报告兼体检单**：行数估计（est vs actual）、物理算子选择、
rewind/rebind、tempdb 溢出，每一条异常最终都翻译成"改键序/改 INCLUDE/改统计/改 SQL"
四类处方。本章给读法，不给模板答案（模板答案是第 08 章的敌人）。⚠️

## 14.1 读计划的三张底牌 ⚠️/✅ 概念

- `SET STATISTICS XML/IO ON`（真机采集口径 ⚠️ 转述）或 SSMS 实际计划；判读三问：
  1) 每算子 est/actual 行数比 >100× 处=统计或嗅探病灶（§3.3 因果链）；
  2) 物理算子是否配上了逻辑期望（seek 变 scan、NL 变Hash 的翻转点）；
  3) 隐式成本：Sort（缺键序红利）、Spill（内存授予失真）、Table Spool（防抖或相关子查询）。
- 计划文本工具：SSMS/在线查看器；Query Store 取历史计划回归比对（§10.3 ✅ 同 URL）。

## 14.2 定位 vs 扫描的判读细节 ⚠️

- seek 谓词的**实际前缀长度**：计划 detail 里 `Seek Keys` 只用第一列而查询带两列谓词=
  键序设计失败（S3 🔧 的直证形态）；
- scan 不一定有罪：小表、高命中、列存段扫描下 scan 是正解（§11.4）——判读必须带
  选择性语境，"见 scan 就加索引"是神话 2 的变体。

## 14.3 回表的账目化 ⚠️/🔧

- key lookup 计数 × 随机页读成本 = 覆盖索引的立项预算；lookup>seek 数倍的计划形态=
  INCLUDE 候选清单。
- 🔧 同构直证（sqlite3 3.45.3，非 SS 行为）：同谓词下
  `SELECT status,total FROM orders WHERE customer_id=?` → COVERING ix_cov 零回表；
  多要一列 order_date → `SEARCH ... USING INDEX ix_orders_cust`（回表形态）。
  一行 SQL 的差异在计划里翻转结构——覆盖收益/成本的判读原型。

## 14.4 特化负载案例族 ⚠️ 重构目录

1. **分页 API**：OFFSET 深翻的 sort+spill → keyset 改写（§12.5）后计划变 seek+早停；
2. **批量装载**：装载期禁用非必需索引、装载后重建（§9.2）+ 统计追补（§3.3）；
3. **倾斜报告查询**：日期前缀+租户维的复合键设计评审（§11.1 键序规则）；
4. **全文/空间回表**：两段式过滤的残留谓词识别（§5.3/§7.3）——粗过滤≠失效。
- 案例的共同结论（重构 ⚠️）：**九成坏计划源于估计失真与键序错配**，结构缺位反而少见。

## 14.5 🔧 本机类比：列存世界的计划对照（非 SS 行为）

环境：duckdb 1.5.5（python），220k 行 orders：

```
EXPLAIN SELECT * WHERE customer_id=777 → SEQ_SCAN + Filters: customer_id=777, ~40 rows
EXPLAIN ANALYZE GROUP BY status        → TABLE_SCAN, Projections: status（列裁剪）, 220k rows 0.00s
CREATE INDEX ix_d ON orders(customer_id) 成功后, 点查计划仍是 SEQ_SCAN（D3 实测）
```

- 读数：列式引擎把"回表/覆盖/键序"三话题整体替换为"列裁剪+zone map 段消除"；行存
  世界的计划判读技能迁移时须**先换坐标系**。这是 §11.4 行存/列存决策线的观测面证据。
- est ~40 rows 与 SQLite 侧 sqlite_stat1 的 `200000 40`（§3.5 实测）互证：两个引擎都
  以"行数/密度"喂优化器——**估计失真是全引擎通病**，14.1 底牌 1 放之四海。

## 14.9 判读 FAQ

- **Q：est/actual 差异多大要立案？**
  A：数量级（>100×）必查；10× 级别结合行数绝对值（万级 10× 比个位 1000× 更值得动手）。
- **Q：并行度（DOP）该在索引章管吗？**
  A：边界：索引
- **Q：Spool 是坏东西吗？**
  A：Eager Spool 常是防抖保险；反复 Spool+高行数才值得改写去相关化。
- **Q：页读取数怎么和索引挂钩？**
  A：SCAN 物理读≈行数/页密度，seek+lookup 物理读≈命中行×树高——两类公式把计划翻译成 §2 账本。
- **Q：计划里看不到统计信息怎么办？**
  A：统计不在计划 XML 内；SHOW_STATISTICS 快照与计划同刻采集（§14.6 四件套）才可对账。
- **Q：分析半天最后发现不是索引问题？**
  A：高概率
- **Q：分析时间盒怎么定？**
  A：三底牌各 15 分钟出假设清单；超盒无假设=收集更多证据，不是继续盯屏幕。
- **Q：线上不能跑 STATISTICS XML？**
  A：用 QS/缓存计划替代实采；计划格式差异 ⚠️ 转述。
- **Q：案例库如何沉淀？**
  A：处方单四件套归档+季度回看“当时假设对了没”——分析能力的复利在回看率里。

计划判读九问的公约数：所有异常先问“估行数对没对”，再问“键序配没配”，最后才问“要不要换结构”。

## 核心概念速览（中英对照）

1. **实际执行计划** — actual execution plan：运行时真值（est/actual 并列）的诊断载体。
2. **估计/实际行数比** — est/actual ratio：>100× 即病灶的统计失真标尺。
3. **Seek Keys 前缀** — seek predicate detail：复合索引实际消费到的键列数。
4. **key lookup 账目化** — lookup budget：回表计数×随机页成本=覆盖立项依据。
5. **Sort/Spill/Spool** — 隐式成本三件套：缺键序、内存失真、防抖/相关的计划痕迹。
6. **rewind/rebind** — 迭代重放标记：相关子查询被"包装"的形态信号 ⚠️。
7. **列裁剪** — column pruning：列存仅读所需列的段级优化 🔧 观测。
8. **段消除** — segment elimination：列存 zone map 跳过无关 row group 的 scan 削减。
9. **坐标系切换** — row/column paradigm shift：行存判读技能到列存的迁移前置。
10. **处方单** — prescription sheet：改什么/预期证据/回滚法的分析结论文书。
11. **四件套归档** — plan+stats+目录+处方：深度分析的标准产物包。
12. **早停** — top/paging early-out：seek+有序下读到 N 即止的执行红利。
