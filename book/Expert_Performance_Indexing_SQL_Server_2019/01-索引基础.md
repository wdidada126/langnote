# 01 · 索引基础（Index Fundamentals）

> 原书 Chapter 1 "Index Fundamentals"，pp.1–27（✅ Crossref 章节记录，DOI 10.1007/978-1-4842-5464-6_1）。
> 章内叙事为 ⚠️ 精读重构（基于通行索引语义 + Microsoft Learn ✅ 文档对位），非原书文本。

## 本章主线

全书的公理章：索引不是"加速器开关"，而是**以写代价与存储代价换取读路径缩短的物理结构**。
本章把 SQL Server 的索引家族摆上桌面——聚簇、非聚簇、堆、唯一、包含列——并给出后面 14 章
反复回用的词汇表（key、leaf、lookup、seek/scan）。

## 1.1 B+ 树：二级索引的骨架 ⚠️ 转述 + ✅ 文档

- SQL Server 非聚簇索引 = 多叉平衡搜索树（B+tree 语义）：中间层存键值+页指针，叶子层存
  键值+行定位符（Heap 为 RID，聚簇表为聚簇键）。✅ 官方口径见 CREATE INDEX 文档：
  https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql
- 树高由键宽与填充度决定：20 万行、4 字节整数键通常 2–3 层即可定位（数量级常识，
  具体到 SQL Server 页结构见第 02 章）。⚠️
- Seek vs Scan 的分界：**可定位的最左连续键前缀**决定 seek 能否成立——这条规则贯穿
  第 11/12/14 章。⚠️

## 1.2 聚簇索引与堆 ⚠️ 转述

- 聚簇索引的叶子即数据页本身，一张表至多一个；无聚簇索引的表 = Heap，行位置可变、
  更新可能产生 forwarding pointer（详见第 02 章）。✅/⚠️ 概念定义与 Learn 索引文档一致。
- 自增键聚簇的"热页"问题（写入集中到最后一页）与其替代方案（哈希/GUID 前缀反转等）
  是本章⚠️重构语境下的经典辩论题。
- 与 InnoDB 的关键差异：MySQL InnoDB **强制**聚簇（主键即组织），SQL Server 允许纯堆——
  这决定了"索引即数据组织"在两引擎里的讨论口径不同，对读
  [../Understanding_MySQL_Internals/00-总览与阅读地图.md] 的存储引擎章。⚠️

## 1.3 非聚簇索引、唯一约束、INCLUDE ⚠️ 转述 + ✅ 文档

- 非聚簇索引独立于数据物理顺序；键列有序 + 叶子回指。
- UNIQUE 约束可由唯一索引实现，但"业务唯一性"应落到约束而非仅靠手工索引（防漂移）。⚠️
- INCLUDE（非键列）：把"只读不回表"的宽列挂到叶子层，参与覆盖而不参与排序——
  键宽/树高与覆盖收益的权衡是全书反复出现的母题（第 02/08/11 章）。✅ 文档同上 URL。

## 1.4 🔧 本机类比：SCAN → SEARCH 的最小实验（非本书引擎行为）

环境：python sqlite3 **3.45.3**（CLI 3.50.6），orders 表 200,000 行（order_id 为 INTEGER
PRIMARY KEY 即聚簇,rowid），脚本 D:\develops\tmp\dbwave_w4_idx19\demo.py：

```
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE customer_id=777
→ (2,0,0,'SCAN orders')
CREATE INDEX ix_orders_cust ON orders(customer_id);
→ (3,0,0,'SEARCH orders USING INDEX ix_orders_cust (customer_id=?)')
```

- 同一谓词，加一条二级索引后计划从全表 SCAN 变为树定位 SEARCH——B+树"换读路径"的
  语义在 SQLite 中可完整观察；SQL Server 的对应展示面是执行计划 + `SET STATISTICS IO`
  （本机不可跑，⚠️，文档口径 ✅ Learn）。

## 1.8 判读 FAQ（防止本章被误用的四条）

- **Q：SQLite 实验里加索引立刻变 SEARCH，SQL Server 也应如此？**
  A：不必然——SS 还需过统计估计与成本比较两道门（第 03 章），低选择性谓词下新索引
  可能仍被判 scan/回表。🔧 实验只证明"结构语义成立"，不证明"代价模型必选"。
- **Q：堆表是错误设计吗？**
  A：未必。堆在小批量高速装载+无点查场景有合理性；问题在于**无主见**地停留在堆形态。
- **Q：INCLUDE 列多了会拖慢 seek 吗？**
  A：seek 沿键走树，INCLUDE 只在叶子生效；代价体现在叶子肥化→页数→缓存命中（第 02 章）。
- **Q：唯一性检查能否替代唯一索引？**
  A：应用层检查在并发写入下不封闭；唯一索引是**存储层保证**，这也是第 13 章删除裁决中
  "删不得"清单的常客。

## 核心概念速览（中英对照）

1. **聚簇索引** — clustered index：叶子即数据行的索引，每表至多一个，决定数据物理组织。
2. **非聚簇索引** — nonclustered index：独立 B+ 树，叶子存键+行定位符（locator）。
3. **堆表** — heap：无聚簇索引的表，行以 RID 定位，更新可产生转发指针。
4. **行定位符** — row locator：二级索引叶子回指数据行的指针（RID 或聚簇键）。
5. **键查找** — key lookup：二级索引命中后回聚簇树取完整行的随机 I/O。
6. **B+ 树** — B+ tree：多叉平衡搜索树，中间层路由、叶子层有序串联。
7. **索引定位** — index seek：以可定位键前缀直接进入树根下降的定位操作。
8. **索引扫描** — index scan：无序遍历（全部或部分）索引叶子的操作。
9. **包含列** — INCLUDE column / non-key column：仅存于叶子、不参与排序的覆盖列。
10. **唯一约束** — unique constraint：以唯一索引承载的业务键约束。
11. **写放大** — write amplification：每多一个索引，每次 DML 需同步维护的树数量。
12. **回表** — table access via locator：中文语境对 key lookup/回取整行的通称。
