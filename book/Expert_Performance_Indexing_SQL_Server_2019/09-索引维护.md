# 09 · 索引维护（Index Maintenance）

> 原书 Chapter 9 "Index Maintenance"，pp.261–318（✅ Crossref，DOI …_9）。58 页运维重章：
> 碎片的度量、REBUILD/REORGANIZE 的语义边界、维护策略的证据化。⚠️ 叙事重构，✅ 锚 Learn。

## 本章主线

页内空隙被随机键插耗尽 → 页分裂 → 逻辑顺序与物理邻接脱钩 = 碎片。本章反对"每夜
10%/30% 阈值一刀切"的行业咒语（Ola Hallengrim 式脚本文化的盲区 ⚠️ 提及人名仅作生态
坐标），主张**按索引角色与维护预算**定制策略。⚠️

## 9.1 碎片的度量与分类 ⚠️/✅

- `sys.dm_db_index_physical_stats` 的 avg_fragmentation_in_percent（逻辑 vs 物理页序错位，
  IN_ROW 叶层）+ page_count/link_count 面貌；LOB/行溢出页的碎片不在同一视野 ⚠️。
- 度量成本：LIMITED 模式抽样快、SAMPLED/DETAILED 渐重；百万页大表全量 DETAIL 本身就是
  维护事件——采样口径先行。⚠️
- 内部碎片（页填充度下降）与外部碎片（区间交错）对顺序读的影响权重不同，扫描型负载
  对后者更敏感。⚠️ 转述

## 9.2 REORGANIZE vs REBUILD 的语义分界 ⚠️/✅

- ALTER INDEX ... REORGANIZE：在线的轻量叶页整理（单页级重排），日志量小、可暂停；
- REBUILD：整树重建（新分配→排序→切换），可换压缩/填充因子，ONLINE=ON 需版本/层级
  支持（Enterprise 口径随版本 ⚠️）；非聚簇 REBUILD 同时刷新统计（聚簇则需另行 UPDATE
  STATISTICS，2019 的统计刷新联动口径 ⚠️ 转述）。
- 决策表（重构 ⚠️）：碎片高+读敏感+窗口够 → REBUILD ONLINE；碎片中+窗口紧 → REORGANIZE；
  碎片高但零读（DMV 证据，ch13）→ 考虑删除而非维护。

## 9.3 维护的策略层 ⚠️ 重构

1. **豁免清单**：堆、小表（<1000 页 ⚠️ 经验带）、批量落地的 staging 索引不参与日常整理；
2. **频率绑定证据**：碎片增速=键随机度×写率的函数，递增键表可能终身不需要 REBUILD；
3. **维护窗口经济学**：REBUILD 的 I/O 与备份链、日志增长争预算——先量预算再定阈值；
4. **变更即测试**：任何阈值调整在等价环境跑一轮才进生产（ch15 方法论回环）。
- 2019 关联：tempdb 内存优化元数据降低目录扫描维护开销 ⚠️（ch3 同款口径）。

## 9.4 统计信息在维护日的联动 ⚠️

- 维护作业序列常识（重构）：先索引结构（REBUILD/REORGANIZE），后统计（UPDATE
  STATISTICS 或依赖自动刷新），避免"重建刷新了统计又被旧采样覆盖"的自伤顺序；
- 采样率随表规模上调（大表 20% 采样已足够密 ⚠️ 经验值），关键倾斜表定点 FULLSCAN。
- ✅ 统计官方概念页（手动/自动更新语义）：
  https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics

## 9.5 🔧 本机类比：维护成本量级（非本书引擎行为）

环境：python sqlite3 3.45.3 / 同 demo.db（SQLite 无在线整理语义，取其**整树重建**面）：

```
REINDEX ix_cov（1128 页覆盖索引整树重建）：0.234s
对比：INSERT 20k 行走 5 个索引结构：0.127s
```

- 诚实边界：SQLite 的 REINDEX≈REBUILD（无 fillfactor/ONLINE 概念），碎片本身 SQLite 以
  freelist 机制表现不同——本类比**只登记"重建成本可测且与批量写同量级"**这一条，
  9.1 的百分比阈值体系属 SQL Server，全部 ⚠️ 转述。
- 可迁移的观测设计：维护前后各拍一次"对象页数 + 典型查询计划 + 运行时间"三件套
  （§2.7 dbstat 面），即可用数字回答"这次整理值不值"——SQL Server 用
  dm_db_index_physical_stats + 查询存储对位（✅ U 见 §9.6）。

## 9.9 判读 FAQ

- **Q：维护能恢复被删光的数据页红利吗？**
  A：部分能：整理/重建恢复物理邻接，但缓存内容已被挤占的真实成本要靠负载时间曲线验证。
- **Q：为什么重建后反而变慢？**
  A：FILLFACTOR 选错（空隙=未来分裂缓冲=现在多读页）、统计未联动刷新、缓存冷启三选一先排查。
- **Q：小表碎片高要紧吗？**
  A：百页以内表的碎片读税约等于噪声；把维护预算让给大表是正解，一刀切方案在此最失真。
- **Q：递增键的索引需要 REORGANIZE 吗？**
  A：尾部追加基本不产生内部碎片；这类索引的维护需求清单通常为空——豁免清单的常客。
- **Q：日志量差多少？**
  A：REBUILD 全程登记新树（大表=备份链事件），REORGANIZE 增量小；恢复模式与窗口共同决定可行集。⚠️
- **Q：碎片率高但计划都正常，维护吗？**
  A：先回答维护想换什么（读 I/O？锁面？空间？）：无预期收益指标的高碎片是良性景观。
- **Q：在线重建真“零影响”？**
  A：两阶段切换+日志回放的资源挤占仍在，且长事务会拖尾；“在线”=可读写，不等于无痛。⚠️
- **Q：内存优化表进维护名单吗？**
  A：无页无语义
- **Q：把维护做成周报的依据链？**
  A：三件套前后对比（§9.5）+ 成本页数量差 + 受影响负载时长——缺一不进报表。

维护章的反直觉结论：多数“必须每晚整理”的动作在证据下会自我取消——留下的才是工艺。

## 核心概念速览（中英对照）

1. **碎片率** — fragmentation percent：逻辑页序与物理页序的错位度。
2. **内部/外部碎片** — internal/external：页内填充空洞 vs 区间级交错。
3. **页分裂** — page split：叶页满后按键序拆半腾位的写放大事件。
4. **REORGANIZE** — 叶整理：在线、可暂停、单页级的轻量碎片整理。
5. **REBUILD** — 重建：整树重排，可改压缩/填充因子，成本最高档。
6. **ONLINE 索引操作** — online rebuild：重建期保留读写可用性的能力（版本/层级 ⚠️）。
7. **dm_db_index_physical_stats** — 物理统计 DMF：fragmentation/page_count 度量入口。
8. **LIMITED/SAMPLED/DETAILED** — 度量三档：成本递增的碎片观测模式。
9. **维护豁免清单** — maintenance exclusion：不参与日常整理的小表/staging 表集合。
10. **窗口经济学** — window economics：维护预算与备份/日志增长的挤占分析。
11. **维护顺序联动** — maintenance ordering：结构先、统计后的作业编排常识。
12. **三件套验证** — before/after trio：页数+计划+时长的维护效果证据法 🔧。
