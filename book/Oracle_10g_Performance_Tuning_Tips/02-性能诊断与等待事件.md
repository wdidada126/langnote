# 02 性能诊断与等待事件 — Oracle Database 10g Performance Tuning Tips & Techniques（精读重构）

> ⚠️ 主题重组口径（章号非原书章号，降级声明见 [00-总览与阅读地图.md](00-总览与阅读地图.md) §3）。本章=全书心脏的"账本篇"：等待事件接口、AWR/Statspack/ASH/ADDM 四件账本的读法。
> Oracle 行为一律 ⚠️ 转述（引擎不可本机实测）；官方文档锚点 ✅（10.2 B14211 Ch5/6/10，https://docs.oracle.com/cd/B19306_01/server.102/b14211/toc.htm 本会话实抓）。

## 1. 等待接口：把"慢"翻译成"在等什么"

- 原理 ⚠️（10g 通说）：服务器进程每做一次可能耗时的外部动作（读块、写日志、等锁、等 CPU 队列），就记一次"事件名+耗时"；`V$SESSION_EVENT`（会话×事件）、`V$SYSTEM_EVENT`（实例合计）、`V$SESSION_WAIT`（此刻）是三面镜子。
- 记账恒等式 ⚠️：**DB time ≈ Σ 非空闲等待时间**。调优=让"高耗时事件"从账本上消失或变得合理。
- 空闲/非空闲分界：`SQL*Net message from client`（等客户端下一条）是空闲类，**不计入病灶** ⚠️——这是新手第一坑，10g 的 wait class（`V$EVENT_NAME.WAIT_CLASS`）把分类做进了视图 ✅。
- 与 #28 册互认：同代 O'Reilly 册的等待章为 ⚠️ 通说（[../Oracle_Performance_Tuning_2e/02-等待事件与响应时间分析.md](../Oracle_Performance_Tuning_2e/02-等待事件与响应时间分析.md)）；本章立场与其一致，证据锚点不同。

## 2. Top 事件速诊表（⚠️ 10g 时代通说病理事典）

| 事件 | 在等什么 | 常见病根 | 下一步视图 |
|---|---|---|---|
| `db file sequential read` | 索引单块读 | 逻辑读过大/聚簇因子差/冷缓存 | `05/06` 章计划判读 |
| `db file scattered read` | 全表扫多块读 | 统计缺失弃索引/mbrc 配小 | `04` 章 IO |
| `log file sync` | 提交等日志落盘 | 日志盘竞争/提交过频 | `04/09` 章 |
| `log file parallel write` | LGWR 写盘本身慢 | 存储层延迟 | OS IO 特征 |
| `latch: shared pool` | 库缓存闩 | 硬解析风暴/未绑定变量 | `05` 章解析经济学 |
| `enq: TX - row lock contention` | 行锁 | 热点行/长事务 | `08` 章 |
| `read by other session` | 首读被同伴占 | 热块并发进入 | ITL/freelist（`08`） |
| `direct read write`（路径加载） | 旁路写 | 批量装载设计 | `09` 章 |
| CPU 无等待（time model 缺口） | 根本没等 | 解析/函数行处理 | 10046+tkprof |
| `control file sequential read` 高频 | 控制文件打卡 | checkpoint/SCN 节拍 | AWR `Checkpoints` 节 |

- 使用纪律 ⚠️：事件名只指"层"，不指"因"；同一事件可以有病理性与生理性两种存在（如 `db file sequential read` 之于健康索引访问）。

## 3. 四件账本的分工（本册时代全景）

1. **Statspack**：快照对（snap A→B）出报告；标准版免费，深夜巡检老牌 ✅（脚本名 ⚠️ `spreporta.sql` 系）。
2. **AWR**（10g 新生，企业版+诊断包许可 ⚠️）：后台 MMON 定期快照入 `WRM$/DBA_ADVISOR_*`；`AWRRPT` 出报告； retention 默认 7 天 ⚠️（贴士册常教改 `SYSAUX` 尺寸与之配套 ⚠️）。
3. **ASH**：内存 1 秒采样环，"冻结现场"用；报告 `ashrpt.sql` ⚠️；解决"事后无 V$SESSION_WAIT"的历史取证。
4. **ADDM**：读 AWR 快照对跑规则树，输出按 DB time 加权的诊断+建议清单；`DBA_ADVISOR_FINDINGS` 视图查 ⚠️。
- 组合拳 ⚠️（本册风格）：AWR 找层 → ASH 找人（session/sql_id） → `V$` 视图找因 → 10046 找行级证据。与 TOP 2e 第 4/5 章同一路线（✅ [../Troubleshooting_Oracle_Performance_2e/04-不可复现问题的实时分析.md](../Troubleshooting_Oracle_Performance_2e/04-不可复现问题的实时分析.md)）。

## 4. AWR 报告的"三遍读法"（⚠️ 通说）

- 第一遍只看头部 6 行：DB time/每秒 redo/缓冲命中率/解析比/硬解析比/Top 事件占比——五分钟定层。
- 第二遍看 Segments by I/O 与 SQL by Elapsed：把"哪个段、哪条 SQL"钉上行号。
- 第三遍才看参数与 advisory 节：任何"改参数"冲动必须以前两遍证据为前提。
- 陷阱清单 ⚠️：命中率是派生指标不是目标（98% 命中可以照样慢）；`SQL ordered by Gets` 排在 `by Elapsed` 前可能误导批处理场景；快照窗口跨维护任务会污染基线。

## 5. 从等待到 SQL：sql_id 是贯穿键

- 路径 ⚠️：AWR Top SQL（`DBA_HIST_SQLSTAT`）/ASH 采样里的 `SQL_ID` → `V$SQL`（子游标/解析次数/版本计数）→ `V$SQL_PLAN`（真身计划）→ 10046 跟踪 + tkprof（服务时间分解）。
- 硬解析账 ⚠️：`V$Sysstat` 的 `parse time (hard)`、`V$LibraryCACHE` 的 miss/reload；贴士册经典条目："共享池闩等待先看每会话解析率"。
- 与跨引擎同构：SQL Server 用 DMV 等待统计+`sys.dm_exec_query_stats` 走同一条"层→查询→计划"路径（✅ [../SQL_Server_Advanced_Troubleshooting/02-动态管理视图与等待统计.md](../SQL_Server_Advanced_Troubleshooting/02-动态管理视图与等待统计.md)）；MySQL 用 performance_schema events_waits（✅ [../Efficient_MySQL_Performance/00-总览与阅读地图.md](../Efficient_MySQL_Performance/00-总览与阅读地图.md)）。

## 6. 无诊断包环境的"穷人的 ASH"（⚠️ 贴士体裁特色）

- 定时脚本 `select ... from v$session_wait` 落表采样（5–10 秒一轮），事后聚合近似历史 ⚠️——Statspack 时代手工艺，本册体裁最可能收录此类贴士。
- 10046 level 10/12 全量跟踪仅开给嫌疑会话（⚠️：trace 文件体积与性能税）。
- 现代对照 ✅：19c/23ai 仍有 ASH 公共视图子集（`V$ACTIVE_SESSION_HISTORY` 非诊断包可见部分口径以文档为准 ⚠️）——本册时代的"土法采样"已无必要。

## 7. 诊断脚本小抄（⚠️ 语法按 10g 通说，生产勿直抄）

```sql
-- 此刻非空闲等待 Top（会话级）
SELECT sid, event, seconds_in_wait, state
  FROM v$session_wait
 WHERE wait_class <> 'Idle' ORDER BY seconds_in_wait DESC;
-- 系统级事件占比
SELECT event, total_waits, time_waited
  FROM v$system_event
 WHERE wait_class <> 'Idle' ORDER BY time_waited DESC;
-- 事件分类表（空闲/非空闲的权威口径）
SELECT name, wait_class FROM v$event_name ORDER BY wait_class;
```
- 与 `V$SYSSTAT` 的 time model 行（`DB time`/`sql elap`）合读才成闭环 ⚠️（10g 起 time model 入统计 ✅ 概念锚：B14211 Ch5）。

## 8. 常见误区三则（⚠️ 通说）

1. **等完再诊断**：`V$SESSION_WAIT` 只在等待瞬间有值——要历史用 ASH/AWR，要精确用 10046。
2. **把 ADDM 结论当处方**：ADDM 给"哪类资源+建议动作族"，不给"这条 SQL 怎么改"；处方权在人。
3. **跨版本比报告**：AWR 的指标口径随版本微调 ⚠️，10g 报表直接对 19c 报表=错误对照。

## 9. 三层下钻现场工：从 AWR 头部到病灶（⚠️ 情景重组）

以"白天 OLTP 偶发卡顿、夜间恢复"的模糊工单走一遍完整取证链（本册体裁最典型的"跟着做"流程）：

1. **层一：定窗**。AWR 取卡顿 30 分钟窗口 vs 昨日同窗（基线对照，`01` 章恒等式）。头部差异：DB time +40%，`read by other session` 进入 Top 5 ⚠️。
2. **层二：定对象**。ASH 按 `CURRENT_OBJ#` 聚合：单表热段；AWR `Segments by Buffer Busy` 同点印证 ⚠️——`V$SEGMENT_STATISTICS` 的 `gc/cr` 行给出"读被占"证据（→ `08` 章段头账）。
3. **层三：定语句**。ASH 按 `SQL_ID` 聚合：两条 UPDATE 交错；`V$SQL_PLAN` 复核其路径（索引命中正常）→ 病灶不是 SQL 写法而是**并发进入同块** ⚠️。
4. **处置阶梯**（单变量纪律，一次一档）：事务错峰 → 键散列（分区/哈希分布 → `06/08`）→ 缓冲分片参数（`03` 章，最后手段）。
5. **回表**：同窗 AWR 对比 + ASH 事件占比复测；报告归档进变更单。
- 本章的账本（AWR/ASH/V$ 三件套）在流程里各司其职：**AWR 定时定序，ASH 定人定话，V$ 定因**。
- 反模式速写 ⚠️：跳过层二直接改参数（"加内存治锁等"）；只看 AWR Top SQL by Elapsed 忽略等待构成——elapsed 高的批量任务未必是元凶。

## 10. 等待接口练习三题（⚠️ 通说答案在本章）

1. `db file sequential read` 占比 60% 但逻辑读/执行计划均健康——诊断：生理性索引负载，转入 CPU 时间核对，不动存储参数。
2. `log file sync` 高而 `log file parallel write` 正常——诊断：LGWR 排队/提交过频，走应用侧事务边界（`09`）而非日志盘扩容。
3. 空闲等待 `SQL*Net message from client` 巨大——诊断：应用侧节流问题（人肉点击/批间隙），不属 DB time 病灶账。
- 三题共用一个心法 ⚠️：**事件名指"等谁"，上下文（配对事件+对象+SQL）才指"为何等"**。

### 附记：等待事件名漂移小注（⚠️ 跨版本实用兜底）

- 事件名会随代际改名/拆分（本册后例：11g 起 `log file sync` 细分子事件、`SQL*Net` 族多次调整口径 ⚠️）；把 10g Top events 结论平移到 19c/23ai 前，逐条在新版 `V$EVENT_NAME` 里映射一遍 ✅ 方法（对读 00 §12.7 文档门户）。
- 映射三查：名称还在吗？空闲/非空闲归类变了吗？配对的"另一侧事件"换名了吗（sync↔parallel write 型配对关系）⚠️。
- 本目录速诊表的失效兜底就是这三查——先对名，再对类，后对因。

## 核心概念速览（中英对照）

| 中文 | 英文 | 一句话 |
|---|---|---|
| 等待事件 | Wait event | 进程一次耗时动作的记账名 |
| 空闲等待 | Idle wait | 不在干活的等，不计病灶 |
| 数据库时间 | DB time | 全体用户会话消耗时间总和 |
| 等待类 | Wait class | 10g 起事件的分组口径 |
| 快照对 | Snapshot pair | 两次采计数切片做差 |
| 会话采样 | ASH sampling | 每秒活跃会话的冻结照片 |
| 诊断结论 | ADDM finding | 规则树加权产出的病灶条目 |
| 时间模型 | Time model (V$SYSSTAT) | DB time 的构成分解账 |
| 应用跟踪 | Application tracing (10046) | 会话级事件+等待行记录 |
| 性能剖析 | Profiling | 用账本把慢定位到对象/语句 |
