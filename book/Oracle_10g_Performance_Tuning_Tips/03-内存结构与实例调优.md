## 1. 内存地图：10g 实例的一页剖面（⚠️ 通说）

- SGA = 共享池（库缓存+字典缓存）+ 缓冲缓存（默认池/KEEP/RECYCLE 多块池）+ 重做日志缓冲 + （10g 新）大型池/Java 池等附属池。
- PGA = 会话私有：排序区/哈希区/游标状态/会话内存；10g 起可用**自动 PGA 管理**（`workarea_size_policy=AUTO` + `pga_aggregate_target`）替代 9i 的逐区手工（`sort_area_size` 族）⚠️——贴士册的典型条目即"哪些场合手工区仍值得固定"。
- 机理纵深请转盘上双权威：《Oracle 编程艺术》中文单文件（✅ [../Oracle编程艺术：深入理解数据库体系结构（第3版）.md](../Oracle编程艺术：深入理解数据库体系结构（第3版）.md)）与 [../Oracle_Internals_An_Introduction/05-内存与共享池.md](../Oracle_Internals_An_Introduction/05-内存与共享池.md)；本章只留"调优视角的配比账"。

## 2. 缓冲缓存：命中率背后的三本账

- 账一 命中率：`V$BUFFER_POOL_STATISTICS` 的 consistent+current get vs physical read ⚠️——99% 可以照样有病（热块闩），90% 可以完全健康（DSS 全扫型）。
- 账二 尺寸建议：10g 官方 advisory 视图 `V$DB_CACHE_ADVICE`（估算改池后的 physical read 曲线）✅ B14211 Ch7；贴士用法=找曲线拐点而非填满内存 ⚠️。
- 账三 池谱：`db_block_lru_latches`（池分片降闩）、`_number_of_lru_latches` 隐藏参 ⚠️、KEEP 池钉热小表（`storage (buffer_pool keep)`）、RECYCLE 池隔离大表防止冲刷 ⚠️——"三池分流"是本册时代的高级贴士。
- 双缓冲池与多块读配合（`db_block_prefetch*`）→ `04` 章 IO 线。

## 3. 共享池与解析：本册时代的"第一 CPU 杀手"

- 结构 ⚠️：库缓存存"语句+计划"（共享 SQL 区）与句柄；字典缓存存解析中间产物；两者共用 `shared_pool_size`。
- 饥饿病理 ⚠️：共享池不足 → 老化（aging out）→ 硬解析风暴 → `latch: shared pool`/`library cache` 等待 → 更慢的解析 → 恶性循环；`V$LIBRARYCACHE` 的 RELOAD、`V$SGASTAT` 碎片类条目（free memory 连续段大小）是证据面。
- 10g 自动化：`shared_pool_advisory`/`sharable memory` 视图 ✅ B14211 Ch7；`cursor_sharing` 三值（EXACT/SIMILAR/FORCE）是止血带不是解药 ⚠️（SIMILAR 在绑定+直方图时代成雷区 → `07` 章）。
- 应用侧解药（往返经济学总账在 `09`）：**绑定变量**——本册必然浓墨的贴士（⚠️ 推定体裁重点），解析成本对比表可平移任何引擎。

## 4. 10g 的自动化分水岭：ASMM 与 AMM

- `statistics_level=TYPICAL/ALL`（10g 新）是自动 advisory 的总开关 ⚠️——关掉它，本章多数"建议视图"失明。
- ASMM（10.2 引入 ✅ B14211 Ch7/Ch4 口径）：`sga_target` 一个数，MMAN 按负载在共享池/缓冲池/大池间搬内存；贴士面：哪些专用负载（如重解析 OLTP）应仍钉死成分。
- AMM（10.2 起 `memory_target` 一步管 SGA+PGA ⚠️）：Windows 与非 /dev/shm 环境的内存归化 ⚠️——本册时代刚出生，其坑（大机 swap、NUMA 观感）是后来者补的课。
- 工程判定 ⚠️：本册主体成文于手工配比与自动化交接期——"手工账你都要会算，自动池你要会看"是它最耐读的一句话。

## 5. 🔧 类比 D4：排序区不足的世界长什么样（SQLite 3.45.3，非 Oracle）

数据与计时见 `D:\develops\tmp\dbwave_w10_ora10g\demo_out.txt`（脚本 `demo.py` 本会话实跑）：

- 无索引列排序 `ORDER BY pad LIMIT 10` → 计划 `SCAN big` + **`USE TEMP B-TREE FOR ORDER BY`**：20 万行全表进临时 B 树再取头 10。
- 索引供序 `SELECT a,b FROM big WHERE a<3 ORDER BY a,b` → `SEARCH big USING COVERING INDEX ix_ab (a<?)`：无临时 B 树，计划里"排序"节点整体消失。
- 计时对照：**临时 B 树排序 12.789 ms vs 供序 11.221 ms（LIMIT 10，本表键窄+排序早停，差距被小 LIMIT 压平——诚实边界 ⚠️）**；把 LIMIT 放大或列变宽，临时 B 树的 CPU+IO 税按行数增长（SQLite 单语句内存上限受 `PRAGMA cache_size` 影响，溢出落盘临时文件——概念同构 Oracle 排序区溢出 `sort runs=磁盘` 的 ⚠️ 账本）。
- 对读 Oracle ⚠️：`SORT ORDER BY`/`SORT GROUP BY` 行操作、PGA workarea 的 one-pass/multi-pass 计数（`V$SQL_WORKAREA_ACTIVE`、`V$SYSSTAT` 的 one-pass 族）——"排序不给你看，溢出才现身"是 10g 贴士的排查要点。自动 PGA 的失败模式正是：大排序互相挤占 → 全体降级 one-pass → 吞吐雪崩 ⚠️。
- **判定：非 Oracle 引擎行为**，仅供"排序=有价格的操作"这一直觉的跨引擎校准。

## 6. 内存类贴士清单（⚠️ 通说重组，按对象分组）

- 缓冲池：热表进 KEEP；月报扫全表历史大表进 RECYCLE；`db_file_multiblock_read_count` 别贪大（→ `04`）。
- 共享池：`session_cached_cursors` 抬句柄命中；`shared_pool_size` 留出硬解析峰值余量；避免 `alter system flush shared_pool` 当"万灵药" ⚠️。
- PGA：批处理会话可 `alter session set workarea_size_policy=MANUAL` 单点放大排序区 ⚠️（经典夜批贴士）；OLTP 会话留给 AUTO。
- 判定顺序：先看等待与 stats 是否指认内存，再谈配比——**内存参数是最容易被冤枉的病灶** ⚠️。

## 7. 观测视图速查（⚠️ 名称按 10g 通说）

## 9. 库缓存小词典（⚠️ 通说，读贴士前的名词关）

- **句柄（handle）vs 共享区（heap）**：会话持句柄引用共享 SQL 区；`V$DB_OBJECT_CACHE`/`V$SHARED_SQL_AREA` 族给对象级账。
- **库命中 vs 执行命中** ⚠️：命中=语句文本找到可复用（省语法/生成）；执行命中=还带可用计划与绑定态（`V$LIBRARYCACHE` 的 PINS/HITS 族分两本账）。
- **失效（invalidation）三源**：依赖对象 DDL、统计重采（10g 起 `DBMS_STATS` 会触游标失效 ⚠️——"采完统计计划全换"的次日惊厥源头）、内存压力老化。
- **reload**：共享区被挤出后重建，比硬解析轻但同属"重复劳动"账 ⚠️；`V$LIBRARYCACHE` 的 RELOAD 列是共享池饥饿的早期烟雾报警器。
- 版本计数（`V$SQL` CHILD 行数）：绑定元数据/环境不一致会造"同语句多子游标"版本爆炸 ⚠️——SIMILAR 模式与 NLS 差异是两大经典因（`05/07` 章合流点）。
- 纵深对读 ✅：[../Oracle_Internals_An_Introduction/05-内存与共享池.md](../Oracle_Internals_An_Introduction/05-内存与共享池.md)（服务级机理）与《Oracle 编程艺术》共享池章（✅ 在盘单文件）。

## 10. 内存病五场景速诊（⚠️ 重组；每场景=证据+处方阶梯）

| 场景 | 账本证据 | 处方阶梯（先窄后宽） |
|---|---|---|
| 硬解析风暴 | `latch: shared pool`+高 parse 率+低执行命中率 | 应用绑定改造（`09`）→ `session_cached_cursors`↑ → 池扩（最后） |
| 热表物理读高 | KEEP 池候选：`V$DB_CACHE_ADVICE` 拐点+对象级读频 | KEEP 钉表 → 分片参数 → 扩池 |
| 大表冲刷缓存 | RECYCLE 候选：scattered read 占比+单次全扫 | RECYCLE 隔离 → 并行全扫错峰（`09`） |
| 夜批排序溢出 | PGA one-pass 计数+TEMP 高峰 IO | 会话级 MANUAL 放大 → `pga_aggregate_target`↑ → 改写 SQL 少排（`07`） |
| 池间互相挤 | ASMM 搬池日志+两侧 advisory 同红 | 拆峰时段 → 钉成分（专用池下限）→ 回退手工配比 |
- 读法：先让"账本指认内存"（左列），再按阶梯从窄往宽动（右列）——**本册所有内存贴士都能装进这张表**（⚠️ 重组断言）。
- 与 `10` 章反查索引互扣：本表左列的事件名即反查表的入口键。

### 附记：内存×症状对应三线口诀（⚠️ 重组收束）

- 池口诀：**读多找缓冲、解析找共享、排序找 PGA**——三池各管一类账，先归类再谈参数 ⚠️。
- 证据口诀：**advisory 给趋势，等待给现场，计数给次数**——`V$*_ADVICE` 的预估曲线只是"如果改尺寸"的假设账单，等事件与 `V$SYSSTAT` 才是当期实际 ⚠️。
- 自动化口诀：ASMM/AMM 时代"钉参数=辞职信"——先证明自动化判错（对比 `V$SGA_TARGET_ADVICE` 与人工推理），再回退手工配比 ⚠️。
- 三线口诀合成本章三张账（命中率/尺寸建议/池谱）的动作面；与 `10` 章反查索引互扣，事件名进、参数名次出。
- 教学诚实话 ⚠️：口诀负责不漏，不负责判对——判对靠第 10 节速诊表的左列证据。
### 附记二：一页纸记忆钩（⚠️）

## 最新演进与工业实践

- **自动化接棒 ✅**：10.2 的 ASMM 至今是自建库默认姿势（19c/23ai PTG 的 Memory 章在册——✅ 19c/23ai 门户本会话实证，00 §12.7）；`memory_target`/AMM 在大机与 Linux hugepages 场景被官方口径长期劝退（12c 文档起明确限制 ⚠️），工业实践收敛为 hugepages+ASMM。
- **视图换代 ⚠️**：`V$DB_CACHE_ADVICE` 等 advisory 系仍在；PGA 建议演进为 `V$PGA_TARGET_ADVICE_HISTOGRAM`（11g）；共享池的"碎片恐惧"随子池（subpool，8i 起）与 12c 的改进基本退场 ⚠️。
- **云上终局**：自治数据库把配比问题整体没收（用户不再见 `sga_target`）✅ 概念锚 docs.oracle.com Autonomous 线（URL 本会话未实抓 ⚠️）——本册"配比学"的教学价值转为**理解自动化替你做的决定**。
- **排序话题跨引擎**：任何引擎都逃不开"内存排序 vs 落盘排序"的账——DuckDB 的 work 文件溢出、PostgreSQL 的 `work_mem` spill（盘上在册目录 `../PostgreSQL_10_High_Performance_3e/`，登记）、MySQL `sort_buffer_size`（✅ [../高性能mysql.md](../高性能mysql.md)）；本章 🔧 D4 的"供序消灭排序"在 SQL Server 叫 index 有序扫描（✅ [../SQL_Server_Advanced_Troubleshooting/05-索引碎片与索引维护.md](../SQL_Server_Advanced_Troubleshooting/05-索引碎片与索引维护.md) 同域）。
- **2026 姿势**：内存病排查主干仍是 `V$SGASTAT`+advisory+等待三联；本册参数名录当"字典源"查，不当当"处方笺"抄。
