## 核心精讲

（以下为教学性梳理，代码均**教学示意，不参与构建**。）

### 6.1 mmap：把文件当内存

`mmap(2)` 把文件（或一部分）直接映射进进程虚拟地址空间，读写就像访问数组，内核负责
缺页加载与回写。好处是**省掉 read/write 的拷贝**；风险是：缺页触发同步磁盘读（毛刺）、
回写时机不可控、大文件映射消耗地址空间与 TLB。

```go
// 教学示意，不参与构建：mmap 语义（Go 标准库无直接 mmap，通常 syscall 或 mmap-go）
data := mmap(fileFd, offset, length)   // 返回可像 []byte 访问的映射
process(data[0:1024])                   // 像内存一样读，内核按缺页加载
// 改完需 msync 保证落盘，munmap 释放
```

### 6.2 异步 I/O：io_uring 是 2026 年的主角

传统 `read/write` 是同步阻塞（或线程池模拟异步）。真正的异步 I/O 让应用「提交一批请求、
稍后收割完成」，从而：① 不阻塞线程；② 把 NVMe 的多队列深度喂满。

- **libaio**：老牌异步 I/O，但仅支持 O_DIRECT、接口笨重；
- **io_uring**（2019 起）：共享环形队列 + 提交/完成分离，支持轮询模式近乎零开销，
  是 2026 年高吞吐存储的事实标准（🔧 2026 视角）。

### 6.3 splice/sendfile：内核内搬运

见第 5.3，这里强调它与「事件驱动 + 异步」的搭配：代理/网关类服务可在不触碰用户态缓冲的
情况下把数据从文件 fd 搬到 socket fd。

### 6.4 事件驱动：epoll 与单线程万级连接

`epoll(2)` 用就绪通知替代「每连接一线程」或忙轮询，让单线程/少量线程管理海量 fd。
这是第 7 章并发模型（Reactor）的内核侧支撑，也是 `gnet` 等框架的底座。

## 版本演进

- 🔧 **2026 视角补入（最重要的一条）**：本书若写异步 I/O 时以 libaio 为主，需补 **io_uring**。
  2024 年书出版时 io_uring 已成熟，但不少教材仍偏重 libaio；2026 年视角 io_uring 是默认选择。
- 6.1 mmap 的权衡（缺页毛刺、大文件地址空间）长期成立，无本质变化。

## 近年研究与工业界开源实践（2015–2026）

- **io_uring 生态**：Rust `tokio-uring`、C 系 `liburing` 等；Go 侧有 `pollereio`/`uring` 类绑定
  （star 数未能核实，未杜撰），以及 `panjf2000/gnet`（11251★）在事件驱动网络 I/O 上对 epoll 的封装。
- **内存映射型 KV/存储**：LMDB 一系用 mmap 做存储（见仓库内其他书对 COW/MVCC 的论述），
  是 6.1 的工程实证。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「mmap 一定最快」 | 缺页毛刺、回写不可控、TLB 压力，大文件未必优于 read |
| 2 | 「异步 I/O 就是开线程」 | 线程池是模拟异步，真异步（io_uring）才能喂满 NVMe 队列 |
| 3 | 🔧 异步只讲 libaio | 2026 年默认是 io_uring，libaio 受限多 |
| 4 | 「epoll 万能」 | epoll 擅长网络 fd；磁盘 fd 的异步仍需 io_uring 类 |
