## 核心精讲

（以下为教学性梳理，代码均**教学示意，不参与构建**。）

### 7.1–7.2 goroutine 与池：既要并发，也要可控

第 1 章说 goroutine 轻（几 KB 栈），但「一请求一 goroutine」若遇突发百万请求，
仍会耗尽 fd、内存与调度器。工程做法是用**工作者池**限制「同时在跑」的 goroutine 数：

```go
// 教学示意，不参与构建：用带缓冲 channel 当信号量做并发上限
sem := make(chan struct{}, 1024)   // 最多 1024 个并发任务
for _, job := range jobs {
    sem <- struct{}{}              // 获取令牌，满则阻塞（背压）
    go func(j Job) {
        defer func() { <-sem }()   // 释放令牌
        process(j)
    }(job)
}
// 也可用 panjf2000/ants 这类池库（见开源实践）
```

### 7.3 Reactor vs Proactor

- **Reactor**：事件就绪（可读/可写）时回调你，你**自己**去做读写（阻塞点在你手里）；
  经典配 epoll。Go 的 netpoller 底层就是 Reactor 思路。
- **Proactor**：你发起异步读写，**内核完成**后通知你（真正的异步），配 io_uring（第 6 章）。
  Go 运行时把网络 fd 的 Reactor 与 goroutine 调度缝合，使「看似同步写、实则异步」。

### 7.4 epoll：网络并发的内核侧

详见第 6.4。`epoll` 的**边缘触发（ET）**要求一次把可读数据读完，**水平触发（LT）**则宽容但可能多次唤醒；
存储服务常选 ET 以降唤醒次数，但编码更挑剔。

### 7.5 背压：别让下游崩

当生产者快于消费者（如日志写入快于磁盘刷出），须用 channel 缓冲 + 令牌/信号量限流，
否则内存暴涨或下游雪崩。背压是存储服务「稳」的关键，也是与第 8 章缓存「容量边界」呼应之处。

## 版本演进

- goroutine/池/Reactor/背压原则长期稳定，2024 年书出版时与当前一致。
- 🔧 **2026 视角补入**：Go 运行时的网络轮询器（netpoller）持续增强，对 io_uring 的支持在
  社区实验中；若书里把「Go 网络并发」完全归因于 epoll，可补一句「运行时抽象可能演进到 io_uring」。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「goroutine 无限开没事」 | fd/内存/调度都有上限，必须池化或限流 |
| 2 | 「Reactor 比 Proactor 好」 | 网络多用 Reactor，磁盘异步用 Proactor/io_uring 更合适，二者场景不同 |
| 3 | 「背压是可选优化」 | 无背压的服务在突发下会雪崩，是稳定性刚需 |
| 4 | 🔧 网络并发只讲 epoll | 2026 年可补 Go netpoller 与 io_uring 的演进视角 |
