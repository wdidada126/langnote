## 核心精讲

（以下为教学性梳理，代码/伪代码均**教学示意，不参与构建**。）

### 1.1 为什么用 Go 写存储

本书的立论起点：存储系统有大量「**等待 I/O**」的并发场景——一个节点同时要服务成千上万个
读写请求，每个请求大部分时间花在磁盘/网络往返上。传统线程模型（1 请求 1 线程）在此会被
上下文切换压垮。Go 的两点恰好对症：

- **goroutine 极轻**：初始栈仅几 KB，可轻松开数十万并发；对比 OS 线程 MB 级栈与调度开销。
- **channel 做并发编排**：用「通信共享内存」替代「共享内存加锁」，降低并发 bug 面。

```go
// 教学示意，不参与构建：用 goroutine + channel 并发处理一批 I/O 请求
func handleAll(reqs []Request) []Result {
    out := make(chan Result, len(reqs))
    for _, r := range reqs {
        go func(r Request) {        // 每个请求一个 goroutine，轻量并发
            out <- doIO(r)          // doIO 内部是阻塞的磁盘/网络 I/O
        }(r)
    }
    res := make([]Result, 0, len(reqs))
    for range reqs {
        res = append(res, <-out)    // 用 channel 收回结果，而非共享切片加锁
    }
    return res
}
```

> 注意：真实存储系统不会无脑「一请求一 goroutine」，而是用**工作者池**（见第 7 章）做背压，
> 否则 fd / 内存会被打爆。这里是把「并发友好」这个论点讲清楚，不是生产写法。

### 1.2 / 1.3 存储为什么是云变革的基石

云的本质是把「计算、存储、网络」变成可计量、可弹性伸缩的资源。其中**存储最难**：
它要同时承诺持久性（不丢）、可用性（不宕）、一致性（读得对）。本书 1.3 把技术演进拆成两轴：

- **提升速度**：从 HDD → SATA SSD → NVMe SSD → 持久化内存（Optane 已退市，见 🔧），
  以及接口从 SATA → PCIe/NVMe 的带宽跃迁。
- **扩大容量**：单盘密度触顶后，靠**分布式**把成千上万盘的_capacity 聚合成一个命名空间。

## 版本演进

- 本书 2024 年出版，立论（Go 适合存储）已被工业界充分验证：
  `cockroachdb/cockroach`（32509★）、`minio/minio`（61350★）、`vitessio/vitess`（21356★）、
  `etcd-io/etcd`（52310★）都是 Go 写的核心存储/基础设施，可作为「Go 适合存储」的现成证据。
- 🔧 **2026 视角补入**：本书 2024-08 出版当月 Go 1.23 发布，引入 `iter` 包与 `range` 迭代器协议。
  流式 I/O（如逐块读大文件）现在更地道地写成 `for v := range seq`，
  比书中基于回调/闭包的流式写法更省样板；教学代码若重写可体现这一点。
- 🔧 **2026 视角补入**：持久化内存（Intel Optane）已于 2022 年退市，书中若按「未来介质」口吻提及，
  须更正为「已退市，不可作为设计选项」。

## 近年研究与工业界开源实践（2015–2026）

- **Go 存储生态已成气候**（印证 1.1 论点）：
  `etcd-io/etcd`（52310★，2026-09 实测，分布式键值/共识）、
  `minio/minio`（61350★，S3 兼容对象存储）、
  `cockroachdb/cockroach`（32509★，分布式 SQL）、
  `vitessio/vitess`（21356★，MySQL 分片集群）、
  `seaweedfs/seaweedfs`（34989★，分布式文件/对象存储）。
  这些项目共同说明「Go + 存储」不是本书作者的一家之言。
- **存储即服务进一步下沉**：云厂商把块/文件/对象存储做成托管服务，本地存储栈与云存储栈
  通过 CSI（Container Storage Interface）打通，是 2025–2026 年的主流形态（🔧 2026 视角）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Go 性能好所以适合存储」 | 更准确的表述是「**并发 I/O 友好 + 贴近系统 + 易交付**」；纯计算密集场景 Go 仍落后 C/Rust |
| 2 | 「存储只是硬件的事」 | 存储的难点在软件层（一致性、容错、分布式），介质只是底座 |
| 3 | 「分布式是为了更快」 | 分布式首要解决的是**容量与可用性**，单节点性能反而常被网络拖慢（见第 10 章） |
| 4 | 🔧 把 Optane/持久化内存当未来介质讲 | Intel 2022 年退出 Optane，已退市，不能当设计选项 |
| 5 | 🔧 流式 I/O 仍用老式回调 | Go 1.23 起用 `iter` 迭代器协议更地道（2026 视角写法） |
