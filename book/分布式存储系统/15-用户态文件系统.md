## 核心精讲

（以下为教学性梳理，代码均**教学示意，不参与构建**。）

### 15.1 FUSE：把文件系统逻辑搬出内核

FUSE（Filesystem in Userspace）在内核留出钩子：当应用对挂载点做 `open/read/write` 时，
内核 FUSE 模块把这些请求通过**设备/dev/fuse 转给用户态守护进程**，守护进程处理完再把结果回传。
于是你可以用任意语言（含 Go）写文件系统，**不用写内核模块、不用重启机器**。

```go
// 教学示意，不参与构建：用 hanwen/go-fuse 风格挂一个内存 FS（概念骨架，非完整可跑）
func main() {
    fs := NewMemFS()                      // 实现 fs.FS / fuse 节点接口（接第 3 章 3.3）
    mountPoint := "/mnt/myfs"
    // 把 fs 挂上；之后对 /mnt/myfs 的读写会回调 fs.Lookup/Read/Write
    fuse.Mount(mountPoint, fs, &fuse.Options{...})
}
// 每个系统调用经 内核FUSE -> /dev/fuse -> 你的 Go 进程 -> 回传，多一次用户/内核往返
```

### 15.3 把第 13 章的 inode 操作翻译成 Go 函数

第 13 章 Minix 的「超级块/inode/目录项/读写路径」在 FUSE 里变成一组回调：
`Lookup`（按名找 inode）、`Open`、`Read`（按 inode+偏移返回数据）、`Write`、`Create`、`Mkdir`……
你只需维护自己的「inode 表 + 数据存放」（内存、磁盘、甚至远程对象存储都行）。

### 15.5 性能与边界

代价：每次文件操作多一次**用户态↔内核态往返**，高 IOPS 场景不如原生内核 FS；
但换来**开发极简、可随意用 Go 生态（channel、并发、net）**。典型适用：网盘挂载、
对象存储转文件接口、加密/压缩叠加层——`juicedata/juicefs`（14471★）正是这类思路的工业级产品。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「写 FS 必须懂内核」 | FUSE 让用户在态用 Go 写，无需内核模块 |
| 2 | 「用户态 FS 和内核 FS 一样快」 | 多一次往返，高 IOPS 有开销，须用缓存/异步缓解 |
| 3 | 「FUSE 只能做内存盘」 | 后端可以是磁盘/对象存储/网络，灵活度极高 |
| 4 | 🔧 只讲 /dev/fuse 往返 | 2026 年补 io_uring/ublk 降低用户态开销的演进 |
