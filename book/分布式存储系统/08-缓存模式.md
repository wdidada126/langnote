## 核心精讲

（以下为教学性梳理，代码均**教学示意，不参与构建**。）

### 8.2 写回 vs 写透：性能与持久性的天平

- **写透（write-through）**：写缓存的同时同步写后端，缓存与后端始终一致；慢，但丢缓存不丢数据。
- **写回（write-back）**：先写缓存就返回，攒一批再异步刷后端；快，但缓存宕机可能丢未刷数据。
  存储引擎（如第 14 章 LevelDB 的 MemTable）本质是「受控的写回 + WAL 保命」。

### 8.3 替换策略：有限内存丢谁

- **LRU**：最近最少用，实现简单，但「一次全扫」会污染热点；
- **LFU**：按频率，抗扫描但冷启动慢、计数难衰减；
- **ARC / LRU-K / TinyLFU**：现代组合策略，命中率显著优于裸 LRU。
  选策略 = 在「实现复杂度」与「命中率」间权衡。

### 8.4 一致性：缓存最易翻车处

多级/多副本缓存下，后端更新后缓存可能陈旧。`写失效`（ invalidate）比`写更新`（update）更常用；
辅以**版本号/ETag**或**租约（lease）**避免「惊群」与「陈旧读」。分布式场景的缓存一致性
会演化成第 10–11 章的副本一致性问题。

### 8.5 Go 落地

```go
// 教学示意，不参与构建：最简 RWMutex + map 缓存（读多写少）
type Cache struct {
    mu sync.RWMutex
    m  map[string][]byte
}
func (c *Cache) Get(k string) ([]byte, bool) {
    c.mu.RLock(); defer c.mu.RUnlock()   // 多读并发
    v, ok := c.m[k]; return v, ok
}
// 高并发读多写少用 sync.Map；追求命中率用 dgraph-io/ristretto（见开源实践）
```

## 版本演进

- 缓存的写回/写透/替换策略是经典课题，2024 年书出版时与当前一致。
- 🔧 **2026 视角补入**：Go 1.24 的 **`weak.Pointer`** 可用于实现「值可被 GC 回收」的弱引用缓存，
  避免强引用导致对象永远不释放（缓存内存泄漏的经典坑）；书出版时（2024-08）此特性未稳定，
  2026 年应作为 8.5 的新选项补入（呼应 [02-Go语言的数据结构.md](02-Go语言的数据结构.md) 2.4）。

- **Go 高性能缓存库**：`dgraph-io/ristretto`（6994★，2026-09 实测，带 admission/TinyLFU 的

  块/行缓存都体现 8.2 写回与 8.4 一致性的工程取舍。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「缓存一定能加速」 | 命中率低/写密集场景，缓存反而添乱（一致性开销 + 内存） |
| 2 | 「写回和写透二选一」 | 常混合：内存写回 + 关键元数据写透 |
| 3 | 「LRU 够用」 | 扫描型负载下 LRU 命中率远差于 ARC/TinyLFU |
| 4 | 🔧 缓存只讲强引用 map | 2026 年补 Go 1.24 `weak.Pointer` 弱引用缓存，防泄漏 |
