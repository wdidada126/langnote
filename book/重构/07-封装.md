# 第 7 章 封装

> **一句话**：封装的全部意义不是「藏字段」，而是**在同一个地方守住一条规则**——一旦规则散落在调用点，任何一次修改都要靠人脑记住全部副本，封装就是为了让「改一次」而不是「改 N 次」。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 7.1 为什么要封装 | 公开字段/集合意味着把规则交给所有调用方去遵守 | 封装的成本是一次编码，收益是每次修改都只改一处 |
| 7.2 Encapsulate Field 封装字段 | 把字段访问收进方法/属性，把约束放进方法体 | 最小、最快、收益最直接的封装手法 |
| 7.3 Encapsulate Collection 封装集合 | 集合不能就地 `add`，要通过对聚合根发号施令 | 防止集合被外部「偷走并可修改」 |
| 7.4 Replace Data Value with Object 以对象取代数据值 | 「就是一个 number」上其实挂着行为（税、单位、精度） | 基本类型偏执的解药 |
| 7.5 配套：Change Value/Reference 与不可变 | 封装之后要确定「这份数据是值还是引用」 | 值语义让封装真正生效（引用共享会绕过约束） |
| 7.6 封装的度 | 走到哪里停手：别为了封装而生成一堆 getter/setter | 过度封装 = 又一种「夸夸其谈通用性」 |

**关键结论**：
- 封装的判据不是「有没有 private」，而是「**约束住在哪**」。
- 集合是最容易被封装失败的字段类型：把 `List` 返回出去，等于把封装交出去了。
- 封装的前提是「值的语义清晰」——共享的可变对象会绕过任何访问方法。

## 核心精讲

> 教学示意代码，不编译、不运行、不参与构建。

### 1. Encapsulate Field：从公开字段到受控访问

```java
// 教学示意，不参与构建
// ❌ 规则写在调用方：谁都能把折扣改成 0.01
public class Order {
    public double discount;         // 可以设成任意值
}

// ✅ 规则住在字段旁边
public class Order {
    private double discount;
    public void setDiscount(double d) {
        if (d < 0 || d > 0.5) throw new IllegalArgumentException("折扣必须在 0~50%");
        this.discount = d;
    }
    public double discount() { return discount; }
}
```

**为什么值得**：注意一个关键差别——**「哪些调用方不该改」这条知识消失了**。`discount` 公开时，这个知识只存在于「读代码的人的脑子里」；封装之后，它变成了**类型系统能检查的东西**。

### 2. Encapsulate Collection：集合是最容易漏出去的东西

```js
// 教学示意，不参与构建
// ❌ 把集合交给外部：外部可以偷偷 push，聚合根毫不知情
class Cart {
  constructor() { this.items = []; }
  get items() { return this.items; }        // 等于把整个数组交出去
}
cart.items.push(hackedItem);                // 聚合根永远不知道

// ✅ 只暴露「意图」，不暴露「容器」
class Cart {
  #items = [];
  add(item) { if (this.#items.length >= 100) throw new Error("cart full"); this.#items.push(item); }
  remove(item) { this.#items = this.#items.filter(i => i !== item); }
  get total() { return this.#items.reduce((s, i) => s + i.price, 0); }
}
cart.add(new Item(10));                      // 聚合根知道发生了什么
```

| 对外应该暴露什么 | 手段 |
| --- | --- |
| 元素的只读视图（能遍历，不能改） | 返回副本 / 不可变视图 / 生成器 |
| 「加一个」这个动作 | `add` / `attach` 方法 |
| 「数量」「合计」这类派生信息 | getter / 计算属性 |
| 「整个容器」 | **几乎从不**直接暴露 |

### 3. Replace Data Value with Object：一个「简单值」不简单

```js
// 教学示意，不参与构建
// ❌ 基本类型偏执：温度和单位分离，任何人都能写出「 Celsius + Kelvin」
function displayTemp(t) { return `${t}°C`; }
displayTemp(37);
// 一个「数字」上还有：换算、边界、精度、单位合法性 —— 全部散落在调用点

// ✅ 把「温度」变成一个会算、会校验的对象
class Temperature {
  constructor(degree, unit = "C") {
    if (!Number.isFinite(degree)) throw new Error("temperature must be finite");
    this.degree = degree; this.unit = unit;
  }
  toFahrenheit() { return this.unit === "C" ? this.degree * 9 / 5 + 32 : this.degree; }
  toString() { return `${this.degree}°${this.unit}`; }
}
const body = new Temperature(37, "C");
```

**适用信号**（对应坏味道「基本类型偏执」「数据泥团」）：
- 同一个基本值上要挂第二、第三个属性（如 `money: double` + `currency: string`）；
- 同一组基本值总是一起出现（数据泥团）；
- 校验逻辑在多处重复（「温度不能为负」写在三四个函数里）。

### 4. 值 vs 引用：封装之前的必答题

| 考虑项 | 选 Value（值） | 选 Reference（引用） |
| --- | --- | --- |
| 相等性 | `a == b` 应该成立 | 同一身份才能相等 |
| 并发 | 可安全共享 | 必须同步 |
| 生命周期 | 随手丢弃 | 需要创建/销毁/释放 |
| 修改 | 「改」= 造一个新的 | 「改」= 原地改 |

```java
// 教学示意，不参与构建
// 值为 true 的封装才成立：没有 setter，也没有人持有别名
public final class Money {            // final 类 + final 字段 = 不可变
    private final double amount;
    private final String currency;
    public Money(double amount, String currency) { … }
    public Money plus(Money other) { … }   // 「改」= 返回新的
    public boolean equals(Object o) { … }  // 由 amount + currency 决定
    public int hashCode() { … }
}
```

### 5. 封装的度：别把封装做成「纯数据类 + 一堆 getter」

```java
// 教学示意，不参与构建
// ❌ 伪封装：字段全是私有的，getter/setter 全在，行为全在别处（纯数据类）
class Customer {
    private String name;
    private String email;
    public void setName(String n) { this.name = n; }
    public void setEmail(String e) { this.email = e; }
    public String getName() { return this.name; }
    public String getEmail() { return this.email; }
}
class CustomerFormatter { String display(Customer c) { return c.getName() + " <" + c.getEmail() + ">"; } }

// ✅ 真封装：字段收起来，同时把行为搬进来（Encapsulate Field → Move Method）
class Customer {
    private final String name;                       // 构造时定死，不需要 setter
    private final String email;
    String display() { return name + " <" + email + ">"; }
}
```

| 症状 | 说明 |
| --- | --- |
| 字段是 private，但 getter 是 public | 封装没有增加任何约束 |
| 只有 setter 没有 getter | 说明字段只是个缓冲区，应该被移除（`Remove Setting Method`） |
| 有人替这个类实现了它的行为 | 说明封装范围应该扩大（`Move Method`，见 `08-搬移特性.md`） |

## 版本演进

| 项 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 示例语言 | Java 1.x：靠 `private` + getter/setter 手写封装 | JavaScript：靠闭包、`#` 私有字段、模块作用域实现封装 |
| 新机制 | 只能手写访问器 | 各语言补齐了**属性（property）**、**不可变集合**、**值类型/record**、**私有字段**——封装成本大幅下降 |
| 封装讨论的重点 | 「要不要给字段加访问方法」 | 「**要不要暴露集合**、要不要做成不可变」——因为语言已经把最简单的那层解决了 |

**2020 年代的重构工具与 AI 辅助**：

- **语言与运行时吸收了封装**：Kotlin 的 `data class`、Java 的 `record`、C# 的 `record`/`init`、TypeScript 的 `readonly` 与 `private` 字段，让「封装一个字段」从十几行样板变成一行。这直接导致 **IDE 生成的 getter/setter 被普遍视为噪音**。
- **IntelliJ 的封装能力**：「Encapsulate Field」与「Replace Data Value with Object」这类手法已有重构动作，但**对集合的封装仍然只能手工做**（工具无法判断「暴露这个集合是否安全」）。
- **AI 辅助**：模型非常擅长生成 getter/setter——这恰恰是需要警惕的方向。正确用法是让 AI 帮你**识别未封装的约束点**（比如「这个字段在三个地方被检查了范围」），而不是替你铺开样板代码。
- **局限**：封装失败的真正原因往往不是「没写 private」，而是「**没人知道这条规则属于谁**」。工具与 AI 都无法替你回答归属问题。

## 近年研究与工业界开源实践（2015–2026）

**趋势**：封装在 2020 年代的主题是**「封装集合」与「不可变性」**——前者是工业界最常见的封装失败点，后者是并发正确性的前提。工具链的重点转向「在 CI 里发现封装泄漏」。

| 仓库 | star（`gh api` 实测，2026-09-25） | 说明 |
| --- | --- | --- |
| `JetBrains/intellij-community` | **20,588★** | Encapsulate Field / Introduce Getter-Setter 等动作的实现；对集合封装仍无自动方案 |
| `dotnet/roslyn` | **20,688★** | 记录类型与不可变集合的语言层支持，正在吸收本章的部分手法 |
| `llvm/llvm-project` | **40,650★** | clang-tidy 的检查项里含「返回内部容器」一类封装泄漏的提示 |
| `rust-lang/rust` | **119,150★** | 所有权与不可变引用机制，把「返回 &mut T 等于放弃封装」变成编译期错误 |
| `google/error-prone` | **7,238★** | 编译期拦截不安全的封装实践（如暴露可变状态） |
| `openrewrite/rewrite` | **3,750★** | 把「加 final / 改不可变集合」一类改动做成批量 recipe |
| `spring-projects/spring-framework` | **60,260★** | 企业侧最常见的封装反模式：贫血实体 + 一堆 setter + Service 里堆逻辑 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」**——封装是最便宜的重构，却最容易被「下次再说」跳过 | 没有预算窗口，改动要挤在功能提交里 | 把「加新功能时顺手封装」写成规范；一个 commit 只做一件事，评审者能分辨 |
| 2 | 🔧 **并发代码的重构风险被低估**——公开一个可变集合或可变引用，会让「封装」在多线程下彻底失效 | 单线程测试无法暴露别名修改带来的竞态 | 并发场景下优先选择**不可变 + 值语义**；暴露任何共享可变状态前先做同步审查（参考 `book/C++并发编程实战2/`） |
| 3 | 🔧 **不谈跨服务与数据迁移的重构**——把「裸字段」封装起来的代价常常是跨层/跨服务的一连串改动 | 封装一个字段可能牵动 DTO、ORM 映射、JSON 序列化契约 | 先在外层做适配层（DTO 转换），再逐步收拢内部；数据库 schema 的改动不在本书范围 |
| 4 | 🔧 **AI 生成代码带来的新债**——模型最爱生成「public 字段 + getter/setter 全套」，即「伪封装」，而且规模巨大 | AI 输出里样板代码比例远高于人类 | 用静态检查禁止「只有 getter/setter 的字段」这类模式；让 AI 输出**少样板**、多行为 |
| 5 | 🔧 本章默认「封装 = 加访问方法」在静态语言里成立；但在动态语言里，公开属性是**语言级默认**，封装要主动做 | JS/Python 没有 `private` 的语言强制力 | 用命名约定、`#`/`__` 约定、闭包或模块作用域补足；不要以为「没报错」就代表封装住了 |
| 6 | 🔧 过度封装：为了「将来可能的校验」给每个字段都加 setter，等于制造出「夸夸其谈通用性」 | 一堆无法解释用途的访问方法是噪音 | 只在**真的有约束**时才封装；没约束的字段直接做成只读或 final |
| 7 | 🔧 把 `Encapsulate Field` 直接等同于「生成 getter」是最常见的误读 | 团队把 IDE 生成 getter 当成完成了封装 | 封装的目标是**守住规则**；判定标准是「有没有人绕过它还能做错事」 |
| 8 | 🔧 第 7 章讨论的是**进程内**的封装；跨进程边界（API 响应里直接吐 domain 对象）在这里没有讨论 | 微服务架构下 domain 对象不应该直接序列化给外部 | 引入明确的边界模型（DTO / API 模型）；本书对此没有覆盖 |
