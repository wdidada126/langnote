# 第 6 章 第一组重构

> **一句话**：这一章只教十招——**在真正面对庞大名录之前，先把手上最常用的十个「动作」练成肌肉记忆**，它们的共同点是：改动小、见效快、几乎不会出错。

---

## 本章地图

| 手法（英文名 + 中译） | 解决什么问题 | 章内步骤要点 | 代价 |
| --- | --- | --- | --- |
| **Change Reference to Value** 将引用对象改为值对象 | 需要「可比较、可缓存、可自由复制」的语义（如 Money、日期区间） | 去掉 setter、实现相等性、确认不可变 | 每次「修改」都要造新对象；GC 压力 |
| **Change Value to Reference** 将值对象改为引用对象 | 需要「全局唯一、有生命周期、被多方共享」的语义 | 引入工厂/缓存、确定身份来源 | 共享带来别名与并发问题 |
| **Duplicate Observed Data** 复制被观察的数据 | 领域数据在一处、界面/日志里另存一份，两边不同步 | 提炼「去哪儿取」的单一入口 + 观察者/订阅 | 需要机制来同步，复杂度上升 |
| **Remove Double Negative** 移除非逻辑 | `if (!(a == b))` 让条件读起来要绕两圈 | 取反内层条件即可 | 注意严格相等与类型转换的边界 |
| **Remove Flag Argument** 移除标记参数 | `foo(true)` 这类布尔开关参数 | 拆成两个语义明确的函数，或传入策略 | 函数数量增加；调用点全改 |
| **Remove Setting Method** 移除设值函数 | 对外暴露的 setter 破坏了不变性与约束 | 改用构造函数/工厂方法 | 需要补一个初始化路径 |
| **Remove Redirect** 移除转发的重复代码 | `a.getB().getC().doWork()` 里的手工转发样板 | 直接调用，或保留转发表层用于兼容 | 直接暴露内部结构 |
| **Replace Boolean with Class** 以类取代布尔值 | `boolean isXxx` 上还要再挂属性/行为 | 建一个小类承载该标志及其行为 | 多一个类；字段名改了调用点全改 |
| **Replace Constructor with Factory Method** 以工厂方法取代构造函数 | 构造函数名字无法表达意图；要返回子类/缓存实例 | 用命名工厂方法替代 `new`，构造函数置私/protected | 工厂类成为新的耦合点；静态工厂难 mock |
| **Replace Error Notification with Exception** 以异常取代错误通知 | 用返回值/状态位报错，调用方常常忘了检查 | 定义异常类型、抛出来、在边界捕获 | 异常会跨越模块边界；滥用异常吞掉控制流 |

**关键结论**：
- 这十招的共同点是**「先改约定，再改行为」**——它们改的是**接口契约**，因此副作用最大、也最需要在有测试的地方做。
- 它们也是名录里「看起来简单、实际最容易翻车」的一组：简单不等于安全。
- 学完这一章，你就有能力处理 80% 的日常不顺手。

## 核心精讲

> 教学示意代码，不编译、不运行、不参与构建。

### 1. Change Value to Reference / Change Reference to Value（一对孪生手法）

```java
// 教学示意，不参与构建
// 值 ⟶ 引用：需要「同一份、共享、有身份」
class Money {                       // 现在是值对象
    Money(double amount, String currency) { … }
}
// 改成引用：管理员只有一份，所有人改的是同一条记录
class MoneyRef {
    private static Map<Key, MoneyRef> pool = new HashMap<>();  // 身份来自这里的 key
    static MoneyRef of(Key k) { … }
}

// 引用 ⟶ 值：需要「可比较、可缓存、安全分发」
// Money 作为值对象应删除所有 setter，并保证 equals/hashCode 由amount+currency决定
```

**判据**：

| 你想要的语义 | 选哪个 |
| --- | --- |
| `a.equals(b)`、能放进 `HashSet`、能安全传给任意线程 | **Value** |
| 需要「全局就一份」、要加锁保护、要监听它的变化 | **Reference** |

### 2. Duplicate Observed Data：同一份数据有两个真相

```js
// 教学示意，不参与构建
// ❌ 领域对象存一份，表单一处又缓存一份，改了一处另一处还是旧的
class Cart {
  constructor() { this.items = []; this.formCount = 0; }   // 第二个真相
  add(item) { this.items.push(item); this.formCount = this.items.length; }
  render()  { return `${this.formCount} 件商品`; }          // 渲染的是副本
}

// ✅ 单一入口：渲染时现算，或明确订阅变更事件
class Cart {
  constructor() { this.items = []; }
  add(item) { this.items = this.items.concat(item); notify(this); }  // 通知而非复制
  get count() { return this.items.length; }                          // 现算，永远一致
  render()  { return `${this.count} 件商品`; }
}
```

### 3. Replace Boolean with Class：布尔值上长出了行为

```js
// 教学示意，不参与构建
// ❌ 「是否VIP」上以后还要挂折扣、有效期、升级规则
order.isVip = true;

// ✅ 用一个有名字的类把「VIP 这套规则」收敛起来
class Vip {
  constructor(expiresOn) { this.expiresOn = expiresOn; }
  get active()  { return this.expiresOn > new Date(); }
  discountOf(amount) { return this.active ? amount * 0.2 : amount; }
}
order.customer.tier = new Vip("2027-01-01");
```

### 4. Remove Flag Argument：拆开关参数

```js
// 教学示意，不参与构建
// ❌ 标记参数：调用点看不出 true 是什么意思
findCustomer(true);      // 是否包含已注销的？

// ✅ 拆成两个语义清晰的入口
findActiveCustomer();
findCustomerIncludingClosed();
```

### 5. Replace Constructor with Factory Method：让创建意图可见

```java
// 教学示意，不参与构建
// ❌ 同一个构造函数无法确定拿到的是哪一族对象
new Animal("dog");
new Animal("cat");
// 于是年长的人写 switch，年轻人写一堆 if

// ✅ 命名工厂方法把「意图」写进名字
public static Animal dog() { return new Animal("dog", DogBehaviour.INSTANCE); }
public static Animal cat() { return new Animal("cat", CatBehaviour.INSTANCE); }
private Animal(String kind, Behaviour b) { … }   // 构造函数收成私有的，意图就锁住了
```

### 6. Replace Error Notification with Exception：别用返回值报错误

```js
// 教学示意，不参与构建
// ❌ 错误通知：调用方漏检查就静默通过
function charge(card, amount) {
  if (!card.isValid()) return { ok: false, code: 12 };
  ...
  return { ok: true };
}
const r = charge(card, 100);
if (r.ok) { /* 继续 */ }   // 忘了写 else，钱没扣却继续跑

// ✅ 以异常取代错误通知：不检查就不可能继续
function charge(card, amount) {
  if (!card.isValid()) throw new PaymentRejected("card invalid", 12);
  ...
}
```

> **边界提示**：反过来（`Replace Exception with Error Notification`）也常常是对的——**当异常被当成正常控制流**时（如「这个用户不存在，给用户展示注册页」），异常会让调用栈变得不可预测。手法是配套的，判断要看场景。

### 7. Remove Double Negative / Remove Redirect / Remove Setting Method（三个小动作）

```js
// 教学示意，不参与构建
// 移除非逻辑
if (!(a === b)) { … }        // ❌
if (a !== b)    { … }        // ✅

// 移除转发的重复代码
class Order { get customerName() { return this.customer.name(); } }   // ❌ 纯转发
// 直接让调用方读 order.customer.name()，或保留一层是为了兼容老接口

// 移除设值函数
class Money { void setAmount(double v) { this.amount = v; } }          // ❌ 破坏不变性
Money(double amount) { this.amount = amount; }                         // ✅ 构造时定死
```

## 版本演进

| 项 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 这十招的呈现 | 分散在各章，没有单独成章 | 第 6 章**专门列出「第一组重构」**，作为给新手的最短路径 |
| 示例语言 | Java | JavaScript，部分条目用函数/闭包表达（如提取工厂函数） |
| 新增条目 | 含 Duplicate Observed Data 等已存在 | 第 2 版把 **Replace Constructor with Factory Method**、**Replace Error Notification with Exception** 等提到第一组，**Reduce 掉一些第 1 版的手**（手法总数从 70+ 降到 60+） |

**2020 年代的重构工具与 AI 辅助**：

- **IDE 支持**：Rename、Extract、Change Signature、Introduce Factory 这些方法在 IntelliJ/Eclipse/VS 里都是现成动作；**Change Value to Reference 这类手法几乎没有任何工具支持**——它本质上是设计语义的变化，只能手工做。
- **AI 辅助**：这十招是**最适合交给模型执行**的一批（改动局部、意图清晰）。但正因如此，风险在于「一次全改」——第 6 章的纪律（一次一个动作）比任何工具都重要。
- **现代化的具体表现**：2015–2026 年间，`Replace Error Notification with Exception` 在 Java 世界里被 `Optional`、`Result` 类型、`Either` 一路补充；在 TypeScript 世界里被 `never`/判别联合进一步取代——这说明**手法会被语言能力吸收**，语言给了更好的机制，手法就该退到幕后。
- **OpenRewrite**：企业里最常见的「第一组重构」实践其实是**框架升级**（比如 `Replace Error Notification with Exception` 在批量迁移日志 API 时一次性生效）。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」**——第一组重构的十条都很「便宜」，但便宜不等于被安排进排期 | 团队里没人把「改个布尔标记」当成工作 | 把这十招写进 Code Review 的 checklist；看见就改，改完提交，不为单独的重构申请窗口 |
| 2 | 🔧 **并发代码的重构风险被低估**——`Change Value to Reference` 在多线程下会把「无锁安全」变成「需要同步」；`Remove Setting Method` 也可能改变可见性时序 | 测试绿 ≠ 无数据竞争 | 并发模块改语义前先做并发测试；改动后跑压力与 sanitizer |
| 3 | 🔧 **不谈跨服务与数据迁移的重构**——`Change Value to Reference` 这类语义变化一旦跨越服务或落库，就是一次数据迁移与兼容发布 | 服务边界会让「改个引用语义」变成项目级风险 | 先做双向兼容的读旧/读新，再切流量；本书完全没有覆盖这一层 |
| 4 | 🔧 **AI 生成代码带来的新债**——这十招正是 AI 最常一次性执行掉的动作，容易出现「十招一起改、diff 不可审」 | 模型倾向于给出「完整的漂亮改动」 | 强制一个动作一次提交；用工具（如 `git bisect`）定位哪一步引入了回归 |
| 5 | 🔧 `Replace Error Notification with Exception` 被很多团队**当成绝对升级**，但异常驱动的分支在**跨模块/跨语言边界**（插件、脚本引擎、RPC）上代价很高 | 异常会穿透模块边界，栈追踪也可能泄漏内部信息 | 按边界定策略：内部用异常；插件宿主与跨语言边界用显式错误对象 |
| 6 | 🔧 第 1 版的「Avoided 字段/布尔」等手法在第 2 版被精简，中英文对照时容易找不到对应条目 | 名录经过合并与改名 | 用本目录总表（`00-总览与阅读地图.md` 第 3 节）与 refactoring.com 的在线名录对照 |
| 7 | 🔧 「第一组重构」默认读者**有完整的单元测试**；实际场景中 Remove Setting Method 会因为缺少构造函数路径而直接编译失败，进而被放弃 | 老系统往往构造路径复杂 | 先用工厂方法把构造意图显式化，再移除 setter；构造函数 overload 太多时改为参数对象 |
| 8 | 🔧 本章没有讨论**测试替身与这十招的相互作用**：引入工厂方法后，静态工厂会显著抬高 mock 成本 | 静态工厂 + 静态工具类是测试隔离的最大敌人 | 工厂方法要可注入（实例方法而非静态方法）；这需要与该手法配套使用 |
