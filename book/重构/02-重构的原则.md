# 第 2 章 重构的原则

> **一句话**：重构不是一个「技术偏好」，而是**用动词形式出现的软件设计**——它要求你在同一段时间里**只戴一顶帽子**（要么只改结构，要么只加功能），这是全书唯一一条不可协商的纪律。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 2.1 何谓重构（定义） | **名词**：对内部结构的调整，不改变可观察行为，旨在提高可理解性、降低修改成本；**动词**：应用一系列手法完成上述调整 | 定义里的「可观察行为不变」是硬约束，也是测试的立项理由 |
| 2.2 两顶帽子 | 同一时刻**要么重构（改结构，不加功能），要么开发（加功能，不改结构）** | 混着做，diff 就没人能审；这是本书最有名的一条纪律 |
| 2.3 为何重构 | 重构让**设计变得廉价**——支撑更快的开发；让代码更易读（「三周后我自己也读不懂」）；help 找到 bug；提升编程享受 | 重构的收益不是「代码好看」，而是**下一次改动更便宜** |
| 2.4 何时重构 | 三次法则（Three Strikes）：犯了三次错就该写抽象；**重构应该在加功能之前做**（让新功能好加），而不是之后补 | 「预备重构」「重构以便复用」都是正当时机 |
| 2.5 重构的挑战 | ① 没人有时间；② 缺乏测试；③ 代码所有权/共享；④ 与重写/优化的边界模糊 | 承认困难，然后给出可操作的解法（先补测试、先约定提交粒度） |
| 2.6 重构、架构和 YAGNI | 重构让**架构决策可逆**；YAGNI 说的「不做」应该在重构出现后重新评估 | 重构与 YAGNI 不冲突：不是不做，是「等证据来了再把它做对」 |
| 2.7 重构与软件开发过程 | 重构在 TDD 的「绿」之后、下一个测试之前；XP 的日常实践里它是默认动作 | 重构不是项目里的一段时间，而是**每一次提交里的一个环节** |
| 2.8 重构与性能 | 「重构在前，调优在后」；性能调优是「不改可观察行为也行」的相邻活动 | 过早优化与重构的差别在于：优化改变的是**资源消耗**，重构改变的是**结构** |
| 2.9 重构起源何处 | 概念源自 Smalltalk 社区（Opdyke/Johnson），Fowler 把它系统化并推广到普通开发者 | 「重构」不是 Fowler 发明的，是他的**命名与 catalog 化** |
| 2.10 自动化重构 | IDE 的重构支持（重构的「卢比孔河」时刻）；自动化能覆盖哪些、不能覆盖哪些 | 自动化执行步骤，不替你做判断；**有测试才能相信自动化** |
| 2.11 延展阅读 | 指向 refactoring.com 与后续文献（TDD、XUnit Test Patterns 等） | 延伸阅读是本书给出的下一步路径 |

**关键结论**：
- 定义的重点在「**可观察行为不变**」——这句话决定了你做重构时**要先建立什么**。
- 「两顶帽子」不是洁癖，是**让 code review 有意义**的前提：一个 commit 里既有 `if` 改写又有新功能，评审者无法判断有没有引入 bug。
- 重构的收益必须折算成「**下次改动省多少时间**」才能说服管理者。

## 核心精讲

> 教学示意代码，不编译、不运行、不参与构建。

### 1. 为什么「两顶帽子」是对的（用 diff 说话）

```js
// 教学示意，不参与构建
// ❌ 混戴帽子：这一次提交同时改了结构和加了功能，评审者无法判断
function rent(customer, movie, days) {
  if (movie.isNewRelease()) {
    return { price: days * 3, points: days > 1 ? 2 : 1, tag: "NEW" };
  }
  // ……同时又插入了会员等级逻辑，谁敢保证没有回归？
}
```

```js
// 教学示意，不参与构建
// ✅ 只戴「重构」帽子：结构变了，外部可见行为完全不变
function rent(customer, movie, days) {
  const calculator = movie.priceCalculator();   // 结构：把算价挪进对象
  return {
    price: calculator.amount(days),
    points: calculator.points(days),
    tag: calculator.tag(),
  };
}
```

评审者只需回答一个问题：「这次改动是行为等价的吗？」——**这就是两顶帽子的全部价值**。

### 2. 性能与重构的分界（一个可执行的判据）

| 活动 | 改变什么 | 允许多少「不可观察行为」变化 | 验证手段 |
| --- | --- | --- | --- |
| 重构 | 结构 | **零**（可观察行为必须一致） | 已有测试全绿 + 新写的特征测试 |
| 性能调优 | 资源消耗/时间 | 允许（只要输出一致） | 基准测试 + 已有测试 |
| 重写 | 一切 | 无所谓 | 新系统的验收测试 |
| 优化（改缓存布局、内联热函数） | 结构 + 资源 | 通常零 | A/B、profiler |

```java
// 教学示意，不参与构建
// 性能调优的例子：行为不变，但资源消耗变化 —— 属于「优化」帽子，不是重构
// 重构阶段：只把「计算」和「输出」分开，保证行为完全一致
// 优化阶段：再做缓存/去重，用基准测试证明收益
```

### 3. 三次法则（Three Strikes）与「预备重构」

```js
// 教学示意，不参与构建
// 第一次：直接写死，能跑就行
if (user.kind === "vip") return discount(0.2);

// 第二次：另一个地方又写了一遍同样的规则
if (user.kind === "vip") return discount(0.2);

// 第三次：这里开始出现「霰弹式修改」——再不改，下一次需求会同时动三个文件
if (user.kind === "vip") return discount(0.2);
```

作者的态度很清楚：**抽象不是一次做对，而是第三次才做**。“Three strikes and you refactor” 意味着容忍两次重复，避免过早抽象（对应坏味道「夸夸其谈通用性」）。

### 4. YAGNI 与重构并不矛盾

```js
// 教学示意，不参与构建
// YAGNI 说：不要为「可能有」的需求留扩展点
class Order {
  // ❌ 为未来可能有的三种支付方式预先写好接口和空实现
  payByCard() {}
  payByAlipay() {}
  payByWechat() {}
}

// 正确顺序：YAGNI 先拒绝 → 真出现需求 → 用重构把它做对
// 1) 先只有一个 pay(amount)，直接实现
// 2) 第二次要支付宝 → Extract Interface / Move Method
// 3) 第三次要微信 → 层次自然浮现
```

**重构 × YAGNI 的合理解读**：YAGNI 管的是「现在不要做」，重构管的是「将来做的时候能低成本做」。两者共同指向——**先写最简单的，让结构在证据出现时自然浮现**。

### 5. 重构的「挑战」在真实团队里的模样

| 挑战 | 书里的回应 | 2026 年的现实补充 |
| --- | --- | --- |
| 没人有时间 | 把重构排进迭代（20% 时间一类做法） | 在 AI 辅助下「小重构」的成本大幅下降，但**大面积重构**仍需专门窗口 |
| 缺乏测试 | 先补测试再动手（见 `04-` 章） | 覆盖率数字不等于安全网；真正有用的是**能捕获本次改动**的测试 |
| 代码所有权 / 共享库 | 用「小步 + 频繁提交」降低冲突 | 单体仓库（monorepo）让冲突更容易，也让批量工具（OpenRewrite 一类）更有价值 |
| 与重写的边界 | 架构崩了才重写 | 微服务拆分、数据迁移这些**不在本书范围**内 |

## 版本演进

| 项 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 2.10「自动化重构」一节 | 刚跨过「卢比孔河」，主要讲 Java IDE 的 Extract Method/Rename 是否已够用 | 承认自动化已是常态，重点改为**自动化的边界与信任问题**（有测试才敢用） |
| 全局示例语言 | Java | JavaScript，并新增「无类环境如何重构」的表述 |
| 新增语境 | 面向对象重构 | **函数式重构**：把「没有类也能重构」写进正文，影响 2.1、2.3 的措辞 |
| 时间压力的表述 | 主要是「迭代里的重构」 | 与敏捷、CI/CD、持续交付的衔接被说得更明确（2.7 节） |

**2020 年代的重构工具与 AI 辅助**：

- **IntelliJ 的重构自动化与它的局限**：IntelliJ 提供 Change Signature、Introduce Parameter Object、Move 等上百个重构动作，且大量带「预览 + 冲突检测」；但它的局限同样明显——
  1. 只覆盖「小规模、局部」的手法；`Replace Conditional with Polymorphism`、`Extract Class` 这类跨模块的 Still 需要人工；
  2. 只做**语法与作用域**层面的等价，不做语义等价证明（重命名一个恰好被反射调用的方法会漏改）；
  3. 对**动态类型**语言（JS/Python）的重构保守，因为「找不到所有调用点」。
- **Roslyn / Clang / rustfix**：把「等价性」交给类型系统与编译器。Roslyn 的语义模型让 C# 的重构最可靠；`rustfix` 则在所有权系统的保证下做最小改动的自动修复。
- **OpenRewrite**：面向「跨仓库、跨版本」的批量重构（如 Java EE → Spring Boot、日志 API 迁移），用 `RewriteTest` 保证每条 recipe 的行为等价——它是 2.10 节「自动化重构」在 2020 年代最实在的形态。
- **AI 辅助重构**：模型可以一次性给出较大的结构改动，但它**不保证行为等价**，也常常不理解你的测试覆盖情况。2020 年代工业界的通行做法是：AI 出方案 → 人拆小步 → 测试兜底 → 小步提交。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」**——2.5 节把它列为「挑战」，但书里没有给出组织级解法 | 需求密度高的团队里，重构永远排在最后；管理者要的是「下次改动快」，不是「代码美」 | 用**度量**换时间：记录「实现同一需求改动的文件数」在重构前后的变化；一次只对一个模块做，做完立刻展示收益 |
| 2 | 🔧 2.2「两顶帽子」在**增量式交付**中难以严格做到：一个真实需求常常既要改接口又要改实现 | 瀑布式分工（先设计后实现）已经死去，混戴帽子是常态 | 用**提交粒度**实现两顶帽子：同一个需求拆成「行为不变的重构提交」+「功能提交」两段；评审按提交分类 |
| 3 | 🔧 2.3 说重构能「帮助找到 bug」，但**没有测试的重构会主动制造 bug** | 很多团队把重构当作「清理」的代名词，在没测试的地方动刀 | 把「没有测试就不重构」写进团队规范；2.3 的收益论述只在有安全网时成立 |
| 4 | 🔧 2.8「重构在前、调优在后」对**性能敏感路径**（热循环、GC 敏感的大对象复用）并不总是成立 | 某些场景必须一开始就考虑内存分配与缓存局部性，重构之后反而更难调优 | 对性能关键路径，先做 profiling 记录基线，再重构，重构后再对比；重构**不能**作为性能回归的挡箭牌 |
| 5 | 🔧 2.6 把 YAGNI 与重构对立起来说明，容易让读者以为「不用重构」是 YAGNI 的含义 | YAGNI 常被误读成「不要抽象」，从而导致复制粘贴泛滥 | 正确的合并读法是：**YAGNI 拒绝的是今天的过度设计；重构负责把明天的过度改造造成低成本** |
| 6 | 🔧 **并发代码的重构风险被低估**——2.1「可观察行为不变」在多线程下不是免费的 | 提取函数、搬移字段可能改变锁的持有范围、内存可见性与执行顺序；测试绿 ≠ 无数据竞争 | 并发模块重构前先加并发测试（TSan/ASan 一类）；重构后再跑压力测试；参考 `book/C++并发编程实战2/` |
| 7 | 🔧 **AI 生成代码带来的新债**——重构对象从「写得烂」变成「AI 写的冗余」 | 模型输出通常结构规整但语义冗余（重复分支、重复校验、无用的中间层） | 把「坏味道扫描」放进 CI；对 AI 产出的代码同样要求「一次一个意图」的提交粒度 |
| 8 | 🔧 2.5「代码所有权/共享」在**单体仓库 + 共享库**场景下被低估 | 一个公共方法的签名改动会让几百个调用点同时红灯，冻结窗口极长 | 先做兼容层（Deprecated 标记），再分批迁移；用批量重构工具（OpenRewrite）替代人工逐处改 |
