# 第 1 章 重构，第一个示例

> **一句话**：整个第 1 章只干一件事——把同一个「影片出租」小程序**从头到尾改一遍**，让读者亲眼看到「一点点改结构，行为却一尘不变」是什么手感，从而消除对重构的恐惧。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 1.1 起点 | 一个 `statement()` 函数，`switch` 按影片类型算租金，拼出一行行的明细字符串 | 起点不脏，只是**没有结构** |
| 1.2 对此起始程序的评价 | 过长的函数、`switch` 承担了不该承担的职责、字段语义散落 | 「没有坏味道」不等于「不需要重构」，但**没有测试就不许动** |
| 1.3 重构的第一步 | 先**跑起来**（测试）再动手，哪怕测试很粗糙 | 纪律：先有安全网，再动结构 |
| 1.4 分解 `statement` 函数 | 用 **Extract Method** 拆成 `amountFor`、`feeFor`、`totalAmount`、`totalFrequentRenterPoints` | 「做什么」和「怎么做」分离 |
| 1.5 进展：大量嵌套函数 | 拆得太碎，命名不当，反而更难读 | 拆分要有度，名字要能「回答问题」 |
| 1.6 拆分计算阶段与格式化阶段 | 把「算钱」和「拼字符串」分成两件事 | 阶段分离是**降低霰弹式修改**的关键 |
| 1.7 分离到两个文件（和两个阶段） | 用类/模块承载两个阶段 | 结构跟着职责走，而不是跟着源文件走 |
| 1.8 按类型重组计算过程 | 把 `switch` 的分支各自搬进影片类型对象 | 用**多态**替代条件分支 |
| 1.9 使用多态计算器 | 引入 `MovieRental`/`Movie`/`PriceCode` 的分派结构 | 加一种新影片类型时不再改 `statement()` |
| 1.10 结语 | 改动总量、每一步的小规模 | 重构不是一次大手术，而是几十次小步 |

**关键结论**：
- 起点代码「能跑、有测试」，重构从**可以安全动手**开始，而不是从「代码很烂」开始。
- 每一步都只有一个意图：**换个名字、挪块代码、删掉一个分支**。
- 最终形态（多态）并不是为了「用设计模式」，而是**下一次加功能时改动最少**。

## 核心精讲

> 以下均为**教学示意代码，不编译、不运行、不参与构建**。第 2 版正文示例用 JavaScript，这里按章节主题给出对应的 JS 与 Java 对照形态。

### 1. 起点（JavaScript，对应书中第 1 版 Java 版的 `statement()`）

```js
// 教学示意，不参与构建
function statement(customer, movies) {
  let totalAmount = 0;
  let frequentRenterPoints = 0;
  let result = ` Rental Record for ${customer.name}\n`;

  for (const r of customer.rentals) {
    let amount = 0;
    switch (r.movie.priceCode) {
      case PriceCode.CHILDREN:
        amount += 1.5 + Math.max(0, r.days - 3) * 0.5;
        break;
      case PriceCode.NEW_RELEASE:
        amount += r.days * 3;
        break;
      case PriceCode.REGULAR:
        amount += 2 + Math.max(0, r.days - 2) * 1.5;
        break;
    }
    frequentRenterPoints++;
    if (r.movie.priceCode === PriceCode.NEW_RELEASE && r.days > 1) {
      frequentRenterPoints++;
    }
    result += `  ${r.movie.title}\t${amount.toFixed(1)}\n`;
    totalAmount += amount;
  }
  result += `Total ${totalAmount.toFixed(1)}\n`;
  result += `Earned ${frequentRenterPoints} frequent renter points`;
  return result;
}
```

这段代码的「病」不是重复，而是**三件事挤在一个函数里**：算每种租金、积分、拼输出文本。想加一种新片型，就得回来改这个巨型 `switch`——这是典型的**霰弹式修改**前夜。

### 2. 第一步：Extract Method（把一段「做一件事」的代码命名）

```js
// 教学示意，不参与构建
function eachRental(customer, fn) {
  for (const r of customer.rentals) fn(r);
}

function amountFor(r) {
  switch (r.movie.priceCode) {
    case PriceCode.CHILDREN:
      return 1.5 + Math.max(0, r.days - 3) * 0.5;
    case PriceCode.NEW_RELEASE:
      return r.days * 3;
    case PriceCode.REGULAR:
      return 2 + Math.max(0, r.days - 2) * 1.5;
    default:
      throw new Error("unknown price code");
  }
}
```

要点：
- **函数的名字回答「是什么」，函数体回答「怎么做」**。
- 提炼之后，调用方读起来像业务语言；`switch` 仍留在原地——因为「怎么算」还没到该搬家的时候。
- 提炼失败时（临时变量太多）要用 **Replace Method with Method Object**，把临时变量变成对象的字段。

### 3. 转折点：把计算阶段与格式化阶段分开

```js
// 教学示意，不参与构建
function createStatementData(customer) {
  const data = {
    customer: customer.name,
    rentals: customer.rentals.map((r) => ({
      movieTitle: r.movie.title,
      days: r.days,
      price: amountFor(r),
    })),
  };
  data.totalAmount = sum(data.rentals.map((r) => r.price));
  data.points = pointsFor(data.rentals);
  return data;
}

function renderText(data) {
  let result = `Rental Record for ${data.customer}\n`;
  for (const r of data.rentals) result += `  ${r.movieTitle}\t${r.price.toFixed(1)}\n`;
  result += `Total ${data.totalAmount.toFixed(1)}\n`;
  result += `Earned ${data.points} frequent renter points\n`;
  return result;
}
```

这一步是**全章的分水岭**：`createStatementData` 是「纯数据」，`renderText` 是「纯展示」。好处是——
- 换一种输出（HTML、邮件、对账文件）只改 `renderText`；
- 换一种计价规则只改 `createStatementData`；
- 前者可以做成**纯函数**，单元测试极便宜。

### 4. 终局：用多态取代 `switch`（Replace Conditional with Polymorphism 的雏形）

```java
// 教学示意，不参与构建
// 把「按类型算钱」变成「对象自己会算钱」
interface Price {
    int priceCode();
    double amount(int daysRented);          // 每种片型只关心这一件事
    int frequentRenterPoints(int daysRented);
}

class ChildrenPrice implements Price {
    public int priceCode() { return PriceCode.CHILDREN; }
    public double amount(int d) { return 1.5 + Math.max(0, d - 3) * 0.5; }
    public int frequentRenterPoints(int d) { return 1; }
}

class NewReleasePrice implements Price {
    public int priceCode() { return PriceCode.NEW_RELEASE; }
    public double amount(int d) { return d * 3.0; }
    public int frequentRenterPoints(int d) { return (d > 1) ? 2 : 1; }
}
```

于是主流程里再也不出现 `switch`：

```java
// 教学示意，不参与构建
double total = 0;
int points = 0;
for (Rental r : customer.rentals()) {
    total  += r.price().amount(r.days());      // 每种片型自己负责
    points += r.price().frequentRenterPoints(r.days());
}
```

**代价要说清楚**：这引入了一组接口与实现类（类数量上升）。如果这辈子只演一种片型，这就是**夸夸其谈通用性**。多态的价值不来自优雅，而来自「**下一次改动的范围最小**」——这正是重构的判断标准。

### 5. 每一步的「小」体现在哪里

| 序号 | 做了什么 | 手法 |
| --- | --- | --- |
| 1 | 补上一个能跑的测试 | （先做，不是手法） |
| 2 | 把 `amountFor` 择出来 | Extract Method |
| 3 | 把积分择出来 | Extract Method |
| 4 | 把「拼字符串」择出去 | Extract Method |
| 5 | 计算与格式化分家 | Extract / Move |
| 6 | `switch` 走进各自的片型对象 | Replace Conditional with Polymorphism |

全章 10 节只完成了这件事：**让「加一种新片型」从「改 3 处代码」变成「加 1 个类」。**

## 版本演进

| 维度和事实 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 示例语言 | 主示例用 **Java**（第 1 版的 rental 示例也是 Java） | 主示例改为 **JavaScript**，`statement` 用函数与数组直接写 |
| 封装形态 | 强调「用类承载行为」，`Movie` / `Rental` / `Customer` 三件套 | 强调**无类也能重构**：用 `map`、闭包、`factory` 表达同样的结构 |
| 多态演示 | 典型 OO：接口 + 实现类 | 同一手法演示为「策略函数表」或「带方法的对象」 |
| 作者的态度 | 重构 ≈ OO 的重构 | 作者明确表示希望说明**重构不必与 OO 紧耦合**，任何语言都能做 |

**2020 年代的重构工具与 AI 辅助**：

- **自动化重构**：IntelliJ / Eclipse / Visual Studio 的 Extract Method、Rename、Introduce Variable 已经把第 1 章第 2–4 步做成「点一下」。所以今天读第 1 章的重点不再是「怎么提炼」，而是「**为什么要提炼、提炼到什么程度停下来**」——工具替你执行步骤，不替你做判断。
- **OpenRewrite**：把第 1 章这类「结构变换」推广到**跨仓库批量执行**（框架升级、API 迁移），一次跑几万处调用点，并用 `RewriteTest` 保证行为等价。
- **AI 辅助**：Copilot/Claude 一类工具现在能直接「帮我把这段提成函数」。风险在于它会一次做五步，diff 变成「什么都看不出来」；而第 1 章的全部价值恰恰是**小步 + 可回退**。因此 2020 年代的正确用法是：让 AI 提建议，你**拆成 1 步一次提交**。
- **局限**：AI 特别不擅长 `Replace Conditional with Polymorphism` 这类「需要重构被调方整体结构」的手法——它往往改完调用点，留下没人调用的旧分支。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」** | 第 1 章默认你有一个「可以停下来重构」的迭代；但是在需求排到季度末的团队里，`statement()` 这种巨型函数是**排期表上的第一个牺牲品** | 把重构换算成「下次改动要省几小时」来提；先在有测试的模块上做，用结果说话 |
| 2 | 🔧 第 1 章**假设代码已经可运行**（有控制台输出、有测试），但真实的老系统往往是「能编译、不敢跑」 | 你连当前行为都没观测到，就无法谈「行为不变」 | 先用特征测试（characterization test）**把当前行为钉住**，哪怕它错；见 `04-构筑测试体系.md` |
| 3 | 🔧 「第 1 步是 `switch` 该被多态取代」，但**只有一种片型时不应立即多态化** | 书里的例子天然有多个类型，容易让读者误以为「见到 switch 就该上多态」 | 判断标准只有一个：**下一次改动的范围是否最小**。见 `03-代码的坏味道.md` 的「重复的 switch」 |
| 4 | 🔧 第 1 章用 JS 重写后，**静态类型兜底消失了**，例子的安全性其实更低了 | 第 1 版 Java 的 `switch` 分支漏掉时会走 `default`；JS 里拼错常量名可能静默变成新分支 | 在动态类型语言里，第 4 步之后必须补**静态结构**（schema/类型定义）或更强测试 |
| 5 | 🔧 **AI 生成代码让「起点」变了**：今天的烂代码有大量是模型一次性生成的「看起来整洁、实则冗余」的代码 | AI 的输出往往结构规整但**语义重复**，和 1999 年的脏代码形态完全不同 | 对 AI 产出同样做坏味道扫描；把「重构」变成每次提交前的固定动作，而不是救火 |
| 6 | 🔧 第 1 章**完全没有涉及并发代码**（`switch` 分支里如果有共享状态，Extract 会引入别名） | 多线程下 Extract Method 可能把可变状态搬到新的共享范围 | 并发代码先保证同步正确再谈结构；参考 `book/C++并发编程实战2/` 的相关部分 |
| 7 | 🔧 「拆成两个文件（和两个阶段）」在无模块系统支持的语言里会变成路径灾难 | 真实项目里文件位置本身就是耦合信号 | 用你语言实际的模块/包机制落地阶段分离，而不是靠目录约定 |
