# 第 4 章 构筑测试体系

> **一句话**：**没有测试的重构不叫重构，叫碰运气**——本章是全书的执行前提：先建立「能立刻告诉你有没有弄坏东西」的自测试代码，之后所有手法才有施行的资格。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 4.1 自测试代码的价值 | 重构的安全性来自「快速反馈」；让测试替你承担记忆负担 | 测试不是给 QA 用的，是给你**敢改代码**用的 |
| 4.2 待测试的示例代码 | 用第 1 章的 rental 程序演示一个**最小的 JUnit 测试**：把「当前行为」钉住 | 第一个测试只需要证明「老样子还在」 |
| 4.3 测试的策略与边界 | 测什么、不测什么；测试的双保险（单元测试 + 特征测试）；覆盖率的正确用法 | 覆盖率是**相关性**指标，不是**充分性**指标 |
| 4.4 让测试成为重构的安全网 | 写测试的顺序：先证明老行为 → 再改结构 → 再跑测试 | 「绿灯 ⟶ 重构 ⟶ 绿灯」是唯一的循环 |

**关键结论**：
- 本章没有提出任何新手法，却是**全书 60 多个手法的许可证**。
- 第 1 章从「重构的第一步」开始，但那一步的前提就在这里——**先让代码可以被安全地观测**。
- 一个重要的实现态度：**先写「会失败但能说明当前行为」的测试**（characterization test），再动结构；等结构稳定后，把它改写成真正表达意图的测试。

## 核心精讲

> 教学示意代码，不编译、不运行、不参与构建。

### 1. 三个「为什么测试」的层次

| 层次 | 目的 | 谁受益 |
| --- | --- | --- |
| 证明「老样子还在」 | 捕捉重构引入的回归 | 重构者本人 |
| 表达「应该是什么」 | 把业务规则显式化，成为设计工具 | 整个团队的沟通语言 |
| 作为设计约束 | 一个难测的设计，往往是个坏设计 | 长期维护者 |

```java
// 教学示意，不参与构建
// 4.2 的起点：为 rental 程序写下第一个「特征测试」
// 它描述的是「当前行为」，哪怕那段行为本身并不合理
import static org.junit.Assert.assertEquals;
import org.junit.Test;

public class RentalTest {
    @Test public void statementOfCustomerWithOneNewReleaseTwoDays() {
        Customer customer = new Customer("Chen");
        customer.addRental(new Rental(new Movie("Star Wars", Movie.NEW_RELEASE), 2));
        String expected =
            "Rental Record for Chen\n" +
            "\tStar Wars\t6.0\n" +
            "Total 6.0\n" +
            "Earned 2 frequent renter points\n";
        assertEquals(expected, customer.statement());
    }
}
```

这个测试的价值不在「对」，而在**精确**——它把那个巨大的字符串输出变成了不可动弹的契约。接下来第 1 章的所有结构改动，只要这个测试还是绿的，就是安全的。

### 2. 拆分断言：让失败的测试「说人话」

```java
// 教学示意，不参与构建
// ❌ 只有一个巨型断言：测试一挂，你不知道是算错了钱还是积分错了
assertEquals("Rental Record for Chen\n\tStar Wars\t6.0\nTotal 6.0\n", customer.statement());

// ✅ 把「输出」拆成可独立断言的数据（这一步本身也是重构：拆分计算与格式化）
@Test public void countsTotalAmountAndPointsSeparately() {
    Customer c = new Customer("Chen");
    c.addRental(new Rental(new Movie("Star Wars", Movie.NEW_RELEASE), 2));

    StatementData data = createStatementData(c);          // 只算不算输出

    assertEquals(6.0, data.totalAmount(), 0.001);
    assertEquals(2,   data.frequentRenterPoints());
}
```

**为什么这算重构**：`assertEquals` 只是一个断言；把它变成「调用 `createStatementData` + 两个数值断言」之后，测试本身就承担了**把计算与输出分开**的设计提倡。

### 3. 测试里的坏味道与「双保险」

```js
// 教学示意，不参与构建
// ❌ 测试里长满了逻辑：for / if / 三元 —— 断言一旦失败，你先怀疑测试自己
test("loyalty points", () => {
  let pts = 0;
  for (const r of customer.rentals) {
    if (r.movie.priceCode === "NEW_RELEASE" && r.days > 1) pts += 2;
    else if (r.movie.priceCode === "NEW_RELEASE") pts += 1;
    else if (r.days > 1) pts += 2;
    else pts += 1;
  }
  expect(pts).toBe(3);
});
```

```js
// 教学示意，不参与构建
// ✅ 用「表驱动 + 已知值」表达规则，逻辑留在被测代码里
const pointsTable = [
  { code: "NEW_RELEASE", days: 2, points: 2 },
  { code: "REGULAR",     days: 2, points: 1 },
];
for (const t of pointsTable) {
  it(`gives ${t.points} points for ${t.code} ${t.days}d`, () => {
    const c = makeCustomer(makeRental(t.code, t.days));
    expect(createStatementData(c).points).toBe(t.points);
  });
}
```

| 测试类型 | 回答什么问题 | 典型代价 |
| --- | --- | --- |
| **单元测试** | 这个改动有没有弄坏这一个行为？ | 需要测试替身；对跨模块改动覆盖不足 |
| **特征测试**（characterization） | 「以前是什么样，现在还是不是那样」 | 会把错误行为也钉住；需要人工判断哪些是 bug |
| **冒烟/集成测试** | 端到端路径还通不通？ | 慢、脆、难定位 |
| **契约测试** | 服务之间的约定没变？ | 需要额外的测试基础设施 |

### 4. 覆盖率的正确用法

| 用法 | 说明 |
| --- | --- |
| 覆盖率**高**但不测「边界」 | 最容易自欺：跑到了不等于断言对了 |
| 覆盖率**低**但每次失败都精确定位 | 对重构而言更实用 |
| 把覆盖率当作** discovers 未测路径**的工具 | 覆盖率数字的作用是告诉你「这里没有测试」，而不是「这里没问题」 |

> 一句话：**重构时你需要的不是高覆盖率，而是「与本次改动直接相关的那几条路径上有精确断言」**。

### 5. 写测试的时机（与两顶帽子的衔接）

```
1. 观察现有行为 → 写下特征测试（先让它失败/或至少证明它现在是对的）
2. 跑绿
3. ──── 现在才戴上「重构」帽子 ────
4. 应用 1 个手法（Extract Method / Move Method / …）
5. 跑测试 → 必须绿
6. 重复 4–5，直到结构达成意图
7. ──── 摘下重构帽子，戴上「功能」帽子 ────
```

## 版本演进

| 项 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 测试框架语境 | JUnit 3（继承 `TestCase`、`testXxx` 命名约定） | JUnit 4/5（`@Test` 注解、`assertThat`、参数化测试更成熟） |
| 示例语言 | Java | 主示例仍是 **Java**（第 4 章的 JUnit 示例在第 2 版保持 Java），而正文手法示例变成 JavaScript |
| 测试范围 | 以**单元测试**为主 | 更明确地区分单元测试与集成测试，并强调**测试的程序化生成与自动生成**（第 2 版更关注「老系统怎么开始测」） |

**2020 年代的重构工具与 AI 辅助**：

- **生成测试**：AI 能从一段老代码直接生成特征测试草案，大幅降低「先补测试」的门槛；但要注意它**会把错误的行为也当成正确行为写进断言**——生成后必须由人逐条确认。
- ** mutation testing（变异测试）**：`pitest`、`surefire` 生态里的变异测试工具开始普及，用来回答「这些测试真正在拦住 bug 吗」，正好补上覆盖率指标的漏洞。
- **AI 辅助重构**：模型可以「一边改结构一边补测试」，但它不知道你的测试是否**相关**。2020 年代工业界共识：**AI 提方案、人定范围、测试兜底、小步提交**。
- **OpenRewrite 的 `RewriteTest`**：把「行为等价」变成对测试的规定——任何批量 recipe 必须自带可执行的验证用例。
- **IntelliJ 的局限**：IDE 能帮你生成测试骨架与 Mock，但对「这个测试与这次改动是否相关」完全无判断；它还**不能帮你决定先测哪一段代码**。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」**——第 4 章默认你有「先停下来写测试」的窗口；但面对一个零测试的老系统，写测试本身就是一个大工程 | 补测试的成本经常高于重构本身，导致重构永远排不进去 | 用**滚动策略**：只为你即将触碰的那段代码补测试；先用大颗粒度的冒烟测试兜住主干，再逐块加密 |
| 2 | 🔧 **特征测试会把 bug 也钉死**，第 4 章只说「先把当前行为测住」，没提醒「测住之后要主动确认哪些是错的」 | 团队把特征测试当圣经，长期把已知缺陷写进断言 | 建立「先记录、再决定、后修正」的三步流程；把被钉住的 bug 记成技术债条目，别悄悄修（会让 diff 混进功能改动） |
| 3 | 🔧 **并发代码的重构风险被严重低估**——本章所有测试都假设顺序执行；重构后测试全绿也不代表没有数据竞争 | 提取/搬移改变锁范围与可见性；测试绿 ≠ 无竞争 | 并发模块：加并发测试（TSan/ASan 类工具）、提高并发量级、跑多轮；参考 `book/C++并发编程实战2/` |
| 4 | 🔧 **不谈跨服务与数据迁移的重构**——本节说的「测试」全是进程内测试；跨服务改动需要契约测试与双向兼容发布 | 微服务环境下，「行为不变」的定义从一次进程扩展成一次端到端发布 | 引入契约测试（Pact 一类）与影子流量；这在本书里零覆盖 |
| 5 | 🔧 **AI 生成代码带来的新债**——测试对象从「写得烂的代码」变成「AI 写的冗余代码」，而 AI 生成的测试常常**与被测代码同构**（一起错） | 模型和测试出自同一次生成，回归检测能力被削弱 | 对 AI 产出的代码额外加**变异测试**与人工抽样评审；不要让「有测试」成为放松审查的理由 |
| 6 | 🔧 「写测试」的示例基于 JUnit，对非 JVM 团队参考价值有限 | 各语言测试框架差异大 | 原则（自测试、特征测试、小步）跨语言通用；框架细节按你所在语言的生态替换 |
| 7 | 🔧 第 4 章没有讨论**测试的速度**：一个跑 40 分钟的测试集会让人彻底放弃重构纪律 | 慢测试导致「攒一批再跑」，diff 失去语义 | 把测试分三层（秒级单测 / 分钟级集成 / 小时级 E2E），重构循环只用第一层 |
| 8 | 🔧 「覆盖率足够就可以重构」是最常见的误读，本章并未给出任何量化门槛 | 团队把覆盖率写进 KPI，反而出现「为覆盖而写的测试」 | 用变异测试分数替代覆盖率作为更诚实的指标 |
