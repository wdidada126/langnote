# 第 9 章 重新组织数据

> **一句话**：数据的形状决定一切——**字段叫什么、是值还是引用、是数组还是对象、类型用什么表示**，这些决定了一次改动要花半天还是花半分钟；本章把手法定在「把数据排列成适合你手上的系统的形状」。

---

## 本章地图

| 手法 | 解决什么问题（对应坏味道） | 要点 | 代价 |
| --- | --- | --- | --- |
| **Rename Field** 重命名字段 | 神秘命名 | 改名字，改所有引用点 | 唯一的「改了测试也不一定拦得住」的手法 |
| **Replace Data Value with Object** 以对象取代数据值 | 基本类型偏执、数据泥团 | 把「一个数字」变成有行为的类 | 需要构造、相等性、序列化支持 |
| **Replace Array with Object** 以对象取代数组 | 下标即语义（`data[0]`、`data[3]`） | 给每个位置起名字 | 索引访问点全改；性能敏感处要权衡 |
| **Encapsulate Field / Encapsulate Collection** 封装字段/集合 | 纯数据类、数据泥团 | 把约束收进访问方法 | 样板代码增加 |
| **Replace Type Code with Class** 以类取代类型码 | 基本类型偏执 | 用类承载类别，校验合法值 | 分支要重写；与序列化/ORM 对齐 |
| **Replace Type Code with Subclasses** 以子类取代类型码 | 类型码的分支各有不同行为 | 每个类别一个子类 | 子类数量随类别增长 |
| **Replace Type Code with State/Strategy** 以状态/策略取代类型码 | 类型码会随状态迁移 | 用状态对象承载迁移语义 | 迁移合法性需额外约束 |
| **Replace Subclass with Fields** 以字段取代子类 | 子类只是常量不同 | 用字段 + 工厂方法替代子类 | 要保证实例化路径正确 |
| **Change Value to Reference** 将值改为引用 | 需要共享/身份/生命周期 | 引入工厂与身份 | 共享带来别名与并发问题 |
| **Change Reference to Value** 将引用改为值 | 需要比较、缓存、安全分发 | 去掉 setter、实现相等性、做成不可变 | 每次「改」要造新对象；分配压力 |

**关键结论**：
- 数据重组的**最高性价比动作是改名**；它不改结构、不改行为，却立刻改变你读代码的方式。
- 数组 → 对象的本质是「**把位置语义换成名字语义**」。
- 值/引用的选择是**语义选择**，不是性能选择：想要「相等」就必须是值。

## 核心精讲

> 教学示意代码，不编译、不运行、不参与构建。

### 1. Replace Array with Object：位置语义 ⟶ 名字语义

```js
// 教学示意，不参与构建
// ❌ 下标即含义：读的人必须记住 0/1/2 分别是什么
export function loadUser(row) {
  return { id: row[0], name: row[1], email: row[2], role: row[3] };
}
// 三个月后有人在第 2 位插入了 middleName，全部错位

// ✅ 用具名对象承载
export function loadUser(row) {
  return { id: row.id, name: row.name, email: row.email, role: row.role };
}
// 更彻底的做法是让数据源就直接产出具名字段，而不是靠位置对齐
```

**什么信号说明该做这件事**：
- 数组里混进了「不同含义但同类」的槽位；
- 数组长度靠约定（"这个数组永远是 4 个"）；
- 数据要跨模块传递，但模块之间对「下标顺序」没有共同承诺。

### 2. Replace Type Code with Class / Subclasses / State-Strategy

```java
// 教学示意，不参与构建
// ❌ 类型码：非法值没有保障，分支散落各处
public class Movie {
    public static final int CHILDREN = 2, REGULAR = 0, NEW_RELEASE = 1;
    private int priceCode;
    public double amount(int days) {
        switch (priceCode) {
            case CHILDREN:   return 1.5 + Math.max(0, days - 3) * 0.5;
            case NEW_RELEASE:return days * 3;
            case REGULAR:    return 2 + Math.max(0, days - 2) * 1.5;
            default: throw new IllegalStateException("bad code");
        }
    }
}
```

```java
// 教学示意，不参与构建
// ✅ Replace Type Code with Class：先把「类别」变成有校验的类
public class PriceCode {
    public static final PriceCode CHILDREN   = new PriceCode("CHILDREN");
    public static final PriceCode REGULAR    = new PriceCode("REGULAR");
    public static final PriceCode NEW_RELEASE= new PriceCode("NEW_RELEASE");
    private final String name;
    private PriceCode(String n) { this.name = n; }
    // 非法值根本构造不出来
}

// ✅ 再进一步：Replace Type Code with Subclasses / State-Strategy
interface Price {
    double amount(int days);
    int points(int days);
}
class ChildrenPrice implements Price { … }
class NewReleasePrice implements Price { … }
```

**三种方案的取舍**：

| 方案 | 适合何时 | 不适合何时 |
| --- | --- | --- |
| 以类取代类型码 | 类别只是个标签，行为很少 | 类别本身要携带行为 |
| 以子类取代类型码 | 每个类别的行为稳定且各自不同 | 类别会频繁增删 |
| 以状态/策略取代类型码 | 类别会**随业务状态互相迁移**（订单：待付 ⟶ 已付 ⟶ 已取消） | 状态之间是静态分类，不会迁移 |

### 3. Change Reference to Value：把共享的 mutable 变成可比较的

```js
// 教学示意，不参与构建
// ❌ 引用语义：两份「同款配置」被当成了两个东西，改了一个另一个还在
const cfgA = loadConfig();
const cfgB = loadConfig();
cfgA.timeout = 3000;
cfgA.equals(cfgB)  // false，但它们内容一样

// ✅ 值语义：相等由内容决定，可以放进 Map / Set / 测试断言
class Config {
  constructor({ timeout = 1000, retries = 3 } = {}) { Object.assign(this, { timeout, retries }); }
  with(patch) { return new Config({ ...this, ...patch }); }   // 「改」= 造一个新的
  equals(o)   { return o.timeout === this.timeout && o.retries === this.retries; }
}
```

**判据**：

| 需求 | 方向 |
| --- | --- |
| `a == b` 应该成立 / 要放进 `Set` / 要能缓存 / 要能被多线程安全共享 | Reference ⟶ **Value** |
| 需要「全局唯一」「有生命周期」「要被多方监听修改」 | Value ⟶ **Reference** |

### 4. Rename Field：成本最低、收益最高的一步

```js
// 教学示意，不参与构建
// ❌ 神秘命名：名字和语义不符，读者只能猜
class Order {
  constructor(d) { this.p = d.p; this.n = d.n; this.q = d.q; }  // 谁看得懂？
}

// ✅
class Order {
  constructor({ principal, quantity, quote }) {
    this.principal = principal;   // 本金
    this.quantity  = quantity;    // 数量
    this.quote     = quote;       // 报价
  }
}
```

> **为什么改名不同寻常**：Rename 是唯一一种「测试可能拦不住」的手法。重命名 `getCustId` 为 `getCustomerId` 不会让任何测试失败，但调用方可能依赖反射、字符串拼接的字段名、序列化后的 JSON key。**改名必须靠人眼与全局搜索**，不要盲信工具。

### 5. 数据重组的顺序（组合拳）

```text
1) Rename Field / Variable        —— 先让名字诚实
2) Replace Array with Object      —— 位置语义 ⟶ 名字语义
3) Replace Data Value with Object —— 给「简单值」补上行为
4) Encapsulate Field/Collection   —— 把规则收进字段旁边
5) Replace Type Code with Class/Subclass/State —— 消除 switch
6) Change Value/Reference         —— 定下最后的值/引用语义
7) Make Data Immutable            —— 若还有并发或时序问题，锁死可变性
```

## 版本演进

| 项 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 示例语言 | Java（数组、枚举靠常量表示） | JavaScript（对象字段、数组更常用，因此 `Replace Array with Object` 更受关注） |
| 类型码处理 | 主要靠子类与 switch | 第 2 版明确给出「Class / Subclasses / State-Strategy」三选一，并强调「类别会不会迁移」这个判据 |
| 第 2 版新增的重点 | — | 更强调**不可变数据与值语义**（`Change Reference to Value`、`Make Data Immutable`），呼应并发与函数式编程的流行 |

**2020 年代的重构工具与 AI 辅助**：

- **语言吸收**：Java `record`/enum 接口方法、Kotlin `data class`、TypeScript 的判别联合（discriminated union）、Rust 的枚举与所有权——**「用类型系统表达类别」已经成了默认做法**，`Replace Type Code with Subclasses` 这类手法的适用范围在缩小。这属于「**语言吃掉手法**」的典型。
- **改名工具与它的边界**：IDE 的重命名对静态类型语言近乎完美，对动态类型语言保守。跨语言边界（反射、ORM 映射、序列化 key、SQL 列名）**必须人工核对**——`Rename Field` 的代价正在这里。
- **AI 辅助**：模型非常擅长「把一个数字字段换成一个对象」这类工作，但**不会主动处理序列化契约与数据库列名**。所以它做完之后，你仍需检查：JSON key 变了吗？DB 字段映射改了吗？对外的 API 契约变了吗？
- **现代化建议**：2020 年代更常见的建议是「**先不可变，再谈优化**」。把 `Change Reference to Value` 提前到设计阶段，能省掉后面一大半并发 bug（`Make Data Immutable`）。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」**——重命名一个公共字段看似零成本，实则牵动 API、DB、文档、前端 | 跨边界改名成本被严重低估 | 先做**契约层适配**：对外保持旧名，内部逐步换新；或者一次性安排兼容窗口 |
| 2 | 🔧 **并发代码的重构风险被低估**——`Change Reference to Value` 在多线程下消灭的是「别名 bug」，`Change Value to Reference` 则可能**引入**需要同步的共享可变对象 | 测试绿 ≠ 无数据竞争 | 并发下优先走 Value + 不可变方向；做一个引用字段前必须确认同步策略（参考 `book/C++并发编程实战2/`） |
| 3 | 🔧 **不谈跨服务与数据迁移的重构**——`Replace Data Value with Object` 落到存储层就是 schema 变更：加列、回填、双写、回滚 | 数据库改造是最容易被低估的重构 | 走演化式迁移（扩展列 → 回填 → 双写 → 切读 → 清理）；本书完全不涉及 |
| 4 | 🔧 **AI 生成代码带来的新债**——模型会把「一个数字」随手扩成一堆同类字段（data clump），而且极易与序列化契约冲突 | AI 输出里「结构规整但语义重复」的比例高 | 让 AI 先给出字段清单与语义说明，人工确认后再落地；加一条 CI 检查限制同类型字段连续出现的数量 |
| 5 | 🔧 「Replace Type Code with Class」往往被生成「只有一个枚举字段的类」，等于换了个壳 | 没有行为的空壳类是噪音 | 只有当该类型码**真的会带来行为**（校验、换算、格式）时才提升为类；否则用语言原生的枚举 |
| 6 | 🔧 本章假定「数组 ⟶ 对象」总是进步，但在**极高性能路径**上，数组的索引访问与内存局部性有真实收益 | 某些热循环里对象的字段访问不一定更快 | 性能敏感路径不要顺手数据化；先 profile，再决定 |
| 7 | 🔧 `Make Data Immutable` 没有出现在第 2 版的正面章节里，但它是 2020 年代最被强调的「大型重构」之一 | 不可变化需要配套的对象分配与 GC 调优 | 按「大型重构」的思路单独推进：先给字段加 final/readonly，再逐步把修改改成「返回新实例」 |
| 8 | 🔧 数据重组之后**没有同步文档与契约**：改名只改了代码，Swagger/文档/SQL 仍写旧名 | 文档与代码漂移是最常见的「重构后遗症」 | 把文档与 schema 视为同一个契约的一部分，纳入同一次提交 |
