# 第 3 章 代码的坏味道

> **一句话**：坏味道不是「代码丑」，而是**「这段代码，下次改动会贵在哪里」的可疑信号**——它是一张索引表，指向该动用哪一组重构手法；读完本章，你手上才真正有「发现机制」。

---

## 本章地图

| 节 | 坏味道（原书 24 条） | 首选手法 | 一句话判断标准 |
| --- | --- | --- | --- |
| 3.1 | **神秘命名** Mysterious Name | Rename Method/Variable/Field | 名字不能「猜」出意图，只能「读」出来 |
| 3.2 | **重复代码** Duplicated Code | Extract Method / Pull Up Method / Extract Superclass | 同一件事写了第二遍 |
| 3.3 | **过长函数** Long Function | Extract Method | 读不完、跳来跳去、一次想不全 |
| 3.4 | **过长参数列表** Long Parameter List | Introduce Parameter Object / Remove Parameter | 参数多到记不住含义与顺序 |
| 3.5 | **全局数据** Global Data | Encapsulate Field / Replace Global Variable with Local | 谁能改、什么时候改、改了影响谁，都不可控 |
| 3.6 | **可变数据** Mutable Data | Extract Method / Spline / Make Data Immutable | 数据能在你没注意的时候被改掉 |
| 3.7 | **发散式变化** Divergent Change | Extract Class / Move Method | 一个方向的变化要改**一个**类里的**多处** |
| 3.8 | **霰弹式修改** Shotgun Surgery | Move Method/Field / Inline Class | 一个方向的变化要改**多个**类里的**一处** |
| 3.9 | **依恋情结** Feature Envy | Move Method | 函数最想待的地方不是它现在待的地方 |
| 3.10 | **数据泥团** Data Clumps | Introduce Parameter Object / Extract Class | 一组参数/字段永远同时出现 |
| 3.11 | **基本类型偏执** Primitive Obsession | Replace Data Value with Object / Replace Type Code with Class | 本该是小对象的东西只是一个数字/字符串 |
| 3.12 | **重复的 switch** Repeated Switches（第 1 版叫「Switch Statement / switch 惊魂」） | Replace Conditional with Polymorphism | 同一个 `switch` 在多处重复，加一个分支要改一堆 |
| 3.13 | **循环语句** Loops | Extract Method / Extract Function | 循环体本身还能再说清楚一件事 |
| 3.14 | **冗赘的元素** Lazy Element（第 1 版叫「Lazy Class / 冗赘类」） | Inline Class / Collapse Hierarchy / Inline Method | 存在的意义只是一次转发 |
| 3.15 | **夸夸其谈通用性** Speculative Generality | Change Interface to Concrete Function / Collapse Hierarchy / Inline Class | 「为了将来可能的需求」提前造了扩展点 |
| 3.16 | **临时字段** Temporary Field | Extract Class / Introduce Null Object | 只在某次计算中间存在，平时是个空壳 |
| 3.17 | **过长的消息链** Message Chains | Hide Delegate | 穿越多层 `a().b().c()` 才能拿到东西 |
| 3.18 | **中间人** Middle Man | Remove Middle Man | 中间人除了转发什么也没干 |
| 3.19 | **内幕交易** Insider Trading | Move Method / Hide Delegate | 一个类伸手进另一个类的私有地盘 |
| 3.20 | **过大的类** Large Class | Extract Class / Extract Subclass | 想改一件事要在类里上下找半天 |
| 3.21 | **异曲同工的类** Alternative Classes with Different Interfaces | Rename / Move / Extract Superclass | 做同一件事，却有两套名字/两套结构 |
| 3.22 | **纯数据类** Data Class | Encapsulate Field / Move Method | 只有字段和 getter，行为全在别处 |
| 3.23 | **被拒绝的遗赠** Refused Bequest | Push Down Method/Field / Replace Inheritance with Delegation | 继承来的东西几乎用不上，接口却被继承污染了 |
| 3.24 | **注释** Comments | Extract Method / Rename / 删除冗余注释 | 注释在解释「做了什么」而不是「为什么」 |

**关于第 2 版的改名**：第 1 版里的 **Switch Statement**（中文版译作「switch 惊魂」）在第 2 版改名为 **Repeated Switches**（重复的 switch），强调的重点从「有 switch 不好」变成「同一批 switch 重复出现」；第 1 版的 **Lazy Class**（冗赘类）在第 2 版改名为 **Lazy Element**（冗赘的元素），范围从「类」扩到「函数/参数」一级。这两处改名本身就说明了 20 年间社区理解的变化。

**关键结论**：
- 24 条不是清单式「检查项」，而是**诊断结果**：每一条背后都有对应的「首选手法 + 备选手法」。
- 判断顺序：**先读代码找「变化方向」**（发散式还是霰弹式），再选类归属，最后才是命名与注释。
- 「没有坏味道」是好事；「有坏味道但改不动」通常意味着**先补测试**。

## 核心精讲

> 教学示意代码，不编译、不运行、不参与构建。

### 1. 发散式变化 vs 霰弹式修改：最有用的一组对照

| | 含义 | 症状 | 首选手法 |
| --- | --- | --- | --- |
| **发散式变化** Divergent Change | 一个方向的变化，需要改**同一个类里的多处** | 加一种新报表，要在 `User` 类里改 5 个方法 | Extract Class / Move Method |
| **霰弹式修改** Shotgun Surgery | 一个方向的变化，需要改**多个类里的各一处** | 换一次计费规则，要改 `Order`、`Pricing`、`Invoice`、`Config` 四个文件的一行 | Move Method / Move Field / Inline Class |

```js
// 教学示意，不参与构建
// ❌ 霰弹式修改：换一种「计费口径」，四处各改一行
class Order       { get amount() { return this.qty * this.rate(); } }   // 改1
class Pricing     { rate() { return cfg.getPrice(); } }                  // 改2
class Invoice     { format() { return this.order.amount(); } }           // 改3
class FeeConfig   { getPrice() { return this.v2 ? 1.1 : 1.0; } }         // 改4

// ✅ 收敛：把「口径」搬进一个专门的 RatePolicy 对象
class RatePolicy { constructor(v2) { this.v2 = v2; }                     // 只改这里
                   apply(amount) { return this.v2 ? amount * 1.1 : amount; } }
class Order { constructor(policy) { this.policy = policy; }
              get amount() { return this.policy.apply(this.qty * this.base); } }
```

### 2. 依恋情结：函数想去另一个类

```java
// 教学示意，不参与构建
// ❌ 依恋情结：这个函数 90% 的注意力都在 Extra 上，却挂在 Order 里
class Order {
    double total() {
        double sum = 0;
        for (LineItem item : items) {              // 反复探听 Extra 的隐私
            if (item.extra().isTaxable()) {
                sum += item.amount() + item.extra().taxRate() * item.amount();
            } else {
                sum += item.amount();
            }
        }
        return sum;
    }
}
```

```java
// 教学示意，不参与构建
// ✅ Move Method：把「算税」这件事整个搬到它热恋的对象身上
class Extra {
    double taxOn(double amount) {
        return this.taxRate() * amount;
    }
    boolean isTaxable() { /* … */ }
}

class Order {
    double total() {
        double sum = 0;
        for (LineItem item : items) {
            sum += item.isTaxable()
                 ? item.amount() + item.extra().taxOn(item.amount())
                 : item.amount();
        }
        return sum;
    }
}
```

> 判断口诀：**「这个函数最常提到的是哪个类的名字？」** 如果答案不是它所在的类，就是依恋情结。

### 3. 重复的 switch ⟶ 多态（第 12 条的重点）

```js
// 教学示意，不参与构建
// ❌ 同一个 switch 出现在三个文件里；加一种新状态要改三处（霰弹式修改）
function shippingCost(kind, days) {
  switch (kind) { case "STANDARD": return days * 1; case "EXPRESS": return days * 2; }
}
function shippingLabel(kind, days) {
  switch (kind) { case "STANDARD": return "std"; case "EXPRESS": return "exp"; }
}
function canRefund(kind, days) {
  switch (kind) { case "STANDARD": return true; case "EXPRESS": return false; }
}
```

```js
// 教学示意，不参与构建
// ✅ Replace Conditional with Polymorphism：把分支搬进对象
const shipping = {
  STANDARD: { cost: (d) => d * 1, label: () => "std", refundable: () => true  },
  EXPRESS:  { cost: (d) => d * 2, label: () => "exp", refundable: () => false },
};
function shippingCost(kind, days)   { return shipping[kind].cost(days); }
function shippingLabel(kind)        { return shipping[kind].label(); }
function canRefund(kind)            { return shipping[kind].refundable(); }
// 新增一种运输方式 = 只加一个 key，其余三个函数一个字都不用改
```

### 4. 临时字段与「纯数据类」：两种最常见的结构病

```java
// 教学示意，不参与构建
// ❌ 临时字段：_discount 只在 applyPromo() 那一次计算中有意义
class Cart {
    void applyPromo(String code) { this._promo = codes.get(code); this._discount = compute(); }
    double total() { return this._discount != null ? base - _discount : base; }
    private String _promo;
    private double _discount;
}

// ✅ 提炼：把「促销」变成有自己生命周期的对象
class Promo {
    Promo(String code) { this.code = code; this.discount = computeFor(code); }
    double apply(double base) { return base - this.discount; }
}
class Cart { void applyPromo(Promo p) { this.promo = p; }
             double total() { return promo == null ? base : promo.apply(base); } }
```

```java
// 教学示意，不参与构建
// ❌ 纯数据类：行为和它所在的对象分了家，于是永远有人替它干活（内幕交易）
class Customer {
    private String name; private String email;
    public String getName() { return name; }
    public void setName(String n) { this.name = n; }
    // …email 的 getter/setter 也是纯搬运
}
class CustomerFormatter { String display(Customer c) { return c.getName() + " <" + c.getEmail() + ">"; } }

// ✅ 把「只有字段和 getter」的类重构成有行为的对象；或反过来承认它就是值对象
```

### 5. 注释（第 24 条）：注释是「代码不会说话」的证据

| 注释类型 | 例子 | 该怎么做 |
| --- | --- | --- |
| 讲「做了什么」的注释 | `// 把金额加上折扣` 后面跟着 `amount = amount - discount;` | 用 **Extract Method + Rename** 让代码自己说；删 |
| 讲「为什么」的注释 | `// 这里是业务方要求的口径，别按表面语义改` | **保留**，并且应该搬进被解释的那段代码旁 |
| 记录「历史包袱」的注释 | `// 兼容 v1 的调用方，2026 年再清理` | 保留，同时把它变成 TODO 或技术债条目 |
| 被注释掉的代码 | `// if (old) { ... }` | 删。版本控制会记得 |

## 版本演进

| 项 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 坏味道表述 | 24 条，正文里逐条给出「症状 / 危害 / 手法」 | 同一批条目的**顺序与措辞都调整过**，「注释」从第 1 版靠后的位置被保留到最后 |
| 两条重要改名 | Switch Statement ⟶ **Repeated Switches**；Lazy Class ⟶ **Lazy Element** | 顺序即分类学：第 1 版按「症状种类」排，第 2 版按「代码失位的层次」排（命名 → 结构 → 数据 → 逻辑 → 继承 → 注释） |
| 示例语言 | Java | JavaScript，并给出函数式环境下的判断（如「没有类时如何识别依恋情结」） |
| 与「手法名录」的衔接 | 每条坏味道对应手册式条目 | 每条坏味道明确写「首选手法 / 备选手法」，更像查表 |

**2020 年代新增（第 2 版名录之外）的坏味道**：这些不是 Fowler 写进第 2 版的条目，而是社区在 2015 年之后总结出、值得补进这张表的信号——

| 新增坏味道 | 症状 | 手法 |
| --- | --- | --- |
| **过度使用 null** | 每一层都在 `if (x == null)`，空指针异常靠运气 | **Introduce Null Object**、`Optional`/`Maybe` 类型、把「无」建模成一层类型 |
| **过度防御性编程** | 参数进来先查 17 项，方法内部又 try-catch 吞掉异常 | 让类型系统与边界校验先替你检查，只在**系统边界**做防御；把「不可能」写成断言 |
| **AI 生成的冗余代码** | 重复分支、重复校验、无用的中间层，结构规整但语义冗余 | 坏味道扫描器 + CI 中的重构建议 |
| **依赖地狱式的通用基类** | 一个 `BaseService` 被所有类继承，谁都改它 | Push Down / Replace Inheritance with Delegation |
| **测试里的逻辑** | 测试断言里写满了 `for`/`if`（Logic-in-Tests） | 用 xUnit Test Patterns 的模式改写测试 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」**——列了 24 条坏味道，但没有一条给出「先修哪条」的优先级 | 一次性全改等于重写；团队往往一条都不改 | 只改**即将触碰的那段代码**（船桨原则：借重构之名做相关改动），不要发起「全项目清理」运动 |
| 2 | 🔧 第 24 条「注释」在中文语境里容易被读成「少写注释」，这与《代码整洁之道》的直接冲突 | Clean Code 主张「注释是必要的恶」但要求写「为什么」；本书更激进：能改名/refactor 掉的注释就该删 | 二者可以同时成立：**讲「做了什么」的注释删掉（本书），讲「为什么」的注释写清楚（Clean Code）** |
| 3 | 🔧 **并发代码里的坏味道无法用同一套手法处理**——「可变数据」在单线程下是坏味道，在多线程下是**必需品** | 提取/搬移会改变锁范围与可见性；很多「过长函数」其实是串行化边界 | 并发相关重构先做同步与可见性检查（`book/C++并发编程实战2/`）；把「并发安全」当作先于结构的约束 |
| 4 | 🔧 **不谈跨服务与数据迁移的重构**——霰弹式修改在服务边界上的表现（一次改要动 6 个仓库 + 数据库 + 契约测试）被完全略过 | 微服务架构下「Move Method」的成本从一次提交变成一次跨团队发布 | 拆服务用绞杀者模式、双向兼容发布；这在本书里没有任何覆盖，要看 `book/微服务架构设计模式.md` |
| 5 | 🔧 **「过度使用 null」没有进入第 2 版的 24 条**（2020 年代最被重视的坏味道之一） | 第 2 版（2019）写作时 `Optional` 刚成为主流，书中只在 Introduce Null Object 里点到 | 把「过度使用 null」「过度防御性编程」补进你团队的坏味道清单（见「版本演进」小节的新增表） |
| 6 | 🔧 **AI 生成代码带来的新债**：模型输出结构规整，但坏味道以「冗余分支 + 重复校验 + 无用中间层」的形式出现 | 传统坏味道扫描器对 AI 产出的「整洁垃圾」识别率低 | 在 CI 里加入重复代码检测与体积度量；对 AI 产出保持与人类同样的审查密度 |
| 7 | 🔧 「过长函数」的阈值（第 1 版说 20 行，第 2 版说更短）与语言强相关 | JS/Python 的表达式密度与 Java 不同；Rust 的生命周期标注会让函数天然更长 | 阈值应按**认知负荷**（一次能记住几件事）而非行数；用圈复杂度与嵌套深度作为更稳的代理指标 |
| 8 | 🔧 24 条里没有一条涉及**测试代码自身的坏味道** | 团队里最容易失控、最影响后续重构速度的正是测试代码 | 用《XUnit Test Patterns》的坏味道表补上 |
