# 第 12 章 处理继承关系

> **一句话**：继承是一种**强承诺**——它把父类的接口和耦合一并继承下来；本章的全部手法只有两个方向：**把不该继承的赶下去（Push Down），把该共享的提上来（Pull Up）**，或者干脆**取消继承，改用委托**。

---

## 本章地图

| 手法 | 方向 | 解决什么问题 | 代价 |
| --- | --- | --- | --- |
| **Extract Subclass** 提炼子类 | 下分 | 一个类里有一批方法只被少数场景使用 | 子类数量随场景增长 |
| **Extract Superclass** 提炼超类 | 上合 | 几个子类有大量重复实现（重复代码） | 超类可能变成「垃圾抽屉」 |
| **Collapse Hierarchy** 折叠继承体系 | 压平 | 继承层次只剩一层或子类是空壳 | 多态扩展点被封死 |
| **Extract Interface** 提炼接口 | 横向 | 不共享继承树，却需要可替换 | 接口加方法要改所有实现 |
| **Pull Up Method / Pull Up Field** 上移方法/字段 | 上合 | 子类里有重复实现 | 基类变胖；依赖被上提 |
| **Push Down Method / Push Down Field** 下移方法/字段 | 下分 | 基类里的方法/字段只有一个子类用 | 基类变空，后续可能折叠 |
| **Replace Inheritance with Delegation** 用委托取代继承 | 换成委托 | 被拒绝的遗赠、继承带来的多余耦合 | 多一层转发；调用多一跳 |
| **Replace Delegation with Inheritance** 用继承取代委托 | 换成继承 | 委托写得太厚，继承反而简单 | 把不必要的耦合带进来 |
| **Replace Subclass with Strategy** 以策略取代子类 | 横向 | 只想换算法实现，不想背继承包袱 | 需要 Extract Interface；策略状态管理更复杂 |
| **Form Special Case** 形成特殊 CASE | 横向 | 在函数里写死的特例分支 | 特例类会被无限扩展 |

**关键结论**：
- 继承的判据只有一条：**子类是不是「就是」父类的一种**？是 → 继承；只是「有父类提供的某种能力」→ **委托**。
- 上移的**副作用**是「基类变胖」：上移前要问一句「这些被上提的东西，父类自己需要吗」；不需要就该先下移、再上移。
- 组合/委托优先是 2010 年代之后的共识，**但它不是免费的**——转发方法写多了，就变成另一个「冗赘元素」。

## 核心精讲

> 教学示意代码，不编译、不运行、不参与构建。

### 1. 继承 vs 委托的判别（先做这个决定）

| 问题 | 答「是」 | 答「否」 |
| --- | --- | --- |
| 子类「是一个」父类吗？（Car is a Vehicle） | 继承 | 委托 |
| 子类的行为会被父类的**演化**影响吗？ | 继承 | 委托 |
| 你只需要父类的一部分能力？ | 委托 | — |
| 子类需要重写父类的多处行为？ | 继承 | — |
| 父类会被多个**无关**的类复用？ | 委托（否则接口被污染） | — |

```java
// 教学示意，不参与构建
// ❌ 被拒绝的遗赠：继承了一堆用不上的方法（fly/sail 都在 public 接口上）
class Car extends Vehicle {
    void fly() { }     // 用不上，却成了公开承诺
    void sail() { }
}
```

```java
// 教学示意，不参与构建
// ✅ Replace Inheritance with Delegation：只暴露我需要的那部分
class Car {
    private final Vehicle delegate = new Vehicle();
    public void start() { delegate.start(); }
    public void stop()  { delegate.stop(); }
}
// 或者抽一个「我需要的接口」出来（Extract Interface 之后再委托）
interface Drivable { void start(); void stop(); }
```

### 2. Push Down：把不该继承的赶下去

```java
// 教学示意，不参与构建
// ❌ 基类里的方法只被一个子类用到；其他子类继承到了用不上的接口
abstract class Animal {
    public void speak() { }
    public void swim()  { }     // 只有 Duck 用；但所有 Animal 都有了
}
```

```java
// 教学示意，不参与构建
// ✅ Push Down Method：只留下有子类的东西
abstract class Animal { }
class Duck extends Animal {
    public void speak() { }
    public void swim()  { }
}
```

**顺序建议**：`Push Down` 常常要先 `Extract Class`/`Move Method` 配合，把方法**先降到那个子类上**，再删掉基类的版本。降不下去的方法说明**它本来不该属于基类**。

### 3. Pull Up：把该共享的提上来

```java
// 教学示意，不参与构建
// ❌ 重复代码：三个子类里各写了一遍同样的方法体
class Account { double interestFor(int days) { return balance * days * 0.0001; } }
class Loan    { double interestFor(int days) { return balance * days * 0.0001; } }
class Credit  { double interestFor(int days) { return balance * days * 0.0001; } }
```

```java
// 教学示意，不参与构建
// ✅ Pull Up Method：提到超类，子类只保留「各不相同的部分」
abstract class FinancialProduct {
    protected abstract double rate();
    public double interestFor(int days) { return balance * days * this.rate(); }
}
class Account extends FinancialProduct { protected double rate() { return 0.0001; } }
class Loan    extends FinancialProduct { protected double rate() { return 0.0002; } }
```

> **注意**：只有当被上移的东西对**父类自己也有意义**时才上移。如果超类不需要 `interestFor`，却因为「子类要复用」而被迫持有它，那其实是**设计错了**——该做的是 Extract Class / Replace Inheritance with Delegation。

### 4. Extract Interface：跨继承树的可替换性

```java
// 教学示意，不参与构建
// ❌ 两个类没有公共父类，但客户只想要「能存钱」这一件事
class SavingAccount { public void deposit(double a) { … } public void audit() { … } }
class Walet         { public void deposit(double a) { … } public void upgrade() { … } }
// 客户被迫依赖完整的 SavingAccount 接口

// ✅ Extract Interface：只为「可替换」这件事建模
interface DepositCapable { void deposit(double amount); }
class SavingAccount implements DepositCapable { … }
class Walet implements DepositCapable { … }
```

**适用信号**：
- 客户代码里有 `if (obj instanceof X)` 之类的类型判断；
- 想在一个列表里混装多种但「行为相似」的对象；
- 想做**测试替身**，却因为类层次而无法 mock。

### 5. Replace Subclass with Strategy：只想换算法，不想继承

```java
// 教学示意，不参与构建
// ❌ 用继承写算法变体：加一种新算法要加一个新子类，且算法与生命周期绑死
abstract class Billing {
    public double amount(int days) { return base() * days; }
    protected abstract double base();
}
class EarlyBirdBilling extends Billing { protected double base() { return 0.8; } }
class PeakBilling    extends Billing { protected double base() { return 1.3; } }
```

```java
// 教学示意，不参与构建
// ✅ 以策略取代子类：算法变成可组合的一等公民
interface RatePolicy { double rate(); }
class EarlyBirdRate implements RatePolicy { public double rate() { return 0.8; } }
class PeakRate       implements RatePolicy { public double rate() { return 1.3; } }

class Billing {
    private final RatePolicy policy;
    public Billing(RatePolicy policy) { this.policy = policy; }
    public double amount(int days) { return 1.0 * days * this.policy.rate(); }
}
```

**什么时候不该上 Strategy**：只有一个实现时，`Extract Interface` 本身就是**夸夸其谈通用性**。等第二种实现出现再换（三次法则）。

### 6. 继承重构的顺序（组合拳）

```text
1) 先判断方向：「该共享」还是「该拆开」
2) 该共享 ──► Collapse Hierarchy / Extract Superclass
              └─► Pull Up Method / Pull Up Field
3) 该拆开 ──► Extract Subclass
              └─► Push Down Method / Push Down Field
4) 层次不再合理 ──► Extract Interface
                    └─► Replace Inheritance with Delegation
                           （或反向：Replace Delegation with Inheritance）
5) 换的只是算法 ──► Replace Subclass with Strategy
```

## 版本演进

| 项 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 章节结构 | 第 1 版把继承相关的手法叫「Generalization（泛化）」，分散编排 | 第 2 版统一为第 12 章「**处理继承关系**」，包括 Extract Subclass / Extract Superclass / Collapse Hierarchy / Extract Interface / Pull & Push / Replace Inheritance with Delegation / Replace Subclass with Strategy 等 |
| 示例语言 | Java，典型 OO 继承示例 | JavaScript：演示**无类语言里如何表达同样的结构**（工厂函数 + 策略对象） |
| 社区倾向 | 1999 年继承是「复用首选」 | 2019 年「组合优于继承」已成主流共识，本章在书末，正好呼应全书的收束 |

**2020 年代的重构工具与 AI 辅助**：

- **语言差异改变了这一章的适用性**：
  - **Go / Rust**：没有传统的类继承，用组合 + trait/接口，因此本章的「继承重构」在多数项目里**根本不会发生**；
  - **Java / C#**：`sealed` 类型、`record`、接口默认方法让「层次」变轻，很多原本需要子类的场景改用接口 + 不可变数据；
  - **TypeScript / Python**：靠结构类型与鸭子类型实现「提炼接口」，成本极低。
- **IntelliJ 的支持与局限**：Pull Members Up / Push Members Down / Extract Interface / Introduce Base Class 都是成熟动作；但工具**无法判断「该继承还是该委托」**，也无法判断「上移之后基类语义是否还成立」——第 1 步的判断仍然只能靠人。
- **AI 辅助**：模型擅长生成子类与接口，但容易**过度使用继承**（给出一个 `BaseService` 上帝基类）；审查时重点看：是不是每个子类都被要求实现一批用不上的方法。
- **现代化的反趋势**：2020 年代出现了「**继承的复兴**」的局部迹象——当类型是 **sealed 的、同模块内的、明确穷尽的**（如 AST 节点、协议状态机），`sealed` + 模式匹配远比策略对象表更好读。判断标准变成了：**层次是否封闭**。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」**——继承重构是全书最「结构上」的重构，一次 Push Down 可能牵动整个层次 | 大型继承体系往往在多个模块里，改动面广 | 优先做**最外层的子类**（改动最小、收益最直观），不要一上来重排基类 |
| 2 | 🔧 **并发代码的重构风险被低估**——`Replace Inheritance with Delegation` 会把「子类覆写方法」变成「委托对象转发」，**锁的持有者可能从子类变成委托对象** | 覆写方法是常见的加锁点；改成委托后同步语义改变 | 并发相关的继承重构要在锁分析之后做；重构后跑并发测试与 sanitizer |
| 3 | 🔧 **不谈跨服务与数据迁移的重构**——`Extract Superclass` 在企业里最常见的变体是「把公共逻辑抽成公共库 ⟶ 跨服务共享」，这直接引出版本、兼容与依赖治理问题 | 公共库的升级往往是「所有下游被迫升级」 | 公共逻辑先用 Adapter 收敛，再决定抽库；本书不涉及依赖治理 |
| 4 | 🔧 **AI 生成代码带来的新债**——模型偏爱「先建一个 `BaseEntity` / `BaseService` 基类」的结构，这恰好制造出最典型的继承反模式 | AI 输出里 `Base*Class` 的比例远高于人类 | 在评审规范里明确限制基类数量；用静态检查禁止「有无用方法的公共基类」 |
| 5 | 🔧 第 2 版写于 2019 年，尚未充分反映 **sealed 类型与穷尽匹配**在 2020 年代的普及；本章对「层次」的偏好需要按语言重新校准 | Java 17+ 的 sealed、C# 的 sealed record、Kotlin 的 sealed 接口、Rust 的 enum 都改变了「什么时候该有层次」 | 层次只在**封闭且在同一个模块内**时才优选；跨模块的多态优先用接口 + 组合 |
| 6 | 🔧 「组合优于继承」被当成绝对律，`Replace Inheritance with Delegation` 因此被过度使用 | 转发方法堆积会产生新的「冗赘元素」和调试链路问题 | 只有当「只需要一部分能力」「层次会被无关类复用」时才换成委托；转发层保持极薄 |
| 7 | 🔧 `Pull Up Method` 之后**基类的语义被扩大了**，后续更容易违反里氏替换原则（子类不能只实现一部分） | 上移是「低成本高后患」的动作 | 上移前先问：父类自己需要它吗？不需要就不是复用问题，而是职责该重新分配 |
| 8 | 🔧 本章默认继承体系是**开放**的（任何人都可加子类）；在 sealed / final 成为常态的语言里，`Extract Subclass` 的预条件（「能被安全扩展」）已经自动满足 | 现代语言默认禁止扩展，反而简化了这一章的许多风险判断 | 利用语言的 final/sealed 做「预条件检查的替代品」；这也是 2020 年代的一个便利 |
