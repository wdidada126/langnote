# 第 5 章 介绍重构名录

> **一句话**：名录不是「招式表」，而是**带预条件的行为保持变换的目录**——学会查表的顺序是「先找坏味道 → 再定目标形态 → 最后选手法」，而不是从第一页开始背。

---

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 名录是什么 | 每个条目 = **名称 + 动机 + 步骤 + 示例 + 参考**；名称让讨论变得精确 | 名字本身就是协作资产：「把这个改成 Extract Class」比「这里 restructuring 一下」强一万倍 |
| 5.2 名录不是配方 | 每步变换都有**预条件**；不满足预条件硬做，等于把 bug 藏进 diff | 手法有前提；读条目先读「动机与预条件」，再看步骤 |
| 5.3 如何检索 | 三种入口：坏味道索引、目标形态索引、字母序在线检索（refactoring.com） | 熟练之后，你是在**组合手法**，不是在查单条 |
| 5.4 手法的粒度与顺序 | 手法之间会互相依赖：Rename ⟶ Move ⟶ Extract Class；顺序错了就白做 | 先做「不改变控制流」的，再做「搬移职责」的 |
| 5.5 名录之外的判断 | 手法解决的是「结构」，解决不了「这里根本不该有这个函数」 | 手法用尽之后仍别扭，说明是**职责划分**问题，回去重读第 3 章 |

**关键结论**：
- 名录的价值首先是**沟通**：让「我要改结构」变成一句可评审、可回滚、可复用的话。
- 第二个价值是**教学**：你看到的是别人已经踩过的坑的抽象形态。
- 第三个价值是**工具**：IDE 的重构菜单就是名录的产品化版本。

## 核心精讲

> 教学示意代码，不编译、不运行、不参与构建。

### 1. 一个条目应该长什么样（以 Extract Class 为例）

| 字段 | 内容 |
| --- | --- |
| **名称** | Extract Class（提炼类） |
| **动机** | 某个类做了太多事；或某组字段/方法天然属于另一个概念 |
| **预条件** | 那部分代码能被整体摘出；被摘出的部分没有被外部依赖反向引用 |
| **步骤** | 1) 决定「什么东西该属于新类」；2) 建立新类，把字段与相关方法搬过去；3) 旧类留一个引用或转发；4) 逐步去掉转发；5) 给新类起名；6) 跑测试 |
| **示例** | 见 `08-搬移特性.md` |
| **代价** | 类数量增加；两方依赖关系需要重新设计；可能引入循环依赖 |
| **参考** | refactoring.com 的同名条目 |

### 2. 检索的三条路径

```text
路径 A（最常用）：坏味道 ⟶ 首选手法
    「霰弹式修改」
      ↓ 首选
    Move Method / Move Field / Inline Class
      ↓ 具体做法
    08-搬移特性.md

路径 B（目标导向）：我想要的结构 ⟶ 手法
    「让加一种新片型只改一个文件」
      ↓
    Replace Conditional with Polymorphism → 10-简化条件逻辑.md
    Replace Subclass with Strategy      → 12-处理继承关系.md

路径 C（在线检索）：按名字查
    refactoring.com 的字母序重命名目录 / 本书末尾「重构列表」与
    「坏味道与重构手法速查表」
```

### 3. 手法是有顺序的（组合拳）

```js
// 教学示意，不参与构建
// 目标：把「算优惠券」从 Order 里彻底搬走
// 顺序错了会白做：
// ❌ 顺序错：先 Extract Method（这样搬的时候还带着一堆对 Coupon 的探听）
// ✅ 正确顺序：
//  1) Rename Variable      —— 先让名字诚实
//  2) Encapsulate Field    —— 先把 Coupon 的字段圈起来（否则搬的时候要连私有一起搬）
//  3) Move Field           —— 把字段搬到 Coupon
//  4) Move Method          —— 把算钱的方法搬到 Coupon
//  5) Hide Delegate        —— 让 Order 只在需要时暴露 Coupon
//  6) Remove Middle Man    —— 等没人需要穿透 Order 之后再撤掉转发
```

### 4. 手法解决不了什么（名录的边界）

| 情况 | 名录能做什么 | 真正的问题 |
| --- | --- | --- |
| 「这个函数根本不该存在」 | Inline / Inline Class | 需求决定职责，手法不决定 |
| 「这段逻辑有两个真相（逻辑重复）」 | Extract / Pull Up | 可能该删掉其中一方 |
| 「这是一个坏命名，改完还是别扭」 | Rename | 概念本身没想清楚，改名只是止血 |
| 「数据库表不这样存」 | 无 | 数据模型要先变（本书不覆盖 schema 重构） |
| 「这个模块在别的进程里」 | Move Method 会变成网络调用 | 架构与部署边界问题（本书不覆盖跨服务重构） |

### 5. 一个「手法 vs 设计决策」的判别试验

> **问自己**：如果我只是执行了这个手法的全部步骤，是否就完成了设计？
>
> 如果答案是「是」——那它是纯手法（Extract Method、Rename）。
> 如果答案是「不是，我还得决定谁是负责人」——那它其实是一个设计决策（Extract Class、Move Method、Extract Interface）。
>
> 后者才是本书真正的重点：**名录给你的动作，设计给你的判断。**

## 版本演进

| 项 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 名录组织 | 按「重构手法」Flat 式编排，前 5 章按手法类别分组 | 重组为**更内聚的 6 组**：重新组织函数 / 搬移特性 / 重新组织数据 / 简化条件逻辑 / 重构 API / 处理继承关系 |
| 示例语言 | Java | JavaScript + 函数式示例（「无类环境下如何重构」） |
| 手法数量 | 70 多个（含第 1 版特有的部分） | 60 多个（合并与重命名，如 Pull Up/Down、Collapse Hierarchy） |
| 与在线版的对应 | refactoring.com 已上线 | 正文 + 书末「重构列表」「坏味道与重构手法速查表」与在线版一一对应 |

**2020 年代的重构工具与 AI 辅助**：

- **IDE 把名录做成了菜单**：IntelliJ 的 Refactor 菜单有上百个动作，每一项就是名录里的一个条目（含预览与冲突检测）。这本书第 5 章教的东西，今天有一半可以直接点。
- **AI 让「查表」变得口语化**：你可以直接说「帮我把这个提成函数」，模型执行的是名录里那条手法——但**它可能跳过预条件检查**。这正是第 2 版强调「名录不是配方」的原因。
- **OpenRewrite 把手法升级成 recipe**：每条 recipe 是一个可执行、可版本化、可跨仓库重复运行的「重构条目」，相当于把名录编译成了流水线。
- **局限**：无论工具多强，**判断「该不该做」**仍然只能由人完成。AI 在执行 Extract Class 时不会告诉你「其实这里该先 Extract Interface，再做依赖倒置」。

## 近年研究与工业界开源实践（2015–2026）

**趋势**：名录本身在 2020 年代基本稳定，研究热点变成「**如何让机器可靠地执行名录里的条目**」。两条主线：
1. **语义等价保证**（Roslyn、TypeScript 编译器、rustfix 一侧）；
2. **规模化执行**（OpenRewrite 一侧，把名录编译成可在 CI 里跑的批量迁移）。

| 仓库 | star（`gh api` 实测，2026-09-25） | 说明 |
| --- | --- | --- |
| `dotnet/roslyn` | **20,688★** | 名录条目「可执行化」的最佳范例：语义模型 + 分析器让重命名、提取变得安全 |
| `JetBrains/intellij-community` | **20,588★** | Refactor 菜单 = 名录的 UI 化；可查看每个重构的实现与冲突处理 |
| `openrewrite/rewrite` | **3,750★** | 跨仓库批量执行的名录（recipe 体系），把「一次改 300 个仓库」变成日常 |
| `google/error-prone` | **7,238★** | 编译期检查 + 自动修正，把名录的一部分变成 CI 门禁 |
| `llvm/llvm-project` | **40,650★** | clang-tidy + fix-it：检查与修正的分离式设计 |
| `rust-lang/rust` | **119,150★** | `clippy` 给出「这里该用手法」的建议，`rustfix` 负责改 |
| `spring-projects/spring-framework` | **60,260★** | 名录最常见的应用现场：框架升级时的批量结构迁移 |

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」**——名录有 60+ 条目，学完就需要时间实践；团队往往一个都不用 | 学会名录和用上名录之间隔着「有空就改」的文化 | 只学你手上正在出现的坏味道对应的 3–5 条；用「船桨原则」把手法用在即将触碰的代码上 |
| 2 | 🔧 第 5 章强调「名录不是配方」，但** CI 里的静态检查工具恰恰把名录当配方用** | 工具给的是「这里可以 Extract」，不保证「应该 Extract」 | 把静态检查当作**提示**而非**门禁**；差异化配置：新代码严格，老代码只报警 |
| 3 | 🔧 **并发代码的重构风险被低估**——名录里的 Move Method / Move Field 在并发模块上会改变锁范围与可见性 | 同一手法在单线程与多线程下的预条件不同 | 并发模块重构前先确认同步语义；手法执行后重跑并发测试 |
| 4 | 🔧 **不谈跨服务与数据迁移的重构**——名录里最「贵」的手法（Extract Class、Move Method）在跨服务场景变成跨团队契约谈判 | 跨服务「重命名一个字段」= API 版本管理 + 数据迁移 + 双写 + 回滚方案 | 走绞杀者模式与双向兼容发布；本书名录对这些场景几乎无话可说 |
| 5 | 🔧 **AI 生成代码带来的新债**——AI 能直接「照着名录执行」，却常常**跳过预条件**，导致「手法执行成功但语义变了」 | 模型不理解你的测试覆盖，也不做等价性证明 | 把 AI 产出的重构当作**高风险的 refactor commit**，逐条跑测试并人工审 diff 的形状 |
| 6 | 🔧 名录以「单个文件内/单进程内」的变换为隐含作用域，没说清**跨模块边界上的手法成本** | 一旦跨越模块/包/服务，Move 的成本呈数量级上升 | 先判断边界：同包用 Move，跨包先引入接口层，跨服务先加适配层 |
| 7 | 🔧 「手法名字」在跨语言社区里不统一（Extract Class 与 Introduce Class、Replace Type Code with Class 的译名差异） | 中译本与英文原书用词不完全一致，团队沟通会错位 | 统一以**英文原名 + 中译名**的写法出现在评审记录里（本目录所有手法都采用这一写法） |
| 8 | 🔧 第 5 章没有讨论**手法的回滚与冲突**：多个手法叠加后，一次错误的 Extract 会连锁影响后续 | 回滚粒度如果只是「一个手法」，代价极大 | 采用「一个意图 = 一次提交」的粒度；重构提交与功能提交严格分家 |
