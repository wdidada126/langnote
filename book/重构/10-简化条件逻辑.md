# 第 10 章 简化条件逻辑

> **一句话**：条件表达式是「**把问题的答案写成了步骤**」——本章的工作不是把条件写短，而是把「如果……那么……」翻译成「**这个问题应当由谁来回答**」，最终让加一个分支只改一个地方。

---

## 本章地图

| 手法 | 解决什么问题 | 要点 | 代价 |
| --- | --- | --- | --- |
| **Replace Conditional with Polymorphism** 以多态取代条件表达式 | 重复的 switch、霰弹式修改 | 先用 Extract Class/Subclass/Interface 造出层次，再把分支搬进各自的实现 | 类/子类数量增长；层次本身要维护 |
| **Collapse Conditional Expression** 合并条件表达式 | 多个分支做同一件事 | 把多个分支合并成一个条件 | 条件变长 |
| **Consolidate Conditional Expression** 合并条件表达式（布尔结果） | 一串独立判断其实等价 | 提取为一个布尔含义 | 可能掩盖短路语义 |
| **Remove Duplicate Conditional Blocks** 移除重复的条件分支 | if 与 else 里两段几乎相同的代码 | 合并逻辑，重新命名 | 合并后要重新确认边界 |
| **Remove Control Flag** 移除控制标记 | `boolean done` 在循环里当开关 | 把循环体提炼成方法，用 return/continue 代替标志 | 需要先把循环体提炼出去 |
| **Replace Nested Conditional with Guard Clauses** 以卫语句取代嵌套条件 | 嵌套三元/嵌套 if 的缩进地狱 | 把「不正常」的分支先 return 掉，主干保持「正常路径」 | 卫语句多了以后函数入口一串提前返回 |
| **Introduce Null Object** 引入 Null 对象 | 到处 `if (x != null)`（2020 年代最被重视的坏味道之一） | 造一个「什么都不做」的实现，让调用点不再判空 | 需要为每个接口造实现；可能被误用成「万能空实现」 |
| **Introduce Assertion** 引入断言 | 关键前提没有被表达 | 用断言把「不可能发生」写出来 | 断言被关掉后问题会静默 |

**关键结论**：
- 条件表达式的重构**不是简化书写，而是转移责任**：把「如何分类」这件事交给合适的对象。
- 多态不是唯一解：当只有两三个分支、且类别不会增长时，`Guard Clauses` 或 `Early Return` 更合适——**不要为了「看起来 OO」而上多态**。
- `Introduce Null Object` 与 `Replace Conditional with Polymorphism` 常常配套：`Replace Type Code with Class` 之后，同一批 `null` 检查往往也该一并消失。

## 核心精讲

> 教学示意代码，不编译、不运行、不参与构建。

### 1. 重复的 switch ⟶ 多态（本章主手法）

```js
// 教学示意，不参与构建
// ❌ 同一个 switch 出现在四处；加一种运输方式要改四处（霰弹式修改）
function cost(kind, days) {
  switch (kind) { case "STD": return days * 1; case "EXP": return days * 2; }
}
function label(kind) {
  switch (kind) { case "STD": return "标准"; case "EXP": return "加急"; }
}
function refundable(kind) {
  switch (kind) { case "STD": return true;  case "EXP": return false; }
}
function eta(kind) {
  switch (kind) { case "STD": return 5;     case "EXP": return 2; }
}
```

```js
// 教学示意，不参与构建
// ✅ 一步到位：把「运输方式」做成一个会回答四件事的对象
const Shipping = {
  STD: { cost: (d) => d * 1, label: "标准", refundable: () => true,  eta: () => 5 },
  EXP: { cost: (d) => d * 2, label: "加急", refundable: () => false, eta: () => 2 },
};
function quote(kind, days) {
  const s = Shipping[kind];
  return { cost: s.cost(days), label: s.label, refundable: s.refundable(), eta: s.eta() };
}
// 新增「次日达」= 只加一个 key；另外三个函数一个字都不用改
```

**为什么多态「贵」但仍值得**：它引入了层次（类/子类/接口）。判断标准还是那句老话——**下一次改动的范围是否最小**。如果一种运输方式只在**一处**被用到，把它包成对象就是**夸夸其谈通用性**。

### 2. 卫语句 vs 嵌套条件：让主干保持「正常路径」

```java
// 教学示意，不参与构建
// ❌ 嵌套条件：缩进把主干淹没了，你得读完 if 才知道正常路径长什么样
public double price(Order o) {
    if (o != null) {
        if (!o.isExpired()) {
            if (o.getCustomer() != null) {
                if (o.getCustomer().isVip()) return o.getAmount() * 0.8;
                else return o.getAmount();
            } else {
                return o.getAmount();
            }
        } else {
            return 0;
        }
    } else {
        return 0;
    }
}
```

```java
// 教学示意，不参与构建
// ✅ 以卫语句取代嵌套条件：把「不正常」的先挡回去，主干只剩正常路径
public double price(Order o) {
    if (o == null)                 return 0;   // 卫语句
    if (o.isExpired())             return 0;
    if (!o.getCustomer().isVip())  return o.getAmount();
    return o.getAmount() * 0.8;
}
```

> 注意：这一步**没有**做任何「设计」。它只是先把「噪音」去掉，为后面的 `Replace Conditional with Polymorphism` 腾出空间。

### 3. Remove Control Flag：把「开关」换成「提前返回」

```js
// 教学示意，不参与构建
// ❌ 控制标记：done 在循环里当 goto 用，读起来要跟着标记走一遍
function findFirst(items, pred) {
  let done = false; let found = null;
  for (const it of items) {
    if (!done && pred(it)) { found = it; done = true; }
  }
  return found;
}

// ✅ 把循环体提炼出去，用 return 表达「结束」
function findFirst(items, pred) {
  for (const it of items) if (pred(it)) return it;
  return null;
}
```

### 4. Collapse / Consolidate：合并的两种不同含义

| 目标 | 例子 | 含义 |
| --- | --- | --- |
| **Collapse Conditional Expression** 合并条件表达式 | `if (a) return 1; if (b) return 1;` ⟶ `if (a \|\| b) return 1;` | 多个分支**做同一件事** |
| **Consolidate Conditional Expression** 合并条件表达式 | `if (a \|\| b \|\| c) { … }` ⟶ 提成一个 `isProblem()` 并命名 | 一串判断其实**表达同一个含义** |

```js
// 教学示意，不参与构建
// ❌ 三个条件其实是同一件事的两个侧面
if (order.amount > 10000 || order.customer.isVip() || order.coupons.length > 5) { escalate(); }

// ✅ Consolidate：把它们收成一个有名字的判断
function needsManualReview(order) {
  return order.amount > 10000 || order.customer.isVip() || order.coupons.length > 5;
}
if (needsManualReview(order)) escalate();
```

### 5. Introduce Null Object：消灭 `if (x != null)`

```java
// 教学示意，不参与构建
// ❌ 每一层都要判空；而且漏掉一处就是 NPE
String name = customer == null ? "" : customer.name();
int points = customer == null ? 0 : customer.points();
boolean vip = customer == null ? false : customer.isVip();

// ✅ 引入 Null 对象
interface Customer {
    String name(); int points(); boolean isVip();
}
class RealCustomer implements Customer { … }
class NullCustomer implements Customer {          // 「什么都不做」的那一支
    public String name()  { return ""; }
    public int points()   { return 0; }
    public boolean isVip(){ return false; }
}
// 调用点彻底干净：
String name   = customer.name();
int points    = customer.points();
boolean vip   = customer.isVip();
```

**适用边界**：
- ✅ 适用于「空」是一个**合法的业务语义**（未登录用户、无 Coupon、未设置地址）；
- ❌ 不适用于「空」是一个**错误**——那应该抛异常，用一个 NoOp 静默吞掉会让 bug 变得不可见。

### 6. Introduce Assertion：把「不可能」写下来

```java
// 教学示意，不参与构建
// 一个关键前提没被表达：这里假设金额一定非负
double total = items.stream().mapToDouble(Item::amount).sum();

// ✅ 用断言把前提固定下来（开发期开、生产可关）
assert items.stream().allMatch(i -> i.amount() >= 0);
double total = items.stream().mapToDouble(Item::amount).sum();
```

| 断言 vs 测试 | 差别 |
| --- | --- |
| 断言 | 在**当前执行路径**上即时检查，成本近零，能抓住「不该发生但发生了」 |
| 测试 | 在**特定场景下**检查，覆盖广但需要跑起来 |

## 版本演进

| 项 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 条件逻辑的重点 | 强调「用多态取代 switch」是 main 手法 | 同一主手法，并**明确列出 `Introduce Null Object` 与 `Introduce Assertion` 作为条件逻辑的收尾手法**（这两条在第 1 版里归属不清） |
| 示例语言 | Java，靠子类演示多态 | JavaScript，可用「策略对象表」直接表达多态分支 |
| 新增语境 | 主要为 OO 语境 | 明确补充**函数式语境**：把分支表变成「类型 → 处理函数」的映射 |

**2020 年代的重构工具与 AI 辅助**：

- **语言吸收了守卫分支**：`Optional`/`Either`、判别联合、模式匹配（Java 21 的 pattern matching for switch、C# 的模式匹配、Rust 的 `match`、TypeScript 的 discriminated union）让 `Replace Conditional with Polymorphism` 的**一半工作被语言提前做掉**。今天再看到大 `switch`，第一选择常常是**模式匹配 + 表达式**，而不是先建一堆子类。
- **Null Object 的现代化形态**：`Optional` 类型系统与 `Null Object` 模式并不冲突——前者在类型上强制你处理空，后者在运行时消除判空。2020 年代的推荐组合是：**类型系统区分「可空/不可空」+ 边界处转换为 Null Object**。
- **AI 辅助**：模型非常擅长「把嵌套 if 改成卫语句」，也擅长生成 Null Object 实现。但它**不会判断「这个空是业务语义还是错误」**——而这正是 `Introduce Null Object` 预条件里的核心判断。它还会顺手把「异常」吞成「静默的空实现」，这是需要重点审 diff 的地方。
- **局限**：`Remove Control Flag` 之后如果函数仍然长，说明**这个函数不只做一件事**，接下来该用 `Extract Method`；AI 常常停在这一步而不再往下拆。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」**——`Replace Conditional with Polymorphism` 是**最贵的手法之一**，需要建层次 + 改所有调用点 | 团队往往选择「加一个 switch 分支」而不是做多态 | 只在**同一批 switch 出现第三次**时才做（三次法则）；先把其中一个分支搬过去，其余逐步跟随 |
| 2 | 🔧 **并发代码的重构风险被低估**——把分支搬进对象时，如果分支里含有对共享可变状态的读改写，**搬移会改变原子性** | 测试全绿，但锁范围变了 | 并发相关分支先确认「这一支是不是在持有锁的状态下执行」；重构后跑并发测试 |
| 3 | 🔧 **不谈跨服务与数据迁移的重构**——`重复的 switch` 在分布式系统里常常是「按租户/渠道分派」，改动涉及多个服务的路由规则与配置下发 | 一次路由改动可能影响多个团队的上线节奏 | 把分支外置为配置/策略服务，先做到「配置可热更新」，再做代码层面的多态化 |
| 4 | 🔧 **AI 生成代码带来的新债**——模型倾向于把每个 `null` 检查都变成「静默的空实现」（假 Null Object），把每个异常都 catch 掉 | AI 输出里大量「看起来整洁、实则掩盖错误」的分支 | 审查 diff 时专门看「catch 块是否为空」「Null Object 是否吞掉了错误」；给两类模式加静态检查 |
| 5 | 🔧 `Introduce Null Object` 被当成「消灭 null 的银弹」，但**「空」到底是业务语义还是错误**，书里只给了一句判断 | 用错方向会让 bug 从「立刻崩溃」变成「悄悄算错」 | 定义清楚：可空字段用 Null Object；非法状态用异常；二者不要混用 |
| 6 | 🔧 第 2 版写于 2019 年，`模式匹配`尚未普及；今天再读本章，会低估**语言能力对这一章的替代作用** | Java 21 的模式匹配、Rust 的 match、TS 的判别联合都已成熟 | 遇到 `switch`：先看语言是否支持**模式匹配 + 穷尽性检查**；支持的话优先用语言，而不是先建子类 |
| 7 | 🔧 「Replace Nested Conditional with Guard Clauses」被当成「总是更优」，但**卫语句过多会让函数的入口变成一堵墙** | 一个函数的正常路径被挤到函数体最后 | 卫语句超过 3 条时，考虑先把前置校验拆成独立的小函数，或把整个函数改写成多态 |
| 8 | 🔧 本章默认被重构的代码是**顺序执行**的；一旦分支里存在回调、延迟执行或异步，多态化会显著改变**执行时机** | 异步/响应式代码里「提前 return」不再等价 | 异步分支不要盲目套用卫语句；先看能否把回调改成返回值 |
