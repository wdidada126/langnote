# 第 8 章 搬移特性

> **一句话**：绝大多数坏味道的根都是同一句台词——**「这段代码的职责放错了地方」**；搬移特性（Move Method / Move Field / Extract Class / Inline Class）就是全书的主手术刀，负责把职责放回它该待的对象。

---

## 本章地图

| 手法 | 解决什么问题（对应坏味道） | 步骤要点 | 代价 |
| --- | --- | --- | --- |
| **Move Method** 搬移函数 | 依恋情结、霰弹式修改 | 提炼出要移的部分 → 目标类建同名方法 → 一面移动一面改名字 → 旧类留委托 → 逐步删除委托 | 接口一旦公开，改动会外溢；要处理双向依赖 |
| **Move Field** 搬移字段 | 霰弹式修改、内幕交易 | 处理读写方 → 目标类建字段 → 改访问方式 → 删旧字段 | 公开字段外移会破坏封装，需先 `Encapsulate Field` |
| **Extract Class** 提炼类 | 过大的类、发散式变化 | 决定「哪个部分属于新类」→ 建新类并把字段/方法搬过去 → 旧类留引用 → 逐步消除转发 | 类数量增加；可能出现循环依赖 |
| **Inline Class** 内联类 | 冗赘的元素 | 把被内联类的内容搬进使用方 → 删掉它 | 一次性大改动；如果不是真死代码，等于把复杂度藏起来 |
| **Extract Subclass** 提炼子类 | 一个用法分支塞在同一类里 | 抽出子类承载该分支 → 用工厂方法决定实例化 | 子类数量膨胀 |
| **Extract Interface** 提炼接口 | 需要「可替换」但无公共父类 | 建接口 → 至少让一个类实现 → 客户改为依赖接口 | 接口加方法要改所有实现；可能变成过度抽象 |
| **Collapse Hierarchy** 折叠继承体系 | 继承层次只剩一层或空壳 | 把内容搬回父类 → 删除子类 | 多态扩展点被封死 |
| **Push Down / Pull Up** 上移下移方法/字段 | 重复代码（上移）/ 基类不相关（下移） | 逐条搬 | 上移会让基类变胖；下移会让基类变空 |
| **Replace Inheritance with Delegation** 用委托取代继承 | 被拒绝的遗赠 | 建委托字段 → 写一个转发方法 → 逐个替换 → 删掉继承 | 多一层转发；每次调用多一跳 |
| **Replace Delegation with Inheritance** 用继承取代委托 | 委托写得太厚 | 把委托字段提升为父类 → 删掉转发方法 | 把不必要的耦合带进来 |

**关键结论**：
- 「搬移到哪」的判断依据是**变化的动机**：一组东西总是**因为同一个原因**变化时，就该待在一起。
- 搬移的**顺序**：先 Rename（让名字诚实）→ 再 Encapsulate（别连私有一起搬走）→ 再 Move → 最后 Remove Middle Man（没人需要穿透时撤掉转发）。
- **先内聚、后解耦**：Extract Class 之前先 Extract Method，否则搬的只是一团更大的泥。

## 核心精讲

> 教学示意代码，不编译、不运行、不参与构建。

### 1. Move Method：辨认「依恋情结」的口诀

> **这个函数最常提到哪个类的名字？** 如果答案不是它所在的类，它就想搬走。

```java
// 教学示意，不参与构建
// ❌ 这个函数几乎只关心 Extra，却挂在 Order 上
class Order {
    double total() {
        double sum = 0;
        for (LineItem item : items) {
            if (item.extra().isTaxable()) sum += item.amount() + item.extra().taxRate() * item.amount();
            else                          sum += item.amount();
        }
        return sum;
    }
}
```

```java
// 教学示意，不参与构建
// ✅ Move Method：分成两步，先搬「算税」这偏心的一部分
class Extra {
    double taxOn(double amount) { return this.taxRate() * amount; }
    boolean isTaxable() { /* … */ }
}

class Order {
    double total() {
        double sum = 0;
        for (LineItem item : items) sum += item.isTaxable() ? item.amount() + item.extra().taxOn(item.amount())
                                                             : item.amount();
        return sum;
    }
}
```

**Move Method 的四个阶段**（书中顺序）：
1. 决定**搬什么、留在哪**：只有部分代码该走时先提炼出一个新方法；
2. 目标类**建一个同名方法**，把实现贴过去；
3. 在目标类里**改名字**让它符合当地语境（这是最容易被跳过的一步！）；
4. 旧类**留一个委托方法**；等到没人再需要旧接口时，删掉委托类本身（如果有）。

### 2. Extract Class：把「一大块职责」切出来

```js
// 教学示意，不参与构建
// ❌ 过大的类：订单的「价格计算」和「订单自身的字段」混在一起
class Order {
  constructor(customer, lines) { this.customer = customer; this.lines = lines; }
  // 下面这五个方法其实都是「算钱」，与订单本身无关
  subtotal() { return this.lines.reduce((s, l) => s + l.qty * l.price, 0); }
  tax()      { return this.subtotal() * this.customer.taxRate(); }
  shipping() { return this.lines.some(l => l.weight > 20) ? 30 : 5; }
  total()    { return this.subtotal() + this.tax() + this.shipping(); }
  refundRate(){ return this.customer.isVip() ? 0.9 : 0.8; }
}

// ✅ 把「钱」这块整体搬进 Pricing 对象
class Pricing {
  constructor(customer) { this.customer = customer; }
  subtotal(lines) { return lines.reduce((s, l) => s + l.qty * l.price, 0); }
  tax(lines)      { return this.subtotal(lines) * this.customer.taxRate(); }
  shipping(lines) { return lines.some(l => l.weight > 20) ? 30 : 5; }
  total(lines)    { return this.subtotal(lines) + this.tax(lines) + this.shipping(lines); }
}
class Order {
  constructor(customer, lines) { this.customer = customer; this.lines = lines;
                                 this.pricing = new Pricing(customer); }
  get total() { return this.pricing.total(this.lines); }   // 只留必要的转发
}
```

**判断「什么该属于新类」的三个问题**：
1. 这些字段/方法能不能**用一个名字概括**？（能 → 这就是一个类）
2. 它们的变化原因和原来的类**一样吗**？（不一样 → 该分家）
3. 把它们搬走之后，原来的类是不是**更清楚了**？（是 → 做）

### 3. Inline Class：反向操作同样重要

```js
// 教学示意，不参与构建
// ❌ 冗赘的元素：MoneyUtil 只被用过一次，还把类型名带到了各处
const price = MoneyUtil.cents(1200).toYuan();

// ✅ 内联后：调用点直接表达意图
const price = 12.0;
// 或者（如果这段逻辑确实有复用价值）→ 那说明该 Extract 的不该这么小
```

> **Inner Class / Inline Class 的反向用法**：当「被内联类」的内容只有一两行时，别建类；把代码搬回去，删掉它。这一步常被忽略，却直接决定了代码库里**类数量是否会失控**。

### 4. Replace Inheritance with Delegation：继承不是免费的

```java
// 教学示意，不参与构建
// ❌ 被拒绝的遗赠：继承了一堆用不上的方法，还被它们的语义绑住
class Car extends Vehicle {
    void fly() { }            // 用不上，却是 public 的一部分
    void sail() { }           // 同上
}
```

```java
// 教学示意，不参与构建
// ✅ 用委托取代继承：只暴露我需要的那部分接口
class Car {
    private final Vehicle delegate = new Vehicle();
    public void start()   { delegate.start(); }
    public void stop()    { delegate.stop(); }
    // fly()/sail() 不见了 —— 外部根本不该知道它们的存在
}
```

**何时该反方向（Replace Delegation with Inheritance）**：当转发方法多到**委托本身就变成了类的全部语义**时，继承反而更清楚。判断标准：**「这个类是不是就是那个东西的另一种形态？」**（Car 就是 Vehicle 的一种 ⟶ 继承；Car 只是「会跑的 Vehicle 记录」⟶ 委托）。

### 5. 搬移顺序总览（组合拳）

```text
发现「这段代码的职责放错了地方」
   ↓
1) Rename Method / Variable      —— 先用名字确认「这是什么」
   ↓
2) Encapsulate Field             —— 别把私有数据连锅端（否则要写一堆访问方法）
   ↓
3) Extract Method                —— 先内聚，别搬一整团泥
   ↓
4) Move Method / Move Field      —— 真正的主手术刀
   ↓
5) Extract Class / Inline Class  —— 重新划定边界
   ↓
6) Remove Middle Man             —— 等没人再需要穿透时，撤掉转发层
```

## 版本演进

| 项 | 第 1 版（1999） | 第 2 版（2019） |
| --- | --- | --- |
| 示例语言 | Java，且示例多为「有类」的设计 | JavaScript，演示**无类环境下如何搬移**：用闭包、模块与对象字面量承载搬移后的职责 |
| 手法名称 | 第 1 版用 Pull Up/Down、Inline Class 等 | 第 2 版把手法定名为 **Move Method / Move Field / Extract Class / Inline Class** 等更直白的名字，并归入「搬移特性」组 |
| 继承相关的侧重 | 更强调继承层次的重构 | 第 2 版更强调**委托优先**（`Replace Inheritance with Delegation` 出现在讨论中），与 2010 年代「组合优于继承」的社区共识一致 |

**2020 年代的重构工具与 AI 辅助**：

- **IntelliJ/Eclipse 的 Move 支持**：Move Method / Move Class / Pull Members Up 都是成熟的重构动作，并带冲突检测；但对**跨语言边界**（方法体里调用了别的文件里的东西）与**动态类型**（JS/Python 的调用点靠运行时才知道）无能为力。
- **Roslyn 与 TypeScript 编译器**：TypeScript 的**结构类型（structural typing）**让 `Extract Interface` 在 JS 世界里变得异常便宜——你不需要显式 `implements`，只要形状对得上就成了。这是 2020 年代「接口被语言吸收」的典型例子。
- **AI 辅助**：`Extract Class` 是 AI 最容易「过度执行」的手法——它会一次把五个方法搬进新类，并给你 30 个需要改的调用点。纪律仍然是：**一次一个意图、一次一次提交**。
- **现代化建议**：`Replace Inheritance with Delegation` 在类型系统更强的语言（Rust、Go）里几乎变成默认选择——它们根本没有传统的类继承，用 trait/接口来替代。这也意味着第 2 版里「处理继承关系」那一章的经验，今天要按语言重新校准。

## 常见误区与本书需修正之处

| # | 误区 / 需修正处 | 现实约束 | 应对 |
| --- | --- | --- | --- |
| 1 | 🔧 **「重构在很多团队里没有时间」**——搬移特性是全书最贵的手法（改动量最大、接口外溢最广），也最容易在排期里被砍 | 一次 Move 往往牵动十几个调用点 | 先把接口收敛（加一层窄接口），再搬实现；或先在内部做 Extract，等接口稳定后再 Move |
| 2 | 🔧 **并发代码的重构风险被低估**——Move Method 在并发模块上会改变**锁的持有范围**；Move Field 可能把一个被多线程共享的字段带进新的同步域 | 搬移后测试仍绿，但并发语义已变 | 搬移前先梳理锁与可见性；搬移后跑并发测试与 sanitizer（参考 `book/C++并发编程实战2/`） |
| 3 | 🔧 **不谈跨服务与数据迁移的重构**——这章讲的全部是「一个类 ⟶ 一个类」；真实场景里是「一个类 ⟶ 一个服务」，成本从一次提交变成一次跨团队发布 | 跨服务搬移需要契约、双写、数据迁移、回滚方案 | 用绞杀者模式逐步迁移；数据库 schema 的改动不在本书范围（见 `book/微服务架构设计模式.md`） |
| 4 | 🔧 **AI 生成代码带来的新债**——`Extract Class` 是 AI 最爱做的动作，它会「顺手」把 8 个方法搬进新类，并一次性改 40 个调用点 | 大 diff 无法人工审全；回归定位困难 | 一个手法一次提交；用 `git bisect` 定位；对 AI 产出的搬移要求「调用点改动清单」先列后改 |
| 5 | 🔧 第 8 章默认「跨类的搬移都是在同一个编译单元内」；在模块化/无模块的语言里，**「文件位置」本身就是耦合**，搬一次代码要动一堆 import 与路径 | 文件移动带来的机械成本被低估 | 先做模块边界的梳理（Export 面），再搬实现；搬完立刻跑一次「未使用 import」检查 |
| 6 | 🔧 `Extract Interface` 在动态类型语言里与静态类型语言里意义不同：JS 里「结构相同就算实现」，容易造出「什么都符合的空接口」 | 缺乏 `implements` 约束时，接口的约束力变弱 | 在 JS 里用类型定义（schema/类型声明）替代接口；接口只在**真的需要多态替换**时才提炼 |
| 7 | 🔧 「Replace Inheritance with Delegation」被推荐为更安全的替代，但**委托的转发方法会永久锁死继承的可能性**——这个反向代价书里提得不够 | 一旦都用委托，将来想换回继承要重写 | 转发方法保持极薄（一行）；为将来的扩展预留接口而非预留继承 |
| 8 | 🔧 搬移后**没有回头清理**：旧类里还留着委托方法、旧字段还挂着 setter，让代码库同时存在两条路径 | 双路径是最常见的「重构后遗症」 | 搬移计划里显式包含「删除旧路径」这一步——**重构不是搬家，是搬家后拆掉老房子** |
