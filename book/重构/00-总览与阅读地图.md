# 《重构（第 2 版）》总览与阅读地图

> **一句话**：重构不是「有空的时候整理代码」，而是**在不改变可观察行为的前提下、用一系列被命名的小步骤改变结构**——命名的价值在于让「改结构」变成一次可以和业务提需求等价讨论、可以自动化测试、可以 code review 的工程活动。

## 3. 全部重构手法的分类总表

> 说明：第 2 版把手法定为六组（外加第 6 章的「第一组重构」短名录）。下表覆盖用户点名与书中主要手法，**末列给出该手法所在的章**。每条都注明「解决什么问题」与「代价/副作用」。

### 3.1 重新组织函数 Composing Methods（第 6 章之前的表现，名录归入「重新组织函数」组）

| 手法 | 解决什么问题 | 代价 / 副作用 | 章 |
| --- | --- | --- | --- |
| **Inline Method** 内联函数 | 函数太薄（只有一层转发），调用比函数体还难读 | 内联过度会让长函数变长；一次性内联大段代码，diff 会失去语义 | 手法主体章 |
| **Extract Method** 提炼函数 | 过长函数、语义被实现淹没；「这段代码在做什么」需要读三行才懂 | 参数/返回值传递让接口变脏；过度提炼产生大量一次性函数 | 全目录通用 |
| **Extract Variable** 提炼变量 | 表达式里的魔法数字/复杂子表达式没有名字 | 多一个局部变量即多一处可变状态，调试要跟随 | 全目录通用 |
| **Inline Variable** 内联变量 | 变量只被用过一次，名字反而制造了间接层 | 内联后长表达式更难逐段读 | 全目录通用 |
| **Replace Temp with Query** 以查询取代临时变量 | 临时变量把「算什么」和「什么时候算」耦合在一起，阻碍后续提炼 | 反复求值可能带来性能或副作用；纯函数才是安全的 | 全目录通用 |
| **Split Temporary Variable** 剖分临时变量 | 同一个临时变量被复用成多种含义（e1、e2、e3 都用 `temp`） | 变量多了以后函数变长 | 全目录通用 |
| **Remove Assignments to Parameters** 移除对参数的赋值 | 参数语义被改写，读者无法从签名判断「入参会不会被改」 | 有时仍需返回一个值，得改用 Extract + Return | 全目录通用 |
| **Replace Method with Method Object** 以函数对象取代函数 | 函数用了太多临时变量，**提炼不下去**时把它们变成对象的字段 | 引入新类与字段样板；类本身可能又变成「过长类」 | 手法主体章 |
| **Substitute Algorithm** 替换算法 | 算法本身过时/低效/难懂，但要**保留原行为** | 新旧算法必须「行为等价」，测试不足时风险极大 | 手法主体章 |

### 3.2 在对象之间搬移特性 Moving Features between Objects

| 手法 | 解决什么问题 | 代价 / 副作用 | 章 |
| --- | --- | --- | --- |
| **Move Method** 搬移函数 | 函数与它操作的数据不在一处（依恋情结）；函数总被另一边的类调用 | 需要同时改两处的引用；接口一旦公开，改动会外溢 | Ch8 |
| **Move Field** 搬移字段 | 字段被另一个类读写得更多（霰弹式修改） | 需处理双向依赖与封装；公开字段外移会破坏封装 | Ch8 |
| **Extract Class** 提炼类 | 类做了太多事（过大类），或某个字段/方法天然属于另一概念 | 类数量增加；两个类之间要重新划分接口，可能出现「循环依赖」 | Ch8 |
| **Inline Class** 内联类 | 类几乎没干什么，只是把上一层加了一层壳 | 大量调用点要改；如果不是真死代码，等于把复杂度藏起来 | Ch8 |
| **Extract Subclass** 提炼子类 | 一个类里有一批方法只被少数场景使用 | 子类数量膨胀；用错了会掉进「继承滥用」 | Ch8 / Ch12 |
| **Extract Interface** 提炼接口 | 两个类并不共享继承树，却需要「可替换」 | 接口加方法要改所有实现；过度抽象变成「夸夸其谈通用性」 | Ch8 / Ch12 |
| **Collapse Hierarchy** 折叠继承体系 | 继承层次只剩一层、甚至子类只是空壳 | 多态分派没了，有些扩展点被封死 | Ch8 / Ch12 |
| **Push Down Method / Push Down Field** 下移方法/字段 | 基类里的方法只被一个子类用到 | 移动后基类变「空」，后续可能被折叠 | Ch12 |
| **Pull Up Method / Pull Up Field** 上移方法/字段 | 子类里有重复实现（重复代码） | 上移会让基类变胖、依赖被上提（返回值若进基类会造成「内幕交易」） | Ch12 |
| **Replace Inheritance with Delegation** 用委托取代继承 | 继承带来了不需要的接口与耦合（被拒绝的遗赠） | 委托层多写转发方法；每次调用多一跳 | Ch12 |
| **Replace Delegation with Inheritance** 用继承取代委托 | 委托写太多了，继承反而更简单 | 会把不必要的耦合带进来 | Ch12 |
| **Replace Subclass with Strategy** 以策略取代子类 | 用继承写算法变体，只想换实现不想继承 | 需要Extract Interface配套；策略对象状态管理更复杂 | Ch12 |

### 3.3 重新组织数据 Organizing Data

| 手法 | 解决什么问题 | 代价 / 副作用 | 章 |
| --- | --- | --- | --- |
| **Rename Field / Rename Variable** 重命名字段/变量 | 神秘命名：名字与语义不符（成本最低、收益最高的手法） | 名字一改，所有引用点全改；跨语言/跨库命名要统一 | Ch7 / Ch9 |
| **Replace Data Value with Object** 以对象取代数据值 | 一个「简单值」上挂了税/折扣/货币单位等行为（基本类型偏执、数据泥团） | 需要构造、比较、序列化支持；值语义与引用语义要区分 | Ch7 / Ch9 |
| **Replace Array with Object** 以对象取代数组 | 数组下标即含义（`data[0]`、`data[3]`），毫无可读性 | 索引访问点全部改写；某些性能敏感场景会掉一点 | Ch9 |
| **Encapsulate Field** 封装字段 | 字段被外部直接读写，约束无处安放 | 多出一堆 getter/setter 样板；Java 侧要小心「纯数据类」变成贫血对象 | Ch7 / Ch9 |
| **Encapsulate Collection** 封装集合 | 集合被外部就地增删，聚合根失效 | 增删要提供专用方法，接口变宽 | Ch7 |
| **Replace Type Code with Class** 以类取代类型码 | 用 `int`/`string` 表示类别，非法值无保障 | 需要重写分支；与序列化/ORM 映射要对齐 | Ch9 |
| **Replace Type Code with Subclasses** 以子类取代类型码 | 类型码的分支各自有不同行为 | 子类数量随类别增长 | Ch9 / Ch12 |
| **Replace Type Code with State/Strategy** 以状态/策略取代类型码 | 类型码行为随状态迁移（订单状态机等） | 状态迁移的合法性需要额外约束 | Ch9 |
| **Replace Subclass with Fields** 以字段取代子类 | 子类只是常量不同（子类里只有字段） | 丢掉子类后需要工厂方法保证实例化正确 | Ch9 |
| **Change Value to Reference** 将值对象改为引用对象 | 需要「同一对象共享/可比较/有生命周期」语义 | 共享带来别名问题；并发下要加锁 | Ch9 |
| **Change Reference to Value** 将引用对象改为值对象 | 需要可缓存、可比较、可安全分发的语义（如 Money、日期区间） | 需要实现相等性/不可变；不可变会抬高对象分配 | Ch6 / Ch9 |
| **Make Data Immutable** 让数据不可变 | 可变数据造成的时序 bug（并发与回调时代尤其突出） | 每次「修改」都要造新对象；年轻代 GC 压力上升 | 名录「大型重构」组 |

### 3.4 简化条件逻辑 Simplifying Conditional Expressions

| 手法 | 解决什么问题 | 代价 / 副作用 | 章 |
| --- | --- | --- | --- |
| **Replace Conditional with Polymorphism** 以多态取代条件表达式 | 同一群 if/switch 对不同「类型」重复出现（重复 switch） | 需要 Extract Class/Subclass/Interface 先造出层次；层次本身要维护 | Ch10 |
| **Collapse Conditional Expression** 合并条件表达式 | 多个条件分支做同一件事（`if (a) return 1; if (b) return 1;`） | 合并后条件变长 | Ch10 |
| **Consolidate Conditional Expression** 合并条件表达式（取布尔结果） | 一串独立判断其实等价，产生了重复判断 | 有时反而掩盖了「短路」语义 | Ch10 |
| **Remove Duplicate Conditional Blocks** 移除重复的条件分支 | if 与 else 里两段几乎相同的代码 | 合并逻辑后分支含义要重新命名 | Ch10 |
| **Remove Control Flag** 移除控制标记 | `boolean done` 在循环/长条件里当开关，读起来像 goto | 需要把循环体提炼成方法才好删 | Ch10 |
| **Replace Nested Conditional with Guard Clauses** 以卫语句取代嵌套条件 | 嵌套三元/嵌套 if 的「缩进地狱」 | 卫语句多了以后函数入口会有一串提前 return | Ch10 |
| **Introduce Null Object** 引入 Null 对象 | 到处 `if (x != null)` 的空值判空污染（2020 年代最被重视的坏味道之一） | 需要为每个接口造一个「什么都不做」的实现；可能被误用成「万能空实现」 | Ch10 |
| **Introduce Assertion** 引入断言 | 关键前提没被表达，代码靠「约定」运行 | 断言被关掉后问题会静默；断言替代不了测试 | Ch10 |
| **Remove Double Negative** 移除非逻辑（如 `if (!(a == b))`） | 双重否定让条件变得难读 | 语义边界要确认（严格相等 vs 类型转换） | Ch6 |
| **Replace Boolean with Class** 以类取代布尔值 | `boolean isXxx` 上还要再加属性/行为（如「是否过期 + 剩余天数」） | 多一个类；布尔字段名改了调用点全改 | Ch6 |
| **Remove Flag Argument** 移除标记参数 | `foo(true)` 这种布尔开关参数 | 要么拆成两个函数，要么传入真策略对象 | Ch6 |

### 3.5 简化调用 / 重构 API Making Method Calls Simpler / Refactoring APIs

| 手法 | 解决什么问题 | 代价 / 副作用 | 章 |
| --- | --- | --- | --- |
| **Hide Delegate** 隐藏委托关系 | 客户一路 `a.getB().getC()` 地穿进内部结构（过长的消息链） | 多一层转发方法；外部一旦依赖转发层就被锁死 | Ch11 |
| **Remove Middle Man** 移除中间人 | 中间人只是转发，没有加任何价值（冗赘元素） | 又要改回消息链 | Ch11 |
| **Introduce Parameter Object** 引入参数对象 | 参数列长得离谱，且常常要「一起增删」（数据泥团） | 参数对象会变成上帝对象；只有 3 个以内参数别用 | Ch11 |
| **Remove Parameter** 移除参数 | 参数没被用到（重构 API 后遗留的死参数） | 某些调用方其实需要它，删早了要补回 | Ch11 |
| **Rename Method** 重命名函数 | 函数名与语义不符（神秘命名） | 所有调用点全改；这是唯一「无法用测试兜底」的手法 | Ch11 |
| **Remove Setter** 移除设值函数 | 对外暴露的 setter 破坏了不变性/约束 | 需要工厂方法或构造参数补上初始化路径 | Ch11 |
| **Hide Method** 隐藏方法 | 方法本不该被外部看到，却因继承/实现被迫 public | 子类重构时要改可见性，可能牵动接口 | Ch11 |
| **Replace Constructor with Factory Method** 以工厂方法取代构造函数 | 构造函数名字无法表达意图（多个构造函数同名）；要返回子类/缓存实例 | 工厂类本身成了新耦合点；静态工厂难 mock | Ch6 / Ch11 |
| **Replace Error Notification with Exception** 以异常取代错误通知 | 用返回值/状态位报错，调用方经常忘了检查 | 异常会跨越模块边界；滥用异常吞掉控制流 | Ch6 / Ch11 |
| **Replace Exception with Error Notification** 以错误通知取代异常 | 异常被当成正常控制流（异常驱动的分支） | 调用方要主动判状态，容易漏检查 | Ch6 / Ch11 |
| **Remove Redirect** 移除转发的重复代码 | `getA().getB().doWork()` 里的手工转发样板 | 直接暴露内部结构 | Ch6 |
| **Duplicate Observed Data** 复制「被观察的数据」 | 领域数据在一处、UI 缓存一份，两边不同步（数据泥团/重复数据） | 需要观察者或响应式流来同步，增加复杂度 | Ch6 |

### 3.6 处理继承关系 / 大型重构（散见于第 12 章与名录）

| 手法 | 解决什么问题 | 代价 / 副作用 | 章 |
| --- | --- | --- | --- |
| **Extract Superclass** 提炼超类 | 两个类有大量重复实现（重复代码） | 超类可能变成「垃圾抽屉」 | Ch12 |
| **Form Special Case** 形成特殊Case | 在函数里写 `if (obj == special)` 的特例分支 | 特例类会被无限扩展 | 名录「大型重构」组 |
| **Teach/Test Driven** 「教」测试驱动（大型重构的第一原则） | 面对没有测试的老系统，先补测试再动刀 | 测试写得不对，后面全白干 | Ch4 / Ch12 |
| **Introduce Null Object** 见 3.4 | 空值分支泛滥 | 见 3.4 | Ch10 |
| **Make Data Immutable** 见 3.3 | 可变数据带来的时序缺陷 | 见 3.3 | 名录「大型重构」组 |
| **Replace Subclass with Strategy** 见 3.2 | 只想要算法可变，不想背继承包袱 | 见 3.2 | Ch12 |
| **Substitute Algorithm** 见 3.1 | 换掉整个算法 | 见 3.1 | 手法主体章 |

### 3.7 记忆锚点

- **一个坏味道 ⇔ 一族候选手法**：书里每一条坏味道后面都跟着「首选手法 + 备选手法」，这是本书最实用的部分；见 `03-代码的坏味道.md` 的对照表。
- **手法不是配方**：每步变换都有**预条件**；条件不满足就硬做，等于把 bug 藏进 diff。
- **组合拳**：单招几乎无用。Move Method 之前往往要先 Rename，Extract Class 之前往往要先 Encapsulate Field。
- **门槛**：Extract Method / Rename 需要测试；Move Field / Replace Inheritance with Delegation 需要类型系统或测试双保险；Replace Constructor with Factory Method 几乎必须靠测试。

## 4. 版本演进时间轴（1999 ⟶ 2026）

| 年份 | 事件 | 对「重构」这个 practice 的影响 |
| --- | --- | --- |
| 1984 | Brodie，《Thinking Forth》提到 factoring：「把代码组织成有用的片段」 | 重构的远祖（概念在软件工程出现前就存在） |
| 1990 | Bill Opdyke 与 Ralph Johnson 的 SIGPLAN 论文《Refactoring: An aid in designing application frameworks and evolving object-oriented systems》 | **refactoring 一词正式诞生** |
| 1992 | Opdyke 博士论文《Refactoring Object-Oriented Frameworks》 | 第一份系统的重构条目清单 |
| 1997 | Roberts、Brant、Johnson，《A Refactoring Tool for Smalltalk》（TOOLS） | 第一个真正可用的**自动化**重构工具（Smalltalk） |
| **1999** | **Fowler《Refactoring》第 1 版**（Kent Beck 序），示例用 **Java**，约 70+ 手法 | refactoring 从高手圈层词汇变成普通开发者的日常动词；第 1 版中译本后于 2015-08 由人民邮电出版（ISBN 978-7-115-36909-3） |
| 2001 | Fowler 提出重构「**跨过卢比孔河**」（crosses the Rubicon） | 指 Java IDE（IntelliJ/Eclipse/JBuilder）自动化重构普及，重构不再是纯手工活 |
| 2002 | Kent Beck，《**Test-Driven Development by Example**》 | 把「重构」放进 TDD 的**绿 → 重构**循环，定义了重构在迭代中的位置 |
| 2007 | Gerard Meszaros，《**XUnit Test Patterns: Refactoring Test Code**》 | 给「重构测试」本身建立了词汇（Test Double、Birthdater、Logic-in-Tests 等） |
| 2012 | Cousot、Cousot、Logozzo、Barnett，OOPSLA《An abstract interpretation framework for refactoring with application to extract methods with contracts》 | 用**抽象解释**自动推断 Extract Method 的前后置条件（在 Roslyn 上实现） |
| 2014–2018 | Java 8 lambda、Kotlin/Swift/TypeScript 流行；静态类型与推断变强 | 「用类型系统吃掉一批重构」：Rust 的所有权、TypeScript 的结构类型让 Move/Extract 更安全 |
| **2018–2019** | **《Refactoring》第 2 版**：示例 **Java ⟶ JavaScript**，新增函数式重构示例，手法名录重组为更内聚的 6 组（中文版 2019-05，ISBN 978-7-115-50865-2） | 明确表态：**重构不与面向对象绑定**，无类语言同样能重构；「面向函数」的重构路径被写进正本 |
| 2019–2022 | OpenRewrite（自动化大规模重构，从 Java 迁移到框架升级）、Roslyn 的分析能力 | 重构从「IDE 里点一下」走向「**跨仓库、跨依赖版本**」的批量自动化 |
| 2023–2026 | **AI 辅助重构**成为主流：大模型能一次做较大的 Extract / Rename / 解释旧代码，但**行为等价性由谁保证**成为新的核心问题 | 重构的对象从「人类写的烂代码」扩散到「AI 写的冗余代码」；「小步 + 测试」的纪律反而更重要（见 `各章「常见误区」小节`） |

> 一句话概括版本演进：**1999 解决「敢不敢改」，2002 解决「在什么时候改」，2019 解决「不用面向对象也能改」，2020 年代正在解决「AI 改了怎么办」。**

## 8. 阅读顺序与写作约定

### 8.1 阅读顺序

1. `01` 先跟着完整走一遍真实案例——建立「重构长什么样」的直觉；
2. `02` 建立**两顶帽子**的纪律；
3. `03` 学会找目标（坏味道 ⇒ 手法）；
4. `04` **务必先读**——没有测试就没资格谈重构；
5. `05`–`12` 按需查表：把 `03` 的坏味道当作索引，直接跳到对应手法章。

> **最小路径（1 天）**：`01` ⟶ `02` ⟶ `03` ⟶ `04`。
> **要做真实重构时**：`03` 找位置 ⟶ `06`–`12` 查手法 ⟶ 回 `04` 补测试。

### 8.2 本目录的写作约定

每个章节文件固定为七段结构：

1. `# 第 N 章 标题` ⟶ `> **一句话**：...`
2. `## 本章地图`（表格：节 | 内容 | 结论）
3. `## 核心精讲`（含 ```js / ```java **教学示意代码**，**不编译、不运行、不参与构建**）
4. `## 版本演进`（第 1 版 1999 的 C++/Java 示例 ⟶ 第 2 版 2019 的 JavaScript/Java、重构工具与 AI 辅助）
5. `## 经典论文与原始文献`（表格，条目均真实可查；不写编造的编号）
