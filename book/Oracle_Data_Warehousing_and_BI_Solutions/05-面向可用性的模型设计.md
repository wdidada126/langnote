## 5.1 设计方法（p.94）

### 5.1.1 关键设计考量（p.94）

- ⚠️ 编者归纳（据目录 p.94–98 的篇幅）：关键考量清单——查询用户的**心智词汇**（业务术语
  直接可映射到列名）、响应时间预期、可理解性（用户敢自己拖拽的 schema 才是好 schema）、
  汇总层级（明细/周/月/年各留哪几层）、历史深度与聚合策略。
- 「可用性驱动设计」的判据（⚠️ 转述）：如果分析用户需要培训两小时才能拼出一个正确查询，
  设计失败——这条判据把 Kimball 式「宽表+一致维度」与 Inmon 式「规范化中枢」拉回同一张
  评分表上，不预设门派（→ 5.2 四选一会谈两派，分别见
  [../数据仓库工具箱.md](../数据仓库工具箱.md)（Kimball）与 [../Building_the_Data_Warehouse/00-总览与阅读地图.md](../Building_the_Data_Warehouse/00-总览与阅读地图.md)（Inmon））。

### 5.1.2 为性能而设计（p.98）

- ⚠️ 转述（现行 19c 口径，✅ https://docs.oracle.com/en/database/oracle/oracle-database/19/dwhsg/database-data-warehousing-guide.pdf ）：
  目录给本节 8 页（✅ p.98–106），按指南主题可对位为——
  1. **物化视图与查询重写**（基本 MV / 高级 MV / PCT 刷新）：把重复聚合变成数据库维护的缓存；
  2. **星型转换与一致性维度**（star transformation）：优化器把星型查询自动改写到汇总表；
  3. **位图/位图连接索引**：低基数维列与「事实按维过滤」的索引答案；
  4. **分区**：装载窗口 + 裁剪；5. **并行**：DOP 规划。
- 🔧 三组本机算术（**非 Oracle 行为**，00 §9）：
  - E1b/c：5M 行星型查询 **13.3ms** → 改打「月×品类」预聚合表（6000 行，建 66ms）后
    **1.27ms**——**一个数量级**的差距就是「汇总管理」的全部动机；
  - E7：1M 行、5 个取值的低基数列上 B 树索引**帮倒忙**（77.3ms → 85.9ms，不降反升），
    而高基数主键等值 0.070ms——本机没有位图索引，这正是「低基数列需要位图」的**反证演示**
    （机理纵深在 [../Cost_Based_Oracle_Fundamentals/08-位图索引.md](../Cost_Based_Oracle_Fundamentals/08-位图索引.md)）；
  - E3：SQLite 汇总表+触发器（50k 插入）：无触发器 125ms、有触发器 **161ms（+29.5%）**，
    换来查询从即时聚合 6.4ms → **0.085ms（≈75×）**——「为性能设计」的本质是**把一次性
    写入税换成每次读取的红利**，新鲜度与代价在此正式摆上天平。

## 5.2 业务场景：四种设计会谈（p.106）

目录用一个贯穿全书的样例业务（Business Scenario，✅ p.106）把四种设计放到同一需求集上比试——
这是本章方法论价值最高之处：**同一查询集，四种 schema，逐一过秤**。

### 5.2.1 规范化设计（p.108）

- ⚠️ 转述：3NF 中枢（Inmon 式）；优势是数据完整性与录入面复用、加载快；劣势是分析查询
  穿表多、业务用户理解成本高（对应 5.1.1 判据失败项）。
- 🔧 E1 侧证：星型三谓词查询中 join 部分是成本主体（13.3ms vs 全扫 3.1ms）——路径更长的
  规范化查询在本机动辄再翻数倍（**非 Oracle 行为**，方向性类比）。

### 5.2.2 维度设计（p.110）

- ⚠️ 转述：星型/snowflake（Kimball 式）；事实表+退化/一致性维度；查询短路径、聚合直观、
  是星型转换与位图连接索引的靶设计；代价是冗余与 ETL 侧的缓慢变化维管理（→ ch.7）。
- 与 03 的接口：本章是把 [03 §3.2](03-Oracle数据仓库导论.md) 的平台原语（RELY 约束、位图、
  分区、MV）**装配**到 schema 上的地方。

### 5.2.3 混合设计（p.113）

- ⚠️ 转述：中枢规范化 + 集市维度化（hub-and-spoke），或用物化视图在 3NF 底座上自动派生
  星型汇总——19c 指南的「物化视图构建汇总表」正是这条路线的原生实现 ⚠️
  （✅ dwhsg 主题，已抽取章级 TOC）。
- ⚠️ 编者归纳：目录给混合设计 3 页（✅ p.113–116）而给单门派各 2–3 页，暗示作者认为
  **现实企业多半落在混合区**，门派纯洁性是教科书现象。

### 5.2.4 OLAP 设计（p.116）

- ⚠️ 转述：立方体/分析视图路线（10g 的 OWB DSS cubes 语境，据归档口径
  ✅ https://docs.oracle.com/cd/E11882_01/index.htm ）；19c 的对应物是 Oracle OLAP 分析视图
  （✅ https://docs.oracle.com/en/database/oracle/oracle-database/19/oladm/ 、
  https://docs.oracle.com/en/database/oracle/oracle-database/19/olaap/ ）——立方体作为
  数据库对象而非独立服务器存活。
- 权衡（⚠️）：预计算立方体读极快、维度组合爆炸时体积失控；现代折中多为「稀疏立方 + MV
  部分物化」⚠️ 编者归纳。

### 5.2.5 其他考量（p.120）

- ⚠️ 编者归纳（据目录 p.120–126 篇幅）：时间维度与日历粒度、垃圾行/保留策略、
  多粒度事实（事务级+周期级快照并存）、代理键序列与装载耦合、安全性（角色/视图掩蔽，
  详见 [08](08-仓库管理与企业控制器.md) 管理面）。

## 5.3 选择最佳方案（p.126）

## 核心概念速览（中英对照）

- **可用性判据** — Usability-Driven Design：用户两小时培训能否自助出正确查询（✅ p.94 主题）。
- **规范化设计** — Normalized / 3NF Design：完整性与装载友好，查询长路径（✅ p.108）。
- **维度设计** — Dimensional Design：星型/snowflake，短路径与聚合直观（✅ p.110）。
- **混合设计** — Hybrid Design：3NF 中枢 + 维度集市或 MV 派生星型（✅ p.113）。
- **OLAP 设计** — OLAP/Cubes Design：分析视图/立方体作为数据库对象（✅ p.116）。
- **汇总管理** — Aggregate Management：明细/周/月/年各层留什么（⚠️）。
- **物化视图重写** — MV Query Rewrite：优化器自动把查询改打到汇总表 ⚠️（✅ dwhsg）。
- **位图索引** — Bitmap Index：低基数列的正解；🔧 E7 演示 B 树在此失效。
- **写入税换读红利** — Write-Time vs Read-Time Cost：🔧 E3 +29.5% 写入换 75× 读取（非 Oracle 行为）。
- **一致性维度** — Conformed Dimension：跨集市可拼接的共享维度（⚠️）。
- **缓慢变化维** — SCD：维度属性演化策略，ETL 侧承接（⚠️，→ ch.7）。
- **裁决四权重** — Approach Selection Rubric：查询形状/用户画像/装载预算/团队经验（✅ p.126）。

## 最新演进与工业实践

2007 → 2026 对位（⚠️ 转述 + ✅ URL）：

- **门派之争的制度化终点**：19c/23ai 仓库指南把 3NF 与星型**并列为合法架构**并按特性给清单
  （✅ dwhsg 主题：星型转换、一致性维度、位图索引、MV）⚠️——本章「四选一裁决表」的思路
  与官方文档完全同向。
- **自动化的边界扩张**：自动 DOP、SQL 计划基线、(云版)自动索引让 5.1.2 的一半手工调校
  变成后台任务 ⚠️；但**模式级决策（四选一）无法被自动索引替代**——这是 2026 工业实践中
  建模岗位仍在的原因 ⚠️ 编者归纳。
- **In-Memory 改写混合设计算术**：IMCS 列存 + 表达式级缓存让「3NF 中枢直接快查」重新可行
  （✅ https://docs.oracle.com/en/database/oracle/oracle-database/19/inmem/ ）⚠️，
  5.2.3 混合路线在今天的实现多了一个「不物化、靠列存」的变体。
- **立方体的现代形态**：Oracle OLAP 分析视图持续在库（✅ /19/oladm/ ）⚠️，但 BI 前端
  （OAC/各 BI 工具）自带缓存与聚合引擎后，数据库侧立方体的使用面收窄 ⚠️ 评价性转述；
  对照 [../Data_Warehouse_Designs/00-总览与阅读地图.md](../Data_Warehouse_Designs/00-总览与阅读地图.md) 的当代模式集。
- **湖仓侧的新输入**：开放表格式上「schema on read + on-write 混合」让 5.2 的选型表多了
  一列（对照 [../Data_Lakehouse_in_Action/00-总览与阅读地图.md](../Data_Lakehouse_in_Action/00-总览与阅读地图.md)）⚠️。
- **本机教学** 🔧：E1b/E3/E7 三件套（10× 预聚合红利、+29.5% 写入税、B 树反证）是讲
  「为什么要有维表和 MV、为什么低基数列要位图」的最低成本实验组合；
  DuckDB/SQLite 无位图索引、无查询重写，**非 Oracle 行为**。
