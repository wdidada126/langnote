## 4.1 Scale Up vs Scale Out（p.76）

- ⚠️ 编者归纳：目录把这一对比放在章首（✅ p.76–84，本章最大块），说明作者的立场是——**平台形状
  （向上扩展单机 vs 向外扩展集群）是仓库的第一决策**，先于任何建模决策。
- 两条路线的传统语义（⚠️ 转述）：
  - **Scale Up（向上）**：更大的 SMP/NUMA 单机、更多 CPU 与内存；管理简单（单实例、单备份、
    单升级路径），代价是单位算力贵、终点由厂商硬件上限决定；
  - **Scale Out（向外）**：多台小机器并联；单位算力便宜、理论无上限，代价是软件层要回答
    「数据怎么切、查询怎么并行、一台挂了怎么办」——在 2007 年的 Oracle 语境里即 RAC 与
    分区/并行查询的组合 ⚠️。
- 成本/可用/可管理三维裁决：目录给出的不是结论而是**评估轴**——成本考量（✅ p.80）、
  可用性考量（✅ p.80）、可管理性考量（✅ p.83）。这三小节让「向上还是向外」变成企业自己的
  加权评分，而不是硬件销售话术。
- 🔧 概念锚点（**非 Oracle 行为**）：E6 实验在单机 DuckDB 内把同一星型查询的线程数设为 1/2/8，
  耗时 35.6 → 18.4 → **8.3ms**（8 线程 4.3×）；20M 行聚合 564 → 216 → 140ms。这演示了
  scale-up 的第一性算术：**同一台机器内部的并行度就是微型 scale-out**，且扩展非线性——
  非线性原因（内存带宽、盘吞吐）正是 4.2「硬件平台」要人盯住的瓶颈清单（00 §9 E6）。

## 4.2 硬件平台（p.77）

- ⚠️ 转述（据 10g/11g 归档口径，✅ 归档文档库入口 https://docs.oracle.com/cd/E11882_01/index.htm ）：
  2007 年 Oracle 认证的仓库硬件形态 = 主流 UNIX/Linux/Windows 服务器 + 企业存储（SAN/NAS）；
  评估轴为：单核性能与核数（向上）、互联与缓存一致性（NUMA 跳数）、内存容量（决定
  buffer cache 能吃下多少热数据）、I/O 吞吐（决定扫描型仓库查询的下限）。
- 「仓库是 I/O 型负载」的经典判断（⚠️ 转述）：分析查询大量全段扫描、聚合、排序落盘，
  瓶颈优先在**盘与内存**，其次在 CPU——这与 OLTP 的「高并发小事务」画像相反，所以本章
  强调不能用 OLTP 的机器选型直觉套仓库。
- ⚠️ 编者归纳：本节在目录中横跨 p.77–80，含对 OEM 服务器 vs 品牌大型机的讨论余地；
  书中立场是「按三维裁决选，不按品牌信仰选」。

## 4.3 成本考量（p.80）

- ⚠️ 转述：成本轴清单——硬件采购、**Oracle 选件授权**（分区/OLAP/压缩/Diagnostic Pack 等
  在 Oracle 计价模型中均为额外选件 ⚠️）、存储增长、三年电力与机房；
  与 ch.3 的「选型即预算」呼应，并为 ch.12 的 TCO 建模埋点。
- 选件问题的算术（⚠️ 转述 + 🔧 类比）：若某查询靠分区消除从 2.7ms 降到 0.5ms（E2，本机
  UNION ALL 视图模拟，**非 Oracle 行为**），企业要回答的是「这个收益值不值一个分区选件
  授权费」——这正是 4.3 的方法论：把特性收益换算成钱，再与授权费对表（00 §9 E2）。

## 4.4 可用性考量（p.80）

- ⚠️ 转述（据归档口径）：仓库的可用性需求常被低估——装载窗口失败、单实例宕机、
  存储链路故障都直接冲击「明早九点的报表」这一硬期限。传统答案：RAC（实例级容错）⚠️、
  Data Guard（库级容灾）⚠️、备份策略与装载断点续跑设计（→ ch.7）。
- ⚠️ 编者归纳：目录把可用性与成本并列而非附于性能，体现书的价值观——**仓库是服务
  （每天必须交付的分析服务），不是一个可停机的实验环境**。

## 4.5 可管理性考量（p.83）

- ⚠️ 转述：管理成本随节点数线性上升 vs 随单机复杂度超线性上升的经验对比；
  补丁/升级窗口（RAC 滚动补丁 ⚠️）、监控面（→ ch.8 的 Grid Control）、schema/权限治理
  在三维表中的权重由企业自己定。
- 与 ch.8/ch.9 的闭环：本章定「机器形状」，ch.8 定「谁来看管」，ch.9 定「跑慢了怎么办」——
  目录层面三章构成运维三部曲。

## 4.6 平台规模测算（p.84）

目录把 sizing 拆成三个子节（✅ p.85 / p.86 / p.89），逻辑是「先问对问题 → 再测 → 再折算」。

### 4.6.1 仓库硬件规模测算所需的信息（p.85）

- ⚠️ 编者归纳（对应目录 p.85–86）：规模测算的输入清单——**行数/字节数存量、年增长率、
  并发查询用户数、峰值装载窗口时长、典型查询的扫描量分布（全表扫描 vs 索引访问比例）、
  结果集尺寸**。书的核心提醒：输入里最重要的不是磁盘容量而是**峰值小时**——仓库负载
  是「早高峰 + 夜批量」的双峰曲线，按平均值配置的机器在两个峰上都会失败。

### 4.6.2 基准测试 Benchmarking（p.86）

- ⚠️ 转述：本节（✅ p.86–89，跨 3 页）讲用真实查询回放而非通用 TPC 分数来选型；
  方法：取企业 Top-N 报表 SQL，在候选平台上带真实数据量测端到端时长。
- 🔧 类比（**非 Oracle 行为**）：E1 实验（5M 事实 + 3 维、三谓词星型查询 13.3ms，同表全扫
  3.1ms）演示「benchmark 必须测你的真实谓词组合」——只测全扫会低估 join 成本 4 倍；
  E1c（预聚合后 1.27ms）进一步说明同一 benchmark 换一种物理设计结果差一个数量级，
  **sizing 必须连设计一起测**（00 §9 E1/E1c）。

### 4.6.3 为 BI 工具测算硬件（p.89）

- ⚠️ 转述：目录明确把「BI 工具层」（应用服务器/报表服务器/门户）的 sizing 单列——
  它们是 CPU/内存型而非 I/O 型负载，且随并发点击数（而非数据量）增长；2007 年 BI 工具
  多为 Java 应用服务器形态，堆内存与缓存命中是主变量 ⚠️。

## 核心概念速览（中英对照）

- **向上扩展** — Scale Up：更大单机；管理简单、单位贵、有硬件上限（✅ p.76 主题）。
- **向外扩展** — Scale Out：多台并联；算术便宜、软件层负责切分与容错（✅ p.76 主题）。
- **三维裁决** — Cost / Availability / Manageability：成本 80、可用性 80、可管理性 83 三小节（✅）。
- **NUMA** — Non-Uniform Memory Access：向上扩展机型的隐形墙 ⚠️。
- **I/O 型负载** — Scan-heavy Workload：仓库画像，瓶颈先盘后 CPU（⚠️ 转述）。
- **选件授权费** — Option Licensing Cost：分区/OLAP/压缩按选件计价，特性收益要换算成钱 ⚠️。
- **装载窗口** — Load Window：夜间批量的硬时限，sizing 输入之一（⚠️）。
- **峰值小时** — Peak-hour Sizing：按双峰峰值而非平均值配置（⚠️ 编者归纳）。
- **真实查询回放** — Workload Replay Benchmarking：用企业 Top-N SQL 选型，不认通用分数（✅ p.86）。
- **工具层 sizing** — BI Tier Sizing：应用/报表服务器按并发点击而非数据量测算（✅ p.89）。
- **并行扩展非线性** — Sublinear Parallel Speedup：🔧 E6 的 8 线程仅 4.3×（非 Oracle 行为）。

## 最新演进与工业实践

2007 → 2026 对位（⚠️ 转述 + ✅ URL）：

- **sizing 问题被弹性算力吞掉大半**：Autonomous Database / ADB-S 按 ECPU 计费、可暂停可缩容
  （✅ https://docs.oracle.com/en/cloud/paas/autonomous-database/serverless/adbsb/ ）⚠️——
  4.6 的「买多大」变成「先跑起来再按账单调」，但 4.6.1 的输入清单（增长率/峰值窗口/
  扫描量分布）仍是估云成本的正确输入 ⚠️ 编者归纳。
- **RAC → 云托管 + 多活**：RAC/Data Guard 仍是现行产品（✅ https://docs.oracle.com/en/database/oracle/oracle-database/19/ ），
  但工业实践中仓库侧的容错越来越多交给「对象存储 + 可重建计算」的架构（对照
  [../Amazon_Redshift_TDG/00-总览与阅读地图.md](../Amazon_Redshift_TDG/00-总览与阅读地图.md)、
  [../Architecting_a_Modern_Data_Warehouse/00-总览与阅读地图.md](../Architecting_a_Modern_Data_Warehouse/00-总览与阅读地图.md)）⚠️。
- **Exadata = 本书问题的官方答案**：Oracle 把 scale-up+scale-out 混合体做成一体机，
  Smart Scan/iMPact 直接回应 4.2 的「瓶颈在 I/O」判断 ⚠️（✅ https://www.oracle.com/database/technologies/ ）。
- **In-Memory 选项改写内存账**：19c In-Memory Column Store 让「内存吃下热数据」从愿望
  变成开关（✅ https://docs.oracle.com/en/database/oracle/oracle-database/19/inmem/ ）⚠️。
- **benchmark 纪律不变**：2026 工业实践仍以真实工作负载回放选型（TPC 分数只作参考），
  与 4.6.2 完全一致 ⚠️；云时代新增的是「用生产流量灰度双平台对比」的廉价试验能力。
- **本机教学** 🔧：E6（线程 1/2/8：35.6/18.4/8.3ms）是讲「并行非线性 + 峰值测算」的
  最低成本演示；DuckDB 单进程多线程 ≠ Oracle RAC/并行查询，**非 Oracle 行为**。
