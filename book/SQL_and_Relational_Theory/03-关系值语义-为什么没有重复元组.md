# 03 关系值语义：为什么没有重复元组、为什么 ORDER BY 不属于查询

> ⚠️ 原书归属推定：Part I/II「值语义」章。这是全书**论证密度最高**的一章之一：
> 一旦承认「关系是值」，「重复元组」和「行顺序」这两个 SQL 习惯就同时失去意义。
> 所有 SQL/代数式为 🔧 自拟教学示意，非书中原文。

## 核心概念速览（中英对照）

- **值语义** — value semantics：关系像整数一样是「值」，无「位置」「份数」概念。
- **重复元组** — duplicate tuple：值语义下两个完全相同的元组不可区分，故只算一个。
- **无序性** — unordered（body 是集合）：元组集合无「第一行/最后一行」。
- **ORDER BY 滥用** — ORDER BY abuse：把排序当成查询语义的一部分，破坏封闭性。
- **表序 vs 展示序** — table order vs presentation order：展示层需要序，数据层不需要。
- **可辨识性（Identity）** — identity：值没有身份；只有变量/实体才有「同一个 vs 另一个」。
- **多重集** — multiset / bag：允许重复的集合，SQL 默认在此语义（见 09）。
- **集合** — set：无重复无序，关系模型所在语义。
- **元组可交换** — tuple commutativity：`{t1,t2} == {t2,t1}`，交换不改变关系。
- **幂等合并** — idempotent union of a tuple with itself：加两次同一个元组 = 加一次。

## 核心精讲

### 3.1 关系是值，值没有「位置」

延续 01.1：relation 是值。一个值没有「它在哪里第几个」。所以：

- 元组的**列没有左右顺序**——`{SNO:'S1', CITY:'London'}` 与 `{CITY:'London', SNO:'S1'}` 是同一元组。
- 元组之间**没有上下顺序**——关系 body 是一个集合，不存在「第一行」。

SQL 之所以看起来「有列序、有行序」，是因为**结果最终要以二维表打印给人看**，打印需要一个顺序。Date 的立场：那是展示层的选择，不是数据的性质。把展示层的顺序当成语义（`SELECT` 里靠列位置、`ORDER BY` 里靠行位置）是把实现细节提升为契约——脆弱且错误。

### 3.2 为什么 relvar 里没有重复元组

核心论证（本书反复出现）：

> 关系是**元组的集合**。集合论里 `A ∪ A = A`。若两条元组**每个属性值都相同**，它们就是**同一个元组**——你不能在集合里放两次「同一个东西」。

反证直觉：有人说「我有两行 `(S1, London)`，代表两次记录」。在纯关系模型里，那要么：
- 二者真的完全相同 → 语义上只有一条，第二条是**冗余**（该用别的属性区分，如时间戳/序号）；要么
- 二者其实不同（少写了一个区分属性）→ 那就**不是重复元组**，是元组定义不全。

🔧 例：`INSERT INTO S VALUES ('S1', 20, 'London')` 执行两次。

```text
关系模型：第二次插入违反「元组已存在」—— relvar 的值仍是 3 元组之一，不产生重复。
纯代数  ：S := S ∪ {t}；因 {t} 已在 S 中，并集不变。
SQL     ：若 S 有以 SNO 为主键 → 第二次报唯一约束错误（用键「逼近」了无重复）。
SQL     ：若 S 无主键 → 真的出现两行相同数据（模型违背，见 09 章 DISTINCT 补救）。
```

关键洞见：**SQL 是靠主键约束事后「压制」重复，而非在语义层禁止重复**；关系模型从定义上就没有重复。这解释了「为什么没定义主键的表会冒出重复行」——那不是特例，是 bag 语义的必然。

### 3.3 ORDER BY 不是查询的一部分

SQL 允许：

```sql
-- 🔧 自拟
SELECT SNO, CITY FROM S ORDER BY CITY DESC, SNO;
```

Date 的批评：`ORDER BY` **不改变结果关系**（仍是同一集合），它只规定**最终呈现**给客户端的行序。因此：

1. **只有最外层查询的 ORDER BY 才有意义**。🔧 视图/派生表/CTE 里的 `ORDER BY`：

```sql
-- 🔧 语义可疑的常见写法
CREATE VIEW v AS SELECT * FROM S ORDER BY SNO;  -- 排序被“存进”视图？
SELECT * FROM v WHERE CITY='London';            -- 这里的序并无保证
```

视图值仍是一个（无序）关系；把 `ORDER BY` 写进它，是「给一个值强加它不该有的属性」。多数 DBMS 要么忽略它，要么在优化时把该排序丢弃——于是你以为的「视图已按 SNO 排好」变成幻觉。

2. **依赖行序的后续运算不正确**。例：想「取状态最高的前 3 个供应商」，正确写法是带 `ORDER BY ... FETCH FIRST 3 ROWS ONLY`（或产品等价的 LIMIT）在**最外层一次性**做；分两步「先排序存表、再取前 3」在关系语义里不成立，因为「存下来的表」并不保留序。

### 3.4 排序破坏封闭性（与 02.5 呼应）

封闭性（02.5）要求「子表达式求值为一个关系」。若在子表达式里塞 `ORDER BY`：

- 子表达式返回值，却多带了一个「顺序」副作用 → 它不再是纯粹的关系值；
- 外层算子（连接、聚合）本应与之无关地重排 → 内层排序**逻辑上必须被丢弃**才正确，丢弃即「无用操作」，不丢弃即「依赖了一个不该依赖的属性」。

两种情况都说明：**内层 ORDER BY 要么没意义、要么有害**。这就是 Date「ORDER BY 是显示机制，不是代数算子」的落点。

### 3.5 那什么时候「看起来」需要序？

- **分页**（`OFFSET/FETCH`）、**TOP-N**：确实需要确定性顺序。Date 的解法是引入**有序关系（ordered relations）/顺序算子**作为代数扩展，把「序」显式建模为一个可命名的属性（如 `SNO ASC`），而不是藏在行的物理排列里。⚠️ 是否在第 3 版正文展开为独立章，本目录不确证。
- 要点：**确定性来自「按某属性排序」这个声明，而非来自「插入顺序 / 磁盘顺序」**。没有 ORDER BY 的 `SELECT * ... LIMIT 10` 在不同执行计划下可返回不同 10 行——这是生产事故的经典来源（🔧）。

### 3.6 工程视角：序是实现细节

[../../paper/doi_10.1145_191839.191884/00-精读笔记.md](../../paper/doi_10.1145_191839.191884/00-精读笔记.md)（AlphaSort）从系统一侧印证了同一结论：排序是**为了匹配缓存层次而精心安排的物理过程**，序不是数据本身的属性而是算力的产物。DBMS 完全可能用归并/哈希/索引返回你「没要求」的顺序。所以「不写 ORDER BY 却假设有序」是把 AlphaSort 精心优化的**副作用**当**契约**——危险。

mini-sql（[../../courses/数据库系统/15445/projects/06-mini-sql](../../courses/数据库系统/15445/projects/06-mini-sql)）里，`Sort` 是执行计划里一个**显式算子**，火山模型默认按插入/扫描顺序吐元组；不排序就没有序——工程上「序必须被显式算子产生」恰好对应「查询语义里序只来自 ORDER BY」。

## 常见误区

| # | 误区 | 纠正视角 |
| --- | --- | --- |
| 1 | 「relvar 里存两行相同数据很正常」 | 值语义下重复元组无意义；SQL 的重复来自 bag 默认 |
| 2 | 「SELECT 结果天然按主键序」 | 无 ORDER BY 即无序；序是执行计划副作用 |
| 3 | 「视图里 ORDER BY 就永久有序」 | 视图是关系值，不保留序；外层重排会丢弃它 |
| 4 | 「先排序物化、再取前 N」等价于 TOP-N | 物化表不保序；应在最外层一次声明 |
| 5 | 「行号/位置可作键」 | 位置不是属性；要用真实属性或显式序列 |
