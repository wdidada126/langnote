# 10 约束的声明式力量

> ⚠️ 原书归属推定：Part III 约束章。Date 的核心信条：**完整性规则应声明为约束（谓词），交给 DBMS 强制**，
> 而不是塞进触发器/应用代码。本文件把域约束、键约束、参照约束、CHECK 串成一个「谓词公理系统」。
> 所有 SQL/代数式为 🔧 自拟教学示意，非书中原文。

## 核心概念速览（中英对照）

- **完整性约束** — integrity constraint：对 relvar 允许取值范围的谓词限制。
- **声明式** — declarative：只说「必须满足什么」，不说「何时检查」。
- **域约束** — domain constraint：属性值必须属于其域（类型 + CHECK）（01.3）。
- **候选键约束** — candidate key constraint：唯一 + 极小（08.1）。
- **NOT NULL 约束** — not-null constraint：属性不许为空（缺失值相关，07）。
- **CHECK 约束** — CHECK constraint：对元组/列的任意布尔谓词。
- **表约束 vs 列约束** — table vs column constraint：CHECK 作用范围。
- **触发器** — trigger：过程式完整性——Date 反对用它替代声明约束。
- **约束即谓词** — constraint as predicate：每条约束都是 04 章的一个断言。
- **可强制 vs 提示** — enforced vs advisory：声明了不代表引擎真检查。

## 核心精讲

### 10.1 约束就是谓词——把 04 章用满

04 章说每个关系背后是一个谓词，每个键是一条唯一性谓词。约束体系正是把这类谓词**显式登记为公理**，由 DBMS 在每次可能违反的更新时检查。

🔧 一个 relvar 完整约束集，等价于一个公理系统：

```sql
-- 🔧 自拟：S 的约束 = 一组谓词公理
CREATE DOMAIN Sno AS CHAR(5) CHECK (VALUE LIKE 'S[0-9]%');   -- 域约束(01.3)
CREATE TABLE S (
  SNO    Sno       NOT NULL,               -- 域 + not-null
  STATUS INTEGER   CHECK (STATUS >= 0),    -- CHECK 谓词
  CITY   CHAR(15)  NOT NULL,
  PRIMARY KEY (SNO)                          -- 唯一性谓词(04.4/08.1)
);
```

每一行都在断言一个关于世界的规则。更新若使某公理为假 → 拒绝。**这是声明式的精髓：规则只写一次、由引擎在所有路径强制，无法被「忘了调校验」的某段代码绕过。**

### 10.2 约束的四层

| 层 | 约束 | 谓词形态 | 对应章节 |
| --- | --- | --- | --- |
| 单元组列 | 域约束 | `v ∈ D` | 01.3 |
| 单元组 | NOT NULL / CHECK | 布尔谓词作用于列/行 | 10.5 |
| 跨元组（同表） | 候选键/主键唯一 | `∀t1,t2: t1[K]=t2[K]⇒t1=t2` | 08.1 |
| 跨 relvar | 参照完整性 | 包含依赖 `π_FK(R)⊆π_K(S)` | 08.2 |

层次越靠下越接近关系模型（键、参照是模型原生），越靠「触发器」越偏离。

### 10.3 声明式 vs 过程式：为什么反对触发器

同一规则「STATUS 不得为负」：

```sql
-- ✅ 声明式：一处写死，任何 INSERT/UPDATE/COPY/迁移都被拦
CHECK (STATUS >= 0)

-- ❌ 过程式：每个写入口都要记得调
CREATE TRIGGER check_status BEFORE UPDATE ON S ... -- 但 COPY/批量导入/别的库呢？
```

触发器的脆弱点：**它是「过程」，依赖你覆盖所有写入路径**。批量装载、数据迁移、并发补写只要绕过触发器，约束就破了，数据库进入「本不该发生」的状态。声明式约束不存在「绕过」——它定义了什么才叫合法值。Date 把这列为 SQL 实践与理论落差的关键一条：SQL **有**声明式约束，但社区**习惯**用触发器/应用层校验（甚至很多产品 FK 不强制，见 [../Delta_Lake_Definitive_Guide/02-基本操作-事务与CRUD.md](../Delta_Lake_Definitive_Guide/02-基本操作-事务与CRUD.md) 里「湖格式 PK/FK 只是元数据提示」的对照）。

「可强制 vs 仅提示」的提醒：声明了 PRIMARY KEY/UNIQUE 是硬约束；但若某产品把 FK 当 ENFORCED=false 的元数据，则**它没在强制参照完整性**——别把声明当保证（呼应 08）。

### 10.4 CHECK 的表达力与边界

标准 SQL 的 `CHECK` 多限于**当前行/当前表**的谓词（不允许相关子查询引用别的表，跨表约束要靠断言域/触发器）。这限制了 CHECK 表达「跨元组」规则：

🔧 想表达「同一城市供应商状态之和不超过 100」——这是跨行聚合约束，单表 CHECK 做不到：

```sql
-- ❌ 非法（标准 CHECK 里通常不许子查询/聚合）
CREATE TABLE S (... CHECK ((SELECT SUM(STATUS) FROM S WHERE CITY=S.CITY) <= 100));
-- ✅ 关系模型的解法：把该约束作为数据库级断言（SQL 无直接语法；靠命名断言/触发器兜底）
```

Date 借此批评：SQL 缺一个**数据库级（跨 relvar）声明式断言**机制。理想语言（他的 Rel/Tutorial Dees，见 12）允许把任意一阶谓词登记为约束。这是「SQL 表达力不足」而非「约束不该存在」的问题。

### 10.5 可空性是约束，且应尽量收紧

`NOT NULL` 是最被低估的约束。07 章主张：**能用 NOT NULL + 域值/默认 就不用 NULL**，把可空性关掉，逻辑回到 2VL（05）。工程默认值应显式且属于域内合法值（Placeholder 思路，07.3），而不是放任列可空导致 6/8/9 章的所有连锁坑。

🔧 反例→正解：

```sql
-- 放任 NULL：查“有部门员工”要 IS NOT NULL，还混 IIT/N/A（07）
Employee(EmpID, Name, DeptID NULLABLE)
-- 收紧：N/A 用一个域内合法值 'UNASSIGNED'（域约束背书）
CREATE DOMAIN Dept AS CHAR(4) CHECK (VALUE IN ('D0','D1',...,'UNASSIGNED'));
```

## 常见误区

| # | 误区 | 纠正视角 |
| --- | --- | --- |
| 1 | 「校验放应用层/触发器更灵活」 | 过程式可被绕过；声明约束唯一强制（10.3） |
| 2 | 「声明了 FK 就有参照完整性」 | 有些产品 FK 仅提示、不强制（10.3/08） |
| 3 | 「CHECK 能表达任何规则」 | 跨表/聚合约束标准 CHECK 常不支持（10.4） |
| 4 | 「列默认可空更保险」 | 可空引入 3VL 全链坑；应主动 NOT NULL（10.5） |
| 5 | 「主键只是查询加速」 | 主键是逻辑公理，先于索引（10.2/08.1） |
