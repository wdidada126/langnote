# 08 外键与参照完整性

> ⚠️ 原书归属推定：Part II/III 约束章。参照完整性是关系模型两大完整性规则之一（另一为实体完整性），
> 源自 Codd 1970。本文件讲清 FK/被引用键/参照动作，以及 **NULL 外键如何破坏参照完整性**。
> 所有 SQL/代数式为 🔧 自拟教学示意，非书中原文。

## 核心概念速览（中英对照）

- **候选键** — candidate key：能唯一标识元组且**极小**的属性组。
- **主键** — primary key：从候选键中选定的、用于被引用的那个（实体完整性要求其非空唯一）。
- **外键（FK）** — foreign key：一 relvar 中引用另一 relvar 候选键的属性组。
- **被引用关系 / 引用关系** — referenced / referencing relvar：FK 指向的方向两端。
- **参照完整性** — referential integrity（RIC）：每个 FK 值必须匹配被引用关系中某元组的候选键值（或按规则为 NULL）。
- **子表 / 父表** — child / parent table：引用方与被引用方（口语）。
- **级联动作** — CASCADE / SET NULL / RESTRICT / NO ACTION：删改被引用键时对引用侧的处理。
- **NULL 外键陷阱** — null FK pitfall：FK 允许 NULL 时，「匹配」语义在 3VL 下变得模糊。
- **包含依赖** — inclusion dependency：RIC 的代数表达：`π_{FK}(引用) ⊆ π_{KEY}(被引用)`。

## 核心精讲

### 8.1 键的层次

- **超键（superkey）**：能唯一标识元组的属性组（可能有冗余属性）。
- **候选键（candidate key）**：**极小**的超键——去掉任一属性就不再唯一。
- **主键（primary key）**：从候选键里挑一个作为「被引用名」。Date 提醒：主键没有逻辑特权，任何候选键都能当被引用键；「必须非空」是实体完整性要求。

逻辑口径（04.4）：候选键就是一条唯一性谓词 `∀t1,t2: t1[K]=t2[K] ⇒ t1=t2`。它先于任何物理索引存在——「主键=索引」是把逻辑契约降格为性能手段（见 [../mysql/06-B树索引.md](../mysql/06-B树索引.md)）。

### 8.2 参照完整性 = 包含依赖

定义：若 relvar `R` 的属性组 `FK` 引用 relvar `S` 的候选键 `K`，则 `R` 中每个元组在 `FK` 上的值，必须在 `S` 中存在某元组在 `K` 上取同值。

🔧 代数（包含依赖）：

```text
π_{FK}(R)  ⊆  π_{K}(S)
```

这是「RIC」最干净的非 SQL 表达——它只谈投影与子集，不涉及 NULL。SQL 用 `FOREIGN KEY ... REFERENCES` 声明它，但一旦允许 FK 为 NULL，这条子集关系就被打了补丁（8.4）。

### 8.3 SPJ 的三外键

回顾 01.5，`SPJ(SNO, PNO, JNO, QTY)` 有三个 FK：

```sql
-- 🔧 自拟 DDL
CREATE TABLE SPJ (
  SNO CHAR(5) REFERENCES S(SNO),
  PNO CHAR(6) REFERENCES P(PNO),
  JNO CHAR(5) REFERENCES J(JNO),
  QTY INTEGER,
  PRIMARY KEY (SNO, PNO, JNO)
);
```

含义：任何供应记录都**必须**挂到一个真实供应商、真实零件、真实项目上。删除某供应商时，若还有 SPJ 引用它，参照完整性要求：要么禁止（RESTRICT，默认最安全），要么级联删除其供应记录（CASCADE），要么把 FK 置 NULL（往往正是灾难，见 8.4）。

### 8.4 NULL 外键如何破坏参照完整性

SQL 允许 FK 列取 NULL，标准语义是「FK 为 NULL 时该行不受 RIC 约束」（视为「尚无引用」）。问题：

- 这引入「部分匹配」的第三种状态（匹配 / 不匹配但应报错 / 因为 NULL 而豁免），本质是 3VL（06）爬进了完整性规则。
- 「NULL 表示还没分配部门」= IIT（值将来会有）；「NULL 表示无部门概念」= N/A。RIC 对二者应不同，但 SQL 一视同仁地豁免（07.2 的分类在这里直接落地）。
- 更糟：`SET NULL` 作为参照动作，会**静默地**把「曾经引用」变成「NULL 引用」，历史丢失且再也无法区分「被删」与「本就未分配」。

🔧 分解式正解（呼应 07.4）：把可空 FK 拆到独立 relvar，用**元组存在性**表达引用与否：

```sql
-- 🔧 自拟：不存在 NULL 外键，引用要么完整、要么整条不存在
Employee(EmpID PK, Name)
Assignment(EmpID PK REFERENCES Employee, DeptID REFERENCES Dept)
-- Assignment 里每条都有完整 DeptID：RIC = 纯包含依赖，无 NULL 豁免
```

⚠️ 是否在第 3 版正文以此作为「消灭 NULL」的落点，本目录按作者一贯主张组织，章号推定。

### 8.5 参照动作与「改主键」

被引用键被改/删时：

| 动作 | 效果 | 与模型张力 |
| --- | --- | --- |
| RESTRICT / NO ACTION | 有子记录则拒绝父操作 | 最贴近「公理不可违」（默认，推荐） |
| CASCADE | 父键变更同步传播到子 FK | 方便但会「悄悄改一大堆数据」，违背最小惊讶 |
| SET NULL / SET DEFAULT | 子 FK 置空/置默认 | 把引用关系降级为 UNKNOWN/魔法值（8.4） |

Date 的观点：键**本不该被改**——主键是实体的逻辑标识，改主键等于「换了个实体」。工程上应让主键与业务属性解耦（代理键或不可变自然键），把「改名字」变成普通属性 UPDATE，而非改键触发级联。

## 常见误区

| # | 误区 | 纠正视角 |
| --- | --- | --- |
| 1 | 「主键是索引」 | 主键是逻辑唯一性公理，索引是实现（8.1） |
| 2 | 「FK 加个 NULL 列无所谓」 | NULL 使 RIC 从包含依赖退化为 3VL 豁免（8.4） |
| 3 | 「ON DELETE CASCADE 很安全」 | 会静默删一大片子记录，慎用（8.5） |
| 4 | 「改了主键就是改了对象」 | 正是信号：键应不可变，改名走属性更新（8.5） |
| 5 | 「有 FK 约束=有参照完整性」 | 若允许 SET NULL/空 FK，完整性被自己的豁免破坏（8.4） |
