# 11 关系值属性（RVA）与嵌套结构

> ⚠️ 原书归属推定：Part III 深入模型章。关系值属性（一列的值本身是关系）触及第一范式边界，
> Date 视其为**合法且有用**的扩展（挑战「关系必须全是标量」的常见教条）。本文件讲 RVA、PACK/UNPACK
> 与「RVA 是否破坏封闭性」。所有 SQL/代数式为 🔧 自拟教学示意，非书中原文；多数 SQL 产品不支持 RVA。

## 核心概念速览（中英对照）

- **关系值属性（RVA）** — relation-valued attribute：某属性的取值本身是一个关系。
- **第一范式（1NF）** — first normal form：教条版要求所有属性是标量；RVA 挑战此点。
- **标量值** — scalar value：不可再分（在模型层面）的单值。
- **PACK / UNPACK** — 压缩/展开：把重复元组的信息折叠进 RVA、或把 RVA 摊平成普通元组。
- **嵌套 relvar** — nested relvar：含 RVA 的关系变量，结构成树。
- **展开封闭性** — closure under unpack：UNPACK 后仍是关系，故仍可与其它关系组合。
- **THE_IS_OF 类算子** — 从复合值取「某成分」的提取算子（作者教学语言中，⚠️）。
- **无重复嵌套** — 值语义依旧：即使列是关系，整个元组仍无重复（03）。
- **代理数组/JSON** — SQL 里的近似物：数组、JSON、XML 列（非关系，无封闭性保证）。
- **正交性** — orthogonality：属性类型（含关系）不应影响算子可用性。

## 核心精讲

### 11.1 「第一范式」没有禁止 RVA

广为流传的「1NF 要求每列都是原子标量」**不是 Codd 原始模型的一部分**，而是后来的通俗化误传。Date 反复指出：

- 关系模型要求「属性值取自某**域**」——而**关系本身可以是一个域**（关系的类型域）。
- 因此「某属性的值是一个关系」完全合法，即 RVA。
- 它**不违反值语义**：一个 RVA 值仍是一个不可分割的整体值（03）；你不能像改数组下标那样改「子关系里第几行」——那是把值当变量用。

结论：把 1NF 当「必须打平一切」的教条，会让人把本应自然建模的一对多结构强行炸成冗余行，反而制造更多 bag 问题（09）。⚠️ 第 3 版是否以独立章标题展开 RVA，本目录按作者一贯主张组织。

### 11.2 一个 RVA 例子

🔧 设 relvar `SC`，每个供应商携带「它所覆盖的城市集合」：

```text
SC(SNO, CITIES)
CITIES 的值是一个关系： { CITY:'London' ; CITY:'Paris' ; ... }
```

一个元组：`{ SNO:'S1', CITIES: { {CITY:'London'}, {CITY:'Paris'} } }`。

对比「打平版」`SC_flat(SNO, CITY)`（两行）。RVA 版把「一个供应商 + 它的城市集合」当作**一个命题**，语义更完整，也避免把 `SNO` 的属性级信息（如 `STATUS`）在多个城市行里冗余重复——这正是 1NF 教条造成的反模式。

### 11.3 PACK 与 UNPACK：一对互逆算子

- **UNPACK**：把 RVA 摊平——对每个元组，按其 RVA 的每个元组复制外层一次，得到普通（打平）关系。
- **PACK**：按指定属性把打平关系折叠——同外层键的多个行合成一个 RVA。

🔧 关系代数式：

```text
UNPACK  CITIES  OF  SC        -- 展开：SC → 打平的 (SNO, CITY)
PACK    CITY  INTO CITIES ON SC_flat   -- 折叠：(SNO,CITY) → (SNO, CITIES)
PACK(UNPACK(SC))  ==  SC       -- 互逆，且不改变值（03 值语义）
```

要点：PACK/UNPACK **保持关系类型**——输入是关系、输出还是关系（封闭性，02.5）。所以你可以 UNPACK 后接 σ/π/⋈，再 PACK 回来，全程可组合。这是「RVA 不破坏代数」的技术证明。

### 11.4 RVA 与封闭性：作者的核心辩护

反对 RVA 者常说「嵌套破坏了关系代数的简洁/封闭」。Date 的回应：

1. **只要把算子定义在「值可为关系」的属性上**，投影/限制/连接照旧作用于元组整体——封闭性保住。
2. PACK/UNPACK 提供「需要打平才能做的运算」的入口，用完再折叠，不牺牲可组合性（11.3）。
3. 真正破坏封闭性的是 **SQL 的 ORDER BY（03）与 bag（09）**，不是 RVA——这是把矛头对准错了靶子。

⚠️ 注意：RVA 在 SQL 标准里有零星支持（如某些产品的行类型/表类型 + `THE_` 提取算子），但**主流关系数据库（MySQL/PostgreSQL）不把它当一等公民**——这也是 Date 批评 SQL 对模型执行不彻底的老例子。

### 11.5 SQL 的 JSON/数组 ≠ RVA

现代 SQL 大量用数组/JSON/XML 列表达嵌套，看起来像 RVA，实则不同：

| 维度 | 关系模型 RVA | SQL JSON/数组 |
| --- | --- | --- |
| 值语义 | 整体值，不可按下标改「内部第几行」 | 可索引、可局部 mutate（更像变量） |
| 算子 | 关系算子照常适用（封闭性） | 各自一套 JSON 函数，不可与 π/⋈ 组合 |
| 重复/序 | 内部仍是无序无重复的关系 | 数组有序有重复（bag 语义） |
| 完整性 | 可施加键/参照约束 | 基本无声明式约束（10 章缺失） |

Date 的立场：嵌套**应当**是「关系值」而非「半结构化的字符串袋」，否则你既丢了封闭性，又把 03/09 的重复行与序问题请了回来。

### 11.6 RVA 在真实产品里的处境（诚实边界）

为免把 RVA 讲成「SQL 也支持、只是你没会用」，需交代现实：

| 产品/标准 | 对 RVA 的支持 | 差距 |
| --- | --- | --- |
| SQL 标准 | 有 row/table 类型（`ROW`、`CREATE TYPE ... AS TABLE`），极少数实现 | 关系算子不能直接作用于其值 |
| PostgreSQL | 复合类型 + 数组 + `TABLE` 返回；无「列本身是关系且可 π/⋈」的一等 RVA | 需展开成普通表才能组合 |
| MySQL | `ROW`/`TABLE` 类型基本不可用；JSON 承担嵌套 | 完全不满足「保封闭性的 RVA」 |
| Tutorial D / Rel | RVA 是一等公民，`THE_`/PACK/UNPACK 内置 | 这才是 Date 心中的「应然」 |

因此本目录对 RVA 的定位是**理论示范**，而非「你今天就能在生产库这么写」：它存在的意义，是用一个干净反例回击两条流行误传——(a)「1NF 禁止嵌套」（11.1）与 (b)「嵌套必然破坏代数封闭性」（11.4）。🔧 务实做法：当 RVA 不可用时，退回 07.4 的**分解 relvar**（打平到独立表 + 主键），既保住值语义，又避免 JSON 数组的 bag 副作用（11.5）。这是把「RVA 的精神」落到「当前 SQL 的手艺」的标准折中。

## 常见误区

| # | 误区 | 纠正视角 |
| --- | --- | --- |
| 1 | 「1NF 禁止任何嵌套」 | Codd 模型只要求值取自域；关系可作域（11.1） |
| 2 | 「RVA 破坏关系代数封闭性」 | PACK/UNPACK 保关系类型，可组合（11.3/11.4） |
| 3 | 「JSON 列就是嵌套关系」 | 它是有序有重复的袋、无关系算子（11.5） |
| 4 | 「 RVA 里第 3 行」 | 值无位置概念（03）；RVA 内也是无序集合 |
| 5 | 「打平总是更安全」 | 打平时外层属性冗余，反致 bag/更新异常（11.2） |
