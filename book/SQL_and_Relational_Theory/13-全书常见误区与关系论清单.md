# 13 全书常见误区与关系论清单

> ⚠️ 原书归属推定：全书综合（非独立章，是对 01–12 论证的收束）。本文件是一张**排雷总表**：
> 每条 SQL 惯用错误 → 对应的关系模型纠正视角 → 等价式/改写 → 落在本目录哪一章。
> 所有 SQL/代数式为 🔧 自拟教学示意，非书中原文。

## 核心概念速览（中英对照）

- **关系论排雷** — relational debugging：用「本应的代数式」对照「实际 SQL 结果」找语义偏差。
- **值语义违反** — value-semantics violation：依赖重复行/行序（03）。
- **bag 偏离** — bag deviation：默认多重集导致的重复计数（09）。
- **3VL 陷阱** — 3VL trap：NULL 使互补谓词留缝、NOT IN 坍缩（06）。
- **德摩根误写** — De Morgan error：否定未翻转连接词（05）。
- **ORDER BY 滥用** — ORDER BY abuse：把展示序当语义（03）。
- **LEFT JOIN 误用** — LEFT JOIN misuse：把外连接当可选匹配并计数（09）。
- **可空性滥用** — over-nullability：该用域值/分解处用了 NULL（07/10）。
- **过程式完整性** — procedural integrity：用触发器/应用层替代声明约束（10）。
- **1NF 教条** — 1NF dogma：误以为禁止 RVA（11）。

## 核心精讲

### 13.1 四大惯用错误总表

| # | SQL 惯用错误 | 现象 | 关系模型纠正视角 | 等价/改写 | 详见 |
| --- | --- | --- | --- | --- | --- |
| 1 | 投影忘 `DISTINCT` | `SELECT SNO FROM SPJ` 出重复 | π 是集合运算，天然去重 | 加 DISTINCT 或 GROUP BY | 02.3/09.2 |
| 2 | 依赖无 ORDER BY 的行序 | 后续 LIMIT/分页结果漂移 | 关系无序，序只来自 ORDER BY | 在最外层显式排序 | 03.3 |
| 3 | 子查询/视图内放 ORDER BY | 以为「已排好」 | 值是关系，不带序；被优化器丢 | 移到最外层 | 03.4 |
| 4 | `NOT IN (…可能 NULL…)` | 结果意外为空 | 3VL：UNKNOWN 使整体丢 | `EXCEPT`/`NOT EXISTS` | 06.4 |
| 5 | `WHERE col <> 'x'` 想要「其它」 | NULL 行两头都不在 | `<>` 对 NULL=UNKNOWN | 补 `OR col IS NULL` 或重建模 | 06.3 |
| 6 | `NOT(A AND B)`→`NOT A AND NOT B` | 漏行 | 德摩根要变 OR | `NOT A OR NOT B` | 05.2 |
| 7 | `SUM(*)/COUNT(*)` 求「非空均值」 | 分母混 NULL 行偏小 | 聚合口径要一致 | `SUM/COUNT(col)` 或消 NULL | 06.5 |
| 8 | `LEFT JOIN` 后 `COUNT(*)` 当匹配数 | 补 NULL 行被计入→偏大 | 外连接造人造行 | `COUNT(right_pk)` | 09.5 |
| 9 | `JOIN` 后 `SELECT *` | 连接键双列、下游错 | 自然连接只留一列 | 显式列清单 | 02.4 |
| 10 | 用触发器/应用层做完整性 | 有绕过路径→脏数据 | 声明式约束唯一强制 | CHECK/KEY/FK | 10.3 |
| 11 | 让外键可空表达「暂无」 | RIC 变 3VL 豁免 | 分解 relvar 用元组存在性 | `Assignment` 独立表 | 07.4/08.4 |
| 12 | `UNION ALL` 用于本应去重的并 | 重复计数 | 关系并=去重 | 改 `UNION` | 09.4 |
| 13 | 把 JSON/数组当嵌套关系 | 有序有重复、无算子 | RVA 才是模型内的嵌套 | 见 11.5 | 11.5 |
| 14 | 「1NF 禁止一切嵌套」 | 强行打平致冗余 | RVA 合法、不违值语义 | PACK/UNPACK | 11.1 |

### 13.2 用代数式做单元测试（全书方法论）

Date 反复教的习惯不是「背规则」，而是**拿关系代数当规格说明书**：

1. 先写出「本应」的代数式（π/σ/∪/−/⋈/÷，见 02）。
2. 写你的 SQL。
3. 对同一数据集，把 SQL 结果 `DISTINCT` 后与代数结果比集合相等。
4. 不等 → 定位到 bag/NULL/序 三类偏离之一。

🔧 例（除法类查询）：「供应了全部零件的供应商」——

```text
代数： π_SNO,PNO(SP) ÷ π_PNO(P)
SQL ： SELECT SNO FROM SP GROUP BY SNO
       HAVING COUNT(DISTINCT PNO) = (SELECT COUNT(*) FROM P)
```

若忘记 `DISTINCT`（PNO 在 SP 里可重复），`COUNT(PNO)` 会偏大、误判「供应了全部」——代数式 `÷` 一步点破这里必须在**集合**上比。这类「用代数定位 DISTINCT」是 09 章的通用招式。

### 13.3 日常 checklist

写 SQL 前：
- 这个结果**是不是一个关系**？→ 需不需要 DISTINCT（13.1-1）？
- 我有没有在**依赖行序**？→ 序只该来自最外层 ORDER BY（13.1-2/3）。
- 有没有 NULL 列参与比较/聚合/外键？→ 见 5/6/7/8/11。
- 完整性规则**声明为约束**了吗，还是塞在代码里（13.1-10）？

写 SQL 后：
- `NOT IN` 换成 `EXISTS`/`EXCEPT` 了吗（13.1-4）？
- `LEFT JOIN` 计数用的是 `COUNT(right_key)` 吗（13.1-8）？
- `GROUP BY` 非聚合列是否合法（09.3）？

### 13.4 务实边界：什么时候 bag/NULL/序 *确实* 有用

Date 是理想主义者，但本清单要诚实：

- **bag 有用**：明细事实表就是要「一笔一行」，重复是信息不是噪声——此时应显式用 `UNION ALL`、`COUNT(*)`（09.4）。关键是**主动选择 bag**，而不是「因为 SQL 默认所以被动掉进 bag」。
- **NULL 有用**：快速原型/稀疏属性用 NULL 现实得多——但要意识到你引入了 3VL 全链坑（06），并对「两类缺失值」保持警觉（07）。Date 的正解（Placeholder/分解）有建模成本。
- **ORDER BY 有用**：分页、Top-N、报表**确实**要序——只是序要在**最外层一次性声明**，且要唯一确定（tie-breaker）以保证可重复（03.5）。

一句话：**偏离模型不是罪，「无意识地偏离」才是**——本目录全部章节的总纲就是这句。

### 13.5 三组「差一点就错」的工作化对照

🔧 以下每组给出「常见 SQL」「代数应然」「修正」，是排雷总表的高频落地：

1. **求「没被引用」的实体**（06.4 / 08.4）

   ```sql
   -- ❌ 子查询可能含 NULL → 整体空
   SELECT * FROM S WHERE SNO NOT IN (SELECT SNO FROM SP);
   -- ✅ 代数=差集；EXCEPT 走集合语义，无 3VL
   SELECT SNO FROM S EXCEPT SELECT SNO FROM SP;
   -- 代数应然： π_SNO(S) − π_SNO(SP)
   ```

2. **自连接找「同市的两个不同供应商」**（02.4 / 03.1）

   ```sql
   -- ❌ 只写 CITY 相等，会把 S1 与 S1 自己配成一对
   SELECT a.SNO, b.SNO FROM S a JOIN S b ON a.CITY = b.CITY;
   -- ✅ 加“不同元组”条件；关系模型里靠候选键区分，不用行位置
   SELECT a.SNO, b.SNO FROM S a JOIN S b ON a.CITY=b.CITY AND a.SNO < b.SNO;
   ```

3. **分组后按组条件筛**（09.3）

   ```sql
   -- ❌ 把组条件写进 WHERE（分组前，引用聚合非法/语义错）
   SELECT CITY FROM S WHERE COUNT(*) > 3 GROUP BY CITY;
   -- ✅ HAVING 才作用于组；WHERE 作用元组（04 谓词对象不同）
   SELECT CITY FROM S GROUP BY CITY HAVING COUNT(*) > 3;
   -- 代数应然： 先 γ_COUNT(σ_…)? —— SQL 无原生分组算子，HAVING 是其近似
   ```

这三组反复验证同一条：**先写代数应然，再补 SQL 的语法糖与安全网（DISTINCT/EXCEPT/HAVING/键去重）**。
