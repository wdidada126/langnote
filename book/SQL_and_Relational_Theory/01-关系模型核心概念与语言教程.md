# 01 关系模型核心概念与语言教程

> ⚠️ 原书归属推定：Part I 导论章。本文件把 Date 反复强调的「先分清 relation 与 relvar、
> 属性/域/度/基数」这套词汇表讲透，并以经典 **SPJ 例库**（S 供应商、P 零件、J 项目）为贯穿全书的关系。
> 所有 SQL/代数式为 🔧 自拟教学示意，非书中原文。概念源头见 Codd 1970。

## 核心概念速览（中英对照）

- **关系** — relation：某「头」之下由元组构成的**集合**（数学上是无序、无重复的）。
- **元组** — tuple：属性名到值的有限映射；口语里的「一行」。
- **属性** — attribute：有名字、有类型（域）的列定义；注意它不是「值」而是「列头 + 位置无关的命名」。
- **域** — domain：某属性允许取值的集合，含类型与约束；两个不同域即使底层类型相同也不可互换。
- **度 / 目** — degree / arity：关系中属性的个数（列数）。
- **基数** — cardinality：关系中元组的个数（行数）。
- **头** — heading：属性名集合及其域、可空性声明；决定「什么样的元组属于本关系」。
- **关系变量** — relvar：取值范围是「某头下的所有关系」的**变量**；数据库本质由 relvar 构成，而非「表」。
- **关系表达式** — relational expression：求值为一个关系的式子，是查询的载体。
- **关系数据库** — relational database：一组 relvar（及其当前值）的整体。
- **声明式语言** — declarative language：只说「要什么」不说「怎么取」，与导航式（层次/网络）模型对立。
- **SPJ 例库** — S/P/J sample database：供应商—供应—零件—项目的教学关系，作者全书反复使用。

## 核心精讲

### 1.1 relation 是值，relvar 是变量（全书第一课）

Date 的第一要务是把两个被日常混用的词分开：

- **relation（关系）** 是一个**值**（value），像整数 `42` 一样不可变、无「所在存储位置」的概念。
- **relvar（关系变量）** 是一个**变量**，它的「当前值」是某个关系；`INSERT`/`DELETE`/`UPDATE` 改变的是 relvar 的值。

SQL 把 relvar 的实现叫做「表（table）」，把关系值也叫做「表」，于是「值 = 变量」的混淆从术语层面就发生了。这个混淆是后续**一切误用的根**：

- 你以为「表有第一行」——其实关系是集合，元组**无序**（见 03 章 ORDER BY）。
- 你以为「表里可以有两行一模一样」——其实值语义下重复元组不成立（见 03、09 章）。
- 你以为「改表就是改数据」——其实你在改 relvar 的当前值，约束（见 10 章）定义了这个值允许的范围。

🔧 关系代数里，`S` 既是 relvar 也是它当前值的简写；写成表达式 `σ (S.STATUS > 20) (S)` 时，最外层 `S` 取的是当前关系值。

### 1.2 头（heading）与元组（tuple）

一个关系由两部分构成：

- **header / heading**：属性集合，每个属性带 {名字, 域, 是否可空}。
- **body**：满足该头的所有元组构成的集合。

元组是**属性名 → 值**的映射，不是「位置序列」。所以：

```text
关系 S 的元组： { SNO: 'S1', STATUS: 20, CITY: 'London' }
```

`SNO`、`STATUS`、`CITY` 的书写顺序**不构成语义**：`{CITY, STATUS, SNO}` 与 `{SNO, STATUS, CITY}` 是同一个元组。SQL 的列序是「展示便利」，关系模型里列是**以名字索引的映射**。这正是为什么「按位置引用列」是可疑的（见 09 章 GROUP BY 位置陷阱）。

### 1.3 域（domain）：不是类型别名

域携带**身份**与**约束**。即使 `SNO` 和 `PNO` 都基于整数：

- 把某个 `PNO` 的值赋给 `SNO` 属性，是**类型错误**——它们是不同的域。
- 域约束是声明式完整性的最小单元（见 10 章）：值合法与否先由域决定，再由键/参照/CHECK 决定。

🔧 多数 SQL 产品允许 `CREATE DOMAIN`（PostgreSQL）或根本不强制域身份（MySQL 把 domain 当伪类型），这本身就是 SQL 对模型的一处偏离。

### 1.4 度与基数

- **度（degree / arity）** = 属性个数。`S` 的度为 3（SNO, STATUS, CITY）——SPJ 常见口径。
- **基数（cardinality）** = 元组个数。投影会降度，限制会（可能）降基数。

关系代数里，「度改变」的算子只有投影/改名/乘/连接；「基数改变」的算子有全部。理解某个算子动了哪个，是写出正确等价式的前提（02 章）。

### 1.5 SPJ 例库（贯穿全书的具体关系）

⚠️ 以下为作者一贯使用的教学关系，属性名按常见口径给出（非书中原文编号）：

- `S(SNO, SNAME, STATUS, CITY)` 供应商
- `P(PNO, PNAME, COLOR, WEIGHT)` 零件
- `J(JNO, JNAME, CITY)` 项目
- `SPJ(SNO, PNO, JNO, QTY)` 供应关系（三外键，见 08 章参照完整性）

🔧 一个典型需求：「找出向项目 J1 供货的供应商编号」。关系代数式：

```text
π SNO ( σ JNO='J1' (SPJ) )
```

对应 SQL：`SELECT SNO FROM SPJ WHERE JNO = 'J1'`——注意 SQL 里它返回的是「带重复可能的行的表」，代数里它是「一个度为 1 的关系」。差异见 03、09 章。

### 1.6 声明式 vs 过程式（承 Codd）

Codd 1970 的核心主张：用户只描述「要什么」，不描述「怎么取」。relvar/relation/attribute 这套词汇正是为了让**逻辑结构与物理存储解耦**：

- 换索引、重排记录、加物化视图，都不该改变一个声明式查询的含义。
- 一旦你依赖「行顺序」「重复行数」「物理列位置」，你就把逻辑重新耦合进了实现（这正是全书排雷的靶心）。

## 常见误区

| # | 误区 | 关系模型的纠正视角 | 详见 |
| --- | --- | --- | --- |
| 1 | 「表 = 关系」 | 表是 relvar 的实现；关系是值，二者层次不同 | 03 |
| 2 | 「第一列 / 第三行有意义」 | 元组无序、属性以名字索引；位置是展示产物 | 03、09 |
| 3 | 「SNO 和 PNO 都是整数就能混用」 | 域有身份与约束，不可互换 | 10 |
| 4 | 「关系里能存两行完全相同的数据」 | 值语义下重复元组坍缩为一个 | 03、09 |
| 5 | 「查询要写清楚取数步骤」 | 声明式：说清结果，优化器决定路径 | 1.6 |
