# 第 10 章 大规模数据处理的演进（The Evolution of Large-Scale Data Processing）

> 对应原书 Part II 第 10 章（英文原题 *The Evolution of Large-Scale Data Processing*；中译「大规模数据处理的演进」）。
> 小节目录 ✅ oreilly.com.cn 实抓：10.1 MapReduce / 10.2 Hadoop / 10.3 Flume / 10.4 Storm / 10.5 Spark /
> 10.6 MillWheel / 10.7 Kafka / 10.8 Cloud Dataflow / 10.9 Flink / 10.10 Beam / 10.11 小结。
> 本文件为精读重构。前十章是"语言"，本章是"文学史"：九个系统如何各自发明语言的碎片，Beam 如何收编。

## 章定位与中心论题

作者的谱系学立场：**每个系统都解决了四问的一部分，并把自己的解法误当成全部需求**。
阅读本章的正确姿势不是记发布年份，而是给每个系统贴"它回答了哪几问、回避了哪几问"的标签——
本书前面九章即评分卡。

## 逐节精读重构（按小节给"一句定位 + 四问记分卡"）

### 10.1 MapReduce

- 定位：把 Google 内部批处理工业化的论文级抽象（Dean & Ghemawat；CACM 版
  ✅ DOI 10.1145/1327452.1327492 经 Crossref 校验，2008；OSDI'04 原版无 Crossref DOI ⚠️）。
- 记分卡：What=✅（key）；Where=全局窗；When/How=输入终止隐式回答。
  **贡献是把"终止证据"制度化，局限是只此一解**。

### 10.2 Hadoop

- 定位：MapReduce+HDFS 的开源复刻，让"批"成为时代默认假设十年。
- 与本书关系：把 10.1 的局限**规模化**了——"等数据齐"成为整个数据工程的组织方式（数仓夜批、T+1），
  为后续所有"流式复兴"埋下张力。对照 [../bigdata/01-大数据技术全景.md](../bigdata/01-大数据技术全景.md) ⚠️（该文件在本目录之外的速览版）。

### 10.3 Flume

- 定位：⚠️ 转述——谷歌内部的近实时日志采集/管道系统（2006 前后论文口径），
  本书谱系里代表"批思维第一次被日志流量撞腰"；
  开源 Apache Flume（Twitter 系）同名不同源，原书亦提醒区分。

### 10.4 Storm

- 定位：2010 年前后（BackType→Twitter）的**逐事件**流处理开创者：低层 tuple 拓扑、
  at-least-once、锚点记账（acker）。
- 记分卡：When 几乎放弃（无事件时间/水位线，"来就算"），What=✅，How=❌（无 pane 概念）。
  历史地位：**证明了逐事件拓扑可扩展**，教训是**语义贫乏会把复杂度甩给应用**。

### 10.5 Spark

- 定位：批优先的统一引擎（RDD→SQL→MLlib）；Structured Streaming 以微批补流式短板 ⚠️（版本细节转述）。
- 记分卡：What/Where=✅（watermark 支持后窗口可用），When/How=微批近似——
  "秒级新鲜 + 完全完备"的中间路线，适合把流当"慢批"的负载。

### 10.6 MillWheel ★（本书的亲生父亲）

- 定位：**本章重心**。谷歌 2013 年工业系统，第一次把
  "持续计算 + 事件时间 + low watermark + 触发/累积 + 容错到持久状态"写进同一个系统。
- 一手文献 ✅：Akidau, Balikov, Bekiroğlu, Chernyak, Haberman, Lax, McVeety, Mills, Nordstrom, Whittle,
  *MillWheel: Fault-Tolerant Stream Processing at Internet Scale*，**PVLDB Vol.6, pp.1033–1044 (2013)**；
  DOI ✅ Crossref 校验 10.14778/2536222.2536229；PDF ✅ https://vldb.org/pvldb/vol6/p1033-akidau.pdf （200）。
  作者名单含本书第二、三作者——谱系即自传。
- 记分卡：四问全 ✅，唯 API 专有、无跨引擎语言 → 直接催生 10.8/10.10。
- 勘误提醒：本仓库 [../bigdata/07-实时计算与流式架构.md](../bigdata/07-实时计算与流式架构.md)
  参考表把此文标为"OSDI 2013"，应为 **PVLDB/VLDB 2013**（见 00 第二节登记；不改他文件）。

### 10.7 Kafka

- 定位：LinkedIn 起源的分布式提交日志（2011）；本书视角下它是**"源与汇的精确一次地基"**（5.6/5.7）：
  可重放 + 位点提交 + 分区内有序。Kafka Streams/事务后来补齐处理语义 ⚠️（细节见姊妹篇）。
- 深读：[../Kafka权威指南2.md](../Kafka权威指南2.md)、[../深入理解Kafka与Pulsar.md](../深入理解Kafka与Pulsar.md)。

### 10.8 Cloud Dataflow

- 定位：MillWheel 思想的托管服务化（2014 GA 口径 ⚠️ 转述），
  同时是 **The Dataflow Model 论文**（1792–1803, PVLDB Vol.8, 2015，
  ✅ DOI 10.14778/2824032.2824076，PDF ✅ https://vldb.org/pvldb/vol8/p1792-akidau.pdf 200）的产品载体——
  第 2~5 章的内容即该论文的语言化重写。

### 10.9 Flink

- 定位：柏林 Stratosphere 血统的"真逐事件流 + 后补批"引擎（区别于 Spark 的"批 + 后补流"）；
  事件时间/水位线 2015–2016 年加入（1.0 时代 ⚠️ 转述），从此与本书模型高度同构。
- 记分卡：四问全 ✅（API 命名各异），**是本书模型的最完整开源镜像**——
  运行时演进请直读 [../Stream_Processing_with_Apache_Flink/00-总览与阅读地图.md](../Stream_Processing_with_Apache_Flink/00-总览与阅读地图.md)。

### 10.10 Beam

- 定位：收束者。Apex 项目（2016.10 入孵化器）→ Apache Beam（2017 TLP ⚠️ 时间线转述）：
  **把 10.1–10.9 的差异降维成"一个模型 + N 个 runner"**——本书第 2 章路线图的产品化终点。
  本章末，作者给出全书唯一"工程选型建议"式的收束：选引擎看运维与生态，
  **写逻辑坚持用模型语言**（可移植性、可测试性、可重放性皆源于此）。
- 记分卡：Beam 不做保证，**只给四问留语法位**；保证是 runner 的事 ⚠️（与 5.9 的路线分派呼应）。

### 10.11 小结

谱系图的读法：横轴时间不重要，纵轴"**对四问的显式程度**"才重要；
本书全部历史观压缩成一句——**流处理的进步史 = 时间参数从隐到显的编译史**。

## 🔧 概念演示：用一段递归 SQL 复现"批→微批→连续流"三档谱系（DuckDB，非真流引擎）

同一聚合逻辑，三档只是"前缀切多细 + 何时发布"（第 1/2 章论断的执行版）：

```sql
with events(i,k,v) as (values (1,'a',10),(2,'a',5),(3,'a',7),(4,'a',-2)),
micro as (select (i-1)//2+1 as batch_no, k, sum(v) as part   -- 微批：每 2 条一切（// 为整除）
          from events group by 1,2),
stream as (select i as row_step, k, sum(v) over (partition by k order by i) as running from events)
select 'batch_all' as mode, 1 as step, k, sum(v) as result from events group by k
union all select 'micro_batch', batch_no, k, sum(part) over (partition by k order by batch_no) from micro
union all select 'row_stream', row_step, k, running from stream
order by mode, step, k;
```

🔧 实测输出：

```text
mode        step  k  result
batch_all   1     a  20.0
micro_batch 1     a  15.0
micro_batch 2     a  20.0
row_stream  1     a  10.0
row_stream  2     a  15.0
row_stream  3     a  22.0
row_stream  4     a  20.0
```

三种 mode 的**终值完全一致**（a=20），发布轨迹截然不同：批一步到位；微批两步（15→20）；
逐行流四步，且**第 3 步报出 22 的"过高估计"、第 4 步才修正回 20**——
最后那一笔 `-2` 迟到修正恰好显影了第 1 章"新鲜但不完备"与第 2 章"How（累积/修正）"的全部张力：
10.2/10.5/10.4 三代系统就是这条轨迹上的三个采样点（第 1 章演示的谱系化版本）。

## 核心概念速览（中英对照）

- **谱系学** — genealogy：按"回答了四问的哪几问"重排系统史的方法
- **T+1 夜批** — nightly batch：Hadoop 时代"等数据齐"的组织化形态
- **逐事件** — per-event/row-at-a-time：Storm 路线，低延迟高语义负担
- **微批** — micro-batch：Spark 路线，秒级新鲜+完全完备的折中
- **提交日志** — commit log：Kafka 的本体，可重放源的原型
- **low watermark** — MillWheel 发明、本书命名的进度承诺
- **持续计算** — continuous computation：MillWheel/Dataflow 的运行时形态
- **托管服务化** — managed service：Dataflow：模型语言的商品化包装
- **统一模型** — unified model：Beam：一个模型多种运行时的收束策略
- **隐→显编译史** — from implicit to explicit：全章史观一句话
- **可移植性论点** — portability argument：作者"写逻辑坚持模型语言"的选型建议
