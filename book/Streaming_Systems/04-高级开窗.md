# 第 4 章 高级开窗（Advanced Windows）

> 对应原书 Part I 第 4 章（英文原题 *Advanced Windows*；中译「高级开窗」）。小节目录 ✅ oreilly.com.cn 实抓：
> 4.1 时机/位置：处理时间开窗 / 4.2 位置：会话 / 4.3 位置：自定义开窗 / 4.4 小结。
> 本文件为精读重构。第 3 章给了"何时可触发"的证据，本章把 Where（开窗法）与 When/How（触发、pane、累积）推向高级形态。

## 章定位与中心论题

固定窗（tumbling/sliding）+ 事件时间 + 水位线，能覆盖 80% 场景；本章处理剩下 20%：
**没有事件时间可用怎么办**（处理时间开窗）、**窗边界由数据自己决定怎么办**（会话窗）、
**现成窗形都不合用怎么办**（自定义开窗）。三者共同展示 Where/When/How 三参数的**正交组合威力**。

## 逐节精读重构

### 4.1 时机/位置：处理时间开窗

- 标题的双写"时机/位置"点出本章论点：处理时间窗**同时改变 Where 和 When**——
  窗边界由墙钟划定（Where），触发也由墙钟决定（When），水位线退场（衔接 3.5）。
- 正当使用场景（重构原书清单）：
  1. 数据根本没有事件时间戳，且无法回填；
  2. 心跳/探活/指标告警类语义本来就是"现在还没来 = 异常"；
  3. 系统负载保护：为迟到设的上限就是业务可接受的等待上限；
  4. **永远不该用**的场景：需要可重放、可调试、跨作业可比较的历史口径（处理时间结果不可重现）。
- 原书的诚实告诫（⚠️ 转述口径）：处理时间窗的输出**依赖机器与时钟**，扩容/恢复后结果漂移是特性不是 bug。
- "何时/如何"的其余正交件在此收拢成一张决策表：
  触发条件（窗尾+水位到 / 处理时间定时器 / 自定义组合）、pane 输出方式（discarding/firing/accumulating，
  第 2 章三模式）、迟到处置（允许迟到窗口内重触发 vs 侧输出落盘）。

### 4.2 位置：会话（Session Windows）

- 会话窗 = **无固定边界、按静默间隔（gap/session window duration）切分的逐键窗**，
  是"Where 由数据决定"的典型：每个新元素都可能**延展或合并**窗。
- 工业原型即 Google Analytics 会话（⚠️ 转述）：30 分钟无活动即断会话；
  难点在三处：窗随数据生长（状态必须记录当前会话边界）、乱序可致**两会话合并**、
  触发只能靠"gap 过去了没"（每键定时器）或水位线（gap 事件时间判据）。
- 与固定窗的本质差异：固定窗的元素归属在到达时可判定；会话窗的归属**可事后改变**——
  这正是第 5 章"pane 身份不稳定 → 精确一次更难"的伏笔。

### 4.3 位置：自定义开窗

- Beam 式解法：开窗即**用户函数** `WindowFn`——给定元素返回其所属窗集合
  （一个元素可入多窗，这统一了滑动窗的"复制"语义 ⚠️ 转述）。
- 原书示例口径（⚠️ 转述）：按"一场球赛一局（inning）"开窗、按日历/工作日开窗等——
  共同点是把**领域语义**（而非时间几何）做成 Where 的回答；
  自定义窗同时要回答触发（When）与合并（How），三者必须配套设计。
- 设计守则（重构表述）：能表达成"固定窗+good key"的不要用会话；能用会话的不要用自定义；
  自定义窗要同时交付**可合并性证明**（给第 5 章）与**可重放确定性**（元素→窗映射纯函数）。

### 4.4 小结

窗不是"时间切片工具"，而是**四问中 Where 的答案载体**；每次偏离固定窗，
都是在把 Where 的决定权从系统交还给数据或用户，代价由 When/How/保证层支付。

## 🔧 概念演示：递归 CTE 造会话窗（DuckDB 1.5.5；非真流引擎）

流式会话窗的"逐元素延展 + gap 判尾"在批语义下等价于经典 **gaps-and-islands**，
用递归 CTE 携带 `(上一事件时间, 会话起点, 会话号)` 状态模拟"每键状态"：

```sql
with recursive events(key, ts) as (values
 ('u1',timestamptz '2024-01-01 10:00'),('u1',timestamptz '2024-01-01 10:10'),
 ('u1',timestamptz '2024-01-01 10:55'),('u1',timestamptz '2024-01-01 12:30'),
 ('u2',timestamptz '2024-01-01 09:00'),('u2',timestamptz '2024-01-01 09:20'),
 ('u2',timestamptz '2024-01-01 10:30')),
ord as (select key, ts, row_number() over (partition by key order by ts) as rn from events),
sess as (
  select key, rn, ts, ts as session_start, 1 as sid from ord where rn = 1
  union all
  select o.key, o.rn, o.ts,
         case when o.ts > s.ts + interval '30' minute then o.ts else s.session_start end,
         s.sid + case when o.ts > s.ts + interval '30' minute then 1 else 0 end
  from sess s join ord o on o.key = s.key and o.rn = s.rn + 1)
select key, sid, min(ts) as session_begin,
       max(ts) + interval '30' minute as tentative_end, count(*) as events
from sess group by key, sid order by key, sid;
```

🔧 实测输出：

```text
key sid session_begin      tentative_end      events
u1  1   2024-01-01 10:00   2024-01-01 10:40   2
u1  2   2024-01-01 10:55   2024-01-01 11:25   1
u1  3   2024-01-01 12:30   2024-01-01 13:00   1
u2  1   2024-01-01 09:00   2024-01-01 09:50   2
u2  2   2024-01-01 10:30   2024-01-01 11:00   1
```

两点引申：① `tentative_end` 之名刻意模仿流式会话"随时可能被延展"的未定态；
② 🔧 实测把 VALUES 按打乱的到达顺序重跑一遍，输出**逐行相同**（`identical: True`）——
批 SQL 只表达"终局归属"，天然到达序无关；而流式会话必须先对未定态窗**提前发射**、
乱序桥接时再**合并重发**，这种"发射-回撤/合并"序列在批语义里根本写不出来。
这一对比正是**为什么流式模型需要 pane/触发/累积三件套**（4.2 难点的显影，🔧 方法说明）。

## 核心概念速览（中英对照）

- **处理时间窗** — processing-time window：以墙钟划定并触发的窗，放弃事件时间正确性
- **会话窗** — session window：逐键、按静默间隔切分、随数据生长的窗
- **静默间隔** — session gap / window duration：断会话的无活动时长
- **窗合并** — window merging：乱序元素桥接相邻会话，流式会话的固有难点
- **自定义开窗** — custom windowing / WindowFn：用户函数决定元素→窗集合映射
- **多窗归属** — element in multiple windows：统一滑动窗复制语义的表达
- **触发器** — triggering：决定 pane 发射时点的 When 策略
- **累积模式** — accumulation：discarding / firing panes / accumulating 三态
- **允许迟到** — allowed lateness：触发后仍接收修正的宽限期（How 的一部分）
- **侧输出** — side output：宽限期外迟到数据的显式落点
- **可重放确定性** — replayable determinism：元素→窗映射须为纯函数，否则不可调试
