# 第 3 章 水位（Watermarks）

> 对应原书 Part I 第 3 章（英文原题 *Watermarks*）。小节目录 ✅ oreilly.com.cn 实抓：
> 3.1 定义 / 3.2 源水位的创建 / 3.3 水位传播 / 3.4 百分位数水位 / 3.5 处理时间水位 / 3.6 案例分析 / 3.7 小结。
> 本文件为精读重构。本章是全书技术核心：水位线是"无界数据上的终点证据"。

## 章定位与中心论题

第 2 章把 When 拆封后立刻遇到悖论：**你不知道"还会不会有更老的数据来"**。
水位线是对这个不可判定问题的**可操作妥协**："我猜测事件时间已推进到 T"，
即宣告"晚于 T 的数据大概不会再来了"——它把批处理免费拥有的"到底了"信号，
变成流式系统中**由源和管道持续维护、可以被违反、违反后果可设计**的一等对象。

## 逐节精读重构

### 3.1 定义

- 时间的三重性（原书在这一节铺陈，⚠️ 与博客 102 同源论述）：
  **墙钟时间**（每台机器一个、会漂、NTP 会跳）、**事件时间**（数据自带，唯一正确基准）、
  **数据处理时间/到达时间**（观察者视角）。**"时钟是万恶之源（多数时候）"**式的论断要求：
  正确性论证一律锚定事件时间，时钟只允许出现在性能与推断里。
- 乱序（out-of-orderness）不是异常而是无界数据的常态；**延迟 = 处理进度 - 事件进度**。
- 定义要点：水位线 W 是**单调不减**的事件时间估计量，W ≥ t 意味着"系统推断事件时间 ≤ t 的数据已（基本）到齐"。
  两个正交参数随之而来：窗口何时**可触发**（W ≥ 窗尾）、迟到数据如何**处置**（第 4 章 allowed lateness）。
- 逻辑水位线（logical watermark，终止标记/分区关闭）vs 近似水位线（heuristic，统计推断）的分野在本节点明。

### 3.2 源水位的创建

- 源的困境：源只看见"到达"，必须从到达序列**反推**事件进度。常用配方 ⚠️（各引擎参数名不同）：
  1. **有界乱序**：W = max(已见事件时间戳) − 允许乱序量（实践中按观测延迟分位数定）；
  2. **分区/分片最小值**：多分区源取各分区水位的 **min** 再合并（分区可能空转，需配 idleness 超时，
     否则整个管道被最闲分区卡死）；
  3. **数据内嵌终止标记**（如"当天最后一条"标志）：最可靠，能造逻辑水位线就别用启发式。
- 原书立场（重构表述）：**能拿到显式信号就不要猜**；猜的时候，参数必须由观测数据分布来定，而非拍脑袋。

### 3.3 水位传播

- 沿 pipeline 传播规则（⚠️ 转述，对照 Beam/Flink 文档语义）：
  **直通算子**（map/filter）原样转发；**多输入算子**（join/union/co-group）取**最小值**——
  输出进度不可能超过最慢输入；**带状态的算子**在转发前须保证已把与该水位相关的水化（flush）完成。
- 由此得到全局单调性：只要每级都遵守传播规则，任意算子看到的 W 都是**下游安全的终点证据**，
  这正是"每个算子可独立决定开窗时机"的正确性基础。

### 3.4 百分位数水位

- 延迟是分布不是常数：用观测延迟的 **P90/P99** 选"允许乱序量"，
  并周期性重估（窗口化统计）。参数权衡：太松 → 结果迟迟不出、状态膨胀；太紧 → 迟到率飙升。
- 原书给出"直方图监控 + 动态调整"的思路（⚠️ 具体实现细节转述）；这与 3.2 的"参数必须观测来定"一脉相承。

### 3.5 处理时间水位

- 处理时间窗同样需要"何时算完"的信号——此时水位线退化为**墙钟定时器**：
  "距窗尾的处理时间到点即触发"。它**不提供任何事件时间正确性**，只在
  "事件时间不可得/不需要"的场合是诚实的选择（衔接第 4 章 4.1）。

### 3.6 案例分析

- ⚠️ 转述：原书以谷歌内部真实管道为蓝本的端到端案例（含多源、乱序、窗口聚合、水位线选型全过程），
  演示"先观察延迟分布 → 定有界乱序参数 → 校验迟到率 → 调整"的闭环方法论；
  本节结论已在 3.2/3.4 重述，故不依赖案例细节即可复现方法论。
  （对照工程版：[../bigdata/07-实时计算与流式架构.md](../bigdata/07-实时计算与流式架构.md) 7.2 节
  "先观测 P99 乱序再定水位"的同一告诫。）

### 3.7 小结

水位线 = **可违反的承诺** + **违反可被设计地吸收**（第 4 章迟到处置）。它不是"精确的进度读数"，
这是所有水位线争论（"迟到算丢还是算对"）的根源性澄清。

## 🔧 概念演示（DuckDB 1.5.5，非真流引擎：批式 SQL 按到达序模拟水位线语义）

**演示 A**：10 分钟滚动窗 + "有界乱序 5 分钟"水位线（W = 到达前缀的最大事件时间戳 − 5min，
用 `max() over (rows unbounded preceding)` + `lag()` 逐步构造），判定每个元素到达时其窗是否已可触发：

```sql
with events(i, ts) as (values (1,timestamptz '2024-01-01 00:01'),(2,timestamptz '2024-01-01 00:06'),
 (3,timestamptz '2024-01-01 00:03'),(4,timestamptz '2024-01-01 00:12'),(5,timestamptz '2024-01-01 00:09'),
 (6,timestamptz '2024-01-01 00:02'),(7,timestamptz '2024-01-01 00:21'),(8,timestamptz '2024-01-01 00:08'),
 (9,timestamptz '2024-01-01 00:33'),(10,timestamptz '2024-01-01 00:04')),
ord as (select *, max(ts) over (order by i rows unbounded preceding) as seen_max from events),
ord2 as (select *, lag(seen_max) over (order by i) as wm_before,
         time_bucket(interval '10' minute, ts) + interval '10' minute as win_end from ord)
select i, ts, win_end, coalesce(wm_before, seen_max) - interval '5' minute as watermark_at_arrival,
       case when coalesce(wm_before, seen_max) - interval '5' minute >= win_end
            then '迟到(窗已触发)' else '准时' end as status
from ord2 order by i;
```

🔧 实测输出（节选，完整见 `D:\develops\tmp\dbwave_ss\demo_out.txt`）：

```text
i=4  ts=00:12  wm=00:01  准时
i=5  ts=00:09  wm=00:07  准时   （乱序到达，但其窗尾 00:10 尚未被水位追过）
i=6  ts=00:02  wm=00:07  准时   （元素时间极老，但窗未触发，仍算"准时入窗"）
i=8  ts=00:08  wm=00:16  迟到(窗已触发)
i=10 ts=00:04  wm=00:28  迟到(窗已触发)
```

关键洞察（即 3.1 的定义在数据上的显影）：**"迟到"相对于窗的触发时刻，而非元素时间戳本身**
（i=6 元素时间极老却"准时"；i=8 只晚了 13 分钟到达却已迟到）。

**演示 G（3.4 百分位水位的定参）**：20 条观测到的到达延迟，取 P90 作有界乱序参数：

```sql
with obs(ingest_lag_min) as (values (0),(1),(2),(2),(3),(5),(8),(1),(0),(4),
 (12),(1),(2),(3),(1),(6),(2),(1),(0),(3)),
q as (select quantile_cont(ingest_lag_min, 0.9) as p90, max(ingest_lag_min) as mx from obs)
select p90 as p90_lag, mx as max_lag,
       count(*) filter (where ingest_lag_min > p90) as would_be_late
from obs cross join q group by p90, mx;
```

🔧 实测：`p90_lag=6.2 | max_lag=12 | would_be_late=2`——选 P90 即接受 2/20 迟到；
选 max 迟到 0 但结果平均多等 12 分钟。这正是 3.4 的权衡数字化。

## 核心概念速览（中英对照）

- **水位线** — watermark：单调不减的事件时间进度估计，"≤T 的数据大概到齐"的承诺
- **有界乱序** — bounded out-of-orderness：W = max(event_ts) − δ 的经典配方
- **最大事件时间戳** — observed key maximum：源反推事件进度的原料
- **空闲检测** — idleness detection：防空分区卡死全局 min 水位的超时机制
- **水位传播** — watermark propagation：多输入取 min、带状态算子先水化后转发
- **逻辑水位线** — logical watermark：来自显式终止标记的可靠版本
- **启发式水位线** — heuristic watermark：来自统计推断的近似版本
- **事件时间** — event time：数据自带时间，正确性唯一锚点
- **处理时间** — processing time：墙钟，仅性能/无事件时间场合可用
- **延迟分布** — lateness distribution：定 δ 的观测依据（P90/P99）
- **迟到元素** — late element：到达时刻晚于其窗触发（相对窗，不相对元素）
- **端到端证据链** — end-to-end progress evidence：源→管道→窗触发的一致性基础

- **Flink 2.x 的水位线修复与语义收紧** ✅：Flink 2.0 发布说明列出"背压/阻塞子任务下水位线空闲超时
  统计不正确（FLINK-35886）"等修复与 `TimeCharacteristic` 移除（✅ https://nightlies.apache.org/flink/
  flink-docs-release-2.3/zh/release-notes/flink-2.0/，200）——3.2 的"idleness 陷阱"在十年后仍是
  真实 bug 来源，印证本章把它列为核心关切的前瞻。
- **水位线思想在湖仓的落地（2024–2026）**：
  - **Paimon Partition Mark Done**：以"分区完成标记"给批/流消费者一个**逻辑水位线**
    （✅ https://paimon.apache.org/docs/master/maintenance/manage-partitions/，200，页内实抓到
    "Partition Mark Done / Streaming Mark Done"章节）——正是 3.2"能拿显式信号就别猜"的存储层实践；

    （✅ https://iceberg.apache.org/docs/latest/flink/ ，200；connector 侧细节 ⚠️ 转述）；
  - **Flink 物化表（Materialized Table）**把"新鲜度"提为一等 DDL 属性——水位/刷新调度的产品化 ⚠️
    （Flink 2.x 文档含 Materialized Table 章节，见上 release-notes 页导航；页面级 URL 404 故不直链）。
- **自适应/ML 水位线**：Beam/Flink 社区均有"按延迟分布自动调 δ"的提案与实现（Dataflow 服务侧的

- **一手论文**：MillWheel（PVLDB 6:1033–1044, 2013，✅ DOI 10.14778/2536222.2536229，PDF ✅ 200）首次把
