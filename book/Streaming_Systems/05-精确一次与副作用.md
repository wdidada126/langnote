# 第 5 章 精确一次及副作用（Exactly Once and Side Effects）

> 本文件为精读重构。本章是"Exactly-once"一词的**去魅与重建**：它不是传输保证，而是端到端结果保证。

## 章定位与中心论题

作者把"精确一次处理（exactly-once processing）"拆成一条流水线上的**多个局部保证**，
并指出真正的难点不在"数据会不会重发"，而在**副作用（side effects）**：
发一次和发两次的邮件、扣一次和扣两次的款，无法靠"重试"变得正确。
全章的解法范式：**让每个输出单元有稳定身份（pane identity），让副作用幂等或可合并，
用持久状态去重，用可合并的累加器吸收重复**。

## 逐节精读重构

### 5.1 为什么精确一次这么重要

- 分布式执行必然失败重放；at-least-once 下"每条数据处理 ≥1 次"，若逻辑非幂等，**结果错误无上限**。
- 术语辨析（本章立论起点）：exactly-once **delivery（传输）几乎不存在也不需要**；
  工程目标恰是"传输 at-least-once（甚至 at-most-once + 补捞），**结果 effectively-once**"。

### 5.2 准确性与完整性

- 正确性 = **准确性（accuracy：算对了）× 完整性（completeness：算全了）**；
  完整性的度量工具正是第 3 章水位线（"何时算全"），准确性要求重复被吸收、迟到被处置（第 4 章机制）。
- 二者不可互相代替：全量重放（完整）若含未完成分区（不准）依然错。

### 5.3 确保在混洗中精确一次

- shuffle 是重放风暴的中心：任务失败 → 上游输出部分重复。原书思路（⚠️ 转述 Beam/Dataflow 实现）：
  shuffle 数据**按 (key, window, pane) 分区落持久存储 + 确认机制**，
  下游只消费"已被完整提交"的 shuffle 分区 → 混洗内部精确一次。

### 5.4 解决确定性

- 即使每元素处理一次，**非确定操作**（随机数、处理时间依赖、乱序到达导致的合并次序）仍破坏可重放等价。
- 去重键的资格讨论（本章精华）：
  - 理想身份 = **元素在数据集中的坐标**（如"第 P 分区第 O 偏移"）——最可靠但依赖源；
  - 退而求其次 = 内容哈希（数据会重复/更新时失效）；
  - 时间戳（受 skew/精度污染，不可靠）。
- 聚合要满足**可合并（mergeable/commutative）**才允许"后写覆盖/并集合并"式去重；
  不可合并的中间态（如任意自定义累加器）需要按 (key,pane) **重算或有序合并**。

### 5.5 性能

- 为精确一次付出的税单：持久化状态、去重簿记、shuffle 提交协议。
- 优化方向（⚠️ 转述）：**只对"非幂等且未去过重"的环节付费**——
  可合并聚合可放宽；有稳定坐标的源可免内容去重；这正是 5.8"使用场景"的前置。

### 5.6 源端的精确一次

- 读侧保证 = **可重放的源 + 可提交的读进度**（位点/游标与作业状态一致性提交 ⚠️ 转述）；
  无界源若无"已读位置"的原子提交，一切下游保证都是空中楼阁。

### 5.7 汇端的精确一次

- 写侧三档（原书框架，⚠️ 转述）：
  1. **幂等写**：天然可重试（按身份 upsert）；
  2. **可合并写**：输出带 pane 身份、汇端做合并（与 5.4 呼应）；
  3. **事务/两阶段提交**：把"提交输出"与"提交状态"绑成一个原子决定；
     代价是端到端延迟被 checkpoint 周期绑架（Flink 2PC sink 的"结果延迟 ≈ 检查点间隔"即此 ⚠️，
     见 [../Stream_Processing_with_Apache_Flink/12-补编-检查点机制与分布式快照.md](../Stream_Processing_with_Apache_Flink/12-补编-检查点机制与分布式快照.md)）。

### 5.8 使用场景

- 何时不需要端到端精确一次：输出幂等（纯 ETL 覆盖写）、业务允许微小重复（先 at-least-once + 下游去重）、
  允许"至少一次 + 人工对账"。**精确一次是设计选择，不是默认美德**——本章最实用的一段。

### 5.9 其他系统

- ⚠️ 转述性对比（书中以 Beam/Dataflow 为主，兼论 Flink/Spark）：
  Flink 走"全局快照（Chandy-Lamport 变体）+ 屏障"路线，Beam 走"存储+去重键+可合并输出"路线，
  两条路线都自称 exactly-once，**付费点不同**（快照 I/O vs shuffle 持久化）。详见姊妹书 12 补编。

### 5.10 小结

端到端精确一次 = 源进度提交 + shuffle 去重 + 确定性执行 + 汇端幂等/事务，四者缺一即降级；
副作用场景优先考虑"重放等价"设计而非机制堆叠。

## 🔧 概念演示：重放造成的 pane 重复，按 (key, pane) 幂等合并（DuckDB，非真流引擎）

模拟：作业崩溃重放后，输出存储里同一 (k, pane) 出现多个版本（attempt 2 为修正后的最新值）。
朴素汇总 vs 去重后汇总：

```sql
with attempts(attempt, k, pane, partial_cnt) as (values
 (1,'u1',1,2),(1,'u1',2,1),(2,'u1',1,2),(2,'u1',2,3),(2,'u1',1,2)),
naive as (select k, sum(partial_cnt) cnt_naive from attempts group by k),
dedup as (select k, pane, arg_max(partial_cnt, attempt) as cnt   -- 后写覆盖=可合并输出
          from attempts group by k, pane),
exact as (select k, sum(cnt) cnt_exact from dedup group by k)
select k, cnt_naive, cnt_exact from naive join exact using (k);
```

🔧 实测：`k=u1 | cnt_naive=10 | cnt_exact=5`。
解读：重复提交使朴素计数翻倍（pane1 两次重复 + pane2 迟到修正被当成新增）；
以 (key, pane) 为身份做"最新覆盖"后回到 5 = 2+3。
**这就是 5.4/5.7 的最小模型**：身份稳定 + 可合并，则重放无害；身份缺失（如 pane 合并致键漂移，
第 4 章 4.2 会话窗）则本章全部技巧失效——两章在此咬合。

## 核心概念速览（中英对照）

- **精确一次处理** — exactly-once processing：结果等效于每元素恰处理一次，非传输承诺
- **有效一次** — effectively-once：at-least-once 传输 + 去重/幂等的结果外观
- **副作用** — side effects：不可重试的外部动作（邮件/扣款/第三方 API）
- **重放等价** — replay equivalence：重放后输出与不重放时不可区分
- **去重键** — dedup key / identity：优先用数据集坐标，慎用哈希与时间戳
- **可合并聚合** — mergeable aggregation：交换幺半群式的累加器要求
- **pane 身份** — pane identity：(key, window, pane) 三元组作为输出单元主键
- **shuffle 持久化** — persistent shuffle：混洗数据落盘+确认换取内部精确一次（⚠️ Dataflow 路线）
- **两阶段提交** — two-phase commit：输出与状态原子绑定提交的汇端方案
- **读进度提交** — reader progress commit：源端精确一次的最小要件
- **准确性×完整性** — accuracy × completeness：正确性的乘法分解
