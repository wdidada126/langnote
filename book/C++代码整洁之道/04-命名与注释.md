## 核心概念速览（中英对照）

- **自解释名称** — Self-Explanatory Name：读者不需外部知识即知用途（4.1.1）
- **领域命名** — Names from the Domain：用业务词汇而非机制词汇（4.1.2）
- **抽象层次匹配** — Appropriate Level of Abstraction：名字的粒度要匹配所在层的抽象（4.1.3）
- **冗余名称** — Redundant Name：`Customer::customerAddress` 式重复上下文（4.1.4）
- **晦涩缩写** — Cryptic Abbreviation：`cnt`、`tmp`、`prevValue` 之类需要口口相传才懂的写法（4.1.5）
- **匈牙利命名法** — Hungarian Notation：`fEnabled`/`nCounter`/`pszName`/`m_nCounter`，把类型编码进名字（4.1.6，本书判为应弃）
- **同名异用** — Same Name for Different Purposes：一处 `value` 多种含义，遮蔽与误用的引信（4.1.7）
- **代码即叙事** — Let the Code Tell a Story：可读性靠结构与命名，而非注释密度（4.2.1）
- **废话注释** — Commenting Obvious Things：`i++; // increment i` 式噪音（4.2.2）
- **注释掉的代码** — Disabled Code：用注释封存"暂时不要"的代码（4.2.3，本书反对：版本控制才是该用的机制）
- **块注释** — Block Comment：`/* … */` 圈起一段代码充当小节标题（4.2.4，解法是抽出函数）
- **有用注释的少数情形** — Rare Cases Where Comments Are Useful：法律头、变更历史、契约文档（Doxygen）、
  特例与算法出处、意图说明（4.2.5）
- **文档注释** — Documentation Comment（Doxygen）：面向 API 使用者的注释，与面向维护者的注释分属两类

## 1. 动机：命名是唯一每天都写的接口

4.1 开篇引用的是 Hal Abelson/Gerald Sussman 那句常被转引的话（"程序是写给人读的，只是顺便让机器执行"）。
作者的论证很 C++：由于**编译器完全不参与命名的语义判断**，命名是少数"工具链帮不了你、只能靠同行评审"的维度——
所以他给了大量正反例（L4-2 坏 / L4-3 好，逐字）：

```cpp
// L4-2 坏名字：num / flag / list / data —— "什么是 data？一切皆数据。"
unsigned int num;  bool flag;  std::vector<Customer> list;  Product data;
// L4-3 好名字
unsigned int numberOfArticles;  bool isChanged;  std::vector<Customer> customers;  Product orderedProduct;
```

同时他用 L4-4（`totalNumberOfCustomerEntriesWithMangledAddressInformation`）挡住另一个方向：**长不等于好**，
L4-5 进一步演示"过度冗长的命名造成的命名混沌"。判据不是长度，而是**信息密度与上下文匹配度**。

## 2. 机制：七条命名规则的可操作形态

| 规则 | 反例（本书或等价） | 正例 | 机器可查吗 |
| --- | --- | --- | --- |
| 自解释 | `d`, `tmp` | `elapsedDays` | 部分（clang-tidy `readability-identifier-length`，⚠️ 文档口径） |
| 领域词汇 | `handleData()` | `reserveCar()`（L4-7 用例控制器） | 否，需评审 |
| 抽象层次匹配 | 高层流程里出现 `fread` | 高层只见 `loadInventory()` | 否 |
| 不重复上下文 | `Customer::customerName` | `Customer::name`（L4-6/L4-8） | 部分（命名检查项可禁前后缀） |
| 不用晦涩缩写 | `addrObj`、`cntMgr` | `address`、`count` | 部分（术语表 + 评审） |
| 弃匈牙利/前缀 | `m_nCounter`、`pszName` | `counter`、`name`（成员用 `name_` 后缀可选） | **是**：`readability-identifier-naming` 直接锁死 |
| 一名一用 | 内外层都叫 `value` | 内层改名 `iterationValue` | **是**：`-Wshadow`（见下实测） |

**4.2 注释机制**同样给出可执行分界：注释的"合法户口"只有五处（L4-15 分类小标题注释、L4-16 许可证头、
L4-17 文件内变更历史、L4-18/L4-19 Doxygen 技术视角与业务视角两种契约注释、以及"特例/算法来源说明"）。
除此之外，**注释的出现即为信号：要么改名，要么抽函数**。

作者还专门用了两个 Apache OpenOffice 3.4.1 的真实代码摘录（L4-1、L4-20）作为"反面教材来自工业现场"的证据——
这个选择值得学：**评审材料里放一个大家都用的开源项目的真实片段，比放同事的代码更不伤感情**。

## 🔧 实测：把"同名异用"变成编译期诊断

`-Wall -Wextra -Wshadow` 下，4.1.7 的隐患不再靠人眼。**已实测 g++ 15.2**：

```text
n1_naming.cpp:14:14: warning: declaration of 'value' shadows a previous local [-Wshadow]
   14 |     int totalWith(int value) const { return value_ + value; }
n1_naming.cpp:11:9: note: shadowed declaration is here
运行输出：
totalWith(5) = 105（本意是含税额，实际是 105）
  循环内 value=0 遮蔽外层 100
  循环内 value=1 遮蔽外层 100
```

要点：程序"跑对了"，但**语义完全靠运气**——形参 `value` 与外层 `value`、成员 `value_` 三者在同一作用域里
互相遮蔽，这正是 4.1.7 说的"同一名称用于不同目的"。把 `-Wshadow -Werror` 加进 CI，规则就从"品味"变成"门槛"。

## 3. 权衡：这一章的规则在哪里会失灵

- **命名长度 vs 编辑器补全**：短名在好的 IDE 里成本很低，长名在深层嵌套里造成右侧不可见。作者的取舍是
  "作用域越大、名字越长"（现代通行判据，与 4.1.3 精神一致）。
- **匈牙利前缀的辩护与反驳**：辩护方（主要是 COM/Win32 遗产）主张接口文档缺失时前缀是唯一类型线索；
  反驳方是本书：C++ 有 `auto`、有 IDE、有模板，类型前缀不仅冗余而且**会撒谎**（`m_nCounter` 改成 `long` 就名不副实）。
  真实结论：前缀类匈牙利在现代 C++ 已无席位，但**成员标记**（`name_` 后缀或 `m_` 前缀）作为"作用域提示"仍有团队在用——
  这是风格问题（第 1 章 1.6.4 的停战协议），不是整洁问题。
- **注释 vs 文档**：Doxygen 注释写给"不读源码的人"，因此**删掉它会有真实用户受损**；行内解释性注释写给"读源码的人"，
  删掉它通常只说明代码该改。判据：**注释的消费者是谁**。
- **注释掉的代码**：作者坚决反对（4.2.3），理由是版本控制已提供该功能。今天的补充反驳：保留被禁代码块 +
  说明"为什么不要"有时优于静默删除（例如为将来的性能权衡留证据）——但**必须写理由**，否则退化为噪音。

## 4. 相邻概念对比

| 概念对 | 差别 | 为什么容易混 |
| --- | --- | --- |
| 命名 vs 术语表（ubiquitous language） | 命名是局部手艺，领域词汇表是团队契约（4.1.2 的实质） | 只纠名字不建词汇表 → 同类概念在不同模块各叫各的 |
| 好名字 vs 长名字 | 目标是"零查询可懂"，长度只是手段 | 看到 `numberOfXxx` 就一路加词，产出 L4-4 式怪物 |
| 文档注释 vs 说明性注释 | 前者描述契约（参数/返回/异常/线程安全），后者解释为什么 | 用文档注释补代码的意图不清，等于把债转给读者 |
| 块注释 vs 函数抽取 | 块注释分隔"小节"；抽函数给小节命名 | 抽函数会引入调用开销的顾虑在 -O2 下基本消失（第 3 章实测） |
| `-Wshadow` vs `readability-*` | 编译器抓**遮蔽**（可能造成 bug），tidy 抓**风格**（不会造成 bug） | 两者都叫"静态检查"，但只有前者能作为门禁证据 |

## 最新演进与工业实践

- **语言演进对位**：C++20/23 之后，命名的负担部分转移给了**类型与约束**：`using Meter = Quantity<1,0,0>` 这类富类型
  （见 [07-编译器搭档-UB-TypeRich与库.md](07-编译器搭档-UB-TypeRich与库.md)）让名字不必携带单位；
  concepts（C++20）让模板参数名可以携带契约（`template<Iterator It>` 优于 `template<typename T>`）；
  C++23 `std::print`/`std::format`（wg21.link/P2093，实测标题 *Formatted output*）让"格式串"成为可检查字面量，
  减少了历史上靠注释解释 `%.2f` 的需要。
- **clang-format / clang-tidy 接管风格层**：`readability-identifier-naming` 可为类/函数/变量/成员/常量分别设定
  前后缀与大小写风格（现代工程把 4.1.6 直接写成配置），`readability-implicit-bool-conversion`、
  `misc-confusable-identifiers`（同形异源 Unicode 字符）是本书规则之外的新增风险。
  ⚠️ 本机未安装，规则名按上游文档口径。
- **cppcheck**：`--enable=style,warning` 提供 `shadowVariable`、`unusedVariable`、`knownConditionTrueFalse` 等，
  在没有 clang-tidy 的环境里是最低成本门禁（⚠️ 本机未安装，未实测）。
- **工业仓库对位**：Google C++ Style 与 abseil 指南都采用"成员后缀 `x_`、无类型前缀、常量 `kCamelCase`"
  ——即**保留作用域提示、抛弃类型提示**，与本书立场一致；Boost 社区则更宽松（`boost::` 命名空间即上下文）。
  fmt 库是"命名即接口"的正面样本：`format_to`/`formatted_size` 一眼分辨输出目标与返回物。
- **测试生态**：4.1.2 的领域命名在测试里收益最大——Catch2 允许自然语句
  `TEST_CASE("a book that is already borrowed cannot be borrowed twice")`，
  几乎逐字对应本书 L2-2 那批 `BookInventoryTest::aBookThatIsAlreadyBorrowedCanNotBeBorrowedTwice`。
