## 核心概念速览（中英对照）

- **安全网** — Safety Net：由自动化测试构成的改动保护层；名字来自高空作业——它不防止你犯错，只防止你摔死
- **测试金字塔** — testing pyramid（本书未用此名，实质相同）：以大量单元测试为底、少量端到端为顶的成本结构
- **单元测试** — Unit Test：自动化、隔离、快速、可重复、无人值守执行的验证
- **测试代码是一等公民** — Test Code Quality（2.5.1）：测试代码必须与产品代码同等（甚至更高）质量
- **测试命名** — Unit Test Naming（2.5.2）：`SUT_Condition_Expectation` 式命名，或直接把需求写进测试名
- **测试独立性** — Unit Test Independence（2.5.3）：任意顺序、单独执行、结果一致
- **一个测试一个断言** — One Assertion per Test（2.5.4）：一个测试只允许一个失败原因
- **独立初始化测试环境** — Independent Initialization of Unit Test Environments（2.5.5）：夹具自建自清，不共享可变状态
- **不测 getter/setter** — Exclude Getters and Setters（2.5.6）：无逻辑的存取器不值得测
- **不测第三方代码** — Exclude Third-Party Code（2.5.7）：库的正确性由库负责
- **不测外部系统** — Exclude External Systems（2.5.8）：网络/文件系统/时钟不进单元测试
- **数据库怎么办** — And What Do We Do with the Database?（2.5.9）：把访问抽象成接口，测试时用替身
- **测试代码与产品代码分离** — Don't Mix Test Code with Production Code（2.5.10）：不把测试钩子焊进生产类
- **测试必须快** — Tests Must Run Fast（2.5.11）：慢测试被跳过，被跳过的测试等于没有
- **测试替身** — Test Doubles / Fake Objects（2.5.12）：fake、stub、mock、spy——用确定性替身换掉真实依赖

## 1. 动机：测试不是"验证写对了"，而是"敢于改"

本章紧跟第 1 章的熵论，给出第一个可执行机制：没有安全网，童子军原则就是自杀——**没人敢在没测的代码上重构**。
作者的真实立场（2.1）是：测试的必要性来自"功能增加会引入回归"这一经验事实，并搬出 1962 年 NASA Mariner 1
事故作反面教材（原版该节即以 Mariner 为开场侧栏）。QA（2.4）不能替代开发者自测：手工 QA 发现缺陷的成本曲线
决定了"晚发现=贵"。

## 2. 机制：十二条规则的因果结构

十二条规则不是并列清单，而是三组：

**A. 质量与可读（2.5.1–2.5.2）**
测试代码是文档、也是会被改的资产。命名的两种风格原版给了成串例子（L2-1/L2-2，逐字）：

```cpp
void CustomerCacheTest::cacheIsEmpty_addElement_sizeIsOne();
void MoneyTest::givenTwoMoneyObjectsWithDifferentBalance_theInequalityComparison_Works();
void UserAccountTest::creatingNewAccountWithExistingEmailAddressThrowsException();   // 需求直接进名
void ChessEngineTest::aCastlingIsNotAllowedIfInvolvedKingHasBeenMovedBefore();
void HeaterControlTest::ifWaterTemperatureIsGreaterThan92DegTurnHeaterOff();
```

**B. 结构与隔离（2.5.3–2.5.5）**
`One Assertion per Test` 一节给出原版最有争议的对照（L2-3 vs L2-4）：同一个 `Money` 比较运算，
把所有断言塞进一个测试里，作者列出两条反对理由——**早断言失败会掩盖后续错误**、**失败原因多=诊断成本高**。
2.5.5 要求夹具在 setup 里重建全部状态，杜绝跨测试污染。

**C. 边界与速度（2.5.6–2.5.12）**
排除 getters/setters、第三方、外部系统，把数据库/服务藏在接口后面（L2-9 抽象 `CurrencyConverter` 接口 →
L2-10 真实实现 → L2-11 Test Double → L2-12/2-13 使用方只依赖抽象 → L2-14 装配点注入）。
**这一串清单就是第 9 章依赖注入模式在第 2 章的预告**：本书的 DI 不是"架构洁癖"，而是"让测试能跑"的直接推论。

## 3. 权衡：规则的代价与失效场景

- "一个测试一个断言"在 C++ 上会被**浮点比较**咬一口：断言本身写得再克制，`==` 仍会因表示误差误报。
  🔧 已实测 g++ 15.2：`100 × 1.10` 在 double 上的真实值是 `110.00000000000001`，因此
  `inv.amountIn("USD") == 110.0` 这条单断言测试**必然失败**，而带容差的断言通过——见下节输出。
  教训：规则管结构，不管数值语义；钱的问题交给第 12 章 Money 类（整数分）。
- "不测 getter/setter"的前提是**真的无逻辑**；带不变式维护的 setter（校验、单位换算、脏标记）必须测。
- "测试要快"与"隔离要彻底"冲突：每测试新建夹具=更多构造成本。原书选择快与净；现代工程通常再加一层
  "测试套件分层"（单测毫秒级、集成秒级、端到端分钟级）。

## 🔧 实测：夹具独立 + 测试替身 + 单断言的真实输出

自写最小框架（无外部依赖）复刻 L2-9…L2-14 骨架；`g++ -std=gnu++17 -Wall -Wextra` 零告警编译，
**已实测 g++ 15.2**：

```text
[ FAIL ] InvoiceTest_amountIn_KnownRate_ReturnsConvertedAmount  (裸 == 比较 double)
[ PASS ] InvoiceTest_amountIn_KnownRate_WithTolerance_...  (带容差 -> 通过)
         实际值 = 110.00000000000001   与 110.0 相等? false
[ PASS ] InvoiceTest_amountIn_UnknownCurrency_ReturnsZero
[ PASS ] InvoiceTest_amountIn_CalledTwice_FakeSeesTwoCalls
[ PASS ] InvoiceTest_twoFixtures_ShareNothing  (2.5.3 独立性)
4 passed, 1 failed; fixture 实例化次数=6（每个测试一个）
```

三条事实被这段输出钉住：①测试替身让 `Invoice` 在无网络下可测；②夹具每个测试独立构造（`built=6`，含修复用例）；
③单断言规则本身不救浮点——它只让**失败原因唯一化**，从而让人一眼看到是"比较方式错了"而不是"逻辑错了"。

## 4. 相邻概念对比

| 概念对 | 差别 | 混用后果 |
| --- | --- | --- |
| Fake vs Stub vs Mock vs Spy | fake 有可用的简化实现（本书 `CurrencyConverter` 替身）；stub 只回预设值；spy 记录调用；mock 断言交互 | 术语混用导致团队对"这个测试到底在验什么"理解不一 |
| 单元测试 vs 组件/集成测试 | 单元=单个类的行为，替身切断一切外部依赖；集成=真实装配 | 把集成测试写成单测 → 慢、脆、跳过（违反 2.5.11） |
| 一个断言 vs 一个测试目标 | 断言数不等于目标数：`assertThat(x).isConvertedToRomanNumeral("IV")` 一条即够 | 用断言数量当 KPI，产出上千个"只测 getter"的噪音测试 |
| 测试命名风格 A（SUT_Cond_Exp） vs 风格 B（需求句） | A 便于定位代码，B 便于追溯需求（本书两者并列，见 L2-1/L2-2） | 混用不统一 → 报告难读，需求覆盖无从统计 |
| 测试覆盖率 vs 安全网强度 | 覆盖率衡量"被执行"，不衡量"被断言" | 追求高覆盖率的团队常有 90% 覆盖、0% 保护 |

## 最新演进与工业实践

- **框架对位（本书用 Google Test，见第 8 章 L8-6/L8-16 输出截图）**：
  - **GoogleTest**：`TEST/TEST_F/EXPECT_*`、夹具、参数化、`MATCHER`；仍是企业内默认选项，CMake 集成用 `gtest_discover_tests`。
  - **Catch2**（头文件式，`TEST_CASE("...","[tag]")` + `REQUIRE`）：**断言表达式本身即文档**，与本书"自解释"精神最契合；
    Catch3 转为非纯头文件并支持 `SCENARIO`/分区。
  - **doctest**：编译更快的轻量选择，适合被测试驱动的库工程。
  - **std::expected 时代的新写法（C++23）**：`CHECK(expectedValue.has_value())` 之类的交互可用 `value_or`+容差断言替代；
    对不可失败函数写"负例测试"的冲动可下降（见 [08-异常与错误处理.md](08-异常与错误处理.md)）。
- **clang-tidy / cppcheck 对测试层的接管**：⚠️ 本机未装，规则名按上游文档口径：
  `modernize-avoid-c-arrays`（测试里的 C 数组）、`cppcoreguidelines-pro-bounds-pointer-arithmetic`、
  `google-readability-todo`（无主 TODO）；cppcheck `--enable=warning,style,unusedFunction` 可查测试夹具里未使用变量。
  更有效的是**在 CI 里强制 `-Wshadow -Wall -Wextra -Werror`**，本书 2.5.1"测试代码同等质量"立刻可执行。
- **工业仓库对照**：abseil 风格指南明确要求"单元测试不得依赖执行顺序"（对应 2.5.3/2.5.5），
  并提供 `absl::` 内的确定性随机/时钟工具；GSL（Microsoft Guidelines Support Library）的 `Expects/Ensures`
  让 5.7.1"防患于未然"与"测试契约"共用一套谓词。
- **测试速度工程化**：现代做法是把"必须快"从美德变成机制——测试分片（ctest `-R` + 并行 `--parallel`）、
  Bazel/CI 级测试选择（只跑受影响目标）、以及本书未预料的：GoogleTest 的 `--gtest_shuffle` 主动暴露顺序耦合，
  把 2.5.3 变成可验证属性而非口号。
- **数据库/时钟/文件系统**：2.5.9 的"接口 + 替身"在今天有三条成熟路线——内存实现（SQLite `:memory:`）、
  fake 时钟（`std::chrono` 抽象层 / absl `FakeClock`）、`std::filesystem` 测试沙箱（C++17 起可用，见
  [../C++17完全指南/10-filesystem.md](../C++17完全指南/10-filesystem.md)）。
