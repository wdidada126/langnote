## 核心概念速览（中英对照）

- **防患于未然** — Prevention Is Better Than Aftercare：先用契约/前置条件把非法输入挡在门外，异常是最后手段（5.7.1）
- **异常即异常（字面义）** — An Exception Is an Exception — Literally!：异常只表达"例外情形"，不做流程控制（5.7.2）
- **快速退出** — If You Can't Recover, Get Out Quickly：无法恢复就让它传播到能恢复处，或直接终止（5.7.3）
- **用户自定义异常类型** — User-Specific Exception Types：从 `std::exception`/`std::runtime_error` 派生并携带上下文（5.7.4，L5-27 `DivisionByZero`）
- **值抛出** — Throw by Value：`throw MyError(...)`，由运行时负责拷贝与生命周期（5.7.5）
- **常量引用捕获** — Catch by `const` Reference：`catch (const MyError& e)`——避免切片、避免悬垂、避免不必要的拷贝争议（5.7.5）
- **catch 顺序** — Correct Order of Catch-Clauses：派生类在前、基类在后，否则永远到不了（5.7.6，L5-28）
- **异常层级** — Exception Hierarchy：`logic_error`/`runtime_error` 两大分支 + 领域子类；不要拿标准异常当业务类型用
- **栈展开** — Stack Unwinding：抛出时逆序析构局部对象——RAII 之所以是异常安全的地基
- **零成本异常模型** — Zero-Cost（Table-Driven）EH：`try` 块本身无运行期插桩，成本在体积与抛出路径（本目录补充）
- **`noexcept`** — 不抛承诺：参与容器搬移策略与终止语义（本目录补充，原书仅涉及 C++11 规范面）
- **可失败函数** — Fallible Function：可能失败的函数；其返回值类型选择（异常/`optional`/`expected`/错误码）是本节的现代焦点
- **错误码** — Error Code / `std::error_code`：跨边界、无栈展开需求的错误通道（C++11 `<system_error>`）
- **`std::expected<T,E>`** — C++23：把"成功值或失败原因"写进返回类型，由调用方强制处理（本目录对位补充）

## 1. 动机：错误处理是"整洁"最难伪装的地方

第 4 章的命名与函数规则可以让烂代码看起来体面，**错误处理不行**：路径覆盖是否完整，直接暴露在崩溃日志里。
作者给出的三条主张彼此咬合：

1. 5.7.1：**绝大多数错误不该以异常出场**，而应在函数入口用契约拦下（前置校验、参数验证）——这与 GSL 的
   `Expects` 与本书 5.4（别留 UB）同源。
2. 5.7.2：**异常名不副实是设计病灶**。用异常表达"用户输入了非法日期"这类**可预期结果**，
   等于把控制流藏进运行时，测试与性能都付双倍成本（"异常慢"的真相见下）。
3. 5.7.3：**恢复点唯一**。捕获发生在"知道该怎么办"的层，其余层一律不捕获——
   `catch(...)` 只放在 `main()`/线程入口这类最后的边界。

## 2. 机制：六条规则的实现细节

**类型设计（5.7.4）**：自定义异常应携带**诊断上下文**（文件名、行号、字段名），否则捕获端只能拿到一句 `what()`。
L5-27 的 `DivisionByZero` 即为此例。层级上从 `std::runtime_error`/`std::logic_error` 派生，
让"只捕标准基类"的老代码仍能兜住。

**抛出与捕获形式（5.7.5）**：
- 抛值：`throw ParseError("app.cfg", 42, "missing key 'port'")`——运行时负责把对象搬到展开安全的存储；
- 捕 `const&`：`catch (const ParseError& e)`。抛引用会切片（捕获端 `typeid` 立刻暴露），捕值可能拷贝大对象，
  捕**非 const 引用**则与"异常对象只读"的直觉冲突且难以绑定临时量。

**顺序（5.7.6）**：`catch (const std::exception&)` 写在前面会吞掉后面所有分支——而且**这不是运行期 bug，
编译器可以直接判决**（实测见下）。

**与 RAII 的咬合**：栈展开只析构**已构造完成**的局部对象。因此"裸 `new` + 后续抛异常"= 泄漏；
这正是 [06-资源管理-RAII智能指针与Move.md](06-资源管理-RAII智能指针与Move.md) 排在前面讲的原因。

## 🔧 实测（已实测 g++ 15.2，`-std=gnu++17 -Wall -Wextra`）

**(1) 自定义异常携带上下文 + 值抛常捕 + 顺序问题**：

```text
  契约拒绝: i=-1
caught ParseError: what=missing key 'port' file=app.cfg line=42 typeinfo=10ParseError
基类先捕获(顺序不佳): boom
抛出前
兜底捕获，程序继续
sizeof(ParseError)=56
```

`typeinfo=10ParseError` 证明**抛值/捕 `const&` 不丢派生类型**（无切片）；`file`/`line` 字段完好传递，
这就是 5.7.4 的"携带上下文"能兑现的东西。同时编译器给出：

```text
warning: exception of type 'ParseError' will be caught by earlier handler [-Wexceptions]
```

**(2) catch 顺序颠倒的诊断（另一份最小样本）**：

```text
warning: exception of type 'std::runtime_error' will be caught by earlier handler [-Wexceptions]
```

`-Wexceptions` 是 GCC/Clang 的默认家族成员，`-Werror` 后即是硬门禁——**5.7.6 从今天起不必靠人眼评审**。

**(3) C++23 `std::expected`：把"可失败"写进签名。** 复刻同一条解析函数，错误用领域枚举而非异常
（`-std=gnu++23 -Wall -Wextra`，实测通过）：

```text
42                     -> ok    42
-7                     -> ok    -7
1x                     -> err   code=0
                       -> err   code=2
99999999999999999999   -> err   code=1
value_or 兜底: money_of("abc")=0, money_of("25")=25
sizeof(expected<int,ParseIssue>)=8  sizeof(optional<int>)=8
```

三点值得记住：①**`std::expected` 在 C++17 下直接不可用**，GCC 15 的判决很明确：
`error: 'expected' in namespace 'std' does not name a template type` + `note: 'std::expected' is only available from C++23 onwards`；
②第一版我把"有尾随字符"错报成 `std::errc{}`，运行结果打出 `err: No error`——**用 errc 当错误类型时必须避免
`errc::success` 出现在 error 分支**，这是 `expected` 的经典自伤（上面 code=0 那行是同族坑的第二形态，注意空串与
尾随字符都映射到了 code 0/2 的枚举顺序上）；③`sizeof` 与 `optional<int>` 同为 8 字节，
**类型富化在这里是免费的**。

## 3. 权衡：异常 vs 错误码 vs `expected`

| 维度 | 异常 | 返回码/`errno` | `std::expected<T,E>` |
| --- | --- | --- | --- |
| 可忽略性 | 不可忽略（忘 `catch` 就终止） | 极易忽略 | 可忽略但 `value()` 前必须判；`value_or` 提供显式默认 |
| 携带上下文 | 强（对象字段） | 弱（一个整数） | 强（`E` 可为结构体） |
| 对 RAII 的压力 | 依赖栈展开（需要纪律） | 无展开 | 无展开 |
| 性能 | 抛出路径贵（含分配），`try` 本身近乎免费（零成本模型） | 最省 | 与返回值同价，`sizeof` 实测 8 |
| 跨边界（C ABI/线程/信号） | 不宜跨越 | 适合 | 适合（POD 化 `E`） |
| 无异常环境（嵌入式/MISRA/`-fno-exceptions`） | 不可用 | 可用 | 可用 |
| 测试 | `EXPECT_THROW` 类断言 | 断言返回值 | 断言 `has_value()`/`error()` |

作者的判据（"异常即异常"）与今天的工业分布高度一致：**构造失败与不变式破坏用异常；
可预期的业务失败用类型（`optional`/`expected`）；跨语言/跨进程边界用错误码**。

## 4. 相邻概念对比

| 概念对 | 差别 | 为什么容易混 |
| --- | --- | --- |
| `logic_error` vs `runtime_error` | 前者=程序 bug（调用方错，如越界索引），后者=运行环境意外（文件不存在） | 二者的正确处置不同：bug 应尽早崩溃，意外应恢复/重试；混用则监控与告警全部失真 |
| `assert` vs 契约 vs 异常 | `assert` 只在调试版生效（`NDEBUG` 后消失）；契约（`Expects`）可配置；异常是可捕获对象 | 用 `assert` 校验**外部输入**是经典事故（发布版校验直接蒸发） |
| `std::optional<T>` vs `expected<T,E>` | optional 只说"没有值"，不说为什么 | 需要向用户解释失败原因时 optional 会逼你把错误塞进日志或输出参数 |
| 异常规范 `throw(A,B)` vs `noexcept` | 前者是运行期检查的动态规范，**C++17 已移除**（`-std=c++17` 下编译失败）；后者是编译期可查询的承诺 | 老代码里 `throw()` 仍会出现，语义由 `noexcept` 接替 |
| `terminate()` vs 崩溃 | `terminate` 是标准定义的"无人可恢复"出口，可安装处理器 | 把 `catch(...)` 当"防崩溃"手段，等于用异常机制关掉自己的诊断能力 |
| 零成本异常 vs "异常很慢" | `try` 无插桩（表驱动），成本集中在抛出（含字符串分配、展开） | 用"异常慢"来为返回码辩护，常常打错了对象：慢的是**抛出**，不是**加 try** |

## 最新演进与工业实践

- **提案对位（本文件实测引用）**：`std::expected` = wg21.link/P0323（R12，标题实测 *std::expected*）→ C++23；
  动态异常规范移除 = P0003（本目录不重复核标题，结论按 C++17 移除口径使用）。
- **C++26 方向**：reflection/metadata（wg21.link/P2996 一类工作）不会改变错误处理格局；
  更相关的是 **`std::execution`（senders/receivers）** 把"异步失败通道"标准化——异步链路上的异常传播至今是空白，
  ⚠️ 该提案号未在本目录内逐一复核，只作方向性提示。
- **`noexcept` 的现代权重**：C++17/20 之后，标准容器对"移动是否 `noexcept`"的依赖更深（vector 扩容策略）、
  ranges/协程帧析构也假定不抛；本书 5.7 未展开，今天必须把它当作错误处理的一部分：**要么 `noexcept` 要么别承诺可恢复**。
- **clang-tidy / 编译器门禁**：`bugprone-exception-escape`（函数可能抛出却没出口）、`performance-trivially-destructible`、
  `modernize-use-noexcept`、`readability-redundant-*`；GCC `-Wexceptions`（实测）、Clang `-Wcatch-value`
  （捕值时的拷贝告警，`-Wcatch-value=3` 可覆盖全部）。⚠️ 规则名按上游文档口径。
- **工业仓库**：
  - **fmt**：`FMT_THROW` 只在解析/格式错误处使用，IO 层错误码不抛——"异常仅例外"的教科书分布。
  - **abseil**：**明确禁用异常**（风格指南规定不用 `throw`/`catch`，改用 `absl::Status`/`absl::StatusOr<T>`），
    是 `expected` 路线的工业化先例；`StatusOr` 的 API 形状（`ok()`/`value()`/`status()`）几乎就是 `std::expected` 的前身。
  - **LLVM**：`llvm::Error`/`Expected<T>` 同理，并配 `llvm::errs()` 报告。
  - **GSL**：`Expects/Ensures` 承担 5.7.1 的"预防"，`fail_fast` 承担不可恢复路径。
- **测试生态**：GoogleTest `EXPECT_THROW/ASSERT_THROW/EXPECT_NO_THROW`；Catch2 `REQUIRE_THROWS_AS(expr, Type)` 与
  `REQUIRE_THROWS_WITH(..., "message")` 可把"上下文是否携带"写成断言；`std::expected` 风格则用
  `CHECK(result.has_value())` + `CHECK(result.error() == Code::X)`。异常层级一旦建起来，
  测试端要断言**具体类型**，否则"抛了个 `std::exception`"也能通过。
