## 核心概念速览（中英对照）

- **设计原则 vs 模式 vs 惯用法** — Principle / Pattern / Idiom：方向性律条 / 语境化的重复解法 / 单语言定型句式，抽象度递减（9.1、9.3）
- **依赖注入** — Dependency Injection（DI）：把协作对象的创建权交出去，构造/设置/接口三式（9.2.1）
- **适配器模式** — Adapter：把既有接口翻译成客户端要的接口，类版靠继承、对象版靠组合（9.2.2）
- **策略模式** — Strategy：算法族可互换；C++ 里降级为函数对象/lambda/模板参数（9.2.3）
- **命令与命令处理器** — Command / Command Processor：请求对象化以支持排队与撤销；处理器持撤销栈（9.2.4–9.2.5）
- **组合模式** — Composite：叶与容器同一接口，树形统一处理（9.2.6）
- **观察者模式** — Observer：主题通知注册表；C++ 无 GC，悬挂订阅者是要命问题（9.2.7）
- **工厂模式** — Factory：封装创建逻辑与依赖装配，把 `new` 集中到一处（9.2.8）
- **门面模式** — Facade：子系统之上的单一简洁入口（9.2.9）
- **金额类** — Money Class：钱的值类型——整数分存储、不可变、运算返回新值（9.2.10，回应 02 章浮点事故）
- **特例对象/空对象** — Special Case Object / Null Object：用行为完备的替身消灭判空与 if 塔（9.2.11）
- **不可变类** — Immutable Class：构造后状态不变——天然线程安全、可作 Map 键（9.3）
- **替换失败并非错误** — SFINAE：模板候选不适用只是"出局"，不是编译错误；探测技法的引擎（9.3）
- **拷贝-交换** — Copy-and-Swap：一个值参 `operator=` 同时兑现强异常安全与自赋值安全（9.3）
- **指向实现的指针** — PIMPL：外壳类只持 `unique_ptr<Impl>`，切断编译依赖（9.3）

## 1. 动机：为什么这章要把 GoF"写薄"

作者对模式的态度是 03 章 KISS 的延续：**模式是词汇不是蓝图**。9.1 明确区分三个层级——
原则（09 章）告诉你"往哪走"，模式告诉你"这类问题长这样"，惯用法（idiom）只在一个语言里成立。
C++ 的特殊性在于：GoF 的多数创建型/结构型模式在这个语言里**要么被标准库吸收**
（Strategy→`<algorithm>` 参数，Prototype→拷贝构造），**要么被语言特性溶解**（Adapter→ranges 适配器）。
本章挑的 11 个模式全部是"在 C++ 里仍需人手写"的；9.3 的 5 个惯用法则是"不写进类型系统就会翻车"的句式。

## 2. 机制：十一个模式与五个惯用法的 C++ 读法

**DI（9.2.1）**：类只声明"我需要什么抽象"（引用/`unique_ptr` 成员），由组合根注入实现——
它是 6.3.7 DIP 的操作化，也是 02 章测试替身能进场的通道；寿命规则：注入引用不持有、
注入 `unique_ptr` 独占、共享才用 `shared_ptr`（接 06 章）。
**Adapter（9.2.2）**：对象版（持有被适配者+转发）优先于类版（继承+转发），后者多重继承易造脆皮。
**Strategy（9.2.3）**：书里保留接口+派生类的教科书写法，但当场承认 C++ 可用 `std::function`/模板参数
免掉继承树——本章 9.2 唯一"预告自己退化"的模式。
**Command+处理器（9.2.4–9.2.5）**：`execute()/undo()` 对；处理器管调度与撤销栈——值语义化现代写法是
`std::function` 对或 ranges 的 view（可序列化需求仍在）。
**Composite（9.2.6）**：09 章实测的 `BundledSale` 就是它——`vector<unique_ptr<Sellable>>` 同时解决所有权与统一接口。
**Observer（9.2.7）**：主题侧弱引用表（`vector<weak_ptr<Observer>>`）或订阅 RAII 句柄自动退订，
二选一才能不留悬挂；这是 C++ 与 Java/C# 事件模型最大的落差处。
**Factory（9.2.8）**：把"造哪个类+装配哪些依赖"从业务代码剥离；现代替代是函数返回+CTAD。
**Facade（9.2.9）**：入口对象别长成第二个上帝类——门面只做翻译与编排。
**Money（9.2.10）**：整数分 + 全 const 成员 + 运算返回新值；同币种校验放构造/运算前置（02 章
`0.1+0.2` 事故的处方）。**特例对象（9.2.11）**：给"缺失/未知"配一个行为完备的替身对象
（⚠️ 书中原型示例类名未二次核对），调用端 `if (x != nullptr)` 全体退场（Tell Don't Ask 的近亲）。
**五惯用法（9.3）**：Include Guard（`#ifndef/#define/#endif`；机制与实测在 13 章收束）；
Immutability（数据成员 const + 方法全 const，Money 的地基）；SFINAE（`enable_if` 重载集探测，
C++20 起让位 concepts，报错对比实测见下）；Copy-and-Swap（`operator=(T other) { swap(*this, other); return *this; }`
——拷贝发生在"提交点"之前，抛了就什么都没变）；PIMPL（前置声明 `struct Impl`，头文件零实现细节）。

## 🔧 实测（已实测 g++ 15.2）

**(1) Copy-and-Swap 的强异常保证**（`-std=gnu++17 -Wall -Wextra`）——构造新 `Buffer` 中途抛出，
赋值对象纹丝不动；自赋值因"先拷贝后交换"天然安全：

```text
caught: build failed: too big
assignment failed, b.size() still 3 (strong guarantee)
self-assign ok, size=3
```

**(2) PIMPL 的析构点坑**：`Widget` 只有 `std::unique_ptr<Impl>` 成员且**不在类外析构处给出**
`~Widget()` 声明时，隐式析构在使用点实例化，`-std=gnu++17 -fsyntax-only` 判决（06 章预告过的报错）：

```text
error: invalid application of 'sizeof' to incomplete type 'Widget::Impl'
```

把 `~Widget();` 声明进类、在 Impl 完整处 `= default` 定义后，同目录样本编译运行通过（`label=pimpl-hidden`）。

**(3) SFINAE → concepts 的诊断进化**（同一约束两种写法，故意用 `double` 实参触发）：
`enable_if` 版（`-std=gnu++17`）与 `std::integral` 版（`-std=gnu++20`）都报
`error: no matching function for call to 'gcd_(double, double)'`，但候选签名分别是——

```text
candidate 1: 'template<class T> typename std::enable_if<std::is_integral<_Tp>::value, T>::type gcd_(T, T)'
candidate 1: 'template<class T>  requires  integral<T> T gcd_(T, T)'   ← 附注 constraints not satisfied
```

一行之差就是 9.3 该节的历史使命终结说明：**探测的活 SFINAE 干得一样好，说人话的活只有 concepts 会**。

## 3. 权衡：模式该写、该买、还是该删

| 模式 | 手写价值 | C++ 现代替代 | 判据 |
| --- | --- | --- | --- |
| DI/Adapter/Command/Observer | 高（跨模块边界） | 无完全等价 | 边界处保留 |
| Strategy | 中 | lambda/模板参数 | 单方法接口≈可调用对象就别建类 |
| Composite | 高（真树形域） | 递归值类型可替 | 无共同基类的同构域用 `std::variant` |
| Factory | 中 | `make_*`+CTAD | 构造本身复杂才值得 |
| Facade | 中 | namespace/模块 | 纯转发的门面是空壳税 |
| Money/Special Case | 高（领域正确性） | 强别称可部分替代（接 07 章） | 涉及钱与缺失值必写 |

惯用法一侧：Copy-and-Swap 的成本是"多一次拷贝"（移动可用时几乎免费）；PIMPL 的成本是一次堆分配+指针间接，
换来的是**编译依赖斩断**——对外 API 与 ABI 稳定场景值回票价，内部小类纯属负资产（详见
[../大规模C++程序设计/05-编译防火墙：隔离技术.md](../大规模C++程序设计/05-编译防火墙：隔离技术.md) 的量化视角）。

## 4. 相邻概念对比

| 概念对 | 差别 | 为什么容易混 |
| --- | --- | --- |
| 模式 vs 惯用法 | 模式语言无关、要讲语境（"何时用"）；惯用法是单语言的定型句式（RAII、PIMPL） | 都叫"最佳实践"；后果是把 Java 的 DI 容器思路硬搬进 C++ |
| 依赖倒置 vs 依赖注入 | DIP 是 09 章原则（依赖抽象），DI 是其注入技法之一（还有工厂/服务定位） | 简历圈常把 DI 框架当 DIP 本体，框架反而制造新依赖 |
| Observer vs 信号槽 | 信号槽是 Observer 的框架化方言；Qt 用元对象系统解决悬挂，标准 C++ 无槽概念 | 手写 Observer 时"谁退订"问题被反复重发明 |
| Null Object vs `optional` | 前者给"缺失"配真行为对象，调用端零判空；后者把缺失放进类型，强制调用端处理 | 都是处理"没有"，但一个消灭分支、一个暴露分支——选哪个取决于行为可否多态化 |
| PIMPL vs 模块 | 都切断编译依赖：PIMPL 靠指针+分离翻译，`import` 靠语言级编译产物 | modules 出现前 PIMPL 是唯一平民方案；今天按工具链成熟度选 |
| Money vs 强别称 `Money` | 别称只解决"米×2≠秒"的混用；Money 还管舍入规则、同币种运算、不变式 | 07 章 Type-Rich 与本章模式对同一问题的两层答案 |
