## 核心概念速览（中英对照）

- **普通单元测试之弊** — Plain Old Unit Testing（POUT）：代码写完再补测试——只能验证"已写的"，无法追问"该写的"（8.1）
- **测试驱动开发** — Test-Driven Development（TDD）：测试先行，让失败测试充当设计的驱动引擎（8.2）
- **红-绿-重构** — Red-Green-Refactor：先写恰好失败的测试（红），写最小实现让它通过（绿），再在绿灯保护下整理（重构）
- **测试即规格** — Tests as Specification：通过行为的测试就是需求的可执行表述
- **代码道场** — Code Kata：以反复练习定式动作内化技法——本章道场题为整数→罗马数字转换（8.2.2）
- **涌现设计** — Emergent Design：不预先画类图，让接口在测试压力下自然成形（8.2/8.3）
- **三角验证** — Triangulation：用更多测试样例逼出泛化实现，反对为单个样例写特判（本章补充）
- **最小实现** — Simplest Code That Passes：绿色阶段的纪律——不多写一行未被测试要求的功能（YAGNI 的执行形态）
- **安全网** — Safety Net：TDD 是"构建安全网"（02 章）的运行时序版：网先于楼
- **可测性即设计信号** — Testability as Design Feedback：难以先写测试，说明耦合或静态状态出了问题（8.3 要义）

## 1. 动机：后补测试为什么救不了设计

8.1 的指控很具体：POUT 时代（先码后测）的测试有四重失真——
**覆盖面失真**（只测得完"已经写出来的路径"，未实现的行为根本没进测试清单）、
**体量失真**（大函数拆不动就凑合不测）、**顺序失真**（测试沦为收尾工序被排期挤掉）、
**心理失真**（"我的代码是对的"成见先入为主）。作者点破因果方向：测试的最大价值不在验证，
而在**约束设计**——一个你现在就写不出通过测试的行为，就不该在重构后的代码里实现它。
这与 02 章十二条规则的关系：02 讲"好测试长什么样"（静态规范），08 讲"测试什么时候写"（动态流程）；
TDD 是规则的最佳执行时机。

## 2. 机制：红-绿-重构与罗马数字的九轮道场

**流程（8.2.1）**：三条铁律式节奏——(a) 先写失败测试（编译失败/断言失败都算红）；
(b) 实现只求快绿，允许丑；(c) 绿光下重构，消除本轮欠下的重复。循环粒度以分钟计。
**道场题（8.2.2）**：`convertIntToRoman(int)`，定义域 1..3999。原书的迭代节拍（00 口径：共九轮；
⚠️ 配套仓库 `clean-cpp/book-samples` 已失效，逐轮切分无法二次核对）本质是一条泛化链：

1. `1→"I"`：硬编码返回——绿灯但毫无泛型；
2. `2→"II"`、`3→"III"`：测试逼出重复拼接；
3. `4→"IV"`：天真贪心给出 `IIII`，**红**——减法式记数法是被测试"发现"的需求，不是被想出来的；
4. `5/9/10`：符号表扩位，`VIIII` 再红；
5. `14/40/49`：`XIIII`、`XXXX` 又红——每次红都在教"罗马数字的语法是查表而非算位"；
6. 重构轮：把 13 组 `(值,符号)` 表驱动化，贪心循环统一处理减法式对；
7. 收尾轮：边界守卫（0 与 4000 抛 `std::out_of_range`，接 5.7.1 的契约先于异常）。

**关键观察**：若从 `1955→MCMLV` 这类综合样例起手，人会直接写"千位百位十位个位各查一张表"的
四段式实现；而按红绿节奏走，表驱动结构是**被逼出来的唯一活路**——这就是"涌现设计"的可复现证据。
**优势清单（8.3）**：永不过期的测试文档、内建 YAGNI（没有失败测试就没有功能）、
重构信心（02 的安全网从"事后补"变"随身长"）、可测性反馈（写不出测试=09 章 6.3.7/6.3.11 的违例报警）。
**适用边界（8.4）**：原型/探索代码（方向未定，测试会先错）、纯表现层胶水与硬件时序类代码（需先建边界，
见 14 章 Main 与测试边界）——作者的诚实话术：TDD 是设计工具不是 QA 替代品，它不产出集成测试与性能测试。

## 🔧 实测（已实测 g++ 15.2，`-std=gnu++17 -Wall -Wextra`）

自写微型断言宏 `EXPECT_EQ`（无框架依赖，语义同 `ASSERT_EQ`），同一套 10 条测试分别跑
"天真贪心 v1"与"减法式表驱动 v2"：

```text
--- roman_v1 ---
FAIL line 36: got [IIII] want [IV]
FAIL line 37: got [VIIII] want [IX]
FAIL line 38: got [XIIII] want [XIV]
FAIL line 39: got [XXXX] want [XL]
FAIL line 40: got [XXXXVIIII] want [XLIX]
FAIL line 41: got [MDCCCCLV] want [MCMLV]
FAIL line 42: got [MDCCCCLXXXX] want [MCMXC]
FAIL line 43: got [MMXXIIII] want [MMXXIV]
RESULT RED  : 2/10 passed, 8 failed
--- roman_v2 ---
RESULT GREEN: 10/10 passed, 0 failed
边界: roman: 1..3999
```

三点现场感：①v1 通过的 2 条恰是"无减法参与"的 `1/3`——红的分布本身就是需求地图；
②v2 的改动只往表里加了 `{900,"CM"}…{4,"IV"}` 五个条目、循环一行未动——绿灯下的重构才敢这么改；
③末行边界消息来自 `throw std::out_of_range`，测试端用 `EXPECT_THROW` 类断言即可收编（接 08 章）。
真实项目建议直接上 GoogleTest/Catch2；这里的裸宏只为展示"红绿的信号与框架无关"。

## 3. 权衡：TDD 的成本清单与回本线

| 成本 | 表现 | 缓解 |
| --- | --- | --- |
| 前置投入 | 每循环写两份代码（测试+实现） | 单元越小回本越快；纯函数类任务几乎立回（本章即例） |
| 测试债 | 断言过细→实现一动全红（脆弱测试） | 断行为不断实现（02 章 2.5.4 单断言的动机） |
| 心智切换 | 从"写功能"切到"想让功能如何被调用" | 先画调用点伪代码再落测试，把切换成本一次性付清 |
| 不适配区 | UI/并发时序/外部系统 | 用 12 章 DI 把可测核挖出来，胶水层豁免 |

回本线判断：**改动频率 × 缺陷代价**。图书馆式领域逻辑（钱、税率、状态机）回本极快；
一次性脚本走 TDD 纯属自虐——这正是 8.4 存在的意义。

## 4. 相邻概念对比

| 概念对 | 差别 | 为什么容易混 |
| --- | --- | --- |
| TDD vs "先写测试"（test-first） | TDD 强调**细粒度循环**与"由测试驱动接口"；笼统的 test-first 可以是大段设计稿 | 面试口径常把两者画等号，丢失了"每次只写一个失败测试"的约束力 |
| TDD vs BDD | BDD 把测试语言换成业务语言（Given/When/Then），驱动的是行为规格；TDD 驱动单元接口 | 都反 POUT，阵营就容易被当成同一派 |
| 红-绿-重构 vs 写-测-修 | 前者"红"是**计划内**的需求探针，后者"测试失败"是事故 | 没经历过计划内红灯的人，会把 TDD 当成"更快的调试" |
| Code Kata vs 刷题 | Kata 要求**重复同一定式直至无意识**并计时/去框架化；刷题求新题覆盖 | 罗马数字题"无聊"恰是其价值：注意力全在流程上 |
| TDD 测试 vs 02 章单元测试 | 同一工件；02 是验收标准，08 是施工进度表 | 分开读容易以为两套测试，实为一体两面 |

## 最新演进与工业实践

- **框架换代**：原书用 GoogleTest 口径；今天 Catch2（单头文件、BDD 宏）与 doctest（更快编译）是 C++
  道场的低摩擦首选——`TEST_CASE/REQUIRE` 的粒度天然贴合红绿循环。⚠️ 版本特性以各自仓库为准。
- **性质测试（Property-Based Testing）是 Kata 的机械化续篇**：给定生成器与不变式自动灌样例
  （罗马数字往返转换"roman→int 应还原"即标准性质），C++ 侧有 QuickCheck 血统的库如
  RapidCheck/fastcheck ⚠️（第三方项目，本目录未逐一核档）。它把"三角验证"从纪律变成机器。
- **变异测试（Mutation Testing）为 TDD 的断言质量兜底**：往实现里注入 bug（`>=` 改 `>`），
  看测试是否变红——红绿循环养出的测试集第一次有了"及格线"度量；C++ 工具如 Mull ⚠️（未核档）。
- **错误路径的现代红利**：TDD 写纯函数 + `std::expected` 返回（08 章对位表），失败分支
  天然只是一条普通断言，不需要 `EXPECT_THROW` 的仪式——C++23 后红绿循环在错误处理上更便宜。
- **CI 语境**：细粒度红绿=细粒度提交，与"小批量集成"的现代 CI 哲学同构；童子军原则（03 章 3.10）
  的"顺手重构"在 TDD 仓库里由绿灯授权，而非评审授权。
