## 3.1 官方摘要：本章是"从要不要换"到"换过去要改什么"的相变点

摘要关键句逐拆（✅）：

- "With no showstoppers found with MariaDB" —— Ch.2 的评估结论：没有一票否决项；
- "evaluating both database and application code for migration to arrive at a **feasible plan**" ——
  对象是**两类资产**：schema/PL-SQL 与宿主应用代码；
- 点名三大工作量源（LOE, Level of Effort）："**mapping data types**、**database code changes**、
  and **rewrites for PL SQL**, and of course **sequences**"——
  作者特意用 "and of course sequences" 收尾：对 Oracle 老用户，序列是**默认存在**的对象，
  换库时它的"有无"问题比性能问题更早爆炸。

## 3.2 Oracle→MariaDB 对象映射表（⚠️ 依摘要点名项 + 官方文档重构）

| Oracle 资产 | MariaDB 落点（2019 基线 10.3/10.4） | 2026 现状 | 取证 |
| --- | --- | --- | --- |
| SEQUENCE 对象 | MariaDB 原生序列（10.3 起 InnoDB 持久化实现；更早为 SEQUENCE 引擎），支持 `NEXT VALUE FOR`/`NEXTVAL`/`SETVAL` Oracle 风味语法 | 仍在主线（docs "Sequence Overview" ✅ 实抓） | ✅ mariadb.com/docs/server/reference/sql-structure/sequences/sequence-overview |
| MySQL 侧对照 | **无序列对象**（双方言分叉样本，🔧B 演示其"支持度分化"性格） | 8.4/9.x 仍无原生 CREATE SEQUENCE ⚠️ | ✅ 兼容性页语境 + 反查未见放出 |
| PL/SQL 包（PACKAGE） | 无对等物：包需拆平为存储过程/函数/会话变量 | 无变化 ⚠️ | ⚠️ MariaDB 无 Oracle 式包（反查缺口登记：官方页未见支持声明） |
| PL/SQL 过程/函数 | MariaDB 存储过程语法子集可承接，游标/异常处理差异逐库过 | 同左 | ⚠️ |
| NUMBER/VARCHAR2/DATE/CLOB | DECIMAL/VARCHAR/DATETIME/LONGTEXT 一类映射；DATE 语义（Oracle 带时分秒）需专门对齐 | 同左；JSON 路径新增（🔧A） | ⚠️ 类型映射细则原书应有（两级目录未放出），本表为通识重构 |
| ROWNUM/分析函数 | 10.2 起窗口函数齐备 | 10.x/11.x 持续演进 | ⚠️（版本级细节未取一手页） |
| 同义词/DB Link | 无对等；CONNECT 引擎可部分替代联邦需求（🔧D 见 05 章） | 同左 | ⚠️ + ✅ kb 页可达（JS 渲染，句子级未抓） |

本章剩余篇幅演示探针长什么样（🔧 组即探针的 SQLite/DuckDB 化身）。

## 3.3 🔧 A 组：JSON——"TEXT 别名 + CHECK"与"原生类型"的两种性格

**被类比对象（✅ MariaDB 官方兼容性页原话）**："MariaDB follows the SQL standard and stores the
JSON as a normal TEXT/BLOB"——MariaDB 的 `JSON` 是 `LONGTEXT` 别名；MySQL 8 则是二进制打包类型。
本机无法装 MariaDB，用两态各取一端做**行为学对照（非 MariaDB 行为）**：

```sql
-- SQLite 3.45.3：模拟"别名+约束"路线
CREATE TABLE logs(id INTEGER PRIMARY KEY, payload TEXT CHECK(json_valid(payload)));
INSERT INTO logs(payload) VALUES('{"k": [1,2,3]}');   -- OK
SELECT typeof(payload) FROM logs;                      -- => 'text'
SELECT json_extract(payload,'$.k[1]') FROM logs;       -- => 2
INSERT INTO logs(payload) VALUES('not-json');
-- => CHECK constraint failed: json_valid(payload)

-- DuckDB 1.5.5：模拟"原生类型"路线
CREATE TABLE logs(id INTEGER, payload JSON);
INSERT INTO logs VALUES(1,'{"k": [1,2,3]}');
SELECT typeof(payload) FROM logs;                      -- => 'JSON'
SELECT payload->>'$.k[1]' FROM logs;                   -- => 2
INSERT INTO logs VALUES(2,'not-json');
-- => Conversion Error: Malformed JSON at byte 0 of input: invalid literal
```

**读法**：两条路线都能拒非法值，但**错误发生在栈的不同层**（约束引擎 vs 类型转换），
存储类别一个 `text` 一个 `JSON`——对位到 MariaDB：`JSON` 列永远可以塞进通过不了
`json_valid()` 的旧数据（别名不强制校验，除非你手写 CHECK ⚠️），
所以"迁 MySQL 8 JSON 列到 MariaDB"要**自带校验约束**，这正是摘要里 "mapping data types" 的活体样本。

## 3.4 🔧 B 组：SEQUENCE——同名特性在方言里的"有/无"分化

**被类比对象（✅）**：MariaDB 序列文档页实抓——序列"generate a sequence of numeric values"，
支持 `NEXTVAL`/`SETVAL` 等 Oracle 风味函数；MySQL 无对应对象（✅ 兼容性页语境 + ⚠️ 反查）。
本机对照（非 MariaDB 行为）：

```sql
-- DuckDB 1.5.5
CREATE SEQUENCE s START 100;
SELECT nextval('s');  -- => 100
SELECT nextval('s');  -- => 101
SELECT nextval('s');  -- => 102

-- SQLite 3.45.3
CREATE SEQUENCE s;            -- => near "SEQUENCE": syntax error
SELECT nextval('s');          -- => no such function: nextval
```

**读法**：Oracle→MariaDB 的序列改写之所以在摘要里被 "of course" 强调，是因为**两侧都有、
语义还不尽同**（如 Oracle 的 `CURRVAL` 会话语义）；而"一侧有一侧无"（本实验）更凶险——
应用层会拿到语法错误而不是行为差异。迁移 LOE 评估时两类要分开计数 ⚠️。

## 3.5 🔧 C 组：生成列/虚拟列——语法兼容≠行为兼容

**被类比对象**：MariaDB 虚拟列远早于 MySQL（5.2 vs 8.0.13 ⚠️ 版本级转述；kb 页
virtual-columns ✅ 可达但内容 JS 渲染未抓句）。本机三态（非 MariaDB 行为）：

```sql
-- SQLite 3.45.3：VIRTUAL 与 STORED 双支持
CREATE TABLE t(a INTEGER,
  b INTEGER GENERATED ALWAYS AS (a*2) VIRTUAL,
  c INTEGER GENERATED ALWAYS AS (a+1) STORED);
INSERT INTO t(a) VALUES(21);       -- SELECT a,b,c => (21, 42, 22)
UPDATE t SET b=99;                 -- => cannot UPDATE generated column "b"

-- DuckDB 1.5.5：默认形态可建，显式关键字反而分裂
CREATE TABLE t2(a INTEGER, b INTEGER GENERATED ALWAYS AS (a*2));
INSERT INTO t2(a) VALUES(21);      -- => (21, 42)
CREATE TABLE t3(a INTEGER, b INTEGER AS (a*2) STORED);
-- => Invalid Input Error: Can not create a STORED generated column!
```

**读法**：三家对 `GENERATED ALWAYS AS` 的接受度互不成子集——**照抄 DDL 的迁移在
"看起来都支持"的特性上翻车，比在明确不支持的特性上更隐蔽**（报错文案三家各异的实测样本已在上）。

## 核心概念速览（中英对照）

- **工作量估算** — LOE (Level of Effort)：按对象类别清点的改写工时，本章摘要三大件=类型映射/PL-SQL 重写/序列
- **数据类型映射** — Data Type Mapping：NUMBER→DECIMAL、CLOB→LONGTEXT 一类跨库翻译表 ⚠️
- **序列** — Sequence：MariaDB 原生对象（✅ 文档实抓），MySQL 长期缺席，Oracle 迁移者肌肉记忆
- **PL/SQL 包拆平** — Package Flattening：Oracle PACKAGE 无对等物时的结构降级策略 ⚠️
- **JSON 别名路线** — JSON-as-TEXT Alias：MariaDB 的 SQL 标准式实现（✅ 官方原话），区别于 MySQL 二进制类型
- **CHECK 约束** — CHECK Constraint：SQLite 与"别名路线"共用的拒错机制（🔧A 实测）
- **生成列** — Generated Column：VIRTUAL/STORED 两态（🔧C 实测三方言互非子集）
- **语法兼容≠行为兼容** — Syntax Parity ≠ Semantics Parity：🔧C 的一句话结论
- **探针式评估** — Probe-Driven Assessment：每个映射断言配一个可执行验证（本章方法论）
- **方言位点** — Dialect Touchpoint：应用代码中按 `SHOW PROCESSLIST` 之类差异分叉的位置 ⚠️

## 最新演进与工业实践

- **MySQL 8.x 侧到 2026 仍无 CREATE SEQUENCE**（⚠️ 反查 Refman 8.4 未见放出）；MariaDB 序列持续为主线
  （10.3 起 InnoDB 持久化实现 ⚠️ 版本细节转述；docs 序列族页面 ✅ 200 且可 WebFetch）；
- **JSON 双路线的当代放大**：MySQL 8 的 JSON 表函数/部分更新与 MariaDB 的别名+函数族各自演进，
  跨库 JSON 中间件（CDC/ETL）至今按"文本+校验"最保守口径处理 ⚠️ 转述；
- **Oracle→开源迁移工具链 2024–2026**：云厂商与第三方出现 Oracle→MySQL/PG 的 schema 转换器
  （AWS SCT/DMS 线 ⚠️ 未取一手页）；本书的"人工对象盘点+探针"方法在异构迁移中仍不被替代——
  工具输出仍需逐条验收；
- **生成列进入所有主流方言后的新分叉**：SQLite(3.31+)/DuckDB 的实测互非子集（🔧C）提示：
  跨库 ORM 的 DDL 生成分支仍是活跃工程问题（对位工业件：SQLAlchemy dialect 层 ⚠️ 常识项）；
