# 02 · DW 2.0 总览与八大构件（原书第 2 章，pp.23–54 ✅）

> 精读重构册。依据：Elsevier 官方书页 TOC「2. DW 2.0 – an overview; the components」✅ + Crossref 页码区间 23–54 ✅。「八大构件」清单源自 @@IN@@ 2005 年前后在 DBTA（Database Trends and Applications）发表的 DW 2.0 宣言文（盘外通说，⚠️ 转述），本章给出其图书版展开 ⚠️。

## 一、章定位

第 2 章是全书**宪法**：32 页篇幅（23–54，本册单章最长之一 ✅ 页距可算）同时干两件事——给出 DW 2.0 的总纲叙事（为什么存在一个"2.0"）与逐一定义构件清单。后续第 3–15 章基本是把本章条目逐项放大。读法上本章≈BDW 的四特征定义章在"下一代"语境的复刻：@@IN@@ 再次用**列举式立法**，这次立的是八条。

## 二、精读札记

### 2.1 总纲：DW 2.0 是什么（✅ 书页简介佐证 + ⚠️ 展开）

Elsevier 书页官方简介（✅ 实抓原句要义）："the first book on the new generation of data warehouse architecture... describes the future of data warehousing that is technologically possible today, at both an architectural level and technology level"，视角"from the top down"。三点解读：

1. **不是愿景文学**：作者强调"today 技术上已可行"——2005 年语境下指的是关系引擎成熟、存储降价、元数据/ETL 工具商品化，无需等待未来科技。
2. **架构级+技术级双层**：先给空间架构（第 3 章四分区），再给技术底座要求（第 5 章流动性）——这个"先图后件"的次序就是全书骨架。
3. **对既有资产的三问**（书页简介原设 ✅）：what lies ahead / what can be salvaged from the current system / how to justify the expense——分别对应本册 02-03（ ahead）、11 迁移章（salvage）、11 成本节（justify）。

### 2.2 八大构件逐条（⚠️ 宣言文通说 + 本册按章归位）

| # | 构件（英文原标） | 一句话教义 | 展开章（本册文件） |
|---|---|---|---|
| 1 | current detail + historically variant data | 存当前明细 + 历史时变数据，1NF 原子级，as-of 可答 | 08（时变结构）、10（粒度） |
| 2 | integrated | 一套环境统一企业数据，与运维数据可整合 | 03（integrated sector）、09（连通性） |
| 3 | shared | 所有应用共享同一份企业数据视图 | 03、13（记录系统） |
| 4 | virtual | 用户经虚拟层访问，物理拓扑对消费者透明 | 05（流动性）、09（连通性） |
| 5 | always open | 永远在线可装载可查，无停机装载窗口 | 05、14（运维） |
| 6 | distributed | 访问分布式下沉到用户端/应用端 | 03（near-line）、09 |
| 7 | paradigm shift | 从"项目制"到"应用资产管理制"的管理范式迁移 | 06（方法论）、14（管理） |
| 8 | technology | 拥抱新技术谱系：并行、列存雏形、对象关系、挖掘内置等 | 05 |

### 2.3 「1.5」的位置：跳代论的技术细节（⚠️ 推定）

同期 @@IN@@ 公开文章还描述了过渡态 DW 1.5（在一代库里加装时变/元数据补丁）。图书版第 2 章与第 16 章（迁移，pp.261–270 ✅）合读可知其立场：1.5 是给重仓使用者的止血带，**新建一律直奔 2.0**——这是"2.0"版本号修辞的攻击性所在：让停在 1.5 显得像用 Windows 98。盘上对位：Data Vault 2.0（[../Data_Vault_2_0/00-总览与阅读地图.md](../Data_Vault_2_0/00-总览与阅读地图.md)）后来居上借了同一套"跳代"话术。

### 2.4 谁该听这部宪法（✅ 书页 Readership 实抓）

官方读者画像：data architects、DBA、系统设计与开发、知识管理——注意**没有业务分析师位置**：DW 2.0 从立书上就是"给建仓人"的架构法典，不是用仓手册。这与 @@RK@@ 系"从用户角度建模"的口吻构成深层分野（08/10 章再战）。

## 三、主题深读：八构件的内在逻辑链

八条不是并列清单，而是一条依赖链：**构件 1（时变明细）是数据本体论**，其余皆为其服务——要答 as-of 查询就必须集成（2）且共享（3）；集成环境要活下来必须技术流动（5、8）；流动环境要用户无感必须虚拟化（4）；无感访问天然分布式（6）；这套节拍无法用瀑布项目管理（7）。因此批评者攻击 DW 2.0"是愿望清单不是架构"时，@@IN@@ 的防御是：架构（第 3 章四分区）已经把清单空间化了。本目录认为这条攻防链恰好是 2026 年"湖仓到底是架构还是营销"论战的 2005 预演——裁判席参照盘上 [../Practical_Lakehouse_Architecture/01-湖仓架构简介.md](../Practical_Lakehouse_Architecture/01-湖仓架构简介.md) 对"湖仓是名词还是形容词"的同样挣扎。

## 四、原书 → 2026 对位

| 构件（2005 语言） | 2026 兑现形态 | 判定 |
|---|---|---|
| 时变明细 + 历史 | Iceberg/Delta 时间旅行、SCD2 主流化、湖仓 bronze 层保留全史 | 兑现（方式未点名）|
| 集成/共享 | "单一事实来源"让位于 mesh 域契约与 catalog 治理；企业级共享仍是卖点 | 半兑现 |
| 虚拟 | 数据虚拟化产品（AtScale/Dremio 类）没能成为中枢，但**视图/动态表/物化视图**把"虚拟"以 SQL 层实现了 | 兑现变形 |
| 常开 | 流式摄取 + zero-downtime 云仓运维 | 兑现 |
| 分布式 | 读写分离自动伸缩取代手工分布 | 兑现 |
| 范式迁移 | DataOps/平台工程 = "项目制→产品制"的当代措辞 | 兑现（迟到十年）|
| 新技术 | 列存/向量化执行（本机 🔧 即用 DuckDB 列存引擎类比）成为默认而非选配 | 兑现 |

## 最新演进与工业实践

- **构件清单的长寿**：2026 任何一份湖仓厂商能力对照表（时间旅行、开放表格式、ACID、CDC 摄取、存算分离、按量伸缩）逐格回看，几乎都能在八构件表找到 2005 原型——本册判定"七条兑现、一条半兑现"，是工业社会对宣言最厚的回礼。
- **未兑现的暗线**：「共享/集成」在 2026 遭遇反向运动：mesh 论断言大环境共享不可规模化（盘上 [../Data_Mesh/00-总览与阅读地图.md](../Data_Mesh/00-总览与阅读地图.md)，波内兄弟域目录在盘 ✅），与八构件中的 2、3 正面相撞；这场架是 @@IN@@-@@RK@@ 古战场的继承者辈分。
- **本机 🔧 类比（非本书引擎/平台行为）**：用 DuckDB 1.5.5 建 200 行订单事实表并按 status 聚合（confirmed 合计 5615.21，脚本登记于 [06-方法论与统计探查处理.md](06-方法论与统计探查处理.md)）——"current detail"一格的当代最小演示：列存引擎上明细与聚合同库共存，as-of/过滤皆 SQL 直答，印证构件 1+8 的技术可行性叙事。
- **实践建议（2026 口径）**：把八构件当**尽调 checklist** 用于平台选型（每格问"你的时间旅行/常开/虚拟层长什么样"），比当信仰清单更有用；对"paradigm shift"一格可延伸问组织：数据团队是项目制还是平台产品制。
