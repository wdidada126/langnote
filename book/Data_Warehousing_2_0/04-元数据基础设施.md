# 04 · 元数据基础设施（原书第 4 章，pp.95–110 ✅）

> 精读重构册。依据：Elsevier 官方书页 TOC「4. The metadata infrastructure; enterprise metadata; business metadata; technical metadata」✅ + Crossref 页码区间 95–110 ✅。三类元数据的命名即官方章题（✅ 级），章内论证顺序为 ⚠️ 按框架重构。

## 一、章定位

16 页（95–110 ✅）谈一件事：**元数据从"文档"升格为"基础设施"**。一代数仓里元数据是附属品（字典文档、事后登记）；DW 2.0 把它写成承重墙——四分区（03 章）之间的迁徙规则、粒度管理器（10 章）的路由判断、时变查询（08 章）的版本解析、安全（08 章）的权限映射，全部以元数据为运行时输入。"infrastructure"这个词在章题里不是修辞。

## 二、精读札记：三层元数据（✅ 层名）

### 2.1 企业元数据 Enterprise metadata

- 记什么：企业数据资产的名录与所有权——有哪些主题域、哪个部门是权威源、数据在组织中的法定身份。
- 2005 落地形态（⚠️ 推定）：中央元数据库表 + 人工登记流程。
- 一句话本质：**治理层的元数据**，回答"谁的数据、算不算数"。

### 2.2 业务元数据 Business metadata

- 记什么：业务口径——指标定义（"收入=已确认订单金额合计"）、单位、同义词、报表项到物理列的语义映射。
- 服务对象：业务用户与分析师的可信消费；@@IN@@ 立场（⚠️ 推定延续 BDW 口径）：口径必须中央登记，集市侧不得私定义。
- 一句话本质：**语义层的元数据**，回答"这个词什么意思"。

### 2.3 技术元数据 Technical metadata

- 记什么：物理事实——源系统→目标表列映射、转换规则、装载频率、血缘边、分区位置。
- 服务对象：ETL（09 章）、监控（07 章）、性能（10 章）的机器可读依据。
- 一句话本质：**工程层的元数据**，回答"数据怎么来的、现在躺在哪"。

### 2.4 三层的合流点：章题为何顺序是"企业→业务→技术"

自上而下的登记顺序（⚠️ 推定论证）：先定所有权，再定口径，最后才能钉物理映射——反向工程（先扫库再补业务含义）正是一代元数据烂尾的死法。此顺序与第 2 章书页自述 "from the top down" ✅ 同构：@@IN@@ 的元数据方法论是他整体方法论的缩影。

## 三、主题深读：作为"运行时组件"的元数据

一代与二代对元数据的根本分歧在**执行语义**：

| 对比项 | 一代（文档） | DW 2.0（基础设施） |
|---|---|---|
| 消费者 | 人（翻字典） | 程序（装载器/路由器/审计器实时查询元数据） |
| 更新时机 | 项目里程碑后补登 | 与 DDL/ETL 变更同事务提交 |
| 失效后果 | 文档过期，库照跑 | 迁徙/路由/权限当场失灵 |
| 存储位置 | Word/Excel/独立字典库 | 环境内数据库表，可 SQL 联查 |

最后一行给了本机 🔧 的可复现切片（**非本书引擎/平台行为**，DuckDB 1.5.5 实跑 ✅）：建三张元数据表并按实体名联查——

- meta_enterprise：`revenue → finance_dept`（企业层：归属）
- meta_business：`revenue → 已确认订单金额合计 / CNY`（业务层：口径+单位）
- meta_technical：`revenue → sales_detail / sum(amt) where status=confirmed`（技术层：源表+变换）
- 三表 JOIN 一次返回完整档案行 `('revenue', 'finance_dept', '已确认订单金额合计', 'sum(amt) where status=confirmed')`——"三层合流可查询"的最小证明；把它换成 information_schema + 独立 catalog 服务即 2026 形态。

## 四、原书 → 2026 对位

| 原书三层 | 2026 词表 | 态 |
|---|---|---|
| 企业元数据 | Data Catalog 的 ownership/domain 字段（Polaris/Glue/Purview 类 ⚠️） | 兑现且产品化 |
| 业务元数据 | 语义层/指标层（metrics layer、dbt exposures、YAML 契约文件） | 兑现（形态换：从登记制到代码评审制） |
| 技术元数据 | 自动血缘（查询解析器采集，openlineage 规范 ⚠️） | **超额兑现**：无需人工登记，引擎自吐 |
| 「基础设施=环境内表」 | 元数据本身入湖成表（catalog 的 catalog），可 join 可版本化 | 兑现 |
| 自上而下登记顺序 | 被血缘自动采集反向击穿：先有物理事实再推断语义——@@IN@@ 顺序论 2026 属理想主义 | 部分落空 |

## 最新演进与工业实践

- **兑现总评**：本章是 DW 2.0 里被 2026 工业界**照单全收且加了杠杆**的一章——三层分工至今是每张 catalog 产品功能矩阵的隐藏骨架；升级点在于采集方式（人工登记→运行时自动捕获）与消费方式（翻字典→API/SQL 直查）。
- **产业面（⚠️ 转述，不可本机实测云产品）**：开放目录栈（Polaris/Unity Catalog/Glue 一线，盘上有 Apache_Polaris_TDG 与 Data_Governance_with_Unity_Catalog 两目录版可续 ✅）把"企业元数据"做成了跨引擎权限面；血缘协议（openlineage 类）把"技术元数据"做成了事件流。
- **落空与反噬**：业务口径的中央登记制在 2026 让位于"指标定义进代码仓库 + PR 评审"——口径漂移没有消失，只是漂移速度从"季度"变"周"，审计面反而更难；@@IN@@ 顺序论的教训是：**治理强度要匹配变更频率**，2005 的静态环境假设不再成立。
- **实践清单（2026）**：① 给每个核心指标建"三层合一"档案行（本 🔧 的三表可折叠成一张宽表/一个 YAML）；② 血缘采集下沉引擎层，禁止人工承诺；③ 目录所有权与权限系统对账自动化。
