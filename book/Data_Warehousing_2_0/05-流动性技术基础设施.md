# 05 · 流动性技术基础设施（原书第 5 章，pp.111–122 ✅）

> 精读重构册。依据：Elsevier 官方书页 TOC「5. Creating the fluid technological infrastructure for DW 2.0 - the underlying technology approach - the separation of static and temporal data」✅ + Crossref 页码区间 111–122 ✅。两个官方小节题（基础技术路线/静态与时变数据分离）即本章骨架（✅ 级）。

## 一、章定位

"fluid（流动）"是 DW 2.0 最容易被读丢、也最被 2026 追认的一个形容词。第 4 章的元数据要流动、第 3 章的四区数据要流动、第 2 章的"always open"要成立——技术底座必须先满足一组反一代属性：**结构可改、介质可换、版本可升、负载可分**。本章两条官方路线：底层技术选择论（the underlying technology approach）与静态-时变分离论（separation of static and temporal data）。

## 二、精读札记

### 2.1 基础技术路线（✅ 小节题 + ⚠️ 内容重构）

@@IN@@ 2005 年对"底座 DBMS/平台"的开列（按当时可得技术 ⚠️ 推定，书页 Key features 一句可作锚 ✅："technology and tools that enable the new generation: metadata, temporal data, ETL, unstructured data, and data quality control"）：

| 技术要求 | 2005 对应物 | 一代的反面 |
|---|---|---|
| 关系引擎为骨，但吃下时间语义 | 时态表/双时钟列 + 应用层 SCD | 一代只有"当前值+备份" |
| 可并行扩展 | MPP 一体机 / 共享磁盘 RAC 类 | 单实例垂直扩容到头即死 |
| 存储拓扑可变 | 表空间/分区迁移在线化 | 物理布局=终身判决 |
| DBMS 版本可滚动升级 | 集群灰度、双活 | 大版本停机 = 装载窗口噩梦 |
| 工具链松耦合 | ETL/BI 经元数据总线对接 | 点对点脚本网，动一发牵全身 |

"fluid"的操作定义（⚠️ 提炼）：**架构部件可以被替换而不中断服务**——这是"always open"的工程前提，也是第 16 章迁移论能"边跑边换零件"的力学基础。

### 2.2 静态与时变数据的分离（✅ 小节题——本章真正的独有新件）

一代把所有列混在一张表里；DW 2.0 要求按**变化频率**拆仓：

- 静态数据（static）：几乎不变的属性——人的姓名、门店地址、产品品牌。一旦写入即稳定，适合高压缩、少版本。
- 时变数据（temporal）：随时间产生新版本的属性——等级、价格、余额。必须带有效区间，是 as-of 查询的对象（与第 11 章结构表征互为表里）。
- 分离的三重红利（⚠️ 推定论证）：① 存储经济学——静态列只存一份；② 更新经济学——高频变更不再锁宽行全列；③ 语义清晰性——"哪列会老"被架构显式回答（一代靠 DBA 记忆）。
- 代价：联查需要连接层（视图/API）粘合，复杂度上移——这正是 2.1"技术路线"要兜住的部分。

### 2.3 与四大分区（03 章）的力学关系

静态-时变分离是**纵切**（列的性质），四分区是**横切**（行的年龄+热度）。二维切完，DW 2.0 的空间坐标系才闭合：任何一行数据的位置 =（扇区, 静/时变类）。本节为 ⚠️ 目录编者综合，原书两章分述未明言此坐标系。

## 三、主题深读：「流动」在 2026 变成了什么

2005 的"流动"是**对抗性概念**（对抗一代的冻结拓扑）；2026 的流动是**默认物理性质**，实现方式作者基本没点名：

- 存算分离：计算层无状态多实例（Snowflake/BigQuery 类 ⚠️），介质更换对用户不可见——2.1 表的第 3、4 行被云架构直接吞掉。
- 表格式的 schema evolution：Iceberg/Delta 加列不改表、分区重排不改查询——"结构可改"以元数据重写（而非数据重写）实现，恰与 04 章"元数据=基础设施"闭环。
- 视图/动态表接管"分离的粘合层"：静态表×时变表的连接被声明为物化视图，引擎负责增量维护——2.2 的代价被自动微增量刷新偿付。

本机 🔧 最小标本（**非本书引擎/平台行为**，DuckDB 1.5.5 实跑 ✅）：prod_static（2 行：pid,brand）与 prod_temporal（3 行：pid,price,recorded_at）分表后经 JOIN 视图 prod_full 合并输出 3 行——静态一份、时变多版本的拆分语义 + 粘合层透明性，一次演示到位；DuckDB 视图不物化，2026 生产需物化引擎，差异已在演进节登记。

## 四、原书 → 2026 对位

| 原书口径 | 2026 现状 | 态 |
|---|---|---|
| fluid infrastructure | 存算分离 + 无状态计算层 = 流动成为云出厂设置 | 兑现（更名） |
| 静态/时变分离 | SCD2/时态表主流化；更彻底的是"列级版本"（data versioning 引擎 ⚠️） | 兑现 |
| 滚动升级不停机 | 云仓版本由厂商托管，用户根本无升级日历 | 超额兑现 |
| 松耦合工具链 | 元数据总线思想由 OpenLineage/Catalog API 兑现；但 dbt 生态同时再造了新的点对点耦合（模型即脚本网风险） | 半兑现 |
| 双切坐标系（⚠️ 编者综合） | 湖表：partition（横）+ 列类型演化（纵）在 DDL 同屏可见 | 追认 |

## 最新演进与工业实践

- **判决**：本章是"预言兑现但死法不同"的典型——fluid 作为卖点已胜利，作为**章节技术清单**已作废：2026 没人再论证"要不要可替换部件"，问题是替换的**成本曲线**（存算分离把介质流动变免费，schema 流动仍是治理难点）。
- **静/时变分离的当代激进版**：一批新引擎把"列级变化频率"做成物理布局参数（按更新率分簇、行日志转列存 ⚠️ 转述，不可本机实测），比 @@IN@@ 的两张表方案更细粒度；保守派做法仍是 SCD2 + 视图，本书方案即其直接祖先。
- **反例登记**：工具链松耦合愿景 vs dbt/Notebook 时代的脚本耦合回潮——元数据总线没成为 OS，只成为了 API 集合；教训：**耦合不会消失，只会转移计费**。
- 本机 🔧 汇总口径：本章标本（分表联查 3 行）+ 08 章 SCD2 as-of + 10 章双粒度对账构成"流动/时变/粒度"三件套演示组（各标非本书引擎/平台行为）。
- **实践清单（2026）**：① 建表时显式回答"哪些列会老"；② 粘合层优先交给有增量维护能力的物化引擎，别用裸视图扛生产 SLA；③ 把"部件可替换"写进采购条款（导出格式、元数据 API、权限模型三处验流动）。
