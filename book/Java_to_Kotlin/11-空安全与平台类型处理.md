## 机制：Java 原形 → Kotlin 翻法 → 重构步序

**Java 原形（隐式 null 约定，无注解）** 🔧：

```java
public class ReportService {
    public String format(Report r) {          // null 进 null 出：口头约定
        if (r == null) return null;
        StringBuilder sb = new StringBuilder();
        for (Row row : r.getRows()) {          // getRows() 可能返回 null——凭记忆
            if (row.getLabel() != null) sb.append(row.getLabel());
        }
        return sb.toString();
    }
}
```

**中间态（IDE 转换产物——平台类型满屏跑）** 🔧：

```kotlin
class ReportService {
    fun format(r: Report?): String? {
        if (r == null) return null
        val sb = StringBuilder()
        for (row in r.rows) {            // rows: (Mutable)List<Row!>! ——外层可 null 也不拦
            if (row.label != null) sb.append(row.label)
        }
        return sb.toString()
    }
}
```

**终态（边界收敛 + 内核非空）** 🔧：

```kotlin
// 第 0 刀在 Java 侧：补注解（编译器按注解"简单名"识别，不限定包 ⚠️ 口径待验）
//   public @Nullable String format(@NonNull Report r)
class ReportService {
    fun format(r: Report): String =      // 注解生效后签名收敛为 T / T?
        r.rows.orEmpty()
            .mapNotNull { it.label }
            .joinToString()
}
// 注解来不及补的过渡形态：入口处一次性防御固化，内核只与收敛后的类型打交道
```

**重构步序**（⚠️ 归纳）：① **登记**——把被 Kotlin 消费的 Java 公共 API 上的 `T!` 出现点列成清单（返回/参数/泛型实参三类）；② **由内而外补注解**——先补最热的边界 API（`@NonNull` 参数、`@Nullable` 返回）；③ 补不到的点做**入口防御**（`?: error("boundary")` / `orEmpty` / `filterNotNull`），当场定空不拖延；④ Kotlin 内核签名只允许 `T` 与 `T?`，`!!` 按 03 档红线逐个歼灭；⑤ 泛型实参单独处理（`List<String!>!` 的"外层可空、元素平台"复合态最阴）；⑥ 全局选项收紧（JSR-305 严格模式类开关 ⚠️ 旗标名未核）。

迁移对照表（⚠️ 归纳）：

| 平台类型出现位 | 形态 | 收敛手段 |
|---|---|---|
| Java 返回值 | `getName(): String!` | `@Nullable/@NonNull`；过渡 `?: 默认` |
| Java 参数 | 赋值给 `T` 时插隐式断言 | 入口显式校验，错误信息定界 |
| 泛型实参 | `List<String!>!` | 元素级 `filterNotNull` + 外层 `orEmpty` |
| Java 数组 | `Array<String!>` | `mapNotNull` 落地为只读 List |
| 覆盖无注解 Java 接口 | 签名可选 `T` 或 `T?` ⚠️ 弹性未验 | 一经调用方使用即定死，先内后外 |
| Kotlin 导出给 Java | 非空参/返默认发 `@NotNull` ✅ 语言事实 | Java 侧 IDE 检查白捡 |

## 老手易错点与批判读法（画像：Java/C++ 经验者）

- **错误行号不可信**：平台类型赋给非空 `T` 时断言织在**赋值点**，NPE 却炸在后续解引用——迁移期定位 bug 要先怀疑"类型边界记账错位"（🔧 实验 2 亲手复现）。
- **注解家族互不兼容**：jetbrains / jsr305 / jakarta / JSpecify 的注解目标（TYPE_USE vs 方法/参数）与语义各异，混用等于没用它——项目内统一一族并从 JSpecify 方向收敛 ⚠️（03 档同款欠账）。
- **可空性是类型的属性不是位置的属性**（03 档主旨的边界版）：`format(r: Report?)` 用 `?: return null` 把口头约定写进签名——比"文档里写 may return null"强一个数量级。
- **C++ 对照**：平台类型 ≈ dlopen 进来的未声明契约引用——头部（注解）补不全，检查器（编译器）就装死；补注解的工程预算按"每个跨界类 3–5 处"估 ⚠️ 推断，且这是**还 Java 时代欠债**，不是 Kotlin 新税。
- **异常史话**：KotlinNullPointerException/TypeCastException 自 1.4 起统一为 NullPointerException ⚠️ 版本口径——读老 stacktrace 时别被旧异常名误导。
- **批判一句**：把全部 `T!` 收敛成 `T?` 是另一种偷懒——内核到处 `?.`/`?:` 只是把 null 传染合法化；正确终态是边界防御一次、内核非空贯穿（对照 [08 档](08-从命令式到函数式风格.md) "管道裸奔"警告）。
