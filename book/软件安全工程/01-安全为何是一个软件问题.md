# 第 1 章 安全为何是一个软件问题（Why Is Security a Software Issue?）

> **一句话**：这一章把「安全」从网络防火墙和入侵检测手里抢回来——**大多数安全漏洞恰恰生在应用软件里，而防火墙后面的代码才是攻击者的真正目标**；全书的说理框架（风险管理、早期发现、SDLC 融入）在这一章全部立起。

## 核心精讲

> 以下全部是**教学示意，不参与构建、不编译、不运行**。

### 1.3 软件保证 vs 软件安全：一张对照表

| 维度 | 软件保证（assurance） | 软件安全（security） |
| --- | --- | --- |
| 关心的问题 | 「软件做它该做的事吗」 | 「软件不做它不该做的事吗」 |
| 对手 | 缺陷、需求偏差、环境故障 | 有智力的攻击者 |
| 度量 | 测试覆盖率、缺陷密度 | 风险（可能性 × 影响）、攻击面 |
| 典型活动 | 测试、评审、CMMI 过程审计 | 威胁建模、滥用案例、安全代码分析 |

### 1.5 不安全的三大来源（原书的核心论证）

```text
分布式（distributed）
  → 状态散落在多个节点，任何一处的信任假设都可能被绕过
可扩展（extensible）
  → 插件/宏/脚本/动态加载让"未来的人"改写"现在"的行为
互联（interconnected）
  → 你的系统与陌生人的系统共享进程间信道
```

原书的判断在 2026 年只剩一条加法：**第四来源是依赖**——你自己的代码可能没问题，但传递依赖里躺着一个 log4j-core（见 06 章 🔧）。

### 1.6 缺陷发现成本的「30 倍律」（示意模型）

```python
# 教学示意，不参与构建、不编译、不运行
# 原书引用的观点：设计阶段修复缺陷的成本远低于发布后。
# 经典来源是 Boehm 的软件经济学曲线；安全缺陷同样满足且更陡。

def fix_cost(stage: str) -> int:
    return {"需求": 1, "设计": 5, "编码": 10, "测试": 20, "发布后": 30}[stage]

# 安全缺陷的特殊性：发布后修复还要加上"攻击者已利用"的窗口期
# （Log4Shell 的补丁发布 72 小时内攻击遍及全球，见 06 章）
```

> 注意：**不要把「30 倍」当作精确常数**——它是 Boehm 在 1980 年代的数据外推，2026 年的实证研究（如 Google 的工程经济分析）给出的倍率因缺陷类型差异极大；但其**单调性**（越晚越贵）从未被推翻。

### 1.2.1 系统复杂性：一个示意（为什么传统 QA 模型失灵）

```text
组件数 n = 50 的系统：
  组件内状态组合    —— 逐个可测（传统 QA 能覆盖的部分）
  组件间交互路径    —— O(n²) = 2450 条，没人测
  与环境的交互      —— 网络/时间/用户行为，无限域
攻击者的选择空间：三条里挑一条 —— 几乎总是后两条
```

> 这张示意图解释了本章 1.5 的论证起点：**复杂度把「测不完」从遗憾变成结构必然**，所以安全必须靠设计与流程管理风险，而不是靠穷举测试消灭缺陷。

### 1.3.1 流程与实践的角色（原书 1.3.1 的浓缩）

原书在这一小节埋了一个常被忽略的观点：**流程本身不产生安全，流程只保证实践被一致地执行**。两者的分工是：

| 流程负责 | 实践负责 |
| --- | --- |
| 谁在什么时机做什么（SDLC 卡点） | 具体怎么做（威胁建模、代码分析、测试） |
| 资源与优先级 | 技术判断与风险裁决 |
| 可重复性与审计痕迹 | 有效性（发现真问题） |

> 只有一半是常见的组织病：只有流程 → 安全剧场；只有实践 → 英雄主义，人走茶凉。本章 1.7 的「管理」之所以排在全书第一章末尾，就是要读者从第一天起把两者绑在一起看。

### 1.4 威胁面：2008 vs 2026 的对照

| 维度 | 2008 年（本书语境） | 2026 年 |
| --- | --- | --- |
| 主要入口 | Web 应用、邮件、网络服务 | API、移动端、云控制面、AI 接口 |
| 攻击者动机 | 声望、小规模牟利 | 勒索产业化、供应链投毒、国家级 |
| 典型武器 | 自研漏洞利用、SQL 注入工具包 | 现成漏洞利用（KEV 在野利用）、窃密即服务 |
| 最大盲区 | 「依赖是可信的」 | **传递依赖本身就是威胁面**（xkcd 2347） |
| 防御重心 | 边界 + 补丁 | 左移 + 持续验证（门禁、签名、零信任） |

> 对照表想说明的不是「原书错了」，而是：**威胁面的形状变了，但「威胁面在应用层、随连接性增长」的判断完全没变**——这正是本章经得起重读的部分。

### 1.7.1 项目经理该问的战略问题清单（原书 1.7.1 的浓缩）

1. 我们的安全目标是什么？要保护什么资产、防什么对手？
2. 什么样的风险水平是可接受的（「足够好」的定义）？
3. SDLC 每个阶段有哪些安全实践值得投入？
4. 我们如何度量安全实践的成效？
5. 出事之后的响应流程是什么？

## 近年研究与工业界开源实践（2015–2026）

**趋势**：本章的三条论证——「应用是主战场」「复杂度在放大风险」「早期投入划算」——全部被强化，但证据链整体换代。

- **内存安全数据**：微软 MSRC（2019）与 Google Chromium 团队（2020）分别报告约 70% 的严重漏洞是内存安全问题；Google Android 的数据显示引入 Rust 后内存安全漏洞占比从 2019 年的 76% 降到 2022 年的 35%——「在 SDLC 前端换语言」成为比任何单点实践杠杆都大的投入。
- **供应链成为第一威胁源**：Log4Shell（CVE-2021-44228，2021）之后，SCA（软件成分分析）从可选项变成 CI 门禁；NIST SSDF 与 EU CRA 把本章 1.7 的「战略问题清单」变成了合同条款。
- **工程经济学的更新**：传统「发布后修复贵 30 倍」让位于「攻击窗口期」的度量——CISA KEV（已知被利用漏洞目录）与 EPSS（漏洞利用概率评分）把 1.6 的「早发现」变成了「优先修真正会被打的」。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **2008 年的威胁统计不能再用** | 书中以当时的安全事件与漏洞数据说理；2026 年应引用 MSRC 70% 内存安全数据、Android Rust 实证、Log4Shell 案例、CISA KEV/EPSS 的优先级治理 |
| 🔧 **「网络机制不够」之外缺了「供应链」** | 原书认为网络与基础设施安全不足以保护应用；2026 年还要加上：**你信任的开源依赖本身可能是最大的攻击面**（SBOM/SLSA，见 06 章） |
| **「30 倍修复成本」被当精确数据** | 它是 1980 年代数据的外推；正确用法是强调**单调性**与攻击窗口期，而非具体倍数 |
| **「安全 = 消灭漏洞」的靶子树得对但解法讲得少** | 本章正确指出漏洞清零不可达，但没给出 2026 年已成熟的替代度量：风险优先级（EPSS）、成熟度基准（BSIMM）、合规基线（SSDF） |
| **「项目经理视角」容易被读成「流程万能」** | 流程只是容器；没有代码级实践（05 章）与架构级实践（04 章），SDL 文档堆得再多也不会让软件更安全——SDL 文档化在 2009–2014 年的退潮就是教训 |
| **1.5 的「三大来源」被当成完整清单** | 原书列举了分布式、可扩展、互联三大结构性来源，但读者应把它当**开放式框架**：2026 年至少要加上「依赖」（xkcd 2347）与「AI 生成代码的不可解释性」两条 |
| **1.3 的 assurance/security 之辨被读成「assurance 不重要」** | 二者是互补不是对立：没有保证（测试、评审、审计）的「安全」只是声明；区别只在**对手是否智能**—— assurance 论证里缺少「对抗性测试」一项时它就抓不住安全问题 |
| **对 1.6「商业论证」只谈成本** | 早期发现的收益还有一半在**声誉与合规**：CVE 披露周期、CRA 义务、客户安全问卷——2026 年的安全投入已经能直接换到订单，这在 2008 年是反向论证 |
