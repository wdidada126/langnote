# 第 8 章 如何起步（Getting Started）

> **一句话**：全书最短的一章回答最实用的问题——**别等完美方案，按你组织的风险容忍度与成熟度挑两三个实践，先做起来**；本章把前面七章压缩成一张「从哪开始」的行动表，2026 年的等价物是一套可以今天下午就跑起来的开源工具栈。

## 核心精讲

> 以下全部是**教学示意，不参与构建、不编译、不运行**。

### 8.1 差距分析：对照 SDLC 逐段打分

| SDLC 阶段 | 本书对应章 | 起步实践（最低配） | 进阶实践 |
| --- | --- | --- | --- |
| 需求 | 03 | epic 级三问（资产/滥用/违反属性） | SQUARE 全流程、威胁建模入 DoR |
| 架构与设计 | 04 | 新架构决策附 DFD + STRIDE 清单 | 架构风险分析常态化、ADR 回链安全原则 |
| 编码 | 05 | pre-commit 秘密扫描 + SAST 基线 | 门禁策略、SAST triage 流程、定向 fuzzing |
| 依赖/组装 | 06 | SBOM 生成 + 依赖扫描进 CI | SLSA 等级、制品签名、DependencyTrack 持续监控 |
| 测试 | 05 | 对解析器/文件格式加 fuzz harness | OSS-Fuzz 接入、DAST、渗透测试节奏 |
| 治理 | 07 | 指定产品安全负责人 + 漏洞响应 SLA | BSIMM/SAMM 测量、SSDF 自评、合规映射 |

### 三种起步路径（原书 8.1 的浓缩 + 2026 补充）

```text
自上而下（治理驱动）
  适合：受监管行业、B2B 交付（客户要 SSDF/SBOM 证明）
  第一步：差距分析 → 定「最低合规线」 → 平台化工具链
自下而上（工程驱动）
  适合：有安全意愿的工程团队、初创
  第一步：CI 加依赖扫描 + 秘密扫描（一次提交完成）→ 逐步加 SAST/门禁
事件驱动
  适合：刚出过事故的组织
  第一步：复盘归因（缺陷在哪一层？03–07 章对号）→ 补对应实践
```

### 2026 版「今天下午就能跑」的最小栈（示意配置，不执行）

```yaml
# 教学示意，不参与构建、不编译、不运行
# GitHub Actions 片段：依赖扫描 + 秘密扫描 + SAST 三件套
name: security-baseline
on: [pull_request]
jobs:
  sca:          # 依赖漏洞（SCA）
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: trivy fs --scanners vuln,misconfig --exit-code 1 .
  secrets:      # 秘密扫描
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }      # 连历史一起扫
      - run: trufflehog git file://. --fail
  sast:         # 轻量静态分析
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: semgrep ci --error
  sbom:         # SBOM 生成并随构建归档
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: syft . -o cyclonedx-json > sbom.json
      - uses: actions/upload-artifact@v4
        with: { name: sbom, path: sbom.json }
```

> 这份配置四个 job 的每一行都对应原书的一章：SCA/组装（06）、秘密/编码（05）、SAST/编码测试（05）、SBOM 归档（07 治理证据）。**起步的意义是把「可发现的失败」变成「必然发生的检查」。**

### 8.1 起步节奏参考（30 / 60 / 90 天）

| 阶段 | 动作 | 验收信号 |
| --- | --- | --- |
| 30 天 | CI 三件套上线；指定安全对接人；建漏洞响应群 | 每个 PR 都被扫描；有第一例告警被 triage |
| 60 天 | SBOM 归档；威胁建模模板进 epic 模板；依赖升级自动化 | 新 epic 带「资产/滥用/属性」三问；依赖升级有自动 PR |
| 90 天 | 门禁策略定级（block/warn）；对最高风险组件加 fuzz harness；差距分析报告上会 | 门禁拦截有记录与豁免流程；管理层签收残余风险台账 |

> 节奏表呼应原书 8.1 的核心观点：**起点按成熟度与风险容忍度选，而不是按最佳实践榜单选**。三个阶段都不要求专职安全团队——它们是被设计成「现有工程师顺手可做」的。

再往后的分岔值得写下来：90 天之后的路线选择**取决于组织类型**——B2B 供应商优先补合规证据（SSDF 自评、SBOM 交付），2C 服务优先补响应能力（MTTR、应急预案），基础设施/开源项目优先补供应链完整性（签名、SLSA 等级）。原书 8.1 的三种起点路径在这一层同样适用：治理驱动型接着做度量，工程驱动型接着做深度（fuzzing/威胁建模），事件驱动型接着做复盘闭环。

| 年份 | 事件 |
| --- | --- |
| **2008** | **本书出版**：起步路径是「差距分析 + DHS BSI 免费资源 + 逐步采纳实践」 |
| 2009–2013 | OWASP SAMM/BSIMM 提供了替代自评的成熟度标尺；BSI 网站内容归入 CERT，本书的行动表成为其纸质快照 |
| 2014–2016 | 容器普及让「起步」第一次有了打包形态：镜像扫描（Clair/Trivy 前身）进 CI |
| 2018 | **OpenSSF 成立**（此前为 Core Infrastructure Initiative）：开源安全协作的社区底座 |
| 2019–2021 | **OpenSSF Scorecard / AllStar**：给仓库自动打安全分；Dependabot 类自动升级成为 GitHub 默认能力 |
| 2021–2022 | EO 14028 + SSDF：采购方开始直接要求「起步证明」（SBOM、自评表） |
| 2023–2026 | SLSA v1.0、sigstore 规模部署、EU CRA 时间表明确——「起步清单」中的多项从「建议」变成「到期必须」 |
| 2020 | **OpenSSF Scorecard** 开源：自检与依赖尽调第一次有了自动化工具（起步差距分析的机器可读版） |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：本章的「如何起步」在 2026 年的第一站几乎总是**GitHub/GitLab 仓库里加扫描**，第二站是**供应链证明**——起步成本从「项目级工程」降到「一次 CI 提交」，同时合规要求把起点抬高。

- **起步三件套的事实标准**：SCA（trivy/osv-scanner）+ 秘密扫描（trufflehog）+ SAST（semgrep/codeql）覆盖最高频漏洞类目，一次 CI 提交完成。
- **scorecard 作为起步体检**：对开源依赖跑 `scorecard`，低于阈值的组件进入替换/加固清单——原书 8.1 的「差距分析」自动套用到依赖上。
- **零信任起步**：对存量系统，2026 年的务实起点是 mTLS + 服务间最小权限（拒绝默认全通），而不是一口气引入完整零信任平台。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **起步清单缺供应链第一站** | 2026 年的第一步是给 CI 加依赖扫描与 SBOM（log4shell 的教训：先知道你有什么）；原书的起步清单没有这一项 |
| 🔧 **「免费资源」指针过期** | DHS BSI 网站已并入 SEI/CERT 资源体系；今天的免费资源是 SSDF 全文、OWASP Cheat Sheets、OpenSSF Scorecard 与 OSV——链接都要现找现验 |
| 🔧 **无 DevSecOps 起步路径** | 原书起步假设有「项目」与「阶段」；2026 年多数团队生活在流水线里，起步的载体是 CI job 与门禁策略，不再是文档流程 |
| **「先做完整的差距分析再动手」** | 差距分析会变成拖延的理由；正确顺序是**先装三件套（当天生效）再补治理差距**——工具先行不等于治理后补，两者并行推进 |
| **起步实践全靠热情个体** | 个体会离职；凡是要「活下来」的实践必须进 CI（机器执行的不会走人）并写进团队 DoD/DoR |
| **把「起步」理解为「小项目才用」** | 原书明确本章服务所有规模；大型组织起步的难点反而在政治与预算（07 章），小组织难点在意愿与时间——路径表要按组织形态重排 |
| **起步 = 上工具，不做 triage 排班** | 工具装完没人看告警，是起步失败的第一大原因；先定「谁看、多久看一次、看了怎么办」，再装工具 |
| **从最难的实践开始（如全员威胁建模）** | 起步实践必须满足「两周内可见产出」，否则热情耗尽；威胁建模这类重投入实践应放在工具链与 triage 习惯稳定之后 |
| **忽视「退出条件」** | 每项起步实践要定义「什么算成功/什么算放弃」，否则会积累一堆无人维护的安全仪式；07 章的度量四问在这里同样适用 |
| **起步阶段跳过 03/04 章，直接从 05 章工具切入** | 工具先行没问题，但 SAST/fuzzing 的产出若没有需求/架构层的归宿（威胁模型、需求条目），triage 会失去优先级依据，最终告警全部被静音——起步清单的每一项都要能回链到它的「上游章」 |
| **把「工具版本」当「实践完成」** | 装 Trivy ≠ 有 SCA 实践：实践 = 工具 + 处置流程 + 责任人 + 度量；起步清单里每行勾选前先确认后三样都在 |
| **90 天后停止回顾** | 起步清单会随组织变化失效（换技术栈、并购、缩编）；把「这份清单还成立吗」放进季度复审，是 07 章「自适应」级别的第一次练习 |

## 与其他章 / 其他书的联系

- **→ 本目录 01–07 章**：本章是全部前文的索引与排序——每条起步实践都应能回链到它所属的章与理由；找不到回链的「安全措施」大概率是仪式。
- **↔ `book/应用密码学（原书第2版）/00-总览与阅读地图.md`**：两本书的「结语姿态」完全一致——Schneier 说「密码学是链条中最容易做对的一环」，本书说「软件安全要按风险管理做到足够好」；**两者合起来才是「构建安全软件」的完整初学者路线：先别发明密码学（01–16 章），再别漏掉流程（01–08 章）**。
- **↔ `book/白帽子讲Web安全.md`**：吴翰清在书末同样给了「安全开发生命周期」的公司级建议——两本书的 08 章互为中外版本的同题作文，可对照读。
- **↔ `book/CISSP认证考试指南.md`**：CISSP 考生最后需要把零散域知识收束成「组织怎么做」，本章是最佳收束材料。
- **↔ `book/计算机安全导论.md`**：导论最后一章的安全管理/伦理部分与本章的治理起步衔接，形成「概念 → 工程 → 管理」的完整学习闭环。
- **↔ `book/软件安全工程.md`（大纲版）**：大纲版的核心思想三行（攻击者视角、足够好的安全、BSI 配套）就是本章 8.2 的全部——想三分钟回顾全书，读大纲；想三周重走全书，读本目录。
- **↔ `book/Kubernetes实战_2.md` 等云原生条目**：2026 年起步清单的「部署/运维」行几乎都在云原生语境里展开（镜像扫描、准入策略、密钥托管）；本书 2008 年的起步清单假设自建机房，落地时需要做一次云原生翻译。
- **↔ `book/SQL必知必会5.md` 等基础类目**：起步路径里「编码实践」一行的最大单项收益（参数化查询、最小权限账号）在 SQL 层就能完成——最便宜的安全投入往往在基本功里，不在安全专项里。
- **↔ `book/应用密码学（原书第2版）/00-总览与阅读地图.md` 的「阅读顺序建议」**：两份地图给出了同一个方法论——「先建主线、再按需深入」；起步章节的裁剪精神（够用就好）与该目录的阅读路径设计互为镜像。
