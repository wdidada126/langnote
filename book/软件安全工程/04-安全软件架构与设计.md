## 核心精讲

> 以下全部是**教学示意，不参与构建、不编译、不运行**。

### 4.2.1–4.2.2 架构风险分析：五步流程

```text
① 软件刻画（Software Characterization）
   画 DFD（数据流图）：外部实体、进程、数据存储、数据流、信任边界
② 威胁分析（Threat Analysis）
   沿每条跨信任边界的数据流，用 STRIDE 生成威胁清单
③ 架构漏洞评估（Architectural Vulnerability Assessment）
   对照已知架构缺陷模式（如「认证在边缘网关做一次，内部服务裸奔」）
④ 风险判定（可能性 × 影响）
⑤ 缓解计划（改架构 / 加补偿控制 / 接受残余风险）
```

### STRIDE：六类威胁与对应缓解

| 威胁 | 违反的属性 | 典型缓解 |
| --- | --- | --- |
| Spoofing（仿冒） | 认证 | 强认证、mTLS/服务身份 |
| Tampering（篡改） | 完整性 | 签名、MAC、完整性校验 |
| Repudiation（抵赖） | 非否认 | 防篡改审计日志 |
| Information Disclosure（信息泄露） | 机密性 | 加密、最小化数据流 |
| Denial of Service（拒绝服务） | 可用性 | 限流、配额、资源隔离 |
| Elevation of Privilege（提权） | 授权 | 最小权限、输入验证、沙箱 |

### 4.2.2 用 DFD 找威胁（示意）

```python
# 教学示意，不参与构建、不编译、不运行
DFD = {
    "external": ["用户浏览器", "第三方支付回调"],
    "processes": ["API 网关", "订单服务", "风控服务"],
    "stores": ["订单库", "会话缓存"],
    "flows": [
        ("用户浏览器", "API 网关", "HTTPS 请求"),
        ("API 网关", "订单服务", "内部明文 HTTP"),   # ← 信任边界内部裸奔
        ("第三方支付回调", "API 网关", "回调（未验签？）"),
    ],
}

def threats(flow):
    """每条跨信任边界的数据流都是威胁候选地（Shostack 四问的简化版）"""
    src, dst, _ = flow
    return ["S: 伪造调用方?", "T: 传输中被改?", "I: 被窃听?", "R: 可抵赖?", "D: 可被耗尽?"]
```

> 示意中那两条被注释的流就是 2026 年云上事故的两个高频源头：**内部流量明文**（零信任要修的第一个）与**回调未验签**（OWASP API Top 10 常客）。威胁建模的产出常常就是这几条「画图时才看得见」的裂缝。

DFD 的一个实用纪律：**每条跨信任边界的数据流都标「协议 + 认证方式 + 数据敏感级」三个注记**。画不出来注记的流，就是没有设计的流——而攻击者最爱没有设计的流。原书 4.2.2 的威胁分析质量，几乎完全取决于 DFD 的粒度：太粗漏威胁，太细画不完，经验值是「一个进程节点 = 一个独立部署与独立信任决策的单位」。

### 4.2.3 架构漏洞评估：高频架构级缺陷清单（2008 与 2026 通用）

| 架构级缺陷 | 表现 | 缓解方向 |
| --- | --- | --- |
| 认证只在边缘做一次 | 内部服务裸奔，一个立足点即全线失守 | 服务身份 + 每跳鉴权（零信任） |
| 授权分散且不一致 | 每个端点各自实现属主检查，漏一个就是 BOLA | 集中式授权中间件/策略引擎 |
| 信任串在一条链上 | 组件 A 信 B、B 信 C，最弱一环决定全局 | 显式信任边界 + 最小权限传递 |
| 会话/凭证生命周期失控 | token 永不过期、登出即遗忘 | 短期凭证 + 吊销机制（Vault 式租约） |
| 日志与业务同域同权 | 攻破业务即篡改证据 | 审计面隔离、append-only 日志 |
| 共享数据库账号 | 无法区分「谁干的」 | 按服务最小账号 + 面向会话的授权（对照数据库 GRANT/REVOKE） |

> 这张表是「架构漏洞评估」一步的产出物形态：**每一条都是 DFD 上的结构性问题，改代码救不了，必须动架构**——这正是 4.1.1 说「架构缺陷贵得修不起」的原因，也是越早做风险分析的理由。

### 4.3 三级知识库

| 层级 | 抽象度 | 实例 |
| --- | --- | --- |
| 安全原则 | 最高 | Saltzer-Schroeder 八原则（最小权限、失效安全……） |
| 安全指南 | 中 | 各技术域的具体规则（CERT 规则、OWASP ASVS 条目） |
| 攻击模式 | 对手视角 | CAPEC 条目（如 CAPEC-34 HTTP 响应拆分）；Hoglund & McGraw《Exploiting Software》的攻击模式目录 |

> 三层之间的用法：**原则裁决冲突，指南生成 checklist，攻击模式生成威胁**。架构评审会上三层的出场顺序是「攻击模式 → 指南 → 原则」——先用对手的清单找问题，再用规则找遗漏，最后用原则裁决新发现的冲突；顺序颠倒会把评审会变成原则背诵会。

## 版本演进

| 年份 | 事件 |
| --- | --- |
| **1999** | Microsoft 提出 STRIDE（SWI 团队）；威胁建模开始工程化 |
| **2004** | Hoglund & McGraw《Exploiting Software》出版：攻击模式（attack patterns）概念的系统化 |
| 2006 | McGraw《Software Security: Building Security In》把「架构风险分析」定为软件安全的四大实践之一 |
| **2008** | **本书出版**：BSI 网站的架构实践沉淀 |
| **2011** | **CAPEC**（Common Attack Pattern Enumeration and Classification）发布 v1.x，由 MITRE 维护，攻击模式有了标准编号体系 |
| **2014** | **Shostack《Threat Modeling: Designing for Security》**：DFD + STRIDE + 四问（What are we building / What can go wrong / What are we going to do / Did we do a good job）成为现代标准操作 |
| 2017 | OWASP ASVS v3 稳定（2021 v4）：安全指南层有了可勾选的验证标准 |
| 2020 | **NIST SP 800-207 零信任架构**：服务间默认互不信任，内部明文通信的第一时间被点名 |
| 2021–2026 | 微服务/服务网格把 DFD 的「进程」变成成百上千个节点，人肉威胁建模撑不住 → 工具化（Threat Dragon、IriusRisk、TAM）+ 模板化；威胁建模「左移但难排期」成为工业界公开承认的痛点 |
| 2018 | OWASP Top 10（2017 版）首次收录「XML 外部实体（XXE）」：DFD 外部实体与解析器信任问题进入大众清单 |
| 2023 | OWASP Threat Modeling Cheat Sheet 与各厂威胁建模指引成熟：模板化成为左移的主导方案 |
| 2024 | EU CRA 把「按风险设计」写进法律义务：架构层的合理安全措施从工程判断变成可被追责的决策点 |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：架构风险分析五步没变，但**架构本身**变了——微服务、事件驱动、多云让 DFD 膨胀到手工不可维护；零信任把「内部可信」假设废除；密钥与签名成为架构层的公民。

- **威胁建模左移的实践困境**：CI 里跑不动白板活动；工业界的答案分三派——（a）模板化（按架构风格套标准威胁清单）；（b）工具化（从 IaC/K8s manifest 自动生成 DFD 候选）；（c）准入门禁（生产变更必须附威胁模型 diff，人审）。
- **零信任重塑「架构漏洞评估」**：原书时代的经典架构缺陷（边缘认证 + 内部明文）在 2026 年是零信任落地的第一目标；评估清单直接从 SP 800-207 的原则推导。
- **密钥管理成为一等架构决策**：密钥放哪（KMS/Vault/HSM）、轮换策略、应用如何取用——2008 年的架构评审根本不问这个问题，2026 年它是 DFD 上必须画出的一个「进程 + 存储」。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **威胁分析止步于单体 DFD，未覆盖微服务/云原生** | 2026 年 DFD 的节点是服务、容器、托管依赖；信任边界包括网络边界（VPC）、身份边界（IAM）、运行时边界（容器/沙箱）；Threat Dragon 等 DFD 工具要能对 IaC 做版本化 |
| 🔧 **攻击模式知识库未引 CAPEC/CWE 编号体系** | 原书 4.3.3 是 Cigital 的攻击模式目录；2026 年标准坐标是 **CAPEC**（攻击模式）与 **CWE**（弱点），缓解映射到 **CVE/OSV**，三者构成可检索的知识链 |
| 🔧 **零信任假设完全缺失** | 原书时代的典型缓解是「加强边界」；SP 800-207 之后「内部明文 + 边缘认证」本身被定义为架构漏洞，缓解方向是服务身份与默认拒绝 |
| 🔧 **密钥管理只作为实现细节** | 2026 年密钥管理是架构决策（KMS 选择、轮换、环境隔离、密钥泄漏演练）；架构评审清单必须包含密钥条目 |
| **把架构风险分析当一次性活动** | 架构随迭代漂移，风险分析必须跟着架构决策点重跑（ADR 里记录安全权衡是 2026 年的通行做法） |
| **「风险 = 可能性 × 影响」被算术化** | 安全风险的可能性没有可靠先验分布，矩阵打分是**沟通工具**不是计算器；给分数做加权平均的「风险计算器」属于伪精确 |
| **安全原则被背完就扔** | 原则的价值在「冲突时裁决」——最小权限 vs 可运维性、失效安全 vs 可用性；建议把每条 ADR 里的安全权衡显式回链到原则 |
| **DFD 画成部署图/网络拓扑图** | 威胁建模的 DFD 关心的是**数据与信任边界**，不是机器与网段；画成拓扑图会漏掉进程级与用户数据级的边界（这也是 SP 800-207 时代的常见返工原因） |
| **攻击模式（4.3.3）被当攻击教学** | 攻击模式的用途是「反推缓解」，与滥用案例（03 章）同向；读攻击模式学攻击姿势而不落缓解映射，是时间黑洞 |
| **架构风险分析产出无人认领** | 风险清单的每一条要有负责人与目标版本，否则就是「写完即归档」；这与 03 章需求优先级的「谁签字」是同一个治理要求 |
| **缓解计划只写技术措施** | 架构级缓解常有三类：改架构、加补偿控制、改流程/运维（限速、演练、监控告警）；只写第一类的缓解计划会漏掉性价比最高的选项 |
| **「架构」一词被限定为代码结构** | 部署拓扑、数据流、组织接口（谁给谁提供什么信任）都是架构的一部分；2008 年的架构图与 2026 年的 IaC 清单描述的是同一个对象，只是载体换了——分析时两者都要看 |
