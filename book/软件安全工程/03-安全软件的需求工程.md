# 第 3 章 安全软件的需求工程（Requirements Engineering for Secure Software）

> **一句话**：这一章把安全从「需求文档里的一个形容词」变成**可 elicitation（获取）、可优先级排序、可验证的工程对象**——滥用案例（abuse case）教你想「软件不该做什么」，SQUARE 流程（Nancy Mead 亲自主笔）给你九步把安全需求走完。

## 核心精讲

> 以下全部是**教学示意，不参与构建、不编译、不运行**。

### 3.2.1 「安全不是一组特性」：功能需求 vs 滥用需求

| 正常用例 | 对应滥用案例 | 隐式安全需求 |
| --- | --- | --- |
| 用户用密码登录 | 攻击者暴力猜密码 | 登录失败限速 + 锁定策略 + 强口令基线 |
| 用户上传头像 | 攻击者上传 webshell 改后缀绕过 | 内容类型嗅探 + 重写文件名 + 存储区不可执行 |
| 用户重置密码 | 攻击者枚举重置链接 | 链接一次性、限时、与账号绑定、不泄露账号存在性 |
| 管理员查看订单 | 低权员工改 URL 里的订单 ID 越权 | 对象级授权检查（2021 OWASP API Top 10 的 BOLA 仍是第一） |

### 滥用案例的最小写法（结构模板）

```python
# 教学示意，不参与构建、不编译、不运行
abuse_case = {
    "name": "越权读取他人订单",
    "actor": "已认证的低权限用户",
    "precondition": "订单查询接口使用 URL 中的 orderId 定位资源",
    "attack_steps": [
        "登录自己的账号，观察订单接口为 /api/orders/{id}",
        "遍历或猜测他人 orderId（IDOR/BOLA）",
        "读取他人订单的手机号与地址",
    ],
    "impact": "个人数据泄露；GDPR 项下可构成违规",
    "countermeasure_reqlist": [
        "REQ-AUTH-01: 每次对象访问执行属主校验（服务端）",
        "REQ-AUTH-02: orderId 使用不可枚举标识（UUID/加密序列）",
        "REQ-AUD-01: 越权尝试计数并告警",
    ],
}
```

> 滥用案例的价值不在「预测攻击」，而在**把每个攻击步骤翻译成一条可测试的需求**。

### 3.3 SQUARE 九步（浓缩版）

```text
1 达成共识（定义与优先级口径）      ← 教育与对齐
2 识别业务/资产/风险目标            ← 为什么需要安全
3 选择需求获取技术                  ← 方法不通用，按项目选
4 抽取安全需求                      ← 滥用案例登场
5 需求分类（本质 vs 增补）          ← 哪些是必须，哪些是配置项
6 需求优先级排序                    ← 与成本/收益对齐
7 检查（inspection）                ← 与正常用例的一致性
8 形式化/建模（按需）               ← 危及生命的系统才值得形式化
9 归档与复用                        ← 知识库沉淀
```

> 原书明确说：第 8 步只在需要时做。**SQUARE 的精神是「排序与裁剪」而不是「全都要」**——这与全书「足够好的安全」一脉相承。

九步里被现实项目验证最有价值的是第 2 步和第 6 步：第 2 步逼团队说出「我们到底保护什么」（多数团队答不上来），第 6 步强迫把安全需求放回资源竞争里（多数团队默认安全需求免费且无限供应）。其余步骤可以裁剪，这两步不行。

### 3.4 SQUARE 输出形态速览（原书 3.4 的浓缩）

| 步骤 | 输出物 | 形态 |
| --- | --- | --- |
| 1–2 | 安全目标声明 | 一页纸，含资产与对手 |
| 3–4 | 安全需求初稿 | 分「本质/增补」两类 |
| 5 | 分类后的需求清单 | 表格：编号/描述/类别 |
| 6 | 优先级矩阵 | 三档（必须/应该/可以）+ 责任人 |
| 7–9 | 定稿需求规格 + 归档 | 进仓库版本管理 |

> 注意第 6 步的「责任人」列是本笔记加的强调：原书 3.6 只谈方法；没有责任人的优先级矩阵在第一次资源冲突时就会作废。

### 3.5 需求获取方法速查（原书 3.5.1 的浓缩）

| 方法 | 何时适用 | 安全场景的注意点 |
| --- | --- | --- |
| 干系人访谈 | 早期、需求模糊 | 问「谁会想滥用它」比问「要什么安全功能」有效 |
| 工作坊 | 需求冲突需要当面解决 | 安全属性冲突（可用性 vs 机密性）只有当面能裁决 |
| 原型/走查 | 界面与流程类需求 | 安全 UX（MFA、提示）必须在原型阶段验证 |
| 场景与用例分析 | 业务流程明确 | 直接升级为滥用案例（3.2） |
| 文档分析 | 接手遗留系统 | 旧系统的威胁模型档案往往比代码更有信息量 |

### 3.6 优先级：三分法

| 档位 | 判据 | 处理 |
| --- | --- | --- |
| 必须有 | 法律义务 / 无法接受的灾难风险 | 阻塞性需求，不可谈判 |
| 应该有 | 高可能性 × 中影响 | 排进当前迭代 |
| 可以有 | 低可能性 / 缓解成本高于损失 | 记录残余风险，交给管理层签字 |

## 版本演进

| 年份 | 事件 |
| --- | --- |
| **2005** | Sindre & Opdahl《Eliciting security requirements with misuse cases》（*Requirements Engineering* 期刊）确立滥用案例方法；**Mead & Stehney 在 SEFM 2005 发表 SQUARE 方法论**——本章作者 Mead 正是 SQUARE 的提出者 |
| **2008** | 本书出版：SQUARE + 滥用案例进入主流项目经理视野 |
| 2009–2014 | 敏捷开发主流化：传统需求文档被 User Story 取代，安全需求工程遭遇「写不进 backlog」的落地危机；「abuser story」成为敏捷社区的过渡方案 |
| 2011 | ISO/IEC 27034-1 发布：把「应用安全需求」纳入国际标准框架 |
| 2018 | GDPR 全面适用：隐私需求从「可选属性」变成法定需求，DPIA（数据保护影响评估）进入需求评审会 |
| 2022 | **NIST SP 800-218 SSDF** 把「Prepare the Organization」阶段的实践（PO.1–PO.5，含安全需求定义）写成可审计清单 |
| 2023–2026 | LLM 辅助需求抽取出现，但滥用案例的**风险判断**无法外包给模型——攻击者思维仍是人的职责；威胁建模与需求工程的边界在实践里越来越模糊（见 04 章） |
| 2019 | OWASP API Security Top 10 首版发布：API 时代的安全需求清单有了专属参照（BOLA 居首） |
| 2016 | OpenSSF / 开源供应链议题升温：组件选型开始需要「安全需求」条目（维护活跃度、漏洞响应记录） |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：滥用案例的「精神」活了下来，载体换了名字——今天的实践叫**威胁建模左移**与**安全 User Story / DoR（Definition of Ready）**；SQUARE 的九步在敏捷里被压缩成「每个 epic 必答的三个问题」。

- **威胁建模左移的实践困境**：微软官方威胁建模工具与 OWASP Threat Dragon 都是「白板 + DFD」形态，但在两周冲刺里难以排期；工业界的折中是「 epic 级轻量威胁建模 + 代码评审时补充」，完全体 SQUARE 只在合规驱动项目存活。
- **需求即代码**：安全需求以 YAML/Markdown 模板进仓库（与 ADR/威胁模型一起做版本管理），评审流程复用 PR——「归档与复用」（SQUARE 第 9 步）由 Git 承担。
- **BOLA 的持续统治**：OWASP API Security Top 10（2019 首版，2023 修订）把对象级授权失效列为第一，正是 3.2 示例里那条需求的现实回声——**它几乎从不缺需求文档，缺的是每个端点的实现验证**。

| 仓库 | star | 说明 |
| --- | --- | --- |
| `OWASP/Threat-Dragon` | **1609★**（2026-09-25 实测） | OWASP 开源威胁建模工具（DFD + STRIDE），滥用案例的现代载体之一 |
| `OWASP/wstg` | **9888★**（实测） | Web 安全测试指南：每条测试项都可反向「翻译」成一条安全需求 |
| `ossf/scorecard` | **5709★**（实测） | 给依赖项目打安全分，间接为「组件选型需求」提供量化输入 |

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **SQUARE 九步在敏捷团队几乎不可用，要给现代裁剪** | 原书是瀑布/阶段门语境下的完整流程；2026 年的等价物是「epic 级三问」（资产是什么/谁能滥用/违反哪条属性）+ backlog 模板字段，原书未提任何裁剪建议 |
| 🔧 **隐私需求只有一段话的待遇** | 2008 年尚无 GDPR；2026 年隐私需求（数据最小化、保留期、DPIA、跨境传输）必须与安全需求并列成章，且多数有法定时限 |
| 🔧 **「需求获取」未覆盖开源依赖的已知风险清单** | 现代做法：选型时查 OSV/CISA KEV/EPSS 与维护活跃度（scorecard），把「依赖风险」写成需求——原书时代组件选型只看功能 |
| **把滥用案例写成攻击百科** | 滥用案例的产出物是**需求**，不是攻击演示；任何不能翻译成可验证需求的滥用案例都应砍掉 |
| **「安全不是一组特性」被读成「不写功能需求」** | 原文本意是安全不能靠加功能（如「加个验证码」）解决；但登录限速这类**仍是需求**，且必须可测试 |
| **优先级三分法缺「谁签字」** | 「可以有」档位的残余风险必须由**业务负责人**书面接受，不是开发团队自行决定——原书 3.6 未强调这一治理动作（07 章补上） |
| **安全需求被写成「不可实现的功能」** | 「系统必须是安全的」不是需求；每条安全需求都要能映射到一个**验证手段**（测试/评审/审计），映射不出的要重写 |
| **滥用案例只覆盖外部攻击者** | 内部威胁与供应链滥用（恶意维护者、被入侵的依赖）在 2008 年的需求方法里缺位；2026 年的滥用案例库必须有「恶意内部人员」「被入侵的第三方」两个常驻角色 |
| **需求冻结后再谈安全** | 威胁环境在项目生命周期内持续变化（新 CVE、新法规）；安全需求要有变更通道，与功能需求走同一个 backlog 而不是独立死文档 |

## 与其他章 / 其他书的联系

- **→ 本目录 04 章**：需求阶段的滥用案例在架构阶段升级为**威胁建模 + 攻击模式**（同一攻击者视角的两个粒度）。
- **→ 本目录 05 章**：每条安全需求最终要有一个对应的**测试**（安全测试 vs 功能测试的对照在 05 章）。
- **→ 本目录 07 章**：优先级排序的「谁签字」问题在治理章展开为风险接受与合规流程。
- **↔ `book/白帽子讲Web安全.md`**：吴翰清的漏洞章节（越权、上传、重置逻辑）可直接当**滥用案例素材库**——把每个漏洞章节反向读成滥用案例 + 需求，是最快的入门路径。
- **↔ `book/软件架构设计_程序员向架构师转型必备.md`**：功能用例图与滥用用例图的对称性，正是「功能架构 vs 安全架构」在需求层的投影。
- **↔ `book/数据库系统概念6/04-中级SQL.md`（4.4 授权）**：「对象级授权」这条最常见的隐式需求，在数据库层有现成的成熟机制（GRANT/REVOKE/角色）；需求工程的职责是**确保应用没有绕过它**。
- **↔ `book/CISSP认证考试指南.md`**：CISSP 对「安全需求获取」的考试叙述比本章更侧重合规框架（BCP/DR、法律），互为补充。
- **↔ `book/计算机安全导论.md`**：导论的「程序缺陷与恶意代码」章节是滥用案例的反面教材库——每个历史攻击案例都可以反向改写成一个滥用案例模板；先读案例再写模板，比凭空头脑风暴高效得多。
- **↔ `book/应用密码学（原书第2版）/07-密钥管理.md`**：「密钥如何产生、存储、轮换、销毁」这一整类常被漏掉的安全需求，在 Schneier 的密钥管理章有完整的生命周期清单——需求评审时按那份清单过一遍，能补上最常缺失的一组非功能需求。
- **↔ `book/Java9并发编程实战手册.md` 等并发类目**：并发正确性需求（超时、取消、背压）几乎从不出现在安全需求清单里，却直接决定可用性与 TOCTOU 暴露面——3.2 的滥用案例应包含「用时间差打你」这一类，而不只有「用恶意输入打你」。
- **→ `book/软件安全工程.md`（大纲版）**：大纲版记录的「安全需求、安全架构设计、安全编码与测试」五段式，其第一段就是本章；大纲是骨架，本章是骨架第一节的展开。
