# 第 2 章 什么使软件安全（What Makes Software Secure?）

> **一句话**：这一章是全书的概念地基——**先定义「安全软件」的属性，再给出改变这些属性的两副眼镜（防御者视角与攻击者视角），最后用「保证案例（assurance case）」把属性声明变成可论证的东西**；1975 年的 Saltzer-Schroeder 原则至今仍是这份属性清单的骨架。

## 核心精讲

> 以下全部是**教学示意，不参与构建、不编译、不运行**。

### 2.2 属性分层：核心属性与影响性属性

| 层 | 属性 | 一句话定义 | 反例 |
| --- | --- | --- | --- |
| 核心 | 机密性 | 未授权者读不到 | 侧信道把密钥时间泄露出去 |
| 核心 | 完整性 | 未授权者改不了 | 缺少 MAC 的配置文件被篡改 |
| 核心 | 可用性 | 授权者用得上 | 算法复杂度攻击耗尽 CPU（ReDoS） |
| 核心 | 可靠性 | 在故障下仍正确运行 | 错误处理路径里崩溃 |
| 核心 | 安全性行为 | 不对环境造成危害 | 特权提升后删除任意文件 |
| 影响 | 认证/鉴别 | 主体身份可验证 | 把「X-Forwarded-For」当身份 |
| 影响 | 非否认 | 行为可绑定到主体 | 日志可被管理员事后改写 |
| 影响 | 可审计 | 行为留痕且不可抵赖 | 审计日志与应用同库同权限 |
| 影响 | 隐私 | 个人数据最小化使用 | 全量日志落库，含 PII |

> 原书把「可靠性/安全性行为」与 CIA 并列为核心属性——这是软件安全区别于经典信息安全的关键：**它关心的对象是「软件的行为」而不是「信息」**。

属性之间不是独立的：机密性失效常常连带完整性失效（读到密钥就能伪造），可用性是三者里最容易被「合法流量」打崩的（ReDoS 与缓存穿透都是普通请求）；而「可审计」这类影响性属性一旦缺席，事后几乎无法区分「是攻击还是故障」。**读属性清单的正确姿势是读属性间的依赖与冲突，而不是逐条打勾。**

### 2.3.1 防御者视角：Saltzer-Schroeder 八原则的 2026 年映射

| 原则（1975） | 一句话 | 2026 年的典型实现 |
| --- | --- | --- |
| Economy of mechanism | 机制尽量简单 | 减少自研加密/自研授权；用标准件 |
| Fail-safe defaults | 默认拒绝 | IAM 默认无权限、K8s NetworkPolicy 默认拒绝 |
| Complete mediation | 每次访问都仲裁 | 服务间 mTLS + 每请求鉴权（零信任的核心） |
| Open design | 安全不依赖机制保密 | 公开设计、公开算法；秘密只在密钥 |
| Separation of privilege | 多重条件才放权 | 高危操作双签、MFA step-up |
| Least privilege | 最小权限 | 短期凭证、按任务的 RBAC |
| Least common mechanism | 共享机制最少 | 租户隔离、独立数据库账号 |
| Psychological acceptability | 易用才被用 | 密钥管理平台化、单点登录 |

> 八条原则里「Complete mediation」在 2008 年的实现是「每个入口都要检查」，在零信任语境下被重写为「**网络位置不构成豁免理由**」——这是本章最值得更新的一处。

### 2.3.2 攻击者视角：从信任边界开始

```python
# 教学示意，不参与构建、不编译、不运行
def process(order: dict, current_user: User) -> None:
    """攻击者会问的四个问题：
    1. order 从哪来？——信任边界外的每一字节都是攻击输入
    2. current_user 是谁认证的？——认证发生在哪一层，能否被旁路
    3. 什么操作需要特权？——授权检查是否在每个入口都存在
    4. 失败时会发生什么？——异常路径常常绕过检查（fail-open）
    """
    discount = order["discount"]          # 客户端传来的价格折扣 → 越权支付
    audit_log.write(current_user, order)  # 日志里可注入伪造字段
```

> 这段代码的每个注释都是一个真实 CVE 的模式。防御者视角读代码问「它对吗」，攻击者视角读代码问「**我能让它做什么它不该做的**」。

### 2.4.1 保证案例：把论证写成树

```text
Goal: 该网银系统机密性足够
├─ Strategy: 逐信任边界论证
├─ Claim: 传输层机密（TLS 1.3，禁用降级）
│   └─ Evidence: TLS 扫描报告 + 配置基线审查
├─ Claim: 存储层机密（字段级加密 + KMS 管钥）
│   └─ Evidence: 密码评审记录 + 渗透测试无密钥泄露发现
└─ Rebuttal: 已知残余风险（内部人员合法访问）→ 监控与审计缓解
```

保证案例不是文档仪式，它的价值在 **Rebuttal（反证）**：强迫团队写下「什么证据能推翻这个结论」。

### 2.4.3 保证案例在 SDLC 中的维护节奏（原书 2.4.3 的浓缩）

| 时机 | 动作 | 产出 |
| --- | --- | --- |
| 需求冻结后 | 建立属性目标与论证骨架 | 案例 v0（claim 树） |
| 设计评审 | 每条 claim 挂缓解设计 | 案例 v1（strategy 层充实） |
| 每个里程碑 | 用测试/扫描结果填 evidence | 可验证的当前版本 |
| 变更与事故后 | 优先更新 Rebuttal 与残余风险 | 活文档 |
| 发布前 | 走一遍论证：哪条 claim 已经不再成立？ | 发布决策的输入之一 |

> 表格要传达的是：保证案例死在「发布前突击写一遍」；活案例的维护成本其实很低——它复用的是测试与扫描本来就要产出的证据，只是**按属性组织**了一次。

## 版本演进

| 年份 | 事件 |
| --- | --- |
| **1975** | **Saltzer & Schroeder《The Protection of Information in Computer Systems》**：八条设计原则（经济性、最小权限、开放设计、完全仲裁、失效安全、特权分离、最小公共机制、心理可接受性）成为本章属性讨论的源头 |
| 1998–2001 | 「软件安全」术语确立；Viega & McGraw《Building Secure Software》把属性落到代码层 |
| 2004–2006 | McGraw 系列著作 + BSI 网站把「属性 → 视角 → 规约」的框架标准化 |
| **2008** | **本书出版**：assurance case 作为一章的收束 |
| 2010 | ISO/IEC 27034「应用安全」系列陆续发布：应用安全生命周期管理的国际标准坐标 |
| 2014 | Shostack《Threat Modeling》把 2.3.2 的攻击者视角工程化为「四问框架」 |
| 2020 | **NIST SP 800-207 零信任架构**发布：信任边界从网络层移到「每一次请求」，2.3.2 的视角被架构化 |
| 2021 | OWASP API Security Top 10：BOLA（对象级授权失效）排名第一——2.3.2 的「current_user 是谁认证的」至今是最常见漏洞 |

| 2022–2026 | 机密计算（Confidential Computing，TEE 隔离）与可验证构建（SLSA）把「核心属性」延伸到计算中的数据与构建链 |
| 2025–2026 | AI 系统的安全属性讨论兴起：模型输出的完整性、提示注入下的机密性——属性词汇表正在被推向「概率性行为」的新对象 |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：属性清单没变，但**属性的实现地点**大迁移——从应用代码移到「身份与基础设施」：零信任把机密性/可用性的一部分责任上移到服务网格与身份层；签名与可验证构建把完整性延伸到制品供应链。

- **零信任**：2.3.1 的「完全仲裁」原则在 2026 年的实现形态是 mTLS + 服务身份（SPIFFE 类）+ 默认拒绝的授权策略；「边界内即可信」成为本书出版时未被点破的头号过时假设。
- **密钥管理平台化**：核心属性里的机密性，其工程难点从来不是加密算法而是**密钥放哪、谁换、谁审计**——Vault 类平台把 Saltzer-Schroeder 的「心理可接受性」做成了产品。
- **完整性上移到供应链**：制品签名（sigstore/cosign 的 keyless 签名）与 SLSA 等级把「完整性」从「传输/存储时」扩展到「构建时」，这是原书完全没有的属性实现层。

| 仓库 | star | 说明 |
| --- | --- | --- |
| `hashicorp/vault` | **36294★**（2026-09-25 实测） | 机密性实现层的平台化样本：动态密钥、租期、审计 |
| `sigstore/cosign` | **6326★**（实测） | 完整性属性的供应链延伸：无密钥签名 + 透明日志 |

| `ossf/scorecard` | **5709★**（实测） | 把属性清单变成开源项目的可自动评测记分卡 |

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **隐含「网络边界」的信任模型** | 原书 2.3 的视角讨论未明确否定「内网可信」；2026 年零信任（SP 800-207）下，**信任边界是最小可验证单元（一次请求/一个函数）**，DFD 的信任边界要画到服务与用户数据对象级 |
| 🔧 **assurance case 实践未成主流，要如实承认** | 原书对 assurance case 寄望很高；现实是除安全关键行业（航空/汽车/医疗）外，Web/互联网行业几乎没人维护它——现代等价物是「威胁建模记录 + 合规基线（SSDF）+ 漏洞预算」，写法不同但功能类似 |
| 🔧 **隐私属性止步于「最小化使用」** | 2018 年 GDPR 之后，隐私从属性变成法律义务（数据主体权利、DPIA、被遗忘权）；隐私工程（privacy engineering）自成学科，本书完全没有 |
| **把 CIA 三元组当安全定义的全部** | 原书已经把可靠性/安全性行为列为核心属性，但读者常只记住 CIA；**软件安全的独特之处恰在「行为」二字**——攻击者操纵的是行为不是数据本身 |
| **属性清单当 checklist 用** | 属性之间有张力（可用性 vs 机密性的备份恢复、可审计 vs 隐私），逐条打勾会漏掉冲突；正确用法是逐条过**冲突** |
| **「开放设计」原则被误读为「开源即安全」** | Saltzer-Schroeder 的本意是「安全不依赖机制保密」，与代码是否公开无关；把密钥藏代码里（security by obscurity）才是它反对的（秘密扫描见 05 章 trufflehog） |
| **核心属性被窄化为 CIA 三元组本身** | CIA 是信息安全的属性；软件安全的核心属性还包括**行为层的可靠性/安全性行为**——只背 CIA 的读者会漏掉「攻击者操纵行为」这半边 |
| **2.3.2 的「攻击者视角」被练习成固定套路** | 攻击者视角的价值是**质疑假设**（这里信任谁、那里凭什么），不是背「OWASP 十大」；套路化的威胁清单恰恰会漏掉新形态（如 AI 提示注入这类没有历史条目的攻击） |
| **保证案例（2.4）被写成合规文档** | assurance case 死于「只写 Rebuttal 不维护证据」；若没有 CI 数据（测试结果、扫描基线）持续喂给它，它只是发布前的写作练习 |
| **「核心属性」与「影响性属性」被记成固定两层** | 分层是分析工具不是教条：同一个属性（如可审计）在不同系统里可能从「影响层」升到「核心层」（如支付/医疗系统）；读原书时要按自己的资产重排层 |
| **攻击者视角讨论止于技术对手** | 2.3.2 的攻击者画像在 2026 年应包含「被滥用的合法用户」与「被入侵的第三方依赖」——两者都不违反任何技术假设，却是最常见的现实入口 |

## 与其他章 / 其他书的联系

- **→ 本目录 03 章**：属性定义之后，第一个落点是把它们写成**需求**（滥用案例 + SQUARE）。
- **→ 本目录 04 章**：防御者视角的原则/模式在架构风险分析里变成威胁建模与缓解设计。
- **→ 本目录 06 章**：属性的「涌现失效」——每个组件都满足属性，拼起来却不满足（授权检查被装配路径绕过）。
- **↔ `book/应用密码学（原书第2版）/02-协议构件.md`**：本章的核心属性在密码学层有精确的原语对应——机密性↔对称加密、完整性↔MAC/AEAD、认证↔数字签名；Schneier 的「协议构件」就是属性的构件化。但注意：**原语正确 ≠ 使用正确**，见 05 章。
- **↔ `book/数据库系统概念6/04-中级SQL.md`（4.4 授权）**：`GRANT/REVOKE` 与角色是「最小权限 + 完全仲裁」在数据层的直接实例；数据库做对了几十年，应用层反而经常在代码里绕过它。
- **↔ `book/CISSP认证考试指南.md`**：CISSP 的 Security & Risk Management / Security Architecture 域就是本章的认证级展开（Saltzer-Schroeder 八原则是必考点）。
- **↔ `book/C++并发编程实战2/03-线程间共享数据.md`**：数据竞争是「核心属性之完整性」在并发层的破坏者——两个线程无同步地写共享状态，本质上就是「未授权的篡改」，只是授权者搞错了自己；并发正确性是行为属性（可靠性）的实现前提。
- **↔ `book/计算机安全导论.md`**：本章 2.2 的属性分层与导论的安全目标章节一一对应，但导论以系统/网络为对象、本章以软件行为为对象——同一套词汇在两个粒度上使用时含义有偏移，对照读可以避免术语混淆。
- **↔ `book/Java并发编程深度解析与实战.md`**：可用性属性在并发层的经典失守是「活锁/死锁/线程池耗尽」——不涉及任何恶意输入，却让 DoS 类攻击的判定从「资源不够」变成「设计没抗住合法流量」；属性分析要同时考虑故障模式与攻击模式。
