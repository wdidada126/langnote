# 《软件安全工程：项目经理指南》总览与阅读地图

> **一句话**：这本书把「软件安全」从渗透测试和漏洞修补拉回到工程学的主场——**安全不是加在发布前的检测环节，而是嵌入 SDLC 每个阶段的工程实践**；它教你以攻击者视角定义「足够好的（good enough）」安全，而它 2008 年的漏洞统计与工具清单，在 2026 年需要一整层现代化重写（SBOM、内存安全语言、模糊测试工业化、DevSecOps）。

## 2. 关于本目录与「大纲版」的关系

- **本目录是深度重写版**，按原书 8 章重组为 8 个章节文件，每个文件含：本章地图 ⟶ 核心精讲（教学示意代码）⟶ 版本演进 ⟶ 经典论文与原始文献 ⟶ 近年研究与工业界开源实践（2015–2026）⟶ 常见误区与本书需修正之处 ⟶ 与其他章/书的联系。
- **大纲式单文件在此**：`book/软件安全工程.md`（清单式大纲，记录核心思想与配套资源）。
  > 两处互链：本目录是深度重写版；`book/软件安全工程.md` 的大纲**不得修改、不得删除**，二者并存互补。本目录所有章节文件只链接该大纲，绝不改动它。
- **不编造章节**：所有章名与节号均取自 Pearson 官方 TOC（`pearson.de` 目录 PDF）与 InformIT 页面核实结果。原书**没有**独立的「威胁建模」「供应链安全」「DevSecOps」章，这些内容以各章「版本演进 / 常见误区」的 🔧 条目补齐，必要时标明是跨章主题。

## 3. 全书结构与文件映射（原书目录已核实）

| 文件 | 对应原书章 | 核心主题 |
| --- | --- | --- |
| 01-安全为何是一个软件问题.md | Ch1 *Why Is Security a Software Issue?* | 软件保证与软件安全之辨、不安全之源（分布式/可扩展/互联）、缺陷早发现的收益、风险管理框架 |
| 02-什么使软件安全.md | Ch2 *What Makes Software Secure?* | 安全核心属性（机密性/完整性/可用性 + 可靠性/安全性行为）、防御者视角 vs 攻击者视角、安全保证案例（assurance case） |
| 03-安全软件的需求工程.md | Ch3 *Requirements Engineering for Secure Software* | 滥用/误用案例（misuse & abuse cases）、**SQUARE 流程模型**（Mead）、需求获取与优先级排序 |
| 04-安全软件架构与设计.md | Ch4 *Secure Software Architecture and Design* | 架构风险分析（软件刻画→威胁分析→架构漏洞评估→风险判定→缓解）、安全原则/指南/**攻击模式**（attack patterns） |
| 05-安全编码与测试.md | Ch5 *Considerations for Secure Coding and Testing* | 代码分析（静态/动态）、编码实践（CERT 规则）、安全测试 vs 功能测试、贯穿 SDLC 的安全测试 |
| 06-安全与复杂性-系统组装的挑战.md | Ch6 *Security and Complexity: System Assembly Challenges* | 安全失效分类、功能视角 vs 攻击者视角（Web Services 双案例）、复杂性驱动因素、深技术难题 |
| 07-治理与更安全软件的管理.md | Ch7 *Governance, and Managing for More Secure Software* | 治理与安全、企业软件安全框架（ESF）、「多少安全才够」、安全与项目管理、实践成熟度 |
| 08-如何起步.md | Ch8 *Getting Started* | 从哪开始：差距分析、BSI 资源、按成熟度与风险容忍度选择实践组合 |

> 原书正文只有 8 章（各章均以 Summary 收尾），没有「第四部分/第五部分」式分组；BSI 网站文献单列在参考文献之后。

**阅读顺序建议**：

- 建立框架 → 01→02→03→04→07（需求→设计→治理主线）；
- 只解决手头问题 → 05（编码测试）与 06（集成/组装）；
- 推动组织变革 → 07→08（治理与落地）。

## 4. 版本演进时间轴（2008 成书 ⟶ 2026）

| 年份 | 事件 | 对本书的冲击 |
| --- | --- | --- |
| **2008** | **原书出版**（成书于 DHS BSI 网站内容） | 本书的「当前时刻」：McGraw 的 Software Security: Building Security In（2006）已成方法论圣经，Microsoft SDL 2004 起内部强制 |
| 2009 | **BSIMM 第一版发布**（McGraw、Chess、Migues，基于 9 家企业实测数据） | 把 Ch7 的「实践成熟度」从定性行动清单变成可计量的基准 |
| 2011 | ISO/IEC 27034「应用安全」系列开始发布 | 给 Ch3/Ch4 的流程建议补上国际标准坐标 |
| 2014 | **Shostack《Threat Modeling: Designing for Security》** 出版；Heartbleed（CVE-2014-0160）暴露 OpenSSL 单点维护困局 | Ch4 的威胁分析获得现代标准操作框架；开源依赖风险首次成为头条 |
| 2015 | AFL 由 Google Project Zero 接手为 **AFL** 持续改进；**OSS-Fuzz**（2016 年）启动 | Ch5 的「黑盒模糊测试」被覆盖率引导的持续模糊测试彻底工业化 |
| 2018 | 微软 MSRC 报告约 **70% 漏洞是内存安全问题**；**xkcd 2347**（2018）成为传递依赖的经典隐喻 | Ch5 编码实践的「结论」被重写：换语言比补漏洞更划算 |
| 2019–2022 | **Google Android 内存安全漏洞占比从 76% 降至 35%**（2022 年起 Rust 代码占新代码比过半） | 内存安全语言转向是本书出版时无法想象的工程事实 |
| 2021 | **US Executive Order 14028**（5·12 行政令）→ NIST **SP 800-218 SSDF**（2022）；**Log4Shell**（CVE-2021-44228） | Ch6「系统组装」的预言成真：传递依赖的漏洞一夜间打穿全球；SBOM 从学术议题变成合规要求 |
| 2022 | **SLSA v1.0**（2023）与 sigstore 规模部署；CISA **KEV** 与 FIRST **EPSS** 上线 | Ch5/Ch6 的漏洞清单思维（2008 年的 CVE 列表）被「实际被利用概率」取代 |
| 2023 | **BSIMM14**：数据扩展到 130+ 家企业；OWASP Top 10 2021 版把 **A06 易受攻击/过时组件**首次抬进前十 | Ch7 的成熟度叙事从「劝导」变成「行业基准」 |
| 2024 | **EU Cyber Resilience Act（CRA）正式通过**（2027 年全面适用）；NIST SP 800-207 零信任架构已广泛落地 | 「足够好的安全」第一次被法律写死了底线：SBOM、漏洞处理时限、安全更新义务 |
| 2025–2026 | LLM 辅助代码审计进入 CI 流水线（SAST 误报与漏报问题依旧）；Rust 进入 Linux 内核主线 | 05 章的工具清单需要整个换代，但「自动化工具不等于安全」的告诫反而更响了 |

> **最重要的一条订正**：本书反复用 2008 年的漏洞统计与「攻击面在变大」说理——方向全对，但**证据链已整体过期**。2026 年的说服工具是：70% 内存安全漏洞数据、Android 的 Rust 实证、Log4Shell 的供应链案例、EU CRA 的法律强制。见各章「常见误区」的 🔧 行。

## 5. 本书没覆盖的缺口（2026 视角）

| 缺口 | 说明 | 补到哪里 |
| --- | --- | --- |
| **软件供应链安全** | SBOM（SPDX/CycloneDX）、SLSA 供应链完整性等级、传递依赖（xkcd 2347）在书中完全没有——2008 年的主流还是「自研为主 + COTS 组件」 | 06 章「版本演进 / 误区」 |
| **内存安全语言转向** | Rust/C++ 之争、Microsoft/Google/Android/Linux 内核的采用数据，本书写作时 Rust 1.0 还没发布（2015） | 05 章「版本演进」 |
| **模糊测试工业化** | 书中的 fuzzing 还停留在随机输入层面；AFL++/libFuzzer/OSS-Fuzz 的覆盖率引导与持续集成完全没有 | 05 章「核心精讲 / 版本演进」 |
| **DevSecOps** | 2008 年没有 CI/CD 门禁、pre-commit 钩子、Dependabot 式自动 PR；「左移」在敏捷语境下完全是另一套工程化 | 07 章、08 章 |
| **零信任与身份** | 书中安全属性讨论隐含「边界防御」前提；NIST SP 800-207（2020）之后「服务身份、最小权限、默认拒绝」是架构层议题 | 04 章「误区」 |
| **漏洞管理现代化** | CVE/CVSS 之外，CISA KEV、EPSS、OSV 的「优先级治理」缺失；SCA（依赖扫描）作为工具类目尚未诞生 | 05/06 章 |
| **AI 辅助审计** | LLM 辅助 SAST 的现状与局限（误报率高、不可复现、可被投毒）需要单独的批判性视角 | 05 章「误区」 |

## 8. 写作约定

- 每个章节文件首行为 `# 第 N 章 标题`，紧接 `> **一句话**：…`；
- 随后固定七个一级小节：本章地图 / 核心精讲 / 版本演进 / 经典论文与原始文献 / 近年研究与工业界开源实践（2015–2026）/ 常见误区与本书需修正之处 / 与其他章 / 其他书的联系；
- 核心精讲中的代码一律标注「**教学示意，不参与构建、不编译、不运行**」；
- 涉及 star 的数字全部为 `gh api` 实测（2026-09-25），未实测的一律不写；
- 🔧 标记 = 原书 2008 年出版、中文版 2009 年，2026 年必须补的新内容。
