# 第 7 章 治理与更安全软件的管理（Governance, and Managing for More Secure Software）

> **一句话**：这一章回答「组织层面怎么让前面六章真的发生」——**治理（谁对安全负责）→ 企业软件安全框架（ESF）→ 「多少安全才够」（风险管理回答）→ 项目管理与实践成熟度**；2008 年它在「劝导」，2026 年 BSIMM 数据基线、SSDF 采购条款和 EU CRA 已经把它的建议写进了合同与法律。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 7.1 | 引言 | 技术实践不会自发落地，缺的是治理与管理 |
| 7.2 | 治理与安全 | 治理 = 明确目标、职责、度量、问责；安全的治理常常挂在 CISO 与 CIO/CTO 的缝隙里 |

## 核心精讲

> 以下全部是**教学示意，不参与构建、不编译、不运行**。

### 7.2 治理的四个问题（原书的浓缩）

```text
① 目标：我们的安全目标与业务目标如何对齐？（保护什么资产、防什么对手）
② 职责：谁批准风险、谁执行实践、谁验证效果？（无主之风险 = 必然失控）
③ 度量：用什么证据说明实践在生效？（指标要可行动，不是「漏洞数」单指标）
④ 问责：度量不好看时发生什么？（奖惩、资源再分配）
```

### 7.2 治理四问 → 指标示例（自检对照）

| 治理问题 | 一个可行动的指标 | 反面指标（勿用） |
| --- | --- | --- |
| 目标对齐 | 关键资产覆盖威胁模型的比例 | 「安全意识提升」 |
| 职责明确 | 每条残余风险都有具名接受人 | 「安全团队负责所有漏洞」 |
| 度量有效 | 高危漏洞 MTTR 趋势 + 门禁逃逸率 | 漏洞总数（随扫描强度波动） |
| 问责闭环 | 被接受风险的复审按时完成率 | 事故后的临时报告 |

### 7.3 企业软件安全框架（ESF）四支柱

| 支柱 | 角色 | 2026 年的形态 |
| --- | --- | --- |
| 治理（Governance） | 战略、预算、跨团队协调 | 安全委员会 + 产品安全负责人（Product Security Lead，业界现职位） |
| 安全技术开发者 | 让开发者有能力写出安全代码 | 内部安全 champs（安全大使）网络 + 培训（LLM 时代的定向演练） |
| 通用构建基础设施 | 把安全能力做成共享平台 | CI/CD 门禁模板、内部 SAST/SCA 服务、内部威胁建模模板 |
| 风险与合规顾问 | 法规、审计、风险接受 | SSDF/CRA/SOC 2 合规映射 + 残余风险台账 |

> 原书明确说：第 8 步只在需要时做。**SQUARE 的精神是「排序与裁剪」而不是「全都要」**——治理亦然：四支柱不是四个部门，而是四类职责，可以由很少的人跨团队承担。

### 7.5 安全与项目管理：差距分析的浓缩问题单

| 问题域 | 原书 7.5 的典型访谈问题 | 有问题的信号 |
| --- | --- | --- |
| 需求 | 安全需求怎么进排期？谁批准裁剪？ | 「开发完再让安全团队看看」 |
| 设计 | 架构变更时谁做安全评审？ | 无评审记录，或评审无人拍板 |
| 编码 | 静态分析结果谁 triage？修复 SLA 是多少？ | 扫描器开着但没人处理告警 |
| 测试 | 安全测试通过标准是什么？ | 「渗透测试没报高危就算过」 |
| 部署/运维 | 新 CVE 公告后多久能出结论？ | 无 SBOM、组件清单靠人肉回忆 |
| 度量 | 上季度修了多少、返工多少、逃逸多少？ | 只有「漏洞总数」一个口径 |

> 这张表是「自检版」：任何一个问题域打问号，就回到对应章（03–06）找具体实践——治理的差距分析不是打分表演，是**给 03–06 章的实践找缺口**。

### 7.4 风险管理框架（原书 7.4 的循环）

```python
# 教学示意，不参与构建、不编译、不运行
def risk_management_loop(assets, threats):
    identify = lambda: [(t, t.exploit_likelihood, t.impact) for t in threats]   # 识别
    analyze  = lambda rs: sorted(rs, key=lambda r: -(r[1] * r[2]))             # 分析排序
    plan     = lambda rs: pick_controls(rs, budget=security_budget)            # 计划（预算内）
    track    = lambda: audit_metrics()                                          # 跟踪
    control  = lambda: re_review_quarterly()                                    # 控制与复审
    return identify, analyze, plan, track, control
```

### 7.6 成熟度自评（示意刻度）

| 级别 | 特征 | 典型证据 |
| --- | --- | --- |
| 0 无意识 | 「我们没被黑过」 | 无任何安全实践记录 |
| 1 项目级 | 少数项目自发做安全评审 | 局部文档，无复用 |
| 2 组织级 | 有标准实践与基础设施 | CI 门禁、培训、安全需求模板 |
| 3 度量级 | 有数据驱动的改进循环 | BSIMM 类基准测量、指标看板、回归追踪 |
> 0→2 级靠的是**开始做**（工具与流程），2→3 级靠的是**坚持做**（数据与习惯），3→4 级靠的是**组织能力**（懂威胁、懂业务的人）。多数组织卡在 2→3：工具买了、流程定了，但没有「每月看一次数据、砍掉一个无效实践」的循环——成熟度不是级别而是循环本身。

## 近年研究与工业界开源实践（2015–2026）

**趋势**：本章的「劝导性」内容基本全部被**数据与法规**取代——治理叙事从「你应该做」变成「你的同行做到了什么程度（BSIMM）」和「法律要求你至少做到什么（SSDF/CRA）」。

- **BSIMM 的实证价值**：13 版迭代下来最有用的结论是——高成熟度组织普遍配置**专职安全大使（安全 champs）**、把 SAST/SCA 做成内部平台服务、有明确的产品安全负责人；ESF 四支柱在数据里全部显形，只是换了名字。
- **DevSecOps 指标**：MTTR（漏洞平均修复时长）、门禁逃逸率、SBOM 覆盖率、威胁建模覆盖率进入工程效能看板——「度量」（7.2 问题③）终于有了行业标准指标集。
- **合规即产品需求**：SSDF 自评表 + SBOM + CRA 技术文档成为 B2B 软件的投标材料；「多少安全才够」在受监管行业第一次有了**法定下限**。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **「实践成熟度」（7.6）缺少数据基准，已被 BSIMM/SAMM 取代** | 原书的自评刻度无行业参照；2026 年的做法是 BSIMM 测量（与 130+ 家企业对比）或 SAMM 自评，再定改进路线 |
| 🔧 **「多少安全才够」缺法定下限** | 2026 年受监管场景已有硬底线：SSDF 采购条款、EU CRA 义务、各行业数据保护法规；风险接受不能低于法定义务 |
| 🔧 **DevSecOps 缺席** | 原书时代无 CI/CD 普及前提；2026 年治理的主战场是流水线（门禁策略、指标看板、自动化依赖升级），ESF 的「通用构建基础设施」支柱几乎是为此准备的 |
| 🔧 **云责任边界未讨论** | 原书的组织边界是「我们自己的开发」；云原生下治理要覆盖「谁对镜像、IaC、托管服务配置负责」——云共享责任模型是新的治理对象 |
| **「治理 = 成立安全部门」** | 治理的核心是职责与度量，不是编制；最有效的形态往往是「平台化基础设施 + 各产品线的安全大使」，而非庞大的集中式安全团队 |
| **成熟度模型当 KPI 玩** | 为过评估而堆文档与成熟度模型本身是治理失败的经典症状；BSIMM 的方法论价值恰在**看别人实际做了什么**，不是给文档打分 |
| **风险台账写成一次性文档** | 台账是活文档：新 CVE（KEV 命中）、架构变更、审计发现都应触发复审；「签字接受」之后无人跟踪是最常见的失效模式 |
| **ESF 四支柱被建成四个部门** | 支柱是职责分类不是组织架构图；2026 年的主流形态是 5–15 人的平台安全组 + 各产品线兼职安全大使，集中式大军普遍被证明低效 |
| **7.2 的「治理与安全」被读成 CISO 一个人的事** | 原书指出安全治理常挂在 CISO 与 CIO/CTO 的缝隙里——2026 年的共识是**产品负责人对产品残余风险负责**，安全团队提供能力与验证，不背业务风险 |
| **合规与安全被划等号** | SSDF/CRA 是下限不是目标；「通过审计」与「攻击者打不穿」是两个集合，重叠但不重合——把合规验收当安全完成是治理最贵的错觉 |
| **7.5 的差距分析表只做一次** | 原书把差距分析当起点，但治理成熟度的证据是**复测的差值**；每年一次复测（配合 BSIMM/SAMM 口径）比一次性的完美报告有用得多 |
| **安全指标与业务指标脱钩** | 只报「漏洞数/修复率」的管理层很快会失去兴趣；把指标翻译成业务语言（可交付性、合规资格、事故止损）是 7.2 治理四问里「度量」一问的真正难点 |
| **ESF 采用被当成一次性项目** | 框架落地有回潮期（裁员、换 CTO、赶工期）；治理设计时要预设「最低不可回退集」——哪几条实践无论压力多大都保留（通常是门禁与响应 SLA） |
