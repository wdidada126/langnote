# 第 5 章 安全编码与测试的考量（Considerations for Secure Coding and Testing）

> **一句话**：这一章把安全落到「每一行代码 + 每一个测试」——**代码分析（静态/动态）、编码实践（CERT 规则）、安全测试（与功能测试相对）**；2008 年它讲的是「用什么工具扫什么漏洞」，2026 年同一章的答案变成「换内存安全语言 + 把模糊测试挂进 CI」。

## 核心精讲

> 以下全部是**教学示意，不参与构建、不编译、不运行**。

### 5.2.1 常见代码级漏洞：2008 vs 2026 的版图变化

| 类别 | 2008 年地位 | 2026 年地位 |
| --- | --- | --- |
| 缓冲区溢出/越界 | 头号漏洞 | **被语言层消灭**（Rust/Go/Java 不给这个机会）；C/C++ 中靠 safe API + 工具缓解 |
| 注入（SQL/命令） | 头二漏洞 | 依然在 OWASP Top 10，但框架层参数化已大众化 |
| 硬编码凭证 | 提一句 | **独立工具类目**（秘密扫描，pre-commit + 历史回扫） |
| 依赖中的已知漏洞 | 未成类目 | **SCA 工具类目**，CI 门禁常客 |
| 反序列化/业务逻辑 | 零散讨论 | Java 反序列化与逻辑漏洞成为测试焦点，纯静态工具基本无能为力 |

### 5.2.2 静态分析：原理与不可逾越的天花板

```python
# 教学示意，不参与构建、不编译、不运行
def sql_query(user_input: str) -> None:
    # SAST 工具能抓到的：字符串拼接进查询（污点从 source 流向 sink）
    cursor.execute("SELECT * FROM users WHERE name = '" + user_input + "'")  # ← 报警

    # SAST 抓不到的：跨三个服务的业务逻辑漏洞
    # "重置链接的 token 用用户 ID + 日期哈希生成，可预测" —— 需要人评审
```

> 静态分析的三难：**误报、漏报、上下文**。数据流/污点分析擅长「source→sink」模式；业务逻辑漏洞几乎全部漏掉。2026 年 LLM 辅助审计提高了「可疑点召回」，但**不可复现、可被注入注释操纵**，只能当 triage 助手，不能当门禁。

使用静态分析的成熟姿势是**基线式管理**：先对存量代码建立「已知发现」基线，门禁只拦**新增**违规，然后按风险逐步消化存量——一步到位清零误报既不可能也会让团队把工具整个关掉。SAST 的治理成本（triage 人力）常常超过工具本身，规划工具时要连人一起规划。

### 5.3 编码实践：三层规则来源（原书 5.3.1 的展开）

| 层 | 来源 | 特点 |
| --- | --- | --- |
| 语言/平台层 | 编译器警告、safe API（`strncpy_s` 类）、语言级内存安全 | 成本最低，能用编译器就别用规则 |
| 组织规则层 | CERT 规则、公司内部 style + 安全会审约定 | 可 lint 化的优先，纯人审规则要定期淘汰 |
| 领域标准层 | MISRA（汽车）、DO-178C 配套（航空）、支付 PCI-DSS 要求 | 合规驱动，有法定效力 |

> 原书写作时只有后两层；2026 年第一层的权重显著上升——**语言选择本身正在变成最重要的编码实践**。

### 5.4.1 安全测试 vs 功能测试

| 维度 | 功能测试 | 安全测试 |
| --- | --- | --- |
| 判定标准 | 规格说明书 | 攻击者模型（软件**不**做什么） |
| 输入域 | 典型值 + 边界值 | 全域随机 + 恶意构造 |
| 通过条件 | 行为符合预期 | 行为在攻击下**可预期**（不崩、不泄露、不提权） |
| 典型技术 | 单元/集成/系统测试 | 模糊测试、渗透测试、SCA、DAST |
| 失败特征 | 缺陷（bug） | 漏洞（vulnerability），可被武器化 |

### 5.5.2 模糊测试：从随机输入到覆盖率引导

```text
2008 年的书：随机/变异模糊测试（黑盒为主，效果看运气）
   ↓ 2013 AFL（Zalewski）：覆盖率反馈引导
   ↓ 2015–2017 AFL++ / libFuzzer：进程内 + 插桩 + 语料库
   ↓ 2016– OSS-Fuzz：大规模持续模糊测试（GitHub 开源项目全覆盖）
2026：结构感知 + 差异化对比 + AI 语料生成；工业界默认配置
```

```c
// 教学示意，不参与构建、不编译、不运行
// libFuzzer 风格的 harness：一行 harness 让解析器接受百万级输入轰炸
#include <stdint.h>
#include <stddef.h>

int parse_header(const uint8_t *data, size_t len);   // 被测解析器

int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    parse_header(data, size);   // 崩溃 = 漏洞 + 最小化复现用例自动落盘
    return 0;
}
```

> OSS-Fuzz 的成绩单（Google 公开数据，2026 年口径）：累计为 **1000+ 开源项目**报告 **上万条**漏洞与数万条缺陷——这是原书时代任何 fuzzing 工具都无法想象的产出。

## 版本演进

| 年份 | 事件 |
| --- | --- |
| 2004 | CERT《Secure Coding in C and C++》（Seacord）确立规则集形态；OWASP Top 10（2003 首版）成为 Web 漏洞知识普及载体 |
| **2008** | **本书出版**：SAST/DAST 尚在早期，fuzzing 是安全专家的小众手艺 |
| **2013** | **AFL**（american fuzzy lop）发布：覆盖率引导模糊测试让 fuzzing 的投入产出比质变 |
| 2015–2017 | **libFuzzer**（进程内、库级 harness）与 **AFL++** 成熟；模糊测试成为编译器/解析器开发的标准配置 |
| **2016** | **OSS-Fuzz** 启动：开源项目持续模糊测试平台 |
| 2019–2022 | **内存安全数据**：MSRC ~70%（2019）、Chromium ~70%（2020）、Android 引 Rust 后内存安全漏洞 76%→35%（2019→2022，Google 公布）；**Rust 进入 Linux 内核主线**（2022 起） |
| 2021 | **Log4Shell**：SCA 从建议性工具变成 CI 门禁；OWASP Top 10 2021 把 **A06 易受攻击与过时组件**首次纳入前十 |
| 2022 | **NIST SP 800-218 SSDF**：编码与测试实践（PW 组）成为可审计清单；CISA **KEV** + FIRST **EPSS** 让「修哪个 CVE」有了优先级依据 |
| 2023–2026 | LLM 辅助代码审计进入 IDE/CI（召可疑点、生成修复建议），同时引入新风险（生成代码本身含漏洞、注释投毒）；Dependabot/renovate 把依赖升级自动化 |
| 2021 | OWASP Top 10 2021 版发布：**A06 易受攻击与过时组件**首次进入前十，SCA 的行业地位在清单层面被承认 |

## 近年研究与工业界开源实践（2015–2026）

**趋势**：本章是全书被时代改造最深的一章——**最大的杠杆从「更好的工具」变成了「更好的语言」**，最大的自动化成果从 SAST 变成了 fuzzing 与 SCA 的 CI 化。

- **内存安全语言转向**：Microsoft/Google/Android/Linux 内核的采用数据（见「版本演进」）说明：对 C/C++ 系统代码，**迁移高危组件比修补更划算**；本书出版时 Rust 1.0（2015）尚未发布。
- **模糊测试工业化**：AFL++/libFuzzer/OSS-Fuzz 把 5.5.2 的「测试库与可执行文件」变成持续基础设施；微软 onefuzz 把同样模式带到 Azure 生态。
- **漏洞优先级**：CVSS 分数 ≠ 实际风险；CISA KEV（已知被利用漏洞）与 EPSS（利用概率预测）+ OSV（结构化漏洞数据库）构成现代 triage 三件套。
- **秘密永不进仓库**：trufflehog 式历史回扫 + pre-commit 钩子让「硬编码凭证」从 CV 里可查到 CI 里可拦。

## 常见误区与本书需修正之处

| 问题 | 说明 |
| --- | --- |
| 🔧 **工具清单整体过期，但结论反而更硬** | 书中列的静态分析器已换代；2026 年的等价物是 codeql/semgrep/Trivy + 门禁策略；不过「自动化工具不能替代人评审」的告诫在 LLM 时代**更加成立** |
| 🔧 **内存安全漏洞按「编码实践可解决」叙述** | 70% 数据（MSRC/Chromium）与 Android Rust 实证说明：对系统代码，**语言选择比任何规则集杠杆都大**；CERT 规则仍有价值但定位是「不可迁移代码的止损」 |
| 🔧 **模糊测试只有一小节且是 2008 年形态** | 覆盖率引导 + 持续化后，fuzzing 是投入产出比最高的自动化安全测试；新解析器/协议实现应默认带 harness |
| 🔧 **无 SCA/依赖测试类目** | 2008 年无此概念；2026 年 Log4Shell 之后 SCA 是 CI 标配，且与 SBOM（06 章）联动 |
| 🔧 **漏洞清单按 CVE 数量说话** | 现代优先级 = KEV（是否被在野利用）+ EPSS（被利用概率）+ 资产暴露面；只按 CVSS 高分排序会修掉一堆没人打的漏洞 |
| **「代码分析」被理解成「跑一遍扫描器」** | 扫描器的价值取决于**处置流程**：误报 triage 责任人、抑制策略、修复 SLA；没有流程的门禁最后总是被跳过 |
| **渗透测试被当作验收手段** | 渗透测试是**抽样验证**不是质量保证——过不了测试说明有问题，过了不代表没有问题；它无法覆盖业务逻辑漏洞的广度 |
| **5.3 编码实践被当成 C/C++ 专属** | 原书语境以系统代码为主；2026 年的编码实践清单要覆盖语言无关的类目：反序列化安全、并发安全、正则复杂度（ReDoS）、日志注入、时序侧信道（比较秘密时用常量时间比较） |
| **安全测试结果不做回归** | fuzzing 找到的 crash 用例、渗透测试的 PoC、SAST 的抑制清单都应该进版本库做回归——否则同一个洞会在重构后原地复活 |
| **「覆盖率」沿用功能测试口径** | 安全测试的覆盖率口径不同：入口点覆盖、信任边界覆盖、攻击面覆盖比行覆盖率更能预测残余风险；用行覆盖率汇报安全测试属于度量错位 |

## 与其他章 / 其他书的联系

- **→ 本目录 04 章**：编码级漏洞的上游是架构级缺陷（信任边界没画对，代码写对也白搭）；反之 SAST 的发现要回流到威胁模型。
- **→ 本目录 06 章**：「测试库与可执行文件」（5.5.2）在依赖时代膨胀成整个 SCA/SBOM 议题，见 06 章系统组装。
- **↔ `book/C++并发编程实战2/03-线程间共享数据.md` 与 `11-多线程应用的测试和除错.md`**：数据竞争是最难被 SAST 抓住的类目之一（TSan 之外大多漏报）；并发代码的安全测试必须专用工具——这是 5.4「安全测试 vs 功能测试」最尖锐的实例。TOCTOU（检查-使用竞态）本身是安全与并发的交叠缺陷。
- **↔ `book/应用密码学（原书第2版）/12-单向哈希函数与MAC.md`**：该章「HMAC 必须用常量时间比较」的告诫是编码实践（5.3）的典型条目——原语正确、实现错误照样漏洞（定时侧信道）。
- **↔ `book/白帽子讲Web安全.md`**：白帽子书逐个展开 5.2.1 的漏洞原理与利用；本书提供的是「把它们挡在编码与测试阶段」的工程流程。
- **↔ `book/数据库系统概念6/04-中级SQL.md`**：SQL 注入的最优解（参数化/绑定变量）本质是**使用数据库既有机制**；授权绕过类漏洞的验证测试可参照其 4.4 的权限模型设计用例。
- **↔ `book/C++并发编程实战2/05-Cpp内存模型与原子操作.md`**：内存模型是理解「为什么 fuzzing 抓不到并发缺陷」的钥匙——数据竞争需要特定交织才显形，普通 fuzzing 的单线程输入覆盖率完全测不到；这正是 TSan/专用并发测试存在的理由。
- **↔ `book/应用密码学（原书第2版）/12-单向哈希函数与MAC.md`**：哈希的「长度扩展攻击」章节演示了一个完整的模式：**编码层缺陷 → 协议层后果 → 编码实践（HMAC）预防**——正是本章「编码实践→代码分析→测试」三层防线的一条完整管线。
- **↔ `book/Rust编程之道.md`**：内存安全语言转向的中文实践材料——所有权与借用检查是「把 5.3 的整套缓冲区规则交给编译器」的方案；与本章 CERT 规则对照读，能看清「哪些规则正在被语言层收编」。
