# 03 · 键值操作与并发控制

> 主题域：一次 `get/set` 到底意味着什么——CAS、expiry、持久化档位、子文档与计数器。
> 章号/章名 ⚠️ 精读重构；✅ 均可点到 docs.couchbase.com；🔧 为本机 SQLite/DuckDB 类比。

## 1. 操作矩阵（键值层）

| 操作 | 语义要点 | 并发/安全凭据 |
|---|---|---|
| `upsert` | 有则覆写，无则创建 | 无（可静默覆盖他人写） |
| `insert` | 已存在即失败 | 键存在性即锁 |
| `replace` | 不存在即失败；可带 CAS | **CAS** |
| `remove` | 可带 CAS | CAS |
| `get` + `touch` | 取值 / 只改过期时间 | — |
| `counter (increment/decrement)` | 服务端原子自增 | 原子性由数据服务保证 |
| append/prepend（⚠️ 2014 基线有，现代 SDK 已不强调） | 字符串拼接 | 非原子，谨慎 |
| 子文档 `lookupIn/mutateIn` | 按 path 读写片段 | path 级存在性谓词 + CAS |

✅ 概念页：[Items, Keys, and Values / Sub-Documents](https://docs.couchbase.com/server/current/learn/data/data.html)、[Extended Attributes](https://docs.couchbase.com/server/current/learn/data/extended-attributes-fundamentals.html)（子文档 API 的扩展，用于「元数据与正文分离」）。

## 2. CAS：单键并发控制的全部

- 每次写产生新的 CAS 令牌；`replace(key, value, cas)` 只在令牌仍匹配时生效，否则返回「已存在/冲突」错误 → 应用必须**重读-重算-重试**。
- 官方把 CAS 明确用于事务的丢失更新防护：「Lost Updates are always prevented by checking against the **CAS value which behaves like an optimistic lock**.」（✅ [learn/data/transactions](https://docs.couchbase.com/server/current/learn/data/transactions.html)）

🔧 **E2 实测（SQLite 模拟读-改-写，非 Couchbase 行为）**：

- 无 CAS：200 次交叉并发（两个客户端先后读同一行、后写者不带条件覆写）→ **200 次静默覆盖**，即丢失更新率 100%。
- 带 CAS（`UPDATE ... WHERE key=? AND cas=?`）：后到写**被拒 200/200**，冲突从「数据错误」变成「可见的异常」——这正是 SDK 里 `KeyExistsError/CasMismatchException` 重试环存在的意义。
- E2b：本机单连接串行，重试环收敛在 0 次；真实集群里重试次数由冲突窗口与退避策略决定（⚠️ 无法本机复现，属转述）。

**工程结论（跨版本通用）**：把 `upsert` 当默认写法 = 放弃并发正确性；**任何「读出来改一点再写回」的路径必须带 CAS**，或者改用原子计数器/子文档。

## 3. 计数器、原子性与热点

- 计数器文档（`{}` 占位 + `incr`）是 2014 年视图时代做「排行/统计」的标准套路（⚠️ 基线口径）。
- 今天依然可用（✅ 各 SDK 的 counter howto），但**同一键的高频自增是天然的单 vBucket 热点**，扩展不出去；现代做法是按分片键拆多个计数器文档再聚合，或直接交给 Analytical/Analytics Service 做扫描（见 [04-视图与二级索引时代.md](04-视图与二级索引时代.md) 与 [10-从2014基线到2026演进手册.md](10-从2014基线到2026演进手册.md)）。
- 🔧 类比：E1b 表明「一个 vBucket = 740 个键」的量级（128 桶配置），同键自增永远落在这一个属主上——热点与映射无关，与**键的粒度**有关。

## 4. expiry、宽限期与物理清理

✅ [Expiration](https://docs.couchbase.com/server/current/learn/data/expiration.html)：文档可设过期；桶/集合可设 **maxTTL**（默认过期 + 显式过期上限）。

🔧 **E2c/E2c2 实测**（30000 键、1/3 设为已过期）：

- 逻辑过期判定（`exp < now`）：**10000 个，0.9ms**。
- 只清理「过期超过 30 秒」的条目 → **实删 0 行**（宽限期内的条目还在）。
- 宽限期结束后真删 → **10000 行，4.5ms**。
- 类比的机制：Couchbase 侧同样把「到期不可见」与「物理 purge」分离（过期分页器周期扫 + 元数据 purge；8.0 起 `expiryPagerSleepTime` 默认 **600**，可在桶 REST API 配置 ✅ [rest-bucket-create](https://docs.couchbase.com/server/current/rest-api/rest-bucket-create.html)）。**推论**：过期时间附近做「删除是否生效」的测试会假阳性——这个坑在本机与真库同构。

## 5. 持久化档位：异步写、副本写、Sync Write

✅ [Durability](https://docs.couchbase.com/server/current/learn/data/durability.html) 关键口径：

- 写可以提出「在集群内存/磁盘上满足几个副本才算成功」的要求；**至多支持 2 个副本的 durability 要求**，3 副本以上不支持。
- 客户端与桶都能设要求，冲突时取更强者；不满足则**通知失败且原数据不变**。
- 8.0 新增集群级选项： Majority 丢失时（故障转移期间）**允许 durable 写降级成功**，官方以 `WARNING: Potential Data Loss` 明确标注风险（✅ [whats-new](https://docs.couchbase.com/server/current/introduction/whats-new.html)）。

🔧 **E3 实测「承诺越硬越慢」的普适曲线**（SQLite WAL，5000 次单行提交，`synchronous` 三档）：

| 档位 | 吞吐 | 平均延迟 |
|---|---|---|
| OFF | 43 180 ops/s | 0.02ms |
| NORMAL | 32 671 ops/s | 0.03ms |
| FULL | **2 143 ops/s** | 0.47ms |

≈20× 的落差是「把 fsync 变成每次请求的承诺」的价格；Couchbase 的 Sync Write 还要叠加跨节点副本往返，因此**真实差距只会更大**（⚠️ 推定，本机不可复现）。读法：延迟敏感的缓存路径用默认异步，账务路径才上 durability。

## 6. 子文档：把「读-改-写」下沉到服务端

- 2014 基线（⚠️）：整文档读-改-写是默认姿势，局部更新靠应用层拼装 + CAS 重试。
- ✅ 现代：`lookupIn/mutateIn` 按 path 定位（`$.address.city`、数组下标），支持 upsert/insert/replace/remove + path 级存在性谓词；「access and mutability at the sub-document level … potentially providing significant improvements in **network performance**」（[learn/data/data](https://docs.couchbase.com/server/current/learn/data/data.html) ✅）。
- 🔧 类比（E5 的另一面，第 6 章给完整数字）：SQLite `json_extract` / `json_patch` 能演示「部分更新 = 服务端读改写」的语义差别——`json_patch('{...}','{...}')` 在本机 3.45.3 可用（✅ 自检跑通），但**没有** Couchbase 的 path 级 CAS 谓词，别把两者混为一谈。
- 反面：子文档不能把 20MB 文档的**索引/查询**问题解决掉，那是第 4 章。

## 7. 跨键原子性：Transactions

✅ [learn/data/transactions](https://docs.couchbase.com/server/current/learn/data/transactions.html)：

- 事务是「一组一起提交或一起撤销」的操作，可跨 **多个 collection / scope / bucket**、跨多节点上的文档；
- 支持 KV 插改删 + 子文档 + 查询；用 CAS 乐观锁防丢失更新；可搭配 durability 保证提交后不丢；
- 它不是 SQL 的 2PC：没有跨语句隔离级别，靠 ATR（async transaction routing）文档做协调（⚠️ 细节转述）。
- 概念对位：[../设计数据密集型应用/07-事务.md](../设计数据密集型应用/07-事务.md)。

## 核心概念速览（中英对照）

- **CAS** — Compare-And-Swap：随每次写变化的 64 位令牌，单键乐观锁的唯一凭据。
- **丢失更新** — Lost Update：两个读-改-写互相覆盖而无人报错，本册 E2 实测发生率 100%（无 CAS 时）。
- **upsert/insert/replace** — 三种写意图：覆写、仅新建、仅替换，选错就等于放弃并发控制。
- **原子计数器** — Counter/Increment：服务端自增，避开读-改-写，但会形成单键热点。
- **过期** — Expiry/TTL：逻辑到期时间；**maxTTL** 是桶/集合级默认与上限。
- **宽限期** — Grace Period：到期后仍可能被救回、且元数据未 purge 的窗口（🔧 E2c 实删 0 行）。
- **持久化要求** — Durability Requirement：写成功前需在多少副本上满足何种驻留等级，最多 2 副本。
- **子文档** — Sub-document：按 path 读写文档片段，省网络也缩小冲突面。
- **路径存在性谓词** — Path Exists/NotExists：把 CAS 思想推广到片段级别的守卫。
- **扩展属性** — XATTR：与正文分离的元数据，子文档 API 的承载位。
- **事务** — Transactions（NoSQL Distributed Transactions）：跨键跨桶的原子单元，靠 CAS + ATR。
- **重试环** — Retry Loop：捕获 CasMismatch 后重读重算的固定写法。
- **异步复制** — Asynchronous Replication：默认写不等副本，性能与安全档位的地基。
- **写意图** — Write Intent：从并发正确性角度选择操作类型的设计动作。
- **热点键** — Hot Key：所有更新集中在一个键/一个属主上的反模式。

## 最新演进与工业实践

1. **API 世代差**：2.x 的「一次配置、长期持有 client」写法早已被统一 SDK 3.x 的 `Cluster.connect()` + 显式重试/退避取代（✅ 迁移文档存在：https://docs.couchbase.com/java-sdk/current/project-docs/migrating-sdk-code-to-3.n.html）；老代码里 `cbstore`/`cas` 手工搬运都属于要重写的部分。
2. **子文档成为默认写法**：文档越大越应该 `mutateIn`，官方 SDK howto 专章（⚠️ 各语言 howto 页名 `subdocument-operations`，data.md 里以 xref 指向 Java SDK 的同名页 ✅ 佐证其存在）。
3. **durability 的可用面**：只支持 ≤2 副本（✅ durability 页），因此「3 副本 + Sync Write」是配置幻觉；8.0 的 failover 期降级开关属于**逃生门不是常态**（✅ whats-new）。
4. **过期与配额联动**：`expiryPagerSleepTime`、`warmupBehavior`、`memoryLowWatermark/HighWatermark` 8.0 起统一进桶 REST API（默认 600 / background / 75 / 85）→ ✅ https://docs.couchbase.com/server/current/rest-api/rest-bucket-create.html
5. **事务的工业位置**：账务、订单状态机这类「多文档一起生效」的场景，今天有官方 Transactions（✅ 上表口径）；2014 只能靠「补偿逻辑 + 幂等键」手搓——这正是本册强调「书要配着 2026 文档读」的典型例子。
6. **可观测性**：写延迟/冲突排查用 `cbstats`（✅ [cbstats-vbucket-details](https://docs.couchbase.com/server/current/cli/cbstats/cbstats-vbucket-details.html)）与 SDK 诊断工具（✅ [sdk-doctor](https://docs.couchbase.com/server/current/sdk/sdk-doctor.html)）；本机不可复现，属 ⚠️ 转述用法。
