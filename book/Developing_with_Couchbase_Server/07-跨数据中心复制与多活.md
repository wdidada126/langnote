# 07 · 跨数据中心复制与多活

> 主题域：官方文案的收尾主线——「从多个客户端跨整个集群访问与更新信息，同时保证数据质量与一致性」。
> 章号/章名 ⚠️ 精读重构；✅ 官方文档；🔧 本机 SQLite 双库类比（非 Couchbase 行为）。

## 1. 两层复制：集群内 vs 集群间

✅ [replication-architecture](https://docs.couchbase.com/server/current/learn/clusters-and-availability/replication-architecture.html)：

- **本地（intra-cluster）**：桶可配最多 3 副本，由 Data Service 负责，写路径同步/异步可选（见 [03-键值操作与并发控制.md](03-键值操作与并发控制.md)）。
- **远端（inter-cluster / XDCR）**：跨集群、可跨数据中心复制，「allows data to be replicated across clusters that are potentially located in different data centers.」（✅ [xdcr-overview](https://docs.couchbase.com/server/current/learn/clusters-and-availability/xdcr-overview.html)）

概念分工（2014 与 2026 一致，✅ 页面仍在）：

| 能力 | 语义 | 现代入口 |
|---|---|---|
| 单向复制 | A→B，B 只读镜像 | ✅ [create-xdcr-reference](https://docs.couchbase.com/server/current/manage/manage-xdcr/create-xdcr-reference.html) |
| 双向/多活 | 每侧既是源又是目标 | ✅ [replication-topologies](https://docs.couchbase.com/server/current/manage/manage-xdcr/replication-topologies.html)（⚠️ 页名以 sitemap 为准） |
| 过滤表达式 | 对**文档键**应用正则，选择性复制 | ✅ xdcr-overview 的 "XDCR Advanced Filtering"（"Each is a regular expression that is applied to the document keys"） |
| 安全检查 | 目的端凭据 SCRAM-SHA 哈希（≥5.5）/ TLS（更早） | ✅ 同页 |
| 冲突处理 | 见第 3 节 | ✅ [xdcr-conflict-resolution](https://docs.couchbase.com/server/current/learn/clusters-and-availability/xdcr-conflict-resolution.html) |

## 2. 键设计与 XDCR 的耦合

第 6 章的键空间纪律在这里有直接回报：

- 过滤表达式只看**键**（✅ 上表原句）⇒ 「哪些数据要跨区域」必须能被键前缀回答；用 collection 做切分后，可按 scope/collection 建立复制关系（✅ [xdcr-with-scopes-and-collections](https://docs.couchbase.com/server/current/learn/clusters-and-availability/xdcr-with-scopes-and-collections.html)、✅ [replicate-using-scopes-and-collections](https://docs.couchbase.com/server/current/manage/manage-xdcr/replicate-using-scopes-and-collections.html)）——这是 2014 之后最重要的能力增量。
- GDPR/数据驻留场景下，「按前缀不复制」比「复制后删除」安全得多（⚠️ 工程判断）。
- 🔧 E7 的隔离直觉（3 个 SQLite 文件 ATTACH 成 3 桶）说明**复制管道天然应按容器划分**，而不是按键正则硬撑。

## 3. 冲突：last-write-wins 的真实代价

Couchbase 的 XDCR 冲突解决是**基于序号的 last-write-wins**（⚠️ 术语转述；✅ 官方冲突解决页在档，并另有 ✅ [xdcr-conflict-logging-feature](https://docs.couchbase.com/server/current/learn/clusters-and-availability/xdcr-conflict-logging-feature.html) 与 ✅ [xdcr-viewing-conflict-logs](https://docs.couchbase.com/server/current/learn/clusters-and-availability/xdcr-viewing-conflict-logs.html) 供事后取证；✅ [xdcr-enable-crossclusterversioning](https://docs.couchbase.com/server/current/learn/clusters-and-availability/xdcr-enable-crossclusterversioning.html) 用 Cross Cluster Versioning 保留版本信息）。

🔧 **E6/E6b/E6c 实测（两个内存 SQLite 库模拟双活，非 Couchbase 行为）**：

1. **E6 单轮**：A、B 各自把 `doc:1` 从 `base` 改成 `A1` / `B1`（同 seq），双向复制后最终值 **`B1`**（同序号时按实现里的裁决键）⇒ **两条并发更新必有一条被静默丢弃**。
2. **E6b 5000 轮**（两侧各自递增 seq）：5000/5000 轮两节点收敛，但「A 的当轮写留在 A」的次数 = **0**，「B 的当轮写留在 B」= **5000** ⇒ LWW 会**系统性偏袒**某一方（本机实现里 B 恒胜）；这不是 bug，而是「用一个可比数字决定胜负」的必然后果——真实集群同理：谁的时间戳/序号大谁赢，业务语义不关心这一点。
3. **E6c 时钟偏斜**：A 侧物理后写的 `'A-late'(seq7)` 被 B 侧更早的 `'B-early'(seq9)` 覆写 ⇒ **因果倒置**，丢的是「后来的那次业务变更」。
4. 结论：**XDCR 多活不适合作为「同一实体的并发写」方案**；它的正确用法是地理读近端化、灾备、按 collection 的数据分发（✅ [GDC 口径](https://docs.couchbase.com/server/current/learn/clusters-and-availability/global-cross-datacenter-replication.html) ⚠️ 页名以 sitemap 为准）。

## 4. 什么时候必须放弃多活写

| 需求 | 结论 |
|---|---|
| 金融账户、库存扣减 | 单写主 + 读写分离；或应用层幂等键 + 冲突表 |
| 用户偏好、资料档案 | 可多活（字段级合并语义，或采用「按用户分片天然单写」） |
| 需要「合并双方改动」 | LWW 做不到 → 在应用层做 CRDT/补丁合并，或退回单写（⚠️ 判断，非官方承诺） |
| 只读副本跨区 | 单向 XDCR，最省心 |

## 6. 一致性词汇对照（防止把话说错）

| 说法 | 在 Couchbase 语境里是否成立 |
|---|---|
| 「XDCR 是最终一致」 | 成立（异步复制） |
| 「多活不会丢写」 | **不成立**，E6b 每轮必丢一条并发更新 |
| 「有事务所以多主安全」 | 不成立：Transactions 解决跨键原子，不解决跨集群冲突（✅ transactions 页无此承诺） |
| 「冲突会被记录下来」 | 只在开启 conflict logging / Cross Cluster Versioning 后 ✅ |
| 「副本数=多活」 | 混淆：集群内副本 ≠ 跨集群复制 |

## 核心概念速览（中英对照）

- **XDCR** — Cross Data Center Replication：集群间、可跨数据中心的异步复制机制。
- **GDC** — Global Cluster Awareness：把多集群当整体管理的视角（⚠️ 名称沿用，细节 ✅ 官方页）。
- **单向/双向复制** — Unidirectional / Bidirectional：镜像 vs 多活。
- **过滤表达式** — Filtering Expression：作用在**文档键**上的正则白/黑名单。
- **检查点** — Checkpoint：已复制位置的持久记录，重启续传依据。
- **seqno** — Sequence Number：vBucket 内写序号，复制进度的通货。
- **last-write-wins** — LWW：以序号/时间戳大小定胜负的冲突解决，**语义上会丢并发写**。
- **冲突日志** — Conflict Logging：把被丢弃的一方留档的功能（✅ 官方页在档）。
- **跨集群版本化** — Cross Cluster Versioning：保留多版本信息的开关。
- **数据驻留** — Data Residency：法规要求数据不出区，靠过滤/collection 复制实现。
- **写主选举** — Single-writer Pattern：多写冲突不可接受时的架构退路。
- **复制延迟** — Replication Lag：跨区 RTT + 队列决定，读写会话要显式承担。
- **优雅切换** — Graceful Failover/Switchover：结合 durable 写开关才安全。
- **拓扑** — Topology（星形/链式/全互连）：XDCR 关系的形状。
- **因果倒置** — Causality Inversion：🔧 E6c 实测——物理后写因序号较小而落败。

## 最新演进与工业实践

1. **collection 级复制是 2024–2026 的主要增量**：桶级整桶复制的老模式被 scope/collection 粒度取代（✅ 第 1 节两个 howto 页），多租户 SaaS 可以「只复制 EU 租户的 collection 到 EU 集群」。
2. **视图时代的过滤技巧退役**：以前靠键前缀绕开不该复制的数据，现在直接按集合建管道 ⇒ 与 [04-视图与二级索引时代.md](04-视图与二级索引时代.md) 一致，键格式债务可以还掉一部分。
3. **移动端一致性**：App Services（托管 Sync Gateway）+ XDCR 双活的组合有官方专页警示（✅ [xdcr-active-active-sgw](https://docs.couchbase.com/server/current/learn/clusters-and-availability/xdcr-active-active-sgw.html)），2014 的「移动 + 多活」章在今天要对位 ✅ [app-services/index.html](https://docs.couchbase.com/app-services/index.html)。
4. **可观测性指标化**：XDCR 指标进入统一 metrics reference（✅ 第 5 节），排障不再靠猜队列。
5. **8.0 的降级开关要进变更评审**：`failover 期允许 durable 写成功` 是逃生门，启用即放弃「写成功=可扛节点故障」承诺（✅ whats-new WARNING）。
6. **托管版差异**：Capella 的集群/网络模型与自建不同（✅ https://docs.couchbase.com/cloud/clouds/private-network.html ），跨区/跨云的复制语义请在产品文档里复核（⚠️ 本册未取到 Capella 侧 XDCR 专页清单，登记为缺口）。
