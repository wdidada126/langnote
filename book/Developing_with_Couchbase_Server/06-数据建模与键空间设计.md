# 06 · 数据建模与键空间设计

> 主题域：官方文案的第二主线——「复杂数据结构（列表与嵌套结构）的构造」；本章把它展开成键空间、内嵌/引用、演化三条纪律。
> 章号/章名 ⚠️ 精读重构；✅ 官方文档；🔧 本机 SQLite/DuckDB 类比（非 Couchbase 行为）。

## 1. 没有 schema ≠ 不用建模

Couchbase 的建模对象不是表，而是三件事：

1. **键空间（key space）**：每个键怎么拼，决定点查效率、可扫描性与迁移时的可读性。
2. **文档边界**：什么内嵌、什么外引（决定一次 IO 能取到多少、以及局部更新的写放大）。
3. **访问路径**：为哪些谓词建索引（GSI/视图/ Search / 向量），以及这些谓词如何被键与文档结构支撑。

✅ 官方教程把这三层直接命名到产品对象上：bucket → scope → collection（https://docs.couchbase.com/server/current/tutorials/buckets-scopes-and-collections.html）。

## 2. 键空间设计：四段式与它的现代替身

2014 年常见写法（⚠️ 基线口径 + ✅ 语义由现代文档支撑）：

```
<type>:<tenant>:<id>            →  "airport:us:22"
<parent>#<child>                →  "user:42#orders:3"
```

理由与代价：

| 设计动作 | 好处 | 代价 |
|---|---|---|
| 类型前缀 | 人类可读、便于视图/索引过滤、便于批量运维脚本 | 键膨胀；**散列会把同前缀键打散到不同 vBucket**，前缀不等于物理邻近 |
| 租户内嵌 | 单键定位多租户 | 跨租户统计必须靠索引；视图时代尤其痛 |
| 用 `META().id` 反查 | 无需二级索引即可点查 | 依赖键格式约定，一旦改键即断链（✅ `META()` 语义见 SQL++ 参考 https://docs.couchbase.com/server/current/n1ql/n1ql-language-reference/index.html ） |
| **把租户放进 collection**（2026 ✅） | 隔离 + 独立 maxTTL + 独立索引 + 独立 XDCR 通道 | 受「每集群 1000 collection」上限约束（✅ https://docs.couchbase.com/server/current/learn/data/scopes-and-collections.html ） |

**本册最重要的口径刷新**：2014 用**键格式**编码的东西（类型、租户、聚合关系），2026 有相当一部分应该改用 **scope/collection** 编码——键格式是字符串约定，collection 是服务器一等对象。

## 3. 内嵌 vs 引用：三种模式的判定

| 模式 | 适用 | 失败模式 |
|---|---|---|
| 全内嵌（聚合根） | 子项与根同生命周期、总是整体读、规模小 | 文档逼近大小上限；任何子项变更都要重写整篇（写放大）；并发冲突面大 |
| 全引用（拆平 + JOIN） | 子项独立增长、需要独立并发更新 | 一次业务读变成 N 次往返；跨键原子性需要 Transactions |
| 混合（ACP：Aggregate/Component/Pointer） | 多数真实场景 | 边界选择是长期债务，需要靠度量迭代 |

🔧 **E5 实测（SQLite，5 万用户 / 100 万订单）**：

| 访问 | 内嵌 JSON | 引用 + JOIN | 解读 |
|---|---|---|---|
| 取单个聚合根（含 20 子项） | **0.13ms** | **0.06ms** | 本机同进程内 JOIN 反而快；内嵌的收益在**跨网络往返**时才显现 |
| 全表按 city 聚合（100 万行） | — | SQLite **433ms** | 行存扫描的代价 |
| 同上，DuckDB 列存 | — | **4.3ms（≈102×）** | 说明「操作型读」与「分析型扫描」该分引擎（→ Analytical Service 的动机） |

结论：**内嵌是为了减少往返，不是为了加速计算**；一旦查询形态变成聚合/扫描，正确的答案不是「把文档拆得更细」，而是把该负载交给索引服务/分析服务（[04-视图与二级索引时代.md](04-视图与二级索引时代.md) 第 7 节、本章第 6 节）。

## 4. 复杂数据结构的构造（列表、嵌套、集合）

官方文案点名的「lists and nested structures」在现代有明确支撑：

- JSON 类型系统与文档结构（✅ [learn/data/data](https://docs.couchbase.com/server/current/learn/data/data.html)：值可为二进制或 JSON，JSON 按 RFC 8259；文档类比行、属性类比列在 ✅ [document-data-model](https://docs.couchbase.com/server/current/learn/data/document-data-model.html)）。
- 数组/对象构造函数与 `FLATTEN`/`OBJECT_PAIRS` 一类表达式在 SQL++ 参考的 functions 分册（✅ 索引入口同上，具体页以 sitemap 检索为准，方法见 [00-总览与阅读地图.md](00-总览与阅读地图.md) 第六节）。
- 子文档路径操作（含数组下标、`arrayp` 谓词）是**局部改结构**的正道（✅ [data.md 的 Sub-Documents 段](https://docs.couchbase.com/server/current/learn/data/data.html)）。
- 元数据与业务字段分离：用 **XATTR**（✅ [extended-attributes-fundamentals](https://docs.couchbase.com/server/current/learn/data/extended-attributes-fundamentals.html)），而不是在文档正文里塞 `_flags`——后者会与视图/索引/迁移互相污染。

🔧 类比：`json_patch` 在本机 SQLite 3.45.3 可用（✅ 自检跑通：`json_patch('{"a":1}','{"b":2}')` → `{"a":1,"b":2}`），可用来体会「文档级覆写」与「片段级合并」在写放大上的本质区别；但**没有** path 级 CAS 谓词，冲突面控制能力不等价。

## 5. 模式演化：无 schema 的债务偿还方式

可操作纪律（⚠️ 工程经验 + ✅ 官方对 flexible schema 的定位）：

1. 文档里保留 `type` 与 `v`（版本号）字段；**不要**把类型只编码在键里。
2. 读写两侧都要向后兼容（新增字段可选、缺字段有默认）；一次性批量改键等于给自己造运维事故。
3. 类型/租户切分优先用 collection（有独立 maxTTL，✅ [expiration](https://docs.couchbase.com/server/current/learn/data/expiration.html)），而不是键前缀。
4. 需要「多文档一起变」时用 Transactions（✅ [learn/data/transactions](https://docs.couchbase.com/server/current/learn/data/transactions.html)：可跨 collection/scope/bucket），别指望多键写原子。
5. 演化到无法静态检查时，把校验放到 Eventing 或写入前的应用层（✅ [eventing-service](https://docs.couchbase.com/server/current/learn/services-and-indexes/services/eventing-service.html)）。

对位原理：[../设计数据密集型应用/04-编码与演化.md](../设计数据密集型应用/04-编码与演化.md)（编码/模式演化的一般框架）。

## 6. 建模决策树（把三章拧成一条）

```
这条数据怎么被读？
├─ 几乎总是按 key 点查            → 只设计键；文档按需内嵌；无二级索引
├─ 按若干属性谓词点查/排序          → 内嵌必要字段 + GSI（含复合/覆盖/偏索引）
├─ 需要文本/地理/向量相似度          → Search Service（可选 Search Vector）/ GSI 向量索引
├─ 跨行聚合、报表、扫描             → Analytical/Analytics Service 或导出（勿用视图硬扛）
├─ 多文档原子改                    → Transactions + durability
└─ 生命周期短（会话/缓存）           → Ephemeral 或 maxTTL；no eviction 需谨慎
```

## 核心概念速览（中英对照）

- **键空间设计** — Key Space Design：用键编码类型/租户/关系的前缀约定艺术，2026 部分让位于 collection。
- **聚合根** — Aggregate：一致演化、整体读写的文档边界（ACP 的 A）。
- **组件/指针** — Component / Pointer：内嵌小子结构 / 用键引用大子结构。
- **写放大** — Write Amplification：为改一个字段重写整篇文档的成本。
- **文档大小上限** — Document Size Limit：内嵌策略的硬天花板（具体值 ⚠️ 以版本文档为准）。
- **collection 隔离** — Collection Isolation：以服务器一等对象承载租户/类型，含独立 maxTTL 与索引。
- **META().id** — 文档元数据函数：SQL++ 中取键/扩展属性的入口。
- **XATTR** — 扩展属性：元数据与正文分离的官方位置。
- **模式演化** — Schema Evolution：无 DDL 前提下的字段兼容纪律（版本字段 + 可选读）。
- **点查** — Point Read：按 key 取文档，KV 模型的主路径。
- **偏索引** — Partial Index：只对满足条件的文档建索引，缩小维护成本。
- **覆盖索引** — Covering Index：查询字段全在索引内，免回表。
- **热点聚合** — Hot Aggregation：把统计写进单键计数器造成的扩展瓶颈。
- **操作型 vs 分析型** — OLTP vs OLAP：🔧 实测 102× 差，决定该用哪个服务。

## 最新演进与工业实践

1. **建模单元换代**：桶内三层（bucket/scope/collection）是当下官方教程主线（✅ tutorials 页 + ✅ [manage-scopes-and-collections](https://docs.couchbase.com/server/current/manage/manage-scopes-and-collections/manage-scopes-and-collections.html)）；「一个应用一个桶」的老规矩被明确替换，同时带来 **1000 collection/集群** 的新上限（✅）。
2. **键不再是租户隔离首选**：collection 支持按集合配 maxTTL、建索引与 XDCR 复制（✅ [xdcr-with-scopes-and-collections](https://docs.couchbase.com/server/current/learn/clusters-and-availability/xdcr-with-scopes-and-collections.html)），比键前缀方案可控得多。
3. **向量落位是建模问题不是索引问题**：embedding 放哪、维度多少、用什么度量（官方支持四种，✅ vectors-and-indexes-overview 见 04 章）必须在文档设计阶段决定；Composite Vector index 甚至要求**同一文档里同时有向量列与标量过滤列**（✅ [composite-vector-index](https://docs.couchbase.com/server/current/vector-index/composite-vector-index.html)）。
4. **RAG 语境下的建模口径**：把 chunk 文本、metadata、embedding 放同一文档，检索时一次取回（✅ 产品叙事见 https://www.couchbase.com/products/ai-services/ ）；盘上同类讨论 [../Vector_Databases/07-应用-语义搜索RAG与混合检索.md](../Vector_Databases/07-应用-语义搜索RAG与混合检索.md)。
5. **计量与成本**：Capella 按配置计费，键/文档设计（大小、collection 数、索引种类）会直接映射到账单（⚠️ 转述；✅ 计费页存在 https://docs.couchbase.com/cloud/billing/billing.html ）。
