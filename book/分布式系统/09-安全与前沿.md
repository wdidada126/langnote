# 第 9 章 Security（安全）+ 全书收尾（2017→2026 演进）

> **本章地图**：安全是分布式系统的「最后一章问题」——开放性与连接性放大的攻击面
> → **安全基础**：CIA 三性（机密性/完整性/可用性）、策略 vs 机制、信任与威胁模型、密码学原语的位置
> → **安全通道（secure channels）**：会话密钥、**相互认证协议**（挑战-响应、Nonce 防重放）、机密性与完整性保护
> → **访问控制**：ACL vs 能力表（capabilities）、信任链与委派
> → **收尾**：3rd 版到 2026 的演进（零信任、mTLS、服务网格）。

## 核心精讲

### 9.1 安全基础

- **CIA**：
  - **机密性（Confidentiality）**：内容不被偷看；
  - **完整性（Integrity）**：内容与来源不被篡改；
  - **可用性（Availability）**：服务不被打瘫；
    - DoS 直接打这一性，且最难用密码学解。
- **策略 vs 机制**：
  - 策略说「谁可以对什么做什么」；
  - 机制是执行手段；
  - 分布式的难点在于**信任跨越组织边界**（没有超级 root）。
- **威胁模型**：书提醒先问三件事——
  1. 谁可能攻击（内部/外部/中间人）；
  2. 能拦截什么（被动窃听 vs 主动注入）；
  3. 系统与用户谁更怕出事。
- **密码学原语的分工**：
  - **对称加密**（AES 系）：快，用于数据面；
  - **公钥加密**（RSA/EC）：慢，用于握手与密钥分发；
  - **哈希 + MAC**（HMAC）：完整性；
  - **数字签名**：来源认证 + 不可否认；
  - 🔧 原语皆不解决「这把公钥真是对方的吗」——那是下一节 PKI/认证的事。

### 9.2 安全通道（secure channels）

- 目标：给一条 Ch4 的普通通道加三件套——**相互认证、机密性、完整性**；
  - TLS 是其工业化身。
- **挑战-响应认证**（用 Nonce 防重放）：

```text
# 教学示意：基于共享密钥 K_AB 的相互认证（Needham-Schroeder 思想的简化版）
A → B : A, rA                      # rA = 一次性随机数（挑战）
B → A : {rA, B, rB}K_AB            # B 用 K_AB 解开挑战并附上自己的挑战
A → B : {rB}K_AB                   # A 回应 B 的挑战
# 协议失败史（书以此讲设计难度）：早期版本被中间人重放攻击——
# 缺 B 的身份绑定/会话密钥新鲜性，修复靠 Nonce + 身份明文混入密文
```

- **会话密钥**：
  - 用公钥（或 KDC 密钥分发中心，Kerberos 模式）协商出一次性对称密钥；
  - 「公钥做握手，对称做数据」的分工从书里讲到现在没变。
- 🔧 书明确指出认证协议的设计反直觉：
  - Needham-Schroeder 1978 提出后仍被发现漏洞；
  - **协议证明（BAN 逻辑、Tamarin/ProVerif 形式化验证）成为必修**。

### 9.3 访问控制（access control）

- **访问控制矩阵**的两种实现方向：
  - **ACL（按行存）**：
    - 每个对象挂一张「谁能干什么」的表；
    - 面向**对象管理者**，好审计、难传递。
  - **能力表（capabilities，按列存）**：
    - 用户手里握着不可伪造的「门票」；
    - 面向**主体**，好委派（把票转手）、难回收（撤票是老大难）。
- 工程混合体：
  - JWT/OAuth token = 数字签名的能力表；
  - 云 IAM = 策略引擎 + ACL 方向。
- **信任链与委派**：
  - 证书链（根 CA → 中级 → 叶子）；
  - 代理权限（delegation）；
  - 跨组织的信任传递是分布式安全区别于单机的核心难题。
- 🔧 可用性（DoS）在访问控制之外：
  - 认证与授权挡不住「打不让你服务」；
  - 需要容量工程与速率限制——CIA 里最「非密码学」的一环。

## 近年研究与工业界开源实践（2015–2026）

- 🔧 **零信任（Zero Trust）成为默认架构**：
  - 「网络边界内即可信」作废——每次访问都要认证+授权（NIST SP 800-207）；
  - Google BeyondCorp（2014 起系列论文）是工业蓝本；
  - 对本书的冲击：**威胁模型从「周界」改为「处处敌意」**，Ch4 的任意两节点通道默认不可信。
- 🔧 **mTLS 普及**：
  - 双向证书认证从银行专线走进微服务标配；
  - Istio/Linkerd 的 sidecar 自动签发轮换短命证书（SPIFFE/SPIRE 的 SVID 身份）；
  - 「相互认证协议」（9.2）从理论课变成每个 Pod 的日常。
- 🔧 **服务网格的安全职责下沉**：
  - 认证、授权、加密、审计从应用代码下沉到基础设施层（mesh/网关）；
  - 对应趋势：应用「无安全代码化」+ 平台「安全即配置」；
  - 代价是信任根集中在控制面——新的单点（呼应全书对中心化与去中心化的拉锯）。
- **实战样本（star 数 2026-09 实测）**：
  - `etcd-io/etcd`（≈52.3k★）的 TLS peer/client 证书 + RBAC；
  - `apache/kafka`（≈33.8k★）的 SASL/mTLS；
  - `hashicorp/consul`（≈30.1k★）Consul Connect 的内置 mTLS；
  - 把 9.2/9.3 直接做成配置项。
- **后量子迁移（2026 进行时）**：
  - NIST PQC 标准（ML-KEM/Kyber、ML-DSA/Dilithium，2024 定稿）；
  - TLS 混合密钥交换开始部署；
  - 「RSA 用到 2050」的书中隐含假设需要更新。
- **机密计算**：
  - TEE（Intel SGX/TDX、AMD SEV）把「内存里的数据也加密」；
  - CIA 加第四维「使用中的机密性」，超出本书威胁模型。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「用了 TLS 就安全了」 | TLS 只覆盖**通道**：密钥管理、证书校验、端点授权、DoS、应用层注入都不在它管辖 |
| 2 | 「认证 = 授权」 | 9.2 的相互认证只回答「你是你」；能干什么由 9.3 访问控制决定——混用导致「认证过的服务拿全量权限」 |
| 3 | 「内网不用加密」 | 零信任视角下内网即敌区；横向移动（lateral movement）是 2020s 攻击标配叙事 |
| 4 | 「能力表天生比 ACL 好」 | 能力的撤销难题至今无完美解；短命 token（过期时间）是用「重新获取的麻烦」换「可撤销性」 |
| 5 | 🔧 本书需 2026 补丁 | 书写于零信任与 mesh 普及前：安全边界概念需整体替换（周界 → 身份）；mTLS/短命证书/策略即代码未覆盖 |
| 6 | 🔧 本书需 2026 补丁 | 密码学时代背景过期：SHA-1/3DES 类旧算法在书例中出现属教学；实际部署按 2026 NIST 推荐（PQC 迁移已开始） |

## 读完本章应能回答的问题

- 为什么「密码学原语 ≠ 安全」？
  - 原语只保证数学性质；密钥怎么生成、分发、轮换、撤销才是实战难点；
  - 书用 NS 协议被攻破的历史讲透这一点。
- Nonce 为什么要用「一次性随机数」而不是时间戳？
  - 时间戳依赖时钟同步（Ch6 的难题被引入安全）；
  - 随机数只要本地生成 + 唯一即可，假设更弱。
- ACL 与能力表在「撤销」上的表现？
  - ACL：改对象的表即生效，撤销快（但列表管理重）；
  - 能力表：票已发出无法收回——只能等过期或换锁（轮换密钥）。
- 零信任改变了本章哪个前提？
  - 「通道两端在同一个信任域内」不再成立；
  - 所以相互认证（9.2）从可选优化变成每次连接的必选项——mTLS 就是这么普及的。
- 为什么 Ch9 的官方 PPT 不存在？
  - 作者在教学上把安全作为可独立裁剪的模块；
  - 本目录建议反向处理：安全不裁剪，近年段（零信任/mTLS）必读。
