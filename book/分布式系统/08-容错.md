# 第 8 章 Fault tolerance（容错）

> **本章地图**：为什么「部分失效 + 不确定性」使容错成为分布式第一公民
> → **故障模型**：故障/错误/失效链条，崩溃、遗漏、时序、拜占庭分级
> → **冗余屏蔽**：信息冗余（纠删码思想）、时间冗余（重试）、物理冗余（副本）
> → **可靠组播**：原子性（全收或全不收）与排序，虚拟同步
> → **分布式提交**：2PC 及其协调者崩溃下的阻塞问题，3PC 与 FLP 的关系
> → **恢复**：前向/后向恢复、检查点（独立 vs 协同）、消息日志（悲观/乐观）、稳定存储。

## 核心精讲

（以下伪代码均为**教学示意，不参与构建**。）

### 8.1 故障模型（failure models）

- 链条：**fault（错误源）→ error（系统内错误状态）→ failure（对外可观察失效）**；
  - 容错 = 阻止 fault 变 failure。
- 严重度递增的模型谱系：
  1. **崩溃故障（crash）**：
     - 安静地停；
     - fail-stop：停了还保证不再发任何消息——最好处理的失效。
  2. **遗漏故障（omission）**：收/发消息偶发丢失。
  3. **时序故障（timing）**：同步系统里的响应迟到（现实网络常态）。
  4. **拜占庭故障（Byzantine）**：
     - 任意行为甚至说谎（信号干扰、被入侵）；
     - 容它需要 3f+1 副本。
- 🔧 工程默认假设：**crash + omission（异步网络）**；
  - 拜占庭只在联盟链/航天/多方互不信任场景必须。

### 8.2 用冗余屏蔽故障

- **信息冗余**：
  - 纠删码（erasure coding）把 k 块编成 n 块、任意 k 块可恢复；
  - 存储副本的省钱替代（RS 码在 HDFS/云存储标配）。
- **时间冗余**：重试（要幂等！接 Ch4 的 at-least-once）。
- **物理冗余**：多副本，两种组织方式（Ch7 已见）：
  - **主备（passive replication）**：
    - 主执行、备热等；故障时接管（failover）；
    - 状态 = 服务的状态迁移。
  - **状态机复制（active replication）**：
    - 所有副本执行**同样的确定性操作序**；
    - 前提：操作序一致（全序广播）+ 执行确定。
- 🔧 状态机复制的两个隐藏条件：
  - 确定性代码（去掉本地随机/本地时钟读数）；
  - **原子多播**保证序——所以下一节的可靠组播是它的地基。

### 8.3 可靠组播（reliable multicast）

- **原子性要求**：
  - 要么所有（存活）目标收到，要么都不收到；
  - 不允许「一部分副本收到了写请求、另一部分没收到」（否则状态分叉）。
- 实现骨架：
  - 发送方到**协调者树/环**；
  - 接收方对丢失发 **NAK**（否定确认）；
  - NAK 抑制（同丢失只发一次 + 定时器）控制反馈风暴；
  - SRM 等系统是原型。
- **虚拟同步（virtually synchronous，Birman）**：
  - 组视图（成员表）变化与消息传递严格排序；
  - 「先看到新视图的消息不会早于旧视图的消息到达」；
  - 把组播做成状态机复制底座的关键抽象。
- 排序升级链：FIFO 组播 → 因果组播 → **全序（atomic）组播**；
  - 全序组播本质上就需要共识（接 8.4）。

### 8.4 分布式提交（distributed commit）与共识

- **两阶段提交（2PC）**：
  - 阶段一：协调者发 PREPARE，参与者锁定资源并回 YES/NO；
  - 阶段二：全票 YES 才 COMMIT。
- **2PC 的死穴（书的重点分析）**：
  - 参与者投 YES 后被「钉死（blocked）」；
  - 协调者在发出 global-commit 前崩溃：参与者既不能提交也不能中止，只能等；
  - **原子性在协调者单点上不成立**。
- **3PC（三段提交）**：
  - 插入 PRE-COMMIT 让双方「隔一步」；
  - 配合超时**猜**结果——消除阻塞；
  - 但引入网络分区下的一致性风险（两个协调者各猜各的）。
- 🔧 **理论边界（FLP, JACM 1985）**：
  - 纯异步系统里哪怕只有一个进程崩溃，也不存在保证终止的确定性共识协议；
  - **3PC 用超时换活性、分区下牺牲一致性，正是绕不过 FLP 的体现**；
  - 工程答案：部分同步 + 领导选举/任期号的共识协议（Paxos/Raft/ZAB）把协调者做成高可用；
  - 「2PC + Raft 的协调者」是数据库分布式事务的当代标准解（Percolator、TiDB）。
- **两将军问题（two generals）**：
  - 不可靠信道上无一次消息交换能达成可靠协定；
  - 「重试 + 确认无穷递归」——FLP 的最简版直觉。

### 8.5 恢复（recovery）

- **前向恢复**：出错后直接修正到新正确状态（如重放未完成操作）；
- **后向恢复**：回滚到检查点重来——工程主流（简单、通用）。
- **检查点（checkpointing）**：
  - 独立检查点：各进程随时存——可能产生**不一致割点**（有的进程已收到某消息有的没存）；
  - **协同检查点**：按协议同步存（Chandy-Lamport 快照是教科书答案）。
- **消息日志（message logging）**：
  - 存检查点 + 记录收到的消息，恢复时重放；
  - **悲观日志**：每条消息落盘再处理（慢但安全）；
  - **乐观日志**：攒批再落（快但崩溃可能丢尾）。
- **稳定存储（stable storage）**：
  - 日志先写 WAL 再改状态；
  - 单机数据库（InnoDB redo log）与分布式（Raft log）共用同一哲学：
    **「日志是真相，状态是日志的缓存」**。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「2PC 提交了就安全」 | 2PC 解决原子性**不解决容错**：协调者单点崩溃可让参与者永久阻塞；生产 2PC 必须叠共识协调者 |
| 2 | 「3PC 比 2PC 好」 | 3PC 消除阻塞但分区下可双提交（不一致）；理论根源 FLP——没有免费午餐，只有取舍 |
| 3 | 「fail-stop 崩溃的进程不会乱说」 | fail-stop 是**理想模型**；真实崩溃可能重复发消息（网络重传）——at-least-once + 幂等逃不掉 |
| 4 | 「检查点越多恢复越快越好」 | 检查点本身是开销与停顿；协同检查点的协议复杂度（与全局快照）常被低估 |
| 5 | 🔧 本书需 2026 补丁 | **书未收录 Raft/ZAB 实现细节**：共识、日志、快照的一体化设计是当代容错的骨架，务必外挂 Raft 论文 + etcd 源码学习 |
| 6 | 🔧 本书需 2026 补丁 | 书的拜占庭内容止于理论推导；HotStuff/门限签名与「诚实多数 + 签名」的实践差异未覆盖 |
