> **本章地图**：进程作为「分布式系统的虚拟处理器」

## 本章地图

- Ch3 把「进程」当作分布式系统的基本执行单元，四步递进：
  - 线程（进程内并发）；
  - 虚拟化（机器级进程）；
  - 客户/服务器（进程的两种角色）；
  - 代码迁移（进程换个地方继续跑）。
- 本书的独特视角：
  - 分布式系统的性能与容错方案，几乎都要求「一个物理节点并发扮演多个逻辑角色」；
  - 所以线程和虚拟化是分布式的前置技术，不只是 OS 话题。
- 3rd ed 用 Python 示例演示多线程服务器；方框小节讨论虚拟化的更多实现细节。

### 3.1 线程与分布式系统

- **为什么需要线程**：
  - RPC/消息处理天然是「等待-处理」循环；
  - 单线程会因一次网络等待卡死整个服务；
  - 线程把「等待」重叠起来。
- 书中经典结构——多线程服务器用「分派器 + 工作线程」：

```python
# 教学示意：多线程服务器骨架（书中示例的简化版）
import threading
def worker(sock_queue):
    while True:
        conn = sock_queue.get()
        handle(conn)          # 阻塞式处理也无妨：别的线程在干活
q = Queue()
for _ in range(8):
    threading.Thread(target=worker, args=(q,)).start()
```

- 三个要点：
  1. **并发隐藏延迟**：
     - 线程数 ≈ 同时在途的慢操作数；
     - 是 Ch1「隐藏通信延迟」扩展技术的执行层实现。
  2. **共享内存换通信**：
     - 同进程线程共享数据，比 RPC 便宜几个数量级；
     - 但引入并发控制——与 `book/多处理器编程的艺术2/18-栅栏.md` 的内存序问题同源。
  3. 线程是软件概念，不需要多核也能用（本书成书时单核多线程仍是常态）。

### 3.2 虚拟化（virtualization）

- **定义（书）**：在宿主与用户之间提供接口的软件层；按接口层级分：
  - **进程虚拟机**：高级语言 VM（JVM、CPython）；
  - **虚拟机监控器 VMM（hypervisor）**：仿真 ISA 层；
    - Type 1（裸金属：Xen/ESXi）vs Type 2（宿主上：VirtualBox）；
  - **容器**：共享内核、按进程组隔离；
    - 书的年代以 OpenVZ/Solaris Zones 讲，今天对应 Docker/K8s。
- **为什么分布式系统要虚拟化**：
  1. **迁移与弹性**：VM 镜像可整体搬家（live migration），支撑云的负载迁移；
  2. **隔离**：多租户共享物理机仍互不干扰；
  3. **环境复制**：把「整个系统状态」变成可复制的制品——Ch7 复制、Ch8 恢复的物理基础。
- 🔧 书中把「虚拟化 = 接口仿真」讲得很清楚：
  - hypervisor 级（指令集）、库级（系统调用）、应用级（语言运行时）各是一种权衡。

### 3.3 客户与服务器

- **客户侧**：
  - 网络用户工作站（NWS）与瘦客户端（X 终端思路）；
  - 今天对应浏览器/云桌面——书预言的「计算回归中心」在 Web 时代成真。
- **服务器侧**三件套：
  1. **联系点（contact point）**：
     - 知名端口 + 目录服务（端口映射器）定位服务。
  2. **超级服务器（superserver）**：
     - inetd/xinetd 模式——平时不跑业务进程，请求来了才 fork；
     - 省内存但冷启动慢；
     - systemd socket activation 是它的当代版。
  3. **有状态 vs 无状态**：
     - **无状态服务器**：请求自包含，崩溃恢复容易、可任意水平扩展（HTTP 的无状态设计）；
     - **有状态服务器**：保存会话，性能好但故障恢复要迁移/重建状态。
- 🔧 工程主流是「无状态计算 + 有状态存储分离」：
  - 这正是「存算分离」架构（见 [../分布式数据库入门进阶与实战/08-分布式数据库架构与软硬结合.md](../分布式数据库入门进阶与实战/08-分布式数据库架构与软硬结合.md)）的原理层解释。

### 3.4 代码迁移（code migration）

- 迁移什么：代码 + 执行状态 + 资源绑定，三者可独立迁移。
- **弱迁移（weak mobility）**：
  - 只搬代码 + 初始数据，程序从头跑；
  - 今天几乎所有方案都是它：容器镜像、serverless 部署、小程序包。
- **强迁移（strong mobility）**：
  - 连执行状态（栈、PC）一起搬，跑到一半换机器继续；
  - 书里用「迁移代理（mobile agent）」讲；
  - 工程上基本死掉了——序列化执行栈跨异构环境太难。
- 迁移模型：
  - 发送者发起（push）；
  - 接收者拉取（pull，如 Java Applet/现代 CDN 脚本）；
  - 异构性问题（指令集、运行时版本）是强迁移衰落的根因。

## 近年研究与工业界开源实践（2015–2026）

- **容器一统天下**：
  - `moby/moby`（star 未核验）、容器运行时 `containerd/containerd`（star 未核验）与 runc；
  - 书中「OS 级虚拟化」的标准化胜利；书成书时 Docker 仅 4 岁。
- **线程模型回摆**：
  - 事件驱动（Node.js、nginx）与协程（Go goroutine、Java 虚拟线程、Rust async）重新定义「多线程服务器」；
  - 「分派器 + 工作线程」被 runtime 内化；
  - 但「用并发隐藏网络延迟」的原理句一字未变。
- **弱迁移的极致：serverless 与快照恢复**：
  - Firecracker microVM（`firecracker-microvm/firecracker`，star 未核验）支撑 AWS Lambda；
  - VM 快照 + COW 恢复技术把「代码迁移」变成「状态迁移 + 就地重启」。
- **实测 star（2026-09，`gh api`）**：
  - `redis/redis` ≈76.5k★：
    - 单线程事件循环 + IO 多线程——本章线程议题的活样本；
    - Redis 证明「无状态式请求处理 + 单线程执行」在特定负载下反而更快，
      是对「多线程一定更好」的天然反例。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「分布式系统课为什么要讲线程」 | 分布式性能设计第一招（隐藏延迟）由线程/协程执行；不懂线程读不懂任何服务器代码 |
| 2 | 「有状态服务器过时了」 | 只是**状态被赶到存储层**；会话黏性、连接状态（QUIC 0-RTT）仍是服务器状态，只是被显式管理 |
| 3 | 「强迁移（mobile agent）是未来」 | 3rd ed 已把它压成历史注脚；跨异构环境序列化执行栈的代价从未被工程接受，弱迁移全面胜利 |
| 4 | 「容器 = 轻量虚拟机」 | 容器共享内核、隔离弱于 VM（安全边界不同）；书中「接口层级」框架提醒两者处于不同抽象层 |
| 5 | 🔧 本书需 2026 补丁 | 书未覆盖 eBPF（内核级可编程拦截层）与 io_uring（异步 I/O 重定义线程阻塞模型）；线程/事件模型的假设需按此更新 |
| 6 | 🔧 本书需 2026 补丁 | 书的虚拟化章不涉及 GPU 虚拟化与 AI 集群调度（vGPU、MIG）；2026 的「资源虚拟化」重点已转向加速器 |

## 读完本章应能回答的问题

- 多线程服务器里线程数怎么定？
  - 下限：能同时遮住「最慢的外部操作」数量；
  - 上限：上下文切换与内存开销；
  - 事件驱动/协程时代由 runtime 自动调度，但「在途慢操作数」仍是容量规划单位。
- 虚拟化的三种接口层级各对应什么产品？
  - 指令集级 → VM（Xen/KVM/ESXi）；
  - 系统调用级 → 容器（Docker/K8s）；
  - 语言运行时级 → JVM/WASM——隔离越强越重，迁移成本越高。
- 无状态服务器真的不存任何状态吗？
  - 存；只是状态要么在请求里（cookie/token），要么被外移到存储层；
  - 「无状态」是对**故障恢复与扩容**的设计承诺，不是字面陈述。
- 超级服务器（inetd）思想今天还活着吗？
  - 活着：systemd socket activation、FaaS 冷启动按需拉起、K8s 的按需 sidecar；
  - 共同点：为低频服务省常驻资源，代价是首请求延迟。
- 强迁移为什么死了？
  - 执行栈/PC 与具体运行时绑定，跨异构环境几乎不可序列化；
  - 替代方案（checkpoint-restore、WASM 暂停恢复）都是弱迁移 + 受限运行时。
