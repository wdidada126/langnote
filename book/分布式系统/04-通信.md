## 本章地图

- Ch4 从「裸网络」走到「让程序员舒服的抽象」：
  - RPC 把远程调用伪装成本地函数；
  - 消息队列把同步调用解耦成异步投递；
  - 组通信把一对一扩展成一对多。
- 全章暗线是**透明性的代价**：
  - 调用越像本地的，失败语义越容易被误解；
  - 这个张力贯穿 RPC 与异步 RPC 的设计。
- 3rd ed 方框小节讲流式通信（多媒体）；正文主战场是 RPC 与 MOM。

## 核心精讲

（以下代码均为**教学示意，不参与构建**。）

### 4.1 分层协议（快速复习）

- OSI 七层 vs TCP/IP 五层的对照；本书只强调三个事实：
  1. **中间件活在第 4~7 层之间**——它不替代 TCP 而是复用；
  2. **TCP 保证的字节流顺序/可靠 ≠ 应用级请求的有序/可靠**：
     - 粘包、重连丢请求都要中间件自己补语义；
  3. UDP 在多播与实时场景不可替代（组通信的地基）。

### 4.2 远程过程调用（RPC）

- 目标：**调用远程过程与调用本地过程语法一致**（Birrell & Nelson 1984 的原始理想）。
- 机制四件套：
  1. **client stub**：打包参数（marshalling）；
  2. 网络传输；
  3. **server stub**：解包、调用真过程；
  4. 结果回传。
- 参数传递的坑：
  - 值传递简单；
  - **引用/指针参数必须复制**（call-by-copy/restore）；
  - 「传指针让服务端改本地内存」在 RPC 下不存在；
  - 复杂数据结构需 IDL + 序列化（书中用 DCE/通用 marshalling 规则讲，当代对应 Protobuf）。
- **失败语义**：
  - 本地调用「没返回 = 没执行」；
  - RPC 却可能「执行了但响应丢了」；
  - at-least-once / at-most-once 语义之争；
  - 根源是**无法区分慢与死**（接 Ch8 故障模型）。
- **异步 RPC**：
  - deferred synchronous：立即返回 handle，稍后取结果；
  - one-way：连 handle 都不要；
  - 书强调：「异步化是承认网络延迟不可隐藏的第一步」。

```python
# 教学示意：RPC 的失败语义
def transfer(acc, amount):   # stub 调用后超时了——
    ...                      # 钱到底扣了没有？重试会不会扣两次？
# at-most-once：不重试，宁可失败
# at-least-once：重试，要求操作幂等
# 书的结论：透明性止步于此，程序员必须知道自己在调远程
```

### 4.3 面向消息的通信（message-oriented communication）

- 书的 2×2 矩阵：
  - **持久（persistent）**：消息存到送达为止；**暂态（transient）**：收方不在线即丢；
  - **同步**：发送方阻塞；**异步**：即发即忘。
- 消息队列系统（MOM）= 持久 + 异步：
  - 天然支持**时间解耦**（收发双方不必同时在线）。
- **消息代理（message broker）**：
  - 在队列之上做协议转换、格式转换、路由；
  - EAI（企业应用集成）的核心组件；
  - 书的例子是 IBM MQ 与 CORBA 通知服务；
  - 当代对应 Kafka/RabbitMQ/NATS（见近年段）。
- 🔧 MOM 与 RPC 的哲学差异：
  - RPC 问「帮我执行」；
  - MOM 说「这里有个事实」；
  - 事实广播天然适合事件驱动架构（Ch2 风格的通信落地）。

### 4.4 组通信与发布-订阅

- **多播（multicast）**：一对多。
  - IP 多播（网络层）：受限于路由器支持；
  - **应用层多播**：端系统自组织树——P2P 思想回声。
- **可靠组播（reliable multicast）**：
  - 保证所有（存活）成员都收到，或都收不到；
  - 用 NAK/反馈抑制/FEC 控制反馈风暴；
  - 完整容错算法在 Ch8 重讲。
- **发布-订阅（pub/sub）**：
  - 按**主题（topic）**或**内容（content-based）**路由；
  - 订阅表即「松耦合的调用图」；
  - 书指出内容路由的扩展性难题（每台 broker 都要匹配所有消息）。

### 4.5 流式通信（方框）

- 连续媒体（音视频）关注**时延抖动与传输率**而非丢包率；
- QoS 参数（带宽/时延/抖动）与资源预留 RSVP 的历史；
- 2026 回看：QUIC/WebRTC 时代 RSVP 已死，但「流 ≠ 文件」的分析框架仍成立。

## 近年研究与工业界开源实践（2015–2026）

- 🔧 **2026 视角：gRPC/HTTP2 对 RPC 假设的冲击**：
  - `grpc/grpc`（≈45.3k★，2026-09 `gh api` 实测）；
  - HTTP/2 多路复用一个连接跑上千并发流，「每请求一线程/一连接」的书本假设失效；
  - 流式 RPC（client/server/bidi streaming）让 RPC 长得越来越像 MOM——
    RPC 与消息的边界在协议层消失了。
- 🔧 **QUIC 重写传输假设**：
  - 用户态实现可靠流 + 每流独立丢包恢复（无队头阻塞）+ 0-RTT 重连；
  - 「TCP 之上的中间件自己补语义」的教科书分工被压缩；
  - 本书成书于 QUIC 定稿前后，未覆盖。
- **io_uring 的冲击**（🔧 2026 视角续）：
  - Linux io_uring 把系统调用从「阻塞-唤醒」改为提交/完成队列；
  - 事件驱动不再需要线程池伪装；
  - Ch3 的「分派器 + 工作线程」模型在存储/网络路径上正被 async runtime 替代。
- **MOM 的两极分化（star 数 2026-09 实测）**：
  - 日志型 `apache/kafka`（≈33.8k★）：持久日志 + 消费者拉取，顺序吞吐优先于低时延；
  - 低时延型 `nats-io/nats-server`（≈20.8k★）与 `rabbitmq/rabbitmq-server`（≈13.9k★）守住传统 broker 场景；
  - 书的「持久/暂态 × 同步/异步」矩阵仍是分类它们的最好语言。
- **云厂商托管化**：
  - Pub/Sub 类产品（Google Pub/Sub、AWS SNS/SQS）把「broker 集群运维」整体消失；
  - 呼应 Ch1 的管理可扩展性。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「TCP 可靠 = 应用消息可靠」 | TCP 保证字节流，不保证连接不断、不保证已读已处理；应用级 ACK 与幂等仍是必须 |
| 2 | 「RPC 要做到完全透明」 | 失败语义（timeout 后执行与否未知）使完全透明不可能；「尽量透明、失败显式」才是工程答案 |
| 3 | 「at-least-once 比 at-most-once 好」 | 取决于幂等性：非幂等操作 + at-least-once = 重复扣款；有幂等键时 at-least-once 才占优 |
| 4 | 「消息队列只是异步 RPC 的替代」 | MOM 的时间解耦与事实广播语义适合事件驱动架构；两者是互补抽象 |
| 5 | 🔧 本书需 2026 补丁 | QUIC 定稿前成书：传输层假设（TCP 队头阻塞、TLS 单独一层）需按 HTTP/3 时代重估；「应用层多播」在直播场景被 WebRTC/SRT 类方案收编 |
| 6 | 🔧 本书需 2026 补丁 | REST 与 gRPC 的取舍、Protobuf vs JSON、Schema Registry（Kafka 生态）等序列化治理话题书均未涉及 |

## 读完本章应能回答的问题

- RPC 的「透明」与「显式失败」如何共存？
  - 语法透明（调用方式一致）+ 语义显式（异常类型区分超时/失败/成功）；
  - 现代框架（gRPC 状态码）正是这个组合。
- 持久消息 vs 暂态消息各配什么场景？
  - 持久：订单、审计、跨服务事件——丢不得；
  - 暂态：行情推送、在线状态、心跳——丢得起、要低延迟。
- 为什么「同步 RPC」也可以建立在异步传输上？
  - 同步/异步是**发送方语义**，持久/暂态是**消息生存期**；
  - 四个维度独立组合，书里矩阵的意义正在于此。
- 内容路由（content-based）为什么难以扩展？
  - 每条消息要在每个 broker 上做全谓词匹配；
  - 主题路由（topic-based）把匹配降为查表，是工程上的妥协。
- 可靠组播与普通重传有什么区别？
  - 前者要求**组视角的原子性**（全收或全不收）；
  - 后者只保证点对点送达——组的原子性需要协调（Ch8）。
