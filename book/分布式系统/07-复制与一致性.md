# 第 7 章 Replication（复制与一致性）

> **本章地图**：为什么复制（性能/可用/就近）与复制的前提（一致性模型）

## 核心精讲

（以下伪代码均为**教学示意，不参与构建**。）

### 7.1 数据中心一致性模型（从强到弱）

| 模型 | 保证 | 一句话直觉 |
| --- | --- | --- |
| **严格一致（strict）** | 写后所有读立即可见 | 需要全局绝对时间，物理上不可实现 |
| **线性一致（linearizable）** | 操作看起来在调用与响应之间的**某一瞬间**原子生效 | 「分布式内存」的等价物；可全局定序且尊重实时序 |
| **顺序一致（sequential）** | 存在某个全局序与各进程程序序一致，但**不必**尊重实时序 | 「有一个合理的世界」但可能慢半拍 |
| **因果一致（causal）** | 有因果关系的操作全节点同序，并发的可不同序 | 向量时钟（Ch6）刻画的那个序 |
| **FIFO（PRAM）** | 同一进程的操作按程序序可见 | 因果的只看自己的弱化版 |

- 🔧 关键辨析（也是全书最重要的一个表）：
  - **线性一致 > 顺序一致 > 因果 > FIFO**；
  - 线性一致用实时钟，顺序一致不用——差这一条，Spanner 与普通多副本系统的差异就全在这。

### 7.2 客户端一致性（client-centric）

- 动机：
  - 大规模弱一致存储（DNS、购物车、社交流）做不到全局一致；
  - 但**每个用户自己的体验不能乱**。
- 四条保证：
  1. **单调读（monotonic-reads）**：
     - 读到的旧数据，之后不会读到更旧的；
     - 把读黏到同一副本。
  2. **单调写（monotonic-writes）**：
     - 同一客户的写在所有副本按发出序执行。
  3. **读己之写（read-your-writes）**：
     - 写完立刻能读到；
     - 会话黏主副本，或读副本前等待。
  4. **写后读（writes-follow-reads）**：
     - 写发生在「刚才读到的那版」之后；
     - 防止基于旧值的写覆盖。
- 🔧 工程落地：
  - 会话黏性（sticky session）、客户端会话 token 标注读版本；
  - 「客户端一致性是**会话**概念，不是全局属性」。

### 7.3 副本管理：放置与分发

- **放置**：
  - 镜像式全复制（小集合）；
  - 按地理位置选点（latency 感知放置：CDN 的 PoP、Spanner 的 region）；
  - 书给出「读性能/写开销/可用性」三目标权衡。
- **内容分发**：
  - **推（push）**：服务器主动更新副本——副本多、读密集合适；
  - **拉（pull）**：客户端/副本主动取——副本多、读稀疏合适（缓存模型）；
  - **租约（lease）**：推拉的折中——给副本一张限期合同，期内推、到期再拉
    （CDN 与元数据缓存的经典设计）。
- **副本数量管理**：动态增减副本组大小（负载驱动），增减本身是一致性操作。

### 7.4 一致性协议

- **主备（primary-backup）**：
  - 写走主，主把更新推给备；
  - 按「阻塞否、并行否」分四象限（同步阻塞→线性一致方向；异步→最终一致）；
  - 简单，主是瓶颈与单点（引 Ch6 选举 / Ch8 共识）。
- **复制写（active replication）**：
  - 所有副本都执行写（经组通信全序广播）；
  - 读可任意副本 → 读快写贵；
  - 要求**确定性执行**（状态机复制思想，接 Ch8）。
- **法定数（quorum / voting）**：
  - N 副本，读 R 个、写 W 个；
  - **约束 R + W > N 且 W > N/2**：读写集合必相交 → 不需要主也能保强读。

```python
# 教学示意：quorum 读写（Dynamo 风格）
N, R, W = 3, 2, 2        # R+W=4 > 3 ✓；W=2 > 3/2 ✓
def write(k, v):
    acks = [store_put(i, k, v) for i in pick(N)]
    return count_true(acks) >= W          # W 个确认才算写成功
def read(k):
    versions = [store_get(i, k) for i in pick(N)][:R]   # R 个副本
    return latest(versions)               # 按版本/时间戳选最新——必须比较！
```

- 🔧 书里特别强调 quorum 的**调参空间**：
  - W=N 读最优（副本读）；
  - R=1 写最优（单副本写）；
  - **参数即产品定位**。
- **缓存一致性**：
  - 失效（invalidation，下次读再取）vs 更新（update，主动推新值）；
  - 写透（write-through）vs 写回（write-back）；
  - CPU 缓存一致性（MESI，见 [../多处理器编程的艺术2/18-栅栏.md](../多处理器编程的艺术2/18-栅栏.md)）是同问题在硬件层的解。

## 近年研究与工业界开源实践（2015–2026）

- 🔧 **CRDT 成熟**：
  - Shapiro 的 CRDT 经 Kleppmann（DDIA 作者）等大力推动进入主流；
  - 协同编辑（Automerge/Yjs）、Redis CRDB、Riak（早期用户）；
  - CRDT = 「把 Ch6 向量时钟的并发冲突，用数据类型代数消解」。
- 🔧 **Jepsen 对一致性模型的经验检验**：
  - Jepsen（aphyr）用分布式黑盒测试把众多系统的宣传一致性**实测打回原形**；
  - MongoDB、Elasticsearch、etcd 历史版本等都有报告；
  - 「一致性模型是契约，必须测出来」——对 7.1 谱系表最好的工程注脚。
- 🔧 **Multi-Raft**：
  - 把 Raft（USENIX ATC 2014）按数据分片跑多个实例；
  - TiKV（`tikv/tikv` ≈16.9k★，实测）、TiDB、CockroachDB（≈32.5k★，实测）、etcd；
  - **每个分片内线性一致 + 分片间靠 HLC/时间戳协调**（接 Ch6 的 HLC）；
  - 主备协议（7.4 第一行）的当代完全体。
- **数据中心一致性产品化**：
  - Spanner、Kafka 的事务、etcd 的 linearizable read（ReadIndex）；
  - 7.1 的模型谱系成为 API 参数（`linearizable` / `sequential`）直接卖。
- **缓存一致性新层**：
  - `redis/redis`（≈76.5k★，2026-09 实测）主从 + Redis Cluster 的 gossip 与一致性哈希；
  - 7.3 放置 + 7.4 协议合体样本。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「CAP 三选二」 | 分区发生时才在 C/A 取舍；无分区时还有延迟维度（PACELC）；把「C」精确到线性一致才有操作意义 |
| 2 | 「最终一致 = 迟早和真值一样」 | 「最终」只收敛到**某个**一致状态；不定义冲突消解（LWW？CRDT？）就没意义 |
| 3 | 「quorum 就是强一致」 | R+W>N 只保证读写集相交；**读时还要比较版本选最新**，且 sloppy quorum（Dynamo 暂替副本）会破坏该保证 |
| 4 | 「客户端一致是全局弱化版」 | 它是**会话内**保证，跨会话/跨用户无定义；黏性会话失效（换设备、换副本）即失效 |
| 5 | 🔧 本书需 2026 补丁 | 书未覆盖 CRDT 与 Jepsen 检验：弱一致系统的冲突消解与可测性已成标准话题，读 Ch7 必须配这两块 |
| 6 | 🔧 本书需 2026 补丁 | 书的副本协议止于主备/quorum/主动复制三件套；**Multi-Raft + Percolator/Spanner 型事务复制**是当前数据库事实标准（接共识专题） |
