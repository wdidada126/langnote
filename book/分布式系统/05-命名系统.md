# 第 5 章 Naming（命名系统）

> **本章地图**：名字是分布式系统的「粘合剂」
> → 三种名字：**人类可读名 → 标识符（identifier）→ 地址（address）**
> → **扁平命名（flat naming）**：广播、转发指针（forwarding pointers）、家基法（home-based）、DHT
> → **结构化命名（structured naming）**：命名空间图、目录节点、别名与挂载、全局-管理-联合三层划分
> → **基于属性的命名**：LDAP → 实现案例：DNS 的层级与缓存。

## 本章地图

- Ch5 回答一个被低估的问题：「有了名字，怎么找到东西？」
  - 在节点可加可退的系统里（Ch1 定义），**按址引用不可持续，按名引用是唯一的解**。
- 章的骨架是「三种名字 + 三种解析机制」：
  - 扁平名（标识符）用什么办法定位；
  - 结构化名（域名式）怎么分层解析；
  - 属性名怎么查询。
- 书中的实现主角是 DNS 与 DHT（Chord）——「集中-分层」与「去中心-哈希」两种哲学的代表。

## 核心精讲

（以下伪代码均为**教学示意，不参与构建**。）

### 5.1 名字、标识符与地址

- **标识符（identifier）三性质**：
  1. 引用至多一个实体；
  2. 同一实体同一标识符；
  3. 一个标识符永不复用于另一实体；
  - UUID 是工程典范。
- **名字解析（name resolution）**：
  - 把名字映射到实体（或其地址/引用）；
  - **地址是名字的一种**——指向「位置」的名字；
  - 把地址当标识符用是反模式：实体一搬家地址就撒谎（书的立场）。

### 5.2 扁平命名：标识符怎么定位

- **广播/多播解析**：
  - 全网问「谁叫这个名」；
  - ARP 与 IP 多播的思路；简单但不可扩展。
- **转发指针（forwarding pointers）**：
  - 实体搬家时留「去向卡」，解析沿指针链走；
  - 优点：只更新局部；
  - 缺点：链断裂（某节点崩溃）全链失效、解析路径可能地理绕远。
- **家基法（home-based approach）**：
  - 实体有一个「家」（常是创建地），家记录当前位置；
  - 例子：移动 IP、早期 Skype、分布式数据库的元数据表；
  - 缺点：
    - **家所在地的地理可扩展性问题**——家远在纽约而实体常驻新加坡，每次解析绕地球；
    - 家是单点（接 Ch1 管理可扩展性）。
- **DHT（分布式哈希表）**：
  - 把 128-bit 标识符哈希到环上，每节点负责一段 key 区间；
  - **Chord**：指针表 O(log N) 项，解析 O(log N) 跳。

```python
# 教学示意：Chord 的指针表思想
# node 负责区间 (predecessor, node]；finger[i] = 环上 node+2^i 的第一个节点
def lookup(key):
    if in_interval(key, (pred.id, self.id)):
        return self                      # 命中本节点
    n = best_finger_below(key)           # 贪心跳向不越过 key 的最远指表项
    return n.lookup(key)                 # 每跳至少缩短一半距离 → O(log N)
```

- 🔧 DHT 解决了「家基法」的扩展性，但牺牲「人类可读」：
  - 工程上常组合——**人类名 → DHT key** 的映射交给上一层（DNS/IPFS 网关皆如此）。

### 5.3 结构化命名：命名空间与 DNS 式分层

- 命名空间 = 有向无环图：
  - **叶子节点**：实体；
  - **目录节点**：表（出边标签 → 节点标识）。
- 解析即「从根沿标签逐级走」；
  - **绝对路径/相对路径**与解析上下文（当前工作目录）——文件系统思维。
- **别名（alias）**：同一实体多个名字；
  - 硬链接：多指针指向同一实体；
  - 符号链接：一个名字存另一个名字的路径；
  - 分布式下的坑：目标删除后留下悬空链。
- **挂载（mounting）**：把外部命名空间接入本空间；
  - NFS mount、DNS 的 NS 委派同构。
- **三层划分（3rd ed 明确讲）**：
  - **全局层（global）**：顶层域——极稳定、跨组织；
  - **管理层（administrational）**：组织内子域——按部门管理；
  - **联合层（mutual）**：单台机器/用户目录——改动频繁；
  - 每层的可用性要求、缓存 TTL、复制策略都不同——**分层即扩展策略**。
- **DNS 要点**（书用大篇幅）：
  - 根/顶级/权威服务器三级；
  - 迭代 vs 递归解析（根服务器只做迭代应答——扩展性的关键决定）；
  - 缓存与 TTL；
  - CNAME 别名；
  - DNS 是全书「把 5.3 的理论做成可运行系统」的完整样本。

### 5.4 基于属性的命名：LDAP

- 名字带不上「找所有 CPU>16 核的打印机」这类查询；
- 属性-值对 + 层级目录（LDAP 的 DN 结构）；
- 把「查询」与「解析」融合的尝试。

## 近年研究与工业界开源实践（2015–2026）

- **服务发现三派**：
  - DNS 派：`hashicorp/consul`（≈30.1k★，2026-09 实测）——分层命名 + 健康检查合一；K8s 内置 CoreDNS 同理；
  - 协调存储派：`etcd-io/etcd`（≈52.3k★，实测）与 `apache/zookeeper`（≈12.8k★，实测）——名字表本身用共识协议维护（Ch6/Ch8 前奏）；
  - DHT 派：`ipfs/kubo`（star 未核验）——Kademlia 的最大规模现役部署，证明 DHT 没死，只是退守特定场景。
- **名字即服务**：
  - CDN 边缘 DNS（GeoDNS）与 Anycast 把「家基法的家」复制到全球——地理可扩展性问题的工业答案。
- **身份命名的新层**：
  - 去中心化标识符 DID、`did:web`、Verifiable Credentials（W3C 标准）；
  - 把「标识符永不复用」的形式化要求搬进身份体系。
- **DNS 安全化**：
  - DNSSEC 部署、DNS-over-HTTPS/TLS（DoH/DoT）；
  - 把本章未涉及的「名字解析可信」补上（正面接 [09-安全与前沿.md](09-安全与前沿.md)）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「地址 = 标识符」 | identifier 三性质明确排除位置信息；把 IP 当实体 ID 用，实体迁移/换网后系统全撒谎（手机漫游、容器重启皆此坑） |
| 2 | 「DHT 是比 DNS 更好的命名」 | DHT 解析的是**不可读的 key**；两者解决不同问题，工程上几乎总是组合而非替代 |
| 3 | 「转发指针只存在于旧移动计算」 | 变体活在到处：对象存储的重定向（302 到新区域）、容器迁移、CDN 重写规则 |
| 4 | 「DNS 缓存 TTL 随便设」 | TTL 是**一致性 vs 负载**的显式旋钮（故障切换慢 = 一致性差）；DNS 本质是弱一致复制系统（接 Ch7） |
| 5 | 🔧 本书需 2026 补丁 | 书未覆盖 service mesh 的名字空间（mTLS 身份 = SPIFFE ID）与零信任下的「名字→身份→连接」三段式；命名已从「定位」演进为「定位 + 认证」合一 |
| 6 | 🔧 本书需 2026 补丁 | 书的 LDAP 内容停留在 2010 年代企业目录；云时代「基于属性命名」的当代表述是资源标签（tag-based routing/policy） |

## 读完本章应能回答的问题

- 为什么「标识符永不复用」这么重要？
  - 复用的标识符让旧引用悄悄指向新实体（缓存、日志、消息里的 ID 全部被污染）；
  - UUID v4/ULID 的规模就是为这条性质服务的。
- 家基法的「家」放在哪里最好？
  - 靠近**解析请求的主要来源**而不是实体本身；
  - 现代变体：多区域元数据表 + 异步同步（元数据自身的复制，接 Ch7）。
- Chord 的 O(log N) 是怎么来的？
  - 指针表按 2 的幂次铺开，每跳把剩余距离减半；
  - 代价：成员变动时维护 O(log N) 项指表。
- DNS 为什么选择「根服务器只做迭代应答」？
  - 递归应答让根承担全部下游解析负载；
  - 迭代把工作分摊给本地递归解析器（可缓存）——可扩展性的关键一步。
- 三层划分对运维意味着什么？
  - 全局层求稳（变更以周/月计）、管理层求可控（按组织边界授权）、联合层求快（TTL 秒级）；
  - 同一套技术在不同层的 SLA 目标完全不同。
- 名字解析和路由是一回事吗？
  - 不是：解析把名字映射到实体/地址（本章）；路由决定包怎么送到那个地址（网络层）；
  - Saltzer 的 RFC 1498 正是为澄清这条边界而写。
- 扁平命名在数据库里的对应物是什么？
  - 表分区的主键路由表 / 对象存储的 object key 索引；
  - 解析目标从「机器」变成「分片」——机制同构。
