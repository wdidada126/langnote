# 03 关系模型与完整性约束

> 单元性质：⚠️ 主题重构。对应教材通行"The Relational Model"单元。深度对照：[../数据库系统概念6/02-关系模型介绍.md](../数据库系统概念6/02-关系模型介绍.md)（形式语言见其 06）与 [../数据库系统概念6/06-形式化关系查询语言.md](../数据库系统概念6/06-形式化关系查询语言.md)；中文权威表述：../数据库系统概论.md 第 2 章；理论纵深：[../Database_Design_and_Relational_Theory/00-总览与阅读地图.md](../Database_Design_and_Relational_Theory/00-总览与阅读地图.md)。

## 1. 关系作为数学对象

关系 = 域（domain）上笛卡尔积的子集；**度（arity）**=属性个数，**基数（cardinality）**=元组数。教材强调两个集合论性质：元组无序、属性值原子（1NF 的根）。域（domain）概念是本书相对 Silberschatz 的特色保留：把"类型+取值约束"独立建模（后并入 SQL 的 CREATE DOMAIN 讨论）。

- **超键/候选键/主键**（superkey/candidate key/primary key）逐级收紧；**外键**（foreign key）实现跨关系引用。
- **关系模式 vs 关系实例**：模式是长期契约，实例随事务瞬息变化——对应 01 章 instance/schema 之辨的形式版。

## 2. 完整性约束三梯队

1. **域约束**：属性值 ∈ 域（NULL 的合法性需显式声明）。
2. **实体完整性**：主键属性非 NULL 且唯一——🔧 exp1 实测：SQLite 中 `INTEGER PRIMARY KEY` 重复插入报 `UNIQUE constraint failed: department.dept_id`。
3. **参照完整性**：外键值要么 NULL 要么存在于被引关系——🔧 exp1 实测：插 dept_id=99 报 `FOREIGN KEY constraint failed`；且须 `PRAGMA foreign_keys=ON`（SQLite 默认 OFF 的历史包袱，见 ../Using_SQLite/07-建表约束与Pragmas.md）。
   级联策略：`ON DELETE CASCADE/SET NULL/RESTRICT`——🔧 exp1：SET NULL 后 Bob 的 dept_id 变 None。

## 3. 元组关系演算与域关系演算（存在性认知）

教材目的不是应考而是给出 SQL 的语义底座：{ t | P(t) }（元组演算）与 { <x1,...,xn> | P(...) }（域演算），安全表达式（safe expression）保证有限结果。关系代数（σ π ⋈ ∪ − ÷）作为过程式中间层，与 SQL 子句逐一对应：SELECT→π、FROM+WHERE→σ、JOIN→⋈。Silberschatz 第 6 章展开更细（含 ÷ 与递归闭包），本册以"能翻译十道 SQL"为合格线。

## 4. NULL：三值逻辑的工程债

UNKNOWN ≠ FALSE：`v = NULL` 恒为 UNKNOWN，聚合函数跳 NULL，GROUP BY 把 NULL 归同组，外连接引入 NULL（🔧 exp2：Dan 无部门，LEFT JOIN 产出 NULL 需 COALESCE 兜底）。教材在此埋伏笔：NOT IN 子查询含 NULL 会让整个谓词变 UNKNOWN 导致空结果——王珊册未强调、Silberschatz 有例题、本目录实测留作 05 章练习。

## 5. 关系模型为何赢

- **非过程声明**：用户描述"要什么"，优化器决定"怎么拿"（08）。
- **数据即事实**：结构与访问解耦，schema-on-write 契约换更新一致性；NoSQL 的 schema-on-read 是其镜像革命（14）。
- **理论可依赖**：FD/JD 理论（06）让"设计好坏"可判定——层次/网状模型给不了。
  ⚠️ 上述评价为本目录综合表述，非原书逐字。

## 6. 从模型到 SQL 的桥（预习 04）

CREATE TABLE = 关系模式声明 + 约束装订；INSERT/DELETE/UPDATE 是唯一合法改实例途径；SELECT 是演算式的表面语法。建议此刻跑一遍 [04-SQL基础-DDL与DML.md](04-SQL基础-DDL与DML.md) 的 exp1，把第 2 节三条约束的报错语料抄进笔记。

## 7. 常见错误清单

1. 把"主键唯一"当成"候选键全部唯一"的充分条件（最小性另判）。
2. 认为外键列类型必须与被引列"同名同类型"——标准只要求可比域；🔧 SQLite 动态类型甚至放宽到亲和性（type affinity，见 ../Using_SQLite/06-SQLite数据类型.md）。
3. 把关系代数 ÷ 与 SQL 的除法（双重 NOT EXISTS / GROUP-COUNT 技巧）混作 trivial——考试高频坑。
4. 忘记参照完整性对 UPDATE 同样生效（改主键侧要重验外键侧）。
5. 把 NULL 当 0/空串存数值缺口——聚合与比较全线中毒。

## 8. 小结

关系模型的三要素（结构/操作/约束）到此齐备：结构=关系，操作=代数+演算，约束=键+参照+域。04/05 章把"操作"展开成可跑的 SQL，06 章把"约束"深化成函数依赖理论。理论纵深读者请直接去 [../Database_Design_and_Relational_Theory/00-总览与阅读地图.md](../Database_Design_and_Relational_Theory/00-总览与阅读地图.md)（Date 的依赖理论全谱）。

## 9. 补充：关系代数十题自测表（SQL 互译）

| 题 | 代数 | SQL 骨架 |
|---|---|---|
| CS 系教师 | σ_dept=CS(instructor) | WHERE dept='CS' |
| 教师姓名+系名 | π_name,dept(teach) | SELECT 两列 |
| 选了 C101 的学生 | π_student(σ_course='C101'(enroll)) | 直接 WHERE |
| 教过 DiscreteMath 的教师 | teach⋈(σ_title=...)(course⋈... ) | JOIN+WHERE |
| 未选任何课 | student − π_student(enroll) | EXCEPT / NOT EXISTS |

## 10. 补充讨论：域（domain）概念的存废之争

Codd 原始表述中域是一等公民（姓名域/编码域共享语义），SQL 标准以 CREATE DOMAIN 承接却几乎无人用（PostgreSQL 实现最完整 ⚠️ 转述），主流工程用"约定+检查约束+代码生成"替代。教材保留域的价值：**让"同名不同义/同义不同名"可被机器发现**——数据集成与治理场景（数据元模型、ISO 元数据注册）其实是域思想的还魂，13/14 章湖仓 schema 治理会再遇。

## 12. 自测四问

1. 元组无序与"ORDER BY 合法"矛盾吗？（不：排序属查询层输出，不属关系。）
2. 外键一定指向主键吗？（标准可指任意候选键；多数引擎实际只支持 PK/UNIQUE，🔧 SQLite 需被引列有唯一索引。）
3. `IN (1,2,NULL)` 与 `NOT IN (1,2,NULL)` 行为为何不对称？（IN 遇 UNKNOWN 可为 TRUE；NOT IN 遇任何 UNKNOWN 即不为真——05 章子查询大坑的代数根源。）
4. 为什么弱实体必须有识别联系？（其键含拥有者成分；没有识别关系就造不出唯一键——02 章映射第 5 步的回声。）

## 13. 除法 ÷ 的两种 SQL 模板（对照 9 节题表）

设 R(A,B)、S(B)，求"覆盖 S 全部 B 值的 A"：

```sql
-- 模板一：双重 NOT EXISTS（教材原生形态）
SELECT r.A FROM R r WHERE NOT EXISTS
 (SELECT * FROM S s WHERE NOT EXISTS
  (SELECT * FROM R r2 WHERE r2.A=r.A AND r2.B=s.B));
-- 模板二：GROUP 计数法（工程更爱，易读）
SELECT r.A FROM R r JOIN S ON r.B=S.B GROUP BY r.A
HAVING COUNT(DISTINCT r.B) = (SELECT COUNT(DISTINCT B) FROM S);
```

🔧 练法：在 exp1 三表上把"教过 CS 与 Math 两系的教师"编成除法题（需自造 teacher_course 联系表），两模板同答=语义自洽的证明。注意模板二在 S 含重复/NULL 时的口径差——键去重是前提（06 章意图约束又现身）。

## 核心概念速览（中英对照）

- **relation / tuple / attribute** — 关系/元组/属性：集合论底座三词
- **domain** — 域：类型+约束的命名单元，本书特色构件
- **degree / cardinality** — 度/基数：列数/行数
- **superkey / candidate key / primary key** — 超键/候选键/主键：唯一性收紧链
- **foreign key** — 外键：跨关系引用句柄
- **entity integrity** — 实体完整性：主键非空+唯一
- **referential integrity** — 参照完整性：外键存在性或 NULL
- **ON DELETE CASCADE / SET NULL / RESTRICT** — 级联/置空/受限：违约处置策略
- **relational algebra** — 关系代数：σ π ⋈ ∪ − ÷ 的过程式中继
- **tuple relational calculus (TRC)** — 元组关系演算：{ t | P(t) }
- **domain relational calculus (DRC)** — 域关系演算：按分量约束
- **safe expression** — 安全表达式：保证有限结果
- **1NF (atomicity)** — 第一范式根定义：属性值不可再分
- **three-valued logic / UNKNOWN** — 三值逻辑：NULL 参与的比较真值

## 最新演进与工业实践

- **约束的现代表达**：PostgreSQL 17（2024）起支持 `NOT ENFORCED` 域约束与更完整的外键动作矩阵；SQL:2023 持续增补断言（assertion）议题 ⚠️ 细节以官方 release notes 为准。
- **SQLite 的实用主义**：外键默认关闭、动态类型亲和、`STRICT` 表（3.37+）逐版收紧——教材理想与工程现实的张力样本（../Using_SQLite/07-建表约束与Pragmas.md）。
- **数据契约回潮**：现代数据栈用 Great Expectations/dbt tests 在仓外重申"完整性约束"，等于把 1970 年代的域/键思想以 pipeline 断言复刻，治理线可参 [../Data_Governance_in_the_Era_of_AI_2e/00-总览与阅读地图.md](../Data_Governance_in_the_Era_of_AI_2e/00-总览与阅读地图.md)。
- **关系 vs 属性图**：SQL:2023 PGQ 让"键+引用"以图语言再叙述，本单元的外键视角是理解图"边属性"差异的底子。
