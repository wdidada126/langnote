# 07 存储结构与索引

> 单元性质：⚠️ 主题重构。对应教材通行"Storage & Indexing"两章的合并单元（教材章数>16 时本目录允许邻章合并，此处按"物理层一册通"重构）。深度对照：[../数据库系统概念6/10-存储和文件结构.md](../数据库系统概念6/10-存储和文件结构.md)、[../数据库系统概念6/11-索引与散列.md](../数据库系统概念6/11-索引与散列.md)；实现视角：../数据库系统实现.md、[../Database_Internals/00-总览与阅读地图.md](../Database_Internals/00-总览与阅读地图.md)、[../Fundamentals_of_Database_Indexing/00-总览与阅读地图.md](../Fundamentals_of_Database_Indexing/00-总览与阅读地图.md)；中文对照：../数据库系统概论.md 第 10 章。

## 1. 磁盘经济学：一切物理设计的母题

块/页（block/page，典型 4–16KB）是 I/O 原子；顺序读吞吐远高于随机读（现代 SSD 亦真，只是差距收窄 ⚠️ 量级随介质变）。DBMS 的应对：**缓冲池（buffer pool）**按 LRU/Clock 置换换页、脏页延迟写回。教材叙事重点：文件组织=把"关系实例"摊到"页序列"上的策略选择。

## 2. 文件组织三式

- **堆文件（heap）**：插入随意，扫描全族——SQLite 的表本质是 B+ 树（ROWID 序）而非纯堆 ⚠️ 方言差异点。
- **顺序文件（sequential）**：按搜索键排布，范围查询天堂，插入需搬家。
- **散列文件（hashing）**：静态哈希+溢出链；动态哈希（extendible/linear）处理桶分裂。DuckDB 的行组（row group）+局部统计是"微分区"变体 ⚠️ 转述。

## 3. 索引：二级结构的总分类

稠密/稀疏（dense/sparse）；主索引（聚簇，一表至多一个）vs 辅助索引（二级）；**B+ 树**（平衡、叶链、范围友好——教材的绝对主角）；**散列索引**（等值 O(1)，无范围无排序）；**位图索引**（低基数列，OLAP 传统武器，写并发代价高）；**多列/复合索引**（最左前缀原则）；**覆盖索引**（index-only 免回表）；**部分索引**（带 WHERE 的瘦身索引）。叶节点装"键→ROWID/主键"还是整行=索引组织表（IOT）之别。

## 4. 🔧 exp4：索引效应的定量现场（30 万行销售表）

方法：`dbwave_w7_dbill\exp4_indexes.py`，SQLite 3.45.3，`sales(id PK, region, product, amount, day)` 30 万行，查询 `region='R3' AND amount>450`（命中 2887 行）：

| 阶段 | 🔧 实测 |
|---|---|
| 无索引 | `SCAN sales`，**17.9 ms** |
| 建 `idx(region, amount)` | `SEARCH ... USING COVERING INDEX idx_sales_region_amount (region=? AND amount>?)`，**0.34 ms**（约 52 倍） |
| 仅 `region=?` | 同索引最左前缀可用 |
| `product='P7'`（非前缀列） | 仍 `SCAN sales`——最左前缀失效的铁证 |
| 部分索引 `WHERE region='R3'` | 对该子集查询 `SEARCH ... USING COVERING INDEX idx_partial` |
| DROP 复合索引后 | 回退 `SCAN`（残余 idx_partial 被试用于子集探测） |

教学结论三连：① `EXPLAIN QUERY PLAN` 里 SCAN vs SEARCH 即"全表 vs 索引"的指纹；② 覆盖索引的省钱处在于**免回表**（查询列全在索引内，COUNT(*) 场景尤其夸张）；③ 复合索引列序=查询谓词谱，写反即废（exp4 的 product 行）。

## 5. 索引的代价税表（教材必给的另一面）

空间（二级索引≈复制键列+指针）、插入/更新放大（每索引多一次结构维护）、优化器选择错误（统计过期→弃索引）、锁与日志足迹。工程守则：少而准的复合索引>多而散的单体索引；写多读少的表上索引是负债。🔧 exp4 补一条：30 万行建索引本身耗时亚秒级，但百万级表上 CREATE INDEX 在生产需并发/在线策略 ⚠️（SQLite 锁全库，PG 有 CREATE INDEX CONCURRENTLY，非本机行为）。

## 6. 与逻辑设计的接口

06 章反规范化常为"少 JOIN"，本章索引决定"JOIN 快不快"——外键列**必须配索引**（否则 CASCADE/查找全表）；这是把教材两章缝合的第一个工程律。🔧 exp1 的 instructor.dept_id 即教科书案例：删 department 行触发对 instructor 的参照检查，无索引时逐行扫（小表无感，百万行即痛）。

## 7. 常见错误清单

1. 以为 UNIQUE 约束与唯一索引是两物（🔧 exp4 `PRAGMA index_list('sales')` 可见 PK 与 UNIQUE 均以索引形态存在）。
2. 在最左列带函数的谓词上等索引（`WHERE upper(name)=...` 需表达式/生成列索引）。
3. 位图索引用于 OLTP 热行（锁放大）。
4. 复制索引列序直觉化：把高频等值列放前、范围列放后（exp4 的 region=? AND amount>? 正例）。
5. 统计不更新（ANALYZE 缺位）导致"有索引不走"——先查统计再怪索引。

## 8. 小结

物理层三问：数据怎么摊（文件组织）、怎么找（索引结构）、怎么省（缓冲与覆盖）。08 章把这三件资源交给优化器调度；09–11 章再给它们加上时间与故障的维度。

## 9. 补充：B+ 树手写演练（纸面 15 分钟）

给定插入序列 (8,20,12,5,15,25,3,17,10,22,7,19)，阶 m=3（叶最多 2 键）：逐键插入、分裂、上推中间键——叶链终态按键升序串联。考点三连：① 分裂上推的是**副本**（叶仍留全键）——B 树与 B+ 树的判据差异；② 删除合并借键（underflow 处理）；③ 高度 h≈log_{⌈m/2⌉}(N/叶容量)——30 万行表按 200 键/叶估三层封顶，解释 exp4 索引扫为何恒定几次 I/O。**手建一遍的收获大于读三章**：这是教材索引章唯一的"肌肉记忆"投资。

## 10. 补充：散列索引的失与得（对照 exp4）

| 场景 | 散列 | B+ 树 |
|---|---|---|
| 等值 `region='R3'` | 平手/略优 | 平手 |
| 范围 `amount>450` | ✗ 无法用 | ✓ |
| 前缀有序扫描/排序消解 | ✗ | ✓ |
| 低基数热点（R3 占 1/10） | 桶溢出链长 | 树仍平衡 |

工程读法：exp4 若把复合索引换成 `region` 单列散列索引，`amount>450` 谓词只能回表后逐行判——"索引存在但只帮了一半"的量化样本。SQLite 不提供用户散列索引（其索引皆 B 树）、MySQL 家族有 MEMORY 表哈希先例 ⚠️ 转述；DuckDB 的 ART 索引对分析负载基本"隐形"——列式靠扫描+ZoneMap 胜过索引，再次印证 06 章"场景决定设计"。

## 11. 补充：索引维护的隐藏账（写入路径）

一次 INSERT 的完整足迹：堆/叶插入 + **每个二级索引一条** + WAL 日志段 + 统计信息延迟更新。exp4 建索引前的 17.9ms 全扫与 0.34ms 索引扫背后，是"读收益×并发写成本"的对账：把 exp4 改造成"插入 3 万行计两次（有/无 idx）"即得自己的写放大系数（🔧 方法一句话，建议留作课后实验，目录脚本已就位可扩展）。

## 12. 自测四问

1. 聚簇索引为何一表至多一个？（物理序只有一种；"逻辑聚簇"概念在列式/分区表中被"排序键"继承 ⚠️。）
2. 覆盖索引对 `SELECT *` 为何失效？（SELECT * 需要未入索引列→回表，覆盖不再成立——08 章戒律 2。）
3. 部分索引何时优于全量？（热点子集小而查询密（如 `WHERE status='open'`），索引体积与写税同步缩——exp4 idx_partial 样本。）
4. IOT 与"表即主键索引"的关系？（IOT 叶=数据行本身；二级索引叶存主键再回 IOT——"回表"定义在 IOT 下改变。）

## 13. 行存 vs 列存速览表（为 13 章 OLAP 埋点）

| 维度 | 行式（教材 B+ 树主场） | 列式（DuckDB/仓系） |
|---|---|---|
| 页内容 | 一行的所有列 | 一列的一段连续值 |
| 点查（整行） | 一次 I/O 完胜 | 逐列拼装，靠 rowid 对齐 |
| 聚合（少数列） | 扫全行浪费带宽 | 只读所需列，SIMD/压缩双赢 |
| 索引角色 | 核心加速器 | 常退位为"跳过统计"（ZoneMap） |
| 更新 | 原地+日志 | 追加+合并（delta） |
| 本机代表 | SQLite（表即 B 树）🔧 | DuckDB 🔧（exp5 百万行聚合 3.8ms） |

一句话记忆：**点查找行、分析找列；索引是行的艺术，扫描是列的艺术**。

## 核心概念速览（中英对照）

- **block / page** — 块/页：磁盘 I/O 原子单位
- **buffer pool / replacement policy** — 缓冲池/置换策略：内存与磁盘的调度中枢
- **heap file / sequential file / hash file** — 堆/顺序/散列文件：三种摊法
- **extendible hashing** — 动态哈希：目录桶+分裂扩容
- **B+ tree index** — B+ 树索引：平衡多叉+叶链，等值与范围通吃
- **dense vs sparse index** — 稠密/稀疏索引：每键一条 vs 每块一条
- **clustering (primary) index** — 聚簇/主索引：与物理序对齐，一表一个
- **secondary index** — 二级索引：辅助路径，叶存指针
- **composite index / leftmost prefix** — 复合索引/最左前缀：exp4 实测主角
- **covering index** — 覆盖索引：免回表的索引列闭包
- **partial index** — 部分索引：带谓词的瘦身索引
- **bitmap index** — 位图索引：低基数 OLAP 利器、OLTP 毒药
- **index organized table (IOT)** — 索引组织表：按主键物理排序
- **write amplification** — 写放大：索引税的时间形态

## 最新演进与工业实践

- ** LSM-tree 时代**：教材 B+ 树中心叙事在工业已扩编为 Bw-tree（CockroachDB/MongoDB 引擎路线）与 LSM（RocksDB/Cassandra/Bigtable）家族；入门先 B+ 树、进阶看 [../Database_Internals/00-总览与阅读地图.md](../Database_Internals/00-总览与阅读地图.md) 与 [../../db/db.md](../../db/db.md) 的论文清单。
- **列式与向量化**：DuckDB 行组+ZoneMap 微型物化统计把"跳过扫描"做成默认（🔧 exp5 百万行聚合 3.8ms 即其成果），教材的索引观在分析域让位于"少干活"（分区/分桶/排序键）。
- **SQLite 索引现状**：WAL+部分索引+生成列索引+FTS5 虚拟表索引（[../The_Definitive_Guide_to_SQLite_2e/00-总览与阅读地图.md](../The_Definitive_Guide_to_SQLite_2e/00-总览与阅读地图.md)），教学实验零成本。
- **自动索引/DBMS 内智**：云托管服务（自动索引推荐/查询内智）在 2024–2026 普及，"人肉选列序"技能被辅助但未被替代——教材此章仍是读懂推荐结果的先修 ⚠️。
