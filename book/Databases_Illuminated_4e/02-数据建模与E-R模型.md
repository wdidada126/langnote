# 02 数据建模与 E-R 模型

> 单元性质：⚠️ 主题重构。对应教材通行"Conceptual Data Modeling / E-R"单元。深度对照：[../数据库系统概念6/07-数据库设计E-R模型.md](../数据库系统概念6/07-数据库设计E-R模型.md)；建模工程视角另册：[../Database_Modeling_and_Design_5e/02-实体联系模型ER.md](../Database_Modeling_and_Design_5e/02-实体联系模型ER.md)；中文设计流程对照：../数据库系统概论.md 第 7 章。

## 1. 建模为什么先于建表

教材立场：直接"想到哪建到哪"的表设计会在需求变更时崩塌；概念模式（conceptual schema）用业务语言（实体/联系/属性）冻结"what"，把"how"（关系模式、索引、分区）推迟。E-R 模型（Chen, 1976）的价值不在图好看，而在**逼出隐藏假设**：基数是 1:1 还是 1:N？联系要不要自己的属性？

## 2. E-R 核心构件

- **实体集（entity set）**与**实体**：一类可区分的业务对象；**主键（key）**选择要求唯一+最小。
- **属性**：简单/复合、单值/多值、派生（stored-vs-derived 之争：教材提醒派生属性冗余是 06 章"更新异常"的伏笔）。
- **联系集（relationship set）**：带**参与约束**（total/partial，双线/单线）与**基数比**（1:1、1:N、M:N）。M:N 联系在关系映射时必拆为独立表——这是学生第一次见到"模型形状决定表数量"。
- **弱实体集（weak entity set）**：无自然键，依赖拥有者（identifying relationship），主键=拥有者键+分辨符（partial key）。

## 3. EER：增强实体联系

教材（与 Silberschatz 第 7 章同谱）在 E-R 上叠三层：**子类/超类**（specialization/generalization）、**约束**（disjoint/overlap、complete/partial）、**聚合/汇集**（aggregation，把联系当实体再参与联系）。EER 对 OO 继承的映射（表-per-类型谱系三种策略）是后续"对象数据库"单元（14 邻域）的桥梁。

## 4. E-R → 关系模式的标准映射（算法化背功）

1. 强实体集 → 表；复合属性展平、多值属性独立表（1:N）。
2. 1:N 联系 → 外键放入 N 端表。
3. M:N 联系 → 独立联系表（双外键+复合主键）。
4. 1:1 → 外键任选一端或合并（教材给权衡：稀疏则独立表）。
5. 弱实体 → 独立表，主键含拥有者键。
6. 子类映射三选：EER 属性并入超表（NULL 多）、子表只放差异+共享超键、或一表一列布尔（约束难表达）。

🔧 **映射落地实验（SQLite，exp1 同款环境）**：上述 1–3 步即 [04-SQL基础-DDL与DML.md](04-SQL基础-DDL与DML.md) exp1 的 department/instructor/course 三表：instructor.dept_id REFERENCES department 兑现"1:N 外键放 N 端"；实测 `PRAGMA foreign_keys=ON` 下删除被引部门报 `FOREIGN KEY constraint failed`，而定义 `ON DELETE SET NULL` 后 Bob 的 dept_id 变 None——参照语义与 E-R 参与约束（total/partial）在此一一对应。

## 5. 建模质量判据（与 06 章的分界）

E-R 层判据：**忠实（faithful）**——每个约束在图中有表达；**最小冗余**——不重复建模；**可映射**——能机械翻译到关系模式。规范化（06）处理的是"翻译之后"函数依赖层面的异常，两者不互相替代。教材常设陷阱题：把"多值属性"直接存逗号串——既违 1NF 又丢可查询性，NoSQL 文档模型用数组重新接纳它（14）。

## 6. 需求驱动的设计流程

需求收集→概念设计（E-R）→逻辑设计（关系模式+规范化）→物理设计（索引/存储，07）→应用实现→运维演化。王珊册把该流程做成"数据库设计"独立章并给出新奥尔良（New Orleans）方法框架，可对照 ../数据库系统概论.md；本书特色在练习形态：给业务语料让学生画 E-R 再数表——建议自测：某"课程-选课-教师-系"语料应至少产出 4 表 1 联系表，与 exp1 结构一致。

## 7. 常见错误清单

1. 把联系的多对多误标为 1:N（漏掉选课人数维度）。
2. 弱实体漏画双框/双菱形——映射时就会丢分辨符。
3. 派生属性入库（age 与 birthdate 并存）→ 更新异常。
4. 用 NULL 表达"未知"与"不存在"两种语义（三值逻辑坑，05 章 JOIN 实测可见 Dan 行需 COALESCE）。
5. E-R 图上加索引注记：概念层不该出现物理决策。

## 8. 小结

本单元的合格标准：给任意中等复杂度业务语料，能在纸上完成"实体/联系/约束"三分、给出映射后的表清单并解释每处外键去向。之后进入 03，把"关系"从映射产物升格为数学对象。

## 9. 补充：一页纸病例演练（含参考答案）

语料："某诊所记录病人、医生、每次就诊（处方多味药）、每味药的库存与供应商；一位医生可属多科室。"
- 实体：Patient、Doctor、Medicine、Supplier；联系：就诊（就诊本身要属性：日期/诊断→联系升格为"就诊"实体，这是教材反复强调的 **联系实体化** 手法）、处方（就诊×药品 M:N，数量属性挂联系）、供应（药品×供应商 M:N，价格属性）、科室（医生 M:N 或经"任职"联系带起止日期）。
- 映射产出 ≥7 表；处方表主键=(就诊ID,药品ID)——学生常漏复合主键。
- 判分点：是否给"就诊"建实体（漏→下次要改模）；多值"诊断"是否拆表；日期区间属性是否落在联系上。

## 10. 补充讨论：为什么 E-R 比 UML 类图更适合数据库教学

两者表达力近似，但 E-R 的**基数比/参与约束**是为"映射到表"校准的原生词汇，UML 多重性（0..*）需要翻译且诱导学生把"对象导航"错当"连接语义"。建模工程册（[../Database_Modeling_and_Design_5e/03-UML对象建模.md](../Database_Modeling_and_Design_5e/03-UML对象建模.md)）给了 UML 派完整表述，两派对照读比站队更有收获。

## 11. 图示速记（文字版）

- 矩形=实体集；椭圆=属性；菱形=联系；双边框=弱实体/识别联系；双线菱形=total 参与；三角/带弧=IS-A（EER 子类）；下划线=键。
- 默画顺序：先椭圆+矩形（有什么）→菱形（怎么连）→基数与参与（连几根线、可否缺席）→键。四步各错一次，映射就错一类。

## 12. 自测四问

1. 1:1 联系何时值得独立成表？（属性稀疏/两侧全参与但更新频率差异大/需历史保留。）
2. total participation 映射成什么约束？（外键 NOT NULL+删除侧受限；🔧 对应 exp1 的 RESTRICT/SET NULL 选择。）
3. 为什么聚合（aggregation）不可省？（联系不能直接当另一联系成员，不提升就断表达力。）
4. 多值属性直接存逗号串，两宗罪？（违 1NF+无法按值索引/约束，14 章文档模型以数组+索引机制重新解决。）

## 13. 映射检查清单（交表前逐项打钩）

1. 每个实体集→表？每个属性→列（复合已展平）？
2. 每个 M:N 联系→独立表且主键=两端键并？
3. 1:N 是否把外键放进 N 端（而非两端各半）？
4. total 参与是否落 NOT NULL？partial 是否落可空+删除策略？
5. 弱实体主键是否含拥有者键+分辨符？
6. 派生属性是否已剔除？多值是否已拆表或声明为数组语义？
7. 每个外键列是否计划配索引（07 章律）？
8. 子类映射策略三选一是否写明并留痕（防 EER 演化歧义）？

## 核心概念速览（中英对照）

- **entity set** — 实体集：可区分业务对象的集合，映射为表
- **relationship set** — 联系集：实体间的业务关联，M:N 必独立成表
- **attribute** — 属性：simple/composite/multi-valued/derived 四类形态
- **key constraint** — 键约束：唯一性+最小性
- **participation (total/partial)** — 参与约束：双线/单线，映射到 NOT NULL/ON DELETE 策略
- **cardinality ratio** — 基数比：1:1、1:N、M:N
- **weak entity set** — 弱实体集：无自然键，主键=拥有者键+分辨符
- **identifying relationship** — 识别联系：弱实体的依赖边
- **specialization / generalization** — 特化/概化：EER 继承轴
- **disjoint / overlap constraint** — 不相交/重叠约束：子类成员资格规则
- **aggregation** — 汇集：把联系提升为可再参与联系的实体
- **conceptual schema** — 概念模式：与实现无关的 what 层
- **EER-to-relational mapping** — EER 映射：本单元第 4 节的机械翻译术

## 最新演进与工业实践

- **图思维回潮**：E-R 的"实体+边"在 2024–2026 以属性图（Property Graph）形态回归主流——SQL:2023 的 PGQ 片段与 Neo4j/GDB 生态使"建模语言"从图到 SQL 双向对齐 ⚠️ 标准细节以 ISO 目录为准。
- **建模工具**：erwin/Data Modeler、dbdiagram.io、PlantUML/mermaid 的 ER 图为课堂常用；本目录建议用 mermaid `erDiagram` 复刻第 4 节三表结构。
