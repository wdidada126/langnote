## 核心精讲

> 以下均为**教学示意，不参与构建**。

### 1. 一个现代化的最小 CMake 骨架

```cmake
# 教学示意：CMake 的目标导向写法（不参与构建）
cmake_minimum_required(VERSION 3.28)          # 2026 年建议 3.28 以上（3.31 量级的现代用法）
project(note_demo LANGUAGES CXX VERSION 1.0.0)

set(CMAKE_CXX_STANDARD 17)                    # 也可以改为 20 / 23
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)                 # 不用 -std=gnu++17

add_library(core src/core.cpp)
target_compile_features(core PUBLIC cxx_std_17)   # 把「需要 C++17」这件事交给使用者
target_include_directories(core PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include)

add_executable(app app.cpp)
target_link_libraries(app PRIVATE core)
```

现代 CMake 的三条心法：

1. **面向目标**（`target_*`）而不是面向变量（`set(... CMAKE_...)`），配置只写在确实需要的地方；
2. **`PUBLIC` 表达「谁用我需要什么」**，`PRIVATE` 表达「只有我自己需要」；
3. **安装与导出**用 `install(TARGETS ... EXPORT)` + `install(EXPORT)`，让包对其他项目可复用。

### 2. 依赖获取的三条路线

```cmake
# 教学示意：CPM 拉取源码依赖（不参与构建）
include(FetchContent)
# CPM 只是 FetchContent 的一层封装，便于缓存与版本锁定

find_package(Boost REQUIRED)                   # 系统/包管理器提供
find_package(fmt CONFIG REQUIRED)              # CMake 包配置模式
target_link_libraries(app PRIVATE fmt::fmt)
```

| 方案 | 适用 | 取舍 |
| --- | --- | --- |
| 系统包管理器（apt/dnf/homebrew） | 通用库 | 版本受发行版约束 |
| vcpkg | Windows / 需要统一工具链 | 生态大但首次构建慢 |
| CPM / FetchContent | 只含头文件的库、内部库 | 可复现、可缓存，但要自己承担构建 |
| Conan | 需要精细的编译选项矩阵 | 灵活，学习曲线陡 |

> 判断准则：**内部库与头文件库用源码依赖（CPM/FetchContent）**，有正式发布流程的第三方库优先包管理器，避免「每个项目都自己造一份依赖树」。

### 3. 告警是免费的静态审查

```bash
# 教学示意：常用告警开关（不参与构建）
g++ -std=c++17 -Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wpedantic -O2 src/app.cpp
clang++ -std=c++17 -Wall -Wextra -Wpedantic -D_GLIBCXX_ASSERTIONS
```

重点告警的含义：

| 告警 | 防的是什么 |
| --- | --- |
| `-Wconversion` | 隐式窄化（`double` → `int`、`size_t` → `int`） |
| `-Wshadow` | 变量遮蔽，读代码时被误导 |
| `-Wold-style-cast` | C 风格强转掩盖真实转换（配合 `-Wconversion`） |
| `-Wsign-conversion` | 符号性混用，跨平台容量问题的温床 |
| `-D_GLIBCXX_ASSERTIONS` | 标准库层面的越界与逻辑错误检查（性能有代价，仅用于调试/测试构建） |

### 4. sanitizer：把「猜 bug」变成「定位 bug」

| 工具 | 查什么 | 备注 |
| --- | --- | --- |
| ASan | 越界、use-after-free、double-free | 开销中等，最常用；配合 LeakSanitizer |
| UBSan | 未定义行为（有符号溢出、错误对齐） | 几乎零开销，可长期开着 |
| TSan | 数据竞争 | 需要重新编译，会放慢；内存序错误它最擅长 |
| MSan | 未初始化内存读取 | 需要全量工具链插桩，较少用 |

> **顺序建议**：本地与 CI 用 `ASan + UBSan`；涉及并发的模块加跑一次 `TSan`；发布前跑一次 `LeakSanitizer` 作为内存泄漏门禁。

### 5. C++ Insights：把模板展开给人看

模板、lambda、`constexpr` 生成的代码在编译器眼里和源码差别巨大；C++ Insights（本次实测 **4.5k★**）能把「编译后的等价源码」打印出来，是排查「为什么我的模板没被实例化」「为什么这里调用了拷贝构造」的神器。

### 6. 静态分析从三条规则起步

```bash
# 教学示意：clang-tidy 的用法（不参与构建）
clang-tidy -p build/compile_commands.json src/app.cpp   # -p 指定编译数据库
# C++ Core Guidelines 检查集：cppcoreguidelines-*，现代风格：modernize-*, performance-*
```

`clang-tidy` 传入 `-p compile_commands.json` 才能知道**每个文件的真实编译参数**——所以**必须启用 CMake 的 `CMAKE_EXPORT_COMPILE_COMMANDS=ON`**，这也是 `clangd` 能从任意编辑器提供准确补全与跳转的前提。

| 工具 | star | 定位 |
| --- | --- | --- |
| `include-what-you-use/include-what-you-use` | **4.8k★** | 头文件包含的最小化 |
| `cppcheck-opensource/cppcheck` | **6.8k★** | 跨平台静态分析，契合旧代码库 |
| `cpp-best-practices/cppbestpractices` | **8.8k★** | 可直接抄的清单与配置 |
| `ccache/ccache` | **3.0k★** | 编译缓存，省 CI 时间 |

### 7. 基准测试：不要凭感觉优化

```cpp
// 教学示意：benchmark 的基本写法（不参与构建）
static void BM_MoveReturn(benchmark::State& state) {
    for (auto _ : state) {
        auto v = build_vector();        // 关注返回值路径的整体成本
        benchmark::DoNotOptimize(v);    // 防止被优化掉
    }
}
BENCHMARK(BM_MoveReturn);
BENCHMARK_MAIN();
```

## 版本演进

| 版本 | 变化 |
| --- | --- |
| C++11 | 模块化提案起步（module TS） |
| C++17 | 文件系统、并行算法；模块进入工作草案但被推迟 |
| C++20 | **模块正式入标准**；`import`、`export`、`module` |
| C++23 | **标准库模块 `import <vector>`** 可用（各编译器支持程度不同）；`std::print` |
| 编译器侧 | GCC 11+ / Clang 15+ / MSVC 19.33+ 对 C++20 特性的支持趋于完整；模块仍需搭配 CMake 的专门支持 |
| 🔧 2026 | 模块化在大型项目里开始有真实收益（编译时间、头文件传播），但生态与工具链仍在铺开 |

## 近年研究与工业界开源实践（2015–2026）

- **「编译数据库」成为基础设施**：`compile_commands.json` 同时服务于 `clangd`、`clang-tidy`、`C++ Insights`，几乎所有项目都在 CI 里开启 `CMAKE_EXPORT_COMPILE_COMMANDS=ON`。
- **clang-format 成为跨团队共识**：一次配置（ based on LLVM / Google 风格）＋ CI 检查，能把「格式争论」彻底消掉。
- **模块化的现实进展**：`import <vector>` 已在主要编译器上可用，但 CMake 对模块接口单元（`*.ixx`/`*.cppm`）的支持成熟度不一，2026 年的合理姿势是**在大型新项目里试点，而不是全面改造**。
- **编译时间成为架构指标**：PCH、Unity Build、ccache、`-fpch-preprocess`、模块化的根本诉求都是「少编译一点」，大型项目开始把「新增头文件的数量」纳入 review 关注点。
- 🔧 **CMake 3.31 量级的现代用法**：`FetchContent` + `CPM` 组合、`CMAKE_CXX_STANDARD` 统一标准、`install(EXPORT)` 规范化引用、`--target all` 之外的目标粒度构建；建议在 2026 年把老式的 `add_definitions`/`set(CMAKE_*)` 写法替换掉。
- 🔧 **`std::print`/`std::format`（P2093）减少了第三方格式化依赖**：它同时改善了「日志也要写基准」这件事的成本。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「只要能编译就行」 | 打开 `-Wall -Wextra -Wpedantic` 并把告警当错误；这是成本最低的质量投入 |
| 2 | 「`printf` 调不出 bug 就换工具」 | 先用 ASan/UBSan；TSan 专治内存序 |
| 3 | 「clang-tidy 一次性全开」 | 先开 `modernize-*`、`performance-*`，存量代码分阶段清理，否则规则会变成噪声被全员忽略 |
| 4 | 「模块是 C++20 就一定能用」 | 语言层面进了标准，但**工具链与生态的成熟度**是另一回事；2026 年适合试点，不适合一刀切 |
| 5 | 「CMake 就是一堆 `set`」 | 现代 CMake 面向目标与导出；老写法（全局变量、手写 install 规则）会拖垮依赖消费方 |
| 6 | 🔧 本讲对 CMake 的篇幅偏少 | 2026 年的建议是**目标导向 + `target_compile_features` + `install(EXPORT)` + CPM**，并把 `CMAKE_EXPORT_COMPILE_COMMANDS=ON` 写进预设 |
| 7 | 🔧 未讲清楚 `compile_commands.json` 的作用 | 它是 `clangd`/`clang-tidy`/Insights 的公共输入，缺了它所有这些工具都会「猜」编译参数 |
| 8 | 🔧 缺少「编译时间是真实成本」的度量 | 建议把编译时间、二进制体积纳入性能回归；用 ccache + ccache 统计验证收益 |
| 9 | 🔧 未提 C++23 标准库模块的可移植性 | `import <vector>` 的可用性与编译器版本强绑定，跨平台的库应提供「模块 + 传统头」两种消费方式 |
