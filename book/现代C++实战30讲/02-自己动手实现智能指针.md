# 讲 02｜自己动手，实现 C++ 的智能指针

> **一句话**：看懂 `shared_ptr` 的实现，才真正看懂引用计数；而理解它的代价（原子操作、控制块、二次解引用），你才会明白为什么现代 C++ 的默认答案是「不要有第二个所有者」。

## 核心精讲

> 以下均为**教学示意，不参与构建**。

### 1. 三态：先选所有权，再选类型

| 语义 | 类型 | 代价 |
| --- | --- | --- |
| 独占，可转移 | `std::unique_ptr<T>` | 一次移动、零原子操作 |
| 共享，引用计数 | `std::shared_ptr<T>` | 控制块的原子增减 + 一次额外间接寻址 |
| 只观察，不延长生命 | `std::weak_ptr<T>` | 计数不增加，`lock()` 可能返回空 |

工程判断的顺序是：**默认用栈对象；必须堆分配时默认 `unique_ptr`；只有语义上真的「共有一份资源」才退回 `shared_ptr`。**

### 2. 手写独占指针

```cpp
// 教学示意：极简 unique_ptr 骨架（不参与构建）
template <typename T>
class my_unique_ptr {
    T* ptr_ = nullptr;
public:
    my_unique_ptr() noexcept = default;
    explicit my_unique_ptr(T* p) noexcept : ptr_(p) {}

    my_unique_ptr(const my_unique_ptr&) = delete;               // 独占：禁止拷贝
    my_unique_ptr& operator=(const my_unique_ptr&) = delete;

    my_unique_ptr(my_unique_ptr&& other) noexcept : ptr_(other.ptr_) { other.ptr_ = nullptr; }
    my_unique_ptr& operator=(my_unique_ptr&& other) noexcept {
        if (this != &other) { delete ptr_; ptr_ = other.ptr_; other.ptr_ = nullptr; }
        return *this;
    }

    ~my_unique_ptr() { delete ptr_; }                            // RAII 的落点
    T* get() const noexcept { return ptr_; }
    T& operator*() const noexcept { return *ptr_; }
    T* operator->() const noexcept { return ptr_; }
};
```

**它就是 RAII 的一个特例**：构造即接管、析构即释放、移动即转移。差别只在于「谁负责在出错时清理」被写进了移动操作。

### 3. 手写共享指针：控制块是核心

```cpp
// 教学示意：控制块与强弱计数（不参与构建）
struct control_block_base {
    long strong = 1;        // 强引用数：为 0 时销毁托管对象
    long weak   = 1;        // 弱引用数：为 0 时销毁控制块本身
    virtual ~control_block_base() = default;

    void add_ref()   { /* 需要 std::atomic_long 的 fetch_add */ }
    void add_weak()  { /* 同上，计到弱引用 */ }
    void release()   {
        if (--strong == 0) {
            dispose();                  // 调用删除器
            release_weak();             // 强引用归零后弱引用也要减一次
        }
    }
    void release_weak() { if (--weak == 0) delete this; }
    virtual void dispose() = 0;
};

template <typename T>
struct control_block : control_block_base {
    T* obj;
    explicit control_block(T* p) : obj(p) {}
    void dispose() override { delete obj; }
};
```

为什么需要**两个**计数？因为 `weak_ptr` 不延长对象生命，但控制块自己要活到最后一个 `weak_ptr` 消失。这就是「弱引用计数」存在的唯一理由，也是很多手写实现的第一个 bug。

```cpp
// 教学示意：weak_ptr 的用法（不参与构建）
std::shared_ptr<Connection> sp = acquire();
std::weak_ptr<Connection> wp = sp;
sp.reset();
if (auto locked = wp.lock()) {        // 可能得到空
    locked->send("hello");
}
```

### 4. 循环引用：计数归不了零的那一类

```cpp
// 教学示意：双向引用造成泄漏（不参与构建）
struct Node {
    std::shared_ptr<Node> parent;
    std::vector<std::shared_ptr<Node>> children;
};
// a->children.push(b); b->parent = a;   // a 与 b 的强引用永远不为 0

// 修正：把父指针改成 weak_ptr
struct NodeFixed {
    std::weak_ptr<NodeFixed> parent;
    std::vector<std::shared_ptr<NodeFixed>> children;
};
```

### 5. 自定义删除器：智能指针的真正卖点

```cpp
// 教学示意：删除策略作为类型的一部分（不参与构建）
auto file_deleter = [](FILE* f) noexcept { if (f) std::fclose(f); };
std::unique_ptr<FILE, decltype(file_deleter)> fp(std::fopen("a.txt", "r"), file_deleter);

// C 资源、C++ 数组、C 风格句柄都能这样包一层
std::unique_ptr<int[]> buf(new int[1024]);      // 数组特化，delete[] 而非 delete
```

> `enable_shared_from_this` 的场景同样真实：在成员函数内部需要「把自己包装成 `shared_ptr` 传给异步回调」时，用 `shared_from_this()`，绝不能用 `this` 去 new 一个新控制块。

## 版本演进

| 版本 | 变化 |
| --- | --- |
| C++98 | `auto_ptr`（拷贝即转移，语义反直觉，已在 C++17 移除）；`shared_ptr` 来自 Boost |
| C++11 | `unique_ptr`/`shared_ptr`/`weak_ptr` 入标准库；`enable_shared_from_this` 就位 |
| C++14 | `make_unique`（避免异常安全的代码重复） |
| C++17 | `shared_ptr<T[]>` 数组特化、`std::allocate_shared` 更能把控制块与对象放在一起 |
| C++20 | `atomic::wait/notify` 让引用计数在无锁路径上更可控；`std::jthread` 与 `shared_ptr` 的取消传播配合 |
| C++23/26 | `std::move_only_function`（可移动、不可拷贝的可调用包装）补上了「只移动回调」的缺口；`std::atomic<T>::wait/notify`（P1135）让共享指针的等待开销更低 |

## 近年研究与工业界开源实践（2015–2026）

- **基准结论一致**：`shared_ptr` 的构造/拷贝都带原子增减，实测通常是 `unique_ptr` 的十几倍开销；`make_shared` 通过「控制块 + 对象同分配」省掉一次分配，但仍多一次间接寻址。
- **`unique_ptr` 已是接口惯例**：现代 C++ 库的工厂函数返回 `unique_ptr<T>`，观察者参数用 `T*` 或 `gsl::not_null<T*>`，所有权在签名上可读。
- **反共享的趋势**：`folly`、`abseil` 等库更倾向于 `unique_ptr` + 显式传递，或直接用值语义；`std::shared_ptr` 多见于插件、异步回调、跨线程共享缓存。
- **内存回收研究**：`shared_ptr` 的循环引用泄漏是内存泄漏的主要来源之一；工业界开始改用区域分配（arena）或所有权图（ownership graph）显式建模，参考 Rust 的所有权检查思路。
- 🔧 **`shared_ptr` 与异步取消**：C++20 的 `jthread`/`stop_token` 让回调取消变常规，但「回调持有 `shared_ptr`」仍是最常见的生命周期 bug；建议对异步回调统一约定「捕获 `weak_ptr`，在 `lock()` 成功后使用」。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「`shared_ptr` 就是 `unique_ptr` 的升级版」 | 二者表达的所有权语义不同；把 `shared_ptr` 当万能指针会让生命周期依赖变得不可读 |
| 2 | 「构造函数里 `make_shared` 之外的地方也要自己管计数」 | 手写计数时最容易漏掉**弱引用计数**，导致对象已销毁而控制块未释放 |
| 3 | 「两个 `shared_ptr` 指向同一对象只是效率低一点」 | 若分别由裸指针构造，会发生**双重释放**；用 `enable_shared_from_this` 或 `make_shared` |
| 4 | 「`unique_ptr` 传参就用 `unique_ptr<T>` 声明」 | 函数参数用 `T*`/`T&` 表达借用，用 `unique_ptr` 表达「交出所有权」；重载集里两者都提供才能让调用方自由选择 |
| 5 | 「`get()` 之后对象一定还在」 | 只要存在 `unique_ptr` 被重置的可能，`get()` 返回的裸指针就随时可能悬空 |
| 6 | 🔧 本讲对 `shared_ptr` 的**原子计数开销**着墨不足 | 多核并发下，共享计数是缓存行争用热点；高频路径应改为独占所有权或显式生命周期管理 |
| 7 | 🔧 本讲的「删除器」只覆盖了 `delete` | 2026 年的常见删除器还有：`fclose`、`DestroyWindow`、`cudaFree`、以及 C++23 的 `std::move_only_function` 承载的可移动回调 |
| 8 | 🔧 缺少「异步回调与生命周期」的现代焦点 | 建议补一条实践规则：跨线程回调捕获 `weak_ptr`，`lock()` 成功后才使用；并在 CI 中开 `clang-tidy` 的 lifetime 检查 |
