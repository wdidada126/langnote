# 讲 04 + 讲 05｜容器汇编（上/下）：从 `vector` 到「需要函数对象的容器」

> **一句话**：容器不是八股清单，而是**四种访问模式（顺序、链表、树、哈希）** 各自的最优解；选错容器的代价，通常比写错算法更大。

## 核心精讲

> 以下均为**教学示意，不参与构建**。

### 1. 容器的四类访问模式

| 类别 | 代表 | 遍历局部性 | 随机访问 | 中间插入 |
| --- | --- | --- | --- | --- |
| 顺序 | `vector`、`deque`、`string` | 极佳 | `O(1)` | `vector` 差，`deque` 尚可 |
| 链表 | `list`、`forward_list` | 差 | 不支持 | `O(1)`（已知位置） |
| 树 | `set`、`map` | 中 | 不支持 | `O(log n)` |
| 哈希 | `unordered_set`、`unordered_map` | 差 | 平均 `O(1)` | 平均 `O(1)` |

**决策顺序**：需要随机访问 → `vector`；只在两端增删 → `deque`；需要键查找 → 先问「`vector` + 二分」是否够用，不够再 `unordered_map`/`map`；需要稳定引用且频繁中间插入 → 链表。

### 2. `vector` 的三个关键行为

```cpp
// 教学示意：vector 的用法与代价（不参与构建）
std::vector<int> v;
v.reserve(1024);            // 一次预测：避免 log n 次扩容与重复搬移
for (int i = 0; i < 1024; ++i) v.push_back(i);

v.push_back(0);             // 若容量已满，可能整体搬家（旧内存不保证保留）
int* p = v.data();          // 扩容后 p 失效——这是最经典的悬垂来源

v.shrink_to_fit();          // C++11，请求而非保证
v.clear();                  // size 归零，capacity 不变：内存没还回去
```

要点：

- **`capacity` 只增不减**（`clear` 与 `shrink_to_fit` 都不保证归还内存）；
- **插入/删除中间元素会搬移后续元素**，代价与位置到尾部的距离成正比；
- **`vector<bool>` 是特例**：它不存放 `bool`，而是位打包，返回代理引用，`data()` 也不存在。

```cpp
// 教学示意：vector<bool> 的危险之处（不参与构建）
std::vector<bool> flags(10);
auto ref = flags[3];        // ref 是代理对象，不是 bool&；flags 重分配后 ref 悬空
bool b = flags[3];          // 正确的用法：立刻取值
```

### 3. `string` / `string_view`：所有权的分界线

```cpp
// 教学示意：string 与 string_view（不参与构建）
std::string s = "hello modern C++";
std::string_view sv = s;                  // 不拥有内存，必须保证 s 活得比 sv 久
// std::string_view sv2 = "abc";          // 指向字面量：可以，但生命周期是静态的
// find 的结果同样是 string_view，务必看清它指向谁
```

规则：**函数签名里用 `std::string_view` 表示「只读、不拥有」，用 `const std::string&` 表示「拥有或需要共享」。** `string_view` 不保证以 NUL 结尾，若需要传给 C 接口要用 `std::string(sv).c_str()` 或先确保原串有终止符。

### 4. 需要函数对象的容器：`map` 与 `unordered_map`

```cpp
// 教学示意：带自定义比较/哈希的关联容器（不参与构建）
struct CaseInsensitiveLess {
    bool operator()(const std::string& a, const std::string& b) const {  // 必须 const
        return std::lexicographical_compare(
            a.begin(), a.end(), b.begin(), b.end(),
            [](unsigned char x, unsigned char y) { return std::tolower(x) < std::tolower(y); });
    }
};

std::map<std::string, int, CaseInsensitiveLess> m;      // 比较器是类型的一部分
m["Apple"] = 1;                                          // operator[] 会插入默认值

if (auto it = m.find("apple"); it != m.end()) {          // 查找更明确，不会插入
    use(it->second);
}
```

三条关键认知：

1. **比较器/哈希器是模板参数**，不是运行时策略；不同比较器就是不同类型，不能混用。
2. **`operator[]` 会插入空值**，语义上「取」用 `find`，「取或默认构造」才用 `[]`。
3. **`unordered_map` 的迭代器/引用在「重哈希」后失效**，且最坏情况退化为 `O(n)`——哈希拒绝服务攻击是真实威胁，可用带随机种子的哈希或有序容器兜底。

### 5. `deque` 与「扁平化」现代企业

```cpp
// 教学示意：map 与 vector 的组合（不参与构建）
std::vector<std::pair<int, std::string>> flat;          // 缓存友好
std::sort(flat.begin(), flat.end(),
          [](const auto& a, const auto& b) { return a.first < b.first; });
auto it = std::lower_bound(flat.begin(), flat.end(), 42,
                           [](const auto& kv, int key) { return kv.first < key; });
```

「**排序 `vector` + 二分查找**」在实测中常常快过 `std::map`：缓存命中带来的收益，往往超过树结构的 asymptotics 优势。

### 6. `noexcept` 与容器扩容的关系

```cpp
// 教学示意：为什么移动构造要 noexcept（不参与构建）
class Point { public: Point(Point&&) {} };              // 可能抛：vector 扩容时改为逐元素拷贝
class Safe  { public: Safe(Safe&&) noexcept {} };       // 不抛：vector 扩容时改为移动
```

## 版本演进

| 版本 | 变化 |
| --- | --- |
| C++98 | 容器一族定型；`vector` 的扩容与 `reserve` 已存在 |
| C++11 | 移动语义进入容器；`emplace_back` 就地构造；`unordered_*` 多参数构造 |
| C++14 | 整型模板参数、`erase`-返回新长度 |
| C++17 | `insert_or_assign`、`try_emplace`（避免构造临时 `pair`）、`std::string_view` |
| C++20 | `std::span`（非 owning 数组视图，取代大量 `T*`/`size` 对）、`std::ranges` 算法、容器普遍获得 `contains` |
| C++23 | `std::flat_map`（扁平哈希映射提案已进标准）、多维下标 `operator[](i, j)`（P2128） |
| C++26 | Ranges 与执行策略的进一步整合；编译期容器的完整性提升 |

## 近年研究与工业界开源实践（2015–2026）

- **扁平化（flattening）成为主流优化**：`std::flat_map`/`std::flat_set`（C++23）把树结构换成「排序数组 + 索引」，实测在查找密集场景显著快于 `unordered_map`。
- **缓存线对齐的自定义容器**：`folly::small_vector`、`eastl`、`boost::container::flat_map` 都提供「小对象内联 + 大对象堆」的混合布局。
- **分配器策略进入类型系统**：`std::pmr` 让「用哪个内存资源」成为模板参数（`polymorphic_allocator`），容器不再硬编码全局 `new`。
- **哈希 DoS 防线**：工业服务普遍对不可信输入的 key 使用随机化哈希或改用有序结构。
- 🔧 **Ranges 改变了容器的使用方式**：容器不再需要 `.begin()/.end()` 书写，`views::filter/transform` 让「不拷贝的惰性管道」成为常规写法（见 `16-未来篇Concepts-Ranges-协程.md`）。
- 🔧 **`std::span` 取代了大量裸指针 + 长度对**：2026 年新代码的默认「数组视图」类型。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「`vector` 满了就重建，所以 `reserve` 无所谓」 | 每次扩容都要搬移并可能触发旧的 `noexcept` 判断差异；能预估就 `reserve` |
| 2 | 「`data()` 得到的指针永远有效」 | 插入、删除、扩容都会让它失效 |
| 3 | 「`vector<bool>` 是 `vector<char>` 的特化，行为一致」 | 它以位存储、返回代理引用、无 `data()`；需要 `bool` 数组请用 `vector<uint8_t>` 或 `bitset` |
| 4 | 「`unordered_map` 永远 `O(1)`」 | 哈希碰撞会让最坏情况退化为链表；且迭代器在重哈希后失效 |
| 5 | 「`clear()` 会释放内存」 | 只改 `size`；需要归还内存可用 `swap` 一个空容器或 `shrink_to_fit` |
| 6 | 🔧 本讲把「关联容器」当作主要选择 | 2026 年的常见答案反而是**排序 `vector` + 二分** 或 `std::flat_map`（C++23）；缓存命中率的收益往往超过 asymptotics |
| 7 | 🔧 未强调 `std::pmr` | C++17 的多态分配器让「同一份容器代码、不同内存来源」成为可能，嵌入式与高性能服务都在用 |
| 8 | 🔧 `string_view` 只作为「新东西」一笔带过 | 它是**所有权边界**的标记：`string_view` 参数必须保证源对象生命周期更长，否则是定时炸弹 |
| 9 | 🔧 缺少 Ranges 视角 | 容器不只是「存数据的」，它现在还是 Ranges 管道的一端（`views::filter`、`ranges::sort` 等） |
