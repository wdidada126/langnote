# 讲 25 + 讲 26｜单元测试：两个库；日志：Easylogging++ 与 spdlog

> **一句话**：测试给你「敢改」的底气，日志给你「线上发生了什么」的证据——前者决定你能不能迭代，后者决定你能不能定位；而这两件事的成败，几乎都取决于**是否 Automate**。

## 核心精讲

> 以下均为**教学示意，不参与构建**。

### 1. 测试的四条实用原则

1. **一个测试只验证一件事**，名字就写清「在什么条件下应该怎样」；
2. **测试必须可重复**：不能依赖全局状态、时间、网络或上次留下的文件；
3. **失败要能定位**：断言消息里带关键输入，而不是「assertion failed」；
4. **跑得快的测试才有人跑**：把慢的集成测试隔离开，别让整个套件拖到十分钟。

```cpp
// 教学示意：googletest 的基本形态（不参与构建）
TEST(ParserTest, RejectsMissingEquals) {
    auto result = parse("key");                        // 返回 expected 时也可直接比较
    EXPECT_FALSE(result.has_value());                  // 或者 EXPECT_EQ(parse("key"), ...)
}

class ConfigTest : public ::testing::Test {           // Fixture：每个用例前后执行
protected:
    std::filesystem::path tmp_;
    void SetUp() override { tmp_ = std::filesystem::temp_directory_path() / "cfg_test"; }
    void TearDown() override { std::filesystem::remove_all(tmp_); }
};

TEST_F(ConfigTest, RoundTripPreservesFlags) { /* ... */ }

// 参数化：同一逻辑覆盖多个输入
class ParseTest : public ::testing::TestWithParam<std::string> {};
INSTANTIATE_TEST_SUITE_P(All, ParseTest, ::testing::Values("a=1", "b=2"));
```

```cpp
// 教学示意：Catch2 的写法（不参与构建）
#include <catch2/catch_test_macros.hpp>
TEST_CASE("parser rejects malformed input", "[parser]") {
    REQUIRE_FALSE(parse("key").has_value());
    REQUIRE(parse("key=value").value() == "value");
    CHECK_THROWS_AS(risky_call(), std::runtime_error);   // 明确期望的异常类型
}
```

| 维度 | googletest | Catch2 |
| --- | --- | --- |
| 分发 | 需要编译/子模块 | 单头文件（v3 有 `amalgamate` 脚本） |
| 断言宏 | `EXPECT_*` / `ASSERT_*` | `REQUIRE` / `CHECK` |
| 参数化 | `TestWithParam` + `INSTANTIATE` | `TEST_CASE_CASE` + `DATA_SET`/generators |
| 编译速度 | 较慢（测试多时） | 相对更好 |
| 附加能力 | 死亡测试、`gtest_main` | 属性测试（v3）、BDD 风格 |

### 2. 关于 Mock 的一条经验

```cpp
// 教学示意：与其 mock 一个网络层，不如把规则抽成纯函数（不参与构建）
// 差：mock HttpTransport 的 37 个方法
// 好：把「请求 → 决策」变成纯函数，测试它；网络只在集成测试里出现一次
Decision decide(const Request& req) { /* 纯逻辑，可穷尽测试 */ }
```

> 经验法则：**mock 的是「边界」，不是「逻辑」**。用 mock 验证「代码按预期调用了依赖」通常价值有限；真正该测的是「在给定输入输出下，结果是否正确」。

### 3. 日志：级别、内容与成本

```cpp
// 教学示意：spdlog 的用法（不参与构建）
#include <spdlog/spdlog.h>
#include "spdlog/sinks/stdout_color_sinks.h"

auto console = spdlog::stdout_color_mt("console");
console->set_level(spdlog::level::info);
console->info("request handled: uri={} status={} us={}", req.uri(), status, elapsed_us);

// 编译期把不输出的级别直接删掉，零成本
template <typename T> void debug_only(const T&) {
    spdlog::debug("detail={}", fmt::detail_never_used());   // 级别关闭时不构造参数
}
```

| 级别 | 用途 | 线上建议 |
| --- | --- | --- |
| `trace`/`debug` | 开发期细节、参数快照 | 生产默认关闭 |
| `info` | 关键事件（启动、配置、请求摘要） | 保留，控制量 |
| `warn` | 可恢复的异常路径 | 保留 |
| `error`/`critical` | 单次失败、需要人工介入 | 必须聚合与告警 |

日志的四条工程纪律：

1. **不要把日志写成「给现在的自己看」**，写清对象、动作、结果、耗时与上下文 ID；
2. **高频路径必须异步**，否则 I/O 会拖垮业务线程；异步队列要有溢出策略（丢弃而非阻塞）；
3. **敏感信息（口令、Token、身份证）绝不能进日志**——这是线上事故的高频来源；
4. **级别可以在运行时调整**，这样线上排查不必重启服务。

```cpp
// 教学示意：同步日志为什么可能是性能问题（不参与构建）
// 同步日志：业务线程 → write() 系统调用 → 磁盘/终端延迟都在调用栈里
// 异步日志：业务线程 → 入队 → 专用线程批量写；代价是丢日志的可能与额外延迟
```

### 4. Easylogging++ 的定位

Easylogging++ 是「单头文件、零依赖、宏驱动」的老牌日志库（本次实测 **3.9k★**），配置方式是用宏注册 logger 与格式化规则。它的优点是可移植到任何老工具链，代价是：

- 大量使用宏，无法被模板与异常正确处理，也无法被调试器单步；
- 内部全局状态较多，单元测试里难以隔离；
- 维护节奏相比 spdlog 明显放缓。

> **选型建议**：新项目用 spdlog（或 `fmt` 自己做一层薄封装）；需要「塞进一个没有包管理器的老项目」时再考虑 Easylogging++。

## 版本演进

| 版本 | 变化 |
| --- | --- |
| 2000s | 日志以 `printf`/` syslog`/自研宏为主 |
| C++11 | 日志库普遍转向「格式化 + 异步队列 + 编译期优化」的架构 |
| C++17 | `std::filesystem`（日志落盘与轮转）、`std::optional`/`variant`（结构化日志字段） |
| C++20 | `std::source_location` 让「打日志的位置」自动可用 |
| **C++23** | **`std::format`/`std::print`（P2093）** 成为日志格式化的标准底座 |
| 2026 | 结构化/机器可解析日志（JSON）成为主流；日志与可观测性（metrics/tracing）融合 |

## 近年研究与工业界开源实践（2015–2026）

- **测试框架的编译时间成为新的瓶颈**：大型 C++ 项目里测试代码的编译量常常超过业务代码，出现了「按目标分批编译」「用更小的测试框架」等实践。
- **属性测试进入 C++ 生态**：Catch2 v3 支持基于生成器的属性测试；Randall 的 *Property-Based Testing with Propeller* 一类思路开始影响 C++ 测试写法（本文不写具体框架编号）。
- **日志即可观测性**：OpenTelemetry 一类标准把 trace/span 引入 C++，日志不再是唯一线索；但「结构化 + 低开销」的需求没变。
- **日志安全合规**：脱敏与「默认不记录请求体」已成合规要求；很多团队把脱敏做进日志库的统一入口。
- 🔧 **`std::format`/`std::print`（P2093）让日志层的成本重新分布**：编译期格式字符串检查 + 类型安全，第三方格式化库的角色从「必需」变成「性能优化」。
- 🔧 **测试构建应默认开启 sanitizer 与 `_GLIBCXX_ASSERTIONS`**：在测试构建里做 ASan/UBSan/TSan 覆盖，是把「并发 bug 早发现」落到 CI 的最有效手段（与 `12-工具漫谈与构建依赖.md` 呼应）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「有测试就够了」 | 覆盖率不等于有效性；断言「没验证任何事」的测试会给人虚假信心 |
| 2 | 「`ASSERT` 与 `EXPECT` 只是严格程度不同」 | `ASSERT` 立即终止当前用例（对 fixture 清理不友好），`EXPECT` 继续跑完能一次看到多个问题 |
| 3 | 「mock 越全面越好」 | mock 会复制依赖的行为假设；优先把逻辑抽成纯函数直接测 |
| 4 | 「日志多＝排查快」 | 无结构的海量日志只会淹没真相；控制级别、结构化字段、脱敏三件事必须一起做 |
| 5 | 「同步日志最简单，先用着」 | 高频路径上同步日志会直接吃掉吞吐；至少提供异步模式用于生产 |
| 6 | 🔧 本讲只比较了两个日志库的 API | 2026 年的选型应把「异步队列溢出策略」「运行期级别调整」「结构化输出（JSON）」「脱敏钩子」列为评估项 |
| 7 | 🔧 未提 `std::format` 对日志层的改变 | 类型安全 + 编译期检查能消掉一大类格式化错误；`std::print`（C++23）进一步降低第三方依赖 |
| 8 | 🔧 缺少「测试在 CI 中的位置」 | 建议把测试流水线分成「快速单测（每次提交）→ sanitizer 套件（合并前）→ 长跑压测/并发测试（夜间）」三档 |
