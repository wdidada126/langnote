# 讲 06 + 讲 22｜异常：用还是不用；以及 optional、variant、expected 与 herbception

> **一句话**：把错误从「中断控制流」改成「返回值」并不新鲜——C++ 在异常、状态码、以及二者混合的 `expected` 之间来回摇摆了三十年；**2026 年的答案不是二选一，而是按「错误是否可预期」分层**。

## 核心精讲

> 以下均为**教学示意，不参与构建**。

### 1. 异常的最小全景

```cpp
// 教学示意：异常的基本流程（不参与构建）
void may_throw(bool fail) {
    if (fail) throw std::runtime_error("disk on fire");   // 抛出：立即展开栈
}
void caller() {
    std::ifstream f("config.ini");                          // RAII：无论是否展开都会关闭
    may_throw(true);                                        // 中间若没有 try，析构照常发生
}
try {
    caller();
} catch (const std::exception& e) {                         // 按「最匹配类型」捕获
    log(e.what());                                          // 顶层兜底
} catch (...) {                                             // 兜底所有其他类型
    log("unknown");
}
```

三个必须知道的行为：

1. **栈展开时，所有已完成构造的局部对象都会被析构**——这正是 RAII 的价值所在；
2. **析构函数若抛异常，进程直接 `std::terminate`**；
3. **catch 的匹配是「最佳匹配」而非第一个匹配的基类**，因此精确类型应放在前面。

### 2. `noexcept`：契约、优化与「不逃出」的声明

```cpp
// 教学示意：noexcept 的三个用途（不参与构建）
void fast_path() noexcept;                    // 1) 契约：保证不抛，可放心优化
void legacy() throw();                        // 2) 动态异常规范已在新标准中被移除

template <typename T>
void sink(std::vector<T>& v) {
    v.push_back(T{});                         // 3) 若 push_back 抛，移动构造必须 noexcept
}
```

- `noexcept` 的语义比 `throw()` 更强（不需要运行时检查），且是**类型的一部分**（`constexpr` 可查询）。
- 析构函数、移动构造、`swap` 应默认 `noexcept`。
- `std::vector` 在扩容时会用 `noexcept` 判断该移动还是拷贝元素；不标 `noexcept` 会退化成逐元素复制。

### 3. 不用异常：`StatusOr` 的路线

```cpp
// 教学示意：错误作为返回值（不参与构建）
class Status {
public:
    static Status OK() { return Status{}; }
    static Status Invalid(const std::string& msg) { return Status{1, msg}; }
    bool ok() const { return code_ == 0; }
    const std::string& message() const { return msg_; }
private:
    int code_ = 0; std::string msg_;
};
template <typename T>
class StatusOr {
public:
    StatusOr(Status s) : status_(std::move(s)) {}                  // 错误分支
    StatusOr(T v) : value_(std::move(v)) {}                        // 成功分支
    bool ok() const { return status_.ok(); }
    const Status& status() const { return status_; }
    const T& value() const { return *value_; }
private:
    Status status_; std::optional<T> value_;    // 与 std::expected<T,Status> 结构几乎一致
};
```

> Google 及其 Abseil 生态的选择是**不用异常**：因为异常使函数变成「控制流不可静态推断」，不利于大规模code review 与二进制体积；代价是每个调用点都要写检查。`absl::StatusOr<T>` 正是这套思路的结晶，也是 `std::expected` 的直接灵感来源。

### 4. `optional` / `variant` / `expected`

```cpp
// 教学示意：三种「值类型」的用法（不参与构建）
std::optional<int> find_index(const std::string& s) {
    auto pos = s.find("x");
    if (pos == std::string::npos) return std::nullopt;     // 没有信息，只是「没有」
    return static_cast<int>(pos);
}

std::variant<int, double, std::string> read_any();          // 三选一的值
auto v = read_any();
std::visit([](const auto& x) { using T = std::decay_t<decltype(x)>;
                               log<T>(x); }, v);            // 穷尽分支由编译器检查

std::expected<int, ParseError> parse(const std::string& s);// C++23：带错误的值
auto r = parse("42");
if (!r) return report(std::move(r.error()));                // 用 error 而非异常
use(*std::move(r));                                          // 需要移动时用 move
```

| 类型 | 承载的信息 | 典型场景 | 代价 |
| --- | --- | --- | --- |
| `T` | 只有成功 | 错误用异常或日志 | 热路径无异常开销 |
| `std::optional<T>` | 成功 / 无值 | 查找失败、可能为空 | 布局为 `T` 或 `bool+T`，无额外分配 |
| `std::variant<T...>` | 成功 / 多种形态 | JSON、命令消息、配置 | 布局为 `max(T...)+判别式` |
| `std::expected<T,E>` | 成功 / 错误对象 | 可预期失败 | 类似 `variant`，但 `visit` 友好 |
| `T` + 异常 | 成功 / 任意异常 | 不可预期、跨库边界 | 需要展开表；栈展开成本不低 |

### 5. 什么时候用哪个：一条判断链

1. **错误可预期**（输入解析、查表、文件不存在、网络超时）→ `optional`/`expected`，或状态码；
2. **错误不可预期**（内存不足、底层库内部失败）→ 异常；
3. **跨 C 边界或跨线程任务边界** → 返回值（异常穿过线程边界会 `std::terminate`，所以 `std::async` 把异常存进 `future`）；
4. **库对外公开 API**：如果库不用异常，就在文档里明确「只通过返回值报告错误」，不要让异常悄悄逃出 ABI。

```cpp
// 教学示意：future 承接跨线程异常（不参与构建）
std::future<int> f = std::async(std::launch::async, []() -> int {
    throw std::runtime_error("worker failed");
    return 0;
});
try { f.get(); } catch (const std::exception& e) { log(e.what()); }   // 异常在 get() 处重现
```

### 6. herbception：课程点出的中间态

讲 22 把「既想保留返回值的轻量、又想拥有异常的传播便利」这一撮做法称为 **herbception**（课程自造词，具体定义以课程原文为准）。它指向一个真实的技术空档：**纯错误码让调用链上几十处判断，纯异常又太重**；`expected` 加上「早期返回式传播」(`if (!r) return ...;`) 正好是这个空档的现代答案。

## 版本演进

| 版本 | 变化 |
| --- | --- |
| C++98 | 异常体系定型；`std::exception`、`what()`；`throw(...)` 规范可用 |
| C++11 | `noexcept` 取代动态异常规范；`std::future::get()` 重抛异常；移动语义改变异常安全写法 |
| C++14 | `std::exception_ptr`（跨线程传递异常）、`nested_exception` |
| C++17 | `std::variant`、`std::optional`、`std::string_view`；`noexcept` 成为类型查询目标 |
| C++20 | `consteval`/`constexpr` 与异常的关系收紧；`std::source_location` 改善日志 |
| **C++23** | **`std::expected` 正式入标准**；`std::print`/`std::format` 让「错误信息的格式化」不再需要第三方库 |
| C++26 | 反射与更好的 `constexpr` 错误处理；异常规范与编译期诊断进一步融合 |

## 近年研究与工业界开源实践（2015–2026）

- **`expected` 进入标准后成为新默认**：2022 年 `std::expected` 进 C++23，此前工业界用 `absl::StatusOr`、`folly::Expected`、`tl::expected` 各自补位。
- **Google 的取舍仍然是「不用异常」**：`abseil/abseil-cpp` 全面使用 `absl::Status/StatusOr`，并在文档中明确不建议在 Abseil 的公共 API 中抛异常。
- **异常在库边界消失**：常见模式是「底层库内部用异常、对外导出 C ABI 时转成错误码」；反之，C++ 项目若在热路径禁用异常，需要配套禁用 `std::vector` 的部分操作语义。
- **错误信息的结构化**：`std::format`/`std::print`（P2093，C++23）让「把错误对象格式化成日志」变成 `std::format("{}", err)` 一行；`std::source_location` 让「出错位置」不再手工传入。
- 🔧 **`if consteval`（C++23）改变了写法的形态**：编译期与运行期分支现在可以写在一处，`constexpr` 函数里的错误处理自然分叉，不必再用 `if (std::is_constant_evaluated())`。
- 🔧 **`std::expected` 与「panic 式」风格的冲突**：Rust 的 `?` 与 Go 的多返回值让新语言的错误传播更短；C++ 的对应做法是「`expected` + 早期返回 + 可选的心照不宣的 `std::unreachable()`」。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「我们用异常，所以资源安全」 | 只有在 RAII 到位时才成立；裸 `new` + 异常 = 必泄漏。异常安全的前提是 `01/02` 章的对象模型 |
| 2 | 「异常是零成本的」 | 只有「没有抛出」的**路径**接近零成本，但展开表与栈展开仍有成本；热路径应标 `noexcept` |
| 3 | 「`throw()` 规范能表达不抛」 | C++20 起动态异常规范被移除，用 `noexcept`；`noexcept` 还是类型的一部分 |
| 4 | 「异常穿过 `std::thread` 的入口函数会被调用方捕获」 | 主线程捕获不到别的线程的异常；要用 `future` 或错误码 |
| 5 | 「`optional` 就是 `T` 加个 bool」 | 对不可平凡构造的 `T` 会构造两次；用 `emplace` 就地构造 |
| 6 | 🔧 本讲把「用异常 vs 不用异常」当成风格之争 | 2026 年的可操作结论：把错误分成**可预期**（`expected`/状态码）与**不可预期**（异常），并写进代码规约 |
| 7 | 🔧 本讲缺少 `std::expected` 的正式落地说明 | `std::expected<T,E>` 已在 C++23 可用；应补：`if (!r) return ...` 的传播模式、与 `visit` 的配合、以及「错误类型必须可比较/可打印」的隐含要求 |
| 8 | 🔧 未提 `std::unreachable()` 与 `assume` | C++23 的 `std::unreachable()` 取代了大量 `if (false)` 与注释式占位，让「这里不可能发生」成为可优化的事实 |
| 9 | 🔧 缺少「异常与 ABI/二进制体积」的现实代价 | 跨 DLL/SO 边界抛出异常在多数平台不被鼓励；导出接口应转为错误码 |
