## 6.3 🔧 E5 实跑：概念卡式审计——血缘登记的覆盖率与路由死角（DuckDB 1.5.5，非本书引擎行为）

母体 G3 做的是「给定变更点，递归查可达下游」（9 边→6 下游，✅ 在盘）；本册错位为**管理会计面**：不查可达性，查登记簿本身可信吗——覆盖率、无主边、盲区清单三笔账。22 个节点、17 条边、11 个作业、部分负责人空缺（种子件，含故意埋的孤儿表 raw.i/tmp.x/bi.z）。

```sql
WITH deg AS (
  SELECT n.node, n.owner,
         count(DISTINCT e1.src) AS fan_in,
         count(DISTINCT e2.dst) AS fan_out
  FROM nodes n
  LEFT JOIN edges_tbl e1 ON e1.dst = n.node
  LEFT JOIN edges_tbl e2 ON e2.src = n.node
  GROUP BY 1,2)
SELECT count(*) AS nodes,
  count(*) FILTER (WHERE fan_in+fan_out=0) AS no_edges,
  round(100.0*count(*) FILTER (WHERE fan_in+fan_out>0)/count(*),1) AS coverage_pct,
  count(*) FILTER (WHERE owner IS NULL) AS no_owner,
  count(*) FILTER (WHERE owner IS NULL AND fan_in+fan_out>0) AS no_owner_wired
FROM deg;
```

**实跑结果**：22 节点 / **覆盖率 86.4%**（3 个零边孤儿）/ 无主资产 8 个 / **「有边无主」6 个** / 最大扇出 2（raw.a 与 stg.e 并列）。

- 三笔账的读法（⚠️ 判读）：① 86.4% 好看吗——**孤儿恰恰是 tmp/raw 旁路**（tmp.x 是「临时表住进生产」的经典病灶，零边=没有作业声明它在被用）；② 「有边无主」×6 比无边更危险：**数据在流动、告警无处可投**——05 章否决清单第 2 条的实数化；③ 扇出 2 说明登记簿规模小，覆盖率指标在 20 节点与 2000 节点下意义完全不同——**审计要连登记簿大小一起报**（⚠️ 此条是本册给 #226 三采集法表补的第四句：任何采集法的覆盖率都要除以资产总数而非边数）。
- 与治理线的接榫：负责人登记簿归治理、信号路由归观测、双边一致性归 E5 这种例行审计（制度面实链 [../Understanding_Data_Governance/00-总览与阅读地图.md](../Understanding_Data_Governance/00-总览与阅读地图.md) ✅；规程册线 [../Data_Governance_Elsevier/00-总览与阅读地图.md](../Data_Governance_Elsevier/00-总览与阅读地图.md) ✅）。

## 6.9 🔧 三角的 SQLite / DuckDB 类比（⚠️ 非本书引擎行为）

- 「血缘覆盖率审计」本质上是嵌入式分析库最擅长的查询形态：节点表 JOIN 边表、按负责人 GROUP BY、COUNT DISTINCT 算扇入扇出——E5 那 48 行 SQL 在 DuckDB 内存模式下半秒跑完 22 节点全图审计，说明观测审计的计算下限比平台厂商暗示的低得多。SQLite 同样能跑这组查询（仅窗口函数语法略有差异：`FILTER` 需改写为 `SUM(CASE WHEN ... END)`），进一步证实该审计逻辑与引擎无关、只与登记簿的表结构有关（⚠️ 非本书引擎行为；SQLite 3.39+ 支持 `quantile_cont` 需加载 `math` 扩展）。
- 类比延伸到五平面坐标系（6.4）：DuckDB 的 catalog 层级（memory → main → staging → temp）在结构上同构于制度/平台/运行/修复四平面——观测信号需要跨 catalog 路由，正如 E5 的 3 个孤儿恰恰落在 `raw.i` / `tmp.x` 这类「临时表住进生产」的 catalog 灰色地带。对策即 6.3 末句：审计连分母一起报，分母按 catalog 分层而非合并（⚠️ 教学类比，非平台对标）。
