# 第 18 章 从猫爷借钱说起——事务简介（事务的原子性、持久性、隔离性、一致性）

> 原书说明：标题为「从猫爷借钱说起——事务简介」，用「借猫」的故事讲清事务的动机。本文件保留这条主线，并按「原子性 / 持久性 / 隔离性 / 一致性」四条线展开，补齐 2020 年之后必须补的 **WAL、组提交、重做/回滚、自动提交与隐式事务** 等现代展开。

## 本章地图

> 一句话：**事务是「要么全发生、要么全不发生、做完就永久生效、别人看不见一半」的四条承诺；InnoDB 用 redo 保证持久、undo 保证原子、锁 + MVCC 保证隔离、约束与业务语义保证一致。**

| 18.2 四个特性怎么落地 | A：undo + redo；D：redo + WAL；I：锁 + MVCC；C：约束 + 业务 | 每个 C 都不是数据库单独能解决的 |

## 核心精讲

> **教学示意，不参与构建。** 下文 SQL 片段仅用于说明事务语义，**未在本机编译、未连接任何 MySQL 实例执行**。

### 18.1 从「借猫」到「转账」

原书的猫爷故事本质是转账问题（教学示意，不参与构建）：

```text
张三给李四转 100 元：
  T1: 读张三余额 -100
  T2: 读李四余额 +100
  ...中间可能崩溃 / 可能被另一个事务打断...
  => 若只完成一半，世界就坏了
```

异常可以归为四类：

| 类别 | 具体表现 | 对应特性 |
| --- | --- | --- |
| 脏写 | 一个事务覆盖了另一个未提交事务的修改 | 原子性 / 隔离性 |
| 脏读 | 读到另一个未提交事务的修改 | 隔离性 |
| 不可重复读 | 同一事务两次读同一行结果不同（**被 update/delete**） | 隔离性 |
| 幻读 | 同一事务两次范围查询结果集不同（**被 insert**） | 隔离性 |

- 原书强调：**“原子性”是对业务动作的抽象，不是对单行 SQL 的抽象** —— 一条 `UPDATE` 本身是原子的，但「转钱 + 记账」不是。

### 18.2 四个特性分别由什么实现

| 特性 | InnoDB 的实现手段 | 备注 |
| --- | --- | --- |
| **A 原子性** | **undo log**（逻辑撤销）+ 事务回滚 | 崩溃时的「半完成事务」靠 redo 里的 prepare 标记 + binlog 补齐 |
| **C 一致性** | 主键/唯一/外键/`CHECK`（8.0.16+ 真正支持 `CHECK`）**+ 应用层业务不变式** | 数据库只能保证「不变式不被破坏」，**不能保证不变式本身正确** |
| **I 隔离性** | **锁（当前读）+ MVCC（快照读）** | 详见 `21-事务隔离级别与MVCC.md` 与 `22-锁.md` |
| **D 持久性** | **redo log（WAL）+ checkpoint + 双写** | 详见 `19-redo日志.md` |
- 🔧 一个常被忽略的点：**持久性和原子性是「一次 fsync 的代价」换来的**，这也是为什么「关 binlog + `innodb_flush_log_at_trx_commit=2`」能显著提速，但会换掉持久性承诺。

### 18.3 事务的生命周期与常见陷阱

- **自动提交**：`autocommit=1`（默认）时，**每条语句都是一个事务** —— 于是 `DELETE FROM big_table` 在大表上会是一个超长事务：undo 巨大、purge 被拖住、主从延迟爆掉。
- **隐式提交**：`CREATE/ALTER/DROP`、`GRANT`、`TRUNCATE`、以及某些 `ALTER` 会**隐式提交当前事务**；本事务里后面的语句就不在当前事务里了。
- **`START TRANSACTION` / `BEGIN`**：显式开启事务；`COMMIT` / `ROLLBACK` 结束。
- **`SAVEPOINT` / `ROLLBACK TO SAVEPOINT`**：事务内部的部分回滚。
  - ⚠️ 注意：InnoDB 的 savepoint **不释放已获得的锁**，`ROLLBACK TO` 之后锁仍然持有。
- **只读优化**：`START TRANSACTION READ ONLY` 可让优化器省掉一些写路径判断。

### 18.4 原子性的代价：回滚段

- 一次 `UPDATE` 在 InnoDB 里实际做了（教学示意，不参与构建）：
  ```text
  1) 加行锁
  2) 在 undo 里记下「改之前的镜像」（用于回滚 + MVCC）
  3) 修改内存页（Buffer Pool）
  4) 写 redo（含该事务的 prepare 信息）
  ```
- 也就是说：**写放大是事务的内生成本**，「简单 UPDATE 一行」实际上写了 undo + redo（可能还有 binlog + doublewrite）。
- **长事务的代价清单**（原书第 20 章埋的伏笔，在这里总结）：
  - undo 空间被长期占用；
  - purge 线程不敢回收版本链 → **MVCC 版本链变长，一致性读变慢**；
  - 主从延迟增大（大事务在从库重放很慢）；
  - 崩溃恢复时间变长。
- 🔧 **大事务拆分**：批量 `DELETE/UPDATE` 应按主键分段（`LIMIT 1000` + 循环 + 每次提交），既降低 undo 压力，也让主从延迟可观察。

### 18.5 持久性的代价：有档位的 durable

- `innodb_flush_log_at_trx_commit`（详见 `X2-日志系统专题.md`）：
  - `1` = 提交即 fsync（不丢已提交）；
  - `2` = 写 OS cache，每秒 fsync（掉电丢 ≤1 秒）；
  - `0` = 每秒写盘。
- 而 `sync_binlog` 管的是 binlog 侧；二者组合决定「能恢复到哪一刻」。
- **持久性不等于「立刻可见」**：提交后数据还在 Buffer Pool 里、只在 redo 里，**磁盘上还不一定有这个页** —— 「持久化」指的是「崩溃后能重放出来」，不是「已经落盘」。

### 18.6 一致性的分层理解

- **数据库层保证**：主键唯一、非空、外键引用（InnoDB 支持，MyISAM 不支持）、`CHECK`（🔧 8.0.16 起真正强制）、`UNIQUE` 约束。
- **业务层保证**：「转出 = 转入」这类不变式，必须由**应用层**在同一个事务里完成。数据库对此的答案是：
  - 用**正确的隔离级别**（RR/Serializable）避免并发破坏；
  - 用**悲观锁**（`SELECT ... FOR UPDATE`）或乐观版本号控制；
  - 用**幂等设计**（唯一键 + 重试）避免重复扣款。

### 18.7 观测与追踪：谁的长事务没提交

```sql
-- 教学示意，不参与构建；具体列名随版本变化
SELECT trx_id, trx_state, trx_started, trx_rows_locked, trx_query
FROM information_schema.INNODB_TRX
ORDER BY trx_started ASC LIMIT 10;
```
- 配套：`performance_schema.data_locks`（8.0，取代 `innodb_locks`）、`performance_schema.data_lock_waits`。
- `SHOW ENGINE INNODB STATUS` 里的 `TRANSACTIONS` 段（8.0 起部分信息迁移到 `performance_schema`，原书时代的输出不一定完整）。

### 18.8 🔧 2026 视角：8.0 给事务带来的边界变化

- **原子 DDL（8.0）**：`ADD/DROP COLUMN` 等 DDL 可回滚（与 binlog 原子性配合），`information_schema.INNODB_TRX` 相关的 DDL 事务行为与 5.7 不同。
- **`CHECK` 约束真的被强制（8.0.16）**：5.7 会解析但不强制，`ALTER TABLE ... ADD CHECK` 在老版本是「纸面约束」——升级后可能有存量数据违反新约束而 DDL 失败。
- 🔧 **`innodb_max_trx_id` 与 trx_id 回绕陷阱**：事务 ID 用完了会切换 ID 分配范围，理论上可能让旧快照的可见性判断出现**异常**（表现为「已提交事务读不到」这类诡异现象）。这是**长事务 + 大量事务**环境中被反复讨论的坑，务必关注 `Innodb_trx_id` 附近的状态量与版本 release notes。
- 🔧 **DDL 不再隐式「不可回滚」**：8.0 的 instant/vs inplace/algo 选择会影响事务边界，复杂变更仍需先在从库验证。

### 18.9 🔧 事务设计的实操建议

| 场景 | 建议 |
| --- | --- |
| 批量 `DELETE` / `UPDATE` | 按主键分段，每段 500~2000 行 + 每次 COMMIT，避免超长事务 |
| 报表 / 导出 | 用可重复读快照，但要设 `max_execution_time` 或改走只读从库，别长时间占用最老 read view |
| 支付 / 扣库存 | 当前读（`FOR UPDATE` 或「条件 UPDATE + 影响行数校验」）+ 幂等键（唯一索引） |
| 导入数据 | 显式 `START TRANSACTION` 批量提交，或干脆 `LOAD DATA`；不要依赖 autocommit |
| 事务里做外部调用 | **不要**：外部 HTTP 失败无法回滚，会把事务拖到超时 |
| 连接池 | 连接归还前确保无未提交事务（`autocommit` 与连接池配置对齐），否则会留下长事务 |
- 「事务里不要调用外部接口」这条铁律的原理解释（教学示意，不参与构建）：
  ```text
  BEGIN;                       -- 事务开始，拿 lock、写 undo/redo
  调用支付网关（可能超时 30s）   -- 锁一直握着，别人一直等；undo 一直占着
  COMMIT;
  ```
  锁等待、undo 膨胀、主从延迟全部集中在这一行上。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：**确定性事务**（Calvin, SIGMOD 2012；Aria, VLDB 2020）把「事务语义」从并发控制里抽出来先定序；**分布式事务**在 Percolator（OSDI 2010）、Spanner（OSDI 2012）、CockroachDB 中被重新表述；**HTAP 下的事务与分析隔离**（TiDB 的 `Add Index` 与读隔离、Aurora 的 HTAP）；**Serverless/存算分离下的事务提交**（PolarDB Serverless 把 redo 上推到共享存储层）。
- **工业界开源**（star 数 2026-09-25 通过 `gh api` 实测）：
  - `mysql/mysql-server`（≈12.4k★）：事务实现 `storage/innobase/trx/trx0trx.cc`；undo `trx0undo.cc`；隔离级别与 MVCC `trx0roll.cc`、`read0read.cc`。
  - `pingcap/tidb`（≈40.6k★）：Percolator 模型的开源实现，是「单库事务语义扩展到分布式」的最佳参考实现。
  - `cockroachdb/cockroach`（≈32.5k★）：HLC + 串行化快照，事务语义跨节点的现代形态。
  - `postgres/postgres`（≈22.2k★）：多版本 + SSI，隔离级别语义与 MySQL 差异最大的对照系统。
  - `facebook/mysql-8.0`（≈115★）：生产环境对长事务、purge 滞后的大量经验补丁。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「事务 = 一条 SQL」 | 事务是**业务逻辑上的单元**；`autocommit=1` 下每条语句自成事务，批量操作会变成超长事务 |
| 2 | 「持久 = 已经写进磁盘」 | 持久是指「崩溃后可通过 redo 重放出来」；页可能还在 Buffer Pool 里 |
| 3 | 「一致性数据库可以保证」 | 数据库只保证**约束不被破坏**；「扣钱和加钱都成功」这类业务不变式由应用层负责 |
| 4 | 「`ROLLBACK TO SAVEPOINT` 会释放锁」 | InnoDB 的 savepoint 回滚**不释放已获得的锁** |
| 5 | 「DDL 都是安全的，反正能回滚」 | 5.7 的 `CHECK` 约束只是纸面；8.0 改成强制后，存量数据可能让 DDL 失败 |
| 6 | 🔧 **本书未覆盖** | 原书基于 5.7.22，**没有** 8.0 的原子 DDL、`CHECK` 真实生效、Undo Tablespaces 独立管理；「DDL 会隐式提交」在 8.0 的行为细节也需在升级手册里复核 |
| 7 | 🔧 **本书未覆盖** | **`innodb_max_trx_id` 与 trx_id 用尽/回绕**带来的可见性陷阱；以及 8.0 对 `read view` 分配方式的改动（见 `21-事务隔离级别与MVCC.md`） |
