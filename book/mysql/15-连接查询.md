# 第 11 章 两个表的亲密接触——连接的原理

> 原书说明：标题为「两个表的亲密接触——连接的原理」，基于 MySQL 5.7.22 撰写。本文件按其思路展开，并补齐 5.5/5.6/8.0 三代的连接算法改进，以及 2020 年之后必须补的 **`HASH JOIN`（8.0.18）、CTE 物化与派生表合并、并行查询 `n_jobs`**。

## 本章地图

> 一句话：**连接的核心问题是「谁做驱动表、怎么配对」**——小表驱动大表、被驱动表的连接列要有索引、把「随机配对」换成「有序或哈希配对」，这就是从 NLJ 到 BKA 再到 HJ 的全部演进逻辑。

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 11.1 连接的本质 | 笛卡尔积 + 筛选；驱动表 / 被驱动表 | 驱动表选错，代价相差几个数量级 |
| 11.2 嵌套循环连接（NLJ） | 外层逐行，内层全扫 | 简单但最贵，除非内层有索引 |
| 11.3 块嵌套循环（BNL / BKA） | 5.5/5.6 起把内层缓存起来批量配对 | 用内存换 IO |
| 11.4 索引嵌套循环（INLJ） | 5.6 起内层走索引查找 | 最佳路线之一：**零临时空间**（Inner 表带索引） |
| 11.5 🔧 哈希连接（HASH JOIN） | 8.0.18 起引入 | 无索引大数据量时的「兜底最优」路线 |
| 11.6 排序合并（SMJ）的位置 | MySQL **无原生 SMJ** | 想用得靠索引有序 + 外层 `sort` + MariaDB 实现 |
| 11.7 `ON` 与 `WHERE` 的区别 | 外连接下二者语义不同 | 写在 `ON` 里还是 `WHERE` 里会改变结果集 |
| 11.8 连接优化手段 | 提示、`STRAIGHT_JOIN`、`JOIN ... USING`、派生表 | 优化器的错误直觉需要「人工干预」逃生舱 |
| 11.9 🔧 2026 视角 | `HASH JOIN`、CTE 物化、`EXPLAIN ANALYZE`、并行连接 | 8.0 的连接优化器已经完全不是 5.7 的形状 |

## 核心精讲

> **教学示意，不参与构建。** 下文 SQL 片段仅用于说明连接算法语义，**未在本机编译、未连接任何 MySQL 实例执行**；`EXPLAIN` 中的 `rows` 是**估算值**，与真实行数可以有数量级差距。

### 11.1 连接的本质：笛卡尔积加过滤

```sql
-- 教学示意，不参与构建
SELECT * FROM t1, t2 WHERE t1.a = t2.b;
-- 等价于
SELECT * FROM (t1 的笛卡尔积 t2) 再挑出 t1.a = t2.b 的行
```

- **驱动表（outer / driving table）**：外层循环的表，决定扫描多少次。
- **被驱动表（inner / driven table）**：内层循环的表，决定每行要查找几次。
- 代价直觉（教学示意）：
  - 驱动表 10 行 × 被驱动表全表 100 万行 = **1000 万次配对**。
  - 反过来：被驱动表 10 行 × 驱动表 100 万行 = **1000 万次配对**。
  - 差别不在配对总数，而在**被驱动表能否走索引**：若被驱动表的连接列有索引，每行只需一次 B+ 树查找（≈3 次页访问），代价从「全表扫描 100 万次」降到「1000 万次索引查找」。
- 原书的核心结论：**小表驱动 + 被驱动表连接列建索引 = 连接查询的两个必要条件**。

### 11.2 嵌套循环连接（NLJ，Nested Loop Join）

```text
for each row r1 in t1 (驱动表):
    for each row r2 in t2 (被驱动表):
        if 连接条件满足: 输出 (r1, r2)
```
- 优点：不需要额外内存，实现极简。
- 缺点：最坏是两表笛卡尔积；**除非内层能在索引上定位**，否则就是全表扫 N×M 次。
- 原书把它描述成「一个 for 循环套另一个 for 循环」，这个直觉在 2026 年依然准确 —— 只是内层被换成了索引查找或哈希探测。

### 11.3 块嵌套循环 / 批量 key access（BNL / BKA）

- **BNL（Block Nested Loop）**，5.5 起：把**驱动表的行批量放进 `join_buffer`**（默认 256KB），逐块与被驱动表比对，减少「被驱动表重复扫描」的次数（被驱动表可能整表只扫一次）。
- **BKA / BKAUnion（Batch Key Access）**，5.6 起：收集的 key 不是拿去和 buffer 做字符串比对，而是**批量拿去被驱动表索引里查**，结果Sorted 后统一返回 —— 本质上是把 NLJ 的内层换成了「批量索引查找 + MRR」。
  ```text
  驱动表 10 行 → 收集 (10 个 key) → 批量到 t2 的索引中查找 → 按主键顺序回表
  ```
- `EXPLAIN` 里的相关标记：`Using join buffer (Block Nested Loop)`。
- `join_buffer_size` 就是这条路的内存旋钮：太小则分块多、被驱动表扫多次。

### 11.4 索引嵌套循环（INLJ，Indexed Nested Loop Join）

- 条件：**被驱动表的连接列上有索引**。
  ```sql
  -- 教学示意，不参与构建
  -- t2 在 t2.b 上有索引
  EXPLAIN SELECT * FROM t1 JOIN t2 ON t1.a = t2.b;
  -- type = ref，Extra 可能出现 Using index / Using where
  ```
- 代价 = 驱动表行数 × 索引查找代价。不需要 `join_buffer`，不需要排序，是**最干净的一条路**。
- 反向陷阱：如果优化器选了「大表做驱动表 + 小表做被驱动表且**无索引**」，就会退化成 BNL/笛卡尔积 —— 这是「一条 SQL 从 100ms 突然变成 100s」的典型剧本。

### 11.5 🔧 哈希连接（HASH JOIN，8.0.18 起）

- **解决的问题**：当**两边都没有合适的索引**、且数据量很大时，NLJ/BNL 都是灾难，优化器只能「凑合」；HASH JOIN 提供了一个有理论保证的兜底路线。
- **两阶段**：
  1. **build（构建）**：选较小的表，按连接键做哈希，建哈希表（可溢写到磁盘）。
  2. **probe（探测）**：扫描大表，对每行算同样的哈希去表里探测匹配。
- **适用/不适用**
  - 适合：无索引、大表、等值连接（`=`）。
  - 不适合：`ON` 条件是范围或不等值（会退化为 NLJ）；非等值连接用不上哈希。
- 原书（5.7.22）**完全没有这条路线**，所以在 8.0 上看到 `Using hash join` 时不要以为「走了新算法反而变差了」——它通常比 BNL 快一个量级。

### 11.6 排序合并连接（SMJ）：MySQL 里其实不存在

- **SMJ（Sort-Merge Join）**在 textbooks 里与 NLJ / HJ 并列，但在 **MySQL 的 InnoDB 执行引擎里没有原生的 SMJ 算子**。
  - MySQL 的连接执行器只有：`Nested Loop` / `Nested Loop with index` / `Hash Join`（8.0.18+）。
  - 想拿到 SMJ 的效果：让**连接键上有索引**（索引本身就是有序的），然后让优化器走 NLJ + 索引查找；**MariaDB** 则有更接近 SMJ 的实现，可横向对照。
- 这解释了一个常见困惑：**「为什么 PostgreSQL/Oracle 上这条连接很快，MySQL 上就慢？」** —— 很大概率是它们选了不同的连接算子，或者 MySQL 只能用 NLJ。

### 11.7 `ON` 与 `WHERE`：外连接下语义不同

```sql
-- 教学示意，不参与构建
SELECT * FROM a LEFT JOIN b ON a.id = b.id WHERE b.name = 'x';
-- 等价于 INNER JOIN（因为 WHERE 把「没匹配到的 NULL 行」全过滤掉了）
SELECT * FROM a LEFT JOIN b ON a.id = b.id AND b.name = 'x';
-- 仍是 LEFT JOIN（不满足条件时 b 侧补 NULL）
```
- 规则一句话：**`WHERE` 在「连接之后」生效，`ON` 在「连接之中」生效**。
- 面试高频：同样的语句，两种写法结果集不同，且优化器是否「能改写成内连接」也取决于此。
- 原书在讲连接语法时顺带提醒过：「`ON a.x = b.x AND 其他条件`」写得随意，会让优化器失去把外连接转内连接的机会。

### 11.8 连接优化的完整工具箱

| 手段 | 作用 | 备注 |
| --- | --- | --- |
| 给被驱动表连接列建索引 | 让 NLJ 变成 INLJ | **最有效的一步**，没有之一 |
| 用小表做驱动表 | 减少外层循环次数 | 优化器通常比人判断得准，`STRAIGHT_JOIN` 是最后手段 |
| 加大 `join_buffer_size` | 缓解 BNL | 连接多时会形成多个 buffer，别无脑调大 |
| 减少 `SELECT *` | 避免回表放大 | 覆盖索引往往能顺带解决连接回表 |
| `STRAIGHT_JOIN` | 强制指定驱动表顺序 | 有效但脆弱，schema 一变就可能失效 |
| `STRAIGHT_JOIN` 的替代：优化器提示 | 8.0 起 `JOIN_ORDER` / `JOIN_METHOD` 提示 | 比 5.6 时代的提示更细粒度 |
| 拆分 SQL | 复杂多表连接拆成若干简单查询在应用层拼 | 连接数 > 3~4 时通常值得考虑 |
- 🔧 **原书（2020）提的优化器提示在 8.0 已被大量移除**：除了 `FOR UPDATE` / `LOCK IN SHARE MODE 之外的大部分优化器提示（`STRAIGHT_JOIN`、`USE INDEX` 等仍在，但 `NO_RANGE_OPTIMIZATION`、`JOIN_ORDER` 一类在 8.0 是新增/保留的混合状态），升级到 8.0 时**必须用 `optimizer_trace` 复核一遍原有提示是否还按预期生效**。

### 11.9 🔧 2026 视角：8.0 的连接优化器不是 5.7 的形状

- **`HASH JOIN`（8.0.18）**：见 11.5。
- **`EXPLAIN ANALYZE`（8.0.18）**：连接场景最直接的收益 —— 它会把**驱动表的实际行数、实际循环次数、每步的实测耗时**打出来。5.7 的 `EXPLAIN` 只有估算值，「估算错误导致驱动表选错」这类问题只能靠猜。
- **CTE 与派生表合并/物化（8.0）**：`WITH ... MATERIALIZED / NOT MATERIALIZED` 可显式指定；**8.0 起公用表表达式不再被自动合并进外层**，可能改变「同一张 `t` 在 CTE 里被扫几次」的直觉。复杂分析报告型 SQL 上，`EXPLAIN` 的输出形态和 5.7 明显不同。
- **并行查询（8.0.22 的 `n_jobs`）**：扫描端可并行，连接算子逐步具备并行能力；OLAP 型多表连接在大表场景（千行以上的明细）上收益显著。
- **连接顺序搜索空间**：优化器对连接顺序做“贪心 + 有限回溯”，连接表越多越容易选错；多表大连接建议直接看 `optimizer_trace` 里 `rows_estimated` vs `rows_actual`。

### 11.10 🔧 连接查询的优化清单（按性价比排序）

| 序号 | 动作 | 预期收益 | 风险 |
| --- | --- | --- | --- |
| 1 | 给**被驱动表**的连接列建索引 | 最高（NLJ → INLJ） | 多一个索引的写成本 |
| 2 | 删掉「看上去有用但实际没被选」的索引 | 中 | 优化器选路可能变好，也可能需要 8.0 的隐藏索引先灰度 |
| 3 | 用 `EXPLAIN ANALYZE` 定位估算偏差 | 高（找到真因） | 需要真实数据量 |
| 4 | 把大范围 `IN (...)` 改成临时表 JOIN | 中高 | 需要额外维护临时表 |
| 5 | 减少 `SELECT *`，改覆盖索引 | 中 | SQL 变更成本 |
| 6 | 拆分 5 张表以上的复杂连接 | 中 | 应用层复杂度上升 |
| 7 | `STRAIGHT_JOIN` 强指定驱动表 | 取决于场景 | 脆弱，schema/数据一变可能失效 |
| 8 | 调 `join_buffer_size` | 低 | 连接多时内存翻倍 |
- 顺序很重要：**第 1 步几乎总是最划算**，而且它同时解决了「查询慢」和「锁范围过大」两个问题（未走索引的 `UPDATE ... JOIN` 会把大片区间锁住，见 `22-锁.md`）。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：**大规模连接处理**在分布式/向量化执行引擎里被重新研究（Spark、Flink、Velox、DuckDB 的 shuffle 式 hash join 与 broadcast join）；**学习型优化器**（用模型预测连接顺序而不是手写成本公式）在 2020 年之后成为主流数据库会议的热门方向；**HTAP 下的连接下推**（行存连接下推到列存副本，TiDB 的 TiFlash、Aurora 的 zero-ETL 思路）。
- **工业界开源**（star 数 2026-09-25 通过 `gh api` 实测）：
  - `mysql/mysql-server`（≈12.4k★）：连接执行器在 `sql/executing_nested_loop_join.cc`（NLJ/BKA）与 `sql/join_optimizer/`；`HASH JOIN` 在 `sql/hash_join_*.cc`。
  - `mariadb/server`（≈8.3k★）：在连接算子（尤其 SMJ 类实现与优化器开关）上与 MySQL 有可对照的历史差异。
  - `pingcap/tidb`（≈40.6k★）与 `cockroachdb/cockroach`（≈32.5k★）：分布式连接基于统计选择 broadcast / shuffle join，是「连接顺序 × 数据分布」最直观的现代样本。
  - `duckdb/duckdb`（≈41.7k★）、`clickhouse/clickhouse`（≈50.1k★）：向量化 hash join，可作为「MySQL HASH JOIN 该长什么样」的参照实现。
  - `postgres/postgres`（≈22.2k★）：`Hash Join` / `Merge Join` / `Nested Loop` 三种算子**同时存在且都能被选中**，与 MySQL 相对单一的执行器模型形成对照。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「连接慢就是加个 `join_buffer_size`」 | 真正的解法是**给被驱动表连接列建索引**，让 NLJ 变成 INLJ |
| 2 | 「驱动表选错了只能靠 `STRAIGHT_JOIN`」 | 先用 `optimizer_trace` 看估算是否离谱；8.0 有更细的连接提示 |
| 3 | 「MySQL 有排序合并连接」 | MySQL 没有原生 SMJ；SMJ 是教材/PostgreSQL 的概念 |
| 4 | 「`ON` 和 `WHERE` 写哪都一样」 | 外连接下二者结果集不同，且影响优化器改写能力 |
| 5 | 「多表连接越多越好」 | 连接顺序搜索空间爆炸；超过 4~5 张表就该考虑拆分或加 materialized CTE |
| 6 | 🔧 **本书未覆盖** | 原书基于 5.7.22，**完全没有 `HASH JOIN`（8.0.18）**；`EXPLAIN ANALYZE` 才是验证「驱动表选对没」的正确工具 |
| 7 | 🔧 **本书未覆盖** | **CTE 物化 / 派生表合并**在 8.0 的默认行为与 5.7 不同（8.0 不再自动合并 CTE），会导致「同一张表被扫多次」；复杂报表 SQL 升级 8.0 后 `EXPLAIN` 形态变化必须复核 |
