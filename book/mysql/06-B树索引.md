# 第 6 章 快速查询的秘籍——B+树索引

> **原书位置**：第 6 章「快速查询的秘籍——B+树索引」，对号章节。原书基于 **MySQL 5.7.22**。
>
> **一句话**：InnoDB 的表就是**一棵以主键排序的 B+ 树**（聚簇索引），二级索引是另一棵 B+ 树；
> 索引让「按序查找」从 O(行数) 变成 O(log(行数))，代价是**写路径上要维护更多树**，并引入「回表」这一额外 I/O。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 6.1 索引即表：聚簇索引 | 叶子节点存**完整行数据**，按主键排序；有且仅有一个 | 「表本身就是一棵 B+ 树」，所以按主键查最快 |
| 6.2 聚簇索引的选择规则 | ① 显式主键 ② 第一个非 NULL 唯一索引 ③ 自动生成 6 字节隐藏 row_id | 这条规则在 5.7/8.0 之间基本稳定，但「唯一索引可以是 NULL」这一点常被误解 |
| 6.3 二级索引 | 叶子节点存「索引列 + 主键值」，不是完整行 | 定位到二级索引后必须**回表**拿完整行 |
| 6.4 回表（bookmark lookup） | 二级索引 → 聚簇索引的两次 B+ 树查找 | 回表次数 = 结果行数 × 一次树查找，是优化器最看重成本项之一 |
| 6.5 B+ 树高度 | 16KB 页、扇出几百，三层即可放千万行 | 为什么「三次磁盘 I/O 就能定位一行」 |
| 6.6 页分裂与树平衡 | 随机键导致页分裂、可能树变矮/变高 | 主键设计决定树的形状与写放大 |
| 6.7 索引的代价 | 每多一个索引，写放大、页空间、优化器选择空间都变大 | **索引不是越多越好** |
| 6.8 🔧 8.0 之后的索引能力 | 函数索引（8.0.13+）、不可见索引、跳过扫描（8.0.13 `skip_scan`）、倒排/全文索引、JSON 多值索引 | 索引的形态正在从「B+ 树一种」走向「多种」 |

## 核心精讲

> 以下 SQL / 结构均为**教学示意，不参与构建**：本目录不搭建真实实例，示例只用于对齐概念。

### 1. 两棵树：聚簇索引 + 二级索引（教学示意，不参与构建）

```
聚簇索引（叶子 = 整行）            二级索引 idx_k（叶子 = k + 主键）
        root                                  root
       /   \                                 /   \
   [非叶]   [非叶]                       [非叶]   [非叶]
    |         |                            |        |
 叶子页     叶子页                      叶子页     叶子页
 (k1,完整行) (k2,完整行)           (k1,pk)    (k2,pk)
                                            ↓
                                      「回表」到聚簇索引按 pk 找整行
```

关键事实：**二级索引的叶子只存「索引列 + 主键」**，因此
「查 `SELECT *` + 走二级索引」必然包含一次回表；而「查的列正好都在二级索引里」就不需要回表（覆盖索引，见 07）。

### 2. B+ 树高度的量级（教学示意，不参与构建）

```
一页 16KB
  非叶子页：主键 BIGINT(8B) + 页号(4B) + 指针 ≈ 每页可放上千个键 → 扇出 F ≈ 1000
  叶子页：若行 200B，一页约 80 行
  ├─ 二层：1000 × 80 ≈ 8 万行
  ├─ 三层：1000 × 1000 × 80 ≈ 8000 万行
  └─ 四层：约 8000 亿行
```

所以** InnoDB 的 B+ 树通常只有 3–4 层**，一次点查最多约 3–4 次页访问（其中只有叶子层大概率真读磁盘，
其余已在 Buffer Pool 中）。这也解释了为什么「树变高」是性能问题的信号：它意味着多一次 I/O。

### 3. 聚簇索引的选择（教学示意，不参与构建）

```sql
-- 演示「隐藏主键」存在的观测方式（只读取信息，不构成构建步骤）
SHOW CREATE TABLE t;
```

| 情况 | 聚簇键 |
| --- | --- |
| 有 `PRIMARY KEY` | 该主键 |
| 无主键，但有第一个「所有列都为 NOT NULL 的唯一索引」 | 该唯一索引 |
| 都没有 | 6 字节隐藏的 `row_id`（单调递增） |

**为什么值得关心**：聚簇键决定了「行在页内的物理顺序」与「二级索引叶子里的指针大小」。
一个很窄的自增主键 → 页内填充率高 + 二级索引叶子更紧凑；
一个很宽的业务键（如长字符串 UUID）→ 页内更容易分裂 + 每个二级索引都要重复存它。

### 4. 回表成本模型（教学示意，不参与构建）

```
扫描 N 行走二级索引：N 次「二级索引叶子页访问」 + N 次「聚簇索引定位」
                    ↑ 若 N 很大且回表随机 → 每次都可能是一次随机 I/O
优化器的典型反应：预估回表成本过高 → 直接放弃二级索引，退化为全表扫描（典型「索引失效」现象）
```

这就是为什么「`SELECT *` 反而更快」的反直觉现象可能成立：
优化器看到「走二级索引要回表 10 万次」就会选择全表顺序扫。
反过来说，**让「回表次数」变成 0 或很小**（覆盖索引 / 缩小结果集），是索引优化的第一杠杆。

### 5. 顺序写 vs 随机写（教学示意，不参与构建）

```
顺序主键插入：新行总落在一页右侧 → 顺序 I/O + 页分裂少
随机主键插入：新行落在随机页     → 随机 I/O + 大量页分裂（且分裂出的两半常不满）
```

这也是「自增主键 vs UUID 主键」在吞吐上的核心差异；
工程上常见的折中是「**雪花/发号器生成的单调主键**」——既有业务含义又接近单调递增。

### 6. 索引的维护成本（教学示意，不参与构建）

```
INSERT  → 每棵二级索引都要插入一次（可能触发该索引的页分裂）
UPDATE  → 若改的是二级索引键，则需要「删除旧版本 + 插入新版本」
DELETE  → 标记删除后，索引项要等 purge 才真正清理
```

推论：**批量导入数据前先去掉二级索引、导完再建**，是「大批量写入提速」的通用手段；
反过来，**在高频写入的表上滥建索引**会持续拖慢写入。

### 7. 索引设计的两条实战规则（教学示意，不参与构建）

**规则一：把「等值列」放前面，「范围列」放后面。**

```
索引 (status, created_at)：
  WHERE status = 1 AND created_at > '2026-01-01'   → 两列都用于定位（status 等值 + created_at 范围）
  WHERE created_at > '2026-01-01'                  → 用不上（跳过了 status）
```

**规则二：让索引尽量「覆盖」高频查询，同时控制索引个数。**

```
查询 SELECT id, name FROM user WHERE city = 'X' AND age = 18
  索引 (city, age, id) 或 (city, age) → 覆盖，无需回表
  索引 (city)                        → 每命中一行都要回表，优化器可能放弃
  索引 (age, city)                    → 最左前缀是 age，常见查询用不上
```

一个可操作的检查顺序：
1. 从慢查询里挑出 Top N 的查询模板；
2. 为每个模板写「等值列在前、范围列在后」的联合索引；
3. 合并前缀相同的索引（`(a)` 已被 `(a,b)` 包含，前者可考虑删掉）；
4. 用 `EXPLAIN` 回归验证，用不可见索引验证「删掉它是否真的有影响」。

## 版本演进

| 版本 | 关键变化 |
| --- | --- |
| **5.7（原书基线）** | 聚簇/二级索引概念稳固；`Adaptive Hash Index` 默认开；全文索引 MyISAM 实现完善、InnoDB 全文索引在 5.6 起可用 |
| **8.0** | 🔧 **函数索引 / 表达式索引**（8.0.13 起）；🔧 **不可见索引**（`ALTER INDEX ... INVISIBLE`，8.0 起，优化器忽略它但仍维护）；🔧 **跳过扫描**（`skip_scan`，8.0.13 起，针对「复合索引跳段」）；🔧 **降序索引**支持；🔧 **JSON 多值索引**（`CAST(... AS ... ...)` 的 `Multi-Valued Indexes`，8.0.17 起）；🔧 InnoDB 全文索引在 8.0 更完整；🔧 统计信息持久化（`mysql.stats_*`）让优化器的估算更稳 |
| **8.4 LTS** | 🔧 优化器默认行为进一步收敛（如默认关闭一些旧规则），`EXPLAIN ANALYZE` 等诊断手段更完善；以官方文档为准 |
| **9.x** | 🔧 向量与 JSON 相关索引能力继续增强，索引形态多元化的趋势延续 |
| **MariaDB / PostgreSQL 对照** | PostgreSQL 有 **BRIN**（块区间索引，适合时序）、**GiST/GIN**（GiST 用于地理/全文，GIN 适合数组与 JSONB）、**生成列 + B-tree 索引**；MariaDB 引入 **SPATIAL/全文**改进与 **`REF_OR_JOIN`** 等索引相关优化 |

## 近年研究与工业界开源实践（2015–2026）

- **`mysql/mysql-server`（2026-09 实测 ≈12.4k★）**：聚簇索引实现在 `storage/innobase/ibd/` 与
  `storage/innobase/btr/btr0cur.cc`（`btr_pcur_open` 是定位一条记录的经典入口）；
  8.0 的 `skip_scan` 与表达式索引都在优化器/索引模块里，可用 `EXPLAIN FORMAT=JSON` 观察。
- **`pingcap/tidb`（≈40.6k★）**：底层是 RocksDB 的 KV，其「索引」其实是把 `(index_key, handle)` 写进 LSM，
  因此「回表」在 TiDB 里是「一次 KV 点查」，成本模型与 InnoDB 不同——这是很好的对照。
- **`facebook/rocksdb`（≈32.1k★）**：LSM 用「多层 + 合并」换写吞吐，代价是读放大与空间放大；
  与 B+ 树的取舍是数据库选型里最经典的一条分界线。
- **`clickhouse/clickhouse`（≈50.1k★）**：主键（sparse index）只做「跳块」，不做行级定位，
  其余靠列存 + 向量化，是「索引概念被重新定义」的代表。
- **研究侧**：近年关于 **B+ 树在 NVMe/PMem 上的退化与复活**（_bw-tree 在真机上不如预期_、
  **写优化树的读放大分析**）、**HTAP 下行列混合索引**、** learned index（学习型索引）**
  都有持续工作；工程上真正上主线的仍是「B+ 树 + 多值/全文/向量索引」的组合。

## 常见误区与本书需修正之处

| # | 常见误区 | 修正（🔧 = 原书出版时未覆盖） |
| --- | --- | --- |
| 1 | 「索引和表是两个东西」 | InnoDB 里**表就是聚簇索引这棵树**，索引是它的附属结构 |
| 2 | 「二级索引叶子存整行」 | 存的是「索引列 + 主键」，拿完整行必须回表 |
| 3 | 「树高度 = 表高度 / 页大小」 | 树高是三层就够放千万行；页大小与行长共同决定扇出 |
| 4 | 「索引越多查询越快」 | 每个索引都是写路径上的负担 + 优化器的选择空间 |
| 5 | 「主键只是业务需要」 | 主键决定聚簇顺序与二级索引体积，是**存储层决策** |
| 6 | 「UUID 做主键更安全」 | 随机主键导致页分裂与写放大；改用单调生成的主键更安全 |
| 7 | 🔧 本书未覆盖 | 原书基于 5.7.22，**未覆盖** 函数索引、不可见索引、跳过扫描、JSON 多值索引；这些在 2026 年的日常优化里已经是常用手段 |
| 8 | 「索引键越小越好」 | 主键宽则每个二级索引的叶子都要重复存它；窄顺序主键通常优于宽随机主键 |
| 9 | 「页数多 = 树高」 | 树高由「扇出」决定，不是由总页数决定；行长与页大小的比值才是关键 |
| 10 | 「`FULLTEXT` 与 `B+ 树` 是一回事」 | 全文索引是倒排结构（词 → 行号），与 B+ 树完全不同，见 07 章对全文/多值索引的讨论 |
