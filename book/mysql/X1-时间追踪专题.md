# 时间流逝何处去——MySQL 里的时间戳、时区与「时间到底是什么」

> 原书说明：本书（2020，基于 MySQL 5.7.22）**没有独立的「时间 / 时区」章节**。本文件按主题聚合原书中散落的时间相关内容（第 4 章数据类型、第 8 章数据目录、第 13 章 binlog 与统计数据、第 18–22 章事务与复制），并补充 2020 年之后必须补的时区与 binlog 时间戳知识。原书对应章号见「与其他章」一节的互链。

## 本章地图

> 一句话：**MySQL 里有两种时间——「墙上时钟」（可被 NTP 回拨、受时区影响，用于给用户看）和「单调时钟」（只用于算耗时，不受回拨影响）**；而列类型 `TIMESTAMP` 与时区变量的组合，是「主从复制数据不一致」与「2038 年溢出」两个经典事故的共同源头。

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 12.1 时钟源 | `CLOCK_REALTIME` vs `CLOCK_MONOTONIC`；`gettimeofday` 的微秒精度 | 用户可见时间用墙上时钟，内部计时用单调时钟 |
| 12.2 服务器侧的时间点 | 连接建立、语句开始/结束、慢日志 `Query_time` 的采集点 | 慢日志里的 `Start: timestamp` 是墙上时钟，`Query_time` 是单调时钟之差 |
| 12.3 `NOW()` 与 `SYSDATE()` | 语句开始时刻 vs 真实执行时刻；语句内固定 | 复制语义不同，强烈建议用 `NOW()` 或显式传参 |
| 12.4 列类型：`TIMESTAMP` / `DATETIME` | 范围、时区转换、微秒、2038 溢出 | `TIMESTAMP` 带时区转换且 2038 溢出；`DATETIME` 不转换但占空间 |
| 12.5 时区变量 | `time_zone`、`system_time_zone`、会话/全局/连接三处时区 | 三处时区不一致 = 数据不一致的头号来源 |
| 12.6 binlog 中的时间戳 | `QUERY_EVENT` 的 `exec_time`、微秒精度、主从时区传播 | `exec_time` 是**执行耗时**不是**事件时间**；别用它做审计 |
| 12.7 表设计建议 | 时间列选型、`DEFAULT CURRENT_TIMESTAMP` 的隐式规则 | 用 `DATETIME(3)` 或 BIGINT 毫秒，避免隐式时区转换 |
| 12.8 🔧 2026 视角 | 8.0 的时区持久化、`performance_schema` 计时、2038 仍未解决 | ⚠️ 现在（2026）建表仍要 conscious 选 TIMESTAMP |

## 核心精讲

> **教学示意，不参与构建。** 下文所有 `--` 开头的语句片段仅用于讲清语义，**未在本机编译、未连接任何 MySQL 实例执行**；结论来自原书与官方文档，数值/默认值请以你实际版本为准。

### 12.1 两种时钟：墙上时钟 vs 单调时钟

- **墙上时钟（wall clock）**：`time(2)` / `gettimeofday(2)` / `clock_gettime(CLOCK_REALTIME)`。可以**被 NTP 校时、被人工改表、甚至回拨**。
  - MySQL 用户能看到的几乎都是它：`SHOW PROCESSLIST` 的 `Time`、`slow log` 的 `Start:`、错误日志时间戳。
- **单调时钟（monotonic clock）**：`clock_gettime(CLOCK_MONOTONIC)`，只增不减，单位纳秒/微秒。
  - 用于**计算时间差**：慢日志里的 `Query_time`、`InnoDB` 内部耗时统计、`performance_schema` 的 `TIMER_START/TIMER_END`。
- 🔧 **为什么要分两种**：如果「计算耗时」用墙上时钟，一次 NTP 把时间往回拨 2 秒，慢日志里就会出现 `Query_time: -1.999` 或者 `Query_time: 187` 这种荒谬值（真实事故）。所以**所有「差值」必须来自单调时钟，所有「展示」才用墙上时钟**。

### 12.2 服务器侧的时间采集点（原书第 8 章的延伸）

一次语句执行的简化时间线（教学示意，不参与构建）：

```text
连接建立（THD 创建）
  └─ 记录 start_time   ← 墙上时钟（CURRENT_TIMESTAMP 语义）
语句解析/优化/执行
  └─ 各种耗时统计       ← 单调时钟相减（Query_time 的真实来源）
语句结束
  └─ 记录 end_time
  └─ 若 耗时 > long_query_time 且 命中 slow log 条件 → 写入 slow log
```

- `long_query_time` 的比较对象是**单调时钟差值**，所以它不受系统改时间影响（这是原书没讲、但排查「慢查询突然变慢」时必须知道的）。
- 🔧 `performance_schema.events_statements_history[_long]` 里的 `TIMER_START` / `TIMER_END` / `TIMER_WAIT` 单位是**皮秒**，且基于单调时钟 —— 这是比 slow log 更精细的低耗时语句归因来源。

### 12.3 `NOW()` 与 `SYSDATE()`：差一个字，复制语义差很多

| 函数 | 取值时点 | 语义 | 在 binlog 里的命运 |
| --- | --- | --- | --- |
| `NOW()` / `CURRENT_TIMESTAMP` | **语句开始时刻**，语句内固定不变 | 事务开始时间 | 8.0 起在 ROW 格式下会被**具体化为实际写入值**，主从中一致 |
| `SYSDATE()` | **真实调用时刻**，每次调用可能不同 | 真·当前时间 | 在 STATEMENT 格式下**不被具体化** → 主从可能得到不同结果 |
| `UNIX_TIMESTAMP()` | 基于 `NOW()` 与时区换算 | — | 同上 |

- 原书第 13 章讲 binlog 时提到过「同一个 SQL 在主从执行结果不同」的坑，`SYSDATE()` 正是高频原因之一。
- 工程建议：**业务代码不要在 SQL 里算时间**，由应用层传入明确的时间值，既避开复制语义坑，也便于测试冻结时间。

### 12.4 列类型：`TIMESTAMP` 与 `DATETIME`

| 维度 | `TIMESTAMP` | `DATETIME` |
| --- | --- | --- |
| 存储 | 4 字节 + 时区转换（5.6+ 可带小数，占 4+1~3 字节） | 5 字节 / 6 字节（5.6+ 支持 `DATETIME(6)`） |
| 范围 | `1970-01-01 00:00:01` ~ `2038-01-01 03:14:07`（UTC） | `1000-01-01` ~ `9999-12-31` |
| 时区 | **存 UTC，读时按会话时区转换** | 原样存取，不做转换 |
| 溢出风险 | ⚠️ **2038 问题**（2026 年仍是生产隐患） | 基本不会 |
| 隐式规则 | 未显式声明 `NOT NULL` 时，`DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` 会被**隐式加上**（这也是老表 unexpected 自动更新的原因） | 无 |

- `DATETIME(6)` 支持**微秒**（6 位小数），`TIME(6)` 同理 —— 记录「精确时间点」时别只到秒。
- 原书第 4 章讲数据类型时只点到为止，2026 年补的两条硬结论：
  - 🔧 **`TIMESTAMP` 的时区转换是「会话时区」相关的**：同一个二进制数据，用不同会话时区读出来是不同的字面量 —— 主从 `time_zone` 不同 + `TIMESTAMP` 列，就可能出现「主上看一条、从上看另一条」。
  - 🔧 **2038 不是玩笑**：MySQL 至今没有把 `TIMESTAMP` 放宽到 64 位（ MariaDB / PostgreSQL / 其他数据库早已解决）。**2026 年新建表请默认用 `DATETIME` 或 BIGINT 毫秒**。

### 12.5 三处时区：`system_time_zone`、`time_zone`、`connection` 的字符集层

- `system_time_zone`：服务器启动时从 OS 继承，只读。
- `time_zone`（可 `global` / `session` / `persist`）：MySQL 真正用于换算的时区。
  - 值是 `'SYSTEM'`（跟随 `system_time_zone`）或 `'Asia/Shanghai'` 之类的具名时区。
  - 🔧 `SET PERSIST time_zone='+08:00'`（8.0 起）可以把时区写进 `mysqld-auto.cnf`，重启不丢 —— 这是 5.7 时代靠 `my.cnf` 手工维护的改进。
- 具名时区依赖 `mysql.time_zone_name` 等系统表（原书第 8 章「数据目录」小节提到的系统库之一）；**若 `mysql.time_zone*` 表被误删/未初始化，具名时区会退化成偏移字符串**。

### 12.6 binlog 里的时间戳（原书第 13 章的必补一节）

- `QUERY_EVENT`（以及 `ROWS_QUERY_LOG_EVENT`）头部含 **4 字节 `exec_time`** + **4 字节 `sql_mode`**（5.6 后扩展）。
  - ⚠️ **`exec_time` 是「事件产生时刻 − 语句开始时刻」的执行耗时差（秒级），不是事件的时间戳**。很多人误以为它是「这条记录发生的时间」，从而用它做审计/回溯 —— 这是错误用法。
- 🔧 8.0 起 binlog 支持**亚秒级时间戳**（`binlog_transaction_dependency_tracking`、`mysqlbinlog` 友好输出），并且新增了 `Transaction_payload` 事件（压缩事务正文），`mysqlbinlog --base64-output` 输出格式与 5.7 不再完全一致。
- 🔧 **复制场景的时间传播**：ROW 格式下 `NOW()` 会被具体化为字面值，从库重放得到相同结果；STATEMENT 格式 + `SYSDATE()` / 依赖 `CURRENT_TIMESTAMP` 的 DDL，则从库会得到「从库自己的执行时刻」。**这正是「主从数据不一致」里最常见的一类**。
- 🔧 8.0.17 起可用的 **Clone Plugin** 在做分布式恢复（distributed recovery）时，是整份数据页 + redo 应用的物理克隆，**不涉及 SQL 层时间戳** —— 与逻辑备份（mysqldump）恢复后的时间点语义不同，这点在「PITR 恢复到哪一刻」的口径上要写进 SOP。

### 12.7 表设计：时间列怎么选

| 需求 | 推荐 |
| --- | --- |
| 只记录「什么时候发生」且不希望被时区偷换 | `DATETIME` / `DATETIME(3)` |
| 需要跟 `CURRENT_TIMESTAMP` 自动维护 | `DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`（显式写全，别靠隐式规则） |
| 需要跟其他系统对时间（Java `Instant`、前端 ISO8601） | `BIGINT` 毫秒时间戳（并且**不要**用 `TIMESTAMP`） |
| 需要精确到亚秒 | `DATETIME(6)` / `TIMESTAMP(6)` |
| 未来还可能超 2038 | 绝对不要 `TIMESTAMP` |

- 隐式规则坑（教学示意，不参与构建）：`CREATE TABLE t (ts TIMESTAMP NULL)` 在某些配置（`explicit_defaults_for_timestamp=OFF`，5.7 默认）下会被改写成 `ts TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` —— 于是**任何一次 UPDATE 都会偷偷改掉这个字段，且不报错**。

### 12.9 🔧 时间相关故障的排查清单

| 现象 | 先查什么 | 常见根因 |
| --- | --- | --- |
| 主从数据不一致 | 两侧 `@@global.time_zone`、`@@session.time_zone` 是否一致；列类型是不是 `TIMESTAMP` | 时区不同 + `TIMESTAMP` 列 + STATEMENT 格式 |
| 报表「当天数据少了一小时」 | 应用层时区与库时区是否对齐 | 应用用 UTC、库用 `+08:00`，边界行被算到前一天 |
| 慢日志突然出现「耗时异常大」 | 是否发生过 NTP 校时/时钟回拨 | 用墙上时钟算耗时会翻车（应当用单调时钟） |
| 2038 告警 | 表里有没有 `TIMESTAMP` 列、最大值是否接近 `2038-01-01 03:14:07` | ⚠️ MySQL 至今未放宽 `TIMESTAMP` 范围 |
| 恢复后「时间点对不上」 | 恢复方式：逻辑备份（SQL 时间戳已固化）还是 Clone/binlog（物理时间点） | 两种恢复口径不同，SOP 要写清 |

### 12.10 🔧 与 PostgreSQL / 其他系统的对照

| 系统 | 时间列语义 | 与 MySQL 的差别 |
| --- | --- | --- |
| MySQL `TIMESTAMP` | 存 UTC、按会话时区渲染、2038 溢出 | 语义混杂，「存的是什么」取决于会话设置 |
| PostgreSQL `timestamptz` | 内部永远 UTC，输出时才按 `TimeZone` 渲染 | **更干净**：存储与呈现分离 |
| PostgreSQL `timestamp` | 无时区，语义同 MySQL `DATETIME` | 对应 MySQL 的 `DATETIME` |
| ClickHouse `DateTime64(3)` | 可带时区、毫秒精度 | 分析场景常见选择 |
- 迁移视角结论：**从 MySQL 迁到 PostgreSQL 时，把 `TIMESTAMP` 一律改成 `timestamptz`** 通常能一并消掉一整类「时区不一致」缺陷。

### 12.11 小结：一张速查表

| 你到底要问的是 | 去问谁 | 要小心什么 |
| --- | --- | --- |
| 「这条记录是什么时候发生的？」 | 业务字段（`occurred_at DATETIME(3)`） | 别用 binlog `exec_time`，那是耗时 |
| 「它什么时候被写进主库的？」 | binlog 事件里的时间或 GTID | STATEMENT/ROW 的具体化行为不同 |
| 「这次查询跑了多久？」 | 慢日志 `Query_time` / `performance_schema` 计时 | 基于单调时钟，不受时钟回拨影响 |
| 「从库看到的状态对不对？」 | 两侧时区 + 列类型 + binlog 格式 | `TIMESTAMP` + 不同时区 = 不一致 |
| 「恢复能回到哪一刻？」 | 备份类型（逻辑/物理）+ binlog 起点 | 两种恢复口径不同，写进 SOP |

## 近年研究与工业界开源实践（2015–2026）

- **围绕时间的工程议题**（2015–2026）：**逻辑时钟与混合逻辑时钟（HLC）**在分布式数据库里的普及（CockroachDB 的 `HLC`、Spanner 的 TrueTime）—— 它们解决的核心问题正是「墙上时钟不可信，但物理时钟必须提供外部一致性」。**TiDB 的 TSO** 用物理时间 + 逻辑位组合成全局时间戳。
- **时间点恢复（PITR）的现代形态**：物理备份 + binlog 回放；🔧 **8.0 Clone + binlog** 组合让「克隆一个从库并追到某一时刻」变成了标准能力。
- **可观测性侧**：`performance_schema` 的皮秒级单调计时、OpenTelemetry 把 DB span 的耗时与墙钟时间并列上报，避免「回拨导致监控曲线断裂」。
- **工业界开源**（star 数 2026-09-25 通过 `gh api` 实测）：
  - `mysql/mysql-server`（≈12.4k★）：`sql/time_zone.cc`、`sql/temporal.cc`、`libmysqltime/` 是时区与 temporal 类型的实现现场。
  - `percona/percona-server`（≈1.3k★）：企业/云厂商分支里常见的时区与 temporal 兼容性补丁。
  - `mariadb/server`（≈8.3k★）：更早提供 `TIMESTAMP` 放宽与虚拟时间列，可作横向对照。
  - `postgres/postgres`（≈22.2k★）：`timestamptz` 语义比 MySQL 的 `TIMESTAMP` 更干净（存 UTC、渲染时转），值得作为「时间列该怎么设计」的正例。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「`exec_time` 就是这条记录的时间」 | 它是**执行耗时差**，不是事件时间；做审计要用业务字段或 GTID + row 位置 |
| 2 | 「`TIMESTAMP` 和 `DATETIME` 差不多，都是存时间」 | `TIMESTAMP` **存 UTC 且按会话时区渲染**，且 2038 溢出 |

| 5 | 「慢日志 `Query_time` 可能是负的」 | 它基于单调时钟，回拨不影响；可能出现异常大值但不应为负 |
| 6 | 🔧 **本书未覆盖** | 原书（2020，5.7.22）没有时间/时区专章：时区三处变量、`SET PERSIST`、binlog `exec_time` 语义、8.0 克隆与 PITR 时间点口径，均需按本节补齐 |
