# 第 22 章 工作面试老大难——锁

> 原书说明：标题为「工作面试老大难——锁」，基于 MySQL 5.7.22 撰写。本文件按其思路展开**行锁 / 间隙锁 / next-key lock、锁等待、死锁检测**，并补齐 5.7/8.0 的演进与 2020 年之后必须补的**`SKIP LOCKED` / `NULLS NOT DISTINCT`、`performance_schema.data_locks`**、以及 MySQL 与 PostgreSQL 的对照。

## 本章地图

> 一句话：**InnoDB 的锁是「索引上的区间锁」——行锁锁住记录本身，间隙锁锁住记录之间的空隙，next-key 锁把两者绑成「左开右闭」的区间；幻读被它消掉，并发度也被它限制。**

## 核心精讲

> **教学示意，不参与构建。** 下文结构与 `--` 片段仅用于说明锁的组织方式，**未在本机编译、未启动任何 MySQL 实例执行**。

### 22.1 为什么需要锁：当前读必须串行

- **快照读（`SELECT`）不需要锁**：MVCC 已经保证了「看到哪个版本」，彼此不干扰（见 `21-事务隔离级别与MVCC.md`）。
- **当前读（`UPDATE` / `DELETE` / `SELECT ... FOR UPDATE`）必须加锁**：因为它要读「最新已提交」并改它，两个这样的操作撞在一起就丢更新。
- 所以「MySQL 读不加锁」这句话只在**普通 `SELECT`** 上成立。

### 22.2 三种行锁：锁的是索引

InnoDB 的锁**建在索引项上**，不是「记录ID」这种逻辑概念：

| 类型 | 锁住什么 | 常用场景 |
| --- | --- | --- |
| **Record Lock（记录锁）** | 单条**索引记录**本身 | 主键/唯一索引等值查询 |
| **Gap Lock（间隙锁）** | 两条索引记录之间的**空隙**（不含记录） | 范围查询、`INSERT` 前挡住别人插在我前面/后面 |
| **Next-Key Lock（临键锁）** | 记录 + 它前面的间隙 = **左开右闭**区间 | RR 下的范围查询默认形态 |

- 索引的结构决定了「区间」这个概念（教学示意，不参与构建）：
  ```text
  聚簇索引（id）：(-∞, 4] (4, 9] (9, 15] (15, +∞)
                   ↑ next-key 是「前开后闭」，其中 4 本身被 Record Lock 锁住
  ```
- 范围查询的加锁示意（RR 下）：`WHERE id < 9` 会锁住 `(4, 9]` 这条 next-key，即**同时锁住 9 这个记录和它前面的间隙**。
- **RR 用 next-key 锁消除幻读**（见 21.7），代价是：**锁的覆盖面比"查询条件"大得多** —— 这是「一个 `UPDATE ... WHERE created_at < now()` 把整表都锁了」的原因。

### 22.3 退化成表锁：最常见的事故

```sql
-- 教学示意，不参与构建
UPDATE t SET status = 1 WHERE name = 'Tom';   -- name 上没索引
-- 后果：全表扫描 → 扫过的每一行都被加 next-key 锁 → 整表被锁
```
- 命中条件：**谓词列上没有合适的索引**（或优化器选择全表扫描）。
- 症状：**一条 DML 之后所有写操作排队**，甚至读（`FOR UPDATE`）也排队；`SHOW ENGINE INNODB STATUS` 里能大量 `lock wait`。
- 对策：
  1. 给谓词列建索引（**不是「给它加个索引肯定走」**，要看优化器的选择）；
  2. 大批量更新按主键分段；
  3. 用 `SELECT ... FOR UPDATE` 前先确认执行计划（用 `EXPLAIN`，8.0 可用 `EXPLAIN ANALYZE`）。
- 相关：MyISAM 是表锁，而 InnoDB 是行锁 —— 但**「行锁」不等于「不会锁表」**：无索引 DML 就是事实上的表锁。

### 22.4 读的两种姿势

| 语句 | 锁 | RR 下的可见性 |
| --- | --- | --- |
| `SELECT col FROM t WHERE id = 1` | 无锁 | 快照（事务开始时刻） |
| `SELECT col FROM t WHERE id = 1 LOCK IN SHARE MODE` | **共享锁 S**（默认 RR 下 next-key） | 最新已提交 |
| `SELECT col FROM t WHERE id = 1 FOR UPDATE` | **排他锁 X**（默认 RR 下 next-key） | 最新已提交 |
| `UPDATE` / `DELETE` | 排他锁 X | 最新已提交 |
- `LOCK IN SHARE MODE`：多个事务**可以**同时持有 S 锁读，但写要排队 → 防「读之后我改、别人也读到了旧值」。
- 在 `READ COMMITTED` 下，**间隙锁基本被关掉**（只对唯一索引等值检查保留），所以并发高但幻读可能出现 —— 这正是 RC 与 RR 在锁层面的根本差异。

### 22.5 锁的相容性

| 请求 \ 已持有 | S | X |
| --- | --- | --- |
| **S** | ✅ 相容 | ❌ 冲突 |
| **X** | ❌ 冲突 | ❌ 冲突 |

- 行级锁只比较**同一索引记录**上的锁；不同行之间天然相容（这是「1000 个事务同时 `UPDATE` 不同行」仍能并发的原因）。
- 表级意向锁（`IS` / `IX`）：InnoDB 会在加行锁前给表加意向锁，用于**快速判断**「这张表现在有没有被锁」，避免逐行扫描（思想与多粒度意向锁一致，见 [15-并发控制.md](../数据库系统概念6/15-并发控制.md) 15.3）。

### 22.6 锁等待与超时

- 当一个事务请求的锁被别人持有，它就进入**等待**，加入该行锁的等待队列。
- 两个兜底机制：
  1. **锁等待超时**：`innodb_lock_wait_timeout`（默认 50s），超时抛 `Lock wait timeout exceeded`。
     - 生产上常把它调小（10s）以快速失败，但要注意**别设得比业务重试窗口还短**。
  2. **死锁检测**：InnoDB 会周期性构造**等待图（wait-for graph）**，若发现环就回滚**代价最小**的事务（通常是 undo 记录最少的那个），抛 `Deadlock found when trying to get lock`。
    - ⚠️ 常见误解：被回滚的不一定是「后到的那个」；MySQL 选的是**回滚代价最小**的 —— 于是一个小事务也可能因为「持有锁少」而被选中。
- 关于死锁检测的性能：大量等待同一行时，检测本身有成本；`innodb_deadlock_detection=OFF` 可以关掉（用超时兜底），高并发热点行场景有时会这么做。

### 22.7 死锁：典型场景与规避

经典的两事务交叉（教学示意，不参与构建）：

```text
T1: UPDATE t SET a=1 WHERE id=1;   -- 锁住 id=1
T2: UPDATE t SET a=1 WHERE id=2;   -- 锁住 id=2
T1: UPDATE t SET a=1 WHERE id=2;   -- 等 T2
T2: UPDATE t SET a=1 WHERE id=1;   -- 等 T1  → 成环，死锁
```

- 规避手段：
  1. **按固定顺序访问**（所有代码路径都先小 id 后大 id）；
  2. **拆分事务**（把长事务里的每步都单独提交，降低持锁时间）；
  3. **减少锁范围**（确保走索引，避免无谓地把大片区间锁住）；
  4. **应用层重试**（死锁是**可重试**的失败，必须捕获 `1213` 并重放）；
  5. 🔧 **用锁友好的 SQL 表达意图**（如 `UPDATE ... WHERE ... ORDER BY ... LIMIT`，或队列场景用 `SKIP LOCKED`）。
- 关于日志：`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段可看到最近一次死锁的两边事务 SQL —— 生产上建议长期收集，它是免费的架构体检报告。

### 22.8 锁的观测（🔧 8.0 已换血）

| 对象 | 版本 | 用途 |
| --- | --- | --- |
| `information_schema.INNODB_LOCKS` / `INNODB_LOCK_WAITS` | 5.7 及以前 | 锁与等待，`SHOW ENGINE INNODB STATUS` 同源 |
| **`performance_schema.data_locks`** | **8.0 起** | 取代 `INNODB_LOCKS`，**能看到间隙锁/next-key 的具体区间** |
| **`performance_schema.data_lock_waits`** | **8.0 起** | 取代 `INNODB_LOCK_WAITS` |
| `SHOW ENGINE INNODB STATUS` | 各版本 | 最近死锁详情、锁等待统计 |
- 🔧 **排查组合拳**（8.0）：
  ```sql
  -- 教学示意，不参与构建
  SELECT * FROM performance_schema.data_locks WHERE lock_status = 'WAITING';
  SELECT * FROM performance_schema.data_lock_waits;
  ```
  `data_locks` 的 `lock_type` / `lock_mode` / `lock_data` 能直接告诉你是 `X, gap` 还是 `X`，以及锁的是哪个区间 —— 这是「为什么我这条语句锁了这么多行」的唯一准确答案。

### 22.9 🔧 2026 视角：锁的语义已能用 SQL 表达

| 新增能力 | 版本 | 意义 |
| --- | --- | --- |
| **`FOR UPDATE SKIP LOCKED`** | 8.0.0 | 「队列抢任务」的标准解法：跳过被别人锁住的行，**不必再用手写 `WHERE id NOT IN (...)` 或 `GET_LOCK()` 模拟** |
| **`FOR UPDATE NO WAIT`** | 8.0.0 | 拿不到锁立刻失败，而不是排队 50 秒 |
| **`FOR SHARE`** | 8.0.0 | `LOCK IN SHARE MODE` 的更清晰别名 |
| **🔧 `NULLS NOT DISTINCT`** | 8.0.0 | 唯一索引允许出现多个 `NULL`（SQL 标准里 NULL 不相等导致唯一约束失效），可用于「打平可空业务键」的唯一性约束 |
| **🔧 间隙锁与 audit 插件** | 8.0 | 第三方审计插件（如企业版审计）会在原语句外额外执行查询，可能**额外加间隙锁**，造成「只读审计开了之后 DML 死锁变多」的现象 |
| **🔧 PostgreSQL 对照** | — | PostgreSQL 也有行锁 S/X、`FOR UPDATE` / `FOR SHARE`（并额外支持 `FOR NO KEY UPDATE`、`FOR KEY SHARE` 更细粒度），但**没有 next-key 锁**，幻读要靠 SSI 或显式谓词锁解决 —— 两个系统在「RR 到底锁了什么」上的差异是面试与迁移双方都该知道的 |

- `SKIP LOCKED` 的典型用法（教学示意，不参与构建）：
  ```sql
  UPDATE task SET owner = 'me', status = 'RUNNING'
  WHERE status = 'PENDING' AND owner IS NULL
  ORDER BY id
  LIMIT 10
  FOR UPDATE SKIP LOCKED;
  ```
  多个 worker 并发执行也不会互相阻塞 —— 这是 2020 年之前只能靠应用层分布式锁实现的语义。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：**无锁/乐观路线对锁的替代**（SSI、OCC 复兴、CockroachDB 的 read intent）；**细粒度锁与索引设计的关系**（Bw-tree 的 latch crabbing、Masstree 的乐观前缀锁）；**队列/工作窃取场景下 `SKIP LOCKED` 式的语义**从数据库扩展到消息系统（RocketMQ/Kafka 的消费位点语义）；** hibernal 的锁等待与尾延迟**（锁等待是 p99 抖动最大的单一来源之一，SLO 治理里常先治理锁）。
- **工业界开源**（star 数 2026-09-25 通过 `gh api` 实测）：
  - `mysql/mysql-server`（≈12.4k★）：锁实现 `storage/innobase/lock/lock0lock.cc`（`lock_rec_lock`、`lock_rec_insert_check_and_lock`、`lock_rec_lock_fast`）；死锁检测 `lock0deadlock.cc`。
  - `postgres/postgres`（≈22.2k★）：`src/backend/storage/lmgr/lock.c` 与 `predicate.c`，**锁 + SSI 双保险**，是「MySQL 该往哪补语义」的主要参照。
  - `pingcap/tidb`（≈40.6k★）：悲观/乐观事务模式，`FOR UPDATE` 语义跨节点；5.0 起默认悲观 + 分布式死锁检测。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「InnoDB 是行锁，不会锁表」 | 无索引 DML 会锁大量/全部行，效果等同表锁 |
| 2 | 「next-key 锁锁的是我 `WHERE` 里的那几行」 | 它锁的是**索引区间**（记录 + 前面的间隙），覆盖面比条件大 |
| 3 | 「死锁一定回滚后到的那个事务」 | 选的是**回滚代价最小**的（undo 记录数最少） |
| 4 | 「`SHOW ENGINE INNODB STATUS` 就够排查了」 | 8.0 要看 `performance_schema.data_locks`，才能看到**具体区间** |
| 5 | 「把 `innodb_lock_wait_timeout` 调小就安全了」 | 超时只是兜底；大量超时说明是设计问题（锁范围/顺序） |
| 6 | 🔧 **本书未覆盖** | 原书基于 5.7.22，**没有** `SKIP LOCKED` / `NO WAIT`（8.0）—— 队列/任务表场景的语义已可通过 SQL 直接表达；**没有** `NULLS NOT DISTINCT` |
| 7 | 🔧 **本书未覆盖** | **`performance_schema.data_locks` 取代 `innodb_locks`**（8.0）；第三方 **audit 插件带来的额外间隙锁**导致的死锁增多，也是 2020 年后新出现的坑 |
| 8 | 🔧 **本书未覆盖** | **MySQL 与 PostgreSQL 在 next-key 锁 / SSI 上的语义差异** —— 迁移项目里最常见的一类「现象相同、原因不同」 |
