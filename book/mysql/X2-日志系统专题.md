# 日志无缝连接——binlog / redo log / undo log 三套日志的职责、落盘与协作

> 原书对应：本书第 13 章讲的是「InnoDB 统计数据是如何收集的」，而 **binlog / redo log / undo log 三套日志的协作**是原书第 13、19、20、22 章的贯穿主线，但没有一章把它们放在一起讲。本文件按主题聚合这一主线，并补齐 2020 年之后（8.0/8.4 时代）必须补的**组提交、无锁 log buffer、Clone 应用 redo** 等内容。

## 本章地图

> 一句话：**undo 保证「能回滚」，redo 保证「不丢」，binlog 保证「能复制与恢复历史」；三者通过一个两阶段提交串起来，通过「组提交」把 fsync 的代价摊薄。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 13.1 三套日志对照 | 层面、内容、生命周期、落盘时机 | 一个事务最多只与 redo 强相关，binlog 是可选的「归档」 |
| 13.2 binlog（归档日志） | STATEMENT/ROW/MIXED、事件结构、GTID、历史文件 | 复制与 PITR 的唯一来源；**默认 8.0 起 `log_bin=ON`** |
| 13.3 redo log（重做日志） | 循环写、mtr、LSN、WAL、`innodb_flush_log_at_trx_commit` | 崩溃恢复靠它；容量固定（8.0 起可动态调） |
| 13.4 undo log（回滚日志） | 逻辑撤销、回滚段、版本链、purge | 原子性与 MVCC 读视图的共同基础 |
| 13.5 两阶段提交（内部 XA） | `prepare` → 写 binlog → `commit` | 这是「redo 已落盘但 binlog 未写」能自愈的关键 |

## 核心精讲

> **教学示意，不参与构建。** 下文为讲清职责边界而做的结构示意与 `--` 片段，**均未在本机编译、未启动任何 MySQL 实例执行**；参数名与默认值随版本变化，请以官方文档为准。

### 13.1 三套日志：先看谁管什么

| 维度 | binlog | redo log | undo log |
| --- | --- | --- | --- |
| 全称 | Binary Log / 归档日志 | Redo Log（重做日志） | Undo Log（回滚日志） |
| 所属 | **MySQL Server 层**（与引擎无关） | InnoDB 引擎层 | InnoDB 引擎层 |
| 内容 | 逻辑/半逻辑的「改动语句或行镜像」序列 | 物理页改动的**增量**（page-oriented，含 LSN） | **逻辑**撤销语句 + 版本链节点 |
| 生命周期 | 滚动文件（可永久保留，注意磁盘） | **循环覆盖写**（大小固定、写满则推进 checkpoint） | 提交后由 purge 线程回收（长事务会拖住） |
| 主要用途 | 复制、PITR、审计 | **崩溃恢复**、页修复 | **回滚（原子性）**、MVCC 读快照 |
| 谁消费 | 从库 IO/SQL 线程、`mysqlbinlog` | 崩溃恢复（& 克隆/Buffer Pool 预热） | `ROLLBACK`、一致性读、 early lock release |
| 是否必须 | 可关（但 8.0 默认开） | 必须 | 必须 |

### 13.2 binlog：复制与恢复的「存档」

- **三种格式**（原书第 13 章提到过 MIXED）：
  - `STATEMENT`：记 SQL 原文。体积小，但存在「不确定函数」（`SYSDATE()`、`UUID()`、`NOW()` 在不同机器）导致主从不一致。
  - `ROW`：记**每行的前后镜像**。最安全，8.0 默认；代价是体积大、`binlog_row_image` 配置影响行镜像范围（`minimal`/`full`/`noblob`）。
  - `MIXED`：默认 former，优化器决定。
- **事件结构**（简化示意，不参与构建）：
  ```text
  [ event header: timestamp, event_type, server_id, end_log_pos, flags ]
  [ event body:    depends on event_type ]
  ```
  常见事件类型：`FORMAT_DESCRIPTION_EVENT` / `QUERY_EVENT` / `TABLE_MAP_EVENT` / `WRITE_ROWS_EVENT` / `UPDATE_ROWS_EVENT` / `XID_EVENT` / `GTID_LOG_EVENT`。
- **GTID**（5.6 引入，8.0 默认 `gtid_mode=ON`）：`server_uuid:transaction_id`，**不再依赖 file/pos**，主从切换与故障自动接管会简单一个量级。
- 🔧 **8.0 的 binlog 变体**：`binlog_transaction_compression`（8.0.14）可对事务正文压缩；`Transaction_payload_events` 把整段事务打包；`RESET MASTER TO`、可设置的 `GTID_PURGED`、binlog 加密与压缩，都改变了「备份 + 恢复」的手感。

### 13.3 redo log：InnoDB 的「账本」

- **形态**：一组固定大小的物理文件（`ib_logfile0/1`，8.0.11 之前），循环写，写满就回头覆盖最老的 —— 所以**redo 只覆盖上一次 checkpoint 之后的那段近期历史**，全部历史靠 binlog。
- **WAL（Write-Ahead Logging）**：**先写日志、再改页**。内存里改页可以慢慢来，但日志必须按 LSN 顺序持久化。
- **mtr（mini-transaction）**： redo 与页修改的**原子单位**。一个 `UPDATE` 产生的页改动 + 对应 redo 记录，属于同一个 mtr；mtr 内的 redo 要么一起生效、要么一起不生效（原书第 19 章详述）。
- **LSN**：redo 里单调递增的字节偏移。**LSN 就是 InnoDB 的时间轴**，checkpoint 推进 = 记录「哪些页的 redo 已经落盘」。
- **落盘开关**：`innodb_flush_log_at_trx_commit`
  | 值 | 行为 | 掉电风险 |
  | --- | --- | --- |
  | 1（默认） | 每次事务提交都 fsync | 无 |
  | 2 | 写 OS cache，每秒 fsync | 掉电丢最近 1 秒 |
  | 0 | 每秒写+fsync | 掉电丢最近 1 秒 |
  🔧 8.4 起 `innodb_flush_log_at_trx_commit` 默认值仍是 1，但二进制包/发行版（如某些发行版）可能改过，**上线前务必核对实际值**。
- 🔧 **容量可动态调节**：8.0.11 起引入 `innodb_redo_log_capacity`，`innodb_log_file_size` / `innodb_log_files_in_group` 被废弃；可以在线扩容/缩容 redo 而不必重启（缩容受「当前 redo 使用量」限制）。**redo 太小 = 高频 checkpoint = 写入抖动**，是大促场景的经典故障。

### 13.4 undo log：回滚与多版本的地基

- **形态**：逻辑日志（记「怎么撤销」）+ 存放在回滚段（rollback segment）里的链式结构。
- **原子性**：`ROLLBACK` 时顺着 undo 链反向执行。
- **MVCC**：一致性读（快照读）**顺着 roll_pointer 链**往前找可见版本 —— 也就是说 **`SELECT` 读历史数据靠的是 undo，不是 redo**。
- **purge**：提交后 undo 不能立刻删（还有快照可能要读），由后台 purge 线程在**最老活跃 read view 之后**回收。🔧 **长事务会卡住 purge → undo 膨胀 → 表空间暴涨**，这是线上最常见的 undo 事故，且和「备份过程中开事务」强相关。
- 详见 `20-undo日志.md`。

### 13.5 两阶段提交：redo 与 binlog 的原子性协调

一个开启 binlog 的事务提交路径（教学示意，不参与构建）：

```text
1) InnoDB prepare：写 redo（含 prepare 标记），按 innodb_flush_log_at_trx_commit 决定是否 fsync
2) 写 binlog（cache → 文件，按 sync_binlog 决定是否 fsync）
3) InnoDB commit：写 redo commit 记录，释放锁，标记事务结束
```

- **崩溃发生在 1 与 3 之间**：恢复时，那些「prepare 了但没 commit」的事务，要去 binlog 里查有没有对应记录 —— **有则补提交，无则回滚**。
  - 这就是「内部 XA（2PC）」，由 `binlog` 作为**协调者**，InnoDB 作为**参与者**。
  - 原书第 19 章把 redo 讲成「说过的话一定要做到」，这里的 2PC 正是「说到一半能不能反悔」的答案。
- 这个模型也解释了**为什么关掉 binlog 可以明显提速**：少了一次 prepare/写盘协调。

### 13.6 组提交：把 fsync 摊薄的胜利

- **问题**：如果每个事务都「写 redo → fsync → 写 binlog → fsync」，一个 fsync 约 0.1–10ms，QPS 就被 fsync 数锁死。
- **解法（组提交 / group commit）**：让一批事务**共用一个 fsync**。
  - **binlog 组提交**：lead 事务收集同批次的 followers，统一写盘、统一 fsync，再让各自继续。
  - **redo 组提交**：同批次的事务 redo 一起写盘。
  - 5.7 之后把 binlog 组提交拆成三个阶段（flush / sync / commit），允许不同阶段有不同的事务集合，**并发度大幅提升**。
- 🔧 相关参数：`binlog_group_commit_sync_delay`（主动延迟多少微秒以攒更多事务）、`binlog_group_commit_sync_no_delay_count`（攒够多少个就不等延迟）。**这是唯一一种「主动加延迟换吞吐」的手段**，常用于从库/批量导入。
- 🔧 8.0 之后：redo 侧有独立的写线程组（`innodb_log_writer_threads`）与**lock-free 的 log buffer 写入**（多事务并发写 log buffer 不再需要互斥锁），binlog 侧则由 Group Replication 的 writeset 依赖追踪进一步细化了并行度（见 `binlog_transaction_dependency_tracking`）。

### 13.7 持久性矩阵：`sync_binlog` × `innodb_flush_log_at_trx_commit`

| `sync_binlog` | `innodb_flush_log_at_trx_commit` | 持久性 | 典型场景 |
| --- | --- | --- | --- |
| 1 | 1 | 最强（宕机不丢已提交） | 金融/订单主库 |
| 1 | 2 | 掉电可能丢最近 1 秒的已提交事务 | 可接受抖动的业务库 |
| 0 | 0 | 最弱（崩溃丢 1 秒） | 仅只读库/离线分析从库 |
| N > 1 | 1 | 折中，binlog 每 N 次 fsync | 老版本常见配置 |

> 注：本表是**配置学**结论，不是实测数据；实际行为受文件系统、磁盘写缓存（`innodb_flush_method` / `O_DIRECT`）、RAID 电池等影响。

### 13.8 🔧 三套日志的容量与磁盘规划

| 日志 | 容量来源 | 满了会怎样 |
| --- | --- | --- |
| binlog | `max_binlog_size`（默认 1GB）+ 保留策略 | `expire_logs_days` / `binlog_expire_logs_seconds`（8.0）到期自动清理；磁盘满则写入失败 |
| redo | 🔧 `innodb_redo_log_capacity`（8.0.11 起可在线调） | checkpoint 不推进 → **写入卡死** |
| undo | 回滚段 + 历史链表长度（由 purge 决定） | 长事务卡 purge → 文件撑满 |

- 一个务实的容量直觉（教学示意，不参与构建，需按实际环境验证）：
  - **redo 太小**：checkpoint 高频触发，写入吞吐出现周期性抖动；
  - **redo 太大**：崩溃恢复要重放更长的窗口，RTO 变差；
  - **binlog 保留过久**：磁盘增长但 PITR 粒度更细，需要权衡；
  - **undo 膨胀**：先解决「最老活跃事务」， undo 不会立刻缩小。

### 13.9 🔧 日志与备份/PITR 的组合

| 恢复目标 | 需要什么 | 步骤要点 |
| --- | --- | --- |
| 掉电/崩溃 | binlog（可选）+ redo + doublewrite | 崩溃恢复自动完成，通常无需人工介入 |
| 误删数据（回到 5 分钟前） | 物理/逻辑备份 + binlog | 备份恢复 → 从备份时刻的 binlog 位置回放 |
| 主库损坏需换一台 | 备份 + 克隆/GTID | 🔧 Clone + binlog 追平 |
| 想「只要某几行」 | binlog 事件（`mysqlbinlog` 解析） | 逻辑级精细恢复，代价最高 |
- 一句话：**没有经过「从备份恢复」演练的备份等于没有备份**；PITR 演练同时验证了 binlog 是否完整、时区与 GTID 是否一致。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：**组提交 / 批量 fsync 的极限优化**——从单机数据库一路延伸到存储引擎内部（RocksDB 的「Durability for Free」，OSDI 2016，用批量组提交把 WAL 的 fsync 成本压到接近零）；**存算分离下的日志下沉**（Aurora「日志即数据库」、PolarDB 的日志上推 redo 到共享存储），本质是「把 redo 当成为存储层写的连续流」；**可信执行/PMem 场景下的 WAAL（write-ahead anywhere logging）**，让 redo 可以直接写在持久内存上，省掉一次拷贝。
- **工业界开源**（star 数 2026-09-25 通过 `gh api` 实测）：
  - `mysql/mysql-server`（≈12.4k★）：binlog 实现 `sql/log_event.cc` / `sql/binlog.cc`；InnoDB redo `storage/innobase/log/`；undo 与 purge `storage/innobase/rem/rectuple.c` 同目录的 `trx/` 下。
  - `facebook/mysql-8.0`（≈115★）：Facebook 分支在 **binlog 组提交、多线程复制、Tokudb 兼容**上的大量工程补丁，是「组提交怎么做到极致」的最佳样本。
  - `percona/percona-server`（≈1.3k★）：`percona-server` 版本常带 `log_warnings`、`binlog` 相关的额外开关与审计插件。
  - `pingcap/tidb`（≈40.6k★）与 `cockroachdb/cockroach`（≈32.5k★）：把 redo（raft log / write-ahead）与共识协议绑成一体的现代形态，**组提交在这里变成了「共识层的一次持久化 + 一次复制」**。
  - `postgres/postgres`（≈22.2k★）：WAL + 全量/增量备份的 PITR 模型与 MySQL「binlog + redo 两段」的差别，值得对照。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「binlog 和 redo 都是日志，可以互相替代」 | 层不同（Server 层 vs 引擎层）、用途不同（复制/PITR vs 崩溃恢复），且**只靠 redo 无法做 PITR** |
| 2 | 「redo 是无限的增长的持久化日志」 | redo 是**循环覆盖**的，只覆盖 checkpoint 之后的窗口；历史只能靠 binlog |
| 3 | 「redo 里存的是 SQL 语句，所以是逻辑日志」 | InnoDB redo 是**物理页增量**（含 LSN），undo 才是逻辑日志 |
| 4 | 「事务提交后 undo 就没用了，可以立刻删」 | 还有 read view 可能读它；purge 受最老活跃事务限制（长事务 → undo 膨胀） |
| 5 | 「关掉 binlog 就没日志了」 | redo/undo 仍在，崩溃恢复与 MVCC 照常工作，只是没有复制与 PITR 能力 |
| 6 | 🔧 **本书未覆盖** | 原书基于 5.7.22，**组提交的三阶段拆分、`sync_binlog`×`innodb_flush_log_at_trx_commit` 矩阵、8.0 无锁 log buffer 与 redo 子线程、`innodb_redo_log_capacity` 动态容量、Clone Plugin 应用 redo、8.0 默认开启 binlog/GTID**，均需按本节补齐 |
| 7 | 🔧 **本书未覆盖** | 「组提交为什么能提升吞吐」「writeset 依赖追踪与并行复制的关系」在 2026 已是 DBA 面试与调优的必答题 |
