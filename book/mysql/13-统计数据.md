## 本章地图

> 一句话：**优化器的每一个判断都由统计信息喂出来，而这些数字本身是「采样的估计值」——
> 于是「慢查询」常常不是 SQL 写坏了，而是**「草料」过期了**：表还是那张表，行数还是那个估算，只是它已经不像今天的这张表了。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 13.1 两层统计：引擎侧与 Server 侧 | InnoDB 统计 vs 优化器统计；谁用在哪 | 引擎统计管「页/行怎么落」，优化器统计管「走哪条路」 |
| 13.2 持久化统计在哪 | `innodb_table_stats` / `innodb_index_stats` 两张表及其字段 | 统计**持久化在 `mysql` 库里**，重启不丢（8.0 默认） |
| 13.3 `n_rows` 与 `index_size` 怎么估出来 | 采样页数 × 平均行长；`index_size` 的单位是页不是字节 | **两者都是估算**，误差随采样页数下降而放大 |
| 13.4 `ANALYZE TABLE` 的四种形态 | 普通、`PERSISTENT`、`ESTIMATE_ONLY`、`MODIFY` + 采样页数 | 采样页数是「精度 vs 代价」的旋钮 |
| 13.5 自动重算的触发线 | `stat_modified_counter` 与 `16 + n_rows/16` | 声明一行不那么激进，**统计腐化是渐进的** |
| 13.6 统计不准 → 慢查询的四种典型形态 | 驱动表选错、范围估算失真、覆盖索引失效、`JOIN` 顺序翻转 | 每一种都有可对照的 `EXPLAIN` 指纹 |
| 13.7 直方图（🔧 8.0） | `ANALYZE ... UPDATE HISTOGRAM ON col WITH n BUCKETS`、列数、适用场景与边界 | 直方图专治「等值/范围谓词的选择性失真」 |
| 13.8 发现与回归：一套可执行的流程 | 慢日志 → `EXPLAIN` 估算/实际差 → `ANALYZE` → 再验证 → 写进 SOP | 把「刷新统计」变成定期任务与告警项 |
| 13.9 🔧 2026 视角 | 8.0 更完整的持久化统计、直方图、多列统计方向、9.x | 5.7 的「采样即估计」模型仍是主干 |

## 核心精讲

> **教学示意，不参与构建。** 下文所有 `--` 片段与结构示意**未在本机编译、未连接任何 MySQL 实例执行**；
> 字段名、默认值随版本变化，请以官方文档与 `SHOW` 类命令的当版输出为准。

### 13.1 两层统计：不是一回事

| 层 | 服务于谁 | 典型内容 |
| --- | --- | --- |
| 引擎侧（InnoDB） | 存储引擎的分配与刷盘决策 | 页用量、段/区分配、change buffer 可用性、undo 长度 |
| 优化器侧（Server） | 成本模型的选择性估算 | 表行数、索引基数、选择性、直方图 |

- 本章讨论的是**优化器侧统计**；它最终会体现在 `EXPLAIN` 的 `rows` 与 `key`（见 `15-EXPLAIN详解.md`）。
- 🔧 一个常见错觉：`information_schema.tables.TABLE_ROWS` 与 `SHOW TABLE STATUS` 的 `Rows`
  **读的都是优化器侧的估算值**，不是精确计数；要精确值得自己 `COUNT(*)`（代价另论）。

### 13.2 持久化统计住在哪里

InnoDB 把统计「持久化」（persistent）到 `mysql` 库的两张表里（教学示意，不参与构建）：

| 表 | 关键字段 | 含义 |
| --- | --- | --- |
| `innodb_table_stats` | `database_name`、`table_name`、`last_update`、`n_rows`、`cluster_index_size`、`sum_of_other_index_sizes` | 表级：估算行数 + 聚簇索引估算页数 |
| `innodb_index_stats` | `database_name`、`table_name`、`index_name`、`last_update`、`n_rows`、`index_size`、`stat_modified_counter`、`sample_size` | 索引级：每个索引的估算页数 + `stat_modified_counter` |

两个版本事实：

- 5.6 默认**非持久化**（`innodb_stats_transient`），统计在内存里、重启即失；
  🔧 8.0 默认**持久化**（`innodb_stats_persistent=ON`），重启后优化器仍看得到旧估算。
- 持久化统计带来的副作用：**「数据全删了但优化器还以为很大」**——因为行数不会随着 `DELETE`/`TRUNCATE` 立刻刷新到新值，
  这类「删完之后更慢了」的现象常被误判成优化器有 bug。

### 13.3 `n_rows` 与 `index_size`：采样出来的估计值

**`n_rows` 的估算路径**（示意，不参与构建）：

```text
随机采样 N 个叶子页（N ≈ innodb_stats_persistent_sample_pages，默认 20）
  → 统计这些页里的实际行数与平均行长
  → 用「平均行长」 × `n_rows` 反推整表估算行数
  → 也用它估算每个索引的页数（index_size）
```

三个必须知道的推论：

1. **默认只采 20 个页**：表越大、行越参差，误差越大。1000 万行的表用 20 页估算，误差可能到数倍。
2. 一旦行的长度差异变大（有的行装 100 字节、有的装 3000 字节），「平均行长」就不是好估计，误差来源从「行数」变成「长度分布」。
3. `index_size` 的单位是**页**，不是字节；想换算成字节要乘 `innodb_page_size`。**它是估算值，不是 `du` 看到的真实值。**

### 13.4 `ANALYZE TABLE` 的四种形态

| 写法（示意） | 作用 | 适用 |
| --- | --- | --- |
| `ANALYZE TABLE t` | 重算并持久化统计 | 低峰期的常规操作 |
| `ANALYZE TABLE t PERSISTENT` | 即便 `innodb_stats_persistent=OFF` 也强制持久化 | 想立刻固化统计但默认关着 |
| `ANALYZE TABLE t ESTIMATE_ONLY` | 只刷新「估算」而不取更精确样本 | 想快速看数 |
| `ANALYZE TABLE t MODIFY` | 只更新内存里的统计 | 从库/只读实例上做最小影响刷新 |

- 你也可以用 `ANALYZE TABLE t PERSISTENT=32` 这类写法**显式指定采样页数**（不同版本的语法细节不同，🔧 以官方语法为准）。
- **代价认知**：采样页数越多越准、越慢；默认是「够用就好」，不是「越准越好」。
- 注意 `ANALYZE` 是**不可回滚的非事务操作**，而且会短暂触及元数据/采样工作；批量刷新时请分批、在低峰执行。
  它是否同步到从库随版本与参数而异（🔧 请核对官方 `ANALYZE TABLE` 条目与 binlog 相关说明）。

### 13.5 自动重算：有一条「溢出线」

InnoDB 用一个计数器防止统计无限腐化（示意，不参与构建）：

```text
每次改动行时 stat_modified_counter += 改动行数
当 stat_modified_counter > 16 + n_rows / 16 时，
  在「表第一次被访问」时触发一次统计重算（受 innodb_stats_auto_recalc 控制）
```

- 这条线的意思是：**大约每 1/16 的行发生变化就可能刷新一次**，不是「每 1/16 行立刻刷新」。
- 副作用：一次批量导入（比如插入 500 万行）可能触发一连串的重算，导完立刻做一次 `ANALYZE` 反而更省事。
- 大表上自动重算还受「最近是否重算过」的抑制，所以**「导完数据后的第一个查询特别慢」**几乎是必然事件。

### 13.6 统计不准 → 慢查询：四种可复现的形态

| 形态 | 统计失真点 | `EXPLAIN` 指纹 |
| --- | --- | --- |
| 驱动表选错 | 表 A 实际只有 100 行，`n_rows` 却是 100 万 | `rows` 与实际差一个数量级；`type=ALL` 出现在不该出现的位置 |
| 范围估算偏差 | 等值/范围谓词选择性被当成均匀分布 | `type=range` 但 `key_len` 偏大、`rows` 与实际差很远 |
| 覆盖索引被判「贵」 | 索引估算页数失真 | `Extra` 里本该有的 `Using index` 消失，改成全扫 |
| `JOIN` 顺序翻转 | 中间表行数估少 | 计划与业务直觉相反，改一行 SQL 就「好了」（假象） |

- 一个反直觉的坑：**统计过期不是一定变慢，也可能变快**——
  行数被估大 → 索引路线被判贵 → 走全扫 → 数据其实变少了，于是「全扫比索引快」，观感上像是优化器在偷懒。
- 排查顺序（呼应 `12-基于成本的优化.md`）：
  `EXPLAIN` 看计划 → `optimizer_trace` 看 `rows_estimated` vs `rows_actual` → 确认是否该 `ANALYZE` → 再谈调参与提示。

### 13.7 直方图：8.0 给统计补的那块拼图

- 🔧 **什么是直方图**：对指定列做**分桶**（bucket）统计，让优化器知道「值不是均匀分布」这一事实。
  ```text
  ANALYZE TABLE t UPDATE HISTOGRAM ON c1, c2 WITH 100 BUCKETS;   -- 示意，未执行
  ANALYZE TABLE t DROP HISTOGRAM ON c1;
  SELECT * FROM information_schema.COLUMN_STATISTICS;             -- 8.0 起可见
  ```
- **它解决什么**：等值与范围谓词的选择性估算。均匀分布假设下 `col = 'X'` 总是估「总行数/不同值数」，
  而真实数据可能 90% 的行都是 `'X'`。直方图能让优化器看到这个偏差。
- **它的边界**（很重要）：
  - 只覆盖**等值/范围**谓词，不直接服务于连接基数（连接基数仍靠索引基数估算）；
  - 桶数有上限（🔧 官方上限约 1020，以当版文档为准），列值分布极 skew 时也要挑列；
  - 直方图在 `mysql` 库里持久化，也会有「数据变了直方图没变」的同样问题，批量写入后需要重新 `ANALYZE`；
  - 只对**比值/选择性估算**生效，不保证优化器一定采纳对应路线。
- 实践：优先在**连接列之外的过滤列**、数据 skew 明显的列、以及 `EXPLAIN` 里估算/实际差得最厉害的列上建直方图。

### 13.8 一套可执行的统计运维流程

| 步骤 | 动作 | 判据 |
| --- | --- | --- |
| 1. 发现 | `pt-query-digest` / 慢日志聚合出指纹 | 出现「同一 SQL 忽快忽慢」 |
| 2. 定位 | `EXPLAIN` + `optimizer_trace`（估算 vs 实际） | `rows_estimated` / `rows_actual > 10` 倍 |
| 3. 刷新 | `ANALYZE TABLE`（必要时指定更多采样页） | 刷新后再跑一次同 SQL |
| 4. 加固 | 该列建直方图 / 补索引 / 改统计行数阈值 | 计划稳定 |
| 5. 防回归 | 批量导入/大促后纳入定时任务；把计划纳入回归基线 | 定期抽检 `n_rows` 与实际量级的偏离 |

> 一句话经验：**「统计」不是一次性动作，而是和「数据增长」同生命周期的运维对象**；
> 在 2026 年依然成立的最小实践是：导入后主动 `ANALYZE`、把慢查询的估算/实际比值做成指标。

### 13.9 🔧 2026 视角：统计子系统补了什么

| 能力 | 版本 | 意义 |
| --- | --- | --- |
| 持久化统计默认开启 | 🔧 8.0 | 重启不丢，但「删了数据行数不降」的新坑随之出现 |
| 直方图 | 🔧 8.0 | 选择性估算摆脱「均匀分布」假设 |
| 更完整的采样控制 | 🔧 8.0 | 采样页数、持久化开关可更细地按表配置 |
| 多列统计方向 | 🔧 研究/各发行版演进中 | 单列统计对「组合谓词」仍会复合放大误差 |
| 9.x 动向 | 🔧 待官方定稿 | 生产选型请以当版官方文档与 release notes 为准 |

仍需注意：**直方图不等于万能**，连接基数、分组基数、以及「统计与数据不同步」的问题，仍要靠 `ANALYZE` 与流程保障。

## 近年研究与工业界开源实践（2015–2026）

- **研究主线**：**基数估算**仍是「优化器的第一短板」；2020 年代的重点是**学习型估算**（模型替代直方图/采样）与
  **运行时反馈回路**（把 `EXPLAIN ANALYZE` 的实测行数回流给优化器），而非单纯提高采样精度。
- **工业界做法**：把「估算/实际行数比」做成**指标**——超过阈值即触发 `ANALYZE`，
  把「统计腐化」从「偶发慢查询」变成「可观测、可收敛」的运维对象。
- **工业界开源**（star 数 2026-09-25 通过 `gh api repos/OWNER/REPO --jq '.stargazers_count'` 实测）：
  - `mysql/mysql-server`（**≈12.4k★**）：统计表与采样逻辑在 `storage/innobase/dict/` 与 `sql/`，直方图在 Server 层的统计模块。
  - `percona/percona-toolkit`（**≈1.55k★**）：`pt-index-usage`、`pt-query-digest` 是**发现**统计问题的常用入口。
  - `mariadb/server`（**≈8.27k★**）：统计与直方图实现的独立分支，可作横向对照。
  - `postgres/postgres`（**≈22.2k★**）：`pg_statistic` + 直方图/MCV 的成熟选择性估算，是 MySQL 5.7 时期的最佳对照。
  - `pingcap/tidb`（**≈40.6k★**）：`statistics` 包提供直方图与多列统计，是「统计子系统该长什么样」的现代样本。
  - `clickhouse/clickhouse`（**≈50.1k★**）：`optimize` 前不做复杂选择性建模，用稀疏索引近似取代，是另一条路线。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「`information_schema.tables.TABLE_ROWS` 是被精确统计的」 | 它是**估算**（来自采样）；精确计数要 `COUNT(*)` |
| 2 | 「`index_size` 是字节数」 | 单位是**页**，需要乘 `innodb_page_size`；且是估算值 |
| 3 | 「跑了 `ANALYZE` 就一劳永逸」 | 统计是**随时间腐化**的对象，批量写入后需要重新评估 |
| 4 | 「统计只影响走不走索引」 | 它同时影响**连接顺序、连接算法、驱动表**，所以影响面是整体性能 |
| 5 | 「直方图能解决一切估算问题」 | 它主要覆盖等值/范围谓词；连接基数与「统计 vs 数据不同步」仍在原处 |
| 6 | 🔧 **本书未覆盖** | 原书基于 5.7.22，**没有** 8.0 的持久化统计默认值变化、**没有** 直方图、**没有** `information_schema.COLUMN_STATISTICS`、**没有**采样页数的按表配置 |
| 7 | 🔧 **本书未覆盖** | 「估算/实际比值」作为运维指标、以及导入后主动 `ANALYZE` 的 SOP，原书没有涉及 |
