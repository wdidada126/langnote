# 第 14 章 基于规则的优化

> 原书说明：标题为「基于规则的优化」，基于 MySQL 5.7.22 撰写。本文件按其思路展开
> **规则改写做了什么、改写如何改变候选路线、以及每一条规则什么时候有收益什么时候有风险**，
> 并补齐 8.0 的派生 CTE 物化、子查询策略选择等新变化。
>
> ⚠️ 本目录**不提供可运行的环境**：所有 SQL 与结构示意都是**教学示意，不参与构建**，未在本机编译、未连接任何 MySQL 实例执行。

## 本章地图

> 一句话：**规则优化不决定「哪条路线最便宜」，它决定「都有哪几条路线可选」。** 常量折叠、等值传播、外连接消除、
> 派生表合并、子查询转半连接——这些改写把 SQL 变成「等价但更好算」的形状；**`EXPLAIN` 看不到其中大部分痕迹**，
> 因为改写发生在优化器内部，只看结果会以为优化器「无视了你的写法」。

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 14.1 规则层在哪里 | 改写（逻辑层）→ 成本选路（物理层） | 规则决定候选集，成本决定赢家 |
| 14.2 常量折叠与条件简化 | `1=1` 折叠、永假条件识别、`COUNT(*)` 等常量改写 | 把「能在编译期算完的事」挪出执行期 |
| 14.3 等值传播与无效条件去除 | `a=b`、`b=c` 推出同族条件；无用条件直接删 | 让本来看不见的索引列变成可用条件 |
| 14.4 `HAVING` 与 `WHERE` 的边界 | 无聚合/无 `GROUP BY` 时 `HAVING` 下推到 `WHERE` | 条件越早被过滤，上层算子越便宜 |
| 14.5 外连接消除 | 「空值拒绝」条件出现时，`LEFT JOIN` 可降级为 `INNER JOIN` | 这是「明明写了左连接却像内连接一样执行」的原理 |
| 14.6 派生表合并 vs 物化 | `derived_merge` 的准入条件、`MERGE`/`NO_MERGE` 提示 | 合并能下推过滤、物化能去重一次算多次 |
| 14.7 子查询 → 半连接 | `firstmatch` / `loosescan` / `materialization` / `duplicateweedout` 四种策略 | 子查询结果不参与投影时，多半不该被物化成临时表 |
| 14.8 `NOT`/`ANY`/`ALL` 的转换与 NULL 陷阱 | `NOT IN` 转反连接的 NULL 安全前提 | 一个 NULL 就能让 `NOT IN` 返回空，改写必须谨慎 |
| 14.9 怎么看到规则做了什么 | `optimizer_trace` 的 transformation 轨迹 | `EXPLAIN` 看结果，`trace` 看改写过程 |
| 14.10 🔧 2026 视角 | 派生 CTE 物化、递归 CTE 解释器、8.0 优化器结构演进 | 「合并还是物化」从 5.7 起就是可切换的产品决策 |

## 核心精讲

> **教学示意，不参与构建。** 下文所有片段与结构示意**未在本机编译、未连接任何 MySQL 实例执行**；
> trace 中的轨迹字段名随版本可能不同，请以当版输出为准。

### 14.1 规则层与成本层的分工

```text
原始 SQL
   │
   ├─ 规则层（本章）：复用式改写，保持语义等价
   │     · 简化条件      · 传播等值      · 消除外连接
   │     · 合并/物化派生表 · 子查询转半连接 · 视图合并
   ▼
改写后的 SQL（逻辑上等价，形状更适合算）
   │
   └─ 成本层（第 12 章）：枚举访问方法 + 连接顺序，按成本取最优
```

- 关键：**规则改写是「白送」的优化，成本选路是「取舍」**。
  规则层应尽量多做（等价且降低代价），成本层只能在留下的选项里比。
- 反过来也成立：**规则不够激进，成本层就无米下锅**。
  例如子查询没转成半连接，优化器只能在「先物化一个临时表」这条路里挑。

### 14.2 常量折叠与条件简化

| 输入（示意） | 改写后 | 收益 |
| --- | --- | --- |
| `WHERE 1 = 1 AND a > 5` | `WHERE a > 5` | 少一次求值 |
| `WHERE updated_at > NOW()` 在可具体化场景 | 折叠为具体时间点 | 让条件变成「常量对列」的可用范围 |
| `WHERE status <> status` | 永假 | 计划直接变成「不可能命中」 |
| `COUNT(*)` 这类常量参数改写 | 计数改写为对常量行的计数 | 减少一次列求值 |

- 「永假」在 `EXPLAIN` 里会表现为 `Impossible WHERE` 之类的提示（见 `15-EXPLAIN详解.md` 的 `Extra` 列）——
  看到它说明优化器已经把整个条件判定为不可能，这是**最便宜的一次优化**。
- trace 里这类改写常出现在 transformation 列表中（字段名随版本不同，🔧 以当版输出为准）。

### 14.3 等值传播与无效条件去除

```text
WHERE a = b AND b = c AND c = 10
  → 传播后：a = 10 AND b = 10 AND c = 10
```

- 业务含义：**让「看不见的列」暴露成常量**。
  例如 `WHERE o.user_id = u.id AND u.id = 100`，传播后 `o.user_id` 变成常量 100，
  于是 `o` 上的 `user_id` 索引从「不可用」变成「`ref`/`const` 级别」。
- 「无效条件去除」则是把 `IS NOT NULL` 之类由类型/约束保证的条件直接删掉，减少执行期判断。
- 这类规则的价值常被低估：**它经常是「加了索引却还是全表扫」的唯一原因**。

### 14.4 `HAVING` 与 `WHERE`：下推的边界

- 聚合查询里，`WHERE` 在分组**前**过滤、`HAVING` 在分组**后**过滤——这是语义。
- 因此**只有不含聚合函数、也不依赖分组的列时**，`HAVING` 里的条件才能下推到 `WHERE`；
  否则下推会改变结果集（这是「下推条件必须满足等价性」的实例）。
- 下推的收益是数量级的：`HAVING` 过滤是**先分组再筛**（代价含分组），`WHERE` 过滤是**先筛再分组**。
  ```text
  SELECT dept, COUNT(*) FROM t WHERE dept = 'A' GROUP BY dept;   -- 等价且 cheaper
  SELECT dept, COUNT(*) FROM t GROUP BY dept HAVING dept = 'A';  -- 原写法
  ```

### 14.5 外连接消除：从 `LEFT JOIN` 到 `INNER JOIN`

```text
原写法：  SELECT ... FROM a LEFT JOIN b ON a.id = b.id WHERE b.name = 'x'
                ↑ b 是「可空侧」，但 WHERE 又要求 b.name 非空
改写后：  SELECT ... FROM a JOIN b ON a.id = b.id WHERE b.name = 'x'
```

- 判据叫**空值拒绝（null-rejecting）**：一旦对「可空侧」施加了非空的等值/范围条件，
  `LEFT JOIN` 就退化成 `INNER JOIN`（左表行若匹配不到 b，其 `b.name` 为 `NULL`，必被 `WHERE` 淘汰）。
- 收益巨大：**退化之后，b 侧就可以用等值访问方法（`ref`/`eq_ref`）甚至走索引**，
  而不是「先全扫 b 再补 NULL 行」。
- 反向提醒：**这解释了「我写了 LEFT JOIN，优化器却当成 INNER JOIN，导致结果行数变少」**。
  如果你的业务真的需要保留左表未匹配行，就要避免写出空值拒绝条件——
  用 `WHERE (b.name = 'x' OR b.name IS NULL)` 之类写法明确表达语义（代价是索引可能用不上）。

### 14.6 派生表：合并还是物化

| 维度 | 合并（`derived_merge`，MERGE） | 物化（MATERIALIZATION） |
| --- | --- | --- |
| 做法 | 把派生表「摊开」到外层查询里 | 先算一次派生表，写入临时表，再参与连接 |
| 适合 | 派生表只出现一次、且无聚合/`DISTINCT`/`GROUP BY`/`LIMIT`/`UNION` | 派生表在多层里被反复引用、或含聚合需要独立结果 |
| 好处 | 过滤条件可下推、避免临时表 | 只算一次，多个外层行复用 |
| 代价 | 有时合并后优化器反而看不清（5.7 时代的经典问题） | 有临时表与写入成本 |

- 关闭方式（示意，未执行）：`SET optimizer_switch='derived_merge=off'`，或用 `NO_MERGE(t@sel1)` 提示只关这一个。
- 🔧 **8.0 起 CTE 的处理更明确**：**CTE 默认按「物化」处理**（派生表仍可合并），递归 CTE 必须物化；
  想让 CTE 参与合并，写法上要满足与派生表同样的准入条件。**写 8.0 时的第一反应应该是「CTE 会不会被物化成一张临时表」**——
  这直接决定它是「优化」还是「负担」。

### 14.7 子查询转半连接：四种落地策略

当子查询不出现在 `SELECT` 列表里（`WHERE id IN (SELECT ...)`）时，最有效的改写是**转成半连接**：

```text
SELECT * FROM t1 WHERE id IN (SELECT id FROM t2);
  ≈ (半连接) 对 t1 的每一行，判断 t2 里是否存在匹配行，命中即停
```

四种策略与它们的性格（对照 `EXPLAIN` 的 `Extra` 文本）：

| 策略 | 含义 | 何时胜出 |
| --- | --- | --- |
| `FirstMatch` | 找到第一个匹配就停 | 选择性高、匹配行少 |
| `LooseScan` | 跳过重复值，避免重复探测 | 内层有索引且重复值多 |
| `Materialize` | 先物化内层结果集 | 内层很小、但被反复探测 |
| `DuplicateWeedout` | 复制外层行去重 | 需要「保留一次外层行」的精确语义 |

- 一条工程判断：**「子查询不参与投影」正是信号**——它只做存在性判断，
  把它物化成一张大临时表通常是最糟的选项之一。
- 注意 `EXPLAIN` 里你看到的表名读作 `<subquery2>` / `<derived2>` 时，说明这一支**确实走了物化**。

### 14.8 `NOT`、`ANY`、`ALL` 与 NULL 陷阱

- `NOT IN (子查询)` **不能直接**当成反连接，除非内层列保证 `NOT NULL`：
  ```text
  x NOT IN (SELECT y FROM t)   -- 只要有一个 y 为 NULL，整个表达式就是 UNKNOWN
                               -- 结果集为空，而不是「不匹配的行」
  ```
  改成 `NOT EXISTS` 或明确加 `NOT NULL` 条件，才能安全转成反连接（anti-join）。
- `ANY/ALL` 通常转成「与 min/max 比较」，且同样要处理 NULL：
  `x > ALL (...)` 等价于 `x > MAX(...)` 且结果非空。
- 工程含义：**`NOT IN` 一旦踩到 NULL，表现为「SQL 突然返回空集」，看起来像数据丢了**；
  这是最经典的「改写条件触发 NULL 语义」事故，排查时先查列的可空性。

### 14.9 怎么看到规则做了什么

```text
SET optimizer_trace="enabled=on";            -- 示意，未执行
SELECT * FROM a LEFT JOIN b ...;
SELECT * FROM information_schema.OPTIMIZER_TRACE;
```

- trace 里的 transformation 列表中，你通常能看到类似这些条目（`condition_folding`、
  `outer_join_to_inner_join`、`subquery_to_derived`、`derived_merge`、`semijoin`、`materialization`、`star_expr_removal`
  等：**具体字段名随版本不同，🔧 请以当版 trace 输出为准**）。
- 用法：当你怀疑「优化器无视了我的写法」时，先用 trace 确认**改写阶段是否发生过**；
  改写发生了却选了个贵的路线，那是成本层的问题（见 `12-基于成本的优化.md`）；
  改写根本没发生，才是这里的问题（例如派生表准入条件不满足）。
- 一条经验：**`EXPLAIN` 只呈现「改完之后」的计划**，所以「我明明写了 A 却得到 B」时，先看 trace 再看 hint。

### 14.10 🔧 2026 视角：8.0 之后规则层的走向

| 变化 | 版本 | 影响 |
| --- | --- | --- |
| CTE 默认物化 / 派生表合并并存 | 🔧 8.0 | 需要重新理解「我这段 SQL 会不会被物化」 |
| 递归 CTE 的执行模型 | 🔧 8.0 | 递归带来新的成本模型问题（反复迭代） |
| 优化器提示体系 | 🔧 8.0 | `MERGE` / `NO_MERGE`、`SEMIJOIN` / `NO_SEMIJOIN`、`MATERIALIZATION` / `NO_MATERIALIZATION` 等成为显式的重写开关 |
| 跳过扫描（skip scan） | 🔧 8.0.13 | 有时「不改写 SQL 也能走索引」，但它属于候选路线而非规则 |
| 优化器内部结构演进 | 🔧 8.x → 9.x | 改写阶段的组织方式持续调整，具体行为以当版 release notes 为准 |

## 近年研究与工业界开源实践（2015–2026）

- **研究主线**：查询改写从「手写规则集」走向**规则框架 + 验证机制**（规则与代价模型分离、可穷举验证等价性），
  以及**JSON 逻辑计划（如 Relational Algebra 归一 + 规则编排）**在开源数据库中普及（Calcite 生态即为一例）。
- **工业界做法**：把「这段 SQL 会不会被物化 / 会不会走半连接」写进**性能回归基线**；
  升级大版本前后对比计划，往往就是靠这一层发现回归。
- **工业界开源**（star 数 2026-09-25 通过 `gh api repos/OWNER/REPO --jq '.stargazers_count'` 实测）：
  - `mysql/mysql-server`（**≈12.4k★**）：改写逻辑集中在 `sql/opt_rewrite/` 与 `sql/optimizer/`，提示解析在 hint 模块。
  - `facebook/mysql-8.0`（**≈115★**）：分支里大量查询改写与子查询物化的工程改进，是「改写策略怎么取舍」的最佳样本。
  - `percona/percona-server`（**≈1.28k★**）：发行版常带优化器相关补丁与细粒度开关。
  - `mariadb/server`（**≈8.27k★**）：其半连接/物化与「NO...」提示体系有自己的一套，可作对照。
  - `vitessio/vitess`（**≈21.4k★**）：在代理层缓存参数化查询计划，改写结果因此被**复用**，一旦改写不当全量受影响。
  - `pingcap/tidb`（**≈40.6k★**）：基于规则的 planner（`planner/core/rule_*.go`）与 cascades 探索并存，是改写工程化的现代样本。
  - `postgres/postgres`（**≈22.2k★**）：`enable_hashagg`/半连接与「subquery pullup」等规则的实现思路可直接对照。
