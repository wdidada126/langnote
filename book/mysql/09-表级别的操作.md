# 表级别的操作——CREATE / DROP / ALTER 与「重建表」的代价

> **原书位置**：主题对应第 8 章「数据的家」中「表文件与表空间」部分，以及原书未设专章的 DDL 内容；
> 本文件名沿用任务映射表 `09-表级别的操作.md`。原书基于 **MySQL 5.7.22**。
>
> **一句话**：DDL 看起来是一条语句，实际是**「拿元数据锁 → 改表结构 →（可能重写整表）→ 提交字典事务 → 释放锁」**的五步过程；
> 其中「是否重写整表」决定了这次 ALTER 是**秒级**还是**锁表数小时**。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 9.1 三类库级/表级操作 | `CREATE`/`DROP`/`TRUNCATE` 快（元数据操作），`ALTER` 可能重写全表 | 判断是否重建看「改了什么」，不看语句长度 |
| 9.2 DDL 的内部阶段 | 准备（校验+MDL）→ 执行（改写/重写）→ 提交（字典事务）→ 收尾 | 崩溃后能「继续」或回滚，靠的是数据字典的事务语义 |
| 9.3 三种 ALGORITHM | `COPY`（建新表+拷数据，锁表）/`INPLACE`（改页元数据，可允许并发 DML）/`INSTANT`（只改行元数据，秒级） | 🔧 `INSTANT` 是 8.0.29 之后最重要的 DDL 进步 |
| 9.4 元数据锁（MDL） | DDL 要拿表的 MDL 排他锁；**被长事务/长查询堵住**是最常见事故 | 「一个 5 分钟的事务卡住一条 ALTER」不是玄学 |
| 9.5 会触发「重建表」的 ALTER | 改列类型、加/删主键、改行格式、改字符集、重建表空间、`OPTIMIZE TABLE` | 重建期间磁盘空间翻倍、IO 翻倍 |
| 9.6 加索引的代价 | `ADD INDEX` 是 INPLACE，但会读写全表并占满 IO | 生产加索引要考虑 `innodb_online_alter_log_max_size` |
| 9.7 `RENAME TABLE` | 原子操作（字典事务内），跨库 rename 也可原子 | 常用于「阴影表 + rename 切换」的发布模式 |
| 9.8 在线改表的第三条路 | gh-ost / pt-osc 类工具：影子表 + binlog 追增 + rename | 当 DDL 无法 INSTANT / 无法 INPLACE 时 |
| 9.9 🔧 8.0+ 的原子 DDL | 表结构变更写入 InnoDB 字典，DDL 可回滚且崩溃可恢复 | 与 5.7「改 .frm 文件」有本质区别 |

## 核心精讲

> 以下 SQL / 结构均为**教学示意，不参与构建**：本目录不搭建真实实例，示例只用于对齐概念。

### 1. 一句话判断「要不要重建」（教学示意，不参与构建）

| 想做的事 | 是否重建表 | 实际行为 |
| --- | --- | --- |
| `ADD COLUMN`（尾部追加，8.0.29+） | 否 | 🔧 `ALGORITHM=INSTANT`，只改行格式元数据 |
| `DROP COLUMN` | 是 | 需要重写（除非后续支持） |
| 修改 `VARCHAR(50) → VARCHAR(100)`（同向放大） | 否（8.0 起 `inplace`） | 只改列元数据 |
| `VARCHAR(100) → VARCHAR(50)`（缩小） | 是 | 需要重写 |
| 改列类型（INT → BIGINT） | 是 | 需要重写 |
| 加/删二级索引 | 否 | `INPLACE`，允许并发 DML（8.0 起部分场景可 INSTANT） |
| 加主键 | 是 | 需要重写整表 |
| `ROW_FORMAT` / `KEY_BLOCK_SIZE` 变更 | 是 | 需要重写 |
| 改字符集/排序规则 | 是（多数情况） | 需要重写 |
| `OPTIMIZE TABLE` | 是 | 等于重建（回收碎片） |
| 修改表/库名（`RENAME`） | 否 | 只改字典表名（8.0 是原子操作） |

> 记忆法：**「只动元数据、不动数据行」→ 快；只要有一行数据要重写 → 等于重建表。**

### 2. DDL 的四个阶段（教学示意，不参与构建）

```
① 准备   校验语法/权限/磁盘空间；申请表的 MDL 排他锁（若被长事务堵住，会一直等）
② 执行  INSTANT：改行格式元数据
        INPLACE：改元数据 + 可能需要读旧表结构 /（加索引则扫描叶子页）
        COPY ：建一张新表，把旧表数据一行一行拷过去（旧表仍可读，但写被阻塞）
③ 提交   InnoDB 数据字典里写入新的表定义（8.0 起是事务）
④ 收尾  旧表空间文件释放（DROP 时）；若失败则回滚字典（8.0 原子 DDL）
```

**为什么「一个慢查询能拖垮 DDL」**：阶段 ① 要拿 MDL。若此时有一个执行了 30 分钟的事务正持有该表的 MDL，
ALTER 会在 ① 排队；更糟的是，**后续所有访问该表的普通查询也会被 MDL 排队**，
于是「一条 ALTER 把整个表的所有查询都堵死」——这是 MDL 的经典雪崩场景。

### 3. 在线改表工具的原理（教学示意，不参与构建）

```
gh-ost / pt-osc 类工具共通思路：
   ① 建一张结构相同的「影子表 _t_new'
   ② 在源表上做数据拷贝，同时把增量（binlog 事件或触发器）追到影子表
   ③ 数据追平后，在一个极短的事务里 RENAME 两张表（MySQL 的 RENAME 是原子的）
   ④ 删除旧表
```

这里的关键前提仍是「RENAME 原子」+「binlog 格式决定增量捕获方式」，
所以这类工具通常要求 `binlog_format=ROW` 且 `binlog_row_image=FULL`（后者保证能算出旧值）。

### 4. 磁盘空间的「翻倍问题」（教学示意，不参与构建）

```
重建表期间：旧表空间 + 新表空间同时存在 → 磁盘占用 ≈ 2× 表大小
  ├─ 若磁盘只剩 10%，重建会失败在最后一步（最尴尬）
  └─ 缓解：先 DROP 旧分区/旧表碎片，或分批重建，或改用 INSTANT/INPLACE DDL
```

### 5. 观测与排障（教学示意，不参与构建）

```sql
-- 查看当前正在跑的 DDL / MDL 等待（只读取信息，不构成构建步骤）
SELECT * FROM performance_schema.metadata_locks;
SELECT * FROM performance_schema.events_statements_history_long WHERE SQL_TEXT LIKE 'alter%';
SHOW PROCESSLIST;
```

| 症状 | 指什么 |
| --- | --- |
| DDL 卡住不动，后面同类查询也卡住 | MDL 排队（长事务/长查询持有锁） |
| 磁盘在 ALTER 期间翻倍 | COPY 式重建 |
| 加索引后 IO 跑满、延迟升高 | 索引构建扫描全表 |
| 重建完成后 `data_free` 变小 | 碎片被回收 |

### 4.1 与 DDL 相关的常见错误（教学示意，不参与构建）

| 报错关键字 | 含义 | 处理 |
| --- | --- | --- |
| `Table metadata lock wait` | MDL 被长事务持有 | 先查 `information_schema.innodb_trx`，杀掉或等待 |
| `Row size too large` | 行超上限（见 04） | 拆表或改行格式 |
| `Too many keys` / `Too many columns` | 索引数/列数超限 | 合并冗余索引、拆表 |
| `Duplicate entry` 在 DDL 中 | 🔧 原子 DDL 下回滚的表现 | 回滚后数据应完好，可放心重做 |
| 磁盘空间不足 | COPY 式重建需要额外空间 | 先清理日志/碎片，或改走影子表方案 |

### 5.1 一条可执行的 ALTER 预案清单（教学示意，不参与构建）

1. **查支持矩阵**：确认目标版本对该操作支持 `INSTANT` 还是必须 `INPLACE/COPY`；
2. **量代价**：估算重建期间的空间与 I/O（≈ 表大小 × 2，时间按吞吐折算）；
3. **清障碍**：先查最老活跃事务（`information_schema.innodb_trx`）与 `information_schema.metadata_locks`，
   避免 ALTER 在第一步就被引爆；
4. **低峰 + 分批**：大表用「分批重建/影子表」或 `gh-ost` 类工具，`--dry-run` 先跑一遍；
5. **回归**：改完用关键查询的 `EXPLAIN` 与压测结果对比，确认收益；
6. **留后路**：保留旧表一小段时间（或用 `RENAME` 切换而非 `DROP`），出现异常可快速回滚。

### 5.2 三种重建的对照（教学示意，不参与构建）

| 手段 | 是否锁写 | 空间 | 适用场景 |
| --- | --- | --- | --- |
| `ALTER ... ALGORITHM=INSTANT` | 否（只改元数据） | ≈不变 | 🔧 8.0.29+ 的尾部加列等 |
| `ALGORITHM=INPLACE` | 视操作，多数允许并发 DML | 略增 | 加索引、改列性态（如 VARCHAR 放大） |
| 影子表 + 追增 + rename | 极短时间 | 翻倍 | 无法 INSTANT 的大表 |
| `OPTIMIZE TABLE` | 视版本（可能是 inplace 的重建） | 翻倍再回收 | 只是想回收碎片 |

## 版本演进

| 版本 | 关键变化 |
| --- | --- |
| **5.7（原书基线）** | 加索引是 `ALGORITHM=INPLACE`（允许并发 DML）；加列是 `COPY`（锁表，除非是尾部追加且 `instant_add_column` 打开的内部优化）；无原子 DDL（表定义改的是 `.frm`，崩溃可能留下不一致） |
| **8.0** | 🔧 **原子 DDL**（表定义进入 InnoDB 字典，DDL 可回滚）；🔧 **instant ADD COLUMN**（8.0.29 起 GA 用法）；🔧 支持 `ALGORITHM=INSTANT` 语法并给出 `LOCK=NONE` 的语义；🔧 加索引/改列类型等逐步提高 `INSTANT` 覆盖面；🔧 元数据锁与 online DDL 的日志上限变量 `innodb_online_alter_log_max_size` 的行为更稳定 |
| **8.4 LTS** | 🔧 DDL 相关默认值与兼容性继续收敛；原子 DDL 的适用面扩大（以官方文档为准） |
| **9.x** | 🔧 继续推进「结构变更像改一个变量一样便宜」的方向 |
| **MariaDB / PostgreSQL 对照** | MariaDB 有 **Instant ADD COLUMN** 与 **Online ALTER TABLE**（`ALGORITHM=INSTANT/INPLACE/COPY`，与 MySQL 8.0 后高度相似但有差异）；PostgreSQL 的 `ALTER TABLE ... ADD COLUMN` 是**纯元数据更新**（同一页内），但 `ALTER TYPE`/加约束等会重写或加锁，且 PG 的 DDL 本身就是事务 |

## 近年研究与工业界开源实践（2015–2026）

- **`github/gh-ost`（2026-09 实测 ≈13.6k★）**：不依赖触发器、靠解析 binlog 做增量，是「无法 INSTANT 时的标准答案」；
  它的 README 明确列出对 `binlog_format=ROW`、`binlog_row_image=FULL` 的要求，正好对应本节第 3 节的结论。
- **`pingcap/tidb`（≈40.6k★）**：DDL 由「DDL Owner + Job 队列」以分布式方式推进，
  变更先在 etcd 里登记成 job 再执行，天然具备「可中断可恢复」——是把 8.0 的原子 DDL 思路推到分布式的样本。
- **`clickhouse/clickhouse`（≈50.1k★）**：`ADD COLUMN` 几乎只是改元数据（数据块延迟物化），
  `OPTIMIZE` 才真正合并——反过来说，这类系统把「重建」的成本挪到了后台。
- **`vitessio/vitess`（≈21.4k★）**：`Live DDL` / `Online DDL` 工作流把 gh-ost 这类工具编排进集群级发布流程。
- **工程规范**：大表上线前「先 `(SELECT COUNT(*) FROM information_schema.columns ...)` 查支持矩阵」、
  用 `gh-ost --dry-run` 预览、在低峰执行、以及「先加索引再改数据」的顺序，是把 DDL 事故率压低的关键动作。

## 常见误区与本书需修正之处

| # | 常见误区 | 修正（🔧 = 原书出版时未覆盖） |
| --- | --- | --- |
| 1 | 「`ALTER TABLE` 只是改结构，很快」 | 只要涉及重写就是全表 COPY，可能锁表数小时 |
| 2 | 「`TRUNCATE` 只是删数据」 | 它是**元数据操作**（等价于 DROP+CREATE），不能回滚，也不会触发外键/触发器 |
| 3 | 「DDL 失败就自动回滚了」 | 🔧 5.7 时代表定义改的是 `.frm`，崩溃/失败可能留下不一致状态；8.0 起才是**原子 DDL** |
| 4 | 「加列一定会重建表」 | 🔧 8.0.29 起尾部加列可用 `ALGORITHM=INSTANT`；条件以官方支持矩阵为准 |
| 5 | 「DDL 卡住只是它自己在等」 | MDL 会**连带堵住所有访问该表的查询**（雪崩），要先杀长事务 |
| 6 | 🔧 本书未覆盖 | 原书无独立 DDL 章，**未覆盖** `ALGORITHM=INSTANT`、原子 DDL、`innodb_online_alter_log_max_size` 的代价，以及 8.4/9.x 的 DDL 演进 |
| 7 | 「`OPTIMIZE TABLE` 会锁表所以别用」 | 多数情况下它是「online」的重建；真正的风险是空间与 I/O，不是锁 |
| 8 | 「先删索引再重建反而更快」 | 对于 COPY 式重建，先删后建省的是「维护两个索引」，通常确实更快，但要注意中途失败的处理 |
