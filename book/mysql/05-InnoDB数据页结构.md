# 第 5 章 盛放记录的大盒子——InnoDB 数据页结构

> **原书位置**：第 5 章「盛放记录的大盒子——InnoDB数据页结构」，对号章节。原书基于 **MySQL 5.7.22**。
>
> **一句话**：一页 = **两块固定头部（File Header 38B + Page Header 56B）+ 两条虚拟记录（Infimum/Supremum）
> + 用户记录区（自中间向右）+ 空闲空间（页中间的缺口）+ 页目录（自尾部向左）**；
> 理解这七个部分，就理解了「为什么页内查找是二分 + 链表遍历」，也理解了「为什么页目录是稀疏的」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 5.1 File Header（38 字节） | 页校验和、页偏移（页号）、表空间 ID、上一页/下一页指针、页类型、LSN | **页与页之间靠双向链表串起来**，这决定了范围扫描的顺序性 |
| 5.2 Page Header（56 字节） | 页目录槽位数、页内记录数、堆顶部位置、空闲/已用字节、页目录首地址、最尾记录位置 | 「页内有多少记录、多少空闲」的账都在这 56 字节里 |
| 5.3 Infimum 与 Supremum | 两条**虚拟**记录，分别代表区间下界与上界（不占用户空间） | 让二分查找可以在「左开右闭」的区间里统一处理，不用特判边界 |
| 5.4 用户记录区与 `next_record` | 记录按主键序串成单向链表；`delete_flag` 只打标记不真删 | **删除 = 打标记 + 链接进垃圾链表**（之后可被复用） |
| 5.5 Free Space（页中间缺口） | 新记录从「右边界」向中间插入，占用的是中间的缺口 | 页内是「双向生长」：用户数据向右，页目录向左 |
| 5.6 Page Directory（页目录） | 槽位（slot）指向「该组最末一条记录」，组内二分 + 组内链表扫描 | 页目录是**稀疏索引**，通常一页只需几个槽位 |
| 5.7 页分裂与页目录重建 | 页满时分裂，分裂后页目录与槽位重排 | 分裂是 B+ 树高度与碎片化的主要来源 |
| 5.8 校验和与部分写失效 | 页有校验和；写入中途崩溃可能造成「半页」→ 需要 doublewrite 副本 | 这是 InnoDB 必须先把脏页写到 doublewrite 缓冲的原因 |
| 5.9 🔧 8.0 之后 | 页结构本身稳定；8.0 起 doublewrite 可独立文件、`innodb_doublewrite` 默认 ON | 页结构变化不大，变化在管理页的后台线程 |

## 核心精讲

> 以下 SQL / 结构均为**教学示意，不参与构建**：本目录不搭建真实实例，示例只用于对齐概念。

### 1. 一页的物理布局（教学示意，不参与构建）

```
 0                 38                      56                (56+2*13)
 ┌──────────────────┬───────────────────────┬──────┬─────────┬─────────────┬──────────────┐
 │   File Header    │     Page Header       │ Infim│ User rec│ Free Space  │ Page Directory│
 │       38B        │        56B            │ um   │ (向右)  │   (缺口)     │  (向左，槽位) │
 │                  │                       │ Supre│         │             │              │
 │                  │                       │ mum  │         │             │              │
 └──────────────────┴───────────────────────┴──────┴─────────┴─────────────┴──────────────┘
                                          ↑ new_records_start   ↑ page_directory_start
```

一句话记忆：**「两头往中间挤」**——用户记录与页目录之间那块越来越大的缺口，就是 Free Space 的真实形状。

### 2. File Header 的字段含义（教学示意，不参与构建）

| 字段 | 作用 |
| --- | --- |
| 页校验和（checksum） | 检测页是否在磁盘上损坏（与内存中重算的校验和比对） |
| 页偏移（页码） | 该页在其表空间内的偏移，等价于 `page_no`，与 space id 一起构成全局定位 |
| 上一页 / 下一页 | **双向链表指针（按 16KB 计）**，让同层满页可以顺序扫 |
| 页类型 | 数据页 / undo 页 / 系统页 / 溢出页等 |
| flush LSN / page LSN | 该页最后一次刷盘的 LSN 与页内最新修改的 LSN，是重做判据 |

### 3. 页内查找：稀疏目录 + 组内链表（教学示意，不参与构建）

```
Page Directory:  [slot0][slot1][slot2][slot3]        每个 slot 指向「该组最后一条记录」
                   ↓       ↓       ↓       ↓
记录链表:  Infimum → r1 → r2 → r3 → r4 → r5 → … → Supremum（单向，按主键序）

查找 k=…：① 用 slot 折半 → 落到一个组  ② 组内沿 next_record 顺序扫描
```

因此页内一次定位的代价 ≈ **「log(槽位数) + 组内几步」**，而不是对全页逐行比对。
这也是为什么**窄表 + 多记录**时页内查找非常快，而**宽表 + 少量记录**时页目录几乎没用。

### 4. 删除与「打标记」（教学示意，不参与构建）

```
删除一行 = ① 记录头 delete_flag = 1  ② 从主链表中摘除，挂进「垃圾链表」
   ├─ 之后插入的新行可复用这些空间（在页内）
   └─ 直到页内空间严重碎片化，才考虑重建表（见 09）
```

推论：**删一万行 ≠ 空间回收**，磁盘文件可能毫无变化；
`DATA_FREE` 长期为空但 `data_length` 大，就是典型的空洞表。

### 5. 页分裂的两种情形（教学示意，不参与构建）

```
情形 A：顺序插入主键       情形 B：随机主键插入
  页内记录有序 → 追加到右侧       页内记录无序 → 需要找到插入点，挤入/分裂
  分裂出的两半仍近似有序          分裂出的两半可能「都不满」，造成碎片
```

工程含义：**主键选择会直接决定页分裂的质量**，进而决定表的空间占用与写放大：
自增主键 → 类似顺序写；UUID 主键 → 更多页分裂、更高写放大（这是「为什么别用 UUID 做主键」的完整解释）。

### 5.1 页目录槽位的数量级（教学示意，不参与构建）

```
一个槽位约指向 4–8 条记录（InnoDB 的页面目录「组」上限由实现决定，常见说法是每 4–8 条一组）
一页 16KB、每行 200B → 约 80 行 → 大约需要 10–20 个槽位
一页 16KB、每行 2KB → 约 8 行 → 大约 2–4 个槽位
```

结论：**页目录是给「一页装很多条中短记录」准备的优化**。行越短，同样一页需要越多的分组与槽位，
二分查找的下降段也越长；行越长，一页里本来就只有几条，页目录省下的比对次数极少。
因此「页目录」对窄表价值高，对超长行几乎无效——超长行本来就已经靠溢出页了。

### 5.2 页结构相关的常见排障（教学示意，不参与构建）

| 现象 | 与页结构的关联 | 处理方向 |
| --- | --- | --- |
| `Page Directory` 槽位频繁重建 | 大量插入/删除导致页内重组 | 减少随机写，或重建表 |
| 表的 `data_free` 很大 | 页内空洞 + 未回收页 | 重建表 / `OPTIMIZE TABLE`（见 09） |
| 页校验和不匹配 | 可能发生部分写失效 | 检查 doublewrite、磁盘健康、文件系统 |
| 单页损坏导致查询失败 | 页损坏后重做也无法修复 | 从备份恢复 + `innodb_force_recovery` 导出数据 |
| 页分裂后 write Amplify 明显 | 随机主键 | 换主键或改用「顺序 + 业务键」的复合方案 |

### 6. 为什么需要 doublewrite（教学示意，不参与构建）

```
正常：  内存脏页 → 直接写到表空间文件
                       ↓ 写入途中崩溃（部分写失效，页被写了一半）
                  页在磁盘上「半损坏」→ redo 重做也没用（重做需要页本身是完好的）

InnoDB 方案：脏页先拷到 doublewrite 缓冲（内存 2MB）→ 连续写到磁盘 2MB 区域 → 再写真正的位置
             崩溃后启动时：若发现页校验和不匹配，先从 doublewrite 区把页的副本拷回来再重做
```

## 版本演进

| 版本 | 关键变化 |
| --- | --- |
| **5.7（原书基线）** | 页结构即本章所述；doublewrite 位于系统表空间 `ibdata1`；页校验和默认 `crc32` |
| **8.0** | 🔧 **doublewrite 可配置为独立文件（`innodb_doublewrite` + 独立 doublewrite 文件）**，默认开启；🔧 页结构本身未变；🔧 change buffer 相关页结构变化（`ib_page` 相关调整）；🔧 数据字典页进入各表空间的 `sdi`，页类型的「系统页」家族变多 |
| **8.4 LTS** | 🔧 doublewrite 与 redo 的 I/O 行为继续优化；默认参数与 8.0 有差异，以官方文档为准 |
| **9.x** | 🔧 页校验和与 I/O 栈在持久化内存/新存储设备上的调整，以官方文档为准 |
| **MariaDB / PostgreSQL 对照** | PostgreSQL 的 `full_page_writes` 用「每 checkpoint 后的首个页写一整页」来避免部分写问题，而不是 doublewrite 区，这是两种截然不同的解法 |

## 近年研究与工业界开源实践（2015–2026）

- **工业实现**：`mysql/mysql-server`（≈12.4k★）中，页目录与记录链表的实现集中在
  `storage/innobase/page/page0page.cc`（`page_dir_*` 系列函数），File Header/Page Header 定义在 `page0types.h`；
  8.0 的 doublewrite 实现在其独立模块中，可关闭以换取吞吐（代价是数据损坏风险）。
- **对照实现**：`facebook/rocksdb`（≈32.1k★）用 block（默认 4KB）+ 校验和 + 可选的整块校验，
  没有「页目录」这类页内索引，因为它块内是排序数组 + 二分查找。
- **对照实现**：`clickhouse/clickhouse`（≈50.1k★）的 `checksums*` 列标记存在于每个 part，
  把「页校验和」升级为「part 级校验 + 远程副本」，与 doublewrite 的动机一致。
- **研究侧**：近年关于 **NVMe 下 doublewrite 是否还必要**、**持久内存下的原子页写**、
  **多设备混合存储下的页迁移**都有工作，但结论高度依赖硬件，工程上仍以官方文档的开关为准。
- **运维经验**：开启 doublewrite 会多一次顺序写（约 2MB 一段），在 SSD 上开销很小；
  而关闭它在部分写入被硬件/文件系统「静默吞掉」的场景下会造成不可恢复的页损坏。

## 常见误区与本书需修正之处

| # | 常见误区 | 修正（🔧 = 原书出版时未覆盖） |
| --- | --- | --- |
| 1 | 「页里就只有数据」 | 两块头部 + 两条虚拟记录 + 页目录，全是固定开销 |
| 2 | 「页内记录是连续数组」 | 是「链表 + 稀疏槽位」；删除只是打标 |
| 3 | 「页目录指向每条记录」 | 指向**每组**的最后一条记录，组内才做链表扫描（所以是稀疏索引） |
| 4 | 「删了数据空间就还回来了」 | 只打 `delete_flag`；文件不缩小（`OPTIMIZE TABLE` 才重建，见 09） |
| 5 | 「有 redo 就不怕页损坏」 | redo 重做的前提是「页本身是完好的」→ 这正是 doublewrite 存在的理由 |
| 6 | 🔧 本书未覆盖 | 原书基于 5.7，**未覆盖** 8.0 的 doublewrite 独立文件化、现代 SSD 上 doublewrite 的取舍、以及 `innodb_doublewrite` 的可观测指标 |
| 7 | 「页目录就是主键索引」 | 页目录是**页内**的稀疏槽位，只在页内定位；跨页定位靠 B+ 树层（见 06） |
| 8 | 「页内记录一定按主键升序」 | 删除/插入会改变物理顺序；逻辑有序靠链表，物理位置会乱（这是页分裂与空洞的来源） |
| 9 | 「页头信息不影响性能」 | 每次改页都要维护 File Header 的 LSN、Page Header 的计数与页目录，是写路径的固定成本 |
