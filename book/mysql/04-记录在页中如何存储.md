# 记录在页中如何存储——行格式、变长字段、NULL 列表与行溢出

> **原书位置**：第 4 章「从一条记录说起——InnoDB记录存储结构」（本章是对的号章节）。
> 原书基于 **MySQL 5.7.22**，行格式部分在 8.0 上同样适用（DYNAMIC 已是默认）。
>
> **一句话**：**行是逻辑概念，页是物理容器**；InnoDB 用「变长字段长度列表 + NULL 位图 + 记录头 + 真实列数据」拼出一条记录，
> 当一行装不进一页时，把大字段的余下数据甩到页外，页内只留 20 字节指针。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 4.1 行格式的演进 | `REDUNDANT` → `COMPACT` → `DYNAMIC` → `COMPRESSED` | 演进主线是「**省字节**」与「**更激进的行溢出**」 |
| 4.2 COMPACT 行记录的组成 | 变长字段长度列表（逆序）+ NULL 位图 + 记录头（含 `next_record`） + 真实数据 | 一个字段存多少字节，直接决定一页能装多少行 |
| 4.3 变长字段长度列表 | 按**列逆序**存放，1 字节或 2 字节（看最大列长度是否超 255 字节） | 只有「真正在页内、长度可变」的列才登记 |
| 4.4 NULL 列表 | 位图压缩 NULL，凑整到字节边界 | NULL 不占数据区，但**占 NULL 位图的一位** |
| 4.5 行溢出阈值 | COMPACT/REDUNDANT：768 字节前导 + 页外；DYNAMIC/COMPRESSED：20 字节指针前缀 | 这是「多少字节以上会触发溢出」的硬门槛 |
| 4.6 溢出页与多页链表 | 溢出数据可能跨多页，靠页与页之间的链表串联 | 读一行大字段最坏要读「n 页 + 1」 |
| 4.7 CHAR / VARCHAR 的存储 | `VARCHAR` 变长；`CHAR` 在 utf8mb4 下按字符算，尾部空格**不保留**（5.7+） | 用 `CHAR` 存长 URL 是空间浪费的常见来源 |
| 4.8 🔧 8.0 之后的关联变化 | 统计信息持久化、`sdi` 中存列定义、`COMPRESSED` 依赖 zlib | 🔧 列定义本身也进了 InnoDB 表 |

## 核心精讲

> 以下 SQL / 结构均为**教学示意，不参与构建**：本目录不搭建真实实例，示例只用于对齐概念。

### 1. COMPACT 行记录的物理布局（教学示意，不参与构建）

```
┌─ 变长字段长度列表 ─┐─ NULL 位图 ─┬─ 记录头(5B) ─┬─ 列 1 ─ 列 2 ─ 列 3 ─┐
│ 逆序登记每个在页内的变长列长度 │  每个可为 NULL 的列占 1 bit  │
│ 1B（≤255B）/ 2B（>255B）      │  凑整到字节                 │
└────────────────────────────────┴────────────────┴────────────────────┘
                     ↑ 记录头里的 next_record（2B 偏移）把页内所有记录串成单向链表
```

四个容易记混的点：
1. 变长字段长度列表是**逆序**的（最后一个列在最前），这是为了给「MySQL 早期版本兼容」留下空间；
2. 记录头固定 5 字节（COMPACT），其中 2 字节是 `next_record` 偏移（有符号，正负表示方向）；
3. `REDUNDANT` 格式里字段长度列表是**正序**的，且行头信息更臃肿；
4. 一条记录的「真实数据」只包含「在页内的那部分」，溢出的部分不在本页。

### 2. 变长字段：多少字节要走页外（教学示意，不参与构建）

```
列类型                      | 页内保留前缀      | 溢出阈值（近似）
VARCHAR/TEXT/BLOB/JSON 于    | COMPACT/REDUNDANT: 768B | 超过约 768 字节（行总长限制 ~8126B 内）
DYNAMIC/COMPRESSED 行格式    | 20B 指针          | 超过 20 字节即可能触发溢出
```

即：**DYNAMIC 更激进**。COMPACT 会把「超长字段的前 768 字节」留在页内，DYNAMIC 只留 20 字节指针，
其余全部放进溢出页 —— 好处是页内更紧凑、能装下更多行；代价是「读这一行」要多一次跨页跳转。

### 3. 一行跨多页的示意（教学示意，不参与构建）

```
数据页A                         溢出页1                溢出页2
┌────────────────────┐        ┌──────────────┐      ┌──────────────┐
│ 行记录(仅 20B 指针) │─next─→ │ 前 8KB 数据  │─next─→│ 后 8KB 数据  │
└────────────────────┘        └──────────────┘      └──────────────┘
```

推论（工程上很实用）：
- **查询没用到的长字段，就不要 `SELECT *`**；`SELECT id, name` 与 `SELECT *` 的 I/O 量可能差几十倍；
- `UPDATE` 把某个短字段「大幅改长」时，可能把行挤出原页 → 页分裂；
- 把大 `TEXT/BLOB` 拆到外键表，是经典的「热表拆分」手段。

### 4. NULL 与空串（教学示意，不参与构建）

```
列 a BIT(1) NULL → NULL 位图占 1 bit（不占数据区）
列 a VARCHAR(10) NULL  存 NULL  → 不占数据区
列 a VARCHAR(10) NOT NULL 存 '' → 占变长字段长度列表的一个 0 值
```

`NULL` 不等于 `''`，也不等于 `0`；对可空列建**普通索引**时，`NULL` 会被索引到（与普通值共存），
而 `IS NULL` 只有在「索引可用」的逻辑下才走索引（详见 [07-B树索引的使用.md](07-B树索引的使用.md)）。

### 5. 四种行格式对照（教学示意，不参与构建）

| 行格式 | 出现版本 | 行内是否留前导数据 | 压缩 | 备注 |
| --- | --- | --- | --- | --- |
| `REDUNDANT` | 5.0 前 | 是（768B） | 否 | 老版本兼容用，浪费空间 |
| `COMPACT` | 5.0+（5.7 仍可选） | 是（768B） | 否 | 逆序变长列表 + NULL 位图 |
| `DYNAMIC`（**默认**） | 5.7+ 默认 | 否（20B 指针） | 否 | 溢出更彻底，页更紧凑 |
| `COMPRESSED` | 5.7+ 可选 | 否（20B 指针） | 是（zlib） | 压缩 CPU 换空间，CPU 成本翻倍 |

查看/指定行格式（只读取结果，不构成构建步骤）：

```sql
-- 查看某表行格式（教学示意，不参与构建）
SELECT ROW_FORMAT FROM information_schema.tables WHERE table_schema='your_db' AND table_name='t';

-- 指定行格式（语法示意）
CREATE TABLE t (id BIGINT PRIMARY KEY, content TEXT) ROW_FORMAT=DYNAMIC;
```

### 6. 什么时候该压缩（教学示意，不参与构建）

| 场景 | 建议 |
| --- | --- |
| 冷数据、归档表、重复度高的文本 | 用 `COMPRESSED`（zlib），空间收益明显 |
| 热表、CPU 敏感 | 保持 `DYNAMIC`，用「拆表/拆字段」而非压缩 |
| 大字段需要随机读 | 避免 `COMPRESSED`，否则每次读都要解压 |

### 6.1 变长列的字节怎么算（教学示意，不参与构建）

```
列定义                        | 是否登记变长列表 | 列内可能占的字节
VARCHAR(10) utf8mb4 存 'abc'  | 是（长度 3）     | 3 字节 + 可能的 NULL 位图开销
VARCHAR(255) utf8mb4 存 'a'   | 变长列表用 2 字节（因为最大可能长度 > 255）
TEXT / BLOB / JSON            | 不登记「长度」，改为登记「20 字节指针前缀」（DYNAMIC）
CHAR(20) utf8mb4 存 'ab'      | 内部按 CHARACTER SET 计算，尾部空格已丢弃
```

两个实用推论：
1. **`VARCHAR(2000)` 这种「把长度一次性开很大」的写法不是好事**：它会把变长列表从 1 字节推到 2 字节，
   且在 utf8mb4 下可能让行长度估算失真；
2. **行长度有硬上限（约 8126 字节）**，超出会报「Row size too large」，
   这时只能把大字段拆出去——这正好与「行溢出」互相印证。

### 6.2 行溢出引发的连锁反应（教学示意，不参与构建）

```
大字段写大值 → 行溢出 → 页内只留指针
   ├─ UPDATE 把该字段再改大 → 行长度再变 → 可能整行挪到别的页 → 页分裂
   ├─ 二级索引里也存「键前缀」，大字段若进了索引键，索引行也会溢出
   └─ 结果：一次写放大成「多次页内搬动 + 分裂」
```

工程结论：**避免把「会频繁变长的大字段」和「热行放在同一张表里」**，
这是「用户表 + 详情表」拆分模式最本质的理由。

## 版本演进

| 版本 | 关键变化 |
| --- | --- |
| **5.7（原书基线）** | 默认行格式 **DYNAMIC**；`CHAR` 尾部空格不再保留；`ROW_FORMAT=COMPRESSED` 仍可用（依赖 zlib） |
| **8.0** | 🔧 行格式本身**没有换新的**；变化主要在周边：**数据字典 InnoDB 化**（列定义存进 `sdi` 表）、统计信息落在 `mysql.stats_*` 表、JSON 多值索引与 `JSON_*` 函数更完整；5.7 的 `mysql_format` 类维护工具已移除 |
| **8.4 LTS** | 🔧 默认字符集 `utf8mb4`，使「一个字符最多 4 字节」成为常态，变长列的空间估算更重要 |
| **9.x** | 🔧 官方继续强化 JSON / 向量类型，长字段的溢出与压缩路径会更常被触发，以官方文档为准 |
| **MariaDB / PostgreSQL 对照** | MariaDB 的 `ROW_FORMAT` 语义与 MySQL 基本一致但 `COMPRESSED` 实现不同；PostgreSQL 更新行时**不原地修改旧元组**，而是写新版本（HOT 更新），因此没有 MySQL 这种「行跨页搬动 + 页分裂」的行为 |

## 近年研究与工业界开源实践（2015–2026）

- **`clickhouse/clickhouse`（≈50.1k★）**：列存把「行」彻底拆成按列打包的数据块 + 通用压缩（LZ4/ZSTD），
  是「行溢出问题」的另一种彻底答案：没有行，也就没有行溢出。
- **`facebook/rocksdb`（≈32.1k★）**：前缀压缩（prefix compression）与块级压缩，对应「省字节」这条主线。
- **`pingcap/tidb`（≈40.6k★）**：底层存储对大值另有「分离大值（大事务/大字段）」的处理路径，
  与 InnoDB 的溢出页思路相近但在分布式层做。
- **工程实践**：常见的做法是「热表只存摘要，长文本/JSON 放子表或对象存储」，
  这既避免了行溢出，也避免了「SELECT * 拖垮一次接口」。
- **研究侧**：近年关注 **持久内存（PMem）下不再需要「原地更新 + 页搬动」**、**面向压缩的列式/混合存储**。

## 常见误区与本书需修正之处

| # | 常见误区 | 修正（🔧 = 原书出版时未覆盖） |
| --- | --- | --- |
| 1 | 「`CHAR(10)` 一定占 10 个字符」 | utf8mb4 下按**字符**计长，尾部空格不保留（5.7 起） |
| 2 | 「`TEXT` 一定很慢」 | 只有真的溢出到页外时才会多一次 I/O；`SELECT` 不取该列就完全不读溢出页 |
| 3 | 「DYNAMIC 比 COMPACT 浪费」 | DYNAMIC 溢出更彻底，**页内能装更多行**，通常整体更省 I/O |
| 4 | 「NULL 不占空间，所以随便建可空列」 | NULL 不占数据区但占位图；更重要的是，`IN`/`!=` 语义与 NULL 混用会让索引失效（见 07） |
| 5 | 「压缩一定更省」 | `COMPRESSED` 用 CPU 换空间，热表上会显著抬高单 query 延迟 |
| 6 | 🔧 本书未覆盖 | 原书成于 5.7.22 时代，**未覆盖** 8.0 之后 JSON 多值索引与列存/HTAP 对长字段读取模式的影响 |
| 7 | 「`VARCHAR(2000)` 就是 2000 字节」 | 实际占用取决于真实内容，但**声明长度会推高变长列表的字节数并影响行长度估算** |
| 8 | 「JSON 列不会让表变大」 | 🔧 JSON 是 TEXT 家族，超阈值照样溢出；8.0 的 JSON 多值索引能让部分查询不必解压整个文档 |
| 9 | 「拆表会让 JOIN 变慢，所以别拆」 | 拆表省下的 I/O 通常远大于一次 JOIN 的成本，尤其拆掉的是「大字段」时 |
