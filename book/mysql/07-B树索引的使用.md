# 第 7 章 B+树索引的使用——联合索引、最左前缀、覆盖索引与索引失效

> **原书位置**：第 7 章「B+树索引的使用」，对号章节。原书基于 **MySQL 5.7.22**。
>
> **一句话**：索引的**结构**在 06 章，索引的**运气**在这一章；
> 真正决定「走不走索引」的是**最左前缀规则 + 选择性估算 + 回表成本**三者，
> 而「明明有索引却走了全表扫描」几乎总是因为这三者之一算错了。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 7.1 联合索引与最左前缀 | 联合索引是「先按 col1 排、再按 col2 排」；`WHERE` 必须从最左列开始才用得上 | 「排序规则」决定哪些查询能用，哪些只能用部分 |
| 7.2 覆盖索引 | 要查的列都在索引里 → 无需回表 | 覆盖索引是「把随机 I/O 变成顺序读」的钥匙 |
| 7.3 索引选择性 | 列区分度越高越值得建索引；重复值多则优化器倾向全表扫 | 选择性 ≈ `count(DISTINCT col)/count(*)` |
| 7.4 索引失效的六类典型场景 | 函数/运算、隐式类型转换与字符集、`LIKE '%x'`、`OR`、非等值 + 范围后失效、统计信息过期 | 每类都能在 `EXPLAIN` 的 `type`/`key` 上看出来 |
| 7.5 索引下推（ICP） | 把「索引列上的 WHERE 条件」下推到引擎层过滤 | 减少回表次数与 Server 层行数 |
| 7.6 排序与索引 | `ORDER BY` 走索引可免排序；`file sort` 是常见瓶颈 | 联合索引的**列顺序**同时决定「能否免排序」 |
| 7.7 IN / `OR` / `UNION` 的取舍 | `IN` 项多时优化器可能改用范围扫描或退化为全扫描 | 分批 + `UNION` 是常见改写手段 |
| 7.8 🔧 8.0+ 的新手段 | 不可见索引（灰度验证）、跳过扫描、函数索引、直方图、`EXPLAIN ANALYZE` | 2020 年之后「怎么确认索引有效」这件事变简单了 |

## 核心精讲

> 以下 SQL / 结构均为**教学示意，不参与构建**：本目录不搭建真实实例，示例只用于对齐概念。

### 1. 最左前缀：联合索引到底在排什么（教学示意，不参与构建）

```
建索引：INDEX idx_c1c2_c3 (c1, c2, c3)     → 叶子里的记录按 (c1, c2, c3) 字典序排列

能用的查询                          │ 只能用「部分」的查询            │ 用不上的
WHERE c1 = 1                       │ WHERE c1 = 1 AND c2 > 5        │ WHERE c2 = 5（跳过 c1）
WHERE c1 = 1 AND c2 = 2            │ WHERE c1 = 1 ORDER BY c2       │ WHERE c3 = 3
WHERE c1 = 1 AND c2 = 2 AND c3 = 3 │ WHERE c1 IN (...) AND c2 = 2   │ WHERE c1 + 1 = 2
```

🔑 **关键规则**：**「等值」列可以乱序，但「范围」列之后的列无法继续用于索引定位**。
即 `(c1=?, c2=?, c3>?)` 可用到全部三列；而 `(c1>?, c2=?)` 只能用 c1，c2 只能在已定位的区间里过滤。

### 2. 覆盖索引（教学示意，不参与构建）

```
查询：SELECT c1, c2 FROM t WHERE c1 = 1 AND c2 = 2
若存在 INDEX (c1, c2) → 叶子里就同时有 c1、c2 → 不回表
若只有 INDEX (c1)     → 每命中一行都要回表拿 c2 → 优化器可能放弃索引
```

判断方法：在 `EXPLAIN` 的 `Extra` 列看到 `Using index` 即表示覆盖索引生效。
它的价值在于**把「随机 I/O × 行数」变成一次顺序索引扫描**。

### 3. 六类典型「索引失效」（教学示意，不参与构建）

| # | 写法 | 为什么失效 | 改写方向 |
| --- | --- | --- | --- |
| 1 | `WHERE DATE(created_at) = '2026-09-01'` | 列被函数包裹 → 无法与 B+ 树键比较 | 改成范围：`created_at >= '2026-09-01' AND < '2026-09-02'` |
| 2 | `WHERE phone = 13800000000`（phone 是 varchar） | 数字与字符串比较触发**隐式类型转换** | 保持类型一致：`WHERE phone = '13800000000'` |
| 3 | `WHERE name LIKE '%明'` | 前置通配符无法用索引定位 | 全文索引 / 倒排 / 前缀列 / 分词 |
| 4 | `WHERE c1 = 1 OR c2 = 2`（c2 未被索引） | OR 两侧需要并集，成本高 | 拆成 `UNION` 的两条查询 |
| 5 | `WHERE c1 > 10 AND c2 = 5` | 范围列之后的列不再用于定位 | 调整索引列顺序（等值列在前） |
| 6 | 统计信息过期导致误判 | 优化器按错误的行数估算回表成本 | `ANALYZE TABLE` / 8.0 的持久化统计信息 |

补充两类常被忽略的：
- **字符集/排序规则不一致**：关联两个表时若列字符集不同，会导致「无法用索引的等值连接」；
- **`NOT IN` / `!=` / `<>`**：多数情况下优化器认为「要找的行占比不确定」，倾向全表扫描。

### 4. 索引下推（ICP）做了什么（教学示意，不参与构建）

```
没有 ICP：引擎层取出一行 → 交给 Server 层过滤（回表后才判断 cond2）
有 ICP：  引擎层在遍历二级索引时，若 cond2 只涉及索引列，就先在这里判掉

收益：减少「回表次数」与「Server 层看到的行数」；范围扫描效果最明显
```

ICP 对「索引列 + 非索引列」的混合条件帮助有限，但对「多个索引列条件」收益显著。

### 5. 排序与 `file sort`（教学示意，不参与构建）

```
ORDER BY c1, c2 且存在 INDEX (c1, c2) → 直接按索引顺序输出，无需排序（Extra 无 Using filesort）
ORDER BY c2, c1                        → 索引顺序不适用 → 需要排序
ORDER BY c1 DESC, c2 ASC               → 混合方向 → 需要排序（8.0 起支持降序索引可改善）
```

「免排序」是联合索引**列顺序设计的第二目标**（第一个目标当然是查询命中）。

### 6.1 改写前后的 EXPLAIN 对照（教学示意，不参与构建）

| 改写 | `type` | `key` | `Extra` 的典型变化 |
| --- | --- | --- | --- |
| `WHERE DATE(c) = '2026-09-01'` | `ALL` | NULL | 无（失效） |
| `WHERE c >= '2026-09-01' AND c < '2026-09-02'` | `range` | idx_c | `Using where` |
| `WHERE name LIKE '张%'` | `range` | idx_name | 视版本可能为 `Using index condition` |
| `WHERE name LIKE '%张'` | `ALL` | NULL | 无（前置通配符） |
| `SELECT c1, c2 FROM t WHERE c1 = 1` + 索引 `(c1,c2)` | `ref` | idx_c1c2 | **`Using index`**（覆盖索引） |
| `SELECT * FROM t WHERE c1 = 1` + 索引 `(c1)` | `ref` | idx_c1 | 无（需要回表） |
| `WHERE c1 > 10 AND c2 = 5` + 索引 `(c2,c1)` | `ALL` | NULL | 最左前缀未命中 |

排查顺序建议：**看 `type`（好→差：`const/eq_ref/ref/range/index/ALL`）、看 `key`（用了哪个索引）、
看 `Extra`（`Using index` / `Using index condition` / `Using filesort` / `Using temporary`）**，
三者结合基本能定位绝大多数「索引没用对」的问题。

### 6.2 索引维护的日常动作（教学示意，不参与构建）

| 动作 | 何时做 | 注意 |
| --- | --- | --- |
| `ANALYZE TABLE` | 大量增删后、上线新查询前 | 让它刷新选择性估算；8.0 的持久化统计信息可减少需要手动 ANALYZE 的频率 |
| 删/改索引前用不可见索引验证 | 想删一个「可能没人用」的索引 | 🔧 8.0+ 可先 `ALTER INDEX ... INVISIBLE`，观察慢查询是否回归，再决定删除 |
| 联合索引合并 | 发现 `(a)` 与 `(a,b)` 并存 | `(a)` 几乎总被 `(a,b)` 覆盖；保留前者只会增加写放大 |
| 检查冗余索引 | 定期（版本升级后尤其） | 用 `sys.schema_redundant_indexes`、`sys.schema_unused_indexes` 视图 |
| 回归 `EXPLAIN` | 上线前 | 把关键查询的执行计划快照放进 CI，避免索引被优化器换掉 |

### 6. 选择性与「优化器为什么放弃我的索引」（教学示意，不参与构建）

```
索引选择性 = count(DISTINCT col) / count(*)
  ├─ 接近 1（主键/唯一键）→ 极值得用
  ├─ 0.1–0.3             → 常用
  └─ 0.001（"性别"这类低基数列） → 优化器通常认为「回表比例太高」而放弃
```

低基数列的正确用法通常是**把它放在联合索引的后段**做「附带过滤」，
而不是单独建索引；单独建低基数列索引，写路径上几乎只有成本没有收益。

## 版本演进

| 版本 | 关键变化 |
| --- | --- |
| **5.7（原书基线）** | ICP 默认 ON；`EXPLAIN` 有 `partitions` 等；无直方图；统计信息存内存，重启后重算 |
| **8.0** | 🔧 **不可见索引**（8.0 起，验证索引价值而不必删它）；🔧 **跳过扫描**（`skip_scan`，8.0.13 起，解决「`WHERE c2=?` 但索引是 (c1,c2)」这类跳段场景）；🔧 **函数/表达式索引**（8.0.13 起）；🔧 **降序索引**；🔧 **直方图**（`ANALYZE TABLE ... UPDATE HISTOGRAM`，8.0 起）；🔧 **持久化统计信息**（`mysql.stats_*`）；`EXPLAIN ANALYZE` 可用 |
| **8.4 LTS** | 🔧 优化器默认行为与可用性进一步改善，`skip_scan` 的适用面与稳定性提升 |
| **9.x** | 🔧 JSON 多值索引与向量索引让「哪些查询能用索引」的定义继续扩张 |
| **MariaDB / PostgreSQL 对照** | MariaDB 支持 **直方图**与更激进的 **索引下推 / 分区裁剪**；PostgreSQL 的 `EXPLAIN (ANALYZE, BUFFERS)` 观察维度更细，且支持 BRIN/GiST/GIN 等多种索引类型 |

## 近年研究与工业界开源实践（2015–2026）

- **工具链**：`EXPLAIN FORMAT=TREE` / `EXPLAIN ANALYZE`（8.0+）让「到底怎么走的」有实测数据；
  `optimizer trace` 能看到优化器的候选路径与最终放弃原因（原书第 16 章，另一位助手负责）。
- **`mysql/mysql-server`（≈12.4k★）**：跳段索引（`skip_scan`）与表达式索引的实现，
  是「原来必须改查询才能用上索引」场景下最重要的两个新能力。
- **`pingcap/tidb`（≈40.6k★）**：优化器（基于 Cascades 风格的 `planner/core/optimizer.go`）与
  MySQL 的规则优化思路同源，但statistics 模块把「直方图 + 相关性 + NDV」做得更细，可作为「为什么估算会错」的对照。
- **工程闭环**：最有效的实践是**慢查询日志 → `pt-query-digest` 归类 → 逐条 `EXPLAIN` → 改索引/改查询 → 回归**，
  并在 CI 里保留关键查询的 `EXPLAIN` 快照；ORM 层禁止 `SELECT *` 与禁止在列上包函数，是最省力的两条规范。
- **研究侧**：近年关于 **learned index（用模型替代 B+ 树）**、**代价函数在真实负载下的漂移**、
  **多列索引自动推荐与冗余索引检测**（区分度/重叠度分析）都有持续工作；
  但落到线上，最有效的仍是把「联合索引列顺序」与「覆盖率」这两件事做对。

## 常见误区与本书需修正之处

| # | 常见误区 | 修正（🔧 = 原书出版时未覆盖） |
| --- | --- | --- |
| 1 | 「建了索引就一定走」 | 优化器按**估算成本**决定，回表成本过高时会放弃 |
| 2 | 「联合索引的列顺序按字段长度排」 | 应按「等值查询频率 + 排序需求」排，范围列放最后 |
| 3 | 「`LIKE '%x%'` 加索引没救」 | 可用全文索引 / 倒排索引 / 分词前缀；8.0+ 也可用函数索引造前缀 |
| 4 | 「列上有函数就用不了索引」 | 8.0.13+ 可选**表达式索引**让函数列也可索引（写入代价更高） |
| 5 | 「索引失效就是 bug」 | 多数是优化器的**理性判断**（估算回表成本太高） |
| 6 | 🔧 本书未覆盖 | 原书基于 5.7.22，**未覆盖** 不可见索引、跳过扫描、函数索引、直方图与 `EXPLAIN ANALYZE`；这些正是 2026 年排查「索引为什么没用」的第一手工具 |
| 7 | 「改了索引就一定会变快」 | 优化器可能仍然选择全表扫描；用 `EXPLAIN` + 回归测试确认 |
| 8 | 「`IN (1,2,3,...1000)` 一定走索引」 | 参数过多时优化器可能放弃索引改写为范围扫描，通常建议分批（如每批 200–500） |
| 9 | 「加索引不需要占用空间」 | 每个二级索引都占独立空间，且都参与写放大与备份体积 |
