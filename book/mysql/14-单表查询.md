# 第 10 章 条条大路通罗马——单表访问方法

> 原书说明：标题为「条条大路通罗马——单表访问方法」，基于 MySQL 5.7.22 撰写。本文件按其思路展开，并补齐 5.6/5.7/8.0 三代的 `ICP`、`MRR`、索引交互改进，以及 2020 年之后必须补的**隐藏索引、降序索引、表达式索引、直方图、`EXPLAIN ANALYZE`**。

## 本章地图

> 一句话：**单表查询「走什么路」由优化器在成本模型上比出来的**——`const` 最快、`range` 次之、`index`（全索引扫描）与 `ALL`（全表扫描）是两条底线，而**回表次数**往往是决定胜负的那个成本项。

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 10.1 访问方法全景 | `system` / `const` / `eq_ref` / `ref` / `range` / `index` / `ALL` | 七种方法的实质是「扫描单位的粒度」由粗到细 |
| 10.2 聚簇索引与二级索引 | 回表（bookmark lookup） | **每一行二级索引记录都可能触发一次聚簇索引查找** |
| 10.3 覆盖索引 | 查询列全在索引里 → 不回表 | 最便宜的提升手段，代价是写放大与空间 |
| 10.4 最左前缀与联合索引 | 索引列顺序即排序规则 | 顺序错了，索引就白建 |
| 10.5 索引条件下推（ICP） | 5.6 起把 `WHERE` 推到存储引擎层 | 减少回表次数；只对「索引列上的部分条件」有效 |
| 10.6 多范围读取（MRR） | 5.6 起按主键顺序批量读 | 变「随机 IO」为「顺序 IO」 |
| 10.7 排序与分组 | `filesort` 的两种算法、索引直接有序 | 排序成本常被低估，是慢查询第二大类 |
| 10.8 索引失效的常见姿势 | 隐式转换、函数、前导模糊、`OR`、`<>` | 失效不是「完全不能用」，而是退化成更便宜/更慢的路线 |
| 10.9 🔧 2026 视角 | 隐藏索引、降序索引、表达式索引、直方图、`EXPLAIN ANALYZE` | 优化器不再只能「猜」 |

## 核心精讲

> **教学示意，不参与构建。** 下文 SQL 片段仅用于说明访问方法语义，**未在本机编译、未连接任何 MySQL 实例执行**；`EXPLAIN` 输出的具体数值随版本与数据分布而异。

### 10.1 访问方法全景（七种 `type`）

| `type` | 含义 | 触发条件（单表） | 成本量级 |
| --- | --- | --- | --- |
| `system` | 表只有一行（系统表/空表 + 主键定位） | 极少数 | 最低 |
| `const` | 主键或唯一索引 **精确等值**，最多一行 | `WHERE id = 1` | 极低（一次定位） |
| `eq_ref` | 多表连接中「被驱动表主键唯一等值」（连接里才多见） | 连接场景 | 低 |
| `ref` | 非唯一索引等值，可能有多个匹配行 | `WHERE email = 'a@b.c'` | 中 |
| `range` | 索引范围扫描 | `WHERE id > 100 AND id < 200` | 中高（取决于范围大小） |
| `index` | **全索引扫描**（通常因为覆盖索引比全表便宜） | 需要全量索引项 | 高 |
| `ALL` | 全表扫描 | 无可用索引 / 优化器认为全表更便宜 | 最高 |

- 🔧 读 `EXPLAIN` 的正确姿势：**先看 `type`，再看 `key`，再看 `rows`，最后看 `Extra`**。`type` 只告诉你「粗粒度路线」，真正决定成本的是回表行数（`rows` × 每行的回表成本）。
- 原书反复强调的一点在 2026 依然成立：**「有索引」不等于「会用索引」，`range` 扫 30% 的表可能比全表扫描更慢**。

### 10.2 回表：单表查询里最大的隐形开销

- **聚簇索引**：叶子节点存**完整行数据**（InnoDB 主键即聚簇索引）。
- **二级索引**：叶子节点存 **索引列 + 主键值**。
- 因此走二级索引拿到行后，要按主键回到聚簇索引读完整行 —— 这就是**回表（bookmark lookup）**。
  ```text
  二级索引 (name='Tom')  →  主键 id=37  →  聚簇索引定位整行  （一次额外 B+ 树查找）
  ```
- **后果**：`SELECT * FROM t WHERE name = 'Tom'` 若 `name` 上有索引，代价 = 索引查找 + **N 次回表**。N 大时反而慢于全表扫描。
- 🔧 **这也是「为什么 `SELECT *` 常常拖慢索引查询」的技术根源**：列越多、行越大，回表越贵。

### 10.3 覆盖索引：最便宜的优化

- 若 `SELECT` 的**所有列**都在某个索引里，**就不必回表** → `EXPLAIN` 的 `Extra` 出现 `Using index`。
  ```sql
  -- 教学示意，不参与构建
  -- 索引 (name, age)，则：
  SELECT age FROM t WHERE name = 'Tom';      -- 覆盖索引，无需回表
  SELECT *  FROM t WHERE name = 'Tom';       -- 需要回表
  ```
- 代价：索引变宽 → **写放大 + 空间 + 缓存命中率下降**。老话「索引越多越好」在覆盖索引上尤其危险。
- 🔧 8.0 还有 `EXPLAIN` 输出的 `Using index condition` 与 `Using index` 的区别要分清：前者是 **ICP**（引擎层过滤），后者才是**纯覆盖索引**。

### 10.4 最左前缀与联合索引的列顺序

- 联合索引 `(a, b, c)` 本质是**先按 a 排序，a 相同时按 b**，依此类推。
- 能用到的前缀：`(a)`、`(a,b)`、`(a,b,c)`；**用不到 `(b)`、`(b,c)`、`(c)`**。
- 排序规则决定「范围条件之后等值/排序是否还能走索引」：把**等值列放前面、范围列放最后**通常最优。
- 常见反例（教学示意，不参与构建）：
  ```sql
  -- 索引 (last_name, first_name)
  WHERE last_name = 'Zhang' AND first_name LIKE 'S%';  -- 可走
  WHERE first_name = 'San';                             -- 不可用
  ```

### 10.5 索引条件下推（ICP，Index Condition Pushdown）

- **5.6 起**：把 `WHERE` 里**能用索引列判断的部分**下推到存储引擎，在取行之前先过滤。
  ```text
  没有 ICP：引擎读索引项 → 回表 → Server 层判断 first_name LIKE 'S%' → 留下
  有   ICP：引擎读索引项 → 在引擎内先判断 LIKE → 只对通过的行回表
  ```
- `EXPLAIN` 表现为 `Extra: Using index condition`。
- 注意：ICP **不减少回表次数中的「判断」，而减少的是返回给 Server 层的行数**，因此主要收益在「大表 + 高选择率过滤」场景。

### 10.6 多范围读取（MRR，Multi-Range Read）

- **5.6 起**：对「一次查询要按非主键顺序访问主键索引」的情形（如范围扫描二级索引），先收集主键、排序去重，再**按主键顺序批量回表**。
- 收益：把随机 IO 变成顺序 IO，并顺带去重（减少回表次数）。
- 代价：**延迟了回表时机**，对「只要前几行 + `LIMIT`」的场景反而更慢 —— 所以它是可关的（`mrr=off` / `mrr_cost_based=on`）。

### 10.7 排序与分组：慢查询的第二大类

- 排序有两条路：
  1. **索引直接有序**（`type=range/index` 且 `ORDER BY` 匹配索引顺序）→ **零排序成本**。
  2. **`filesort`**：Server 层排序，两种算法
     - 单路（旧）：一次性把「排序键 + 行数据」都读入排序缓冲区 → 内存占用高。
     - 双路（5.7+ 更常见）：先读排序键和 rowid 排序，再回表取数据 → `sort_buffer_size`、`max_length_for_sort_data` 成为调优旋钮。
- `sort_buffer_size` 不够就做**外部归并排序**（临时文件），这是「一次 `ORDER BY` 跑 30 秒」的典型成因。
- 🔧 `EXPLAIN` 里看到 `Using filesort` 不必恐慌 —— 「索引有序」和「filesort」是两条不同的快路，关键是**有没有真的排序**；8.0 的 `EXPLAIN ANALYZE` 会输出实际的排序耗时与内存使用情况，比 5.7 的 `EXPLAIN` 精确得多。

### 10.8 索引失效的常见姿势（不是「失效」而是「退化」）

| 写法 | 为什么 | 替代方案 |
| --- | --- | --- |
| `WHERE col + 1 = 100` / `WHERE DATE(created) = '2026-09-25'` | 列上套函数 → 索引列被「遮蔽」 | 改写成范围条件 |
| 字符串列与数字比较（`WHERE phone = 13800138000`） | **隐式类型转换**，相当于列上套函数 | 保证类型一致 |
| `WHERE name LIKE '%San'` | 前导通配配不了索引前缀 | 全文索引 / 前缀索引 + 应用层过滤 |
| `WHERE a = 1 OR b = 2`（`a`、`b` 都有索引） | `OR` 难以合并成单次索引扫描 | `UNION` / `IN` 改写 |
| `WHERE status <> 1` / `NOT IN` | 负向条件选择率难估 | 改写成正向区间 |
| 联合索引跳列 | 违反最左前缀 | 调整索引顺序 |

- 原书对「魔鬼藏在细节中」的强调，在索引这一章体现得最彻底：**差一个函数、差一个引号，成本模型立刻把路线从 `const` 换到 `ALL`**。

### 10.9 🔧 2026 视角：优化器已经比 2020 年聪明得多

- **隐藏索引（Invisible Index，8.0）**：`ALTER TABLE t ALTER INDEX i INVISIBLE`，让优化器看不见它，用来**灰度验证「删掉这个索引会不会炸」**——比直接删安全得多。
- **降序索引（Descending Index，8.0）**：`(a ASC, b DESC)`，专为 `ORDER BY a ASC, b DESC` 设计，避免 filesort。
- **表达式索引 / 函数索引（8.0.13）**：`CREATE INDEX idx ON t ((UPPER(name)))`，让「列上套函数」的查询重新可用索引。
- **直方图（8.0）**：`ANALYZE TABLE t UPDATE HISTOGRAM ON col WITH 100 BUCKETS`，当列的数据分布**严重倾斜**（如 `status` 有 99% 是同一个值）时，给优化器提供「真实选择性」，避免它因为「估算值错误」选错路线。
- **`EXPLAIN ANALYZE`（8.0.18）**：真正**执行**并输出每步的实际耗时、实际行数与循环次数 —— 这是把「估算 vs 实际」差距摆到台面上的唯一手段，原书第 15 章的 `EXPLAIN` 只能给估算值。
- **并行扫描（8.0.22 的 `n_jobs` / innodb 并行读）**：大表全表扫描/范围扫描可以分成多个 `n_jobs` 并行推进，让「全表扫描」的成本从线性单线程变成多核。

### 10.10 🔧 用 `EXPLAIN ANALYZE` 复核本章结论

（教学示意，不参与构建，需在真实实例上执行）

```sql
EXPLAIN ANALYZE SELECT age FROM t WHERE name = 'Tom';
```

值得逐项对照的输出：

| 字段 | 在看什么 | 对应本章哪节 |
| --- | --- | --- |
| `Actual Loops` | 驱动表行数是否比估算大一个数量级 | 10.1 |
| `Rows Removed by Filter` | ICP 是否真的过滤掉了大量行 | 10.5 |
| `Actual rows` vs `rows` | 估算误差的来源（统计/倾斜） | 10.8、16.5 |
| `Buffer pool reads` | 是否发生了大量随机读（回表） | 10.2 |
| `Sort Method / Sorting` | 是否有真排序、用了多少内存 | 10.7 |

- 经验法则：**「估算行数 ≈ 实际行数」是优化器可信的前提**；不相等时先修统计，再谈加索引。

## 近年研究与工业界开源实践（2015–2026）

- **近年研究**：**「估算误差」的研究**——直方图、采样统计与学习型基数估计（learned cardinality estimation）在 2019–2024 年成为数据库顶会热点；**向量化 + 编译执行**让 OLAP 型单表扫描的成本模型与 OLTP 完全不同；**并行/分布式执行框架**（Velox、DuckDB）重新定义了「单表扫描」这一算子的实现上限。
- **工业界开源**（star 数 2026-09-25 通过 `gh api` 实测）：
  - `mysql/mysql-server`（≈12.4k★）：优化器成本模型 `sql/optimizer/cost_model.cc`；ICP 与 MRR 在 `ha_innobase::index_read` 相关路径；直方图实现在 `sql/field.h` 与 `sql/sql_analyze.h` 周边的 `Opt_hists`。
  - `mariadb/server`（≈8.3k★）：更早提供 ROR/MRR 变体与「optimizer switch」颗粒度更细的开关。
  - `clickhouse/clickhouse`（≈50.1k★）、`duckdb/duckdb`（≈41.7k★）：**列式 + 向量化**的单表扫描，与 InnoDB 的「行式 + 回表」形成鲜明对照，是理解「为什么回表贵」的最好反例。
  - `pingcap/tidb`（≈40.6k★）：CBO 全面基于统计与直方图，且 TiFlash 列存副本可把 OLAP 型单表扫描从行存侧卸走。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「建了索引 `EXPLAIN` 就一定走」 | 优化器按**成本**选路线；选择率、回表代价会让它选全表扫描 |
| 2 | 「回表是错误，一定要消灭」 | 有些场景回表比全表扫描便宜；覆盖索引只是「更便宜的候选方案之一」 |
| 3 | 「`Using filesort` = 有 bug」 | 它只是「需要排序」的中性标记；8.0 要区分「索引有序」与真排序 |
| 4 | 「`OR` 就不能用索引」 | 可能走 `range` 扫描多段索引；`IN` 与 `UNION` 改写也常常可行 |
| 5 | 「索引越多，查询越快」 | 每个索引都是一份需要维护的有序副本：写放大、空间、优化器选择负担 |
| 6 | 🔧 **本书未覆盖** | 原书基于 5.7.22，**没有**隐藏索引、降序索引、表达式索引、直方图、`EXPLAIN ANALYZE`；`EXPLAIN ANALYZE` 已经是 2026 年排查「估算行数与实际行数严重不符」的第一手段 |
| 7 | 🔧 **本书未覆盖** | **数据倾斜下的选择性估算**：`status` 列 99% 同值这类场景，5.7 只能靠采样猜，8.0 要靠显式直方图 |
