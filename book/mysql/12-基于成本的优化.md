# 第 12 章 谁最便宜就选谁——基于成本的优化

> 原书说明：标题为「谁最便宜就选谁——基于成本的优化」，基于 MySQL 5.7.22 撰写。本文件按其思路展开
> **成本常量、访问方法的成本比较、连接顺序的估算、优化器为何选错、以及 `optimizer_trace` 视角怎么读**，
> 并补齐 5.7/8.0 两代成本模型的改进与 2020 年之后必须补的**直方图、优化器提示、`EXPLAIN ANALYZE` 对照**。
>
> ⚠️ 本目录**不提供可运行的环境**：所有 SQL 与结构示例都是**教学示意，不参与构建**，未在本机编译、未连接任何 MySQL 实例执行。

## 本章地图

> 一句话：**优化器不「懂 SQL」，它只会在一张候选路线的账单上挑总价最低的那条；账单的输入是统计信息，账单的科目只有两个——**「读多少页（I/O 成本）」和「比较多少行（CPU 成本）」。** 所以「为什么没走索引」几乎总是三种情况之一：统计不准、成本常量不符实、候选路线本身建得不全。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 12.1 优化器的两层结构 | 规则改写（缩小候选集）→ 成本选路（在候选集里挑最便宜） | 规则与成本的分工：前者决定「有哪些选项」，后者决定「谁赢」 |
| 12.2 两张账单：I/O 成本与 CPU 成本 | 页读取成本、记录评估成本、默认常量（`io_cost` 1.0 / `cpu_cost` 0.2 量级）、`innodb_page_size` 的折算 | 所有估算最终都折算成「读多少页、比多少行」 |
| 12.3 一条 SQL 的两份报价 | 全表扫描 vs 索引范围扫描：一次定位 + 逐页扫 + 逐行比 + 回表 | 回表次数常常是决定胜负的那个科目 |
| 12.4 访问方法的价格梯度 | `const` / `eq_ref` < `ref` < `range` < `index` < `ALL`（与 `index_merge` 的位置） | 从「常数代价」到「越扫越贵」，选路的本质是在这条梯度上比总价 |
| 12.5 连接顺序怎么算 | 驱动表行数 × 各候选访问方法的重复次数；左深树与剪枝 | 三表以上「哪个顺序最便宜」靠穷举+剪枝，因此统计误差会被放大 |
| 12.6 优化器为什么会选错 | 统计过期、范围估算失真、`LIMIT` 影响、回表成本低估、隐式转换、排序/TEMPORARY 成本被忽略 | 选错不等于有 bug，多半是「账单的输入不准」 |
| 12.7 `optimizer_trace` 视角怎么读 | `rows_estimated` vs `rows_actual`、`considered_access_paths`、`reconsidering_access_paths` | trace 回答「为什么」，`EXPLAIN` 只回答「是什么」 |
| 12.8 🔧 2026 视角 | 直方图进入成本模型、优化器提示、`EXPLAIN ANALYZE` 实测对照、skip scan 与并行读 | 5.7 的成本模型已被多次重写，默认值不等于事实 |

## 核心精讲

> **教学示意，不参与构建。** 下文所有 `--` 片段与结构示意都只用于说明成本是怎么算出来的，
> **未在本机编译、未连接任何 MySQL 实例执行**；具体常量与默认值随版本变化，请以官方文档为准。

### 12.1 两层结构：规则先缩圈，成本再选路

```text
SQL
 ├─ ① 基于规则的改写（第 14 章详述）：子查询 → 半连接、派生表合并、常量折叠、外连接消除
 │    作用：「候选路线生成/裁剪」，不改变「谁最便宜」的判断方式
 └─ ② 基于成本的选路（本章）
      作用：在 ① 留下的候选集里，为每张表挑访问方法、为多表挑连接顺序与连接算法
```

- 关键认知：**规则阶段负责「有没有这个选项」，成本阶段负责「这个选项值不值」**。
  例如「子查询转半连接」是规则（选项变多了），「半连接用 materialization 还是 firstmatch」是成本。
- 推论：**优化器永远只在你给它的候选集里挑**。索引不存在、统计缺失、提示没写，都会让「最优路线」根本不在候选集里。

### 12.2 两张账单：I/O 成本与 CPU 成本

MySQL 把一切折算成两个科目（教学示意，不参与构建）：

| 科目 | 含义 | 默认常量（5.7/8.0 量级，以官方 cost model 文档为准） |
| --- | --- | --- |
| I/O 成本（io_cost） | 读取一个页的代价 | 约 `1.0`（16KB 页为基准；页大小变化时按比例折算） |
| CPU 成本（cpu_cost） | 处理一行记录的代价 | 约 `0.2`（评估一行、比对键值各有一份） |

- **一次范围扫描的账单大致是这样拼出来的**（示意，不参与构建）：
  ```text
  成本 ≈ 「定位区间的一次读」 + 「区间内 N 页 × io_cost」 + 「M 行 × cpu_cost」 + 「回表 K 行 × (io_cost + cpu_cost)」
  ```
  - 注意「区间内 N 页」是**页**而不是行：优化器不知道页里有多少行，只能拿统计信息里的估算行数除以记录长度。
- 🔧 **页大小的折算**：`innodb_page_size` 不是 16KB 时，单页 I/O 成本会按比例缩放；
  这也是「小页实例上索引更划算、大页实例上顺序扫描更划算」这类经验的量纲来源。
- **实践含义**：全表扫描的成本 ≈ 表占的页数 × io_cost，几乎与行数无关；
  这解释了「小表走全扫、大表才走索引」的普遍现象——**不是优化器偏爱全扫，是小表的「页数」太便宜**。

### 12.3 一份「报价单」：全表扫描 vs 索引范围扫描

假设一张表约 10000 行、约 500 页，二级索引 `idx_age` 上查 `age BETWEEN 20 AND 25`（教学示意，不参与构建）：

```text
方案 A：全表扫描
  读 500 页 × io_cost ≈ 500
  评估 10000 行 × cpu_cost ≈ 2000
  ──────────────────────────────
  合计 ≈ 2500        （行数越多越贵，但只扫一遍）

方案 B：idx_age 范围扫描
  定位起点 1 页 × io_cost ≈ 1
  估计命中 200 行 → 约 20 页 × io_cost ≈ 20
  二级索引上比对 200 行 × cpu_cost ≈ 40
  回表 200 行 × (io_cost + cpu_cost) ≈ 440
  ──────────────────────────────
  合计 ≈ 500          （赢，但赢在「回表被摊薄」，前提是命中行数真的只有 200）

若实际命中 20000 行（统计说错了），方案 B 变成 ≈ 5000，优化器会立刻改回全表扫描。
```

三个必须记住的结论：

1. **命中行数的估算误差，会被回表科目放大**——这是「优化器突然变慢」最常见的机制。
2. `LIMIT` 会改变账单：命中行数受 `LIMIT` 限制时，提前终止的收益能压过全表扫描。
3. 覆盖索引把「回表」这一项直接删掉，所以它是**最便宜的结构性提升**，不是玄学。

### 12.4 访问方法的价格梯度（与 `EXPLAIN` 的 `type` 一一对应）

| `type` | 触发条件（语义） | 成本特征 |
| --- | --- | --- |
| `system` / `const` | 主键或唯一索引上的等值匹配，最多一行 | 近乎常数，直接定位 |
| `eq_ref` | **连接**时被驱动表用唯一索引做等值匹配 | 每个驱动行一次索引查找，一行命中 |
| `ref` | 非唯一索引上的等值匹配 | 每个驱动行扫一小段，**行数随重复值放大** |
| `range` | 范围/IN/LIKE 前缀等区间条件 | 按区间页数与估算行数计价 |
| `index` | 全索引扫描（覆盖索引场景常见） | 比全表扫便宜一点（列更窄），但仍是 O(索引行数) |
| `index_merge` | 多索引条件求交/并（受成本与版本约束） | 省部分 I/O，但合并本身有 CPU 成本 |
| `ALL` | 全表扫描 | 最贵，通常是统计或索引的警报 |

- **连接场景里 `eq_ref` 与 `ref` 的差别最有业务含义**：被驱动表的连接列上有唯一索引时是 `eq_ref`（每个驱动行只查一次），
  没有唯一索引就退化成 `ref`（每个驱动行扫一小段）**并且在高并发下等价于放大锁与 latch 争用**。
- 顺序大致是：`const / eq_ref` < `ref` < `range` < `index` < `ALL`；
  **但顺序只用来「大致判断贵不贵」，真正决定胜负的是总价**（例如 `range` 因回表太多，可能输给覆盖索引的 `index`）。

### 12.5 连接顺序怎么算：账单是相乘的

三表连接的账单示意（教学示意，不参与构建）：

```text
驱动表 t1（估算 1000 行，走 range）
  └─ 对每个 t1 行，在候选路线里选 t2 的最便宜访问方法（假设 eq_ref，1 行）
       └─ 对每个 (t1,t2) 组合，选 t3 的最便宜访问方法（假设 ref，10 行）
       = 1000 × (1 × 10) = 10000 行被处理
```

- **总量是「驱动行数 × 后续各步的每行成本」的乘积**，所以**驱动表选错的代价是乘法级的**，不是加法级。
- 这与「小表驱动大表」的口头经验完全吻合：驱动表少一行，整体少一个量级。
- 优化器的搜索策略：先枚举/剪枝连接顺序（左深树为主），对每张表枚举访问方法，再按累计成本排序取最优。
  **剪枝意味着「没有被算到的组合不等于不存在」，它也意味着误差可能沿树向上累积**。
- 🔧 `optimizer_search_depth`（控制搜索深度）与 `optimizer_prune_level`（是否剪枝）这类旋钮在部分发行版里仍可影响，
  但把调参当作首选方案通常是本末倒置——**先修统计，再谈调参**。

### 12.6 优化器为什么会选错：七类高频根因

| # | 根因 | 典型症状 | 第一动作 |
| --- | --- | --- | --- |
| 1 | 统计信息过期 | 刚灌入大批数据后突然全表扫 | `ANALYZE TABLE`（见 `13-统计数据.md`） |
| 2 | 范围/等值选择性估算失真 | 命中行数估少，回表成本被低估 | 补直方图、`FORCE INDEX`、改写谓词 |
| 3 | 回表成本权重不符合本机 | 明明覆盖索引更好却全扫 | 用 `optimizer_trace` 看分项 |
| 4 | 隐式类型转换/字符集转换 | 索引「失效」 | 保证列与常量类型一致（`varchar` 对比整数是最常见坑） |
| 5 | `ORDER BY` / `GROUP BY` 的成本被算进临时表与 filesort | 合理索引路线被判贵 | 让排序走索引，或接受临时表 |
| 6 | 连接顺序剪枝过早 | 三表以上的慢查询 | 更新统计、缩小连接规模、用提示限定顺序 |
| 7 | 统计缺失导致「平均分布」假设 | 新表/刚导入数据的首个查询很慢 | 载入后主动 `ANALYZE` |

> 提醒：**优化器选错 ≠ 有 bug**。绝大多数情况是「账单的输入（统计）不准」或「候选集不全（缺索引/缺提示）」。
> 一上来就 `FORCE INDEX` 掩盖问题，会让统计继续腐化，下一次规模变化时会以更慢的方式爆发。

### 12.7 `optimizer_trace` 视角：回答「为什么」

一次会话内的完整读法（教学示意，不参与构建，**未执行**）：

```text
SET optimizer_trace="enabled=on";                  -- 只在需要排查的会话里开
SELECT * FROM t1, t2 WHERE ...;                    -- 触发优化
SELECT * FROM information_schema.OPTIMIZER_TRACE;  -- 或 SELECT ... FORMAT=JSON
SET optimizer_trace="enabled=off";
```

trace 里最值得看的三个字段：

| 字段 | 在告诉你什么 | 怎么用 |
| --- | --- | --- |
| `rows_estimated` vs `rows_actual` | **估算与实际的鸿沟**，成本模型的诊断入口 | 两者差一个数量级 ⇒ 先修统计或建直方图 |
| `considered_access_paths` | 每张表被考虑过的访问方法及其分项成本 | 看「输给谁」，以及被输掉的那项成本是哪个科目 |
| `reconsidering_access_paths` | 读到 `ref` 键之后重新评估是否改用范围扫描的环节 | 「先 ref 后改 range」的抖动就出在这里 |

- 与 `EXPLAIN` 的分工：`EXPLAIN` 告诉你「最终选了什么」（见 `15-EXPLAIN详解.md`），
  trace 告诉你「**为什么**是这个，其他选项报价多少」。**先 `EXPLAIN`，卡住了再 `optimizer_trace`。**
- `optimizer_trace_max_mem_size` 太小会截断 trace，看到的一半是「没写完」，别据半截结论下判断（见 `16-optimizer-trace.md`）。

### 12.8 🔧 2026 视角：成本模型在 8.0 之后补了哪些课

| 能力 | 版本 | 对成本模型的影响 |
| --- | --- | --- |
| 持久化统计 + 采样控制 | 5.6 引入 / 8.0 更完整 | 估算的输入来源变可控 |
| 直方图 | 🔧 8.0 | 等值/范围谓词的选择性估算不再只能靠「平均分布」 |
| `EXPLAIN ANALYZE` | 🔧 8.0.18 | 用**实测**行数与耗时直接对照估算，误差一眼可见 |
| 优化器提示（`JOIN_ORDER` / `JOIN_METHOD` 等） | 🔧 8.0 | 在候选集不完整时把「最优解」硬塞进候选集 |
| 跳过扫描（skip scan） | 🔧 8.0.13 | 给「低选择性列上的分组查询」补了一条新候选路线 |
| 并行读（`innodb_parallel_read_threads`） | 🔧 8.0.x | 只读场景下全表扫描的成本被重新计价 |

> 结论：**5.7 的成本常量在今天只能当教学用的「量纲」**，不是本机的事实。
> 排查顺序建议固定为：读 `EXPLAIN` → 看 `optimizer_trace` 的估算/实际差 → 修统计或补直方图 → 最后才考虑提示与调参。

## 近年研究与工业界开源实践（2015–2026）

- **研究主线**：**基数估算**（cardinality estimation）仍是优化器的第一短板——从采样、直方图一路到**学习型估算**
  与「即时重估」（runtime feedback / feedback loop）。**端到端可观测**是把估算误差变成可诊断数据的关键一步。
- **工业界做法**：把 `EXPLAIN ANALYZE` 的 `actual rows` 回流到慢查询分析流水线，用「估算/实际比值」作为**索引与统计健康的指标**，
  而不是等用户报障。
- **工业界开源**（star 数 2026-09-25 通过 `gh api repos/OWNER/REPO --jq '.stargazers_count'` 实测）：
  - `mysql/mysql-server`（**≈12.4k★**）：成本模型在 `sql/optimizer/`，trace 在 `sql/opt_trace.cc`，常量定义随版本变动。
  - `facebook/mysql-8.0`（**≈115★**）：Facebook 分支在**优化器与成本估算**上的大量工程补丁，是「估算不准怎么救」的样本。
  - `percona/percona-toolkit`（**≈1.55k★**）：`pt-query-digest` 把慢日志汇总成可排序的指纹，是成本问题的**发现**端。
  - `pingcap/tidb`（**≈40.6k★**）：基于代价的自主优化器 + 丰富的统计（直方图、多列统计），值得对照其 `stats` 模块。
  - `clickhouse/clickhouse`（**≈50.1k★**）：以「估算行数 + 分布采样」为核心代价来源，是分析型代价模型的对照。
  - `postgres/postgres`（**≈22.2k★**）：`pg_statistic` + 直方图/MCV 的选择性估算，是 MySQL 8.0 直方图之前的最佳对照。
  - `vitessio/vitess`（**≈21.4k★**）：在代理层做**计划缓存与参数化**，直接影响「带参数进来时优化器看到的是什么」。

| 2 | 「`EXPLAIN` 的 `rows` 就是表的行数」 | 那是**优化器估算**，可能差几个数量级（见 `15-EXPLAIN详解.md`） |
