# 数据页长什么样——「页」是 MySQL 与磁盘之间的最小单位

> **原书位置**：主题对应第 3 章「字符集和比较规则」前后对「记录/页」的铺垫内容，以及第 5 章「盛放记录的大盒子——InnoDB数据页结构」与第 9 章「存放页面的大池子——InnoDB的表空间」。
> 本文件名沿用任务映射表 `03-数据页长什么样.md`。原书基于 **MySQL 5.7.22**。
>
> **一句话**：**磁盘上的一切都是页（默认 16KB）**；页是「空间分配、I/O、缓存、崩溃恢复」四件事的共同单位——
> 空间分配以页为单位，I/O 以页为单位，Buffer Pool 以页框为单位，redo 重做的最小单元也是「某个页的某处被改了什么」。

## 本章地图

| 节 | 内容 | 结论 |
| --- | --- | --- |
| 3.1 为什么是页，而不是字节或记录 | 减少 I/O 次数、减少元数据成本 | 页是**成本折中点**：太小 → 元数据开销大，太大 → 半页浪费 + 恢复代价高 |
| 3.2 页的五种「身份」 | 数据页/索引页、Undo 页、系统页、事务系统页、空闲页（Free）、溢出页 | 一个.ibd 文件里不只有数据页，还有 BLOB 溢出页、段管理页等 |
| 3.3 页与表空间的层次 | 表空间 → 段(segment) → 区(extent，1MB=64 页) → 页(page) → 行(record) | 「段/区/页」这套层级是 **B+ 树的存储映射**，不是逻辑概念 |
| 3.4 区的两种分配策略 | 统一区 vs frag 碎片区（inode 页管理，临时用满后升级为统一区） | 大量单表小表会造成碎片区，空间利用率下降 |
| 3.5 页的物理布局 | 页头(38 字节 File Header) + 页头 Page Header + 虚拟记录 + 最小/最大记录 + 用户数据 + 空闲空间 + 页目录 | 页内是「**变长链表 + 槽位索引**」结构，不是数组 |
| 3.6 页与 Buffer Pool 的关系 | 页 ↔ 页框 1:1，哈希表定位，脏页写回 | 页是磁盘概念，页框是内存概念，二者靠「(space, page_no)」对应 |
| 3.7 与行溢出的衔接 | 数据页只留 20 字节指针，真实数据放溢出页 | 行溢出后一页放不下一行，跨页链表由此产生 |
| 3.8 🔧 8.0 之后 | 页大小仍 16KB 默认；`sdi` 页、数据字典表存放方式变化；独立表空间默认 ON | 🔧 页的「内容分类」在 8.0 变多了（数据字典页、统计信息表页等） |

## 核心精讲

> 以下 SQL / 结构均为**教学示意，不参与构建**：本目录不搭建真实实例，示例只用于对齐概念。

### 1. 页与表空间的层级（教学示意，不参与构建）

```
一个表空间（.ibd 文件或 ibdata1 中的一个逻辑区间）
  └── 若干「段 segment」：叶子节点段、非叶子节点段、回滚段……（B+ 树的每层一个段）
        └── 「区 extent」= 连续 64 个页 = 1MB
              ├── 统一区（full extent）：整区分配给某段
              └── 碎片区（frag extent）：先零星拿页，攒够了升为统一区
                    └── 「页 page」= 16KB（默认）
                          └── 若干「行 record」（COMPACT/DYNAMIC 格式）
```

**为什么有「区」这一层**：如果 B+ 树叶子节点每次只申请一页，文件就会出现大量不连续的散布页，
顺序读会退化成随机读。「区」的意义就是**让 B+ 树的相邻页在磁盘上大概率相邻**。

### 2. 页的内部布局（教学示意，不参与构建，细节见 [05-InnoDB数据页结构.md](05-InnoDB数据页结构.md)）

```
┌──────────────────────────── 16KB ────────────────────────────┐
│ File Header(38B) │ Page Header(56B) │ Infimum │ Supremum │  │
│ 用户记录区（从中间向右生长）              │  Free Space（缺口） │
│                                              │  Page Directory  │
│                                              │  (槽位，从尾部向左)│
└──────────────────────────────────────────────────────────────┘
```

三个「反直觉但正确」的点：
1. 用户记录从**中间**开始向右增长，空闲空间在中间，页目录从**尾部**向左增长；
2. 每条记录自带 `next_record` 指针，页内记录是**单向链表**（所以删除一行只需改指针）；
3. 页目录是**稀疏索引**（槽位存储「该组里最末一条记录的地址」），用于分页查找时快速定位。

### 3. 页的类型清单（教学示意，不参与构建）

| 页类型 | 装什么 | 是否常见 |
| --- | --- | --- |
| 数据页 / 索引页（`PAGE_B-tree`） | 用户记录（叶子=数据，非叶子=索引目录项） | 主力 |
| Undo 页（`PAGE_UNDO_LOG`） | undo 日志记录 | 高频 |
| 系统页 / inode 页 | 段、区的元信息（FSP/HDR/XDES/IBUF/BITMAP 等） | 每表空间头部若干 |
| 事务系统页 | 事务槽位、读写事务链表 | 系统表空间内有 |
| 溢出页 | 大字段的前 20 字节之外的余下数据 | 出现即代表发生过行溢出 |
| 🔧 数据字典页（8.0） | `sdi` 等字典表的行 | 8.0 起字典不再是 `.frm` 文件 |

### 4. 页大小与 I/O（教学示意，不参与构建）

```
一次读取 = 一整页进入页框（16KB）
  ├─ 顺序扫描：每页读一次，成本 ∝ 页数
  ├─ 回表：可能每页读两次（二级索引页 + 聚簇索引页）
  └─ 随机 Insert：若页不在池中，则「先合并 change buffer，再真正读页」
```

推论：**「减少回表」和「减少扫描页数」是同一类优化**——所以覆盖索引、更短的主键、更紧凑的页内填充率，
三者共同决定「一行占多少页」。这也是为什么用 UUID 做主键会让表「突然变大」：
随机主键导致页内填充率下降 + 聚簇索引页分裂更频繁。

### 5. 页分裂与合并（教学示意，不参与构建）

```
B+ 树插入 → 目标页已满 → 页分裂（约复制一半记录）
   ├─ 主键（聚簇索引）：顺序插入时分裂出的两半仍近似有序 → 顺序写
   ├─ 二级索引：同样分裂，可能比聚簇索引更「碎」
   └─ 频繁更新大字段 → 页内页外反复搬动 → 页目录与空闲区碎片化
```

🔧 8.0 起 InnoDB 对页分裂与合并有进一步改进（自适应分裂点等），并可通过
`innodb_buffer_pool_size` 与「更紧凑的行格式」间接缓解。

### 6. 观测（教学示意，不参与构建）

```sql
-- 表空间/页的规模概览（生产上在大实例上要加 WHERE 限制）
SELECT name, engine, data_length, index_length, data_free
FROM information_schema.tables
WHERE table_schema = 'your_db';
```

`data_free` 长期偏大往往是碎片区/未回收空间（与 `ALTER TABLE ... ENGINE=InnoDB` 重建相关，见 [09-表级别的操作.md](09-表级别的操作.md)）。

### 6.1 页大小与 I/O 的粗略换算（教学示意，不参与构建）

```
16KB/页 × 64 页/区 = 1MB/区
1GB 数据 ≈ 65536 页
一次全表扫描 1GB ≈ 65536 次 16KB 读（顺序时，磁盘/SSD 的带宽决定实际耗时）
若每行 200B → 每页约 80 行 → 1GB 约 500 万行
回表一次 → 同样的页数但要读两遍（索引页 + 聚簇页），I/O 近似翻倍
```

用这套换算做「预算式优化」很有效：
**先算出「一列占多少页」，再看有没有必要把它放进热表。**

### 6.2 页相关的常见排障（教学示意，不参与构建）

| 现象 | 与页的直接关联 | 处理方向 |
| --- | --- | --- |
| 表文件大小远大于 `data_length` | 大量碎片区/空洞页 | 重建表（见 09） |
| 写入突然变慢且持续增长 | 页分裂频繁（随机主键） | 换自增/雪花主键 |
| 单表行数很多但查询很快 | 页内填充率高 + 索引命中 | 保持页紧凑即可 |
| 大量小表导致元数据页偏多 | inode 页/段管理页占比高 | 合并小表、减少表数量 |

### 6.3 页与「表空间文件增长」的关系（教学示意，不参与构建）

```
INSERT  → 需要新页 → 从 free list 拿 → 拿不到则从表空间「尾部扩文件 + 分配新页」
                        ↑
                  DROP/TRUNCATE 时若 innodb_file_per_table=ON，则文件本身被回收
                  否则（旧版共享表空间）空间只能留给 ibdata1 继续使用
```

这解释了运维上的一个经典问题：**共享表空间（`ibdata1`）一旦膨胀就很难收缩**，
因为区段一旦分配出去就不能还给操作系统。这也是 8.0 把 undo、doublewrite 逐步从 `ibdata1` 里搬出去的动机之一。

## 版本演进

| 版本 | 关键变化 |
| --- | --- |
| **5.7（原书基线）** | 页大小 16KB；`innodb_file_per_table=ON`；段/区/页模型稳定；`ibdata1` 承载系统表空间（含 change buffer、undo 早期版本） |
| **8.0** | 🔧 **undo 表空间独立化**（默认 `innodb_undo_tablespaces=2`，undo 不再全塞进 ibdata1）；🔧 数据字典 InnoDB 化，字典页进入各表空间的 `sdi`；🔧 `ibdata1` 里 InnoDB 只剩 doublewrite 与 change buffer；独立表空间 `.ibd` 含 `sdi` |
| **8.4 LTS** | 🔧 相关默认值继续收敛（如 change buffer 默认占池 25%、`innodb_dedicated_server` 参与空间分配），文档层面新增「主机内存分配」说明 |
| **9.x** | 🔧 页管理模块与 HeatWave 共存下的 I/O 路径调整，以官方文档为准 |
| **MariaDB / PostgreSQL 对照** | MariaDB 沿用同样的页/extent 概念但实现细节不同；PostgreSQL 的 page 默认 **8KB**，且 tuple 可以跨页（TOAST 之前另有 `TOAST` 之外的行溢出路径），与 InnoDB 的「页内放不下就溢出到页外」有差异 |

## 近年研究与工业界开源实践（2015–2026）

- **`clickhouse/clickhouse`（≈50.1k★）**：列存把「页」换成「 granules + block 批量读」，单次 I/O 更大、更顺序，
  是可对照的「页语义变宽」样本。
- **`facebook/rocksdb`（≈32.1k★）**：以固定大小 block（默认 4KB）为读写单元 + SST 文件布局，
  与 InnoDB 的页在思想上一致，但淘汰与压缩策略完全不同。
- **`pingcap/tidb`（≈40.6k★）**：底层用 RocksDB，其 Region（默认 96MB 区间）概念相当于「逻辑上的大页」，
  分裂/合并由 PD 调度——这是分布式数据库对「页」的一次重新抽象。
- **研究侧**：近年工作集中在 **大页（THP/PMem）下的页管理**、**NVMe 下的页大小选择**、
  **多租户下的空间配额与碎片控制**。
- **线上经验**：`data_free` 高、页内填充率低，通常不是「页的问题」而是「主键随机 + 大量更新/删除」造成的，
  重建表（见 09）是最直接的缓解手段。

## 常见误区与本书需修正之处

| # | 常见误区 | 修正（🔧 = 原书出版时未覆盖） |
| --- | --- | --- |
| 1 | 「一行数据 = 一次 I/O」 | 一页装很多行，I/O 次数 ∝ 页数；一行再大也只占一页的承载量 |
| 2 | 「页越大越快」 | 8.0 默认仍 16KB；页太大反而降低空间利用率并放大恢复代价 |
| 3 | 「表空间的页一定是连续的」 | 区连续、页不保证跨区连续；顺序读性能依赖 B+ 树层的区分配连续性 |
| 4 | 「.ibd 文件里只有数据页」 | 还有 inode 页、BLOB 页、段管理页等，8.0 起还有 `sdi` 页 |
| 5 | 「数据全在 .ibd 里」 | 🔧 8.0 起 undo 在独立 undo 表空间，字典在 `sdi`；`ibdata1` 内容大幅减少 |
| 6 | 🔧 本书未覆盖 | 未覆盖 **8.0 的 undo 表空间独立化**、**ibdata1 内部还剩下什么**、以及 **THP/PMem 对有效页大小的影响** |
| 7 | 「页一旦分配就不能收回」 | 独立表空间下 `DROP`/`TRUNCATE` 会回收文件；共享表空间的已分配区通常不归还 OS |
| 8 | 「页越多越慢」 | 顺序扫描时页多不等于慢；真正慢的是**随机分布导致的非顺序读** |
