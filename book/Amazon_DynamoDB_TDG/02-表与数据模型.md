# 02 · 表与数据模型：键的物理学（⚠️ 重构章题）

> 章定位：DynamoDB 没有「列、行、join」，只有表/条目/属性和一个两键定位模型。本章把官方数据模型语义讲透，并用本机 SQLite 复现「聚簇复合键」这一物理直觉（明确非 DynamoDB 行为）。

## 1. 三层术语对照（先解毒 SQL 思维）

| SQL 世界 | DynamoDB 世界 | 口径 |
|---|---|---|
| 表 schema（列定义） | 表只定义主键 1–2 个属性，其余属性自由、跨条目异构 | ⚠️ 转述（✅ NamingRulesDataTypes.html 200 存目） |
| 行 | 条目 item | ✅ |
| 列 | 属性 attribute（名-值，可嵌套） | ✅ |
| 主键 | 分区键 PK（简单主键）或 PK+排序键 SK（复合主键） | ✅ |
| 一页数据 | 条目集合 item collection：同一分区键下全部条目 | ⚠️ 概念转述 |

- 官方核心组件页 ✅（200）：https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.CoreComponents.html ——本章概念以此页为主题锚。

## 2. 主键设计的物理含义

- 分区键哈希决定条目落在服务内部哪个分区：同 PK 值 ⇒ 同分区 ⇒ 可局部事务/可 Query。⚠️ 转述（服务内部实现不外露，文档口径）。
- 排序键决定分区内聚集顺序：`pk=X AND sk BETWEEN...` 是 DynamoDB 唯一「原生高效」的范围查询形态（03 章 Query）。
- 硬约束（务必记背）：
  - 单条目上限 **400 KB**（✅ 实抓 WorkingWithItems.html 页面原文含「400 KB」与「Item sizes and formats」小节，2026-09-27）。
  - LSI 所在分区数据上限 **10 GB**（✅ 实抓 SecondaryIndexes.html 页面原文含「10 GB」）。
  - PK/SK 类型固定：S/N/B 三种之一（✅ NamingRulesDataTypes 页主题）；分区键哈希宽度等实现细节 ⚠️ 不再展开为数字断言。
- 「400 KB 决定你能不能把视频塞进条目」——正确做法是把大对象放 S3、表里放键 ⚠️ 官方最佳实践通识。

## 3. 类型系统

- 标量：S / N / B / BOOL / NULL；N 为十进制字符串语义、精度上限 ⚠️ 不写死数字（以 NamingRulesDataTypes 页当前版为准 ✅ 存目）。
- 嵌套：M（map）、L（list）——文档模型能力所在，嵌套深度上限 ⚠️ 转述。
- 集合：SS / NS / BS——只能整集合读写、不可寻址元素 ⚠️ 转述；与 Redis set 语义差异对位 [../Learning_Redis/00-总览与阅读地图.md](../Learning_Redis/00-总览与阅读地图.md)。
- SDK 高低层：低层 `{ "S": "x" }` 描述符 vs 高层 DocumentClient 自动映射 ⚠️ 通识转述。

## 4. 🔧 类比一：SQLite WITHOUT ROWID = 「聚簇复合主键」的物理学

方法（本机可复跑，Python 3.13.2 + sqlite3 3.45.3）：

```sql
CREATE TABLE forum (pk TEXT, sk TEXT, body TEXT, PRIMARY KEY(pk,sk)) WITHOUT ROWID;
-- 2000 分区 × 100 条目 = 200k 行
SELECT * FROM forum WHERE pk=? AND sk>=? AND sk<=? ORDER BY sk;
```

实测数字（2026-09-27，D:\develops\tmp\dbwave_w4_dyn\exp.py）：
- 200k 行插入 0.43s；「PK 等值 + SK 范围」形态 ×200 次共 **0.5ms**（平均约 2.5µs/次，命中主键）。
- 同表「只给 SK 不给 PK」定位一次：**51.3ms** 全表扫描。
- `EXPLAIN QUERY PLAN`：`SEARCH forum USING PRIMARY KEY (pk=? AND sk>?)`——键前缀命中即走聚簇序。
- **声明：以上为 SQLite 行为，非 DynamoDB 行为。**类比点只有两条因果：①键前缀决定能否「免费」聚集；②缺前缀则退化为全扫。DynamoDB 里这个退化叫 Scan 且按 WCU/RCU 真实收钱（05 章）。
- 谱系对照：LSM vs B-tree 的存储组织理论在 [../设计数据密集型应用/03-存储与检索.md](../设计数据密集型应用/03-存储与检索.md)；DynamoDB 内部 ⚠️ 社区通识为 LSM 谱系，官方未承诺，不作实证。

## 5. 与文档/宽列模型的正面对照

- vs MongoDB 嵌套文档（[../MongoDB_The_Definitive_Guide_3e/00-总览与阅读地图.md](../MongoDB_The_Definitive_Guide_3e/00-总览与阅读地图.md)）：Mongo 可任意字段查询+索引补位；DynamoDB「没建键的查询≈花钱全扫」，文档自由只体现在非键属性。

## 6. 建模前的三个自检问句

1. 我的 PK 会不会出现「单值热点」（秒杀商品 id 做 PK→单分区超载）？⚠️ 转述最佳实践，症状口径见 05 章自适应容量。
2. 我是否需要「同实体跨键聚合」？需要→GSI 提前规划（04 章），别指望事后免费。
3. 我的条目里谁可能长大？任何会持续追加的 list 属性都是 400KB 炸弹——拆条目或 S3 引用 ⚠️。

## 7a. 建表实操语义清单 ⚠️ 转述（✅ 组件页主题域在架）

- 表名规则：字母数字下划线点连字符、长度区间、区分大小写 ⚠️（NamingRules 域）；同账号同区域唯一。
- 主键一旦定、不可改：改键=新表+迁移+别名切换——这是「键即架构」的字面意义 ⚠️。
- 表状态机 CREATING→UPDATING→ACTIVE，删除有回收窗 ⚠️ 细节不写死。
- 容量与计费属性建表即选（05 章两模式）；加密选项建表即定（09 章）。
- Streams 开关、TTL 属性指针、Global Tables 区域清单都是表级元数据——本章是后续八章的「挂载点总表」。

## 8. 数据类型速查（逐类型多行版）

- S 字符串：UTF-8、空串受限 ⚠️；键列常见型。
- N 数字：以十进制字符串传输、精度上限 ⚠️ 不写死；键列可用、运算仅 ADD 表达式。
- B 二进制：字节串；键列可用 ⚠️。
- BOOL / NULL：原生布尔与空值标记 ⚠️——注意 NULL≠属性缺失，条件表达式里是两种谓词。
- M map / L list：文档嵌套载体；深层访问走点路径 `a.b.c` 与索引 `[i]` ⚠️，UpdateExpression 支持原子下钻（03 章）。
- SS / NS / BS：同构集合，可整删元素、无逐元素计费寻址 ⚠️；NS 上 ADD 可实现原子计数（06 计数器手法前置）。
- 向量：2025-26 起向量检索专用形态（10 章 ✅ 页证）——本节以本书基线口吻保留 ⚠️。

## 7b. 键选择的一页纸判据 ⚠️ 方法论收束

- 先看「最大自然聚簇单元」：用户/会话/订单头——它做 PK 候选。
- 再看「该单元内的排序需求」：时间、类型、序号——它做 SK 候选。
- 校验三件事：基数够散（不热点）、单单元体量有顶（≤10GB/分区口径 ✅、条目≤400KB ✅）、跨单元查询都有索引方案（04 章）。
- 任何一条不过，回 06 章做实体分解/键重排——不要在键上赌服务会宽容。
- 最后把 PK/SK 写进 09 章 IAM 评审：键就是权限边界（LeadingKeys 域 ⚠️）。

## 10. 一句话记忆卡

- 表只定义两个键，其余自由是「读路径的自由豁免」换来的。
- PK 定命运，SK 定秩序，400KB 定生死 ✅。
- item collection 是 DynamoDB 给「局部性」唯一的官方表达。
- 异构属性是文档能力的全部，也是全部。
- 改键=换表：把「不可变」写进设计评审第一行。

## 核心概念速览（中英对照）

1. **表** — table：仅定义 1–2 个主键属性的容器 ✅。
2. **条目** — item：一行级记录，≤400KB（✅ WorkingWithItems 实抓）。
3. **属性** — attribute：名-值对，支持嵌套 M/L，跨条目可异构 ⚠️。
4. **分区键** — partition key：哈希定分区的强制第一键 ✅。
5. **排序键** — sort key：分区内聚集次序的第二键，可选 ✅。
6. **复合主键** — composite primary key：PK+SK，定义 item collection 边界。
7. **条目集合** — item collection：同 PK 的条目群；LSI 的 10GB 约束作用于此（✅ 页含 10 GB 字样）。
8. **标量/嵌套/集合类型** — scalar / nested / set types：S,N,B,BOOL,NULL / M,L / SS,NS,BS ⚠️。
9. **DocumentClient** — high-level API：属性描述符与原生类型自动映射层 ⚠️。
10. **聚簇复合键** — clustered composite key（类比语）：SQLite WITHOUT ROWID 演示的键前缀物理序 🔧。
11. **热点分区** — hot partition / skewed key：单 PK 值吞吐集中的反模式 ⚠️。
