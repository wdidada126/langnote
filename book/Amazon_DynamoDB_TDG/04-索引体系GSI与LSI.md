# 04 · 索引体系：GSI 与 LSI（⚠️ 重构章题）

> 章定位：二级索引是 DynamoDB 唯一「换一种键重新活一次」的机制，也是建模章（06）的前置词表。取证锚：SecondaryIndexes.html ✅200（页面原文含 eventual consistency only、10 GB、Vector indexes 等 2026 现状字样）、bp-indexes-general.html ✅200。

## 1. 定义与不对称性

- **LSI（本地二级索引）**：同分区键、换排序键。表创建时一起声明、不可后加/不可删 ⚠️ 转述；作用域受「分区 10GB」硬约束 ✅（页面原文「10 GB」）。
- **GSI（全局二级索引）**：任意新 PK（可 +SK），独立于基表键；可在线创建、有回填（backfill）状态 INDEX_STATUS ✅ 主题页存目；**只支持最终一致读** ✅ 原文字样。
- 每个索引有自己的键 schema 与**独立吞吐消耗**（GSI 按自身键读写计费 ⚠️），表级配额类约束随服务限额演进 ⚠️ 不写死个数。

## 2. 投影（projection）：复制多少决定费用多少

- 三种模式：KEYS_ONLY / INCLUDE(指定属性) / ALL ⚠️/✅ 主题页存目。
- 心智：索引=「另一张只装必要列的表」；投影 ALL 的宽行大索引 ⇒ 写放大直接吃基表 WCU 之外另计 ⚠️。

## 3. 什么时候必须上 GSI（场景清单）

1. 反向查询：「按订单号找用户」而基表键是用户 → GSI(orderId PK)。
2. 时间线聚合：按天/按主题重聚同一批条目。
3. **稀疏索引（sparse index）**：只有携带索引键属性的条目才进索引——GSI 天然过滤，是最省空间的条件查询技巧 ⚠️ 社区通式（AWS 博客大量示范 ✅ 存目）。
4. 与基表一致性档位差异：GSI 最终一致 ⇒ 写后立读索引结果不可依赖 ⚠️（03 章强一致只在基表）。

## 4. 🔧 类比二：GSI = 辅助表 + 键重排（SQLite 版）

方法（同 02 章数据集，200k 行 forum 表）：

```sql
CREATE TABLE gsi_sk_first (sk TEXT, pk TEXT, PRIMARY KEY(sk,pk)) WITHOUT ROWID;
INSERT INTO gsi_sk_first SELECT sk,pk FROM forum;  -- 一次性「全量回填」
SELECT * FROM gsi_sk_first WHERE sk>=? AND sk<=? ORDER BY sk;
```

实测：回填 200,000 行；「SK 前缀」范围查 ×200 共 **139.4ms**（约 0.7ms/次）。因数据里同一 SK 串跨 2000 个线程重复，单次查询扇出 9.9 万行——恰好演示「GSI 查询天然跨分区扇出，代价随行分布而定」⚠️ 概念类比。
**声明：SQLite 触发器/手工同步是强一致的；DynamoDB GSI 是异步复制、仅最终一致——这是两者最大语义分歧，类比只借「键重排+独立存储」的形状 🔧。**

## 5. 🔧 类比三：GSI 回填与投影成本（DuckDB 版）

方法（DuckDB 1.5.5）：主表 `ev`（200k 行）+ 哈希「索引表」`ev_gsi(body_hash,pk,sk)`。
- 基表键前缀范围查：**3.94ms** 返回 40 行；索引表定值探测（未命中键）：**0.37ms** rows=0。
- 演示要点：索引查询不摸基表大列（投影列独立存储）、未命中也要付一次索引读——「索引只省扫描，不省存在性检查」🔧。
**声明：DuckDB 为本地 OLAP 引擎，无异步复制、无计费，非 DynamoDB 行为。**

## 6. LSI 的战术位与退役趋势

- LSI 优势：与基表同分区、可强一致读、无需独立容量 ⚠️ 转述；劣势：创建时锁死、10GB 分区约束 ✅、灵活性远逊 GSI。
- 社区趋势 ⚠️：新项目普遍直接 GSI，LSI 只剩存量表兼容位。
- 对位表（盘上兄弟怎么讲索引）：Cassandra 二级索引与 SAI 的「代价自知」叙事 [../Cassandra_The_Definitive_Guide/00-总览与阅读地图.md](../Cassandra_The_Definitive_Guide/00-总览与阅读地图.md)（05/10 章域）；Mongo 索引=独立 B 树、可强一致读 [../MongoDB_The_Definitive_Guide_3e/00-总览与阅读地图.md](../MongoDB_The_Definitive_Guide_3e/00-总览与阅读地图.md)（03 章域）。Redis 无索引概念（[../Learning_Redis/00-总览与阅读地图.md](../Learning_Redis/00-总览与阅读地图.md) 02 章「自设二级索引」模式恰与 Dynamo GSI 同思想）✅。

## 7. 索引键选择的三条军规 ⚠️ 转述自 AWS 最佳实践域（✅ bp-indexes-general.html 200 存目）

1. GSI 的 PK 同样受哈希分区命运约束——低基数键在索引里照样热点。
2. 索引数不是免费的：写一条基表 ⇒ N 个索引各写一份（写放大可视化类比 DDIA [../设计数据密集型应用/03-存储与检索.md](../设计数据密集型应用/03-存储与检索.md) 二级索引维护节）。
3. 先列访问模式清单，再上索引；「可能以后要用」的索引就是未来的账单 ⚠️。

## 8. 索引决策矩阵（访问形态 → 键方案）

| 需求 | 首选 | 次选 | 别选 |
|---|---|---|---|
| 主实体按时间拉列表 | 基表 PK+SK(时间前缀) | — | Scan+Filter ⚠️ |
| 反查（另一键找同实体） | GSI(反查键 PK) | 应用层双写两表 ⚠️ | LSI(键不可换) ✅ 约束 |
| 条件过滤类列表 | 稀疏 GSI（缺键即不入） | FilterExpression on Query ⚠️ | 全表 GSI+Scan |
| 分组统计 | 预聚合计数器条目(06) | Streams 下游物化(07) | 实时聚合扫全分区 ⚠️ |
| 相似/语义检索 | 向量索引(10 ✅) | 外部检索栈(ES 册) | 键硬编码相似度 ⚠️ |

- 每加一个索引=写路径多一次复制+独立计费——把矩阵打印贴在表设计评审第一页 ⚠️。

## 9. 索引生命周期操作序 ⚠️ 转述

1. 创建：基表 ACTIVE 后在线建 GSI；状态可见（索引独立进度）。
2. 回填：存量条目异步灌入；回填期查询结果不完整——切换读流量要等 INDEX_STATUS 就绪 ⚠️。
3. 运行：基表写带动索引写；投影宽度决定索引自身吞吐消耗 ⚠️。
4. 修改：索引键 schema **不可变更**——错键=删索引重建，与主键同判「键即命运」⚠️。
5. 删除：删 GSI 释放其配额占用；LSI 不可单删 ✅ 约束。

## 10. 键设计自检（索引版三问）

- 我的 GSI 键基数够吗？一天百万订单用 `day` 做 PK 就再造一个热点 ⚠️。
- 我的投影会随属性增长变 ALL 吗？先 KEYS_ONLY，看需求再加列 ⚠️ 通式。
- 下游能容忍索引读最终一致吗？「写 A 读 B 立即可见」场景必须换方案（强一致基表读/事务）✅。

## 12. 索引故障剧本速查 ⚠️（✅ 状态语义域）

- 症状「GSI 查不到刚写入的条目」→ 预期内（最终一致 ✅ 原词）；改读基表或加读重试窗口，勿加写锁。
- 症状「回填卡住/索引慢」→ 基表写压力挤占索引吞吐 ⚠️：临时扩索引容量或错峰。
- 症状「删了 GSI 费用没降」→ 检查基表是否仍高 WCU——索引删除不减基表写，只减复制份 ⚠️。
- 症状「Query 索引结果乱序」→ 索引键 SK 设计不含序（时间未补零定宽 ⚠️ 06 章前缀编码基本功）。
- 症状「LSI 装不下」→ 10GB 分区顶帽 ✅：要么拆分区键，要么迁 GSI（键重排自由）。
- 复盘口径：索引事故九成回到「键基数/投影宽度/一致性档」三要素，本章 §7 军规逐条对照。

## 13. 一句话记忆卡

- GSI=换一套键重活一次，代价是只还你最终一致 ✅。
- LSI=出生时焊死的把手：同区强一致，分区 10GB 封顶 ✅。
- 投影宽度是索引的账单旋钮，ALL 是最贵档 ⚠️。
- 稀疏是免费的 WHERE，别浪费这个天赋 ⚠️。
- 索引不可改键：和主键同判——键即命运。

## 核心概念速览（中英对照）

1. **LSI** — local secondary index：同 PK 换 SK，建表时定死，分区 10GB 约束 ✅。
2. **GSI** — global secondary index：全新键集，在线可建，最终一致 only ✅。
3. **投影** — projection：ALL / KEYS_ONLY / INCLUDE 三种复制宽度 ⚠️。
4. **回填** — backfill：索引追平存量数据的过程，状态可见 ⚠️。
5. **稀疏索引** — sparse index：缺索引键即不入索引的免费过滤 ⚠️。
6. **写放大** — write amplification：一写多索引副本的成本形态 ⚠️。
7. **跨分区扇出** — cross-partition fan-out：索引查询天然跨全键空间扫 🔧(类比演示)。
8. **最终一致索引读** — eventually consistent index read：写后立读索引不可靠 ✅ 字样。
9. **独立吞吐** — separate throughput：GSI 读写各自计入费用面 ⚠️。
10. **索引反模式** — index as future bill：为想象需求建索引的成本教训 ⚠️。
