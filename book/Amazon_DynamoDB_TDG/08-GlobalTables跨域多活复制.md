# 08 · Global Tables：跨区域多活的工程化（⚠️ 重构章题）

> 章定位：Dynamo 论文的「多区域」理想在产品里的兑现与折衷。取证锚：GlobalTables.html ✅200 实抓——页面原文含「Version 2」「last-writer-wins」「multi-region eventual consistency (MREC)」，本章 2026 现状以该页为准。

## 1. 概念底座：从论文到服务

- 论文侧 ⚠️：跨 DC 异步复制 + 版本向量解决合并（[../../paper/SOSP/doi_10.1145_1294261.1294281/00-精读笔记.md](../../paper/SOSP/doi_10.1145_1294261.1294281/00-精读笔记.md)）。
- 服务侧 ✅：Global Tables=同表在多区域的**多活**复制，冲突以 **last-writer-wins（LWW）** 收敛，官方定性「multi-region eventual consistency (MREC)」——页面原词实抓。
- 与「跨区域备份/只读副本」的区别：多活=每个区域都能写；备份=单写多读。选错档=架构级事故 ⚠️。

## 2. v1 → v2 的世代差 ⚠️ 转述（✅ v2 名称以页面字样为准）

| 维度 | v1（旧世代） | v2（现世代） |
|---|---|---|
| 实现 | 表间双向 Streams 回环，表互指伙伴 ⚠️ | 服务原生复制，一表多区域副本 |
| 编排 | 手动/CFN 多栈拼 | 控制台/CFN 直接添加区域，支持多账号 ⚠️ |
| 迁移 | — | 就地升级 v1→v2 ✅（页面版本条目域） |
| 视图 | 每区独立表 | 全局表+区域副本统一概念 |

- v1 时代 Streams 回环的三个坑（07 章 §4）正是 v2 的立项理由 ⚠️ 推断自两代语义差。

## 3. LWW 的账单：你放弃了什么

- 并发双写同键：晚到者抹掉早到者——**没有合并语义**，不像论文版本向量至少保两版本 ⚠️/✅（LWW 字样 ✅ 页证）。
- 时钟：服务内部时间戳序（epoch+时间戳）⚠️ 细节转述；用户不可见 NTP 问题但受其果。
- 规避手法 ⚠️：①键分区让写「物理分域」（同键只归一个区域写）；②计数器类改「每区一条+读时合并」；③业务必须全序时用条件写/事务限定单区（03 章）。
- DDIA 理论位：[../设计数据密集型应用/05-复制.md](../设计数据密集型应用/05-复制.md) 多主复制的冲突处理章节——Global Tables 是「多主+LWW」的托管标本；一致性时钟深水区在 [../设计数据密集型应用/09-一致性与共识.md](../设计数据密集型应用/09-一致性与共识.md)。

## 4. 延迟、读档与费用 ⚠️ 转述

- 跨区域复制为异步：区外读必为最终一致（MREC 定义 ✅ 页证），区内读仍可强一致（跨区强一致不存在，别在设计评审里许诺）。
- 副本读费按区另计、复制流量计费 ⚠️ 细则页未静态取证，口径「多区成本≈单区×N+复制流量」。
- 灾难恢复切换：任一区可独立承载写；回切后的数据收敛窗口=复制延迟 ⚠️。

## 5. 运维要点 ⚠️ 方法论（✅ 主题域在 GlobalTables 页内）

1. 表创建即声明多区，或事后 add region（v2 支持）——事后加区有回填窗口。
2. 监控按区拆：复制滞后指标（region-level replication latency）是 SLO 一等公民 ⚠️。
3. IAM 与 KMS 跨区配置：每区独立密钥授权链路 ⚠️（09 章衔接）。
4. Streams 与 Global Tables 叠加使用时，流视图/消费拓扑需按区各自部署 ⚠️。

## 6. 对照表：三种「多区域」哲学的分工

- DynamoDB Global Tables：托管多活、LWW、最终一致（本章）⚠️/✅。
- Cassandra 多数据中心复制：可调一致性、用户自管拓扑（[../Cassandra_The_Definitive_Guide/00-总览与阅读地图.md](../Cassandra_The_Definitive_Guide/00-总览与阅读地图.md) 07/08 章域）✅ 盘上。
- MongoDB 跨区部署：以多数派/拓扑标签逼近强一致（[../MongoDB_The_Definitive_Guide_3e/00-总览与阅读地图.md](../MongoDB_The_Definitive_Guide_3e/00-总览与阅读地图.md) 08/09 章域）✅ 盘上。
- 谱系一句话：**自由度与托管度此消彼长**，Dynamo 选了「承诺极简、违约不可能」的那端 ⚠️ 评述。

## 7. 区域拓扑与准入判据 ⚠️ 方法论

- 区域选择三轴：用户地理质心 / 数据驻留红线（09 章 §7）/ 成本梯度 ⚠️。
- 准入自问（任一为「是」即慎入多活）：
  1. 同键是否会被两区并发写且都不可丢？（LWW 必丢一版 ⚠️）
  2. 业务是否需要跨区域读己之写？（区外读=最终一致 ✅ MREC）
  3. 库存/余额/唯一性仲裁类强序逻辑是否内嵌？（应单区收口 ⚠️）
  4. 合规删除能否接受跨区副本+PITR 窗口的复活风险？（09 章联动）
- 反准入（适合画像）：用户档案/偏好/会话/内容状态——「谁赢」不敏感、就近读写收益立现 ⚠️。
- 演练项：断复制、区半死（可写不可读？）、回切滞后清零——每季至少一练 ⚠️。

## 8. LWW 案例三连（纸面推演 ⚠️）

- 案例A 游戏存档：双区各写同档 → 后写抹前写。解法：会话粘滞单区（写随玩家移动换主），换主期用版本哨兵条件写收敛 ⚠️。
- 案例B 点赞计数：LWW 直接丢增量。解法：每区每桶一条计数条目，读侧求和（06 计数器手法+§3-③）⚠️。
- 案例C 商品详情双编辑（运营后台美区+欧区）：编辑冲突应显式化。解法：改「草稿单区主写+发布事件广播」——多活≠必须双活写 ⚠️。
- 三连共同结论：Global Tables 把冲突处理从「合并」降维为「避让」，设计工作从服务端搬到键与流程层 ✅/⚠️。

## 11. 一句话记忆卡

- 多活=到处可写，也=冲突自己会「消失」——LWW 的消失是静默的 ✅⚠️。
- 论文用版本向量保存分叉，服务用时间戳裁决分叉：商用化=把合并改成避让。
- MREC 三个字读作「区外读请当缓存」✅ 原词。
- v2 的历史意义：把「复制正确性」从用户代码收回服务承诺 ⚠️。
- 最诚实的架构文档写法：给每把键写上「归哪个区写」的户口。

## 12. 记忆卡补四行

- 判据一句话：「同键并发双区写都要活」=不兼容；「谁后到谁说话」=欢迎 ⚠️。
- 复制滞后不是 bug 清单项，是你的产品承诺项——UI 文案先于架构认领它 ✅/⚠️。
- 每把键写户口（主写区），每次演练留斜坡（灰度回切），两件事做到就配谈多活。
- 论文读者注意：版本向量的「优雅」在商用托管里换成了「可预期」，01 章六项收编在此结算。
- 加一条判据：能讲清「谁后到谁说话」的业务就上，讲不清的业务先别上——LWW 不接受申诉 ✅⚠️。

## 核心概念速览（中英对照）

1. **全局表** — global table：多区域可写副本集合 ✅ 页证概念。
2. **MREC** — multi-region eventual consistency：官方定性原词 ✅。
3. **后写胜出** — last-writer-wins (LWW)：冲突唯一裁决者 ✅ 原词。
4. **多主复制** — multi-leader replication：DDIA 分类学坐标（05 章）。
5. **v1/v2 世代** — generation：Streams 回环 → 服务原生复制 ⚠️/✅。
6. **就地升级** — in-place conversion：v1→v2 迁移路径 ✅ 域。
7. **写分域** — write partitioning：按区域划分键的 LWW 规避法 ⚠️。
8. **复制滞后** — replication lag：跨区域 SLO 主指标 ⚠️。
9. **单写者承诺** — single-writer discipline：条件写/事务限定区的收敛手段 ⚠️。
10. **回填窗口** — backfill window：新加区域的追数据期 ⚠️。

## 最新演进与工业实践

- **现状口径 ✅**：官方页现名「Global tables version 2」叙事在架（2026-09-27 实抓），v1 仅存量语义；本书（2021-22 推定）覆盖的多为 v1 时代操作，阅读时以 08 章 §2 表为补丁。
- **工业实践 ⚠️**：全球游戏会话/用户档案是最典型负载——「就近读写 + LWW 可接受」的判定即 Global Tables 准入测试；金融余额类因 LWW 直接出局（转单区+跨区只读分析）。
- **论文回声**：Dynamo 论文的「始终可用」在服务里以「任一区可写」保留，「多版本合并」则被 LWW 阉割——对位精读 [../../paper/SOSP/doi_10.1145_1294261.1294281/00-精读笔记.md](../../paper/SOSP/doi_10.1145_1294261.1294281/00-精读笔记.md) 的 quorum 章节，理解「为什么托管=语义收缩」。
- **2025-26 语境 ⚠️**：AWS 将 Global Tables 并入「灾备+边缘就近」双叙事；与 CloudFront/Lambda@Edge 组成的边缘读写栈是无服务器全球化的默认答案（转述，未逐页取证）。
