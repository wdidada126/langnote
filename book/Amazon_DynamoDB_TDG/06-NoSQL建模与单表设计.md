# 06 · NoSQL 建模与单表设计：键即架构（⚠️ 重构章题）

> 章定位：本书（按文体推定）的重头戏。DynamoDB 建模不是「第三范式纠偏」，而是把访问模式编译成键布局。取证锚：single-table vs multi-table 官方博客 ✅200 实抓、bp-modeling-nosql-b / bp-general-nosql-ddl 两页 302 版本跳转 ⚠️ 存目可引。

## 1. 方法论倒置：从 ER 到「访问模式清单」

- 第一步不是画实体，而是穷举应用侧查询：每条写「读/写 × QPS × 键形状 × 一致性档」。⚠️ 方法论口径（官方 best practices 域 ✅ 存目）。
- 范式在 DynamoDB 无执行器支撑：没有 join，跨实体组装要么预连接（denormalize 到条目），要么应用层多读拼接（付多次 RCU）⚠️。
- DDIA 理论对位：[../设计数据密集型应用/02-数据模型与查询语言.md](../设计数据密集型应用/02-数据模型与查询语言.md)（模型与派生数据）与 [06-分区.md](../设计数据密集型应用/06-分区.md)（按键分区的再平衡难题在托管服务里被「你选键」替代）。

## 2. 核心手法卡（社区通称 ⚠️ 转述）

| 手法 | 英文 | 一句话 |
|---|---|---|
| 实体分解 | entity decomposition | 大实体拆成多条目共享 PK，绕 400KB |
| 实体并置 | co-location | 用同 PK 把「要一起读的东西」焊在一个条目集合 |
| 前缀编码 | key prefixing | SK 里编 `TYPE#sub#date` 让 Query 前缀命中多类条目 |
| 稀疏索引 | sparse index | 只有带 GSI 键的条目入索引（04 章复用） |
| 反向索引 | inverted index | GSI 键反转，服务「另一头查」 |
| 计数器条目 | counter item | ADD 原子累加 + TTL 分桶 ⚠️ |
| 锚定/别名 | anchoring/alias | 跨实体关系用指向键而非外键求值 ⚠️ |

- 上述手法组合的极端形态=**单表设计**（一个业务域全部实体挤进一张表+两三个 GSI）；其旗手为 Rick Houlihan《The DynamoDB Book》⚠️ 转述（非本书、非 Packt，00 §3 谱系表已辨析）。

## 3. 🔧 类比五：宽行 vs 窄行的「读取代价」实验（非 DynamoDB 行为）

方法：SQLite 表 `items(pk PRIMARY KEY, blob)`，两条记录分别存 400KB 与极小载荷，每次新建连接做 PK 点查 20 次取中位数（exp.py A4 段，Python 3.13.2 / sqlite3 3.45.3）：
- 小行（实测落库仅 1B——`'y'*1024` 在 SQL 里被数值强制成 `0`，属实验插曲，如实登记）：**0.06ms**。
- 400KB 大行：**0.36ms**（约 6 倍）。
- 解读与分歧声明：B-tree 页式存储下整行读代价增长温和（≈6×）；而 DynamoDB 按 §2 计费模型同尺寸差是 **1→100 RCU（100×）**——「行尺寸税」在服务侧远比本地引擎陡峭，这正是「实体分解」手法存在的经济学理由 🔧⚠️。

## 4. 单表 vs 多表：官方的收口（2022 博客 ✅ 实抓）

- AWS 官方博客明确：单表=「按访问模式聚合」，多表=「按实体聚合」；两者都合法，**服务配额与热点治理**才是取舍轴——表数撞账号级配额、单表省钱但键空间拥挤易误伤 ⚠️/✅ 混合（原文口径：以访问模式定表，反对为省成本强行一表）。
- 2026 文档侧已提供 per-table 指标/配额治理工具，「表太多管不动」的原始动机被部分消解 ⚠️ 转述。
- 判据口诀 ⚠️：访问模式高度共享键空间→单表；模式互不相干或需物理隔离配额→拆表。

## 5. 反模式刑场 ⚠️ 转述（社区复盘通识）

1. 自增 id 做 PK：哈希均匀性崩坏+尾部热点 → 改哈希散列或加桶前缀。
2. 无界 list 属性：评论越写越大的「定时炸弹条目」→ 拆条目集合。
3. 「先 Scan 再说」：上线三周后账单十倍 → 键规划期补齐 GSI。
4. 把 DynamoDB 当消息队列：Streams 有 24h 保留窗口约束（07 章）→ 队列职责给 SQS/Kinesis ⚠️。
5. 过度单表：一个表塞下八个限界上下文，GSI 键命名冲突、权限难以按域切分 ⚠️。

## 8. 建模工作坊十步（评审可直接抄 ⚠️ 方法论）

1. 穷举访问模式：写「谁以什么频率按什么键读/写什么」到可数为止。
2. 标注每条模式的延迟/一致性档位需求。
3. 圈出最大自然聚簇单元 → 基表 PK 候选。
4. 圈出单元内排序需求 → SK 候选（定宽时间前缀优先）。
5. 把剩余模式交给 GSI 候选清单：每候选写投影最小集。
6. 对每条模式做 RCU/WCU 纸面折算（05 章 §8 计算器）。
7. 热点体检：低基数键、时间尾部、全局单行——逐个上桶/后缀/分解手法。
8. 决定表数：按 §4 官方判据（访问模式共享度+配额治理）。
9. 写迁移与回填预案（索引生命周期见 04 章 §9）。
10. 出「模式-键-索引-费用」四栏对照表，进评审与告警阈值设定（09 章）。

## 9. 迷你案例两个（纸面演化，非真实服务数据 ⚠️）

### 9.1 论坛表三步演化
- V0 关系惯性：posts 表自增 id 做 PK → §5 反模式 1+2 双踩。
- V1：threadId 做 PK、时间定宽做 SK、回帖=同集合条目 → Query 天然分页；楼中楼用 SK 里编 `REPLY#parentId` 前缀。
- V2：加 GSI(author, threadId) 支撑「我的发帖」列表——稀疏化：草稿条目不写 author 索引键即不入 ⚠️。
- 全程检验：无一条「按内容关键字搜」——那是检索栈的活（ES 册），别在 Dynamo 上 Scan 硬扛 ⚠️。

### 9.2 订单表读模型拆分
- 基表键：orderId PK——点查快，但「买家订单列表」无键可用。
- 方案对比：①GSI(buyerId, createdAt)：一次写两份、最终一致读 ⚠️✅；②Streams 下游物化买家维度表（07 章）：可加富化逻辑、多一份表运维 ⚠️；③双写两表：一致性责任回到你的代码——最贵的自由 ⚠️。
- 判据复用 §4：买家读频率高、无富化需求→①；需要搜索/推荐联动→②。

## 11. 一句话记忆卡

- 先清单后建表：访问模式是需求说明书，键是施工图纸。
- 没有 join 的数据库里，反规范化是日常，不是堕落 ⚠️。
- SK 里编前缀，等于把两张表焊进一个条目集合。
- 稀疏 GSI：不写的自由，也是索引的能力。
- 会长的属性=会爆的属性：无界 list 是延时炸弹 ⚠️。
- 单表是「按访问聚合」不是「按省钱聚合」——官方判据 ✅ 别念反。
- 低基数 PK 是自增 id 的转世，热点永不为新人让路 ⚠️。
- 评审桌上最贵的一句话：「以后可能要按这个字段查」。

## 12. 记忆卡补三行

- 宽行实验 6× vs 账单 100×：本地引擎的宽容会惯坏云端的设计（🔧 §3）。
- 访问模式清单会过期：每次大迭代重跑 §8 十步，别供着旧表结构。
- 「把 DynamoDB 用成对的」与「用成贵的」是同一份图纸的正反面。

## 核心概念速览（中英对照）

1. **访问模式优先** — access-pattern-first：先清单后建表的方法论 ⚠️。
2. **反规范化** — denormalization：以存储与写放大换读路径单一 ⚠️。
3. **单表设计** — single-table design：全业务域挤一表+GSI 的手法（✅ 官方博客定性）。
4. **实体分解** — entity decomposition：大实体拆条目集合 ✅ 概念/⚠️ 细则。
5. **并置** — co-location：同 PK 焊住一起读的数据 ⚠️。
6. **前缀编码** — key prefixing：SK 内编类型/日期做路由 ⚠️。
7. **稀疏 GSI** — sparse GSI：缺键即不入索引的过滤 ⚠️。
8. **宽行** — wide item：逼近 400KB 的条目，读费 100× 化 🔧⚠️。
9. **尾部热点** — hot tail / skewed key：自增键的分区灾难 ⚠️。
10. **无界增长属性** — unbounded attribute：会撑爆上限的 list 字段 ⚠️。
11. **表配额治理** — table quota governance：拆表的官方新理由（✅ 博客域）。

## 最新演进与工业实践

- **官方立场文件 ✅**：Single-table vs. multi-table（2022-08，博客 200 实抓）至今仍是 DynamoDB 建模争论的收口文本；2024+ 文档最佳实践域持续同调（bp-modeling 页 302 在架可引 ⚠️）。
- **《The DynamoDB Book》影响 ⚠️**：单表方法论社区传播主源；注意其立场比 AWS 官方更激进（「almost always single table」），读书时把 §4 官方判据当平衡器。
- **2025-26 新变量：向量索引（10 章 ✅ 实抓）**：「嵌入存条目 + 专用索引」把「相似检索」纳入键模型之外第三读法，单表叙事出现新张力——按访问模式建表的元规则不变。
- **工业实践 ⚠️**：游戏会话与 IoT 状态类应用普遍「单表+稀疏 GSI+时间前缀 SK」；SaaS 多租户加 `tenant#` 前缀分区防串热。盘上对位：[../nosql精粹.md](../nosql精粹.md)（占位存目）、MongoDB 3e 第 05 章域「模式与反规范化对照」。
