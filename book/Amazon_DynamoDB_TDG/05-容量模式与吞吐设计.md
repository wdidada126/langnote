# 05 · 容量模式与吞吐：计费即物理（⚠️ 重构章题）

> 章定位：在 DynamoDB 里「性能问题=账单问题=布局问题」三位一体。RCU/WCU 不是报表指标，而是设计输入。取证锚：Introduction.html ✅200（原文含 on-demand、single-digit millisecond）、DAX.html ✅200、Programming.retries.html ✅200；计费换算细则页 302（版本化跳转）⚠️ 转述。

## 1. 两种容量模式

| 模式 | 语义 | 适合 |
|---|---|---|
| 预置 provisioned | 显式买 RCU/WCU 配额，可调自动伸缩目标 ⚠️ | 负载可预测、想压单价 |
| 按需 on-demand | 不设配额按用量付费，官方页证实存在 ✅ | 脉冲/未知负载、原型期 |

- 模式可互转 ⚠️ 转述；按需单价更高换弹性——「先按需探形、再预置定型」是社区通行路径 ⚠️。
- 预置模式的自动伸缩（target utilization）与**自适应容量**（adaptive capacity，热点分区临时放行）⚠️ 均为转述口径，未逐一取静态页证。

## 2. RCU/WCU 换算模型 ⚠️ 转述（模型本身即考点）

- 1 写容量单位 WCU = 每秒写 1 个 ≤**1KB** 条目；1 读容量单位 RCU = 每秒读 ≤**4KB** 最终一致条目；强一致读双倍 ⚠️。
- 读费按「命中条目大小向上取整到 4KB」——**这就是宽行税**；投影不减读费（先定位后裁剪）⚠️。
- 🔧 类比四（RCU 算术模型，本机真实计算，非计费行为）：对 02 章 forum 表抽样 4000 行，平均条目 226B → ceil(226/4096)=**1 RCU**；构造 1KB → 1 RCU；400KB（上限宽行）→ ceil(400KB/4KB)=**100 RCU**。同一次点查，400KB 行比典型小行贵 100 倍——数字由 Python `math.ceil` 实算（exp.py A3 段）🔧。
- 结论式建模军规 ⚠️：把「每请求 RCU 数」当容量预算单位来评审表结构，与「每请求毫秒」同等地位。

## 3. 限流与退避（服务侧物理）

- 超配额返回 `ProvisionedThroughputExceededException`（HTTP 400 语义）✅ 主题在 retries 页 200；指数退避+抖动是标准客户端姿势。
- 分区级限流先于表级：热点 PK 单分区顶帽 ⚠️；自适应容量会「代管」热点但费用惩罚 ⚠️。
- 批量写部分失败语义：BatchWriteItem 返回 UnprocessedItems 需回灌 ⚠️ 转述。

## 4. 缓存层：DAX 与 Redis 的分野

- **DAX**（✅ DAX.html 200 存目）⚠️ 转述要点：集群内存写穿（write-through）缓存，应用端点替换 SDK 即用，默认项 TTL 短（分钟量级）；只加速读路径，最终一致语义。
- 对比 Redis（[../Learning_Redis/00-总览与阅读地图.md](../Learning_Redis/00-总览与阅读地图.md) 02/03/05 章域）：Redis 是通用数据结构服务器、自己负责一致性与失效；DAX 是「DynamoDB 协议兼容的托管读缓存」，写穿由服务维护。选型问句：你要缓存「对象」还是要「数据结构+副作用」⚠️。
- 对位盘上另一册：[../Redis_Cookbook](../Redis_Cookbook/) 目录在册（缓存模式百科），本册不重复其内容。

## 5. 容量估算工作流（考试与生产通用）⚠️ 方法论转述

1. 列访问模式：读写 QPS × 平均/最坏条目尺寸 → 直接折 RCU/WCU（用 §2 的 ceil 算术）。
2. 峰值系数与增长斜率 → 预置值 + 自动伸缩或按需兜底。
3. 压测路径：本地替身（DynamoDB Local，功能子集 ⚠️）无法复现限流，容量验证只能在云测试环境——本册无账号，全部止步于算术模型 🔧+⚠️。

## 8. 容量速查表（纸面计算器 ⚠️ 模型口径 + 🔧 实算）

- WCU 需求 = ceil(条目KB→1KB 进位) × 写QPS ⚠️ 模型。
- RCU 需求 = ceil(条目B→4KB 进位) ×（最终一致?1:2）× 读QPS ÷ 分页折算 ⚠️ 模型。
- 🔧 三例实算（Python math.ceil，exp.py A3 变体，数字即结论）：
  - 例1 会话表：条目 300B、读 5k/s 最终一致 → ceil(300/4096)=1 ⇒ 5000 RCU。
  - 例2 档案表：条目 50KB、读 200/s 强一致 → ceil(51200/4096)=13、×2 ⇒ 5200 RCU——同 QPS 下为例1 的 **1.04 倍**，全因尺寸×一致性。
  - 例3 富文本条目 400KB：单次 Get 计费颗粒=100 RCU；宽行瘦身 8 倍 ⇒ 颗粒费直接除 8。
- 写侧同理：1KB 进位让「小写高频」与「大写低频」在 100KB 条目上差 100 倍 WCU ⚠️ 模型口径。

## 9. 模式选择决策流 ⚠️ 方法论

1. 负载未知/尖峰比>10 → on-demand 起步 ✅ 名词页证。
2. 稳定可预测 → 预置 + 自动伸缩目标（保守起步 70% 利用率口径 ⚠️）。
3. 热点疑似（键基数低/时间尾部）→ 先修布局（06 章）再谈扩容——自适应容量是救火不是防火 ⚠️。
4. 读占绝对大头且容忍陈旧 → DAX ✅ 存目；要数据结构副作用 → Redis 对位（[../Learning_Redis/00-总览与阅读地图.md](../Learning_Redis/00-总览与阅读地图.md) 07 章解决方案域）。
5. 跨模式切换评估：按需单价 vs 预置利用率的盈亏平衡点在「利用率>~40-50%」区间 ⚠️ 社区通识比例，非官方数字。

## 11. 限流事故复盘四问 ⚠️ 方法论（✅ 主题域 retries 页）

1. 是表容量不足，还是单分区顶帽？看 ConsumedRCU 总量 vs 分片分布两个信号，只有后者指向键布局。
2. 退避参数是否在放大雪崩？无抖动的同步退避让脉冲负载同相重试 ⚠️。
3. 强一致读是否无差别铺开？逐模式审计：多数 UI 读容忍陈旧，换最终一致直接减半（§2 模型）。
4. 按需是不是更便宜的答案？把实际利用率代入 §9 步骤 5 的区间判断 ⚠️。
- 加分题视角：限流不是「容量不够买一点」的问题，而是「访问模式撞了分区物理」的问题——06 章手法卡在此显形 ⚠️。

## 13. 一句话记忆卡

- 读 4KB 进位、写 1KB 进位：尺寸是隐藏乘数（🔧 1→100 实算）。
- 强一致=双倍 RCU：为新鲜感付的明确税 ⚠️✅。
- 限流先查分区顶帽，再查表配额——顺序别反 ⚠️。
- 退避要带抖动，否则你的客户端会同相尖叫 ⚠️✅。
- DAX 管「读多且可旧」，Redis 管「结构且要活」——先问语义再上缓存。
- 按需起步、预置定型、热点修键：三步是同一件事的三种时刻。

## 核心概念速览（中英对照）

1. **预置容量** — provisioned capacity：买配额 + 自动伸缩模式 ⚠️。
2. **按需容量** — on-demand capacity：按用量计费、免配额规划 ✅ 页证。
3. **RCU** — read capacity unit：4KB 最终一致读/秒 的单位；强一致×2 ⚠️。
4. **WCU** — write capacity unit：1KB 写/秒 的单位 ⚠️。
5. **宽行税** — item-size billing penalty：条目越大每次读写费数级跳（🔧 1→100 RCU 实算）。
6. **自适应容量** — adaptive capacity：服务对热点分区的临时放行 ⚠️。
7. **限流** — throttling：超配额 4xx + 退避重试 ✅ 主题页。
8. **指数退避+抖动** — exponential backoff with jitter — 标准限流客户端策略 ✅。
9. **UnprocessedItems** — 批量写残差：需自行回灌 ⚠️。
10. **DAX** — DynamoDB Accelerator：托管写穿最终一致读缓存 ⚠️（✅ 页面存目）。
11. **写穿缓存** — write-through cache：与 Redis 自管失效模式的对照轴 ⚠️。
12. **贡献者洞察** — Contributor Insights：热点键观测 ⚠️。
