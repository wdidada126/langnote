## 核心精讲

（以下为教学性梳理，代码均**教学示意，不参与构建**。）

### 4.1–4.2 业务流程与表结构（教学示意）

```text
# 教学示意，不参与构建：抢红包两条主链路
发红包: 用户发起 -> 生成红包总额/个数 -> 预生成金额(二倍均值法) -> 写 DB(待抢) + 写 Redis(库存=个数)
抢红包: 用户点击 -> Redis DECR 库存(原子) -> 若>0 则分到金额 -> 异步/同步落 DB 明细 -> 返回
```

- **表**：`红包表`（总额、个数、已抢、状态）、`红包明细表`（用户、金额、时间）。

### 4.3 二倍均值法（随机金额算法）

```text
# 教学示意，不参与构建：二倍均值法
剩余金额 M，剩余个数 N（N>=1）
每次可抢上限 = M / N * 2
本次金额 = random(0.01, 上限)，最后一次直接拿剩余
性质：每次期望=M/N，且不会出现某人拿走近全部
```

这是工程上最常用、足够公平的近似；**不是**精确正态分布，但简单稳健。

### 4.4–4.5 发与抢（教学示意）

```java
// 教学示意，不参与构建：抢红包核心——Redis 原子扣减防超发
Long remain = redisTemplate.opsForValue().decrement("redpacket:stock:" + packetId);
if (remain != null && remain >= 0) {
    // 抢到名额：分配金额（可 Lua 保证原子），落库明细
    redPacketService.recordDetail(userId, amount);
    return amount;
} else {
    redisTemplate.opsForValue().increment("redpacket:stock:" + packetId); // 回补
    return null; // 已抢光
}
```

- **关键点**：用 Redis 的 `DECR`（原子）做库存 gate，避免多线程/多请求「超发」；
  金额分配与 DB 落账要在「抢到名额」之后，且最好用 Lua 脚本或事务保证原子。

### 4.6–4.7 压测与优化

- **JMeter 压测**暴露的典型问题：超发（未原子扣减时）、DB 成瓶颈、明细表锁竞争。
- **优化方向（书中给出并实战）**：
  1. 库存扣减走 Redis 原子操作 / Lua；
  2. 金额分配与明细落库**异步化**（消息队列，预告第 5–6 章）；
  3. 数据库批量/分库分表；
  4. 缓存预热与防雪崩（呼应第 3 章）。

## 版本演进

- **本书无第二版**；本节写 2020 年口径 → 2026 年视角。
- **🔧 Lua 脚本已是 Redis 原子操作的标配**：2020 年本书强调 `DECR` 原子，但「扣库存 + 取金额 + 落账」
  多步需原子时，2026 年统一用 **Lua 脚本**（EVAL）或 Redis 7 的 **Functions**，避免竞态。
- **🔧 异步化首选成熟消息队列**：本书在 4.7 提到异步，正式方案在第 5–6 章 RabbitMQ；
  2026 年也可选 Kafka/RocketMQ/Pulsar（见 00-缺口）。
- **🔧 库存类场景的 Redis 模块**：2026 年 Redis 的 `INCR`/`DECR` 仍适用，但高并发库存更常见落地为
  Redis + 本地缓存 + 限流（Sentinel/Resilience4j）组合，本书未覆盖限流。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「先查库存再扣减」安全 | 两步非原子，并发下必超发；必须原子 `DECR`/Lua |
| 2 | 「Redis 扣了就一定能落库」 | 需处理「抢到名额但落库失败」的回补/补偿逻辑 |
| 3 | 「二倍均值法绝对公平」 | 只是近似均匀，非精确正态；且依赖随机种子质量 |
| 4 | 「压测通过=线上稳」 | 压测环境/数据分布常与线上不同，需容量规划 |
| 5 | 🔧 本书多步操作未统一 Lua | 2026 年多步原子用 Lua/Functions，减少竞态窗口 |
| 6 | 🔧 本书异步化只铺垫未展开 | 正式异步方案在第 5–6 章，且 2026 可选 Kafka/RocketMQ |
| 7 | 🔧 本书缺限流/防刷 | 抢红包需限流+风控，2026 用 Sentinel/Resilience4j，本书未覆盖 |
