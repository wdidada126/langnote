## 核心精讲

（以下为教学性梳理，代码均**教学示意，不参与构建**。）

### 6.1 死信队列（DLQ）

- **死信（Dead Letter）**：一条消息在以下情况会变成「死信」：
  1. 被消费者 **`basicReject`/`basicNack` 且 `requeue=false`**；
  2. 消息 **TTL 过期**；
  3. 队列**达到最大长度**装不下了。
- **死信队列**：给业务队列配 `x-dead-letter-exchange`（和可选 `x-dead-letter-routing-key`），
  上述死信会被转发到指定的 Exchange/Queue，便于**告警、重试、人工处理**——而不是默默丢。

### 6.2 死信实战（教学示意）

```java
// 教学示意，不参与构建：声明一个带死信转发的队列
@Bean
public Queue orderQueue() {
    return QueueBuilder.durable("order.normal")
        .withArgument("x-dead-letter-exchange", "order.dlx")
        .withArgument("x-dead-letter-routing-key", "order.close")
        .build();
}
```

### 6.3 延迟队列 = 普通队列 + TTL + 死信（教学示意）

```text
# 教学示意，不参与构建：订单支付超时流程
1) 下单成功 -> 发消息到 "order.delay"（带 TTL=30min）-> 不绑定消费者
2) 30min 后消息 TTL 过期 -> 变死信 -> 转发到 DLX "order.dlx" -> 进 "order.close" 队列
3) 消费者监听 "order.close" -> 查订单：若仍"未支付"则关单；已支付则忽略
```

- **核心技巧**：延迟队列在 RabbitMQ 里**没有原生类型**，是用「**消息 TTL + 死信转发**」组合模拟的。
  这是本章最重要的工程知识点。
- **注意坑**：RabbitMQ 的队列级 TTL 是「队头阻塞式」——如果队列里前面的消息 TTL 更长，
  后面短 TTL 的消息会被前面挡住。生产常用**「插件 `rabbitmq_delayed_message_exchange`」**或
  **「每延迟档位一个队列」**规避。本书 6.3 实战需留意这一点。

### 6.4 总结

死信 + 延迟是「可靠消息 + 定时任务」的解法之一；它与第 7 章的锁一起，构成并发控制的两条主线
（一个解耦异步、一个互斥串行）。

## 版本演进

- **本书基于 RabbitMQ 3.x**；到 2026 年：
- **🔧 延迟消息的官方化**：`rabbitmq_delayed_message_exchange` 插件已成熟，是 2026 年做延迟队列的
  **首选**（避免 TTL + 死信的队头阻塞坑）；本书只讲 TTL+死信组合，需补插件方案。
- **🔧 流式队列（Stream）也能做延迟/重放**：RabbitMQ 3.9+ Stream 支持按偏移消费，2026 年多一种选择。
- **🔧 延迟任务的替代方案**：2026 年也可用「数据库定时扫描 + 分布式调度（XXL-JOB/Elastic Job）」
  或「Redis ZSet 分值定时」做关单，不一定非走 MQ；选型见 00-缺口。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「RabbitMQ 有原生延迟队列」 | 没有；是 TTL + 死信组合，或 `rabbitmq_delayed_message_exchange` 插件 |
| 2 | 「TTL 队列延迟很准」 | 队列级 TTL 有队头阻塞：前面长 TTL 会挡住后面短 TTL |
| 3 | 「死信=出错才用」 | 过期、满队列也会进死信，不只是消费失败 |
| 4 | 「关单只用 MQ 延迟」 | 也可用定时任务/Redis ZSet；且需防「已支付仍被关单」（消费幂等） |
| 5 | 🔧 本书未提延迟插件 | 2026 首选 `rabbitmq_delayed_message_exchange` 插件，规避队头阻塞 |
| 6 | 🔧 本书延迟方案单一 | 2026 可选 Kafka 定时/topic、RocketMQ 定时消息、调度框架，需横向比 |
