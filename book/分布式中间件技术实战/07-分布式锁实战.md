# 第 7 章　分布式锁实战

> 原书第 7 章是**并发控制的集中章**：系统讲「分布式锁」为什么需要、三种主流实现
> （数据库 / Redis / ZooKeeper），并落地一个「书籍抢购」场景。这是本书里**唯一用到 ZooKeeper 的地方**
> （也是它宣传「协调中间件」却只给锁实现的落点），第 8 章的 Redisson 锁是它的「升级版」。

## 核心精讲

（以下为教学性梳理，代码均**教学示意，不参与构建**。）

### 7.1 为什么需要分布式锁

- 单机 `synchronized`/`ReentrantLock` 只管一个 JVM 内的线程；**多实例部署时，锁要跨进程**，
  必须借助一个所有节点都能访问的「第三方协调者」（DB / Redis / ZK）。
- 好锁的要素：**互斥、可重入、防死锁（超时/自动释放）、容错（协调者挂了怎么办）、尽量高性能**。

### 7.2 数据库实现（教学示意）

```sql
-- 教学示意，不参与构建：悲观锁扣库存
BEGIN;
SELECT stock FROM book WHERE id=1 FOR UPDATE;   -- 行锁
UPDATE book SET stock=stock-1 WHERE id=1 AND stock>0;
COMMIT;
```
- 优点：无需额外中间件；缺点：DB 成瓶颈、行锁范围有限、`FOR UPDATE` 长事务易锁等待。

### 7.3 Redis 实现（教学示意）

```java
// 教学示意，不参与构建：SET NX EX 加锁 + 唯一 value 防误删 + Lua 解锁
String token = UUID.randomUUID().toString();
Boolean ok = redisTemplate.opsForValue()
    .setIfAbsent("lock:book:1", token, Duration.ofSeconds(10)); // NX + EX 原子
if (Boolean.TRUE.equals(ok)) {
    try { /* 临界区：扣库存 */ }
    finally {
        // 用 Lua 保证「只删自己的锁」，避免误删别人刚拿到的锁
        String script = "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end";
        redisTemplate.execute(new DefaultRedisScript<>(script, Long.class),
                              List.of("lock:book:1"), token);
    }
}
```
- **关键点**：`NX EX` 必须**一条命令原子**（否则「加了锁还没设过期」时崩溃会死锁）；
  解锁必须**校验 value 再删**（否则可能删掉别人的锁）；锁内业务超时需要**看门狗续期**
  （这正是第 8 章 Redisson 帮你做的）。

### 7.4 ZooKeeper 实现（教学示意）

```text
# 教学示意，不参与构建：临时顺序节点抢锁
1) 在 /locks/book 下创建 临时顺序节点 /locks/book/seq-00000001
2) 看自己是不是序号最小的节点 -> 是则获锁
3) 不是 -> Watch 前一个序号节点，等它释放(删)后被唤醒再判断
4) 客户端会话断开 -> 临时节点自动删除 -> 锁自动释放(天然防死锁)
```
- ZK 的**临时节点（Ephemeral）+ 顺序节点（Sequential）**天然解决「崩溃防死锁」；
  但**性能比 Redis 低**（写要过 ZK 集群、有网络往返），且需要维护 ZK 集群。

### 7.5 书籍抢购实战

- 用上述任一锁把「查库存 → 扣库存」包成临界区，避免多实例同时扣导致**超卖**。
- 工程上更常见的是「Redis 原子扣减（第 4 章）+ 锁兜底」，而非全程持锁。

## 版本演进

- **本书无第二版**；本节写 2020 年口径 → 2026 年视角。
- **🔧 Redisson 封装是 2026 默认做法**：手写 7.3 的 `SET NX` + Lua + 看门狗容易出 bug，
  第 8 章 Redisson 的 `RLock` 已内置看门狗续期、可重入、公平锁——这是 7.3 的工程化答案。
- **🔧 ZK 锁的现代化**：2026 年直接用 **Curator 的 `InterProcessMutex`**（封装了 7.4 的全部细节）；
  且 ZK 锁因性能多被用于「选主/配置」而非高 QPS 抢锁，高并发抢锁首选 Redis/Redisson。
- **🔧 锁的替代：乐观锁/无锁**：很多场景用数据库 `version` 乐观锁或 Redis 原子操作即可，
  不一定需要显式分布式锁（呼应第 4 章）。

- **Redisson 与 Curator 是两条事实标准**：Java 侧分布式锁几乎都走这两者，而非手搓。
- **RedLock 争议**：Redis 作者提出的 RedLock 曾被分布式系统专家 Martin Kleppmann 质疑
  （基于系统时钟假设）；2026 年生产多以「单 Redis 实例锁 + 兜底」或「Redisson 多锁分段」务实处理，
  而非盲信 RedLock 的强安全宣称。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「`SETNX` 之后 `EXPIRE` 两步走」安全 | 两步非原子，崩溃会死锁；必须用 `SET NX EX` 一条命令 |
| 2 | 「解锁直接 `DEL`」 | 可能删掉别人的锁；必须校验 value（Lua）再删 |
| 3 | 「拿锁后随便跑，不会超时」 | 业务超时需要看门狗续期，否则锁过期别人进来 → 超卖 |
| 4 | 「ZK 锁性能比 Redis 好」 | 反之；ZK 写有集群往返，高 QPS 抢锁首选 Redis/Redisson |
| 5 | 「数据库 `FOR UPDATE` 万能」 | DB 成瓶颈、长事务锁等待，不适合高并发 |
| 6 | 🔧 本书 ZK 只给锁实现 | ZK 真实能力远大于锁（Watcher/配置中心/选主），需另读 `../ZooKeeper-分布式过程协同技术详解.md` |
| 7 | 🔧 本书手搓锁易错 | 2026 直接用 Redisson `RLock` / Curator `InterProcessMutex`，内置续期与可重入 |
| 8 | 🔧 本书未提 RedLock 争议 | 2026 对 RedLock 安全假设有质疑，生产务实处理 |
