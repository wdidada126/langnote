# 第 5 章 复制：接受分歧与弱一致（Replication: accepting divergence）

> 覆盖原书第 5 章（Reconciling different operation orders / Amazon's Dynamo /
> Disorderly programming / CRDTs / The CALM theorem / What is non-mononicity good for? /
> The Bloom language / Further reading）。
> 本章是全书最「超前」的一章：作者在 2013 年就系统讲了 CRDT 与 CALM，
> 而这两件事在 2026 年才真正大规模进入产品——因此本章的补丁方向与前几章相反：
> **不是修正结论，而是补上「后来真的发生了」**。

## 本章地图

> 一句话：**如果不想在分区时放弃可用性，就必须放弃强一致；放弃强一致的代价由「合并」承担，
> 而合并有两种做法：让数据结构天然可合（CRDT），或让计算逻辑天然单调（CALM）。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Reconciling different operation orders | 分区恢复后如何收敛 | 可交换操作直接收敛，不可交换操作必须引入顺序（=协调） |
| Amazon's Dynamo | 一致哈希、部分 quorum、向量时钟、读修复、gossip/Merkle、PBS | **概率性**最终一致：能检出冲突，但不保证等价于某个正确串行执行 |
| Disorderly programming | 无序编程 | 把操作设计成可交换的（credit/debit、max），就能免协调 |
| CRDTs | 结合律 + 交换律 + 幂等律 = 半格 | **强保证**最终一致：结果等价于某个正确串行执行 |
| The CALM theorem | 一致性即逻辑单调性 | 单调程序**无需协调**即可保证最终一致 |
| Non-monotonicity | 否定、聚合、集合差引入非单调 | 2PC 的一致投票、多数派、2/3 多数本质上都是「计数到 0」的否定 |
| The Bloom language | 基于 Dedalus 的 Ruby DSL | collections（事实）+ lattices（CRDT），用 confluence 分析找必须协调的部分 |

## 核心精讲

> **教学示意，不参与构建。** 以下伪代码与数据结构均为教学性重述。

### 5.1 顺序不同 → 结果不同：所有冲突的根源

```text
同一个字符串，不同副本收到的操作顺序不同：
  副本 A 看到 1,2,3 → "Hello World!"
  副本 B 看到 2,3,1 → "World!Hello "
→ 顺序不同导致结果不同，这就是需要「调和（reconciliation）」的原因。

两类操作：
  可交换（commutative）：credit/debit、max()、集合并 → 任意顺序都收敛，无需协调
  不可交换：write 覆盖、字符串 concat → 必须引入顺序，而引入顺序 = 昂贵的协调
Pat Helland 的洞见（本书引用）：**以操作为中心**的工作可以做成可交换的，
                               而裸 READ/WRITE 语义不容易。
```

### 5.2 两类最终一致：概率性 vs 强保证

```text
Eventual consistency with probabilistic guarantees
  能检测冲突，但不保证结果等价于某个正确的串行执行；正常运行时也可能出现异常。
  代表：Amazon Dynamo（及其衍生 Riak、Voldemort、Cassandra）。
Eventual consistency with strong guarantees
  结果收敛到公共值，且**等价于某个正确串行执行**，不产生异常结果。
  代表：CRDTs，以及 CALM 定理所刻画的单调程序。
```

这个二分法是本章的骨架。很多人把「最终一致」当成一类东西，本书明确分成了
**「可能出错的最终一致」与「保证正确的最终一致」**——这是读本章最大的收获。

### 5.3 Dynamo 的六件套

```text
① Consistent hashing（一致哈希）
   把 key 映射到负责它的节点集合；客户端可直接算出位置，不必每次远程查询。

② Partial quorums（部分仲裁 / sloppy quorum）
   写 W-of-N，读 R-of-N；常见建议 R + W > N，使读写仲裁至少有一个重叠节点。
   ⚠ 但 R + W > N **不等于**强一致（见下）。

③ Is R + W > N the same as "strong consistency"?  ——答案：不是。
   原因一：节点失败/分区时，Dynamo 会引入原本不在偏好列表里的节点，仲裁集合可变；
   原因二：分区两侧都允许写入。
   → 只能给出概率性保证。

④ Conflict detection and read repair
   用**向量时钟**跟踪值的因果历史（其他选择：无元数据/LWW、时间戳如 Cassandra、版本号）。
   读时联系 R 个节点，丢弃更旧版本；
   若存在并发且不可比较的版本 → 返回多个值，由客户端/应用层决定怎么合。

⑤ Replica synchronization: gossip and Merkle trees
   Gossip：每 t 秒随机选节点通信，概率性同步；可扩展、无单点，但只有概率保证。
   Merkle trees：多粒度哈希，快速定位「哪些 key 不一样」，只交换必要的那部分。

⑥ Dynamo in practice: PBS（probabilistically bounded staleness）
   用反熵速率、网络延迟、本地处理延迟来估算读取的一致程度。
   本书引用的实测例子（Yammer 环境）：
     R=1, W=1 → 不一致窗口 1352 ms
     R=2, W=1 → 降到 202 ms，同时读延迟仍较低
```

PBS 的工程意义极大：它把「最终是多久」这个本书第 2 章的追问，
变成了一个**可以被测量和调参的数字**。

### 5.4 CRDT：把收敛性写进数据结构

```text
CRDT 要求的三条代数性质：
  Associative（结合律）  a+(b+c) = (a+b)+c
  Commutative（交换律）  a+b = b+a
  Idempotent（幂等律）   a+a = a
数学本质：join / meet 半格（semilattice）。
只要所有副本最终看到同一组操作，无论顺序、重复、延迟，都收敛到同一结果。

常见类型（本书列举）：
  Counters  Grow-only counter（merge = max）；PN-counter（两个 grow counter：一增一减）
  Registers  LWW register（按 timestamp/version 取最大）；
             Multi-valued register（向量时钟，保留并发值）
  Sets       Grow-only set（merge = union，不能删）；
             Two-phase set（一加一删两个集合，元素只能加一次删一次）；
             Unique set、LWW set、PN set、Observed-remove set 等
  还有 Graphs、text sequences（见 Shapiro 2011 综述）

与 Dynamo 的对应关系（本书点明）：
  LWW-register            ↔ Dynamo 用时间戳覆盖
  Multi-valued register   ↔ Dynamo 保留并暴露并发修改，由应用层 reconcile
```

### 5.5 CALM：一致性即逻辑单调性

```text
CALM（Consistency As Logical Monotonicity）：
  逻辑单调的程序保证最终一致，因此可以安全地在**无协调**的情况下执行。

单调 vs 非单调：
  单调逻辑：推论不会被后来学到的新知识推翻（retraction-free），答案只会越来越精确。
    例：知道 Tweety 是鸟 → 推断它会飞（单调逻辑下不会被推翻）。
  非单调逻辑：已有结论可能被新信息推翻。
    例：后来知道 Tweety 是企鹅 → 推翻「会飞」。

非单调性的来源：否定（negation）、聚合（aggregation）、集合差（set difference）、
                全称量化、除法 → 都需要「等全局信息齐了」才能定论。
本书的洞见：分布式聚合与协调协议（2PC 的一致投票、Paxos 的多数派、Byzantine 的 2/3 多数）
            本质上都可视为一种「否定 / 计数到 0」，因此代价高昂。

开放世界 vs 封闭世界：
  OWA（Open-world assumption）  知识不完整，不能从未知推出否定
  CWA（Closed-world assumption）+ Circumscription  假定已知事实完备，才能做确定断言

关系代数 / Datalog 中的单调性：
  单调算子  selection、projection、natural join、cross product、union、无否定的递归 Datalog
  非单调算子 negation、set difference、division、universal quantification、aggregation
```

### 5.6 Bloom：把 CALM 变成可分析的程序

```text
Bloom：基于 Dedalus（时序逻辑编程语言）的 Ruby DSL。
  每个节点有 collections（事实集合） + lattices（CRDT）。
  语句默认无序（order-independent）；
  用 CALM / confluence analysis 判断哪些部分**必须**协调。
```

作者此处留了一个诚实的尾巴：本章最后一节原文标题写作
**"What is non-mononicity good for?"**（原文拼写如此，正文中讨论的概念是
non-monotonicity / 非单调性），本目录照抄原标题并注明。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「R + W > N 就是强一致」 | 本书明答**不是**：仲裁集合可变、分区两侧都收写 → 只是概率性保证 |
| 2 | 「最终一致只有一种」 | 本书分成**概率性**与**强保证**（CRDT/CALM）两类，差别是「是否等价于某个正确串行执行」 |
| 3 | 「CRDT 会魔法般解决所有冲突」 | 只对**可交换的**操作成立；不可交换语义（如覆盖写）仍要靠 LWW 或人工规则，代价是丢写 |
| 4 | 「LWW 是 CRDT 所以很安全」 | LWW-register 确实是 CRDT，但它用时间戳覆盖 → **并发写会静默丢失**，业务上未必可接受 |
| 5 | 「向量时钟能无限记录历史」 | 随节点数膨胀，需要裁剪与墓碑；且它只**检测**并发，不负责合并 |
| 6 | 「单调性只是逻辑学概念」 | 它直接决定「能不能免协调」——CALM 定理的全部内容 |
| 7 | 🔧 「CRDT 只是学术玩具」 | 2026 年已是协同编辑与离线优先产品的标准底座（见上节实测 star），作者当年的判断被验证 |
| 8 | 🔧 「gossip 只在 Dynamo 系里用」 | 现代系统仍广泛用于成员管理与反熵，只是常退居元数据/辅助通道 |
| 9 | 🔧 「本章的中立性」 | 作者自己在附录承认本章「相当 Berkeley 中心」（偏 CRDT/CALM 一派）；读时应补看 Dynamo/PBS 一脉的原始论文作平衡 |
| 10 | 🔧 「弱一致 = 不用测试一致性」 | 一致性档位是**契约**，同样需要故障注入验证（Jepsen 一类实测已扩展到弱一致档位的验证） |

## 思考题

1. 挑你系统里三个写操作，判断它们是否可交换；不可交换的那个，代价是什么？
2. 用向量时钟手算一次三节点并发写，说明「返回多个值给应用层」之后应用层该怎么合并。
3. 把你们的一致性档位写成 PBS 的形式：在正常期，读到陈旧值的概率与窗口是多少？
4. 用 CALM 的眼光审查一个聚合查询：它非单调吗？非单调的部分需要哪种「等」？
5. 对比 LWW-register 与 multi-value register：你们的业务能接受哪种丢写/哪种复杂度？
