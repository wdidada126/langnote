# 第 3 章 时间与顺序（Time and order）

> 覆盖原书第 3 章（What is time? / Does time progress at the same rate everywhere? /
> Failure detectors (time for cutoff) / Time, order and performance / Further reading）。
> 本章是全书的暗线：**「序」是被造出来的，不是被发现的**。
> 没有序，第 4 章的日志复制无从谈起，第 5 章的冲突检测也无从判断。

## 本章地图

> 一句话：**我们只能用「时间」这个词掩盖一个事实——分布式系统里没有天然全序；
> 要么假设全局时钟（贵且脆），要么接受本地时钟（只能得偏序），要么彻底放弃时钟去造逻辑时间。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| What is time? | 时间作为「全序的来源」 | 时间戳之所以有用，是因为它能给事件排序 |
| Global-clock assumption | 假设存在一个精确全局时钟 | 理想化；时钟同步只能做到有限精度，是 anomalies 的温床 |
| Local-clock assumption | 每台机器自己的钟，无全局钟 | 只能得**偏序**；跨机时间戳不可比 |
| （逻辑时间） | Lamport 钟、向量时钟（见 Further reading） | 放弃物理时间，用因果关系造序 |
| Failure detectors | 用超时做判断；Cassandra 的累积型检测器 | 失败检测是「时间」最实用的用途，也是最容易误判的地方 |
| Time, order and performance | 什么时候真的需要序？ | CALM 定理给答案（第 5 章）；很多场景「尽力而为」即可 |

> 关于小节口径：章节页抓取时只完整取到「What is time?」「Does time progress at the same rate
> everywhere?（global-clock / Local-clock）」「Failure detectors」「Time, order and performance」

## 核心精讲

> **教学示意，不参与构建。** 以下时钟算法为教学性重述，不对应任何可执行实现。

### 3.1 时间为什么重要：它是全序的廉价来源

```text
全局时钟假设之所以诱人：
  它天然给出「所有节点上所有操作的精确顺序」——
  即使这些节点从未互相通信，也能用时间戳排出先后。

代价：
  这个顺序的精度受限于时钟漂移（clock drift），而不是网络延迟。
  引发 anomaly 的常见场景（作者列举）：
    · 运维或用户误改机器本地时间；
    · 一台时间严重过期的机器加入集群；
    · 各机时钟以略有差异的速率漂移。
```

作者点名了两个真实系统的取舍：

- **Cassandra**：假设时钟同步，用时间戳解决写冲突（新时间戳者胜）。时钟漂移 → 新数据可能被旧数据覆盖。
- **Google Spanner**：论文描述 **TrueTime API**——既同步时间，也**估计最坏情况的时钟漂移**，
  把不确定性显式化，而不是假装它不存在。

这是本章最有价值的一句潜台词：**Spanner 的关键不是「时钟更准」，而是「误差有界且被显式使用」**。

### 3.2 本地时钟假设：偏序，不是全序

```text
Local-clock assumption：
  每台机器有自己的钟，但没有全局钟。
  → 不能用本地钟判断「远端时间戳在我的本地时间戳之前还是之后」。
  → 只能给每个系统内部的事件排序：得到的是偏序（partial order）。

单机上仍然可以用时间戳排序，也可以用超时——
  前提是别让时钟乱跳；
  在一台由终端用户控制的机器上，这其实是过强的假设。
```

### 3.3 逻辑时间：彻底放弃时钟

本章 Further reading 把「Lamport clocks, vector clocks」归在同一节，指向 Lamport 1978。
工程上这两种钟的分工是：

```text
Lamport 钟（逻辑钟）
  规则：每个事件取 max(本地计数, 收到的计数) + 1；消息携带计数。
  给出：与因果序相容的一个全序（但不反推因果——C(a)<C(b) 不能推出 a 因果先于 b）。

向量时钟（Vector clock）
  规则：每个节点维护一个长度 = 节点数的向量；本地事件自增自己的分量；消息携带整个向量；
        合并时逐分量取 max。
  给出：可判定的因果关系——
        V(a) ≤ V(b)   → a 因果先于 b（或相等）
        V(a) 与 V(b) 不可比 → 并发（需要冲突解决）
  代价：向量长度随节点数增长，需要裁剪/墓碑等工程手段。
```

第 5 章 Dynamo 的「冲突检测与读修复」直接用向量时钟判断「是不是并发写」，
本章是它的原理前置。

### 3.4 失败检测器：时间最实用的用法，也是最危险的判断

```text
最简单的失败检测器：超时到期就判定失败。
难点不在「超时」，而在「怎么判断远端是否真的失败」：
  · 理想：能适应网络状况变化，不把超时写死；
  · Cassandra 的 accrual failure detector：
      输出「怀疑度」（0 到 1 之间的连续值），而不是 up/down 二值；
      由上层应用自己权衡「判得准」与「判得早」。
```

这一点对架构非常关键：**失败检测本质上不是布尔问题**。
二值化（up/down）是把不确定性过早抹掉的产物，而「怀疑度」保留了让上层做权衡的空间。

### 3.5 时间、顺序与性能：什么时候真的需要序？

```text
需要序的场景：希望每个中间操作都把系统从一个一致状态带到下一个一致状态
              （典型：数据库的响应必须反映全部可用信息）。
不需要那么多序的场景：
  · 长跑计算，只关心最终结果；
  · 分区期间只能访问部分系统，可接受「尽力而为」的答案；
  · 用户其实分不出「较新的答案」与「保证正确但昂贵的答案」——
    作者的比喻：某用户的粉丝数是 X 还是 X+1？某查询的 Top-3 是不是绝对最优？

反问：同步常常被当成钝器，施加在所有操作上，而只有一部分操作真正影响最终结果。
     「什么时候需要序才能保证正确？」——CALM 定理给出答案（第 5 章）。
```

## 近年研究与工业界开源实践（2015–2026）

- **误差有界时间成为基础设施**：Spanner（OSDI 2012）之后，
  「时钟不准」从「要避免的风险」变成「要显式建模的输入」；
  无专用硬件的系统普遍采用 HLC（OPODIS 2014）把物理钟与逻辑钟合并，
  既保留可读性（接近物理时间）又保因果序。
- **因果一致的工程化**：从「向量时钟 + 应用自己合并」（第 5 章 Dynamo 路线）
  演进到「系统提供因果一致档位」，把本章的偏序概念变成可选项。
- **失败检测的多信号化**：单一超时/怀疑度之外，
  与服务网格、熔断、健康检查的信号融合；判定权上移给策略层，正呼应本书 3.4 的「不要二值化太早」。
- **流式系统的时间语义**：事件时间 vs 处理时间、水位线（watermark）成为标准概念，
  把本章「什么时候需要序」变成了可配置的算子语义。
- **开源实测**：`apache/kafka` star = **33848**（2026-09 `gh api` 实测）——
  Kafka 的时间戳与流式语义是本章「事件时间」议题最常被参照的开源实现之一；
  协调服务 `etcd-io/etcd` star = **52310**（同期实测），其任期（term/epoch）机制
  是本书第 4 章「epoch 作为逻辑时钟」的直接落地。
- 本目录所有代码均为教学示意、不参与构建，不引用任何需要跑出来的性能数字。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「有 NTP 就等于时钟同步」 | 同步只能做到有限精度；**漂移**才是常态，也是 anomaly 的来源 |
| 2 | 「时间戳可以跨机比较」 | 本地时钟假设下不能；跨机比较需要全局时钟假设或逻辑时钟 |
| 3 | 「Lamport 钟能判断因果」 | 只能给出与因果相容的全序；**判断并发要看向量时钟**（或等价机制） |
| 4 | 「向量时钟可以无限长」 | 随节点数增长；工程上必须裁剪、复用槽位、配合墓碑 |
| 5 | 「失败检测就是 ping 不通就下线」 | 🔧 应为连续「怀疑度」+ 上层权衡（本书 3.4 的 accrual detector 就是这个意思） |
| 6 | 「Spanner 的时钟特别准所以能强一致」 | 🔧 关键是**误差有界并显式参与协议**（commit-wait 一类机制），不是绝对精度 |
| 7 | 🔧 「顺序越严越好」 | 序是成本；本书 3.5 明确说同步常被当钝器滥用，只有部分操作真的影响结果 |
| 8 | 🔧 「本书讲全了时间的用途」 | 作者自述**跳过了一致快照**；快照理论见 Chandy & Lamport 1985 |
| 9 | 🔧 「LWW（最后写入者胜）用时间戳很安全」 | 在漂移与并发存在时会静默丢写；这是第 5 章 Dynamo 路线的主要风险点 |
| 10 | 🔧 「本地时钟在用户机器上也可用于超时」 | 本书明说：终端用户可能改系统日期，这是过强假设 |

## 思考题

1. 你们系统的时间戳来自哪里？它的误差界是多少？写进设计文档了吗？
2. 用向量时钟手算一次三方并发写：哪些版本可比、哪些并发？并发的那几份由谁合并？
3. 把你们的失败检测改成「输出怀疑度」的形式：不同业务分别该在多高的怀疑度上摘除节点？
4. 挑一个查询，判断它是否真的需要「反映全部可用信息」——如果不需要，可以省掉哪一层同步？
5. 作者自述跳过了一致快照：读 Chandy & Lamport 1985，说明它如何同时用上「时间」与「快照」两件事。
