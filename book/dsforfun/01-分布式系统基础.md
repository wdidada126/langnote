# 第 1 章 分布式系统基础（Distributed systems at a high level）

> 覆盖原书第 1 章（What we want to achieve / What prevents us… / Abstractions and models /
> Design techniques: partition and replicate / Further reading）。
> 本章是全书唯一「不谈算法、只谈目标与代价」的一章，也是后面四章的评价尺子：
> 第 2 章的不可能结果、第 4/5 章的两条复制路线，都是在回答本章提出的问题。

## 本章地图

> 一句话：**分布式编程的全部内容，就是处理「距离」和「不止一个东西」这两个后果——
> 信息只能按光速传播，而独立的东西会独立地失败。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| What we want to achieve | 可扩展性、性能、延迟、可用性（含容错） | 这些目标**互相拉扯**，不能同时拉满 |
| What prevents us… | 节点数、距离（物理限制）+ 可理解性 | 「节点越多越容易坏」是概率事实，不是运维事故 |
| Abstractions and models | 抽象=裁剪现实；模型=精确描述关键性质 | 保证越弱 → 自由度越大 → 可能更快，但更难推理 |
| Partitioning | 切分成独立子集 | 限制数据量、允许分区独立失败 |
| Replication | 复制多份 | 唯一「强一致」模型才能让人像用单机一样编程 |

## 核心精讲

> **教学示意，不参与构建。** 本章无官方代码，以下公式与伪代码均为笔记为讲清概念而写。

### 1.1 四个目标，其实只有一把尺子

作者把目标列成一组：可扩展性（scalability）、性能（performance）、延迟（latency）、
可用性（availability）。它们的定义值得抄下来，因为后面所有取舍都要回到这里：

```text
Scalability   加机器后，性能/容量按期望增长的能力（线性是理想，实际有协调开销）
Performance   单位时间完成的工作量（吞吐）——与「延迟」是不同的量
Latency       从发起操作到得到响应之间的等待时间（不是带宽）
Availability  系统处于可服务状态的时间比例 = uptime / (uptime + downtime)
```

最容易混淆的是 **performance 与 latency**：吞吐可以靠加并发堆上去，
但单次请求的延迟下界由**物理距离**决定，堆机器救不了。
这就是本章「两个后果」里的第一条——信息按光速传播。

可用性还有个反直觉的算术（作者给了九的对照表）：

```text
90%  → 一年可停  一个多月
99%  → 一年可停  <4 天
99.9% → 一年可停  <9 小时
99.99% → 一年可停  <1 小时
99.999% → 一年可停  ~5 分钟
99.9999% → 一年可停  ~31 秒
```

注意这张表的隐藏前提：**「停」是全系统不可用**。真实系统里更常见的是
「某个功能不可用」「某些用户不可用」，所以 2026 年的实践已经普遍改用
**SLO + 错误预算（error budget）**而不是单看几个九（见「版本演进」）。

### 1.2 容错的定义：先声明你要容忍什么

作者给的容错定义极短，却是全书最有操作性的一句：

```text
Fault tolerance = 系统在故障发生后仍按「明确定义的方式」行事的能力。
推论：你无法容忍你没有考虑过的故障。（You can't tolerate faults you haven't considered.）
```

这句话的工程后果是：**故障模型（failure model）必须写在设计文档的第一页**，
而不是等出事后写进复盘。第 2 章会把它形式化为 crash-fail / partition / Byzantine 三类。

### 1.3 阻止我们达成目标的三件事

```text
① 节点数（number of nodes）：
   节点越多，「至少一个节点出问题」的概率越高。
   设单节点可用性 a，n 个节点「全部正常」的概率 ≈ a^n（独立失效假设下）。
   n=100、a=99.99% → 全系统正常概率只剩 ~99%，多出来的 1% 就是分布式要还的债。
② 距离（distance）：
   信息传播速度有上限，跨地域往返 RTT 是硬下界，加机器、加带宽都改不了。
③ 可理解性（intelligibility）：
   同时运转的部件超过人能同时把握的数量，就会把「异常（anomaly）」误当「错误（error）」。
   作者的俏皮话：如果你更聪明，这些异常本该在你的预料之中。
```

第③条常被读者跳过，但它其实是全书方法论的自白：
**本书通篇在用「模型」对抗第③条**——模型就是把现实裁剪成能推理的样子。

### 1.4 抽象与模型：保证越弱，自由度越大

```text
抽象（abstraction）：拿掉与解题无关的现实细节，让事情可管理。
模型（model）：精确描述分布式系统的关键性质。
  系统模型（system model）：同步 / 异步
  故障模型（failure model）：crash-fail / partition / Byzantine
  一致性模型（consistency model）：strong / eventual
```

作者点明的张力值得反复咀嚼：

- 我们**想要**「像单机一样工作」的系统，但**现实**是很多节点；
- 最熟悉的抽象（比如在分布式系统上实现共享内存）往往**太贵**；
- **保证越弱 → 行动自由度越大 → 可能更快**，但也更难推理；
- 反过来，**暴露更多内部细节**（如列存让用户感知局部性）能换性能，代价是更难用。

这一条是第 4/5 章两条复制路线的总纲：
第 4 章付出协调代价换「像单机一样」，第 5 章放弃「像单机一样」换可用性。

### 1.5 两大设计手法：分区与复制

```text
Partitioning（分区/分片）
  把数据集切成更小、互相独立的子集。
  + 性能：每次只查一部分数据；相关数据可放同一片
  + 可用性：分片可独立失败，需要更多节点同时故障才影响整体
  - 跨片访问低效、各片增长速度不同 → 再平衡（rebalance）问题
  作者直言：分区高度依赖具体业务，很难泛泛而谈，所以本书重点放在复制。

Replication（复制）
  同一份数据放多份。
  只有一种一致性模型（强一致）能让你「像数据没被复制过一样」编程；
  其他模型都会把复制的内部细节暴露给程序员。
  弱模型可以提供更低延迟、更高可用性，不一定更难理解，只是**不同**。
```

最后这句「not necessarily harder to understand, just different」是本书的价值取向：
它拒绝把弱一致说成「将就」，而是把它当成**另一套需要学习的语义**。第 5 章的 CRDT 与 CALM 就是这套语义的地基。

### 示例：把「加机器」的收益算清楚（教学示意）

```text
场景：单请求串行处理 10ms，目标延迟预算 50ms，目标吞吐 1000 rps。
A. 只加机器（无状态横向扩容）：
   单核 ~100 rps（10ms/请求） → 需要 ≥10 核；延迟不因加机器变差（+负载均衡 ~1ms）。
B. 复制（强一致多数派写，跨机房）：
   单机房 RTT 0.5ms → 写延迟 ≈ 本地 fsync + 一次多数派往返 ≈ 1.5–2ms；
   跨机房 RTT 30ms  → 写延迟 ≈ 30ms+，直接吃掉 60% 预算。
C. 分区（按用户 ID 分片）：
   单片数据量降到 1/8 → 查询扫描量下降 → 吞吐上升，但跨片事务（第 4 章 2PC）开始出现。
结论：加机器解决吞吐，不解决延迟；跨机房复制解决可用性，代价是延迟；
      分区解决数据规模，代价是跨片操作。三件事互不替代——这就是本章的表。
```

## 版本演进

本书写于 2012–2013，本章的「目标清单」至今没变，但**度量方式与部署底座**变了：

| 维度 | 本书时期（2013） | 2026 现状 |
| --- | --- | --- |
| 可用性度量 | 几个九的年度停机表 | SLI/SLO + 错误预算，按功能/用户分域度量（Google SRE 一书之后普及） |
| 延迟关注点 | 平均延迟为主 | **尾部延迟**（p99/p99.9）为主，long tail 由 GC/邻居噪声/重试风暴造成 |
| 扩容单位 | 虚拟机、手工容量规划 | 容器 + 声明式弹性（HPA/KEDA 等）、serverless 按请求扩缩 |
| 距离的处理 | 单数据中心为主，跨机房是特例 | 多可用区/多区域是默认选项，边缘计算把「距离」推到用户侧 |
| 分区方式 | 业务手工分片 | 托管服务的自动分片/再平衡，分片成为平台能力 |
| 可理解性 | 靠抽象与模型 | 追加可观测性（tracing/metrics/log 三件套）与混沌工程作为「预期之外的异常」的兜底 |

作者在本章没写、但今天必须补的一条：**成本**。
2013 年的取舍三角是「一致性/可用性/延迟」，2026 年还要加上「钱」——
跨区流量费、副本存储费、闲置算力费，常常才是架构决策的真正约束。

## 近年研究与工业界开源实践（2015–2026）

- **SLO 与错误预算的工程化**：Google《Site Reliability Engineering》（2016）与之后的
  《SRE Workbook》把本章的「可用性定义」推进为可执行的指标体系；
  主流可观测性平台（Prometheus 生态、OpenTelemetry）默认按 SLI 采集。
- **尾部延迟的工程对策**：对冲请求（hedged requests）、绑定期望（tied requests）、
  自适应并发控制——均出自上文 Dean & Barroso 2013 的落地。
- **混沌工程**：把「你无法容忍没考虑过的故障」变成可执行流程
  （故障注入演练、常态化演练）。本章 1.2 的容错定义是它的理论依据。
- **分区与复制成为平台能力**：关系型与 KV 系统普遍内置自动分片与再平衡，
  「要不要分片」从算法问题变成了**成本与运维边界**问题。
- **可复现实验口径**：本目录所有代码为教学示意，不参与构建；
  因此本目录不引用任何需要跑起来的性能数字，star 数一律以 `gh api` 实测为准
  （本书仓库 `mixu/distsysbook` 实测 star = 2676，2026-09）。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「可扩展 = 加机器更快」 | 加机器涨的是**吞吐**；单请求延迟的下界由距离决定，加机器不动它 |
| 2 | 「性能 = 延迟」 | 吞吐与延迟是两个量；本章明确分开，选型时别用一个指标回答两个问题 |
| 3 | 「可用性就是 uptime」 | 应分功能、分用户域度量；单一 uptime 数字会掩盖局部不可用 |
| 4 | 「容错是运维的事」 | 🔧 容错首先是**建模**问题：没声明的故障无从容忍（本章 1.2） |
| 5 | 「弱一致 = 将就/不成熟」 | 🔧 本书明确反对这种读法：弱模型**不一定更难理解，只是不同**；2026 年 CRDT 的产品化（见 05 篇）已经证明它可以给出强保证 |
| 6 | 「复制解决可用性，分区解决容量，两者可叠加无代价」 | 🔧 两者叠加会引出跨片事务与跨片一致性（本书第 4 章 2PC、第 5 章 Dynamo），代价在后面两章才付 |
| 7 | 🔧 「本书的目标清单是完整的」 | 2013 年之后**成本**（跨区流量、存储、闲置算力）成为第四维度；本章未涉及，读时自行补上 |
| 8 | 🔧 「几个九的表格够用了」 | 现代实践用 SLO + 错误预算，并且按依赖链分摊预算；表格只适合做直觉建立 |

## 思考题

1. 用本章的「三个阻止因素」分别解释一次你经历过的线上故障：哪个是节点数、哪个是距离、哪个是可理解性？
2. 把你们系统的可用性指标改写成 SLO 形式：SLI 是什么、预算是多少、谁有权花掉它？
3. 选一个跨机房部署，估算「多数派写」吃掉多少延迟预算（参考 1.5 示例），再决定副本放置。
4. 「保证越弱 → 自由度越大」：举一个你系统里**故意**选弱一致的例子，说明换来了什么。
