# 第 2 章 抽象层次与不可能结果（Up and down the level of abstraction）

> 覆盖原书第 2 章（A system model / The FLP impossibility result / The CAP theorem /
> Strong consistency vs. other consistency models / Further reading）。
> 本章是全书的理论心脏：它先把「现实」裁剪成**系统模型**，再在这个模型上证明两件不可能的事，
> 最后给出「既然强一致有代价，那就看看别的一致性模型」的谱系。

## 本章地图

> 一句话：**模型 = 关于环境与设施的一组假设；假设越弱，算法越健壮，也越难有结果。
> FLP 说异步下共识不可能有确定性解；CAP 说分区期强一致与高可用不可兼得。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| A system model | 节点、通信链路、时序假设；共识问题的四条性质 | 「无共享内存、无共享时钟」是所有麻烦的源头 |
| Two impossibility results | FLP（给算法设计者）与 CAP（给实践者） | 前者限死确定性，后者限死分区期的 C/A |
| The FLP result | 异步 + 一个崩溃故障即无确定性共识算法 | 工程上只能在**安全性/活性**或**同步假设**上让步 |
| The CAP theorem | C/A/P 三选二；CA/CP/AP 三类系统 | P 不是可选项，真实取舍是分区期的 C vs A |
| Consistency models | 强（linearizable/sequential）、客户端中心、因果、最终 | 一致性模型是**程序员与系统之间的契约** |

## 核心精讲

> **教学示意，不参与构建。** 本章的定理只做工程化重述，证明细节不在本文展开。

### 2.1 系统模型：三条假设撑起后面所有结论

```text
分布式程序的核心事实：
  ① 程序在独立节点上并发执行；
  ② 节点通过「可能引入不确定性、可能丢消息」的网络相连；
  ③ 没有共享内存，也没有共享时钟。

由此推出四条（作者原文列举）：
  · 知识是本地的：节点只能快速访问本地状态，关于全局状态的信息可能已经过期；
  · 节点可以独立失败与恢复；
  · 消息可能延迟或丢失（而且「网络故障」与「节点故障」难以区分）；
  · 各节点时钟不同步。
```

**节点（Nodes）**：能执行程序、把数据放易失内存（故障即丢）或稳定存储（故障后可读）、有时钟。
主流故障模型是 **crash-recovery**；**Byzantine** 因成本与实现复杂度，商业系统中很少处理（作者原话）。

**通信链路（Communication links）**：双向发送消息；通常假设链路提供 FIFO 顺序且消息可能丢失。
**网络分区** = 网络坏了但节点还活着——此时被分区的节点**仍可能被部分客户端访问**，
所以它必须和「崩溃节点」区别对待（这是很多事故处理失误的根源）。

**时序假设**三选一：

```text
同步（Synchronous）  进程锁步执行；消息延迟有已知上界；时钟准确。
                     → 好分析，但不现实。
异步（Asynchronous） 无任何时间假设；执行速率独立；无延迟上界；无可用时钟。
                     → 这是「不做假设」（non-assumption）。
部分同步（Partially synchronous） 现实系统最好情况：大多数时候有上界，偶尔消息无限延迟、时钟失步。
```

**健壮的系统模型做出最弱的假设**，因此算法能容忍更多样的环境。这是本章的方法论起点：
FLP 之所以不可能，正因为它在**最弱的异步假设**下要求一个确定性算法。

### 2.2 共识问题的四条性质

```text
Agreement（一致性）  所有正确进程必须同意同一个值
Integrity（完整性）  每个正确进程最多决定一个值，且该值必须是被某个进程提出过的
Termination（终止性）所有进程最终会做出决定
Validity（有效性）   若所有正确进程都提出同一个值 V，则决定必为 V

互斥、选主、组播、原子广播 = 共识问题的实例。
```

第 4 章的所有「防止分歧」的算法，本质都是在**放弃其中一条**的前提下给出可用解。

### 2.3 FLP：作者引用的原文结论

> "there does not exist a (deterministic) algorithm for the consensus problem in an
> asynchronous system subject to failures, even if messages can never be lost, at most one
> process may fail, and it can only fail by crashing (stopping executing)"

工程读法（比原文更重要）：

```text
FLP 不是说「共识做不到」，而是说「在纯异步模型下没有确定性算法能保证终止」。
因为它总能被构造成「永远停在二价（bivalent）状态」的一条执行。
所以工程实现必须在以下三处之一让步：
  ① 引入时间（超时/随机化）——回到部分同步；
  ② 放弃 liveness（宁可停，也不能错）——Paxos/Raft 的选择；
  ③ 放弃 determinism（随机化算法）。
本书第 4 章明写：Paxos 放弃 liveness 以保 safety。这就是 FLP 的直接后果。
```

### 2.4 CAP：三类系统与作者的四个结论

```text
C（Consistency）   所有节点在同一时间看到相同数据（CAP 里的 C 特指强一致）
A（Availability）  节点故障不阻止存活节点继续操作
P（Partition tolerance） 网络/节点故障导致消息丢失时，系统仍能继续运作

CA：full strict quorum、2PC。不区分节点故障与网络故障；为防分歧，分区时必须全面停写。
    → 早期传统分布式关系数据库多属此类（不具分区容错意识）。
CP：多数派 quorum 协议（如 Paxos）。分区时只留多数派侧可写，少数派侧不可用。
    → 容忍 f 个故障需 2f+1 个节点。
AP：带冲突解决的 Dynamo 类系统。两侧都收写，事后调和（第 5 章）。
```

作者给出的四个结论（值得抄进设计文档）：

1. 早期分布式关系数据库设计时**没有考虑**分区容错（多为 CA）；
2. 分区期间，**强一致与高可用存在矛盾**；
3. **正常运行时**，强一致与性能（低延迟）也存在矛盾；
4. 若不想在分区时放弃可用性，就必须探索**强一致之外**的一致性模型。

作者同时保留了清醒：Brewer 本人指出「三选二」的说法有误导性——
**一致性与可用性不是绝对的二元对立**（除非你把自己限制在强一致范畴内）；
并且 **ACID 的 C ≠ CAP 的 C**（前者是事务约束，后者是副本可见性）。

### 2.5 一致性模型谱系：契约，不是开关

```text
一致性模型 = 程序员与系统之间的契约：
  程序员遵守某些规则 → 系统保证数据存储上的操作结果可预测。

强一致（维持 single-copy 假象）
  Linearizable（线性一致）  操作看起来原子执行，且顺序符合真实时间全序（Herlihy & Wing 1990）
  Sequential（顺序一致）    操作看起来原子执行，所有节点看到同一顺序，但不必符合真实时间（Lamport 1979）
                            ⚠ 顺序一致不可组合（does not compose）
弱一致
  Client-centric（客户端中心） 保证客户端不会看到更旧的版本（常由客户端缓存库实现）
  Causal（因果）               弱模型里可用的最强模型，有因果关系的事件保持顺序
  Eventual（最终一致）         停止写入后，经过「未定义的一段时间」所有副本收敛
```

作者对最终一致的两记重拳必须记住：

- 最终一致是**平凡可满足的**（trivially satisfiable，只是活性性质），没有补充信息就毫无用处；
- 因此必须追问两件事：**「最终」是多久？**（收敛时间下界/典型时长）**副本如何达成一致？**（如 LWW，若时钟错乱就会丢写）。

## 版本演进

本书写作期（2012–2013）恰好处在「CAP 之后、PACELC 尚未进入教科书」的窗口，
因此本章最需要 2026 补丁：

| 议题 | 本书（2013） | 2026 应当补的 |
| --- | --- | --- |
| CAP 的适用期 | 明确写了「分区期」的 C/A 取舍 | 仍成立；但**正常期**的取舍要用 **PACELC** 表达（Abadi 2012）：Else 分支是 L（latency） vs C |
| CAP 的批判 | 已引用 Brewer 的「三选二有误导」 | 应补 Brewer 亲撰的 **《CAP Twelve Years Later》（IEEE Computer 2012）**：分区是罕见事件，多数时候你在做延迟与一致性取舍 |
| 一致性模型 | 强/客户端中心/因果/最终四档 | 追加 **可串行化与快照隔离**（事务侧）、**读写一致性/单调读**（客户端侧）、**有界陈旧（bounded staleness）** 等更细档位 |
| 声称强一致的验证 | 无（当时无系统化的第三方实测） | **Jepsen**（Kyle Kingsbury 自 2013 起）用故障注入实测大量系统，多次证明「文档声称的强一致」在分区/时钟/成员变更下不成立 |
| 因果一致 | 只作为弱模型中的最强档提及 | 已成为可工程实现的档位（因果稳定的向量/HLC 方案），并有产品化实现 |
| 线性一致的代价 | 只说「每次操作都要通信」 | 已可量化：一轮多数派往返 + fsync 是下界；并有 ReadIndex/租约读等优化路径 |

## 近年研究与工业界开源实践（2015–2026）

- **PACELC 成为选型语言**：今天讨论「要不要强一致」时，标准问法是
  「分区期要 C 还是 A（PACELC 的 then 分支），正常期要低延迟还是强一致（else 分支）」——
  本书第 2 章只覆盖了 then 分支。
- **Jepsen 实测**：自 2013 年起对大量分布式数据库与协调系统做故障注入测试，
  反复揭示「声称的线性一致」在分区、时钟跳变、成员变更、磁盘故障下会被打破。
  这直接把本书 2.5 的「契约说」变成了**可证伪的工程命题**：契约要写清、也要能被测。
- **一致性档位产品化**：许多系统开始把一致性做成**可调档位**（强一致读 / 有界陈旧读 / 最终一致读），
  正对应本章「一致性模型是契约」的说法——契约变成了接口参数。
- **共识实现的普及**：本书写作时 Raft 刚提出、etcd 刚起步；到 2026 年共识已是标准库级别的基础设施。
  相关实测：`etcd-io/etcd` star = **52310**（2026-09 `gh api` 实测）。
  算法细节见本目录 [04-复制-防止分歧与强一致.md](04-复制-防止分歧与强一致.md)。
- **可验证一致性**：形式化方法与模型检查（TLA+ 等）被用于验证共识与一致性协议，
  把本章「模型」一词真正落到了可执行的规格上。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「CAP 三选二：随便挑两个」 | P（分区容错）**不是可选项**——分区会发生。真实取舍是分区期的 C vs A |
| 2 | 「ACID 的 C = CAP 的 C」 | 前者是事务完整性约束，后者是副本可见性；本书已明确区分 |
| 3 | 「FLP = 共识不可能」 | 是**异步模型下无确定性解**；工程上靠超时/随机化（部分同步）绕开，Paxos/Raft 都这么做 |
| 4 | 「Paxos/Raft 违反 FLP」 | 它们满足部分同步假设，且**放弃 liveness** 保 safety，正好是 FLP 允许的三种让步之一 |
| 5 | 「最终一致 = 弱但够用」 | 🔧 必须追问「最终是多久」与「如何收敛」，否则这句话没有信息量（本书 2.5） |
| 6 | 「R+W>N 就是强一致」 | 🔧 见 [05-复制-接受分歧与弱一致.md](05-复制-接受分歧与弱一致.md)：部分 quorum 下仲裁集合可变，只是概率性保证 |
| 7 | 🔧 「CAP 覆盖了所有一致性取舍」 | CAP 只讲**分区期**；正常期的延迟-一致取舍是 **PACELC**（Abadi 2012），本书未收录，必须补 |
| 8 | 🔧 「顺序一致可以组合」 | 本书明写顺序一致**不可组合**：把两个顺序一致的系统拼起来，整体不保证顺序一致 |
| 9 | 🔧 「文档说强一致就是强一致」 | 需第三方故障注入验证（Jepsen 一类实测），本书写作期尚无此实践 |
| 10 | 🔧 「异步模型只是理论洁癖」 | 恰恰相反：异步是最弱假设；在它之下成立的结论最稳健，本章的「健壮模型=最弱假设」是选型时的护身符 |

## 思考题

1. 用「系统模型的三条假设」写出你们系统的模型：是同步、异步还是部分同步？这个选择决定了后面能用什么算法。
2. FLP 允许的三条让步（时间 / liveness / 随机化），你们依赖的共识实现选了哪一条？如何验证？
3. 把你们的核心存储按 PACELC 重述：分区期（then）选什么，正常期（else）选什么？写成 ADR 一句话。
4. 「一致性模型是契约」：挑一个接口，写出它承诺的是哪一档（线性/顺序/因果/最终/有界陈旧），并说明客户端该怎么配合。
