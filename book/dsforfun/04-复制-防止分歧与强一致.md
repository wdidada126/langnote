# 第 4 章 复制：防止分歧与强一致（Replication: preventing divergence）

> 覆盖原书第 4 章（Synchronous replication / Asynchronous replication /
> An overview of major replication approaches / Primary-backup / 2PC /
> Partition tolerant consensus algorithms / Paxos, Raft, ZAB / Replication methods with strong
> consistency / Further reading）。
> 本章是全书篇幅最大、也最需要 2026 补丁的一章：它讲清了「防止分歧」的代价阶梯，
> 但写于 Raft 刚提出、Multi-Raft 与 NewSQL 尚未出现之时。

## 本章地图

> 一句话：**防止分歧 = 让系统表现得像一份数据；代价从「1n 消息的主备」一路涨到「多数派往返的共识」，
> 而 2PC 卡在中间：能回滚却会阻塞，且不分区容错。**

| 节 | 内容 | 结论 |
| --- | --- | --- |
| Synchronous replication | 写 N-of-N；返回前所有副本确认 | 强持久性，但速度=最慢节点，不容忍任何节点丢失 |
| Asynchronous replication | 写 1-of-N；主先应答，之后异步扩散 | 快、容忍延迟波动；弱持久性，可能分歧、可能丢数据 |
| Overview of approaches | 防分歧（single copy，需共识）vs 可能分歧（multi-master） | 共识四属性 + 按消息数分类的代价阶梯 |
| Primary/backup | 日志传送；async（1n）/ sync（2n） | 只能 best-effort；split-brain、replication lag、手动切换 |
| 2PC | voting + decision 两阶段 | 可回滚（优于 1PC），但**阻塞**、N-of-N、CA 不分区容错 |
| Partition-tolerant consensus | 网络分区、多数派、角色、epoch、duels、编号提案 | 打破对称：分区期只留一侧活动 |
| Paxos / Raft / ZAB | 三种分区容错共识算法 | Paxos 最重要、ZAB 服务 ZooKeeper、Raft 为可理解性设计 |
| Strong consistency 对比 | static master / N-of-N / majority vote | 越往上容错越好，代价是消息数与延迟 |

## 核心精讲

> **教学示意，不参与构建。** 以下消息流与算法描述为教学性重述，不对应任何可执行实现。

### 4.1 同步 vs 异步复制：N-of-N 与 1-of-N

```text
通用复制模型（作者的四阶段）:
  (Request) → (Sync) → (Response) → (Async)
  同步阶段发生在返回客户端之前；异步阶段发生在返回之后。

同步复制（active / eager / push / pessimistic）
  写 N-of-N：返回前必须被所有 N 台服务器接收、存储并确认。
  + 非常强的持久性保证（除非 N 份全丢，已接受的更新不会丢）
  - 速度 = 最慢的服务器；对网络延迟抖动极敏感
  - 不容忍任何服务器丢失（丢一台就写不了，可能只能只读）

异步复制（passive / pull / lazy）
  写 1-of-N：主立即应答，之后再扩散。
  + 快；对内网延迟波动更容忍；只要至少一个节点存活就「可用」（理论上）
  - 只有弱（概率性）持久性：唯一持有数据的节点在扩散前挂掉 → 数据永久丢失
  - 不保证各节点状态一致 → 多处收写就会产生分歧（divergence）
```

### 4.2 方法与代价：一条消息数阶梯

作者（引自 van Renesse & Guerraoui 一脉的分类）按**达成一次更新所需的消息数**排了序：

```text
维持单副本一致性（single-copy consistency）的算法：
  1n 消息  异步主备（asynchronous primary/backup）
  2n 消息  同步主备（synchronous primary/backup）
  4n 消息  2PC、Multi-Paxos
  6n 消息  3PC、带重复选主的 Paxos

不维持单副本一致性（gossip / partial quorum 等）→ 见第 5 章

经验法则：同步等待越多 → 保证越强、性能越差；
        2PC 与 quorum 系统的吞吐差异，在讨论分区与延迟容忍时才真正显现。
```

### 4.3 主备复制：最常用，也最「尽力而为」

```text
所有更新在 primary 上执行，操作日志/变更通过网络送给 backup replicas。

异步主备（1 条消息 "update"）：MySQL 复制默认模式。
  副本总是至少落后一个操作；主失败 → 未发送的更新丢失（replication lag）。
同步主备（2 条消息 "update" + "acknowledge receipt"）：
  仍只能提供弱保证——若主在给客户端发 ACK 前失败，
  会出现「备份已提交但客户端认为失败」，需要人工清理/协调。

整体只能提供 best-effort 保证：
  · lost updates / incorrect updates
  · split-brain：临时网络问题触发切换，主与备同时活跃
  · 故障切换通常手动 / ad-hoc，不是完全容错的（“hot backup”）
```

### 4.4 2PC：能回滚，但会阻塞

```text
阶段一 voting（“OK to commit?”）
  协调者把更新发给所有参与者；参与者处理并投票 commit/abort；
  投 commit 时把更新写入临时区（write-ahead log），第二阶段结束前视为临时。
阶段二 decision（Commit or Rollback）
  协调者决定并通知所有人；全票 commit 才把临时区内容变为永久并回 ACK。

优点：相比主备这种“1PC”，第二阶段允许回滚，避免副本分歧。
缺点：
  · 阻塞（blocking）：协调者或参与者单点失败会阻塞进度，直到节点恢复；
  · 假设稳定存储永不丢、节点不会永久崩溃；
  · CAP 视角：2PC 是 CA，**不是分区容错**——协调者失败时无法安全提升新协调者，需人工干预；
  · 写 N-of-N，对**尾部延迟**敏感。
```

### 4.5 多数派与 epoch：分区容错共识的骨架

```text
网络分区：到一个或多个节点的链路故障，节点本身仍活跃，甚至仍接收客户端请求。
  → 无法区分「远端失败」与「远端不可达」；
  → 强制单副本一致的系统必须能「打破对称（break symmetry）」：分区期只留一个分区活动。

Majority decisions：只需 (N/2 + 1)-of-N 同意 → 用奇数节点（3/5/7）；
  含多数的分区继续，少数分区停止处理操作（牺牲可用性防分歧）。
  多数派还能容忍分歧：临时分歧最多阻止协议继续（牺牲 liveness），但不违反 safety。

Roles：单一 leader（Paxos 称 proposer）协调，followers（acceptor/voter）转发与投票。
Epochs（Raft 称 term）：每个 epoch 只有一名指定 leader；epoch 充当**逻辑时钟**，
  让节点能识别「过时节点」（epoch 小的命令被忽略）。

Leader changes via duels：心跳维持领导；超时者转 candidate、epoch+1、发起选举；
  必须获多数票；竞选之间加**随机等待**以减少同时竞选（dueling）。
Numbered proposals：epoch 内提案用严格递增编号；follower 接受某编号的**第一个**提案。

Normal operation（Paxos 两轮）:
  1) Prepare(n) → Promise(n; 已接受的最高编号提案及其值)
  2) AcceptRequest(n, 自己的值 或 收到的最高编号的值) → Accepted(n, value)
  Paxos 核心安全约束：一旦某提案被多数接受，其值永不变（防竞争 leader 回滚）。
    对应 Lamport 的 P2 / P2b / P2c。
FLP 的现实：Paxos **放弃 liveness**（宁可无限期等待也不出错）以保 safety。
实现挑战（作者列出，指向 Google《Paxos Made Live》）：
  leader lease 优化、稳定存储持久化与防损坏、安全的成员变更、
  新副本/崩溃恢复后的安全同步、快照与垃圾回收。
```

### 4.6 三种算法与强一致方法对比

```text
Paxos：强一致分区容错复制里最重要的算法之一。
      用于 Google Chubby（BigTable/Megastore 依赖）、GFS、Spanner。
      Lamport 1998《The Part-Time Parliament》；公认难实现；
      核心难点：Paxos 描述单轮共识，而实现要高效跑多轮并处理成员变更。
ZAB：ZooKeeper 的原子广播协议（Junqueira & Reed 2008 一脉）。
      原子广播与纯共识在定义上不同，但同属保证强一致的分区容错算法。
Raft：为**可理解性**设计，提供相同保证；论文描述了成员变更机制；被 etcd 采用。
      （本书写作时 Raft 论文尚新，标注年份 2013。）

强一致方法关键特征对比（照抄本书的对照维度）：
  Primary/Backup  单一静态主；复制日志，备不参与执行；复制延迟无界；非分区容错；手动/ad-hoc 切换
  2PC             一致投票（commit/abort）；静态主；无法承受协调者与节点在提交期间同时失败；
                  非分区容错；对尾部延迟敏感
  Paxos           多数投票；动态主；可稳健应对 n/2-1 个同时失败；对尾部延迟较不敏感
```

## 版本演进

本章是全书最需要「时间补丁」的一章。作者在 2013 年写它时，Raft 论文本身还没正式发表完，
etcd 才刚起步，Multi-Raft 与 NewSQL 都还不存在。

| 议题 | 本书（2013） | 2026 现状 |
| --- | --- | --- |
| Raft 的地位 | 作为「更易教学的算法」与 Paxos/ZAB 并列 | **Raft 已成为事实标准**：论文正式发表于 USENIX ATC 2014，开源实现遍地；新系统默认选 Raft 而非自研 Paxos |
| 共识的使用粒度 | 单组共识（一个集群一组） | **Multi-Raft**：按分片各一组共识组（Spanner/TiDB/CockroachDB 一脉），随之而来跨组事务与跨组负载均衡 |
| 2PC 的处境 | 判为 CA、非分区容错 | 结论仍成立；但实践上 2PC 的协调者**被放进共识组**（协调者本身高可用），从而把阻塞风险大幅压缩 |
| 强一致的代价 | 「一轮多数派往返」这个概念 | 已可量化（本地 fsync + 一次多数派往返），并发展出 ReadIndex 读、租约读、follower 读等优化路径 |
| 成员变更 | 列为「实现挑战」 | 单步/联合共识等成熟方案，并有工具化验证 |
| 一致性声称的验证 | 无 | **Jepsen** 一类第三方故障注入实测，反复验证/证伪各系统的强一致声称 |
| 协调服务的形态 | ZooKeeper/Chubby 一脉 | 除 ZK/etcd 外，Kafka 一类系统把共识下沉到自身（KRaft），减少对外部协调服务的依赖 |

## 近年研究与工业界开源实践（2015–2026）

- **Raft 的普及**：2013 年本书写作时 Raft 尚是「新算法」；到 2026 年它已是默认选择。
  最典型的开源落地是 etcd——实测 `etcd-io/etcd` star = **52310**（2026-09 `gh api` 实测）。
  本书 4.6 说「Raft 被 etcd 采用」，这句话在十年后被完全验证，而且远不止 etcd。
- **Multi-Raft 与 NewSQL**：Spanner（OSDI 2012）确立的「按分片各一个共识组 + 跨片 2PC」范式，
  成为新一代分布式数据库的标准骨架；随之产生的工程议题是
  跨组事务的原子提交、跨组热点迁移与单组吞吐天花板。
- **共识下沉 / 去外部依赖**：Kafka 一类系统用自身共识机制（KRaft）替代外部协调服务，
  把本书第 4 章的「共识」从「一个独立服务」变成「系统内嵌能力」。
  实测 `apache/kafka` star = **33848**（2026-09 `gh api` 实测）。
- **强一致读的优化**：ReadIndex、租约读、follower 读等方案把「读也要走多数派」的代价降下来，
  但各自对时钟与旧主复活有不同假设——这正是本书第 3 章时间与第 2 章模型的交汇处。
- **Jepsen 实测**：对大量声称强一致的系统做分区、时钟跳变、成员变更、磁盘故障注入，
  多次揭示实现层面的安全漏洞。**本书 4.6 的「公认难实现」在今天依然成立**，
  而且现在有了可复核的第三方证据。
- **成员变更的工程化**：联合共识/单步变更与自动化 membership 管理成为成熟库能力；
  本书把成员变更列为「实现挑战」，今天的建议是**直接用成熟实现，别自己写**。
- 本目录所有代码为教学示意、不参与构建；star 数均为 2026-09 `gh api` 实测，
  查不到的一律写「star 未核验」。

## 常见误区与本书需修正之处

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「同步复制就是强一致」 | 同步主备仍是 N-of-N + 静态主 + 无界复制延迟，**非分区容错**；强一致需要「防分歧」的协议保证 |
| 2 | 「2PC 是 CP」 | 本书明写 **2PC 是 CA、不分区容错**：协调者挂了就只能等人来，无法安全提升新协调者 |
| 3 | 「主备复制 + 自动切换 = 容错」 | 本书把它定性为 best-effort：split-brain、lost update、手动切换是它的常态 |
| 4 | 「Raft 比 Paxos 更强/更安全」 | 二者在同等容错假设下等价；Raft 赢在**可理解性与工程收敛**，不是更强的保证 |
| 5 | 「多数派写丢不了数据，切主也没风险」 | 成员变更期的双多数派、旧 epoch 提交陷阱、缺 fencing 的实现都是真实事故源 |
| 6 | 「共识很慢，所以别用」 | 🔧 慢的是**跨故障域的多数派往返**；流水线、批处理、fsync 优化都在这条地板之上做文章 |
| 7 | 🔧 「一个集群一组共识就够了」 | 现代系统是 **Multi-Raft**：一组共识有吞吐天花板，按分片拆组才扩得动（伴随跨组事务代价） |
| 8 | 🔧 「用上 Raft 库就等于实现了强一致」 | 还要保证状态机确定性执行、正确的快照与成员变更；Jepsen 实测反复证明实现层漏洞普遍存在 |
| 9 | 🔧 「本书列的实现挑战可以自己慢慢啃」 | 2026 年的正确做法是**用成熟实现**（etcd/各语言 Raft 库），自定义只限日志语义与快照格式 |
| 10 | 🔧 「5 副本比 3 副本好，默认上 5」 | 5 副本容忍 2 故障但写需 3 个 ACK：延迟与成本同时上升，应按可用性目标反推副本数与放置 |
| 11 | 🔧 「读也要走一遍多数派」 | 已有 ReadIndex / 租约读 / follower 读等方案，但各自依赖不同的时钟与领导权假设，选型要写清 |
