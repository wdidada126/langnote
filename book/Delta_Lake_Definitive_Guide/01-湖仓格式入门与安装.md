## 核心精讲

### 1.1 数据湖的四个原始故障（教学示意）

裸 parquet 目录当表用，会同时踩中四类问题：

1. **读到半写状态**：写入者边写文件边被读取者 LIST 到，看到「有 A 文件没 B 文件」的中间态——没有原子发布。
2. **schema 无契约**：上游加一列、改类型，下游静默读错（列顺序错位、类型隐式转换）。
3. **更正即重写**：UPDATE/DELETE 只能整分区 `INSERT OVERWRITE`，并发写互相覆盖。
4. **无法回滚/审计**：数据被覆盖就是被覆盖，出错只能靠对象存储版本控制人肉找回。

一句话：**文件系统只有「对象」原语，没有「表」原语**。表格式要补的就是表原语：
原子提交、schema、快照、可查询的历史。

### 1.2 表格式的三件套

```text
<table-format> = 元数据协议（快照/日志如何组织）
               + 表操作原语（DDL/DML 到文件布局的映射）
               + 引擎约定（谁来实现读写，协议如何版本化）
```

Delta 的答案：**以事务日志（transaction log）为核心**——每次成功写表 = 往 `_delta_log/`
追加一个编号递增的 commit 文件，commit 文件列出该快照「新增/删除了哪些 data file」。
读取 = 从最新 commit 重建当前文件清单（再叠加 checkpoint 加速）。

### 1.3 Delta Lake 的定位（书中反复强调的四条）

- **ACID on object storage**：对象存储没有 rename/原子写，Delta 用「一次提交一个 JSON」的串行化点绕过。
- **批流同一张表**：同一份数据既是批表也是流 source/sink（第 7 章）。
- **时间旅行/审计**：历史 commit 即历史快照（第 5 章）。
- **可扩展的存储布局**：分区、Z-ORDER、liquid clustering、DV（第 9/10 章）。

⚠️ 注意术语：Databricks 语境里的 **lakehouse（湖仓）** = 数据湖的成本 + 数据仓库的管理与 ACID；
Delta 是它在 OSS 层的载体。原书第 9 章才进入架构层，第 1 章只给这个词的定义。

### 1.4 竞品坐标（务必与 [../bigdata/10-计算引擎的演进.md](../bigdata/10-计算引擎的演进.md) 对照）

| 维度 | Delta Lake | Apache Iceberg | Apache Hudi |
| --- | --- | --- | --- |
| 元数据核心 | 事务日志（JSON commit + parquet checkpoint） | 快照清单（metadata.json + manifest list/files） | timeline（instant 文件）+ 文件索引 |
| 出身 | Databricks（2019 开源，现 Linux 基金会） | Netflix（2017 开源，ASF 顶级） | Uber（2016 开源，ASF 顶级） |
| 引擎重心 | Spark/Databricks 一等公民，多引擎经协议/Kernel | 引擎中立性最强（Spark/Flink/Trino/Hive/StarRocks…） | Spark 为主，写入侧重 |
| 协议披露 | PROTOCOL.md（spec 在 delta.io） | 表规格文档，REST catalog 已事实标准 | 规格文档 |
| 跨格式 | UniForm（一份数据三种元数据） | — | OneHoodie |

判断口径（2026）：**选 catalog/治理层比选表格式更容易锁定成本**。Databricks 上 Delta 默认；
多引擎混合环境里 Iceberg 的 catalog 生态更开放；Delta 用 UniForm/Delta Kernel 反攻这一劣势（见 03、05 章文件）。

### 1.5 开源与治理史

- 2019-03 Databricks 宣布开源 Delta Lake；2020-06 Delta 1.0（承诺 API 稳定）。
- 2021-06 捐赠给 Linux Foundation；同期 Databricks 发 Delta Sharing（第 14 章）。
- 2023–2025 OSS 3.0/3.1/3.2 → 🔧 4.0（统一元数据、UniForm GA、type widening），版本演进详表见各章「版本演进」段。

### 2.x 安装矩阵（教学示意）

```bash
# spark-sql 挂 delta-core（版本号要与 Spark 大版本匹配，示例非书中原文）
spark-sql --packages io.delta:delta-spark_2.12:3.2.0 \
  --conf "spark.sql.extensions=io.delta.sql.DeltaSparkSessionExtension" \
  --conf "spark.sql.catalog.spark_catalog=org.apache.spark.sql.delta.catalog.DeltaCatalog"
```

要点：

1. **两个 conf 必配**（Spark 3.x 起）：`DeltaSparkSessionExtension` 注入 Delta 的 SQL 解析/优化规则；
   `DeltaCatalog` 让 `CREATE TABLE ... USING DELTA`、`ALTER TABLE` 走 Delta 语义。
   漏配的后果：能读表，但 DML/时间旅行语法报错——新手最高频故障。
2. **兼容矩阵**：delta-spark 3.x 支持 Spark 3.4–3.5；🔧 4.0 对齐 Spark 4.0。
   配套表在 delta.io「Rapid Release Notes」，选型时先看 Spark 版本再选 Delta。
3. **Databricks 内置**：DBR 里 Delta 永远内置且领先 OSS（DV/liquid clustering 先 DBR 后 OSS 是常态）。
4. **云厂商托管 Spark**：EMR（Delta 为可选组件）、Dataproc（可选 image）、Synapse（原生支持）——
   第 4 章「生态」还会讲 Trino/Flink/Presto 读 Delta 的旁路。
5. **delta-standalone / kernel**：不依赖 Spark 的最小 Scala/Java 库（事务构建、日志解析），
   加上社区 Rust 实现 delta-rs，是第 6 章「原生应用」的基础设施。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「Delta 是 Databricks 私有格式」 | OSS 版可独立跑在任何 Spark 上，协议文档公开；Databricks 只是最大贡献者 |
| 2 | 「装了包就能用全部语法」 | 必须配 extensions + catalog 两个 conf；否则 MERGE/DESCRIBE HISTORY 解析失败 |
| 3 | 「表格式 = 文件格式」 | Parquet 是文件级编码，Delta 是表级元数据协议，二者正交（Delta 默认用 Parquet） |
| 4 | 🔧 「OSS 与 Databricks 功能同步」 | DV、liquid、clustered 表等常先在 DBR GA；选型核对各自 release notes |
