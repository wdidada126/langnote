## 核心精讲

### 12.1 没有 catalog 的 Delta 是什么样

- 路径挂载（`spark.read.format("delta").load("/mnt/...")`）：权限靠存储 IAM 粗管，
  「谁能读哪张表」退化为「谁能 LIST 哪个目录」；重命名/迁移即断链。
- Hive Metastore：有名字空间但 ACL 弱、无列行级策略、审计零散。
- 结论：**表格式管 ACID，catalog 管 ACL/发现/血缘**——两层都缺就不成「湖仓」。

### 12.2 Unity Catalog 对象模型

```text
metastore（区域级根）
└── catalog                      ← 环境/域隔离（main、sandbox、prod）
    └── schema（database）
        └── secured objects：TABLE / VIEW / MODEL / VOLUME / FUNCTION / CONNECTION
```

- Delta 表注册进 UC 后获得**三段式全名** `catalog.schema.table`，
  所有策略、血缘、审计以此为主键；同名表在不同 catalog 即不同对象。
- 表形态：
  - **managed table**：UC 管存储生命周期（DROP 即清数据）；
  - **external table**：只登记不接管存量路径（入湖迁移主流形态）。
- 🔧 2024-06 UC 开源（含 REST API），从「Databricks 特性」变为可自建的公共治理层；
  与 Iceberg REST catalog 阵营开始正面竞争——读本章时把「UC」理解为「模型 + 两个实现（托管/开源）」。

### 12.3 权限原语

```sql
-- 教学示意
GRANT USE CATALOG ON prod TO `analysts`;
GRANT SELECT ON TABLE finance.gmv_daily TO `analysts`;
GRANT MODIFY ON bronze.kafka_orders TO `ingest_svc`;
CREATE SHARE customer_data AS
  IN Catalog prod, Schema prod.sales, Table prod.sales.orders;   -- 共享对象（接第 12 章文件）
```

- ACL 模型：主体（USER/GROUP/SERVICE PRINCIPAL）× 对象层级 × 权限位
  （SELECT/MODIFY/OWN/EXECUTE/READ VOLUME…），就近覆盖（对象级 > schema 级 > catalog 级）。
- 与存储 IAM 的分层：**用户凭证 → UC 授权 → UC 服务身份访问云存储**——
  分析师不再需要 S3 路径权限，这是「治理下推、凭证收敛」的关键句。

### 12.4 动态访问控制（策略即函数）

```sql
-- 教学示意：行过滤 + 列掩码（绑定 SQL/UDF 函数，UC 在建表时声明）
CREATE TABLE hr.employees (...)
  WITH ROW FILTER ON 1 TO func hr.filter_by_region USING (region)
  COLUMN MASK ON ssn USING func hr.mask_ssn(ssn);
```

- **row filter**：查询计划插入谓词函数结果；不同主体见不同行，物理表仍一张。
- **column mask**：列值经函数改写（脱敏/哈希/置 null）后再出结果——比视图方案少一层维护。
- **tags/attributes + data classification**：元数据打标（PII/FINANCIAL），策略与检索都按标签走；
  发现类工具（自动 PII 检测）补「人忘了打标」的洞。
- 机制边界：mask/filter 由**引擎侧（SQL warehouse）强制**，绕过引擎直读对象存储则失效——
  所以必须配合 12.5 的凭证收敛（IAM 不允许人直读）。

### 12.5 存储治理：external location 与 credential

- **storage credential**（IAM role 绑定）：UC 代访云存储；**external location**（URL 前缀）：
  划定可挂载边界——两者拼出「表→路径」的信任链，杜绝「任意路径挂载表」的走私。
- 迁移路径（书中 medallion 视角）：legacy 目录 → external table 登记 → 逐步转 managed。

### 13.1 元数据即数据

- 每个 UC catalog 自带 `information_schema`（tables/columns/table_privileges…）；
  🔧 Databricks `system.*` 库（billing、access、lineage、audit）把治理做成可 JOIN 的事实表。
- 用例模板（教学示意）：

```sql
SELECT object_name, grantee_name, privilege_type
FROM prod.information_schema.table_privileges
WHERE privilege_type = 'SELECT' AND grantee_name LIKE '%contractor%';
```

- 对照：Delta commit 是**数据面**元数据（版本/操作者/指标），UC 是**访问面**元数据（ACL/标签/血缘），
  13.2 的血缘把两者缝合。

### 13.2 血缘：从计划采集，而非人工登记

- 表级：UC 在每次查询执行时记录 read/write 依赖（哪个表流进哪个表）——
  第 9/10 章的 medallion 管道自动成为血缘图，DLT/Lakeflow 的声明依赖最完整。
- 列级：由查询计划推导列到列的变换边（能力随版本演进，粒度以官方文档为准）。
- 消费场景：影响分析（改 silver 一列会炸哪些 gold/报表）、合规取证（PII 从哪流到哪）、
  成本归因（下游热度决定上游要不要 OPTIMIZE）。
- 诚实边界：**「自动采集」不等于「全」**——外部引擎直读文件、笔记本取数都是暗管道；
  所以治理文档都同时强调「只允许经 UC 访问」。

### 13.3 数据流治理闭环（两章合流）

```text
登记（catalog/标签）→ 授权（最小权限）→ 执行（filter/mask 强制）
→ 观测（审计日志 + system 表 + 血缘）→ 整改（发现暗管道/过度授权 → 收紧）
```

- 审计三问的落点：谁读了（access 日志）、谁改了（Delta history + commitInfo.userId）、
  改了什么（CDF）。**第 4 章文件的时间旅行与 CDF 在这里变成治理工具**——
  一套机制（日志）两用（ACID + 审计）是本章最值得记住的设计品味。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「有了 UC 就安全了」 | filter/mask 依赖引擎执行；绕过 UC 直读对象存储即失守，凭证必须收敛 |
| 2 | 「catalog = 表格式」 | 两层正交（第 3 章文件 4.2）；UC 上也能挂 Iceberg/视图/模型 |
| 3 | 「血缘靠人画」 | UC 自动采集计划级血缘；人工登记只补外部暗管道 |
| 4 | 「DROP 了还能时间旅行找回来」 | managed table DROP 连带存储清退；找回靠备份/克隆纪律 |
| 5 | 🔧 「UC 是 Databricks 专有」 | 2024-06 起开源实现存在；「模型归 Databricks，实现开始分化」 |
