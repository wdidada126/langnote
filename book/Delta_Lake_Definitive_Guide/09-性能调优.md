## 核心精讲

### 10.1 代价模型：慢在哪一层

```text
查询延迟 ≈ 元数据重放(_delta_log/checkpoint)
         + 文件清单获取（stats 过滤前的 LIST/解析）
         + 被裁后文件的扫描 IO（行数 × 列宽）
         + 谓词逐行评估 + DV bitmap 过滤
```

- 症状→手段对照：`DESCRIBE HISTORY` 看 numFiles 增长（小文件）；
  Spark UI 看 scanned file 数与 skipping 命中率；元数据耗时长 → 日志膨胀/checkpoint 问题。

### 10.2 小文件与 OPTIMIZE

- 目标文件尺寸（Databricks 经验口径）：**单文件 ~1GB 量级**（非硬规），
  分区内文件数 × 平均大小决定扫描并行度与元数据体积。
- 产生源：流式微批（第 6 章文件）、动态分区覆盖、过多 reducer、频繁小 MERGE。
- 语法与机制：

```sql
-- 教学示意
OPTIMIZE events;                                  -- 全表 bin-pack（只合并不聚簇）
OPTIMIZE events WHERE dt = '2026-01-01';          -- 按 filter 限定范围，增量维护常用
OPTIMIZE events ZORDER BY (user_id);              -- 合并 + 重排聚簇
```

- OPTIMIZE = 一次普通事务（新快照 add 合并文件、remove 旧文件）；历史文件等 VACUUM。
  与并发 DML 的关系：合并重写会物化被改行——MERGE 冲突时 OPTIMIZE 重试/失败属正常现象。

### 10.3 data skipping 的能与不能

- 机制：commit 里每个 add 带 min/max/nullCount stats；查询谓词与 stats 求交，
  不相交文件**整文件不进扫描计划**。
- 边界条件（高频考点）：
  1. 只对**前 `delta.dataSkippingNumIndexedCols`（默认 5）个非分区列**统计——把高频过滤列排到 schema 前面是合法且有效的土办法（或用 partition/liquid 替代）。
  2. 文件级粒度：一个文件内值域覆盖宽 → skipping 失效；**Z-ORDER/liquid 就是为了把值域做窄**。
  3. 函数包裹列（`WHERE year(ts)=2026`）可能用不上 stats（取决于表达式下推与 transform；分区裁剪同理要求谓词与分区表达式同构）。
  4. DV 生效后文件仍被引用，扫描计划多了 bitmap 过滤一步；stats 会更新删除基数辅助整文件裁剪（🔧 细节随版本增强）。

### 10.4 Z-ORDER：机制与极限

```text
文件重排：把 (a,b) 两列值做比特交错 → 按 Z 值排序写出
        → 同一文件内 a 的局部性与 b 的局部性同时（粗略）成立
```

- 对比复合排序：`ORDER BY (a,b)` 只对前导列友好（b 值域全局分散）；
  Z-ORDER 的交换哲学：**两列都有局部性，但都不完美**（值域呈方块而非带状）。
- 实测建议姿势：`OPTIMIZE ... ZORDER BY (col)` 选**高基数 + 高频等值/范围过滤**列；
  基数太低（性别类）无收益。
- 硬约束（务必背）：**一个表只能存在一种 Z-ORDER 组合**（对相同列集重排）；
  Z-ORDER 只在 OPTIMIZE 重写文件时发生，是「聚簇债」的形态。
- 代价：Z-ORDER 重排打散插入序 → 「按时间追加」的天然局部性被牺牲，别对仅按时间过滤的表乱 ZORDER。

### 10.5 分区 vs data skipping vs 聚簇：三选一决策

| 判据 | 分区 | 普通文件+skipping | Z-ORDER/liquid |
| --- | --- | --- | --- |
| 过滤列形态 | 低基数枚举（dt、region） | 任意 | 高基数（user_id、device） |
| 粒度 | 目录级，硬裁剪 | 文件级 | 文件级、可调 |
| 可逆性 | ❌ 建表定死，改需重建 | ✅ | ✅ 重聚簇即可 |
| 失控风险 | 分区爆炸/倾斜 | — | 低 |
| 现代倾向 | 时间列常留 | — | 其余尽量交给聚簇 |

原书与 2024+ 社区共识一致：**「先分区狂魔，后 skipping/聚簇救火」的旧路线正在被 liquid 取代**。

### 10.6 Liquid Clustering

```sql
-- 教学示意
CREATE TABLE metrics (...) USING DELTA CLUSTER BY (device_id, to_date(ts));
ALTER TABLE legacy SET CLUSTER BY (user_id);          -- 渐进接管旧表
OPTIMIZE metrics;                                     -- 增量物化聚簇（无 ZORDER 子句）
```

- 定位：**统一替代「分区 + Z-ORDER」两层手工物理设计**的声明式聚簇。
- 机制：声明聚簇键 → OPTIMIZE **渐进式**重排新写与热点数据（不是全量重写）；
  查询时按聚簇键做文件级裁剪（stats 与聚簇对齐）。
- 关键性质：
  1. **可演化**：换键不重建历史（渐进收敛），分区做不到；
  2. 无分区目录爆炸、无「忘填 dt」事故；
  3. 早期限制多（须 managed table、限制行过滤类特性等，DBR 13.3+ GA 方向、OSS 3.x 预览跟进——以官方文档为准）；
  4. `to_date(ts)` 这类 transform 让「时间粗粒度 + 实体细粒度」一表打尽。
- 迁移叙事（书中路径）：分区表 → appendOnly/新表 liquid 起步 → 旧表 `SET CLUSTER BY` 慢慢收敛。

### 10.7 DV 时代的 OPTIMIZE（新运维科目）

- 读债来源：每个文件的 DV bitmap 越大，行过滤越慢；跨多个 OPTIMIZE 周期的 DV 合并物化。
- 策略：DML 热表「高频小 OPTIMIZE（合并 DV）」比「低频全表 OPTIMIZE」稳；
  VACUUM 同时清被物化掉的旧 DV 文件（第 4 章文件 5.3）。

### 10.8 自动化与观测（Databricks 口径）

- **Auto Optimize**（写入路径自动 bin-pack，serverless/云侧）与
  **Predictive Optimization**（后台按价值信号调度 OPTIMIZE/Z-ORDER，DBR 12.2+）：
  把「要不要跑 OPTIMIZE」变成平台问题。
- 观测抓手：`with_optimize_hint` 类作业指标、cost governance 视图、
  以及最朴素的 `DESCRIBE HISTORY` 里 numAddedFiles/numRemovedFiles 比值趋势。
- 其余 Spark 侧手段（广播 join、AQE coalesce、cache）与 Delta 无关但常一起考，见
  [../bigdata/05-Spark性能优化.md](../bigdata/05-Spark性能优化.md)。

## 常见误区

| # | 误区 | 修正 |
| --- | --- | --- |
| 1 | 「OPTIMIZE 越勤越好」 | 每次都是全文件重写 + 一次 commit；按分区增量 + 按价值触发才是正解 |
| 2 | 「Z-ORDER 多列效果 = 复合索引」 | 文件内多维独立局部性，非 B+ 树前缀语义；每表仅一种 ZORDER |
| 3 | 「分区数越多裁剪越狠」 | 分区爆炸伤元数据/LIST/小文件；高基数列绝不该做分区 |
| 4 | 「liquid 立刻重排历史」 | 渐进物化：不 OPTIMIZE 就一直处于「半聚簇」态 |
| 5 | 「skipping 对任何列生效」 | 默认只前 5 列有 stats；schema 列序是性能参数（可配合 liquid 放弃此技巧） |
| 6 | 🔧 「调优全靠手工」 | 云侧 Auto/Predictive Optimization 已成默认，手工会话价值转向键设计与验收 |
