## 一句话总结
SPANN 用「倒排索引 + 内存放中心点、磁盘放长 posting list」的混合思路，把十亿级向量的近似最近邻搜索从「内存吃不起」变成「小内存 + SSD 也能又快又准」——在三个十亿级数据集上，达到同样 90% recall 时比 DiskANN 快 2 倍，仅用 32GB 内存即可在约 1 毫秒内达到 90% recall@1/recall@10。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：ANNS（近似最近邻搜索）要在十亿级高维向量里毫秒级召回最近邻，但纯内存算法在数据量大时贵到用不起。
- 为什么难：全内存方案内存成本爆炸；纯磁盘方案延迟高；既要低延迟又要高 recall 还要省内存，三者互相打架。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 内存图索引 | HNSW、CAGRA | 图遍历找近邻 | 快但内存大 |
| 内存-磁盘混合 | DiskANN、SPANN | 内存放索引、磁盘放数据 | 省内存、低延迟 |
| 量化压缩 | PQ、RaBitQ | 压短向量 | 省内存但需重算距离 |

- 本文属哪类：内存-磁盘混合路线，但用倒排（inverted index）而非图的范式。
- 2-3 个必懂关键名词：
  - ANN / ANNS：Approximate Nearest Neighbor Search，允许极小概率找错换速度。
  - Inverted Index（倒排索引）：用中心点（centroid）组织 posting list，查询时只访相关列表。
  - recall@K：返回 K 个里真近邻的占比；论文以 90% 为「可用精度」门槛。

## 1. 问题背景与动机
- 前人工作简述：内存 ANNS（HNSW 等）在快+高 recall 上很成功，但规模一大内存成本极高；于是出现混合内存-磁盘方案（如 DiskANN）。
- 前人缺陷/未解决问题（逐条）：
  1. 内存成本爆炸：纯内存算法在十亿级数据上不可承受。
  2. 磁盘访问效率：混合方案要保证低延迟必须减少磁盘访问次数、且只取高质量 posting list。
  3. 建索引均衡：posting list 长度不均会拖慢查询，需要平衡。

## 2. 核心方法
- 最直观类比：把图书馆的「目录卡」放前台（内存），把「整本书」放书库（磁盘）；查书先翻目录卡，只去书库取最相关的几本。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 建索引：用分层均衡聚类（hierarchical balanced clustering）平衡各 posting list 长度，并把聚类边界附近的点也补进 posting list（augment by closure），提升召回。
  2. 存储布局：posting list 的中心点放内存，巨大的 posting list 放 SSD 磁盘。
  3. 查询（search）：用 query-aware 动态剪枝，只访问必要的 posting list，减少磁盘访问。
  - 输出：每个查询的近似 top-K 近邻（低延迟、高 recall）。
- 形式化要点：目标是在固定内存下，最小化磁盘访问次数同时保 recall；核心超参在聚类数、posting list 长度、剪枝阈值（🔧 细节见论文）。
- 理论性质/保证：以工程/系统协同设计为主，无显式理论最优性保证。

## 4. 实验结论（概览）
- 对比基线：DiskANN 等 SOTA ANNS 方案。
- 数据集：三个十亿级（billion-scale）向量数据集。
- 指标：达到目标 recall 的查询延迟、内存占用、QPS。
- 结论方向（摘要给出的已核实数字）：
  - 达到同样 90% recall、同样内存下，比 DiskANN 快 2 倍。
  - 仅 32GB 内存即可在约 1 毫秒内达到 90% recall@1 与 recall@10。
