## 一、背景与问题：三代分析平台的演化与"两层架构"的四顽疾

### 1.1 论文的立场（摘要，第 1 页）

"今天的数仓架构将在未来数年内萎缩，被一种新的架构模式——Lakehouse——取代"，其三个特征：(i) 基于开放直接访问数据格式（Apache Parquet/ORC）；(ii) 对机器学习与数据科学的一等支持；(iii) 最先进的性能。注意这是**立场论文 + 系统实践报告**的混合体：论点（数仓式）与证据（Delta Engine 的 TPC-DS 成绩）并重。

### 1.2 三代平台叙事（§1 Introduction，第 1–2 页）

- **第一代**：操作库 ETL 集中到数仓，schema-on-write，服务 BI/决策支持。问题：存算耦合的本地一体机必须按峰值付费；无法存储/查询视频、音频、文本等非结构化数据。
- **第二代**：把原始数据全部下沉到**数据湖**（Hadoop/HDFS，后来 2015 年起被 S3/ADLS/GCS 云对象存储取代——持久性 >10 个 9、异地复制、极低成本与 Glacier 级归档）。schema-on-read 带来"什么都能便宜地存"，但把数据质量与治理问题**推给下游**；湖中一小部分数据再 ETL 进下游数仓（Teradata/Redshift/Snowflake）供 BI。作者断言"lake + warehouse 两层架构如今在财富 500 强企业中几乎人人在用"（§1，第 2 页）。
- **稻草人方案（straw-man）**：干掉数据湖、全存进"存算分离的现代数仓"。作者以"采纳度低"为据否定：仍管不好非结构化数据，仍无法让 ML 负载直接快读（§1，第 3 页）。

```
(a) 第一代：数仓一体机               (b) 第二代：湖+仓两层（现状）        (c) 第三代：Lakehouse
┌──────────────┐                ┌────────┐   ETL   ┌──────────┐      ┌──────────────────────┐
│ 结构化数据     │──ETL──▶ 数仓    │ 任意格式 │ ────▶ │ 数仓(BI)  │      │  任意格式 + 元数据/缓存/ │
│ (操作库)      │                │ 数据湖  │        │ 湖(BI之外)│      │  索引层（湖即仓）        │
└──────────────┘                └────────┘        └──────────┘      └──────────────────────┘
  BI 报表                        ML/DS 直读湖       ML/DS 直读湖       BI / DS / ML 同读同管
  存算耦合·按峰值付费             双份拷贝·天级陈旧    一段ETL            开放格式·直接访问·少段ETL
```

（按论文图 1 语义重绘；(b) 中"湖→仓"即被批判的两段 ETL 链。）

### 1.3 两层架构的四个问题（§1，第 2 页；§2 展开）

1. **Reliability（可靠性）**：湖与仓保持一致困难且昂贵，持续 ETL 工程 + 两套引擎的语义差异（数据类型、SQL 方言、schema 归一化程度不同）不断引入 bug 与故障模式。
2. **Data staleness（数据陈旧）**：新数据入仓常以"天"计，反而不如第一代（操作数据当场可查）。引用 Dimensional Research/Fivetran 调研：**86% 的分析师在用过期数据，62% 每月多次等待工程资源**（§1，第 2 页，文献[47]）。
3. **Limited support for advanced analytics（高级分析支持有限）**：TensorFlow/PyTorch/XGBoost 都无法在数仓上高效工作——它们要用非 SQL 代码扫大数据集，走 ODBC/JDBC 低效，且无法直接访问数仓私有格式；厂商建议导出成文件，等于**再加第三段 ETL**（§1，第 2–3 页）。
4. **Total cost of ownership（总拥有成本）**：双份存储 + 私有格式锁定推高迁移成本。

核心研究问题被提炼为一句话（§1，第 3 页）：**能否把基于 Parquet/ORC 的数据湖，变成同时具备数仓性能与管理特性、又能被高级分析直接快速 I/O 的系统？**

### 1.4 既有"半个 Lakehouse"趋势的证据（§2 末，第 3 页）

所有主流数仓近年都加了 Parquet/ORC **外部表**（但管理特性、ETL 复杂度照旧，且引擎主要为自己的内部格式优化，外部表常表现不佳）；同时 Spark SQL/Presto/Hive/Athena 等直接跑湖上 SQL 的引擎获得大量投资（但缺 ACID、缺索引）。Lakehouse = 把两条趋势合流。

## 二、核心方法精读：三块技术支柱

### 2.1 Lakehouse 定义与总体架构（§3，第 3 页；复现论文图 1(c)/图 2）

定义：**基于低成本、直接可访问存储的数据管理系统，同时提供传统分析型 DBMS 的管理与性能特性——ACID 事务、数据版本、审计、索引、缓存、查询优化**。代价是放弃关系 DBMS 的"数据独立性" cornerstone（存储格式成为公共 API），§3.3 全部篇幅都在回答"放弃了它怎么还能快"。

```
        ┌──────── ETL/ELT ────────┐
        ▼                         │
 ┌─────────────────────────────────────────┐
 │           Data Lake (对象存储 S3/ADLS)    │
 │   开放格式数据文件 (Parquet/ORC)           │
 │  ┌───────────────────────────────────┐  │
 │  │ Metadata / Caching / Indexing 层    │  │  ← 事务管理、治理、
 │  │ (如 Delta Lake：定义"表版本=哪些对象")│  │    版本、辅助数据结构
 │  └───────────────────────────────────┘  │
 └───────┬───────────┬───────────┬─────────┘
         ▼           ▼           ▼
       SQL API   声明式       元数据 API      ← 多引擎并行访问
       (BI)     DataFrame     (ML 直读)
                (Data Science)
```

（图 1/2 语义重绘：Lakehouse 与两层架构的差别是把"Metadata, Caching, and Indexing Layer"插进湖里，从"湖+仓"塌缩为"湖即仓"。）

作者自述其实现栈：Delta Lake（元数据层）+ Delta Engine（C++ SQL 引擎，即后来 Photon 的前身）+ Databricks ML Runtime（§3，第 4 页）。同时声明"其他设计也可能成立，Parquet 也可换成更好格式"。

### 2.2 支柱一：元数据层实现可靠数据管理（§3.2，第 4 页）

- 谱系：Apache Hive ACID（最早，用 OLTP DBMS 记录"表版本↔文件集"）→ 2016 年 Databricks 开发 **Delta Lake**（事务日志以 Parquet 存在湖自己身上，可扩展到**每表数十亿对象**）→ Netflix 的 **Apache Iceberg**（类似设计，支持 Parquet 与 ORC）→ Uber 的 **Apache Hudi**（侧重流式入湖，**当时不支持并发写**）。
- 经验性结论：元数据层相对裸 Parquet/ORC 湖"性能相当或更好"，且白送事务、回滚、time travel、zero-copy clone；采纳速度快——"**Delta Lake 三年内在 Databricks 覆盖了约一半的计算小时**"、"数千客户在用"（第 4 页，两处均为口径：约半数负载/半数 compute-hours）。
- 元数据层还是**数据质量**与**治理**的天然落点：Delta 的 schema enforcement、constraints API（违约记录自动拒绝或隔离）；授权前查访问控制、可靠审计日志。
- 作者承认的开放问题（§3.2 Future Directions，第 4 页）：日志放对象存储 ⇒ 高读带宽、免运维，但**事务/秒受限于对象存储延迟**；三者当时都只支持**单表事务**，跨表事务待扩展。

### 2.3 支柱二：不换存储格式如何做出现代 SQL 性能（§3.3，第 4–5 页）

数仓的性能来自：热数据放 SSD、统计信息、索引、格式与引擎协同优化。Lakehouse 放弃最后一条（格式=公共 API），但论证前三种优化都可"格式无关"地外挂：

1. **Caching（缓存）**：因为有事务元数据层，"缓存文件是否仍有效"可被运行中事务精确判定，所以放心把 S3 文件缓存在节点 SSD/RAM；且**缓存可以是转码后的格式**——Databricks 的缓存会对 Parquet 做部分解压，等价于封闭数仓的内部格式优势。
2. **Auxiliary data（辅助数据）**：基础表格式之外可维护完全自控的旁路文件。Delta 在事务日志的同一 Parquet 文件里维护**每文件列级 min/max 统计**支撑 data skipping，正在实现 **Bloom filter 索引**；理论上可承接 NoDB/H2O 一系"裸文件上也索引"的学术积累（文献[1][2][34]）。
3. **Data layout（数据布局）**：格式固定不等于布局固定——记录排序（单维或 **Z-order/Hilbert 空间填充曲线**多维聚簇）仍可控（文献[39] Morton 1966）。

三者的分工逻辑（§3.3，第 5 页）：**热数据靠缓存**（多数查询集中在热子集，缓存后与封闭数仓同质）；**冷数据靠布局+统计跳过**（决定性能的是读入量，zone map + 聚簇能像专有数仓一样最小化 I/O）。

### 2.4 支柱三：高级分析的高效访问（§3.4，第 5–6 页；复现论文图 4）

```
用户程序:  users = spark.table("users")          ← 声明式 DataFrame
           buyers = users[users.kind=="buyer"]   │ 惰性求值，不触发 IO
           train_set = buyers["date","zip",…]     ▼
                    .fillna(0)
        ┌────────────────────────────────────┐
        │ 惰性求得的查询计划(逻辑/物理)          │  SELECT(kind="buyer")
        │  → 优化器下推 selection/projection    │  PROJECT(date,zip,…)
        └───────────────┬────────────────────┘  PROJECT(NULL→0)
                        ▼  传给数据源插件
        Delta Lake client → 查元数据层：读哪些分区/
        用不用缓存/data skipping → model.fit(train_set)
```

要点：ML 库（MLlib、GraphFrames、SparkR、Koalas 等）的数据准备大多落在 DataFrame 上，而 Spark SQL 已证明**声明式 DataFrame 可整体优化**（文献[11]）；把谓词/投影下推进 Delta 数据源插件后，ML 负载自动吃到 2.3 节的全部优化。反面是 tf.data 一类不携带查询语义的 API，以及"数据加载-CPU/GPU 传输重叠"这种数仓圈没管过的问题（引 Richins et al. HPCA 2020 说明推理侧加速器利用之难）。另有 MLflow 记录训练用表版本（time travel 复现实验）、feature store 应复用 DBMS 事务/版本原语等延伸讨论。

### 2.5 研究问题与行业含义（§4，第 6–7 页）

- **替代路线被点名质疑**：给数仓建大规模并行 serving 层（如 Hive LLAP）——更贵、更难管、大概率更慢，且把"选高效读格式"问题后移；对象存储的低成本/高带宽/高可用三大卖点全部被 serving 层稀释。治理角度：法规要求随时检索/删除旧数据，开放格式保证"不等厂商"的通路。
- 对**其他数据管理研究**的外溢：polystore（BigDAWG）的部分查询会退化为"直接查湖"；数据集成/清洗可就地跑（大数据集间的大 join/聚类）；HTAP 可作为 Lakehouse 前置 bolt-on（用事务 API 归档、按一致快照查询）；feature store 可回归为"带 DBMS 功能的湖抽象"；serverless 引擎（Starling 一类）需要集成元数据层而非裸扫文件；**data mesh**（Dehghani 2019）这类组织形态因"数据全员直接可读"而更易落地。

### 2.6 元数据层的提交协议（示意伪码，综合 §3.2 与姊妹篇 Delta 论文 §3.2.2）

本文只给架构立场，"日志如何原子提交"的细节在 Delta PVLDB'20；为便于独立阅读，此处补一段最小伪码（语义忠于两篇原文）：

```
function commit(table, actions):            # actions: add/remove/metaData/txn…
  r  := latest_visible_log_id(table)        # 读 _last_checkpoint + LIST 日志尾部
  write_data_objects(actions, GUID命名)      # 并行；此刻对任何读者不可见
  loop:
    if atomic_put_if_absent(table, "00000{r+1}.json", actions):
      return r+1                            # 提交点：唯一日志槽位占得 ⇒ 可串行化
    else:
      r  := latest_visible_log_id(table)    # 乐观并发：让号重试
      validate_no_conflict(actions, log(r+1))  # 冲突则放弃重来
```

关键洞察：**可串行化不来自锁或日志服务，而来自"版本号=对象键"这一设计的 CAS 语义**；数据对象的不可变 + 日志的单调追加 = MVCC 的极简云原生变体。

## 三、实验与数据：TPC-DS SF30K（§3.3 Performance Results + 图 3，第 5 页）

唯一一组定量实验：Delta Engine（当时基于 Spark 的新 C++ 引擎）对比四家主流云数仓（DW1–DW4，覆盖云厂商自营与第三方），TPC-DS **power test、scale factor 30,000（30TB）**，960 vCPUs/家、带本地 SSD，横跨 AWS/Azure/GCP。图 3 柱值按图例顺序读数（原文数字见正文）：

| 系统 | Power Test 时长 (s) | 花费 ($) |
|---|---|---|
| DW1 | 2,996 | 153 |
| DW2 | 7,143 | 286 |
| DW3 | 5,793 | 206 |
| DW4 | 37,283 | 570 |
| Delta Engine（on-demand） | 3,302 | 104 |
| Delta Engine（spot） | **3,252** | **56** |

结论表述（原文措辞）：" comparable or better performance at a lower price point"——时长与最便宜数仓相当或更好，**成本约为各家的 1/3 至 1/10**。两个诚实性注脚：① 这是厂商自测（基准非审计运行，且系统匿名化为 DW1–DW4，无法第三方复核）；② 脚注 1 披露了一个重要不对称：**各家都从"数据已缓存在 SSD"的热身状态起跑**（因为部分被比数仓只支持节点附加存储），Delta Engine 在冷缓存起跑时慢 18%——热身条件部分抵消了湖存储的延迟劣势。

| 时间旅行 | time travel | 查询表的过去快照（§3.2） |
| 零拷贝克隆 | zero-copy cloning / CLONE | 不复制数据生成本表新副本（§3.2） |
| 数据跳过 | data skipping | 用 min/max 等统计跳过无关文件（§3.3） |
| 区域映射 | zone map | 每文件的列值域摘要，跳过判定的实现（§3.3） |
| 转码缓存 | transcoded caching | 缓存中以更利于执行的形态存放 Parquet（§3.3） |
| Z 排序 / 希尔伯特曲线 | Z-order / Hilbert curve | 空间填充曲线实现多维聚簇（§3.3，Morton 1966） |

## 六、批判与延伸

### 6.1 批判

1. **利益相关方叙事**：论文论证的"可行证据"几乎全部来自 Databricks 自家系统（Delta Lake 采纳占比、Delta Engine TPC-DS），比较对象匿名（DW1–DW4）、条件有不对称（§三 的缓存脚注）。它是优秀的**研究议程设定**（research agenda），但作为"数仓将死"的证据则偏弱——数仓阵营（Snowflake 也讲 Iceberg、Databricks 也做 SQL warehouse）随后的演化恰恰是双向渗透而非单向替代。
2. **"wither"（萎缩）预测未被完全兑现**：写作两年后的现实比预言更复杂——Lakehouse 成为共识，但**格式战争**（Delta/Iceberg/Hudi）恰是本文"开放格式是核心"论断的反讽：三个元数据层互不兼容，生态至今用 UniForm/catalog 同步/转换来弥合；本文 §3.2 只轻描淡写地提了"其他设计也可能"。
3. **跨表事务与高事务率**是作者自认的洞（§3.2/§7 of Delta 论文），本文未展开：BI 语义里事实表+维表成组发布、CDC 多表原子入湖都需要多表原子性，后续 LakeVilla、Iceberg REST Catalog 方向在补课。
4. **非结构化数据论证偏口号**：把"湖能存图片音频"当核心卖点，但"如何**查询**它们"（向量检索、SQL/ML 混合谓词）在本文只有 feature store 一段远景；2023 年后的向量检索+Lance/Parquet 混合布局才算填上。
5. 性能支柱一的隐含前提：查询引擎要能"转码缓存 + 自控旁路文件"，这实际把一部分封闭数仓的复杂度请了回来（只是挪到缓存层），"开放格式=简单"的叙事被打了折扣。

### 6.2 延伸

- 与 Delta PVLDB'20 笔记对读（事务日志格式、S3 put-if-absent 协议工程细节在那篇）；再与 `Engineering_Lakehouses_with_Open_Table_Formats/06-事务与并发写.md` 对照三家并发协议差异。
- 引擎侧后续：Delta Engine 更名 **Photon**（C++ 向量化执行），其论文与博客可作为本文 2.3 节"缓存转码 + 辅助数据"的工程终点；另一极是 Iceberg 阵营的 Daft/Trino 直读路线。
- 研究议程兑现度盘点：多表事务、湖上向量检索、湖上 serverless 按查询计费（S3 请求成本与元数据层交互）——都能从本文 §4 找到原始问句。
- 治理线延伸：本文"开放格式便于合规删除"的论点，在各家"选择性删除"（Delta 2.x 前的整文件重写 vs Deletion Vector，见 `../../book/Delta_Lake_Definitive_Guide/07-高级特性-DV与CDF.md`）上得到戏剧性印证。

### 6.3 思考题（5 道）

1. 论文承认 Lakehouse "放弃了部分数据独立性"（§3）。请对照 Codd 1970 的两级映射论证：把存储格式升格为公共 API 后，哪些原本由 DBMS 内部承担的优化自由度转移给了谁？"转码缓存"是不是把失去的独立性偷运回来的后门？
2. §3.3 的三件武器（缓存/旁路统计/布局）都被声称"格式无关"。若把它们全部启用且深度定制（如缓存部分解压数据），系统与"封闭数仓"的实质差异还剩下什么？请用"更换查询引擎的成本"与"更换存储格式的成本"两个维度回答。
3. 元数据层"约半数负载、三年"的采纳速度，与外部表"所有大厂都支持"的普及度（§2 末），哪个更能支撑"数仓将死"的论题？设计一个能证伪本文主张的观察指标。
4. TPC-DS 实验让所有对手"数据已在 SSD 上热身"（脚注 1），Delta Engine 冷缓存慢 18%。请论证：这个不对称对"成本 1/3–1/10"的结论影响大还是小？分别在被比数仓按存储计费/不按存储计费两种定价模型下讨论。
5. §3.4 把 ML 数据加载优化归约为"声明式 DataFrame 下推到数据源插件"。对不携带查询语义的 tf.data/PyTorch DataLoader，是否存在通用的"半声明式"协议（例如只声明列集合与谓词句柄）让湖侧优化仍然生效？与 §4 的 feature store 论点如何衔接？

## 八、阅读方法与常见误读提醒

1. **这是立场论文，不是系统论文**：全文只有一个实验（图 3），其余是架构论证与行业观察。按"研究议程"读它，别按"基准报告"读它；系统细节去 Delta PVLDB'20 找。
2. **"Lakehouse"在本文是架构模式，不是产品**：把"用了 Delta/Iceberg 表格式"直接等同"实现了 Lakehouse"是常见话术滑坡——§3 的定义要求管理与性能特性齐备（缓存、统计、布局一样不少），只上事务层是"半个"。
3. **别把"数仓将死"读成"云数仓收入将死"**：论文预言的是架构中心从仓移向湖上的仓式功能；Snowflake/BigQuery 后来大量吸收开放格式（Iceberg 支持），恰是其"以另一种形式被承认"。
4. **注意 §3.3 脚注 1 的实验起跑条件**，以及对比系统匿名的原因（厂商不可点名引用非审计运行）——这两点决定该实验的可引用边界。
5. **建议配套**：先读姊妹篇 [`../doi_10.14778_3415478.3415560/00-精读笔记.md`](../doi_10.14778_3415478.3415560/00-精读笔记.md)（支柱一），再回本文 §4 的研究问题清单，能明显感到"工程文写实现、立场文写野心"的分工。

## 九、一页总结（复习卡）

- **问题**：湖+仓两层架构带来可靠性、陈旧性、ML 不友好、TCO 四大成本；单纯"存算分离数仓"或"裸湖+SQL 引擎"各治不了全病。
- **方案**：Lakehouse = 开放格式（Parquet/ORC）之上加元数据层（事务/版本/质量/治理），配三件格式无关的性能武器（转码缓存、旁路统计与索引、布局优化），ML 侧用声明式 DataFrame 承接同一批优化。
- **证据**：Delta Lake 三年占 Databricks 一半计算小时；TPC-DS SF30K power test 上 Delta Engine 与主流云数仓同速、成本 1/3–1/10（自测、匿名对比、缓存起跑）。
- **让步**：放弃部分数据独立性；单表事务、事务/秒受限；缓存把封闭引擎复杂度请回一部分。
- **地位**：与 Delta PVLDB'20 互为表里——一篇定架构愿景，一篇交存储实现；两者合起来定义了 2020s "开放表格式"赛道的议程。
