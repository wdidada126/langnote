## 一句话总结

生物医学的 Text-to-SQL 难在"问题里藏着领域常识"——比如"全基因组显著性阈值是多少""效应方向""试验分期过滤"。本文发布 BiomedSQL：6.8 万条问题/SQL/答案三元组，建在整合基因-疾病关联、组学因果推断、药物审批记录的 BigQuery 知识库上。实测最强大的 Gemini-3-Pro 仅 58.1%，多步 Agent 达 62.6%，而专家基线是 90.0%——差距巨大，任务远远未解决。

## 0. 给新手的阅读前置（背景知识地图）

- 大问题：生物医学研究者越来越依赖大型结构化数据库做分析。但把"哪些基因与阿尔茨海默显著相关且药物已进入 III 期？"翻译成 SQL，光靠语法翻译不够，还要懂领域隐性标准（阈值、方向性、分期）。
- 为什么难：
  1. 隐性领域推理：问题不直说"p < 5e-8"，模型必须自己知道全基因组显著性阈值；
  2. 知识库模式复杂（多来源整合）；SQL 结构嵌套深。
- 主流做法对比：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 通用 Text-to-SQL 基准 | Spider/BIRD | 通用查询能力 | 缺领域隐性推理 |
| 领域基准 | BiomedSQL（本文） | 生物医学知识库+科学推理 | 填补空白（本文） |
| Agent 增强 | BMSQL（论文自提） | 多步推理/工具调用 | 比 baseline 高但仍远低于专家 |

- 本文属于哪类：基准+评测+一个 Agent 基线三合一。
- 必须先懂的名词：
  - GWAS 显著性阈值：全基因组关联研究中常用的 p 值门槛（约 5e-8，具体口径 🔧）。
  - 执行准确率（execution accuracy）：生成的 SQL 跑出来的结果是否与标准答案一致。
  - 知识库（KB）：整合多来源结构化知识的数据库，本文为 BigQuery 上的统一库。

## 1. 问题背景与动机

- 前人工作：Spider/BIRD 等通用基准推动 Text-to-SQL 大发展，但问题以"字面可译"为主。
- 未解决的问题：
  1. 缺少显式考察科学推理（隐性领域标准）的 Text-to-SQL 基准；
  2. 真实生物医学库（基因-疾病-药物多源整合）上 LLM 能力底数不明。

## 2. 核心方法（基准构造）

- 类比：出题人不是考"把中文翻成 SQL 语法"，而是考"你懂不懂这行的行规"——每道题都要模型先补上没明说的领域常识，再写 SQL。
- 具体做法（构造 → 评测）：
  1. 知识库构建：把基因-疾病关联、组学数据的因果推断、药物审批记录整合进一个 harmonized 的 BigQuery 数据库；
  2. 模板生成：由模板生成 68,000 条（问题, SQL, 答案）三元组；每题要求模型推断领域判据（显著性阈值、效应方向、试验分期过滤等），而非纯句法翻译；
  3. 评测矩阵：开源/闭源 LLM × 多种提示策略 × 多种交互范式（含多步 Agent）。
- 输出：公开基准 + 评测结论 + BMSQL 多步 Agent 基线。

## 3. 变体 / 工程版

- BMSQL：论文提出的定制多步 Agent，是其框架下的工程化尝试（步骤设计 🔧 见原文）。

## 4. 实验结论（概览）

- 对比设置：多类开源/闭源 LLM，跨提示策略与交互范式。
- 结论方向（摘要明确给出）：
  - Gemini-3-Pro：baseline prompting 下 58.1% 执行准确率；
  - BMSQL 多步 Agent：62.6%；
  - 专家基线：90.0%——存在巨大差距，任务远未解决；
  - 🔧 其他模型/策略的逐项数字查原文表格后补。
