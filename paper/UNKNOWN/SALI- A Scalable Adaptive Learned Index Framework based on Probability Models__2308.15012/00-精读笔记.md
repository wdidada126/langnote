## 一句话总结
学习索引虽快，但在多核并发下「撑不大」。SALI 用两套策略（节点自适应演化 + 轻量统计维护）让学习索引在 64 线程下插入吞吐比次优学习索引平均高 2.04 倍，同时查找吞吐追平最强基线。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：传统索引（B+树等）靠固定规则定位数据；「学习索引（Learned Index）」用模型拟合数据分布，直接预测「某个 key 大概在哪」，从而加速查找。但数据会增删改、会倾斜，单线程模型在多核并发下会掉链子。
- 为什么难：并发写入时模型要更新、要加锁，容易成为瓶颈；工作负载倾斜（某些 key 特别热）时固定结构失效；多核下缓存一致性与锁开销放大。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 静态学习索引 | CDF-based (SageDB 思路) | 用累积分布预测位置 | 快但难更新 |
| 细粒度锁学习索引 | LIPP | 写锁细化到节点 | 并发好但扩展性有限 |
| 自适应/可更新 | Updatable Learned Index | 支持动态更新 | 易失衡 |
| 本文 | SALI | 节点演化 + 轻量统计 | 高并发可扩展 |

- 本文属哪类：在 LIPP（细粒度写锁学习索引）之上做「自适应 + 可扩展」增强。
- 2-3 个必懂关键名词：
  - Learned Index（学习索引）：用机器学习模型代替/增强传统索引定位 key。
  - Concurrency / Scalability（并发/可扩展）：多核下吞吐随线程数线性提升的能力。
  - Workload Skew（负载倾斜）：访问分布不均，部分 key 过热。

## 1. 问题背景与动机
- 前人工作简述：学习索引通过拟合数据分布、预测性定位 key，显著提升查找性能；但现有学习索引存在约束，多核存储上可扩展性差。
- 前人缺陷/未解决问题：
  1. 并发场景下扩展性不足，多线程插入/查找易遇瓶颈。
  2. 面对工作负载倾斜时缺乏自适应能力，并发性能下降。
  3. 缺少轻量的统计信息维护手段以进一步提升可扩展性。

## 2. 核心方法
- 最直观类比：传统索引像一本固定目录；SALI 像一本会「随读者习惯自动重排、加书签」的智能目录——热门章节自动扩页、并随时记一笔统计，让大家同时翻书也不卡。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：持续写入/查找的 key 流（多核并发）。
  2. 关键操作（两套策略）：
     - Node-evolving strategies（节点演化策略）：让学习索引适应各种工作负载倾斜，提升并发性能。
     - Lightweight strategy（轻量策略）：在学习索引内部维护统计信息，进一步提升可扩展性。
     - 将上述策略应用到 LIPP（使用细粒度写锁的学习索引结构）上验证。
  3. 输出：高并发、高可扩展的学习索引。
- 形式化要点：核心是通过节点形态自适应演化 + 轻量统计，平衡「模型更新代价」与「并发度」；具体超参见原论文 🔧。
- 理论性质/保证：以系统经验为主，无严格理论保证（🔧 原文未强调）。
