## 一句话总结
当所有人都在用 MongoDB 这类 JSON 文档库时，本文把「被遗忘」的原生 XML 数据库（BaseX、eXist-db、Sedna）重新拉出来，和 JSON 系（MongoDB、CouchDB、Couchbase）在大型 DBLP 语料上做了一次异构复杂 schema 的正面横评——想回答「XML 系在复杂查询上是否还能打」。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：关系库要求先定死表结构；现实里大量数据是半结构化的（XML、JSON、日志、IoT 报文），于是出现了「文档型数据库（Document-Oriented DBMS, DODBMS）」——直接存文档、按文档查询。
- **为什么难**：
  - 文档结构可以嵌套、可以异构（同一集合里文档字段各不相同）；
  - 查询语言差异大：XML 系用标准化的 XPath/XQuery，JSON 系各家用各自的查询方式；
  - 「复杂查询 + 大数据量」下的可扩展性缺少公认的横向比较。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 原生 XML 数据库 | BaseX、eXist-db、Sedna | 以 XML 为存储与查询的一等公民，支持 XQuery/XPath | 标准查询语言表达力强，生态式微 |
| JSON 文档数据库 | MongoDB、CouchDB、Couchbase | 以 JSON/BSON 文档为中心，查询 API 灵活 | 生态繁荣、易上手，标准化查询能力弱 |
| 关系库 + JSON 类型 | PostgreSQL jsonb | 在关系库里存 JSON | 兼顾事务与 SQL，复杂嵌套查询效率受限 |
| 混合/多模数据库 | 多模 NewSQL | 一套引擎支持多种模型 | 通用但往往各项都不极致 |

- **本文属于哪一类**：不是新系统，而是**综述 + 基准评测（benchmark）**，站在「XML vs JSON」这条分界线上做对照。
- **必懂关键名词**：
  - **XQuery / XPath**：XML 的标准化查询/路径语言，能表达相当复杂的导航与构造逻辑。
  - **异构复杂 schema（heterogeneous complex schema）**：同一集合内文档结构差异大、嵌套深——这正是本文 benchmark 刻意选择的难点。
  - **DBLP**：计算机文献书目数据集，常被用作文档型数据库的测试语料（本文使用大规模 DBLP 语料）。

## 1. 问题背景与动机
- 前人工作简述：大数据时代涌现了大量 NoSQL 方案来缓解关系库「结构僵硬」的问题；原生 XML 数据库原本是为操作 XML 数据设计的，后来被重新包装进「NoSQL 文档数据库」这个大类别，随后又被更现代的 JSON 系大面积取代。
- 前人的缺陷 / 未解决问题（逐条）：
  1. **XML 系被过早放弃**：作者认为 XML 方案在「异构集合上的复杂查询」上仍有性能价值，但缺少证据支持这个判断。
  2. **缺少可扩展性与性能的清晰对比**：研究界没有给出「XML 存/查 vs JSON 存/查」在同等条件下的系统性比较。
  3. **没有大数据合规（Big Data-compliant）的基准**：据作者所知，面向这类文档库的大数据基准是空白。
  4. **IoT 场景的现实需求**：来自传感器/执行器的数据有的用 XML、有的用 JSON，选型缺少依据。

## 2. 核心方法
- **最直观类比**：两派都在「用集装箱运货」——XML 派用的是带标准吊具、能精确指定「第几层第几格那个箱子」的重型集装箱（XQuery/XPath），JSON 派用的是装卸更快、但吊具各家自造的轻型箱。本文做的事是：拉一批真实大货（DBLP），让两派在同一条航线上跑一遍计时。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：选定六个文档数据库——XML 派 BaseX、eXist-db、Sedna；JSON 派 MongoDB、CouchDB、Couchbase；以及大规模 DBLP 语料。
  2. **关键操作一：设计异构复杂 schema 的基准**。不采用扁平简单结构，而是刻意构造结构复杂、文档间异构的 schema，贴近真实场景。
  3. **关键操作二：在统一负载上执行查询**。设计一组覆盖不同复杂度的查询，在六个系统上分别执行 🔧 查询清单与负载细节见原论文。
  4. **关键操作三：测可扩展性与性能**。在不同数据规模下观察各系统的表现（可扩展性 scalability）🔧 具体维度查原论文。
  5. **输出**：XML 系与 JSON 系的对比结论 + 一个可复用的文档数据库基准。
- **形式化要点**：核心是「基准设计」——schema 复杂度、数据规模、查询复杂度三者构成实验网格；超参数包括文档数量、查询集合 🔧。
- **理论性质 / 保证**：无理论保证（🔧 论文为实证评测）；贡献在于基准的可复用与结论的可对照。

- 数据集：大规模 DBLP 语料（文献书目数据），采用异构复杂 schema。

## 7. 2026 视角（🔧）
- 产业格局上 JSON 系（MongoDB 等）已是文档数据库事实标准，原生 XML 数据库主要留在出版、档案、医疗交换（如 HL7/CDA）等 XML 标准根深蒂固的垂直领域。
- 但本文提出的「异构复杂 schema + 复杂查询」评测思路并不过时：现代 lakehouse 里的半结构化数据（Parquet + 嵌套类型）同样面临「结构异构 + 复杂导航查询」的挑战。
- 近年趋势是把文档/嵌套数据放进列式湖仓，并用 SQL/DataFrame 而非 XQuery 来导航；XQuery 的表达力优势因此被稀释，但其「标准化、可优化」的思想仍在。本节为趋势性判断 🔧。

## 8. 新手学习路线
- **10 分钟**：读摘要 + 第 0 节，理解「XML 派 vs JSON 派」两组系统各有哪些代表。
- **30 分钟**：装一个 MongoDB 和一个 BaseX，把同一批 DBLP 数据各导入一份，写一条「找出某作者所有合著者」的查询，比较两边写法与耗时。
- **进阶**：精读本文的基准设计（schema 与查询集），尝试把它移植到一个新的文档库上；思考「异构嵌套 + 复杂导航」在今天的列式湖仓上是否仍是痛点。
