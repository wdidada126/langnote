## 一句话总结
PDSP-Bench 是个面向「分布式异构环境下并行流处理」的基准系统：区别于传统只测同构集中式顺序管线，它强调并行算子结构与 ML 负载集成，并在 Apache Flink 上揭示「并行度对性能的非线性、甚至反直觉」效应。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：流处理系统（SPS，如 Flink）要在分布式、异构资源上靠「算子并行」撑住海量实时负载。怎么科学地测它的性能，是选型与调优的前提。
- **为什么难**：现有基准多假设「同构集中式 + 顺序算子管线」，无法刻画真实分布式并行流处理的复杂行为。
- **几类主流解法**：

| 路线 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 顺序管线基准 | 传统 SPS 基准 | 测单管线吞吐 | 简单，但忽略并行/异构 |
| 分布式可扩展基准 | Theodolite、SProBench | 测扩展行为 | 偏宏观扩展 |
| 并行结构 + ML 基准 | 本文 PDSP-Bench | 并行查询 + ML 负载 | 更贴真实分布式 |

- **本文属哪类**：面向「并行 + 分布式异构」流处理的基准系统方向。
- **2-3 个必懂关键名词（直觉解释）**：
  - **Stream Processing System（SPS，流处理系统）**：持续处理数据流的系统（如 Apache Flink）。
  - **operator parallelism（算子并行度）**：把一个算子拆成多份同时跑，以利用多核/多机。
  - **parallel query structure（并行查询结构）**：由并行算子组成的查询拓扑，而非单条顺序管线。

## 1. 问题背景与动机
- **前人工作简述**：现有基准多用「同构集中式环境下的顺序算子管线查询」分析 SPS。
- **前人缺陷/未解决问题（逐条）**：
  1. **忽视并行结构**：没重点测分布式异构下的并行算子。
  2. **忽视 ML 负载**：未集成机器学习模型作为流处理负载。
  3. **缺系统理解**：对「并行度如何利用资源」缺乏系统性基准。

## 2. 核心方法
- **最直观类比**：旧基准像「只测一条单车道公路的时速」；PDSP-Bench 像「在立交桥（多车道、异构车型、还跑着 AI 卡车）上系统测车流」，看加车道到底提速还是堵死。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：真实应用衍生的并行查询结构 + 合成查询 + ML 模型负载。
  2. **关键操作**：在 **Apache Flink** 上用并行查询结构与合成查询做基准；同时允许把 ML 模型集成进 SPS 负载；并比较不同「学习化代价模型」在 PDSP-Bench 生成负载上的训练/推理效率。
  3. **输出**：关于并行度与性能关系的系统性观察（含非线性/反直觉效应）。
- **形式化要点**：核心是「并行结构 + 异构分布式 + ML 集成」的基准设计；超参为并行度、查询结构与模型（具体🔧查原论文）。
- **理论性质/保证**：以实验揭示趋势（非理论保证）。

## 4. 实验结论（概览）
- 对比基线：已有 SPS 基准与学习化代价模型（具体🔧查原论文）。

- 指标：吞吐、资源利用率、代价模型训练/推理效率。
- 结论方向：
  - 揭示不同查询负载下「并行度的非线性、甚至反直觉效应」；
