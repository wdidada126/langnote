## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：ML 流水线 = 关系运算（预处理/后处理数据集）+ 矩阵运算（核心模型）。现有系统多只优化矩阵运算，并假设关系运算的输入已预先物化成矩阵。但现实中关系运算的输入本身就很复杂（由一堆矩阵运算组合而来），需要「直接在大矩阵数据上跑关系查询」的可扩展引擎。
- 为什么难：关系算子（尤其 JOIN）遇上矩阵数据，既要利用矩阵稀疏性，又要控制分布式通信；朴素物化中间矩阵会爆内存/磁盘。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 矩阵专用系统 | 现有 ML 系统 | 只优化矩阵运算 | 忽略关系侧 |
| 关系+矩阵混合 | 本文 MatRel | 在矩阵上直接做关系查询 | 减少物化、提速 |
| 查询优化 | 传统优化器 | 重写计划 | 未针对矩阵稀疏性 |

- 本文属哪类：关系查询处理在矩阵数据上的扩展与优化。
- 2-3 个必懂关键名词：
  - Relational Operator（关系算子）：SELECT/PROJECT/JOIN 等。
  - Algebraic Rewrite（代数重写）：用等价变换把查询计划换成代价更低的。
  - Bloom Join：利用 Bloom filter 减少 JOIN 时的数据传输。

## 1. 问题背景与动机
- 前人工作简述：大规模 ML 普及，流水线含关系+矩阵混合运算；现有系统聚焦矩阵运算，假设关系算子输入已物化为中间矩阵。
- 前人缺陷/未解决问题：
  1. 关系算子的输入在 ML 流水线中可能由复杂矩阵运算组合而成，无法简单预物化。
  2. 缺少能直接在「大矩阵数据」上高效执行关系查询的处理器。

## 2. 核心方法
- 最直观类比：过去是把食材先全部切好装盘（物化成矩阵）再做菜（关系运算）；本文是「边切边做」，并且把切菜和炒菜的工序合并优化，省掉一堆盘子。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：大矩阵数据（内存分布式集群）。
  2. 关键操作：
     - 提出在大矩阵数据上做高效、可扩展关系查询处理的技术。
     - 用代数变换规则（algebraic transformation rules）把执行计划重写成计算代价更低的形式。
     - 分布式查询计划优化器利用 merge 函数的稀疏性诱导（sparsity-inducing）特性，以及 Bloom join 策略来高效评估各类 JOIN。
     - 基于代价模型设计输入矩阵的优化分区方案，最小化通信。
  3. 输出：在 Apache Spark 上原型实现（MatRel），高效执行混合查询。
- 形式化要点：核心是「稀疏性 + 代数重写 + 通信感知分区」协同；具体规则与代价模型见原论文 🔧。
- 理论性质/保证：以系统经验为主（🔧 原文未强调理论保证）。
