## 一句话总结
RocksDB 在 LevelDB 的 LSM 骨架上，把「并发模型、分层策略、元数据协议、键值组织」全面参数化，用「吞吐 / 延迟 / 抖动 / 空间」四把尺子量每个开关——本质不是改 LSM 定义，而是把每个默认值变成按工况可调的函数。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：闪存 + 多核时代，随机小写在 SSD 上虽无寻道，但 FTL 读改写 + GC 擦除放大仍在；如何把 LSM-tree 改成能撑生产级写密集、宽键空间、尾延迟敏感的嵌入式引擎。
- 为什么难：LevelDB 单线程后台、一库一策略、无多列族，在高端多核 SSD 机器上把吞吐钉死在个位数 MB/s；生产负载要求隔离调参与平稳尾延迟。
- 几类主流解法（表格）：

  | 方法 | 代表 | 思路 | 优缺点 |
  |------|------|------|--------|
  | 单策略 LSM | LevelDB / Cassandra | 一套 compaction 策略 | 简单，但工况不匹配则糟 |
  | 全可调 LSM（本文） | RocksDB | universal / level 双轨 + 列族 + rate limiter | 灵活强，但复杂度转嫁运维 |
  | 纯 KV 分离 | WiscKey | 大值出 LSM | 写放大低，但点查多一跳 |

- 本文属于哪一类：架构研讨会报告 / 设计原则演化总账（非实验论文）。
- 2-3 个必懂关键名词：
  - LSM-tree：写先进内存 MemTable，后台合并（compaction）成有序 SST 文件，把随机写摊平成顺序写。
  - universal vs level compaction：size-tiered（写放大低、空间贵）vs leveled（读稳、空间省、写贵）两种合并策略。
  - Column Family（列族）：同进程内多个独立键空间，各自 memtable / 层级 / 策略，但共享 WAL 与 MANIFEST。

## 1. 问题背景与动机
- 前人工作简述：1996 LSM-tree 论文定下「随机写 → 顺序写」骨架与三重指标；2006 Bigtable、2011 LevelDB 把骨架做成两代躯体。
- 前人缺陷 / 未解决问题（逐条）：
  1. 闪存重写仍在：无寻道，但 FTL 内部读改写 + GC 擦除放大，页粒度重写伤害仍在。
  2. LevelDB 天花板：单线程后台、无多列族、写停顿粗暴，撑不住 Facebook 写密集负载。
  3. 缺隔离调参：一库一策略，无法按列族分别优化。
  4. 尾延迟敏感：生产要平稳尾延迟，而非仅均值吞吐。

## 2. 核心方法
- 最直观类比：像「同一台发动机（LSM），把油门、变速箱、冷却全改成可调旋钮」——不再换发动机，而是按路况（负载）调每个参数。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：写密集 KV 负载（对象存储 / 消息 / 图谱索引），键域宽、尾延迟敏感。
  2. 关键操作（四个参数轴）：
     - 并发模型：多线程后台池 + rate limiter + 分级写停顿（slowdown / stop）。
     - 隔离粒度：列族（CF）共享 WAL + MANIFEST，各自 memtable / 层级 / 策略。
     - 分层策略双轨：universal（写放大低）vs level（读稳、空间省）。
     - 键值组织（后续）：覆盖写 / 单删除按住墓碑读放大、BlobDB 按住大值写放大。
  3. 输出：同一 LSM 定义下，吞吐 / 延迟 / 抖动 / 空间四尺可量化的工程谱系。
- 形式化要点：
  - level 写放大 ≈ O(T × L)（T=扇出、L=层数），每层只碰 1+T 个文件；universal 写放大 ≈ O(log_ratio N)。
  - 可串行化来自「版本号 = 对象键」的 CAS 语义（MVCC 极简云原生变体）。
- 理论性质 / 保证：无形式化最优性；属工程权衡，每个特性须以四把尺子量化。

教学示意（level compaction 触发，文档语义，非逐字）：
```
on_write_stall_check:
  if len(L0) >= level0_stop_trigger: PAUSE_WRITES        # 硬闸
  if len(L0) >= level0_slowdown_trigger: SLOW_WRITES
  for n in 1..6:
    if size(Ln) >= target_file_size_base * multiplier^n:
      pick 1 file f in Ln
      D = {g in Ln+1 : overlap(f,g)}                     # |D| ≈ fanout T
      schedule(merge(f, D) -> Ln+1)                       # 每条记录被重写 ~T 次
```

## 4. 实验结论（概览）
- 本文为架构研讨会报告，无严格 benchmark 章节（🔧 通说）；证据为 Facebook 生产负载的逐特性 A/B 与相对 LevelDB 的并发优势。
- 可量度公开事实（文档 / TOS'21 定性）：多线程 compaction 近线性随核数抬升；universal 纯写下写放大显著低于 level；BlobDB 降大值 compaction 流量。
