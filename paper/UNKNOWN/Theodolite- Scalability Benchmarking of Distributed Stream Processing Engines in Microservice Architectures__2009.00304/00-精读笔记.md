## 一句话总结
「这个流处理引擎能不能扛住三倍流量？」这个问题以前靠拍脑袋回答。Theodolite 给出一套方法：先定义微服务形态的流处理用例（use case），再为每个用例找出真正影响扩展性的负载维度（workload dimension），一个「用例 × 维度」设计一个基准；然后用统一框架在不同负载强度和不同实例数下跑，看资源需求怎么随负载增长——并已在 Kafka Streams 与 Flink 上做了 4 个用例、7 个维度的实测。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：分布式流处理引擎（Distributed Stream Processing Engine，DSPE，如 Kafka Streams、Apache Flink）要持续处理大数据流；当流量涨上去时，你需要知道加多少机器才够——这就是可扩展性（scalability）问题。
- 为什么难：
  - 「可扩展性」不是单一指标：数据速率涨、key 数量涨、窗口变大、状态变大……每种涨法对系统的压力完全不同；
  - 流处理常以微服务形式部署，涉及容器编排、网络、存储，测起来变量太多；
  - 不同论文的基准各自为政，无法横向比较。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 吞吐/延迟基准 | Yahoo! Streaming Benchmark 等 | 固定负载测吞吐与延迟 | 简单，但不回答「扩展性」 |
| 领域专用基准 | ESPBench、ShuffleBench、PDSP-Bench | 针对特定场景设计负载 | 场景真实，覆盖面有限 |
| 维度化可扩展性基准（本文） | Theodolite | 按「用例 × 负载维度」拆开测 | 系统性强，设计成本高 |

- 本文属于哪一类：维度化的可扩展性基准方法论——贡献更多在「怎么设计基准」而不是「谁的分数高」。
- 必懂关键名词：
  - 用例（use case）：微服务形态的流处理任务需要完成的业务功能（本文给出 4 个，来自工业物联网 IIoT 数据处理）。
  - 负载维度（workload dimension）：可能影响该用例可扩展性的负载侧变量（如每秒事件数、不同 key 的数量、窗口长度等）；本文识别了 7 个。
  - 处理实例数（number of processing instances）：并行度；基准在不同「负载强度 × 实例数」网格上跑，看资源需求如何演化。

## 1. 问题背景与动机
- 前人工作简述：分布式流处理引擎天生以可扩展性为核心设计目标；围绕吞吐、延迟已有不少基准与评测工作。
- 前人的缺陷 / 未解决问题（逐条）：
  1. 基准不区分负载维度：很多基准只给出「一个总分」，无法说明「是数据量涨导致的瓶颈，还是 key 基数涨导致的瓶颈」。
  2. 忽略微服务部署形态：现代流处理常以微服务部署在云上，已有基准很少覆盖这种部署与弹性伸缩场景。
  3. 缺少「资源需求如何随负载演化」的刻画：只知道某个配置下跑多快，不知道要撑住增长的负载需要多少资源。
  4. 缺少通用执行框架：不同基准各写一套执行脚本，难以复用、难以在云环境中自动化。
  5. 缺少真实场景用例：通用合成负载难以代表工业物联网（IIoT）等真实业务的多样计算特征。

## 2. 核心方法
- 最直观类比：想知道一座桥能承受什么，不能只问「它能承重多少吨」——要分别测「总重量」「车流密度」「风速」「单侧偏载」。Theodolite 就是给流处理系统列这样一张「分项承重表」：每种压力（负载维度）单独加压，看它在哪个维度上先塌。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：一组用微服务实现的流处理用例 + 候选负载维度。
  2. 关键操作一：定义用例。定义微服务形式的流处理必须完成的用例（本文给出 4 个，来源于工业物联网数据处理）。
  3. 关键操作二：识别负载维度。对每个用例，识别可能影响其可扩展性的负载维度（本文共 7 个）。
  4. 关键操作三：一维度一基准。为每个「用例 × 相关负载维度」设计一个基准：固定其它条件，只改变该维度的负载。
  5. 关键操作四：网格化执行。通用框架把用例的 dataflow 架构实现跑在「该维度的不同负载 × 不同处理实例数」的网格上。
  6. 输出：资源需求随负载增长而演化的曲线/结论，用于判断可扩展性。
- 形式化要点：核心是「维度分解」这一实验设计思想；超参数 = 负载维度的取值序列 + 处理实例数的取值序列 🔧 具体维度清单见原论文。
- 理论性质 / 保证：无理论保证（🔧 论文为方法论 + 实证）；价值在于可复现与可推广的实验设计。

## 4. 实验结论（概览）
- 对比基线：Kafka Streams 与 Apache Flink 互为对照，并比较不同的部署选项（deployment options）。
- 数据集 / 负载：4 个来自工业物联网（IIoT）数据处理的用例 + 7 个对应的负载维度。
- 评价指标：可扩展性——核心观察是资源需求如何随负载增长而演化（resource demand evolution），辅以吞吐/延迟等常规指标 🔧 具体指标口径查原论文。
- 结论方向：
  - Theodolite 方法可用：能区分出不同负载维度对可扩展性的不同影响。
  - 两个引擎在不同维度与部署选项下表现各异，不存在统一赢家 🔧。
  - 🔧 摘要未给出任何具体数字（如吞吐、延迟、资源需求曲线），请查原论文图表后补入。
  - 论文的主要目的是评估 Theodolite 方法本身（evaluating the Theodolite method），顺带给出两个引擎的可扩展性实测。

## 5. 开源代码与动手实践
- 仓库地址：https://github.com/cau-se/theodolite
- 语言：Java / Kotlin 为主（Kafka Streams 与 Flink 均基于 JVM），配合容器编排配置（🔧 以 README 为准）
- 典型流程（教学示意，以 README 为准 🔧）：
  ```bash
  # 1) 克隆仓库，按 README 准备 Kubernetes 集群与 Kafka 集群
  git clone https://github.com/cau-se/theodolite
  # 2) 选一个用例（如聚合/窗口计算），固定其它条件，只改「每秒事件数」跑一轮
  # 3) 换一个维度（如 key 基数），再跑一轮，对比两条曲线的形状差异
  # 4) 固定负载，改变处理实例数，看资源需求与延迟的权衡
  ```
  新手最有价值的练习：亲自发现「吞吐不够时，加机器不一定有用」——瓶颈可能在某个特定维度上。
- 许可与资源提醒：索引明确说明「未逐一检查每个仓库的存活、许可、运行环境」，商用前自核 🔧；需要 Kubernetes + Kafka 环境，资源开销不小，建议先用最小规模跑通。

## 7. 2026 视角（🔧）
- 流处理已是实时数仓、实时监控、实时特征的底座；Kafka + Flink 是事实标准组合，可扩展性评测的需求只增不减。
- 云原生（Kubernetes、Serverless）让「弹性伸缩」成为常态，因此「资源需求随负载如何演化」这类曲线比「峰值吞吐」更有决策价值——本文的方法论因此仍然适用。
- 近年趋势是把基准与成本（云账单）挂钩，以及针对 shuffle/状态后端等特定瓶颈做专项基准。本节为趋势性判断 🔧。

## 8. 新手学习路线
- 10 分钟：读摘要 + 第 0 节，记住「4 个用例 × 7 个负载维度 × 2 个引擎」这个骨架。
- 30 分钟：想清楚你自己的流处理任务有哪些「负载维度」（数据速率？key 基数？窗口长度？），把它们列出来——这就是 Theodolite 方法的第一步。
- 进阶：精读论文对 7 个负载维度的定义与选取理由；在自己的 Flink 作业上复现「单维度加压」实验；对比 ShuffleBench 看专项基准与通用维度基准的差异。
