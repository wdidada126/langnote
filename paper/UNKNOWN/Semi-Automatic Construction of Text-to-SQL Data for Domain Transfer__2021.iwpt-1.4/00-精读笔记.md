## 一句话总结
把训练好的语义解析器迁到新领域时，强且便宜的「领域内数据」很关键；本文通过「上下文相关采样（context-dependent sampling）」构造 SQL 查询、并引入「主题（topic）」概念，形成一条覆盖广泛 SQL 空间的半自动 Text-to-SQL 数据集构造流水线，做出的数据在多个维度上可与专家标注媲美，并能提升 SOTA 语义解析器的领域迁移表现。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：Text-to-SQL 数据构造 / 领域迁移——把在某个库上训好的「自然语言 → SQL」模型迁到结构不同的新库时，缺新领域训练数据；手工标贵，本文「半自动」造覆盖广、质量高的新领域数据。
- 为什么难：真实 SQL 查询空间巨大、跨表 join 复杂，以前半自动方法处理不了复杂查询，造出的数据分布偏、迁移效果差。
- 几类主流解法（表格）：

  | 路线 | 代表 | 直觉 |
  |------|------|------|
  | 手工标注 | Spider 人工标注 | 质量高但贵、难扩到新领域 |
  | 模板 / 随机生成 | 早期合成 SQL | 难覆盖复杂真实查询 |
  | 本文：上下文相关采样 + topic | 半自动流水线 | 按库结构采样 SQL，topic 控覆盖与多样 |

- 本文属于哪一类：数据构造方法论文，服务于领域迁移。
- 2-3 个必懂关键名词：
  - domain transfer（领域迁移）：把模型从源库迁到结构 / 内容不同的目标库。
  - context-dependent sampling（上下文相关采样）：造 SQL 时考虑已采样表 / 列上下文，使生成查询结构连贯（能正确 join）。
  - topic（主题）：本文引入的概念，用来控制 / 组织生成数据的覆盖面与多样性。

## 1. 问题背景与动机
- 前人工作简述：已有半自动构造 Text-to-SQL 数据的方法，但处理不了真实 SQL 复杂度。
- 前人缺陷 / 未解决问题（逐条）：
  1. 复杂查询处理不了：旧方法无法生成 / 覆盖现实里多表、复杂条件的 SQL。
  2. 数据覆盖窄：造出的数据集偏窄，迁移增益有限。
  3. 缺质量可控机制：难以保证生成数据与专家标注可比。

## 2. 核心方法
- 最直观类比：像按「菜谱（库结构）+ 主题（今天做什么菜）」生成既合理又多样的菜单（SQL 查询），而不是瞎点菜；生成的菜还能对应自然语言描述。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：目标领域的数据库 schema。
  2. SQL 构造：用 context-dependent sampling 依库结构采样出连贯、可执行的 SQL（正确处理 join / 上下文）。
  3. 引入 topic：用「主题」概念组织采样，覆盖更广 SQL 空间、控制多样性。
  4. 半自动标注：对生成的 SQL 配自然语言问题（部分自动、部分人工校验）。
  - 输出：覆盖广、质量接近专家标注的 Text-to-SQL 数据集，用于领域迁移训练。
- 形式化要点：核心是「上下文相关采样 + topic 组织」的构造流水线；超参数为采样规模、topic 粒度（🔧 以正文为准）。
- 理论性质 / 保证：无形式化保证；靠实验证明与专家标注可比 + 提升迁移。

教学示意（构造流水线，非逐字）：
```
schema = load_target_schema(domain)
for topic in topic_set:                       # topic 控覆盖
    sql = context_dependent_sample(schema)    # 依已采样上下文保证 join 连贯
    nl  = auto_or_human_annotate(sql)         # 半自动配自然语言
    dataset.add(sql, nl, topic)
# 产出：覆盖广、质量近专家标注的 Text-to-SQL 数据
```
