## 一句话总结
把训练好的语义解析器迁到新领域时，强且便宜的"领域内数据"很关键；本文提出通过"上下文相关采样（context-dependent sampling）"构造 SQL 查询、并引入"主题（topic）"概念，形成一条覆盖广泛 SQL 空间的半自动 Text-to-SQL 数据集构造流水线，做出的数据在多个维度上可与专家标注媲美，并能提升 SOTA 语义解析器的领域迁移表现。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：**Text-to-SQL 数据构造 / 领域迁移**——把一个在某个库上训好的"自然语言→SQL"模型，迁到结构不同的新库时，缺新领域的训练数据。手工标贵；本文要"半自动"地造出覆盖广、质量高的新领域数据。
- **为什么难**：真实 SQL 查询空间巨大、跨表 join 复杂，以前的半自动方法处理不了复杂查询，造出的数据分布偏、迁移效果差。
- **几类主流解法**：

| 路线 | 代表 | 直觉 |
|------|------|------|
| 手工标注 | Spider 人工标注 | 质量高但贵、难扩到新领域 |
| 模板/随机生成 | 早期合成 SQL | 难覆盖复杂真实查询 |
| 本文：上下文相关采样 + topic | 半自动流水线 | 按库结构采样 SQL，引入主题保证多样与可控 |

- **本文属哪类**：**数据构造**方法论文，服务于领域迁移。
- **关键名词直觉**：
  - **domain transfer（领域迁移）**：把模型从源库迁到结构/内容不同的目标库。
  - **context-dependent sampling（上下文相关采样）**：造 SQL 时考虑已采样的表/列上下文，使生成的查询在结构上连贯（能正确 join）。
  - **topic（主题）**：本文引入的概念，用来控制/组织生成数据的覆盖面与多样性。

## 1. 问题背景与动机
- 前人工作简述：已有半自动构造 Text-to-SQL 数据的方法，但处理不了真实 SQL 的复杂度。
- 前人缺陷/未解决问题（逐条）：
  1. **复杂查询处理不了**：旧方法无法生成/覆盖现实里多表、复杂条件的 SQL。
  2. **数据覆盖窄**：造出的数据集偏窄，迁移增益有限。
  3. **缺质量可控机制**：难以保证生成数据与专家标注可比。

## 2. 核心方法
- **最直观类比**：像按"菜谱（库结构）+ 主题（今天做什么菜）"来生成一份既合理又多样的菜单（SQL 查询），而不是瞎点菜；生成的菜还能对应自然语言描述。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：目标领域的数据库 schema。
  2. **SQL 构造**：用 context-dependent sampling 依库结构采样出连贯、可执行的 SQL（正确处理 join/上下文）。
  3. **引入 topic**：用"主题"概念组织采样，覆盖更广的 SQL 空间、控制多样性。
  4. **半自动标注**：对生成的 SQL 配自然语言问题（部分自动、部分人工校验）。
  - 输出：覆盖广、质量接近专家标注的 Text-to-SQL 数据集，用于领域迁移训练。
- **形式化要点**：核心是"上下文相关采样 + topic 组织"的构造流水线；超参数为采样规模、topic 粒度（🔧 以正文为准）。
- **理论性质/保证**：无形式化保证；靠实验证明与专家标注可比 + 提升迁移。
