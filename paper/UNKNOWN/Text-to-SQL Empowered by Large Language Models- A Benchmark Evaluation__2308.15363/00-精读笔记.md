## 一句话总结
大模型给 Text-to-SQL 带来了新范式，但缺一个系统的基准来回答「怎么提示最有效、最省 token」。论文先把提示工程拆成三块（问题表示、示例选择、示例组织）做大规模对比，总结出各自利弊，再由此集成为一个新方案 DAIL-SQL，把 Spider 排行榜刷新到 86.6% 执行准确率；同时还系统考察了开源大模型的潜力、监督微调的利弊，并强调要用 token 效率来评价提示方案。

## 0. 给新手的阅读前置（背景知识地图）
- 这个子方向解决什么大问题：用大模型把自然语言问题变成 SQL。范式已从「训练专用解析器」转向「如何提示/微调大模型」。
- 为什么难：
  - 提示的写法千变万化，缺少可比的实验口径；
  - 效果与成本（token 数）要同时考虑；
  - 闭源模型强但贵，开源模型便宜但需要微调，取舍不明。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
|零/少样本提示 | 早期 LLM 用法 | 直接把问题 + schema 丢给模型 | 简单，复杂查询易错 |
| 结构化提示工程 | DAIL-SQL、DIN-SQL | 系统组织问题表示与示例 | 效果显著提升，需要调参 |
| 分解 + 自纠正 | DIN-SQL、MAC-SQL | 把问题拆开、逐步生成并纠错 | 复杂查询强，链路长 |
| 监督微调（SFT） | 本文也考察 | 用标注数据微调开源模型 | 成本低、可私有化；需数据 |
| 智能体协作 | MAC-SQL、MAG-SQL | 多角色协作生成/校验 SQL | 上限高，成本最高 |

- 本文属于哪一类：第二类的基准评测 + 集成方案（并横向覆盖第四类）。
- 必懂关键名词（直觉版）：
  - 问题表示（question representation）：把「问题 + 数据库 schema」怎么塞进提示（是否带外键、是否带注释、格式如何）。
  - 示例选择 / 示例组织（example selection / organization）：少样本示例挑哪些、以什么结构呈现。
  - 执行准确率（execution accuracy）：生成的 SQL 执行后结果是否与标准答案一致（比「SQL 串完全一致」更实用）。
  - token 效率：每道题花多少 token——直接决定线上成本。

## 1. 问题背景与动机
- 前人工作简述：大模型已成为 Text-to-SQL 的新范式，各类提示工程方法层出不穷。
- 前人缺陷 / 未解决问题（逐条）：
  1. 缺少系统的基准：没有统一的评测来回答「有效、高效、经济」三个问题；
  2. 提示工程各要素的利弊不清楚：问题表示、示例选择、示例组织各自怎么影响效果，缺少对比实验；
  3. 开源大模型的潜力未被充分研究：多数工作只测闭源模型；
  4. 监督微调的利弊缺乏系统结论；
  5. 缺少 token 效率这一评价维度：以往只在准确率上比高低。

## 2. 核心方法
- 最直观类比：同样的食材（问题 + 示例 + schema），摆盘方式不同，食客（大模型）给出的结果差异巨大。论文先做了一整套「摆盘对比实验」，再按结论配出一份最优菜单（DAIL-SQL）。
- 具体做法（输入 → 关键操作 → 输出）：
  - 输入：自然语言问题 + 数据库 schema（+ 可选的标注示例）。
  - 关键操作：
    1. 系统对比提示工程的三个维度：问题表示、示例选择、示例组织，并总结各自的 pros and cons；
    2. 基于结论提出 DAIL-SQL：把这些维度上表现最好的做法集成为一个方案；
    3. 考察开源模型：在多种场景下测试开源 LLM，并用监督微调进一步增强；
    4. 引入 token 效率作为与准确率并列的重要评价指标。
  - 输出：SQL（以及一整套可复用的提示工程经验）。
- 形式化要点：DAIL-SQL 在各维度上的具体选择与提示模板 🔧 查原论文。
- 理论性质 / 保证：无理论保证（论文以大规模实证评测为主 🔧）。

## 3. 变体 / 工程版（如有）
- 面向闭源模型：DAIL-SQL 的提示组合；
- 面向开源模型：监督微调（SFT）版本，论文同时讨论了 SFT 的优缺点；
- 实践中常见做法是把 DAIL-SQL 的提示模板套到自家模型上（🔧 以仓库为准）。

## 4. 实验结论（概览）
- 对比基线：此前的提示工程方法（具体清单 🔧 查原论文）与不同的开源/闭源 LLM。
- 数据集：Spider 排行榜（以及若干场景设定）。
- 评价指标：执行准确率（execution accuracy） 与 token 效率。
- 结论方向（摘要给出的已核实数字）：
  - DAIL-SQL 在 Spider 排行榜上取得 86.6% 执行准确率，刷新了当时的最好成绩（sets a new bar）；
  - 开源 LLM 在 Text-to-SQL 上展现出可观潜力，监督微调能进一步增强（同时有得有失）；
  - 在 token 效率这一指标上，不同方法的差距显著，方案选型必须同时考虑成本。
- 🔧 各方法在具体数据集上的准确率与 token 开销请查原论文 Table 后补入。

- 典型流程（教学示意，以 README 为准 🔧）：

  4. 用执行准确率评估，并统计每条请求的 token 消耗；

## 7. 2026 视角（🔧）
- Text-to-SQL 已从「提示工程」演进到「智能体 + 执行反馈 + 后训练」的组合：开源模型经 SFT/RL 后在公开榜上逼近甚至超过闭源模型。
- token 成本与延迟成为系统选型的一等公民：同样的准确率，成本可以差一个数量级。
- 本节为趋势性判断，具体榜首数字 🔧 查当年排行榜。

- 10 分钟：读摘要 + 本笔记 §0、§2，记住「86.6% 执行准确率」与「提示三要素 + token 效率」。
