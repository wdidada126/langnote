## 一句话总结
大模型做 Text-to-SQL 常靠「事后改 SQL」，但大多只是用规则硬修、还缺执行验证。SEA-SQL 用「自适应偏差消除 + 动态执行调整」两套机制，在零样本提示下既纠偏又保证可执行，仅用 GPT-3.5 的成本就逼近 GPT-4 的效果。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：LLM 时代 Text-to-SQL 的主流做法是「先生成 SQL，再后处理修正」。但修正常依赖错误案例分析出规则，且往往没有真正执行验证；同时多数强方法依赖昂贵的 GPT-4 / few-shot。
- 为什么难：LLM 生成有固有偏差；修正规则易过拟合；不执行就不知道 SQL 能不能跑、跑得对不对；GPT-4 成本太高。
- 几类主流解法：

|------|------|------|--------|
| 提示工程 | 早期 GPT 系 | few-shot / CoT | 强但贵 |
| 执行引导 | 自洽/EX 类 | 跑 SQL 验证 | 需执行环境 |
| 本文 | SEA-SQL | 语义增强 + 自适应精炼 | 低成本接近 GPT-4 |

  - Dynamic Execution Adjustment（动态执行调整）：保证修正后的 SQL 真正可执行。

## 1. 问题背景与动机
- 前人工作简述：LLM 推进 Text-to-SQL；常见需求是「对生成的 SQL 做后修正」。多数工作通过分析错误案例造规则消除模型偏差，且缺乏对 SQL 的执行验证；主流技术依赖 GPT-4 与 few-shot，成本高。
- 前人缺陷/未解决问题：
  1. 修正过程多为「规则硬修」，缺乏对 SQL 的执行验证。
  2. 强方法依赖 GPT-4/few-shot，成本昂贵，缺少低成本高效精炼方案。

## 2. 核心方法
- 最直观类比：大模型写的 SQL 像初稿，自带一些「写作习惯偏差」。SEA-SQL 先请一位「语文老师」（自适应偏差消除）改掉套路化错误，再请一位「编译器」（动态执行调整）确保句子真的能运行，全程零样本、不靠昂贵大模型。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：自然语言问题 + 数据库 schema。
  2. 关键操作（SEA-SQL 两件套）：
     - Semantic-enhanced schema（语义增强 schema）：扩充数据库信息以优化 SQL。
     - Adaptive Bias Elimination（自适应偏差消除）：用微调的偏差消除器缓解 LLM 固有偏差。
     - Dynamic Execution Adjustment（动态执行调整）：保证「偏差消除后 SQL」的可执行性。
     - 整体以零样本提示在低成本下提升性能、降低资源消耗。
  3. 输出：修正后、可执行的 SQL。
- 形式化要点：语义增强提供上下文，偏差消除器（微调）纠偏，执行调整闭环验证；超参/训练细节见原论文 🔧。
