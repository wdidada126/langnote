## 一句话总结

把"一条 SQL 会烧多少 CPU 和内存"当成一个纯机器学习问题：只用 SQL 语句文本训练模型，查询还没跑就能估出资源占用，Twitter 用它来调度联邦 SQL 集群里不平衡的 OLAP 负载。

## 0. 给新手的阅读前置（背景知识地图）

这个子方向解决什么大问题？ 数据库/SQL 引擎在真正执行一条查询之前，需要知道"这条查询大概多贵"，才能做调度（把大查询派给哪台机器）、准入控制（会不会打爆集群）、以及防止一条失控的 ad-hoc 查询拖垮全公司分析师的体验。

为什么难？
- 查询的真实代价取决于数据分布、统计信息、执行计划、机器环境——全是运行时才知道的东西。
- 传统做法（基于代价的优化器，CBO）依赖表统计信息和代价公式，在生产环境里对复杂 ad-hoc 查询经常估得不准；而拿到准确统计信息本身在大数据平台上就计算代价高昂（摘要原话：用传统 DBMS 方法计算 SQL 查询的资源占用"计算代价高昂"）。

几类主流解法（简化对照表）：

| 路线 | 代表思路 | 优点 | 缺点 |
|------|---------|------|------|
| 传统 CBO | 统计信息 + 代价公式 | 无需训练、可解释 | 统计信息难维护、对复杂查询失准 |
| 代价模型 + 机器学习特征 | 把计划树特征喂给回归模型 | 更准 | 通常需要拿到执行计划/统计信息 |
| 本文：纯 SQL 文本预测 | 只用历史"SQL 语句 → 实际资源用量"日志训练 | 硬件/软件无关、不在引擎内核算任何东西 | 依赖历史日志质量（🔧 失效模式细节见原论文） |
| 基数估计学习化 | 预测中间结果行数再推代价 | 贴近优化器内部 | 与具体引擎耦合 |

本文属于哪一类？ "纯 SQL 文本预测"路线——这一点是它最鲜明的卖点：模型训练和在线预测都只消费普通 SQL 字符串，因此能跨异构环境复用。

关键名词直觉解释：
- SQL 联邦系统（federated SQL system）：一个"门面"，底下接多个不同引擎/数据中心的集群，用户只提交 SQL，系统决定去哪算。Twitter 的场景横跨本地数据中心与云。
- 查询代价（query cost）：本文具体指 CPU 使用率与内存使用率两项资源占用。
- ad-hoc 查询：分析师随手写的探索性查询，没有固定模式，最难预测、也最容易失控。

## 1. 问题背景与动机

- 前人工作简述：传统 DBMS 用基于统计信息的代价模型估计查询成本；学术界已有把机器学习引入基数估计/代价估计的一系列工作（本仓库 `Are We Ready For Learned Cardinality Estimation-__2012.06743`、`Balsa- Learning a Query Optimizer Without Expert Demonstrations__2201.01441` 等）。
- 前人缺陷 / 本文针对的未解决问题（逐条）：
  1. 统计信息获取太贵：大数据时代用传统 DBMS 方法计算 SQL 查询的资源占用，本身的计算代价就很高。
  2. 与引擎/硬件耦合：现有方法多依赖特定引擎的执行计划、统计信息或硬件 profile，难以推广到异构环境（Twitter 的联邦系统恰好横跨本地与云端、多种后端）。
  3. 需要侵入引擎内核：在引擎内做代价计算会带来额外负担；本文目标是"不在 SQL 引擎内核中做任何计算"。
  4. 业务痛点：Twitter 的 SQL 引擎集群上 OLAP 负载不均衡，需要更好的查询调度与容量手段（包括抢占式扩容），这要求一个"查询还没跑就知道它多贵"的预测服务。

## 2. 核心方法

最直观类比：像快递公司根据"包裹面单上写的内容"预测这单货要占多大车厢——不拆包（不执行查询），只看面单（SQL 文本）+ 历史运单数据（过去同类查询实际占了多少资源）来训练一个估算器。

具体做法（输入 → 关键操作 → 输出）：
- 输入：历史查询请求日志——每条记录是"SQL 语句 + 该查询实际消耗的 CPU/内存"。
- 关键操作：从 SQL 语句本身构造特征并训练代价预测模型（摘要强调训练与在线预测"仅使用普通 SQL 语句"，从而与硬件和软件均无关）。模型具体结构、特征工程细节 🔧 见原论文（arXiv 摘要未展开）。
- 输出：在线阶段输入新查询的 SQL，直接输出预测的 CPU 使用率与内存使用率，供调度与容量决策消费。

部署形态（摘要核实）：作为独立的代价预测服务运行，服务于 Twitter 跨本地数据中心与云数据中心的联邦 SQL 系统，支撑三类用途：改进查询调度、缓解 SQL 引擎集群中不平衡的 OLAP 负载、支持抢占式（pre-emptive）扩容。

理论性质/保证：无理论保证，属工程驱动的机器学习方法；效果以实测精度衡量。

- 指标：CPU 使用率预测精度、内存使用率预测精度（摘要口径）。

## 7. 2026 视角（🔧）

- 生产级"用 ML 预测查询资源/代价"今天已是云数仓与大公司的标配能力（资源调度、查询准入、弹性扩缩容都依赖它）；本文是"纯 SQL 文本、引擎无关"路线的早期代表。
- 近年趋势：序列模型/LLM 直接理解 SQL 文本用于代价与性能预测的探索增多；本文"只用 SQL 字符串即可预测"的设定与今天 LLM 路线高度兼容，可视为其前身思想。（以上为方向性判断，具体系统与文献 🔧 待补。）
