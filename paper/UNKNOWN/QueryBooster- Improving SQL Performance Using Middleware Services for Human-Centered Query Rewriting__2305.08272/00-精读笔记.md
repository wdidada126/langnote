## 一句话总结
QueryBooster 是一个架在「应用 ↔ 数据库」之间的中间件：它用一套好写又好懂的规则语言 VarSQL 让用户表达「我想怎么改这条查询」，还能从「原查询 + 改写后查询」的例子中自动归纳出重写规则并推荐高质量规则，从而在应用层和数据库层都是黑盒时，靠人的领域知识把 SQL 跑得更快。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：在真实系统里，发往数据库的 SQL 往往由应用框架生成，开发者和 DBA 看得到「这条查询慢」，却改不了应用代码、也改不了数据库内核——两头都是黑盒。查询重写（把等价但更慢的 SQL 换成更快的等价 SQL）是经典提速手段，但「怎么让人方便地说出重写意图」是痛点。
- **为什么难**：已有重写方案要么太底层（要写优化器规则），要么不够灵活（不能结合领域知识），用户没有足够自由度表达「按我的数据特征这么改」。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 优化器内重写 | 数据库自带 | 基于代价自动改写 | 用户无法注入领域知识 |
| 中间件改写 | **QueryBooster** | 用户写规则/示例 | 灵活、人本，但需人参与 |
| 学习型重写 | learned rewriter | 模型学改写 | 自动化但难解释 |

- **本文属哪类**：中间件改写，强调「人本（human-centered）」——人定规则，系统帮忙归纳与推荐。
- **2-3 个必懂关键名词**：
  - **查询重写（query rewriting）**：把一条 SQL 变成结果相同但执行更快的另一条 SQL。
  - **VarSQL**：本文提出的规则语言，表达「在满足某模式时，把查询改成某种形式」。
  - **等价（equivalent）**：改写前后返回结果集一致，这是重写正确的前提。

## 1. 问题背景与动机
- 前人工作简述：查询重写被证明能提性能，但既有方案不给人足够自由度表达重写需求。
- 前人缺陷/未解决问题（逐条）：
  1. **自由度不足**：用户难以按自己的数据与领域知识定制重写。
  2. **应用/数据库双黑盒**：在很多系统里用户既不能改应用也不能改内核，只能在中间插手。
  3. **规则难写**：即便有规则语言，写高质量规则本身门槛高。

## 2. 核心方法
- **最直观类比**：QueryBooster 像「快递中转站」，包裹（SQL）经过时被按站长（你）写的便签（VarSQL 规则）重新打包，但站长不用每次手写便签——给几个「原样 vs 理想样」的例子，中转站自动总结出便签并推荐最好的。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：应用发来的 SQL（流经中间件）。
  2. **规则表达**：用户用 VarSQL 写重写规则，或用「原查询 + 改写查询」示例。
  3. **规则归纳与推荐**：系统把示例泛化为重写规则，并推荐高质量规则。
  4. **输出**：改写后的等价 SQL 发往数据库执行，端到端更快。
- **形式化要点**：核心是 VarSQL 规则语言（模式匹配 + 重写模板）；超参数为规则质量评估（具体指标 🔧 见论文）。
- **理论性质/保证**：保证改写等价性由用户规则定义；性能提升来自端到端实测。
