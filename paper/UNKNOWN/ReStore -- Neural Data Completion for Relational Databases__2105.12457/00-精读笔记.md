## 一句话总结
OLAP 分析默认表是完整的，但真实世界常常缺元组（缺整行数据），此时直接跑聚合查询（SUM/AVG/COUNT）的结果会显著偏离真实值；以前只能靠人手动补数据，还得有统计功底判断「补够了没有」。ReStore 提出一类「模式结构化（schema-structured）」的神经补全模型，自动合成出与缺失元组相似的合成数据，再用补全后的表回答查询，在真实数据上把聚合查询的相对误差最多降低了 390%。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：分析型处理（OLAP）假设「所有表的数据都是齐的」。现实里数据缺失很常见——某些分区没采集、某段时间日志丢了、某些来源未接入。缺失的不只是单元格（NULL），还可能是整行元组（missing tuples）。这类缺失最阴险：查询不会报错，只是悄悄给出一个偏差巨大的数。
- 为什么难：
  1. 缺失是「看不见」的：你无法统计「有多少行本该存在却不在这」，因为它不在表里。
  2. 关系结构复杂：关系库由多张通过外键相连的表组成，缺失可能发生在任意一张表，影响会沿着连接传播。
  3. 人工补全成本高：需要领域专家判断缺什么、补多少。
  4. 补全的判定需要统计功底：判断「数据集现在是否真的完整」本身就是统计学问题。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 直接用不完整数据查询 | 现状做法 | 缺多少算多少 | 零成本但聚合结果偏差大 |
| 人工补全 | 领域专家 | 人判断并补齐数据源 | 准但贵、慢，不可扩展 |
| 经典统计插补 | 均值/回归/多重插补 | 用统计量填补 | 只适合单元缺失，难处理整行缺失与关系结构 |
| 生成模型合成 | GAN 类表格模型 | 学分布后采样新行 | 能生成整行，但通常只针对单表 |
| 模式结构化神经补全（本文） | ReStore | 让生成模型理解整个库的 schema 与外键关系 | 复杂，需按库训练 🔧 |

- 本文属于哪一类：最后一类——关系感知的神经数据补全，把「整个关系库的 schema 结构」显式纳入模型设计。
- 必懂关键名词：
  - missing tuples（缺失元组）：本该存在但没有出现在表里的整行记录，区别于某格为空的 NULL。
  - aggregate query（聚合查询）：`SELECT SUM(x) / AVG(x) / COUNT(*)` 这类把多行压成一个数的查询；行数一旦少，聚合值就系统性偏低/偏高。
  - relative error（相对误差）：`|估计值 - 真值| / 真值`，本文用它衡量「用不完整数据直接查」有多不准，以及补全后改善多少。

## 1. 问题背景与动机
- 前人工作简述：经典 OLAP 方法（含各类近似查询处理 AQP 与采样方法）普遍假设各表数据完整；缺失值处理研究多集中在单元格层面的插补（imputation），少有针对关系库中「整行缺失」且保持多表关系的自动方案。
- 前人缺陷 / 未解决问题（逐条）：
  1. 经典方法在不完整表上失效：一旦存在缺失元组，SQL 聚合查询的结果可能与在完整数据集上算出的结果显著不同。
  2. 只能人工补全：当时应对缺失数据的唯一办法是人工补数据集，工作量巨大。
  3. 需要统计技能判断完整性：判断一个数据集是否真的补完整，本身需要良好的统计学训练，普通工程师难以胜任。
  4. 缺少自动化：整体上缺少「自动合成缺失元组、且尊重关系库结构」的端到端方案。

## 2. 核心方法
- 最直观类比：一份人口普查表少登记了几个街区。直接统计，人均收入就会偏高/偏低。以前的办法是派人挨家挨户回访（人工补）；ReStore 相当于训练了一个「熟悉这个城市结构的模拟器」，让它按已有的街区规律补出缺失街区的居民记录（合成元组），再用补全后的表去统计——结果自然更接近真相。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：一个存在缺失元组的关系数据库（多张表 + 外键关系）。
  2. 关键操作：
     - 提出一类新的（神经）模式结构化补全模型（neural schema-structured completion models）——模型设计显式地以整个库的 schema 结构（表、列、外键）为骨架，而不是把每张表孤立看待。
     - 用这类模型合成（synthesize）与缺失元组相似的合成数据，即生成「看起来像那些缺失行」的元组。
     - 用补全后的数据回答聚合查询，从而降低误差。
  3. 输出：补全后的关系数据（以及在其上更准确的聚合查询结果）。
- 形式化要点：核心贡献是「模型类别」——schema-structured completion model；具体的网络结构、按库训练方式、合成样本量如何确定、误差如何估计 🔧 需查原论文正文。
- 理论性质 / 保证：论文未给出误差的理论界（🔧），以实验验证为主。

## 7. 2026 视角（🔧）
- 「用生成模型补数据」在 2026 年已相当常见，但用在数据库内核里服务聚合查询仍是相对小众而有价值的方向；随着企业数据湖里「可信完整性」问题凸显（数据源接入不全、埋点丢失），这类「补得对不对」的能力会变得更重要。
- 与之相邻且更工业化的方向是数据可观测性 / 数据契约：与其事后补全，不如事前检测缺失。两者可视为互补。
- 本节为趋势性判断 🔧，具体工业落地形态请以当年现状为准。
