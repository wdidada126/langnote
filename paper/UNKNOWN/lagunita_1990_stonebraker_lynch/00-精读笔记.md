## 一句话总结
Stonebraker & Lynch 在 1990 年断言「第三代单体通用 DBMS」撑不住下一代应用（TB 级、大对象、类型扩展、长事务、异构联邦），主张把数据库拆成可组合、按域定制的模块——「one-size-fits-all is dead」的最早系统表述，是后来 C-Store / 列存 / NewSQL / Lakehouse 的预言清单。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：当「一个通用关系数据库」既装不下新数据形态（视频、数组、基因组），又扛不住新规模（TB→PB）与新负载（长事务、ML）时，数据库架构该往哪走。
- 为什么难：单体系统牵一发而动全身，任何算法（索引、恢复、类型、规则）都要为「通用」妥协，无法为特定领域极致优化。
- 几类主流解法（表格）：

  | 方法 | 代表 | 思路 | 优缺点 |
  |------|------|------|--------|
  | 单体通用 DBMS | 第三代关系系统 | 一套引擎服务所有 | 易用但天花板低 |
  | 模块化 / 可定制（本文） | EXODUS / OpenODB / Postgres | 部件可替换、按域定制 | 灵活但复杂度高 |
  | 开放湖仓（后世） | Lakehouse / Iceberg | 开放格式 + 元数据层 | 本文预言的延续 |

- 本文属于哪一类：研究议程 / 立场文（务虚的「路线图」），不是系统论文。
- 2-3 个必懂关键名词：
  - monolithic / general-purpose DBMS：单体式通用数据库，本文批判对象。
  - one-size-fits-all is dead：一刀切架构已死，按域定制才是未来（本文精神）。
  - mediator（中介器）：跨异构库做语义集成的设想，是后来数据集成 / 数据虚拟化的前身。

## 1. 问题背景与动机
- 前人工作简述：1988 年 Laguna Beach 工作坊汇聚「DBMS 研究是否终结」的焦虑；当时 SQL 关系系统（Oracle / DB2 / Informix）商业化起飞，一派认为「数据库已解决」。
- 前人缺陷 / 未解决问题（逐条，即报告列的「七堵墙」）：
  1. 规模墙：TB 级表建索引 / 备份 / 恢复以「天」计，既有架构扩不上去。
  2. 数据形态墙：为「递小记录」设计，大对象 / 数组无对应存取结构。
  3. 类型墙：静态类型 + 持久数据 + 模式演化的组合未解决。
  4. 规则墙：触发器 / 规则必须进内核，而非外挂专家系统。
  5. 事务模型墙：传统假设「短事务」，长事务 / 版本 / 时态模型缺失。
  6. 空间 / 多级存储墙：内存–磁盘–归档三级下，优化器要感知归档超长延迟。
  7. 并行墙：TB 扫描可能「周一提交、周四出结果」，需重构成可近线性加速。

## 2. 核心方法
- 最直观类比：像「一个万能瑞士军刀用不顺手，于是换成可换头工具箱」——锯、钻、刀各用最合适的头，而不是拿同一把刀去锯木头。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：对「下一代应用」的需求清单（科学数据、数据挖掘、多媒体、长事务、异构联邦）。
  2. 关键主张：
     - 拆掉单体：存储管理、访问方法、事务 / 锁、类型系统、规则引擎、优化器各自可替换。
     - 按应用域定制：每个领域（NASA 影像、基因组、零售流水）用不同模块组合。
     - 全球异构互联：用 mediator 做语义集成，为「1000 / 10000 站点」重造分布式算法。
  3. 输出：一份「改革 + 综合」的研究议程，指引此后十年数据库方向。
- 形式化要点：本文是立场文，无算法 / 形式化；其力量在「问题清单 + 案例 + 资助呼吁」的论证结构。
- 理论性质 / 保证：无；属于望远镜式预言，不是施工图。

## 3. 变体 / 工程版（如有）

## 4. 实验结论（概览）
- 本文无实验；证据为行业观察与案例清单（NASA 10^16 字节影像、人类基因组、零售数据挖掘等）。
- 结论方向：既有单体 DBMS 不足以承载 2000 年后的应用，研究不应宣布「已解决」。

## 7. 2026 视角（🔧）
- 「one-size-fits-all is dead」从宣言变成教科书共识：列存、向量化、NewSQL、Lakehouse、专用向量库各行其道。
- 但关系模型未被「复杂对象」取代，而是自我扩展（JSON / 数组进了 PostgreSQL）；全球统一库以 Web / 云形态、而非 DBMS 联邦形态实现。
- 本节为趋势判断（🔧 具体生态以当年为准）。
