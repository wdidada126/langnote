## 一句话总结
探索式分析（用户边看边想、不知要查啥）需要数据库「猜下一步要取哪些块」来预取（prefetch）減少等待。现有预取器只适用于导航式或只靠逻辑地址、不懂数据语义。SeLeP 用「被访问块内数据值的编码」做语义预取，把预取建模成时间序列预测，用 encoder-decoder LSTM 学访问模式，在真实探索负载上命中率最高提升 40%、I/O 时间最高降 45%，平均达 95% 命中率、80% I/O 缩减。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：数据库要「交互流畅」，就得在用户发查询前把可能要的数据块提前取进内存（prefetching），避免卡 I/O。
- 为什么难：探索式负载「用户自己都不知道下一步看什么」，没有先验可调优；数据量大时地址空间爆炸；频繁共访问（co-access）模式难预测。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 导航式预取 | 传统预取器 | 动作有限、按路径 | 限导航场景 |
| 逻辑地址预取 | SQL 负载预取 | 靠块地址 | 不懂语义、大库失效 |
| 语义预取（本文） | SeLeP | 编码块内数据值 | 懂语义、适应两类负载 |

- 本文属哪类：基于学习的语义预取（机器学习 + 存储/缓冲）。
- 关键名词直觉：
  - prefetching（预取）：提前把可能用到的数据块载入内存/缓存。
  - exploratory workload（探索式负载）：用户试探性分析，查询路径不确定。
  - hit ratio（命中率）：预取的数据后来真被用到的比例。
  - encoder-decoder LSTM：一种序列模型，适合把「访问历史」当时间序列预测「下一步访问」。

## 1. 问题背景与动机
- 前人工作简述：传统预取提升交互性；SOTA 预取器专为「导航式（navigational）」负载设计（动作数有限）；SQL 负载预取器主要依赖数据逻辑地址而非语义。
- 前人缺陷/未解决问题（逐条）：
  1. 只覆盖导航式：SOTA 预取器仅适合动作有限的导航场景。
  2. SQL 预取不懂语义：靠逻辑地址，在库大（地址空间广）或频繁共访问时预测复杂模式失败。
  3. 探索式无先验：探索负载缺乏 a priori 知识来调优系统。

## 2. 核心方法
- 最直观类比：不像「按门牌号（地址）猜邻居会不会来」，而是「看包裹里装了什么（数据值）」来判断下次会不会一起被取——SeLeP 通过块里数据的语义来预判访问。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：被访问数据块及其内部的数据值。
  2. 关键操作：编码块内数据值，把预取任务建模为时间序列预测；用 encoder-decoder LSTM 学数据访问模式，对两类负载（导航式 + SQL）都做预取决策。
  3. 输出：对未来会被访问的数据块的预测（预取目标）。
- 形式化要点：核心是「语义编码 + 序列预测」替代「逻辑地址关联」；具体编码方式与 LSTM 结构 🔧 查原论文。
- 理论性质/保证：无形式化保证；以实证（命中率/I/O 缩减）为主。

- 对比基线：SOTA 预取器（导航式 + SQL 地址式）。
- 数据集：真实世界探索式负载（real-life exploratory workloads）。
- 指标：hit ratio（命中率）、I/O time（I/O 时间）。
- 结论方向（摘要给出的已核实数字）：
