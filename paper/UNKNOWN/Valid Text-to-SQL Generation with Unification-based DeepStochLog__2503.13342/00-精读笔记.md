## 一句话总结
用大语言模型把自然语言翻译成 SQL 时，因为没有硬性的语法与 schema 约束，偶尔会生成**不可执行的非法查询**，限制了它在真实场景中的可用性。本文提出一个**神经符号（neurosymbolic）框架**：用**基于合一（unification-based）的定子句文法（Definite Clause Grammar, DCG）**把 SQL 的语法约束和数据库 schema 约束编码进去，从而**保证生成的查询一定合法**；同时建立与语言模型的**双向接口**，继续借用 LLM 的自然语言理解能力。在 SQL 文法的一个子集上的评测显示：**输出的查询全部合法**，并且大幅提升了原模型的合法性、执行准确率与与标准答案的对齐程度。

- **三个必懂的关键名词**：
  1. **合一（unification）**：来自逻辑编程（Prolog）的概念——把两个带变量的项匹配起来，并在这个过程中给变量赋值。比如把 `SELECT ?x` 和 `SELECT city` 匹配得到 `?x = city`。它天然能表达「这里填列名」这类带依赖的约束。
  2. **定子句文法（Definite Clause Grammar, DCG）**：用逻辑规则描述语法的一种方式；本文用它来描述「什么样的 SQL 是合法的」。
  3. **神经符号（neurosymbolic）**：神经网络（负责感知/理解，如 LLM 读懂问题） + 符号系统（负责精确推理/约束，如文法）的混合范式。

## 1. 问题背景与动机
- **前人工作简述**：随着 LLM 能力增强，把自然语言翻译成 SQL 主要靠 LLM 的生成能力。这条路线强大、灵活、零样本即可用。
- **前人缺陷 / 未解决问题（逐条）**：
  1. **缺少硬性语法/schema 约束**：LLM 生成 SQL 时没有硬约束，会**偶尔产出不可执行的非法查询（invalid queries）**。
  2. **这些失败限制了真实场景的可用性**：不可执行的查询直接打断业务链路，用户对系统失去信任。
  3. **事后重试成本高**：靠「生成—验错—重试」可以缓解，但仍有失败可能，且带来额外延迟。
  4. **受限解码的表达力不足**：简单 token 级约束难以表达需要**跨远位置的依赖**（例如某个子查询内部必须自洽）。
  5. **没有充分利用 LLM 的理解能力**：纯符号系统在语言理解上很弱；需要把两者优势真正结合起来。

## 2. 核心方法
- **最直观类比**：LLM 像一个很会说外语但不讲规矩的天才；DCG 文法像一本严格的护照查验手册。**神经符号框架**就是让这位天才在「查验手册」的监督下开口：每次要说出一个词，手册先检查合不合法；通过合一机制，手册还能记牢「刚才定下的名字」并在后面一致地引用它。于是既保留了天才的语言理解，又杜绝了「胡说 SQL」。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：自然语言问题 + 目标数据库的 schema（表/列结构）+ 一个 LLM。
  2. **关键操作一：用文法编码约束**。提出神经符号框架：使用 **unification-based definite clause grammars（基于合一的定子句文法）** 来同时施加上 **SQL 语法约束（syntax constraints）** 与 **数据库 schema 约束（schema constraints）**。
  3. **关键操作二：保证合法**。正因为所有生成都必须落在文法允许的推导之内，框架能 **guarantee the generation of valid queries（保证生成合法查询）**。
  4. **关键操作三：双向接口**。建立一个**与语言模型的双向接口（bi-directional interface）**，一方面把 LLM 的概率/表示拉进文法推导，另一方面把 LLM 的自然语言理解能力用起来。
  5. **输出**：一条对该 schema 合法且可执行的 SQL 查询。
- **形式化要点**：
  - 选择了 **DeepStochLog** 作为神经符号载体（随机化/概率化的 Definite Clause Grammar，能与神经网络联合训练与推断）；具体概率参数化与推断算法 🔧 见与方法相关的原论文正文。
  - 核心设计目标是「**合法性硬约束**优先于自由生成」。
- **理论性质 / 保证**：框架在**文法覆盖范围内保证生成的 SQL 一定合法**；论文明确评测结果「all our output queries are valid」。注意这是相对于**文法所覆盖的 SQL 子集**而言，超出该子集的查询不在保证范围内。

## 7. 2026 视角（🔧）
- 「能不能保证可执行」是 Text-to-SQL 落地企业的第一道门槛。今天的常见做法是三选一或叠加：**语法层面的 constrained decoding**、**生成后校验 + 自纠**，以及本文代表的**形式文法硬约束**。
- 本文的价值在于提供了一条**可证明而非经验性**的路线：合法性来自文法的推导线，不用靠「试试看」。代价是要写文法、且支持范围受文法覆盖限制。
- 近年趋势：把约束解码下沉到推理引擎（ vLLM 类的 grammar/sampling 约束）、把自纠做成强化学习，以及把 schema 校验做成「执行前的静态检查」步骤。本节含趋势判断，最新工程实践 🔧 需查当年资料。
