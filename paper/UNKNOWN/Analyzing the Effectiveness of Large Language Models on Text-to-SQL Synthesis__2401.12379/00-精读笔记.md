## 0. 给新手的阅读前置

读这篇前，建议先备齐这些概念：

- **Text-to-SQL / 程序合成**：给模型「自然语言问题 + 数据库 schema」，让它输出正确的 SQL `SELECT` 查询。本仓库同批的 `AMBROSIA`、`Schema Linking (2102.01847)` 都是这个任务。
- **Spider 数据集**：跨域 Text-to-SQL 的权威基准，模型要在没见过的数据库上泛化。本文所有实验都基于 Spider。
- **微调（fine-tuning）vs. 提示（prompting）**：① 是「改模型权重」——在 Spider 上继续训练一个开源模型；② 是「不改权重、只写提示词」——把示例塞进上下文（Few-shot）或让另一个模型帮忙改错（纠错）。
- **QLoRa**：一种低显存微调技术，能在消费级/单卡上微调大模型（15B 级别），本篇用它来微调 WizardCoder。
- **执行准确率（execution accuracy）**：不只看 SQL 字符串是否一致，而是把生成的 SQL 在数据库上跑，结果集和正确答案一致才算对——比字符串匹配更公平。
- **Few-shot / Zero-shot**：Few-shot = 在提示里给几个「问题→SQL」范例；Zero-shot = 不给范例，直接让模型做。

读完你会清楚：2024 年初，「自己微调一个小开源模型」和「直接调大厂 API」这两条路，在 Text-to-SQL 上差了多少，以及错都错在哪。

## 1. 问题背景与动机

大语言模型（LLM）出现后，Text-to-SQL 这条「程序合成」老任务被重新点燃。本文的目标不是提出一个新模型，而是**做一次扎实的「有效性分析（effectiveness analysis）」**：把几种有代表性的 LLM 用法摆到同一张桌子上，比较它们在 Spider 上的真实表现，并**找出它们到底为什么失败**。

作者关心的核心问题是：
- 本地开源模型微调后能到什么水平？
- 直接用商用大模型（GPT 系列）+ 提示/纠错策略能到什么水平？
- 那些**没生成对的查询**，错误能不能被系统地归类？归类后能不能告诉我们「LLM 程序合成还差在哪、该往哪改」？

这种「既报数字、又做错误 taxonomy（分类法）」的写法，对工程落地特别实用——它告诉你上 LLM 之前要先防哪几类坑。

## 2. 核心方法

论文沿两条主线展开：

### 路线一：本地开源模型微调
- 基座模型：WizardLM 出品的 **WizardCoder-15B**（一个面向代码的大模型）。
- 方法：在 Spider 训练集上做 **QLoRa 微调**，让模型学会「输入 (问题 + schema) → 输出 SELECT 查询」。
- 结果：生成查询的**执行准确率最高到 61%**。

### 路线二：商用大模型 + 提示/纠错
- 第一棒：用 **gpt-3.5-turbo-16k** 做 **Few-shot**（提示里放若干范例）生成初版 SQL。
- 第二棒：用 **gpt-4-turbo** 做 **Zero-shot 错误纠正**（error correction）——把第一棒可能写错的查询交给更强的模型改一遍。
- 结果：执行准确率最高到 **82.1%**。

### 错误分类法（本文最有价值的部分之一）
作者把所有**错误查询**归纳成 **7 类**，覆盖绝大多数失败案例：

1. **选错列 / 列顺序错**（selecting the wrong columns or wrong order of columns）
2. **按错列分组**（grouping by the wrong column）
3. **条件里的值预测错**（predicting the wrong values in conditionals）
4. **用了和真值不同的聚合函数**（using different aggregates than the ground truth）
5. **JOIN 子句多余或过少**（extra or too few JOIN clauses）
6. **Spider 数据集自身的不一致**（inconsistencies in the Spider dataset）
7. **查询结构完全错误**（completely incorrect query structure）

作者指出：几乎（if not all）所有错误都能落进这 7 类，这对理解 LLM 程序合成的故障点、指明改进方向很有启发。

## 3. 变体 / 工程版

本文是分析性工作，提出的是「方法组合」而非单一新模型。可看作两条工程路线的早期范本：

- **微调路线范本**：QLoRa + 开源代码大模型（WizardCoder-15B），对应今天大量「本地小模型 Text-to-SQL」工作的起点。
- **API 路线范本**：Few-shot 生成 + 更强模型 Zero-shot 纠错的两段式流水线。这个「先生成、再纠正」的思想在后续很多工作里被发扬（例如本仓库 `DIN-SQL` 的分解+自纠错、`Text-to-SQL Error Correction with Language Models of Code`、`MAGIC` 的自纠错指南等）。
- 配套开源：`cuplv/text-to-sql-wizardcoder` 即本文微调/实验代码入口。

## 4. 实验结论（概览）

- **本地微调开源模型（WizardCoder-15B + QLoRa）**：Spider 执行准确率约 **61%**（上限）。说明 2024 年初，仅靠中等规模开源模型微调，离「好用」仍有明显差距。
- **商用 API 组合（gpt-3.5-turbo-16k Few-shot + gpt-4-turbo Zero-shot 纠错）**：执行准确率约 **82.1%**（上限）。比本地路线高出约 20 个点，凸显当时「模型规模 + 纠错」的红利。
- **错误可系统性归类**：失败几乎都能归入上述 7 类，其中「列/聚合/JOIN/条件值」类错误是 LLM 程序合成的主要短板，外加一部分源于 Spider 数据自身不一致。
