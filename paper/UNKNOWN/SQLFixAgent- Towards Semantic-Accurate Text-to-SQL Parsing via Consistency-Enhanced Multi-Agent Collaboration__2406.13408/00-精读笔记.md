## 一句话总结
微调后的 LLM 能写出语法正确的 SQL，却常犯「语义不对」的错（答非所问）；SQLFixAgent 用一套「一致性增强的多智能体」来检测并修复错误 SQL——核心 agent SQLRefiner 配合 SQLReviewer（橡皮鸭调试找语义错配）和 QueryCrafter（生成候选修复），借助相似修复检索与失败记忆反思选出最佳 SQL；在 5 个基准上，Bird 执行准确率提升超 3%，且 token 效率更高。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：Text-to-SQL 不仅要「语法对」，更要「语义对」（真正回答用户问题）；微调 LLM 常语法过关但语义跑偏。
- **为什么难**：语义错配隐蔽，模型自己难发现；单纯重写容易原地打转。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 直接生成 | 微调 LLM | prompt→SQL | 语法好、语义易错 |
| 自校正 | 各类 self-repair | 再生成修正 | 易循环 |
| 多智能体修复 | 本文 SQLFixAgent | 角色分工+记忆 | 稳、效率高 |

- **本文属哪类**：多智能体协作的「语义纠错/修复」框架。
- **2-3 个必懂关键名词**：
  - **Semantic Accuracy（语义准确率）**：SQL 是否真正对应了用户问题的语义，而非仅语法正确。
  - **Rubber Duck Debugging（橡皮鸭调试）**：向「鸭子」逐步讲解代码以自我发现问题，本文用于让 agent 找语义错配。
  - **Failure Memory（失败记忆）**：记录过去修复失败案例以避免重蹈，提升选择质量。

## 1. 问题背景与动机
- 前人工作简述：微调 LLM 在 Text-to-SQL 上能生成语法合法 SQL，但语义准确性不足，影响可用性与体验。
- 前人缺陷/未解决问题（逐条）：
  1. **语义不准确**：生成的 SQL 常语法对但语义错（答非所问）。
  2. **难自检**：模型缺乏可靠机制发现语义错配。

## 2. 核心方法
- **最直观类比**：写完 SQL 后，不是自己闷头改，而是拉一个「审查小组」——有人专门挑刺（SQLReviewer 当橡皮鸭）、有人出改稿（QueryCrafter）、有人拍板选最优（SQLRefiner），还翻旧账避免再犯（失败记忆）。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：疑似有语义错误的 SQL + 用户问题 + schema。
  2. **SQLReviewer（辅助）**：用橡皮鸭调试法识别 SQL 与问题的潜在语义错配。
  3. **QueryCrafter（辅助）**：若发现错误，用微调 SQLTool 生成多个候选修复 SQL。
  4. **SQLRefiner（核心）**：借助相似修复检索与失败记忆反思，从候选中选最合适的最终修复。
  - 输出：语义更准确的修复后 SQL。
- **形式化要点**：核心是「三 agent 协作 + 一致性增强（检索/记忆）」；超参在候选数与检索/记忆机制（🔧 细节见论文）。
- **理论性质/保证**：无理论最优性保证；实证在 Bird 上 +>3% 执行准确率且 token 更高效。
