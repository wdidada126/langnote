## 一句话总结
Bigtable 用「稀疏有序多维映射 + 区间分片（tablet）+ LSM 三层存储栈」在廉价机器集群上提供 PB 级、低延迟、schema 可动态演化的半结构化存储；它把持久化外包给 GFS、把协调外包给 Chubby，自身只做「有序映射的分片服务」，成为 NoSQL 与云存储的原型机。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：PB 级、数千廉价机、低延迟随机读写、列经常变动的「表」，传统关系数据库与纯文件系统都覆盖不了。
- 为什么难：既要水平扩展到几千台机器，又要在廉价的随机 I/O 上拿到低延迟；还要让 schema 每周都能变。
- 几类主流解法：

| 方法 | 代表 | 思路 | 取舍 |
|------|------|------|------|
| 关系型分库分表 | 传统 RDBMS + 中间件 | 强 schema、SQL、事务 | 扩展靠人肉分片、运维重 |
| 纯键值 + 顺序文件 | GFS | 大文件顺序读写 | 随机点查/可变记录无能为力 |
| 稀疏有序映射 + 区间分片 | Bigtable | 行有序、列族动态、tablet 自动分裂 | 放弃跨行事务、依赖 Chubby |
| 最终一致 KV | Dynamo | 始终可写、无中心协调 | 放弃强一致 |

- 本文属哪一类：稀疏有序映射 + 区间 tablet + LSM，典型「写优化分布式存储」。
- 2-3 个必懂关键名词：
  - tablet：行的连续区间，是负载均衡与调度的最小单元（类比：一本书按页码切成若干「分册」）。
  - SSTable：不可变、按键有序的持久文件（类比：一旦印好就不能改的字典页）。
  - Chubby：分布式锁/命名服务，Bigtable 用它保证「一个 tablet 只有一个写者」（类比：图书馆的借书登记册）。

## 1. 问题背景与动机
- 前人工作简述：GFS 解决了大文件顺序读写；MapReduce 解决了批处理；但两者都不提供低延迟随机读写、可变记录与按 key 索引。
- 前人缺陷/未解决问题（逐条）：
  1. 商用 RDBMS 无法同时满足 WebScale 与 PB 级 + 水平扩展；垂直分库分表运维不堪重负。
  2. 纯 GFS 只解决顺序大文件，随机点查、记录原地更新无能为力。
  3. 产品 schema 频繁演化（每周新增列），关系模型的固定 schema 太僵。
  4. 多数负载只需要「单行原子」，并不需要跨行 ACID，但当时系统要么给太多（重事务），要么给太少（纯 KV）。

## 2. 核心方法
- 最直观类比：把数据库想成一本「超级通讯录」——按姓名（行键）字典序排好的大册子，每页（列族）记录不同类型的属性，每个属性还保留历史版本（时间戳）。这本册子太厚，于是按姓名字母段切成很多「分册」（tablet）分给不同管理员（tablet server）；新改动先记在便签（memtable）上，便签写满就印成一页新字典（SSTable）归档，后台定期把多页合并去重（compaction）。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：按 `(row key, column family:qualifier, timestamp)` 索引的字节值。
  2. 关键操作：写先追日志（commit log）再入 memtable；memtable 满刷成 SSTable；后台做 minor/major compaction；行按字典序范围切成 tablet，由 Master 调度到 tablet server；客户端经 Chubby + METADATA 表三级定位直接访问 tablet server。
  3. 输出：一个有序、稀疏、多版本、可按行/范围高效访问的分布式表。
- 形式化要点：数据模型 = `sparse, distributed, multi-dimensional sorted map`；一致性仅保证单行原子；tablet 按行键区间划分，分裂点在最大 SSTable 字典序中点附近。
- 理论性质/保证：单行 read-modify-write 原子；Chubby 租约保证一个 tablet 同一时刻只有一个写者（正确性底线）；Chubby 长时间不可用 → 全部 tablet 降级只读（宁可只读也不允许双主写）。

## 4. 实验结论（概览）
- 对比基线：论文以「小规模基准 + 生产环境定性」自证，而非与 RDBMS 横评。
- 数据集/指标：64 台服务器随机读/顺序扫描吞吐、恢复时间；生产规模（PB 级部署）定性描述。
- 结论方向：随机读延迟多数落在毫秒级；恢复时间正比于 commit log 尾部而非 tablet 大小；Google 内部有上百个 PB 级部署。🔧 精确数字（如常被转述的「70% <1ms、99% <10ms」、生产规模具体数值）请查原论文 Figure/Table 后补入，本笔记未逐字复核。

- 官方仓库：无（Google 内部系统，未开源）。

## 7. 2026 视角（🔧）
- Bigtable 是 NoSQL/云存储的原型机：HBase、Cassandra、Spanner 存储层、字节系 KV 都能找到它的直系后代。
- 今天工业界主流仍以「有序映射 + 区间分片 + LSM」为核心（TiKV、CockroachDB、Bigtable 本身持续演化）；Chubby 式协调服务的思想被 etcd/ZooKeeper/Consul 继承。
- 新趋势：存算分离（参见 Aurora/Socrates 笔记）、LSM 上湖（Paimon/Delta）、以及用 FPGA/智能网卡卸载 compaction。具体 SOTA 🔧 查当年工业实践。

## 8. 新手学习路线
- 10 分钟：读摘要 + 本笔记第 0、2 节，理解「稀疏有序映射 + tablet + SSTable」三件套。
- 30 分钟：对照 §2 的架构图，搞清「客户端如何经 Chubby/METADATA 三级定位到 tablet server」；跑一个 HBase 伪分布式实例建表写数。
- 进阶：读 LSM-tree 1996 与 RocksDB 笔记理解 compaction 三放大；读 Spanner 笔记看「缺的那块事务」如何补回；读 DDIA 第 3 章（列族=聚合、排序=聚簇索引）。
