## 一句话总结
向量太多内存装不下，只能放 NVMe SSD 上做磁盘检索；但在「一台机器拆成多个段（segment）」的向量数据库里，每个段内存/磁盘都有限，还要兼顾精度、速度、空间。Starling 用一个「内存导航图 + 重排后的磁盘图（更局部）+ 块搜索策略（少读盘）」的组合，在 2GB 内存 + 10GB 磁盘的段上塞下 3300 万条 128 维向量、recall@10 与平均精度超 0.9、延迟低于 1ms，吞吐比 SOTA 高 43.9 倍、延迟低 98%。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：高维向量相似搜索（HVSS / ANNS）在 RAG、推荐、多模态里无处不在。数据一大，内存索引放不下，必须上磁盘（SSD）。难点在「磁盘 I/O 慢」，检索时尽量少读盘、读也得读得连续。
- 为什么难：
  - 单机可拆成多个段（segment）以横向扩展，但每段内存+磁盘预算都很紧，要在精度/效率/空间三者间精细平衡；
  - 图索引（如 HNSW）在内存里很香，但原样落盘会因随机访存导致大量昂贵 I/O；
  - 现有磁盘方法没同时把「精度、效率、空间」都解决好。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 内存图索引 | HNSW、NSG | 每层连近邻，贪心走图 | 快但占内存，落盘随机 I/O 灾难 |
| 磁盘图索引 | DiskANN、SPANN、Starling | 图存盘 + 优化布局/读盘 | 省内存，但布局与 I/O 是核心难题 |
| 倒排/量化落盘 | SPANN（IVF+磁盘） | 聚类分桶、粗量化存盘 | 简单，但边界近邻易丢失 |

- 本文属于哪一类：磁盘图索引路线，但专门针对「段（segment）」这一工业部署单位做数据布局与搜索策略协同设计。
- 2-3 个必懂关键名词：
  - data segment（数据段）：向量数据库里单机上的一个存储/检索单元，内存与磁盘都有限，是本文的优化对象。
  - disk-resident graph index（磁盘驻留图索引）：图的邻接与向量主要存在 SSD 上，查询时按需读盘。
  - I/O efficiency（I/O 效率）：少做、且连续地做磁盘读写，是磁盘检索的性能命脉。

## 1. 问题背景与动机
- 前人工作简述：ANNS 有内存图（HNSW 等）与磁盘方案（DiskANN、SPANN 等）。图索引精度/速度平衡好，但内存开销大；磁盘方案开始把数据放 SSD。
- 前人缺陷/未解决问题（逐条）：
  1. 内存图难落盘：HNSW 式结构落盘后随机访存导致大量昂贵 I/O。
  2. 段场景被忽视：工业向量库用「多段」扩展，每段资源受限，需同时权衡精度/效率/空间，现有磁盘方法没整体解决。
  3. 布局不优：磁盘图的节点排布若不注重局部性，搜索路径会跨盘乱跳，带宽被浪费。
  4. I/O 未最小化：查询执行中缺乏系统性的「块级」读盘策略。

## 2. 核心方法
- 最直观类比：把磁盘上的图想成一座大图书馆（书在书架=SSD），内存里只放一张「楼层导览图（导航图）」。找书时先靠导览图定大致区域，再按「排架顺序（重排后的磁盘图）」连续取书，并且一次搬一整块书架（块搜索）而不是一本本跑。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：某数据段内的高维向量（受 2GB 内存 / 10GB 磁盘预算约束）。
  2. 关键操作一：数据布局。包含 (a) 一个内存驻留的导航图 (in-memory navigation graph)，和 (b) 一个重排后的磁盘图 (reordered disk-based graph)，重排增强局部性（locality），从而缩短搜索路径、减少磁盘带宽浪费。
  3. 关键操作二：块搜索策略 (block search strategy)。以「块」为单位组织磁盘读取，最小化查询执行中昂贵的磁盘 I/O 次数。
  4. 输出：在给定段上高效返回近似近邻，保持高 recall 同时低延迟。
- 形式化要点：目标是同时优化精度、效率、空间；核心超参是内存/磁盘预算分配与块大小（🔧 具体参数名请查正文）。
