## 一句话总结

企业里数据散落在各种表格、文档、知识库中，LLM 智能体干活前得先「找对数据」。CMDBench 是第一个专门评测「复合 AI 系统里的数据发现能力」的基准：实验发现，数据检索器不给力会让下游任务准确率平均掉 46%——找数据这一步远比想象中重要。

## 0. 给新手的阅读前置（背景知识地图）

- **这个子方向解决什么大问题**：LLM agent 要完成分析任务，第一步是从企业数据平台里找到「正确的数据源」。如果检索器找错了表/文档，后面 LLM 再聪明也是白搭。但过去没有 benchmark 专门衡量「数据发现」这一环的好坏。
- **为什么难**：企业数据是**多模态**的（结构化表、半结构化文档、非结构化文本）且**来源众多**（各部门数据孤岛）；发现还分粒度——先粗定位「哪个数据源相关」（coarse-grained），再细定位「具体哪些列/字段」（fine-grained），两级都要评。
- **几类相关评测的对照**：

| 评测类型 | 关注点 | 缺陷 |
|----------|--------|------|
| 传统数据发现基准 | 表/列匹配本身 | 不建模多模态、多数据源 |
| 复合 AI 系统（CAS）基准 | 只看端到端任务准确率 | 无法归因到「数据发现」环节 |
| **CMDBench** | 粗+细两级数据发现 + 任务执行 | ——（本文贡献） |

- **本文属于**：基准/评测类论文（benchmark paper）。
- **关键名词直觉解释**：
  - **复合 AI 系统（Compound AI System, CAS）**：不是单个模型端到端出答案，而是 LLM 智能体 + 工具 + 检索器等多种组件协作的系统（如 RAG、agent 工作流）。
  - **粗粒度发现（coarse-grained）**：先判断哪些数据源/模态与任务相关（找「对的书架」）。
  - **细粒度发现（fine-grained）**：在选中的数据源里定位具体条目/列/字段（找「对的那本书的那一页」）。

## 1. 问题背景与动机

- **前人工作简述**：数据发现研究长期面向人类分析师（如数据湖表搜索、schema matching）；LLM 兴起后，CAS 成为数据分析新范式，但评测只盯端到端效果。
- **前人缺陷/未解决问题（逐条）**：
  1. **现役数据发现基准不建模多模态与多数据源**：多数只针对单一模态（纯表格）的发现任务，与真实企业环境脱节。
  2. **CAS 基准只评端到端**：任务失败时无法区分是「检索器找错数据」还是「LLM 推理出错」，难以指导系统优化。
  3. **检索器设计对下游影响的量化缺失**：没人系统回答「换个数据检索器，agent 任务准确率会差多少」。

## 2. 核心方法

- **最直观类比**：CMDBench 像一场「寻宝比赛裁判」——不只看选手最后有没有挖到宝藏（任务结果），还分两步打分：有没有找对藏宝的岛（粗粒度）、有没有在岛上挖对坑（细粒度）。这样就能知道选手输在导航还是挖坑。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **数据构造**：把开放域的既有数据集/基准改造为模拟企业数据平台的形态——涵盖问答、复杂推理、自然语言查表（text-to-SQL 类）任务，并把它们分布到**多模态（表格/文本等）、多数据源**的孤岛式组织中。
  2. **评测设计**：对同一任务，分别评测（a）粗粒度数据发现（选对数据源/模态）、（b）细粒度数据发现（选对具体列/字段）、（c）端到端任务执行准确率。
  3. **变量控制**：替换不同的数据检索器（retriever）设计，观察下游任务表现变化。
  4. **输出**：一套可复用的基准 + 「检索器设计影响下游」的量化结论。
- **形式化要点**：任务执行可形式化为给定数据上下文 c（由检索器从数据源集合 D 中选出）后 LLM 的回答质量 Q(y, c)；CMDBench 把 Q 对「检索质量」的敏感性作为核心测量对象。
- **理论性质/保证**：基准类论文，无理论保证；贡献在数据构造方法论与可复现评测协议。

## 3. 变体 / 工程版（如有）

- 无独立变体；基准本身含多个任务难度层级与模态配置，可视作「内置变体」。开源仓库提供评测流水线，可视作工程版。

## 4. 实验结论（概览）

- **对比对象**：多种数据检索器设计（不同检索策略/模态覆盖）× LLM agent 配置。
- **数据集**：由开放域问答、复杂推理、结构化数据 NL 查询等既有数据集/基准改造而来的企业模拟数据平台（具体数据集清单 🔧 查论文实验节）。
- **指标**：粗/细粒度发现准确率、端到端任务准确率。
- **结论方向**：
  1. 数据检索器设计对下游任务影响显著：**任务准确率平均下降 46%**（检索器不佳时，跨模态/数据源/难度均成立）；
  2. 粗粒度与细粒度发现的错误会分别传导到端到端表现；
  3. 说明 CAS 需要专门的优化策略来为任务匹配合适的 LLM agent 与检索器组合。

## 5. 开源代码与动手实践

- **仓库地址**：https://github.com/megagonlabs/CMDBench （Megagon Labs 官方 GitHub 组织）
- **语言**：Python（评测框架 + agent/检索器封装）🔧。
- **典型流程（教学示意，以 README 为准 🔧）**：
  1. 安装依赖并下载数据集（部分为开放域数据集的改造版）；
  2. 配置 LLM API 与检索器（可选不同检索策略）；
  3. 运行粗粒度/细粒度发现评测与任务执行评测脚本；
  4. 汇总对比不同检索器配置的得分。
- **许可与资源提醒**：代码许可 🔧；运行需 LLM API 费用；企业模拟数据平台的搭建可能需要一定磁盘与索引构建时间。

## 7. 2026 视角（🔧）

- 2024–2026 年，企业级「AI 数据工程师 / 数据 agent」产品兴起，「检索器质量决定 agent 上限」已成共识；CMDBench 提供的粗细两级归因评测思路被后续 agent 基准广泛借鉴。
- 趋势一：评测从单轮发现走向多轮 agentic 数据探索（试探→反馈→再检索）。
- 趋势二：多模态统一检索（文本+表格+图像 embedding）成为数据平台标配，细粒度 schema 级 grounding 仍是难点。
- 🔧 本节为趋势性评述，具体基准与产品动态以公开资料为准。
