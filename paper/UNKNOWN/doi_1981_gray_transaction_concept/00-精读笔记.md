## 一句话总结
Gray 把「故障」与「并发」两大宿命收进一个对用户可见的抽象——事务（ACID），系统用恢复 + 并发控制 + 原子提交（2PC）兑现它；换来生产力与数据完整性，付出性能、事务边界与分布式阻塞的代价。这是 ACID 一词的首次成文面世。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：在共享数据库中，让「一组操作」要么全部生效、要么像没发生过，且并发执行互不踩踏——即「正确性契约的最小单位」。
- 为什么难：磁盘会坏、进程会崩、上千终端同时改同一库；早期每个应用各自加锁、各自写恢复代码，脆弱且重复。
- 几类主流解法（表格）：

  | 方法 | 代表 | 思路 | 优缺点 |
  |------|------|------|--------|
  | 应用自管 | CODASYL / 层次模型 | 程序员自己加锁写恢复 | 易错、重复造轮子 |
  | 系统托管（本文） | 事务 + 恢复 + 并发控制 | 边界（begin/commit）兜底一切 | 编程简单、但有性能与边界代价 |
  | 弱一致 / 最终一致 | NoSQL / BASE | 放弃强 ACID 换扩展 | 扩展好、语义弱 |

- 本文属于哪一类：系统托管的「事务抽象」总纲（概念层，非某引擎）。
- 2-3 个必懂关键名词：
  - ACID：原子性、一致性、隔离性、持久性——事务的四条契约（本文首次命名）。
  - 2PC（两阶段提交）：跨节点原子提交的协议，协调者先 prepare 再 commit，故障时参与者可能悬挂。
  - 可串行化：并发效果等价于某一种串行执行顺序——隔离性的数学定义。

## 1. 问题背景与动机
- 前人工作简述：Eswaran / Gray / Ries 1976 在 IBM 报告中定义了可串行化与两阶段锁；Gray & Reuter 的恢复理论（日志、影子页、稳定存储）在 70 年代末成型。
- 前人缺陷 / 未解决问题（逐条）：
  1. 错误恢复散落各应用：每个程序自己写检查点、回滚，写不对就丢数据。
  2. 并发互相踩：丢失更新、脏读、死锁，缺少统一正确性标准。
  3. 缺少「分布式原子性」：跨库提交没有统一协议，半成功状态频发。
  4. 「强一致」的代价无人系统总结：性能、长事务、边界归属的张力未公开讨论。

## 2. 核心方法
- 最直观类比：事务像「转账」——从 A 扣钱、向 B 加钱这两步必须绑成一个不可分割的动作；系统保证中间任何崩溃都回到起点或完整完成。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：应用程序以 `BEGIN; ...; COMMIT`（或 `ABORT`）包裹一组操作。
  2. 关键操作：
     - 恢复管理器：写 WAL（先日志后数据），崩溃后 redo 已提交、undo 未提交。
     - 并发控制：2PL 在 commit 时释放锁，使交错调度可归约为串行序。
     - 分布式：2PC 让跨节点「全提交或全放弃」。
  3. 输出：数据库从一个合法状态变到另一个合法状态，对应用暴露「提交 / 中止」两种结果。
- 形式化要点：
  - 原子性由 undo 日志保证；持久性由「日志先落稳定存储」保证；隔离性由可串行化 + 2PL 保证。
  - 一致性是「应用声明约束 + 系统机制合力」的结果，并非系统单方面属性。
- 理论性质 / 保证：可串行化提供并发正确的可证明标准；2PC 保证跨节点原子性，但故障时可能阻塞（prepared 悬挂）。

教学示意（转账事务，说明四属性）：
```sql
BEGIN TRANSACTION;
  UPDATE account SET balance = balance - 100 WHERE id = 'A';
  UPDATE account SET balance = balance + 100 WHERE id = 'B';
COMMIT;   -- 日志落盘、修改对外可见、锁释放
```
- 崩溃在两步之间 → undo 回滚（原子性 A）。
- 并发也动 A/B → 2PL 避免丢失更新（隔离性 I）。
- COMMIT 返回即持久（持久性 D）；余额守恒靠约束（一致性 C，依赖 I 成立）。

## 3. 变体 / 工程版（如有）
- 后续弱级别：SQL-92 四级隔离、快照隔离（SI）；长事务 → saga / 补偿事务 / 事件溯源。
- 现代实现：Spanner（TrueTime 做分布式外部一致）、TiDB / CockroachDB（共识替代 2PC 阻塞）。

## 4. 实验结论（概览）
- 本文为立场 / 概念论文，无基准实验。
- 论证方式：用「编程模型简化、完整性可集中声明、故障语义清晰、可度量（tpmC）」四优点 vs 「热点吞吐、长事务失灵、边界难定、弱级别语义缺口、分布式阻塞、系统复杂度」六局限。
- 结论方向：事务是必要的、几乎不可替换的核心抽象，但其边界必须被诚实画出（Limitations 半篇的价值）。

## 7. 2026 视角（🔧）
- ACID 仍是关系 / NewSQL / 分布式数据库的定义性词汇；NoSQL 的「放弃 ACID 换扩展」最终多以「补回事务」（事务型 Mongo、CockroachDB、NewSQL）收场。
- 分布式事务从 2PC 阻塞走向共识（Paxos / Raft / Spanner TrueTime），但「热点吞吐 vs 强一致」张力仍在。
