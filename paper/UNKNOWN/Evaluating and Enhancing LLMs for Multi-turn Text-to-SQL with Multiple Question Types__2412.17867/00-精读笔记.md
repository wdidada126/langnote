## 0. 给新手的阅读前置（背景知识地图）
**这个子方向解决什么大问题？** Text-to-SQL 是把用户的自然语言问题（「去年销售额最高的产品是哪个？」）自动翻译成可执行的 SQL。过去大多研究「单轮、干净、能直接映射成 SQL」的理想设定；可真实产品里用户是**多轮对话**的：会追问、会改口、会问一些 SQL 根本答不了的问题（比如常识判断、闲聊）。

**为什么难？**
1. **问题类型混杂**：有的问题能直接转 SQL，有的需要先澄清、有的根本不是查数据库能解决的（ambiguous questions）；
2. **多轮上下文**：第 3 句「那它的价格呢？」依赖前两句的语境，模型容易丢失或错用历史；
3. **评测缺失**：现有 benchmark（Spider、BIRD 等）多是单轮，没法衡量「问题分类 + 多轮 SQL 生成」的综合能力。

**主流解法分类：**

| 路线 | 代表 | 思路 | 局限 |
|------|------|------|------|
| 单轮 prompt | 直接 few-shot / CoT | 简单直接 | 不处理多轮与 ambiguous |
| 多轮建模 | STAR、RAT-SQL+TC 等 | 引入对话历史编码 | 问题类型单一，仍偏 SQL 生成 |
| **评测套件（本文）** | MMSQL | 先系统定义问题类型，再仿真多轮对话来考模型 | 属评测+诊断，不直接给出新模型 |
| 多智能体（本文增强） | MMSQL-Agent | 专用 agent 判类型、选策略 | 工程复杂度上升 |

**本文属哪类？** 同时是「评测基准」+「增强方法」：先用 MMSQL 诊断，再用多智能体框架增强。

**3 个关键名词直觉解释：**
- **multi-turn（多轮）**：用户与系统连续多句交互，后句依赖前句，不是一次性提问；
- **question type（问题类型）**：本文把用户问题分成多类（可转 SQL / 需澄清 / 非 SQL 可答等），分类准了才能选对回答策略；
- **multi-agent framework（多智能体框架）**：让不同「专家 agent」分工——一个负责判断问题类型，一个负责决定怎么答，再交给生成 SQL 的 agent。

## 1. 问题背景与动机
- **前人工作简述**：基于 LLM 的 Text-to-SQL 近年突飞猛进；多数方法集中在「SQL 生成」本身，用各种 demonstration 检索、中间推理步骤（CoT 等）提升准确率。
- **前人缺陷（摘要逐条）：**
  1. **只盯 SQL 生成，忽略对话复杂性**：真实世界对话式查询（conversational queries）复杂得多，前人很少顾及；
  2. **ambiguous 问题无人管**：含糊、无法直接用 SQL 回答的问题会导致不可靠响应，却缺乏处理；
  3. **缺少能仿真真实的评测**：没有同时覆盖「多样问题类型 + 多轮 Q&A」的测试套件，无法系统评估模型的「问题分类能力 + SQL 生成能力」。

## 2. 核心方法
**最直观类比**：像给客服人员做「情景模拟考试」——不光考他会不会写工单（SQL），还要考他遇到「顾客问了个没法查的问题」时知不知道先澄清、遇到「追问」时知不知道接着上一句说。考完试发现大家都容易在哪栽，再配一个「先分诊再派单」的多人协作流程来补强。

**具体做法（输入 → 关键操作 → 输出）：**
- **输入**：自然语言的多轮对话（含多种问题类型）；
- **关键操作**：
  1. 构造 **MMSQL 测试套件**：仿真真实场景，覆盖多种问题类型与多轮问答，用来同时评估「问题分类」与「SQL 生成」；
  2. 用 MMSQL 评估多个主流 LLM（开源 + 闭源），定位影响多轮表现的关键因素；
  3. 提出 **LLM 多智能体框架**：由专用 agent 识别问题类型、决定合适的回答策略，再驱动 SQL 生成；
- **输出**：更稳的多轮 Text-to-SQL 系统，能妥善处理多样且复杂的用户查询。

**形式化要点**：核心是「先分类、后决策」的两阶段控制流（问题类型识别 → 回答策略选择）；具体 agent 通信协议与提示词设计 🔧 以论文/代码为准。

**理论性质/保证**：属工程/经验性工作，无理论最优性保证；贡献在评测设计与实证增强效果。

## 4. 实验结论（概览）
- **对比基线**：多个流行 LLM（开源与闭源），作为被评估对象；
- **数据集**：MMSQL 自建多轮、多类型测试套件；
- **指标**：问题分类准确率、SQL 生成准确率、多轮整体成功率（🔧 精确数字查原论文 Table/Figure）；
- **结论方向**：
  1. 通过 MMSQL 评估识别出影响多轮表现的关键因素；
  2. 多智能体框架「显著增强」（significantly enhances）模型处理对话动态复杂性的能力；

## 7. 2026 视角（🔧）
- 多轮、agentic 的 Text-to-SQL 已成为 2025–2026 年主流方向：Text2SQL 从「单句翻译」走向「对话式数据分析助手」，问题分类/澄清（clarification）与工具调用成为标配；
- 本文「先分类后决策」的多智能体思路与当下 agent 框架（如 text-to-SQL agent、MCP 工具调用）高度契合；
- 具体最新基准与 SOTA 数字 🔧 查当年评测（Spider 2.0、BIRD 多轮扩展等）。

## 8. 新手学习路线
- **10 分钟**：读 arXiv 摘要 + 本笔记第 0、2 节，理解「问题类型分类」为什么是多轮 Text-to-SQL 的关键；
- **30 分钟**：浏览 MMSQL 项目页与 GitHub README，看它定义了哪几类问题；用自带脚本对一个开源 LLM 跑一遍评测；
- **进阶**：精读多智能体框架章节，尝试把「类型识别 agent」接到你熟悉的 Text-to-SQL 模型前做消融；对照 QDA-SQL 比较两种多轮增强路线的取舍。
