## 一句话总结
Rel2Graph 提出从任意数量的关系数据库自动构建统一「属性知识图（property knowledge graph）」的方法，还支持把合取 SQL 查询映射成基于模式的 NoSQL 查询；在 Spider / KaggleDBQA 上用执行准确率（EA）验证：在图上跑 NoSQL 查询的结果与关系库跑 SQL 一致——保证图既准又完整。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：关系数据库（表+主外键）是主流，但图结构更适合做关联推理/知识问答。把关系数据转成统一知识图，能跨库联合查询，但「怎么自动、保真地转」缺乏系统评估。
- 为什么难：表到图的映射规则多（实体/关系/属性），且要支持把 SQL 查询也「翻译」到图查询。
- 几类主流解法：

| 方法 | 代表 | 思路 |
|------|------|------|
| 手工映射 | 中间件/视图 | 人工定义 |
| 自动 KGC | Rel2Graph | 自动建属性知识图 |

- 本文属哪类：自动知识图构建（KGC）+ 查询映射。
- 2-3 个必懂关键名词：
  - 属性知识图（property knowledge graph）：带属性的图（节点-边-属性），如 RDF/属性图。
  - 合取查询（conjunctive query）：由多个条件连接而成的 SQL 查询。
  - 执行准确率（EA）：在图上执行结果与原库一致的比例。

## 1. 问题背景与动机
- 前人工作简述：已有若干关系→图的方法，但缺乏对更广数据库的系统性评估，且查询映射问题被忽视。
- 前人缺陷/未解决问题（逐条）：
  1. 评估不系统：缺跨多库的系统评测。
  2. 查询映射缺位：少有把 SQL 映射为图查询的方案。

## 2. 核心方法
- 最直观类比：把多个 Excel 表自动拼成一个「关系网」大图，并附一本「翻译词典」——以后用图查（NoSQL）也能得到和用 SQL 在原表查一样的答案。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：任意数量的关系数据库。
  2. 自动建图：KGC 方法构建统一属性知识图。
  3. 查询映射：把合取 SQL 映射为基于模式的 NoSQL 查询。
  4. 输出：统一知识图 + 可在图上执行的等价查询。
- 形式化要点：核心是确保图「高准确率与完整性」，以 EA 量化；超参数为映射规则（🔧 见论文）。
- 理论性质/保证：以 EA 保证结果对齐；无形式化保证。
