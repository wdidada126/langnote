## 一句话总结
用户提的问题五花八门：有的查「事实」（谁拿了冠军），有的要「统计」（哪个省份销量最高）。这篇论文给葡萄牙语搭了一个分流器：先用分类器判断问题类型，事实型问题交给神经 QA 模块，统计型问题交给 Text-to-SQL 解析器，分流准确率超过 99%。

## 0. 给新手的阅读前置（背景知识地图）

子方向解决什么大问题：自然语言问答有多种答案来源——开放文本（QA 模型读文找答案）或结构化数据库（Text-to-SQL 生成查询）。真实系统里两类问题混在一起，需要决定「这道题谁来答」。

为什么难：
- 两类问题在语言表面差异不大（都可以是 wh-问句），纯规则分流不可靠；
- 多语言（葡语）场景下，可用工具和数据集比英语少得多，需要拼装/翻译已有的英语资源。

几类主流解法（表格）：

| 路线 | 直觉做法 | 代表 |
|------|---------|------|
| 单一端到端式 | 一个大模型通吃所有问题类型 | 各类端到端 QA |
| 检索 + 抽取式 | 先检索文档再抽答案 | 经典 open-domain QA |
| 模块路由式 | 先分类问题，再派发给专用模块 | 本文 |

本文属哪类：模块路由式，是「多技能问答系统」的代表性架构实证。

关键名词直觉解释：
- Neural Question Answering Reasoner：读自然语言文本抽答案的神经模型（span/extraction 式 QA）；
- NL → SQL parser（Text-to-SQL）：把问题翻译成 SQL 去数据库里查；
- 问题路由（routing）：一个前置分类器判断问题应交给哪个模块——本文的「分流闸门」。

## 1. 问题背景与动机

前人工作简述：Transformer 大幅提升了神经 QA 与语义解析各自的能力；已有工作分别针对事实型 QA 或 Text-to-SQL 单独建系统。在葡语方面，此前已有用 mRAT-SQL+GAP 等做葡语 Text-to-SQL 的探索（本仓库有对应条目）。

前人的缺陷（逐条，据摘要与架构动机）：
1. 问题类型异质被忽略：不同问题需要不同的回答技术，单一管线顾此失彼——事实型问题走 SQL 反而绕远，统计型问题读文本抽不出答案；
2. 缺乏统一的葡语集成系统：葡语的 QA 工具与 Text-to-SQL 工具各自为政，没有人把它们装进一个可运行的完整系统并验证路由可行性；
3. 训练资源缺口：葡语的 QA/Text-to-SQL 训练与测试数据不足，需要翻译改造英语数据集 🔧 具体翻译了哪些数据集查原文。

## 2. 核心方法

最直观类比：医院的分诊台。病人（问题）先到分诊台（分类器），感冒的（事实型）去内科（QA 模块），要拍片的（统计型）去放射科（Text-to-SQL）。各科室专业化处理，分诊台保证走对门。

具体做法（输入 → 关键操作 → 输出）：
1. 输入：用户输入的自由格式葡语自然语言问题；
2. 问题分类器：判断该问题属于哪类（需要事实抽取，还是需要数据库查询）；
3. 路由：
   - 事实型 → Neural Question Answering Reasoner（神经 QA 模块，在文本上抽答案）；
   - 统计/查询型 → 自然语言 → SQL 解析器（Text-to-SQL，在数据库上执行）；
4. 输出：对应模块返回的答案。

形式化要点：架构为「分类器 + 两个异构求解模块」的管道；实现使用葡语 NLP 的主流工具链（BERTimbu 等葡语预训练模型被采用 🔧 工具清单以原文为准）。

理论性质/保证：系统论文，无理论保证；关键验证点是路由分类的准确性（实测 >99%，见下节）。

## 4. 实验结论（概览）
- 数据集：QA 与 Text-to-SQL 两类数据集（葡语版，由英语数据集翻译而来 🔧 数据集名称查原文）；
- 对比基线：路由模块自身的分类精度、以及两个下游模块各自的评测结果 🔧；
- 指标：路由准确率 + 下游问答/SQL 生成质量指标 🔧；
- 结论方向：系统以超过 99% 的准确率选择正确的回答方式（摘要明确给出），验证了「模块化问答分流」策略在葡语上的可行性。

## 7. 2026 视角（🔧）
- LLM 时代，「分流」思想的对应物是 tool use / routing agent：让大模型先决定调用检索、SQL 还是其他工具；本文是这类架构在单语言场景下的小型化先例 🔧；
- Text-to-SQL 在非英语语言的落地（政府开放数据、企业报表）仍依赖本文展示的「翻译数据集 + 本地预训练模型」组合拳，近年多语言基准（MultiSpider 等）推动该方向标准化 🔧。
