## 一句话总结
System R 是 IBM 用「真做一个多用户关系 DBMS 原型」来裁决「关系模型是否可行」的工程运动：它产出 SEQUEL→SQL 语言、代价优化器（访问路径选择）、RRA 解释执行、RELSTORE 存储子系统、2PL 与提交日志——几乎每一样都成为后来四十年关系数据库的出生证明。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：1970 年 Codd 提出关系模型，但产业主流怀疑「声明式遍历在硬件上不可用、无实现」；需要一次工程裁决。
- 为什么难：要在真实并发、故障、大数据量下兑现简洁性，还要发明一门非过程化语言并高效翻译。
- 几类主流解法（当时格局）：

| 方法 | 代表 | 思路 | 取舍 |
|------|------|------|------|
| 层次/网络模型 | IMS / CODASYL | 指针导航、用户管存储 | 性能好但绑定物理、难共享演化 |
| 关系模型 + 解释执行 | System R | 声明式 SQL + 优化器 + 存储子系统 | 翻译税，但开发效率与可共享性胜 |
| 关系模型 + 编译执行 | 后世（Neumann 2011 等） | 关掉解释开销 | 工程复杂 |

- 本文属哪一类：关系系统工程化的「验证性原型」总收束（Codd 模型的第一次整体兑现）。
- 2-3 个必懂关键名词：
  - SQL / SEQUEL：本文官宣「SEQUEL 因商标冲突改名 SQL」——集合导向的非过程化查询语言。
  - 代价优化器（access path selection）：由 Selinger 一系奠基，用统计信息选访问路径，把「声明式性能责任」揽到系统侧。
  - RRA（关系代数机器）：解释式执行层，逐算子向存储子系统要数据——其「逐算子往返税」是后世编译执行要关掉的。

## 1. 问题背景与动机
- 前人工作简述：Codd 1970 给模型；IMS/CODASYL 是现役主流；SQL/DS 前史产品违反 Codd 十条；应用无声明式界面。
- 前人缺陷/未解决问题（逐条）：
  1. 性能怀疑：声明式「扫所有元组」被认为在 70 年代硬件上不可用。
  2. 无实现：模型是数学，没人造出上生产的 DBMS。
  3. 编程界面真空：应用如何「说要什么而不说怎么做」没有答案。

## 2. 核心方法
- 最直观类比：把建数据库系统想成「盖一座工厂来验证一种新流水线理念」。Codd 提了理念（关系模型），System R 是「真把工厂盖起来、跑起来、算清成本」的那份结项报告——它证明这条流水线不但能转，还能养活后续所有 SQL 工厂（DB2、Oracle）。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：SQL 语句（来自应用/终端）。
  2. 关键操作：① 编译侧 parser → normalizer → optimizer 产出关系代数计划；② RRA 解释执行各算子，向存储子系统要页/记录；③ DBWS 看门狗统一管理锁表与日志；④ RELSTORE 用 B+树索引、缓冲池、定长槽页落地；提交走「先写日志(commit record) 再释放 2PL 锁」。
  3. 输出：一个真实可用的多用户关系 DBMS 原型 + 一份诚实复盘。
- 形式化要点：2PL 多粒度锁、WAL 提交顺序、单/多版本（Multran）实验、R* 分支原型 2PC。
- 理论性质/保证：在真实负载下验证关系模型工程可行；证明「非过程化语言 + 代价优化器」能补上性能缺口（多数典型查询拉到可接受区间）。

## 3. 变体 / 工程版（如有）
- 单版本（原地覆盖）与多版本（Multran，读者不挡写者）两条实现线——MVCC 的第一次成文对照实验。
- 分布式分支 R* 完整实现两阶段提交（2PC）；后续商业化 SQL/DS（1982）、DB2（1983）。

## 4. 实验结论（概览）
- 对比基线：CODASYL/IMS 式应用、手写导航程序。
- 指标：响应时间、开发效率、并发/故障下的行为。
- 结论方向（定性，原笔记标注数字未逐字复核）：声明式查询的编译/解释开销在短事务/点访问场景是可见税，但在复杂/即席查询与开发效率上显著占优；「关系系统不可用」被推翻，「关系系统慢」未被彻底推翻。🔧 精确数字请查原论文 Table/Figure 后补入。

## 7. 2026 视角（🔧）
- System R 锁定的「SQL + 优化器 + 存储子系统」三件套仍是今天每一个关系数据库的骨架；DB-Engines 榜单上 SQL 家族的全部份额起点在此。
- 优化器（Selinger 代价模型）演化为今日的 Cardinality Estimation、自适应查询执行；RRA 解释被编译/向量化执行取代（Neumann 一系）。
- 新趋势：AI 辅助优化器、存算分离下的执行引擎重构；但对外接口仍是关系/SQL，证明 1970–81 的抽象经受 50 年考验。具体演进 🔧 查当年教材/综述。

## 8. 新手学习路线
- 10 分钟：读摘要 + 本笔记第 0、2 节，理解「用造出来裁决模型」与 SQL/优化器/存储三件套。
- 30 分钟：对照 §2 架构图，走一遍 `SELECT ... WHERE` 从 parser → optimizer → RRA → RELSTORE 的链路；体会「逐算子往返税」。
- 进阶：读 Codd 1970 与 Gray 1981 做同人群对照；用 PostgreSQL `EXPLAIN` 实地看优化器计划，体会 Selinger 遗产；读 Neumann 2011 理解编译执行如何回应本文自认的解释开销。
