## 一句话总结
Qrlew 是一个开源库：它先把普通 SQL 解析成一种「带类型、值域、行归属信息」的中间表示 Relations，再自动把它改写成等价但满足差分隐私（Differential Privacy）的 SQL，最后还能塞回标准数据库执行——让数据需求方写普通 SQL、数据 owner 拿到强隐私保证、隐私专家只负责改写。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：很多分析场景要在「不泄露个人敏感信息」的前提下，让分析师用 SQL 查统计数据（如「某病区平均年龄」）。差分隐私（DP）能在数学上保证「单条记录进不进数据集，对查询结果影响有界」，但手写满足 DP 的 SQL 极其困难。
- 为什么难：DP 要求对查询结果加噪声、对「查询灵敏度（sensitivity）」精确建模；一旦 SQL 含 join、聚合、条件组合，手写噪声与 clipping 很容易出错或过度牺牲精度。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 引擎内 DP 查询接口 | Google DP、OpenDP | 数据库原生支持 DP 聚合 | 灵活但需重写查询逻辑 |
| 合成数据 | DP 合成库 | 生成带噪声的替身表 | 易用但保真度有限 |
| SQL→DP-SQL 改写 | Qrlew | 解析为 IR 后自动改写 | 用户写普通 SQL，但改写正确性依赖 IR |

- 本文属哪类：第三类——自动改写路线，关键是引入了能「跟踪类型/值域/行归属」的中间表示。
- 2-3 个必懂关键名词：
  - 差分隐私（Differential Privacy, DP）：给结果加可控噪声，使单条记录难以被反推。
  - 中间表示（IR, Intermediate Representation）：编译器概念；这里指介于 SQL 与执行之间的、携带语义信息的数据结构。
  - 行归属（row ownership）：知道某行数据属于哪个个体，才能正确计算「改这一行的影响有多大」（即灵敏度）。

## 1. 问题背景与动机
- 前人工作简述：已有一些 DP-SQL 引擎与库，但大多要求使用者直接以 DP 原语书写查询，或用合成数据。
- 前人缺陷/未解决问题（逐条）：
  1. 使用门槛高：分析师必须懂 DP 才能写出合规查询，与「用普通 SQL 提数」的工程现实脱节。
  2. 集成成本高：数据 owner 侧往往要引入专门引擎，难以在已有标准数据存储上直接跑。
  3. 信任边界不清：改写者（隐私专家）与数据 owner 可能分属不同组织，需要一种「owner 无需懂 DP、只需信任改写者」的分工。

## 2. 核心方法
- 最直观类比：把 SQL 当成菜谱，Qrlew 是「自动把家常菜谱翻译成『符合食品安全规范』版本」的助手——食客（分析师）写原菜谱，后厨（数据 owner）按翻译版做，监管（隐私专家）只改菜谱。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：一条标准 SQL 查询。
  2. 解析为 Relations（IR）：保留丰富数据类型、值域范围、行归属信息——这是普通 SQL AST 不具备的。
  3. 重写为 DP 等价查询：基于 IR 中的灵敏度信息，自动注入噪声/clipping 等 DP 机制，生成语义等价的「差分隐私版 SQL」。
  4. 输出：可回灌到各类标准数据存储执行的改写后 SQL。
- 形式化要点：核心是 IR 必须可追踪「值范围 + 行归属」，才能正确估计查询灵敏度并施加最小必要噪声；超参数（噪声规模 ε/δ）由改写者设定 🔧 具体 API 以代码为准。
- 理论性质/保证：提供 DP 的形式化保证（依赖标准 DP 组合定理）；改写等价性需满足「语义等价 + 灵敏度有界」。
