## 一句话总结
分布式流处理框架常用来「shuffle（重分发）数据做就近聚合」，但现有基准多不聚焦这一步。ShuffleBench 是专为「大规模 shuffle 操作」设计的开源基准：用黑盒方式测延迟/吞吐/可扩展性，灵感来自大型云可观测平台的近实时分析需求，高度可配。配套实验在云原生环境用 Flink、Hazelcast、Kafka Streams、Spark 跑出：Flink 吞吐最高，Hazelcast 延迟最低。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：流处理框架要「把数据重分发（shuffle）到正确节点做聚合」，这一步常成性能瓶颈，却少有专门基准。
- 为什么难：shuffle 涉及网络重分发，受框架实现、配置、规模影响大；要可复现地评测难。
- 几类主流解法：

| 通用流基准 | 既有 benchmark | 评端到端 | 不突出 shuffle |

| 微基准 | 自写 | 单指标 | 难对比 |

- 本文属哪类：流处理/分布式系统的基准测试（benchmark）路线。
- 关键名词直觉：
  - shuffle（洗牌/重分发）：把数据流按 key 重新分到各节点，以便做状态本地聚合。
  - state-local aggregation（状态本地聚合）：聚合状态放本节点，减少跨节点。
  - stream processing framework（流处理框架）：Flink、Kafka Streams、Spark Streaming 等。
  - latency / throughput（延迟/吞吐）：单条处理快慢 / 单位时间处理量。

## 1. 问题背景与动机
- 前人工作简述：分布式流处理框架用于构建可扩展、可靠的应用做流上的变换与聚合。
- 前人缺陷/未解决问题（逐条）：
  1. 缺 shuffle 专项基准：已有基准不聚焦「框架主要用来 shuffle 再聚合」的场景。
  2. 聚合逻辑被当黑盒：实际聚合是黑盒组件，需把 shuffle 与聚合解耦评测。
  3. 缺近实时可观测场景对齐：少有基准源自真实大规模可观测平台需求。

## 2. 核心方法
- 最直观类比：像评测「快递分拣中心」——不关心包裹里装啥（聚合黑盒），只测「按目的地重新分拣（shuffle）」这道工序在多大规模下多快、多稳。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：流处理框架部署 + 配置参数 + 数据生成设定。
  2. 关键操作：
     - 设计 ShuffleBench：聚焦 shuffle 操作、把聚合当黑盒；
     - 借鉴大型云可观测平台近实时分析需求，采用性能工程界的延迟/吞吐/可扩展性指标与方法；
     - 高度可配，域无关；
     - 以现成 Kubernetes 工具交付，含 4 个 SOTA 框架实现。
  3. 输出：可复现的 shuffle 性能评测结果与对比。
- 形式化要点：核心是「shuffle 聚焦 + 黑盒聚合 + 域无关可配」的基准设计；具体 workload 模型 🔧 查原论文。
- 理论性质/保证：无形式化保证；以实证基准与对比为主。

## 4. 实验结论（概览）
- 对比基线：四种框架互相对比——Flink、Hazelcast、Kafka Streams、Spark（云原生环境）。
- 数据集/负载：ShuffleBench 生成的 shuffle 负载（多种配置）。
- 指标：延迟（latency）、吞吐（throughput）、可扩展性（scalability）。
- 结论方向（摘要给出的已核实结论）：
  - Flink 吞吐最高；
  - Hazelcast 延迟最低。
  - 🔧 各配置精确延迟/吞吐/扩展性数字查原论文 Table/Figure 后补。
