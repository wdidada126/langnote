## 一句话总结
把机器学习塞进数据库的「学习型组件」（如 learned index、基数估计）上线后，最怕数据和负载悄悄漂移导致模型失效；NeurBench 提出一个能定量、可控地制造「数据漂移 + 负载漂移」的基准套件（核心是 drift factor 概念 + 保相关性的生成框架），让你系统评估这些组件在真实漂移下的鲁棒性。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：近年「learned database components」把 ML 嵌进数据库（如用神经网络做索引、做基数估计、做查询优化）。它们离线训练，但线上数据/负载一直在变（drift），容易悄悄退化。
- **为什么难**：漂移类型多、难量化、难以复现；此前工作只在某一种漂移下测，无法系统比较。
- **几类主流解法（评测视角）**：

| 评测对象 | 代表 | 思路 |
|----------|------|------|
| learned index 基准 | SOSD | 静态评测 learned index |
| 鲁棒性测试 | Testing Robustness of Learned Index | 测抗扰 |
| 本文 NeurBench | drift factor + 生成框架 | 可控/可定制漂移 |

- **本文属哪类**：面向 learned DB 组件的**基准/评测**工具，属数据库系统内核研究。
- **2-3 个必懂关键名词**：
  - **learned database component（学习型数据库组件）**：用 ML 实现的 DB 模块，如 learned index、learned cardinality estimator。
  - **drift（漂移）**：数据分布或工作负载随时间变化，导致模型性能下降。
  - **drift factor（漂移因子）**：本文提出的、用来定量刻画漂移程度的核心概念。

## 1. 问题背景与动机
- 前人工作简述：learned DB 组件被广泛研究；数据库是动态的（数据/负载持续漂移），组件需在此下保持有效。
- 前人缺陷/未解决问题（逐条）：
  1. **评测不系统**：已有工作只在特定漂移下测试，无法跨多种漂移或按需定制漂移做系统比较。
  2. **漂移难量化/难复现**：缺少统一的「漂移程度」度量与可复现的生成方法。

## 2. 核心方法
- **最直观类比**：给「学习型数据库组件」做体检——不是随便换个数据测，而是像调旋钮一样定量调出「病情轻重」（drift factor），再生成一套既真实漂移、又保留原有相关性的数据与负载来考它。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **定义 drift factor**：提出一个核心概念，把各类漂移量化成可比较的「程度」。
  2. **漂移感知生成框架**：基于该定义，生成「保留内在相关性」又体现真实漂移的数据与负载。
  3. **套件化评测**：在可控/可定制漂移下，跑代表性 learned DB 组件看其表现。
  - 输出：一套可复现的漂移评测结果与洞察。
- **形式化要点**：核心是 drift factor 的量化定义 + 保相关性的生成框架（🔧 具体公式以论文为准）。
- **理论性质/保证**：无理论保证；以「能生成真实且可控漂移」的实证有效性为主。

## 3. 变体 / 工程版（如有）
- 套件支持多种漂移类型与可定制漂移场景，可作为 learned index / 基数估计等组件的回归测试平台（🔧 以仓库为准）。

## 4. 实验结论（概览）
- 对比基线：若干代表性 learned DB 组件（具体清单 🔧 查原论文）。
- 数据集：基于生成框架造出的漂移数据与负载。
- 指标：组件在漂移下的准确性/效率保持度。
- 结论方向：实验表明 NeurBench 能生成真实的数据/负载漂移，并揭示代表性 learned 组件在不同漂移场景下的表现差异；🔧 精确数字查原论文图表后补（摘要未给精确数字）。
