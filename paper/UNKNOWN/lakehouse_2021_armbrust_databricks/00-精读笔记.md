## 一句话总结
Lakehouse 主张在低成本、直接可访问的开放存储格式（Parquet / ORC）之上，加一层「事务元数据层 + 格式无关的性能武器（缓存 / 统计 / 布局）」，把数据湖变成同时具备数仓管理与性能、又能被 ML 直接快读的系统——「湖即仓」。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：传统「数据湖 + 数仓」两层架构带来可靠性差、数据陈旧、ML 不友好、总拥有成本高的四顽疾；如何既保留湖的开放廉价，又拿下仓的性能与治理。
- 为什么难：开放格式（Parquet）没有「事务 / 索引 / 统计」，直接在裸文件上做 SQL 会慢且无法保证 ACID；封闭数仓性能好但格式私有、锁死生态。
- 几类主流解法（表格）：

  | 方法 | 代表 | 思路 | 优缺点 |
  |------|------|------|--------|
  | 两层架构 | 湖 + 数仓（Teradata / Redshift） | 湖存原始、ETL 进仓 | 治理好、但双份拷贝 / 天级陈旧 |
  | 存算分离数仓 | Snowflake / BigQuery | 私有格式 + 分离 | 性能好、但格式锁定 |
  | 本文 Lakehouse | 开放格式 + 元数据层 | 湖即仓 | 开放、省、但放弃部分数据独立性 |

- 本文属于哪一类：架构立场论文 + 系统实践报告（非纯实验论文）。
- 2-3 个必懂关键名词：
  - metadata layer（元数据层）：定义「表版本 = 哪些对象」的层（Delta / Iceberg / Hudi），提供 ACID、time travel、零拷贝克隆。
  - data skipping（数据跳过）：用每文件列级 min / max 统计跳过无关文件，是「开放格式也能快」的关键。
  - Z-order / Hilbert curve：空间填充曲线，做多维聚簇以最小化读入量。

## 1. 问题背景与动机
- 前人工作简述：第一代数仓（存算耦合一体机）→ 第二代数据湖（HDFS / S3，schema-on-read）→ 「湖 + 仓」两层架构成为财富 500 强标配。
- 前人缺陷 / 未解决问题（逐条）：
  1. 可靠性差：湖与仓两套引擎语义不一致，持续 ETL 引入 bug。
  2. 数据陈旧：入仓常以「天」计，反而不如第一代当场可查。
  3. 高级分析支持有限：TensorFlow / PyTorch 无法在数仓上高效扫大数据，导出文件又多一段 ETL。
  4. 总拥有成本高：双份存储 + 私有格式锁定推高迁移成本。

## 2. 核心方法
- 最直观类比：像「在公共仓库（开放货架）旁边配一个智能管理员（元数据层）」——货架任何人都能直接拿（开放格式），但管理员记得每版放了什么、哪里有索引、热货放哪，于是既开放又快。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：S3 / ADLS / GCS 上的 Parquet / ORC 开放格式数据。
  2. 关键操作（三支柱）：
     - 支柱一：元数据层（Delta / Iceberg / Hudi）提供 ACID、版本、审计、time travel、zero-copy clone。
     - 支柱二：格式无关性能武器——转码缓存、旁路统计（Bloom filter）、数据布局（Z-order 聚簇）。
     - 支柱三：声明式 DataFrame 把 ML 负载的谓词 / 投影下推到数据源插件，ML 自动吃到前两者优化。
  3. 输出：BI / DS / ML 同读同管的开放平台，放弃「数据独立性」换直接访问。
- 形式化要点：
  - 提交协议：版本号 = 对象键的 CAS 语义，使「可串行化」不依赖锁，而是 MVCC 的云原生变体。
  - 热数据靠缓存、冷数据靠布局 + 统计跳过，两者分工覆盖全负载。
- 理论性质 / 保证：无形式化证明；实验仅一组 TPC-DS SF30K 自测（对手匿名）。

教学示意（元数据层提交，综合论文与 Delta PVLDB'20，非逐字）：
```
function commit(table, actions):
  r = latest_visible_log_id(table)
  write_data_objects(actions)              # 并行写，此刻对读者不可见
  loop:
    if atomic_put_if_absent(table, "00000{r+1}.json", actions):
      return r+1                           # 占得唯一日志槽 ⇒ 可串行化
    else:
      r = latest_visible_log_id(table)      # 乐观并发，让号重试
      validate_no_conflict(actions, log(r+1))
```

## 4. 实验结论（概览）
- 对比基线：四家主流云数仓（DW1–DW4，匿名）在 TPC-DS power test、SF 30,000（30TB）、960 vCPUs。
- 指标：执行时长、花费。
- 结论方向（摘要已核实）：Delta Engine 与主流云数仓「同速或更快、成本约 1/3 至 1/10」；但属厂商自测、对手匿名、缓存起跑有不对称（冷缓存慢 18%）。

## 7. 2026 视角（🔧）
- Lakehouse 成为共识，但「格式战争」（Delta / Iceberg / Hudi 互不兼容）恰是本文「开放格式是核心」的反讽，靠 UniForm / catalog 同步弥合。
- 跨表事务、湖上向量检索、serverless 按查询计费仍是活跃方向；Snowflake / BigQuery 也吸收开放格式，预言被双向渗透式兑现。
- 本节为趋势判断（🔧 具体生态以当年为准）。
