## 一句话总结
针对大模型做 Text-to-SQL 时「单条生成质量不稳、风格单一」的问题，本文提出 XiYan-SQL：用多生成器集成产出多样且高质量的候选 SQL，配合自研的 M-Schema（半结构化 schema 表示）、「监督微调 + 上下文学习（ICL）」双路生成、精修器（refiner） 纠错、以及候选选择器，在 BIRD、Spider、SQL-Eval、NL2GQL 等多个基准上取得 SOTA（如 BIRD 75.63%、Spider 89.65%）。

## 0. 给新手的阅读前置（背景知识地图）
- 大模型做 Text-to-SQL 的现状：直接用 LLM 把自然语言问题 + 数据库结构（schema）转成 SQL，已成为主流。痛点：单次生成容易「一时失手」；不同提问方式/微调风格产出差异大。
- 本文四大核心概念：
  - 多生成器集成（multi-generator ensemble）：不只生成 1 条 SQL，而是用多个「风格不同」的生成器各产出若干候选，再从中挑最好的。
  - M-Schema：作者提出的半结构化 schema 表示方法，比纯文本 DDL 更利于模型理解表结构。
  - ICL vs SFT：ICL = 在提示里给几个示例（少样本）；SFT = 用标注数据微调模型。
  - Refiner / Selector：精修器对每条候选 SQL 做逻辑/语法纠错；选择器从候选里挑最优。
- 关键基准名词：Spider（英文跨域 text-to-SQL 标杆）、BIRD（更贴近真实、含噪声与大量数值的标杆）、SQL-Eval / NL2GQL（其它评测，含图数据库查询 NL2GQL）。

## 1. 问题背景与动机
- 前人工作：LLM 在 text-to-SQL 上表现强，但单生成器存在质量与多样性不足的问题；schema 表示方式对效果影响很大，但缺乏统一好方案。
- 本文动机：用多生成器 + 多样候选 + 精细挑选提升稳健性与上限，并改进 schema 表示。

## 2. 核心方法
- 最直观类比：像一家「SQL 写作工作室」：先有一份清晰的「数据库说明书」（M-Schema）；再让几位写作风格不同的高手（多生成器：有的擅长 ICL、有的擅长 SFT）各自写几稿；编辑逐稿纠错（refiner）；最后主编挑出最准的一稿（selector）。多稿择优，比单人单次稳得多。
- 具体做法（输入 → 关键操作 → 输出）：
  1. M-Schema 表示：把数据库 schema 转成半结构化表示，提升模型理解。
  2. 双路生成（多生成器）：一路用 SFT 训练多个「偏好不同」的模型产出多样候选；一路用 ICL（含基于 NER 命名实体识别的示例选择，避免只盯着实体）。
  3. Refiner 精修：纠正每条候选的逻辑/语法错误。
  4. Selector 选择：微调一个选择模型，辨别候选 SQL 的细微差别，挑出最优。
- 形式化要点：核心是「多生成器 + 多样候选 + 精修 + 优选」同时提升质量与多样性；超参为各生成器配置与选择阈值。
- 理论性质/保证：无形式化保证；以实验验证稳健性。

## 4. 实验结论（概览）
- 基准：BIRD、Spider、SQL-Eval、NL2GQL 等多个方言/场景数据集。
- 结论方向（含论文报告的具体 SOTA 数字，来自摘要）：
  - BIRD 执行准确率 75.63%；Spider 测试集 89.65%；SQL-Eval 69.86%；NL2GQL 41.20%；
  - 多生成器集成相比单生成器显著提升稳健性；M-Schema 与 NER 示例选择对效果有正向贡献。

## 5. 开源代码与动手实践
- 仓库：https://github.com/XGenerationLab/XiYan-SQL（官方实现，含 M-Schema、模型与文档）
- 典型流程（教学示意，非逐字复制；以仓库 README 为准 🔧）：
  1. 准备数据库与问题，用 M-Schema 生成半结构化 schema；

  3. 用 refiner 纠错、selector 优选；
  4. 在 BIRD/Spider 等基准评测执行准确率。

## 7. 2026 视角（🔧）
- 多生成器 / 自集成是 LLM text-to-SQL 的主流套路之一：与「自我一致性（self-consistency）」「多 agent 投票」思路一致。
- Schema 表示（M-Schema 类）成为关键工程：如何让 LLM 看懂库结构是效果分水岭。
- 新趋势：批评式修正（XiYan-SQL-CRITIC）、结合检索/工具调用等。

## 8. 新手学习路线
