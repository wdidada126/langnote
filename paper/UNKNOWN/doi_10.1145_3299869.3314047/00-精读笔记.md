## 一句话总结
Socrates 把 SQL Server 改造成「无状态计算 + 页服务器（Page Server）+ 单逻辑日志（X-Store）+ 平台共享存储」的分层架构：副本不再重放日志、页按需物化、故障切换与库大小解耦——与 Aurora 同为「日志即数据库」，但 Socrates 选择信任自家云平台底座、把持久性外包，而 Aurora 自建存储节点自治副本。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：第一代云托管数据库「进程持有数据、副本重放日志、恢复正比于日志量」，弹性/高可用/备份全部被绑定。
- 为什么难：要保住 SQL Server 单实例的全部可编程性（T-SQL、事务、索引语义），同时让「日志持久性、页物化、副本新鲜度、恢复」各自独立伸缩。
- 几类主流解法：

| 方法 | 代表 | 思路 | 取舍 |
|------|------|------|------|
| 单机搬进 VM | 早期 SQL Azure | 实例规格决定一切 | 纵向弹性天花板、HA 靠日志重放 |
| 库侧自持副本 | Aurora（2017） | 存储节点六副本 + quorum | 层厚、跨平台性弱 |
| 平台外包 + 分层 | Socrates（2019） | 单日志流 + 页服务器 + 平台存储 | 层薄、深度绑定云平台 |

- 本文属哪一类：云原生 OLTP 存算分离（与 Aurora 并列的两种纯血形态之一）。
- 2-3 个必懂关键名词：
  - Page Server（页服务器）：按页地址区间分区，惰性把 redo 物化成页、按需供应「as-of-LSN 页」的权威服务层。
  - X-Store：append-only 的持久日志服务，对上层表现为「一条逻辑日志」。
  - Falcon：让只读副本不再重放日志、按水位读「as-of-LSN 页」的机制。

## 1. 问题背景与动机
- 前人工作简述：SQL Server 此前云路线（SQL Azure → VM 自托管）本质是「单机数据库搬进虚拟机」；高可用靠 Always On 可用性组在副本上重放日志。
- 前人缺陷/未解决问题（逐条）：
  1. 纵向弹性天花板：存储/IOPS/内存同涨同跌，升配=换更大 VM。
  2. 高可用靠日志重放：副本延迟不可控、每个可读副本重复完整重放劳动。
  3. 备份/恢复与数据规模同阶：TB 级库恢复以小时计。
  4. 运维侵入服务：补丁/升级/伸缩都要在「持有数据的进程」上动刀。

## 2. 核心方法
- 最直观类比：传统数据库像「厨师（计算）必须守着自己的冰箱（数据），备厨（副本）要照着主厨的每步操作重做一遍菜」。Socrates 像「主厨只写一张不可篡改的流水账（X-Store 日志），另有一队配菜员（Page Server）按单做菜并直接端给客人；备厨不再重做，看单子最新到哪一步即可上菜；冰箱换成公共冷库（平台存储），谁都不拥有数据」。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：SQL 事务（T-SQL）。
  2. 关键操作：① 主 compute 生成 redo 仅 append 到 X-Store，拿到持久确认即 ack 客户端；② 各 Page Server 从 X-Store 拉 redo、惰性物化所管页区间、应答 compute 的「页 P as-of LSN ℓ」请求；③ Falcon 只读副本不重放日志，按水位读页；④ 故障切换 = 新 compute 从 X-Store 尾部续接，无 crash recovery。
  3. 输出：保住完整 SQL 语义、秒级且与库大小无关的 failover、近零成本读扩展。
- 形式化要点：单写者模型（唯一日志生产者）；页幂等物化靠「页内 LSN 比较」（ARIES 血统）；fencing/term 拒绝过期主。
- 理论性质/保证：单写者隔离性留在计算层；复制流即执行流（与 Calvin/Aurora 同源思想）；故障切换正确性与缓冲池/库大小无关。

## 4. 实验结论（概览）
- 对比基线：SQL Server 既有形态、传统 Always On 可用性组。
- 数据集/指标：OLTP 型负载；写延迟、只读扩展边际成本、failover/恢复时间、弹性。
- 结论方向（定性，原笔记标注无第三方基准、刻度未逐字复核）：提交延迟与 X-Store 一次 append 往返同阶；加只读副本近零边际成本；切换与库大小解耦；备份还原退化为元数据+日志尾操作。🔧 精确数字请查原论文 Figure/Table 后补入。

## 7. 2026 视角（🔧）
- Socrates 与 Aurora 并立为「云原生 OLTP 存算分离的两种纯血形态」，其思想已融入主流云数据库（Azure SQL Hyperscale、Aurora、PolarDB、AlloyDB 等）。
- 今天趋势：更激进的存算分离（远程内存/计算卸载）、serverless 数据库（按请求计费、冷备副本）、以及把 redo 物化彻底下沉到存储层。
- 新议题：平台绑定 vs 跨云可移植、单写者天花板如何被共享存储多写突破。具体 SOTA 🔧 查当年云数据库综述。

## 8. 新手学习路线
- 10 分钟：读摘要 + 本笔记第 0、2 节，理解「无状态计算 + 页服务器 + 单日志流」三件套与 Aurora 的差异。
- 30 分钟：对照 §2 伪码走一遍 `UPDATE accounts SET bal=bal-100 WHERE id=42` 的提交旅程；对比 Aurora 同款六步的差异（集中在 quorum 判定 vs 单流确认）。
- 进阶：读 Aurora 与 Snowflake 笔记做三角对照；思考「单写者 + 无状态」如何使在线升级成为可能；读 ARIES/WAL 材料理解页 LSN 幂等物化。
