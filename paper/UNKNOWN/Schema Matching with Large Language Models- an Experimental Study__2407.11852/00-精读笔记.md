## 一句话总结
Schema 匹配是「找出两张表的字段之间语义对应关系」的脏活。本文系统地拿现成大语言模型来干这活，发现：给模型的上下文太多或太少都不好，但选对「提示范围（task scope）」能让 LLM 帮你 bootstrap 大部分匹配、大幅省下数据工程师的人工。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：Schema Matching 要在两个关系 schema 的元素（表/列）之间找出语义对应（如 A.name ≈ B.customer_name）。这是数据集成、迁移、湖仓治理的基础。
- **为什么难**：仅靠字段名/类型会撞上同义/异义；往往需要理解业务语义；人工匹配昂贵且易错。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 字符串/规则 | 传统 similarity | 名字/类型相似 | 快但不懂语义 |
| 深度学习 | PoWareMatch 等 | 学习语义表示 | 需训练数据 |
| LLM 提示 | 本文 | 零样本提示匹配 | 省数据但看上下文 |

- **本文属哪类**：用现成（off-the-shelf）LLM 做 schema matching 的实验研究。
- **2-3 个必懂关键名词**：
  - **Schema Matching（schema 匹配）**：建立两 schema 元素间的语义对应。
  - **Task Scope（任务范围）**：提示 LLM 时包含多少上下文信息的方式（本文核心变量）。
  - **Verification Effort（验证成本）**：人工复核 LLM 输出所需的精力。

## 1. 问题背景与动机
- **前人工作简述**：LLM 在 data wrangling 多任务有用，但用现成 LLM 做 schema matching 缺乏系统评估。
- **前人缺陷/未解决问题**：
  1. 不清楚「给 LLM 多少上下文」会影响匹配质量。
  2. 缺少对 LLM 匹配「质量/验证成本/决断力/互补性」的系统性比较。

## 2. 核心方法
- **最直观类比**：让一个懂业务的顾问比对两张表头。给他太少信息他猜不准，给他整本字典他又看花眼；本文就是系统地试「给他看多少、怎么给」，找出最省人工的配置。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：两个关系 schema（仅用元素名与描述）。
  2. **关键操作**：
     - 仅用**名字和描述**识别两 schema 间的语义对应。
     - 从**健康领域**新建一个基准；提出不同 **task scopes**（提示 LLM 做匹配的方法，差异在提示含多少上下文）。
     - 用 task scopes 把 LLM 匹配与**字符串相似度基线**比较，考察匹配质量、验证成本、决断力（decisiveness）、互补性。
  3. **输出**：各 task scope 下的 schema 匹配结果与评估。
- **形式化要点**：以不同上下文量的 prompt 模板为变量做受控实验；具体 prompt 设计见原论文 🔧。
- **理论性质/保证**：实验研究，无理论保证（🔧 原文以经验为主）。

## 4. 实验结论（概览）
- 对比基线：字符串相似度基线。
- 数据集：新建健康领域基准 + 考察多维度指标。
- 指标：匹配质量、验证成本、决断力、互补性。
- 结论方向（摘要已给）：
  - 匹配质量会因「上下文太少」和「上下文太多」而都受损。
  - 总体上，使用**更新的 LLM 版本会提升决断力**。
  - 找到了**验证成本可接受**、且能识别「大量真实语义匹配」的 task scope。
  - LLM 有潜力 **bootstrap（启动）** schema 匹配流程，仅凭字段名与描述、无需数据实例即可辅助数据工程师提速。
  - 🔧 各 task scope 精确指标数字查原论文 Table/Figure 后补。
