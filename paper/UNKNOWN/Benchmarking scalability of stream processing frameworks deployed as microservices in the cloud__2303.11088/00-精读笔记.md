## 一句话总结

"流处理框架跑在 Kubernetes 微服务里"是新潮流，但谁扩得动？作者用 740+ 小时、最多 110 个微服务实例、每秒 100 万条消息的实验测了 5 个框架（Flink、Kafka Streams、Samza、Hazelcast Jet、Beam）：**资源给足大家都能近线性扩展**，但"扩容速率"差别巨大，且没有绝对赢家；用 Beam 抽象层在任何场景都更费资源。

## 0. 给新手的阅读前置（背景知识地图）

- **大问题**：数据密集型系统正从"独立流处理集群"转向"微服务 + Kubernetes"的部署形态。选型要看：负载涨了，加资源（横向加实例）能不能线性换来吞吐？
- **为什么难**：可扩展性受制于框架内部并行模型、状态管理、反压机制与云资源编排，因素交织；跨云（公有/私有）与跨框架的公平对比需要严格的实验设计。
- **主流做法对比**（本文评测的 5 框架）：

| 框架 | 一句话画像 |
|------|-----------|
| Apache Flink | 功能最全的流处理引擎，状态管理强 |
| Kafka Streams | 嵌入应用内的轻量流库，依赖 Kafka |
| Apache Samza | 老牌 Kafka 生态流处理器 |
| Hazelcast Jet | 内存数据网格上的流引擎 |
| Apache Beam | 统一编程抽象，跑在 runner 之上 |

- **本文属于哪类**：系统性基准评测（非新系统提出）。
- **必须先懂的名词**：
  - **可扩展性（scalability）**：资源翻倍时吞吐能否跟着翻倍（理想=线性）。
  - **微服务部署**：把处理逻辑拆成独立小服务，由 Kubernetes 编排伸缩。
  - **SUT 与资源供给速率**：被测系统与"加多少资源能维持多少吞吐"的斜率。

## 1. 问题背景与动机

- 前人工作：流处理框架基准多为独立集群形态；微服务化部署形态下 5 大框架的横向对比缺失。
- 未解决的问题：
  1. 微服务 + K8s 形态下各框架能否线性扩展、扩容斜率多少；
  2. 用 Beam 抽象层（一次编写多处运行）是否要付出资源代价；
  3. 公有云与私有云的结论是否一致。

## 2. 核心方法

- 类比：让 5 位长跑选手同场加量训练——跑道（K8s 集群）相同、补给（云资源）可控，记录每人"每加一分训练量能多跑多少"，得出耐力曲线。
- 具体做法（输入 → 操作 → 输出）：
  1. 在 Google Cloud 与私有云的 Kubernetes 集群上部署 5 个框架的微服务化 SUT；
  2. 逐级增加实例数（最多 **110 个并发微服务实例**）与负载（最高 **100 万条消息/秒**），累计 **740+ 小时**实验；
  3. 记录吞吐-资源曲线，量化近线性程度与扩容速率差异。
- 输出：跨框架、跨云的可扩展性排名与选型结论。

## 3. 变体 / 工程版

- 基准工具 **Theodolite** 已开源，可用于对自家负载做同款实验（含 SUT 打包与编排）。

## 4. 实验结论（概览）

- 对比设置：5 框架 × 双云环境 × 多级资源/负载。
- 结论方向（摘要明确给出）：
  - 资源充足时，**所有框架均近似线性可扩展**；
  - 但各框架**应对负载增长所需加资源的速率差异显著**；
  - **不存在绝对最优框架**，排名取决于具体用例；
  - **用 Beam 作抽象层在任何用例下资源需求都显著更高**；
  - **垂直扩展**（加大单实例规格）可作为横向扩展的补充手段；
  - 🔧 各框架吞吐-资源曲线与具体斜率查原文图表后补。
