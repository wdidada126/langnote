## 一句话总结
自动生成的 SQL 复杂查询常出错，而不会 SQL 的用户又没法检查修改。STEPS 的思路是：让模型**先用自然语言一步步解释自己要怎么查**，用户像批改作文一样直接改那些错掉的步骤，系统再按改好的步骤重新生成 SQL——不懂 SQL 的人也能修好查询。

## 0. 给新手的阅读前置（背景知识地图）

**子方向解决什么大问题**：Text-to-SQL 生成的查询有错时，普通用户既看不懂 SQL、也没有可靠手段纠错。这一子方向研究**人机交互机制**，把「纠错」从读代码变成改解释。

**为什么难**：
- 复杂查询（多表连接、嵌套）错误率高，一次性生成的准确率有天花板；
- 错误修复需要「用户能看懂 + 系统能落实」的中间表示——太技术化用户看不懂，太口语化系统没法精确执行。

**几类主流解法（表格）**：

| 路线 | 直觉做法 | 代表 |
|------|---------|------|
| 生成后自动校验 | 执行结果、重排序、自一致性 | 各类 rerank/execution-feedback 方案 |
| 提问式澄清 | 系统主动问用户歧义点 | 澄清问句类工作 |
| 可编辑解释式 | 展示中间推理步骤，让用户直接改 | **本文 STEPS** |

**本文属哪类**：可编辑解释式，核心是把「step-by-step reasoning」从纯 prompt 技巧升级为**双向交互界面**。

**关键名词直觉解释**：
- **Step-by-step explanation（逐步解释）**：把「如何从问题到 SQL」拆成若干中间步骤，每步用自然语言描述（类似思维链，但给用户看、也供用户改）；
- **Editable（可编辑）**：用户可直接在界面上增删改这些步骤文本；
- **重生成（regeneration）**：系统以修改后的步骤为条件重新生成 SQL，使编辑落实为查询修正。

## 1. 问题背景与动机

**前人工作简述**：关系数据库无处不在，但大量用户不熟 SQL；自动 Text-to-SQL 技术已有长足进步，但针对非专家用户的「验证 + 修正」环节长期薄弱。已有交互类工作（如澄清式问答）试图解决歧义，但修复能力有限。

**前人的缺陷（逐条，摘要明确给出两点，并延伸出第三点）**：
1. **复杂查询错误率高**：即便 SOTA 方法，在复杂查询上仍频繁出错；
2. **缺少灵活的验证/修正手段**：用户没有一种不依赖 SQL 知识的方式去确认「生成的查询是不是我想要的」并加以修改；
3. **错误定位困难**：SQL 是一整段黑盒输出，用户即使知道结果不对，也说不清哪一环错了。

## 2. 核心方法

**最直观类比**：翻译官先给你看他整理的「翻译提纲」（第一步：找订单表；第二步：按月份分组；第三步：只统计上海），你发现第二步理解错了，直接在提纲上改成「按季度分组」，翻译官据此重新产出正式译文（SQL）。你全程不需要会写 SQL。

**具体做法（输入 → 关键操作 → 输出）**：
1. **输入**：用户自然语言问题 + 数据库；
2. **逐步解释生成**：模型先把问题分解为一系列中间步骤（自然语言描述的查询计划）；
3. **用户编辑（核心交互）**：用户在界面上查看步骤，对理解错误的步骤直接编辑（改表述、删错步、补漏步）；
4. **重生成**：以编辑后的步骤序列为输入，重新生成最终 SQL；
5. **输出**：修正后的 SQL 查询与执行结果。

**形式化要点**：可视为两段式语义解析——「问题 → 步骤序列 → SQL」，第二步以第一步的输出为条件；用户编辑相当于对隐变量（查询计划）的直接干预。

**理论性质/保证**：无形式化理论保证；以多数据集实验 + 24 人用户研究验证有效性（见下节）。

## 4. 实验结论（概览）
- **数据集**：多个 Text-to-SQL 数据集（含 Spider 类复杂查询基准 🔧 名单查原论文）；
- **对比基线**：多个 SOTA 自动生成方法（无交互版本）；
- **指标**：SQL 生成质量指标 + 24 人用户研究（任务完成度、错误修复效果等 🔧）；
- **结论方向**：在用户参与编辑的前提下，该方法能取得**优于多个 SOTA 方法**的表现；用户研究表明非专家用户借助步骤编辑可以成功修复错误查询。
