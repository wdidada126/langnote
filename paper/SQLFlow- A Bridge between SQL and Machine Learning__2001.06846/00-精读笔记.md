## 一句话总结
SQLFlow 让数据工程师用熟悉的 SQL 就能写完整的机器学习工作流——它不强改各数据库的 SQL 方言，而是作为「桥」架在 MySQL/Hive/MaxCompute 等数据库与 TensorFlow/XGBoost/scikit-learn 等 ML 引擎之间，并把 SQL 程序编译成可在 Kubernetes 上容错执行的云原生工作流；已在蚂蚁、滴滴、阿里等工业场景落地。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：工业 AI 系统多是端到端 ML 工作流（推荐、BI），但 ML 代码与数据库/SQL 生态割裂，开发效率低。
- 为什么难：不同数据库有不同 SQL 方言；ML 引擎多样；要让「写 SQL 的人」也能训练/预测模型，需要无缝衔接与云原生执行。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 扩展 SQL 方言 | 部分系统 | 改方言支持 ML | 与多库/多引擎难兼容 |
| 桥接层 | 本文 SQLFlow | 不改方言、桥接多库多引擎 | 兼容好、需解析协作 |
| 笔记本/ pipeline | 通用 ML 平台 | 独立写流程 | 与 SQL 脱节 |

- 本文属哪类：数据库与 ML 引擎之间的「桥接/编译」层。
- 2-3 个必懂关键名词：
  - SQL 方言（dialect）：不同数据库（MySQL、Hive…）略有差异的 SQL 语法。
  - Collaborative Parsing（协作解析）：SQLFlow 扩展语法时与各 SQL 方言兼容解析的算法。
  - Kubernetes-native Workflow（云原生工作流）：把 SQL 程序编译成可在 K8s 上容错、可部署执行的流程。

## 1. 问题背景与动机
- 前人工作简述：一些数据库系统通过扩展自身 SQL 方言支持 ML。
- 前人缺陷/未解决问题（逐条）：
  1. 方言割裂：改自身方言难以兼容 MySQL/Hive/MaxCompute 等多种系统。
  2. ML 生态难接入：训练/预测常与数据库分离，开发割裂。

## 2. 核心方法
- 最直观类比：SQLFlow 像一个「万能转接头」——你用惯常的 SQL 写指令，它一边兼容各种插座（数据库方言），一边连到各种电器（ML 引擎），再把整件事编排成可上云跑的流程。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：带有 ML 扩展语法的 SQL 程序（训练/预测/特征处理）。
  2. 桥接多系统：兼容 MySQL、Hive、MaxCompute 等数据库与 TensorFlow、XGBoost、scikit-learn 等 ML 引擎。
  3. 协作解析算法：小心扩展 SQL 语法，使其能在多种方言下工作。
  4. 编译上云：把 SQL 程序编译为 Kubernetes 原生的容错工作流以便云部署。
  - 输出：可在云上容错执行的端到端 ML 工作流。
- 形式化要点：核心是「最小方言侵入 + 协作解析 + 云原生编译」；支持监督/无监督、深度/树模型、可视化解释、数据处理与特征抽取（🔧 细节见论文）。
- 理论性质/保证：无理论最优性保证；贡献在系统与工业落地。
