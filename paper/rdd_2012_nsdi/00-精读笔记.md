## 一、背景与它回应的问题

### 1.1 时代前提：迭代式负载把 MapReduce 的"落盘纪律"打成瓶颈

2010 年前后的两类新负载暴露了 Hadoop 式数据流的结构性不适：

1. **机器学习迭代**（逻辑回归、k-means、矩阵分解）：同一数据集被扫过几十轮，每轮只改一点状态。MapReduce 每轮都要把中间结果写回 HDFS（3 副本）、下一轮再读回来——数据复制成了"每次迭代重新交一遍的过路费"。
2. **交互式查询**：人手一个 shell 探索数据，每次查询复用上一轮的中间集合；批排队的分钟级延迟与"秒级改一行再看"的工作流根本错配。

当时的补救方案各有致命伤：Hadoop + named pipe/流式常驻（如 Twister 类）丢失了容错与通用性；Dryad 用文件连阶段，同样是"中间结果必须物化到分布式存储"；VoltDB 类内存并行数据库假定硬件可靠、以副本+2PC 容错，工作集被内存容量和复制写吞吐双重钳制。**共同缺口：没有一种抽象能既驻留内存、又天然容错、还允许应用随意重组算子。**

### 1.2 答案一句话

RDD：**只能经确定性的转换集创建、可分区、不可变、容错的内存对象集合**。容错不靠副本检查，靠 **lineage（血缘）**：记住"从哪个稳定存储、经哪串确定函数、怎么分区"的完整谱系，内存数据丢了就重算——于是"内存不是需要保护的资产，而是可失效可重建的缓存"。三个设计支柱（论文 §2）：**通用执行模型（任意算子组合）、高层抽象的容错（一次抽象接管，应用零协议）、基于数据位置的调度**。

## 二、核心设计精读

### 2.1 RDD 是什么：一份五件套元数据 + 一个计算函数

论文给 RDD 的"接口契约"由五类元数据构成，全部由框架捕获、供调度器使用：

```
① 表示(representation): 它是哪个变换作用于哪些父 RDD 得到的(血缘边)
② 函数: 对单个分区执行 compute(Partition,  BlockContext): Iterator
③ 依赖(dependencies): 对每个父分区, 子 RDD 如何求值(窄/宽+分区谓词)
④ 分区信息(partitioner): 如 HashPartitioner / RangePartitioner
⑤ 亲和位置(preferredLocations): 每个分区希望在哪台节点计算(供就近调度)
```

关键约束：**不可变 + 确定性**。同一个分区在任何节点重算结果相同，lineage 才敢充当恢复剧本。"值对框架不透明、结构对框架透明"——这是它区别于数据库表（结构也透明）与对象缓存（两者都不透明）的中间态。

### 2.2 转换 / 行动：懒执行撑起整张 DAG

算子分两族（论文 §3.2 的示例签名，Scala 味）：

- **转换（transformation）**：`map / filter / flatMap / union / sample / join / groupByKey / sortByKey / distinct`——只登记"待做的转换"，不触发计算；
- **行动（action）**：`reduce / collect / count / first / saveAsTextFile / saveAsHadoopFile`——真正请求结果，触发作业调度。

```
val lines = sc.textFile("hdfs://…/big.log")     // RDD① 源自稳定存储
val errors = lines.filter(_.contains("ERROR")) // RDD② 窄依赖, 血缘链①→②
errors.cache()                                  // 声明: 之后要复用
val pairs = errors.map(x => (keyOf(x), 1))      // RDD③ 窄
pairs.countByKey()                              // 行动: ④ 宽依赖(join by key)触发作业
```

`cache()` 体现"内存=缓存"的机制面：首次物化后驻留（可配 MEMORY_ONLY / 序列化 / 溢出到盘 / 仅存谱系），内存吃紧按 LRU 淘汰——**淘汰不报错**，因为血缘保证任何分区随时可重算。`checkpoint(dir)` 则把 RDD 落盘并**剪断血缘**，用于长链迭代（ML 的收敛循环）与 shuffle 链过长时封顶恢复成本。

### 2.3 窄依赖 / 宽依赖与 stage 划分（本文最常被面试的部分）

```
窄依赖(narrow):  子 RDD 的每个分区 → 至多固定(小)数量父分区
   map/filter/union/sample(逐分区)、带本地性提示的 join(cogroup 的退化形)
   ⇒ 可在同一节点流水线执行, 父分区永不"同时被多子需要跨机聚合"
宽依赖(wide):   子 RDD 的每个分区 → 依赖父 RDD 的"大量/全部"分区
   join/groupByKey/sortBy/distinct(默认)
   ⇒ 必须跨节点搬运数据(shuffle), 父各分区产出必须先完整物化
```

**调度规则**：从行动算子逆向遍历血缘图，**遇宽依赖切 stage，窄依赖进 pipeline**：

```
buildStages(rdd):                      # 伪码(按论文 §4/Fig.4 思想整理)
  stage = new Stage(rdd)
  for (parent, pred) in rdd.dependencies:
      if dependency(parent, rdd) is narrow: stage.parents += buildStages(parent).merge
      else:                                 schedule(new Stage(parent))  # shuffle 边界
  return stage

执行: 每个 stage 内一分区=一任务, 任务把 pipeline 中全部窄变换
      融合成一次遍历(无中间物化!); 上游 stage 落 shuffle 文件,
      下游 stage 的 map 任务按 partitioner 范围拉取(可本地优化)
```

与 Dryad/MapReduce 的本质差别在此浮出：MapReduce 把"阶段"固化为人格化的 map/reduce 两级、中间结果一律写分布式存储；RDD 的 stage 是**派生的**（由依赖类型自动划出），pipeline 内部**零物化**，shuffle 文件只是 stage 间的临时物流而非"数据集"。

### 2.4 容错精读：丢了什么，赔什么

论文 §5（含 Fig.4-6 的例子）给出一张按"位置×故障范围"的赔付表，复述其逻辑：

```
情形A 某节点 lost 一个 cache 分区(窄依赖链):
    只重算该分区; 因为窄依赖, 它的父分区只服务于它一个
    → 若父在别节点还活着且只被它依赖? 不会, 窄=一父至多入几个子,
      重算范围=本分区谱系的局部, 无需全图
情形B 节点整体挂(其上任一 RDD 的多个分区+其 shuffle 输出):
    这些 RDD 的下游按 lineage 重建各自需要的分区;
    非持久化(未 cache)的 RDD 只有子受影响 → 子重算时顺带重算
情形C 宽依赖处丢 shuffle 输出分区:
    该 map 分区被多个下游 reduce 拉取 → 必须重算这个 map 分区
    (不是重算整个上游 stage, 粒度仍是分区级)
封顶: checkpoint(π) 后, 最坏只需从最近检查点而非最初数据源重算
```

两条隐含设计：① **恢复以分区为单位**，且分区是窄依赖下"自洽重算的最小封闭单元"——这正是窄依赖在容错维度上的第二次回报（第一次是流水线）；② shuffle 文件不是容错数据，它靠"确定性重算 map 任务"保护，而非靠复制——因此不需要 HDFS 3 副本的 3× 存储，也解释了为什么 RDD 常态"零副本"。

### 2.5 与"数据放置感知调度"的咬合

preferredLocations 把 HDFS 块位置/对象缓存位置带进血缘图；调度器优先把任务派给"数据已在手"的节点，其次"同机架"。宽依赖之后位置信息如何传播？论文答：**默认按分区的父分区位置集合传播，允许应用自定义规则**（如 join 后按一侧继承、或广播给两侧）。配合推测执行（straggler 副本竞速）与延迟物化，"内存驻留 + 就近计算 + 丢了重算"三件事合成一个自洽的循环——这是 RDD 作为**系统**而非单个技巧的地方。

### 2.6 一次作业的完整解剖（把三根支柱串起来）

仍以 §2.2 的例子跑 `pairs.countByKey()`，按论文机制走一遍（流程为机制复述，非原文示例）：

```
1. driver 侧: action 触发 → 从 RDD④ 逆向遍历血缘,切出 stage 图:
     S1: textFile→filter→map 全窄依赖 → 合成一个 pipeline stage
     S2: countByKey 前的按键重分布 → 宽依赖 → shuffle 边界
2. 调度器给 S1 每个 HDFS 块分一个任务, 按 preferredLocations 派
   到持有该块的节点; 任务内 读块→filter→map 一次遍历,零中间物化,
   产出按键分区后的 shuffle map 输出(本地磁盘, 非容错数据!)
3. S2 的 reduce 任务按 partitioner 范围跨网拉取 map 输出分片,
   做 map-side 预合并后的计数, 结果回 driver 汇总
4. 故障切片: 若某节点在 S1 中途挂掉 →
   其在途任务重新派到他节点(输入在 HDFS, 天然可重读);
   若挂在 S1 完成、S2 拉取中途 → 丢失的 map 输出分区按谱系
   只重算那几个分区(cache 过的上游同理), 不回放整个 stage
```

三个机制在流程中显形：懒执行让 stage 图在 action 前完整可见（才能全局融合 pipeline）；血缘把"故障恢复"化归为"分区级重放的函数求值"；shuffle 文件的非容错身份，正是"内存/本地盘都是缓存"论断在运行时的具体形状。

### 2.7 与近邻系统的构件级对照

| 构件 | RDD | MapReduce | ShareNothing MPP |
|---|---|---|---|
| 中间结果 | pipeline 零物化 / stage 间本地文件 | 每阶段落 HDFS | 落盘或全复制 |
| 容错单位 | 分区（重算） | 任务（重算，输入可靠） | 事务（回滚+副本切换） |
| 一致性协议 | 无（不可变+确定性） | 无 | 2PC+锁 |
| 编程模型 | 任意算子组合+复用 | 固定 map/reduce 两级 | SQL/存储过程 |
| 故障假设 | 常态化 | 常态化 | 罕见且可靠硬件 |
| 内存角色 | 一等缓存（LRU 可淘汰） | 基本无（流式缓冲） | 工作集（须被保护） |

## 三、实验与工程取舍

论文 §6/§7 的实验在 4–200 节点的小规模集群（本地 + EC2）上对比 Hadoop 实现（下述加速比按论文图表口径转述，**具体刻度未逐字复核，本笔记以数量级表述并在核实记录声明**）：

1. **逻辑回归（10 轮迭代）**：Spark 在 4 节点小集群上对 Hadoop 呈**约 20 倍**量级优势，且优势主要来自"数据集缓存在内存 + pipeline 内无物化"，而非计算本身——节点越少、每轮复用越强，优势越明显。
2. **k-means / naive Bayes**：200 节点 EC2 集群上对 Hadoop 呈**数倍到约一个数量级**的加速（论文强调 Spark 的加速随集群规模"温和衰减"，因带宽成为主约束时两边趋同）。
3. **PageRank（迭代图算法）**：Spark 迭代间延迟降到**秒级**，Hadoop 每轮都要重读全图——交互式工作流与批工作流的分水岭案例。
4. **多查询复用（MLlib 应用 + Shark/SQL 前身场景）**：首个查询把数据集物化进缓存后，后续查询呈**数倍到十倍级**加速，验证"cache 命中即免费"的摊销模型。
5. **容错开销实测**：注入节点故障，"只重算损失分区"的恢复时间远小于 HDFS 复制式重建（无数据搬运）；代价是计算密集 RDD 的重算可能比读副本慢——论文诚实给出"lineage vs replication"权衡图（检查点周期是这条曲线的旋钮）。

深层取舍清单：

| 取舍点 | 选择了 | 放弃了 | 换来的 |
|---|---|---|---|
| 容错机制 | lineage 重算（零副本） | 故障瞬间的确定性低延迟 | 内存即缓存、免 3× 存储与复制写、故障恢复无数据搬运 |
| 数据可变性 | 不可变 + 确定性变换 | 原地更新/细粒度写 | 可重算性、缓存无失效协议、谱系即审计 |
| 抽象粒度 | 分区级集合（粗于行事务） | OLTP 式随机读写一致性 | ML/ETL 负载的通用表达与流水线 |
| 中间状态 | stage 间 shuffle 文件 + pipeline 零物化 | 阶段间全局检查点 | 迭代复用 + 窄依赖融合的执行效率 |
| 容错边界 | 只保证 RDD 容错，不保证算子副作用 | 任意程序的事务语义 | 应用须幂等（saveAs* 等约定） |
| 元数据位置 | driver 单点持有 RDDGraph | 元数据的水平扩展 | 调度决策全局可见、实现简单（后续版本再优化） |

## 四、与相关工作对比

- **vs ShareNothing 并行数据库（论文 §8 的相关工作章，任务书所称"§7"按正式发表版章节为准——精读时请直接对照 "Related Work" 一节）**：论文的批评结构是：传统 MPP 数仓假定**网络与盘可靠**，于是用"2PC + 全副本持久化"做容错，把应用削成"持久数据上的无状态事务"。后果有三：① 中间结果/工作状态也必须持久化或复制 → 内存不能当缓存用，工作集被内存上限与复制写吞吐双重钳制（点名 VoltDB 的写吞吐上界 = 最慢副本）；② 只适合"短事务、可预定义"负载，迭代/即席程序无处安放；③ 假定硬件可靠与"故障罕见"在云/大集群上不再成立。RDD 的赌注相反：**故障常态化，用重算代替复制，把内存降级为可丢弃缓存**，从而让"程序作为对中间集合的任意重组"合法。两者在"谁怕节点失效"这个问题上背道而驰。
- **vs Hadoop/MapReduce（课程资料：[../../mit6.824/mapreduce.pdf](../../mit6.824/mapreduce.pdf)、[../../courses/并行与分布式系统/MIT6.824/notes/L02-MapReduce.md](../../courses/并行与分布式系统/MIT6.824/notes/L02-MapReduce.md)）**：MR 的容错同样靠"重算任务"（输入在可靠存储 + 任务确定），RDD 把它推广到**内存驻留的多阶段图**：MR 每阶段强制落可靠存储，RDD 只在 shuffle 边界临时物化。可视为"把 MR 的容错哲学认真贯彻到内存"的产物。
- **vs Dryad/DryadLINQ、GraphLab、FlumeJava（同节相关）**：Dryad 文件连 DAG（无通用共享抽象）、GraphLab 图专用+双缓冲 checkpoint（容错是专用协议）、FlumeJava 有类似"谱系重算"但无交互式/缓存语义。RDD 的贡献是把这些零件**收敛为一个带一等抽象（血缘+分区+位置）的框架**，应用不再感知容错协议。
- **vs Bigtable（本仓库精读：[../bigtable_2006_osdi/00-精读笔记.md](../bigtable_2006_osdi/00-精读笔记.md)）**：同代两种数据观。Bigtable：计算向数据移动，数据必须住在被租约保护的存储里；RDD：数据向计算驻留，存储只是血缘的根锚点，中间态丢了就重算。前者牺牲内存管理换 serving 一致性，后者牺牲可变性换迭代自由——合读可见 2006–2012 年"计算/状态"耦合度被逐步解开的全过程。
- **vs Snowflake/湖仓（本仓库精读：[../doi_10.1145_2882903.2903741/00-精读笔记.md](../doi_10.1145_2882903.2903741/00-精读笔记.md)）**：RDD 的"内存=可重建缓存"与 Snowflake 的"SSD 缓存=不可变文件块、零失效协议"是同一枚硬币的两面（都靠不可变性取消缓存一致性），但方向相反：前者用缓存加速**计算图**，后者用缓存加速**查询**；十年后云数仓走向"对象存储 + 本地 SSD 缓存 + 无状态计算"，等于承认"共享内存集群"输给了"共享不可变数据的存算分离"——这条判决线正是 §六争议的核心。
- **书目互链（均已验证存在）**：[../../book/Spark大数据分析与实战.md](../../book/Spark大数据分析与实战.md)；[../../book/Use_Iceberg_with_Spark/01-为什么要用Iceberg搭配Spark.md](../../book/Use_Iceberg_with_Spark/01-为什么要用Iceberg搭配Spark.md)（RDD 时代之后"表格式接管可靠性"的现状样本）；[../../courses/并行与分布式系统/MIT6.824/notes/L17-Spark与RDD.md](../../courses/并行与分布式系统/MIT6.824/notes/L17-Spark与RDD.md)、[../../courses/并行与分布式系统/MIT6.824/notes/L18-数据并行谱系.md](../../courses/并行与分布式系统/MIT6.824/notes/L18-数据并行谱系.md)（谱系一讲把 RDD 放进 MapReduce→Spark→Dask 的演化轴）；[../../book/Design Data-intensive Applications.md](../../book/Design%20Data-intensive%20Applications.md)（DDIA 派生/分区/容错章可作第二遍读物）。

## 五、关键术语中英对照

| 英文 | 中文 | 一句话含义 |
|---|---|---|
| Resilient Distributed Dataset (RDD) | 弹性分布式数据集 | 不可变、分区、容错的内存集合抽象 |
| lineage | 血缘 | 从稳定源出发经确定变换的全谱系，容错的剧本 |
| driver | 驱动节点 | 捕获 RDD 元数据（RDDGraph）并调度的主节点 |
| partition | 分区 | 并行与重算的最小单元 |
| transformation / action | 转换/行动 | 登记待做计算 vs 触发执行的算子两族 |
| narrow / wide dependency | 窄/宽依赖 | 子分区至多依赖少数父分区 vs 依赖大量分区 |
| stage | 阶段 | 以 shuffle 边界切出的流水线任务组 |
| pipeline | 流水线 | 窄依赖算子融合、中间结果零物化 |
| shuffle | 洗牌 | 宽依赖引发的跨节点按键重分布 |
| cache / persist | 缓存/持久化 | 物化到内存(可选序列化/溢盘)供复用 |
| checkpoint | 检查点 | 落盘并剪断血缘，封顶重算链 |
| storage level | 存储级 | MEMORY_ONLY/DISK/序列化等缓存形态 |
| partitioner | 分区器 | Hash/Range 等决定记录落哪个分区 |
| preferred locations | 亲和位置 | 分区期望的计算节点，就近调度依据 |
| lazy evaluation | 懒执行 | 转换不即时算，行动触发才构建 DAG |
| speculation | 推测执行 | 慢任务起副本竞速，取先完成者 |
| determinism | 确定性 | 同输入同结果，重算等价于读副本的前提 |
| shared-nothing (MPP) | 共享无存并行数据库 | 论文对照批判的传统阵营 |
| two-phase commit | 两阶段提交 | MPP 容错阵营的协调代价代表 |

## 六、批判与延伸

**批判性阅读：**

1. **"内存不是瓶颈，而是缓存"是有条件的论断**。它成立的前提：① 工作集能进（或溢到盘后仍高命中）内存；② 重算成本 < 读副本成本（计算轻、复用高的负载反而不利——纯扫描型作业 Spark 相对 Hadoop 并无神话）；③ 故障率不至于让长血缘链频繁重放。论文自己在 §7 承认带宽是规模增长后的主约束。
2. **后续争议（外围信息，未逐条查证，引用需谨慎）**：Stonebraker 阵营 2014 年前后公开质疑 Spark "一技之长（one-trick pony）"；学界有对 Spark SQL 性能逐项解剖的论文（如 "May the Source Be with Spark" 一类评论文），Databricks 以 "progressive parallelism" 等立场回应；工程侧的"打脸式演化"同样诚实：JVM 对象缓存的 GC 灾难催生 Tungsten（2015，堆外内存+码生成），"内存不可变集合"不适合机器学习之外的可变状态，参数服务器/特征平台另起炉灶，交互式缓存被 Alluxio/Tachyon、以及 Delta/Iceberg 这类"文件级缓存"接管。
3. **lineage 容错的暗面**：确定性假设不容许非确定源（读外部实时库、随机数未固定种子即破功）；重算是**串行化在故障之后**的延迟长尾；driver 单点持有元数据曾是百万分区规模的实际瓶颈（后续版本用 DAG 序列化/本地性简化等工程修补）。
4. **"零副本"不等于零成本**：跨版本对比时，Hadoop 阵营的 3× 存储被换成重算的 CPU 与故障放大窗口；当集群进入"计算/存储都按独立商品计费"的云上形态（Snowflake/湖仓路线），"重算比复制便宜"的天平重新倾斜——RDD 的取舍高度依赖"计算比存储便宜"这一 2012 年经济假设。
5. **写作视角**：论文案例全选对 Spark 最有利（小集群、迭代、高复用），对最不利的（单次全扫、宽依赖主导、shuffle 密集）着墨极少；读实验章节要带着"负载画像"的怀疑。

**延伸：**

- **RDD 之后的抽象下沉**：Dataset/DataFrame（2016）把不可变 RDD 降级为"优化器的物理计划中间层"，API 层退出主流——论文五件套元数据中最长寿的是 partitioner 与 preferredLocations（今天仍是 Spark 调度器输入）。
- **血缘思想的扩散**：可重算谱系作为容错范式早已溢出 Spark——流处理的状态后端+重放、工作流引擎（Airflow 的 task 幂等重跑）、训练平台的 checkpoint、乃至数据库的"不可变文件+清单"（本仓库 Delta 精读 [../doi_10.14778_3415478.3415560/00-精读笔记.md](../doi_10.14778_3415478.3415560/00-精读笔记.md)）都是同族。
- 与本仓库 Bigtable/RDD 双笔记对读（见 §四末条），可完成一次"以存储换计算 vs 以计算换存储"的对照实验式阅读。

## 七、一页总结（复习卡）

- **问题**：迭代 ML 与交互查询需要中间态常驻内存，而 MR 强制逐轮落盘、并行 DB 强制持久化+2PC，都不给"可容错的内存中间态"留位置。
- **方案**：RDD=不可变分区集合 + 五件套元数据；transformations 懒建图 / actions 触发；窄依赖融合成 pipeline、宽依赖切 stage（shuffle 为界）；容错靠 lineage 重算（分区粒度）+ checkpoint 封顶，内存降格为可淘汰缓存；调度吃 preferredLocations 做就近放置。
- **所得**：迭代/复用负载数量级加速、零副本免复制流量、应用侧容错代码为零、shuffle 文件可丢。
- **所欠**：确定性/幂等约束、driver 单点、重算长尾、对低复用负载无优势、副作用不受保护。
- **地位**：大数据系统"以计算换存储"路线的顶点；血缘/不可变/存算分离三大观念经由它和后续湖仓路线渗入整个数据基础设施。

## 九、思考题（5 道）

1. 论文称 RDD 与"分布式共享内存（DSM）"有本质区别。请构造一个需要原地更新的应用（如在线特征存储），说明为什么它在 RDD 上必然退化为"每次全量重算 + cache 换代"，而 DSM/Bigtable 类系统各自怎么解（提示：不可变+确定性 vs 租约+可变，两种一致性的成本重心不同）。
2. 长迭代作业（1000 轮梯度步）的血缘链极长。请推导检查点周期 t 与"单节点故障的期望恢复时间"的关系式（设每轮重算成本 c、故障概率 p），并说明为什么 ML 实践中往往取"每若干轮才 checkpoint"而不是"每轮"——这条曲线在计算成本 c 很大时会怎么变？
3. 窄依赖让"只重算损失分区"成立。请找出论文规则的一个漏洞：`union` 是窄依赖，但如果一个子分区同时依赖两个父 RDD 的**同位置**分区，某节点故障时重算范围如何界定？框架要保证什么才能不让重算退化为全链？（提示：分区索引对齐与血缘边的"分区谓词"字段。）
4. ShareNothing 数仓用"每分区 3 副本 + 快速切换副本"实现约秒级恢复，RDD 用重算实现恢复。给出一个参数量化两者（故障率 λ、集群大小 N、数据集大小 S、扫描带宽 B、重算 CPU 单价），并指出在什么参数区间"内存=缓存"论断翻转成"内存必须被复制"——这能否解释今天云上 GPU 训练 checkpoint 全面回潮复制/对象存储的现象？
5. 对照本仓库 Bigtable 笔记思考题 5：Snowflake 用"不可变文件 + 缓存键"免掉失效协议，RDD 用"不可变集合 + 血缘"免掉缓存保护。请再比较第三种：Bigtable 的 SSTable 同样不可变，却仍需租约——"不可变性"究竟免除了什么、又免除不了什么？（答题框架：不可变性免除**读路径**的一致性；免除不了**写路径/所有权**的仲裁。）

## 十、阅读方法与常见误读提醒

1. **别把 RDD 读成"更快的 MapReduce"**：加速比只属于"高复用/迭代"画像的负载；单次全表扫描的 ETL 上 Spark≈Hadoop（论文自己给出趋同图）。把"Spark 快"当普适定理是最常见的误读。
2. **lineage ≠ checkpoint，二者是互补旋钮**：面试常把"血缘重算"说成 RDD 的容错"唯一"机制；论文的真实立场是"默认血缘、长链加检查点"——恢复策略是一个带成本的谱系，不是一个点。
3. **"内存不是瓶颈"被过度引用**：原论文语境是"很多应用的**工作集**能进内存，故内存容量不该是系统的第一约束"，它既不是说内存无限，也不是说 IO 问题消失；把它当论战口号引用前先回到 §2/§7 的原文条件。
4. **任务书标题与正式发表版副标题不同**：检索/引用时用 "In-Memory Cluster Computing"（NSDI 版）；看到 ML Workloads 题名的 PDF 多是 2012-01 技术报告，章节编号与个别表述有差异（相关工作章的编号以 USENIX PDF 为准）。
5. **建议配套阅读**：先 MIT6.824 L17/L18 讲义建立执行图直觉 → 本文 §3–§5（抽象与容错机制）→ §8 相关工作章（对并行 DB 的批判原文比本笔记 §四更锋利）→ 最后读 Snowflake/Delta 笔记，看"内存缓存"观念在存算分离时代的变形。
