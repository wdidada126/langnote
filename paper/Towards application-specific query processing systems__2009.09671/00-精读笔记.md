## 一句话总结
传统数据库给一堆配置旋钮（knob）让你调，但**用户和数据地理分布**带来的架构级取舍（比如状态放在云端还是边缘）根本不是旋钮能调的。本文提出一种愿景：把查询处理拆成一个个可拼装的「查询处理单元（Query Processing Unit, QPU）」，让架构师按每个用例（per use case）组装出专用查询系统——并用一个「状态可灵活放在数据中心或边缘」的系统演示了这种做法，说明状态位置直接决定「响应时间 vs 结果新鲜度」的取舍。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：任何查询密集型应用都要把查询系统调到贴合自己的需求与负载。但「调」的层次通常只是参数，而真正影响体验的是**架构**——数据放哪、状态放哪、在哪计算。
- **为什么难**：
  - 用户与数据地理分布（geo-distribution）带来的取舍是**架构级**的，不是参数级的；
  - 边缘（edge）离用户近、响应快，但状态可能陈旧；数据中心（data center）状态新、一致性强，但往返延迟高；
  - 不同应用的答案不同，而通用数据库只有一套固定架构。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 参数调优 | 数据库 knobs、LlamaTune、GPTuner | 在固定架构上调参 | 上手快，天花板明显 |
| 地理分布式数据库 | Spanner、CockroachDB 系 | 用一致协议跨地域复制 | 强一致，延迟与成本有代价 |
| 边缘/雾计算 | 各类边缘数据系统 | 把计算推到靠近用户处 | 延迟低，一致性与运维复杂 |
| 可组装专用系统（本文） | Proteus / QPU | 用统一构件按用例拼装，并显式控制状态放置 | 表达力强，需重新设计系统栈 |

- **本文属于哪一类**：**可组装的专用查询系统（vision 型论文）**——提出抽象与架构愿景，并用一个演示系统证明其表达力。
- **必懂关键名词**：
  - **Query Processing Unit（QPU）**：本文提出的核心抽象——一个封装了**原子查询处理任务**的分布式构件，可作为积木拼装成完整查询系统。
  - **状态放置（state placement）**：决定查询系统把状态放在数据中心还是边缘；这个决定直接换来「响应时间 ↔ 结果新鲜度」的取舍。
  - **结果新鲜度（result freshness）**：查到的结果有多接近最新数据；把状态放边缘可以更快响应，但看到的数据可能更旧。

## 1. 问题背景与动机
- 前人工作简述：数据库系统通过查询处理子系统实现高效的查询式数据检索；设计查询密集型应用的关键环节是**把查询系统调到契合应用需求与负载特征**。
- 前人的缺陷 / 未解决问题（逐条）：
  1. **配置项覆盖不到架构级决策**：传统数据库提供的配置参数，**覆盖不到由用户与数据地理分布引发的设计决策与取舍**。
  2. **一套架构服务所有应用**：通用查询系统的架构固定，无法为单个用例定制。
  3. **状态放置不可控**：应用架构师无法自主决定「状态放在哪里」，而这恰恰决定了延迟与新鲜度的权衡。
  4. **缺少可组装的抽象**：没有像 QPU 这样的统一构件，让「拼装一个查询系统」变得可行。

## 2. 核心方法
- **最直观类比**：传统数据库像「买一台固定布局的成品厨房，只能调火候」；本文的愿景像「把灶台、水槽、冰箱做成标准模块（QPU），你按自家厨房形状自由摆放」——甚至连「冰箱放厨房里还是放楼下储藏室（状态放边缘还是云端）」都由你决定，代价与收益也一目了然。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：应用的需求（延迟目标、新鲜度要求、用户与数据的地理分布）+ 一组 QPU。
  2. **关键操作一：定义 QPU 抽象**。提出分布式抽象 Query Processing Unit，封装原子的（primitive）查询处理任务。
  3. **关键操作二：以 QPU 为积木组装查询系统**。展示如何用 QPU 作为 building block 拼装出完整查询系统。
  4. **关键操作三：架构师自主决定架构与状态放置**。应用架构师通过控制**查询系统的架构**与**其状态的放置**，构造出专门适配其用例的查询系统。
  5. **输出**：一个为特定用例定制、可部署的查询系统。
- **形式化要点**：核心是 QPU 这一抽象及其组合语义；关键设计变量 = QPU 的种类与组合拓扑 + 每个 QPU 的状态放置位置 🔧 具体形式化见原论文。
- **理论性质 / 保证**：🔧 摘要未给出理论保证（论文定位为 vision + expressiveness 演示）。

## 7. 2026 视角（🔧）
- 边缘计算、多云、数据主权合规让「状态放哪里」从学术问题变成了每个架构师都要回答的工程问题；本文提出的「按用例组装 + 显式状态放置」正是这一现实的理论先声。
- 同时，Serverless 数据库与「按 SLA/价格选型」的产品化趋势，把这种架构级取舍包装成了用户可见的选项。
- 「把查询系统拆成可组合单元」的思想，与后来的可组合数据系统（composable data systems）、以及数据流编排系统是一脉相承的。本节为趋势性判断 🔧。

## 8. 新手学习路线
- **10 分钟**：读摘要 + 第 0 节，记住两个关键词：**QPU（可拼装的查询处理单元）** 与 **响应时间 vs 新鲜度**。
- **30 分钟**：拿你熟悉的一个查询服务，画出它的数据流与状态位置，然后问自己：如果状态搬到离用户更近的地方，延迟会降多少？结果会旧多少？
- **进阶**：精读 QPU 的抽象定义与组合规则；思考「新鲜度」该如何量化（ staleness 指标）；对照 Spanner 与 Serverless 查询处理，比较「一致性优先」与「延迟优先」两条路线的代价。
