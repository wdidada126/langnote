## 一句话总结

针对大模型做 Text-to-SQL 时「单条生成质量不稳、风格单一」的问题，本文提出 **XiYan-SQL**：用**多生成器集成**产出多样且高质量的候选 SQL，配合自研的 **M-Schema（半结构化 schema 表示）**、「监督微调 + 上下文学习（ICL）」双路生成、**精修器（refiner）** 纠错、以及**候选选择器**，在 BIRD、Spider、SQL-Eval、NL2GQL 等多个基准上取得 SOTA（如 BIRD 75.63%、Spider 89.65%）。

## 0. 给新手的阅读前置（背景知识地图）

### 0.1 大模型做 Text-to-SQL 的现状
- 直接用 LLM（如 GPT 系列）把自然语言问题 + 数据库结构（schema）转成 SQL，已成为主流。
- 痛点：单次生成容易「一时失手」；不同提问方式/微调风格产出差异大。

### 0.2 本文四大核心概念
- **多生成器集成（multi-generator ensemble）**：不只生成 1 条 SQL，而是用多个「风格不同」的生成器各产出若干候选，再从中挑最好的，类似「多人投票 / 多稿择优」。
- **M-Schema**：作者提出的**半结构化 schema 表示方法**，比纯文本 DDL 更利于模型理解表结构。
- **ICL vs SFT**：ICL = 在提示里给几个示例（少样本）；SFT = 用标注数据微调模型。本文两者都用。
- **Refiner（精修器）**：对每条候选 SQL 做逻辑/语法纠错；**Selector（选择器）**：从候选里挑最优。

### 0.3 关键基准名词
- **Spider**：英文跨域 text-to-SQL 标杆；**BIRD**：更贴近真实、含噪声与大量数值的标杆；**SQL-Eval / NL2GQL**：其它评测（含图数据库查询 NL2GQL）。

## 1. 问题背景与动机

前人工作：
- LLM 在 text-to-SQL 上表现强，但**单生成器存在质量与多样性不足**的问题：一条生成若错就直接失败；不同方言/场景下单一样式未必最优。
- schema 表示方式（如何把表结构喂给模型）对效果影响很大，但缺乏统一好方案。

本文动机：用**多生成器 + 多样候选 + 精细挑选**提升稳健性与上限，并改进 schema 表示。

---

## 2. 核心方法：XiYan-SQL

### 2.1 直觉类比
像一家「SQL 写作工作室」：先有一份清晰的「数据库说明书」（M-Schema）；再让几位**写作风格不同的高手**（多生成器：有的擅长 ICL 模仿示例、有的擅长按规范微调写作）各自写几稿；然后**编辑**逐稿纠错（refiner）；最后**主编**挑出最准的一稿（selector）。多稿择优，比单人单次稳得多。

### 2.2 步骤
1. **M-Schema 表示**：把数据库 schema 转成半结构化表示，提升模型理解。
2. **双路生成（多生成器）**：
   - 一路用 **SFT** 训练多个「偏好不同」的模型，产出多样高质量候选；
   - 一路用 **ICL**，并设计基于**命名实体识别（NER）的示例选择**，避免只盯着实体。
3. **Refiner 精修**：纠正每条候选的逻辑/语法错误。
4. **Selector 选择**：微调一个选择模型，辨别候选 SQL 的细微差别，挑出最优。

### 2.3 核心思想与结果
- 通过「多生成器 + 多样候选 + 精修 + 优选」同时提升**质量与多样性**。
- 在多个方言数据集上验证了稳健性；报告 SOTA：BIRD 75.63%、Spider 89.65%、SQL-Eval 69.86%、NL2GQL 41.20%。
