## 一句话总结
图向量搜索（GVS，如 HNSW/NSG）因图遍历难以并行而难降延迟；Falcon 用 FPGA 硬件加速器（流水线算子 + 片上 Bloom filter 跟踪搜索状态）配合「延迟同步遍历（DST）」算法（放宽遍历顺序以填满加速器），在 FPGA 上实现比 CPU/GPU GVS 低最多 4.3×/19.5× 延迟、高最多 8.0×/26.9× 能效。

## 0. 给新手的阅读前置（背景知识地图）
- 这个子方向解决什么大问题：图向量搜索（GVS）用近邻图（如 HNSW、NSG）做近似最近邻（ANN）搜索，是 LLM 检索、搜索引擎、推荐系统的核心，目标是在线搜索延迟尽可能低。
- 为什么难：要在单次查询内并行（intra-query parallelization）降延迟，受限于 (a) CPU/GPU 硬件架构；(b) 图遍历本身难以并行。
- 几类主流解法（表格）：
  | 方法 | 代表 | 思路 | 优缺点 |
  |------|------|------|--------|
  | 软件 GVS | HNSW / NSG | 在图上贪心游走 | 质量高但难并行降延迟 |
  | GPU GVS | 各类 | GPU 并行 | 吞吐高但单查询延迟/能效受限 |
  | 本文 Falcon | FPGA + DST | 硬件加速 + 算法协同 | 低延迟、高能效 |
- 本文方法属于哪一类，与前身关系：属于图向量搜索的「硬件-算法协同设计」，前身是各类软件 / GPU GVS。
- 2-3 个必须先懂的关键名词（直觉解释）：
  - GVS（Graph-based Vector Search）：基于近邻图的向量检索。
  - DST（Delayed-Synchronization Traversal，延迟同步遍历）：放宽遍历顺序以最大化加速器利用率的图遍历算法。
  - 片上 Bloom filter：在 FPGA 上用 Bloom filter 跟踪已访问搜索状态，减少内存访问。

## 1. 问题背景与动机
- 前人工作简述：GVS 因高搜索质量/性能流行；但 intra-query 并行降延迟受硬件与图遍历本质困难限制。
- 前人 N 个缺陷/未解决问题（逐条）：
  1. 现有 CPU/GPU 架构难以高效并行化图遍历 → 单查询延迟居高。
  2. 算法与硬件脱节，加速器利用率不足。

## 2. 核心方法
- 最直观类比：像把「在迷宫里找出口（图遍历）」交给一个专门设计的硬件迷宫芯片（Falcon），并调整探路策略（DST）让芯片始终满负荷，而不是让 CPU 一步步走。
- 具体做法（输入→关键操作→输出）：
  - 输入：向量数据集与查询；构建好的近邻图索引。
  - 关键操作：
    - Falcon：硬件 GVS 加速器，实现高效 GVS 算子、将算子流水线化，并用片上 Bloom filter 跟踪搜索状态以减少内存访问。
    - DST：高效的图遍历算法，放宽遍历顺序以最大化加速器利用率，同时提升搜索性能与质量。
    - 两者协同：硬件-算法 co-design。
  - 输出：低延迟、高能效的图向量搜索系统（FPGA 原型）。
- 形式化要点：FPGA 原型实现；超参数（如 Bloom filter 大小、遍历宽度）见原论文 🔧。
- 理论性质/保证：实验表明，相比 CPU/GPU GVS，延迟低最多 4.3×/19.5×，能效高最多 8.0×/26.9×。
