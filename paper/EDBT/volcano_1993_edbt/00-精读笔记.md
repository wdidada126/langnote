# Volcano — An Extensible and Parallel Query Evaluation System — 精读笔记

> EDBT 1993 / 技术报告 UCB-CSD-93-××（Graefe & Lohman 系谱，⚠️ 作者与版本以原文为准；亦常引 ICDE 1991 版本）
> 三态标注：✅ 论文硬写事实 / ⚠️ 记忆或二手归纳 / 🔧 本地可复演实验

## 一、基本信息

| 项 | 内容 |
|---|---|
| 系统 | Volcano（Berkeley/Graefe 主笔；⭐ 与后来 Microsoft 同名服务器无关，亦与 CockroachDB 的 "volcano 模型" 术语同源） |
| 影响 | Iterator（pull-based，火山）执行模型的命名来源；级联式优化器（cascade-style optimizer）的出处（✅） |
| 下游 | Orca（SIGMOD 1994 ⚠️）、Cascades（⚠️）、Greenplum/HyPer 早期、Calcite 算子框架（⚠️） |

## 二、问题史：1990 初执行引擎的两个病

- 既有引擎：过程式解释执行、单算法写死（一个 join 一种做法）、无扩展点（✅ 论文 §1）。
- Volcano 两个命题：
  1. **可扩展**：算子/类型/函数外置注册，"新硬件新算法即插即用"（✅）；
  2. **可并行**：执行计划是**算子树+并行度标注**，同树既跑单机也跑共享无集群（✅）。

## 三、核心设计一：火山模型（pull-based iterators）

- 统一协议三方法：`open() / get_next() / close()`；上层向下层**拉**一行，行到顶端即吐（✅ 招牌）。
- 优点：算子可组合、并流控制天然（背压免费）、流水线零缓冲（⚠️ 归纳）。
- 缺点（后知）：每行一次虚调用+元组物化在行对象里 → 解释开销大，被 vectorized/data-centric（MonetDB/X100 ⚠️）与编译执行（HyPer/查询编译 ⚠️）超越——但接口思想统治至今（✅）。

## 四、核心设计二：算子库与物理多样性

- 每种逻辑操作多个物理实现：sort-merge join / hash join（含 Grace 分区）/ index join / nested loop；聚合分 sort/hash 两路（✅）。
- 算子带**成本接口**：优化器可为"计划片"询价（✅ 大意）。
- 并行原语：Exchange/分流器（gather/scatter/broadcast/repartition）作为一等算子插入（✅ 术语 Exchange 为 Volcano 首创系 ⚠️ 凭记忆）。

## 五、核心设计三：级联式优化器（Cascade-style search）

- 自顶向下规则改写 + **memo 结构**（等价类分组，去重复搜索）+ 优先级队列按"待优化目标"驱动（✅ 论文 §5）。
- 规则（transformations）与物理属性（排序/分区/演示 ⚠️）分离；与 ExODUS（Graefe 80 年代原型）一脉（⚠️）。
- 这即后来 Cascades 框架的前身：Orca/Greenplum ORCA、Calcite Volcano planner 直接沿用"火山/级联"命名（✅ 谱系）。

## 六、评测（✅ 定性）

- 论文实验含单机基准与并行扩展曲线（共享无原型机群），强调"同代码扩到 N 机近线性"（⚠️ 数字凭图表）。
- 对比当时 System R 血统引擎：扩展性与优化器搜索质量是卖点，原始吞吐非主打。

## 七、批判读法

- 行式迭代器抽象在 1993 合理，2000s 后成为性能债：列式批处理+SIMD 的复兴本质是"对 Volcano 的反命题"（⚠️ 对照：MonetDB/X100、Data-Juggling）。
- 论文"可插拔一切"部分靠 UC Berkeley 的 Pascal/模板实现，工程移植时扩展点成本被低估（⚠️ 记忆：源码后开源传播有限）。
- 并行正确性（偏斜、死锁）以 Exchange 算子吸收，但反压/中断处理写得薄（⚠️）。
- 优化器章节是全篇最被低估的部分——memo+规则搜索后来成为所有 cost-based 优化器的骨架；读它应当与 Selinger（1979 ⚠️）并置（⚠️ 评价）。

## 八、🔧 本地微实验（非本书引擎行为）

1. **手搓火山**：py 生成器链实现 scan→filter→hashagg→limit 四算子，各自 `next()` 拉一行——感受"背压免费"与 Limit 提前终止。
2. **代价询价**：给 filter 加选择率参数，同一计划枚举"先投影还是先过滤"两序，手写成本公式选序——迷你级联搜索。
3. **Exchange 分流**：multiprocessing 两 worker 按 hash 键分流聚合，模拟 repartition join。
4. **memo 去重**：对三条等价改写（交换律）建等价类表，统计朴素枚举 vs memo 的搜索节点数。
5. **列式反命题**：同一聚合任务用逐行生成器 vs numpy 批量各跑一次，计时差量化"Volcano 税"。

## 十一、最新演进与工业实践

- " volcano vs vectorized vs compiled"三分成为执行引擎教科书叙事；现代系统常混合（DuckDB 向量化+push-based、ClickHouse 批式）（⚠️）。
- Apache Calcite 把 Volcano/Cascades 搜索工业化：流处理与湖仓查询的默认优化器框架（⚠️）。
- push-based（Dataflow/NSM，⚠️ Materialize 等）复兴是对 1993 拉式的又一次反命题；接口层（算子代数）原封不动（✅ 判断）。
- 2024–2026：LLM 生成查询计划/UDF 仍需火山接口做执行底座；Volcano 论文从"性能文献"转型为"接口设计文献"被引用（⚠️ 判断）。
