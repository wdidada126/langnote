## 一句话总结
医疗 Text-to-SQL 的"真实考场"：题目不是研究员编的，而是从 222 名真实医院员工（医生、护士、保险审核、病历团队）的提问里来的；模型不但要会写 SQL，还要听得懂"出院后 30 天内"这类时间表达，更要识趣地承认"这个问题数据库答不了"。

## 0. 给新手的阅读前置（背景知识地图）

### 0.1 这个子方向在解决什么大问题
医生每天都在信息系统里翻病历，但 EHR 系统的检索界面极其难用。Text-to-SQL 能让他们直接用自然语言查结构化病历库（如 MIMIC-III、eICU）：问"ICU 里 60 岁以上患者的 30 天死亡率是多少"，系统生成 SQL 执行。EHRSQL 要回答的问题是：**现有 Text-to-SQL 模型离"能进医院"还有多远？**

### 0.2 为什么难
- **医院的需求面极宽**：从"查一下某病人的检验值"这种简单检索，到"计算生存率"这种复杂统计操作；
- **时间表达无处不在**：医疗问题几乎全是时间敏感的——"过去 48 小时""术后 7 天内""上次化疗之后"，SQL 里的时间推理极易出错，且可能人命关天；
- **不可回答问题**：数据库里根本没有的信息（如病人的主观感受），模型必须会说"我不知道"，而不是编造 SQL——这在医疗场景是安全底线；
- **真实问题 vs 学术问题的鸿沟**：以往基准的问题多由标注员照着 schema 编，和一线医护的真实提问分布差异很大。

### 0.3 主流解法一览
| 路线 | 直觉 | 代表 |
|------|------|------|
| 学术跨域基准 | 通用 schema + 标注员编题 | Spider、SParC 🔧 |
| 垂直领域基准 | 真实领域库 + 真实用户问题 | **EHRSQL（医疗）**、BookSQL（会计）等 |
| LLM 时代方法 | 大模型 + 提示/微调 + 执行反馈 | 各类 LLM-for-Text-to-SQL |
| 可靠性增强 | 不可回答检测、置信度校准 | EHRSQL 后续系列工作 🔧 |

### 0.4 三个关键名词的直觉解释
- **MIMIC-III / eICU**：两所开源 EHR 数据库——前者是 Beth Israel 医院的 ICU 记录，后者是多中心 ICU 数据集；均需在 PhysioNet 签协议后才能使用，是医疗 NLP 的标准底座。
- **不可回答问题（unanswerable question）**：数据库 schema 覆盖不了的问题（比如"病人为什么焦虑"）。刻意留在测试集里，专钓"硬答"的模型。
- **留出式（held-out）不可回答问题**：这类问题在问卷中收集但在训练集中隐藏，专用于评测模型"知之为知之"的能力，防止模型靠背题学会拒绝。

## 1. 问题背景与动机

### 1.1 前人工作简述
- Text-to-SQL 长期由 Spider 类跨域基准驱动，近年 LLM 大幅推高榜单；
- 医疗侧此前缺少"问题来自真实医护、数据库是真实 EHR"的基准；
- 团队先在医院做了问卷调研（见 §2），以调研产物为种子构建了本数据集——EHR-SeqSQL（本仓库收录的姊妹篇）后来在此之上扩展出多轮版本。

### 1.2 前人的缺陷 / 未解决问题（据摘要归纳）
1. **问题分布失真**：以往基准的问题不是真实用户问出来的，难以反映医院的广泛需求；
2. **时间推理缺位**：医疗场景的时间敏感问题没有被系统纳入评测；
3. **"硬答"无代价**：缺少可回答/不可回答的区分，模型胡编也没惩罚；
4. **研究-落地断层**：Text-to-SQL 研究与医疗健康实际部署之间差距大，需要实用基准来度量。

## 2. 核心方法

### 2.1 最直观类比
一般基准像"老师照课本出题"；EHRSQL 是"把考卷发给 222 位真实从业者，请他们写下工作中真想问数据库的问题"——再用这些问题去考模型，连"这题超纲了"都要如实承认。

### 2.2 具体做法（输入 → 关键操作 → 输出）
- **输入**：真实医院的问卷调研 + 两个开源 EHR 数据库（MIMIC-III、eICU）；
- **关键操作**：
  1. 在某大学医院开展问卷调查，向 **222 名医院员工**（医生、护士、保险审核、健康记录团队）收集真实问题，用回复创建**种子问题**；
  2. 将这些问题**人工链接**到 MIMIC-III 与 eICU 两个数据库上；
  3. 纳入多种**时间表达**（时间敏感问题）；
  4. 纳入从调查中收集的**留出式不可回答问题**；
- **输出**：一个实用向医疗 Text-to-SQL 基准，评测三个能力：① 生成反映医院广泛需求的 SQL（简单检索到复杂统计）；② 理解时间表达；③ 区分问题可回答/不可回答。

### 2.3 形式化要点
- 评测形式仍是 (问题, schema, 数据库) → SQL（或拒答）的三元组预测，指标以执行准确率类为主 🔧（精确指标定义查原文）；
- "留出式"设计保证了不可回答检测评测的有效性。

### 2.4 理论性质 / 保证
基准论文无算法保证；其方法学贡献是"真实用户问题 + 留出式不可回答"的数据构建协议。

## 4. 实验结论（概览）
- **评测对象**：主流 Text-to-SQL 模型（规则/解析器/神经/LLM 各代 🔧，清单查原文 §5）；
- **数据集**：基于 MIMIC-III 与 eICU 的 EHRSQL 测试集；
- **指标**：执行准确率 + 时间表达子集表现 + 不可回答检测表现 🔧；
- **结论方向**（摘要明示的挑战框架）：该数据集构成一组独特挑战——医院级需求广度、时间表达理解、可回答性判别；基准用于向"弥合研究与医疗实际部署的差距"迈进；

## 7. 2026 视角（🔧）
- **LLM 把榜单抬高，但"敢不敢用"仍是问题**：2023 年后 GPT 系/开源 LLM 在 EHRSQL 上准确率大幅提升，然而不可回答检测、幻觉拒答与时间推理仍是医疗部署的卡点 🔧；
- **工业地位**：EHRSQL 是医疗 Text-to-SQL 的事实标准基准之一（NeurIPS D&B 轨 + 持续维护），各大 EHR 厂商的 AI 助手评测常引用 🔧；
- **趋势**：拒答与校准（知不知道自己不知道）、隐私合规（合成 EHR 数据）、与 EHR-SeqSQL 系多轮交互评测的融合，是后续三年的主线 🔧。
