## 一句话总结
不微调模型，只靠提示词工程：把「自然语言 → SQL」这个大难题拆解成几个子任务（分类难度、找 schema 链接、生成 SQL 骨架、填子句），再让 LLM 分步作答并自我纠错——在 Spider 上把当时 LLM 的执行准确率从约 79.9% 的 SOTA 推到 85.3%，还在 BIRD 上拿到 55.9% 的当时 SOTA。

## 0. 给新手的阅读前置（背景知识地图）
- 大问题：让不懂 SQL 的用户用自然语言查数据库（Text-to-SQL / NL2SQL）。评测主战场是 Spider（跨库、200+ 表）与 BIRD（更贴近真实脏数据）两个基准，核心指标是执行准确率（execution accuracy）。
- 为什么难：要同时完成 schema 理解（几百个表/列选对几个）、条件理解（嵌套、分组、排序）、SQL 语法正确性；跨库泛化（训练时没见过的库）更是难点。
- 主流解法分类（直觉）：
  | 类别 | 思路 | 代表 |
  |------|------|------|
  | 微调专用模型 | 在标注对上训练 seq2seq | RAT-SQL、RESDSQL 等 |
  | LLM 直接提示 | few-shot 一次生成 | 早期 GPT-4 prompting |
  | 分解 + 提示（本文） | 拆子任务、链式喂给 LLM，不改参数 | 本文 |
  | 多智能体/多轮 | 多个角色协作或迭代 refine | MAC-SQL 等后续工作 |
- 关键名词直觉：
  - *In-context learning*：不训练参数，靠 prompt 里的示例教会模型做事。
  - *Schema linking*：把问题中的词对应到数据库里正确的表和列——Text-to-SQL 错误大户。
  - *Self-correction*：让模型生成后自查（含检查 SQL 方言/遵守指令等分类器式提示），发现错误再改。

## 1. 问题背景与动机
- 前人工作：微调路线（RAT-SQL、RESDSQL 等）长期霸榜 Spider；LLM 出现后大家直接 few-shot 提示，但摘要指出——微调模型与 LLM 提示方法在 Spider 上存在显著性能差距。
- 前人缺陷（逐条）：
  1. LLM 一次性生成整条复杂 SQL，推理负荷过重，简单 few-shot 打不过微调 SOTA；
  2. 不做分解时，schema linking 与 SQL 结构推断互相纠缠、一起出错；
  3. 生成后没有系统性纠错机制，小语法/方言错误直接报废整条查询。

## 2. 核心方法
- 最直观类比：解一道大题不硬算，先把应用题拆成「读题 → 列方程 → 分步求解 → 验算」——每步只让 LLM 干一件小事，前一步的答案作为后一步的输入，最后还加一道「验算」关卡。
- 输入→关键操作→输出：
  - 输入：自然语言问题 + 数据库 schema；
  - 关键操作（分解流水线）：
    1. 难度分类（difficulty classification）：先判断问题属于简单/中等/难/extra 难，决定用哪套提示；
    2. Schema linking 分类（decomposition: schema linking）：识别问题涉及的表/列/取值；
    3. SQL 骨架分类与生成（query classification + skeleton）：先定 SQL 逻辑结构，再按子句（SELECT/GROUP BY/ORDER BY…）分步填充；
    4. 自我纠错（self-correction）：用 zero-shot「检查指令遵从」「检查 SQL 方言正确性」等模块化提示让 LLM 找错并修正；
  - 输出：最终 SQL。
- 形式化要点：全部通过 prompt 实现，无参数更新；每个子任务配一套 few-shot 分类/生成提示 🔧（提示模板细节查原论文/仓库）。
- 理论性质/保证：无形式化保证，属实证方法论文。

## 4. 实验结论（概览）
- 模型：3 个 LLM（具体型号 🔧 查原论文；摘要称 experiments with three LLMs）。
- 数据集与指标：Spider（holdout test set）、BIRD（holdout test set）；指标为执行准确率。
- 经摘要核实的结论：
  - 分解方法对三个 LLM 的简单 few-shot 性能一致提升约 10%；
  - Spider holdout：原 SOTA 79.9 → 本文 85.3（写作当时的新 SOTA）；
  - 以 in-context 学习击败许多重度微调模型至少 5%；
  - BIRD holdout：55.9%，当时新 SOTA。
