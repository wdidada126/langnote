## 一句话总结
现有 Text-to-SQL 数据大多假设「一句话只有一种正确 SQL」，而 AMBROSIA 故意造出「即使把数据库摆出来仍然含糊」的问题，逼模型先识别歧义、再给出多种合理解读——结果发现连最强的 LLM 都经常翻车。

## 0. 给新手的阅读前置（背景知识地图）

- **子方向解决什么大问题**：Text-to-SQL 想把人说的话（自然语言问题）自动翻成能在数据库上跑的 SQL。但真实用户说话常常不严谨：「每个部门工资最高的员工」到底是指「每个部门里工资最高的那一个人」，还是「工资高于该部门平均水平的那些员工」？这种**歧义（ambiguity）** 在真实场景里无处不在，而大多数模型默认「只给一个答案」，遇到歧义就会乱猜。
- **为什么难**：歧义不是靠「看数据库」就能消除的——本文的关键发现是：哪怕把完整的数据库结构和数据都给模型，歧义依然存在。也就是说，问题本身就含有多种合理意图，需要模型先「意识到有歧义」，再分别列出每种解读。
- **几类主流解法（表格）**：

  | 思路 | 做法 | 与本文关系 |
  |------|------|-----------|
  | 单答案解析 | 假设问题无歧义，直接产出 1 条 SQL | 本文的对比基线 / 被批评对象 |
  | 歧义检测 + 多解读 | 先判断是否有歧义，再产出多个候选 SQL | 本文基准所鼓励的目标能力 |
  | 交互式澄清 | 让系统反问用户以消除歧义 | 相关方向（本仓库另有交互式 Text-to-SQL 论文） |

- **本文属哪类**：本文不是提出某个新模型，而是**造了一个专门针对歧义的评测基准（benchmark）**，用来衡量现有模型「识别歧义 + 给出多种正确解读」的能力。
- **2-3 个关键名词直觉解释**：
  - **语义解析（semantic parsing）**：把自然语言映射成机器可执行的程序（这里是 SQL）。
  - **歧义（ambiguity）**：同一个问题可以对应多个都「说得通」的 SQL。本文归纳了三种：作用域歧义（scope ambiguity）、附加歧义（attachment ambiguity）、模糊性（vagueness）。
  - **受控数据库生成（controlled generation of databases from scratch）**：作者从零「设计」出数据库和对应问题，确保歧义是故意造出来的、且即便给出数据库上下文也消不掉——这是本基准能成立的核心技巧。

## 1. 问题背景与动机

- **前人工作简述**：实用的语义解析器被期望能理解用户话语并映射到可执行程序，即使话语有歧义。Text-to-SQL 领域已有 Spider 等大规模基准，但主流评测默认「每个问题有唯一标准 SQL」，模型只要答对一条就算成功。
- **前人 N 个缺陷 / 未解决问题（逐条）**：
  1. 现有基准（如 Spider）**隐含假设问题无歧义**，于是模型从未被要求去「识别歧义」或「给出多种解读」；一旦真实用户说出含糊问题，系统只能硬给一个可能错误的答案。
  2. 之前缺少一个**专门、可控、能系统化制造歧义**的评测集，导致「模型到底会不会处理歧义」这一能力长期无法被量化比较。
  3. 即便把数据库上下文（schema + 数据）提供给模型，歧义是否还会残留？这一点前人没有系统验证过——本文用受控生成的方式正面回答了它。

## 2. 核心方法

- **最直观类比**：像出题人故意出「脑筋急转弯」——不靠模糊表述蒙混，而是先把数据库和答案都设计好，再反过来构造一句「怎么读都合理、但意思不同」的问题，专门考模型能不能看出「这里有好几种理解」。
- **具体做法（输入 → 关键操作 → 输出）**：
  - **输入**：自然语言问题 + 对应数据库（schema 与数据都给出）。
  - **关键操作（受控生成）**：从零生成数据库，使问题天然带有歧义，并且**即使把数据库上下文全给模型，歧义仍然存在**（这是本文方法论的题眼）。
  - **输出**：每个问题附带（a）它属于哪类歧义、（b）多种合理「解读」、（c）每种解读对应的正确 SQL。共覆盖三类歧义：scope ambiguity、attachment ambiguity、vagueness。
- **形式化要点**：基准把「歧义类型 → 解读集合 → 每个解读的 SQL」做成结构化标注，使评测可以分别考察「模型是否识别出有歧义」「每种解读的 SQL 是否正确」。
- **理论性质 / 保证**：本文是基准论文，不涉及算法正确性证明；其贡献在于**可控构造法**保证了「歧义在给定数据库下依然成立」，从而让评测结果可信。
