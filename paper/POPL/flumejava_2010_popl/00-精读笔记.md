## 二、问题史

裸 MapReduce 写多阶段管道（清洗→join→聚合×N）会：(1) 每阶段落盘 HDFS，IO 放大；(2) 调试要整跑全管道；(3) 样板代码淹没逻辑。Google 内部先有 QueBEQUE（⚠️ 名字来自 Quebec 法语区梗，材料仅有二手提及），证明"把管道写成嵌套表达式"可行但缺组合性与调试设施。FlumeJava 的立场：**用 Java 泛型把数据流图做成 lazy DSL——构建期只画图，运行期才优化执行**。

## 三、核心设计/机制

| 机制 | 内容 |
|---|---|
| PCollection + 链式 op | parallelDo/GroupByKey 等类型化算子，构建期只生成图 ✅ |
| 图重写优化 | 融合相邻 ParallelDo（fusing），省掉中间物化 ✅ |
| 检查点 | 图中间节点物化（checkpoint）以支持**部分重跑**与调试 ✅ |
| 动态分片 | Reshuffle 打破优化器造成的热点 ✅ |
| 类型安全 | 编译期查 pipeline 类型（vs 裸 MR 运行时炸）⚠️ 归纳 |

✅ 论文报告：同一应用在 FlumeJava 上比手写 MapReduce 代码量降 ~70%、管道延迟降 ~60%（数字以原文表格为准 ⚠️ 不写死）。

## 四、批判读法

FlumeJava 的历史身份是"证明批处理 DSL 可行"，但它**只批不流**——这正是 [[millwheel_2013_vldb]] 立项理由，也是 [[dataflow_model_2015_vldb]] 统一模型把两者都收编的原因。读时应把握三段论：MapReduce(2004, 原语) → FlumeJava/QueBEQUE(2010, 批 DSL+图优化) → Dataflow model(2015, 流批统一语义=Apache Beam)。另一批判点：Reshuffle 作为"逃生舱"暴露了**优化器无法自动处理数据依赖倾斜**这一根本局限，30 年后自适应执行（Eddies 线、AQP ⚠️）仍在解同一题。

## 🔧 五组纯本地微实验

1. **lazy DSL 骨架**：py 实现 PCollection/ParallelDo/GroupByKey，构建期只产 DAG 列表，打印计划再执行——复现"画图与跑图分离"。
2. **Do 融合收益**：3 个连续 map 阶段，对比"逐阶段物化到磁盘"与"融合流式"的总字节数（本地 tempfile 计时）。
3. **检查点重跑**：注入第 3/5 阶段异常，比较全管道重跑 vs 从最近 checkpoint 重跑的时间。
4. **热点复现与 Reshuffle**：造 key 倾斜的 GroupByKey（zipf），观察单 reducer 拖尾，再对输入做 salt-去盐模拟 Reshuffle。
5. **DuckDB 对照**：同一 4 阶段管道分别用 py DSL 与单条 DuckDB SQL 表达，统计中间落盘次数——理解"融合优化器后来被 SQL 引擎吸收"。

## 最新演进与工业实践（2024–2026 视角）

FlumeJava 随 Google 内部栈退役，其 DNA 活在两处：Dataflow 服务的批模式仍跑 FlumeJava 风格图重写 ✅（⚠️ 内部实现细节未公开证实），Apache Beam 的 Translate-优化-Execute 架构是同一思想的开源化。2024 后流批一体叙事（Flink 2.0 统一表 API ⚠️、Spark Declarative Pipelines）里，"DSL+图优化+检查点"三件套已是行业默认配置——FlumeJava 是这条配置线的最早公开文字之一。
