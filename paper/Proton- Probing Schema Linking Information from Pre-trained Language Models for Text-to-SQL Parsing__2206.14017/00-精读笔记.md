## 一句话总结
Text-to-SQL 要能拎清「问题里提到的列/表」离不开 schema linking；Proton 不用额外参数、也不靠规则，而是用 Poincaré 距离的「探针」从预训练语言模型里挖出它暗藏的表结构关系，用来增强图式解析器，三个基准上刷新 SOTA。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：Text-to-SQL 要把问题转成 SQL。关键一步是 schema linking——正确认出问题里指的「未见过的列或表」，否则生成的 SQL 会指错字段。
- **为什么难**：测试库里的表结构往往训练时没见过；表面文字不匹配时（同义、改写）更难对应；规则方法脆弱，有监督方法要额外标注。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 规则 schema linking | 字符串匹配 | 快但脆弱 | 同义/改写失效 |
| 有监督 linking | 分类器 | 需标注 | 准但贵 |
| **Proton（探针）** | 无监督探针 | 从 PLM 挖关系 | 无需参数/标注 |

- **本文属哪类**：Text-to-SQL 的 **schema linking** 增强，用探针（probing）技术。
- **2-3 个必懂关键名词（直觉解释）**：
  - **Schema Linking（模式链接）**：把问题中的词对应到数据库的表/列。
  - **PLM（预训练语言模型）**：如 BERT，已在大规模语料上学到丰富语义。
  - **Probing（探针）**：用一个小测试，探查大模型「内部是否已经藏着某种知识/结构」。

## 1. 问题背景与动机
- 前人工作简述：可迁移到新库的 Text-to-SQL 解析器很重要；schema linking 是关键一步。常用的是基于规则的方法。
- 前人缺陷/未解决问题（逐条）：
  1. **规则方法脆弱**：表面形式不同（同义、改写）时就抓不到语义对应。
  2. **缺无监督的关系抽取**：不想为 schema linking 额外标注或加参数。
  3. **未利用 PLM 内部知识**：大模型其实已隐含表结构关系，但没被系统提取出来增强解析。

## 2. 核心方法
- **最直观类比**：像用「探测器」扫描一座已建好的大楼（预训练模型），发现墙里其实埋着电路图（schema 关系）——不用拆楼重建，只要会探测，就能把图取出来用。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **探针提取关系**：基于 **Poincaré distance（双曲空间距离）**的 probing 流程，从大规模 PLM 中引出关系结构。
  2. **无监督、零额外参数**：整个过程无需额外标注，也不引入可训练参数。
  3. **增强图式解析器**：用引出的关系增强（augment）当前的图式（graph-based）解析器，改善 schema linking。
  - 输出：更好的 schema linking，进而更准确生成 SQL。
- **形式化要点**：核心是「Poincaré 距离探针 → 关系结构 → 图解析器增强」；超参为探针结构与距离度量（🔧 见原论文）。
- **理论性质/保证**：以实证为主；贡献之一是「完全无监督、零参数」的关系提取。
