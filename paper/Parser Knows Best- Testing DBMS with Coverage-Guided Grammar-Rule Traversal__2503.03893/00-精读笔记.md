## 一句话总结
ParserFuzz 从 DBMS 自带的 SQL 语法定义文件里自动抽取语法规则来生成查询，无需任何种子语料就能「喂饱」语法特性覆盖，并用代码覆盖率做反馈引导变异，在 5 个流行 DBMS 上发现 81 个未知 bug（34 个已修）。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：DBMS 是数据密集型应用的核心，里面藏着的 bug（功能错、安全漏洞）后果严重。自动化测试（fuzzing，模糊测试）就是自动造大量输入去「撞」bug。
- **为什么难**：已有 DBMS fuzzer 只覆盖了 SQL 方言里一小撮语法特性，大量功能没被测到。
- **几类主流解法**：

| 路线 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 语料驱动 fuzz | 传统 SQL fuzzer | 变异已有 SQL 种子 | 易上手，但覆盖面窄 |
| 语法驱动 fuzz | 本文 ParserFuzz | 从语法定义抽规则生成 | 覆盖全，无需种子 |
| 计划引导测试 | Testing DB Engines via Query Plan | 用计划做引导 | 不同切入点 |

- **本文属哪类**：语法驱动 + 覆盖引导的 DBMS 模糊测试。
- **2-3 个必懂关键名词（直觉解释）**：
  - **fuzzing（模糊测试）**：自动生成海量随机/变异输入来触发程序崩溃或错误。
  - **grammar-rule coverage（语法规则覆盖）**：生成器覆盖了多少条 SQL 语法规则——衡量「测得多全」。
  - **code coverage（代码覆盖率）**：被测程序里多少代码被执行到，用作 fuzzer 的反馈信号。

## 1. 问题背景与动机
- **前人工作简述**：已有不少工具全面测试 DBMS 找 bug，但只覆盖了各 DBMS 特有 SQL 方言中一小撮语法元素。
- **前人缺陷/未解决问题（逐条）**：
  1. **语法覆盖窄**：大量 SQL 特性从未被测试工具触及。
  2. **依赖种子语料**：多数工具需要输入语料，难以系统覆盖生僻语法。
  3. **缺反馈引导**：未充分利用覆盖率反馈去组合不同语法特性。

## 2. 核心方法
- **最直观类比**：别的 fuzzer 像「拿着几篇范文改词造句」，容易漏掉生僻句式；ParserFuzz 像「直接拿语法书（DBMS 自带语法定义），逐条规则照着造句子，并用『这段代码跑到了没』做导航继续造」。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：DBMS 内置的 SQL 语法定义文件。
  2. **关键操作**：
     - 自动**抽取语法规则**用于生成 SQL 查询（无需输入语料）；
     - 生成多样查询以**饱和语法特性覆盖**（弥补前人遗漏）；
     - 用**代码覆盖率作反馈**引导查询变异，组合不同语法特性去撞更多功能/安全 bug。
  3. **输出**：触发 bug 的 SQL 用例 + bug 报告。
- **形式化要点**：核心是把「语法规则遍历」与「覆盖率引导变异」结合；超参为规则抽取与变异策略（具体🔧查原论文）。
- **理论性质/保证**：以实验验证在 bug 发现、语法/代码覆盖上超越 SOTA。
