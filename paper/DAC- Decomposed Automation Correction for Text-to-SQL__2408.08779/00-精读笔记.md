## 一句话总结

LLM 生成的 SQL 经常有错，直接让 LLM"看着 SQL 改"效果很差——DAC 的思路是把纠错拆解成"实体链接 + 骨架解析"两个子任务，先分别生成问题对应的实体和骨架，再与初始 SQL 对比找出差异作为纠错反馈，平均提升 3.7%。

## 0. 给新手的阅读前置（背景知识地图）

- **子方向解决什么大问题**：Text-to-SQL 要把用户的自然语言问题自动转成 SQL 查询。LLM 出现后这条路线的性能成为主流，但生成的 SQL 仍会出错（表名/列名链接错、结构嵌套错），错一个词整条查询就废了。
- **为什么难**：纠错的前提是"能发现错在哪"。已有研究表明 LLM 其实不太会**检测**自己生成的 SQL 哪里错了（摘要引用的前人结论），所以"直接改"变成盲改。
- **主流解法几大类**：

| 类别 | 代表思路 | 直觉 |
|------|---------|------|
| 提示工程/in-context learning | C3、CHESS 等 | 用更好的上下文（schema 链接、相似示例）一次生成到位 |
| 微调专用模型 | CodeS 等 | 专门训练一个 SQL 语言模型 |
| 生成后纠错（本文所属） | DAC、self-consistency 类 | 先生成，再检查修正 |
| 交互式/编辑链 | CoE-SQL 等 | 多轮编辑逐步逼近正确 |

- **本文属于**：生成后纠错路线，核心创新是把"检测错误"也任务化了。
- **关键名词直觉解释**：
  - **实体链接（entity linking）**：把问题里的词（"北京的用户"）对齐到数据库的真实元素（表 `user`、值 `'北京'`）。
  - **骨架（skeleton）**：SQL 的结构轮廓——用了哪些子句、怎么嵌套（如 `SELECT ... FROM ... WHERE ... GROUP BY ...`），不含具体词。类比：骨架是衣服的版型，实体是缝上去的扣子。
  - **分解式纠错（decomposed correction）**：不直接看完整 SQL 挑错，而是把"答案应该长什么样"拆成实体和骨架两部分分别生成，然后 diff 找差异。

## 1. 问题背景与动机

- **前人工作简述**：LLM-based Text-to-SQL（提示工程与微调路线）已是主流；在此之上，**自动化纠错（automated correction）**作为增强手段出现——对生成结果再做一轮修正以提升性能（摘要核实）。
- **前人缺陷（摘要逐条对应）**：
  1. **现有纠错方法要求 LLM 直接面对生成的 SQL 进行修正**；
  2. **此前研究表明 LLM 不知道如何检测错误**（does not know how to detect mistakes），直接纠错效果差；
  3. 因此需要一个让 LLM"更容易发现错在哪"的纠错框架。

## 2. 核心方法

- **最直观类比**：改作文。与其让老师盯着整篇作文空泛地说"再检查一遍"，不如先单独列出"这篇文章该用的关键词清单"和"该有的段落结构"，再逐项对照作文——哪些关键词漏了、哪段结构不对，一目了然。
- **具体做法（输入→关键操作→输出）**：
  1. **输入**：自然语言问题 + 数据库 schema + 初始生成的 SQL。
  2. **关键操作**：
     - **第一步（分解）**：让 LLM 分别生成该问题对应的**实体**（应链接到哪些表/列/值）和**骨架**（应有的 SQL 结构）；
     - **第二步（对比）**：将初始 SQL 与生成的实体、骨架做 diff，差异点即为纠错反馈；
     - **第三步（修正）**：基于反馈让 LLM 修正 SQL。
  3. **输出**：修正后的 SQL。
- **形式化要点**：论文先给出一项分析性结论：**分解式纠错优于直接纠错，因为基于分解子任务的结果来检测和修复错误，比直接面对 SQL 更容易**（摘要原文）。🔧 该论证的形式化表述（定义 1 / 命题等）见论文正文。
- **理论性质/保证**：🔧 属实证方法论文，无统计理论保证；有效性由三个基准上的实验支撑。
