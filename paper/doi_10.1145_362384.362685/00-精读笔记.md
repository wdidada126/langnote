## 一、历史背景与它回应的问题

### 1.1 1970 年前的数据库世界

理解这篇论文，必须先理解它反对的是什么。20 世纪 60 年代末，"大型共享数据库"（large shared data banks）是新兴事物： airlines 订票（SABRE）、银行、政府档案库，多个部门、多个程序并发访问同一份数据。当时的主流数据组织方式有两类：

1. **层次模型（hierarchic）**：以 IBM IMS（1968 年随 System/360 推出）为代表。数据组织成树，记录通过"父子链"物理连接。想从"部门"导航到"雇员"再到"工资"，程序员必须知道链的走向。
2. **网络模型（network/CODASYL）**：以 DBTG 报告（1971 年定稿，本论文写作时正在起草）为代表。数据组织成图，记录之间用显式的集合（set）指针相连，程序员用 FIND / GET NEXT 之类的导航式指令遍历。

这两类模型的共同特征是：**数据的逻辑结构与物理存储结构（指针、链、索引、记录顺序）暴露在用户面前**。程序的正确性依赖于"你知道数据在磁盘上是怎么串的"。

### 1.2 Codd 要回应的三个问题

- **数据依赖问题**：应用逻辑与存储细节（指针、顺序、访问路径）耦合。改变存储结构（加索引、换组织方式、重排记录）必须改程序。这在大型共享库里是灾难——schema 演化被物理布局锁死。
- **可共享性问题**：多个用户、多套程序并发读写同一库，需要一种对用户"可通约"（communicable）的数据表示。导航式模型下，两个程序对"同一棵树"的理解可能因为持有不同指针路径而不一致。
- **非过程化（declarative）语言的可行性问题**：当时的常识是"检索必须告诉机器怎么取数"。Codd 要论证：存在一种数学上严格定义的高阶语言，用户只说"要什么"，"怎么做"交给系统。这在当时被认为是学术空想——论文标题里的 "for Large Shared Data Banks" 就是针对性表述：不是玩具模型，而是为大规模并发共享场景设计。

### 1.3 论文的学术血统

Codd 是数学家出身（牛津数学学士、硕士，1956 年入 IBM），早期研究细胞自动机与可计算性。他把**集合论与一阶谓词逻辑**这套数学工具带进了数据建模，这在此前的工程主导文献（CODASYL、IBM 内部技术通讯）里几乎从未出现过。论文开篇即声明：模型必须建立在"能被非计算机专业人员理解的数据表示"之上，数学形式化不是装饰，而是数据独立的根基。

## 二、技术内容精读

论文的术语系统与今天教科书略有差异（如 rel var/rel const），下面按原文论证顺序逐段展开。

### 2.1 关系、域与元组：模型的形式定义

**关系（relation）** 在数学上是笛卡尔积的子集。Codd 的定义链：

- **域（domain）**：每个属性（论文中称 attribute）规定一个取值集合，如"雇员工号"的域是整数，"姓名"的域是字符串。Codd 强调域是对"现实世界事物类别"的形式化，并且要求**同名的域必须"可比"**（comparable）——这是后来连接运算合法性的前提：只有在同一域（或可比域）上的值才能做等值判断。
- **n 元关系**：D1 × D2 × … × Dn 的任意子集即一个关系。集合语义意味着关系**没有重复元素**、**没有内部次序**。
- **元组（tuple）**：关系中的元素。一个元组是 ⟨d1, d2, …, dn⟩，各分量取自对应域。属性数 n 称"度"（degree）；论文里元组按属性"无序"，实际系统以列序存储只是实现细节。
- **映射（mapping）**：Codd 把"元组属性值的指派"用映射来表示——一个元组对应一个从属性名到域值的函数。这个观点让"记录"成为一阶对象而非"字段指针的聚合体"，字段之间是逻辑并列关系，没有物理先后。

**关系不能以关系为元素（域禁止是关系）**：论文要求所有域都是"简单值"集合（不可再分解的关系），即今天所谓**第一范式（1NF）** 的原始表述。Codd 在文中承认定义上允许"关系的集合"（relations over relations）会让嵌套结构自然成立，但他**特意禁止**，理由有二：(1) 禁止嵌套能让模型"简单到可以在终端上呈现"，用户可以直接看懂一张表；(2) 嵌套会重新引入"结构导航"，违背非过程化初衷。这个取舍影响深远，也长期被批评（对象-关系数据库、文档数据库都在"还债"），1990 年前后 Codd 在《The Relational Model for Database Management Version 2》中部分放宽了立场——即后来 D.1 至 D.5 若干讨论的前奏（具体年份表述以该书名版为准，本文不展开）。

### 2.2 关系是"谓词的外延"：语义学核心

这是全文最深刻、最常被忽略的一节。Codd 给每个关系（表）配一个谓词：

> 例：关系 `EMP(ENO, NAME, DEPT, GRADE, AGE)`，对应谓词
> "雇员 e 姓名为 n，属于部门 d，工资等级为 g，年龄为 a"。

语义主张：

- 一个**元组 = 该谓词的一个实例被断定为真**。表不是"记录集合"这种工程隐喻，而是"一组被数据库所有者断言为真的命题"。
- 关系模型因此天然携带**谓词逻辑**：连接、选择、投影对应逻辑合取、存在量词、量词消去。Codd 论文中"数据库 = 谓词的集合 + 其在关系中的外延"这一观点，是后来"关系数据库 = 模型论中的模型（model）"这一形式语义的起点。
- **信息单源原则（information principle，论文中的表述雏形）**："关于世界的所有信息，都应当以唯一的方式表示——表中的值。" 指针、链、"哪个记录在哪个物理块"不得携带用户可见语义。这条原则直接推出数据独立：语义只在值里，存储随便动。

### 2.3 关系运算与"高阶"数据子语言

论文定义了操作的封闭性方向（完整的关系代数/微积分刻画是其 1971/1972 后续论文补全的，本文不细究）：

- **投影、限制（选择）、连接、并、差**等运算：输入关系、输出关系——运算是"关系上的关系"，模型自洽（closure），查询结果可以继续当关系用，这就允许语言组合、视图定义、嵌套表达式。
- **rel var / rel const**：Codd 用"关系变量可绑定到查询执行中的中间关系，关系常量对应表"的记号来描述语言表达式的语义，相当于今天"范围变量（range variable）+ 元组演算"的雏形。
- 论文论证了这类语言的**非过程化性质**：表达式只描述"结果关系满足什么条件"，不描述"从哪条索引进、沿哪条链走"。Codd 特别指出，这使语言可以支持**高阶视图（view）**——用户可以定义与基表无关的派生关系并像基本关系一样查询。
- **视图更新问题（view updating）**：论文坦率承认这是未解决的难点——往视图里插一条元组，可能对应基表上多个解甚至无解。Codd 提出了若干"合理更新"的准则与限制。这一问题至今没有完全解决（SQL 标准的可更新视图条件只是一份工程妥协清单）。

### 2.4 数据独立的三层论证

Codd 对"数据独立"的论述是论文影响商业世界的直接原因。他把独立性拆成两层（后来的术语）：

1. **物理独立性**：改变存储结构——加/删索引、换组织方式（顺序文件 ↔ 散列 ↔ 多索引 B 树）、页分裂、记录重排——程序与查询不变。论文中的支撑论据：关系语义中根本不存在"记录顺序""访问路径"这些概念，所以物理层没有任何东西被接口暴露。Codd 花了不少篇幅谈存储与索引技术（如"给定查询，系统应能自动选用某索引"），说明他并非不谈物理——而是坚持物理**决策权归系统**（优化器），归系统的前提正是语言是非过程化的。
2. **逻辑独立性**：改变 schema 的逻辑可见部分——增删属性、拆分/合并表——已有程序应少改或不改。Codd 诚实地承认这一层更弱：视图机制能缓冲"加列/改名/拆表"，但属性删除会破坏依赖它的视图。这个坦承是后来所有"schema 演化难"讨论的源头。

与之对照，CODASYL 程序中 `FIND FIRST member OF set-name` 同时表达"逻辑上取部门下第一个雇员"和"物理上沿集合指针走"，一句话焊死了两层。这就是 Codd 反复攻击的"procedure-orientation"。

### 2.5 与层次/网络模型的逐条对比

论文中段的对比表是"宣战书"：

| 维度 | 层次/网络模型 | 关系模型 |
|---|---|---|
| 数据间联系的表达 | 物理指针/链，用户可见 | 值相等（外键连接），用户只见表 |
| 检索方式 | 导航式，过程化 | 描述式，非过程化 |
| 记录次序 | 有语义（链序、物理序） | 无意义（集合语义） |
| schema 变更 | 波及程序 | 物理层被隔离 |
| 面向的用户 | 专业程序员 | 增加"终端用户/非程序员"一档 |
| 完备性 | 难以形式化论证 | 数学基础，可证明语言能否表达某查询 |

Codd 按用户把语言分成三档（display-oriented / programmer / mathematician 类），主张关系语言可以覆盖全部三档——这直接预告了 SQL 的设计目标（查询与操作一体，从 ad-hoc 查询到应用嵌调）。

### 2.6 论文没有说什么（同样重要）

以今天的眼光，1970 论文**缺失**：SQL（彼时尚无，SQL 源自 1974–79 的 System R/SEQUEL 工作）、空值与三值逻辑（1979 年后才有专文）、完整性约束的公理化（1971 "Further Opinion"）、关系完备性判据（1972）、事务与并发控制、更新异常与范式的操作化分解理论（函数依赖/规范化是 Codd 与后来的 Fagin、Armstrong、Date 等人发展的）、任何实现与性能数据。这些空白既是它的局限，也是整个后续 15 年"关系研究产业"的空间。

## 三、论点逻辑链小结

把全文压缩成一条论证：

1. 大共享库的核心矛盾是"数据必须长期演化，程序必须长期存活"，两者被存储结构耦合杀死。
2. 解药是让用户看到的只有"值在表里"，其余一切（顺序、路径、索引、链）沉入系统内部。
3. 要做到 (2)，语言必须非过程化——否则"怎么做"必然泄露物理。
4. 非过程化语言需要严格语义，否则连"查询等价""优化保义"都谈不上——用谓词逻辑。
5. 于是：关系模型 = 集合论的数据结构 + 谓词逻辑的语义 + 关系代数的运算。三者同构于"表、真、算"，这就是数据独立的根基。

第 4 步的"优化保义"当时并未展开，但正是它十几年后孵化出基于代价的优化器（System R、R*、Volcano）这一整个领域——见 paper 目录内 Neumann 2011（编译执行）、以及本仓库 `db/` 下的优化器笔记。

## 四、后续影响与被修正处

### 4.1 影响线（已核实的锚点）

- **1981 年图灵奖**授予 Codd，授奖理由明确指向本论文开创的关系模型理论。
- **IBM System R（1973–1979）** 把设想变成工程，产出 SEQUEL→SQL；1979 年 Oracle V2 成为首个商用 SQL 关系数据库（Oracle 公司名即蹭了关系模型热度）。
- **SQL 标准化**：ANSI X3.135（1986）、ISO 9075。SQL 是"关系代数 + 元组演算"的工程混合体，并在多处偏离了 Codd 的模型。
- **范式理论/规范化**（1NF→BCNF→4NF/5NF）、**关系完备性**、**视图更新**、**外键**等主题全部是本论文留下议题的直接延伸。
- **分析型世界**：数据仓库（Kimball/Inmon）、MapReduce 之后的 SQL 复兴（Hive/Spark SQL/Presto/BigQuery），"一切皆表"的默认心智即 Codd 的遗产。

### 4.2 被修正/被争议之处

1. **1NF 禁令被现实突破**：多值依赖、嵌套表（SQL:1999 的 TABLE/ARRAY 类型）、对象关系（PostgreSQL 的复合类型/数组）、JSON（Postgres jsonb、Mongo）都在不同方向放宽"不可再分"的教条。今天多数教科书干脆用"平表 + 数组列"的混合姿态。
2. **SQL 不等于关系模型**：Codd 生前反复批评 SQL（重名视图、NULL 三值逻辑的混乱、ORDER BY 携带语义、缺 `WITH NO DATA` 之类），著名战斗"12 rules"（1980 年代中期，具体年份本文未逐条核实）就是对"伪关系系统"的抨击。工程史选择了 SQL，理论史保留了对它的持续修正。
3. **性能质疑与平反**：1980 年代初"关系=慢"是主流判断（如 Gray 1981 谈事务时也隐含关系系统的代价问题；Stonebraker 与 Gray 的公开辩论）。列存 + 向量化/编译执行（见本目录 Neumann 2011、 MonetDB/X100 一系）在 2005 年后彻底逆转，"关系模型本身慢"最终被证伪——慢的是第一代优化器与行存解释器。
4. **非过程化的边界**：窗口函数、递归查询（SQL:1999 的 WITH RECURSIVE）说明纯"描述式"有表达力与性能上限，现代引擎用向量化/编译执行把"怎么算"的控制权以系统内策略的形式部分收回——恰是 Codd 三层独立性划分的精细化：语言层保持描述式，执行层交给系统。
5. **分布式/NewSQL 时代**：CAP、共识、分片对"一张全局大表"假设的冲击（TiDB/Spanner/CockroachDB）是新的"修正"，但对外 API 仍保持关系/SQL，说明 1970 年的接口抽象经受了 50 年考验。

## 六、思考题（5 道）

1. Codd 为什么坚持域不能以关系为元素（1NF 原始表述）？如果允许嵌套关系，论文关于"非过程化与数据独立"的论证链在哪一环会被削弱？结合对象关系与 JSON 的返工历史回答。
2. "所有信息都以表中值的形式表示"（information principle）与 CODASYL 的"集合指针"对比：指针到底"泄露"了什么语义？请构造一个具体场景，说明"依赖指针语义"的程序在 schema 重构时如何损坏。
3. 论文允许视图查询、但对视图更新只给出了若干限制性准则。请按谓词/基表模型分析：往视图 `SELECT e.name, d.dname FROM emp e JOIN dept d ...` 中插入一行，对应基表上有哪些可能解？为什么"无唯一解"是语义问题而非工程问题？
4. 有人说"关系模型的成功是因为数学优美，失败之处在于性能"。结合本文三层论证与 2005 年后列存 + 编译/向量化执行的事实，判断这句话哪半对、哪半错，并给出你认为真正的因果链。
5. Codd 把"物理独立性"建立在"语言不暴露访问路径"上，因此优化器成为关系系统的阿喀琉斯之踵。试讨论：当现代系统普遍提供 hint、聚簇索引、物化视图与向量化执行选项时，这是在背离 Codd 还是在以另一种方式实现 Codd 的目标？

### 6.1 原文结构导览

论文约 10 页、六个小节，论证密度很高。按下表定位原文（小节名按原文标题直译）：

| 原文小节 | 内容一句话 | 精读优先级 |
|---|---|---|
| Introduction | 提出"数据模型"应作为用户与系统之间的契约；点明三类用户 | ★★★ 动机全在这 |
| Terminology | 定义关系、域、元组、映射、rel var/rel const；1NF 禁令 | ★★★ 形式定义 |
| Data Model for Large Shared Data Banks | 谓词语义、信息单源原则、与层次/网络模型逐条对比 | ★★★ 核心 |
| Representation and Language（数据子语言） | 关系运算封闭性、非过程化语言的高阶性质 | ★★☆ |
| Views and Updates | 视图定义与更新、视图更新的困难（坦承未解决） | ★★☆ |
| Storage Structures / Retrieval（存储与检索讨论） | 索引、访问路径归系统决策；论证物理独立 | ★★☆ |
| Conclusion | 展望：高阶语言 + 优化器是未来 | ★☆☆ |

### 6.2 术语速查（1970 原文 ↔ 现代对应）

| Codd 原文术语 | 现代教科书对应 | 备注 |
|---|---|---|
| relation | 表（table） | 但"表允许重复行/无序列"已偏离关系语义 |
| relation name / heading | 表名 / 列头 | 论文强调"属性名是关系的一部分" |
| domain | 列的数据类型 + 值域语义 | 域要求"可比性"，比类型更严 |
| tuple | 行（row） | 元组是映射，不是字段序列 |
| degree / cardinality | 列数 / 行数 | — |
| rel var / rel const | 范围变量 / 基表 | 通向元组关系演算的记法 |
| mapping | 元组 = 属性→值的函数 | "无序"性的形式表达 |
| relations of relations | 嵌套/复合类型 | 论文主动禁止（1NF 原始表述） |
| information insignificance | 次序无关性 | 行序、列序无语义 |
| data independence | 物理/逻辑独立性 | 论文的主打卖点 |

### 6.3 谓词视角的实例化演算

用论文自己的方式走一遍，可以看清"表 = 断言集合"如何支撑查询语义。

基表与谓词：

```text
EMP(eno, name, dept, grade)   谓词 P: "员工 eno 名为 name，在 dept 部门，等级 grade"
DEPT(dept, dname, mgr)        谓词 Q: "部门 dept 名为 dname，经理员工号 mgr"
```

查询（非过程化表述，等价于 Codd 的高阶语言直觉）：

```text
{ t | ∃ d ∈ EMP, e ∈ DEPT : d.dept = e.dept ∧ d.grade > 3 ∧ t = ⟨d.name, e.dname⟩ }
```

- 该表达式的语义 = 谓词 `∃d,e: …` 的全部真实例在投影 ⟨name, dname⟩ 上的外延。
- 优化器可以任意改写（先选 grade、先连接、换索引），只要改写前后**外延相同**——这就是"优化保义"的数学内容，其前提正是语言不携带过程信息。
- 对比 CODASYL 写法：`FIND DEPT USING index; FIND FIRST EMP WITHIN SET D-E; IF GRADE>3 …`——"真值条件"与"导航动作"揉在一句里，改写没有任何保义定理可依据。

### 6.4 三类用户与语言分层

Codd 把"数据银行用户"分三类，是论文里非常"产品思维"的一段：

1. **显示导向用户（display-oriented）**：只需查询与浏览，不写程序——对应今天 BI/即席查询；要求语言接近自然描述。
2. **程序员用户（programming-oriented）**：需要嵌入式数据操作 + 过程逻辑——对应今天的 OLTP 应用开发。
3. **数学家/分析师用户（mathematics-oriented）**：需要高阶、可组合的表达——对应今天的数据科学/复杂分析 SQL。

主张：同一套关系语言（加上宿主语言胶水）应同时覆盖三类。这个分层预言了 SQL 的"一种语言、三种用法"（即席、嵌入、存储过程）格局，也解释了为什么 Codd 坚持语言必须"高阶"（可组合）——低阶语言只服务第 2 类用户。

### 6.5 关键论断摘录（中译，供检索定位）

- "如果一种数据结构要让用户在逻辑上理解数据库，它必须是用户可通约（communicable）的。"——模型选择的标准是"可理解性"，不是性能。
- "关于数据库的全部信息，都应以同一种方式表示：表中的值。"——信息单源原则（information principle 的 1970 雏形表述）。
- "记录的物理次序与行的逻辑次序都不应携带用户可见的信息。"——次序无关性；这句话直接否定"按链序读取"类语义。
- "数据子语言应当是非过程化的：用户指定'要什么'，由系统决定'怎么得到'。"——优化器职责的宣言。
- "视图的更新是一个尚未完全解决的问题。"——全文最著名的一次诚实。

## 八、阅读方法与常见误读提醒

1. **不要把论文里的 relation 直接当 SQL 表读**：SQL 表是多重集（允许重复行）、列有序、可含 NULL；Codd 的关系是集合、无序、无 NULL（空值 1979 年后才讨论）。凡是"论文定理"与"SQL 行为"冲突处，通常论文是对的、SQL 是工程妥协。
2. **不要把"非过程化"读成"没有算法"**：Codd 把算法（访问路径、连接顺序）从用户手里拿走，交给系统——论文对索引/存储的讨论恰说明他知道算法重要，只是主张决策权的位置。
3. **"1NF 禁令"不是数学必然而是人机界面选择**（见 §2.1）：嵌套在 1970 被禁是为了"表能打印在终端上给人看懂"。今天读它应当带着"这个理由还成立吗"的问题意识——成立一半：可理解性仍是表结构的核心优势。
4. **读对比章节时注意稻草人风险**：Codd 对网络模型的批评针对的是"物理指针暴露"，而 CODASYL 支持者反驳（如 1980s Gray/Stonebraker 的性能之争）针对的是"优化器不可控"。两拨人都对，争的是同一枚硬币的两面。
5. **建议配套阅读**：Date《An Introduction to Database Systems》对应章节（模型教科书化）、《Readings in Database Systems》（"上帝之书"）收录的相关批评与续篇、以及 DDIA 第 2/9 章（用今天分布式视角回看数据独立性）。

## 九、一页总结（复习卡）

- **一句话**：把"数据的逻辑表示"从"物理存储结构"中剥离出来，方法是让逻辑层只剩一种对象——关系（表），其语义是谓词的真值外延，其操作是封闭的关系代数，其语言是非过程化的。
- **三大支柱**：信息单源原则（一切皆值在表中）/ 运算封闭性（高阶、可组合）/ 次序无关性（行、列、物理布局无语义）。
- **两个直接推论**：物理独立（随便改存储）、逻辑独立（视图缓冲 schema 演化，但有残余破坏）。
- **一个坦承的洞**：视图更新难；SQL 与 NULL 是后人塞进来的偏离。
- **一条历史判决**：模型赢了接口之争（SQL/表是默认心智），输在"朴素实现必然慢"的工程质疑上三十年——直到列存 + 编译/向量化执行（本目录 Neumann 2011）把质疑证伪。
