## 0. 给新手的阅读前置（背景知识地图）
- 这个子方向解决什么大问题：Text-to-SQL（NL2SQL）把用户自然语言问句翻译成 SQL，能大幅降低访问关系数据库的门槛，支撑智能问数、对话式 BI 等大量商业应用。LLM 的出现让这项技术的性能大幅跃升。
- 为什么难：自然语言有歧义与欠规范；数据库 schema（表 / 列）与实例值需要被正确对齐；如何公平评测、如何分析并修复错误，都是开放挑战。
- 几类主流解法（综述按四个生命周期维度组织）：

  | 维度 | 关注点 | 典型内容 |
  |------|--------|----------|
  | Model（模型） | 如何翻译 | 处理 NL 歧义、schema / 实例对齐、ICL / 微调 |
  | Data（数据） | 训练从哪来 | 训练数据收集、数据合成、benchmark |
  | Evaluation（评测） | 怎么算好 | 多指标、多粒度评测 |
  | Error Analysis（错误分析） | 错在哪 | 错误归因、指导模型演进 |

- 本文方法属于哪一类，与前身关系：本文是**综述**，不是提出新模型；它把前人零散的 Text-to-SQL 工作按统一框架串起来，前身是 Spider 时代以来的各类方法与评测。
- 2-3 个必须先懂的关键名词（直觉解释）：
  1. **Text-to-SQL / NL2SQL**：自然语言转 SQL 的统称。
  2. **schema / 实例对齐**：让模型知道「问题里的词」对应数据库里「哪张表、哪一列、哪个值」。
  3. **benchmark**：标准化的评测数据集（如 Spider），用来公平比较不同方法的准确率。

## 1. 问题背景与动机
- 前人工作简述：Text-to-SQL 随 LLM 兴起而性能大增，但工作散落、缺乏统一梳理；LLM 带来新的 NL 歧义、schema 对齐、评测粒度等挑战。
- 前人 N 个缺陷 / 未解决问题（逐条）：
  1. 领域缺乏按「全生命周期」统一组织的综述，模型 / 数据 / 评测 / 错误分析各自为政。
  2. LLM 时代特有的问题（NL 歧义与欠规范、schema 与实例对齐、细粒度评测、错误归因）需要被系统归纳。
  3. 实践者缺乏「怎么开发一个 Text-to-SQL 方案」的可用经验法则与对开放问题的指引。

## 2. 核心方法（综述框架）
- 最直观类比：像一本「旅游攻略」——先告诉你要去哪些景点（四个维度），再给一张「怎么玩最顺」的地图（经验法则），最后指出「还有哪些地方没开发」（开放问题）。
- 具体做法（按生命周期四个维度组织）：
  - **Model**：覆盖处理 NL 歧义 / 欠规范、把 NL 正确映射到数据库 schema 与实例的翻译技术。
  - **Data**：从训练数据收集、因训练数据稀缺而做的数据合成，到各类 Text-to-SQL benchmark。
  - **Evaluation**：用不同指标与不同粒度从多角度评测 Text-to-SQL 方法。
  - **Error Analysis**：分析错误以找根因，并指导模型演进。
  - 此外：给出开发 Text-to-SQL 方案的 **rule of thumb（经验法则）**，并讨论研究挑战与开放问题。
- 形式化要点：核心是「四维框架 + 经验法则 + 开放问题」的梳理，而非单一算法；配套 **Text-to-SQL Handbook**（https://github.com/HKUSTDial/NL2SQL_Handbook）供动手实践。
- 理论性质 / 保证：综述类工作，以提供结构化认知与资源索引为主。

## 4. 实验结论（概览）
- 本文为综述，无单一对比实验；它对已有工作的结论做归纳：
  - 模型维度：LLM + ICL / 微调显著提升翻译质量，但受 schema 对齐与上下文长度制约。
  - 数据维度：数据合成是弥补训练数据稀缺的关键手段。
  - 评测维度：需在多指标、多粒度下综合判断。
  - 错误分析维度：错误可归因并用于指导改进。
- 🔧 各维度下的具体方法对比、准确率数字请查原论文对应章节与所引文献的 Table / Figure。

## 7. 2026 视角（🔧）
- Text-to-SQL 已是 LLM 落地最活跃的方向之一，主流是「大模型 + 上下文学习 + 执行反馈 / 多智能体」，并与 Agent、RAG、Text-to-X 等趋势交汇；评测也从单点准确率走向更真实的多轮 / 多数据库场景。🔧 近年趋势请以最新版本综述与基准核对（本文本身已多次修订至 v7）。
