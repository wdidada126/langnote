## 二、问题史：GRACE 与"两遍哈希"的分岔

- 经典 hash join（Mobedi 1980 ⚠️）：一侧建表全内存——建表侧超内存即退化嵌套循环（灾难）。
- Grace：两侧按同一哈希**分区到桶**（分区×分区小表建 probe）——内存有界，但两侧都要读写分区（I/O 下限高 ✅ 本文观察）。
- Hybrid hash join：只对**建表侧分区**，探测侧只扫被溢出分区——比 Grace 省一遍大表 I/O（✅ 论文主角）。
- 命题：给出三者在内存 M、元组数 n 下的**精确 I/O 期望公式**，划出各胜场（✅）。

## 三、核心结论（✅ 论文大意，公式凭记忆 ⚠️）

- Grace 总 I/O ≈ 两侧各一遍读+分区写+重读+输出 ≈ 4–5 遍关系规模。
- Hybrid：小侧一遍读+溢出侧重读+大侧（1+溢出轮数）遍——**小侧装得下内存时仅 ~2 遍**，碾压 Grace。
- 判据一句话：可建表侧装内存→hybrid；双侧都大→Grace 的对称分区才回本（✅ 结论方向）。
- 论文含多桶/直方图变体与模拟验证（⚠️ 细节以图表为准）。

## 四、批判读法

- 公式假设均匀哈希与顺序 I/O：偏斜键（zipf）下分区倾斜=长尾，1990 未解，数据倾斜优化（两阶段加盐/自适应）是后话（⚠️）。
- "磁盘时代遍数"模型在 SSD/内存时代需重标定：遍数不再是唯一代价（带宽/并行度上位），但**分区即并行**的推论反而更强（⚠️ 判断）。
- Grace 在分布式语境的复活：shuffle join=对称分区 join（Spark/Trino 默认大 join 策略）——本文的 Grace/hybrid 分岔映射为"全 shuffle vs 广播 join"（✅ 谱系判断）。
- 教学法：讲 join 算法史，本文是 Mobedi(1980)→Grace(1984)→本文(1990)→Shawn/Daniel(1994 自适应 ⚠️) 链条的定量枢纽（⚠️）。

## 五、🔧 本地微实验（非本书引擎行为）

1. **三算法对拍**：sqlite 造 10^6×10^6 行 join，手写 Grace（两侧分桶文件）/hybrid（单侧分区+溢出轮）/broadcast（小侧全进内存），计文件读写量。
2. **内存悬崖**：扫描可用内存 M 从 n→n/10，测 hybrid 溢出轮数与总 I/O 曲线，复现论文拐点。
3. **倾斜注入**：zipf 键分布跑对称分区，统计最热桶大小与墙钟（体验"分区即长尾"）。
4. **两阶段加盐**：热键拆子桶二次处理，对比直跑 Grace 的总字节。
5. **遍数换带宽**：同一 join 用 DuckDB（向量化）跑，感受"遍数模型"低估并行 SIMD 的程度。

## 八、最新演进与工业实践

- 引擎默认策略仍按本文判据：小表广播、大表 shuffle（Spark AQE 把"何时改广播"动态化 ⚠️）。

- 2024–2026：倾斜治理（AQE/自适应加盐）成为云数仓性能工单第一名——本文的"均匀假设"仍是所有事故的隐含背景（⚠️ 判断）。
