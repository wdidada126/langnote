## 二、问题史：分析负载卡在"最后一公里"

- 数据科学栈断层：pandas 内存爆炸→要上 Spark/仓库，部署与运维跳变（✅ 论文 §1 痛点叙事）。
- SQLite 之于事务嵌入的成功没有被复制：市面缺"一个 .dll 就能跑 SQL 列存"的选项（✅）。
- 命题：把 MonetDB/X100（库内 [[monetdb_x100_2005_cidr]] 本批已建）的向量化+列式思想搬进**可嵌入单文件**引擎（✅ 谱系直承，同 CWI）。

## 三、核心设计（✅ 论文点+⚠️ 版本演进注明）

- **进程内执行**：无 server、无网络；客户端即引擎（✅ SQLite 类比）。
- 向量化解释执行：列块+select vector（X100 血统），后引入查询编译路径（⚠️ 2024+）。
- Push-based 执行模型改造（2022 博客线 ⚠️ 非论文）：算子树反向驱动，改善缓存/分支局部性。
- **直接查文件**：Parquet/CSV/JSON 表函数，零导入（✅ 招牌；与 Arrow 零拷贝互操作 ⚠️ 演进）。
- 存储格式：行/列混合格式（Raasveldt 论文后自研，"Data Blocks"设计 ⚠️ 博客文献）+ MVCC 缓冲管理（✅ 方向）。
- R 客户端/扩展系统（社区扩展：sqlite/postgres 连接器 ✅ 论文后爆发）。

- 后续第三方基准（DuckDB vs ClickHouse/Velox 各说）非论文内容（⚠️ 边界）。

## 五、批判读法

- Demo 文体=广告：架构细节（缓冲池、事务、格式）几乎全靠后续博客/演讲补——**论文不可独立作为设计文献**（⚠️）。
- 单进程单写者假设：多进程并发写=文件锁地狱，SQLite 的老坑复刻（⚠️ 社区高频事故）。
- "嵌入式≠小数据"营销有灰区：超宽表/超多并发场景仍要回到 C-Store/ClickHouse 式专用（⚠️ 判断）。
- 与 Polars 的关系（DataFrame 引擎 vs SQL 引擎之争）：DuckDB 用 SQL 接口赢生态，Polars 用表达式赢 API——接口层竞争大于内核（⚠️ 判断）。

## 六、🔧 本地微实验（非本书引擎行为）

1. **一行嵌入式**：pip duckdb，内存 SQL 直读 CSV/parquet 聚合，对比 pandas 同任务的峰值内存（psutil 采样）。
2. **列式红利**：宽表 20 列只 SELECT 2 列，测 DuckDB vs SQLite 扫描字节与耗时。
3. **零拷贝互操作**：DuckDB→Arrow→pandas 往返，对比 csv 中转的序列化开销。
4. **单写者锁**：两进程并发 ATTACH 写，复现锁冲突语义，体会嵌入式边界。
5. **TPC-H 迷你**：内置 tpch 扩展 SF=1 跑 Q1/Q6，观察 push 向量化与解释的差距（开关 experimental ⚠️）。

## 九、最新演进与工业实践

- 1.0（2022）→ 稳定性承诺；扩展仓库（spatial/iceberg/delta/httpfs）把"嵌入式"扩成"边缘查询运行时"（⚠️）。
- Quack/加密、客户端 SDK 嵌入移动/浏览器（WASM）——SQLite 生态剧本重演（⚠️ 判断）。
- 与 Iceberg/Delta 直读、MotherDuck 云托管构成"本地-云"双层（⚠️）。
- 2024–2026：AI 管道（特征工程/评测数据集切分）默认内嵌 DuckDB；"SQL 即数据框"的接口战争由它阶段性终结（⚠️ 判断）。
