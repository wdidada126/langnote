## 一句话总结
CaaS-LSM 在「存算分离」的 LSM 键值存储里，把最拖后腿的 Compaction（压实/合并）从数据库里彻底解耦成一种「无状态服务」，配合自适应调度控制面与完善错误处理，相比传统 LSM-KVS 最高带来 8 倍吞吐提升、P99 延迟最多降 98%。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：LSM-tree（Log-Structured Merge-tree）是 RocksDB、Cassandra、TiDB 等主流 KV 存储的底层结构。写入先落内存再刷盘，后台不断把多层数据「合并压实」（Compaction）以回收空间、保证读性能。在「存算分离」架构（计算节点与远程存储分离，如云上 EBS/对象存储）下，Compaction 涉及大量跨网络读写，容易成为瓶颈。
- 为什么难：把 Compaction 卸载到存储侧后，会出现四件事没人好好解决——Compaction 与 LSM 引擎强耦合、资源负载不均衡、调度困难、以及大量瞬时/执行错误难以处理。
- 几类主流解法：

| 路线 | 代表 | 思路 | 取舍 |
|------|------|------|------|
| 单机 LSM 调优 | RocksDB 原生 | 在本节点做 Compaction | 简单，但存算分离下网络开销大 |
| 卸载 Compaction 到存储节点 | 若干前置工作 | 把 Compaction 搬到存储侧 | 缓解网络，但耦合强、调度弱 |
| Compaction-as-a-Service（本文） | CaaS-LSM | 把 Compaction 解耦成无状态服务 | 灵活、易调度，但需解决一致性/错误 |

- 本文属哪一类：存算分离 LSM 的「Compaction 服务化」方案。
- 关键名词直觉：
  - Compaction（压实）：把多层、多版本的小文件合并成大文件，删掉过期数据；是 LSM 的「垃圾回收」。
  - 存算分离（Disaggregation）：计算和存储不在同一台机器，存储走网络，延迟与带宽成为新约束。
  - 无状态执行（Stateless）：Compaction 服务不长期持有 LSM 内部状态，可随时调度/替换，避免与引擎的协调开销。

## 1. 问题背景与动机
- 前人工作简述：多数研究把 Compaction 卸载到存储节点以缓解计算-存储间的网络压力。
- 前人缺陷/未解决问题（逐条）：
  1. 卸载后的 Compaction 与 LSM-KVS 之间仍有强依赖，缺乏灵活性。
  2. 资源负载均衡没解决。
  3. Compaction 调度策略缺失。
  4. 复杂的瞬时/执行错误（transient & execution errors）没有系统化处理。

## 2. 核心方法
- 最直观类比：传统 LSM 像「餐厅厨师自己洗碗」（Compaction 和营业强耦合）；CaaS-LSM 像「把洗碗外包给一家独立洗碗公司」——厨师只管炒菜，洗碗公司按需派单、弹性调度、洗坏了按流程重洗，彼此不黏在一起。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 解耦 + 无状态：把 Compaction 从 LSM-KVS 中剥离，做成可独立调度、无状态的服务执行单元。
  2. 控制面（Control Plane）：引入性能与资源联合优化的控制面，用「自适应运行时调度与管理策略」保证性能与资源利用率。
  3. 错误处理：用精细的错误处理逻辑覆盖不同层级的瞬时与执行错误。
  4. 输出：在存算分离环境下跑得更快、更稳的 LSM-KVS。
- 形式化要点：三大贡献——解耦无状态化、自适应控制面、错误处理；超参数以论文为准 🔧。
- 理论性质/保证：以系统实现与实验为主，未提供形式化理论保证。

## 4. 实验结论（概览）
- 对比基线：传统 LSM-KVS、以及面向存算分离优化的 SOTA LSM-KVS。

- 指标：吞吐、P99 延迟。

## 7. 2026 视角（🔧）
- 存算分离是云数据库主流架构之一，LSM 在远程存储下的 Compaction 开销是业界持续投入的方向；「把后台任务服务化/卸载」的思想也出现在云厂商的存储卸载方案中。
