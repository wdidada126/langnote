让查询优化器"先在家做作业"：把整个工作负载的查询计划延迟想象成一张大部分空着的表格，利用"这张表格其实是低秩的"这一洞察，用纯线性方法预测没测过的格子的延迟，从而离线挑出值得真正试跑的好计划——不碰查询热路径，还保证线上永不回退。

## 0. 给新手的阅读前置（背景知识地图）

大问题：DBMS 的查询优化器要为每条 SQL 选一个执行计划。传统优化器基于成本模型估算，估算错了就选慢计划。learned optimizer 想用机器学习/强化学习替人找更好的计划，但落地艰难。

为什么难：好的计划选择依赖真实的执行延迟，而试跑（exploration）本身很贵——在线试跑会把慢查询塞进生产负载；神经网络又有推理开销和不可解释性。

主流解法（表格）：

| 解法类别 | 思路 | 缺陷 |
|----------|------|------|
| 传统成本模型优化器 | 基数估计 + 代价公式 | 估计失准是老大难 |
| RL/神经网络优化器（Bao、Balsa 等） | 学一个模型在线/离线选计划 | 神经网络贵，且常被放进查询"热路径" |
| 竞争探索（Balsa） | 多个优化器比赛、用真实执行喂经验 | 在线探索拖累生产负载 |
| 离线低秩探索（本文） | 工作负载=部分观测的低秩矩阵，线性预测未观测延迟 | 需要离线探索阶段 |

本文属于离线探索 + 轻量预测类，明确主张把学习过程移出查询热路径。

关键名词直觉：
- 低秩矩阵：一张大部分格子空着的"查询 × 计划"延迟表，但每行每列高度相关——所以只用少量实测就能补全全表，跟推荐系统"看少量评分猜你的口味"是同一个数学。
- 离线探索（offline exploration）：在部署前的准备阶段主动挑一些"信息量最大"的 (查询， 计划) 对真跑一遍，喂给模型。
- no-regressions（不回退）：上线后绝不比原有计划更慢的保证——生产环境最在乎的一条。

## 1. 问题背景与动机

前人工作：learned query optimization 近年代表包括 Bao（用 RL 在候选优化器提示间选择）、Balsa（多优化器竞争 + 真实执行反馈）、LEON 等神经网络计划模型；它们证明了学习式优化能大幅超越传统成本模型。

前人缺陷（逐条）（摘要明确指向的问题）：
1. 近期的 learned optimizer 部署依赖昂贵的神经网络——推理开销和训练成本都不低。
2. 探索策略多为ad-hoc（临时拍脑袋的策略），缺乏系统化的问题形式化。
3. 很多方案把昂贵模型直接放进了查询处理的热路径——每条查询都要先过一遍神经网络，生产环境难以接受。
4. 在线探索型方案（如 Balsa）会拖慢真实负载。

## 2. 核心方法

最直观类比：像推荐系统冷启动。用户（查询）对商品（执行计划）的"评分"（延迟）矩阵大半空白，但口味（延迟模式）是低秩的——用几个主动挑选的试跑填补关键格子，剩下的用线性代数推出来，根本不需要深度网络。

具体做法（输入 → 关键操作 → 输出）：
- 输入：工作负载中的查询集合 + 每条查询的候选计划空间。
- 关键操作 1（建模）：把工作负载建模为部分观测的低秩矩阵——行是查询，列是计划，格子是延迟，大量格子未观测。
- 关键操作 2（预测）：用纯线性方法（低秩矩阵补全思想）从已观测格子预测未观测的计划延迟，几乎零计算开销。
- 关键操作 3（离线探索形式化）：把"选哪些格子真跑"形式化为主动学习（active learning）问题，并给出简单启发式决定探索顺序。
- 关键操作 4（部署）：上线后用预测结果选计划；模型不进热路径，保留 no-regressions 保证（不确定时退回原优化器）。🔧 退回机制的确切设计见原论文。
- 输出：每条查询的计划选择，离线探索预算换长期负载提速。

形式化要点：延迟矩阵 M ≈ UVᵀ（U、V 低秩因子）；探索目标是在预算内最大化预测质量的提升。🔧 精确的目标函数与算法伪代码见原论文。

理论性质：作者主张 no-regressions guarantee（不回退保证），且方法不对底层 DBMS 做假设（黑盒适用）。🔧 该保证的成立条件与证明/论证见原论文。

## 3. 变体 / 工程版（如有）

- 线性版（主打）：纯低秩线性预测，资源占用极小。
- TCNN 版：提出 transductive Tree Convolutional Neural Network（直推式树卷积网络），把查询树结构卷进来，预测更准但计算更贵——同样 3 小时负载缩到 1.5 小时的效果，它只需 0.5 小时探索就能达成（线性版需 1.5 小时）。属于"预算换探索时间"的变体。

## 4. 实验结论（概览）

- 对比基线：传统优化器与 learned optimizer 先行工作（🔧 具体是否含 Bao/Balsa 及版本待查原论文）。
- 数据集/负载：真实工作负载基准（🔧 具体是哪些 benchmark、DBMS 平台待查原论文）。
- 指标：负载总运行时间、探索开销、尾延迟/回退次数。
- 结论方向（摘要明确，已核实）：
  1. 仅 1.5 小时离线探索（线性版），即可把 3 小时的负载压到 1.5 小时；
  2. TCNN 版达到同等降幅只需 0.5 小时探索；
  3. 相比"神经网络进热路径"的方案，本方案开销低且有 no-regressions 保证，且不依赖特定 DBMS。

## 7. 2026 视角（🔧）

- learned optimizer 的工业落地一直卡在"开销与风险"上；LimeQO 的"离线化 + 线性化 + 不回退"三板斧代表了 2025-2026 年该方向向生产可部署靠拢的主流趋势：与其在线聪明，不如离线勤快、在线保守。
- 趋势：云厂商在托管数据库里做"影子负载回放 + 计划调优"的离线管线；低秩/矩阵补全这类轻量统计学习在 DB 自治（索引推荐、参数调优）中被复用。🔧 后续引用与云数据库中的实际集成情况待查。
