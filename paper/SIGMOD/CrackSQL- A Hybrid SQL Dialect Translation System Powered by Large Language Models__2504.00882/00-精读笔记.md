## 一句话总结
把一条 PostgreSQL 的 SQL 改写成 MySQL 能跑的 SQL，手工写规则累、纯靠 LLM 又会「编造不存在的函数」——CrackSQL 让规则和 LLM 打配合，按功能切段、逐段翻译，稳得多。

## 0. 给新手的阅读前置（背景知识地图）

**子方向解决什么大问题**：企业里往往同时存在 Oracle、MySQL、PostgreSQL、SQL Server 等异构数据库，应用迁移/上云时需要把成千上万条 SQL 从一种方言（dialect）改写成另一种。方言差异包括语法（如 `LIMIT` vs `TOP`）、函数（如日期函数各不相同）、语义细节。

**为什么难**：
- 语法差异只是表层，**语义的微妙差别**（隐式类型转换、NULL 处理、排序规则）更容易埋雷；
- 复杂查询动辄上百行、多层嵌套，一次性整体翻译容易顾此失彼。

**几类主流解法**：

| 路线 | 代表 | 问题 |
|------|------|------|
| 人工重写 | DBA 手改 | 昂贵、慢、易错 |
| 规则系统 | 各类迁移工具 | 每对方言都要手工定制规则，**维护成本高**，复杂查询覆盖不全 |
| 纯 LLM 翻译 | 直接喂给 GPT 类模型 | **不可靠**：会生成不存在的函数/语法（幻觉），复杂查询尤甚 |
| **规则 + LLM 混合（本文）** | CrackSQL | LLM 负责灵活适配，规则/检索负责兜底校准 |

**本文属哪类**：第一个**混合式（hybrid）**SQL 方言翻译系统（摘要自称 first）。

**关键名词直觉解释**：
- **SQL 方言（dialect）**：同一标准 SQL 在不同数据库产品中的「口音」，如 PostgreSQL 方言 vs MySQL 方言；
- **功能切分（functionality-based query processing）**：把长 SQL 按功能块（子查询、JOIN、聚合、窗口函数等）切开，逐块翻译再拼装——类比「长文章先分段再逐段翻译」；
- **跨方言语法嵌入（cross-dialect syntax embedding）**：一个能同时理解不同方言语法的向量表示模型，用来把源片段和目标方言的等价语法「对齐」。

## 1. 问题背景与动机
- 前人工作简述：方言翻译是异构数据库互操作的老问题；已有手工重写、规则系统、LLM 直接翻译三条路线。
- 前人缺陷（摘要明示，逐条）：
  1. 人工重写与规则系统**维护代价高**（要为每对方言定制翻译规则）；
  2. LLM 直接翻译**结果不可靠**，典型失败是「生成不存在的函数」，复杂查询尤其严重；
  3. 复杂长查询整体翻译时，相互依赖的查询操作难以一次处理对。

## 2. 核心方法
- **最直观类比**：翻译一本文言文交错拉丁文的书——纯靠博学译者（LLM）会自己编词，纯靠对照词典（规则）又翻不动长句。CrackSQL 的做法是：先用语法分析器把书按章节切好（功能切分），每段先用词典直译打底（规则），拿不准的段落叫译者翻译并配上一段「该作者惯用表达对照表」（跨方言语法嵌入检索），最后把各章拼回全书（局部到全局）。
- **具体做法（输入→关键操作→输出）**：
  - 输入：源方言 SQL + 目标方言（如 PostgreSQL → MySQL）；
  - 关键操作：① 基于**功能（functionality-based）**把冗长复杂 SQL 切成段，缩小 LLM 单次处理粒度；② 用新提出的**跨方言语法嵌入模型**做精确的语法对齐（源片段 ↔ 目标方言等价构造）；③ **自适应的「局部到全局（local-to-global）」翻译策略**，逐步解决相互依赖的查询操作；
  - 输出：目标方言的可执行 SQL。
  - 支持三种翻译模式（🔧 模式具体名称查原文/README），并提供 Web 控制台、PyPI 包、命令行多种使用方式。
- **形式化要点**：语法对齐建模为跨方言的语义等价检索问题（嵌入空间中匹配）🔧；局部到全局策略的形式化描述查原文。
- **理论性质**：系统论文，以工程有效性为主，无理论保证。

## 7. 2026 视角（🔧）
- 数据库国产化/云迁移浪潮下方言翻译需求旺盛（Oracle→PostgreSQL、MySQL→各种云原生库）；商业工具（如各大云的 DTS/迁移服务）与开源 LLM 方案并存。
- 趋势：LLM + 语法树（AST）对齐成为主流做法，纯 prompt 翻译已被证明不可靠；方言对覆盖度与「可执行验证回路」（翻译后自动跑测试）是当前竞争焦点。
- 与 Text-to-SQL 的融合：统一「SQL 理解-生成-修正」底座的趋势明显。
