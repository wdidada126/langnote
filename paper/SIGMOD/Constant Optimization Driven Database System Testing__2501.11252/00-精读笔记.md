## 一句话总结
借用编译器里「常量折叠/常量传播」的直觉：把查询谓词中的表达式替换成一个常量后，谓词的判断结果理论上不应变化——如果 DBMS 的结果变了，那它多半有 bug。CODDTest 用这一思路在 5 个成熟 DBMS 里找到了 45 个此前未知的 bug。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：数据库管理系统（DBMS）是极复杂的软件，即便像 SQLite、MySQL 这样被广泛使用的系统，也可能在特定查询上「悄悄算错答案」。这类错误叫做逻辑 bug（logic bug）：不会崩溃、不会报错，只是返回错误结果。相比崩溃类 bug，逻辑 bug 更难被发现，因为开发者和用户都容易忽视「结果不对」这件事。
- 为什么难：要判断一个查询结果「错了」，你需要知道「正确答案是什么」。但自动化测试里没有标准答案可对照——这叫 Oracle 问题（测试预言问题）。因此该方向的核心研究内容是设计各种 oracle（判定正确性的准则）。
- 主流解法几类（表格）：

| 类别 | 直觉 | 代表工作 |
|------|------|----------|
| 差分测试 | 同一功能用两种实现跑，结果应一致 | 等价表达式改写类 oracle |
| 元变形测试（metamorphic） | 改写查询/数据但保持语义，结果应不变 | Nonconforming inputs、PQS 等 |
| 基于规则/构造性生成 | 只生成能预知结果的查询（如全表行集、递归 CTE） | PQS（用一种简洁语言生成可验证查询） |
| 查询分区 | 把查询拆成多段分别验证 | Partition-based testing |
| 本文：常量优化驱动 | 谓词中表达式换成常量，结果应不变 | CODDTest |

- 本文属于：元变形测试思想的新变体——oracle 来源于编译优化语义：常量替换不应改变谓词真值。
- 关键名词直觉：
  - 常量折叠（constant folding）：编译器在编译期就把 `1+2` 直接算成 `3` 的优化。
  - 常量传播（constant propagation）：若已知变量 x 的值恒为 5，则把后面用到的 x 直接替换成 5。
  - 谓词（predicate）：查询中判断真假的布尔表达式，如 `WHERE a + 1 > 2`。

## 1. 问题背景与动机
- 前人工作简述：DBMS 测试已有大量工作，包括用差分测试比较不同 DBMS 的结果、用等价表达式改写构造 oracle、用查询分区等。作者团队此前也在 SQLancer 框架下贡献了多种 oracle。
- 前人的缺陷/未解决问题（逐条）：
  1. 许多现有 oracle 需要生成结构受限的查询（如 PQS 只支持一种简洁查询语言），或需要维护多个 DBMS 做交叉验证，适用面和实现成本受限。
  2. 有些方法针对特定 SQL 特性（如窗口函数、递归 CTE、地理空间数据），覆盖面窄。
  3. 缺少一种实现简单、语义假设清晰、可作用于普通用户查询的通用 oracle。本文提出：利用「常量替换后谓词结果应保持不变」这一来自编译优化的不变量，作为新的通用 oracle。

## 2. 核心方法
- 最直观类比：数学老师改卷时有个技巧——把一道题里的某一项换成它的值，答案不应该变；如果学生（DBMS）换之前和换之后给出两个不同答案，说明学生算错了。CODDTest 就是拿这个「不变量」当裁判。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：某个数据库状态 + 一条含谓词的查询。
  2. 关键操作：评估谓词中某个表达式的当前值（例如表达式 `a + 1` 在某行取值为 7），然后用常量 `7` 替换该表达式，生成改写后的查询。基于常量折叠/传播语义，改写前后谓词的真值应当一致，因此查询结果（哪些行被选中、被投影的谓词输出等）也应一致。
  3. 输出：在真实 DBMS 上执行原查询与改写查询；若结果不一致 → 报告一个逻辑 bug（附最小化复现用例）。
- 形式化要点：设查询含谓词 P，P 中的子表达式 e 在数据库状态 s 下求值为常量 c。用 c 替换 e 得到 P'。若 P 与 P' 语义等价，则替换后结果不应变化；任何差异即 oracle 违反。
- 理论性质/保证：oracle 的正确性来自 SQL 语义（表达式求值的确定性），属「构造性正确」；论文以实验与人工分析说明其检出能力与实现简易性（🔧 具体理论分析细节查原文）。

## 4. 实验结论（概览）
- 对比对象（被测 DBMS）：SQLite、MySQL、CockroachDB、DuckDB、TiDB 共 5 个成熟且被广泛测试的 DBMS。
- 对比基线：与最先进 DBMS 测试方法做人工对比分析。
- 指标：发现的独特 bug 数、独特逻辑 bug 数、仅 CODDTest 可检出的 bug 数。
- 结论方向（摘要给出的已核实数字）：共发现 45 个此前未知的独特 bug，其中 24 个为独特逻辑 bug；人工分析显示 11 个逻辑 bug 只有 CODDTest 能检出。作者强调该方法实现简单、易于被实践采用。
