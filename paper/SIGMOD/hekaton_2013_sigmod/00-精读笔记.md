## 二、问题史：磁盘引擎吃主存红利为什么难

- Buffer pool 架构的惯性税：页帧、闩锁、日志按磁盘设计——主存普及后这些成为纯开销（✅ §1 论证）。
- 同题竞品：SAP HANA（重建栈）、Oracle TimesTen（旁挂异构）、Volt/H-Store（改应用模型 ⚠️ 库内 [[hstore_2008_vldb]] 已建）。
- Hekaton 命题：**不改变 SQL/T-SQL 应用接口**的前提下，对可内存驻留的热表做 10–30x 加速（✅ 立场：局部替换而非革命）。

## 三、核心设计

### 3.1 内存优化表与无闩锁索引

- 表脱离页世界：行直接放内存（96 字节内联描述符 ⚠️ 细节凭记忆）；索引=**无闩锁并发哈希**（指针 CAS，位图分代计数做内存回收）（✅）。
- 索引即指针数组，不存数据副本 → "每表多哈希索引近乎免费"（✅ 卖点；无范围索引是后话 NC2/NwScan ⚠️）。

### 3.2 乐观 MVCC 与"无游标锁"

- 提交版本链（begin/end 时间戳字段内联行头）；读不加锁，写冲突=**回滚重试**（乐观默认，pessimistic 模式后补 ⚠️）。
- 游标不持锁不 latch：扫描靠版本链一致性视图（✅ 与传统引擎游标语义的断裂点）。

### 3.3 编译查询（native compilation）

- 存储过程编译成机器码（Interpreted 模式并存但慢）：消除解释器、谓词逐行编译（✅ 招牌；HyPer 编译思想的工业同代 ⚠️ 对照）。
- 编译单元约束：可序列化 T-SQL 子集（不支持动态 SQL 等 → 功能鸿沟论文自认 ⚠️）。

### 3.4 日志与恢复

- 行级 redo + 表级"快照文件"（checkpoint 周期）；恢复=快照+日志应用（✅）。
- **提交不 fsync**（durability 可选 SC_ANDDur/SC_and_Any 两档）：高吞吐档依赖上层冗余（✅ 与 Aurora/Socrates 持久层哲学互补 ⚠️ 对照 [[socrates_2019_sigmod]] 已建）。

## 四、评测（✅ 定性）

- 内部 OLTP 微基准：单核吞吐数倍于解释引擎；核数扩展近线性（乐观冲突率随共享度涨，⚠️ 曲线以图表为准）。
- 论文诚实列出"退化场景"：长事务扫描、写热点、不可编译 T-SQL（✅）。

## 五、批判读法

- "内存表≠内存数据库"：SQL Server 其余部件（备份/复制/DW）按磁盘语义设计，Hekaton 是补丁而非重构——运维复杂度转移给了用户（⚠️）。
- 乐观默认在大热点下重试风暴：pessimistic 模式 2016+ 才补（⚠️ 版本线凭记忆）。
- 编译存储过程的"子集语言"困境：生态兼容税长期存在，社区抱怨集中于此（⚠️）。
- 与 Volt 对照最能出题：**同为 OLTP 加速，Hekaton 改引擎不改应用、Volt 改应用不改并发模型**——2013 年的两条路都没赢，赢家是"云上托管 Postgres"（⚠️ 判断）。

## 六、🔧 本地微实验（非本书引擎行为）

1. **无闩锁哈希**：CAS 插入槽位+分代引用计数，多线程压测观察无锁扫描的内存回收（epoch reclamation 雏形）。
2. **乐观 MVCC**：行头(begin,end)时间戳版本链，两写线程冲突→败者重试，计重试率随热点 Zipf 指数曲线。
3. **游标免锁**：长扫描中途大量提交新版本，验证快照读不阻塞。
4. **fsync 档位**：每次提交 os.fsync vs 纯 append，测延迟与"拔电丢多少"。
5. **编译 vs 解释**：同一聚合循环 py 手写 if 分支 vs numpy 编译式，量化解释税量级。

## 九、最新演进与工业实践

- SQL Server 2016+：计算列、交叉表、pessimistic、内存中 OLTP 与列存索引组合（HTAP 缝合 ⚠️）；Azure SQL 托管实例继承（⚠️）。
- Postgres 阵营走"UNLOGGED 表+逻辑复制+pg_prewarm"曲线逼近，Hekaton 式孤岛路线收缩（⚠️ 判断）。
- 2024–2026：向量热表+低延迟 API 让"编译式内存引擎"叙事在 AI 服务层复活（如嵌入式分析型 KV），论文仍是该形态最干净的设计文档（⚠️ 判断）。
