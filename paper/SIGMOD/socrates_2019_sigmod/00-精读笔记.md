## 一、基本信息

| 项 | 内容 |

| 会议 | SIGMOD 2019（Azure SQL Database 下一代引擎） |
| 定位 | "存算分离的终态"：计算无状态 + 页服务器（Page Server）+ 日志服务（Log Service），可分离可合体的三权分立 |

## 二、问题史：为什么要"三tier"而非"两tier"

- 两tier 存算分离（Aurora 式）痛点：存储节点理解 redo → 引擎与存储协议耦合；故障转移需"追赶"；读扩展受计算节点缓存冷启动惩罚（⚠️ 论文 §1 论证线）。
- Azure 的现实约束：单一 SQL 引擎要同时服务多租户弹性和超大规模单库；**混部（co-located）与分离（disaggregated）必须同一代码路径**（✅ 论文强调的部署弹性）。
- 设计答案：把"日志持久化""页物化""计算"拆成三个可独立伸缩的服务，各自用共识/副本解决可用性（✅）。

## 三、架构组件

| 组件 | 职责 | 关键点 |
|---|---|---|
| Compute Replica (CR) | T-SQL、优化器、事务、缓冲池（只读页） | 无状态，可任意拉起（✅） |
| Log Service (LS) | 接受 redo，多副本持久化（Paxos 系），**提交=日志服务 quorum 持久** | 与 Azure Storage 分层归档（✅） |
| Page Server (PS) | 消费日志、物化页、按需服务版本页 | 把"写时物化"从计算侧彻底搬走（✅） |
| Fabric/控制面 | 编排、配额、计费 | 略（⚠️） |

### 3.1 读路径的"版本页拉取"

- CR 缓冲池 miss → 向 PS 要"截至自己已知 LSN 的页版本"；PS 落后则现场追日志（✅ 机制）。
- 后果：**计算侧恢复=拉页即恢复**，无重放——failover 时间与事务大小解耦，这是比 Aurora "tail page repair" 更进一步的物化位置（✅ 对照判断 ⚠️ 措辞）。

### 3.2 两类副本形态

- **Mixed（合体）**：单节点同时演三角色，小库省 RPC（✅ 卖点：不强制分布式税）。
- **Disaggregated（分离）**：大库三角色分家独立扩（✅）。

### 3.3 写吞吐与带宽治理

- 日志带"页修改位图"信息让 PS 预取；网络放大问题通过 batching 与压缩控制（✅ 大意 ⚠️ 细节）。
- 只读副本（RW→RO）订阅日志流，秒级可见（✅）。

## 四、评测（✅ 定性）

- 论文以 TPC-C/内部混测：分离形态下吞吐与 Aurora 同数量级宣称（⚠️ 无同台公开曲线）；合体形态小库延迟优于全 RPC 设计（✅ 结论方向）。
- failover 恢复曲线：事务再大恢复时间近似常数（✅ 核心图景）。

## 五、批判读法

- "一页一 RPC"的读路径对缓冲池命中率是硬依赖：冷启动风暴（thundering herd on PS）论文轻描淡写（⚠️）。
- 三角色协议栈复杂：LS 共识、PS 追页、CR 读一致性三者交叠，工程正确性论证远比 Aurora 单协议薄——论文自认多处"细节从略"（⚠️）。
- SaaS 视角偏差：论文大量篇幅在服务化（弹性/多租/计费），数据库内核洞见密度低于 Aurora 篇（⚠️ 评价）。
- 后续"Computing, fast and cheap: Logging at the speed of storage"（PoDS 2020，LogService 论文 ⚠️）才补上日志层的硬内容——读 Socrates 必须二刷那篇。

## 六、🔧 本地微实验（非本书引擎行为）

1. **角色分家**：三进程（计算/日志/页）用本地 socket 通信，测"合体=函数调用"vs"分离=RPC"的小事务延迟差——理解 mixed 形态动机。
2. **恢复=拉页**：kill 计算进程，新进程仅靠"页服务+日志流"重建缓冲池可用性，计时对比全量重放。
3. **版本页请求**：页服务维护 (page,lsn)→image 表，计算侧带"已知 lsn"读，观察落后注入时的现场追日志行为。
4. **位图预取**：redo 记录附页号位图，PS 侧批量预取 vs 逐页按需，计 RPC 次数。
5. **RO 订阅**：第二进程 tail 日志文件维护影子页集，测复制滞后分布。

## 九、最新演进与工业实践

- Azure SQL DB Hyperscale（2019→GA）即 Socrates 产品化；超大规模单库上限至 100TB 级（⚠️）。
- Log Service 独立论文（PoDS 2020）+ "Computing, Fast and Cheap"（⚠️）补齐日志层与读扩展细节。
- 行业同构：PolarDB 共享日志、OceanBase 4.x 存算分离改造，"页服务+日志服务"拆分成为云 SQL 主流模板之一（⚠️）。
- 2024–2026：AI 工作负载下的向量列与冷热分层继续压在 Socrates 骨架上；合体/分离双形态被证明是云 DB 的长期现实（⚠️ 判断）。
