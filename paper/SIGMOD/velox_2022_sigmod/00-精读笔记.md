## 二、问题史：为什么要"引擎下面的引擎"

- JVM 系（Presto/Spark）天花板：GC、对象头开销、行式中间表示；重写每个引擎代价不可承受（✅ §1 论证）。
- 答案：下沉公共层——**向量化解释+表达式 JIT（LLVM）双模、列式内存编码、连接器抽象**做成库，上层 SQL 方言与调度各自保留（✅ 分层策略）。

## 三、核心设计（✅ 论文目录式复述 ⚠️ 细节凭记忆）

### 3.1 列式内存与编码

- 一切向量=**flat/dictionary/runcle/constant/biased** 等编码的组合（encoding tree）；算子在编码上直接工作，**免解码剪枝**（✅ 招牌：lazy materialization + 编码感知）。
- 与 Arrow 关系：互操作边界明确，内部表示更富（⚠️ 设计口径凭记忆）。

### 3.2 执行模型

- Push-based 向量化算子树（驱动反转）+ 表达式求值向量化；复杂类型（ARRAY/MAP/ROW）一等支持（✅）。
- 内存仲裁：统一 MemoryPool/ arbitrator 多查询共享限额（✅ "unified memory management" 卖点）。
- 扩展点：函数（vectorized 简写宏）、连接器、聚合自定义（✅ 设计动机=复用）。

### 3.3 集成形态

- Presto native（Prestissimo）：Coordinator 调度+Velox worker——Meta 生产主力（⚠️ 规模数字凭博客）。
- Spark via Gluten：同一底座跑 Spark 计划（⚠️ 生态判断）。

## 四、评测（✅ 定性）

- 论文基准多为内部 Presto-Velox 对比：TPC-H/DS 类数倍加速（⚠️ 曲线为准）；论文承认"优化器/调度差异未剥离"（✅ 诚实点）。

## 五、批判读法

- Bulletin 短文文体=发布公告：架构表格化、无消融实验——**读 Velox 应读源码文档，论文只是护照**（⚠️）。
- 向量化解释 vs 编译（HyPer 线）的钟摆再摆：Velox 押注解释+SIMD，JIT 仅表达式级——与 [[monetdb_x100_2005_cidr]]（已建）的 17 年判断一致但代价是分支预测税仍在（⚠️ 判断）。
- "统一引擎库"叙事风险：上层引擎行为差异（优化器质量/容错语义）不可被共享库抹平——Presto-SQL 语义兼容是 Prestissimo 最难工程（⚠️ 对照 [[presto_2019_icde]] 已建）。
- 开源 Velox ≠ Meta 内部 Velox（内部算子/连接器未出）——引用其数字时注意（⚠️）。

## 五、🔧 本地微实验（非本书引擎行为）

1. **编码感知扫描**：手写 RLE 列块，谓词在段级求值（免展开），对比全展开过滤的字节量。
2. **lazy 物化**：构造"过滤后仅剩 1% 行"的查询，延迟解词典 vs 先解词典，计时。
3. **字典地狱**：高基数键的 dict 编码退化测试，观察何时 flat 更优——复现 encoding 选型问题。
4. **统一内存池**：两查询共享限额的分配器模拟（token bucket），测超卖时的排队公平性。
5. **push vs pull**：同一三算子链分别生成器拉式/回调推式实现，对比函数调用开销（perf 计数）。
