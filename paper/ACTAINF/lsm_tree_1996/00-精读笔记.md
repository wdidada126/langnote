## 二、问题史：B 树在低配硬件上的写崩溃

- 1990s 末硬件不对称：读带宽增长快，**写 I/O 与小粒度随机写极贵**；B 树一次插入触发多层页分裂与随机写（✅ 论文动机）。
- 目标负载画像：插入/删除/批量刷新为主、查询为辅（档案型系统，如呼叫记录）（✅）。
- 论文核心问题：能否把"写"全部转成顺序追加，把"读放大"交给后台整理？（✅ 表述归纳）

## 三、LSM 树设计

### 3.1 部件两分 + run 分层

- **Y-structure**（内存 C0：一个可变 B 树 + 若干不可变定长 run C1..）与 **O-structure**（磁盘 C2：单个大 run，仅顺序重写）（✅ 原文术语）。
- 写入 = 追加内存 + commit log；C0 满 → 落成新 C1；run 分层按尺寸倍数增长（典型 ~10 倍）。
- **Rolling merge**：同级 run 攒够即向下一层合并——分层控制"至多 k 个同级 run"（✅）。

### 3.2 代价三账本（论文记号 ⚠️ 具体符号凭记忆）

| 指标 | B 树 | LSM 树 |
|---|---|---|
| 插入 I/O | 高（页分裂） | 低（顺序写，摊还） |
| 点查代价 | ~树高 | 随 run 数增长，靠 Bloom/缓存压住 |
| 空间 | 页内碎片 | 墓碑开销 |
| 稳定状态 | 读优 | 写优 |

- **墓碑（delete marker）**：删除不物理移除，写一条 tombstone，合并时才消亡——读放大与删除语义的长期隐患自此埋下（✅ 原文有 delete marker 概念）。
- 论文给出 e、N 等参数下 I/O 代价公式并数值对比 B 树（✅ 结论：写密集场景优 1–2 个数量级）。

### 3.3 辅助结构

- Bloom filter（当时称空间/时间折衷过滤器，✅ 论文引用 Bloom 1970）、LRU 缓存热 run 索引、commit log 先行（✅）。

## 四、评测（✅ 定性）

- 用呼叫记录（CDR）类负载模拟：插入主导时 LSM 显著占优；读主导时回退，作者坦承（✅ 诚实点）。
- 无 RocksDB 时代的"写放大/空间放大"三轴术语（1996 未提 ⚠️ 属后人 Siakernas/Subramanian 框架）。

## 五、批判读法

- 论文把"读"当二等公民：点查要探所有层 run，范围查询要做归并——现代变体（labeled LSM、NO-LSM、Monkey）全在还这笔债（⚠️）。
- 合并调度被写成后台免费行为，实际是尾延迟与写放大的风暴眼（RocksDB leveled/tiered/FIFO 诸策略是 20 Years LSM 研讨会的议题 ⚠️）。
- 墓碑 + 压缩不彻底 → 空间放大与"僵尸读"（删除键被反复复活），生产事故常客。
- O'Neil 原型的"分层参数固定"在真实偏斜负载下需自适应（Monkey、Dostoevsky、LCS 等 2017+ 工作 ⚠️）。

## 六、🔧 本地微实验（非本书引擎行为）

1. **手写迷你 LSM**：dict 内存表 + 满则 flush 成排序 JSONL + 分层 rolling merge，统计插入 10^5 键的总写字节数 vs 朴素 B 树模拟。
2. **读放大曲线**：构造 L0/L1/L2 各 k 个 run，测点查平均探测文件数与假阳率（Bloom 开关对照）。
3. **墓碑生命周期**：插入→删除→合并，跟踪同键在三阶段的读结果与文件字节变化。
4. **leveled vs tiered**：模拟两种合并策略下的写放大与空间放大数值表（RocksDB 论文 2014 实验的单机微缩版 ⚠️）。
5. **前缀压缩**：对排序 run 手工做块内公共前缀剥离，测压缩比。

## 九、最新演进与工业实践

- RocksDB 成为事实标准（MySQL MyRocks、CockroachDB、Cassandra、RocksDB 之上的 AFS/KV 无数）；Universal/Leveled/FIFO 策略与自适应调优（DBOS ⚠️）产业级应用。
- "20 Years LSM-tree"研讨会（2021+）：LCS、label 优化、写放大理论（Dostoevsky、bLSM 路线）（⚠️）。
- 云原生化：写放大小题化——S3 上的 LSM（Delta 压实、PolarFS）与 CaaS-LSM（库内已建档）等把合并外置（⚠️）。
- 2024–2026：向量索引（HNSW 段文件）与倒排索引普遍复用 LSM 分层合并骨架——"LSM 是后台整理范式"已成共识（⚠️ 判断）。
