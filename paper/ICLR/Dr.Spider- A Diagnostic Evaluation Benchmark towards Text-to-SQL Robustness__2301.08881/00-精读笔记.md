## 一句话总结

给 Text-to-SQL 模型做一次全面「体检」：在 Spider 的开发集上设计 17 种扰动（改数据库、改自然语言问句、改 SQL），看模型在「题面稍微变一变」时还稳不稳——结果发现最鲁棒的模型整体也要掉约 14 个点。

## 0. 给新手的阅读前置（背景知识地图）

- 子方向解决什么大问题：Text-to-SQL 把「自然语言问题」翻译成可执行的 SQL。模型在标准基准（如 Spider）上准确率很高，但真实用户的问法千奇百怪、数据库也在变，模型是否「背题」而非「真懂」？这需要鲁棒性（robustness）评测。
- 为什么难：扰动必须是「语义等价或语义有控制的改变」——改了问句但不能改变正确答案；同时扰动维度多（库结构、问句、SQL 三层），单靠人工规则覆盖不了语言多样性。
- 几类主流解法：

| 路线 | 代表 | 直觉 |
|------|------|------|
| 同义替换类 | Spider-Syn | 把列名/关键词换成同义词 |
| 知识增强类 | Spider-DK | 在问句中加领域知识 |
| 现实化类 | Spider-Realistic | 去掉问句中的列名提示 |
| 综合诊断类 | Dr.Spider（本文） | DB/NLQ/SQL 三维 17 种扰动的系统化体检 |

- 本文属哪类：综合诊断类——一次覆盖三大输入层面的细粒度扰动家族。
- 关键名词直觉解释：
  - *Perturbation（扰动）*：对输入做受控的小改动（如换列名拼写、改问句措辞），正确 SQL 不应（或应按规则）变化。
  - *NLQ*：Natural Language Question，用户的自然语言问句。
  - *Test-suite (execution) evaluation*：不只比对 SQL 文本，而是用多个等价测试数据库执行结果来判对错，是 Text-to-SQL 的标准评法。

## 1. 问题背景与动机

- 前人工作：神经 Text-to-SQL 模型（RAT-SQL、SmBoP、PICARD、T5 系等）在 Spider 等跨领域基准上表现优异；此前的鲁棒性测试集（Spider-Syn、Spider-DK、AdvETA 等）揭示了模型对任务特定扰动的脆弱性。
- 前人缺陷（论文逐条指出）：
  1. 只关注个别现象：以往鲁棒性测试集通常只针对单一语言现象或单一维度，不成体系；
  2. 依赖规则或少量人工样本：限制了扰动的自然性与多样性；
  3. 无法覆盖语言丰富度：例如需要句级改写（paraphrase）的 NLQ 扰动，规则方法生成不了；
  4. 缺细分分析：缺乏对模型设计选择（模型大小、解码器结构、实体链接组件）与鲁棒性关系的系统拆解。

## 2. 核心方法

- 最直观类比：驾校考试不能只考「标准题库」，Dr.Spider 相当于把同一道驾驶题换成三种天气（数据库变了）、三种问法（考官换措辞）、三种路线表达（标准答案换写法）来考，看司机是不是只会背路线。
- 具体做法（输入 → 关键操作 → 输出）：
  - 输入：Spider 的开发集（跨领域 Text-to-SQL 基准）；
  - 关键操作：设计 17 种扰动，分三组——
    - DB 扰动（3 种）：利用数据库结构特性按预定义规则改数据库（表名/列名/值等，测试模型是否真读懂 schema）；
    - NLQ 扰动（9 种）：提出「专家-众包-AI 协同」框架，用大规模预训练语言模型（OPT）模拟人类构造自然语言问题的行为来生成多样化改写，再经人工筛选；
    - SQL 扰动（5 种）：程序化修改 SQL 的局部语义及问句中对应 token，尽量少动表面文字，测模型对局部语义变化的敏感度；
  - 输出：约 15K 条扰动样本（论文 v1 数据），形成 pre-perturbation / post-perturbation 平行测试集，用 test-suite evaluation 打分。
- 理论性质/保证：评测型工作，无算法定理；其「保证」在于扰动构造的语义控制（扰动后正确答案由构造规则确定）。

## 3. 变体 / 工程版（如有）

- 官方仓库将测试集按前缀组织：`DB_*`（3 套）、`NLQ_*`（9 套）、`SQL_*`（5 套），每套含扰动前后平行数据，方便任何模型即插即测（README 核实）。
- 仓库提供 leaderboard（微调模型与 in-context learning 方法两条榜）：微调阵营中 PICARD 76.6→65.9（pre→post 平均 EX），Codex 上下文学习 74.6→64.4（README 数字，经核实）。

## 4. 实验结论（概览）

- 对比基线：SOTA Text-to-SQL 模型——RAT-SQL、SmBoP、T5-3B(+LK)、PICARD 等微调模型，以及 Codex 等 in-context learning 方法（README leaderboard 与论文核实）。
- 数据集：基于 Spider dev 集构造的 17 个扰动测试集（DB 3 + NLQ 9 + SQL 5）。
- 指标：执行准确率（EX）的扰动前后对比。
- 结论方向（摘要核实）：
  1. 即使最鲁棒的模型，总体也出现 14.0% 的性能下降；
  2. 在最具挑战性的扰动上下降高达 50.7%；
  3. 提供 breakdown 分析：模型规模、解码器架构、实体链接组件对鲁棒性各有影响（🔧 各分项结论查论文正文）。

## 5. 开源代码与动手实践

- 仓库地址：论文官方 https://github.com/awslabs/diagnostic-robustness-text-to-sql（v1 脚注）；作者镜像 https://github.com/shuaichenchang/diagnostic-robustness-text-to-sql（当前可用，含完整数据与评测脚本）；占位符的 https://github.com/saparina/text2sql-nlvariation 为社区相关实现（保留备查）。
- 语言：Python（数据预处理 `data_preprocess.py`、评测脚本、基于 test-suite evaluation 的打分）。
- 典型流程（教学示意，以 README 为准 🔧）：
  ```bash
  mkdir data && tar -xvf data.tar.gz -C data   # 解压 17 套扰动数据
  python data_preprocess.py                     # 从 Spider dev 拷贝原始库/表
  # 1) 让你的模型跑 Spider-dev，预测 SQL 存到 predictions/Spider-dev/<model>/pred.sql
  # 2) 让你的模型跑每个 post-perturbation 集并存预测
  python copy_pre_perturbation_predictions.py --model [model_name]
  # 3) 用 test-suite evaluation 在每个扰动集上评测
  ```
- 资源提醒：数据打包为 `data.tar.gz`；评测依赖 Spider 官方 test-suite 评测环境；注意 Spider 数据集自身许可对本基准的约束 🔧。

## 7. 2026 视角（🔧）

- LLM 时代 Text-to-SQL 主流已转向 in-context learning、RAG（schema linking + few-shot 示例检索）与微调小模型（如 NSQL、CodeS）的路线之争；Dr.Spider 揭示的「表面措辞敏感」问题仍是今天 prompt 工程与 schema linking 的核心痛点。
- 鲁棒性评测逐渐被更贴近真实企业场景的基准（BIRD、Spider 2.0）部分接管，但「受控扰动诊断」方法学仍被广泛复用。
- 后续趋势：多轮/多方言/企业级 schema、SQL 方言差异、以及把鲁棒性作为 RL 微调奖励信号的一部分。

## 8. 新手学习路线

- 10 分钟：读摘要 + 本笔记第 0 节，记住「DB/NLQ/SQL 三维 17 扰动」框架。
- 30 分钟：看官方仓库 README 的目录结构与 leaderboard 表，挑 1-2 个扰动集（如 NLQ 改写类）看具体样例；有条件用一个小模型在 Spider-dev 上跑通评测脚本。
- 进阶：读论文第 4-5 章 breakdown 分析，理解模型规模/解码器/实体链接对鲁棒性的影响；再对照 BIRD 论文思考「受控扰动」与「真实噪声」两种评测哲学的差异。
