## 一、来源与版本考证（三处必须知道的坑）

1. **页码有两个互斥版本，USENIX 自己就是错的之一。** USENIX 论文页的 BibTeX 写 `pages = {261--264}`，但**官方 PDF 的页眉实印是 251 起、264 止（共 14 页）**：第 1 页页眉 "…(OSDI '12) **251** Spanner: Google's Globally-Distributed Database"，末页页眉 "**264** …"。4 页装不下 14 页正文，故 BibTeX 著录明显有误；dblp 通说的 **251–264** 与 PDF 实物一致，本笔记采用 251–264。→ 教训：**页码以 PDF 页眉为准，不要相信会议网站的引用块。**
2. **术语在两版之间被换掉。** OSDI'12 用 **directory** 作为复制/局部性/搬迁的单位，且作者自己打趣："**directory 这个词的选择是一次历史意外（a historical accident）；更合适的名字也许是 bucket**"。TOCS'13 把它改名为 **tablet**。因此同一概念在两个版本里名字不同，二手资料常混用；本笔记以 OSDI'12 的 directory 为主，并标注它**与 Bigtable 的 tablet 不是一回事**（§2 明确说"不同于 Bigtable，Spanner 给数据分配时间戳"）。
3. **两个"流行但非本文"的术语，必须一并纠正。**（a）**"intent partition" 不属于 OSDI'12**：全文 PDF 检索 `intent` / `partition of intent` → **零命中**；OSDI'12 里对应机制的名字是 **τ_TM^safe（事务管理器安全时间）+ §4.2.4 用锁表中"键区间 → 已 prepare 事务时间戳"的细粒度映射来消除伪冲突**，"intent partition" 是 TOCS'13 扩展版对该机制的重命名与展开——**本次未能取得 TOCS 全文**（ACM 付费墙、四个公开镜像均 404/403），故该词的确切定义标注为**通说、未直接核实**，§3.5 只讲 OSDI'12 已核实的实现。（b）**`PRODO` 同样不是本文术语**：全文检索 → 零命中，论文里也没有任何近似拼写的协议名；真实存在的组合是 **"客户端驱动的 2PC" + "每个参与者的 prepare/commit 记录本身走 Paxos"**（§4.2.1）。下文按论文原词讲解，不采用这两个词。

## 二、背景与问题

### 2.1 从 Bigtable 的抱怨里长出来的数据库

论文 §1 的起点不是理论，而是一条被反复收到的用户反馈：尽管许多项目愉快地使用 Bigtable，**"我们也持续收到用户抱怨，说 Bigtable 对某些应用难以使用——那些有复杂、演化中 schema 的应用，以及在广域复制存在时要求强一致性的应用"**。正因为如此，Google 内部许多应用选择了 **Megastore**（半关系模型 + 同步复制），"**尽管它的写吞吐相对较差**"。由此论文给出一句自我定位，值得单独引用：**"Spanner 从一个 Bigtable 式的版本化键值存储，演化为一个带时间性的多版本数据库（a temporal multi-version database）。"** 数据存在有模式的半关系表里；数据被版本化，**每个版本自动带上其提交时间戳**；旧版本受可配置的垃圾回收策略约束；应用可以在旧时间戳上读。

### 2.2 它宣称解决的问题

- **两个"在分布式数据库里很难实现"的特性**（§1 原话）：(a) **外部一致（externally consistent）** 的读写；(b) **整个数据库在某一时间戳上的全局一致读**。这两者带来三个直接收益：**一致备份、一致的 MapReduce 执行、原子 schema 变更**——全部在全球尺度上、且在持续有事务进行时完成。
- **外部一致的定义（论文自己的措辞，含一个重要等号）**：事务被赋予**具有全局意义的提交时间戳，且时间戳反映串行化序**；若 T1 在 T2 开始之前提交，则 T1 的提交时间戳小于 T2。论文进一步写明 **"外部一致性（或者等价地，线性一致性 [20]）"**——即本文把 external consistency 与 linearizability 当作同一性质使用（引用时不要以为二者是不同概念）；并宣称 **"Spanner 是第一个在全球尺度提供这类保证的系统"**。
- **关键使能器与代价（全文题眼）**：**"新的 TrueTime API 及其实现是关键使能器……如果不确定性很大，Spanner 就会慢下来等掉这段不确定性（Spanner slows down to wait out that uncertainty）。"** 正确性直接以时钟质量为前提。运维上，复制配置可由应用**在细粒度上动态控制**——哪些机房存哪些数据、副本离用户多远（控读延迟）、副本之间多远（控写延迟）、保几个副本（控持久性/可用性/读性能），系统还能**在机房之间透明搬迁数据以均衡资源使用**；一个 Spanner 部署称为一个 **universe**，因为管理的是全球数据，"**运行的 universe 只有个位数**"（当时是 test/playground、development/production、production-only 三个）。

## 三、核心机制精读

### 3.1 分层与 directory/Paxos 组（§2）

```
 客户端(F1 / SQL / MapReduce)
        │
 ┌──────▼───────────────────────────────────────────────┐
 │ spanserver   （100~1000 个 tablet 实例）             │
 │  ├─ 事务/目录管理层： 锁表(key range → lock state)   │  ← 2PL + wound-wait + keepalive
 │  ├─ 复制状态机层：    每个 tablet 一个 Paxos 状态机  │  ← 长寿命 leader + 10s 租约
 │  └─ tablet：(key:string, timestamp:int64) → string   │  ← 与 Bigtable 同为 KV，但**给数据打时间戳**
 ├──────────────────────────────────────────────────────┤
 │ Unisys 文件 → Colossus（GFS 的后继）                 │
 └──────────────────────────────────────────────────────┘
   directory = 一组共享同一 key 前缀的**连续键** = 复制/局部性/搬迁单位
   Paxos 组  = 一个 directory 的副本集合（默认 3~5，跨机房）
```

- **两处规模/演进坦白**：早期版本曾让一个 tablet 承载**多个** Paxos 状态机，"**该设计的复杂度（多种复制配置）让我们放弃了它**"；增删副本靠后台任务 **Movedir**（同时用于组间搬迁 directory），因为 **"Spanner 尚不支持 Paxos 内部的配置变更"**。另需注意**写必须在 leader 上启动 Paxos，读可以直连任何"足够新"的副本**（原文：reads "access state directly from the underlying tablet at any replica that is sufficiently up-to-date"）；**每个 leader 副本本地维护锁表**，把 key 区间映射到锁状态；一句被忽视的性能前提：**"拥有长寿命的 Paxos leader 对高效管理锁表至关重要"**——细粒度共识与悲观锁必须绑在同一台机器上，否则锁表每次换主都要重建。
- **数据模型不是纯关系型**：**行必须有名字**——每张表要求一或多列**有序主键**；"只要某列有值（即使是 NULL），行才存在"。这个结构被刻意强加，因为**它让应用通过选 key 来控制局部性**。层级用 **`INTERLEAVE IN PARENT … ON DELETE CASCADE`** 声明，层级顶端是 **directory table**：该表中主键为 K 的行 + 所有后代表中以 K 为字典序前缀的行 = 一个 directory。原文点明意义：**"这种交错之所以重要，是因为它让客户端能描述跨多表的局部性关系——在一个分片分布式数据库里这是好性能的必要条件；没有它，Spanner 无从知道最重要的局部性关系。"**

### 3.2 TrueTime：把时钟不确定性做成 API（§3）

论文只给 API 骨架，实现细节留给"另一篇论文"（原话如此）。Table 1 就是全部三个方法：

| 方法 | 语义（原文） |
|---|---|
| `TT.now()` | 返回 `TTinterval: [earliest, latest]` |
| `TT.after(t)` | 当 t **确实已经过去**时返回 true |
| `TT.before(t)` | 当 t **确实尚未到达**时返回 true |

- 形式化保证：**`tt.earliest ≤ τ_abs(e_now) ≤ tt.latest`**（任何一次调用的区间必包含该调用事件的绝对时刻）；**ε = 区间宽度的一半（瞬时误差界）**，**ε̄ = 平均误差界**。时间**纪元类比 UNIX time，并做闰秒抹平（leap-second smearing）**。
- 实现（§3，全部为原文事实）：每机房若干 **time master**——多数配 **GPS 接收机 + 专用天线且物理隔离**（降低天线故障、无线电干扰与欺骗的相关性），其余称 **Armageddon masters**，配**原子钟**；作者特意算了一句成本账：**"原子钟并不贵：一台 Armageddon master 的成本与一台 GPS master 同量级。"** 各 master 互相比较时间基准；每台 master **拿自己的参考与自己本地钟的走时速率交叉校验，若明显发散就把自己踢出**。daemons **向多个 master 轮询**（近邻机房的 GPS master + 远机房 GPS master + 若干 Armageddon master），并**用 Marzullo 算法的变体检测并剔除说谎者**，据此把本地钟同步到"不说谎者"上；本地钟频率超出按器件规格与环境保守推出的界则该机器被踢。
- **量化与哲学（生产实测，§3）**：**ε 通常呈锯齿形，在每个轮询周期内从约 1 ms 涨到约 7 ms；因此 ε̄ 多数时候为 4 ms。当前轮询周期 30 秒，采用的漂移率 200 微秒/秒。** 另在 §1 处口径为"不确定性一般小于 10ms"。设计哲学一句话：**TrueTime 不是"更准的时钟"，而是"知道自己有多不准、并能回答'某时刻是否已确实过去'的时钟"**——外部一致性只需要后者。

### 3.3 提交时间戳协议：Start + Commit Wait（§4.1.2）

Spanner 的时间戳**不是从中心授时服务领号**，而是**由 Paxos 在提交写入时赋予**，并靠两条不变式撑住外部一致性：

```
不变式①（单调性）同一 Paxos 组内，分配给 Paxos 写的时间戳单调递增，**跨 leader 也成立**。
         跨 leader 如何保证？→ 靠不变式③：leader 只能在自己租约区间内分配时间戳。
         每分配一个 s，就把 s_max 推进到 s。
不变式②（外部一致）start(T2) 晚于 commit(T1) ⇒ s1 < s2。
不变式③（租约不相交）同一 Paxos 组任意两个 leader 的租约区间互不相交（默认租约 10s）。
         由此推出**退位约束**：leader 退位前必须等到 TT.after(s_max) 为真。
```

两条协议规则即足以保证不变式②，论文给出了完整证明链（照录）：

```
Start        协调者 leader 分配 s_i ≥ TT.now().latest，且在 e_server_i（提交请求到达）之后计算
Commit Wait  协调者 leader 确保客户端在 TT.after(s_i) 为真之前看不到 Ti 提交的任何数据
             ⇒ s_i < τ_abs(e_commit_i)

证明：s1 < τ_abs(e_commit_1)      (commit wait)
      τ_abs(e_commit_1) < τ_abs(e_start_2)   (假设)
      τ_abs(e_start_2) ≤ τ_abs(e_server_2)   (因果性)
      τ_abs(e_server_2) ≤ s2                  (start)
      ∴ s1 < s2                                (传递性)
```

注意**"参与者 leader 在此无关紧要"**（原文括注）——Start 规则只约束协调者；参与者只在下一条规则的实现里被卷入（§4.2.1）。这一分工是理解"为什么每个参与者还要挑 prepare 时间戳"的关键。

### 3.4 事务类型与"谁在哪读"（§4.1，Table 2）

| 操作 | 并发控制 | 是否加锁 | 服务节点 |
|---|---|---|---|
| 读写事务 | §4.1.2 | **pessimistic（2PL）** | leader |
| 只读事务 | §4.1.4 | **lock-free** | 时间戳必须在 leader；读可在任意（受 §4.1.3 约束） |
| 快照读（客户端给定时间戳） | — | **lock-free** | 任意满足 §4.1.3 的副本 |
| 快照读（客户端给定陈旧上界） | §4.1.3 | **lock-free** | 同上 |

- 只读事务**必须预先声明为无写**，"它不是'恰好没写的读写事务'"；读在系统选定的时间戳上无锁执行，**因此不会阻塞进来的写**；论文称其"具有**快照隔离 [6] 的性能优势**"。只读事务与快照读一旦被选定时间戳，**除非该时刻数据已被 GC，提交即成定局**——因此**"客户端不必在自己的重试循环里缓冲结果"**；服务器失败时，客户端**靠重放"时间戳 + 当前读取位置"就能在另一台服务器上继续查询**。这是"读不阻塞"带来的实际编程收益。

### 3.5 安全时间、2PC-over-Paxos，与"任务书所说的 intent partition"（§4.1.3、§4.2.1、§4.2.4）

**(a) 副本何时"足够新"？** 每个副本维护 **`τ_safe = min(τ_safe^Paxos, τ_safe^TM)`**，读在 τ 上可被满足当且仅当 `τ ≤ τ_safe`。

- `τ_safe^Paxos` = **已应用的最高 Paxos 写的时间戳**（因时间戳单调且写按序应用，故该时刻之下不会再出现写）。`τ_safe^TM` = 该组上**所有"已 prepare 未 commit"事务的 prepare 时间戳最小值减一**（`min_i(s_prepare_{i,g}) − 1`），无此类事务则不受限——原因：**参与者尚不知道这些事务会不会提交，受影响状态是不确定的**。协调者保证 **s_i ≥ 所有参与组的 s_prepare**，因此这条下界可靠。 只读事务的 `s_read` 选择（§4.1.4/§4.2.2）：简单做法 `s_read = TT.now().latest` 保外部一致，但可能因 `τ_safe` 未推进而阻塞，所以"**Spanner 应当分配能满足外部一致的最旧时间戳**"。为此**要求每个只读事务提供 scope 表达式**（概括整事务将读哪些 key；独立查询可自动推断）。单组服务时→ 交给该组 leader（**当前实现只允许在 Paxos leader 上选 s_read**），且**单机读通常优于 `TT.now().latest`**：定义 **`LastTS()`** = 某组最后一次已提交写的时间戳，**若无 prepare 中的事务，则 `s_read = LastTS()` 平凡满足外部一致**。多组服务时最复杂的方案是与所有组 leader 做一轮基于 `LastTS()` 的协商；**Spanner 当前实现选了简单方案——省掉那一轮协商，直接在 `TT.now().latest` 上读（可能要等安全时间推进）。**

**(b) 读写事务与 2PC（§4.2.1）——"被 Paxos 救活的 2PC"**

```
伪码（按论文 §4.2.1 逐步还原）
CLIENT                                        SPANSERVER
─ 事务内读：发给组 leader，leader 取读锁后读最新版本
─ 冲突时用 wound-wait[33] 避免死锁（而非等待图检测）
─ 写全部缓冲在客户端，直到 commit 才发出
  · 期间持续发 keepalive，防参与者 leader 超时回收本事务
─ commit：客户端自选一个"协调组"，把(协调者身份+缓冲写)发给**每个参与者的 leader**
        ──► 非协调参与者 leader：先取写锁 → 挑一个**大于自己此前所有已分配时间戳**的
            prepare 时间戳 → **把 prepare 记录通过 Paxos 落日志** → 上报 prepare 时间戳
        ──► 协调者 leader：也取写锁，但**跳过 prepare 阶段**；收齐所有人的 prepare 时间戳
            后才挑整事务的 s；→ **等 TT.after(s)**（commit wait）→ 提交记录走 Paxos
```

- **"让客户端驱动 2PC"的理由是网络物理学的**："这避免了数据跨越广域网链路被发送两次。" **为什么不再有 Gray 式阻塞**：2PC 的协调者/参与者状态本身被 **Paxos 复制**，leader 崩溃后新 leader 从 Paxos 日志里就能读出"这个事务是否已决"，因此不需要悬挂在 prepared。这与 [`../doi_1981_gray_transaction_concept/00-精读笔记.md`](../doi_1981_gray_transaction_concept/00-精读笔记.md) §2.5 第 5 条构成正面对话——**共识没有取代 2PC，而是把 2PC 的状态变成可恢复的复制状态机**。
- **注意 2PL 并未被 TO 取代**：论文的组合是"**读写事务的读写用两阶段锁；分配时间戳靠 2PL 的锁序**"（"Transactional reads and writes use two-phase locking. As a result, they can be assigned timestamps at any time when all locks have been acquired, but before any locks have been released."）。把它读成"Spanner 用 TO 替代了 2PL"是常见误读。

**(c) 伪冲突与"intent partition 之实"**（§4.2.4 Refinements，OSDI'12 已核实的原文）

- **`τ_safe^TM` 的弱点**："**单个 prepare 中的事务就会阻止 tsafe 推进。结果，更晚时间戳上的读全部无法执行，即使这些读与该事务不冲突。**" **修法**："通过在锁表里增加一个**从 key 区间到已 prepare 事务时间戳的细粒度映射**来消除伪冲突；这一信息**可以存放在锁表中——它本来就把 key 区间映射到锁元数据**。读到来时，只需与它冲突的那些 key 区间的细粒度安全时间比较。"
- **`LastTS()` 有对称的弱点**（刚提交的事务会迫使无冲突的只读事务也排到它之后），可用"锁表里 key 区间 → 提交时间戳的细粒度映射"同样补救——而论文在这里留下一句重要的坦白：**"我们尚未实现这个优化。"** 另外 `τ_safe^Paxos` 还有第三个弱点：**没有 Paxos 写时它无法推进**（§4.2.4 末）。**结论**：任务书要求精读的"intent partition"，在 OSDI'12 里的**真实对应物就是上面这些段落**（细粒度 safe time / 锁表里的 prepared-时间戳映射）；TOCS'13 给它起名 intent partition——**本笔记只把已核实的机制写成事实，把该词的出处标为通说。**

**(d) 原子 schema 变更（§4.2.3）——TrueTime 独占的能力**

- 为什么不能用普通事务："**参与者数量（一个数据库里的组数）可能达到百万级**"。做法：schema-change 事务**被显式赋予一个未来的时间戳，并在 prepare 阶段注册**；因此**跨数千台服务器的 schema 变更能以对其他并发活动极小的干扰完成**。读写隐式依赖 schema，故要与任何已注册的 schema-change 时间戳 t 同步：**自身时间戳早于 t 者可继续，晚于 t 者必须阻塞在它之后**。原文判词：**"没有 TrueTime，把 schema 变更定义在时刻 t 上是毫无意义的。"**（对比：Bigtable 支持单机房原子 schema 变更，但**会阻塞一切操作**。）

### 3.6 论点逻辑链小结

1. 用户要的是**关系语义 + 广域同步复制下的强一致**，Bigtable 给不了，Megastore 给了但写吞吐差 ⇒ 需要新的底座。而全球"一个数据库"的语义核心难点只有一个：**给并发事务分配一个既反映真实时间先后、又能被所有副本一致认可的序**。
2. 解法 = **物理时间戳**（而非逻辑号）；物理时间不可信的障碍，用**"输出区间 + 等待越过区间上界"**绕开 ⇒ **TrueTime + commit wait**。序要持久且不可反悔 ⇒ **时间戳由 Paxos 写入时赋予**，2PC 状态也进 Paxos 日志 ⇒ **同时解决"2PC 悬挂"和"跨 leader 时间戳单调"**（靠租约不相交 + 退位前等 `TT.after(s_max)`）。
3. 读不能挡在写/协调者前面 ⇒ **MVCC 版本 + 安全时间 + 无锁快照/只读事务** ⇒ 读扩展与历史读、一致备份、一致 MapReduce。而一切的性能上界 = **ε**、一切的正确性前提 = **ε 真的是界**，所以**硬件（GPS+原子钟）与运维（剔除说谎者/坏机器）成了数据库正确性的一部分**。

## 四、实验与生产经验（取自论文 §5，全部标注图/表号）

### 4.1 微基准与"等待税"的实测（§5.1，Table 3、Table 4）

测试环境（原文逐项）：**分时共享机器**，每 spanserver 用 **4GB RAM + 4 核（AMD Barcelona 2200MHz）**；客户端另机；每 zone 一个 spanserver；机房间**网络距离 < 1ms**（作者补了一句"这种布局应该很常见：多数应用并不需要把数据分散到全世界"）；库为 **50 个 Paxos 组、2500 个 directory**；操作是 **4KB** 的独立读写；**压缩后全部读命中内存**，故"我们只测 Spanner 调用栈的开销"；先跑一轮不计量的读来预热位置缓存。**Table 3（延迟 ms / 吞吐 Kops/sec，10 次运行的均值 ± 标准差）**

| 1D（关 commit wait） | 9.4±.6 | — | — | | 4.0±.3 | — | — |

**Table 4：2PC 的可扩展性（参与方数 → 提交延迟均值 / 99 分位，ms）**：`1: 17.0±1.4 / 75.0±34.9` → `5: 31.5±6.2 / 104.5±52.2` → `25: 35.5±5.6 / 100.4±42.7` → `50: 42.7±4.1 / 93.7±22.9` → `100: 71.4±7.6 / 131.2±17.6` → **`200: 150.5±11.0 / 320.3±35.1`**。读法：**跨 200 组的提交中位已贵到 150ms 级、99 分位 320ms**——这正是 §4.2.3 说"schema 变更不能用普通事务（参与者可能上百万）"的量化依据，也是应用应尽力把相关数据交错进同一 directory 以走单组提交的理由。

### 4.2 杀机房实验（§5.2，Figure 5）

配置：测试库切成 **1250 个 Paxos 组**，**100 个客户端**以合计 **50K reads/s** 持续发非快照读，**所有 leader 显式放置在 Z1**；开始 5 秒后杀掉某 zone 的全部服务器，三种姿势：**杀非 leader 区 Z2** → 读吞吐**无影响**（读本来就可打到任意够新副本）；**leader-soft**（预先通知交接后再杀 Z1）→ **下降在图上看不见，约 3–4%**；**leader-hard**（直接杀 Z1）→ **完成速率几乎掉到 0**，随各组重选 leader 升到约 **100K reads/s**（作者明说是实验伪影：系统有余量且 leader 不可用期操作被排队），随后回落到稳态。
- **恢复时间 ≈ 10 秒**，因为 leader 租约就是 10 秒——到期时间均匀散布在 10 秒内，到期即重选；约 10 秒后所有组重新有 leader。**更短租约能降低服务器死亡对可用性的影响，但会带来更多租约续期流量**；作者当时"**正在设计并实现让从副本在 leader 故障时释放 leader 租约的机制**"。可迁移的结论：**"无 leader = 不能读"**——Spanner 的读扩展依赖"足够新的副本"，而时间戳分配（只读事务）与 leader 生命周期都挂在租约上，**共识系统的可用性瓶颈往往不在日志复制，而在租约到期窗口。**

### 4.3 TrueTime 自身的可靠性证据（§5.3，Figure 6）

- 两个必答问题：**ε 真的是界吗？ε 会恶化到多糟？** 对前者，作者给了一条运维统计：**"机器数据显示，坏 CPU 的出现概率是坏时钟的 6 倍。也就是说，相对于严重得多的其他硬件问题，时钟问题极为罕见。"** 结论是"TrueTime 的实现与我们所依赖的任何其他软件一样可信"。
- 对后者：**Figure 6 在数千台 spanserver、机房相距最远 2200km 的范围内采样 timeslave 刚轮询完 time master 之后的 ε 值**（此采样**刻意抹掉了本地钟造成的锯齿**，因此测的是"master 不确定性（通常为 0）+ 到 master 的通信延迟"），画 90/99/99.9 分位。**两次可归因的抖动，作者直接归因给运维动作**：**3 月 30 日的尾部延迟下降来自减少瞬时网络链路拥塞的网络改进**；**4 月 13 日一次约一小时的 ε 抬升，源于一个机房为例行维护关停了两台 time master。** ⇒ 结论：**"授时基础设施是数据库的性能依赖项，其维护窗口会直接体现在提交延迟上。"**

### 4.4 首个生产客户 F1（§5.4，Table 5、Table 6）

- **时间线与迁移前的痛**：Spanner **自 2011 年初**开始在生产负载下被实验性评估，作为 Google 广告后台重写项目 **F1** 的一部分。F1 原来建立在**手工分片很多层的 MySQL** 上；未压缩数据集**几十 TB**——"相比许多 NoSQL 实例算小，但已大到让分片 MySQL 为难"。旧方案把每个客户及其全部相关数据放进固定分片，好处是能按客户使用索引和复杂查询，代价是**业务逻辑里必须知道分片**；而**"最后一次 resharding 耗费两年多的高强度工作，需要协调与测试横跨数十个团队以控制风险"**，复杂到无法例行执行——于是团队只能**把一部分数据放到外部 Bigtable 里限制 MySQL 增长，这又损害了事务行为与跨全部数据查询的能力**（这是全文最有说服力的"问题陈述"）。
- **选 Spanner 的三条理由（原文列举）**：免去手工 resharding；提供同步复制与自动故障切换（MySQL 主从的 failover 困难，且**冒数据丢失与停机风险**）；F1 需要强事务语义。
- **Table 5：directory 内 fragment 数分布**：1 个 → **超过 1 亿个 directory**；2–4 → 341；5–9 → 5336；10–14 → 232；15–99 → 34；100–500 → **7**。绝大多数 directory（即绝大多数客户）只有 1 个 fragment，意味着其读写被保证发生在单台服务器上；而 **>100 fragment 的 directory 全是存 F1 二级索引的表**，跨多 fragment 写"极其罕见"，只在**未调优的批量导入以事务方式执行时**见过。⇒ "热行/索引写要打散多个 directory"这一设计担忧在生产里几乎没被触发。
- **Table 6：F1 侧感知的操作延迟（24 小时）**：**所有读 mean 8.7ms / σ 376.4ms / 计数 21.5B**；**单站点提交 72.3 / 112.8 / 31.2M**；**多站点提交 103.0 / 52.2 / 32.1M**（东海岸机房副本在挑 leader 时优先级更高，数据即从这些机房的 F1 服务器测得）。两个坦率解释：**写延迟大 σ 来自锁冲突肥尾**；**读延迟更大 σ 部分因 leader 分布在两机房、只有一个有 SSD**，且统计含两机房**每一次**读——**读字节数均值约 1.6KB、σ 约 119KB**（读大小分布本身极重尾）。
- 一项优雅的技巧：**Spanner 的时间戳语义让 F1 能高效维护"由数据库状态计算出的内存数据结构"**——F1 把**全部变更的逻辑历史日志作为每个事务的一部分写进 Spanner**；初始化时在某个时间戳上取全量快照，之后**只读增量变更**来更新内存结构。相关工作的自我定位（§6）：**"跨机房一致复制作为存储服务已由 Megastore 和 DynamoDB 提供。DynamoDB 提供键值接口，且只在一个 region 内复制。Spanner 沿用 Megastore 的半关系数据模型，甚至沿用相似的模式语言。"** 并直言 **"Megastore 没有达到高性能"**：它架在 Bigtable 之上，通信代价高，且**不支持长寿命 leader**——多副本都可发起写，于是**即使逻辑上不冲突的写在 Paxos 协议里也必然冲突，一个 Paxos 组的吞吐在每秒几次写就崩掉**。

## 五、对比分析：Spanner ↔ Dynamo（同一光谱的两端锚点）

对照阅读：[`../doi_10.1145_1294261.1294281/00-精读笔记.md`](../doi_10.1145_1294261.1294281/00-精读笔记.md)。两篇都是"大厂自研 + 设计 + 生产经验"体裁，相隔五年，取向**互为镜像**；把它们并读是理解"一致性—可用性—延迟"三角最快的路径。

| 维度 | Dynamo (2007, AP 端) | Spanner (2012, ACID 端) |
|---|---|---|
| 抽象 | KV，`get/put(key, ctx, obj)`，对象 <1MB，无 schema | 半关系 + SQL，**有序主键 + INTERLEAVE 层级**，多版本带时间戳 |
| 一致性 | 最终一致 + 会话保证；**无隔离**、仅单键更新 | **外部一致（=线性一致）** + 可串行化事务 + 全局一致快照读 |
| 冲突 | **不裁定**：版本分叉交应用调和（semantic reconciliation） | **必裁定**：2PL 定序 + Paxos 选唯一胜者 + wound-wait 消死锁 |
| 时间 | **向量时钟**（逻辑偏序，可能不可比） | **TrueTime**（物理区间 + `TT.after` 等待） |
| 复制 | 异步补齐 + sloppy quorum（**无共识**） | **同步**：多数派持久化才返回；每 directory 一个 Paxos 组 |
| 写可用性来源 | **代收 + hint**（任何健康节点都能接写） | **必须找 leader**（写只能在 leader 启动 Paxos） |
| 收敛手段 | read repair + **Merkle 反熵**（事后对账） | 不需要对账：**复制即提交前提**；靠 Move/Split 再平衡 |
| 读扩展 | R=1 档当"高性能读引擎" | **follower 服务快照读**（实测吞吐随副本近乎线性，5 副本 50 Kops/s） |
| 故障应对对象 | 节点瞬时故障、整机房、网络分区 | leader 租约到期、机房被杀、time master 维护 |
| 关键性能代价 | 99.9 分位约 200ms（均值高一个量级）；分叉由并发写者驱动 | **每次写提交付 commit wait ≈ 5ms**；跨 200 组提交 150ms/99 分位 320ms |
| 谁付代价 | **应用程序员**（写调和、接受删除复活） | **硬件+物理定律**（每机房 GPS+原子钟、跨洋 RTT、光速下界） |
| 规模自陈 | **初版目标仅"数百存储主机"**，成员信息开销随规模线性增长 | universe **个位数**；单 F1 有 >1 亿 directory |

**三条最值得展开的对照**

1. **"R+W>N"不是共识，这个差别决定了两篇的全部分歧。** Dynamo 的读写集合相交只能给出"高概率读到最新 + 因果不乱"，因为它没有**唯一胜者裁定**机制；Spanner 用"leader + 多数派 + 2PC-over-Paxos"把裁定放进数据库内部。所以 Dynamo 必须保留并发版本并外溢到业务，Spanner 才敢说"事务时间戳反映串行化序"。详见 [`../../courses/并行与分布式系统/MIT6.824/notes/L10-一致性与线性一致性.md`](../../courses/并行与分布式系统/MIT6.824/notes/L10-一致性与线性一致性.md)。
2. **两篇是"人造时间"的两条技术路线**。向量时钟零硬件成本、只给偏序、可能不可比；TrueTime 要原子钟+GPS、给带界的物理时刻、可比较但需等待。**TiDB 的中心化 TSO 与 CockroachDB 的 HLC 是这两极的中间解**（前者用单点授时换掉硬件依赖，后者用混合逻辑时钟把不确定性上移给重试），见 [`../../courses/并行与分布式系统/MIT6.824/notes/L07-时间时钟与事件顺序.md`](../../courses/并行与分布式系统/MIT6.824/notes/L07-时间时钟与事件顺序.md) 与 [`../../db/db.md`](../../db/db.md) 的 TSO/HLC/TrueTime 取舍表。
3. **对 Gray 1981 两条局限的相反回答。** Gray 自陈局限：#1 强一致与高吞吐的张力、#5 分布式 2PC 阻塞。Dynamo 的处理是**承认并绕开**（放弃 C 与 I，2PC 根本不用）；Spanner 的处理是**正面对撞**（细化共识粒度到 directory、把 2PC 状态复制化从而消除 prepared 悬挂、用 commit wait 换外部一致），代价写在 Table 3/Table 4 里。两者合起来才是 Gray 那页 Limitations 的完整脚注——见 [`../doi_1981_gray_transaction_concept/00-精读笔记.md`](../doi_1981_gray_transaction_concept/00-精读笔记.md)。

**仓库内其它对照坐标**：[`../../book/分布式数据库入门进阶与实战/05-BASE与CAP及分布式一致性模型.md`](../../book/分布式数据库入门进阶与实战/05-BASE与CAP及分布式一致性模型.md)（该章有一句可作裁判式总结："Spanner 用'多数派 + 有界延迟（TrueTime）'把分区期的可用性换成了'少数侧拒绝读写'——被归 CP"）、`../../book/分布式数据库入门进阶与实战/06-事务基础与分布式事务.md`（14.2 节 Spanner 配方与 14.4 Calvin 对比）、`09-共识算法.md`（"单组粒度：一个 Raft 组吞吐有上限，所以 BigTable/TiKV/Spanner 都走…"）、`04-数据分片与数据复制.md`（把 Spanner 的 tablet 列入"分片分裂/合并"一栏）。

## 七、批判与延伸

**这篇论文站得住的地方**

1. **TrueTime 是概念层面的真创新**：不是"把钟做准"，而是**把不确定性提升为一等公民接口**（返回区间 + 能回答"是否确实已过"）。这使得正确性证明可以在"钟不准"的现实中成立（§4.1.2 的四步证明链）。
2. **它给出了一份罕见的"一致性定价单"**：关掉 commit wait 写延迟 14.4→9.4ms（≈5ms），Paxos 本身 ≈9ms，ε 一般 1–7ms、均值 4ms，跨 200 组提交 150ms。**"外部一致性贵多少"这个问题，本文是第一个给出生产量级答案的**。
3. **F1 一节是诚实的问题陈述，且机制之间的耦合讲得清楚**：几十 TB 就足以让分片 MySQL 崩溃、"最后一次 resharding 耗时两年多、横跨数十个团队"——这种把组织成本写进论文的做法，比任何抽象动机都有说服力；而为什么必须长寿命 leader（锁表效率）、为什么退位要等 `TT.after(s_max)`（租约不相交）、为什么客户端驱动 2PC（广域链路只走一次数据）——每个"为什么"都在原文里。

**需要批评与警惕的地方**

1. **正确性押在一个无法验证的物理假设上**：全部保证依赖"**ε 真的是界**"。作者给的是**统计式信心**（坏 CPU 比坏时钟常见 6 倍）与**运维证据**（Fig 6 的分位数），而不是证明。**GPS 欺骗、共模故障（如闰秒处理错误、卫星系统故障）、授时母机配置错误都在 §3 的失败模式清单里**——而一次时钟界被突破，后果是**已提交事务的序被永久颠倒且不可检测**。这是比 Dynamo 的"分叉"严重得多的故障类型：Dynamo 错了会看见多版本，Spanner 错了会看见**违反时序的串行序**。
2. **commit wait 与两处 safe-time 优化都只是"当前实现"的权宜，被作者自己指出可优化**：OSDI'12 留下"**我们尚未实现这个优化**"（`LastTS()` 细粒度化，§4.2.4），TOCS 版更明确承认协调者可等参与者先提交再等更短的时间。也就是说 **Table 3 的 5ms 不是下界，而 §4.2.4 的三个"弱点"段落是作者自陈的技术债**。
3. **可用性叙述有系统性偏乐观，且悲观并发控制与集中时间戳分配留下明确代价**：论文强调"多数派 + 少数派读写的分区容忍"，但 **Figure 5 的 leader-hard 实验里读吞吐"几乎掉到 0"、恢复要等约 10 秒租约到期**。把它当"五个九无代价"是误读：**"无 leader 即无读"是 Spanner 的真实边界**，而 leader 分布（优先级/搬迁）成了运维核心手段。另一面，只读事务的 `s_read` **当前只能在 Paxos leader 上分配**、多组场景**放弃协商而用 `TT.now().latest`（可能阻塞等安全时间）**——两条都在原文里以"当前实现"措辞承认；写延迟的大标准差被归因于**锁冲突肥尾**，即悲观并发控制在生产上确实是尾延迟主源。
4. **"第一个全球规模外部一致事务系统"这句宣言应连同前提一起引用**：前提是 Google 自建机房、每机房配 GPS+原子钟、可控网络、个位数 universe，且论文自己承认"多数应用并不需要把数据分散到全世界"。**没有该硬件预算时这句结论不可搬运**（TiKV 用 TSO、CockroachDB 用 HLC 正是对这一前提的替代性回应）。
5. **体裁限制**：**OSDI'12 只有 14 页、无分布式事务负载的端到端吞吐/扩展性曲线**（无 YCSB 式对比、无与 Megastore/Dynamo 的横向实验），大量深度（运维数据、五个九、intent partition、历史读）在 TOCS'13 与后续 SIGMOD'17 *Becoming a SQL System*。把本 PDF 当作 Spanner 的完整图景会漏掉这些。

**延伸线索**

- 版本对照：OSDI'12（本篇，无 DOI）↔ **TOCS'13 `10.1145/2491245`（有 DOI，含 intent partition 与更完整评测）** ↔ SIGMOD'17 *Spanner: Becoming a SQL System*。上游使能技术：GFS/Colossus、Bigtable、Paxos、2PL 与可串行化（Eswaran/Gray/Ries）、wound-wait、Marzullo 的一致性投票、**Megastore（直接的半关系前身）**。下游路线：**Cloud Spanner**（托管）、**CockroachDB**（HLC + 不确定性窗口，把模糊性交给重试）、**TiDB/TiKV**（Multi-Raft + 中心化 TSO，放弃 TrueTime 换实现简单）、**YugabyteDB**、**Amazon Aurora/DSQL**（同一目标、不同架构）、**Calvin**（确定性调度，与本仓库 `book/分布式数据库入门进阶与实战/06` 的 14.4 正面对照）。

## 九、一页总结（复习卡）

- **一句话**：把**时钟不确定性做成 API**（TrueTime 返回区间 + `TT.after` 等待），于是**物理时间可以当提交序用**；再用 **"每 directory 一个 Paxos 组 + 客户端驱动 2PC + 2PC 状态本身走 Paxos"** 消除 Gray 式阻塞——第一次在全球尺度上同时拿到 ACID、外部一致与读扩展。
- **三个必须记住的机制**：① Start + **Commit Wait** 两规则 → 外部一致性（四步证明）；② **租约不相交 + `s_max`** → 时间戳跨 leader 单调（且退位要等）；③ **`τ_safe = min(τ_safe^Paxos, τ_safe^TM)`** → 无锁快照/只读事务能打到任意够新的副本。
- **一组该背的数字**：ε 锯齿 **1→7ms**、ε̄ **4ms**、轮询 **30s**、漂移 **200us/s**、租约 **10s**；commit wait **≈5ms**、Paxos **≈9ms**；快照读吞吐 **13.5→38.5→50 Kops/s**（1→3→5 副本）；2PC 参与者 **1→200** 时提交 **17→150ms**（99 分位 **75→320ms**）；F1 实测：读 **8.7ms**（σ 376ms，21.5B 次）、单站提交 **72.3ms**、跨站 **103.0ms**；>1 亿个 directory 中绝大多数只含 **1 个 fragment**。
- **两条最容易被忽略的自我坦白 + 一条历史判词**：坦白是 `LastTS()` 细粒度优化"**我们尚未实现**"、杀 leader 区不预告时**读吞吐几乎掉到 0、约 10 秒才恢复**。而 Spanner 证明的不是"ACID 可以在全球做"，而是**"只要肯把物理定律（光速、时钟漂移）买进来当设计参数，ACID 就能在全球做"**——这既是它的成就，也是它不可普遍搬运的原因。Dynamo 说"一致性交给业务"，Spanner 说"时间交还给硬件"，NewSQL 十年史就是在这两句之间找中点。
