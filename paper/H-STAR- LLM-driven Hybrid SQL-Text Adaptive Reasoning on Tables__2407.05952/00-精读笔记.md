## 一句话总结
表格问答（Tabular QA）里，纯文本推理的 LLM 不会算数、纯 SQL/符号推理又读不懂语义——H-STAR 让 LLM 两样都用：先把大表精准裁剪出「需要的列和行」，再按问题类型自适应地决定是「语义直接查」还是「文本推理 + SQL 计算加持」，在三个基准上超过当时最强方法。

## 0. 给新手的阅读前置（背景知识地图）

- **大问题**：给一张表和一个自然语言问题，直接给出答案（Tabular QA / 事实核查）。难点是它同时需要「读懂人话」和「精确算数」。
- **为什么难**：LLM 对长表格注意力稀释（无关列/行干扰）；符号引擎（SQL、程序）缺乏语义泛化；两条路线各管一半。
- **主流解法**：

| 路线 | 直觉 | 弱点 |
|------|------|------|
| 文本推理（textual） | 把表格序列化成文本，让 LLM 直接读 | 数学/比较运算易错 |
| 符号推理（symbolic） | 生成 SQL/程序执行 | 语义理解弱，写不对查询 |
| 混合（hybrid） | 文本管理解，符号管计算 | 如何分工/何时切换是难点 |

- **本文属于**：混合路线（hybrid），核心创新在「分阶段 + 自适应」。
- **关键名词直觉**：
  - **Schema/子表抽取（table extraction）**：先从大表里挑出与问题相关的列，再挑出相关的行，只把「最小可用子表」喂给 LLM。
  - **自适应推理（adaptive reasoning）**：按问题类型路由——查值类走语义查找，计算/逻辑类走「文本推理为主、SQL 结果为辅」。
  - **Fact verification（事实核查）**：判断陈述与表格是否相符，与 QA 共用同一套能力。

## 1. 问题背景与动机

- 前人工作：文本路线（直接让 LLM 读表）与符号路线（如 BINDER 这类「LLM 写混合程序」的方法，H-STAR 仓库自述基于 BINDER 与 TabSQLify 两条前作）各有代表。
- 前人缺陷（依摘要逐条）：
  1. **文本推理**：语义解释强，但遇到数学运算、数值比较就出错。
  2. **符号推理**：计算可靠，但缺乏语义理解，难以处理措辞含糊或需要常识匹配的问题。
  3. **整体**：缺乏「按问题类型动态选择推理策略」的机制——所有问题用同一套流程，导致简单查值题被过度复杂化、复杂计算题又力不从心。

## 2. 核心方法

- **直观类比**：先做「考试审题划重点」（只留下相关行列），再按题型选解法——填空题直接找答案（语义查找），计算题列算式（文本推理 + SQL 校验）。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. 输入：表格 T + 自然语言问题 q。
  2. 关键操作（两阶段）：
     - **阶段一 表格抽取**：「multi-view 列检索」（从多个视角判断哪些列与问题相关）→ 保留相关列 → 行抽取 → 得到小子表；
     - **阶段二 自适应推理**：对问题分类——直接查找/词汇类问题用语义（文本）推理；量化/逻辑类问题在文本推理之上叠加符号（SQL 式）推理支持。
  3. 输出：答案（QA）或真/假判断（fact verification）。
- **形式化要点**：🔧 两阶段的 Prompt 设计、列/行相关性判定的形式定义与问题类型分类器细节，查原文第 3 节后补。
- **理论性质**：无理论保证类声明（工程方法）；摘要强调的是效果与效率（显著优于 SOTA 且流程更省 token 🔧）。

## 4. 实验结论（概览）

- **对比基线**：当时的文本推理与符号推理 SOTA（含 TabSQLify、BINDER 系方法 🔧 具体清单查原文）。
- **数据集**：三个基准——TabFact（事实核查）、WikiTQ-WikiTableQuestions（表格 QA）、FeTaQA（自由文本式 QA）；三者均由官方仓库 `datasets/` 目录直接提供。
- **结论方向**：H-STAR 在三个数据集上均显著超过 SOTA（摘要明示），验证混合自适应路线优于单一策略。

## 5. 开源代码与动手实践

- 仓库地址：https://github.com/nikhilsab/h-star （NAACL 2025 官方实现）
- 语言：Python 3.9（conda 环境），依赖 OpenAI API / Google Vertex AI。
- 典型流程（教学示意，以 README 为准）：
  1. `conda create -n hstar python=3.9` + `pip install -r requirements.txt`；
  2. 把 OpenAI key 写入 `key.txt`（Gemini/PaLM 需 Vertex AI 的 json 凭证）；
  3. `python run_gpt.py`（OpenAI 模型）或 `run_gemini.py`；
  4. 中间结果存 `results/`；用 `evaluate.ipynb` 评 TabFact/WikiTQ，`python fetaqa_score.py --model_name <MODEL>` 评 FeTaQA。
- 许可与资源提醒：仓库未见 LICENSE 文件 🔧；运行需调用付费 LLM API，复现实验注意配额与费用。

## 7. 2026 视角（🔧）

- 表格推理在 2025-2026 已与 Agent/工具调用合流：主流做法是让 LLM 把 SQL 当工具调用而非「二选一的推理范式」，H-STAR 的「按题型路由」思想演化为更通用的 planning/工具选择问题。
- 工业界 ChatBI 场景中，「先裁剪再推理」的子表抽取已是标准工程实践（减少 token 与干扰）；与 Text-to-SQL 榜单（BIRD、Spider）路线相比，H-STAR 关注的是 QA/事实核查而非 SQL 生成本身。
