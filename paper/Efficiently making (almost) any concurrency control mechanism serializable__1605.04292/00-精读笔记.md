## 一句话总结
与其把数据库的并发控制协议推倒重写成"安全但慢"的可串行化版本，不如给任何"快但不安全"的协议（比如快照隔离）外面罩一层轻量"安全网"（SSN）：平时照常高速运行，提交那一刻做个小检查，发现可能形成危险环就回滚——用很小的代价换来真正的可串行化。

## 0. 给新手的阅读前置（背景知识地图）

### 0.1 这个子方向在解决什么大问题
OLTP 数据库的并发控制（CC）决定多个事务同时读写时谁先谁后。**可串行化**是金标准（并发执行的结果等价于某个串行顺序），但防异常的代价高（锁开销、乐观验证开销、大量事务被中止浪费的工作）；**弱隔离**（快照隔离 SI、读已提交 RC）快得多，却允许写偏斜（write skew）等异常。核心矛盾：**性能与正确性如何兼得？**

### 0.2 为什么难
- 防异常 = 时刻警惕并发冲突，而这与"放行一切、事后补救"的高效路径天然冲突；
- 事后补救（提交时验证）若要回看全部历史依赖，代价可能爆炸；
- 现代多核 + 大内存引擎要求验证逻辑本身也必须可扩展（不能成为新的单点瓶颈）；
- 异构负载（含长只读事务）会让很多 CC 协议退化，验证机制还要对这些稳健。

### 0.3 主流解法一览
| 路线 | 直觉 | 代表 |
|------|------|------|
| 悲观锁 | 先锁再动，冲突提前排队 | 2PL 系 |
| 乐观并发控制 | 先干活，提交前验证 | OCC（严格化版本） |
| 多版本 + 弱隔离 | 各读各的快照，只防写写冲突 | SI（Hekaton 等内存引擎采用） |
| **提交时认证器（本文所属）** | 底层协议照常跑弱隔离，提交时刻叠加一道"可串行化安检" | **SSN（本文）** |

### 0.4 三个关键名词的直觉解释
- **可串行化（serializable）**：并发执行的事务结果，等同于某种"一个接一个跑"的顺序结果。等价刻画是**串行化图（serialization graph）无环**。
- **认证器 / certifier**：事务提交时做的"安检"。它不改变事务怎么执行，只决定放行还是回滚。SSN 就是一个可叠加在几乎任何 CC 之上的安检仪。
- **直接依赖（direct dependencies）**：事务 T 直接读了谁写的值、T 写的值直接被谁读了。SSN 提交时只检查直接依赖——不必回看整个历史，就能判断"放行 T 会不会造出依赖环"。

## 1. 问题背景与动机

### 1.1 前人工作简述
- 经典谱系：2PL、OCC、MVCC/SI 各据一方；SI 因内存数据库兴起而流行（如 Hekaton），但其写偏斜异常是人尽皆知的软肋；
- 学术界早有"把 SI 修补为可串行化"的思路（如 Fekete 等人的经典 SSI 工作 🔧——本文作者 Fekete 正是那一脉）；
- 现代硬件（多核、大内存）让"验证必须 latch-free、可并行"成为硬指标。

### 1.2 前人的缺陷 / 未解决问题（据摘要归纳）
1. **性能-严格性权衡被认为不可避免**：可串行化的 CC 方案要付出更高代价防异常（运行时开销 + 中止事务浪费的工作）；
2. **修补方案往往绑死特定协议**：缺少一种能"叠加在几乎任何 CC 机制上"的通用可串行化方案；
3. **异构负载脆弱**：很多方案在含长只读事务的负载下表现退化，或对特定事务类型有偏向；
4. **可扩展性**：依赖跟踪与验证若不能无锁存（latch-free）并行，就会在多核上成为瓶颈。

## 2. 核心方法

### 2.1 最直观类比
机场安检（SSN）不管你是在免税店逛了多久（事务怎么执行），只在你登机口（提交时刻）扫一眼：如果你登机会让"谁影响了谁"的因果链闭合成一个环（出现危险结构），就请你下飞机（回滚）；否则放行。因为只查"直接连着你的链段"（直接依赖），扫描极快。

### 2.2 具体做法（输入 → 关键操作 → 输出）
- **输入**：任何性能更高但允许异常的底层 CC 方案（快照隔离、读已提交等）上运行的事务流；
- **关键操作**：
  1. 底层 CC **保留对调度和事务访问的全部控制**，SSN 只叠加在旁边，跟踪事务间产生的**依赖关系**；
  2. **提交时刻**执行高效验证测试：只检查提交事务的**直接依赖**，判断放行该事务是否可能造成依赖循环；
  3. 可能造成环 ⇒ 中止该事务以避免潜在循环；否则放行；
  4. 进一步优化：**可跳过跟踪大多数读操作**，降低认证开销，仍保证可串行化；
- **输出**：可串行化的执行历史，开销极小。

### 2.3 形式化要点
- 正确性锚点：可串行化 ⇔ 串行化图无环；SSN 的验证测试保证提交后不会形成"危险结构"（摘要表述为避免潜在的依赖循环），从而维持可串行化 🔧（"危险结构"的精确定义与证明见原文，本笔记未逐字核实）；
- "跳过跟踪大多数读"为何不破坏正确性：与所检查的直接依赖集合的充分性有关 🔧（细节查原文 §3–§4）。

### 2.4 理论性质 / 保证
- 通用性："几乎任何"CC 机制都可叠加（摘要原话 almost any）；
- 稳健性：不偏向特定事务类型，保持底层 CC 特性；
- 可扩展性：依赖跟踪与验证测试高效、**完全并行、无锁存（latch-free）**，适配现代多核大内存多版本系统。

## 3. 变体 / 工程版（如有）
- 论文的工程载体是 **ERMIA**：一个可运行多种 CC 方案的内存优化 OLTP 引擎（SIGMOD 2016 首发 🔧），SSN 以"快照隔离 + SSN"的形态实现在其上；
- 2026 年该引擎由 SFU DIS 实验室持续维护（仓库迁移至 sfu-dis/ermia）。

## 4. 实验结论（概览）
- **评估平台**：大量仿真 + ERMIA 内存引擎上"快照隔离 + SSN"的真实实现；
- **负载**：传统 OLTP 负载 + 含**长只读事务**的异构负载；
- **结论方向**（摘要明示）：
  1. SSN 在各种工作负载下表现**稳健**，不偏向特定事务类型（即使底层 CC 存在偏向）；
  2. 能高效处理异构负载；
  3. 跳过跟踪大多数读后，仍以极小开销产生可串行化执行；
  4. 评估确认 SSN 是一种**性能稳健、开销低**的有前景的可串行化方法；

## 7. 2026 视角（🔧）
- **工业地位**：可串行化快照隔离已是现代分布式/内存数据库的常见卖点（CockroachDB、YugabyteDB、SQL Server 的 SI/SSI 系谱 🔧）；"提交时认证器"思想进入多条产品线；
- **主流实现**：SSI 类（SQL Server）与依赖图/认证器类方案并存；SSN 的"直接依赖 + latch-free 验证"对多核内存引擎（ERMIA、Hekaton 系）影响持久 🔧；
- **趋势**：RDPM/持久内存与多核扩展让验证路径的并行化愈发关键；确定性数据库（deterministic database）是另一条绕开验证的路线，与 SSN 形成路线对照 🔧。
