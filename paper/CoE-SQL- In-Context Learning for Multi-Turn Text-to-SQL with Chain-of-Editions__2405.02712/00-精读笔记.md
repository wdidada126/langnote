## 一句话总结

让大模型别每次都从零写 SQL，而是把当前问题看成对上一轮 SQL 的「几步小修改」，一步步输出编辑链（Chain-of-Editions），从而在多轮对话式 Text-to-SQL 上又快又准。

## 0. 给新手的阅读前置（背景知识地图）

- **子方向解决什么大问题**：Text-to-SQL 要把自然语言变成可执行的 SQL；多轮（对话式）场景下，用户的问题是「再按价格排序」「只看 2023 年的」这类依赖上文的话，模型必须结合对话历史和之前的 SQL 才能答对。
- **为什么难**：多轮语境下要正确「指代消解」（"他"、"那个表"指什么）；对话历史很长时 prompt 容易塞不下、关键信息被稀释；从头生成整条 SQL 比局部修改更容易引入新错误。
- **几类主流解法**：

| 路线 | 思路 | 代表 |
|------|------|------|
| 微调专用模型 | 在 SParC/CoSQL 等数据上 fine-tune seq2seq | RAT-SQL、T5 系（🔧 型号细节查原文） |
| 上下文学习（ICL） | 不改模型，靠设计 prompt + few-shot 示例 | DIN-SQL、C3 等（索引中有条目） |
| 交互状态建模 | 显式跟踪对话中每个元素的状态 | Tracking Interaction States（本仓库 2012.04995） |

- **本文属哪类**：ICL 提示设计路线——不动模型参数，纯靠 prompt 结构提升 LLM 多轮表现。
- **关键名词直觉**：
  - *ICL（上下文学习）*：把示例和任务描述写进 prompt，让模型「照猫画虎」，不训练。
  - *Chain-of-Editions（编辑链）*：把「从上一条 SQL 到新 SQL」的改动拆成一串小操作（如 add WHERE、change 列名），让模型显式写出每一步。
  - *SParC / CoSQL*：Spider 的多轮版数据集（单轮→多轮上下文）和对话版（含澄清式交互），是该方向两个标准基准。

## 1. 问题背景与动机

- 前人工作：Spider/SParC/CoSQL 上先有大量微调模型；LLM 兴起后出现用 ICL 做 Text-to-SQL 的尝试，但多数针对单轮。
- 前人的缺陷（逐条）：
  1. 多轮场景直接套单轮 ICL，忽略「相邻两轮 SQL 往往高度相似」这一结构先验；
  2. 把完整对话历史一股脑塞进 prompt，长对话下噪声多、效果下降；
  3. 从头生成整条 SQL，浪费了上一轮已经写对的绝大部分子句；
  4. 缺少系统性的消融实验回答「prompt 里该放什么、怎么放」。

## 2. 核心方法

- **最直观类比**：改作业。老师（用户）说「把第 3 题的 100 改成 200」，你不会重做整道题，只改那一处。CoE-SQL 就是教模型做这样的「改作业」。
- **具体做法（输入→关键操作→输出）**：
  1. 输入：对话历史、数据库 schema、上一轮生成的 SQL、当前用户问题；
  2. 关键操作：提示 LLM 先输出一条「编辑链」——若干原子编辑操作（🔧 具体操作类别（增删改子句、改列等）以原文定义为准），再据此产出新 SQL；
  3. 输出：当前轮的 SQL 查询。
- **形式化要点**：把多轮解析从 `f(history, question) -> SQL` 转化为 `g(prev_SQL, edit_chain) -> SQL` 的迭代修正视角，编辑链相当于中间推理步骤（与 CoT 思想同源）。
- **理论性质**：无形式化保证，属经验方法；论文通过大量消融实验确定最优 prompt 配置（🔧 具体最优配置查原文 Table）。

- 2024-2026 年，多轮 Text-to-SQL 已成为 LLM Agent + 数据库落地的核心场景之一；编辑/修正式提示思想被广泛吸收进「先草稿再修」「自反思重写」类 pipeline；同时微调路线被 reasoning LLM 与执行反馈（execution feedback）方法部分取代。主流实现多为「强 LLM + schema linking + 执行校验」组合，CoE-SQL 的编辑链是这类迭代修正思路的早期代表之一。
