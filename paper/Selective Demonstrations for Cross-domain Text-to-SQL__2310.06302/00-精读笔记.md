## 一句话总结
跨库 Text-to-SQL 里，给 LLM 加「领域内示例」能大幅提升效果，但需要领域内标注。ODIS 框架用「域外示例 + 合成领域内示例」混合检索来构造演示（demonstrations），在不依赖领域内标注的前提下，比单一数据源基线更强，在两个跨库数据集上执行准确率分别提升 1.1 和 11.8 个点。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：让模型在「没见过的数据库」上也能把问题转成 SQL（cross-domain）。
- 为什么难：每个库 schema 不同，模型需要快速适应新结构；又不想为每个库手工标注训练/示例数据。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 微调 | RESDSQL | 在大量跨库数据上训练 | 强但需标注 |
| 上下文学习（少样本） | 本文 ODIS | 给 few-shot 示例 | 免训练、吃示例质量 |
| 示例选择 | 检索相似示例 | 挑好演示 | 关键在来源 |

- 本文属哪类：in-context learning 路线下的「演示（demonstration）选择」子方向。
- 关键名词直觉：
  - demonstration（示例/演示）：prompt 里给模型的「(问题, SQL)」范例，教它怎么写。
  - cross-domain（跨域）：训练/适配时没见过目标数据库的 schema。
  - in-domain vs out-of-domain 示例：来自目标库（领域内）vs 来自其它库（域外）的示例。

## 1. 问题背景与动机
- 前人工作简述：LLM + in-context learning 在跨库 Text-to-SQL 上泛化好，且无需领域内标注；但已有研究发现加入「领域内示例」能大幅提升表现。
- 前人缺陷/未解决问题（逐条）：
  1. 领域内示例依赖标注：想用领域内示例就得先有目标库的标注，成本高。
  2. 不清楚示例里什么在起作用：哪些因素（schema 相似度？问句相似度？）真正带来提升，缺乏系统分析。
  3. 单一数据源有上限：只用域外或只合成领域内，都各有局限，缺少混合利用。

## 2. 核心方法
- 最直观类比：考试前既看「别的科目的类似题」（域外示例），又自己「照着目标题库风格出几道模拟题」（合成领域内示例），再把两类题混着当复习资料。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：目标问题 + 目标库 schema + 域外示例池 + 文本生成能力。
  2. 关键操作：ODIS 框架先分析「示例里哪些因素有用」，再检索域外示例并合成领域内示例，用混合来源构造 demonstrations。
  3. 输出：一组高质量演示，拼进 prompt 交给 LLM 生成 SQL。
- 形式化要点：核心贡献是「混合来源检索 + 合成」的演示选择框架；具体检索特征/合成方式以原论文为准 🔧。
- 理论性质/保证：无形式化保证；以实证提升为主。
