## 一句话总结
SQLucid 是一个面向「自然语言查数据库」的交互界面，用可视化对应、中间查询结果、以及可逐步编辑的自然语言 SQL 解释，帮非专业用户看懂并修正 SQL，用户研究显示任务完成率与信心显著提升。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：不仅要把自然语言翻成 SQL，还要让用户「信任并改得动」这条 SQL——尤其在医疗、金融等高利害场景。
- **为什么难**：现有 Text-to-SQL 系统准确率与可靠性有限；用户看不懂生成的 SQL，错了也不知道错在哪，更不敢改。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 纯文本生成 | 各类 Seq2Seq/LLM | 直接给 SQL 文本 | 快，但不可解释、难纠错 |
| 解释生成 | 部分工作附加 NL 解释 | 给一句话说明 SQL 在做什么 | 仍较静态 |
| 交互式界面 | **SQLucid** | 可视化对应 + 中间结果 + 可编辑分步解释 | 易懂可改，但偏 HCI/系统 |

- **本文属哪类**：交互式人机界面（HCI）+ Text-to-SQL 落地，属于「可解释/可用化」路线。
- **2-3 个必懂关键名词**：
  - **自然语言接口（NLI for DB）**：用大白话问数据库、系统回 SQL/答案。
  - **可视化对应（visual correspondence）**：把 SQL 各子句高亮映射到问题里的词、数据库里的列，建立「谁对应谁」。
  - **中间查询结果（intermediate results）**：SQL 执行到一半（如 WHERE 过滤后）的临时表，用于让用户逐步确认。

## 1. 问题背景与动机
- **前人工作简述**：ML 进步让自然语言数据库接口准确率提升，但在高利害领域仍不够可靠；已有系统多只给最终 SQL，缺乏让用户理解/纠错的手段。
- **前人缺陷/未解决问题（逐条）**：
  1. 用户难以判断生成的 SQL 是否正确、是否符合本意。
  2. 出错时缺少「可编辑、可逐步确认」的介入点，非专家无从下手。
  3. 信任缺失导致系统在实际高利害场景难以落地。

## 2. 核心方法
- **最直观类比**：传统系统像「扔给你一张看不懂的处方」；SQLucid 像「把处方逐条翻译成大白话、并把每一项检查的中间结果摊开给你看，你还能直接在便签上改」。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：自然语言问题 + 数据库。
  2. **关键操作**：集成三类能力——(a) 可视化对应（SQL 片段 ↔ 问题词/列）；(b) 展示每步中间查询结果；(c) 以自然语言给出可编辑的分步 SQL 解释。
  3. **输出**：用户可理解、可微调的 SQL 与查询结果。
- **形式化要点**：核心是「解释 + 中间结果 + 可视化对应」三位一体的交互设计；具体 UI 组件与算法以原论文为准（🔧）。
- **理论性质/保证**：属以用户研究验证的 HCI 工作，无算法理论保证（🔧）。
