## 一句话总结

闭源大模型（GPT-4o）做 Text-to-SQL 效果好但有隐私、成本、时延问题。BASE-SQL 用**开源 Qwen2.5-Coder-32B 微调**搭出一条四段流水线，BIRD 开发集 67.47%、Spider 测试集 88.9%，超过多数开源方案甚至部分 GPT-4o 方法，且每生成一条 SQL 平均只需 **5 次** LLM 调用。

## 0. 给新手的阅读前置（背景知识地图）

- **大问题**：Text-to-SQL = 把自然语言问题翻译成可执行的 SQL，是"人人可用数据库"的关键。企业落地时关心：数据不能出内网（隐私）、调用要便宜快速（成本/效率）——这把闭源 API 路线挡在门外。
- **为什么难**：表/列名与问题里的词对不上（模式映射）、复杂查询要多层嵌套、单次生成容易错在细节。
- **主流做法对比**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| ICL 提示闭源模型 | DAIL-SQL、GPT-4o 直答 | few-shot 提示 | 效果好；隐私/成本差 |
| 开源模型 SFT | **BASE-SQL（本文）** | 微调开源模型+流水线 | 私有化可行；需训练资源 |
| 强化/推理增强 | Arctic-Text2SQL-R1 | RL 优化推理 | 上限高；训练复杂 |

- **本文属于哪类**：第二类，主打"容易实现、便宜高效"的工程基线。
- **必须先懂的名词**：
  - **SFT（监督微调）**：拿（问题, SQL）对训练开源模型。
  - **BIRD / Spider**：两个主流 Text-to-SQL 基准，前者偏真实脏库、后者偏学术。
  - **Schema Linking**：把问题里的词对齐到具体表/列，Text-to-SQL 的第一道关。

## 1. 问题背景与动机

- 前人工作：ICL 方法依赖闭源模型；已有开源微调方案缺一个"易实现且效果能打"的基线。
- 未解决的问题：
  1. 开源模型微调路线缺乏可复现的强基线；
  2. 单次生成 SQL 错误率高，缺少结构化的纠错环节；
  3. 多数方法 LLM 调用次数多、生成慢。

## 2. 核心方法

- 类比：工厂流水线——先"对图纸"（Schema Linking），多名工人各出一件毛坯（Candidate Generate），质检员挑毛病返工（Revision），最后把合格件合成成品（Merge Revision）。
- 具体做法（输入 → 操作 → 输出），四组件：
  1. **Schema Linking**：裁剪/对齐相关表列，缩短提示；
  2. **Candidate SQL Generate**：微调后的 Qwen2.5-Coder-32B-Instruct 生成多个候选 SQL；
  3. **SQL Revision**：对候选逐一检查修订；
  4. **SQL Merge Revision**：合并修订产出最终 SQL。
- 输出：单条最终 SQL；平均每次生成仅 **5 次** LLM 调用（摘要口径）。
- 基座：Qwen2.5-Coder-32B-Instruct（开源）；训练数据与超参 🔧 见原文。
