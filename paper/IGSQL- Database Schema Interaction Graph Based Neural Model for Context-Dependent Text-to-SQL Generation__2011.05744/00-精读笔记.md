## 一句话总结
在多轮对话里把「历史问题」变成 SQL 已经有人做了，IGSQL 的发现是：**schema（表和列）本身也有历史**——上一轮用过的表/列这一轮更可能再用，用一张「schema 交互图」记住这件事，就能显著提升多轮 Text-to-SQL 的准确率。

## 0. 给新手的阅读前置（背景知识地图）

**子方向解决什么大问题**：让用户用一句句自然语言查数据库，系统把每句话翻译成 SQL。单轮只看一句话；多轮（context-dependent）还要结合前面的对话，比如用户先问「列出各学院的人数」，再问「那计算机学院呢？」——第二句必须结合第一句才能翻译。

**为什么难**：
- 指代与省略：后一句常常省略主语、只用代词或「这个学院」这类说法；
- 多轮的搜索空间组合爆炸：每轮的 SQL 相互依赖，一个 token 翻译错会污染后续所有轮次。

**几类主流解法（截至本文发表时的格局）**：

| 路线 | 直觉做法 | 代表 |
|------|---------|------|
| 修正式 | 先生成上一轮 SQL，再做增删改 | Edit-based 类模型 |
| 历史拼接式 | 把历史 utterance/SQL 拼进输入再编码 | 早期 encoder-decoder 方案 |
| 结构增强式 | 在 schema 与问题之间建关系图，显式传递信息 | RAT-SQL、本文 IGSQL |

**本文属哪类**：结构增强式——它在「历史信息」这个维度上从「用户输入」扩展到了「schema 条目」。

**关键名词直觉解释**：
- **Schema item（schema 条目）**：表名、列名，翻译时模型要「选中」哪些条目进 SQL；
- **Schema interaction graph（schema 交互图）**：把条目当节点、条目间关系当边的图，本文的图中边还带「这条关系在历史中出现过吗/出现了几次」的时间信息；
- **Gate mechanism（门控机制）**：解码时给不同来源的词表打分加权，决定这一步更该输出 SQL 语法词、列名还是问题里的词。

## 1. 问题背景与动机

**前人工作简述**：SParC 与 CoSQL 两个多轮跨领域基准提出后，主流模型（如 RAT-SQL 系列）在编码器里融合历史用户输入（utterance history），在解码器里对历史 SQL token 做注意力，已经把多轮任务推到一个不错的水位。

**前人的缺陷（本文针对的点）**：
1. **只利用了「用户输入」的历史**：历史 utterance 被反复研究，但 schema 条目本身的历史被忽略——上一轮已经被用过的表/列，往往就是本轮相关答案所在的表/列，这个信号没人显式建模；
2. **schema 关系多为静态**：已有的 schema 编码把表-列、列-列关系当成固定图结构，不随对话轮次变化，缺少「时间维度」；
3. **解码端对候选词一视同仁**：解码时 SQL 语法词、schema 词、自然语言词混在一个词表里，历史信息的贡献没有被区分加权。

## 2. 核心方法

**最直观类比**：把 schema 想成一间厨房。以前的模型只记「用户点过什么菜」，IGSQL 还记「哪些锅碗瓢盆最近被用过」——刚用过的锅（表/列）大概率马上还要用，不用每次都重新找。

**具体做法（输入 → 关键操作 → 输出）**：
1. **输入**：第 k 轮的问题 + 全部历史问题 + 数据库 schema（表、列及其外键/主键关系）；
2. **schema 交互图编码器**：以 schema 条目为节点建图，图中除了常规的表-列归属、外键关系边外，关键创新是**引入历史交互信息**：某条 schema 关系在历史轮次中被查询使用过，边上的表示会随之更新（通过图注意力网络在图上传播信息）；
3. **问题编码器**：同时用编码器捕捉历史用户输入的信息（沿用前人思路）；
4. **门控解码**：解码每个 SQL token 时，用一个 gate 对不同词表来源（SQL 关键字、schema 相关词、问题中的词）的重要性加权，再输出预测；
5. **输出**：本轮的 SQL 查询。

**形式化要点**：模型整体是 encoder-decoder 结构；schema 交互图上做的是带历史信息融合的 graph attention；解码在 SQL 语法约束下逐步生成 token（具体公式与损失函数见原文 🔧）。

**理论性质/保证**：无形式化理论保证，属实证型工作；消融实验（原文 Table 🔧）用于验证 schema 交互图编码器各组件的贡献。

## 4. 实验结论（概览）
- **数据集**：SParC 与 CoSQL——两个大规模、跨领域、多轮（上下文相关）Text-to-SQL 基准；
- **对比基线**：当时的 SOTA（含 RAT-SQL 系列方法 🔧 具体名单查原文）；
- **指标**：逐轮与整体的 question matching / interaction matching 类指标 🔧 精确数字查原论文后补；
- **结论方向**：IGSQL 大幅超过此前 SOTA，在两个数据集上均取得当时新的最优结果；对比与消融实验证明 schema 交互图编码器确实有效，而非靠参数量堆出来的提升。

## 7. 2026 视角（🔧）
- 大模型时代，多轮 Text-to-SQL 的主流做法已转为「LLM + 上下文工程 + SQL 执行校验」，RAT-SQL/IGSQL 这类专门设计的图编码器不再是榜首标配，但其「schema 状态也随对话演化」的观察被沿用进多轮 agent 的记忆设计 🔧；
