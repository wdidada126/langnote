## 二、问题史：批引擎为什么回答不了"现在"

- Meta 分析负载画像：数十工程师盯着 <10s 的即席查询，MapReduce/Tez 批分钟级不可接受；全量进 MPP 仓库（Parquet-only）又丢 Hive/Iceberg 存量数据可达性（✅ §1 论证）。
- 三难：通用连接器 × 交互延迟 × PB 扩展——论文立场是**把"内存+流水线+不写盘"定为第一约束**（✅）。

## 三、核心设计

### 3.1 全内存流水线

- 查询在 worker 间以 **stage→task→driver→pipeline→operator** 分层（✅ 术语栈），算子间 Page（列批）流式传递，spill 仅作逃生门（✅ 定位）。
- 与 Spark 的关键分歧：不做血缘容错、不承诺任意大规模 shuffle——**用"交互式预算"反推架构极简**（✅ 判断对照 [[rdd_2012_nsdi]]）。

### 3.2 连接器即世界观

- 统一元数据接口（Hive metastore、Iceberg、Delta、RDB 数百源 ✅ 论文"SQL on Everything"题眼）；谓词/聚合下推按连接器能力分级（✅）。

### 3.3 执行细节（✅ §5 主题）

- 向量化？否——Presto 长期算子式行批混合，表达式解释执行（后版本才加 codegen/向量化 ⚠️ 演进）；列内存布局 Page 压缩。
- 调度：coordinator 拉元数据统计做 cost-based join 重排/分布式广播（CBO 2018+ ⚠️ 版本线）；Morsel-driven 并行非默认。
- 容错=重跑整查询（交互时长有界，✅ 哲学声明）。

### 3.4 表达式与 UDF

- Java 字节码动态生成表达式（codegen 前史 ✅ 论文提 compile 部分路径 ⚠️ 粒度凭记忆）；SQL UDF 沙箱化。

## 四、评测（✅ 定性）

- TPC-DS 类：交互预算下 vs Spark SQL/Druid 各有所长（⚠️ 图表为准）；Meta 生产规模（千 worker、月查询亿级 ✅ 论文 §7 运营数字）。
- 与 Dremel 对照：开放连接器赢了存量战争，性能叙事让给专用系统（⚠️ 判断）。

## 五、批判读法

- "内存优先"=对超大规模 shuffle 型查询（大 join 全表重排）结构性劝退——论文诚实标注适用边界，用户不诚实（常拿它跑批 ⚠️）。
- 重跑即容错在 10s+ 查询长尾上会爆炸（失败重跑风暴），Meta 用"查得更快"掩盖"错得更频"（⚠️ 读法）。
- 表达式解释执行的"Volcano 税"（库内 [[volcano_1993_edbt]]/[[monetdb_x100_2005_cidr]] 本批已建对照）：Presto 性能史半部是向量化补课史（⚠️）。
- fork 政治学：Trino 分裂证明"查询引擎社区治理"比技术更难（✅ 事实）。

## 六、🔧 本地微实验（非本书引擎行为）

1. **流水线 vs 物化**：DuckDB 跑大 hash join 开/关 spill 对比峰值内存与延迟（体验逃生门语义）。
2. **下推分级**：手写两"连接器"（一个支持谓词下推一个不支持），同查询计扫描字节差。
3. **重跑风暴**：注入 20% 任务失败率，对比"整查询重跑 vs 分段血缘恢复"（DuckDB/自写 mini 引擎）。
4. **Page 列批**：JSON 行流改列批+RLE，测解释执行吞吐变化——体会行/批混合税。
5. **广播 join 选择**：小表广播 vs 重分区两策略在 1→8"节点"下的流量/延迟对比。
