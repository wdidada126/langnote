## 一句话总结
数仓里一张报表的字段，到底是上游哪张表的哪一列变来的？LINEAGEX 是一个轻量 Python 库：给它一条 SQL，它解析语法树推出「列级血缘」，还能画成交互图，帮你查数据质量问题出在哪个环节。

## 0. 给新手的阅读前置（背景知识地图）

- 大问题：数据血缘（data lineage）回答「这个数据从哪来、经过什么变换」。企业数动辄上千条 SQL 任务，没有血缘就没法做数据质量监控、存储重构、工作流迁移——改一张上游表不知道会炸掉哪些下游。列级（column-level）血缘是最细也最有用的一档：精确到「输出列 A 来自输入表的列 B×C 合并」。
- 为什么难：SQL 里别名、嵌套子查询、`SELECT *`、UDF、CTE 层层套娃后，「哪列变成哪列」在语法树上并非一眼可见；还有语义歧义（比如表达式列）需要消歧决策。
- 主流解法对比：

| 路线 | 思路 | 代价 |
|------|------|------|
| 执行引擎集成 | 数据库/调度系统在执行时记录血缘（如系统表、hook） | 与引擎强耦合，接入成本高，有运行时开销 |
| 静态解析 | 纯离线解析 SQL 语法树推导血缘（本文路线） | 轻量、免执行，但要自己处理语法多样性+歧义 |

- 本文属于：静态解析路线的轻量工具型系统（Demo Track 论文，重在可用性与演示）。
- 关键名词直觉：
  - 查询解析树（parse tree）：SQL 文本按语法规则长成的树，血缘推导就是在树上「顺着列走」；
  - 列级血缘：输出列与输入列之间的映射边集合；
  - 歧义（ambiguity）：如 `SELECT a+b AS c` 中 c 到底算「来自 a 和 b」还是「无直接来源」，需要策略消歧。

## 1. 问题背景与动机
- 前人工作：已有若干血缘系统，两条主要路线——与查询执行集成（数据库内置或调度侧捕获），以及一些静态解析工具。
- 前人缺陷（论文摘要逐条）：
  1. 执行集成类：为获取血缘引入额外开销（overhead），且绑定特定引擎；
  2. 静态类：对列级血缘的准确率/覆盖率不满意（fail to achieve satisfying accuracy），即推不全或推错。
  → 本文目标：不执行查询、不绑引擎，仍做到高覆盖 + 高准确。

## 2. 核心方法
- 最直观类比：给 SQL 做「食材溯源」。别的做法要么真把菜做一遍边做边记（执行集成），要么只粗看菜单猜食材（粗糙静态解析）；LINEAGEX 拿着菜谱（parse tree）从每道成品菜逐刀回溯到原始食材，遇到「混合酱料」就按规则拆解标注。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：SQL 查询（文本）；
  2. 关键操作①：把 SQL 解析为查询解析树；
  3. 关键操作②：智能遍历解析树，逐算子传播列的来源（投影/连接/聚合/别名等逐层展开）；
  4. 关键操作③：处理歧义——对表达式列、`SELECT *` 展开等模糊情形采用消歧策略，保证覆盖与准确；
  5. 输出：列级血缘图，并通过交互式界面可视化。
- 形式化要点：🔧 血缘的形式化定义（输出列到输入列的函数/关系）与各算子的传播规则表，查原文后补。
- 理论/性质保证：摘要未给理论保证，卖点为「高覆盖 + 高准确 + 轻量」的工程指标。

## 7. 2026 视角（🔧）
- 数据血缘已是现代数据栈（data mesh、数据目录、dbtd 类工具链）的标配能力：OpenLineage 等规范推动跨系统血缘标准化；
- 列级血缘在 AI 时代更吃香——特征/训练数据的溯源审计需要列粒度；
- 开源生态里 sqllineage、SQLGlot 等也是常用静态解析选项，LINEAGEX 的差异化在消歧策略与可视化一体；
- 🔧 上述生态现状为方向性判断，具体工具版本与采用情况未逐一核实。
