## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：Text-to-SQL 把自然语言问句翻成 SQL。现实对话常是多轮（follow-up 问句依赖前文），且跨不同数据库（schema）。「上下文相关（context-dependent）」比单轮难：要记住前面说过啥、前面生成的 SQL 是啥。
- **为什么难**：① 多轮要利用交互历史与当前句；② 生成 SQL 容易犯「表-列不匹配」「外键依赖错」；③ 跨域意味着不能死记某库结构。
- **几类主流解法（Text-to-SQL）**：

| 路线 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 基于草图/槽位 | RAT-SQL、RESDSQL | 先出骨架再填 | 结构稳；依赖 schema 链接 |
| 序列生成 + 指针 | 本文 PG-GSQL | 拷贝上一轮 SQL token + 生成新 token | 多轮友好；需控词表 |
| 预训练/大模型 | 近年 LLM 系 | 直接生成 | 强；成本高 |

- **本文属哪类**：编码器-解码器 + 指针生成 + 引导解码（序列生成派，专注多轮）。
- **2-3 个必懂关键名词**：
  - **指针-生成网络（Pointer-Generator）**：解码时既能「生成」新词，也能「拷贝」输入/历史里的词（这里从上一轮 SQL 拷 token）。
  - **引导解码（Guide Decoding）**：解码时限制可预测词表，避免不合法的表-列/外键组合。
  - **SParC**：一个跨域、多轮（context-dependent）Text-to-SQL 基准。

## 1. 问题背景与动机
- 前人工作简述：多数神经 Text-to-SQL 聚焦单轮跨域；多轮上下文相关任务（SParC）更需要利用历史 SQL。
- 前人缺陷/未解决问题（逐条）：
  1. 单轮方法不擅长复用历史 SQL 的 token。
  2. 解码易犯表-列依赖、外键依赖错误。
  3. 跨域下对 schema 的表预测不准。

## 2. 核心方法
- **最直观类比**：多轮问数据库像连续对话，第二问常是「在那张表的基础上再加个条件」。PG-GSQL 像会「照抄」上一句 SQL 里能用部分的秘书（指针拷贝），同时手边有张「只能用这些表/列」的清单（引导解码），不乱写，避免张冠李戴。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：交互历史 + 当前问句 + schema。
  2. **交互级编码器**：编码历史上下文。
  3. **指针-生成解码器**：混合「拷贝上一轮 SQL token」与「生成新 token」。
  4. **引导组件（Guide）**：限制词表，避开表-列/外键依赖错误。
  5. **列-表链接机制**：提升对表的预测准确率。
  6. **输出**：当前轮的 SQL。
- **形式化要点**：核心是「指针拷贝历史 + 引导约束词表」；超参为引导强度等（🔧 以论文/代码为准）。
- **理论性质/保证**：实证在 SParC 超 SOTA；无理论最优性。

## 4. 实验结论（概览）
- 对比基线：此前 SOTA 的 context-dependent Text-to-SQL 模型（在 SParC 上）。
- 数据集/指标：SParC 基准；指标为 question match（QM）与 interaction match（IM）准确率。
- 结论方向（摘要已核实数字）：
  - 基础版：dev 集 QM **34.0%**、IM **19.0%**。
  - BERT 增强版：dev 集 QM **53.1%**、IM **34.7%**，比前 SOTA 高 **5.9%** QM、**5.2%** IM。
  - 🔧 test 集精确数字与各消融请查原论文 Table 后补入。

## 7. 2026 视角（🔧）
- Text-to-SQL 已被 LLM（GPT 系、开源大模型）大幅推进，多轮/跨域仍是重点；PG-GSQL 的「历史拷贝 + 词表约束」思想在如今仍作为可控生成的技巧被沿用（尤其中小模型/低成本场景）。
- 趋势：LLM + 执行反馈 + 多轮记忆。本节为趋势性判断。
