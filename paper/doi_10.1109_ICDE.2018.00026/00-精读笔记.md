## 一、背景与它回应的问题

### 1.1 一个二分法困局

磁盘数据库用缓冲管理器透明管理大于内存的数据集（教科书式设计：页哈希表 + pinPage/unpinPage + LRU/Second Chance [Effelsberg & Härder 1984]）；但"对纯内存负载，典型缓冲管理器是最大低效来源"（原文引 Harizopoulos et al. SIGMOD 2008）。于是 H-Store、Hekaton、HANA、HyPer、Silo 等内存系统**干脆抛弃缓冲管理器**，直接用虚存指针存关系和索引——代价是：数据超过内存时只能劝用户加内存或删数据（"not a viable solution"），而 scale-out 也有硬件与运维成本。

内存系统在"超内存数据"上的补课方案各有致命不便（原文 §Related Work，逐条点名）：

- **Anti-Caching**（Brandeis, PVLDB 2013）：按元组粒度把冷元组踢去 SSD，但**索引不能搬走**——而"索引可占 OLTP 总内存的相当大比例"[11]，只缓解"差一点装得下"的场景，不是通解。
- **Siberia**（Microsoft, PVLDB 2014/ICDE 2013）：离线分类冷热、事务式迁移，但内存索引只覆盖热元组，还得靠 Bloom/自适应范围过滤兜底；多离线进程、多参数、两套存储管理器——"高复杂度可能妨碍了它的广泛采用"（原文语）。
- **OS swap/mmap**（QuickStore；Stoica & Ailamaki 对 H-Store 的启用研究；Graefe et al. 的 Shore-MT）：数据库放弃驱逐控制，原地更新与 ARIES 式恢复几乎无法做；OS 不懂"这张表在被全扫"；Linux 实测不适合 DB 负载——"因此我们认为依赖 OS 换页不是可行替代"（通说级引用，其 §II 原文措辞更细）。
- **Bw-tree/LLAMA**（Adobe, ICDE 2013/PVLDB 2013）：原地更新的反面——为条目造"差分"新版本，换来 latch-free 与（特定负载下）更低 SSD 写放大；但"创建与遍历 delta 是不可忽略的开销，性能低于原地更新的内存系统"（原文评价，且团队后来用《Building a Bw-tree takes more than just buzz words》[SIGMOD 2018] 补充了这一论点）。

而硬件天平翻转了：DRAM 容量与多核吞吐狂涨，PCIe/NVMe SSD 比 SATA 快一个数量级、比 DRAM 慢约 10 倍但**便宜约 10 倍**——五年法则 [Gray & Graefe 1997] 的经济账重新把"页式缓冲管理器"摆回牌桌。论文的问题因此是：**能不能设计一个现代硬件上高效、透明、可扩展的缓冲管理器，使"管超内存数据"这件事不再以牺牲内存级性能为代价？**

### 1.2 答案一句话

三支柱：**指针 swizzling**（热页访问零哈希查找）+ **精益驱逐**（不给任何访问记账，随机投机 unswizzle 出"冷却页"，FIFO 排队再判活）+ **可扩展同步**（乐观闩/版本校验 + epoch 替代 pin 计数 + 全局闩只留在冷路径）。效果：**工作集全驻内存时，TPC-C 吞吐达到纯内存 B+-树的 97%**（67K vs 69K tps 单线程）；数据集越出内存时，用 PCIe SSD 平滑退化而非"掉悬崖"。页大小 **16 KB**、LeanStore+B+-树共约 **4000 行重度模板化 C++11**。

## 二、核心设计精读

### 2.1 指针 swizzling：页状态机与"单一亲引用"（§III-A, §IV-B）

每个对页的 8 字节引用称为 **swip**，用 1 bit 指针标签区分两态：swizzled（存虚存指针）/ unswizzled（存逻辑页号）。访问热页 = 一条可预测分支 + 指针解引用；swizzled 页仍有逻辑页号，只是存在帧头而非引用里。

朴素 swizzling 的死结：一页可同时被一个 swizzled 引用与一个 unswizzled 引用指着（多父引用），不借助全局闩几乎无法维持一致性。LeanStore 的釜底抽薪：**每页恰有一个"拥有者"swip**——缓冲池整体成为"页森林"：

```
            root swip(池外)
                │swizzled
               P1(hot) ──unsw──► P7(cold,SSD)      P3(in-flight 加载中)
              ╱   │
        P4(hot)  P2(cooling: unswizzled 但仍在 RAM，挂在 FIFO)
   (孩子未全 unswizzle 的父页不可先驱逐——B 树内部页天然优先于叶被换出)
```

由此派生三个工程件：帧内存父指针（不持久化、维持成本低，因为子先于父被 unswizzle）；数据结构自描述（页存"结构标记"，缓冲管理器经**迭代回调**枚举页上全部 swip 而无需懂页布局）；因此"任何固定页 + 树状结构"都能挂进同一个全局置换策略——索引、堆、B+-树、甚至列存布局共用一个策略（这是 Anti-Caching/Siberia 做不到的透明性）。

页的完整生命周期（原文图3 重绘）与热路径访问（伪码示意）：

```
        ┌──────────── 访问命中 cooling：重新 swizzle，回热（免 I/O 缓刑）───────────┐
        │                                                                        │
 cold(SSD) ──load/swizzle──► hot(RAM, swizzled) ──随机投机 unswizzle──► cooling(RAM, 挂 FIFO)
                                                                        │ 队尾 & min(epoch)>p.epoch
                                                                        ▼
                                                                  evict（脏则回写 SSD）

if (likely(swip.tag == POINTER)) page = swip.pointer;   // 热路径=1 个可预测分支
else page = cooling_lookup_or_io(swip.pageID);          // 冷路径才碰全局闩/哈希
```

### 2.2 精益驱逐：不追踪热页，只识别冷页（§III-B, §IV-C）

LRU/2Q 每次访问都要写追踪结构（链表头、second-chance 位）——热路径上就有写共享、就 ping-pong。LeanStore 反转视角：**热页访问零额外工作**，冷页靠"投机"发现——内存吃紧时，随机挑一页 unswizzle 进**冷却态**（仍在 RAM！），按 FIFO 排队；被再访问 → 重新 swizzle 回热态（免 I/O 的"缓刑"，类似 Second Chance 的宽限期）；排到队尾且（2.4 的）epoch 判活通过 → 真正驱逐。冷却配额约 10%（5%–20% 均稳，默认 10%）。命中率实测（均匀负载 z=1.0，5GB 数据/1GB 池）：LeanEvict(10%) 92.8%，介于 Random/FIFO 92.5% 与 LRU 93.1%/2Q 93.8% 之间，离 OPT 96.3% 有 3.5 个百分点——**用一次投机 unswizzle 的近似代价换掉了每次访问的记账**，作者论证"复杂策略的运行时开销会吃掉那点命中率优势"。

### 2.3 乐观闩：读路径零同步（§III-C, §IV-F, §IV-I）

传统引擎一行更新 = 一打闩（原文举例：Shore-MT 单行更新 15 次闩获取 [Johnson et al.]），且 B 树根闩/全局哈希闩是"热闩"——缓存行 ping-pong，NUMA 上更是灾难。LeanStore 把读彻底乐观化：

```
lookup(key):                        # 遍历阶段一闩不取
  v0 = 沿途各页闩.version             # 只读版本计数
  r = descend_and_search(...)
  if 任何页.version != v0: restart()  # 校验失败=曾有写者，从头再来
  return r

insert/update/delete:               # 只锁要改的那一页
  同上遍历(不锁) → 取叶闩(版本号+1) → 改 → 放闩
  仅 SMO(分裂/合并) 才重启为"沿途锁内部页"的悲观路径
```

即 Optimistic Lock Coupling（乐观锁耦合）家族（原文引 Cha et al. 2001、其 ART 同步论文 DaMoN 2016 与《Building a Bw-tree...》）。区间扫描用 **fence key** 切成多次独立查找，从而**取消叶间右链**——磁盘 B+-树的经典补丁在乐观协议下不再必要。写者与写者、写者与读者之间仍是闩/校验的博弈：读者可能白跑一趟（有重启成本），但读者是多数、且重启只浪费一次廉价的内存遍历。

### 2.4 epoch 回收：pin 计数的替身（§IV-G）

不锁不 pin 的页可能正被别的线程读着就被驱逐/复用——这是无锁数据结构的老问题。LeanStore 采用 **epoch（分代）方案**而非 hazard pointer：

```
全局计数器 global_epoch（自增频率 ∝ 驱逐量/常数~100：太频繁 ping-pong，太迟钝积压）
线程开始操作: local = global        结束: local = ⊥
驱逐页 p 前: 若 min(所有线程 local) > p.unswizzle 时的 epoch ⇒ p 无人在读，可复用
长操作(全表扫)拆成小段逐段进出 epoch；I/O 绝不在 epoch 内：
  缺页时 → 放闩、退 epoch、读盘 → 抛 C++ 异常 → 数据结构的 handler 从根重启整个小操作
```

对照本仓库 [`../hazard_pointers_tpds2004.md`](../hazard_pointers_tpds2004.md)：HP 每次读登记指针（每操作多次共享写），epoch 把记账摊到"代切换"（每操作两次本地写），代价是退役延迟依赖"线程会周期性退出 epoch"——异常重启机制正是为守住这条前提。删除页复用也走 epoch：线程本地"已删页小缓存"，够新才敢用，兼顾缓存局部性与置换策略纯度。后台写者线程是唯一被允许的异步驱逐代理：循环刷冷却 FIFO 上的脏页。

### 2.5 I/O 路径与预取（§IV-D, §IV-H）

并发加载去重：in-flight I/O 哈希表（页号→{OS mutex, 新分配帧}），首线程全局闩下建帧后即放闩、自己阻塞 `pread`；其余线程在**该页的 mutex** 上等——全局闩从不横跨 syscall，SSD 并发读保得住。扫描预取与提示（hinting）：扫描线程经 in-flight 组件同时挂多个异步读；扫描读入的页**直接以 cooling 态入场**（而非 hot），冷却池有上限，所以大扫描既不吃热页、也不必 unswizzle 真热页——**抗缓冲池颠簸**是教科书式论断的工程落地。NUMA：缓冲池与空闲链按节点切分（尽力而为），除置换所需元数据外全部中心化；实测把远程访问比从 75% 压到 14%、再涨约 8%。

### 2.6 帧交错布局（§IV-I，容易被跳过的一处硬件细节）

buffer frame（页号、脏位、闩、epoch 标记等头部元数据）与页内容**物理交错**排布，而不是传统"帧表存指针→指针指向散落的页体"。两个理由逐字抄录：热路径局部性（帧头被高频访问，与页体同缓存行邻域）；更隐蔽的**组相联退化**——页大小取 2 的幂时，若不交错，所有页头部的地址步长相同，会映射进同一 L1 组（Intel L1 只有 8 路），"只有极少数页头能驻留缓存"。这一小节是"页要贴着 CPU 缓存放"最实质的文本证据。

## 三、实验与工程取舍（数字均已逐字复核 PDF）

### 3.1 关键读数

- 平台：Xeon E5-2687W v3（10C/20T, 64GB）+ Intel DC P3700 NVMe（2700/1080 MB/s 顺读/顺写，随机同量级）；Linux 4.8，direct I/O 裸块设备（ext4 与 Linux NVMe 栈本身是瓶颈——作者明说）。TPC-C 去 think time，对比配置为 BerkeleyDB 6.0 与 WiredTiger 2.9（**均关闭事务/日志/压缩**），LeanStore 与内存 B+-树同样不记日志——见 §六批判第 1 条。
- **特性消融（单线程 100wh, 16KB 页）**：传统式基线 30K → +swizzling 48K → +精益驱逐 62K → +乐观闩 67K tps；纯内存 B+-树 69K（ overhead ~3%）。BDB 10K / WT 16K。swizzling+精益驱逐合贡献约 2×；乐观闩单线程仅"略快"（无竞争），多线程才显威。
- **扩展性（10 核/20 线程）**：BDB 5 线程即饱和（峰值 20K，加速比 2.4×）；WT 20 线程 8.8×；LeanStore 10 线程 8.8×、开超线程 12.6×。与同源系统横比：Silo 805K、FOEDUS 1,109K、LeanStore 845K tps（作者归因 FOEDUS 的定制访问路径：定长数组、垂直分区、追加表）。对 Graefe 的 swizzling 版 Shore-MT：近同设置下 ~70K，差 10 倍——swizzling 只治翻译，不治闩与 pin。
- **60 核 NUMA（4×E7-4870 v2）**：worker 绑仓库（TPC-C 专用优化）为基线 → 预触碰（pre-fault）内存 → NUMA 感知分配，逐级到 **56.9× 加速比**（远程访存 75%→14%）。
- **超内存 TPC-C（图9）**：20GB 池、数据 10→50GB 越池：LeanStore 贴着纯内存曲线走（同时后台向 SSD 写约 500MB/s），因置换策略能精准锁定工作集；**Linux swap 又慢又抖**（作者用此图终结 OS 换页论）；BDB 十分钟烧穿池、WT 仍慢 2 倍以上。冷启动预热：PCIe SSD 约 8 秒达峰，SATA SSD 35 秒，**机械盘约 15 分钟内只有 ~10 tps**（随机读 5MB/s）——"性能掉悬崖"是磁盘时代内存系统兴起的根因；SSD 时代只需"平滑退化"，故 LeanStore 宣言：**只配 SSD 用，别接硬盘**。
- **点查微基准（YCSB-C 风, 5GB 数据/1GB 池/20 线程）**：uniform 92K lookups/s（76K IOPS，完全 I/O 主导，z=1.25 也仅 193K/75K IOPS）→ 偏斜继续升高则吞吐指数级脱离 I/O 地板（z≈1.5 起进入 15M–74M 量级）→ **高偏斜端 129M–143M lookups/s、零 I/O**：工作集缩进 1GB 池，性能与 IOPS 解耦——一个数据讲清"工作集在不在内存"才是新瓶颈（图内各柱与偏斜值的精确对应因双栏 OCR 排版易混，此处只锚定两端点与量级）。冷却配额扫描（1%→50%）：5%–20% 平坦，仅 z≈1.6（工作集≈池大小）处掉 >10%。
- 双扫描互扰实验（10GB orderline + 0.7GB orders 并发扫，池 2–12GB）：小表扫描在任何池大小下不受扰动（置换持续保住其工作集）；池=10GB（略小于两表之和）时出现 25s/50s 周期性 I/O 但吞吐仍高——hinting + 有限冷却池协同防颠簸的直接证据。

### 3.2 取舍表

| 选择 | 买到 | 付出 |
|---|---|---|
| swizzling + 单亲引用 | 热页访问 = 1 个可预测分支；无全局翻译哈希闩 | 数据结构被约束成森林；多父引用（B+ 树叶链、交叉指针）需额外机制——作者明确列为可扩展方向而非已实现 |
| 投机随机 unswizzle（LeanEvict） | 热路径零记账；单闩保护冷却结构（仅冷路径） | 命中率比 LRU 低 ~0.3pt、比 OPT 低 3.5pt；一个参数（10%）但极端偏斜比下敏感 |
| 乐观闩 + 校验重启 | 读零同步、写单闩，多核/NUMA 线性可扩展 | 读者可为写者白跑；SMO 走悲观路径；正确性论证比锁协议难 |
| epoch 回收替代 pin/HP | 每操作 2 次本地写；页帧复用批量判活 | 长操作必须拆段；I/O 内禁入 epoch → 异常重启机制；退役延迟上界=最慢线程 |
| 无 DB 内异步 I/O 线程（ICDE 版） | 实现简（~4K 行）、行为可预测 | 缺页线程同步 `pread`，单页延迟全额暴露；扩展版引入 swap worker+自旋补此短板（通说） |
| 16KB 页 | 对 NVMe 顺写友好、元数据摊销适中 | 对 NVM/低延迟设备偏大（后来者用 4KB 级细粒度，通说） |
| 关日志跑 TPC-C | 干净分离"缓冲管理"这一个变量 | 生产引擎的 WAL/检查点成本未计入——横比内存系统时此数偏乐观 |

## 六、批判与延伸

1. **实验的"无日志真空"**：为归因，LeanStore 与对手同关日志——但生产页式引擎（InnoDB、Umbra）开销大头恰在 WAL/检查点。"97% of in-memory"是缓冲管理层的胜利，不是端到端的承诺。其作者系之后续工作（Umbra、以及通说中的 LeanStore 扩展版对 NVM 日志的适配）补的正是这一课。
2. **单亲引用是双刃剑**：换来置换策略的全局透明与实现的 4K 行，代价是图状引用（叶间链、跨树指针）需要"fat swip"一类补丁——论文明确标注"非根本限制"，但至今未见本文内的完备实现，属于诚实留白。
3. **乐观读的重启成本被轻描**：写热点页上的高频读者可能反复校验失败（"活锁"风险靠工程常数压制而非协议排除）；对照 FOEDUS 的字节寻址 PCM 定制与 Silo 的 OCC，三家的"可扩展性买法"各押一注，ICDE 版未做同负载三方对垒（仅 tps 一点位横比）。
4. **术语的自反**：文章反复引用 latch-free 文献又自称不用 latch-free——Leis 在多处对"buzz words"（自引 [36] 的标题梗）保持警惕；读这篇请把它当**页式原地更新阵营的方法论样板**，而非"无锁引擎"竞品。
5. **延伸验证**：LeanStore 已开源（TUM/Leis 团队维护，通说——本次未核验仓库状态）；DuckDB 0.10+ 的 out-of-core 执行采用 LeanStore 作缓冲管理器（通说，未逐字复核，可作二次考证题）。缓存侧"页贴着 L2/L3 放"的口号化表述请以扩展版与演讲为准，引用本笔记时按 §〇-2 的措辞分级。

## 八、思考题（5 道）

1. LeanEvict 的命中率（92.8%）低于 LRU（93.1%）却快得多。请就"SATA HDD（毫秒级、随机读惩罚大）"与"Optane/PMem（纳秒级、字节可寻址）"两个端点分别重估这笔交换的汇率，推导"投机 unswizzle 策略"在哪个设备时代会失效。
2. 单亲引用把缓冲池变成森林，B+-树叶链因此被取消、改由 fence key + 乐观校验支撑。若要在 LeanStore 上实现跨表外键的"多父共享页"（如 SaaS 多租户页），fat swip 需要哪几处状态机改动？epoch 回收的正确性论证会新增什么义务？
3. 缺页处理选择"线程自己 `pread` + 其余等 OS mutex"，而扩展版改为"swap worker + 闩上自旋"。用排队论粗析两种方案各自的失效场景（IOPS 饱和 vs 线程数≫CPU），并说明为何"自旋"必须与乐观闩的版本校验同时成立。
4. 论文用 C++ 异常做"重启从根遍历"。批评者称异常路径难以静态推理。请为该机制设计最小充分测试集（提示：SMO 与驱逐竞争、epoch 退出时机、hinting 页在冷却队首被再次命中），并解释每个用例试图证伪哪条不变式。
5. 对比 C-Store 的 epoch/HWM/LWM（粗粒度**可见性**时间）与 LeanStore 的 epoch（**生命周期**代）：同名不同物。请各写出它们"最迟必须推进"的驱动量，并讨论一个同时含二者的 HTAP 引擎（行存乐观页 + 列存不可变段）里两套 epoch 应如何桥接。

## 九、常见误读提醒

1. **LeanStore 不是"反缓冲管理器"**，恰恰是给缓冲管理器**平反**：证明它透明、统一、可扩展的老功能可以在不付老成本的前提下保留。
2. **"常驻 CPU 缓存"不是本文纲领**（§〇-2）；按原文引"well-predicted if"与帧交错，别引口号。
3. **乐观闩 ≠ 无锁/等待自由**：写者之间是真互斥；读者是"可重试的乐观"。与 ART/Silo 同族但非同一协议。
4. **"无 swap"读法**：反对的是 OS swap；换页（swap in/out）是它的本职。冷却态≠已驱逐。
5. **10× vs Shore-MT、56.9× on 60 cores** 都绑定"同关日志/TPC-C 语义"的设定，不是全系统冠军声明；FOEDUS 的 1,109K 仍在其上，作者自证定制访问路径的收益存在。
6. 数字全部出自 ICDE 版 PDF 的 10 核 + 60 核两平台、16KB 页、P3700 SSD；换平台勿外推。

## 十一、一页总结（复习卡）

- **问题**：内存引擎抛弃缓冲管理器后，"数据越内存"只能靠加 RAM/反缓存/OS swap/Bw-tree delta 四条补丁路，各牺牲透明性、索引覆盖或原地更新。
- **方案**：swizzling（访问=一条分支）+ 投机 unswizzle 的精益驱逐（热路径零记账，10% 冷却 FIFO 缓刑区）+ 可扩展同步三件套（乐观闩校验、epoch 代回收替代 pin、全局闩只在冷路径）；帧交错护缓存；预取+hinting 护扫描。
- **所得**：驻内存时 ≈97% 纯内存 TPC-C（67K/69K）；多线程/60 核 NUMA 高加速比（845K tps、56.9×）；越内存平滑退化（BDB/WT 数倍~数十倍；OS swap 又慢又抖）；预热 8s（NVMe）。
- **所欠**：日志/恢复不在实验内；单亲引用约束图状结构；乐观读者重启成本；"自旋闩+swap worker"要等扩展版。
- **位置**：页式 OLTP 阵营对"内存时代还要不要缓冲池"的正面回答；与 C-Store（列存读写分离）、Neumann（编译执行）三点连线即 TUM—MIT 两支谱系在 2005–2018 的完整剖面。
