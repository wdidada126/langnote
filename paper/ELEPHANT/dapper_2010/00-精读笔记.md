## 二、问题史：为什么日志与指标不够

- 请求穿越数十服务、百次 RPC；单机日志无法重建**跨服务时序与因果**（✅ 论文 §1）。
- 约束四硬：低开销（<0.1% 生产 CPU ✅ 论文目标口径）、全栈覆盖（任何语言/中间件）、应用零改码、可伸缩采集（✅）。
- 已有学术方案（Magpie/Lorce ⚠️）不满足"零埋点+百万 QPS"（✅）。

## 三、核心模型：Trace = span 树

### 3.1 三件套

- **TraceID**：请求全局身份，跨进程透传；**SpanID**：每 RPC/本地段一节点；**Annotation**：事件点（✅）。
- 上下文传播三载体（✅ 招牌设计）：pull 模式（客户端拉）/ push 模式（透传请求上下文，如 GCS、Bigtable）/ tracing header 注入（HTTP/URL）。
- "无埋点"真相：库层（GCS/协议层/HTTP 层）内置传播钩子，应用只改启动 flag（✅ 边界诚实）。

### 3.2 采集与查询

- 本地 daemon 汇聚、**采样**（默认万分之一可配 ✅）、异步上传（Chubby/GFS/Bigtable 存储与查询 ⚠️ 细节凭记忆）。
- 查询=给 trace id 或属性条件，重建标注时序图（✅）。

## 四、评测（✅ 论文口径）

- 全 Google 数千应用、采集 10^? 量级 span；CPU 开销 <0.1%、采样缺口靠高值请求定向采样补（✅ 大意）。
- 案例：发现某服务 20% 延迟来自日志锁竞争类"看不见的串行化"（⚠️ 案例凭记忆，以原文 §5 为准）。

## 五、批判读法

- 采样与尾延迟观测天然冲突：万分之一下 P99.9 事故常不被采到——头部采样 vs 尾部采样（TALENT/Sample-and-Hold ⚠️）是十年后补的课（⚠️）。
- 异步/队列/批处理语义下"因果边"易断（论文以 annotation 手工缝合），云原生消息队列时代放大该痛点（⚠️）。
- 报告体裁：工程散文、无严格评估协议——引用它应把它当**模型定义**而非实验文献（⚠️ 定位）。
- 与 eBPF 零埋点路线对照：Dapper 的"库层钩子"假设可控技术栈，异构开源栈里退化为 eBPF/服务网格旁路（⚠️ 判断）。

## 六、🔧 本地微实验（非本书引擎行为）

1. **手搓 span 树**：HTTP 三层微服务（threading），W3C traceparent 头透传，输出 JSON 树重建调用图。
2. **采样对比**：头部 1% 随机采样 vs 尾部的"慢请求全留"策略，测 P99 事故捕获率。
3. **断链复现**：插入消息队列（文件队列）让异步消费者断 TraceID，手工补 link 字段体验缝合。
4. **开销测量**：每请求打 20 条 annotation 的开销占比，逼近 0.1% 目标反推批传/异步化必要性。
5. **时钟偏移**：两进程间加 ±50ms 偏移，观察 span 图出现"子早于父"错序——理解为什么必须用**区间差**而非绝对时刻（✅ Dapper 明说的对策）。

## 九、最新演进与工业实践

- OpenTelemetry 统一三信号（trace/metric/log）✅；eBPF（Pixie/Grafana ⚠️）走"零埋点旁路"补异构栈。
- LLM 应用追踪（LangSmith/OTel GenAI 语义约定）把 span 树延伸到 prompt/token 粒度——"trace=span 树"模型原样复用（⚠️ 判断）。
- 2024–2026：尾部采样与成本治理成为可观测账单焦点，Dapper 的采样假设被重新定价（⚠️ 判断）。
