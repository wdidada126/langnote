## 0. 给新手的阅读前置（背景知识地图）

**子方向解决什么大问题**：数据分析里常见这样的需求：「找出性价比高、又不贵、评分又好的酒店」——没有一个维度同时最优，而是要返回**不被任何其他点在所有维度上碾压**的那些「帕累托最优」结果。这就是 Skyline 查询。

**为什么难**：
- Skyline 依赖「维度间两两支配比较」，与 SQL 基于集合的关系代数不合拍，标准 SQL 没有对应算子；
- 要手工改写成多路 JOIN/嵌套反例查询，语义绕、易写错，且在分布式引擎上性能差。

**几类主流解法（表格）**：

| 路线 | 直觉做法 | 代表 |
|------|---------|------|
| SQL 改写式 | 用 NOT EXISTS 嵌套查询模拟支配关系 | 标准兼容但笨重 |
| 算法研究式 | 设计专门的 skyline 计算算法（BNL、SFS 等） | 单机/集中式系统研究 |
| 引擎原生集成 | 在执行引擎内核中新增算子与语法 | **本文（Spark SQL）** |

**本文属哪类**：引擎原生集成——语法、解析、优化到执行全程打通。

**关键名词直觉解释**：
- **Skyline / 支配（dominance）**：点 A 支配点 B = A 在所有维度不比 B 差且至少一维严格更好；skyline = 没被任何人支配的点集；
- **Apache Spark SQL**：Spark 的结构化数据处理模块，提供类 SQL 接口与分布式执行引擎；
- **算子集成（operator integration）**：把新查询能力做成引擎的一等公民——有自己的语法、逻辑计划和物理执行，而不是靠用户拼 SQL 模拟。

## 1. 问题背景与动机

**前人工作简述**：Skyline 查询自 Börzsönyi 等提出以来，单机算法（BNL、分治、索引辅助等）研究充分；在分布式/大数据系统上，Spark 是主流框架且自带 Spark SQL 的便捷接口，但对 skyline 原生不支持。

**前人的缺陷（逐条，据摘要与背景）**：
1. **Spark SQL 无原生支持**：用户想做 skyline 必须自己动手，把需求改写进 SQL 标准或 Spark 的类 SQL 语言；
2. **改写繁琐且易错**：等价的 SQL 改写冗长、可读性差，多目标维度一多就难以维护；
3. **性能损失**：改写后的查询无法利用专门为 skyline 设计的执行策略，在大数据量下代价高。

## 2. 核心方法

**最直观类比**：以前想在 Spark 里做「帕累托筛选」，好比想用剪刀剪圆片——自己徒手绕着剪（SQL 改写）；本文是给 Spark 装了一把圆规（原生 skyline 算子），一笔成型还更快。

**具体做法（输入 → 关键操作 → 输出）**：
1. **输入**：带 skyline 子句的类 SQL 查询（用户指定哪些维度上要「最大化/最小化」）；
2. **语法与解析层**：为 Spark SQL 扩展了简洁的 skyline 语法，用户无需手工改写（具体子句关键字见原文 🔧）；
3. **执行层**：在 Spark 执行引擎内实现 skyline 计算（基于支配关系比较的分布式 skyline 算法，具体算法选型与分布式实现策略查原文 🔧）；
4. **输出**：skyline（帕累托最优）结果集。

**形式化要点**：skyline 的形式化定义即经典支配关系；工作重点在系统侧——把该算子接入 Spark SQL 的查询处理管线（解析 → 逻辑计划 → 物理执行）。

**理论性质/保证**：正确性上等价于标准 skyline 语义；效率上由实验证明优于改写方案。复杂度理论分析不是本文重点。
