## 一句话总结

向量检索（给推荐/搜索引擎找相似内容）太吃算力了，FANNS 的思路是：告诉它你要的召回率和预算，它自动帮你「算法 + FPGA 硬件」一起定制，比 CPU 基线最快快 37 倍，8 块 FPGA 卡横向扩展还能打赢 GPU。

## 0. 给新手的阅读前置（背景知识地图）

- **这个子方向解决什么大问题**：AI 系统要把文本/图片编码成高维向量，检索时需要在几十亿向量里找出最相似的 Top-K（最近邻搜索）。精确搜索代价不可接受，所以都用近似最近邻（ANN）算法；但数据规模 × 查询吞吐的要求（如搜索引擎每秒数万查询、PB 级文档）让纯 CPU/GPU 方案在成本或扩展性上吃紧——后摩尔定律时代，专用硬件成为出路。
- **为什么难**：ANN 有两大算法家族（基于图、基于量化/哈希），各有参数（图度数、量化段数、探测数…）；硬件上有资源约束（BRAM、DSP、片上缓存、带宽）。算法参数和硬件资源分配**互相耦合**——改一个算法参数可能让最优硬件设计完全不同，手工调优几乎不可能。
- **几类主流解法**：

| 解法 | 直觉 | 代表 |
|------|------|------|
| 图索引加速（CPU/GPU） | 邻居图上贪心导航 | HNSW、DiskANN、CAGRA |
| 量化/哈希加速 | 压缩向量算近似距离 | PQ、Faiss-IVF、Falconn++ |
| FPGA/ASIC 专用加速 | 为检索定制硬件流水线 | **本文 FANNS**、Falcon（图索引 FPGA 版） |

- **本文属于**：第三类，但关键创新在「自动化软硬协同设计」：不手工设计加速器，而是按召回率要求 + 资源预算自动生成。
- **关键名词直觉解释**：
  - **PQ（Product Quantization，乘积量化）**：把长向量切成若干段，每段用小编码本近似，距离查表估算——省内存省算力，代价是近似误差。
  - **ADC（Asymmetric Distance Computation）**：查询向量不量化、只量化库内向量，逐段查表算距离的近似计算方式。
  - **FPGA**：现场可编程门阵列，可把算法烧制成定制电路，延迟低、能耗比高，但开发门槛高——这正是 FANNS 想自动化的部分。
  - **召回率（recall）**：近似结果与精确 Top-K 的重合比例，是 ANN 的「正确率」指标。

## 1. 问题背景与动机

- **前人工作简述**：向量检索是搜索引擎、推荐、RAG 的基础设施；CPU 上有 Faiss 等成熟库，GPU 有 CAGRA 等；FPGA 上此前有零散的量化搜索加速器，但都是「固定设计、固定算法配置」。
- **前人缺陷/未解决问题（逐条）**：
  1. **手工设计不可移植**：已有 FPGA 加速器为特定数据集/召回率/硬件板卡定制，换需求就得重做。
  2. **算法与硬件割裂**：没有框架能根据「用户想要的召回率」和「手里的资源预算」同时决定算法配置与硬件结构。
  3. **缺少横向扩展（scale-out）支持**：多数加速器只做单卡，没有内建网络能力，撑不起数据中心级检索服务。

## 2. 核心方法

- **最直观类比**：FANNS 像「定制家具的自动化工厂」——你提出需求（房间大小=硬件预算、要装多少东西=召回率），它自动出图纸并生产家具（生成 FPGA 加速器），而不是买固定尺寸的成品柜。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：用户给定的目标召回率、数据集、FPGA 硬件资源预算。
  2. **关键操作**：
     - 在 IVF-PQ（倒排文件 + 乘积量化）算法空间中搜索合适的算法配置（如量化段数、每段比特数、探测列表长度）；
     - 依据算法配置自动生成匹配的硬件设计（距离计算流水线、片上缓存分配、列表扫描单元），算法与硬件参数联合优化；
     - 加速器内嵌**硬件 TCP/IP 栈**，支持多块 FPGA 通过网络组成集群横向扩展。
  3. **输出**：定制化的 FPGA 向量检索加速器（端到端框架，从索引构建到查询服务）。
- **形式化要点**：设计问题可视为约束优化——在资源约束 R（BRAM/DSP/带宽）下选择算法参数 θ 与硬件结构 h，最大化给定召回率目标下的吞吐。FANNS 用自动化设计空间探索求解。
- **理论性质/保证**：召回率是显式输入目标（按需保证近似质量），无其他理论保证。

## 3. 变体 / 工程版（如有）

- **单机版与集群版**：仓库分 `FPGA_local`（单卡）与 `FPGA_with_network`（含硬件网络栈的多卡扩展）两套实现，另有 `CPU_GPU_baselines`（Faiss 等 CPU/GPU 基线实验）。
- **作者后续系列**：同一思路延展到 RAG 服务——Chameleon（VLDB 2025，FPGA 检索 + GPU 推理的异构解耦系统）、Falcon（VLDB 2025，图索引向量搜索的 FPGA 加速）、RAGO（ISCA 2025，RAG 服务系统优化）。官方 README 中均给出链接与引用。

## 4. 实验结论（概览）

- **对比基线**：FPGA 前作加速器、CPU（Faiss 等）、GPU 方案。
- **数据集**：大规模公开向量数据集（具体为 SIFT/DEEP 等哪个组合 🔧 查论文实验节）。
- **指标**：吞吐（QPS）、延迟（中位数与 P95）、召回率约束下的性能、多卡扩展性。
- **结论方向**（数字来自论文摘要，经核实）：
  1. 相比 FPGA 基线最高 **23.0×** 加速、相比 CPU 基线最高 **37.2×** 加速；
  2. 八加速器配置下，相比 GPU 方案中位延迟 **5.5×**、P95 延迟 **7.6×** 的加速，扩展性优于 GPU；
  3. 证明 FPGA 集群在数据中心向量检索场景的可行性。

## 5. 开源代码与动手实践

- **仓库地址**：https://github.com/WenqiJiang/SC-ANN-FPGA （README 自述为 SC'23 论文官方仓库）
- **语言/技术栈**：FPGA 开发（HLS/C++ 等 🔧）+ CPU/GPU 基线（含 Faiss 实验）脚本；目录含 `FPGA_local`、`FPGA_with_network`、`CPU_GPU_baselines`。
- **典型流程（教学示意，以 README 为准 🔧）**：
  1. 在支持 HLS 的 FPGA 工具链上编译加速器 bitstream；
  2. 构建向量索引（IVF-PQ），加载目标数据集；
  3. 单卡跑召回率-吞吐曲线，或多卡 + 网络栈跑扩展性实验；
  4. 用 `CPU_GPU_baselines` 复现对照实验。
- **许可与资源提醒**：许可 🔧；⚠️ 复现需要真实 FPGA 板卡（如 AWS F1 或 Alveo 级）与 HLS 工具链，门槛与成本高；新手建议先只跑 CPU/GPU 基线部分理解实验设置。

## 7. 2026 视角（🔧）

- 向量检索已成 RAG 服务的主要瓶颈之一，2024–2026 年「检索加速」从学术议题变成系统热点：FPGA（Falcon）、GPU（CAGRA）、以及商用向量数据库的硬件感知优化并行发展。
- 软硬协同设计思想延续到 RAG 全链路：Chameleon（VLDB 2025）把 FPGA 检索器与 GPU LLM 推理解耦组合，RAGO（ISCA 2025）做系统性 RAG 性能优化。
- 工业界主流仍是 GPU + 高性能向量索引（HNSW/IVF 系），FPGA 方案在特定延迟/能耗约束场景（电信、边缘、金融低延迟）有落地空间。
