## 一句话总结

工业 4.0 / IoT 场景下的企业流处理（把业务数据和实时流混在一起算）没有任何现成基准能覆盖，ESPBench 补上这块空白：一套带查询负载、基准执行流程和配套工具包的基准，并用它实测了 Apache Spark、Apache Flink、Hazelcast Jet 三大流引擎。

## 0. 给新手的阅读前置（背景知识地图）

**这个子方向解决什么大问题？** 数据不再只是「存好了再查」——工厂传感器、用户点击、金融行情每秒产生海量事件，需要**边到边算**（流处理，stream processing）。而你要为一个企业选型（Spark? Flink? Jet?），第一个问题就是：**用什么基准来比？**

**为什么难？**
1. 企业场景不是纯粹的「高频小事件」：它们往往要把**流数据与慢变的业务主数据（维表/参考数据）做富化（enrich）与关联**，负载形态和经典流基准差别很大；
2. 现有基准（如线性路由的 Yahoo! Streaming Benchmark 一类）不覆盖这种「企业级复杂用例」（摘要原话：existing benchmarks do not cover them）；
3. 流系统测量本身有坑：乱序、网络抖动、背压，测出来的延迟很容易失真，需要**结果正确性校验 + 客观延迟测量**的工具支撑。

**主流解法分几类？**

| 类型 | 代表 | 特点 |
|------|------|------|
| 学术微基准 | NEXMark 谱系 | 查询模式经典，但偏「拍卖网站」式合成负载 |
| 工业公开基准 | Yahoo! Streaming Benchmark | 易上手，负载单一，常被批评失真 |
| 企业级基准 | **ESPBench（本文）** | 面向企业真实负载形态：流 + 业务数据富化、多查询并存 |

**本文属哪类？** 第三类的开创者——专为「企业流处理」设计的基准。

**3 个关键名词直觉解释：**
- **流处理（stream processing）**：数据像传送带一样流进来，系统在流动中持续计算并输出结果；
- **富化（enrichment）**：事件本身只有 ID（如机器 ID），要 JOIN 上主数据（如这台机器的型号、厂商）才算得出业务结论——ESPBench 负载的核心特征；
- **Apache Beam**：一套可移植的编程 API，同一份查询代码可以跑在 Spark、Flink 等不同引擎上——ESPBench 用它保证「同一查询、多引擎」的公平性。

## 1. 问题背景与动机

- **前人工作简述**：流处理系统的性能对比此前依赖 NEXMark 式学术基准与 Yahoo! Streaming Benchmark 等公开基准；学术界与工业界也积累了一批单系统调优研究。
- **前人缺陷（摘要逐条）：**
  1. **覆盖缺口**：现有基准不覆盖「企业用流数据富化核心业务数据与分析」这类复杂用例——即「实时流 + 慢变业务数据 + 多查询」的组合形态；
  2. **测量可信性缺口**：复杂用例下比较不同流架构本来就难（摘要原话：Comparing streaming architectures for these complex use cases is challenging），缺少能**校验查询结果正确性**与**客观测量延迟**的支撑工具；
  3. 由此导致的后果是：企业选型只能靠厂商宣传或零散实验，缺乏可复现的对比依据。

## 2. 核心方法

**最直观类比**：ESPBench 之于流引擎，就像一条「标准化考试」：题目（查询负载）统一、评分标准（结果校验 + 延迟测量）统一、考试流程（基准执行过程）统一，而且发了一整套「监考工具」（toolkit）防止作弊和计时不准。

**具体做法（输入 → 关键操作 → 输出）：**
- **输入**：企业级流负载（源自工业 4.0 / IoT 型场景）+ 若干条覆盖典型企业查询模式的查询；
- **关键操作**：
  1. 定义基准架构与基准执行流程（benchmarking process，摘要明言三要素：architecture、benchmarking process、query workload）；
  2. 用 **Apache Beam** 编写**官方提供的查询实现**，使同一份查询逻辑可分别投递到不同引擎；
  3. 提供配套 toolkit 负责驱动基准执行、**校验查询结果的正确性**、并进行**客观的延迟测量**；
- **输出**：各流处理系统在这些企业查询上的吞吐 / 延迟对比，以及结果正确性的可信判定。

**形式化要点**：查询负载的形式化定义（每条查询的数据源、窗口、JOIN 形态）🔧 以论文正文为准。

**理论性质/保证**：无性能定理；其核心「保证」是方法论层面的——结果可校验、延迟测量客观。

## 4. 实验结论（概览）

- **对比系统**：三个当时最先进的流处理系统——**Apache Spark、Apache Flink、Hazelcast Jet**（摘要核实）；
- **查询实现**：官方提供、统一用 Apache Beam 开发；
- **指标**：吞吐与端到端延迟（含结果校验）；
- **结论方向**：
  1. 实验本身突出证明了 **toolkit 的必要性**：没有它，既无法确认各系统算出的结果对不对，也测不出客观的延迟（摘要原话：Our results highlight the need for the provided ESPBench toolkit…）；
  2. 三系统各有相对强弱（具体哪个查询谁快谁慢的精确数字 🔧 查原论文表格后补）；
  3. 每个系统都需要针对性的工程投入才能跑出公平数字——这正是「企业选型不能只看厂商基准」的证据。

## 7. 2026 视角（🔧）

- 流处理在 2020 年代后期已收敛为 Flink 系（含实时数仓场景）与 Spark Structured Streaming 系两大主流，Kafka Streams / Jet 等各有生态位；ESPBench 三引擎对比的选择在当时极具代表性；
- 企业选型趋势从「引擎性能」转向**云托管服务的总拥有成本**（Confluent/阿里云/Flink on K8s 等），但「流+维表富化」仍是核心负载形态——ESPBench 的负载设计思想仍然适用；
- 近年基准趋势：加入 exactly-once 语义故障注入、乱序/迟到数据处理、批流一体对比等维度（🔧 沿革细节待考证）；lakehouse 流批混合（本仓库 `paper/lakehouse_2021_armbrust_databricks` 一线工作）也在改变「流处理基准」的边界。
