## 一句话总结

这篇论文指出：此前 LLM 做 Text-to-SQL 的工作各自用不同的 prompt 构造方式（数据库怎么写进 prompt、示例怎么检索和排列），导致结果不可比、贡献归因不清，于是作者对 prompt 构造的各个环节做了一次系统性的对照实验，给后续研究给出「该怎么搭 prompt」的参考结论。

## 0. 给新手的阅读前置

读这篇之前，你只需要知道三件事：

1. **Text-to-SQL 是什么**：把用户的自然语言问题（"去年销量最高的产品是哪个？"）翻译成能在数据库上执行的 SQL 查询。传统做法是训练专门的语义解析模型，2023 年起主流做法改用大语言模型（LLM）。
2. **In-context learning（上下文学习）与 prompt 构造**：不微调模型，而是把「任务指令 + 数据库 schema + 若干示例（demonstrations）」拼成一段提示文本喂给 LLM。这段文本里**每个部分怎么写、示例怎么选、顺序怎么排**，就是本文所说的 prompt construction（提示构造）。
3. **三种实验设置**：
   - **Zero-shot**：prompt 里不放任何示例，只有指令和数据库信息；
   - **Single-domain（单域）**：示例和问题来自同一个数据库；
   - **Cross-domain（跨域）**：模型要在没见过的数据库上工作，示例通常从其他数据库检索。

不需要任何数据库系统知识，也不需要深入 NLP 背景——这是一篇「实验方法学」论文，读它的价值在于学会**如何公平地评价 prompt 策略**，而不在于某个具体模型。

## 1. 问题背景与动机

2023 年上半年，用 LLM 做 Text-to-SQL 的工作爆发式增长：有的用示例检索策略（挑相似问题作为 demonstrations），有的加入中间推理步骤（如思维链），有的微调 schema 表示。这篇论文的核心观察是：

- **策略耦合、无法归因**：每篇工作同时改了多个变量——示例怎么选、数据库 schema 怎么描述、指令怎么写、要不要推理步骤——最后报告一个整体提升，说不清到底哪个改动起了作用。
- **缺乏可比性**：A 论文和 B 论文即使都用同一个 LLM、同一个数据集，因为 prompt 文本构造不同，数字也不能直接比。
- **缺少选型依据**：后来者面对「prompt 到底该怎么写」这个问题时，没有系统的实验证据可参考。

因此作者的动机非常清晰：**把 prompt 构造拆成可控的维度，在统一实验条件下逐项对比**，回答「在 zero-shot、单域、跨域三种设置下，prompt 的各个组成部分分别贡献了多少性能」。

## 2. 核心方法

这篇论文没有提出新模型，它的「方法」就是一套严谨的对照实验设计：

1. **拆解 prompt 构造维度**：把一段典型的 Text-to-SQL prompt 分解为主要组成部分——任务指令（instruction）、数据库信息（schema 如何呈现）、示例示例选择与排列（demonstration selection / organization）、中间推理步骤等。
2. **控制变量对比**：在固定模型与数据集的前提下，每次只变动一个 prompt 维度，观察性能变化，从而分离各因素的真实贡献。
3. **覆盖三种设置**：zero-shot（无示例）、single-domain（同库示例）、cross-domain（跨库泛化）分别实验，因为同一策略在不同设置下的结论可能相反。
4. **输出选型建议**：基于实验结果，为后续 Text-to-SQL 研究给出 prompt 构造的实践建议。

> 🔧 论文正文中具体使用了哪些基准数据集（如 Spider、WikiSQL 等）、评测指标与具体数字，本次仅依据 arXiv 摘要核实写作，精确实验表格请以原文为准。

## 3. 变体/工程版

- 本文本身是实证研究，没有「工程变体」，但它的结论直接服务于后续大量 prompt 工程：
  - 依赖示例检索的框架（如 DIN-SQL、MAC-SQL 这类多阶段/多智能体方案）在选示例、排 prompt 时可以参考其对照结论；
  - zero-shot 场景（无法检索示例的新库冷启动）可依据其 zero-shot 部分的发现来写指令与 schema 描述。
- 代码仓库提供了实验的 prompt 模板与复现脚本，可作为后续研究「控制 prompt 变量」的起点脚手架。

## 4. 实验结论概览

- **总体发现**：prompt 构造方式对 LLM 的 Text-to-SQL 性能有显著影响，且不同设置（zero-shot / 单域 / 跨域）下各因素的相对重要性不同；这证实了「不可比」问题确实存在且影响很大。
- **对后续研究的启示**：报告 Text-to-SQL 结果时应明确披露 prompt 构造细节；比较不同方法时应固定 prompt 变量。
- 🔧 各维度的具体结论（例如「示例质量比数量更重要」「指令措辞影响相对较小」这类细粒度发现，以及具体准确率数字）本笔记未逐项核实，请以论文正文实验部分为准。

## 7. 2026 视角

从今天回看，这篇 2023 年的 workshop 论文有几个「后见之明」式的价值：

1. **prompt 构造公平性问题早已成为共识**：2023-2024 年间大量 Text-to-SQL 框架（DIN-SQL、MAC-SQL、CHESS 等）涌现时，社区逐渐意识到必须固定 prompt 变量才能公平比较——本文正是最早系统提出并实验这一点的文章之一。
2. **schema linking 依然是核心**：后来的工作（如 RSL-SQL 等强基线）反复证明「数据库信息如何进入 prompt」是最大杠杆之一，与本文的实验框架结论方向一致。
3. **方法迁移**：这种「拆维度、控变量、分设置」的评测方法学，已经超出 Text-to-SQL，被借用到各类 LLM 结构化生成任务（Text-to-Cypher、API 调用等）的论文写作中。
4. **局限**：2023 年实验基于当时的模型版本，具体数字在 2026 年的更强模型上不能直接沿用，但其「可比性方法论」不随模型过时。
