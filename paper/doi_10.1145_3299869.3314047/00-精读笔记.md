## 一、背景与它回应的问题

### 1.1 时代前提：第一代"云托管"没有触及架构本体

SQL Server 此前的云路线（SQL Azure → VM 上自托管）本质上仍是"单机数据库搬进虚拟机"：

1. **纵向弹性天花板**：实例规格决定一切，存储容量、IOPS、内存同涨同跌；升配 = 换更大的 VM，伴随停机与数据搬迁。
2. **高可用靠日志重放**：Always On 可用性组在副本上后台重做（redo apply）主库日志——副本延迟不可控、每个可读副本都要重复一遍完整的重放劳动、故障切换后新主还要走一遍崩溃恢复的尾巴。
3. **备份/恢复与数据规模同阶**：TB 级库的恢复时间以小时计，跨区域容灾要重新拷全量备份。
4. **运维侵入服务**：补丁、升级、伸缩都要在"持有数据的进程"上动刀，进程即状态，重启即事故。

核心提问：**能否保住 SQL Server 单实例的全部可编程性（T-SQL、事务、索引语义），同时让"日志持久性、页物化、副本新鲜度、恢复"各自成为可独立伸缩的云服务？与 Aurora 的区别何在？**

论文的问题意识与 Aurora 同源（都是"复制单元太大、恢复单元太大"），但归因不同：Aurora 认为不可信的是**平台 IO 与块存储语义**，所以自建日志存储；Socrates 认为可以信任**自家平台的分布式存储底座**，于是把刀挥向"副本必须重放日志"这条千年老规。理解这一分歧，两篇的所有设计差异都会变得顺理成章。

### 1.2 答案一句话

无状态计算（单写多读）+ **Page Server 层**（按页地址区间分区，惰性把 redo 物化成页、按需供应"as-of-LSN 页"）+ **X-Store 单条逻辑日志**（append-only、持久性交给云平台分布式存储底座）；副本不再重放日志（论文名 **Falcon** 的机制），页像对象一样按需拉取——failover、备份、加副本全部与"重做多少日志"解耦。与 Aurora 同为"日志即数据库"，但 Socrates 走的是"**单副本共享存储 + redo 按需应用**"路线，Aurora 走的是"六副本自治存储节点"路线。

## 二、核心设计精读

### 2.1 架构总览（ASCII，按论文结构复述）

```
          ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
 用户 →   │ Compute 主写   │  │ Compute 只读  │… │ Compute 只读  │
          │ 完整 SQL 引擎  │  │ 同一引擎,     │  │ 不必重放日志,  │
          │ 生成 redo 流    │  │ 无状态        │  │ 可冷启动       │
          └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
                 │ ①仅 append redo   │ ②页读取(带 LSN 水位) │
        ┌────────┴───────────────────┴───────────────┴────────┐
        │        Page Server 层(多个, 按页地址区间分区)           │
        │  角色A: 从 X-Store 拉 redo, 惰性物化页(缓存+材料库)      │
        │  角色B: 向 compute 供应页; 自身近乎无状态可重启           │
        └────────┬─────────────────────────────▲──────────────┘
                 │ ③页镜像异步落池               │ ④按需读 redo/旧页
        ┌────────┴─────────────┐    ┌──────────┴─────────────┐
        │ Pooled/Hadar 存储池    │    │ X-Store: append-only    │
        │ 不可变页/段文件,平台级   │    │ 日志服务(单逻辑副本, 底层  │
        │ 分布式存储底座(持久性外 │    │ 云存储保证多副本/纠删码)   │
        │ 包), 靠引用计数做 GC    │    │ 时间点读、尾部查询        │
        └──────────────────────┘    └────────────────────────┘
```

与 Aurora 一图可辨：Aurora 的"存储节点"同时干 append、复制、物化三件事（6 份日志、quorum 判定在库这一侧）；Socrates 把三件事拆给三层——X-Store 只管日志、Page Server 只管物化与供页、存储池只管字节持久。

### 2.2 无状态计算与单写者模型

- 计算副本 = 完整 SQL Server 进程，但**不拥有任何数据**：buffer pool 仍在（热页缓存），却只承担性能角色，不承担正确性角色——这与 15445 缓冲池项目"缓存错了会怎样"的思想实验形成对照（[`../../courses/数据库系统/15445/projects/01-buffer-pool/README.md`](../../courses/数据库系统/15445/projects/01-buffer-pool/README.md)）。
- **单写者**：任何时刻只有一个 compute 实例能产生新日志（提交路径：生成 redo → append 到 X-Store → 拿到持久化确认即回客户端）。只读副本的"新鲜度"不是重放进度，而是"允许读到 X-Store 的哪个 LSN"。
- 收益立现：进程可以随意重启/迁移/换版本（补丁不再是运维事件）；加只读副本不复制任何数据，冷启动即可服务（首次读页时才物化）。
- 提交路径（复述，非原文图）：事务产生的 redo 按顺序 append 进 X-Store 单流；X-Store 确认持久（平台层多副本落定）后计算节点即可向客户端 ack。注意此路径上**没有页写、没有副本等待、没有 quorum 计数**——写延迟的下界被压缩为"一次日志服务往返"，这是与 Aurora"攒批+等 4ack+连续前缀判定"最可观测的协议差异。

### 2.3 Page Server：物化者与供页者

- 数据库的页地址空间（page-id 空间）被**切区间托管给多个 Page Server**：任务口径所称"Distributed DM"（相对单机集中式的数据管理层）即指这种"页管理职责随规模从中心化走向分布化"的部署形态；组件确切命名与切分粒度细节**未逐字复核**，本笔记按机制而非原词引用。
- 每个 PS 对所辖页区间做两件事：(a) 从 X-Store 拉 redo、惰性物化 base 页并保持"页 + 未来 redo 增量"的差分管线；(b) 应答 compute 的 `页 P, as of LSN ℓ` 请求。
- **PS 近乎无状态**：数据真相在 X-Store/存储池，PS 崩溃 = 重启换新 PS 接管该区间，不触发全库恢复——Aurora 的 segment 独立性思想被进一步提炼成"以页区间为故障单元"。
- 热点与再平衡：某页区间访问倾斜时，可为其增派 PS 副本（同一区间多个服务者）而非迁移数据——因为物化结果可重建，再平衡只是"路由表变更"，这与 shared-nothing 数仓的 rebalance 痛点（Snowflake 笔记 1.1 节所述）在 OLTP 侧被同一手法消解。
- 读路径伪码（示意）：

```
compute.read(P, as_of=ℓ):
    ps = route(P)                      # 按页号路由到负责区间的 Page Server
    if ps.has(P, applied≥ℓ): return 页
    else: ps 从存储池取 P 的旧 base 版本(≤ℓ)
          从 X-Store 区间流 (base_lsn, ℓ] 的 redo, 幂等应用 → 返回
    # 幂等性锚点仍是"页内 LSN 比较" —— ARIES 血统在分布式环境复活
```

### 2.4 X-Store 与"单副本共享存储"：与 Aurora 的分水岭

- X-Store 是 **append-only 日志结构的持久服务**：对上层表现为"一条逻辑日志"；物理多副本/纠删码、跨故障域放置，全部委托给云平台分布式存储底座（Azure 体系；任务口径称之为"盘古式共享存储"，**盘古实为阿里巴巴内部文件系统之名，与本文无关**，本笔记以"平台级共享存储底座"表述，见核实记录）。
- 于是持久性问题从"Aurora 式应用层 quorum（写 4/6）"变成"**存储层承诺单流写不丢**"；数据库协议里不再有 tail-of-log 两端区间——因为不存在 6 个各自 ack 进度不一的副本，日志流天然有序持久。
- 这是两种云原生哲学的分野：**Aurora 不信任平台存储的语义（块设备 IO 不确定），自建日志存储；Socrates 相信自家云平台的存储底座，把通用持久性外包、专注数据库语义层。** 前者跨平台性与自持冗余更强，后者层数更薄、账更清晰。

### 2.5 Falcon：不再重放日志的只读副本

- 传统 AG（可用性组）副本的三大成本：重放全部 redo 的 CPU/IO、重放滞后造成的读旧、副本规格必须接近主库。
- Falcon 机制：副本**不后台重放**；读请求带新鲜度水位向 PS 要"as-of 最新可用 LSN"的页，X-Store 是唯一的变更流。效果：(a) 副本延迟不再是"重放竞赛"；(b) 副本可以是极小规格甚至冷备（不计费地停着，起来就服务）；(c) 读写分离的"读扩展"不再摊薄主库资源。
- 一致性边界：只读副本看到的是"日志里某个已持久 LSN 的快照"，等价于快照隔离下的历史读——**不是**分布式可线性化读（单写者模型里写后读一致性靠客户端路由/水位约定解决，细节论文从略）。
- 水位推进策略（本笔记归纳）：PS 可保守地把"可见 LSN"停在检查点边界，以保证副本读到的页集自洽（不撕裂）；这与 Aurora 副本"随存储层物化进度可见"是同一问题的两种节流方式。

### 2.6 HADR、故障切换与容灾

- **区域内 failover**：旧主失联 → 控制面选出新 compute 实例、颁发新任期（fencing 语义与 Aurora 的 term 同族）→ 新主从 X-Store 尾部续接 LSN 即开始写。**没有 crash recovery**：未提交的散尾从未成为"可依赖的持久前缀"，页也从未被提前定稿。切换时长与 buffer pool/库大小无关——两代云 OLTP 论文在此结论完全一致。
- **跨区域 HADR/DR**：X-Store 日志流持续拷至远端（连续、增量），远端 PS 按需物化；灾难时远端提升为主，恢复目标从"拷备份+重放"降为"切指针+补日志尾"。可用性组语义被重构为"单日志流的多消费端"，而非"两条数据库互为副本"。任务口径"Distributed DM 的 HADR"即指这一"管理层分布式部署下的容灾协议"；缩写口径未逐字核实，机制描述以论文可考元素为准。
- GC 与一致性快照：存储池中的不可变页/日志段以引用计数存活（快照、备份、旧版本各自钉住所需文件）——与 Snowflake"版本清单钉住微分区"同构，但钉住的单元是页与日志段而非查询级文件集。

### 2.7 一次写提交的完整旅程（串起 2.2–2.6）

仍以 Aurora 笔记 2.8 节的 `UPDATE accounts SET bal = bal - 100 WHERE id = 42`（命中页 P）为例，在 Socrates 中走一遍（流程为机制复述，非原文示例），便于两篇对照：

```
1. 主 compute: 解析/优化/加锁, 生成 redo "页P@off := newbytes",
   附带单调 LSN = 1007(分配者唯一: 当前任期的写者)
2. append 到 X-Store 单流; X-Store 依平台存储语义确认持久 → 回客户端 commit
   —— 没有"选 4 份 ack、判连续前缀"这一段(与 Aurora 最大流程差异)
3. 异步: 负责 P 所在区间的 Page Server 从流上消费到 1007,
   在自己节奏里物化(或只把"未来增量"挂在旧页上)
4. 只读副本 SELECT P: 向 PS 要 "P as of ℓ=当前可用水位";
   PS 已物化 → 直返; 未物化 → 取 base 版本+补放 (base_lsn, ℓ] redo, 幂等
5. 崩溃点分析:
   a) 第 2 步前主挂: 客户端没收到 OK, 记录未成可依赖前缀, 新主续写自然覆盖/截断
   b) 第 2 步后主挂: 日志已持久, 新主凭围栏从流尾 1007 续写; PS 无恙, 页服务不中断
6. 跨区域: 远端持续拿到 1007 之后的日志流; 灾难提升时"切写者+补尾"即恢复可服务
```

对照 Aurora 的同款六步：差异集中在第 2 步（quorum 判定 vs 单流确认）与第 3/4 步（物化发生在复制体内部 vs 独立的 PS 层）。**同一个 UPDATE 走两遍，是理解两种"日志即数据库"方言最快的方式。**

## 三、实验与工程取舍

论文实验在 Azure 平台与 SQL Server 既有形态对照（OLTP 型负载），**无第三方基准**；下述为定性结论，TPC 类图刻度未逐字复核：

1. **写路径**：提交延迟与 X-Store 一次 append 往返同阶，去掉了"多副本各自落盘+页写"的长尾。
2. **只读扩展**：加副本近零边际成本（不拷数据、不重放），读延迟随 PS 层扩容可控。
3. **failover/恢复**：切换与库大小解耦；备份/还原从"小时级数据搬运"变为"元数据+日志尾操作"。
4. **弹性与运维**：计算/PS/存储三层独立扩缩，打补丁 = 换无状态进程。
5. **冷热分层效应**：读扩展的边际成本趋近"网络+PS 内存"，因为冷副本无需携带全量重放成果；此结论在论文中为机制演示而非严格基准（刻度未复核）。

深层取舍清单：

| 取舍 | 选择了 | 放弃了 | 换来的 |
|---|---|---|---|
| 日志持久性 | 单逻辑流 + 平台共享存储 | Aurora 式库侧 6 副本/quorum | 层薄、账清；深度绑定自家云平台 |
| 副本新鲜度 | PS 按需物化（Falcon 不重放） | 副本本地全量热页 | 零重放成本、冷备副本；读路径依赖 PS 可用性 |
| 写拓扑 | 单写者 | 多主可写 | fencing 简单、语义=单机；写扩展靠换大计算 |
| 数据分布 | PS 按页区间分区 | 计算层分库分表 | SQL 单实例语义完整；跨区写仍需上层方案 |
| 兼容策略 | 保留 SQL Server 全引擎 | 借云化重写引擎 | 生态无损迁移；优化空间受既内核约束 |
| 运维形态 | 三层各自无/少状态 | 单进程紧耦合极限性能 | 秒级换主、在线升级；组件间网络跳数增加 |

把本表与 Aurora 笔记第三节的取舍表并排看，会得到一个干净的判据：**凡 Aurora 表中出现"库侧/存储节点"的行，Socrates 表中都对应"平台层/独立服务层"的行**——同一组需求（持久、物化、新鲜度、围栏）在两种信任边界下的重新落位。这也是答思考题 1 的钥匙。

## 四、与相关工作对比

- **vs Aurora（本仓库精读：[../doi_10.1145_3035918.3056101/00-精读笔记.md](../doi_10.1145_3035918.3056101/00-精读笔记.md)）**：同一问题的两家答卷——Aurora"存储节点自治"（segment 六副本、quorum+tail-of-log 在库侧），Socrates"职责分层外包"（日志一条流、物化独立成层、持久性交平台）。可记为：**Aurora 把数据库的恢复问题变成存储问题，Socrates 把存储问题变成平台问题。** 两者共享：redo 小记录复制、按需物化、term/围栏、秒级 failover、单写多读。
- **vs Snowflake（本仓库精读：[../doi_10.1145_2882903.2903741/00-精读笔记.md](../doi_10.1145_2882903.2903741/00-精读笔记.md)）**：OLTP/OLAP 存算分离镜像。Snowflake 取消原地更新（不可变文件+清单）换取"零一致性协议"；Socrates 保留页级原地语义，用"单日志流+按需物化"把协议收敛到最小。三者（含 Aurora）合看即"云上事务/分析系统形态学"的三原型。
- **vs Spanner/共享无存 NewSQL**：Spanner 以分片+2PC+Paxos 原生分布式为第一原则（参见 [`../../courses/并行与分布式系统/MIT6.824/notes/L15-Spanner全球数据库.md`](../../courses/并行与分布式系统/MIT6.824/notes/L15-Spanner全球数据库.md)）；Socrates 是"单机语义最大化保留"路线，跨区可写不在承诺内——两条路线的高下之争见 [`../../notes/多数据中心架构.md`](../../notes/多数据中心架构.md)（仓库既有笔记）。
- **vs 经典 WAL/ARIES 谱系**：PS 的"页 LSN 幂等应用"就是 ARIES redo 规则的云化重生；对照动手项目 [`../../courses/数据库系统/15445/projects/07-wal-recovery/README.md`](../../courses/数据库系统/15445/projects/07-wal-recovery/README.md)——那里恢复发生在单机重启时，这里恢复被消解为"永远不需要恢复"。
- **vs Gray 事务谱系（本仓库精读：[../doi_1981_gray_transaction_concept/00-精读笔记.md](../doi_1981_gray_transaction_concept/00-精读笔记.md)）**：Gray 的"事务是原子单位"在 Socrates 中被拆为"原子性=X-Store 日志位置、持久性=平台存储、隔离性=单写 compute"——三属性三个家。

## 六、批判与延伸

**批判性阅读：**

1. **厂商论文、平台绑定**：实验全在自家云与自家引擎上；"持久性外包给平台存储"的前提是你对该平台有近乎无限的信任——跨云可移植性实质上让渡给了 Azure，这与 Aurora 自建存储层形成鲜明商业对照（技术选择背后是云厂商的纵向整合战略）。
2. **PS 层的双重身份未完全讲透**：PS 既当缓存又当"物化材料库"，其可用性就进入了读路径关键链；论文对 PS 分区再平衡、热点页区间的处理着墨有限（对缓存型系统这是老问题）。
3. **单写者的语义红利与天花板并存**：保住 T-SQL 单实例语义的代价是写扩展=纵向扩容；跨区域可写、冲突消解等 NewSQL 核心难题被体系性回避。
4. **术语与命名密度高**：Falcon/Hadar/X-Store/BAG 等内部代号散布全文，部分组件边界只在工程后续文档中才清晰（本笔记凡未逐字核实者均已标注口径）。
5. **"读旧"问题被水位约定掩盖**：只读副本默认读"最近可用 LSN"，业务要"读己之写"需要客户端携带水位或路由到主——论文未展开该编程模型的工程成本。
6. **论文可读性债**：结构上"组件巡礼"多于"不变式清单"，若能在开头给出三条正确性不变式（单一写者流、页幂等物化、围栏任期），后文全部机制都能被压缩半页讲完——这是两代云 OLTP 论文共同的写作遗憾。

**延伸：**

- 三篇连读路线（本仓库均已有精读）：Snowflake 2016（OLAP 形态）→ Aurora 2017（OLTP·库侧自持副本）→ Socrates 2019（OLTP·平台外包），可自拟一篇"云原生数据系统形态学"小结。
- 与国产云 OLTP 的对照阅读入口：仓库既有材料 [`../../notes/X-Engine.md`](../../notes/X-Engine.md)（LSM 路线）与 [`../../notes/aurora.md`](../../notes/aurora.md)（Aurora 外围链接合集）；PolarDB 的"共享日志存储"介于两者之间，可作课后比较。
- 学术侧：Kossmann 一脉的弹性查询处理研究（如 *The Case for Distributed Shared Nothing Databases for Elastic OLTP*，未核 DOI）恰可作为 Socrates 路线的理论注脚。
- 商品形态侧：Socrates 要素落地为 Azure SQL Hyperscale（未核文献），与 Aurora 之于 RDS 的关系对偶——"论文定架构、产品线收编"成为 2016–2021 云数据库的标准叙事模板。
- 观点史侧：Stonebraker 阵营早年断言"关系模型与云不兼容"，Aurora/Socrates 双双证伪其"必须抛弃 SQL 单实例语义"的部分——可结合仓库 [`../../book/Readings_in_Database_Systems/00-总览与阅读地图.md`](../../book/Readings_in_Database_Systems/00-总览与阅读地图.md) 的观点谱系做延伸阅读（该链接已验证存在）。

## 七、一页总结（复习卡）

- **问题**：第一代托管 SQL Server 的弹性/HA/备份全部受制于"进程持有数据、副本重放日志、恢复正比于日志量"。
- **方案**：计算无状态化（单写多读）；X-Store 单逻辑日志 + 平台共享存储承担持久性；Page Server 按页区间分区、惰性物化、as-of-LSN 供页；Falcon 让副本告别重放；HADR=日志流跨区续接。
- **所得**：秒级且与库大小无关的 failover、近零成本读扩展、备份还原元数据化、在线打补丁。
- **所欠**：平台锁定、单写天花板、PS 可用性进入读关键路径、跨区可写未解。
- **地位**：与 Aurora 并立为"云原生 OLTP 存算分离的两种纯血形态"；与 Snowflake 笔记对读即完整"存算分离三角"。

## 九、思考题（5 道）

1. 持久性外包（Socrates）与 quorum 自持（Aurora）：若平台共享存储本身出现分区/双写（极小概率但非零），两种架构各靠什么机制保证日志不分叉？说明"信任边界"移动后，正确性论证的责任如何随之移动。
2. PS 回答 `页P as of ℓ` 的物化是幂等的——请复用 2.3 伪码论证：两个 PS 实例短暂并存（旧 PS 未死、新 PS 已接管同一页区间）时会发生什么？围栏机制必须部署在哪一层才够（compute→X-Store 还是 PS→存储池）？
3. Falcon 消灭了副本重放，但把"副本延迟"改写成了"PS 物化滞后 + 水位推进策略"。请构造一个读负载，比较新旧两种模型下该负载的最坏可见性延迟。
4. Snowflake 的 GC 单位是"微分区文件（被版本清单钉住）"，Socrates 是"页/日志段（被引用计数钉住）"，Aurora 是"segment 内旧版本（被 min-contiguous LSN 钉住）"。请解释为什么 OLTP 系统无法像 OLAP 那样用"整块重写"回避页级 GC 的细粒度核算。
5. 为什么说"单写者 + 无状态计算"使在线升级成为可能，而 Aurora 的只读副本升级（滚动）与之相比各有什么窗口？从"谁拥有正确性状态"一句话出发作答。

## 十、阅读方法与常见误读提醒

1. **别把 Page Server 读成"远程缓冲池"**：BP 是无正确性角色的缓存，PS 是物化与供页的**权威服务层**（其答案可重建、其宕机可接管）——把它当缓存会低估协议角色，当数据库又会高估其状态。
2. **"单副本"仅指逻辑日志一条流**：物理字节的多副本/纠删码在平台层，并未消失；"Socrates 只存一份数据"是常见以讹传讹（本笔记 2.4 的分水岭正在于"谁负责这份冗余"）。
3. **HADR ≠ 跨区域多活**：它是高可用与容灾（failover/DR），不提供跨区并发写；拿它与 Spanner 比"多活"是错置比较对象。
4. **组件代号需以论文原文为准**：Falcon/Hadar 等在本笔记中的边界描述基于论文行文结构与可靠二手资料整理，未逐字复核处均已标注；引用作文献综述时请先回查原文。
5. **建议配套阅读顺序**：先读 Aurora 笔记建立"日志即数据库"心智，再读本文 2.3–2.5 做逐层对照，最后回读 Snowflake 笔记第三节，完成 OLTP/OLAP 存算分离三角。
