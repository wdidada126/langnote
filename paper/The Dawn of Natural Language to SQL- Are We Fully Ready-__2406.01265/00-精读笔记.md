## 一句话总结
大模型把 NL2SQL（自然语言转 SQL）的效果推高了，但「到底能不能上生产」没人说得清。本文做了一套多角度评测框架 NL2SQL360，把主流方法按数据领域、SQL 特征等维度细细横评，并且用它在设计空间里自动搜出了一个叫 SuperSQL 的方案——在 Spider 测试集上执行准确率 87%、BIRD 上 62.66%。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：让不懂 SQL 的用户用一句自然语言问「上个月销量最高的三个城市是哪些」，系统自动生成可执行的 SQL 去查库。这叫 NL2SQL / Text-to-SQL。
- **为什么难**：
  - 自然语言有歧义，同一个问题可以对应多种 SQL；
  - 换一个数据库（跨领域 cross-domain）schema 就全变了，模型必须「看 schema 说话」；
  - 复杂 SQL 涉及嵌套子查询、多表 join、GROUP BY/HAVING 等结构；
  - 「看起来对」和「执行结果对」不是一回事，所以评测口径很关键。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 序列到序列（seq2seq）+ 语法约束 | IRNet、RAT-SQL | 编码器读问题+schema，解码器按语法生成 | 结构可控，跨域泛化靠 schema linking |
| 预训练语言模型微调 | Graphix-T5、RESDSQL | 用 BERT/T5 编码 schema 与问题 | 效果强，需要标注数据 |
| 大模型提示（prompting / ICL） | DIN-SQL、C3、CHESS | 用 few-shot 示例和分解式提示引导 LLM | 无需训练，token 成本高、对提示敏感 |
| 智能体 / 多轮自校正 | MAC-SQL、SQLFixAgent | 生成→执行→看错→改 | 更接近实用，链路复杂 |

- **本文属于哪一类**：它本身不是一个新的生成模型，而是**评测框架 + 设计空间搜索**——用统一尺子量所有方法，并自动组合出最优方案（SuperSQL）。
- **必懂关键名词**：
  - **Spider**：跨领域 Text-to-SQL 的经典基准，多库多表，标注 SQL 较复杂。
  - **BIRD**：更贴近真实业务的大规模基准，强调外部知识与执行效率，难度显著高于 Spider。
  - **执行准确率（execution accuracy, EX）**：跑生成的 SQL 和金标 SQL，比对**返回结果**是否一致，比「字符串是否相同」更合理。

## 1. 问题背景与动机
- 前人工作简述：LLM 出现后，NL2SQL 的范式从「训练专用 seq2seq 模型」转向「提示/微调大模型」，各类方法（分解式提示、自校正、多智能体）层出不穷，榜单数字快速攀升。
- 前人的缺陷 / 未解决问题（逐条）：
  1. **评测角度单一**：多数工作只报一个总分（如整份 Spider 的 EX），看不出「哪类数据领域」「哪类 SQL 结构」上强弱。
  2. **无法回答「能不能上生产」**：总分高不代表在特定业务场景下可靠，缺少面向应用场景的横向对比。
  3. **缺少统一比较平台**：不同论文的实验设置、切分方式、指标口径不一致，难以公平对照。
  4. **方法选型靠拍脑袋**：面对几十种方法，工程师不知道「我的场景该选哪个」，缺少自动化的设计空间探索。

## 2. 核心方法
- **最直观类比**：以前的 NL2SQL 榜单像「高考总分排行榜」，只告诉你谁分高；NL2SQL360 像「各科成绩单 + 志愿填报助手」——既告诉你谁擅长代数、谁擅长几何，也能根据你的需求自动推荐最合适的组合。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：一批 NL2SQL 方法（含 LLM 系与传统系）+ 一批评测数据集（Spider、BIRD 等）+ 一堆「角度」（数据领域、SQL 特征如是否含子查询/聚合/多表 join 等）。
  2. **关键操作一：多角度切分评测**。NL2SQL360 把测试集按不同维度切开，在每个切片上分别打分，形成细粒度画像。
  3. **关键操作二：设计空间（design space）探索**。把 NL2SQL 系统拆成可替换的模块/超参（如提示策略、schema 链接方式、后处理等 🔧 具体维度清单见原论文），在该空间里用 NL2SQL360 自动搜索。
  4. **关键操作三：选出最优解**。搜索结果是 SuperSQL——在 Spider 上以执行准确率衡量表现突出的一个具体组合方案。
  5. **输出**：各方法的多角度横向对比结论 + 一个针对用户特定需求的最优 NL2SQL 方案。
- **形式化要点**：核心是「评测维度集合」与「方法设计空间」两个笛卡尔积上的搜索问题；超参数即设计空间中每个模块的可选项 🔧（论文未在摘要给出维度全表）。
- **理论性质 / 保证**：无理论保证（🔧 论文以实证为主）；其价值在于评测口径的一致性与可复现。

## 3. 变体 / 工程版（如有）
- **SuperSQL**：本文通过设计空间搜索得到的具体方法，是「框架产出的样例解」，可以看作 NL2SQL360 的一次能力演示。
- **按场景定制**：框架的设计目标是「针对不同应用场景推荐不同方法」，因此理论上可以为「金融报表库」和「医疗问答库」给出不同答案 🔧。

## 4. 实验结论（概览）
- 对比基线：当时主流的（leading）NL2SQL 方法，涵盖不同范式 🔧 具体清单查原论文表格。
- 数据集：Spider、BIRD（摘要明确提及两者的 test set）；并覆盖不同数据领域与 SQL 特征的切片。
- 评价指标：执行准确率（execution accuracy）为主 🔧 是否含其他指标需查原论文。
- 已核实结论（摘要原文数字）：
  - SuperSQL 在 **Spider test set 上执行准确率 87%**。
  - SuperSQL 在 **BIRD test set 上执行准确率 62.66%**。
  - 两者均被描述为「competitive（有竞争力）」水平。
- 结论方向：不同方法在不同切片上强弱差异明显，**不存在通吃的单一方法**；因此「按场景选型」比「追榜」更重要。🔧 各切片上的精确对比数字请查原论文图表后补入。

## 7. 2026 视角（🔧）
- 到 2026 年，NL2SQL 已是 BI/数据分析产品的标配入口，但「可信度」仍是落地瓶颈：企业普遍要求「生成 SQL 可解释 + 结果可校验 + 有权限约束」。
- 评测重心从「单条 EX」转向「真实业务库上的端到端成功率、成本（token/延迟）、以及错误可恢复性」；多角度/分场景评测已成为共识。
- 趋势包括：结合数据库内容的 grounding、执行反馈自校正、以及把 NL2SQL 放进更大的 agent 工作流里。本节为趋势性判断，具体数字与产品格局 🔧 查当年资料。

## 8. 新手学习路线
- **10 分钟**：读摘要 + 第 0 节，记住两个数字（Spider 87%、BIRD 62.66%）和两个概念（多角度评测、设计空间搜索）。
- **30 分钟**：找一个你熟悉的 NL2SQL 方法（如 DIN-SQL），在 Spider 上按「有无子查询」切片各取 20 条，自己统计成功率，体会「总分掩盖差异」。
- **进阶**：精读 NL2SQL360 的评测维度定义与设计空间定义；尝试为某个垂直领域（如电商订单库）复现一次「自动选型」；对照 Dr.Spider 检验所选方案在扰动下的稳定性。
