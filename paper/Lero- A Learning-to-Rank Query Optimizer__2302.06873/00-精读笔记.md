## 一句话总结
把「预测查询计划的确切执行代价」这个很难的回归问题，改成「判断两个计划谁更快」这个容易得多的排序问题：让优化器站在数据库原生优化器的肩膀上，通过两两比较不断学习，把 PostgreSQL 的计划执行时间最多降 70%。

## 0. 给新手的阅读前置（背景知识地图）

**子方向解决什么大问题？** 你给数据库发一条 SQL，DBMS 内部的查询优化器要在成百上千种等价执行计划（不同 join 顺序、不同索引、不同连接算法）里挑一个。传统数据库（如 PostgreSQL）用**基于代价的优化器（CBO）**：用统计信息 + 代价模型估算每个计划的执行代价，选最小的。代价模型估算不准（尤其是复杂 join、相关数据分布）时，选出的计划可能慢几个数量级。

**为什么难？**
- 真实执行延迟受硬件、缓存、并发等影响，精确建模几乎不可能；
- 基数估计（cardinality estimation）误差会沿计划树指数放大；
- 学习型方法要处理持续变化的负载和数据分布。

**主流解法分类（表格）：**

| 类别 | 思路 | 代表 |
|------|------|------|
| 改进基数/代价估计 | 用 ML 学更准的中间结果行数或代价 | 各种 learned cardinality estimation |
| 端到端学习优化器 | 用强化学习/自监督直接「生成」最优计划 | Balsa、Neo 等 |
| **学习排序（本文）** | 不预测绝对代价，只学「谁比谁好」的相对顺序 | **Lero** |
| 基于提示/枚举的选择 | 保留原生优化器，用 ML 选 hint | COOOL 等 |

**本文属哪类？** 学习排序类——且是「寄生」在原生优化器上的增强型，不从头造轮子。

**关键名词直觉解释：**
- **计划（plan）**：一条 SQL 的具体执行方案，比如「先做 A join B 用哈希连接，再做 join C」；
- **learning-to-rank（学习排序）**：搜索/推荐领域的技术，核心是模型只需要给出正确排序，不需要给出精确分数；
- **pairwise（成对法）**：学习排序的一种训练方式，把「排序」拆成大量「A 是否优于 B」的二分类任务。

## 1. 问题背景与动机

- 前人工作：一类用 ML 替换/增强 CBO 里的代价模型或基数估计；另一类（如深度强化学习型优化器）直接从零学习整个优化策略。它们在部分 benchmark 上表现出色。
- 前人的缺陷（论文逐条指出）：
  1. **性能不稳定**：让模型直接预测执行时间/代价，本质是回归任务，误差没有界，偶尔会把好计划排到很后，导致个别查询灾难性变慢；
  2. **训练成本高**：需要大量真实执行计划的 latency 标注（要真的跑一遍），又贵又慢；
  3. **模型更新慢**：数据/负载变了以后，重新训练端到端模型代价大，难以持续适应；
  4. **侵入性强**：许多方案要求替换原生优化器，工程集成风险高，丢弃了数据库几十年的优化智慧。
- 核心洞察：**优化查询根本不需要知道计划「多快」，只需要知道「谁更快」**。相对顺序比绝对数值容易学得多。

## 2. 核心方法

**最直观类比**：与其请一位品酒师给每瓶酒打出精确分数（谁也打不准），不如让他只做一件事——给定两瓶酒，说出哪瓶更好。这个判断简单得多，而且成千上万次两两比较叠加起来，就能得到可靠的完整排序。

**具体做法（输入 → 关键操作 → 输出）：**
1. **输入**：一条 SQL + 原生优化器枚举出的候选计划集合（Lero 建在原生优化器之上，不自己枚举）。
2. **训练数据构造**：对同一查询的多个计划，用真实执行得到相对快慢，构造「计划对」标签（谁优于谁）。
3. **pairwise 分类器训练**：模型输入是两个计划的表示（计划树结构 + 算子特征等），输出是「计划 A 优于计划 B」的概率。二分类比回归好学得多。
4. **推理时排序**：对候选计划做（基于 pairwise 分数的）排序聚合，选出最优计划。通常可以从原生优化器的 top 计划出发做增量比较，比较次数远小于全排序。
5. **持续学习**：随着查询不断执行，新的真实执行结果不断变成新的训练样本，模型自动跟上负载与数据变化。

**形式化要点**：把「选出 argmin_cost(plan)」的目标，转化为学习函数 f(plan) 使得对任意 plan_i 优于 plan_j，有 f(plan_i) > f(plan_j)，即只要求序关系一致性，不要求 f 近似任何物理量。（论文中的具体损失函数与特征编码细节 🔧 见原论文 §3-4。）

**理论性质/保证**：排序目标对代价估计误差更鲁棒；但本文主要是系统/实证工作，无强理论保证。其「非侵入式设计」的保证是工程性的：可在任意现有 DBMS 上以最小集成成本实现。

## 4. 实验结论（概览）
- **基线**：PostgreSQL 原生优化器，以及其他学习型查询优化器（论文中具体对哪些方法 🔧 见原论文实验节）。
- **数据集/负载**：多个 benchmark（如 JOB 类负载等 🔧 精确列表见原文）。
- **指标**：计划执行时间（端到端延迟）、优化开销、随负载变化的适应性。
- **结论方向（摘要核实）**：
  - 在多个 benchmark 上达到「接近最优」的表现；
  - 相比 PostgreSQL 原生优化器，计划执行时间最多降低 **70%**；
  - 相比其他学习型优化器，最多降低 **37%**；
  - 能持续学习、自动适应负载与数据变化。
