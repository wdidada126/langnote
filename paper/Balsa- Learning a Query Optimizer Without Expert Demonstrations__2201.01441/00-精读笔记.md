## 一句话总结

传统优化器要专家写好几年，已有的"学习型优化器"（如 Bao）又得靠专家优化器示范才能学。Balsa 用**深度强化学习**证明：从零开始、不需要任何专家示范，也能学出查询优化器——在 Join Order Benchmark 上 2 小时追平两个专家优化器，再学几小时运行时最高快 **2.8×**。

## 0. 给新手的阅读前置（背景知识地图）

- **大问题**：SQL 发给数据库后，先由**查询优化器**决定执行计划（先 join 哪两张表、用不用索引……）。计划好坏可差几个数量级。专家优化器（System R 谱系）动辄数万行规则，难适配新硬件/新负载。
- **为什么难**：计划空间是组合爆炸的；真实执行一次计划代价高（不能拿生产库随便试）；盲目学习早期会跑出灾难性慢查询。
- **主流做法对比**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 基于代价（CBO） | System R/PostgreSQL | 枚举计划+代价模型 | 成熟稳定；代价模型靠手调 |
| 模仿学习 | Bao | 学习专家优化器的建议 | 起点好；**依赖专家**，上限被锁死 |
| 从零强化学习 | **Balsa（本文）** | 无示范，自探索学计划 | 无专家依赖；需安全机制兜底（本文） |

- **本文属于哪类**：第三类，核心贡献是"无专家"设定下的两阶段安全学习框架。
- **必须先懂的名词**：
  - **Join Order Benchmark（JOB）**：基于 IMDb 的 113 条多 join 分析查询集，优化器试金石。
  - **强化学习（RL）**：智能体试动作（选计划）、拿奖励（越快越好）逐步改进策略。
  - **计划代价估计**：传统优化器预测执行开销的模型（Balsa 不依赖其准确性）。

## 1. 问题背景与动机

- 前人工作：Bao（SIGMOD'21）用 RL 调优专家优化器的提示；Neo 等模仿学习方法需要专家计划做示范。
- 未解决的问题：
  1. 模仿学习的性能上限=专家优化器的上限，专家错了学错；
  2. 未来计算环境（新硬件、新引擎）可能**根本没有可用的专家优化器**可模仿；
  3. 纯探索的 RL 早期会产生极慢查询，生产环境不可接受。

## 2. 核心方法

- 类比：学开车——先在模拟器里随便撞（便宜），掌握基本盘后再上真路（真实执行），且上真路时始终带着"教练刹车"（回退机制），绝不把车开进沟里。
- 具体做法（输入 → 操作 → 输出）：
  1. **阶段一：模拟器学习**——用一个与具体引擎无关的简单代价模拟器做 RL 热身，学到 join 顺序等基本常识；
  2. **阶段二：真实执行安全学习**——切到真库执行拿真实时延做奖励；每一步都有安全兜底：跑不出结果/超时则回退到传统优化器计划，保证"任何时刻都可用"；
  3. 奖励为计划时延，策略逐步收敛（算法细节/超参 🔧 见原文）。
- 理论/系统性质：学习过程中始终有可用计划（安全性），且不依赖代价模型的准确性。

## 3. 变体 / 工程版

- 论文实现即工程版（基于 Postgres 生态做执行后端 🔧）；与 Bao 的关键差异是无示范、无专家优化器依赖。

## 4. 实验结论（概览）

- 对比基线：开源专家优化器与商业专家优化器（PostgreSQL / SQL Server 类，🔧 具体以原文为准）；负载：JOB。
- 结论方向（摘要明确给出）：
  - **2 小时学习即追平两个专家优化器**；
  - 再学几小时，工作负载总运行时最高快 **2.8×**；
  - 🔧 逐查询/逐时段曲线与绝对时延数字查原文 Figure 后补。
