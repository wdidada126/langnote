## 一句话总结
多轮 Text-to-SQL（像 CoSQL 那样的连续追问）里，已有方法只是把历史对话信息塞进当前句子的表示里，却没有显式地表征和跟踪「**交互状态**」——即历史 SQL 留下的、与当前意图相关的状态。本文定义了**两类交互状态**（基于 schema item 的 schema-state 与基于 SQL keyword 的 SQL-state），用**关系图神经网络**和**非线性层**分别更新它们的表示，再用动态的状态表示去解码当前轮的 SQL；在 CoSQL 上超过了当时排行榜上的其他已发表方法。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：真实查数是对话式的——「列出所有学生」→「只看男生」→「按年龄排序」。多轮 Text-to-SQL 要求模型理解**当前这句话相对于前文做了什么修改**。
- **为什么难**：当前轮的句子经常**高度省略**（只说「只看男生」），必须靠上下文补全；而上下文不只是「前几句话」，还包括**已经生成的历史 SQL**所隐含的结构状态（选了哪些列、有没有 GROUP BY、有没有 ORDER BY）。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 上下文拼接/历史编码 | 早期对话模型 | 把历史 utterance 编码后拼进当前表示 | 简单，但「状态」是隐式的、难以定位 |
| 编辑式建模（edit-based） | 后续 CoE-SQL 等 | 把当前轮看成对上一轮 SQL 的编辑 | 直观，但需要额外建模编辑动作 |
| 交互状态显式跟踪（本文） | IST-SQL | 显式定义并更新 schema-state 与 SQL-state | 可解释、结构化，需要设计状态定义与更新网络 |
| LLM 多轮对话 | 2023 年后主流 | 直接把历史 SQL 与 schema 塞进提示 | 强大，但对长上下文与错误累积敏感 |

- **本文属于哪一类**：**交互状态显式跟踪**路线。
- **必懂关键名词**：
  - **multi-turn / conversational text-to-SQL**：连续多轮、上下文相关的 Text-to-SQL（代表基准 CoSQL、SParC）。
  - **schema state**：与 schema item（表/列）相关的交互状态——当前查询已经涉及哪些列、还可能涉及哪些列。
  - **SQL state**：与 SQL keyword（SELECT / WHERE / GROUP BY / ORDER BY…）相关的交互状态——当前查询在 SQL 结构上走到了哪一步。
  - **relational graph neural network（关系图神经网络 / R-GNN）**：在带**边类型**（关系）的图上做消息传递，适合建模 schema 内丰富的结构关系（主键-外键、同表列等）。

## 1. 问题背景与动机
- 前人工作简述：多轮 Text-to-SQL 的已有研究通常用上下文信息来丰富 utterance 表示，并进一步影响解码过程；CoSQL/SParC 等基准提供了带交互历史的对话数据。
- 前人缺陷/未解决问题（逐条）：
  1. **把上下文当特征而非状态**：只把历史当「额外特征」编码进来，没有显式描述和跟踪交互状态。
  2. **忽略历史 SQL 的结构信息**：交互状态其实由**历史 SQL 查询**决定，并与当前意图相关，这一点被忽视。
  3. **schema 侧状态未建模**：多轮中「哪些表/列还在被使用」是持续变化的，缺少专门表示。
  4. **SQL 侧状态未建模**：「当前 SQL 处在哪个子句/关键字阶段」同样缺少专门表示。
  5. **状态不动态**：即使有表示，也缺少随轮次推进的**更新机制**。

## 2. 核心方法
- **最直观类比**：对话查数像两个人一起填一张 SQL 表单：一个人要一直记着「我们已经勾了哪些列（schema 状态）」「表单填到哪一栏了（SQL 状态）」。本文就是把这两块「记忆」显式写成状态，并每轮更新。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：当前轮的 utterance、对话历史（含历史 SQL 查询）、数据库 schema（通常含多张表）。
  2. **定义两类交互状态**：分别基于 **schema items** 与 **SQL keywords** 定义状态。
  3. **状态更新**：
     - **schema-state**：用**关系图神经网络（R-GNN）**更新其表示（利用 schema 内部的关系结构做消息传递）。
     - **SQL-state**：用**非线性层**更新其表示。
  4. **解码**：用动态更新的 schema-state 与 SQL-state 表示去**解码当前轮对应的 SQL**。
  5. **输出**：当前轮的 SQL 查询。
- **形式化要点**：两类状态（schema-state / SQL-state）+ 两种更新机制（R-GNN / 非线性层）是本文的方法骨架；摘要未给层数、维度等超参数 🔧。
- **理论性质/保证**：无（经验性方法）。

## 7. 2026 视角（🔧）
- 多轮 Text-to-SQL 已进入 LLM 主导阶段：把历史轮次、历史 SQL 与 schema 一起放进提示，配合执行反馈与澄清式追问，是当前的默认做法。
- 但「**状态**」这个概念并没有过时：工业界的对话式 BI、指标问答系统仍然显式维护「当前查询的筛选条件/维度/度量」这一状态机，以避免大模型在多轮中丢失上下文。本文的两类状态划分（schema 侧 / SQL 结构侧）仍是有用的建模脚手架。
- 近年趋势还包括：多轮中的**指代消解与省略恢复**、错误累积的自动纠正、以及与权限/口径约束结合。
- 本节为趋势性判断；具体 SOTA 🔧 查当年榜单。

## 8. 新手学习路线
- **10 分钟**：读摘要 + 第 0、2 节，记住两个状态：schema-state（涉及哪些列）与 SQL-state（填到哪一栏）。
- **30 分钟**：打开 CoSQL 随机看一段对话，试着自己把每轮的「状态变化」写下来；再跑通 IST-SQL 的推理示例。
- **进阶**：精读状态的定义与更新公式；做消融（只留一类状态）看各自贡献；用 LLM 提示复现同一任务，比较两者在多轮省略场景下的差异。
