## 一句话总结
当向量数据大到一台机器装不下时，必须把数据切成很多片（shard），查询时只搜其中少数几片。过去「怎么切」和「怎么路由到正确的那几片」是绑死的一套方案，本文把**路由算法做成模块化插件**——任意切分方法都能配任意路由算法——从而第一次让「均衡图划分（balanced graph partitioning）」这种切分质量高但没有配套路由的方法真正能用起来；在十亿级数据上，90% recall@10 的 QPS 最高比最强对手高 **2.14 倍**。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：在十亿甚至更大的向量库里找最近邻。单机装不下，就必须**分布式**：把数据分片放到多台机器上，查询时只把请求发给少数几个分片，才能同时保证低延迟和高吞吐。
- **为什么难**：
  - **分片要保持「邻居聚集」**：理想情况下，一个点的所有近邻都应该落在同一两个分片里（所谓的 neighborhood-preserving shards），否则一次查询要问很多台机器。
  - **路由要准还要快**：查询来了怎么快速判断该去哪几片？路由本身若太慢/太占内存，就把分片省下的时间全赔进去了。
  - **切分与路由耦合**：历史上一个切分方法配一个专属路由算法，好切分方法（如均衡图划分）没人会给它配路由，导致它一直用不起来。
  - **十亿级规模**：训练（train）路由器的时间必须短，否则每天重建索引的业务根本扛不住。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 聚类分桶（IVF / k-means 路由） | Faiss IVF、SPANN | 用 k-means 把空间切桶，查询时按桶心距离挑几桶 | 路由极简单，但簇边界处的近邻会被切散 |
| 空间划分树 | KD-tree / 球树 / 随机投影树 | 递归切分空间 | 低维好用，高维要砍很多树 |
| 图划分（Graph Partitioning） | 本文所用的 balanced graph partitioning | 先在点上建近邻图，再切成均衡且跨边最少的片 | 切片质量最好（近邻更集中），但天然没有路由方法 |
| 学习式路由 | 各种 learned router | 学一个模型预测该去哪几片 | 灵活，但训练成本高、泛化未明 |

- **本文属于哪一类**：把「图划分」路线补完——提供**通用的、可插拔的高质量路由算法**，并提出**强理论保证**。
- **三个必懂的关键名词**：
  1. **neighborhood-preserving shard（保邻分片）**：任意查询点的近邻只集中在极少数分片里，这是整个方法成立的前提。
  2. **routing algorithm（路由算法）**：查询一到就决定「搜哪几个 shard」的模块，本文的核心贡献。
  3. **balanced graph partitioning（均衡图划分）**：让每个分片大小差不多、同时跨分片的边尽量少的图切分方法；质量高但过去缺配套路由。

## 1. 问题背景与动机
- **前人工作简述**：把 ANNS 拆成多个子问题（decompose into sub-problems）是分布式 ANNS 的骨干思路。已有工作一般会给出一整套「这种切分 + 这种路由」的方案，两者强绑定；也有针对特定切分设计的路由方法，在特定数据上表现不错。
- **前人缺陷 / 未解决问题（逐条）**：
  1. **路由与切分方法紧耦合（inextricably linked）**：换个切分就要重写一套路由，工程上无法复用。
  2. **高质量切分无路由可用**：balanced graph partitioning 是公认质量好的切分方法，但**没有天然对应的路由算法**，因此迟迟没能落地于 ANNS pipeline。
  3. **缺乏理论保证**：现有路由多为启发式，对「为什么能找到正确的分片」缺少可证明的性能界。
  4. **可扩展性受限**：部分现有方案训练慢、内存占用高，无法应付 billion-scale。
  5. **高召回区间的吞吐不足**：要在 90% 以上 recall 维持高 QPS，先前方法需要搜索过多分片。

## 2. 核心方法
- **最直观类比**：把一个超大城市切成若干片区，每片有自己的快递站。以前是「这个城市专门配一种导航法」，换区划方式就要重做导航；本文做的是**一个通用导航仪**——不管你怎么划区，它都能快速告诉你该去哪几个快递站找包裹，而且还能证明「按它走一定不会走冤枉路太多」。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：大规模向量点集（十亿级），以及一个选定的**切分方法**（本文重点使用 balanced graph partitioning）。
  2. **关键操作一：切分（Partitioning）**。把输入点切成若干个 **neighborhood-preserving shards**，目标是任意点的近邻尽可能只落在少数几个 shard 内。
  3. **关键操作二：模块化路由（Modular Routing）** ⬅️ **核心贡献**。设计**简单且高效**的路由算法，并**证明强理论保证**。它的关键特征是**模块化**：不依赖任何特定切分方法，可与任意 partitioning method 组合。
  4. **查询流程**：查询到达 → 路由器判定应该搜索哪些 shard → 只在这些 shard 上跑 ANNS → 合并 top-k 结果返回。
  5. **输出**：查询的近似最近邻集合，同时获得高 recall 与低延迟。
- **形式化要点**：
  - 关注的性能指标是 **QPS @ recall@10**（如在 90% recall@10 下的每秒查询数）。
  - 设计要求：路由**训练极快（extremely fast to train）、延迟低（low latency）、召回高（high recall）**——三个目标同时兼顾，这是本文优化的核心。
  - 🔧 具体的路由判定规则、理论保证的精确表述（常量与对数因子的形式）需查论文正文的 Theorem 陈述。
- **理论性质 / 保证**：论文明确 **prove strong theoretical guarantees on their performance**（对路由算法给出强理论性能保证）。这正是先前启发式路由所缺失的部分。🔧 具体定理与假设以论文原文为准。

## 3. 变体 / 工程版（如有）
- **模块化 plug-in 组合**：本文没有单一「算法」，而是一类可以搭配的组合——
  - Partitioning 侧可选 balanced graph partitioning 或其它方法；
  - Routing 侧换成本文提出的任一种新路由；
  - 二者按可用内存、延迟预算自由组合。这种「解耦」是最大的工程价值。
- **规模级**：完整 pipeline 在 **billion-scale** 数据集上做端到端评估，说明不是只适用中等规模的玩具数据。

- **动手建议**：
  1. 先用百万级子集跑通，再上十亿级（否则一次构建可能很久）；
  2. 固定 partition 不变，**换不同 routing 方法**比较 recall@10/QPS，体会本文「模块化」的卖点；
  3. 观察 shard 数量变化对 recall 的影响，找出自己喜欢的质量/延迟折中点。
