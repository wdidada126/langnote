## 一句话总结
RAINBLOCK 指出公链（如以太坊）低吞吐的瓶颈是用 Merkle 树验证交易带来的 I/O，于是用两招破局——把交易处理与 I/O 解耦（I/O 移出关键路径）+ 用为区块链定制的「分布式分片 Merkle 树（DSM-TREE）」减少 I/O 放大——在跨三洲四区域的地理分布下跑到 2 万 TPS。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：公链每笔交易都要先验证（数据来自不可信节点），以太坊用 Merkle 树做「可验证」——但这带来巨大 I/O 开销，成了吞吐瓶颈。
- **为什么难**：区块链要「去信任 + 可验证 + 高吞吐」三者兼得；Merkle 树验证需大量随机读盘，传统存储布局不适应。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 共识优化 | 各类 BFT/PoW 改 | 改共识提吞吐 | 不直接解决 I/O 瓶颈 |
| 存储定制 | **RAINBLOCK** | 定制 Merkle 存储 + I/O 解耦 | 直击 I/O，但与共识解耦 |
| 分片链 | 分片方案 | 并行分片 | 跨片复杂 |

- **本文属哪类**：存储/系统架构侧，针对「验证 I/O」而非共识。
- **2-3 个必懂关键名词**：
  - **Merkle 树**：用哈希把数据组织成树，根哈希可证明某数据是否被篡改（区块链验证基石）。
  - **I/O 放大（I/O amplification）**：为验证一笔交易要读很多无关节点，读放大严重。
  - **DSM-TREE（分布式分片 Merkle 树）**：本文提出的 Merkle 树变体，专为区块链状态存储裁剪。

## 1. 问题背景与动机
- 前人工作简述：以太坊等用 Merkle 树在应用交易前先验证其真实性。
- 前人缺陷/未解决问题（逐条）：
  1. **吞吐瓶颈在 I/O**：论文实证低吞吐源于 Merkle 树处理的 I/O 瓶颈，而非共识。
  2. **I/O 在关键路径**：验证 I/O 阻塞了交易处理。
  3. **存储未定制**：通用存储对区块链状态不友好，I/O 放大严重。

## 2. 核心方法
- **最直观类比**：把区块链节点想成「快递分拣中心」，每包裹（交易）要先拆箱验真（Merkle 验证）才处理；RAINBLOCK 把「验真」挪到后台流水线，并改用「为包裹定制的高效货架（DSM-TREE）」，前台分拣不再卡等。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：待处理的区块链交易。
  2. **解耦**：把交易处理与 I/O 分离，I/O 不再占关键路径。
  3. **定制存储**：用 DSM-TREE 存系统状态，降低 I/O 放大。
  4. **输出**：更高吞吐且安全性不变的交易处理。
- **形式化要点**：核心是「处理/I/O 解耦 + DSM-TREE 减少读放大」；安全性沿用 Merkle 验证语义。
- **理论性质/保证**：保持与原链同等安全性（不削弱安全），仅改 I/O 与存储结构。
