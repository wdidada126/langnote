## 一句话总结

KV 分离（把 value 挪出 LSM 树单独存日志）能降低写放大，却让垃圾回收（GC）变得昂贵。Parallax 提出**按 value 大小分级放置**：大值进日志、小值原地放、中等值前几层进日志+最后几层原地合并——在 RocksDB 与 BlobDB 之间取长补短，吞吐最高提升 12.4×/17.83×。

## 0. 给新手的阅读前置（背景知识地图）

- **大问题**：LSM-tree（RocksDB/LevelDB 的底座）把随机写变成顺序写，但写路径上同一份数据会被反复重写（**写放大 / I/O 放大**）。在 NVMe 快盘上，value 大时重写 value 本身成为主要开销。
- **为什么难**：两条路各有硬伤——
  - **原地放（RocksDB 默认）**：compaction 要拖着 value 反复搬家 → I/O 放大严重；
  - **KV 分离（BlobDB/WiscKey 思路）**：key 留在 LSM、value 进独立日志，compaction 轻了；但更新/删除后旧 value 变垃圾，需要 **GC 扫日志**，更新密集负载下 GC 开销爆炸。
- **主流做法对比**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 原地放置 | RocksDB | value 跟 key 一起进 LSM | 简单；I/O 放放大 |
| 完全 KV 分离 | BlobDB、WiscKey | value 全进日志 | 写放大低；GC 重 |
| 混合放置 | **Parallax（本文）** | 按 KV 大小分级决定放哪 | 兼顾两者（本文） |

- **本文属于哪类**：第三类——用解析模型给 KV 分级，再对每级用不同放置策略。
- **必须先懂的名词**：
  - **写放大（I/O amplification）**：实际写入字节量 ÷ 用户写入字节量。
  - **compaction**：LSM 后台把多层 SSTable 归并的过程，重写数据的主要来源。
  - **value log GC**：KV 分离后清理日志中失效 value 的过程。

## 1. 问题背景与动机

- 前人工作：WiscKey（FAST'16）提出 KV 分离；BlobDB 是 RocksDB 的分层实现；已有工作证明分离在快设备上收益显著。
- 未解决的问题：
  1. 分离的收益其实**与 KV 大小有关**，此前缺乏显式的收益建模；
  2. 更新/删除密集时 value log GC 代价极高，"一刀切全分离"得不偿失。

## 2. 核心方法

- 类比：搬家策略——家具特别大（大值）直接走货运（日志）最省事；小件（小值）随手装箱（原地）即可；中等件（中等值）前期走货运，到最后一两趟"顺路清货"（末端层级全量 compaction 时就地合并），免掉专门的回收行程。
- 具体做法（输入 → 操作 → 输出）：
  1. **建模**：推导 KV 分离收益随 KV 尺寸变化的解析模型；
  2. **分级**：据此把 KV 分为 small / medium / large 三类（阈值由模型给出）；
  3. **放置**：large 永远进日志；small 永远原地；medium 前面层级进日志，**到最后 1-2 层做 full compaction 时合并回原地**，同时回收日志空间——不需要额外 GC 扫描。
- 输出：系统 **Parallax**（RocksDB 之上的改造实现）。

## 3. 变体 / 工程版

- Parallax 本身即工程实现（基于 RocksDB）；核心超参数为 small/medium/large 阈值与"末端层数"（典型为最后 1–2 层，🔧 精确设置见原文）。

## 4. 实验结论（概览）

- 对比基线：RocksDB（全原地）、BlobDB（全分离）；负载：YCSB 各类（除 scan 类）。
- 结论方向（摘要明确给出）：
  - 吞吐：较 RocksDB 最高 **12.4×**、较 BlobDB 最高 **17.83×**；
  - I/O 放大：分别最高降低 **27.1×** 与 **26×**；
  - CPU 效率：分别最高 **18.7×** 与 **28×**；
