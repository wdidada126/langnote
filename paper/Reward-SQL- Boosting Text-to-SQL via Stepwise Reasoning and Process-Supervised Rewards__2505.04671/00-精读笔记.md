## 一句话总结
复杂 SQL 让大模型（LLM）容易一步走错。Reward-SQL 先让模型学会「分步、看数据库反馈地」拼 SQL（CoCTE 框架），再训练一个「过程奖励模型（PRM）」在每一步都打分引导，用强化学习把推理过程而非只看最终答案来优化，从而显著提升准确率与跨库泛化。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：Text-to-SQL 是把自然语言问题（如「每个部门工资最高的员工是谁？」）自动翻译成 SQL 的任务。大模型（LLM）让这事变强，但复杂查询（多表连接、嵌套子查询、聚合）依然容易出错。
- 为什么难：(1) 复杂 SQL 需要多步推理，模型容易在中间步骤犯错且难以回头；(2) 传统做法只在「最终 SQL 对不对」上给奖励（结果监督），中间走了弯路却没人纠偏；(3) 模型缺乏「执行反馈」——它其实可以跑一下中间结果来验证。
- 几类主流解法（表格）：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 上下文学习（ICL） | GPT-4 类闭源模型 | 给几个示例直接生成 SQL | 强但贵、难私有化部署 |
| 监督微调（SFT） | DIN-SQL、RESDSQL | 用标注数据微调开源模型 | 便宜可部署，但复杂查询欠优 |
| 结果监督 RL | 仅看最终答案对错 | 用最终正确性当奖励 | 中间错误难纠正 |
| 本文：过程监督 RL | Reward-SQL | 每步给奖励，引导推理 | 更稳定、可解释，但需要 PRM |

- 本文属于哪一类：开源模型 + SFT 打底 + 过程监督强化学习（process-supervised RL），并引入「执行感知（execution-aware）」的分步推理。
- 2-3 个必懂关键名词：
  - CTE（Common Table Expression，公共表表达式）：SQL 里 `WITH ... AS (...)` 的写法，可把中间结果命名复用，相当于「分步建临时表」，便于把复杂查询拆成可验证的小步。
  - 过程奖励模型（PRM）：不只判断最终答案，而是对推理的每一步打分，告诉模型哪一步走得好、哪一步走歪。
  - 执行感知（execution-aware）：让模型在推理中用「在数据库上实际跑一下中间结果」来发现自己错没错。

## 1. 问题背景与动机
- 前人工作简述：基于 RL 的 LLM 已提升 Text-to-SQL；但面对复杂查询仍受限于两点：缺少「基于数据库反馈的分步执行感知推理」，以及缺少「过程级奖励」来引导推理优化。
- 前人的缺陷/未解决问题（逐条）：
  1. 推理不可分解：复杂查询一步到位易错，缺乏中间可验证、可纠偏的步骤。
  2. 只有结果监督：只在最终 SQL 对不对上给奖励，中间弯路无人纠偏，优化不稳定。
  3. 忽视执行反馈：模型没有利用「在数据库上实跑中间视图」来自我校验。

## 2. 核心方法
- 最直观类比：写复杂 SQL 像解一道多步应用题；前人只在「最后答案」上判分，错了也不知道哪步错。本文让模型先学会「每写一步就验算一下」，再配一位「逐步打分老师（PRM）」，每步都反馈，最后用强化学习把「好步骤」固化下来。
- 具体做法（输入 → 关键操作 → 输出）：
  1. CoCTE 推理框架（分治 + 执行感知）：把 SQL 通过中间视图验证与结构化 CTE 逐步组合，每步都能在数据库上验证，提升准确率与可解释性。
  2. Reward-SQL 三阶段：
     - (1) 模型初始化：用 SFT 让 LLM 具备结构化 CoCTE 推理能力；
     - (2) 过程奖励设计：训练 PRM，结合「执行感知的轨迹评分」与「基于熵的步骤加权」，给出密集且可解释的过程监督；
     - (3) 过程监督 RL 与推理：把 PRM 融入训练与推理，用过程信号稳定优化、改善轨迹探索。
  3. 输出：更准、更可解释、泛化更好的 Text-to-SQL 生成。
- 形式化要点：PRM 提供「跨步骤的稠密奖励」；超参包括熵加权系数、RL 训练目标；核心是让奖励信号落在推理过程而非仅最终答案。
- 理论性质/保证：论文以实验为主，强调 PRM 带来的训练稳定性与探索改善（🔧 严格理论保证查原文）。

## 7. 2026 视角（🔧）
- Text-to-SQL 已从「序列生成」走向「推理 + 强化学习 + 过程监督」，与代码大模型、Agent 路线深度融合；过程奖励/验证器（PRM/verifier）是衡量复杂查询质量的关键组件。
