## 一、背景与问题：寻道时间支配一切的时代

### 1.1 性能模型前提（论文 §1，定性）

1990 年代中期的成本结构：磁盘容量便宜但**一次随机寻道 ≈ 10 ms**，顺序传输同样 10 ms 能读几页；主存（1996 年语境下几十~几百 MB）对"在线表"来说始终不够装。B-tree 的每次插入/删除平均要触碰**根到叶路径上多个页面**，且各页在盘上物理散落——写密集负载下，吞吐被寻道次数直接钉死。论文的对策与 Rosenblum/Ousterhout 的 LFS（日志结构文件系统）同源：**把一切随机写转成追加（append），把混乱留给后台顺序合并**。

### 1.2 论文的"第三条路"定位（§1/§2，对比既有两类方案）

- **B-tree（原地更新）**：读友好（点查 O(log) 次页面访问、范围查询顺叶走）、写残酷（每写多次随机 I/O + 页面重组）。
- **纯日志/磁带归档（LFS 思路）**：写完美（全顺序），但查询必须扫全部历史——读残酷。
- **LSM-tree**：折中——把"刚写的差量"留在内存（C0）和少量新文件（C1 各 run）里，**用"分层合并"控制差量堆积**，让绝大多数查询只碰最新的少数几份数据。

### 1.3 论文自报的三重性能指标（§1 的核心框架）

作者用三个互相拉扯的量给存储结构定价（这是全文的"问题定义"，也是现代三放大三角的前身）：
1. **插入/删除吞吐**（throughput）——越高越好；
2. **查询响应时间**（query response time）——点查要访问的盘页面数；
3. **实时性**（real-time response）——最近写入的数据多快可见、且**主存故障时只丢最近 t 秒**而非全表。
论文的原话框架（定性）：B-tree 把三者同时压向自己不能承受的一角；LSM-tree 明确**牺牲查询换吞吐**，并用"real-time 响应取决于 C0 驻留时间"这一性质守住在线业务底线。空间维度（空间放大/墓碑驻留）在 1996 文中只是附带讨论，**"写放大/读放大/空间放大"三角是现代（RocksDB 社区）对本文的回读式表述**，引用时注意时代差。

## 二、核心设计精读

### 2.1 C0 与 C1：主存组件 + 差量文件序列（§2，ASCII 重绘）

```
        写路径（追加，永不回头改）              读路径（多源归并）
   INSERT/DELETE k,v ──┐                    point-GET(k):
                       ▼                      1.查 C0（内存, O(1)）
              ┌──────────────┐                2.查最新 run 的 B-tree 页
              │ C0 内存有序表 │◄─ WAL(可选日志)  3.依次查其余 N-1 个 run
              └──────┬───────┘                4.首个命中即返回(新压旧)
        写满(每 t 秒) │ 顺序写出                RANGE-SCAN(a,b):
                     ▼                          C0 与各 run 的 [a,b] 切片
   C1 = [run1 | run2 | ... | runN]             做归并（新值覆盖旧值,
        ▲ 每个 run 是一个"按键有序的差量文件"     tombstone 屏蔽旧值）
        │ (differential, 非全量影像)
        └── 后台 k 路归并: 定期把所有 run 合成新 run
```

要点逐条：
- **C0（component 0）**：内存里的按键有序结构；所有新写先进这里，因此"最近 t 秒内的数据"永远在内存——这就是 real-time 响应的来源；主存故障最多丢 C0 内容（配合日志可恢复）。
- **C1（component 1）**：磁盘组件。写满的 C0 顺序落盘为一个 **run**（差量文件：只含这段时间的新增/删除，删除记 `deleted` 墓碑条目）。C1 = 一串按落盘时间排列的 run。
- **最新 run 的 B-tree 索引**：论文给**最近一两个 run** 额外维护磁盘页级的键索引（近似"每个 run 一个 B-tree"），因为查询的时间局部性使绝大多数点查命中新 run——这是在"纯日志"上补回读能力的第一块补丁。
- **merge（合并）**：后台线程周期性把 C1 的 N 个 run 做 k 路归并，压成一个新的大 run（新值覆盖旧值、物理消掉部分墓碑）。约束是**合并速度必须追上产生速度**：合并耗时 < t（C0 写满周期），否则写请求排队——1996 论文已经写明了"写停顿（write stall）"的条件，与今天 RocksDB 的 stop-for-compaction 同构。

**插入代价的推演**（论文 §2 模型，此处定性重述）：每条记录在 C0 里"免费"；落盘 1 次顺序写；此后每轮 C1 内归并被重写 1 次。⇒ **写放大的根源不是"写"，而是"合并"**——把 merge 频率降下来吞吐就上去，代价是 run 变多、读变慢。三角权衡在结构上是自相似的。

### 2.2 查询语义与弱点（§2.3/§3）

```
point-GET(k) 期望盘 I/O ≈ 1(最新run页) + (N-1)×每run一次探测   ← 线性于 run 数
```
- **点查**：从新到旧依次探测 C0 与各 run，命中即停。代价随 run 数线性增长；论文给的缓解手段是"新 run 有索引 + 时间局部性使探测多在头部结束"，后来 LevelDB/RocksDB 用 **Bloom filter** 把这个"探测"从磁盘 I/O 降到内存位判定（论文未提，属后人补票，标注时间差）。
- **范围查询：本文结构性的弱点，论文自己承认**。区间 [a,b] 必须对**每个 run 分别取出区间切片再做归并**：热区间（最近 t 秒写入）走 C0 很快；**冷区间要触碰全部 N 个 run**，顺序 I/O 次数 ≈ Σ每个 run 的区间页数——大表全范围扫描时甚至劣于 B-tree 的单遍叶链。论文的立场是 OLTP 式"小范围+时间局部性"查询为主，此弱点可忍；**后来一切 LSM 引擎的读优化（Bloom、迭代器缓存、L0 限文件数、level 化分层）都是在这个弱点上补课**——RocksDB 把"range scan 差"当真痛点的工程演化见 [`../rocksdb_2013_ieee_deb/00-精读笔记.md`](../rocksdb_2013_ieee_deb/00-精读笔记.md)。

### 2.3 伪码：读写与合并的完整生命周期（机制按论文模型重述，非原文伪码）

```text
INSERT/DELETE(k, v):                       # 写路径：永不触碰盘上旧值
    WAL.append(k, v | DEL)                 # 可选日志（论文设想可放磁带）
    C0.insert_sorted(k, v | DEL)           # 内存有序表；键重复则新压旧
    if sizeof(C0) >= M:                    # 每 t 秒触发一次
        schedule_merge();                  # 合并必须耗时 < t，否则写请求排队(stall)

flush_and_merge():                         # 后台
    run_new = ordered_dump(C0)             # 顺序写：一个差量 run（含墓碑）
    C0 = empty
    C1 = merge_all(C1 + [run_new])         # 对全部 run 做 k 路归并：
                                           #   同键取最新；DEL 屏蔽旧值，
                                           #   且（视预算）物理丢弃"DEL+其屏蔽的旧值"

GET(k):                                    # 点查：从新到旧，命中即停
    if k in C0: return answer(C0[k])        # 最近 t 秒的数据零盘 I/O
    for run in C1 from newest to oldest:   # 最新 run 走其 B-tree 页索引
        if k in run: return answer(run[k]) #   其余 run 各 ~1 次探测 I/O
    return NOT_FOUND

RANGE_SCAN(a, b):                          # 范围查：无法"命中即停"——弱点所在
    iters = [scan(C0, a..b)] + [scan(run, a..b) for run in C1]  # 每源一个有序切片
    return k_way_merge(iters, dedup_by_key_newest_wins, skip_deleted)
```

三行读后自检：为什么 GET 循环可以 break 而 RANGE_SCAN 不能？为什么 DELETE 不直接去 run 里删？为什么 flush 排在 merge 前面还是后面是免费的、而 merge 的**频率**是要花钱的？——三个答案分别对应读裁决规则、非原地更新的本质、写放大=合并频率函数。

### 2.4 多级推广：LSM-tree 的"tree"字（§4，定性）

单层 C1 的问题：全表数据量有限制、合并成本随 run 总量线性涨。论文把结构**纵向推广为 C0→C1→C2→…→Cn**：第 i 级容量按几何级数增长，只有当下一级"装不下一轮合并结果"时才整级下沉，**每级内部的 run 互不重叠**（与 C1 内 run 键域重叠形成对照）。这直接预示了 LevelDB/RocksDB 的 L0（重叠）+ L1..Ln（分层不重叠、size ratio ~10）形态：

```
C0 ──flush──► C1: run1..runN（键域重叠, 按时间）
                 │ 合并/下沉（几何增长因子）
                 ▼
               C2: 少量大run（键域不重叠）──► ... ──► Cn（最大最冷）
   ⇒ 每条记录被重写的总次数 ≈ O(层数)，换取各级查询只需"至多1次触碰"
```

### 2.5 故障恢复与"廉价磁带"愿景（§2/§5，定性）

- 主存故障：C0 丢失 = 最多丢 t 秒数据；配合日志重放可精确恢复（论文语带"日志本身也放磁带"的归档设想）。
- 磁盘故障：从备份 + 日志重建。
- 论文的长期卖点：**冷层可以搬到低价介质（磁带）**——"the fallacy of shrinking storage costs"一文是同一论调的续篇，此处不展开。

### 2.6 论文的实验方法（§3–§5，定性转述）

论文没有跑今天意义上的 benchmark：用**参数化代价模型 + 模拟/分析**，在"插入率 vs 内存大小 vs 查询响应"三轴上对比 B-tree 与 LSM-tree（含单层/多级变体）。可复述的定性结论（数值未逐字复核，见核实记录）：
- 同等内存预算下，LSM-tree 的**写吞吐高出 B-tree 一个量级**方向的优势，且对内存规模远不敏感（B-tree 吞吐随 buffer 缩小急剧恶化）；
- 代价模型里**查询/范围查询响应 LSM 劣于 B-tree**，与 §2.2 的结构分析一致；
- 多级方案的合并总量受"几何增长因子"控制——这即是 size-tiered 与 leveled 两种 compaction 策略的共同祖先。

## 三、实验与工程取舍（取舍表）

论文机制 → 现代放大指标的映射（本仓库叙事用法，1996 原文未用这些名词）：

| 设计决策（1996） | 收益侧 | 代价侧（现代术语） | 后续工程回应 |
|---|---|---|---|
| 写先进内存 C0，满才落盘 | 写放大极低：**写放大≈O(层数)**，顺序 I/O | 读放大：点查最多探 N 个 run + C0 | LevelDB/RocksDB：L0 文件数阈值 + Bloom |
| 差量 run + 墓碑，不做原地更新 | 追加写；崩溃语义简单（不撕裂） | 空间放大：旧值/墓碑驻留直到被合并消掉 | Paimon deletion vector、Delta DV（湖侧同题） |
| 定期全量 k 路合并 | run 数受控、空间回收 | 合并=后台重写风暴，瞬时抢 I/O | RocksDB rate limiter / 并行 compaction |
| 合并周期 < t 的硬约束 | 保证不积压 | 违反即**写停顿**（论文原版 stall） | universal→level 策略之争（见 RocksDB 笔记） |
| 多级几何下沉 | 冷数据 I/O 与容量都受控 | 冷范围查询跨层归并 | 分层存储/介质下沉（磁带→HDD→SSD） |
| 新 run 带 B-tree 索引 | 时间局部性点查快 | 每 run 维护索引的空间 | 统一 SSTable 索引块 + 两级 index |

与 B-tree 的"三角"总账（现代 RUM 视角，1996 文的三重指标为原型）：**B-tree = 读优/空间优/写劣；LSM = 写优/实时优/读劣（尤其范围）**。1996 论文的赌注是：写密集 + 时间局部性访问是多数 OLTP 的真实形态，读劣可以用索引/缓存工程补，而寻道之痛无法工程补。这个赌在闪存时代被放大成立（寻道消亡但**随机写页重写依然贵**），见 RocksDB 笔记。

一次写入 / 一次点查 / 一次冷范围扫描的盘 I/O 对照（模型级，n=run 数，h=B-tree 树高，q=区间页数，定性）：

| 操作 | B-tree（原地更新） | LSM（单层 C0+C1） | LSM（多级） |
|---|---|---|---|
| 写 1 条记录 | 叶页重写 + 沿途分裂/日志 ⇒ 多次随机写 | 内存 O(1) + 分摊 1 次顺序写 + 后续被合并重写 | 同上，重写上界 ≈ O(层数) |
| 点查（键存在，新写入） | h 次随机读 | 1（C0）～1+n 次读 | 1 + O(层数) 次读 |
| 点查（键不存在） | h 次随机读 | **n+1 次全探测**（最坏形态） | O(层数) 次（每层至多 1） |
| 冷范围扫描 [a,b] | 顺叶链 q 页（近顺序） | **跨 n 个 run 各取切片再归并** | 逐层归并，热层少触碰 |

表的第一列到第三列的移动方向，就是论文全部修辞的方向：用"点查/范围多几次有界探测"换"写入从随机页重写变成顺序追加"；而第二列到第三列的移动（多级化）则把"探测次数 ∝ run 数"收敛成"∝ 层数"——LevelDB/RocksDB 的 L0/L1+ 设计（见互链）正是第三列的工程化。

## 四、相关工作对比（仓库内互链）

- **← LFS（Rosenblum & Ousterhout 1991）**：LSM 的直接思想来源（追加日志 + 后台段清理）；LFS 面向文件系统"整段回写"，LSM 面向键值表"差量归并 + 多源读合并"，核心差异是 LSM 引入了**读时跨 run 归并语义**。本仓库暂无 LFS 笔记。
- **→ LevelDB（2011）/RocksDB**：本文骨架的工业直系。C0→memtable+immutable memtable；run→SSTable；C1→L0（重叠）+L1..Ln（不重叠）；新 run 的 B-tree→SSTable 数据块索引。**互链**：[`../../book/精通LevelDB.md`](../../book/精通LevelDB.md)（源码级中文讲义，SSTable/LSM 章节即本文机制的 2011 实现）、[`../rocksdb_2013_ieee_deb/00-精读笔记.md`](../rocksdb_2013_ieee_deb/00-精读笔记.md)（同一骨架上十七年的参数空间演化）。
- **→ 湖仓侧 LSM（任务要求的互链）**：[`../../book/Apache_Paimon_Streaming_Lakehouse/02-核心数据结构LSM树与主键表.md`](../../book/Apache_Paimon_Streaming_Lakehouse/02-核心数据结构LSM树与主键表.md)——Paimon 主键表把 C0 换成 Flink 状态里 changelog 缓冲、run 换成 L0 小文件、merge 换成 sorted-run compaction，是本文思想在对象存储上的投影；其 [`09-Compaction与删除向量.md`](../../book/Apache_Paimon_Streaming_Lakehouse/09-Compaction与删除向量.md) 处理的正是本文 §2.1 预告的"合并追不上产生"问题。与 [`../doi_10.14778_3415478.3415560/00-精读笔记.md`](../doi_10.14778_3415478.3415560/00-精读笔记.md)（Delta）对照：Delta 用"日志+重放"做版本，LSM 用"差量+归并"做版本——同一时代硬件的两种答案。
- **排序原语同源**：[`../doi_10.1145_191839.191884/00-精读笔记.md`](../doi_10.1145_191839.191884/00-精读笔记.md)（AlphaSort）——LSM 的 merge 本质就是外排序的 k 路归并阶段；AlphaSort 把归并搬上 RISC 流水，LSM 把归并做成常驻后台服务。
- **日志式 KV 的另一支**：[`../doi_10.1145_1294261.1294281/00-精读笔记.md`](../doi_10.1145_1294261.1294281/00-精读笔记.md)（Dynamo）——其持久化组件同样是"内存+哈希 log+定期合并"，但按哈希键组织，点查免归并、**范围查询被彻底放弃**（一致性哈希语义）；LSM 保有序故保范围查询。
- **采用 LSM 的旗舰系统**：本仓库已有 [`../spanner_2012_osdi/00-精读笔记.md`](../spanner_2012_osdi/00-精读笔记.md)（Pillar 数据层按列族分层组织，通说其存储树属 LSM 谱系，引用时以该笔记表述为准）。Bigtable（2006 OSDI）笔记已补录：[`../bigtable_2006_osdi/00-精读笔记.md`](../bigtable_2006_osdi/00-精读笔记.md)——LSM 落地为分布式存储的里程碑，回链本文。

## 六、批判与延伸

### 6.1 批判

1. **读劣被系统性地低估了**：论文对"时间局部性"的信仰在 OLTP 成立，但 1996 的分析几乎没给范围/分析型查询留出路（Bloom filter 还要等 14 年、leveled compaction 也要等）；今天回头看，LSM 真正的工程成本全花在"还读债"上——L0 阈值、索引块缓存、迭代器预取都是利息。
2. **空间放大只被当"待清理的垃圾"，没被当一等指标**：墓碑驻留、旧版本重复、合并临时空间（论文提到 merge 需临时缓冲）都影响容量规划，1996 文语焉不详；"空间放大"作为三角之一其实是 S3/RocksDB 时代补的课。引用"LSM 三角权衡（1996）"时把现代定义安到论文头上属时代错置。
3. **模型实验的外部效度**：参数化模型建立在"寻道 10ms、内存几十 MB"的介质假设上，闪存/SMR/ZNS/内存级 SSD（Optane 兴亡）之后常数全部重排——**结论定性存活（顺序写优于随机页重写），定量数字全部作废**，这恰是它 2013 年被重写一次（RocksDB）的原因。
4. **"无原地更新"的副作用论文没算**：非原地 ⇒ 读旧版本要跨 run 找最新 ⇒ MVCC/快照语义天然免费（这是送给 LevelDB/Bigtable 的厚礼，但对纯实时系统是可读状态分裂）；论文视角两者都没展开。
5. 4 作者署名常被引成 "O'Neil & O'Neil"，Cheng/Gawlick 的贡献（尤其 Gawlick 后来的 Oracle 关系存储工作）在引文里消失——文献计量学意义上这是篇"被简化的论文"。

### 6.2 延伸

- 同一骨架的参数空间如何被十七年穷举：universal vs level、大小比例、L0 停写阈值、KV 分离（BlobDB）、覆盖写——见 [`../rocksdb_2013_ieee_deb/00-精读笔记.md`](../rocksdb_2013_ieee_deb/00-精读笔记.md)。
- LSM 上湖（对象存储）后的新问题：小文件放大与 compaction 异步化，见 Paimon 笔记 [`02`](../../book/Apache_Paimon_Streaming_Lakehouse/02-核心数据结构LSM树与主键表.md)/[`09`](../../book/Apache_Paimon_Streaming_Lakehouse/09-Compaction与删除向量.md) 两章；Delta 的 VACUUM/Legacy compaction 是同题异解。
- 谱系研究线（本仓库未收录，供按图索骥）：bLSM（O'Neil 组 2012，DOI 已查证存在于 Crossref `10.1145/2213836.2213862`）、Monkey（2014）、Wacky（SIGMOD'20）、RUM Conjecture（2019）、LTSM/S3（2007）。
- 介质更新后"写便宜了，LSM 是否还需要？"：答案被 RocksDB/ Cassandra/ CockroachDB/ MyRocks/ TiKV 持续投票为"仍需"——随机页重写（含 GC/擦除）在 SSD 上照样构成放大，顺序化的理由只是换了物理机制。

### 6.3 思考题（5 道）

1. 论文约束"merge 耗时 < t"。设 C1 有 N 个 run、总量 S、合并带宽 B：写出 stall 临界条件，并推导"把 C1 拆成两级（各 ~√N 个 run）"如何改变该临界——这正是 §4 多级化对单层化的本质优势。
2. 点查代价 ≈ 1 + 探测新 run 数。Bloom filter 把它变成纯内存判定但有假阳率 f；若 L0 有 4 个文件、f=1%，推演一次 miss 查询的期望盘 I/O，并回答：为什么 RocksDB 默认对 L0 文件逐个建 filter 而 L1+ 按块共享？（对照 LevelDB 笔记。）
3. 范围查询"冷区间触碰全部 run"。若业务 95% 查询是"最近 24 小时"，t 取多大能让 95% 范围查询只碰 C0+C1 头部？这相当于什么内存预算？——用本文模型重做一次论文没做的容量规划练习。
4. 墓碑在"删除后立刻做范围读"时会拖慢读（跨 run 扫 tombstone 再屏蔽）。设计一种把删除也变成"覆盖写"的替代（现代 covering tombstone），并论证它把哪部分成本转嫁给了空间放大。
5. LSM 的差量-归并视角下，Delta Lake 的"日志+checkpoint"（[`../doi_10.14778_3415478.3415560/00-精读笔记.md`](../doi_10.14778_3415478.3415560/00-精读笔记.md)）与本文的 run-merge 同构吗？给出"同构"与"不同构"各一条硬理由（提示：按键有序 vs 按事件时序）。

## 八、阅读方法与常见误读提醒

1. **别把现代三放大名词按回 1996**：论文的三重指标是吞吐/查询响应/实时响应，"空间放大"是后补视角；写放大/读放大/空间放大三角的严格出处是 RocksDB-S3 一系与 RUM（见 6.2）。
2. **C1 的 run 键域重叠、C2+ 不重叠**——这是理解 LevelDB 为什么 L0 特殊对待（每文件全量 Bloom、文件数阈值严格）的钥匙；拿"所有层都不重叠"的直觉读本文会错位。
3. **论文是"结构+模型"论文，不是系统论文**：没有实现、没有 benchmark 曲线复刻价值；引用它的正确方式是引用机制与三重指标框架，而非任何定量数字。
4. **"LSM 适合所有负载"是最大误读**：论文自己划了界——读密集/大范围扫描/小内存高并发查询场景它明确劣于 B-tree；TiKV/Cockroach 时代"LSM+MVCC"的成功在于负载恰好是它的甜点区（写多、时间局部读）。
5. **配套阅读顺序**：本文（骨架与问题）→ LevelDB 笔记 [`../../book/精通LevelDB.md`](../../book/精通LevelDB.md)（第一副工业躯体）→ [`../rocksdb_2013_ieee_deb/00-精读笔记.md`](../rocksdb_2013_ieee_deb/00-精读笔记.md)（参数空间演化）→ Paimon 02/09 章（上湖后的新形态）。

## 九、一页总结（复习卡）

- **问题**：寻道时间支配的磁盘上，B-tree 原地更新把每次写变成多次随机 I/O；纯日志写快但读要扫历史。
- **方案**：内存有序缓冲 C0（实时性+合并预算的来源）+ 磁盘差量 run 序列 C1（追加式落盘）+ 后台 k 路归并（外排序复用）+ 多级几何下沉（把每条记录的重写次数控制在 O(层数)）。
- **所得**：写吞吐数量级优势、对内存规模不敏感、最近 t 秒数据零盘 I/O、非原地更新送来的免费版本语义（MVCC 的胚胎）。
- **所欠**：点查随 run 数线性变差（靠索引/Bloom 补）、冷范围查询必须跨全部 run 归并（论文自认、结构性的）、空间放大与合并临时空间、stall 风险内建于"合并必须追上产生"。
- **位置**：LFS 的追加思想 × 外排序的归并原语 × B-tree 的索引补丁 ⇒ 生成式结构；十四年后 LevelDB 借它复活，闪存时代 RocksDB 把它的参数空间铺满，湖仓时代 Paimon/Delta 把同一张力搬上对象存储。
