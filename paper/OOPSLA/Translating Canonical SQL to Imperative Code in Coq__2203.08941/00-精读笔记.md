## 一句话总结
SQL 用得最广、实现最多，但在**相关子查询（correlated queries）**和 **NULL 值语义**这些关键点上，各家实现要么行为不一致、要么干脆有 bug。本文借助 SQL 形式化与查询编译器近年来的进展，做出了 **DBCert**——**第一个把规范形式（canonical form）SQL 查询翻译为命令式代码的机械验证编译器**：先把 SQL 完整翻译到**嵌套关系代数（Nested Relational Algebra）**（可用于查询优化），再定义一个足够表达 SQL 的小命令式语言 **Imp**（可编译到 JavaScript 等执行语言），最后以**嵌套关系演算**为中间步骤，机械化地验证从嵌套关系代数到 Imp 的翻译。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：查询编译器把 SQL 变成可执行的计划/代码。编译器本身也可能错，而数据库里的错误会直接导致错误结果、错误报表。能不能像验证操作系统内核那样，**用证明助手机器验证查询编译器是正确的**？
- **为什么难**：SQL 语义非常微妙——**NULL 的三值逻辑**、**相关子查询**（内层引用外层变量）、集合与包（bag）语义、分组与聚合的边界情况；任何一块形式化不干净，证明就无法闭合。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 测试 / 差分测试 | SQLancer、各类 fuzzing | 随机生成查询对比多个引擎 | 能找 bug，但不保证没有 bug |
| SQL 语义形式化 | 近年 SQL 形式化工作 | 用逻辑/代数精确定义 SQL 语义 | 提供可靠地基，但只到语义层 |
| 已验证的查询优化器 | 部分研究原型 | 验证优化规则重写的等价性 | 覆盖优化阶段，未必到代码生成 |
| 端到端已验证编译器（本文） | DBCert | SQL → 代数 → 演算 → 命令式代码，全链路机械验证 | 保证最强，但工程与证明成本极高 |

- **本文属于哪一类**：**端到端机械验证的 SQL 编译器**。
- **必懂关键名词**：
  - **canonical form（规范形式）**：把 SQL 的多种写法归一化到一个定义良好的核心形式，便于形式化与编译。
  - **Nested Relational Algebra（嵌套关系代数）**：允许关系值作为属性值（嵌套）的关系代数，比平关系代数更能直接表达 SQL 的分组/嵌套结构。
  - **Nested Relational Calculus（嵌套关系演算）**：上述代数的演算（声明式）对应物，本文用它作为代数→命令式代码之间的中间层。
  - **Imp**：本文定义的一个**小而足够表达 SQL** 的命令式语言，可面向多种执行语言（含 JavaScript）。
  - **mechanically verified / Coq**：在证明助手 Coq 中写出定义并用机器检查的证明，而非纸面证明。

## 1. 问题背景与动机
- 前人工作简述：SQL 是使用与实现最广的查询语言；近年出现了对 SQL 语义的形式化工作以及查询编译器方面的进展，为验证奠定了基础。
- 前人缺陷/未解决问题（逐条）：
  1. **关键特性不一致**：在**相关子查询**与 **NULL 值语义**等关键特性上，众多实现存在分歧。
  2. **实现含 bug**：分歧之外还有实打实的正确性错误。
  3. **缺少已验证的翻译**：没有把 SQL 翻译到命令式代码的**机械验证**编译器（验证通常只覆盖优化或语义子集）。
  4. **缺少可用的中间层**：SQL 到可执行代码之间需要一个既能做优化、又便于证明的中间表示。

## 2. 核心方法
- **最直观类比**：把 SQL 翻译成机器能跑的代码，就像把中文说明书翻成英文说明书再翻成流水线工序；每翻一步都可能译错。DBCert 的做法是：**每一版译文都附带一份机器可检查的「与原文等价」证明**。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：写成**规范形式（canonical form）**的 SQL 查询。
  2. **SQL → 嵌套关系代数**：规约并机械化验证一个**完整**的翻译；该代数可直接用于**查询优化**。
  3. **定义 Imp**：一个小而充分的**命令式语言**，足以表达 SQL，并能面向多种执行语言（包括 JavaScript）作为目标。
  4. **嵌套关系代数 → Imp**：以**嵌套关系演算**为中间步骤，机械化验证这一翻译。
  5. **输出**：可执行的命令式代码，且翻译过程带机器检查的正确性证明。
- **形式化要点**：三段式链条 **SQL → Nested Relational Algebra → (Nested Relational Calculus) → Imp**；难点在于 NULL 语义与相关子查询的建模。摘要未给证明规模（行数）等数据 🔧。
- **理论性质/保证**：**有**——这是本文核心卖点：整条翻译在 Coq 中被机械验证（正确性保证，而非测试覆盖率）。

## 7. 2026 视角（🔧）
- 「已验证的数据库组件」仍是一条稳定但小众的研究线：查询优化器的重写规则验证、已验证的存储引擎/事务协议、以及 SQL 语义的形式化持续有工作出现。
- 工业界的现实做法仍以**大规模差分测试与模糊测试**为主（成本低、收益快），形式化验证多用于窄而关键的组件。DBCert 的价值在于证明了「SQL 到代码」全链路可被机器验证这条路线可行。
- 近年趋势：把证明助手与可执行代码提取（extraction）结合、把形式化 SQL 语义用于测试预言（oracle）生成、以及与编译到 WASM/GPU 等新目标结合。
- 本节为趋势性判断；具体进展 🔧 查当年文献。

## 8. 新手学习路线
- **10 分钟**：读摘要 + 第 0、2 节，记住链条：**SQL → 嵌套关系代数 → 嵌套关系演算 → Imp**。
- **30 分钟**：自己找一个「相关子查询 + NULL」的例子，在任意两个数据库（如 PostgreSQL 与 SQLite）上跑，看结果是否一致——这就是本文的动机来源。
- **进阶**：读论文中 SQL → 嵌套关系代数的翻译规则与 NULL 的建模方式；在 Coq 中复现一个极小的翻译定理；思考「为什么要用嵌套演算做中间层」而不是直接从代数到 Imp。
