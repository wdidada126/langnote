## 一句话总结

企业里往往有成百上千个数据库，用户问"上季度华东区销售额"时，系统连**该查哪个库、哪张表**都不知道。DBCopilot 把这个问题拆成两步：先用一个轻量"导航器"（schema 路由）把问题送到正确的库和表，再交给 LLM 生成 SQL。

## 0. 给新手的阅读前置（背景知识地图）

**子方向解决什么大问题**：传统 Text-to-SQL 研究（Spider 等）默认"只有一个数据库、schema 已给定"。现实企业有成百上千个库，问题来了：先把哪个库、哪些表喂给 LLM？全塞进去上下文根本放不下。

**为什么难**：
- schema 数量巨大且不断变化，检索空间远超一般 RAG；
- 不同数据库之间表名、列名大量重复（`id`、`name`、`date` 到处都是），必须结合**关系上下文**才能区分。

**几类主流解法**：

| 思路 | 直觉 | 缺点 |
|------|------|------|
| 全量塞上下文 | 把所有 schema 给 LLM | 超长上下文、贵、易幻觉 |
| 人工配置 | 为每个库手写路由规则 | 不可扩展 |
| 检索式路由（本文） | 学一个索引，把问题"导航"到目标库/表 | 需要训练信号，本文用自动生成解决 |

**本文属哪类**：检索式 schema 路由 + LLM 生成 SQL 的两段式框架。

**关键名词直觉**：
- **Schema Routing**：给定自然语言问题，先检索出"该查哪个数据库的哪些表"，相当于 Text-to-SQL 的"定位"环节。
- **Schema-agnostic（schema 无关）**：路由模型不针对单个数据库特化，一个模型服务海量库。
- **Schema-to-Question 生成**：反向构造训练数据——从 schema 出发自动生成"可能被问到的问题"，省去人工标注。

## 1. 问题背景与动机

- **前人工作**：LLM 时代的 NL2SQL（如各种 prompting/微调方案）在"单库、schema 已给定"的设定下表现不错；信息检索领域的稠密检索可以找文档，但直接照搬来找 schema 效果不佳。
- **前人缺陷/未解决问题**：
  1. 现有 NL2SQL 方法大多假设目标 schema 已知，无法直接用于"数据库多到不知道查哪个"的真实场景；
  2. 把海量 schema 全部塞进上下文不可行（长度、成本、准确性都崩）；
  3. 为成百上千个库逐个训练/配置路由器不可扩展；
  4. 跨库的表名/列名歧义严重，通用文本检索器难以区分。

## 2. 核心方法

**最直观类比**：像酒店前台。客人用大白话说需求，前台（路由器）不自己办业务，而是快速判断"这事该去几号柜台（哪个库哪张表）"，再把客人精确带到柜台（LLM 生成 SQL）。

**具体做法（输入→关键操作→输出）**：
- 输入：自然语言问题 + 海量数据库的 schema 集合；
- 关键操作：
  1. **解耦**：把 schema 无关的 NL2SQL 拆成 schema 路由 + SQL 生成两阶段；
  2. **可微搜索索引**：用单一轻量级可微索引为海量数据库 schema 建立语义映射；
  3. **关系感知联合检索**：检索时考虑表之间的关系上下文，把问题"导航"到目标数据库和表；
  4. **反向数据生成**：引入 schema-to-question 生成范式，从 schema 自动生成训练用问题，无需人工干预即可学习并适配路由器；
  5. 把路由出的 schema 交给 LLM 生成 SQL。
- 输出：目标 SQL 查询。

**形式化要点**：路由建模为可微检索问题（schema 表征 + 问题表征的匹配学习 🔧 细节查原论文）。

**理论性质/保证**：无理论保证，属系统+学习型工作。

## 3. 变体 / 工程版（如有）

- 反向 schema-to-question 生成可视为一种**数据增广变体**：新库接入时自动生成训练信号，无需人工标注，是框架可扩展性的关键。

## 4. 实验结论（概览）

- **对比基线**：通用稠密检索器 + 各类 NL2SQL 方案（🔧 具体基线清单查原论文）。
- **数据集**：Text-to-SQL 标准数据集 + 大规模数据库场景设置（🔧 具体数据集与库数量查原论文）。
- **指标**：schema 路由命中率与下游 SQL 生成准确率（🔧 精确数字查原论文后补）。
- **结论方向**：单一轻量路由器即可在海量数据库上准确导航，并显著提升端到端 NL2SQL 效果；自动生成的反向数据足以替代人工标注训练路由器。

## 7. 2026 视角（🔧）

- 企业级 Text-to-SQL 落地中，"schema 选择/路由"已被公认为比 SQL 生成本身更关键的瓶颈之一；多库、多租户场景下检索式路由成为标配组件。
- 近年趋势：与 RAG 基础设施融合（把 schema 当作可检索资产）、Agent 式"先探库再查数"工作流、以及大上下文模型带来的"暴力塞 schema"回潮——两种路线仍在拉锯。
- 本文的"反向生成训练数据"思路在 2025-2026 年被广泛借鉴为合成数据范式（🔧 该论断为方向性判断，具体引用情况待核实）。
