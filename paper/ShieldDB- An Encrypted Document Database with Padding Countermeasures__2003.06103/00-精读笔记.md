## 一句话总结
数据泄露频发，ShieldDB 用「可搜索加密（searchable encryption）」在加密文档上保留搜索能力且不怎么牺牲可扩展性。但纯理论原语怕真实威胁——懂行的攻击者能用访问模式（access pattern）泄露反推明文。ShieldDB 针对性地加「填充（padding）对策」，在「数据库持续更新、攻击者可任意时段监视」的更强威胁模型下，始终混淆访问模式，并额外提供前向隐私、重加密、flush 等能力；在 Azure Cloud 上做了完整实现与评估。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：数据库要在「全程加密」下仍能检索，且不让攻击者从「访问了哪些数据」推断明文。
- 为什么难：可搜索加密（SE）能搜加密数据，但会泄露访问模式；强攻击者借访问模式就能破 confidentiality。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 全磁盘加密 | 传统 | 整盘加密 | 检索需解密、泄露多 |
| 可搜索加密 SE | 早期 SE | 密文上搜 | 快但漏访问模式 |
| 填充对策（本文） | ShieldDB | 混淆访问模式 | 抗强威胁、保可用 |

- 本文属哪类：加密数据库 / 可搜索加密 + 抗访问模式泄露路线。
- 关键名词直觉：
  - searchable encryption（可搜索加密）：在密文上直接做关键字搜索的密码学原语。
  - access pattern leakage（访问模式泄露）：攻击者能看到「查了哪些文档/块」，从而推断内容。
  - padding（填充）：通过补齐数据长度/结构来混淆真实访问模式。
  - forward privacy（前向隐私）：新插入的数据不会泄露给已持令牌的攻击者。

## 1. 问题背景与动机
- 前人工作简述：可搜索加密能在不解密情况下保留搜索功能，且对可扩展性影响小。
- 前人缺陷/未解决问题（逐条）：
  1. 真实威胁未处理：理论原语在真实世界会被「利用访问模式泄露」的攻击者攻破。
  2. 威胁模型太弱：前人多假设静态/受限监测；未覆盖「库持续更新 + 攻击者可任意时段监视」。
  3. 缺高级特性：前向隐私、重加密、flush 等实用安全/效率特性少有集成。

## 2. 核心方法
- 最直观类比：像把文件锁进带玻璃窗的柜子——能隔着玻璃找（可搜索加密），但攻击者会数你开了哪几格（访问模式）。ShieldDB 给柜子加「假抽屉/统一外形」（padding），让外人看不出你真正开了哪格。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：加密文档 + 搜索令牌。
  2. 关键操作：
     - 在可搜索加密之上，设计填充对策（padding countermeasures）；
     - 针对「持续更新 + 任意时段监视」的更强威胁模型；
     - 保证对数据库的访问模式始终被混淆；
     - 额外提供前向隐私、重加密（re-encryption）、flush 等能力。
  3. 输出：在强威胁下仍保密的加密文档数据库。
- 形式化要点：核心是「padding 对策 + 强威胁模型 + 高级安全特性」；具体填充算法与威胁模型定义 🔧 查原论文。
- 理论性质/保证：提供针对访问模式泄露的混淆保证与前向隐私等（密码学保证，细节以原论文为准 🔧）。
