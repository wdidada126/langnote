## 一句话总结
湖仓（lakehouse）规模大、异构强，却缺少关系引擎那样的声明式语言和优化能力。RumbleML 把声明式语言 JSONiq 带入湖仓：用同一种语言统一做数据清洗、准备、训练、推理和模型/结果管理，且相比 Spark 不损失性能——让「数据整理」和「机器学习」落在同一套系统、同一种语言里。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：湖仓（lakehouse）把数据湖（存原始多模态数据）和数据仓库（结构化分析）合二为一，规模巨大、数据异构（JSON、Parquet、CSV 混存）。但它往往不好用——缺一个像 SQL 那样「说清楚要什么、让系统优化怎么算」的声明式语言。
- 为什么难：湖仓数据半结构化/异构，SQL 不够灵活；Spark 等虽能算但偏命令式、ML 与数据整理要用不同工具，割裂。
- 几类主流解法（表格）：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| SQL 数仓 | 传统 DW | 声明式但只管结构化 | 灵活度不足 |
| 命令式大数据 | Spark | 通用计算 | ML 与整理割裂、非纯声明 |
| 声明式湖仓语言 | 本文 RumbleML / JSONiq | 用 JSONiq 统一数据与 ML | 统一但生态较新 |
| 湖仓平台 | Delta/Lakehouse 论文 | 存储层统一 | 语言层仍分散 |

- 本文属于哪一类：湖仓的声明式编程层——用 JSONiq 把数据工程与 ML 工程统一。
- 2-3 个必懂关键名词：
  - Lakehouse（湖仓）：兼具数据湖的灵活存储与数据仓库的分析能力的架构。
  - JSONiq：一种类 XQuery 的声明式语言，原生处理 JSON/半结构化数据。
  - 声明式（declarative）：只描述「要什么」，不写「怎么算」，由引擎优化执行（对比命令式）。

## 1. 问题背景与动机
- 前人工作简述：Lakehouse 近年规模与异构度空前，被众多工业玩家采用；但使用门槛高，缺乏声明式语言与关系引擎般的优化能力。
- 前人的缺陷/未解决问题（逐条）：
  1. 难用：湖仓缺乏声明式语言和优化的可能性。
  2. 数据与 ML 割裂：数据清洗/准备用一套工具，训练/推理又一套，跨系统切换成本高。
  3. 异构处理弱：半结构化/多模态数据没有统一的声明式表达。

## 2. 核心方法
- 最直观类比：传统湖仓像「仓库里堆满各种形状货物，却只有扳手（命令式 API）没有清单系统（声明式语言）」；RumbleML 引入一份「通用清单语言 JSONiq」——你只写「我要什么样的干净数据和模型」，它就能在湖仓里统一调度清洗、训练、推理，不必在多个工具间搬货。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：湖仓中的异构数据（JSON/Parquet/CSV 等）+ 用 JSONiq 写的任务描述。
  2. 关键操作：RumbleML 作为集成进 RumbleDB 引擎、基于 JSONiq 的高级声明式库，用同一语言完成：数据清洗、数据准备、训练、推理、模型与结果管理。其核心设计洞见是：
     - 训练/评估/测试集可表示为「同质扁平对象的序列」；
     - 模型可封装为「把测试集映射为带预测结果集」的函数项；
     - 估计器可封装为「把训练集映射为模型」的函数项。
  3. 输出：在同一系统、同一种语言内完成的数据整理 + ML 流水线结果。
- 形式化要点：以 JSONiq 的函数项（function items）把模型/估计器当作一等公民；🔧 具体语法与执行计划查原文。
- 理论性质/保证：论文强调「功能/生产力大幅提升且不损失性能」；以与 Spark 的对比验证（🔧 理论分析查原文）。
