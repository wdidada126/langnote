## 一、背景与它回应的问题

### 1.1 写优化与读优化的世界观

论文开篇即立场鲜明：**主流 DBMS 都是"写优化"的行存**——一次记录的所有字段连续放置，一次磁盘写即可落全部字段（原文 §1）。这对 OLTP 极好，对"大扫描、少投影列、聚合为主"的仓库负载极差：查询要的列被无关属性稀释，磁盘带宽被浪费。列存（Sybase IQ、Addamark、KDB）早已在商用利基市场证明了自己，但它们的共同软肋是**几乎不支持在线更新**（KDB/Addamark 按插入序存列，更新代价高）。

两条更深的时代曲线（原文以 CPU/磁盘比价论证）：CPU 速度增速远高于磁盘带宽增速，于是"**用富余的 CPU 换稀缺的磁盘带宽**"——编码、压缩、在压缩态上直接执行——成为读优化系统的第一性原理；而"刀片/grid"廉价机群（原文引 DeWitt & Gray 1992）要求任何新引擎从第一天起就按 shared-nothing、G 节点、水平分区来设计。

### 1.2 "one-size-fits-all 之死"的前奏

论文 §10 相关工作中引用的 [FREN95]（Clark D. French, *One Size Fits All Database Architectures Do Not Work for DSS*, SIGMOD 1995）就是这句后来被反复引用的口号的原始出处——注意：**口号属于 French 1995，C-Store 论文将其作为动机引用并身体力行地"再犯"了一次**：它并不宣称列存取代行存，而是宣称**一个系统内部要同时装下两种存储**（WS 写优化 + RS 读优化），用 tuple mover 缝合。这是"按负载拆引擎"思想的关键一步：向上承接 Stonebraker 自己的版本化/写优化谱系（Lagunita 1990、Coda；文字提及），向下直接开启 H-Store（OLTP 侧重启）与 Vertica（C-Store 商用化，dbdb.io 明确记载）的双线，以及仓库里已精读的 Dynamo/HBase/Cassandra 式"按负载选存储结构"的世界（见 §四）。

### 1.3 核心矛盾与论文答案

矛盾的精确表述（原文 §1）：**列按"查询友好的序"排 → 插入昂贵；列按"插入友好的序"存 → 查询次优。** C-Store 的答案：不做取舍，做**混合**——

```
        ┌──────────────────────┐
 SQL ──►│  查询处理器/执行器     │──►更新：拆成 insert(WS)+delete(标记)
        └───────┬──────────────┘
        读:同时扫两处│▲
        ┌────────▼────────────┐ │
        │ WS (Writeable Store)│◄┘ 内存优先、不压缩、全 B-tree、小
        └────────┬────────────┘
                 │ Tuple Mover：LSM 式 merge-out（MOP）批量下沉
        ┌────────▼─────────────────────────────┐
        │ RS (Read-optimized Store)：不可变列存 │ 压缩+排序+位图，大
        │  proj1│ proj2│ … │ projN + join index │
        └──────────────────────────────────────┘
```

写路径永远只碰小的 WS（吸收 LSM-tree [ONEI96] 思想，原文点名"we use a variant of the LSM-tree concept"），读路径主要扫巨大但只读的 RS；新鲜度用 epoch（LWM/HWM 双水位）来标价。这句话值得划重点：**C-Store 是"OLTP 用 LSM 写路径 + OLAP 用不可变排序列存"这一整个现代范式（Parquet 表、Delta Lake、Snowflake、Aurora）的共同祖先之一。**

## 二、核心设计精读（VLDB 2005 正文）

### 2.1 数据模型：投影、段、存储键、连接索引（§2–§3）

物理层**没有表、也没有"表+索引"**——C-Store 只实现**投影（projection）**，且这个词被有意偏离关系代数用法：投影 = 锚定某逻辑表 T、选出 T 的若干列，再沿 **n:1 外键链**"顺便"把外键另一端表的列拼接进来的冗余集合（原文明确"we do not store the base table"）。行数与锚表相同；示例（原文 Table 1/Example 1–2）：

```
EMP1(name, age | age)  EMP2(dept, age, DEPT.floor | DEPT.floor)  EMP3(name, salary | salary)
       └── 竖线后是排序键：同一份数据按不同键排序的多份"视图" ──┘
```

- **段（segment）**：投影按排序键做**值域水平分区**，每段一个 Sid；段是调度/复制/合并的原子。
- **存储键（storage key）**：同一（投影、段）内跨列对齐同一条"逻辑行"的编号。**RS 中 SK 不落地**——按记录在列中的物理序推断；**WS 中 SK 显式存储**，且从"RS 最大 SK+1"起分配，天然不冲突（节点把本地计数器与站点 id 拼接成全局唯一）。
- **连接索引（join index）**：跨投影重建整行的边表——`(sid, storage_key)` 对，把 T1 的每条记录指到 T2 中"同一逻辑行"的位置。任意一行的全部属性必须能沿 join index 路径走到某个统一序上，这是覆盖性约束；join index 与"发送方"段共存，指针混指 RS/WS 两界。
- 于是**物理设计问题**被重新定义（原文 §2 末）：在空间预算 B 内，给定训练负载（或查询日志），自动选择"投影集合 × 排序键 × join index × 段布点"，并保证 **K-safety**（挂 K 个节点仍可重建全部表）——作者明说在写自动设计工具（呼应 [PAPA04]）。

### 2.2 RS：四种编码与"在压缩态上执行"（§3.1）

RS 列按排序键有序、不可变（只由 tuple mover 整段重写），编码按 **{自身序/外部序} × {少重复值/多重复值}** 四分：

| 型 | 场景 | 表示 | 检索结构 |
|---|---|---|---|
| Type 1 | 自序、少值 | 三元组 (值, 起始位置, 重复次数)，即 RLE | 值上聚簇 **densepack B-tree**（无空洞，大块 64–128KB，高≤2） |
| Type 2 | 外序、少值 | 每值一条位图 (v, bitmap)，位图再 RLE | "偏移 B-tree"定位第 i 个值 |
| Type 3 | 自序、多值 | 块内存首值、块间存差分（delta），类 VSAM | 块级 densepack B-tree |
| Type 4 | 外序、多值 | 不压缩 | 仍可 densepack B-tree 索引 |

关键论断（原文 §8.2）：**"能在压缩表示上直接执行"是 C-Store 性能之钥**——例如对 Type 2 列做选择，只需读入命中值的位图分片，列本身不必按该值排序（这一思想的现代回声是 bitWeaving/压缩态谓词求值，原文自己把先迹归给 [GRAE91, WESM00]）。

### 2.3 WS：为可更新而生的"丑"结构（§4）

WS 与 RS 用**同一套投影/join index 模式**（为了只写一个优化器），但物理上完全相反：不压缩；每列是 `(v, sk)` 对全体，落在**常规 B-tree** 上（原型直接建在 BerkeleyDB 上，[SLEE04]）；排序键另建 `(s, sk)` B-tree。写放大因此可观——一次插入 = 每投影每列一次 B-tree 插入——这正是"WS 必须小、内存扛住热数据"的理由。**删除是纯标记**（见 2.4），更新 = 插入 + 删除，绝不原地改 RS。

### 2.4 epoch：事务、快照与"不锁的读"（§6，C-Store 最原创的一节）

C-Store 拒绝在只读大查询与写事务之间动态加锁（原文：必然读写冲突、阻塞与死锁），改用**粗粒度时间纪元 + 双水位**：

```
时间轴 ──►   e0        e1        e2        e3(当前)
             ├─────────┼─────────┼─────────┤
TA(时间戳权威)：广播 epoch-end → 收齐各站 epoch-complete → 广播 HWM=e
LWM：由 tuple mover 的合并进度决定，"LWM 追赶 HWM"，
     两者间距 = 可调的"历史可见窗口"（空间 vs 新鲜度）

只读事务：取有效时间 ET ≤ HWM，零锁零 2PC；可见性 = IV/DRV 逐记录判定
读写事务：严格两阶段锁 S2PL；日志只记 UNDO（NO-FORCE, STEAL），
          REDO 不做传统回放——恢复靠从其它投影"查询复制"（见 2.5）
提交协议：master 不发 PREPARE，收齐 worker 完成后直接广播 commit
          （代价：收到 commit 后、落盘前宕机的站点可能缺更新，
           靠冗余投影恢复补齐——原文 6.2.1 明示）
```

- **IV（插入向量）**：WS 每段每记录存"插入于哪个 epoch"；RS 不存（tuple mover 保证 RS 内无晚于 LWM 的插入）。
- **DRV（删除记录向量）**：每投影一列，0=未删，否则存删除发生的 epoch；稀疏 → 用 Type 2 位图压缩；存于 WS（要可更新）。
- epoch 号计划像 TCP 序号一样**回绕回收**，前提是数据保留期有限（原文举例"存两年"）。
- 原文对 epoch 粒度的自我批评很坦诚：不支持任意时刻时间旅行（"onerously expensive"），只能落在 epoch 栅格上；epoch"通常以秒计"。

### 2.5 Tuple Mover：LSM 的 merge-out 版（§7）

后台任务寻找"值得合并"的 (RS 段, WS 段) 对，执行 **MOP（merge-out process）**（流程与不变式为原文 §7 内容，下方伪码为示意重写、非原文措辞）：取 WS 段中插入时刻 ≤ LWM 的记录 → 已删且删除 ≤ LWM 的直接丢弃（"用户不可能查到它还存在的时刻"）→ 其余与新写的 RS' 做归并：逐块读旧 RS、按 DRV 剔除、与 WS 列值合并写出 RS'。RS' 记录获得**新存储键** → 顺带重建进出 join index、维护 DRV；全部完成后**原子切换** RS→RS'，旧空间释放。原文特意论证：old-master/new-master 整段重写优于原地更新，因为几乎所有对象本来就要移动。

```
MOP(WS_seg, RS_seg):                       # 不变式: RS 内所有记录插入时刻 ≤ tlastmove(RS)
  delta = {r ∈ WS_seg | r.insert_epoch ≤ LWM and (r.del_epoch == 0 or r.del_epoch > LWM)}
  RS' = ∅                                  # 丢弃 delete ≤ LWM 的行——它们已不可见
  for col in 排序归并(RS_seg.col, delta.col by sortkey):   # 逐列流式归并
      emit(col, new_sk = next(RS'.sk))     # 新 SK ⇒ 记 (old_sk, epoch) → new_sk 到 MOP 日志
  rebuild_join_indexes(delta, RS')         # 进出边全部重写
  atomic_cutover(RS_seg → RS');  free(old)
  tlastmove(RS') = max(r.insert_epoch for r ∈ delta)   # ≤ LWM, 恢复协议依赖此单调性
```

### 2.6 恢复 = 冗余即备份（§6.3）

三情形：(a) 站点宕机没丢数据——重启后把网络上为它排队的更新追完即可（读多环境里便宜）；(b) RS+WS 全毁——凭 K-safety 从其它投影/join index **用查询重建**，只需能从远端取回 IV/DRV 辅助列；(c) 仅 WS 毁——RS 只被 tuple mover 写、通常无恙，难点是识别"已下沉到远端 RS"的记录：解法是 tuple mover 为每条下沉记录留一份 **(旧SK, epoch)→(新SK, RS) 日志**，按最老 WS 记录截断。恢复查询的谓词形状（原文 §6.3.1 给出了完整 SQL）：`insertion_epoch > tlastmove(Sr) AND (deletion_epoch = 0 OR deletion_epoch >= LWM) AND sort_key IN K`。

### 2.7 执行器与优化器（§8）

十类算子（原文列举）：Decompress / **Select（输出位串而非子集！）** / Mask（按位串裁剪投影）/ Project / Sort / Aggregation / Concat（同序投影拼接）/ **Permute（按 join index 重排投影）** / Join / 位串三件套 BAnd-BOr-BNot；中间数据类型只有 Proj、Col、Bits 三种。迭代器沿用 Volcano [GRAE93]，**但每次 `get_next` 返回单列 64K 元素块**——保留数据流与控制流耦合，把流量粒度改成列式（向量化执行最早成文的设计之一；对照本仓库 [`../doi_10.14778_2002938.2002940/00-精读笔记.md`](../doi_10.14778_2002938.2002940/00-精读笔记.md) §6.1）。优化器：Selinger 式代价驱动 + 两阶段搜索，代价模型**必须感知输入输出的压缩类型**（Type 2 上的 Select 只读命中位图，但每个不同值要备一页内存缓冲），核心决策只有两个：选哪些投影、在哪一层放 Mask。

### 2.8 任务清单里的"六子系统"在哪里（考证后归位）

流传的六件套：**SQL 查询处理器（经 REST 接口访问存储）、WOS（写优化存储）、EFS（极简文件系统）、PROS（按排序键谓词路由）、Epochlizer（按 epoch 同步提交检查点）、Observatories（可插拔性能观测站）**，外加原型期论文里的 **Delta Index**（给 WS 未合并数据建的按记录位图式索引，补齐"新数据没有位图"的洞）。本节命名与展开均来自姊妹论文/项目文档（未逐字复核，见 §〇 第 4/5 条），与本文对照关系：WOS≈WS，PROS 的输入正是 2.1 的段值域+排序键，Epochlizer 即 §6 的 TA/epoch 协议，REST 是执行器与存储层之间的进程间接口（原型工程隔离用）。写论文与做系统是两种文体：**正文一篇讲思想，组件名散在工程文档里**——引用六件套时请给出处层级。

## 三、实验与工程取舍

### 3.1 论文自带的数字（已逐字复核官方 PDF pp. 562–563，非二手转述）

设置：单节点 3.0GHz Pentium、2GB 内存、750GB 盘；TPC-H scale 10 的 lineitem/orders/customer 子集（6000 万行 lineitem，原始 1.8GB），7 条查询（Q1–Q7，多为 count/max 型聚合与一次三表 join）；三系统同预算 2.7GB（行存装不进，单独给足它需要的 4.5GB），**两个商用对手被关闭锁与日志**。逐查询秒数（空间受限表：C-Store/行存/商用列存）：Q1 0.03/6.80/2.24、Q3 4.90/93.26/29.54、Q4 2.09/722.90/22.23、Q6 8.50/652.90/32.83、Q7 2.54/265.80/33.24……原文汇总：**平均快行存 164 倍、快商用列存 21 倍**；再放开空间、给对手喂与本实验投影等价的物化视图（行存膨胀到 11.9GB ≈ 6 倍空间），C-Store 仍**快行存 6.4 倍、快列存 16.5 倍**（后者占 1.83 倍空间）。静态占用：1.987 vs 4.480 vs 2.650 GB。作者自限（原文 §9/§1 结论段）：**WS 与 tuple mover 尚未集成进实验**，单站点、无段分区、无网格节点，"非常初步"。

### 3.2 取舍表

| 设计选择 | 买到了什么 | 付出了什么 |
|---|---|---|
| 冗余投影替代"表+索引" | 每查询走最优序；高可用顺带白送 | 空间×写放大；join index 昂贵（改一个投影要动所有进出边——原文自述） |
| 压缩到骨里再排序 | 冗余在预算内可行；压缩态执行省带宽 | 代价模型复杂化；解压点要精算 |
| epoch 粗粒度快照 | 只读查询零锁、K-safety 同步即复制 | 新鲜度=epoch 长度；时间旅行被栅格化；LWM 落后时历史窗吃 WS 空间 |
| 不记 REDO 日志、恢复靠查冗余投影 | 日志极薄（只 UNDO），恢复免回放 | 提交无 PREPARE：单站 commit 后宕机窗口靠副本兜底；跨数据中心时投影重建慢 |
| LSM 式批量下沉 | RS 永远不可变、可大压缩 | 新数据不在最优布局里，须靠 Delta Index（原型期）补洞 |
| 列存但迭代器仍 Volcano 式 | 复用优化器/调度骨架 | 每列一次跨算子往返；靠 64K 块摊薄 |

## 四、相关工作与谱系对照

- 论文 §10 亲列的对手与先迹：Monet（"设计上最接近，但存插入序、无混合架构、无重叠投影"）、Sybase IQ/Addamark/KDB（列存先驱、无本事务模型）、data mirrors [RAMA02]（双引擎合体但目标是加速仓库查询，非同时扛 OLTP）、倒排文件/Bubba、压缩综述 [ROTH93]。
- **与 LSM 谱系**（[`../../book/Database_Internals/07-日志结构存储.md`](../../book/Database_Internals/07-日志结构存储.md)、[`../../book/精通LevelDB.md`](../../book/精通LevelDB.md)）：C-Store 是"OLAP 版 LSM"——WS≈memtable+不可变 run，MOP≈major compaction，DRV≈删除标记，LWM/HWM≈checkpoint 水位；差异在于 C-Store 的"main tree"按查询序重排且多份冗余。
- **与 Dynamo/HBase/Cassandra 一系**（[`../doi_10.1145_1294261.1294281/00-精读笔记.md`](../doi_10.1145_1294261.1294281/00-精读笔记.md)）：恰好互为镜像——NoSQL 为写扩展性放弃 SQL/事务/二级索引，C-Store 为读优化把写路径压进一个小 WS；"按负载裁剪引擎"同一口号下的两个方向；K-safety（存冗余）vs Dynamo 复制（为可用）。
- **直接后代 Vertica**（dbdb.io 记载其商用化）：把 WS/RS/epoch 换成更工程化的"ROS 列段 + WOS + tuple mover + projections"，机制血脉照搬（通说，细节未逐字复核）。
- **湖仓时代的回响**：不可变列段 + 元数据 + 后台合并 = Parquet/Delta/Iceberg 世界（[`../doi_10.14778_3415478.3415560/00-精读笔记.md`](../doi_10.14778_3415478.3415560/00-精读笔记.md)、[`../lakehouse_2021_armbrust_databricks/00-精读笔记.md`](../lakehouse_2021_armbrust_databricks/00-精读笔记.md)）；Aurora/Snowflake/Socrates 的"日志即数据库/存算分离"（`../doi_10.1145_3035918.3056101/`、`../doi_10.1145_2882903.2903741/`、`../doi_10.1145_3299869.3314047/`）在"页/段不可变 + 后台下沉"轴上都是 C-Store-LSM 思想的云原生变体。
- 姊妹论文：ICDE 2007 *Materialization Strategies in a Column-Oriented DBMS*（Crossref 核实：`10.1109/icde.2007.367892`）研究投影物化时机，是"冗余投影"决策的后续论文。

## 六、批判与延伸

1. **这是一篇"设计论文"而非"系统论文"**：实验时 WS+tuple mover 未接入、无段/无多节点、对手关了锁与日志——作者自己都列在 §9。后世引用者常把这 164× 当成端到端正面对决，是对文本的超额使用。
2. **epoch 的隐契约**：新鲜度=epoch 秒级 + LWM 滞后的双重折扣。论文用"real-time warehouse 是需求"开头，却用粗纪元收尾——这个张力在 Vertica（微批+DELTASTAGE 类机制）与今天的"实时湖仓"里仍在被解。
3. **冗余投影写放大**是结构性成本：每个投影的每列、每条边上的 join index 都要动，作者自认 join index "expensive to maintain"，而论文没有给写基准。检验它的时刻推迟到了 H-Store 与列存混战年代。
4. **真正被历史验证的点**：(a) 不可变压缩列段 + 后台合并的读写分离（湖仓全族）；(b) 压缩态上执行；(c) 列粒度流量块（向量化前夜）；(d) 冗余排序视图当"索引即数据"用；(e) 物理设计自动化问题（投影×排序键×预算）的形式化。
5. **常见引用坑**：说"C-Store 发明了列存"错（IQ 1995）；说"C-Store 发明了 LSM"错（O'Neil 1996，本仓库 LSM 笔记）；C-Store 的贡献是**第一次把列存、LSM、快照隔离、冗余复制、列式执行缝进一个带统一 SQL 与自动物理设计的读优化引擎并公之于众**。

## 八、思考题（5 道）

1. 排序键同时扮演"压缩字典序、分区路由键、join index 锚点"三重角色。若某列基数极高（如时间戳）且几乎不进谓词，为它单独建投影值得吗？写出预算 B 下的成本收益框架，并指出 tuple mover 合并序与之的耦合。
2. HWM 与 LWM 之间的"历史窗"是 WS 空间的直接来源。推导：给定到达率 λ、查询历史深度 d、合并周期 τ，WS 稳态大小与 DRV 位图密度的表达式——并解释为什么"epoch 秒级"能成立而"毫秒级"会让 WS 爆炸。
3. 提交协议省略 PREPARE 后，单站点"承诺即宕机"的窗口为何可接受？把 K-safety 的重建查询（§2.6 的 SQL）改成可证明覆盖三种故障情形的恢复算子，需要什么不变式（提示：tlastmove 单调性与 IV/DRV 的存放位置）？
4. RS' 归并会给全部记录重发存储键。分析 join index 风暴：一次 MOP 涉及几条边？如果投影间存在星型多表锚定，能否用"跨投影共 SK"的不变式把维护成本从 O(边数) 降到 O(1)？C-Store 为什么没这么做？
5. 只读查询输出位串（Select→Bits，Mask 才裁剪）。这与 40 年后 SIMD 选择（AVX-512 mask 寄存器、filter/compact 指令）是同构的。设计一个把 Type 2 位图列直接别名到 SIMD 掩码寄存器的执行原语，并说明何时别名失效（列宽不是位宽的整倍数、跨块谓词等）。

## 九、常见误读提醒

1. 把"WOS/EFS/PROS/Epochlizer/观测站/Delta Index"当作本篇论文内容引用——六个名字本篇一个都没有（§〇 第 4 条），出处层级要写对；"椭圆过滤器"是彻底讹传。
2. 把 164× 读成"列存 164 倍秒杀行存"——那是空间受限、单节点、只读、对手无锁无日志的 7 条聚合查询均值；论文自己的 caveat 在同页。
3. 把"快照隔离"当 PostgreSQL 式 per-transaction SI——这里是 epoch 栅格上的"历史模式"，且**只对只读事务免锁**，读写侧是 S2PL。
4. 把投影当物化视图的自动维护问题——C-Store 干脆不存基表，投影是唯一的物理真相，重建整行靠 join index。
5. 把 tuple mover 当"垃圾回收"——它同时是排序重铸机（新 SK）、可见性推进器（LWM 追赶）与恢复日志的生成者（MOP 日志）。

## 十一、一页总结（复习卡）

- **问题**：行存写优化 vs 仓库读优化的世界观冲突；列按查询序排则写贵、按插入序存则读钝；廉价机群要求 shared-nothing + 自动物理设计。
- **方案**：混合架构——小的可写列存 WS（LSM 式、全 B-tree、不压缩）+ 巨大不可变读优化列存 RS（投影×排序键×四编码×位图），tuple mover 按 LWM 批量归并下沉；epoch + HWM/LWM + IV/DRV 让只读查询零锁快照、读写事务 S2PL + 仅 UNDO 日志；K-safety 冗余投影兼任高可用与恢复（恢复=查询复制）；十算子位串执行、每迭代 64K 列块、压缩感知两阶段优化器。
- **所得**：空间受限七查询均值快行存 164×/快商用列存 21×；冗余投影只用对手 40%~60% 空间；"读写分引擎+不可变列段"范式定型。
- **所欠**：WS/tuple mover 未进实验；单节点；新鲜度受 epoch/LWM 双折扣；join index 写放大无基准；六子系统名在别处（姊妹论文），"椭圆过滤器"为讹传。
- **位置**：上承 LSM(1996)/IQ(1995)/French 口号(1995)，下开 Vertica、湖仓不可变列段与"按负载裁剪引擎"的全时代；与 LeanStore（页式 OLTP 复活缓冲管理器）构成本仓库存储引擎精读的两翼。
