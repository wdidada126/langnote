## 一句话总结
通用大模型（GPT、Claude、LLaMA、Qwen 等）很强，但「吃表格」这件事一直没做好。TableGPT2 用 59.38 万张表、236 万个「查询-表格-输出」三元组做预训练与微调，并专门设计了一个能同时看懂表结构（schema 级）和单元格内容（cell 级）的表格编码器，与解码器拼成多模态大模型；在 23 项以上基准指标上，7B 版本平均提升 35.20%、72B 版本平均提升 49.32%，同时通用能力没有退化。

## 0. 给新手的阅读前置（背景知识地图）
- **这个子方向解决什么大问题**：让大模型真正「懂表格」——既能回答问题，也能查询、清洗、转换、画图，服务企业里的数据库/数据仓库/BI 场景。
- **为什么难**：
  - 表格是二维结构（行 × 列），而语言模型天然吃一维序列，序列化后会丢结构信息；
  - 真实表格很不规整：列名缺失/含糊、合并单元格、单位写在单元格里；
  - 表格任务种类多（问答、SQL、清洗、匹配、摘要、图表），通用能力还不能丢。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 直接序列化表格喂给 LLM | 通用 LLM + prompt | 把表转成 Markdown/CSV 文本 | 简单，但结构信息丢失、长表吃不下 |
| 表格预训练模型 | TAPEX、TAPAS 类 | 设计专门的预训练任务学表格语义 | 表格任务强，通用能力弱 |
| 专用表格编码器 + 通用解码器 | **TableGPT2** | 编码器吃表格，解码器出语言/代码 | 兼顾两者，训练与工程成本高 |
| Agent + 沙箱执行 | TableGPT Agent 类 | 模型生成代码/SQL，沙箱执行取结果 | 结果可验证，但链路长、延迟高 |

- **本文属于哪一类**：第三类（并在工程上延伸出第四类的 agent 形态）。
- **必懂关键名词（直觉版）**：
  - **schema 级信息**：表有哪些列、列的含义与类型（「表的骨架」）。
  - **cell 级信息**：单元格里的具体内容（「表的血肉」）。
  - **多模态**：这里指「表格」与「自然语言」两种模态由不同编码器处理后再融合，类似视觉语言模型的做法。

## 1. 问题背景与动机
- 前人工作简述：GPT、Claude、LLaMA、Qwen 等模型重塑了 AI 应用，但表格数据的集成能力明显滞后。
- 前人缺陷 / 未解决问题（逐条）：
  1. **数据库/数仓的数据集成能力不足**：高级应用需要模型真正接入结构化数据，而这块一直薄弱。
  2. **海量表格数据未被挖掘**：现实中表格是最主要的数据载体之一，潜力远未释放。
  3. **BI 场景要求「可适配且精确」**：这正是许多现有 LLM 难以满足的地方。
  4. 真实表格的**歧义查询、列名缺失、不规则表**缺少针对性设计。

## 2. 核心方法
- **最直观类比**：给模型配一副「既能看表格骨架、又能看清每个格子」的眼镜（专用表格编码器），再把它接到一张会说话的嘴（通用解码器）上——于是它既懂表，又会说人话、写代码。
- **具体做法（输入 → 关键操作 → 输出）**：
  - 输入：表格（schema + 单元格）与自然语言查询。
  - 关键操作：
    1. **大规模表格语料预训练/微调**：使用 **593.8K 张表** 与 **2.36M** 条高质量的「查询-表格-输出」三元组；
    2. **新型表格编码器**：显式捕获 schema 级与 cell 级信息，专门针对歧义查询、列名缺失、不规则表；
    3. **多模态拼接**：编码器与解码器结合，形成类似视觉语言模型的大多模态模型；
    4. **多规模发布**：7B 与 72B 两个规模。
  - 输出：面向表格任务的答案/代码/SQL，同时保留通用语言与编码能力。
- **形式化要点**：关键超参数是「训练数据规模（593.8K 表 / 2.36M 三元组）」与「编码器设计」；预训练目标与编码器结构细节 🔧 查原论文。
- **理论性质 / 保证**：**无**理论保证（论文以大规模预训练与基准评测为主 🔧）。
