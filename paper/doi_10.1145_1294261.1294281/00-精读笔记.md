## 二、背景与它回应的问题

### 2.1 2007 年亚马逊平台的真实约束

论文 §1 的立论基础不是学术上的复制模型，而是一段运维事实：亚马逊是"数千万客户、数万台服务器、全球多数据中心"的平台，**任何一次宕机都有直接金钱后果并损害客户信任**。由此引出的关键判断是——应用的可靠性与可扩展性"取决于它如何管理自己的状态"。

原文的口号式例子（§1）：客户必须"即使在磁盘故障、网络路由抖动、或者某个数据中心被龙卷风摧毁时"也能查看并修改购物车。所以管理购物车的服务的要求是：**它的存储必须随时可读、随时可写**。

### 2.2 需求画像（§2.1–2.3，逐条对应论文）

- **查询模型**：单键读写，状态是以唯一键索引的二进制 blob；**没有跨多个数据项的操作，也不需要关系模式**。对象"通常小于 1MB"。
- **ACID**：论文原话是"亚马逊的经验表明，提供 ACID 保证的数据存储往往可用性很差（tend to have poor availability）"，因此 Dynamo **主动放弃一致性（ACID 里的 C）以换取高可用**；并且明确"不提供任何隔离性保证，只允许单键更新"。这一句是整篇论文的立场宣言，也是它与 Gray 1981 的正面分歧点。
- **效率**：必须跑在**商用廉价硬件**上；延迟在 **99.9 分位**上度量（不是平均值）。示例 SLA（§2.2）："峰值 500 req/s 下，99.9% 的请求在 300ms 内返回"。
- **规模假设**：因为只服务亚马逊内部、非对抗环境（无鉴权需求），**初版设计目标只有"数百个存储主机"的量级**——论文自己承认了规模上限，并在后文讨论扩展。
- **持久性与延迟的解耦诉求（§2.3）**：作者指出传统的"主/从复制"把两者绑死了；而 quorum 类方案（PACELC 之前的直觉）让写延迟受制于最慢副本，因此需要把"数据放置"和"持久性/可用性契约"分开。

### 2.3 它回应的问题（论文自己的提法）

论文 §1 对学术贡献的定位很克制：**"本工作对研究界的主要贡献，是评估不同技术如何组合起来构成一个单一的高可用系统"**，并"证明最终一致（eventually-consistent）的存储系统可以用于生产环境、承载要求苛刻的应用"。也就是说：**Dynamo 不发明新算法**——一致性哈希、向量时钟、Merkle 树、gossip 全都来自前人（论文分别引用 [10,20]、[12]、[13]、[9]）；它的贡献是**组合、调参与在亚马逊级别生产环境中的存活证明**。

## 三、核心机制精读

论文 §4 用 Table 1 把机制与"问题"一一对应，这张表是全篇最好的地图（原文照录）：

| 问题 | 技术 | 收益 |
|---|---|---|
| 分区 | Consistent Hashing | 增量可扩展 |
| 写的高可用 | Vector clocks + 读时调和 | 版本大小与更新速率解耦 |
| 临时故障处理 | **Sloppy Quorum + Hinted Handoff** | 部分副本不可用时仍保证可用性与持久性 |
| 永久故障恢复 | **Merkle 树反熵** | 后台同步发散副本 |
| 成员与故障检测 | **gossip 成员协议 + 故障检测** | 保持对称性，避免中心化的成员/存活注册表 |

### 3.1 一致性哈希 + 虚拟节点 + 偏好列表（§4.2–4.3）

```
             hash 环（MD5(key) mod 2^128 → 顺时针）
        ┌──────────┐                      ┌──────────┐
   ────►│  token   │──── keys in range ──►│  token   │
        │  node A  │      (F, A]           │  node B  │
        └──────────┘                      └──────────┘
              (A, B] ──► 负责节点 = 从 A 顺时针数 N 个**不同物理节点**

  preference list(N=3, k ∈ (A,B]) = [ A, B, C ]      ← 协调者 = 表头
  为容忍故障，偏好列表实际收录 > N 个节点
```

要点（都是原文细节，不是通说转述）：

- **虚拟节点/令牌**：一个物理节点占据环上**多个**点（"tokens"），目的是：节点下线时其负载被**均匀摊给所有剩余节点**；新节点上线时从每个节点各接走**大致等量**的负载；并且可**按物理容量分配令牌数**以容纳异构硬件。
- **去重规则**：由于一个物理节点可拥有多个令牌，环上顺时针前 N 个位置**可能不足 N 个不同物理机**；偏好列表构造时**跳过重复位置，只保留不同物理节点**。这是实现层面的关键，很多转述漏掉了。
- **不用多跳 DHT**：论文明确说不用 Chord/Pastry 式多跳路由，"多跳会增加响应时间抖动，抬高高分位延迟"；Dynamo 自述是 **"zero-hop DHT"**——每个节点本地维护足够路由信息，直连目标。
- **跨机房放置**：偏好列表被构造为**跨多个数据中心分布**，因此整机房故障不需要人工干预（§4.6 末）。

**§6.2 的分区策略演进（生产血泪，论文最有价值的一段）**：

| 策略 | 做法 | 结局 |
|---|---|---|
| 1（初版上生产） | 每节点 T 个随机令牌，**按令牌值切分区间** | 新节点要"偷"区间，源节点须**扫本地存储**取数据→低优先级 bootstrap，旺季**耗时近一天**；节点增删使许多区间变化→**Merkle 树全部重算**；无法整环快照→归档低效 |
| 2（过渡） | 哈希空间先切成 Q 个**等分片**，令牌**只用于计算分区→节点的映射** | 解耦了"分区"与"放置"，但**负载均衡效率最差**；仅作为 1→3 的迁移中间态 |
| 3（最终） | Q 个等分片 + 每节点 **Q/S 个令牌**（S = 节点数） | **负载效率最好**；成员信息体积**降三个数量级**（有利 gossip）；分片边界固定→**可整文件搬迁**（bootstrap/恢复快）、**可单独归档**。代价：改成员需协调以保持不变式 |

作者对失败根因的一句话总结值得单独背下来：**"这一策略的根本问题在于数据分区与数据放置被纠缠在了一起（intertwined）"**。

### 3.2 向量时钟与版本语义（§4.4–4.5）

Dynamo 的取舍不是"丢更新"，而是**把更新变成不可变的新版本**：每次修改产生一个新版本，允许同一对象多个版本共存。于是判定"谁是祖先"就交给向量时钟。

- 定义（原文）：向量时钟是 `(node, counter)` 对的列表，**对象的每个版本各关联一个**；若第一个对象的时钟在**所有节点**上的计数都 ≤ 第二个，则前者是后者的祖先、可丢弃；**否则判为并发冲突，必须交给上层调和**。
- 两层调和术语：**syntactic reconciliation**（系统靠向量时钟自己判定，多数情况）vs **semantic reconciliation**（系统判不了，把叶子上的多个版本连同 context 一起返回，由客户端业务逻辑归并，如"合并购物车"）。
- **写必须带 context**：`get(key)` 返回对象**或"冲突版本列表"+ context**；`put(key, context, object)` 中 context 对调用者不透明、含版本信息，**服务端会校验其有效性**。用该 context 的更新即视为"已调和分叉、塌缩为单一新版本"。
- 论文的诚实警示（§4.4）：**"某些故障模式会导致系统内不止两个、而是若干版本"**；并且"这样一来 'add to cart' 永不丢失，但 **被删除的项目可能复活（deleted items can resurface）**"。

```
        Sx:1          Sx:2              并发！两者互不为祖先
     [D1] ──────►  [D2]  ──(client@Sy 读 D2 后写)──►  [D3] Sx:2,Sy:1
                     └──(另一客户端也基于 D2 写)────►  [D4] Sx:2,Sz:1
        compare(D3, D4): Sx 相等、Sy 与 Sz 各有大小 → 无法比较 → get() 返回 {D3,D4}
```

### 3.3 Sloppy Quorum、N/R/W 与 Hinted Handoff（§4.3、§4.6）

- 记号：`N` 副本数（**"per-instance" 配置**），`R` 读需响应数，`W` 写需响应数；`R + W > N` 保证读写集合相交。
- **sloppy quorum 的精确定义（常被转述错）**：Dynamo **不强制严格的 quorum 成员**；读写在"**偏好列表中前 N 个健康节点**"上执行——它们"未必是环上顺时针遇到的前 N 个节点"。
- **Hinted handoff 机制（原文例子）**：N=3 时若 A 短暂不可达，本应落在 A 的副本改发给 D；该副本带**hint 元数据**注明"真正接收者是 A"；接收节点把它存放在**单独的本地数据库**并周期扫描；一旦探测到 A 恢复，D 主动交付，成功后 D 可删除本地副本**而不降低系统总副本数**。
- 极端可用性档位（原文）：`W=1` 意味着"只要系统中**还有任意一个节点**能持久化写入，写就被接受"——**只有全部节点不可用时写才被拒绝**。
- 代价被明写：**"低 W/R 会增大不一致风险，因为写请求在未经过多数副本处理时就被判成功返回；这引入了持久性的脆弱窗口（vulnerability window）"**。
- 生产配置：**常见 N=3，典型 (N,R,W) = (3,2,2)**；另有把 Dynamo 当"高性能读引擎"的服务设 **R=1, W=N**（同时充当重量级后端之上的权威持久缓存）。

### 3.4 读修复与 Merkle 反熵（§4.5、§4.7）

两条互补通道，注意**分工不同**（不是"一个快一个慢"这么简单）：

1. **Read repair（写路径外的顺带修复）**：协调者会**等一小段时间**收集未到的响应；若响应里出现**陈旧版本**，协调者就地用最新版本更新那些节点。原文理由："它在机会性时刻修复漏掉最近更新的副本，**从而减轻反熵协议的负担**"。
2. **Anti-entropy + Merkle tree（处理永久故障/副本永久丢失）**：hinted handoff 只在"成员变动少、故障是瞬时的"时有效——hint 副本可能自身先挂掉。为此 Dynamo 用 Merkle 树做后台副本同步。
   - 树的定义照录："叶子是**单个 key 的值**的哈希，父节点是孩子的哈希"；根相等 ⇒ 叶子集合相等、无需同步；否则**逐层交换孩子哈希直到叶层**，两侧据此判定哪些 key "out of sync"。
   - **关键工程细节**：**每个节点为它承载的每个 key range（即每个虚拟节点覆盖的键区间）各维护一棵独立的 Merkle 树**，以便只比较该区间是否新鲜。这解释了 §6.2 里"区间一变就得重算 Merkle 树"为何是非平凡操作。

### 3.5 执行、持久层与去中心化控制（§4.1、§4.8–4.9、§5）

- **协调请求的实现**：请求协调建立在事件驱动消息底座上，处理流水线按 **SEDA** 风格分阶段；全部用 Java NIO 通道；**每个客户端请求在处理节点上创建一个状态机**（一个实例恰好服务一个请求），负责定位责任节点、发请求、等待、重试、打包响应。
- **可插拔持久引擎（§5）**：组件全用 Java 实现；在用的引擎包括 **BDB Transactional Data Store、BDB Java Edition、MySQL，以及"内存缓冲 + 持久后备存储"**。选型依据是**对象大小分布**："BDB 适合几十 KB 量级，MySQL 能处理更大对象"；**多数生产实例用 BDB TDS**。（注意：这与我读到的部分二手叙述"Dynamo 用 LSM/LSM 血统 + tombstone 删除"不同——**本 PDF 正文没有出现 tombstone / 失效删除 小节**，勿把 Cassandra 的细节安到本文头上。）
- **成员与故障检测（§4.8 + 附录 A）**：**明确区分"故障"与"永久退出"**——亚马逊环境里节点不可达常是瞬时的，不应因此触发重平衡或修复不可达副本；反向地，**人为误操作可能意外拉起新节点**。因此**加入/退出环必须显式发起**（管理员用命令行工具或浏览器连到某节点下达成员变更），变更连同发起时间写入持久存储形成**历史**。之后**gossip 每秒随机挑一个 peer，双方高效地调和各自持久化的成员变更历史**，得到最终一致的成员视图。
- **配置管理**：新节点首启自行选 token 集合并持久化到本地磁盘；种子（seed）机制 + 外部发现（附录 A.2）用于冷启动。

### 3.6 论点逻辑链小结

1. 商业代价上，**拒绝写的代价 > 读到旧数据的代价** ⇒ 可用性优先级压倒一致性（§1、§2.1）。
2. 要"随时可写"，就不能让写请求绑定在固定的少数物理机上 ⇒ **sloppy quorum + hinted handoff**（§4.6）。
3. 一旦允许任何节点代收写，副本必然发散 ⇒ 必须**保留并发版本而不是覆盖** ⇒ **向量时钟 + 读时调和**（§4.4）。
4. 一旦允许版本分叉，就必须把它**收敛**回去 ⇒ **read repair（快、机会性）+ Merkle 反熵（慢、兜底）**（§4.5/4.7）。
5. 一旦不允许中心协调者存在（它本身是可用性瓶颈）⇒ **一致性哈希 + 全量对称 + gossip 成员视图**（§4.2/4.8）。
6. 于是最终一致 + 会话级保证 + 可调 R/W/N = "把一致性—可用性—持久性做成三个旋钮"（§4.6、§6.1）。

## 四、实验与生产经验（全部取自论文 §6，标注图表号）

论文 §6 的标题是 "Experiences & Lessons Learned"——它的"实验"是**生产系统实测**，不是仿真。以下每一条都能在 PDF 中找到对应图/表/小节。

| 主题 | 出处 | 可核实结论 |
|---|---|---|
| 运行环境 | §6.1 前 | 所有测量取自**线上真实系统**，配置 **(3,2,2)**，**"a couple hundred nodes"**，同构硬件；每实例跨多机房，机房间高速链路 |
| SLA | §6.1 | 常见服务级要求："99.9% 的读写在 **300ms** 内完成" |
| 延迟形态 | Fig 4（2006 年 12 月旺季，30 天） | 延迟随请求率呈明显**日周期（diurnal）**；**写延迟高于读**（写总要落盘）；**99.9 分位约 200ms，比平均值高一个数量级**（受负载波动、对象大小、局部性共同影响） |
| 写缓冲换性能 | Fig 5（24h） | 每节点加**内存对象缓冲**、写线程周期性刷盘、读先查缓冲；**仅一千个对象的小缓冲**就在峰值时把 **99.9 分位延迟降低约 5 倍**并抹平高分位 |
| 缓冲的代价与补救 | §6.1 | 服务器崩溃会丢掉缓冲中排队的写。缓解：**协调者从 N 个副本中指定 1 个做 "durable write"**；由于协调者只等 W 个响应，这一个慢副本的持久写不影响整体写延迟 |
| 负载不均衡 | Fig 6（24h，30min 窗口；阈值 ±15%） | **低负载时不均衡率高达 20%，高负载时接近 10%**；解释是高峰时大量热门 key 被访问、key 的均匀分布使负载变均匀（1/8 峰值负载下热门 key 被访问得少） |
| 分区策略对比 | Fig 7、Fig 8（S=30, N=3，等量成员信息下比效率） | 效率定义 = **平均节点服务请求数 / 最热节点服务请求数**；**策略 3 最好、策略 2 最差**；策略 3 相对策略 1 还**把成员信息体积减小三个数量级** |
| 分叉版本到底有多少 | §6.3（24h，购物车服务） | **99.94% 的请求只见 1 个版本**；2 个版本 0.00057%、3 个 0.00047%、4 个 0.00009% ⇒ **分叉极罕见**。更重要的反直觉结论：**版本数上升的主因不是故障，而是同一数据的并发写者增多**，而并发写增多"通常由 busy robot（自动客户端程序）触发，极少由人触发" |
| 客户端驱动协调 | §6.4、Table 2（24h） | 写必须由偏好列表内节点协调（它要生成**因果上包住被更新版本**的新版本戳；若改用物理时间戳版本化，则任意节点都能协调写）。把协调状态机移到客户端库后，客户端**每 10 秒**向随机节点拉一次成员信息（选 pull 是因为客户端规模下更可扩展、服务端几乎不存客户端状态），最坏暴露于 10 秒陈旧视图；检测到成员不可达则立即刷新。实测 **99.9 分位读写约 68.9/68.5ms → 30.4/30.4ms（降低至少 30ms）**，平均约 3.9/4.02ms → 1.55/1.9ms |
| 后台任务不能压垮前台 | §6.5 | 副本同步与 handoff 都属后台任务，早期生产环境中它们与前台 put/get **争抢资源**。解法：**准入控制 + 反馈环**——持续监控前台磁盘延迟、锁冲突/事务超时导致的失败、队列等待，比较其分位数与预设阈值（原文例：最近 60 秒 DB 读 99 分位是否接近 50ms）来决定分给后台多少时间片 |
| 总体运营结果 | §6.6 | 已有众多亚马逊内部服务使用 Dynamo **两年**；应用侧 **99.9995% 的请求在未超时的情况下拿到成功响应**，且**"迄今未发生过数据丢失事件（no data loss event has occurred to date）"** |
| 对上层开发的真实影响 | §6.6 | 与商用数据仓库不同，Dynamo **把一致性问题和调和逻辑暴露给开发者**。作者主张这没有想象中可怕：亚马逊平台本就为高可用构建、许多应用早已自行处理故障与不一致，**移植成本不高**；新应用则需在开发初期分析"选哪种冲突调和机制才契合业务" |

## 五、对比分析：Dynamo ↔ Spanner（同一光谱的两端锚点）

对照阅读：[`../spanner_2012_osdi/00-精读笔记.md`](../spanner_2012_osdi/00-精读笔记.md)。两篇相隔五年、同属"超大规模公司自研分布式存储"的体裁（都是"设计 + 生产经验"混写、都有"我们如何踩坑"章节），但取向**互为镜像**：

| 维度 | Dynamo (2007) | Spanner (2012) |
|---|---|---|
| 抽象 | 无模式 KV：`get/put(key, ctx, obj)`，对象 <1MB | 半关系型：有序行键 + 表 + **交错层级**，类 SQL |
| 正确性契约 | **最终一致** + 会话保证；无隔离，仅单键更新 | **外部一致**（真实时间序 = 提交序）+ 可串行化事务 |
| 冲突处理 | **不裁定**：版本分叉抛给应用调和 | **必裁定**：2PL 定序 + Paxos 多数派选唯一胜者 |
| 时钟 | 逻辑的（向量时钟），**不用物理时钟排序**（但可选 timestamp 版本化模式） | **物理时钟为原语**：TrueTime 返回不确定区间 |
| 复制协议 | sloppy quorum R/W/N（**无共识**） | 每分区一个 **Paxos 组**（默认 5 副本）+ **Paxos 化的 2PC** |
| 分区 | 一致性哈希 + 虚拟节点（令牌） | 按 key 有序切 directory，**Split/Merge/Move** 自动重分片 |
| 副本收敛 | 事后：read repair + Merkle 反熵 | 事前：写必须多数派持久化才返回（**同步复制**） |
| 扩容摩擦 | bootstrap 需扫库迁移、Merkle 重算（§6.2 之痛） | Move/Split 是后台常态，但改副本配置仍**不支持 in-Paxos 变更**、要用 Movedir |
| 读扩展 | R=1 档当高性能读引擎 | **follower 服务快照读/历史读**，绕开 leader |
| 可用性数字 | 99.9995% 请求不超时，零数据丢失事件 | 生产实例读均值 8.7ms、站点内提交 72.3ms、跨站点 103.0ms（**注意均值/方差量级差很多**） |
| 谁付代价 | **应用程序员**（写调和逻辑、接受删除复活） | **硬件与延迟**（原子钟+GPS、每次写提交付 commit-wait） |

**三条值得展开的分歧**：

1. **"R+W>N" 与"多数派"不是一回事**。前者只保证读写集合相交，因而能给出"因果序不乱 + 高概率读到最新"；它**不能**给出线性一致，因为并发写交错时没有任何机制裁定唯一胜者。Dynamo 的选择是**承认裁定不了、把它交给业务**（§4.4 semantic reconciliation）；Spanner 的选择是**在数据库内部把裁定做掉**（2PL 决定冲突序，Paxos 决定提交与否）。这正是 [`../../courses/并行与分布式系统/MIT6.824/notes/L10-一致性与线性一致性.md`](../../courses/并行与分布式系统/MIT6.824/notes/L10-一致性与线性一致性.md) 与 [`../../courses/并行与分布式系统/MIT6.824/notes/L08-Paxos共识原型.md`](../../courses/并行与分布式系统/MIT6.824/notes/L08-Paxos共识原型.md) 两讲的边界。
2. **向量时钟 vs TrueTime：两种"人造时间"的对偶**。向量时钟只表达**因果偏序**，代价是版本可能不可比、必须外溢到应用；TrueTime 表达**带误差界的物理时刻**，代价是硬件与 sleep 税。前者是"逻辑派"、后者是"硬件派"，见 [`../../courses/并行与分布式系统/MIT6.824/notes/L07-时间时钟与事件顺序.md`](../../courses/并行与分布式系统/MIT6.824/notes/L07-时间时钟与事件顺序.md)。
3. **对 Gray 1981 的相反方向继承**。Gray 承认 ACID 在分布式会阻塞（2PC prepared 悬挂）却仍推荐它——"正确性优先于可用性"；Dynamo 干脆把这条局限当成**卖点反转**：正因为 ACID 系统"往往可用性差"，才放弃 C 与 I。Spanner 则是**把 Gray 的两条局限（热点吞吐、分布式阻塞）同时工程化解决**（细粒度 Paxos 组 + 无 2PC 阻塞），代价高到只有 Google 付得起。对照 [`../doi_1981_gray_transaction_concept/00-精读笔记.md`](../doi_1981_gray_transaction_concept/00-精读笔记.md) §2.5 的第 1、5 条。

**仓库内其它对照坐标**：[`../../book/分布式数据库入门进阶与实战/05-BASE与CAP及分布式一致性模型.md`](../../book/分布式数据库入门进阶与实战/05-BASE与CAP及分布式一致性模型.md)（该章把"Dynamo 式 R+W 交叠读时顺手补落后副本"列为读修复/反熵范式的原型）、[`../../book/分布式数据库入门进阶与实战/04-数据分片与数据复制.md`](../../book/分布式数据库入门进阶与实战/04-数据分片与数据复制.md)（"无主 quorum：Dynamo 式读写集合，修复靠反熵"）、[`../../book/软件架构设计/11-多副本一致性.md`](../../book/软件架构设计/11-多副本一致性.md)。

## 七、批判与延伸

**这篇论文站得住的地方**

1. **"不发明、只组合"的定位是诚实且稀缺的**。它给出的是可被复核的生产证据（§6 每个数字都有图表号与观测窗口），而非合成负载下的理想曲线。
2. **§6.2 分区策略演进是全文最珍贵的部分**：明确写出初版为什么失败（扫库、Merkle 重算、无法归档），并给出"分区与放置必须解耦"这一可迁移的设计原则。**多数论文不会承认初版设计在生产的狼狈**。
3. **反直觉的实测结论**（分叉主因是并发写者/机器人而非故障；低负载反而更不均衡）只能来自真实系统，这类"负结果"是 Dynamo 对研究社区最实在的贡献，也与它自陈的贡献定位一致。

**需要批评与警惕的地方**

1. **§6.3 自己承认"无法给出一致性影响的完整刻画"**：outage 长度、故障类型、组件可靠性、工作负载等因素的数据"超出本文范围"。也就是说，**"最终一致在生产上够不够用"这个核心命题，本文只用一个"版本数分布"做了代理度量**，并没有度量业务正确性。这是它被引用得最多、也被误信得最多之处。
2. **规模上限被自己写死**：初版目标只有"数百存储主机"，成员信息要全量 gossip/广播，论文明说**"维护路由信息的开销随系统规模增长，是本设计的可扩展性限制"**，并寄望分层扩展或 O(1) DHT。今天把它当作"可无限扩展"的模板是过度解读。
3. **可用性数字的分母不透明**：**99.9995%** 是"应用未超时即拿到成功响应"的比例，而不是 CAP 意义下"分区时仍可用"的证明；**"零数据丢失事件"** 也只是**截至发表时**的经验观察，且建立在"内部非对抗环境 + 无鉴权需求 + W 被调高"的前提上。论文其实把这两点讲清楚了，是转述者常常不讲。
4. **"sloppy quorum + 读修复"给不了跨键不变式**。购物车语义（可丢删除、可加回）只是**恰好**容忍分叉；把 Dynamo 用于任何需要余额守恒/库存不超卖的场合，都要求应用自己实现调和或另加机制——这正是 DynamoDB 后来补"事务 API"、Cassandra 后来补 **LWT(Paxos)** 的原因。**AP 系统里嵌一条 CP 通道**是产业给本文打的补丁，不是本文自己的方案。
5. **持久性与延迟被解耦的代价被轻描淡写**。W=1 + 写缓冲 + 单副本 durable write 的组合，把"已确认写"的持久性押在"该副本/那台机器不崩"上；论文的补救（指定一个副本做真落盘）只是降低概率，不是消除窗口。
6. **术语被后世稀释**。今天大量"Dynamo 风格"系统把 Dynamo 等同于"哈希环 + R/W/N"，而**丢掉了 hinted handoff 与 sloppy quorum 这对可用性主力**（也丢掉了 §6.2 的分区/放置解耦）。本文的可用性魔法**主要在这一招**，不在哈希环本身。
7. **版本存储的成本被推给了版本机制本身**：向量时钟随写者集合增长，Dynamo 用"读时调和 + 塌缩分支"控制它，但**多机器人高频写同一 key** 正是 §6.3 观察到分叉数上升的场景——即最热、最需要可扩展性的场合恰好是它的弱区。

**延伸线索**

- 直系后代：**Cassandra / ScyllaDB / Riak / Voldemort / DynamoDB**（其中 DynamoDB 是"托管 + 补上事务与强一致读选项"的产品化改写，不等于本文）。
- 冲突调和的**自动**解法：Shapiro 等的 **CRDT**（把"抛给应用"变成"数据结构自身可交换合并"）；这是本文"semantic reconciliation"的直接对立面。
- 反思 Dynamo 立场、走另一端的系统：[`../spanner_2012_osdi/00-精读笔记.md`](../spanner_2012_osdi/00-精读笔记.md)、CockroachDB（HLC 替代原子钟）、TiKV（中心化 TSO 替代 TrueTime）。
- 理论定位：CAP（Brewer 2000 提出、Gilbert & Lynch 2002 证明）与 **PACELC**（2010）为本文的直觉提供了正式语言；Dynamo 论文本身**没有出现 "CAP" 一词**（本次全文检索确认）——把它写成"首篇 CAP 实践论文"属于后设叙事。

**思考题（4 道）**

1. 论文 §6.2 说策略 1 的根本毛病是"分区与放置纠缠"。请论证：为什么把哈希空间先切成固定 Q 个分片（策略 3）能让 bootstrap 从"扫库"降为"传文件"？并说明这一改动的**新成本**（为何"改成员需要协调"）。
2. 设 N=3、R=W=2。构造一个包含两次并发写与一次读的历史，使得读返回最新版本却**没有**满足线性一致性。然后说明：如果要求"读到的版本必须包含所有已确认写"，需要额外引入什么机制、它为什么必然伤害可用性。
3. §6.3 的实测显示"分叉数上升由并发写者（机器人）驱动，而非故障"。据此推导：在什么业务形态下，向量时钟的版本数会**无界**增长？Dynamo 的"读时塌缩分支"为什么无法阻止它？CRDT 又是在哪个假设上消解了它？
4. 本文说"提供 ACID 的数据存储往往可用性很差"，而 Spanner 用 TrueTime + Paxos 实现了全球 ACID 并宣称五个九。判断这两句是否矛盾——请从"故障模型（谁不可用）"与"复制是同步还是异步"两个角度给出你的论证。

## 九、一页总结（复习卡）

- **一句话**：为了"购物车永远可写"，把**一致性从系统保证降级为可调旋钮 + 应用责任**，并用 **sloppy quorum + hinted handoff（可用性）× 向量时钟 + 读时调和（正确性外溢）× Merkle 反熵 + 读修复（收敛）× 一致性哈希 + gossip（去中心化）** 这一套组合在真实生产里跑通。
- **两个最常被忽略的细节**：偏好列表要**去重到不同物理节点**；Merkle 树是**每个 key range 一棵**（因此区间变化 = 全部重算）。
- **一组该背的生产数字**：(N,R,W)=(3,2,2)；SLA 99.9% < 300ms；99.9 分位约 200ms（均值高一个数量级）；一千对象的小缓冲把 99.9 分位降约 5 倍；99.94% 请求只有 1 个版本；客户端驱动协调省掉 ≥30ms 的 99.9 分位；**两年、99.9995% 不超时成功、零数据丢失事件**。
- **一条诚实的自我限制**：初版只按"数百存储主机"设计，成员信息开销随规模线性增长——**可扩展性是它自己承认的短板**。
- **一条历史判词**：Dynamo 的真正遗产不是"哈希环"，而是**证明了"把一致性交给业务"是一个可以上线的选项**；此后十年的 NoSQL 论战、以及 NewSQL 集体"把 ACID 补回来"，都是在这一命题上工作。
