## 一句话总结

空间数据库算几何查询时没有「标准答案」可对，怎么知道它算错了？Spatter 的招数是：把输入几何图形做旋转、平移、缩放等仿射变换，变换前后的查询结果必须跟着「等价地变」，一旦不满足这个数学约定，就抓到一个逻辑 bug。

## 0. 给新手的阅读前置（背景知识地图）

- **子方向解决什么大问题**：数据库测试的核心难题是**预言问题（oracle problem）**——给一条 SQL，你不知道正确的输出应该是什么，自然无法判断数据库答得对不对。空间数据库（SDBMS）尤其难：几何计算（相交、包含、距离、面积）连人工验证都费劲，更别说自动比对。
- **为什么难**：空间对象（点、线、面、多边形集合）结构复杂、拓扑关系（DE-9IM 模型 🔧 术语）微妙，随机生成 SQL 大多是无效或退化的，随机生成几何图形又常常测不到深层逻辑分支。
- **几类主流解法**：

| 路线 | 思路 | 代表 |
|------|------|------|
| 差分测试 | 多个引擎/配置互相比对 | 图数据库差分测试（Gremlin 系） |
| 元变测试（Metamorphic Testing） | 构造「输入变 → 输出必怎么变」的变换规则当判据 | PQS、TQC、本文 AEI |
| 语法/覆盖率引导生成 | 用语法有效性 + 覆盖率反馈生成有效查询 | SQUIRREL、语法树遍历 |

- **本文属哪类**：元变测试（变体）——用「仿射等价」这一几何性质做预言；并配一个几何感知的 SQL 生成器。
- **关键名词直觉解释**：
  - **仿射变换（Affine Transformation）**：旋转、平移、缩放、剪切这类保持直线与平行关系的几何变换；它们会可预测地改变面积、长度、位置等量。
  - **逻辑 bug（Logic Bug）**：不崩溃、不报错，但**返回错误结果**的缺陷——对用户最隐蔽、最危险。
  - **预言（Oracle）**：自动判断「结果对不对」的机制；本文的预言是「仿射等价输入的结果必须满足可推导的对应关系」。

## 1. 问题背景与动机

- 前人工作简述：数据库逻辑 bug 测试近年发展出 Pivoted Query Synthesis（PQS，OSDI'20）、基于查询计划的引导测试、图数据库的图变换测试等（其中 Rigger 组系列工作）；fuzzing 已接入 PostGIS 底层库（oss-fuzz）查内存类缺陷。
- 前人缺陷/未解决的问题（逐条，据摘要与相关文献推断）：
  1. **空间数据没人管**：上述方法均针对标量/关系数据或图数据，未处理几何类型与空间函数；
  2. **缺真值（ground truth）**：空间查询结果无法预知，传统「比对期望输出」失效；
  3. **随机形状生成器太弱**：朴素随机生成的几何体大多是无效或过于退化的形状，测不出深层逻辑缺陷；
  4. **已有预言不适用空间语义**：仿射变换如何与 SQL 语义（投影、过滤、聚合、空间谓词）联动，此前没有方案。

## 2. 核心方法

- **最直观类比**：把一张地图上的所有地块整体旋转 90 度、放大 2 倍，那么「哪两个地块相邻」「A 是否包含 B」「周长变成几倍」都应该按数学规律可预测地变化。如果数据库在变换后的地图上算出的关系和原来的不成比例，它内部一定有一处算错了。
- **具体做法（输入→关键操作→输出）**：
  - 输入：目标 SDBMS（PostGIS、DuckDB Spatial、MySQL、SQL Server）；
  - 关键操作一：**几何感知生成器**——按空间数据的特点（有效几何体的构造规则、空间函数的参数约束）生成高质量、可执行的 SQL 语句（而非随机拼凑）；
  - 关键操作二：**仿射等价输入（AEI）预言**——对查询中的几何输入施加仿射变换 T，推导出结果应满足的等价关系（如谓词不变性、度量按 T 缩放 🔧 精确变换规则逐函数推导查原文），执行原查询与变换查询并比对；
  - 输出：违反等价关系即报告一个潜在逻辑 bug。
- **形式化要点**：仿射变换保持拓扑谓词（ST_Contains、ST_Intersects 等）的真值不变，同时对长度/面积/距离给出确定的缩放因子——这正是「等价」可被机器判定的数学基础（🔧 论文中的形式定义与适用函数范围查原文核对）。
- **理论性质/保证**：预言是无损的必要条件式（等价必须成立，不成立必有 bug），不会漏报已触发者；但仿射变换不覆盖所有函数语义时该函数无法被测试（🔧 原文对覆盖率限制的表述待核）。

## 4. 实验结论（概览）

- 对比基线：朴素随机形状生成器；被测系统：PostGIS、DuckDB Spatial、MySQL、SQL Server。
- 指标：发现的未知独特 bug 数、确认数、修复数。
- 结论方向（数字均据摘要，已核实）：
  1. 测试活动共发现 **34 个此前未知的独特 bug**，其中 **30 个被开发者确认，18 个已修复**；
  2. 几何感知生成器在「独特 bug 检出数」上**显著优于**朴素随机形状生成器；
  3. AEI 预言能找出 **14 个此前方法全部漏掉**的逻辑 bug。
- 🔧 逐引擎 bug 分布、每类函数的检出分布、测试吞吐（语句/小时）等精确数字查原论文后补。

## 7. 2026 视角（🔧）

- 空间能力已成为主流引擎标配（PostGIS 生态、DuckDB Spatial、MySQL/SQL Server 内建几何类型），随之而来的逻辑正确性问题在 GIS、LBS、自动驾驶地图等场景的代价越来越高；
- 数据库「差分/元变测试」在 2020 年代成为软件工程与数据库交叉的热点，Rigger 组的 PQS→TQC→图变换→本文 AEI 是一条清晰的「把预言推广到新数据类型」主线；
- 2026 年趋势：LLM 辅助生成测试查询 🔧（通说）与形式化语义模型结合，可能进一步压缩「无法判定对错」的角落。

## 8. 新手学习路线

- **10 分钟**：读本文摘要，理解「仿射变换 = 免费的真值」这一个核心想法；
- **30 分钟**：在 PostGIS/DuckDB 里手工做一次小实验：造一个多边形，做 ST_Contains 查询；再把它旋转/平移后重跑，观察结果应保持一致——亲手感受 AEI 预言；
- **进阶**：读 PQS（OSDI'20）与本文正文，比较两类预言的构造逻辑；然后跑 Spatter 仓库，尝试对一个空间函数族统计其 AEI 可测比例。
