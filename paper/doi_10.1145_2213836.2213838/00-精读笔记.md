1. **三重混淆点**，是本笔记"考证"示范价值的来源：
   - 会议名被误记为 SOSP 2011（实为 EuroSys 2012）；

## 二、背景与问题：分区数据库里，事务为什么慢

### 2.1 问题设定

OLTP 负载 + share-nothing 分区 + 跨分区事务 + 同城/跨洲复制。传统方案的账单：

- **悲观路线（2PL 跨节点）**：锁等待图上叠网络往返，死锁检测要么中心化的（单点）要么分布式的（探测风暴）。
- **乐观路线（OCC + 2PC）**：执行零协调，但**提交时**要 prepare/commit 两轮 + 每个参与者故障悬挂风险（Gray 1981 §2.5 第 5 条，[`../doi_1981_gray_transaction_concept/00-精读笔记.md`](../doi_1981_gray_transaction_concept/00-精读笔记.md)）；冲突率高时大量回滚。
- **复制路线**：要么同步复制（每写等 quorum），要么异步复制（丢严格可串行化）——Spanner 用 Paxos 把两者缝合，代价是每一笔事务都付共识的轮次。

### 2.2 Calvin 的关键观察

> **可串行化问题本质是"排序"问题；如果能在执行之前就确定性地知道每个事务的读集/写集，那么"排序"可以与"执行"解耦，且排序可以一次做完、无限预做。**

数据库对事务顺序唯一真正的需求是一个**满足读写依赖的全序**。这个全序不需要"等事务算出结果"才能定——只要每个事务的**声明式读写集**（基于主键/索引键的谓词范围）在入口就能算出来。于是：协调轮次从"执行期/提交期"被前移到"入口期"，而入口期的排序可以**流水线化、批量预分配**。

## 三、核心设计精读

### 3.1 三阶段流水线（论文主架构）

```
        客户端事务(命令集)
             │
   ┌─────────▼──────────┐
   │ ① INGRESS / 规划     │  每条命令用 schema 推导:
   │   计算 read set /    │  读集(键范围) + 写集(键范围)
   │   write set          │  多分区事务的读集必须静态可知
   └─────────┬──────────┘
             │ (txn, RW-sets)
   ┌─────────▼──────────┐
   │ ② DETERMINISTIC      │  每个分区有 owner；跨分区事务由其
   │    ORDERING 序列化器  │  第一键范围 owner 充当"序列化点"，
   │                      │  分配全局时间戳并【持久化顺序记录】
   └─────────┬──────────┘
             │ 已定序的事务流（按时间戳排序、可预执行排队）
   ┌─────────▼──────────┐
   │ ③ EXECUTION +        │  各分区按时间戳顺序apply，无锁等待、
   │    REPLICATION       │  无冲突回滚；日志记录本身=复制单元，
   │                      │  副本按同一全序 apply ⇒ 严格可串行化
   └────────────────────┘
```

要点逐条：

1. **读写集声明（①）**：命令必须能在执行前给出键范围（等值键、主键上的范围扫描）。这限制了"读依赖前文结果"的事务形态——Calvin 要求事务逻辑**确定性且读集静态可知**；确需动态读集的负载要么改写要么退化（论文承认的适用范围，定性）。
2. **序列化器（②）**：一个 per-partition 的"定序服务器"维护本键范围的全局时间戳分配。跨分区事务的读集交集使"谁负责定序"可被规则化（本笔记按论文精神转述为"首键 owner 定序"，细节措辞未逐字核）。定序结果**先持久化再执行**——顺序即日志，崩溃后按已持久化顺序重放。
3. **执行与复制合一（③）**：事务按时间戳顺序在 primary 上 apply；apply 产生的"已定序命令"直接发给 replica —— **没有独立的日志复制协议，复制流就是执行流**。所有副本看到同一全序 ⇒ 严格可串行化 + 外部一致性（顺序由真实时间戳分配器给出；与 Spanner 的 commit-wait 相比，Calvin 不等待时钟不确定性窗口，但依赖"入口到执行顺序"的因果假设，论文对时钟要求显著弱于 TrueTime，定性表述）。
4. **只读事务**：不必参与写序，但为保严格可串行化需等到"其快照时间戳之前的写都已 apply"——**这是 Calvin 最著名的延迟软肋**（排队深度决定读延迟）。

### 3.2 伪码：一笔跨分区转账（按论文机制整理，非原文）

```pseudo
-- ① ingress
txn = { cmds:[ dec(A,100), inc(B,100) ] }
for c in txn.cmds:
    c.read_set  = schema_plan_keys(c)   -- A 的键范围
    c.write_set = keys(c)
txn.rwsets = union(...)                 -- 静态可算 ⇒ 合法

-- ② ordering (serializer at owner(txn.first_key))
ts = serializer.next_ts()
persist_order_record(ts, txn)           -- 顺序先落盘，可无限预做
ship(txn@ts, to=所有涉及分区的 primary 与 replica)

-- ③ execution (每个分区各自维护 apply_ts)
on partition p:
    while queue.head.ts == apply_ts + 1:
        t = queue.pop()
        for c in t.cmds touching p:
            apply(c)                    -- 无锁: p 由本节点独占
        log_append(t@ts)                -- 这条即复制记录
        apply_ts = t.ts
    ack_to_serializer(t.ts)             -- 仅用于回收/进度，不参与决票

-- 只读事务
on read_only(R):
    wait until per-partition apply_ts >= R.snapshot_ts  -- 软肋：等积压
    execute(R) against materialized state
```

对照传统 2PC：提交路径上没有 prepare/commit 两轮投票；②的 `persist_order_record` 是唯一强持久点，但它**可以批量、可以流水线预填**，网络成本被摊到入口而非提交。

### 3.3 确定性的边界

- UDF、随机数、系统时间、外部服务调用都会破坏"读集静态可知"与"重放等价"——Calvin 要求把它们**参数化为事务输入**（先记录随机种子/时间值再入序）。这与今天的 deterministic execution/共识状态机（SMR）要求同构。
- 与 H-Store/VoltDB 的关键差异（论文立场，转述）：H-Store 也分区独占，但其全局顺序要经 EEI 协调器在两阶段间往返；Calvin 把协调全部前移，**执行期零轮次**，且不要求存储过程形态。

## 四、实验与工程取舍（定性声明）

- 实验形态：作者用自研原型 + 多数据中心仿真/EC2 类平台，负载含 TPC-C 类与合成基准（具体规模、节点数、吞吐数字**未逐字复核，不引用**）。
- 报告结论的定性概括（通说）：
  1. **吞吐**：写多/跨分区事务场景下相对 OCC+2PC 基线有数量级级优势（"orders of magnitude"为论文宣传语，本次未复核原文图表，标注待核）；
  2. **延迟**：可预测——延迟由"入口排队深度+复制距离"决定，而非锁等待/回滚的方差；
  3. **代价**：只读事务快照延迟、读写集静态化的应用改造成本、序列化器的热点扩展问题。
- 工程取舍一句话：**用"应用写法的确定性约束 + 读延迟"换"写路径零协调 + 复制与事务统一"**。这笔交易在金融级窄负载（账户转账类）里划算，在分析型/动态读集负载里不划算——正是后续 FaCT、SLOG 等"保留预排序、放宽读路径/执行模型"工作的切口（通说）。

## 七、批判与延伸

1. **"零协调"是移花接木而非消失**：协调从提交期搬到入口期，序列化器仍是逻辑单点（每键范围一个）；跨分区热点事务的定序会退化为等待。批判性阅读时应问：预排序把 2PC 的**可用性**风险换成了**吞吐公平性**风险——悬挂没了，队头阻塞来了。
2. **读集静态化是隐性契约**：它把数据库复杂度转嫁给应用写法（schema 设计、键选取、确定性函数）——与 Gray 1981 "复杂性从应用转移到系统"的立场**相反**，Calvin 做了一次诚实的回摆。这是"系统简单 ⇒ 应用受限"光谱上的明确锚点，可与 Dynamo 笔记的"最终一致 ⇒ 应用自补偿"对读。
3. **只读路径是最大短板**：快照需等积压排空，读延迟随写入速率增长；FaCT/SLOG 等后继（通说）沿"保留定序、改读路径/解耦复制与执行"方向修正；TiDB/YugabyteDB 等 NewSQL（[`../../db/newsql.md`](../../db/newsql.md)、[`../../db/YugabyteDB.md`](../../db/YugabyteDB.md)）则各取 Calvin/Spanner 的零件混配。
4. **元数据事故本身的方法论教训**：一篇论文的 Crossref 容器字段可以是错的（Calvin 被挂 SIGMOD），而 DOI 仍是唯一可靠身份证——引用必须以"作者+题名+DOI 三者互证"，不能只信其一（见 §一）。
5. **与共识的关系**：Calvin 的"持久化顺序记录再执行"相当于把单一序列化器的决定当作无需投票的日志——本质上是用**分区所有权假设**替代共识；网络分区时该假设如何降级（fencing/租约）论文着墨有限（定性判断，未逐字核）。

## 十一、思考题（5 道）

1. Calvin 声称"执行前即可确定事务全序"，前提是读写集静态可知。请构造一个"读依赖本事务前序命令结果"的转账应用写法，说明它为何落入 Calvin 的适用范围之外，并给出两种工程改写（预查+键固定、拆事务）各自牺牲了什么语义。
2. 对比 Calvin 与 Spanner 的提交延迟构成：前者≈入口排队+一次广播，后者≈2PC+Paxos+时钟等待。在低竞争、单数据中心场景谁更优？在高竞争热点账户场景呢？论证"预排序的优势区间"边界。
3. Calvin 的"顺序记录先持久化再执行"与共识日志的"多数派提交后才 apply"，在故障恢复语义上有什么本质差异？提示：前者依赖分区 owner 唯一性，后者不依赖——若 owner 假设被网络分区打破，各自会怎样？
4. 论文用宗教改革家命名"预定论"。请据此说明：为什么确定性重放要求把时间/随机/外部调用参数化为输入，这与状态机复制（SMR）的确定性条件是否同构？举一个你的代码库中会破坏该条件的实际例子。
5. 引用链考察：为何 `10.1145/2168836.2168854` 会被误当作 Calvin 的 DOI，而 Calvin 自己的条目又挂着 SIGMOD 容器？请给出你在文献管理系统中防止这两类污染的三步校验流程（提示：Crossref 作者-题名-前缀互证，见 §一与 §七.4）。

## 十二、误读提醒与核实记录

### 12.1 误读提醒

1. **会议名**：Calvin 是 **EuroSys 2012**（伯尔尼，4 月），不是 SOSP 2011；"SOSP/OSDI 才是数据库系统论文的家"是会议圈层偏见，EuroSys 在系统界地位无需辩护。
2. **DOI 双坑**：`2168836.2168854`=LazyBase（同论文集的另一篇）；`2213836.2213838`=Calvin 本体但容器字段有误。写简历/综述时二选一并加注。
3. **"Calvin 消灭了 2PC"是夸大**：它消灭的是**提交期**协调，入口期定序与顺序持久化仍在——只是可以被流水线预做。
4. **Calvin 不弱于 Spanner 的只是轮次数**，不是全部代价：读延迟、静态读集、owner 单点是论文自认的交换条件；把两者比成"谁彻底赢了"属于常见简化。
5. 期刊版（TODS 2014）与会议版内容有扩展（复制与故障处理细节），引用机制时注意版本差。
