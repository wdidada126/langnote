## 一句话总结
Agentic Text-to-SQL 要让一个请求串起多次 LLM 调用，现有 LLM 服务框架只按「独立请求」调度，SLO 破坏严重——HEXGEN 用「全局负载均衡派发 + 自适应本地优先级队列」的分层调度器，在异构 GPU 集群上服务多租户 Text-to-SQL 工作流，实测 P95 尾延迟降 1.42~1.56 倍、吞吐升 1.49~1.81 倍。

## 0. 给新手的阅读前置（背景知识地图）

- **大问题**：把 Text-to-SQL 做成生产级服务——用户问句进来，Agent 要做多阶段推理（schema 链接 → 生成 → 执行/修正 → 回答），每次都是一次 LLM 推理调用；要在企业异构 GPU 集群上低延迟地同时服务很多用户。
- **为什么难**：① 阶段间有依赖（DAG），不能各请求独立调度；② 尾延迟（P95/P99）有 SLO 约束；③ 集群 GPU 型号混杂、多租户共享；④ 请求到达率动态波动。
- **主流解法**：

| 路线 | 直觉 | 弱点 |
|------|------|------|
| 通用 LLM 服务框架 | vLLM/TGI 等按独立请求做 continuous batching | 不懂工作流依赖，SLO 频繁违约 |
| 单机 Agent 编排 | LangChain 类框架管流程 | 不管集群资源与调度 |
| **工作流感知调度** | 把 Agent 工作流的依赖结构纳入调度决策 | 本文所属（新方向） |

- **本文属于**：工作流感知调度路线，聚焦 agentic Text-to-SQL 这一具体负载。
- **关键名词直觉**：
  - **Agentic workflow（代理工作流）**：一条用户请求 ≠ 一次模型调用，而是「规划-生成-验证-修正」的多步调用链，后一步依赖前一步的输出。
  - **SLO（service-level objective）**：如「95% 的请求在 10 秒内返回」；调度器的成绩单。
  - **异构 GPU 集群（heterogeneous GPUs）**：同一集群里混着不同型号/显存的卡，任务要「对号入座」。

## 1. 问题背景与动机

- 前人工作：LLM 推理优化（continuous batching、PagedAttention 等，通说 🔧）大幅提升单模型服务效率；Agent 框架解决功能编排；Text-to-SQL 研究专注准确率。
- 前人缺陷（依摘要逐条）：
  1. **多阶段依赖被无视**：现有 LLM 服务框架主要为独立推理任务设计，看不到 Text-to-SQL 工作流的阶段依赖；
  2. **SLO 违约频繁**：对 Text-to-SQL 负载性能次优、服务水平目标破坏严重；
  3. **部署复杂**：企业异构 GPU 集群 + 多租户场景缺少专门支持；
  4. **超参难调**：调度参数在不同负载下需要反复手工调整。

## 2. 核心方法

- **直观类比**：一条 Text-to-SQL 请求像一张「点单后要现做的多道菜套餐」（步骤有先后依赖），而传统调度像「每道菜都当外卖单独立跑」——HEXGEN 是懂菜谱的餐厅经理：先在全局把各桌订单均衡分配给不同灶台（GPU），再在每个灶台内部按「哪桌快凉了先做哪道」动态排序（本地优先级队列）。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. 输入：多租户 agentic Text-to-SQL 请求流 + 异构 GPU 集群画像；
  2. 关键操作：
     - **系统化分析**：先对 agentic Text-to-SQL 工作流的调用结构/时延特征做剖析，指导调度设计；
     - **分层调度器**：全局层做负载均衡的任务派发（把各请求的推理调用分到合适的引擎/GPU）；本地层用自适应优先级队列在实例内部决定先执行哪个调用（照顾依赖与截止时间）；
     - **轻量仿真调参**：用模拟器（simulation-based）自动调关键调度超参（如 alpha），提升对不同负载的鲁棒性与适应性；
  3. 输出：满足 SLO 的低尾延迟、高吞吐调度决策。
- **形式化要点**：🔧 工作流 DAG 形式化、优先级函数与全局派发的优化目标（SLO 违约最小化）定义查原文后补。
- **理论性质**：系统论文，无理论证明类声明；贡献在调度机制与仿真调参方法。

## 4. 实验结论（概览）

- **对比基线**：SOTA LLM 服务框架（摘要称 "state-of-the-art LLM serving frameworks"；🔧 具体名单——vLLM 类、之前工作 HexGen 等——查原文）。
- **数据集/负载**：真实 Text-to-SQL 基准 + 多种请求 trace（仓库提供 trace3 等输入示例）。
- **指标**：P95 尾延迟、端到端吞吐、SLO 违约率。
- **结论方向**（摘要明示，数字可直接引用）：
  1. 所有 trace 上 **P95 尾延迟降低 1.42~1.56×**；
  2. **吞吐提升 1.49~1.81×**；
  3. 在多样负载下收益一致。
- 🔧 消融（分层调度各组件贡献、alpha 调参敏感性）与不同 GPU 配置的细分数字查原文后补。

## 5. 开源代码与动手实践

- 仓库地址：https://github.com/relaxed-system-lab/hexgen-flow （官方）
- 语言：Python 3.8+（模拟器：`simulator/`，含 `cli / core / internal / profiler / ui` 模块）。
- 典型流程（教学示意，以 README 为准）：
  1. `pip install -r simulator/requirements.txt`；
  2. 运行 `python simulator/cli/start_simulator.py --input ./simulator/cli/input_file_trace3.json --n-engines 4 --arrival-rate 1.0 --trace-output ./result/trace_output.json --stats-output ./result/stats_output.json`；
  3. 关键参数：`--n-engines`（引擎/模型实例数）、`--arrival-rate`（请求到达率）、`--SLO`（服务水平目标）、`--alpha`（优化引擎参数）；
  4. 输出 trace 与逐请求延迟统计，可用于分析调度行为；仓库近期还加入了新 trace 与 baseline。
- 许可与资源提醒：仓库未见 LICENSE 文件 🔧；模拟器无需真实 GPU，适合纯 CPU 复现调度实验；注意其基于 ETH EASL Scratchpad 代码（README 致谢），遵守上游许可。

## 7. 2026 视角（🔧）

- 「Agent 工作流感知的 LLM 服务系统」是 2025-2026 系统方向的热点：负载从「单请求」变成「有依赖的调用 DAG」，调度对象从 token 变成工作流阶段；HEXGEN-FLOW 是该潮流中 Text-to-SQL 场景的代表工作。
- 工业界方向：企业 ChatBI/数据智能体平台需要这类调度层（多租户 SLO 保障）；通用 LLM 服务框架（vLLM 系）也在逐步吸收工作流感知能力（🔧 一般性判断）。
