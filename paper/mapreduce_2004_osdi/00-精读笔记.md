## 一、背景与它回应的问题

### 1.1 时代前提：专家稀缺，而"在千台机器上跑计算"人人在即

2004 年前后的现实（论文 §1 的抱怨）：数据在涨（TB 级成为常态）、机器在便宜（上千台双路 Xeon + 本地盘的廉价机群，即 GFS 服务的负载底座），但**每个分布式计算都要工程师手工处理分片、调度、机器失败、数据分发、网络与负载均衡**——门槛高到只有少数专家能写，且错误百出。同期业界的学术答案是网格计算/面向服务的编程模型（Globus 等），Google 内部的实践答案是从 Tangram（网页索引流水线的分层数据并行系统）演化出的"map/reduce 两函数 + 自动容错调度"。论文的问题因此是：**能不能把"分布式"从用户的编程模型里整体抹掉，只留两个函数？**

### 1.2 答案一句话

把"大规模可并行化"且"用户已经会写"的**函数式计算模式**（映射 + 归并到按 key 分组的可迭代值集）抽成接口：`map(k1,v1)→list(k2,v2)`、`reduce(k2, list(v2))→list(v2)`；框架负责切分输入、副本/本地性调度、按 key 分组排序的 shuffle、至少一次执行与故障恢复、结果提交。中间 key 有序这一不变式，让 join/merge/排序类算法可以用几十行代码表达。

### 1.3 与 GFS 的因果闭环（读本篇的前置）

本框架的容错合同——任务**至少执行一次**、输出可追加可重复——直接继承自 GFS 的 at-least-once 追加语义与"记录级去重"合同（精读笔记见 [`../doi_10.1145_945445.945450/00-精读笔记.md`](../doi_10.1145_945445.945450/00-精读笔记.md) §2.5）。GFS 在 2003 年把"精确一次"甩给应用层，MapReduce 在 2004 年给出了应用层最优雅的消化方式：**确定性函数 + 中间结果按任务隔离 + 最终结果临时文件+原子改名发布**。两篇必须对读：没有 GFS 的宽松合同，就没有 MapReduce 的重执行自由；没有 MapReduce 这个"第一个孩子"，GFS 的合同看起来就只是推卸责任。

## 二、核心设计精读

### 2.1 执行全景（ASCII，论文 §2.3 的复述）

```
 输入(存放在 GFS, 如 gfs:///wc/input/*)
      │ 逻辑切分为 input split(默认 16~64MB/个)
      ▼
 ┌──────────── Master ────────────┐
 │ 任务状态机: M 个 map × R 个     │  空闲 worker 心跳领任务;
 │ reduce 各为一份工作;超时/宕机    │  记录哪个 worker 在跑哪个任务、
 │ →回收→在新 worker 上重做         │  中间文件位置清单
 └───┬────────────────────────┬───┘
     │派 map 任务(优先数据所在机器)│派 reduce 任务
     ▼                         ▼
 worker: 读 GFS 分片        worker: 从各 map worker 机器"拉取"
   → 跑 map 函数              属于本 reduce 分区的中间文件
   → 中间 key-value 先写       → 按 key 归并排序
     内存环形缓冲               → 跑 reduce 函数
   → 溢写磁盘, 按 R 分区        → 输出追加写临时 GFS 文件
     (每个 reduce 一份)        全部完成后: 临时文件 → 最终路径
 master 把中间文件位置清单       原子 rename 发布(提交点!)
   告知 reduce worker
 不变式: ①reduce 看到的 key 全局有序 ②同一 map 输出按分区连续存放
        ③任何任务都可能被执行 ≥1 次,但输出只有一份"正式"版本
```

### 2.2 接口与不变式：赢在"受限通信"（论文 §2.1–2.2）

- 一切都是 `<key, value>` 二元组（字符串对，具体解释交给用户函数），天然可序列化、可落盘、可分区——**接口没有任何共享内存假设**。
- 三条框架承诺的不变式：(1) map 输出按中间 key 分区（默认 `hash(key) mod R`，用户可换 partitioner），(2) 分区内**按 key 排序后分组**交给 reduce（`list(v2)` 按 key 字典序逐 key 给出），(3) reduce 输出落 GFS。排序+分组是论文最被低估的一笔：**它把"聚合"从需要用户自管理的哈希表，变成了可外部排序归并的顺序 IO 问题**——TB 级聚合因此不可能 OOM。
- 惯用法（§2.5）：分布式 grep、词频、倒排索引构建、**分布式 merge/排序**（用"确定性的二分采样近似分位点"实现 range partitioner——这是 §3.2 接口增强里 combininer/sorter 之外最有工程味道的细节）、倒排归并求文档相似度（canopy 聚类）、PageRank 式矩阵计算。

### 2.3 容错：把 GFS 的合同兑现成工程（论文 §2.4/§2.6）

```
任务状态机(map 与 reduce 同构, master 内存维护):
  waiting → inprogress(worker 领走, 记 worker+时间戳)
  inprogress --worker 心跳超时/崩溃--> waiting(重派; 旧输出作废)
  inprogress --worker 报完成--> done(记录其本地中间文件位置)

关键点:
  map worker 死 → 它产出的本地磁盘中间文件随机器一起没,
    这些 map 任务必须重做(新机器上); 已完成的 reduce 若已拉走旧输出
    不受影响? 不受影响, 因为拉取按"当前 done 任务清单"进行
  reduce worker 死 → 无中间产物, 直接重跑;
  最终一致性来源: 用户函数被假定"对输入是确定性的",
    重跑同一任务得到同一输出; 提交靠 rename 原子化 →
    外部观察者永远只看到一套自洽输出 —— "大事务"错觉
```

"至少一次 + 确定性 + 原子发布"三者合取，才得到用户视角的"恰好一次"——这个论证结构在今天的流式系统（Kafka/K8s 控制器）里仍是标准配方。对照课程笔记 [`../../courses/并行与分布式系统/MIT6.824/notes/L16-Kafka分布式日志.md`](../../courses/并行与分布式系统/MIT6.824/notes/L16-Kafka分布式日志.md)。

### 2.4 §4 核心论证：为什么函数式抽象赢过"共享状态 + 锁/事务"方案

论文 §4（*Why is this functional?*）是全文思想浓度最高的一章，值得完整复述其论证结构：

1. **备选的"自然"设计**：暴露一个受锁或事务保护的**分布式可变数据结构**（论文点名 Linda 式元组空间一类），worker 在其中读写。这看似更"通用"。
2. **为什么它输**：(a) 它把分布式环境的非确定性、并发交错、故障中断路径**原样暴露给应用开发者**——"调试一个非确定的、分布式的、并行的程序，远比调试一个确定的、顺序的程序困难"（§4 要义，此处为转述）；(b) 通用协调（分布式锁/2PC）在千台机群上的可扩展性与成本都很差；(c) 最关键的：**框架一旦允许任务通过共享可变状态通信，就无法合法地重排、复制、重做任务——自动并行与自动容错的自由度被用户代码没收了**。
3. **为什么函数式约束赢**：map/reduce 只能"从参数读、向输出追加"，通信被限制在单向数据流里 → 任务之间**无副作用、可交换、可复制** → 框架获得三项完全自由：任意顺序调度、任意次数重做（容错）、任意数量冗余执行（对付 straggler）。抽象的"表达力损失"恰好等于"调度自由度的收益"——这是分布式系统设计史上一次干净的"约束即能力"演示。
4. **与数据库/事务方案的对照**（§7 与 §4 的呼应）：并行数据库用"查询语言 + 内部调度"达到类似效果，但 2004 年时它的可扩展性受限于 scale-up 硬件与全量依赖商用许可；MapReduce 的"命令式两函数 + 自有机群"在当时反而覆盖了更广的人群与负载（论文自认的边界也在这里：**延迟敏感、迭代式、细粒度状态的负载不属于这个抽象**，§8 的展望被 Spark 等后来者兑现，见课程笔记 [`../../courses/并行与分布式系统/MIT6.824/notes/L17-Spark与RDD.md`](../../courses/并行与分布式系统/MIT6.824/notes/L17-Spark与RDD.md)）。

### 2.5 straggler 与 backup tasks、本地性调度（论文 §3.1）

**本地性调度（locality-aware scheduling）**：每个输入分片在 GFS 里有 3 副本 → master 优先把 map 任务派给**持有副本的那台机器**（退而求其次：同机架机器），使"读"不发生跨网络（数据不动、代码动）。reduce 侧无本地性可言（输入来自所有 map 机器），论文对此坦承。这是"移动计算而非移动数据"论断的第一次大规模工程落笔。

**straggler 与备份执行（backup execution）**：即便没有故障，机群也总有慢任务（磁盘降级、邻居干扰、后台服务抢占）——一个掉队的 reduce 能把小时级作业拖成小时级加零头。论文 §3.1 的方案是**在最后阶段对剩余少量任务做冗余调度**：

```
master 监控每个 inprogress 任务的进度曲线
  if 进入收尾阶段 and 剩余未完成任务数 <= K and 该任务跑得太慢:
      再派一份相同任务给别的 worker(原任务不取消)
  先完成者生效(结果按"任务"而非"执行"索引, 后者自然作废)
  代价: 少量多余算力; 收益: 整个作业的尾延迟被砍掉
```

配套手段还有：**动态负载均衡**（M、R 远大于 worker 数，master 维持任务队列，空闲 worker 来领，天然把快机器喂饱）、**空闲超时参数**、以及把 R 取 2 的幂以便"mod 分区"与后续子作业共享分区方案。M 的经验值：让"分片大小 ≈ 一个块的大小"，与 GFS 的 64MB chunk 呼应——**分片是逻辑的，副本放置是 GFS 的，两层各管各的粒度**。

### 2.6 接口增强与协调的备选实现（论文 §3.2/§2.7）

- **combiner（合并器）**：在 map 侧先做一次局部 reduce 再进 shuffle，纯为削减网络/磁盘流量；使用合同是函数可交换可结合（§3.2 明说这是"优化而非语义"，语义正确性由用户保证——本课程思考题 4 的陷阱源）。
- **可插拔的 partitioner / comparator / sorter**：分区函数（如分布式 merge 用采样分位点做 range 分区）、key 比较器、以及"进入 reduce 前是否排序"都可配置；**input/output reader-writer 抽象**把"GFS 文件"泛化成任意按 record 切分的东西（DB、GFS、压缩流），这一层就是后来 Hadoop InputFormat 的祖先。
- **分布式缓存式便利**（§3.2）：为 map 任务广播只读大表（倒排词典/黑名单）的机制，本质是"把 broadcast 变量外包给 GFS 读"。
- **§2.7 备选实现**：论文展示过一种"文件系统即协调服务"的替代栈——master 数据结构表现为 GFS 命名文件，worker 通过创建带租约超时的文件获得互斥（利用 GFS 的原子 create/rename），以文件交换代替 RPC。作者以此说明框架对 RPC 并无硬依赖，也**第一次把"存储原语可以升格为共识原语"写进正文**（对照 Chubby 论文 2006/2007，课程 L12 笔记 [`../../courses/并行与分布式系统/MIT6.824/notes/L12-ZooKeeper与ZAB.md`](../../courses/并行与分布式系统/MIT6.824/notes/L12-ZooKeeper与ZAB.md)）；生产实现仍选内存 master + 重启恢复，因为 master 状态可从任务状态机廉价重建。

### 2.7 一次作业的生命周期解剖（串起全部机制）

以"对 GFS 目录下一万个 100MB 日志文件做词频"为例，按论文各章机制端到端走一遍（流程为论文机制的合成复述，非原文示例）：

```
1. 用户注册 MapF/ReduceF, 指定输入目录/M/R → 提交给 master
2. master 枚举文件(经 GFS), 按 16~64MB 切 split → M=约 6.4 万个 map 任务
   全部入 waiting 队列; R 取 2 的幂(如 4096)
3. 1 千台 worker 各自心跳领任务: master 查该 split 的 GFS 副本位置,
   优先把任务派回持有副本的机器(本地性), 记 inprogress
4. worker 流式读 split → 跑 MapF → 中间对进内存环形缓冲 →
   溢写本地盘并按 hash(key) mod 4096 分成 4096 份(各自内排)
5. 某 worker 宕机: 心跳超时 → 其 inprogress map 任务回到 waiting,
   在别的机器重做(旧本地输出随机器陪葬, 无需清理)
6. 全部 map done → master 把"每个 reduce 分区在哪些机器哪些文件"
   的清单发给 reduce worker → 拉取+多路归并(按 key 有序)
7. 收尾阶段剩 3 个 reduce 迟迟不完: master 触发 backup execution,
   冗余重跑, 先完成者定结果
8. 每个 reduce: 写临时 GFS 文件(追加) → 自己完成后 rename 到最终目录
   → master 全部 done 后向用户报告 "作业提交"
9. 用户下次全表扫描: 重复执行过的任务不会产生重复词
   —— 因为 MapF 确定性、中间文件按任务隔离、最终输出 rename 单版本
```

第 3、5、7、9 步分别就是本地性、至少一次、straggler、正确性合同四大主题的"现场显影"；把它和 p1_mapreduce 项目 README 的概念映射表并排看，等于做了一次论文→代码的同态验证。

## 三、实验与工程取舍

论文 §6.2 的性能测量是在真实生产机群上的作业解剖，而非第三方基准（以下**具体刻度未逐字复核，一律定性表述**）：

1. **排序 1TB**（§6.2.1 场景）：约 1800 台双路 Xeon 级机器、数千 map 任务 + 上千 reduce 任务，总耗时数十小时量级。论文的结论性观察：瓶颈在**磁盘与网络的持续传输带宽**，master 调度 RPC 与任务启动开销只占极小比例——"框架税"低到可忽略，这在当时是对"抽象必有性能损失"质疑的正面回应。
2. **字符串处理/计数作业**（§6.2.2 场景）：数十亿 URL 计数类作业，扩展性观察为"机器数增加时吞吐近线性"，同样说明调度非瓶颈。
3. **生产规模自述**：§5 称系统支撑 Google 每日数千个作业的常态运行（数量级为论文行文口径，未复核）。

深层取舍清单：

| 取舍 | 选择了 | 放弃了 | 换来的 |
|---|---|---|---|
| 编程模型 | 两个纯函数 + key-value 流 | 共享状态/任意协调的通用性 | 自动并行、自动容错、非专家可用 |
| 执行语义 | 至少一次重做 | 精确一次(交给确定性+原子发布伪装) | 无分布式事务的任务回收/重派 |
| shuffle | 全量物化中间结果到磁盘 | 流水线低延迟 | 容错简单(任一点可重放)、超 TB 聚合不爆内存 |
| 调度 | 本地性优先 + 拉取式 shuffle | 推送式的最优带宽利用 | 异构/落后机器自适应、读侧背压天然 |
| 尾延迟 | backup tasks 冗余执行 | 算力(重跑) | 作业 makespan 可控 |
| 提交 | 临时文件 + rename 原子发布 | 细粒度流式可见性 | "整个作业像一个大事务"的用户心智 |
| 分片 | 16–64MB 逻辑 split | 小作业低延迟 | 与 GFS 64MB chunk 对齐的批量流式 IO |

## 四、与相关工作对比

- **vs GFS（同批精读：[`../doi_10.1145_945445.945450/00-精读笔记.md`](../doi_10.1145_945445.945450/00-精读笔记.md)）**：上下游共生。GFS 提供"大 chunk + at-least-once 追加 + 原子 rename"合同，MapReduce 是兑现合同的第一应用；反过来 MapReduce 的本地性调度读的是 GFS 的副本位置视图。**先读 GFS §3 再读本篇 §2.4，因果链才完整。**
- **vs Tangram / 早期数据并行系统**（§7）：Tangram 已用分层 map/reduce 式抽象构建 Google 索引流水线，但局限在"索引构建"单一领域、接口更复杂；MapReduce 的贡献是把这套模式**去领域化**成两函数通用接口并给出全栈实现与测量。
- **vs 并行数据库 / SQL 扩展**（§4、§7）：同目标（屏蔽分布式的声明式/半声明式抽象），差异在依赖与边界：数据库依赖查询优化器与封闭 schema，扩展上限受制于 scale-up；MapReduce 以"命令式函数 + 无 schema"换水平扩展与工程简单，代价是把关系代数该做的事（join 策略、聚合下推）全部手工化或后交给 Pig/Spark SQL。
- **vs Linda/元组空间类"共享状态"方案**（§4 直接对比对象）：见 §2.4 的完整论证——**可重排/可重做性是本篇与 §4 的分水岭**，也是"函数式抽象为何赢"的一句话答案。
- **vs Spark/RDD（课程 L17/L18 笔记：[`../../courses/并行与分布式系统/MIT6.824/notes/L17-Spark与RDD.md`](../../courses/并行与分布式系统/MIT6.824/notes/L17-Spark与RDD.md)、[`../../courses/并行与分布式系统/MIT6.824/notes/L18-数据并行谱系.md`](../../courses/并行与分布式系统/MIT6.824/notes/L18-数据并行谱系.md)）**：Spark 保留"受限通信 ⇒ 可重做"的元定理，只把"每阶段物化磁盘"换成"血缘重建内存 RDD"——本篇 §3.2 展望的"迭代负载用内存共享中间输出"正是 Spark 的立项陈述。
- **vs Dremel/BigQuery（本仓库 [Dremel 精读](../doi_10.14778_1920841.1920886/00-精读笔记.md)）**：MapReduce 是批式容错的" throughput 抽象"，Dremel 是交互式的扇出-聚合树——二者共享 GFS/Colossus 底座，分别定义"分析"与"加工"两半；Snowflake/Delta 谱系（本仓库同目录笔记）则把本篇的"批正确性配方"移植进 ACID 表语义。
- **课程谱系**：L02 讲义与课堂讨论见 [`../../courses/并行与分布式系统/MIT6.824/notes/L02-MapReduce.md`](../../courses/并行与分布式系统/MIT6.824/notes/L02-MapReduce.md)；全课程论文定位表见 [`../../courses/并行与分布式系统/MIT6.824/papers/papers.md`](../../courses/并行与分布式系统/MIT6.824/papers/papers.md)；课程书目总笔记 [`../../book/MIT%206.824%20Distributed%20Systems.md`](../../book/MIT%206.824%20Distributed%20Systems.md)。

## 五、关键术语中英对照

| 英文 | 中文 | 一句话含义 |
|---|---|---|
| map function | 映射函数 | k1,v1→中间 k2,v2 列表, 无共享状态 |
| reduce function | 归约函数 | 对同一 key 的值集做聚合 |

| intermediate key-value | 中间键值 | 按 hash(key) 分区并排序的 shuffle 单元 |
| partitioner | 分区器 | key→reduce 编号, 可自定义(range 分区等) |
| shuffle | 洗牌 | 按 key 重分布: map 落盘、reduce 拉取+归并 |
| combiner | 合并器(局部 reduce) | map 侧预聚合, 削减 shuffle 流量 |

| backup task | 备份任务 | 收尾阶段对慢任务的冗余重执行 |

## 六、批判与延伸

**批判性阅读：**

1. **"简单"是对谁的简单**：两函数抹掉了分布式调度，但抹不掉数据倾斜、爆炸中间输出、组合器语义陷阱（reduce 函数必须可结合可交换才能当 combiner 用）；工程经验全部回流到"如何设计 key"这一新玄学。论文对此的坦诚度不高（§8 才顺带提及负载形态依赖）。
2. **全量落盘是时代妥协**：为容错与超内存聚合付出的代价，在迭代式负载（ML）上被放大成百倍级的 IO 浪费——Spark 对本文的直接修正；读本文时应把"物化即容错"理解为 2004 年内存/网络价格下的解，不是逻辑必然。
3. **确定性假设是隐性合同**：at-least-once + 重做安全的前提是用户函数确定（无随机、无外部可变读取）；论文把这点写得轻描淡写，实践中"带随机数/带墙上时钟的 map 静默破坏正确性"是 Hadoop 时代的经典事故。对照 GFS 笔记 §六之 2（合同转嫁生态）。
4. **backup tasks 的参数是拍的**：§3.1 承认冗余执行的触发阈值与范围由经验设定，无理论刻画——后来 Dremel/Spark 对尾延迟的治理（更快失败、谱系重建）说明这不是终点。
5. **评测的不可复现性**：全部数字来自 Google 私有负载与私有栈（GFS/Borg），外部世界通过 Hadoop 复刻时踩到的坑（小文件、HDFS rename 成本、本地性在容器化后失效）不在论文射程内；读作"该架构在 Google 形态下成立"。

**延伸：**

- **谱系阅读**：GFS 笔记（合同制定）→ 本篇（合同兑现）→ 课程 L17/L18（内存化修正）→ 仓库 [`../doi_10.14778_1920841.1920886/00-精读笔记.md`](../doi_10.14778_1920841.1920886/00-精读笔记.md)（交互式对照）；"约束即能力"论证在 Raft 笔记（[`../../courses/并行与分布式系统/MIT6.824/notes/L05-Raft一-选举与日志复制.md`](../../courses/并行与分布式系统/MIT6.824/notes/L05-Raft一-选举与日志复制.md)）里以另一种形态复现（限制时钟/成员变更假设，换取协议可证）。
- **动手对照**：本仓库已实现课程项目 [`../../courses/并行与分布式系统/MIT6.824/projects/p1_mapreduce/`](../../courses/并行与分布式系统/MIT6.824/projects/p1_mapreduce/)（Go，进程内 master/worker 模拟；README 的"概念↔代码"映射表把 §2 master 任务状态机、§2.4 心跳超时重做、§3.1 备份任务、§2.4 幂等发布 rename 逐一落到 `mapreduce/master.go`/`worker.go`/`rpc.go`），**读完论文按其映射表走查源码是本篇笔记推荐的实验环节**。
- 论文 §8 的预言（更丰富的原语、迭代负载内存共享、多级 MapReduce）几乎逐条兑现于后续工业系统，可当"路线图级论文"的范本：它的准确不是数字准确，而是**边界的准确**。

## 七、一页总结（复习卡）

- **问题**：让非分布式专家也能安全地把计算摊到上千台机器上，且框架能自由调度与重做。
- **方案**：map/reduce 两纯函数 + key-value 流；输入分片对齐 GFS 块；master 任务状态机 + 心跳超时重派；at-least-once + 确定性 + 临时文件 rename 原子发布；本地性调度 + 拉取式 shuffle + 动态负载均衡 + 收尾 backup tasks；§4 以"受限通信⇒可重排可重做"完成对锁/事务方案的论证性击杀。
- **所得**：编程模型降到两人时；千台机群容错常态化；"移动计算不移动数据"工程落地；尾延迟有了第一个主流解。
- **所欠**：迭代/低延迟负载、倾斜治理、确定性假设的文档化、备份参数理论、可复现评测。
- **地位**：与 GFS（存储合同）、Bigtable（行级收紧）构成 Google 三件套；Hadoop/Spark/数据流系统全是它的子孙与修正；数据并行工业化元年（L02）的命名文本。

## 九、思考题（5 道）

1. §4 的论证可否倒过来读：如果框架提供"每任务独占写一个 GFS 文件 + 全局可见"的**文件系统即协调服务**模型（§2.7 的备选实现思路），这算共享可变状态还是无副作用通信？请用它实现一个分布式 Top-K，并判断它是否还能合法地重做任务。
2. 备份执行（backup task）与 GFS 的 at-least-once 追加在语义上同构：都靠"确定性 + 去重/原子发布"消化重复。请分别写出：map 任务被冗余执行时中间结果为什么不会互相污染（提示：中间文件按任务索引 + reduce 拉取时机）？reduce 被冗余执行时最终输出为什么只有一份（提示：rename 的原子性与后到者覆写谁）？
3. 本地性调度假设"数据在本地磁盘副本"，而今天的云上对象存储（S3）不提供"哪台机器有副本"的视图（对照 Snowflake 笔记：计算节点对数据无所有权）。请论证：MapReduce 的哪一半（容错/调度/ shuffle）在对象存储上依然成立，哪一半必须被重新设计？
4. combiner 是一个可交换、可结合的"局部 reduce"。若用户把一个不满足交换律的 reduce 函数当 combiner 挂上去，系统会在什么输入/故障交错下给出错误结果？请构造一个两分区 + 一次重执行的反例，并说明为什么类型系统救不了这个合同。
5. 论文把 M、R 的选择留给用户（R 建议 2 的幂便于取模分区），且 map 全部完成是 reduce 开始的硬屏障。请从"屏障 = 容错边界"的角度解释：为什么本篇宁可让 reduce 等待也不与 map 重叠？Spark 的 stage/血缘机制在什么意义上只是把这个屏障挪到了"窄依赖边界"上？

## 十、阅读方法与常见误读提醒

1. **别把 §4 读成"函数式优于命令式"的语言之争**：争的是**通信拓扑**（共享可变状态 vs 单向数据流），不是语法。用命令式语言写 map 函数完全合法；用 Haskell 写一个读写共享元组空间的程序照样输。
2. **"MapReduce 慢"不是对本篇的反驳**：2004 年论文自我定位是吞吐与可用性，§8 已自认延迟/迭代短板。拿 Spark 的 benchmark 打它是年代错置；正确的批评姿势是"物化即容错"这一选择的代价结构（见取舍表）。
3. **at-least-once ≠ 用户最终看到重复**：作业级正确性靠确定性+原子发布伪装成 exactly-once；把"MapReduce 没有事务"与"MapReduce 会产出重复结果"混为一谈是课程讨论区高频错误（L02 笔记有对应辨析）。
4. **备份任务 ≠ 推测执行的全部**：backup task 只在收尾阶段触发且针对"剩余少数任务"；把 §3.1 与后来 Hadoop 的 `mapred.map.tasks.speculative.execution` 默认全开划等号，是对原文的放大误读。
5. **DOI/版本陷阱**：引用时认准 OSDI 2004 PDF（USENIX 官网）；CACM 2008 重刊版与 2010 "flexible data processing tool" 版本措辞有异。ACM DL 的 10.5555 条目只是镜像记录，**不是**本文拥有 DOI 的证据（详见 §〇 与核实记录）。
6. **建议配套阅读顺序**：GFS 笔记 §2.5 → 本篇 §2.4 → §4 → §3.1 → p1_mapreduce 源码走查；最后读 L18 数据并行谱系把"为什么它赢过锁方案"放进二十年的长河里复核。
