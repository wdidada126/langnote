## 一句话总结
现代数据库引擎要同时藏好"内存访问、I/O、同步"多种时延来源才能打满 CPU；MosaicDB 用无栈协程（stackless coroutines）+ 精心设计的调度策略，在一个已经藏好内存时延的 OLTP 引擎里进一步藏好 I/O 与同步时延，且不让纯内存负载变慢；配合"协程—事务"范式避免超订阅、降低争用，最高比此前 SOTA 快 33 倍。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：**时延隐藏（latency hiding）**——现代 OLTP 引擎里，CPU 大量时间花在"等数据"（cache miss、SSD I/O、锁同步）而不是真算。把"等"和"算"重叠起来，让 CPU 总在干正事，就能提吞吐。
- **为什么难**：现有系统大多只藏单一时延（如用预取藏 cache miss），缺对"内存 + I/O + 同步"多种时延的联合优化；且大库超出内存时，批调度会出"掉队者（straggler）"拖慢整体。
- **几类主流解法**：

| 路线 | 代表 | 直觉 |
|------|------|------|
| 软件预取藏内存时延 | CoroBase（协程+预取） | 用协程重叠计算与取数，藏 cache miss |
| 批调度 | 传统 batch | 一批事务一起跑，仅适合纯内存 |
| 本文：协程+双队列流水线 | MosaicDB | 联合藏内存/I/O/同步，流水线调度避免掉队 |

- **本文属哪类**：**系统**论文，OLTP 引擎的时延隐藏协同设计；是 CoroBase（VLDB 2021）的扩展。
- **关键名词直觉**：
  - **latency hiding（时延隐藏）**：用异步预取/协程，让"等数据"和"算别的"并行，减少空等。
  - **stackless coroutine（无栈协程）**：轻量上下文切换原语，让一个线程跑很多事务的"小步"，挂起/恢复代价极低。
  - **coroutine-to-transaction（协程—事务）**：把每个事务包成一个协程，调度器在协程间切换以重叠 I/O 与计算。
  - **dual-queue pipelined scheduling（双队列流水线调度）**：把"内存受限"和"存储受限"事务分开排队，长流水线喂满存储后端、又控预取距离。

## 1. 问题背景与动机
- 前人工作简述：CoroBase 等用协程+软件预取藏好纯内存 OLTP 的 cache miss；但只解决内存时延。
- 前人缺陷/未解决问题（逐条）：
  1. **只藏单一时延**：现有系统仅缓解个别时延（如内存），缺多时延联合优化。
  2. **批调度在混合负载失效**：超出内存时，事务 profiles 不再相似，批内出现掉队者，吞吐下降。
  3. **易超订阅/争用**：多线程铺满事务会超订阅、增加锁争用。

## 2. 核心方法
- **最直观类比**：像餐厅后厨——CoroBase 让"切菜等食材"和"炒别的菜"重叠；MosaicDB 进一步把"等冰柜取货（I/O）""等传菜窗口（同步）"也一起排进流水线，并且不让纯内存快菜被慢菜拖死。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：一个含内存表+SSD 冷表的 OLTP 引擎与事务流。
  2. **无栈协程**：用 stackless coroutines 把事务拆成可挂起/恢复的小步。
  3. **双队列流水线调度**：内存受限事务进热队列、存储受限事务进冷队列，长流水线喂满存储带宽、同时控制预取距离。
  4. **协程—事务范式**：避免超订阅、降低争用。
  - 输出：在混合（内存+存储）负载下高吞吐、且不拖累纯内存负载的 OLTP 引擎。
- **形式化要点**：核心是"协程 + 双队列流水线调度"协同藏多类时延；超参数含流水线长度、队列阈值（🔧 以正文为准）。
- **理论性质/保证**：无形式化最优性保证；靠实验证明目标达成且最高 33× 加速。

## 4. 实验结论（概览）
- 对比基线：此前 SOTA OLTP 引擎（含 CoroBase 类）。
- 数据集/负载：内存 resident 与超内存（含 SSD I/O）混合负载、只读/读写等。
- 指标：吞吐（事务/秒）、延迟。
- 结论方向（摘要/演讲稿已核实数字）：MosaicDB 达成多时延联合隐藏且纯内存负载不退化；最高比此前 SOTA **快 33×**（只读、40 线程场景报告）。
