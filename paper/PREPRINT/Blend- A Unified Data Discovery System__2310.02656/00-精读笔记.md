## 一句话总结

数据发现（在数据湖里自动找出"哪两个表可以 join、哪些列相关、哪些内容可以合并"）此前是一个算子一个系统、一个任务一套索引。BLEND 把 join/相关性/union 发现统一成**一组低层算子**，配**统一索引结构**与**基于规则的优化器**（能自动把 SQL 重写成算子流水线），让任意发现任务像搭积木一样组合，运行时也更快。

## 0. 给新手的阅读前置（背景知识地图）

- **大问题**：数据湖里堆着成百上千张"野"表。想用它们之前必须先"发现"：谁和谁能 join（Joinable）、哪两列数值上相关（Correlatable）、哪些列内容同域可合并（Unionable）。这就是 Data Discovery。
- **为什么难**：
  1. 三类发现各自的搜索空间都是组合爆炸；
  2. 每类发现都有自己的专用索引，任务一组合索引就打架；
  3. 真实任务是复合的（先 union 再 join 再算相关），ad-hoc 拼接又慢又难维护。
- **主流做法对比**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 专用单算子系统 | LSH Ensemble（union）、lshensemble/join 类各自系统 | 一任务一系统 | 单点强；组合弱 |
| 端到端流水线 | ad-hoc 脚本 | 手工串联 | 灵活；无优化、慢 |
| 统一算子框架 | **BLEND（本文）** | 低层算子+统一索引+规则优化器 | 组合自由且高效（本文） |

- **本文属于哪类**：第三类——数据发现领域的"查询引擎化"。
- **必须先懂的名词**：
  - **Joinable**：两表存在可 join 的列对（值域重叠、语义对应）。
  - **Unionable**：两列同域同语义，可以纵向合并（schema 变体的列）。
  - **Correlatable**：两列数值上存在（统计）相关关系。

## 1. 问题背景与动机

- 前人工作：数据发现研究各自打磨单个算子（join 发现、相关性发现、union 发现），各有配套索引。
- 未解决的问题：
  1. 真实任务需要**多算子组合**及其索引协同，现有系统做不到；
  2. 复合发现流水线运行时间长，缺少统一的执行优化层。

## 2. 核心方法

- 类比：以前"查户口、查婚姻、查征信"各去一个衙门各带一套检索工具；BLEND 把这些业务拆成同一套"底层档案检索积木"，配一个统一档案库（统一索引）和一个懂规则的调度员（优化器），复杂查询自动拆解成积木组合，工具不再重复造。
- 具体做法（输入 → 操作 → 输出）：
  1. **低层算子集**：把各类发现分解为一组基础算子，作为复杂用户任务的积木（算子清单 🔧 见原文）；
  2. **统一索引结构**：一个索引服务多个发现算子，避免每算子一套索引；
  3. **规则优化器**：尽可能把 SQL 表达的发现请求**重写**为低层算子流水线，缩短执行时间；
  4. 输出：支持任意发现任务灵活流水线组合的系统 BLEND。
- 性质：相比 ad-hoc 流水线与单点方案，灵活性与效率俱优（摘要口径）。

## 3. 变体 / 工程版
