## 一句话总结
用强化学习微调 LLM 做 Text-to-SQL 时，奖励要么靠真跑 SQL（数据库反复调用，太慢），要么靠 LLM 打分模型（显存开销大）；本文把 SQL 转成图、用图匹配算奖励（GMNScore），全程不碰数据库也不占大显存，再加一个对 CTE 子查询逐步打分的 StepRTM，在 Spider 和 BIRD 上稳定超过已有奖励方案。

## 0. 给新手的阅读前置（背景知识地图）

大问题：RL 已成提升 LLM Text-to-SQL 能力的主流手段（类似 RLHF/RLVR 的套路），而 RL 的命脉是奖励信号——奖励准，模型学得对；奖励贵，训练就跑不动。

为什么难：Text-to-SQL 最「诚实」的奖励是真执行生成的 SQL 与金标准结果比对，但 RL 训练一个 batch 要对成百上千个候选 SQL 反复查库，延迟巨大；改用 LLM 充当裁判（Bradley-Terry 奖励模型）又要把大模型常驻 GPU，显存和推理开销都吃不消。

主流解法分类：
| 类别 | 思路 | 代价 |
|------|------|------|
| 执行奖励（execution-based） | 真跑 SQL 比对结果 | 最准，但延迟高 |
| LLM 奖励模型（Bradley-Terry） | 用 LLM 打分 | 免执行，但 GPU 显存开销大 |
| 图匹配奖励（本文） | SQL 转图 + 图匹配算相似度 | 免执行、显存开销小 |
| 过程奖励（process reward） | 对推理中间步骤打分 | 需要设计步骤监督（本文 StepRTM 属此类变体） |

本文属哪类：结果奖励用图匹配（免执行）+ 步骤奖励监督 CTE 子查询的组合。

关键名词直觉解释：
- Outcome reward / Stepwise reward：结果奖励只看最终 SQL 好不好；步骤奖励还看中间推理/子查询每步对不对——后者监督信号更密。
- CTE（Common Table Expression）：SQL 里的 `WITH ... AS (...)` 子句，把复杂查询拆成命名的中间子查询，天然是「步骤」的载体。
- 图匹配（graph matching）：把 SQL 解析成结构图（节点=表/列/操作符，边=依赖/作用关系），两张 SQL 的相似度变成两个图的匹配程度——结构对了才算对，不依赖具体文本措辞。

## 1. 问题背景与动机
- 前人工作简述：RL 提升 LLM Text-to-SQL 已被广泛采用；奖励设计两条主线：执行式比对（如以执行结果一致性为 reward）与 LLM 裁判式（Bradley-Terry 偏好模型）。
- 前人缺陷（逐条）：
  1. 执行奖励延迟高：RL 循环中反复调用数据库执行候选 SQL，训练吞吐被数据库往返拖垮，难以扩展。
  2. LLM 裁判显存开销大：需要额外部署大模型奖励模型，GPU 显存与算力占用严重，同样阻碍 RL 管线规模化。
  3. 两类方法都只给终局信号，缺少对中间子查询的监督，模型「蒙对结果但过程混乱」时得不到纠正，SQL 可读性差。

## 2. 核心方法
- 最直观类比：以前判卷要么「真跑一遍程序看输出」（太慢），要么「请一位教授逐份审阅」（太贵）；本文改成「对照语法结构图打勾」——把标准答案和考生答案都画成语法树，两棵树长得像就给分，又快又便宜。
- 具体做法（输入→关键操作→输出）：
  - 输入：问题、金标准 SQL、策略模型生成的候选 SQL。
  - 关键操作：
    1. GMNScore（结果奖励）：将金标准 SQL 与候选 SQL 分别解析为图表示，计算图匹配得分作为 RL 的结果奖励——免执行、轻显存；
    2. StepRTM（步骤奖励）：对候选 SQL 中的 CTE 子查询逐步打分，提供中间监督，兼顾功能正确性与可读性；
    3. 将两者组合进 RL 训练循环，替代执行奖励 / LLM 裁判。
  - 输出：经过 RL 微调、Text-to-SQL 能力更强的 LLM。
- 形式化要点：奖励函数 = 图匹配度量（结构相似性）+ 步骤级奖励（CTE 子图与金标准对应子结构的匹配）；具体图构造规则与匹配算法见原论文 🔧。
- 理论性质：工程方法论文，无理论保证；价值主张是「奖励信号质量接近、成本大幅降低」。

## 3. 变体 / 工程版（如有）
- GMNScore 与 StepRTM 可解耦使用：只用结果奖励，或叠加步骤奖励；消融实验覆盖了组合方式。
- 图匹配奖励器本身轻量，可与不同 RL 算法/基座模型搭配 🔧 具体组合以论文实验为准。

## 4. 实验结论（概览）
- 对比基线：执行式奖励与 LLM-based Bradley-Terry 奖励模型等既有奖励方案。
- 数据集：Spider 与 BIRD（两大标准 Text-to-SQL 基准）。
- 指标：Text-to-SQL 准确率（Spider 的执行准确率/精确匹配、BIRD 的执行准确率 🔧 具体口径以论文为准），以及奖励计算的时间与显存开销。
- 结论方向（摘要原文）：在对比与消融实验中，本文奖励模型持续优于既有奖励模型；同时显著降低时间成本与 GPU 显存占用；StepRTM 额外带来正确性与可读性收益。

## 7. 2026 视角（🔧）
- RLVR（可验证奖励的 RL）是 2025-2026 年 LLM 后训练主旋律；Text-to-SQL 的奖励设计从「执行比对」向「结构化/免执行/混合奖励」分化，本文是免执行路线的代表之一。
- 工业训练管线关注奖励计算吞吐：图匹配、编译期校验、轻量执行沙箱（如 DuckDB 内存库）等低成本奖励形态都被探索；「奖励 hacking」（结构对但语义错）仍是免执行路线需持续防御的问题。
- Spider 已趋饱和，BIRD 及更贴近生产的基准成为 RL 训练与评测主战场。
