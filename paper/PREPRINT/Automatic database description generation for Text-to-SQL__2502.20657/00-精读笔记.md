## 一句话总结
当数据库没有现成的表/列说明时，论文用大模型做一套「双向」描述生成——先整体到局部、再局部回整体——自动写出易懂的库描述，在 BIRD 上让 SQL 准确率提升近 1 个百分点、达到人工描述约 37% 的水平。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：Text-to-SQL 中，表/列的自然语言描述（description）是连接「人话问题」和「数据库 schema」的桥梁。很多真实数据库只有冷冰冰的字段名（如 `cust_id`、`txn_amt`），没有说明，模型很难理解该查什么。
- 为什么难：
  1. 缺失普遍：生产库常缺注释，字段名缩写、歧义严重。
  2. 层级依赖：列的含义依赖所属表，表的含义依赖整个库的语义，单向生成易丢失上下文。
  3. 质量评估难：自动生成的描述到底「好不好用」需要下游 SQL 准确率来检验。
- 几类主流解法（表格）：

  | 流派 | 思路 | 代表 |
  |------|------|------|
  | 人工/规则写描述 | 专家手工注释或基于命名规则 | 传统做法 |
  | 检索/模板生成 | 从数据样本或外部知识生成说明 | 早期自动化 |
  | LLM 生成描述 | 用大模型理解 schema 并写出描述 | 本文（双向过程） |

- 本文属哪类：用 LLM 自动生成数据库描述以增强 Text-to-SQL，并提出 coarse-to-fine 与 fine-to-coarse 的双向流程。
- 2-3 个关键名词直觉解释：
  - 数据库描述（database description）：用自然语言写出的「这个库/表/列是干什么的」，喂给 Text-to-SQL 模型当上下文。
  - coarse-to-fine（粗到细）：先理解整个库，再到表，最后到列，自顶向下。
  - fine-to-coarse（细到粗）：先从列这一最细粒度理解，再回推表与库的整体语义，自底向上。

## 1. 问题背景与动机
- 前人工作简述：Text-to-SQL 研究多聚焦模型架构与 schema linking，但往往假设已有高质量的表/列描述；当描述缺失时性能下降，而人工补描述成本高。
- 前人缺陷 / 未解决问题（逐条）：
  1. 描述缺失场景被忽视：多数方法依赖显式描述，缺描述时 bridging 失效。
  2. 单向生成有信息损失：仅自上而下或仅自下而上都难兼顾全局一致与局部准确。
  3. 缺乏自动化生成+验证闭环：少有工作把「生成描述」与「下游 SQL 准确率」直接挂钩评估。
- 本文动机：提出在显式描述不可用时自动生成有效数据库描述的方法，并通过双向流程兼顾全局对齐与局部准确性。

## 2. 核心方法
- 最直观类比：给一个陌生数据库写「使用说明书」。普通做法是随便给每列写一句（容易写偏）；本文的做法是：先俯瞰整库、再逐表逐列写细（粗到细），然后反过来从每个字段的细处校验、回看整库与表的概括是否贴切（细到粗），两份视角相互修正，得到既连贯又准确的说明。
- 具体做法（输入→关键操作→输出）：
  - 输入：一个（缺少描述的）数据库 schema（表、列、可能的数据样本）。
  - 关键操作：采用双过程（dual-process）方法：
    1. coarse-to-fine（粗到细）：利用 LLM 的固有知识，引导理解从「数据库 → 表 → 列」逐层深入，提供库结构的整体认知并确保上下文对齐。
    2. fine-to-coarse（细到粗）：从列这一最细粒度出发，在回看表级时提供更准确、更细腻的理解。
    3. 两份描述相互补充/校验，形成最终库描述。
  - 输出：每个表/列的自然语言描述，作为 Text-to-SQL 模型的增强上下文。
- 形式化要点：方法以 LLM 提示流程组织，核心是双向（粗↔细）描述生成；无显式形式化定理。
- 理论性质 / 保证：🔧 本文为经验性方法，未声明形式化保证；具体 prompt 设计与融合策略见原论文/代码。

## 4. 实验结论（概览）
- 对比基线、数据集、指标：在 BIRD benchmark（知名跨域 Text-to-SQL 基准）上评估；指标为 SQL 生成准确率（execution accuracy 类）。
- 结论方向：
  1. 使用本文生成的描述，相比不使用描述，SQL 生成准确率提升 0.93%。
