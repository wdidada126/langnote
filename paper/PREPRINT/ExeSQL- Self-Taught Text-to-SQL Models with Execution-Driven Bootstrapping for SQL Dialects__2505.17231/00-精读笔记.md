## 一句话总结
现有 Text-to-SQL 模型几乎只会 SQLite 方言——因为训练数据都是它。ExeSQL 让模型"自学成才"：自己生成候选 SQL，放进真实数据库里执行，只留下跑得对的孩子当教材，再用偏好训练迭代自我提升——在 PostgreSQL、MySQL、Oracle 上平均比 GPT-4o 分别高出 15.2%、10.38%、4.49%。

## 0. 给新手的阅读前置（背景知识地图）

- 子方向解决什么大问题：Text-to-SQL 的基准（Spider、BIRD）几乎全部基于 SQLite，导致模型在真实企业常用的 PostgreSQL、MySQL、Oracle 等方言上水土不服——语法细节、特有函数、类型系统都不同。如何为"没有现成标注数据"的方言训练出一个能打的模型？
- 为什么难：
  1. 缺数据：方言专用的 (问题 → 正确 SQL) 标注对几乎不存在；
  2. 静态造数据不可靠：光靠提示 LLM 生成 SQL 而不执行验证，产出噪声极大（看起来像 SQL，跑起来错）；
  3. 训练闭环缺环境：不接入真实执行环境，模型永远学不到"SQL 语义对不对"，只学到表面句式。
- 几类主流解法（表格）：

| 路线 | 思路 | 局限 |
|------|------|------|
| 直接迁移 | 拿 SQLite 模型硬套其他方言 | 方言语法/函数错漏百出 |
| 静态合成数据 | LLM 提示生成方言训练对 | 无验证，噪声大 |
| 执行驱动自举（本文） | 生成 → 真实执行过滤 → 偏好训练，循环迭代 | 需要搭建各方言的可执行环境 |

- 本文属哪类：第三类——执行反馈在训练期的完整闭环（区别于只在推理期用执行反馈修正的 Agent 路线）。
- 关键名词直觉解释：
  - 自举（bootstrapping）：模型用自己生成的数据训练自己，好数据喂下一轮，像滚雪球；
  - 拒绝采样（rejection sampling）：生成一堆候选，用执行结果做筛子，只有执行正确/结果一致的才保留；
  - 方言（dialect）：SQL 各实现之间的"口音"差异——如 PostgreSQL 的类型系统与窗口函数细节、Oracle 的 `CONNECT BY` 层级查询等。

## 1. 问题背景与动机

- 前人工作简述：Text-to-SQL 模型在 SQLite 系基准上成绩强劲；LLM 提示路线与微调路线都已成体系；DPO 类偏好训练方法成熟。
- 前人的缺陷 / 未解决问题（逐条）：
  1. 模型有效性局限于 SQLite，根源是数据集限制；
  2. 真实应用需要多方言生成能力，现有模型直接迁移表现差；
  3. 静态提示造数据（不执行验证）噪声大、不可靠；
  4. 训练闭环中缺乏真实执行环境，模型预测无法锚定到可执行语义，导致数据过滤只能做表面文章，泛化受限。

## 2. 核心方法

- 最直观类比：学方言不能只背课本（静态数据），得把孩子扔进方言区生活（真实执行环境）——每天让孩子说（生成候选 SQL），大人只夸说得让本地人听懂的（执行正确），孩子拿"被夸的话 vs 被打回的话"对照学习（偏好训练），日复一日（迭代自举）。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：基座 LLM + 多方言数据库环境（PostgreSQL、MySQL、Oracle 等）+ 问题集；
  2. 关键操作：迭代式查询生成（模型对问题产生多个候选 SQL）→ 基于执行的过滤（如拒绝采样：执行验证，只留正确者）→ 偏好训练（正确解为正例、错误解为负例，构造偏好对训练）→ 循环迭代，模型逐步适应新方言；
  3. 输出：方言感知（dialect-aware）的 Text-to-SQL 模型。
- 形式化要点：核心是"可验证的反馈引导学习"——反馈信号来自真实执行，而非人工标注或表面相似度。🔧 偏好对构造细节、每轮数据规模、使用的偏好优化算法（DPO 或其变体）查原论文后补。
- 理论性质/保证：无理论证明，方法 + 实证型论文。

## 7. 2026 视角（🔧）
- "训练期接入真实执行环境"已从加分项变为标配：方言适配、企业私有 SQL 方言（如各云厂商 warehouse SQL）的 Text-to-SQL，普遍采用生成-执行-过滤-偏好的自举流水线；
- 与 2025 年兴起的"可验证奖励强化学习（RLVR）"思潮同源；ExeSQL 的拒绝采样 + 偏好训练可视为其轻量版（无需 PPO 等重型 RL 设施）；
- 🔧 多方言基准（如后续dialect 专项评测）的出现与 ExeSQL 数字的相对位置，需另行检索。
