## 一句话总结

给数据库请一个"AI 实习 DBA"——D-Bot 先从诊断文档里自学知识，出问题后自动生成提示词、调用工具、用树搜索追根因，10 分钟内产出诊断报告，而人类 DBA 可能要花几小时。

## 0. 给新手的阅读前置（背景知识地图）

- 子方向解决什么大问题：企业往往同时维护成百上千个数据库实例，一旦出现慢查询、锁等待、内存暴涨等异常，DBA 要人工看监控、翻日志、查手册。人工诊断慢（摘要：等几个小时在很多在线场景不可接受）、经验难传承、规则难随数据库版本更新。
- 为什么难：异常种类爆炸（每种数据库、每个版本症状不同）；根因常常不止一个且互相纠缠；诊断需要"文档知识 + 系统实时状态 + 工具执行"三方结合。
- 主流解法几大类：

| 类别 | 代表思路 | 直觉 |
|------|---------|------|
| 经验规则 | Oracle/Percona 等的专家系统、监控告警规则 | 人写的 if-then 规则，准但覆盖窄、更新贵 |
| 统计/ML 检测 | 基于指标时序的异常检测+关联分析 | 能发现"不对劲"，但说不清"为什么" |
| LLM 诊断 | D-Bot、各类 LLM Agent | 用大模型读文档、拟提示词、调工具、写报告 |

- 本文属于：LLM 诊断路线，且强调"离线知识抽取 + 在线多智能体协作"的完整系统。
- 关键名词直觉解释：
  - 根因分析（root cause analysis, RCA）：不是记住"CPU 高"这个症状，而是顺着因果链找到真正源头（比如是某条坏 SQL 引起的连锁反应）。
  - 树搜索式诊断：把"可能的根因"组织成一棵树，像走迷宫一样逐层展开验证，而不是一次猜到底。
  - 提示词生成（prompt generation）：根据当前异常自动拼装最适合的上下文（匹配到的知识点 + 检索到的工具），喂给 LLM。

## 1. 问题背景与动机

- 前人工作简述：传统方案是 DBA 经验沉淀成的规则库与告警系统（摘要称 existing empirical methods）；自动调优/诊断工具（如基于 ML 的 knob tuning、异常检测）也已存在多年。
- 前人缺陷（摘要逐条对应）：
  1. 覆盖场景有限：经验方法只支持有限的诊断场景。
  2. 规则更新人力成本高：数据库版本一升级，诊断规则就要跟着改，劳动密集。
  3. 响应不及时：DBA 管不过来大量实例，人工响应以小时计，在线业务等不起。
  4. 纯 LLM 直接诊断也不够：vanilla 模型（如直接用 GPT-4）缺乏领域知识与工具调用能力，效果显著逊于本文系统（摘要结论）。

## 2. 核心方法

- 最直观类比：一家医院的新医生。离线阶段先读遍教科书（诊断文档）做笔记；在线接诊时，先自动开检查单（生成提示词、调诊断工具），然后像侦探一样顺着线索树逐层排查（树搜索），遇到疑难杂症还会多科室会诊（多 LLM 协作机制）。
- 具体做法（输入→关键操作→输出）——摘要明确列出四大技术：
  1. 输入：数据库异常（监控指标、日志等）+ 诊断文档（手册、博客、案例）。
  2. 关键操作：
     - (i) 离线知识抽取：从诊断文档自动提取结构化知识；
     - (ii) 自动提示词生成：做知识匹配与工具检索，拼出带上下文的 prompt；
     - (iii) 树搜索根因分析：用树搜索算法逐层假设、验证、深入；
     - (iv) 多根因协作机制：复杂异常有多个根因交织时，多智能体分工协作。
  3. 输出：有理有据的诊断报告（根因 + 解决方案），摘要称可在可接受时间内完成（例如 10 分钟内，对比 DBA 的数小时）。
