Bauplan 把湖仓做成「所有计算都是函数（FaaS）」的可组合数据系统，随之出现一个新问题：成千上万个数据负载函数该怎么调度？团队干脆发布了一个确定性模拟器 Eudoxia，让你不用烧真集群就能快速迭代调度算法。

## 0. 给新手的阅读前置（背景知识地图）

这个子方向解决什么大问题？ 数据湖仓（data lakehouse）把数据湖的开放存储和数仓的管理能力合到一起。传统湖仓里「SQL 查询」和「Python 机器学习流水线」是两套运行时、两套运维。Bauplan 的激进主张是：把两种负载统一成一个 FaaS（Function-as-a-Service）运行时——用户提交的每个 SQL 查询/Python 步骤都是一个云函数。而一旦「一切皆函数」，就诞生了一个经典但全新的问题：数据工作负载的函数调度。

为什么难？
1. 数据负载与普通 Web 函数不同：函数之间有数据依赖（表血缘）、资源需求差异巨大（1 秒扫描 vs 1 小时训练）、且对冷启动与数据本地性敏感；
2. 调度算法迭代不能靠真集群试错：太贵、太慢、结果不可复现（云环境噪声大）；
3. 可组合数据系统（composable data system）的 API 面大、用例多样，调度空间呈组合爆炸。

主流解法分几类？

| 类型 | 思路 | 局限 |
|------|------|------|
| 直接在真实系统上调 | 在生产/测试集群 A/B 不同调度器 | 贵、慢、不可复现 |
| 通用离散事件模拟器 | 用现成网络/集群模拟框架 | 对数据负载语义（表、血缘、FaaS 冷启动）建模不足 |
| 领域专用确定性模拟器 | 针对数据 FaaS 负载定制、结果可复现 | 本文（Eudoxia）所在类别 |

本文属哪类？ 第三类——为「可组合湖仓 + FaaS 调度」量身定做的确定性模拟器。

3 个关键名词直觉解释：
- FaaS / serverless：用户不管理服务器，提交函数，平台负责调度与资源分配（极简类比：点外卖 vs 自己开火）；
- 确定性模拟器（deterministic simulator）：同样的输入永远得到同样的模拟轨迹——这让调度算法的对比实验可以复现、可以精确归因，是它相对真集群实验的最大优势；
- 可组合湖仓（composable lakehouse）：数据系统像乐高一样由可替换的部件拼成（Bauplan 的关键词是「spare data parts」，即数据部件可插拔），用户通过 FaaS API 组合它们。

## 1. 问题背景与动机

- 前人工作简述：Bauplan 此前的工作（同作者团队）论证了「git 式分支 + FaaS 式 SQL/Python 统一运行时」的湖仓架构；调度领域则有经典的数据中心调度研究（Borg/YARN/Kubernetes 谱系）与各类查询调度器。
- 前人缺陷 / 未解决问题（摘要逐条）：
  1. 统一 FaaS 运行时带来全新调度挑战：SQL 查询与 Python 流水线同池调度，负载异构性远超传统查询调度或通用函数调度（摘要：introduces novel challenges in scheduling and optimization of data workloads）；
  2. 缺少描述这个调度问题的形式化刻画：可组合 DLH 的编程模型到底把调度问题定义成了什么样，此前没人系统刻画（摘要：we characterize the underlying scheduling problem）；
  3. 迭代成本高：在真实基础设施上迭代调度算法昂贵且不可复现，需要把模拟（simulation）确立为有效的迭代工具（摘要：motivate simulations as an effective tools to iterate on the DLH）；
  4. 没有现成工具：社区缺少一个可广泛模拟数据工作负载、且允许用户高度自定义调度算法实现的模拟器——Eudoxia 就是为填补这个空白而发布的。

## 2. 核心方法

最直观类比：Eudoxia 之于湖仓调度，就像飞行模拟器之于飞行员培训——不用真飞机（真集群）就能练所有紧急情况（负载高峰、函数排队、资源抢占），而且每次「飞行条件」都一模一样，进步还是退步一测便知。

具体做法（输入 → 关键操作 → 输出）：
- 输入：数据工作负载的描述（作为云函数提交的 SQL 查询与 Python 流水线，含资源需求与依赖）+ 用户自定义的调度算法；
- 关键操作：
  1. 从可组合 DLH 的编程模型出发，形式化刻画底层调度问题（负载、资源、目标函数）；
  2. 用离散事件模拟推进时间，模拟函数排队、资源分配、执行与完成的全过程；
  3. 确定性设计：固定随机性，使相同输入产生相同模拟结果，保证对比实验可复现；
  4. 开放调度算法接口：用户可以「highly customizable」地实现自己的调度器（摘要原话）；
- 输出：各调度算法在模拟负载下的性能表现（吞吐/延迟/资源利用等 🔧 具体指标以论文正文为准），供开发者在「自己的基础设施假设」下廉价评估调度算法。

形式化要点：调度问题的形式化（任务图、资源向量、目标）🔧 以论文正文为准。

理论性质/保证：主要工程保证是确定性/可复现性；统计意义上的保证（模拟与真实集群的保真度差距）🔧 查正文实验部分。
