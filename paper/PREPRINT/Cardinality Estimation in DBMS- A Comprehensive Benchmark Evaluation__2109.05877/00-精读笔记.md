## 一句话总结
十年间冒出一堆「准确率惊人」的基数估计方法（尤其 ML 派），但没人回答过真问题：它们放进真数据库里，到底能不能帮查询优化器选出更好的执行计划？ 这篇论文把十几种代表性方法塞进 PostgreSQL 端到端评测，还指出常用的 Q-Error 指标根本反映不了计划质量，并提出了新指标 P-Error。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：SQL 执行前，优化器要选「连接顺序、用哪个索引、扫多少数据」；这些决策全靠基数估计——预测每个中间算符会输出多少行。估错（常常差几个数量级）就会选烂计划，查询从 1 秒变 1 小时。
- 为什么难：多表连接后数据相关性爆炸（列与列不独立）；直方图/采样等传统手段在多谓词组合下失真；ML 方法虽准但要训练、要更新、推理还有延迟。
- 几类主流解法：

| 路线 | 代表 | 直觉 |
|------|------|------|
| 传统统计 | 直方图、采样、system catalog | 便宜、随库更新，但独立性假设在多表下崩塌 |
| 数据驱动 ML | DeepDB、NeuroCard | 从数据学联合分布，准但训练/更新贵 |
| 查询驱动 ML | MSCN、BayesCard 系 | 从历史查询学，贴合负载但难泛化 |
| 混合/查询级 | FLAT、本文被测的多数 ML 方法 | 双路信息融合 |

- 本文属哪类：基准评测论文——不造新估计器，而是把上述各派塞进真 DBMS 打擂台。
- 关键名词直觉：
  - Q-Error：估计行数与真实行数的比值（取 ≥1 的倍数），传统精度指标。
  - P-Error（本文新指标）：按「计划空间」加权评估估计误差对最终执行计划的影响——子计划在优化器里的重要性不同，Q-Error 一视同仁是错的。
  - 端到端：不只看估计准不准，而是真的在 PostgreSQL 里跑出执行计划、量执行时间。

## 1. 问题背景与动机
- 前人工作简述：2010 年代后期 ML 基数估计井喷（DeepDB、NeuroCard、MSCN、FLAT、BayesCard 等），论文都报 Q-Error 很低、推理很快；此前也有 Are We Ready For Learned CardEst（2012.06743）等工作做过学习型估计器的离线评测。
- 前人缺陷/未解决问题（逐条）：
  1. 缺端到端验证：没有研究系统评估「这些方法能否真正改进真实优化器的计划质量」——这是 CardEst 方法的终极目标。
  2. 指标失真：Q-Error 无法区分「关键子计划」与「无关子计划」的误差重要性，所以估得准不等于计划好。
  3. 实用性维度缺失：模型体积、训练时间、更新效率、推理延迟等影响落地的重要因素没有被横向对比过。
  4. 数据/负载不统一：各家论文各用各的数据集与查询集，无法公平比较。

## 2. 核心方法
- 最直观类比：以前比基数估计像「比谁体重秤准」；这篇论文是「让所有秤进医院真看病」——秤准不准最后要看病人（查询计划）是不是真的被治好（执行更快）。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 构建基准：新真实世界数据集 STATS（复杂、真实的统计数据集）+ 多样查询负载 STATS-CEB。
  2. 集成被测方法：把多个最具代表性的 CardEst 方法（传统 + ML 派，完整名单 🔧 查原文）逐一接入开源数据库 PostgreSQL 的优化器。
  3. 端到端评测：量化它们对查询计划质量的真实改进，并横向考察推理延迟、模型体积、训练时间、更新效率与精度。
  4. 指标创新：论证 Q-Error 的局限，提出 P-Error 反映端到端计划质量。
  5. 输出：数据/负载/方法三维度的关键发现 + 全部开源。
- 形式化要点：P-Error 将优化器视角下的计划空间（join 顺序/算符选择集合）纳入估计误差的度量，对影响计划分支的子计划误差加权（🔧 精确定义查原文第 4 节左右）。
- 理论性质/保证：无（基准论文）；贡献是评测框架、指标与发现。

## 4. 实验结论（概览）
- 对比基线：PostgreSQL 内置估计器（直方图等）+ 多个代表性 CardEst 方法接入同一优化器。
- 数据集/负载：STATS 数据集 + STATS-CEB 查询负载（论文新造，公开可下）。
- 指标：端到端计划质量/执行时间、Q-Error、新 P-Error、推理延迟、模型体积、训练时间、更新效率。
- 结论方向（摘要核实的定性结论）：
  1. 各方法在不同数据/查询设定下表现差异显著，得出多条关键发现（逐条清单 🔧 查原文）。
  2. Q-Error 不能反映计划质量：它无法区分不同子计划在优化中的重要性。
  3. P-Error 能更好反映端到端性能。
  4. 🔧 各方法的端到端执行时间、P-Error/Q-Error 精确数值，查原论文表格后补。

## 7. 2026 视角（🔧）
- 本文确立的「端到端 + 计划感知指标」已成为 CardEst 研究的标准方法论；STATS-CEB 被大量后续论文采用，是最常用的 CardEst 基准之一。
- 趋势：①ML 估计器的更新与鲁棒性（动态负载、跨库泛化，如 ALECE/PRICE）；②估计器与优化器协同设计（而非只换估计器）；③云数据库里 query-driven 方法因安全/免训练优势回潮。
- 本节为趋势性判断 🔧，最新 SOTA 与工业落地需另行调研。

## 8. 新手学习路线
- 10 分钟：读摘要 + 本笔记第 0 节，理解「基数估计为什么决定计划好坏」与「Q-Error vs P-Error」。
- 30 分钟：clone 官方仓库，只跑 PostgreSQL 内置估计器在 STATS-CEB 上的端到端评测，感受「估错行数 → 计划变烂」。
- 进阶：接入一个 ML 方法（如 FLAT）对比 P-Error 与端到端时间；精读 P-Error 定义一节并思考它为什么比 Q-Error 合理；再读 2012.06743 对比两代评测方法论。
