## 一句话总结

给小中型数据集配向量数据库，Milvus 这类重型系统太杀鸡用牛刀。Bhakti 是一个轻量、易部署、纯 Python3 友好的向量库：多种相似度算法 + 文档模式匹配预过滤 DSL + 可移植数据文件，还附带一套"给对话历史中问答各配权重"的 LLM 记忆方案。局限也很诚实：不支持 HNSW 等近似算法，大数据集不适用。

## 0. 给新手的阅读前置（背景知识地图）

- 大问题：LLM 没有长期记忆，外挂"向量数据库"存对话/文档，用时语义检索最相关片段塞回提示词（RAG）。个人项目/原型机场景需要一个几行代码就能跑的向量库。
- 为什么难：向量检索要在高维空间找最近邻；工业级系统（HNSW 图索引、量化压缩）工程复杂、部署重；而小数据集又用不上这些复杂度。
- 主流做法对比：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 重型分布式 | Milvus、Qdrant 集群 | 分布式+近似索引（HNSW/IVF） | 海量数据快；部署运维重 |
| 嵌入式轻量 | FAISS、Chroma、Bhakti（本文） | 单机简单索引/全量扫 | 易上手；规模受限 |
| 数据库插件 | pgvector | 复用 SQL 生态 | 融合好；性能中等 |

- 本文属于哪类：第二类，卖点在"轻 + 可移植 + LLM 记忆一体化"。
- 必须先懂的名词：
  - 向量相似度：余弦/欧氏/内积等度量两个 embedding 的接近程度。
  - 预过滤（pre-filtering）：先按元数据/模式匹配缩小候选集，再做向量检索。
  - HNSW：分层可导航小世界图，主流近似最近邻索引（Bhakti 明确不支持）。

## 1. 问题背景与动机

- 前人工作：工业向量库功能全但重；嵌入式方案各有所长，但"便携数据文件 + DSL 预过滤 + LLM 记忆语义加权"的组合不多见。
- 未解决的问题：
  1. 小中型数据集缺少"零运维"向量库选项；
  2. LLM 对话记忆里，问题与答案的重要性通常被同等对待，缺少细粒度权重控制。

## 2. 核心方法

- 类比：Bhakti 像一个随身的便签本——不大，但写字（写入）、翻找（检索）、换本子（迁移数据文件）都极顺手；它还发明了一种"重点标注笔"：给对话里每个问题/答案段单独标注重要度。
- 具体做法（输入 → 操作 → 输出）：
  1. 存储：向量 + 文档的可移植数据文件，无缝对接 Python3；
  2. 检索：多种相似度算法可选；DSL 定义文档模式匹配做预过滤，再算相似度；
  3. LLM 记忆方案：对话历史入库存 (问题, 答案) 对，检索时可为问题与答案分别赋权，实现对单段对话历史语义重要性的细粒度控制。
- 明确局限（作者自陈）：不支持 HNSW 等近似方法 → 大数据集性能受限。

## 3. 变体 / 工程版

- 系统本身即工程产物；记忆方案可独立于存储引擎，移植到其他向量库。

## 5. 开源代码与动手实践

- 仓库：https://github.com/vortezwohl/bhakti（官方；pip 安装方式以 README 为准 🔧）。
- 典型流程（教学示意）：`pip install` → 建库写入文档向量 → DSL 预过滤 + 相似度查询 → 接入自己的 LLM 对话循环做记忆。
- 资源提醒：单机即可；数据量建议控制在中小规模（无近似索引，全量计算）。

## 7. 2026 视角（🔧）

- 向量库市场两极分化：云上重型系统持续卷分布式与 GPU，而"嵌入式轻量 + 与 LLM 框架一键集成"赛道（Chroma、LanceDB、Bhakti 类）因个人 Agent 开发兴起而繁荣；预过滤 DSL 与记忆加权是差异化尝试 🔧。
