## 一句话总结
科学家们在一类「数据库即服务」平台上手写了一堆零散的 SQL 查询，这些查询日志里其实藏着一段段「连贯的探索任务」（比如先 SELECT 看看、再 GROUP BY 聚合、最后微调条件）。这篇论文从每条 SQL 提取特征，把查询序列自动切分成一段段有意义的探索会话，并用多组负载实验验证了方法有效。

## 0. 给新手的阅读前置（背景知识地图）
- **大问题**：数据库负载分析（workload analysis）通常把查询当独立个体，但真实分析型用户的查询是**成串**的——一个「探索会话（exploration）」里，查询彼此相关、逐步演进。识别出这些会话，是查询推荐、预取、成本核算等下游任务的前提。
- **为什么难**：
  1. 日志里往往没有显式会话边界（没有「任务开始/结束」标记）；
  2. 分析型即席查询（ad-hoc）五花八门，聚类不能只看文本相似；
  3. 「同一任务」的判定标准本身就是研究问题。
- **主流解法几类**：

| 路线 | 直觉 | 弱点 |
|------|------|------|
| 时间窗切分 | 相邻查询间隔短即同会话 | 探索节奏不定，误差大 |
| 文本/结构聚类 | 查询字符串或解析树相似即同类 | 忽略演化与顺序 |
| 特征驱动的序列切分（本文） | 提取 SQL 语义特征，按特征流变化切分会话 | 特征设计需要领域知识 |

- **本文属于**第三类。
- **关键名词直觉**：
  - **探索会话（exploration）**：用户围绕同一分析目标连续发出的一组相关查询，如逐步细化过滤条件的过程。
  - **SQLShare**：面向无数据库经验科学家的 database-as-a-service 平台，其公开负载是本文的研究对象——据原平台作者称，这是唯一一个以「用户上传数据集上手写即席查询」为主的公开负载。
  - **查询特征（query features）**：从 SQL 语句抽出的刻画向量，如表数、谓词类型、聚合函数、投影列、复杂度等，用于衡量相邻查询的「演进关系」。

## 1. 问题背景与动机
- 前人工作：SQLShare 平台与其负载公开发布；负载分析/会话识别此前多用时间窗或文本相似度。
- 前人缺陷（据摘要与对象特点归纳）：
  1. 缺少针对「手写即席查询为主」负载的会话识别方法；
  2. 时间窗/纯文本相似度无法刻画探索过程的结构化演进；
  3. 缺乏在真实 ad-hoc 负载上的实证验证。

## 2. 核心方法
- **最直观类比**：看一个人的浏览历史，虽然每页内容不同，但「搜索→点开详情→换关键词再搜」的模式能分出一个个「购物任务」。本文对 SQL 做同样的事：从每条查询提取特征，观察特征流，在「任务变了」的地方切一刀。
- **输入 → 关键操作 → 输出**：
  1. 输入：按时间排序的 SQL 查询日志（研究对象为 SQLShare 负载）；
  2. 关键操作：(a) 对每条查询提取特征（描述其结构与语义属性）；(b) 利用特征序列把查询序列**切分（segmentation）**成连贯探索段；(c) 多组负载上的经验性测试验证；
  3. 输出：切分后的探索会话序列。
- **形式化要点**：会话切分可形式化为「特征相似度/演化度评分 + 切分点选择」的优化问题（🔧 具体评分函数与算法查原文）。
- **理论性质**：以实证为主（🔧 无硬性理论保证）。
