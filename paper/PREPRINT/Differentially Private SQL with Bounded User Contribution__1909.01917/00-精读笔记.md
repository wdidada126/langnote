## 一句话总结
差分隐私查询引擎大多假设「一个人只对应一条记录」，现实根本不是这样（一个用户可能贡献几百行）。这篇 Google 的论文提出一个通用可扩展的方法：在 SQL 引擎里以关系代数算子的形式**限制每个用户的贡献量**，从而在「一人多行」的真实数据上安全做差分隐私聚合，并用随机化测试框架验证正确性、在行业基准上测了实用度。

## 0. 给新手的阅读前置（背景知识地图）
- **大问题**：差分隐私（DP）是「查询结果不泄露任何单个人太多信息」的形式化保证：对相邻数据集（差一个人）的查询结果分布几乎不变。学界算法很多，但**端到端可用的 DP 查询引擎很少**。
- **为什么难**：
  1. 现有系统普遍假设「一人一记录」（unit of privacy = 一行），真实数据一人可对应任意多行，隐私预算会被同一个人反复消耗；
  2. 要在通用 SQL（JOIN、GROUP BY、HAVING 等组合）上做 DP，噪声注入与语义的组合极其复杂；
  3. 还要工程上可扩展、部署上可用。
- **主流解法几类**：

| 路线 | 直觉 | 弱点 |
|------|------|------|
| 逐查询加噪 | 每个聚合结果加 Laplace/Gaussian 噪声 | 一人多行时灵敏度失控 |
| 限贡献 + 加噪（本文） | 先把每人贡献截断到上限，再做 DP 聚合 | 截断损失部分信息 |
| 查询改写/拒绝机制 | 只允许安全的查询模板 | 表达能力受限 |

- **本文属于**「限贡献 + 通用 SQL 引擎集成」路线。
- **关键名词直觉**：
  - **差分隐私（DP）**：数学定义 ε-DP——改变任何一个人的数据，任何查询结果分布变化不超过 e^ε；实现手段通常是「加精心标定的随机噪声」。
  - **用户贡献上界（bounded user contribution）**：规定每个用户最多影响结果多少行/多少权重；如同「每人限投一票」，之后灵敏度分析才有界。
  - **随机化测试框架（stochastic test framework）**：反复扰动单条记录、统计输出分布差异，实证检验系统行为是否符合 DP 定义（类似 DP 的「隐私测试/审计」）。

## 1. 问题背景与动机
- 前人工作：DP 理论与大量单查询算法成熟；已有少数端到端 DP 查询引擎实现。
- 前人缺陷（据摘要归纳）：
  1. 现有系统假设每个人最多关联一条记录，实践中不现实；
  2. 端到端 DP 引擎稀缺，缺少在真实 SQL 负载上的系统化实践；
  3. 缺少对 DP 系统正确性的实用验证手段。

## 2. 核心方法
- **最直观类比**：匿名问卷调查本想「每人一份答卷」，结果有人交了 50 份。解决办法：先按人分箱、每人只统计有限份（限贡献），再加噪声发布统计——既公平又保隐私。
- **输入 → 关键操作 → 输出**：
  1. 输入：含用户标识的数据库、SQL 聚合查询、隐私参数（预算）；
  2. 关键操作：(a) 把「限贡献」表达为**关系代数中的一个算子**（可与其他代数算子组合）；(b) 在 SQL 引擎中实现该算子，使聚合（含一人多行的场景）先经限贡献处理再做 DP 噪声；(c) 用自研随机化测试框架验证正确性；
  3. 输出：带 DP 保证的 SQL 聚合结果。
- **形式化要点**：限贡献算子保证任意用户对中间结果的影响被截断至常数，从而使聚合函数的 DP 灵敏度为有界值，噪声标定随之成立（🔧 算子形式化定义查原文）。
- **理论性质**：方法在「限贡献前提下」满足差分隐私保证；通用性与可扩展性为主要卖点（🔧 证明与参数细节查原文）。
