## 一句话总结

数据分析常常要在"写 SQL"和"拖图表"两套工具间来回横跳——DashQL 干脆把 SQL 和图形语法（grammar of graphics）融合成一种"分析语法"，让一个自包含脚本就能表达从数据接入、转换到可视化的完整分析工作流，并借此做全局优化。

## 0. 给新手的阅读前置（背景知识地图）

- **子方向解决什么大问题**：一次数据分析通常不止一条查询：先清洗、再聚合、再画图、再调整参数重跑。这些步骤散落在 SQL 客户端、Python notebook、BI 工具里，**工作流被工具边界切碎**，难以整体优化与复用。
- **为什么难**：SQL 擅长关系变换但不表达可视化；BI/notebook 擅长可视化但不擅长声明式的数据变换，也不易被数据库内核优化。要"一种语言覆盖全流程"，需要把两种语法模型缝合起来并让优化器看得见全流程。
- **主流解法几大类**：

| 类别 | 代表思路 | 直觉 |
|------|---------|------|
| Notebook 编排 | Jupyter 系 | 代码单元按顺序执行，灵活但状态难追踪 |
| BI 拖拽工具 | Tableau 等 | 图形化，但逻辑封闭在工具内 |
| SQL + 外挂 DSL | 各种 orchestration 工具 | 用 YAML/Python 包装 SQL，两层割裂 |
| 语言融合 | **本文 DashQL** | 直接扩展 SQL 语法，工作流本身就是脚本 |

- **本文属于**：语言融合路线，站在 DuckDB 这类嵌入式分析引擎的生态上（🔧 引擎绑定关系依据作者背景与项目生态推断，非摘要原文）。
- **关键名词直觉解释**：
  - **Grammar of graphics（图形语法）**：把图表拆解为数据、映射、标记、变换等正交成分的声明式描述方式（ggplot 的理论基础）。
  - **Grammar of analytics（分析语法）**：本文的提法——在图形语法之上再叠加工作流编排成分，让"整个分析"成为语法对象。
  - **谓词下推（predicate pushdown）**：把过滤条件尽量推到数据源一侧执行，少搬数据。本文说的是跨越可视化/查询边界的**远程**谓词下推。
  - **自适应物化（adaptive materialization）**：按需决定中间结果是否落地缓存，而不是无脑全存或全不算。

## 1. 问题背景与动机

- **前人工作简述**：SQL 是关系数据库的标准语言但只覆盖查询本身；可视化与工作流由外置工具承担（notebook、BI）。同一团队背景的 DuckDB/学术分析型数据库生态长期关注交互式分析效率。🔧 前人具体系统对比以论文 Related Work 为准。
- **前人缺陷（摘要逐条对应）**：
  1. **工作流不自包含**：没有一种语言能用"自包含脚本"描述完整分析工作流，步骤散落各处。
  2. **无法整体优化**：数据接入、编码、变换、可视化分属不同工具，优化器只能看到各自片段，做不了跨边界（holistic）优化。
  3. **中间结果处理粗放**：可视化驱动的聚合、远程下推、自适应物化这类"看得见全流程才能做"的优化在外置工具组合里难以实现。

## 2. 核心方法

- **最直观类比**：把"SQL + 图表配置"从两份文件合并成一份菜谱。以前 SQL 是"备菜说明"、BI 工具是"摆盘说明"，厨师（优化器）只能分段理解；DashQL 把整份菜谱写成一种语言，厨师可以通读全谱，先决定哪些步骤根本不用做（下推）、哪些半成品值得提前做出来放冰箱（物化）。
- **具体做法（输入→关键操作→输出）**：
  1. **输入**：一份 DashQL 脚本（SQL 语句 + 可视化声明 + 工作流依赖）。
  2. **关键操作**：
     - **语言层**：DashQL 作为 **SQL 的扩展**，把图形语法成分（图表定义、数据映射）并入同一语法，脚本自包含、语句间可声明依赖；
     - **处理层**：对文本化分析工作流做高效、交互式的处理（增量解析、依赖图调度 🔧 细节以论文为准）；
     - **优化层**：利用模型与查询元数据做三类全局优化——**可视化驱动的聚合**（只为将要画的图算必要的粒度）、**远程谓词下推**（把过滤推给远端数据源）、**自适应物化**（按代价决定中间结果缓存）。
  3. **输出**：交互式呈现的完整分析工作流（含图表）。
- **形式化要点**：语法设计 = SQL 语法 ⊕ 图形语法，并新增工作流相关语句结构。🔧 语法形式文法与语句清单见论文正文。
- **理论性质/保证**：无统计理论保证；价值主张是交互性能与跨层优化收益（实验型）。
