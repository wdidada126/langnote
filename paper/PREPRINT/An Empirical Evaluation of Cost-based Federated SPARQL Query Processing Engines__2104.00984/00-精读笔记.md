## 0. 给新手的阅读前置（背景知识地图）

- 子方向解决什么大问题：RDF 是一种用「主语-谓语-宾语」三元组表示知识的图数据模型；SPARQL 是查询 RDF 的语言（类似 SQL 之于关系表）。现实中数据分散在多个站点，联邦查询（federated query） 就是「一条查询跨多个独立数据源联合求解」，不用先把所有数据搬到一个地方。
- 为什么难：跨多个数据源时，系统必须决定「先查哪个源、把中间结果传到哪、怎么少发请求」。这依赖基数估计（cardinality estimation）——估计每一步会产出多少数据。估错了，查询计划就烂，跑得极慢。
- 几类主流解法（表格）：

  | 引擎类型 | 做法 | 与本文关系 |
  |---------|------|-----------|
  | 基于代价（cost-based）的联邦引擎 | 用基数估计选查询计划 | 本文评测对象 |
  | 基于规则的联邦引擎 | 用启发式固定策略 | 非本文重点（作为对照背景） |
  | 集中式 SPARQL 引擎 | 数据已在同一库 | 联邦的「非分布」对照 |

- 本文属哪类：本文是实证评测 + 评测方法论——提出专门针对「cost-based 联邦 SPARQL 引擎」的细粒度指标，弥补通用指标无法量化「基数估计准确度」的缺口。
- 2-3 个关键名词直觉解释：
  - 联邦查询（federation）：查询跨多个独立端点，系统在运行时决定如何拆分、路由、合并。
  - 基数估计（cardinality estimation）：预测某步查询会返回多少三元组 / 结果；它是「基于代价优化」的眼睛。
  - 查询计划（query plan）：先算哪部分、把中间结果传给谁的顺序安排；计划好坏直接决定总耗时。

## 1. 问题背景与动机

- 前人工作简述：已有不少研究从多维度比较 SPARQL 联邦引擎——查询运行时间、结果集完整性与正确性、被选中的源数量、发出的请求数量等。
- 前人 N 个缺陷 / 未解决问题（逐条）：
  1. 上述指标都很「通用」，但无法量化、评估 cost-based 联邦引擎里「基数估计器」到底准不准。
  2. 基数估计误差会如何影响「整体查询运行时间」，此前没有被精确测量过——而这是评价 cost-based 引擎优劣的关键。
  3. 缺少一套细粒度（fine-grained） 的 benchmark 指标，来区分「是计划选得好」还是「只是运气好 / 数据小」。

## 2. 核心方法

- 最直观类比：给 5 个「跨国快递调度系统」做体检——以前只量「包裹多久到、丢没丢」，本文新加了一项「系统对每家仓库库存量的预测准不准」，因为预测歪了，调度自然乱。
- 具体做法（输入 → 关键操作 → 输出）：
  - 输入：5 个 cost-based 联邦 SPARQL 查询引擎 + 现有及新提出的评测指标 + LargeRDFBench 查询集。
  - 关键操作：设计一套针对 cost-based 联邦引擎的细粒度评测指标，专门衡量「基数估计误差」及其对「整体查询运行时间」的影响；用这套指标在 LargeRDFBench 上评测 5 个引擎。
  - 输出：对实验结果的详细分析，揭示新的洞察，供未来 cost-based 联邦引擎开发参考。
- 形式化要点：本文贡献在于评测方法论（新指标），而非新引擎或新算法；通过把「基数估计误差」与「端到端运行时间」关联起来，使引擎的「智能程度」可被量化。
- 理论性质 / 保证：无算法正确性证明；价值在于提供可复现的评测口径。

- 对比基线、数据集、指标：评测 5 个 cost-based 联邦 SPARQL 引擎；使用 LargeRDFBench 查询；除传统指标外，加入本文新提出的「基数估计准确度 / 误差对运行时间影响」细粒度指标。
