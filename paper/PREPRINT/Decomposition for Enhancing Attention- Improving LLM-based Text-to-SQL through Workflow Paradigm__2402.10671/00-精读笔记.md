## 一句话总结

让 LLM 一步到位"读 schema + 读问题 + 想 CoT + 写 SQL"，注意力会被摊薄、容易分心。DEA-SQL 把这件事拆成一条流水线式工作流：先判定哪些信息真正有用，再按问题类型走不同的提示模板，最后自我纠错——每一步只让模型专注一件事，Spider 榜单刷到当时 SOTA。

## 0. 给新手的阅读前置（背景知识地图）

子方向解决什么大问题：Text-to-SQL（NL2SQL）= 自然语言 → SQL。LLM 时代最简单的做法是"一个长 prompt 一步生成"，但 schema 又长又杂、问题又绕，模型注意力分散，容易抄错列名、漏条件。

为什么难：单个 prompt 里塞了 schema 定义、问题、 few-shot 示例、CoT 推理要求——上下文互相干扰（注意力被摊薄），且不同类型的问题（简单聚合 vs 嵌套查询）适合的解题路径不同。

几类主流解法：

| 思路 | 直觉 | 缺点 |
|------|------|------|
| 单步直接生成 | 一把梭 | 注意力分散，复杂查询易错 |
| 单步 CoT | 加"想一想再写" | 仍是单步，干扰依旧 |
| 微调路线 | 训练专用模型 | 算力成本、数据依赖 |
| 工作流分解（本文） | 拆成多个专职步骤的流水线 | 流程设计复杂、步骤间误差传递 |

本文属哪类：prompting 工作流（多步分解）路线，纯提示工程、不训练模型。

关键名词直觉：
- 注意力分散（attention distraction）：上下文里无关信息太多，模型"看花了眼"，本笔记标题的"Decomposition for Enhancing Attention"即针对此。
- 工作流范式（workflow paradigm）：把一个任务拆成多个固定阶段，每阶段用专属 prompt，像工厂流水线。
- 自我纠错（self-correction）：生成的 SQL 先自查/试执行，发现问题再改一轮。

## 1. 问题背景与动机

- 前人工作：2023-2024 年 LLM Text-to-SQL 主流是"单步思维链（CoT）提示"：把 schema、问题、示例、推理指令放一个 prompt 里让模型一口气完成；DIN-SQL、DAIL-SQL 等已探索部分分解与示例选择。
- 前人缺陷/未解决问题：
  1. 单步 CoT 中，schema 信息、问题语义、推理要求混杂，LLM 注意力被分散，对长 schema（BIRD 类真实库）尤其严重；
  2. 上下文中大量与当前问题无关的冗余信息（无关表/列）干扰判断；
  3. 一套固定 prompt 无法适配不同难度/类型的问题；
  4. 缺少系统性的错误回收机制，错了就错了。

## 2. 核心方法

最直观类比：考试答题。单步 CoT 像"一边翻 50 页资料一边写答案"；DEA-SQL 像"先划掉资料里无关的页（信息判定）→ 看题型选答题模板（问题分类）→ 写完检查一遍再交卷（自我纠错）→ 错题记进错题本（主动学习）"。

具体做法（输入→关键操作→输出）：
- 输入：数据库 schema + 自然语言问题；
- 关键操作（工作流三件套）：
  1. 信息判定模块：先识别并消除与当前问题无关的冗余信息，让后续生成聚焦在相关 schema 子集上——直接缓解注意力分散；
  2. 基于问题分类的 prompt 结构：把问题分类（简单/复杂等类型 🔧 分类体系细节查原论文），不同类走不同 prompt 结构与解题路径；
  3. 自我纠错 + 主动学习模块：对生成结果进行自我检查修正；主动学习机制用于收集/利用错误样本改进流程 🔧 细节查原论文。
- 输出：SQL 查询。

形式化要点：属提示工程/系统型工作，无算法定理；核心贡献是工作流设计与各模块的 prompt 组织。

理论性质/保证：无理论保证，以实验为准。

## 7. 2026 视角（🔧）

- 本文 2024 年的"工作流分解"思想已成为 Text-to-SQL 的标准形态，并在 2025-2026 年演化为 Agent 化多步管线：schema 链接 Agent → 生成 Agent → 执行反馈修复 Agent；本文的信息判定模块对应今天的 schema linking，自我纠错对应 execution feedback。
- 单步长上下文模型变强后，"分解是否还有必要"有过争论；实践共识是：复杂查询与真实脏 schema 场景下，结构化工作流依然显著更稳。
- 工业落地的 Text-to-SQL 产品普遍采用"分类路由 + 分步生成 + 纠错"的骨架，与本文设计高度同构（🔧 方向性判断）。
