## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：多轮（context-dependent / multi-turn）Text-to-SQL = 把一连串有上下文依赖的自然语言问句逐步翻译成 SQL。例如用户先问「列出销售部的员工」，接着问「其中工资最高的三个」——第二句要靠第一轮的信息才能翻译对。
- 为什么难：
  1. 数据稀缺：标注多轮对话+SQL 代价极高，公开数据集小，模型难以学到复杂的跨轮依赖。
  2. 跨库泛化：同一套对话逻辑要能套到没见过的数据库 schema 上。
  3. 上下文消歧：代词、省略、指代需要结合历史轮次解析。
- 几类主流解法（表格）：

  | 流派 | 思路 | 代表 |
  |------|------|------|
  | 强监督多轮模型 | 直接用标注的多轮数据训练 parser | SParC/CoSQL 基线 |
  | 预训练 + 微调 | 在大规模语料/单轮数据上预训练再微调 | STAR 等 |
  | 数据增强 | 自动造更多训练对话 | 本文（Self-Play） |

- 本文属哪类：数据增强（data augmentation）——用自我博弈（self-play）生成新训练交互。
- 2-3 个关键名词直觉解释：
  - 多轮 Text-to-SQL：用户与系统多回合对话，后续问句依赖前轮上下文。
  - 自我博弈（Self-Play）：两个（或同一）模型互相对练——一个当「用户」生成问句，一个当「parser」翻译 SQL，从而自动产出新对话样本。
  - Goal Query（目标查询）：用户本轮真正想查的 SQL「意图」，作为生成问句的种子。

## 1. 问题背景与动机
- 前人工作简述：上下文相关 Text-to-SQL（SParC、CoSQL 等基准）已有强模型，但受限于训练数据稀缺，难以学到复杂上下文依赖，也难泛化到未见过数据库。
- 前人缺陷 / 未解决问题（逐条）：
  1. 训练数据太少：难以学习复杂上下文依赖。
  2. 跨库泛化弱：模型难以把学到的对话模式迁移到新数据库。
  3. beam search 质量受限：生成多样性/准确性不足。
- 本文动机：用 self-play 利用上下文信息合成新交互，把模型适配到新数据库，从而扩充训练集提升效果。

## 2. 核心方法
- 最直观类比：让两个机器人互相聊天练手——一个机器人扮演「提问题的用户」，另一个扮演「把问题翻成 SQL 的助手」。用户基于一个「目标 SQL 意图」编出一句自然语言问句，助手把它翻成 SQL；对出来的对话如果合理，就收进训练教材。这样无需人工标注就能造出大量练习对话。
- 具体做法（输入→关键操作→输出）：
  - 输入：已有（较小）的多轮 Text-to-SQL 数据集 + 目标数据库 schema。
  - 关键操作：
    1. 设计 SQL-to-Text 模型：以采样出的「目标查询（goal query，代表用户意图）」为条件，生成对应的自然语言问句（扮演用户）。
    2. 自对弈：生成的问句交给一个 text-to-SQL 语义解析器翻译，形成「用户—parser」的多轮交互。
    3. 过滤（filter）：筛掉不合理/不一致的 synthesized 交互。
    4. 再训练（retrain）：用增强后的数据重新训练模型。
  - 输出：扩充后的多轮训练集 + 在 SParC/CoSQL 上更鲁棒的 parser。
- 形式化要点：核心是「goal query 条件化的 SQL→Text」与「Text→SQL 解析」的闭环自生成；关键在于过滤保证合成数据质量。
- 理论性质 / 保证：🔧 本文为经验性方法，未声明形式化保证；具体过滤准则见原论文。

## 4. 实验结论（概览）
- 对比基线、数据集、指标：在 SParC 与 CoSQL 两个广泛使用的跨领域多轮 Text-to-SQL 数据集上，对比一个强基线（strong baseline）；指标为对应基准的准确率（exact-set-match / 对话级准确率等）。
- 结论方向：
  1. self-play 提升了强基线在 SParC 与 CoSQL 上的准确率。
  2. 分析表明 self-play 能模拟多种对话主题关系、增强跨领域泛化、并改善 beam-search 表现。
