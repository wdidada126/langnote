## 一句话总结

稀疏张量编译器让用户写高级代码就能算稀疏张量，但"先做哪步聚合、用什么遍历顺序"这些决定仍要用户自己拍；Galley 把数据库世界的基于代价的查询优化搬进张量编程，用户只写"要什么"，系统自动决定"怎么算"。

## 0. 给新手的阅读前置（背景知识地图）

子方向解决什么大问题？ 数据分析/机器学习里大量计算本质是稀疏张量运算（_join 上的 ML、子图计数、推荐系统的因子分解等）。写稀疏张量程序时，计算顺序的差异可以让性能差几个数量级——这正是数据库优化器 50 年来解决的同一类问题。

为什么难？
- 同一个张量代数表达式有多种等价的求值计划（先 join 哪两个、先对哪个轴求和），搜索空间巨大。
- 稀疏性使得"代价"极难估计：中间结果的大小取决于数据的具体稀疏模式。
- 稀疏张量编译器（如 Finch/TACO）解决了"怎么高效执行给定的计算"，但不解决"该执行哪个计算"。

几类主流解法（简化对照表）：

| 路线 | 代表 | 局限 |
|------|------|------|
| 手写优化 | 用户手工改写 einsum/循环顺序 | 依赖专家经验，不可扩展 |
| 张量编译器 | TACO、Finch | 只编译"给定的"程序，不做计划选择 |
| 数据库优化器 | System-R 风格 CBO | 传统上只处理 join + 聚合（sum）等，算子覆盖窄 |
| 本文：张量代数的 CBO | Galley | ——（把 CBO 下降到张量编译器 IR） |

本文属于哪一类？ 数据库优化器路线在张量世界的移植，且是两个"首次"：首个对稀疏张量代数做基于代价的下降（cost-based lowering）到稀疏张量编译器命令式语言的系统；首个能优化求和与乘积之外任意算子的系统。

关键名词直觉解释：
- FAQ 框架（Factorized Queries）：一类关于"聚合查询如何高效分解求值"的理论框架，源自数据库因子化查询理论；本文对其做了扩展。
- 下降（lowering）：编译术语——把高级声明式表达翻译成低级可执行形式；这里指把张量代数翻译成张量编译器的命令式语言。
- 聚合步骤（aggregation step）：把"多维求和/乘积/任意算子归约"拆成的一个个可独立优化的子计算单元。

## 1. 问题背景与动机

- 前人工作简述：张量编程抽象允许用户通过高级命令式接口写高性能程序；稀疏张量编译器（TACO、Finch 等）把该范式扩展到稀疏张量（摘要）。
- 前人缺陷 / 未解决问题（逐条）：
  1. 用户仍需做复杂决策：程序结构和内存布局的选择（遍历顺序、中间结果物化等）依然压在用户身上（摘要原话）。
  2. 没有张量版 CBO：此前无人对稀疏张量代数做基于代价的下降到张量编译器 IR。
  3. 算子覆盖窄：既有优化（含数据库对 polymatroid/FAQ 类理论的应用）基本只覆盖求和与乘积；max、min、比较等任意算子的优化是空白。
  4. 跨领域执行器不通吃：张量框架与关系数据库各擅一隅，缺一个把两边优长接起来的中间层。

## 2. 核心方法

最直观类比：把 SQL 优化器塞进张量编程世界。你写 einsum 风格的"要什么"（比如"对这几个稀疏矩阵按这几种模式做运算再归约"），Galley 像老练的优化器一样翻遍等价计算计划，挑最便宜的，再翻译成稀疏张量编译器（Finch）能高效执行的代码。

具体做法（输入 → 关键操作 → 输出）：
- 输入：用户编写的声明式张量程序（张量代数表达式，允许求和/乘积之外的任意算子）。
- 关键操作（摘要核实的两步路线）：
  1. 分解：通过对 FAQ 框架的新颖扩展，把输入程序分解为一系列聚合步骤；
  2. 逐优化与下降：对每个聚合步骤基于代价进行优化（选择等价计算方案），并转换为具体程序，交给稀疏张量编译器编译执行。
- 输出：经优化、由稀疏张量编译器执行的高效张量程序。

形式化要点：基于 FAQ 框架的扩展（🔧 扩展的精确定理与代价模型细节查原论文后补）。

理论性质/保证：分解正确性有 FAQ 理论支撑；性能保证为实验性（🔧 详见原论文）。

## 4. 实验结论（概览）

- 对比基线：竞争性张量/ML 方法（joins 上的 ML 任务）、最先进关系数据库（子图计数任务）（摘要口径；具体系统名 🔧 查原论文）。
- 指标与结论方向：
  - joins 上的机器学习：比竞争方法快 1–300 倍；
  - 子图计数：比最先进关系数据库快 5–20 倍；
  - 优化开销极小（优化器自身耗时几乎不拖后腿）。
