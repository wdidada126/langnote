## 一句话总结

让 LLM 把自然语言变成 SQL，在企业级大数据库上会碰到四大难题：目录太大、schema 太大、生成的 SQL 可能跑不通、自然语言本身有歧义。CHESS 用四个各管一段的 agent 组成流水线——先检索相关信息、再剪枝 schema、然后生成并迭代打磨候选 SQL、最后用"自然语言单元测试"验证——在 BIRD 测试集上，开源模型做到 71.10% 准确率（距最强闭源方法 2% 以内），LLM 调用量省约 83%。

## 0. 给新手的阅读前置（背景知识地图）

- **子方向解决什么大问题**：Text-to-SQL——把"上季度华东区销售额 top 10 的产品是什么"翻译成能直接执行的 SQL。它是"自然语言当数据库界面"的核心，LLM 时代重新爆红。
- **为什么难**（摘要列的四条，正是 CHESS 四个 agent 的分工依据）：
  1. 数据库**目录（catalog：表/列的描述）与取值**规模巨大，塞不进 prompt；
  2. 需要跨**大 schema 推理**（几十上百张表时 LLM 会迷路）；
  3. 要保证生成 SQL 的**功能正确性**（能跑、且跑对）；
  4. 自然语言问题天然有**歧义**。
- **几类主流解法**：

| 路线 | 思路 | 代表 |
|------|------|------|
| 微调专用模型 | 在 Text-to-SQL 数据上 fine-tune | PICARD、ResdSQL 等 |
| 提示工程单模型 | schema linking + 精心 prompt | C3、DIN-SQL |
| **多 agent 流水线** | 拆成检索/选择/生成/验证分工 | **CHESS** |
| 微调 + 强化 | RL 打磨生成策略 | CSC-SQL 等 |

- **本文属哪类**：多 agent 流水线（无需微调，模型可插拔，支持开源本地模型 = 隐私友好）。
- **3 个关键名词直觉**：
  1. **Schema linking/选择**：从全库几十张表里挑出回答这个问题真正用得上的几列几表——token 省、准确率还升；
  2. **候选生成与迭代细化**：先生成多个候选 SQL，再按数据库返回的反馈（错误信息、执行结果）一轮轮修；
  3. **自然语言单元测试**：把问题的每个约束（"top 10"、"按销售额降序"）写成一条自然语言断言，让 LLM 检查候选 SQL 的执行结果是否逐条满足——相当于给 SQL 做单元测试。

## 1. 问题背景与动机

- **前人工作简述**：Text-to-SQL 是长期研究问题（Spider 时代以微调模型为主）；BIRD 基准引入真实大库后，"工业级规模"成为分水岭；LLM 出现后 in-context 方法（C3 等）成为主流。
- **前人缺陷（摘要四条难点的反面，逐条）**：
  1. **大 catalog/大取值塞不下**：直接把全库 schema 喂给 LLM 不可行，多数方法只能处理玩具级库；
  2. **大 schema 上推理失准**：表多时 LLM 选错表/列是主要错误来源之一；
  3. **功能有效性无保证**：生成的 SQL 可能语法错、或语义与问题不符，缺少系统化验证环节；
  4. **歧义无处安放**：自然语言的多解性（"最好"是按销量还是按利润？）未被结构化处理；
  5. **隐私与成本**：闭源 API 准确率领先但企业不能把数据发出去，且 token 成本高。

## 2. 核心方法

- **最直观类比**：把"一个人裸考"改成"四人流水线工厂"：资料员（IR）先把考题涉及的资料翻出来，审题员（SS）把不相关的书页全部抽走，答题员（CG）草拟多份答卷并反复修改，质检员（UT）拿着逐条验收标准把不合格答卷打回——每一步都只让 LLM 看它必须看的东西。
- **具体做法（输入 → 关键操作 → 输出）**：
  - 输入：自然语言问题 + 数据库（含目录与值）；
  - 关键操作① **Information Retriever（IR）**：抽取与问题相关的数据/取值（keyword 匹配、LSH 相似度、列值过滤等）；
  - 关键操作② **Schema Selector（SS）**：把庞大 schema 剪枝成可管理的子 schema（先基于局部信息筛列，再让 LLM 精选），同时化解部分歧义；
  - 关键操作③ **Candidate Generator（CG）**：在子 schema 上生成高质量候选 SQL，并**迭代细化**（带执行反馈的多次修订）；
  - 关键操作④ **Unit Tester（UT）**：把问题约束转成**基于 LLM 的自然语言单元测试**，逐条验证候选 SQL，选出通过者；
  - 输出：经过验证的最终 SQL；
  - 框架各环节**可配置**：可按算力/隐私预算选择是否启用某 agent、用开源还是闭源模型。
- **形式化要点**：🔧 各 agent 的输入输出契约与迭代细化/测试生成的 prompt 结构查原文第 3 节后补。
- **理论性质/保证**：无理论保证；工程保证 = UT 的逐约束验证 + 全程开源模型可本地部署（隐私保留）。

## 4. 实验结论（概览）

- **基准**：BIRD（真实大库 Text-to-SQL 基准）；
- **对比**：闭源最强方法 + 开源模型方法群；
- **指标**：执行准确率（EX）、LLM token 用量、LLM 调用次数；
- **结论方向（摘要核实数字）**：
  - Schema Selector 使准确率提升约 **2%**、LLM token 减少 **5×**；
  - 在**使用开源模型的方法中**达到 SOTA（隐私可部署）；
  - 高算力预算配置下 BIRD test 准确率 **71.10%**，距领先闭源方法 **2% 以内**，LLM 调用约省 **83%**；
- 🔧 各配置完整消融表、与 DIN-SQL/C3/MAC-SQL 等逐一对比数字，查原论文后补。

## 7. 2026 视角（🔧）

- 多 agent 流水线（检索→剪枝→生成→验证）已成为工业界 Text-to-SQL 的主流架构范式，CHESS 是该范式的代表与常被引用基线；
- BIRD 榜单此后被新方法不断刷新（含 XiYan-SQL 等多生成器集成路线，本仓库有收录），准确率水位持续上移 🔧 当前最高分查 BIRD 官方榜单；
- 趋势：schema linking 与 LLM 长上下文能力互相博弈（上下文越长越不依赖手工剪枝，但成本与噪声仍在）；"自然语言单元测试/验证"思想泛化到 agent 输出可靠性方向；本地开源模型 + 隐私部署是企业落地的默认选择。

## 8. 新手学习路线
