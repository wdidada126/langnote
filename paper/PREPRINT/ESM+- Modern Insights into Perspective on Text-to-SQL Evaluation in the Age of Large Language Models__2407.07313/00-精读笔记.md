## 0. 给新手的阅读前置（背景知识地图）

**这个子方向解决什么大问题？** Text-to-SQL 就是「你说人话，我帮你写 SQL」。模型生成了一大段 SQL 之后，你怎么知道它写对了没有？这就是评测（evaluation）问题——听起来只是「跑一下对答案」，实际上判分本身就是个研究难题。

**为什么难？** 同一个自然语言问题可以有多种 SQL 写法：别名不同、子查询 vs JOIN、谓词顺序不同……这些都该算对。反过来，一个 SQL 可能「碰巧」跑出正确结果但逻辑是错的（比如 NULL 处理错了、边界条件错了），换个数据就错。所以「对/错」的判定必须既容忍写法差异，又不放过逻辑漏洞。

**主流评测指标分几类？**

| 指标 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| Exact Set Matching (ESM) | 把 SQL 解析成结构化表示，与金标准严格比对 | 判定确定性强、无需执行 | 太死板：写法不同但语义正确的查询被误判为错（假阴性） |
| Execution Accuracy (EXE) | 在测试数据库上执行，比较结果集 | 直觉、宽容写法差异 | 结果对了不代表逻辑对了，结构错误被漏掉（假阳性） |
| **ETM（本文）** | 同时用语法（树结构）与语义元素做增强树匹配 | 两者兼顾 | 需要解析与匹配实现，复杂度更高 |

**本文属哪类？** 第三类：结构匹配的改良派。名字里有个梗——它在「ESM（Exact Set Matching）」基础上加号升级（v1 叫 ESM+），后因实现是「增强的树匹配」而改名 ETM。

**3 个关键名词直觉解释：**
- **假阳性（false positive）**：试卷答错了但被判对——EXE 容易犯这个错；
- **假阴性（false negative）**：答案正确但被判错——ESM 容易犯这个错；
- **LLM 时代的评测特殊性**：不做微调的 LLM 生成的 SQL 风格/结构变化更大，传统指标在这类输出上失真更严重（摘要明确指出这一点，是本文动机的核心）。

## 1. 问题背景与动机

- **前人工作简述**：Text-to-SQL 评测长期由两大指标把持——Spider 等基准沿用的 Exact Set Matching Accuracy (ESM)，以及更常见的 Execution Accuracy (EXE)。它们让该领域十年来的排行榜成为可能。
- **前人缺陷（摘要逐条）：**
  1. ESM 的「rigid matching（死板匹配）」会漏掉**语义正确但风格不同**的查询——把好答案判成错的；
  2. EXE 会**高估正确率**：它忽略「恰好产出正确输出」的结构性错误（比如隐式 NULL 语义、重复行处理），数据一换就翻车；
  3. 这两个问题在评估**不做微调的 LLM 输出**时尤其严重，因为 LLM 生成的 SQL 在风格和结构上比微调模型更加五花八门，指标失真被放大；
  4. 也就是说：**排行榜上的数字可能系统性偏离真实能力**，而这会影响整个领域的方向判断——这是「评测方法论」级别的问题。

## 2. 核心方法

**最直观类比**：批改作文。ESM 是「逐字逐句必须和范文一样」（错杀改动句式的好文章）；EXE 是「中心思想差不多就给分」（漏掉论据是编的学生）；ETM 是「先看文章骨架（结构）是否成立，再看用词达意（语义）是否等价」。

**具体做法（输入 → 关键操作 → 输出）：**
- 输入：模型生成的 SQL + 金标准 SQL（+ 相应数据库 schema）；
- 关键操作：将双方 SQL 解析为语法树，进行**增强树匹配**——同时比对语法元素（树的结构、子句组织）与语义元素（谓词、投影、聚合等语义成分），从而既容忍「语义等价的改写」，又识别「结果碰巧对但结构错」的情况；
- 输出：判定「正确 / 错误」，并可进一步给出与 ESM/EXE 的分歧案例统计。

**形式化要点**：摘要未给出形式化定义的细节；树匹配的具体规则（如何定义等价、如何处理嵌套子查询与别名等）🔧 以论文正文为准。

**理论性质/保证**：本文属评测方法论文，无性能定理；其「保证」体现为经验性的低误判率（见下）。

## 4. 实验结论（概览）

- **对比对象**：EXE 与 ESM 两大现有指标；
- **评测对象**：9 个基于 LLM 的模型（摘要明言「evaluating nine LLM-based models」；具体哪 9 个 🔧 查正文）；
- **指标**：假阳性率与假阴性率（指标自身的误判率，而非模型能力排名）；
- **结论方向**：
  1. EXE 与 ESM 的假阳性 / 假阴性率**最高可达 23.0% 与 28.9%**（摘要给出的核实数字）——即现有排行榜上有相当比例的判定是错的；
  2. ETM 将这两项分别压到 **0.3% 与 2.7%**（摘要核实数字）；
  3. 作者据此认为 ETM 为社区提供了更稳健可靠的 Text-to-SQL 评测方式，并开源了脚本。
- 🔧 各模型在具体基准（如 Spider 族）上的完整对比表、逐模型数字，查原论文后补。

## 7. 2026 视角（🔧）

- LLM 时代 Text-to-SQL 评测正在从「单一执行准确率」转向**多维度评测**：执行等价性校验、语义等价判定（甚至用 LLM 判等，如 LLM-SQL-Solver 一类工作）、鲁棒性诊断与歧义处理都在并行发展；
- 工业界的 Text-to-SQL 产品（BI 助手、ChatBI 等）更关心「结果可信度」，因此对假阳性（不可靠回复）的容忍度远低于学术榜单——本文指出的 EXE 高估问题在生产环境里被持续放大；
- ETM 这类结构化指标能否成为社区标准，取决于解析器生态与方言覆盖；近年趋势是把「判分」本身也交给具备工具调用能力的裁判系统（LLM-as-a-judge + 形式化校验的混合）。
