## 一句话总结
给大模型挑 few-shot 例子做 Text-to-SQL 时，**例子太像不如例子多样**。这篇论文先定义了「演示多样性」怎么量化，再提出 Fused：不用人工标注，让模型把已有 SQL 反复合并（fuse）出新例子，攒出一个高多样性演示池，白拿几个点的提升。

## 0. 给新手的阅读前置（背景知识地图）

**子方向解决什么大问题**：LLM 时代的 Text-to-SQL 主流是 in-context learning——把若干「问题 → SQL」示例放进 prompt，让模型照葫芦画瓢。**挑哪些示例**（demonstration selection）直接决定准确率。

**为什么难**：
- 示例池通常人工标注，覆盖面窄、标注贵；
- 相似度检索（拿问题相似度挑例子）挑出来的示例往往高度同质，模型学不到多种 SQL 写法。

**几类主流解法（表格）**：

| 路线 | 直觉做法 | 代表 |
|------|---------|------|
| 相似检索式 | 用向量相似度从人工池里找最像的 k 条 | 多数 ICL 管线默认做法 |
| 自动生成式 | 让模型自己写/改出示例，摆脱人工池 | 本文 Fused |
| 思维链式 | 给示例加推理链 | ACT-SQL 等本仓库条目 |

**本文属哪类**：自动生成式，核心创新在「多样性」这个度量与优化目标上。

**关键名词直觉解释**：
- **Demonstration（演示）**：prompt 里的示例对（自然语言问题 + 对应 SQL）；
- **Demonstration pool（演示池）**：示例的备选库，挑 k 条进 prompt 的地方；
- **Diversity（多样性）**：池中示例在 SQL 模式上的差异程度——本文给出了可计算的度量方式（度量细节见原文 🔧）。

## 1. 问题背景与动机

**前人工作简述**：已有工作（如相似度检索、按难度排序挑选）讨论了**如何从一个人工标注的演示池中选出与用户问题相关的示例**，选法多样，但池子本身是固定的。

**前人的缺陷（逐条，来自摘要与原文论述）**：
1. **多样性不足**：人工标注的演示池天然受标注者视野限制，示例风格与 SQL 模式趋同，实验证明现有标注数据多样性不够；
2. **标注成本高**：扩池要人来写新示例，人力开销随领域数量线性增长；
3. **只研究「选」，没研究「池」**：如何度量并提升演示池本身的多样性，此前缺乏系统讨论。

## 2. 核心方法

**最直观类比**：与其让老师（人工）再手抄 100 道例题，不如让学生（LLM）把已有的例题两两「杂交」——把 A 题的嵌套结构接到 B 题的条件上——生成一批长得完全不同的新例题，反复几轮，题库的「题型覆盖面」就上去了。

**具体做法（输入 → 关键操作 → 输出）**：
1. **输入**：一个初始演示池（可来自少量人工标注，也可完全无人工）+ LLM；
2. **多样性度量**：先提出一个可计算的指标衡量池子的多样性，并用实验说明现有人工标注数据在指标上的不足；
3. **迭代融合（Fused）**：每一轮让 LLM 从池中取示例进行**融合改写**（fusing），把两条或多条示例的问题与 SQL 组合、改写出一条新的「问题-SQL」对，生成后经筛选入库，迭代多轮；
4. **输出**：一个高多样性、无需人工（human-free）或仅需极少人工的演示池；推理时按需从池中选 k 条放进 prompt。

**形式化要点**：多样性指标的形式化定义与迭代融合的收敛/停止条件见原文 🔧。

**理论性质/保证**：实证方法，无形式化理论保证；论文用指标测量 + 下游准确率双重验证有效性。

## 3. 变体 / 工程版（如有）
- 论文给出两种使用形态：**有少量人工标注**（在人工池基础上融合扩充）与**完全无人工**（从零迭代合成）两种设置，后者提升幅度更大（见下节）🔧 具体配置细节查原文。

## 4. 实验结论（概览）
- **数据集**：多个主流 Text-to-SQL 基准（含 Spider 类数据集 🔧 完整名单查原论文）；
- **对比基线**：人工标注演示池 + 相似度检索等 ICL 选例基线 🔧；
- **指标**：Text-to-SQL 生成准确率（如 execution accuracy 类指标 🔧）+ 作者提出的多样性指标；
- **结论方向**：与人工标注的演示池相比，Fused 在多个数据集上平均提升 **3.2%**（有人工标注设定）；**完全无人工标注**时平均提升 **5.0%**（摘要原文给出的数字，均为平均含义 🔧 各数据集分解值查原论文）；
- **定性结论**：实验确认现有标注演示池多样性不足，是限制 ICL 性能的一个真实瓶颈。

## 7. 2026 视角（🔧）
- 2024 年后 ICL 演示工程演化出「检索 + 生成 + 自一致性」混合管线；在 Text-to-SQL 上，演示多样性思想已延伸到 schema 链接示例与错误修正示例的构建 🔧；
- 随着模型上下文窗口变大、few-shot 需求下降，该方向的重心从「选例子」转向「给模型构造训练数据（自举合成）」，Fused 的迭代合成可视为这条数据合成路线的早期一环 🔧。
