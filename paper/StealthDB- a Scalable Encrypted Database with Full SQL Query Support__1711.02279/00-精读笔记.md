## 一句话总结
把整个数据库跑在 Intel SGX 这种「可信硬件飞地（enclave）」里，让敏感数据即使落在不可信的云服务器上也是加密的，同时只改很少的 DBMS 代码就能支持完整 SQL；原型基于 Postgres，在 2GB 未加密数据上跑完整 TPC-C，平均吞吐只比原生 Postgres 降 30%。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：把数据库放到别人（云厂商）的机器上，又不想让对方看到明文数据。加密数据库要在「数据全程加密」和「还能正常查、查得快」之间找平衡。
- **为什么难**：
  - **强加密（公钥/混淆电路）** 安全但开销巨大；
  - **弱加密（保序加密 OPE 等）** 快但泄露太多信息（leakage）；
  - **可信硬件路线** 需要特殊设备，且前人方案常围绕某款特定硬件「定制化」，换设备就废。
- **几类主流解法**：

| 路线 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 密文上的特殊密码算法 | 保序加密、可搜索加密 | 直接对密文做比较/匹配 | 功能受限、泄露模式多 |
| 通用安全计算 | 混淆电路、全同态加密 | 在密文上任意计算 | 安全但极慢，难撑事务负载 |
| 可信执行环境 (TEE) | Intel SGX、TrustZone | 硬件给一小块「飞地」跑明文，外部只看密文 | 性能好、改动小，但 TCB 与侧信道是隐患 |

- **本文属于哪一类**：TEE/SGX 路线——把 DBMS 放进 SGX enclave，明文只在 enclave 内出现。
- **2-3 个必懂关键名词**：
  - **Intel SGX (Software Guard Extensions)**：CPU 支持的「飞地」机制，在不可信主机上划出一块受硬件保护、外界（含 OS）看不见的内存与计算区域。
  - **TCB（Trusted Computing Base，可信计算基）**：系统里「必须信任」的最小代码/硬件集合，越小越安全。
  - **leakage（泄露）**：加密方案在运算时无意暴露的元信息（如访问模式、大小关系），弱加密方案泄露严重。

## 1. 问题背景与动机
- **前人工作简述**：加密数据库要么用「密文上特殊算法」（强安全但高开销 / 弱安全但大泄露），要么用「可信协处理器」（如 Cipherbase、TrustedDB 用非标准专用设备）。
- **前人缺陷/未解决问题（逐条）**：
  1. **强算法开销大**：公钥加密、混淆电路等导致显著性能损耗。
  2. **弱算法泄露多**：保序加密等暴露大量访问/顺序模式。
  3. **依赖非标准设备**：Cipherbase/TrustedDB 围绕特定硬件设计，难以迁移、通用性差。
  4. **缺完整 SQL + 可扩展事务**：许多方案只能支持受限查询或小规模负载。
  5. **改动 DBMS 成本高**：要把现有 DBMS 改造成密文友好，工程代价大。

## 2. 核心方法
- **最直观类比**：把数据库装进一个「防弹保险箱（SGX enclave）」，外面的人（云厂商、OS）只能把加密数据递进去、把加密结果拿回来，箱子里怎么算、数据长什么样他们全看不到；而且这个箱子能跑在「任意新一代 Intel CPU」上，不挑机器。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：SQL 查询与（加密的）数据库文件，运行在支持 SGX 的普通 Intel CPU 上。
  2. **关键操作一**：以 Intel SGX 为可信基构建 StealthDB，把 DBMS 的核心执行放进 enclave，明文仅在 enclave 内解密与计算。
  3. **关键操作二**：保持**很小的可信计算基 (TCB)**，从而对稳态与查询执行期间都给出相对强的安全保证。
  4. **关键操作三**：对现有 DBMS 只做**少量改动**即可接入，并支持**大规模事务负载**（transactional workloads）。
  5. **输出**：在密文数据库上执行完整 SQL（含事务），对外不泄露明文。
- **形式化要点**：核心设计目标是「小 TCB + 完整 SQL + 可扩展事务 + 少改动」；本文以系统实现与经验评估为主，未给出可证明的密码学安全界。🔧 具体 enclave 内/外职责划分与威胁模型请查正文。
- **理论性质/保证**：以「硬件信任 + 小 TCB」提供实际安全保证，并非形式化密码学证明。🔧 威胁模型与侧信道分析以论文原文为准。

## 4. 实验结论（概览）
- **对比基线**：未修改的原生 Postgres（运行在 2GB 未加密数据集上）。
- **数据集/负载**：完整 TPC-C 基准（事务型）。
- **评价指标**：平均吞吐 (average throughput)。
- **结论方向（摘要给出的已核实数字，可直接引用）**：
  - 在 **2GB 未加密数据集**上，StealthDB 原型支持完整 TPC-C，**平均吞吐比未修改的 Postgres 下降 30%**。
  - 同时具备：可扩展到大规模事务负载、对 DBMS 改动小、稳态与查询执行期间相对强的安全保证。

## 7. 2026 视角（🔧）
- 机密计算（Confidential Computing）已成云厂商标配能力，SGX 之外还有 AMD SEV、AWS Nitro Enclaves 等；「把 DB 跑在 TEE 里」从论文构想走向产品（如各类机密数据库/分析服务）。
- 但侧信道、enclave 内内存上限、以及「明文仍在飞地内」的信任假设，仍是工程与研究的活话题；与密态计算（HE/OPE）的混合路线在发展。本节为趋势性判断，具体产品矩阵 🔧 查当年资料验证。
