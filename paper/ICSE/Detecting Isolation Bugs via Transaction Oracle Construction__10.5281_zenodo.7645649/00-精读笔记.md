## 一句话总结
Troc 不去「重写一个参考数据库」，而是把一条并发事务「解耦成一组各自在专属数据库视图上独立执行的 SQL 语句」作为预言：只要真实事务执行结果和这些独立语句的结果不一致，就说明数据库违反了它声称的隔离级别——在 MySQL/MariaDB/TiDB 上挖出了一批此前未知的隔离缺陷。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：数据库用「事务 + 隔离级别」保证多用户并发时数据不出错。但实现有 bug 时，数据库会悄悄违反自己声称的隔离级别（如 REPEATABLE READ），导致查到错数据/错状态——这就是 isolation bug。自动测出它很难。
- **为什么难**：传统验证要么要「参考实现」，要么只支持很简单的操作/历史，覆盖不到真实库的复杂事务特性。
- **几类主流解法**：

| 路线 | 代表 | 思路 | 取舍 |
|------|------|------|------|
| 历史图检查 | ELLE 等 | 从执行历史建依赖图查违例 | 只支持简单操作、不支持谓词 |
| 差分测试 | SQLancer/DT2 等 | 多库结果比对 | 需多库语义一致 |
| 预言构建（本文） | Troc | 解耦事务成独立语句做预言 | 不需参考库，但构造视图复杂 |

- **本文属哪一类**：基于「事务预言构建（Transaction Oracle Construction）」的隔离缺陷检测。
- **关键名词直觉**：
  - **隔离级别（Isolation Level）**：数据库承诺的并发行为契约，如 Read Committed / Repeatable Read / Serializable。
  - **Oracle（预言）**：测试中判断「系统这次行为对不对」的标准答案来源；Troc 用「独立语句执行结果」当预言。
  - **解耦成独立语句**：把事务里多条 SQL 拆开、各自在按隔离语义构造的视图上跑，等价于「串行、无干扰」的预期结果。

## 1. 问题背景与动机
- 前人工作简述：已有事务可靠性保障多依赖简单数据结构与执行历史验证隔离性，不支持实际库中多数常见事务特性。
- 前人缺陷/未解决问题（逐条）：
  1. 需要参考实现或只支持受限操作/历史。
  2. 覆盖不到真实 DBMS 的复杂事务特性。
  3. 难以自动、通用地检测隔离级别被违反。

## 2. 核心方法
- **最直观类比**：把一条并发事务想成「几个人同时改同一张表」。Troc 的做法是：把每个人的动作单独、按顺序、在一份「干净副本」上重做一遍，得到「本该得到的结果」；如果数据库真实跑出来的和这份副本不一致，就说明有人（数据库）没守规矩。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **解耦（Decouple）**：把一条事务拆成若干独立 SQL 语句。
  2. **构造视图（View Construction）**：按声称的隔离级别，为这些语句各自构造「专属数据库视图」（如给 SELECT 构造变更历史视图、给 UPDATE 附加新数据版本）。
  3. **独立执行**：在各自视图上执行独立语句，得到预期结果。
  4. **比对**：真实事务执行结果与独立语句结果不一致 → 报告 isolation bug。
  5. 输出：被触发的隔离缺陷及复现用例。
- **形式化要点**：核心是「按隔离语义构造视图 + 独立语句执行」作为预言；支持常见事务特性而不需参考库。超参数以论文为准 🔧。
- **理论性质/保证**：给出「独立语句结果即等价于串行预期」的构造逻辑（摘要称构建预言而不重实现参考库）。

## 4. 实验结论（概览）
- 对比基线/对象：在 MySQL、MariaDB、TiDB 三个广泛使用的关系库上实测。
- 指标：发现的隔离缺陷数量（含新缺陷）。
- 结论方向：
  - ICSE 会议摘要：在最新版本中检测到 **5 个此前未知**的隔离缺陷。
  - 中科院软件所新闻稿：共发现 **12 个**事务相关隔离缺陷，其中 **7 个**为尚未披露的新缺陷。

## 7. 2026 视角（🔧）
- 数据库正确性/一致性测试是系统领域热点；Troc 的「预言构建」思路影响后续 TxCheck 等工作。国产数据库也在引入此类自动化测试。
- 近年趋势：把预言构造与复杂谓词/多语句依赖结合（TxCheck）、以及把隔离检查做成可扩展黑盒工具（IsoVista/VeriStrong 系）。具体生态 🔧 查当年资料。

## 8. 新手学习路线
- **10 分钟**：读摘要 + 本笔记第 0、2 节，理解「解耦事务 + 按隔离语义造视图 + 比对」。
