## 0. 给新手的阅读前置（背景知识地图）

- **子方向解决什么大问题**：传统 text-to-SQL 研究假设"一个固定数据集 + 一次性训练"。但实际系统面对的是不断到来的新数据库/新业务（任务流），模型必须持续适应。
- **为什么难**：
  1. 新任务几乎没有标注（标注 SQL 又贵又需要懂业务）——数据稀缺；
  2. 重训整个模型成本高，而且历史任务数据往往因隐私/存储原因不能全量保留；
  3. 只在新任务上学会导致**灾难性遗忘**——把学过的 SQL 语法结构、模式链接能力"忘掉"。
- **几类主流解法**：

| 路线 | 直觉 | 代表思想 |
|------|------|----------|
| 全量重训 | 数据都留着，来一个任务重训一遍 | 简单但成本高、隐私受限 |
| 正则化持续学习 | 限制重要参数的改动 | EWC 一类 |
| 记忆回放 | 存一小撮旧样本，混合进新任务训练 | 情景记忆回放（本文采用） |
| 半监督学习 | 用伪标签利用无标注数据 | 自训练（本文采用） |
| **本文：SSL + CL 结合** | 两条腿走路：伪标签扩数据 + 记忆回放防遗忘 | SSCL（本文） |

- **本文属哪类**：半监督 + 持续学习的交叉路线，且专门为"监督受限（supervision-limited）"的任务流设计。
- **关键名词直觉解释**：
  - *任务流（task stream）*：任务按时间顺序排队到来，训练完当前任务才能见到下一个，且旧数据不再完整可得。
  - *自训练（self-training）*：模型先给无标注样本预测"伪标签"，挑可信的当训练数据。
  - *情景记忆回放（episodic memory replay）*：维护一个小存储区保存少量有代表性的旧样本，新任务训练时混入回放，对抗遗忘。

## 1. 问题背景与动机

- 前人工作：text-to-SQL 主流工作（Spider/WikiSQL 榜单）面向单任务、固定数据划分；持续学习社区有 EWC、记忆回放等方法，但鲜少针对 text-to-SQL 的结构特点；也已有工作开始关注跨数据库泛化。
- 前人的缺陷（论文动机）：
  1. 现有 text-to-SQL 方法默认新任务的数据库上有充足标注——现实里恰恰没有；
  2. 标注少时直接微调极易在**没见过的数据库**上过拟合；
  3. 为省成本只在新任务上训，会遗忘已学的 SQL 结构与数据库模式知识；
  4. 全量重训要求保留所有历史数据，成本与隐私都不可行；
  5. SSL 与 CL 两个社区各自为战，二者的内在互补关系（伪标签可改善回放质量、记忆可反过来辅导自训练）此前没有被用于 text-to-SQL。

## 2. 核心方法

- **最直观类比**：实习生每接一个新项目（新数据库），没有老员工全程带（缺标注），就自己先试着写、把靠谱的自写记录留档（伪标签）；同时随身带个小本本抄录以往项目的关键案例（记忆回放），每周翻一遍避免手生——两件事互相加强。
- **具体做法（输入→关键操作→输出）**：
  1. 输入：按时间到达的 text-to-SQL 任务流，每个任务 = 一个数据库 + 少量标注 + 较多无标注问题；
  2. **方案一 Vanilla**：对无标注样本做自训练生成伪标签实例扩充监督数据；用"情景记忆回放"替代全量重训，在效率与旧任务性能间折中；
  3. **方案二 SFNet（改进版）**：利用 CL 与 SSL 的内在联系——用记忆里的历史信息辅助当前的自训练（提升伪标签质量），同时把高质量伪实例反哺进记忆，改善未来任务的回放效果；
  4. 输出：在整条任务流上都能保持较好性能的 text-to-SQL 模型。
- **形式化要点**：持续学习形式化为任务序列 t=1..T 上的顺序优化；SSL 部分为伪标签损失 + 监督损失；记忆为容量受限的缓冲区（🔧 选择/更新策略与损失公式查原文第 3 节）。
- **理论性质**：无理论保证，属实证方法。

## 7. 2026 视角（🔧）

- LLM 时代 text-to-SQL 默认用大模型 + few-shot，"持续学习"形态变化为：检索增强 + 微调小模型做路由/回退的组合；但"新数据库标注稀缺"的问题在 BIRD、Spider 2.0 类真实基准上依旧尖锐。
- 本文的 SSL+CL 互补思想可迁移到今天的数据智能体场景（无标注的新库、新表持续接入），伪标签 + 记忆回放仍是低成本方案；是否已被后续 text-to-SQL 持续学习工作直接引用/扩展 🔧 查引用链后补。
