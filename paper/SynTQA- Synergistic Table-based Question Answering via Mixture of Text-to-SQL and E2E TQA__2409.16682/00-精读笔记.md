## 一句话总结
表格问答有两条主流路线：Text-to-SQL（先生成 SQL 再执行）和端到端 TQA（模型直接读表给答案）。论文先把两条路线各自的强项测清楚（前者擅长算术运算和长表，后者擅长歧义问题、非标准表头和复杂表格内容），然后用一个「与模型种类无关」的答案选择器把两边的候选答案挑出最好的，集成之后明显强于任何单一模型。

## 0. 给新手的阅读前置（背景知识地图）
- **这个子方向解决什么大问题**：给用户一张表和一个自然语言问题，让系统直接给出答案——这就是表格问答（Table-based QA, TQA）。它是企业 BI「用说话的方式查数据」的基础能力。
- **为什么难**：
  - 表格形态千奇百怪：列名不规范、缺失、单元格里塞复合内容；
  - 问题类型跨度大：有的要做算术/聚合，有的要消歧，有的要读长表；
  - 标注与评测难：同一问题可能有多种「正确」的推理路径。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 语义解析（Text-to-SQL） | RAT-SQL、RESDSQL、DAIL-SQL | 先生成 SQL，再执行拿答案 | 可解释、可做算术；怕歧义和非标准表头 |
| 端到端 TQA（E2E） | TAPAS、TableLLM 类 | 模型直接读表输出答案 | 容忍歧义与复杂内容；算术/长表易错 |
| 混合 / 集成 | **SynTQA** | 两条路都跑，再用选择器挑答案 | 更稳，但要额外训练/调用选择器 |

- **本文属于哪一类**：第三类——而且是「模型无关（agnostic to any model types）」的集成框架。
- **必懂关键名词（直觉版）**：
  - **E2E TQA**：不给中间的 SQL，模型端到端地「看着表直接回答」，类似人眼看表答题。
  - **答案选择器（answer selection）**：多个模型各给一个答案，由它来判断该信谁。
  - **feature-based / LLM-based selector**：前者用手工设计的特征打分，后者直接让大模型来判。

## 1. 问题背景与动机
- 前人工作简述：Text-to-SQL 与 E2E TQA 两条路线都在多个 benchmark 上取得了成功，但一直是各做各的。
- 前人缺陷 / 未解决问题（逐条）：
  1. **从未被放在同一基准下系统比较**：两条路线的强弱之前没有被量化对比过。
  2. **协同效应完全未被探索**：没有人研究「把两者结合」能不能更好。
  3. **单一路线存在能力盲区**：Text-to-SQL 在歧义问题、非标准 schema、复杂表格内容上吃力；E2E TQA 在算术与长表上吃力。

## 2. 核心方法
- **最直观类比**：像「两位专科医生会诊」——一位擅长算账，一位擅长读复杂病历；最后由一个分诊台（选择器）来判定该采纳谁的结论。
- **具体做法（输入 → 关键操作 → 输出）**：
  - 输入：一张表 + 一个自然语言问题。
  - 关键操作：
    1. **两条并行通路**：一边跑 Text-to-SQL（生成 SQL → 执行得到答案），一边跑 E2E TQA（直接生成答案）；
    2. **候选答案集合**：把两边（可含多个模型）的结果作为候选；
    3. **答案选择器**：用 feature-based 或 LLM-based 的选择器，从候选中挑出最终答案。
  - 输出：最终答案。
- **形式化要点**：选择器对模型类型无感知（model-agnostic），因此可以接入任意 Text-to-SQL 模型和任意 E2E TQA 模型；feature-based 选择器使用的具体特征集 🔧 查原论文。
- **理论性质 / 保证**：**无**理论保证（论文以实证为主 🔧）。

## 3. 变体 / 工程版（如有）
- 选择器的两种实现：**feature-based**（轻量、可离线训练）与 **LLM-based**（零训练、调用成本更高）。
- 由于框架与模型类型无关，也可用于「多个 Text-to-SQL 模型 + 多个 E2E 模型」的更大规模集成（🔧 以原论文为准）。

## 4. 实验结论（概览）
- 对比基线：各个被集成的单一模型（state-of-the-art Text-to-SQL 模型与 E2E TQA 模型，具体清单 🔧 查原论文）。
- 数据集：多个 benchmark 数据集（具体名称 🔧 查原论文）。
- 评价指标：答案正确率（accuracy）。
- 结论方向：无论用 feature-based 还是 LLM-based 选择器，集成后的性能都**显著优于**各个单独模型。

## 7. 2026 视角（🔧）
- 表格问答在企业 BI 场景依然是刚需；主流实现是「LLM 生成 SQL + 执行反馈修正」，或用长上下文模型直接读表。
- 「多通路 + 选择器/裁判」的思路已经很常见（自一致性采样、执行结果投票、rerank 都属于这一族）。
- 近年趋势：把通路选择做成可学习的路由、用执行结果作为最强特征、以及把成本（token 与延迟）纳入优化目标。本节为趋势性判断，具体数字 🔧 查当年资料。

## 8. 新手学习路线
- **10 分钟**：读摘要 + 本笔记 §0、§2，记住「Text-to-SQL 擅长算术/长表，E2E 擅长歧义/非标准表头/复杂内容」。
- **30 分钟**：在一个小型表格问答数据集上，手工统计「哪些问题 SQL 路线错、哪些 E2E 路线错」，体会互补性。
- **进阶**：复现两种选择器并对比成本/收益；思考选择器能否用执行结果、表结构特征作为输入；阅读 2401.12379 的误差分析做对照。
