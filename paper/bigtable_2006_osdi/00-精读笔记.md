## 一、背景与它回应的问题

### 1.1 时代前提：Google 的三类需求压垮了"关系或文件"二选一

2000 年代中期的 Google 产品（搜索网页索引、地图、Google Earth、翻译、GMail/Orkut 的用户画像）对存储提出共同要求：**PB 级数据、数千台廉价机器、低延迟随机读写、大量列的"表"、原子性只需单行、schema 要能每周演化**。同时满足"关系语义 + WebScale"的商用 RDBMS 不存在，垂直分库分表又让运维不堪重负；纯 GFS 只解决"大文件顺序读写"，随机点查与可变记录无能为力。

论文的答案是一个**中间物**：不做 SQL、不做多行事务，但提供有序行、稀疏列、多版本单元格与单行原子性的**半结构化分布式存储**，并把自己完全架在 GFS + Chubby 两个内部设施之上。它用"抛弃关系代数换水平扩展"的姿态，成为 NoSQL 时代事实上的原型机（HBase、Cassandra、Spanner 的存储层都从它派生）。

### 1.2 设计目标一句话

论文 §1 列出的目标：**行级（而非任意粒度）的强一致性 + 很高可用性 + 支持模式（schema）的动态演化 + 能同时服务需要事务与不需要事务的应用 + 实现简单、运维省心、覆盖面广（wide applicability）**。注意"实现简单"是真目标：Bigtable 把一切难题（持久性、复制、锁、命名）外包给 GFS 与 Chubby，自己只做"有序稀疏映射的分片服务"这一件事。

## 二、核心设计精读

### 2.1 数据模型：一个稀疏的、分布式的、排序的多维映射

论文对表的定义是一句话：**table = sparse, distributed, multi-dimensional sorted map**，按 `(row key, column key, timestamp)` 三元组索引，值是客户视角不透明的字节序列：

```
row-key │ column-family:qualifier@timestamp → value(bytes)
────────┼──────────────────────────────────────────────────
"cr:foo"│ content:title@1141848522 → "The Many Dimensions..."
        │ anchor:cntr@1141848523   → "37"
"cr:bar"│ lang:en@1141848522       → "The World Wide Web"
```

- **行键任意字符串、读写单行原子、按字典序存储**；行不跨 tablet 拆分（一行再大也整体落在一个 tablet 里）。行的字典序是整个系统的承重墙：range scan、点查前缀、tablet 分裂、客户端事务都建立在它上面（Google 的经验是设计 row key 要"预知查询模式"，如把 URL 逆序、给时间戳加前缀）。
- **列族（column family）**是列的物理分组与访问控制/加密单元，一个族内列通常同生共死（schema 只声明族，qualifier 可随时新增——"schema-on-write 的最低限度版本"）；**时间戳**实现单元格多版本，可配保留 N 个版本。
- 与关系模型对照：关系模型要求每行每列一个值（第一范式）、模式固定、行无序；Bigtable 的"超记录（super-record）/稀疏列/行有序/族内动态 qualifier"每一项都在突破这些纪律（详见 §四与 Codd 笔记对照）。

### 2.2 总体架构：一切皆 tablet，tablet 之下全托给 GFS

```
        客户库(可缓存定位) ──扫描/读写(按行)──┐
        管理工具(建表/快照)                    │
   ┌──────────────────────────────────────────▼──────────┐
   │ Master(可选高可用,同一时刻活跃者唯一)                   │
   │  分配tablet到服务器·负载均衡·失活回收·GC·建表/删除      │
   └────┬─────────────────────────┬───────────────────────┘
        │ 分配/租约                │ tablet 定位(根目录三级)
   ┌────▼─────────┐          ┌────▼──────────────────────┐
   │ TabletServer×N│◄─读写────►│ Chubby: 锁/命名/选主/定位   │
   │  服务多个tablet│          │   root → METADATA → .META. │
   │  memtable     │          └───────────────────────────┘
   │  +commit log  │
   │  缓存读SSTable │
   └────┬─────────┘
        │ 全部持久化文件(单副本交给GFS,64KB块3复制)
   ┌────▼─────────────────────────────────────────────────┐
   │ GFS 分布式文件系统: SSTable/commit log/快照文件          │
   └──────────────────────────────────────────────────────┘
```

- 表的水平切分为 **tablet**（论文典型值：随 tablet 数增多逐渐增大到 100–200MB 量级；精确阈值以论文图注为准，本笔记不作逐字引用），一个 tablet 同一时刻只由一个 tablet server 的"租约"持有，行有序 ⇒ "分配一行到哪台机器"退化为"行键落在哪个区间"，天然支持 range scan。
- Master 非常薄：不服务数据读写，只做 tablet 的调度/负载均衡/GC/模式变更；客户直接从 Chubby 与 METADATA 表解析定位后**绕过 Master** 访问 tablet server——Master 挂了只是无人调度，读写不受影响。这是"控制面/数据面分离"的教科书样本。

### 2.3 tablet 定位的三级结构（Chubby 之上找 tablet）

```
Chubby 文件 "/bigtable/loc2" ──► 存 METADATA 表 root tablet 的位置
METADATA 表(系统表,前两个tablet) ──► 每个 tablet 一行,记 "表名,行前缀" → tablet server
   ├─ 第1个tablet: .META. 表自身的定位 + "0"~ 之前所有表的 tablets
   └─ 第2个tablet: "~" 之后的(客户端表名若以 ~ 开头,直接放第3个tablet避混)
.META. 表: 每个用户表 tablets 一行一行全列出
```

客户端库缓存定位、缓存失效自动回源重查；METADATA 本身也是 Bigtable 表（自举靠 Chubby 里的 root 位置）。定位最坏三次查找（Chubby + 两个 METADATA tablet），配合客户端缓存把摊销成本压到近零。这解决了"分片再多，元数据不能成为瓶颈"的问题，代价是 Chubby 进入关键路径（见 §2.6）。

### 2.4 LSM 三层存储栈：memtable + SSTable 家族 + compact

SSTable 是 Bigtable 也是后来一切 LSM 系统的原子概念：**不可变的、按键有序的 string→string 稀疏索引文件**，存在 GFS 上，内部 64KB 块（可整体压缩；块间可用前缀/熵编码——论文对编码只给了"块内可压、可用两种方案"的定性描述），文件尾放块索引，配 Bloom filter：

```
一个 tablet 的读路径(列族级组织!)           写路径
 读(row,col,ts):                        写(row,col,ts,v):
   memtable(内存BufferTree)                 追加 commit log(GFS,顺序写)
   → 该列族的 SSTable 最新者                   插入 memtable
   → 同族更旧的 SSTable(逆序合并多版本)         memtable 满(典型 1–2MB)
   跳表用 Bloom filter + 稀疏索引定位           └► minor compact: memtable→新SSTable
   跨列族: 各族独立取文件再归并                  (期间旧SSTable+log 仍有效,失败可重放log)
```

三层含义展开：
1. **memtable**：可变有序结构（论文点名 BufferTree 式结构），缓冲最近写入；每次写入**同步追加** GFS 上的 commit log（顺序写让廉价盘的写带宽变成"日志带宽"）；memtable 不持久化——恢复靠 log 重放，因此恢复时长只正比于 log/memtable 而非 tablet 大小（这是相对"整 tablet 落盘"方案的关键改进，也是 LSM "以顺序换随机"的原始论证）。
2. **SSTable 家族**：一个 tablet 的多个列族各自维护一条新→旧的 SSTable 序列；**读一个单元格可能要探测同族多个 SSTable**，Bloom filter 与"只读需要的块"控制扇出。只读的 SSTable 可整体常驻内存（in-memory SSTable），点查成本趋近纯内存表。
3. **compact 策略**（论文 §5.3）：
   - *minor compact*：memtable→SSTable，高频、廉价；
   - *major compact*：把一个 tablet 的**全部** SSTable 归并成一个（顺带清理被删单元格、过期版本），触发条件是"小文件太多/死空间比例超标"；选择器**轮转**挑"垃圾最多"的 tablet 以摊平开销，且并发数受限（论文示例配置为个位数）；
   - *tablet split*：major compact 后若 tablet 仍超限，在**最大 SSTable 的字典序中点**附近一分为二，交回 Master 重新调度。
   - 这构成读放大（多文件归并）、写放大（major 全量重写）、空间放大（死版本滞留）的三角——后来 RocksDB 把这条曲线做成了可调参数系（本仓库 LSM 谱系笔记可互证）。

### 2.5 一致性、租约与"客户端粗粒度事务"的取舍

Bigtable 内建只保证**单行原子性**（含多列族多列），跨行没有事务。论文 §5.4 给了三个"客户端自助"的原子性配方，全部建立在"行租约 + 表锁 + 全 tablet 变更"原语上：

```
配方A 单行 read-modify-write:
  tablet server 发给客户行租约(限时) → 客户在租约内原子完成读改写 → 归还
配方B 跨行但单 tablet(常见: 一批相关行相邻):
  客户申请"整个 tablet 的 mutation 锁" → 批量全量变更一次提交 → 释放
配方B' 跨 tablet 的批量装载(bulk load):
  离线生成 SSTable 直写 GFS → 申请 tablet 分裂到匹配区间 → 移入表
配方C 多 tablet 大事务: ❌ 没有。要 2PC 请去 Spanner(本文之后 6 年才出现)
```

取舍逻辑：Google 内部负载大多是"聚合更新一行"（PageRank 权重、倒排列表、用户画像），单行原子够用；引入行锁/2PC 会把 Master/Chubby 拖进数据面、牺牲可用性。**把事务语义的缺口留给客户端机制和上层应用**，是"简单、可规模化的存储核心"这一论文目标（wide applicability + easy implementation）的直接兑现。

### 2.6 Chubby 依赖清单与故障语义

论文 §6 把 Bigtable 对 Chubby 的依赖列成五行：tablet 定位根文件、Master 存在性/选主锁、**每 tablet 的租约锁**（防一个 tablet 被两台服务器同时服务——correctness 的底线）、表的访问控制锁、GFS 锁服务器目录。故障语义被明确设计为：**Chubby 长时间不可用时，租约到期后全部 tablet 变只读**；短暂抖动则只影响定位读与新 tablet 分配。换言之 Bigtable 选择"用可锁性换正确性"：宁可整体降级只读，也不允许双主写。这与 Dynamo 系（always writable、最终一致）构成 NoSQL 的两极，本仓库 Dynamo/Spanner 笔记（若已建）可对照；没有 Chubby 就没有 Bigtable 的一致性承诺，这是它不能开源照搬的最大原因。

### 2.7 一次扫描的完整解剖

```
客户: Scan(table=cr, row_prefix="cr:") 
1. 客户库解析定位(缓存命中则跳过 Chubby/METADATA)
2. 对"cr:foo..cr:hzz"区间所在 tablet server 发流式 read RPC
3. 服务器对每个行区间: memtable+各列族SSTable做 k 路归并,
   按行字典序吐单元格; 谓词/时间戳过滤在服务器端完成
4. 客户翻页: 断点即"上次行键", 区间跨 tablet 时透明续接到下一服务器
→ 有序行 + 服务器端归并 = "扫描是一等公民"而非索引外快路径
```

对照 §2.3：扫描期间无任何全局协调参与，成本只取决于命中 tablet 的 SSTable 文件数与块缓存命中——性能模型清晰到可以用图 6 的定性曲线说尽（见 §三）。

## 三、实验与工程取舍

论文 §8 的实验是"小规模自证 + 生产环境定性"，而非竞品 PK：

1. **64 台服务器基准**（每台双 Xeon/4GB）：随机读吞吐随"内存中索引占比"变化显著（论文图 8：全内存索引到仅 5% 常驻，吞吐呈台阶式下降，量级为数千 ops/s 降到数百）；随机读延迟分布见图 9（**70% 在 1ms 内、99% 在 10ms 内**是常被转述的两个刻度，未逐字复核，以图注为准）；顺序扫描吞吐远高于随机点查（体现"行有序 + SSTable 块"对扫描友好）。
2. **恢复时间**：tablet 重加载耗时正比于其 commit log 尾部而非 tablet 大小（论文图 7 定性结论：恢复只需"重放少量记录 + 打开若干只读 SSTable"），这是 memtable/log 分离设计的直接红利。
3. **生产规模**（§9，定性）：撰写时 Google 内部有**上百个 Bigtable 部署**，最大的数个有 PB 级、上亿行×百万列级规模，tablet 总数十万量级、单日请求十亿量级——均为论文口径的"数十/数百/数十亿"表述，精确刻度未复核，本笔记不以精确数字引用。

深层取舍清单：

| 取舍点 | 选择了 | 放弃了 | 换来的 |
|---|---|---|---|
| 数据模型 | 稀疏有序映射、列族内动态列 | 关系模式、跨行一致性声明 | schema 周级演化、稀疏列不占空间、range scan 一等化 |
| 一致性范围 | 单行原子 + 客户端租约事务 | 多行 ACID/2PC | 核心极简、控制面不碰数据面、可用性优先 |
| 存储引擎 | LSM（log+memtable+SSTable 族） | B 树的原生读放大优势 | 廉价盘上的高写吞吐；代价=compaction 三放大 |
| 持久性外包 | GFS 单写+底层 3 副本、log 同步 | 自管复制协议 | 存储层故障域收敛到 GFS 语义 |
| 协调外包 | Chubby 租约/锁/选主 | "无协调即可用"的独立性 | 一个 tablet 只有一个写者的强正确性；Chubby 挂=全表只读风险 |
| 分片粒度 | 区间 tablet，按行数无数据迁移 | hash 分片的绝对均衡 | 免 rehash 的热点缓解、扫描局部性、分裂即扩容 |
| Master 角色 | 薄控制面，可单点 | 控制面高可用 | 实现简单；数据面在 Master 宕机时照常服务 |

## 四、与相关工作对比

- **vs Codd 关系模型（本仓库精读：[../doi_10.1145_362384.362685/00-精读笔记.md](../doi_10.1145_362384.362685/00-精读笔记.md)）**：Codd 1970 的革命是"数据独立性"——用固定关系模式换掉指针式导航，让存取逻辑与物理彻底分离；Bigtable 36 年后做了**反向运动**：保留"值不透明、无声明式查询"，却把 schema 从"表级强约束"降回"列族级弱约束"，把"无序集合"改回"有序行可导航"。可以说 Bigtable 不是回到 IMS，而是承认：**Codd 的独立性以模式可预见为前提，Web 数据模式不可预见，于是"结构"成为可选配置**。这正是"NoSQL 是对关系模型的反叛"叙事的技术版（反叛的不止 Bigtable，见 §六延伸）。
- **vs GFS（本仓库课程笔记：[../../mit6.824/gfs.md](../../mit6.824/gfs.md)、[../../courses/并行与分布式系统/MIT6.824/notes/L03-GFS分布式文件系统.md](../../courses/并行与分布式系统/MIT6.824/notes/L03-GFS分布式文件系统.md)）**：GFS 面向大文件追加写、POSIX 弱化（record append 原子）；Bigtable 在其上补了"随机读、可变、按 key 索引"。分层的意义：Bigtable 全部正确性论证只需要 GFS 的两个原语（顺序 append、文件 rename），把自己对底层的假设压到最小。
- **vs MapReduce（仓库暂无精读笔记；课程资料 [../../mit6.824/mapreduce.pdf](../../mit6.824/mapreduce.pdf)、[../../courses/并行与分布式系统/MIT6.824/notes/L02-MapReduce.md](../../courses/并行与分布式系统/MIT6.824/notes/L02-MapReduce.md)）**：MapReduce 是批处理引擎、Bigtable 是 serving 层；论文互文（MapReduce 读 Bigtable 表作为输入）——Google 用"文件+函数+表"三件把计算与存储都水平化了。
- **vs 同期 RDBMS 分片方案（中间件 sharding）**：Bigtable 的区间 tablet + 自动分裂把"分片路由/再平衡/热点缓解"内建了；中间件方案要求人肉分库分表键，扩容=数据迁移。
- **vs Dynamo（本仓库暂无该笔记；概念对照）**：同为"存储系统不卖 SQL"，Dynamo 选"始终可写 + 最终一致 + 无中心协调"，Bigtable 选"单写者 + 强一致（行内）+ 中心租约"。两者是 NoSQL 的南北两极，后来的系统基本是在两极之间连线。
- **vs Dremel（本仓库精读：[../doi_10.14778_1920841.1920886/00-精读笔记.md](../doi_10.14778_1920841.1920886/00-精读笔记.md)）**：Dremel 在 Colossus/GFS 文件上做交互式嵌套查询（列式投影），Bigtable 在同样底座上做低延迟点查/扫描（行式有序）；一个"查询要快"，一个"写入要稳"，合并起来就是后来"KV serving + OLAP 双引擎共湖"的 2006 年版本。
- **vs Snowflake（本仓库精读：[../doi_10.1145_2882903.2903741/00-精读笔记.md](../doi_10.1145_2882903.2903741/00-精读笔记.md)）**：有趣的对照是"谁拥有数据所有权"——Bigtable 的行归 tablet 服务者所有（写入必须经它），Snowflake 把所有权交给不可变文件+元数据指针（任何节点可读）。前者要租约换一致，后者用不可变免锁换弹性；同一 GFS 思想树结出的两种果实。
- **课程与书目互链（均已验证存在）**：[../../courses/并行与分布式系统/MIT6.824/notes/L04-Bigtable.md](../../courses/并行与分布式系统/MIT6.824/notes/L04-Bigtable.md)（本课的精读讲义）；[../../book/Design Data-intensive Applications.md](../../book/Design%20Data-intensive%20Applications.md)（DDIA 第 3 章把 Bigtable 数据模型讲成"列族=聚合、排序=聚簇索引"，适合作第二遍读物）。

## 六、批判与延伸

**批判性阅读：**

1. **实验是"机制自检"不是"系统横评"**：64 台机器的小基准 + 生产定性数字，没有与任何 RDBMS/sharding 中间件对比；"可扩展到 PB"的证据来自内部部署而非公开度量。读时应把 §8 当"成本模型演示"，把 §9 当"存在性证明"。
2. **一切优点都带着 Chubby 的账单**：租约模型意味着网络分区/Chubby 抖动期间**可用性直接牺牲**（只读降级），论文诚实承认此点，但"锁服务在关键路径"后来被证明是 Bigtable 扩展（跨数据中心）的天花板——Spanner 用 TrueTime+2PC 补课，恰好证明这里缺了一块。
3. **compaction 的尾部延迟被低估**：major compact 的全量重写与读请求抢带宽/磁盘，论文用"轮转选择器 + 并发上限"缓解而非解决；"LSM 的写优势以不可预测的 compaction 暂停为代价"是后续十年研究（RocksDB/Design-compiled KV 等）反复处理的主题。
4. **单行原子的"够用论"有幸存者偏差**：作者服务的是内部可改代码的负载；对外部开发者，缺多行事务直接把复杂度推给应用（"事务日志表""状态机行"等土法），这也是 NewSQL 兴起的反作用力。
5. **行键设计是隐形 schema**：宣称 schema-free 却要求"按查询模式设计 row key 与列族"，错误的键设计导致热点/全表扫——自由度的代价从运行时转到了设计时，DDIA 称之为"隐式模式"。

**延伸：**

- **谱系**：LSM 概念源头 O'Neil 1996（Log-Structured Merge-Tree）→ Bigtable 工程化 → HBase/Cassandra/RocksDB/LevelDB/S3 on RocksDB（Spanner 存储层 tablet 化 LSM）——"tablet + SSTable 家族"的每个构件都能在今天的云数据库里找到直系后代。
- **数据模型之争**：Bigtable 的"有序稀疏映射"与 Codd 的关系代数分别是"可导航"与"可声明"两个极端的化身；Dataset/查询优化器后来的发展（如 Snowflake、Dremel 走向声明式）表明真正的答案是**存储层保留可导航性、查询层重建声明式**——1970 与 2006 两篇论文在同一仓库里形成完整对话（精读对读建议见 §十）。
- 与本仓库 [`../rdd_2012_nsdi/00-精读笔记.md`](../rdd_2012_nsdi/00-精读笔记.md) 对读：同代 Google/伯克利两条路线——Bigtable 说"数据住在我管的存储里，计算靠近它"；RDD 说"数据住内存/可重算，调度器别碰它"。两者分别是"以存储换计算"与"以计算换存储"。

## 七、一页总结（复习卡）

- **问题**：PB 级、数千廉价机、低延迟随机读写、schema 常变、只要行级一致性的存储基座，RDBMS 与 GFS 都不覆盖。
- **方案**：稀疏有序多维映射（行/列族/时间戳）；区间 tablet + 三级定位（Chubby→METADATA→.META.）；LSM 三层（commit log+memtable→SSTable 家族→minor/major compact+split）；单行原子 + 客户端租约/整 tablet 变更/bulk load 三个粗粒度配方；GFS 管持久、Chubby 管协调，自身只做"有序映射分片服务"。
- **所得**：水平扩展到十万 tablet 量级、schema 动态演化、扫描一等公民、恢复时间正比 log 尾部、控制面极简。
- **所欠**：无多行事务、Chubby 故障=降级只读、compaction 尾延迟、row key 设计负担隐形化、实验无横评。
- **地位**：NoSQL/云存储的原型机（HBase/Cassandra/Spanner/Dynamo 的参照系）；与 GFS、MapReduce 合称 Google 三件套；LSM 工程化的第一次大规模验证。

## 九、思考题（5 道）

1. 论文把 METADATA 表的前两个 tablet 特判为"自举定位"，第三个 tablet 留给以 `~` 开头的表名。请证明：为什么不能把 .META. 的定位信息直接全存进 Chubby？（提示：Chubby 文件的尺寸上限与写吞吐、"定位缓存可重建 vs 锁不可重建"的职责差异。）
2. major compaction 的触发器在"小文件太多"与"死空间比例"两个条件间轮转选择 tablet。设计一个只写不读、但删除极频繁的负载（如每 5 分钟全量覆盖索引），分析它会把哪条触发路径推向最坏情形，读放大还是空间放大先爆？
3. 租约给客户端做整 tablet mutation 时，若 tablet server 在客户提交前崩溃：新任 tablet server 从 GFS 读到的表状态是什么？为什么这个设计不需要 undo 日志也不需要两阶段提交？（提示：commit log 重放边界 + 行租约只能由当前 tablet 持有者发出。）
4. 若用 Codd 的 12 条规则逐条审判 Bigtable（见 Codd 笔记 §2），它在哪几条上完全失败、哪几条上"以退为进"（如规则 0"程序可互操作"反而因字节透明而更强）？给出你的评分表并说明哪种评价范式更适合 serving 层。
5. Snowflake 笔记思考题 1 讨论过"不可变文件使缓存零一致性"。Bigtable 的 SSTable 同样不可变，但 tablet 有唯一写者租约。请比较：两种"不可变"各自免掉了什么协议、又必须引入什么协议？（提示：清单指针推进的原子性 vs tablet 单写者的选举原子性——一个靠 rename，一个靠租约。）

## 十、阅读方法与常见误读提醒

1. **别把 Bigtable 读成"数据库"**：它没有查询语言、没有优化器、没有跨行一致性，是一台"有序映射的分片 serving 机器"。把它当存储引擎读，把"数据库"的期待放到上层（Borg/Omnipower/F1/Spanner 谱系）。
2. **"LSM 三层"是本笔记的提炼，不是论文用语**：论文只给了 memtable/commit log/SSTable/compaction 各节；"三层栈 + 三放大"是后人（RocksDB 时代）的总结框架，写论文引用时用 §2.4 的机制描述，不要用"论文提出 LSM 三层"这种表述。
3. **tablet ≠ 分区表 partition**：tablet 是连续行区间、自动分裂、可无迁移地再平衡（搬的是租约不是数据——文件全在 GFS）；把它理解成 MySQL 分区或 Kafka 分片都会引出错误问题（"扩容要搬多少数据"——答案是 0）。
4. **注意依赖的不可替换性**：GFS/Chubby 在 2006 年没有开源等价物，照抄论文搭 HBase+ZooKeeper 只是同构移植；真正学到的是"正确性外包、自身最小化"的分层方法论，选型时注意你的"Chubby"（etcd/ZooKeeper/Consul）进入关键路径的深度。
5. **建议配套阅读**：本仓库 Codd 笔记（先读，建立"被反叛的对象"直觉）→ 本笔记 §2 → MIT6.824 L04 讲义（[../../courses/并行与分布式系统/MIT6.824/notes/L04-Bigtable.md](../../courses/并行与分布式系统/MIT6.824/notes/L04-Bigtable.md)）→ DDIA 第 3 章；最后读 [../doi_10.1145_2882903.2903741/00-精读笔记.md](../doi_10.1145_2882903.2903741/00-精读笔记.md) 看同一底座上的另一种架构决断。
