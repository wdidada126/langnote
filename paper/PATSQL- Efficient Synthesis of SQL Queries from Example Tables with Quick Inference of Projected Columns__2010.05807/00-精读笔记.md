## 一句话总结
PATSQL 用关系代数里的「投影算子可上提」性质，把示例表编程（programming-by-example）合成 SQL 中最容易组合爆炸的「投影列推断」快速搞定，并在 226 条基准/Kaggle 教程查询上解决 68%、89% 在一秒内解出。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：Programming-by-example（按例编程）让不懂 SQL 的人给「输入表 + 期望输出表」，系统自动反推出正确的 SQL。门槛低、很实用。
- **为什么难**：SQL 功能多（聚合、嵌套），示例表一大，候选空间就组合爆炸，尤其是「该 SELECT 哪些列（投影）」这一步。
- **几类主流解法**：

| 路线 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 枚举/搜索 | 早期 PBE | 遍历候选程序 | 准但随规模爆炸 |
| 约束求解 | 约束式合成 | 用约束缩小空间 | 强但实现复杂 |
| 代数优化 | 本文 PATSQL | 投影上提 + 约束下推 | 高效处理投影列 |

- **本文属哪类**：基于关系代数性质、面向示例表的 SQL 合成路线。
- **2-3 个必懂关键名词（直觉解释）**：
  - **programming-by-example（按例编程）**：给输入和期望输出，系统自动生成满足的程序（这里是 SQL）。
  - **projection（投影）**：SQL 里 `SELECT` 决定「输出哪些列」——最容易组合爆炸的部分。
  - **relational algebra（关系代数）**：SQL 背后的数学操作集合（选择、投影、连接等），有可证明的等价变换。

## 1. 问题背景与动机
- **前人工作简述**：已有 PBE 方法支持聚合、嵌套等丰富 SQL 特性，但示例表规模一大，计算成本显著上升。
- **前人缺陷/未解决问题（逐条）**：
  1. **投影列组合爆炸**：推断 `SELECT` 哪些列是合成的关键，却在前人工作中造成组合爆炸。
  2. **缺乏代数层面的高效处理**：没有充分利用关系代数的等价变换来缩小搜索。
  3. **规模化受限**：大示例表下难以在可接受时间内合成。

## 2. 核心方法
- **最直观类比**：拼乐高时，普通方法把「选哪几块积木」放到最后乱试；PATSQL 发现「先把选列这一步从最里层提到最外层」等价于原结构，于是可以提前、快速定下要哪些列，避免反复试错。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：输入表 + 期望输出表（示例）。
  2. **关键操作**：
     - 利用关系代数性质，把程序草图（program sketch）中的**投影算子上提**到其它算子之上，保持语义不变；
     - 从而**快速推断**投影列（前人的组合爆炸点）；
     - 引入一种新约束形式及其**自顶向下传播机制**，高效完成草图补全。
  3. **输出**：满足示例输入输出对的 SQL 查询。
- **形式化要点**：核心是「投影上提 + 约束传播」的代数优化；超参为草图结构与约束（具体🔧查原论文）。
- **理论性质/保证**：基于关系代数的等价变换，保证语义不变；以效率实验验证。
