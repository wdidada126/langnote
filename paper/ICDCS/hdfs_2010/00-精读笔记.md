## 二、问题史：GFS 论文之外还差什么

- GFS 是内部系统无源码；开源界需要可移植、跨硬件、社区可演进的同语义 FS（⚠️ 动机归纳）。
- Hadoop 负载画像：数百万级大文件、追加写为主、随机改几乎为零；吞吐优先、延迟其次（✅）。
- 与通用 DFS 的差异点全部围绕"GB 级块 + 流式读取"展开（✅）。

## 三、架构

### 3.1 NameNode / DataNode / Client

- NameNode：全量元数据（文件树+块位置）驻内存；持久化=**fsimage + editlog**（✅ 与 GFS 单日志不同，双件制）。
- DataNode：以**块**为单位汇报，启动时全量 block report，周期增量（✅）。
- Client 库负责块选择策略（近机架/近本机），元数据走 NN、数据流直连 DN（✅）。

### 3.2 块与副本

- 默认块 128 MB、3 副本（✅ 版本口径 ⚠️）；放置策略=本机架×2+异机架×1，写流水线 pipeline 传播（✅）。
- **机架感知**是相对 GFS 的显性增量：拓扑代价模型写进 API（✅）。

### 3.3 一致性与写入

- 强一致性元数据 + "文件关闭后才可见"语义；追加写原子于单块（✅）。
- Lease（租约）管写入者，Hard lease 处理慢 DN（✅ 术语原文有）。
- 快照（可挂载命名空间快照）、联邦（Federation 多 NN 共享 DN 池）为后续版本论文点到/演进项（⚠️）。

### 3.4 容错与再平衡

- DN 心跳超时→块复制补齐；Balancer 按磁盘利用率重分布（✅）。
- NN 高可用：论文时代靠 NFS/standby 手工，QJM（Quorum Journal Manager）多 NN 是 2012+ 演进（⚠️）。

## 四、与 GFS 的对照速查（✅/⚠️ 混合）

| 维度 | GFS | HDFS |
|---|---|---|
| 元数据 | 单 master + 日志 | NN 双件制（image+edit）✅ |
| 一致性 | 宽松 | 关闭后可见、追加块内原子 ✅ |
| 拓扑 | 隐式 | 机架感知一等公民 ✅ |
| 实现 | C++ 内部 | Java 开源社区 ✅ |
| 块大小 | 64MB | 128MB ✅ |

## 五、批判读法

- "small files problem"论文自认：元数据全内存→十亿级小文件即 NN OOM 之源，Archive/Har/S3 直读全是在还债（⚠️）。
- 单写者追加语义对湖仓 Upsert 负载不适配——Delta/Iceberg 在其上重新发明事务日志（[[lakehouse_2021]]/库内 Delta 档）（⚠️）。
- 吞吐叙事回避延迟：NameNode RPC 在交互查询时代成为瓶颈，Alluxio/缓存层皆因它而生（⚠️）。
- Java 化与 POSIX 缺口（O(1) rename 缺失）长期被批，直到最近版本才补目录原子 rename（⚠️ 演进）。

## 六、🔧 本地微实验（非本书引擎行为）

1. **块流水线**：3 进程串成 pipeline 收块副本，kill 中段观察尾段重排。
2. **机架放置**：模拟 2 机架×4 节点，按"本机架2+异机架1"策略写 100 块，统计跨机架流量。
3. **image+edit 恢复**：fsimage JSON + editlog JSONL 重放重建文件树，对比全量日志重放成本。
4. **block report 风暴**：NN 启动时 10^4 DN 同时汇报，测"渐进汇报"与否的排队差异。
5. **小文件元数据税**：10^6 个 1KB 文件 vs 1 个 1GB 大文件，按每文件 150B 元数据估算 NN 内存。

## 九、最新演进与工业实践

- Hadoop 3.x：EC 纠删码副本替代 3x、默认块 128→256MB 讨论、多 NN Raft（⚠️）。
- 云时代存算分离：S3/OSS 取代 HDFS 成为湖仓底座，"HDFS 兼容层"（JindoFS/Alluxio）承接（⚠️）。
- 2024–2026：新建数仓/湖项目默认对象存储；HDFS 存量在私有云与电信域长期服役——论文作为"批处理时代存储范式"定格（⚠️ 判断）。
