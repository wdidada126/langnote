## 一句话总结
复杂 SQL 很难直接拆成可重组合的子查询。本文提出模块化「查询计划语言 QPL」，把 SQL 系统拆成简单规则的子查询；并用 SQL Server 优化计划反向翻译出 QPL、给 Spider 加注 QPL。结果：QPL 这种模块化表示对既有语义解析架构更友好，训练 text-to-QPL 比直接 text-to-SQL 更有效，且 QPL 能改写成简单问题、对非专家更可解释。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：Text-to-SQL 在「跨库 + 复杂查询」上泛化差；复杂 SQL 难以正确生成。
- **为什么难**：(1) 现有数据集缺「问题分解」标注；(2) SQL 语法复杂，多数复杂查询拆不出能简单重组合的子查询。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 端到端 seq2seq | 早期模型 | 直接生成 SQL | 复杂查询易崩 |
| 问题分解 | 本文 QPL | 先拆子问题/子查询 | 可解释、易组合 |
| 中间表示 | IRNet、中置表示 | 先生成中间语言 | 桥接自然语言与 SQL |

- **本文属哪类**：「问题/SQL 语义分解 + 中间表示（QPL）」路线。
- **关键名词直觉**：
  - **QPL（Query Plan Language）**：作者提出的、把 SQL 拆成简单规则子查询的模块化语言。
  - **query optimization plan**：数据库优化器生成的执行计划；本文借它把 SQL 翻成 QPL。
  - **semantic parsing（语义解析）**：把自然语言映射到形式化查询（如 SQL）的任务。

## 1. 问题背景与动机
- 前人工作简述：问题分解（question decomposition）被用于提升复杂 SQL 解析，但面临两大障碍。
- 前人缺陷/未解决问题（逐条）：
  1. **数据集缺分解标注**：现有数据集没有「问题→子问题」的分解标签。
  2. **SQL 难拆解**：因语法复杂，多数复杂查询无法拆成可轻易重组合的子查询。

## 2. 核心方法
- **最直观类比**：把「一道超长应用题」改写成「一串小学生也会的小步骤」（QPL 子查询），每步都能单独算、最后拼回答案。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：SQL 查询（及自然语言问题）。
  2. **关键操作**：
     - 提出 **QPL**，系统化把 SQL 拆成简单规则的子查询；
     - 利用 SQL Server 查询优化计划，开发 **SQL→QPL 翻译器**；
     - 用翻译器给 **Spider** 数据集增补 QPL 程序标注。
  3. **输出**：(a) QPL 数据集；(b) text-to-QPL 解析器；以及两个扩展优势。
- **形式化要点**：核心是把「语义解析目标」从 SQL 换成更易学的 QPL；QPL 还能改写成简单问题，形成 (复杂问题, 分解问题) 数据集，训练出「对 schema 敏感的 Question Decomposer」；且 QPL 对非专家更可解释。超参数/语法细节 🔧 查原论文。
- **理论性质/保证**：无形式化保证；以实证（更易学、更可解释）为主。

## 4. 实验结论（概览）
- 对比基线：直接 text-to-SQL 的语义解析架构。
- 数据集：Spider（增补 QPL 标注）。
- 指标：解析准确率等（具体 🔧 查原论文）。
- 结论方向（摘要给出的已核实结论）：
  - QPL 的模块化特性有益于既有语义解析架构；
  - 对语义等价的查询，训练 **text-to-QPL** 比 **text-to-SQL** 更有效；
  - QPL 可被改写成简单问题（得到分解数据集），且更可解释。
