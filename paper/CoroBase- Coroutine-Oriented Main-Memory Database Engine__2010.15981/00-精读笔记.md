## 一句话总结
主存数据库的查询很慢的一个原因是 CPU 在等内存（指针 chasing 导致的缓存缺失）。CoroBase 用轻量级协程把「等待」变成「干活」：事务被建模成协程，一批事务互相让出 CPU，一个在等内存时另一个继续跑——数据预取的收益被无缝叠加到整个引擎上，读密集负载接近 2 倍提升。

## 0. 给新手的阅读前置（背景知识地图）

- **子方向解决什么大问题**：数据全放内存后，磁盘 I/O 不再是瓶颈，**CPU 访问内存的延迟**成了新瓶颈。B+ 树等「指针丰富的结构」走一条树路径要多次随机访存，每次都可能 cache miss——这段时间 CPU 闲着，叫**数据停顿（data stall）**。
- **为什么难**：想用**软件预取**（提前发出 prefetch 指令把数据搬进缓存）隐藏停顿，问题是预取后你迟早要「等数据到了再继续」——等待期间让 CPU 干什么？单线程没法干别的；改接口做批处理又会破坏应用兼容性。
- **主流解法几类**（表格）：

| 类别 | 直觉 | 代表工作 |
|------|------|----------|
| 缓存友好数据结构 | 减少指针追逐本身（B-tree 节点变胖、列存） | HyPer、LeanStore 等 |
| 软件/硬件预取 | 提前把未来要用的数据拉进缓存 | 单算子级 prefetch 研究 |
| 批处理/向量化 | 一次处理一批 tuple 提高局部性 | MonetDB/X100、HyPer 编译执行 |
| **协程化执行** | 等待时切换到别的协程干活 | **本文 CoroBase** |
| 多线程 | 用更多核掩盖单线程停顿 | 各类并行引擎 |

- **本文属于**：协程化执行——把「协程 + 预取」系统性地推广到整个数据库引擎。
- **关键名词直觉**：
  - **协程（coroutine）**：比线程更轻的执行单元，可以主动「让出（yield）」并在稍后「恢复（resume）」，切换开销极小（用户态完成）。
  - **软件预取**：CPU 指令 `prefetch`，告诉硬件「这个地址的数据我马上要用，先帮我搬到缓存」。
  - **事务内批处理 vs 事务间批处理**：前者在同一事务内攒一批操作再统一发预取（需要改 API）；后者把**不同事务**当成不同协程互相切换（应用完全无感知）——本文核心。

## 1. 问题背景与动机

- **前人工作简述**：主存 DBMS 研究（HyPer 等）解决了存储层瓶颈，但缓存缺失/TLB 缺失成为主要开销；此前已有研究在单个算子（如索引扫描）内用协程 + 预取隐藏停顿，也有系统用事务内批处理来攒预取。
- **前人缺陷/未解决问题**（逐条，摘要明确）：
  1. 只针对**单个组件和操作**（比如只加速了 B+ 树查找），不是完整引擎方案；
  2. 采用**事务内批处理**：必须修改应用程序接口（把事务改写成批量提交），**破坏向后兼容性**；
  3. 因此不清楚协程预取能否应用于**完整数据库引擎**、以及在**各种负载下端到端收益**究竟多大——CoroBase 正面回答这两个问题。

## 2. 核心方法

- **最直观类比**：以前的预取像「你在餐厅点单后必须干站着等菜」（事务内批处理还得改点菜规矩）；CoroBase 的做法是服务员拿到一个订单后，趁等厨房出菜的空档马上去处理下一桌订单——每个订单（事务）都作为一个协程，等待时自动让别人上，互不耽误，顾客（应用）完全感觉不到流程变了。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：并发到达的事务流（OLTP 为主）。
  2. **关键操作**：
     - **coroutine-to-transaction 范式**：把每个事务实现为一个协程；
     - 在引擎内部的可能发生 cache miss 的点（如 B+ 树下一层节点访问）前发出软件预取，然后 **yield 让出 CPU**；
     - 运行时调度器切换到其他就绪事务协程执行；数据到达后恢复原协程；
     - 由此实现**事务间批处理（inter-transaction batching）**：预取收益保留，但应用程序接口不变。
  3. **输出**：一个完整的协程化主存 DBMS 引擎（含并发控制），端到端跑 OLTP 负载。
- **形式化要点**：引擎执行模型被改写为协作式调度状态机；事务为协程，访问路径上「可能 miss 的节点」为 yield 点；🔧 具体 yield 点选取策略与恢复机制（含 C++20 协程等实现细节）查原文。
- **理论性质/保证**：无概率性理论保证，属系统实证；关键性质是**透明性**（不改应用）与**普适性**（对无法从预取获益的负载也保持竞争力）。

## 4. 实验结论（概览）

- **平台**：48 核服务器。
- **对比基线**：非协程化的基线引擎（CoroBase 自身的同步版本）及先前预取方案 🔧 具体基线列表查原文。
- **负载**：多种 OLTP 负载（读密集/写密集/混合 🔧）。
- **指标**：吞吐量（tpmC 类/每秒事务数）等端到端指标。
- **结论方向**：读密集型负载性能**接近 2 倍提升**；对本质上无法从软件预取获益的负载（写密集等），仍保持有竞争力的性能（不劣化）。

## 7. 2026 视角（🔧）

- C++20 标准协程落地后，「协程化执行」已从研究走向工程：UMBRA/LeanStore 系工作、若干商业引擎在执行器中采用协程式算子调度与预取（🔧 具体产品化程度以公开资料为准）。
- 趋势：(1) 协程与向量化执行融合；(2) PMEM/SSD 扩展内存层次下预取更重要；(3) 异步 I/O（io_uring）与协程天然契合，扩展到非纯主存场景。CoroBase 是该路线在「完整引擎 + 端到端评测」上的标志性验证。
