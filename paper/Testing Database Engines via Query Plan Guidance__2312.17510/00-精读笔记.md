## 一句话总结
给数据库找「逻辑错误」（查出来的结果不对）已经有测试预言（test oracle），难的是**生成什么样的测试用例**。本文的直觉是：SQL 是声明式的，同一条查询可能被执行成很多种不同的**物理查询计划**；如果能让测试去探索更多样的查询计划，就能覆盖到更多（可能出错的）行为。于是他们用「变异数据库状态」的办法诱导 DBMS 生成多样的计划，在 SQLite、TiDB、CockroachDB 上找出 53 个未知 bug，探索到的独特查询计划数是朴素随机生成的 4.85~408.48 倍、是覆盖率引导的 7.46 倍。

## 0. 给新手的阅读前置（背景知识地图）
- **这个子方向解决什么大问题**：自动发现数据库引擎的缺陷，尤其是**逻辑错误（logic bug）**——不崩溃、不报错，但结果算错了，这是最难发现的一类。
- **为什么难**：
  - 逻辑错误没有崩溃迹象，需要「测试预言（test oracle）」来判断对错；
  - 测试用例 = 数据库状态 + 查询，组合空间近乎无限；
  - 覆盖率类指标（行覆盖）与「是否触发有趣行为」相关性有限。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 随机生成 + 差分测试 | 早期 fuzzing | 随机造查询，与参考实现/等价变换比对 | 简单，命中率低 |
| 覆盖率引导 | SQUIRREL 等 | 用代码覆盖率反馈指导生成 | 需要插桩（多为白盒） |
| 语法/语法规则覆盖 | Parser Knows Best | 按语法规则遍历 | 语法层面充分，语义层面弱 |
| **查询计划引导** | **QPG（本文）** | 以「物理查询计划的多样性」为反馈 | 黑盒可用（多数 DBMS 暴露计划），贴合语义 |

- **本文属于哪一类**：最后一类。
- **必懂关键名词（直觉版）**：
  - **测试预言（test oracle）**：判断一次执行「对不对」的机制（如等价表达式变换、差分测试）。
  - **逻辑算子 → 物理算子**：SQL 只说「要 join」，DBMS 要决定用 hash join 还是 merge join；**查询计划**就是物理算子构成的树。
  - **变异（mutation）**：这里不是改查询，而是改**数据库状态**（数据分布、统计信息等），从而迫使优化器选别的计划。

## 1. 问题背景与动机
- 前人工作简述：已有多种 test oracle 可以发现逻辑错误；要实现全自动化测试，需要把 oracle 配上「测试用例生成技术」（测试用例 = 数据库状态 + 一条查询）。
- 前人缺陷 / 未解决问题（逐条）：
  1. **生成策略缺少语义导向**：朴素随机生成不知道什么样的用例「有意思」；
  2. **覆盖率引导不等于行为多样**：代码覆盖引导的探索与「触发不同执行行为」并不等价；
  3. **白盒依赖**：覆盖率引导往往需要插桩，商用/闭源系统不好用；
  4. **同一条 SQL 的多种执行路径被忽视**：SQL 是声明式的，一个逻辑算子可对应多个物理算子，而现有方法没有把「计划多样性」当作探索目标。

## 2. 核心方法
- **最直观类比**：同一道菜（SQL），厨房（优化器）可能有十种做法（物理计划）。以前的测试是随机点菜；QPG 是不断调整「食材状态」，逼厨房换做法，于是把各种做法都试一遍——做法试得越多，越可能撞上某道工序的失误。
- **具体做法（输入 → 关键操作 → 输出）**：
  - 输入：目标 DBMS + 初始数据库状态 + 查询集。
  - 关键操作：
    1. **提出 Query Plan Guidance（QPG）概念**：把「探索到更多样的查询计划」作为测试引导目标；
    2. **状态变异**：逐步对数据库状态施加「有希望的（promising）」变异，使 DBMS 为后续查询生成不同的查询计划；
    3. **配合 test oracle**：得到的用例交给 oracle 判断结果是否正确。
  - 输出：更有可能触发逻辑错误的测试用例（以及被发现的 bug 列表）。
- **形式化要点**：核心是「什么算有希望的变异」这一反馈机制；具体的变异算子与选择策略 🔧 查原论文。
- **理论性质 / 保证**：**无**理论保证（论文以实证为主 🔧）；工程性质是**黑盒、通用**——因为多数 DBMS（包括商业系统）都会向用户暴露查询计划。

## 4. 实验结论（概览）
- 对比基线：朴素随机生成方法、代码覆盖率引导方法。
- 被测系统：**SQLite、TiDB、CockroachDB**（三个成熟、广泛使用、已被大量测试的系统）。
- 评价指标：发现的唯一（unique）未知 bug 数；探索到的独特查询计划数。
- 结论方向（摘要给出的已核实数字）：
  - 发现 **53 个**此前未知的唯一 bug；
  - 探索到的独特查询计划数是朴素随机生成的 **4.85~408.48 倍**；
  - 是代码覆盖率引导方法的 **7.46 倍**。

## 8. 新手学习路线
- **10 分钟**：读摘要 + 本笔记 §0、§2，理解「SQL 声明式 → 计划多样 → 用计划当反馈」这条链。
- **30 分钟**：对一条简单 SQL 手动改数据分布，用 EXPLAIN 观察计划变化，体会「状态变异 → 计划变化」。
- **进阶**：在 SQLancer 上跑通 QPG；读论文中「有希望的变异」如何被挑选；思考能否把计划多样性用于评估自己的回归测试集质量。
