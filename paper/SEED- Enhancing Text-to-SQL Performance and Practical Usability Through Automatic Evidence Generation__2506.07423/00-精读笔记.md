## 一句话总结
现实里用户不会写「证据（evidence）」，但主流 Text-to-SQL 研究靠 BIRD 数据集默认证据已给；SEED 自动从数据库 schema、描述文件、取值里抽取证据，让模型在「无证据」真实场景下也能生成准确 SQL，甚至有时比用 BIRD 人工证据还强。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：让不懂 SQL 的人用自然语言问数据库、自动得到可执行 SQL。难点在「数据库结构复杂、自然语言含糊、领域知识缺失」。
- **为什么难**：真实环境没有「专家给好的证据/背景说明」；而且人工写的证据本身可能有错漏，反而误导模型。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 微调专用模型 | RESDSQL、RAT-SQL | 在 schema 上训练encoder | 准但需训练、迁移弱 |
| 大模型的上下文学习 | DIN-SQL、ACT-SQL | 用 prompt + 示例/CoT | 灵活但吃证据质量 |
| 证据/描述增强 | SEED（本文） | 自动补 evidence | 贴近真实部署 |
| 数据库描述生成 | Automatic DB description | 生成表/列说明 | 与 SEED 互补 |

- **本文属哪类**：证据增强路线，定位在「上线前没人手写好 evidence」的真实痛点。
- **关键名词直觉**：
  - **evidence（证据）**：用户问题之外的、帮助模型理解数据库的背景信息（如「某些列是外键」「某列取值含义」）。
  - **BIRD 数据集**：当前主流 Text-to-SQL 评测集，特点就是「带 evidence」；但也因此偏离真实「用户不会给证据」的设定。
  - **no-evidence scenario**：不给任何人工证据、纯靠模型 + 自动生成证据的场景，最接近生产。

## 1. 问题背景与动机
- 前人工作简述：SOTA Text-to-SQL 大量依赖 BIRD，而 BIRD 假设问题自带 evidence，隐含「用户懂数据库、能提供领域知识」——这与 Text-to-SQL「让非专家查数据」的初衷矛盾。
- 前人缺陷/未解决问题（逐条）：
  1. **假设与现实错位**：研究设定要求用户提供 evidence，真实用户给不出，导致「论文好看、上线拉胯」。
  2. **人工 evidence 有缺陷**：BIRD 里人工写的证据存在缺失或错误，直接拉低模型表现。
  3. **缺乏自动证据生成**：此前少有系统从数据库自身（schema、描述文件、cell 值）自动产出可靠 evidence。

## 2. 核心方法
- **最直观类比**：把「专家手写的使用说明」换成「系统自己读说明书 + 翻数据」——SEED 像一位会自己读数据库文档、抽样看数据、再给用户写「给模型的提示条」的助手。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：数据库 schema（表/列/类型）、描述文件、实际数据取值。
  2. **关键操作**：系统「Systematically analyzes」schema、描述、取值，抽取相关信息（例如关联列、取值分布、业务含义）形成 evidence 文本。
  3. **输出**：一段自动生成的 evidence，喂给下游 Text-to-SQL 模型提升生成准确率与鲁棒性。
- **形式化要点**：核心是把「证据生成」从人工步骤变成可复用管道；论文给出 SEED 这一命名（System for Evidence Extraction and Domain knowledge generation）。超参数/具体抽取规则以原论文为准 🔧。
- **理论性质/保证**：无形式化保证；贡献在工程化证据抽取 + 实证提升。
