## 一句话总结
现有 Spider 评测用「与标准答案 SQL 字符串匹配」来衡量，会把「结果等价但写法不同」的 SQL 误判为错。本文提出 test suite accuracy：从大量随机数据库里蒸馏出一小撮高覆盖度测试库，在测试套件上比「答数（denotation）」来高效逼近语义准确率，并证明 Spider 原指标平均有 2.5%、最坏 8.1% 的假阴性率。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：怎么「正确评价」Text-to-SQL 模型——不仅看 SQL 写没写对，更看查出来的结果对不对。
- 为什么难：同一问题可有多种等价 SQL 写法；按字符串匹配会把正确的判错（假阴性），低估模型。
- 几类主流解法：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 字符串匹配 | 早期 Spider 指标 | 比 SQL 文本/执行结果串 | 简单但有假阴性 |
| 执行结果匹配 | 本文 test suite | 在测试库上比结果 | 贴近语义、更公平 |
| 人工校验 | 手工抽样 | 人看对错 | 准但不可规模化 |

- 本文属哪类：评测指标（evaluation methodology）路线，是 Text-to-SQL 的「裁判标准」改进。
- 关键名词直觉：
  - denotation（指称/答数）：SQL 执行后得到的结果集；语义等价看 denotation 是否一致。
  - test suite（测试套件）：一组数据库实例，用来检验 SQL 行为；本文从随机库蒸馏得到。
  - false negative（假阴性）：模型其实对、却被评测判错。

## 1. 问题背景与动机
- 前人工作简述：Spider 等采用「标准答案 SQL 匹配」的评测，常按执行结果字符串是否一致来判分。
- 前人缺陷/未解决问题（逐条）：
  1. 等价 SQL 被误判：写法不同但结果相同的 SQL 被判错，低估模型真实能力。
  2. 缺高效语义近似：直接计算语义准确率代价高，需要可行近似。
  3. 指标失真未知：原指标的假阴性率到底多大，此前无人系统量化。

## 2. 核心方法
- 最直观类比：与其要求「答案卷面和标准答案逐字相同」，不如「出几道不同数据的小测验，看学生算出的结果对不对」——只要几套题覆盖够广，就能公平判断真懂没懂。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：标准答案 SQL（gold query）+ 大量随机生成的数据库。
  2. 关键操作：从大量随机库里蒸馏出一小撮对 gold query 达到高代码覆盖度的测试库；评测时计算预测 SQL 在测试套件上的 denotation 准确率。
  3. 输出：对语义准确率的紧上界（tight upper-bound）高效估计——即 test suite accuracy。
- 形式化要点：核心是用「代码覆盖度」指导蒸馏，保证测试套件小且代表性强；给出语义准确率的紧上界。超参数（覆盖度阈值等） 🔧 查原论文。
- 理论性质/保证：提供语义准确率的紧上界估计（近似而非精确保证）；并对 Spider leaderboard 21 个模型做实证验证，100 例人工核对均正确。

## 4. 实验结论（概览）
- 对比基线：Spider 原评测指标。
- 数据集：Spider leaderboard 上 21 个提交模型；11 个数据集提供蒸馏测试套件。
- 指标：false negative rate（假阴性率）、语义准确率近似（test suite accuracy）。
- 结论方向（摘要给出的已核实数字）：
  - 原 Spider 指标平均假阴性率 2.5%，最坏 8.1%，说明需要 test suite accuracy；
  - 在 100 个样例上人工验证本文方法始终正确；
  - 实现与 11 个数据集的测试套件已公开。
  - 🔧 各模型在 test suite 下的具体准确率数字查原论文 Table 后补。
