## 一句话总结
在加密的 MySQL 数据库上直接跑 SUM/GROUP BY 这类聚合统计：Hermes 把预先算好的聚合统计量「打包」进密文里，全局聚合常数时间完成（不用昂贵的 Galois 自同构），再配一套基于槽位掩码/移位的原地更新算法，首次同时做到「聚合快」和「记录可增删改」，且在 IND-CPA 模型下可证安全。

## 0. 给新手的阅读前置（背景知识地图）

- **大问题**：把数据外包给不可信服务器（云数据库）后，希望服务器能**直接在密文上计算**并返回结果，而自己看不到任何明文——即「可计算的加密」。
- **为什么难**：全同态加密（FHE）允许对密文做加/乘，但密文**天然不可变**（改一条记录≈重加密重写，代价巨大）；数据库记录却是高频增删改的——这两者结构性错配。另外 FHE 的 SIMD 打包（一个密文装一排槽位）与「改中间某一条」也是矛盾的。
- **主流解法**：

| 路线 | 直觉 | 弱点 |
|------|------|------|
| TEE/SGX 硬件飞地 | 明文在可信硬件里算 | 信任硬件厂商，侧信道风险 |
| 保序/可搜索加密 | 只支持有限操作集 | 泄漏模式，功能性受限 |
| FHE 数据库 | 密文上算任意加/乘电路 | 更新极贵，只读分析场景 |

- **本文属于**：FHE 数据库路线，但专攻「**动态更新 + 全局聚合**」这对此前不可兼得的性质。
- **关键名词直觉**：
  - **BFV 方案 / SIMD 槽位（slots）**：一个 BFV 密文是多项式，可切成几十到几千个「槽」，每槽放一个数；密文相加=所有槽对应相加（免费获得向量化并行）。
  - **Galois 自同构**：FHE 里做「槽位旋转/置换」的操作，是打包方案中最贵的操作之一——Hermes 的卖点之一就是全局聚合**不需要它**。
  - **IND-CPA**：标准语义安全定义——敌手拿到密文也分不出加密的是哪一条消息；「可证安全」指更新算法在这个模型下有严格证明。

## 1. 问题背景与动机

- 前人工作：FHE 理论与库（如 OpenFHE/SEAL/HELib 🔧 通说）成熟度提升，已有若干「加密数据库」尝试（同仓库可见 StealthDB、ShieldDB 等）。
- 前人缺陷（依摘要逐条）：
  1. **高频更新难**：可变数据库记录与 FHE 密文「改一次≈重写整个密文」的结构性错配，使外包库无法支撑动态负载；
  2. **聚合贵**：常规 FHE 聚合需要昂贵的槽旋转（Galois automorphism），聚合查询时延高；
  3. **快与活不可兼得**：既有 FHE 数据库系统从未在大规模上同时交付「高性能聚合」与「原地更新」。

## 2. 核心方法

- **直观类比**：与其每次点名都要把全班（整列密文）重新报数，不如让每个「小组信封」里预先装好小组的总分——老师拆一个信封就知道小组总分，全班总分只需把几个信封相加，根本不用来回挪动里面的学生；而且往信封里加/减一个学生有专门的安全算法，不用重造信封。
- **具体做法（输入 → 关键操作 → 输出）**，核心设计两块（摘要明示）：
  1. **SIMD 感知的打包数据模型**：把**预计算的聚合统计量直接嵌进每个密文**；无条件全局聚合（如 SUM）只需把少量「组级密文」相加——**常数时间、零 Galois 自同构**；
  2. **基于多项式槽位掩码与移位的同态更新算法**：支持真正的**原地**元组插入/删除，且在标准 IND-CPA 模型下**可证安全**。
- **范围取舍（作者的自觉限定）**：只支持「无条件全局聚合」这一类查询，以此同时换取高性能与可更新——这是一个明确的「功能换性能」设计决定。
- **系统形态**：以 **C++ 编写的 MySQL 可加载函数（UDF 插件）**实现，SQL 用户不改查询习惯即可用 `SELECT / GROUP BY / CAST` 等标准操作；密码学基于 OpenFHE 的 BFV 方案（README 明示）。
- 🔧 具体多项式算法（掩码/移位构造）、安全证明与打包布局参数查原文后补。

## 4. 实验结论（概览）

- **对比基线**：常规 FHE 实现（逐条加密/独立密文基线，README 的 `eval_baseline.sh` 所指 🔧 具体基线配置查原文）。
- **数据集**：TPC-H 基准 + 三个真实数据集（摘要明示）。
- **指标**：查询吞吐、元组插入、元组删除。
- **结论方向**：Hermes 在三类指标上均显著优于常规 FHE 实现，验证其对「高动态 + 分析型」负载的有效性（摘要明示）。
- 🔧 精确数字（加速比、插入/删除吞吐）查原文实验节或仓库 `all_results.txt` 后补。

## 5. 开源代码与动手实践

- 仓库地址：https://github.com/hpdic/hermes （官方；README 自述 "Homomorphic Encryption as MySQL UDFs"，全称 Homomorphic Encryption for Relational MySQL Engine Support）
- 语言：C++（MySQL UDF 插件 + OpenFHE/BFV），附 Python 绘图脚本。
- 典型流程（教学示意，以 README/INSTALL.md 为准）：
  1. 按 `INSTALL.md` 编译安装 UDF 插件并打补丁（`patch/` 目录）；
  2. `./experiments/script/convert_csv.sh` 预处理数据 → `load_csv.sh` 载入 MySQL；
  3. 分别跑 `eval_encrypt.sh / eval_insert.sh / eval_remove.sh / eval_baseline.sh`；
  4. `eval_all_hermes.sh` 全量扫描，结果汇总到 `all_results.txt`。
- 可用的 SQL UDF（README 明示，体会设计的关键入口）：`HERMES_ENC/DEC_SINGULAR_BFV`（标量加解密）、`HERMES_SUM_BFV`（同态聚合）、`HERMES_PACK_CONVERT / HERMES_PACK_GROUP_SUM / HERMES_PACK_GLOBAL_SUM`（打包与组/全局求和）、`HERMES_PACK_ADD / HERMES_PACK_RMV`（槽位插入/删除 = 动态更新）、`HERMES_MUL_BFV`（密文乘）。
- 许可与资源提醒：Apache-2.0；FHE 计算本身计算/内存开销大，小机器上手建议用小数据集；生产使用需自行评估安全参数。

## 7. 2026 视角（🔧）

- 机密计算当前三足鼎立：TEE（Intel TDX/AMD SEV/Arm CCA）、MPC、FHE；FHE 在数据库领域仍以「受限查询集 + 研究原型」为主，Hermes 代表的最新潮流是**选准一个可证明又实用的查询子集**（无条件聚合）把系统做扎实，而非追求全 SQL。
- 工业界（如 Microsoft SEAL 生态、FHE 硬件加速初创）持续推动；与向量数据库的关系：FHE 上做相似检索仍非常昂贵，是公开难题（🔧 一般性判断）。
