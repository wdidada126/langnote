## 0. 给新手的阅读前置（背景知识地图）

**子方向解决什么大问题**：Text-to-SQL 要把「查询每个部门工资最高的员工」这样的自然语言变成 SQL。难点在于模型要泛化到训练时**没见过的数据库**（cross-domain）：新库的表名、列名、取值分布都不同，标注数据又贵又少。

**为什么难**：
- 给每个新数据库人工标注「问句-SQL」对成本极高；
- 现实中查询呈长尾分布，简单查询多、复杂查询（多表连接、嵌套子查询）少，模型见得少就做不好；
- 直接用模板机械生成问句，语言生硬、分布失真，反而污染训练集。

**主流解法分类**（本文属于第一类的自动化升级版）：

| 路线 | 代表思路 | 优缺点 |
|------|---------|--------|
| 人工/半自动数据增强 | 人工写模板或改写已有问句 | 质量高但费人 |
| 自动数据增强 | 从 SQL 端合成数据再回译成问句 | 可规模化，但问句质量是瓶颈 |
| 预训练+schema 联合建模 | 大模型直接学 schema 表征 | 不额外造数据，但域差距仍难跨 |

**关键名词直觉解释**：
- **AST（抽象语法树）文法**：把 SQL 看成一棵树，按文法规则在树上「长」出新查询——保证生成的 SQL 语法一定合法，且能按文法覆盖不同子结构（从而覆盖复杂查询）。
- **SQL 模式（SQL pattern）覆盖率**：把 SQL 的骨架抽象出来（去掉具体表名列名后的结构），论文要求生成的 SQL 至少覆盖训练数据中 80% 的模式，保证「分布对齐」。
- **层级式生成（hierarchical generation）**：不直接一步把 SQL 翻成问句，而是先抽关键字/骨架，再逐步展开成自然语言，类似「先列提纲再写作文」。

## 1. 问题背景与动机

- 前人工作：跨域 Text-to-SQL 的代表数据集与模型（WikiSQL、Spider 及其上的解析器）都受限于「训练库数量少」。已有数据增强工作两条路：① 需要人工介入保证生成数据质量（费人）；② 全自动但只能应付简单 SQL（复杂查询出错或干脆生成不了）。
- 前人缺陷逐条：
  1. **人工依赖**：生成数据要人审/人写，无法规模化；
  2. **复杂 SQL 缺位**：已有自动方法生成的多是单表简单查询，对多表连接、嵌套查询无能为力，而这恰是 Spider 这类难数据集的痛点；
  3. **分布失真**：生成的 SQL/问句分布与真实训练集不匹配，增强收益打折；
  4. **生成数据量一大，训练效率骤降**：缺乏对海量合成样本的筛选机制。

## 2. 核心方法

**最直观类比**：为了教学生（模型）做没见过的题型，老师（本文框架）先按大纲（AST 文法）自动出题（生成 SQL），再自己把每道题的题干用自然语言写出来（SQL→问句生成），最后只挑最有练习价值的题给学生刷（采样策略）。

**具体做法（输入 → 关键操作 → 输出）**：
1. **输入**：目标数据库（schema + 数据）；
2. **自动 SQL 生成**：基于 AST 文法在数据库上自动产生大量 SQL 查询，并施加约束——生成的 SQL 模式须覆盖训练数据中至少 **80%** 的模式（该数字来自摘要，经核实）；
3. **层级式 SQL-to-Question 生成**（主要贡献）：把 SQL 分层解码——先生成关键信息/骨架，再生成流畅的自然语言问句，比直接 seq2seq 翻译 SQL 的质量更高；
4. **采样策略**：对海量生成数据按简单规则采样，大幅提升训练效率。

**输出**：扩充后的「问句-SQL」训练对，用于增强任意下游 Text-to-SQL 解析器的训练。

**理论性质**：本文偏工程框架，无形式化理论保证；AST 文法生成天然保证 SQL 语法合法性这一点是「结构性保证」。

## 4. 实验结论（概览）

- **数据集**：WikiSQL、Spider（英文）+ DuSQL（中文），均为跨域基准。
- **对比**：各自数据集上的强基线解析器，加/不加本文数据增强做对照。
- **结论方向**：三个数据集上一致提升，消融实验显示层级生成组件是提升的关键来源。
