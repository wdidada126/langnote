## 一、背景与问题：对象存储为什么"存得下、管不住、查不快"

### 1.1 问题设定（§1，第 3411–3412 页）

云对象存储（S3/Azure Blob/GCS/Swift）是地球上最大最便宜的存储，天然适合放数据仓库/数据湖；但它们的实现只是**键值存储**：元数据操作（LIST）昂贵、跨键一致性缺失，导致 ACID 与高性能两难。作者自报经验证据：2014–2016 年 Databricks 云服务**约一半的支持工单升级**源于云存储策略导致的数据损坏、不一致或性能问题（第 3411 页，"Anecdotally"口径）。

### 1.2 对象存储 API 与性能画像（§2.1/§2.3，第 3413–3414 页）

- 接口：桶 + 键（字符串，习惯上模拟路径）；**没有廉价的 rename**；LIST 按字典序从 start key 返回，**S3 每次最多 1000 键、耗时几十到几百毫秒**——百万对象顺序列举需要分钟级。
- 读：支持字节范围请求（这是列式格式可行的前提）；**基础延迟 5–10 ms，单请求约 50–100 MB/s**，要读几百 KB 才到半速、几 MB 才近峰值；典型 VM 有 ≥10 Gbps 网络，需 8–10 个并行读才能打满。
- 写：整对象替换（可原子），部分系统支持 append。⇒ 点更新要求对象小、扫描要求对象大，二者冲突。
- 作者总结的表存储三原则（§2.3 "Implications"）：热数据紧邻存放（列式）；对象做大但别太大（更新要整写）；**避免 LIST**、尽量按字典序键区间请求。

### 1.3 一致性细节（§2.2，第 3413 页）

主流对象存储为**每键最终一致、跨键无保证**。S3 当时的模型被精确描述：新对象写后读一致，**例外**是写入方若先 GET 过不存在的键（负缓存）则之后一段时间可能读不到自己刚写的对象；**LIST 永远最终一致**。这是全文协议设计要绕开的雷区（注：S3 已于 2020-12 转为强一致，属论文写作时点事实，见"批判与延伸"）。

### 1.4 既有三种做法及其天花板（§2.4，第 3413–3414 页）

1. **文件目录**（Hive 式分区目录 + Parquet）：多对象更新无原子性、失败留 corrupted 状态；最终一致导致读者看到半新半旧；每对象页脚统计的高延迟读让"data skipping 比查询本身还久"；无版本/审计等管理功能。
2. **封闭存储引擎**（Snowflake 式把元数据放在强一致专有服务；Hive ACID 用 metastore RDBMS）：解决正确性，但每次 I/O 都要经元数据服务（可用性/性能/成本瓶颈，Snowflake Spark 连接器读数据要流经其服务）、连接器工程量大、供应商锁定；Hive metastore 在百万对象表上成为瓶颈。
3. **元数据进对象存储**（Delta 的选择）：事务日志直接放湖里，仅靠对象存储操作 + 乐观并发实现可串行化。作者声称 2016 年首创此设计，写作时点 Hudi 与 Iceberg 跟进（§2.4 第 3414 页）。

## 二、核心方法精读：日志即表

### 2.1 存储格式（§3.1 + 图 2，第 3414–3415 页；ASCII 重绘）

一张 Delta 表 = 一个目录：数据对象（Parquet，可按 Hive 约定分区）+ `_delta_log` 子目录（零填充编号的 JSON 日志 + 定期 Parquet checkpoint + `_last_checkpoint` 指针）：

```
mytable/
├── date=2020-01-01/
│   ├── 1b8a32d2ad.parquet   ← 数据对象（GUID 命名；分区列进目录名）
│   └── a2dc5244f7.parquet
├── date=2020-01-02/
│   └── ba68f6bd4f.parquet
└── _delta_log/
    ├── 000001.json  000002.json  000003.json   ← 每事务一条日志
    ├── 000003.parquet                            ← checkpoint：1..3 条压缩态
    ├── 000004.json  000005.json
    └── _last_checkpoint                          ← 内容如 {version: "000003"}
```

**日志动作集合**（§3.1.2，共 6 类）：
- `metaData`：表 schema、分区列、存储格式、配置（append-only 标记等）；首版本必含，后续整体覆盖。
- `add` / `remove`：加入/移除数据对象。**add 携带统计**（记录数、列级 min/max、null 计数）；同一路径重复 add 以最新统计为准（可用于"升级"老表的统计类型）。remove 带删除时间戳，对象**延迟物理删除**（保留期内旧快照仍可读，tombstone 必须留在日志里）。
- `dataChange` 标志：add/remove 置 false 表示该事务只是重排/补统计（压缩、改序），流读消费者可整体跳过。
- `protocol`：声明读写此表所需的协议版本——格式演进的守门员。
- `commitInfo`：操作者/时间等出处信息（审计日志的原料）。
- `txn`：`(appId, version)` 应用侧事务 ID——**exactly-once 写入**的钩子：流作业把自己的输入流 offset 与 add/remove 写进同一条原子日志记录，崩溃后重放即可判定从哪续。

**Checkpoint**（§3.1.3）：每 10 个事务（默认）把日志前缀压成一个 Parquet——去冗余规则：被 remove 的 add 成对消掉（remove 作 tombstone 保留）、同对象多次 add 保最新、同 appId 的 txn 保最新、metaData/protocol 保最新。产物是"每行一个当前对象 + 其统计"的列式文件，**天然适合用 Spark 并行查询元数据**。作者经验断言：用 checkpoint 找查询相关文件"几乎总是快过 LIST + 读 Parquet 页脚"（第 3415 页）。零填充编号让"找 checkpoint 之后的新日志"退化为一次字典序 LIST。

### 2.2 读协议（§3.2.1，五步，第 3416 页）

```
1) 读 _last_checkpoint 拿近期 checkpoint ID（读到过期值也无妨）
2) 从该 ID 起 LIST 日志目录，收集更新的 .json/.parquet
   —— 容忍最终一致造成的空洞（如见 04、06 不见 05：
      以最大 ID 为目标版本，等待缺件可见）
3) checkpoint + 尾部日志重放 ⇒ 表状态（add 无配对 remove 的对象集+统计），可并行
4) 用统计做 data skipping，圈定相关文件
5) 读数据对象；某 worker 暂不可见 ⇒ 短暂重试
```

设计哲学：**不变式只有一条**——"`N.json` 存在且可见 ⇔ 版本 N 已提交"；其余一切（页脚、_last_checkpoint、对象可见性）都只是性能提示，过期不破坏正确性。

### 2.3 写协议与"无锁服务"的可串行化（§3.2.2，第 3416–3417 页）

```
1) 定基线：按读协议 1)2) 找最新日志 ID r（读版本 r 的数据，如需）
2) 并行写新数据对象（GUID 命名，落到分区目录）——此时对读者不可见
3) 原子创建 (r+1).json（put-if-absent 语义）：
     成功 → 事务提交（唯一 root 数据结构落定）
     失败（他人已占号）→ 乐观并发重试；许多场合可复用第 2) 步的对象重新竞争
4) （可选）写 checkpoint 并更新 _last_checkpoint —— 纯性能操作，
   任意点崩溃都不会损坏数据
```

**put-if-absent 在不同后端的落地**（全文最"工程"的一张表，§3.2.2）：

| 存储 | 原子手段 | 备注 |
|---|---|---|
| GCS / Azure Blob | 原生条件写（atomic put-if-absent） | 直接用 |
| HDFS / ADLS(带文件系统 API) | 原子 rename（临时文件改名，撞名即败） | 开源连接器可用 |
| **Amazon S3（写作时点）** | **无**上述原语 | Databricks 服务：轻量协调服务只管日志写（负载极低，读写数据不经过它）；开源版：单 Spark 驱动内内存态发号 + 可插拔 `LogStore` 接口外接强一致存储 |

**隔离级别与事务率**（§3.3/§3.4，第 3417 页）：写-写经"一号一主"天然**可串行化**（提交序=日志编号序）；读为**快照隔离**（想可串行化读可用"假写"占号）；连接器缓存最新已见日志 ID ⇒ 实际上"读己之写"+单调版本序。**只支持单表事务**，多表共享日志被列为未来方向。写事务率受日志写延迟（几十~几百 ms）限制，约**每秒数笔**——作者论证这对 OLAP/批量入湖足够（流式摄取靠少数高并行作业合批提交），不够时可换低延迟 LogStore（日志尾驻 DBMS、异步刷对象存储）。

**形式化提交竞赛**（综合 §3.2.2 协议与 §3.3 隔离性论证）：

```
# 并发写者 W1、W2 同时基于版本 r 提交：
W1: create_if_absent("00000{r+1}.json", actions1) → OK   # 占号成功，提交为版本 r+1
W2: create_if_absent("00000{r+1}.json", actions2) → FAIL # 槽位已占
W2: read "00000{r+1}.json"(W1 的提交) → validate(actions2, delta)  
    # 冲突检查（如同文件 add、schema 变更）；无冲突则携带 r+2 重试第 3 步
# 不变式: ∀ 版本 N，恰好一个 N.json 存在且内容即该版本全部真相
#         ⇒ 提交序 = 编号序 = 可串行化序；读者永远只见"完整版本"
```

读者侧无需任何协调：版本 r 可见 ⇔ `r.json` 可见；旧对象在被 remove 后仍物理保留到保留期结束（tombstone + lazy delete），因此**长读不阻塞写、写不撕裂读**——这就是"日志即表"四个字的完整含义。

### 2.4 建立在事务之上的功能层（§4，第 3417–3419 页）

- **Time travel / rollback**：数据与日志全部不可变 ⇒ 按旧日志 ID 读即可；SQL 语法 `AS OF timestamp` / `VERSION AS OF id`；示例回滚：`MERGE INTO mytable USING mytable TIMESTAMP AS OF <old_date> …`；**CLONE**（copy-on-write 语义的表快照克隆）写作时在研——后成为 Iceberg 式 zero-copy clone 的同源概念。
- **UPSERT / DELETE / MERGE**：GDPR 删除、迟到数据修正等经新 add/remove 事务完成，读者全程不被阻塞。
- **流式读写三件套** = 写压缩（小对象快速落地→后台 `dataChange=false` 事务合并）+ exactly-once（`txn` 动作）+ **日志追尾**（从上次 ID 起 LIST 即见增量，`dataChange=false` 记录可跳过）⇒ 作者称许多场景可**撤掉 Kafka/Kinesis 消息总线**，用表当秒级延迟消息队列（§4.3 + 图 1 的架构简化案例）。
- **数据布局优化**：`OPTIMIZE`（默认目标对象 ~1 GB，可配）；**Z-Order**（Morton 1966 空间填充曲线，多维局部性；与每对象 min/max 统计耦合生效——Z 序让每个文件在每个维度上值域都变窄，可跳文件变多）；云服务上的 **AUTO OPTIMIZE** 自动压缩新写。
- **缓存**：不可变 ⇒ 本地 NVMe 缓存无失效风暴问题。成本论据（§4.5，第 3418 页）：i3 比 m5 贵约 50% 换来每核 ~237 GB NVMe，热数据集用 i3+缓存划算。
- **审计**：`DESCRIBE HISTORY`；Databricks 的"锁定执行模式"禁止 UDF 直触云存储，保证 commitInfo 只能由引擎写 ⇒ 不可篡改审计链。
- **Schema enforcement/evolution**：写入强制匹配 schema（作者称这一简单检查消灭了大量"多作业混写同目录"时代难以定位的脏数据问题）；日志记 schema 史 ⇒ 加列等变更无需重写旧 Parquet。
- **连接器**（§4.8）：Spark（批+流）全功能；Hive/Presto/Athena/Redshift/Snowflake 只读。只读系统大量借力 **symlink manifest files**（Hive 为符号链接发明的目录清单文件）：每目录写一个原子更新的文件列表，非分区表得到全一致快照、分区表得到"每分区内一致"。

### 2.5 生产使用画像（§5–§6 之前的部署证据，第 3412/3419–3420 页）

数千客户、日处理 EB 级、约占 Databricks 总负载一半；用例含 SIEM（某大厂全公司 TCP/UDP 流、认证、SSH 日志入 PB 级 Delta 表，日增数百 TB，100+ 分析师直接查询，Z-ORDER 支撑多维取证）、基因组学（Big Data Genomics 先例、与 Regeneron 开源 Glow；多例相对裸 Parquet 提速超 100×）、ML 图像库（百万级 KB 小图改为表内 BINARY 记录，喂 GPU 推理）、GDPR 合规、MLflow 联动（自动记录训练数据的表版本）。作者自报云存储类支持问题占比从一半降到近乎为零——均为厂商口径。

## 三、实验与数据（§6，第 3420–3422 页；全部数字取自原文）

1. **分区数爆炸（§6.1，图 4）**：33,000,000 行小表、1000~1,000,000 分区、16 节点 i3.2xlarge（每节点 8 vCPU/61 GB/1.9 TB SSD），S3 上跑 `SUM` 全表：
   - Hive（第三方托管）在 **10,000 分区即超 1 小时**；Presto 在 **100,000 分区超 1 小时**（图未画出）；
   - Databricks Runtime 读裸 Parquet：100,000 分区 **450 s**（已做集群并行 LIST 优化）；
   - **Delta：1,000,000 分区 108 s；日志缓存到 SSD 后 17 s**（比裸 Parquet 在 1/10 分区数下还快 ~26 倍）。
2. **Z-Order vs 全局排序（§6.2，图 5）**：网流数据（sourceIP/sourcePort/destIP/destPort 均匀随机），100 个 Parquet 对象，测点查可跳过文件比例：按 (sourceIP,…) 全序仅对 sourceIP 有效（99%），对其余三列失效（0%/47%/44%/0% 档口）；**Z-order 四列后每个维度至少可跳 43%，等概率假设下平均 54%**（单列排序平均 25%）。真实规模佐证：§5.4.1 组织 500 TB 流量表多维查询**跳过 93% 数据**。
3. **TPC-DS 1 TB power test（§6.3，图 6）**：1 master + 8 worker i3.2xlarge（各 8 vCPU），事实表按日期代理键分区，三次均值，时长（小时）：**Databricks+Delta 0.93 < Databricks+Parquet 0.99 < 第三方 Spark+Parquet 1.44 < 第三方 Presto+Parquet 3.76**。注意 Delta 对 Parquet 的优势本实验里只有 ~6%（作者明说：小表为主时分区元数据优势不显，Delta 主要加速了长查询）——与实验 1 对照才见全貌。
4. **写性能（§6.4，图 7）**：400 GB TPC-DS `store_sales`（CSV 源）装载入 Delta vs 入 Parquet 耗时相近 ⇒ 统计收集开销可忽略。
5. 诚实性注记：这是**以机制动机为目标的对照实验**（同硬件比 Parquet/Hive/Presto 与 Delta 的元数据路径），不是审计版 TPC-DS；无与 Hudi/Iceberg 的任何直接对比（当时版本迭代太快，§8 只作定性比较）。

## 四、与相关工作对比（仓库内互链）

- **本文 vs 封闭引擎**：Snowflake（§2.4 方案 2/§8）用专有强一致元数据服务换正确性，代价是全 I/O 过 Frontend 与锁定；Aurora/Redshift/BigQuery 需 DBMS 中介访问。Delta 的赌注：**OLAP 负载写事务率低、事务大**，乐观协议配得上对象存储延迟，故"格式+客户端库"即可，无常驻服务（S3 仅日志发号需轻量协调）。
- **本文 vs 同期开源表格式（§8 写作时点的自评，务必带时间戳理解）**：Hudi 当时单写者；Iceberg/Delta 均并发写；Delta 独有 Z-order、流式追尾源、云服务缓存、manifest 连商业数仓。⚠️ 三主客已大不同（Iceberg 后来居上成开放标准叙事，Deletion Vector/CDF 双方都有，Row Tracking/DV 使"整文件重写式 UPDATE"退休）——演化史见指南书笔记 [`../../book/Delta_Lake_Definitive_Guide/07-高级特性-DV与CDF.md`](../../book/Delta_Lake_Definitive_Guide/07-高级特性-DV与CDF.md)。
- **本文 vs Hive ACID**：metastore RDBMS 记状态 ⇒ 百万分区瓶颈 + 运维负担；Delta 把"元数据服务"换成"不可变日志 + checkpoint"，计算集群顺带并行化元数据查询（checkpoint 即 Parquet——这是对 MonetDB/X100 式"列存擅长扫描"经验的元数据侧 reuse，可与 [`../doi_10.14778_2002938.2002940/00-精读笔记.md`](../doi_10.14778_2002938.2002940/00-精读笔记.md) 对读：同一时代硬件下的两副面孔）。
- **HDFS 小文件问题谱系**（§6.1 引 Naik/Gummalla 2019）：Delta 的"小对象入湖 + 事务压缩"是 S3 语境下同一问题的新解。

## 六、批判与延伸

### 6.1 批判

1. **"无服务"是话术半句**：GCS/Azure 上确实纯协议；但作者自认 S3（当时最大市场）需要常驻轻量协调服务发号（§3.2.2）——高可用论证"协调器只碰日志不碰数据"成立，但"运维近零"对 S3 用户打了折。后续历史也证明：跨云一致性原语（S3 条件写 2021 年才到、Read-after-write 2020-12 强一致化）是让这套协议真正"无服务"的外部变量，**论文的优雅建立在当时恰好不成立的前提上**。
2. **单表事务的局限被轻描淡写**：真实数仓发布常是多表原子切换（星型模型维表+事实表）；日志按表分裂导致跨表只能靠应用层协议。§7 一句带过，之后十年该问题（catalog 级原子性、Iceberg REST、多表事务）反复被补票。
3. **每秒数笔写事务的上限**决定了 Delta 不是 OLTP：秒级流延迟下限由对象存储钉死（§7 承认）。"撤掉 Kafka"的案例都成立在"秒级可接受"的子集上；毫秒级链路仍需消息总线。
4. **实验的自选性**：§6.1 用"1M 分区"这种对 Parquet 最狠的配置开场（作者亦承认小表场景 Delta 仅快 6%，§6.3）；100× 提速出自特定高维选择查询的 anecdote。数字全部真实且口径自洽，但**分布偏向机制最优点**，需配 §6.3 的"6%"一起读。
5. **§8 对 Hudi/Iceberg 的功能对比是 2020 快照**，几乎全部"独有"项在 3 年内被追平或反向领先（Iceberg 的隐藏分区/分区演化设计更激进）；引用本文做格式选型论证属时代错置。
6. manifest 只读集成（§4.8）实为一致性降级方案：分区表仅"每目录一致"，跨分区可撕裂——文中一笔带过，生产上是真坑（后由各自引擎原生连接器消解）。

### 6.2 延伸

- 读演化史的最佳路径是 [`../../book/Delta_Lake_Definitive_Guide/05-原生应用与Delta-Kernel.md`](../../book/Delta_Lake_Definitive_Guide/05-原生应用与Delta-Kernel.md)：本文"格式+协议而非服务"的赌注，最终由 Delta Kernel（托管协议实现）与 UniForm（一份数据多格式元数据）推向"日志格式本身成为可互换 API"的方向。
- 并发协议对照精读：`Engineering_Lakehouses_with_Open_Table_Formats/06-事务与并发写.md`（Iceberg 的 catalog CAS 与 Delta 的对象存储 put-if-absent 是同一问题的两种根信任假设）。
- 与 [`../lakehouse_2021_armbrust_databricks/00-精读笔记.md`](../lakehouse_2021_armbrust_databricks/00-精读笔记.md) 的互读次序建议：先本文看"日志层怎么做对"，再看立场文看"这一层如何撑起整个架构论题"。
- 研究议程延续：多表事务、毫秒级流、二级索引（本文 §7 只预告 Bloom filter）、协调器托管化（Delta 2.x 后的 Managed/REST catalog 与 Deletion Vector，均超出本文时间窗）。

### 6.3 思考题（5 道）

1. 写协议第 2 步"先并行写数据对象、再争抢日志槽位"意味着失败重试时可能留下**永久无人引用的孤儿对象**。论文说"某些场合可复用第 2) 步的对象重新竞争"，请分析：哪些操作可以安全复用、哪些必须重写的？垃圾回收应当依据什么信息判定对象不可达？（对照 VACUUM 与保留期机制。）
2. put-if-absent 在 S3 上缺位时，论文用"只写日志的轻量协调服务"补位。请对比：这个协调服务与 Snowflake 的元数据服务在**故障半径**（crash 后谁能读/谁能写）与**性能上限**上的本质差异——"只碰日志不碰数据"到底换来了什么？
3. §3.3 说快照读要升级为可串行化读可以"写一条假写占号"。请论证该技巧为何有效（提示：占号后你观察到的版本区间），并给出一个不用假写、仅靠客户端缓存日志 ID 无法达成的异常场景。
4. Z-order 在 §6.2 的均匀随机数据上平均每维可跳 54%，远达不到全局排序对首列的 99%。这说明 Z-order 的收益边界在哪里？若查询谓词分布已知（90% 查询带 sourceIP 等值 + 时间范围），你会选全局排序、Z-order 还是混合布局？
5. checkpoint 是日志的 Parquet 压缩态，本身不可变、每 10 事务一份。请推导：checkpoint 间隔取 1 与取 10000 分别把成本压到哪一侧（写放大 vs 读时重放）？流读"追尾"场景下最优间隔如何随版本变化？

## 八、阅读方法与常见误读提醒

1. **把本文当"协议规范"而不是"产品手册"读**：真正的设计资产是 §3 的日志格式与提交协议（JSON schema 至今向后兼容）；§4 的功能清单大多已改名换貌（AUTO OPTIMIZE→OPTIMIZE 托管化、Z-ORDER→Liquid Clustering）。
2. **"ACID"的边界要看清三个限定词**：单表、写少读多、快照隔离读——§3.3/§3.4 的诚实声明比摘要里的"ACID"三个字更重要。拿它对照 OLTP 事务论文是范畴错误。
3. **实验的对照组是"裸 Parquet/Hive/Presto"，不是 Iceberg/Hudi**：全文没有一行与另两家的定量比较；§8 的定性对比句请连同时间戳引用。
4. **"表当消息总线"有秒级延迟地板**（§7），且写事务率每秒数笔：判断适用性先问"我的下游能接受多长的处理间隔"。

## 九、一页总结（复习卡）

- **问题**：对象存储便宜但只是最终一致的 KV——多对象无原子、LIST 昂贵、页脚统计读不起，湖上表无 ACID 无性能。
- **方案**：把"表的真相"编码进一条不可变 JSON 日志（版本 r = 重放 1..r 的动作），checkpoint 化 Parquet 令元数据查询享受列存与集群并行；提交=争抢唯一日志槽位（put-if-absent），乐观并发即得可串行化；无任何常驻服务（S3 除外，需轻量发号器）。
- **所得**：ACID、time travel、exactly-once 流、UPSERT/MERGE、Z-order 跳过、缓存、审计——全挂在同一日志上；百万分区元数据从小时级降到百秒级（17 s 缓存），TPC-DS 1 TB 快裸 Parquet 6%、快 Presto 4 倍。
- **所欠**：单表、秒级、写事务率个位数；二级索引缺位；S3 协调依赖。
- **位置**：与 Iceberg（2018 Netflix→2020 ASF）、Hudi（Uber）同开"开放表格式"赛道；本文是其奠基工程报告中唯一"格式即协议"立场最纯粹的一篇——三年后的 Lakehouse 论文把它升格为整个数据平台的元数据支柱。
