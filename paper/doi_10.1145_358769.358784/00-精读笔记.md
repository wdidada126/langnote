## 二、背景与问题：一场"证明 Codd 是对的"的工程运动

### 2.1 1974 年的论战格局

Codd 1970 给出关系模型后，产业与学术的主流质疑非常实际（通说，与 Codd 笔记 §三呼应）：

1. **性能怀疑**：层次/网络模型（IMS、IDMS）靠"用户带指针游走"获得快性能；关系模型声明式遍历"所有元组"，被认为在 70 年代硬件上不可用。
2. **无实现**：模型是数学，没有人造出能上生产的 DBMS，IBM 内部甚至一度以"违反 Codd 十条"的产品（SQL/DS 前史）与学术阵营互相拉扯。
3. **编程界面真空**：应用如何声明"要什么而不说怎么做"，语言层没有答案。

IBM San Jose/Yorktown/Watson 研究中心于是立项 System R（1974/75，负责人 W. F. King，通说），使命被本文概括为三个交付：**做一个真实可用的多用户关系 DBMS 原型；发明并稳定一门查询语言；用实现与测量裁决"关系模型可行性"之争**。这是一次罕见的"以造出来为论证方式"的科研工程——本文的副标题式叙事正是 "we built it, here is what it cost, and the model survives"。

### 2.2 论文自己声明的评估问题

- 关系模型在真实并发、故障、大数据量下是否兑现其简洁性承诺？
- 编译式访问路径选择（优化器）能否补上"声明式查询"的性能缺口？
- 一门高度非过程化的语言（SQL）能否被普通程序员接受、并被编译器高效翻译？
- 代价是什么：响应时间、代码体量、运维复杂度、以及哪些设计事后证明是错的？

## 三、核心设计精读

### 3.1 总体架构：编译器侧 + 存储侧，以消息为界

论文对 System R 的经典划分是"上半身（语言与优化）+ 下半身（存储子系统）"，两侧以进程/地址空间分离、经消息交换交互（此分离结构为通说表述，具体进程边界细节以原文为准，未逐字核）：

```
            ┌────────────────────────────────────────────────┐
            │                  应用 / 终端                     │
            └───────────────┬────────────────────────────────┘
                            │ SQL 语句
        ┌───────────────────▼───────────────────┐
        │  SQL 预处理器/编译侧（上半身）           │
        │  parser → normalizer → optimizer       │
        │        (视图合并/谓词规范化)  (Selinger   │
        │                              代价模型,   │
        │                              1979 通说)  │
        │  输出：关系代数操作计划                   │
        └───────────────────┬───────────────────┘
                            │ 计划（代数算子序列）
        ┌───────────────────▼───────────────────┐        ┌─────────────────┐
        │  RRA：关系代数执行机器（解释式）          │  消息   │ DBWS            │
        │  join/投影/选择/排序等算子逐个解释执行    ├───────►│ 锁/日志/恢复/提交  │
        │  （"relational algebra machine"）       │        │ 看门狗服务        │
        └───────────────────┬───────────────────┘        └────────┬────────┘
                            │ 页/记录级请求                        │
        ┌───────────────────▼───────────────────┐                │
        │  RELSTORE 存储子系统（下半身）           │◄───────────────┘
        │  页空间管理·B+树索引·缓冲池·记录定长槽位    │   （锁表/日志由其管理）
        └────────────────────────────────────────┘
```

- **RRA（关系代数机器）**：编译侧不生成机器码，而是产出一串**关系代数算子请求**，由解释器逐算子驱动、向存储子系统要数据。这是 70 年代解释开销观念下的选择；其代价（每操作一次上下层往返）正是后来编译执行路线（本仓库 [`../doi_10.14778_2002938.2002940/00-精读笔记.md`](../doi_10.14778_2002938.2002940/00-精读笔记.md)，Neumann 2011）反复对照的起点。
- **DBWS（DataBase WatchDog Service，锁/日志守护模块；缩写展开为通说，标注待核）**：并发控制与恢复的"看门狗"。它作为**独立于用户任务的服务线程/模块**存在，管理锁表与日志序列；用户任务的每次页/记录访问都要经过它做相容性检查。论文的线程模型要点（通说转述）：存储子系统多任务并发，DBWS 以串行化的锁/日志临界区保证全局一致性——这是"把正确性收拢进一个守护点"的早期范本，与 Gray 1981 §2.2 的恢复架构同构。
- **RELSTORE**：定长页 + 记录槽（slotted page）、B+ 树索引、缓冲池；其后的 ARIES 谱系（本仓库 [`../../db/ARIES.md`](../../db/ARIES.md)）正是对这套日志/恢复机制的教科书化。

### 3.2 SEQUEL → SQL：一次商标意外塑造了语言史

论文重述了命名公案（通说，各教材一致）：Chamberlin & Boyce 最初的语言叫 **SEQUEL**（Structured English QUEry Language）；因与 Hawker Siddeley 的 "SEQUEL" 导弹/飞机名称**商标冲突**，更名为 **SQL**（Structured Query Language），读音按字母 S-Q-L。工程含义比名字更重要：

1. SEQUEL-XRM（1974–76）→ SEQUEL 2 → **SQL**（IBM 文档版）→ ANSI 1986 / ISO 1987 标准化——本文是这条链的"官方结案陈词"。
2. 语言设计教训：集合导向（一次一关系）优于记录导向；子查询/视图/授权被验证可用；而**空值与三值逻辑**是论文承认的后患（"NULL 的设计是遗憾"为广为转述的 Selinger/Date 评论，归属未核，标注通说）。

### 3.3 并发控制与"两阶段提交的原型化"

- 系统级并发控制 = **谓词锁 + 两阶段锁（2PL）**：概念来自 Eswaran/Gray/Ries 1976（Gray 笔记 §1.1 已述）；System R 是其**第一个工业级落地场**（通说）。锁粒度多粒度化（表/页/行）与意向锁在实现中演化（细节以原文为准，未逐字核）。
- **提交协议**：本地提交走"日志强制先写"的顺序——commit 记录在修改可见之前落入日志序列；这即是 prepare/commit 两段式日志思想在单库环境的原型。跨站点的事务（R* 分支）才完整实现 **two-phase commit**：prepare 收集全票、commit 记录写序（通说；Gray 1981 §2.1 给出 2PC 的概念表述，本文/谱系给出实现表述）。
- 读提交松弛：System R 实现了"度数"光谱的早期版本——只读查询可运行在快照/不一致读模式换取吞吐（通说；Gray 1981 §2.3 度数语言与之互证）。

```pseudo
-- 提交路径（按论文精神整理的伪码，非原文逐字）
on commit_request(txn):
    for obj in txn.locks: assert txn holds all locks in 2PL sense  -- 未释放任何锁
    force_log(record: BEGIN_COMMIT, txn_id)      -- WAL：日志先于数据可见
    DBWS.release_all(txn.locks)                  -- 2PL：提交点集中释放
    force_log(record: END_COMMIT, txn_id)        -- 之后修改对外可见
on crash_recovery:
    scan_log_forward(): redo 已提交事务的页修改
    scan_log_backward(): undo 未提交事务
```

### 3.4 多版本分支（Multran）与单版本的取舍

论文描述了 System R 的两条实现线：**单版本**（更新原地覆盖，读被锁挡）与**多版本**（每修改留版本历史，读者不挡写者，通说）。这是"MVCC 第一次成文对照实验"之一，本仓库 [`../../db/mvcc.md`](../../db/mvcc.md) 系列的史前史可追溯到此处；代价（版本膨胀、垃圾回收）论文已直言。

### 3.5 论点逻辑链小结

1. 模型之争只能由实现裁决 → 造一个真系统。
2. 声明式语言的可行性 = 语言（SQL）× 翻译（normalizer）× 代价优化（Selinger）× 执行（RRA）× 正确性（DBWS/2PL/日志）。
3. 每一环都被原型验证"能做"，同时每一环都暴露代价（解释开销、NULL 语义、2PL 热点、恢复复杂度）。
4. 结论：关系模型工程上成立；产业可放心押注——SQL/DS（1982）与 DB2（1983）随即商业化（通说）。

## 四、实验与工程取舍：论文"Evaluation"部分的诚实

- **性能结论定性表述**（本笔记未逐字复核原文表格，数字不引）：论文报告 System R 在 370 级硬件上的实测**并不总是胜过 CODASYL/IMS 式应用**——声明式查询的编译与解释开销在短事务/点访问场景是可见税；但在复杂查询、即席查询与开发效率上显著占优；优化器（访问路径选择）能把多数典型查询拉到可接受区间。"关系系统慢"的说法在 1981 年并未被彻底推翻，被推翻的是"关系系统不可用"。
- **工程教训清单**（论文以复盘口吻给出，条目化转述）：
  1. 解释式执行（RRA 逐算子往返）是吞吐瓶颈之一——为编译执行/向量化留下四十年后续议题。
  2. 2PL + 提交点放锁在热点数据上的冲突率随并发上升——Gray 1981 Limitations #1 的实验版。
  3. NULL/三值逻辑给 normalizer 与优化器带来的边角复杂度超预期（通说）。
  4. 原型规模（数万行级）暴露"论文里没有的代码"问题：恢复、并发、目录管理的相互纠缠远比单模块论文复杂——这直接催生了后来 Gray & Reuter 1993 教科书化（通说）。
- **评估的自我批评尺度**：作为建造者自评，本文天然倾向"目标达成"叙事；对"哪些指标是自证、哪些是产业后果"的分离，读者需借外部史料（INGRES 对照、DB2 后来性能危机、Teradata/Oracle 商业竞争）校正。

## 七、批判与延伸

1. **"实现验证模型"叙事的强与弱**：强在本文是四十年接口（SQL）的出生证明，DB-Engines 至今榜单都是它的下游（[`../../db/DBEngines.md`](../../db/DBEngines.md)）；弱在建造者自评天然过滤失败细节——例如"多版本分支最终未成为主流提交物""NULL 决策的过程"都需靠 Selinger、Date 的后续文章补全。建议把本文与 Gray 1981 对读：前者乐观，后者专章写 Limitations。
2. **本文没说的**：分布式（R* 单列他文）、统计目录的失效场景、优化器在真实工作负载上的退化——这些在 80 年代 DB2 性能危机与 90 年代 TPC 基准运动中被翻案（通说，延伸线索见 [`../../db/db_optimize.md`](../../db/db_optimize.md)）。
3. **延伸谱系**：
   - 执行层：RRA 解释 → Volcano/Extism 迭代器 → 编译执行（HyPer [`../../db/HyPer.md`](../../db/HyPer.md)）→ 向量化（ClickHouse 等）——解释开销问题四十年后才被 Neumann 2011 一系彻底关闭。
   - 并发层：2PL/Multran → MVCC 主流化（[`../../db/mvcc.md`](../../db/mvcc.md)）→ 快照隔离异常学（Adya 1999）。
   - 提交层：本地 WAL → 2PC → Paxos/共识 → Spanner（[`../spanner_2012_osdi/00-精读笔记.md`](../spanner_2012_osdi/00-精读笔记.md)）与 Calvin 的"预排序去协调"（[`../doi_10.1145_2213836.2213838/00-精读笔记.md`](../doi_10.1145_2213836.2213838/00-精读笔记.md)）。
4. **组织遗产**：16 人署名本身是"研究项目即人才泵"的证据——Gray 去了 Tandem/DEC/MSR，Selinger 去了 Stanford 与后来的决策支持产品，Lindsay 一系进入 Tandem/Compaq——本文作者名单半数是后来二十年数据库工业的布网者（通说）。

## 十、思考题（5 道）

1. System R 用"解释式 RRA + 优化器"兑现声明式语义，代价是每算子与存储子系统往返。请按四十年后的向量化/编译执行知识，指出这套架构里**哪一条约束在 1977 年是真实的、哪一条后来被硬件与编译器技术证伪**。
2. 论文承认关系访问在短查询上有"翻译税"。构造一个点查询（按主键取一行）场景，逐步对比 IMS 指针游走与 System R 全链路（parse→normalize→optimize→RRA→RELSTORE）各自的指令级开销来源，并说明为什么后来的 plan cache 是必要的补丁。
3. DBWS 把锁/日志/提交收拢为单一守护点。若你重设计 System R 的线程模型以利用多核，守护点会成为瓶颈——请给出至少两种拆分方案（分片锁表、日志流水线）并说明各自引入的正确性风险。
4. "实现验证模型"的叙事是否意味着 System R 的设计选择（NULL、三值逻辑、SQL 语法）都被误当成了模型本身的一部分？举一例说明后人对它的翻案（如 Date 对 NULL 的持续批评）。
5. 把本文 §Evaluation 的自评与 Gray 1981 Limitations 六条对读：Gray 的哪几条局限其实是 System R 团队自己已经付出过学费、但本文未展开的？据此评价"建造者回顾文"的史料可靠性。

## 十一、误读提醒与核实记录

### 11.1 误读提醒

1. **DOI 别引错**：流传的 `10.1145/358769.358771` 不存在（Crossref/handle 双源实测），正确为 `10.1145/358769.358784`。
