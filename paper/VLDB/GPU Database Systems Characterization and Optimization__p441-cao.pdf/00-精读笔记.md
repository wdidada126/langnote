## 一句话总结
给四套 GPU 数据库系统做「跨栈 + 微架构」体检，用 roofline 模型找出算力/带宽被浪费的地方，再针对性改实现与用 MIG 做资源分配，单查询延迟降 1.9×、并发吞吐最高提 6.5×。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：GPU 显存带宽大、并行度高，很适合加速分析型查询；但「有 GPU」不等于「用得好」。本文研究的是怎么把 GPU 数据库跑得快——既要单查询快，也要多查询并发时把 GPU 喂满。
- 为什么难：GPU 资源（SM 数量、DRAM 带宽、缓存、MIG 分区）很多，但 DBMS 的实现常没「对症」利用；查询特征（算密集型 vs 访存密集型）、数据量、并发度都会改变瓶颈所在。
- 几类主流解法（刻画/优化路线）：

| 路线 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 跨栈性能剖析 | 本文 | 从查询到底层硬件指标，定位瓶颈 | 系统、可迁移；不直接给新算法 |
| roofline 模型 | 经典方法 | 用「算/带宽」上限判断受限于算力还是带宽 | 直观；需准确采集指标 |
| MIG 资源隔离 | NVIDIA 多实例 GPU | 把一块 GPU 切成多个实例并行服务不同查询 | 提升并发；切分粒度受限 |
| 并发查询调度 | 各 GPU DBMS | 批量查询并行执行 | 提吞吐；易因资源争用掉速 |

- 本文属哪类：属于「系统刻画 + 工程优化」，不是提出新索引/新算子，而是告诉业界「现有 GPU DBMS 哪里没跑满、怎么改」。
- 2-3 个必懂关键名词：
  - Roofline 模型：一张图横轴是算术强度（每字节内存访问对应的浮点运算），纵轴是可达性能；点在「算力屋顶」下说明受算力限制，在「带宽斜线」下说明受内存带宽限制。
  - MIG（Multi-Instance GPU）：把一块物理 GPU 切分成多个独立实例，各自有专属算力和显存，适合并发跑多个查询/多租户。
  - Microarchitectural 指标：GPU 底层的 SM 占用率、DRAM 带宽利用率、L2 命中率、warp 效率等。

## 1. 问题背景与动机
- 前人工作简述：已有研究比较过不同 GPU DBMS 的查询性能，但缺少「把查询性能与 GPU 资源利用、微架构指标连起来」的跨栈分析。
- 前人缺陷/未解决问题（逐条）：
  1. 只比快慢，不解释「为什么慢」——瓶颈在算力、带宽还是同步开销说不清。
  2. 没用 roofline 这类经典模型把「资源被浪费」量化出来。
  3. 没给出可落地的实现级 + 资源分配级优化（如 MIG 怎么切）。
  4. 对并发场景（多查询同时跑）的资源争用研究不足。

## 2. 核心方法
- 最直观类比：GPU DBMS 像一辆大马力跑车（GPU），之前大家只比「谁跑完一圈快」，本文是把它开上测功机，看发动机转速、油温、轮胎抓地，找出「马力没用满」的环节再调校。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 选系统：评测四套 GPU 数据库（含 SOTA 的 Crystal 与较新的 TQP 等）。
  2. 跨栈采集：跑基准查询，同时采 DBMS 层指标（算子耗时）与 GPU 微架构指标（SM/DRAM/L2/warp）。
  3. roofline 定位：把每个查询画到 roofline 上，判断是算力受限还是带宽受限，找出资源利用不足。
  4. 两层优化：实现层（改算子/内存布局/同步）+ 资源分配层（用 MIG 给并发查询切分 GPU 实例）。
  5. 输出：优化后的系统配置与对应的延迟/吞吐收益。
- 形式化要点：核心是「瓶颈诊断 → 对症下药」，没有新理论公式；关键超参是 MIG 实例划分方式与并发度。
- 理论性质/保证：无理论最优性保证，贡献在经验性刻画与工程优化。

## 4. 实验结论（概览）
- 对比基线：四套 GPU DBMS 在优化前后的自身对比（含 Crystal、TQP）。
- 数据集/指标：分析型查询基准；指标为单查询延迟、并发查询吞吐、各类 GPU 微架构利用率。
- 结论方向（摘要已核实数字）：
  - 单查询执行延迟降低 1.9×。
  - 并发查询执行吞吐最高提升 6.5×。

## 7. 2026 视角（🔧）
- GPU 数据库（如 GPU 加速的列式/向量引擎）在交互式分析、向量检索、HTAP 加速中持续受关注；MIG 与多实例隔离已成为云上「一块卡服务多查询/多租户」的标配思路。
- 趋势：把 roofline/微架构剖析做成「自动调优闭环」，以及异构（CPU+GPU）流水线调度。本节为趋势性判断，具体产品矩阵请查当年资料。
