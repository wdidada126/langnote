## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：自驱动（autonomous / self-driving）DBMS 想自己调优（索引、knob、分区等），它依赖 ML「行为模型」预测某配置下查询多快/多准，而不真去跑。但训练这种模型需要大量「(配置, 真实运行表现)」数据，而真跑查询极贵——SOTA 方法 93%+ 时间花在跑查询训练而非调优。
- 为什么难：① 收集训练数据要在 DBMS 里反复执行查询，成本高；② 模型是「实例相关」的，环境一变就要重训；③ 要在「少跑查询」和「模型别太不准」之间权衡。
- 几类主流解法：

| 路线 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 数据库 gym（仿真环境） | OtterTune 系、本文的 gym | 在安全环境里跑负载、造训练数据 | 安全但造数据仍慢 |
| 主动学习 | 多种 | 只挑最有价值的配置去测 | 减少样本但仍有执行成本 |
| 近似/代理执行 | 本文 Boot | 改查询语义+跳重复执行 | 极快；需保证模型误差可控 |

- 本文属哪类：在「数据库 gym」里加一层 MMA 加速，属于训练数据收集加速。
- 2-3 个必懂关键名词：
  - 行为模型（behavior model）：预测「给定配置下查询会多快/资源耗多少」的 ML 模型，是自驱动 DBMS 做决策的大脑。
  - 数据库 gym：一个仿真/沙箱环境，让 DBMS 安全地生产训练数据、训练并评估模型，不动生产库。
  - MMA（Macro- and Micro-Acceleration）：宏加速改「跑哪些/怎么跑查询」的整体语义，微加速在算子内部用近似遥测、跳过重复部分。

## 1. 问题背景与动机
- 前人工作简述：已有自驱动 DBMS 与数据库 gym（如 OtterTune、各类 knob/index 调优），普遍靠执行查询造训练数据。
- 前人缺陷/未解决问题（逐条）：
  1. 训练数据收集占 93%+ 时间，真实部署不现实。
  2. 模型实例相关，环境变化需重训，又得再花一遍昂贵执行。
  3. 缺少在不显著损伤模型精度的前提下「大幅加速数据收集」的系统性方法。

## 2. 核心方法
- 最直观类比：自驱动 DBMS 像健身房里练肌肉的运动员，行为模型是「教练对动作效果的预测」；平时教练得让运动员把每个动作真做无数遍才能学准（慢）。Boot 像给运动员配了「阻力带+动作捕捉」——用近似但够用的方式替代部分真实负重，练得快得多，肌肉记忆（模型）只差一点点。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：目标 DBMS + 代表性负载（SQL 轨迹）。
  2. 宏加速（Macro）：修改查询执行语义，例如用近似的运行时遥测代替精确计数，或合并等价执行路径。
  3. 微加速（Micro）：在算子内部跳过重复/冗余的执行步骤，只采集模型需要的信号。
  4. 训练：在 PostgreSQL 的数据库 gym 里用加速后的数据训练行为模型。
  5. 输出：训练好的行为模型 + 大幅缩短的数据收集时间。
- 形式化要点：核心是「近似执行换速度，且保证模型误差可接受」；超参是近似强度/跳过量的平衡。
- 理论性质/保证：论文给出精度退化的经验界（modest degradation），非严格理论最优。

## 4. 实验结论（概览）
- 对比基线：SOTA 行为模型训练流程（非加速版）。
- 数据集/指标：DBMS 负载基准；指标为训练数据收集时间、模型精度（预测误差）。
- 结论方向（摘要已核实数字）：
  - 训练数据收集时间最多降低 268×。
  - 模型精度仅「适度下降（modest degradation）」。
  - MMA 方法随数据集规模与工作负载复杂度可扩展。
