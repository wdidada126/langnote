## 二、问题史：RDBMS 如何"赢过一次、输掉未来"

- 关系模型靠**数据独立+代数接口**统一了 1980–2000（✅ 论文史观）。
- 新负载六边（✅ 论文 §2 清单式论证）：web 读写比、社交图谱递归、传感器流、科学数组、分析扫描、键值缓存——每个都踩中单一 SQL 引擎的某根软肋（页存、锁、B 树、行式、批式）。
- 判词："the market for general-purpose systems is ending"（✅ 立场句 ⚠️ 措辞凭记忆）。

## 三、负载-架构映射（论文核心表格的复述，✅ 大意）

| 负载 | 错配点 | 处方 |
|---|---|---|
| 读多写少页缓存（web） | 关系开销/锁 | 键值缓存 |
| 分析扫描 | 行式 I/O | 列存+压缩 |
| 社交/推荐递归 | JOIN 爆炸 | 图遍历原生 |
| 传感流 | 事务延迟 | 微批流 |
| 科学数据 | 元组模型 | 数组存储（SciDB） |
| OLTP 高并发 | 闩锁 | 主存单线程（H-Store） |

（⚠️ 表格行序与措辞为笔记归纳，论文正文为逐段论证。）

## 四、批判读法

- **预言半对**：专用化确实爆发（NoSQL 蛮荒 2010–2015 ✅）；但"融合引擎"反攻也真实——Postgres 用扩展生态吞掉 JSON/数组/向量（pgvector ✅），云数仓用 HTAP 缝合 OLTP/OLAP（⚠️）。
- 低估了**接口统一性**的市场价值：多引擎=多套一致性/运维/权限，企业为此付"通用税"心甘情愿（⚠️ 对照 2015+ 的"回到 Postgres"潮流）。
- 论文把 SQL 当靶子，但多数病灶其实在**物理架构**（页/锁/行式），与 SQL 接口正交——"one SQL, many engines"是它没写出的第三条路（⚠️ 判断）。
- 修辞学范本价值：负载驱动设计的论证结构至今是体系结构课教材（✅）。

## 五、🔧 本地微实验（非本书引擎行为）

1. **JOIN 爆炸模拟**：10^4 节点幂律图，SQL 递归三跳 vs 邻接表 BFS，计中间表行数。
2. **行/列扫描对拍**：同一张宽表，SQLite 行扫 vs parquet 列扫求和，计时与字节量。
3. **数组切片**：numpy C-order vs Fortran-order 对"时间轴切片"的带宽差，复现科学负载错配。
4. **缓存旁路**：键值读走内存哈希 vs 走 B 树索引，测延迟分布。
5. **通用税量化**：用 Postgres JSONB + 普通表双写同一负载，感受"融合引擎"的常数开销。

## 八、最新演进与工业实践

- NoSQL 野蛮生长期（2009–2014）≈ 论文的直接果实；随后"NewSQL/多模 SQL"把分裂重新缝合（⚠️）。
- pgvector/JSONB/ClickHouse 的边界战争按负载切片重演——论文框架仍是解释力最强的地图（✅ 判断）。
- 云厂商"多引擎一条 SQL 入口"（Athena/Synapse 类联邦、BigQuery 多模）是 OSFA 论题的 2024–2026 答案：接口 one-size、物理 many-engine（⚠️ 判断）。
