## 一句话总结
FASTER 在高性能和混合存储上很成功，但遇到「工作集远大于内存、且访问极度倾斜」的工业负载就吃力。F2（FASTER v2）改用「两层、面向记录」的设计：无锁日志压实、给冷记录用的两级哈希索引、给读热点用的读缓存——在目标负载上比现有 KV 存储吞吐高 2–11.9 倍，并已开源。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：搜索、消息、Serverless 等大规模服务用 KV 存储扛高吞吐；但当「内存装不下全部工作集、且少数 key 被疯狂访问（倾斜）」时，传统 LSM/B-Tree KV 对现代硬件利用不佳。
- 为什么难：大且倾斜的负载同时带来——索引开销大、压实（compaction）重、读热与写热工作集不重叠难以分别优化。
- 几类主流解法：

| 路线 | 代表 | 思路 | 取舍 |
|------|------|------|------|
| LSM / B-Tree KV | RocksDB 等 | 成熟通用 | 大倾斜负载下硬件利用差 |
| FASTER | 原 FASTER | 高性能、混合存储 | 大倾斜负载仍有短木板 |
| 两层记录式（本文） | F2 | 冷热分离 + 读缓存 + 无锁压实 | 针对倾斜负载优化 |

- 本文属哪一类：并发 KV 存储的演进设计，FASTER 的继任者。
- 关键名词直觉：
  - 倾斜工作负载（Skewed Workload）：少数 key 被极频繁访问（如热点用户），多数很冷。
  - 工作集大于内存：活跃数据放不下 RAM，需混合/分层存储。
  - Latch-free（无锁）：用原子操作而非锁做并发控制，减少争用、提升多核扩展。

## 1. 问题背景与动机
- 前人工作简述：FASTER 作为高性能开源 KV 库，在内存与混合存储都表现出色。
- 前人缺陷/未解决问题（逐条）：
  1. 面对大倾斜负载时，索引与压实开销高。
  2. 读热与写热工作集不重叠，却未被分别高效管理。
  3. 对「工作集远大于内存」的场景利用现代硬件不充分。

## 2. 核心方法
- 最直观类比：FASTER 像一辆好车，但拉「超大且头重脚轻」的货就吃力；F2 像给这辆车做了改装——把「冷货」和「天天要的热货」分开放（两层设计）、给热货加个随手取的架子（读缓存）、并且卸货（压实）全程不用停车锁门（无锁）。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 两层、面向记录的设计：处理大于内存的倾斜负载，冷热记录分开组织。
  2. 无锁日志压实：多线程日志压实的新无锁算法。
  3. 两级哈希索引：为冷记录降低索引开销。
  4. 读缓存（Read-cache）：专门服务读热点记录。
  5. 输出：在目标负载上更高吞吐的 KV 存储。
- 形式化要点：核心创新——两层记录式架构、无锁日志压实、两级哈希索引、读缓存；超参数以论文为准 🔧。
- 理论性质/保证：以系统实现与实验为主，未提供形式化最优性保证。
