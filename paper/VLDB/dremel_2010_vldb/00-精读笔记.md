## 二、问题史：为什么文件不够、SQL 不动

- 数据现实：web 级数据天然是**嵌套重复记录**（protobuf 风格），GFS 上以列式分块文件（Columnar Block Files）落盘（✅）。
- Google 内部当时的选择：MapReduce 跑批太慢（分钟起步）；交互式工具缺标准接口——Dremel 的靶心是**秒级 ad-hoc + 列存扫描 + 嵌套 schema**（✅）。
- 容量假设：单查询扫 PB 级、列族裁剪后 TB 级；并发数百查询（✅ 论文量级口径）。

## 三、数据模型：嵌套表与重复树

### 3.1 Record/Group/Field 代数

- Schema = 类型树；每字段带 mode（required/optional/repeated）；行是**树**不是元组（✅）。
- 展平（flatten）语义争议核心：一条记录内多个 repeated 字段的组合做**笛卡尔积**——这是 Dremel 语义被后来 Iceberg/SQL:2023 嵌套模型反复对照的点（⚠️）。

### 3.2 列式存储（CBF）

- Columnar Block File：块内按列切段，编码压缩（bitpacking/RLE 等，✅），嵌套 repeated 字段用**路径物化**列 + min/max 结构（⚠️ 细节凭记忆：论文提 level-encoding 思想，具体 definition/repetition level 是 Parquet 后来命名）。

## 四、执行引擎：树状下推

- 查询计划执行树（Set Expression Operators）：Scan / Group / Union / Selection / Aggregation / Join 以**集合表达式**算子组成树，数据按 block 批量流动（✅）。
- Shortest-path scheduling：协调者把计划树直接铺到存储节点，扫描尽量在数据所在机（✅）。
- **多级扇出（multi-level dispatch）**：根服务器→中间层→叶层，千台并发分发+回收，靠"先结果后细节"的流式回收压缩尾延迟（✅）。
- **延迟物化（late materialization）**：投影先行、属性后取，配合 skip-index（block min/max）跳过（✅）。
- Shuffle-Join 与 Broadcast/Partitioned Join：小表广播、大表按 join 键重分区（✅）。
- 无分布式事务——Dremel 只读已提交到 GFS 的不可变文件；写入路径属于 Colossus/其他系统（✅ 边界声明）。

## 五、评测（✅ 定性）

- 论文曲线：扫描量 <1TB 时近线性扩展；10^12 行表投影+过滤秒级返回（⚠️ 具体秒数以图表为准）。
- Join 与聚合在数百节点规模下受网络与扇出支配；作者自述瓶颈在"root server 回收"（⚠️ 记忆口径）。

## 六、批判读法

- Dremel 语义（笛卡尔展平）与标准 SQL 不等价且论文轻描淡写——BigQuery 多年后的 UNNEST 语法即为此补丁（⚠️）。
- 树状下推假设查询只读；对交互 BI 的更新/事务需求零答案——那是 F1/Spanner 的地盘，Google 用系统分工回避了 HTAP 命题（⚠️）。
- 论文是架构素描：调度器容错（leaf 失败重试策略）、内存管理几乎未写，复现者（Cloudera Kudu/Drill 系）都踩了坑（⚠️）。
- 与同期 PowerDrill（⚠️ 未建）、Redshift（SIGMOD 2012 ⚠️ 未建）对照：Dremel 赢在嵌套模型+PB 规模假设，输在无成本模型公开。

## 七、🔧 本地微实验（非本书引擎行为）

1. **重复树展平**：手写 JSON 含两个 repeated 字段，实现"组内笛卡尔 vs 拉链对齐"两种展平，对比结果行数差异——理解 Dremel 语义争议。
2. **列存块裁剪**：按列切 JSONL 成块并记 min/max，跑谓词统计跳过块数。
3. **多级扇出模拟**：threading 造 1→4→16 树，每叶随机 sleep，对比"串行回收 vs 流式合并回收"的总延迟。
4. **延迟物化**：先全表过滤投影出 row-id 集，再按键取宽列——对比一次性宽行扫描的字节量。
5. **位 packing**：小整数列表手写 bitpack+RLE，测压缩比。

## 十、最新演进与工业实践

- BigQuery（2010 GA→ slot 定价 2019→ 存算分离再改）全线继承 Dremel 语义；UNNEST/STRUCT/ARRAY 语法固化嵌套模型（⚠️）。
- Presto/Trino/ClickHouse 把"列存+扇出"范式商品化；Dremel 论文成为 OLAP 架构引用的默认锚点（⚠️）。
- SQL:2023 属性图+嵌套讨论中 Dremel 展平语义被再次点名（⚠️）。
- 2024–2026：向量列与 JSON 类型进入 BigQuery，嵌套模型与半结构化路线合流——Dremel 当年"repeated field"的直觉被行业追认（⚠️ 判断）。
