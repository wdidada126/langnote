## 一句话总结
PolySI 是一个"只看输入输出就能审讯数据库"的工具：不管数据库内部多复杂，只要在它外面跑一批事务、记录客户端观察到的执行历史，就能判断这个声称提供快照隔离（SI）的数据库有没有偷偷违反 SI，违反了还能给出人能看懂的反例。

## 0. 给新手的阅读前置（背景知识地图）

### 0.1 这个子方向在解决什么大问题
数据库的隔离级别决定并发事务彼此"能看到什么"。可串行化（serializable）最安全但性能代价大；快照隔离（Snapshot Isolation, SI）是一种流行的折中：每个事务在一致的快照上读、提交时检查写写冲突，既躲开了可串行化的部分性能惩罚，又防住了脏读、丢失更新等多种异常。问题是：云数据库厂商声称提供 SI，实际上有没有bug？ 需要独立的"检查器"来验收。

### 0.2 为什么难
- 生产级数据库内部复杂且往往不可获取（闭源云服务），只能黑盒测试；
- 检查本质是"给观测到的执行历史找一种合法解释"，是一个组合搜索问题（判定可串行化相关的历史性质是 NP 完全级别的 🔧），暴力搜索不可行；
- 真实工作负载的历史动辄成千上万事务，SMT 求解器容易被约束规模拖垮；
- 检出违例还不够：反例必须人能看懂，否则没法定位原因。

### 0.3 主流解法一览
| 路线 | 直觉 | 代表 |
|------|------|------|
| 白盒/内部测试 | 深入数据库代码或协议做模型检查 | 需要源码，覆盖面受限 |
| 预言/统计式黑盒测试 | 构造特殊事务 + oracle 判断异常 | 如 Detecting Isolation Bugs via Transaction Oracle Construction（本仓库收录） |
| 图刻画 + SMT 求解 | 把"历史是否满足 SI"编码成约束交给求解器 | Cobra 系工作 🔧；PolySI（本文） |
| Jepsen 类工程化探测 | 分布式系统一致性探测的工程实践 | Jepsen（口径偏工程报告） |

### 0.4 三个关键名词的直觉解释
- 快照隔离（SI）：事务读的是"开事务那一刻拍下的照片"，写提交时若别人已经改过同一行则自己回滚。它挡住了一堆异常，但防不住 write skew（写偏斜）这类 anomaly——这正是检查器要抓的对象之一。
- 黑盒检查（black-box checking）：不打开数据库引擎，只在客户端执行事务、收集各客户端观察到的读写历史，然后判断"是否存在一种满足 SI 的执行能解释这些观察"。
- 广义多边形图（generalized polygon graph）：一种描述历史中"读写先后约束"的图结构；SI 成立当且仅当图中不存在某种坏环。PolySI 基于新的刻画，并证明其健全性与完备性（不冤枉好人、不放过坏人）。

## 1. 问题背景与动机

### 1.1 前人工作简述
- 隔离级别理论与实践（ANSI SQL 隔离级别、SI 的形式化刻画）已发展数十年；
- 近年出现了一批一致性/隔离性黑盒检查工具，普遍把问题交给 SMT 求解器，配合图论刻画（多边形图一类）缩小搜索空间 🔧；
- PolySI 团队之前有检查器工作的积累（通讯作者组在一致性验证方向持续产出 🔧）。

### 1.2 前人的缺陷 / 未解决问题（据摘要归纳）
1. 现实打脸：近期在声称提供 SI 的生产级云数据库中确实发现了 SI 异常——说明"厂商说有 SI"不等于"真有 SI"，需要可用的独立验收工具；
2. 已有黑盒检查器效率不足：在大规模工作负载上跑不动或太慢，难以支撑真实的云数据库验收；
3. 可理解性欠缺：检出违例后缺乏可理解的反例，难以定位根因；
4. 内部不可见：生产云数据库内部复杂且往往不可获取，凡是依赖白盒信息的方法都不可用。

## 2. 核心方法

### 2.1 最直观类比
把数据库想象成一家只接受点单、不接受参观的餐厅。PolySI 的做法是：派一批"侦探顾客"（客户端工作负载）同时去点单（执行事务），各自记录上菜顺序和菜品内容（执行历史）；回家后用一套严格的账本规则（广义多边形图刻画）核对：能不能找到一种后厨操作顺序，既符合所有人看到的菜，又满足 SI 的规矩？ 找不到 ⇒ 厨房（数据库）作弊了，而且账本能指出是哪几笔单子对不上（可理解反例）。

### 2.2 具体做法（输入 → 关键操作 → 输出）
- 输入：客户端采集到的执行历史（各事务的读写集合与观察值）；
- 关键操作：
  1. 用广义多边形图对 SI 做新刻画，把"历史满足 SI"转化为图上无坏环的判定；
  2. 将该判定编码为 SMT 约束，采用 GP 的紧凑约束编码压缩约束规模；
  3. 施加领域特定的约束剪枝优化，提前排除不可能的分支，加速求解；
- 输出：SI 成立与否；若违例，给出可理解的反例（哪几个事务构成违反 SI 的证据链）。

### 2.3 形式化要点
- 论文证明了其 SI 刻画的健全性与完备性：检查器说"合规"则历史确实满足 SI；说"违规"则确实存在可展示的违例 🔧（证明细节见原文 §3–§4）。
- 与既有 polygon-graph 刻画的关系（是推广/泛化）🔧——"generalized"一词来自摘要，具体推广点查原文。

### 2.4 理论性质 / 保证
健全 + 完备（上述）；工程上通过紧凑编码与剪枝实现可扩展性（摘要称可扩展到大规模工作负载）。

## 4. 实验结论（概览）
- 评估对象：三个生产云数据库 + 已知异常基准 + 广泛的工作负载；
- 核心结论（摘要明示）：
  1. 成功复现全部 2477 个已知 SI 异常（数字来自摘要，直接可信）；
  2. 在三个生产云数据库中检测到新的 SI 违例并识别了其原因；
  3. 在广泛工作负载下优于最先进的黑盒检查器，且可扩展到大规模工作负载；
- 🔧 精确数字（吞吐/求解时间对比、各云数据库名称与违例明细）查原文 §5 后补。
