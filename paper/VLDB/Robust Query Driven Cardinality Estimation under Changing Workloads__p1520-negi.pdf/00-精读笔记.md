## 一句话总结
针对"查询驱动"的基数估计模型在负载/数据漂移时会突然变很差、难以上线的问题，提出两种加固手段——训练时对未见表/列特征做随机掩码（让模型更依赖稳健的 DBMS 统计特征）+ 引入 join bitmaps 让采样特征在 join 间保持一致——使模型在漂移下泛化大幅变好：仅用 4 万条小查询训练的模型能泛化到 16 表规模的 Join Order Benchmark，比 PostgreSQL 快 2 倍，且最坏也不比 PostgreSQL 差。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：基数估计（cardinality estimation）= 估一个查询会返回多少行，是优化器选执行计划的核心。查询驱动的模型从历史查询日志里学，轻量、快、好适配任意查询；但它怕"漂移"——查询模式或底层数据变了，模型就可能崩。
- 为什么难：真实系统里负载和数据一直在变；标准查询驱动模型一到未见过的表/列或数据更新就不可预测地变差，导致"比不学还糟"，所以难部署。
- 几类主流解法：

| 路线 | 代表 | 直觉 |
|------|------|------|
| 数据驱动学习 | DeepDB | 从数据分布学，不依赖查询历史 |
| 查询驱动学习 | MSCN、Quicksel、本文 | 从查询日志学，轻量但怕漂移 |
| 本文加固 | 特征掩码 + join bitmaps | 在查询驱动框架上做鲁棒化改造 |

- 本文属哪类：查询驱动学习范式下的"鲁棒化"改进，而非换范式。
- 关键名词直觉：
  - workload drift（负载漂移）：查询模式或数据分布发生变化，使在历史负载上训好的模型失效。
  - feature masking（特征掩码）：训练时随机遮掉部分表/列特征，逼模型在"信息缺失"时仍能估，从而更依赖稳健特征。
  - join bitmaps：把基于采样得到的特征在 join 上保持一致（借 sideways information passing 思想），解决跨表采样特征不一致问题。

## 1. 问题背景与动机
- 前人工作简述：查询驱动模型（如 MSCN 等）轻量、快、易适配；但部署难，因为漂移下表现不可预测。
- 前人缺陷/未解决问题（逐条）：
  1. 漂移下不可预测变差：模型在未见表/列或数据变化时可能远差于朴素基线，无法放心上线。
  2. 对缺失查询信息脆弱：一旦查询涉及训练时没见过的表/列，特征不完整就崩。
  3. 跨 join 的采样特征不一致：基于采样的特征在 join 上难以保持一致，影响多表查询估计。

## 2. 核心方法
- 最直观类比：像训练一个"即使蒙住部分考卷信息也能答对"的学生（掩码），并且让他在做连表题时把各表的抽样笔记对齐成同一套（join bitmaps），这样换套题也不慌。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 输入：历史查询日志（含真实基数）。
  2. 特征掩码训练：在涉及未见表/列的查询上，随机遮掉部分表/列特征，迫使模型更多依赖"基于最新 DBMS 统计、在漂移时仍有用的稳健特征"。
  3. join bitmaps：用 sideways information passing 思想，把基于采样的特征扩展到 join 上并保持跨表一致。
  4. 适配数据更新：上述两点都可扩展到处理数据更新场景。
  - 输出：在漂移/更新下仍稳健的查询驱动基数估计模型。
- 形式化要点：核心是对"查询表示"和"神经网络训练"两处做改造；超参数含掩码比例、采样规模（🔧 以正文为准）。
- 理论性质/保证：无形式化保证；靠实验证明跨负载/跨库泛化显著更好，且最坏不差于 PostgreSQL。

## 4. 实验结论（概览）
- 对比基线：标准查询驱动模型、PostgreSQL 内建估计。
- 数据集/负载：JOBLight-train（4 万条、最多 3 表合成查询）、Join Order Benchmark（JOB，最多 16 表）等。
- 指标：跨负载/跨库泛化误差、端到端查询运行时间。
- 结论方向（摘要已核实数字）：
  - 在 JOBLight-train（4 万条、≤3 表）上训的模型，可泛化到 JOB（≤16 表），比 PostgreSQL 快 2×。
  - 即便在最难漂移场景，本文模型也从不超过 PostgreSQL，而标准查询驱动模型可能远差于 PostgreSQL。
  - 数据更新与其他负载上也有类似鲁棒性。
