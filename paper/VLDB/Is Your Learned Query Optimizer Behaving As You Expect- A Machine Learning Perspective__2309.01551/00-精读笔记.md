## 0. 给新手的阅读前置（背景知识地图）

**子方向解决什么大问题**：查询优化器决定 SQL 怎么执行（先连哪张表、用不用索引），选错计划查询可能慢百倍。近十年 ML 兴起后，出现了「学习型查询优化器」（LQO），用强化学习等代替传统动态规划来搜计划。但 LQO 论文的实验口径五花八门，究竟谁更强、和 PostgreSQL 比到底如何，缺少统一标尺。

**为什么难**：
- LQO 本质是 ML 系统，除了模型本身，还涉及训练数据怎么生成、训练/验证/测试怎么划分等一整条 ML 流水线，各家口径不一；
- 查询负载划分方式（哪些查询训练、哪些测试）会剧烈影响结论；
- 数据库社区的传统 benchmark（如 TPC 系列）并不天然等于 ML 意义上的合理 split。

**主流解法分类（简表）**：

| 类别 | 思路 | 代表 |
|------|------|------|
| 传统优化器 | 动态规划 + 基数/代价估计 | PostgreSQL 等 |
| 学习基数估计 | 用模型估中间结果行数 | 学习型 cardinality estimation 一族 |
| 学习代价模型 | 用模型估算子代价 | learned cost models |
| 端到端 LQO | RL 等直接选计划 | Balsa、Lero、Bao 类 |

**本文属哪类**：不是新优化器，而是**评测/基准工作**——把 LQO 当作标准 ML 流水线来审视和统一评测。

**关键名词直觉**：
- **LQO（learned query optimizer）**：用机器学习模型替代（或辅助）传统优化器做计划选择的系统；
- **QOP（query optimization problem）**：把「给查询选最优计划」形式化为优化问题，本文把它当作 ML 问题来拆解；
- **train/test split**：哪些查询给模型学、哪些查询拿来考试——划分方式直接决定「考试成绩」的可信度；
- **ML pipeline**：数据生成 → 特征化 → 训练 → 验证 → 评测的完整链路，任何一环不严谨都会美化结论。

## 1. 问题背景与动机

- 前人工作：LQO 的兴起既得益于深度学习的进步，也得益于把查询优化问题（QOP）直接表述成 ML 问题的「直白公式化」——常以强化学习取代动态规划。
- 前人缺陷 / 未解决问题（逐条，出自论文摘要）：
  1. 各 LQO 对「从查询生成训练数据」施加了各自的限制，互相不可比；
  2. 训练/验证划分做法随意（arbitrary），缺乏 ML 社区的规范；
  3. 评测往往在自愿挑选的 benchmark 查询子集上进行，容易挑有利负载；
  4. 除模型开发外的整条 ML 流水线都有很大改进空间，导致 LQO 的真实水平被高估。

## 2. 核心方法

**最直观类比**：像一个「考试委员会」发现各学校（LQO）都在自己出题自己改卷，于是重新命题、统一阅卷、统一划分数线，结果发现传统学校（PostgreSQL）的成绩反而更好。

**具体做法（输入→关键操作→输出）**：
1. **输入**：现有 LQO 系统 + 一组 benchmark 查询与数据库。
2. **关键操作**：
   - 提出一个新的**端到端基准评测框架**，把 LQO 评测的 ML 流水线标准化（数据生成、划分、训练、评测统一口径）；
   - 带读者逐阶段过一遍 ML pipeline 的每个数据科学环节，并针对 QOP 的特殊性给出 ML 视角的新洞见；
   - 在统一框架下对已有 LQO 做严格评测，比较其与 PostgreSQL 的表现。
3. **输出**：标准化的评测协议、可复现的对比结论与框架代码。

**理论性质**：以实证与评测方法学为主，无定理类保证（🔧）。

## 7. 2026 视角（🔧）
