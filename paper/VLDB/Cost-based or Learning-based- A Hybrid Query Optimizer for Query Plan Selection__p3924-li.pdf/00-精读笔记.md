## 一句话总结
HyperQO 不纠结「成本优化器好还是学习优化器好」，而是把两者「杂交」：用学习式方法先生成高价值的 hint（提示），再用成本式方法把 hint 补全成完整计划，最后用一个「带不确定性估计」的模型挑出最可能最快的计划——在真实数据集上把 PostgreSQL 的总延迟降 25%、尾延迟降 65%。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：查询优化器的任务是给一条 SQL 选「执行计划」（先 JOIN 哪两张表、走哪个索引等）。传统优化器按「代价模型」估算每个计划的成本来选最优；近年出现「学习式优化器」，从历史经验里学选计划。
- 为什么难：传统成本优化器对简单查询稳，但复杂查询的代价估算常失准；学习式优化器在「训练分布之外的动态负载」上会翻车。
- 几类主流解法：

| 路线 | 代表 | 思路 | 取舍 |
|------|------|------|------|
| 成本式（Cost-based） | 传统 optimizer | 用代价模型枚举选优 | 稳但复杂查询估不准 |
| 学习式（Learning-based） | 各类 learned optimizer | 从历史学选计划 | 复杂查询好，但换负载垮 |
| 混合式（本文） | HyperQO | 两者候选 + 不确定性选优 | 取长补短，更鲁棒 |

- 本文属哪一类：混合优化器（Hybrid Optimizer），把两类优化器各自生成候选计划再统一挑选。
- 关键名词直觉：
  - Plan（执行计划）：数据库实际执行 SQL 的「操作步骤单」，顺序不同性能差百倍。
  - Hint（提示）：给优化器的「建议」，如「先用表 A 和 B 做 JOIN」，缩小搜索空间。
  - 不确定性（Uncertainty）：模型对「这个计划的执行时间预测」有多不自信；越不自信越要保守。

## 1. 问题背景与动机
- 前人工作简述：传统成本优化器高效稳定但对复杂查询质量差；学习式优化器能学高质量计划，但在分布漂移的动态负载上表现差。
- 前人缺陷/未解决问题（逐条）：
  1. 单一优化器各有短板：成本式复杂查询差，学习式动态负载差。
  2. 如何生成「高质量候选计划」没有现成好办法。
  3. 如何从多个候选里挑最好的，缺一个能反映置信度的评估。

## 2. 核心方法
- 最直观类比：成本优化器像「按菜谱估时的老厨师」，学习优化器像「凭经验直觉的新厨师」；HyperQO 让新厨师先给个方向（hint），老厨师照着把整道菜做完，最后再由一位「知道自己对每道菜把握多大」的主管挑出最稳的出餐。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 基于 hint 的候选生成：学习式方法生成「高收益 hint」，成本式方法把 hint 补全成完整执行计划，作为候选集（两类优化器各贡献候选）。
  2. 基于不确定性的最优计划选择：一个模型预测每个候选的执行时间 + 不确定性（即对预测的置信度），用不确定性指导最终挑选。
  3. 输出：被选中的最优执行计划。
- 形式化要点：两大挑战对应两大贡献——hint 候选生成、不确定性选优；超参数以论文为准 🔧。
- 理论性质/保证：以实验为主，未提供形式化最优性保证。
