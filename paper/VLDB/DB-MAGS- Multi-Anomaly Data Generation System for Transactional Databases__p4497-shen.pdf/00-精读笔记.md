## 一句话总结
DB-MAGS 是一个给「事务型数据库」造异常数据的系统：单异常细分到 5 大类 18 小类并给出细粒度根因，多异常则区分「因果型」与「并发型」并枚举组合——弥补了已有基准「类型不全、根因粗糙、并发异常造假」的缺陷，让根因定位算法有更真实全面的评测数据。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：数据库在线跑着跑着会出「性能异常」（如锁冲突、资源瓶颈导致变慢甚至崩）。要找出根因（哪条 SQL、哪个资源），需要大量带标注的异常数据来训练和评测诊断算法（如 DBSherlock、BALANCE）。但公开真实异常数据集极少。
- 为什么难：真实异常类型多、根因细、且常多个异常同时发生（多异常），而多异常之间还有因果/并发关系，难以真实复现。
- 几类主流解法：

| 路线 | 代表 | 思路 | 取舍 |
|------|------|------|------|
| 单异常注入基准 | DBPA 等 | 造一些异常数据 | 类型覆盖窄、根因粗 |
| 多异常合成 | 直接拼单异常 | 简单但数据不真 | 非真实注入，不可信 |
| 统一多异常复现（本文） | DB-MAGS | 真实注入 + 细粒度根因 + 异常关系枚举 | 全面真实，但系统复杂 |

- 本文属哪一类：异常数据生成系统（benchmark/dataset generator），不是诊断算法本身。
- 关键名词直觉：
  - 性能异常（Performance Anomaly）：数据库变慢/出错的非预期状态，常由锁冲突、资源瓶颈等引发。
  - 根因（Root Cause）：导致异常的「那一条 SQL / 那一个资源」，诊断算法要找的就是它。
  - 多异常（Multi-anomaly）：多个异常同时出现，可分为「因果型」（一个引发另一个）与「并发型」（独立同时发生）。

## 1. 问题背景与动机
- 前人工作简述：DBPA 是唯一公开的事务库性能异常基准，但覆盖不全。
- 前人缺陷/未解决问题（逐条）：
  1. 异常类型覆盖不全（只有大类，缺细分小类）。
  2. 根因粒度粗（有的算法要定位到具体 SQL，老基准给不到）。
  3. 多异常只假设独立，忽略因果/并发依赖，且未真正注入运行中的库（而是合成单异常数据），不真实。

## 2. 核心方法
- 最直观类比：老基准像「只给孩子出『感冒/发烧』两类病、且分不清是病毒还是细菌的考卷」；DB-MAGS 像「一套覆盖几十种细分病症、还标注了是哪种细菌、并且能模拟『感冒引发肺炎』或『感冒+过敏同时犯』的完整病历生成器」。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 单异常分类：归纳影响性能异常的因素，选出 5 大类，再细分为 18 小类，便于对症下药。
  2. 多异常建模：把多异常之间的关系分为「因果型」与「并发型」，枚举不同组合。
  3. 真实注入：在运行中的事务库上真实注入异常，并附带细粒度根因（含具体根因 SQL）。
  4. 输出：统一、真实、全面且带细粒度根因的异常数据集。
- 形式化要点：两大贡献——统一/真实/全面的数据生成 + 细粒度根因；18 小类与因果/并发枚举是核心。超参数以论文为准 🔧。
- 理论性质/保证：以系统实现与实验为主，未提供形式化保证。

## 4. 实验结论（概览）
- 对比基线/对象：已有基准 DBPA（覆盖度、根因粒度、多异常真实性对比）。
- 指标：异常类型覆盖数、根因粒度、多异常组合多样性。
- 结论方向（经摘要核实）：DB-MAGS 在类型全面性、根因细粒度、多异常（因果/并发）真实复现上均显著优于已有基准。

- 数据库可观测性/根因诊断（AIOps for DB）是工业热点；高质量、带细粒度根因的多异常数据仍是稀缺资源，DB-MAGS 这类生成系统对评测 LLM/ML 诊断助手很重要。
