## 一句话总结
RCRank 把「慢查询根因诊断」当成多模态机器学习问题：同时吃下 SQL 语句、执行计划、执行日志、关键性能指标（KPI）四类信息，用自监督预训练对齐跨模态、用「根因自适应跨 Transformer」融合，再用「影响感知」目标同时识别并排序根因——让运维先修「提速最猛」的那个原因。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：云数据库里一条慢查询可能由多种原因造成（缺索引、统计信息旧、锁等待、资源争用……）。根因诊断能定位并指导修复，但「哪个原因最该先修」需要排序。
- **为什么难**：根因信号分散在 SQL 文本、执行计划、日志、KPI 等多种异构数据里，且「影响大小」难量化。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 规则/专家系统 | 传统 DBA 规则 | 人工经验 | 可解释但覆盖低 |
| 单模态 ML | 仅日志/仅 KPI | 一类信号 | 信息不全 |
| 多模态排序 | **RCRank** | 四类信号融合+影响排序 | 更准更细，复杂 |

- **本文属哪类**：多模态机器学习做根因识别+排序。
- **2-3 个必懂关键名词**：
  - **根因（root cause）**：导致查询变慢的可修复因素。
  - **执行计划（execution plan）**：数据库打算怎么跑这条 SQL 的步骤树。
  - **影响感知排序（impact-aware ranking）**：不只识别根因，还按「修了能提速多少」排序。

## 1. 问题背景与动机
- 前人工作简述：慢查询影响增大，根因诊断对检测与修复不可或缺。
- 前人缺陷/未解决问题（逐条）：
  1. **只识别不排序**：旧方法难区分「哪个根因提速效果最大」，修复效率受影响。
  2. **模态利用不足**：多数方法没充分利用 SQL/计划/日志/KPI 的多模态信息。
  3. **跨模态对齐弱**：异构信号间难以有效融合。

## 2. 核心方法
- **最直观类比**：把慢查询当「病人」，SQL 是主诉、执行计划是检查单、日志是化验、KPI 是体征；RCRank 像多位专科医生会诊后，不仅列出可疑病因，还按「先治哪个最救命」排好序。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：SQL 语句 + 执行计划 + 执行日志 + KPI 四类多模态信息。
  2. **自监督预训练**：增强跨模态对齐与任务相关性，得到表达力强的嵌入。
  3. **根因自适应跨 Transformer**：自适应融合不同特征的多模态信号。
  4. **影响感知训练**：统一模型同时识别并排序根因。
  5. **输出**：根因类型 + 按潜在提速效果排序的清单。
- **形式化要点**：核心是多模态融合 + impact-aware 目标；超参数为融合结构与排序损失权重（🔧 见论文）。
- **理论性质/保证**：实证优于 SOTA；无形式化保证。
