## 二、问题史：流/批 API 分裂的根源

- 2013–2015 生态：Storm（纯流微处理）、Spark（微批）、MillWheel/Apache Flink（异步）各说各话——正确性/延迟/成本三角（✅ 论文 §1 三维图）无人同时给答案。
- 关键提问：**用户真正要选的不是"流还是批"，而是"何时算完整、以何代价"**（✅ 论文革命句）。

## 三、模型核心：四轴选择空间（✅ §2–§4 主题）

1. **事件时间 vs 处理时间**（WHEN 的定义权归数据）（✅）。
2. **窗口**：fixed/sliding/session/global——按键开窗（✅）。
3. **触发**：watermark 过界/定时/数据量，**允许对同一窗口多次发射（retrigger）**（✅ 招牌——"部分结果流"合法化）。
4. **组合/合并**：合并策略（discard/final/accumulate）+ 再触发修正=迟到数据语义解药（✅）。
- 正交组合⇒同一程序可编译为批（全等 watermark 假设）或流（增量）——**模型统一而非运行时统一**（✅ 论断）。
- Exactly-once 继承 MillWheel 配方（读位+状态原子提交 ✅）。
- 可加性分类（algebraic/deduplicative…）给"增量维护成本"排序（✅ 大意）。

## 四、评测与运营（✅ 定性）

- Google 内部大规模生产（搜索索引/计费/广告）验证"一套模型跑批流"（✅ 案例叙事 ⚠️ 数字）。
- 论文坦承：模型不消除"成本意识"，参数（允许迟到、触发频率）仍是工程判断（✅）。

## 五、批判读法

- 与 SQL 标准的流语义之争（流式扩展的窗口语法五花八门）：Dataflow 四轴是**实现先行、标准追认**的典型（⚠️ 判断）。
- "正确性-延迟-成本"三角优雅但不可微分：实践中三者由产品默认值决定，模型只是解释框架（⚠️ 评价）。
- Beam 落地后"一次编写到处运行"兑现度存疑（Runner 能力参差，Flink/Spark 语义偏差 ⚠️ 社区现实）——**模型是最大公约数，也是被最小公约数绑架**（⚠️ 判断）。
- 与 Naiad [[naiad_2013_sosp]]（已建）对读成双峰：Naiad 给理论（及时数据流），Dataflow 给词汇表（用户可选维度）——流处理 2015 年的两本教科书（✅ 教学判断）。

## 五、🔧 本地微实验（非本书引擎行为）

1. **四维矩阵**：用文件模拟（事件时间戳乱序流入），分别配置"处理时间窗 vs 事件时间窗+watermark"，对比窗口计数误差。
2. **再触发修正**：同一窗口先发射部分和、迟到事件到达后发射"修正增量"，下游做合并（accumulate）还原终值。
3. **合并策略表**：sum/max/去重计数三类按可加性分类，模拟"仅追加存储"下各自的修正成本。
4. **Session 窗口**：gap 合并算法实现，观察乱序对会话边界的影响。
5. **批流等价**：同一聚合分别以"全量批"与"微增量+终触发"跑，验证结果一致性与总开销差。

## 九、最新演进与工业实践

- Beam 成事实标准词汇（Flink 2.x/Spark/云厂商 API 全部沿用四轴术语 ✅）。
- 湖仓流式化（Flink CDC→Iceberg 提交=再触发的文件化 ⚠️）与特征平台（事件时间=特征穿越解药）是模型红利主战场。
- 2024–2026：LLM 数据管道（乱序 token 日志的窗口化聚合）重新消费本文词汇——"四轴"成为无 SQL 背景工程师也能入流的最低语言门槛（⚠️ 判断）。
