## 一句话总结
LSM 键值存储放到「NVMe + SSD + HDD 混合硬盘架」上时，把哪个文件放哪块盘没有万能答案——Keigo 作为中间件，按每块盘的并发度、带宽、容量动态安排文件布局，还加了持久只读缓存和 I/O 分流，让 RocksDB 这类生产级存储在重读负载下快 18 倍、重写下快 4 倍。

## 0. 给新手的阅读前置（背景知识地图）

这个子方向解决什么大问题？
LSM-tree（Log-Structured Merge tree）是 RocksDB、LevelDB 等生产级 KV 存储的骨架：写入先进内存与 WAL，攒成不可变文件（SSTable）逐层向下压缩（compaction）。当底层存储不再是单块盘、而是「快速 NVMe + 大容量 SSD/HDD」的层次结构时，文件该放在哪一层直接决定读写吞吐。

为什么难？
- 没有万能布局：写密集负载希望写吞吐高，读密集负载希望热数据都在快盘上；同一个布局不可能对所有负载都最优。
- 并发度差异被忽视：不同设备不仅带宽/延迟不同，可并行处理请求的深度（queue depth、通道数）也不同，传统放置策略只看带宽/容量。
- 改造成本高：要让每个 KV 存储自己支持异构放置，需要侵入式改造，且难以适应负载变化。

主流解法（表格）
| 路线 | 思路 | 局限 |
|------|------|------|
| KV 存储内建分层（RocksDB 多级路径） | 手动指定各级目录所在盘 | 需人工调优，不懂负载/并发 |
| 专用异构 KV 系统 | 为特定设备组合重写存储引擎 | 不可移植，生态割裂 |
| 通用文件系统/卷管理 | 对 KV 无感知地条带化 | 不理解 LSM 文件语义，放置盲目 |
| 中间件式协同设计（本文） | 对生产级 LSM 透明插入一层并发/负载感知放置 | 中间件自身的元数据开销需控制 |

关键名词直觉解释
- LSM-tree / compaction：写优化结构，靠后台把文件层层合并；合并会产生大量临时 I/O，是性能干扰的主要来源。
- 非易失（Non-Volatile）存储层次：断电不丢数据的多种介质堆叠（NVMe SSD、SATA SSD、HDD 等），各自带宽、延迟、并发能力差异巨大。
- 并发感知（concurrency-aware）：不只问"这块盘快不快"，还问"它能同时伺候几个请求"——高并发设备适合放需要并行读的文件。
- I/O differentiation（I/O 分流）：识别当前 I/O 是"前台用户读"还是"后台 compaction"，给不同来源的请求不同待遇（放不同盘/不同优先级）。

## 1. 问题背景与动机
生产级 LSM KVS（RocksDB、LevelDB、Speedb）广泛部署，但面对异构存储层次时的既有做法存在以下缺陷：

1. 一刀切放置失效：不存在对所有负载都最优的数据放置方案——写多与读多的负载对"哪类文件放快盘"的要求完全相反（这是 Keigo 的核心观察）。
2. 现有分层机制不理解并发：KV 存储自带的 multi-path 功能只按静态层级/容量划分，未利用各设备的并发深度差异，也未随负载动态调整。
3. 专用系统不可移植：为特定设备组合定制的 LSM 系统无法直接服务已部署在 RocksDB 等引擎上的海量业务。
4. 依赖昂贵 profiling：一些自适应方案需要长时间的负载画像（profiling），在负载漂移后失效。
5. 缓存不持久：重启后读缓存全冷，热身期读性能骤降。

## 2. 核心方法
最直观类比：把餐厅厨房想成 LSM 引擎，备菜间/冰箱/仓库是不同速度的存储。Keigo 是一个懂行的"库房主管"：根据每样食材（文件）是用于即时出餐（读热）还是批量腌制（compaction 产物），以及冰箱门能同时开几扇（设备并发度），动态决定放哪，并给点单客人（前台读）永远优先于内部搬运工（后台 compaction）。

具体做法（输入 → 关键操作 → 输出）
- 输入：任意支持插件的 LSM KVS（RocksDB/LevelDB/Speedb）+ 由 NVMe/SSD/HDD 等组成的存储层次。
- 关键操作（三大技术）：
  1. 并发感知数据放置（concurrency-aware data placement）：为每个设备建模带宽、容量与并发能力，按文件的读写特征与负载状态决定文件落在哪块设备（并在负载变化时重评估/迁移 🔧 迁移策略细节查论文）；
  2. 持久化只读缓存（persistent read-only caching）：用非易失设备缓存只读数据（过滤块/热 SSTable 🔧 具体缓存对象查论文），重启不失效，消除冷启动；
  3. 基于上下文的 I/O 分流（context-based I/O differentiation）：区分 I/O 来源（用户前台读 vs 后台 flush/compaction），将不同上下文的 I/O 路由到最合适的设备与并发队列。
- 输出：一个可移植的存储中间件，对上层生产级 LSM 透明增强，使异构硬件的整体吞吐显著提升。

形式化要点：设备能力模型（带宽/并发/容量三元组）+ 放置决策函数（🔧 具体建模与决策公式查论文方法节）。

理论性质/保证：无理论定理；为系统型贡献，提供正确性/兼容性论证（对上层引擎 API 兼容）。

## 7. 2026 视角（🔧）
- 混合闪存/分层存储在云厂商与本地高性能 KV 部署中仍是刚需，"存储介质多样化"（QLC SSD、ZNS SSD、SMR HDD、CXL 内存池）让并发/带宽异构性愈发显著，Keigo 式"放置中间件"思路价值上升。
- ZNS（zoned namespace）与 F2/FASTER 类写优化 KV（本仓库相关条目）是同期活跃方向；学术与工业界均在探索"KV 引擎 ↔ 新介质"协同设计。
- RocksDB 生态内 Speedb、以及各类 compaction 调度/分层优化（CaaS-LSM、ELMo-Tune-V2 等，见本仓库）持续演进；自动调优（含 LLM 辅助调参）与设备感知放置正在合流。
