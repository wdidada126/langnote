## 一句话总结
EET 在「查询级」操纵之外，提出更细的「表达式级」操纵：对一条 SQL 里的表达式做「语义保持的等价改写」，改写前后结果必须一致——只要数据库对原查询和改写后查询给出不同结果，就说明有逻辑 bug。它对任意查询都适用，在 MySQL/PostgreSQL/SQLite/ClickHouse/TiDB 上共找到 66 个独立 bug（其中 35 个逻辑 bug）。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：数据库「逻辑 bug」指数据库算出了错误的结果集（不是崩，而是悄悄给错答案）。自动找出它需要一个「预言（oracle）」来判断对错。EET 给出了一个通用、强力的预言。
- 为什么难：以往方法在「整条查询」层面做等价变换，受限于能生成的查询模式，复杂语义覆盖不到；且很多逻辑 bug 藏在特定表达式里。
- 几类主流解法：

| 路线 | 代表 | 思路 | 取舍 |
|------|------|------|------|
| 查询级等价变换 | 早期 metamorphic 测试 | 整句改写后比对 | 受查询模式限制 |
| 透视查询合成 | SQLancer/PQS | 保证某行必被取回 | 通用但构造受限 |
| 表达式级等价变换（本文） | EET | 表达式级保语义改写 | 对任意查询适用、更细 |

- 本文属哪一类：基于「等价表达式变换（Equivalent Expression Transformation）」的 DBMS 测试预言。
- 关键名词直觉：
  - 逻辑 bug（Logic Bug）：数据库没崩、但返回了错误结果（如漏行、算错）。
  - 等价表达式（Equivalent Expression）：数学/语义上和原表达完全一样的另一种写法（如 `a+b` 与 `b+a`），对同样数据必得同样结果。
  - 表达式级变换：只改 SQL 里某个子表达式，而非整条查询——因此不受整句模式限制，能触达更细的语义。

## 1. 问题背景与动机
- 前人工作简述：既有方法通过操纵查询、检查结果是否符合预期来检测逻辑 bug，但只在查询级操纵，无法处理复杂查询语义，被迫限制生成查询的模式，降低测试效力。
- 前人缺陷/未解决问题（逐条）：
  1. 查询级操纵受模式限制，覆盖不到复杂语义。
  2. 难以对任意查询通用地产生「可验证对错」的用例。

## 2. 核心方法
- 最直观类比：过去像是「整道菜重写后比对口味」，只能做几种固定菜；EET 像是「只替换菜里的某一种调料为等价调料（如糖换成等甜度的代糖），整道菜味道必须不变」——哪个数据库做出来的味道变了，就是它处理这种调料有 bug。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 表达式级操纵：对查询中的表达式做语义保持的等价变换（与查询整体模式无关）。
  2. 预言：原查询与变换后查询必须返回相同结果；不同 → 逻辑 bug。
  3. 实现：构建在 SQLsmith 之上，随机生成 SQL 并对其表达式做 EET。
  4. 输出：触发的崩溃/逻辑 bug 及复现查询。
- 形式化要点：核心论点——「语义保持地改写表达式，也保持整条查询语义、且独立于查询模式」；支持任意查询。超参数以论文为准 🔧。
- 理论性质/保证：给出 EET 的通用性与正确性论证（变换保语义即结果一致）。
