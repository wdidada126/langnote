## 二、问题史：为什么不用 CORBA 锁 / 共识库裸用

- 分布式系统的锁需求分两类：**细粒度高频**（DB 行锁，不该走远端服务）与**粗粒度低频**（选主、成员、命名）；Chubby 只做后者（✅ 原文立场）。
- 2003 年前夜：共识（Paxos 1998 ⚠️）工程化成本高；用户手写脑裂补丁灾难频出——Google 的答案是把共识封装成**带文件语义的锁服务**（✅ 动机归纳）。
- 设计口号：可用性优先于性能，锁持有以秒级租约计（✅）。

## 三、接口：一个小型分布式文件系统

- 路径 /cubby/...；节点 = 文件 = 锁；**内容 ≤ 64KB**（✅ 上限硬写），写者持锁，读者随时可读。
- Client 库维护本地缓存 + **租约/keep-alive**（✅）。
- 四种事件（✅ 原文枚举）：lock acquired/released、file content changed、disassociated（client 掉锁）。
- 锁语义：排他写锁、共享读锁；写锁可升级为"写后仍持读"（⚠️ 细节凭记忆）。

## 四、实现：一个 server 是主，其余是副本

### 4.1 共识层

- 内部跑 **Paxos 家族变体**做日志复制；主副本（master replica）处理读写，写日志过半即 ack（✅ 论文表述粒度）。
- 一致性检查点：状态快照 + 日志（⚠️ 细节凭记忆）。

### 4.2 租约与掉锁

- Client 与 server 相互 keep-alive：**client 租约过期自动释放锁**（防死锁的根基）；server 组租约过期则副本自杀退出——保证同一时刻至多一个主服务锁表（✅）。
- 双租约设计是本文最常考考点：**client 租约管正确性，server 租约管活性**（⚠️ 教学口径）。

### 4.3 失败模型与可用性数字

- 论文报告单 cell 约 5 副本跨多机架；年宕机分钟级（✅ 量级记忆 ⚠️ 分钟数凭原文表）。
- "可用性事故大多来自计划内变更/磁盘老化"（⚠️ 论文 §7 运维教训方向）。

## 五、经验与教训（✅ 论文 §7 主题）

- 锁内容 64KB 限制逼出"小指针+大存储分离"模式（Bigtable 把 schema 放 GFS、Chubby 只放指针 ✅）。
- 客户端滥用：拿 Chubby 当消息总线/细粒度锁 → 性能塌方；教训是**接口设计要限制误用面**（⚠️ 归纳）。
- DNS 缓存、防火墙等环境坑反复出现（⚠️ 论文吐槽清单）。

## 六、批判读法

- 锁语义≠事务：Chubby 不提供跨锁原子性，组合用它的人自己踩死锁（⚠️）。
- 租约的"时钟误差预算"被一笔带过：网络分区下双主风险由副本自杀兜底，但脑裂窗口在真实事故史里有账（ZooKeeper 后来用更严的协议链 ⚠️ 对照）。
- 闭源且与 Google 运维耦合——开源替代 ZooKeeper 明确以"Chubby 语义但更快更严共识"为卖点（✅ 对照判断）。
- "loosely-coupled"标题的哲学：不承诺低延迟、不承诺高吞吐——任何拿它做热路径的设计都是误用（✅ 原文立场）。

## 七、🔧 本地微实验（非本书引擎行为）

1. **租约锁**：JSON 文件存锁状态+过期时间戳，两进程抢锁，持锁者 SIGSTOP 模拟卡死，观察对方在租约过期后接管——理解防死锁。
2. **watch 事件**：轮询内容版本号 vs "通知"回调，模拟 disassociated 事件触达。
3. **半数 ack**：5 个本地 socket 各带随机延迟，主写需 ≥3 ack，测提交延迟与 kill 1 副本的影响。
4. **副本自杀**：cell 内心跳断链时让"主"自我降级，验证无双主。
5. **64KB 指针模式**：大配置放"GFS 式文件"，锁节点只存路径，对比全量塞内容的写放大。

## 十、最新演进与工业实践

- Google 内部 Chubby 服役至今并被持续现代化（大容量、跨 region 协调），公开论文仅 OSDI'03 一篇（⚠️）。
- 行业事实标准迁移到 etcd/ZooKeeper/Consul：ZAB/Raft 替代手写共识，watch 语义继承 Chubby（⚠️）。
- Kubernetes 控制面 = etcd 上的"Chubby 化"命名+锁+成员三合一（⚠️ 映射判断）。
- 2024–2026：协调服务进一步下沉为平台默认件；Chubby 论文的教学价值集中在双租约与 64KB 哲学（⚠️ 判断）。
