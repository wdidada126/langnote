# Large-scale Incremental Processing Using Distributed Transactions and Notifications (Percolator) — 精读笔记

> OSDI 2010 · Peng & Dabrowski（Google，⚠️ 作者全名以原文为准）
> 三态标注：✅ 论文硬写事实 / ⚠️ 记忆或二手归纳 / 🔧 本地可复演实验

## 一、基本信息

| 项 | 内容 |
|---|---|
| 会议 | OSDI 2010，通称 Percolator |
| 定位 | 在 Bigtable（行内原子）之上搭出**跨行事务 + 增量计算**的搜索索引存储层 |
| 血统 | BigTable [[bigtable_2006_osdi]]（已建）之上的事务封装；Google 索引流的实际脊梁（✅ 论文自述规模） |

## 二、问题史：索引构建为什么等不起批处理

- 旧模式：MapReduce 全量批 + 增量段合并（⚠️ 大索引更新延迟小时级；论文 §1 叙事）——新网页可见性受批周期支配。
- Bigtable 只有行内原子，索引需要"多文档多 cell 一致更新 + 读己之写"——于是需要**分布式事务层**（✅ 动机）。
- 目标：以行级并发、快照读、严格两阶段锁（S2PL）+ 乐观提交支撑持续增量写，同时保留 MapReduce 做初始批量装载（✅）。

## 三、数据模型：把状态机写进 Bigtable 列

### 3.1 单行多 cell 的事务状态布局（✅ 原文列族语义）

| 列 | 含义 |
|---|---|
| Data | 业务值 + 提交时间戳（读时可见） |
| Lock | 互斥锁，持锁者身份 = 事务协调器地址 |
| Write | 该 cell 是否被未决事务写过的标记（值为该事务 start ts） |
| Ack | 已回滚/提交确认集合（处理"提交中崩溃"的幂等） |

### 3.2 时间戳 oracle

- 中心化的单调时间戳分配服务（Tso），兼当冲突序（✅ 论文 §3.1：可容忍降级用 Bigtable lease）。

## 四、事务协议

### 4.1 两阶段 + 乐观提交

1. **Start**：从 oracle 取 start ts；读=对每组 cell 读 **<=start ts 的最新提交版本**，并在首读处写 Lock（primary/secondaries 区分，✅）。
2. **Commit 第一阶段**：为所有写 cell 写 Write 列（带 prepare=commit candidate ts），其中 **primary 是最后一步**（✅）。
3. **Commit 第二阶段**：把 primary 的 commit ts 写进 Data；secondaries 异步补写（✅ 关键创新：提交延迟由 primary 一个写决定）。
4. 读方发现未决锁：try_to_commit 帮助推进（乐观恢复），回滚用 Rollback 标记（✅）。

### 4.2 隔离级别

- 读：**快照隔离**（start ts）+ 写后读用自身写版本（✅）。
- 写-写：S2PL + "last commit wins 变体"，写冲突时读提交时间戳决定回滚（✅ 大意 ⚠️ 细节）。

### 4.3 观察者（Observations）= 增量计算引擎

- 注册"cell 组变化 → 派生计算写回另一 cell"的触发器（✅）：爬虫状态、PageRank 式多轮收敛、查询改写链都写成观察者 DAG（⚠️ 论文以爬虫例子为主）。
- 级联提交天然形成依赖传播，失败重跑用幂等 cell 状态解决（✅ 大意）。

## 五、评测（✅ 定性）

- 论文自述：初始索引在少量集群日内由 MapReduce 装载，日常增量以事务+观察者维护；吞吐数字以"每秒数十万更新"量级出现（⚠️ 具体曲线凭图表）。
- 与"重做全量批"对比的更新可见性从小时级降到秒级（✅ 核心卖点）。

## 六、批判读法

- **中心化 oracle 是标度天花板**：跨数据中心时延下 commit ts 分配变瓶颈——这正是 Spanner 用 TrueTime 重做一遍的原因（✅ 对照 [[spanner_2012_osdi]]）。
- S2PL + 每 cell 多列读写在 Bigtable 上的开销：论文不讳言"跨行事务性能是行内事务的几分之一"（⚠️ 量级凭记忆）。
- 观察者模型把"流计算"塞进"存储+触发"——概念优雅，但调试/反压语义贫弱，工业流计算（Millau/Flume ⚠️ 未建）走了独立路线。
- 论文是系统散文，伪代码极少；TiKV/CockroachDB 诸家自述受其启发但协议细节已换（Percolator 事务模型在 TiDB 白皮书里是"乐观+2PC"改造版 ⚠️）。

## 七、🔧 本地微实验（非本书引擎行为）

1. **迷你 Bigtable**：dict[(row,col,ts)]=value，实现"读 <=start ts 最新版"。
2. **primary-last commit**：JSONL 日志模拟两阶段：写 secondaries 的 Write→最后写 primary Data→崩溃注入在 primary 前，观察读方 try_to_commit 恢复。
3. **锁冲突回滚**：两线程对同行抢 Lock，败者按时间戳规则回滚重试。
4. **观察者链**：cellA 变更触发 B、B 触发 C，统计级联提交次数与幂等重放。
5. **oracle 瓶颈**：中心单线程发 ts vs 本地时钟混合，测跨"机房"（sleep 注入）提交延迟。

## 十、最新演进与工业实践

- Google 索引层后续迁移到更专用栈（⚠️ 内部演化未公开），Percolator 成为"事务层论文"的常引原型。
- TiDB 把 Percolator 模型产品化（client 侧 2PC + TSO 集群化）——单 oracle 问题以"TSO 多活+本地缓存"缓解（⚠️）。
- 增量计算文艺复兴（Materialize/Differential Dataflow、Databricks DLT）与"观察者"思想跨时空呼应（⚠️ 判断）。
- 2024–2026：湖仓提交协议（Iceberg REST Catalog CAS、Delta OCC）仍在解 Percolator 式"元数据原子可见性"，问题换了皮没换骨（⚠️ 判断）。
