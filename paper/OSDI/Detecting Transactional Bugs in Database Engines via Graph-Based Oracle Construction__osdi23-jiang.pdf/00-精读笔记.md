## 一句话总结
TxCheck 用「语句依赖图」描述事务里 SQL 语句之间的细粒度依赖，再用 SQL 级插桩捕获这些依赖，最后据此构造「语义等价的测试用例」当预言——从而能处理真实查询里常见的复杂操作和谓词，在 TiDB/MySQL/MariaDB 上找到 56 个独立事务 bug（52 个被确认、18 个已修）。

## 0. 给新手的阅读前置（背景知识地图）
- 子方向解决什么大问题：事务 bug 指 DBMS 的事务机制实现有缺陷，导致本该 ACID 的行为出错（如并发下返回错误结果、破坏隔离）。自动找出它们需要「预言」判断事务执行是否正确。
- 为什么难：已有方法（如 ELLE）只用简单操作模式（如往 list 追加常量），且普遍不支持 WHERE 这类谓词，漏掉大量真实 bug；也常只测隔离级别，忽略与隔离级别无关的事务 bug。
- 几类主流解法：

| 路线 | 代表 | 思路 | 取舍 |
|------|------|------|------|
| 历史依赖图 | ELLE | 把执行历史建成依赖图查违例 | 只支持简单操作、不支持谓词 |
| 隔离预言构建 | Troc | 解耦事务成独立语句 | 聚焦隔离级别 |
| 图式预言构建（本文） | TxCheck | 语句依赖图 + 插桩构造等价用例 | 支持复杂操作/谓词 |

- 本文属哪一类：基于「图式事务预言构建（Graph-Based Oracle Construction）」的事务 bug 检测。
- 关键名词直觉：
  - 事务 bug（Transactional Bug）：事务机制实现错误，可导致静默错误（更危险）。
  - 语句依赖图（Statement-Dependency Graph）：把事务里各 SQL 之间的关系（读写依赖等）画成图。
  - 语义等价测试用例：由原用例经变换得到的、应当产生相同结果的另一组用例；结果不同即 bug。

## 1. 问题背景与动机
- 前人工作简述：已有事务测试用特定操作模式捕捉事务规则违例（如 ELLE 把历史建成依赖图）。
- 前人缺陷/未解决问题（逐条）：
  1. 只支持简单操作（如常量追加），复杂操作触发的深层 bug 测不到。
  2. 普遍不支持谓词（WHERE/JOIN 等），漏掉大量真实 bug。
  3. 多聚焦于隔离级别，忽略与隔离级别无关的事务 bug。

## 2. 核心方法
- 最直观类比：过去像是「只检查每个人是否在固定格子里排队」（简单模式），顾不到真实流程；TxCheck 像是「画出每个人在流程里和谁有交接（依赖图），再用监控记下实际交接，据此造出一份『理应完全相同』的流程副本」——副本跑出来和原流程不一样，就说明流程本身有 bug。
- 具体做法（输入 → 关键操作 → 输出）：
  1. 语句依赖图：描述事务中 SQL 语句之间的细粒度依赖。
  2. SQL 级插桩（Instrumentation）：捕获语句间可能的依赖。
  3. 事务预言构建：用依赖图生成语义等价的测试用例。
  4. 正确性论证：论文给出所构造用例语义等价性的正确性证明。
  5. 输出：触发的 transactional bug 及复现用例。
- 形式化要点：三大技术贡献——语句依赖图、SQL 级插桩、事务预言构建；并证明等价性。超参数以论文为准 🔧。
- 理论性质/保证：论文建立了生成语义等价测试用例的正确性（correctness）。

## 7. 2026 视角（🔧）
- 事务正确性测试是数据库系统可靠性核心；TxCheck 的「依赖图 + 插桩」范式进一步推动了对复杂谓词/操作的覆盖，被后续工作（如 EET、PolySI 等）引用。
- 近年趋势：把预言构造扩展到快照隔离/可串行化的黑盒检查（IsoVista、VeriStrong 系），以及结合 SMT 的高效验证。具体生态 🔧 查当年资料。
