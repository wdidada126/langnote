## 二、问题史：为什么 2006 年需要 Bigtable

- 关系型数据库在 web -scale 写吞吐与横向扩展上撞墙：单机主库+复制拓扑撑不住 Google 的增量爬取与索引构建（⚠️ 归纳）。
- 当时可行的替代：GFS 提供 append-only 分布式文件语义，但缺"随机读写 + 稀疏分布式多维排序映射"这一层抽象（✅ GFS 是 Bigtable 的底座）。
- SOSP/OSDI 同期路线对照：PNUTS（微软，后来的 Cosmos 前身）、HBase（Apache，受本文直接启发而生的开源实现）（⚠️ 对照项）。
- 设计目标四件套：scale（行/列双向扩展）、high performance（P99 延迟可控）、high availability、general use（不绑定单一负载）（✅）。

## 三、核心概念：稀疏分布式多维排序映射

论文把数据模型写成一个映射（✅原文式表述）：

```
(row: string, column: string, time: int) → string
```

- **稀疏**：不存的格不占空间，列族内空列零成本。
- **排序**：行键字典序；行的局部性单位——一个行的修改只涉及一台服务器。
- **列族**（column family）：列键 `family:qualifier`，同一列族的列倾向物理聚存，是 I/O 与访问控制的单位。
- **时间戳版本**：每格保留最近 N 个版本（可配），新旧值天然构成变更历史。

## 四、架构三层：Tablet / GFS / Chubby / Compaction

### 4.1 Tablet 与三层树

- 行键空间切分为 tablet（目标 100–200 MB，✅），tablet 是负载均衡与迁移单位。
- 定位路径三层：Chubby 里的特例文件 → Root tablet（整集群仅一个）→ Meta tablet → 数据 tablet，树可无限向下扩（✅）。

### 4.2 组件分工

| 组件 | 职责 |
|---|---|
| Client 库 | 缓存 tablet 位置，链接式预取（✅） |
| Master | tablet 分配/迁移/负载均衡，**不在读写路径上**（✅） |
| Tablet Server | 持有 tablet，服务读写，跑 Minor/Major Compaction（✅） |
| GFS | tablet 数据与提交日志的最终落盘介质（✅） |
| Chubby | 锁服务：单 Master 选举、粗粒度锁、Schema/访问控制信息存放（✅） |
| Buckets | 供 SSTable 使用的分布式哈希文件（⚠️ 论文提及，细节少） |

### 4.3 SSTable 与 LSM 血统

- SSTable：不可键改变的排序字符串表，块索引 + Bloom filter，是 LSM-tree（[[lsm_tree_1996]]）思想在分布式环境的物化（⚠️ 谱系判断）。
- 写路径：memtable（内部用排序树）→ 满则 flush 成 SSTable → 后台 Major Compaction 归并；Commit Log 在 GFS 上保证崩溃恢复（✅）。
- 读路径三源归并：memtable + 若干 SSTable，靠 Bloom filter 与"块内无更新/删除则整块跳过"的元技巧加速（✅）。

## 五、实现要点（论文 §5–§6）

- **两级 LSM**：内存 memtable + 磁盘 SSTable 树，论文自述"只在 memtable 层利用 LSM 原则"（✅）。
- **压缩**：Block 级 16–64 KB；采用 Bentley–McIlroy 式字符串共享压缩，两段式"Commons prefix / 字典引用块"（✅）；热块先不压，最后 10% 新块不压（✅）。
- **扫描**：单 tablet 内 128 KB 预取 + 跨 tablet 异步预读，读吞吐场景下扫描性能远超点查循环（✅）。
- **一致性接口**：行内原子；跨行无事务（只在 single row 内保证）——这是对 Spanner 前时代的明示边界（✅，对照 [[spanner_2012_osdi]]）。
- **Chubby 锁**：tablet 服务器崩溃后，其 tablet 需等租约过期才能被重新分配——可用性换一致性的典型代价（⚠️）。

## 六、评测与数字（✅ 摘录）

- 1 读线程 + 8 写线程 /  tablet server，随机读约 350 QPS/线程量级，写吞吐受内存 flush 节奏支配（⚠️ 具体曲线以论文图表为准）。
- 64 台服务器、1 TB 表批量扫描：约 10^5 记录/秒级别（⚠️）。
- "随机读延迟 vs 时间戳"图：最近版本命中 memtable 时延迟最低，版本老化后回退磁盘。

## 七、批判读法

- 论文是**经验报告**而非系统构建指南：Master 故障恢复、跨数据中心复制等运维难点几乎没写（⚠️）。
- 行内原子把复杂业务推给上层——"用 Bigtable 的谁在做事务"这个问题论文回避了，答案要等 Percolator 与 Spanner（⚠️）。
- Google 论文常见的规模幸存者偏差：60+ 内部项目都跑得好，不代表通用负载（如低基数频繁二级索引）也适合（⚠️）。
- 开源复刻（HBase/Cassandra）丢掉了 Chubby→ZooKeeper 之外的不少细节（tablet 预热、块缓存策略），性能对比 HBase 论文要打折读（⚠️）。

## 八、🔧 本地微实验（非本书/非集群行为，纯单机模拟）

1. **SSTable 手工版**：写 3 个各自有序的 key 段文件 + 块索引，模拟一次 major compaction 归并成 1 文件——体会"写放大换读放大"。
2. **Bloom filter 跳读**：用 py 手写 10% 假阳率的 Bloom，对 10^5 个 miss 查询统计"省下的磁盘块读次数"。
3. **时间戳版本裁剪**：JSONL 追加写 + N=3 版本保留策略，模拟 scan 只见最新 N 版。
4. **行键稀疏性**：对比"稠密二维表 CSV"与"只存非空格"的字节数差，感受稀疏列族的存储收益。
5. **tablet 切分**：按行键字典序中点把 sorted 文件切成 100–200 KB 块，模拟负载均衡单位。

## 十一、最新演进与工业实践

- Bigtable 已成为 GCP 托管产品（2015 GA），并支撑 Analytics Hub、Datastore 等上层（⚠️）。
- HBase 2.x/3.x、Amazon DynamoDB（key-value 化改造）延续了"列族+行内原子"的 NoSQL 范式（⚠️）。
- 存算分离浪潮（Aurora/Sota 化）反证 Bigtable 的"GFS 通用文件系统当唯一持久层"路线：专用 redo 通道成为新共识（⚠️）。
- 宽列模型在时序场景（OpenTSDB）与画像场景仍活跃；向量检索时代 Bigtable 加了 AnnIndex 一类二级索引（⚠️）。
- 2024–2026 云厂商 Bigtable 兼容层（如 Cassandra bridge）持续存在，论文本身未再更新（✅ 判断：经典定格）。
