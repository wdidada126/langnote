## 一句话总结

多轮问数据库时，用户的第二个问题往往是「那改成只看 2023 年的呢？」——与其让模型每次从零生成整条 SQL，不如在上一轮的 SQL 上做编辑（改几个 token）。EditSQL 用这种 token 级编辑机制在 SParC 多轮基准上大幅超过了从零生成的基线。

## 0. 给新手的阅读前置（背景知识地图）

子方向解决什么大问题：单轮 Text-to-SQL（Spider）只需「一问一答」；但真实用户是连续追问的（「查销量最高的歌手」→「他唱过的歌呢？」）。跨领域上下文依赖的 Text-to-SQL 要在没见过的新数据库上，结合对话历史把每一轮问题译成 SQL。

为什么难：
- 当前问题里充满省略与指代（「他唱过的歌」的「他」指上一轮答案）；
- 相邻问题语言上相互依赖，单独看根本无法解析；
- 还要同时应对跨领域的陌生 schema。

几类主流解法：

| 路线 | 代表 | 直觉 |
|------|------|------|
| 从零生成 + 历史拼接 | CD-Seq2Seq | 把历史问题和历史 SQL 串起来，每次重新生成整条 SQL |
| 编辑上一条 SQL | 本文 EditSQL | 上一条 SQL 大部分是对的，只需局部修改 |
| 状态跟踪/对话式 | CoSQL 系 | 把任务视为对话状态跟踪 |

本文属哪类：第 2 类的开创性工作——「SQL 是序列，编辑发生在 token 级」。

关键名词直觉解释：
- Interaction Match（IM）：多轮评测指标——一整段对话里所有轮次的 SQL 都对才算该段得分；
- Question Match（QM）：单轮粒度的正确率；
- 跨领域（cross-domain）：训练与测试用不同领域的数据库，考察泛化而非记忆。

## 1. 问题背景与动机

- 前人工作：SParC（ACL 2019）与 CoSQL（EMNLP 2019）两个数据集（本文作者团队同时发布）把「跨领域 + 上下文依赖」正式变成基准；当时的基线 CD-Seq2Seq 把历史拼进输入、每轮从零生成 SQL，效果很差。
- 前人的缺陷/未解决问题（本文逐条给出动机）：
  1. 从零生成浪费且易错：相邻问题的 SQL 往往高度重叠（只改个 WHERE 条件），从零生成等于每次重做全部决策，任何一步错整条报废；
  2. 错误传播：历史 SQL 的错误被原样拼进输入，模型容易被带偏；
  3. 复杂 schema 处理不足：跨领域意味着每轮面对陌生表结构，编码器需要同时消化「用户话语上下文」与「表 schema 上下文」。

---

## 2. 核心方法

- 最直观类比：改作文不是重写一篇，而是圈出要改的句子动笔。上一轮 SQL 就是草稿，新问题只带来一处两处的「修改指令」。
- 具体做法（输入 → 关键操作 → 输出）：
  - 输入：对话历史（历史问题 + 历史 SQL）+ 当前问题 + 数据库 schema；
  - 关键操作 1（编辑机制）：把上一轮预测的 SQL 视为 token 序列，解码器在编辑模式下重用上一条 SQL 的 token——可以原样保留、也可以改写/插入/删除单个 token；这种简单机制让模型对历史错误更鲁棒（不必整条继承）；
  - 关键操作 2（utterance-table encoder）：一个同时编码「话语上下文（历轮用户话）」与「表 schema」的编码器，把对话与库结构放进同一表征；
  - 关键操作 3（table-aware decoder）：解码时感知 schema 信息生成/编辑 token；
  - 输出：当前轮的 SQL。
- 形式化要点：把「上下文依赖解析」从「序列到序列」重构为「序列到编辑序列」；编辑操作作用在 token 级，因而灵活且模型只需学局部差异。
- 理论性质：无理论保证；实证型工作。

## 3. 变体 / 工程版

- 同一仓库还实现了对照模型 CD-Seq2Seq 及其 segment copy 变体（复制历史片段），作为从零生成路线的代表；
- 代码同时支持 Spider（单轮）、SParC、CoSQL（多轮）与 ATIS（Suhr et al. 2018 设定）四个数据集的训练与评测，是当年多轮 Text-to-SQL 的通用实验床。

## 4. 实验结论（概览）

- 数据集与指标：SParC（主实验）、CoSQL、Spider、ATIS；指标 Question Match（QM）与 Interaction Match（IM）。
- 对比基线：CD-Seq2Seq（含 segment copy 变体）等从零生成基线。
- 主要数字（均取自官方 README，与论文对应）：
  - SParC：EditSQL QM dev 47.2 / test 47.9；IM dev 29.5 / test 25.3（用预测的历史查询）；对照 CD-Seq2Seg 仅 QM dev 21.9、IM dev 8.1；
  - CoSQL：EditSQL QM dev 39.9 / test 40.8；IM dev 12.3 / test 13.7；
  - Spider（单轮参考）：dev 57.6 / test 53.4。
- 结论方向：编辑机制显著优于从零生成；用 gold query 做历史的上界实验（SParC QM dev 53.4）说明历史质量影响显著。

## 5. 开源代码与动手实践

- 仓库：https://github.com/ryanzhumich/editsql ，语言 Python（PyTorch 1.0，Python 3.6，年代较久）。
- 典型流程（教学示意，以 README 为准 🔧）：
  1. `conda create -n editsql python=3.6` 并 `pip install -r requirements.txt`；
  2. 下载预训练 BERT 权重放到 `model/bert/data/annotated_wikisql_and_PyTorch_bert_param/`，下载数据库 sqlite 文件到 `data/database`；
  3. 按 `run_sparc_editsql.sh` 训练（SParC）/ `run_spider_editsql.sh`（Spider）/ `run_cosql_editsql.sh`（CoSQL）；
  4. 用配套 `test_*.sh` 复现 dev 结果（作者提供训练好的 checkpoint 下载）；
  5. ATIS 实验需自建 MySQL 数据库并在 `parse_args.py` 填账号。
- 许可与资源提醒：代码基于 Suhr et al. 2018（NAACL 2018）实现改造；需 GPU；Python 3.6 + PyTorch 1.0 依赖老旧，建议用 conda 隔离环境或容器；长对话可能 GPU OOM（README 提示可跳过超长交互）；LICENSE 条款 🔧 待查。

## 7. 2026 视角（🔧）

- 专用编辑式解码器随 BERT 时代专用模型一同退场：如今多轮 Text-to-SQL 由 LLM 以对话上下文直接生成，编辑思想以更轻的形式存活——例如 CoE-SQL 的「编辑链」上下文学习；
- 「利用相邻查询的结构重叠」这一洞察在工业界并未过时：对话式 BI（如基于 LLM 的数据问答产品）常用「改写上一条查询」来降低延迟与错误率；
- 对新手的启示：多轮任务的正确指标是 IM 而非 QM——一段对话全对才算对，这个严格口径至今仍是多轮 Text-to-SQL 评测的共识。

- 10 分钟：读摘要 + 本笔记第 0 节，理解「编辑 vs 从零生成」的对立与 QM/IM 两个指标。
