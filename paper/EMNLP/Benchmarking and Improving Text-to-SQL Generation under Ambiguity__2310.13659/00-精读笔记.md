## 一句话总结

真实库的表名/关系路径常有歧义，一个问题本可翻译成两条都合法的 SQL，但主流模型 top-1 只能押一个。本文发布 **AmbiQT 基准**（3000+ 歧义样例）证明现有系统离"top-k 覆盖全部合理解释"很远——原因是 beam search 只做 token 级多样——并提出 **LogicalBeam**：按计划模板多样化 + 受限填充，top-k 全覆盖能力最高提至 **2.5 倍**。

## 0. 给新手的阅读前置（背景知识地图）

- **大问题**：`"id"` 这类列名可能同时出现在多张表里；`player → team → stadium` 与 `player → stadium` 两条路径都能"说得通"。一个问题存在**多个合法 SQL**，系统应该像搜索引擎一样给 top-k 而不是只给一个答案。
- **为什么难**：现有基准默认唯一正确答案；解码器（beam search）为凑多样性只会在 token 层面变花样（同义改写、加空格），产生大量"看起来不同、逻辑相同"的无用候选。
- **主流做法对比**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 唯一答案训练 | Spider 标准评测 | top-1 精确匹配 | 简单；忽略歧义现实 |
| top-k 通用解码 | beam search | 保 k 个高概率序列 | token 级多样≠逻辑多样 |
| **逻辑级多样解码** | **LogicalBeam（本文）** | 计划模板多样化+受限填充 | 真正覆盖不同合理解释（本文） |

- **本文属于哪类**：评测（AmbiQT）+ 解码算法（LogicalBeam）双贡献。
- **必须先懂的名词**：
  - **词汇/结构歧义**：同一词对应多列（词汇）；同一语义对应多条 join 路径（结构）。
  - **top-k 覆盖率**：正确/全部合法解释出现在前 k 个候选中的比例。
  - **受限解码（constrained decoding）**：生成时强制满足语法/schema 约束。

## 1. 问题背景与动机

- 前人工作：Text-to-SQL 评测普遍假设答案唯一；带歧义的交互式系统（如 AMBROSIA 一线）开始关注问题歧义。
- 未解决的问题：
  1. 缺一个系统化、可量化的"歧义下 top-k 能力"基准；
  2. 主流 beam search 在歧义场景的失败机理未被揭示——它把 SQL 当字符串，top-k 里只有 token 级无用多样性。

## 2. 核心方法

- 类比：点菜时别只报菜名，报"烹饪方式"——先保证 k 个候选来自**不同做法**（不同查询计划模板），再在每个做法里填上具体食材（表列名）。
- 具体做法（输入 → 操作 → 输出）：
  1. **AmbiQT 基准**：3000+ 样例，每条文本因词汇和/或结构歧义可解释为两个合理 SQL（构造方法 🔧 见原文）；
  2. **诊断**：评测多个系统（含最先进 LLM）与解码算法，确认 top-k 覆盖远低于理想；
  3. **LogicalBeam 解码**：两部分融合——
     - 基于计划的模板生成：用**反事实生成**（counterfactual）实现模板多样化；
     - 受限填充的 beam search：仅在 schema 名上分支，提供值多样性。
- 输出：top-k 候选列表（覆盖多个合法解释）。

## 3. 变体 / 工程版

- LogicalBeam 是即插即用解码层，不改动底层模型权重；可与任意自回归 Text-to-SQL 模型组合。

## 4. 实验结论（概览）

- 对比基线：多个 Text-to-SQL 系统 + 标准 beam search /采样解码（含 LLM）。
- 结论方向（摘要明确给出）：
  - LogicalBeam 在 top-k 中生成全部候选 SQL 的能力最高达 SOTA 模型的 **2.5 倍**；
  - 同时提升 SPIDER 与 KaggleDBQA 上的 **top-5 精确匹配与执行匹配** 准确率；
  - 🔧 逐基准逐 k 的覆盖率/准确率数字查原文表格后补。
