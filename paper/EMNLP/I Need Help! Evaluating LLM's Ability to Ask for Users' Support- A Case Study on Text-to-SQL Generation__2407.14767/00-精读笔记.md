## 一句话总结

一个「知道自己不知道」的 LLM 才是好助手：本文研究 LLM 在写 SQL 遇到信息缺口时，**会不会、该不该、什么时候**向用户提问。发现没有外部反馈时许多 LLM 根本意识不到自己需要帮助——「开口求助」本身是一种需要专门度量的能力。

## 0. 给新手的阅读前置（背景知识地图）

- **大问题**：真实 Text-to-SQL 中，用户的问题经常**信息不全**（有歧义的列名、未说明的时间范围、缺失的表信息）。聪明的系统有两条路：瞎猜着写（可能错）或**主动向用户要信息**（clarification / 求助）。后者有代价——打扰用户、增加用户负担。
- **为什么难**：模型要**自知不确定**（自我评估信心），还要权衡「问一次的收益 vs 打扰的成本」；LLM 通常被调优成「自信作答」，天生不擅长承认不会。
- **几类相关解法**：

| 类别 | 直觉 |
|------|------|
| 直接生成 | 不管缺不缺信息，硬写一条 SQL |
| 被动澄清 | 用户发现结果不对再返工 |
| 主动求助（本文） | 模型判断信息不足时先提问 |
| 多候选/一致性 | 采样多条 SQL，分歧大=不确定（可作为求助信号） |

- **本文属哪类**：第三类的**评测框架研究**——提出指标来衡量「求助能力」，而非提出某个新模型。
- **关键名词直觉**：
  - *主动求助（proactive support-seeking）*：系统在没有被告知的情况下，自己决定发起提问。
  - *性能-负担权衡*：提问可能提升正确率，但每次提问都消耗用户时间与耐心；好系统要在两者间取最优。
  - *信息可用性（information availability）*：实验变量——被追问后用户能提供多少帮助（从「什么都没有」到「完全解答」）。

## 1. 问题背景与动机

- 前人工作：Text-to-SQL 的歧义处理与澄清研究（如 Benchmarking and Improving Text-to-SQL Generation under Ambiguity）、交互式语义解析（Model-based Interactive Semantic Parsing）；LLM 的自我校准（self-calibration）研究表明 LLM 判断自身不确定性的能力有限。
- 前人缺陷/未解决问题（逐条）：
  1. 几乎所有评测都假设「输入信息完备」，**LLM 面对信息缺口时的行为没有被系统度量**。
  2. 「什么时候该求助」缺少量化指标——此前只有定性的澄清策略讨论。
  3. LLM 的**自我认知局限**（意识不到自己缺信息）在 Text-to-SQL 具体任务上未被验证。
  4. 外部信号（用户反馈、工具结果）对触发求助的作用不明。

## 2. 核心方法

- **最直观类比**：考驾照时遇到不认识的标志，学员该「凭感觉开」还是「停车问教练」？本文设计了一场考试：故意出一些「缺条件」的题，观察学员（LLM）是硬开、还是问；问得多但都对=好事吗？问得太多把教练烦死=坏事。然后给每个学员按「开对率 + 教练被烦程度」综合打分。
- **具体做法（输入→关键操作→输出）**：
  - 输入：故意构造信息不足的 Text-to-SQL 任务实例。
  - 关键操作 1：提出**评估指标**，量化「性能提升 vs 用户负担」的权衡（如：求助后的正确率增益、求助频率/次数带来的负担）。
  - 关键操作 2：在**不同信息可用性条件**下（用户能提供的帮助程度不同）让多个 LLM 执行任务，观察其求助行为。
  - 关键操作 3：对比「有无外部反馈」时的表现，检验外部信号是否触发正确求助。
  - 输出：各 LLM 求助能力的量化画像与结论。
- **形式化要点**：🔧 指标的精确定义（公式）、信息可用性的具体分级、涵盖哪些 LLM（GPT-4o / Claude / 开源模型等）与多少任务实例，请查原文第 2–3 节。
- **理论性质**：无理论保证；贡献是评测框架与实证发现。

## 3. 变体 / 工程版（如有）

- 无算法变体；实验覆盖多个 LLM 与多种信息可用性设置的组合，形成评测矩阵。
- 工程延伸方向（本文启发）：把「不确定时先问」做进交互式 Text-to-SQL 产品；与本仓库 SQLucid（带解释的交互查询）互补。

## 4. 实验结论（概览）

- 对比对象：多个主流 LLM（🔧 具体型号查原文）。
- 数据/任务：自建的信息不足 Text-to-SQL 案例集。🔧 规模查原文。
- 指标：性能提升、用户负担及综合权衡指标（自提出）。
- 结论方向：
  1. **没有外部反馈时，许多 LLM 难以意识到自己需要用户支持**（会硬猜）；
  2. 外部信号（反馈/工具结果）对触发正确求助很重要；
  3. 为改进 LLM 的求助策略提供了方向性洞见。

## 7. 2026 视角（🔧）

- 「主动澄清/求助」已成为 2025–2026 LLM Agent 研究的核心议题之一（agentic clarification、uncertainty-aware prompting），本文是较早把该能力**作为独立评测对象**的 Text-to-SQL 实证工作。
- 现代 Text-to-SQL 系统（含商用 Copilot 类产品）普遍加入澄清环节；常见工程手段是用自一致性（多采样分歧度）作为「该问用户」的触发信号——正是本文所说「外部信号」的自动化版本。
- 与「self-calibration / 校准」研究的关系是持续热点：LLM 的过度自信仍是可靠性瓶颈，求助指标有望成为 agent 评测标准配置。

## 8. 新手学习路线

- **10 分钟**：读 arXiv 摘要 + 本文「0. 阅读前置」；理解「性能-负担权衡」与「信息可用性」。
- **30 分钟**：精读原文指标定义与主要实验图；浏览 i-need-help 仓库了解实验配置。
- **进阶**：动手做个小实验——给一个 LLM 出 10 道「故意缺列名/缺时间范围」的 Text-to-SQL 题，统计它主动提问的比例；再对比加上「你可以提问」提示后的变化。
