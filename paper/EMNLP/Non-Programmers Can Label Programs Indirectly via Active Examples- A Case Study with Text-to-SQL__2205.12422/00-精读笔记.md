## 一句话总结
非程序员看不懂候选 SQL 程序，怎么让他们给 Text-to-SQL 标注正确答案？APEL 让标注者不直接读程序，而是看程序在「主动挑出的简单输入」上的输入输出例子来间接选对的那个；用它重标 Spider，达到了和专家标注一样的 75% 准确率，还揪出原标注里不少细微错误。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：训练 Text-to-SQL 模型需要大量「问句→正确 SQL」标注，但写 SQL 是程序员活儿，成本高、扩不动。能不能让不懂 SQL 的人来标？
- **为什么难**：标注者看不懂 SQL 候选，直接让他们选「哪段程序对」不现实。
- **几类主流解法**：

| 方法 | 思路 | 优缺点 |
|------|------|--------|
| 专家手写标注 | 程序员写 gold SQL | 准但贵 |
| 众包弱监督 | 用规则/弱标 | 便宜但有噪 |
| 本文 APEL | 看 I/O 例子间接选 | 非程序员可用 |

- **本文属哪类**：数据标注 / 人机协作方法，以 Text-to-SQL 为案例。
- **2-3 个必懂关键名词**：
  - **semantic parser（语义解析器）**：把自然语言映射到形式程序（如 SQL）的模型；本文用 Codex 作种子解析器。
  - **active examples（主动样例）**：系统主动挑一个简单输入，让不同候选程序在此输入上输出不同，从而暴露差异。
  - **indirect labeling（间接标注）**：不读程序本身，而通过其 I/O 行为来判断对错。

## 1. 问题背景与动机
- 前人工作简述：Text-to-SQL 等语义解析依赖大量程序级标注，通常由专家完成。
- 前人缺陷/未解决问题（逐条）：
  1. **非程序员无法标注程序**：直接展示候选 SQL 他们看不懂。
  2. **标注成本高、易有错**：专家标注贵，且原标注可能存在细微错误却难发现。

## 2. 核心方法
- **最直观类比**：让不懂菜谱的人评判两道菜谁对——别给他看菜谱（程序），而是给他同一份食材（输入），让他尝两道菜成品（输出）挑哪个对；APEL 还会聪明地选「两道菜差别最明显」的那份食材。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **种子解析器生成候选**：用 Codex 等语义解析器为每个问句生成若干候选程序。
  2. **主动挑输入**：APEL 主动搜索一个简单输入，使得候选程序在该输入上输出明显不同。
  3. **间接标注**：非程序员只需在该输入上挑选「正确的输出」，从而反推出哪个程序正确，可用于微调解析器。
  - 输出：问句的正确程序标注（及可用于微调的数据）。
- **形式化要点**：核心是「用 I/O 例子的差异替代程序可读性」做标注；主动样例搜索是关键（🔧 搜索策略以论文为准）。
- **理论性质/保证**：无理论保证；以「达到专家 75% 准确率 + 发现原标注错误」的实证为主。

## 3. 变体 / 工程版（如有）
- 框架可推广到其它语义解析/程序标注任务（不止 Text-to-SQL），只要能跑候选程序的 I/O（🔧 以论文讨论为准）。

- 对比基线：原 Spider 专家标注（作为参照）。
