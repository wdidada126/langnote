## 一句话总结
流处理作业要长期运行，必须能在线伸缩（加減并行度）。但现有伸缩方法同步粒度太粗、状态迁移太笨重，一伸缩就卡顿甚至系统停摆。DRRS 用三个招数解决：细粒度伸缩信号 + 重路由（减少传播延迟）、精巧的记录调度（减少处理暂停）、以及把待迁移状态切成独立子集的「子规模划分（subscale division）」——在 Flink 上实现后，峰值与平均延迟最多降 81.1% 和 95.5%，伸缩时长缩短 72.8%~86%，且非伸缩期间不受影响。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：流处理作业是 7×24 长期运行的，流量高峰要扩容、低谷要缩容，这就叫**动态伸缩（dynamic scaling）**；有状态的作业（带窗口聚合、join 状态）伸缩时还要搬状态。
- **为什么难**：
  - 伸缩需要同步（synchronization，例如全局一致的检查点/屏障），粗粒度同步会让整条流水线停下等；
  - **状态迁移（state migration）** 要把大量状态从旧实例搬到新实例，搬的时候处理要暂停；
  - 状态之间还有依赖关系，粗暴地整体搬迁代价极大。
- **几类主流解法**：

| 方法 | 代表 | 思路 | 优缺点 |
|------|------|------|--------|
| 停止-重启式伸缩 | 早期 Flink savepoint 重部署 | 停作业、改并行度、从 savepoint 恢复 | 简单，停机时间长 |
| 键组重分配（key-group） | Flink 原生 rescale | 按 key group 重新分配状态 | 通用，迁移粒度与暂停仍不够细 |
| 细粒度在线伸缩（本文） | DRRS | 细粒度信号 + 重路由 + 记录调度 + 子规模划分 | 延迟与伸缩时长大幅下降，实现复杂 |
| 资源调度/预测式伸缩 | Phoebe、Demeter | 预测负载提前调配资源 | 减少伸缩次数，不解决伸缩本身代价 |

- **本文属于哪一类**：**细粒度在线伸缩（on-the-fly scaling）**——直接优化「伸缩这个动作本身」的系统级开销。
- **必懂关键名词**：
  - **伸缩信号（scaling signal）**：触发/协调伸缩的同步标记（类似检查点屏障）；传播得越慢，系统等待越久。
  - **状态迁移（state migration）**：扩容时把部分 key 的状态从旧并行实例搬到新实例的过程。
  - **子规模划分（subscale division）**：本文的核心机制——把待迁移状态切成**相互独立的子集**，从而把迁移拆成更细、更可控的批次。

## 1. 问题背景与动机
- 前人工作简述：动态伸缩对流处理引擎至关重要，因为作业长期运行，需要自适应的资源管理；已有系统（如 Flink）提供基于 savepoint/key-group 的重分配方案，也有基于负载预测的调度工作。
- 前人的缺陷 / 未解决问题（逐条）：
  1. **粗粒度同步（coarse-grained synchronization）**：现有伸缩方法的同步粒度太粗，导致性能下降。
  2. **低效的状态迁移（inefficient state migration）**：状态迁移方式不够高效，代价高。
  3. **系统停摆（system halt）**：上述两点会导致系统停顿。
  4. **高处理延迟（high processing latency）**：伸缩期间延迟显著上升。
  5. **依赖相关开销**：迁移中的状态之间存在依赖，整体搬迁带来额外开销，缺少更细粒度的控制手段。

## 2. 核心方法
- **最直观类比**：给飞行中的飞机换引擎，最怕的是「整机停飞等待」。粗粒度方案像「让所有乘客先系好安全带、全机静默十分钟再换」；DRRS 像「分成若干小组，一组一组地换座位，换完一组立刻放行」——并且让「换座位」的通知（伸缩信号）走快速通道，而不是逐个座位传话。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：运行中的有状态流处理作业 + 伸缩决策（如并行度从 N 调到 M）。
  2. **关键操作一：细粒度伸缩信号 + 重路由（re-routing）机制**。让伸缩信号更细粒度，并配合重路由，显著缓解**传播延迟（propagation delay）**。
  3. **关键操作二：记录调度机制（record-scheduling）**。精巧地调度记录的流动，大幅减少**处理暂停（processing suspension）**。
  4. **关键操作三：子规模划分（subscale division）**。把待迁移状态划分为**相互独立的子集**，降低依赖相关的开销，实现更细粒度的控制与更好的运行时适应性。
  5. **输出**：伸缩完成后继续运行、且在伸缩期间延迟与停顿都大幅降低的流处理作业。
- **形式化要点**：核心是「把伸缩这件事在**信号、记录、状态**三个层面同时细化」；超参数包括信号粒度、子规模划分的份数与调度策略 🔧 具体见原论文。
- **理论性质 / 保证**：🔧 摘要未给出理论保证（论文以系统实现与实测为主）；可确认的工程性质是「**非伸缩期间不受干扰**（without disruption in non-scaling periods）」。

## 7. 2026 视角（🔧）
- 云原生流处理（K8s 上的 Flink、Serverless 流处理）让**弹性伸缩**成为核心能力，伸缩期间的抖动直接影响 SLA，因此「细粒度 on-the-fly 伸缩」是刚需而非锦上添花。
- 状态后端也在演进（远端状态存储、存算分离），这会改变状态迁移的成本结构——本文的「子规模划分」思路在存算分离架构下可能更简单，也可能面临新的瓶颈。
- 值得注意的判断标准：**非伸缩期间不受干扰**是这类方案能否被采纳的前提，任何以牺牲常态性能换取伸缩速度的取舍都需要谨慎评估。本节为趋势性判断 🔧。
