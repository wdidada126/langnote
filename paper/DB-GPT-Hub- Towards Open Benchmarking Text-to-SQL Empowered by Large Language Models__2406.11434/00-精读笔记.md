## 0. 给新手的阅读前置（背景知识地图）

**子方向解决什么大问题**：Text-to-SQL（NL2SQL）= 把人的自然语言问题翻译成数据库能执行的 SQL。它是"人为什么不能用嘴查数据库"这一老大难的核心。LLM 出现后，这条链路的主流玩法分两大派：

| 路线 | 直觉 | 代表做法 |
|------|------|----------|
| Prompting（提示工程） | 不改模型，靠写好提示 + few-shot 示例 + 分解步骤 | 各种 prompt 工程、in-context learning |
| Fine-tuning（微调） | 拿标注的「问题→SQL」对继续训练模型 | LoRA/QLoRA 等参数高效微调 |

**为什么难**：prompting 路线的评测刷得很多（Spider 榜单卷），但微调路线的系统评测稀缺——微调要算力、要数据管线、要对齐实验设置，各论文口径不一，结果没法比。

**本文属哪类**：基准/评测基础设施（benchmark suite），不是单一新模型。

**关键名词直觉**：
- **Text-to-SQL / NL2SQL**：自然语言问题 → SQL 查询，评测通常看执行准确率（EX，Execution Accuracy）。
- **微调（Fine-tuning）**：在预训练模型上用领域数据继续训练，让模型"专精"某任务。
- **开放基准（Open Benchmarking）**：代码、数据划分、评测脚本全公开，别人能用同一把尺子复测。

## 1. 问题背景与动机

- **前人工作**：Spider、BIRD 等 Text-to-SQL 数据集与榜单建立后，围绕 LLM 的评测大量集中在 prompting 路线；开源生态（如 DB-GPT 项目）也积累了微调管线。
- **前人缺陷/未解决问题**：
  1. 微调路线的基准化研究不足——各论文模型规模、数据、训练超参各搞一套，结论无法横向比较；
  2. 微调需要可观算力，个人与小团队难以复现，社区缺一个"标准化且模块化"的开源实现来降低成本；
  3. prompting 与 fine-tuning 两条路线的收益边界（什么时候微调才划算）缺乏系统性的实证回答。

## 2. 核心方法

**最直观类比**：prompting 路线已经有很多"考卷+评分器"，这篇是给"考前补习班（微调）"也定了一套统一的教材、课时表和评分标准，让不同补习班能同台比较。

**具体做法（输入→关键操作→输出）**：
- 输入：Text-to-SQL 数据集（Spider 系列与 BIRD 等 🔧 以仓库配置为准）+ 中/大型开源 LLM；
- 关键操作：提供模块化、易扩展的代码库，封装数据预处理、主流 LLM 的微调（含参数高效微调方法 🔧 具体方法清单以 README 为准）、以及标准化评估流程；
- 输出：可比的微调评测结果 + 一套可复用的实验管线。

**形式化要点**：摘要未给出新算法；核心贡献是工程化的基准设计与评估协议（🔧 细节查原论文）。

## 7. 2026 视角（🔧）

- 2024 年后 Text-to-SQL 的竞争重心从"单模型刷 Spider"转向"企业级落地"：schema 链接、大规模库路由、执行反馈纠错、Agent 化多步工作流成为主流。
- 微调路线在企业私有化部署中依然重要（数据不出域），但基座模型能力提升后，"何时需要微调"的答案越来越偏向"少量高质量数据微调或干脆 RAG+prompting"。
- 开源基准生态（BIRD 榜、Spider 2.0 等 🔧）持续演进，本文的"标准化微调评测"思路仍是企业内评测的常用做法。

## 8. 新手学习路线

- **10 分钟**：读 arXiv 摘要 + 本笔记第 0、2 节，搞清 prompting vs fine-tuning 两条路线。
- **30 分钟**：浏览 GitHub 仓库 README 与示例配置，理解一条微调管线包含哪些模块。
- **进阶**：用小规模数据 + LoRA 在 Spider 子集上跑通一次微调→评测闭环，再对照原论文中 prompting 基线结果，体会两条路线的差异。
