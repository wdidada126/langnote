## 一句话总结
应用常通过"数据库代理"透明地连 DBMS（连接池化、负载均衡）。但传统代理在用户态转发包，内核反复在用户/内核空间拷 buffer、系统调用费 CPU。Tigger 提出 **user-bypass**：用 Linux eBPF 把代理逻辑推进内核态，消除这些开销；实现了一个兼容 PostgreSQL 的代理，对比主流代理，在某场景同时把事务延迟降最多 29%、CPU 占用降最多 42%。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：**数据库代理（DBMS proxy）**——在客户端与后端 DBMS 之间加一层中间盒，做连接池化（少开连接）、负载均衡、协议解析等。云上很常见（AWS RDS Proxy、PgBouncer、ProxySQL…）。
- **为什么难**：代理要实现 DBMS 网络协议（应用层逻辑），所以传统上是用户态程序：包从网卡到用户态、再转发出去，内核不停在用户/内核空间拷 buffer，系统调用也吃 CPU。
- **几类主流解法**：

| 路线 | 代表 | 直觉 |
|------|------|------|
| 用户态代理 | PgBouncer、ProxySQL、MaxScale | 实现协议逻辑、做连接池；但有用户/内核拷贝开销 |
| 内核旁路（kernel bypass） | DPDK 等 | 绕过内核拿性能，但改架构大 |
| 本文：user-bypass（eBPF） | Tigger | 把代理逻辑用 eBPF 推入内核态，消除拷贝/系统调用开销 |

- **本文属哪类**：**系统**论文，数据库代理的高性能实现。
- **关键名词直觉**：
  - **user-bypass（用户旁路）**：不绕过内核，而是把应用逻辑"塞进"内核跑（借 eBPF），避免用户/内核来回拷。
  - **eBPF**：Linux 提供的"在内核里安全运行自定义小程序"的机制，Tigger 用它实现代理转发逻辑。
  - **connection pooling（连接池化）**：代理替客户端维护到 DBMS 的少量持久连接，多路复用请求，省去每连接开销。

## 1. 问题背景与动机
- 前人工作简述：PgBouncer、Pgpool-II、MaxScale、ProxySQL、AWS RDS Proxy 等代理实现 DBMS 协议做连接池/负载均衡。
- 前人缺陷/未解决问题（逐条）：
  1. **用户态转发开销**：代理在用户态收包、处理、转发，内核反复拷 buffer 到用户态再回来。
  2. **系统调用 CPU 开销**：每次网络收发都伴系统调用，累加吃 CPU。
  3. **未利用现代 OS 自定义执行能力**：现有代理没借 eBPF 等把逻辑移入内核。

## 2. 核心方法
- **最直观类比**：传统代理像"前台在用户办公室里来回跑腿传话（每次都要进出内核这扇门）"；Tigger 像"把传话员直接安排在大楼内部（内核），少跑门、少折腾"。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **输入**：客户端 SQL 连接请求（PostgreSQL 协议）。
  2. **user-bypass**：用 Linux eBPF 把代理的协议解析/转发逻辑推进内核态执行，省去用户/内核 buffer 拷贝与大量系统调用。
  3. **实现 Tigger**：一个兼容 PostgreSQL 的代理，保留连接池化/负载均衡等功能。
  - 输出：低延迟、低 CPU 的 DBMS 代理。
- **形式化要点**：核心是"eBPF 在内核态实现代理逻辑"的 user-bypass 技术；超参数含 eBPF 程序结构与池大小（🔧 以正文为准）。
- **理论性质/保证**：无形式化保证；靠实验证明延迟/CPU 双降。

## 7. 2026 视角（🔧）
- eBPF 在数据面（网络、可观测性、安全）已普及；把"有状态"的 DBMS 协议逻辑放进 eBPF 仍属前沿。云厂商代理（RDS Proxy 等）多走用户态/DPDK，Tigger 展示了内核态代理的潜力。
