## 一句话总结
用 LLM 处理长法律合同、厚报告这类文档时，一次性调一次 LLM 经常漏抓、抓错；DocETL 把「文档处理流水线」写成声明式查询，再让**智能体（agent）自动重写查询计划**——拆数据、拆任务、插入验证步骤——实测输出准确率比精心调过的基线**高出 25%–80%**。

## 0. 给新手的阅读前置（背景知识地图）
- **大问题**：从 PDF/合同/报告等非结构化文档里做提取、汇总、判断（如「找出所有不可抗力条款」）。SQL 时代有 ETL 流水线，现在换成 LLM 执行「语义算子」，问题是 LLM 单次调用不可靠且贵。
- **为什么难**：
  1. **长文档**：上下文长、信息散布，单次调用容易漏（摘要例：识别长法律文档中的全部 force majeure / indemnification 条款）；
  2. **准确性没人管**：现有 LLM 流水线框架主要优化**成本**，不是准确性；
  3. **怎么改查询**：把任务/数据拆开的方式组合爆炸，人工调优不可扩展。
- **主流解法分类（直觉）**：
  | 类别 | 思路 | 代表 |
  |------|------|------|
  | 声明式 LLM 流水线（省成本） | 用户写算子，系统按原样执行、优化成本 | 本文批评的既有框架 🔧 |
  | **声明式 + 智能体重写（本文）** | agent 自动改写计划 + 验证输出 | DocETL |
  | 端到端 LLM 应用 | 手写 prompt 链 | 各种 pipeline 脚本 |
- **关键名词直觉**：
  - *语义算子（semantic operator）*：把「用 LLM 做映射/过滤/聚合」当成关系代数算子来组合。
  - *重写指令（rewrite directives）*：预定义的「查询改写套路」，如把长文档切块再分别提取（map-reduce 式拆解）。
  - *计划评估（plan evaluation）*：合成针对具体任务的验证 prompt，给候选执行计划打分，择优。

## 1. 问题背景与动机
- **前人工作**：LLM 展示了处理非结构化数据的潜力，催生了一批**声明式 LLM 数据处理框架**（摘要原话：recent proposals for declarative frameworks for LLM-powered processing of unstructured data）。
- **前人缺陷（逐条）**：
  1. 现有框架聚焦「执行用户指定操作时**降成本**」，而非**提准确性**；
  2. 大多数操作**按用户写的方式原样执行（单次 LLM 调用）**，对复杂任务/复杂数据不准确，即使 prompt 已优化；
  3. 缺乏「判断哪个改写后的计划更好」的系统性评估机制；
  4. 智能体生成与评估计划本身有延迟，缺乏高效的优化算法来取舍。

## 2. 核心方法
- **最直观类比**：老练的数据工程师拿到一句模糊需求后，不会照字面直接跑一条大 SQL，而是改写成「先切分、再分段提取、再合并、加校验」的一串小步骤，并抽检验证每步输出——DocETL 就是把这个改写和验证过程交给 agent 自动做。
- **输入→关键操作→输出**：
  - 输入：用户用声明式接口定义的文档处理流水线（含自定义语义算子）+ 文档集合；
  - 关键操作三大件（经摘要核实）：
    1. **逻辑重写（logical rewriting）**：面向 LLM 任务特性的查询重写，基于「rewrite directives」（拆数据、拆任务或两者都拆）；
    2. **agent 引导的计划评估**：合成并编排**任务专属的验证 prompt**，为候选计划输出打分；
    3. **优化算法**：在「agent 生成/评估计划的延迟」约束下高效搜索有希望的计划；
  - 输出：优化后的执行计划 + 准确率更高的处理结果。
- **形式化要点**：语义算子代数、重写指令的形式定义与优化器搜索空间 🔧 查原论文后补。
- **理论性质/保证**：无形式化保证，属系统 + 实证论文；准确性提升 25%–80% 为实测（见第 4 节）。
