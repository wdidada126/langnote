## 一句话总结
把「用大白话问图数据库」这件事拆给三个各司其职的 AI 智能体：预处理（识别实体、重写问题、路径链接、抽 schema）、生成（微调过的 LLM 出 GQL）、精修（拿执行报错反哺修正）；还顺手造了个金融图谱数据集 StockGQL，在 StockGQL 和 SpCQL 上都显著超过基线。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：关系型数据库用 SQL，图数据库（如 Neo4j 的 Cypher、Nebula 的 nGQL）用**图查询语言（GQL）**。NL2GQL 就是「自然语言 → GQL」，让人不用学图查询语法也能查图。
- **为什么难**：图查询涉及「点-边-路径」结构，比 SQL 多了拓扑约束；单一 LLM 直译容易在 schema 对齐、路径规划、语法正确性上翻车。
- **几类主流解法**：

| 方法 | 思路 | 优缺点 |
|------|------|--------|
| 端到端 LLM 直译 | 直接 prompt 出 GQL | 简单但易错 |
| 流水线（识别→生成） | 分模块串起来 | 可控但易断层 |
| 多智能体（本文） | 多 agent 协作+自检 | 更准但更重 |

- **本文属哪类**：多智能体（multi-agent）协作框架，是 LLM + 数据库方向的新形态。
- **2-3 个必懂关键名词**：
  - **GQL（Graph Query Language）**：图数据库的查询语言，如 Cypher / nGQL；本文主要面向 nGQL 语法。
  - **multi-agent（多智能体）**：多个各管一摊的 LLM 角色协作完成任务。
  - **schema linking（模式链接）**：把问句里的词对应到图里的点类型/边类型/属性。

## 1. 问题背景与动机
- 前人工作简述：把 LLM 用到数据库（Text-to-SQL 等）很火；图数据库作为典型非关系库，自然语言转 GQL（NL2GQL）也开始被研究。
- 前人缺陷/未解决问题（逐条）：
  1. **流程过于「一条直线」**：现有方法依赖 streamlined 流程，忽视让 LLM 自主规划、并与其他 LLM 协作应对复杂 NL2GQL 的潜力。
  2. **高质量开源 NL2GQL 数据稀缺**：尤其基于 nGQL 语法的公开数据集很少。

## 2. 核心方法
- **最直观类比**：把「翻译一句话成图查询」交给一个三人小组——资料员（预处理）、翻译员（生成 GQL）、校对员（拿报错改稿），三人接力比一个人硬扛更稳。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **Preprocessor agent（预处理）**：做命名实体识别、问题重写、路径链接、抽取与问题相关的 schema，作为上下文。
  2. **Generator agent（生成）**：一个在 NL-GQL 数据上微调过的 LLM，依据问题与相关 schema 生成 GQL 语句。
  3. **Refiner agent（精修）**：用 GQL 执行返回的报错信息，去修正 GQL 或上下文。
  - 输出：可在图数据库执行的 GQL。
- **形式化要点**：三个 agent 协同；Generator 是微调模型（非纯 prompt），Refiner 形成「执行→报错→修正」闭环（🔧 训练/协作细节以论文为准）。
- **理论性质/保证**：无理论保证；以「显著超过基线」的实证为主。
