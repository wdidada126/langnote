## 一、背景与它回应的问题

### 1.1 时代前提：数仓搬上云，两条老路都不通

2012–2016 年的"云数据仓库"基本沿两条路线起步：

1. **共享磁盘（shared-disk）**：把传统 MPP/单机 RDBMS 直接搬进虚拟机，数据放在共享存储（NAS/SAN/早期块存储）上。问题：云对象存储（S3）不提供 POSIX 语义与可靠锁，共享磁盘层的扩展性与故障隔离都很勉强；存储容量与计算规模被迫同涨同跌。
2. **共享无存（shared-nothing）**：以同期某主流云数仓为代表，数据按分布键静态分片到固定节点。问题有三：扩容/缩容要**重新分布数据**（rebalance，大表以 TB 计、耗时以天计）；单集群内一个坏节点拖慢整个查询（straggler 放大）；多租户/多工作负载共享一个集群时互相排队，隔离与弹性互相矛盾。

论文的核心提问：**能不能把"计算组织"与"数据组织"彻底解耦，让两者各自独立弹性伸缩，同时保住关系引擎的完整语义（ACID、ANSI SQL、隔离性）？**

### 1.2 答案一句话

三层彻底分离：云端服务层（无状态 SQL/元数据/优化服务）+ 查询处理层（**Multi-Cluster, Shared-Data** 的多个独立"虚拟仓库"弹性 VM 集群）+ 持久存储层（S3 上的不可变压缩列式**微分区**，带版本从而支持时间旅行）；用"数据不可变 + 元数据指向快照"这条根，同时解决弹性、隔离、缓存一致性、克隆与误操作恢复。

## 二、核心设计精读

### 2.1 三层架构总览（ASCII）

```
                ┌────────────────────────────────────────────┐
 用户/BI/驱动 → │  ① Cloud Services 层（无状态、可水平复制）      │
                │  鉴权/多租户管理 · SQL 解析与优化 · 全局元数据    │
                │  计划生成 · 微分区裁剪(pruning) · 弹性缓存       │
                └───────┬──────────────────┬─────────────────┘
                        │ 下发计划/元数据快照 │ 元数据/版本推进
        ┌───────────────┴──┐        ┌──────┴───────────────┐
        │ ② 虚拟仓库 W1      │        │ ② 虚拟仓库 W2 (同数据!) │   ...Wn
        │ MPP: VM1..VMk     │        │ MPP: VM1..VMm         │
        │ 每节点: slave 进程  │        │ 规模/状态彼此独立        │
        │ + 本地 SSD 缓存    │        │ + 本地 SSD 缓存         │
        └───────┬──────────┘        └──────┬───────────────┘
                │ 只读不可变文件(带版本指针)      │
        ┌───────┴──────────────────────────┴───────────────┐
        │ ③ Persistent Storage：Amazon S3                    │
        │ 压缩列式微分区(micro-partition)，永不原地改写          │
        │ 全部变化=生成新版本 → 时间旅行 / 零拷贝克隆               │
        └───────────────────────────────────────────────────┘
```

要点：②中多个 W 可以同时查询**同一份** S3 数据——这就是"multi-cluster, shared-data"命名的由来：集群间既不共享内存、也不共享磁盘，只**共享数据（只读、不可变）**，因此没有任何跨集群锁与一致性协议。

### 2.2 云服务层：把"大脑"做成无状态

- 解析/优化/元数据管理/访问控制/计费/编排都放在服务层，服务层自身是分布式无状态进程，可任意增删副本。
- **全局元数据服务**是系统真正的"单写入序列化点"：表 = 一组微分区文件 + 一个指向某版本清单的指针；DML/DDL 的原子性通过"先写不可变新文件、再原子推进元数据指针"实现（类似快照隔离的持久化版本，但作用在文件清单层）。
- 查询编译（优化器生成计划）与查询执行彻底分家：仓库节点只是执行者。这与后来"服务层按语句收费/计算层按秒收费"的商品形态直接对应（论文以设计含义为主，商业细节不在此展开）。

### 2.3 查询处理层：虚拟仓库与弹性 VM

执行层是标准的 MPP（各节点 slave 进程协作跑计划片段、节点间 shuffle），但三个关键决定让它"弹性"：

1. **节点是短暂的（ephemeral VM）**：VM 随时可被替换/扩缩，节点不拥有数据的"所有权"。数据在 S3，任何节点都能读任何微分区 → 扩容不需要 re-balance，缩容不需要迁移。这正面拆掉了 shared-nothing 的命门。
2. **缓存只读故无一致性负担**：每个节点带本地 SSD 缓存，缓存对象是不可变文件块，因此**永不失效**（只需按容量淘汰）。论文把"不可变存储"列为让本地缓存方案在云上成立的关键：无需跨节点缓存一致性协议。
3. **多集群隔离**：不同部门/负载/并发查询可路由到相互独立的仓库，互不抢占；同一份数据被 N 个仓库各自缓存，热点数据自然复制到多个集群的 SSD 上（以冗余缓存换隔离与弹性）。

伸缩机制（论文描述 + 后续开源印证）：仓库大小可在分钟级 suspend/resume/resize；内部用弹性 VM 管理工具（文中点名 **Dashing**，后开源）按队列水位自动增减同类 VM，并保留一定"热备"实例以避开冷启动。伪码（示意）：

```
# Dashing 式集群伸缩循环（按论文思想简化）
loop every T:
    backlog = queue_length(cluster) + running_but_slow()
    if backlog > HIGH and size(cluster) < max_size: add VMs(pre-warmed)
    if backlog == 0 for IDLE_TIMEOUT: suspend(cluster)   # 秒级停表,不再计费计算
    if unhealthy(node): drain 其查询到新节点              # 数据在 S3,换机无痛
```

### 2.4 存储层：微分区 + 不可变版本 + 时间旅行

- 数据以**微分区**（micro-partition）组织：细粒度、压缩、**列式**、不可变的小文件（每分区几百行到几百 MB 量级；产品文档给出的 50–500MB 典型值属外围资料，2016 论文并未突出该数字，本笔记不以论文结论相称）。
- 每个微分区自动生成丰富统计元数据（min/max、distinct 估计、NULL 数等）集中存放于服务层；查询优化时做**分区裁剪**：谓词能与 min/max 区间不相交即整块跳过。**没有二级索引、没有物化视图调优、没有分区/聚簇键的事前设计**——论文把这列为对传统数仓 DBA 工法的系统性取消：云的带宽足够扫，裁剪靠元数据即可。
- **时间旅行（Time Travel）**：因为文件不可变、每次写产生新版本清单，历史版本天然保留；用户可查询/恢复到保留期内任意时间点（误删救急、审计、可复现实验），克隆表/模式只复制元数据指针即完成（零拷贝克隆）。伪码：

```
TABLE t: versions = [ v17(fileset=A,B,C), v18(fileset=A,B,D), v19(fileset=A,D,E) ]
UPDATE t ...:  写新微分区 E(与被改分区不重叠的整块重写), 指针 v18→v19   # 原子
SELECT ... FROM t AT(VERSION => 18):  按 v18 清单扫描                  # 时间旅行
CREATE TABLE t_clone LIKE t AT(19):  新表指针直接指向 v19 同一批文件      # 零拷贝
```

这套"清单指针 + 不可变文件"的取舍：用**存储换正确性与弹性**（旧版本占空间直到过期回收；更新是重写整块微分区而非原地改行）。这正是后来所有湖仓表格式（Iceberg/Delta/Hudi）采纳的同构设计。

### 2.5 聚簇与自动重聚簇（clustering / re-clustering）

问题：微分区裁剪只在新数据装载时"近似有序"，随插入/更新退化，查询剪枝率下降。传统答案（range/hash 分区、索引重建）要求停机或事前决策。Snowflake 的答案是**声明式、后台、增量**：

```
ALTER TABLE t CLUSTER BY (date_col, tenant_id)   # 仅声明意图,数据不动
# 后台服务持续:
while clustering_depth(t) > target:
    选取剪枝收益最高的若干"拥挤"微分区
    按聚簇键重排后重写为新的微分区(仍是新版本,旧块留给时间旅行)
    推进指针
```

特点：重聚簇与查询完全异步、按需计费、无需维护窗口；`clustering_depth`/`clustering_factor` 作为可观测指标（论文以"深度/因子"描述其度量思想）。本质是**把物理设计的"一次性决定"变成"持续控制回路"**——用云的廉价存储与后台算力消解了数仓运维最重的工法。

### 2.6 半结构化与其他 SQL 能力（按论文着墨从简）

论文强调完整 ANSI SQL 与事务语义是区别于当时 NoSQL 系大数据分析器的卖点，并给出对 JSON 类半结构化数据的原生类型支持（变体类型 + 展平函数，装载时不强制 schema、查询时可关系化投影）。UDF、行级安全等企业特性文中亦有提及，此处不逐一展开。

### 2.7 一次查询的完整解剖（串起三层）

以 `SELECT count(*) FROM sales WHERE day BETWEEN '2015-01-01' AND '2015-01-31' AND tenant=42` 为例，按本文架构走一遍（流程为论文机制的复述，非原文示例）：

```
1. 用户经 ODBC/驱动接入服务层 → 鉴权、解析、优化器生成计划
2. 优化器查全局元数据: 取表当前版本清单(如 v19), 对 10 万个微分区
   用 (day_min,day_max,tenant 统计) 剪枝 → 剩下 3800 个候选分区
3. 选定一个虚拟仓库(按租户/负载路由), 下发计划 + 分区清单切片
4. 仓库内各 VM 的 slave 进程认领分区切片:
     本地 SSD 有该文件块 → 直接读; 否则 GET S3 → 落盘缓存 → 读
   列式解码只取 day/tenant 两列(谓词列), count 不需要投影其余列
5. 部分计数在节点间按 MPP 方式汇聚(slave 之间走 VM 网络)
6. 结果回到服务层, 流式返回客户端; 仓库空闲超时则 suspend
   若中途某 VM 失联: 其分区切片重新派给其他节点(数据在 S3,无人丢失)
```

三个"设计—收益"对应在流程中显形：剪枝发生在**服务层编译期**（所以任何仓库都受益）；失败重试的代价是**重派切片**而非重分布数据；缓存命中与否决定**同一查询第二次快不快**——这三点分别解释了论文对旧路线的三个优势。

## 三、实验与工程取舍

论文的实验章节以"真实云负载上的机制演示"为主，而非 TPC 排行榜（下述为定性结论，具体图表数值未逐一复核，不以精确数字引用）：

1. **弹性曲线**：同一查询在成倍扩大的仓库上近线性加速，说明执行层瓶颈可被"加机器"直接消解；而仓库缩到 0（suspend）与数据可用性无关，成本模型由此成立。
2. **缓存效果**：冷集群首查需从 S3 拉数据，重复查询命中本地 SSD 后延迟显著下降；多集群场景下热数据被多份缓存复制。
3. **聚簇效果**：大表在声明聚簇键并经后台重聚簇后，扫描剪枝率提升、查询时间数量级缩短——演示"控制回路式物理设计"的收益。
4. **多租户隔离**：并发工作负载被路由到不同虚拟仓库后互不干扰（对比单集群排队/抢占）。

深层取舍清单：

| 取舍 | 选择了 | 放弃了 | 换来的 |
|---|---|---|---|
| 数据放置 | 全量在 S3、计算无所有权 | 极致本地性/单查询最低延迟 | 免 rebalance、秒级弹性、坏节点无痛替换 |
| 写入模型 | 不可变微分区+版本 | 原地更新的写放大低 | 缓存零一致性、时间旅行、零拷贝克隆 |
| 物理设计 | 元数据剪枝+后台聚簇 | 手工索引/物化视图的微调上限 | 免 DBA 工法、自适应负载变化 |
| 架构位置 | 三层可独立扩缩 | 单机紧耦合的性能红利 | 多租户隔离、按集群计费的商品形态 |
| 依赖 IaaS | 直接吃 S3/EC2 红利 | 对底层存储的自控 | 持久性/容量运维外包（S3 的设计持久性即卖理由） |

## 四、与相关工作对比

- **vs Dremel（同仓库精读：[../doi_10.14778_1920841.1920886/00-精读笔记.md](../doi_10.14778_1920841.1920886/00-精读笔记.md)）**：同为"嵌套/列式 + 扇出执行"，但 Dremel 是 Google 内网只读 ad-hoc 分析器（无 ACID 写入面、语言无 join），Snowflake 则把完整关系事务 + SQL 搬上公有云；Dremel 的"投影即性能"与 Snowflake 的"剪枝即性能"分别是列存思想在两种数据组织（嵌套记录树 vs 微分区表）下的化身。
- **vs 同期云数仓（shared-nothing MPP）**：本文是对"静态分片 + 单集群"路线的直接批判；multi-cluster shared-data 之后成为云数仓事实标准（行业后续走向属通识，此处不展开各竞品细节）。
- **vs 湖仓（lakehouse）路线**：Snowflake 是"云数仓"阵营，湖仓阵营用开放表格式在对象存储上复刻本文验证过的全部要素（不可变文件+快照清单+时间旅行+统计剪枝）——可见其设计的可迁移性；两者之争随后收敛于"托管闭环 vs 开放格式"。
- **vs 执行层研究（本仓库 [../doi_10.14778_2002938.2002940/00-精读笔记.md](../doi_10.14778_2002938.2002940/00-精读笔记.md)，Neumann 2011）**：Neumann 优化"一个计划怎样跑得快"（执行骨架），Snowflake 优化"一群计划怎样在多租户云上弹性地跑"（系统形态）；二者正交，合成后二十年 OLAP 工程的两大主题。
- **vs 排序/物理布局经典（本仓库 [../doi_10.1145_191839.191884/00-精读笔记.md](../doi_10.1145_191839.191884/00-精读笔记.md)，AlphaSort 1994）**：AlphaSort 把"缓存层次"变成排序第一约束；Snowflake 的 re-clustering 则把"磁盘布局"变成可持续重写的后台作业——都是把物理设计从静态决定改为运行时策略。

## 六、批判与延伸

**批判性阅读：**

1. **论文非中立文本**：作者是厂商工程师，实验全部在自己的托管系统上做，没有第三方基准（TPC-DS 数字、与 Redshift/BigQuery 的对比均缺席）。"弹性带来成本优势"是结构论证而非度量论证。
2. **不可变重写的写放大**：UPDATE 触及某微分区即整块重写，高频小批量写入会放大存储与聚簇维护成本；论文以"批量装载 + 后台维护"回避了 OLTP 式负载的讨论。
3. **缓存冗余的隐性成本**：multi-cluster 隔离靠"N 份缓存"实现，数据量超过缓存容量、且多集群访问同一大表时，S3 重复拉取的带宽与延迟成本被弹性话术淡化。
4. **元数据服务是软核心**：全局剪枝、版本推进都压在服务层，论文未正面讨论该层的规模上限与故障域边界（后续公开演讲称其分片化演进，属论文外信息）。
5. **供应商锁定作为设计副产品**：私有文件格式使"数据可迁出但不可用"——这正是湖仓阵营攻击的靶点，也是本文历史地位的另一面：设计被开放格式全面复刻。

**延伸：**

- 与 Dremel/BigQuery 谱系对照阅读，可得"云上分析系统两条血统"：内网统一设施（Dremel→BigQuery）与公有云商品（Snowflake）；前者演化出语言与嵌套模型创新，后者演化出错峰计费、自动聚簇等产品化创新。
- "快照清单 + 不可变文件"已被 Iceberg/Delta/Hudi 标准化：本仓库 [`../../book/Use_Iceberg_with_Spark/04-时间旅行与元数据表.md`](../../book/Use_Iceberg_with_Spark/04-时间旅行与元数据表.md) 展示的元数据表/时间旅行，可视为本文存储层思想的开源实现（该链接已验证存在）。
- 后续官方论文（如 VLDB 2019 讲运维与多集群调度的 *Efficient and Scalable Query Processing on SSDs in Snowflake* 等，本笔记未核实其 DOI）继续在缓存/聚簇/伸缩上迭代；学术侧"elastic query processing"综述可作延伸阅读入口。

## 七、一页总结（复习卡）

- **问题**：云上没有既保住关系语义又彻底弹性的数仓；shared-disk 受制于对象存储语义，shared-nothing 受制于静态数据放置。
- **方案**：三层解耦；虚拟仓库（多集群共享不可变数据）；S3 微分区+列式+统计剪枝；版本化带来时间旅行/零拷贝克隆；声明式聚簇+后台重聚簇；短暂 VM+只读缓存免一致性；Dashing 自动伸缩。
- **所得**：扩缩容零数据迁移、租户级隔离、缓存无失效协议、DBA 物理设计工法被控制回路取代。
- **所欠**：写放大、缓存冗余成本、无第三方评测、私有格式锁定。
- **地位**：与 Dremel（嵌套列式交互分析）、Neumann 2011（编译执行）并列为"现代 OLAP 三篇形态论文"——本文贡献的是**系统形态**而非算法。

## 九、思考题（5 道）

1. 论文宣称"缓存不可变所以无需失效协议"。请讨论：当 S3 上某微分区因重聚簇被"替换"时，各集群缓存里的旧副本何时、凭什么作废？（提示：版本清单推进与缓存键的关系——键含文件标识则旧副本自然成垃圾，无需协议。）
2. multi-cluster shared-data 与经典 shared-disk（如 RAC）在"共享什么"上有本质区别。为什么说共享"不可变数据"可以完全免锁，而共享"可变磁盘"必须引入分布式一致性协议？
3. 微分区 + min/max 剪枝被宣传为"取消索引"。请构造一个反例查询（提示：高基数列上的等值点查、数据完全乱序且表超大），分析剪枝与 B 树/位图索引在该场景的 IO 差距，进而说明"取消索引"的隐含前提是什么。
4. 若把 Dremel 的嵌套列式分解（另一篇精读笔记）嫁接到 Snowflake 的存储层，重聚簇单元该是"记录树"还是"微分区"？两种选择对写放大与剪枝粒度各有什么影响？
5. "时间旅行 + 零拷贝克隆"本质是把备份/恢复/沙箱变成元数据操作。请从快照隔离的角度形式化：表版本清单指针的原子推进需要哪些前提，S3 的哪些语义（最终一致性窗口、rename 原子性）是这套机制的隐患，论文/产品层面用什么兜底？

## 十、阅读方法与常见误读提醒

1. **别把本文当基准测试论文读**：它的贡献在架构论证，实验是机制演示；评价弹性收益要看成本曲线而非查询延迟榜。
2. **"存算分离"不等于"随便拆"**：本文能分离是因为写路径被改造成"不可变文件+版本指针"；任何保留原地更新的系统照抄三层，会立刻撞上共享磁盘的锁问题——这正是 RAC 路线被本文超越的原因。
3. **微分区 ≠ 分区表**：微分区是物理装载产物、对用户近乎不可见；传统 range/hash 分区是逻辑设计决定、影响语义。把"取消分区设计"读成"取消分片"是常见混淆（分片职责被"任何节点可读任何块"消解）。
4. **注意行文立场**：文中对竞品路线的批评均不点名，读者应把"被批判的 shared-nothing 云数仓"理解为一种架构类型，而非某厂商现状——各竞品此后也大量吸收了本文要素。
5. **建议配套阅读**：先读 Dremel 笔记（列式+扇出的原始论证），再回看本文存储/执行两章，最后翻湖仓书第 3/5 章看这些思想在开放格式中的对应物。
