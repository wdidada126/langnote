## 一、背景与问题：从 LevelDB 到 RocksDB，问题换了

[`../doi_10.1007_s002360050048/00-精读笔记.md`](../doi_10.1007_s002360050048/00-精读笔记.md) 的 1996 年问题：**磁寻道贵 ⇒ 把随机写摊平成顺序写**。RocksDB 2013 的起点是这问题换了物理皮：

- **闪存取代磁盘**：没有寻道，但**随机小写 ⇒ FTL 内部读改写 + GC 擦除放大**，页粒度重写的伤害仍在；顺序大写的优势仍在——**LSM 骨架保留，但每一处"为 10 ms 寻道设计的常数"都要重估**。
- **LevelDB（2011）的天花板**（通说，RocksDB 立项动机）：单线程后台任务（一个 compaction + 一个 flush）在 8 核 + 数百 GB 内存 + 多盘/SSD 机器上把吞吐钉死在个位数 MB/s 量级；无多 CF 概念（HBase 式"一个宽表拆多个列族"只能开多 DB 实例）；没有 WAL 定制；写停顿（stop-the-world flush）粗暴。
- **Facebook 的需求画像**（通说，即 2013 文的场景底座）：对象存储/消息/图谱索引类负载，写远大于读、键域宽（每列族模式不同）、延迟必须平稳（tail latency 比均值重要）、单机核多内存大。

⇒ 本文的"论文问题"不是发明新结构，而是：**同一副 LSM 骨架上，哪些设计决策（并发模型、分层策略、元数据协议、键值组织）该按什么原则演化**。"Performance-centric"的确切含义：**每个特性开关都必须能用吞吐/延迟/空间/抖动四把尺子量出来**，反对当时学术界流行的"功能为中心"路线（HBase/LevelDB 皆有其功能包袱）。

## 二、核心设计精读

### 2.1 总体骨架：LevelDB 躯体的直接继承（ASCII 重绘）

```
写: Put(k,v)/Delete(k[,v]) → WAL 追加 → MemTable(跳表)
                                     │ 写满(默认64MB×max_write_buffer_number队列)
                                     ▼
                              Immutable MemTable ──flush──► L0 文件(键域重叠!)
读: GET: MemTable → L0(逐文件) → L1..L6(二分索引+Bloom) → MergeIterator 裁决新/旧/墓碑
后台: Compaction 线程池(可配 parallelism) : L0→L1(触发阈值) ; Ln→Ln+1(尺寸超限)
元数据: CURRENT → MANIFEST-x (版本编辑日志: 增删SST/水位/列族注册)
```

对照 1996 论文的三个"补票"（LevelDB 完成、RocksDB 继承再放大）：L0 重叠 = C1 的 run 序列；L1+ 不重叠 = C2..Cn 的分层下沉；Bloom+两级索引 = 新 run B-tree 索引的泛化。**RocksDB 的全部演化都发生在这张图的参数与后台协议上。**

### 2.2 列族（Column Families）——"一套 LSM 骨架的多个实例共享一个日志"（2013 同期设计增量，通说；机制以官方文档为准）

- 定义：一个 DB 内多个独立键空间，**每个 CF 有自己的 memtable、SSTable 层级、compaction 参数、块缓存配额**，但共享 WAL 与 MANIFEST：

```
DB ── WAL(1条, 全局序列号) ──► 记录带 (cf_id, seq, key, value)
   ── MANIFEST(版本编辑日志) ──► 登记每个 CF 的层级演变
   ├─ CF"a": memtable + L0..L6   (level compaction, 大值)
   └─ CF"b": memtable + L0..L2   (universal, TTL 短)
WriteBatch: 跨 CF 原子写 = 同一 WAL 记录批 ⇒ 崩溃恢复按 seq 重放
```

- 为什么这是"性能为中心"的决策而不是功能堆砌：HBase 语义上一个表多列族本同宽表，LevelDB 时代要么混在一个键空间（compaction 互相拖累）要么开 N 个 DB（WAL 翻倍、flush 翻倍、句柄爆炸）。**CF = 把"隔离调参"与"共享日志/恢复协议"拆开**：写放大按 CF 各自策略走，fsync 与恢复却只有一套——这是本笔记"参数空间演化"叙事的第一层：**隔离粒度**。
- 工程注意（文档记载）：CF 多则每个 CF 每层各持文件句柄/索引缓存，元数据成本随 CF 数涨；atomic flush（跨 CF 原子刷盘）是后来的补票。

### 2.3 两层 compaction 策略：universal vs level——三角权衡的两端旋钮

同一 LSM 分层上，"**何时合并、和谁合并**"就两个主策略（RocksDB 全部特色机制都围绕这个二选一展开）：

```
UNIVERSAL (size-tiered): 把 L0 起所有有序 run 按 年龄/尺寸比(≈2~10) 成段归并
  run: [r1][r2][r3..r7 攒够比例一起并] [R_big][R_bigger]
  写放大 ≈ O(log_ratio(总量)) 量级(低) —— 但每次大并临时需 ~2 倍空间, 尾部读要扫多个大run

LEVEL (leveled): L0→L1 小批量, Ln→Ln+1 只在层级超出 target_file_size_base×multiplier^n 时,
  每次只挑 Ln 中 1 个文件 + Ln+1 中重叠的 ~T(=10) 个文件   (fanout 固定小)
  写放大 ≈ O(T × L)（高, 每条记录在每层被重写 ~T 次）—— 但空间放大最小、点查每层至多触 1 文件
```

**取舍表（本节的"一等公民"，数字按默认配置量级定性）：**

| 维度 | Universal（size-tiered） | Level（leveled） |
|---|---|---|
| 写放大 | **低**（对数级次数） | 高（每层 ~T 倍重写，层数×扇出） |
| 空间放大 | 高（待并 run + 大并临时 ≈1.x~2x） | **低（≈1.1x）** |
| 点/范围读 | 冷数据跨多 run，读放大高 | **每层 1 次触碰，稳定** |
| 合并 I/O 突发 | 大并=大块顺序写，SSD 友好但抖动 | 小并频繁，总字节多但平滑 |
| 停顿风险 | 大并未完又攒够 → **暂停写入**(stall) | L0 文件数越限触发 slowdown，可控 |
| 适用 | 写密/读稀/日志型/空间宽裕 | 读写混合/延迟敏感/空间紧 |

- RocksDB 相对 LevelDB 的关键工程动作：universal 的**触发比例、最小合并 run 数、每层大小上限**全部可调；level 的 `target_file_size_base/multiplier、level0_slowdown/stop_trigger` 可调；**rate limiter**（`delayed_write_rate`）把合并 I/O 摊平，防 tail latency；`compaction_threads` 并行化——这些都是"骨架不动、旋钮全开"的具体形态。
- 与 1996 论文的映射：universal = 单层 C1 的"全量 k 路归并"直系；level = 多级 C2..Cn"几何下沉"直系——**LSM 谱系其实只有这一对策略双胞胎，两家系统（Cassandra=universal、HBase/LevelDB=level）各认亲一边，RocksDB 把双份都给了。**

两策略的触发规则伪码（按官方文档语义重写，参数名取默认量级示意）：

```text
# LEVEL：谁超限谁下沉，一次只碰 1+T 个文件
on_every_write_stall_check:
  if len(L0) >= level0_stop_trigger(≈24|32): PAUSE_WRITES      # 硬闸(1996 的 stall)
  if len(L0) >= level0_slowdown_trigger(≈12|16): SLOW_WRITES
  for n in 1..6:
    if size(Ln) >= target_file_size_base * multiplier^n:
       pick 1 file f in Ln;  D = {g in Ln+1 : overlap(f,g)}      # |D| ≈ fanout T≈10
       schedule(merge(f, D) -> Ln+1)                             # 每条记录在此被重写 ~T 次

# UNIVERSAL：攒够比例才动，一次可能吞掉整段历史
runs = [L0..Lk] 按年龄排序
if len(runs) >= min_merge(默认~4) 且 (最大相邻比或累计比 >= 阈值):
    D = 从最老 run 起的一段前缀
    schedule(merge_all(D) -> 新 run)      # 单次大并：临时空间≈|D|，写放大低但 I/O 突发
```

读这份伪码的姿势：LEVEL 把 1996 的"合并追不上产生"约束拆成了**高频小额分期**（平滑、总利息高）；UNIVERSAL 拆成了**低频大额整付**（总利息低、还款日抖动大）。rate limiter/停写阈值/并行度全是在给这两种还款计划装减震器。

### 2.4 WAL 与 MANIFEST：写优化引擎的"元数据账本协议"（机制以文档为准）

- **WAL**：Put/Delete 先追加写日志（可 `sync=false` 换吞吐、组提交 batch、`wal_ttl/size` 轮转）；memtable 以序列号有序跳表驻内存。**列族共享一条 WAL**——恢复 = 重放 WAL 里 `seq > manifest 记录` 的条目进各自 memtable。`disable_wal`（bulk load）给"以 SST 旁路灌数据"留了口子。
- **MANIFEST**：版本编辑（VersionEdit）追加日志——每条记录 = "CF x 的 L3 新增文件 y（键域、大小、序列号区间）/删除文件 z / 水位推进"；`CURRENT` 指针文件指向当前 MANIFEST，滚动重建（compaction 时把历史编辑物化成新 MANIFEST）。**读到的"当前树形状"= 最后一次 MANIFEST replay**，这是 1996 论文里没写、工业 LSM 必须自答的"结构本身的事务"。
- 演化看点：RocksDB 之后把 WAL 也做成可独立管理（`DBWriteBatch`、WAL 管理器与 CF 解绑的 wals 目录、2021 年起的 `wal_prefetch`），MANIFEST 的多列族膨胀问题由 `manifest_preallocation_size` 与文件热替换缓解——账本协议也在演化，不是定稿。

恢复流程伪码（文档语义，标注时间窗：骨架自 LevelDB 即有，细节历代微调）：

```text
recover(db):
    manifest = read_file(CURRENT)                  # CURRENT 只认一个 MANIFEST
    V = replay(manifest)                           # V = {每个 CF 的层级形状, 各 SST 的 seq 区间}
    for wal in sort(WAL dir):                      # 按生成序重放
        for (cf_id, seq, k, v|DEL) in wal.records:
            if seq <= V.max_flushed_seq(cf_id) : skip   # 已落盘者幂等丢弃
            V.memtables[cf_id].insert_sorted(k, v|DEL)  # 未 flush 者回灌内存
    # 语义保证：重放顺序=序列号序 ⇒ 键的可见性与崩溃前一致(新压旧、墓碑屏蔽)
```

这段账本协议回答了 1996 论文没展开的三件事：**结构本身的崩溃原子性**（VersionEdit 追加 + CURRENT 原子指针）、**跨 CF 的写序统一**（全局序列号而非每 CF 自计时钟）、**重放幂等**（`max_flushed_seq` 水位）。列族共享 WAL 的成本也藏在第四行：恢复重放是**全 CF 联合扫描**，一个 CF 的落后 flush 会拖长所有 CF 的恢复——6.1 批判 2 与思考题 1 所指的正是这笔账。

### 2.5 覆盖写与键值分离：把"墓碑"和"大值"两个放大源各自按住（**后续演化**，超出 2013 文时间窗，机制以官方文档与 TOS'21 为准）

- **覆盖写（covering tombstone）**：`Delete(k, snapshot)`——在已知"最新快照里 k 不存在"时，写一条**能屏蔽更旧快照**的墓碑。它治的是 2.2/1996 论文都提过的**删除后的范围读拖慢**（墓碑跨 run 被反复扫描）：一条强墓碑替代一串弱墓碑，读放大↓，代价是语义约束（只对无 MVCC 需求的快照安全）。TOS'21 明确把"覆盖写/单删除"列为读放大方向的设计增量。
- **BlobDB（键值分离，KV separation）**：值超过阈值（如 1KB）不进 LSM，写进独立 **blob 文件**（带 TTL/GC），SST 里只留 `BlobIndex(文件号, 偏移, 长度)`。治的是**改一列要重写整键的写放大**（宽行更新场景）：小键的 LSM 顺序合并继续便宜，大 value 的重写从 compaction 流量里摘出去。代价：点查多一跳、blob GC 另算账、范围读预取变难——**三角没消失，只是换了条边**。与 LSM 学术线的 Wacky/Monkey 同思路。

### 2.6 演化总账：同一骨架的四个参数轴（叙事收束）

| 演化阶段（通说年代） | 动的轴 | 代表决策 |
|---|---|---|
| LevelDB 2011 | 骨架定型的补票 | L0 重叠+分层不重叠、Bloom、跳表 memtable |
| **本文 2013** | **并发与资源模型** | 多线程后台池+rate limiter、写停顿分级(slowdown/stop)、(同期)CF 雏形 |
| 2014–2018 | 分层策略全可调 | universal/level 双轨旋钮、CF 级参数、atomic flush、compaction filter/TTL |
| 2016–2021 | 键值组织 | 单删除/覆盖写、MergeOperator、**BlobDB**、Direct IO+manifest 演进 |

⇒ **"设计原则的演化"的真实内容：不是改 LSM 的定义（1996 已定），而是把每一个"默认值"变成"用四把尺子（吞吐/延迟/抖动/空间）量出来的工况函数"**——这正是标题 "performance-centric design principles" 的落点。

## 三、实验与工程取舍（口径全部定性，未逐字复核 2013 原文）

- 论文体裁是**架构研讨会报告/blog view**：没有严格 benchmark 章节（通说）；其证据形态是 Facebook 生产负载（对象存储/索引类）上"逐特性开关的 A/B 与吞吐-延迟曲线"，以及相对 LevelDB 在高端多核 SSD 机器上的数量级并发优势。**具体倍数数字本笔记不引用**（见核实记录声明）。
- 可量度的公开工程事实（RocksDB 文档/基准与 TOS'21 记载，定性转述）：① 多线程 compaction/flush 把后台吞吐随核数近线性抬升直到 I/O 饱和；② universal 在纯写基准下写放大显著低于 level（对数量级 vs 层数×扇出量级）；③ BlobDB 在大值负载显著降 compaction 写流量、但点查延迟微升；④ 覆盖写/单删除改善"删除热区"的范围读。
- **本仓库视角的取舍总表**已在 2.3 给出；补一行"被放弃的选项"：RocksDB 没走 HBase 的 region 分片路线、没走 WiscKey 式纯 KV 分离为默认（BlobDB 可关）——两次"不换骨架只拧旋钮"的克制，恰是对 1996 骨架强度的最强背书。

## 六、批判与延伸

### 6.1 批判

1. **出处本身即教训**：一篇被广泛引用的"2013 RocksDB 论文"在 Crossref/OpenAlex 双双无名、vldb.org 原链 404、作者著录出现 "Siadatas" 式讹传——**架构研讨会/blog view 类文献是引用系统的暗物质**；本笔记把全部机制断言锚到可核实的 TOS'21 与官方文档，正是对此的补救。凡引本篇，请把"〇"节一起引。
2. **"演化"叙事的幸存者偏差**：报告视角天然把每个设计记成"权衡后的最优"；实际 RocksDB 历史里大量特性因测试矩阵爆炸被劝退（如早期 WAL 共享的边角崩溃、多 CF 的句柄成本），TOS'21 承认"简单性也是筛选器"——读演化史要连"没发生的设计"一起读。
3. **参数空间的代价是复杂度**：官方文档数百个调参项、universal 大并的 stall 抖动、多 CF 的恢复重放大——"全可调"把成本从引擎转嫁给运维；这与 Cassandra/HBase"一个策略拍死"的路线是另一种三角（开发成本/运维成本/性能上限）。
4. **benchmark 缺席**：作为研讨会报告它没给可复现实验（通说）；2.3 取舍表的定性数字来自文档级事实与公开基准常识，**不是论文图表**——请勿在学术引用中把它当实验论文。
5. KV 分离与 MVCC 的张力被轻描淡写：BlobDB 与覆盖写/单删除的语义交叉（blob 引用计数、GC 与快照可见性互锁）是后续多年才磨平的，2013 时间窗的"设计原则"对此应有诚实的空白标注。

### 6.2 延伸

- 反向阅读顺序：先读 [`../doi_10.1007_s002360050048/00-精读笔记.md`](../doi_10.1007_s002360050048/00-精读笔记.md) 拿骨架，再回本篇看 2.6 的四轴表——"哪个旋钮在 1996 论文里埋着"逐条可对号。
- 同一方法论的当代复刻：TiKV/RocksDB 的 raft 引擎调参、CockroachDB、MyRocks、ClickHouse 的 part-merge——universal/level 之争在每一家重新上演；Paimon 的 `num-sorted-run.stop-trigger` 与 RocksDB 的 L0 停写阈值字面同源（见互链 09 章）。
- TOS'21（DOI 核实无误）是"设计原则演化"体裁的规范版，其作者 Dong/Kryczka 是 RocksDB 后期主力贡献者，与本篇（通说 Borthakur）构成"创始期/成熟期"两封自述信。
- 介质再变（CXL 内存、ZNS SSD、Optane 退场）时，本笔记 2.3 取舍表的"SSD 友好"假设将再次成为演化对象——**三角不变，常数常新**。

### 6.3 思考题（5 道）

1. 列族共享 WAL ⇒ 一个 CF 的 flush 慢会拖累全局恢复重放（重放要跨全部 CF）。请给出"该共享"与"该解绑"各自的负载画像，并解释 TOS'21 的 WAL 管理器演化（wals 目录与 CF 解绑）动了哪侧天平。
2. universal 写放大 O(log_ratio N) vs level 的 O(T·L)：取 ratio=10、T=10、L=6，两条曲线在数据总量多大时交叉？由此推导"为什么日志型（写多读少）选 universal 而在线服务选 level"——并与 Paimon 湖上默认 leveled + full compaction 的取舍对照。
3. 覆盖写"一条强墓碑屏蔽更旧快照"要求无 MVCC 读需求。若业务同时要"快照隔离读"和"删除热区快范围扫"，只能回到单删除+KV 分离组合——请画出三种墓碑在"读放大/空间放大/GC 复杂度"三轴上的相对位置（定性即可）。
4. rate limiter 把 compaction I/O 摊平到固定带宽 B。设写入速率 R、level 策略写放大 WA：给出 B 与 WA、R 的不等式使系统不进入 stall，再论证"为什么突发写（R 瞬时 2×）比持续写更容易击穿该约束"（提示：universal 大并的原子性）。
5. 1996 论文的"merge 耗时 < t"约束，在 RocksDB 里被拆成哪三个可配阈值（L0 文件数 slowdown/stop、pending-compaction-bytes、待并 run 比）？各治哪种病？这与 1996 思考题 1 的"拆两级"方案在机制上等价吗？

## 八、阅读方法与常见误读提醒

1. **先分清"哪句有锚"**：本篇每个机制句都标了三档来源之一——"2013 文（通说）"/"官方文档（可核）"/"TOS'21（DOI 已核）"。引用时把档位带上，尤其**不要把 2.5 的 BlobDB/覆盖写说成 2013 论文内容**（超出其时间窗，属后续演化）。
2. **别将本篇当实验论文**：体裁是架构观点报告（blog view），无 benchmark 章节（通说）；凡" RocksDB 快 LevelDB 数倍"式的数字引用应转向 TOS'21 或官方基准文档。
3. **universal≠"旧"、level≠"新"**：二者是 1996 单层/多级两兄弟，各有最优工况（2.3 表）；"默认选哪个"在 LevelDB(level)/RocksDB(level)/Cassandra(universal)/Paimon(分层) 各不同，是负载声明不是时代先进度。
4. **列族不是"多表"**：CF 是**同进程同日志的多副 LSM**，没有跨 CF 事务查询、没有二级索引；拿它当关系表用会同时踩中恢复重放与句柄成本两个坑（2.2/2.4）。
5. **配套**：读骨架回 [`../doi_10.1007_s002360050048/00-精读笔记.md`](../doi_10.1007_s002360050048/00-精读笔记.md)；读实现回 [`../../book/精通LevelDB.md`](../../book/精通LevelDB.md)；读上湖形态读 Paimon [`02`](../../book/Apache_Paimon_Streaming_Lakehouse/02-核心数据结构LSM树与主键表.md)/[`09`](../../book/Apache_Paimon_Streaming_Lakehouse/09-Compaction与删除向量.md)；读同代平行演化读 [`../spanner_2012_osdi/00-精读笔记.md`](../spanner_2012_osdi/00-精读笔记.md)。

## 九、一页总结（复习卡）

- **问题**：1996 骨架在闪存多核时代全面重估——寻道没了但 FTL/GC 重写仍在，LevelDB 的单线程后台与"一 DB 一策略"撑不住 Facebook 的写密集、宽键空间、尾延迟敏感负载。
- **方案**：骨架不动，参数空间全开——① 并发模型：多线程后台池 + rate limiter + 分级写停顿；② 隔离粒度：列族（独立 memtable/层级/策略，共享 WAL+MANIFEST 账本协议）；③ 分层策略双轨：universal（写放大低、空间与尾延迟贵）vs level（读稳、空间省、写贵）；④ 键值组织（后续）：覆盖写/单删除按住墓碑读放大、BlobDB 按住大值写放大。
- **所得**：同一 LSM 定义下吞吐/延迟/抖动/空间四尺可量化的工程谱系，成为 TiKV/Cockroach/MyRocks/Paimon 们的公共底座。
- **所欠**：出处书目系统无名（本篇自身即文献学标本）；无严格实验；复杂度转嫁运维；KV 分离×快照语义多年才磨平。
- **位置**：LSM 谱系的"躯干期"——1996 定骨（论文笔记互链），2011/2013 长肉（LevelDB→RocksDB），2021 自述成史（TOS'21，DOI 已核），2020s 上湖（Paimon/Delta 互链）。
