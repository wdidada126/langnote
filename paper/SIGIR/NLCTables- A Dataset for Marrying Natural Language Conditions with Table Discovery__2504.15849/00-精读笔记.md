## 一句话总结
表发现（table discovery）原来主要靠「给一张查询表或几个模糊关键词」来捞表，结果还得人肉筛；NLCTables 提了个新任务 nlcTD——让用户用「一张查询表 + 一段自然语言条件（NL）」一起精筛，并造了含 627 条多样查询（NL-only / union / join / fuzzy）、22080 张候选表、21200 条相关性标注的基准；评测 6 个 SOTA 方法暴露了巨大差距。

## 0. 给新手的阅读前置（背景知识地图）
- **子方向解决什么大问题**：企业/数据湖里有成千上万张表，要做分析先得「找到相关的表」（table discovery / 表发现）。传统方法给一张表或几个关键词就返回一堆候选，用户还得自己筛。
- **为什么难**：单靠表或关键词太粗；用户真正想要的是「在 A 表基础上，满足某自然语言条件（如『只要 2020 年以后的』『能和 B 表 join 的』）的表」，这种「表 + NL 条件」组合检索此前没人系统研究。
- **几类主流解法**：

| 方法 | 思路 | 优缺点 |
|------|------|--------|
| 表相似/union 搜索 | 按列相似找可并表 | 常见但粗 |
| 关键词检索 | 几个词捞表 | 简单但不准 |
| 本文 nlcTD | 查询表 + NL 条件联合精筛 | 更贴合需求但更难 |

- **本文属哪类**：表发现（table discovery）任务与基准创新，属数据集成/数据湖治理。
- **2-3 个必懂关键名词**：
  - **table discovery（表发现）**：从表集合中找出与需求相关的表。
  - **nlcTD（NL-conditional table discovery）**：本文提出的新任务——查询表 + 自然语言条件共同约束。
  - **union / join 条件**：「把结构相似的表合并」或「能按键连起来的表」两类典型 NL 条件。

## 1. 问题背景与动机
- 前人工作简述：现有表发现方法主要基于查询表或模糊关键词检索，返回大结果集让用户手筛。
- 前人缺陷/未解决问题（逐条）：
  1. **检索粒度粗**：仅靠查询表/关键词，无法满足「带自然语言细化条件」的精确需求。
  2. **缺任务与数据**：没有把「表 + NL 条件」结合的任务定义与基准。

## 2. 核心方法
- **最直观类比**：找人介绍对象，旧方法是「给张照片 + 几个词」返回一堆人；新方法是「给张照片 + 一句『要爱运动的、能聊得来的』」，更精准地筛。
- **具体做法（输入 → 关键操作 → 输出）**：
  1. **定义 nlcTD 任务**：输入 = 一张查询表 + 一段 NL 条件；输出 = 满足条件的相关表。
  2. **构建 nlcTables 基准**：涵盖 NL-only、union、join、fuzzy 四类条件，共 627 条查询、22080 张候选表、21200 条相关性标注。
  3. **评测 6 个 SOTA**：在基准上跑现有表发现方法，暴露差距。
  - 输出：任务定义 + 大规模基准 + 评测结论。
- **形式化要点**：核心是「查询表 ⊗ NL 条件」的联合相关性判定；四类条件覆盖典型细化语义（🔧 标注与判定准则以论文为准）。
- **理论性质/保证**：数据集/基准论文，无理论保证。
