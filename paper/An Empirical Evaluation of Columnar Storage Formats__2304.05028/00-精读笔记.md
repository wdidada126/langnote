## 0. 给新手的阅读前置（背景知识地图）

- **子方向解决什么大问题**：分析型数据库（OLAP）常常「只查几列、但要扫几百万行」。如果按行存，就得把整行都读进来；**列存（columnar storage）** 把同一列的数据挨在一起存，只读需要的列、还能按列压缩，省 IO 又省空间。
- **为什么难**：列存格式要在「压缩率」「解码速度」「随机跳过能力」「跨平台兼容」之间做权衡。格式定下来后，各种系统都依赖它（Parquet / ORC 几乎成了事实标准），改起来牵一发动全身。
- **几类主流解法（表格）**：

  | 格式 / 思路 | 特点 | 与本文关系 |
  |------------|------|-----------|
  | Parquet | 起源于 Hadoop 生态的列式格式，嵌套数据支持好 | 本文两大被评测对象之一 |
  | ORC | Hive 生态的列存格式，统计信息丰富 | 本文两大被评测对象之一 |
  | 行存（对照） | 按行连续存，事务型（OLTP）友好 | 作为列存的反面参照 |

- **本文属哪类**：本文是**实证评测（empirical evaluation）**——深挖 Parquet / ORC 内部实现，用自研 benchmark 在不同负载下压测，给出「哪些设计决策对现代硬件友好」的建议。
- **2-3 个关键名词直觉解释**：
  - **列存（columnar / column store）**：同一列的值连续存放，利于压缩和只读取需要的列。
  - **字典编码（dictionary encoding）**：把重复出现的字符串 / 值用「编号」代替，既省空间又加快比较（如 `SELECT * WHERE city='Beijing'` 直接比对编号）。
  - **块压缩（block compression）**：把一连串数据块整体压缩（如 snappy / zstd）；压缩率高但随机访问要整块解压。
  - **谓词下推 / 辅助数据结构**：格式里存的最小值 / 最大值等统计，让引擎能跳过整块不相关的数据（min-max 索引之类）。

## 1. 问题背景与动机

- **前人工作简述**：现代数据分析系统几乎都支持 Parquet / ORC 等开源列存格式以便跨平台共享数据；也有很多 DBMS 有自家专有格式。
- **前人 N 个缺陷 / 未解决问题（逐条）**：
  1. Parquet 与 ORC **诞生于 2010 年代初、为 Hadoop 生态设计**，距今已「超过十年」；而此后**硬件（更大内存、更快 SSD/NVMe、GPU）和工作负载（机器学习）都已大变**，老格式是否还合身没人系统验证过。
  2. 此前缺乏一个**深入格式内部、可灵活配置工作负载**的 benchmark，来公平比较不同设计决策在现代环境下的取舍。
  3. 新兴负载（如 ML 预处理、GPU 解码）对列存提出了老格式没考虑过的新要求。

## 2. 核心方法

- **最直观类比**：像把两款卖了近十年的「国民级」压缩收纳箱拆开，按今天的生活场景（大房子、搬家频繁、要用机器分拣）重新称重、测容量，告诉你「哪些隔层设计该保留、哪些该改」。
- **具体做法（输入 → 关键操作 → 输出）**：
  - **输入**：Parquet 与 ORC 两种格式，配合多种工作负载配置（数据分布、列类型、读写模式等）。
  - **关键操作**：深入格式内部（编码方式、压缩、统计信息、存储布局），设计一套 benchmark 在不同配置下**压测「性能」与「空间效率」**。输出：从全面评测中提炼出对现代硬件和真实数据分布**有利的设计决策**，并指出老格式在 ML / GPU 场景的低效之处。
- **形式化要点 / 提炼的设计建议（均来自摘要，已核实）**：
  - 默认就开启**字典编码**（dictionary encoding by default）；
  - 整数编码算法应**偏向解码速度而非压缩率**（favoring decoding speed over compression ratio）；
  - 让**块压缩变成可选项**（making block compression optional）；
  - **嵌入更细粒度的辅助数据结构**（finer-grained auxiliary data structures）。
  - 同时指出：在处理常见 **ML 工作负载** 和用 **GPU 解码** 时，现有格式设计存在低效。
- **理论性质 / 保证**：本文为实证论文，不证明算法性质；其价值在于「用受控实验把经验性设计建议坐实」。
