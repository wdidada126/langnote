## Redis常见的数据结构？

String、Hash、List、Set、SortedSet。

### 1.String 字符串类型

是redis中最基本的数据类型，一个key对应一个value。
    
String类型是二进制安全的，意思是 redis 的 string 可以包含任何数据。如数字，字符串，jpg图片或者序列化的对象。

实战场景：

1. 缓存： 经典使用场景，把常用信息，字符串，图片或者视频等信息放到redis中，redis作为缓存层，mysql做持久化层，降低mysql的读写压力。
2. 计数器：redis是单线程模型，一个命令执行完才会执行下一个，同时数据可以一步落地到其他的数据源。
3. session：常见方案spring session + redis实现session共享

### 2.Hash （哈希）

是一个Mapmap，指值本身又是一种键值对结构，如 value={{field1,value1},......fieldN,valueN}}

![](../images/1289934-20190621232209365-1000366002.png)

实战场景：

1.缓存： 能直观，相比string更节省空间，的维护缓存信息，如用户信息，视频信息等。

###  3.链表
 
List 说白了就是链表（redis 使用双端链表实现的 List），是有序的，value可以重复，可以通过下标取出对应的value值，左右两边都能进行插入和删除数据。

![](../images/1289934-20190621233618769-504231907.png)

使用列表的技巧

- lpush+lpop=Stack(栈)
- lpush+rpop=Queue（队列）
- lpush+ltrim=Capped Collection（有限集合）
- lpush+brpop=Message Queue（消息队列）

实战场景：

1.timeline：例如微博的时间轴，有人发布微博，用lpush加入时间轴，展示新的列表信息。

### 4.Set   集合

集合类型也是用来保存多个字符串的元素，但和列表不同的是集合中  1. 不允许有重复的元素，2.集合中的元素是无序的，不能通过索引下标获取元素，3.支持集合间的操作，可以取多个集合取交集、并集、差集。


![](../images/1289934-20190622001013515-677922001.png)

实战场景;

1. 标签（tag）,给用户添加标签，或者用户给消息添加标签，这样有同一标签或者类似标签的可以给推荐关注的事或者关注的人。
2. 点赞，或点踩，收藏等，可以放到set中实现

### 5.zset  有序集合

有序集合和集合有着必然的联系，保留了集合不能有重复成员的特性，区别是，有序集合中的元素是可以排序的，它给每个元素设置一个分数，作为排序的依据。

（有序集合中的元素不可以重复，但是score 分数 可以重复，就和一个班里的同学学号不能重复，但考试成绩可以相同）。


![](../images/1289934-20190622000959260-539243592.png)

实战场景：

1. 排行榜：有序集合经典使用场景。例如小说视频等网站需要对用户上传的小说视频做排行榜，榜单可以按照用户关注数，更新时间，字数等打分，做排行。


## 统一对象模型
Redis 的统一对象模型，可以理解为它为了高效管理不同数据类型，而构建的一个“万能容器”。它没有直接使用底层的 SDS、字典等数据结构，而是对这些结构做了一层封装，这个封装就是 `redisObject` 结构体。

它的设计解决了两个核心问题：一是如何统一地表示和处理字符串、列表、哈希等不同类型的数据；二是如何让每种数据类型，能根据场景灵活地选用最高效的底层实现，从而在性能和内存占用之间取得平衡。

### 核心结构：`redisObject`

每个存储在Redis中的键（Key）和值（Value），最终都会以 `redisObject` 的形式存在。它的核心字段共同描述了“这是什么数据，以及数据在哪”。

```c
typedef struct redisObject {
    unsigned type:4;        // 对象的数据类型，如 OBJ_STRING, OBJ_LIST
    unsigned encoding:4;    // 对象的底层编码，如 OBJ_ENCODING_INT, OBJ_ENCODING_QUICKLIST
    unsigned lru:LRU_BITS;  // 用于记录对象的访问信息，服务于内存淘汰策略
    int refcount;           // 引用计数，用于内存回收和对象共享
    void *ptr;              // 指向真正存储数据的底层数据结构的指针
} robj;
```

### 两大核心机制

1.  类型多态与命令检查：`type` 字段让Redis在执行命令前，能快速检查键的值对象是否支持该命令。比如对一个字符串键执行 `LPOP`，Redis会通过检查 `type` 发现类型不匹配，直接返回错误，保证了操作的安全性。

2.  编码多态与内存优化：`encoding` 字段是统一对象模型实现“一类型、多实现”的关键。它允许同一种数据类型，在不同的场景下使用不同的底层数据结构。
    *   String：可能会用 `int`（整数）、`embstr`（短字符串，≤44字节）、`raw`（长字符串）三种编码。
    *   List：早期用压缩列表（ziplist）和双端链表，现在主要用快速列表（quicklist）。
    *   Hash/Set/ZSet：在元素数量少、体积小时，会使用内存效率极高的压缩列表（ziplist）或整数集合（intset）；当数据量增长后，则会自动转换为哈希表（dict）或跳跃表（skiplist）以保证性能。

这种设计让编码方式（`encoding`）对外是完全透明的，我们操作数据时无需关心内部实现，Redis会自动选择最优方案。

### 设计带来的好处

*   内存优化：对小数据量使用压缩结构，可极大节省内存。
*   灵活扩展：增加新的数据类型或优化现有编码，不会影响整个系统。
*   执行效率：通过类型和编码的双重检查，实现了类似“多态”的效果，让命令执行更加精准高效。

结合你正在规划的项目，这个统一对象模型正是支持你在“P1 核心语义”阶段实现“WRONGTYPE 检查”和“通用 DEL/EXISTS/TYPE 命令”的底层基石。


## 内置数据结构

基于你的发散，Redis内部的底层数据结构（也就是编码方式 `encoding`）主要可以归纳为以下 8 种。正是这些结构在`redisObject`中的灵活组合，才实现了你说的“一类型，多实现”。

我把它们的核心特点和主要应用场景整理成了一个清单，方便你对照查看：

### Redis 内部数据结构一览

| 数据结构 | 核心特点与设计目的 | 主要应用场景（数据类型） |
| :--- | :--- | :--- |
| SDS (简单动态字符串) | Redis自定义的字符串实现，二进制安全，能O(1)获取长度，并自动扩容，避免缓冲区溢出。 | String类型的底层实现，以及所有键（Key）的存储。 |
| Dict (字典/哈希表) | 高性能的键值对映射结构，是Redis实现快速查找的基石。 | Hash类型（数据量大时）、Set类型（数据量大时），以及整个Redis的键空间。 |
| Ziplist (压缩列表) | 为节省内存而设计的紧凑型顺序结构，所有数据连续存储。但更新时可能引发“级联更新”，有一定性能开销。 | 元素较少且每个元素较小时，作为Hash、List、ZSet的底层编码（Redis 7.0前）。 |
| Intset (整数集合) | 专为存储整数而设计的有序数组，查找快速且内存占用极低。 | Set类型，当所有元素都是整数且数量较少时。 |
| Listpack | 作为Ziplist的升级替代品，同样紧凑高效，但解决了“级联更新”的问题，性能更稳定。 | Redis 7.0+ 中，用于替代Ziplist，作为Hash、ZSet等类型在小数据量时的底层编码。 |
| Quicklist (快速列表) | List类型的“终极”实现。它是一个双向链表，但每个节点存储的是一段Ziplist或Listpack，兼顾了内存效率和访问性能。 | List类型（Redis 3.2+ 至今）。 |
| SkipList (跳跃表) | 一种有序的链表，通过多层索引实现了约 O(logN) 的查询、插入和删除效率。 | ZSet (有序集合) 类型，与Dict配合使用，保证了按分数（Score）排序和范围查询的高效。 |
| Embstr (嵌入式字符串) | 这是SDS的一种优化编码方式，将`redisObject`和SDS数据存储在一块连续的内存中，减少了内存分配次数和指针开销。 | String类型，当字符串长度较短（通常≤44字节）时使用。 |

### 一些关键细节

*   编码是动态转换的：Redis会根据数据大小和元素数量自动、透明地切换编码，在内存效率和性能之间取得平衡。例如，当你的Set中所有元素都是整数且个数超过`set-max-intset-entries`（默认512）时，编码就会从`Intset`自动升级为`Dict`。
*   版本演进：Redis的数据结构实现也在不断优化。例如，3.2版本后用`Quicklist`替代了`Ziplist`和`LinkedList`作为List的唯一实现；7.0版本后又引入`Listpack`来全面取代`Ziplist`，以避免其级联更新的性能隐患。
